## 背景

OpenClaw 的 cron 任务是很多自动化工作流的地基：每天汇总 issue、定时巡检日志、周期性同步数据源。社区里反复出现同一类现象——同一个任务在聊天里让 agent 做一次效果不错，挂到 cron 上跑几天就跑偏：要么每次推一堆没营养的消息，要么悄悄漏掉关键动作。

问题通常不在模型，而在 instruction 的写法。多数人把 cron instruction 当成聊天 prompt 来写，这是第一个误区。

## Cron 和对话的三点本质差异

1. **无人值守**：触发时没人在场澄清歧义，指令里模糊的地方不会被追问，只会被执行错。
2. **会话隔离**：每次触发往往是新上下文，上一轮做了什么、发现了什么，agent 默认不知道。
3. **成本乘以频率**：一句模糊指令每小时跑一次，浪费也是乘以 24 的。

理解这三点，写法就清楚了：cron instruction 不是对话，而是一份交给模型执行的小型 runbook。

## 做法：六段式模板

我现在的 cron instruction 基本固定六个部分：

1. **任务身份与时间语义**：第一行说明这是什么任务，时间范围写死（如“过去 24 小时”并注明时区），不用“今天”“最近”。
2. **数据来源与工具边界**：允许访问哪些文件 / URL / MCP 工具，白名单写清楚，禁止自由发挥。
3. **判定规则**：什么算“有事”。这是最常被省略的一段，也是消息轰炸的根源。
4. **输出契约**：结果写到哪里、什么格式、什么条件下静默。核心一条——**无事不发消息**。
5. **异常处理**：工具调用失败重试几次，仍失败是写日志还是告警，别让 agent 自己决定。
6. **状态记录**：处理过的条目写入状态文件，下次跳过，保证幂等。

对比一下。

反例：

> 每天早上帮我看一下仓库的新 issue，有问题告诉我。

改后（简化版）：

```text
任务：检查 X 仓库过去 24 小时（UTC+8）新开且带 bug 标签的 issue。
来源：仅通过 GitHub MCP 工具读取，不浏览其他页面。
输出：仅存在未处理 issue 时发消息，每条含标题、链接、一句话摘要；无则不发任何消息。
异常：API 失败重试 1 次，仍失败则向 logs/check.log 追加一行错误，不发消息。
状态：已处理的 issue 编号追加到 state/issues.json，已存在的跳过。
```

## 踩坑点

- **相对时间词**：“今天”“最近”是最常见的事故源，服务器时区和你想的可能不一致。
- **假设有记忆**：“接着上次的继续”这种写法在 cron 里基本必挂，状态必须落盘。
- **塞人设和语气要求**：“你是一个资深的……”这类内容只会稀释关键指令，runbook 不需要人设。
- **没有静默规则**：agent 默认倾向“汇报点什么”，不写明无事不发，你就会每天收到 24 条“一切正常”。
- **一个 instruction 塞多个任务**：改一个判定规则就得重测整个任务，拆开。
- **上线即放开通知**：先手动触发、dry-run 几天，输出落文件，确认稳定再推消息。

## 可复用建议

- 一句口诀：**cron 管时间，instruction 管逻辑**。调度器决定什么时候跑，instruction 只回答“跑的时候做什么”。
- instruction 存文件、进 git，像代码一样 review 和回滚。
- 输出永远先落文件，推送只是文件之上的一个动作。
- 每条 cron 配一个手动触发入口，改完先跑一遍，再等下一次定时触发。

## 总结

Cron instruction 的本质，是把一次成功的交互压缩成一份无人监督时也能稳定执行的说明书。时间交给调度器，判定、输出、异常、状态写进 instruction，你的 agent 才算真的在“值班”，而不是每天定时上线表演一次。
