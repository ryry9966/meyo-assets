## 背景

OpenClaw 装好后，多数人的默认姿势是挂一个主力云端模型，所有请求全量走 API。跑上一两周就会遇到两个现实问题：一是账单涨得比预期快——摘要、分类、格式转换这类“不贵”的任务也在稳定烧 token；二是有部分内容本来就不想出本地：私人日志、内部代码片段、聊天记录。本地模型恰好能补这一块，于是问题变成了怎么分。

## 问题

路由的核心不是“哪个模型更强”，而是“这个任务到底需要什么能力”。我实际用的判断标准只有三条：

1. 涉及工具调用、多步推理、agent 编排 → 云端旗舰模型；
2. 输入含隐私内容，且任务本身简单 → 本地模型；
3. 需要稳定的长上下文 → 云端（本地小模型上下文一长就容易截断、丢信息）。

## 做法

分四步走：

**1. 先盘点任务，再定规则。** 把 OpenClaw 里跑的 skill 和自动化流程列成表，标注复杂度和数据敏感度。我的结论：定时摘要、RSS 过滤、日志归档这类可以下沉到本地；写代码、联网整合回答、需要稳定 tool call 的流程留在云端。

**2. 本地起一个“够用”的模型。** Ollama 跑个 7B~14B 的指令模型即可，别一上来就追大参数。在 OpenClaw 侧配成独立的模型 ID，和主力模型分开管理，方便分别看用量。

**3. 按入口路由，而不是按消息路由。** 在 skill / agent / channel 级别直接指定模型，比在对话中途切换稳定得多：定时任务类 skill 全部指向本地，交互式对话默认走云端。确实需要内容级分流时，用一个前置分类步骤——本地模型输出路由标签，再由脚本把任务派给对应模型，避免主模型自己“决定”路由导致行为不可复现。

**4. 配回退链 + 记数据。** 主力 → 备用云端 → 本地，保证限流或断网时 agent 不至于瘫掉。同时记录每次调用的模型、延迟和 token 数，跑一周，数据会告诉你规则该往哪边调。

## 踩坑点

- **本地模型工具调用不可靠。** 小模型经常不发起 tool call 或参数填错，agent 直接空转循环。凡是涉及工具的 skill，别放本地。
- **结构化输出不稳。** 本地模型生成 JSON 需要强制 schema 校验加重试，否则下游解析悄悄失败。
- **显存冲突。** 本地 LLM 和 Whisper/TTS 抢同一张卡，路由生效后整体延迟反而变差，注意错峰或用量化 CPU 跑。
- **回退抖动。** 本地模型响应快但质量明显差，用户感知是“AI 变笨了”。回退条件要保守，宁可偶发失败也别频繁横跳。

## 可复用建议

- 默认全走云端，拿任务清单逐项下沉到本地，而不是反过来先本地再补救；
- 路由粒度选 skill / agent 级，内容级分流只用于隐私场景；
- 每条路由规则设预算上限，超额自动降级到便宜链路；
- 保留一条“全本地降级链路”，定期演练，别等云端挂了才发现本地配置早就过期。

## 总结

多模型路由的价值不在省钱本身，而在于让敏感数据有处可去、让简单任务不占用昂贵额度。先用一周的真实日志摸清任务分布，再定路由规则，比一开始就写一套复杂策略靠谱得多。规则越简单，半年后还敢改的人才越多。
