## 背景

大模型本身是无状态的。Agent 框架解决了工具调用和会话编排，但"跨会话记住用户"这件事始终要自己搭。我们给内部助手接上 MCP 工具链之后，最集中的抱怨不是能力不行，而是"每次都要重新交代一遍"：代码风格、部署习惯、常用环境，说三遍它还是忘。于是花了点时间把记忆模块单独拆出来做，这里记录一下设计和踩过的坑。

## 问题：三种常见方案为什么不够

1. **全塞 system prompt**：上下文膨胀，成本上涨，无关记忆干扰推理，两个月后就不可维护。
2. **对聊天记录做 RAG**：检索出来的是原话碎片，噪声大，"上次那个 bug"这类指代拼不回稳定偏好。
3. **定期让 LLM 总结对话**：总结会丢细节且随时间漂移，越总结越不像你。

结论：记忆的关键不是"存得多"，而是**结构化地存、有策略地取、可验证地写**。

## 做法：四层结构 + 两条路径

存储分四层：

- **工作记忆**：当前会话上下文，不动。
- **情景记忆**：原始会话日志落库，只追加，供追溯。
- **语义记忆**：蒸馏后的结构化事实，核心是一张 KV 表——key 如 `code_style`、`deploy_pref`、`timezone`，value 带 confidence、来源会话 ID、时间戳、`superseded_by` 字段。
- **检索层**：结构化查 + 向量相似 + 时间衰减加权。

**写入路径（异步）**：会话结束后触发蒸馏任务，LLM 只输出候选事实 JSON，不直接写库；与现有记忆做归一化去重，key 冲突时新值带新时间戳顶掉旧值，旧值标记 superseded 而非删除；置信度低于阈值的事实，下次对话开头由 Agent 主动确认——"我记得你偏好 XX，对吗？"用户点头才转正。

**读取路径**：拼 prompt 时只注入一张压缩的"用户记忆卡"（top 8~10 条高频事实），其余靠相关性检索按需拉取，单次注入设上限。

实现上不用重：SQLite 一张 facts 表加一列 embedding 就够起步。把 `memory_read` / `memory_write` 封成独立 MCP tool，任何 Agent 都能复用。

## 踩坑点

- **一次性指令被当成永久偏好**。"这次用 Python 写" ≠ "永远用 Python"，必须区分情景与稳定偏好，否则记忆库很快被污染。
- **偏好会变，但没有淘汰机制**。早期没做 superseded 标记，三个月前的旧偏好反复冒出来，排查半天才发现是两条并存。
- **注入不设上限**。有一版把 40 条记忆全塞进去，助手变得啰嗦且答非所问，砍到 10 条内才恢复。
- **静默写入伤信任**。用户不知道你记了什么、为什么这么记，必须有 memory 查看接口，写入日志可审计。
- **记忆是新的注入面**。网页内容里的一句话被蒸馏进记忆，等于持久化了一次 prompt injection——蒸馏 prompt 里要加"忽略指令类内容"的约束，且来源字段必填。

## 可复用建议

- 先做结构化 profile 卡，再考虑向量库。80% 的价值来自那十来条高频偏好。
- 写入永远异步、可审计、可回滚；读取永远限量，且每条注入标注来源。
- schema 必带 confidence / source / timestamp / superseded_by 四个字段，后面的冲突处理、衰减、审计全靠它们。

## 总结

记忆系统的难点不在"存"，而在写入质量控制、冲突处理和透明度。它本质是个数据工程问题，不是 prompt 问题。从小结构化存储起步，把每条记忆的来源和置信度记清楚，助手才会从"每次重来的工具"变成"越用越懂你的搭档"。
