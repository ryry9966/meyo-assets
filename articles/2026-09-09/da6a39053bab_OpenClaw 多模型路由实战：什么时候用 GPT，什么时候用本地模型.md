## 背景

OpenClaw 的模型接入是开放的：既可以挂 GPT 这类云端模型，也可以通过 Ollama、LM Studio 接本地模型。实际用下来，多数人会走向两个极端——要么全走云端 API，月底账单难看；要么全压本地，工具调用一塌糊涂，还以为是 Agent 逻辑写错了。多模型路由本质上不是省钱技巧，而是把「任务」和「模型能力」对齐的工程问题。

## 问题：按什么分？

我的分层原则看三条线：

1. **是否涉及工具调用链。** 凡是涉及 MCP 工具编排、多步执行的链路，用云端强模型。本地小模型的 function calling 格式稳定性普遍不行，一次 JSON 崩坏就会触发重试循环。
2. **上下文长度。** OpenClaw 的 system prompt 加上插件和 MCP 工具描述，轻松吃掉几千 token。本地 8k 窗口的模型留给对话的空间非常少，截断后表现断崖式下跌。
3. **数据敏感性。** 涉及私人笔记、本地文件内容的任务优先本地；通用问答、公开资料整理走云端。

## 做法：在 OpenClaw 里落地

- 给模型起语义化别名，比如 `main`（云端主力）、`fast`（本地小模型）、`privacy`（本地专用），配置里显式声明，不要靠 session 临时切。
- 在 agent/插件层面做静态路由：定时任务、消息分类、摘要这类固定流水线直接绑 `fast`；交互式对话和代码任务绑 `main`。
- 配置 fallback 链时把降级事件写进日志。云端超时降级到本地是合理的，但你必须知道它发生了，否则质量劣化是无感的。
- 每周看一次 token 消耗和调用分布。路由规则合不合理，数据会告诉你。

## 踩坑点

- **别用本地模型做路由判断本身。** 用小模型决定「这个任务归谁」，判断错误率会传导到全链路。要么规则写死，要么用强模型判断。
- **量化版本差异比想象中大。** 同一个本地模型，Q4 和 Q8 的工具调用成功率可能差出一截。做路由前先用固定测试集验证你实际部署的那个量化版本。
- **fallback 不是免费午餐。** 静默降级到弱模型后，输出风格和质量都会变，下游如果依赖固定格式，会连环失败。
- **隐私判断要覆盖整条链路。** 任务本体走了本地，但某个插件内部调了云端 embedding 或搜索 API，「全本地」的假设就不成立。路由前把插件的出口捋一遍。

## 可复用建议

- 维护一张「任务类型 → 模型」映射表，放进配置仓库，随代码一起 review。
- 路由规则宁粗不细。三档（云端 / 本地快 / 本地隐私）足够覆盖 90% 场景，规则越细，维护成本越高，误路由越多。
- 准备一个 20~30 条的固定评测集（含工具调用样例），每次改路由或换模型版本后跑一遍回归。
- 对本地模型保持「够用就好」的预期：它们适合分类、摘要、格式转换，别指望扛复杂推理。

## 总结

多模型路由的价值不在省钱本身，而在于让每类任务跑在能力匹配、成本合理、隐私可控的模型上。OpenClaw 的多模型接入让这件事的工程成本很低，难的是划分标准——先按「工具调用、上下文、敏感性」三条线粗分，跑起来，再用日志和评测集迭代。稳定可观测的粗路由，远好于一套没人敢动的精细规则。
