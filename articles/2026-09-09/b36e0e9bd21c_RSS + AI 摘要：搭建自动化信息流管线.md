## 背景

订阅源多了之后，RSS 阅读器从工具变成了负担。我大概订了 60+ 个源，每天未读 300+ 条，真正值得看的不到 10%。这个帖子记录一下我用 OpenClaw Agent + MCP 搭的一条自动化管线：定时抓取 RSS，LLM 摘要打分，过滤后按分级推送。思路不新，但工程细节不少，值得沉淀。

## 问题

核心诉求有三个：

1. 不要逐条读，只要摘要 + 值得读的理由；
2. 相似内容去重——一个事件往往有 N 家报道；
3. 分级处理：高分全文存档，中分进摘要列表，低分直接丢弃。

## 方案设计

整条管线分四层：

- **采集层**：定时任务触发 OpenClaw workflow，通过 fetch 类 MCP 工具拉取配置里的全部订阅源，解析出标题、链接、摘要、发布时间；
- **处理层**：对每条做正文抽取（很多源 feed 里只有 summary，需要抓原文再提取正文），然后批量交给 LLM 做摘要和 0–10 打分；
- **状态层**：SQLite 存已处理条目的内容 hash，保证幂等，支持跨天去重；
- **分发层**：按分数路由——8 分以上全文 Markdown 存进笔记库，5–7 分进每日摘要推送，5 分以下静默归档。

## 实施步骤

1. 建 YAML 格式的 feed 列表，每条源带分类标签和基础权重；
2. 写一个插件脚本注册 RSS fetch 工具，输入 URL，返回解析后的条目数组；
3. Agent 端写摘要 prompt，要求固定输出：一句话摘要、三个要点、评分、评分理由；
4. 定时任务每天早上跑一次，产出按分类分组的 Markdown 日报；
5. 日报通过 webhook 推到 IM，全文写入笔记目录。

## 踩坑点

- **RSS 里只有摘要**：约三分之一的源只有两三百字摘要，直接总结会丢关键信息。必须做正文抽取，我用 readability 类库兜底。
- **反爬与编码**：部分站点对无 UA 请求返回 403，或 gzip 解压异常。fetch 工具记得带 UA 并处理压缩头。
- **Token 成本失控**：一开始每条都过 LLM，成本不低。改成两级过滤——先用规则（关键词、来源权重）筛掉明显不相关的，再进 LLM，调用量降了约 60%。
- **去重失效**：同一事件标题各异，URL 去重没用。改为对摘要句做向量相似度，阈值 0.85 以上合并。
- **幻觉**：feed 挂了或正文抽取为空时，LLM 会硬编。加了空内容检测，抽取失败的条目直接标记"原文获取失败"，不进摘要。

## 可复用建议

- **配置驱动**：feed 列表、分数阈值、推送渠道全放配置文件，代码不动；
- **保留原始数据**：摘要可以重新生成，原文快照丢了就没了，落库前先存 raw；
- **幂等优先**：任何一步挂掉重跑都不应产生重复推送，hash 状态表是底线；
- **校准评分**：每周人工抽看被低分丢弃的条目，确认没误杀，评分标准同步写回 prompt；
- **先影子模式**：跑两周只写不推，人工核对质量后再开推送，别一上来就全自动。

## 总结

管线跑了一个多月，每天早上 10 分钟过一遍日报，信息焦虑明显下降。它不产生新信息，只是把筛选成本转移给了机器。对 OpenClaw 用户来说，RSS 是最容易上手的自动化数据源——结构化、免费、量大，很适合作为 Agent 实践的第一个真实场景。最后一条心得：管线里最贵的不是 LLM 调用，而是错误信息安静地流进你的阅读队列。
