## 背景

在 OpenClaw 这类 agent 框架里，cron 任务和传统 crontab 有本质区别：到点执行的不是一段固定脚本，而是把一段 instruction 交给 agent，由它现场决定调哪个工具、走哪条链路、怎么汇报结果。换句话说，**instruction 是一个无人值守会话的 system prompt**。

这就带来一个常被忽视的事实：instruction 的质量直接等于任务的稳定性。写得好是自动化，写得不好，每次触发都是一场随机演出。

## 问题：三类典型翻车

1. **写成聊天语气**。"帮我看看今天的日程"——"看看"是总结、是发消息还是改日程？agent 只能猜。
2. **假设有上下文**。每次触发是独立会话，你白天的对话、上次任务的结果它一概不知，但 instruction 里却写着"延续之前的思路"。
3. **没有失败路径**。数据源挂了、MCP 工具没权限时，agent 的默认倾向是给出一个"看起来合理"的结果。在定时任务里，编造比失败危险得多。

## 做法：把 instruction 当工单写

我的经验是按六段式骨架写，每段一两行：

```text
【目标】本次触发的唯一目的，一句话。
【数据】从哪获取：用哪个工具/MCP、什么参数、取不到怎么办。
【边界】只读还是可写；禁止哪些动作（如：不要主动给联系人发消息）。
【输出】发到哪个渠道；固定格式模板；长度上限。
【异常】任何一步失败时，明确要求"报告失败原因"，而不是跳过或编造。
【身份】告知 agent 这是定时任务，无人确认，副作用需谨慎。
```

举一个日报任务的实例（节选）：

```text
【目标】生成昨日仓库动态日报。
【数据】调用 github MCP 的 list_commits，repo=xxx，时间窗为过去 24h。
【输出】发送到我绑定的 Telegram：提交数 + 3 条要点，每条不超过 30 字。
【异常】API 报错或提交为 0 时，发送"今日无动态（原因）"，不要推测内容。
```

## 踩坑点

- **时区**。cron 表达式的基准时区和 agent 运行环境可能不一致，"每天 9 点"可能实际 17 点才触发。先手动触发一次看时间戳。
- **指令过载**。背景塞太多会稀释重点，核心约束（边界、输出、异常）放最前面。
- **把可变数据写死在 instruction 里**。仓库名、频道 ID 这类会变的东西，要么放配置，要么让任务运行时读取，否则每次变更都要改 prompt。
- **不指定输出渠道**。不写明发到哪，agent 会走默认行为，往往不是你要的。
- **跳过手动验证**。上线前用立即触发跑 3~5 次，对比输出是否稳定，比等真实时间点第一次翻车便宜得多。

## 可复用建议

- 心法一句话：**把 instruction 当成给外包的工单，而不是给同事的微信**。假设对方一无所知，只看这一张纸办事。
- 按任务类型沉淀模板：日报、监控、清理、提醒各留一份骨架，新任务只填空。
- 一个任务一个职责。想同时做三件事，就建三个 cron，别在一个 instruction 里排队。
- 让 agent 在输出末尾自报一行"本次调用的工具与失败项"，等于自带日志，排查问题快很多。

## 总结

cron 任务的 instruction 本质是一份无人值守的执行契约：目标唯一、来源明确、边界清晰、失败可报告。你把它写得越像规格说明，它跑得就越不像抽卡。先用手动触发验证，再交给时间。
