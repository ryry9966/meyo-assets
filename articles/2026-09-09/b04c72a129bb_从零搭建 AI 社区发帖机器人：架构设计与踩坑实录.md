## 背景

我们社区每周需要一篇技术周报帖，人工整理耗时且经常拖更。于是我用 OpenClaw 做了一个发帖机器人：定时聚合社区动态，生成周报草稿，经人工确认后自动发布。跑了一个多月，发了 6 期，中途翻车若干次，这里把架构和踩坑记录下来。

## 问题

拆下来其实是三个问题：

1. **信息聚合**：来源分散（论坛新帖、GitHub Release、群聊精选），噪声大；
2. **内容质量**：LLM 会编造链接、语气漂移，直接发出去不可接受；
3. **发布可靠性**：定时任务重试、论坛限流、重复发帖。

## 架构与做法

整体是五段式流水线，OpenClaw 作为 agent 运行时，各环节通过 MCP 工具接入：

```
fetcher(MCP) → 清洗/去重 → agent 生成 → 人工审核队列 → publisher 插件
```

- **Fetcher**：三个 MCP server 分别拉 RSS、GitHub API、论坛接口，输出统一 JSON schema；
- **清洗去重**：按 URL 哈希存入 SQLite，已见过的条目直接丢弃；
- **Agent 生成**：无状态运行，系统提示词从配置文件加载，工具返回的条目作为唯一事实来源，明确禁止模型自行补充链接；
- **审核队列**：生成的草稿先落库，我在管理页点确认才触发发布；
- **Publisher**：一个调用论坛 HTTP API 的插件，带幂等键（本期日期），重复请求会被服务端唯一约束拦下；
- **调度**：cron 触发 OpenClaw headless 运行，每次运行的输入、工具调用、产出都写 trace 日志。

## 踩坑实录

1. **模型编造链接**。第一版让模型"整理本周动态"，它凭记忆补了几个不存在的仓库地址。解法是硬约束：只能引用工具返回的 `url` 字段，发布前再对每个链接跑一次 HEAD 校验，404 直接打回。
2. **重复发帖**。发布超时后 cron 重试，导致同一期发了两遍。根因是发布操作不幂等。加上"期号唯一键 + 先查后发"之后没再复现。
3. **语气漂移**。最初把历史帖子塞进上下文"参考风格"，几期之后文风越来越油腻。改成无状态运行，风格只由版本化的系统提示词控制，上下文只放原始素材。
4. **MCP 工具超时拖垮全链路**。某个数据源挂了，整个任务卡死。给每个 MCP 调用加了独立超时，单源失败降级为"本期缺该板块"，不阻塞整体。
5. **首期就想全自动**。幸好没这么干，草稿里出现过两条不合适的内容。人工审核队列留了一个半月才逐步放开，目前仍保留抽检。
6. **token 成本失控**。一次把全部原始帖塞进上下文，单期成本翻了三倍。改为先让模型对每个来源做摘要再聚合，上下文长度稳定下来了。

## 可复用建议

- 先上**人工审核队列**，再谈全自动，审核数据反过来能帮你改进提示词；
- 一切外部写操作（发帖、评论）都按**幂等**设计，key 用业务语义（如期号）而非随机值；
- **不信任模型记忆**，所有事实性内容必须来自工具返回，并做发布前校验；
- 提示词与素材分离，提示词进版本库，改风格等于改代码；
- 每次运行留 trace，排障时比翻论坛后台快得多。

## 总结

这个项目本身不难，难的是把"模型会出错"当成默认前提来设计架构：约束事实来源、幂等发布、降级容错、保留人工闸门。机器人现在稳定产出周报，我每周的实际工作量从两小时降到十分钟审核。如果你也在用 OpenClaw 做类似的自动化，欢迎在评论区交流你的流水线设计。
