## 背景

E2E 测试是回归保障里最贵的一环：写得慢、选择器脆、UI 一改就得跟着修，团队里往往只有少数人愿意长期维护。现在 Agent 配上浏览器自动化工具（Playwright 类的 MCP 工具），让 AI 真实打开页面、观察 DOM、再生成测试成为可能。关键区别在于：不是让 AI 凭需求文档"猜"测试，而是让它基于真实页面状态写。

## 问题

两个极端都不好用：

- **纯手写**：慢，覆盖率靠自觉，维护意愿持续走低。
- **让 AI 直接生成**：选择器靠猜，跑起来要么全红，要么全绿但断言形同虚设。

我们要的是中间那条路：AI 干探索和样板的苦活，人守住审查和业务判断。

## 做法

**1. 给 Agent 挂上真实浏览器工具**
Playwright MCP 或同类插件，确保 Agent 能导航、截图、读取 accessibility tree。这是整个方案的前提。

**2. 分角色协作，别用一个 Agent 包打天下**

- **探索 Agent**：按用户旅程走一遍页面，记录关键路由、表单校验行为、边界状态；
- **生成 Agent**：基于探索记录 + 团队选择器规范生成测试代码。优先级：`data-testid` > role/label，禁止依赖动态 class；
- **审查环节**：人或审查 Agent 检查断言有效性、有没有 sleep、有没有过度 mock。

**3. 生成即验证**
测试生成后立刻在本地跑，失败的反馈给生成 Agent 迭代，最多 2-3 轮，还不行就人工接管，别恋战。

**4. 固化成可复用的工作流**
把整套流程做成 skill 或插件：输入是"页面 URL + 用户旅程描述"，输出是可运行的 spec 文件 + PR。

## 踩坑点

- **Agent 没真的打开页面就开始写**：产出全是幻觉选择器。判断方法很简单——看它是否调用了浏览器工具，没调用就打回。
- **断言注水**：生成 Agent 天然倾向堆一堆弱断言（只检查元素存在）。要求每个用例至少包含一个带业务语义的断言。
- **用 sleep 修 flaky**：明确禁止 hard wait，强制用 waitFor 类等待条件。
- **让 Agent 自己把测试改绿**：它会演变成删断言。修复必须人审，或把"变绿手段"限定在等待策略和选择器调整。
- **一次生成太多**：一次只做一个用户旅程、5-8 个用例，保持可审查的粒度。

## 可复用建议

- 选择器规范单独成文档，作为生成 Agent 系统提示的一部分，别每次口头交代；
- 探索与生成拆成两个 Agent，上下文更干净，幻觉更少；
- AI 生成的测试一律走 PR + CI，和人类代码同标准，不开后门；
- 每轮失败原因记录下来，攒成团队的 prompt 知识库，比换模型更划算。

## 总结

Agent 写 E2E 的价值不在"全自动"，而在分工：最枯燥的页面探索、样板代码、断言骨架交给机器，人保留审查权和业务判断。我们落地后的体感是，新页面补一套冒烟 E2E 从半天缩到半小时左右——前提是流程里有真实的浏览器工具，以及一道不让 AI 自己糊弄过去的审查卡点。
