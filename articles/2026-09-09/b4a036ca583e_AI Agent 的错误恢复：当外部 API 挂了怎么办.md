## 背景

Agent 的能力边界，基本等于它能调用的外部服务。LLM 本身、搜索、数据库、各种 MCP 工具——任何一环抖动，整条任务链都受影响。Demo 阶段看不出问题，一上生产就会发现：外部 API 故障不是"会不会发生"，而是"多久发生一次"。

## 问题

故障通常表现为三种：

1. **直接崩**：异常没接住，agent 循环终止，任务死在一半。
2. **疯狂重试**：429、超时被无脑 retry，token 和配额双烧，还可能触发对方更严格的限流。
3. **最隐蔽的**：工具调用失败后，模型不承认失败，自己编一个结果继续往下跑。下游拿到的是幻觉数据。

第三种最危险，因为它不报错。

## 做法

1. **错误分类**。429 / 503 / 超时 → 可重试；400 / 401 / 404 → 重试无意义，直接走降级。429 优先读 `Retry-After` 头，别自己猜。
2. **指数退避 + 抖动**。基数 1 秒，×2 递增，加随机 jitter，上限 3~5 次。避免所有实例同时重试形成风暴。
3. **熔断**。同一上游连续失败 N 次就短路一段时间，之后用 half-open 状态小流量探测恢复。
4. **结构化错误回传给模型**。不要抛完异常就完事，把类似 `{ok: false, error: "rate_limited", retryable: true}` 的 envelope 塞回 tool result，明确告诉模型"失败是事实，不要编数据"。
5. **状态持久化 + 断点恢复**。长任务每步落盘，上游恢复后从断点续跑，而不是从头重烧 token。
6. **任务级 deadline**。单次工具超时之外，给整个任务设总时限，防止"每次重试都在成功，但整体永远跑不完"。

## 踩坑点

- **非幂等操作不能盲目重试**：下单、发通知重试一次就是双倍。写操作务必带幂等键（唯一 request id）。
- **降级要有边界**：fallback 到缓存数据时要打上"过期数据"标记，否则模型会把旧数据当实时数据用。
- **熔断器不做 half-open**：上游恢复了，你的 agent 还在"罢工"，而且没人知道。
- **把原始错误堆栈丢给模型分析**：模型面对模糊错误容易做出激进决策（比如放弃整个任务或强行编造）。给结构化字段，比给一堆日志有效得多。

## 可复用建议

- 所有工具调用走统一封装层，错误 envelope 格式全局固定，别每个插件各写一套。
- 把失败处理策略写进工具描述或 system prompt：可重试的等一等，不可重试的换路径，都不行就明确报告失败——"明确失败"也是合法输出。
- 对上游失败率做监控告警，别等用户反馈才知道搜索接口挂了一上午。
- OpenClaw 生态里插件众多，建议社区约定一套通用的 retryable / fallback 语义，跨插件组合时错误行为才可预测。

## 总结

外部 API 挂了不可怕，可怕的是 agent 的三种坏反应：崩、死循环重试、编数据。错误恢复本质是工程问题而不是 prompt 问题：分类、退避、熔断、降级、断点续跑，一层层兜住。核心原则只有一条——让模型看到的永远是结构化的事实，决策逻辑交给明确的策略代码。
