## 背景

用 Agent 做自动化一段时间后，几乎都会撞到同一堵墙：单个 agent 串行处理任务时，工具输出的日志、代码片段、检索结果不断挤占上下文，跑得越久越“健忘”，而且一个长任务会卡住后面所有事。OpenClaw 的 subagent 机制提供了另一条路：主 agent 把独立任务拆给子 agent，各自跑在隔离上下文里，干完只带结论回来。听起来简单，真正用起来有不少工程细节。

## 问题拆解

我们最早想并行化的场景有三类：

- **信息收集**：同时扫多个文档和 MCP 接口，汇总成一份调研笔记
- **批量处理**：对多个文件、多个数据源做同构操作
- **探索性尝试**：让两三个子 agent 用不同思路解决同一个问题，选最好的结果

串行模式下这三类任务平均耗时 6-10 分钟，且主上下文很快被中间输出填满，后续推理质量明显下降。

## 做法

**1. 先划边界，再谈并行。** 判断标准很朴素：子任务之间是否写同一批文件、是否依赖彼此的中间结果。有共享写入的，要么按文件划分所有权，要么老老实实串行。

**2. 子任务提示词写成 mini-SOP。** 每个委派出去的任务固定四段：目标（要产出什么）、约束（不许动哪些文件、能用哪些工具）、输入（只给相关路径和关键背景，不要把主对话整个塞过去）、返回格式（结论 + 关键证据 + 遗留问题，控制在几百字内）。

**3. 返回值即契约。** 强制子 agent 只回摘要，不回完整过程。这是控制主上下文的关键：主 agent 聚合的是结论，不是日志。

**4. 并行度从 2 起步。** 主 agent 发出任务后进入等待，聚合结果、裁决冲突。我们试过 6 路并行，token 消耗和失败重试的复杂度明显上升，2-4 路是性价比区间。

## 踩坑点

- **写冲突最疼。** 两个子 agent 同时改一个文件，后写的覆盖先写的，且很难察觉。现在约定每个子 agent 只能写自己的工作目录，最后由主 agent 合并。
- **过度委派。** 有段时间什么都要开子 agent，两行的小改动也委派，结果编排开销比任务本身还大。现在的原则：预估超过 3 步工具调用、或会产生大量中间输出的，才委派。
- **上下文饥饿。** 子 agent 不知道主对话里的隐含约定（比如“这个接口要兼容旧版本”），产出方向跑偏。解法是把关键约束显式写进子任务提示词，别指望自动继承。
- **静默失败。** 子 agent 卡在循环里或提前退出，返回空结果。现在每个子任务都带超时和重试预算，失败必须显式返回原因，由主 agent 决定降级还是重派。
- **权限收敛。** 子 agent 会继承 MCP 工具权限，涉及写操作和数据导出的插件，我们单独做了只读变体给子 agent 使用。

## 可复用建议

- 一个子 agent = 一个可交付物，不做“顺便也帮我看看”
- 子任务提示词模板化，放进插件配置随取随用
- 落盘记录每个子任务的输入输出，出问题能回放
- 先串行验证任务本身正确，再并行化——并行只是加速，不修复错误

## 总结

Subagent 编排的本质不是“更多 AI”，而是隔离与并行：用上下文隔离换主 agent 的清醒，用并行换时间。它更像微服务架构在 agent 侧的投影——边界清晰、契约明确、可观测，才能稳定扩展。把子 agent 当成需要良好接口设计的同事，而不是随手甩活的黑盒，编排这件事就成功了一半。
