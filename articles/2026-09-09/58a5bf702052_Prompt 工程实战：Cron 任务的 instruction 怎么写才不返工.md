## 背景

OpenClaw 的 cron 任务本质上就一句话：**到点把一段 prompt 喂给 agent，让它在指定会话里跑一次**。配置里那段 instruction 就是任务的全部逻辑。

很多人把 cron 当"定时提醒"用，instruction 写得像给自己看的备忘录——"每天早上看下 GitHub 通知，有重要的发我"。人执行时能脑补，agent 执行时全靠猜。我最近把七八个定时任务从"偶尔能用"调到"稳定运行"，核心经验就一条：**cron instruction 是接口契约，不是备忘录**。

## 问题：三个典型翻车现场

1. **上下文断层**。cron 任务大多跑在隔离会话里，你平时和 agent 聊的偏好、项目背景统统不在场。instruction 里写"照老规矩处理"，agent 的"老规矩"和你的不是同一套。
2. **输出口径不明**。跑完发到哪个渠道、几行以内、要不要 markdown、无数据时说不说话——没写清楚就是每天抽奖。
3. **工具调用靠回忆**。不指明数据来源，模型会用训练记忆"回答"天气、新闻、仓库状态。定时任务里出现编造数据，比不执行更糟。

## 做法：一个能直接抄的结构

我把 instruction 固定成五段式：

```text
【任务】每天 09:00（Asia/Shanghai）汇总我 GitHub 上昨天的 issue 动态。
【来源】只使用 github 工具查询，禁止凭记忆回答。
【判空】查询失败或无新动态时，只回复"今日无更新"并结束，不要推测。
【输出】发送到 Telegram，正文不超过 6 行，按 仓库 / 变化 / 链接 三行一组。
【边界】只读，不允许任何写操作（close / comment 都禁止）。
```

每一段在防什么：

- **触发语境 + 时区**：让 agent 明确自己是定时触发，"今天"以哪个时区为准。
- **数据来源**：锁死工具，等于给幻觉上锁。
- **判空出口**：定时任务八成的线上事故是"数据没查到还硬编一段"，必须给它一条合法的提前退出路径。
- **输出契约**：渠道、长度、格式写死，下游（包括你自己）才好消费。
- **权限边界**：cron 是无人值守执行，只读任务就明说只读。

## 踩坑点

- **时区不一致**：cron 表达式的时区和 agent 理解的"今天"可能差一整个偏移量，instruction 里显式写，别省。
- **输出超长被截断**：消息渠道有长度限制，不限制行数，agent 会给你写小作文。
- **重跑导致重复推送**：失败后手动重跑，结果早上发两遍。要求输出带日期，发送前检查当天是否已发过。
- **一个任务干三件事**："拉数据 + 总结 + 发周报"塞一个任务，中间一步挂了全挂还难定位。拆小，用固定输出格式衔接。
- **上线前不试跑**：cron 最坑的是首次真实暴露就在生产时间的凌晨。务必手动触发跑三次，再故意断掉数据源跑一次，专门验证判空分支。

## 可复用建议

1. 把 instruction 当函数签名写：输入（来源）、处理（边界）、输出（格式），三样缺一不可。
2. 每个任务必须有判空出口和"最坏情况行为"。
3. 输出用固定模板，牺牲一点灵活性，换来的稳定性是赚的。
4. 每周看一次执行日志，把你在聊天里反复追问 agent 的问题，固化进对应任务的 instruction——日志是最好的需求来源。

## 总结

Cron 任务的稳定性，七分靠 instruction 写法，三分靠工具本身。写的时候默认对面是一个**没有上下文、无人监督、到点必须交活**的新同事：目标、来源、判空、格式、边界五段写全，大部分翻车现场就不会发生。定时化不是把 prompt 定时发出去，而是把交付标准一起定时发出去。
