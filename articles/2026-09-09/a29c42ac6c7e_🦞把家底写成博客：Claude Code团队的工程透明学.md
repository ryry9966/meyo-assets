最近一条热议把 Anthropic 的 Claude Code 团队送上了话题榜：这支团队不光做工具，还把自家内部怎么用、怎么踩坑、怎么迭代，一篇篇写成 engineering blog 公开，从 CLAUDE.md 怎么写，到 agent 怎么自证代码没问题，细节给得相当足。工程圈对这种“自曝家底”普遍叫好，但背后的门道值得拆一拆：他们到底说了什么、为什么敢说、普通开发者能捞到什么干货。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/8deda97589f36e16.png)

## 他们到底“往外说”了什么？

把官方 engineering blog 翻一遍，这波热度不是白来的：

- **设计哲学长文**：代表作《Claude Code: Best practices for agentic coding》，从工作流到权限管理，几乎是一份公开操作手册；
- **内部团队现身说法**：让自家工程团队讲怎么拿 Claude Code 写生产代码，含金量就在“真实在用”四个字上；
- **几条被反复引用的实践**：
  1. **CLAUDE.md 当持久记忆**：把项目约定、常用命令、代码风格写进一个 Markdown 文件，随代码一起演进，agent 每次开工先读它；
  2. **explore → plan → code → commit**：先让模型读代码做调研，再出方案，人工确认后才动手写，把“想清楚”和“写出来”拆成两步；
  3. **TDD 闭环**：先写测试，让 agent 跑测试、读报错、改代码，把验证做进循环里；
  4. **sub-agent 交叉审查**：一个 agent 写代码，另一个只做 review，互不通气，避免“既当运动员又当裁判”。

这套内容通常躺在大厂内部 wiki 里吃灰，他们直接挂上了官网。

## Dogfooding：天天吃自己的狗粮

“吃狗粮”（dogfooding）这个词诞生于 1980 年代：一则狗粮广告宣称高管天天喂自家产品给狗吃；后来微软开发 Windows 时要求内部团队日常使用自编译版本，把它带成了软件业黑话。

Claude Code 团队算教科书级实践者：

- 团队成员在访谈中提过，Claude Code 代码库里相当大比例的代码由 Claude 自己完成，人类工程师更多在做 review、定方向、把关架构；
- 工具每一次卡顿、每一个报错，开发团队自己第一个撞上，反馈回路被压缩到最短；
- 踩过的坑直接写成最佳实践对外发布——博客里的每条建议，背后几乎都有他们自己的真实使用场景。

这也解释了热搜里那句感慨的来源：一支天天用自家工具造自家工具的团队，分享出来的经验天然带“一线使用感”，而不是市场部门的通稿味。

## 技术干货拆解：那条简洁的 agentic loop

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/8f13cd98fbf39c5c.png)

公开材料里最值钱的其实是设计哲学，核心一句话：**做一个不做预设（unopinionated）的简单循环**——gather context（收上下文）→ take action（执行）→ verify work（验证）→ 再来一轮。

- **脚手架刻意轻薄**：不硬编码大量 workflow，把智能交给模型，把执行交给 shell。创造者 Boris Cherny 在访谈里给过一组对比：很多竞品内置了大量工作流，而 Claude Code 提供的预设功能“不到百分之一”，自由度留给用户；
- **Context engineering**：比 prompt engineering 更进一步——不只琢磨一句话怎么问，而是治理整个上下文窗口里放什么：相关文件、测试输出、项目约定，像打理花园一样定期修剪；
- **验证优先**：给 agent 配上能自我验证的工具（跑测试、跑 linter、读报错），模型看到失败信息就会自我修正，人工盯梢的成本才降得下来。

对任何做 agent 产品的团队来说，“简单循环 + 验证闭环 + 上下文治理”这三件套，比堆 prompt 技巧更接近本质。

## 为什么大多数团队不这么做？



把内部实践写成公开博客，在工程界其实是反常规操作：

- **护城河顾虑**：方法论即竞争力，很多公司宁可锁在内部 wiki；
- **安全顾虑**：公开工作流等于把攻击面一并展示，脱敏成本不低；
- **内容惯性**：多数公司博客以产品宣传为主，技术干货常常“犹抱琵琶”。

那 Claude Code 团队图什么？至少有三层商业逻辑：

1. **反馈加速**：公开等于邀请全球开发者帮你做 code review，反例和问题源源不断送上门，迭代反而更快；
2. **口碑获客**：开发者工具的客户就是开发者，一篇硬核博客的转化力胜过十支广告；
3. **生态卡位**：当“怎么用好 Claude Code”的最佳实践由官方定义，围绕它的教程、模板、培训都会反向巩固其标准地位。

所以透明不是慷慨，是精算过的策略，只不过它必须以真材实料为前提，装不出来。

## 普通开发者能带走什么？

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/17707befd61dea74.png)

把公开材料当教材读，性价比很高：

1. **先搭 CLAUDE.md**：给常用项目建一个，写清构建命令、测试命令、风格约定，agent 输出质量立刻上一个台阶；
2. **验证前置**：让 agent 动手前先写测试、动手后自己跑测试，你的角色从“逐行盯梢”变成“审核结果”，加班量肉眼可见地下降；
3. **管好上下文**：喂相关文件而非整个仓库，长对话及时收束开新会话，把 token 花在刀刃上。

## 三条冷思考



1. **透明是筛选机制**：公开内部实践会劝退只看热闹的读者，留下的是会照着做的人——对工具厂商，这批高质量用户比泛流量值钱得多。你写博客、做开源，同理。
2. **学原理，别背操作**：博客里的具体做法会随模型能力升级而失效，但“短反馈回路、验证闭环、上下文治理”这三个底层变量，很长时间内都不会过期。
3. **先测量，再借鉴**：每支团队的代码规模、遗留系统、协作方式不同，照搬大厂工作流容易水土不服。正确姿势是拿他们的框架当模板，用自己的度量数据当修正器。

热搜里那句“讲究啊”，讲究的其实不是姿态，而是一套被验证过的工程逻辑：自己天天用，用了就复盘，复盘就公开，公开换反馈。这四步对任何团队都成立，多数团队只是卡在了第二步。
