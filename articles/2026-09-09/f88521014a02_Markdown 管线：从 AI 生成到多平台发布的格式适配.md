## 背景

用 Agent 生成内容，最后一步往往不是生成，而是发布。LLM 的天然输出载体是 Markdown，但发布目标——公众号、知乎、掘金、自建博客——对格式的接受度各不相同。同一份 Markdown 直接扔到四个平台，通常会收获四场排版事故。这篇文章记录我用 OpenClaw 搭的一条适配管线，核心思路：把 Markdown 当作中间表示（IR），把平台差异收敛到独立的适配层。

## 问题

- 公众号编辑器不认 Markdown，只收内联样式的 HTML，还会剥掉 `<style>` 标签和大部分外链；
- 表格、脚注、任务列表等 GFM 扩展，各平台支持参差不齐；
- 图片相对路径出了本地即失效，需要转存图床并重写 URL；
- 移动端表格和代码块普遍横向溢出；
- 更麻烦的是 LLM 输出本身不稳定：嵌套列表错位、代码围栏未闭合、Markdown 里混入 HTML，用正则处理很容易在代码块内部误伤。

## 做法

管线分五步，所有转换写在代码里，不靠 prompt：

1. **归一化**：用 unified/remark 把原始输出解析成 mdast，统一换行、列表缩进、围栏闭合。解析失败就直接报错，不做字符串修补。
2. **校验**：对 AST 做 lint——标题是否跳级、图片链接是否可解析、代码块语言标记是否缺失。这一步封装成 MCP tool，让 Agent 在发布前自检。
3. **资产处理**：图片转存对象存储，重写 URL，压缩到平台限制内。
4. **平台适配器**：每个平台一个 transform 插件。公众号适配器把节点树渲染为内联样式 HTML；掘金/知乎基本透传，只降级不支持的语法（如脚注转文末引用）；博客走主题渲染。
5. **预览与发布**：每个目标先生成渲染结果，diff 确认后再调用发布接口。发布动作同样封装为 MCP tool，签名类似 `publish(target, content_id)`。

关键原则：适配过程中**绝不让 LLM 重新生成内容**，只做确定性转换。

## 踩坑点

- 早期在 prompt 里要求“输出适合公众号的格式”，效果时好时坏。格式约束放进 prompt 天然不可靠，该代码做的事交给代码。
- 用正则处理 Markdown，遇到代码块内含 `#` 或 `---` 必炸。一切基于 AST。
- remark 和 markdown-it 对 footnotes、task list 的解析行为不一致，适配器测试要锁定解析器版本。
- 公众号粘贴时行高字号会被编辑器二次处理，内联样式要把 `line-height`、`font-size` 全部写死。
- 图片重传后压缩有损，重要截图保留原图 URL 备查。

## 可复用建议

- **单一事实源**：一份 Markdown + frontmatter 元数据，各平台版本都是构建产物，随时可重建；
- 适配器做成插件，配快照测试，fixture 用最小复现样例；
- 每个平台维护一张格式清单（支持什么、会剥什么），踩一次坑记一条；
- 转换保持幂等，输出带构建日志，方便回滚定位；
- 预览环节不要省，diff 是最后一道防线。

## 总结

这条管线的本质是把“格式适配”从生成环节剥离：LLM 负责内容，代码负责结构转换，MCP 把发布动作暴露给 Agent。搭好之后，新增平台的成本就是写一个 transform 插件加一张格式清单，内容侧完全无感。
