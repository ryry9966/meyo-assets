## 背景

用 Agent 写技术内容已经不是新鲜事：在 OpenClaw 的工作流里，让模型产出一份 Markdown 初稿，人工审校后发到公众号、静态博客（Hugo/VitePress）、掘金或知乎，是常见链路。实际做下来会发现，工作量不在生成，而在"同一份内容、多套格式约束"的落地。

## 问题

碎片化来自两层：

1. **AI 产出不规范**：标题层级跳跃（H1 直接跳 H4）、`*` 和 `_` 混用、夹带 `<u>`、`<sub>` 这类内联 HTML、脚注语法 `[^1]`、超宽表格、frontmatter 混在正文里。单平台看没问题，跨平台一发布就炸。
2. **平台渲染不一致**：公众号不认 Markdown，要转内联样式的 HTML，且对外链图片有防盗链；掘金、知乎对 GFM 的支持程度不一；静态站要处理 frontmatter 和图片路径。每个平台手工排一遍版，不可维护。

## 做法

核心原则：**一份规范源（canonical Markdown），多个纯函数适配器**。

**第一步：定义规范源。** 全文只允许一个 H1；代码块必须标注语言；图片统一放 `assets/` 相对路径；标题、摘要、标签、各平台专属字段全部收敛到 frontmatter，正文零平台痕迹。

**第二步：归一化。** 用 mdformat 或 prettier 固定配置统一格式，markdownlint 做规则检查（标题层级、禁裸 HTML、代码块语言）。这一步封装成 MCP 工具暴露给 Agent，比如 `md.normalize`，模型写完自己先跑一遍，而不是等人眼兜底。

**第三步：AST 级转换，别用正则。** 用 remark/mdast 解析成语法树再改写。典型规则：`[^1]` 降级为行内括号；裸 HTML 剥离；表格超过 3 列降级为列表；嵌在列表里的代码块提取到顶层。

**第四步：目标适配器。** 每个平台一个纯函数：输入规范文档，输出平台格式。公众号走 renderer 输出内联 CSS 的 HTML；静态站直出 MD，只重写图片路径；掘金基本直出，处理个别扩展语法。

**第五步：图片管线。** 单独抽象：本地路径转平台 URL，公众号先传素材库再替换链接，补齐 alt 文本。图片是跨平台最容易断的一环。

**第六步：golden file 快照。** 每个适配器留一组输入/期望输出，改动转换规则时跑 diff，防止"顺手优化"悄悄改坏某平台的排版。

## 踩坑点

- 公众号 HTML 走白名单，`class` 直接无效，`style` 之外的属性基本被剥，内联样式要写全。
- 微信图片防盗链：外链图在编辑器里正常，发布后裂图，必须传素材库。
- frontmatter 忘了剥离就发出去，读者满屏看到 `---`，适配器里加断言。
- 硬换行 vs 段落：CRLF 和行尾双空格在不同渲染器结果不同，归一化阶段统一掉。
- emoji 在部分 RSS 编码链路会乱码，不确定就别用。
- 正则处理嵌套结构（列表里的代码块）必然出错，遇到就退回 AST。

## 可复用建议

- 规范源 + 纯函数适配器是通用模式：换目标平台只是加一个适配器，上游完全不动。
- 校验规则写进仓库并工具化，让 Agent 在发布前自检，而不是靠审稿人抓格式。
- 管线设计成幂等的：跑两遍和跑一遍结果一致，重发不炸；每次转换留日志，出问题能回溯。

## 总结

这条管线的价值不在某个具体转换，而在把"格式决策"从发布动作里剥离出来：内容只写一次，格式约束全部收敛到代码里。Agent 负责产出规范源，适配器负责确定性转换，人只审内容本身。链路稳定之后，新增平台的边际成本就是一个小函数加一份快照。
