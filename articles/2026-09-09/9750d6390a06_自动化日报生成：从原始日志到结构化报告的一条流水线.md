## 背景

我们手上服务不算多，但日志散落在几台机器上。之前每天的流程是：早上到工位，挨个 `grep` 错误日志、数告警、凭记忆写日报，整个过程 15 分钟左右，还经常漏掉凌晨的零散告警。后来我用 OpenClaw 的定时任务加一个预处理脚本搭了条日报流水线，跑了两周比较稳定，把过程和踩的坑记下来。

## 问题

动手前先明确了三个核心问题：

1. **原始日志不能直接喂模型**。一天的日志动辄几十 MB，token 成本不可接受，而且模型面对大段原始日志很容易幻觉编造异常。
2. **日报格式必须稳定**。报告是给人横向对比看的，字段和段落顺序天天变就没意义了。
3. **流水线自己也会挂**。挂了没人知道，日报静默消失，比没有日报更糟。

## 做法

### 第一步：脚本层做切片和统计（不用模型）

- 按天切割日志，只取昨日窗口的数据；
- 用 Python 做确定性统计：错误总数与 Top N 类型、按 message 模板归并的聚类、QPS 采样点、新增错误关键词；
- 输出一份中间 JSON，通常只有几 KB。

原则很简单：**模型只看统计摘要，永远不看原始日志**。

### 第二步：Agent 按模板生成报告

- 由定时任务触发，prompt 中给死结构：概览 / 异常与根因猜测 / 与前一日对比 / 待办建议；
- 把前一天的报告 JSON 一并传入，让"对比"有真实依据，而不是模型现编；
- 要求先产出固定 schema 的 JSON，再由模板渲染成 Markdown——JSON 给机器归档，Markdown 给人看。

### 第三步：分发与留档

- Markdown 推送到群 webhook；
- JSON 按 `reports/YYYY-MM-DD.json` 落盘，保留 90 天后压缩。

## 踩坑点

1. **时区**。日志是 UTC，日报按本地时间算"昨天"，第一次跑出来的"昨天"其实是前天。现在切片统一写死一个时区，脚本和 prompt 都引用同一个配置。
2. **日志格式漂移**。某次升级改了错误行格式，解析脚本没报错，但统计全是 0，日报看起来"风平浪静"。补救：加断言，当日解析行数低于历史均值 20% 时直接告警终止，而不是照常出报告。
3. **模型输出漂移**。早期版本标题和段落顺序每次不同，没法对比。改成模型只负责"分析"、不负责"排版"后彻底解决。
4. **失败要出声**。任何一步异常，推送一条纯文本错误摘要到同一个群，宁可吵到人，不可静默消失。

## 可复用建议

- **分层是关键**：确定性的事（切片、统计、格式）交给脚本，模糊的事（归因、建议）交给模型。这条边界划清楚，稳定性自然就上来了。
- 中间产物必须是机器可读的（JSON + schema），人看的报告只是它的渲染结果之一。
- 想让报告可对比，模板和字段就不能随意动。
- 切换前先跑一周"影子模式"：照常生成但不推送，和人工日报对照，确认没有明显遗漏再切。

## 总结

这套流水线没有用到任何复杂技术，价值在于把每天早上那 15 分钟归零，而且日报质量比手写更稳——至少不会再漏看凌晨三点的那条告警。整套配置不到 200 行，迁移成本很低。下一步我打算把周报、月报建在同一个 JSON 中间层上，那才是这套东西真正的复利所在。
