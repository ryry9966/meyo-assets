## 背景

在 OpenClaw 的 Agent 和插件开发里，让模型输出结构化数据是绕不开的环节：工具调用参数、MCP 请求体、自动化流程的中间状态，大多靠“只输出 JSON”这类约定来传递。但 prompt 里写得再明确，实际拿到的输出仍然是长尾分布——尤其在多模型混用、上下文很长、或字段内容本身含代码时。

## 问题

我们最初只处理两种格式：裸 JSON 和 ```json 围栏。上线后陆续遇到：

- 前后带说明文字：“以下是解析结果：{...}”
- 各种标签包裹：`<json>`、`<output>`，甚至自定义标签
- 围栏语言标注缺失，或写成大写 ```JSON
- 字段值里嵌套围栏（模型生成了含示例代码的内容）
- Python 风格残留：单引号、`True`/`None`、尾逗号
- max_tokens 截断，JSON 只剩前半截

任何一种都能让 `json.loads` 直接抛异常，整条 Agent 链路中断。

## 做法

后来我们把解析重构成一条分层管线：每层只解决一类问题，失败就交给下一层。

1. **标签定位**：正则提取围栏块和常见标签块。用非贪婪匹配，且优先取最后一个完整块——模型经常在解释文字里附带示例 JSON。
2. **括号配平提取**：上面没命中时，逐字符扫描原文，计数花括号配平，并跳过字符串内部和转义符。这一层能兜住“JSON 混在散文里”的情况。
3. **按失败类型修复**：先标准解析，报什么错修什么。尾逗号删掉；智能引号替换成直引号；`True`/`None` 映射成 `true`/`null`。**不要盲目 `replace("'", '"')`**，会把 `It's` 这类合法内容打碎。
4. **模型自修复兜底**：修复失败时，把原文加报错信息回传，让模型重试一次。只重试一次，避免循环烧 token。
5. **Schema 校验**：拿到合法 JSON 后用 pydantic / jsonschema 验字段。格式合法不等于语义正确。

核心骨架大致是：

```python
def parse_llm_json(raw: str):
    for extractor in (extract_fenced, extract_tagged, extract_balanced):
        chunk = extractor(raw)
        if not chunk:
            continue
        obj = try_load_with_repair(chunk)
        if obj is not None:
            return obj, extractor.__name__
    return None, "failed"
```

## 踩坑点

- 贪婪正则会把多个 JSON 块拼成一坨；非贪婪在嵌套围栏处提前截断。两种写法都要用真实输出测过才算数。
- 截断型输出修复成功率很低，硬修出来的“完整 JSON”往往是错的，应直接走重试而不是修复。
- 修复顺序影响结果：先替换单引号再处理转义，可能双重破坏。
- 温度调到 0 也不保证格式稳定，长上下文里模型“忘了”约定很常见。
- `except: return None` 静默吞错是最坑的写法，问题会延迟到下游才爆，排查成本翻倍。

## 可复用建议

- 解析器做成纯函数，返回 `(对象, 走了哪条路径)`，把路径写进日志。统计一段时间，如果某个模型 80% 走 repair 路径，那就是改 prompt 的信号，而不是继续加修复规则。
- Few-shot 示例比口头强调格式有效得多，给两三个输出示例，格式遵循率会明显提升。
- 能用 function calling / 结构化输出 API 就优先用，标签方案只作为兼容层保留。
- 修复逻辑按报错类型分发成小函数，别堆成一坨字符串替换。

## 总结

防御性解析的本质不是把 prompt 写得更凶，而是承认模型输出是长尾分布，用分层管线加观测把不确定性圈在可控范围内。这套管线在我们插件里跑了几个月，解析失败从偶发中断降到可忽略，且每次失败都能从日志定位原因。有同类需求的可以按这个分层思路搭，全部代码不到百行，欢迎在社区帖子里交流各自的 extractor 写法。
