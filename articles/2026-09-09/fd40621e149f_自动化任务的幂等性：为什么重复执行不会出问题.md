## 背景

在 OpenClaw、Agent 和 MCP 工具链里搭自动化，有一个事实绕不开：**任何任务都可能被执行不止一次**。Webhook 是"至少一次"投递，超时会重发；Agent 调工具超时后，往往会重试；cron 任务跑得久一点，就和下一轮重叠；人工看到"好像失败了"，顺手再触发一次。重复执行不是异常路径，而是常态路径。

## 问题

如果任务里有副作用操作，重复执行就是事故。典型场景：告警机器人网络抖动，Agent 重试了工具调用，同一条告警在群里发了三遍；定时同步任务 cron 重叠，目标系统出现重复记录；重跑一次失败的流水线，前面已成功的步骤又执行了一遍。这些问题不在"功能对不对"，而在"跑两遍还对不对"——这正是幂等性要回答的：**同一操作执行一次和执行 N 次，最终状态一致**。

## 做法

按下面顺序给任务加幂等保护：

1. **盘点副作用**。把任务里的写操作列出来：发消息、建记录、调外部 API、写文件。读操作天然幂等，重点全在写。
2. **确定幂等键**。用业务键而不是随机数：告警用事件 ID，同步用"源记录 ID + 版本号"，工单用触发事件的唯一标识。关键是它在触发时刻就确定了，与重试次数无关。
3. **数据库唯一约束兜底**。应用层先查再写有竞态，直接给幂等键建唯一索引，写入冲突就当作"已处理"跳过，`INSERT ... ON CONFLICT DO NOTHING` 一行解决。
4. **分步任务记台账**。多步流水线建一张执行记录表，每步完成即落状态，重跑时跳过已完成步骤，只补失败的。
5. **外部 API 透传幂等键**。对方支持幂等键头就带上；不支持就"先查后做 + 做完校验"。
6. **文件操作原子化**。写临时文件再 rename，避免半成品和重复覆盖。

## 踩坑点

- **幂等键在重试时重新生成**。最常见的错误：key 每次尝试随机生成，重试等于换了新 key，去重完全失效。key 必须来自业务事实。
- **check-then-act 竞态**。两个并发请求同时通过"不存在"检查，然后各自写入。靠 SELECT 查重不够，必须靠唯一约束。
- **去重窗口 TTL 太短**。重试可能发生在几分钟后，10 秒的去重缓存挡不住。
- **多层重试叠加**。HTTP 客户端重试 + Agent 层重试 + 调度层重试，没有统一幂等键时，重复次数是乘积。
- **时间戳当 key**。同一毫秒内两次触发会撞 key，时钟回拨更麻烦。

## 可复用建议

- 写自动化任务时默认假设：**它至少会被跑两次**。按这个假设设计，大部分问题提前消失。
- 幂等键在最外层触发入口生成，全链路透传，别在中间环节再造。
- 优先数据库唯一约束，其次才是应用层判断。
- 给关键任务补一个"连续跑两遍"的测试用例，第二遍结果必须和第一遍一致。回归时它比任何文档都可靠。

## 总结

幂等性不是性能优化，而是自动化的正确性底线。重试机制保证任务"最终会执行"，幂等设计保证"执行多次等于执行一次"，两者合起来，自动化才敢无人值守地跑。下次写定时任务或工具插件时，先问一句：这段逻辑跑两遍，会出什么事？答不上来，就先补上幂等键。
