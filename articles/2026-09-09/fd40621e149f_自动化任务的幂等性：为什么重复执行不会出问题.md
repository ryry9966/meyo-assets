## 背景

在 OpenClaw / Agent / MCP 这类自动化体系里，**重复执行是常态，不是异常**。网络超时后的重试、webhook 的重投、定时任务的重叠触发、用户手滑多点一次、甚至 Agent 自己判断“上一次没成功”再跑一遍——这些都是日常。

我见过一个典型场景：一个“每天把未关闭 issue 汇总发到群”的定时任务，因为容器重启导致 cron 补跑，同一条汇总发了两遍。功能没坏，但信任坏了——用户开始怀疑系统的每一条输出。

## 问题

非幂等操作在重复执行时会放大副作用：建两张一样的工单、发两条通知、库存扣两次、状态机连跳两步。这类错误的麻烦在于**事后很难追溯**：日志里两次执行都“成功”了，只有下游数据能看出不对。

## 做法

1. **先分类操作。** 读操作、按目标状态设置（PUT 语义）天然幂等，不用管；创建、发送、递增这类不幂等，重点防护。
2. **用业务键做幂等键。** 不要用随机 UUID——每次重试生成的都不同，等于没防。应该用上游消息 ID、外部事件 ID、或者“任务 ID + 时间窗口”这类重试前后稳定的标识。
3. **先记账，再执行。** 执行前查键：已存在且成功 → 直接返回上次结果；已存在且进行中 → 拒绝或等待；不存在 → 原子写入“进行中”，执行完成后更新终态。
4. **状态机用条件转移。** 写成“仅当 status = pending 时才置为 sent”，把幂等下沉到数据层，而不是依赖应用层判断。
5. **不可回滚的副作用前置判断。** 发邮件、调第三方付费 API 这种没法撤销的动作，去重检查必须放在副作用之前，别指望事后补偿。

## 踩坑点

- **键粒度选错。** 用时间戳做键，每次重试键都不同；只用用户 ID 做键，合法的第二次执行会被吞掉。键要精确到“这一次业务动作”。
- **check-then-act 有竞态。** 两个并发请求同时查到“不存在”，然后都执行。必须用原子的 set-if-absent（如 SETNX、数据库唯一索引冲突），不能先查后写。
- **“进行中”没有租约。** 一次执行中途崩了，记录永远停在进行中，后续全部被拒。要给进行中状态加超时或租约，到期允许接管。
- **记录 TTL 短于重试窗口。** 重试晚于记录过期才到达，去重失效。TTL 必须覆盖最大可能的重试延迟。
- **Agent 侧的非确定性。** 重试时模型重新生成参数和 ID，两次请求在业务上其实变成了两个任务。幂等键要在进入 Agent **之前**确定（比如取自上游消息），不能让模型自己编。

## 可复用建议

- 把幂等封装成 MCP 工具层的**统一包装器**：自动提取键、查记录、写状态，而不是每个工具各写一套。
- 能“声明期望状态”就不要“下发追加命令”。设置配置天然幂等，append 类操作要警惕。
- 任务日志里固定打印幂等键，排查重复问题时能对上账。
- 上线前主动做破坏性测试：手动重复投递、并发双发，验证行为符合预期，而不是等用户帮你发现。

## 总结

幂等不是锦上添花的优化，而是让“重试”这个最基本的可靠性手段可以放心使用的前提。反过来讲，一个不可重试的任务，在自动化系统里才是真正脆弱的。把“跑两次会怎样”写进每一次任务设计里，成本很低，收益很实。
