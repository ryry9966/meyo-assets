## 背景

E2E 测试是前端工程里最“知道该做但总被推迟”的事：用例写得慢、选择器脆、页面一改就红。我们团队的核心链路长期只有十几个手工维护的 Playwright 用例，覆盖率全靠自觉。

最近我们尝试让 OpenClaw 的 Agent 通过 MCP 接入浏览器和测试运行器，把“探索页面 → 生成用例 → 跑失败 → 自修复”这条链路自动化了一部分。跑了一个多月，效果实际，坑也不少，这里做个记录。

## 问题

直接把需求扔给 Agent，说“帮我写 E2E 测试”，基本不可用：

1. 它不了解你的路由结构和组件实现，选择器全靠猜；
2. 生成用例断言很弱，比如只断言“页面能打开”，跑起来全绿但什么都没测到；
3. 失败后让它自己修，它倾向于加 `waitForTimeout(3000)` 把 flaky 掩盖掉。

核心矛盾在于：Agent 需要确定性的事实（DOM、路由、测试结果），而它默认只能靠训练记忆去猜。

## 做法

思路很简单：把不确定的部分交给 Agent，把确定的部分做成 MCP 工具。

**第一步：暴露确定性工具。** 通过 MCP 给 Agent 三个工具：`list_routes`（读路由配置）、`get_dom_snapshot`（返回精简后的可访问性树）、`run_test`（执行指定测试文件并返回结构化结果）。禁止它直接操作原始 HTML。

**第二步：限定探索范围。** 每次只处理一条用户旅程，比如“登录后创建项目并邀请成员”。全站一把梭只会撑爆上下文。

**第三步：生成与校验循环。** Agent 调工具探索页面，产出 Playwright 用例；`run_test` 执行后把失败栈喂回去，允许它修改选择器和等待策略，最多迭代三轮。

**第四步：人工闸门。** Agent 只输出 diff，不自动 commit。断言强度由人审——这是目前唯一没法外包给模型的环节。

## 踩坑点

- **假绿灯**：Agent 很会写“能过但没用”的测试。我们在规则文件里强制要求每条用例至少含一个数据断言（文本、数量或跳转 URL），并加一道模型评审断言强度。
- **Flaky 与真坏的混淆**：让它自动重跑修选择器，会把偶发超时也当成选择器问题，越修越乱。后来加了一条规则：同一用例连续两次失败先标记 flaky，交人判断。
- **快照太大**：原始 DOM 快照轻松几十 K token。改用可访问性树加白名单字段裁剪后，单页能压到 2K 左右。
- **权限收敛**：`run_test` 必须跑在容器里。Agent 生成的代码不可信，至少不能长期可信。

## 可复用建议

1. 把团队测试规范写成规则文件放进仓库，比在 prompt 里反复强调有效得多；
2. MCP 工具返回结构化 JSON，别返回自由文本，Agent 的行为会稳定很多；
3. 迭代上限和人工闸门是底线：Agent 参与写路径没问题，碰主干分支不行；
4. 先覆盖“创建/编辑”这类高频 CRUD 旅程，别指望一步到位做全量回归。

## 总结

Agent 写 E2E 测试，本质是把“读页面、查选择器、跑测试、看报错”这些机械劳动交出去，而“测什么、断言多严”仍然由人决定。一个多月的经验浓缩成一句话：工具越确定，Agent 越可靠。它不是测试工程师的替代品，更像一个不嫌烦的初级同事——把规范和边界写清楚，产出是可用的；糊弄它，它就糊弄你。
