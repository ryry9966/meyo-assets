## 背景

用 OpenClaw 挂一个定时 Agent，接上 MCP 的发布工具，自动往社区发内容——这套流程半天就能搭起来。真正难的不是"发出去"，而是让发布节奏不招人烦。我见过不止一个自动化账号，内容本身没问题，却因为"每 30 分钟准点发一条"被管理员盯上，最后进了限流名单。

## 问题

固定节奏本身就是最强的机器特征。人对时间的感知是不均匀的：集中刷一阵子，然后消失几小时；深夜几乎不说话；回复速度忽快忽慢。而 `cron + 固定间隔` 给 Agent 的是一种均匀、无边界、可预测的时间观。调度层不改，内容写得再自然也没用。

## 做法：四层节奏控制

我把调度拆成四层，逐层叠加：

**1. 抖动调度。** 基础间隔上叠加随机偏移，30%–40% 的幅度比较自然：

```python
interval = base * (1 + rng.uniform(-jitter, jitter))
```

关键点是 RNG 必须带固定 seed，否则复现排查时你根本说不清"昨晚为什么在那个点发了"。

**2. 活跃时段建模。** 参照目标社区的时区（不是服务器的）配置活跃窗口，深夜概率压到接近零：

```yaml
schedule:
  base_interval: 45m
  jitter: 0.35
  active_hours: "08:00-23:30"
  night_factor: 0.1
  daily_cap: 6
  burst_cooldown: 20m
```

**3. 配额与冷却。** daily_cap 宁小勿大；连续发 2 条后强制冷却。发过的目标 ID 落盘做幂等，防止重启后补发、重复发。

**4. 事件驱动优先。** 这层效果最好：与其定时瞎发，不如挂事件——有人回了、有新帖命中关键词、被人 @ 了，再触发发布。时间调度只做兜底。有上下文的低频输出，远比无上下文的定时输出更像"在场"。

## 踩坑点

- **均匀随机 ≠ 人类节奏。** 人是"会话式"活动的。更好的模型：随机挑 2–3 个活跃窗口，窗口内偏密集，窗口之间长时间沉默。
- **时区错位。** 服务器 UTC、社区北京时间，active_hours 配完全反了，变成深夜高频发帖，比不抖动更可疑。
- **内容乱拼比机械更假。** 开场白池子随机组合，结果跟上下文对不上，一眼就是模板。变化要服务于语境，不是纯随机。
- **重试没纳入节奏。** 发布失败后固定 30s 重试，特征同样很明显。重试也要指数退避加抖动。
- **别越界到伪装。** 节奏自然化的目的是不扰民、尊重社区规则，不是隐藏自动化身份。要求标注 bot 的社区就老实标注，被封号的代价远高于一条标签。

## 可复用建议

- 全局共享一个限速器（token bucket），别让每个脚本各配一份配额；
- 上线前先跑 dry-run：只打调度日志不真发，观察一周节奏曲线再放开；
- 留一个 kill switch，一条命令暂停所有发布；
- 调度参数全部进配置文件，不要硬编码在 Agent 的 prompt 里。

## 总结

节奏控制的本质，是把机器的均匀时间观换成人的不规则但有意的时间观：低频、有上下文、尊重时段。做到这几点，账号"像不像人"其实已经不重要——重要的是它不再打扰任何人，这才是自动化能长期留在社区里的前提。
