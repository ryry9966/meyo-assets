## 背景

用过 Agent 的人都有同感：每次新会话都要重新交代一遍——"代码用 TypeScript"、"回复别啰嗦"、"部署先走 staging"。上下文窗口再大，会话结束就清零。记忆系统要解决的不是"存得多"，而是"下次用得上"。

## 问题

常见的三种失败模式：

1. **全量堆上下文**：把历史对话塞进 prompt，token 成本飙升，关键偏好被噪音淹没；
2. **只存不用**：记了一堆笔记，没有读取策略，等于没记；
3. **记了就是真理**：用户三个月前说喜欢某框架，现在早换了，Agent 还按旧偏好办事。

核心矛盾就四个：写什么、什么时候写、怎么读、怎么过期。

## 做法

我的方案是三层结构，落在一个 OpenClaw 插件里，通过 MCP 暴露工具：

**L1 会话暂存区**：当前会话内用 scratchpad，会话结束即弃，不进持久层，从源头控制噪音。

**L2 结构化画像（核心）**：一个 `profile.yaml`，只存可执行的稳定事实：

```yaml
- fact: 偏好 TypeScript，禁 any
  scope: coding
  confidence: 0.9
  updated_at: 2025-06-01
  source: session#412
```

每条带置信度和时间戳，字段固定，便于 diff 和审查。

**L3 情节日志 + 向量索引**：长尾上下文（项目细节、踩过的坑）按条存 SQLite，跑 embedding 建索引，按需检索，不默认注入。

**写入策略**：不在对话中途靠 LLM "顺手写"——太不稳定。改为会话结束时跑一次提取 pass，候选事实和现有画像比对：重复则跳过，冲突则新覆旧、旧值进 history，低置信度标待确认。

**读取策略**：每次会话启动，把 L2 画像渲染成 ≤300 token 的摘要注入 system prompt；L3 只在相关任务时用 `memory_search` 工具查询。读写全部走 MCP 工具调用，Agent 自己也能显式触发。

## 踩坑点

- 提取 pass 不加 schema 约束，LLM 会产出"用户人不错"这种无法执行的事实。prompt 里必须限定：只提取影响未来行为的信息。
- 向量检索单独用会漏精确匹配，"禁 any"这种关键词靠语义召回不稳。要结构化查询 + 向量兜底，双通道。
- 画像会膨胀。设上限（比如 50 条），满了触发摘要压缩，或按 updated_at 淘汰。
- 别忘了"遗忘"接口。用户说"以后别用 X 了"，要能删或降权，否则信任直接崩。

## 可复用建议

- 记忆文件进 git，每次变更可 review、可回滚，比黑盒数据库放心得多；
- 写一个回放测试：拿历史会话跑新记忆策略，对比画像 diff，改策略不再靠感觉；
- 记忆操作留审计日志，画像被写坏时能定位到哪次提取出的错。

## 总结

记忆系统不玄学，本质是一个带时间戳、置信度和读取策略的小型数据工程问题。先把 L2 结构化画像做对，L3 按需再上。原则只有一条：宁可少记，不可记错——错误记忆比没有记忆更伤体验。
