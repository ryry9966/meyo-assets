## 背景

E2E 测试是大多数团队"知道该写、但一直在欠债"的部分：写起来慢、选择器脆、维护成本高。最近我们把 Agent 接进测试流程，让它承担"初稿生成 + 自跑自修"，人只负责审查断言质量。跑了一段时间后记录一下实际做法和踩坑，给同样想试的朋友一个参照。

## 问题：直接让 LLM 生成测试为什么基本不可用

直接问模型"给这个页面写个 Playwright 测试"，产出通常跑不起来：选择器是编的、API 是猜的、断言是套话。核心原因不是模型不会写测试，而是它没有执行反馈——看不到真实 DOM，也看不到失败输出。所以方案的关键不是写更好的 prompt，而是给 Agent 一个**"写完就能跑、跑了能读结果"的工具闭环**。

## 做法

在 OpenClaw 里把这些能力封装成一个 MCP Server 挂给 Agent，暴露四类工具：

1. **浏览器操作**：基于 Playwright 的 navigate / click / fill / snapshot。snapshot 返回带 ref 的可访问性树，Agent 用 ref 定位元素，而不是猜 CSS 选择器；
2. **测试执行**：run_test 工具，只跑单个 spec 文件，返回截断后的失败栈，控制 token 消耗；
3. **文件读写**：限定在 `tests/` 目录内，防止误改业务代码；
4. **约定注入**：启动时把仓库里的测试规范（data-testid 规则、fixture 用法、禁止 sleep）作为上下文喂进去。

执行流程是：

1. 人先给出关键用户路径清单（下单、登录、退款这类），**一次会话只做一条路径**；
2. Agent 用浏览器工具手动"走"一遍路径，观察真实 DOM；
3. 基于观察生成测试初稿并执行；
4. 失败则读输出、修改、重跑；设 3 次重试上限，超过就停下写失败报告交给人；
5. 转绿后提交 PR，人审断言。

## 踩坑点

- **最坑的一条：Agent 会修测试来适配 bug。** 页面本身有 bug 时，它会把断言改成符合错误现状的值。对策是让它对照已知正确的环境跑，并要求在 PR 里说明每个断言预期值的来源。
- **断言退化成"页面能打开"。** 必须在规范里明确：每条用例至少一个业务断言（金额、状态、落库数据），否则生成的全是废话测试。
- **Flaky 处理**：Agent 非常喜欢 `waitForTimeout`。规范里直接禁止，只允许等状态、等元素；再配一个简单检测——同一条用例连跑 5 次，挂 1 次就打回。
- **别贪量**：一次生成 20 条用例，token 烧得多、失败定位也难。一条路径一次会话，实测通过率从三成提到八成左右。

## 可复用建议

- **优先投资工具层而不是 prompt。** "跑一下并把输出读回来"这一个工具的价值，超过所有提示词技巧。
- 把测试规范写成仓库内的文档让 Agent 读取，比在会话里反复口头约束稳定得多。
- 给 Agent 产出加 mutation 自检：临时改坏一处被测逻辑，确认测试会变红，防止"永不失败的测试"混进主干。
- 生成用例打独立 tag，CI 单独统计其稳定性，数据差就回炉重写。

## 总结

Agent 写 E2E 测试是可行的，但定位要清楚：它是一个提交 PR 等你 review 的初级工程师，不是 autopilot。瓶颈在工具闭环和护栏，不在模型能力。先把执行反馈搭好，再用规范文档约束行为，最后靠人审断言兜底——这三层做完，E2E 的技术债是真能还上的。
