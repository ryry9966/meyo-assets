## 背景

Agent 的能力边界，基本就是它能调用的工具边界。OpenClaw 提供了对话编排和工具调用框架，但真正让它"能干活"的，是背后接入的外部服务：搜索、数据库、内部系统、第三方 SaaS。对接这件事听起来只是"发个 HTTP 请求"，实际坑比想象多。

## 问题

常见翻车场景：

- 模型拼错参数，请求直接 400；
- 密钥写死在配置文件里，随代码一起进了仓库；
- 接口偶发超时，自动重试把同一笔工单创建了两次；
- 工具返回 50KB 原始 JSON，几轮对话就把上下文塞爆；
- 注册的工具太多，模型选错工具的概率明显上升。

这些都不是"模型不够聪明"，而是对接层设计的问题。

## 做法

以把一个内部工单系统接进 OpenClaw 为例，我们的路径是：

1. **选接入方式**。优先用 MCP server：协议标准化，工具 schema、鉴权、传输都有约定，换模型或换客户端时迁移成本低。只有高度定制的内部逻辑才考虑写原生插件。
2. **定义 schema，宁窄勿宽**。一个工具只暴露一个明确动作，参数用 enum 收紧可选值，description 写清楚"什么时候该用我"。比如 `create_ticket` 的 `priority` 直接限定枚举，比让模型自由发挥稳定得多。
3. **鉴权与密钥**。全部走环境变量或 secret manager，MCP server 启动时注入；OAuth 类服务把 token 刷新放在对接层，模型永远不接触凭据。
4. **加固对接层**。设置请求超时；写操作强制带幂等键；按指数退避重试，且只对幂等操作重试；分页接口在对接层聚合完再返回。
5. **裁剪返回内容**。API 原始响应先在对接层做摘要和字段过滤，只回传模型需要的部分，完整响应落日志。
6. **先干跑，再放开**。写操作加 dry-run 开关，人工确认后再真调用；同时记录每次调用的入参、出参和耗时，方便回溯。

## 踩坑点

- **description 太敷衍**。模型选工具主要靠 description，写得含糊就会出现"该查订单却调了创建接口"。
- **工具数量失控**。单个 Agent 挂 30+ 工具后选择准确率明显下降，按场景拆 Agent 比堆工具有效。
- **忽略幂等性**。网络抖动后的自动重试，在"下单、发消息"这类接口上会造成重复写入。幂等键要在对接层强制，别指望模型记得。
- **上下文膨胀**。直接 return 整个响应对象，token 很快见底。
- **版本漂移**。外部 API 升级改了字段，schema 不跟着改，模型按旧认知传参会持续报错。对接层要做响应校验，字段缺失就显式报错。

## 可复用建议

- 对接层保持"薄"：一个工具一个动作，多步编排放在 Agent 流程里，不要塞进一个大而全的工具。
- 错误信息也是给模型看的提示词：返回结构化、可操作的错误，"缺少字段 date"远好于一句 "Bad Request"。
- 每个工具标注读写属性：读操作可放宽自动执行，写操作默认要求人工确认。
- 沉淀自己的 MCP server 模板，鉴权、重试、日志这些样板代码写一次就够。

## 总结

对接外部服务的核心不是"能调通"，而是调用在异常路径下依然可控：schema 收紧、凭据隔离、幂等重试、返回裁剪。这四件事做好，Agent 与 API 的握手才算真正握稳。OpenClaw 的工具生态给了足够自由度，而自由度的代价，是这层纪律得自己守。
