## 背景

Agent 的价值不在"会聊天"，而在能真正触达外部系统：查工单、拉数据、触发部署。在 OpenClaw 里，这条链路主要靠三种方式打通：内置插件、自定义工具（function calling 风格的工具注册）、以及 MCP server。三者的本质是一样的——把一个 HTTP 调用包装成模型可理解、可调用的工具。

## 问题

实际对接时，最常见的不是"调不通"，而是调通了但不可靠：

- 工具描述含糊，模型传参自由发挥；
- 接口超时或限流后，Agent 拿不到结构化错误，开始编造结果；
- 返回体太大，一次调用吃掉大半个上下文窗口；
- 密钥写死在配置里，日志一打全泄露。

## 做法

以对接一个内部查询服务为例：

1. **先定接口，再写实现。** 工具名单一职责（如 `query_order_status`），参数用 JSON Schema 严格约束类型与必填项；描述里写清"什么场景该用、什么场景不该用"。这段描述是给模型看的文档，不是给人看的注释。
2. **选注册方式。** 一次性的进程内调用用插件/工具注册即可；需要跨项目复用、独立进程、多个 Agent 共享的，封装成 MCP server，用 stdio 或 SSE 暴露。
3. **认证走环境变量。** API key 从 env 或密钥管理服务读取，配置文件里只留占位符。
4. **错误结构化返回，不要抛异常。** 返回 `{"ok": false, "error": "rate_limited", "retry_after": 30}` 这类格式，Agent 才能判断该重试还是该放弃并告知用户。裸异常只会让模型瞎猜。
5. **在工具层做超时、重试与限流保护**，别指望模型自己"等一下"。同步调用设硬超时（如 10s），长任务改成异步任务 ID + 轮询工具。
6. **返回体做裁剪。** 只回传模型需要的字段，大结果落盘或写缓存，返回一个引用句柄。

## 踩坑点

- 工具描述只写"查询数据"，模型把各种查询都往这里塞，描述必须具体到场景。
- 上游 500 返回的 HTML 页面被原样塞给模型，上下文瞬间污染。工具层必须先兜住异常响应。
- 重试不加退避，限流雪上加霜。
- 日志级别开太高，把 Authorization 头打进了排查日志。
- MCP server 改了接口没同步改描述，Agent 仍按旧签名传参，排查半天才发现。

## 可复用建议

- 把每个工具当公共 API 对待：有版本号、有变更记录、有最小测试集（固定 prompt → 期望调用参数）。
- 上线前用 dry-run 模式记录所有工具调用，人工过一遍参数再放行。
- 一个工具只做一件事，复杂流程用多个工具组合，编排交给 Agent。

## 总结

对接外部服务的核心不是"能发请求"，而是让 Agent 在成功、失败、限流、超时各种情况下都知道下一步该做什么。接口收窄、错误结构化、密钥外置、返回裁剪——这四件事做到位，这次握手才算真正握稳。欢迎大家把自己对接时的错误码设计和重试策略贴出来对比。
