## 背景

大多数人用 OpenClaw 的第一天，交互模式都是同一个：你发消息，Agent 回答。它再聪明，本质上也是个被动组件——不问不动。但个人助理类 Agent 真正的价值，往往在"你没问的那部分"：磁盘快满了、仓库有新提交、日历有冲突、昨天让它跟进的事没下文。这些事没人会专门去问。

OpenClaw 用一个很小的机制补上了这块：heartbeat。网关按固定间隔（默认约 30 分钟，可配置）唤醒 Agent，Agent 醒来后读工作区里的 `HEARTBEAT.md`，按里面的指令决定"做事并汇报"还是"保持沉默"。一个 Markdown 文件，就是 Agent 的自主行为契约。

## 问题

没有 heartbeat，周期性任务只有两条路：要么你定时去问（那要 Agent 干什么），要么写外部 cron + 脚本绕过 Agent（失去推理和上下文整合能力）。`HEARTBEAT.md` 解决的是中间地带：需要"判断"的周期性任务——检查完还要决定要不要说、要不要做。

## 做法

1. 在 Agent 工作区创建 `HEARTBEAT.md`，用 checklist 风格写任务，每条尽量包含四段：**触发条件、检查方式、执行动作、静默条件**。例：检查 `~/work/repos` 下各仓库是否有未推送提交；有则汇总列表；无异常则不汇报。
2. 在配置里为 agent 打开 heartbeat，设置间隔（every）和投递目标（target），即主动消息发到哪个会话。调试期把间隔调到 1–2 分钟。
3. 明确"沉默协议"：告诉 Agent 没事时回复 `NO_REPLY`，网关就不投递。这一步不做，你会在第三条心跳消息后把它静音。
4. 观察两三轮日志，确认判断符合预期，再调回生产间隔。我常用 30 分钟到 2 小时，按任务性质分档。
5. 心跳任务里可以调用工具和 MCP：抓 RSS、跑只读 shell、查日历，让它有"感知"而不是空转。

## 踩坑点

- **频率 ≠ 勤快**。每次心跳都消耗 token，哪怕最后沉默。高频 + 任务多，一天烧掉的量很可观。
- **指令模糊必翻车**。"帮我盯一下服务器"这种写法，Agent 会自行解释成频繁汇报，甚至某天自作主张重启服务。动作要写死边界：只读、汇报格式、什么情况才升级为通知。
- **长任务别放心跳里**。心跳应短平快；重活交给外部 cron 触发、Agent 处理结果，避免唤醒堆积。
- **文件会腐烂**。任务做完不删，几个月后 HEARTBEAT.md 变成杂物间，每轮白耗 token。定期归档已完成项。

## 可复用建议

- 先跑两周只读任务（检查、汇总、提醒），建立信任后再加写操作（移动文件、提 PR、发消息），并给写操作设确认阈值。
- 把心跳决策追加写入一个日志文件，事后能审计"它几点检查了什么、为什么沉默"，比事后猜靠谱得多。
- 一条经验法则：心跳负责"感知与判断"，高风险动作要么需要人在场确认，要么降级为只通知不执行。

## 总结

`HEARTBEAT.md` 本身只是个 Markdown 文件，价值在于它把"什么时候主动"从代码约定变成了可编辑的行为契约。写得好，Agent 从聊天窗口里的应答机变成常驻的巡逻进程；写得差，它就是一个定时骚扰你的通知源。差别不在机制，在你怎么写那份文件。
