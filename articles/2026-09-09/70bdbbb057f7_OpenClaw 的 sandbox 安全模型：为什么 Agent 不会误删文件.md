## 背景

OpenClaw 的典型用法是给 Agent 一台“能动手”的机器：exec 工具跑 shell、读写工作区文件、通过 MCP 和插件扩展能力。能力一大，绕不开的问题就是——模型偶尔会犯低级错误，也可能被外部内容注入指令。社区里被问得最多的安全话题是：它会不会哪天手一抖，把我的文件删了？

## 问题拆解

误删文件不是单一故障，而是几个条件同时成立：

1. Agent 拿到了能执行破坏性命令的工具（exec）；
2. 执行环境能看到不该看的路径（比如宿主机全盘）；
3. 危险操作前面没有任何人工闸门；
4. 出了事无据可查、无法回滚。

只堵其中一条，风险只是变小。OpenClaw 的思路是把四条同时堵上，做成分层的 sandbox 模型。

## 做法：四层防线

**第一层：容器隔离。** Agent 的执行环境默认跑在 Docker sandbox 里，而不是宿主机 shell。容器内有独立文件系统，就算模型真执行了 `rm -rf`，删的也只是容器内的目录树。

**第二层：最小挂载。** 默认只把 workspace 目录 bind mount 进容器，且可以设为只读。Agent 眼中的“整个世界”就是工作区，宿主机上的照片库、SSH 密钥、系统配置对它根本不存在——不是不能删，是看不见。

**第三层：工具策略与审批。** tools policy 里可以显式 deny 高危工具，或把 exec 设为需确认；开启 exec 审批后，Agent 拟好命令会先停下来等人点头。低风险操作可以进白名单自动放行，其余一律询问。

**第四层：审计与可回滚。** sandbox 内的执行有日志可查；工作区用 git 管理，任何误操作都能 revert。真正不可恢复的宿主机文件，从头到尾就没进入过 Agent 的可见范围。

## 踩坑点

- **图省事关沙箱**：用直连模式让 Agent 跑在宿主机 shell，四层防线瞬间只剩审批层。演示可以，长期跑别这么干。
- **挂载范围失控**：为了“方便”把整个 HOME 挂进容器。挂得越多，沙箱越像摆设，爆炸半径跟着变大。
- **审批疲劳**：什么都要点确认，人很快会开始无脑通过。只对真正危险的命令保留人工闸门，否则闸门形同虚设。
- **多 Agent 共享环境**：共用同一个容器或工作区时，A 写坏的文件会被 B 读走。按项目拆 workspace，必要时拆 sandbox。
- **忘了网络也是攻击面**：容器能任意访问外网时，提示注入可以从“删文件”升级成“数据外泄”。

## 可复用建议

1. 默认开沙箱，确有依赖或性能需求再按 agent 粒度放开。
2. 挂载只给 workspace，敏感目录宁可只读。
3. 破坏性工具一律走审批，低频高危命令宁可慢一步。
4. 工作区上 git，把“可回滚”变成习惯而不是祈祷。
5. 定期翻审计日志，确认策略真的在生效，而不是只写在配置里。

## 总结

OpenClaw 防误删的核心，不是假设“模型变聪明了”，而是承认它一定会犯错，然后用容器隔离、最小挂载、工具策略、人工审批四层机制，把单点错误牢牢限定在工作区内。安全模型的价值不在降低出错概率，而在控制爆炸半径——把可能出事的地方圈得足够小，翻车也只是工作区里一次 `git revert` 的事。
