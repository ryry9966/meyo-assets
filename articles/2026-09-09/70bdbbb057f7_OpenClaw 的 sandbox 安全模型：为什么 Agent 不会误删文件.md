## 背景

OpenClaw 的典型部署形态是**本地常驻网关**：一个 agent 长期在线，通过 shell、文件读写等工具直接操作机器。这和问答式使用 LLM 完全不同——工具调用是真实生效的，`rm` 敲下去文件就没了。

很多人的第一反应是“在系统提示词里写清楚不要删文件”。这篇帖子想讲清楚为什么这不够，以及 OpenClaw 实际靠什么兜底。

## 问题：提示词是建议，不是边界

提示词约束有三个结构性缺陷：

1. **非确定性**。同一个任务跑两次，路径展开、命令拼接都可能不同；
2. **上下文污染**。网页内容、消息频道里的文本会进入模型上下文，一次注入就可能改变它的“意图”；
3. **一次就够**。安全是 AND 逻辑：99 次正确 + 1 次 `rm -rf $WORKDIR/*`（变量恰好为空）就是事故。

所以结论很朴素：**不能让“模型听话”成为唯一防线。**

## OpenClaw 的分层做法

OpenClaw 的 sandbox 模型本质是四层防御，每层独立生效、互为冗余：

- **第一层：执行隔离。** Agent 的 shell 在沙箱容器内运行，默认看不到宿主机文件系统，能操作的只有显式挂载进去的目录。
- **第二层：最小可写面。** workspace 是唯一默认可写路径，其余挂载可设为只读。删除操作被物理限制在任务目录内。
- **第三层：工具策略。** shell 工具可配置命令白名单/黑名单，危险模式（递归强删、通配符删除、提权命令）被拦截或降级。
- **第四层：提权确认门。** 标记为 elevated 的操作——包括逃出沙箱在宿主机执行——必须经过人工确认，不会静默通过。

配置思路（具体键名以你所跑版本的文档为准）：

```jsonc
{
  "sandbox": { "mode": "all" },
  "workspace": { "mount": "~/agent-workspace" },
  "tools": { "shell": { "elevated": "confirm" } }
}
```

配置完务必做**越界演练**：让 agent 尝试读 `/etc/passwd`、删 workspace 外的文件、静默提权。预期结果全部失败，这套模型才算生效。

## 踩坑点

- **挂载过宽**。把整个 home 或项目根目录挂进沙箱，隔离形同虚设。只挂任务所需目录。
- **高估正则拦截**。base64 编码、变量拼接、下载脚本再执行都能绕过黑名单。把拦截当减速带，别当防火墙。
- **忽略沙箱内网络**。容器里能出网，数据外泄通道就是开着的，生产环境建议限制出网目标。
- **改完不验证**。版本升级后策略语义可能变化，越界用例要当回归测试反复跑。
- **没有恢复手段**。确认门也可能被你顺手点掉，workspace 纳入 git 或定时快照，最后一层永远是自己。

## 可复用建议

1. 最小可写面：可写目录 ≤ 任务所需，其余只读或不挂载；
2. 不可逆操作（删除、覆盖、对外发消息）必须过确认门，不靠 prompt；
3. 拦截规则从白名单起步，而不是黑名单；
4. 固定一套越界用例，每次升级后跑一遍；
5. agent 可写目录必须有快照——恢复能力比拦截更可靠。

## 总结

“Agent 不会误删文件”不是因为它足够聪明，而是因为它所在的环境里，误删要么物理不可达，要么必须经过你的确认。OpenClaw sandbox 模型的价值在于：**把安全从概率问题变成架构问题**。提示词可以引导行为，但边界只能由系统划出。
