## 背景

OpenClaw 这类常驻 Agent 网关，最大的能力来源和最大的风险点其实是同一件事：模型可以调用 shell 和文件工具。让 Agent 帮你整理目录、批量重命名很好用，但 `rm -rf` 只要执行错一次就够呛。在把一个自动化清理任务交给它之前，我把 sandbox 的实现和配置完整过了一遍，这篇帖子记录这个安全模型到底是怎么兜底的。

## 核心问题：模型的"意图"不等于"执行权"

很多框架里，模型输出的 tool call 会被直接执行，安全性靠 system prompt 里写一句"请小心"。OpenClaw 的设计前提不同：**模型只能"申请"操作，真正的执行权在宿主侧的网关**。每一次工具调用都要先经过策略层裁决，裁决不过，请求根本不会落到 shell。

## 它具体怎么做的

按我读配置和实测的顺序整理：

1. **文件系统隔离**。默认 sandbox 模式下，Agent 看到的 "HOME" 是工作区目录的映射，不是真实家目录。容器内路径在宿主侧只对应 workspace 下的子目录，真实目录不在挂载范围内。
2. **命令先过策略层再执行**。删除、覆盖、递归操作会命中规则表：工作区内的操作直接放行；工作区外的写操作要么被拒绝，要么触发显式确认。
3. **路径归一化**。`../`、symlink、绝对路径这些逃逸手法会在解析阶段被拉回沙箱根目录判断，越界即拒绝。
4. **全量审计日志**。每次 tool call——参数、结果、是否被拦截——都落盘。误操作不可怕，不可回溯才可怕。

## 我做过的验证步骤

光看文档不算数，我实际跑了三个用例：

- 让 Agent 删除工作区内的测试文件：正常执行，审计日志有记录；
- 让它"清理上上级目录的旧文件"：请求被策略层拦截，返回权限不足，模型转而申请提权，我没有批准，流程终止；
- 在工作区放一个指向宿主目录的 symlink，再让它顺着删：路径归一化后判定越界，拒绝。

三次测试，宿主文件完好。

## 踩坑点

- **把真实家目录挂进 sandbox**。图省事 `-v ~:/home/agent` 等于亲手拆护栏，这是最常见的自我推翻。
- **网关用 root 跑**。隔离是相对运行用户的，root 下沙箱形同虚设。
- **MCP/插件工具不自动继承 shell 的策略**。第三方 server 的文件工具，权限完全取决于你给它的配置，接入前先看它暴露了什么能力。
- **"临时"关沙箱调试**，然后忘了开回来。建议配置分层，默认配置永远带沙箱。
- **混淆沙箱内路径与宿主路径**。排查问题时，Agent 报告的路径要先映射回宿主侧再看。

## 可复用建议

- 把"执行权在宿主、不在模型"当作评审任何 Agent 系统的第一原则；
- 破坏性操作默认拒绝、白名单放行，不要反过来；
- 每个 Agent 独立 workspace，控制爆炸半径；
- 提权前先翻审计日志，用历史行为决定信任级别。

## 总结

OpenClaw 防"误删"不是靠模型自觉，而是靠结构：隔离的文件系统视图、宿主侧的策略裁决、路径归一化、可回溯的审计日志。模型再强也可能产出错误的 tool call，好的安全模型假设错误必然发生，然后保证错误被限制在可恢复的范围内。这也是我评审其他 Agent 框架时一直套用的一把尺子。
