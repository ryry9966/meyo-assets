## 背景

E2E 测试是团队里公认的"重要但不讨喜"的活：写起来重复，维护起来脆弱。我们长期只有核心链路有覆盖，新页面基本靠手点。OpenClaw 生态里 Playwright MCP 这类浏览器操作工具成熟之后，我们尝试把这件事交给多个 Agent 协作完成，跑了几轮迭代，把经验沉淀成这篇帖子。

## 问题

直接丢需求给 LLM 说"帮我写 E2E 测试"，效果通常很差：

- 选择器靠猜，`button:nth-child(3)` 一堆，页面一改全崩；
- 没有真实页面上下文，路由和交互流程容易幻觉；
- 用例数量失控，失败一片，没人有精力修。

核心矛盾是：模型缺少"页面长什么样"的第一手信息。所以思路不是让一个 Agent 硬写，而是拆成**探索、生成、验证**三个角色，形成闭环。

## 做法

1. **Explorer Agent（探索）**：接入 Playwright MCP，按任务书逐页遍历目标站点，输出结构化页面快照——路由、可交互元素（优先 `data-testid`）、表单字段、跳转关系，存为 JSON。
2. **Spec Writer Agent（生成）**：读取页面快照 + 仓库里 2~3 个既有测试文件作为风格样例，按用户旅程生成 spec 骨架，每条用例标注"验证什么业务语义"。单批控制在 5~8 条。
3. **Runner / Critic Agent（验证）**：跑 Playwright，失败时把报错与 trace 摘要回传给 Critic，由它判断是选择器问题、时序问题还是真实 bug——前两者自动修，后者停下来报告。

三个角色用同一个 skill 编排。探索产物入库，后续页面改动只重跑 Explorer 做 diff，再由 Writer 增量更新用例，避免全量重生成。

## 踩坑点

- **截图滥用**：早期让每步都截图，上下文很快爆炸。改为只在断言前截一张，并降分辨率。
- **选择器纪律**：必须在任务书里写死"只用 `data-testid` / role / label 三类选择器"，否则模型会自作聪明写 CSS 路径。没有 testid 的老页面，先提 PR 补属性再生成，比让 Agent 硬凑划算得多。
- **断言质量**：生成侧倾向写弱断言（只查元素存在）。Critic 的检查清单里加一条"断言是否体现业务结果"——比如下单后校验订单号落库，而不是按钮消失。
- **环境漂移**：本地与 CI 的 baseURL、测试账号不同。快照里只存相对路径，账号走环境变量注入。

## 可复用建议

- 把**页面快照 JSON** 作为 Agent 间的通用交接物，测试生成与浏览器操作彻底解耦，任何能操作浏览器的 MCP 工具都能复用这条链路；
- 固定种子数据 + 可重置的测试环境，否则 flaky 会淹没 Agent 的修复信号；
- 人只审两样东西：断言语义，以及 Critic 判定为真实 bug 的报告。

## 总结

Agent 写 E2E 不是"一键全自动"，而是探索—生成—验证的闭环。它的价值在于把最枯燥的选择器修补和用例铺量自动化掉，让人退回到定义"什么是对的"这个位置。我们目前新页面首版用例的生成成本从半天降到半小时左右，维护频率也明显下降。编排方式不绑定具体框架，欢迎社区里交流各自的实践。
