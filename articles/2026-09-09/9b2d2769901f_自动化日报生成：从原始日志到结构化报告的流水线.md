## 背景

我们团队有七八个服务，每天产生大量运行日志。日报原来靠人肉：早上拉前一天日志、翻监控、拼一段话发到群里。写一份要二十多分钟，而且每个人抓的重点不一样，口径经常漂移。这次用 OpenClaw 的定时触发 + Agent + MCP 工具把这件事自动化了，跑了一个多月，记录一下做法和踩过的坑。

## 问题

1. 日志分散在多个文件，格式不统一，人工摘录费时；
2. 容易漏掉"不响但异常"的指标，比如错误率连续三天的缓慢上升；
3. 报告口径不稳定，换个值班的人风格就变。

## 做法

核心思路一句话：**确定性的部分用脚本，非确定性的部分才交给模型。** 流水线分四段：

**Step 1 采集与归一化。** 定时任务（cron 触发）按天聚合原始日志，统一转成 JSON Lines：`timestamp / service / level / metric / value`。这一步纯代码，Python 或 jq 就够，完全不碰模型。

**Step 2 统计快照。** 脚本再产出一份"统计快照"：总量、错误分布、环比变化、Top N 异常事件，控制在几百行以内。这是后面模型能看到的唯一输入。

**Step 3 Agent 生成报告。** Agent 通过 MCP 的文件读取工具拿到快照，按固定模板输出：总体状态、异常事件、环比趋势、待跟进事项。prompt 里写死三条约束：只允许引用快照中出现的数字；字段缺失就写"数据缺失"；禁止推测原因。

**Step 4 校验与投递。** 生成结果先过一遍 schema 校验——字段是否齐全、每个数字能否在快照里找到出处。通过才推送；失败重试一次，仍失败则降级为只发原始快照并@人。

## 踩坑点

- **早期直接喂原始日志给模型**：token 爆炸，而且模型会"顺手改写"几个数字。换成快照输入后消失。
- **时区错位**：定时任务按 UTC 跑，日志按本地时间写，出现过日报少两小时数据。现在统一按服务部署时区切日。
- **日志轮转边界**：任务跨零点运行时部分文件已轮转，要按文件名里的日期回捞，不能只读"当前文件"。
- **静默失败**：脚本挂了没人发现，群里照发旧数据。补救规则：当天快照文件不存在就拒绝生成，宁可空跑报警。
- **prompt 漂移**：模板改一次口径就变。现在模板和 prompt 入仓库，改动走 review。

## 可复用建议

1. 能用代码算出来的绝不让模型算，模型只负责归纳与表达；
2. 给模型的输入做减法：快照远好于原始日志；
3. 输出必须可校验，schema 是最后防线；
4. 降级路径和成功路径一起设计，"不发"永远好过"发错的"；
5. 上线前两周保留人工复核，口径稳定后再逐步放权。

## 总结

这套方案的价值不在"用 Agent 写日报"本身，而在于把流程切成采集、归一、生成、校验四段，模型只出现在第三段，前后都是确定性代码。"统计快照喂模型 + schema 兜底"这个模式，可以直接平移到周报、告警摘要、变更回顾等场景，供大家参考。
