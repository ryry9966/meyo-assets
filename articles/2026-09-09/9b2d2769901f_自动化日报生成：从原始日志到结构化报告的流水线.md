## 背景

我们团队有几个长期跑的服务，日志分散在多个实例上。日报此前靠人工：登录机器、grep 计数、粘贴进模板，每天 30 分钟起步，还经常漏项。这篇文章记录把这件事改造成全自动流水线的过程，思路对任何“定时把原始数据变成结构化摘要”的场景都适用。

## 问题

拆开看，人工日报有三个硬伤：

1. **噪音大**：原始日志格式不统一，混着调试输出和堆栈，人肉筛选不可靠；
2. **数字不可信**：手抖、漏统计、口径漂移，数字经常对不上；
3. **LLM 直读日志不可行**：我们最初把日志直接丢给 Agent 总结，结果它会把没出现过的错误“脑补”成有据可查的条目，无法用于汇报。

核心矛盾一句话：**确定性的统计不能交给模型，叙述性的总结不该由人来做**。

## 做法

最终流水线分五段，每段独立脚本、独立落盘：

```
采集 → 清洗/结构化 → 聚合 → 摘要生成 → 分发
```

1. **采集**：由定时任务触发（我们用 OpenClaw 的定时 Agent 任务），拉取目标时间窗内的原始日志到工作目录；
2. **清洗**：逐行解析为 JSON，过 schema 校验；解析失败的行写入 reject 文件，同时记录 `parsed/total` 比例；
3. **聚合**：按模块、级别、错误类型分组，算出次数、耗时分布、错误率。**所有数字在这一步用代码算死**；
4. **摘要**：把聚合后的 JSON 交给 Agent，Prompt 明确“只允许引用输入数据中的数字，禁止推断”，输出套固定模板；
5. **分发**：写入按日期命名的路径，再推 webhook。重跑覆盖而非追加。

## 踩坑点

- **时区**：容器是 UTC，日志时间戳是本地时间，第一版日报窗口整整偏了 8 小时。现在采集时统一显式指定时区；
- **格式漂移**：上游改了一次日志格式，解析器静默返回空结果，日报照发但内容为空。加了两道保险：`parsed/total` 低于阈值直接中断；空报告视为失败而非正常推送；
- **模型编数字**：Prompt 约束后仍偶发。最后在聚合结果里附带一个“数字清单”，要求输出中每个数字都能在其中找到，代码侧做一致性校验；
- **静默失败**：流水线挂了没人知道。补了心跳检查，连续两个周期没产出就报警。

## 可复用建议

- **LLM 只做叙述，不做计算**——这是整条流水线最重要的设计决策；
- 每个阶段的中间产物都落盘，排障时能逐段回放；
- 中间数据必须过 schema，别相信“上游不会变”；
- 报告开头固定一行“数据覆盖区间 + 总条数”，人工核对只看这一行；
- 模板和 Prompt 进版本管理，改口径可追溯。

## 总结

改造后稳定跑了近两个月，人工介入从每天 30 分钟降到 2 分钟（只剩最终核对）。回头看，价值不在于“用了 Agent”，而在于把确定性部分和语言部分干净地分开了：**代码负责准，模型负责顺**。这条分界线想清楚了，周报、告警摘要、变更记录都能用同一套骨架复用。
