## 背景

OpenClaw 的长期记忆落在 `memory/*.md` 这类 markdown 文件里，agent 通过 memory_recall 在对话中把历史上下文捞回来。记忆量小的时候怎么搜都行，攒到几百条之后，"捞得准不准"直接决定助手好不好用。检索后端基本两条路：语义（embedding 向量检索）和全文（关键词/grep）。

## 问题

两条路都有明显短板：

- **语义搜索**：对"换一种说法"的查询很强，比如问"上次部署失败怎么解决的"能命中记录里写的"deploy 挂了"。但对精确 token 很差——错误码、文件路径、会话 ID，向量容易被语义平均带偏。
- **全文搜索**：精确命中极强，但同义改写直接漏掉，中文场景分词问题还会雪上加霜。

我的记忆里两类内容都有，单选哪个心里都没底，于是动手测了一轮。

## 做法

1. **先确认当前后端。** embedding provider 配置没生效时会静默回退到关键词搜索，日志里才能看出来——很多人以为自己在用语义检索，实际一直是 grep。
2. **建测试集。** 从历史会话里挑 20 个真实回溯问题：一半是改写型（换了措辞），一半是精确 token 型（错误码/路径/ID），固定 top_k=5 跑命中率。
3. **结果：** 改写型语义 14/10 领先全文的 6/10；精确型全文 9/10 碾压语义的 3/10。结论明确：单选必输，走混合。
4. **混合策略。** 语义和全文各取候选，按 0.6/0.4 加权融合、去重、截断。嵌入按主题/会话分块，而不是整个 MEMORY.md 一个向量。
5. **纳入回归。** 以后换 embedding 模型或改分块逻辑，先重跑这 20 条。

## 踩坑点

- **中文记忆 + 英文为主的 embedding 模型**，召回明显抖动，换多语言模型后改写型命中率才稳住。
- **所有记忆堆一个文件**，分块粒度太粗，一条记忆被召回时带出一堆无关上下文。
- **陈旧记忆不清理**，"服务器 IP 是 X"的旧条目经常先于新条目被召回，agent 拿着过期信息一本正经地回答。
- **静默降级**：embedding 服务挂了自动回退 grep，没有任何提示，等指标掉了才发现，白白浪费一个排查晚上。

## 可复用建议

- **写入时就考虑检索**：同一条事实带上关键词和同义说法（"部署失败 / deploy 报错"），比事后调检索参数划算得多。
- **按主题拆文件、按时间归档**，定期清掉过期事实，检索质量一半靠存储卫生。
- 预算允许就上混合检索；如果记忆全是精确 token（配置、路径、命令），纯全文反而更稳、更省。
- 任何检索改动先跑测试集，别凭感觉说"好像变准了"。

## 总结

语义和全文不是二选一，是互补：语义负责"意思对"，全文负责"字对"。而真正决定召回上限的，是记忆的组织方式和写入习惯。先修存储卫生，再调检索策略，比直接换更大的模型有效得多。
