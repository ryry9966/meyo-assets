最近一条技术热搜颇值得玩味：把同一个编程任务交给不同的 AI 编程工具，底层调用的明明是同一个模型，最终消耗的 Token 却相差 70 倍。翻译成人话：同样的模型能力，有人 1 块钱办成的事，有人花了 70 块。差距不在模型本身，而在模型外围那一圈"看不见的工程"——系统提示词、上下文组装、Agent 循环、缓存策略。这篇就把这个成本黑洞拆开看看，钱到底漏在哪儿。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/053146881326f8da.png)

## 先补课：Token 计费的三个基本事实

看懂成本差距，先明确三件事：

1. **Token 是计价的最小单位**。1 个 Token 约等于 0.75 个英文单词或半个汉字。代码里充满括号、短变量名和符号，Token 密度比散文更高，同样的代码量换算下来并不便宜。
2. **输入是大头**。编程场景下模型每次要读入大量代码上下文，输入 Token 常占总消耗的 90% 以上。输入单价虽只有输出的几分之一，但架不住基数大。
3. **缓存是分水岭**。主流厂商提供 prompt caching：重复出现的上下文命中缓存后，价格可降至原价的十分之一左右。用不用缓存，同一任务的成本能差一个数量级。

记住这三点，后面的"黑洞"全都由此展开。

## 黑洞一：看不见的 System Prompt 与上下文注入

每个工具把你的问题发给模型之前，都会先"加料"：

- **系统提示词**：工具的行为规则、代码风格约束、安全策略，有的精简到几百 Token，有的膨胀到上万；
- **代码上下文**：光标附近的代码、打开的标签页、通过 embedding 检索出的相关文件，甚至整个仓库的目录树和结构摘要；
- **工具定义**：Agent 模式要告诉模型"你有哪些工具可调用"，每个工具的参数描述（JSON Schema）都是实打实的 Token。

同样一句"帮我修这个 bug"：工具 A 可能只组装 2k Token（当前函数片段加简短指令），工具 B 可能组装 30k（巨型系统提示 + 5 个相关文件 + 目录树）。单次请求差 15 倍，再叠加多轮对话，差距被指数级放大。

## 黑洞二：Agent 循环的乘法效应

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/76763c495d50d7f4.png)

传统代码补全是"一问一答"，一次请求一次计费；如今的 Agent 模式则是"自主多步"：

1. 模型先调用读文件工具 → 发起第 2 次请求；
2. 看到代码后决定搜索关键词 → 第 3 次请求；
3. 找到相关实现后动手编辑 → 第 4 次请求；
4. 测试失败，回来再改 → 第 5、6 次请求……

关键在于：**每一轮请求都要把完整历史对话重新发送一遍**。一个 10 步的 Agent 任务，若每步累积 20k Token 上下文，总输入轻松突破十万——而用户在界面上只看到"任务完成"一次。

70 倍差距的大头正来自这里：有的工具默认单轮问答，有的默认跑完整 Agent 循环，同一个任务，计费次数差了一个数量级。不是模型变贵了，是工具的"自动化野心"在替你下单。

## 黑洞三：缓存、重试与后台调用

还有三个更隐蔽的开销项：

- **没用 prompt caching**：同样的上下文每轮全价重算，成本差 5~10 倍；
- **隐性重试**：输出超时、格式解析失败时自动重试，失败的调用照样计费；
- **后台请求**：自动补全、commit message 生成、代码库索引摘要……你没主动点击的功能也在悄悄烧 Token。

这也解释了一个行业现象：订阅制工具为什么纷纷给重度 Agent 用量设限。厂商按 Token 向模型方付真金白银，个别用户的自动化重度用法会导致单用户成本倒挂，限额本质是一道成本防火墙。

## 三项实测：数据怎么说

复盘报道中的实测设计，思路值得借鉴：

1. **同任务横向对比**：相同的 bug 修复任务分发给多个工具，统计端到端 Token 消耗，Agent 型工具显著高于补全型，最大相差 70 倍；
2. **抓包看请求**：拦截发往模型 API 的真实 payload，发现系统提示词与注入上下文占单次请求的绝对大头，用户的原始输入反而是零头；
3. **缓存开关对比**：同一任务在启用缓存后，总成本直接下降一个数量级。

三条数据指向同一个结论：**决定成本的不是模型，而是工具的上下文策略、循环策略与缓存策略。模型同价，工程不同价。**

## 选工具前，先过这三道关

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/9c8bb92e21344e93.png)

把实测发现收敛成一个判断框架，选型或评估时依次问三个问题：

- **它怎么组装上下文？** 精准检索还是大水漫灌？有没有裁剪、摘要与去重机制？
- **Agent 模式能不能踩刹车？** 有没有步数上限、Token 预算、关键操作前的人工确认？
- **账单透不透明？** 用不用缓存？有没有按请求粒度的用量面板？看不到明细的成本都谈不上可控。

最后给三条实用建议：

1. **按任务分层用工具**：小修小改用轻量补全，复杂重构才开 Agent，把预算花在刀刃上；
2. **看总成本而非订阅费**：留意用量限额与超额条款，重度用户不妨自己算一笔单任务 Token 成本；
3. **建立 Token 预算意识**：像管理云服务器账单一样管理 AI 用量，定期审查哪些后台功能在无声消耗。

模型能力的差距在缩小，工程能力的差距在拉开。下次为编程工具付费时，你买的不只是模型，更是它背后上下文工程的手艺——而这套手艺的账单，真的可能相差 70 倍。
