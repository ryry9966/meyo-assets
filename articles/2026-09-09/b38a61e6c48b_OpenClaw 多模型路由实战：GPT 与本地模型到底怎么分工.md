## 背景

OpenClaw 本身不绑定单一模型，一个 agent 可以同时挂云端的 GPT 系列和本地的 Ollama/vLLM（Qwen、DeepSeek 蒸馏版等）。真正的问题从来不是"能不能接"，而是"每次调用该走谁"。社区里常见两种极端：图省事全走云端，月底账单难看，还把带敏感信息的上下文送出去；或者出于隐私全部本地化，结果复杂工具编排任务的成功率掉一截。

## 问题

路由的本质是三个变量的权衡：质量、成本、数据边界。云端强模型在长上下文推理、多工具编排、严格 JSON 输出上明显更稳；本地模型赢在数据不出机器、边际成本接近零、延迟可控。难点在于很多任务是混合的：一段含密钥的日志需要分析（敏感），但分析本身又需要强推理（质量）。一刀切必然顾此失彼。

## 做法

我们的思路是先分类，再分级，最后配置路由。

**1. 任务分桶。** 按"敏感性 × 难度"把请求分成四类：低敏+简单（格式化、翻译、摘要）、低敏+复杂（多步规划、代码重构）、高敏+简单（内部日志摘要、含 token 的报错排查）、高敏+复杂（脱敏后的架构分析）。分类规则写进 skill 描述，让路由有据可依。

**2. 默认本地，按需升级。** 在 providers 里配两组模型，默认指向本地中小模型（如 14B 量化版），命中升级条件时 fallback 到 GPT。OpenClaw 现成的 fallback 链够用，不需要额外引一套路由服务。

**3. 升级条件要具体、可复现。** 我们用三条：意图分类置信度低于阈值；任务涉及的工具调用超过 2 个；本地模型首轮输出 schema 校验失败。不要用"感觉不行就换云"这种没法写进日志的判断。

**4. 记录路由决策。** 每次请求记一条：命中哪条规则、用了哪个模型、耗时和 token 数。跑一周再回看，路由规则才有迭代依据。

## 踩坑点

- **本地模型的工具调用是重灾区。** 不少量化模型的 function calling 格式不稳，JSON 括号都能少一半。对策：本地侧加 schema 校验加一次重试，仍失败直接升级云端，不要在本地死磕。
- **上下文窗口是隐性截断。** 本地 32K 看着够用，但 system prompt 加 MCP 工具描述加历史很容易超，超了就是静默截断，表现为"模型突然变笨"。要给截断加告警，别靠人肉发现。
- **fallback 别造成重复执行。** 本地模型已经发出工具调用再切云端，可能让同一个 MCP 工具被执行两次。切模型前先检查调用是否已落地。
- **量化版本一换行为就漂。** 从 Q4 换 Q5、从 14B 换 32B，路由阈值全要重标。本地模型变更要走和代码一样的回归流程。

## 可复用建议

- 先做两档粗路由（本地默认+云端升级），跑稳了再考虑更细的打分，别一上来就过度设计。
- 脱敏要放在路由之前，"这次先不脱敏、下不为例"是数据事故的标准开头。
- 给每个 provider 设预算上限和限速，路由写得再好也挡不住一个死循环的 agent。
- prompt 保持模型无关，把模型差异收在适配层，否则每加一个模型都要改一遍提示词。

## 总结

多模型路由不是算法问题，而是工程治理问题：把质量、成本、数据边界变成可测量的指标，用最简单的规则先跑起来，靠日志迭代规则。OpenClaw 的 providers 加 fallback 机制足以承载这套做法，剩下的功夫都在分类规则和回归验证上。从今天开始给你的路由决策记日志，比纠结用哪个模型更有价值。
