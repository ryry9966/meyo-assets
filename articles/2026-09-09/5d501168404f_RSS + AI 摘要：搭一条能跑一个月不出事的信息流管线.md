## 背景

作为搞自动化的人，我每天要扫的信息源不少：技术博客、GitHub Release、几个 Paper feed、少量行业动态。RSS 依然是这些源里最稳的接入方式——结构化、可轮询、不依赖任何平台的推送算法。问题在于量：订阅源一多，未读堆积，真正值得读的可能不到 10%。这篇记录我用 OpenClaw 的 agent + 定时任务搭的「抓取 → 过滤 → 摘要 → 推送」管线，跑了一个多月，成本和稳定性都还可控。

## 问题

直接让 LLM 读原始 RSS 有几个明显毛病：

1. 噪声大，逐条摘要纯烧 token；
2. 多个源常报道同一件事，摘要出来全是重复；
3. 部分 feed 只有 summary 没有全文，直接摘要会失真；
4. 跑批结果不做筛选，等于把噪声换了个格式。

所以目标不是「AI 帮我读」，而是「AI 帮我筛 + 压缩」，最终产出每天一份高信噪比 digest。

## 做法

管线分四段，各段解耦，中间落库（SQLite 就够）：

**1. 抓取层。** miniflux 自托管聚合，没有 feed 的站点用 RSSHub 补。cron 每 30 分钟拉新条目，按 GUID 去重写库。这层不碰 LLM。

**2. 预过滤层。** 规则先行：关键词黑白名单、来源权重、标题 + 首段 simhash 近似去重。实测能砍掉 60-70% 条目，是成本控制的关键。

**3. 摘要层。** 候选条目按主题分批（5-10 条一组）给模型，要求结构化输出：单行摘要 + 3 个要点 + 相关度评分（0-10）+ 是否与已推送内容重复。长文截断时明确要求「仅基于给定内容」，不足就输出「信息不足」——宁可缺失，不可编造。

**4. 推送层。** 评分 ≥ 7 的进当日 digest，按主题分组，每晚 webhook 推到 IM。digest 附原文链接，摘要是入口不是替代品。

编排上我没写死一个大脚本，而是把三段逻辑注册成 MCP tool，由 agent 按计划调度。好处是某段挂了可单独重跑，改 prompt 只动 tool 配置。

## 踩坑点

- **幻觉**：早期摘要会「补全」feed 里没有的细节。改成严格限定输入范围，并在解析时校验要点能否在原文 fuzzy match，匹配不上就丢弃。
- **成本失控**：源加到 40+ 时 token 翻了几倍。加硬预算：每日调用上限，超了只处理预筛后的 top N。
- **HTML 污染**：不少 feed 的 content 带大量内联标签和 tracking 脚本，直接塞 prompt 既费 token 又让模型分心。入库前统一抽纯文本。
- **去重失效**：不同源措辞差异大，simhash 阈值调了好几轮，最后标题 + 首段一起算才稳。
- **feed 腐烂**：一个月后约 1/5 的源陆续失效。加了健康检查，连续失败 N 次告警，人工决定删还是修。

## 可复用建议

- **原始数据先落库，摘要做成独立的幂等步骤**。prompt 迭代后只重跑摘要，不用重新抓。
- **两段式过滤（规则 → LLM）比单靠 LLM 便宜且稳定**，规则层做得越狠成本越低。
- **prompt 当配置管理**，进版本库，每次改动记录效果变化，方便回滚。
- **留反馈通道**：digest 里加「值得 / 不值得」标记，攒两周数据回头调阈值和关键词，比拍脑袋调参有效。

## 总结

这条管线的核心思路：RSS 解决稳定接入，规则便宜地砍量，LLM 只做它擅长的压缩归组，人只面对一份 digest。每天 token 成本几毛钱，维护主要是偶尔修 feed。它不性感，但稳定、可迁移——换个源列表就是另一条管线，比如把 GitHub Release 摘要推给团队。欢迎交流，尤其好奇大家的相关度评分都是怎么定的。
