## 背景

OpenClaw 这类常驻型 AI 助手有个绕不开的问题：agent 平时是"睡着"的，谁来决定它什么时候醒、醒来做什么。heartbeat（心跳）就是这个唤醒机制，常见实现有两条路：

- **轮询（polling）**：定时器每隔 N 分钟唤醒一次 agent，检查任务清单、待办文件，有活干活，没活返回 no-op；
- **推送（push）**：外部事件（webhook、消息到达、定时触发）主动唤醒 agent，事件来了立刻处理。

## 问题

两条路各有硬伤。轮询的问题直观：间隔短了烧 token、刷上下文，agent 还容易在无事可做时硬挤出一段回复打扰用户；间隔长了时效差，用户十分钟前交办的事，半小时后才被看到。

推送的问题更隐蔽：需要一个常驻入口，agent 离线或重启时事件会丢，还要处理鉴权、重放、去重。对一个跑在家用小机器上的个人助手来说，复杂度陡增。

## 做法：低频轮询兜底 + 关键事件推送

我的折中方案分三层：

1. **兜底心跳**：低频轮询（20–30 分钟一次），作为保底检查。心跳 turn 的提示里明确契约：无事可做时只输出固定标记、不调工具、不通知用户，把单次成本压到最低。
2. **推送通道**：时效敏感的事件（告警、邮件到达、外部 webhook）先落本地队列（SQLite 足够），再由 gateway 转成唤醒消息投给 agent，重启不丢、天然去重。
3. **事件分级**：不紧急的（RSS 更新、日报汇总）不推送，只写入待办文件，等下一次兜底心跳统一处理，天然批量化。

## 踩坑点

- **心跳没有幂等**：同一待办被两轮心跳重复执行。给动作加幂等键，或处理前先落标记。
- **心跳 turn 超时重叠**：上一轮没跑完下一轮又触发。加一个简单的锁文件即可。
- **webhook 裸奔**：公网端点必须带签名校验，否则等于给自己开了个 API 后门。
- **agent 在心跳里"硬回复"**：没有明确 no-op 契约时，模型倾向于总输出点什么，噪音直接推进你的 IM。

## 可复用建议

- 先上低频轮询，确认不够用再加推送，别一上来就搭消息总线；
- 队列是推送方案的必需品，不是优化项；
- 记录每次心跳的 token 消耗，跑一周就知道间隔合不合理；
- 心跳和推送最终都收敛为"给 agent 发一条消息"，两条路径共用一套处理逻辑，别维护两套。

## 总结

轮询买的是简单和可靠，推送买的是时效。个人助手的合理答案通常是：低频轮询当安全网，少数高优事件走推送，中间用本地队列兜住可靠性。先用最笨的方案跑起来，让 token 消耗和事件延迟这些数据告诉你，哪里值得升级。
