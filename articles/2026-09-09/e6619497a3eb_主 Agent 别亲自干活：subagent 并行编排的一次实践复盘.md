## 背景

用 OpenClaw 做了一段时间自动化后，最常见的瓶颈不是模型能力，而是让一个主 agent 从头干到尾：上下文越滚越长、任务只能串行、中途一次失败就把整个会话带偏。OpenClaw 的 subagent 机制（派生独立会话、共享同一套 MCP 工具和插件）恰好给了另一个解法：主 agent 只做拆分、派发和聚合，重活交给并行的子会话。

## 问题

举个典型场景：定期扫描三个仓库的依赖变更并出一份汇总报告。让主 agent 自己做，流程是读文件 → 逐个分析 → 写报告，所有中间产物都堆在同一个上下文里。三个仓库还行，到五个以上就开始出现两个症状：一是中间过程把关键指令“挤出”了注意力窗口，后半段输出质量明显下降；二是串行跑完要二十多分钟，超时和中断的风险随时长线性上涨。

## 做法

我们的编排规则最终收敛成四步：

1. **判断可并行性**。任务满足“无相互依赖、输入自足、输出可结构化”才拆。有依赖关系的强拆并行，结果就是互相覆盖。
2. **派发自包含的 prompt**。每个 subagent 的指令必须自带完整上下文：目标、涉及的路径、约束条件、输出格式。不要假设它能看到主会话的历史——它看不到。
3. **规定收敛格式**。强制返回 `status（ok / failed / partial）+ 三行以内摘要 + 产物落盘路径`。这一条是关键，后面讲为什么。
4. **主 agent 只聚合**。汇总各分片结果，failed 的重试一次或降级标记，不亲自介入细节。

改造后五个仓库的扫描从串行 20+ 分钟压到 6 分钟左右，主会话上下文只增加几百 token。

## 踩坑点

- **返回太长撑爆主上下文**。早期没限制输出格式，subagent 把整段分析贴回来，聚合时主 agent 反而先“消化不良”。所以第三步的格式约束不是可选项。
- **静默失败**。subagent 挂掉后返回空内容，聚合端把它当成“没有数据”继续跑，报告里出现静默缺口。显式 status 字段就是为此加的。
- **写冲突**。两个 subagent 同时改同一个文件必炸。我们的原则是并行任务只读，写操作收敛到主 agent 单点执行；必须并行写代码时用独立 worktree。
- **并发顶到 rate limit**。一口气派八个，配额尖峰直接 429。并发上限从 3 起步，观察后再调。
- **隐藏依赖**。比如两个“独立”任务其实都要先更新同一个索引文件，这种只能事后从失败日志里发现，拆分时要人工过一遍。

## 可复用建议

- subagent prompt 四件套模板：目标 / 输入（路径、范围）/ 约束（不许做什么）/ 输出格式。缺一不可。
- 产物一律落盘，subagent 只回传路径和摘要；重试只补失败分片，保证幂等。
- 每个 subagent 记录 token 消耗，编排跑一周后再决定值不值得继续并行——有些任务并行省的时间抵不过费用尖峰。
- 优先把只读类任务（扫描、检索、批量分析）并行化，写类任务保持串行或单写者模式。

## 总结

subagent 编排本质上是工程问题而不是模型问题：上下文隔离解决注意力稀释，结构化收敛解决信息回传，显式状态解决静默失败。建议从两三个并行的只读任务开始试，把模板和失败处理跑顺，再扩展到更重的场景。并行带来的不只是速度，更是主 agent 推理质量的稳定性——这一点比省下来的那十几分钟更值钱。
