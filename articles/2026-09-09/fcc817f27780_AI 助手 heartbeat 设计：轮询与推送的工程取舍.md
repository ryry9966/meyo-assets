## 背景

在 OpenClaw 这类 agent 框架里，heartbeat 指让助手周期性"醒来检查一次"的机制：有没有到期提醒、监控的文件变了没有、定时任务该不该跑。听起来简单，但它往往是 agent 项目里烧 token 最快的地方——因为大部分心跳醒来后其实无事可做。

触发源基本两类：**轮询**（agent 按固定间隔自己查状态）和**推送**（外部调度器/事件总线在条件满足时把事件递给 agent）。两种我都跑过一段时间，记录一下取舍。

## 问题

- 轮询间隔短了，大量空转 turn，每次都是一次模型调用 + 上下文追加，成本和记忆污染都难看；
- 间隔长了，提醒延迟不可接受，错过窗口无补救；
- 直接上推送（webhook/事件总线），会遇到 at-least-once 重复投递、事件风暴时的背压、断线补拉；
- 最容易忽视的一点：心跳把对话上下文当日志用，几轮之后有效上下文被空转记录挤占。

## 做法

核心思路一句话：**把"判断要不要醒"和"醒了干什么"拆开，判断不进模型。**

1. **盘点触发源**。时间型（cron/到期）走调度器；可观测的事件型（文件变化、webhook、新消息）走推送；只有状态不透明的外部源才留给轮询。
2. **两段式轮询**。第一段是无模型的轻量脚本（查 mtime、查 API 返回码、比对阈值），命中条件才发起 agent turn；未命中记一行 metrics 直接结束。
3. **推送侧做三件事**：幂等键（trigger_id + 时间桶）去重；到达即合并——同一 tick 内积压的多个事件合并成一个 turn；断线重连后拉状态增量（delta），不重放整个事件队列。
4. **并发守卫**。上一轮 turn 未结束时不叠加新 turn，pending 事件入队等合并，避免长任务期间心跳堆积。
5. **观测三个数**：唤醒次数、有效 turn 比例（醒来后真的做了事的）、每有效动作的 token 成本。这三项直接决定调参方向。

## 踩坑点

- 心跳间隔照抄示例配置（比如 30s），一晚上烧掉大半月额度；务必显式设置，并按触发源分级。
- 空转 turn 也会写进会话历史，两三天后 agent 开始引用旧心跳"自言自语"；空转结果只进 metrics，不进上下文。
- at-least-once 投递没做幂等，同一个提醒被执行了两遍。
- 笔记本/容器休眠期间 cron 静默丢失，醒来没有补跑逻辑；要么用持续在线的调度器，要么醒来先做一次 catch-up 检查。
- 时区错位：cron 按 UTC 配，用户按本地时间提需求。

## 可复用建议

- **推送优先**：凡是能挂 hook/事件源的东西不要轮询，轮询只作为不透明外部源的兜底。
- 任何心跳路径必须**幂等 + 可合并**，这两点决定推送方案省不省心。
- 两段式检查脚本保持无状态、无模型依赖，方便单独测试和复用。
- 把间隔做成配置项而非常量，并且区分"检查间隔"（便宜）和"模型唤醒间隔"（贵）。

## 总结

轮询赢在简单和无状态，推送赢在精确和成本。真正值钱的设计不是二选一，而是把触发判断从模型推理里剥离出来：用便宜的手段决定醒不醒，用模型处理醒来之后的事。心跳做得好，agent 的主动性才不会变成账单的主动性。
