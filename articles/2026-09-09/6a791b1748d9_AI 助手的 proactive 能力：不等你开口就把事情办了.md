## 背景

绝大多数 Agent 的使用方式是拉式的：打开会话、输入指令、拿结果、关掉。价值不低，但隐含前提是你得记得去问。OpenClaw 这类常驻 Agent 的价值在另一半：它一直在跑，有 cron、heartbeat、webhook 这些事件入口，具备"不等你说"的物质基础。但把常驻跑起来和把 proactive 做对，中间隔着不少工程问题。

## 问题

把 Agent 变成 proactive，本质是回答三个问题：

1. **触发从哪来**：定时任务、webhook、文件变化、邮箱轮询，谁是靠谱的事件源？
2. **该不该做**：不是每个事件都值得唤醒一次完整会话，怎么过滤？
3. **边界在哪**：主动执行写操作、发消息，权限和成本怎么管？

多数"AI 助手很烦"的体验，都出在第三问没答好。

## 做法

我的方案是把 proactive 拆成三段：**触发 → 判断 → 执行**，各自独立、可单独测试。

**第一步，接入事件源。** cron 处理周期任务（早报、仓库巡检）；webhook 处理外部事件（CI 完成、表单提交）；低频信息源（如邮件）用 MCP server 暴露只读工具，由 heartbeat 周期性拉取。

**第二步，两级判断。** 先用规则做便宜的分诊——关键词、发送者白名单、时间窗口，大部分事件在这一层就被丢弃。剩下的才进入一次轻量 LLM 调用，输出结构化结果：`act / draft / ignore` 加一句理由。不要用完整 Agent 会话做分诊，那是大炮打蚊子。

**第三步，动作分级。** 允许的动作分三档：

- **observe**：只读，随便做，结果进日志；
- **draft**：生成草稿（邮件草稿、PR 描述、摘要），推给人确认；
- **act**：直接执行，仅限白名单动作，每个任务有预算上限。

上线初期只用 draft 档，观察一两周误报率，再逐步放开 act。

**第四步，冷却与汇总。** 同一主题设冷却时间（如 6 小时内不重复提醒）；proactive 动作不逐条推送，而是汇进每日一份 digest，紧急事件走即时通知白名单。

## 踩坑点

- **自触发循环**：Agent 自己写的文件、发的消息又变成新事件，无限唤醒自己。解法是给所有 Agent 产出的内容打标，触发器一律跳过。
- **触发风暴**：轮询间隔太短，token 账单两周翻倍。规则过滤必须放在 LLM 之前，并记录每次唤醒的消耗，超预算就熔断。
- **权限继承**：proactive 会话默认继承了交互会话的全部工具，等于无人值守时手握全钥匙。务必给它单独的工具子集。
- **状态过期**：分诊时判断"该做"，执行时前置条件已变。执行前重新校验一次关键条件，别信几分钟前的快照。
- **时区**：cron 按 UTC 配置，早报凌晨四点推到手机。所有定时任务显式声明时区。

## 可复用建议

- 每类 proactive 任务写成一个 manifest：触发条件、动作档位、预算、冷却时间、失败策略，一个文件说清楚，方便 review 和回滚。
- 触发、判断、执行三段分离，各自可单测，不必整条链路跑通才能验证。
- 所有 proactive 动作留审计日志：什么事件、为何触发、做了什么、花了多少。出问题时这是唯一能救你的东西。

## 总结

Proactive 的价值不在"主动"本身，而在克制。判断得准、动作有分级、执行有边界，助手才是"帮你把事办了"；反过来就是推送噪音制造机。工程上没有黑魔法：便宜的事件过滤、明确的动作档位、默认保守的执行策略，加上一段时间的误报观察，就能把主动能力做得可信。
