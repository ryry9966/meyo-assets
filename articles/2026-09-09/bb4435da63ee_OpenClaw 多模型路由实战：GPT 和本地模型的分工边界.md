## 背景

OpenClaw 本质上是一条常驻链路：消息渠道进来，Agent 处理，MCP 工具执行，结果回复出去。模型只是链路中的一环。配置层面它很开放——models 里可以设主模型加 fallback，agents 可以按 agent 各自指定模型，Ollama、LM Studio 这类本地后端也能直接接。问题在于，"能配多模型"和"该把什么任务路由给哪个模型"是两件事，后者才是真正的工程问题。

## 问题

两种极端都会出事：

- **全上 GPT**：定时巡检、群消息摘要这类长跑自动化 token 消耗惊人，月底账单难看；内网日志、个人文件等敏感数据全部出域，合规上说不清。
- **全上本地模型**：闲聊摘要够用，但一遇到多步工具调用、长上下文归纳，小模型开始幻觉，function calling 的参数格式崩坏，Agent 链路静默失败。

## 做法

1. **先给任务分层。** 把 OpenClaw 里的真实负载过一遍：高频低复杂度（提醒、格式化、简单摘要）、低频高复杂度（多工具编排、代码修改、长文档分析）、涉敏感数据（内网日志、本地文件）。列成表，不凭感觉。
2. **主模型留给"贵的正确"。** 主 agent 的 primary 配 GPT 这类一线云模型。主链路承担工具调用和上下文压缩，错了会级联，这里不要省。
3. **本地模型做"便宜量大的脏活"。** 单独开一个子 agent，模型指向 Ollama 里的中等模型，跑摘要、分类、格式转换这类失败成本低、可重试的任务。
4. **敏感数据强制走本地。** 凡是可能带出内网信息的任务，路由到本地模型，慢一点可以接受。
5. **配 fallback，但要可观测。** fallback 用来兜 API 限流和网络抖动，前提是日志里能看清"这次实际用了哪个模型"，否则排障全靠猜。
6. **灰度验证。** 切换路由后拿一周真实流量对比三张表：工具调用成功率、平均延迟、token 开销。

## 踩坑点

- **本地模型的 tool use 兼容性是最大的坑。** 很多模型声称支持 function calling，实际返回的参数结构不稳定，OpenClaw 端校验失败后整条调用链断掉。上线前先拿真实工具集跑一轮冒烟测试，别信榜单。
- **上下文别只看标称值。** 本地模型标 32k，长会话经过几轮压缩后质量下滑明显。核心 agent 别在上下文上抠成本。
- **静默 fallback 会掩盖问题。** 本地模型挂了自动切回 GPT，体验没变，但你以为省下的钱其实都在账单里。fallback 触发必须有告警。
- **GPU 争抢。** 本机同时跑转录、索引、推理时，本地模型延迟抖动很大，路由决策要把"当下机器负载"算进去。

## 可复用建议

- 路由按任务特征（复杂度 / 敏感度 / 频次）决定，不按模型信仰决定。
- 模型池保持 2~3 个。多了之后，评测、提示词适配、监控每一项都是负担。
- 每次路由变更留一版对比数据，成本和成功率必须一起看，单看任何一个都会得出错误结论。

## 总结

多模型路由不是省钱技巧，而是把"正确性、成本、隐私、延迟"四个约束显式化的过程。OpenClaw 提供了全部配置入口，剩下的工作是自己把任务画像摸清楚。我的经验浓缩成四句话：主链路不省、脏活下放、敏感数据不出门、fallback 可观测。做到这四条，路由策略基本不会返工。
