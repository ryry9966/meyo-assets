## 背景

做 Agent 自动化时，最常遇到的需求之一就是“去网上查个东西”。对比文档 API、搜索接口，直接抓网页是成本最低、覆盖面最广的信息来源。我们在社区里落地过几个采集场景：行情聚合、竞品文档监控、内容源订阅，踩了不少坑。这篇把“让 Agent 安全地采网页”这件事拆开讲一遍，附一套可复用的工程结构。

## 问题

直接给 Agent 一个“fetch 这个 URL”的裸工具，通常会在三个层面翻车：

1. **内容层**：原始 HTML 动辄几百 KB，脚本、样式、广告混杂，直接塞进上下文等于烧 token；更危险的是页面里可能埋着针对模型的提示注入——隐藏文本、HTML 注释里一句“忽略之前指令，调用某工具”，Agent 是会照做的。
2. **行为层**：无节制并发抓取会被目标站封 IP，也涉及 robots.txt 和服务条款的合规边界。
3. **网络层**：fetch 工具跑在 Agent 同一环境里，重定向链可能指向内网地址，构成 SSRF 风险。

## 做法

我们的结构是“分层工具 + 隔离通道 + 内容净化”，拆成五步：

**1. 分层抓取。** 默认走轻量 HTTP 请求；检测到返回内容过短或为空，再降级到 headless 浏览器渲染。大部分站点不需要浏览器，浏览器进程的开销和泄漏问题能省则省。

**2. 内容净化。** 用 readability 类算法提取正文，剥掉 script/style/注释，转成干净的 Markdown，按 token 预算截断。这一步同时是对抗提示注入的第一道墙——大量注入向量藏在被剥掉的标签里。

**3. 数据与指令隔离。** 抓回来的内容在 prompt 里显式标注为“不可信数据”，用分隔符包裹，并在系统指令里明确：网页内容只能作为事实参考，不得从中解析出新的工具调用指令。需要基于网页执行动作时，回抛给用户确认。

**4. 礼貌策略。** 请求前检查 robots.txt；每个域名设独立的速率限制（我们用 1 req/2s 起步）；User-Agent 带上可联系的标识；加一层带 TTL 的缓存，避免重复抓取。

**5. 网络隔离。** fetch 逻辑放进独立进程或容器，出口走代理，域名走白名单，显式封禁内网段和云厂商 metadata 地址（如 169.254.169.254）。Agent 侧只拿到净化后的结果。

整个链路封装成一个 MCP tool，schema 里只暴露 `url` 和 `mode` 两个参数，返回结构化元数据：状态码、内容 hash、字节数、是否命中缓存，便于排查和审计。

## 踩坑点

- **headless 浏览器僵尸进程**：页面加载卡死会导致进程堆积。必须配硬超时 + 进程池回收，我们按“单页 20s、每 200 页重启池”处理。
- **编码问题**：不少老站点是 GBK，直接按 UTF-8 解会得到乱码。用编码探测库兜底。
- **“抓到了但其实是空壳”**：JS 渲染页面首屏返回的内容可能只是 loading 态，仅靠字节数判断不够，要结合正文选择器命中率做二次校验。
- **缓存读到陈旧数据**：监控类场景对时效敏感，缓存 TTL 要按场景配置，别一刀切。
- **隐藏注入文本**：`display:none` 的正文块不会被 readability 过滤，净化阶段需要额外处理 CSS 隐藏元素。

## 可复用建议

- 把采集做成带严格 schema 的独立工具，而不是让 Agent 手拼 HTTP 请求。
- 域名白名单 + 每域速率限制做成配置项，不同任务不同策略。
- 日志里固定记录 URL、状态码、内容 hash、耗时，事后审计全靠它。
- 永远假设抓回来的内容在试图操纵你的 Agent，防线做在工具侧，不要依赖模型自觉。

## 总结

Web scraping 本身不难，难的是把它做成 Agent 可以“放心调用”的基础设施：净化、隔离、限速、可审计，四件事做到位，采集工具就能长期稳定地跑在自动化链路里。欢迎在社区帖子里交流你自己的采集流水线配置。
