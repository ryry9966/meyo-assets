## 背景

OpenClaw 的 Cron 工具很适合做定时自动化：每天早上汇总一次 GitHub 通知、定期巡检日志、每周生成待办回顾。但很多人写 cron 任务的方式，就是把平时聊天的那句话原样塞进去——"每天早上八点帮我看下通知"——然后发现输出忽长忽短、格式漂移，有时干脆跑偏。

原因很简单：cron 任务的执行环境和交互对话完全不同。

## 问题：定时任务不是对话

交互时，agent 有上下文、有历史，你可以随时追问纠正。Cron 任务没有这些：

- **没有会话上下文**：尤其隔离会话模式下，每次运行都是全新 session，"上次说的那个文件"它根本不知道；
- **没有现场纠偏**：跑歪了没人拉它，输出直接投递到你的频道；
- **指令是静态的，环境是动态的**：路径变了、消息变多了，instruction 不会自己更新。

所以 cron 的 instruction 不是"提示词"，而是一份**无人值守的运行手册**。

## 做法：按 Runbook 的方式写

我现在的模板固定五段，每个任务都套：

```text
【目标】一句话说清要产出什么。
【输入】数据从哪来：具体路径 / 具体工具调用 / 具体查询方式，写绝对路径。
【步骤】先做什么后做什么，2~4 步，不让 agent 自由编排。
【输出】格式锁死：不超过 X 行、固定字段、发到哪个频道；无新内容时回复"无更新"或直接不发。
【边界】明确禁止项：不做写操作、重试不超过 N 次、失败时说明原因而不是静默跳过。
```

两个关键实践：

1. **状态外置**。需要"增量"语义的任务（比如只处理新消息），让任务把游标写进状态文件，每次先读再写。别指望 agent 记得上一次。
2. **先手动跑通再上日程**。写完先交互式跑一遍或用立即执行验证输出，确认格式和副作用符合预期，再启用 cron 表达式。这和上线前先过 staging 是一个道理。

## 踩坑点

- **时区**：确认调度器按哪个时区解析 cron 表达式，配置里显式指定（如 `Asia/Shanghai`），别赌宿主机默认值，迁移机器时最容易翻车；
- **一个任务三件事**：又要汇总通知又要清文件又要发日报，职责越多越容易半途跑偏，拆成多个 job；
- **输出刷屏**：agent 默认输出是"写给人看的长报告"，必须在 instruction 里锁格式，比如"第一行一句话结论，最多再列 5 条要点"；
- **静默失败**：网络错误、工具不可用时它可能敷衍一句就结束。要求失败也按固定格式上报，必要时投到单独频道；
- **提示词腐烂**：instruction 里写死了模型名、路径、插件命令，环境一升级就全废。像维护代码一样定期 review。

## 可复用建议

1. 把 instruction 当代码：留版本注释、改动有记录、定期 review；
2. 幂等优先：同一时间跑两次，不该产生两份副作用；
3. 格式即契约：输出结构写进 instruction，别靠"它应该懂"；
4. 短路条件前置：没有新数据就早退，省 token 也省注意力；
5. 沉淀自己的模板库，新任务复制后改三处（输入、输出、时间）即可上线。

## 总结

Cron instruction 的质量，直接决定自动化是省心还是添乱。核心一句话：**把它当成写给一个没有记忆、不能追问的值班同事的交接文档**——目标、输入、步骤、格式、边界，一段都不能少。写清楚这五段，大多数"定时任务跑飞了"的问题在上线上线前就能拦住。
