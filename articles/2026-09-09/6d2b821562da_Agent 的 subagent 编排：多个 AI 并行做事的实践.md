## 背景：单 agent 的瓶颈

用 Agent 干活久了会遇到一个典型场景：任务一大，单 agent 就开始“变慢变笨”。上下文里塞满了中间产物——搜索结果、报错日志、读过一半的文件——真正有用的信号被稀释。而且所有步骤严格串行，一个调研任务可能大半时间花在等待工具返回上。

## 问题：不是模型不行，是编排不行

具体痛点有三个：

1. **上下文污染**：一次任务里读二十个文件，早期内容到后期已经没有参考价值，却一直占着窗口；
2. **串行等待**：互不依赖的子任务被迫排队；
3. **脆弱**：中途一步报错，整条任务链断掉重来。

## 做法：扇出-汇总模式

我在 OpenClaw 里用得最多的编排形状是 fan-out / reduce：

1. **主 agent 只拆解和汇总，不直接干活**。它把任务切成若干互不依赖的子任务，每个子任务定义清楚：输入、边界（只动哪些文件/目录）、输出格式。
2. **每个子任务交给一个 subagent**，各自有独立上下文窗口和受限工具集。比如只挂载 MCP 的文件读写工具、禁掉 shell；“给这五个模块各写单测”就拆成五个 subagent，每个只允许碰自己那个目录。
3. **并发度控制在 3–5**。再高容易撞 API 限流，也更容易在共享资源上打架。
4. **结构化回传**。subagent 不返回完整过程记录，只返回约定格式的结果：改动文件列表、结论、阻塞原因。主 agent 拿到的是压缩后的信息，汇总时上下文依然干净。

实测收益：一批文件级重构任务，串行约 40 分钟，并发后 12 分钟左右跑完，主 agent 的上下文占用降到原来三分之一。

## 踩坑点

- **共享工作区冲突**：两个 subagent 同时改一个文件，或撞上对方的 git index lock。解法是拆任务时按文件/目录硬切边界，git 操作只留给主 agent 串行做。
- **结果回传太大**：subagent 把整段 diff 塞回来，主 agent 上下文立刻爆掉。约定输出必须是有上限的结构化 JSON，原始产物落盘、只回传路径。
- **错误被静默吞掉**：并发任务里一个 subagent 失败若只返回空结果，主 agent 会当成“没问题”继续汇总。每个子任务必须带状态字段，失败要给原因；重试的前提是任务幂等。
- **成本翻倍**：每个 subagent 都要重新加载一遍项目上下文，token 消耗不是线性的。“一个 subagent 只处理一个函数”这种粒度多数时候不划算。

## 可复用建议

- **先写任务契约，再写编排**：输入、边界、输出格式先固定，编排逻辑只是执行契约。
- **按资源边界拆分，不按逻辑步骤拆分**：前者天然无冲突，后者引入隐式依赖。
- **每个 subagent 单独留会话日志**，排障时能还原完整轨迹。
- **主 agent 保持“瘦”**：上下文里只放任务列表和汇总结果，不放中间产物。
- **幂等是并发的前提**，不能幂等的操作（比如写数据库）老老实实串行。

## 总结

subagent 编排不是新范式，本质是分布式系统的老经验——任务切分、资源隔离、结构化通信、失败处理——在 agent 语境下重用一遍。收益明确：更快、上下文干净、局部失败不拖垮全局。但它同样放大坏设计的问题：任务边界切不清楚的编排，比单 agent 串行更混乱。建议从一批互不依赖的小任务开始试，比如批量写单测、批量做代码迁移，跑通一次完整的扇出-汇总流程，再考虑更复杂的依赖编排。
