## 背景

跑过一段时间的 Agent 项目后你会发现：脚本写完只是开始，真正消耗维护精力的是各种"外部依赖挂了"的场景——LLM 供应商限流、MCP 工具背后的第三方 API 超时、搜索/天气/支付接口间歇性 5xx。传统 Web 服务也有这个问题，但 Agent 放大了它：一次任务动辄串起十几个工具调用，任何一环抖动都可能让整条链报废，或者更糟——带着错误状态继续跑完。

## 问题在哪

Agent 场景下的故障处理有两个特殊之处：

1. **失败发生在任务中间态**。"从头再来"代价高，还可能重复产生副作用（重复下单、重复发通知）。
2. **Agent 有"幻觉式恢复"的倾向**。工具返回异常时，模型可能编一个看似合理的值接着推理，错误被静默吞掉，直到最后产出一份自信满满的错误结果。

## 做法：把恢复逻辑压到工具层

核心原则：重试、降级、超时这些事不要指望模型自己判断，写死在工具 / MCP server 的封装里，Agent 只看到干净的结果接口。

**1. 错误分类先行。** 瞬时错误（超时、429、502/503）走自动重试；确定性错误（401、400、参数校验失败）直接结构化返回给 Agent，让它改参数或改道，不要浪费重试额度。

**2. 重试要克制。** 指数退避加随机抖动，上限 2–3 次，且只对幂等操作开自动重试。写操作一律要求下游支持幂等键（任务 ID + 步骤号），否则宁可失败上抛。

**3. 超时必须显式。** 每个工具调用设独立超时（HTTP 类我一般给 15s，长任务类按业务定），避免一次挂起卡死整个会话。很多"Agent 不动了"，其实是某个工具没设超时。

**4. 降级要诚实。** fallback 到备用 API 或缓存数据时，返回结果必须带 `degraded: true` 和数据时间戳。否则 Agent 拿着三天前的缓存继续推理，比直接失败更危险。

**5. 长任务落检查点。** 多步骤任务在每步之间持久化状态，失败后从最近检查点恢复，而不是整个重跑。对自动化流水线这一条尤其重要。

## 踩坑记录

- 在 MCP server 里把异常 catch 掉返回空字符串——Agent 会把空结果当成功，后续步骤全部建立在假数据上。错误要么抛出去，要么结构化返回。
- 把"最多重试 3 次"写在系统提示词里让模型遵守——不可靠，模型偶尔重试十次，偶尔一次都不试。控制流必须在代码里。
- 重试没做去重，一次下单接口抖动导致用户收到两条通知。
- fallback 返回了空数组但没标记降级，Agent 报告"当前无任何数据"，用户差点误删正常配置。

## 可复用建议

- 工具层统一封装 `withRetry(fn, { retriableErrors, maxAttempts, timeout })`，所有插件复用，不要每个工具各写一套。
- 错误返回固定结构：`{ ok, retriable, code, message }`，模型看到 `retriable` 才请求重试，减少瞎猜。
- 记录每次工具调用的失败率与耗时，故障往往在指标恶化几天后才被用户感知到。
- 给关键外部依赖准备一个 healthcheck 工具，Agent 开工前先探一次，早失败早改道。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 的日常运行环境。错误恢复本质上是工程问题而非提示词问题：分类、退避、显式超时、诚实降级、检查点——这五件事做在工具层，模型层只负责拿到干净信号后做决策。做到这些，你的 Agent 才算从"演示能跑"进入"敢挂在自动化里"的阶段。
