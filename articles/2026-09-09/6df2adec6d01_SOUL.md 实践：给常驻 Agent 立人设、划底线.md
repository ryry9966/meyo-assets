## 背景

OpenClaw 这类长期运行的 Agent 和“一次性对话”最大的区别在于：它有记忆、有常驻身份，还会通过 Telegram 等渠道代表你发言，通过 MCP 工具操作你的文件、日历甚至付款流程。默认的系统提示词只能保证“能干活”，保证不了“像谁、不越界”。

SOUL.md 就是补上这一层的文件。它和管权限的 config、管任务流程的 AGENTS.md 各司其职，专职回答两个问题：这个 Agent 是谁，以及它绝不做什么。

## 问题

不加约束时，常见三类翻车：

1. **人设漂移**：跨天会话里，昨天冷静简洁的助手今天突然满篇表情符号。
2. **过度顺从**：你在群里半开玩笑说“帮我回他一句”，它真的以你的口吻发了出去。
3. **边界模糊**：分不清“建议你删掉这个文件”和“直接执行删除”之间的区别。

这些问题靠往系统提示词里堆话解决不了——职责混在一起，改一处动全身。

## 做法

我的 SOUL.md 最终收敛为四段，总共不到 400 字：

**1. 身份（一段话）**：一句话定位 + 与用户的关系，例如“你是我的常驻助理，语气像话不多但靠谱的同事”。别写传记。

**2. 语气（给例子，不给形容词）**：写“专业、友好”没用，模型抓不住。直接给三条范例：收到模糊指令时怎么追问、拒绝时怎么说、汇报结果时用什么句式。

**3. 硬性边界（3~7 条，祈使句）**：不主动给通讯录联系人发消息；不执行涉及付款转账的操作；不删除回收站之外的数据；用户情绪激动时先确认再执行。每条都要具体到能判“是/否”。

**4. 降级行为**：拿不准时的默认动作。我写的是“涉及外发、花钱、删除的操作，先复述意图请求确认，被拒绝就停下”。

写完放进版本控制，和代码一样走 review。

## 踩坑点

- **写太长**。超过一两千字后，后半段明显被稀释，底线条目会失焦。宁可删，不可堆。
- **把 SOUL.md 当权限系统**。它是行为软约束，真正的硬限制要落在工具权限层：只读挂载、白名单、危险命令二次确认。SOUL 拦不住越权调用。
- **人设与场景冲突**。工作渠道要克制，私人聊天太正式又很怪。多渠道使用的话，语气段按渠道各写一条。
- **升级后不复查**。模型一换，人设表现可能整体漂移，SOUL.md 要像回归测试一样，重跑几个典型场景。

## 可复用建议

- 四段式模板：身份 / 语气范例 / 底线清单 / 降级行为。先抄结构再填内容，不要整份搬别人的。
- 建立“事故→分层”的习惯：Agent 做错事时，先判断是提示词问题、权限问题还是 SOUL 问题，只改对应那一层。
- 每月用一个固定的小红队提示词集合（诱导发消息、诱导花钱、诱导越权）跑一遍，边界失效就更新文件并记录变更原因。

## 总结

SOUL.md 的价值不在“拟人化”，而在收敛不确定性：Agent 是谁、什么话不能说、什么事必须先问。写短、写具体、进版本控制，并在工具层配好真正的硬约束——这四件事做到，长期运行的 Agent 才敢放心让它接触真实世界。
