## 背景

社区内容运营有个老大难：每周精选、版本公告、常见问题整理，重复性高但没法不做。我的目标很克制——不是造一个"全自动内容工厂"，而是让一个跑在 OpenClaw 上的 Agent 承担 80% 的重复劳动，人只做最后把关。

## 问题

第一版是典型的一次性脚本：调 LLM 生成，直接 POST 到社区 API。跑三天就暴露了问题：

- 文风漂移，不同批次像不同人写的
- 网络超时重试后，同一内容发了两遍
- 网关重启后定时任务重复触发
- 出了问题没有任何审计痕迹，不知道哪篇是谁发的

结论：发帖这个动作本身很简单，难的是幂等、限流、审批和可回溯。

## 做法

架构上分四层：

1. **触发层**：OpenClaw gateway 的定时任务（每周一 09:00），同时保留手动触发的口子。
2. **生产层**：Agent 按 skill 模板生成草稿。输入是固定的信息源（git log、issue 列表、上周热帖），prompt 模板进 git，改动走 PR。
3. **封装层**：社区 API 用 MCP 包了三个工具——`list_posts`、`get_post`、`create_post`。Token 用专用小号，只开读写帖子的最小权限。
4. **发布层**：默认走"人审模式"——草稿先推到我的 IM 私聊会话，回复"发"才调用 `create_post`；发布后内容 hash、帖子 ID、时间戳写入本地 SQLite。

稳定跑两周后，才对低风险内容（如每周精选）关闭人审；公告类始终保留。

## 踩坑点

- **文风漂移**：靠"结构化模板 + 两篇固定 few-shot + 温度 0.3"压住。光写"用工程化语气"没用，必须给样本。
- **重复发帖**：重试逻辑放在客户端，发布前先按 hash 查本地库；后来又在 MCP 工具里加了服务端查重，双保险。
- **定时任务重复触发**：gateway 重启后任务重放。解法是把"本周已生成"状态持久化，任务开始先检查。
- **审批消息被当成新指令**：我在私聊里回了句"再改改标题"，Agent 直接重跑整个流程。后来把审批会话和任务会话隔离，审批走状态机，只认"发 / 弃 / 改"三个词。
- **富文本转义**：Markdown 转社区编辑器格式时丢过段落和代码块，最后在插件里做了确定性转换，不再依赖模型输出格式。

## 可复用建议

1. 先跑"只产草稿不发布"模式至少一周，确认质量再开闸。
2. 幂等键和限流不是可选项，是基础设施，发帖类自动化必须有。
3. API 封装越薄越好，业务逻辑留在 prompt 和工作流里，方便迭代。
4. 所有产物落盘：prompt 版本、草稿、发布记录、错误日志，出事能回放。
5. 高风险内容（公告、涉及时事）永远保留人审。

## 总结

这个机器人代码量不到三百行，大部分精力花在状态管理和失败路径上——这才是自动化的真实成本。它现在每周稳定产出，我从没指望它"写得像人"，只要求它稳定、可撤回、出问题能查。想上手的朋友，建议从最小闭环开始：一个定时任务、一个薄 MCP 工具、一个人审环节，先跑起来再谈优化。
