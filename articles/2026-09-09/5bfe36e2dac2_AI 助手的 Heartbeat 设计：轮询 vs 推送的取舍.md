## 背景

OpenClaw 这类常驻 Agent 框架里，heartbeat（心跳）是让助手"主动做事"的基础机制：每隔一段时间唤醒一次模型，检查有没有待办、要不要整理记忆、该不该执行定时任务。实现上有两条路线——**轮询**（agent 定时醒来自己查）和**推送**（外部事件来了主动叫醒 agent）。我们在搭自动化工作流时两条都走过，这里记录一下取舍。

## 问题

纯轮询的代价很直接：每次心跳都是一次完整的模型调用，带上 system prompt 和上下文，token 成本随频率线性增长。为了"感觉实时"把间隔压到一两分钟，一天光空转就烧掉不少调用；放宽到 30 分钟，用户又会觉得"助手把我忘了"。

纯推送则反过来：省 token、延迟低，但工程量大——webhook 可达性、事件去重、失败重试都要自己管。更麻烦的是有些事根本不是事件驱动的，比如"每天早上汇总一次昨日数据"，没有事件可推。

## 做法：推送为主，轮询兜底

我们的结论是不二选一，而是分层：

1. **给唤醒源分类**。把所有触发点列出来，标注两个属性：能否容忍延迟、是否天然事件化。用户新消息、监控告警属于低延迟事件，走推送；记忆整理、日报汇总属于时间驱动，走轮询。
2. **推送层**。外部系统通过 webhook 或 MCP 通知进入消息队列，agent 订阅队列，事件到达即唤醒。关键是在进模型之前先过一层确定性判断：dedup key + 合并窗口，5 秒内的同类事件合并成一次唤醒。
3. **轮询层降级为安全网**。心跳保留但拉长到 30 分钟，职责收窄为三件事：补偿丢失的推送、执行 cron 类任务、活性自检。心跳 prompt 里不带完整业务上下文，只放一张轻量任务清单。
4. **可观测**。每次唤醒记录 wake_reason、消耗 token、实际产出的动作数。跑一周后你会得到一张"谁在浪费心跳"的清单，据此调频率。

## 踩坑点

- **心跳带全量上下文**。最初我们的心跳 prompt 直接复用会话上下文，每次空转 8k token。改成轻量清单后，单次降到 500 以内。
- **推送没做幂等**。webhook 重试导致同一条告警触发两次执行。dedup key 必须在入队时生成，不能指望模型自己判断"这事是不是做过了"。
- **用模型做"要不要醒"的判断**。有人把空转检查也交给 LLM，这等于把省下的 token 又花回去。确定性检查（查文件标志位、查数据库状态）能挡掉九成无效唤醒。
- **定时任务依赖心跳对齐**。30 分钟心跳意味着 cron 误差最多 30 分钟。对时间敏感的任务要单独用精确调度器，心跳只做兜底。

## 可复用建议

- 心跳频率做成 per-plugin 配置，不要全局一个值；
- 合并窗口 3–10 秒通常够用，再长会影响体感；
- wake_reason 落日志，这是后续优化最值钱的数据；
- 接入任何新事件源之前，先问一句：这条事件重试三次会发生什么？

## 总结

轮询和推送不是对立选项，而是对应不同延迟容忍度的两种唤醒通道：推送负责快，轮询负责稳，中间用确定性闸门控制成本。把"每次唤醒都花钱"当作第一性假设来设计，heartbeat 才不会从功能变成负担。
