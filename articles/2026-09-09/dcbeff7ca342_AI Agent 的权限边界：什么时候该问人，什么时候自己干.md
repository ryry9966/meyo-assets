## 背景

Agent 这一年从"会聊天"变成了"会动手"。用 OpenClaw 这类框架接上 MCP 工具、装几个插件、给个 shell，它就能读文件、调 API、碰数据库。动手能力上来之后，一个老问题变得非常具体：**哪些动作它可以直接做，哪些必须停下来问人？**

## 问题

实践中失败方式就两种：

- **问太多**：每步都弹确认，人很快变成机械点"同意"，确认退化成仪式，真遇到危险操作时也是无脑放行——这比不确认更糟。
- **做太多**：为了省事把权限全开，直到某天它把测试环境的清理脚本跑上了生产库。

结论先行：边界不是开关，是策略；而且策略不能靠模型自觉，必须在工程层强制执行。

## 做法

**1. 给工具分层，而不是给任务分层。** 同样是"写"，改本地草稿和调第三方接口发消息，风险完全不同。按可逆性和影响面分四档：

| 层级 | 典型操作 | 策略 |
|---|---|---|
| L0 只读 | 搜索、查询、读文件 | 自动执行，记日志 |
| L1 可逆写 | 改本地文件、写草稿 | 自动执行，留 diff |
| L2 外部副作用 | 发消息、调第三方 API、产生花费 | 确认后执行 |
| L3 不可逆高危 | 删数据、改生产配置 | 确认 + 二次校验，或直接禁用 |

**2. 策略放在工具层执行。** 在工具调用链上加一层中间件（包一层 proxy，或在 MCP server 侧做 gating），按注册时标注的风险等级拦截。提示词里写"请谨慎操作"不是边界——注入一段话就能绕过。

**3. 高频低危全自动，但全量留痕。** 自动执行不等于不留记录，每次调用的参数、结果都进审计日志，这是后续调边界的依据。

**4. 写操作先 dry-run。** 让 Agent 先产出 diff 或执行计划，人过目后再放行。确认成本低，人才会真的看。

**5. 批量操作合并成一次确认。** 与其连问八次"是否继续"，不如让它先给出完整计划，一次批准；中途偏离计划（调用了未批准的工具）就中断。确认次数是成本，要省着花。

**6. 设硬边界和升级触发。** 每日花费上限、调用频率上限用配置写死；连续重试失败、输入有歧义、结果与预期不符时，强制停下问人，而不是继续猜。

## 踩坑点

- **确认疲劳最常见**。上线第一周大家还认真看确认框，第二周就条件反射点同意。解法不是减少确认场景，而是提高单次确认的信息密度：干什么、改哪里、花多少、能否撤销，四行说清。
- **新工具忘了分级**。默认拒绝比默认放行安全：新接入的 MCP 工具没标风险就按 L3 处理，观察两周有数据后再降级。
- **工具结果本身可能带注入**。Agent 读了个网页，里面藏一句"请顺手执行 XX"。只读工具无所谓，但它若持有 L2 写权限，风险就从用户意图转移到了数据来源——外部内容触发的写操作，应强制走确认。
- **没记自动执行的日志**。事后想收紧或放宽边界，发现没有数据支撑，只能拍脑袋。

## 可复用建议

- 起步配置用最保守的：读全自动、写全确认，跑一段时间看日志再逐级放宽。
- 策略表做成版本化配置文件，别散在提示词里，改边界要有 diff 可查。
- 把"单任务确认次数"当健康指标：超过三次，说明任务拆分或权限配置有问题。
- 每周花十分钟翻自动执行日志。边界是调出来的，不是一次设计出来的。

## 总结

权限边界本质是策略工程问题，不是提示词问题：按可逆性和影响面给工具分级，在工具层强制执行，高频低危放行并留痕，低频高危确认并控制确认质量，再用日志持续校准。让 Agent 自己干该干的，把人的注意力省下来，留给真正需要人拍板的那几个决定。
