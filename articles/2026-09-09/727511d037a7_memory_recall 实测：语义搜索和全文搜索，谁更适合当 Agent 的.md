## 背景

OpenClaw 的 memory_recall 是记忆链路里调用最频繁的一环：会话开始或任务执行中，从 memory 目录的一堆 markdown 文件里捞出相关片段注入上下文。默认走语义检索（embedding 向量），也有人直接用全文关键词（SQLite FTS5 / ripgrep）。两种方案我都实跑过一段时间，结论很明确：**各有盲区，单独用哪个都不够**。

## 问题

两个真实翻车场景：

- **语义路的坑**：搜 `ERR_SOCKET_TIMEOUT` 这类精确 token，embedding 召回基本失效——错误码、配置名、版本号这种"字面即语义"的内容，向量表示很平。反过来，问"上次支付回调 500 的原因"，会把语义相近但事实无关的"上次部署失败"排到前面。
- **全文路的坑**：写记忆时记的是"支付宝"，提问时说的是"alipay"，一个字对不上，直接空结果。中文同义改写比英文还多，全文路对此非常脆弱。

## 做法：双路召回 + RRF 融合

1. **切块入库**：memory 文件按标题/小节切 300–500 token 的块，元数据带文件路径和日期。别整文件入库，也别切太碎。
2. **双路召回**：全文一路（FTS5 或直接 `rg`），语义一路，各取 top 10。
3. **融合排序**：用 RRF（score = Σ 1/(k + rank)，k 取 60），只看排名不看分数，省去两路分数量纲对齐的麻烦。
4. **后处理**：按日期做轻量衰减、去重、阈值截断。
5. **注入**：命中块连同来源路径一起进 prompt，出问题时能回溯到原文件。

最小改动版：语义召回为空或 top1 分数过低时，fallback 到全文 grep。五行代码，能救回一半的精确 token 场景。

## 踩坑点

- **embedding 模型对中英混排不友好**：选型时务必用中文样本实测，"部署"和 "deploy" 在不少模型里向量距离很远。
- **增量索引缺失**：memory 是高频写入的，忘了增量重建，就会"明明记了却 recall 不到"——而且没有报错，全靠体感发现。
- **静默失败**：日志里要能区分"没有这条记忆"和"检索没命中"，记下 recall miss，否则排查永远在猜。
- **chunk 过大**：命中一段注入一大段，token 爆炸还稀释注意力，top1 看着分高，实际不可用。

## 可复用建议

- 默认上混合检索，别二选一；资源敏感时"语义为主 + 全文兜底"也够用。
- 原始 markdown 是 source of truth，索引只是加速层，随时可重建。别把唯一状态存在向量库里。
- 攒一个 20–50 条的召回测试集（问题 → 应命中的文件），每次改检索参数跑一遍，比肉眼判断靠谱得多。
- 高频事实（服务名、端口、凭据键名）在记忆里用稳定命名书写，给全文路留抓手。

## 总结

语义搜索解决"换个说法也能找到"，全文搜索解决"精确 token 一击即中"。memory_recall 是高频、低容错路径，工程上的正确答案是**双路召回 + 融合**：实现不复杂，盲区互补，还保留了可回溯的原始文件。先跑混合，再谈调优。
