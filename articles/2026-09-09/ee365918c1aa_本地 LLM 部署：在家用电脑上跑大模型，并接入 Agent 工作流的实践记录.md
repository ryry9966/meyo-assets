## 背景

过去一年小模型的实用化速度超出预期。7B~14B 档的模型在工具调用、JSON 结构化输出这类任务上已经够用。对 OpenClaw 用户来说，本地部署的价值不在"复刻旗舰模型"，而在三件事：私有数据不出门、离线可用、调用不计费——Agent 工作流动辄一晚上跑几千次调用，本地模型的边际成本为零。

## 问题

真正的门槛不是"跑起来"，而是"跑得适合 Agent"。网上大部分本地部署教程以聊天问答为目标，但 Agent 场景的痛点完全不同：上下文要长（工具结果回灌很快撑爆窗口）、function calling 要稳（坏一个 JSON 整个循环就断）、吞吐要扛得住并发。这三点决定了选型和参数，答案和聊天场景差别很大。

## 做法

1. **先盘硬件，再选模型。** 经验值：8B 模型 Q4 量化约占 5~6GB 显存，14B 约 9~10GB，32B 基本 24GB 起步。显存不够就别硬上，掉到 CPU 推理后速度往往掉一个数量级。macOS 统一内存可以放宽一档，但同样要给 KV cache 留 20~30% 余量。
2. **部署层选 Ollama 或 llama.cpp 的 `llama-server`**，两者都提供 OpenAI 兼容接口。OpenClaw 侧只要把 `base_url` 指到 `http://localhost:11434/v1`，模型名填对应 tag 即可。想要更细的参数控制（批次、KV cache 量化）用 llama.cpp，想省事用 Ollama。
3. **模型选型盯两点**：原生支持 tool calling、官方提供 Q4/Q5 量化。Qwen 系列在中文 Agent 任务上的 function calling 是我实测最稳的一档，可作默认起点。
4. **显式配置上下文窗口**，这是最容易被忽略的参数，下面展开。
5. **上线前跑一组固定回归样例**：3~5 个典型 Agent 任务（单工具调用、多工具链、应拒答的输入），换模型、换量化后重跑，别凭感觉切换。

## 踩坑点

- **上下文窗口默认值太小。** Ollama 默认只有 2k~4k，Agent 跑几轮工具调用后历史被静默截断，表现是"模型突然忘了系统提示"，极难排查。务必把 `num_ctx` 拉到 16k 以上，同时确认显存放得下 KV cache。
- **量化别贪低。** Q2 档位聊天勉强能看，但结构化输出会出现不闭合的 JSON、编造参数名。Agent 场景建议 Q4_K_M 起步，显存富余上 Q5/Q6。
- **温度设 0~0.2。** 默认 0.8 的温度会让工具调用参数变得"有创意"。
- **Ollama 默认串行处理请求。** 如果 Agent 并行发多个工具调用，请求会排队，尾延迟暴涨。调大 `OLLAMA_NUM_PARALLEL`，或换 `llama-server` 加 `--parallel`。
- **部署完先记录 tokens/s 基线。** 之后速度突然变慢，多半是显存溢出触发了 offload，看日志能确认。

## 可复用建议

- **混合路由最务实**：本地小模型做工具路由和格式化，复杂推理留给 API 大模型。OpenClaw 侧配两个 provider 按任务分派，成本与隐私兼得。
- **把选型参数化**：量化版本、上下文长度、并行数全部进配置文件，方便 A/B 和回滚。
- **保留每次换档的回归测试结果**，三个月后你会感谢这份记录。

## 总结

本地 LLM 不是用来替代旗舰模型的，它是 Agent 工具链里一块便宜、私有、永远在线的基座。把预期降下来，把上下文、量化、并发三个参数管住，家用电脑完全能承担 Agent 工作流里的大部分调用。先建回归基线，再谈换模型——这是我这轮折腾里最值得带走的一条经验。
