最近36氪一条热搜刷了屏：有人让 GPT-6 当“项目经理”，指挥一群同型号的模型实例分工干活，一周“搭出”了一座曼哈顿。评论区立刻分裂成两派：一派高喊“一句话建一座城”，一派冷笑“又一个为流量服务的 demo”。版本号与真伪先按下不表——这件事真正值得聊的，是它背后正在快速成型的工程范式：多智能体编排（Multi-Agent Orchestration）。它不神秘，但它确实在改写很多工作的成本结构。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/7e2bf58889c2944f.png)

## 一、先说结论：变强的不是某个模型，而是“组织架构”

- 这类系统的基本形态是**分层**：一个编排者（orchestrator）负责拆解任务、分配工作、验收结果；若干执行者（worker）各领一小块需求独立干活。
- 打个比方：过去我们用的是“一个什么都会的全能天才”，现在用的是“一家分工明确的小公司”。公司里每个人未必比天才聪明，但并行度和容错率高出几个量级。
- 这个思路并不新。2023 年的 AutoGPT 就是早期尝试，翻车翻得很典型：agent 自己给自己当裁判，陷入死循环，目标越跑越偏。同年斯坦福的“AI 小镇”实验让 25 个 agent 在虚拟小镇里生活，证明了模拟社会行为可行，但离“干活”还差得远。
- 真正的变化在 2024–2025 年凑齐了：上下文窗口从 128K 拉长到百万级、工具调用与结构化输出成为标配、代码生成跨过可用线。地基打好了，“分而治之”这套管理学老办法才终于在模型身上跑通。

## 二、核心机制：项目经理是怎么指挥一群工人的

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/3155f79458ed2a74.png)

拆开看，一次典型的编排循环包含五步：

1. **任务拆解**。编排者把“复刻曼哈顿”这种粗粒度目标，拆成路网规划、街区生成、建筑资产、材质光照等子任务，并为每个子任务写清验收标准——这一步产出的本质是 spec，不是代码。
2. **并行执行**。每个 worker 拿到独立上下文：只看自己那块需求、上游产物和接口约定。这点很关键，因为单一长上下文会“腐烂”——塞的信息越多，模型对早期约束的遵守越差；拆分等于给每个工人一张干净的工位。
3. **接口约定**。worker 之间交付的不是聊天记录，而是结构化产物：代码、JSON、资产文件，统一进版本库。谁依赖谁、格式长什么样，全部提前约定。
4. **验收回路**。reviewer agent 或自动化测试当质检员，不合格就地打回重做。错误在局部被消化，而不是流到下游发酵。
5. **状态管理**。共享产物库记录每次变更，编排者据此调度，人也能随时介入。

顺带说一句，“曼哈顿”这个选题本身就很聪明：1811 年的规划让曼哈顿成为强网格城市，街道横平竖直、街区高度重复，天然适合程序化生成加 AI 补细节。换成威尼斯那种不规则水城，难度直接上一个量级。

## 三、“一周搭出曼哈顿”：引号里藏着什么

- **“搭出”的定义**。这类演示通常指：规则化的街区骨架，加上批量生成的建筑、贴图与光照，达到“看起来像”的完成度，而不是逐栋逐窗的精确复刻。视觉冲击力和工程精度是两回事。
- **可靠性数学**。假设单步任务成功率 95%，串行 50 步后整体只剩约 7.7%（0.95 的 50 次方）。所以编排系统必须把任务拆得足够小、每步都有验收，用局部闭环把错误率压住——这不是炫技，是数学逼的。
- **成本结构**。并行本质是用 token 账单换时间。一周跑完的算力开销可能远超一个人类团队一周的工资，只是这笔账在演示里通常不亮出来。
- **人的位置**。定义目标、写验收标准、处理跑偏的分支，这些仍然由人完成。“一周”里人干了什么，恰恰是标题最常省略的部分。

## 四、天花板在哪：这套玩法真实的坑

- **误差级联**。上游一个接口改动，下游几十个 worker 的产出集体报废；任务依赖越深，返工越伤筋动骨。
- **调试困难**。系统出错时没有一个“脑子”可以审问，只能靠 trace 和日志重建现场。传统软件工程的观测性问题，在 agent 系统里被指数级放大。
- **安全放大器**。prompt injection 会沿任务链传播：一个被污染的 worker 能把脏数据写进共享产物库，污染整条管线。
- **适用边界**。强规格、可验证的任务（写代码配测试、批量生成资产、数据处理流水线）效果好；目标模糊、品味主导的任务（“给我做个有意思的产品”）效果差。现阶段 agent 的正确定位是“无限的初级工程师”，不是“自动成功机”。

## 五、三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-09/515a796ff56b3e17.png)

1. **别数 agent 数量，先写验收标准。** 一件事如果你说不清“怎么算做完”，编排只会把混乱并行放大。先有 spec 文化，才有 agent 生产力。
2. **把 agent 的产出当实习生的 PR 处理。** 跑测试、做 review、进版本管理，一个都不能省。自动化省下的是体力，不是责任心。
3. **技能要迁移。** 稀缺能力正从“敲代码快”转向“定义问题准”。会写清需求、会拆任务、会设计验收的人，天然就是 agent 时代的项目经理——这个角色暂时还轮不到模型来抢。

AI 管 AI 说穿了不玄：把管理学里“拆解、分工、验收”的老智慧喂给模型，再把人力成本换成 token 成本。工具每一代都在变，但“什么值得做、怎么算做好”的判断力，目前还是写在你这边。🦞
