## 背景

OpenClaw 的 workspace 里，`MEMORY.md` 管记忆，`AGENTS.md` 管协作约定，而 `IDENTITY.md` 管的是最容易被忽视的一层：**agent 是谁**。名字、语气、边界、风格，全在这一个文件里。多数人首次部署时随手填几行，之后再不碰——直到某天发现同一个 agent 在不同会话里判若两"人"。

## 问题

跑久了的 agent 常见三类漂移：

1. **语气漂移**：今天精炼克制，明天热情满溢；
2. **边界漂移**：本该拒绝的操作，换个说法它就做了；
3. **配置散落**：身份信息一部分在 IDENTITY.md，一部分在启动参数，一部分"长"在了会话记忆里。改一处，不知道会不会牵动另一处。

团队场景更糟：每个人凭手感调 prompt，无法 review，无法回滚，也无法解释"它为什么变成这样"。

## 做法

核心思路：**把身份当配置文件管理，而不是当 prompt 灵感**。

**1. 最小化起点**

```markdown
# IDENTITY.md
name: atlas
tone: 克制、直接，先结论后细节
hard-boundaries:
  - 不执行删除类操作，除非命令带 --confirm
  - 不在回复中猜测未验证的事实
soft-preferences:
  - 代码示例优先于文字描述
  - 不使用感叹号
```

硬边界写"行为 + 替代动作"，软偏好写可观察的规则，不写抽象形容词。

**2. 纳入版本控制**：IDENTITY.md 和代码同仓库、同 PR 流程，改动必须带动机说明。

**3. 小步迭代**：每次只动一个维度。改语气就不动边界，方便定位"哪个改动导致了行为变化"。

**4. 定期回顾**：每月翻一次失败案例日志，区分两类问题——记忆问题（不知道）归 MEMORY.md，身份问题（知道但没做）归 IDENTITY.md。

**5. 打 tag**：稳定版本打 tag，出问题可回滚到上一个已知良好身份。

## 踩坑点

- **写太长**。身份文件超过一屏，关键约束会被稀释。宁可删减，不可堆砌。
- **只有禁令没有出口**。"不许做 X"但没说该做什么，模型会绕路而非遵守。
- **和记忆混写**。把"昨天用户说了什么"写进身份文件，每次记忆更新都会污染身份。
- **多实例共用一份**。并行跑多个 agent 时共用同一身份，人格和职责会互相渗透。用 base + override：一份基础身份，每个实例只覆盖差异段。

## 可复用建议

- 把 IDENTITY.md 的 diff 当作行为变更日志，每次发版附上身份变更摘要。
- 迭代由失败案例驱动，不做凭空的人设优化。
- 新 agent 接入时先复制一份验证过的身份模板再按场景裁剪，比从零写省一半时间。

## 总结

身份不是一次性写死的人设，而是随使用持续校正的配置。可 review、可回滚、可解释——这就是 IDENTITY.md 工程化的全部意义。它不会让 agent 更聪明，但会让它更稳定地是"同一个它"。
