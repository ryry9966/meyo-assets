## 背景

LLM 本身无状态。上下文窗口再大，跨会话的偏好——“commit message 用中文”“默认目标平台是 Arm64”“别自动 npm install”——没法靠每次塞 prompt 解决。在 OpenClaw 这类长期运行的 agent 场景里，接上 MCP 工具之后，真正的分水岭不是工具多不多，而是 agent 有没有一套可靠的记忆系统。

## 问题：三种典型的“假记忆”

实践中最常见的三种失败：

1. **记了不用**。提取管线跑得很欢，写进库了，但召回环节没接上，偏好从未进入上下文。
2. **记了就信**。三个月前用户说“用 pnpm”，现在团队统一换 npm 了，旧记忆反而每次都在帮倒忙。
3. **越记越胖**。什么都往里存，检索时召出一堆聊天碎片，挤占上下文还带偏输出。

根因是很多实现把记忆当成“一个向量库”，而它实际上是一个需要写入策略、置信度、版本管理和垃圾回收的数据系统。

## 做法：分层 + 双策略

**存储分三层：**

- **会话层**：scratchpad，会话结束即弃，解决单次任务内的临时状态。
- **偏好层**：结构化字段（语言、工具链、代码风格、通知习惯），每条带置信度和更新时间。小而稳，是核心资产。
- **事件层**：episodic 记忆，向量化存储，按需检索，允许丢失。

**写入策略比存储更重要：**

- 显式信号（“以后都……”“记住我……”）直接写入，高置信。
- 推断信号（连续三次拒绝某类建议）先低置信写入，累计出现 N 次再升级，避免一次巧合被固化成“偏好”。
- 冲突不做覆盖，做版本化：新值标记 `supersedes` 旧值，保留可回溯性。

**召回按类型分流：**

- 偏好层小而稳定，每轮直接注入，总量控制在几百 token 以内。
- 事件层走 embedding 检索，top-k 加相关性阈值，宁缺毋滥。
- 更进一步：把记忆暴露成 MCP resource，让 agent 在需要时主动查询，而不是无脑全量注入。

## 踩坑点

1. **相似度 ≠ 相关**。检索“数据库偏好”很可能召回历史报错记录。检索前加类型过滤，比换 embedding 模型管用。
2. **置信度只增不减**。用户三个月没确认过的偏好，权重不该和昨天刚确认的一样。加时间衰减，或让 agent 在合适时机顺口确认一次。
3. **记忆对用户不可见**。记错一次，用户只会觉得“这 AI 有毛病”。记忆必须可查看、可编辑、可删除，`forget` 应当是一等公民接口。
4. **并发写**。多实例或插件同时更新偏好表，不加版本号迟早出脏数据。

## 可复用建议

- Schema 先行：先定义偏好字段再写代码，别用自由文本存偏好。
- 写入走异步队列批量处理，别阻塞主对话链路。
- 写个一次性脚本定期跑一致性检查，输出冲突值和新旧值报告，比上线后 debug 省事得多。

## 总结

好的记忆系统，标准不是“存得多”，而是**召回得准、允许被修正**。建议的落地顺序：先做小而稳的结构化偏好层并打通注入链路，事件层后加，把记忆当成一个带版本管理和 TTL 的数据系统来运营。做到“记错能改、过期能删”，agent 才算真正记住了你。
