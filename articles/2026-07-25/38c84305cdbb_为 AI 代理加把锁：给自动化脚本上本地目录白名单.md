## 问题场景

让 Agent 或者自定义 MCP 工具直接读写本地文件，是日常自动化里最常见的需求——批量处理文档、生成报表、写配置文件。但一旦放开文件系统的访问权限，Agent 意外删除关键目录、覆盖系统文件或读走敏感信息的风险就会陡然升高。尤其是在多步骤自动化流程中，一个错误的路径拼接就能造成不可逆的数据丢失。

更现实的是，很多自动化项目从单机脚本演进而来，大量使用 `open()`、`os.listdir()` 等原生操作，缺乏统一的访问控制层。于是“加护栏”就成了工程上必须补的一环：**让 Agent 只能访问你明确授权的目录，其他路径一律拒绝**。

## 目标与设计原则

这个护栏不需要像沙箱那样完整，而是提供一种低成本、可嵌入现有脚本的目录白名单校验。设计上遵循三条原则：

1. **路径必须解析为绝对路径再校验**——防止相对路径、符号链接绕过；
2. **白名单是允许访问的文件夹集合，不包括文件粒度**——管理成本低，适合多数批量操作；
3. **封装替换原生 `open` 等调用，而非全局 Monkey‑patch**——避免副作用，方便测试。

## 实现步骤：一个可复用的 SafeFS 封装

下面以 Python 为例，给出一个最小可行的安全文件系统包装器，可在 OpenClaw 自定义工具函数或 MCP 服务器中直接使用。

### 1. 定义白名单与路径检查

```python
import os
from pathlib import Path
from typing import List, Union

class FileAccessError(PermissionError):
    """文件路径不在白名单中时抛出"""
    pass

def _resolve_path(path: Union[str, Path]) -> Path:
    """转为绝对路径并解析符号链接"""
    return Path(os.path.realpath(os.path.abspath(path)))

class SafeFS:
    def __init__(self, allowed_dirs: List[str]):
        # 所有白名单目录预处理为解析后的 Path 对象
        self._allowed = [_resolve_path(d) for d in allowed_dirs]

    def _check_access(self, target: Path):
        """检查 target 是否在白名单目录内"""
        target = _resolve_path(target)
        for base in self._allowed:
            try:
                target.relative_to(base)
                return   # 通过
            except ValueError:
                continue
        raise FileAccessError(f"Access denied: {target}")
```

这里用 `Path.relative_to()` 判断路径是否在允许的目录树内，比字符串前缀匹配可靠得多，能正确处理 `/dir/sub` 和 `/dir_sub/...` 这种误判。

### 2. 包装常用文件操作

对脚本中最常用的操作进行简单包装：

```python
class SafeFS:
    # ... 接上面

    def open(self, path, mode='r', *args, **kwargs):
        self._check_access(path)
        # 只允许在已有文件上读/写/追加，避免通过未存在路径绕过检查
        if 'w' in mode or 'a' in mode or 'x' in mode:
            parent = _resolve_path(path).parent
            self._check_access(parent)
        return open(path, mode, *args, **kwargs)

    def listdir(self, path):
        self._check_access(path)
        return os.listdir(path)

    def mkdirs(self, path, exist_ok=True):
        self._check_access(path)
        os.makedirs(path, exist_ok=exist_ok)

    # 其他如 copy/move 同理，先校验源和目标
```

对于写模式，增加父目录校验，是因为文件尚不存在时路径本身可能未被白名单直接包含，但父目录已被允许。这种处理能覆盖“写入新文件”的常见场景。

### 3. 在 OpenClaw 或 MCP 工具中集成

假设你为一个自动化节点编写了三个工具函数：`read_report`、`save_summary`、`list_outputs`，只需要实例化一个全局的 `SafeFS` 对象，然后把所有原生文件操作替换为 `fs.open(...)` 等调用即可：

```python
fs = SafeFS(allowed_dirs=["/data/project_outputs", "/tmp/reports"])

def read_report(filename: str) -> str:
    with fs.open(filename, 'r') as f:
        return f.read()
```

不需要改动其他现有逻辑，甚至可以在配置文件中声明白名单路径，运行时动态加载。

## 踩坑点与工作记录

实际落地时，几个细节反复踩过坑：

- **符号链接穿透**：用户可能在白名单目录内创建指向 `/etc` 或家目录的软链接。只用 `os.path.abspath` 会保留链接名，必须用 `os.path.realpath` 解析到物理路径再检查。
- **相对路径与当前工作目录**：自动化进程的工作目录可能随时间变化。每次校验前统一转换为绝对路径，且白名单本身也以解析后的绝对路径存储，能消除这类漂移。
- **多线程/多协程环境**：白名单在初始化后是只读的，线程安全天生满足；文件操作函数本身无状态，不需要额外锁。如果使用 `asyncio`，注意 `open` 是同步阻塞的，可配合 `run_in_executor`。
- **`shutil` 和其他库的捕获**：如果自动化脚本引用了第三方库内部直接 `open` 其他路径，仅靠业务代码层面的替换是无法拦截的。这时要么对依赖的库同样做白名单检查，要么从架构上把文件访问集中到少数几个工具函数中。我们的经验是后者更可控。
- **路径规范化差异**：Windows 上的盘符大小写、分隔符对于 `relative_to` 可能敏感。统一用 `Path.resolve()` 处理，并在白名单初始化时同样 `resolve`。

## 可复用建议

这个“安全文件系统”包装器不到 100 行代码，却能在多数单机自动化项目中直接集成。建议：

- **把白名单配置外置**，放在 YAML/JSON 中，与代码解耦；
- **在测试中特意准备带符号链接的目录树**，验证拒绝访问行为；
- **对于只读工具，只用 `mode='r'` 且不允许写/执行**，可以进一步收紧；
- **对 MCP server 暴露的资源，同理可以在工具的 handler 内使用该封装**，让每个工具只看到自己的数据目录；
- **记录被拒绝的访问日志**，方便事后排查是误报还是 Agent 行为异常。

如果希望更进一步，可以把 `SafeFS` 与 Agent 的上下文绑定，实现“不同 Agent 拥有不同白名单”，但当前阶段保持单实例全局就足够大多数自动化场景使用。

## 总结

给自动化脚本加目录白名单，本质上是把“最小权限”原则落地到文件系统层。它不如容器隔离那么厚重，但足够轻量，特别适合已经有一堆脚本但缺乏访问控制的团队快速兜底。通过路径解析、白名单前置检查、替换关键 I/O 调用，能够有效防止 Agent 的“写入散射”和对系统敏感文件的误读。再加上日志和测试，这个小护栏就能在每天的自动化流中默默保护你的数据。

把上面的 `SafeFS` 贴进项目，补上几条白名单路径——你的 Agent 就只会在你划定的沙盒里活动了。
