# 背景：当自动化脚本有了“腿”，文件系统就是它的地雷区

在 MCP、插件、Agent 自动化链条里，我们经常让一个脚本或工具去执行文件操作：读取配置、写日志、抓取本地数据、导出报告。这个节点一旦被链式调用触发，尤其是放在计划型 Agent 的 action 步骤里，它几乎拥有了当前进程用户的全部文件访问权限。如果你跑在一个开发机上，它可能会读 `.env`、`ssh key`、项目配置，甚至修改 `/etc/hosts`。

不少团队的做法是：用容器隔离，或者干脆让 Agent 只输出文本，不做文件操作。但现实需求是，你总得让它把 CSV 写到某个目录、从某个文件夹读取模板。一刀切禁止文件访问会降低自动化程度，而放任不管又埋下巨大隐患。

我们需要一种**工程化的中间态**：给脚本挂一个“目录白名单”，只允许它读写指定目录，其余位置完全不可见，甚至在运行时无法通过 `..` 或者符号链接逃逸出去。

# 问题拆解

一个可被 Agent 调用的脚本，对文件系统的危险操作集中在三类：

1. **读敏感文件**：通过相对路径或绝对路径读取 `.env`、`~/.ssh/config`、`/etc/passwd` 等。
2. **写系统关键路径**：下载的脚本直接写入 `~/.bashrc`、`crontab`、`/usr/local/bin`。
3. **通过符号链接与路径穿越逃逸**：`/allowed_dir/../../.ssh/id_rsa`，或者白名单目录里存在指向外部的软链接。

单纯靠正则匹配路径很容易被绕过。一个较为可靠的方案是**基于文件描述符限制 + 系统调用拦截（或 landlock）**，但这对很多脚本语言和部署环境来说侵入性太高。

我们在实际用 Go 写的几款 MCP 工具里，发现可以借助 `chroot` 的轻量化应用，结合只读挂载、`proc` 隔离，构建一块“围栏”，然后让脚本在这个环境里执行。不依赖 Docker，不要求 root，只需要一个预构建的 rootfs 骨架。

下面给出一个在 Linux 环境（也适用于 macOS 需要调整）能让 Agent 工具链复用的方案。

# 做法：用最小 chroot 环境强制目录白名单

## 步骤 1：构建围栏骨架

我们创建一个目录作为 jail 的根，例如 `/opt/agent-jails/run-<uuid>`，里面只放必需的最小文件集和白名单目录的绑定挂载。

最小骨架可以这样准备（以 Ubuntu/Debian 为例）：

```bash
JAIL_BASE=/opt/agent-jails/base
mkdir -p $JAIL_BASE/{bin,lib,lib64,etc,dev,proc,tmp}
# 复制一个静态编译的 busybox 或你需要的解释器进去
cp /bin/busybox $JAIL_BASE/bin/
# 如果你需要运行 Python 脚本，就需要把 Python 解释器和其依赖库放入
# 推荐用 statically linked 的 Python 或者把整个 miniconda env 复制进去
```

关键是**只放必需的二进制和库**。不要直接把宿主机的 `/usr` 挂进去。

## 步骤 2：准备白名单目录并挂载

假设白名单目录为 `/allowed/data/`，我们需要让 jail 里能读写这个目录。为了让 jail 内程序看起来自然，可以把它挂到 jail 的 `/data` 下面。

每次运行前动态创建一个 run 目录：

```bash
RUN_DIR=$(mktemp -d /opt/agent-jails/run-XXXXXX)
mount --bind $JAIL_BASE $RUN_DIR
# 使用 bind mount 将白名单目录挂进去
mount --bind /allowed/data $RUN_DIR/data
# 挂载必要的系统目录（注意只读或最小权限）
mount -t proc none $RUN_DIR/proc
mount --bind /dev $RUN_DIR/dev
```

在 macOS 上没办法直接这样做，可以考虑用 `sandbox-exec` 配置 profile 代替，但思路类似。

## 步骤 3：在 jail 内降权并执行脚本

用 `chroot` 切换到 jail 内，同时降权到一个非 root 用户，防止脚本通过 mount 等手段搞事。

```bash
chroot --userspec=1000:1000 $RUN_DIR /bin/busybox sh /scripts/run.sh
```

这时候脚本所能看到的文件系统根就是 `$RUN_DIR`，它无法通过 `..` 或绝对路径碰到宿主机的任何文件（除非你把宿主机根目录 bind 进去了，千万不要这么做）。它只能访问 `/data` 下内容。

## 步骤 4：处理日志与输出

脚本如果有写日志、输出文件的需求，要么全部限制在 `/data` 下，要么在 jail 内挂载一个 tmpfs 供临时文件使用，run 结束后销毁。

```bash
mount -t tmpfs tmpfs $RUN_DIR/tmp
```

这样即使脚本乱写，也不会污染宿主机。

# 踩坑点

1. **动态链接的二进制依赖地狱**：如果你要跑 Python，必须把所有依赖的 `.so` 都复制进 jail，使用 `ldd /usr/bin/python3` 查看列表，然后一一把库复制到对应 `/lib`，否则会提示 `No such file or directory`。推荐用 `pyinstaller` 打包成单个可执行文件，放进只有 busybox 的环境中执行，减轻依赖负担。

2. **$PATH 和环境变量泄露**：进入 chroot 后环境变量是继承的，可能会携带宿主机的敏感信息（如 API key）。在 chroot 命令前先用 `env -i` 清空，只传递必要的变量。

   ```bash
   env -i PATH=/bin:/usr/bin HOME=/data chroot ...
   ```

3. **网络访问的连带问题**：脚本可能尝试发起网络请求下载恶意代码再执行，此时白名单目录也防不住。如果需要断网，在 jail 启动时不挂载网络 namespace，但 chroot 本身不隔离网络。可以配合 `unshare -n` 创建无网络 namespace，前提是 Linux 内核支持且允许非 root 使用。

4. **chroot 逃逸**：老生常谈，chroot 不是安全边界，如果有 root 权限可以轻松逃逸。所以我们要求必须降权到普通用户，且该用户对 jail 内没有任何特权指令可用。只给 busybox 和必要的解释器，且必须把 `mount`、`chroot` 等命令移除。

5. **macOS 上的替代方案**：macOS 没有原生 chroot + bind mount 的轻松使用方式，如果你主要在 macOS 开发，可以考虑用 `sandbox-exec` 写一个 sbpl 配置：

   ```scheme
   (version 1)
   (allow default)
   (deny file-read* file-write* file-ioctl*
         (path "/")  ;; 禁止根目录所有操作
         )
   (allow file-read* file-write* file-ioctl*
         (path "/allowed/data")) ;; 白名单
   ```

   然后用 `sandbox-exec -f profile.sb python3 script.py` 运行。虽然比 chroot 简陋，但足够应对大部分场景。

# 可复用建议

- **把 jail 构建与销毁封装成 MCP 工具或 Agent 调用前的预处理 hook**：我们可以写一个小小的 binary `jail-run --allowed-dir=/path --cmd="python3 task.py"`，内部自动创建临时 jail，挂载指定白名单目录，执行脚本，最后清理挂载点并删除临时目录。
- **白名单目录读写权限还可以细分**：例如提供 `--read-only-dir` 和 `--write-dir` 参数，对只读目录用 `mount --bind -o ro` 挂载，进一步降低风险。
- **把日志输出到宿主机的一种安全方式**：让脚本把结果写到 `/data/output.json`，宿主机在执行结束后去这个路径（即白名单目录内）读取，不要试图通过管道传递，避免打破隔离边界。
- **这条护栏不能替代代码审查，但可以作为纵深防御的一层**：即使你信任当前调用的脚本，将来它被替换、更新、或通过依赖投毒时，这层限制会直接阻断其访问敏感路径。

# 总结

给自动化脚本加目录白名单，本质是遵循最小权限原则在文件系统上的落地。在 Agent 自动化高速拼接的链条中，任何一个节点都不应该拥有随意探索宿主文件系统的自由。通过 chroot + bind mount 或 sandbox-exec 构建文件访问护栏，我们可以让脚本只看到它应该看到的目录，同时不牺牲太多开发灵活度。

这个方案在几条内部用 Go 编写的 MCP 工具链中跑了几个月，尚未出现逃逸或误拦问题，对执行效率影响也极小（启动延迟约 30ms）。希望这些踩坑经验能给你的 Agent 系统增加一层可复用的安全屏障。
