## 背景：你的自动化脚本在“裸奔”吗？

在 OpenClaw、MCP 宿主或自定义 Agent 中，工具调用往往需要直接触碰本地文件系统。比如让 Agent 帮忙整理某个目录下的文件、读取配置、生成报表再写回磁盘。这类操作一旦把文件路径的选择权完全交给模型输出，就会打开一个巨大的风险窗口：模型可能返回 `../../.env`、`/etc/passwd` 甚至 Windows 下某敏感路径，然后再配合一个“读取文件并返回内容”的工具，轻松实现信息窃取。

所以，只要你的 Agent 或自动化脚本具备**写入 / 读取 / 执行**任意本地路径的能力，就需要一个可靠的**文件访问护栏**。最常用也最容易落地的方式，就是给工具调用加上**本地目录白名单**——只允许在预先设定的安全基路径及其子目录内操作。

这篇文章会给出一个可直接复用的工程方案，并重点聊聊那些你以为“不可能被绕过”的坑。

## 问题拆解：要在哪里做限制？

假设你有一个 MCP 工具名叫 `read_local_file`，接收 `relative_path` 参数，Agent 可以传递相对路径，工具内部拼接工作目录后读取。最简单的“白名单”想法是：`destPath = path.join(baseDir, relativePath)`，然后判断 `destPath.startsWith(baseDir)`。

但 path.join 和 startsWith 的简单组合远远不够，下面是一个更可靠的方法。

## 实现步骤：三层防线

### 1. 解析与规范化
对所有输入路径先做 `path.resolve(baseDir, userPath)`，得到一个标准化绝对路径。如果 baseDir 本身是相对路径，也要先 resolve 成绝对路径。

```ts
const safeResolve = (base: string, target: string): string => {
  const resolvedBase = path.resolve(base);
  const resolvedTarget = path.resolve(resolvedBase, target);
  return resolvedTarget;
};
```

### 2. 白名单检查：规范化后前缀匹配
比较 `resolvedTarget` 是否以 `resolvedBase + path.sep` 开头，而不是简单 startsWith(baseDir)。因为 `/var/app/user` 会以 `/var/app` 开头，这不算真正的子目录。

```ts
const isWithinDir = (base: string, target: string): boolean => {
  const normalizedBase = path.resolve(base) + path.sep;
  const normalizedTarget = path.resolve(base, target) + path.sep;
  return normalizedTarget.startsWith(normalizedBase);
};
```

注意末尾加 `path.sep` 的两处——防止 `/var/app` 匹配 `/var/app-user` 的情况。

### 3. 禁止额外路径穿越
如果工具接受绝对路径或包含 `..` 的相对路径，上面的 resolve 已经解决了。但有一种情况：用户输入 `./subdir` 和你预想的一致，但如果没有 resolve，`./subdir` 和 `baseDir` 做 startsWith 会怎样？所以强制 resolve 是必须的。

## 踩坑记录：四个看起来“安全”的疏忽

### 坑 1：符号链接逃逸
如果白名单目录内有一个指向 `/etc` 的符号链接，Agent 请求 `./link-to-etc/passwd` 时，规范化结果为 `/etc/passwd`，前缀不再匹配白名单目录，这一点上面逻辑已经能拦截。**但要小心**：如果你的工具在判断白名单时解析了符号链接，但实际操作时使用了没有解析符号链接的路径（例如某些库的 API），就存在 TOCTOU 风险。所以务必在检查前用 `fs.realpathSync` 或 `fs.realpath` 获取真实路径再进行判断，注意同步 / 异步一致。

```ts
const isSafePath = (base: string, userPath: string): boolean => {
  const baseReal = fs.realpathSync(path.resolve(base));
  const targetReal = fs.realpathSync(path.resolve(base, userPath));
  return targetReal.startsWith(baseReal + path.sep);
};
```

### 坑 2：Windows 盘符与大小写
在 Windows 上，`C:\Users` 和 `c:\users` 可能被视为同一路径，但 `startsWith` 区分大小写。建议统一 `toLowerCase()` 或使用 `path.normalize` 后比较。另外，Windows 允许 `C:` 与 `C:\` 的不同语义，最好直接禁止相对盘符的输入，只允许在当前盘工作。

### 坑 3：baseDir 未尾随分隔符的“前缀骗过”
前面已经提到了 `/var/app` 与 `/var/app-user` 的问题。如果你仅仅 `target.startsWith(base)`，碰巧没有加上分隔符，会被恶意输入骗过。这是非常常见也非常隐蔽的错误。

### 坑 4：相对 baseDir 本身的“逃逸”
如果你没有先将 baseDir 解析为绝对路径，而 baseDir 本身又是像 `./workspace` 这样的相对路径，那么攻击者输入 `/etc/passwd` 时，`path.resolve('./workspace', '/etc/passwd')` 会直接返回 `/etc/passwd`——因为 path.resolve 如果有绝对路径参数，会丢弃前面的参数。解决办法：永远先 resolve baseDir，再 resolve target，并且拒绝绝对路径参数，或将其视为不安全并报错。

更健壮的做法：如果 `path.isAbsolute(userPath)`，直接拒绝；或者将绝对路径与 baseDir 拼接的行为视为潜在攻击，抛出异常。

## 可复用建议：封装成通用中间件

如果你的 Agent 有多个文件相关工具（读、写、删除、执行），可以为每个工具套用一个通用校验函数，甚至在 MCP server 层统一拦截 `callTool` 中的应用层参数。封装要点：

- 导出 `createSafeFileAccessor(baseDir, allowSymlinks = false)`，`allowSymlinks` 控制是否允许符号链接指向外部。
- 提供 `readSafe(relativePath)`、`writeSafe(relativePath, content)` 等安全包装。
- 校验失败统一返回标准错误，避免向模型暴露绝对路径或系统细节。

在 OpenClaw 插件中，你可以直接在 `tool.execute` 里使用这个 accessor，从而让社区插件更容易遵循最小权限原则。

## 总结

给 Agent 加上本地目录白名单并不复杂，但要想真的安全，必须把路径解析规范化、前缀匹配严格化、符号链接真实化，并且针对 Windows 的怪癖做好防御。上面提供的 resolve + realpath + separator 三层校验，足够覆盖绝大多数场景，而封装成通用模块后，你的每一个文件工具都可以低成本复用。

最后提醒一点：文件访问护栏是纵深防御中的一环，本身不能替代对 Agent 能力的权限最小化设计。限制工作目录、只读挂载、容器隔离等手段应该配合使用，才能真正放心让自动化脚本触碰我们的文件系统。
