## 背景：当 Agent 的脚本跑在你的笔记本上

无论是用 OpenClaw 搭建本地工具链，还是通过 MCP 插件让 LLM 调用本机脚本，我们经常会给 Agent 开放文件读写能力——例如让它处理 `~/projects/data` 下的 CSV、在 `./output` 里生成报告，或者读取配置文件。默认情况下，Agent 的 Python 进程拥有当前用户的所有文件权限，可以访问 `~/.ssh`、`/etc/passwd` 甚至整个文件系统。一旦脚本行为失控（幻觉生成的路径、prompt 注入、逻辑 bug），就可能误删、泄密或污染重要目录。

在工程实践中，不是所有环境都方便上 Docker、虚拟机或 seccomp 这类重型沙箱。我们需要一个轻量、可注入、与 OpenClaw 等 Agent 框架融合的“文件访问护栏”——只允许脚本在指定的本地目录内行动。

## 问题拆解

目标是：对一段 Python 自动化代码，限制其文件操作（`open`、`os.remove`、`shutil.rmtree` 等）只能发生在白名单目录列表内，任何越界访问都会被拦截并抛出异常。方案要满足：

- 无外部依赖，可直接嵌入现有脚本或 OpenClaw 的 `@tool` 中。
- 能处理符号链接、相对路径，避免逃逸。
- 对已有代码入侵性低，最好通过上下文管理器一键开启。
- 方便记录违规行为，便于审计。

## 实现：路径规范 + 内建函数替换

核心思路分两步：第一步，把所有传入的文件路径规范化成绝对路径并解析符号链接；第二步，用规范化后的路径去检查是否以白名单目录为前缀。如果未命中，直接抛出 `PermissionError`。我们通过替换 Python 内建的 `open` 以及 `os` 模块下的危险函数来嵌入这个检查。

### 1. 路径检查函数

```python
import os

ALLOWED_DIRS = [
    os.path.realpath("/home/user/projects/safe_dir"),
    os.path.realpath("/tmp/agent_workspace"),
]

def is_path_allowed(path: str) -> bool:
    # 解析所有符号链接和相对路径
    real_path = os.path.realpath(path)
    for allowed in ALLOWED_DIRS:
        # 确保是前缀且防止 /dirA 匹配到 /dirAbc
        if real_path == allowed or real_path.startswith(allowed + os.sep):
            return True
    return False
```

注意必须使用 `os.path.realpath` 而不是 `abspath`，否则符号链接轻松绕过。

### 2. 包装内建 `open` 与危险函数

```python
import builtins
import functools

def _make_guarded_open(original_open):
    @functools.wraps(original_open)
    def guarded_open(file, mode='r', *args, **kwargs):
        # 只对写入或读写操作做限制，纯读取可酌情放宽，但这里统一约束
        if not is_path_allowed(file):
            raise PermissionError(f"Access to {file!r} is not allowed")
        return original_open(file, mode, *args, **kwargs)
    return guarded_open

# 同理处理 os.remove 等
def _make_guarded_remove(original_remove):
    @functools.wraps(original_remove)
    def guarded_remove(path, *args, **kwargs):
        if not is_path_allowed(path):
            raise PermissionError(f"Remove {path!r} blocked")
        return original_remove(path, *args, **kwargs)
    return guarded_remove
```

### 3. 上下文管理器：干净的进入/退出

```python
import os as os_module

class FileGuard:
    def __init__(self, allowed_dirs=None):
        if allowed_dirs:
            global ALLOWED_DIRS
            ALLOWED_DIRS = [os.path.realpath(d) for d in allowed_dirs]
        self._originals = {}

    def __enter__(self):
        # 保存原始引用
        self._originals['open'] = builtins.open
        self._originals['remove'] = os_module.remove
        # 还可以添加 os.rename, os.rmdir, shutil.rmtree 等
        builtins.open = _make_guarded_open(self._originals['open'])
        os_module.remove = _make_guarded_remove(self._originals['remove'])
        return self

    def __exit__(self, *args):
        builtins.open = self._originals['open']
        os_module.remove = self._originals['remove']
        # 恢复所有函数
```

使用时：

```python
with FileGuard(['./workspace', '/tmp/sandbox']):
    with open('workspace/data.txt', 'w') as f:
        f.write('OK')
    # 下面这句会抛出 PermissionError
    open('/etc/passwd')
```

### 4. 与 OpenClaw 的 `@tool` 集成

只需在工具函数的业务逻辑外包裹 `FileGuard`：

```python
from openclaw import tool

@tool
def process_data(filename: str):
    with FileGuard(allowed_dirs=['./data', './output']):
        with open(filename) as f:
            ...
```

这样，哪怕 LLM 生成的 `filename` 是 `../../.env`，也会在 `is_path_allowed` 那一步被 `realpath` 解析后拒绝。

## 踩过的坑

1. **符号链接逃逸**  
   用户在 `/tmp/sandbox` 内创建指向 `/etc` 的软链，`/tmp/sandbox/secret -> /etc/passwd`，如果没有用 `realpath` 解析，`startswith` 检查直接通过。必须对**目标路径**实时 `realpath`。

2. **相对路径的上下文**  
   `os.path.realpath` 依赖当前工作目录。如果在 `with` 块内改变了 `os.chdir`，解析结果可能不同。建议在进入 `FileGuard` 时固定 `cwd = os.getcwd()`，检查前用 `os.path.join(cwd, path)` 再解析。

3. **Windows 盘符和大小写**  
   Windows 上 `C:\` 与 `c:\` 是同一路径，需要用 `os.path.normcase` 处理；同时盘符可能不同，需要额外逻辑。

4. **线程/协程安全**  
   简单的替换在单线程下没问题；多线程时，修改全局 `builtins.open` 会作用于所有线程。可改用 `threading.local` 或者不修改全局，而是用显式调用包装函数的方式。

5. **漏掉只读操作**  
   `os.listdir`、`os.stat` 也会泄露目录结构，是否拦截取决于安全级别。建议至少拦截 `listdir`，或者将白名单逻辑也复制到这些函数。

6. **已导入模块的旧引用**  
   如果在 `import shutil` 之后才替换 `os.remove`，`shutil.rmtree` 内部仍会使用原始的 `os.remove`（因为它在导入时已绑定）。解决办法：①在程序最顶部执行替换；②或者同时修改 `shutil` 等模块中的函数，这会变得复杂。对于轻度防护，通常能够覆盖直接的文件操作即可。

## 可复用的工程建议

- **封装为 `pip` 包**：把上述逻辑做成一个 `agent-file-guard` 包，支持配置白名单、违规回调（日志、告警）。
- **记录而非静默拒绝**：每次拦截时打日志（包含时间戳、尝试的路径、调用栈），方便安全审计和调试 Agent 的“坏行为”。
- **与系统级防护组合**：该护栏是应用层的第一道防线，生产环境建议再叠加 seccomp、AppArmor 或 Docker 的 `--read-only` 与 `--tmpfs` 限制。
- **显式声明能力**：在 OpenClaw 的工具描述里写明“仅能访问 `./data` 和 `./output`”，让模型预先知道边界，降低幻觉越界的可能。

## 总结

给自动化脚本加本地目录白名单，本质上是“路径计算 + 内建函数替换”的轻量级访问控制。它可以有效阻止因逻辑错误或 prompt 注入引发的多数文件越界行为，实现成本极低，且对 Agent 框架（OpenClaw、MCP 插件）非常友好。当然它并非银弹，更深度的隔离仍需依赖操作系统机制。但作为开发、调试和内部自动化的第一层护栏，这套方案足够实用且易于复现。
