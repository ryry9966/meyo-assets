## 背景

OpenClaw 的自动化链路里，同一个任务经常会被触发多次：上游重试、定时任务重叠、人工补跑、Agent 再次调用同一个 MCP 工具。幂等性解决的不是“第二次执行会报错”，而是“第二次执行不会产生额外副作用”。

如果任务不幂等，遇到的问题通常不是崩溃，而是更隐蔽的重复写库、重复通知、重复创建资源。这类问题在生产里比异常更难排查。

## 问题

典型的非幂等场景：

- 每次执行用随机 ID 或时间戳创建资源。
- 每次执行向外部 API 发一次请求，但不传幂等键。
- 每次执行都追加日志、发消息、扣库存、发通知。
- 先检查再写入，但没有唯一约束，并发重试时出现竞态。
- MCP 工具封装了有副作用的 HTTP 接口，Agent 或 Task 重试时直接再调一次。

## 做法/步骤

**1. 给每次业务操作一个稳定键**

不要用随机 ID。用业务主键或输入内容的哈希作为资源 ID，例如 `resource_id = hash(tenant + biz_key)`。这样第二次创建同一资源时能命中同一条记录。

**2. 先记录意图，再执行副作用**

在插件或工具入口处，向本地执行日志表写入一条记录，字段包括 `idempotency_key`、`status`、`result`。对 `idempotency_key` 建唯一索引。执行前先查状态：

- `completed`：直接返回上次结果；
- `in_progress`：返回同一任务句柄或短等待；
- `not_started`：标记为 `in_progress` 后执行。

**3. 写入操作改成条件写**

数据库层用 `INSERT ... ON CONFLICT DO NOTHING` 或 `UPDATE ... WHERE version = ?`。即使并发重试，也只会有一次生效。

**4. 外部调用带幂等键**

调支付、消息、工单等外部接口时，传递统一的 `Idempotency-Key`。如果对方不支持，就通过本地 outbox 去重：先落库去重，再发送；发送成功后再更新状态。

**5. 文件和消息路径固定化**

生成文件不要用时间戳命名。用内容哈希或版本号，如 `report/2024-q3.json`。通知类任务先把“待通知”写入队列或表，由单独 worker 消费，worker 再按消息 ID 去重。

**6. 用测试验证**

对同一个任务连续跑两次，检查资源数量、外部调用次数、结果一致性。并发测试要同时跑多个相同任务。

## 踩坑点

- **把“第二次没报错”当幂等**。接口可能返回成功，但底层已经创建两条记录。
- **只加缓存不加持久化**。内存去重在服务重启后失效。
- **先查再写但没有唯一约束**。并发下两个执行同时通过检查。
- **任务状态机不可重入**。从 `pending` 到 `running` 的更新没有条件，重复执行会把已完成任务拉回运行态。
- **外部 API 不支持幂等**。这时必须自己做 outbox 或人工对账，不能假设对方会去重。

## 可复用建议

- 做一个通用执行器：`run_idempotent(key, fn)`，内部完成查状态、抢锁、执行、存结果。
- 所有插件的副作用入口先过执行日志表，不直接调外部接口。
- 资源 ID 尽量由业务字段推导，不要使用自增 ID 或随机 UUID 作为幂等依据。
- 对定时任务加锁，例如 `pg_advisory_lock(task_key)`，避免重叠执行。
- 幂等键要包含租户、业务类型、业务键和操作版本；不要只用一个宽泛的任务名。

## 总结

幂等性不是让任务永远只跑一次，而是让重复执行收敛到同一种结果和同一组副作用。对自动化链路来说，关键是提前设计稳定键、持久化执行状态、用唯一约束兜底，并把外部副作用从主流程中拆出来。做到这些，重试、补跑和并发触发才会真正安全。
