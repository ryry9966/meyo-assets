## 背景

在 OpenClaw、Agent、MCP 工具和插件编排的自动化链路里，重复执行几乎是一种常态。

可能的原因包括：

- 消息队列或事件源出现重复投递；
- 网络超时后客户端发起重试，但服务端已经成功处理；
- 用户重复点击、重复触发同一个自动化任务；
- Agent 多步推理中，同一个 MCP 工具被多次调用；
- 插件并发执行，两个 worker 同时拉起同一个任务。

如果任务本身不是幂等的，重复执行就会产生重复副作用：重复创建 Issue、重复发送告警、重复写入数据库、重复调用外部计费接口。

下面是一个很常见的翻车现场：你给 OpenClaw 配了一个“错误日志自动创建 GitHub Issue”的自动化。某天凌晨消息队列抖动，同一条错误日志被投递三次。插件跑了三次，仓库里多出三个一模一样的 Issue。

这就是典型的非幂等任务。

## 问题

在很多自动化实践中，我们把“幂等”理解得过于简单，以为“尽量别重复执行”就行。但分布式系统里，**至少一次投递**才是工程上的默认假设。重试机制是保证可用性的必要手段，如果没有幂等设计，重试就会放大副作用。

在 OpenClaw 的插件和 MCP 工具链路中，这个问题更突出：同一个工具可能被多个 Agent 或插件复用，工具作者无法预知调用方会重试几次。因此，幂等不能只靠调用方“小心”，而应该落实到任务本身。

## 做法/步骤

### 1. 为每个自动化任务确定一个业务唯一键

幂等的核心是让同一个业务动作无论执行多少次，都能被识别为“同一个任务”。

唯一键要具备**可复现性**，不能使用随机 UUID。例如“错误日志转 Issue”可以用：

```
repo + 错误指纹 + 发生时间窗口
```

错误指纹可以是对堆栈关键帧的哈希，时间窗口用来避免同一错误长时间内被合并成一个任务。

### 2. 在任务入口处做原子性登记

不要“先执行，后登记”。必须先占位，再执行。

可以使用数据库唯一约束作为最终兜底。例如建一张 `task_runs` 表：

```sql
CREATE TABLE task_runs (
    task_key TEXT PRIMARY KEY,
    status TEXT NOT NULL,
    result JSONB,
    updated_at TIMESTAMPTZ
);
```

任务入口先插入一条 `running` 状态。如果插入时触发唯一键冲突，说明任务已经存在，按状态决定后续操作。

### 3. 使用明确的任务状态机

建议状态为：

```
pending -> running -> succeeded / failed
```

- 如果重复执行时状态为 `succeeded`，直接返回上次结果；
- 如果状态为 `running` 且未超时，说明有并发执行，可以等待或跳过；
- 如果状态为 `failed`，可以按策略重试，但重试时 `task_key` 不能变。

更新状态时要用条件更新，避免并发覆盖。例如：

```sql
UPDATE task_runs SET status = 'succeeded'
WHERE task_key = $1 AND status = 'running';
```

如果更新行数为 0，说明状态已经被其他执行者处理。

### 4. 将外部非幂等调用改造成幂等

很多外部 API 已经提供幂等键支持：

- Stripe 等支付接口支持 `Idempotency-Key` header；
- 自建服务可以在数据库层做唯一约束；
- GitHub Issues 没有直接幂等键，可以先按仓库、标题和标签组合查询，存在则返回已有 Issue，不存在再创建。

如果外部服务完全不支持幂等，例如某些即时通讯接口，就需要在业务侧引入去重表或消息去重键。

### 5. 在 OpenClaw 插件 / MCP 工具层做封装

如果你在写 OpenClaw 插件或 MCP server，可以在工具定义中统一加入 `idempotency_key` 参数，并让工具内部先查后写。

框架层可以提供一个 `@idempotent` 装饰器或中间件，自动使用工具名、命名空间和参数哈希生成任务键。这样每个新接入的工具默认具备幂等能力，不需要每个开发者重复造轮子。

一个简化示例：

```python
def run_task(task_key, fn):
    try:
        insert_task_run(task_key, 'running')
    except UniqueViolation:
        existing = get_task_run(task_key)
        if existing.status == 'succeeded':
            return existing.result
        if existing.status == 'running':
            return wait_or_skip(existing)
        # failed 状态可以抢锁重试
    try:
        result = fn()
        update_task_run(task_key, 'succeeded', result)
        return result
    except Exception:
        update_task_run(task_key, 'failed')
        raise
```

## 踩坑点

- **只做内存去重**：进程重启后去重信息丢失，重复执行又会发生。内存去重只能作为前置加速，不能替代持久化约束。
- **唯一键过粗或过细**：过粗会导致不同任务被误判为重复；过细（例如加入时间戳）会让重复执行生成不同 key，幂等失效。
- **先执行后登记**：并发时两个 worker 都执行完才写记录，已经产生了重复副作用。必须先占位。
- **忽略“部分成功”**：一个任务包含多个外部调用，前面成功后面失败，重试时如果盲目重复整个任务，会重复前面已成功的副作用。应将任务拆成更小的幂等步骤，或记录已完成步骤，重试只补做失败部分。
- **依赖客户端生成 key 但规则不一致**：不同插件实例或 SDK 版本生成 key 的逻辑不同，导致同一任务不同 key。应把 key 生成逻辑放在服务端或统一 SDK。

## 可复用建议

- 把幂等做成 OpenClaw 插件 SDK 的基础能力，而不是每个插件单独实现。
- 对每个自动化任务，在文档中明确写出“是否幂等”和“重复执行有什么副作用”。
- 测试用例覆盖四类场景：重复触发、并发触发、失败重试、进程重启后重复触发。
- 数据库唯一约束是最可靠的兜底，Redis 只能用于前置快速判断。
- 保留任务执行审计日志，方便回溯重复触发的来源。

## 总结

自动化任务的可靠性，不能建立在“消息只投递一次”的假设上。OpenClaw、Agent 和 MCP 工具链中的重试、并发和事件重复都是常态。

幂等设计让重复执行从“事故”变成“安全冗余”。只要从业务唯一键、持久化占位、状态机和外部调用改造四个层面落实，重复执行就不会产生额外副作用。一个任务可以被触发三次，但最终仓库里只会出现一个 Issue。
