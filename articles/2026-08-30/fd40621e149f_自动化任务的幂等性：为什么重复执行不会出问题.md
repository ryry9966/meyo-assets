## 背景

在 OpenClaw / Agent / MCP / 插件的自动化实践里，几乎没有一个任务只会被触发一次。定时器可能抖动，消息队列会重投，Webhook 会因为对端超时重试，用户在界面上可能双击，Agent 在多轮推理里也可能重复调用同一个工具。如果你按“收到事件就执行”来写逻辑，重复执行只是时间问题。

重复执行带来的问题并不抽象：重复写库、重复发送通知、重复调用付费外部 API、状态被覆盖、下游系统限流甚至封禁。尤其是 MCP 工具调用，客户端超时重试是很常见的行为，工具侧如果不做幂等，就会产生副作用叠加。

## 问题

幂等性要解决的核心是：同一个业务操作执行多次，和执行一次的效果相同。注意这里说的不是“系统不报错”，而是“业务结果不漂移”。一个典型的反例是：自动化任务收到 `payment.created` 事件后直接给用户加权益，如果同一个事件被重复投递三次，用户就会获得三份权益。

在 OpenClaw 这类 Agent 自动化环境里，重复触发的来源更复杂：除了传统的事件重复投递，还有 Agent 决策层面的重复调用、MCP 工具的超时重试、插件之间的级联触发。缺少幂等设计时，排查起来往往表现为“偶发多了一条数据”“金额对不上”“通知发了两遍”。

## 做法/步骤

### 1. 给每个任务定义幂等键

在任务入口处确定一个业务唯一标识，例如 `event_id + task_type`、`request_id + action`，或者 MCP 工具的 `tool_call_id`。这个键要能唯一代表“一次业务意图”，而不是“一次进程执行”。

```text
idempotency_key = event_id + ":" + task_type
```

### 2. 入口层做去重

不要一上来就执行任务，先用幂等键查一下是否处理过。可以用数据库唯一索引加插入，也可以用 Redis `SET key value NX EX` 做短时去重。推荐数据库唯一约束作为最终兜底，Redis 作为快速拦截层。

```sql
INSERT INTO task_execution(idempotency_key, status)
VALUES (?, 'PROCESSING')
ON CONFLICT (idempotency_key) DO NOTHING;
```

如果插入影响行数为 0，说明是重复请求，直接跳过或者返回已有结果。

### 3. 状态机驱动执行

把任务状态拆成 `PENDING -> PROCESSING -> SUCCESS/FAILED`，每次状态流转都用数据库事务或原子操作完成。重复请求进来时，如果发现状态已经是 `SUCCESS`，就不再执行后续逻辑。这比单纯的锁更可靠，因为状态本身可以作为恢复依据。

### 4. 外部副作用后置

如果任务要调用外部 API、发消息、写文件，先落库标记“准备执行”，再执行外部调用，成功后更新状态为 `SUCCESS`。如果执行到一半进程崩溃，下次重试可以根据状态记录决定是否补偿，而不是盲目再执行一次。

### 5. 给 MCP 工具加幂等包装

在工具 handler 层做一个装饰器，要求调用方传入 `idempotency_key` 或 `tool_call_id`。工具被调用时先查去重表，存在则直接返回缓存结果；不存在则执行并记录结果。这样即使 Agent 重复调用同一个工具，也不会产生重复副作用。

## 踩坑点

- **只靠前端禁用按钮不够**。分布式环境下，两个实例可能同时处理同一个事件，本地锁和前端防重都挡不住。
- **Redis 锁过期时间太短**。任务还没执行完锁就释放，另一个实例会进入执行。可以用锁续期，但更稳妥的是用数据库状态做最终裁决。
- **数据库唯一约束 + 软删除会失效**。如果执行记录被软删除，唯一键还在，重复插入会一直冲突；如果物理删除，唯一约束虽然能复用，但会丢失审计信息。
- **先执行外部调用再写库**。崩溃时无法判断外部系统是否已经执行成功。正确顺序是先写状态，再执行外部调用，最后更新结果。
- **把重试和幂等混为一谈**。重试是为了最终成功，幂等是为了重复调用结果一致。两者要配合，但设计目标不同。一个任务可以重试多次，但每次重试都必须幂等。
- **用时间窗口做去重**。时间太短会漏掉慢任务，时间太长会误拦截正常的新任务。用业务唯一键而不是单纯的时间戳。

## 可复用建议

- 在 OpenClaw 自动化任务入口统一加一个幂等中间件，所有事件先经过它。
- 每个 MCP / 插件工具都要求调用方传入 `idempotency_key`；如果没有，就根据参数哈希生成一个。
- 执行记录表至少保留 `idempotency_key`、`status`、`result`、`created_at`、`updated_at`，方便排查重复触发。
- 测试时主动构造重复事件：连续发送相同事件两次，观察第二次是否跳过；模拟任务执行中进程崩溃，重启后重试是否安全。
- 监控重复调用次数和跳过率。如果跳过率异常升高，说明上游触发机制可能出了问题。

## 总结

幂等性不是自动化任务的可选优化，而是基础设计。重复执行不是 bug，而是分布式系统和 Agent 环境的常态。用“唯一键 + 状态机 + 副作用后置”三件套，能覆盖大多数自动化场景。先把重复执行当作默认会发生的事，你的任务才能在重试、抖动、并发中保持稳定。
