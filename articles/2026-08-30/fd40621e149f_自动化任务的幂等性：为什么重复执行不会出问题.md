## 背景：自动化任务天然面对“至少一次投递”

在 OpenClaw、Agent、MCP、插件这类自动化体系里，任务来源非常杂：定时器可能因为进程重启、时区偏移或多实例部署而多跑一轮；Webhook 回调可能因为第三方服务超时重试而重复推送；Agent 在调用工具或 MCP 服务器时，可能因为模型超时、网络抖动把同一个动作执行两遍；消息队列、人工补跑、监控脚本也都带着“至少一次投递”的默认假设。

重复执行本身并不可怕，可怕的是重复执行产生额外副作用：同一条消息被发送两次、同一条记录被插入多次、同一个外部 API 被连续扣费或推送。幂等性要解决的，不是“让任务只执行一次”，而是“当任务被重复执行时，系统状态和外部影响保持一致”。

## 问题：幂等不会自动发生

很多自动化任务的读操作天然幂等，但写操作通常不是。常见问题：

- 先查库判断不存在，再插入；并发两个请求都查到不存在，最终两条都插入。
- 任务重试时，随机生成的时间戳、UUID、临时文件路径每次变化，导致同一个业务动作产生多份残留。
- 外部服务没有幂等接口，重试会造成重复通知或重复扣款。
- 部分成功场景：本地写入成功、外部调用超时，重试时本地唯一键已经存在，简单返回“已存在”会把任务错误地标记为成功，漏掉后续步骤。

## 做法：从入口到存储层层设防

### 1. 为每个任务分配稳定幂等键

不要让每次重试都生成新的随机 ID。幂等键要来自业务本身，比如订单号、用户 ID + 动作类型 + 日期窗口、外部事件的 event_id。在 OpenClaw 的插件或 Agent 工具定义里，可以显式暴露 `operation_id` 参数，让调用方传入稳定标识。

### 2. 数据库唯一约束兜底

最可靠的一层是存储层的唯一索引。例如：

```sql
CREATE UNIQUE INDEX uk_task_operation ON tasks(operation_id);
```

插入时用 `INSERT ... ON CONFLICT DO NOTHING` 或捕获唯一键冲突，冲突后查询已有结果直接返回。这样即使上层逻辑漏判，并发下也不会产生重复记录。

### 3. 状态机原子转移

如果任务有状态流转，使用条件更新抢占执行权：

```sql
UPDATE tasks SET status='running' WHERE id=? AND status='pending';
```

影响行数为 1 才继续执行；为 0 说明已被其它进程抢占，直接退出。这比先查询再更新安全得多。

### 4. 外部调用做请求去重

对于短信、支付、推送等外部 API，如果服务端支持幂等键就优先传入；不支持则在本地建一张 `request_log` 表，调用前先查是否已成功调用，调用后立刻落库。重试时命中记录就不再发起真实请求。

### 5. 让任务本身尽量“可重放”

优先使用 upsert、`INSERT ... ON DUPLICATE KEY UPDATE` 或全量覆盖更新，而不是累加、拼接。比如“更新用户积分”可以写成设置为绝对值，而不是 `+10`；累加操作需要配合唯一流水表防重。

## 踩坑点

- **先查后写竞态**：唯一约束必须在数据库层，否则并发下必现。
- **重试参数漂移**：如果请求里包含当前时间、随机数、临时目录，即使幂等键相同，副作用仍可能不同。应把这些可变因素从幂等键覆盖的语义中剥离，或在重试时沿用初次参数。
- **Webhook 重复投递**：第三方回调通常不保证 exactly-once，必须按 `event_id` 去重，而不是按内容判断。
- **部分成功被误判**：插入冲突不代表任务整体已完成。需要支持“已有记录则查询状态，继续后续步骤”，而不是一律返回成功。
- **忽略缓存和消息队列**：缓存预热、消息消费也需要幂等，尤其是消费者重启后 offset 重置会重复消费同一批消息。

## 可复用建议

- 新建任何写任务时先问一句：它被执行两次会怎样？如果答案不是“和一次一样”，就必须加幂等设计。
- 唯一索引在建表阶段就加，不要等出现重复数据再迁移清洗。
- 插件/工具的描述里写清幂等键的获取方式和唯一范围，让模型或调用方有据可依。
- 测试用例至少覆盖：同参数并发 2 次、同参数重试 3 次、部分成功后重试。
- 监控幂等键冲突次数和去重命中率；冲突不是错误，而是保护机制正在工作。

## 总结

自动化系统的可靠性不来自“保证只执行一次”，而来自“重复执行也不会错”。在 OpenClaw、Agent、MCP、插件这些容易叠加重试的链路里，稳定幂等键、数据库唯一约束、状态机原子更新和外部调用去重构成了四道防线。把幂等性当作工程默认项，重复执行就会从故障源变成安全冗余。
