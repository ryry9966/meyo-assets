## 背景

目前多数 AI 助手仍然是“你问它答”的模式。你要手动输入“帮我查一下昨天构建失败的原因”，它才会去调用工具、读日志、给结论。这种被动模式在对话场景里没问题，但在 OpenClaw、Agent、MCP、插件和自动化组合的环境里，有一个明显的效率缺口：很多触发条件其实是固定的、可枚举的，完全可以在你开口之前就完成。

比如：每天早上检查依赖更新并生成 PR、监控到某个错误日志后自动创建 issue、CI 失败后主动汇总相关提交并把嫌疑 commit 列出来。这些场景的共同点是——触发信号明确、判断标准可描述、执行动作可白名单化。

## 问题

如果每个任务都要等人来发起，Agent 就只是一个带工具调用的 Chatbot，没有发挥“自动化节点”的价值。但直接把 Agent 挂到定时任务或 webhook 上，又容易出现误触发、循环触发、权限过大、上下文爆炸等问题。

真正要解决的不是“让 Agent 更聪明”，而是给它一个可控的主动执行框架：在什么条件下可以自己动，动之前要不要确认，动完之后怎么追责和回滚。

## 做法/步骤

在 OpenClaw 环境里，我用的是一个四段式结构：感知、决策、执行、反馈。

**1. 感知层：把事件源统一成结构化输入**

事件可以来自几个地方：OpenClaw 的 scheduled trigger 定时任务、MCP server 暴露的 resource/watch 能力、插件监听的 webhook、文件系统变化、Git 仓库的 push 事件等。

关键是不要在感知层做复杂逻辑，只做三件事：去重、限流、标准化。例如 webhook 过来的事件先提取 `event_type`、`repo`、`commit_sha`、`timestamp`，然后放进一个待处理队列。定时任务则直接生成一个固定格式的 event 对象。

**2. 决策层：让 Agent 先判断“要不要动”**

事件进入队列后，由 OpenClaw 拉起一个 Agent，给它最小的上下文：事件内容、相关的 3~5 条历史记录、可用工具列表。要求它输出结构化结果，而不是直接执行。

典型的决策 prompt 可以这样约束：

```
你是一个值班助手。收到以下事件：
{event}
判断是否需要采取动作。如果不需要，输出 {"action": "none", "reason": "..."}
如果需要，输出 {"action": "run", "tool": "工具名", "params": {...}, "confidence": 0.0~1.0}
```

这里要强调：决策阶段不能调用写操作工具，只能读。写操作必须放到执行层，并且受白名单控制。

**3. 执行层：白名单 + dry-run + 人工确认**

根据决策结果的风险级别分流：

- 只读动作（查询日志、汇总提交、生成报告）：自动执行，结果写回消息通道。
- 写动作（创建 PR、修改配置、发送通知）：默认先 dry-run，把将要执行的内容展示出来，等待人工确认。只有低风险且次数受限的场景（比如每天最多 1 次）才允许自动执行。

执行工具使用 MCP 暴露，但不要把 shell 全量权限给 Agent。按场景拆成小工具，例如 `create_dependency_update_pr`、`create_issue_from_error`、`notify_channel`，每个工具内部做参数校验和幂等处理。

**4. 反馈层：审计日志 + 结果回写**

每次 proactive 任务都要记录：事件源、决策理由、执行工具、参数、结果、耗时。可以用 OpenClaw 的日志插件或外部监控系统收集。结果同时回写到最初的通知渠道，避免“Agent 偷偷做了事但没人知道”。

## 踩坑点

实际跑起来，以下几个问题最常见：

**触发风暴**：webhook 重试或文件变化会连环触发多个 event。必须在感知层做事件指纹去重（例如用 `event_type + repo + commit_sha` 做 key），并设置同一指纹 10 分钟内的冷却时间。

**上下文膨胀**：把大量历史日志塞进决策 prompt，会导致 Agent 判断变慢且容易跑偏。只给最近事件和最小关联上下文，历史通过工具查询按需获取。

**误判后无法回滚**：写操作如果没有 dry-run 或回滚方案，一旦 Agent 判断错误就麻烦。建议所有写工具都支持 `--dry-run` 参数，或者在执行前把将要修改的内容完整打印出来。

**循环触发**：Agent 执行完创建 issue 后，issue 创建事件又可能被 webhook 捕获，导致再次触发。给执行层加一个 `source: proactive` 标记，感知层过滤掉来自 proactive 自己产生的事件。

**权限过大**：不要图省事给 Agent 一个 `run_shell` 工具。即使有确认机制，shell 权限也容易出问题。按任务拆小工具，每个工具只做一件事，并且参数严格校验。

## 可复用建议

1. **新场景先跑 shadow mode**：只生成建议和计划，不实际执行。观察一周误报率，误报低于预期再放开只读自动执行，最后才考虑写操作自动执行。

2. **动作白名单 + 风险分级**：只读动作自动，写动作人工确认，高风险操作即使人工确认也要二次校验。这个分级要写在 Agent 的系统 prompt 里，而不是靠每次提醒。

3. **给每个 proactive 任务设置 TTL 和最大执行次数**：例如一个定时任务如果连续失败 3 次，就自动暂停并通知维护者，避免无人值守环境下持续消耗资源。

4. **审计日志包含决策理由**：不要只记“执行了什么”，还要记“为什么执行”。Agent 输出的 confidence 和 reason 对后续排查误判非常有帮助。

5. **把触发条件写清楚，比给 Agent 更多上下文更有效**：实际使用下来，大部分 proactive 任务不需要复杂的推理能力，只要把“什么条件下做什么”描述清楚，配合结构化输出，效果就很稳定。

## 总结

Proactive 能力不是把 Agent 变成无人值守的自动化机器人，而是把可枚举的触发条件交给 Agent 做初筛，人工只处理异常和确认。工程上真正重要的是边界、可观测性和回滚能力，而不是追求“更聪明”的模型。

在 OpenClaw 环境里，用“感知-决策-执行-反馈”四段式结构，配合动作白名单、dry-run 和审计日志，可以比较稳妥地实现“不等你开口就把事情办了”。先选低风险、可枚举、有明确完成标准的场景下手，跑通一两个之后，再逐步扩大范围。
