## 背景

在 OpenClaw 这类 Agent 框架里处理批量任务时，单 Agent 经常被三种问题拖慢：上下文膨胀、串行等待、工具副作用互相干扰。比如一个流程既要做多源检索，又要写文件，还要调用 MCP 工具。如果全部塞进同一条执行链，一旦出错，定位和重跑成本都不低。

## 问题定义

更好的做法是：主 Agent 负责拆解与合并，多个 subagent 并行执行互不依赖的子任务。目标不是“并发越多越好”，而是可控并行——每个子任务有明确输入输出、隔离工作区、最小权限、可重试。

## 做法/步骤

1. **先拆任务，不拆 Agent。**  
   按数据依赖把任务切成 N 个 leaf job。能让 subagent 返回 JSON schema，就不要让它返回自由文本。例如：

```json
{
  "task_id": "j_012",
  "source": "url",
  "summary": "...",
  "key_points": [],
  "status": "ok"
}
```

2. **给 subagent 最小权限。**  
   worker prompt 只描述输入、约束、输出格式和失败返回方式。工具只挂它需要的 1-2 个，避免多个 worker 同时写同一文件或争抢同一个 MCP session。

3. **并行调度。**  
   主 Agent 使用 subagent runner 或线程池，建议先设 `max_workers=4`、`timeout=180s`、`retry=2`。不要一上来开 20 个，除非你确认下游 API 和 MCP server 能承受。

4. **汇合结果。**  
   主 Agent 按 `task_id` 收集结果，先校验 schema，再把异常任务聚合成“需要重跑”或“需要人工处理”的列表，不要因为一个任务失败就丢弃整批。

5. **可观测性。**  
   每个 subagent 的入参、工具调用、输出都带同一个 `trace_id`。没有 trace_id 的并行任务等于黑盒，排障时只会看到一坨混在一起的日志。

## 踩坑点

- **上下文复制太大。**  
  把全量文档塞给每个 subagent，token 成本成倍增长，输出也容易变脏。只传必要字段和引用。

- **MCP 工具冲突。**  
  同一个 MCP server 被多个 worker 并发调用，可能出现 session 断开或限流。每个 worker 使用独立 client/session，对共享资源加锁或串行化。

- **输出漂移。**  
  要求返回 JSON，但模型仍可能加解释文字。后处理提取 JSON，失败则标记 `parse_error`，不要中断全量任务。

- **静默失败。**  
  subagent 返回 `status: ok`，但实际可能没执行。校验必要字段非空，关键任务让它附上证据引用。

- **成本失控。**  
  并行降低时延，但不会降低总 token，甚至因重复 prompt 增加总消耗。先跑 2-3 个样本，再放大规模。

## 可复用建议

- 把“拆任务—并行执行—合并结果”封装成固定 pipeline：输入 task manifest，输出 result manifest。
- worker 输出带 `schema_version` 字段，后续升级不破坏主 Agent。
- 所有写操作加幂等 key，例如 `task_id`，避免重试时重复建文件或重复发送。
- 下游限流时，立即回调并行度，配合指数退避重试。
- 增加 dry-run 模式：subagent 只返回执行计划，不做真实写操作，便于调试。

## 总结

Subagent 编排不是让一堆 AI 自由聊天，而是把并行执行变成一条受控流水线。关键在拆分明、契约清晰、失败可重试、状态可追踪。先在 OpenClaw 里跑通“主 Agent 调度 + 少量 worker + JSON 汇合”的最小闭环，再逐步增加并行度和工具能力，比一次性上重型编排更实用。
