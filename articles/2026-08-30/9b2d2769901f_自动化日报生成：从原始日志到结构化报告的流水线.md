## 背景

团队里跑了十几个自动化任务：数据同步、模型推理、定时爬取、告警巡检等等。每天早上的第一件事，就是逐个打开日志文件、CI 面板、消息通知，把前一天的情况手动汇总成日报。时间一长，这件事变成了一种“稳定但毫无成就感”的负担：同一份日志要翻好几遍，漏看一个失败任务就可能耽误半天。

后来我们尝试用 OpenClaw 加 Agent 来做自动化日报，把“原始日志 -> 结构化报告”这个过程固化成一条流水线。这篇文章记录一下具体做法和踩过的坑。

## 问题

原始日志有几个明显的特点：

- **来源分散**：有的在本地文件，有的在对象存储，有的通过 API 暴露，有的只能从 IM 通知里翻。
- **格式不统一**：有 JSON、纯文本、带 ANSI 颜色码的终端输出，也有半结构化的表格。
- **噪声大**：一次任务可能产生几千行日志，真正重要的只有十几行。
- **上下文容易超限**：如果直接把全量日志塞给大模型，要么 token 爆炸，要么关键信息被淹没。

所以，不能简单地把日志丢给 Agent 让它“总结一下”，而是要先做采集、清洗、结构化，再生成报告。

## 做法 / 步骤

### 1. 统一采集入口

我们用 MCP 封装了日志数据源。每个数据源对应一个 MCP 工具，比如：

- `read_local_log`：读取本地日志文件，支持按时间范围过滤。
- `query_ci_jobs`：查询 CI 任务状态和失败日志。
- `fetch_object_storage_logs`：从对象存储拉取指定前缀的日志。

这样做的好处是：Agent 不需要知道日志到底存在哪里，只需要调用统一的工具接口。后续数据源迁移，也只改 MCP server，不动 Agent。

### 2. 定义结构化 Schema

在写任何提取 prompt 之前，先定义日报需要哪些字段。我们定的 schema 大致是：

```
{
  "task_name": "任务名",
  "status": "success / failed / skipped / running",
  "duration_seconds": 123,
  "key_output": "关键输出摘要",
  "error_message": "错误信息（如果有）",
  "log_ref": "原始日志路径或链接"
}
```

这个 schema 是后续所有提取、汇总、展示的基础。不要边写边加字段，否则最后日报会越来越乱。

### 3. 分层处理流水线

整条流水线分三层：

**第一层：预处理**

用脚本或简单规则先过滤掉明显无用的日志行，比如 debug 日志、重复的进度输出、ANSI 颜色码。对于大文件，先按时间范围截取，或者用 grep 提取包含关键字（`error`、`failed`、`exception`、`completed`）的上下文。

**第二层：结构化提取**

把预处理后的日志片段交给 Agent，配合结构化提取 prompt，要求输出 JSON。这里的关键约束是：**只提取，不推理**。明确告诉 Agent：不要推断任务失败原因，不要补全日志里没有的信息，只把日志中明确出现的状态、耗时、错误信息填进 schema。

**第三层：汇总生成**

拿到所有任务的结构化结果后，再让 Agent 根据模板生成 Markdown 日报。模板大致包括：今日概览、失败任务列表、耗时统计、关键输出、需人工跟进事项。

### 4. 定时触发与推送

用 OpenClaw 的定时任务在每天早上固定时间触发流水线。生成完日报后，推送到 IM 群，同时保存一份 Markdown 到仓库，方便回溯。

## 踩坑点

1. **日志格式漂移**  
   同一个任务，不同版本的日志格式可能完全不一样。一旦上游改了日志输出，下游解析器就会静默失效。我们的做法是：在结构化提取层加一个校验，如果 Agent 返回的 JSON 里 `status` 为空或者 `duration_seconds` 为 0，就标记为“解析失败”，而不是硬填一个默认值。

2. **上下文长度控制**  
   即使做了预处理，有些日志片段依然很长。我们限制每个任务的日志片段最多 2000 行，超过就只保留开头、结尾和关键字命中附近的上下文。实测这样能把提取准确率保持在一个可接受的水平。

3. **时区问题**  
   定时任务跑在 UTC，日志时间戳是本地时间，差 8 小时。一开始总是把“昨天”的日志漏掉。后来统一用 ISO 8601 带时区的时间戳，采集时按本地时区算范围。

4. **敏感信息泄露**  
   日志里偶尔会出现 token、密码、用户手机号。我们在预处理层加了脱敏规则，把常见敏感字段替换成 `***`，再交给 Agent。

5. **Agent 幻觉**  
   有一次 Agent 把“任务超时”写成了“任务失败，原因：数据库连接池耗尽”，但日志里根本没有这个信息。后来我们加了强约束：**错误信息必须引用日志原文**，不允许生成日志中不存在的结论。同时保留 `log_ref` 字段，方便人工核查。

## 可复用建议

- **先定义 Schema，再写 Prompt**。Schema 是流水线的合同，避免 Agent 自由发挥。
- **分层处理，不要一步到位**。原始日志 -> 结构化事件 -> 日报摘要，每层职责单一，出错好定位。
- **保留原始日志引用**。报告里每个任务都带上 `log_ref`，人工复核时能快速跳转。
- **用 MCP 封装数据源**。不要把文件路径、API 地址硬编码在 Agent prompt 里，后续维护会轻松很多。
- **失败任务优先展示**。日报的价值在于让人快速看到“需要关注什么”，成功任务可以折叠或只给统计数字。

## 总结

自动化日报的本质，是把“人肉翻日志”变成一条可重复、可监控、可回溯的流水线。OpenClaw 负责编排，MCP 负责数据源抽象，Agent 负责结构化提取和汇总。整个方案不算复杂，但真正花时间的是处理日志格式漂移、上下文长度、敏感信息和幻觉这些工程细节。做完之后，每天早上打开 IM 就能看到一份结构清晰、带原始日志引用的日报，人工只需要花几分钟扫一眼失败项，剩下的时间可以去做更有价值的事。
