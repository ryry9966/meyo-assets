## 背景

团队维护几个后端服务，日志分散在 Loki、K8s Pod 和本地文件中。每天要花 20-30 分钟整理日报：看错误日志、汇总变更、标注异常。重复且容易漏，尤其周末或发布日，人工整理经常滞后。于是想把这件事自动化，但一开始就遇到不少现实问题。

## 问题

简单脚本只能按关键字抓日志，无法判断上下文；直接把当天所有原始日志丢给 Agent，上下文爆炸且输出不稳定；不同服务日志格式、时区、级别定义不统一，清洗成本高；MCP 连接偶尔超时，整条流水线容易断。

## 做法/步骤

### 1. 定义日报结构

先把日报固定为四块：变更摘要、异常事件、性能指标、遗留问题。结构比“自由发挥”更容易让 Agent 输出稳定，也方便后续 diff 和归档。

### 2. 采集与预处理：把原始日志变成结构化事件

用 OpenClaw 的 MCP 客户端连接 Loki 和文件系统 MCP。先通过 jq 和正则把原始行解析为统一 JSON 事件：

```json
{
  "ts": "2025-06-01T08:12:03Z",
  "level": "ERROR",
  "service": "order-api",
  "msg": "db connection timeout",
  "trace_id": "abc123"
}
```

这一步不依赖大模型，全部用确定性脚本，好处是可复现、可单测。可以在 OpenClaw 的插件里配置一个 `log_cleaner` 工具，输入原始行，输出结构化 JSON。清洗层统一处理时区、级别映射、字段抽取和无效行丢弃。

### 3. 用 Agent 做两级分析

第一级：按服务切分事件，让 Agent 只处理某个服务当天的事件，输出异常摘要、数量、时间分布。提示词明确要求只输出 JSON，不要解释。

第二级：把各服务的摘要汇总，让 Agent 按日报模板生成 Markdown。上下文控制得很小：每个服务摘要不超过 200 字，避免重新引入原始日志。

### 4. 输出与推送

生成的 Markdown 写入 Git 仓库的 `reports/2025-06-01.md`，同时通过 webhook 推送到 IM。如果某天 Agent 输出格式错误，回退到上一版模板，并保留原始结构化事件文件，便于人工复查。

## 踩坑点

- **上下文爆炸**：第一次把所有日志粘给 Agent，结果它开始脑补不存在的异常。解决：先聚合，每个服务只给 top 10 错误和统计数字。
- **时区不统一**：Loki 返回 UTC，文件日志是本地时间。统一在清洗层转成 UTC，日报展示时按本地时间渲染。
- **异常判定阈值**：刚开始所有 WARN 都进异常事件，日报变成流水账。后来只保留 ERROR 和连续 3 次以上的 WARN。
- **MCP 连接不稳定**：Loki 偶尔超时，MCP server 会卡住。需要在工具外层加重试和超时，否则整个流水线断掉。
- **不要过度设计模板**：第一版做了图表、趋势图，结果维护成本远超收益。后来先纯文本，后续再考虑可视化。

## 可复用建议

- **分层流水线**：采集、清洗、分析、渲染、推送各层解耦，任何一层挂了可以单独重跑。
- **模板版本化**：日报模板放 Git 里，改了要能 diff，这样能追踪输出变化。
- **先跑通最小闭环**：只处理一个服务、一种日志源，跑通后再横向扩展。
- **确定性脚本承担清洗和过滤**，Agent 只做语言理解和总结，别让它处理噪音。
- **每天保留原始结构化事件文件**，便于审计和回溯，也方便后续训练或调整规则。

## 总结

自动化日报不是“把所有日志喂给大模型”，而是一条工程化流水线：先用确定性脚本把原始日志变成结构化事件，再用 Agent 做低上下文的汇总与总结，最后输出到可追踪的位置。真正省时间的是中间的清洗层和模板约束，而不是模型本身。这个模式也适用于其他重复性报告任务：先用工具把噪音压下去，再让模型做它擅长的语言工作。
