## 背景

写日报是很多团队日常动作，但信息来源分散：git 提交、需求评审、线上告警、群聊结论、CI 状态。每天人工翻这些日志拼日报，重复且容易漏。我们在 OpenClaw 场景里尝试用 Agent + MCP 搭了一条“日志 → 结构化日报”的流水线，这里记录可复用的做法和坑。

## 问题

原始日志的问题不在“没有数据”，而在“太杂”：格式不统一、噪声多、事件之间缺少因果。直接把这些文本丢给 LLM，要求“生成今日日报”，通常会得到看似流畅但夹杂幻觉、遗漏或时序错乱的输出。所以核心难点不是生成，而是先把日志变成可信的结构化中间层。

## 做法

我们拆成五步：

### 1. 采集与归一化

用 MCP 把不同数据源接成统一事件流。每个事件至少包含：时间（UTC）、来源、类型、标题、正文、关联人或项目。比如 git commit、issue 更新、监控告警、IM 里的结论都映射到同一 schema。这里不追求语义，只做字段对齐。

### 2. 清洗与过滤

规则先滤掉明显噪声：自动回复、CI 中间状态、重复通知、机器人消息。再用一个小模型或关键词规则做粗分类，决定事件是否值得进入日报候选。这一步能砍掉 60-80% 的原始量。

### 3. 事件抽取与聚类

把候选事件按时间窗（如一天）分批。Agent 对每批做抽取，输出结构化条目：done（完成）、doing（进行中）、blocker（阻塞）、next（明日计划）、risk（风险提示）。注意不是直接生成句子，而是填充 JSON 字段。

### 4. 结构化中间层

定义严格 schema，例如：

```json
{
  "date": "2025-01-15",
  "done": [{"summary": "...", "source": "git:abc"}],
  "doing": [],
  "blockers": [],
  "next": []
}
```

所有 summary 必须能回溯到原始事件 id。这层是整条流水线的关键，也是审计和修正的基础。

### 5. 报告生成与推送

基于中间层套模板生成 Markdown，推送 IM 或写入文档。模板固定，只有数据变，避免 LLM 即兴发挥。

## 踩坑点

- **直接端到端生成不可控**：我们最早让 Agent 从原始日志直接写日报，结果同一天两次生成结果差异很大，还编造了不存在的会议。后来强制走 JSON 中间层，幻觉明显下降。
- **上下文超长**：一天日志可能几万 token。我们是先按来源分片，每片单独抽取，再合并去重，而不是全部塞进一个 prompt。
- **时区混乱**：git 时间是 UTC，IM 是本地时间，监控是 epoch。统一转成 UTC 存储，展示时再转本地。
- **结构化输出不稳定**：早期让模型“返回 JSON”经常多解释文字或字段缺失。后来加上 JSON Schema 约束、retry 机制，并在解析失败时回退到模板补齐。
- **敏感信息**：日志里可能带密钥、客户名。我们在清洗阶段加脱敏规则，并在 Agent prompt 里声明“只提取工作事项，不复制凭据”。

## 可复用建议

- **先定义中间 schema，再让模型填充**，比端到端生成可靠得多。
- **MCP 作为数据源抽象**：git、issue、监控、IM 都封装成 MCP tool，流水线只依赖 tool 输出，不关心各平台 API 细节。
- **保留原始日志索引**：日报里每个条目带 source id，点开能看原始日志，方便复核和追溯。
- **日报是增量，不是全量**：只关心“今天发生了什么变化”，而不是罗列所有日志。过滤掉无变化事件。
- **设计成插件化**：采集、清洗、抽取、推送都做成可替换模块，某个数据源挂了不影响主流程。

## 总结

从原始日志到结构化日报，稳定性的关键不在生成模型多强，而在中间层和约束。MCP 解决了数据源接入的碎片化，Agent 负责抽取和填充，模板负责输出一致性。这样一条流水线跑起来后，人工只需要每天花几分钟 review 和修正，而不是从零拼日报。
