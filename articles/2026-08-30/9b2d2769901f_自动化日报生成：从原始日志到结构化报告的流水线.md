日报自动化最难的不是“写出来”，而是报告能否被回查、被信任、被复用。把原始日志直接丢给 Agent“总结一下今天”，通常会得到通顺但无法定位来源的文本。

## 背景

日常要汇总 CI 失败、发布记录、告警、定时任务异常和关键业务指标。数据分散在 Git、GitHub Actions/Jenkins、K8s events、应用日志、on-call 通知里。OpenClaw/Agent/MCP 可以把拉取动作工具化，但工具输出格式、粒度、噪声都不同。

## 问题

直接“一个大 prompt 总结全部日志”有三个问题：上下文浪费在重复信息和调试噪声上；LLM 容易算错数量和时间；输出格式不稳定，今天 JSON、明天散文，后续无法入库或对比。

所以流水线顺序应是：先结构化，再统计，最后让 LLM 只写判断与叙述。

## 步骤

### 1. 定义报告契约

先固定输出结构：

```yaml
date: "2026-04-08"
window: [utc_from, utc_to]
sources: [ci, git, alert, cron]
status: healthy
incidents:
  - time: ...
    entity: ...
    severity: high
    summary: ...
    raw_ref: ...
changes: []
metrics: {}
risks: []
followups: []
```

状态、风险等级用枚举值，不要自由发挥。

### 2. 采集与归一化

每个来源写一个适配器，统一为事件结构：

```yaml
ts: ...
source: ci
severity: warning
entity: checkout-svc
title: build timeout
detail: ...
raw_ref: https://...
```

在 OpenClaw/Agent 流程里，建议把每个来源封装成 MCP tool，如 `get_ci_errors`、`get_git_commits`、`get_alert_events`。调度器只做组合，不让工具互相猜格式。

### 3. 预清洗与去重

先做确定性处理：丢 debug/trace；把 ID、时间戳、IP 等变量归一化后再指纹去重；每源按严重度/时间取前 N 条；超长栈保留头尾关键 30～40 行，不要只截前 1500 字。

### 4. 分组摘要再汇总

当日事件很多时，不要一次塞给模型。先按 `entity` 或 `service` 分组生成小组摘要，再做全局摘要，既省 token 也保留细节。

### 5. 渲染与发送

数量、告警数、变更列表、SLO 达标情况由代码算好。LLM 只生成事件说明、风险判断和 followup。最后套固定 Markdown 模板发送。

## 踩坑点

1. **原始日志直灌**：严重告警被稀释成“基本稳定”。必须分层汇总。
2. **时间窗写死自然日**：跨时区会错。统一用 UTC from/to 传给工具。
3. **仅按消息文本去重**：trace id、时间戳变化会导致重复。先去除变量再指纹。
4. **让模型算数**：模型说“少量失败”，实际 12 次。数字必须先由代码统计。
5. **清洗后丢失 raw_ref**：报告无法回查，可信度下降。保留原始链接或 ID。
6. **只要求“返回 JSON”**：常夹带解释或缺字段。使用 JSON Schema 约束并写解析 fallback。

## 可复用建议

- 先跑通一个源，例如只汇总 CI 失败，再逐步加 Git、告警、定时任务。
- Prompt 和 schema 做版本化；保留原始事件、处理后事件和最终报告，便于回归对比。
- 前 1～2 周发草稿到内部频道，人工纠正后沉淀为 few-shot 示例。
- 空窗口输出 `no events in window`，不让模型硬编“平稳运行”。
- 拉取、清洗、格式化分开放，替换数据源时不改总体编排。

## 总结

从原始日志到结构化报告，难点不在 Agent 能力强弱，而在流水线是否可追踪、可回滚、可验证。先把数据变成统一事件，再用代码算数，最后让模型做叙述和风险判断，日报才会从日常负担变成可复用资产。
