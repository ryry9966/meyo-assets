## 背景：两个词都被叫“定时任务”

在 OpenClaw 里配置 Agent 周期行为时，cron 和 heartbeat 经常被混着用。表面上看，两者都能让 Agent 按某种节奏执行动作；但底层调度模型完全不同。选错不是跑不起来，而是会在你意想不到的时刻漏执行、重执行，或者让 Agent 空转消耗资源。

## 问题：混用后的典型症状

做自动化的人大概率见过以下场景：

- 用 heartbeat 做日报，服务重启后间隔被重置，日报时间越偏越远；
- 用 cron 做健康检查，机器在整点宕了十分钟，那轮检查直接跳过，没人知道；
- 同一个任务被两个调度入口触发，幂等没做好，产生重复数据。

这些不是配置手误，而是把两种调度语义当成了同一种东西。

## 核心区别：墙钟锚定 vs 相对间隔

**cron 锚定的是墙钟时间。** 它在“每天 9:00”或“每周一 8:30”这样的绝对时间触发，与服务何时启动无关。适合和人类作息、日历、外部系统约定对齐的任务。

**heartbeat 锚定的是相对间隔。** 它从进程启动（或上一次 beat）开始计时，每隔固定时长触发一次。它不关心现在是几点，只关心“距离上次过了多久”。

这个区别决定三件事：

1. **服务重启影响不同。** cron 不受重启影响，到点就触发；heartbeat 的计时起点会随重启重置。
2. **宕机补偿语义不同。** cron 在宕机期间错过的触发默认不会补跑（除非做 catch-up）；heartbeat 的间隔会在恢复后重新起算。
3. **时区敏感度不同。** cron 必须明确时区，跨区域部署容易踩坑；heartbeat 与时区无关。

## 实操：怎么选

判断标准很直接——问自己一个问题：**这个任务的触发时机，是“日历说了算”还是“系统自己说了算”？**

### 适合 cron 的场景

- 日报、周报、月报等按日历周期产出
- 与外部系统约定时间的数据同步（如“每天凌晨 2 点拉取上游数据”）
- 固定窗口内的批量处理
- 业务上要求“必须在某个时间点之后执行”

配置时务必显式声明时区，不要依赖系统默认：

```yaml
schedule:
  type: cron
  expr: "0 2 * * *"
  timezone: "Asia/Shanghai"
  catch_up: false   # 明确是否补跑
```

### 适合 heartbeat 的场景

- Agent 自身状态巡检与自愈
- 队列/任务积压检测
- 会话保活、心跳上报
- 条件触发的轮询（“每 30 秒检查一次是否有新任务”）

```yaml
schedule:
  type: heartbeat
  interval: 30s
  on_start: true    # 启动时是否先跑一次
  jitter: 2s        # 抖动，避免多实例同时触发
```

### 重叠场景的处理

有些任务两种都能做，这时看失败语义。比如“每小时同步一次数据”：

- 用 cron，服务在某小时整点宕机，那一小时的数据要等下一次，且下游可能感知到缺口；
- 用 heartbeat，服务恢复后 30 分钟内会自动跑一次，但后续节奏会漂移。

**工程上的建议：对外部有约定时间的用 cron；对内部状态维护用 heartbeat；对“至少执行一次”有强诉求的，用 heartbeat + 持久化 last_run 做兜底。**

## 踩坑点

1. **时区陷阱。** cron 表达式不携带时区信息，容器默认 UTC，部署到云上后“每天 9 点”变成“每天 17 点”。必须显式指定 timezone。

2. **重叠执行。** 任务执行时间超过调度间隔时，cron 和 heartbeat 都可能出现并发执行。对非幂等任务必须加锁或单飞机制。

3. **heartbeat 漂移。** 如果 heartbeat 用 setTimeout 实现且间隔太短，实际触发间隔会因事件循环延迟而漂移。关键任务要记录实际执行时间，而非依赖框架的“名义间隔”。

4. **cron 漏跑无感知。** 宕机期间的 cron 不会自动补跑，如果不做监控，漏跑可能长期不被发现。建议对关键 cron 任务记录 last_success_time，超过预期窗口未更新就告警。

5. **重启重置 heartbeat。** 依赖 heartbeat 做“每 24 小时”的任务时，每次部署都会重置计时。要么持久化 last_run，要么这种场景直接换 cron。

## 可复用建议

- **一个任务只归一个调度入口管。** 需要多节奏时，把任务拆成独立 handler，分别挂到 cron 或 heartbeat。
- **cron 任务显式声明 timezone 和 catch_up，不要留默认。**
- **heartbeat 任务加 jitter，避免多实例同步触发造成的峰值。**
- **长任务必须考虑并发控制，调度器本身不保证串行。**
- **关键调度任务记录 last_run 和 last_success，用监控兜底漏跑。**

## 总结

cron 和 heartbeat 的区别不在“哪个更高级”，而在触发语义：一个问“现在几点了”，一个问“过了多久了”。选型时先回答这个问题，再考虑重启行为、宕机补偿和时区。剩下的交给显式配置和监控。
