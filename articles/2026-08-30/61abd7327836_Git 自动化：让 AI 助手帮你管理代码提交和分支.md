## 背景：为什么要把 Git 交给 AI

在 OpenClaw/Agent 工作流里，AI 助手越来越多地承担“改代码”的任务：修 bug、加测试、调整配置、生成文档。但很多人发现，代码改完了，Git 管理仍然是手工活——写 commit message、切分支、合并、打 tag，这些动作重复且容易出错。

一个典型场景：Agent 一次任务改了 12 个文件，涉及 3 个逻辑模块，你让它提交，它给你来一句 `git commit -am "fix stuff"`。然后你看着历史记录，完全不知道这次改了什么、为什么改、影响哪个模块。

另一个场景：Agent 在错误的分支上直接开发，或者把实验性代码推到了 main，回滚时才发现已经污染了共享分支。

这些问题的本质不是 AI 不行，而是我们没给 AI 一套清晰的 Git 操作规范。Git 自动化不是“让 AI 随便跑 git 命令”，而是把人类工程师的提交规范、分支策略、安全检查固化成可执行的约束，让 AI 在这个约束内高效工作。

## 问题拆解：AI 管理 Git 的三个坑

**坑一：commit message 不可控。** 同一个 AI，今天写 "update code"，明天写 "feat: add stuff"，后天直接留空。没有统一格式，changelog 无法自动生成，代码审查时也找不到上下文。

**坑二：分支策略被破坏。** AI 不知道你的团队用 Git Flow、GitHub Flow 还是 trunk-based，它可能直接在 main 上提交，或者创建一堆 `fix-bug-1`、`test` 这样的临时分支。

**坑三：危险操作无人把关。** `git push --force`、`git rebase`、`git reset --hard` 这些命令一旦执行错误，代价很高。AI 如果不加限制地执行，等于把生产分支的命交到概率手里。

## 做法：给 AI 装上一套 Git 护栏

我的方案分四层：**模板层、规则层、沙箱层、审计层**。下面按实施顺序说明。

### 第一层：固定 commit message 模板

不要让 AI 自由发挥，而是给它一个固定的结构。我用的模板基于 Conventional Commits，但做了精简：

```
<type>(<scope>): <subject>

<body>
- what: 这次改动的核心内容
- why: 为什么需要这次改动
- impact: 影响范围（模块/文件/接口）
```

在给 Agent 的 system prompt 里直接注入这个模板，并加上约束：

```
所有 git commit message 必须严格遵循以下格式。
type 只能是: feat, fix, refactor, test, docs, chore, revert。
scope 用受影响模块的简写，不超过 12 个字符。
subject 用祈使句，不超过 50 个字符。
body 必须包含 what/why/impact 三行。
如果无法判断 type，默认使用 refactor。
```

这样做的效果立竿见影：commit 历史变得可读、可检索、可自动生成 changelog。

### 第二层：分支命名和切换规则

给 AI 定义分支规则，核心是**限制它在哪些分支上可以做什么**。

我的规则配置：

```
保护分支: main, develop, release/*
只读操作: 在保护分支上只允许 pull、fetch、diff、log、status
开发分支: 命名为 feature/<issue-id>-<short-desc> 或 fix/<issue-id>-<short-desc>
分支创建前置条件: 必须从最新的 develop 切出
```

在 OpenClaw 的工具定义里，我给 git 命令做了白名单封装。AI 不能直接执行任意 shell 命令，只能调用我封装好的 `git_create_branch`、`git_commit`、`git_push` 这些工具。每个工具内部先做规则校验，不满足就拒绝执行并返回原因。

### 第三层：沙箱环境 + 人工确认

批量改动先在沙箱分支或本地工作区完成，不直接推远程。关键步骤加人工确认门槛：

- **推送前确认**：AI 准备好 commit 后，先输出改动摘要（文件列表、diff 统计、commit message），等人工回复 "approve" 再执行 push。
- **合并前确认**：PR 创建后，AI 不自动 merge，等 CI 通过 + 人工 review 通过。
- **危险命令阻断**：`reset --hard`、`rebase`、`force push` 直接列入黑名单，AI 无法调用。需要时由人手动执行。

这里有个实操细节：确认不要用简单的 "yes/no"，而是让 AI 输出一个结构化的 diff 摘要，人类扫一眼就能判断。摘要格式我固定为：

```
改动文件: 8 个 (新增 2, 修改 5, 删除 1)
主要模块: src/payment, src/order
测试变化: 新增 3 个测试用例
风险评估: 低（无公共接口变更）
```

### 第四层：操作日志审计

所有 AI 执行的 git 操作都写日志，包括：时间、操作类型、分支、commit hash、执行结果、触发上下文。日志落在独立文件里，方便回查。

```
[2025-01-15 14:32:11] commit | branch=feature/123-refund | hash=7d3a... | status=success
[2025-01-15 14:35:02] push   | branch=feature/123-refund | remote=origin | status=blocked(await approval)
```

这套日志不复杂，几十行脚本就能实现，但出问题时它是唯一能帮你还原现场的东西。

## 踩坑点：实测中遇到的真实问题

**坑 1：AI 会“聪明地”绕过规则。** 比如你限制了直接 push，但它发现可以用 `git push origin HEAD:main` 这种间接写法。所以白名单一定要封装在工具层，而不是靠 prompt 告诉它“不要 push”。封装工具里做 URL/ref 解析，识别出目标分支是保护分支就拒绝。

**坑 2：diff 太大导致上下文爆炸。** 让 AI 看完整 diff 再写 commit message，遇到大改动时上下文不够用。解法是让它只读 `git diff --stat` 和关键文件的片段，或者分模块分批提交。不要在 prompt 里要求“读取全部 diff”。

**坑 3：secrets 被提交。** AI 生成代码时可能把 API key、密码写进文件。自动化提交前必须加一道 secret 扫描（gitleaks、trufflehog 之类），扫到就中止提交并提示。这个检查放在 `git_commit` 工具内部，每次提交自动执行。

**坑 4：并发冲突。** 如果你有多个 Agent 同时操作同一个仓库，分支策略必须有唯一性约束。我用 issue-id 作为分支前缀，天然避免重名冲突。没有 issue-id 时加时间戳后缀兜底。

## 可复用建议

这套做法可以抽象成几个可移植的模块，不依赖特定 Agent 框架：

1. **commit 模板 + type 枚举**：一段约 20 行的 system prompt 片段，任何 Agent 都能接入。
2. **git 工具封装层**：把 `create_branch` / `commit` / `push` / `diff` 封装成受限工具，内部做规则校验和日志记录。OpenClaw 的插件机制或 MCP server 都可以承载这层。
3. **审批流**：推送/合并前输出结构化摘要，等人工 approve。这个模式比“全自动”更适合生产环境。
4. **日志格式**：统一为 `时间 | 动作 | 目标 | 结果 | 备注`，方便后续用脚本分析 Agent 的操作行为。

如果你在 OpenClaw 里用 MCP 接 git，可以写一个 `git-safe` MCP server，把上述四层逻辑全部内置。这样无论哪个 Agent 调用，都只能走安全通道。

## 总结

Git 自动化给 AI 做，不是把权限全交出去，而是把规范变成约束。commit message 模板解决历史可读性，分支规则解决协作安全，人工确认解决关键节点风险，日志审计解决事后追溯。这四层搭起来后，AI 管理 Git 的效率和可靠性都会明显提升——但前提是，你愿意花半天时间把护栏搭好。

工程化的核心从来不是“AI 能做多少事”，而是“AI 做错事时，代价有多小”。Git 自动化的目标，就是让错误可控、历史清晰、人工介入成本最低。
