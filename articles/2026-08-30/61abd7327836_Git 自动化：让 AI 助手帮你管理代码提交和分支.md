## 背景：为什么 git 操作成了 agent 自动化的断点

在 OpenClaw 场景里，我们通常让 agent 负责“改代码、跑测试、生成文档”，但这些产物最后都要进入 git 版本库。很多工作流在 agent 完成修改后就停了，需要人手动 commit、切分支、合并 PR。一次两次还好，如果 agent 在批量修 bug 或连续迭代功能，人工提交会明显拖慢节奏，而且提交信息风格很难保持一致。

## 问题：直接给 shell 不现实，信息质量也不稳定

有人会想：给 agent 一个 bash 工具，让它自己执行 git 不就行了。这确实能跑通，但风险很大。agent 可能误执行 `git reset --hard`、`git clean -fd` 或 `git push --force`，一旦上下文里出现错误建议，工作区可能被直接毁掉。另外，模型生成的 commit message 经常过长、中英混杂，或者把多个无关改动塞进一个提交；分支名也可能出现空格、大小写混乱，不利于后续检索和 CI 校验。

更现实的路径是：把 git 操作收口到一组白名单工具，再通过 prompt 规则约束行为。

## 做法：接入 MCP git server + 注入 git 行为规则

### 1. 让 agent 通过受控工具访问 git

在 OpenClaw 中，我习惯给 agent 加一个 MCP git server，而不是直接暴露 shell。这样它能执行的命令只有 status、diff、add、commit、branch、checkout、log 等基础集合，危险命令默认不可达。配置示意如下：

```json
{
  "mcpServers": {
    "git": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/path/to/repo"]
    }
  }
}
```

如果工作区需要多仓库，可以按项目分别配置，避免 agent 跨仓库误操作。

### 2. 在系统提示或任务模板中固定提交规范

光有工具还不够，必须把 git 行为写进 prompt。我常用的片段是：

```text
你拥有一组受控 git 工具，仅用于当前工作区。
允许：status, diff, add, commit, branch, checkout, log, show。
禁止：reset --hard, clean, rebase, push --force, 修改 .git 目录。
提交信息必须遵循：<type>(<scope>): <subject>
subject 不超过 50 个字符，全部小写英文。
如果工作区有未提交变更，先执行 status 与 diff 确认改动范围，再提交。
禁止直接在 main/master 提交，如有新任务先创建分支。
```

这段规则看起来简单，但能避免绝大多数提交信息混乱和误操作。

### 3. 让分支和提交跟着任务走

我通常在任务开始前要求 agent 先确认当前分支，如果不是 main/master，就可以继续；如果是主分支，则先创建 `fix/<slug>` 或 `feat/<slug>` 分支。例如，用户说“修复登录超时”，agent 的完整操作序列大致是：

```bash
git status
git checkout -b fix/login-timeout
# 修改代码
git add src/auth/login.py
git diff --cached
git commit -m "fix(auth): correct timeout handling"
```

这样每个任务都落在独立分支上，提交信息也足够小，后续 cherry-pick 或回滚都方便。

## 踩坑点：这些地方最容易翻车

1. **工具白名单没做好**：如果 agent 拿到的还是 shell，它会“创造性”地执行危险命令。务必用 MCP 或插件层收口。
2. **并行任务抢一个工作区**：两个 agent 会话同时切分支，会互相覆盖未提交内容。建议每个会话使用独立 worktree，或者限制一个工作区同时只跑一个 git 任务。
3. **commit hook 卡住 agent**：pre-commit 如果运行失败或超时，agent 可能反复重试同一个提交。最好让 hook 输出明确错误，并允许 agent 读到 hook 失败原因后停止或修复。
4. **中文路径/文件名被转义**：git 默认可能输出八进制转义，agent 解析 diff 或 status 时容易读错。可以设置 `core.quotepath false` 让输出可读。
5. **push 权限默认关闭**：本地提交风险可控，推到远端就要额外小心。如果必须允许 push，只允许 feature/fix 分支，禁止 main 和 force push。

## 可复用建议

- 把 git 命令封装成返回 JSON 的工具，便于 agent 结构化解析，而不是依赖自然语言输出。
- 在 prompt 中固定提交信息模板，并限制 subject 长度。可以要求 agent 在提交前先输出一遍内容供确认。
- 用 pre-commit 或 CI 检查提交信息和分支名，与 agent 的规则形成闭环。比如分支必须匹配 `(feat|fix|chore)/[a-z0-9-]+`。
- 记录 agent 执行的 git 操作日志，方便出问题时回溯是模型决定还是人工操作。
- 小步提交优于大提交。agent 每完成一个可验证的步骤就提交一次，回滚时粒度更细。

## 总结

Git 自动化不是让 AI 在仓库里为所欲为，而是把版本控制变成 agent 工作流中的一个可调用、可审计、可回滚的环节。OpenClaw 用户可以用 MCP git server 快速接入，关键是做好命令白名单、提交规范、分支策略和校验闭环。这样一来，很多原本需要手动介入的提交和分支管理，可以交给 agent 在受控范围内完成，真正把“改代码—测试—提交”串成一条自动线。
