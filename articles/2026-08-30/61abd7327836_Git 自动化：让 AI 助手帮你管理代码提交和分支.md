# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

在 OpenClaw、Agent、MCP 插件这类自动化工作流里，AI 助手经常需要生成代码、修改配置、更新文档。这些变更最终都要落到 Git 仓库里。但让 AI 直接执行 `git add . && git commit -m "update"` 这种粗放操作，很快就会把仓库历史弄得一团糟：commit message 没有语义、分支混乱、甚至误删未提交的工作。

更麻烦的是，Agent 往往运行在无人值守的环境中。今天它可能在一个 feature 分支上改了三行代码，明天又在 main 分支上把配置推了上去。手动检查每一个提交既不现实，也违背了自动化的初衷。

所以问题不是“要不要让 AI 管 Git”，而是“如何给 AI 一个安全、可审计、能自我解释的 Git 操作边界”。

## 问题拆解

在实际项目中，AI 直接操作 Git 主要面临四类风险：

1. **权限越界**：Agent 拿到一个无限制的 shell 工具，顺手执行 `git push --force`，覆盖远程历史。
2. **分支混乱**：Agent 不知道当前上下文应该用哪个分支，在错误分支上提交，或者反复创建无意义的分支。
3. **提交信息退化**：缺乏约束时，AI 倾向于生成 `fix`、`update`、`wip` 这类低价值 message，破坏 changelog 和 bisect 能力。
4. **并发冲突**：多个 Agent 同时操作同一个仓库，本地分支状态不一致，导致 push 被拒绝或合并冲突。

这些问题的本质是：**通用 Git 命令对 Agent 来说过于灵活，缺少领域约束和上下文注入**。

## 做法与步骤

我的方案是把 Git 能力收敛成一个受限的工具集，通过 MCP server 暴露给 Agent，并在调用层加上策略校验。

### 第 1 步：定义有限指令集

不要给 Agent 一个裸 shell。封装一组语义明确的 Git 工具，例如：

- `git_status`：读取工作区状态（只读）
- `git_diff`：查看未暂存/已暂存差异（只读）
- `git_create_branch`：基于当前 HEAD 创建新分支，强制命名规范（如 `feat/agent-<timestamp>`）
- `git_commit`：暂存指定文件并提交，必须传入 type/scope/description 三个字段
- `git_push`：推送当前分支到远程，默认不带 `--force`
- `git_switch_branch`：切换到已有分支

危险操作（`reset --hard`、`rebase`、`force push`、删除远程分支）**完全不暴露**。即使 Agent 的 prompt 被绕过，工具层也不提供这些能力。

### 第 2 步：在 Agent 上下文中注入仓库状态

每次 Agent 开始工作前，让编排层自动调用 `git_status` 和 `git_diff`，把结果注入到 system prompt 的“当前环境”部分。这样 Agent 知道自己在哪个分支、有哪些未提交改动、最近一次提交是什么。

示例注入片段：

```
当前 Git 环境：
- 分支：feat/openclaw-git-automation
- 工作区状态：2 个修改文件（README.md, src/commit.py）
- 未暂存 diff 摘要：修改了 commit message 生成逻辑
```

这比让 Agent 自己探索要可靠得多，也减少了误操作概率。

### 第 3 步：强制 Conventional Commits

在 `git_commit` 工具内部实现 Conventional Commits 校验。Agent 传入结构化字段，服务端拼接成完整 message，例如：

```
输入：type=feat, scope=mcp, description=add git branch listing tool
输出：feat(mcp): add git branch listing tool
```

不允许裸写 message，所有提交必须经过这个工具。对于自动生成的代码变更，可以让 Agent 先调用一个 `generate_commit_message` 辅助工具（基于 diff 内容生成建议），再由人工或规则确认后提交。

### 第 4 步：分支策略自动化

在编排流程中定义分支规则：

- 新任务默认从 `main` 拉取最新，创建 `feat/agent-<task-id>` 分支
- 任务完成后，Agent 只能推送自己的分支，不能直接操作 `main` 或 `develop`
- 合并由 CI 或人工 PR 完成，Agent 无法直接 merge 到受保护分支

这样每个 Agent 任务天然隔离，冲突概率大幅降低。

### 第 5 步：加入 dry-run 和审批

对于重要仓库，`git_commit` 和 `git_push` 可以先进入 dry-run 模式：只返回将要执行的命令和变更摘要，不实际执行。外部系统（或者用户）确认后再放行。这在无人值守场景下尤其重要，相当于给 AI 的 Git 操作加了一道人工闸门。

## 踩坑点

实际落地时，这几个坑比较典型：

1. **误把 Agent 当人**：给 Agent 完整的 shell 命令，然后试图通过 prompt 约束它“不要做危险操作”。这不可靠。工具层的白名单才是真正的边界。
2. **提交信息过长或含特殊字符**：AI 生成的 description 可能包含换行、emoji、甚至 Markdown 链接。必须在服务端做 sanitize，截断到 72 字符以内，替换换行为空格。
3. **并发操作同一文件**：多个 Agent 同时改同一个文件时，即使分支不同，合并时也会冲突。解决方案是任务粒度和文件锁：一个文件在同一时间只允许一个 Agent 写入。
4. **Agent 忘记切换分支**：有些 Agent 在 task 开始时忘记调用 `git_create_branch`，直接在 `main` 上提交。可以在 `git_commit` 工具里强制检查当前分支名，不符合 agent 分支规范时拒绝执行。
5. **推送失败后 Agent 重复尝试**：如果远程有更新，Agent 可能不停 push 然后失败。需要让工具返回明确的错误类型（如 `non-fast-forward`），并在 prompt 中引导 Agent 先 pull/rebase（或放弃）。

## 可复用建议

- **封装成独立 MCP server**：把上述 Git 工具打包成一个 `git-mcp` 服务，OpenClaw 通过 MCP 客户端连接。配置项包括允许的分支前缀、是否启用 dry-run、commit message 正则等。
- **保留审计日志**：每次工具调用记录输入参数、返回结果、时间戳和 Agent 标识。出了问题可以回溯是哪一步、哪个 Agent 触发的。
- **用 CI 做最后防线**：即使 Agent 推了错误分支，受保护分支的 CI 检查（例如禁止未签名提交、禁止直接 push main）也能拦截。
- **从小仓库开始试点**：先在文档仓库或内部工具库上跑通流程，验证 Agent 提交质量和分支规范性，再推广到核心代码库。

## 总结

Git 自动化不是让 AI 替你做所有 Git 决定，而是通过工具收敛、上下文注入和流程约束，让 AI 在安全边界内高效完成重复性提交和分支管理。核心原则是：**危险操作不暴露、所有提交可追溯、分支隔离、人工可干预**。

在 OpenClaw 生态里，这套能力完全可以通过一个自定义 MCP server 实现。比起让 Agent 拿着 shell 乱跑，一个受限但可靠的 Git 工具集，才是工程上可持续的方案。
