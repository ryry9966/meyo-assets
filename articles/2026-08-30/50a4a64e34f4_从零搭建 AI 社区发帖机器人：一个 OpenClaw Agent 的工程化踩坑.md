## 背景

社区运营需要保持稳定、有质量的技术内容输出，但人工写帖耗时且难以规模化。我尝试用 OpenClaw 的 Agent 能力搭建一个自动发帖机器人：由 Agent 完成选题、内容生成、格式整理，通过 MCP 调用社区发帖接口，再用本地调度器定时触发。目标不是替代人，而是把“从草稿到发布”的重复劳动自动化，人只做最终审核。

这个项目断断续续做了两周，中间踩了不少坑。大部分问题不在 AI 能力本身，而在工程细节：接口稳定性、上下文管理、时区与调度、格式兼容。下面按架构、步骤、踩坑、建议来写。

## 问题定义

需求拆解后主要有四个环节：

1. **选题与内容生成**：根据社区近期话题或知识库生成一篇 800 字左右的技术帖。
2. **格式转换**：社区编辑器对 Markdown 支持不完整，需要预处理。
3. **发布动作**：调用社区 API，携带鉴权信息，处理限流和失败重试。
4. **调度与监控**：每天固定时间触发，失败时告警并记录日志。

如果用纯脚本硬编码，每次调 Prompt、改话题都要动代码。用 OpenClaw 的 Agent 可以把“生成”和“发布”解耦：Agent 负责内容生成和逻辑判断，MCP 工具负责具体动作（查询热点、发帖、检查状态）。这样后续换社区、换模板只需改配置文件。

## 做法与步骤

### 1. 定义发帖 Agent

在 OpenClaw 中配置一个专用 Agent，给它三个工具：

- `fetch_trending_topics`：通过 MCP 连接一个内部接口，返回最近 7 天社区讨论热度关键词。
- `generate_post`：调用 LLM 生成 Markdown 正文和标题，传入主题、字数限制、风格约束。
- `publish_post`：通过 MCP 调用社区发帖 API，返回帖子 ID 和状态码。

Agent 的 system prompt 里写清楚流程：先查趋势 → 选一个具体技术点 → 生成正文 → 调用 publish_post。同时加了硬性规则：不得生成任何外部链接、不得出现敏感词、标题不得超过 30 字。

### 2. 封装 MCP Server

社区发帖 API 需要登录 Cookie 和 CSRF Token。我写了一个轻量 MCP Server（Python），内部维护会话，使用 `requests` 库自动处理 Cookie 更新。MCP 工具暴露 `publish_post(title, content)`，返回 JSON。这样 Agent 不需要关心底层鉴权，只处理文本。

### 3. 调度与状态记录

使用系统 cron 每天 10:00 触发一个 Python 脚本，脚本调用 OpenClaw 的 CLI 启动 Agent 任务。每次运行记录一个 run_id，并把 Agent 的输出、工具调用、耗时、token 消耗写入本地 SQLite。如果 publish_post 返回非 200 或 Agent 中途报错，脚本发一条通知到内部 IM。

### 4. 内容质量兜底

在 Agent 生成后、发布前，增加一个本地校验层：

- 检查字数是否在 600-1300 区间。
- 检测是否包含未转义的 HTML 标签。
- 用正则过滤掉代码块中的多余空行。
- 如果标题为空或重复，自动替换为备用模板标题。

校验层不依赖 LLM，纯规则，保证基本可用性。

## 踩坑实录

### 坑一：社区 API 的会话失效导致 403

第一次上线时，publish_post 经常返回 403。排查发现是 MCP Server 里的 Cookie 过期后没有刷新机制。因为 cron 任务间隔 24 小时，社区会话有效期只有 2 小时。解决办法：在 MCP Server 的每个工具调用前主动检查 Cookie 有效性，如果 401/403 就重新登录。另外在 Agent 侧加了对 publish_post 返回值的判断：如果是 403，Agent 会重试一次并提示“会话已刷新”。

### 坑二：Markdown 被社区编辑器吃格式

社区编辑器会自动把换行合并，导致代码块和列表排版混乱。第一次发布的帖子代码缩进全丢了。后来在 generate_post 的 Prompt 里明确要求“代码块前后必须各空一行，列表项不要嵌套超过两层”，并在校验层把 `\n` 统一替换为 `\n\n` 后再替换回去，只对正文段落处理，不破坏代码块内的换行。

### 坑三：定时任务的时区偏移

cron 跑在 Docker 容器里，默认 UTC 时间，导致帖子在凌晨 3 点发布而不是上午 10 点。解决办法是在容器启动时设置 `TZ=Asia/Shanghai`，并在 Agent 的 system prompt 里强调“发布时间必须符合本地时区”。但 LLM 有时还是会生成“早上好”之类的词，后来直接让脚本在发布前检查当前小时，如果不是 9-11 点就跳过，防止内容与时间不匹配。

### 坑四：上下文无限增长

OpenClaw 的 Agent 默认保留全部对话历史，连续跑一周后 token 消耗暴涨。每天选一个话题生成一帖，但历史里累积了前几天的全部工具调用结果。解决：在 OpenClaw 配置中设置 `max_context_tokens` 和滑动窗口，只保留最近 3 轮对话。另外让脚本每次启动都新建一个会话 ID，不跨天复用。

### 坑五：LLM 偶尔“自由发挥”加链接

虽然系统提示写了“不得添加外部链接”，但 LLM 偶尔会输出一个 markdown 链接，比如 `[参考](http://...)`。第一次审核时没注意，发布后被社区管理员警告。后来在校验层加了正则：匹配所有 `http` 或 `www`，直接删除整段或替换为纯文本。同时把这一条写进 generate_post 的 negative prompt 里，重复强调 3 次。

## 可复用建议

1. **把发布动作独立成 MCP Server**：与 Agent 解耦，便于单独测试和替换。不要直接在 Agent 里写 HTTP 请求。
2. **用状态机管理任务**：`idle → generating → validating → publishing → published`，每一步都有日志和超时。不要依赖 Agent 内部状态。
3. **准备 fallback 模板**：如果 LLM 生成失败或校验不通过，降级到人工预置的 3-5 篇模板帖，避免当天断更。
4. **记录每次 run 的 trace 和成本**：在 SQLite 里存 token 用量、工具调用次数、耗时。一周后就能看出哪个环节最耗资源。
5. **审核环节不要省**：自动发布的帖子必须进入草稿箱，由人点一下“发布”。我后来改成了 publish_post 只创建草稿，人工确认后再真正发布，风险降低很多。

## 总结

这个发帖机器人本质上是一个“LLM 生成 + 工程调度 + 接口适配”的组合。OpenClaw 的 Agent 负责让流程更像人：先查信息、再思考、再行动。但真正决定稳定性的，是 MCP 的会话管理、校验层、状态机和监控。AI 能写好 80% 的内容，剩下的 20% 要靠工程兜底。如果你也想做类似的自动化，建议先把“发布”这个动作跑通，再逐步加入生成和调度，不要一上来就端到端全自动。

目前这个机器人每天稳定产出 1 篇草稿，人工审核只需要 1 分钟。下一步计划接入 OpenClaw 的插件系统，让社区用户可以通过命令手动触发特定主题的生成，而不是只靠定时任务。
