# AI 助手的 heartbeat 设计：轮询 vs 推送的取舍

在 OpenClaw/Agent/MCP/插件自动化的场景里，heartbeat 往往不只是“活着吗”，还承担状态同步、进度拉取、事件通知。选型时，很多人默认轮询简单，但到了多 Agent 和插件编排时，延迟和资源开销会暴露出来。推送看起来更实时，可重连、乱序、重复投递又让人头疼。这里记录一套我们落地过的折中方案。

## 背景：心跳到底在解决什么

先区分两类需求：

- 存活探测：确认远端进程、插件或子 Agent 是否还在。
- 状态/事件同步：需要感知任务进度、队列变化、外部 webhook 到达。

这两类需求如果混在同一个 heartbeat 里，很容易让协议越来越重。实践上建议分开：存活心跳保持轻量，业务状态走独立事件流或按需查询。

## 问题：轮询和推送各自的边界

轮询实现简单，客户端定时调用 `/status`，服务端返回快照。但问题是：如果 5 秒一次，10 个 Agent 就是每秒 2 次请求；如果间隔太长，又会出现几秒甚至十几秒的状态滞后。在多实例部署时，还容易出现“同一秒内大量请求”的尖峰。

推送（SSE/WebSocket/webhook）实时性好，但需要维护长连接。NAT 超时、代理缓冲、进程重启都会导致连接中断；重连后又存在“断线期间事件丢失”的缺口。如果只靠推送，消费端还要处理事件乱序和重复投递。

## 做法：轮询兜底，推送优先

我们在插件和 MCP 工具链路里采用“推送为主、轮询对账”的模式：

1. 客户端启动时，先拉一次全量 `GET /state`，拿到当前快照和最新 `sequence`。
2. 建立 SSE 或 WebSocket 连接，订阅增量事件。每个事件带单调递增的 `sequence`、`event_id`、`type`、`payload`。
3. 服务端每 30 秒发送一个 comment/ping 帧，客户端超时未收到则判定连接假死，主动重连。
4. 客户端另起一个低频轮询（例如 60 秒），只拉 `sequence` 水位线。如果发现本地落后，再触发一次全量对账，补上推送断开期间的缺口。

协议上，所有事件都带幂等键。消费端用 `event_id` 或业务唯一键去重，即使重复投递也不会重复执行副作用。

## 踩坑点

**轮询间隔与惊群**  
多 Agent 共享同一个后端时，固定间隔轮询容易在整点、半点集中。可以用随机抖动（例如 `interval = base * (1 + random(-0.1, 0.1))`）把请求错开。

**推送连接假死**  
TCP 连接没断，但数据已经不通了。常见于 NAT 超时或反向代理缓冲。必须加应用层心跳，不能依赖 TCP keepalive。代理层注意关闭 SSE 缓冲（如 Nginx 的 `proxy_buffering off`）。

**事件乱序/重复**  
不要用时间戳排序。时钟偏移会导致顺序错乱。单调递增的 `sequence` 更可靠。消费端持久化已处理的最大 `sequence`，重复事件直接丢弃。

**背压**  
推送事件过快，消费端处理不过来时，会在连接缓冲区堆积，最终拖垮进程。可以在客户端实现有界队列，超出阈值时丢弃并记录，触发一次全量对账恢复。

**重连后的状态缺口**  
只依赖推送，断线期间的事件会永久丢失。所以必须有兜底对账机制，最简做法就是周期性或重连后拉取一次快照。

## 可复用建议

- 心跳与业务分离：存活探测用轻量 ping/pong，状态同步走事件流或查询接口。
- 重连采用指数退避 + 抖动，避免瞬时风暴。例如 1s -> 2s -> 4s -> 最大 30s。
- 事件协议必须包含 `sequence` 和幂等键，这是后续排查和补数的基础。
- 推送异常时自动降级为轮询，恢复后再切回，保证可用性。
- 记录连接重连次数、心跳延迟、事件积压量。没有观测，心跳问题很难定位。

## 总结

轮询是保底，推送是优化。不要试图用单个心跳解决所有状态同步需求。分层设计，推送优先、轮询对账，再配好幂等和观测，基本能覆盖 OpenClaw/Agent/MCP/插件自动化里的绝大多数场景。心跳设计本身不复杂，复杂的是边界条件：断线、乱序、重复、背压。把这些想清楚，方案就不会跑偏。
