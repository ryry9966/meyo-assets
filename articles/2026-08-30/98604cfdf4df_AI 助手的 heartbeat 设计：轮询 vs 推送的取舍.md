## 背景

在 OpenClaw / Agent / MCP / 插件的自动化实践里，经常出现一个模式：Agent 调用某个工具或外部服务触发一个异步任务，例如构建镜像、跑离线批处理、等待人工审批、监听文件变化，然后需要知道任务何时完成。这个“知道完成”的机制，本质上就是一个 heartbeat / 状态同步问题。

实际落地时，常见的实现有两类：

- **轮询（polling）**：客户端定时请求状态接口，直到拿到终态。
- **推送（push）**：服务端在状态变化时主动通知客户端，通常借助 SSE、WebSocket 或 webhook。

## 问题

轮询实现简单，几乎不挑部署环境：只要客户端能出站访问 HTTP 接口即可。但轮询是在延迟与资源消耗之间做权衡：间隔短了，浪费算力、带宽和数据库连接；间隔长了，任务完成后 Agent 可能还傻等很久。

推送实时性更好，但要求服务端能主动触达客户端。这意味着要么维护长连接，要么暴露公网回调地址。同时还要处理连接断开、重连、消息乱序、重复投递、幂等消费等一系列问题。在 OpenClaw 插件或 MCP server 场景中，部署环境往往千差万别：有的跑在容器里只有出站网络，有的在 NAT 后面无法接收 webhook，有的服务端不支持长连接。因此没有单一最佳方案，只能根据约束做取舍。

## 做法 / 步骤

### 1. 先定义状态模型

一个最小可用的 heartbeat 状态可以包含这些字段：

```json
{
  "task_id": "uuid",
  "status": "pending|running|done|failed|timeout",
  "progress": 0.42,
  "message": "processing...",
  "updated_at": "2025-01-01T12:00:00Z",
  "version": 7
}
```

其中 `version` 必须单调递增，用于处理推送乱序和重复问题。

### 2. 先用轮询打底

在 MCP 工具中触发异步任务后，返回 `task_id`，Agent 侧进入等待循环，每隔一段时间调用一次 `get_status`，直到 `status` 变成终态或超过最大等待时间。轮询间隔可以做退避：前 10 次 1 秒，之后 2 秒、5 秒，上限 10 秒。这样能降低服务端压力，又不至于在任务早期响应太慢。

### 3. 预留推送接口

在设计状态服务时，把“状态变化”抽象成一个内部函数，例如 `on_status_change(task_id, old_status, new_status)`。后续接入 SSE 或 webhook 时，只在这个函数里向外发事件，不影响核心状态机。

### 4. 引入推送与降级

如果部署环境允许，可以接入 SSE。事件结构类似：

```json
{"task_id": "uuid", "version": 8, "status": "done", "progress": 1.0, "message": "ok"}
```

客户端收到事件后比较 `version`，只接受高于本地版本的状态，避免旧事件覆盖新状态。推送连接断开时，自动切回轮询；推送恢复后再切回去。可以设置一个容忍窗口：断线后 5 秒内重连成功则继续推送，否则进入轮询模式。

## 踩坑点

1. **轮询接口必须幂等**：如果 `get_status` 有副作用，比如重置计时器或触发新任务，并发轮询会直接打乱状态。查询接口应该设计为纯只读。

2. **推送乱序与重复**：网络重传可能导致同一事件多次到达。务必用 `version` 字段做幂等和排序，服务端更新状态时要保证原子性。

3. **长连接需要应用层心跳**：很多 SSE / WebSocket 实现不会立即发现连接已死。建议每 30 秒发一个 ping/pong 或空注释行，超时未收到则主动断开并重连。

4. **超时判定不要只看客户端时钟**：客户端与服务器时间可能不同步。应基于服务端返回的 `updated_at` 和本地接收时间计算，或者由服务端直接返回是否超时。

5. **防火墙限制**：Agent 如果运行在 NAT 后面，推送通常无法穿透。此时只能选择轮询，或者使用反向隧道（出站 WebSocket），但复杂度会大幅上升。

6. **过早优化推送**：在任务量小、实时性要求不高时，轮询完全够用。一上来就上 WebSocket + 消息队列 + 重连管理，往往属于过度设计。

## 可复用建议

- 把 heartbeat 逻辑封装成独立模块，配置项包括 `interval`、`max_retries`、`backoff_factor`、`push_url`、`reconnect_interval` 等。
- 状态机明确为 `PENDING -> RUNNING -> DONE/FAILED/TIMEOUT`，不允许跳跃。任何非法转换都要记录日志。
- 观测性很重要：每次轮询或推送事件都记录 task_id、延迟、版本号、重连次数。出问题时能快速判断是网络问题还是状态机问题。
- 优先考虑 SSE 而不是 WebSocket：SSE 基于 HTTP，部署简单，支持自动重连，单向推送已经够用。
- 如果使用 webhook，一定要加签名校验，防止伪造状态事件。
- 在 OpenClaw 插件中，MCP 工具可以返回 `task_id` 和 `status_url`，让 Agent 自行选择轮询还是等待推送，保持工具接口简单。

## 总结

AI 助手的 heartbeat 不是简单的“每隔几秒问一次”，而是根据部署约束、实时性要求和资源预算做权衡。工程上的经验是：先实现可靠、无副作用的轮询，再在必要时加入推送，并保留降级路径。轮询保证正确性和简单性，推送优化延迟和资源。两种模式可以共存，关键是状态模型一致、版本控制严格、观测到位。最终目标是让 Agent 不因等待状态而卡死或误判，同时不给基础设施增加无谓负担。
