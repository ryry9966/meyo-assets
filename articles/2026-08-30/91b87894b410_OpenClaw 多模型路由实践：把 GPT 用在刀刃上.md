## 背景

在 OpenClaw 里接模型不像聊天客户端只选一个模型。Agent 链路里有意图识别、工具调用、结构化提取、长文本总结、敏感数据清洗等环节，不同环节对模型能力、延迟、成本、隐私的要求差异很大。全用 GPT 成本会随调用量线性上涨，部分内部数据处理也不适合出网；全用本地模型，复杂推理和工具调用容易出错，拖垮自动化流程。多模型路由是绕不开的工程问题。

## 问题

什么时候该走 GPT，什么时候该走本地模型？如果只按“复杂/简单”二分，实践中会频繁踩坑。真正需要回答的是：这个任务对模型能力的硬性要求是什么？数据能不能出网？失败后有没有降级路径？

## 做法与步骤

### 1. 把任务按能力需求拆开

不要笼统地说“本地模型不行”。先列高频任务：

- 意图识别、实体提取、分类、格式化输出：通常本地模型够用。
- 工具调用、多步推理、复杂代码生成、长文档总结、模糊指令理解：优先 GPT。
- 涉及隐私、密钥、内部数据的预处理：默认本地模型。

### 2. 在 OpenClaw 中建立路由规则

思路是按 task/agent 维度绑定模型，而不是全局切换。示例配置思路：

```yaml
router:
  default: local
  rules:
    - task: tool_call
      model: gpt-4o-mini
    - task: complex_reasoning
      model: gpt-4o
    - task: pii_redaction
      model: local
```

默认本地，只有明确需要强工具调用或复杂推理时才上云。这样成本可控，规则也保持克制。

### 3. 给本地模型设置能力边界

本地模型更适合做“有约束的输出”：固定 JSON、固定分类、短文本改写。尽量用 JSON Schema 或正则校验兜底，不要让它自由发挥工具调用。若本地模型要参与工具选择，至少限制在小工具集内，并在 MCP 工具层做入参校验。

### 4. 加降级路径

本地模型解析失败、输出格式错误、超时，自动切换到 GPT；GPT 侧超时或限流时，降级到本地模型处理简化版 prompt。降级要记录原因，否则会掩盖问题。

### 5. 记录路由命中与成本

至少记录每条请求的路由结果、模型、token 数、延迟、是否降级。跑几天后，把“本地模型失败率”和“GPT 成本分布”拿出来看，再调整规则。

## 踩坑点

- **本地小模型工具调用不稳定**：经常生成不存在的工具名或非法 JSON。不要把它直接暴露给完整工具集。
- **上下文长度会静默截断**：本地模型上下文窗口小，长 prompt 很容易被截断，输出看起来正常但实际丢了关键信息。需要显式控制输入长度。
- **模型切换导致行为不一致**：GPT 和本地模型对同一套 prompt 的输出风格可能差异很大，下游 MCP 如果依赖固定格式，容易解析失败。最好统一输出 Schema。
- **敏感数据误上云**：有些数据字段看起来不敏感，但组合起来可识别。涉及内部文档、用户 PII 时，默认本地更稳妥。
- **规则过多难以维护**：不要一上来做几十条细粒度规则，先按任务大类分，后续用数据说话。

## 可复用建议

- 默认本地，显式上云。路由规则保持克制。
- 本地模型只做“高约束、低推理”任务，复杂工具调用交给 GPT。
- 在 MCP/工具层做 Schema 校验，别把模型输出直接当可信输入。
- 设置每日 token 预算与告警，避免某个自动化任务跑飞。
- 每两周回看一次路由日志，把高失败率任务升级到 GPT，把稳定任务降级到本地。

## 总结

OpenClaw 的多模型路由不是“哪个模型更好”的问题，而是把不同成本和能力匹配到合适任务。GPT 适合复杂推理、工具调用和模糊意图；本地模型适合高频、低推理、敏感数据的结构化处理。路由规则不用一开始就完美，先用“默认本地 + 显式上云”跑起来，再根据失败率和成本慢慢调，比一次性设计完整策略更靠谱。
