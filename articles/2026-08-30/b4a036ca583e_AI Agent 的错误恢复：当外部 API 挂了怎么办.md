在 OpenClaw 这类 Agent 编排环境里，外部 API 调用是工作流中最容易出问题的环节。天气、地图、支付、CRM、向量库、模型推理服务，任何一方出现超时、限流、5xx、返回结构变化，都会直接影响 Agent 的任务完成率。与其祈祷第三方永远稳定，不如把错误恢复做成工具层的默认能力。

问题不是“API 挂了”，而是 Agent 面对失败时的行为不可控：有的会把错误信息当成事实继续推理；有的会反复重试直到上下文窗口被错误堆栈塞满；还有的会因为一个工具失败而中断整条任务链。更糟的是，如果多个 Agent 或任务同时触发重试，可能把小故障放大成对下游的流量冲击。

我建议把恢复逻辑放在工具层，而不是依赖模型临场发挥。步骤如下：

**1. 错误分类**

给每个外部工具定义统一错误契约：`ok`、`error_type`、`message`、`fallback`。`error_type` 至少区分 `timeout`、`rate_limit`、`server_error`、`client_error`、`invalid_response`。分类依据 HTTP 状态码、异常类型和响应结构校验结果。只有明确可重试的类型才进入重试流程，4xx 这类客户端错误通常不应盲目重试。

**2. 重试策略**

对 `timeout`、`rate_limit`、`5xx` 使用指数退避加抖动。例如 base delay 500ms，最大 3 次，退避因子 2，抖动 ±20%。重试必须设置上限，否则 Agent 可能被一个慢接口拖死。

**3. 超时控制**

每次外部调用都带超时，例如 10s。连接超时和读取超时分开设置。在 OpenClaw 工具里，可以用 `Promise.race` 或 `asyncio.wait_for` 包裹；如果用 MCP，可以在 client 层统一加超时中间件。

**4. 降级与兜底**

为关键工具准备 fallback：缓存上一次成功结果、返回默认值、调用备用数据源。降级结果必须在 `message` 或 `fallback` 字段标记“数据可能过期/非实时”，让 Agent 知道不能把它当作最新事实。

**5. 熔断与隔离**

对同一个下游服务的连续失败计数，达到阈值后暂时短路，直接返回“服务暂不可用，请稍后再试”。熔断器按服务维度隔离，不要全局共用一个。

**6. 可观测性**

记录每个工具调用的耗时、错误类型、是否重试、是否降级。用结构化日志或 tracing，方便事后复盘。

踩坑点：

- **非幂等操作盲目重试**：创建订单、发送通知、扣款等操作，如果下游不支持幂等，重试可能造成重复副作用。这类工具需要额外设计：使用幂等键，或在重试前把操作变成可查询状态的异步任务。
- **把完整错误堆栈喂给 LLM**：既浪费 token，又可能让模型沿着错误信息编造原因。只给模型摘要和可执行动作，例如“第三方超时，已重试 3 次，返回上一次缓存结果”。
- **没有超时**：一个挂起的请求可以卡住整个 Agent loop，尤其是同步工具。所有外部调用都要有硬超时。
- **多个工具共用一个熔断器**：A 服务故障导致 B 服务被短路，影响面被放大。熔断器必须按下游服务或工具粒度隔离。
- **降级结果未标记**：Agent 以为拿到新鲜数据，做出了错误决策。降级时要在返回结构中明确标记。
- **让模型自己决定是否重试**：模型可能无限重试或放弃过快，且不可复现。重试策略应该由工具层或中间件执行。

可复用建议：

可以封装一个通用的外部调用包装函数，统一处理超时、重试、熔断、降级，返回结构化结果。例如在 TypeScript 中：

```ts
const result = await withRecovery(
  () => callWeatherAPI(city),
  {
    retries: 3,
    timeoutMs: 8000,
    fallback: () => getCachedWeather(city),
    circuitKey: 'weather',
  }
);
```

对 MCP 工具，可以做一层代理/中间件，在工具执行前后统一注入错误处理，避免每个工具重复写逻辑。测试时用 chaos 工具模拟超时、5xx、畸形响应，验证 Agent 是否能正确使用降级数据并继续任务。

总结：外部 API 挂了是常态，不是意外。把错误分类、重试、超时、降级、熔断、可观测性做成工具层的基础设施，Agent 才能在真实环境里稳定运行。模型负责推理和决策，工具层负责可靠地失败。
