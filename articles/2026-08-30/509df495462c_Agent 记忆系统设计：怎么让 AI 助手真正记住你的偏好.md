## 背景

很多 Agent 项目做到后面，都会卡在同一个问题上：换一个会话，AI 就忘了你之前说过什么。于是有人把整段聊天记录塞进 system prompt，有人接了个向量库做“长期记忆”，但效果往往不稳定——要么上下文爆炸，要么检索出来的记忆牛头不对马嘴。

在 OpenClaw/Agent/MCP 的实践里，记忆系统不是“存得多”就能用，而是要解决三个工程问题：

1. **什么该记**：用户的即时指令、长期偏好、事实信息、行为习惯，不能混在一起。
2. **什么时候用**：记忆要在正确的时机被检索并注入，而不是全量堆给模型。
3. **怎么更新**：偏好冲突、时间衰减、用户显式纠正，都需要明确的规则。

## 问题拆解

典型的失败模式有几种：

- **短期当长期用**：把对话历史直接当长期记忆，导致噪声严重，真正有用的偏好被淹没。
- **没有结构**：偏好以自然语言散落在日志里，检索只能靠关键词，语义稍微变一下就读不出来。
- **写入无节制**：每次对话都调“记住”工具，记忆库膨胀，工具调用开销大，还容易污染后续上下文。
- **冲突无来源**：用户说“我不喜欢用 Docker”，后来又说“这次用 Docker 部署”，系统不知道哪次优先级更高。

这些问题如果不提前设计，记忆系统很快就会变成“垃圾堆”。

## 做法 / 步骤

一个可落地的轻量方案，不需要一上来就上复杂架构。核心是分层 + 结构化 + 工具化。

**1. 分层记忆**

至少分三层：

- **会话级 scratchpad**：当前任务临时状态，会话结束即清空。
- **用户 profile**：稳定偏好和事实，例如“常用语言是 Python”“部署偏好是 Docker Compose”。
- **行为记忆**：用户与 Agent 交互中表现出的习惯，例如“喜欢先看方案再执行”“不喜欢冗长解释”。

**2. 结构化 schema**

用 JSON 定义每一条记忆，而不是存纯文本。例如：

```json
{
  "key": "deploy_preference",
  "value": "docker_compose",
  "source": "user_explicit",
  "confidence": 0.9,
  "updated_at": 1716000000,
  "ttl": 15552000
}
```

`source` 用来区分来源：用户显式声明 > 行为推断 > 系统默认。`ttl` 控制有效期，避免陈旧偏好永久占用。

**3. 通过 MCP / 插件暴露工具**

在 OpenClaw 里可以做一个 MCP server，对外提供三个工具：

- `remember_user_preference(key, value, source, confidence)`：写入或更新记忆。
- `search_memory(query)`：根据当前上下文检索相关记忆。
- `list_active_preferences()`：列出当前仍然有效的高置信偏好，供用户审查。

工具返回应明确区分“命中”“未命中”“已冲突”，不要让模型在没结果时自己编造。

**4. 注入策略**

不要把所有记忆都塞进 system prompt。只注入满足以下条件的条目：

- 置信度高于阈值（例如 0.7）
- 未过期
- 与当前任务语义相关（可以用简单 embedding 或关键词得分）

短期任务只注入与任务直接相关的少量条目，避免上下文浪费。

**5. 更新与冲突处理**

偏好更新不能简单覆盖。建议做轻量合并：

- 相同 `key` 且 `source` 等级更高（用户显式 > 行为推断）则覆盖。
- 相同 `key` 且等级相同，则比较 `confidence` 和时间戳，新数据加权更高。
- 冲突无法自动解决时，返回“存在冲突”，让模型询问用户，而不是静默选一边。

## 踩坑点

- **全量注入**：短期看似乎“模型都知道”，但很快会撞到上下文上限，且噪声会降低指令遵循能力。
- **无时间衰减**：用户三个月前说的偏好可能已经失效，不做 ttl 或访问频率衰减，系统会越来越“固执”。
- **只存不查**：记忆库很全，但检索策略太弱，永远用不上。检索质量比存储容量更重要。
- **忽视用户可见性**：用户看不到自己被记了什么，会不信任。提供一个 `/memory` 查看/删除入口，能显著减少“你记错了”的挫败感。
- **敏感信息无边界**：不要把凭据、token、私密对话内容写进通用记忆库。敏感数据应当隔离，或只保存在本地加密存储。

## 可复用建议

- **从最小 schema 开始**：先只做用户 profile 和偏好两类，跑通闭环再加向量检索。
- **把记忆工具当成一等公民**：在 system prompt 里明确告诉模型何时应该调用记忆工具、何时不该调用，减少无效写入。
- **记录来源和时间**：所有记忆条目都要有来源、置信度、时间戳，否则后期无法清理。
- **给用户控制权**：支持查看、修改、删除记忆，尤其是用户显式纠正后要能立即更新。
- **可观测性**：在调试模式下输出“本次注入了哪些记忆、为什么”，方便排障。

## 总结

Agent 记忆系统的目标不是“让 AI 像一个有无限记忆的人”，而是在正确的时刻、以正确的粒度，提供正确的上下文。分层存储、结构化 schema、工具化读写、冲突处理和时间衰减，是工程落地中最值得投入的四个点。OpenClaw 的 MCP/插件机制天然适合做这类记忆工具：把记忆从 prompt 层面剥离，交给可观测、可控制的工具链，才能真正做到“记住你的偏好”，而不是“记了一堆没用的东西”。
