## 背景：Agent 有了工具，但缺少“岗位说明”

在 OpenClaw 的实践里，Agent 不再只是聊天机器人。通过 MCP、插件和自动化管线，它能读写文件、调用外部服务、下发构建指令，甚至操作浏览器。能力越强，越需要一个稳定的行为契约：它是谁、能做什么、遇到模糊指令时怎么处理。

如果只依赖每次会话里的提示词，有几个明显问题：上下文一长，Agent 会逐渐偏离最初的设定；多 Agent 协作时，各自风格漂移；工具权限开放后，Agent 可能做出“技术上可行但业务上不该做”的操作。SOUL.md 就是为这类问题准备的——一个放在 Agent 项目目录下的 Markdown 文件，像代码一样被版本管理，明确 Agent 的人格与边界。

## 典型问题：三个真实翻车场景

1. **行为漂移**：一个原本设定为“只提供建议、不直接改配置”的运维 Agent，跑了 20 轮对话后，开始主动执行 `kubectl delete pod`，理由是“帮你清理资源”。SOUL.md 没写清“删除操作必须二次确认”，模型忘了初始约束。
2. **工具滥用**：接入了邮件发送 MCP 的 Agent，在用户说“通知相关人员”时，直接给整个邮件组群发了一份包含内部日志的草稿。边界缺失，导致工具被以错误范围调用。
3. **协作不一致**：三个 Agent 分别负责代码生成、代码审查、文档编写，结果一个用英文输出、一个用中文、一个混用术语。没有统一人格定义，协作产物质量像拼凑的草稿。

## 做法：SOUL.md 的五个核心模块

SOUL.md 不需要面面俱到，但要覆盖以下五块。

**1. 核心身份（一句话）**  
例如：“你是一个面向内部开发者的 CI 排障助手，语气克制、结果导向，不提供未经证实的操作建议。”这句话放在文件最顶部，Agent 加载时最先读到。

**2. 操作边界（白名单 + 黑名单）**  
白名单比黑名单更可靠。写清“允许执行：只读查询、日志搜索、状态检查”，以及“禁止执行：删除、重启、修改配置文件、发送外部邮件”。如果工具很多，按工具名列出权限，而不是笼统地说“不要做危险操作”。

**3. 决策规则（何时停下）**  
定义必须停下并请求确认的场景，例如：影响生产环境、涉及个人数据、批量操作超过 5 个对象、删除或覆写文件。给 Agent 一个明确的“止损线”。

**4. 工作流模板**  
把常见任务的步骤写进去，比如排障流程：收集日志 → 定位可能原因 → 给出诊断和建议 → 等待用户确认 → 执行修复。这样即使上下文很长，Agent 也有稳定的路径可循。

**5. 语气与输出格式**  
明确输出语言、代码块风格、是否使用 emoji、结论前置还是过程前置。别小看这一点，多 Agent 协作时，格式统一能让结果直接拼接，不用二次清洗。

## 踩坑点

- **写太长**：超过 500 行的 SOUL.md，模型实际只会记住前几段和最后几段。关键约束必须放在开头，重复强调。
- **否定式表述太模糊**：“不要做危险操作”等于没说。要写成“禁止执行任何修改 `/etc` 下文件的命令”。
- **与系统提示词冲突**：SOUL.md 的优先级要高于默认 system prompt，否则会被稀释。通常在加载时把 SOUL.md 拼接到 system prompt 最前面。
- **多 Agent 各自为政**：如果每个 Agent 有自己的 SOUL.md，要确保边界不互相打架。建议在团队级放一个 baseline SOUL.md，项目级只覆盖差异部分。
- **把 SOUL.md 当成权限控制**：这是最大的坑。SOUL.md 只是提示词层面的约束，不是安全沙箱。真正的危险操作仍然要靠运行时权限、命令白名单和审计日志来控制。

## 可复用建议

1. **用 YAML frontmatter 结构化关键字段**：把身份、允许工具、禁止操作、确认策略放进 frontmatter，方便程序解析，也能让模型更清晰地识别。
2. **纳入 CI 检查**：在 CI 里增加一个 lint 步骤，检查 SOUL.md 是否包含必备字段、是否有明显的模糊否定词。
3. **做行为对齐测试**：准备一组测试输入，比如“帮我把这个服务重启一下”“把这个文件删掉”，检查 Agent 是否按 SOUL.md 停下确认或拒绝。
4. **保持简短，定期修剪**：SOUL.md 不是文档库，是行为契约。每加一条新规则，就考虑删掉一条过时的。
5. **与工具描述配合**：MCP 工具自身的描述也要写清权限边界，SOUL.md 里的约束要和工具描述一致，否则模型会感到矛盾。

## 总结

SOUL.md 本质上是一份给 Agent 的“职位说明书 + 安全手册”。它不能替代代码层权限控制，但能把“可能越权”变成“默认停下确认”，把“风格漂移”变成“输出稳定”。在 OpenClaw 这类 Agent 编排环境中，把 SOUL.md 当代码一样评审、测试、版本管理，是让多 Agent 真正可用的基础工程习惯。
