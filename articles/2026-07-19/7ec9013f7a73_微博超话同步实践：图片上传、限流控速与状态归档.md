# 微博超话同步实践：图片上传、限流控速与状态归档

## 背景

团队需要将海外社区（如 Twitter、博客）的内容自动同步到微博超话，以便中文用户及时获取动态。人工搬运不仅效率低，还容易漏帖、错帖。我们在 OpenClaw 的自动化体系上构建了一条超话同步管线，重点解决了图片上传、接口限流和状态归档三个工程问题。这篇文章不讨论合规性，专注技术落地的真实踩坑和可复用设计。

## 问题拆解

同步管线需要完成以下动作：

1. 从源平台拉取素材（文本、图片、链接）
2. 通过微博接口将内容发布到指定超话
3. 保留发布记录，避免重复发送
4. 应对微博严格的反爬与频率限制

微博开放平台对普通开发者的权重不高，但超话发帖并未完全封闭，通过模拟手机端或网页端请求仍可稳定运行。我们选择维护一套 cookie 认证 + 抓包验证的轻量方案，而不是使用受限的官方 API。

## 做法与步骤

### 1. 图片上传：从原始资源到微博 pic_id

微博发布带图帖时，需要先上传图片获得 `pid`，再将 pid 传入发帖接口。上传流程如下：

- **请求方式**：`multipart/form-data`，图片字段名为 `b64_data` 或直接附二进制流，视接口版本而定
- **关键参数**：除了图片，还需附加 `token`（从 cookie 中提取）、`cb`（jsonp 回调，可固定）等
- **返回格式**：通常为一串 JSON，包含 `data.pics.pic_1.pid`，即需要的 pid

**踩坑点**：
- 图片必须 **≤5MB**，且支持 `jpg/png/gif`，webp 会上传失败但无明确报错，仅返回空数组
- 部分网络下需要携带 `Referer: https://weibo.com/` 和 `Origin` 头，否则会被 CORS 或风控拦截
- cookie 时效约 48~72 小时，过期后上传接口返回 `-100` 或重定向至登录页，需要自动化刷新

在 OpenClaw 中，我们将图片上传封装成 `weibo_upload_image` 的 MCP 工具。工具内建了尺寸预检、格式转换（Pillow 转 JPG）与指数退避重试，确保上游 Agent 只需传入图片 URL 即可拿到 pid。

### 2. 限流控速：用令牌桶对抗频率限制

超话发帖频率过高会被临时封禁（现象为发帖返回成功但在超话内不可见，或直接返回错误码 10024）。观察得出安全窗口约 **每分钟不超过 2 条**，突发超过 5 条容易触发风控。我们使用分层的限流策略：

- **全局发帖令牌桶**：容量 2，填充速率 2/min，所有超话共享
- **单超话冷却**：同一超话连续发布后强制 `sleep(45s)`，避免话题维度降权
- **错误感知降速**：若收到 `10024` 或 `20019`（操作太频繁），立即休眠 90 秒并重置令牌桶

实现上，OpenClaw 的 Skill 可以直接读取 Redis 中的计数，或使用内置的 `rate_limiter` 装饰器。我们选用 Redis Lua 脚本来保证原子性：

```
-- 伪代码
local current = redis.call("INCR", key)
if current == 1 then
    redis.call("EXPIRE", key, 60)
end
if current > 2 then
    return 0  -- 拒绝
end
return 1
```

该限流器同时作为 MCP 资源暴露，Agent 可在决策前查询 `weibo:rate:usage` 来评估等待时间。

### 3. 状态归档：防重与幂等

重复发布是同步流水线的大忌。我们以 **源平台内容 ID + 目标超话 ID** 作为唯一键，在 SQLite 中维护一张 `sync_log` 表：

```sql
CREATE TABLE sync_log (
    source_id TEXT,
    topic_id  TEXT,
    status    TEXT,   -- 'success', 'failed', 'skipped'
    weibo_mid TEXT,
    pid       TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (source_id, topic_id)
);
```

每次发帖前进行“查重-发帖-记录”的事务性操作。如果相同组合已存在且状态为 success，则跳过；若为 failed，可根据失败原因决定是否重试。SQLite 轻量但足以支撑万级记录，搭配定时 VACUUM 能长期稳定运行。重要的是，**不要依赖微博回调去重**，微博可能返回不同的 mid，甚至吞帖不报错。

### 4. 串联成 OpenClaw Skill

最终的 Skill 定义如下（简化版）：

```yaml
skill: weibo_sync
trigger: cron("0 */4 * * *")  # 每4小时一次
steps:
  - source.fetch_posts
  - foreach post:
      - check duplicate via sync_log
      - weibo_upload_image
      - weibo_publish_to_topic
      - rate_limiter_wait
      - insert sync_log
```

当遇到 cookie 过期、限流熔断等异常时，Skill 会通过 OpenClaw 的告警通道通知维护者，并将当前批次剩余任务存档，等待下次触发。

## 可复用建议

- **配置外部化**：超话 topic_id、cookie、限流阈值全部放入环境变量或 OpenClaw 的 `secret` 管理，方便切换账号
- **使用 MCP 分层**：图片上传、状态查询、限流配额均作为独立 MCP 工具，允许其他 Agent（如内容审核、数据看板）复用
- **日志与观测**：每个发帖动作记录结构化日志（耗时、状态码、pid），接入 Grafana Loki 或简单的 `logging` 库，便于定位“发布了但没显示”的幽灵帖
- **降级策略**：如图片上传失败，可先发布纯文本帖，再通过评论补图，虽然体验折损，但保证时效性

## 总结

微博超话自动化同步并非“一发了之”，图片、限流、状态是工程防线的主战场。通过在 OpenClaw 下构建 MCP 工具层和健壮的 Skill，我们在连续运行数月后，同步成功率保持在 96% 以上，绝大部分失败源于 cookie 过期提前刷新不及时，其余均被限流熔断和重试机制消化。这套实践不依赖特定平台 API，对需要维护多个微博账号、多个超话的团队有直接参考价值。

以上所有代码与配置已抽象为可复用的 OpenClaw 插件包，欢迎社区讨论改进。
