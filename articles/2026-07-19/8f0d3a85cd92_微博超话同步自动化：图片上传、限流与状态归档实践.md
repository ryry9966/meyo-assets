## 背景

维护多个微博超话的内容同步，是不少技术博主和垂直领域运营者的日常：新文章发布后，要把摘要、配图同步到对应超话，以提高曝光。手动发布不仅费时，还容易漏发、重复发布。如果能用 Agent 把这件事自动化，就能把精力省下来做更有价值的事。

OpenClaw 这类工具已经可以编排复杂的自动化流程，但对接微博超话这类非公开 API 时，仍然有不少工程细节需要打磨。本文记录一次完整的实践方案，涵盖图片上传、限流应对和发布状态归档，供同样在折腾微博自动化的同学参考。

## 问题拆解

微博超话发布面临三个核心问题：

1. **图片上传与引用**：发布带图帖子需要先上传图片获得 `pid`，再在发帖接口中引用。上传接口有特定的签名规则和格式要求。
2. **接口限流与风控**：频繁请求会触发 429 状态码，甚至导致账号被暂时限制发布。需要设计合理的重试和等待机制。
3. **状态管理**：要确保每条内容只发布一次，失败后能自动重试，同时保留完整的操作日志，便于排障。

## 实现路径

### 1. 认证与登录态维护

微博移动端 API 主要依靠 Cookie 中的 `SUB` 或 `M_WEIBOCN_PARAMS` 等字段保持会话。实践中最稳妥的方式是扫码登录后，将完整的 Cookie 字符串保存为环境变量，供 Agent 在运行时注入请求头。每隔一段时间（如一两天）需要重新扫码，可结合 OpenClaw 的通知能力发送过期提醒。

### 2. 封装为 OpenClaw 可调用的工具

将微博的核心操作封装成两个工具函数，通过 OpenClaw 的 tool 机制暴露给 Agent：

- `weibo_upload_image(image_path)`：上传图片，返回 `pid`。
- `weibo_post_to_super_topic(content, pid, topic_name)`：发布到指定超话。

工具内部处理签名、请求重试和异常翻译，使 Agent 只需关心业务参数。在 OpenClaw 中，这些工具既可以在 Workflow 中按步骤调用，也可以由 LLM 根据计划自动编排。

### 3. 图片上传细节

上传接口使用 `multipart/form-data` 格式，核心字段如下：

```
url: https://picupload.weibo.com/interface/pic_upload.php
params:
  mime: image/jpeg
  data: (binary)
  ... 及其他固定参数
headers:
  Referer: https://m.weibo.cn/
```

需要注意：
- 图片尺寸不能过大，超过 5MB 会失败，建议先统一压缩到 2K 宽度以内。
- 上传必须携带正确的 `Referer` 和 `Origin`，否则接口直接拒绝。
- 返回的 `pid` 是一个字符串，后续发帖时需拼接为 `pic_id=pid` 的形式。

### 4. 发布与超话标识

发帖接口的请求体类似：

```json
{
  "content": "帖子正文 #超话名称#",
  "pic_id": "xxxx",
  "visible": 0,
  "topic_id": "超话ID"
}
```

难点在于 `topic_id` 和超话名称之间的转换。部分超话可以直接在正文中加入 `#名称#` 标签，内部会自动关联；但有些严格的超话需要额外传入 `topic_id` 和 `st`（话题签名）参数。`st` 可通过访问超话主页获取，有数小时的有效期，可以缓存以提升效率。

### 5. 限流与重试设计

微博对发布频率非常敏感，实测连续发布 3～5 条后，很容易触发 429。应对策略：

- **间隔发布**：每条发布之间固定休眠 60–120 秒。
- **智能退避**：捕获 429 异常后，解析响应中的 `Retry-After` 头（如果有），否则按指数退避（如 5min / 10min / 20min）重试，直至成功或达到最大重试次数。
- **错误码翻译**：将微博返回的错误码映射为可读信息，如“操作频繁”、“需要安全验证”，便于 Agent 决定是否继续或通知人工介入。

在 OpenClaw 的 Workflow 中，可以用 `sleep` 节点和循环控制来实现上述逻辑，同时记录每次重试的时间线。

### 6. 状态归档

为了避免重复发布，需要维护一个内容级别的状态存储。最简单的做法是使用 SQLite 数据库，表结构如下：

```sql
CREATE TABLE sync_log (
  id INTEGER PRIMARY KEY,
  content_hash TEXT UNIQUE,    -- 内容唯一标识（如 MD5）
  status TEXT DEFAULT 'pending', -- pending/uploaded/posted/failed
  image_path TEXT,
  pid TEXT,
  post_url TEXT,
  retries INTEGER DEFAULT 0,
  last_error TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME
);
```

每次运行时，查询 `status='pending'` 或 `status='failed'` 且重试次数未超上限的记录，按时间顺序处理。发布成功后更新状态为 `posted`，失败则递增重试次数并记录错误。这种状态机模型让整个流程变得简单可控。

## 踩坑与心得

- **图片上传偶发“try again”**：通常是服务端瞬时过载，直接使用原图重试一次即可，不需要重新编码。
- **超话 st 缓存失效**：如果发布返回“话题不存在”，多半是 st 过期，此时应刷新 st 再重试。可在工具中内置“失败-刷新-重放”逻辑。
- **内容审核导致发布静默失败**：有时微博返回的状态是成功，但帖子被系统删除或仅自己可见。因此发布后最好用另一个微博账号快速检查可见性，或者每隔一段时间做一次抽查。
- **Cookie 过期**：预先检测登录态有效性，若发现接口要求重新登录，立即通过 OpenClaw 的通知渠道通知维护者扫码，避免长时间处于无效运行状态。

## 可复用的建议

1. **将微博操作抽象为独立 Service**：不与 OpenClaw Agent 的业务逻辑强耦合，未来切换到其他自动化平台也只要改 adapter。
2. **所有的操作都记日志**：不仅是成功/失败状态，还包括每步接口的 request-id（如果有）、耗时、重试次数，方便事后分析。
3. **遵守平台规则**：控制发布频率，不冒用他人超话，不大量发布营销向内容。自动化的底线是不要让你的号成为“服务故障”的通知中心。
4. **使用 OpenClaw 的 Workflow 调度**：将“扫描待发内容 → 逐个处理 → 归档”设为一个定时运行的 Workflow，配合简单的 CRC 检查，就能稳定运行很久。

## 总结

微博超话同步没有一行代码的银弹，但通过合理设计状态机、健壮的限流处理以及 OpenClaw 的自动化编排，可以把一个原本需要每天半小时做的重复性工作，压缩到近乎零维护。本文提供的方案已在若干技术超话中实际运行数月，希望这些实战经验能为你省去从头摸索的功夫。
