# 微博超话同步实践：图片上传、限流与状态归档

## 背景
在日常内容分发中，将公众号、博客等渠道的图文同步到微博超话是一个常见需求。手动搬运耗时且容易出错，尤其是在需要高频发布多条内容时。我们希望用自动化流水线解决这个问题，但微博开放平台对超话发帖的支持有限，很多操作只能通过逆向网页接口来实现。

团队内部使用 OpenClaw 作为 Agent 调度中心，配合自定义 MCP Tool 完成各种自动化任务。此次同步机器人也是基于这个框架构建的：OpenClaw 按计划触发任务，调用同步工具，完成图片处理、上传、发帖、状态归档的完整闭环。这里把真正踩过的坑与工程化经验记录下来。

## 问题拆解
看似简单的同步动作，实际包含多个隐含难题：

1. **图片必须本地上传**  
   微博超话不支持直接引用外部图片链接，所有配图都需要先通过上传接口保存到微博图片服务器，获取 `pid` 后再嵌到发帖参数中。图片格式、大小、EXIF 信息都可能触发拦截。

2. **严格的限流与风控**  
   频繁发帖或同质内容会被判定为机器人，导致账号受限或需验证码。不仅要控制请求频率，还要在内容层面做随机变换。

3. **状态不可追溯**  
   如果任务中途失败（网络抖动、cookie 失效等），没有记录会导致重复发帖或漏发，必须设计可重试的状态机。

4. **登录态脆弱**  
   cookie 有效期短，且需要从页面抓取动态 token（如 `st`），一旦失效整个流程中断。

## 工程化实践步骤
整个同步管道分为 5 个阶段，下面逐一说明关键做法。

### 1. 登录态与 CSRF 维护
利用一个独立的“登录保养”定时任务，每隔 30 分钟检测 cookie 是否还能正常访问微博首页。若失效，则走模拟登录流程（账号密码加密在环境变量中）刷新 cookie，并提取发帖必须的 `st` 参数缓存到内存或 Redis。后续所有请求头部统一携带 `Referer` 和 `User-Agent`，模拟移动端行为。

### 2. 图片预处理
从内容源拿到的原图可能是 PNG、WebP 或超尺寸的 JPEG。为通过微博上传校验，统一执行：
- 转换为 JPEG 格式（`PIL.Image.save(..., format='JPEG', quality=85)`）
- 限制最长边不超过 1200px，文件大小压缩到 1MB 以内
- 移除 EXIF 信息，避免隐私暴露和二次处理异常
- 生成一个随机文件名防止冲突

### 3. 图片上传
研究微博 H5 发图接口，最终稳定的流程是：
- 用 `requests` 发送 `multipart/form-data`，字段包含 `st` 和图片二进制
- 注意 `Content-Type` 不要手动指定，让 `requests` 自动生成带 boundary 的头
- 提取返回 JSON 中的 `pid`，失败时根据错误码判断是 cookie 失效、格式错误还是频控

### 4. 超话发帖
拼接文本时，避免完全相同的正文。我们采用模板变量替换，随机插入表情符号、空格或换行，并在文末附加一条 #每日分享# 的固定话题。发帖接口携带 `pid` 数组、文本内容和超话 ID，响应中可获取帖子 URL。

### 5. 限流与抖动控制
- **请求级**：上传图片与发帖之间随机 sleep 2~5 秒；每次任务（一条帖文）后休息 10~30 秒。
- **日级**：根据账号权重设置每日最大发帖量（测试号暂设为 5 条/天），通过计数器或数据库记录当天已发数量，超限自动暂停并告警。
- **内容级**：相同来源的内容如果连续同步，会刻意调换配图顺序、变换摘要句式，降低被算法命中的概率。

### 6. 状态归档
使用 SQLite 维护一张 `sync_task` 表，字段包括：任务 ID、源内容摘要、图片本地路径、上传后 pid、发帖状态（`pending/uploaded/posted/failed`）、重试次数、帖子链接、时间戳。这样任何一步失败都可以从最近的成功状态恢复，且不会重复消耗每日配额。OpenClaw 的任务回调中更新状态，并提供简单的 Web 面板查询同步记录。

## 踩坑清单
- **图片格式“表里不一”**：有些图片扩展名是 `.jpg`，实质却是 WebP，上传后微博返回格式错误。解决：用 `PIL` 强制转码，不信扩展名，只信真实的格式头。
- **CSRF token 过期**：发帖接口偶尔返回 100005（st 无效），即使是刚刚从页面抓取的。增加一步重试：若出现 token 错误，先重新请求页面获取新 `st`，再重试发布，成功率达 99%。
- **Cookie 域限制**：微博 cookie 的 `Domain` 可能是 `.weibo.com` 或 `.weibo.cn`，跨子域使用时需确保带上所有相关字段。用 `requests.Session` 并保持同一会话，减少 cookie 丢失。
- **被标记为商业推广**：含短链接或明显广告词可能被超话主持人屏蔽。解决：不使用 t.cn 短链，链接用文字替代或干脆不放链接，保持原生讨论感。

## 可复用建议
- **封装为 MCP Tool**：把上述功能打包成一个标准的 MCP 工具 `weibo_sync`，输入参数：文本模版、图片列表、超话 ID。OpenClaw 的 Agent 可以直接调用，同时也方便其他项目复用。
- **幂等设计**：以 “源内容标识+超话 ID” 作为唯一键，发帖前先查归档表是否已有成功记录，防止重复发送。
- **监控与降级**：集成简单的健康检查，当日限额耗尽或连续 3 次失败时，通过 Webhook 通知运维，并自动暂停任务直到人工确认。
- **模拟正常用户**：偶尔在执行流程中插入一次“仅浏览不发帖”的动作，爬取几个超话帖子增加账号活跃度，能有效降低风控概率。

## 总结
微博超话同步远非调用一个 API 那么简单，它更像是一个微型的数字生存游戏：处理格式、维护登录、躲避检测、记录状态。工程化的核心是在可靠性和合规性之间找到平衡——既不触碰平台红线，又能稳定完成任务。这次实践最终沉淀为一个可配置的 MCP 工具，结合 OpenClaw 的调度能力，团队其他成员只需填写文案和图片地址即可自动同步。唯一不变的规律是：类似工具必须持续跟随平台风控策略迭代，长期维护不可避免。
