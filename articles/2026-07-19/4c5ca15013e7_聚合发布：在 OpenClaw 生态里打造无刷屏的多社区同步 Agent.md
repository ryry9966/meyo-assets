## 背景：当自动化发布变成“信息轰炸”

在 OpenClaw 以及 MCP 插件生态中，我们会频繁使用 Agent 把开发进度、实验结论、知识条目自动推到多个社区：Discord 频道、Slack 工作区、Telegram 讨论组，甚至通过 Webhook 生成一条 Twitter 线程。最初的想法很简单——写一次，处处可见。但很快就会发现，如果每条 commit、每个 issue 评论、每个片段都实时推送，所有订阅者就会在同一时间收到几乎相同的信息洪流。

这不是设想中的“多平台覆盖”，而是机械刷屏。对于维护开源项目或技术写作的个人来说，这种体验尤其糟糕：读者会因为重复信息而静音频道，你也会因为担心打扰而不敢再推送。真正需要的是一种**有边界**的自动化同步：既能覆盖关键触达点，又不会让任何人感到被骚扰。

能否用 OpenClaw 本身的 Agent 能力，结合简单的消息缓冲与聚合逻辑，来解决这个问题？本文记录了我的一次工程实践——不引入额外 SaaS 服务，只靠一个轻量 MCP 工具和几条规则，把“刷屏式同步”改造成“摘要式发布”。

## 问题拆解：什么导致了刷屏？

多社区同步刷屏的本质不是推送动作本身，而是**时间维度上的密度过高**与**语义维度上的冗余**。典型场景包括：

- GitHub 上的多个连续 commit，被 Webhook 逐条转发到所有频道。
- 同一篇日志的 title、摘要、链接被分别当作独立消息发布。
- 多个 Agent 节点（如不同 MCP 工具）对同一个事件重复响应，各自产生一条内容相近的通知。

直接解决的办法不是降低推送频率那么简单，因为不同社区对时效性的要求不同。我们需要一个**消息聚合层**，它会：

1. 将同一来源在短时间内的多条事件收集起来；
2. 根据语义相似度或事件类型进行合并；
3. 生成一条精心排版、适合该平台格式的摘要；
4. 再按规则（时间窗口、关键词白名单等）决定是否立即推送、延时批量推送，还是等待人工确认。

## 做法：构建基于 Agent 的聚合发布管道

我选择在 OpenClaw 的运行环境中嵌入一个自建 MCP 工具，它提供了消息缓冲、合并和发布接口。整体架构大致如下：

```
[GitHub/其他事件源] --> [MCP工具: message-buffer] --> [聚合 Agent] --> [多平台推送 MCP]
```

### 步骤 1：定义事件接收与缓冲

首先让 OpenClaw 的 Agent 创建一个消息缓冲区。我用一个本地 JSON 文件作为简单持久化存储，每条记录包括：

- `source`: 事件来源（如 `github.push`）
- `timestamp`: 事件发生时间
- `payload`: 原始内容（标题、描述、链接等）
- `group_key`: 用于聚合的键，例如仓库名 + 分支名

当新的 Webhook 到达时，Agent 调用 `message-buffer` 的 `add_event` 工具，把事件写入缓冲区，并立刻返回，不进行任何推送操作。

### 步骤 2：聚合窗口与合并逻辑

我设置了一个 15 分钟的聚合窗口。每 15 分钟，Agent 执行一次 `flush_and_summarize`：

- 扫描缓冲区中所有超过窗口时长的 `group_key`。
- 对于同一 `group_key` 下的多条 `push` 事件，合并 commit 列表，生成一条类似 “`repo/main` 过去 15 分钟合并了 3 个 commit：`fix(auth)`, `feat(api)`, `chore(deps)`” 的消息。
- 对于纯文本类型（如博客发布），检查标题和描述是否高度重复（简单比对 Levenshtein 距离），若相似则只保留最近的一条，并标注“多次更新”。
- 合并完成后，将这些原始事件从缓冲区移除，只留下摘要事件。

这里的聚合逻辑不需要复杂的 NLP，工程上够用即可。关键字白名单也很重要：如果某条事件的标题包含 `#urgent` 或 `#security`，则绕过聚合窗口，立即推送。

### 步骤 3：多平台格式适配与发布

聚合 Agent 生成一条摘要后，再交给一个轻量级的“多渠道渲染器”：

- Discord / Slack：适合 `embed` 格式，将摘要标题、描述、链接分别放入对应的字段。
- Telegram：使用 MarkdownV2，注意转义特殊字符。
- Twitter（X）：自动截断为 280 字符，并附上 link。

这个渲染器通过不同的 MCP 工具完成（例如 `post_discord_webhook`, `post_telegram` 等）。Agent 根据目标社区选择相应的工具。

为避免因为网络问题导致部分平台推送失败而重试产生重复，我在发布前对每条摘要计算一个 `content_hash`，并在本地记录推送状态。即便重跑，也会跳过已推送的消息。

### 步骤 4：人工确认的可选环节

不是所有消息都适合全自动推送，例如月刊式摘要或包含主观判断的开发日志。这时 Agent 会把聚合好的摘要先以草稿形式存入一个“人工审查”通道（比如发送到我的私人 Discord 频道），并附上一个“确认推送”的按钮或指令。我只有回复 `!publish` 后，Agent 才会真正执行多渠道发布。这是避免机械刷屏的最后一道边界。

## 踩坑点与经验

1. **聚合窗口的平衡**  
   15 分钟对我来说刚好，但对频繁迭代的项目可能仍然偏长。如果窗口太大，消息失去时效性；太小则依然刷屏。建议开始时用 10 分钟，观察一段时间后调整。

2. **去重的粒度**  
   仅靠 `group_key` 合并 commit 还不够，有些 PR 讨论会产生多次 `issue_comment` 事件，容易出现“同一个讨论被摘要两次”的问题。需要更细粒度的去重，我最终引入 `(repo, issue_number, event_type)` 组合键，并在合并时只保留最新评论的摘要。

3. **MCP 工具的超时与并发**  
   当缓冲区积累了大量事件时，一次性 `flush_and_summarize` 可能耗时较长，导致工具调用超时。解决方法是分页处理，每次只处理 30 条，并让 Agent 循环调用直到缓冲区为空。

4. **不同平台的格式转换细节**  
   Telegram 的 MarkdownV2 对 `-`, `.` 等字符要求转义，稍不注意就会发出一条格式错乱的消息。可以通过构建一个专门的 `escape_telegram` 函数，并配合单元测试守住底线。

5. **白名单误判**  
   我设置的 `#urgent` 关键词过于简单，导致某条包含“这不是 urgent 但想提醒”的 commit 被立即推送。后来改为匹配 `critical` 或 `security` 时还需要结合提交者身份校验。

## 可复用建议

- **从最小化开始**：先只聚合 GitHub push 事件，验证流程后再扩展到 issue、PR 评论等。
- **提供“暂停”开关**：在 OpenClaw 环境中可用一个全局变量，随时禁用自动推送，改为仅记录日志。这对突发事件（如确定某个发布有误）很有用。
- **保留原始事件日志**：即使聚合后删除了缓冲条目，也应存入归档，便于日后排查。
- **平台差异化不只是格式**：有些社区（如 Discord）允许更长的内容，而 Twitter 需要极度精炼。可以配置不同渠道的摘要长度限制。
- **加入“最近一条”去重**：在每次推送前，查询该平台最近一条消息内容，如果与即将推送的内容哈希值相同，则跳过。这是防止因重试而产生重复的最后防线。

## 总结

自动化多社区同步的边界不在于技术能否实现毫秒级分发，而在于**对信息密度的敬畏**。通过一个简单的消息缓冲、聚合窗口加上人工确认，就可以把原本惹人厌的刷屏行为，转变为一次令人舒适的摘要投递。在 OpenClaw + MCP 的框架下，这套机制完全可以做成一个可配置的 Agent 插件，让更多社区成员复用。

当你的同步管道不再被静音、不再被抱怨“又发重复消息”时，才是真正守住了自动化的边界。
