## 背景

部署 OpenClaw Gateway 作为 Agent/MCP 插件的统一入口后，健康检查几乎是每套编排的首要信号源。但在生产环境中，经常会面临一个尴尬的状况：监控面板显示 Gateway 频繁重启或不可用，打开日志却发现满屏都是 `/health` 请求，真正导致失败的报错被淹没在数百兆的重复日志里，排障效率极低。

团队在一次凌晨故障中吃了大亏——`/health` 返回 503，但网关本身进程并未退出，只是依赖的配置中心有一次短暂的 GC 停顿。因为没有对健康检查日志做任何区分处理，当时排查所花的 20 分钟基本都浪费在 grep 过滤上。事后复盘，决定把健康检查日志彻底从普通请求日志中拆分出来，并建立一套可复用的排查步骤。

## 问题定义

核心问题可以拆成两层：

1. **日志噪音**：存活探针（liveness）和就绪探针（readiness）每隔数秒就被 K8s 或负载均衡器调用一次，如果在访问日志中不做区分，高频写入会淹没真实的业务错误与依赖超时。
2. **信号丢失**：当健康检查失败时，默认的错误日志往往只记录 HTTP 状态码，缺少失败的根因上下文——是数据库连接池耗尽？是 MCP 服务器心跳超时？还是插件自身 panic 被 recover 后返回了 500？

如果不解决这两点，健康检查日志不但不能帮助定位问题，反而成为干扰项。

## 做法与步骤

### 1. 区分存活探针与就绪探针

OpenClaw Gateway 默认暴露两个端点：`/health/live` 和 `/health/ready`。前者只检查进程是否存活，不触碰任何外部依赖；后者会级联检查数据库、消息队列、注册的 MCP Server 连通性等。排查时需要第一时间弄清楚是哪个探针失败，因为存活探针失败通常意味着进程即将重启，就绪探针失败则往往指向某个下游组件。

### 2. 将健康检查日志分流

最直接的做法是在 Gateway 的日志中间件中增加路径过滤，将 `/health*` 的请求单独输出到 `health-check.log`。如果使用的是 OpenClaw 内置的日志配置，可以在 `log.yaml` 中通过 `exclude_paths` 将其从主访问日志中移除，同时创建一个独立的 `health_logger`：

```yaml
logging:
  access:
    exclude_paths:
      - /health/live
      - /health/ready
  health_logger:
    level: debug
    file: /var/log/openclaw/health.log
    rotation: daily
```

完成后，主日志会干净很多，而健康检查的详细记录则被单独归档。

### 3. 让健康检查输出结构化信息

仅仅分流还不够，必须让每一条健康检查日志具备排查价值。在 OpenClaw 的探针逻辑中，可以定制返回体，并将依赖检查的耗时、错误原因注入到日志上下文中。例如使用 JSON 结构化日志：

```json
{
  "timestamp": "2025-04-15T10:23:01.423Z",
  "probe": "readiness",
  "status": 503,
  "duration_ms": 3012,
  "checks": {
    "database": "timeout",
    "cache": "ok",
    "mcp_server_a": "unreachable"
  }
}
```

有了这样的日志，排障时只需 `jq 'select(.checks.database=="timeout")'` 就能快速定位到阻塞点，而不必再去翻网络层或连接池的日志。

### 4. 设置告警阈值时屏蔽瞬断

健康检查日志常见的一个坑是：下游组件的瞬断（比如 Redis 短暂地拒绝连接）会被就绪探针捕获并记入日志，进而触发告警。但这类抖动通常在几十秒内自愈，过多报警反而会降低值班人员的敏感度。建议在监控侧对连续 3 次或持续 1 分钟以上的就绪探针失败再触发告警，并在日志采集时打上 `transient_failure: true` 标签，方便后期聚合统计。

## 踩坑记录

- **日志轮转失效**：我们在初期将健康检查日志与主日志共用同一个 rolling policy，结果因为写入量突然变大，`max_size` 迅速被撑满，导致历史日志被误删。后续为健康检查日志单独配置了更大的保留天数，避免排障时找不到历史记录。
- **debug 级别泄露敏感信息**：为了抓到连接池的详细信息，一度把健康检查日志设为 `debug`，结果将部分 API 密钥变量名打印了出来。务必在上线前对敏感字段做脱敏，哪怕是在健康检查日志里。
- **健康检查本身成为瓶颈**：如果就绪探针每次都做全量依赖检查，探针延迟会随着依赖数量线性增长，极端情况下甚至超过 K8s 的超时阈值，导致 Pod 被误杀。可以把开销大的检查改为异步结果读取，探针只检查最近一次健康状态缓存，这样既保证了准确性，又降低了延迟。

## 可复用建议

1. **统一日志 schema**：无论健康检查还是业务请求，所有日志都使用同一套字段规范（至少包含 trace_id、probe_type、dependency_status），方便后续在 Grafana 或 Loki 中做关联查询。
2. **日志与探针行为解耦**：不要为了让日志好看而修改探针逻辑，也不要为了减少日志量而降低探针频率。两者分开管理，互不干扰。
3. **保留“失败前的成功”**：健康检查失败时，集群调度器可能会立刻重启 Pod，导致容器日志丢失。建议通过 sidecar 或集中采集器（如 Vector/Fluentd）将最后几分钟的 `health.log` 推送到远端，这样即便容器被销毁，也能拿到失败现场。
4. **定期演练**：每季度挑一个低峰时段，人为注入一次就绪探针失败（例如关闭 Redis 白名单），观察日志分流、告警延迟、恢复流程是否按预期运作。

## 总结

OpenClaw Gateway 的健康检查日志并不需要被当作洪水猛兽。只要做好分层分流、结构化记录和告警阈值优化，它就能从单纯的运维噪音转变为确定系统健康象限的关键信号。在实际落地时，优先完成“日志分流 + 结构化输出”这两步，就已经能解决 80% 的排障痛点，后续再逐步引入远端备份和演练，形成完整的可观测性闭环。
