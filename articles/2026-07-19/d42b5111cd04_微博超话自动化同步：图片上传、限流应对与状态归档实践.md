## 背景

在日常运营中，我们经常需要将内容同步到微博超话，尤其是配合 AIGC 管线批量产出图文时。“每次手动发帖”很快会变成瓶颈。用 OpenClaw 这类编排工具构建一条自动化流水线，可以显著降低重复劳动。

但在实际落地时，微博开放平台的接口远非“调通即用”。图片上传的报文构造、接口限流策略、发布状态的可追溯性，都是工程上无法回避的问题。本文记录了一次基于 OpenClaw 的微博超话同步实践，重点解决上述三个痛点。

## 问题分析

一个完整的超话发帖流程大致是：

1. 准备图文素材（文本 + 图片）；
2. 逐个上传图片，获取 `pid`；
3. 调用发帖接口，填入文本、超话 ID（`fid`）和 `pid` 列表；
4. 记录发布结果，避免重复或遗漏。

表面看似简单，但三个问题会让脚本变得脆弱：

- **图片上传** – 微博要求 `multipart/form-data` 格式，且 `pic` 字段必须是文件的二进制流。很多 HTTP 客户端库的默认编码会破坏文件指纹，导致上传失败。
- **接口限流** – 类似 `10022`（IP 限制）、`10023`（用户调用次数超限）等错误码频繁出现，无脑重试只会加剧封禁。微博普通授权应用每小时发帖量通常只有 150 次，图片上传也有独立频控。
- **状态缺失** – 没有归档机制，一旦网络抖动或进程重启，很容易重复发布相同内容，或漏发后无从追溯。

## 实践步骤

以下实践以 OpenClaw 为调度平台，结合自实现的 WeiboClient 模块完成。整体流水线如下：

```
素材就绪 → 图片预处理 → 上传图片(含重试) → 组装参数 → 发帖 → 写入状态库
```

### 1. 图片预处理

微博单张图片限制 ≤5MB，建议统一转为 JPEG、压缩至 3MB 以内。可以借助 `sharp` 或本地 CLI 工具，在 OpenClaw 的 `bash` 或 `node` 步骤中完成。GIF 需特殊处理，否则可能被转成静图。

### 2. 封装 WeiboClient

用一个轻量类封装以下逻辑：

- **令牌管理**：自动使用 `refresh_token` 续期，并缓存到环境变量或临时文件。
- **上传图片**：构造正确的 `multipart/form-data`，注意 `Content-Type` 不要手动拼接 `boundary`，交给库自带的方法。关键代码示意（Node.js 环境）：

```js
const form = new FormData();
form.append('access_token', token);
form.append('pic', fs.createReadStream(imgPath), { filename: 'img.jpg' });

const res = await axios.post('https://upload.api.weibo.com/2/statuses/upload.json', form, {
  headers: form.getHeaders(),
  timeout: 30000,
});
```

如果返回 `error_code`，根据类型决定是立即失败还是进入重试队列。

- **超话 fid 缓存**：`/2/search/topics.json?q=超话名称` 可以取到 `topicid`，即 `fid`。建议本地建一个 KV 映射，避免每次请求。

### 3. 限流控制与重试

最直接的方案是引入一个“限速队列”。每秒钟最多发起 1 次请求，上传图片和发帖共用一个桶。当遇到 429 或以下官方错误码时，执行指数退避：

- `10022`：IP 请求超限。等待 5 分钟后重试，必要时切换出口 IP。
- `10023`：用户请求超限。延长间隔到 30 秒后再试。
- `10024`：用户请求接口超限。同上。

在 OpenClaw 中，可以用 `delay` 节点配合循环逻辑实现，或者直接将重试逻辑写入脚本，对外只暴露一个 `publishToChaohua(content, images)` 函数。

### 4. 状态归档

为什么需要归档？仅仅依赖接口返回的 `id` 并不够——如果发帖成功但写入数据库前崩溃，这条记录就丢了，重启后会再次发起。所以应遵守“先查后发”原则：

- 对每条待发布内容计算哈希（文本+图片列表的联合摘要）。
- 查询本地 SQLite 或 Redis 中是否已存在该哈希及对应的 `post_id`。
- 若已存在且 `post_id` 有效，直接跳过。
- 否则执行发布，成功后立即写入 `{ hash, post_id, create_time }`。

这样即使中间状态丢失，只要素材不变，就不会重复。

## 踩坑记录

- **图片数量幻觉**：超话发帖接口 `statuses/update` 最多带 9 张图片，但若 `visible` 参数填错或超话本身有特殊限制，可能只有第一张显示。测试时建议用非公开超话。
- **fid 并非数字 ID**：部分超话的 `topicid` 是类似 `100808xxxxxxxx` 的长串，并不是简便的数字，必须从搜索接口获取。
- **上传接口的 Content-Type 陷阱**：如果手动设置 `Content-Type: multipart/form-data` 而没有 `boundary`，服务端会报 `pic URL error` 或直接拒绝。一定让库生成，例如 `axios` 的 `form.getHeaders()`。
- **进程重启导致重复**：即使采用了哈希去重，如果哈希计算依赖动态时间戳，则会失效。因此必须使用内容本身的稳定指纹。
- **接口文档过时**：部分官方文档给出的域名（如 `upload.api.weibo.com`）和参数说明需要实测验证，某些情况下需要升级为 `api.weibo.com` 的路径。

## 可复用建议

- **将 WeiboClient 做成独立模块**，在 OpenClaw 中通过 `javascript` 或 `python` 脚本步骤调用。模块对外提供 `uploadImages(paths)` 和 `postToTopic(text, pids, fid)` 两个原子动作。
- **用 SQLite 维护状态库**，结构简单：`content_hash TEXT PRIMARY KEY, post_id TEXT, created_at INTEGER`。可以放在项目目录下，与流水线一起维护。
- **引入哨兵值**：如果某次发布因权限或素材问题永久失败（比如图片违规），记得在状态库中标记 `blocked`，避免重复尝试导致账号受限。
- **监控与日志**：归档过程同时输出 JSON 格式的运行日志，方便后续排查。

## 总结

把微博超话同步纳入自动化流水线，难点从来不是“跑通一次”，而是让它在限流、异常、重启等真实环境下稳定工作。图片上传的报文细节、频控下的退避策略、基于内容指纹的状态归档，这三者缺一不可。

OpenClaw 给这些可编程的可靠性逻辑提供了很好的承载空间——你不需要再去写一个完整的后端服务，只需把上述模块化逻辑嵌入工作流。希望这次实践能帮你在构建自己的微博自动化方案时，少踩一些坑。
