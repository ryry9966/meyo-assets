## 背景

用 OpenClaw 或类似的 Agent 流程自动生成内容并发布，已经能省下大量重复劳动。但很快你会发现一个痛点：发布完就完了，所有文章、图片散落在任务日志和临时目录里，想回溯某次生成的原文、复用配图，或者做一次内容审计，几乎不可能。自动化发布如果没有配套的归档机制，基本等于在流沙上盖楼。

本方案面向已经跑通“Agent 生成→发布”流水线的同学，介绍一种轻量的本地归档方式：统一输出 Markdown 正文、下载图片到本地，并用一个 `assets.json` 文件管理所有资源关系，方便检索、迁移和二次加工。

## 问题拆解

一个典型的自动发帖流水线大致是：Agent 接收主题 → 调用图文生成能力（可能是多步 MCP 工具） → 组装内容 → 推送到平台 API。在这中间，真正需要归档的对象有三类：

1. **最终文章正文**（已排版、已处理好的 Markdown）
2. **文章引用的图片**（可能是生成的、也可能是抓取的）
3. **资源映射与元数据**（哪篇文章用了哪些图、生成时间、发布状态）

很多同学的做法是只保留一份最终的 Markdown，图床链接直接嵌在文中。这种方式有两个致命问题：

- 图床随时可能失效，或清理策略不透明，导致历史文章变成“缺图文档”
- 缺少资产清单，无法快速知道本地有哪些图片归属于哪篇文章，排重和复用困难

因此，归档方案需要同时解决**内容固化**和**资产可索引**两个问题。

## 本地归档设计

### 1. 约定目录结构

一个工程化的目录长这样：

```
posts_archive/
├── 2025/
│   └── 04/
│       ├── uid-abc123.md
│       ├── uid-abc123/
│       │   ├── img_001.png
│       │   └── img_002.jpg
│       └── assets.json        # 该月资产清单
└── assets.json                # 全局索引（可选，定期生成）
```

要点：

- 按年月分桶，避免单目录文件数过多。
- 每篇文章使用唯一 `uid`（比如短 UUID 或时间戳+随机数）命名，正文、图片目录均以该 uid 为前缀。
- 图片不放进文章目录会导致引用路径复杂，不利于整体打包移动；放进专属子目录，相对路径只需 `./uid-abc123/img_001.png`，纯 Markdown 也能正确预览。

### 2. 生成 Markdown 并落地

在 Agent 生成内容的最后一步，不要再直接把内容扔给发布工具。改为：

1. 从 Agent 输出中取出 Markdown 文本和所有图片的临时 URL（通常是 base64 或临时对象存储地址）。
2. 为本文生成一个 uid。
3. 创建 `posts_archive/{yyyy}/{mm}/{uid}/` 目录。
4. 逐一将图片 URL 下载到该目录，文件名建议使用 `img_{idx}.{ext}`，并记录映射。
5. 将 Markdown 中的图片引用替换为本地相对路径，写入 `{uid}.md`。

这一过程可以封装成一个 MCP 工具或一个命令行脚本，让 Agent 在“发帖前”调用。对接方式可以是：

```python
# 伪代码：Agent 动作
save_article_locally(
    uid="abc123",
    markdown_content=raw_md,
    image_urls=[...],
    base_path="posts_archive/2025/04"
)
```

工具内部做完下载、路径替换后，返回新的 Markdown 正文，再交给发布模块。这样发布和归档同时完成，不会增加额外的步骤。

### 3. 维护 assets.json

每处理完一篇文章，就在当月目录下的 `assets.json` 中追加一条记录。格式建议：

```json
{
  "uid": "abc123",
  "created": "2025-04-09T10:30:00Z",
  "title": "从文章中提取的标题或主题",
  "markdown_file": "uid-abc123.md",
  "images": [
    "uid-abc123/img_001.png",
    "uid-abc123/img_002.jpg"
  ],
  "tags": ["mcp", "archive"],
  "published": true
}
```

如果文章是自动发布的，还可以加上 `published_url`、`publish_time` 等字段。`assets.json` 用追加写入的方式维护，避免全量重写大文件引发并发问题（如果你有多文章并行归档的场景）。每个月结束时可以用一次全量扫描校验完整性。

## 真实踩坑点

**图片下载失败导致归档不完整**

经常会遇到图床临时抽风或 URL 过期。下载时必须实现重试与超时机制，并记录失败状态到 `assets.json`（增加字段 `download_error`）。不能因为一张图下载失败就丢弃整篇文章的归档。我的做法是下载失败时保留原始 URL 的注释在 Markdown 中，并设置一个告警，后续人工补图。

**文件名冲突与图片去重**

同一个流水线可能多次生成相同或相似的图片，如果直接用图片 URL 的哈希命名看似能去重，但会导致多篇文章引用同一文件，一旦某个文章被删除或移动，容易破坏其他文章的引用完整性。建议**不做跨文章去重**，每篇文章独立保存图片，即使浪费一点磁盘，换来的是隔离性和可迁移性。

**assets.json 与目录不一致**

手动移动文件或删除文章后，`assets.json` 很容易变成过期数据。推荐提供一个校验脚本：遍历当月目录下的所有 uid 子文件夹，与 `assets.json` 对比，报告缺失和多余项，用于日常巡检。这类脚本可以定期用 cron 或 Agent 定时任务执行。

## 可复用建议

- **用 uid 作为唯一纽带**，不要在 `assets.json` 中使用标题作为主键，标题会变。
- **将归档工具做成 MCP 服务**，这样任何 Agent、插件都可以通过标准协议调用，而不用每个流水线都写一段落地逻辑。
- **离线索引**：如果文章量很大，可以定期将所有月的 `assets.json` 合并为一个 SQLite 数据库，提供全文检索和图片使用频次统计，这对后续批量更新图片或审计特别有用。
- **图片格式与压缩**：在下载图片时，如果需要长期归档，可以统一转为无损 PNG 或压缩 WebP，并限制最大尺寸，避免某天发现归档目录膨胀了上百 GB。

## 总结

自动发帖流水线加上本地归档并不是一个高深需求，但它能大幅降低后期维护成本，尤其是当内容积累到几十上百篇后，有清单和没清单的工作效率差一个数量级。核心思路就三点：目录结构化、图文落地本地、用机器可读的 `assets.json` 维护资产关系。

这种模式本身也很适合和其他自动化流程联动，比如定期检查归档完整性、为历史文章自动批量替换失效图片、或从归档中重新生成不同平台的适配版本。把沉淀做好，后面的想象力才展得开。
