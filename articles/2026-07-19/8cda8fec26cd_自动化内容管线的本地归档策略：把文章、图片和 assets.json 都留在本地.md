## 背景

用 OpenClaw 搭建一条自动发帖流水线已经不算难事：让 Agent 根据知识库生成 Markdown 文章，调用 MCP 工具拉取/生成配图，最后通过接口发布到CMS或社交媒体。但很多人会把归档这一步完全交给平台，本地的中间产物杂乱堆放，时间一长，想重建某篇文章的上下文、迁移到另一个发布渠道，或是排查历史内容时，就变得非常痛苦。

常见的后果：

- Markdown 文件散落在项目不同目录，命名无规律。
- 图片引用都是远程 URL，存储服务迁移后链接全部失效。
- 每篇文章的元数据（标题、标签、用到的图片清单、生成参数等）要么丢在日志里，要么根本不存在。

我在自己的 OpenClaw 站群管线里引入了一个轻量的本地归档层，发布之后把所有相关资源按规范落地到本地，用版本控制管起来。这篇就是这套做法的工程化记录。

## 问题定义

我们需要一个可复用的归档动作：在自动发帖流水线成功发布文章后，将以下三类内容可靠地保存到本地目录：

1. **文章 Markdown**——最终发布的版本，图片引用已替换为相对路径。
2. **所有图片文件**——从远程下载到本地，保证离线可看。
3. **assets.json**——记录文章元数据、图片映射关系、来源流水线等信息，方便后续自动化消费。

整个流程必须是幂等、可重入的，不能因为某张图片下载失败就让整个归档崩掉。

## 目录结构设计

采用以日期与 slug 为键的结构，兼容人工查看和脚本遍历：

```
archive/
  2025-03-21-thinking-in-mcp/
    article.md
    images/
      a1b2c3d4.png
      e5f6g7h8.jpg
    assets.json
```

`assets.json` 的约定 schema（简化版）：

```json
{
  "slug": "thinking-in-mcp",
  "title": "与 MCP 协作的思考",
  "created_at": "2025-03-21T10:30:00Z",
  "pipeline": "openclaw-blog-gen",
  "original_md_hash": "sha256:...",
  "images": {
    "https://cdn.example.com/img/abc.png": "images/a1b2c3d4.png",
    "https://cdn.example.com/img/def.jpg": "images/e5f6g7h8.jpg"
  }
}
```

图片文件名使用远程 URL 的 SHA-256 前 8 位，避免重名；映射关系在 `images` 字段守着一一对应，方便反查。

## 核心实现步骤

### 1. 准备输入

流水线在发布阶段会产出一个上下文对象，例如在 OpenClaw 里通过一个 MCP 工具返回：

```python
{
  "markdown": "## 标题\n![](https://cdn...)\n",
  "meta": {"slug": "thinking-in-mcp", "title": "..."},
  "image_urls": ["https://cdn.example.com/img/abc.png", "https://..."]
}
```

如果 pipeline 本来就有 `assets.json`，直接把原始 JSON 传入；没有则从上下文构造。

### 2. 创建归档目录并写入文章

使用 `pathlib` 建立上述目录，将原始 Markdown 先写入临时位置，等图片处理完毕再覆盖。

### 3. 下载图片并更新引用

遍历 `image_urls`，对每个 URL：

- 基于 URL 生成确定性文件名（如 `hashlib.sha256(url.encode()).hexdigest()[:8] + ext`）。
- 下载图片到 `images/`，设置合适的超时与重试（比如 3 次，间隔指数退避）。
- 若下载失败，写入一个本地的占位图并记录 warning，不让流程中断。
- 在 Markdown 内容中将该 URL 替换为相对路径 `images/filename`。

边下载边构建 `images` 映射表，同时校验下载文件的魔数，防止保存到非图片内容。

### 4. 生成或改写 assets.json

将原始元数据与图片映射合并，写入最终 `assets.json`，附带 `original_md_hash` 和当前时间戳。如果之前存在同名归档目录，可以通过比较哈希决定是否覆盖，避免重复处理。

### 5. 嵌入到 OpenClaw 管线

可以把以上步骤封装成一个 `archive_post` 函数，通过以下方式触发：

- 自定义 MCP Server 暴露 `archive` 工具，在 Agent 发布成功后由 ReAct 流程自行调用。
- 或者在发布流程的 `finally` 代码块中直接调用本地库，保证即使发布部分失败也会尝试归档已有内容。

我推荐后者，少一次 MCP 往返，更可靠。

## 踩坑点

- **图片重名覆盖**：如果用原始文件名容易碰撞，必须用内容哈希或 URL 哈希。这里选 URL 哈希是为了与 assets.json 映射可逆。注意不能直接用完整 URL 做文件名（含特殊符号），哈希是最稳。
- **相对路径引用标准**：Markdown 里统一用 `images/xxx`，不要加 `./`，避免不同渲染器差异。发布时如果需要绝对路径，可以由发布侧再做一次替换，归档层只管保真。
- **大图与下载超时**：有些图片源在国内/外网络不稳定，设置 connect timeout = 5s, read timeout = 15s，失败后换占位图并继续，千万别阻塞整体归档。
- **assets.json 版本控制**：如果直接用 Git 管理 archive，注意图片文件可能会让仓库快速膨胀。建议图片单独用 Git LFS 或定期归档到对象存储，这里只讨论本地结构持久化。
- **与流水线的状态同步**：如果发布是异步的，归档时可能文章尚未最终渲染。务必在确认“发布成功”的回调里做归档，或者 Agent 拿到最终 markdown 后再调用归档工具。

## 可复用建议

- **配置化**：把归档根目录、占位图路径、下载超时等抽成 YAML/环境变量，方便在不同 OpenClaw 工作区之间复用。
- **函数式接口**：核心函数签名像 `archive(md: str, meta: dict, image_urls: list[str], base_dir: Path) -> Path`，没有副作用，单元测试好写。
- **增量处理**：先算 `assets.json` 的哈希，与已有归档比较，一致就跳过，节省下载和时间。这在大批量迁移历史内容时很实用。
- **日志**：下载成功/失败、图片替换数量、归档路径都输出结构化日志，方便后期排障。可以借助 Python 的 `logging` 模块配 JSON 格式输出。

## 总结

在自动发帖管线里加一个本地归档层，本质是在帮自己保留“内容主权”。文章、图片、元数据三位一体落盘后，未来无论是迁移发布平台、用静态站点生成器重建博客，还是用脚本做批量内容审计，都有一份确定的数据源。

在 OpenClaw 生态里，这套思路完全可以进一步封装成可插拔的 MCP Service 或插件，让任何 Agent 驱动的发布流程都带上一键归档能力。目前的实现已经能让我的多条发布管线安心跑下去，遇到任何问题都可以回溯到某一天的本地文件状态，调试成本直线下降。

保管好自己的内容资产，这是自动化内容工程里不该跳过的步骤。
