## 背景：为什么你还困在坏掉的 JSON 里？

在 OpenClaw 这类 Agent/MCP 串联的自动化实践中，我们常会要求 LLM 输出一份长文，同时又要让下游程序拆分处理。最常见的选择是 JSON —— 看起来标准、可解析、边界清晰。

但实际跑起来，尤其是输出内容超过千字、包含多段引用、代码块或自然语言说明时，坏掉的 JSON 几乎成了系统崩溃的第一诱因。缺少引号、字符串内未转义、行末多了个逗号、括号层级错乱……这些问题在模型输出里高频出现，而一旦发生，严苛的 `json.loads()` 就会直接抛异常，整个 Agent 管道卡死。

很多人选择给解析器各种 `try-except`、正则修补、llm 重试，但工程实践中会发现：**用 JSON 承载长篇自然语言内容，本质上在用数据交换格式去干内容描述格式的活，迟早会踩坑。**

## 从 JSON 转向标签格式的思路

一个更务实的方向是：放弃纯 JSON，改用**自定义 XML-like 标签**来描述结构化区块。比如原本需要输出：

```json
{
  "summary": "...",
  "steps": "...",
  "notes": "..."
}
```

现在直接要求模型输出：

```xml
<SUMMARY>
这里是摘要，可以有多行、任意符号，不再需要转义双引号。
</SUMMARY>
<STEPS>
1. 第一步...
2. 第二步中的 "引号" 和换行都很安全。
</STEPS>
<NOTES>
补充说明……
</NOTES>
```

解析端不再依赖完整的 JSON 语法树，只需用正则或简单的流式状态机提取标签后的内容，容错能力大幅提升。对于 Agent 链路中需要将大段文字作为下游函数参数、或者积累多轮对话后再做切分的场景，这个方案尤其适用。

## 具体实现步骤

### 1. 设计标签规范

标签名用大写英文，前后一致，不要嵌套。单次输出标签数量控制在 5 个以内，避免模型搞混。如果需要列表，可以直接让列表项放在同一个 `<STEPS>` 标签内，每行一条，下游再按行拆分。切记：**标签就是内容容器，别指望它承担逻辑嵌套。**

### 2. 编写提示词

提示词中明确给出输出格式，最好带上一个 few-shot 示例。示例要展示标签是如何包裹长文本的，并强调“不要添加任何额外 JSON 或解释”。例如：

```
请严格按照以下标签格式输出，标签之外不要输出任何内容：
<SUMMARY>
（摘要内容）
</SUMMARY>
<STEPS>
步骤1...
步骤2...
</STEPS>
<NOTES>
注意事项...
</NOTES>
```

如果你用的是 OpenClaw 的 `prompt_template`，可以把格式示例做成 `example` 部分，并用大括号占位变量。

### 3. 编写健壮的提取器

不要用正则硬匹配整个文档，而是逐个标签从流式 chunk 中提取。一个最简提取器如下：

```python
import re
from typing import Dict, Optional

def extract_tag_content(text: str, tag: str) -> Optional[str]:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1).strip() if match else None
```

如果标签缺失，可以返回 `None` 触发重试；如果部分缺失（只有开始标签），可以利用积累的 buffer 再等待下一段流式内容。

### 4. 与 Agent 框架集成

在 OpenClaw 的 MCP 工具调用前后，可以用一个简单的 “结构化解析节点” 把标签内容转换成字典，再传递给下游的 hard-coded 参数。不需要引入重量级 XML 解析库，因为内容本身就是我们与模型约定的“半结构化”格式，强解析反而脆弱。

## 实际踩过的坑

- **标签重名与误匹配**：如果内容中也出现了 `<SUMMARY>` 字样，就会干扰提取。解决方法是使用非对称分隔符，例如 `[SUMMARY_START]...[SUMMARY_END]`，或者使用前后不一致的标记比如 `<<SUMMARY>>`。实践中发现 `[SUMMARY]` 和 `[/SUMMARY]` 对模型更友好，不易误生成。
- **流式输出时标签未闭合**：这是最大的痛点。LLM 在生成过程中可能在某次 chunk 结束时只有 `<STEPS>` 而没有闭合标签。提取器必须维护一个缓冲区，只在检测到完整标签对时才上交内容，否则等待后续 chunk。
- **模型输出额外的说明**：有时候模型会在标签前后加上 “好的，这是你要的格式：” 之类的客气话。可以在 prompt 中加一句 “直接输出标签，不要加任何前缀和后缀”，同时在提取器侧先清洗掉非标签段的文本。
- **标签大小写不一致**：有人用了 `<summary>` 而定义的是 `<SUMMARY>`。最好在提取时把标签统一转成大写。但更可靠的是 prompt 中坚持一种格式并多次强调。

## 可复用的工程建议

- **少嵌套、多顺序**：如果数据本身有层级，宁愿按顺序输出多个平行标签，再在代码里组装，不要挑战模型的多层嵌套能力。
- **必备重试与校验**：提取完所有标签后，校验是否存在必要标签，如果不完整则重新请求模型。注意设置最大重试次数，防止死循环。
- **混合 JSON 与标签**：当部分字段确实是数字、布尔值等简单类型时，不妨用标签包裹一个 mini JSON，比如 `<META>{"count":5,"status":"ok"}</META>`，这样这部分依然可由 `json.loads()` 稳定解析，而长文本部分用标签承载。
- **在 OpenClaw 中做默认模板**：如果团队频繁用到这种结构，可以抽象成 `structured_tag_prompt` 工具函数，注入自定义标签名和示例，减少重复工作。
- **监控坏格式占比**：实战中记录标签格式违反率（缺失标签、多输出等），持续优化提示词。一旦低于 1%，基本可满足生产需求。

## 总结

JSON 是宝贵的通用数据格式，但把它强加于 LLM 长文结构化输出往往会将自己困在转义地狱和脆弱的解析器上。采用自定义标签，本质上是在与模型建立一个更宽松、更接近自然语言输写的契约：“你只需要按约定把内容包起来，剩下的我来处理。” 在 OpenClaw 这类重视可靠性和可维护性的 Agent 工程中，这种似乎“不标准”的设计反而是更成熟的选择。

当你的下一个自动化流水线被坏 JSON 阻断时，不妨试试放下 `json.loads()`，拿起 `<SUMMARY>`。
