## 背景

自动化 Agent 的本地操作已越来越常见——无论是通过 OpenClaw 的任务编排，还是基于 MCP 的工具调用，Agent 都可能直接读写、删除你的文件。如果放任脚本拥有整个用户目录甚至根目录的访问权限，一次提示词错误或模型幻觉就可能导致项目源码被误删、环境配置被覆写、私密文件被读取。在工程实践中，“最小权限”永远不是空话。给 Agent 戴上本地文件访问的缰绳，最直接且低成本的手段，就是实现一个**基于目录白名单的访问护栏**。

## 问题：为什么需要白名单而不是事后修补

- **扩散风险**：比如 Agent 被要求“清理所有日志”，如果工作目录设置不当，它可能递归到上层目录。
- **隐私泄露**：若 MCP 插件允许读取文件，通过路径遍历 `../../.ssh/id_rsa` 即可窃取密钥。
- **调试安全**：测试阶段的脚本往往没有权限意识，白名单可以在开发期就拦截越界操作。

目标很明确：**只允许 Agent 访问若干指定的目录，任何落在白名单外的路径操作都必须拒绝。**

## 实现步骤

### 1. 定义白名单与路径规范化

用 Python 的标准库即可构建一个轻量级护栏。核心思路是：
- 配置一组允许的绝对路径根目录，例如 `["/home/user/project", "/tmp/agent_workspace"]`。
- 所有传入的文件路径，先转为绝对路径并通过 `os.path.realpath()` 消除符号链接与相对路径。
- 检查规范化后的路径是否以任一白名单目录为前缀。

示例实现：

```python
import os
from pathlib import Path
from typing import List, Union

class FileAccessGuard:
    def __init__(self, allowed_roots: List[Union[str, Path]]):
        # 统一转为 Path 对象并解析为绝对、无符号链接的真实路径
        self._roots = [Path(root).resolve() for root in allowed_roots]

    def _canonical(self, path: Union[str, Path]) -> Path:
        # resolve() 已完成 realpath 和绝对路径转换
        return Path(path).resolve()

    def is_allowed(self, path: Union[str, Path]) -> bool:
        target = self._canonical(path)
        # 必须与至少一个白名单根目录匹配（包含自身或子路径）
        return any(
            target == root or root in target.parents
            for root in self._roots
        )

    def assert_allowed(self, path: Union[str, Path]):
        if not self.is_allowed(path):
            raise PermissionError(f"Access to {path} is blocked by guard")
```

### 2. 在 Agent 工具调用中集成

以 OpenClaw 的自定义工具为例，将文件操作封装一层检查：

```python
from openclaw.tools import tool

guard = FileAccessGuard(["/app/workspace", "/var/log/app"])

@tool
def read_file(filepath: str) -> str:
    guard.assert_allowed(filepath)
    return Path(filepath).read_text(encoding='utf-8')
```

所有读写、删除、重命名等函数都应在入口处调用 `assert_allowed`。对于 MCP 服务器，可以在资源或工具的 handler 首行插入检查逻辑，实现“一处配置，全局生效”。

### 3. 强化：拒绝符号链接穿透

即使路径看起来在白名单内，恶意符号链接仍可能指点到外界。`resolve()` 会将符号链接完全展开，所以对比的是**最终真实路径**，这从根上阻断了此类攻击。如果业务需要支持符号链接保持语义，可改用 `absolute()` 并额外检查每一段路径组件，但工程上更推荐直接拒绝或使用 `resolve()`。

## 踩坑清单

- **Windows 盘符与大小写陷阱**：`C:\Users` 与 `c:\users` 在 Windows 下是同一路径，但字符串比较可能失败。应使用 `os.path.normcase()` 统一转小写后再比较，或者在 `resolve()` 后使用 `Path` 的 `samefile()`（仅限已存在路径，不适用于还不存在的文件）。
- **相对路径工作目录谬误**：调用脚本时当前工作目录可能不是你想的那样。永远将相对路径与预设的基础路径（如 workspace 根）合并后再规范化，或强制要求传入绝对路径。
- **TOCTOU（检查时间到使用时间）**：在 `assert_allowed` 通过后，路径对应的文件可能被替换为恶意符号链接。如需高安全场景，应在打开文件前再次解析 `os.path.realpath()` 并检查，或者使用 `openat`+`O_NOFOLLOW` 等系统调用（需要平台支持）。
- **挂载点与容器边界**：Docker 挂载卷或 FUSE 文件系统可能导致白名单目录实质指向外部，需确保护栏运行在与 Agent 相同的内核命名空间中。
- **临时目录泄露**：不要忘记把 `/tmp` 或 Agent 专用的临时目录加入白名单，否则正常的临时文件操作也会抛异常。

## 可复用建议

- **配置化与分层**：通过环境变量（例如 `AGENT_ALLOWED_ROOTS=/data/proj,/tmp/sandbox`）注入白名单，与代码解耦。在组织层面可制定强制护栏策略。
- **日志与审计**：在 `assert_allowed` 拒绝时记录详细日志，包含调用栈、请求路径、白名单列表，便于事后排查与攻击溯源。
- **封装成独立包**：将 `FileAccessGuard` 封装为一个轻量级 Python 包，供不同 Agent 或 MCP 插件复用，并可扩展支持网络地址白名单、命令白名单等。
- **与现有安全机制协同**：操作系统级的 AppArmor、SELinux 或容器的只读根文件系统，配合应用层白名单，形成纵深防御。

## 总结

给 Agent 的文件访问加上目录白名单，是一种低成本、高收益的工程化护栏手段。它不能解决所有安全问题，但能以“默认禁止”的模型大幅降低意外破坏的概率。实施中一定要注意路径规范化的细节，尤其符号链接与平台差异。对于任何将本地文件操作暴露给大模型调用的系统，这应该成为标准配置，而不是可选项。
