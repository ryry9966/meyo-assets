## 背景

在 Agent 辅助写作的流水线里，文章生成、配图、发布这些环节已经可以被编排得比较顺畅。但很少有人关注发布之后的“事后管理”：生成的内容散落在各个平台、图片依赖第三方图床、元数据与正文脱钩。一旦图床改动、平台删帖、或者需要批量检索与再分发，很快会陷入“内容多了，但拿不回来”的困境。

我用 OpenClaw 搭建了一套从内容 topic 到发布的全自动流水线，完成多平台推送后，自然会想：能不能把每次生成的内容、配图、以及文章与图片的映射关系，以可检索、可重用的方式归档到本地？这篇文章记录的就是这块归档层的设计。

## 问题拆解

归档这件事看着简单，但一旦配合自动流水线，就会冒出几个非功能需求：

1. **完整性**：文章正文（通常 Markdown）、所有引用的图片、以及文章元数据必须绑定存储，不能只留一个链接。
2. **可追溯**：需要知道每张图片对应哪篇文章的哪处引用，方便以后替换或迁移图床。
3. **无侵入**：不能因为归档步骤导致生成主流程失败或延迟过多。
4. **可复用**：归档产物干净、可直接用于本地静态站点生成、或者喂给其他 Agent 检索。

## 归档目录结构设计

最终我选择在 NAS 上建一个 `published-archive` 仓库，按日期分桶，每条内容是一个独立的子目录：

```
published-archive/
├── 2025/
│   └── 04/
│       └── post-20250401-deploy-agent/
│           ├── article.md
│           ├── images/
│           │   ├── img-01.png
│           │   └── img-02.jpeg
│           └── assets.json
```

`article.md` 是最终的 Markdown 文件，其中图片引用已全部替换为相对路径，如 `![screenshot](images/img-01.png)`。

`assets.json` 记录映射关系和一些关键元数据，示例：

```json
{
  "id": "post-20250401-deploy-agent",
  "title": "如何部署一个简单的 Agent 容器",
  "created_at": "2025-04-01T10:32:00Z",
  "source": "openclaw-auto-publish",
  "images": [
    {
      "file": "images/img-01.png",
      "original_url": "https://cdn.example.com/u/abc123.png",
      "alt": "部署架构图"
    }
  ]
}
```

这个 `assets.json` 的核心作用是：哪怕以后图床链接全部失效，我依然可以通过它重建“原始链接 → 本地文件”的映射，也方便写脚本批量迁移。

## 归档步骤实现

归档逻辑作为一个单独的 `archiver` 模块，注册在发布流水线的最后一个 step。大致流程：

### 1. 接收输入

从上游 Agent 拿到三个东西：`markdown` 正文、一个图片 URL 列表（或者直接是本地路径）、以及文章元数据（标题、生成时间、流水线 id 等）。

### 2. 解析并下载图片

用正则提取 `![alt](url)` 中的 `url`，去重后下载到 `images/` 目录。下载时用 `uuid` 重命名文件，保留原始扩展名，避免文件名冲突。伪代码：

```
for each unique_image_url in markdown:
    ext = guess_extension(url) or ".png"
    local_name = f"img-{short_uuid()}{ext}"
    local_path = f"{dir}/images/{local_name}"
    download(url, local_path)
    markdown = replace(markdown, url, f"images/{local_name}")
    record_mapping(local_path, url)
```

需要处理下载失败的情况（超时、403、内容非图片），失败的图片保留原链接并记录到 `assets.json` 的 `error` 字段，不阻断流程。

### 3. 序列化文章

将替换完图片链接的 Markdown 正文写入 `article.md`，Lint 一下是否有残留的外部图片链接，若有则告警。

### 4. 写入 assets.json

构造完 images 数组后，与文章元数据合并写入。为了防止并发写冲突，使用写入临时文件再原子替换的姿势，虽然没有高并发，但防了脚本被重复触发时的脏写。

### 5. Git 提交（可选）

因为归档目录本身是一个 Git 仓库，归档步骤最后会执行一次 `git add . && git commit -m "archive: post-xxx"`，自动记录历史版本。这一步在脚本里加了个锁，避免多进程并行 git 操作。

## 踩坑点

1. **图片格式判断不可靠**  
   CDN 链接经常不带扩展名，`Content-Type` 可能是通用的 `application/octet-stream`。只靠魔数检测（用 `file` 命令或读文件头 bytes）才稳妥。否则 `.webp` 命成了 `.png`，后续解析会出问题。

2. **相对路径与最终发布混淆**  
   归档内部使用 `images/xxx` 的相对路径，但如果后续某个 Agent 误把这套归档目录当作发布源，图片路径会指向本地不存在的文件。因此规定 `article.md` 只能出现在归档目录内，不做发布用途，从流程上杜绝这种误用。

3. **文件名去重 vs 可读性**  
   用纯 uuid 虽然安全，但没有任何业务含义。折中方案是 `{short_prefix}_{uuid8}.{ext}`，比如 `arch_c3f2e1a1.png`，既保证唯一，又在部分场景下肉眼可区分。

4. **大图与超时**  
   自动流水线有时配图是上游 AI 生成的高分辨率位图，数十 MB。下载时候需要设置合理的超时（30s）和重试 2 次，并且限制文件大小上限（50MB），超出只记 remote_url，不再拉取。

## 可复用建议

如果想把这套归档能力直接集成到自己的 OpenClaw 工作流里，可以：

- 封装成一个 OpenClaw **Tool** 或 **MCP Server**，暴露 `archive_article(markdown, metadata, images)` 接口，内部完成上面所有步骤。这样任意 Agent 流程里都能直接调。
- 元数据建议带上前端 matter，归档工具可自动解析 `title`、`date`、`tags` 生成目录树，便于对接 Hugo 或 Next.js 静态站。
- 如果不想引入 Git 操作，可以直接用 SQLite 记录所有版本，查询更灵活，但丢失了文件级别的历史。
- 注意权限：归档目录的写入账号应与发布流程的账号一致，否则会出现文件 owner 错乱。

## 总结

本地归档看似是发布流水线中“锦上添花”的一步，但它其实是保证内容资产长期可控性的底线。用统一的 `assets.json` 作为索引，配合相对路径图床，就可以把 Agent 生成的散落内容，沉淀成结构化的数据。再配合 Git 或定期备份，即使外部的图床、平台、API 发生变化，你也始终有一份完整的自占副本。

自动化做久了，会越来越意识到：**能持续拿回自己的数据，比新的生成能力更重要。**
