## 背景

在多平台内容分发的日常里，微博超话经常作为必须覆盖的渠道。纯手动操作不仅重复枯燥，还容易因为图片格式不对、发布频率过高等问题反复失败。随着 OpenClaw 与 MCP 工具链的成熟，我们有机会把这一流程抽象成可审计、可自愈的自动化流水线。

本文记录一次基于 OpenClaw Agent 的微博超话同步实践，核心聚焦三个工程问题：**图片上传**、**限流处理**以及**发布状态归档**。目标是构建一个即使半夜无人值守，也能通过重试与状态机正常收尾的同步任务。

## 问题拆解

1. **图片上传**  
   微博超话不允许直接使用外链图片，所有配图必须先上传至微博图床获取 `pid`。上传接口对 Cookie、Referer 和图片格式都有校验，直接用 `requests` 裸发大概率撞墙。

2. **限流**  
   超话发帖频率一旦触及平台阈值，会返回“操作过于频繁”之类的错误，账号可能被冷却 15–30 分钟。不做退避处理，重试风暴只会加剧封禁。

3. **状态归档**  
   同步任务可能跨多个批次，部分成功、部分限流、部分因格式原因永久失败。没有状态记录，就会丢失上下文，导致重复发布或漏发。

## 整体架构

利用 OpenClaw 的 Agent 调度能力，设计了一个三阶段的同步流水线：

- **收集阶段**：Agent 接收待发内容（文本 + 本地图片路径），写入任务表，状态置为 `pending`。
- **发布阶段**：调用两个 MCP 工具：`upload_image_to_weibo` 和 `post_to_supertopic`，内部处理登录态、上传、发帖、限流识别与退避。
- **归档阶段**：每次执行后更新任务状态，并提供查询接口，方便外部监控面板或下游 Agent 使用。

所有状态集中存放在 SQLite 里，单文件即可便携部署。

## 具体实现

### 1. 登录态维护

微博接口高度依赖登录 Cookie。使用 Playwright 模拟扫码或账号密码登录，将最终的 Cookie 持久化为 JSON 文件，并设置定时刷新。每次调用上传或发帖接口时，自动加载最新 Cookie，同时校验 `SUB` 令牌有效性。若 cookie 失效，Agent 可以通过预设通知渠道（如钉钉、邮件）提醒人工介入。

### 2. 图片上传踩坑与解法

通过抓包分析，确定上传接口为：
```
POST https://picupload.weibo.com/interface/pic_upload.php
```
需要 `multipart/form-data`，字段包括 `pic1`（文件）、`cb`、`mime` 等。关键点：

- **Referer 必须为 `https://weibo.com/`**，且与请求中的域一致。
- 图片格式建议统一转为 `jpg`，`webp` 可能导致上传成功但后续发帖时被丢弃。
- 上传成功后返回类似 `cb({"code":"A00006","data":{"pics":{"pic_1":{"pid":"007YdWsBgy1hwnv8..."}}})` 的 JSONP，需解析提取 `pid`。

工具 `upload_image_to_weibo` 接受本地路径，内部进行格式检查与转码，再携带 Cookie 调用上传接口。上传失败的异常会被捕获，并写入归档状态 `upload_failed`。

### 3. 超话发帖与限流对抗

发帖接口示意：
```
POST https://weibo.com/aj/mblog/add?ajwvr=6
```
参数包含 `text`、`pic_id`（前一步拿到的 `pid`）、`topic_id`（超话 ID）等。

**限流识别**：当返回 JSON 中包含 `code` 为 `100001` 或 `msg` 为“操作过于频繁”时，触发退避流程。  
**退避策略**：设置基础冷却时间 900 秒，叠加随机抖动 0–300 秒，将任务状态更新为 `rate_limited`，并记录下次可重试时间。Agent 的调度循环会定期扫描 `rate_limited` 且冷却期满的任务，再次尝试。

**注意事项**：超话 ID 不同于超话名称，需要提前通过搜索接口或网页抓取获取。文本中不再手动加 `#话题#`，避免格式错误。

### 4. 状态归档设计

`task_log` 表结构：

| 字段             | 说明                                 |
|------------------|--------------------------------------|
| id               | 自增主键                             |
| task_id          | 业务任务 ID，幂等去重用               |
| content_hash     | 内容摘要，用于重复检测               |
| status           | 枚举：pending / uploading / uploaded / posting / rate_limited / success / failed |
| retry_count      | 当前重试次数                         |
| last_error       | 最后一次错误信息                     |
| next_retry_at    | 限流状态下允许重试的时间戳           |
| created_at / updated_at | 时间戳                           |

每次状态变更都更新 `updated_at` 并追加详细日志文件。该设计让任何一步中断都可被定位，也方便统计成功率与限流频次。

## 踩坑复盘

- **图片 CDN 延迟**：上传成功后，`pid` 有时不能立即用于发帖，需等待 3–5 秒再调用发帖接口，否则可能返回“图片不存在”。
- **超话门槛**：部分超话有等级或关注天数限制，发布失败时需区分“账号受限”与“网络抖动”。我们在 `last_error` 中细分错误码，避免无意义重试。
- **Cookie 污染**：并行运行时若同时触发登录刷新，可能导致 Cookie 文件写冲突。通过文件锁（`fcntl`）解决。
- **代理问题**：某些机房 IP 被微博标记，发帖直接失败。实践加入了代理池切换能力，作为可选增强。

## 可复用建议

- 将上传与发帖封装为标准 MCP 工具，暴露 `upload_image_to_weibo` 和 `post_to_supertopic`，让其他 Agent 像搭积木一样复用，不必重复造登录轮子。
- 限流退避与状态归档组合成通用“可靠执行器”，可用在其他有频率限制的社交平台发布中（如小红书、贴吧），只需替换具体接口逻辑。
- 利用 OpenClaw 的流程编排，可加入发布后效果检查（例如通过 `check_weibo_post_visible` 工具验证是否成功推送到超话），进一步提高闭环质量。

## 总结

这套实践运行月余，将微博超话同步的手动耗时降低了 90%，且通过明确的状态归档避免了“发没发过”的疑惑。工程上没有魔法，只有对接口行为与错误模式的细心归纳。对 OpenClaw 用户而言，这是一次“把脏活交给 Agent，把可靠性留给自己”的有益尝试。如果您的 Agent 也需要接管更多社交渠道，这套图片上传、限流对抗、状态归档的组合拳应该是一个务实的起点。
