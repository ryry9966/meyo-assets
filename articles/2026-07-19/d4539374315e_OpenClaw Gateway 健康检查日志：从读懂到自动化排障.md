## 背景

在 OpenClaw 体系的线上部署中，OpenClaw Gateway 是所有 Agent、MCP Server 与外部插件调用的统一入口。无论是 Kubernetes 的 liveness/readiness 探针，还是上游负载均衡器的主动探测，健康检查请求每秒钟都在持续涌入。一旦健康检查返回非预期状态，整个服务链路就可能被摘除流量，直接导致功能不可用。

经历过几次“网关明明活着，却被负载均衡踢掉”的故障后，我发现很多问题其实早就写在健康检查日志里，只是没有被正确解读。本文整理了一套面向工程实践的健康检查日志分析思路，帮助你快速排查问题，建立可复用的监控策略。

## 问题定位：一碗粥里找米粒

OpenClaw Gateway 默认日志量不小，健康检查请求混杂在业务请求中，肉眼难以分离。更麻烦的是，即使服务主进程正常，也可能因为依赖服务（如 Redis、MCP Server）短暂不可用，导致健康检查端点在特定条件下返回 503，使网关被误杀。

典型的故障场景包括：

- 健康检查端点返回 200，但 body 内容不符合探测器的预期（例如需要特定字段为 `ok`）。
- 高并发健康检查导致连接池满，反而让正常请求失败。
- 上游负载均衡器探测频率过高，网关日志出现大量 `499` 或超时，被误认为不可用。

因此，光看状态码远远不够，需要结合请求耗时、探测来源、上下文信息来定位根因。

## 做法/步骤

### 1. 统一日志格式，确保关键字段存在

首先检查 OpenClaw Gateway 的日志配置。推荐使用结构化 JSON 输出，至少包含以下字段：

```json
{
  "timestamp": "2025-03-01T08:12:03.456Z",
  "method": "GET",
  "path": "/healthz",
  "status": 200,
  "duration_ms": 12.3,
  "remote_addr": "10.0.1.5",
  "user_agent": "kube-probe/1.28",
  "upstream_service": "master",
  "error": ""
}
```

如果还是纯文本格式，可以自定义日志模板。确保 `path` 字段能区分健康检查路由（一般为 `/healthz`、`/ready`、`/live`），`user_agent` 能识别探测来源（如 K8s 探针、AWS ELB、自研监控）。

### 2. 使用日志采样和过滤

用 `grep` 或者日志平台（如 Loki + Grafana）过滤出健康检查相关的日志：

```bash
# 从文件尾快速查看最新健康检查
tail -f /var/log/openclaw-gateway.log | grep '/healthz\|/ready\|/live'
```

如果健康检查日志量过大，可以考虑在网关层对健康检查请求设置独立的日志级别，甚至配置**条件日志记录**：只记录状态非 2xx 或耗时超过 500ms 的健康检查，避免日志洪流。在 OpenClaw Gateway 中，可以在插件或中间件配置中实现：

```yaml
middleware:
  health_check:
    log_if:
      status_not_in: [200, 204]
      duration_gt_ms: 500
```

### 3. 解读核心指标：延迟与上下游联动

单条日志中的 `duration_ms` 是黄金指标。正常健康检查延迟通常稳定在 5~20ms。如果突然上升到几百毫秒甚至秒级，基本可以断定有资源争用或依赖服务抖动。结合 `upstream_service`，可将延迟异常归因到具体上游。

例如，当 MCP Server 健康检查出现超时，日志可能显示：

```json
{"path": "/healthz/mcp-servers", "status": 503, "duration_ms": 5100, "error": "dial tcp 192.168.1.10:9090: i/o timeout"}
```

此时不要只盯着网关，要迅速去对应的 MCP Server 查看其自身健康状态与资源使用。

### 4. 建立自动化排障规则

将日志分析沉淀为 Prometheus 告警规则或日志平台的聚合查询。我常用的几项：

- **错误率飙升**：5 分钟内健康检查非 2xx 比例超过 5% 触发 warning，超过 20% 触发 critical。
- **延迟 P99 异常**：`duration_ms` 的 P99 连续 3 分钟超过 500ms 告警。
- **探测来源分布**：如果某个 `remote_addr` 或 `user_agent` 的健康检查全部失败，可能是探测节点自身网络问题，而非网关故障。

在 Loki 中，可以用 LogQL 快速统计：

```logql
sum(rate({job="openclaw-gateway"} | path=~"/healthz|/ready" | status != 200 [5m])) by (status)
```

## 踩坑点

1. **把探活失败等同于服务死**  
   负载均衡器探测时，如果网关正在 GC 或刷新路由表，可能出现短暂 503，但几秒后自愈。若立即触发告警并灰度摘除实例，会加剧雪崩。务必设置连续失败阈值（如连续 3 次）才判定失效。

2. **忘记检查健康检查端点本身的逻辑**  
   有些团队在 `/healthz` 里串联了数据库 Ping、Redis Ping，甚至调用外部 API。一旦某个外部依赖抖动，健康检查就失败，导致整个网关被摘除。应该区分 **浅健康检查**（仅判断进程存活）和 **深健康检查**（依赖就绪），由不同路由承担，并配置不同的探测策略。

3. **日志级别设置不当**  
   线上环境如果把健康检查也设为 DEBUG 级别，每秒上千条日志会让落盘 I/O 爆满。建议至少对健康检查路由强制使用 INFO 或 WARN，只记录异常。

4. **忽略 `user_agent` 差异**  
   不同云厂商的 LB 探测行为可能不同：有的要求返回 body 特定字符串，有的仅看状态码。日志中的 `user_agent` 能告诉你该请求需要满足什么契约，避免“我看着正常但探针不认”的窘境。

## 可复用建议

- **统一命名约定**：所有服务的健康检查路径保持 `/healthz`（存活）、`/ready`（就绪）、`/status`（深度）三级，并在网关路由文档中写明。
- **构建健康检查专用看板**：用 Grafana 创建一个面板，只展示健康检查的请求量、延迟、状态码分布、错误 Top N，让值班人员一眼定位。
- **将异常日志接入 ChatOps**：当健康检查连续失败时，把最近 10 条异常日志和上下游拓扑图一起推送到群聊，减少排查信息孤岛。
- **定期做混沌测试**：主动 kill 掉一个 Redis 实例，观察网关健康检查日志的输出是否符合预期，验证告警是否收敛。

## 总结

OpenClaw Gateway 的健康检查日志是服务稳定性的“脉搏”，读懂了能提前发现依赖恶化、资源瓶颈、配置错误等问题。关键不是记住几条命令，而是形成“日志格式 → 过滤采样 → 指标提取 → 自动化告警”的闭环。希望这篇实战思路，能帮你从被动救火转向主动巡检。
