# OpenClaw 定时任务防重入锁：为什么 5 分钟任务会撞车？

在 OpenClaw 的自动化编排里，定时任务是最常见的触发器之一。你配置了一条“每 5 分钟执行一次”的规则，任务偶尔跑得慢一点，下一次触发就和新实例撞在一起——两条（甚至多条）任务同时操作同一批数据或同一个外部系统，轻则产生重复记录，重则状态机错乱。这种“撞车”不是 cron 表达式写错了，而是**执行时间 > 触发间隔**造成的重入问题。本文梳理这一问题的背景、排查思路，以及一套可复用的防重入锁方案。

---

## 背景：触发间隔和实际执行时长是两个维度

OpenClaw 的定时器底层通常基于 Quartz/Cron 或平台自带的调度器，它们严格按照表达式触发任务，不关心上一次执行是否结束。常见配置类似：

```
cron: "0 */5 * * * ?"
```

调度器在第 0、5、10……分钟各触发一次任务。如果单次任务平均耗时 2 分钟，一切正常；但如果某次因为下游 API 抖动、数据量大或网络超时，实际执行了 7 分钟，那么在第 5 分钟触发的实例还没跑完，第 10 分钟的实例又启动了，两个实例就会并发执行。

在单机部署的 OpenClaw Agent 中，这种并发可能在线程池里产生竞争；在多 worker 的集群部署下，问题会更严重——不同节点完全没有共享状态，各自触发任务，撞车概率更高。

---

## 问题表现：不是报错那么简单

重入的后果通常比报错更隐蔽：

- **数据重复处理**：批量同步任务可能把同一批数据写入两次，查重逻辑失效。
- **乐观锁冲突**：如果带版本号更新，第二次写入会抛出 `OptimisticLockException`，但任务已经走了大半流程，前面的副作用（如通知发送、缓存更新）无法撤销。
- **下游压力放大**：外部 API 瞬间承受两倍调用量，可能被限流甚至封禁。
- **日志污染**：排查问题时，很难区分哪条日志属于哪次实例，拖慢根因分析。

因此，单靠“执行快一点”或者“加大间隔”不是工程方案，必须在任务入口做互斥控制。

---

## 做法：基于 Redis 的防重入锁

### 1. 选锁

文件锁、数据库行锁在分布式场景下都不如 Redis 简单可靠。推荐使用 **Redis 的 `SET key value NX PX milliseconds`** 命令实现获取锁的原子性。如果团队已经有 Redisson 等封装库，直接用它的 `RLock` 会更安全。

### 2. 实现步骤

以 OpenClaw 的脚本节点或自定义插件为例，关键代码如下（伪代码，适配 JavaScript/Python/Java 逻辑均可）：

```javascript
const lockKey = "task-lock:order-sync";
const lockValue = uuid();            // 唯一标识，防止误删他人锁
const acquired = await redis.set(lockKey, lockValue, "PX", 600_000, "NX");

if (!acquired) {
  console.log("任务已在执行，跳过本次触发");
  return;
}

try {
  // 核心业务逻辑
  await doOrderSync();
} finally {
  // Lua 脚本原子性判断并释放锁
  const script = `
    if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
    else
      return 0
    end
  `;
  await redis.eval(script, 1, lockKey, lockValue);
}
```

要点：

- **锁超时时间**需要大于任务历史最大执行时间的 120%，例如 5 分钟任务最大可能跑到 8 分钟，锁超时设 10 分钟。
- **锁值唯一**，释放时必须校验，防止因执行超时锁自动过期后，误删已经由下一个实例持有的锁。
- 异常退出时 finally 块保证释放。

### 3. 锁续期（可选但推荐）

如果无法准确预估最大执行时间，可以用 **看门狗机制** 自动续期。Redisson 的 `RLock` 默认每 10 秒检查一次并续期 30 秒。自研实现时，可以起一个独立间隔任务，在业务代码仍持有锁的条件下，通过 Lua 脚本续期 `PEXPIRE`。

---

## 踩坑点

1. **锁超时太短，业务还没跑完锁就过期**  
   症状：两个实例同时进入临界区。解决：根据实际 prod 环境的 p99 执行时间设置超时，并加上续期。

2. **未捕获异常导致锁不释放**  
   所有可能抛出异常的代码（包括第三方 SDK 调用）都要包进 try…catch，finally 里保证释放或过期。

3. **使用 SETNX 后忘记设过期时间**  
   如果只用了 `SETNX` 而没有 `EXPIRE`，一旦进程崩溃，锁永远不释放，任务彻底卡死。务必用 `SET...PX` 的原子命令。

4. **集群环境锁失效（节点主从切换）**  
   Redis 主节点宕机后，如果锁还没同步到从节点，新的主节点会丢失锁信息，导致两个客户端同时持有锁。对于强一致性要求的场景，可以换用 **RedLock** 算法或使用 Zookeeper 等 CP 系统，但会增加复杂度。多数定时任务场景下，单机 Redis 哨兵模式的短暂失效可以接受，配合数据库幂等再做兜底。

5. **锁粒度问题**  
   如果多个不同任务共用一个锁，会互相阻塞。应该按任务逻辑单元（如 “order-sync”、“report-generate”）分别定义锁 key。

---

## 可复用建议

将防重入逻辑抽象成一个 **任务装饰器/中间件**，避免每个任务手写相同的锁代码。装饰器接收锁 key、超时时间、是否续期等参数，统一处理获取、续期、释放与异常日志。伪代码：

```javascript
function withLock(key, ttl, fn) {
  return async (ctx) => {
    const lock = await acquireLock(key, ttl);
    if (!lock) return skip(ctx);
    try {
      return await fn(ctx);
    } finally {
      await lock.release();
    }
  };
}
```

对于 OpenClaw 工作流，可将该装饰器包装成**可复用节点**，其他流程直接拖入前置步骤即可。同时，监控任务重合度——若“跳过执行”次数突增，说明任务变慢，需要优化或调整间隔。

另外，业务侧最好也做**幂等设计**，用唯一标识（如业务单号+版本）防止极端情况下锁失效导致的重复写入，形成双重防护。

---

## 总结

5 分钟任务撞车，本质是调度周期与执行时长的错配。靠加大间隔无法根治，用一把基于 Redis 的防重入锁能以极低成本解决问题。关键是：

- 原子获取锁并设置过期；
- 释放时校验持有者；
- 合理设置超时与可选的续期；
- 抽象为中间件复用，降低维护成本。

在 OpenClaw 的自动化实践里，这类基础防护能让任务编排更稳健，避免因偶发抖动引发的连锁故障。
