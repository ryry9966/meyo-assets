## 背景

如果你在折腾内容自动发布流水线——无论是通过 OpenClaw 调度 Agent 生成文章，还是用自定义脚本把 Markdown 推到各个平台——很快会撞上一个现实问题：**本地到底该留下什么？**

发布成功只是第一步。过几个月想回溯某篇内容的原始素材，发现图片链接 404；想把某篇文章改一版跨平台重发，但找不到当时裁剪过的封面图；或者更糟，Agent 跑了一周，产出了几十篇内容，本地只有一堆零散的 `.md` 文件，没有任何结构化元数据。

这些问题本质上都是“内容资产管理”的问题。本文记录我在个人自动化流水线中逐步形成的一套轻量本地归档方案，不依赖外部服务，只用目录结构 + JSON 元数据 + 少量脚本，就能让文章、图片和发布状态可追溯、可复现。

## 问题拆解

流水线在发布环节通常会做三件事：生成 Markdown、上传图片到远端（如 CDN 或平台图床）、调用发布 API。如果只保留最终的发布版本，会遇到几个典型痛点：

1. **图片与源文件分离**：Markdown 里是远端 URL，本地没有原始图片，断网或 CDN 变动就无法重建页面。
2. **无结构化元数据**：标题、slug、发布日期、平台状态散落在脚本变量或环境变量里，事后检索困难。
3. **流水线与存档耦合**：存档逻辑和发布脚本搅在一起，一旦发布流程升级，历史内容的回填就变成体力活。
4. **无法离线浏览**：所有引用都是远程 URL，本地打开 MD 就是一张“图片缺失”的残骸。

因此设计目标很明确：

- 本地目录自包含：一个目录塞进当次发文所需的所有素材和元数据。
- 远端-本地双向映射：记录图片的原始文件与最终远端 URL 的对应关系。
- 不绑定特定平台或发布工具：存档格式应能脱离流水线独立读取，哪怕将来换 Agent 框架或发布接口。

## 做法与步骤

### 1. 目录结构约定

以单篇文章为一个归档单元，按 `content/YYYY-MM-DD-slug/` 组织：

```
content/
└── 2025-03-01-automated-pipeline-archiving/
    ├── article.md          # 本地可浏览版本（图片引用为相对路径）
    ├── publish.md          # 远端发布用版本（图片引用为 CDN URL）
    ├── images/
    │   ├── cover.png
    │   ├── diagram-01.png
    │   └── screenshot-02.png
    └── assets.json
```

- `article.md`：面向人类阅读或本地预览，图片采用 `images/cover.png` 的相对路径。
- `publish.md`：实际推送到平台的版本，图片路径替换为最终的远端 URL。可由脚本从 `article.md` 和 `assets.json` 自动生成。
- `images/`：原始图片文件。文件名使用语义命名（或 hash），避免冲突。
- `assets.json`：结构化的资产管理文件。

### 2. assets.json 设计

尽量扁平，字段只记录“必须且能稳定获得”的信息，避免过度膨胀。一个最小可用定义：

```json
{
  "version": "1.0",
  "slug": "automated-pipeline-archiving",
  "title": "自动发帖流水线的本地归档实践",
  "date": "2025-03-01",
  "tags": ["automation", "archiving", "openclaw"],
  "platforms": {
    "zhihu": "published",
    "wechat": "draft"
  },
  "images": [
    {
      "local_path": "images/cover.png",
      "remote_url": "https://cdn.example.com/abc123.png",
      "alt": "archiving pipeline overview",
      "width": 1200,
      "height": 630,
      "sha256": "a1b2c3..."
    }
  ]
}
```

字段说明：

- `version`：JSON 格式版本号，未来修改结构时用作兼容判断。
- `slug`：用作目录名和标识符，确保唯一。
- `title`、`date`、`tags`：基础元数据，方便汇总脚本扫描。
- `platforms`：记录各平台发布状态，便于追查哪些渠道已经推送。
- `images`：数组记录每张图片的**本地路径到远端 URL 的映射**，并附带尺寸和 hash。hash 可用于校验图片完整性，尺寸则避免二次读取。

### 3. 流水线集成

将存档步骤从发布脚本中抽成一个独立模块，通过简单的 CLI 或作为 OpenClaw 的 MCP 工具调用。伪流程如下：

1. **准备阶段**：Agent 生成原始 Markdown 内容，图片已落盘到临时目录或指定 `images/` 下。
2. **图像处理与入库**：
   - 用 `sharp` 或类似库获取宽高。
   - 计算文件 SHA256。
   - 生成远端文件名（例如用内容 hash 或时间戳+随机数）。
   - 将图片复制/移动到归档的 `images/` 目录，如果需要可同时生成缩略图。
3. **上传与映射**：按远端平台要求上传图片，得到最终的 `remote_url`。这一步可能在归档模块内完成，也可由独立的 uploader 完成并返回映射。
4. **生成 assets.json**：收集上述元数据，写入 JSON。
5. **生成两版 Markdown**：
   - 保留 `article.md`，确保图片链接均为 `images/xxx` 的相对路径。
   - 基于 `assets.json` 中映射，将 `article.md` 中的本地路径替换为对应的 `remote_url`，生成 `publish.md`。这一步可以简单用字符串替换，安全起见可结合 `mdast` 等 AST 工具精确替换。
6. **发布与状态更新**：发布完成后，将各平台状态写回 `assets.json` 的 `platforms` 字段。

整个模块的功能非常适合包装为一个 MCP server 的 tool，例如 `archive_article`，接收原始 markdown 文本、图片本地路径、平台映射等参数，返回 `assets.json` 和归档路径。这样无论是 OpenClaw 中的人工触发，还是全自动 Agent 循环，都能直接通过工具调用完成标准化存档。

## 踩坑点

1. **图片重名覆盖**  
   多篇文章可能都使用 `cover.png`。如果直接平铺在全局 `images/` 下，必然冲突。解决方式是用文章 slug 作为命名空间，图片存在于各文章的 `images/` 子目录，或在上传环节对文件名加 hash 前缀。推荐后者，因为从 CDN 角度也更友好。

2. **远端 URL 漂移**  
   某些平台图床可能会定期更换域名，或者在二次传播中被代理替换。`assets.json` 中的 `remote_url` 应始终记录**你在发布时确认可用的 URL**，而不是猜测的最终形态。如果后续需要迁移，可以单独写脚本根据 hash 重新匹配。

3. **JSON 格式僵化**  
   初始版本字段太死板，后期想加 `excerpt`、`canonical_url` 这类字段就得全量改写。从一开始就加 `version` 字段，读档时做兼容处理。同时让工具忽略不认识的字段，避免因新增字段导致旧存档不可读。

4. **Markdown 路径替换不彻底**  
   Markdown 中图片引用可能有多种写法：`![alt](img.png)`、`<img src="img.png">`，甚至位于 HTML 块中。简单的字符串替换容易漏掉。建议使用统一的 AST 处理，或强制生成内容时统一使用 `![alt](image.png)` 格式，降低替换复杂度。

5. **相对路径层级**  
   如果归档目录嵌套，`article.md` 和 `images/` 的相对路径必须严格保持根在文章目录下，不要出现 `../images/` 的引用，这样整个目录复制到任意位置都能正常打开。

## 可复用建议

- **将存档逻辑做成无状态工具**：输入 markdown 文本、图片 Buffer 及平台配置，输出归档路径和 `assets.json`。不依赖全局配置，方便在任何 Agent 环境中调用。
- **利用 git 做版本管理**：把整个 `content/` 目录纳入 git，每次发布自动 commit，附带平台状态。这样不仅能回溯，还能轻易比较不同版本。
- **校验闭环**：提供一个 `validate` 子命令，检查 `assets.json` 中列出的图片是否都在 `images/` 里、`local_path` 是否有效、`sha256` 是否匹配、`article.md` 引用的图片是否全部在 JSON 的 `images` 数组中。这能防止“图片漏归档”的情况。
- **与发布解耦**：发布模块只负责“将某篇已归档的文章推送到某平台”，归档模块只负责“生成文章并存档”。两者通过 `slug` 和 `assets.json` 沟通，各自独立演进。

## 总结

自动化发帖流水线不能只管发不管收。本地归档不是事后的“备份”，而应该作为发布流程的一个标准输出产物。通过约定清晰的目录结构、一份精简的 `assets.json`，以及独立的工具模块，可以做到：

- 任何一篇文章都可在本地完整、离线浏览。
- 图片原始素材和远端 URL 映射永久记录，抗 CDN 失效。
- 跨平台发布状态可查询、可续推。
- 为未来的内容分析、重发布或格式转换提供结构化数据基础。

这套方案没有黑魔法，全是擦屁股的工程活儿，但一旦落地，就会发现整个内容管线突然可控了许多。
