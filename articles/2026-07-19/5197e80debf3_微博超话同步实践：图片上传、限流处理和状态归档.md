## 背景

我把微博超话当作一个结构化的内容分发出口，用来同步某些垂直信息源。手动维护太消耗注意力，于是用 OpenClaw 搭了一条自动化管线：Agent 定时抓取源数据，经格式化后调用微博的发帖能力完成同步。整个过程里，图片上传、限流策略和发布状态归档这三块踩了不少坑，整理出来供有类似需求的同学参考。

## 问题拆解

超话发帖不同于普通微博，它要求在正文中携带 `#超话名称#` 话题标记，并且接口行为对图片上传有额外校验。主要难点集中在：

1. **图片上传**：微博移动端 / PC 端的上传接口有差异，超话专用的话题页上传字段与普通 `statuses/upload` 不完全一致。
2. **限流规避**：短时间内高频发帖会触发请求频率限制或账号风控，表现形式包括验证码、接口静默失败甚至临时冻结。
3. **状态归档**：必须可靠地记录哪些内容已经发布过，避免重复，同时又要支持断点续传。

我们的做法是围绕一个无头请求客户端，实现“登录→上传→发帖→记录”的 pipeline，并做好异常分支处理。

## 实现步骤

### 1. 建立持久化会话

使用 `requests.Session` 承载登录态。先通过扫码或账号密码登录获取 `cookie`，关键字段是 `SUB` 和 `SUBP`。考虑到扫码更适合自动化环境，我写了一个简单的回调接口来接收扫码结果。会话创建后做一次健康检查，调用 `https://weibo.com/aj/account/watermark` 类似接口确认登录有效。

### 2. 图片上传

微博的图片上传接口是 `https://picupload.weibo.com/interface/pic_upload.php`，参数较多且签名逻辑隐晦。经过抓包和反复尝试，稳定可用的最小参数集合如下：

- `data`：图片字节流，Content-Type 为 `image/jpeg` 或 `image/png`
- `mime`：`image/jpeg`
- `marks`：固定值 `1`
- `app`：`miniblog`
- `s`：`rdxt`
- `url`：留空

上传成功后返回的 JSON 中提取 `pid`，它是后续发帖接口的图片唯一标识。踩坑点在于，如果你直接在 `statuses/update` 中填入 `pid` 有时会失败，必须用 `statuses/share` 或超话专用发帖接口，并把 `pic_id` 作为独立参数传递。

另外，图片大小要控制在 5MB 以内，过大会被静默丢弃，最好提前用 Pillow 压缩到 1920px 宽以内。

### 3. 超话发帖

发帖接口使用 `https://weibo.com/aj/mblog/add`，请求体是 `application/x-www-form-urlencoded`，主要字段：

- `text`：正文，必须以 `#超话名#` 开头
- `pic_id`：上一步获取的 pid
- `pub_source`：`topic`
- `topic_id`：超话的 id，可从超话页面 URL 中提取
- `sync_wb`：`1`（同步到个人主页）

这个接口返回的状态码比较混乱，有时成功返回 `code` 为 `"100000"`，有时是 `"0"`。我的经验是同时检查 HTTP 状态码和响应里的 `msg` 字段。

### 4. 限流与重试

单账号的发帖频率控制在 2～3 分钟一条比较安全。我们实现了一个基于令牌桶的本地限速器，而不是简单 `sleep`。当请求返回特定错误码（`"100001"` 频率过高、`"20003"` 需要验证码）时，进入指数退避重试：首次等待 120s，然后 240s，最多重试 3 次，仍失败则标记为 `BLOCKED` 并告警。

有些情况下会 IP 被暂时屏蔽，表现为发帖接口 302 跳转到验证码页面。此时切换代理池出口即可继续，因此我在 session 层做了动态代理注入。

### 5. 状态归档

我用 SQLite 表记录每一篇待同步内容的去重键（源内容的 URL 或 hash）、发布状态（`PENDING` / `POSTED` / `FAILED` / `BLOCKED`）以及对应微博的 `mid`。当 OpenClaw Agent 提交任务时，先检查该去重键是否已有 `POSTED` 记录，有则跳过，无则进入发布流程。这样即使 pipeline 崩溃，重启后不会重复发帖。

## 可复用建议

整套逻辑最终封装为一个 OpenClaw 可调用的工具（Tool），并注册为 MCP server。Agent 只需传入文本和图片 URL，工具内部处理下载、上传、发帖、归档。其他社区成员如果想接入类似场景，建议：

- 先用一个临时账号验证接口，不要直接上生产号，避免风控。
- 图片处理前置：异步下载、压缩、生成 pid，减少同步阻塞。
- 把“检查已发布”放在 pipeline 最前端，尽早过滤，节省请求配额。
- 为发帖接口建立单独的日志，记录请求体摘要和响应，方便排查静默失败。

## 总结

微博超话同步的自动化难点不在于接口本身，而在于处理边界条件和维持长期稳定。通过工程化的方式，把图片上传的细节、限流策略、状态归档做成可重试、可观测的流水线，最终交给 OpenClaw Agent 统一调度，就可以用较低的维护成本完成内容分发。如果你也有类似的跨平台同步需求，可以借鉴这套模式，将重心放在 schema 映射与监控上，而不是重复踩坑。
