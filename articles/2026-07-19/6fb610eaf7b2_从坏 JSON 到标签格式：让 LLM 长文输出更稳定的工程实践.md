在构建基于大语言模型（LLM）的 Agent、MCP 工具或自动化插件时，我们常常需要让模型返回结构化的长文内容——例如自动生成的项目报告、多段落的分析摘要，或需要分段渲染的富文本页面。很多开发者的第一反应是要求模型输出 JSON，因为 JSON 易于解析、生态成熟。但一旦遇到千字以上的复杂嵌套输出，“坏 JSON”几乎成了常态：缺少逗号、引号未转义、大括号不匹配、输出在中间被截断，导致整个解析流程崩溃，Agent 任务失败。

这篇文章不讨论泛化的提示技巧，而是面向 OpenClaw-CN 社区里那些需要在高可靠性工程环境中驱动 LLM 输出的同行，记录我如何从频繁处理坏 JSON 过渡到使用自定义标签格式，让长文结构化输出更稳定、更可维护。

## 背景：为什么坏 JSON 如此常见

在 LLM 文本生成过程中，模型是逐 token 自回归生成的，它并不天然“理解”严格的 JSON 语法，只是根据训练数据中的模式来续写。对于短输出，靠少量 few-shot 示例就能得到合法 JSON；但输出长度一旦超过 500 字，特别是涉及多层嵌套对象或包含大量自由文本字段（如 `"content": "一段很长的分析..."`）时，风险指数级上升。

典型故障模式包括：
- 尾部 bracket 丢失：模型生成了主要内容后，由于上下文窗口注意力分散，忘记闭合最外层或中间层的 `}` 或 `]`。
- 字符串转义失控：在长文本中出现未转义的双引号、换行符、反斜杠，破坏整个对象结构。
- 提前截断：受 max_tokens 限制，输出在 JSON 中间切断，补全无法修复。
- 数值格式漂移：例如将需要字符串输出的字段生成了布尔值或数字。

对于需要全自动化运行的 Agent 流程，一次 JSON 解析失败意味着需要引入重试、修复逻辑，大幅增加延迟和不确定性。一些方案尝试用“JSON 修复器”来后处理，但这些修复器本身也是启发式的，对深层嵌套错误力不从心。

## 替代方案：基于标签的半结构化格式

一个被多次验证有效的思路是放弃 JSON，改用类似 XML 的自定义标签来分隔不同语义块。让模型按照约定格式输出，比如：

<OUTPUT>
<TITLE>项目进展周报</TITLE>
<SUMMARY>本周核心交付包括...</SUMMARY>
<DETAILS>
<SECTION label="模块A">
...多段落自由文本...
</SECTION>
<SECTION label="模块B">
...多段落自由文本...
</SECTION>
</DETAILS>
</OUTPUT>

这种做法的优势在于：
- 容错性强：即便某一标签未闭合，解析器仍可提取其他已闭合的部分，不会整体失败。
- 对长文本友好：模型只需记住当前所处标签的上下文，而不是整个 JSON 树的缩进和逗号。
- 解析简单：可使用简单的正则或基于行的状态机提取标签内容，避免依赖重量级解析器。
- 便于流式处理：可以在 token 流中实时检测标签开启/关闭，逐步组装结果，不用等待整个输出结束。

## 具体实践步骤

### 1. 定义你的标签规范（DTD-Lite）

为你的任务设计一套固定的自定义标签集合，命名使用大写字母和下划线，避免与常见文本词汇冲突。例如，对于多文档摘要输出，可以定义：

- `<DOCUMENT id="...">`...</DOCUMENT>`
- `<ABSTRACT>`...</ABSTRACT>`
- `<KEYPOINTS>` 与 `<POINT>`...</POINT>`
- `<CONCLUSION>`...</CONCLUSION>`

向模型说明规则时，要明确：**标签必须成对出现**，标签内文本可以任意长，且 **不要** 在标签正文内再出现同样的标签（如确实需要，使用转义或替换）。

### 2. 编写清晰的 Prompt 模板

在 system prompt 或 user prompt 中固定输出格式约定，并提供 2-3 个短示例（few-shot），展示输入与对应的标签输出。示例应覆盖正常流程和边界情况（如空摘要、超长段落）。强调：“只输出最终标签结构，不要添加任何外围解释或 Markdown 代码块标记。”

避免使用“输出 JSON”这个词，彻底改变模型的生成先验。

### 3. 实现一个稳健的提取器

在代码端，不用把整个响应当作 XML 去合法解析（那又会引入严格的闭合要求）。可以写一个基于正则表达式的轻量提取器，按优先级提取各标签主体。例如 Python 中：

```python
import re

def extract_section(text, tag):
    # 非贪婪匹配，允许换行
    pattern = rf"<{tag}>(.*?)</{tag}>"
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1).strip() if match else None
```

对于有属性标签如 `<SECTION label="...">`，适当调整正则。提取时，从最外层 `<OUTPUT>` 开始，依次拿取各段内容；即使个别缺失，其它字段依然可用，避免整个流程崩溃。

如果需要处理流式输出，可以维护一个缓冲区，当检测到闭合标签时触发回调，实时推送部分结果。

## 踩坑点与应对

**坑1：标签名称与正文内容冲突**

模型可能在生成的自由文本中无意写出 `<TITLE>` 这样的字符串。应对方法：一是标签命名尽量独特（如 `::TITLE::`），二是给 prompt 加一条“如果正文中需出现标签字符，请使用实体引用 `&lt;` 和 `&gt;`”，三是解析时对未闭合或重复出现的标签做合理的 fallback 处理。

**坑2：模型不遵守闭合顺序**

有时模型会输出 `<A><B>text</A></B>` 这种错误嵌套。对此，在设计上尽量减少同层标签的交叉嵌套，采用平坦结构；提取时可用顺序扫描，记录当前打开标签的栈，发现错误嵌套则丢弃有问题的块，而不是整体报错。

**坑3：截断导致最后一个标签缺失闭合**

这是免不了的，但至少其他完整标签仍可提取。可以在 prompt 中要求将最重要的字段（如摘要）放在靠前位置，降低截断带来的信息损失。

**坑4：模型有时候仍然偷偷输出 JSON**

如果 prompt 里没有严格禁止 JSON，模型可能因为训练数据惯性，在长标签里嵌入 JSON 片段。这通常无害，只要标签能闭合。如果必须避免，可以在 prompt 中明确要求：“输出必须是标签格式，不要包含任何 JSON 结构。”

## 可复用的工程建议

1. **模板化你的标签体系**：将标签定义、prompt 片段和解析代码封装成一个可配置的模块，后续不同任务仅需替换标签集和示例。
2. **集成进 Agent 的 tool 返回**：如果你的 Agent 通过 tool 调用 LLM，可以让 tool 的 response schema 直接返回 `tagged_text` 字符串，然后由上层统一解析，降低耦合。
3. **保留一条 JSON 后路**：对于关键数值字段（如评分、数量），可在标签内嵌一个简单 JSON 字符串，如 `<META>{"score": 0.87}</META>`，这样既保留 JSON 的精确性，又避免整个长文本受 JSON 弱点影响。
4. **增加校验而非强校验**：解析后对必需字段做非空验证，缺失则触发轻量重试，而不是直接认为失败。这样既稳健又不笨拙。
5. **记录输出样本**：每次发现新的边界情况，补充到 few-shot 示例库中，持续提升稳定性。

## 总结

从坏 JSON 切换到自定义标签格式，本质上是在 LLM 的“结构化需求”和“生成不稳定性”之间寻找一个更宽松、更容错的契约。它并非银弹，但经过多个长文自动化项目的验证，能显著降低解析失败率，让 Agent 流程更加流畅。对于 OpenClaw 社区的开发者，如果你的插件或 MCP 工具需要从 LLM 获取复杂长输出，不妨在下一版中尝试这种半结构化设计——你会发现，少一点严格的语法约束，反而收获了更多的工程确定性。
