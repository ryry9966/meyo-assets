## 背景：为什么“输出 JSON”那么脆弱

在 OpenClaw 的 Agent 编排、MCP 工具调用插件或自动化内容生成管道中，我们经常要求 LLM 以结构化数据返回——摘要、多段正文、元信息、引用列表等。最自然的选择是 JSON，因为几乎所有编程语言都能解析它。

问题在于：当输出长度超过几百行，JSON 就会频繁出现三类故障：

- 括号/花括号不成对（尤其在代码块或嵌套对象中遗漏 `}`）
- 字符串中未转义的换行、双引号或反斜杠
- 最后的 `]` 或 `}` 缺失，或者模型在末尾多输出一句解释

这些情况下，`JSON.parse` 直接报错。你可能会做修复（比如用正则补齐括号、按行找键），但修补逻辑脆弱且不可移植。更糟糕的是，长 JSON 的错误往往出现在深层嵌套，手动调试极其费力。

在 OpenClaw 的实际场景中，LLM 输出常交给下一个工具节点或 MCP 服务器，中间一个解析失败就会中断整条管道。因此，工程上需要一个比 JSON 更容错、更易拆分、能被模型稳定生成的结构化方式。自定义标签格式就是被验证有效的一种。

## 设计：用标签划定语义区

核心思路是把长文按语义切分成若干区段，用成对的文本标签包裹，例如：

```
[SUMMARY]
这是一段摘要...
[/SUMMARY]

[KEYWORDS]
keyword1, keyword2, keyword3
[/KEYWORDS]

[SECTION:引言]
这是引言内容，可以跨多行。
包含任意字符，无需转义。
[/SECTION:引言]

[SECTION:方法]
方法的描述...
[/SECTION:方法]
```

解析器只需要按标签匹配起始和结束位置，提取其中的内容。这种方式有以下工程优势：

- **边界清晰**：不需要担心引号、花括号的配对，内容可以自由换行。
- **拆分容易**：标签本身就是内容段的分割符，后续处理可以按标签名路由到不同下游（例如 `[SUMMARY]` 写入数据库，`[SECTION]` 渲染成 Markdown）。
- **容错度高**：即使模型在末尾多输出无关文字，只要核心标签闭合，内容依然可以被正确提取。
- **适合流式输出**：OpenClaw 的 invoke 流式接口可以逐 token 递送，我们可以实现一个状态机，逐标签识别，不必等整个响应完成再解析。

## 正确做法：Prompt 模板 + 轻量解析器

### 1. 设计标签约定

标签名应具备唯一性，避免与输出正文中可能出现的字符串冲突。我习惯使用前缀如 `%%` 或 `【】`，但在英文内容中用 `[OUTPUT:xxx]` 也足够。规则：

- 每个语义块用一对标签：`[BLOCK_NAME]` 和 `[/BLOCK_NAME]`
- 支持带参数的标签，如 `[SECTION:标题]`
- 明确禁止在正文中出现与标签相同的行首模式（可在 prompt 中说明）

### 2. Prompt 示例（简化）

假设需要一个工具来总结长文档并返回多节摘要：

```
You will generate a structured summary using the following format:

[SUMMARY]
Brief overall summary here.
[/SUMMARY]

[KEY_POINTS]
- Point 1
- Point 2
[/KEY_POINTS]

[SECTION:Background]
Background content, can be multiple paragraphs.
[/SECTION:Background]

[SECTION:Analysis]
Analysis content.
[/SECTION:Analysis]

Important rules:
- Do NOT output anything outside these blocks.
- Do NOT use "[SECTION:" or "[/SECTION:" in the content body.
- Keep each block self-contained.
```

经过测试，绝大多数模型（包括较小型的本地模型）都能稳定遵循这种显式标签格式，失败率远低于 JSON 生成。

### 3. 解析实现（Python）

解析逻辑可以非常简单，甚至用正则就能覆盖多数场景：

```python
import re

def parse_tagged_output(text: str) -> dict:
    result = {}
    # 匹配 [BLOCK] 内容 [/BLOCK]
    pattern = r'\[(\w+(?::[^\]]*)?)\]\s*(.*?)\s*\[/\1\]'
    for match in re.finditer(pattern, text, re.DOTALL):
        block_name = match.group(1)
        content = match.group(2).strip()
        result[block_name] = content
    return result
```

对于 `SECTION:标题` 这种带参数的标签，通过 `split(':', 1)` 即可区分类型和参数，然后组织成嵌套字典或列表。更复杂的场景，如多级嵌套标签，可以用栈实现，但建议**避免嵌套**，保持扁平，以降低模型出错概率。

### 4. 集成到 OpenClaw 工具

在 OpenClaw 的 `tool` 函数节点里，我们可以这样调用：

```python
@tool
def summarize_document(text: str) -> dict:
    prompt = build_tag_prompt(text)  # 注入上述 prompt
    raw = llm.invoke(prompt)         # OpenClaw 支持的调用
    return parse_tagged_output(raw)
```

解析失败时，我们能得到部分结果（至少一些块成功提取），而不是像 JSON 那样什么都没拿到。这给系统以“优雅降级”的能力。

## 踩坑点与注意事项

1. **标签冲突**  
   模型有时会在正文中引用示例或使用 `[SUMMARY]` 作为标题。缓解方法：选更生僻的标签，例如 `[[SUMMARY]]`、`<|summary|>` 或 `%%SUMMARY%%`。在 prompt 里强调“除了我指定的标签，不要用方括号包裹其他内容”也能减少冲突。

2. **未闭合的标签**  
   如果模型在生成 `[SECTION:xxx]` 后中断，后半截正文会包含未闭合的内容。解析函数应能检测到缺失的 `[/SECTION:xxx]`，并丢弃该块或纳入前一个完整的块作为容错处理。简单的策略：从后向前查找未闭合的标签，忽略一切尾随文本。

3. **多标签混合与顺序**  
   同一类型块可能出现多次（如多个 `SECTION`）。解析器需支持返回列表，而不是覆盖。正则匹配会按顺序得到，需按业务逻辑聚合。

4. **与 GBNF 语法约束的适配**  
   部分后端（如 llama.cpp）支持 GBNF 语法，我们可以提供一个严格的语法来强制模型只输出标签格式。但 GBNF 编写复杂，且严格的约束可能在长文时降低了模型的灵活性。实践中，对较大模型（7B+）只需良好的 prompt 引导就够了。

5. **在 MCP 工具链中的序列化**  
   如果你的工具被注册为 MCP 服务，返回的是 JSON 或者是文本，那么解析后的标签数据可以无缝地再封装成标准结构，输出给下一个工具。从 MCP 的视角看，这只是一个“返回结构化文本解析结果”的函数。

## 可复用建议

- **统一标签规范**：在团队内部约定一套标签命名规范，例如 `[OPC:模块:子项]`，方便跨项目复用解析器。
- **编写通用的 `TaggedOutputParser`**：实现一个类，能注册期望的标签列表，验证完整性，返回有序 dict。
- **在 OpenClaw 工作流中，把标签解析作为独立节点**：先让 LLM 生成带标签的文本，再接入解析节点，分解为多个下游输入，使工作流更清晰。
- **配合流式输出构建实时 UI**：通过 SSE 推送已识别的标签块，前端可以逐一渲染，提升用户体验。
- **保留原始输出**：无论解析成功与否，永远把 LLM 的原始文本存储下来，便于调试和改进 prompt。

## 总结

标签格式不是银弹，无法完全替代 JSON 在 API 通信中的地位，但在 LLM 长文输出这一特定工程领域，它提供了一个更稳健、更易维护的结构化方案。你需要付出的只是设计一套标签约定、编写几十行的解析器，就能换得更高的一次生成成功率，减少管道中断和手动修复的负担。

对于 OpenClaw 社区的实践者来说，当你下一次被坏 JSON 折磨时，不妨尝试在 prompt 中画几个方括号，你可能会发现稳定性的提升比预期的更明显。
