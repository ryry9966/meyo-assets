## 背景

我维护着一个技术博客，平时会把新文章摘要推送到相关微博超话，用来增加一点自然曝光。手工操作多了就发现两个问题：一是文章配图需要单独上传再填入，二是超话发帖有隐藏的频率限制，封控后整号受限，三是经常忘记哪篇已经发过，导致重复发帖被社区管理员警告。

眼看 OpenClaw 已经能稳定编排定时任务和 Agent 动作，就决定把整个流程工程化：从 Markdown 源文件中提取摘要和配图，自动上传图片到微博图床，在特定超话发帖，并完整记录状态，避免重复与越限。整个过程踩了一些坑，核心集中在图片上传、限流策略和状态归档三处，下面把可复现的做法梳理出来。

## 问题拆解

1. **图片上传**：超话发帖不允许外链图片，必须使用微博图床。公开 API 权限难申请，只能复用 web 端的上传接口。
2. **限流控制**：非认证账号在超话发帖频率过高会触发验证码或禁言，需要策略化控制。
3. **状态归档**：需要一套轻量的机制追踪“哪篇文章/哪个帖子”已经成功同步，避免重复推送。

## 做法与步骤

### 整体编排

我在 OpenClaw 中定义一个定时 Worker，每天上午 10 点触发一个 Agent 任务。这个 Agent 会顺序执行：

1. 读取新增的博客文章列表（通过对比上次同步时间戳）。
2. 对每篇待同步文章生成摘要文本、提取本地路径的配图。
3. 通过微博图床上传配图，拿到 `pid`。
4. 构建超话发帖请求，附带 `pid` 和超话 gid。
5. 成功后记录状态，失败重试一次后报警。

下面重点展开图片上传与限流归档的实现。

### 图片上传

直接使用 `playwright` 打开微博发帖页面然后 `upload` 文件存在大量不确定等待，于是改用更稳定的方案：通过 HTTP 直接 `POST` 表单到微博的 `pic_upload` 接口。

该接口地址为：
```
https://picupload.weibo.com/interface/pic_upload.php
```
需要携带以下参数（`multipart/form-data`）：
- `cb`：随机 jsonp 回调名，可留空
- `mime`: `image/jpeg` 或 `image/png`
- `data`: 图片的 base64 编码
- `url`: `0` （固定）
- `markpos`: `1`
- `logo`: `1`

同时，必须在 `Cookie` 中带有有效的 `SUB`、`SUBP` 等登录票据，`Referer` 设为 `https://weibo.com`。否则返回的 `pid` 无效。

调用后返回类似 `"data":{"pics":{"pic_1":{"pid":"xxx"}}}` 的 JSON，提取 `pid` 即可。注意：如果图片超过 5MB 或格式为 webp，接口会静默失败，需要预先用 `sharp` 等工具转换。

### 限流控制器

我实现了一个简单的限流模块，核心是一个 JSON 文件 `rate_limit.json`，记录每次成功发帖的毫秒时间戳。Agent 在发帖前执行检查逻辑：

- 读取文件，筛选过去 **1 小时** 内的记录条数。
- 若 ≥ 2 条，则直接将本次任务挂起，等待下一个周期。
- 同时增加随机延迟（10~60 秒）再写入下一次请求，避免固定间隔被识别。

这个文件会随状态归档一起持久化，不会因任务重启而丢失历史。

### 状态归档

用 SQLite 或 JSON 都行，为维护方便我选了 JSON 行文件 `sync_state.jsonl`，每条记录包含：
- `blog_slug`：文章唯一标识
- `weibo_post_id`：成功发帖后微博返回的帖子 id
- `pic_pid`：使用的图片 pid
- `timestamp`：发帖时间

发帖前先 grep `blog_slug` 是否存在，存在则跳过。发帖成功后追加一条新记录。同时配合 cron 动作，每次运行时清理 30 天前的旧记录，保持文件不会无限增大。

## 踩坑点

- **cookie 时效**：`SUB` cookie 一般 24 小时过期，需要定期通过扫码刷新。我采用 OpenClaw 的 Secret 变量存储 cookie，并加了一个每隔 20 小时的刷新提醒 Agent，手动扫码后写入新 cookie。
- **图片格式白名单**：非 JPG/PNG/GIF 会上传失败，而且错误信息不明确。必须强制转换格式，推荐统一输出为 80% 质量的 JPEG。
- **超话发帖接口的 gid**：不同超话的 `gid` 需要提前用浏览器抓包获取，不是话题 id。建立超话白名单时一并记录即可。
- **验证码**：首次长时间未活动后较容易触发文字验证码。接入一个 simple 的打码服务或者图形识别在 Agent 流里不划算，最终选择降低单日发送上限（每天 3 条），并用随机时间窗口规避。

## 可复用建议

1. **cookie 持久化与刷新**：把 cookie 放在 OpenClaw 的 Secrets 中，写一个简单的状态页监控剩余有效期，手动刷新成本更低。
2. **状态文件纳入版本控制**：`sync_state.jsonl` 和 `rate_limit.json` 都定期 git commit，避免本地丢失后重发。
3. **灵活的频率窗口**：超话限频策略可能变动，将窗口时长和最大次数作为配置项，不要硬编码。
4. **图片预处理流水线**：在 Agent 中加入图片尺寸缩放、压缩和格式转换步骤，防止上传环节出错。
5. **失败告警**：对于连续失败两次的文章，标记为 `error` 状态并推送一条个人私信，避免沉没。

## 总结

这套微博超话同步方案，通过组合 HTTP 图片上传、限流控制器和状态归档，目前已平稳运行两个月，零封号、零重复。整个过程没有依赖不可控的第三方 API，仅用 OpenClaw 的定时调度和 Agent 编排就把繁琐的重复劳动固化成了可维护的自动化脚本。如果你也有类似的多平台分发需求，上述三个模块的实践应该可以直接复用或参考。
