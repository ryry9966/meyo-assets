## 背景

团队每天站会前需要汇总 Git 提交、CI 流水线、线上错误日志和任务系统变更。人工整理大约要 40 分钟，而且容易漏掉关键失败项。我们基于 OpenClaw 的定时任务、MCP 工具和插件能力，做了一条日报流水线：定时采集多源日志，先归一化成结构化事件，再交给 LLM 生成固定格式日报，最后推送到 IM。

## 问题

原始日志有三个典型问题：

1. 异构：Git log、CI 输出、监控告警的数据结构完全不一样。
2. 噪声大：CI 日志里大量依赖下载、缓存命中；Git 里混着自动格式化提交。
3. 上下文超限：一天下来原始日志可能几 MB，直接塞给模型会超出 token，且模型容易被旧信息干扰。

所以核心工作不是“写 prompt”，而是先做一层数据收口，把原始日志转成“事件流”。

## 做法

### 1. 采集层：统一事件模型

通过 MCP 工具连接各数据源。以 Git 和 CI 为例：

- Git MCP 拉取当天 commit；
- CI API 拉取流水线状态；
- 监控 MCP 查询错误数和告警列表；
- 任务系统拉取状态变更。

每个源输出统一结构：

```json
{
  "source": "ci",
  "time": "2026-01-15T10:23:00+08:00",
  "title": "api-server 构建失败",
  "detail": "单测 TestLogin 超时，logs/ci-20260115.log",
  "severity": "high",
  "link": "https://ci.example.com/build/1234"
}
```

### 2. 预处理层：降噪与截断

写一个 Python 脚本或 OpenClaw 插件做清洗，规则包括：

- 过滤依赖下载、构建缓存、自动格式化提交；
- 合并同一错误在多个步骤中的重复记录；
- 每个源最多保留 80 条，按时间和严重度排序；
- detail 截断到 300 字符；
- 正则脱敏 token、手机号、内网 IP。

处理后的 JSONL 通常从几 MB 降到 30–60 KB。这个中间事件层是整条流水线最关键的部分。

### 3. 生成层：结构化输出

把 JSONL 交给 LLM，使用固定模板要求输出 JSON：

```json
{
  "summary": "一句话摘要",
  "completed": [],
  "in_progress": [],
  "risks": [],
  "tomorrow": []
}
```

Prompt 中明确：只使用给定事件；不要推测；缺失项返回空数组；输出必须是合法 JSON。提供 1 个 few-shot 示例，以及 JSON schema 校验。

### 4. 投递层：推送与归档

生成结果通过 IM 插件发到团队群，同时落一份 Markdown 到知识库，便于每周回顾。

OpenClaw 侧的任务配置大致如下：

```yaml
trigger:
  schedule: "0 18 * * 1-5"
  timezone: "Asia/Shanghai"
steps:
  - id: collect
    type: mcp
    server: git
    tool: list_commits
    timeout_seconds: 120
  - id: normalize
    type: script
    file: scripts/normalize_events.py
  - id: generate
    type: llm
    template: prompts/daily_report.j2
    output_schema: schemas/daily_report.json
  - id: deliver
    type: plugin
    plugin: im_push
```

## 踩坑点

- **MCP 超时**：CI 接口经常超过默认 30 秒。给采集步骤设置 120 秒超时，并让单源失败不阻塞整体。失败源写入空数组，日报标注“未采集到”。
- **时区偏差**：容器默认 UTC，18 点触发实际是北京时间凌晨 2 点。必须在 schedule 里显式设置 `timezone: "Asia/Shanghai"`，并且查询时用绝对时间范围。
- **模型输出漂移**：要求 JSON 但模型偶尔包 ` ```json ` 代码块或加注释。后处理先提取 JSON，再 schema 校验；失败重试一次，仍失败则降级为纯文本模板。
- **上下文污染**：如果事件里没带时间戳，模型会把旧错误当成今天发生。统一事件模型必须强制带 `time`，并在 prompt 中限制只处理当日事件。
- **敏感信息泄露**：日志里可能带 token 和手机号。预处理阶段必须做脱敏，不能只靠模型自觉。

## 可复用建议

1. 先做中间事件层，不要让模型直接接触原始日志。事件层稳定后，换模型、换模板成本都很低。
2. 模板与数据分离。日报模板单独维护，数据用 JSON schema 约束。
3. 保留人工确认环节。初期先推到草稿频道，稳定后再推送正式群。
4. 记录每次生成的输入 hash、输出和失败原因。出现“为什么日报说这个完成了”时能快速回溯。
5. 控制 token 成本。每日事件控制在 200 条以内，detail 截断，短上下文模型通常足够。

## 总结

这条流水线的核心不是“让 AI 写日报”，而是把异构日志先收口成结构化事件流。OpenClaw、MCP 和插件负责连通与调度，预处理脚本负责降噪，LLM 只负责最后的组织表达。跑稳之后，日报从人工 40 分钟变成每天约 5 分钟抽查确认。
