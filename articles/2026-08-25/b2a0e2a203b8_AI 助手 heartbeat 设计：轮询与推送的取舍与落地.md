## 背景

在 OpenClaw 插件、Agent 编排以及 MCP 工具链里，heartbeat 几乎是绕不开的基础组件。节点是否在线、任务执行器是否存活、插件连接是否已断开、长连接是否被中间设备静默回收，这些问题都需要一个轻量机制来回答。

## 问题

heartbeat 通常有两种实现路径：

- **轮询（Polling）**：客户端每隔固定时间请求一次健康检查接口，服务端被动响应。
- **推送（Push）**：服务端通过 WebSocket、SSE 或 TCP keepalive 主动发送心跳帧，客户端根据接收间隔判断连接健康。

轮询实现简单、无状态、易于水平扩展，但存在延迟与资源浪费：间隔太短会产生大量无效请求，间隔太长又无法及时发现故障。推送延迟低、带宽占用小，但需要维护长连接，处理断线重连、连接数限制、背压等问题。

我经历过一个典型场景：某个 OpenClaw 插件通过 MCP server 向 Agent 暴露任务状态。最初为了快速上线，客户端每 5 秒轮询一次 status 接口。小规模跑通后，节点数增长到几十个，服务端 QPS 开始升高；更麻烦的是在移动端或代理网络下，轮询请求会被系统延迟，导致状态更新滞后。后来改为 SSE 推送，延迟明显降低，但引入了新坑：连接在 NAT 后 60 秒左右被静默断开，客户端却不知道，导致“假在线”。

## 做法/步骤

1. **先明确心跳目的。** 是只做存活检测，还是同时携带任务进度、租约续期？如果同时做业务状态同步，建议将心跳与业务事件分离。
2. **选择模式。** 低频状态同步可以继续用轮询，间隔 10–30 秒；高频事件或需要实时感知的上线/下线，优先使用推送。已有 WebSocket/SSE 基础设施时可以默认推送；否则先轮询，稳定后再局部升级。
3. **参数设计。** 轮询间隔建议 10–30 秒，超时阈值取 `max(3 个间隔, 网络抖动上限)`。引入随机抖动（jitter），避免大量客户端同时请求造成惊群。
4. **推送实现。** WebSocket 或 SSE 心跳帧可以设置 ping/pong 或服务端定期发送最小事件。客户端侧用单调时钟记录 `last_seen`，超过阈值则主动断开并重连。重连使用指数退避加随机抖动，上限 30–60 秒。
5. **保留降级通道。** 无论推送多稳定，都建议保留一个低频轮询健康检查作为兜底。当推送连接异常或服务端只支持 HTTP 时，客户端可以自动降级为轮询。

## 踩坑点

- **NAT/网关静默断开**：长连接被中间设备断开，客户端感知不到。必须设置应用层心跳间隔小于 NAT 超时（常见 60 秒），并启用 TCP keepalive。
- **重试风暴**：多个客户端同时重连会打满服务端连接队列。重连延迟必须加随机抖动，避免同步。
- **时间不同步**：不要使用对端返回的时间戳做超时判断，应使用本地单调时钟计算间隔。
- **推送连接数限制**：大规模节点下，服务端维持大量长连接会占用文件描述符和内存。可以考虑按需订阅或网关聚合。
- **轮询延迟与 QPS 平衡**：不要为了追求实时把轮询间隔设到 1 秒，这样会迅速榨干服务端。必要时应改为推送。
- **僵尸节点**：心跳正常但业务已卡死。心跳包应携带轻量指标（如最后任务执行时间、队列深度）或使用租约机制。

## 可复用建议

- 心跳响应保持轻量，避免在健康检查接口里做数据库查询或复杂计算。
- 将 heartbeat 做成独立组件，业务模块只订阅状态变更，不直接依赖心跳实现。
- 对心跳丢失做连续失败计数，避免瞬时网络抖动导致误判下线。
- 在 OpenClaw 插件中，如果 MCP server 支持 notifications/事件，优先用推送传递状态变更；否则退回轮询。
- 监控三个关键指标：心跳延迟、丢失率、重连次数。它们能提前暴露网络或服务端问题。

## 总结

轮询与推送不是对错之分，而是不同约束下的取舍。轮询简单可靠但延迟和资源成本高；推送实时高效但连接管理复杂。工程上比较务实的路线是：先用轮询跑通，明确延迟和资源瓶颈后，对关键链路升级为推送，并保留轮询作为降级兜底。大多数稳定系统都不是纯轮询或纯推送，而是两者混合，配合合理的超时、退避和监控，才能在不牺牲简单性的前提下获得可接受的实时性。
