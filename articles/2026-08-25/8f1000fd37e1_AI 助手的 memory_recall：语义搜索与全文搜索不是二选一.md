# 背景

给 OpenClaw、Agent 或 MCP 插件接长期记忆时，最常见的做法是把历史记录、文档、操作日志切片后做 embedding，再通过向量相似度召回。这个路径在演示里效果不错，但落到生产环境，memory_recall 经常在两个场景翻车：

- 用户问“那个 OOM 报错后来怎么处理的”，向量召回返回的是 timeout、内存泄漏、pod 重启等一堆相关但非精确的结果。
- 用户问“上次支付回调失败那次，改了哪个配置”，语义搜索可能被“支付”“回调”“失败”这些泛化词带偏，反而找不到配置项里的精确字段。

问题不在于语义搜索不好，而在于 **memory_recall 不是单一检索问题**。它同时需要精确匹配和模糊理解。全文搜索和语义搜索各管一段，硬要用一个替代另一个，召回质量就会忽高忽低。

# 问题

## 语义搜索适合什么

- 同义表达：用户说“服务挂了”，记忆里写的是“nginx worker process exited”。
- 跨语言或口语化复述：比如“那个下单接口突然变慢”对应记录里的“order api p99 latency spike”。
- 没有明确关键词，需要靠上下文找回记忆。

## 全文搜索适合什么

- 精确 token：错误码、容器名、接口路径、UUID、版本号、环境变量名。
- 日志片段：例如 `read: connection reset by peer`。
- 配置项或命令：如 `max_connections=200`。
- 需要可解释、可定位到原文的场景。

如果一个 query 里带精确标识符，语义搜索很容易把它“模糊掉”。如果把 `POST /api/v1/orders` embedding 后检索，可能会召回 `GET /api/v2/order` 这类近邻，但它不是用户想要的。相反，如果用全文搜索去匹配“上次那个服务挂了怎么处理的”，就会因为中文分词和同义表达问题召回失败。

# 做法/步骤

在 OpenClaw 的 memory 模块里，我目前采用双通道召回，不把所有压力都放在向量库上。

1. **记忆写入时分类**  
   将记忆内容拆成两个字段：`text` 存原文，`keywords` 存标准化关键词，比如错误码、服务名、接口路径、配置项。写入时同时更新全文索引和向量索引。

2. **全文索引选型**  
   小规模直接用 SQLite FTS5 足够，不必上 Elasticsearch。如果已有 Meilisearch 或 Typesense，也可以复用。关键是要保留原始 token，不要被默认分词切碎。

3. **recall 入口做 query 分析**  
   在调用 embedding 之前，先做一层规则判断：  
   - 如果 query 包含错误码、路径、UUID、版本号等模式，先执行全文检索，并把命中的结果加权置顶。  
   - 如果 query 是自然语言问句，没有明显精确标识符，再交给语义检索。

4. **混合召回与合并**  
   全文 top 10 + 向量 top 10，合并后做一次轻量 rerank。如果无法引入 rerank 模型，也可以用规则合并：精确 token 命中优先，语义相似度作为次要排序依据。

5. **元数据过滤优先**  
   不要一上来就全库向量搜索。先根据时间范围、会话、来源、用户权限过滤，再在小范围内召回。这样既能降低延迟，也能减少噪音。

6. **回归评估**  
   准备 30～50 条真实 query，标注理想记忆片段，对比 recall@k。特别是要覆盖错误码、路径、配置项这类精确场景，否则评测指标会虚高。

# 踩坑点

- **纯向量搜索对精确标识符不可靠**  
  一旦 memory 里出现 `OOM`、`503`、`/v1/orders` 这种短 token，embedding 很容易把它们和相似但不相同的内容混淆。结果看起来相关，实际不可用。

- **中文全文搜索默认分词不理想**  
  SQLite FTS5 默认 tokenizer 对中文支持有限，英文错误码、路径、下划线字段容易被切碎。需要配置自定义分词，或者额外存储一份不做分词的 `keywords` 字段。

- **把全文搜索当成“落后方案”**  
  很多项目一上 embedding 就完全抛弃关键词检索，导致精确场景全部退化。实际上，规则 + 全文 + 语义的组合往往比单用向量召回更稳。

- **只看语义相似度分数，不看召回来源**  
  memory_recall 返回结果时如果不带来源和匹配类型，排障时很难判断是语义偏差还是全文分词问题。建议接口里保留 `match_type` 和 `score`。

- **忽略写入成本**  
  每条记忆都做 embedding 写入，会带来额外延迟和成本。小规模场景可以用本地 fastembed 或轻量模型，不必每条都调用高成本 API。

# 可复用建议

- **默认双通道，不要二选一**。全文负责精确，语义负责泛化，两者合并后再排序。
- **精确 token 命中时，优先相信全文结果**。即使语义分数更高，也不应覆盖精确匹配。
- **给 memory_recall 加 hard filter**。时间衰减、会话绑定、权限过滤应该放在召回之前，而不是召回之后。
- **保留原文和关键词字段**。关键词字段可以帮助全文检索，同时避免 embedding 对短 token 的失真。
- **用真实 query 做回归**。如果没有覆盖精确标识符场景，评测结果会偏向语义搜索，但线上不一定好用。

# 总结

语义搜索和全文搜索不是替代关系，而是两种匹配器。语义搜索解决“意思相近”，全文搜索解决“原样命中”。在 OpenClaw/Agent 的 memory_recall 里，比较务实的路径是：先做规则和全文，再补语义，最后用混合召回和评估收口。这样比一上来就全量 embedding 更可控，也更能在真实自动化场景里稳定工作。
