## 背景：为什么 AGENTS.md 不是“另一个 README”

在 OpenClaw 里接 MCP、插件和自动化任务后，最先失控的往往不是模型能力，而是工作空间上下文。AI 会默认用通用经验猜测项目结构：把 `src/` 当成唯一源码目录、跳过 `justfile` 里的封装命令、在你不希望它碰的 `data/raw/` 里做批量重命名。

AGENTS.md 解决的不是“介绍项目”，而是“约束代理行为”。它和 README 的区别很直接：README 写给人看，AGENTS.md 写给 AI 执行者看。前者可以讲愿景、背景、贡献指南；后者只需要回答一个问题——**在这个目录里，AI 应该怎样正确地开始工作。**

我最初没有维护 AGENTS.md，结果 OpenClaw 在跑一个日志清洗任务时，直接用系统 `find` 扫描了包含大型二进制缓存的目录，拖慢整个 session。后来加了明确的“目录禁区”和“优先命令”，同类问题没有再出现。

## 问题：没有边界说明时，Agent 会做什么

比较常见的有四类：

1. **命令选择错误**：不读项目自带的任务封装，直接用底层命令拼参数。
2. **目录权限越界**：对 `vendor/`、`node_modules/`、`data/raw/` 做修改，污染依赖或原始数据。
3. **忽略 MCP/插件约定**：比如项目规定通过某个 MCP 服务访问数据库，但 Agent 自己去猜测连接串。
4. **产出格式偏差**：日志、报告、提交信息风格和团队习惯不一致。

OpenClaw 本身会读取工作空间中的规则文件，但没有任何规则文件时，它只能依赖模型默认行为。AGENTS.md 的本质，是让“默认行为”变成“被明确授权的行为”。

## 做法：一个可落地的 AGENTS.md 结构

我的实践是把文件放在项目根目录，命名为 `AGENTS.md`，并保持 100–200 行以内。太长会被截断或稀释注意力，太短则失去约束力。

推荐五段式结构：

### 1. 一句话定位
说明这个项目是什么，以及当前目录对 AI 的总体要求。例如：
> 这是一个数据管道仓库，所有修改必须保持 CLI 可复现，禁止交互式操作。

### 2. 目录边界
用极短列表声明“可改 / 只读 / 禁止进入”。不要写成长篇目录树，AI 需要的是判断依据，不是文档。
```markdown
- 可修改：`src/`、`tests/`、`config/`
- 只读：`data/raw/`、`vendor/`
- 禁止进入：`.secrets/`、`build-cache/`
```
这类信息比 README 中的“项目结构”更可执行，因为它是明确的权限表。

### 3. 常用任务入口
优先列出封装命令，而不是底层命令。例如：
```markdown
- 运行测试：`./scripts/test.sh`
- 构建镜像：`just build`
- 查看任务状态：通过 `task-mcp` 服务查询
```
如果某个任务必须走 MCP 或插件，明确写“不要绕过”。这是防止 Agent 自行拼接命令的关键。

### 4. 代码与提交约定
只写和 AI 产出直接相关的规则：提交信息格式、代码风格、是否需要追加变更说明。不要复制整个 style guide，链接过去即可。

### 5. 禁止事项
用“不要”列表收尾，比正向描述更难被忽略。例如：
- 不要修改 `data/raw/` 下任何文件
- 不要在未确认前执行 `git push --force`
- 不要直接读取 `.env` 内容用于回显

## 踩坑点：AGENTS.md 不是越全越好

第一个坑是**把 AGENTS.md 写成文档镜像**。我见过有人把整个 README 复制进去，结果 OpenClaw 在处理复杂任务时，关心的是规则而不是背景介绍，长段描述被忽略，真正重要的命令反而没被读取。

第二个坑是**规则过期**。项目切换了测试框架，但 AGENTS.md 里的命令还是旧的。Agent 会严格照做，造成更隐蔽的错误。解决办法很简单：把 AGENTS.md 的更新纳入常规代码评审，项目结构变化时先改它。

第三个坑是**与插件配置冲突**。OpenClaw 的插件或 MCP 服务可能自带指令，AGENTS.md 中如果写相反规则，Agent 可能产生矛盾执行。需要明确优先级，例如：
> 若与插件指令冲突，以本文件为准，除非任务明确要求使用插件配置。

第四个坑是**一次性写入后不再验证**。写完 AGENTS.md，最好跑一个小任务验证一下。比如让 OpenClaw 执行测试命令，观察它是否正确调用了 `./scripts/test.sh` 而不是自行生成 `pytest` 参数。

## 可复用建议

- **按环境拆分**：如果工作空间同时包含前端、后端、数据管道，用一个根 `AGENTS.md` 指向各子目录规则，而不是堆在一起。
- **保留“验证片段”**：在文件末尾附一个最小验证任务，例如“检查你是否使用了封装测试命令”，方便新 session 快速自检。
- **写规则时用否定加例外**：`不要修改 X，除非任务明确要求并且用户确认`。这样兼顾安全和灵活性。
- **把 AGENTS.md 纳入版本管理**：它应该和代码一起评审、一起提交，而不是放在本地未跟踪文件里。
- **留意上下文长度**：保持 AGENTS.md 精简，必要时用链接指向详细文档，而不是让每个 session 都负担全部内容。

## 总结

AGENTS.md 是 OpenClaw 工作空间里最便宜、最直接的约束层。它不替代 README，也不替代插件的系统提示，而是补上“这个具体目录下，哪些事情可以做、哪些事情不要做”的空缺。

工程环境里，AI agent 最大的问题不是“不会做”，而是“太会自由发挥”。AGENTS.md 的作用，就是把自由发挥限制在可预期、可复现的范围内。对 OpenClaw 用户来说，维护一份清晰、克制、持续更新的 AGENTS.md，比堆更多工具提示更有效。
