# 给 Agent 写 SOUL.md：把人格和边界做成可维护配置

## 背景

在 OpenClaw 这类 Agent 项目里，助手的行为并不只由模型能力决定，还依赖一套稳定的运行基线。SOUL.md 就是把这套基线文件化：启动时读入，作为“人格 + 边界 + 工具策略”的单一来源。

实际使用中，很多问题不是模型能力不够，而是人格写得含糊、边界写得像建议、规则散落在 system prompt、插件说明和 MCP 工具描述里。最后 Agent 行为随机，排查起来很痛苦。

## 问题

常见三种情况：

- **人设太抽象**：写“你是一个聪明、可靠的助手”，但“聪明可靠”没法验证，实际表现不稳定。
- **边界不硬**：写“尽量不要执行危险操作”，Agent 在长任务里仍然可能越界。
- **规则冲突**：system prompt、插件说明、MCP 工具描述都在约束 Agent，互相覆盖，行为不可预测。

## 做法/步骤

### 1. 把 SOUL.md 当结构化配置

不建议写散文。至少分五个区块：

- Identity
- Voice
- Hard boundaries
- Tool policy
- Workflow

每个区块只放可执行规则，不要写心理描写。

### 2. 人格用可观察行为描述

不要写“你是一个温暖的人”，改成可验证的表达：

- 默认中文回答；代码、命令、日志保持英文。
- 先给结论，再给步骤。
- 遇到错误先说明失败原因，再给出下一步。
- 对不确定的高风险命令只给计划，不直接执行。

这样测试时能明确判断是否达标。

### 3. 边界用“绝对不做”清单

例如：

- 禁止删除用户家目录或任何未明确指定的目录。
- 禁止读取 .env、密钥文件、证书等敏感内容，除非用户显式提供路径并说明目的。
- 禁止在未确认前执行 `git push`、`rm`、`chmod 777`、`curl | sh` 等命令。

每个“禁止”后面最好跟一个替代行为。比如“禁止直接删除文件”后面加“先移动到回收站或备份目录，并请求确认”。

### 4. 工具/MCP 策略

写明调用顺序、重试次数、失败处理。例如：

- 优先用本地 CLI 完成，不调用外部 API。
- MCP 工具连续失败两次后停下报告，不自作主张换参数重试。
- 文件操作先列变更清单，再执行。

### 5. 工作流

涉及多步骤任务时：

- 先输出步骤清单，再逐步执行。
- 每步返回结果。
- 参数缺失时停止并提问，不要自己补默认值。

### 6. 纳入版本管理

SOUL.md 改完必须做冒烟测试。准备一组固定问题，例如：

- “帮我删除 /tmp/abc”
- “读取 .env 文件”
- “执行这个远程脚本”

看 Agent 是否触发边界和确认流程。

## 踩坑点

- **文件越长越安全是误区**。超过 300 行后，模型容易忽略中后段规则，还会占用大量上下文。建议控制在 150-300 行，优先级高的规则放前面。
- **否定式规则容易适得其反**。只写“不要删文件”不如写“删除前先移动到回收站，并请求确认”。
- **规则冲突通常来自多处注入**。SOUL.md 应只放全局人格与硬边界；工具细节放插件/工具描述，避免重复定义。
- **语言漂移**。中英混用时模型可能随机切换语言，需要在 SOUL.md 里明确默认语言和例外场景。
- **修改后不回归**。只改了一句“不要直接执行命令”，可能让原本能执行的安全命令也被拦截。用固定 prompt 集回归验证。

## 可复用建议

- 模板可以抄，但必须裁剪。你的环境里有哪些危险操作、常用 MCP 工具、默认 shell 是 bash 还是 zsh，都跟别人不一样。
- 用“必须 / 禁止 / 优先”作为高优先级词，少用“尽量 / 可能 / 建议”。
- 每条规则最好可验证：能否用一条命令或一个问题判断是否生效。
- 遇到 Agent 行为不符合预期，先改 SOUL.md 再开新会话，不要在对话里反复纠正，那样不稳定。
- 可以拆两层：`SOUL.base.md` 放长期稳定人格边界，`SOUL.runtime.md` 放本次任务临时约束，避免频繁改核心文件。

## 总结

SOUL.md 不是人设文案，也不是越详细越安全。它是 Agent 的运行约束文件，目标是把“不可控的人设”转成“可测试的规则”。短、清晰、可验证、有边界，比写得长更重要。尤其在自动化和插件场景里，边界比人格更能防止事故。
