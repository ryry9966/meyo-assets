## 背景

在 OpenClaw 或类似 Agent 项目里，能力膨胀是一个很现实的问题。早期做法是把所有工具说明、操作手册、常用命令全部塞进 system prompt，或者一次性注册几十个 MCP 工具。结果就是上下文占用高、响应变慢，模型还容易在工具选择时串台：用户只是问“最近一次构建为什么失败”，它却先调用了一大堆无关的 API，甚至读错了日志目录。

OpenClaw 的 Skills 机制提供的思路是：**能力常驻，但默认只加载索引，命中后再加载完整技能包**。也就是说，系统里可以放 30 个技能，但模型在一次对话里通常只需要看到其中一两个的详细内容。

## 问题

理想很直接，落地时通常会卡在三个地方：

1. 如何让模型准确判断“现在该加载哪个技能”？
2. 如何避免技能正文加载后又把上下文撑爆？
3. 多个技能职责重叠时，如何保持稳定选择，而不是每次随机选一个？

这些不是单纯靠多写 prompt 就能解决，需要在技能结构、索引设计和测试方式上做约定。

## 做法 / 步骤

### 1. 先划分技能边界，而不是先写文档

建议一个技能只解决一类任务。例如：

```text
skills/
  git-release/
    SKILL.md
  incident-response/
    SKILL.md
  sql-query-audit/
    SKILL.md
```

不要创建万能技能。一个叫 `devops` 的技能里塞进发布、回滚、日志、监控、数据库，最终一定会变成一个小型手册，失去按需加载的意义。

### 2. 用 SKILL.md 的 frontmatter 做索引

OpenClaw 的 Skills 机制通常依赖每个技能目录下的 `SKILL.md`，其中 frontmatter 用于登记元信息。一个简洁的示例如下：

```markdown
---
name: git-release
description: 根据提交记录生成发布说明和 changelog
when_to_use: 用户要求生成 release note 或 changelog 时
requires: git
provides: release_note_generation
version: 1.0.0
---

# Git Release

## 前置检查
- 确认当前目录是 git 仓库
- 确认 main 分支与远端同步

## 执行步骤
1. 运行 `git log --oneline --decorate`
2. 过滤出 merge commit 和 feat/fix 记录
3. 按模板生成 changelog
4. 不直接推送，先输出草稿供确认
```

这个 frontmatter 就是索引。系统默认只需要加载这些元信息，不需要把正文塞给模型。

### 3. 在 OpenClaw 配置中开启技能扫描

以工程目录下的配置为例，通常可以这样声明：

```yaml
skills:
  enabled: true
  path: ./skills
  index_only: true
```

关键点是 `index_only` 这类模式：启动时只扫描 frontmatter 和技能列表，不把技能正文注入上下文。模型需要根据 `when_to_use`、`description` 判断是否触发。

### 4. 让模型按“索引匹配 → 加载 → 执行”的路径走

在 agent 的系统提示中，可以加入一个轻量的选择逻辑：

> 当用户请求与某个可用技能匹配时，先输出技能名称，再读取该技能的完整 SKILL.md，然后按其步骤执行。若无匹配技能，使用通用流程。

这样做的目的是把“选择技能”和“执行技能”拆开。模型不需要一开始就携带所有技能的操作细节，只需理解每个技能大概能干什么。

### 5. 为触发词做正反例测试

技能写完后，至少准备一批测试输入，例如：

- “帮我整理最近的发布说明” → 应命中 `git-release`
- “最近有什么新功能” → 可能不应触发技能，只做普通总结
- “回滚到上一个版本” → 如果已有 `rollback` 技能，不应误触发 `git-release`

把误触发和漏触发都看作 bug。

## 踩坑点

### 1. 索引描述写得太宽

如果 `when_to_use` 写成“用户需要帮助时”，那这个技能会被频繁误加载。建议控制在 20～40 个词以内，同时给出明确场景，而不是抽象意图。

### 2. 技能正文还是太长

索引轻量了，但正文如果动不动几百行，加载一次就可能吃掉大量 token。技能正文应保留操作步骤、命令模板、校验规则和异常分支，不要放历史背景、长篇说明或与当前任务无关的文档。

### 3. 缺少退出条件

很多技能只写 happy path，模型一旦加载后，即使中途发现不适用，也会硬套步骤。每个技能最好写明“不适用场景”或“前置检查失败时停止”。

### 4. 技能职责重叠

例如 `release` 和 `changelog` 两个技能都能处理发布说明，模型可能随机选择一个。解决办法是合并，或者在索引里明确互斥关系。

### 5. 配置了 `index_only` 但没有给模型查看技能列表的能力

如果模型根本不知道有哪些技能，索引就没意义。需要确保系统提示或工具能返回可用技能列表，而不是只靠模型猜。

## 可复用建议

**把“轻量索引”和“完整技能”当成两个不同资产来维护。** 改索引时只考虑“是否能被准确命中”，改正文时只考虑“执行步骤是否可复现”。

**给技能做版本管理。** frontmatter 里保留 `version`，技能正文变更后跑一轮触发测试，避免看起来只是改文案，实际影响了选择结果。

**结合 MCP 工具做权限边界。** Skills 适合承载流程知识和操作模板，敏感凭证、高风险操作仍应通过 MCP 工具或外部授权执行，技能本身不要替代权限控制。

**记录加载指标。** 每次技能被加载时记录技能名、token 占用、是否执行成功。运行一段时间后，你就能发现哪些技能其实很少被用到，哪些技能误触发率高。

## 总结

OpenClaw 的 Skills 机制不是简单地给 AI 助手加一堆知识卡片，它的核心价值在于**把能力从常驻上下文中解耦出来，按需装载、用完即走**。要让它稳定工作，更重要的是建立清晰的技能边界、轻量索引、加载策略和回退路径。

工程上最值得投入的不是写更多技能，而是把“何时加载、加载什么、加载后如何退出”这三个问题在机制里固化下来。这样，Agent 才能在上下文占用和实际能力之间保持平衡，而不是在系统提示和工具列表里继续堆东西。
