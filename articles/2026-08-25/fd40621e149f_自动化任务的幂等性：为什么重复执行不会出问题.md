## 背景：重试、重放与重复触发是常态

在 OpenClaw/Agent/MCP/插件自动化实践里，任务不会总按理想路径只执行一次。调度器可能抖动，Agent 可能因为模型超时重试同一个工具调用，MCP server 可能收到客户端重放，插件热加载后也可能重新跑一遍初始化逻辑。把“一次执行”当成默认假设，通常会在某个凌晨被重复工单、重复消息或重复写库打醒。

幂等性不是新概念，但自动化链路拉长后，单点幂等很难兜住全链路。一个任务从触发器到 Agent 再到 MCP 工具，最后落库或调用外部 API，只要有一环重复，最终效果就可能重复。

## 问题：重复执行到底坏在哪

重复执行不一定坏。查询类操作天然幂等，例如读取当前状态、搜索文档。真正危险的是有副作用的操作：

- 创建资源：重复创建 issue、工单、群组、文件
- 发送通知：重复发消息、邮件、webhook
- 外部写操作：重复调用支付、开票、CRM
- 状态推进：把已完成的订单又推进到下一状态

一个典型场景：Agent 调用 MCP 的 `create_ticket`，工具返回超时但实际已创建成功。Agent 会重试，结果同一问题生成了两张工单。问题不在重试，而在工具没有暴露幂等语义。

## 做法：让重复执行变得安全

### 1. 入口生成幂等键

在任务或工具调用入口生成唯一 key，例如基于事件 ID、任务 ID、操作类型和业务主键生成确定性 ID。不要用随机 UUID 作为业务幂等键，因为重试时会变。可以用：

- `task_id + step_name + business_id`
- 外部事件的 `event_id`
- 内容哈希：对核心参数做 SHA-256 截断

这个 key 贯穿后续所有环节。

### 2. 存储层做唯一约束

如果最终要写数据库，给幂等键加唯一索引。重复插入会失败，捕获后返回已有结果即可。PostgreSQL 示例：

```sql
CREATE UNIQUE INDEX uniq_ticket_idempotency_key
ON tickets (idempotency_key);
```

应用层插入前先查，或直接插入并捕获唯一冲突。并发下先查再插不可靠，唯一索引才是底线。

### 3. 工具层明确支持幂等键

MCP server 的工具如果能接收 `idempotency_key` 参数，应该把它传给下游 API 或存储。很多外部 API 支持 `Idempotency-Key` 头，例如部分支付和工单平台。如果不支持，就自己在 server 内维护一个 request 表：

```text
request_id  unique
response    jsonb
status      created/done
```

收到重复 request_id 时直接返回缓存的 response，不再执行副作用操作。

### 4. 状态机用条件更新而不是盲写

如果任务会推进状态，不要直接 `UPDATE order SET status='paid' WHERE id=?`。这样重复执行会覆盖其他状态。改成条件更新：

```sql
UPDATE orders
SET status='paid', paid_at=now()
WHERE id=? AND status='pending';
```

影响行数为 0 说明已经不是 pending，重复调用可以安全跳过。这种“比较并交换”是幂等推进的核心。

### 5. 外部回调按事件 ID 去重

如果自动化任务接收外部 webhook 或消息回调，不要只按内容判断是否处理过。同一事件可能被平台重推。应当记录 `event_id`，处理前先插入 event 表并检查唯一约束，或者用 Redis `SETNX` 抢锁标记。

## 踩坑点

- **只在前端或 Agent 层做防重**：重试可能绕过入口，真正防线要在存储或工具侧。
- **用时间戳做幂等判断**：同一秒可能有多个请求，且时钟漂移会造成漏判。
- **先查再插的竞态**：两个并发请求都查到不存在，然后都执行副作用。唯一索引/原子操作才能避免。
- **把随机 UUID 当幂等键**：每次重试生成新 UUID，等于没有幂等。
- **忽略下游不幂等 API**：本地幂等了，但下游 API 不支持，重复调用仍然危险。需要包装一层，本地记录请求状态并对账。
- **只处理成功重复，不处理部分失败**：有些操作可能创建了资源但响应丢失，重试时如果直接报错而不是返回已有资源，会造成卡死。捕获唯一冲突并查回原记录是好习惯。

## 可复用建议

1. 每个有副作用的 MCP 工具都定义 `idempotency_key` 参数，即使暂时不用也要留位置。
2. 任务入口统一生成确定性 key，不要散落在业务代码里。
3. 数据库层面所有关键创建表都给业务幂等键加唯一约束。
4. 对外部 API 调用包装一层 request/response 缓存，按 request_id 幂等。
5. 测试时故意重复执行同一任务 2-3 次，观察是否产生重复副作用。这个测试比单元测试更能暴露问题。
6. 如果暂时无法做到全链路幂等，至少在文档里标注哪些操作是幂等的，哪些不是，避免 Agent 误判。

## 总结

自动化任务幂等性的本质，是承认“任何请求都可能被重复投递”，然后把防线放在最不容易被绕过的位置：存储约束、条件更新和工具层协议。不要指望调用方自觉，也不要把随机性误认为幂等。一个稳定的 OpenClaw/MCP 自动化链路，应该能在重试、重放和重复调度下产生相同的外部效果，而不是“不出错但重复了一堆东西”。

重复执行不会出问题，不是靠运气，而是靠每一层都留好幂等键、唯一约束和条件写。
