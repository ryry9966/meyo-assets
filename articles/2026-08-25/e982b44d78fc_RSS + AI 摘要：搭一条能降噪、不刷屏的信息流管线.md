## 背景

RSS 没有消失，它只是退回了基础设施的位置。对做自动化的人来说，RSS 仍然是成本最低的稳定输入：结构简单、可轮询、可去重。真正的麻烦不在“能不能抓到”，而在订阅数上来以后，未读列表变成另一种噪音。AI 摘要的意义也不是替你读完所有文章，而是把“值得读原文”的信号提前压缩出来。

这条管线我在 OpenClaw 里用 Agent 做调度，抓取、清洗、摘要、推送拆成独立工具。目标很明确：增量、幂等、少打扰、可回查。

## 问题

实际跑起来主要会遇到三类问题。第一，重复和伪更新：有些源 guid 不稳定、有些靠标题哈希、有些改了发布时间就重发。第二，AI 摘要容易啰嗦或脑补，尤其低质量源信息不足时模型会自己补常识。第三，推送节奏失控：逐篇推会刷屏，积压到晚上一起推又会把噪音重新聚集。所以实现上不是简单“RSS 解析 + 调一次 LLM”。

## 做法

### 1. 源与采集

维护一份 JSON 或 OPML 列表，每个源包含 name、feed_url、category、tags、enabled、health。fetcher 独立定时跑，设置 UA、超时和最大体积。解析后只保留 title、link、guid、summary、published、content 字段。采集阶段不做全文抓取，避免把管线拖死在慢源上。

### 2. 清洗与去重

用 link 或 guid 做主键，缺失时用 title + published 做哈希兜底。HTML 清洗要移除 script、style、nav 和广告节点，正文截断到可控长度。过滤规则：正文少于 200 字、纯视频/图片、命中标题党词表、与最近 N 条重复。状态写入 SQLite 或 KV，保证任务重跑不会重复处理。

### 3. AI 摘要与分类

批量处理，每次 5-10 条。提示词固定输出 JSON，例如 summary 为三点、每点不超过 25 字，tags 最多 3 个，score 1-5，need_read 布尔值。正文只取前 1500 字符，temperature 调低。关键约束是“只依据原文，无法判断就写信息不足”，这能明显减少脑补。解析 JSON 时允许截断和重试一次，不要把一次坏输出变成整批失败。

### 4. 推送与调度

OpenClaw Agent 按固定节奏执行，支持 dry-run。推送按分类合并，每半天或一天发一条摘要，而不是逐篇推。need_read 高的条目单独放一组，但同样合并后推送。静默时段和本地时区要在调度里写死，避免夜间提醒。

## 踩坑点

- **相对链接**：摘要里、正文里的 href 很多是相对路径，必须用 urljoin 转成绝对地址，否则推送出去全是死链。
- **缺 guid**：有些源完全不给 guid，只用 link 兜底；有些 link 会带同一篇文章的不同 UTM 参数，需要先归一化。
- **模型脑补**：对低质量源，模型会补出文章里没有的结论。约束要写进提示词，并且保留原文链接让用户自行判断。
- **全文抓取**：不要在采集阶段做。可以在分数高时异步补抓，但要设置超时和最大正文长度。
- **任务重入**：定时任务可能上一次还没跑完下一次就启动，用锁文件或数据库锁防止并发。
- **费用和限流**：源多时 LLM 成本上升很快。可以先按长度和标题词过滤，小模型做初筛，大模型只处理高价值条目。
- **推送噪声**：即使是摘要，逐条推送也会打扰。合并摘要才是降噪的关键。

## 可复用建议

- 输出必须结构化，但人读的摘要正文也要留存，方便后面搜索。
- 每条记录保留 raw 和 cleaned 两个版本，排障时能区分是源的问题还是清洗的问题。
- 源健康度要落地：连续 N 次失败就自动禁用并写日志，而不是让任务反复重试。
- 插件/MCP 拆分：把 fetch、clean、summarize、push 做成独立工具，Agent 只负责排程和异常处理，排障会简单很多。
- 先跑 dry-run：开真实推送前，先看一两天会产生多少条、哪些会被判 need_read，再决定频率和阈值。

## 总结

这条管线不追求聪明，只追求少打扰。RSS 负责稳定输入，AI 负责把长文压成短信号，Agent 负责节奏和异常处理。最终效果是：你不再需要刷一屏标题，只需要看一条合并摘要；想深入时，原文链接仍然在那里。对 OpenClaw 用户来说，最有价值的不是“接了一个大模型”，而是把摘要、推送、源健康度这些工程细节做扎实。
