“AI 开始替人类调用 AI，token 用量已是人类 5.2 倍。”这个数据刚出现时，很多人第一反应是“AI 觉醒了”。但拆开看，它更像一个 Agent 时代的基础设施信号：过去我们统计 token，数的是“人问、模型答”；现在越来越多请求的起点不是人类键盘，而是另一个模型。它替你查资料、调工具、写代码，再让另一个模型检查一遍。整条链路里，token 消耗自然翻着跟头往上涨。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-25/a499828daf43c993.png)

## 一、这 5.2 倍不是“AI 觉醒”，而是调用链变长了

一个典型的人类请求可能长这样：

- 用户输入：“帮我看看杭州明天天气，写进周报。”
- 人类侧 token 消耗：大约 20～40 token。
- 模型直接回答：大约 80～150 token。

但如果交给一个 Agent 完成，链路会变成：

1. 主模型理解任务，输出一个工具调用：查天气。
2. 工具返回 JSON 格式的天气数据，可能带一堆字段。
3. 主模型把天气数据重新读入上下文，开始写周报。
4. 写完后，它可能再调用一次“格式整理”工具，或让另一个模型做质检。
5. 每一步都要把 system prompt、历史对话、工具结果重新塞进上下文窗口。

所以一次任务从人类侧的 100 token，膨胀到 500～3000 token 并不稀奇。5.2 倍只是平均值，复杂任务里 20 倍也不夸张。

这其实不是“AI 自行其是”，而是 **AI 开始以调用者的身份进入系统**。过去工具是死的，现在工具背后也可以是模型；过去接口是给人看的，现在接口是给模型读的。调用链一变长，token 账单就变了。

## 二、Token 爆炸的五股“膨胀力量”

把 5.2 倍拆开，至少能看到五个技术性原因。

1. **系统提示词重复注入**  
   Agent 每调用一次工具或子模型，往往都要重新带上 system prompt。一个 system prompt 可能就占了 500～2000 token。如果任务需要 5 次工具调用，光“自我介绍”就重复烧了 5 遍。

2. **工具描述和 JSON Schema 太占地方**  
   Function calling 需要把每个工具的名称、参数、字段类型、描述塞进上下文。一个复杂 API 的 schema 可能吃掉 800 token，比用户原始问题还长。

3. **Agent Loop：边做边想，停不下来**  
   很多 Agent 采用 ReAct 模式，即“思考—行动—观察”循环。模型每走一步都要重新生成推理，再等工具返回。循环步数一多，上下文像滚雪球一样增长。

4. **自反思与自我纠错**  
   为了让结果更可靠，一些系统会让模型“先写一遍，再读一遍，再改一遍”。质量上去了，token 也翻三倍。这是典型的“用算力换准确率”。

5. **AI-to-AI 协议层的冗余**  
   当模型通过 A2A、MCP 等协议互调时，中间会夹带状态描述、能力声明、消息格式包装。这些对人类不可见，但都是 token。

## 三、Token 不是抽象数字，是钱、延迟和碳排放

很多人看到“5.2 倍”只会想到“AI 更厉害了”，但工程上它是一个成本信号。

- **成本**：按主流模型每百万 token 1～3 美元粗略计算，如果一家公司过去每天消耗 100 万 token，现在是 520 万，推理成本同步上涨。有些场景下，一个原本 0.01 美元的任务会变成 0.05 美元，毛利直接被打穿。
- **延迟**：多跳 Agent 是串行执行的。每一步都要等模型生成、工具返回、再进入下一步。用户等 3 秒和等 15 秒，体验完全不同。
- **能耗**：推理不是免费的热力学过程。虽然单次推理能耗不高，但高频、多跳、长上下文会放大数据中心负载。Token 效率不该只是财务指标，也应该是碳排指标。

不过也不是所有 token 都“花得冤”。很多膨胀是必要的：工具调用、反思校验、多模型协作确实能提升任务成功率。问题是，当 token 账单涨得比成功率快得多，就需要停下来看一下。

## 四、如何不让 AI 把 token 当成“免费自助餐”

如果系统里的 agent 开始大量调用其他模型，优先做的不是砍功能，而是压缩无谓消耗。

1. **上下文缓存和前缀复用**  
   相同的 system prompt、工具 schema 不要每次从零计算。把公共前缀缓存起来，命中后成本能显著下降。

2. **给工具描述“瘦身”**  
   写 Function schema 时像写简历：能一个字说清，就不要写一段话。字段描述、参数示例精简后，效果未必下降，token 可能省下 30%。

3. **限制 Agent 最大步数**  
   给 Agent Loop 设上限，比如一次任务最多 8 步。超了就强制返回当前结果，或在第 6 步让模型做一个“阶段性总结”。这能避免它在死循环里烧 token。

4. **模型路由**  
   不是每一步都用最大模型。简单意图分类、格式转换这类任务，用小参数模型足够；复杂推理再切大模型。分层路由可以把成本打下来。

5. **上下文压缩与记忆抽取**  
   长任务里，历史对话不要原样堆积。定期把旧信息压缩成摘要，或把关键实体抽出来放进工作记忆，能有效控制上下文长度。

工程师式提醒：如果你发现某个 agent 每次执行任务都像在给自己写小作文，第一步应该查 system prompt，而不是急着换更大模型。

## 五、冷思考：5.2 倍会继续涨吗？

短期看，AI 调用 AI 的比例大概率还会上升。Agent 从“单次问答”进入“任务执行”，多跳调用是刚需。但长期不会无限膨胀，因为经济理性会踩刹车。

- **成功率约束**：调用链太长，失败概率也会上升。多跳 Agent 的端到端成功率可能低于单步模型，用户不会为一个总是跑偏的任务持续付费。
- **自适应 token 预算**：越来越多框架会把 token 消耗作为优化目标之一，动态决定是继续循环还是提前收手。
- **缓存与端侧小模型**：公共部分缓存、轻量模型先做意图判断，都会把重复 token 压下来。

所以“5.2 倍”更像一个阶段性的结构变化：AI 从被调用者，变成了调用者。基础设施需要重新设计，而不是简单地把账单放大五倍。

## 写在最后：三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-25/23a7228d45008fc0.png)

1. **给 agent 设“token 预算”**  
   任何生产环境里的 agent 都应该有显式的步数和上下文长度上限。没有预算的自动调用，就像不给信用卡设额度。

2. **把工具描述和 system prompt 当成成本项**  
   重写一次工具描述，可能比优化模型参数更能省钱。先做 token 足迹分析，再决定从哪里动刀。

3. **监控“非人类调用占比”**  
   如果某天非人 token 突然翻倍，先别急着庆祝 AI 能干更多活了。很可能某个 agent 正在循环调用自己，顺便烧掉了下个月的云预算。
