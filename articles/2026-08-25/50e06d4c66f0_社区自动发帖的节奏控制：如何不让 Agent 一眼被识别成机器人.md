# 背景

在 OpenClaw 社区里，不少自动化实践会把 Agent、插件或 MCP 工具接上社区发布接口，用于发布版本更新、同步工单状态或定期推送技术笔记。刚开始通常很容易跑通：队列塞任务，定时器触发，HTTP 请求发出，返回 200。但跑几天后，账号可能被风控、删帖、禁言，或者被社区成员明显标记为 bot。

问题多数不是内容质量差，而是节奏不像人。本文整理一个可落地的节奏控制模块，重点处理发帖时间、行为序列和内容指纹。

# 问题：机器人感来自哪里

从实践观察，被识别为机器人通常有四个信号：

1. **时间规律过强**：固定每 30 分钟、整点、半点触发，时间分布过于均匀。
2. **动作序列单一**：登录→发帖→退出，缺少人类的阅读、停留、编辑、分段行为。
3. **内容指纹明显**：同一模板跨多个节点重复，标题句式一致，正文长度方差过小。
4. **缺乏反馈感知**：不根据帖子表现或社区活动调整频率，发完即走。

社区风控不一定公开规则，但上述特征很容易被统计模型或人工识别。所以方案不是加随机数这么简单，而是把发帖当作一个带有状态和约束的调度系统。

# 做法：把“节奏”做成显式模块

我在 OpenClaw 的自动化插件里拆出 `post_rhythm` 模块，包含四层：内容队列、时间调度、动作序列、熔断观察。

## 1. 内容队列与模板去重

发帖前先对内容做变形：保留语义，改变结构。可以根据节点或社区规则定义槽位，例如标题前缀、正文首句、结尾评论引导。每次从同义句库取不同组合，并做长度扰动。不要直接把同一段文案复制到多个板块。

示例配置：

```yaml
content:
  templates:
    - body: "更新了 {module} 的修复，主要变化是 {change}。"
      slots:
        module: ["任务调度器", "MCP 客户端", "日志采集"]
        change: ["减少延迟", "修正重试", "提高超时判断"]
  max_title_len: 42
  min_body_len: 200
  jitter_len_ratio: 0.12
```

## 2. 时间调度：抖动 + 冷却 + 会话化

不用固定间隔。将发帖时间建模为“活跃会话 + 休息期”。每个会话内可以安排 1-3 个动作，会话之间冷却时间随机。白天活跃、夜间低概率。示例：

```python
def next_delay(state):
    base = random.uniform(18, 45)  # 分钟
    if state.action_count > 3:
        base += random.uniform(40, 90)
    if local_hour in [2, 3, 4, 5]:
        base *= random.uniform(2.5, 5.0)
    return base * state.community_factor
```

关键不是绝对随机，而是让时间分布接近社区正常用户的节奏，避免“精确均匀”和“夜间高频”。

## 3. 动作序列：不要只做“登录-发帖-退出”

真实用户发帖前会浏览、停留、可能编辑。把动作序列抽象成可编排步骤：

- 打开社区首页，停留 8-20 秒；
- 读取目标板块最近 10-20 条帖子标题；
- 模拟阅读其中 2-3 条，停留 10-30 秒；
- 打开发帖页，输入标题和正文，停顿 5-15 秒；
- 发布后 20% 概率在 1-3 分钟内做一次编辑，补一句说明；
- 发帖后不立即退出，停留 1-5 分钟。

这些动作不一定真的能绕过所有风控，但可以明显降低行为模式的机械感。

## 4. 熔断观察：给发布回路加约束

每次发布后记录帖子状态、响应时间、是否触发验证码、是否收到异常返回。若连续 3 次出现时间异常、删除、封禁警告，则暂停当前账号 24 小时并切换队列。观察期至少要覆盖一个完整自然日。

# 踩坑点

- **把随机间隔当成唯一手段**：只改时间，动作和模板不变，仍然容易被识别。
- **过度使用真实浏览器自动化**：在无必要情况下驱动完整浏览器容易引入更多指纹，维护成本高。优先用官方 API 或轻量请求层。
- **忽略时效规则**：有些社区对技术更新帖有集中帖限制，插件必须读取并遵守版块规则，否则自动发帖会放大违规。
- **模板槽位太少**：同义句只有 2-3 条时，运行一周后内容指纹会非常明显。建议至少 10 条以上并定期轮换。
- **夜间频率没降下来**：很多 Agent 进程 7x24 运行，默认夜间同样积极，这是最容易被发现的规律。

# 可复用建议

把节奏控制做成独立 MCP 工具或插件的一部分，对外暴露：`schedule_post`、`maybe_edit`、`update_community_profile`、`pause_account`。配置项与业务解耦，便于不同社区复用。实现时做到：

1. 所有调度参数可配置，不改代码即可调。
2. 记录完整的发帖审计日志，便于复盘与排障。
3. 灰度发布时只对 1-2 个低权重账号开放，观察 5-7 天再扩大。
4. 将规则检查放在队列入口，违反规则直接丢弃。
5. 每两周人工抽查一次自动发布内容，补充新的同义句和模板槽位。

# 总结

社区自动发帖的机器人感，主要来自节奏和行为的机械一致，而不是发帖本身。工程上把它当作一个带约束的调度系统：内容去重、时间抖动、动作序列化、熔断观察。控制好节奏，可以减少对社区的打扰，也能让自动化更稳定地跑下去。最终目的不是伪装成人类，而是让自动化行为符合社区运行习惯，减少无意义摩擦。
