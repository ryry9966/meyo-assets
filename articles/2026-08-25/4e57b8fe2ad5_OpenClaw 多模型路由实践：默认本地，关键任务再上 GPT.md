## 背景

OpenClaw 里接入 GPT 很顺，但如果每条消息都往云端发，成本、延迟、数据出域都会逐渐变成问题。另一边，本地 7B/8B 模型跑简单分类、脱敏、格式转换通常够用，但复杂工具调用、多步推理和开放对话容易发散。

多模型路由要解决的不是“换哪个模型”，而是“什么任务交给谁，失败后怎么兜底”。

## 问题

实际接入后常见几类现象：

- 简单任务，例如“把这段日志转成 JSON”，也占用云端额度，批量跑几千条时成本明显。
- 本地模型能处理，但输出格式不稳定，下游 MCP 插件或 Agent 解析失败。
- 复杂 Agent 计划、`tool_call` 参数生成交给本地模型，参数错误导致工具执行失败，返工成本比直接调 GPT 还高。
- 敏感数据不希望出内网，但云端模型默认会传输或记录。

这些不能靠单模型解决，只能靠路由和约束。

## 做法 / 步骤

先不要上复杂智能路由。按下面顺序落地。

**1. 确定三类任务**

- A 类：必须本地。包含敏感字段、内部日志、文档的脱敏、分类、摘要、格式转换。
- B 类：必须云端。多步工具调用、复杂指令理解、开放式对话、需要强 JSON schema 且不允许失败的输出。
- C 类：可本地优先，云端兜底。例如信息提取、标题生成、标签归类。

**2. 配置模型池**

在 OpenClaw 中配置两个模型入口：`cloud` 指向 GPT 类 API，`local` 指向内网 vLLM/Ollama 暴露的 OpenAI 兼容接口。模型命名不要硬编码具体版本，建议用别名，方便切换。

**3. 写路由规则**

示例逻辑：

```yaml
router:
  default: local
  rules:
    - when:
        input_contains_private_fields: true
      route: local
    - when:
        task_type: [summarize, classify, extract, redact]
      route: local
    - when:
        task_type: [agent_plan, tool_call, open_chat]
      route: cloud
    - when:
        input_tokens: ">12000"
      route: cloud
    - when:
        local_parse_failed: true
      route: cloud
```

字段名以你部署版本为准，重点是规则顺序和默认值。推荐默认本地，而不是默认云端。因为本地处理不了会失败，失败升级可观测；默认云端则很难发现哪些流量其实可以降级。

**4. 本地输出加约束**

本地模型不要让它自由发挥。给固定 system prompt、输出模板和 few-shot 示例。如果部署支持 structured output 或 grammar，直接限制 JSON 字段和类型。例如要求：

- 只输出 JSON 对象；
- 字段固定为 `category`、`entities`、`summary`；
- 不要输出 Markdown 代码块。

这能大幅降低解析失败率。

**5. 设置兜底**

本地模型超时、OOM、解析失败、`tool_call` 非法时，自动把原始输入和错误信息打包转给云端模型重试。注意不要把本地模型生成的半成品也带过去，只带原始输入和失败原因，避免被错误格式带偏。

**6. 观察指标**

记录每次路由的模型、任务类型、耗时、解析成功、是否升级云端。跑两三天后看：

- 本地解析成功率低于 95% 的任务，考虑直接改云端或更换本地模型；
- 升级率很低且成本可接受的分类任务，可以继续本地；
- 云端流量里出现大量简单提取，说明路由规则没覆盖到。

## 踩坑点

- **本地 JSON 不稳**：7B/8B 模型经常多输出一个反引号、漏逗号、字段名写错。不要靠 prompt 硬约束，优先用 constrained decoding 或 json_schema 校验，失败进入重试。
- **上下文长度**：本地模型窗口通常 8k 到 32k，长文档直接塞会崩或丢信息。路由前先看 token 数，超过本地窗口 70% 就切云端，或者先分块再本地处理。
- **工具调用乱编参数**：本地小模型看到多个 tool schema 容易生成不存在的参数。若必须本地处理工具调用，只暴露一个工具、参数不超过 3 个，并且使用 strict schema。
- **并发出问题**：本地模型推理慢，批量任务一多就排队。给本地任务加队列长度和超时，超过 10 到 20 秒直接走云端，不要拖死整个 Agent 流程。
- **隐私反噬**：本地处理敏感数据虽然安全，但日志、错误回传里可能带上原始内容。兜底到云端前先做字段过滤，只传必要文本。

## 可复用建议

- 先采用“默认本地 + 关键升级”，不要一上来就做评分式智能路由。人工规则能覆盖 80% 场景，且好排查。
- 给每类任务维护一张小表：任务类型、示例、首选模型、输入上限、是否允许云端。配置路由照着表写，避免拍脑袋。
- 升级日志要留原因码，例如 `parse_error`、`timeout`、`too_long`、`tool_call_invalid`。没有原因码，后面很难调规则。
- 模型能力不是固定的。换本地模型后要重新跑一组固定样例，看解析成功率，不要只看 benchmark。
- GPT 不要用于纯格式化任务。把重复、确定、批量的事情沉到本地，云端只处理难和需要泛化的部分。

## 总结

多模型路由在 OpenClaw 里不是“大模型调度系统”，而是控制边界：本地负责隐私和批量，云端负责复杂和兜底。落地顺序应该是：先跑通一个模型、再接入第二个模型、再写死规则路由、最后才考虑自动路由。大多数实践里，稳定的规则和清晰的回退，比“智能”更重要。
