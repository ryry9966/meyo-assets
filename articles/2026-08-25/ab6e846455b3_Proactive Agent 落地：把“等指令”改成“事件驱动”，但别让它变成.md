# Proactive Agent 落地：把“等指令”改成“事件驱动”，但别让它变成骚扰源

## 背景

大多数 Agent 的工作方式仍是被动响应：你发一条消息，它调工具、读上下文、返回结果。这个模式在问答、代码生成、信息检索里够用，但在运维、开发、数据同步等场景里，真正有价值的是“事情已经发生，Agent 先判断再动作，最后只告诉你结果”。比如 CI 失败、磁盘使用率超过阈值、依赖库发布新版、日程变更、监控指标异常，这些都不该等用户想起来才去查。

把 Agent 从“被动工具”改成“主动助手”，不是让它定时随便醒，而是给它一个受控的事件驱动链路。

## 问题

Proactive 能力最容易做成骚扰源：定时任务频繁调用 LLM，产生的通知太多，最后用户全部静音。工程上需要解决四件事：

1. 触发源从哪里来？
2. 条件判断放在哪一层？
3. 动作权限如何收窄？
4. 通知如何收敛、去重、可关闭？

在 OpenClaw/Agent/MCP 体系里，这些可以拆成一条流水线：事件源 -> 触发条件 -> 决策/执行 -> 通知回执。

## 做法/步骤

以一种典型组合为例：外部系统 webhook 进入 OpenClaw，MCP server 提供只读查询工具，Agent 负责复杂判断，动作执行走预设的幂等脚本。

### 1. 事件源接入

优先使用现成的事件通道，不要自己写轮询。GitHub Actions 失败、Prometheus alert、日历 webhook、容器事件都可以通过 webhook 落到一个轻量队列或事件表里。事件体只保留必要字段：来源、类型、时间戳、唯一 ID、载荷摘要。

### 2. 先静态过滤，再让模型判断

不要让每条事件都进入 LLM。先用规则过滤掉明显不关心的部分。例如：

```yaml
triggers:
  - name: ci_failed_main
    source: github_workflow
    condition:
      repo: "org/core"
      branch: "main"
      status: "failure"
    action: notify_owner
    max_per_hour: 1
```

规则层可以用 YAML/JSON 配置，改动成本低。只有规则无法覆盖、需要语义判断的事件才交给 LLM。例如“这个失败是否与当前正在处理的故障单相关”，此时调用 Agent 做一次短上下文判断，并限制 token 和工具范围。

### 3. 动作执行保持最小权限与幂等

主动执行的动作应尽量只读或低风险：创建 issue、发通知、打标签、回滚前需要二次确认。将可执行动作封装成独立工具，每个工具都必须满足：

- 幂等：同一事件重复到达不会重复创建/重复通知；
- 可审计：记录触发原因、执行结果、耗时；
- 可回滚：写操作有对应撤销或说明。

### 4. 通知收敛

主动行为最终需要通知到人，但不能一条事件一次通知。聚合策略可以按来源、时间窗口、严重级别合并。例如 10 分钟内同一个 CI 失败任务只通知一次，后续新增失败只更新原通知。用户可以设置静默时段，也可以对某个触发源一键暂停。

一个简化流程如下：

```
webhook -> 事件去重 -> 规则过滤 -> [LLM 可选判断] -> 幂等动作 -> 聚合通知 -> 用户回执/静默
```

## 踩坑点

**触发风暴与重复执行**。事件源偶发重试、同一事件被多个 webhook 重复投递，如果动作不幂等，会重复建 issue、重复发消息。必须用事件唯一 ID 做去重，并对动作执行结果做记录。

**把 LLM 当成唯一决策器**。每条事件都问 LLM，既慢又贵，还会因为上下文不足产生幻觉。正确做法是规则优先，LLM 只处理少量高价值判断。

**权限过大**。主动 Agent 一旦拿着写权限，容易在误判时造成真实影响。生产环境建议只给只读或审批流权限，高风险操作必须由用户确认。

**通知疲劳**。没有聚合和静默机制，proactive 很快会变成噪音源。需要让用户能调整阈值、暂停来源、查看触发历史，而不是只能全局开关。

**事件乱序与时区**。时间比较、窗口聚合必须用统一 UTC 时间戳；事件可能乱序到达，需在事件体里带发生时间，而非依赖接收时间。

## 可复用建议

1. 把 proactive 能力做成独立模块，与主对话 Agent 解耦。触发、判断、动作、通知分别可替换。
2. 静态规则先行，LLM 仅做语义兜底。
3. 所有动作默认幂等，关键写操作走审批。
4. 提供 dry-run 模式，先只记录“如果触发会做什么”，跑一周再开真实执行。
5. 给每个主动行为留 trace：触发条件、事件 ID、模型输入/输出、动作结果、通知状态。
6. 让用户掌握开关：按来源暂停、按时间段静默、按阈值调整，而不是让 Agent 自行决定要发多少。

## 总结

Proactive 能力的目标不是“Agent 更爱说话”，而是让它在合适的事件点替用户完成低风险闭环。落地时，先把规则和幂等做好，再让模型参与复杂判断，最后用聚合通知降低打扰。这样主动助理才不会被用户卸载。
