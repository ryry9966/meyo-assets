## 背景

在 OpenClaw 的 Agent 自动化里，很多任务已经从“聊几句”变成“实际执行”：读文件、跑命令、调 MCP、发请求、改配置。没有约束时，Agent 会“发挥过度”：输出风格忽冷忽热，误删文件，反复调用外部服务，或者在长任务里慢慢偏离目标。

SOUL.md 可以理解为 Agent 每次启动都会读的项目级“人格与边界文件”。它比散落在 prompt 里的规则更稳定，可以版本化、评审、复用，也方便团队知道一个仓库里的 Agent 到底被灌了什么规则。

## 问题

实际使用中，常见几类问题：

- **人格不一致**：同一个任务换模型或工具后，语气和行为明显变化。
- **边界模糊**：用户说“帮我整理项目”，Agent 可能顺手提交代码、安装依赖、修改锁文件。
- **规则难维护**：提示词藏在代码里或某个聊天记录里，团队其他人完全不知道。
- **工具冲突**：MCP 或插件已经暴露了能力，SOUL.md 说“禁止”，但工具仍然可以调用。

## 做法/步骤

1. **放对位置**  
   项目级放在仓库根目录 `SOUL.md`，个人全局放在 `~/.openclaw/SOUL.md`。建议项目级覆盖全局，临时任务指令再覆盖项目级，但硬边界不要被临时指令放宽。

2. **结构化内容**  
   SOUL.md 不要写成散文。建议至少分五个区块：

   - 身份与语气：一句话定义角色，例如“你是本仓库的工程助手，输出简洁、可执行、不编造。”
   - 核心原则：先读后改；最小变更；可回滚；不确定先问。
   - 允许操作：列出明确可做的动作。
   - 禁止操作：列出不能做的动作。
   - 工作流：任务开始先看 README、检查 `git status`、结束总结变更。

3. **边界分级**  
   用四个等级替代模糊描述：

   - `READ_ONLY`：只读文件、只读命令。
   - `WRITE_ALLOWED`：只允许写入指定目录，如 `.openclaw/tmp/`。
   - `EXEC_ALLOWED`：允许执行的白名单命令。
   - `NETWORK_ALLOWED`：允许访问的外部域名或 MCP 服务。

   每一档下面列具体路径或命令，而不是写“不要乱操作”。

4. **示例片段**

   ```markdown
   # SOUL.md

   ## 身份
   你是 OpenClaw 项目助手，输出简洁，不编造。

   ## 允许
   - 读取仓库内所有文本文件
   - 运行 git status、git diff、ls 等只读命令
   - 写入 .openclaw/tmp/ 下的临时文件

   ## 禁止
   - 不执行 rm、git reset --hard、git push --force
   - 不修改 package-lock.json 或 pnpm-lock.yaml
   - 不向外部域名发送请求，除非任务明确要求并经用户确认
   ```

5. **自动加载**  
   如果 OpenClaw 支持注入项目上下文，就把 `SOUL.md` 作为 system prompt 的一部分。不支持的话，可以在会话开始前让 Agent 先读该文件，或者通过插件/MCP 读取后拼进上下文。

6. **验证**  
   写一个固定测试任务：“用三句话总结你的身份和边界；如果任务要求删除文件，你会怎么处理？”看它是否准确引用 SOUL.md，而不是泛泛而谈。

## 踩坑点

- **否定句容易被忽略**  
  “不要删除”远不如“仅允许删除 `/tmp` 下文件，其他路径一律拒绝”有效。模型对明确白名单更敏感。

- **太长等于没有**  
  人格描述超过 300–500 字后，模型在长任务中容易遗忘。硬规则放最前面，语气描写放后面。

- **只靠提示词不够**  
  SOUL.md 说禁止调用某 MCP 工具，但工具仍然暴露。需要在 MCP server 或 OpenClaw 工具权限里关闭该能力，形成双层约束。

- **多文件冲突**  
  全局和个人项目混用时，Agent 可能读到两份 SOUL.md。明确优先级：项目级覆盖全局；临时 prompt 不能放宽删除、网络等硬边界。

- **修改后不生效**  
  可能是缓存或会话未重启。修改 SOUL.md 后需要新开会话，并用测试任务确认加载。

## 可复用建议

- **分层管理**：全局放通用边界和个人偏好；项目放仓库规范；任务临时指令放 prompt。不要把一次性要求写进 SOUL.md。
- **用“必须/允许/禁止”替代长段落**：每条一行，减少歧义。
- **边界落到工具层**：MCP 服务端做 allowlist 限制，OpenClaw 命令白名单限制危险操作。
- **评审变更**：SOUL.md 的修改像代码一样走 PR，记录为什么改动。它会影响所有使用该仓库的 Agent 行为。
- **定期审计**：每月跑一次 audit 任务，让 Agent 列出自己理解的边界，对比文件，发现漂移。

## 总结

SOUL.md 给 Agent 提供了一个稳定的“人格底座”和“操作围栏”。它解决的不是“让 AI 更聪明”，而是“让 AI 行为可预期、可回滚、可审计”。真正可靠的边界需要三层：SOUL.md 写清楚规则、工具/MCP 做权限限制、变更走版本评审。不要指望一段提示词就能挡住所有误操作，但一个结构清晰、版本化的 SOUL.md，会让 Agent 自动化在团队里更容易落地。
