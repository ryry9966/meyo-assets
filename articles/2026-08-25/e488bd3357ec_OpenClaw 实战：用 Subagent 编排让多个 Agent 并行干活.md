## 背景

在 OpenClaw 里做自动化时，单 Agent 串行处理多任务很容易遇到两个问题：一是上下文膨胀，二是整体耗时长。比如一个任务需要同时抓取多个数据源、生成代码、检查规范、写总结，如果全塞给一个 Agent，它会在不同目标之间来回切换，输出质量不稳定，而且 API 调用时间线性叠加。

Subagent 编排的思路是把大任务拆成若干小任务，交给多个子代理并行执行，最后由主代理汇总。这样每个子代理只需专注一个窄目标，上下文干净，执行速度快，也更容易做权限控制和错误隔离。

## 问题

并行不是简单“多开几个 Agent”。实践中真正要解决的是四件事：

1. 任务如何拆，拆到什么粒度。
2. 多个子代理如何调度，如何控制并发。
3. 结果如何回收、校验、合并。
4. 失败、超时、资源冲突如何恢复。

如果这些没有设计好，很容易变成“伪并行”——主代理仍然在等某个慢任务，或者多个子代理互相覆盖文件、输出格式不一致，最后汇总时反而更乱。

## 做法 / 步骤

### 1. 定义子代理角色与工具权限

先不要急着写调度逻辑。给每个子代理明确角色、可用工具和输出契约。例如：

- `fetcher`：只读 MCP 搜索/抓取工具，输出 `{title, summary, status}`。
- `coder`：只能写 `/workspace/tmp/` 目录，不能删除已有文件。
- `reviewer`：只读代码和规则库，输出问题列表。
- `formatter`：只接收结构化数据，输出最终 Markdown。

在 OpenClaw 中可以用 subagent 的 system prompt 和工具白名单来限制权限。默认只读，写操作限定目录，删除操作禁止或需要主代理确认。

### 2. 任务拆分

主代理把任务拆成无依赖的独立单元。每个单元包含：

- 类型：对应某个子代理。
- 输入：最小必要数据。
- 期望输出：固定 schema。

例如批量处理 20 个 URL，拆成 20 个 `fetcher` 子任务，而不是让一个子代理循环处理 20 个 URL。这样并行度才真正上得来。

### 3. 并行调度

在 OpenClaw 中通过任务队列控制并发。可以用类似下面的伪代码：

```ts
const tasks = urls.map(u =>
  spawnSubagent('fetcher', {
    url: u,
    output_schema: { title: 'string', summary: 'string', status: 'string' }
  })
);

const results = await runWithConcurrency(tasks, 4);
```

并发数不要设太高。API 限流时并发 3 以内比较稳，本地工具可以放到 5-8。每个子任务设置独立超时，避免某个任务挂起拖垮整个批次。

### 4. 结果回收与校验

每个子代理返回 JSON。主代理用 schema 校验：`status` 是否为 `ok`，`data` 字段是否齐全，`error` 是否为空。不合法结果进入重试队列，而不是直接丢弃或强行汇总。

### 5. 重试与降级

失败或超时的子任务重试一次。如果仍失败，记录日志并降级为人工处理或串行补跑。不要无限重试，否则会放大 API 费用和资源占用。

## 踩坑点

### 上下文污染

子代理经常会输出“好的，我来处理”“以下是结果”等多余文字，或者把推理过程混进结果里。主代理汇总时还得费劲清洗。

**解决**：子代理 system prompt 末尾强制要求“只输出 JSON，不要输出任何解释”，主代理侧做 JSON 提取和容错解析。

### 资源竞争

多个子代理同时写同一文件、同一数据库表，会出现锁冲突、覆盖、脏数据。

**解决**：给每个子代理分配独立工作目录或临时表，汇总时再统一合并。写操作尽量设计为追加而不是覆盖。

### 权限过大

并行场景下，如果子代理拥有删除、重命名、全局写权限，一旦误操作，影响范围会被并行放大。

**解决**：默认只读，写操作限定白名单路径。删除操作、批量覆盖操作必须主代理审核或人工确认。

### 任务粒度过细或过粗

拆得太碎，调度和上下文开销超过实际收益；拆得太粗，并行度不足，退化成串行。

**经验**：单个子任务执行时间最好控制在 5-30 秒，输入输出数据量尽量小。如果超过这个范围，考虑再拆一层或合并小任务。

### 观测缺失

并行任务出错后，如果日志里没有标识，很难定位是哪个子任务哪一步失败。

**解决**：为每个子任务生成 `trace_id`，在日志中记录子代理类型、输入摘要、开始/结束时间、退出状态。OpenClaw 的日志系统可以配合使用。

## 可复用建议

- **最小权限**：给 subagent 配置 MCP 工具白名单，删除操作默认关闭。
- **输出契约**：统一 `{status, data, error}` 结构，主代理做 schema 校验。
- **幂等设计**：任务本身可重复执行，不依赖全局状态，避免重试产生副作用。
- **并发控制**：API 类任务并发 3-5，本地文件类任务 5-8，根据实际限流调整。
- **人工卡点**：批量写操作、批量删除、发布类动作前加 dry-run 或人工确认。
- **超时与回收**：设置全局超时，定期回收僵尸子任务，避免长时间占用资源。

## 总结

Subagent 编排不是“开更多 AI 同时跑”，而是把任务拆成可并行、可观测、可恢复的小单元。真正的工程重点在于四个词：**边界、权限、输出契约、观测**。把这四点控制好，多个 Agent 并行才能真正提效；否则只会把串行混乱变成并行混乱。
