## 背景

OpenClaw-CN 社区的内容更新频率不低，人工整理技术帖、统一格式、再发布到社区，既耗时又容易出错。我们想做一个发帖机器人，把 RSS、GitHub Release、内部简报等来源自动整理成符合社区规范的帖子，生成草稿后由人工确认发布。目标不是全自动，而是把“找内容、格式化、写图片描述”这些重复动作自动化，同时保留可审计的审核节点。

## 问题拆解

实际动手前，先明确要解决的几个问题：

- 多源内容抓取与去重，避免重复发帖。
- 输出内容要符合社区调性：标题长度、标签、Markdown 语法、图片 prompt 规范。
- 发布链路需要可观测、可回滚，不能只靠大模型自由发挥。
- 上下文窗口有限，不能无脑把全文塞给模型。
- 图片 prompt 必须纯插画、无文字、无 logo，否则配图容易翻车。

## 整体架构

我们采用分层结构：

`采集层 -> 调度层 -> 生成层 -> 审核层 -> 发布层 -> 状态存储`

- **采集层**：通过 MCP Server 暴露 `fetch_rss`、`fetch_url`、`get_github_release` 等工具，统一拉取原始内容。
- **调度层**：用 cron 或 webhook 触发，只负责产生待处理任务，不直接发布。
- **生成层**：由 OpenClaw Agent 调用采集工具获取内容，再生成结构化 JSON。
- **审核层**：先做本地规则扫描，再推送到审核群或后台，人工确认。
- **发布层**：通过社区 API 或 webhook 发布，支持 dry-run。
- **状态存储**：用 SQLite 或 Postgres 记录任务状态、模型版本、原文 hash、输出结果。

## 关键实现步骤

### 1. 采集与调度

把不同来源抽象为 `source_type + source_url`，统一入库。调度任务只负责创建 `pending` 状态的任务，后续步骤异步处理。每一条任务都带 `source_url` 和 `content_hash`，用于后续去重和幂等。

### 2. 生成层：结构化输出

模型不直接输出 Markdown，而是固定输出 JSON，渲染交给代码完成。System prompt 里强制要求以下结构：

```json
{
  "title": "文章标题",
  "content": "Markdown 正文",
  "tags": ["OpenClaw", "MCP"],
  "image_prompts": {
    "cover": "英文插画 prompt",
    "img1": "英文流程图 prompt",
    "img2": "英文 checklist prompt"
  }
}
```

同时约束：标题不超过 40 字，不使用某些品牌词，内容为 Markdown，图片 prompt 必须包含 `no text, no letters, no watermark, no logo, pure illustration only`。生成时开启 JSON mode 或函数调用，减少格式错误。

### 3. 审核与发布

生成结果进入 `pending_review`。本地规则先检查敏感词、链接域名白名单、Markdown 完整性，再推送人工确认。发布时用 `content_hash` 和 `source_url` 做唯一索引，避免重试导致重复发帖。接口支持幂等键时优先使用。

### 4. 日志与回滚

每次生成记录完整上下文：prompt、模型版本、temperature、原文 hash、输出 JSON、发布结果。一旦出问题，可以快速定位是采集、生成还是发布环节。

## 踩坑实录

### 坑 1：上下文爆炸

刚开始直接抓取网页全文塞给模型，结果要么超出上下文限制，要么摘要跑偏。解决：先用可读性提取正文纯文本，按段落分块摘要，再汇总生成最终内容。不要偷懒把原始 HTML 直接喂进去。

### 坑 2：Markdown 污染

模型返回的 `content` 外层经常包裹 ` ```json ` 代码块，或者换行变成 `\n`，发布后出现多余符号。解决：强制 JSON mode，并在解析时兼容剥离 markdown code fence。后置校验标题是否包含 `#` 等非法字符。

### 坑 3：图片 prompt 不稳定

模型很容易生成带文字、海报、logo 的描述，但社区要求纯插画。解决：在 system prompt 里反复强调“画面中不得出现任何文字、字母、中文、logo、水印”，并在代码里后置校验 prompt 是否包含 `text`、`letter`、`logo`、`watermark` 等词，命中则自动重试一次。

### 坑 4：发布接口限流与重复发帖

发布失败后重试，如果接口没有幂等处理，会重复发帖。解决：发布前先查 `content_hash` 是否已存在；发布请求携带幂等键；每次重试前检查状态机，只有 `reviewed` 状态才允许发布。

### 坑 5：敏感词误伤

技术文章容易出现“代理”“自动化”等词，被社区敏感词系统误伤。解决：审核层先做本地敏感词扫描，命中后标记人工确认，保留白名单机制。

### 坑 6：时区问题

定时任务默认 UTC，和北京时间不一致，导致发布时间错乱。解决：统一存储 UTC 时间，展示层再转换。

## 可复用建议

- **从半自动开始**：先自动生成草稿，人工审核后再发布，跑通后再逐步放开自动发布范围。
- **生成与渲染分离**：模型只输出 JSON，Markdown 渲染、标签合并、图片 prompt 校验都放在代码层。
- **对图片 prompt 做后置校验**：正则检测 `text/letter/logo/watermark` 等词，不符合就重试，避免人工反复修改。
- **发布层做成适配器**：社区 API 变更只影响一个模块，上层逻辑不用动。
- **保留完整生成记录**：每条任务至少记录 prompt、模型版本、输出 JSON、发布结果，方便回滚和调 prompt。

## 总结

这套发帖机器人落地成本不高，核心在于结构化输出、幂等发布和本地审核。它不追求全自动，而是把重复劳动自动化，同时保留人工决策点。实际用下来，最麻烦的反而不是模型生成，而是接口限流、格式污染和图片 prompt 校验这些工程细节。如果你的社区也有类似需求，可以先从“自动生成草稿 + 人工确认发布”的 MVP 开始，一周左右就能跑通。
