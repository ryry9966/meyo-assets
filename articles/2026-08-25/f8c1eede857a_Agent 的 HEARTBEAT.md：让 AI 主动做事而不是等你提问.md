## 背景

很多 OpenClaw 用户的 Agent 还停在“问答式自动化”：你发一句，它动一下。真正需要持续关注的事情，比如检查告警、回收日志、跟进依赖更新、看某个目录是否出现新文件，往往还是靠人肉提醒，或者写一堆外部 cron 脚本。

问题不是 Agent 能力不够，而是我们没有给它一个稳定的“节拍”。外部 cron 能定时触发脚本，但脚本没有 Agent 的判断力；Agent 能理解任务，但默认只会在对话里等你。

HEARTBEAT.md 的思路很简单：把“什么时候该动、动什么、做到什么程度、做完怎么记录”写成一个 Agent 常驻读取的运行节拍文件。它不是 prompt 库，而更像运维手册里的 runbook。

## 问题

常见的主动式自动化失败，通常卡在三点：

1. **被动等待**：Agent 只在用户输入后响应，没有空闲时自我唤醒的入口。
2. **任务遗漏**：重要检查分散在不同对话里，换个会话就丢了上下文。
3. **不可验证**：Agent 说“做过了”，但没有日志、没有状态、没有下次检查时间，无法判断真假。

HEARTBEAT.md 解决的就是这三件事：触发节拍、任务清单、可验证记录。

## 做法 / 步骤

### 1. 先定心跳频率和边界

不要一上来就做“每 5 分钟检查全世界”。建议从 30 分钟一次、只读检查开始。心跳任务应当是轻量、可失败、不影响主流程的。

例如：

- 每 30 分钟检查一次未处理告警
- 每小时检查一次备份目录大小
- 每天检查一次依赖更新

边界要写清楚：心跳任务默认只读，写操作必须 dry-run 或人工确认。

### 2. 建立 HEARTBEAT.md

把文件放在 Agent 工作区，例如 `~/.openclaw/agents/home-ops/HEARTBEAT.md`。内容可以这样组织：

```markdown
# HEARTBEAT.md

## 心跳触发
- 频率：每 30 分钟
- 模式：只读检查，不允许直接修改业务文件

## 主动任务
### T-01 告警检查
- 检查：最近 30 分钟是否有未处理告警
- 完成标准：输出告警数量、级别、是否需人工处理
- 动作：仅汇报，不自动处理

### T-02 备份检查
- 检查：最近一次备份是否成功
- 完成标准：返回备份文件时间戳和大小
- 动作：若失败，只记录并提醒

## 禁止事项
- 禁止自动删除任何日志
- 禁止自动发送对外消息
- 写操作必须 dry-run

## 状态
- last_heartbeat: 未执行
- next_heartbeat: 未设置
```

### 3. 让 Agent 每次醒来先读它

在 OpenClaw 的 Agent instructions 或 system prompt 中加入一句：

> 每次被唤醒或开始任务前，先读取 HEARTBEAT.md。如果没有需要执行的心跳任务，回复 `heartbeat: skip`，不要做多余动作。

这句话很关键。它让 Agent 知道：主动不是“自由发挥”，而是先看运行手册。

### 4. 接入触发源

触发方式可以根据你的环境选择：

- 如果 OpenClaw 支持 schedule/trigger 插件，优先用它。
- 如果没有，可以用外部 cron 调用 OpenClaw CLI，或通过 MCP cron server 唤醒 Agent。
- 更简单的方式：开一个常驻会话，让 Agent 按 HEARTBEAT.md 自己 sleep 和唤醒。

我个人更推荐外部 cron + MCP，因为进程隔离更好，不容易被用户会话打断。

### 5. 执行并写回日志

每个任务要有唯一 ID、状态、时间、下次检查时间。不要写回 HEARTBEAT.md 本体，而是追加到 `heartbeat.log.jsonl`：

```json
{"task_id":"T-01","status":"ok","detail":"0 alerts","time":"2025-01-01T10:00:00Z","next":"2025-01-01T10:30:00Z"}
{"task_id":"T-02","status":"warn","detail":"backup file missing","time":"2025-01-01T10:00:00Z","next":"2025-01-01T11:00:00Z"}
```

这样 HEARTBEAT.md 保持小而清晰，历史记录外置，便于检索。

## 踩坑点

### 1. 文件膨胀导致上下文超限

很多人会把每次心跳结果都写进 HEARTBEAT.md，几天后文件就几千行，Agent 读取时上下文爆掉。

对策：HEARTBEAT.md 保持 100 行以内，只放任务定义和当前状态；历史日志走 JSONL 外置文件。

### 2. 重复执行

同一个任务被多次触发，Agent 每次都说“需要处理”，于是反复执行同一件事。

对策：每个任务设置 `last_run_at` 和 `status`。Agent 读完文件后先判断：如果距离上次执行不到最小间隔，且状态为 ok，就跳过。

### 3. 幻觉完成

Agent 可能没有真正调用工具，就说“检查完成，无异常”。

对策：完成标准必须可验证。要求 Agent 在日志里附上工具返回摘要、文件 hash、命令退出码等证据。比如“备份检查完成”必须包含 `ls -l` 的文件大小和时间戳，不能只有一句结论。

### 4. 定时唤醒与用户会话冲突

同一个 Agent 实例既处理心跳任务，又处理用户对话，容易出现工具争用或上下文污染。

对策：心跳任务使用独立 Agent，或至少用独立会话。用户会话不要直接掺和心跳执行。

### 5. 权限失控

主动任务一旦有写权限，很容易误删、误发消息。

对策：默认只读，写操作全部 dry-run。只有经过人工确认或白名单校验后，才允许执行真实写动作。

## 可复用建议

- **把 HEARTBEAT.md 当运行手册，不是聊天记录**。保持精炼，任务定义清晰。
- **从小任务开始**：先只做“读取并汇报”，稳定运行一周后再逐步增加动作。
- **使用 JSONL 日志**：每行一条记录，方便后续用 `jq` 或脚本统计。
- **与 MCP 工具联动**：比如用文件系统 MCP 读日志、用告警 MCP 查未处理事件、用通知 MCP 发提醒。HEARTBEAT.md 负责编排，MCP 负责执行。
- **每周人工 review 一次心跳日志**：删掉低价值任务，调整频率，避免 Agent 变成只会制造噪音的机器人。

## 总结

HEARTBEAT.md 的核心不是定时器，而是把“主动”显式化：何时做、做什么、做到什么程度、怎么证明做过。对 OpenClaw 用户来说，它是一层很薄的运行约定，不需要引入复杂调度系统，却能明显改变 Agent 的行为模式。

如果你现在还没有任何主动任务，建议从“每 30 分钟只读检查一次未处理告警”开始。先让它学会有节奏地醒来、看完手册、如实汇报，再谈下一步自动化。
