# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

Agent 早就不是只会聊天的角色了。在 OpenClaw、MCP、插件和自动化脚本的配合下，它可以读文件、改配置、调接口、跑命令，甚至操作数据库。能力越大，越容易出两类问题：一类是把 Agent 当成“遥控器”，每一个动作都让用户点确认，结果 Agent 只是换了个壳的命令行；另一类是完全放开，等出了事才发现它删错了表、发错了请求。

权限边界本质上不是一个开关，而是一套风险分级与确认策略。它决定了 Agent 在什么条件下可以自己干，什么条件下必须停下来问人。

## 问题

很多框架只提供“工具是否可用”的开关，不提供“在什么条件下可以自主执行”的粒度。比如一个文件整理 Agent，允许它读目录、重命名文件，但不允许删除；一个发布 Agent，允许它生成 PR，但不允许直接 merge。如果只靠自然语言 prompt 说“不要做危险操作”，效果很差，因为模型对“危险”的理解不稳定。

更麻烦的是，权限问题经常被推迟到执行阶段才发现。Agent 已经跑了一半，突然弹出一个确认框，用户要么随手点掉，要么流程卡死。真正需要的是提前定义清楚边界，让 Agent 在规划阶段就知道哪些路可以走，哪些路需要拿钥匙。

## 做法 / 步骤

**第一步：给工具做风险分级。**  
不要用模糊的自然语言，而是给每个工具标注机器可读的风险等级。常见分级可以是 `read`、`write`、`delete`、`external`。例如：

```yaml
tools:
  list_files:
    risk: read
    auto_approve: true
  read_file:
    risk: read
    auto_approve: true
  write_file:
    risk: write
    auto_approve: false
    confirm: true
  delete_file:
    risk: delete
    auto_approve: false
    confirm: true
    require_reason: true
  call_api:
    risk: external
    auto_approve: false
    confirm: true
    allowlist: ["api.example.com"]
```

这样的配置不依赖模型“自觉”，而是执行前就能被策略引擎判断。

**第二步：把权限策略注入到 Agent 上下文。**  
不要只在外部拦截。比如告诉 Agent：“你可以读取文件，但任何写入操作都必须先向用户确认，并说明改动内容和影响范围。”这样 Agent 在规划时就会把确认步骤安排进流程，而不是执行到一半被硬性打断。

**第三步：确认请求要结构化。**  
不要只问“是否继续？”，要给出操作、目标、影响范围、可回滚性。例如：

> 准备修改 `/data/config.yml`，将 `timeout` 从 30 改为 60，影响 2 个服务，可回滚。是否执行？

这种请求让用户能做快速判断，而不是被迫猜。

**第四步：设置超时默认拒绝。**  
确认请求超过一定时间（比如 5 分钟）未响应，默认不执行。避免异步场景下挂起等待，把后续流程卡死。

**第五步：记录决策日志。**  
每个写操作都记录：Agent 的提议、权限策略的判断结果、用户确认或拒绝、最终执行结果。日志是后面复盘权限边界是否合理的依据。

## 踩坑点

**确认疲劳。**  
如果 Agent 每改一个字段都问一次，用户很快就会习惯性点“同意”，权限边界等于没有。对策是批量确认，或者在同一个会话里对同类型操作合并确认。比如“以下 3 处配置修改是否一起执行？”

**工具内部越权。**  
MCP 工具可能内部调用其他服务，权限标注只看到外层工具，实际副作用超出预期。对策是对 MCP 服务做命名空间隔离，审查工具描述中关于副作用的说明，必要时在测试环境抓包验证。

**只读工具不干净。**  
有些接口名义上是 `GET`，实际会写日志、触发告警、消耗配额。第一次接入时，先在测试环境确认副作用，不要把“只读”当成绝对安全。

**异步任务权限上下文丢失。**  
定时任务运行时用户可能不在场，确认机制无法触发。对策是后台任务默认采用更严格策略：只允许只读和可回滚操作，或者要求用户提前预授权。

**自然语言描述权限太模糊。**  
“不要做危险操作”“重要操作要问用户”这类 prompt 基本无效。必须用机器可读的风险等级和条件，否则权限边界会随着模型状态漂移。

## 可复用建议

- **权限策略作为代码管理**，版本化，和生产配置一起 review。不要散落在 prompt 或注释里。
- **引入风险分数。** 例如只读=0，写入=1，删除=3，外部=5。一个会话累计风险分超过阈值（如 10）后，后续所有操作都必须确认。这样能防止多个中低风险操作累积出大问题。
- **区分交互式会话和后台任务。** 交互式可以宽松一些，后台任务默认更严格，因为用户不在场。
- **定期复盘审计日志。** 哪些确认是多余的，哪些自动执行应该升级为确认。权限边界需要根据实际使用情况迭代。
- **对 MCP 插件做沙箱。** 限制可访问目录、网络域名、环境变量，防止插件拿到的权限超出声明范围。

## 总结

权限边界的目标不是“不让 Agent 做任何事”，而是让它在低风险区域自主，在高风险区域精准打断。一套可用的策略至少包含：风险分级、默认策略、结构化确认、超时拒绝、审计日志。工程上要尽量把“什么时候问人类”变成可配置、可测试、可复盘的规则，而不是依赖模型自觉或用户忍耐力。
