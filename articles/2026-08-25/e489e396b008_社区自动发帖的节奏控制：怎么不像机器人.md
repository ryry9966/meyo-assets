## 背景

社区自动发帖在 OpenClaw/Agent 实践里，常被简化成两步：用 Agent 生成内容，再用浏览插件或 MCP 工具提交。很多人把精力放在 prompt 和工具链，发布节奏只写成固定 sleep 或 crontab。结果不是立即被风控，就是发出去没有互动。

识别为机器人，通常不是因为自动化本身，而是节奏不符合社区里真实用户的分布：发布时间太整齐、动作太快、内容句式重复、发布后不回应。

## 问题拆解

1. **时间维度**：固定间隔、整点触发、每天同样时间。
2. **行为维度**：打开页面到提交只用几秒，没有停留、滚动、修改。
3. **内容维度**：模板只替换标题和链接，句式高度一致。
4. **反馈维度**：发布后不处理回复、不修正、不参与上下文，继续跑下一条。

这些单点问题合在一起，会让账号看起来像队列消费者，而不是社区成员。

## 做法：把节奏控制做成独立模块

建议不要直接在每个 Agent 脚本里写随机 sleep，而是抽出一个节奏控制器，可以作为本地模块或 MCP server，向 Agent 暴露查询与上报接口。

### 1. 发帖窗口

先观察目标社区最近 N 天的新帖分布，计算活跃时段。不要 24 小时均匀发。定义窗口和权重，例如工作日 10:00-11:00、15:00-16:00、20:00-22:00，周末下午。窗口内再做随机抖动，而不是固定 10:30。

### 2. 动作分解

把发帖拆成：打开页面 -> 停留 -> 滚动 -> 编辑 -> 停顿 -> 检查 -> 提交。每步延迟使用偏态分布，避免均匀随机。不要全程只用 `sleep(10)`。

### 3. 内容模板增加状态

发布前让 Agent 读取社区最近几篇帖子，生成不同摘要和句式；准备多套开场白、结论、标题结构，按权重选择，避免同一模板高频复用。

### 4. 冷却观察

发布后进入冷却期，例如 15-30 分钟内不立即发下一条。如果出现回复或引用，先处理互动任务，形成“发帖 -> 响应 -> 再发帖”的闭环。

## 踩坑点

- **全局随机导致凌晨发帖**：只靠 random 不够，必须有窗口约束。
- **固定延迟仍像机器**：10s/20s 这种常量很容易被识别，需要带噪声的延迟。
- **登录态和验证码**：节奏控制器要能感知登录态过期或验证码出现，立即暂停队列，而不是继续重试。
- **多账号并发关联**：多个 Agent 同时发不同账号，容易触发关联。账号之间要加不同行为参数和随机抖动。
- **忽略内容质量**：节奏再像人，内容千篇一律也会被举报。

## 可复用建议

- 把“像人”变成可量化指标：发帖间隔方差、会话停留时长、编辑次数、回复率、删帖率。
- 日志留痕：记录计划时间、实际时间、延迟原因、风控结果。
- 灰度运行：先在小流量和低活跃时间试跑 3-7 天，再逐步扩大。
- 保留人工审核：自动生成内容进入待审队列，发布前随机抽检。
- 对社区规则做配置化：不同平台的频率、外链、内容限制不同，节奏策略应可配置下发。

## 总结

自动发帖不像机器人，核心不是加一个随机 sleep，而是把时间窗口、动作分解、延迟分布、内容变化和发布后反馈纳入同一个控制器。工程上先做可观测、可暂停、可回退，再谈跑量。稳定、可控、可解释，比快和量更重要。
