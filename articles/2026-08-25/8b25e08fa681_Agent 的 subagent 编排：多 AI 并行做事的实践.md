## 背景

在 OpenClaw 里跑复杂任务时，单 agent 的默认形态很容易变成“一个大脑串行处理所有事”。比如让一个 agent 同时负责读取多个仓库、调用 MCP 工具、写文件、做总结，结果上下文里塞满中间结果，越到后面越容易跑偏；如果每个工具调用都要等返回，整条链路耗时线性叠加。

subagent 编排的思路是：主控 agent 只做拆分、调度和汇聚，具体子任务交给隔离的 worker agent 并行执行。

## 什么任务适合并行 subagent

不是所有任务都适合并行。一个简单判断标准：子任务之间没有共享可变状态，且每个子任务有明确输出物，就可以考虑拆分。

适合拆的典型场景：

- 同时检查多个仓库、目录或数据源；
- 同时调用多个独立 MCP 工具或插件能力；
- 一份长报告的不同章节，基于不同素材分别生成；
- 需要互相独立验证的探索型任务。

不适合拆的：强依赖链、需要共享完整上下文才能决策、以及结果之间需要实时同步的任务。

## 实践做法

### 1. 主控只做调度，不做具体活

我会把主控 agent 的 prompt 限制在三件事：读任务清单、生成 subagent、按 schema 校验并合并结果。主控不直接读大文件、不重算结果、不替 subagent 补逻辑。这样能避免主控上下文膨胀。

### 2. 给 subagent 窄 prompt 和受限工具

每个 subagent 只给完成当前子任务必要的工具和提示。比如一个“查依赖版本”的 subagent，只给 `mcp__filesystem` 和 `mcp__git`，不给写权限；一个“写发布说明”的 subagent，只给一个输出目录，不放开读取全盘。

输出要求用 JSON 或文件产物，不要用自由对话。推荐每个 subagent 写入独立工作目录：

- `/tmp/agents/repo_scout/result.json`
- `/tmp/agents/release_notes/draft.md`

### 3. 并行调度与限流

如果一次性拉起 10 个 subagent，很容易触发上游 API 限流或者把 MCP 工具打爆。我会先按任务类型分组，把并发控制在 2-3 个，跑通后再放开。

关键点：

- 每个 subagent 要有独立上下文，不共享会话；
- 用 request id 串联日志；
- 给每个任务设置超时和最大 token。

### 4. 汇聚与校验

汇聚阶段只做“拼装”，不做“重算”。主控根据预定义 schema 校验字段是否齐全，缺失就降级或重试，不让主控补写。

一个简单汇聚策略：

- 只接受合法 JSON 或文件路径；
- 字段不齐的子任务重试一次；
- 多次失败则标记为 `partial`，在最终产物中留空并说明来源。

## 踩坑点

**格式漂移**：subagent 聊着聊着把 JSON 输出变成了自然语言解释。解决办法是 prompt 里给出输出示例，并在主控侧做 schema 校验。

**上下文串味**：多个 subagent 共用同一个上下文窗口，结果 A 任务看到了 B 任务的中间产物。独立上下文比“在一个长对话里反复切换角色”更可靠。

**并发过高**：并行不是越多越好。API 限流、工具服务端排队、本地 CPU 争抢都会导致整体变慢。建议从 2-3 个并发开始压。

**日志缺失**：只记最终结果，不记每个 subagent 的输入、输出路径和耗时。排障时会很难定位是哪个子任务出问题。

**错误授权**：给 subagent 过多工具权限，比如写权限、执行命令权限。一个只读查询任务不应有删除或覆盖能力。

## 可复用建议

1. 先串行跑通单个 subagent，再并行化；
2. 输出用文件 artifact，少用对话文本传递长内容；
3. 主控校验用 JSON schema，不靠自然语言判断；
4. 每个 subagent 设置超时、重试上限和降级策略；
5. 日志里带上 `request_id`、`subagent_name`、`duration_ms`、`output_path`；
6. 工具权限最小化，必要时用沙箱或只读挂载。

## 总结

subagent 编排不是“让更多 AI 一起干活”那么简单，它本质上是把并发、隔离、失败处理和可观测性引入 agent 工作流。OpenClaw 的优势在于可以用 MCP 工具和插件组合快速搭出 worker 角色，但真正的收益来自克制：主控少做，子任务边界清晰，输出可校验。先把串行版本跑稳定，再逐步提高并行度，通常比一上来就上复杂编排更可靠。
