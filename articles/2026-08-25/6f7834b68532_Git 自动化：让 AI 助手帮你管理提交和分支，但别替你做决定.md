## 背景

在 OpenClaw 这类 agent 工作流里，代码维护经常是任务完成后的“最后一公里”。小修一个解析逻辑、改一下配置、补两行测试，都要手动跑 `git status`、看 diff、想 commit message、切分支。动作不复杂，但频率很高，很消耗注意力。

后来我把一部分 Git 操作拆给 AI 助手处理，原则很明确：**机械执行和初步判断交给 agent，破坏性决策和最终确认留给人。** 这篇文章记录我目前的实践方式、踩过的坑，以及可复用的封装思路。

## 问题

如果直接对 agent 说“帮我提交所有改动”，通常会得到几种结果：

- `git add -A` 把临时文件、本地配置、甚至没加进 `.gitignore` 的密钥一起暂存；
- commit message 千篇一律是 `update`、`fix bug`；
- 在错误分支上提交，或者把 main 当成工作分支；
- 大 diff 下 AI 开始“脑补”修改意图，生成的提交信息不准确。

所以 Git 自动化的难点不在“能不能执行命令”，而在**上下文边界和权限控制**。不解决这两个问题，自动化只会制造更多噪音提交和恢复成本。

## 做法 / 步骤

我目前的做法是分层：**只读诊断 -> 建议生成 -> 确认执行**。在 OpenClaw 里通过 Git MCP Server 或自定义 tool 封装，不直接暴露 shell。

### 1. 只提供只读工具集

给 agent 开放一组只读命令：

```
git status --porcelain=v1
git diff --stat
git diff --cached -- <path>
git branch --show-current
git log --oneline -10
```

这些足够让 agent 判断仓库状态，但不会产生任何写操作。

### 2. 提交信息生成

让 agent 基于 staged diff 生成 conventional commit 格式。提示词里给 few-shot 示例：

- `fix(auth): handle expired token refresh`
- `feat(parser): add fallback for missing fields`

要求 subject 不超过 72 字符，body 解释修改意图而不是复述文件名。生成后默认只展示，不直接提交。

### 3. 分支管理

从任务描述中提取分支名，例如中文任务转成 `feat/order-export-fix`。清理旧分支前先检查 `git branch --merged`，只允许删除已合并分支，并保护 `main/master/release/*`。agent 输出删除计划，经确认后执行。

### 4. 执行层白名单

定义允许执行的 git 操作：`add <specific files>`、`commit`、`branch`、`checkout -b`、`switch`、`status`、`diff`、`log`。明确禁止 `push --force`、`reset --hard`、`clean -fd`、`rebase`。

脚本层做参数校验：commit 必须带 message；add 的文件必须在仓库内且不能匹配敏感文件模式，例如 `.env`、`*.pem`、`*.key`。

### 5. 审计日志

每次 agent 调用写操作时，记录 action、command、before/after commit hash。可以用 OpenClaw 的 memory 插件，也可以直接写文件。出问题时能回溯到具体哪一步。

## 踩坑点

### 1. `git add -A` 是重灾区

我遇到过一次把 `.env.local` 提交进本地历史，虽然随后 reset，但已经足够让人警惕。现在规则是：agent 必须先列出未跟踪文件，由人确认 add 范围，再执行 stage。永远不让 AI 自己决定 `add -A`。

### 2. 长 diff 超出上下文

几千行 diff 时，AI 生成的 commit message 质量会急剧下降。解决方法是分文件提交，或者工具层只传 `--stat` 和关键文件 diff。我通常设置上限：超过 200 行 diff 就拆分处理。

### 3. pre-commit hook 修改文件

执行 commit 后，文件可能被 hook 格式化或修改，仓库状态会再次变脏。agent 可能误判为“提交失败”。封装工具时，commit 后必须重新执行 `git status --porcelain` 并把结果返回给 agent，让它感知真实状态。

### 4. 提交信息校验不能只靠模型

大模型偶尔会输出 `WIP`、`fix bug` 这类噪音。脚本层用正则校验 conventional commit 格式，不通过就拒绝提交，返回给用户手动处理。

### 5. 权限和分支保护

写操作使用带审批的 bot 账号，不要让 agent 使用你的主账号 SSH key。分支保护在服务端也要配置，不能只依赖 agent prompt。即使客户端被绕过，服务端仍然能拦住 force push。

## 可复用建议

- **工具粒度要小。** 不要做一个 `run_git_command` 万能工具，而是拆成 `get_status`、`stage_files`、`create_branch`、`commit`。粒度越小，越容易控制权限和审计。
- **优先使用现成 Git MCP Server。** 社区里有封装好的实现，重点看它是否支持 allowed commands 配置和只读模式。自己写 shell 解析容易出安全漏洞。
- **在系统提示词里写死约束。** 例如：`You may only call read-only git tools unless the user explicitly approves a write operation.` 这种前置约束比事后拦截更有效。
- **每个 commit 关联任务 ID。** 让 agent 在 body 里加 `Refs: #issue`，方便追溯到具体需求。
- **先做小范围试点。** 建议先只让 AI 生成提交信息，所有执行由人完成。跑一两周稳定后，再逐步开放自动创建分支和自动提交。

## 总结

Git 自动化适合作为 agent 工作流中的辅助层，而不是无人值守的写代码机器人。把只读诊断、建议生成、审批执行拆开，配合白名单、审计日志和分支保护，才能真正减少日常维护成本。否则一个误提交就可能花掉你更多时间恢复。

对 OpenClaw-CN 的同学来说，性价比最高的起点是：先接入只读工具和提交信息生成。等这两步跑稳了，再考虑自动提交和分支管理。
