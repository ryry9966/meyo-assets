## 背景

每个工程师都经历过这样的早晨：打开终端翻 git log，切到监控面板看告警，再去云平台检查定时任务执行情况，最后手动拼出一份日报。这个过程琐碎、易遗漏，且几乎没有任何技术积累价值。在 OpenClaw 社区中，越来越多的团队开始用 Agent + MCP 的思路接管这类重复性文字工作，但大多数方案要么过度设计，要么只能跑通 demo，一进生产就崩。

这篇文章记录了一次真实场景下的自动化日报生成流水线搭建过程。目标很明确：把多种来源的原始日志自动汇总、清洗、提取关键事件，按预设模板生成 Markdown 日报，最后推送到协作工具。

## 问题拆解

看似简单的“自动写日报”背后有几个痛点：

- **日志来源分散**：业务服务日志、Git 提交记录、CI/CD 执行结果、数据库定时任务状态，每种日志的访问方式和格式都不同。
- **时间对齐困难**：不同系统可能使用 UTC、本地时间甚至无时区信息，混在一起会让日报时间线混乱。
- **信号提取成本高**：原始日志中 90% 是噪音，真正需要写进日报的只有错误、重要操作和异常完成状态。
- **Agent 幻觉风险**：直接把全量日志丢给 LLM，它可能会编造没发生过的事件，或者遗漏关键信息。
- **可维护性差**：临时拼凑的脚本在日志格式变更后立刻炸掉，团队没人愿意长期维护。

针对这些问题，我们没有选择直接写一个巨大的 Python 脚本来“一锅乱炖”，而是设计了一条可拆解、可复用的处理流水线。

## 做法：四阶段流水线

整个流水线分为收集、解析、汇总、生成四个阶段，使用 OpenClaw 的 Agent 做编排，通过 MCP 连接各类日志源，模板引擎负责最终报告输出。

### 1. 收集阶段：统一接入层

利用 MCP Server 将不同日志源抽象为统一的文本资源。

- 对于本地文件日志（如 `/var/log/app/`），挂载 File System MCP Server，Agent 可以按日期范围读取文件内容。
- 对于 Git 提交记录，使用 Git MCP Server，提供 `git log --since/--until` 的能力。
- 对于 CI/CD 状态和定时任务，通过自建 HTTP MCP 将内部 API 包装成工具，Agent 可以直接查询指定时间区间内的 pipeline 结果或任务执行状态。

这一步的关键是 **时间参数标准化**：所有 MCP 工具统一接收 ISO 8601 格式的起止时间，由调用方（Agent）负责转换时区，避免下游各自理解时间。

### 2. 解析阶段：规则优先 + Agent 兜底

我们没有直接把原始日志扔给 LLM，而是先做一轮规则提取。原因很简单：规则快、稳定、成本低。

- 对于结构化的 JSON 日志，写 jq 表达式提取错误级别和高亮事件。
- 对于半结构化的 CI 输出，用正则匹配 `FAILED`、`ERROR`、`build time` 等关键词，生成摘要片段。
- 对于完全非结构化的文本日志，规则覆盖不了的部分，才将片段交给 Agent 做语义提取，并严格限制输出格式为 JSON 数组，要求必须包含 `source`, `timestamp`, `event`, `severity` 字段。

这样做既控制了 LLM 调用量，也为后续步骤留下了可审计的中间数据。

### 3. 汇总阶段：分片总结与去重

普通日报的长度通常在数百字以内，但原始日志的文本量可能达到数万 token，超过 Agent 的上下文窗口。我们的策略是“分片总结 + 关键事件聚合”：

- 将解析阶段产出的结构化事件按时间排序后，按 20 条一组分片，每片用 Agent 生成一小段自然语言描述。
- 再将所有片段的描述收集起来，做一次全局去重和优先级排序（错误 > 变更 > 一般信息）。
- 最后汇总成一份不超过 800 字的内部摘要，作为日报的核心内容。

这个过程中容易踩到一个坑：分片之间如果有跨时间的关联事件（比如一个操作在 9:00 触发了一个错误，10:00 得到修复），单独总结会丢失上下文。解决方案是让 Agent 在生成每段描述时，额外输出 `related_events` 列表，汇总阶段将这些关联事件合并描述，而不是各自独立呈现。

### 4. 生成阶段：模板化输出

日报格式需要稳定，不能每次都由 LLM 即兴创作，否则团队成员会抱怨格式变来变去。我们使用预先定义的 Jinja2 模板，将汇总阶段产出的结构化数据填入固定章节：

- 昨日核心指标（从监控系统获取，非日志）
- 变更记录（Git）
- 异常与告警
- 定时任务执行摘要
- 风险提示和待办事项（由 Agent 基于事件推理生成，但必须标注“由 AI 推断”）

最终 Markdown 报告通过飞书 Webhook MCP 插件推送到群，同时存档到 Git 仓库，方便回溯。

## 踩坑记录

1. **时区地狱**：某次 CI 日志使用 UTC，服务器日志使用 CST，8 小时偏差导致日报中事故发生在“未来”。所有时间戳在收集阶段统一转为 UTC 存储，生成报告时再转回本地时区。
2. **Agent 编造修复记录**：Git log 中没有任何关于某个 bug 的修复提交，但 Agent 因为看到了错误关闭的日志，直接写了一句“已修复”。解决方法是在提示词中严格限定：没有 git commit 记录的操作，不得声称修复完成，只能写“错误已消失，原因待查”。
3. **大文件 OOM**：某天的应用日志超过 200MB，File System MCP 直接全量读取导致 Agent 进程 OOM。后续改为流式读取，并设置了 5MB 截断上限，超出的部分仅保留错误行。
4. **模板漂移**：飞书消息格式一旦被 LLM 微调，就容易出现字符超出、Markdown 语法错误。最终我们将模板与 LLM 完全解耦，Agent 只生成纯数据，格式拼装由代码完成。

## 可复用建议

- **优先统一日志格式**：如果能把各系统的日志统一输出为 JSON（带 `level`、`message`、`timestamp` 字段），后续自动化成本会成倍下降。
- **MCP 作为边界层**：不要把日志抓取逻辑写在 Agent 里，MCP 提供了清晰的接口边界，切换日志源时改动最小。
- **保留中间态**：将解析后的结构化事件持久化到 SQLite 或 JSON 文件，不仅方便调试，还能在日报生成失败后快速重跑数据清洗部分，而不需要重新采集。
- **设置人工确认环节**：如果日报中包含 Warning 级别以上的事件，可以先推送到一个只对自己可见的渠道进行核验，确认无误再群发，避免传播错误信息。
- **用指标支撑日报**：纯粹的日志转述价值有限，最好能从 Prometheus 等监控系统拉取关键指标变化，融入日报，让报告更具决策意义。

## 总结

这条自动日报流水线运行几个月后，最大的收获并不是“省了每天 15 分钟”，而是日报内容变得标准化、可追溯，任何一项记录都能快速定位到原始日志。对于 OpenClaw 社区的实践者来说，自动化日报是个很好的切入口——既足够简单，让你可以用它来验证 Agent + MCP 的编排能力，又足够有代表性，能暴露出日志处理、幻觉控制、上下文管理等工程问题。如果你想尝试，建议从 1～2 个日志源开始，先把“收集-解析-模板”这条全自动链路跑通，再逐步接入更多数据源和智能总结能力。
