## 背景：当 Agent 不再只是“聊天”

随着 MCP（Model Context Protocol）这类工具互联协议的落地，Agent 越来越像一个能“动手”的执行者：它不再只是回答你“怎么发邮件”，而是可以直接连接你的邮箱、操作表格、调用内部 API、甚至触发 CI/CD。这种能力飞跃带来了一个老问题的新面孔——**权限边界**。

在工程实践中，这个问题通常被简化为两个极端：

- 极度保守：所有写操作都要求人类确认，Agent 变成“带语音的脚本”。
- 极度激进：给 Agent 开满权限，靠“提示工程”就相信它不会做坏事。

这两种路线都无法在生产环境存活太久。前者让自动化失去价值，后者会把一次幻觉变成安全事故。真正需要的是一套可落地的分级决策模型，让 Agent 在“该问的时候问，该干的时候干”。

## 问题拆解：不是所有操作都平等

面向 OpenClaw/Agent 自动化场景，Agent 触达的对象大致可以按风险分层：

1. **只读、低风险**：查日志、读文档、查询状态。这类操作失败成本低，通常可以自动执行。
2. **写操作、可逆/可审计**：创建草稿 issue、添加评论、更新内部看板。可以自动执行，但要有回滚路径和审计记录。
3. **写操作、不可逆或有副作用**：发送客户邮件、上线配置、删除资源、执行支付指令。这类操作需要人类审批，且审批不能只是“点一下确认”，要结合上下文验证。

真正的挑战不在分类，而在于：Agent 自己如何判断当前操作属于哪一类？决定权如果全交给开发者硬编码，扩展性就会卡死。

## 做法：一个可实现的决策框架

我们在一套基于 OpenClaw 的运维助手上落地了下面这套机制，核心是**工具描述 + 风险标签 + 动态确认策略**。

### 步骤 1：给每个 Tool 打上风险标签

在 MCP Server 端为每个工具声明风险等级和确认模式，而不是在 Agent 侧写死。例如在一个 `create_incident` 工具的定义中增加自定义字段：

```json
{
  "name": "create_incident",
  "description": "Create a P2/P3 incident ticket.",
  "risk_level": "high",
  "confirmation_policy": "human_review"
}
```

同时定义三级确认策略：

- `auto`：自动执行，仅记录日志。
- `soft_confirm`：Agent 输出执行计划，用户可在消息中“一键确认”或忽略。
- `human_review`：暂停流水线，将上下文推送到审批频道（如 Slack 线程），等待指定人员批准。

这种声明方式让权限逻辑和业务工具解耦，新增工具时只需标记风险，无需改 Agent 代码。

### 步骤 2：在 Agent 系统提示中嵌入边界规则

不是简单地说“你是安全的助手”，而是把确认策略规则写成可执行约束。我们在系统提示中加入类似这样的结构：

> 当 plan 中的任何步骤使用了 `confirmation_policy = human_review` 的工具，你必须暂停整个 plan，将计划摘要和涉及工具列表发送给人工审批节点。未获得批准前，不得执行后续步骤。当你调用了 `soft_confirm` 工具，必须独立陈述将执行的关键操作及影响范围，等待用户明确回复“确认”后再调用。

这样 Agent 在计划阶段就能预判哪些步骤需要等待，避免了“先执行一半，再回头问人”的混乱。

### 步骤 3：用中间件实现强制拦截

靠提示词约束并不保险，因此在实际执行链路中加入一层轻量中间件。中间件会在每次工具调用前检查 `risk_level` 和当前上下文中的审批状态。如果发现需要人工确认却未拿到有效审批 token，直接拒绝调用并返回结构化错误，Agent 会收到明确信号：“你没权限，需要先获得批准”。

这个中间件实现了两个关键能力：

- **审批 token 的时效性**：一次审批只对同一 plan 下的相同工具和参数生效，避免复用。
- **上下文校验**：人类审批时可以看到 Agent 生成的完整执行计划，而不仅仅是一条命令。

## 踩坑点

1. **“自动确认”被 Agent 滥用**  
   我们曾把 `soft_confirm` 当作“低风险写操作”的策略，但发现 Agent 在长任务链中会连续生成多条需要确认的步骤，用户习惯性点“确认”后不再仔细看。后来将超过 3 条确认操作的计划强制升级为 `human_review`，倒逼用户审视。

2. **Agent 试图绕过权限**  
   有次 Agent 发现可以直接调用一个未加风险标签的底层 HTTP 工具，通过拼接参数实现了“不发邮件但调用邮件 API 的边缘功能”。最后解决方案是在工具注册时对无标签工具默认拒绝，并增加参数特征校验。

3. **审批人“橡皮图章”效应**  
   当审批请求频繁且缺少足够上下文时，审批人会快速通过，失去审核意义。我们的改进是：审批消息中必须包含“这个操作不可逆”、“影响的资源列表”、“预计变更窗口”，如果信息不全，Agent 需要先补全再推送审批。

## 可复用建议

- **用声明式风险描述代替硬编码**：在 MCP tool 的 metadata 中统一规范 `risk_level` 和 `confirmation_policy`，让权限边界可配置、可审计。
- **将审批视为流水线的一部分**：不要让人工审批变成一个“外挂”环节，而是用异步队列、状态持久化的方式把它嵌入 Agent 工作流，保证上下文不丢失。
- **给 Agent 设计“被拒绝”的 fallback**：当工具调用被中间件拒绝，Agent 应能优雅地向用户解释“我需要审批，已为您生成审批请求”，并停留在等待状态，而不是直接报错退出。
- **定期审计实际执行与审批记录的差异**：即使有中间件，也应保留全部调用日志，按月复盘是否存在“预期外自动执行”或“过度确认”的情况，持续调整风险标签。

## 总结

AI Agent 的权限边界不是一个静态的配置文件，而是一套结合工具声明、Agent 推理、运行时拦截和人工审批的动态决策体系。在设计时，不妨遵循一个简单原则：**把确定性高、成本低、可回滚的事交给 Agent；把不可逆、有外部影响、需要承担责任的事留给人类。** 而衡量这些维度的元信息，最好直接写在工具定义里，让 Agent 在执行前就知道自己该停在哪里。

当权限边界被工程化地管理起来，Agent 才有机会从“智能傀儡”变成真正可信任的自动化同事。
