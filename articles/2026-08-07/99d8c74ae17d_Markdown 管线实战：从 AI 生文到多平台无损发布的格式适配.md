## 背景

在 OpenClaw 的自动化内容管线里，越来越多的工作流依赖 LLM 直接产出 Markdown，然后分发到多个平台：微信公众号、知乎、Notion 文档库、GitHub Pages、邮件列表，甚至是内部基于 Markdown 的 CMS。问题是，这些“消费者”对 Markdown 的支持并不统一。同一份 AI 生成文本在 Obsidian 里排版精美，到了公众号后台可能标题层级丢失、代码块塌缩、数学公式完全不渲染。手工逐一适配既脆弱又不可规模化，于是需要一条工程化的 **Markdown 格式适配管线**。

## 问题拆解

典型的坑集中在三类：

1. **语法集冲突**：微信仅支持极简 HTML 子集，不用标准 Markdown；知乎编辑器能解析多数基本语法，但对围栏代码块的语言标注处理飘忽；Notion 的 Markdown 导入器会把 `#` 标题转为数据库属性。
2. **富元素丢失/变形**：LaTeX 公式、Mermaid 图表、内嵌 HTML、脚注等，在不同目标端表现完全不同。
3. **元数据与样式的携带**：YAML front matter 在多数发布平台需要剥离，但封面图、描述、标签等信息又必须保留。

如果只是写一个“转公众号格式”的脚本，后续每增加一个发布渠道就得补一个补丁。因此我们需要的是**管线化**的转换层，能够在 Agent 或 MCP 工具链中位置明确，可组合、可测试。

## 做法：构建三阶段管线

把格式适配拆成三个可复用的阶段：

**阶段一：规范化（Normalize）**

将 AI 产出的原始 Markdown 转为严格的 CommonMark 子集，并修复常见瑕疵。用 OpenClaw 的 `post_process` 钩子或一个 MCP 服务实现。规则包括：
- 统一换行为 LF，移除行尾空格。
- 将 4 空格缩进代码块转换为围栏代码块（确保平台兼容）。
- 为无语言标注的围栏代码块自动补充 `text`，避免后续高亮库报错。
- 将 HTML 标签标准化（如 `<br>` 转 `<br/>`）。
- 提取 front matter，序列化为独立 JSON 供后续阶段使用。

这个阶段的输出是所有下游都可以接受的最小公共集。

**阶段二：适配（Adapt）**

针对目标平台套用不同的 **规则集合**。每个规则集可以是一个 YAML 配置文件，由插件读取执行。常见的规则：
- **微信公众号**：将图片链接替换为微信素材 media_id 占位，由前置上传步骤填充；剥离除 `<strong>`, `<em>`, `<p>`, `<img>`, `<br>` 外的所有 HTML 标签；代码块转为带灰色背景的 `<pre>` 片段（内联样式）；将 `###` 以下标题降级为加粗段落，因为公众号最多显示两级标题。
- **知乎**：保留标准 Markdown，但转义 `@` 和 `#` 以防止误触发提及和话题；数学公式从 `$$` 转为知乎支持的 `![](https://www.zhihu.com/equation?tex=...)` 格式。
- **Notion**：将 Markdown 转为 Notion API 的 blocks JSON。这里可以调用一个 MCP 服务，内部用 `turndown` 反向转换时保证表格、折叠块的正确映射。
- **GitHub Pages**：保持原样，仅修改内部链接路径以适配 Jekyll 目录结构。

**阶段三：验证（Validate）**

适配后输出需要自动化检查，防止上线后翻车。可以在 OpenClaw 的任务流水线中加入校验步骤：
- 长度截断检查（公众号正文上限）。
- 非法字符扫描（如零宽字符、不可见控制符）。
- 图片链接可达性探测（HEAD 请求）。
- 对比原文与适配后文本的段落数量，防止意外丢失内容。

如果使用 MCP 工具，可以让 LLM 主控节点调用一个“lint-markdown”工具，返回诊断结果，驱动重试修复。

## 踩坑与排查

- **围栏代码块语言标注的兼容性**：最初以为可以保留 `python`，但微信公众号会把 `<code>` 里的内容当普通文本处理，若代码中含有 `<` 或 `>`，需做 HTML 实体转义，否则内容被吞。所以这个转义必须在公众号适配器中后置执行。
- **表格的幻灭**：多数轻写作平台不支持复杂 table。方案是把 >3 列的表格在适配阶段渲染成 Markdown 图片（用 Node 调 headless 浏览器截图），同时保留原始表格文本作为无障碍回退，放入 `alt`。
- **数学公式的双路径发布**：知乎支持 URL 公式，公众号完全没有。做法是：公众号适配器自动将 `$...$` 转为 SVG 图片链接（提前用 MathJax 渲染），再上传为微信素材。渲染时机放在管线阶段二，设计成可配置的图片化阈值（inline 公式默认不转）。
- **MCP 工具的幂等性**：一旦适配失败，Agent 可能重复调用转换。确保 MCP 工具接收原始规范化结果和平台标识，总是产生相同输出，不依赖外部状态，方便重放。

## 可复用建议

1. **定义内部中间表示（IR）**：不要直接面对各平台写一堆 `if-else`。将规范化后的 CommonMark AST 作为 IR，各适配器仅操作 AST 进行裁剪和增强，保证可测试性。推荐用 `unified` / `remark` 生态处理 AST。
2. **将适配规则配置化**：发布平台、规则集、后期脚本路径都放在 YAML 里，Agent 根据发布任务动态加载，无需修改管线代码。
3. **用 CI 做格式回归**：每次改动适配规则后，跑一遍包含所有目标平台的转换并截图对比。OpenClaw 管线若支持子任务并行，可以同时适配到多个平台，再触发视觉比对。
4. **预置最低渲染保障**：把每个平台的适配结果包装为一个 `Renderer` 接口（`render(normalizedAST, metadata) => string`），并附带回退机制：若专有适配失败，退回到纯文本输出，保证内容至少可读。
5. **接入 MCP 服务生态**：把规范化器和各平台适配器封装为 MCP 工具，LLM 可按需组合调用，而不是硬编码流程，为后续增加新平台提供灵活性。

## 总结

从 AI 生成 Markdown 到多平台发布，真正的挑战不是某一种格式的转换，而是如何构建可维护、可扩展的管线。通过“规范化-适配-验证”三阶段架构，结合 AST 操作、配置驱动的规则集和 MCP 服务封装，可以在 OpenClaw 的自动化流程中获得稳定、可审计的发布输出。这套管线已经在我们团队的内容运营工作里持续运行，适配平台从 3 个扩展到 7 个，新增一个平台只需添加一个 YAML 规则集和对应的轻量适配器函数，总体改造成本很低。**

最后的彩蛋**：别相信任何一个平台“完全支持 Markdown”的承诺，用管线去验证，而不是用肉眼。
