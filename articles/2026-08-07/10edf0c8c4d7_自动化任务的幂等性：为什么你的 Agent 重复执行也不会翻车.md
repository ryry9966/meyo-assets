# 自动化任务的幂等性：为什么你的 Agent 重复执行也不会翻车

在 OpenClaw 上运行的 Agent，经常要处理来自 MCP 工具、定时调度或 Webhook 的触发。无论是爬取、入库、发通知还是调外部 API，总绕不开一个问题：同样的任务被重复触发，凭什么不出错？

这不是“偶尔重复”的小概率事件。调度器重试、手动补跑、消息队列 at-least-once 语义，都会让你的插件或 Agent 不期而遇地执行两次以上。如果不做幂等设计，数据重复、状态异常、对外服务被重复调用就是家常便饭。这篇文章不谈理论概念，只讲在 OpenClaw 自动化实践里，如何让重复执行成为安全操作。

## 哪些场景最容易踩坑

通常有三类操作特别需要幂等保护：

1. **外部写操作**：调用第三方 API 创建资源（如发邮件、建工单、推送消息）。对方没有幂等接口，多次调用就会产生多条重复记录。
2. **数据库插入**：看似简单的 INSERT，如果没设计好唯一约束，每次 Agent 重跑就多一行脏数据。
3. **状态转移**：把任务从“待处理”改成“已完成”，如果没有条件更新（如乐观锁），并发时可能出现状态跳跃或重复处理。

举个例子：一个监听邮件并自动创建工单的 Agent，收到同一封邮件两次（webhook 重发），如果没有去重机制，就会在工单系统里多出一条完全相同的记录。

## 设计幂等的工程化步骤

让任务幂等不是加一行 `if` 判断就完事，需要从“鉴别、存储、决策”三个环节去落地。

### 1. 确定幂等键（Idempotency Key）

找到一个能唯一标识本次业务操作的“业务键”。尽量使用上游系统提供的天然标识，比如邮件 Message-ID、订单号、GitHub event ID。如果实在没有，可以用“关键字段组合 + 时间窗口”生成 hash，但要注意组合字段的稳定性。

在 OpenClaw 的 Agent 里，通常可以在插件上下文的 metadata 中携带这个 key。对于 MCP 工具调用，也可以在调用参数里显式传入 `request_id`，由工具提供方支持幂等。

### 2. 建立防重检查层

在真正执行业务逻辑之前，拿幂等键去一个原子存储中做“已处理”标记。最简单的方案是用数据库的唯一约束：

```sql
INSERT INTO idempotency_records (key, created_at)
VALUES ('evt_123456', now());
```

如果 key 已存在，插入会报唯一键冲突，捕获这个异常直接跳过后续操作。数据库的 ACID 特性天然适合做这件事，比在代码里用 `setnx` 加锁更可靠——后者需要处理超时、故障时的状态回滚。

对于超大规模任务，可以使用 Redis 的 `SET key value NX EX seconds`，但必须结合业务失效窗口和一致性风险做权衡。

### 3. 让业务操作本身变得安全

即使去重检查过了，业务操作仍需防御性设计：

- **数据库写入**：能用 `INSERT ... ON CONFLICT DO NOTHING` 就不要用普通 INSERT，同时配合业务键的唯一索引。
- **外部 API 调用**：如果对方支持幂等键，优先使用；若不支持，就在本地维护“调用记录 + 返回结果”的映射，一旦发现已存在相同 key 的调用，直接返回缓存响应。
- **状态流转**：务必用 `UPDATE tasks SET status = 'done' WHERE id = ? AND status = 'pending'` 这种条件更新，并检查 affected rows。多个 Agent 同时跑也不会出现状态覆盖。

### 4. 处理 MCP 工具调用的幂等

当你的 Agent 调用 MCP Server 暴露的工具（比如 `create_document`），幂等性不能只靠 MCP 层的重试机制。好的实践是：在 Agent 的调用封装层挂一个幂等装饰器，记录调用指纹（工具名 + 参数 hash + 业务时间窗），若发生重复，直接短路返回上次的成功结果。

如果 MCP 工具提供了 `idempotency_key` 参数，Agent 需要在运行时生成稳定的 key 并注入。如果不提供，可以改变调度方式：对于不幂等的工具，只允许 exactly-once 触发，由外部调度器保证（比如使用支持去重的消息队列）。

## 踩过的坑

在实际落地中，有几个容易翻车的地方：

- **时间窗口不一致**：为了节省存储，幂等记录往往设置过期（如 24 小时）。但上游系统可能超过这个窗口重放事件，导致防重失效。应该根据业务最大重试间隔设置过期，或者使用分区表存储长周期 key。
- **分布式并发竞争**：用“先查再插”模式在并发下必然有 race condition。必须依赖数据库唯一约束或原子的 `INSERT ... ON DUPLICATE KEY` 类语句。不要在应用层判断。
- **MCP 调用超时的伪幂等**：第一次调用 MCP 工具超时了，Agent 判定失败并重试，但实际服务端已经执行成功。这种情况靠本地幂等 key 无法解决，需要 MCP 服务端支持幂等或者查询接口做状态核对。
- **指纹不唯一**：用业务字段拼出的 key 可能因为时区、格式差异而不一致。建议在源头统一格式化后再生成指纹，或直接使用上游系统透传的独特标识。

## 可复用的实践建议

1. **把幂等性变成插件的默认能力**：在 OpenClaw 插件基类里增加 `with_idempotency(key, handler)` 的辅助方法，让每个需要防重的步骤自动走去重存储。
2. **统一幂等记录存储**：维护一张通用幂等表，包含 `key`, `result`, `expire_at`。不仅防止重复执行，还可用于返回缓存的执行结果，降低下游压力。
3. **测试时模拟重复场景**：手动触发两次相同事件、故意让任务超时重试、在并发测试中使用 `parallel` 工具，确保幂等机制在这些场景下都稳健。
4. **MCP 工具评估标准**：在选型或自建 MCP 工具时，将“是否支持幂等调用”作为安全性的一票否决项。对不支持的，必须在 Agent 侧补齐防御层。

## 总结

自动化任务的幂等性，本质不是“阻止第二次执行”，而是让第二次、第三次执行和第一次一样安全无害。它的核心在于一个稳定的身份标识、一个原子化的防重标记和一套防御性的业务处理模式。

在 OpenClaw 生态里，Agent 的可靠性不是靠祈祷“只执行一次”，而是靠工程上扎实的去重设计。把这套机制内建到你的插件和 MCP 集成里，重复执行就不再是需要焦虑的异常，而是系统韧性的体现。
