## 背景

OpenClaw 社区里越来越多的团队开始把 Agent、MCP 工具链和自动化插件直接接进协作空间，让 AI 参与问题答疑、代码审查、知识库检索甚至部分工作流的自动执行。这种深度的集成在提高效率的同时，也打开了新的信息泄漏面：Agent 很可能会在回复、总结、自动生成的记录中，无意间把内部工作流的设计细节、密钥片段、项目代号甚至商业敏感数据带到社区对话里。

常见的风险入口包括：

- 通过 MCP 工具调用了内部接口，Agent 把返回结果原文嵌入最终呈现给社区成员。
- 插件在解析工作流日志时，把包含内部路径、内网 IP 的调试信息直接吐出。
- 开发者为了方便，直接把包含敏感信息的 Prompt 或知识库接入 Agent，没有做脱敏处理。
- Agent 的“记忆”或上下文窗口里积攒了多轮对话，混入了早期的私密信息，被后续的社区成员通过追问诱导出来。

下面我会从工程化的角度，梳理一套可以在 OpenClaw + MCP 体系下落地的防泄漏做法、几个容易被忽视的踩坑点，以及可以直接复用的安全 CheckList。

## 核心做法与步骤

### 1. 给 Agent 的上下文做“最小化与脱敏”

任何 Agent 可见的上下文，都要假设它有可能被原样输出到公共频道。因此，在组装 Prompt 或提供工具调用结果时，最好在插件层完成一次强制脱敏：

- **字段级过滤**：对 JSON 返回、数据库查询结果，移除 `secret`、`token`、`password`、`private_key` 等敏感字段，或者替换成占位符 `[REDACTED]`。
- **正则脱敏层**：在 OpenClaw 的自定义插件中插入一个预处理钩子，用正则匹配常见泄漏模式：API Key（形如 `sk-xxx`）、AWS Secret Key、JWT Token、内网 IPv4 地址（`10.x.x.x`, `192.168.x.x`）、信用卡号、邮箱地址等，统一替换为 `[FILTERED]`。
- **领域词屏蔽列表**：维护一份不允许出现在公开输出中的关键词清单（如内部项目代号、客户名称、内部系统 URL），一旦命中，触发告警并阻止输出。

实现上可以在 MCP 的服务端代理一层，所有工具调用的原始输出先过脱敏过滤器，再交给 LLM。

### 2. 输出审查与拦截

不能寄希望于模型自己判断是否泄密，必须在 Agent 生成的最终消息推送到社区之前，再加一道输出安全门。

- **安全评分模型**：用另一个轻量级模型（或者基于规则引擎）对输出文本进行敏感度评分，高于阈值的消息自动进入人工审核队列或直接丢弃，并通知管理员。
- **黑白名单动作**：对明确的机密模式，如私钥头 `-----BEGIN RSA PRIVATE KEY-----`，直接阻断发送，返回系统预设的“回复过滤”提示。
- **上下文 diff 对比**：如果 Agent 被要求基于给定文档回答，可以在输出阶段对比“原始文档片段”与“回答”的相似度，如果逐字复制了过多内部文档内容（尤其是非公开段落），也算一种泄漏，需要拦截。

### 3. 工作流与权限的隔离设计

- **MCP 工具权限分级**：把工具分成“只读公开数据”、“只读内部数据”、“写入操作”等级别，绑定到不同 Agent 实例。面向社区的 Agent 绝对不允许挂载任何能访问含内部数据源的工具。
- **会话域隔离**：每次社区会话都使用独立的 Agent 会话，禁止跨对话的记忆共享。如果必须使用长期记忆，将其严格限制在“用户偏好”、“公开知识”等安全域，并通过 RAG 引擎控制检索范围。
- **日志脱敏**：Agent 运行日志、工具调用记录如果对开发者可见，也要做同样的脱敏处理，避免通过日志间接泄漏信息到协作文档或 issue 讨论中。

### 4. 可复用的自动化流程（与 OpenClaw 集成）

可以把上面的步骤打包成一个 OpenClaw 安全插件，在 Agent 声明周期中插入三个钩子：

1. **pre-llm-hook**：清洗所有进入 LLM 的上下文。
2. **post-llm-hook**：对 LLM 原始输出做规则 + 模型过滤。
3. **pre-reply-hook**：最终发布前再做一次关键词扫描。

配置示例（概念）：
```yaml
security_guard:
  enable: true
  pre_filter:
    regex_patterns:
      - "(?i)(sk-[a-zA-Z0-9]{20,})"
      - "(?i)(aws_secret_access_key[=: ]+[A-Za-z0-9/+=]{20,})"
    redact_replacement: "[SECURED]"
  output_filter:
    max_similarity_to_source: 0.85
    block_on_score_threshold: 0.7
  reply_filter:
    forbidden_keywords_path: "/etc/openclaw/blacklist.txt"
```

## 踩坑点

1. **“过滤了就安全”是幻觉**  
   正则只能对付固定模式，无法防御经过变形的敏感信息（如 Base64 编码、分片拼接）。攻击者可能引导 Agent 多次输出部分信息，再组合还原。需要配合语义分析和上下文累积监控。

2. **脱敏过度导致功能不可用**  
   过度替换会破坏代码、配置示例，让 Agent 在回答技术问题时毫无价值。需要细致地按类型分级处理，例如对代码块内的可疑字符串只标记而不删除，同时加提示。

3. **插件链性能与延迟**  
   多道过滤如果都在关键路径上，会增加 1~3 秒延迟。建议把重量级模型检查放在异步队列，但阻止消息发送必须是同步的；此时可使用缓存和启发式规则先快速拦截。

4. **社区平台自身的缓存/引用机制**  
   Agent 输出一旦发送，即使后来发现泄密并删除，也可能已被截屏、引用、搜索引擎收录。防御重点必须放在“不发出”而非“事后删除”。

## 可复用建议

- **建立安全基线清单**，纳入团队 Agent 上线前的 Checklist：
  - [ ] 所有 MCP 工具均完成数据脱敏代理。
  - [ ] 输出端部署关键词黑名单和模式匹配。
  - [ ] 面向公共频道的 Agent 无任何“写”权限。
  - [ ] 日志和长期记忆经过独立脱敏处理。
  - [ ] 定期用“诱导性测试用例”做红队演练，验证 Agent 是否会泄漏特定内部信息。
- **渐进式脱敏**：先在开发环境完全明文运行，观察实际输出的信息类型，再提炼出需要屏蔽的特征，避免一开始就过度设计。
- **利用 OpenClaw 插件市场** 或内部共享，把安全模块组件化，多个 Agent 复用同一个安全配置，降低维护成本。

## 总结

Agent 在社区中泄密不是会不会发生的问题，而是何时发生、严重到什么程度的问题。应对核心是“信任最小化”：不要把希望寄托在 LLM 自身的判断上，而是在上下文入口、输出出口、工具权限三个层面分别设防。紧密结合 OpenClaw 的插件机制和 MCP 的工具代理层，可以把安全红线转化为一组可工程化、可审计的自动流程，让 AI 既能帮到社区，又不会成为泄露内部信息的缺口。
