# OpenClaw 沙箱安全模型拆解：为什么你的 Agent 不会一把梭删掉整个项目

## 背景：Agent 操作文件是刚需，也是最危险的边界

只要你的 Agent 不止于聊天——不管是做本地自动化、MCP 工具链、代码补全还是插件编排，文件系统的读写几乎绕不开。一旦 Agent 拥有了 `write_file` / `delete_file` 这样的能力，安全边界就不再是一个口号，而是一个实打实的工程问题。

传统做法是把“是否允许删除”交给用户确认，或者在 prompt 里反复强调“不要删重要文件”。但这两种方式都极其脆弱：确认弹窗破坏自动化流程，prompt 约束则完全依赖模型自觉，任何一次幻觉都可能导致灾难。

OpenClaw 从设计之初就把“文件操作安全”作为 Agent 运行时的第一性约束，而不是事后补丁。它的 answer 是一套轻量但分层的沙箱模型。

## 问题拆解：误删文件到底是怎么发生的？

在真实工程中，Agent“误删文件”通常不是因为它有主观恶意，而是三类情况的叠加：

1. **路径解析错误**：模型生成了相对路径 `../../config.yml`，但运行时上下文让它误以为自己在另一个工作目录。
2. **操作语义混淆**：模型把“删除临时文件”理解成“清理整个 build 目录”，但参数传成了项目根。
3. **权限无边界**：Agent 拥有和宿主进程一样的文件系统权限，删 `/etc` 和删 `./tmp` 对它来说是一样的 syscall。

这三条的根因不是模型不够聪明，而是**缺少运行时的硬隔离**。

## OpenClaw 的做法：三层沙箱，卡住每一个误操作路径

### 第一层：工作区边界（Workspace Root Jail）

OpenClaw 的所有文件操作默认被限定在一个显式声明的 `workspace_root` 内。这个路径可以是项目根、可以是 `/home/user/agent-sandbox`，但无论如何，Agent 无法通过 `..` 跳出这个目录。

实现上并不是简单的字符串前缀匹配，而是调用 OS 层面的 `realpath` 解析后再做前缀比对。也就是说，即使模型生成 `../../etc/passwd`，OpenClaw 也会先在真实文件系统上解析出绝对路径，然后发现它不在 workspace_root 的子树内，直接拒绝执行并返回结构化错误。

这个机制非常硬，相当于在文件和 Agent 之间加了一层 chroot 式的逻辑隔离（虽然不是真正的内核 namespace，但足够应对绝大多数自动化场景）。

### 第二层：操作白名单与令牌机制

OpenClaw 把文件操作分为三个安全等级：

- **Read-only**：读文件、列出目录、获取元数据。默认开放，无需令牌。
- **Write-restricted**：写文件、创建目录。需要声明式授权，可以在 task 级别配置写入允许的路径前缀。
- **Destructive**：删除文件/目录、重命名、移动。这一等级默认被禁用，除非用户显式在 task 配置中打开 `allow_destructive_ops` 并且绑定一个一次性的操作令牌（op token）。

令牌机制的意义在于：即使你的 task 描述里写了“清理构建产物”，Agent 也不能直接执行 `rm -rf`。它必须先生成一个操作计划，包含要删除的具体文件列表，然后向 sandbox 请求一个针对这些路径的令牌。令牌是路径绑定且有时效的，且每次令牌签发都会记录在审计日志里。

这样就把“意图”和“执行”拆开了，哪怕模型幻觉生成了一句“删掉所有文件”，sandbox 也会因为拿不到覆盖整个 workspace_root 的令牌而拒绝执行。

### 第三层：dry-run 模式与预检审计

对于写入和删除类操作，OpenClaw 还提供了一个 dry-run 通道：Agent 可以先声明它想做什么操作，sandbox 只返回“如果允许执行，会对哪些文件产生什么影响”，而不真正落盘。

这个模式在自动化流水线里特别有用。比如你让 Agent 清理三天前的日志，它会先 dry-run 一把，输出一个文件清单，你或者上层编排逻辑可以快速扫一眼，再决定是否真正执行。

## 踩坑点：那些看起来没问题但会翻车的细节

在实践中，有两个容易忽视的坑：

**1. 软链接破界**

如果你的 workspace_root 内有指向外部的软链接，`realpath` 解析后的路径会跳出边界。OpenClaw 默认会拒绝跟随指向外部的 symlink 进行写入或删除，但读操作不受影响。这意味着如果 Agent 被允许读取一个指向 `/etc/` 的 link，它其实可以读到外部文件内容。解决方法很简单：创建 workspace 前保证内部没有外部指向的 symlink，或者在 task 配置中打开 `symlink_follow_restrict`。

**2. 路径匹配与 glob 展开**

Agent 经常用 `*.log` 这种 glob 来批量操作，但 glob 展开发生在 sandbox 内部，而不是模型侧。如果展开后的文件列表里包含一个在 writable 白名单之外的路径（比如 `../outside.log`），sandbox 会整批拒绝，而不是部分执行。这时候 Agent 可能会误以为自己操作成功了，因为它的生成文本里没有接收到异常。想要避免这种情况，建议在 task 模板里加入“操作后必须自检文件列表”的强制步骤，并且把错误信息以 JSON 格式返回给模型上下文。

## 可复用建议：如何给自己的 Agent 加类似的安全层

即使你暂时没有用 OpenClaw，这套三层模型也可以部分复用到你自己的 MCP 工具或插件上：

- **文件操作统一走一层 proxy 函数**，内部做路径解析和白名单匹配，绝不让 Agent 直接调用 `os.remove`。
- **引入操作令牌**，哪怕只是内存中的一个简单字典，记录“预期操作路径+时间窗”，也能大幅降低误删风险。
- **dry-run 优先**，尤其是批量删除、重命名等操作，先返回影响清单，确认后再执行，这在自动化脚本里是零成本的安全增益。
- **把 sandbox 错误信息结构化喂回模型**，让 Agent 知道“不是我不做，是安全层拦了”，避免它重复尝试或产生错误记忆。

## 总结

OpenClaw 的沙箱安全模型把“防止误删文件”这件事从 prompt 层面的祈祷，变成了运行时层面的多层约束：工作区隔离挡住路径逃逸，操作令牌切断直接执行危险动作的通路，dry-run 提供了可审计的操作预演。三层组合下来，Agent 即使产生删除意图，也必须穿过一道道显式授权才能落盘。

这不是过度设计，而是让 Agent 真正进入日常文件操作的必要前提。当你的自动化流程不再需要有人盯着“它会不会删库”，工程信心才能真正建立起来。
