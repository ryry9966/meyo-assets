在 OpenClaw、Agent 或 MCP 工具链里，让 LLM 输出结构化数据几乎是标配。JSON 是最常见的选择，但真实场景里，模型返回的往往不是单纯的 `{"key":"value"}`。它可能被包在 markdown 代码块中，前后夹带解释性文字，甚至同时混用 XML 标签和多段 JSON。本文将围绕这些“脏”输出，谈一谈防御性解析的工程实践。

## 一、背景：为什么输出总是不干净
当你在 prompt 中要求“只输出 JSON，不要其他内容”时，LLM 仍然可能：
- 用 ` ```json` 包裹，甚至用 ` ```` 无语言标注。
- 先输出一句“好的，这是结果：”然后再给 JSON。
- 为多个步骤返回多个 JSON 块，或混合使用 `<tool_call>` 这类 XML 标签。
- 由于 token 限制，JSON 在中间被截断。

自动化流水线如果只靠 `JSON.parse`，一次格式异常就能让整个 Agent 任务中断。因此，防御性编程不是过度设计，而是保证系统鲁棒性的基本要求。

## 二、问题定位：解析脆弱的三种典型表现
1. **裸 JSON 正常，但代码块包裹就报错** —— 解析器没有预先剥离 markdown 标记。
2. **多段 JSON 或标签混用时，只取了第一段** —— 缺少按需匹配的逻辑，比如需要从 `<result>` 标签内精准提取。
3. **截断 JSON 直接导致异常退出** —— 没有容错修复机制，比如自动补全括号或降级处理。

这些问题的根源在于：我们期望模型输出遵守协议，但工程上必须假设协议会被违反。

## 三、做法与步骤：构建健壮的解析管道
### 1. 提取候选 JSON 片段
不要直接将整个 response 丢给解析器。先用正则提取可能的 JSON 对象/数组：
- 匹配 ` ```json` 或 ` ``` ` 代码块内容。
- 匹配裸 JSON 对象（以 `{` 开头、`}` 结尾）或数组（以 `[` 开头、`]` 结尾）。
- 如果业务协议使用了自定义 XML 标签，如 `<function_call>`，则优先提取标签内文本，再对内容尝试 JSON 解析。

注意：要用非贪婪匹配，并处理多个候选片段的情况。

### 2. 顺序尝试解析
对提取到的每个候选片段，依次尝试 `JSON.parse`，直到成功或全部失败。这样做的好处是，就算模型在回答前面加了一句“这里是对应的数据：”，真正 JSON 依然能被捕获。

### 3. 对截断 JSON 的修复性解析
如果所有片段都无法直接解析，说明可能存在截断。可尝试：
- 使用栈扫描，自动补全缺失的 `}` 或 `]`。
- 对数组，若最后一个元素不完整（如字符串未闭合），移除该元素再解析。
- 使用类似 `jsonrepair` 的轻量库（若环境允许），但需谨慎控制依赖。

截断 JSON 恢复出来的数据可能丢失最后部分字段，因此要在业务层有默认值兜底，并在日志中标记“partial JSON repaired”。

### 4. 结构化校验与降级
解析通过后，仍需做 schema 校验。例如用 JSON Schema 或简单的类型检查，确保必需字段存在、类型正确。如果校验失败，根据场景决定：
- **关键路径**：重试（配置重试次数与退避），重试时可以调整 prompt 加大强调格式约束。
- **非关键路径**：使用安全默认值，记录异常指标，让流程继续。

## 四、踩坑点
- **多编码与不可见字符**：尤其在使用某些在线 LLM 接口时，response 中可能混入零宽字符或 BOM。解析前做一次 `trim()` 和不可见字符清洗是必要的。
- **数字与布尔被模型写成字符串**：`"true"` 与 `true` 的差异，应在 schema 层做好转换或容忍。
- **换行符内嵌在字符串值里**：合法的 JSON 里 `\n` 是转义的，但模型可能输出真实换行，破坏解析。正则提取时，注意 `dotAll` 模式。
- **标签混合的多模态输出**：有时 LLM 在同一个回答里输出 `<thought>` 解释和 `<output>` JSON，你只想要后者。提取策略必须明确匹配标签，避免将解释文本误作 JSON。

## 五、可复用建议
1. **封装解析函数**，不要到处写 `try { JSON.parse } catch`。统一使用 `safeJsonParse(text, options)`，支持自动剥离 markdown、多片段尝试、修复截断等策略。
2. **添加结构化日志**，记录每次解析的原始片段长度、成功与否、修复次数。这对线上排障和模型行为分析极有价值。
3. **与 prompt 工程配合**：在 system prompt 中要求严格格式是一方面，但别完全依赖它。防御代码应独立工作，即使模型完全忽略格式要求也能尽量恢复数据。
4. **为 schema 演进准备兼容逻辑**：字段新增时，旧模型可能没返回，解析应设置默认值而非报错。

## 六、总结
LLM 输出解析的防御性编程，本质是把“模型会出错”作为设计前提。JSON/标签混合处理只是其中一环，其思路可以延伸到函数调用参数解析、Agent 任务分解等更多场景。核心在于：不要信任原始输出，提取、清理、修复、校验、降级，层层递进。投入少许防御性代码，能大幅降低自动化流程的脆弱性，也让你在调试模型行为时更有底气。

在 OpenClaw 这类强调工具链可组合性的平台上，一个鲁棒的解析器往往是连接 LLM 与现实动作的“润滑剂”，值得花时间打磨。
