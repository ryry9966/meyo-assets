# AGENTS.md：为 OpenClaw 智能体编写可落地的工作空间说明书

## 背景：Agent 不是读心术

在 OpenClaw 里把一个 Agent 接到项目仓库后，很快会遇到现实问题：Agent 不知道这个项目的构建命令、不知道哪些目录是生成的、不知道团队的命名约定，甚至连“不要直接改 package-lock.json”这种基础规则都需要你反复在 prompt 里声明。

早期做法是每次在对话上下文里贴一大段项目约定，或者把这些内容塞进 System Prompt。但 System Prompt 很快就会臃肿不堪，而且切换项目时还要手动替换。社区里逐渐形成了一种实践：使用一个放在仓库根目录的 `AGENTS.md` 文件，作为 Agent 进入工作空间后优先读取的“使用手册”。

这份文件不是 README——README 是给人看的，AGENTS.md 是给 Agent 看的。它的目标是用结构化的方式，把一个项目的工程约束、目录职责、常用命令、代码风格准则摊开在 Agent 面前，降低 Agent 胡乱猜测的概率。

## 到底解决了什么问题

1. **上下文窗口浪费**：团队里每个人每次和 Agent 交互时，都要手动重述一遍项目规则，浪费 token 也容易遗漏。
2. **Agent 误操作**：不知道 `dist/` 是构建产物，Agent 可能直接修改；不知道测试命令怎么跑，Agent 可能会瞎猜一个 `npm test`。
3. **多人协作不一致**：不同开发者给 Agent 下指令时，对项目的描述不一样，Agent 得到的信息不稳定，行为也不一致。
4. **工具调用目标模糊**：OpenClaw 的 Agent 有文件读写、命令执行等工具，如果不告诉它哪些路径可以安全操作、哪些脚本是安全的，它可能执行危险命令。

`AGENTS.md` 把这些散落在各处、口口相传的“Agent 应该知道的事”集中到一个可版本控制的文件里，随项目演进一起维护。

## 做法：从零写一份可用的 AGENTS.md

以下是一个适合 Node.js / TypeScript 项目的精简模板，我们可以在此基础上按项目实际情况裁剪。

```markdown
# Agent Instructions

## 0. Role & Tone
You are an expert TypeScript developer working in a monorepo.
Be concise, prefer code over natural language, and always cite file paths.

## 1. Project Structure
- `packages/` — source code, one package per subdirectory
- `tests/` — integration tests, mirrors `packages/` structure
- `dist/` — build output, do NOT edit directly
- `scripts/` — safe utility scripts, run with `tsx scripts/<name>`
- `docs/` — public documentation, keep in sync with API changes

## 2. Build & Test
- Install: `pnpm install`
- Build: `pnpm build`
- Lint: `pnpm lint`
- Test (unit): `pnpm test -- --run`
- Test (single file): `pnpm test path/to/test.test.ts -- --run`
- Type-check: `pnpm typecheck`

## 3. Naming Conventions
- File names: kebab-case
- Variables/functions: camelCase
- Types/interfaces: PascalCase
- Test files: co-located or in `__tests__/` with `.test.ts` suffix

## 4. Code Style
- Prefer `interface` over `type` for object shapes
- Always declare return types for exported functions
- No default exports, use named exports
- Use `node:` prefix for built-in modules (`import fs from 'node:fs'`)

## 5. Do NOT
- Edit `dist/`, `node_modules/`, `coverage/`, or generated files
- Change `package.json` scripts without asking
- Run `rm -rf` or destructive commands without explicit confirmation
- Add new dependencies without explaining why

## 6. When Making Changes
- Run `pnpm lint` and `pnpm typecheck` after each change
- If fixing a bug, add a regression test
- Update `docs/` if public API changes
```

### 集成到 OpenClaw 工作流

在 OpenClaw 中，`AGENTS.md` 可以通过 Workspace 配置被自动注入到每次会话中：

1. 将 `AGENTS.md` 放在项目根目录，加入版本控制。
2. 在 OpenClaw 的 workspace 配置文件（例如 `openclaw.workspace.yaml`）中，通过 `context` 或 `systemPrompt` 字段引用该文件，让 Agent 在启动时读取。
3. 若使用 MCP 服务器提供上下文，也可以在 MCP 的资源列表里暴露 `AGENTS.md`，让 Agent 在需要时主动拉取。

关键点：不要只把 `AGENTS.md` 的内容一次性粘贴到 System Prompt 里就算完。更好的方式是利用 OpenClaw 的文件读取工具，让 Agent 在初始化阶段**自行读取**并保持引用。这样既有明确的“合同”文件，又避免 System Prompt 过长导致注意力稀释。

## 踩坑点

**不要写成文档**  
AGENTS.md 要的是指令，不是教程。避免大段解释性文字，用短句、列表、明确的“Do / Do NOT”。Agent 对声明式约束的遵循度远高于冗长的建议。

**避免和项目实际行为脱节**  
最常见的问题：文件里写的测试命令是 `npm test`，但项目实际上已经迁移到 `vitest`，正确命令是 `npx vitest run`。Agent 拿到错误指令的执行后果比没有指令更糟。因此 `AGENTS.md` 需要随 CI 配置一起维护，理想情况下让 CI 脚本校验 `AGENTS.md` 里的命令是否依然有效。

**命名约定要具体**  
写成 “follow clean code principles” 等于没写。错误示例：`Write clean code`。正确示例：`File names: kebab-case. Exported functions must have explicit return types.`

**安全边界要硬**  
一定要把禁止修改的目录写清楚，尤其是 `dist/`、生成代码目录、自动维护的锁文件。避免 Agent 在修复 bug 时忍不住“顺手”改了不该动的地方。如果项目有敏感文件（密钥、证书路径），也列出忽略规则。

**不要把 AGENTS.md 当成银弹**  
AGENTS.md 解决的是**陈述性知识**的传递问题，但 Agent 仍然需要足够的上下文来理解具体任务意图。它不能替代在 prompt 里给出的任务描述和验收标准，只能作为基础约束层。

## 可复用建议

1. **模板化按项目类型维护**  
   建立内部模板库，分别准备 Node.js、Python、Go 等语言的 AGENTS.md 骨架，团队新项目开箱即用，只填项目特异部分。

2. **与 pre-commit 钩子联动**  
   可以用简单脚本检查 Agent 产出的 diff 是否触碰了禁区目录（如 `dist/`），把 `AGENTS.md` 里的禁止项变成可执行的 check。

3. **分层设计**  
   对于 monorepo，根目录放一份全局的 `AGENTS.md`（通用规则），子包里需要特殊说明的在包根目录再放一份 `AGENTS.md`，Agent 按作用域读取。OpenClaw 的文件读取工具可以按当前工作目录决定优先读取哪个。

4. **在 Agent 回归测试里加入知识校验**  
   如果你已经对 Agent 行为做回归测试，可以增加一个 case：给定一个典型任务，验证 Agent 是否遵守了 `AGENTS.md` 里的关键约束（例如是否修改了禁改目录）。

5. **版本锁定与 diff 追溯**  
   把 `AGENTS.md` 当作代码的一部分，在 PR 中查看其变更。每次更改都可能影响所有使用该仓库的 Agent 行为。

## 总结

`AGENTS.md` 本质上是项目的“AI 接口规范”——它用人类可维护的格式，为进入代码库的每一个 AI Agent 规定了基础行为和边界。写好它不需要追求技术深度，而需要工程纪律：准确、精练、与项目现状严格一致。

在 OpenClaw 体系里，这份文件是 Agent 工作空间配置的基石。把它当作一个持续维护的工程制品，而不是一次性的“给 AI 写说明书”就能避免大部分团队踩过的坑。
