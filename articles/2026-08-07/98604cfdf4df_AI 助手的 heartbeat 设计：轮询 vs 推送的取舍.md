## 背景

在 OpenClaw 这类插件化 AI 助手框架中，大量自动化能力依赖“外部事件触发”：一个新告警、一次代码提交、一个 MCP 资源变更、任务队列的新消息。要让 Agent 及时响应，必须解决一个基础问题——**如何让插件感知到“有新事发生”**。

业界主流的两种思路很清晰：

- **轮询（Polling）**：定时查询外部状态，比较差异后触发动作。
- **推送（Push/Webhook/SSE）**：外部系统在事件发生时主动通知插件，插件被动接收。

两种方案都已经烂熟，但真正落到工程实现时，要踩的坑远比教材里写得复杂。本文从 OpenClaw 插件开发者和自动化 SRE 的视角，梳理 heartbeat 设计中轮询和推送的取舍逻辑、实现要点和避坑经验。

---

## 问题：heartbeat 的本质不是“取数”，而是“可靠性契约”

很多人误以为 heartbeat 只是定期 ping 一下。但实际上，在一个需要处理业务流程的 AI 助手里，heartbeat 承担的是：

- 外部状态同步的触发点（例如检测新告警）
- 自身健康监控（插件是否存活）
- 失联判定与故障转移

如果把 heartbeat 做成单纯的定时轮询，频繁调用远端 API 容易触发限流；完全依赖推送，断线、丢消息后的补偿又很难做。因此，工程上常需要**混合策略**，并且要定义清楚数据一致性、延迟、可靠性的取舍。

---

## 做法 / 步骤：在插件中实现可切换的心跳策略

以一个典型的 OpenClaw 告警插件为例，它需要监听 Prometheus AlertManager 的新告警并将其推给 LLM 做摘要。我们一步步构建合适的心跳机制。

### 1. 统一 heartbeat 接口

无论底层采用哪种方式，我们希望在插件侧看到一致的初始化与事件消费模型。可以抽象一个 `HeartbeatSource`：

```
start(): Promise<void>       // 启动心跳
stop(): Promise<void>        // 停止
onEvent(cb: (event) => void) // 事件回调
```

在插件初始化时根据配置选择 `PollingSource` 或 `WebhookSource`，后续逻辑完全无感。

### 2. 轮询实现重点：缓存 + 签名去重

轮询模式下，每次拉取需要准确判断“哪些是新事件”。典型做法：

- 获取事件列表后，对每条事件生成不可逆签名（例如 hash(event.id + timestamp)）。
- 与上次拉取的签名集合做 diff，新增的部分触发 `onEvent`。
- 维护有限的窗口（例如仅缓存最近 2 轮签名），避免无限内存增长。

频率选择建议：如果业务可接受 30 秒延迟，就选 30 秒；不要选择 5 秒以内，否则 API 限流会迅速教你做人。

### 3. 推送实现重点：幂等 + 补偿

推送路径一般使用 webhook 或 SSE（如 MCP 的 Server-Sent Events 资源更新推送）。必须处理：

- **幂等消费**：用 event id 去重。插件的 onEvent 回调内部交给一个去重队列，调用 `getOrSet(eventId, callback)`，防止重复推送导致 AI 多次处理。
- **断线补偿**：推送断开后，依赖一个轻量轮询作为兜底。例如，当 SSE 连接断开超过 1 分钟，自动启动 2 分钟一次的轮询，直到连接恢复。
- **验证来源**：webhook 必须校验签名（HMAC），否则攻击者可以伪造事件。

### 4. 混合模式实现：推送优先 + 兜底轮询

一个健壮的心跳模块会同时持有两种 source，并引入优先级：

1. 优先启动推送源（webhook 或 SSE）。
2. 同时启动极低频的轮询（例如 5 分钟），仅用作心跳探活和补偿。
3. 当推送源连续超时或断开超过一定时间，自动将低频轮询提升为正常频率（例如 1 分钟）。
4. 推送恢复后，降级轮询频率。

这样就得到了接近实时的响应，又不会丢失事件。

## 踩坑点

- **签名去重用的是内存缓存，重启插件后签名丢失**，可能导致重复消费。解决方案：在插件的持久化存储（如 SQLite、Level）中保留最近 1000 个 event id，启动时加载。
- **webhook 推送延迟过大时，误判为超时**：有些外部系统会批量积压几分钟后再推送。需将超时容忍设为远大于轮询周期，例如 API 推送历史数据可能慢至 5 分钟，补偿轮询频率不能短于这个窗口，否则重复事件爆炸。
- **API 分页和时间窗口混乱**：轮询时如果 API 不支持按时间范围过滤，每次只能拉全量并自行分割，签名单集合越来越大，最后 OOM。务必在选型时要求外部系统支持 `?updatedSince=` 或游标。
- **SSE 重连风暴**：推送客户端在重连时要实现指数退避，不能断开后每秒重试，否则后端直接把你 IP 封了。

## 可复用建议

- **封装一个 `HybridHeartbeat` 模块**，放到公司的插件模板里，后续新插件只需配置两种 source 的地址、频率、降级阈值，不用重写逻辑。
- **利用 MCP 的 subscriptions 机制**：如果你的 MCP 服务端支持 `resources/subscribe`，在插件中使用 SSE 订阅资源变更，这是标准推送路径，省去自己搞 webhook 的麻烦。但同样要配合补偿轮询。
- **指标化你的心跳**：暴露 Prometheus 指标，如 `heartbeat_poll_total`、`heartbeat_push_reconnects`、`heartbeat_event_duplicates`。上线后你会发现真实的延迟分布和丢事件概率远比设计时想的糟糕。
- **定义“最新”而非“全部”**：对于告警类场景，大部分时候只需要知道“当前活跃告警的最新快照”，而非事件流。此时用 1 分钟轮询拉最新状态并全量替换，比维护事件流简单得多。

---

## 总结

轮询和推送不是二选一，而是两个组件：实时通道（推送）和可靠性底座（补偿轮询）。在 OpenClaw 插件的工程实践中，**永远不要完全信任推送，也永远不要让轮询成为你唯一的实时手段**。根据业务延迟容忍度和外部系统的能力，混合出合适的“推-拉”比，才能让 AI 助手既灵敏又不丢消息。

好用的 heartbeat 不需要花哨，只要让你半夜不再被“为啥 AI 没响应告警”的电话吵醒，就够了。
