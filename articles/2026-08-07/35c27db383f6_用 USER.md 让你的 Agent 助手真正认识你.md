## 背景：Agent 每次都在重新认识你

AI 助手越来越强，但有个问题始终没变：你每次启动一个会话，就等于从零开始。无论是用 OpenClaw 搭建本地 Agent，还是通过 MCP 挂接外部工具，Agent 对你的项目结构、你的工作习惯、你的命名偏好一无所知，除非你每次都手动交代一遍。

典型场景：

- 你让 Agent 写一个 Python 脚本，它用了 `snake_case`，而你的仓库强制 `camelCase`；
- 你让 Agent 设计数据库表，它默认加了 `created_at` 和 `updated_at` 但你团队规定用 `ctime` 和 `utime`；
- 你要引用内部 API，每次都得把文档地址、认证方式重新说一遍。

这些不是 Agent 能力问题，而是缺乏**持久化的用户上下文**。OpenClaw 的系统提示可以定义通用行为，但真正高精度的协作，依赖更个人化的配置——这就是 USER.md 要解决的事。

## 问题：通用 Prompt 的粒度不够

大多数 Agent 的配置方式是往 `.clawrc` 或启动参数里塞一个长长的 `system_message`。这样做的缺点很明显：

- **无法共享**：换个项目甚至换个机器，就要重新复制粘贴；
- **难以迭代**：修改一次要重启环境，且容易和项目级提示混淆；
- **缺乏结构**：一长段自然语言描述，Agent 很容易忽略关键点。

我们需要一个低摩擦、可版本化、Agent 能准确理解的方式告诉它“我是谁、我习惯怎么干活”。USER.md 就是这个思路的工程化落地。

## 做法：给 Agent 一份你的说明书

### 第一步：创建 USER.md

在你的 OpenClaw 用户目录下创建文件，典型路径是 `~/.openclaw/user.md`。内容用 Markdown 编写，结构要清晰，Agent 能快速解析要点。参考模板：

```markdown
# 基本信息
- 角色：后端开发，主要使用 Go 和 Python
- 操作系统：macOS，终端使用 zsh
- 编辑器：VSCode，已安装 Vim 插件

# 编码偏好
- 命名：Go 遵循标准风格，Python 用 snake_case
- 注释：公开函数必须有 docstring，格式用 Google style
- 错误处理：优先返回 error，不要 panic
- 测试：使用 testify 断言库，文件命名为 *_test.go

# 项目上下文
- 当前主项目路径：~/code/backend-services
- 该仓库采用 monorepo，服务在 services/ 目录下
- 内部库包名前缀：git.internal.example.com/org/lib
- 生成代码请使用该前缀导入

# 输出风格
- 解释不求长篇，给出关键决策原因即可
- 代码块要带语言标识和必要的行内注释
```

### 第二步：让 OpenClaw 加载 USER.md

如果你使用 OpenClaw 的命令行工具，可以在配置文件（如 `~/.openclaw/config.yaml`）中指定：

```yaml
user_context_file: ~/.openclaw/user.md
```

如果是通过库集成，在初始化 Agent 时读取文件内容并注入到系统提示的最前面。一个简单实现：

```python
import os
from pathlib import Path

def load_user_context(path: str = "~/.openclaw/user.md") -> str:
    p = Path(path).expanduser()
    if p.exists():
        return p.read_text()
    return ""
```

将返回值放在 `system_prompt` 的最上方，前面加一句：“以下是你需要知道的用户信息，请在所有回答中遵守：”

### 第三步：验证与迭代

用一个标准化问题来测试是否生效，比如：“请写一个 Python 函数来处理用户登录，并测试它。”观察 Agent 是否自动使用了你规定的命名、测试框架和注释格式。如果偏差明显，回顾 USER.md 是否描述得过于含糊，或是否被后续系统提示覆盖了。

## 踩坑点

1. **内容过于冗长**  
   有人想把自己的一天都写进去——从咖啡偏好到开会时间，这只会浪费 Token，Agent 也不会参考。控制 USER.md 在 500 字以内，只保留直接影响代码生成和组织风格的偏好。其他临时信息通过会话输入补充。

2. **隐私泄露**  
   绝对不要在 USER.md 里放 API Key、JWT Token、内部 IP 等信息。这些文件很可能被同步到 Git 或日志里。安全凭证应通过环境变量注入。

3. **Agent 忽略部分规则**  
   如果发现 Agent 没遵守，不要立刻下结论说 USER.md 无效。检查最终拼合成的系统提示（debug 模式下打印出来），看看是不是后面的指令覆盖了前面的。必要时刻意调整顺序或用“请始终遵守以下规则”这类措辞强化。

4. **跨机器更新不同步**  
   建议把 USER.md 放到 dotfiles 仓库管理，通过符号链接指向。或者写一个安装脚本，自动从远程拉取并拷贝到 `~/.openclaw/`。

## 可复用建议

- **分层管理**：USER.md 负责个人偏好，项目级的 `.claw.md` 负责仓库规范，团队级的在文档中维护。Agent 应同时加载三个来源，USER.md 优先级高于团队级。
- **精简表达**：能用列表的不要写段落，能用示例的不要抽象描述。比如“不要返回裸 SQL，用 ORM 查询”，不如写：“请使用 GORM 的链式查询，示例：`db.Where(...).Find(&users)`”。
- **定期审计**：每两周用一次对话测试，检查规则是否仍然适用。团队成员变动、技术栈升级都可能导致旧规则失效。
- **结合 MCP**：如果你的 Agent 通过 MCP 连接了内部知识库，可以把 USER.md 路径作为固定资源提供给 Agent，避免每次手动指定。

## 总结

让 Agent 理解你，不是一个“未来 AI 才具备”的愿景。一份 300 行不到的 USER.md，配合正确的加载机制，足以消除大部分无效沟通。这项实践的投入很低，回报却直接反映在每次输出质量上。你已经花了那么多时间选工具、搭环境、调 Prompt，是时候花 15 分钟写一份 USER.md 了。
