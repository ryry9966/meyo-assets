## 背景

在 OpenClaw 平台上构建自动化工作流时，Agent 需要频繁采集外部网页——补充上下文、拉取最新文档、监控竞品价格。直接给 Agent 开放 `fetch` 或 `requests` 权限虽然方便，但很快会撞上现实问题：IP 被目标站点封锁、忽略了 robots.txt 导致合规风险、请求频率失控拖垮内部网络，并且整个采集过程完全黑盒，出了事只能对着日志发懵。

我们需要的不是又一个“通用爬虫”，而是一个轻量、可配置、可审计的采集中间层，让 Agent 的所有出站 HTTP 动作都经过统一的稽核与保护。这个中间层，内部我们叫它“稽客（Scrap Auditor）”。

## 问题拆解

开放式 Agent 在网页采集上的典型翻车路径：

1. **缺少 robots.txt 识别** —— Agent 不关心也不理解爬虫协议，直接扫描敏感路径，触发法律或反爬机制。
2. **无频率控制** —— Agent 循环调用时可能对同一域名瞬间发出数十个请求，立刻被识别为恶意流量。
3. **审计黑盒** —— 没有结构化记录“谁在什么时间抓了什么页面、是否合规、响应状态如何”，运营排查靠猜。
4. **重试策略野蛮** —— 遇错直接重试，没有指数退避，反而加速了封锁。
5. **结果不可复现** —— 动态内容没做缓存，同一个 URL 在不同 Agent 运行中返回不同结果，调试困难。

这些问题单靠 Agent 自身的“道德约束”无法解决，必须在架构上增加一层安全代理。

## 做法：构建稽客 MCP 工具

思路是：将稽客实现为一个独立 HTTP 代理/API 服务，并封装为 MCP 工具，Agent 不再直接联网，而是通过 MCP 调用该工具发起受控的网页请求。

### 1. 核心组件

- **协议解析器**：基于 `robotparser`（或等效实现）缓存各域名的 robots.txt，每条请求前检查 User-Agent 与路径是否被允许，并读取 `Crawl-Delay`。
- **令牌桶限速器**：按域名维度分配桶，支持通过环境变量 `AUDITOR_RPS` 设定默认速率，特殊域名允许单独调参。
- **UA 管理**：统一设定标准 UA，避免暴露 Agent 原始特征。
- **获取引擎**：针对静态内容使用 `httpx` 或 `aiohttp`；需要 JS 渲染时调用 Headless Chromium（通过 Playwright 池化），仅在配置开启时启用，控制资源。
- **审计日志**：结构化输出 JSON 行式日志，包含 `timestamp`, `agent_id`, `url`, `compliance`（true/false）, `status_code`, `latency_ms`, `cache_hit`。
- **可选缓存**（LRU / TTL 可配）：减少重复请求，提高可复现性。

### 2. 封装为 MCP 工具

编写一个简单的 MCP 服务器（使用 `mcp` SDK 或直接实现 JSON-RPC），暴露以下工具：

- `auditor_fetch`：传入 `url`, `method`（默认 GET）, `options`（如是否需要渲染、自定义 headers 等），返回 `content`, `status_code`, `final_url`, `cached`。
- `auditor_compliance_report`：返回最近采集的合规统计，供调试或运维检查。

在 OpenClaw 中配置该 MCP 服务器连接，Agent 即可通过标准工具名调用，例如 `mcp__auditor_fetch`。

### 3. 工作流示例

Agent 需要采集某个产品页面，调用：

```
mcp__auditor_fetch { "url": "https://example.com/product/123", "render": true }
```

稽客内部流程：
1. 检查域名 `example.com` 的 robots.txt 是否已缓存，无则请求并缓存。
2. 判断 `/product/123` 是否被允许；不允许则返回错误，并记录合规拒绝。
3. 检查令牌桶是否允许本次请求，不足则等待（或立即返回 429 给 Agent）。
4. 使用 Playwright 打开页面，执行关键的 JS 渲染，等待网络 idle。
5. 提取 HTML，返回结果，记录审计日志。

Agent 拿到内容后继续推理，全程无需关心合规细节。

## 踩坑记录

- **robots.txt 解析并非简单**：`Allow` 和 `Disallow` 的顺序与匹配算法需要严格遵循 Google 扩展标准，自己写容易踩坑，最好直接使用 Python 的 `urllib.robotparser` 或 `reppy`，并定期测试几个典型站点（如 `github.com/robots.txt`）。
- **动态渲染成本巨大**：Headless 浏览器启动慢、内存高。建议池化固定实例数（比如 2~4 个），配合请求队列，同时给 Agent 明确提示“渲染模式较慢”，让 Agent 只在必要时开启。
- **令牌桶粒度拿捏**：按域名限速合理，但需注意某些 CDN 或共享 IP 下多个站点实际在同一服务器，需更细粒度的域名归一化（如忽略子域名）。可选支持按 IP 限速，但实现复杂。
- **缓存带来的新鲜度陷阱**：Agent 可能需实时数据，却命中了陈旧的缓存。务必在工具描述中明确 `render` 模式下默认不缓存，或在缓存响应中附带 `X-Cache-Age` 信息，让 Agent 自行判断。
- **日志泛滥**：高并发运行时审计日志可能迅速膨胀，使用日志轮转（RotatingFileHandler）并限制保存天数。

## 可复用建议

1. **将稽客作为 OpenClaw 团队的基础设施插件部署**，任何新建 Agent 工作流都默认通过它采集，避免各自实现。
2. **配置分层**：全局默认（限速、UA、缓存 TTL）放在环境变量，特定域名覆盖写在 YAML 配置文件中，稽客启动时加载。
3. **增加健康检查与监控**：暴露 `/health` 和 `/metrics`（Prometheus 格式），监控限速等待数、合规拒绝率、平均延迟，方便运维察觉异常采集。
4. **与内部 SOC 协作**：合规拒绝事件可推送到告警通道，例如通过 webhook 通知安全团队，避免法律风险发酵。
5. **灰度开放渲染能力**：先在非生产环境让 Agent 使用渲染模式，观察资源消耗与错误率，再逐步开放给关键任务。

## 总结

“稽客”并非要限制 Agent 的能力，而是给自动化采集戴上护具。通过统一的代理层，我们获得清晰的审计追踪、可量化的合规性和可控的资源开销。对于严肃地在生产中使用 OpenClaw 的团队，这一层不是可选项，而是工程成熟度的标志。

部署上，它只是一个数百行的 Python 服务外加标准 MCP 封装，但其带来的可观测性和安全性值得投入一个下午的集成工作。未来还可扩展支持基于语义的白名单过滤、内容脱敏等能力，让 Agent 既能高效“看世界”，也不给自己或组织挖坑。
