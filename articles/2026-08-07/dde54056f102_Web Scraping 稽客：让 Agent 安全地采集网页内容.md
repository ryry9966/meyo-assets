# Web Scraping 稽客：让 Agent 安全地采集网页内容

## 背景：Agent 需要上网，但“随便爬”就是埋雷

无论是用 OpenClaw 等 Agent 框架实现信息助手，还是通过 MCP server 扩展工具能力，但凡 Agent 要触网，Web scraping 几乎是绕不开的基础动作。查天气、搜文档、追踪竞品动态、提取公告摘要——这些场景都需要 Agent 替我们从网页中取回结构化信息。

但直接把 `requests.get(url, timeout=10)` 丢给 Agent 是危险的。几个典型场景：

- Agent 为了回答用户“帮我看看这 100 个网站最新活动”，无节制并发爬取，3 分钟内被 CDN 封锁 IP；
- 内部测试环境遗漏 robots.txt 检查，爬了对方禁爬目录，收到警告邮件；
- 某次 scrape 拉回 7MB HTML，全量喂给 LLM，消耗大量 token，返回结果还是乱码；
- 无意中抓取到个人隐私数据，在日志里明文留存，带来合规风险。

问题的本质不是“爬”本身，而是缺少一个**稽客层**——也就是一个能替 Agent 在采集过程中把关安全、效率、合规性的中间层。稽客（Guardian Scraping Proxy），顾名思义，像门卫一样审核每一次采集请求与返回内容。

## 问题拆解：Agent 上网需要守哪些门

把风险结构化，大致是四类：

1. **反爬与可用性**：IP/UA 被拉黑、频率过快触发验证码、页面需要 JS 渲染但只取了静态 HTML、目标站直接返回 403/5xx。
2. **合规与边界**：未遵守 `robots.txt`，未检查内容使用条款，抓取到受版权保护的付费数据。
3. **资源浪费**：不必要的大体积页面全量下载，LLM 被无效内容淹没，无缓存导致重复请求。
4. **内容安全**：被抓取内容可能包含 XSS payload、恶意跳转，或抓取到未脱敏的用户数据。

光靠 Agent 自己（即 LLM 调用工具）很难在这四方面做出正确判断，因此需要一个可复用的稽客模块，嵌入到每一次网页采集流程里。

## 做法：构建可嵌入 MCP 工具的稽客层

工程上，我们不必重复造轮子，可基于现有生态实现一个“采集稽客”服务，并将其封装成 Agent 可直接调用的 MCP 工具（例如 `scrape_with_guardian`）。以下是一个可落地的设计拆解。

### 1. 请求前拦截：绝不盲爬

在发起 HTTP 请求前，须过三道卡：

- **域名/路径白名单**：维护一个允许采集的域列表，或反向维护黑名单（内网地址、已声明禁爬站点）。可通过环境变量下发，策略粒度支持通配符。
- **robots.txt 检查**：用 Python 的 `robotparser` 模块自动拉取目标站的 `robots.txt`，解析 `User-agent` 规则，判断当前路径是否在 Allow 范围内。缓存 robots 解析结果（TTL 1 小时），避免重复请求。
- **速率控制**：用令牌桶或滑动窗口限制同一域名在单位时间内的请求次数，例如每域名 5 次/秒。令牌桶基于 Redis 实现，可跨 Agent 实例共享。

只有这三项都放行，才真正发送请求。

### 2. 请求中控制：隐匿又克制

- **UA 与请求头标准化**：设置仿真的 `User-Agent`（如 Chrome 桌面版）、`Accept-Language`，且禁止 Agent 自定义 `Cookie`，防止越权。
- **可插拔代理**：对接代理池（如自建 Squid + 付费住宅代理），为高价值站点或批量任务自动启用。代理不可用时，退化为直连并记录告警。
- **超时与重试策略**：连接超时 8s，读取超时 15s，只重试一次（仅针对 5xx 和网络错误），避免重试风暴。
- **渲染方案按需选择**：默认用 `httpx` 取静态 HTML，当发现页面内容过短（<500 字符）且 meta 含 SPA 特征时，自动降级到 Playwright headless 渲染，但需单独累加耗时统计，并强制设置渲染超时 30s。

### 3. 响应后净化：安全且“瘦”

- **内容长度硬限制**：响应体 ≥ 2MB 时截断，只保留前 1MB 并返回摘要，避免大段无效内容进入 LLM 上下文。
- **HTML 净化**：使用 `lxml` 或 `bleach` 剥离 `<script>`、`<style>`、注释、隐藏元素，仅提取 `body` 内可见文本，同时移除敏感模式（邮箱、身份证号、手机号）或替换为 `[REDACTED]`。
- **安全响应头审计**：如果 `Content-Type` 非 `text/html`/`application/json` 等预期类型，直接拒绝并返回结构化错误，防止 Agent 误读二进制流。

### 4. 全链路日志与可观测性

每一次采集动作记录结构化事件：目标 URL、耗时、状态码、是否命中缓存、最终返回给 LLM 的字符数、合规检查结果（pass/fail）。这些日志同步到 Loki 或 Elasticsearch，用于后续审计和成本分析。

### 5. 封装成 MCP 工具

将上述逻辑封装成一个 MCP server 资源，暴露给 Agent：

```json
{
  "name": "scrape_with_guardian",
  "description": "Safely fetch and clean web page content.",
  "parameters": {
    "url": { "type": "string", "description": "The URL to scrape" }
  }
}
```

Agent 只需传入 `url`，工具内部完成所有稽客动作，返回 `{"status": "success", "text": "...", "from_cache": false}`。失败时返回明确错误码，例如 `robots_denied`、`too_large`、`proxy_failure`。如此一来，Agent 调用方完全不用关心采集细节。

## 踩坑实录

- **robots.txt 大站延迟**：某些 CDN 后的 robots.txt 响应极慢（>5s），需设置短超时（2s）并缓存空结果，避免阻塞后续请求。
- **动态渲染的代价**：Playwright 渲染一次平均消耗 200~500ms 和大量内存，一旦 Agent 并发调用，很容易打爆 worker。必须限制渲染并发数为 2（可通过信号量控制），超出时返回静态内容或提示稍后重试。
- **代理 IP 重用的“污染”问题**：同一代理 IP 短时间内访问多个不同域，容易被识别为爬虫。建议按目标域池化代理，或至少做到请求间随机切换。
- **文本提取不干净**：部分新闻站正文埋在 `div.article-body`，通用剥离可能丢失内容。可预置常见站点提取规则（类 `readability` 算法），否则 Agent 拿到的文本过于碎片化，影响下游问答质量。

## 可复用建议

- **直接复用已有库**：`Scrapy` 的 downloader middleware 思路可以直接借鉴，但无需引入整个框架；Python 生态中的 `httpx` + `selectolax` + `robotparser` 已足够轻量。
- **配置外置**：域名白名单、代理地址、速率阈值全部通过配置文件或环境变量注入，方便 Operator 动态调整，无需重新部署 Agent。
- **与 Agent 框架集成测试**：在 OpenClaw 等框架中，将稽客工具作为默认内置工具，并在 CI 中验证其对恶意输入（内网地址、超大页面、禁爬路径）的行为，确保拦截有效。
- **从“安全采集”延伸到“可信引用”**：可在返回内容中附带 `source` 元数据（标题、域名、Last-Modified），供 Agent 在回答时标注出处，进一步增强可信度。

## 总结

让 Agent 上网并不难，难的是让它“安全、合规、经济”地上网。Web scraping 稽客层本质上是一个前置信关，它约束 Agent 的无序行为，保护采集目标不被滥用，也保护 Agent 自身不因不当抓取而陷入法律或运维风险。

对于正在实践 OpenClaw、MCP 或自动化插件的同学，我的建议是：不要等到第一次被 ban、第一次收到投诉、第一次因返回内容过大烧掉几十美金 token 时才想起安全采集。一开始就把稽客逻辑写进工具层，它比事后补救廉价得多，而且是负责任工程实践的基本动作。
