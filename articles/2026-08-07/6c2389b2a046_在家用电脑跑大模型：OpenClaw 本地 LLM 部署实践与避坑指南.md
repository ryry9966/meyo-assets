## 背景

在以 OpenClaw 为代表的 Agent 自动化体系里，大语言模型通常是“大脑”。但每当任务涉及私有数据、无网环境、频繁短响应或延迟敏感型工作流时，完全依赖云端模型就不再理想。本地部署 LLM 能够提供更低的端到端延迟、完全的隐私控制，并且一次部署后无需按 token 持续付费。对于 MCP 工具调用、自动化脚本生成这类场景，本地方案还能避免因公共 API 限流而导致的级联失败。

问题在于，家用电脑的硬件资源有限，消费级显卡的显存大多在 4 GB 到 16 GB 之间，内存带宽也远低于数据中心 GPU。本文提供一套在普通 PC 上跑可用大模型的工程化实践，重点放在与 OpenClaw 生态的集成和常见踩坑点上。

## 硬件与模型选择

**基本门槛**  
- 内存：建议 32 GB 以上，16 GB 仅能勉强运行量化后的 7B 参数模型。  
- 显卡：NVIDIA 独显 (4 GB 显存起)，或苹果 M 系列芯片（利用统一内存）。纯 CPU 推理也是可接受的退路，但在长上下文时速度明显下降。  
- 硬盘：模型文件普遍 4~10 GB，预留 50 GB 以上避免意外。

**模型选型**  
量化是消费级硬件跑大模型的唯一出路。推荐 GGUF 格式的 Q4_K_M 或 Q5_K_M 量化版本，在质量与速度间平衡较好。用于 Agent 工作流时，优先选择指令遵循能力强、支持 function calling 或原生 JSON 模式输出的模型。Qwen2.5-7B-Instruct、Llama-3.1-8B-Instruct 是性价比最高的起点。若承担代码生成或工具调用密集的任务，可尝试专门的 Qwen2.5-Coder-7B 或 DeepSeek-Coder-V2-Lite。显存不足 6 GB 时，退回到 3B 级别的 Qwen2.5-3B 仍能处理很多格式化输出。

## 部署步骤（以 Ollama 为例）

Ollama 是目前最省心的本地推理运行时，提供 OpenAI 兼容 API，开箱即用的量化模型库，以及 GPU 加速支持。

1. **安装与启动**  
   ```bash
   curl -fsSL https://ollama.com/install.sh | sh
   # 若要让 Docker 或局域网内其他服务访问，需绑定 0.0.0.0
   export OLLAMA_HOST=0.0.0.0:11434
   ollama serve
   ```

2. **拉取模型**  
   ```bash
   ollama pull qwen2.5:7b-instruct-q4_K_M
   ```
   也可通过 Modelfile 自定义系统提示、温度、上下文长度等参数。

3. **验证 API**  
   ```bash
   curl http://localhost:11434/v1/chat/completions \
     -H "Content-Type: application/json" \
     -d '{
       "model": "qwen2.5:7b-instruct-q4_K_M",
       "messages": [{"role":"user","content":"say hello"}]
     }'
   ```
   该端点与 OpenAI 格式基本一致，可直接配置到 OpenClaw 的模型后端。

4. **接入 OpenClaw**  
   在 OpenClaw 的模型配置中，将 `api_base` 指向 `http://<ollama-host>:11434/v1`，`api_key` 填任意占位值即可。若需为 Agent 指定专用模型，可在 agent 配置的 `llm` 块内覆写。

   如果已经使用 LiteLLM 代理统一管理模型，也可以将 Ollama 注册为 LiteLLM 的一个 provider，利用它的重试、限速机制来保护本地资源。

## 关键踩坑

**1. 网络隔离导致访问失败**  
Ollama 默认只监听 127.0.0.1。如果 OpenClaw 运行在 Docker 容器中，请求将被拒绝。必须设置 `OLLAMA_HOST=0.0.0.0:11434` 或用 Nginx 反向代理。测试时直接用 `curl` 从容器网络访问确认可达性。

**2. 上下文长度失控**  
Agent 工作流很容易积累很长的对话历史，而 7B 模型默认的 4096~8192 上下文窗口在启用 KV 缓存后仍会迅速消耗内存。应在模型配置中明确限制 `num_ctx`（如 4096），并在 OpenClaw 会话管理中加入摘要或清理逻辑，避免 OOM 崩溃。

**3. 量化模型的格式漂移**  
低比特量化有时会破坏模型的指令跟随稳定性，尤其是当提示要求同时输出推理链和 JSON 的复杂结构时。实践中发现，Q4_K_M 版本在连续工具调用 10 轮后，偶尔出现字段缺失或非 JSON 尾注。应对方法是：采用结构化生成（如 ollama 的 `format: json` 参数强制 JSON），并在 Agent 层做解析异常的兜底（fallback 到默认动作）。更稳健的做法是使用 XGrammar 或 lm-format-enforcer 等约束解码。

**4. 并发请求被静默串行化**  
家用 GPU 通常只能同时服务一个推理请求。当多个 Agent 或插件并发调用本地模型时，Ollama 会内部排队，导致端到端延迟飙升。解决思路：  
- 限制 OpenClaw 对本地模型的并发数（通过 LiteLLM 的 `rpm` 限制）。  
- 将重要、延迟敏感的任务分流到云端，本地作为备用。  
- 接受纯 CPU 推理来处理低优先级、后台批处理任务，释放 GPU。

**5. 散热与功耗**  
长时间满载运行会让显卡风扇满速，尤其在夏季。可以监控 GPU 温度（`nvidia-smi`），适当降低 `num_gpu` 层数或改用 CPU 推理来分散压力，但会牺牲速度。

## 可复用建议

1. **“Docker Compose 全家桶”**  
   将 Ollama、LiteLLM 和 OpenClaw 放在同一 compose 文件中，通过内部 network 通信，用 `depends_on` 控制启动顺序，可以快速在任意机器上复现环境。

2. **混合模型路由**  
   在 OpenClaw 中为不同任务配置不同模型后端。例如：
   - 本地 7B 模型负责格式化输出、简单分类、代码补全和敏感内容处理。  
   - 云端模型负责复杂推理、长文档分析、多步规划等高负载任务。  
   利用 LiteLLM 的 `router` 模式做 fallback，当本地模型超时或报错时自动切换到远端。

3. **监控与告警**  
   部署后至少要用 Prometheus + Grafana 或简洁的 `glances` 监控以下指标：
   - GPU 利用率、显存、温度  
   - 请求延迟、队列长度  
   - 上下文内存使用（Ollama 的 `/api/ps` 端点可查到）  
   当显存长期超过 90% 时，触发 Agent 自动缩短上下文或切换模型。

4. **模型定期重评估**  
   本地部署的成本很低，不妨每个月用相同测试集重新评测新发布的量化模型，观察指令遵循、格式稳定性有没有改进，以此决定是否更换。

## 总结

在家用电脑上跑大模型已经不再是玩具阶段。只要选对量化模型、控制好上下文长度、处理好并发与容错，就能搭建出既私密又低成本的本地方案，直接为 OpenClaw 的自动化工作流服务。整个部署过程不需要复杂的环境配置，依靠 Ollama 的 API 兼容性即可快速接入现有工具链。最关键的是养成按需量化的习惯——不是所有任务都需要最强模型，本地推理的真正价值在于把合适的计算留在本地，把成本和延迟同时降下来。
