# AI Agent 的错误恢复：当外部 API 挂了怎么办

## 背景

在 Agent 驱动的自动化流程中，我们经常需要调用外部 API 获取数据或执行操作：天气查询、数据库读写、翻译接口、Slack 通知，或者通过 MCP 调用的远端工具。这些依赖一旦出现不可用、超时或限流，整个 Agent 工作流就可能中断。对于定时运行的自动化链路（如每日报表生成、工单流转），这种中断比单次查询失败影响更大。因此，需要为 Agent 设计一套工程化的错误恢复机制，而不是简单地在 prompt 里加一句“如果失败就重试一次”。

## 问题拆解

典型的失败场景包括：
- **瞬时性错误**：网络抖动、短暂超时、服务端 503，重试后往往恢复。
- **持续性故障**：API 服务宕机、密钥过期、区域服务中断，持续数分钟到小时级。
- **逻辑性错误**：参数格式不合法，但 Agent 也可能会反复尝试，导致风控或脏数据。
- **限流与配额耗尽**：429 Too Many Requests，盲目光速重试会加剧封禁。

如果不做控制，Agent 轻则陷入死循环重试，重则因缓存缺失导致下游任务收到空结果、误触发告警或重复提交事务。

## 做法与步骤

### 1. 为工具定义错误响应结构

在 OpenClaw 或类似框架中，每个工具调用都应该返回标准化字段，而不仅仅是字符串描述。建议包含：
```json
{
  "success": false,
  "error_type": "timeout|rate_limit|auth|server_error",
  "message": "请求超时，已重试2次",
  "retryable": true
}
```
Agent 的推理循环可以据此判断下一步动作，而不是猜测自然语言错误信息。

### 2. 在工具包装层内置重试与退避

不要把重试逻辑塞进 Agent 的 prompt。应该在工具函数的实现侧（或中间件）完成：
- 指数退避重试（如最大3次，间隔1s/2s/4s），监控重试次数和总耗时。
- 对 429 响应，尊重 `Retry-After` 头部，暂停后重试。
- 4xx 客户端错误不重试，立即返回失败。

### 3. 设置降级与兜底

对非主线关键数据，可以设计降级链：
- 优先调用主 API，失败且非关键任务时，使用本地缓存（如上一次成功结果）。
- 对翻译、摘要等辅助功能，失败后返回原文或标记“暂不可用”，不阻塞主流程。
- 对于强依赖（如支付接口），则必须中止并推送告警，必要时接入人工确认环节。

降级逻辑同样封装在工具层，让 Agent 看到的是“降级后的结果”并附加提示，而非直接抛出异常。

### 4. 引入熔断器

当一个外部 API 连续失败超过阈值（如一分钟内连续 10 次失败），直接熔断该工具一段时间（如 5 分钟）。熔断期间，Agent 调用该工具会立即得到“服务暂时不可用”的标准化错误。熔断器的状态变化应记录到日志，并通知运维通道。

### 5. Agent 层面的决策编排

工具已经处理了大部分瞬时故障，但 Agent 依然需要处理降级、熔断或不可重试的错误。可以在系统指令中定义明确策略：
- 工具返回 `error_type: rate_limit` 且 `retryable: false`：暂停该工具调用并调整任务优先级，或通知用户。
- 工具返回 `error_type: server_error` 但任务关键：询问用户是否等待或切换到备用服务（如果有）。
- 对于纯日志或总结类步骤，可选择跳过。

实际落地时，可以在 Agent 循环中增加一个“错误状态机”，根据工具错误类型和任务上下文动态决定下一步，而不是仅仅基于自然语言。

## 踩坑点

1. **在 prompt 里写重试逻辑**：Agent 可能无限循环“让我再试一次”，消耗大量 token 和时间，还会因为上下文变长而越发笨拙。
2. **无幂等性保护**：支付、创建订单等接口重试需通过幂等键（如 requestId）。否则退避重试可能重复扣款或重复建单。
3. **缓存降级变成过期数据**：缓存上一次成功结果时，必须标注数据时效性并在结果中注明“缓存数据，更新时间 X 分钟前”。否则下游决策基于过期信息可能出错。
4. **熔断粒度太粗**：一个工具挂了对所有任务都熔断，可能影响多样化流程。应按工具+任务类型做细粒度隔离。
5. **吞没错误信息**：为了“优雅降级”，有些团队会把所有错误都转成“服务暂时不可用”，导致排查困难。务必保留原始错误码和调用栈片段，并接入监控告警。

## 可复用建议

- **工具定义模板**：每个工具都带上 `retry_on`、`fallback`、`circuit_breaker` 的配置项，通过中间件统一处理。
- **Agent 流程预留人工节点**：在自动化链路中设置“需要人工确认”的状态，当错误累计超过阈值或涉及资金操作时，Agent 暂停并通知人工。
- **健康检查与主动切换**：在 Agent 启动或定时巡检中对关键 API 做健康探测，若发现服务不可用，可提前切换备用 endpoint 或降级策略，避免运行时频繁失败。
- **记录每一次错误和恢复策略**：结构化日志包含 traceId、工具名、错误类型、重试次数、降级动作。即使最终任务成功，也要让下游清楚哪些数据是降级获得。

## 总结

外部 API 的可靠性不在我们控制范围内，但 Agent 的弹性可以设计。把重试、退避、降级、熔断等通用能力下沉到工具层，并让 Agent 通过标准化的错误结构做出决策，可以避免“API 一挂，全链路停摆”的窘境。最终目标不是 100% 无故障，而是故障发生时，系统能够以最低成本继续运行，或安全暂停并等待恢复，同时在事后便于复盘改进。
