## 背景

在 OpenClaw 里构建自动化代理或工作流时，周期性任务是基本需求——抓取 API 数据、生成日报、轮训消息队列、设备心跳检测等等。平台内置了两种任务触发器：**Cron 调度**与**Heartbeat 调度**。它们看起来都能“定时执行”，但在设计模型和运行表现上有本质差异。如果选型失误，轻则任务堆积，重则在服务重启后静默漏跑，排查起来非常头疼。

本文将基于实际踩坑经验，拆解两种调度的行为差异，给出可工程化落地的选择与方法。

## 什么是 Cron 与 Heartbeat（行为定义，不是 UI 名称）

**Cron 调度**：基于“墙钟时间”的定点触发。你在 task 里写 `cron: "0 9 * * *"`，它就会在每个日历日的 09:00 执行。这类调度在乎的是“在**那个时间点**有没有触发”。

**Heartbeat 调度**：基于固定间隔的连续触发。设置 `interval: 300`（秒），意味着从上一次触发完成后（或从启动开始）开始计时，间隔一到就再次触发。它不在乎现在是几点几分，只在乎“又过了多长时间”。

这两者对应的 openclaw 配置片段如下：

```yaml
# cron 任务
tasks:
  - name: daily-report
    schedule: cron
    cron: "0 9 * * *"
    timezone: "Asia/Shanghai"
    concurrencyPolicy: Forbid

# heartbeat 任务
  - name: mqtt-healthcheck
    schedule: heartbeat
    interval: 30
    maxConcurrent: 1
```

注意：上述键名可能因 OpenClaw 版本略有差异，但语义一致。

## 问题场景

- 你有一个每 30 秒执行一次的心跳检测，偶尔发现日志里同一条任务同时出现了两个实例，导致重复告警。
- 你设置了一个每天早上 8 点的 cron 任务，某天早上重启了 openclaw 进程，结果 8 点没触发，直接跳到了第二天。
- heartbeat 的 interval 设成了 10 分钟，但单次任务执行了 12 分钟，导致后续任务不断堆积，内存缓慢爬升。

这些问题背后，都是对两种调度模型的理解不够精准。

## 工作机制拆解与关键差异

### Cron 调度

- 触发点由系统时钟决定，每次触发时检查“当前时间是否满足表达式”。
- 若上一个实例仍在运行，OpenClaw 默认行为通常为 **Forbid**（阻止新任务创建），不会并发。可在配置中改为 `Replace`（杀掉旧任务启新）。
- 风险：若进程在触发时间点恰好不可用（重启中），该时间点会被**彻底错过**，不会补偿执行。对“不可错过”的场景需要外部监控兜底。
- NTP 时间跳变可能导致同一分钟被触发两次，或直接跳过。

### Heartbeat 调度

- 基于定时器（ticker），从任务“启动”或“上一次完成”后开始计时。OpenClaw 通常采用 **固定速率**：即便单次执行耗时较长，下一个 tick 可能会在短时间后立即发生（即基于开始时间的间隔），这很容易导致并发。
- 如果配置了 `maxConcurrent: 1`，新的触发会被丢弃或排队，但排队会导致任务积压，表现为“执行越来越滞后”。
- 服务重启后，心跳间隔重新开始计算，完全无视历史对齐。例如原本期望在整点触发，重启后可能滑到了诡异的时间点。

## 踩坑实录

1. **Heartbeat 与幂等性**  
   即使设置了 `maxConcurrent: 1`，如果在任务内部没有做业务幂等（例如同一笔订单处理两次），当任务存活时间超过间隔且调度器允许排队时，仍可能出现“串行重复执行”。建议在关键逻辑处引入分布式锁（Redis/etcd）做双重保险。

2. **Cron 的时区陷阱**  
   不少容器镜像默认时区是 UTC，`cron: "0 9 * * *"` 实际在 UTC 09:00 触发，而业务期望北京时间 09:00。务必显式声明 `timezone`，并同步校验 Pod 的 `/etc/localtime`。

3. **Heartbeat 间隔过小导致 goroutine 泄漏**  
   曾经遇到 `interval: 1s` 但任务平均耗时 3 秒，且没有设置 `maxConcurrent`。几分钟后 openclaw 的 goroutine 数量暴涨，最终 OOM。最小安全间隔应保证 `interval > p99 执行耗时 + buffer`。

4. **Cron 漏跑不易感知**  
   推荐在 task 开始时写入一个 `lastStartTimestamp` 指标，并通过外部探活（如 Dead Man's Snitch）监测该指标是否按预期更新，弥补 Cron 自身无补偿的缺陷。

## 可复用的选择思路

做决策时，问自己三个问题：

- **“错过一个时间点是否可以接受？”**  
  若无法接受（如日终对账），用 Cron，并配合外部监控防止漏跑。
- **“任务是否需要尽快响应状态变化，且对精确时间点无要求？”**  
  若是典型的循环检测（如消息队列拉取、设备在线状态轮询），用 Heartbeat，同时务必做幂等和并发控制。
- **“任务单次执行耗时是否经常大于间隔？”**  
  这种情况下两种调度都有问题：Cron 会丢时间点，Heartbeat 会堆积。根本解法是优化任务性能，或改为事件驱动（用 webhook/MCP 通知）替代定时轮询。

简单总结成图：  
- **Cron** → 定点报告 / 数据快照 / 周期性对账  
- **Heartbeat** → 状态轮询 / 健康检查 / 消费未确认消息

工程上，我会在 task 配置开头注释掉最初的设计意图，防止后来者因为看不懂“为什么这里用 heartbeat 而不是 cron”而改错。注释里写清：预期执行频率、可容忍的最大延迟、以及是否需要并发控制。

## 总结

Cron 与 Heartbeat 没有绝对的优劣，它们分别对齐了“定点事件”和“周期间隔”两种编程模型。选错的代价是反复排障和业务漏处理。看清底层行为（时钟依赖、并发策略、重启对齐）并辅以幂等设计和外部监控，才是在 OpenClaw 上稳定运行周期性任务的正解。下次再写定时任务时，先停下来问一句：我需要的是“在9点做”还是“每5分钟做一次”？往往答案就已经出来了。
