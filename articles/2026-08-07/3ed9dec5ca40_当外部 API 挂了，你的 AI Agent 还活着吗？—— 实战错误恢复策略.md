# 当外部 API 挂了，你的 AI Agent 还活着吗？—— 实战错误恢复策略

> 面向 OpenClaw / Agent / MCP / 插件 / 自动化实践者  
> 不谈大词，只讲我踩过的坑和现在每天在用的方法。

## 1. 背景：Agent 总是在等那个“不靠谱”的 API

无论是通过 MCP 调用外部工具，还是在插件里拉取实时数据，Agent 的运行往往卡在某个外部服务上——订单查询、天气接口、模型推理、向量检索。这些外部 API 总有不可靠的时候：

- 上游发布导致 5xx 持续 10 分钟  
- 第三方限流突然收紧，把所有请求标记为 429  
- 一次 DNS 抖动让所有连接超时  
- 看起来正常的 API，偶尔返回半截 JSON

如果你的 Agent 没做任何防御，结果就是**任务中断、状态丢失、重复扣费，甚至给用户返回错误结论**。对自动化流水线来说，一次 API 故障可能让整个工作流卡死，需要人工清理。

## 2. 问题定义：错误恢复不是“多试几次”

直接在 `try except` 里套一个 `while True` 是最常见的错误恢复，但它带来的问题往往比解决的问题更多：

- **无限制重试消耗资源并加剧服务端压力**  
- **非幂等操作被重复执行**（比如创建订单、发送通知）  
- **任务状态丢失**，重启后无法继续  
- **长时间阻塞让上游调用方超时**，级联故障  

真正的错误恢复需要**分类处理、快速失败、优雅降级和状态保留**，同时保证关键副作用只发生一次。

## 3. 做法 / 步骤

下面是我在 OpenClaw 工具链里沉淀下来的 4 层防御方案。

### 3.1 第一层：重试 + 退避，但不是无限

用 Python 的 `tenacity` 库，所有网络请求统一使用以下逻辑：

```python
from tenacity import (
    retry, stop_after_attempt, wait_exponential, retry_if_exception_type
)

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
    retry=retry_if_exception_type((httpx.ConnectError, httpx.RemoteProtocolError)),
    reraise=True,
)
async def call_api(url, payload):
    async with httpx.AsyncClient(timeout=10) as client:
        resp = await client.post(url, json=payload)
        resp.raise_for_status()
        return resp.json()
```

关键约束：

- **只重试可恢复错误**（网络异常、503/429），不对 400 或 401 重试  
- **最大重试次数 + 指数退避 + jitter**，防止 thundering herd  
- **每次重试前检查剩余任务超时**，避免把上游等死  

### 3.2 第二层：降级与回退

对 Agent 关键路径上的每个外部依赖，都准备**至少一个备用方案**：

- **主 API → 次 API**：例如从付费天气 API 切到免费缓存数据  
- **实时查询 → 本地缓存**：用 Redis 或文件缓存上一次成功结果，设置合理 TTL（例如 5 分钟）。当 API 不可用时返回过期数据并打上 “可能过时” 标签  
- **完整功能 → 最小功能**：例如搜索 API 挂了，Agent 自动回复“暂时无法搜索，但我可以基于已有资料回答”

在 OpenClaw 的 MCP 工具定义中，可以给每个工具添加 `fallback` 字段，在调用失败时自动执行降级函数。

### 3.3 第三层：熔断器（Circuit Breaker）

当错误率高到一定程度，重试和降级也无济于事时，需要**快速失败**：

- 使用 `pybreaker` 或自己实现一个基于时间窗口的计数器  
- 错误率超过 50% 时，熔断器打开，直接抛出自定义异常，不再尝试请求  
- 设置半开状态：至少 30 秒后允许一次探针请求，成功则关闭熔断器，失败则继续熔断  

这能保住你的 Agent 不会因为依赖彻底宕机而卡死，同时让上游获得明确失败信号。

### 3.4 第四层：幂等键与状态检查点

这是**最容易翻车**的一层，尤其是涉及支付、消息发送、数据写入的操作。

- **每个外部写操作都生成幂等键**，通常是一次性任务 UUID+操作类型  
- 调用 API 时将幂等键放到请求头或参数中，服务端实现幂等最好，否则客户端自行检查  
- **状态持久化**：Agent 执行到哪一步、哪些外部调用已完成，都存到外部状态存储（如 Redis、SQLite）  
- 重启后**先回放已完成步骤**，跳过已成功的操作，只重试未完成或失败的部分  

在 OpenClaw 里，可以利用其任务图的节点状态，结合自定义的 `checkpoint_store` 做到断点续跑。

## 4. 踩坑实录

- **重复扣费**：支付 API 返回 timeout，Agent 重试，结果用户被扣了两次。根本原因是支付回调没有幂等性。解决：强制要求支付方支持幂等键，否则自己记录每次调用状态，手动对账。  
- **缓存陈旧导致幻觉**：降级到本地缓存后，Agent 拿着 3 天前的数据信誓旦旦地告诉用户“今天晴天”。必须强制在回复中注明数据来源和时间。  
- **熔断器过于敏感**：一次网络抖动导致熔断器打开，后续所有请求全部失败。需要合理设置错误率阈值和窗口大小，避免单一错误触发熔断。  
- **日志缺失**：错误发生时只有一条 500 错误码，没有请求 body 和 trace，无从排查。建议在重试/降级的所有分支都打印结构化日志，带上 `correlation_id`。  

## 5. 可复用建议

- **统一封装客户端**：不要在每个工具里重复实现重试和熔断，写一个 `ReliableAPIClient`，所有外部调用通过它发起。  
- **配置驱动**：将重试次数、超时时间、降级策略做成 YAML 配置，不同环境可以差异化。  
- **故障注入测试**：用 `toxiproxy` 或 Linux tc 模拟网络延迟、丢包，验证降级和熔断是否按预期工作。  
- **监控错误预算**：就算做了全面恢复，依然要统计真实错误率，当错误预算耗尽时及时告警，避免“优雅的失败”变成业务损失。

## 总结

外部 API 挂掉不是“意外”，而是**迟早要面对的生产常态**。在一个可靠的 AI Agent 系统中，错误恢复不应该是一个事后补丁，而应该和正常路径一样被精心设计。从重试退避、降级回退，到熔断和状态恢复，每一步都针对特定故障模式，才能让你的 Agent 在风暴中保持“体面的失败”，而不是崩溃。

如果你正在用 OpenClaw 开发工具链，不妨现在就去检查：你的每个 MCP 插件，是不是都只写了 happy path？
