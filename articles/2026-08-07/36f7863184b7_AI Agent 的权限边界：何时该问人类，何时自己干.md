# AI Agent 的权限边界：何时该问人类，何时自己干

当 AI Agent 不再只是聊天，而是真正开始读写文件、调接口、跑命令的时候，“它能做什么”很快就让位于“它**该在什么时候停下来问**”。这一条权限边界划得合理，Agent 才是提效工具；划得激进，一个误判就能把生产环境搞挂。

这篇文章来源于我们在 OpenClaw 上接入 Agent 做运维和代码仓库自动化的实战，重点不是理论，而是我们怎么定义权限等级、怎么落地确认机制、以及踩过的坑。

---

## 一、为什么权限边界在 Agent 系统中远比 AI 本身重要

传统的 RPA 或脚本，操作边界是代码写死的，风险可控。Agent 不同，它具备规划和工具调用能力，同一套工具在不同上下文中能组合出完全不同风险级别的行为。

比如“执行 shell 命令”这个工具，你让他查看进程信息没问题；但如果他某天决定“删掉昨天那些临时文件”，就可能误删还在用的日志。Agent 没有真正的“后果理解”，它只根据 prompt 和返回值做下一步决策。权限边界就是我们替它划的硬栏杆。

在 OpenClaw 这类能够通过 MCP 挂载任意工具的 Agent 平台上，权限问题更加突出：开发者很容易把数十个工具塞给 Agent，几个高风险工具混在日常工具里，出事只是时间问题。

---

## 二、按风险分层，而不是靠 Agent 自己“想清楚”

我们第一时间就放弃了“让 Agent 在 prompt 里自己判断何时该确认”的方案。实践中 Agent 要么过于保守、事事都问，要么过于自信、直奔高风险操作。

我们的做法是对每个工具函数定义 **risk_profile**，在 Agent 调用工具前由调度层统一拦截。分层规则如下：

| 等级 | 描述 | 示例操作 | 策略 |
|------|------|----------|------|
| 0 – 只读 | 纯查询，不改变任何外部状态 | 读文件、查数据库、list 容器 | 直接执行，异步记录日志 |
| 1 – 低写 | 写操作但影响面完全在沙箱或 Agent 工作区内 | 写 `/tmp/agent/` 下的文件、创建临时分支 | 自动执行，向用户推送摘要通知 |
| 2 – 高写 | 写操作影响共享资源、外部系统 | 更新配置文件、重启服务、调用生产 API | **同步确认**，等待人类回复后执行 |
| 3 – 敏感 | 涉及凭证、权限变更、财务或安全操作 | 修改 IAM 策略、删除 S3 bucket、操作支付订单 | 强制终端确认 + 审批记录 + 二次校验 |

这些定义以 JSON schema 写在工具注册表中，MCP server 暴露工具时同时带上 `risk_level` 字段。Agent 调度器在执行前，先检查元信息，决定是通过、拦截还是转人工。

例如一个用于重启容器的工具：

```json
{
  "name": "restart_container",
  "risk_level": 2,
  "requires_confirmation": true,
  "confirmation_prompt_template": "即将重启容器 {container_id}，请确认操作"
}
```

Agent 规划完调用链后，调度器按最高风险等级拉闸，而不是等每步都确认。

## 三、怎么把确认做得不打断心流

“人类审批”一旦设计成阻塞式对话窗口，用户的工作就会被频繁打断，结果是要么关掉审批，要么敷衍点确认。

我们的做法是：

- **统一入口异步化**：所有风险等级 2 的确认消息，默认进入消息队列，通过 IM、邮件或 OpenClaw 内的通知中心推送，不弹模态框。用户可以在方便时统一处理。
- **批量确认**：如果 Agent 规划了一个多步骤任务，里面包含 3 个高风险操作，调度器会把它们打包成一个任务单，用户勾选批准项后一次放行。
- **时效与降级**：确认请求如果 5 分钟内没响应，自动拒绝并让 Agent 走降级路径。避免任务卡死。

这里有一个容易踩的坑：很多团队会忽略 **降级路径设计**。当人类拒绝或超时，Agent 不能直接崩溃或乱试，必须预定义替代行为（例如：只输出报告、跳过该步骤并标记风险、或切换为只读模式）。

## 四、实际翻过的三个坑

### 1. Agent 用低风险操作“拼装”出高风险行为

Agent 可能会用多个 level-0 和 level-1 的工具组合出更高影响面。比如先读密钥文件（0 级），再写到另一个位置（1 级），再通过其他 API 泄露出去。

**对策**：不只看单个工具风险，还要在运行时做**调用链分析**。我们做了一个简单的状态机追踪数据流，当检测到敏感信息被从受限域拷贝到外部可访问位置时，强制阻断并上报。

### 2. 确认疲劳导致安全降级

上线初期风险策略太严，level-1 操作也要确认，用户直接要求关掉所有审批。后来我们把 level-1 改为静默执行+摘要推送后，对 level-2 的确认接受度反而高了。

**教训**：确认的成本必须明显低于等待成本，但又要覆盖真实风险。只在高写操作上卡点，其余自动化。

### 3. 工具风险等级设完就不再更新

随着业务变化，原本“低风险”的工具可能变成高风险。一个重启开发环境容器的工具，某天被用于重启预生产集群，因为环境标识被 Agent 动态拼接。

**对策**：每两周审查一次工具调用审计日志，重点关注那些“被用在非预期上下文”的操作，用实际数据反推风险分级调整。

## 五、可复用的工程骨架

如果你正在 OpenClaw 生态里给 Agent 挂工具，可以考虑这样开始：

- 在 MCP server 的工具描述 schema 中增加 `risk_level` 和 `confirmation_message` 字段。
- 编写一个 **RiskInterceptor** 中间件，挂载在 Agent 的工具调用管道上。
- 基于 risk_level 策略：0/1 放行，2 入审批队列，3 强拦并记录完整上下文。
- 审批侧实现一次批量确认接口，而不是每个操作单独打断。
- 定期跑一份《Agent 权限越界报告》，把所有 risk_level 为 0/1 但结果影响到共享资源的调用记录下来。

---

## 总结

AI Agent 的权限边界不是写在 prompt 里的“请小心操作”，而是代码化的、可审计的路障。好的边界设计让 Agent 在该快的时候快，在该停的时候停，而且停下来时不会把人的耐心磨光。对于 OpenClaw 这种已经把 Agent 能力推得足够远的平台，这一步不做，后面全是雷。

**不要让一个能改你配置的系统，拥有它不懂克制的自由。**
