## 背景

当我们用 AI 辅助生产技术内容时，输出几乎都是 Markdown。无论是 OpenAI、Claude 还是本地模型，生成的文章、Tutorial、Release Notes，拿到的第一手格式就是 Markdown。问题在于，这些内容最终要分发到不同的平台：GitHub Pages、微信公众号、知乎、Notion、飞书文档，甚至 Confluence。每个平台对 Markdown 的“方言”容忍度完全不同，甚至关键语法（换行、图片、公式、表格）的行为差异巨大。

在过去半年的持续内容输出中，我们逐渐把“Markdown 后处理”固化成一条自动化管线，让它成为 OpenClaw 任务编排中的一个标准流程。这篇文章就还原这个管线的设计、实现、踩坑，以及几个可以立即复用的模式。

## 问题拆解

我们的典型内容流程是：用 Agent 触发 LLM 生成原始 markdown → 人工微调 → 多平台发布。痛苦集中在第三步。看似只是复制粘贴，实则每次都要花 5~15 分钟做格式清理，遇到公式和表格甚至要重写。核心矛盾有三类：

1. **换行与段落差异**：微信公众号编辑器要求段间空行，连续两个换行才会产生段落间距；GitHub 则对紧邻换行友好，而一些平台会吃掉单个 `\n`。
2. **扩展语法支持不一致**：脚注、任务列表、LaTeX 公式、高亮块（`== ==`）等，在知乎、公众号上基本不工作。
3. **图片与资源引用**：本地相对路径在其他平台无法解析，需要提前替换成图床 URL，且不同平台对图片尺寸、居中的要求也不同。

手动处理这些问题不仅低效，还容易遗漏。如果把这项工作自动化，理想形态是：一份 AI 生成的原始 Markdown，经管线处理后，产出分别适配 GitHub、微信公众号、知乎、Notion 的 Markdown 文件。

## 管线设计

我们的管线运行在 OpenClaw 的任务流中，由一个专用 Agent 负责调用。整体分四步：

### 1. 平台规则配置

通过一个小的 MCP Server 暴露各平台的格式需求。Server 维护一个 JSON 配置，内容类似：

```json
{
  "wechat": {
    "line_breaks": "double",
    "image_type": "upload_url",
    "forbidden_syntax": ["footnote", "latex", "definition_list"],
    "code_block_require_lang": true
  },
  "zhihu": {
    "line_breaks": "single",
    "support_tables": true,
    "image_type": "zhihu_upload",
    "forbidden_syntax": ["callout", "math_block"]
  }
}
```

OpenClaw 里的 Agent 在遇到“格式化 Markdown”任务时，会先从该 MCP Server 拉取目标平台规则，再调用本地转换器。

### 2. 通用预处理

预处理脚本基于 `mistune` 或 `markdown-it-py` 做 AST 遍历，完成以下操作：

- 统一换行符为 LF，并根据目标平台要求插入空行（公众号需要段间保留两个换行）。
- 清除或转换不支持语法：比如脚注转成文内括号注释；数学 `$$...$$` 块在微信目标下被替换为图片占位符，后续由渲染步骤替换成已上传图床的公式图片。
- 代码块自动补齐语言标记：微信编辑器如果 codeblock 没有语言标识，常会丢失高亮，脚本会检测缺失标记并补 `text`。
- 图片引用改写：将所有本地路径或相对路径替换为配置里的图床前缀，如果是需要上传到知乎的场景，则输出一份待上传清单供后续人工触发。

### 3. 平台专属后处理

预处理后得到一份“规范化 Markdown”，再按不同平台套一层专属过滤器：

- **微信公众号**：额外移除所有内联 HTML 标签（微信会直接过滤），并将 `>` 引用块转成带 Emoji 的普通段落，因为微信编辑器的引用样式不稳定。
- **知乎**：表格必须包含表头分隔行且所有列左对齐（否则渲染崩溃），脚本会强制重写表头语法；同时预留一个 `<!--more-->` 折叠标签。
- **Notion**：Notion 导入 Markdown 不支持嵌套列表过深，最多三层。管线会自动将超过三层嵌套的列表平铺成段落加缩进效果。

### 4. 输出与人工核验

管线最终输出多份文件：`article-github.md`、`article-wechat.md`、`article-zhihu.md`、`article-notion.md`。OpenClaw 的 Agent 会把这些文件打包上传到临时位置，并艾特负责人进行最终核验。通常我们只在公众号和知乎文件上花 1~2 分钟微调外观，其他基本零改动。

## 踩过的坑

1. **mathjax 转图片的时机**：最初直接在预处理阶段把所有 LaTeX 公式用 MathJax 渲染成 SVG 并上传图床，但发现知乎支持部分 LaTeX（行内公式可渲染），强制转图片反而降低阅读体验。后将决策逻辑改为：仅当目标平台不支持对应公式语法（块级或行内）时才渲染。

2. **代码块缩进问题**：AI 生成的内容偶尔会有以 Tab 或 4 空格缩进开始的“代码块”，在标准 Markdown 中会被解析为代码块，但有些平台（如飞书）只认围栏式 ```。我们在预处理中统一将缩进代码块转为围栏式。

3. **编码与特殊字符**：微信编辑器对某些 Unicode 符号（如数学粗体 𝘅）会显示乱码，导致整段丢失。管线添加了一步字符替换映射，将不安全的特殊字符转成普通文本。

4. **图片上传的异步处理**：当管线自动上传图片到图床时，图床服务限流可能导致部分图片链接仍为空。我们改成同步批量上传并重试 2 次，失败则保留原始引用并在日志告警，由人工补传。

## 可复用建议

- **不要试图编写万能转换器**：为每个平台单独写过滤器，哪怕有代码重复，也比一堆 `if-else` 分支可维护得多。
- **让规则配置外置**：用 MCP 或简单的 JSON/YAML 存放平台差异，新增加平台只需补充配置和少量过滤器。
- **结合 CI 触发**：把管线集成到 Git 仓库的 pre-commit 或 CI 中，每当有新文章提交，自动生成分发用文件，避免遗忘。
- **保留原始 Markdown**：管线应始终保有一个未修改的原始版本，方便未来增加新平台或变更规则时重新生成。

## 总结

从“AI 生成 Markdown”到“多平台内容分发”，中间的格式适配是一项容易被忽略的工程债务。我们通过一条结合 OpenClaw Agent、MCP 配置和模块化过滤器的管线，把每次发布前的摩擦降到几乎为零。这条管线并不复杂，但它让我们从机械的格式调整中解放出来，把精力集中在内容质量上。如果你也正被多平台内容分发困扰，不妨用类似的方式抽象出一层后处理，哪怕最初只有 50 行脚本，也能立刻带来收益。
