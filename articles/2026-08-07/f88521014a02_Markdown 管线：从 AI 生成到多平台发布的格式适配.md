## 背景

用 Agent 或大模型批量生成内容后，下一步往往是把结果发布到多个渠道：微信公众号、知乎、Notion、个人博客（基于 GitHub Pages 或 Hugo）等等。这些平台对 Markdown 的支持程度完全不同——有的根本不认 markdown，有的认但会阉割部分语法，有的需要把内容拆成 API 可接受的 JSON 结构。如果每个平台都手动复制粘贴再修格式，不仅效率低下，还容易引入各种样式脏数据。

工程化的解法是建一条 Markdown 管线：让 AI 输出标准化的 markdown，中间层做一次语义保留的格式转换，最后按目标平台的约束生成对应的格式并推送。这篇文章记录我在 OpenClaw 场景下搭建这条管线时的主要问题、选型思路和可复用的实践。

## 问题拆解

把问题摊开来看，主要是三类不兼容：

1. **语法支持差异**  
   - 微信公众号：基于富文本编辑器，完全不解析 markdown。需要提前把 markdown 转成符合微信后台限制的 HTML 片段（代码高亮样式会被过滤，表格宽度限制严格）。  
   - 知乎：支持部分 markdown，但图片必须通过知乎的上传接口托管，不能简单依赖外链。表格、脚注的处理也经常走样。  
   - Notion：使用块（block）模型，markdown 的层级结构必须映射为 block 数组，且 API 对富文本标注（加粗、斜体、行内代码等）有特定格式要求。  
   - 静态网站生成器（如 Hugo、VitePress）：对 GFM 支持相对完整，但前端模板对 frontmatter、短代码的依赖需要额外生成。

2. **资源引用处理**  
   AI 生成的 markdown 里可能包含本地路径、临时外链或相对路径图片。多平台发布时，图片必须上传到各平台各自的 CDN 或用统一图床替换链接。若涉及代码截图（例如用 carbon 生成的高亮图片），尺寸和命名也需要规范。

3. **元数据与排版约束**  
   各平台的标题层级深浅、摘要、封面图、标签等元数据格式各异。微信要求摘要字数限制，知乎需要话题绑定，Notion 需要指定父页面/数据库 ID 等。

## 做法与步骤

### 1. 标准化 AI 输出
首先约束 Agent 的 system prompt，要求输出纯 GFM 语法的 markdown，并通过 few-shot 示例强调：
- 图片用 markdown 语法，且链接必须为空占位符或统一前缀，留待管线替换。
- 不使用 HTML 标签（除 `<details>` 等在特定场景可允许）。
- 代码块必须指定语言。
- 表格列数控制，避免超宽。
- 避免多级嵌套的无序列表，微信转 HTML 时易丢样式。

在 OpenClaw 中，可通过 Agent 调用 MCP 工具（如自建的内容审查工具）对生成内容做一次快速校验，确保不出现超出标准的语法。

### 2. 构建中间转换层
转换层我选择用 Python 实现，核心依赖 `mistune` 做 markdown 解析，生成统一的内部文档模型（一个 dict，包含标题、段落、图片、代码块等有序列表）。然后为每个目标平台编写适配器，把内部模型渲染成平台需要的格式。  
关键转换规则：
- **微信**：渲染成 HTML，将代码块替换为带内联样式的 `<pre>`（高亮通过 Pygments 预处理为行内 span），表格包裹在 `<div style="overflow-x:auto">` 中，列表使用微信兼容的 `<section>` 模拟。由于微信会过滤 class 和 style，内联样式尽量精简。图片全部上传到微信临时素材然后替换链接。
- **知乎**：输出兼容知乎的 markdown，保留 GFM 表格但限制列宽。图片通过知乎 API 上传后替换链接。
- **Notion**：使用 `notion-client` 库，把内部模型按递归规则转为 blocks 数组（每个块类型指定富文本注释数组），处理列表嵌套时正确设置子块关系。
- **静态网站**：直接输出原 markdown，附加 frontmatter（标题、日期、标签）用于 Hugo 等生成器。

### 3. 自动化发布管线
管线运行在 OpenClaw 的一条 workflow 上：  
- AI 生成内容 → 写入临时文件。  
- 触发转换脚本，生成各平台目标文件（微信 HTML 文件、知乎 markdown、Notion blocks JSON、网站 markdown）。  
- 并行或顺序执行发布：微信使用 Selenium 模拟浏览器输入 HTML（注意借助 `wxpy` 或官方 API 可能受限）；知乎使用自动化工具（如 `zhihu-py`）上传图片并发布文章；Notion 通过 API 创建页面并追加 blocks；网站通过 git 提交推送触发 CI 部署。  

发布步骤中加入重试逻辑和失败告警，避免部分成功造成内容不同步。

## 踩坑实录

1. **微信代码块高亮丢失**  
   最初尝试直接在 HTML 里用 `<code>` 带 class，但微信会清洗掉所有 class 和复杂的 style。最终改为使用 Pygments 生成完整内联样式的 `<span>` 包裹每个 token，虽然 HTML 体积膨胀，但能保住高亮效果。如果内容极长，可考虑将代码块渲染为图片替代，但会牺牲可访问性和可搜索性。

2. **表格在微信裁剪**  
   移动端微信对太宽的表格会横向截断。转换层增加了表格列宽预测：若总字符数超过阈值，自动将表格转为图片（用 matplotlib 渲染），否则保留 HTML 表格。需要权衡视觉和加载速度。

3. **Notion API 的速率限制**  
   批量 append blocks 时频繁触发 429。改为每次请求最多添加 100 个块，并在请求之间插入 500ms 延迟，同时利用 API 的块分组批量创建子块，降低请求数。

4. **图片上传失败静默跳过**  
   有些平台上传接口不稳定，偶尔超时。为每个上传步骤添加重试队列（最多 3 次），失败后记录日志但不阻塞整体发布，事后人工补发。

## 可复用建议

- **用内部文档模型解耦**：不要针对每个平台写零散的字符串替换，而是建立语义化模型，适配器只关心如何编码为该平台的格式。
- **配置文件驱动**：每个平台的认证信息、父页面 ID、图床配置等抽离到环境变量或配置中心，方便切换和维护。
- **增量测试**：先为每个适配器写单元测试，用已知 markdown 输入验证输出片段，再集成到管线中。
- **监控和通知**：通过 Webhook 将发布结果推送到你的聊天工具（如 Slack、微信机器人），确保内容运营同学能及时知晓。
- **从简单开始**：最初不要试图覆盖所有平台，先打通一两个最重要渠道，再逐步添加适配器。

## 总结

Markdown 管线本质上是内容自动化最后的一公里。它不复杂，但琐碎且容易忽视。在 OpenClaw 这类 Agent 编程环境中，利用脚本语言快速搭建中间层，结合 MCP 工具的校验能力，能够把 AI 生成到多平台发布的工作流从“半自动”提升到“一键可靠发布”。当你不再需要为不同平台手工调格式时，所节省的不仅是时间，更是持续输出的信心。
