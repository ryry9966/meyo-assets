不论你日常使用 OpenClaw 编排自动化任务，还是通过 MCP 让模型调用外部工具，一个常见痛点始终存在：Agent 对你的工作习惯、本地环境、代码偏好几乎一无所知。每次新建会话都要重复交代“我习惯用 pnpm”、“我的项目在 ~/workspace/agent-playground”、“请用中文回复”这类信息。上下文窗口有限，重复输入成本高，还可能导致模型遗忘关键约束。

这类问题的本质不是模型能力不足，而是缺失一份结构化的“用户画像”。一份设计得当的 USER.md，可以成为 Agent 的系统级记忆，让它启动时就清楚你是谁、你在做什么、你想要什么。这篇文章会介绍如何在 OpenClaw 中实现可复用的 USER.md，以及在工程化落地过程中的一些实践和踩坑记录。

---

## 1. 背景与问题定义

在 Agent 实践中，“用户上下文”往往被零散地塞进 prompt 的 system message 或开场白里，缺乏统一的存储和加载机制。常见表现：

- 脚本执行时默认使用系统 Python，而不是你常用的 conda 环境；
- 操作文件路径时，Agent 总是从根目录开始猜，而不是直接使用你的项目根目录；
- 分支命名、commit 风格、注释语言等细节每次都要重说一遍；
- 当任务跨越多个子 Agent 或调用链，用户偏好信息会丢失。

这不仅是效率问题，还会影响自动化流水线的稳定性。我们需要一个确定的“用户自述文件”，让它成为 Agent 初始化流程的一部分。

---

## 2. USER.md 的设计思路

USER.md 不是简单记事本，而是一份面向 Agent 的可解析用户档案。设计时应考虑三个层次：

- **静态信息**：语言、时区、名称、常用 shell、编辑器和 IDE 配置、开发环境路径。
- **偏好与规范**：包管理器（npm/pnpm/yarn）、代码风格（缩进、引号、命名规范）、Git 工作流、注释语言。
- **环境变量与上下文**：指向常用项目目录、密钥引用（不存明文），以及 MCP 工具链的约定。

文件格式推荐 Markdown，理由是在绝大多数平台都能直接渲染，且 Agent 可以按标题提取段落。示例如下：

```markdown
# USER.md
## 基本信息
- 称呼：Alex
- 语言：zh-CN（中文回复）
- 时区：Asia/Shanghai（UTC+8）

## 工作环境
- 系统：macOS
- shell：zsh
- 默认编辑器：cursor
- 包管理器优先级：pnpm > yarn > npm

## 项目约定
- 代码仓库根目录：~/workspace
- 当前活跃项目：agent-playground, openclaw-plugins
- 分支命名：feat/xxx 或 fix/xxx
- Commit 规范：Conventional Commits

## 工具链
- MCP 配置文件：~/.openclaw/mcp.json
- Python 环境：conda activate agent-dev
- Node.js 版本管理：fnm
```

这只是基础模板，具体内容可根据你的实际场景增减。

## 3. 在 OpenClaw 中的加载方式

OpenClaw 天然支持通过配置文件注入系统级上下文。建议的实现路径如下：

**步骤一：确定 USER.md 的存放位置**
建议放在 `~/.openclaw/user.md` 或与项目绑定的位置 `project/.openclaw/user.md`。如果需要切换多身份，可采用 `~/.openclaw/profiles/` 目录。

**步骤二：在 openclaw.yaml 中引用**
在 OpenClaw 的配置文件中加入自定义上下文，例如：

```yaml
user_context_file: ~/.openclaw/user.md
```

然后在 Agent 启动时，读取该文件内容并拼接到 system prompt 的固定位置。更推荐的方式是通过 MCP 资源动态提供：编写一个轻量 MCP server，提供 `resource://user-profile`，返回 USER.md 的全文。这样做的好处是可以在调用链的任何节点重新获取用户上下文，而不依赖会话初始注入。

**步骤三：Agent 提示模板中嵌入**
在 system prompt 模板中加入变量 `{{USER_CONTEXT}}`，由框架在运行时替换为 USER.md 内容。注意控制长度，避免撑破上下文窗口。可以考虑只注入相关小节，而非全量。

**步骤四：在自动化流程中引用**
如果工作流由多个子任务构成，每个子任务启动时都应携带用户上下文。可以利用 OpenClaw 的 task 模板或 MCP 工具在每次调用前自动获取 `resource://user-profile`，并将其追加到 messages 中。

## 4. 踩坑记录

实践过程中，以下几个点需要留意：

- **上下文窗口污染**  
  USER.md 写得过于冗长，尤其在频繁调用的自动化循环里，会快速消耗 token 预算。建议静态信息长度控制在 300–500 字以内，环境相关部分可按需动态加载。

- **敏感信息泄露**  
  API key、私钥路径等绝不能直接写入 USER.md，因为该文件可能被不同 Agent 实例读取，日志中也可能泄露。密钥应通过环境变量或专门的 secret 管理工具提供，USER.md 中只写入变量名或引用说明。

- **多项目冲突**  
  当同时维护多个项目时，通用习惯可能与项目特定要求冲突（例如包管理器优先级）。解决方法是为每个项目准备一份 `project/.openclaw/user.md`，并让 Agent 优先检测项目级的配置。OpenClaw 支持层级合并，先加载全局，再覆盖项目级设定。

- **变更不生效**  
  修改 USER.md 后，若 Agent 已缓存上下文，可能看不到更新。建议在每次会话开始或关键任务前加入一个“刷新用户上下文”的动作，或者在 MCP server 中返回资源时带上 `no-cache` 提示。

- **Agent 忽略用户偏好**  
  即使上下文已注入，模型在某些 prompt 中仍可能遗忘。可以通过在关键指令中显式引用 USER.md 的内容，比如“请根据你的 user profile 中所述，使用 pnpm 初始化项目”，增强遵循率。

## 5. 可复用建议

在你的团队或组织中推广 USER.md，可以采用以下方式：

1. **模板化**  
   提供一份基础模板，让开发者 fork 后自行裁剪。模板中保留常用字段，用占位符标记必填项。

2. **与 MCP 深度结合**  
   将用户画像做成 MCP 的动态 resource，支持按场景过滤。例如 `user-profile?scope=git` 只返回 Git 相关约定，减少无关信息。

3. **校验与提示**  
   在 OpenClaw 启动时检查 USER.md 是否存在，若缺失则输出友好提示，引导创建。这可以通过 hook 脚本实现。

4. **版本控制（注意隐私）**  
   不包含敏感信息的全局 USER.md 可以纳入 dotfiles 仓库管理，配合多设备同步。项目级的 user.md 可以提交到仓库中，作为团队协作规范的一部分。

5. **定期更新**  
   每季度或每次环境重大变更后，回顾并更新 USER.md，确保 Agent 始终基于最新信息工作。

---

## 总结

一个设计得当的 USER.md，不是增加维护负担，而是让 AI 助手从“通用工具”变成“个人助理”的关键一步。在 OpenClaw 这类 Agent 框架中，通过结合配置文件和 MCP 资源，可以让用户上下文可发现、可注入、可按需裁剪，从而显著降低重复沟通的成本，并提高自动化任务的执行准确性。

从今天开始，为你的 Agent 写一份 USER.md，让它在每次启动时就知道自己是在为谁工作。
