## 背景：为什么定时任务需要两种模式

在 OpenClaw 这类面向 Agent 与插件化的自动化框架中，时间驱动逻辑几乎是所有稳定运行 Workflow 的骨架。无论是周期性抓取 MCP Server 的状态、执行固定时间的数据同步，还是守护一个长时间运行 Agent 的健康检查，都依赖「定时任务」。

与其他框架只提供单一的 cron 调度不同，OpenClaw 同时暴露了 **Cron** 和 **Heartbeat** 两种触发方式。一开始很多人会直觉认为这只是两种表达时间的方法，但在工程实践里，它们的资源模型、失败容忍度和适用场景完全不同。错用会导致任务堆积、漏报、甚至 Agent 卡死。本文将结合在实际运维 OpenClaw 插件生态时的经验，梳理这两种模式的设计意图、选型逻辑与踩坑记录。

## 问题：一眼 Cron，一时爽，上线就感不对

最常见的保守做法是：所有周期任务都直接上 Cron 表达式。比如每 5 分钟触发一次数据采集插件「poll-mcp-status」，每 30 分钟运行一次「clean-agent-logs」。在开发机上跑几天也没问题，一旦放到生产环境，问题就暴露出来：

1. **任务执行时间超出间隔**：数据采集插件一旦遇到下游 MCP 服务抖动，单次执行可能超过 5 分钟，Cron 仍然准时触发，导致多个相同任务并发，争抢数据库连接或者产生重复写入。
2. **Agent 生命周期绑定混乱**：有些任务需要在 OpenClaw Agent 实例启动后持续运行，但 Cron 与 Agent 状态无关，Agent 挂掉重启后，旧 Cron 注册可能残留幽灵任务。
3. **不适合精确的轮询守护**：需要「每隔 10 秒检查一次任务队列深度」这种高频轻量检查，Cron 的最小粒度为一分钟且无内置去重，高频使用会引入大量定时器压力。

Heartbeat 正是为了解决这类问题而设计的，它的核心不是「在固定时刻触发」，而是「在上一轮完成后，等待固定间隔，再发起下一轮」。

## 做法：两种模式的触发语义对比

在 OpenClaw 配置中，Cron 和 Heartbeat 都可以通过插件 manifest 或任务调度 API 注册。区别在于引擎内部的调度状态机：

- **Cron 任务（系统时钟驱动）**：由全局 Cron Scheduler 管理，基于系统时间匹配调度，严格按照 `*/5 * * * *` 这种表达式触发。任务之间完全独立，上一次任务未完成不影响下一次触发，除非显式启用并发控制（MaxConcurrency=1）。
- **Heartbeat 任务（实例心跳驱动）**：绑定在 OpenClaw Agent 或 Plug-in Runtime 的生命周期内。上一个任务执行结束（`Completed` 或 `Failed`）后，计时器开始计时，达到间隔后再启动下一次。间隔不是事件间隔，而是**完成到下一次启动的静止间隔**。

实现一个简单的对比示例：

```yaml
# Cron 风格：每 5 分钟采集一次
task_type: cron
schedule: "*/5 * * * *"
max_concurrency: 1        # 防止堆积的关键参数
job:
  entry: mcp_collector/run

# Heartbeat 风格：采集完成后等待 5 分钟再执行
task_type: heartbeat
interval: 300s            # 静止等待 300 秒
job:
  entry: mcp_collector/run
```

表面看效果差不多，但实际区别很大：Cron 的「每 5 分钟」是墙钟时间，如果采集过程花了 2 分钟，那任务结束后 3 分钟就会再次触发。Heartbeat 则是任务结束后等待完整的 5 分钟，总周期变成了「执行耗时 + 5 分钟」，任务密度更低但更安全，不会随下游响应变慢而恶性堆积。

## 踩坑点：这些地方很容易翻车

### 1. Heartbeat 与 Agent 重启的竞态
Heartbeat 任务在 Agent 崩溃重启后，会重新加载定时器，容易造成一次立即触发（看实现版本）。如果任务逻辑不是幂等的，可能导致重复执行。需要在任务入口处做防重锁，例如基于 Redis 的 `SETNX`，或者在任务表中记录 `last_run_id` 避免重复处理同一批次数据。

### 2. Cron 的时区隐式依赖
OpenClaw 的 Cron 解析器默认跟随宿主进程时区。在多区域部署时，Docker 镜像没设置 `TZ`，导致 Cron 触发时间偏移 8 小时。务必在 Agent 部署环境强制设定 `TZ=UTC`，并在表达式里用 UTC 时间编排业务逻辑，避免本地时间幻觉。

### 3. 并发限制配置不生效
Cron 任务的 `max_concurrency=1` 在某些旧版本插件 SDK 中只作用于同一定义的任务实例，如果对同一个插件入口多次注册不同 ID 的 Cron 任务，并发限制是独立的，仍然会同时跑多个。解决办法是集中管理，不要在多个配置文件中重复注册同一逻辑的任务。

### 4. Heartbeat 的间隔过长导致错觉
设置 `interval: 600s` 后，发现任务每隔接近 620 秒才触发一次。这不是 bug，而是因为 Heartbeat 间隔是「完成到启动」的静止时间，若任务自身执行需要 20 秒，周期自然拉长。业务上需要保证最大周期，就要用 `interval - max_exec_time` 来推算配置值。

## 可复用建议：一套选型 check list

在实际维护 OpenClaw Agent 集群时，我总结了下面的决策流程，适合在评审每个定时任务时快速对照：

1. **任务是否与 Agent 实例强绑定？**
   - 是 → 必须使用 Heartbeat，避免 Agent 重启后残留 Cron 任务。
   - 否 → 进入下一步。

2. **执行耗时是否可能超过间隔的一半？**
   - 是 → 倾向于 Heartbeat，避免并发堆积；若坚持用 Cron，必须加防重锁且设置 `max_concurrency=1`。
   - 否 → 可以安全使用 Cron。

3. **业务是否需要严格按墙钟时间对齐？**
   - 是（如每天 0 点对账）→ 只能用 Cron，Heartbeat 会因为任务执行延时导致时间漂移。
   - 否（如采集、轮询、心跳上报）→ Heartbeat 更稳定。

4. **频率是否大于 1 次/分钟？**
   - 是 → 避免使用 Cron，Cron 最小粒度 1 分钟，高频轮询用 Heartbeat（或长连接、watch 机制），防止调度器压力过大。

5. **任务是否幂等？**
   - 无论哪种模式，必须保证任务可重复安全执行。Heartbeat 的重启触发、Cron 的偶尔重叠，都需要幂等兜底。

额外补充：对于需要长时间运行的守护类任务，比如持续读取 MCP 资源变更流，建议放弃定时模式，直接使用 OpenClaw 的 Stream Subscription 或长连接，避免用轮询制造无意义负载。

## 总结

Cron 和 Heartbeat 并非谁更好，而是解决不同层面的时间可靠性问题。Cron 是「墙钟可靠」，适用于固定时刻的对账、日切、报表生成；Heartbeat 是「间隔可靠」，更适合跟服务负载直接相关的采集、轮询和健康检查。理解这两种可靠性语义的差异，比背 Cron 表达式更重要。

实际工程里，最危险的永远是「一条 cron 走天下」的惯性。每个定时任务注册时都应该问一遍：我需要的是墙钟可靠，还是间隔可靠？答案会自然指向正确的选择。
