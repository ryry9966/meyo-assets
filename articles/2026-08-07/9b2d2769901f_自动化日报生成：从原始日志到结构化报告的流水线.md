## 背景：被日报绑架的早晨

每天早上到工位第一件事，就是从几套系统的运行日志、CI 输出、Git 提交记录里捞出关键事件，写成一份结构清晰的日报发给团队。这活儿不难，但重复、琐碎，而且人眼扫日志总有漏掉关键异常的时候。恰好团队已经跑着 OpenClaw 作为日常助手的基础设施，我们决定把这个流程工程化成一条无人值守的流水线。

## 问题拆解：什么在阻止直接丢给模型

原始日志有几个典型特征让“一把梭”变得不现实：

- **总量大且增长快**：一天的业务日志轻松破十万行，远超 LLM 上下文窗口。
- **非结构化噪音多**：时间戳、trace id、堆栈信息混在一起，需要选择性提取。
- **日报要求结构固定**：指标汇总、异常事件、部署记录、待跟踪事项都得覆盖，不能凭空编造。
- **时效与幂等性**：同一区间不能重复出报，也不能漏掉跨天临界点的事件。

这意味着需要一套分阶段、有状态的 Agent 流水线，而不是一句 prompt 就能搞定。

## 做法：用 MCP 工具链把日志变成结构化日报

我们的流水线建立在 OpenClaw 的 Task Agent 之上，借助自定义 MCP Server 对接日志源，让 Agent 以可控的方式按步骤获取、摘要、组装。

### 1. 日志获取 MCP 工具

写了一个名为 `log-fetcher` 的 MCP Server，对外暴露两个工具：

- `list_log_sources(date)` — 返回当天可用的日志源列表（如 `ci-build`, `prod-api`, `db-slowlog`），每种标注大概行数和关键字段。
- `get_log_chunk(source, offset, limit)` — 按偏移量取一段原始日志（每段控制在 2000 行以内），返回纯文本加元数据。

Agent 不会看到全量日志，但它可以像翻书一样按需索取。这种设计把上下文压力转移到了工具的调用策略上。

### 2. 流水线设计

一次日报生成被拆为四个阶段，由 Agent 自主规划执行。

**阶段一：信息检索**
Agent 调用 `list_log_sources` 了解当日有哪些数据源，然后对每个源询问“是否有异常/关键变更”，通过多次 `get_log_chunk` 结合 `cat` 风格的摘要提示先产出源级摘要。

**阶段二：摘要合并与验证**
收集所有源级摘要后，Agent 进入验证模式。它被要求检查是否有明显缺失（比如昨天有部署但摘要里没提到），若怀疑有缺失，会调用带更细时间范围的 `get_log_chunk` 进行补全。

**阶段三：结构化模板填充**
此时上下文里只有经过提炼的关键事件列表，Agent 按照预设的日报模板输出：

- 整体概况（1-2 句）
- 服务健康与指标摘要
- 异常事件（含发生时间、影响、是否恢复）
- 部署与变更记录
- 遗留项 / 待办

**阶段四：分发与落库**
生成的 Markdown 日报通过一个 `send_report` 工具（走企业微信或邮件）发出，同时将报告哈希和覆盖的时间窗口存入 SQLite，下一轮执行前先查库避免重复。

### 3. 实际调用链示例

下面是一段简化的任务 Prompt（系统指令通过 OpenClaw 的 Goal 注入）：

```
你是日报生成代理人。
1. 获取昨天所有日志源的摘要。
2. 验证关键事件无遗漏。
3. 按指定模板输出日报，仅使用工具返回的数据，不得编造。
4. 发送前自语检查是否满足模板完整性。
```

Agent 的操作日志可以看到：
- `list_log_sources("2025-03-26")`
- `get_log_chunk("prod-api", 0, 2000)` → 摘要
- `get_log_chunk("prod-api", 2000, 2000)` → 摘要
- ... 合并后输出日报。

### 4. 代码骨架

MCP Server 的核心用 Python 实现，利用 `mcp` 标准库快速构建：

```python
@server.tool()
async def get_log_chunk(source: str, offset: int, limit: int) -> str:
    path = LOG_ROOT / source / f"{DATE}.log"
    lines = read_lines(path, offset, limit)
    return "\n".join(lines)
```

Agent 通过 OpenClaw 内置的 MCP 客户端直接使用该工具，无需额外适配。

## 踩坑实录

**坑1：大日志的摘要失真**
早期我们让 Agent 一次性读取整个 CI 日志（三万多行）硬出摘要，结果 LLM 无提示截断，导致一次构建失败被忽略。改进为强制按 2000 行分区摘要后再合成，并增加验证提示“报告中是否包含所有错误级别的事件？”。

**坑2：时间窗口的边界问题**
每晚 23:59 到 0:00 之间的日志归属容易双重计数。最终通过原子写入 `last_processed_until` 时间戳，并且日报覆盖 `[last_processed_until, now)` 左闭右开规避。

**坑3：幻觉信息美化报告**
有次模型在缺乏数据时自行补充了一段“服务整体稳定”，实际上凌晨有局部故障。修复方式：强制检查每条陈述是否都能追溯到工具返回的原始摘要，并在系统指令中加入“不推断不猜测”。

## 可复用建议

- **细粒度工具优于大上下文**：别试图把全部日志塞进 context，做成带游标的分片工具，让 Agent 本身成为调度器。
- **摘要-验证-模板三阶段解耦**：在内部 Task 中显式切分，可以用不同温度或不同模型实例调优，节省成本。
- **模板外置**：日报的结构放在一个独立的配置文件中，Agent 读取后填充，非技术人员也能改模板。
- **保留一键重跑能力**：通过提供 `--force` 参数忽略时间戳锁，允许手动重出日报，用于调试或补报。
- **人审兜底**：目前我们在 `send_report` 前增加一个“草稿审阅”开关，发送到指定群确认后再发全组，节省抽检精力。

## 总结

把日报生成从手工作业变成 Agent 流水线，本质上是把一个非结构化数据抽取问题转化为有状态工具编排问题。借助 OpenClaw 与 MCP 的工具描述能力，我们得到了一个稳定跑了一个多月、误报率极低的生产级小流程。对于团队里其他类似的重复性报告场景（周报、on-call 摘要），这条流水线的设计思想能低成本复用。
