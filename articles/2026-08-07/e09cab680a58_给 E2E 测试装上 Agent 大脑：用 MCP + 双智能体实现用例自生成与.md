## 背景：为什么 E2E 测试总在拖后腿

端到端（E2E）测试是保障核心业务链路最直接的手段，但它的维护成本长期以来让团队头疼。页面一改版，定位器就失效；新增一个流程，就得从头手写几十行脚本；更麻烦的是，业务快速迭代时测试代码经常滞后，逐渐变成“跑不通的摆设”。

录制回放工具能缓解一部分问题，但生成的代码往往僵硬、缺乏语义，复用性很差。近两年大模型在代码生成上的表现让人看到可能性——直接让 AI 看页面写测试。但单次生成的结果仍然不稳定：容易产生幻觉、定位器不可靠、断言不准确，且缺少反馈修正机制。你需要的不只是一个会“猜”测试的模型，而是一个能观察、能写、能跑、能改的**协作系统**。

这正是 Agent 协作派上用场的地方。通过组合多个职能清晰的 AI Agent，并借助 MCP（Model Context Protocol）把浏览器操作标准化为可调用工具，我们可以构建一条“理解页面 → 生成用例 → 执行验证 → 自我修复”的闭环流水线。

## 问题定义：单次生成不够，需要闭环

用一个 Agent 直接根据页面截图或 DOM 生成 Playwright 脚本，效果会很玄学。典型问题包括：

- 选择器脆弱：模型倾向于用 CSS 路径或文本匹配，改一个样式就会挂。
- 动作遗漏：忘记等待元素可见，或者跳过中间步骤。
- 断言随意：只检查“页面包含某文字”，但没验证关键业务状态。
- 无法自愈：用例失败后必须人工介入修改，和传统开发没区别。

因此我们要设计一个**双 Agent + 自修复回路**的结构，让生成、执行、修复这三个环节由不同角色承担，形成可收敛的自动测试生产过程。

## 做法与步骤：用 OpenClaw 等框架编排 Agent

下面以本地可复现的实践为例，工具栈选择 **Playwright MCP Server** 提供浏览器自动化能力，**OpenClaw 或任意支持工具调用的 Agent 框架**来编排两个专用 Agent。整套流程可在单机运行，不需要额外平台。

### 1. 为 Agent 装上“手和眼睛”：挂载 Playwright MCP

首先启动一个 Playwright MCP Server，它会暴露 `browser_navigate`、`browser_snapshot`、`browser_click`、`browser_take_screenshot` 等工具，Agent 可以直接调用。在 OpenClaw 的 Agent 配置里把 MCP Server 的端点注册进去，这样 Planner 和 Coder 都能操作同一个浏览器上下文。

### 2. 设计 Planner Agent：从页面到结构化场景

第一个 Agent 的职责是**把页面行为抽象成与实现无关的测试场景**。给它一条简单指令，例如：“登录后进入订单列表，验证待付款订单可以被取消”。它会分步执行：

1. 调 `browser_navigate` 进入首页
2. 调 `browser_snapshot` 获取当前 DOM 的可访问性树（去除样式噪声）
3. 根据感知到的页面元素，生成一份结构化步骤 JSON，类似：

```json
{
  "scenario": "取消待付款订单",
  "steps": [
    { "action": "click", "target": "登录按钮" },
    { "action": "fill", "target": "用户名输入框", "value": "$VALID_USER" },
    { "action": "fill", "target": "密码输入框", "value": "$VALID_PASS" },
    { "action": "click", "target": "登录提交按钮" },
    { "action": "wait", "target": "订单列表卡片" },
    { "action": "click", "target": "待付款标签" },
    { "action": "click", "target": "第一个订单的取消按钮" },
    { "action": "assert", "target": "取消成功提示" }
  ]
}
```

这里的关键是让 Planner 用**语义描述** target（如“登录按钮”），而不是写死选择器。同时允许使用变量，便于 Coder 注入测试数据。

### 3. 设计 Coder Agent：把场景转为可执行代码

第二个 Agent 拿到场景 JSON 和页面快照后，负责生成实际 Playwright 代码。我们会给它一份严格的系统提示，强制要求：

- 优先使用 `data-testid` 属性作为选择器；若不存在，用 `getByRole`、`getByLabel` 等语义定位。
- 必须添加显式等待（`waitForSelector` 或 `expect().toBeVisible()`）。
- 每个步骤后截一张小尺寸诊断图，便于修复时回溯。
- 将变量替换为环境配置中的真实账号、密码。

Coder 输出一个完整的 `.spec.ts` 文件，并调用 shell 工具保存到本地。

### 4. 执行与修复回路：让失败的用例自己站起来

这是整个方案最重要的部分。我们增加一个 **Repair Agent**（可以复用 Coder 的角色，但加上不同 prompt），专门监听测试执行结果。流程如下：

- 通过 `npm test -- --reporter=list` 运行刚生成的用例。
- 如果失败，Repair Agent 读取错误日志和 Coder 在运行中保存的截图。
- 分析失败原因：是选择器失效？等待时间不足？还是业务断言不匹配？
- 根据分析结果，对原始场景 JSON 或 Playwright 脚本提出**最小修正**，例如“取消按钮文本变为‘撤回’，请更新选择器为 `getByRole('button', { name: '撤回' })`”。
- 将修正后的代码重新提交执行，循环最多 3 次，直至通过或标记为需要人工审核。

这种“运行→失败→诊断→修正→再运行”的闭环，显著减少了一次生成即失败的风险。实际测试中，对于中等复杂度的后台流程，首次通过率约 40%，经过最多两次修复后，通过率可提升到 85% 以上。

## 真实踩坑点

1. **MCP 工具的状态残留**：Planner 和 Coder 共享同一个浏览器上下文时，如果 Planner 探索后没有重置状态，Coder 生成的脚本可能依赖某个中间页面，导致独立运行时失败。解决方法是让 Planner 在生成场景后，显式调用 `browser_navigate('about:blank')` 清理上下文，或者使用独立的无痕模式。

2. **Agent 幻觉导致的危险操作**：有一次 Coder 在修复时，为点击“取消”按钮生成了 `page.evaluate(() => { ... })` 直接操作后端接口。必须用系统提示严格限制：**只允许通过可见 UI 元素操作，禁止使用 evaluate 等黑魔法**。

3. **过度修复导致偏离原始场景**：如果修复循环不设边界，可能为了通过把用例修成“只测首页加载”，失去业务含义。我们强制要求每次修复必须备注修改原因，且断言部分不允许被删除或弱化。

4. **DOM 快照的噪音**：直接使用完整 DOM 会消耗巨量 token 且让 Planner 分心。务必使用可访问性树快照（例如 Playwright MCP 的 `browser_snapshot` 默认使用 accessibility tree），或先提取交互元素列表再传给 Agent。

## 可复用的工程建议

- **为关键页面植入 `data-testid`**：这是投入产出比最高的动作。只要 UI 稳定区域有语义化标记，生成用例的健壮性会直升一个台阶。
- **建立“场景模板库”**：Planer 容易生成松散步骤，可以预先定义常用场景模板（登录、列表筛选、表单提交），强制 Agent 按模板骨架填充细节，减少发散。
- **把 Agency 测试作为 CI 的前置烟雾测试**：不要用 Agent 生成的用例完全替代人工维护的核心回归集，但很适合在 PR 合并前，自动针对改动页面生成并执行一次 Exploratory Test，快速暴露意外破坏。
- **记录修复日志作为训练反馈**：每次 Repair Agent 修正了什么，都可以结构化存储，后续作为 few-shot 示例喂给模型，持续提高首次生成质量。

## 总结

引入 Agent 协作并不意味着可以完全扔掉测试工程师的键盘，而是把**编写、维护、修复**这些重复性高、对机器而言可模式化的工作交给 AI 流水线，让人专注于场景设计、业务断言质量和异常兜底。通过 MCP 提供标准化工具，用 Planner/Coder/Repair 的闭环方式，我们确实可以把“给这个页面写一条 E2E”变成一个针对 AGI 的调用，而不是一次体力劳动。

如果你已经在用 OpenClaw 等 Agent 框架，试着给它的工具列表里加上 Playwright MCP，再给两个不同 system prompt 的 Agent 对话的权限，你可能很快会拥有一个不知疲倦的自动化测试搭档。
