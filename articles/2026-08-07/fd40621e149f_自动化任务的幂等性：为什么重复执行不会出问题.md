## 背景：重试带来的“幽灵执行”

在 OpenClaw 的 Agent 编排、MCP 工具调用或插件驱动的自动化流程里，你几乎无法避免同一个任务被多次触发。原因往往很朴素：

- 消息队列至少投递一次（at-least-once delivery）
- HTTP 回调超时后客户端重试，实际服务端已处理成功
- 用户在面板上不小心双击了「运行」按钮
- Agent 策略在不确定性中反复尝试同一个工具调用

如果不做任何防护，重复执行可能会创建两条相同的工单、重复发送通知、对同一个资源执行两次变更——数据错乱、脏数据、业务投诉随之而来。

让同一个请求无论执行多少次，最终效果与执行一次相同，这就是**幂等性**。它是工程上最小的安全网，也是自动化系统从“能用”走向“可依赖”的第一道门。

## 问题：无幂等性的典型故障

设想一个通过 MCP Server 暴露的「创建云服务器」工具。某次 Agent 决策后调用该工具，因网络抖动返回超时，Agent 框架判断失败并再次调用。如果服务端没有幂等控制，你将得到两台相同的机器，而用户只想要一台。

类似的场景还包括：

- 基于 Webhook 触发的内容发布流程，重复推送同一篇文章
- 定时备份任务因调度器 HA 切换而执行两次，产生两份额外存储费用
- 支付回调通知多次抵达，发起重复扣款

这些问题的共同点：**操作本身非幂等，且没有基于业务标识的去重机制**。

## 做法/步骤：设计幂等执行的几个关键点

### 1. 定义清晰的幂等键

每个自动化任务都应携带一个由调用方或业务本身决定的幂等键（idempotency key）。这个键不是随机 UUID，而是要能唯一标识一次业务意图。比如：

- 消息去重：`msg_id` 或 `event_id`
- 订单操作：`order_id + action_type`
- 定时任务：`task_name + scheduled_time`

键的粒度很重要。只用 `task_name` 去重会导致不同参数的执行被误判为重复；反过来，把时间戳塞进去则会让幂等性完全失效。

### 2. 状态机 + 乐观锁

在任务执行的持久化上下文中（数据库或状态存储），引入简单的状态机：

`pending → processing → completed / failed`

使用乐观锁更新状态，例如（伪代码）：

```
UPDATE tasks SET status = 'processing', version = version + 1
WHERE id = :id AND status = 'pending' AND version = :old_version
```

只有成功将状态从 `pending` 扭转为 `processing` 的执行者才有资格继续。其他重入请求会因更新行数为 0 而提前退出，可以选择直接返回已有结果，或者返回「正在处理中」。

### 3. MCP 工具内置幂等层

如果你在开发或使用 MCP Tool，建议将幂等键作为必填参数之一。工具实现侧可以：

- 将 `idempotency_key` 与执行结果缓存（带 TTL），重复请求直接返回缓存。
- 对创建类工具，利用数据库的唯一索引（如 `UNIQUE(idempotency_key)`）阻止重复写入。
- 对于有副作用的查询类工具（如触发报告生成），同样适用。

示例工具定义片段：

```json
{
  "name": "create_issue",
  "parameters": {
    "idempotency_key": { "type": "string", "required": true },
    "title": { "type": "string" },
    "description": { "type": "string" }
  }
}
```

### 4. 对已有系统的“外挂式”幂等

有时你无法修改自动化执行的目标系统，只能在上游做幂等。这时候可以维护一张轻量级的去重表，记录 `(key, status, result)`。所有执行请求先查表再决定是否真正执行，执行完毕后更新状态。这种模式在插件化架构中很实用——插件本身无感知幂等，但调度器负责去重。

## 踩坑点

- **状态锁粒度过大**：用全局锁（如 Redis 锁全表）会导致无关任务互相阻塞。请用幂等键本身作为锁资源。
- **未区分「执行中」和「已完成」**：一个请求正在跑，另一个相同 ID 的请求到来，如果直接返回“done”可能导致调用方提前处理未就绪的结果。正确做法是返回“processing”，或阻塞等待直到完成。
- **QPS 高时缓存穿透**：仅靠数据库唯一索引扛高并发会引发大量重试错误，可配合 Redis 的 `SET NX EX` 做快速互斥。
- **失败的幂等处理**：第一次执行失败，是否允许第二次执行？通常应该允许，但需要明确将状态从 `failed` 重置为 `pending` 或直接允许传入新的幂等键重试。
- **超时任务的状态一致性**：定时任务如果因为执行超时被调度器认为失败重试，但实际任务仍在跑，需要设置合理的超时检查和心跳机制。

## 可复用建议

1. **为每个对外暴露的自动化入口增加幂等键参数**，不管底层是否立即支持。习惯养成后，往幂等方向演进成本极低。
2. **使用 OpenClaw 的任务模型**时，将 `task_id + attempt` 作为天然幂等键，确保同一尝试不会重复处理。
3. **避免仅依赖分布式锁而不持久化状态**。锁过期可能导致重复执行，最终必须由数据库唯一约束或状态机兜底。
4. **测试幂等性：对任何自动化流程，编写一个测试用例：并发发送 N 个相同的执行请求，验证最终业务效果只有 1 次。**
5. **为失败重试预留接口**：前端或 Agent 调用时，允许通过不同的幂等键（如追加 `retry` 维度）发起全新尝试，而不是死锁在旧的失败状态。

## 总结

幂等性不是高深的技术，而是一种工程习惯。在自动化任务频繁交织、工具随意调用、重试几乎无处不在的 Agent 和 MCP 生态中，它就像代码里的静默守护者——不用时无感，缺失时致命。你只需要一个稳定的幂等键、一套极简的状态切换、一层廉价的去重缓存，就能让系统在重试风暴里保持优雅。

最终目标是：**用户可以毫无心理负担地多次点击同一个按钮，Agent 可以重试任何工具调用，而世界依然井然有序。**
