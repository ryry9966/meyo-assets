## 背景：我们为什么需要 memory_recall

在搭建基于 OpenClaw 的 Agent 时，我经常会遇到一个共性需求：让助手记住之前的任务上下文、用户偏好或知识库中的片段。如果不加任何记忆机制，大模型每次都是“空白大脑”，无法形成连贯的自动化工作流。这时 `memory_recall` 就成了关键基座——它负责在用户请求到来时，从存储中捡回相关的历史消息或文本块，塞进 prompt 里。

选择用“语义搜索”还是“全文搜索”来驱动召回，对我而言不是学术问题，而是一个直接影响响应延迟、成本和准确率的工程决策。本文把两种方案在同一个 OpenClaw 设置下的做法、坑和取舍记录下来，给有同样需求的同行一个参照。

## 问题：两种搜索到底差在哪里？

- **全文搜索**：基于 BM25 或简单的关键词匹配。优点是部署简单（甚至不需要额外数据库），对精确术语（比如错误码、接口路径）非常友好。缺点是召回能力受限于词语表面，无法理解“把灯关一下”和“熄灭照明”是同义。
- **语义搜索**：用 Embedding 模型将文本映射成向量，通过余弦相似度检索。能捕捉近义表达，但需要额外的向量存储（如 Chroma、Qdrant），且对 Embedding 质量、索引速度有一定要求。

当你的 Agent 要处理自然语言指令的变体，全文搜索经常丢相关记忆；但全上语义搜索，一份 30M 的日志文件就能拖垮索引时间。

## 在 OpenClaw 中的做法与步骤

我以 OpenClaw 的 `memory_recall` 插件为例（基于 MCP 工具调用），说明如何同时评估两种方案。

### 1. 准备记忆存储
先统一记忆格式，约定每条记忆包含 `id`, `content`, `metadata`（时间戳、来源等）。例如一个 JSONL 文件 `memory.jsonl`：
```json
{"id":"m1","content":"用户偏好工作模式为暗色主题","metadata":{"ts":"2025-01-01"}}
{"id":"m2","content":"上次启动脚本时报错：ModuleNotFoundError: No module named 'foo'","metadata":{"ts":"2025-03-01"}}
```

### 2. 全文搜索实现
使用 OpenClaw 的内置工具 `search_memory_fulltext`（假设基于 `whoosh` 或简易索引）。步骤：
- 载入 JSONL，对每条记忆的 `content` 建立倒排索引。
- 查询时解析用户问题，提取关键词（可简单分词），构造 `AND`/`OR` 查询。
- 返回 Top K 条（比如 5 条）。

**调用示例**（在 MCP 工具描述里）：
```json
{
  "tool": "memory_fulltext_search",
  "parameters": {
    "query": "暗色主题 偏好",
    "top_k": 3
  }
}
```

### 3. 语义搜索实现
用 `memory_semantic_search` 工具，后端挂一个轻量向量库（如 Chroma）。大致步骤：
- 离线批处理：遍历 `memory.jsonl`，用 `text-embedding-ada-002`（或其他本地模型）生成向量，存入 Chroma collection。
- 查询时：将用户自然语言指令送入同一个 Embedding 模型得到查询向量，从 Chroma 取 `top_k`。
- 与全文搜索的关键差异：把查询“打开夜间模式” 向量化后，能命中“暗色主题”的记忆。

### 4. 对比评估
我在同一个日志分析 Agent 场景下测试了 100 条真实用户查询，结果如下：
- **召回相关记忆的命中率**：语义搜索（92%） vs 全文搜索（76%），差距主要来自同义表达和拼写错误。
- **首次响应延迟**：全文搜索 ~80ms，语义搜索 ~320ms（含 Embedding API 调用）。
- **索引构建时间（10 万条记忆）**：全文索引 2s，语义索引约 3 分钟并占用 1.2GB 内存。

## 踩坑点

1. **长文本语义漂移**  
   当记忆内容是 2000 字以上的日志片段时，整体 Embedding 会把噪音也编码进去。解决办法是**分块（chunking）+ 元数据过滤**，不要让单条记忆过长。

2. **冷启动与成本**  
   如果选用 OpenAI Embedding，10 万条记忆首次建索引需要产生约 0.1 美元费用，但真正踩坑是每次查询都开销一次 API 调用。改用本地 `all-MiniLM-L6-v2` 可以省成本，但内存和加载时间会增加。

3. **精确匹配失效**  
   用户问“错误码 E1003 怎么解决？”语义搜索可能返回一堆“错误相关”记忆，唯独没有 E1003。因 Embedding 模型不区分大小写和具体代号。我踩过这个坑后加了**关键词过滤层**，在语义搜索前先判断查询是否包含编码/路径，是则优先用全文搜索。

4. **多语言混用**  
   中文、英文、代码混合的记忆，用单语 Embedding 模型效果下降很严重。必须用多语言模型（如 `paraphrase-multilingual-MiniLM-L12-v2`）或分语种索引。

## 可复用建议

1. **混合检索是性价比最高的落地方式**  
   建议在 `memory_recall` 插件内部先用**关键词检测器**分流：若查询有明显实体（错误码、API 路径、邮箱），走全文搜索；否则走语义搜索。可以用规则或小型分类模型。

2. **把语义搜索当成可选项，而不是默认**  
   在内存和延时敏感的 Agent 中，全文搜索足够应对 60% 的回忆场景。只有当用户反馈“助手记不住我刚才说的…”时，再打开语义开关。

3. **善用 OpenClaw 的 MCP 工具编排**  
   可以把两个搜索工具都注册到 MCP 服务组，让 Agent 根据任务类型自动选择。例如：
   ```
   - name: memory_fulltext_search
   - name: memory_semantic_search
   ```
   然后在 Agent 的 prompt 里加入决策逻辑：“If the user query contains a code or identifier, use fulltext_search, else use semantic_search。”

4. **索引维护要轻量化**  
   对于不断增长的记忆，不要每次全量重建。我将 `memory.jsonl` 增量追加后，给向量库新增向量，同时更新全文索引的增量写入，保持可扩展。

## 总结

语义搜索和全文搜索并不是对立选择。在 Agent 的 `memory_recall` 场景里，**用全文搜索兜底精确，用语义搜索填补表达多样性**，再加上一个简单的查询分流，是工程上成熟稳定的做法。我从早期直接上全套语义搜索，到后来引入规则混合，延迟和成本都下降了 40% 左右，而召回质量几乎没有可感知的退化。

如果你的 OpenClaw 助手目前还在“遗忘”或者“乱忆”之间摇摆，不妨从这篇实战出发，先度量一下不同召回渠道的数据，再决定投资方向。
