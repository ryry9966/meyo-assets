## 背景

在构建基于 OpenClaw、Agent 或 MCP 插件的自动化流水线时，服务端经常需要感知助手（或执行节点）是否存活、任务是否卡死、当前进度如何。这种存活检测与状态同步，就是“heartbeat”。社区里常见两类实现思路：

- **轮询（Polling）**：助手每隔固定间隔主动请求状态接口
- **推送（Push）**：建立长连接，由服务端主动下发事件

两种方案在工程落地中差异巨大，但并没有单一的“最佳实践”。本文从真实项目踩坑出发，梳理取舍逻辑、关键实现步骤，以及可复用的设计模式。

## 问题

最近在实现一个多步骤 Agent 任务，需要让前端感知任务进度，同时又要让运行器确认调度中心在线。很自然地，初期采用了最简单的轮询：前端每 2 秒 GET 一次 /task/{id}/status，调度中心据此判断客户端存活。

很快暴露了三个问题：

1. **无效请求过多**：任务耗时从几秒到十几分钟不等，大量请求返回“运行中”，浪费带宽和 CPU。
2. **延迟放大**：轮询间隔 2 秒，状态变更平均延迟就是 1 秒；如果临时调整间隔，心跳间隔也跟着变，超时阈值要同步重算。
3. **连接堆积**：并发任务数上升后，轮询请求占用大量短连接，数据库 session 查询压力明显增大。

切换到 WebSocket 推送后，把这些短轮询全换成长连接事件流，服务端压力立刻下降。但长连接本身也带来了新的维护负担：断线重连、心跳超时清理、负载均衡后的会话保持等。

## 做法

最终我们沉淀了一套混合策略，兼顾系统不同部分的特性：

### 1. 任务进度与结果：SSE（Server-Sent Events）

Agent 执行任务时，服务端通过 SSE 把阶段变更、日志行、最终结果推送到前端。前端只需建立一次连接，就能连续消费事件。HTTP/2 下没有连接数限制，实现也远比 WebSocket 简单，尤其适合**单向推送**场景。

```
# 服务端示例（Python FastAPI）
from fastapi import FastAPI
from sse_starlette.sse import EventSourceResponse
import asyncio

app = FastAPI()

async def event_generator(task_id: str):
    while True:
        # 从消息队列取事件
        event = await get_task_event(task_id)
        yield event
        if event.type == "task_end":
            break

@app.get("/task/{task_id}/stream")
async def stream(task_id: str):
    return EventSourceResponse(event_generator(task_id))
```

### 2. Agent 存活检测：带退避的轻量轮询

对于“这个 Agent 还活着吗”，轮询依然是最稳健的选项，原因是：

- 网络环境复杂时，长连接容易误判失联
- 心跳请求体积极小（通常只返回 `{"status":"ok"}`）
- 可以用指数退避避免固定频率的毛刺

具体做法：Agent 每 10 秒发一次 POST /heartbeat，调度中心记录时间戳。超时 30 秒无心跳则标记失联。轮询间隔动态调整，在任务空闲时退避到 30 秒，任务执行中保持 10 秒。

### 3. 内部通道：WebSocket 的按需使用

当多个微服务需要双向通讯时（比如调度器主动杀死任务、Agent 上报中断），会选择 WebSocket。但必须做三件事：

- **强制心跳**：客户端每 15 秒发送 ping 帧，服务端回复 pong
- **重连策略**：指数退避 + 随机抖动，避免惊群
- **会话状态重建**：断连后客户端立即发送上次已收到的事件 ID，服务端做增量推送

## 踩坑点

- **SSE + HTTP/1.1 浏览器连接限制**：如果同时开多个 SSE 流，超过 6 个会被阻塞。用 HTTP/2 或改用 WebSocket 解决。
- **轮询造成的数据写放大**：如果心跳接口每次都要写数据库（更新时间戳），高并发下很伤。改用 Redis 续期，或只写内存、定期批量落地。
- **“假活”心跳**：有些代理或容器会缓冲 TCP，应用层觉得连接正常，实际上对端已死。必须在心跳请求里带上唯一序列号，服务端验证是否连续。
- **推送重连时全量同步的开销**：断线后盲目全量拉任务状态会引发雪崩。要设计游标/增量同步机制。

## 可复用建议

1. **单任务推送用 SSE 就够了，不要一上来就 WebSocket**。SSE 无协议改造成本，库支持普遍。
2. **存活检测保持 HTTP 轮询**，配合动态间隔 + Redis 续期，简单可靠。
3. **一定要模拟网络闪断测试**：连续 kill 连接、断网 5 秒，观察重连后的状态连续性。
4. **为心跳设计“软、硬”超时**：软超时（15 秒）只报警不摘除，硬超时（30 秒）触发自我保护，避免网络抖动导致大面积 false positive。
5. **在日志中埋点**：记录心跳间隔的 p50/p99，可及时发现间隔异常漂移。

## 总结

AI 助手的 heartbeat 设计，本质是**在简单轮询与实时推送间寻找系统性平衡**。没有银弹，但可以形成明确的决策链：

- 需要进度回传 → SSE
- 需要双向控制 → WebSocket（做好重连）
- 仅需确认存活 → 轻量轮询 + 动态间隔

把心跳视作系统韧性的一环，而不是随手一个定时请求，就能避免上线后第三天的凌晨报警。
