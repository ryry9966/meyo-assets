## 背景：当 AI 走进你的仓库

OpenClaw 这类 Agent 框架让 AI 能够直接在工作空间里执行命令、读写文件、调用 MCP 服务。它不再只是一个对话窗口，而是一个可以真正操作代码仓库的自动化助手。但问题也随之而来：AI 默认不了解你的项目约定、目录职责、敏感文件边界，甚至不知道哪些测试命令是安全的。

一个典型的翻车场景：让 Agent 优化某个模块，它却遍历了全仓，把 `node_modules` 里的代码也改了；或者它用了一个已经废弃的内部脚本，因为那个脚本恰好排在 PATH 靠前的位置。这些问题不是模型的错，而是**缺乏一份写给 AI 的工作空间说明书**。

AGENTS.md 就是为此而生的。它是一份放在仓库根目录的 Markdown 文件，专门为 AI Agent 提供项目上下文和操作边界。你可以把它看作给新同事的 onboarding 文档，但读者是代码化的智能体。

## 问题拆解：没有 AGENTS.md 时会发生什么

1. **任务越界**：Agent 修改了本不该碰的文件，比如 CI 配置、锁文件、自动生成的代码。
2. **信息过载**：Agent 为了理解代码结构，需要反复通过 `ls`、`cat` 探索目录，浪费大量 token 和时间。
3. **命令误用**：Agent 把开发环境的启动命令直接用在生产配置上，或者用了仅限本地使用的脚本。
4. **安全泄漏**：Agent 可能将 `.env` 内容、密钥路径等暴露在终端输出中，即便你事后删除，日志也可能已泄露。
5. **风格不一致**：不同 Agent 任务产出的代码风格、命名约定、commit message 格式参差不齐。

这些问题不是靠更长的系统提示词就能解决的。系统提示是通用约束，而 AGENTS.md 是**工作空间强相关的上下文说明书**，可以随仓库版本化、随分支演进。

## 实践做法：写一份能用的 AGENTS.md

### 1. 文件位置与加载机制

把 `AGENTS.md` 放在仓库根目录，与 `README.md` 同级。OpenClaw 在启动工作空间时会自动扫描并加载该文件，将其内容注入到 Agent 的工作上下文中（通常作为 system message 的补充）。为了确保生效，可以在 OpenClaw 配置中显式指定：

```yaml
workspace:
  agent_instructions_file: "AGENTS.md"
```

如果版本不同，建议将 `AGENTS.md` 纳入版本控制，这样 Agent 在执行历史任务时也能读到对应分支的约定。

### 2. 内容结构建议

一份务实的 AGENTS.md 约 200-500 行，不宜过长（token 浪费）。推荐以下七个板块：

- **Project Overview**：一句话说明项目是什么，用哪种语言/框架，一句话描述架构风格（如“模块化 monorepo with pnpm workspaces”）。
- **Directory Map**：关键目录的用途，不穷举所有文件，只列 Agent 很可能需要知道的（`src/`, `tests/`, `scripts/`, `docs/`, `config/` 等）。
- **Development Commands**：安装依赖、启动开发服务、运行测试、构建、lint 的命令，并标注哪些命令是安全的、哪些会修改生产数据。
- **Code Conventions**：命名规范、文件组织、测试放置规则、commit message 模板。可以引用 `.eslintrc`、`prettier.config`，但 Agent 无法直接读取配置文件的语义，所以最好用自然语言重述一遍。
- **File Boundaries**（最重要）：明确**只读文件/目录**（`package-lock.json`, `CHANGELOG.md`, `generated/`）、**禁止操作的文件**（`.env`, `credentials/`, `terraform/` 等）、**可安全修改的范围**。这是防止越界的第一道防线。
- **MCP / Tool Preferences**：列出可用的 MCP 服务器和首选工具，例如“使用 `git-mcp` 而不是手写 git 命令”，或“使用 `issue-tracker-mcp` 查询任务”。这能避免 Agent 自己做字符串拼接去调 API。
- **Constraints & Anti-patterns**：常见的错误操作和陷阱，比如“不要直接运行 `docker-compose down -v`，会清空开发数据库”，“不要修改 `tsconfig.json` 的 paths，除非你同时检查了 webpack 别名配置”。

### 3. 撰写技巧与工程化思维

- **用 Agent 能理解的语言**：避免被动语态和隐含前提。例如，不要说“请注意路径”，而是说“所有测试文件位于 `tests/` 目录下，命名格式为 `*_test.py`”。
- **标记命令的副作用**：用 emoji 或标签标注，比如 🔴 表示危险、🟢 表示只读。Agent 会利用这些视觉线索。
- **示例优于描述**：给出正确的命令调用示例，Agent 模仿示例的成功率远高于抽象描述。
- **版本注释**：在文件顶部注明最后更新日期和对应的 OpenClaw 版本，避免信息过期。

## 踩坑记录

在真实使用中，我们踩过这几个坑：

1. **AGENTS.md 变成“大而全”的项目文档**。有人把 8000 行的技术文档全部塞进去，结果每次 Agent 调用都要加载这堆无用上下文，token 消耗剧增，响应速度明显变慢。**教训**：只保留 Agent 当前任务可能用到的元信息，详细文档放在 `docs/`，并在 AGENTS.md 中给出索引（“详细架构见 `docs/ARCHITECTURE.md`”）。

2. **命令描述不完整**。写了“运行测试用 `npm test`”，但没有说明这个命令会同时跑 e2e 测试，需要启动数据库容器。Agent 在 CI 环境中照做，直接阻塞 10 分钟。**教训**：标注命令的前提条件和执行时间，比如“需要 Docker 运行中，耗时约 3 分钟，仅修改单元测试时用 `npm run test:unit`”。

3. **File Boundaries 模糊**。只说“不要改生成的代码”，但没列出来具体目录。Agent 在重构时仍进了 `gen/` 目录。**教训**：必须用绝对路径或相对根目录的 glob 明确列出禁止/只读区域，Agent 很少主动查 `.gitignore`。

4. **忽略了跨分支差异**。主分支的 AGENTS.md 无法覆盖功能分支的特殊约定（比如某个实验模块），导致 Agent 在分支上操作时沿用主分支的旧规则。**教训**：在开发分支上同步更新 AGENTS.md，或者至少在 PR 模板中提醒检查 AGENTS.md 是否需要调整。

## 可复用建议

- **提供社区模板**：维护一个 `AGENTS.md` 模板仓库，按技术栈分类（Node.js monorepo、Python 微服务、Go CLI 工具等），团队 clone 后只填项目特定信息。
- **CI 检查**：写一个脚本，验证 AGENTS.md 中列出的禁止修改文件确实被 Agent 触及时会报警（例如检查 git diff 的路径）。
- **与 `.gitignore` 联动**：AGENTS.md 中不要列出所有忽略文件，而是注明“任何 `.gitignore` 中的路径在未特别说明情况下均视为不可修改”这一规则，由框架层面保证。
- **定期瘦身**：每两个版本迭代后清理 AGENTS.md，删掉过时的命令和废弃的目录，保持信息密度。
- **培训 Agent 主动查阅**：在系统提示中增加一句：“在执行任何修改前，先阅读仓库根目录的 `AGENTS.md` 并确认文件边界”。这是增强可靠性的低成本手段。

## 总结

AGENTS.md 不是一份“政治正确”的文档，而是一线工程中确实能降低 Agent 操作风险的说明书。它的核心价值在于**将隐式项目知识显式化、结构化**，让 AI Agent 不再是“盲飞”，而是带着一份工作空间地图在执行任务。写得越好，Agent 产生的怪事就越少，你对自动化的信任感也会随之增加。

对于 OpenClaw 用户来说，AGENTS.md 是连接人类工程规范与 AI 执行能力的那座桥——修好它，不要让它成为断头路。
