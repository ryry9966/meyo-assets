## 背景

基于 OpenClaw + MCP 构建的 AI Agent，大量依赖外部 API 或远程工具完成实际工作：查询天气、调用搜索引擎、触发 CI/CD、读取数据库。这些依赖天然不可靠——服务可能因为限流、超时、网络抖动或对方宕机而临时不可用。如果 Agent 在工具调用失败时不做任何处理，整个任务链会直接中断，用户体验很差，尤其在自动化流水线里，一次第三方故障就能拖垮一整条 workflow。

最近在维护一套使用了多个 MCP server 的 Agent 时，我们碰到了频繁的间歇性 API 故障，迫使系统性地设计了错误恢复与降级策略。这篇文章记录下实践思路和可复用的工程做法。

## 问题

Agent 调用外部工具时，典型失败模式有三种：

1. **瞬时故障**：网络超时、短暂限流，重试后即可恢复。
2. **持续性故障**：对方服务宕机、密钥失效、接口下线，重试无效。
3. **部分失败**：一次请求中部分数据返回成功，部分字段缺失或出错。

不做处理时，Agent 会直接把工具返回的报错原文当作事实，然后自行推断出不可控的结论，甚至开始“编造”数据。更糟糕的是，某些 Agent 设定里，工具调用失败会直接终止整个会话，没有任何恢复机会。

## 做法与步骤

### 1. 为每个外部依赖定义重试策略

不要无差别重试。区分幂等请求和非幂等请求：

- **幂等的 GET 类请求**：执行 `exponential backoff`，起始等待 500ms，上限 5s，最多重试 3 次。可在 MCP server 内部实现，例如使用 `tenacity` 库。
- **非幂等 POST 类请求**：仅重试连接超时等明确安全的错误，业务逻辑错误（如 400）不重试，直接返回结构化错误给 Agent。

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
import requests

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=0.5, max=5),
    retry=retry_if_exception_type((requests.Timeout, ConnectionError)),
)
def call_weather_api(city: str):
    ...
```

### 2. 在 MCP 工具中返回结构化错误

MCP 工具调用失败时，不要让 Agent 拿到原始异常字符串。定义统一的错误返回格式，包含错误原因、是否可重试、建议后续动作。

```json
{
  "error": "WEATHER_API_TIMEOUT",
  "retryable": true,
  "message": "当前城市天气数据暂时无法获取，请稍后重试或使用缓存数据",
  "fallback_available": true
}
```

Agent 的系统提示词里增加处理指引：遇到 `retryable` 为 true 的错误，可在下一个用户回复中询问是否重试；如果 `fallback_available` 为 true，则使用旧数据并标注时间。

### 3. 实现本地 fallback 缓存

对频繁使用、时效性要求不高的数据，维护本地过期缓存。例如天气信息可缓存 30 分钟，当实时 API 失败时自动返回缓存值，并在返回说明里加上“数据来源于最近一次成功查询 (2025-01-15 14:30)”之类的注释。

简单实现可使用 Python 的 `functools.lru_cache` 配合手动过期，或用 `cachetools.TTLCache`。

### 4. 增加断路器

防止重试风暴把上游服务打得更死，也保护 Agent 自身的资源。对每个外部服务实例维护一个失败计数器，连续失败 5 次后进入 OPEN 状态，后续请求直接短路返回降级响应，不再实际发起调用。设定 30 秒后进入 HALF_OPEN 尝试恢复。

可用 `pybreaker` 这类库快速集成。

### 5. Agent 层面的降级指令

在 Agent 的系统提示词中明确告知每个工具的降级行为：

> 如果天气工具返回错误且提供了 fallback 数据，请使用该数据，并在回复中注明数据可能不是最新的。如果所有数据源都不可用，直接告知用户当前无法获取天气，建议用户稍后重试，不要编造数据。

## 踩坑点

- **无差别重试导致雪崩**：早期配置对所有异常都重试（包括 400、403），结果有次 API key 过期后，几秒钟内重试了上千次，对方服务直接把我方 IP 拉黑。务必只对 transient error 重试。
- **缓存与真实数据偏差**：有次在线订单查询失败后使用了库存缓存，结果实际已售罄，导致用户下单时冲突。这类强一致性场景绝不能使用 fallback 缓存。
- **Agent 忽略结构化错误**：光在工具返回协议里定义了 error code，但没有在 prompt 里教 Agent 怎么使用，它还是直接把那串 JSON 贴给用户，反而更困惑。必须在 prompt 里配示例。
- **断路器时间窗口设置不当**：初期断路器打开时间太短（10 秒），对方服务还没恢复又被打，反复开关加剧问题。建议至少 30 秒，配合外部监控告警。

## 可复用建议

- **为每一个 MCP tool 定义 error contract**：工具描述里写明可能返回的错误类型和相应降级行为，Agent 才能做出正确的决策。
- **分级处理**：区分可降级场景（天气、新闻、非关键数据）与不可降级场景（支付、订单提交），后者宁可失败也不要用错误数据。
- **监控与告警**：工具调用失败率、断路器打开次数都应纳入可观测性体系，避免“静默降级”导致业务不正常却无人知晓。
- **在 dev 环境主动注入故障**：用 chaos engineering 思路，模拟各类 API 故障，验证 Agent 的降级路径是否工作，避免生产首次遇到时手忙脚乱。

## 总结

给 AI Agent 接入外部 API 时，错误处理不能是一个事后补的补丁，而应该从一开始就设计成多层防御体系：底层工具做好重试、断路器与缓存，中间层输出结构化错误，Agent 层理解这些错误并执行降级策略。这样即使外部服务动荡，Agent 也能保持基本可用，而不是直接崩溃。工程上代价不高，但对可靠性的提升非常显著。
