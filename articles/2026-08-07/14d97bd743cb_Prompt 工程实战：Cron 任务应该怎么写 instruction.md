# Prompt 工程实战：Cron 任务应该怎么写 instruction

## 背景

在 OpenClaw、Agent 联动 MCP 工具的自动化体系里，越来越多的人开始把定时任务（Cron）挂在 Agent 上。比如：每天早上 9 点汇总昨日的客户反馈、每隔 6 小时检查一次服务健康状态、每周五自动生成周报草稿。

但很快你会发现一件事：**同样的 Agent、同样的工具，人工让它做时结果很漂亮，一变成 Cron 定时触发，输出就开始“发飘”。**

根本原因不是模型变笨了，而是 **Cron 任务的运行上下文和人机对话的上下文完全不同**。人工调用时，我们会带上前置信息、交互式纠正、确认步骤；Cron 执行时，Agent 每次都是“冷启动”，它只能严格依赖你写死在 instruction 里的那条 prompt。

因此，Cron 任务里的 instruction 写作，其实是 Prompt 工程里最考验严谨性的分支之一。

## 问题：为什么 Cron 任务特别容易跑偏？

我观察到的三类高频翻车场景：

1. **幻觉式补全**：因为没有实时对话纠偏，Agent 会“脑补”它觉得合理的数据。比如让它“总结今日客户反馈”，结果时间戳是昨天的，它自己编了几条看起来很真实的评论。
2. **动作重复或遗漏**：没有明确“是否已执行过”的判断逻辑，同一个任务连续两次运行，可能重复发消息，或者第二次直接跳过关键步骤。
3. **输出格式漂移**：一次输出纯文本，一次输出 Markdown 表格，一次突然加了一段情感评论，导致下游自动化流程解析失败。

## 做法：五条铁律式 instruction 结构

针对以上问题，我在多个生产 Agent 上收敛出一套 instruction 写作框架，一共五条硬规则。

### 1. 显式声明“本次是定时任务，禁止补全默认值”

instruction 第一段一定要让 Agent 明白自己的执行身份。不是对话助手，而是无交互、无追问的自动执行器。

> 示例开头：
> “你正在作为自动定时任务运行，没有对话交互能力。如果缺少必要数据，必须明确报告缺失项并中止，而不是假设数值、时间或内容。”

这个声明能显著降低幻觉。

### 2. 固化步骤，每步一个可验证的动作

把任务拆成检查、获取、处理、输出四个阶段，并且每一步都要求输出中间状态（在日志或临时变量中），方便事后排障。

例如一个“每日库存预警”任务：
- 步骤1：调用 `get_current_date` 工具，确认执行日期。
- 步骤2：读取库存数据库（MCP 工具），获取所有 SKU 库存量。
- 步骤3：筛选低于安全库存的 SKU，生成列表。
- 步骤4：将列表按指定格式推送到企业微信群。

每个步骤都 **不允许跳过**，即使 Agent 认为“我可以直接给你结果”。

### 3. 内嵌幂等性判断

Cron 可能出现延迟、重跑。instruction 里必须包含一条：**“先检查今天是否已经成功输出过最终结果，如果存在则直接返回‘已执行’并退出”**。

具体实现可以利用 MCP 提供的文件系统或数据库工具，写一个简单的执行记录文件，例如 `last_run_date.txt`。在步骤1之后立即读取该文件时间戳，判断是否重复执行。

### 4. 严格定义输出协议

不要写“把结果整理出来”，而要给出输出模板，精确到字段和字符：

```
输出格式：
- summary: 一句话总结
- items:
    - sku: string
    - stock: number
    - status: "LOW" | "OUT"
- generated_at: ISO8601 time
```

如果需要在飞书、企微等渠道发送，还要给出消息类型的 JSON schema 示例。这样下游解析才可靠。

### 5. 明确异常处理与降级路径

Cron 任务最大的天敌是“工具调用失败后，Agent 开始即兴发挥”。必须把常见异常的处理逻辑写死：

> “如果调用获取数据工具返回错误或超时，重试一次，间隔 5 秒；若仍然失败，输出错误原因并生成一条告警消息发送到 #oncall 频道，然后中止任务。”

给不出错方案，Agent 就很容易进入自由发散区。

## 踩坑点实录

- **时间假设陷阱**：写“今天”时 Agent 可能做本地时间猜测。一定要让它调用时间工具，不要在 prompt 里依靠自然语言“今天”字眼。
- **工具能力假设**：使用了 MCP 下的某工具，instruction 往往写得看似美好，但实际该工具所需的参数名、结构没对齐，导致工具调用失败后 Agent 自行编造数据。因此写完 instruction 后需要至少用 `dry-run` 模式跑一次。
- **没有考虑 token 截断**：Cron 任务输出如果过长被截断，最后的关闭标签或 JSON 可能不完整，导致解析崩溃。instruction 里最好加上“如果输出超过 2000 字符，优先保留最新数据并裁剪 summary 描述”。

## 可复用建议

1. **把 instruction 做成模板，变量化**：日期范围、收件人、频道名等用 `{{变量}}` 占位，运行时替换，减少手改 prompt 带来的笔误。
2. **用 MCP 工具做执行状态存储**：例如一个轻量的 KV 工具，记录 `last_success_time`、`last_fingerprint`，避免重复执行。
3. **为每个 Cron Agent 建立“测试”指令**：在正式 instruction 不变的情况下，额外维护一条 `dry-run` 指令，把所有推送、写入操作替换成打印日志。先在 sandbox 里跑通，再上生产。
4. **日志里打印原始 instruction 指纹**：方便快速回溯是不是指令被误改导致行为变化。

## 总结

Cron 任务写 instruction，本质上是一个“把离散的人类意图翻译成严格的无状态程序”的过程。它需要你放下对模型“聪明”的期待，回到对流程、边界、异常处理的工程设计上来。

一旦你用这五条铁律把 instruction 工具化，定时 Agent 任务的稳定性会显著提升——而不再是“每天早上开盲盒”。

在 OpenClaw 社区里，很多稳定性问题最后追回来，都落在 instruction 的那几行字上。花一小时打磨，比花一周排障划算得多。
