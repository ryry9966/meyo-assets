# 给 Agent 脚本装个路径护栏：本地目录白名单实现与避坑

上线一个自动化脚本或 Agent 插件时，最常见的心跳时刻不是功能不跑，而是它突然“手滑”写入/删除了不该碰的目录。在 OpenClaw、MCP 这类允许工具动态调用本地资源的环境里，脚本往往拿到的是整台机器的文件系统访问权——用户的文档、配置、甚至授权密钥都裸露在一个写烂了的 `os.remove` 面前。最近的社区讨论里，已经有开发者因为大模型生成的 Python 工具在测试时误清理了 `~/.ssh` 而付出代价。

这当然不是阻止自动化的理由，但提醒我们：给脚本的 I/O 加一道“路径护栏”的成本，远低于事后救火。下面是一个可以在实际工程里落地的做法：通过猴子补丁式的白名单包装，把 Agent 产生的文件操作严格锁死在指定目录内。

## 问题拆解

大多数情况下，Agent 通过 MCP 工具或自定义插件执行的 Python 代码是图灵完备的。你给了它 `write_file` 能力，它就真的能 `open('../.env', 'w')`。即便你在 prompt 里写了“不要访问系统目录”，模型仍然可能被越狱或产生幻觉路径。纯粹靠 prompt 意图约束不可靠，需要在运行时从文件系统 API 层面做强制拦截。

我们想要的护栏特性：

- 只允许在预设的一组目录（如 `/data/workspace`、`./output`）及其子目录内读写。
- 拒绝任何穿透到白名单之外的路径，包括符号链接、相对路径绕过。
- 对 Agent 执行逻辑透明，不改变原有脚本的调用风格（仍然 `open`/`os.remove`），减少改造阻力。
- 在恶意操作发生时提供明确的报错并记录，方便排障。

## 轻量方案：用 `pathlib` 实现路径门禁

最直接的方法是写一个受控的 `SafeFileSystem` 上下文，在执行脚本前全局替换高风险的内置函数。下面是一个针对 Python 的最小实现示例，覆盖了 `open`、`os.remove`、`shutil.rmtree` 等用频最高的操作。

```python
import os
import shutil
import builtins
from pathlib import Path
from functools import wraps

class FileGuard:
    def __init__(self, allowed_paths):
        # 统一解析为绝对路径，规避相对路径和符号链接
        self.allowed = [Path(p).resolve() for p in allowed_paths]

    def _is_safe(self, path):
        real_path = Path(path).resolve()
        return any(real_path.is_relative_to(p) for p in self.allowed)

    def safe_open(self, original_open):
        @wraps(original_open)
        def wrapper(file, mode='r', *args, **kwargs):
            if self._is_safe(file):
                return original_open(file, mode, *args, **kwargs)
            raise PermissionError(f"Access denied: {file}")
        return wrapper

    def safe_remove(self, original_remove):
        @wraps(original_remove)
        def wrapper(path, *args, **kwargs):
            if self._is_safe(path):
                return original_remove(path, *args, **kwargs)
            raise PermissionError(f"Remove denied: {path}")
        return wrapper

    def __enter__(self):
        self._original_open = builtins.open
        self._original_os_remove = os.remove
        self._original_shutil_rmtree = shutil.rmtree

        builtins.open = self.safe_open(self._original_open)
        os.remove = self.safe_remove(self._original_os_remove)
        shutil.rmtree = self.safe_remove(self._original_shutil_rmtree)
        return self

    def __exit__(self, *args):
        builtins.open = self._original_open
        os.remove = self._original_os_remove
        shutil.rmtree = self._original_shutil_rmtree
```

使用时，在 Agent 调用脚本的入口包裹一下即可：

```python
with FileGuard(allowed_paths=["/tmp/agent_jobs", "./data"]):
    result = run_agent_generated_code()   # 内部所有 open/remove 受控
```

## 踩过的坑

1. **`Path.resolve()` 是必须项**  
   初始版本直接用传入字符串比对，结果用户传入 `"./data/../.env"` 这种相对路径就直接绕过了。`resolve()` 会消除 `..` 和符号链接，得到真正的绝对路径。但注意在挂载卷上 `resolve()` 可能耗时，不适合高频路径检查；可以用缓存 `real_path` 应对。

2. **符号链接会制造“合法陷阱”**  
   如果白名单目录 `/app/output` 内的某个子目录是软链指向 `/etc`，恶意或错误的代码可以通过该链接写入系统路径。更严谨的做法是禁用白名单目录下的符号链接，或递归 `resolve()` 每个路径组件，但这会大幅提高复杂度。对于非高安全场景，依赖管理员约束白名单目录自身无链接已经足够。

3. **部分库绕过 `builtins.open`**  
   一些 C 扩展或使用 `io.FileIO` 直接操作的库不会走 `builtins.open`。如果 Agent 加载了这样的第三方包（比如数据库驱动或图像处理库），它们可能直接绕过拦截。缓解办法是进一步 monkey-patch `io.open` 并且对允许的路径扫描 `openat` 等底层调用，但对通用插件来说性价比不高。工程上我会在 `FileGuard` 启动时打一个 warning 日志，提醒开发者在白名单目录里只放可信数据。

4. **Windows 下的盘符和大小写**  
   `is_relative_to()` 在 Python 3.9+ 好用，但在 Windows 上路径有盘符（如 `C:\workspace`）。确保初始化时所有白名单都用同一个大小写形态（如 `resolve()` 后的绝对路径），否则大小写不匹配可能导致误拒。适配多平台时最好加上单元测试覆盖典型路径。

## 可复用的工程建议

- **封装为装饰器或上下文管理器**  
  上面的 `FileGuard` 可以直接集成到 OpenClaw 的自定义工具封装里，例如在你的 MCP 服务器启动时，对每个工具调用包装 `FileGuard`。这样每次 Agent 调用工具，文件系统被隔离在指定目录下，安全边界清晰。
- **配合进程级隔离**  
  如果业务强安全，可以考虑将 Agent 脚本运行在 `subprocess` 子进程中，并用 `chroot` 或平台级的 `Landlock` (Linux)、Apple Sandbox 做双重保护。白名单模式可以作为轻量第一步。
- **日志与告警**  
  在拒绝访问时打印详细日志（原路径、操作类型、调用栈），能帮助快速发现 prompt 设计问题或恶意输入尝试。
- **集成到测试套件**  
  编写一个故意访问白名单外路径的用例，验证护栏抛错，作为回归测试常驻。很多越界问题都是在迭代中“不小心解开”的。

## 总结

给 Agent 文件操作加本地目录白名单，本质上是一次防御性编程的回归。它不追求完美安全（正如不存在完美沙箱），但把风险面从“任意路径可读写”收敛到几个可控目录，这是自动化工程中性价比极高的安全投入。上面的实现不到 50 行代码，可以直接贴在项目里。配合路径解析与运维规范，你可以安心让脚本在本地高速运转，而不用半夜爬起来检查 `.bashrc` 还在不在。
