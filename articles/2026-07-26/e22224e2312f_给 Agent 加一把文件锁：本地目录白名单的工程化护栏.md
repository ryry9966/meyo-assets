## 背景

在 OpenClaw、MCP 工具链或自动化脚本里，Agent 越来越像一个真实的操作者：可以读写文件、执行命令、调用外部 API。一旦赋予它文件访问能力，一个常见的风险就是“失控的读写”——一次幻觉生成的路径就能把系统配置文件覆盖，或者把敏感数据目录压缩后通过邮件发送出去。

成熟的框架通常会在云端沙箱或 Docker 里兜底，但大量自动化场景仍然需要直接操作宿主机的本地文件系统。比如你用 OpenClaw 搭配自定义 MCP server 来处理本机下载目录、整理项目文档、生成静态站点，如果不对文件访问范围做限制，就等同于把一个 `rm -rf` 权限直接交给了一个偶尔会犯糊涂的 LLM。

本文不讨论复杂的沙箱方案，只聚焦一个低成本、可复用的工程实践：**给所有本地文件操作加一个目录白名单**，让 Agent 只被允许在指定目录及其子目录下进行读写。

## 问题拆解

最朴素的想法是“在工具函数的入口处，检查一下传入的路径是不是在白名单里”。但实际落地时需要解决几个细节：

1. 路径规范化：`~/docs/../etc/passwd` 和 `/etc/passwd` 应该被识别为同一个位置。
2. 符号链接穿透：白名单目录下的一个软链接可能指向域外文件，如果不处理，白名单可能被绕过。
3. 相对路径与工作目录：Agent 运行时当前目录不确定，相对路径可能指向意想不到的地方。
4. 并发与缓存：实时解析路径有开销，需要权衡性能与安全。
5. 跨平台兼容：Windows 盘符、路径分隔符、大小写敏感等差异。

目标是把这些问题封装成一个可复用的模块，对外暴露极简的检查接口或装饰器，让后续所有文件工具都可以直接使用。

## 实现步骤

### 1. 定义白名单与校验函数

以 Python 为例，使用 `pathlib` 和 `os.path.realpath` 可以覆盖大部分问题：

```python
import os
from pathlib import Path
from typing import List

class FileGuard:
    def __init__(self, allowed_dirs: List[Path]):
        # 预先解析为绝对路径，去掉末尾分隔符
        self.allowed = [Path(d).resolve().as_posix().rstrip('/') for d in allowed_dirs]

    def is_allowed(self, target: Path) -> bool:
        # 解析真实路径，消除 .. 与符号链接
        real = target.resolve()
        # 目录需要特殊处理：如果目标是目录且尚未存在，resolve 会保持原样，
        # 此时可以先用 parent 解析再还原，或者单独处理存在性。
        # 为安全起见，这里要求目标已存在时才允许操作。
        if not real.exists():
            # 对不存在的路径，可以基于 parent 做检查，防止预创建攻击
            real_parent = real.parent.resolve()
            # 检查父目录是否在白名单的子目录内
            return any(
                real_parent.as_posix().startswith(ad) for ad in self.allowed
            )
        # 对于已存在文件/目录，直接判断前缀
        return any(real.as_posix().startswith(ad) for ad in self.allowed)
```

要点：用 `resolve()` 同时解决相对路径、`..`、符号链接，并统一为 POSIX 风格路径做前缀匹配。对于尚不存在的路径（例如写一个新文件），限制其父目录必须在白名单内，避免通过创建新文件跳出边界。

### 2. 包装 MCP 工具

在 OpenClaw 的自定义工具或 MCP server 里，把 FileGuard 内嵌到每个文件相关工具的实现中。以删除文件工具为例：

```python
from mcp.server.fastmcp import FastMCP
from pathlib import Path
import os

mcp = FastMCP("safe-fs")
guard = FileGuard([Path("/home/user/safe_workspace")])

@mcp.tool()
def delete_file(path: str) -> str:
    target = Path(path).expanduser()
    if not guard.is_allowed(target):
        return "拒绝访问：路径不在白名单范围内"
    # 执行实际删除
    target.unlink()
    return f"已删除 {target}"
```

同样的包装可以作用在 `read_file`、`write_file`、`list_directory` 等工具上。如果工具数量多，可以写一个装饰器统一处理。

### 3. 对存量脚本的“无痛接入”

如果不是从零开始，而是在已有的自动化脚本上加护栏，可以考虑两种方式：

- **猴子补丁**：在脚本入口处动态替换 `open`、`os.remove` 等内置函数，加入目录检查。
- **路径代理**：要求脚本只通过一个统一的“文件管理器”对象存取文件，底层实现封装白名单逻辑。

建议优先走统一管理器路线，因为猴子补丁容易遗漏，而且 `shutil`、`os.system` 等调用方式很难完全拦截。

## 踩坑记录

1. **符号链接穿越**：最容易被忽略的场景。若白名单目录 `/safe` 下存在指向 `/etc` 的软链接，Agent 可以通过 `/safe/link_to_etc/passwd` 读取到域外文件。`Path.resolve()` 会跟随软链接，所以上述 `is_allowed` 能识别并拒绝。但如果业务确实需要保留软链接，需额外做白名单目录内不可创建对外软链接的限制，或在 `resolve()` 后拒绝跨白名单的路径。

2. **`os.path.realpath` 与 Windows 盘符**：Windows 路径可能带盘符，建议统一转换为大写盘符后再做前缀比较。另外 Windows 下 `resolve()` 返回的路径仍是反斜杠，也要显式转换为正斜杠再比较。

3. **性能开销**：每次文件操作都调用 `resolve()` 可能带来轻微 I/O 开销，并发高时可用 LRU 缓存解析结果，但注意缓存失效问题（目录重命名）。

4. **父目录权限控制**：对还不存在的路径，只靠 `parent.resolve()` 检查仍有可能被绕过，例如创建深层目录树时，中间路径可能还未创建。安全要求较高的场景，可以在创建目录时逐级检查，或者要求先手工建立白名单下的顶层目录。

5. **传入参数为字符串时的疏忽**：务必在检查前调用 `expanduser()` 解析 `~`，否则 `~/.ssh/id_rsa` 这样的路径可能绕过检查。

## 可复用建议

- **抽离为独立模块**：把 FileGuard 做成单独的 `file_guard.py`，与业务逻辑解耦，方便跨项目复用，也可以打包成内部 PyPI 包。
- **配合日志告警**：每次拦截都输出结构化日志（时间、调用工具、请求路径、真实解析路径），方便后续审计，也便于发现 Agent 的异常行为模式。
- **分层白名单**：除了全局白名单，可以按工具类型（读、写、删除）分别定义不同的允许目录，进一步收紧权限。
- **动态配置**：白名单目录可以从环境变量或配置文件读取，避免硬编码，在容器化部署时也可以通过挂载卷来灵活调整。
- **测试用例**：编写针对边界情况的单元测试，覆盖软链接、`../`、不存在路径、绝对/相对路径、带空格和特殊字符的情况，确保更新时不会退化。

## 总结

给 Agent 加文件访问护栏并不是一个高深的安全课题，但在日常工作流中却能有效避免低级但破坏力极强的错误。相比市面上庞杂的权限系统，一个集中实现的本地目录白名单更轻量、更可控，特别适合个人或小团队的自动化需求。

只要做到路径规范化、符号链接处理、对不存在路径的父目录校验这三件事，就能挡住绝大多数因为 prompt 失控或模型幻觉导致的文件越权操作。剩下的，就是在每个新增工具里把这道“检查点”变成肌肉记忆。

文件操作是 Agent 的双手，白名单就是给这双手戴上的工程手套——不影响干活，却能防止不小心碰到不该碰的东西。
