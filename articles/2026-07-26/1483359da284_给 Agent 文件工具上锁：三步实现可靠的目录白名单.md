## 背景

在自动化实践中，Agent 经常需要在本地文件系统上执行读写操作：生成报表、处理日志、修改配置文件等。如果直接把文件系统能力暴露给 Agent（无论是 MCP 工具、插件的 subprocess 调用还是内嵌脚本），都会面临一个核心风险：Agent 被 prompt 注入或自身行为失控时，可能访问甚至覆盖敏感路径（如 `~/.ssh`、`/etc/passwd`、源码仓库外的关键配置）。

把 Agent 关进“文件沙盒”是工程化落地的第一步。本文不引入重量级容器方案，而是用一层轻量路径白名单，在工具调用层面拦截非法访问。以下方案以 Python 环境为例，但思路同样适用于 Node.js 等其他 MCP/插件运行时。

## 问题定义

假设我们为 Agent 实现了一个文件读取工具 `read_file`，接受参数 `filepath: str`。工具的逻辑原本是：

```python
def read_file(filepath: str) -> str:
    with open(filepath, "r") as f:
        return f.read()
```

这种实现下，Agent 可以传入 `/etc/hosts`、`../../.env` 等任意路径。我们需要把它改造为只在白名单目录内生效的版本。白名单定义为 `ALLOWED_BASE_DIRS = ["/workspace/project", "/workspace/shared_data"]`，且经过路径解析后，最终访问的真实路径必须位于其中一个基础目录之下。

## 实现步骤

### 1. 路径规范化与校验函数

路径检查不能只做字符串前缀匹配，必须解决三类问题：相对路径、符号链接、路径遍历字符（`..`）。

```python
import os

ALLOWED_BASE_DIRS = [
    os.path.realpath("/workspace/project"),
    os.path.realpath("/workspace/shared_data"),
]

def is_path_allowed(user_path: str) -> bool:
    # 将用户输入结合当前工作目录解析为绝对路径，并消除符号链接
    real = os.path.realpath(user_path)
    for base in ALLOWED_BASE_DIRS:
        # 保证不会通过类似 /workspace/project_evil 这样的前缀绕过
        if real == base or real.startswith(base + os.sep):
            return True
    return False
```

关键点：
- 使用 `os.path.realpath` 同时做了绝对路径转换和 symlink 解析，防止 Agent 通过软链接跳出白名单。
- 比较时加上 `os.sep` 避免前缀误匹配（如 `/workspace/project-a` 与 `/workspace/project`）。

### 2. 改造工具函数，加入访问控制

在工具入口处调用校验，拒绝访问时抛出明确异常并记录日志：

```python
def read_file(filepath: str) -> str:
    if not is_path_allowed(filepath):
        raise PermissionError(f"Access denied: {filepath}")
    with open(filepath, "r") as f:
        return f.read()
```

对于复杂工具（如批量文件操作、通配符展开），应在每个实际访问的路径上分别校验。例如 `glob` 结果中遍历时逐个检查。

### 3. 处理 TOCTOU 竞态窗口

上述实现中校验与打开文件之间存在时间差。攻击者可能在校验通过后、`open` 之前修改符号链接的目标。更安全的做法是基于文件描述符检查已打开的文件，但在脚本工具场景下成本较高。工程折中方案：**在 `open` 后立即获取真实路径再次对比**，不过这也可能引入 TOCTOU 延迟。对于中等威胁模型，采用实时校验 + 缩短校验-使用窗口通常可接受。如果运行环境有高安全要求，建议直接用操作系统级沙盒（如 `firejail`、`bubblewrap`）引入内核强制隔离，但本文重点放在应用层轻量护栏。

## 踩坑记录

- **`normpath` 不等于 `realpath`**  
  见过有人用 `os.path.normpath` 拼接后直接判断前缀，这只能消除 `..` 和重复斜杠，无法解决 symlink 逃逸。务必用 `realpath`。
- **路径大小写问题**  
  在 macOS/Windows 上文件系统可能不区分大小写，靠前缀匹配容易出问题。建议统一用 `realpath` 后再小写比较（若 FS 不区分大小写，`realpath` 通常会返回实际路径名，可再调用 `.lower()` 做标准化）。
- **白名单配置硬编码**  
  环境切换（开发/生产）时白名单路径不同，将 `ALLOWED_BASE_DIRS` 通过环境变量 `AGENT_ALLOWED_DIRS` 注入，用逗号分隔，启动时解析，便于运维配置。
- **通配符展开绕过**  
  如果工具接受如 `*.txt` 并内部调用 `glob`，那么攻击者可能通过精心构造的目录 + symlink 使 glob 结果包含白名单外文件。建议对 glob 结果的每一项单独校验。

## 可复用建议

1. **将校验函数抽成公共装饰器或中间件**  
   对于 MCP 工具，封装一个 `@require_path_whitelist` 装饰器，统一处理路径参数校验，减少重复代码。
2. **记录所有拦截事件**  
   被拒绝的访问应记录日志（时间、请求路径、解析后路径、调用堆栈），便于发现异常行为或错误配置。
3. **配合 Agent 身份区分目录范围**  
   如果有多个 Agent 实例或租户，可以在白名单逻辑中加入 `agent_id` -> 基础目录的映射，实现更细粒度的隔离。
4. **定期审计目录范围**  
   随着项目演进，白名单目录内部可能产生新的符号链接或挂载点，要定期检查是否存在逃逸可能。

## 总结

目录白名单是一种低成本、易实施的 Agent 文件访问护栏。通过合理的路径规范化（`realpath`）和前缀匹配，能有效阻断多数利用路径特性的越权访问。它无法替代内核级沙盒，但作为第一道防线，足以应对日常自动化场景中的误操作和低强度注入风险。将这一机制作为 Agent 文件工具的开发模板，能够在不显著增加复杂度的前提下，把安全基线抬高一个台阶。
