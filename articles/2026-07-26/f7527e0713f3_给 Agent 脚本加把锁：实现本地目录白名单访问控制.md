## 背景：当自动化脚本拿到了你的文件系统

OpenClaw 社区里越来越多的 Agent 开始通过 MCP、自定义插件或简单的 Python 脚本直接与本地文件系统交互。不管是自动整理项目文档、批量处理数据，还是执行 CI 任务，我们很容易在 prompt 里随手写一句：“把生成的文件放到 `/tmp/output` 里”。但一旦 Agent 开始自己拼接路径、执行 shell 命令，风险就来了——一个笔误可能删掉 `/etc` 下的配置文件，或者把私钥文件发到了错误的目标。

常见的保护姿势是“手工审批每次文件操作”，但在频繁迭代的自动化工作流里，这会让 Agent 变得笨重。另一种误区是认为“跑在容器里就安全了”，可很多开发环境为了便利，直接把宿主机代码仓库挂进了容器，Agent 实际上拥有相当高的写入权限。我们需要一层轻量的**文件访问护栏**，在不牺牲效率的前提下，圈定 Agent 可以触碰的目录。

## 问题拆解：真正的威胁不是 `rm -rf`

表面上看，危险指令是 `rm -rf /`，但实际上更隐蔽的风险来自：

- 路径遍历：`../../etc/passwd` 逃逸出预设工作区。
- 符号链接绕路：用户或进程在白名单目录内创建一个指向 `/home/user/.ssh` 的软链，Agent 顺着链访问了敏感文件。
- 相对路径与 `cwd` 漂移：Agent 在执行中途 `cd` 到了其他目录，之后使用的相对路径完全偏移。

护栏的核心目标不是去猜测 Agent 的意图，而是**在执行任何文件 I/O 前，将最终要访问的绝对路径纳入白名单校验**。

## 实现步骤：用 MCP server 封装安全文件操作

OpenClaw 的 MCP 机制可以注册自定义工具，我们以此为例（插件和纯脚本同理），把文件读写包装成白名单受限的工具。

### 1. 定义白名单配置

用一个简单的 JSON 或环境变量指定允许的目录列表：

```json
{
  "allowed_dirs": [
    "/workspace/project/data",
    "/workspace/project/output"
  ]
}
```

建议使用绝对路径，并在初始化时解析好，避免每处理一次路径都做重复计算。

### 2. 实现路径规范化函数

任何传入的路径都要过一遍“安检”，核心函数示例（Python）：

```python
import os

def normalize_path(user_path: str, cwd: str = "/") -> str:
    # 转成绝对路径（相对路径基于可信的基目录）
    if not os.path.isabs(user_path):
        user_path = os.path.join(cwd, user_path)
    # 解析所有符号链接和 "../"
    real_path = os.path.realpath(user_path)
    return real_path
```

这里 `cwd` 应该由服务器内部维护一个安全的工作目录（比如白名单中的某个固定位置），而**不能从 Agent 上下文动态获取**，否则仍可能被污染。

### 3. 安全检查与工具封装

```python
def is_allowed(real_path: str, allowed_dirs: list) -> bool:
    return any(real_path.startswith(d) for d in allowed_dirs)

def safe_read_file(path: str) -> str:
    real_path = normalize_path(path)
    if not is_allowed(real_path, allowed_dirs):
        raise PermissionError(f"Access denied: {real_path}")
    with open(real_path, "r") as f:
        return f.read()
```

同样的逻辑包装给写操作、删除、重命名等函数，然后注册为 MCP server 的工具。**在系统 prompt 里明确告诉 Agent：只能使用 `safe_read_file`、`safe_write_file` 等工具进行文件操作，禁止直接调用 shell 命令执行 `cat`、`echo` 等。**

这样做等于在文件系统调用前加了一层应用层审计，比事后检查日志要可靠得多。

### 4. 应对必须调用 shell 的场景

有些自动化脚本确实需要调用外部工具（如 `ffmpeg`、`git`），这些工具以文件参数形式接收路径。这时单纯的函数封装不够，需要“命令参数过滤”。一个折中的办法是：在执行 `subprocess.run` 之前，先扫描命令行参数中所有可能指向文件的字符串，依次用规范化和白名单检查。实现可借助 Shell 的词法分析，或简单约定“所有文件参数必须使用绝对路径且以 `@` 前缀引用，脚本自动去掉前缀并校验”。虽然不够优雅，但在可控环境中足够有效。

## 踩坑记录

1. **符号链接的 realpath 陷阱**  
   `os.path.realpath` 会彻底解析链接，但如果白名单目录本身是一个符号链接，就会出现“路径前缀不匹配”的问题。建议白名单目录在配置时也执行一次 `realpath`，把标准化后的路径存入列表。

2. **挂载点与多文件系统**  
   在容器化环境里，`/workspace` 可能来自宿主机挂载，`realpath` 解析后会变为 `/mnt/host_data/workspace`，导致与白名单中的 `/workspace` 不一致。请在初始化白名单时统一解析。

3. **并发与工作目录**  
   如果有多个 Agent 进程共用同一个 MCP server，每个请求的工作目录可能不同。需要在请求上下文中维护独立的安全 `cwd`，避免交叉污染。

4. **白名单过宽**  
   不要直接把 `/home/user` 加进去，这样依旧可能泄露 `.ssh`、`.gitconfig` 等。应精确到项目子目录，并考虑排除某些隐藏目录。

## 可复用建议

- **抽象为中间件**：将路径校验逻辑抽成独立模块，MCP、插件、自定义脚本都可以复用。
- **白名单配置化**：用环境变量或配置文件管理，方便在不同环境（本地、CI）切换，不要在代码里硬编码。
- **与 OpenClaw 的 workspace 机制配合**：OpenClaw 支持设定工作区，做好双向限制——workspace 定义逻辑边界，白名单定义文件系统边界。
- **日志与告警**：所有被拒绝的访问尝试都应记录日志，便于发现 Agent 行为异常并优化 prompt。

## 总结

“给 Agent 加目录白名单”听起来像是权限管理的初级课，但实际落地时路径解析、链接遍历、相对目录这些细节才是真正的坑。用 MCP server 封装安全工具，配合规范化的路径检查，可以用不到 100 行代码为自动化脚本打造一个可靠的执行护栏。它不防坏人，但能很好地防止好人代码犯傻。当你的 Agent 能在深夜安全地整理文件时，你会发现这层锁花的时间非常值得。
