## 背景

在 OpenClaw 生态中，插件是连接 Agent 与外部服务的关键桥梁。插件通常会通过配置项携带鉴权信息，例如 `appId`、`appSecret`，再由内置的 HTTP 客户端将请求发往上游 Gateway。很多团队在插件配置里随手将 `appId` 写成 JSON 数字：

```json
{
  "appId": 10023456,
  "appSecret": "abc123"
}
```

这个看似无害的习惯，却可能在下游校验严格或者签名计算依赖字符串类型的场景中，直接触发 Gateway 异常，导致整个 Agent 链路不可用。

本文记录一次真实的排障过程，从现象、定位、修复到可复用建议，帮助 OpenClaw 用户避开这类“静默的类型陷阱”。

## 问题现象

最近一个 Agent 插件在调用下游内部网关时，持续返回 `401 Unauthorized`，但 `appSecret` 校验无误。同一套凭证在 Postman 中用字符串格式传 `appId` 却正常 200。插件的请求日志里只看到返回体 `{"code":"SIGN_ERROR","message":"signature mismatch"}`，网关侧也没有输出更细的错误。

初步怀疑签名算法有问题，但排查后发现签名逻辑正确，加签时的 `appId` 被当作字符串处理，那问题就出在传出去的值上。

## 做法/步骤

### 1. 抓取实际请求体

OpenClaw 插件默认不打印完整请求体，为了排查，我临时在插件的 `onRequest` 钩子里增加一行：

```ts
console.log('outgoing body:', JSON.stringify(requestBody));
```

从日志里看到类似：

```
{"appId":10023456,"timestamp":1711360000,"sign":"A1B2C3..."}
```

注意 `appId` 没有引号，它在 JSON 序列化时是数字，网关接收后解析出的 `appId` 也还是数字。

### 2. 对比 Postman 正常请求

Postman 中我输入的是 `appId` 字符串 `"10023456"`，实际 Body：

```json
{"appId":"10023456","timestamp":1711360000,"sign":"XYZ..."}
```

差异明显：数字 vs 字符串。网关侧签名算法是在字符串类型基础上做拼接、编码和哈希的。数字类型在 JSON 反序列化后参与拼接时，会先被转成字符串，但如果中间涉及前导零截断、或者网关使用的语言对数字默认序列化行为不同，签名结果就会偏差。

### 3. 确认网关校验逻辑

和网关维护者沟通后，确认其签名逻辑伪代码：

```
raw = appId + timestamp + secret
sign = md5(raw)
```

如果 `appId` 是数字，拼接时会被语言自动转换为 `"1.0023456e7"`（科学计数法）或直接丢失精度，导致 `md5` 结果对不上。需强制保持字符串类型。

## 踩坑点

- **前导零丢失**：如果 `appId` 以 0 开头，比如 `01023456`，JSON 数字会变成 `1023456`，签名直接作废。  
- **科学计数法**：部分编程语言处理大整数时，会把 `100234567890123` 序列化为 `1.00234567890123e14`，网关拼接时就会变成意外字符串。  
- **隐式转换**：开发者可能以为网关会“智能”容忍数字，实际往往不会，尤其在严格匹配签名的场景中，类型不一致是硬伤。
- **日志不全**：网关只返回“签名错误”而不打印收到的原始值，导致定位花了一定时间。建议在插件侧就完成请求体日志输出。

## 可复用建议

1. **始终用字符串定义 ID 类字段**  
   所有 `appId`、`clientId`、`userId` 这类业务标识，在 JSON 配置里统一写成字符串。虽然 OpenClaw 配置允许数字，但下游接口几乎总是按字符串设计。

2. **插件配置增加校验**  
   可以编写简单的 JSON Schema 校验插件配置，对关键字段强制 `"type": "string"`。OpenClaw 的插件模板支持自定义校验函数，在加载配置时提前拦截。

3. **统一签名工具函数**  
   如果多个插件都需要与 Gateway 交互，最好封装一层签名工具，内部显式将所有参数 `toString()`，避免数字误传。例如：

   ```ts
   function buildSign(appId: string, timestamp: number, secret: string) {
     return md5(appId + timestamp + secret);
   }
   ```

   `appId` 参数类型限定为 `string`，编译期就能防止数字传入。

4. **请求日志规范**  
   在插件开发规范里，要求 debug 模式下打印完整请求体（脱敏后），便于快速对比正常请求差异。

5. **验收用例覆盖**  
   在插件接入验收时，除了正常流程，增加一个数字类型 `appId` 的异常用例，确保能返回明确的类型错误而不是透传签名异常。

## 总结

一个 `appId` 的类型差异，表面看是 JSON 序列化的细节，但在 Agent 自动化链路中，足以引发签名错误、网关拦截，甚至导致整个 OpenClaw 任务延迟。处理这类问题的关键不是亡羊补牢，而是从源头强制字符串类型、增加防呆校验、并把排查所需的日志提前埋好。工程上成熟的系统，总是靠“约定优于配置”和“尽早暴露错误”来降低排障成本，而不是祈祷下游永远兼容。
