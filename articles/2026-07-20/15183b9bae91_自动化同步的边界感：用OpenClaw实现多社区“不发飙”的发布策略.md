## 背景：一次同步引发的“社交死亡”

把一篇技术文章同时推到 Twitter、Discord、Telegram、Slack、飞书群、多个 Reddit 子版块——这件事听起来效率很高，但如果你真的只用一条 MCP 指令无脑群发，大概率会收到“你是不是被盗号了”的私信。

自动化发布的核心矛盾在于：**平台希望你活跃，但社区希望你克制**。尤其是当你同时维护着开发者社区、用户群、公告频道和个人的社交账号时，同样的内容在不同语境下意味着完全不同的打扰程度。

在实际操作 OpenClaw 做多社区同步时，我发现问题并不在于能不能发，而在于**没有设置发布节奏和内容变体的边界**。下面我会结合 Agent + MCP + 本地调度器的实践，梳理一套可复用的“防刷屏”同步策略。

## 问题拆解：刷屏到底怎么发生的？

自动化引起的刷屏通常有三种情况：

1. **同质内容短时间跨平台轰炸**：推文、Discord 消息、TG 频道几乎同时出现一字不差的文本，关注你的人会在不同客户端收到重复信息流。
2. **忽略平台上下文**：在代码仓库的 Discussion 里发了带 emoji 的营销文案，或者在即时通讯群发了长篇大论。
3. **触发平台的速率限制与风控**：短时间内 API 调用过频导致限流、折叠甚至临时封禁，反而降低了实际触达。

我们的目标不是不发，而是做到：**一次创作，按需变体，分时分频分发**。

## 做法：构建一个带“节奏感”的发布 Agent

我使用 OpenClaw 搭建了一个发布 Agent，流程如下：

### 1. 定义内容源与变体规则

首先，不直接群发原始正文，而是让 Agent 基于同一份结构化内容（标题、摘要、链接、标签）生成三种变体：

- **即时通讯版本**：2-3 句简短消息，带一个明确的价值点，适合群聊、Telegram、Discord。
- **社交平台版本**：1-2 段导语 + 关键结论 + 链接，适合 Twitter、Mastodon、Bluesky（字符限制需考虑）。
- **论坛/社区版本**：完整摘要 + 你的思考背景 + 讨论引导，适合 Reddit、Discord 论坛频道、GitHub Discussion。

我给 Agent 的 System Prompt 中明确了每个变体的风格约束，并禁止在所有版本中使用夸张语气词。

```yaml
# MCP 配置示例（消息转换工具链）
tools:
  - name: content_variant_generator
    description: 根据目标平台生成不同的消息变体
    parameters:
      template_type: ["instant_msg", "social_post", "forum_thread"]
      max_length: [200, 500, 1500]
      tone: "technical, understated"
```

### 2. 构建分时调度队列

所有发布任务不是一次性执行，而是推入一个本地调度堆栈，由 Agent 根据平台设定的“冷静窗口”依次放出。我使用了一个简单的 JSON 任务队列 + cron 触发：

```json
[
  {"platform": "telegram_channel", "delay_min": 0, "variant": "instant_msg"},
  {"platform": "twitter", "delay_min": 15, "variant": "social_post"},
  {"platform": "discord_forum", "delay_min": 60, "variant": "forum_thread"},
  {"platform": "reddit", "delay_min": 120, "variant": "forum_thread"}
]
```

每一次发布完成后，Agent 会记录时间戳，下一个任务仅在当前时间 > 上次发布时间 + delay_min 后才允许执行。这样即便多个平台并行配置，也不会在 5 分钟内把同一个人的信息流刷屏。

### 3. 平台级去重与频率保护

通过 MCP 连接器拉取各平台的最近 10 条消息（如果 API 允许），在发布前做一次相似度检查。如果发现过去 12 小时内已经发过标题高度相似的内容，Agent 会主动跳过，并写入日志“Skipped due to dedup”。

同时设置硬性频率上限：同一平台内，每小时最多 1 条原创广播；每 3 小时最多 1 条带链接的推广消息。这些阈值写在 Agent 的约束文件里，不会因为手动操作而被绕过。

## 我踩过的坑

1. **Telegram 的 markdown 转义地狱**  
   在即时通讯版本中，`_`、`*` 、 `` ` `` 等符号在不同客户端 escape 行为不一致。最终放弃 Markdown 模式，全部用纯文本 + 换行来分隔信息，大幅减少格式异常。

2. **不同 Discord 服务器的权限模型**  
   MCP Bot 在多个 Discord 服务器间切换时，很容易因为缺少 `Send Messages` 或 `Use External Emojis` 权限静默失败。建议在每条发布任务前先做权限校验，失败时降级为发送私信提醒给管理员而非直接放弃。

3. **Reddit 的自我推广判定**  
   即使内容完全原创，如果短时间内跨多个 subreddit 发布，Reddit 的自动过滤器可能标记为 spam。我的实践是同一内容最多选 2 个相关性最高的 subreddit，且发布时间间隔至少 4 小时，附带一句诚恳的讨论引导，而不是扔下链接就走。

## 可复用建议

- **构建发布指纹**：为每次发布生成 `title_hash`，存入本地 SQLite，去重窗口建议 24 小时，避免误伤正常的连载内容。
- **变体不要只换皮**：如果 Agent 只是同义词替换，社区一眼就能看穿。应该让变体重构信息结构，比如论坛版本增加“为什么写这篇”、“踩了什么坑”等背景。
- **允许手动“刹车”**：在 Agent 的前端暴露一个 `pause_all` 接口，一旦有人反馈刷屏，可以一键暂停所有队列。相信我，这个功能你早晚会用上。
- **优先维护核心社区的体验**：如果你的主要用户集中在 Discord 或飞书群，那里的频率限制应该最严格。宁可放弃某些长尾平台的同步，也不要透支核心读者对你的容忍度。

## 总结

多社区同步自动化的难点从来不是“能不能发出去”，而是以什么样的节奏、口吻和时机出现在不同人群的信息流里。OpenClaw 给了我们细粒度控制 MCP 工具链的能力，但真正的边界感来自你对每个社区“正常交流频率”的感知。

用 Agent 做发布时，我的原则是：**让自动化替你执行繁琐的格式化与排队，但让人类始终掌握“合不合适发”的判断开关**。这样一来，同步行为就不再像一台失控的群发机器，而更像一个懂得分寸的工具人。
