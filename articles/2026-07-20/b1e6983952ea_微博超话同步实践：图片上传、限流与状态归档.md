## 背景

在维护一个定期更新的内容库时，需要将精选内容自动同步到特定微博超话。手工执行「上传图片→编写文案→选择超话→发布」不仅机械，还容易遗漏或超时。我们希望把这一链路交给 Agent，让它按照预设的频率和规则完成同步，同时保留完整的执行记录，便于排查问题。

围绕 OpenClaw 的 Agent 框架，我们构建了一条以「内容源 → 图片上传 → 超话发帖 → 限流退避 → 状态归档」为核心的自动化流水线。下文拆解其中的关键环节和实际遇到的工程问题。

## 问题拆解

一个看似简单的发帖动作，在自动化落地时至少需要解决：

- **图片上传**：微博图片需要先上传到图床获取 `pid`，再作为发帖参数携带。
- **超话发帖**：需要超话标识、正确的参数组装，以及 cookie 会话保持。
- **限流与异常处理**：接口频率限制、敏感内容拦截、cookie 失效等均会导致流程中断。
- **状态归档**：记录哪些内容已经发布，避免重复；同时保存帖子 ID、发布时间、失败原因等元数据，形成可追溯的日志。

如果在 Agent 内硬编码逻辑，任何接口变动或异常都会让维护成本陡增。因此我们在遵循 OpenClaw 插件化思路的基础上，将微博相关动作封装为工具，并通过状态机驱动整个流程。

## 做法与步骤

### 1. 整体架构

定义一个 OpenClaw Agent，通过 cron 式任务触发。Agent 内部按顺序调用：

- 内容读取器：从本地 Markdown 或 API 获取待发内容（含文案与图片路径）。
- 微博图片上传工具：获取 `pid`。
- 超话发帖工具：组合参数，携带 `pid` 和超话 ID 发帖。
- 限流处理与重试逻辑：以指数退避应对频率限制。
- 状态归档器：将结果写入 SQLite。

所有操作都以工具函数的形式暴露，方便通过 MCP（Model Context Protocol）复用或调试。

### 2. 图片上传：获取 `pid`

使用微博的 `picupload.php` 接口，关键点：

- 必须以 `multipart/form-data` 方式上传，图片字段名固定为 `pic1`。
- 需要在请求中携带有效的登录 cookie（一般是 `SUB` 和 `SUBP`）。
- 返回 JSON 中的 `data.pics.pic_1.pid` 即所需标识。

封装后的工具示例（伪代码）：

```python
def upload_image(image_path, cookies):
    url = "https://picupload.weibo.com/interface/pic_upload.php?m=upload&enc=utf-8&app=miniblog&data=1"
    files = {'pic1': open(image_path, 'rb')}
    resp = requests.post(url, files=files, cookies=cookies, timeout=30)
    resp_data = resp.json()
    if resp_data.get('code') == '100000':
        return resp_data['data']['pics']['pic_1']['pid']
    else:
        raise Exception(f"Upload failed: {resp_data}")
```

**踩坑点**：图片长宽过大或格式异常（如 CMYK）可能导致 `code=200` 但仍无 `pid`，需要预先用 Pillow 标准化为 2MB 以内的 RGB JPEG。

### 3. 超话发帖：组参与发布

发帖接口为 `https://weibo.com/aj/mblog/add`，主要参数：

- `text`：文案内容，需进行 URL 编码。
- `pic_id`：上一步获取的 `pid`，多个图片用逗号连接。
- `topic_id`：超话 ID（如 `100808xxxxxxxx`），可通过搜索超话后从 URL 中提取。
- 额外参数如 `isReEdit=false`、`rank=0`、`sync_wb=0`。

此外必须在请求头中携带 `Referer: https://weibo.com` 以及正确的 cookie。

成功后响应中会包含帖子 ID `mid`，用于归档。

### 4. 限流处理

微博对发帖频率有严格的隐性限制。常见现象：

- 返回 `code=100001`，提示「操作太频繁」。
- 返回 `code=100002` 或包含 `msg` 字段说明限制时间。

我们的重试策略如下：

- 捕捉到频繁错误时，根据返回的等待时间或默认策略进行指数退避（如 30s、60s、120s，最多 3 次）。
- 若因 cookie 失效（如返回 `-100`）则抛出不可重试错误，提醒更新凭证。
- 在 Agent 层面设置全局最小间隔（如 90 秒），避免连续触发。

这样既不会因为一次限制就彻底失败，又能防止盲目重试加重封禁风险。

### 5. 状态归档

使用 SQLite 持久化同步状态，表结构要点：

```sql
CREATE TABLE IF NOT EXISTS sync_log (
    content_hash TEXT PRIMARY KEY,
    title TEXT,
    image_pid TEXT,
    post_id TEXT,
    post_url TEXT,
    status TEXT CHECK(status IN ('pending','success','failed','blocked')),
    retries INTEGER DEFAULT 0,
    error_message TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

流程中，发送前检查 `content_hash` 是否已存在 `success` 记录，存在则跳过。发送成功后更新 `post_id` 和 `post_url`；发送失败记录 `error_message` 并增加 `retries`，后续任务可读回重试。

为了保证原子性，更新操作使用事务，避免并发 Agent 任务导致重复发布。

## 踩坑记录

1. **图片上传的 cookie 时效**：如果长期复用同一组 cookie，可能会触发验证或登录失效，建议定期检查并人工刷新，或接入模拟登录流程（需额外的安全考量）。
2. **pic_id 的参数格式**：多个 pid 直接用英文逗号分隔，不能有空格。如果错误使用列表传参，微博会无视图片。
3. **超话 ID 不是数字**：部分超话 ID 较长且包含字母，务必完整保留，否则发帖会落入个人主页而非超话。
4. **敏感内容静默屏蔽**：有时接口返回成功，但帖子实际被屏蔽（仅自己可见）。在归档表增加 `post_url` 并定期人工抽检是必要的。
5. **同步脚本的幂等**：如果同一内容因为重试导致两次发帖，通过 content hash 去重非常关键。建议同时对文案和图片路径进行摘要计算。

## 可复用建议

- **封装为 MCP 工具集**：将图片上传、超话发帖、cookie 校验做成独立工具，供不同 Agent 调用，也方便在 Playground 里直接调试。
- **配置化频率**：通过环境变量或配置文件设置发帖间隔、最大重试次数、超话列表等，避免硬编码。
- **日志与告警**：在归档失败时，通过 Agent 的通知能力（如 Webhook）发送告警，提醒人工介入。
- **状态可视化**：基于 SQLite 日志简单搭建一个仪表盘，或导出 CSV 定期复盘失败原因。

## 总结

通过 OpenClaw Agent 串联微博超话发帖的全流程，我们把原本散落的操作收敛为一条可控的工程管线。图片上传的细节、限流的非线性重试、以及状态归档的防呆设计，这些看似边角的工程点，正是自动化可靠性的基石。

后续可以继续延伸，例如接入更多的内容源（RSS、Notion 数据库）或多平台同步。如果你在构建类似的 Agent 管道，希望上面的拆解能帮你少踩一些坑。
