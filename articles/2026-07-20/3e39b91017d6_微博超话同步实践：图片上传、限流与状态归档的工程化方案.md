## 背景

有一个内容分发自动化需求：当主站发布新文章后，需要将摘要、图片和链接同步至特定微博超话。最初想法是通过 OpenClaw 编排 Agent，调用微博开放接口完成发帖。但很快发现，微博超话发帖并非标准开放能力，开放平台主要面向应用内分享，对超话发帖的支持相当模糊，而且实际执行中更容易触发反爬和图片审核。于是我们将目标调整为：在最小风险下完成稳定同步，做到可观测、可重试、可归档。

本文的场景基于以下选型：

- 编排平台：OpenClaw（用于调度、状态管理）
- 执行载体：Playwright 驱动的 Headless 浏览器（封装为 MCP 工具）
- 存储：本地 SQLite 用于同步状态归档
- 图片处理：前置压缩与格式转换
- 通知：失败时通过 webhook 发送告警

## 问题拆解

看似简单的“发一条超话帖子”背后有三个难点：

1. **图片上传链路**：微博超话的图片上传不同于普通微博，需要先获取超话专属的 `pic_id` 并通过特定域上传，且对图片内容有隐形审核，直接传原图可能被静默丢弃。
2. **限流与风控**：短时间内重复发帖或频繁登录会触发验证码甚至临时封禁，超话页面还会根据行为频率限制操作。
3. **状态归档**：异步任务需要记录每条帖子的审核状态（是否成功发送、是否仅自己可见、是否被系统删除），否则运维会陷入“发了没发”的黑洞。

## 做法与步骤

### 1. 图片预处理与上传拆解

从主站媒体资源中获取图片后，不是直接上传，而是先在本地进行标准化：

- 使用 `sharp` 将图片转为 JPEG，质量压缩至 80%，长边不超过 1280px，避免过大或非标准格式触发审核。
- 移除 EXIF 元数据，降低风控注意度。
- 生成唯一文件名：`{md5(content)}.jpg`，便于去重和缓存。

上传采用分段操作，通过 Playwright 拦截网络请求定位真实上传接口。关键步骤：

- 在超话发帖页面，先“模拟选择图片”，监听 XHR 请求，发现实际 POST 地址为 `https://picupload.weibo.com/interface/pic_upload.php`，但需要附带 `mime` `type` 和从页面拾取的 `pic_id` 参数，该参数通过请求 `https://weibo.com/aj/static/pictype.json` 获取。
- 将文件以 `multipart/form-data` 格式 POST，且必须设置 `Referer: https://weibo.com/` 和当前 cookie。
- 上传成功会返回 `pid`，该 `pid` 将用于后续发帖 API。

踩坑点：如果直接使用通用微博图片上传接口，图片会出现但超话帖的图片区域为空。必须使用超话页面内嵌的上传通道。

### 2. 发帖与限流应对

发帖核心是一个复合操作：拼接文本 -> 插入图片 pid -> 提交表单。没有公开 API，只能操纵 DOM 或者直接调用内部 XHR。我们采用后者，定位到发帖请求：

```
POST https://weibo.com/aj/mblog/add?ajwvr=6&__rnd={timestamp}
```

Body 参数中 `text` 为超话标签 + 文案，`pic_id` 为上传得到的 PID，`pub_source` 等字段保持与浏览器一致。

限流表现有两类：

- **频率限流**：返回 `{"code":"100001","msg":"操作频繁"}` 或直接无响应。对此实现了指数退避重试，但最多重试 2 次，避免持续撞墙。
- **内容限流**：图片或文案被判定违规，发帖表面成功但实际只有本人可见。需要事后巡检。

为了降低集体风控，我们在 Agent 内部维护了一个“发帖冷却窗口”——同一账号两次发帖间隔 ≥ 15 分钟，每天最多发 4 条，用 OpenClaw 的状态变量控制。

### 3. 状态归档与可观测性

每次同步任务生成一个 `sync_id`，并在 SQLite 中记录以下状态：

- `PENDING`：预处理完成，等待发帖
- `POSTING`：正在执行上传和发帖
- `SUCCESS`：发帖接口返回成功，并获得 `mid`（帖子 ID）
- `NEED_CHECK`：返回成功但需要进行可见性校验（延迟 5 分钟后用无登录态 curl 访问帖子链接，若返回 404 或提示“暂无查看权限”则标记为 `FAILED`）
- `FAILED`：明确失败或不可见

归档表结构：

```sql
CREATE TABLE IF NOT EXISTS weibo_sync_log (
  sync_id TEXT PRIMARY KEY,
  article_url TEXT,
  weibo_text TEXT,
  image_pid TEXT,
  post_mid TEXT,
  status TEXT,
  retries INTEGER DEFAULT 0,
  created_at TEXT,
  updated_at TEXT
);
```

OpenClaw 工作流在每一步更新状态，最终通过 webhook 发送摘要，非成功条目触发人工介入。

## 踩坑点

1. **图片审核静默失败**：含有二维码、公众号水印的图片，上传和发帖都返回成功，但帖子不可见。解决方案是增加“后期可见性检测”，并禁止醒目水印图片进入同步管线。
2. **Cookie 保鲜**：模拟登录后保存的 cookie 有效期短，且存在 `SUB` 关键 cookie 变更。通过定时健康检查脚本，每天至少刷新一次登录态，发现异常立即告警。
3. **超话 ID 映射不稳定**：不同客户端的超话详情页 URL 规则不一致，部分超话还存在同名不同 ID 的问题。我们通过爬取超话主页的 `oid` 字段来建立稳定映射，并缓存 24 小时。
4. **MCP 工具的超时设计**：一张图片上传可能耗时 8-15 秒，发帖请求阻塞更久，必须在 MCP 工具内设置 30 秒超时和合理的重试逻辑，否则编排流程会卡死。

## 可复用建议

- **将图片预处理独立成函数或 MCP 工具**，对所有发布目标统一应用，减少各渠道适配成本。
- **发送与监控分离**：异步发帖后，务必设计事后巡检机制，而非只靠接口返回确认成功。
- **限流策略配置化**：将发帖间隔、日限额等写成环境变量，方便调整而无需修改代码。
- **归档不止于成功/失败**：中间状态如 `NEED_CHECK` 能大幅减少“假成功”带来的遗漏，值得在所有社媒同步任务中推广。
- **如果场景允许，优先选择官方渠道**：超话同步对账号权重依赖极大，新账号极易被限制，旧账号也不保证稳定。若实在需要自动化，可在非高峰时段低频进行，保持行为的拟人化。

## 总结

微博超话同步不是简单的 API 调用，而是一套包含图片适配、风控对抗和状态审计的工程体系。利用 OpenClaw 的编排能力和 Playwright 驱动的 MCP 工具，我们可以构建可灰度、可重试、可观测的同步管道。当前方案每天稳定同步 2-3 条内容，人工介入率低于 10%，整体可维护性已达到生产级别。下一步计划将超话发帖部分抽象为标准化的 MCP Server，供社区复用。

同步社交媒体这件事情，最值钱的往往不是“能不能发出去”，而是“发出去了你知不知道它到底在不在”。
