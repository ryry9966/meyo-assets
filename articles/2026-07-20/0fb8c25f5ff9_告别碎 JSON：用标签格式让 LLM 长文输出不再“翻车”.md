## 背景

在 OpenClaw 这类 Agent/自动化实践里，让 LLM 输出结构化结果几乎成了刚需——解析摘要、拆分执行步骤、从长文档中提取多段分析，这些都需要下游程序能稳定地消费模型输出。一开始大家会自然选择 JSON，觉得格式严谨、解析器现成。但一旦输出变长，或者内容里夹杂换行、引号、代码块，JSON 就开始频繁“崩坏”：少一个花括号、字符串溢出、非法转义，整个流水线直接报错，Agent 重试成本陡增。

几个月下来，我在多个 MCP 插件和内部流水线中都反复撞上同一个问题：长文场景下维护 JSON 输出正确的工程投入，远大于它带来的便利。后来切换成**自定义标签格式**（类似 XML 的非严格写法），稳定性显著提升，重试次数断崖式下降。这篇文章复盘整个决策过程、具体做法和踩过的坑，给同样在折腾结构化输出的同学一点可迁移的经验。

## 问题：为什么长文 JSON 这么容易坏？

LLM 是逐 token 生成的，长文本中有几个致命点：

- **闭合符号的长距离依赖**：多层嵌套的对象或数组，最后的 `}` 或 `]` 距离起始位置可能几百 token，模型经常提前闭合或忘记闭合。
- **特殊字符转义**：用户输入中包含的引号、反斜杠、HTML 标签，很容易打破 JSON 字符串的边界。
- **内容里“夹带” markdown 代码块**：` ```json ` 包裹的习惯会污染原始输出，即使提示词禁止，也不靠谱。
- **非英语字符和空格**：中英文混排时，JSON 中偶尔出现的全角引号、不可见空格，会让 `json.loads` 直接崩溃。

市面上有 `json_repair` 这类工具，能处理一部分闭合和缺失逗号问题，但对于字符串内部结构被破坏、或存在多个非法 token 的长文修复，成功率并不理想。更关键的是，修复操作本身是黑盒——你不知道修出来的内容语义是否被扭曲，这在严肃的自动化链路里是不可接受的。

## 做法：从 JSON 迁移到标签格式

核心思路是用**人工定义的、容错性高的分隔标记**来代替 JSON 的严格语法树。具体分三层：提示词设计、后处理解析、防御性清洗。

### 1. 设计标签结构

根据任务将输出分成若干**命名块**。例如，需要从长对话里提取总结、情绪标签和执行项，可以设计为：

```
<summary>
...这里放摘要内容...
</summary>
<sentiment>
...这里放情绪标签...
</sentiment>
<actions>
...这里放代办列表，每行一项...
</actions>
```

这样做的好处是：模型只需记住简单的开始/结束标签对，不涉及复杂嵌套，容错空间大。即使某一对未正确闭合，我们仍可按顺序切割，部分失败比整体不可用要好得多。

### 2. 在 Prompt 中固化输出契约

必须用明确的样例教会模型。一个经过打磨的提示词片段（简化后）：

```
请严格使用以下格式回复，不要添加额外的 markdown 代码块：
<summary>
（这里写总结）
</summary>
<sentiment>
positive / neutral / negative
</sentiment>
<actions>
- action 1
- action 2
</actions>
重要：标签名必须完全一致，内容中不要出现 "</summary>" 或 "</actions>" 这样的文字，如果必须出现，请用空格或替换表述。
```

我一般还会加一句：“如果某个块没有内容，请写 ‘N/A’ 但保留标签对”，避免模型省略标签导致解析器撞空。

### 3. 解析器实现（Python 伪代码思路）

解析策略采用**贪婪正则匹配**+**备用切割**：

```python
import re

def parse_tagged_output(text: str) -> dict:
    # 先做基础的清洗：去掉可能包裹的 markdown code fences
    clean = text.strip()
    clean = re.sub(r"^```[^\n]*\n?|```$", "", clean, flags=re.MULTILINE).strip()

    result = {}
    # 逐个匹配我们关心的标签
    for tag in ["summary", "sentiment", "actions"]:
        pattern = rf"<{tag}>\s*(.*?)\s*</{tag}>"
        match = re.search(pattern, clean, re.DOTALL)
        if match:
            result[tag] = match.group(1).strip()
        else:
            # 缺失时记录为空，触发后备处理
            result[tag] = None
    return result
```

若匹配失败，则启动**容错切割**：按 `<tag>` 出现的位置截取内容，直到发现下一个标签的开始或文本结束。即便丢失了闭合标签，至少能抢救大部分内容，而不是全盘丢弃。

### 4. 与 OpenClaw 流水线集成

在 OpenClaw 的 `tool` 或 MCP server 中，把上述解析器封装成独立函数。调用时增加两层保障：

- **自动重试**：解析结果如果有关键字段为 None，就向模型反馈“格式错误，请严格按照模板重试”，最多 2 次。
- **内容安全过滤**：提取的文本用 `html.unescape` 处理（很多模型会额外转义），再用简单的字数/空值校验，防止乱码进入下游数据库。

## 踩坑清单

从两个月的实际使用中，提炼出几个高频坑和应对措施：

1. **模型把标签名写错大小写或加空格**，如 `< Summary >`。  
   **应对**：正则匹配时用 `re.IGNORECASE`，并允许标签前后有一个空格。或者在 prompt 里加入常见错误示范：“不要写成 `<Summary>`，必须是 `<summary>`”。

2. **内容中出现 `</summary>` 字面量**。  
   **应对**：提示词明确禁止，解析器发现多余闭合符号时，采用第一次出现的 `</tag>` 作为结束，舍弃之后的内容并加日志告警。

3. **长内容导致标签跨越 token 边界，模型忘记闭合**。  
   **应对**：如果某个块特别长，可以考虑拆成多个子标签（如 `<action_1>` `</action_1>`），降低记忆负担。

4. **中文全角括号和空格**：`＜summary＞` 这种几乎必然导致正则失效。  
   **应对**：预处理阶段统一将全角符号替换为半角，特别是 `<` `>` `/`。

5. **模型“创作欲”迸发，额外添加解释**，如 “好的，下面是您要求的输出：
   <summary>…”。  
   **应对**：解析前强行剥离所有非标签内容，只保留第一个 `<` 到最后一个 `>` 之间的部分，作为候选文本。

## 可复用建议

如果你正在维护 OpenClaw 插件、MCP 服务或任何需要 LLM 结构化输出的 Agent，可以考虑：

- **将标签解析器独立为标准 tool**，接受 prompt 返回的原始文本，输出字典和解析状态。
- **维护一个“格式模板库”**，针对不同任务预定义标签集，避免每次都重新设计 prompt。
- **建立解析成功率监控**：每次解析记录是否命中完整标签，累计失败率超过阈值时，自动回退到更宽松的流式切割，并通知开发者。
- **不要彻底抛弃 JSON**：如果输出结构高度嵌套且确实是短文本，JSON 仍是最佳选择。但一旦内容长度超过 500 字，优先考虑标签格式。

## 总结

JSON 在短小的 API 响应中无可替代，但在长文、多段落的结构化提取场景下，它强制模型维护高精度的语法树，本质上与语言模型的概率生成特性相矛盾。自定义标签格式放弃了嵌套的能力，却换来了**解析健壮性**和**可恢复性**——哪怕输出破损，你仍能得到部分有效信息，这对生产环境的 Agent 流水线至关重要。

稳定性不是靠护城河式的修复补丁堆出来的，而是选择与模型行为更匹配的数据契约。当你的下一个 OpenClaw 插件因为 JSON 错误频频重试时，不妨试试换成标签，效果可能会让你意外。
