## 背景

如果你用 OpenClaw 搭过自动发帖流水线，大概率遇到过这类场景：Agent 根据热点抓取、模板拼装出一篇 Markdown 贴文，再调生图插件产出一张 cover 图，最后通过发布技能推到平台。一切自动跑通之后，突然有一天你想复用某篇旧文的文案或图片，或者排查某天为什么发了张错图。这时你才意识到——所有产物只是散落在临时文件夹里，文件名是 `output_17.png`、`final_v2.md`，没有任何结构化索引。

这不是架构缺陷，只是缺少一个轻量的本地归档层。

这篇文章记录我在 OpenClaw 自动化流程中加入「本地归档」的实践经验，核心思路很简单：**每篇内容独立存档，用 assets.json 做索引**。面向已经在玩 Agent/插件/MCP 的用户，偏工程落地向。

## 问题拆解

一个标准的自动发帖 pipe 大致长这样：

1. 选题/素材采集 → 2. 文章生成（Markdown） → 3. 配图生成（通常是封面图） → 4. 发布

归档的问题集中在第 2、3 步的产出如何保存、如何组织。具体痛点：

- **产物散落**：文章和图片存放在不同临时目录，甚至内存里就直接发布完事了。
- **引用易断**：文章里的图片引用可能是发布平台返回的 CDN URL，本地根本找不到原图。
- **无元数据**：不知道文章什么时间生成的、用了哪个 Prompt、标签是什么，想搜索只能翻聊天记录。
- **重复覆盖**：同一天跑多次，文件名相同导致旧版本被冲掉。

## 设计方案

### 归档目录结构

我最终采用的目录结构十分朴素：

```
archives/
  2025-04-01-some-post-uuid/
    index.md
    images/
      cover.png
    assets.json
```

说明：
- 目录名：`日期-短slug-短uuid`，确保唯一且可读。
- `index.md`：最终版的 Markdown 正文，图片引用统一使用 `./images/cover.png` 这种相对路径。
- `images/`：该文章关联的所有本地图片。
- `assets.json`：单篇的元信息文件，结构化存储标题、生成时间、标签、来源、发布状态等。

### assets.json 结构

每篇文章的 `assets.json` 示例：

```json
{
  "id": "2025-04-01-some-post-a1b2c3",
  "title": "自动发帖流水线本地归档实践",
  "created_at": "2025-04-01T10:30:00Z",
  "tags": ["automation", "openclaw", "agent"],
  "source": "rss-feed-item-42",
  "published": true,
  "publish_urls": {
    "twitter": "https://x.com/...",
    "blog": "https://example.com/..."
  },
  "prompt_version": "v3",
  "images": [
    {
      "file": "images/cover.png",
      "alt": "归档架构示意图",
      "generated_by": "dalle3"
    }
  ]
}
```

你也可以再加 `summary`、`word_count` 等字段，按需扩展。

## 集成到自动流水线的步骤

假设你的自动发帖 pipe 是在 OpenClaw 里通过一系列 Agent 指令或一个 Task 实现的，我直接在 pipe 末尾插入了一个「归档步骤」，大概长这样：

1. **文章生成完成后**，拿到 Markdown 字符串和图片文件路径列表（如果图片是 base64 或远程 URL，先下载到临时目录）。
2. **组装归档目录**：按规则生成目录名，创建目录。
3. **写入 index.md**：将 Markdown 内部图片路径替换成 `./images/xxx` 的相对形式，然后写入。
4. **移动/复制图片**到 `images/` 下，保持原名或重命名为统一的小写短名。
5. **构造 assets.json 并写出**：从流水线上下文里取标题、标签、发布时间等字段填进去。
6. （可选）更新一个顶层的 `assets_index.json` 汇总所有文章，方便全局搜索。

在实际代码层面，我把这些逻辑封装成了一个 MCP Server——就叫它 `archiver`——暴露一个 `save_post` 工具。我的 OpenClaw 任务在最后一步直接调用这个 MCP 工具即可，传入文章内容、图片文件列表、元数据字典。这样做的好处是归档逻辑完全与发布解耦，修改归档规则时不需要动管道其他部分。

## 踩坑记录

1. **图片路径地狱**：生图插件返回的可能是 `file://`、相对路径、甚至 base64 字符串。在归档前一定要归一化，统一转成本地文件，否则 `index.md` 里的引用会错乱。建议在最靠近归档的节点做路径转换，不要污染上游逻辑。

2. **文件名冲突**：同一篇文章如果重新生成，目录名如果只依赖日期和 slug 就会撞车。因此引入了短 UUID（8 位），保证幂等写入但不会覆盖历史版本——其实就是追加，保留每次生成的快照，方便回溯。

3. **并发写入**：当多个流水线同时向同一个 `archives/` 目录写顶层索引文件时，会出现竞争。我的处理是 `archiver` 工具内部对索引文件写操作加文件锁，或者干脆放弃顶层索引，改用 `ls archives/` 遍历来查找，避免中心化瓶颈。

4. **体积膨胀**：如果你每天都生成几十篇文章，每篇带 2MB 的原图，存储压力会渐渐冒头。可以加一个后置脚本定期压缩旧图片或只保留缩略图，assets.json 里记录原图 CID/URL，不做本地全量存储。

## 可复用的建议

- **把归档抽象成独立工具**：不管你是用 MCP Server、普通 Python 脚本还是 Node 插件，只要接口约定为「接收 content + images + meta，返回 archive id」，就能插到任何 Pipe 里。
- **统一相对路径规范**：在所有 Markdown 产出阶段就强制要求图片引用必须是可以本地化的相对路径，这样归档环节几乎零额外处理。可以写个 linter 在发布前置校验。
- **assets.json 别过度设计**：保持字段扁平，避免嵌套数组里的对象过深，否则后期查询费力。优先以单个 archive 目录 + 单个 JSON 文件为最小单位，够用就好。
- **利用 OpenClaw 的 Task Context**：把归档需要的元数据（如 Prompt 版本、触发源）在 Task 上下文中一路传递，最后喂给 archiver，避免事后反查。

## 总结

自动发帖流水线往往重“发”轻“存”，但内容的长期价值恰恰在于可回溯、可复用。一个简单的本地归档方案——以目录为单位、assets.json 为索引——不会拖慢管道，也不会增加多少复杂度，却能在你某天需要找「那篇配图很好看的帖」时，省去翻聊天记录、翻系统日志的绝望。

现在我的 OpenClaw 内容 Pipe 已经全部接入了 `archiver` 工具，所有文章自动留档，偶尔配合一个小的前端页面直接浏览 `archives/` 下的内容，有一种自己搭建 CMS 的快感——但实际只是写了不到 200 行 Python。

工程化的自动化，不是堆工具，而是让每个产出都落袋为安。
