## 背景：结构化输出的陷阱

在 OpenClaw 这类 Agent 框架里，我们经常需要让 LLM 从长篇对话、文档或网页中提取结构化信息，或者生成带明确字段的复杂回复。最直觉的做法是要求模型返回 JSON，比如：

```
{"name": "Alice", "skills": ["Python", "Docker"], "summary": "..."}
```

在理想条件下，如果使用支持函数调用（function calling）或 constrained decoding 的推理后端，JSON 输出基本可靠。但一旦遇到以下场景，坏事就来了：

- 输出**超过 2k tokens** 的长文本，模型开始丢失括号。
- 内容里含有双引号、换行符等需要转义的字符，模型时常“忘记”转义。
- 你用的是不支持严格 JSON 模式的工具链（例如某些本地模型、通过 MCP 桥接的远程服务、或者自定义插件管道）。
- 碰到需要**嵌套列表**或**多段落摘要**的复杂结构，JSON 的层级和逗号让模型很痛苦。

结果就是：解析器频繁抛异常，Agent 工作流中断，你必须写一堆 try-catch 和修复正则，维护成本很高。

## 问题本质：为什么长文 JSON 容易坏？

LLM 是逐 token 生成的，没有“回退修改”能力。JSON 对语法的严格要求（成对的 `{}`、`[]`，末尾不能有逗号，字符串必须转义）与自回归生成的特性天然矛盾。当生成到第 1500 个 token 时，模型很难再“记住”第 3 层嵌套的左花括号是不是已经闭合了。尤其当模型需要在值里输出自然语言长段落时，易混入未转义的引号，直接炸掉整个结构。

我们真正需要的不是一个严格符合 RFC 的 JSON，而是一种**容错性高、边界明确、易于用简单正则可恢复的结构化格式**。

## 方案：转向类似 XML 的标签格式

在实践中，我把要求从「返回 JSON」改成「返回标签包裹的结构」，稳定性有质的提升。例如，原本要求：

```json
{
  "title": "...",
  "author": "...",
  "key_points": ["...", "..."],
  "full_content": "..."
}
```

现在改为：

```
<title>这里是标题</title>
<author>Alice</author>
<key_points>
- 要点一
- 要点二
</key_points>
<full_content>
这里是多段落全文，可以自由包含 "双引号"、换行，
不需要担心转义。
</full_content>
```

### 为什么它更稳？

1. **明确的起始与结束标记**：`<tag>` 和 `</tag>` 比 JSON 的花括号更不容易在长文中被模型“丢掉”。即使模型偶尔漏掉一个闭合标签，正则 `re.findall(r'<tag>(.*?)</tag>', text, re.DOTALL)` 也只会影响该字段，其余字段仍可提取。
2. **内容不需要转义**：标签内部可以原样放置自然语言，双引号、换行、反斜杠都不是问题。
3. **列表可以用 Markdown 列表或逐行分隔**，避免 JSON 数组中逗号缺失引发的解析崩溃。
4. **流式解析友好**：在做 SSE 流式输出时，我们可以按标签边界逐步解析已接收的片段，提前展示部分结果，而 JSON 必须等待整个对象完整才能解析。

## 做法与步骤

### 1. 设计标签 Schema

首先定义清晰、不与内容冲突的标签名。建议用描述性的英文单词或驼峰命名，避免通用词。例如：

```
<ArticleTitle>...</ArticleTitle>
<AuthorName>...</AuthorName>
<KeyPoints>
每行一个要点
</KeyPoints>
<FullBody>
多段正文
</FullBody>
```

并与模型约定：**不要输出任何标签之外的无关文本，所有内容必须包裹在对应标签内**。

### 2. 编写健壮的提取函数

关键点：用正则的**非贪婪匹配**和 `re.DOTALL`，并对缺失字段提供默认值。

```python
import re

def extract_tag(text: str, tag: str) -> str | None:
    pattern = rf'<{tag}>(.*?)</{tag}>'
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1).strip() if match else None
```

对于列表字段，可以约定按行分割：

```python
key_points_raw = extract_tag(text, "KeyPoints")
key_points = [line.strip("- ").strip() for line in key_points_raw.splitlines() if line.strip()] if key_points_raw else []
```

### 3. 在 Agent 提示词中落地

在 OpenClaw 的 Task 或 Prompt 模板里，明确给出格式示例，并强调**不要**输出 JSON。例如：

```
You must output the extracted information strictly using XML-like tags as shown below.
Do not output any other text. Do not use JSON.

<ArticleTitle>The title here</ArticleTitle>
<AuthorName>Name</AuthorName>
<KeyPoints>
- First point
- Second point
</KeyPoints>
<FullBody>
The full content can go here,
across multiple lines, with "quotes" and everything.
</FullBody>
```

如果你的 Agent 使用了 MCP 工具，可以在工具的 description 里也标注接受的输入格式为标签格式，而不是 JSON。

## 踩坑实录

并不是换成标签就万事大吉，几个容易掉进去的坑：

- **内容里出现相同标签**：如果正文里有 `<FullBody>` 字样，会导致正则提前截断。可以要求模型用 `<FullBody><![CDATA[ ... ]]></FullBody>` 包裹，或者改用更生僻的标签（如 `__FULL_BODY__`），但 CDATA 会增加模型出错概率。实践中，我会要求：**不要在内容里使用尖括号，如果必须出现，请用 HTML 实体 `&lt;` 和 `&gt;`**。
- **模型“偷懒”输出 JSON**：即便提示词明确要求标签，某些模型仍可能忍不住输出 JSON。可以在解析前加一个 fallback：先检测是否是有效 JSON，如果是且用户场景允许，直接解析；否则强制按标签提取。同时，将“用标签回复”的要求在 system prompt 中重复多次。
- **不可见字符干扰**：长文有时会带入零宽空格或 BOM，导致 `</tag>` 匹配不上。提取前建议用 `text.encode('utf-8', 'ignore').decode('utf-8')` 清洗。
- **多值字段冲突**：比如要提取多个人名，如果用 `<Person>Alice</Person><Person>Bob</Person>`，正则可能只捕获第一个。需要显式告知模型用 `<Persons>\nAlice\nBob\n</Persons>` 并在代码中按行切分。事先和模型约定好列表表示法。

## 可复用建议

1. **在自己的 OpenClaw 插件或 Action 里抽象一个 `TagBasedParser`**，传入 schema 定义（字段名、标签名、类型、是否多值），统一处理提取和缺省。
2. **对输出做 schema 校验**：提取后检查必填字段是否存在，类型是否合理，如果不符，触发重试机制（例如让 Agent 重新生成）。
3. **与流式消费结合**：在 SSE on_chunk 回调中，用简单的状态机跟踪当前开启的标签，当遇到闭合标签时立即触发部分处理，提升用户体验。
4. **模型选型差别**：经测试，GPT-4 级模型基本能稳定遵循标签指令；部分 7B 开源模型需在 few-shot 示例中给出更多标签格式的样本，并在解码时设置稍高的 repetition_penalty 避免重复输出标签。
5. **渐进迁移**：如果已有的 Agent 链大量使用 JSON 输出，不必一次性全改。可以先用标签格式包裹最易出问题的长文本字段，其他字段继续用 JSON，最后通过一个合并层组装。

## 总结

放弃对“完美 JSON”的执念，转向标签格式，是在长文结构化输出场景下一次低成本、高收益的工程选择。它利用模型对自然标记的天然友好性，大幅减少解析失败率，也让流式处理和多字段提取变得更简单。OpenClaw 社区里的 Agent 构建者、MCP 工具开发者，在遇到频繁的 JSON 解析错误时，不妨尝试这个思路。
