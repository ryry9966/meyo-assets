## 背景
多平台内容分发已经是不少内容团队的标配，微博超话作为垂直兴趣圈的流量入口，能带来额外的曝光。但手动往超话发帖、传图、填话题标签，重复且耗时。在 OpenClaw 这类自动化框架里，我们已经可以把“发微博”抽象成一个定时任务，但真正落到超话场景时，踩坑才刚开始：图片要单独上传，接口签名和参数跟普通发微博不一样，限流返回的不是明确的状态码，出错后没有状态记录就只能蒙眼重试。

这篇文章记录一次真实的微博超话同步实践，聚焦三个核心问题：**图片上传细节、限流规避策略、状态归档设计**。

## 总体流程
1. 从本地内容池取一条待发内容（含文本与本地图片路径）
2. 模拟登录态，获取超话的 `st` 参数
3. 上传图片，拿到 `pid`
4. 调用发帖接口，携带文本、`pid`、`st`，将帖子发布到指定超话
5. 根据响应判断是否触发限流，若触发则退避重试
6. 无论成功还是最终失败，写入状态库归档

整个过程在 OpenClaw 的定时插件中执行，单个同步任务耗时通常在 2–5 秒（不含退避等待）。

## 关键步骤与踩坑点

### 1. 图片上传：必须用 multipart，不走 base64
微博的图片上传接口是：
```
https://picupload.weibo.com/interface/pic_upload.php
```
参数里常见的 `cb`、`mime` 等属于老式跨域 JSONP 的遗留，服务器实际接收时会忽略大部分参数，但表单中的文件必须用 `multipart/form-data` 上传，字段名为 `pic1`。

**踩坑 1：** 如果用了 HTTP 库默认的 `json: true` 或者把图片转成 base64 塞进请求体，会返回 `-200` 或者直接连接重置。正确做法是用 `form-data` 包构建表单，文件作为 `pic1` 流加入。

**踩坑 2：** 必须模拟浏览器头部，否则即使上传成功，返回的 `pid` 也会被服务端标记失效。关键 Header 包括：
- `Referer: https://weibo.com/`
- `User-Agent` 使用较新的 Chrome UA
- `Cookie` 中必须包含非过期的 `SUB` 字段

示例构造（Node.js）：
```js
const form = new FormData();
form.append('pic1', fs.createReadStream(imagePath), { filename: 'upload.jpg' });
const res = await axios.post(UPLOAD_URL, form, { headers: { ...form.getHeaders(), Referer: 'https://weibo.com/', 'User-Agent': ua, Cookie: cookieStr } });
// 返回格式为 <script>parent.xxx({"data":{"pics":{"pic_1":{"pid":"..."}}}})</script>
// 需要正则提取 pid
```

### 2. 发帖到超话：st 参数不能硬编码
发帖接口：
```
https://weibo.com/aj/mblog/add
```
POST 表单参数：
- `text`: 微博正文（会自动解析链接）
- `pic_id`: 上一步取得的 pid
- `topic_id`: 超话 ID（6 位数字，如 `100808xxxxxxxxx`）
- `st`: 超话的临时 token，每次打开超话页面都会变化

**踩坑 3：** 直接从页面拿到 `st` 后，如果期间浏览器访问了其他页面，`st` 会失效。因此必须发帖前实时请求超话页面并提取。正则提取 `"st": "([^"]+)"` 即可，但某些情况下页面结构变化要容错。

**踩坑 4：** 不带 `st` 或传错 `st`，请求会返回 `{"code":"100001","msg":"请稍候"}` 或帖子直接发到了个人主页，而不是超话内。所以每次发帖前需要发出一个 GET 请求获取新 `st`，这会增加约 1 秒耗时，但必要。

### 3. 限流处理：退避与状态机
微博接口的限流没有明显的 HTTP 429，而是返回 `code: "100005"` 或 `msg` 中包含“频率”。当检测到这类响应时，不能立即重试，否则会被临时 ban 更长时间。

**策略：**
- 首次遇到限流等待 30 秒，之后指数退避（30s → 60s → 120s）
- 最多重试 4 次（5 次总计）
- 其他错误（如 `100001` 登录失效、`100100` 内容违规）直接标记失败，不重试

**踩坑 5：** 有时限流返回并不是标准 JSON，而是页面注入的提示 HTML，需要正则匹配 `操作频繁` 等关键字做兜底判断。

### 4. 状态归档：工程的可观测性
在没有归档的情况下，半夜定时任务失败了你根本不知道哪一步挂了，也不可能在重试时跳过已成功的步骤。为此，设计了一个简易的状态机，用 SQLite 记录：
- `pending`: 等待执行
- `uploading` → `uploaded`: 图片上传阶段
- `posted`: 发帖成功
- `rate_limited`: 触发限流，等待重试
- `failed`: 最终失败

每条记录存储 `task_id`、`retry_count`、`last_error`、`step`，OpenClaw 任务结束时可发送通知。这个设计让出问题后能快速定位是图片上传失败还是发帖限流，也避免了重复发帖。

## 可复用建议
- **封装 WeiboClient 类**：将上传图片、获取 st、发帖等方法内聚，对外只暴露 `postToTopic(text, imagePath)`。
- **重试装饰器**：限流退避可以做成一个带状态回调的 async 装饰器，自动根据错误类型判断是否重试。
- **Cookie 保鲜**：在 OpenClaw 环境中单独维护一个 cookie 池，定时检测有效性，失效时可通过简单通知提醒人工更新。
- **检查清单**：每次任务启动前，验证 cookie 是否有效、本地图片是否存在、st 能否正常获取，预先阻断无效任务。
- **状态机抽象**：将每个步骤的状态变化记录到 DB，配合简单的 Web dashboard 查看历史，能极大降低运维心智负担。

## 总结
微博超话的自动化同步看起来简单，但真正工程化后，图片上传的特殊要求、超话 token 的动态性、限流的非标处理，以及状态记录的缺失，都会让定时任务从“偶尔成功”变成“经常翻车”。通过 multipart 上传、实时抓取 st、指数退避重试以及轻量级状态归档，这套逻辑已经在 OpenClaw 中稳定运行了数周，每天自动同步 3 条超话帖，人工介入几乎为零。

如果你的团队也在用 OpenClaw 做微博运营自动化，这些实践可以作为一个起点，后续还可以扩展多超话分发、话题标签提取等能力。关键还是把每个接口的脾气摸透，以及永远不要相信“一次就能成功”的请求。
