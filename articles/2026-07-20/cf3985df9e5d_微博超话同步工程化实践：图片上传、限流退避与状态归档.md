## 背景

在多平台内容分发的自动化链路中，微博超话通常被视作一个“不可靠端点”——接口行为封闭、限流策略隐晦、图片上传稳定性差。但出于社区运营需要，我们又必须将经过审核的长文、图文消息同步到指定超话，并保持发布状态的完整追溯。

围绕 OpenClaw 的 Agent 与插件体系，我们构建了一条相对稳健的同步管道。它不假设微博接口永远可用，而是把每一次同步当作可能失败的异步任务来处理，并用最小成本的归档设计保障可观测性。本文将拆解图片上传、频率控制与状态归档三个关键环节，并给出可复用的 MCP 封装建议。

## 问题拆解

1. **图片上传不稳定**  
   微博移动端上传接口对图片尺寸、格式、EXIF 信息都有隐含要求。直接使用 Pillow 处理的 PNG 经常被拒，返回 `pic_id` 为空或无效。
2. **限流触发点分散**  
   发帖接口、上传接口、超话签到接口各自独立计数，且限流阈值不公开。一旦某个窗口被触发，后续所有请求都会在数分钟内返回 `100005` 或 `20101` 等风控码。
3. **状态丢失难以排查**  
   如果仅依赖 Agent 的运行日志，一旦任务重试或进程重启，很难知道某条内容到底“发没发出去”“卡在哪一步”。运营同事也无法自行查证。

## 做法与步骤

### 1. 图片预处理与多级重传

我们实现了一个轻量图片预处理插件，集成到 OpenClaw 的 `image_processor` hook 中：

- 统一转换为 JPEG，质量 92，去除 EXIF；
- 限制长边 2048 px，文件大小 < 3 MB；
- 上传采用两段式：先调用 `pic_upload` 获取 `pic_id`，然后将 `pic_id` 拼入发帖 body。

针对 `pic_id` 无效的情况，做了**三级回退**：  
`原图 → 重采样缩小 20% → 转 base64 直传（部分旧接口兼容）`。  
多数失败都可在第一次回退中修复。少数持久失败会触发上报告警，暂存待人工介入。

### 2. 全局限流令牌桶 + 用户态退避

微博的限流是**账号级**的，且同账号在同一时刻可能存在多个 OpenClaw 工作流（例如多个 Agent 并发操作不同超话）。我们在插件层实现了一个 Redis 令牌桶：

- 每账号每分钟最多 4 次写操作（发帖/转发/评论），图片上传单独限制为每分钟 6 次；
- 请求前尝试获取令牌，拿不到则延迟队列等待；
- 若仍返回限流错误码，进入**指数退避 + 老化重置**：首次等待 45 秒，第二次 2 分钟，第三次直接挂起任务 15 分钟，并将该账号的所有操作转为“限流冷却”状态，拒绝新任务争用。

令牌桶配置以 MCP 资源形式暴露，允许运维动态调整而不必重新部署插件。

### 3. 轻量状态归档表

我们没有引入繁重的任务调度框架，而是在 OpenClaw 的 SQLite 插件上维护一张 `sync_log`：

```sql
CREATE TABLE sync_log (
    id TEXT PRIMARY KEY,
    content_hash TEXT,
    target_super_topic TEXT,
    status TEXT,          -- pending / image_ok / posted / failed
    retries INTEGER DEFAULT 0,
    last_error TEXT,
    created_at INTEGER,
    updated_at INTEGER
);
```

每个同步流程分为三个状态节点：  
`pending → (上传成功) → image_ok → (发帖成功) → posted`  
任何环节失败都会记录 `last_error` 和 `retries` 增量，并推入延迟重试队列。超过 5 次重试则标记为 `failed`，自动通知运营群。

## 踩坑点

- **图片格式的隐性约束**  
  同一张 JPEG，由 PIL 保存的有时会被拒，而用 `ffmpeg` 重新封装一次就能过。推测与 JPEG 的压缩参数或色彩空间有关。最终方案是统一过一遍 `ffmpeg -i in.jpg -q:v 2 out.jpg`，稳定性显著提升。
- **多超话发帖共享限流窗口**  
  最初是每个超话独立执行流，没有做全局令牌协调，结果一个超话的自动签到直接把发帖额度吃光，导致其他超话连续失败。改造为账号级全局令牌桶后消失。
- **Cookie 时效与二次验证**  
  微博 Cookie 有效期不固定，可能持续数天，也可能在一次异地登录后立即失效。我们增加了 Cookie 有效性预检步骤：每次任务开始前，用“登录状态查询接口”快速验证，若失效则走 Backup Token 自动刷新，刷新失败直接报错退出，避免大量脏数据。
- **状态更新非原子**  
  在高并发重试下，出现过 `image_ok` 状态被覆盖为 `pending` 的竞争。后续使用 SQLite 的 `UPDATE ... WHERE status = 'pending'` 条件写操作保证状态单向演进。

## 可复用建议

1. **封装为 MCP Server**  
   将上述图片上传、发帖、限流、状态查询等能力抽象成一个 MCP Server，暴露 `weibo.sync_post`、`weibo.check_limit`、`weibo.query_log` 等工具。Agent 只需组合调取，不需要关心协议细节。
2. **配置化限流参数**  
   令牌桶容量、退避时间、最大重试次数全部外挂为 JSON 配置，通过 MCP Resource 下发。当微博策略调整时，无需重新构建镜像。
3. **多维度监控**  
   至少监控三类指标：`upload_success_rate`、`post_success_rate`、`account_cooling_down`。当冷却状态超过 30 分钟时，钉钉/webhook 告警。
4. **策略即代码**  
   把退避、回退、Cookie 刷新等逻辑写成独立的策略函数，通过 OpenClaw 的 `policy_chain` 机制组装，便于单元测试。

## 总结

微博超话的自动化同步并非简单的 API 调通，而是一个持续与限制条件妥协的工程问题。通过图片多级回退、账号级令牌桶、状态归档，以及将这套能力封装为 MCP 工具，我们将同步成功率从最初的 82% 提升到 98.5% 以上，同时大幅降低了运营排查成本。对 OpenClaw 用户来说，这层抽象使得发布流程回归到“描述意图—自动执行—可查可修”的 Agent 范式，值得在类似不可靠端点的集成中复用。
