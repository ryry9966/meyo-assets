## 背景

在 OpenClaw 生态中，网关（Gateway）负责将外部请求路由到对应的插件执行。插件注册时需要提供完整的描述信息，其中 `appId` 是核心标识之一。通常我们把它定义成字符串，因为它在 JSON 配置中就是以字符串形式出现。

在一次内部插件接入时，我将配置从 YAML 迁移到代码动态注册，习惯性地把 `appId` 填成了数字类型。结果出现了一个让人困惑的现象：插件能够正常被扫描和注册，但在实际调用时，Gateway 始终返回 **404 Not Found**，日志中也看不到任何下游调用的痕迹。

起初以为是路由没对齐，反复检查路径和版本号都没有结果。最后通过对比可以正常工作的插件配置，才发现是 `appId` 的类型问题。这篇文章还原整个排查与修复过程，并给出一些可复用的工程建议。

## 问题现象

- 插件在启动日志中显示已成功注册，Gateway 也能识别到该插件的存在。
- 使用相同的路由规则调用时，Gateway 返回 404，提示“Plugin Not Found”。
- Gateway 的 debug 日志没有显示任何与下游插件通信的记录，只有路由匹配失败的信息。
- 在 Gateway 的内存存储中，可以用管理 API 列举出所有插件，但唯独缺失了该插件的记录。

## 排查过程

### 1. 确认插件是否注册成功

第一步查看插件自身的健康检查和注册日志。插件进程启动后向 Gateway 发送注册请求，返回 200 OK，并且周期性的心跳也正常。这基本排除了插件端的问题。

### 2. 核对 Gateway 路由规则

检查 Gateway 的路由配置文件，确认 `basePath`、`endpoint` 以及版本号是否与请求一致。使用 `/v1/plugins/{appId}/...` 的调用路径没有问题。

### 3. 用管理 API 查看注册表

这是关键一步。Gateway 暴露了一个内部管理端点 `/admin/plugins`，可以返回当前注册表中的所有插件信息。通过 curl 调用该端点，发现列表里没有我的插件，而其他插件都在。

为何注册成功，却没有出现在注册表里？这指向了 Gateway 在处理注册信息时可能做了过滤或筛选。

### 4. 对比正常插件与异常插件

将两个插件的注册 JSON 体进行 diff，发现唯一结构性的差异是 `appId` 字段的类型：

```json
// 正常插件
{
  "appId": "my-plugin",
  "version": "1.0.0",
  ...
}

// 异常插件
{
  "appId": 10001,
  "version": "1.0.0",
  ...
}
```

我在代码中使用了一个常量 `APP_ID = 10001`，注册时直接将这个整型值放入 JSON 对象中，序列化后 `appId` 变成了数字类型。Gateway 在反序列化时，期望 `appId` 是字符串，但拿到了数字，可能触发了类型断言失败或忽略了该字段，导致插件被部分注册（心跳正常）但无法存入路由表。

### 5. 修复与验证

将常量改为字符串 `APP_ID = "10001"`，重新部署后，管理 API 中立刻出现了该插件，调用也恢复正常。

事后查看 Gateway 的源码（基于 OpenClaw 规范实现），发现其在更新注册表时会执行 `plugin.appId.trim()` 之类的字符串操作。当 `appId` 为数字时，`trim()` 方法不存在，导致异常被静默捕获，插件注册被终止，但没有返回错误给客户端。

## 踩坑点总结

- **JSON 类型敏感，却无严格校验**：Gateway 接受注册时不校验 `appId` 的类型，导致错误在半路才暴露，排查成本很高。
- **数字类型的 JSON 字段，序列化后丢失引号**：在动态语言或弱类型场景下，如果直接用模板拼 JSON，很容易出现类型写死的问题。建议始终使用强类型序列化库（如 Go 的 `json.Marshal`、TypeScript 的 `zod`），并在关键字段上显式定义为 `string`。
- **管理 API 是排障利器**：没有管理 API 提供的全局注册表视图，这次排查会花更长时间。建议所有网关/注册中心都保留这类内部接口。
- **静默失败要不得**：Gateway 在遇到不合规字段时应该记录 warn 日志并返回 4xx 错误，而不是直接忽略。

## 可复用建议

1. **使用类型安全的注册方式**  
   如果使用 SDK 进行插件注册，优先选择强类型的配置结构体，避免手写 JSON 字符串。

2. **增加注册信息校验**  
   在 CI 或部署流水线中，增加一个环节对插件注册 JSON 做 schema 校验，确保 `appId` 为 `string`，且符合命名规范。

3. **完善 Gateway 的可观测性**  
   打开 Gateway 的 debug 日志，并在注册失败时输出明确的错误原因和原始请求体。同时暴露指标（如 `plugin_registration_failures_total`）便于监控报警。

4. **文档中的示例尽量贴近实际情况**  
   OpenClaw 社区文档里对 `appId` 的描述应该强调它始终是一个字符串，即使看起来像数字。给出反面示例有助于开发者避开这个坑。

## 总结

一个微小的类型错误，在松散的接口约定下被放大成功能完全不可用的问题。这提醒我们在构建插件生态时，不仅要关注协议设计，也要在 Go、TypeScript 等强类型语言中严格约束数据模型，同时在 Gateway 层做好容错和提示。故障不可怕，怕的是没有痕迹可查。任何一次成功的排障，都是在反馈机制与可观测性上的一次改进。
