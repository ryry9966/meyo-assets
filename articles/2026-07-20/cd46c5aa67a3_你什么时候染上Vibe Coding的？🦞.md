2025年开年，Andrej Karpathy 随手甩出一个词——Vibe Coding。人们在转发里大笑，然后突然陷入沉默：“等等，我好像早就染上了。” 那种只描述意图、完全交由大模型吐出代码、跑不通就再塞回去的“感觉驱动开发”，正在从梗变成一种真实的编程实践。本文不教你怎么写代码，而是拉开工程学视角，聊聊这种“上头”体验背后的机制、代价，以及怎样健康地 Vibe。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-20/965ea4c9597f28b6.png)

## 究竟什么是 Vibe Coding？

Karpathy 的原话很直白：“完全沉浸在感觉里，拥抱指数，忘记代码的存在。” 这句话拆开，就是当下数千名开发者正在做的事情。

- **工作流重构**：传统的编辑-编译-测试循环（edit-compile-test loop）被替换为“自然语言描述 -> 大模型生成 diff -> 人肉复制粘贴 -> 运行报错就扔回给模型”。
- **心智卸载**：开发者不再逐行阅读实现逻辑，甚至刻意回避阅读代码。Karpathy 自己都承认：“如果报错，我就直接把报错信息丢给模型，最后能跑就行。”
- **技术基座**：这不是凭空出现的。从 GitHub Copilot 到 Cursor、Windsurf，再到 Claude 的 artifact，代码生成模型在 2024-2025 年跨越了“可执行雏形”的门槛，使得“只说不写”成为可能。

Vibe Coding 本质上是一种**意图编程（intent-based programming）**，但更极端——它连“验收”环节也交给了模型。你只提供最终目标的模糊表达，模型负责结构、语法、异常处理。它很像上世纪 80 年代“程序合成”学术领域的梦想，只是今天 LLM 用概率把它变成了日常工具箱。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-20/3520e2cd0ac25b2e.png)

## 为什么我们会上头？

如果你第一次尝试 Vibe Coding 时，内心蹦出“这也太爽了”，那你踩中的不是 bug，是精心设计的人类奖励机制。

- **即时反馈回路的劫持**：用自然语言说一句“给我一个带深色模式的登录页”，30 秒内出现一个可交互的前端，按需继续微调。这种**几十秒粒度的爽感**，比传统开发中“写完函数、跑通单元测试”快了至少一个数量级。大脑的多巴胺系统对这种高频、可预期的正反馈没有抵抗力。
- **认知负荷断崖式下降**：处理命名、类型匹配、异步逻辑、CSS 布局细节，这些曾被程序员视为“理所当然”的微型决策，累积起来消耗大量工作记忆。Vibe Coding 直接外包了所有次级决策，让你进入一种**纯净的心流**——只关心“做什么”，完全无视“怎么做”。
- **创造者门槛归零**：非工程师可以在一小时内用 Vibe Coding 做出一个内部工具。过去需要学 Python/JavaScript 的壁垒，现在只剩“会说话”就行。这让大量产品经理、设计师、创业者直接跨入“可建造”的范围，奇妙的成就感极具传染性。

这种体验背后，是“完成感”前置、困难后置的心理魔术。就像信用卡消费，当前愉悦，账单稍后。

## 魔法失效时，代价是什么？

Vibe Coding 最大的陷阱在于：生成代码的质量分布是一条肥尾曲线。多数时候它能工作，恰好给你足够的安全感；可一旦踩进尾巴，代价往往昂贵。

- **技术债的掩埋速度**：当你不阅读生成代码时，重复的逻辑、循环导入、非必要的数据库查询会被一层层掩埋。它们不致命，但会让系统逐渐变成一碗意大利面。Karpathy 自己调侃：“我做出来的应用只是一碗‘可食用的面条’。” 这种可食用面条在原型阶段无害，但一旦你决定把它真正部署，维护成本会吞噬所有最初省下的时间。
- **能力退化螺旋**：阅读代码和构建心智模型，是程序员保持能力的基本训练。Vibe Coding 把它从日常中抽走，意味着下一次定位故障、解决边缘 case 时，你手上的“调试直觉”已经生锈了。这是一个经典的“自动化悖论”——自动化程度越高，人类操作员在异常面前越脆弱。
- **安全与正确性的黑洞**：LLM 生成的代码中可能包含已知漏洞、过时的库版本，甚至幻觉出的 API。你若不审查，就相当于把应用的安全边界完全交给模型的训练分布。对于涉及用户数据、支付、身份认证的场景，这无异于靠掷骰子运行。

此外，当大模型对某个错误无能为力时，Vibe 开发者会陷入一种罕见的挫败感——你甚至不知道从哪里开始阅读那堆“面条”来修复问题。

## 如何健康地 Vibe？

把 Vibe Coding 妖魔化没有意义，它显然是一个高效的原型工具。问题在于如何为“感觉”套上工程缰绳。

- **分级采用策略**：将代码分为“风控线内”和“风控线外”。原型、内部管理后台、一次性脚本可以尽情 Vibe。生产环境核心逻辑、数据处理流水线、鉴权模块，必须回归传统评审流程，哪怕先用 Vibe 生成初稿，也要逐行通过 code review。
- **建立 AI 时代的代码卫生标准**：至少要求 AI 生成**接口契约（contract）**和**测试用例**。即使你不读实现，也要让模型输出一套针对需求描述的测试，然后跑通它们。这不是信任代码，而是信任测试的监督效果。
- **保留10%的底层阅读**：抽出少量时间，真正阅读模型生成的代码，不是 debugging，而是纯学习。看看它如何处理并发、怎么抽象数据层。这种有意识的阅读能防止“代码盲化”，并为未来可能出现的排障保留一些方向感。

一句话总结：把 Vibe 当喷气背包来快速跃迁想法，但要清楚，喷气背包不能代替走路和开车。

## 三条冷思考

Vibe Coding 不是编程的终点，而是一面镜子，照出我们与代码关系的变迁。在彻底沉浸之前，请记住三件事：

1. **“能跑”不等于“合格”**：原型软件的“能跑”与生产系统的“能跑”之间，隔着部署监控、错误预算、回滚策略、压测数据。别让 Vibe 出来的速度冲昏头脑，误把 demo 当成产品。
2. **审计是最后的防火墙**：哪怕 AI 写了全部代码，人类也必须保留审计权利。未来可能会诞生“Vibe Auditor”角色——专门阅读、评估 AI 生成代码的质量与安全，这个职位的价值只会上升。
3. **基础理论永不贬值**：分布式系统为什么有 CAP 约束？数据库索引为什么是 B+ 树而不是哈希？这些基础知识不会因为代码生成而消失，反而因为 AI 容易写出“表面正确、深处荒谬”的实现而变得更加珍贵。懂底层，才能识别模型什么时候在胡说。

Vibe Coding 染上的时候，你可能正坐在凌晨三点的屏幕前，忽然发现不必再为一个 CSS 居中问题搜索 StackOverflow。那一刻的轻松感真实不虚。但让这份轻松变成可靠的工程能力，需要我们亲手划定边界——用理性驾驭感觉，而不是用感觉替代理性。
