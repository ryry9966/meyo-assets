## 1. 背景与问题

在一些基于 OpenClaw 编排的自动化内容分发流程里，除了同步到主流社交平台，偶尔也需要把图文推送到指定的微博超话。这不是为了蹭热点，而是受限于特定社区运营需求——某些知识类超话依然有稳定的互动受众，可以用 Agent 批量维护。

我们最初尝试用脚本直接调微博开放平台接口，很快遇到三个典型问题：

1. **图片上传不稳定**：带图的微博要先调用 `statuses/upload` 得到 `pic_id`，再携带该 id 发博。上传接口偶尔返回成功，但后续发博时提示图片无效，或者大图被静默丢弃。
2. **限流不透明**：发博接口有用户级和 IP 级频率限制，文档写了次数，实际触发阈值却更低，连续发文很容易被沉默封禁一段时间，连测试流量也会被拦。
3. **同步状态丢失**：脚本跑完不看数据库，重试时无法判断哪些已经发过，导致重复发帖或漏发，手工查日志排查成本极高。

下面整理一套在 OpenClaw 中落地、兼顾图片上传健壮性、限流退避和状态归档的工程化做法。

## 2. 实现步骤

### 2.1 基础接入与 Token 管理

使用微博开放平台的 OAuth2.0 授权，预先手动获取长期 `access_token` 并存放于环境变量或 OpenClaw 的密钥管理模块。由于场景是“本人账号向公开超话发帖”，无需每次弹窗授权，一次拿 token 定期刷新即可。

在 OpenClaw 的 Workflow 中定义一个自定义 Action，内部发起 HTTP 请求时统一携带 `access_token`。为方便排障，把所有请求的 `X-RateLimit-Remaining`、`X-RateLimit-Reset` 头记录到日志。

### 2.2 图片上传：重试 + 尺寸校验

微博的 `statuses/upload` 接口要求图片以 `multipart/form-data` 上传，关键约束：

- 单张图片不超过 **5MB**，否则直接拒绝。
- 支持 `pic` 字段，但官方文档里参数名容易误写为 `media`，必须核对最新文档。
- 上传成功后返回一个 `pic_id`（字符串），后续发博需在 `statuses/update` 中用 `pic_id` 参数传递，而不是直接放图片 URL。

工程上我们这样做：
- 图片生成节点先输出本地文件，OpenClaw 动作里用 `file` 类型读取，计算 size，超过 5MB 自动等比压缩。
- 上传请求设置超时 30 秒，若返回 `error_code` 10006（图片不存在）或网络超时，重试最多 3 次，间隔递增。
- 上传成功后，将 `pic_id` 与本地图片路径配对存入临时字典，避免发博时用错。

### 2.3 发博与超话关联

发博接口 `statuses/update` 需要带上超话标识。实测发现，仅需在 `status` 文本末尾或开头插入超话话题，例如 `#开源工具#`，同时设置 `visible` 参数为 0（公开）即可，不需要额外 `topic` 参数。若超话存在，微博会自动聚合。

为了避免内容被识别为营销导致降权，每条博文会随机变化话题位置，并且不携带外链。

请求示例（伪代码）：
```text
POST https://api.weibo.com/2/statuses/update.json
access_token=xxx&status=今天分享一个排障思路 #OpenClaw实践#&pic_id=abcd1234
```

### 2.4 限流处理：基于响应头的令牌桶

观察多个账号的请求，发现发博接口实际限制大约 **每 15 分钟 24 次**（比文档宣称的略低），同一 IP 下多账号共享阈值。图片上传接口限制更松，但单次上传大图可能被额外限速。

我们的应对：
- 每次发博后解析响应头 `X-RateLimit-Remaining`，当剩余次数 ≤ 2 时，进入冷却状态。
- 冷却逻辑：检测 `X-RateLimit-Reset` 返回的 Unix 时间戳，计算到该时间的差值并加 60 秒缓冲，然后 `sleep`。同时把当前时间戳写入一个本地文件锁，防止并发动作重复计算。
- 发博动作内部用简单令牌桶：每分钟最多发 3 条，无论剩余次数如何，先执行本地速率控制，这样可以将突发流量抹平。

### 2.5 状态归档：以消息摘要为幂等键

同步结果需要一个低成本的状态存储。我们放弃复杂数据库，直接用 **SQLite** 文件保存在 OpenClaw 工作区目录，表结构如下：
```sql
CREATE TABLE sync_log (
    content_hash TEXT PRIMARY KEY,
    status TEXT,        -- pending/success/failed_upload/failed_limit
    pic_id TEXT,
    weibo_id TEXT,      -- 发博成功后返回的 id
    retries INTEGER,
    last_error TEXT,
    created_at INTEGER,
    updated_at INTEGER
);
```
每次准备发博前，计算 `status + 图片路径的 MD5` 作为 `content_hash`（注意图片文件路径比内容更稳定），如果该 hash 已经存在且状态为 `success`，直接跳过。发博失败则递增重试次数并记录错误信息。这样可以避免重启流程后重复发文，也方便统计成功率。

特别要注意**并发生成时避免写锁冲突**：在 OpenClaw 的 Workflow 中，通过一个专门的动作排队，确保对 SQLite 的写入是串行的，或使用 `WAL` 模式。

## 3. 踩坑点复盘

1. **图片 `pic_id` 失效**  
   上传成功后立即发博可能提示“图片不存在”。解决方案：在上传后延时 2~3 秒再发博，并且在发博失败且错误码与图片相关时，重新上传该图片获取新 `pic_id`。

2. **超话话题错误**  
   如果超话名称带特殊符号（如半角括号），需要将整个话题文本 URLEncode 再拼进 `status` 参数，否则接口会把 `#` 截断。建议一律把 `status` 字段整体 encode。

3. **限流封禁后“假恢复”**  
   官方文档写的封禁窗口较小，但我们遇到过持续 30 分钟的 IP 屏蔽，此时任何请求都返回 403。解决方案是准备多个出口 IP 并做容灾切换，但成本较高。我们在低要求场景下直接 `sleep` 更长时间，并增加全局冷却标记，避免反复撞墙。

4. **微博 id 获取失败**  
   发博成功但返回体缺少 `idstr` 的情况偶发，此时我们将该记录状态标记为 `success`，但 weibo_id 留空，并记录原始响应，防止因缺少 id 而重复发文。

## 4. 可复用建议

- **封装为 OpenClaw 插件/技能**：将图片上传、发博、限流排队收敛成一个自定义插件，对外暴露 `weibo_sync` 动作，内部管理所有 token、冷却和归档。Agent 只需传入文本和图片路径。
- **通过 MCP 暴露工具**：如果把上述逻辑包装成 MCP Server，Agent 可以自主决定何时发博，同时借助 Server 端的限流保护，避免 Agent 误操作触发封禁。
- **多账号轮换**：如果发博量大，可以在存储层维护一组 `access_token`，由排队逻辑择优使用剩余次数最多的账号，并隔离各自冷却状态。
- **状态外移**：SQLite 归档很方便，但若多副本运行，可改为 Redis + 持久化，但注意幂等键的设计保持一致。

## 5. 总结

在 OpenClaw 的自动化体系里接入微博超话同步，不是一套“所见即所得”的体验：图片上传需要反复重试、限流需要仔细观察响应头并退避、状态归档必须防御重复和并发。好在这些问题都可以在 Workflow 层面用动作封装解决，并不依赖黑盒平台。整体上，这套方案每天可稳定同步几十条图文到超话，失败率控制在 5% 以下，异常可追溯。如果你也有类似需求，建议先小流量验证 2～3 天，读懂接口的“潜规则”，再逐步提高同步频率。
