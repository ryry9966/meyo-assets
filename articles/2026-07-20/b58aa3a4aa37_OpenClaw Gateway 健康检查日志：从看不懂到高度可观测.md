# OpenClaw Gateway 健康检查日志：从看不懂到高度可观测

Gateway 是 OpenClaw 体系中最接近流量入口的组件，无论你接的是 Agent 对话、MCP 服务还是插件调用，所有的请求都会先命中 Gateway 的端口。健康检查（Health Check）则是 Gateway 能否正常工作的第一道哨兵——容器编排平台（Kubernetes 等）通过定期探测来决定是否将流量切到某实例。健康检查出问题，轻则导致实例被反复摘除，重则引发级联重启，让整个代理链路抖动。

然而，大部分同学在看 Gateway 日志时，面对刷屏的 `GET /healthz` 或 `GET /readyz` 只会感到困惑：这些请求到底算正常还是异常？什么响应码代表“不健康”？日志里那些几毫秒的响应为何会让 Pod 重启？本文将以 OpenClaw Gateway 典型部署为背景，梳理健康检查日志的解读方法、排障路径和配置建议。

## 背景：Gateway 健康检查的双面性

OpenClaw Gateway 默认启用两个健康检查端点，对应 Kubernetes 中的两种探针：

- **存活检查（liveness）**：通常挂载在 `/healthz`，只验证进程是否存活，不检测依赖。如果连续失败，kubelet 会杀掉容器重启。
- **就绪检查（readiness）**：通常挂载在 `/readyz`，除进程存活外，还会做轻量依赖检查（如本地缓存状态、必要子服务连通）。连续失败会从 Service 端点中摘除该 Pod，不再接收流量。

两种探针的默认间隔都是 10 秒，超时通常设为 3 秒，连续失败阈值多为 3 次。Gateway 日志里，每一条健康检查请求记录都像一个微型快照，包含了请求方法、路径、返回码、耗时、来源 IP 以及可能的错误信息。

## 常见问题：为什么健康检查日志总让人误判？

最典型的困惑是：**“日志里全是 200，但 Pod 还是在重启。”**

这是因为很多人只关注了响应码，忽略了耗时。存活检查的代码逻辑极简，理论上永久返回 200，但如果节点负载高或进程阻塞，响应可能延迟到 5 秒以上，超出探针超时（3 秒），kubelet 会把这种超时直接算作失败。Gateway 虽然向自己返回了 200，但 kubelet 根本没等到这个响应。

另一种情况是就绪检查返回 503，日志里却只看到 `GET /readyz 503 4ms`。这通常说明依赖侧有问题（例如下游 MCP 服务不通），但就绪检查只是如实反映了“不可用”状态，并不会体现在日志堆栈里。如果你只看 Gateway 自身日志，很容易漏掉真实根因。

## 做法：四步读懂健康检查日志

以下操作基于 OpenClaw Gateway 的默认 JSON 日志格式，配合 `jq` 进行快速定位。

### 第一步：确认日志级别和格式

确保 Gateway 日志级别至少为 `info`，并输出为 JSON 行（Line-delimited JSON）。然后通过 `grep` 过滤探针路径：

```bash
kubectl logs -l app=openclaw-gateway --tail=200 | grep -E '"(GET|HEAD) /healthz|/readyz"' > health.log
```

### 第二步：用 jq 提取关键字段

```bash
jq -r '[.timestamp, .request_path, .status, .latency_ms, .error] | @tsv' health.log | sort
```

关注以下字段：
- `status`：200 仅表示 Gateway 自身视角的响应成功，不代表探针结果。
- `latency_ms`：大于探针超时时间即致命。通常需要保证 P99 低于 200ms。
- `error`：若出现 `context deadline exceeded` 或 `timeout`，说明探针超时。
- `request_path`：区分 `/healthz` 和 `/readyz`，排障维度不同。

### 第三步：绘制时序视图

连续抓取几次日志，打上时间戳，制成简单折线或表格。重点找连续出现的异常模式，比如就绪检查每 10 秒返回 503，且持续超过 30 秒，那么该 Pod 一定已经被摘除。把这段时间的依赖服务日志（如 MCP hub 或本地缓存）拿出来对比，通常能直接定位根因。

### 第四条：模拟探针逻辑验证

如果你怀疑是探针配置不合理，可以用 `kubectl exec` 进入容器，手动发送探针请求，观察耗时和返回：

```bash
time curl -v http://localhost:8080/readyz
```

注意，这里的 `curl` 返回时间包含了 TCP 握手和传输，会比 Gateway 内部记录慢一点，但足以判断是否超过超时阈值。

## 我踩过的三个坑

### 坑 1：用同一个端点做存活和就绪检查

很多快速开始的例子会把存活和就绪都指向 `/healthz`。一旦网关依赖下游某个服务故障，就绪检查依然返回 200，导致故障 Pod 没有被摘除，不断接收用户请求并返回 502/504，严重扩大影响面。**必须分离两个端点**，并让就绪检查做更多语义化判断。

### 坑 2：超时设置跟着感觉走

看到官方默认探针超时 1 秒，觉得太短，手动改成 10 秒。结果一个真实暂停（如 GC）让所有 Pod 都卡在 8 秒，探针不超时，但业务请求全部超时，流量切不出去。超时应当基于部署环境的 P99 延迟来设定，且保持存活探针比就绪探针稍短。

### 坑 3：忽略健康检查的“冷启动”窗口

MCP 服务或插件加载可能需要 5-15 秒，如果 `initialDelaySeconds` 过短，Pod 启动后立刻被就绪检查标记为失败，重启循环。此时日志里会出现大量 503，但 Gateway 进程本身已经完全正常。解决方法是根据最大依赖加载时间再加 5 秒设置初始延迟。

## 可复用的建议

1. **结构化健康检查端点**  
   让就绪检查返回 JSON 体，包含依赖状态的描述信息，如 `{"status":"not_ready","deps":{"mcp_hub":"unreachable"}}`。这样不仅日志可读，Prometheus 指标也能直接捕捉。

2. **为探针生成独立的日志标记**  
   在 Gateway 访问日志中间件里，给来自 kube-probe 的请求专门加一个标签 `"probe": "liveness"` 或 `"readiness"`，方便集中过滤和统计。

3. **用指标代替看日志**  
   真正的工程化实践是建立指标：`gateway_healthcheck_duration_seconds`（分位值）、`gateway_readiness_status`。设置告警规则：P99 超过探针超时时间的 80% 即可预警，避免人工盯日志。

4. **压测环境先过一遍**  
   新部署前，用简单的负载工具对健康检查端点施压，观察高 QPS 下的延迟分布。曾经遇到一个 Bug：Gateway 的健康检查处理函数里有一个低效的哈希运算，导致单次探针被打到 500 并发时 P99 飙升至 1.2 秒，直接触发超时重启。

## 总结

看 OpenClaw Gateway 的健康检查日志，核心不是数 200 还是 503，而是建立三个维度的关联：**响应码 + 耗时分布 + 依赖状态快照**。当你能从一条日志中立刻判断出“这一次探针是否会触发平台动作”时，才算真正看懂。配合 JSON 结构化日志、指标化和合理的探针配置，才能让健康检查从骚扰性的重启来源，变成你观测体系中最可靠的一层护栏。
