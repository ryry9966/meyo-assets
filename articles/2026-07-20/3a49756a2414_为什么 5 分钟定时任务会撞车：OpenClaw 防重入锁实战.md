## 背景

在 OpenClaw 上跑自动化工作流时，我们经常会用定时触发器来周期性地调用 Agent 或 MCP 工具。一个典型的配置是每 5 分钟执行一次任务，例如定时拉取外部数据、巡检节点状态、清理过期资源。最初一切正常，直到某天我们发现任务执行时间偶尔超过 5 分钟——可能是下游 API 响应变慢，也可能是处理的数据量增加。此时问题出现了：上一个实例还没跑完，下一个调度时间又到了，新实例被触发，两个（甚至更多）实例同时运行同一份业务逻辑。

这就是典型的“任务重入”。在我们没有做任何保护的情况下，两次并发的执行会操作同一批数据、发送重复通知、占用相同的临时文件，轻则产生脏数据，重则引发竞态条件导致服务异常。本文将以 OpenClaw 上的实践为例，拆解这一问题的根源，并给出一种工程化的防重入锁方案。

## 问题分析

假设我们有一个 `data-sync` 任务，cron 表达式为 `*/5 * * * *`。任务逻辑大致如下：

1. 从外部 API 拉取增量数据
2. 通过 Agent 调用 MCP 工具做格式转换
3. 写入内部数据存储
4. 更新游标，记录最后同步时间

正常情况下，步骤 1-4 耗时约 2 分钟，远小于 5 分钟的间隔，看上去很安全。但当外部 API 发生抖动，第 1 步的请求超时重试了两次，总耗时骤增到 6 分钟。在 OpenClaw 的默认调度器里，定时器只负责“按时触发”，并不关心上一次执行是否结束。于是一个 6 分钟的任务在启动后 5 分钟就会被第二次触发，两版同步逻辑同时运行，各自拉取相同的增量数据、各自更新游标，最终导致数据重复写入，甚至游标被错误地回退。

可以直观理解为：调度器的间隔是指“发射间隔”，而非“完成后再等待 5 分钟”。这就是撞车的本质原因。不仅要解决单次耗时超过间隔的问题，还要考虑到时钟漂移、容器重启、多实例部署等更复杂的场景。

## 做法与步骤

我们采用“执行前加锁、执行后释放”的分布式锁模式。由于 OpenClaw 本身没有内置防重入功能，我们通过一个轻量的外部锁服务来实现。这里以 Redis 锁为例，因为它部署简单、大部分 MCP 环境都已具备。

### 1. 抽象锁服务

编写一个 MCP 工具或 Agent 可调用的脚本，提供两个动作：
- `acquire_lock(lock_key, ttl)`：尝试获取锁，成功返回 `true`，否则 `false`
- `release_lock(lock_key)`：释放锁

伪代码（Python）：
```python
def acquire_lock(redis_client, lock_key, ttl=300):
    return redis_client.set(lock_key, "1", nx=True, ex=ttl)

def release_lock(redis_client, lock_key):
    redis_client.delete(lock_key)
```
`lock_key` 我们使用 `openclaw:cron:data-sync` 这样的命名，保证不同任务互不干扰。`ttl` 设置一个合理上限，比如任务预期最大执行时间的 1.5 倍（例如 10 分钟），防止进程异常退出导致锁永不释放。

### 2. 在 OpenClaw 任务中集成

每个定时触发的 Agent 工作流开头增加一个“获取锁”步骤，结尾增加“释放锁”步骤，并用条件判断来保护主逻辑。

```
[定时触发] -> [调用 acquire_lock]
                ├─ 成功 -> [执行业务逻辑] -> [调用 release_lock] -> [结束]
                └─ 失败 -> 记录日志，直接结束（或设置重试标记）
```

如果锁获取失败，说明已有实例在运行，直接退出，避免重入。这里只需在 OpenClaw 的可视化编排或 YAML 配置中插入对应的 MCP 工具调用即可。

### 3. 处理异常路径

关键点：锁的释放必须放在 `finally` 类似的机制中。如果 OpenClaw 的任务编排不支持异常捕获，可以在业务逻辑末尾使用条件节点，或者在 MCP 工具的 `release_lock` 实现中加入超时自动释放保底。更稳妥的做法是依赖 Redis 的 TTL 自动过期，这样即使 release 漏调，锁也会在预定时间后释放，不会形成死锁。

### 踩坑点

- **锁超时设置过短**：如果 TTL 小于任务实际执行时间，运行中的任务会因为锁自动过期而失去保护，让第二个实例乘虚而入。可用的策略是动态续期：任务内部每隔一段时间调用 `expire` 延长锁，但复杂度较高，建议先用固定的安全 TTL。
- **锁粒度问题**：不要整个系统用一把锁。锁的 key 必须精确到任务实例，否则不同定时任务之间会互相阻塞。
- **Redis 单点风险**：生产环境可能考虑 Redis Sentinel 或 Redlock。但任务防重入的可用性要求通常较低，短暂的锁服务不可用可以接受直接跳过本次执行，记录告警即可。
- **多实例部署**：如果 OpenClaw 自身部署了多个工作节点，文件锁会失效，必须使用 Redis、etcd 这类分布式锁。
- **re-lease 不是幂等的**：不要简单地在获取锁时先 `del` 再 `set`，这样会释放掉其他实例的锁。用 `SET NX` 原子操作。

## 可复用建议

1. **模板化锁节点**：将 acquire/release 封装成 OpenClaw 的通用组件或子工作流，所有长耗时定时任务直接复用。
2. **配置化 TTL**：不同任务根据历史耗时配置不同的锁 TTL，可通过任务变量传入。
3. **监控与告警**：记录每次“锁获取失败”事件，统计跳过执行的频率。如果连续多次跳过，说明任务耗时异常增长，需要排查。
4. **兜底幂等**：即使有了锁，业务逻辑也应尽量设计成幂等（例如通过游标、数据版本号去重），双重保险。
5. **必要时考虑调度器改造**：如果团队对定时调度的需求复杂，可以引入像轻量级任务队列（如 PG 队列+SKIP LOCKED）来彻底避免同任务并发，但引入新组件成本较高，锁方案对中小规模足够友好。

## 总结

5 分钟任务会撞车，根本不是概率问题，而是时间问题——只要任务执行时间存在大于间隔的可能，就一定会发生。OpenClaw 的灵活编排让我们可以快速构建自动化，但工程细节仍需自己把控。通过一个标准的防重入锁，我们用极小的额外成本解决了并发执行带来的脏数据与故障风险。下次给 Agent 挂上定时触发器时，不妨顺手加上这把“安全锁”，让你的自动化流跑得更稳。
