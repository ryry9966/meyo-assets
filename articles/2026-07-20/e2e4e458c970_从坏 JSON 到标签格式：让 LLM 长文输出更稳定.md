## 背景：为什么要让 LLM 输出结构化长文

在 OpenClaw、MCP 插件、自动化 Agent 里，经常会要求模型一次性生成“长文本 + 结构化元数据”——比如一份完整的分析报告，同时附带 JSON 格式的标题、摘要、标签、评分等字段，方便下游系统消费。最自然的做法是让模型输出一个 JSON 对象，里头某个字段就是长文本。但实践下来，这条路对长输出极不友好。

## 问题：JSON 在长文本场景下太脆弱

LLM 输出的 JSON 经常出现以下问题：

- 长文本内部的引号、换行、反斜杠等特殊字符未正确转义，导致整个 JSON 无法解析。
- 最后一段代码块的三引号缺失，或者大括号、方括号未闭合。
- 模型多输出一个逗号，或者在解释说明时额外加上了 markdown 标记。
- 使用 `json.loads` 或 `JSON.parse` 时，哪怕只有一个字节的错误，整个结构就废了。

在需要生成上千字的报告时，这些问题的出现概率非常高，甚至接近 20%～30%。在 Agent 流水线里，一次解析失败就意味着需要重试、降级或人工干预，严重影响自动化稳定性。

## 做法：用自定义标签替代 JSON 结构

我们切换的思路非常简单：**放弃 JSON，改用类似 XML 的自定义标签包裹不同部分**。例如，原来期望的 JSON 是：

```json
{
  "title": "xxx",
  "summary": "...",
  "body": "长文本..."
}
```

改为要求模型输出：

```
<title>xxx</title>
<summary>...</summary>
<body>
这里可以是任意长度的文本，包含各种标点、换行、
甚至代码块，只要不出现 </body> 就不会干扰解析。
</body>
```

解析代码也不再依赖严格的 JSON 解析器，而是基于正则或简单的字符串匹配。以 Python 为例：

```python
import re

def extract_tag(text: str, tag: str) -> str | None:
    pattern = rf"<{tag}>\s*(.*?)\s*</{tag}>"
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1).strip() if match else None
```

对 `body` 这类可能很长的内容，非贪婪匹配 `(.*?)` 配合 `re.DOTALL` 即可正确取到全部内容，只要内容里不出现闭合标签本身。为了让输出更稳定，我们会在提示词里要求模型严格遵守这一格式，并给出示例。

如果是多个同类条目（例如列表），可以用 `<item>...</item>` 重复出现，解析时使用 `re.findall` 收集。

## 踩坑点

1. **标签名冲突**  
   长文本中可能意外出现与标签同名的字符串，例如报告里正好讨论 `<title>` 标签。解决方法是使用足够独特的前缀，如 `<oc_title>`, `<oc_body>`，或添加命名空间 `x-`。OpenClaw 社区有用户直接用 `<|title|>` 这样 LLM 极少会自然输出的分隔符，效果也不错。

2. **模型不遵守输出格式**  
   即使提示词里要求严格输出纯文本标签，模型偶尔还是会加上 markdown 代码块（例如 ```` ``` ````）。这时解析需要做一层预处理：去掉最外层的代码块包装，再提取标签。

3. **未闭合或嵌套标签**  
   一旦 model 生成不完整的标签，整个提取就会失败。可以在提取每个标签时做健壮性处理：如果找不到闭合标签，就让 `extract_tag` 返回 `None`，并记录日志。对核心字段（如 `body`），可以设计一个 fallback 逻辑——比如将 `<oc_body>` 之后直到文末的所有内容作为正文，前提是确认没有后续标签。

4. **性能与依赖**  
   正则提取开销极小，但在高频调用时，`re.DOTALL` 可能会导致回溯。如果输出体量很大（几十 KB），建议用更简单的滑动窗口或索引查找 `<tag>` 和 `</tag>`，避免正则的长匹配时间。这里 Python 的 `str.find` 足够应付大部分场景。

## 可复用建议

- **制定输出规范文档**：在自己团队的 Agent prompt 模板中，明确列出要使用的标签及必须严格遵守的规则，并提供“正确示例”和“错误示例”，让模型知道不允许出现额外解释。
- **优先使用唯一标签名**：采用前缀或特殊分隔符，例如 `<report_meta>`, `<report_body>`，降低冲突概率。
- **解析时宽容，但验证严格**：标签提取完成后，对 `title`、`summary` 等字段仍可做长度、非法字符校验，不符合期望时触发重试，而不是将错误内容直接传给下游。
- **保留错误现场**：每次提取失败时，将原始输出完整记录到日志或临时存储，便于后续排查是 prompt 不够清晰，还是模型确实出现了奇葩输出。
- **多模型适配**：如果你同时用 OpenAI、Claude、开源模型，注意到不同模型对 XML 格式的遵循程度略有差异，建议准备两三套 prompt 变体，通过少量评测选定最稳定的一套。

## 总结

在需要 LLM 输出长文章与结构化数据共存的场景下，JSON 的严格语法让它变成了“坏格式频发”的源头。转向自定义标签格式，本质上是降低了解析器对格式正确性的依赖，同时保留了结构化的能力。这不是一种“更好”的技术，而是一种更适合当前 LLM 输出特性的工程取舍。

在我们使用的 OpenClaw + MCP 自动化管道里，切换标签格式后，结构化提取的成功率从约 78% 提升到了 98% 以上，长文场景的稳定性得到了极大改善。这套方法同样适用于任何需要控制 LLM 输出结构、又不想被 JSON 解析拖累的 Agent 实践者。
