## 这是谁的问题

如果你在用 OpenClaw、Agent 或 MCP 工具链搭建自动发帖流水线，大概率遇到过类似窘境：

- 生成的文章正常发布，几天后想修改重发，却发现原始 Markdown 早已被覆盖或丢失；
- 配图来自临时对象存储，链接过期，图片全裂；
- 多平台分发后，根本记不清某个版本的文章用了哪些图、图的尺寸与来源。

本质上，我们的流水线在生产内容的同时，却没有同步搭建一个可靠的本地归档机制。哪怕只是一次性内容，一旦涉及审核、审计或二次复用，缺少本地归档就会变成工程负债。

这篇文章不谈高大上的内容中台，只讲一件事：如何用**极简的文件结构 + 一份 assets.json**，给你的自动发帖流水线接上本地归档能力。

---

## 目标：最小化归档，最大化可复现

我们希望做到：

1. **文章落盘为独立 Markdown 文件**（含 frontmatter），所有图片引用变成相对路径。
2. **所有配图下载到本地**，统一存放在一个 `images/` 目录下。
3. **生成一份 `assets.json`**，记录每张图片的原始 URL、本地文件名、尺寸、hash 等信息。
4. **目录结构自描述**，一眼能看到某个发布批次的全貌。

可以这样约定一个归档单元：

```
posts/
└── 2025-03-21-my-automation-post/
    ├── article.md
    ├── images/
    │   ├── 3f2a9b1c.png
    │   └── 7d4e6f8a.jpg
    └── assets.json
```

`article.md` 中的图片引用已经从 `https://cdn.example.com/xxx` 替换为 `./images/3f2a9b1c.png`。整个目录可以打包、版本控制，或直接扔进对象存储做冷备，随时拿出来都是“可构建”的状态。

## 怎么做：一条脚本 / 一个 MCP 工具

我们的流水线大体是：Agent 调用 LLM 生成文章及图片描述 → 根据描述生成图片 → 组装 Markdown → 发布到目标平台。归档只需在“组装完 Markdown 并拿到所有图片 URL”之后插入一个步骤。

具体可以拆成四步：

### 1. 抓取信息
从生成结果中提取：
- 文章正文（完整的 Markdown）
- 所有图片 URL（包括正文中的以及 frontmatter 中的封面图等）
- 元数据：标题、slug、创建时间、来源平台等

### 2. 创建归档目录
按 `posts/{date}-{slug}/` 创建目录。如果 slug 包含特殊字符，做一次安全文件名处理。

### 3. 下载图片并更新引用
对每个图片 URL：
- 生成一个本地文件名，例如取 URL 的 SHA-256 前 8 位加原始扩展名（若无扩展名则通过 `Content-Type` 推断）。
- 下载图片到 `images/` 目录，设置超时与重试。
- 在 Markdown 中把该 URL **全局替换**为 `./images/{文件名}`。
- 记录到数组里，用于后续生成 `assets.json`。

### 4. 生成 assets.json
```json
{
  "title": "My Automation Post",
  "slug": "my-automation-post",
  "created": "2025-03-21T10:00:00Z",
  "images": [
    {
      "original_url": "https://cdn.example.com/abc.png",
      "local_path": "images/3f2a9b1c.png",
      "width": 1200,
      "height": 630,
      "size_bytes": 204800,
      "sha256": "3f2a9b1c..."
    }
  ]
}
```

有兴趣的话，还可以加上图片的生成 prompt、生成模型、色彩空间等字段，方便后续溯源。

这段逻辑可以用 Python 脚本实现，搭配 `aiohttp` + `aiofiles` 做并发下载；也可以封装成 MCP 工具，挂在 OpenClaw 的 Agent 上，在发布动作完成后自动调用。选择哪种方式取决于你的链路是命令行的，还是完全 Agent 驱动的。

## 踩坑记录

以下是我在实际落地中遇到的几个典型问题，如果你动手做，大概率也会碰到。

### 图片文件名灾难
直接用 URL 的路径部分做文件名是坑——特殊字符、中文、空格、超长路径直接导致文件系统报错。**只使用 hash + 扩展名**是最稳妥的方式，同时检查扩展名是否在黑名单（如 `.php`、`.exe`）以防伪装。

### 并发下载引发的 429 与连接池耗尽
发布后可能带十几张图，如果无限制并发请求同一个 CDN，很容易触发限流。设置并发度（比如 4 个协程），加上指数退避重试很重要。另外，记得设置 `TCPConnector` 的 `limit_per_host`，否则会耗尽本地端口。

### Markdown 替换不完全
图片引用可能出现在多个地方：正文、frontmatter 的 `coverImage`、HTML 的 `<img>` 标签等。替换时务必用正则一次匹配所有可能的写法（`![](...)`, `<img src="...">`），同时记录替换次数，零次替换时打 warning，避免认为已成功而实际未生效。

### 重名 URL 导致覆盖
有时同一张图被引用多次（如正文与封面相同），如果用原 URL 的 hash 命名，自然会指向同一个文件。但要注意不要重复下载并二次写文件，可以通过判断本地是否存在来跳过下载。

### 超大文件
偶尔会碰到文章里嵌入了视频或巨型 GIF，归档体积爆炸。建议设置最大下载尺寸（如 50MB），超过后仅记录原始 URL 并标记为“未下载”。

## 可复用建议：把它当成流水线的一个标准组件

不要为每一个项目单独写这段逻辑，把它抽象成一个**可配置的归档工具**，输入就是 `{ markdown, image_urls, metadata }`，输出一个归档目录路径。可以做成：

- **独立的 CLI 工具**：通过 `stdin` 或文件传入 JSON，方便在任意 Shell 流水线中调用。
- **MCP 资源/工具**：暴露 `archive_post` 方法，Agent 在完成发布后自动调用，并返回归档路径作为结果，可进一步用于日志记录或通知。
- **OpenClaw 插件**：注册一个后处理钩子，监听“发布成功”事件，异步触发归档。

另外，强烈建议把归档目录纳入 Git 仓库（至少对关键文章）。你会发现，当需要回溯某篇文章的历史版本时，`git log -- posts/2025-03-21-*/article.md` 比任何后台都快。

---

## 总结

自动发帖流水线的本地归档，听起来是个不起眼的辅助功能，但它是内容工程质量的分水岭。一旦你把文章、图片和资源清单落盘为自包含的文件夹，你就拥有了：

- 绝对的数据主权，不依赖任何外部链接；
- 可审计的发布历史，方便排查事故；
- 随时重新发布的“源文件”，甚至换平台也不怕。

在 OpenClaw 生态里，这件事天然适合用一个小型 MCP 工具或 Agent 插件来完成。花半天时间把它沉淀下来，后续所有项目都能复用，值得。
