## 背景：当内容分发遇上自动化

社区运营、技术作者、小型团队越来越依赖自动化手段将同一篇内容推送到 Twitter、Discord、Telegram、知乎、SegmentFault 等多个渠道。借助 OpenClaw 这类可插件化的 Agent 框架，结合 MCP 工具（比如平台 API 封装），构建一条「内容更新 → 自动分发」的流水线已经非常容易。

但“能发”和“发得好”之间有一条明显的边界：**自动化发布极易演变成跨平台的信息轰炸**。你的一条博文更新可能在三分钟内同时出现在五个社区，对关注你多个账号的读者而言就是多次刷屏，轻则取关，重则被平台限流或处罚。

本文将剥离掉内容生成与账号管理的部分，只聚焦一个问题：**在自动化同步管道中，如何从工程层面避免重复推送和控制发布节奏**。

## 问题拆解：刷屏的三类来源

实际踩过的坑里，刷屏并不只是因为“发得太多”，而常常来自以下场景：

1. **事件重复触发**  
   Webhook 重试、上游 CMS 的多次保存、Git 仓库的 rebase 推送都会导致同一条内容被反复送入发布流水线。

2. **多平台无差别推送**  
   不考虑各平台的受众重叠和发布频率限制，所有平台同时、同频、同样式地轰炸。

3. **批量回溯发布**  
   迁移历史内容或补发时，一次性将几十条旧文全量同步，瞬间占领时间线。

设计同步策略，本质上就是要为这些场景加上节流、去重和分批控制。

## 系统工程做法：中心调度器 + 指纹去重 + 令牌桶

我们并不需要重型消息队列，一个轻量的中心调度器配合 Redis 就能解决绝大部分问题。整体的发布流水线可以拆成三个核心步骤。

### 1. 生成内容指纹，只做必要去重

所有进入流水线的内容，首先计算一个 **幂等指纹**。可以使用标题 + 正文前 200 字符的 SHA-256，或者更稳定的 `canonical_url + content_hash` 组合。指纹写入 Redis，并设置一个与业务匹配的过期时间（通常 24～72 小时）。

```
fingerprint = sha256(title + body[:200])
if redis.exists(f"published:{fingerprint}"):
    drop
```

**注意**：不要仅依赖 URL 去重，因为同一篇文章可能在不同平台使用了不同的短链接或追踪参数，会导致去重失效。

### 2. 基于令牌桶的跨平台限流

不同平台的速率限制差异极大。例如 Twitter API 对发推有 3 小时 300 条的窗口限制，Discord webhook 往往限制每秒 1 条，知乎发文章的频率限制则颗粒度更粗。

工程上最简单的做法是 **为每个目标平台维护独立的令牌桶**（可以基于 Redis + Lua 实现，或者用内存速率限制器）。每次发布前尝试获取令牌，未获取到的消息进入延迟队列，在下一个窗口自动重试。

OpenClaw 的 Agent 流程中可以这样编排：

- `ContentNormalized` 事件 → 去重检查 → 平台令牌桶检查 → 调用 MCP 发送工具
- 如果令牌不足，则将消息体及目标平台写入 Redis 延迟队列，由一个轻量的 `delayed_publisher` 协程定期轮询。

### 3. 批量发布合并，避免“瞬间风暴”

对于历史内容迁移或需要同时发布多条的场景，增加一个合并窗口：收集 5 分钟内同平台的所有待发内容，如果超过阈值（比如 3 条），就合并为一条摘要消息发送，并附带原文链接列表。这虽然牺牲了一些点击率，但极大避免了刷屏副作用。

## 一个可落地的 OpenClaw Agent 示例（伪代码）

```python
class RateLimitedPublisher:
    def __init__(self, platform_configs):
        self.buckets = {p: TokenBucket(c.rate, c.capacity) for p, c in platform_configs.items()}
        self.fingerprint_store = RedisFingerprintStore(ttl=86400)

    async def publish(self, content: Content, platforms: list[str]):
        fp = content.fingerprint()
        if self.fingerprint_store.exists(fp):
            return

        for plat in platforms:
            if not self.buckets[plat].consume():
                await self.enqueue_delayed(plat, content)
                continue
            await mcp_call(plat, content.to_platform_format(plat))
            self.fingerprint_store.mark(fp)
```

这部分逻辑完全可以封装成一个 MCP 工具，供 OpenClaw 的 Planner Agent 调用，从而实现“发布策略”与“业务逻辑”解耦。

## 踩坑记录与关键边界

- **429 响应不能简单重试**  
  很多平台会在 HTTP 429 中返回 `Retry-After` 头，需要解析后动态调整本地令牌桶的填充速率，否则持续触发限流会被临时封禁。

- **fingerprint 的时间窗口陷阱**  
  TTL 设置过长会导致合理的内容更新被误判为重复，比如文章发布后又修改了错别字。建议保留一个“内容版本号”或 `updated_at` 字段，与指纹组合使用，更新后自动使旧指纹失效。

- **跨平台的内容映射表必不可少**  
  当一个平台发布成功而另一个失败时，需要持久化记录，否则可能造成部分平台永久漏发。使用一张 `publication_log` 表记录 `content_id, platform, status, published_at`，方便对账和补偿。

- **不要试图在 Agent 里写死阈值**  
  平台速率限制会变化，将限流参数做成 YAML 或环境变量可配置，并通过简单的 admin 接口允许临时放宽或收紧。

## 可复用建议

1. **抽离一个 Publisher Service 而不是散落在多个 Agent 动作里**  
   哪怕它只是一个常驻进程，也能让你的自动化工作流干净很多。

2. **将去重指纹发布时间与用户可见的发布时间解耦**  
   去重存储可以用单独的前缀，避免因为展示层的需求变动影响核心限流逻辑。

3. **加入干跑模式（dry-run）**  
   在迁移或调整策略时先模拟发布，查看哪些消息会被丢弃、延迟或合并，确保不会引入静默遗漏。

4. **监控必须覆盖频控行为**  
   在日志里标出 `dropped_by_dedup`、`delayed_by_rate_limit`、`merged_batch` 等事件，便于观察你的发布策略是否过于激进。

## 总结

自动化发布要做的不是“全部发出去”，而是像一个懂得社交分寸的人：不同场合适度发言，不说重复的话，不占用过多的公共注意力。给你的发布流水线加上去重、令牌桶和合并延迟这三板斧后，刷屏问题基本可以从工程层面根治。而且在 OpenClaw + MCP 的体系下，上面的逻辑完全可以封装成可复用的工具或 Skill，后续接入新平台时只需关注对应的限流参数和内容格式适配。

控制节奏，比内容本身更能留住读者。
