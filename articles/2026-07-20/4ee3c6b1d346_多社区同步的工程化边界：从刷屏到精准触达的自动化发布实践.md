## 背景：一次推送，多群翻车

很多用 OpenClaw 搭建日常自动化管线的团队，都会遇到同一个动作的放大效应：一篇博客发布、一个 Release 生成，通过 Agent 或 MCP 服务同时推送到 Discord、飞书、Slack、Telegram 等多个社群。本意是提升触达效率，结果却变成了“同一条消息，换个群再来一遍”的刷屏灾难。

这类机械式同步的根因，不是哪款工具不好，而是缺少一个专门处理“渠道间关系”的发布调度层。把内容生产与渠道分发混在一起，最终就是 for-each channel 的暴力广播。

这篇文章记录我们在 OpenClaw 社区内，用 Agent 和 MCP 插件体系，打磨出一套多社区发布时的去重、合并与人工卡点的实践方法。不堆新名词，只谈工程上的边界设计。

## 问题定义

自动化同步变成刷屏，通常具备三个特征：

1. **相同内容多端重复**：同一个 Changelog，原封不动推给 5 个频道。
2. **时间窗口内集中轰炸**：一次运维通知，连续触发多个渠道，半分钟内刷满屏。
3. **缺少重要性区分**：拼写修复和严重漏洞公告，被同等处理，社群成员很快疲劳。

这些问题背后，是缺少一套“内容指纹 + 发布状态机 + 聚合窗口”的基础设施。如果只靠 MCP server 原生的推送能力，没有上层决策，就永远停不下刷屏。

## 做法：构建发布调度 Agent

我们的核心思路是：**用 OpenClaw 的 Agent 代替直接调用渠道 API，让 Agent 做出渠道级别决策。** 渠道的 MCP server 只作为动作执行端，不作为决策端。

### 1. 内容模型与指纹

将每一条待发布的内容，抽象为一个统一结构：

```yaml
content_id: "post-2025-03-release-v2"
title: "v2.0 发布说明"
summary: "修复了自动登录异常..."
source_url: "https://example.com/posts/v2"
channels:
  - type: discord
    channel_id: "123"
    priority: main
  - type: slack
    channel_id: "C456"
    priority: secondary
publish_time: "2025-03-22T10:00:00Z"
```

`content_id` 必须是**稳定且可标准化**的。我们采用 `源系统` + `文章 slug` + `版本号` 拼接，避免标题微调导致指纹失效。如果来自 GitHub Release，直接用 `repo + tag`。

### 2. Agent 决策流程

用 OpenClaw 定义一个专用于分发的 Agent “Distributor”，它拥有两个 MCP 工具：`query_publish_queue` 和 `channel_send`。Agent 的内部流程设计为：

1. 从队列拉取一条待发内容。
2. 查询本地持久化存储（SQLite），检查该 `content_id` 在过去 `cooldown_hours` 内是否已发布到**任意主渠道**。  
   - 若是，则跳过所有 `secondary` 渠道；  
   - 若主渠道未发，则推送到 `main` 渠道，并记录。
3. 对于次要渠道，只发送一个简洁卡片，内含原始链接，而不是全文。
4. 若同一 `content_id` 在队列中出现多次更新（如连续 edits），Agent 将这些小更新收集起来，直到冷却窗口结束，生成一条合并消息：“本文过去 2 小时内更新了 3 次，内容摘要：...”。
5. 所有发送动作写入日志（时间、渠道、结果），方便回溯。

这套流程利用 OpenClaw 的任务编排，让每一步都是可观察、可中断的，而不是一个一次性 fire-and-forget 的 API 调用。

### 3. 人工卡点（Human-in-the-loop）

为重要渠道（如全员公告频道），我们加入了一个 MCP 工具 `request_approval`。Agent 在准备发送前，会通过交互式终端或即时消息，向管理员发起确认：“即将向 #general 推送《v2.0 发布说明》，请回复 yes/no”。只有收到“yes”，才会继续执行。  
这个卡点不是阻碍自动化，而是充当安全边界，防止误操作引发真正的事故。

## 踩坑记录

1. **指纹失效**  
   初期直接用 `sha256(title + body)`，结果拼写修正后指纹全变，导致大量旧内容被重新推送。改为基于源系统 id 后解决。

2. **部分渠道发送失败导致状态不一致**  
   Discord 发送成功，Slack 却因限流失败，下次调度时，Agent 看到仅主渠道发过，又会试图补发 Slack。解决方案是记录每个渠道独立的发送状态，并设置重试上限，超过后标记为 `failed_no_retry`，转为人工处理。

3. **时间窗口与实时性的冲突**  
   把冷却时间设成 6 小时，导致产品紧急通告延误。最终改成分级窗口：安全公告 0 分钟冷却，普通文章 2 小时冷却。

4. **日志膨胀**  
   详细记录每个决策是有代价的。我们限制了只保留 30 天明细日志，超出部分按月汇总到统计表，防止 SQLite 文件爆炸。

## 可复用建议

- **分离内容与渠道**：不要把渠道列表写在 MCP server 的配置里，而是由 Agent 根据内容模型和规则动态决定。
- **优先设计状态机，再写代码**：定义清楚“未发”“已发主渠道”“已全发”“合并发布”“失败”等状态，所有动作都围绕状态转移，而不是单纯的 if-else。
- **为人工介入留口子**：再多规则也抵不住一次异常，一个 `request_approval` 工具能让系统从失控边缘拉回。
- **监控分发的“噪音比”**：统计每天同一内容跨渠道重复推送的次数，一旦超过阈值，立即调整规则，这个指标比“推送成功率”更能反映健康度。
- **重用 OpenClaw 的上下文管理**：Agent 自身的短期记忆可以记录“这次会话里已经讨论过该 content_id”，避免同一轮对话内重复建议，这在不启用持久存储时是轻量的去重手段。

## 总结

自动化同步的价值不在于“全自动”，而在于“有边界的主动”。利用 OpenClaw 的 Agent 能力和 MCP 工具生态，我们能够把“推送到多社群”从一个简单的 for 循环，升级成带有内容指纹、状态机、冷却窗口和人工确认的决策系统。这样，每条消息到达用户时，是精准的一条，而不是群里的第三条重复推送。

下次你准备用脚本批量同步时，不妨先问一句：这次的调度，是按渠道做的循环，还是按内容做的决策？这个区别，就是刷屏与精准的边界。
