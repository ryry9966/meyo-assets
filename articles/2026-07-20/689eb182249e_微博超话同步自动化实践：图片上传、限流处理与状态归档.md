# 微博超话同步自动化实践：图片上传、限流处理与状态归档

## 背景

在运营多账号或做内容分发的场景里，把某个渠道的图文定时同步到微博超话是一种常见需求。手工操作不仅重复，还容易因为忘记已发内容而重复发布，或者在图片格式、限流策略上踩坑导致账号异常。

在 OpenClaw 生态里，这类需求通常落在一个 Agent 定时任务上：准备好图文素材，调用微博相关接口完成发布，并记录发布状态以便去重。这篇文章聚焦三个最容易出问题的环节——图片上传、限流控制和状态归档，给出可工程化的实践方案。

## 核心问题拆解

一次完整的超话同步流程可以简化为：

1. 从素材源获取待发布内容（文本 + 图片列表）
2. **上传图片**，得到可用于发布微博的 `pic_id`
3. **检查限流窗口**，决定是否允许本次发布
4. 组装参数（文本、图片 id、超话 id 等）发送微博
5. **归档发布状态**，避免日后重复发送
6. 处理异常（重试或入库待人工处理）

其中第 2、3、5 步是稳定运行的工程关键。

## 图片上传：别被寄宿接口和参数顺序坑

微博的官方开放平台对普通开发者不太友好，多数实践会走寄宿在 m.weibo.cn 或网页版的上传链路。这里以 `https://picupload.weibo.com/interface/pic_upload.php` 为例，说明几个踩坑点。

**坑点 1：multipart/form-data 参数顺序**

这个上传接口对表单字段顺序敏感。之前遇到过一个典型错误：把 `app_id`、`token` 等参数放在文件字段之前导致 `-100` 错误，而换成文件字段在最前面就正常。调试时可以通过抓包对比浏览器请求，调整字段顺序到完全一致。

**坑点 2：Cookie 与 Referer**

上传请求需要维持有效的登录 Cookie（如 `SUB`），并且 `Referer` 必须为 `https://m.weibo.cn/` 或对应域名，否则会被拦截。在实践中，我们把它封装成一个独立的上传步骤，失败时立即刷新 Cookie。

**坑点 3：图片大小和格式**

格式推荐统一转为 `jpg` 或 `png`，大小控制在 5MB 以内，超过会被静默丢弃。上传成功后返回的 `pic_id`（形如 `0065YhLxly1hxxxxx`）需要在发微博时带上。

为了可复用，我会封装一个 `WeiboUploader` 工具，输入本地图片路径，返回 `pic_id` 或抛出可重试异常。在 OpenClaw 里可以作为一个 MCP tool 暴露：`upload_weibo_image`。

## 限流处理：比“频率”更重要的是“日上限”

微博对发布行为有隐性限制，不仅有每分钟/每小时的频率限制，还有单日总量上限。高频发布会导致账号被风控（验证码、禁言甚至冻结），而日总量超限可能直接返回 `20019`（频繁操作）或 `10024`（发布内容过多）。

我采用的策略是两层限流：

- **本地令牌桶算法控制发布间隔**：设定每 3 分钟最多发布一条，突发容量为 1。这能保证即便素材积压，也不会短时间内连续发送多条。
- **全局日发布计数器**：每天重置，达到阈值（如单日 40 条）后停止自动发布，把积压内容转为待处理任务。

实现时不需要依赖 Redis，一个本地 SQLite 表足够：

```sql
CREATE TABLE rate_limit (
    date TEXT PRIMARY KEY,
    count INTEGER DEFAULT 0
);
```

每次发布前检查当日计数，如果已达上限，将任务标记为 `deferred`，并通知运维手动介入或等次日自动重试。对于接口返回的限流错误码（如 `20019`），会触发指数退避重试，最大间隔 30 分钟，超过次数则归档为失败任务，防止无限重试加重风控。

## 状态归档：指纹去重 + 流水线式确认

多次运行 Agent 很容易导致同名内容重复发布。解决方案是对每条素材生成内容指纹（可取 `sha256(text + 图片URL列表)`），存入发布状态表：

```sql
CREATE TABLE publish_log (
    fingerprint TEXT PRIMARY KEY,
    status TEXT, -- pending / success / failed / skipped
    weibo_id TEXT,
    created_at TEXT,
    error_msg TEXT
);
```

在发布前查询指纹是否已存在且状态为 `success`，如果存在则直接跳过。这种机制比单纯依赖外部任务队列更可靠，因为它不依赖上游的“已处理”标记。

此外，微博发布后有时不会立刻返回 `weibo_id`，而是需要稍后查询。我在流水线中增加了“确认”环节：发布成功后等待 5 秒，用返回的临时 ID 轮询一次微博详情接口，拿到正式 `mid` 后再写入归档，状态才改为 `success`。这样可以避免发布已被删除但本地仍标记为成功的情况。

## 与 OpenClaw / Agent 体系的结合

在 OpenClaw 里，这套流程可以作为一组 MCP 工具实现：

- `upload_weibo_image(path)` —— 上传图片，返回 pic_id
- `post_weibo_super_topic(text, pic_ids, topic_id)` —— 发布超话微博
- `check_daily_limit()` —— 查询当日剩余可发条目数

然后由一个定时触发的 Agent 串联调用：拉取待发内容 → 上传图片 → 限流检查 → 发布 → 归档。失败时用 Agent 的异常处理链路把上下文记录到日志，方便排查。

如果不想走 MCP 方式，也可以将核心逻辑打包成一个 Python 脚本，通过 OpenClaw 的 `run_command` 调用，只不过工具粒度的可观测性会差一些。

## 可复用的工程建议

1. **图片上传独立封装**，屏蔽参数顺序和 Cookie 细节，提供统一的重试语义。
2. **双层限流**（频率 + 日总量）比单一频率限制更能模拟人的操作节奏，降低风控概率。
3. **指纹去重** 优于依赖外部队列状态，尤其适合素材源可能重放或补偿的场景。
4. **发布后确认机制** 用轮询补齐最终状态，保证本地归档的 `weibo_id` 真实有效。
5. **所有状态落在本地 SQLite**，轻量且易于迁移，过期的成功日志可以按月归档清理。

## 总结

微博超话同步自动化的难点很少有人讲透，实际上图片上传的协议兼容和限流策略才是决定系统能否长期无人值守运行的核心。把这两个骨头啃下来，再加上一个可靠的指纹归档，就能构建一套几乎不操心的内容分发管道。对于 OpenClaw 用户来说，这套设计可以很自然地融入 MCP 工具集，让 Agent 编排发布流程时不再被这些脏活累活绊住。
