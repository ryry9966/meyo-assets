## 背景：长文结构化输出的“最后一公里”痛点

在 OpenClaw 或类似的 Agent/自动化管线里，我们经常把大语言模型（LLM）当作一个“提取器”或“总结器”，让它从大量文本中生成结构化结果，比如任务列表、知识条目、元数据。最自然的方案是让模型输出 JSON，然后 `json.loads()` 直接消费。

但在实际工程中，尤其是当输出长度超过 1000 字、嵌套层级较多或模型被要求“边思考边输出”时，**JSON 的稳定性会急剧下降**。常见症状包括：

- 多出的尾部逗号、缺失引号、注释
- 字符串中未转义的换行或反斜杠
- 键名重复、结构不完整
- 多段 JSON 混合解释说明

用正则修、重试、请求 GPT-4 修复，这都能跑，但把时间花在修补格式上，既浪费 token 又不可靠。尤其在自动化工作流里，一次解析失败可能导致整个管线中断。

于是我开始实验**标签格式**，发现它在长文输出场景下比纯 JSON 表现得稳得多，而且对模型更友好。

## 问题拆解：为什么 JSON 在长文中容易坏掉？

大语言模型本质上是概率化地预测下一个 token。JSON 的语法约束非常严格：大括号匹配、引号闭合、逗号规则……这些对短输出问题不大，但随着长度增加，模型很容易在一些边缘位置“漏了”一个 `"` 或多打一个 `,`。一旦出现这些错误，整个文档对 JSON 解析器来说就不可读。

更致命的是**混合输出**。如果 prompt 允许模型“解释+JSON”，或者赋予它推理步骤，模型常常会在 JSON 前后加上自然语言，甚至把 JSON 拆成多块。这时用正则提取首个 `{...}` 都可能失败。

## 方案：用简单的可定界标签封装结构化内容

核心思路是放弃“全篇必须是合法 JSON”的假设，转而去定义一个**极易匹配的容器标签**，让模型把结构化内容放在标签内部。解析器只需要提取标签之间的原始字符串，再按约定格式（可以是简化的 JSON、YAML 片段、甚至自定义语法）进行解析。

例如，要求模型输出：

```
<tasklist>
- 阅读文档 && 完成摘要 | 优先级: 高
- 发送周报给团队 | 优先级: 中
</tasklist>
```

或者带键值的版本：

```
<result>
标题: 重构日志模块
负责人: jack
状态: 进行中
</result>
```

解析时，只需用正则提取 `<result>(.*?)</result>`，拿到内文再逐行处理。即便模型在标签外写了再多的解释，也不会干扰解析。

实际测试发现，哪怕总输出超过 3000 token，只要标签名足够唯一（如 `<openclaw_output>`），模型的边界保持能力远好于嵌套 `{}`。原因在于标签是“平坦”的语义标记，不像 JSON 那样需要深度平衡大括号和引号状态。

## 具体实践：在 OpenClaw 工作流中的落地步骤

我在 OpenClaw 里构建了一个“长文档摘要→任务拆解”流水线，步骤大致如下：

1. **设计标签规范**  
   选用 `<task_block>` 作为容器，每行一个任务，格式固定：`- 任务描述 | 截止日期 | 负责人`

2. **构造 prompt**  
   明确告知模型“将任务列表放在 `<task_block></task_block>` 之间，不要在该标记外输出任何任务”。给出 Few-shot 示例。

3. **解析器实现**  
   使用 Python 的正则非贪婪匹配：
   ```python
   import re
   match = re.search(r'<task_block>(.*?)</task_block>', response, re.DOTALL)
   if match:
       content = match.group(1).strip()
       tasks = parse_lines(content)  # 自定义行解析
   ```
   如果未匹配到，触发 fallback：尝试正则提取类似列表的文本，或直接记日志等待人工检查。

4. **错误处理与回退**  
   标签内部的格式依然可能出错，但范围被限定在标签内。这时可以设计一个**修复函数**，比如检测到某行缺少分隔符，就用默认值补全，不会影响整体流程。

## 踩坑记录

### 1. 标签名冲突
如果用户输入中恰好含有 `</task_block>`，会导致匹配提前截断。解决办法是使用带随机后缀或命名空间的标签，如 `<out_8472_task_block>`，并保证 prompt 中不让用户输入直接进入标签区域（例如通过角色分离标记）。

### 2. 内部标签嵌套需求
有时需要多级结构。纯扁平标签不够用，可以采用命名约定：`<item>...</item>` 配合 `<list>...</list>`，并编写分步抽取逻辑，但这已经接近自己实现简单解析器。此时要权衡复杂度，如果嵌套很深，考虑回退到 JSON，但搭配**标签包裹**做第一层提取。

### 3. 模型遗忘闭合标签
少数情况下模型会漏掉闭合标签。为此，解析时可以添加一个容错逻辑：如果未找到 `</task_block>`，就以全文末尾作为结束点，或使用启发式截断（如遇到下一个可能的标签）。

### 4. 转义与特殊字符
标签内部可能包含 XML 特殊字符 `<`、`>`、`&`，如果内容由模型自由生成，最好要求模型不使用这些字符，或约定用 Unicode 全角符号替代。如果可能，选择纯文本格式（如 YAML 的缩进）可以避开转义问题。

## 可复用建议

- **先包后解原则**：外层用唯一标签定界，内层再采用尽可能简单的格式（每行一条记录、键值对、Markdown 列表）。不要把深层嵌套的 JSON 塞到标签里，否则弱化优势。
- **给出强约束示例**：在 prompt 里展示至少两个完整的、带标签的示例，让模型清晰地学习边界。
- **解析宽容，校验严格**：标签内部解析器可以忍受少量格式偏差（例如缺一个空格），但解析后的字段必须通过业务校验（日期格式、责任人是否存在），不通过则纳入失败队列。
- **保留原始标签内容**：即使解析成功，也建议将标签内原始文本写入日志或存储，方便事后调试和改进 prompt。
- **Plan B 仍保留 JSON**：对于短小、固定结构的元数据字段，JSON 依然是首选。可以混合使用：模型输出中，小段 JSON 用代码块包裹，长列表用标签包裹。

## 总结

JSON 不是 LLM 结构化输出的唯一答案。当输出变长、模型自由度增加，严格语法带来的脆弱性会被放大。引入标签格式是一种务实折衷——牺牲一定的可读性通用性，换取在自动化管线下极高的解析成功率。这种做法特别适合 OpenClaw 中需要稳定抽取长文本的信息流、生成任务指令、拆解工作步骤的场景。

需要的仅仅是：一个独一无二的标签名、一段清晰的 prompt、和一个不足 10 行的正则解析函数。做过一次样板之后，就可以成为团队内部复用的小模式。
