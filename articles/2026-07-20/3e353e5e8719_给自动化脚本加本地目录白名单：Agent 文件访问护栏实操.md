## 背景：Agent 自动生成代码正在直接操作你的文件系统

在基于 OpenClaw 的 Agent 编排中，我们经常让大模型生成 Python 脚本、Shell 命令或调用 MCP 工具来完成本地任务，比如数据处理、文件归类和报告生成。这种模式极大提高了效率，但也引入了一个不容忽视的风险：**由 LLM 生成的代码直接在宿主机文件系统上执行读写操作，没有任何边界**。

无论你是用 `exec()` 直接执行代码片段，还是通过 `subprocess` 运行临时脚本，一旦模型产生幻觉、未正确理解路径，或者发来了恶意注入的代码，就可能覆盖重要配置、删除用户文件，甚至读取敏感信息。安全领域有一个基本原则——最小权限。自动化过程不需要读写整个文件系统，它只需要访问一个或几个特定的工作目录。

基于这个思路，我们可以构建一个轻量级的“文件访问护栏”（File Access Guard），强制把自动化脚本的文件 I/O 限制在一组本地目录白名单内，越界即拦截，不给越权访问留机会。

## 核心问题：如何在不修改 Agent 骨架的前提下，有效限制生成代码的文件操作范围？

常见的应对方式有几种：
- 容器/沙箱：用 Docker 或 Firejail 等方式隔离整个进程，但这会引入额外依赖和性能损耗，对轻量化 Agent 来说过重。
- 静态代码审查：用 AST 分析脚本中的文件操作，检查路径是否在白名单内。但动态路径、拼接、`pathlib` 等用法很难穷尽，容易绕过。
- 运行时代码修补：在脚本运行前，动态替换所有文件相关内置函数，注入路径检查逻辑。

工程实践中，第三种方法兼具轻量与可控性，尤其适合 Agent 本地执行环境。我们可以写一个上下文管理器，使用 Python 的 `sys.modules`、`builtins` 和 `os` 模块 hook，拦截 **open()、os 模块的所有路径操作**，并配合 `pathlib.Path.resolve()` 规范化路径，杜绝符号链接逃逸。

## 实现步骤：构建可重用的文件护栏上下文

### 1. 定义白名单目录集合与检查函数

白名单应该是**严格规范化**的绝对路径集合。为避免绕过，对任何输入路径都需转换为绝对路径且消除符号链接再判断。

```python
import os
from pathlib import Path

class FileGuard:
    ALLOWED_DIRS: set[Path] = set()

    @classmethod
    def configure(cls, *dirs):
        cls.ALLOWED_DIRS = {Path(d).resolve() for d in dirs}

    @classmethod
    def is_allowed(cls, target: Path) -> bool:
        resolved = target.resolve()
        return any(
            resolved.parts[:len(allowed.parts)] == allowed.parts
            for allowed in cls.ALLOWED_DIRS
        )
```

`is_allowed` 通过路径前缀匹配判断，只要目标路径的起始部分与白名单目录完全匹配就放行。需注意直接比较 parts 可能误判 /data2 与 /data，通过长度限制和完整 parts 相等来避免。

### 2. 拦截 builtins.open

替换全局 `open`，在打开文件前自动对路径做白名单判断。写入和读写都要拦截。

```python
import builtins

def _guarded_open(file, mode='r', *args, **kwargs):
    path = Path(file).resolve()
    if not FileGuard.is_allowed(path):
        raise PermissionError(f"Access to {path} is not allowed by file guard")
    return builtins.open(file, mode, *args, **kwargs)
```

注意，`open` 可能传入文件描述符（整数），这时直接放行（通常是由其他系统调用产生，已受控）。

### 3. 拦截 os 模块中的文件操作函数

仅拦截 `open` 还不够，`os.remove`、`os.rename`、`os.listdir`、`os.chdir` 等都可能绕过。我们需要 monkey-patch 整个 `os` 模块，在每个涉及路径的函数前加上相同的检查。可以维护一个需要拦截的函数列表：

```python
import os

WRAP_FUNCTIONS = ['remove', 'rename', 'listdir', 'chdir', 'unlink', 
                  'rmdir', 'mkdir', 'mkdirenv', 'symlink', 'link']

def _wrap_os_function(func_name):
    original = getattr(os, func_name)
    def wrapper(*args, **kwargs):
        # 第一个参数通常是路径
        if args and isinstance(args[0], (str, bytes, os.PathLike)):
            path = Path(os.fspath(args[0])).resolve()
            if not FileGuard.is_allowed(path):
                raise PermissionError(f"os.{func_name}: {path} is not allowed")
        return original(*args, **kwargs)
    setattr(os, func_name, wrapper)
```

对于 `symlink` 和 `link` 需要同时检查源和目标。更完整的是还要拦截 `os.path` 中的相关操作，但如果 hook 了 `os` 高级操作，路径拼接类函数不会实际修改文件系统，风险可控。同样，对 `shutil` 模块的 `copy`、`move`、`rmtree` 等也需要包裹。可以通过动态遍历 `shutil` 中涉及路径的函数进行代理。

### 4. 用上下文管理器启用和恢复

护栏不应全局常量生效，而应在执行自动化脚本时才激活，避免影响 Agent 框架自身的文件操作。我们使用上下文管理器，在进入时替换函数，退出时恢复原始状态。

```python
import contextlib

@contextlib.contextmanager
def file_guard(*allowed_dirs):
    FileGuard.configure(*allowed_dirs)
    # 保存原始引用
    original_open = builtins.open
    original_os_attrs = {name: getattr(os, name) for name in WRAP_FUNCTIONS}
    # ... 同样保存 shutil 等
    
    try:
        builtins.open = _guarded_open
        for name in WRAP_FUNCTIONS:
            _wrap_os_function(name)
        yield
    finally:
        builtins.open = original_open
        for name, orig in original_os_attrs.items():
            setattr(os, name, orig)
```

### 5. 在 Agent 执行处集成

当 Agent 生成并执行脚本时，用 `with file_guard("/home/user/agent_workspace", "/tmp/agent_tmp"):` 包裹 `exec()` 或 `subprocess.run()`。如果是子进程方式执行单独的 `.py` 文件，可以在生成的脚本头部注入“文件护栏激活代码”，即通过写入一段 `import guard; guard.activate(...)` 来让子进程也受控。不过更简单的做法是确保只在同一个 Python 进程内执行动态代码，避免子进程绕过。

## 踩坑点与解法

1. **相对路径逃逸**  
   攻击者可以传入 `../../etc/passwd`。解决方案是始终 `resolve()` 转换成绝对路径，禁止在检查前使用相对路径。同时拦截 `os.chdir`，防止通过改变工作目录来影响相对路径评估，或者干脆禁用 `chdir`（许多自动化场景不需要切换目录）。

2. **符号链接绕过**  
   如果白名单目录内存在指向白名单外目录的符号链接，`resolve()` 会跟随符号链接，解析成真实路径，从而导致被拦截。这可能是预期行为，但也可能破坏正常功能。如果业务上需要允许访问符号链接指向的目标，应通过配置单独声明。默认情况下，`resolve()` 的严格行为恰好能防止此类逃逸。

3. **`open` 多种参数形式**  
   `open` 可接受文件描述符、`Path` 对象、包含 fd 的整数等。我们在包装函数中必须小心处理类型，对整数 fd 直接放行；对路径类参数则检查。

4. **内置模块缓存与子线程**  
   修改 `os` 模块会影响所有线程，如果想要线程局部限制，需要引入 TLS 变量，复杂度增加。多数 Agent 执行是同步的，这个影响可控。此外，某些 C 扩展级的文件操作可能绕开 Python 层面 hook，此时需要结合 `audithook`（Python 3.8+）或更底层的限制，但日常场景不多见，暂不构成主要威胁。

5. **`shutil` 等高级库**  
   这些库底层通常调用 `os` 模块函数，因此只要 `os` 层被 hook，`shutil.rmtree` 等也会在删除文件时触发检查。但拷贝操作 `shutil.copy` 在内部使用 `open` 和 `os` 函数，同样会被拦截。建议在测试中实际调用这些库以验证完整性。

## 可复用建议：将护栏封装为独立模块

将上述逻辑封装成一个 pip 包 `agent_file_guard`，提供 `FileGuard` 类和 `file_guard` 上下文管理器，并支持 JSON/YAML 配置文件定义白名单。项目里只需：

```python
from agent_file_guard import file_guard

# 在 Agent 执行代码前
with file_guard("/data/agent_jobs", "/tmp/safe"):
    exec(generated_code)
```

同时，可以在护栏模块中加入审计日志，记录所有被拦截的越权尝试，便于调试和监控。对于生产环境，建议配合 `logging` 输出详细拦截信息，必要时触发告警。

## 总结

给自动化脚本加上本地目录白名单，是实现 Agent 文件访问最小权限的工程化、低成本方案。它不依赖重量级容器，直接在 Python 运行时层面织入路径检查，可以有效防御无心的错误和有意的路径遍历攻击。

需要认清的是，这种 hook 方案并非绝对安全，它局限于纯 Python 代码且在同一进程内执行的情况，无法防御 C 扩展或外部原生程序。若你的 Agent 会调用任意命令行工具，仍应配合进程级沙箱。但作为第一道防御线，目录白名单护栏能够拦截绝大多数“自动化错误”，让 Agent 的行为变得可预期、可审计。
