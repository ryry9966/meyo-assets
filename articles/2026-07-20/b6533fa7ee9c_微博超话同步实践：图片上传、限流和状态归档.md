## 背景

在维护多个微博超话的过程中，定期发布带图文的内容是一项重复性很高的工作。手动操作不仅耗时，还容易遗漏关键节点，尤其跨多个超话时，登录、选图、传图、编辑帖文、发布这一连串动作的边际成本非常高。于是我尝试用脚本实现一套可控的同步流程，让超话内容发布变得可追溯、可暂停、可恢复，而不是简单地“一把梭”。

这个脚本长期运行在本地或一台低配 VPS 上，面向的不是高并发场景，而是低频、长周期的日常运营。它在设计上更接近一个带状态管理的 Agent：每次任务启动时检查待发列表，按规则执行动作，并在事后归档结果。下面记录的就是在这个过程中，关于图片上传、限流策略和状态归档的关键实践。

## 问题拆解

微博超话发帖的链路大致可以分为三步：

1. 获取超话的发帖权限与基本信息（超话 ID、等级要求等）。
2. 上传图片，获取服务端返回的 `pid`。
3. 携带 `pid` 与帖文内容，调用超话发帖接口完成发布。

看起来简单，但真实场景中会遇到几个典型问题：

- **图片上传有时效性**：从上传图片到实际发帖之间的时间窗口不能太长，否则 `pid` 可能失效或被回收。
- **超话级与账号级限流**：每个超话每日有发帖/评论数量上限，账号整体也有操作频率限制，跨超话调度时需要分别跟踪。
- **状态不明**：发帖接口返回的成功并不代表帖子一定展示，后续仍可能被反垃圾策略过滤。因此每次操作都需要记录详细上下文，方便回溯和补发。
- **登录态维护**：Cookie 过期或风控策略变化会导致接口返回异常，需要能够感知并报警。

## 做法与步骤

### 1. 登录态与请求封装

使用 `requests.Session` 保持 Cookie 持久化，并定期从本地文件恢复。登录采用扫码方式手动完成，获取的关键 Cookie 字段写入 `.weibo_cookies.json`，脚本启动时加载。对于每次请求，统一添加 `Referer` 与 `User-Agent`，降低被风控的概率。

### 2. 超话信息获取

通过微博的公开接口获取超话列表及对应的 `topic_id`，同时检查当前账号在目标超话的等级。这一步可缓存结果，避免每次发帖前都全量拉取。

### 3. 图片上传

这是最容易出错的环节。微博网页版上传图片的实际地址是 `https://picupload.weibo.com/interface/pic_upload.php`，参数较为复杂，除了图片二进制数据外，还需要 `cb`、`mime`、`pid` 等多个字段。上传时必须带上从页面解析得到的 `crossdomain` 参数和 `referer`，否则会返回 `-100` 或 `-200` 错误。

为降低失败率，我做了以下几点：

- 图片大小统一处理到 5MB 以内，格式转为 `jpg`。
- 上传请求的 `headers` 完全模拟浏览器，包括 `Origin` 与 `X-Requested-With`。
- 使用 `multipart/form-data` 构造表单，确保文件名包含在 `Content-Disposition` 中。
- 上传成功后立即记录 `pid` 与上传时间戳，并在 10 分钟内使用该 `pid` 发帖，否则标记为过期并触发重新上传。

### 4. 发帖接口与限流策略

发帖接口需要构造 `topic_id`、`content`、`pic_id`（即 `pid`）、`visible` 等参数。每次调用前，检查两个维度的限流标记：

- **超话维度**：在本地 SQLite 中维护每个超话的每日已发帖计数，达到上限后该超话当日不再调度，并记录提醒。
- **账号维度**：全局请求计数器，单次图片上传后至少间隔 2 秒，发帖后间隔 5～8 秒，避免触发频率限制。如果接口返回“操作太频繁”之类的错误码，触发指数退避，最长等待 5 分钟。

### 5. 状态归档

每次发帖行为都写入状态表，字段包括：

- 目标超话 ID、帖文摘要、图片本地路径及上传后的 `pid`
- 接口返回的原始响应体、状态码、时间戳
- 是否确认展示（后续可通过爬虫回查）
- 重试次数与最后错误原因

这张表的作用是事后回溯，而不是实时监控。当某条内容疑似未成功展示时，可以通过状态表定位到具体接口返回，判断是参数问题、限流问题还是反垃圾过滤，然后决定是否换号重发或调整内容。

## 踩坑记录

**图片上传返回 `-200` 未登录**  
即便 session 中的 Cookie 看似有效，仍可能因缺少页面级的 `crossdomain` 校验字段而失败。解决方案是从发帖页的 HTML 中提取 `crossdomain` 并存入请求参数，同时确保 `Referer` 与 Cookie 属于同一域。

**超话发帖返回“今日已发帖上限”**  
微博不同超话的发帖上限并不完全相同，部分冷门超话限制更严。脚本需要能处理这种非标错误，将其归类为“超话级限流”，避免错误重试导致账号被限制。

**`pid` 过期导致发帖失败**  
早期版本上传图片和发帖之间存在太长的队列等待时间，导致部分 `pid` 失效。改为“即传即发”的模式后，这个问题基本消失。

## 可复用建议

1. **将登录态管理独立出来**：不要把登录逻辑混杂在业务代码里，支持从文件恢复 Cookie，并在检测到失效时主动通知人工重登。
2. **分级限流，本地状态表先行**：不要指望平台按规矩返回明确的限流提示，用本地计数器做第一道防线。
3. **状态归档用轻量数据库**：SQLite 足够，无需引入外部依赖。保留原始响应信息，未来排查成本会低很多。
4. **为上传播放准备备用路径**：不同账号、不同 IP 可能遇到不一样的风控策略，多准备一两个备用账号和出口 IP 可以提升整体可用性。
5. **不要挑战平台底线**：这种自动化应严格控制在个人运营所需的低频场景，切忌做高频、批量发帖或营销推广。

## 总结

这次实践本质上是在没有开放 API 的情况下，通过逆向和状态管理，把一个重复性手工流程改造成可监控、可恢复的自动化任务。整个系统的核心不是“发得快”，而是“每步可查、异常可追溯”。在 OpenClaw / Agent 的语境下，这类带状态的脚本其实就是最务实的自动化起点：定义清楚每一步的输入输出和失败分支，让机器做它擅长的事，把决策和异常处理留给人类。
