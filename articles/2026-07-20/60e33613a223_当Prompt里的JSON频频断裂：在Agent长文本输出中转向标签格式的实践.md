## 背景

在构建 OpenClaw 社区常见的 Agent 工具链时，有一个非常普遍的诉求：让 LLM 生成一大段需要后续程序解析的结构化内容，比如一份摘要报告、多步骤操作指令，或者复合工具调用的返回结果。多数人的第一反应是让模型输出 JSON，然后 `json.loads` 一把梭。这个路径在一开始跑通 Demo 时都没问题，但随着真实场景里上下文变长、输出内容变复杂，我们开始频繁碰到 JSON 损坏导致管道阻塞。

更令人头疼的是，这些坏掉的 JSON 并不是偶发 bug，而是系统性地出现：模型在几百个 token 后遗漏一个引号，数组的最后多了一个逗号，或者因为流式解码导致某个键值对写到一半被截断。由于 JSON 的容错性极差，只要一处不合语法，整个文档就无法解析。对于一个需要 7×24 小时无人工介入的自动化 Agent，这种脆弱性让人难以接受。

我们团队在几个内部项目中陆续尝试了多种替代方案（包括约束解码、Few‑shot 修补、正则修复器），最终落到了一种看似原始但在工程上非常稳定的方案：**自定义 XML‑like 标签格式**。这篇文章将复盘完整的决策过程、落地方式、踩过的坑，以及可复用的设计模板。

## 问题：JSON 为什么在长文输出中容易翻车

错误的根本原因并不复杂。LLM 本质上是概率采样的文本生成器，**它对结构形态的“记忆”会随着输出长度的增加而弱化**。当模型在生成了一段 500 词的分析后需要输出 `"conclusion": "..."`，它可能连这个字符串是否已经闭合都记不清了。另外，许多本地部署的模型在微调阶段并没有被特意训练过长 JSON 的生成，遇到键值嵌套时容易像人类打字一样出错。

更具隐蔽性的是流式解析场景。当 Agent 使用 SSE 流接收输出，并希望逐 chunk 解析 JSON 以实时展示结果时，前面所有关于 JSON 完整性的假设都会变得无比苛刻。哪怕模型本身生成了一个完美的 JSON，只要一个 chunk 在网络中延迟，半棵 JSON 树就会解析失败。多数团队最后选择在流完全结束才解析，但这依然无法解决 JSON 本身的语法脆弱性。

## 转向标签格式的工程化方案

我们选择的自定义格式看起来像这样：

```
<response>
<title>OpenClaw v0.3 更新日志摘要</title>
<actions>
- 重构了 MCP 连接池
- 添加了工具调用超时熔断
</actions>
<summary>
本次版本更新聚焦稳定性，解决了高并发下的连接泄漏问题...
</summary>
</response>
```

### 1. 标签 Schema 设计原则

- **顶层必须有一个唯一的根标签**（如 `<response>`），作为提取边界。
- **字段内容使用独立的子标签**，避免在内容里直接使用前缀后缀标记（如 `--- TITLE ---`），后者极容易和正文中的类似文本混淆。
- **内容可以是多行纯文本、Markdown 甚至嵌入列表**，不必像 JSON 那样将长文本硬塞进字符串并转义引号、换行符。
- 如果内容里可能出现 `<` 或 `</`，可以要求模型使用 CDATA 区段，但实测极少有模型会在普通文本描述中输出 `<title>` 这样的标签，可以暂时忽略。

### 2. Prompt 侧的调整

在 System prompt 里明确告知模型输出格式，并给出最少一个完整示例。关键点是让模型知道**这是一个必须遵守的合同**，而不只是“建议”。我们常用的 Prompt 片段：

```
你必须严格按照以下标签格式输出，不得添加额外解释，也不得更改标签名称：
<response>
<title>简短标题，不超过一行</title>
<actions>
- 每行一个行动项
</actions>
<summary>
一段完整的中文摘要，可以包含多段落。
</summary>
</response>
```

注意：这里要求模型不要输出任何包裹在格式外的文字，否则解析需要先截断噪音。

### 3. 解析器的实现思路

虽然 XML 库在标准 Python 中可用，但我们实践中更倾向于使用**正则表达式提取标签内容**，因为它对不完美的结构有更高的容忍度（可以处理标签未完全闭合、内容中夹杂无效字符的情况）。核心代码非常简单：

```python
import re

def parse_tagged(text: str, root: str = "response") -> dict | None:
    pattern = rf"<{root}>(.*?)</{root}>"
    match = re.search(pattern, text, re.DOTALL)
    if not match:
        return None
    body = match.group(1)
    # 提取常规子标签
    result = {}
    for field in ["title", "actions", "summary"]:
        m = re.search(rf"<{field}>(.*?)</{field}>", body, re.DOTALL)
        if m:
            result[field] = m.group(1).strip()
    return result if result else None
```

这段代码不会因为多一个换行符或少一个空格而崩溃。即使模型在 `<summary>` 标签里写了 Markdown 表格，仍然可以安全提取整个字符串交给下游处理。

## 在实践中踩过的坑

### 坑1：模型偶尔会输出“不完整根标签”

当模型生成长文本时，可能会在 `<response>` 输出一半时达到 max_tokens 限制，导致缺失 `</response>`。此时正则提取返回 None。针对这种情况，我们加入了一个 fallback：如果没找到闭合根标签，就尝试从开头提取 `<title>` 等子标签，只要得到任何一个字段就当作有效结果；如果全部失败，则将全文作为 `raw` 字段返回，交给人工或二次处理。

### 坑2：内容中意外出现“</summary>”类的字符串

这会导致提取被截断。一种粗暴有效的做法是：使用非贪婪匹配并取第一个闭合标签，然后对提取结果进行长度过滤，如果明显过短（例如小于 10 字符），则丢弃并记录告警。更专业的手段是要求模型将特殊字符写入 CDATA 块，但 Agents 里很少需要这么高级的操作。

### 坑3：流式输出时的消费模式

标签格式对流式解析友好得多，因为你可以构建一个简单的状态机：当遇到 `<response>` 进入收集状态，再根据标签开始/结束事件分派数据。我们实现了一个 `TagStreamParser`，它实时回调每个字段的完整内容，前端可以据此渲染进度，而不用等待整个响应完成。这和平时 JSON 流式解析的复杂程度完全不是一个量级。

## 可复用的建议

- **不要把标签格式用于严格嵌套的数据结构**。如果数据是多层对象数组，JSON Schema + 约束解码（如 Guidance、LMQL）仍是更好选择。标签格式最适合那些以长文本为主、附带你希望在代码中引用的元数据的输出场景。
- **在 Agent 链中统一采用这种“弱结构化”中间层**。让模型输出标签包裹的 Markdown 报告，再由下一级节点使用更精确的工具（如函数调用）提取结构化表格，可以大幅降低单次生成的严谨性要求，提升管道整体吞吐。
- **将解析器作为独立组件**，并暴露可配置的回退策略。例如：优先解析标签格式，失败则尝试从输入中剥离 Markdown 代码块再解析，最后回退到全文。这样即使 prompt 漂移，系统也不至于立刻瘫痪。
- **在模型评估中加入格式稳定性指标**。我们可以用重复运行 50 次、统计成功解析率的方式来度量某个模型的长文格式遵从能力，这比单次人工评判可靠得多。

## 总结

从坏掉的 JSON 迁移到自定义标签格式，本质是把**从模型获取结构化数据的容错责任，从生成端转移到了解析端**。生成端（LLM）永远不可能 100% 遵守语法，但解析端可以采用更宽松的匹配策略。在一个工程化的 Agent 系统中，把脆弱的假设推到解析层，用少量代码容忍格式瑕疵，比反复修复 Prompt 和模型行为来得更经济。

对于 OpenClaw 社区中那些已经在和 Agent 打架的开发者来说，如果你发现当下游程序因为一个莫名的逗号而整个夜里的批跑失败，不妨花半天时间切换到标签格式——它也许看起来不够“性感”，但生产环境中的目标从来就不是代码的优雅程度，而是天亮了还剩多少头发。
