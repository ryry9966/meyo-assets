## 背景

在 Agent 辅助内容生产的场景里，“生成即发布”的模式越来越常见。OpenClaw 之类的工具链可以复述 prompt、调用图片生成服务、整理多段文案，最后直接推送到 WordPress、微信公众号、Twitter 等多个渠道。但一旦发布完成，生成的文章、配图和元信息往往就散落在 Agent 会话记录、临时目录或 CDN 上，缺少“落盘”归档。当我们需要回溯某篇帖子、迁移平台、或者基于历史内容构建知识库时，才发现资产已经丢失或者元信息不全。

因此，一个可靠的本地归档步骤是必要的——它应当能够在自动发帖流水线中无感运行，完整保存文章 Markdown、所有图片文件，并附带一份结构化的 `assets.json`，为后续的检索、复用和版本管理提供基础。

## 要解决的问题

- **资产分散**：正文在 log 里，图片只有外部 URL，没有本地副本。
- **元信息缺失**：不知道哪张图是封面、内嵌还是 SEO 用的社交卡片，无法自动化二次处理。
- **目录结构混乱**：不同帖子保存方式不统一，难以批量操作。
- **与流水线解耦不足**：归档逻辑耦合在发布脚本里，更换平台时需要重写。

## 归档方案设计

我们采用以 post slug 为单位的目录结构，所有资产自包含在一个文件夹内，便于迁移和备份。

```
posts/
└── my-first-automated-post/
    ├── article.md
    ├── images/
    │   ├── cover.png
    │   ├── diagram.png
    │   └── inline-01.png
    └── assets.json
```

### article.md

标准 Markdown 文件，图片引用使用相对路径 `./images/xxx.png`，确保文件夹自包含，不依赖任何外部链接。在发布前，可以通过脚本将相对路径替换为对应平台的图片 URL；归档时则保留相对路径。

### images/

所有图片本地化保存。来自图片生成服务（例如 Midjourney、DALL·E、Stable Diffusion WebUI）的图片需要在归档步骤中下载到该目录。文件名统一小写、使用有意义的命名（如 `cover.png`、`flowchart.png`），避免使用自动生成的随机字符串。

### assets.json

这是一个关键的结构化清单，记录帖子及所有关联资产的元信息。推荐结构如下：

```json
{
  "slug": "my-first-automated-post",
  "title": "My First Automated Post",
  "description": "简短的摘要或 open graph description",
  "tags": ["automation", "openclaw", "mcp"],
  "created_at": "2025-04-06T10:30:00Z",
  "language": "zh",
  "article_file": "article.md",
  "images": [
    {
      "file": "images/cover.png",
      "type": "cover",
      "alt": "Automation pipeline architecture diagram",
      "width": 1200,
      "height": 630,
      "mime_type": "image/png"
    },
    {
      "file": "images/diagram.png",
      "type": "inline",
      "alt": "Workflow of local archiving",
      "width": 800,
      "height": 600,
      "mime_type": "image/png"
    }
  ]
}
```

- `images` 数组中 `type` 字段（`cover`、`inline`、`opengraph`、`thumbnail` 等）明确每张图片的用途，方便发布脚本根据平台要求选择合适图片。
- 宽高尺寸等信息可用于生成响应式 `srcset` 或验证平台图片限制。

## 在自动发帖流水线中集成

我们可以将归档步骤设计为一个可复用的 MCP 工具或一个独立脚本，放在内容生成之后、多渠道发布之前执行。

### 使用 MCP filesystem 服务器

OpenClaw + MCP 生态提供了标准的 `filesystem` 服务器。在 Agent 的任务流程中，我们可以指示 Agent：

1. 生成文章 Markdown 内容，并得到所有图片的临时 URL。
2. 调用 `filesystem` 的 `write_file` 创建 `posts/{slug}/article.md`。
3. 对每个图片 URL，使用一个“下载并保存到本地”的工具（或者让 Agent 通过 shell 运行 `curl` 或 `wget`）将图片写入 `images/` 目录。
4. 组装 `assets.json` 的 JSON 对象，再通过 `write_file` 写入。

实际实践中，由于 MCP 的 `filesystem` 服务通常不能直接下载网络资源，我们需要一个额外的 MCP server 或本地命令来完成下载。例如可以配置一个简单的 `fetch-to-file` MCP 工具，或者直接让 Agent 执行 shell 命令：

```bash
curl -o posts/my-first-post/images/cover.png "https://image.cdn.example.com/abc.png"
```

然后在 agent prompt 中明确要求：所有图片必须下载到本地并更新 `assets.json`。

### 使用独立归档脚本

更工程化的做法是编写一个 Python/Node.js 脚本，读取一个中间 JSON（包含标题、slug、内容、图片 URL 列表），然后自动完成目录创建、文件写入与清单生成。这个脚本可以作为流水线的一个固定步骤，与具体的发布 Action 解耦。

举例：Agent 输出一个 `build_artifact.json`，再由 `archive.py` 消费：

```json
{
  "slug": "my-post",
  "title": "...",
  "markdown": "...",
  "images": [
    {"url": "https://...", "type": "cover", "alt": "..."}
  ]
}
```

`archive.py` 解析后执行归档，并将完成状态写回，确保可观测。

## 踩坑点

1. **网络图片不稳定**  
   外部图片 URL 可能有时效性（例如 DALL·E 生成的图片链接仅在数小时内有效）。必须在生成后立即归档下载，避免过期后无法获取。

2. **文件名冲突与特殊字符**  
   slug 中可能包含特殊字符，需要做安全化处理（只保留字母、数字、连字符、下划线）。图片原始文件名可能包含空格或中文，下载时应重命名为预设的名称。

3. **assets.json 的同步**  
   如果后续手动补充了图片或修改了文章，很容易忘记更新 `assets.json`。建议提供 `rescan` 脚本，能够重新扫描目录结构并根据现有文件更新清单。

4. **大图与尺寸控制**  
   生成的高分辨率图可能体积很大，归档时最好同时生成一份压缩的缩略图，并在 `assets.json` 中记录原始图和缩略图的路径，便于发布时按需选用。

5. **Git 版本控制**  
   将 `posts/` 目录纳入 Git 仓库时，图片文件会使仓库体积迅速膨胀。建议使用 Git LFS 或定期打包备份，同时 `.gitignore` 中至少排除原始大图，仅保留压缩后的版本。

## 可复用建议

- **将归档逻辑封装为标准 MCP 工具**：编写一个 `local-archiver` MCP 服务器，提供 `archive_post` 方法，接受 slug、markdown、图片 URL 列表等参数，自动完成目录创建、下载与 `assets.json` 写入。这样任何基于 MCP 的 Agent（不仅限于 OpenClaw）都可直接调用。
- **发布与归档分离**：提供一个“发布适配器”脚本，读取本地归档目录和 `assets.json`，根据目标平台（WordPress、Hexo、微信公众号）生成对应的发布 payload。这样更换平台时只需修改适配器，归档层保持稳定。
- **CI 自动归档**：如果使用 GitHub Actions 或类似 CI/CD，可以在生成内容的 step 后添加归档 step，并将 `posts/` 目录上传为 artifact 或推送到专门的归档仓库，实现无人值守归档。
- **可选的静态站点生成**：归档目录结构天然兼容 Hexo、Hugo 等静态站点生成器。加上 frontmatter 后可直接生成个人博客或知识库，进一步提升资产价值。

## 总结

给自动化内容流水线加入本地归档步骤，成本很低，收益却很实在——把所有文章、图片、元信息落盘为自包含的文件夹，不仅提升了可回溯性，也为跨平台发布、二次创作和长期维护打下了干净的数据基础。结合 OpenClaw 的 Agent 能力和 MCP 文件工具，可以零摩擦地将归档嵌入现有流水线，让自动化不再“一发即忘”，而是有积累、可管理的数字资产。
