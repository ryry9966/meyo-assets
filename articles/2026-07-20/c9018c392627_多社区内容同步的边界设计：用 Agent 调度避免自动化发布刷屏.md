## 背景

在 OpenClaw 等 Agent/MCP 社区里，用自动化机器人将一篇新文章、一次版本更新、一条实验记录同步到 Discord、Slack、Telegram、Twitter、论坛等多个社区，已经是常见操作。这类工具往往基于标准 MCP 插件，将“发送消息”封装成 Tool，再由 Agent 在特定事件触发时调用。初期体验很顺畅，直到几个版本迭代后，群友开始抱怨：“同一个更新，Bot 在三个频道各发一遍，还带转发，根本是刷屏。”

刷屏不只消耗社区成员的注意力，更危险的是，很多平台会对重复、高密度推送做账号标记、入沙盒甚至封禁。作为实践者，我们需要在自动化发布管道中加入一套可控的“边界”，而不是简单地 `for platform in platforms: send(msg)`。

## 问题拆解：为什么自动发布变成了刷屏

刷屏的根源是三个缺失：

1. **去重缺失**：同一内容的多个触发事件（比如 Git webhook + RSS 抓取 + 手动测试）分别触发了发布动作，没有一条记录比对“这条内容是不是已经在窗口内发过”。
2. **频率控制缺失**：多个平台几乎同时收到消息，用户在不同渠道被反复提醒，本质上是一次信息爆炸被多次放大。
3. **聚合缺失**：低频但重要的更新（如每周进展）和高频琐碎信息（如 issue 评论）混在一起，没有汇总为摘要，反而条目式堆砌。

设计目标很明确：为自动发布设定边界——在同一时间窗口内，同一内容在所有社区的总曝光次数应最少且合理。

## 做法：实现一个基于 MCP 的发布调度边界

### 1. 内容指纹与去重窗口

为每条待发布内容计算指纹（`fingerprint = sha256(title + 正文前 512 字符 + 所需平台列表排序后拼接)`）。将该指纹写入 Redis，并设置 TTL 等于去重窗口长度（如 6 小时）。每次调用前检查指纹是否存在，若存在则直接丢弃，返回 `ignored` 状态给 Agent。

使用标题和前 512 字符而非全文哈希，是为了容忍文末的署名、声明等非关键变更；同时配合 SimHash + 汉明距离，可以将“仅改了几个错别字”的情况归并，避免因微小编辑导致重复推送。实践中，我建议至少在指纹策略中忽略自定义时间戳和 UUID 尾部。

### 2. 平台优先级与间隔发送

将目标平台划分为两组：**即时通道**（如特定频道的 Discord 消息、微博）与**汇总通道**（如论坛帖子、每周邮件）。即时通道采用固定间隔（每个平台间隔 30 秒 – 2 分钟，视 API 限制调整）顺序发送，并在中间插入短暂的随机延迟，避免因时间戳过于规律被反爬策略拦截。汇总通道则不触发单条推送，而是将内容写入“每周摘要队列”，由另一个定时任务统一打包发送。

在 MCP server 侧，我实现了一个 `schedule_publish` 工具，其参数包含：
- `fingerprint`
- `platforms[]`
- `group` (instant / digest)
- `dry_run`

工具内部会先检查指纹、判断窗口期，再根据分组放入对应队列或立即调度。

### 3. Agent 决策与人工干预接口

Agent 作为调度的大脑，可以通过提示词约束：“除非用户明确指令覆盖，否则必须遵循调度边界”。同时提供一个 `force_push` 工具，供管理员紧急绕过所有限制，但该工具会强制写审计日志并通知管理员。这样既保持了自动化的流畅，也留有紧急通道。

## 踩坑实录

**踩坑 1：平台限流与重试风暴**  
Discord 的全局速率限制（global rate limit）和 Twitter API v2 的 429 响应，在密集发送时极容易触发。最初用简单的指数退避重试，结果堆积的重试任务导致了二次风暴。后来改为：发送器在收到 429 时，将受影响平台标记为“冷却”，暂停该平台所有待发任务，并根据响应头 `Retry-After` 设置一个恢复定时器。

**踩坑 2：消息格式转换器维护成本**  
跨平台渲染 Markdown 差异巨大：Slack mrkdwn 不支持嵌套列表，Telegram 的 MarkdownV2 需要转义特殊字符，Twitter 仅支持纯文本 + 链接。如果手动维护 if-else 模板，很快会变成屎山。建议抽象一个 `MessageFormatter` 管道，按平台类型加载模板，并支持 `dry_run` 时预览渲染结果。切换平台只需新增一个 formatter 文件。

**踩坑 3：指纹窗口与时效性冲突**  
六小时的去重窗口意味着如果发布后发现重大错误需要快速修正并重推，会被直接 ignore。解决方案是在指纹键上打一个 `priority` 标记，紧急修正可以携带 `force=true`，此时只检查 15 分钟窗口，并可集成一条附加说明（如“【更正】”）自动附加到消息前。但滥用 force 会带回刷屏问题，所以审计日志会记录每次 force 调用并生成每周报表。

**踩坑 4：dry-run 不够真实**  
早期 dry-run 只模拟指纹检查，不检验消息长度、平台限流状态。导致一次 dry-run 通过后，实际发送时因为消息正文 + 链接超出 Discord embed 限制而失败。修复方式是将格式校验、长度裁剪和当前限流状态一并在 dry-run 中执行，并把预发布的完整样例返回给 Agent 做最终确认。

## 可复用建议

- **把发布边界封装成 MCP Tool**：一方面能让不同的 Agent 复用同一调度逻辑，另一方面便于测试和 mock。
- **设置多级配置**：通过环境变量定义默认窗口长度、平台优先级、静默时段（如 UTC 2:00-6:00 不发送非 urgent 消息），不同社区可使用不同配置文件。
- **审计与回放**：所有发布决策（包括忽略、聚合、force）记录结构化日志，最好接入 sqlite/PostgreSQL，提供 `recent_decisions` 工具让管理员查看最近 48 小时的调度结论，避免“为什么没发”的沟通成本。
- **静默模式**：提供全局 `mute_until` 设置，当社区有其它重大活动时，可以临时挂起自动推送，防止信息夹击。
- **测试 checklist**：每接入一个新平台，务必执行一次带真实 API 的 dry-run，检查格式、长度、特殊字符转义和限流恢复流程。

## 总结

自动化发布的目的不是“触达所有人”，而是“在合适的时间以合适的形式传递给需要的人”。为内容管道加入去重、频率控制和聚合摘要，并非限制效率，而是在保护社区成员的注意力与平台账号的信誉。在 OpenClaw 和 MCP 生态中，我们完全可以用几个标准化的 Tool 和一条清晰的调度链，把“刷屏 Bot”变回可靠的数字助理。

设定边界，才是对自动化最大的尊重。
