# 自动发帖流水线本地归档实战：从散落资产到有序归档

## 背景

如果你用 OpenClaw 编排 Agent 自动生成社交媒体内容（如小红书帖子），很可能经历过这样的循环：Agent 生成一段文字、自动配图、调用发布工具，然后一切都消失在黑盒里。等你想复盘某条高互动帖子的原始提示词、复查图片质量或构建训练数据集时，发现只有平台的后台截图，真正“干净的”资产早已不可追溯。

本地归档不是“锦上添花”，而是让自动化内容管线从一次性工具走向可持续系统的关键一环。这篇文章聊的是：如何为你的 Agent 发帖管线设计一套可靠、低摩擦的本地归档方案，覆盖文章、图片和 `assets.json` 元数据。

## 问题拆解

一个典型的发帖流水线会输出三类资产：
- **文本内容**：可能是 Markdown 格式的文案，也可能包含话题、标题等结构化字段。
- **图片资源**：通常是远程 URL（如 OSS 临时链接），容易过期且无法保证后续可用。
- **发布参数**：包括生成时间、使用的模型、prompt 版本、Agent 状态等，这些元数据若不刻意保存，很快就会丢失。

如果只是随便往文件夹里丢文件，很快会遇到命名冲突、图片缺漏、 `assets.json` 膨胀到无法解析、并发写入损坏等问题。

## 工程化归档方案

### 1. 定义资产清单结构

采用一个轻量的 `assets.json` 文件记录每次生成任务的原子数据，而不是把所有历史塞进一个大 JSON。推荐单文件记录一次任务，或者用 JSONL 追加。以一次发帖为单位的结构：

```json
{
  "task_id": "20250411-a3f2b",
  "created_at": "2025-04-11T07:12:00Z",
  "model": "gpt-4o",
  "prompt_version": "v2.1",
  "post": {
    "title": "...",
    "body_md": "posts/20250411-a3f2b.md",
    "images": [
      "images/20250411-a3f2b-cover.jpg",
      "images/20250411-a3f2b-img1.jpg"
    ]
  },
  "published": false
}
```

`task_id` 用日期+短哈希，保证可排序且避免碰撞。Markdown 文件和图片文件的路径使用相对路径，整个归档目录可以整体迁移。

### 2. 文章归档

将生成的 Markdown 原文持久化到 `posts/` 目录。文件名来自 `task_id`，例如 `posts/20250411-a3f2b.md`。这样做的好处是仅凭文件名就能反查任务记录，也方便脚本批量处理。

关键点：写入时必须保证原子性。最简单的做法是先写临时文件，再 `os.rename`（在 POSIX 上是原子操作）：

```python
tmp = f"posts/.{task_id}.tmp"
with open(tmp, "w") as f:
    f.write(content)
os.rename(tmp, final_path)
```

### 3. 图片下载与内容寻址

远程 URL 可能包含随机字符串，并且随时失效。因此生成结束后立即下载图片，并用内容哈希（SHA256 前 12 位）重命名，避免重复存储完全相同的图片。

步骤：
- 计算图片内容的 SHA256，取前 12 位作为标识。
- 保存为 `images/{hash}.jpg`。
- 在 `assets.json` 中记录该相对路径。

Python 示例片段：

```python
import hashlib, requests

resp = requests.get(url, timeout=10)
resp.raise_for_status()
img_hash = hashlib.sha256(resp.content).hexdigest()[:12]
img_path = f"images/{img_hash}.jpg"
with open(img_path, "wb") as f:
    f.write(resp.content)
```

若图片下载失败，可记录到 `assets.json` 的 `errors` 字段，并设定重试逻辑（如 3 次指数退避）。

### 4. 流水线集成

在 OpenClaw 的管线上，通常可以在“内容生成→后处理→发布”之间插入一个归档步骤。如果使用 MCP 工具，可以封装一个 `local_archive` 工具，接收生成结果并写入文件系统。这样无论后续发布是否成功，资产已安全落地。

一种典型的编排顺序：
> 内容生成 → 图片生成/检索 → **本地归档** → 人工审核（可选）→ 发布

## 踩坑实录

- **assets.json 膨胀**：如果所有记录都写进一个 JSON 文件，几百次迭代后解析就会变得很慢。解决方案是改用 JSONL 每天一个文件，或直接上 SQLite（轻量且支持并发读）。
- **并发写入损坏**：多个 Agent 并行运行时，不加锁直接写同一个 JSON 会导致文件损坏。改用文件系统上的单文件记录、或基于数据库的事务，可以根治。
- **文件名跨平台问题**：Windows 下路径分隔符、保留字符容易踩坑。统一使用 POSIX 风格相对路径（`/`），在代码中处理平台差异。
- **图片下载超时与内存占用**：大图下载可能把内存撑爆，需要流式写入，并对大小设置上限（如 10 MB）。超时要重试，但避免无限重试耗尽资源。
- **占位图与失败处理**：若图片下载彻底失败，保留一个本地占位图，并在元数据中标记 `image_error: true`，方便后续人工补全。

## 可复用建议

1. **封装成 MCP 工具或独立 Python 模块**  
   输入：任务 ID、Markdown 文本、图片 URL 列表。输出：写入本地归档并返回状态。这样可以很方便地在任何 Agent 管线中插拔。

2. **使用内容哈希管理图片去重**  
   不仅节省磁盘，还能快速判断“新图”还是“旧图复用”，在生成统计或成本分析时有用。

3. **设计可演进的元数据 schema**  
   用 JSON 时预留 `extra` 字段，后续加字段不需要破坏现有记录。也可以考虑用 Pydantic 模型校验。

4. **定期压缩与清理**  
   比如保留最近 90 天的原始大图，更早的图片可转存为 WebP、降低分辨率后封存。编写 cron 脚本自动执行。

5. **版本控制可选**  
   如果把归档目录纳入 Git（图片用 LFS），每次成功生成自动 commit，历史回溯会更方便，但要注意仓库大小。

## 总结

本地归档是自动化内容流水线的“黑匣子”。它不需要复杂的基础设施，几个小文件 + 一条 JSONL 就能帮你省去未来大量人工恢复的成本。对于 OpenClaw 这类 Agent 编排工具的使用者来说，把归档做成管线中的固定步骤，就像给代码加单元测试一样，刚开始是约束，后来就是安全感。

**没有归档的 AI 内容管线，终将变成无法复盘的熵增现场。**
