## 背景

给 Agent 或自动化流水线里的 LLM 安排「生成长文+结构化提取」任务，最常见的设计就是让模型输出 JSON——字段清晰，解析方便，上下游容易对接。 这个想法在短输出时基本没毛病，可一旦让模型生成几百行以上的周报、分析摘要、多段落翻译、或者分节长篇文档，问题就接连不断：缺少逗号、字符串里忘转义的引号、多行文本里混进了换行符、数组括号不匹配…… 任何一个低级错误，都能让整个 JSON 对象解析失败，把整条流水线卡死在 `JSONDecodeError` 上。

更要命的是，长文场景下重复几次重试很可能耗尽 token 预算，而返回的错误信息对普通用户几乎没用。社区里不少 OpenClaw 和 MCP 工具链的用户都踩过这个坑：一旦 JSON 解析失败，后面整个工具调用、持久化、前端渲染全部停摆。

经过在几条 Agent 管线上的实际折磨之后，我们发现一个简单但非常有效的替代方案：**把结构信息从 JSON 转移到自定义的标签格式（tag-based format）**，让解析从“严格语法校验”变为“容错的模式匹配”，大幅降低因长文本引发的解析故障。

## 问题拆解：JSON 为什么在长文输出里频频翻车？

1. **转义地狱**  
   长文本里随处可见双引号、反斜杠、换行符，模型很容易遗漏转义。即使强化 prompt，仍会出现 `"text": "他说："没问题""` 这种无效 JSON。

2. **括号与逗号的脆弱平衡**  
   一个 2000 行的 JSON 中只要有一处花括号或逗号多余/缺失，解析器就会全盘否定，而你很难肉眼定位错误位置。

3. **流式与部分解析的尴尬**  
   很多管线采用流式输出，JSON 不完整时无法增量解析；即使使用 ijson 等流式解析器，对无效字符的容忍度仍然很低。

4. **重试成本极高**  
   长文本意味着每次生成消耗大量 token，一次解析失败就需要重新生成整个长文，代价远高于短回答。

## 解法：用标签替代 JSON 的结构功能

思路很简单：放弃 JSON 的嵌套层级，改用自定义的标签块（类似 XML 但不要求 DTD，也不必严格合法）界定不同区域。例如，一个周报生成任务原本要求输出：

```json
{
  "summary": "...",
  "tasks": [
    {"name": "...", "status": "...", "detail": "..."}
  ],
  "risks": "..."
}
```

改为标签格式，模型只需输出：

<REPORT>
<SUMMARY>
这里写摘要，可以有任意换行、引号、“特殊符号”……
</SUMMARY>
<TASKS>
<TASK>
<NAME>任务一</NAME>
<STATUS>进行中</STATUS>
<DETAIL>……长文本……</DETAIL>
</TASK>
<TASK>
...
</TASK>
</TASKS>
<RISKS>
...风险描述...
</RISKS>
</REPORT>

解析器不再关心转义、逗号，只关心「从 `<SUMMARY>` 到 `</SUMMARY>` 之间截取文本」。对长文本的友好度直线上升：因为内容本身就是纯文本，不存在 JSON 编码带来的二次伤害。

## 工程化步骤

### 1. 设计标签体系

- **唯一性标签名**：避免模型自然语言中可能出现的词，例如用 `SECT_KP` 而不是 `SUMMARY`，或加前缀 `RPT_`。
- **闭合规则**：一律使用开启-闭合对，不允许自闭合，避免模型混淆。
- **不要求整体包裹**：顶层可以不套根标签，但建议套一层作为边界校验。

### 2. 修改 Prompt

在 system prompt 或任务提示中明确要求使用标签格式，给出示例。示例里故意在文本中包含双引号、换行、单引号，让模型学会“内容就是自由的”。

示例片段：

你的输出必须使用以下格式：
<RPT_SUMMARY>
这里可以写摘要，允许包含任意标点如双引号："你好"
</RPT_SUMMARY>
<RPT_BODY>
...长文本...
</RPT_BODY>

不要额外包裹 JSON 或代码块。

经验：强调“不要用 markdown 代码块包裹”，否则还得先去掉首尾的 `` ``` ``。

### 3. 后端解析器实现

推荐用正则 + 最小匹配惰性量词一次性提取。Python 伪代码：

```python
import re

def parse_tagged(text: str) -> dict:
    result = {}
    # 提取所有 <TAG_NAME> 内容 </TAG_NAME>
    pattern = re.compile(r'<(\w+)>(.*?)</\1>', re.DOTALL)
    for match in pattern.finditer(text):
        tag = match.group(1)
        content = match.group(2).strip()
        # 处理同一标签多次出现（如多个 TASK）
        if tag in result:
            if isinstance(result[tag], list):
                result[tag].append(content)
            else:
                result[tag] = [result[tag], content]
        else:
            result[tag] = content
    return result
```

`re.DOTALL` 让 `.` 能匹配换行符，处理跨行内容。惰性量词 `*?` 防止贪婪匹配吞掉后续标签。

### 4. 容错与补全机制

模型经常漏掉闭合标签，例如输出到一半被截断。此时可以在解析前做简单修复：

```python
def auto_close_tags(text: str, known_tags: list[str]) -> str:
    for tag in known_tags:
        open_count = len(re.findall(rf'<{tag}>', text))
        close_count = len(re.findall(rf'</{tag}>', text))
        text += f'</{tag}>' * (open_count - close_count)
    return text
```

再按顺序添加缺失的闭合标签，避免解析时炸裂。

如果解析结果缺失关键字段，可以触发轻量重试（只要求模型补全缺失部分），远比重新生成全篇划算。

## 踩坑记录

1. **标签名出现在正文里**  
   有一段正文里出现了“`<RISK>`”这样的字面符号，导致误匹配。解决：使用更奇怪的标签名如 `::RISK::` 或 `{{RISK}}`，但注意避开模型可能误解的模板语法（如 Mustache）。目前最安全的是全大写带前缀的组合，如 `RPT_RISK`，几乎不会与正常文本冲突。

2. **同一标签多次出现，解析器默认只保留最后一个**  
   需要在提取逻辑中判断类型，遇到重复标签将其转为列表存储，如上面代码所示。

3. **嵌套标签处理**  
   我的场景中尽量保持一层结构，避免嵌套。若需嵌套，正则提取就要换成简单的栈式解析器，复杂度提升，但仍在可控范围。

4. **模型返回中夹带“注释”**  
   有些模型会在标签外写额外说明，如“下面是摘要：<SUMMARY>...”。这会导致提取到的内容前多出说明文字。可通过在提取时舍弃标签外的字符，或 prompt 中严令“只输出标签结构，不要任何额外文字”来解决。

## 可复用建议

- **封装通用解析类**：传入标签列表和原始文本，返回字段字典，内部自动处理补全、去重、去前后空白。
- **与 MCP 工具配合**：如果标签输出是给下游工具使用，可以在 MCP 工具中内置解析逻辑，不暴露 JSON 格式的脆弱性。
- **容错优先**：宁愿解析出部分内容继续流水线，也比全盘崩溃好。因此正则提取失败时，可以使用简单规则按段落切分作为降级。
- **日志记录原始输出**：即便成功解析，也建议将原始文本与解析结果一并落库，方便回查模型偶尔的标签错乱。

## 总结

JSON 是优秀的结构化数据格式，但不适合承载“有长段自然语言”的混合内容输出。用标签格式替代 JSON，本质上是用自由文本包裹结构信息，把解析从容错性极低的语法校验，变成简单的模式截取。这一转变在 Agent、自动化报告生成、长文翻译、多节文档生产等场景下，显著降低了重试次数和 token 损耗，并大大减少凌晨告警的 `JSONDecodeError`。

如果你也在 OpenClaw 或插件体系中频繁遇到输出解析失败，不妨给标签格式一个机会。它可能不 elegant，但足够 pragmatic。
