# 定时任务防重入锁：为什么 5 分钟间隔的任务还是会“撞车”

## 背景：一个看似安全的间隔

在 OpenClaw 这类自动化平台中，定时触发器是最常见的能力之一。你可以轻松定义一个每隔 5 分钟执行一次的 Agent 任务：查询某个 API 状态、生成报告、清理过期数据。直觉上，只要间隔大于任务的最坏执行时间，就不会出问题。所以你按最快的 5 分钟设置好了，任务通常在 2 分钟左右跑完，看起来很安全。

直到某天，下游服务偶尔抖动，任务耗时飙到 8 分钟；或者一个第三方 MCP 工具响应超时，任务卡住；又或者 Agent 被复杂分支拖住了脚步。而定时触发器并不知道上一个实例还在跑，它准时在 5 分钟后再次启动一个新实例。于是两个甚至更多的任务副本同时运行，争抢同一个资源：写入同一张表、操作同一个文件、调用同一个有速率限制的外部接口。

这就是**定时任务重入**——任务还没结束，下一个又被触发，导致逻辑错乱、资源竞争，以及难以排查的偶发 Bug。本文基于 OpenClaw 的实际运行环境，给出一种轻量、可落地的防重入锁方案。

## 问题复现：5 分钟任务怎么撞的车

假设你有一个任务 `fetch-and-sync`：调用一个 HTTP API 拉取数据，进行清洗后写入本地 SQLite。程序平均执行时间约 3 分钟，所以你设置了 5 分钟的定时间隔。在平稳运行时，任务总是在上一个结束后才开始下一个。

某天，API 提供方限流，接口从 200ms 的响应恶化到每请求阻塞 20 秒。任务里刚好有 10 次分页请求，执行时间被推向 8 分钟。此时：

- 第 N 次触发：12:00 开始，预计 12:08 结束。
- 第 N+1 次触发：12:05 准点开始，此时上一个任务仍在运行。

结果两个进程同时写入同一张表，造成主键冲突、数据重复，甚至因为 SQLite 的写锁竞争导致两个进程同时失败。排查日志时，你会发现时间戳交错，难以定位。更糟的是，如果任务包含“发送通知”逻辑，用户可能收到多次重复消息。

## 方案：基于文件锁的轻量互斥

在单机/单体服务的部署下（大多数 OpenClaw 实例的常见形态），使用**文件锁**是成本最低且可靠的防重入手段。核心思路：每个任务获取一个独占的文件锁，如果失败就说明已有实例在运行，本次直接退出。

### 做法

在你的任务脚本入口处加入锁获取逻辑。以 Bash 为例：

```bash
#!/bin/bash
LOCKFILE="/tmp/mytask.lock"
exec 200>"$LOCKFILE"
if ! flock -n 200; then
    echo "任务已在运行中，本次退出"
    exit 1
fi

# 正常任务逻辑...
# 完成后自动释放锁（进程退出时文件描述符关闭）
```

如果是 Python 脚本，可以用 `fcntl` 或 `portalocker`：

```python
import fcntl
import sys

lockfile = '/tmp/mytask.lock'
with open(lockfile, 'w') as f:
    try:
        fcntl.flock(f, fcntl.LOCK_EX | fcntl.LOCK_NB)
    except BlockingIOError:
        sys.exit("已有任务实例运行中")
    # 执行任务...
```

在 OpenClaw 中，如果你使用 Agent 调用外部命令，这个文件锁可以放在被调用的 Shell 脚本或 Python 入口里。如果是纯 Node.js 编写的 Agent，也可以用 `proper-lockfile` 等库实现相同逻辑。

### 步骤小结

1. 选择一个唯一的锁文件路径（保证对应用户有读写权限）。
2. 任务开始时，以非阻塞方式尝试获取排他锁。
3. 若拿到锁，继续执行核心逻辑；否则立即退出并记录日志。
4. 任务结束后（无论正常或异常），确保释放锁。通常利用进程退出时操作系统自动回收文件描述符的特性，但注意不要手动 `fork` 或 `daemonize` 后丢失描述符。
5. 加上超时保护，防止脚本意外僵死导致锁永久不释放。

## 踩坑点与加固

### 1. 锁文件残留与权限问题

锁文件本身的**内容无所谓**，但必须确保运行时用户能创建并锁定它。常见错误是把锁文件放在只有 root 可写的目录（如 `/var/run`），导致任务用户无权操作。建议使用 `/tmp` 或用户家目录下的专用路径，并在部署初始化时显式创建。

### 2. 脚本异常退出未释放锁

如果脚本被 `kill -9` 强制终止，内核会自动释放进程持有的所有文件锁，因此 `flock` 是安全的。但若你在脚本中使用 `trap` 或试图清理临时文件，不要错误地删掉正在被锁定的 fd，先关闭 fd 再删除。

### 3. 定时器分钟数偏差

某些 cron 实现有秒级偏差，不能保证严格准点。如果你在 5 分钟 cron 内看到了“未获得锁而退出”的日志，这不是 bug，而是上一次任务轻微超时后留下的正常痕迹。只要日志清晰，就可以忽略。

### 4. 任务执行时间过长导致连锁慢

如果任务频繁触发但每次都因锁而退出，意味着工作堆积。你需要**监控退出次数**，并在连续 N 次锁获取失败时发出告警，提示“任务可能耗时异常”。

### 5. 在 Docker 中的注意事项

如果 OpenClaw 部署在容器中，主进程 PID 为 1，需要注意信号处理。同时，锁文件路径建议统一使用挂载卷下，避免重启容器后路径变化。

## 可复用建议

把锁逻辑封装成通用模块，让每个定时脚本或 Agent 任务都能一行引入。例如，提供一个 `task_lock.sh` 公共库：

```bash
source /opt/openclaw/lib/task_lock.sh
acquire_lock "sync-data" || exit 1
```

在 Python 项目中可以写一个上下文管理器：

```python
from task_utils import file_lock

with file_lock("sync-data"):
    run_job()
```

你还可以扩展功能：锁等待时间（非立即退出而是重试）、最大锁持有时间（防止脚本僵死）、以及锁状态暴露给健康检查端点。

另外，记录每次任务的实际耗时，配合 Prometheus / InfluxDB 等监控，可以动态评估最优触发间隔，从设计层面减少重入概率。

## 总结

定时任务防重入是一个**低投入、高回报**的工程习惯。在 OpenClaw 的自动化流程中，即使只加一行文件锁，也能避免大量由重入引发的诡异问题和数据脏读。本文方案简单到只有几行代码，却能挡住最典型的“5 分钟任务撞车”场景。

- **当任务间隔足够长时**：文件锁是沉默的保镖，无人察觉。
- **当下游抖动任务超时时**：它会果断拒绝新实例，守护数据一致性。
- **当需要排查时**：明确的“已退出”日志让你一眼看到问题根源。

如果你正在构建定时触发的 Agent 或插件，现在就去检查一下：你的任务是否已经上了锁？
