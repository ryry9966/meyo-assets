最近 36kr 发了一篇一手实测智谱最强模型的稿子，标题里抛了个挺有意思的概念——AI 编程「御三家」要成型了。所谓御三家，业内一般默认指的是 Anthropic 的 Claude、OpenAI 的 GPT、Google 的 Gemini 这三家在代码能力上长期咬得很紧的大模型。如今智谱（GLM 系列）被拎出来跟它们对位讨论，说明国产模型在 coding 这个细分赛道上，确实摸到了第一梯队的门槛。今天就借这条热搜，把「AI 编程模型」这件事掰开揉碎聊一聊：它到底在比什么、御三家格局怎么形成的、以及作为开发者我们该怎么用。

## 一、AI 编程模型，到底在比什么？

很多人以为「写代码」就一个维度，其实评测一个编程模型至少要看四层能力：

1. **单文件函数级补全**：给一段需求或注释，能不能写出正确的函数。这是 Copilot 时代的主战场，对应的经典 benchmark 是 HumanEval、MBPP。今天主流模型在 HumanEval 上基本都能跑到 85% 以上，这一层已经接近「饱和」。
2. **仓库级理解与改动**：给一个真实开源项目的 issue，能不能定位到对应文件、读懂上下游调用、给出 patch。对应 SWE-bench Verified，这是目前区分度最高的硬指标，Claude 3.5/3.7 Sonnet 一度把这个分数从 20% 多拉到 60%+，差距非常显著。
3. **Agent 化的多步执行**：能不能调用 shell、读文件、跑测试、看报错、再修代码，像一个真正的初级工程师那样闭环。这考验的是工具使用、长上下文、错误恢复能力。
4. **工程审美与协作**：写出来的代码风不风格统一、要不要乱加依赖、会不会过度设计。这一层目前还没有特别好的自动化指标，更多靠人工盲评。

所以下次再看到「XX 模型超越 GPT-4」的标题，先问一句：超的是哪一层？

## 二、「御三家」是怎么打出来的

回顾一下过去两年的时间线，能看出编程能力是怎么一步步成为顶级模型的硬护城河的：

- **2021 年**：GitHub Copilot 上线，背后是 OpenAI 的 Codex（GPT-3 的代码微调版）。第一次让大众感受到「AI 真的能写能跑的代码」。
- **2023 年初**：GPT-4 发布，HumanEval 一举拉到 67%，把第二名甩开一截。
- **2024 年中**：Claude 3.5 Sonnet 横空出世，在 SWE-bench 上把仓库级能力拉到一个新档位，Cursor、Cline、Aider 这些 AI IDE/Agent 工具几乎一夜倒向 Claude。
- **2024 年底~2025 年**：Gemini 2.x 凭借百万级 token 上下文，在「整库塞进去再问」的玩法上扳回一城；与此同时国产侧 DeepSeek-Coder、Qwen-Coder、GLM 等持续追赶。

御三家格局的本质，是**预训练数据 + RLHF 标注 + Agent 化训练 + 工具生态**四件套同时发力。任何一家想挤进去，单刷 benchmark 是不够的，必须在真实 IDE 场景里被开发者「日常用」，才能形成正反馈。

## 三、智谱这次为什么被拿来对位

按 36kr 的实测描述，智谱新一代模型在以下几个点上表现可圈可点：

- **仓库级任务**：在中等规模项目里能正确定位多文件改动，patch 一次过的比例显著提升。
- **中文场景**：对中文注释、中文需求文档的理解明显比海外模型「顺」，这点对国内团队是真实生产力。
- **价格 / 推理速度**：作为闭源 API，价格策略和延迟控制做得比较激进，适合做 Agent 类应用的高频调用。
- **工具调用稳定性**：function calling 的格式遵循度提高，少了很多「JSON 括号漏一个」的低级错误。

但要客观看：在最硬的 SWE-bench Verified 上，目前公开数据里 Claude 系仍然领先，Gemini 和 GPT 在不同子集上互有胜负。智谱说「成为御三家之一」更准确的表述是——**在国产闭源模型里，它和 DeepSeek 是目前最有希望进国际第一梯队的两家**。竞争还没结束。

## 四、对普通开发者，意味着什么

模型卷成这样，最大的受益者其实是写代码的人。但「怎么用」才是关键：

- **不要只用一个模型**：Claude 写重构、GPT 想架构、Gemini 啃长文档、国产模型处理中文需求——任务拆开，模型分工，效果远好于「一个模型用到死」。
- **善用 Agent 工具链**：Cursor、Cline、Continue、Aider 这些工具的价值，是把模型从「聊天框」搬进「文件树 + 终端」。同样的模型，放在 Agent 里能发挥的能力是聊天窗的 2~3 倍。
- **学会写 prompt-as-spec**：把需求写得像一份小型 PRD，包含输入输出、边界条件、已有约束。模型越强，对模糊需求的容忍度反而越低，因为它会「认真按你说的错的来做」。
- **保留 code review 习惯**：AI 写的代码，bug 密度其实并不比人低，只是分布不同——它很少写错语法，但容易在边界条件、并发、安全上犯隐蔽错误。

## 五、三条冷思考 / 实用建议

1. **别迷信榜单，建一套自己的私有评测集**。挑 10~20 个你日常真实遇到的任务（修 bug、写脚本、读老代码），每次新模型出来跑一遍，比看任何 benchmark 都靠谱。这个动作做一次，受用一年。
2. **AI 编程的瓶颈正在从「模型」转向「上下文工程」**。模型再强，喂给它的代码片段、文档、报错日志组织得乱七八糟，效果一样烂。未来一两年，**把上下文喂对**会比**挑哪个模型**更值得投入精力。
3. **警惕「能跑就行」的滑坡**。AI 让写代码门槛骤降，但也让「我也不知道为什么能跑」的代码大量进入生产环境。如果你是团队 leader，现在就该思考：怎么在 PR 流程里加一道「作者必须解释这段 AI 代码为什么这么写」的关卡。技术债不会因为它是 AI 写的就自动消失，反而会因为没人真正读过而加倍。

御三家也好，四国杀也好，名次每个季度都会变。真正不变的是：**模型是杠杆，不是替身**。杠杆越长，握杠杆的人越要稳。
