最近 36kr 报道了清华团队一篇挺有意思的工作：当系统里同时跑着上百个 Agent，传统的 Session（会话）机制就开始捉襟见肘了，他们的思路是——干脆把 Session 这一层重做一遍。听起来像是底层基建的小修小补，但如果你做过多 Agent 系统，就会知道这其实是个相当扎心的痛点。今天用一篇长文，把这件事讲清楚：Session 到底是什么、为什么多 Agent 时代它会塌方、清华团队在重做什么、以及对工程师和产品经理意味着什么。

## 先说人话：Session 到底是个啥

如果你只用过 ChatGPT 这种单 Agent 对话产品，可能对 Session 没什么概念——它就是「一次对话」嘛。但在工程视角下，Session 远比这复杂：

- **它是状态容器**：保存上下文消息、用户身份、权限、临时变量、工具调用记录。
- **它是隔离边界**：A 用户的对话不能泄漏到 B 用户那里，同一用户的不同任务也要相互独立。
- **它是生命周期单位**：何时创建、何时销毁、何时持久化，都按 Session 走。
- **它是计费与审计的颗粒度**：token 消耗、调用链路、错误回放，都挂在 Session 上。

在 Web 时代，Session 这一层已经被 Cookie、JWT、Redis 这套组合拳打磨得相当成熟。但 Web 的 Session 假设是「一个用户对一个服务」，请求-响应的模式非常清晰。到了 LLM 单 Agent 时代，事情还能凑合：把对话历史塞进 Session，下次请求拼回 prompt 即可。

问题是，多 Agent 时代来了。

## 为什么上百个 Agent 会让 Session 塌方

想象一个稍微复杂点的场景：你让一个「项目助理 Agent」帮你写周报，它会调用「日程 Agent」拉日历、调用「代码 Agent」总结 commit、再调用「邮件 Agent」起草发送。每个子 Agent 又可能再 fan out 出几个孙 Agent。一次任务下来，几十上百个 Agent 实例在跑，是常态。

这时候传统 Session 模型会出现几个典型崩坏：

1. **上下文爆炸**：每个 Agent 都想把「相关历史」放进自己的 Session，结果同一份对话被复制 N 份，token 成本指数级上涨。
2. **状态不一致**：A Agent 改了某个共享变量（比如「用户当前选择的项目」），B Agent 还在用旧值，因为它们各自有独立 Session。
3. **生命周期错乱**：父 Agent 已经结束了，孙 Agent 还在跑；或者中间某个 Agent 挂了，整个调用树的状态怎么回滚？
4. **权限传递混乱**：用户授权了主 Agent 访问邮箱，子 Agent 该不该继承？继承到第几层？
5. **可观测性灾难**：日志散落在 N 个 Session 里，想复盘一次任务为什么失败，得手工拼凑调用链。

用一句话总结：**Web 时代的 Session 是「一棵小树」，多 Agent 时代的 Session 是「一片相互纠缠的森林」**。继续用旧抽象，迟早出事。

## 清华团队「重做 Session」的核心思路

根据公开资料，这个工作的关键不是改某个 API，而是从抽象层重新定义 Session 这个概念。可以拆成几个要点来理解：

### 1. Session 从「线性历史」升级为「图结构」

- 传统 Session 是一条消息列表（list of messages）。
- 新模型把 Session 抽象为 DAG（有向无环图）：节点是状态快照，边是 Agent 调用关系。
- 好处是父子 Agent 的上下文继承、分叉、合并，都有了明确的语义，不用每个团队自己 hack 一套。

### 2. 上下文按「视图」共享，而不是按「拷贝」共享

- 类比数据库的 view：底层只有一份事实数据，每个 Agent 拿到的是按需投影出的视图。
- 子 Agent 想看父 Agent 的某段对话？给个引用，而不是把内容塞进自己的 prompt。
- 这一项直接砍掉了「上下文爆炸」的大头，token 成本能下来一大截。

### 3. 显式的生命周期协议

- 每个 Session 节点有明确的状态机：created → active → suspended → committed / rolled-back。
- 父 Session 结束时，子 Session 必须有明确归宿——要么 commit 回父，要么独立持久化，要么显式丢弃。
- 听起来像数据库事务？是的，多 Agent 系统里很多问题，本质和分布式事务是一类问题。

### 4. 权限与身份随 Session 流动

- 权限不是 Agent 自带的，而是挂在 Session 上传递的能力（capability）。
- 父 Agent 可以委派子集权限给子 Agent，子 Agent 不能自行扩权。
- 这一步把「Agent 安全」从代码审计层面，下沉到了基础设施层面。

## 历史回声：这事其实不是第一次发生

如果你工程经验够长，会觉得这套思路眼熟。计算机科学里，「重做 Session 抽象」其实反复出现过：

- **进程 → 线程 → 协程**：并发单元越来越轻，调度模型越来越细。
- **HTTP 无状态 → Cookie → Session → JWT → OAuth**：身份与状态的载体不断演进。
- **Monolith → 微服务 → Service Mesh**：服务间通信的「中间层」越做越厚。
- **裸 SQL → ORM → 事务管理器 → 分布式事务**：数据一致性边界一步步上抬。

每一次抽象升级，触发条件都很相似：**当并发实体的数量级跳一个台阶，旧抽象的成本就会突然不可承受**。从单 Agent 到多 Agent，正是这种台阶。所以清华这个工作不是「灵机一动」，而是顺着工程演化的必然方向往前推了一步。

值得一提的是，业界的 LangGraph、AutoGen、CrewAI 等框架其实也在各自摸索类似的事情，只是侧重点不同：有的强调编排 DSL，有的强调通信协议，有的强调记忆系统。Session 这一层被单独拎出来当成一等公民来设计，是相对新的视角。

## 对工程师和产品经理的现实影响

如果你正在做或将要做多 Agent 产品，这件事不只是论文层面的乐子。落到实操：

- **架构选型时，问一句「Session 模型是什么」**：很多框架对此含糊其辞，等系统跑到 50 个 Agent 时再发现就晚了。
- **token 成本审计要看 Session 拓扑**：如果你的账单异常高，大概率是上下文重复拷贝，而不是模型本身贵。
- **可观测性要按任务而非按调用建**：trace 工具如果只能看到单次 LLM 调用，多 Agent 场景几乎没法 debug。

## 三条冷思考

1. **新概念多半是旧问题换皮**：Agent 工程里 80% 的难题，在分布式系统、数据库、操作系统课本里都有同构版本。读老书比追新论文性价比更高。
2. **不要急着上百个 Agent**：很多场景 3 个 Agent 能解决，硬堆到 30 个只会让上下文成本和故障率一起飙升。Agent 数量不是炫技指标。
3. **基础设施的红利期才刚开始**：模型层卷得激烈，但 Session、Memory、Tool、Permission 这些「Agent 中间件」还有大量空白。对工程团队来说，这是比追大模型更现实的机会窗口。

抽象这东西，平时看不见摸不着，真到出事的那天，你会怀念有人提前把它想清楚。
