最近一则话题在开发者圈里刷屏：运营商推出的算力套餐打着"15元数百万Token"的旗号，看起来便宜得不像话，可真要拿来跑业务，一句简单的"你好"竟然能烧掉5万Token，开发者直呼用不起。这事儿乍一看像是营销玩文字游戏，往深里挖，其实牵扯出大模型计费、上下文窗口、推理成本等一连串容易被忽视的工程问题。今天就把这套"低价算力套餐"的账本拆开来算一算。

## 一、Token 到底是什么，为什么不能用"字数"理解

要看懂账单，先得搞清楚 Token 这个计费单位。它不是字符，也不是单词，而是模型分词器（Tokenizer）切出来的最小语义片段。

- **英文场景**：一个常见单词通常 1 Token，长单词或生僻词会被切成 2~3 个 subword。比如 `tokenization` 可能被切成 `token` + `ization`。
- **中文场景**：主流模型对中文的切分粒度差异巨大。GPT 系老分词器里，一个汉字往往要 2~3 个 Token；国产模型针对中文优化后，常见汉字可以做到 1 字 1 Token，甚至更省。
- **代码与符号**：缩进、换行、标点都算 Token。一段格式良好的 JSON，Token 数可能比你以为的多 30%。

所以"数百万 Token"这个数字，听起来海量，落到中文长文本场景里，可能也就够生成几百篇千字短文。问题是，**实际业务里你消耗的 Token 远不止"用户输入 + 模型输出"这么简单**——这才是"一句你好烧掉5万"的真正解释。

## 二、一句"你好"为什么能烧掉5万 Token

用户输入两个字，模型回个三五个字，按 Token 计费撑死也就几十个。能烧到 5 万，背后一定有"看不见的输入"。常见的几个吞 Token 大户：

1. **System Prompt（系统提示词）**：很多企业把人设、行为约束、输出格式、安全策略全塞进 system prompt，动辄两三千字。每次请求都要带上，等于每说一句话先"复读"一遍说明书。
2. **RAG 检索注入**：检索增强生成场景里，会从知识库取 Top-K 文档拼进 prompt。如果一次塞 10 段、每段 1000 字，瞬间就是 1 万 Token 起步。
3. **多轮对话历史**：模型本身是无状态的，多轮对话靠把历史消息全发回去维持上下文。聊到第 20 轮，前 19 轮都要重发一遍。
4. **Function Calling 的工具描述**：注册了几十个工具？每个工具的 JSON Schema 描述都要随请求带上，几千 Token 起步是常态。
5. **思维链（CoT）与推理模型**：像 o1、DeepSeek-R1 这类推理模型，会生成大量"思考过程"作为中间 Token，这些**用户看不到，但要计费**。一道数学题输出可能只有 50 字，思考过程能写 5000 字。

把这几样叠起来：3000 字 system prompt + 1 万字 RAG 上下文 + 2 万字对话历史 + 5000 字推理 token + 工具描述若干，5 万 Token 不仅不夸张，在某些 agent 场景下属于"日常水平"。

## 三、运营商套餐的"低价"是怎么算出来的

运营商和云厂商推算力套餐，喜欢拿"百万 Token 单价"做宣传锚点。这个锚点本身没毛病，问题在于细则里藏着不少落差：

- **模型分级差价**：套餐里能用的可能是 7B、13B 级别的小模型，对标头部旗舰模型的能力差一截。真要跑生产，多半得切换到更贵的型号，价格直接翻 5~10 倍。
- **输入输出不同价**：业内通行做法是 input Token 便宜、output Token 贵，差价常见 3~5 倍。宣传时只标低的那个数字，业务里输入输出比例却很难均衡。
- **缓存命中率**：部分厂商对"prompt 缓存命中"的部分打 1~2 折。但缓存命中需要 prompt 前缀完全一致，工程上未必能用上。
- **并发与限速**：低价套餐通常 RPM（每分钟请求数）和 TPM（每分钟 Token 数）都被卡得很死，并发一上来就排队，业务高峰期等于不可用。
- **超额阶梯计费**：套餐内单价低，超出后按市场价甚至更高计费。一旦业务量起来，账单会有断崖式跳变。

说白了，宣传价是"理想测试条件下的最优值"，真实业务里的有效单价可能要乘上 3~5 倍才接近实际。

## 四、开发者怎么把账单打下来：一份省钱清单

吐槽归吐槽，活还得干。Token 优化在工程界已经形成了一套相对成熟的打法：

1. **Prompt 瘦身**：把 system prompt 从"小作文"改成结构化要点，能用列表就别用段落，能用缩写就别写全称。一般能砍掉 30%~50%。
2. **分级路由**：简单意图用小模型兜底，复杂任务才路由到旗舰模型。一个客服系统里，70% 的问题用 7B 模型就能解决。
3. **上下文压缩**：多轮对话里，超过 N 轮的历史用摘要替代原文；RAG 场景用 reranker 精筛，把 Top-10 压到 Top-3。
4. **善用缓存**：把固定的 system prompt、知识库片段放在 prompt 前缀，命中 prompt cache 后输入端能省 50%~90%。
5. **流式 + 提前停止**：开启 streaming，监测到答案足够就主动 abort，避免模型把话说完。
6. **本地化部署兜底**：高频、低复杂度任务用开源模型自建推理（如 vLLM + 量化），把单位成本压到 API 调用的 1/10 甚至更低。
7. **可观测性先行**：给每次调用打 tag，按业务、按用户、按链路统计 Token 消耗。没有度量，谈优化都是空话。

## 五、冷思考：算力定价的下一站

Token 计价模式本身就值得反思。它把"语义价值"和"字符长度"强行挂钩，导致开发者的优化方向被严重扭曲——大家不是在思考"怎么让模型答得更好"，而是在琢磨"怎么让模型答得更短"。长期看，行业可能会演化出更合理的计价方式：按任务计费、按结果计费、按订阅席位计费，而不是死盯着 Token 数。

眼下能落地的三条建议：

- **看 EA（Effective per-call Average）而非标价**：评估任何套餐前，用自己真实业务的 prompt 跑 100~1000 次压测，算出每次调用的实际平均成本，再做横向对比。
- **预算上设熔断**：在网关层设 Token 配额和金额上限，单用户、单接口、单日三层熔断，避免一次 prompt 注入或死循环把月度预算烧光。
- **别把鸡蛋放一个篮子**：保持至少两家供应商的接入能力，模型能力、价格、稳定性都在快速变动，锁死一家等于把议价权交出去。

大模型这门生意，真正的成本优势从来不在宣传海报上，而在工程师对每一个 Token 的较真里。能把账算明白的团队，才有资格谈规模化。
