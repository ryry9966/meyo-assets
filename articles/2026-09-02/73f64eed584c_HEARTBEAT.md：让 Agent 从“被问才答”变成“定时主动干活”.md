## 背景

大多数 Agent 的默认形态是被动式的：你发消息，它回复，然后休眠。聊天场景下没问题，但一旦把 Agent 当作个人自动化中枢——盯邮箱、发日报、监控任务——“被问才答”就成了天花板。

OpenClaw 用一个很小的机制解决这个问题：heartbeat(心跳)。系统按固定间隔(默认约 30 分钟，可配)唤醒 Agent 一次，让它读取工作区根目录的 `HEARTBEAT.md`。这个文件就是你给 Agent 的“主动行事清单”：哪些事值得检查、满足什么条件才汇报、没事就保持安静。

## 问题：为什么不能只靠 system prompt

在系统提示里写一句“请主动帮我做事”基本无效，原因有三：

1. 被动会话里根本没有触发时机——你不发消息，模型不会自己跑起来；
2. “主动”没有具体定义，模型每次理解都会漂移；
3. 要做的事会随时间变化，每次改 system prompt 的代价太高。

把“主动性”落成一个用户可编辑、可进版本管理、每次心跳都会注入的 Markdown 文件，是把模糊意图变成工程契约的最小改动。

## 做法：五步搭起来

1. **建文件**。在工作区根目录放 `HEARTBEAT.md`,开头写一段全局规则，例如：“逐项检查下列任务；只在满足条件时输出结果；无事可做时只回复 `HEARTBEAT_OK`,不要打扰用户。”
2. **列任务**。一行一条，条件必须可判定。比如：“若未读邮件中出现带附件的账单，提取金额与截止日期并推送”；“每天上午 9 点(本地时区)发送昨日摘要”。避免“看看有没有有意思的事”这类写法。
3. **调间隔**。间隔就是成本旋钮。巡检类任务放宽，时效类(盯某个构建、盯某个价格)再收紧。先从 30 分钟起步观察。
4. **接输出通道**。心跳产出要有去处：行动性内容推到 IM 通道，过程性日志落到文件，不要把所有输出都当成通知。
5. **用好静默路径**。`HEARTBEAT_OK` 是关键设计：无事发生时 Agent 只回这个标记，不发通知、不产生消息噪音。把它写进文件开头的规则里，模型通常会遵守。

## 踩坑点

- **Token 烧钱**。`HEARTHEAT.md` 每次心跳都会注入上下文，写几百行等于给自己装了个定时烧钱器。控制在 30 行以内，细节让 Agent 按需去读别的文件。
- **时区**。“每天 9 点”在容器里默认按 UTC 跑，要么改容器时区，要么在任务里显式写明时区。
- **重复与积压**。某次心跳跑了长任务，下一拍可能重复触发或堆积。重活拆出去交给子任务/脚本，动作尽量幂等，或用一个 `last-run` 状态文件去重。
- **条件模糊**。判定不了的规则等于没有规则，只会换来随机打扰。
- **模型自由发挥**。偶尔会执行清单外的事，开头规则补一句“只做清单内的事”。

## 可复用建议

- 把 `HEARTBEAT.md` 当自然语言版 crontab 维护：一行一事、定期修剪、进 git。
- “心跳 + 状态文件”是通用模式：心跳负责“该不该做”，状态文件负责“做到哪了”。
- 数据获取交给 MCP 工具，心跳只负责调度和判断，职责分层才好排障。
- 起步配置建议三件事：每日摘要、收件箱分诊、一个你真正关心的监控项。跑一周再决定增删。

## 总结

HEARTBEAT.md 本身只是一个小文件，但它把 Agent 的定位从“聊天接口”挪到了“后台工人”：文件是契约，间隔是节奏，静默是特性。门槛低到一个 Markdown 文件，但要做稳，靠的还是工程习惯——可判定的条件、幂等的动作、克制的通知。建议先让心跳安静地跑起来，再逐步把真正值得被打扰的事交给它。
