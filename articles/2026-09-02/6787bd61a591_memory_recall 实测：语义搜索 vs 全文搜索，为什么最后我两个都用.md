## 背景

OpenClaw 的 memory_recall 是 agent 回捞长期记忆的入口：会话里遇到「上次那个配置怎么改的」这类问题，agent 调 recall，从记忆库里捞几条相关的条目塞回上下文。记忆库本质是一堆 Markdown 文件（按天/按主题切分），recall 的召回质量直接决定 agent 是「记得事」还是「一本正经地编」。

我的场景：一台自托管 OpenClaw，记忆条目 2000+，中英文混合，且包含大量专有名词——服务名、路径、命令、设备 ID。之前一直用全文搜索，最近搭了语义方案跑了一轮对比。

## 问题

两种召回的偏差方向完全相反：

- **全文搜索**（FTS5 / ripgrep 一类）：词面匹配，命中就是命中。但换个说法就抓瞎——记的是「打印机驱动装不上」，问「打印功能异常」就捞不到。
- **语义搜索**（embedding + 向量检索）：能跨表述匹配，但对精确 token 不敏感，「端口 5432」和「端口 5433」在向量空间里几乎一样近。

单选哪个都有明显短板。真正的问题是：怎么量化差距，以及怎么组合。

## 做法

1. **先建评测集**。从最近一个月的真实会话里抽 30 条 recall 请求，人工标注每条对应的「应命中条目」。这步最费时间，但最值钱。
2. **两路实现**：
   - 全文：SQLite FTS5，条目入库时做简易中文切分；
   - 语义：本地 embedding 模型（bge-m3）+ sqlite-vec 存向量，余弦相似度，**按段落而非整篇文件**建向量。
3. **指标**：hit@5 为主，顺带记 P95 延迟。
4. **融合**：两路各取 top 8，用 RRF（倒数排名融合）合并，取前 5 进上下文。

## 结果与踩坑

全文 hit@5 约 63%，语义约 71%，融合后 87%。提升主要来自「换说法」类查询。过程中踩的坑：

- **坑一：语义检索对专有名词很弱。** 设备 ID、命令名这类查询，全文几乎必中，语义经常排到 10 名开外——embedding 会把相近 token 当同义处理。
- **坑二：中文分词不处理，FTS5 默认 tokenizer 基本不可用。** 整句会被当成一个 token。我用最简单的二元切分（bigram）就够用了。
- **坑三：按整篇文件建向量会「稀释」。** 一篇 2KB 的日记得分被无关段落拉低。切成段落/条目粒度后命中率明显上升。
- **坑四：top_k 别给太大。** 15 条以上反而让 agent 被弱相关记忆带偏，实测 5~8 条刚好。

## 可复用建议

1. 别从选模型开始，先攒 20~30 条带标注的真实查询。没有评测集，一切调优都是玄学。
2. 混合召回做默认策略：全文保底专有名词，语义负责自然语言变体，RRF 融合几十行代码就够。
3. 向量按条目/段落切，不要按文件切。
4. 给 recall 加日志（query + 命中条目 + 排名），跑两周就能人工看出系统在哪类查询上失效。
5. recall 失败要有降级：两路都空时明确告诉 agent「没找到」，比硬塞弱相关内容好。

## 总结

语义搜索赢在「换了说法也能找到」，全文搜索赢在「精确的东西绝不认错」，单独用哪个都会在另一半查询上翻车。我测下来性价比最高的方案是 hybrid：两路召回 + RRF 融合，实现成本低、行为可解释、出问题可回滚。先把评测集建起来，后面的优化才有方向。
