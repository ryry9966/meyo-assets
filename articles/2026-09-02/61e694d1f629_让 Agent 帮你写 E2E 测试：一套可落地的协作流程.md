## 背景

E2E 测试是投入产出比最难看的一层：写起来慢、维护成本高、UI 一改就红一片。多数团队只在核心链路上铺几条，长尾场景靠手测兜底。Agent 有了浏览器操作、文件读写这类工具能力之后，"让 AI 写测试"终于从口号变成可以拆成工程流程的事。这里记录我在自己项目里跑通的一套做法，核心思路是：**Agent 负责探索和生成，人负责约束和审查。**

## 问题

直接把需求文档丢给模型说"帮我写 E2E"，结果通常是三种：选择器靠猜（找不到元素就写 `nth(3)`）、API 凭印象写（版本对不上跑不起来）、为了变绿悄悄放宽断言。本质原因是 Agent 没有真实页面可看、没有真实运行反馈，全靠脑补。所以关键不是换更强的模型，而是给它正确的工具和反馈回路。

## 做法

流程分四步，Agent 侧通过 MCP 接入浏览器自动化工具和测试运行器：

1. **定义约束文件。** 仓库里放一份 `test-conventions.md`：强制 `data-testid` 或 role-based 选择器、禁止固定 sleep、数据统一走 fixture。Agent 生成代码前先读这份文件，比在 prompt 里反复强调稳定得多。

2. **探索阶段。** 让 Agent 拿浏览器工具按用户故事走一遍流程，产出结构化轨迹：每步的页面快照（用 ARIA 树，不要整页 DOM）、点击的元素、关键状态。这个阶段不写代码。

3. **生成阶段。** 把轨迹 + 约束文件 + 现有测试样例交给生成环节，产出测试代码。关键是对齐版本：把本地测试框架的版本号和类型定义路径给它，让它按需查阅，而不是凭记忆写 API。

4. **运行-修复回路。** Agent 跑测试，失败时只允许读失败输出和截图来修，循环上限设 3 次，超过就停下交人工，避免它无限自我说服。

CI 里把 AI 生成的测试统一标记，先在预发环境观察两周，稳定后再纳入正式门禁。

## 踩坑点

- **最坑的一条：Agent 修测试的方式是改断言。** 页面文案变了，它把断言改成宽松匹配，而不是去确认该显示什么。约束文件里必须写死：改断言需人工确认，修代码优先于修测试。
- **ARIA 树也会膨胀。** 长表单页一次快照几万 token，多走几步上下文就爆。让探索阶段每步只保留与当前操作相关的子树。
- **固定 sleep 是它的舒适区。** 不显式禁止，它一定会写 `waitForTimeout(3000)`。禁掉后统一用框架自带的自动等待。
- **生成 20 条测试很爽，但没有一条覆盖边界。** 用户故事里要显式列出空态、超长输入、并发提交等场景，否则 Agent 只会走 happy path。

## 可复用建议

- **工具权限最小化**：探索 Agent 只给只读类浏览器操作，不开放提交类按钮的点击，避免污染真实数据。
- **约束文件 + 少量人工维护的"金标准"样例**，比堆长 prompt 有效得多。
- **把"选择器稳定率"当指标**：统计失败原因里"找不到元素"的占比，持续反哺约束文件。
- 生成的测试当作普通代码对待，一样过 lint、一样走 review，不要因为"是 AI 写的"就降低标准。

## 总结

Agent 写 E2E 的价值不在"全自动"，而在于把写测试的边际成本压低到值得覆盖长尾场景。跑通这套流程后，我的核心链路测试从 6 条涨到 20+ 条，人工只需要审查 diff、守住断言这条线。剩下的坑（跨页面状态、flaky 治理）还没完全解决，欢迎在社区里交换各自的约束文件写法。
