## 背景

Agent 接上 MCP 工具和插件之后，能力从"聊天"变成了"执行"：读写文件、调 API、发消息、跑 shell。能力上去了，一个老问题变得尖锐——哪些动作可以直接做，哪些必须停下来等人确认。

## 问题

实践中常见两种失败模式：

1. **什么都问。** 每读一个文件都要批准，几轮之后人开始无脑点"允许"，确认机制退化成橡皮图章，比不确认还危险。
2. **什么都不问。** 一句模糊指令被放大成一串删除、支付、群发操作，出事时才发现中间没有任何闸门。

根因相同：没有事先定义权限边界，而是把判断留给运行时的模型——模型对风险的自我评估并不可靠。

## 做法：按动作分级，而不是按场景猜

把 Agent 能调用的每个工具（MCP tool、插件方法、命令模板）预先标一个风险层级，策略跟层级绑定。模型只负责选工具，不负责给自己的动作定级。

- **T0 只读、本地、无副作用**：读文件、查询、搜索。直接放行。
- **T1 可逆写、影响面小**：改工作区文件、写草稿、本地 commit。自动执行，但必须留 diff 和日志。
- **T2 外部可见副作用**：发消息、调第三方写接口、部署测试环境。默认暂停，展示"将要做什么"，等人确认。
- **T3 不可逆或高影响**：删数据、生产变更、超阈值支付。硬闸门，建议不开放给 Agent，由人执行，Agent 只产出操作方案。

分级看三个维度：**可逆性**、**爆炸半径**、**确认成本**。T2 之所以暂停，是因为问一次的成本远低于做错的成本；T0 之所以放行，是因为问得太频繁，人必然疲劳。

落地步骤：

1. 盘点 Agent 的全部工具面，逐个定级，写进工具配置而不是 prompt。
2. 执行层加统一 gate：T2 以上先输出执行计划（参数、目标、影响），确认后放行。
3. 全量记录工具调用，事后可审计。

## 踩坑点

- **确认疲劳**：T2 一天来几十次，人会批量批准。解法是预授权加上限：自动执行，但单次金额 ≤ X、每日总量 ≤ Y、到期自动收回。
- **批量操作藏雷**：一次确认覆盖 50 个子动作，里面混着删除。gate 要到动作粒度，批量任务先展开成清单再确认。
- **权限蔓延**：allowlist 只增不减，半年后 Agent 什么都能干。定期 review，预授权默认过期。
- **策略写在 prompt 里**："危险操作请先询问"这类 prompt 约定没有结构化保障，长对话中会被稀释。策略必须是执行层的硬约束。

## 可复用建议

- 层级跟工具走，不跟会话走；新工具接入先定级再启用。
- 默认 dry-run：Agent 先给计划，人看计划放行，比事后回滚便宜得多。
- 预授权等价于一张限额卡：有额度、有有效期、有范围。
- T1 以上动作全部落日志：时间、工具、参数、结果、是否人工确认。

## 总结

权限边界不是"信不信任模型"的问题，而是把工程里成熟的变更管理搬进 Agent：分级、闸门、审计、限额。原则一句话——**可逆且影响小就自动，不可逆或影响大就停下**。Agent 的自主性应该是你授权出来的，而不是它自己长出来的。
