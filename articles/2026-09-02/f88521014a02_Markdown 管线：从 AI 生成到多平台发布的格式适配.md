## 背景

让 Agent 写完一篇技术帖只是前半程。真正费时间的是后半程：同一篇 Markdown 要发公众号、知乎、掘金和静态站，四处的方言、过滤规则、图片策略都不一样。手工逐平台改格式，偶尔一次还行，常态化更新根本撑不住。我们在社区内容自动化的实践里搭了一条转换管线，把"生成"和"发布"之间的适配收敛成代码。

## 问题

实际跑起来之后，麻烦集中在三处：

1. **AI 生成端不规范。** LLM 输出的 Markdown 语法边界模糊：标题层级跳跃（H1 直接跳 H4）、代码块缺语言标记、混入裸 HTML、脚注和任务列表随手用。这些在 GitHub 上没问题，到了严格的渲染器里全是坑。
2. **平台方言差异。** 公众号不认原生 Markdown，粘贴 HTML 时会过滤部分标签，样式必须全部内联；知乎对外链有风险提示；不少平台不支持脚注和任务列表。
3. **图片链路。** 外链图床有防盗链，公众号素材库要求先上传再引用，图片 URL 必须在渲染阶段重写。

## 做法：四层管线

核心原则是**用 mdast（AST）做转换，不做字符串替换**：

1. **生成层收敛。** 在 Agent 的 system prompt 里锁定一个"内部语法子集"：只用 GFM 的稳定特性，禁裸 HTML，代码块必须带语言标记。生成端收一寸，适配端少写十行兜底逻辑。
2. **规范化层。** 用 remark 生态做 lint 和自动修复：补齐标题层级、统一列表缩进、剥离多余 HTML。CI 里跑 markdownlint，不合格直接打回给 Agent 重写。
3. **适配层。** 为每个平台写一个 serializer：mdast 遍历 → 节点级转换 → 输出目标格式。公众号走 HTML + 内联样式 + 预展开的代码高亮；静态站近乎原样输出。front-matter 承载平台差异配置（摘要、tags 映射、封面）。
4. **发布层。** 图片先行：适配器先调用各平台上传接口（封装成 MCP tool）拿到新 URL，再整体渲染。收敛之后，Agent 一条指令就能产出全部平台版本。

## 踩坑点

- **公众号会"清洗"HTML。** 即便全内联，`position` 等属性照样被剥掉。实测下来，代码块最稳的做法是预渲染成带行内 style 的 `<span>` 序列，不要依赖平台高亮。
- **正则转换是技术债。** 早期用正则处理嵌套列表和代码块内的特殊符号，反复出 bug。换 mdast 之后，转换逻辑变成对确定性节点类型做分支，可测试性完全不同。
- **快照测试别省。** 准备 3~5 篇覆盖各种语法特性的样例文，每次改适配器跑一次多平台输出 diff，比人眼检查可靠得多。
- **表格是重灾区。** 部分平台对 GFM 表格支持不全，必要时降级为 HTML 表格并内联样式。

## 可复用建议

- 先写一页"内部语法子集规范"，让所有生成任务以此为契约，适配层只做映射、不做猜测。
- 适配器做成独立插件或 MCP server，CLI 和 Agent 共用同一套实现，避免两处维护。
- 元数据驱动：发布配置全部进 front-matter，管线本身零硬编码平台名。

## 总结

多平台发布的本质，是把"方言差异"从每次手工操作前移到一次性工程投入。管线化之后，Agent 负责生成与调用，管线负责确定性转换，人只对内容本身负责。这条路不炫技，但在长期更新的场景里，省下的时间是实打实的。
