## 背景

用 OpenClaw 跑内容类任务时，AI 产出几乎都是 Markdown——够通用，Agent 好写，人也好审。但真正落地会发现：Markdown 只是"源格式"，不是"发布格式"。同一篇稿子发到博客、公众号、掘金、GitHub，格式要求各不相同，手工适配的成本随平台数量线性增长。这篇帖子记录我目前在用的管线思路，核心是把"适配"变成可测试的代码，而不是每次复制粘贴时的手工修补。

## 问题

三类麻烦叠加：

1. **AI 输出本身不稳定**。标题层级随意（有时直接从 ### 开始）、代码块缺语言标记、爱插大量 `---` 分割线、图片链接是编造的 URL。
2. **平台方言差异**。公众号不支持部分 HTML 标签、代码高亮要靠内联样式；掘金只认 GFM；个别平台会把嵌套列表解析崩。
3. **字符串级替换不可靠**。用正则改 Markdown，遇到嵌套结构（列表里的代码块、表格里的反引号）很容易改坏。

## 做法

管线分四步，全部基于 AST，不碰字符串：

**1. 源头约束。** 在 Agent 的 system prompt 里固定输出规范：H1 唯一、代码块必须带语言、禁止 HTML、图片只输出占位符（如 `[IMG:cover]`），由管线后期替换成真实图床链接。

**2. 规范化（normalize）。** 用 remark/unified 解析成 mdast 后跑一遍自定义规则：统一标题层级、补齐代码语言、清理空段落。这一步的输出是"内部标准格式"，后续所有转换都基于它。

**3. 平台转换（transform）。** 每个目标平台一个插件，输入 mdast、输出目标内容。比如公众号插件把代码块渲染成内联样式的 HTML；掘金插件主要做链接改写（相对路径→绝对路径）。

```
mdast → normalize → wechat-transform → 渲染预览
mdast → normalize → juejin-transform → 渲染预览
```

**4. 干跑校验（dry-run）。** 发布前先本地渲染一遍，检查表格列数、图片可达性、代码块完整性，再走发布 API。我把整条管线封成了一个 MCP 工具，Agent 调 `publish(content, target)` 即可，`target=dry-run` 时只出报告、不改状态。

## 踩坑点

- **别用正则改 Markdown**。我早期在正则上耗了两天，换 AST 操作后规则反而越写越简单。
- **编造的图片 URL 必须在源头拦住**。占位符方案比事后检测幻觉链接便宜得多。
- **公众号的 `<details>` 会被吞**，折叠内容要降级成普通段落或前置摘要。
- **中文表格对不齐不是 bug**，是等宽字体下中文占两列，别在转义层修。
- **golden 文件测试必不可少**。每个平台转换配 3-5 组样例输入和期望输出，改规则跑测试，防止"修好公众号、弄坏掘金"。

## 可复用建议

- 输出规范写进 system prompt，同时用 lint 兜底，两层缺一不可。
- 固定一个内部标准格式（IR），平台差异收敛到 transform 层，新增平台只写一个插件。
- 所有发布动作提供 dry-run 模式，Agent 自动化时先跑报告再实发。
- 管线配置进版本管理，格式规范变更可追溯。

## 总结

多平台发布本质是"格式方言"问题，解法和编译器同构：源约束 → 规范化 → 目标生成 → 校验。把适配逻辑从"每次手工修"变成"有测试的转换插件"后，新平台接入成本降到半天以内，AI 生成的稿子终于能直接进发布流程。这套管线对任何用 Agent 做内容分发的场景都适用，欢迎在社区里交流补充各自的 transform 实现。
