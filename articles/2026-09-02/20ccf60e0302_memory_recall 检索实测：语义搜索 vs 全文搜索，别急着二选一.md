## 背景

memory_recall 是 OpenClaw agent 回忆历史对话和笔记的主要入口。它走哪种检索、能不能换，直接决定 agent "记不记得住"的体感。最近我在自己的实例上把语义搜索和全文搜索各跑了一段时间，又试了混合方案，把数据和坑记在这里，供大家参考。

## 问题

两种典型故障：

- **全文搜索找不到**：问"上次那个报错怎么处理的"，原文里是具体错误码和文件路径，提问时用的是自然语言，关键词对不上，检索返回空。
- **语义搜索找不准**：问"把 config 里 timeout 的默认值找出来"，向量检索返回几段"长得像"的配置讨论，偏偏跳过真正写了数值的那条记录。

结论很清楚：**语义搜索擅长同义改写，全文搜索擅长精确标识符**。单用任何一个都有系统性盲区。

## 做法

1. **盘点语料**：把 memory 目录按类型分（对话片段、笔记、报错记录），确认每类的典型 query 长什么样。
2. **双路检索**：
   - 全文路：SQLite FTS5 / BM25。注意中文必须换支持中文分词的 tokenizer 或字符 bigram，默认空格分词对中文基本失效。
   - 语义路：选确认支持中文的 multilingual embedding 模型，chunk 控制在 200–400 字，带上时间戳 metadata。
3. **合并**：用 RRF（倒数排名融合）合并两路结果，加时间衰减权重，最近 7 天记录适当加权。
4. **建评测集**：整理 20–50 条 golden query，统计 top-5 命中率，每次改配置前后各跑一遍。别靠体感调参。

## 踩坑点

- **中文分词**：FTS5 默认 tokenizer 按空格切，整段中文变成一个 token，全文路直接报废。换分词方案后命中率明显回升，这是我踩的最深的一个坑。
- **英文 embedding 模型处理中文会静默降级**：相似度分数看起来正常，排序却是错的，很难第一时间发现。
- **语义搜索会返回"高分但错误"的结果**，agent 很容易被带偏。让 memory_recall 输出来源和时间，方便事后排查。
- **chunk 尺寸**：大于 800 字稀释相关性，小于 100 字丢上下文，300 字左右比较稳。
- **时间衰减别调太狠**，半年前的报错记录也该能翻出来。

## 可复用建议

- 默认上 hybrid：全文负责 ID、错误码、路径类的精确命中，语义负责改写类问题。预算有限只保留全文 + 好的中文分词，也比裸语义稳。
- 把 golden query 评测集当回归测试，换 embedding 模型、改 chunk 参数都跑一遍。
- 在 system prompt 里约束 agent 的调用习惯：先用精确关键词查，不满意再把问题改写成自然语言查一遍，两轮取并集。

## 总结

这不是二选一的题。语义搜索解决"说法不一样"，全文搜索解决"字面必须一样"，真实的 memory 查询两类都有。工程上 hybrid + 中文分词 + 小评测集，成本不高，收益立竿见影。有跑出更好融合权重的，欢迎在评论区交流。
