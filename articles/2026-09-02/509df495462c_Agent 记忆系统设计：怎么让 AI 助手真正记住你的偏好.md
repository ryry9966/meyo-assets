## 背景

用 OpenClaw 这类长期运行的 Agent 时，最影响体验的往往不是模型能力，而是"每次都要重新教一遍"。会话结束上下文清空，你的代码风格、常用目录、部署习惯、回复语言偏好，全部归零。真正的解法不是把系统提示词越写越长，而是给 Agent 加一层可持久化、可检索、可更新的记忆系统。这篇帖记录我给自己助手做记忆层的方案，不花哨，但够用。

## 问题：四种典型失败

1. **记不住**——会话结束即失忆；
2. **记错**——一次性请求被当成永久规则（"这次用 TS 写" 被记成 "永远用 TS"）；
3. **记太多**——记忆无限膨胀，检索回一堆无关内容污染上下文；
4. **记旧**——偏好变了，旧记忆还在，两条打架。

这四条正好对应记忆系统的四个必备能力：持久化、写入门槛、检索预算、更新与淘汰。

## 做法

**先分层。** 我把记忆拆成三层：

- 会话内上下文：不落盘，随会话消失；
- 偏好档案：结构化小文件（几百 token 以内），每次会话开始全量注入；
- 情节记忆：具体事实和事件，SQLite 存原文 + 向量索引，按需检索。

偏好档案是收益最高的部分，每条记录至少带四个字段：

```json
{
  "key": "commit_style",
  "value": "conventional commits，中文 subject",
  "source": "explicit",
  "updated_at": "2025-06-01"
}
```

`source` 区分 explicit（用户明说）和 inferred（从行为推断），直接决定它能否被覆盖。

**写入设门槛。** 通过 MCP 暴露 `memory_write` / `memory_update` / `memory_search` 三个工具给 Agent，但规则收紧：只有用户明确表达的偏好直接写入；推断类条目要求同一模式至少出现三次才记。写入前先按 key 查重，存在就走 update 而不是 append——否则同一个偏好会存出十几个变体。

**检索有预算。** 偏好档案全量注入；情节记忆语义检索只取 top-3 且相似度过阈值，总 token 预算硬性限制（我设 800）。检索不到就不注入，宁缺毋滥。

**定期整理。** 跑一个 cron 任务做"合并睡眠"：去重、合并同义条目、超过 90 天未命中的 inferred 条目降权或删除，冲突按"explicit > inferred、新时间戳优先"裁决。

## 踩坑点

- 最大的坑是把一次性约束记成永久偏好。`source` 字段就是为此设计的；另外 value 里尽量存具体行为，不要存"用户喜欢简洁"这种无法执行的泛化描述；
- 记忆内容会被注入 prompt，属于典型注入面。外部文件、网页摘录不要直接进记忆，至少加来源标记；
- 别让 Agent 每轮自由写入。我放开过一次，两小时攒了两百条，全是"用户今天提到 xxx"级别的垃圾；
- 淘汰机制一开始就要有，后补很难——没人愿意删"可能有用"的数据。

## 可复用建议

- 先只做偏好档案这一层，收益/成本比最高，一个 JSON 文件加一段会话开始的注入逻辑就够，情节记忆按需再加；
- 验证方法很朴素：开全新会话，说"帮我提交这次改动"，看它是否直接套用你的 commit 规范。整理一份 10 条偏好的回归清单，每次改动记忆逻辑都跑一遍；
- 偏好条目控制在两位数以内，超了说明你在用记忆代替整理。

## 总结

记忆系统的核心不是"存得多"，而是写入门槛、检索预算、淘汰机制这三件事。先把偏好档案做扎实，Agent 就会从一个每次入职的新实习生，变成一个记得住你习惯的长期同事——不更聪明，但明显更省心。
