## 背景

LLM 本身无状态。你告诉它“提交信息用中文、不加 emoji”，下次新会话它照样给你英文提交。对单人长期使用的 Agent 来说，记忆不是锦上添花，而是体验的分水岭：偏好能被稳定记住的助手，才会从“每次都要重新调教的工具”变成“越用越顺手的同事”。

## 问题：三种常见错误姿势

1. **全塞 system prompt。** 偏好攒到几十条后 token 膨胀，关键指令被稀释，反而更容易被模型忽略。
2. **只靠会话历史。** 上下文一清空就归零，跨项目、跨周的记忆完全不存在。
3. **一上来就上向量库。** 记忆不到一百条就搞 embedding + 检索，运维成本大于收益，检索噪声还会往 prompt 里塞无关偏好。

## 做法：一套最小可行记忆系统

**第一步：分清记忆类型。** 偏好（稳定、长期，如代码风格）、情景（某次任务的上下文）、工作记忆（当前会话）。三者混存是后面一切混乱的根源。给偏好设计固定 schema：`{category, key, value, confidence, updated_at}`。

**第二步：写路径加门槛。** 通过 MCP 暴露 `memory_save / memory_update / memory_forget` 三个工具，但要规定：同一偏好看第二次，或用户明确说“以后都这样”，才允许落盘。第一次就写，会把临时性表述永久化。

**第三步：读路径做混合检索。** 会话启动时注入两类内容：一是 `category` 精确命中的高置信偏好（占大头），二是少量语义检索结果兜底。每条记忆带来源和时间戳，Agent 才知道哪些可信。

**第四步：更新与遗忘。** 用户说“以后别这样了”，新记忆要覆盖旧记忆而不是并存；`updated_at` 超过三个月且从未命中的条目，进垃圾回收。没有遗忘机制的记忆库只会越来越不准。

**第五步：建最小评测集。** 十几组对话回放：改口偏好、临时表述、冲突偏好。每次改检索逻辑跑一遍，比拍脑袋可靠得多。

## 踩坑点

- **临时表述被永久化**：“这次用 Python 写”被 Agent 记成“用户偏好 Python”。置信门槛 + 显式触发词能挡住大部分。
- **向量检索当主力**：偏好类记忆是短句、语义高度重叠，纯相似度检索经常捞回一堆近义但无关的条目。分类 + 精确匹配应优先。
- **静默写入**：Agent 自动记偏好但不留痕，用户不知道它“以为”你是谁。所有写入记日志，并提供 `memory_list` 让用户随时查看、可删除。
- **敏感信息入云**：偏好记忆和代码仓库一样，默认本地存储（SQLite/JSON 完全够用），别为了省事直接同步到第三方。

## 可复用建议

- 100 条以内用文件或 SQLite；超过且需要跨项目共享，再考虑向量检索。不要倒着来。
- 把记忆服务做成独立 MCP server，任何客户端都能复用，别绑死在某个 Agent 框架里。
- 偏好按 `confidence` 分级注入：高置信直接进 system prompt，低置信只在相关话题出现时检索。
- 定期（比如每周）跑一次记忆审计脚本：清理过期条目、冲突条目、命中率为零的条目。

## 总结

让 Agent 记住偏好，本质上是一个普通工程问题：写路径加置信门槛，读路径分类优先，更新有覆盖和遗忘，再加一个能回放的评测集。不需要模型层面的黑科技，一个百来行的 MCP server 加一个清晰 schema 就能覆盖 80% 的场景。先让“记错”变少，再谈“记得多”。
