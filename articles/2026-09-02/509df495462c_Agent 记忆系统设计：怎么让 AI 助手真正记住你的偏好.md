## 背景

LLM 本身无状态。你上周告诉助手"回复用中文、示例代码用 Python、别加表情"，这次会话它照旧忘了。上下文窗口再大也救不了——不是记不下，而是没人负责把偏好从聊天记录里捞出来、整理好、在正确时机喂回去。记忆系统就是补这个缺口的工程件，和模型能力关系不大，和 schema、检索、生命周期管理关系很大。

## 问题：三种常见失败模式

1. **全量塞 system prompt**。早期最省事，结果是上下文膨胀、成本上升，新旧偏好矛盾时模型随缘站队。
2. **只靠一句"请记住我"**。写入全凭模型心情，格式不统一，下次根本检索不到。
3. **每次全文检索聊天记录**。噪声太大，注入 3000 token 的历史，只为支撑一句"他喜欢浅色主题"。

## 做法：四步

**1. 分层存储。** 我把记忆分三类：偏好（稳定事实，如语言、代码风格）、事件（会话摘要、做过什么）、流程（用户教过的操作步骤）。SQLite 单表就够，字段：`id`、`type`、`content`、`tags`、`confidence`、`created_at`、`last_used`。别一上来上图数据库。

**2. 写入走独立抽取。** 会话结束后，用一次单独的 LLM 调用做结构化抽取，JSON schema 约束输出。每条记忆要原子化（一条只说一件事）、自包含（禁止"他""之前那个"这类指代）、带来源。去重用 embedding 相似度加阈值（0.85 起步，按误合并率再调）。用户显式说"记住/忘掉"时走直写或墓碑删除，不进抽取管线。

**3. 读取走检索 + 压缩。** 会话启动时按 相似度 × recency × confidence 打分，取 top-k（控制在 500 token 内），以固定分区注入 system prompt。同一套输入必须产出同一套检索结果，方便排查。运行中再暴露 `memory_search` / `memory_write` / `memory_delete` 几个 MCP tool，让 Agent 按需查写。

**4. 生命周期管理。** 偏好会变：新旧条目冲突时新的覆盖、旧的降级保留（留排查余地）；被命中且未被否认的记忆 confidence 加一；长期未命中的按半衰期衰减，低于阈值归档。没有衰减机制的记忆库，半年后就是一团互相矛盾的陈旧断言。

## 踩坑点

- 抽取顺手挂在主对话里做，输出格式漂移严重。务必独立调用 + schema 校验，失败就丢弃，不要静默修复。
- 相似度阈值太低会碎片化（"喜欢拿铁"存出五条变体），太高会把"喜欢甜咖啡"和"喜欢拿铁"误合并。
- 记忆里混入敏感信息（住址、密钥）。要做分级：敏感类本地加密存，且必须提供一键清除——这是信任问题，不是功能细节。
- 没有评测集。固定 20 组回放会话跑一遍，统计记忆命中率，改一版跑一遍，否则调优全靠体感。

## 可复用建议

- 一条记忆 = 一个原子事实 + 来源 + 时间戳 + 置信度。这四件套能撑到很后期。
- 给用户可见性：一个 `memory_list` 命令让用户看、改、删。用户不信任的记忆库，等于没做。
- 先保证"读路径"的确定性，再优化"写路径"的召回。顺序反了会调到怀疑人生。

## 总结

Agent 记忆本质上是一个带生命周期的 ETL + 检索问题，不是 prompt 措辞问题。分层存储、独立抽取、确定性检索、衰减与冲突处理，四件事做扎实，助手就能稳定记住你的偏好。从 SQLite + embedding 起步，跑通评测，再谈更复杂的结构。
