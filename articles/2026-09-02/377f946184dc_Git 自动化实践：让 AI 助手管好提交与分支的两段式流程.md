## 背景

OpenClaw 这类常驻型 AI 助手的价值，不只在替你写代码，更在接管那些"琐碎但必须做对"的工程动作。Git 日常操作就是典型场景：写完功能忘了提交、commit message 全是 `update`、合并完的分支堆在本地、偶尔把临时文件带进提交。单看都不大，累积起来严重拖慢协作。

## 问题

把 git 直接丢给 agent，常见三个翻车点：

1. **瞎编提交信息**：只看文件名就生成 message，和实际 diff 对不上；
2. **无差别 add**：一句 `git add -A` 把日志、密钥、构建产物全扫进去；
3. **危险操作不受控**：`push --force`、`reset --hard`、在脏工作区上 rebase，出事没有回滚余地。

## 做法

我的落地方式是"只读先行 + 两段式提交"，分四步：

**1. 只读先行。** 先只给 agent 接入只读能力（MCP git server 的 status / diff / log / branch，或 shell 白名单里的只读命令），让它先学会"看"，输出结构化的变更摘要。

**2. 固化提交规范。** 写一份 skill/SOP 文件放进仓库：Conventional Commits 格式、分支命名（`feat/xxx`、`fix/xxx`）、"提交前必须先跑 status 和 diff"的硬性动作。规范本身进版本管理，改了有据可查。

**3. 两段式提交。** agent 先产出提交计划——按逻辑拆分文件分组 + 每组 message 草稿，确认后再执行。本地 commit 可以放权自动跑，push 一律人工确认。

**4. 定期清理。** 每周让 agent 扫一遍：列出已合并未删除的本地分支、两周未动的 WIP 分支，生成清理清单。删分支的动作依然走确认。

## 踩坑点

- **diff 超上下文**：大改动别硬塞，先看 `--stat`，再挑关键文件分批读。
- **交互式命令必挂**：`rebase -i`、`git add -p` 在非交互 shell 里跑不了，要么用 `GIT_SEQUENCE_EDITOR` 换成脚本，要么直接规避。
- **自提交死循环**：agent 改了自己的 skill 文件又触发提交，反复循环。把 agent 自身的配置目录排除在自动提交范围外即可。
- **中间态误判**：merge 冲突、detached HEAD、rebase 未完成时，agent 容易继续瞎操作。规范里要写死一条："检测到非干净状态就停下并报告"。

## 可复用建议

1. 把 git SOP 写成仓库里的 skill 文件，不要靠聊天口头约定；
2. 优先用 MCP git server 而非裸 shell，权限面小、动作可枚举；
3. 所有 git 命令落日志，事后能审计 agent 到底干了什么；
4. 分级放权：读自动、本地写半自动、远程写全自动拒绝；
5. 密钥从源头解决：`.gitignore` 先配好，再加一条"提交前 grep 疑似密钥"的自检。

## 总结

Git 自动化不是让 agent 替你做所有决定，而是把它训练成一个守规矩的提交员：看得准、写得规范、动作有边界、危险处停手。先收权、再给规范、最后逐步放权——这条路径在任何支持工具调用的 agent 框架上都成立，欢迎在评论区交流你们的权限划分方案。
