## 背景

OpenClaw 的 cron 任务，本质是到点把一条 instruction 喂给 agent。它和聊天 prompt 有个根本区别：**没有人在场**。session 多是隔离的，没有“接着上次说”的上下文；产出按配置直接投递到渠道，或者静默落地。instruction 写得含糊，不会有追问来兜底，只会得到一次跑偏的运行。

我自己的体会是：cron 跑不稳定，八成不是调度配置的问题，而是那条 prompt 的问题。

## 常见问题

复盘过几个翻车的任务，失败模式基本集中在这几类：

1. **依赖对话上下文**：instruction 里写“继续之前的话题”，但隔离 session 里什么都没有。
2. **时间口径不清**：“总结今天的消息”——时区没锁、窗口没定，agent 自行猜。
3. **没有输出契约**：只说“给我个摘要”，格式每次漂移，长起来直接刷屏。
4. **数据源没指定**：没说用哪个 MCP 工具或插件，agent 要么自由发挥，要么编。
5. **没有异常路径**：上游接口一挂，每次运行都往群里发一坨报错。

## 做法：五段式模板

我现在的 instruction 基本按五个固定段落写。一个实际例子（每日摘要、投递 Telegram）：

```text
[目标] 汇总过去24小时的行业新闻，输出不超过8条摘要。
[时间] 以系统时间为准，时区 Asia/Shanghai，覆盖窗口为过去24小时。
[工具] 只允许使用 web_search，不得凭记忆生成；每条附原始链接。
[输出] 每条一行：标题 + 一句话摘要 + 链接；不要总结陈词，不要表情。
[异常] 结果少于3条时发送"今日无可推送内容"；检索失败最多重试2次，仍失败只发一行原因。
```

逐段说明：

- **目标**：一句话说清做什么、产出什么，形容词能删就删。
- **时间**：agent 侧通常拿得到系统时间，但时区与窗口口径仍要显式写死，这是最容易被忽略的一项。
- **工具**：把允许调用的工具列成白名单。MCP server 一多，agent 一犹豫就开始漂。
- **输出**：格式、条数上限、要不要附链接，全部写死。输出契约越具体，行为越可复现。
- **异常**：这是和交互 prompt 差别最大的地方——空结果、失败、重试上限，都要给出明确动作。

配置层面还有两点：只执行不投递的任务，记得把投递关掉或设为静默，否则每次运行都会往渠道丢结果；重活拆小，让单次运行稳稳落在 timeout 内。

## 踩坑点

- **别写“有问题就问我”**：无人值守没人回答。改成写日志，或发一条失败通知。
- **隔离 session 不等于没状态**：确实需要跨次状态（比如去重）时，让任务第一步先读写一个状态文件，别指望它“记得上次”。
- **频率别一上来就固定**：先一次性触发或按 1 分钟间隔试跑三五次，输出稳定了再固化成每天一次。
- **instruction 进版本管理**：cron 配置里的 prompt 就是代码，改前 diff，改后 commit，出问题能回滚。

## 可复用建议

- 一个 cron 只干一件事；复杂流程拆成主任务 + 子任务，或让单任务只做汇总。
- 目标、时间、工具、输出、异常——五段缺一段，概率上就多一种翻车方式。
- 把失败路径当成一等公民来写。它比成功路径更决定这个任务“敢不敢长期开着”。

## 总结

写给 cron 的 instruction 不是聊天 prompt，而是一份**无人值守的作业交接单**：目标、时间、工具、输出契约、异常路径，一次交清。稳定性来自可预期，可预期来自写得足够死的 prompt。下次 cron 跑偏，先别动调度，把那条 instruction 按“交接单”的标准重写一遍，多半就好了。
