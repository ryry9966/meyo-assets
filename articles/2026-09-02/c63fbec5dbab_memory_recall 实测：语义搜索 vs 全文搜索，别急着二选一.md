## 背景

OpenClaw 的 `memory_recall` 决定 agent 能不能“想起来”。它有两条典型检索路径：语义搜索（embedding 向量 + 相似度）和全文搜索（SQLite FTS5 / BM25）。社区里常见两种极端结论：“向量检索才是未来”和“全文搜索又快又省”。我们在自己的自动化工作流里跑了一个多月，结论是：两者能力边界非常清晰，混合使用才是正解。

## 问题：两类典型翻车

- **语义翻车**：用户问“上次那个 GitHub Actions 报错怎么解决的”，召回的是几条泛泛的 CI 笔记，真正带着 `error TS2307` 的那条排不进 top-3。语义模型对精确 token（错误码、路径、ID）天生不敏感。
- **全文翻车**：用户换个说法“之前部署失败那事”，FTS 按“部署失败”还能命中；但说成“那次服务器起不来”就全军覆没。

本质一句话：**语义搜索擅长同义改写，不擅长精确匹配；全文搜索正好相反。**

## 做法

1. **先建评测集**。从历史会话挑 30 条真实提问 + 期望命中的记忆条目，存成 JSONL。没有这个，任何选型都是玄学。
2. **全文路径**：OpenClaw 的 memory 底层是 SQLite，开 FTS5。注意中文必须换 tokenizer——默认 `unicode61` 会把整句中文当成一个 token，等于搜不到。用 trigram tokenizer，或写入前先做分词。
3. **语义路径**：接一个 embedding provider。记忆条目本来就短，一条一个 chunk 即可，别切太碎；top-k 从 5 起，相似度阈值 0.35 左右起步再调。
4. **混合融合**：两路各取 top-5，用 RRF（倒数排名融合）合并，十行代码的事。融合后再按时间衰减加权，避免三个月前的旧结论盖过新结论。
5. **跑评测集对比 hit@3**。我们这组数据：纯语义 0.63，纯 FTS 0.57，混合 0.87。你的数据一定不同，所以才要自己测。

## 踩坑点

- **换 embedding 模型必须全量重建索引**。新旧向量混在一个空间里，相似度就是垃圾数据。记忆表里加一个模型版本字段，重建时好过滤。
- FTS 对英文标识符很强，但路径、命令里的斜杠和点号会被切碎。重要 ID 建议写入记忆时单独存一列，做精确匹配兜底。
- top-k 贪大把上下文塞满，模型反而开始幻觉没召回过的内容。宁可 k=5 + 一次 rerank。
- 相似度阈值跨模型不可比。0.35 在 A 模型合适，换 B 模型可能过滤掉一切。

## 可复用建议

- **写入侧比检索侧更重要**：每条记忆自带日期、标签、一句话结论，任何检索方式都受益。
- 把每次“召回失败”的 case 记进评测集——评测集才是这套系统唯一的长期资产。
- 短期项目用 FTS 就够：零外部依赖、成本为零；跨会话的长期知识库才值得上 embedding。
- 混合方案不一定需要向量库，SQLite + 本地 embedding 模型对个人自动化场景完全够用。

## 总结

memory_recall 的质量 = 写入规范 + 检索策略 + 持续评测。语义和全文不是对手，是互补：一个解决“换个说法还能找到”，一个解决“精确的那个词在哪”。先用 30 条真实查询测出基线，再决定投入多少，别凭感觉站队。
