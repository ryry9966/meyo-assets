## 背景

用 OpenClaw 跑 agent 的同学应该都有体感：同一个模型、同一套插件，换个工作空间效果天差地别。差别往往不在能力，而在 agent 进入目录后"看到了什么"。AGENTS.md 就是社区里逐渐收敛出的一个约定：在工作空间根目录放一份 markdown，agent 启动或遍历目录时优先读取。可以这么理解——README 写给人，AGENTS.md 写给 AI。

## 没有 AGENTS.md 会怎样

剩下的全靠模型猜，典型症状：

- 仓库用 pnpm，agent 默认 `npm install`，锁文件一换，diff 满屏；
- 测试命令猜错，跑了个不存在的脚本就宣布"任务完成"；
- 不知道 `dist/` 是构建产物，直接改了它；
- commit 信息、命名风格每次都不一样，review 全靠人肉纠偏。

这些不是模型变笨了，是上下文缺失。工具再强，也不知道你家仓库的规矩。

## 怎么写：五段骨架

一份能落地的 AGENTS.md，建议控制在几十行内，按这个结构写：

```markdown
# 项目速览
这是什么、技术栈、主要目录职责（三五行）

# 命令清单
安装 / 构建 / 测试 / lint 的确切命令，写死，不写"参考 package.json"

# 约定
命名风格、分支策略、commit 规范

# 禁区
生成目录不要改、密钥文件不要读、发版需人工确认

# 完成判据
改完代码后必须跑 `pnpm test`，全绿才算完成
```

多模块仓库可以在子目录再放一份，OpenClaw 按就近原则合并，子目录规则覆盖根目录。MCP 工具和子 agent 也会继承这份上下文，相当于一次配置、全链路生效。

## 踩坑点

- **写太长**。超过一两百行，关键指令被稀释，agent 注意力明显下降。宁可短而准。
- **和 README 冲突**。README 更了但 AGENTS.md 没跟上，agent 会拿到两套互相矛盾的指令。把它纳入 code review，和代码一起改。
- **命令写模糊**。"跑一下测试"不如 `pnpm -F web test`。模糊指令约等于没有。
- **写入敏感信息**。这份文件会随上下文进模型，token、内网地址、生产配置一律别放。
- **一次性写完就不管**。最有效的迭代方式是：agent 犯同一个错，就回去补一条对应规则。

## 可复用建议

1. 起步控制在 50 行以内，超了就往子目录拆；
2. 硬约束用"禁止/必须"句式，软偏好用"优先"句式，前者服从度明显更高；
3. 写完让 agent 复述一遍它理解的规则，能快速暴露歧义；
4. 模板化：新项目从上一个项目裁剪，别每次从零写。

## 总结

AGENTS.md 的本质，是把"人知道但 AI 不知道"的事变成一次性沉淀。它不提升模型能力，但能消除大部分低级失误，成本几乎为零。如果你还在靠口头约定或反复人工纠偏，建议今天就给工作空间补上这份手册。
