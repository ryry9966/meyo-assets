## 背景

OpenClaw 的 Agent 默认带工具调用能力：MCP 接外部服务、插件接消息渠道、自动化任务常驻后台。这类 Agent 不是一次性问答，而是长期、跨会话、跨渠道在跑，行为一致性就成了工程问题。同一个助手，在终端里干练利落，到家庭群里开始输出小作文，多半不是模型的问题，而是人格定义没有单点收口。

SOUL.md 就是这个单点。它位于工作区，每次会话启动时注入上下文，和 AGENTS.md、TOOLS.md、MEMORY.md 各管一摊。可以把它理解为：system prompt 是运行时注入的，SOUL.md 是你长期维护、进版本库的"人格源文件"。

## 问题

没有 SOUL.md 或写得很随意时，常见三类故障：

1. **人格漂移**：换模型、升级版本、加新插件后，语气和决策风格悄悄变了，没人知道哪次改动引起的。
2. **边界失守**：Agent 拿到 shell 和消息权限后，对"帮我删掉所有日志"这类指令照单全收。
3. **审计困难**：行为不对时，说不清是 prompt 的问题、工具描述的问题，还是记忆污染。

## 做法

我的 SOUL.md 分五段，控制在 60 行以内：

- **身份**：一句话说清它是谁、服务谁。例如"我的私人助理，优先处理个人事务，不扮演客服"。
- **语气**：给 2-3 个具体示例（理想回复长什么样），比堆形容词有效得多。
- **原则**：3-5 条决策倾向，如"不确定就问，不编造""涉及花钱的操作必须确认"。
- **边界**：明确不做的事，每条一行。关键是在负面规则后面跟上替代动作——"不主动联系联系人；如需外呼，先列草稿等确认"。
- **升级规则**：什么情况必须停下来问人。

工程动作上做三件事：放进 git 跟其他配置一起管；改动走 diff review；准备约 10 条固定的探针 prompt，每次改完 SOUL.md 或换模型跑一遍，看回复风格是否回归。相当于给人格做冒烟测试。

## 踩坑点

- **写太长**。超过百行后，模型对中间段落的遵守率明显下降，还会出现自相矛盾的规则。精简比全面重要。
- **只写禁令**。没有替代动作的"不要做 X"，模型会在边界上反复试探。
- **和工具描述打架**。某个 MCP server 的 description 写着"可自动执行"，SOUL.md 说要确认，后者通常输。工具描述也要过一遍。
- **塞入易变内容**。当前项目上下文、临时任务清单属于 MEMORY 或任务系统，放进 SOUL.md 会让人格每几天变一次。
- **出事不改**。每次越界行为都是一条缺失边界的信号，当场补进去，别攒着。

## 可复用建议

- 一条规则只说一件事，能用示例就不用形容词。
- 边界按资产风险排序：花钱、删数据、对外发消息、隐私，这四类必须显式覆盖。
- SOUL.md（人格）、AGENTS.md（协作约定）、工具配置三者职责分开，宁可重复一条，不要交叉定义。
- 每季度重读一遍，删掉没起作用的规则——人格也需要瘦身。

## 总结

SOUL.md 的价值不在"让 Agent 更像人"，而在把行为约束从散落的 prompt 变成一份可 review、可回滚、可测试的配置。当成代码来维护，它就是 Agent 最可靠的那层护栏；当成签名档案来写，它很快会变成没人看的许愿池。
