## 背景

我们社区每天有不少优质讨论散落在群聊、issue 区和论坛里，但缺少一个稳定的"对外发声"渠道——周报靠人肉整理，有价值的讨论没人沉淀成帖子。于是我花了一个周末，基于 OpenClaw 的 Agent + MCP 插件机制搭了一个自动发帖机器人，目标是：每天定时从数据源抓取讨论，由 Agent 汇总成草稿，经人工确认后自动发布。本文记录架构决策和踩过的坑。

## 最初的问题

第一版是典型的一次性脚本：cron 定时跑，抓数据 → 拼 prompt → 调 LLM → POST 发帖。跑了一周就暴露三类问题：

1. **重复发帖**：LLM 调用超时后脚本重试，但任务本身不记状态，同一条内容发了三遍。
2. **内容失真**：模型会"脑补"讨论中不存在的结论，甚至编出看起来合理的链接。
3. **无人兜底**：发帖失败静默退出，第二天才发现断更。

这三个问题分别指向状态管理、数据可信度和可观测性，靠改 prompt 救不回来，必须在架构层面解决。

## 重构后的架构

最终版拆成五个模块，彼此只通过状态库通信：

- **采集器（MCP 工具）**：把群消息导出、issue 列表、RSS 封装成 MCP tools。Agent 每次调用拿到的是结构化真实数据，而不是靠它自己回忆。
- **Agent 编排**：OpenClaw Agent 负责读数据、筛话题、写稿，工具调用上限设为 8 次，防止循环不收敛。
- **审核闸门**：草稿落库并推送管理员群，人工确认后才进入发布队列。全自动发帖在第一周就被明确否决了。
- **发布器**：独立 HTTP 适配层，带指数退避重试和幂等键（同一内容 hash 只发一次）。
- **状态库**：SQLite 记录每次任务的 id、输入快照、草稿和发布结果，是唯一真相来源。

流程：定时触发 → 采集器 → Agent 生成草稿 → 审核闸门 → 发布器 → 回写状态，失败即告警。

## 踩坑点

1. **Agent 循环不收敛**：最初没限调用次数，模型反复"再看一眼数据"，一轮任务跑了二十多分钟。加上限次和明确的停止条件描述后，稳定在 3-5 次调用内完成。
2. **幂等键设计错了**：第一版用"日期"做幂等键，补跑历史任务时全被拦截。改成"内容 hash + 任务类型"才对。
3. **cron 的时区问题**：容器里是 UTC，定时触发比预期晚 8 小时。现在统一在应用层处理时区，cron 只负责整点叫醒。
4. **把幻觉当格式问题**：一开始试图靠 prompt 压制编造链接，效果时好时坏。真正的解法是让所有引用都来自 MCP 工具返回的数据——模型只做归纳，不产生事实。
5. **告警比功能重要**：加了一个 30 秒一次的心跳检查，任务超时或队列堆积就推管理员。这个 20 行的改动，价值超过之前所有功能迭代。

## 可复用建议

- 状态先行：先设计任务状态表，再写 Agent 逻辑。
- Agent 只做归纳，事实一律来自工具返回。
- 发布必须有幂等键和人工闸门——宁可慢一天，不要错一次。
- 长任务设调用上限和整体超时。
- 上线前先写告警，再写新功能。

## 总结

机器人现在每天稳定产出 1-2 篇草稿，人工确认后发布。回头看，技术含量最高的部分不是 prompt，而是状态管理、幂等和可观测性这些"不性感"的工程活。Agent 负责聪明，架构负责可靠——缺了任何一个，产品都无法长期运行。工程结构已整理到社区共享区，欢迎取用改进。
