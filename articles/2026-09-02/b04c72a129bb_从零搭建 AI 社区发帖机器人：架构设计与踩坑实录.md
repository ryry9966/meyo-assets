## 背景

社区运营里有一类活儿很机械：每周整理精华帖摘要、发布活动回顾、同步版本更新。人工做费时，还容易断更。我的目标是做一个跑在 OpenClaw 上的发帖机器人：定时触发，Agent 生成草稿，过一道质量门控后自动发布。听起来就是 cron 加一次 LLM 调用，实际跑起来问题不少。

## 问题：为什么"直接调模型发帖"不行

第一版架构极简：cron 触发 → Agent 生成 Markdown → 调社区 API 发帖。上线三天暴露了三个致命问题：

- **重启后重复发帖**：Agent 会话状态丢失，同一主题发了两遍；
- **幻觉链接**：模型编造了不存在的帖子 URL，读者点了 404；
- **内容趋同**：连续几期摘要结构和措辞几乎一样。

结论很明确：把"发布"当成 LLM 的一个副作用，工程上不可控。必须把生成和发布拆成两个阶段，各自幂等。

## 做法：五层架构

1. **触发层**：OpenClaw 的 cron 任务定时触发，附带 `topic` 参数（如 `weekly-digest`）。
2. **素材层**：自写一个 MCP 工具封装社区只读 API，拉取本周新帖、精华标记和统计。模型只能基于工具返回内容写作，禁止自由生成 URL。
3. **生成层**：Agent 产出草稿 + 元数据（标题、标签、引用的 source_id），写入本地 SQLite，状态置为 `draft`。
4. **门控层**：确定性校验器，检查敏感词、必填字段、链接是否全部来自素材白名单，再和历史发帖做相似度比对（阈值 0.85），不通过就打回重生。
5. **发布层**：唯一的写入口。发帖前先写一条 `publishing` 记录（幂等键 = `hash(topic + date)`），成功后更新为 `published`。任何重试先查这条记录。

## 踩坑实录

- **幂等键设计错一次**：最初用运行时间戳做键，一重试就变成新键，等于没做。改成 `hash(topic+date)` 才真正幂等。
- **429 雪崩**：批量发布触发社区 API 限流，第一版立刻重试，越打越死。改成指数退避加随机抖动，超过 5 次转告警，不再硬打。
- **相似度去重误杀**：阈值 0.7 时不同主题也被拦截。调到 0.85 后归零，但前提是每周素材池本身要足够分散。
- **时区坑**：cron 按 UTC 跑，周一的摘要周日晚上就发了。所有时间统一转 `Asia/Shanghai` 再参与计算。
- **模型自由发挥**：在 system prompt 里明确"只允许引用工具返回的 source_id"，比事后逐个验证链接有效性强得多。

## 可复用建议

- 写操作必须独立成模块，带幂等键和状态机，不要让 Agent "顺手"调发布 API；
- 状态落 SQLite 或文件，不要依赖 Agent 会话记忆——重启是常态，不是异常；
- 生成与发布之间加一道确定性校验，LLM 只负责内容，规则负责兜底；
- 预留总开关和降级模式（只产草稿、不发布），出问题时人工接管成本最低。

## 总结

机器人现在稳定跑了两个多月，人工介入只剩每周扫一眼草稿队列。核心心得一句话：把 LLM 当成一个会犯错的"内容工人"，用确定性的工程手段给它圈好边界——状态机管重复，白名单管幻觉，退避管限流。架构本身不难，难的是把每一条失败路径都想一遍再动手。
