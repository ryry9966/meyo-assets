## 背景

常驻型 Agent（比如跑在自己机器上的 OpenClaw）有个先天限制：模型不会自己"醒着"，但你又希望它有主动性——定时巡检、到期提醒、盯 CI 状态、清理过期任务。heartbeat 就是为这个设计的机制：让 Agent 周期性自我唤醒，判断"有没有值得做的事"。

唤醒策略基本两条路：**轮询**（定时触发）和**推送**（事件驱动）。两者不是二选一，但取舍想清楚，成本和体验能差一个数量级。

## 问题

轮询的问题是无差别唤醒：每个周期都构造 prompt、可能调用 LLM、写回上下文——哪怕 99% 的心跳结论是"无事发生"。频率高，token 账单和消息骚扰一起涨；频率低，实时性没法看。

推送的问题恰好相反：按需唤醒很省，但依赖事件源有 webhook 能力，而且"错过即丢失"——推送失败、网络抖动、Agent 正在重启，事件就没了。没有持久化和对账机制，推送的可靠性撑不起自动化场景。

## 做法

我的实践是分层混合，步骤如下：

1. **拆心跳层级**。把心跳分成"廉价检查层"和"昂贵推理层"。廉价层是纯脚本：diff 上次状态、比对阈值、看时间戳，只有命中条件才组装 prompt 调 LLM。这一步能砍掉九成无效唤醒。
2. **合并与去抖**。事件先进队列，设一个批处理窗口（比如 2 分钟），窗口内多次触发合并成一次心跳，避免 Agent 被同一件事连续叫醒。
3. **默认静默**。心跳内部走独立会话，不进主对话上下文。结论是"无事"就直接丢弃；只有"需要人类介入"才往主会话冒泡。
4. **推送优先，轮询兜底**。Git、CI、监控告警这类原生支持 webhook 的源全走推送；无推送能力的源用低频轮询采样，本地 diff 出增量。
5. **推送落盘 + 心跳对账**。收到的推送先写队列文件，心跳时统一消费，并核对上次消费位点，补上推送丢失的窗口。

## 踩坑点

- **心跳污染主上下文**。早期我把心跳结果直接写进主对话，几百条"一切正常"很快把上下文撑爆，模型行为开始漂移。隔离会话是硬要求。
- **推送重试引发事件风暴**。webhook 超时重试，Agent 被同一事件唤醒五次。必须做幂等：按事件源 + 事件 ID 去重。
- **心跳里藏副作用**。在心跳里自动执行删除、部署类命令，出过一次事故后我改成默认只读 + 告警，执行动作一律等人工确认。
- **同步抖动**。多个任务都卡在整点触发，撞限流。加随机 jitter 把心跳打散。

## 可复用建议

选型判据很简单：**事件源是否原生支持推送** + **事件是否可预测**。有推送能力的源一律推送；无推送能力但状态可预测的，低频轮询 + 本地 diff；高频变化的，轮询采样就好，别追求逐事件。另外建议记录每次心跳的 token 消耗和"有效唤醒率"，这个比值是心跳参数调优唯一的客观依据。

## 总结

轮询是确定性的兜底，推送是效率上的优化，工程上几乎总是混合使用。heartbeat 设计的本质不是"定时任务怎么写"，而是**唤醒策略**：什么值得叫醒模型、什么叫醒了也白叫、什么叫醒了必须通知人。把这三个问题分开回答，心跳就不会变成烧钱的噪音发生器。
