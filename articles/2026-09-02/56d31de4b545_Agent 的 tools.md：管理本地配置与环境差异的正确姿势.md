## 背景

OpenClaw 的 agent workspace 里，`AGENTS.md` 管的是行为规范，而 `TOOLS.md`（下文统称 tools.md）管的是另一件事：**这台机器本身**。它由你自己维护，随会话注入上下文，等价于给 agent 的一份“本机说明书”。

单机玩 agent 时感受不深；一旦同一套配置要跑在笔记本、家庭服务器、VPS、CI 上，差异立刻显形：包管理器一个 brew 一个 apt，Python 版本不同，代理端口不同，GPU 只在其中一台。MCP 解决的是“工具能力的标准化接口”，但它不负责告诉你“这台机器上该怎么用”。

## 问题

三个常见反模式：

1. **把环境细节写进 system prompt**（AGENTS.md / SOUL.md），跨机同步后全是污染——A 机器的路径出现在 B 机器的上下文里。
2. **每次口头交代**。重复消耗 token，还依赖你每次都记得说。
3. **什么都不写**，让 agent 猜。猜错就是 apt 乱装、路径跑偏、在错误的环境里 pip install。

本质上，环境事实和 agent 行为是两类信息，混在任何一层都会漂移。

## 做法

1. **先分层**。机器无关的规范留在 AGENTS.md；机器相关的全部进 tools.md。判断标准只有一条：换一台机器，这条还成立吗？不成立就挪走。
2. **按固定结构写**，建议五个小节：运行时（Python/Node 版本与确切调用方式）、包管理偏好（uv 优先、brew 负责哪些）、路径约定（工作目录、数据目录、日志位置）、外部服务（本地端口、代理、SSH 主机别名）、禁忌清单（不许动的目录、不许跑的命令）。
3. **模板化**。`tools.md.example` 进 git，每台机器复制一份改成实情，实文件不进同步。
4. **让 agent 参与维护**。它撞到新事实（比如“这台机器 pip 装不进系统目录”），让它提议追加一条，你人工 review 后合入。
5. **定期校验**。换环境后发一个 smoke test 提示，让 agent 复述它读到的关键事实；对不上就改。

## 踩坑点

- **越写越长**。tools.md 常驻上下文，超过一屏就该砍。写事实，别写教程。
- **过期信息比没有更糟**。端口换了、路径删了没更新，agent 会照着错误信息反复撞墙。每次系统升级后过一遍。
- **敏感信息直接入库**。token、内网拓扑写进实文件，再被 workspace 备份带走就麻烦了。用环境变量引用或占位符。
- **和 MCP 能力重复**。MCP server 已经暴露的能力不要复述，tools.md 只写 MCP 覆盖不到的本机事实。

## 可复用建议

- 一行一条事实，用“键: 值”格式，diff 友好。
- 版本写具体（3.12，而不是“新版”），模糊描述对 agent 无效。
- 团队场景按角色出模板：开发机、服务器、CI 各一份基线。
- 把“更新 tools.md”写进 AGENTS.md 的收尾清单，形成闭环，别靠人肉记。

## 总结

tools.md 的价值不在“多一个文件”，而在把**机器事实**与**agent 行为**解耦：规范跟着人走，事实跟着机器走。保持短、准、仅本机、常更新，它就会从“又一个要维护的文档”，变成多机部署时最省心的那一层。
