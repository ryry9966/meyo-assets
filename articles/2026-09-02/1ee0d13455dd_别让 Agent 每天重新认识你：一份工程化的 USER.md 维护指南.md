## 背景

大模型本身没有长期记忆，每次会话都是“初见”。OpenClaw 的解法是把 workspace 里几个固定文件常驻注入上下文：AGENTS.md 管行为约束，SOUL.md 管人格语气，而 USER.md 管的是“你是谁”。这大概是成本最低、收益最直接的一个文件——但在很多人手里，它要么是空的，要么变成一篇没人读的自传。

## 问题

两种典型失败模式：

- **完全不写**。结果就是每天向 agent 重复自我介绍：时区、技术栈、命名偏好、回复语言……
- **过度书写**。几千行 Markdown 把上下文挤满，真正有用的信息被稀释；模型还会对陈旧条目过度泛化——你三年前写过“在学 Rust”，它就永远倾向于用 Rust 回答你。

核心矛盾在于：USER.md 的每一行都是常驻 token，必须像管理生产配置一样管理它。

## 做法

**1. 划清边界。** 只放“稳定且会影响决策”的事实：时区与工作时段、主力技术栈、沟通语言、项目角色、硬性偏好（如“方案先给结论再给依据”“不要主动重构我的代码”）。动态信息走每日笔记或记忆文件，不要塞进来。

**2. 用“可判定”标准写条目。** 每条自问：模型读到这句，行为会有什么具体改变？“我喜欢简洁”没用；“代码注释只解释 why 不解释 what，回复默认中文，术语保留英文”才有用。避免形容词堆砌，写可执行的规则。

**3. 结构化分层。** 一个可复用的骨架：

```markdown
# 用户画像
## 环境
- 时区 Asia/Shanghai，工作日 10:00–19:00 在线
## 技术栈
- 主力：Go、K8s；熟悉：Python；明确不用：Java
## 协作偏好
- 回复中文；先结论后依据
## 当前关注（带日期，过期删除）
- 2025-06：正在做 MCP server 接入
```

**4. 让 Agent 参与维护，人工把关。** 在 AGENTS.md 加一条规则：发现新的稳定偏好时，先向用户确认，再以“日期 + 条目”追加到 USER.md；每周或每月 review 一次，删掉过期项。配合 git 还能看到自己画像的演变史。

## 踩坑点

- **过期信息不清理**。换城市、换岗位、换技术栈后，新旧条目并存，模型随机选用一个，输出看起来像“人格分裂”。
- **写入敏感信息**。手机号、住址、密钥路径，分享截图或日志时容易外泄。写到“内网机器”这个粒度就够了。
- **职责混淆**。用户事实放 USER.md，行为规范放 AGENTS.md，语气人格放 SOUL.md。放错位置，之后想改都找不到。
- **膨胀失控**。给自己定硬上限，比如 50 行，写不进来说明该删旧的了。
- **过度画像导致回答变窄**。写“我只信某个框架”，agent 在你真的需要对比方案时会迎合你，而不是给你有效信息。

## 可复用建议

- 把 USER.md 当配置文件对待：版本管理、变更留痕、定期 review。
- 条目统一用“领域：可执行规则”的格式，agent 好引用，人也容易扫读。
- 多 agent 场景下，USER.md 保持单一来源，各 workspace 软链或同步，避免版本漂移。
- 新环境冷启动的好办法：先用一周让 agent 记录你的高频纠错，再把纠错沉淀成条目——比凭空自我总结准确得多。

## 总结

USER.md 的价值不在“写了多少”，而在“每一条都能改变模型行为”。把它当成一份需要持续维护的生产配置，而不是一次性简历：边界清晰、条目可判定、有淘汰机制。做到这三点，agent 不再每次都重新认识你，而是像老同事一样，清楚你的上下文、你的边界和你的偏好。
