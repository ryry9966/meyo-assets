## 背景

写代码这些年，真正花在"想"上的时间没想象中多，反倒是 `git status`、拆 commit、写 message、切分支、清理已合并分支这些机械操作吃掉了不少碎片时间。这类事有明确规律、可枚举、可校验，天然适合交给 agent。OpenClaw 这类常驻助手拿到工具权限后，完全可以把 git 变成一条"半自动流水线"。

## 问题

最直观的想法是给 agent 一个 shell，让它随便跑 git。实际试过就知道很快出事：它可能在错误的目录执行、把 `.env` 提交进去、甚至自作主张 `reset --hard`。所以核心问题不是"能不能自动化"，而是**边界画在哪**。

## 做法

**1. 收敛工具面。** 优先走 MCP git server 或受控 exec，不要给全量 shell。做一份命令白名单：`status / diff / log / add / commit / branch / switch / merge --ff-only`；明确拉黑：`push --force`、`reset --hard`、`clean -fd`、`checkout -- .`。

**2. 写一份工作流约定**，放进 agent 的系统提示或项目里的 agent 说明文件：

- 动手前先执行 `git status` + `git diff --stat`，汇报现状
- 提交按逻辑分组，message 用 conventional commits，带 scope
- 新任务一律从 main 拉分支，命名 `feat/xxx`、`fix/yyy`
- push 前必须列出将要推送的 commit，等人确认

**3. 大 diff 分批。** diff 超过几百行就先只看 stat，按文件分组提交，避免上下文塞爆后 message 全是空话。

**4. 兜底交给 hook。** pre-commit 跑 lint 和 secret 扫描（比如 gitleaks）。agent 再聪明也绕不过 hook，这一层才是真正的保险。

## 踩坑点

- **工作区漂移**：会话跨目录后，第一次 commit 提到了别的 repo。解法：每条 git 命令前校验 `pwd` 和 repo 根，或在工具层固定 cwd。
- **detached HEAD**：agent 在旧 commit 上堆了一串提交，切回分支后"消失"。约定它操作前必须确认当前分支非 detached。
- **敏感文件**：`.env`、私钥差点进库。`.gitignore` 之外，pre-commit 的扫描才是硬兜底。
- **token 爆炸**：一次性塞 3000 行 diff，生成的 message 等于没写。按文件、按 hunk 分批。
- **直推 main**：哪怕它"觉得没问题"。主分支写权限一律收走，统一走 PR。

## 可复用建议

- 把"允许/禁止命令清单"沉淀成通用 agent 配置片段，每个项目只改分支策略部分。
- **先 dry-run**：让 agent 输出"计划执行的 git 命令列表"，你确认后再执行。这个模式几乎零成本，收益极大。
- 已合并分支清理做成定时任务：每周五让 agent 跑一次 `git branch --merged` 列清单，删不删你说了算。
- 留审计日志：agent 执行过的每条 git 命令落盘，出问题能回放。

## 总结

git 自动化的价值不在"全自动"，而在把机械部分（分组、命名、检查清单）交给 agent，把决策（推不推、合不合）留给自己。白名单 + dry-run 确认 + hook 兜底，这三层做完，AI 管 git 才敢真的天天用。
