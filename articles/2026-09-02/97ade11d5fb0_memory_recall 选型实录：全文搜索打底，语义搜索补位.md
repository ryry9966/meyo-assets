## 背景

OpenClaw 的 `memory_recall` 是 agent 取回历史记忆的入口：用户问一句，插件去记忆库里捞相关条目，塞回上下文。默认走全文搜索，社区里不少人接了 embedding 做语义检索，然后开始争论谁更强。我把自己那台常驻 assistant 的记忆库（约 3000 条，中文为主，混代码片段）当靶场，两套都跑了一遍。

## 问题

两套方案翻车的方式完全不同：

- **全文搜索**：换个说法就捞不到。存的是“部署失败，端口被占用”，问“为什么起不来”召回为零。中文还有硬伤——SQLite FTS5 默认 tokenizer 下，搜“部署”命中不了“部署失败”。
- **语义搜索**：对精确 token 很差。查 `ECONNRESET`、`--dry-run` 这类错误码和参数，向量召回一堆“看着像但不是”的条目，真正那条反而排后面。

结论先行：这不是二选一的问题，是分工问题。

## 做法

1. **先修全文基线。** FTS5 换 trigram tokenizer（或入库前用 jieba 切词再存），中文命中率立刻正常。记条目时顺手带 tag 和日期字段，排序时加权。
2. **再加语义一路。** 中文场景选了 bge-m3 本地跑，向量库用 sqlite-vec 就够，3000 条根本不需要独立向量服务。
3. **混合融合。** 两路各取 top-5，用 RRF（reciprocal rank fusion）合并取前 3。不要把两边原始分数直接相加，量纲不同，永远调不齐。
4. **建评测集。** 写了 25 条查询，一半是换说法的复述，一半是精确词（报错码、命令、人名），看 hit@3。每次改动前后跑一遍，不凭感觉。

## 踩坑点

- trigram 索引体积翻几倍，但 3000 条也就十几 MB，可接受；条目上十万再换分词预处理方案。
- embedding 模型一换（哪怕同系列小版本升级），全部向量作废。索引里要存模型版本号，启动时校验。
- top-k 贪大没好处。召回 10 条塞进上下文，噪声会带偏 agent，3 条高质量胜过 10 条沾边。
- 记忆是增量写的，向量索引有滞后。写入后同步更新向量，别攒批量任务。
- 纯代码片段和配置块，两路都费劲，最后靠写入时打的 tag 捞回来。写入质量比检索调参更值钱。

## 可复用建议

- 记忆少于几百条：别上向量。全文 + 分词修好 + 排序加权，够了。
- 上千条且查询多为口语化复述：加语义一路，RRF 融合。
- 先建评测集再动手，检索改动没有评分就是盲调。
- 精力花在记忆写入的结构化上（tag、时间、来源），比在检索端堆 trick 回报高。

## 总结

实测跑分：全文修好分词后 hit@3 从 0.4 到 0.68，加语义混合后到 0.84。语义搜索没有替代全文搜索，它补上的是“换说法”这半边；精确召回仍然靠全文。工程上的稳妥路径一句话：**全文打底，语义补位，评测说话。**
