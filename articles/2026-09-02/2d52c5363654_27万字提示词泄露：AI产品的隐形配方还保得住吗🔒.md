27 万字是什么概念？差不多一部长篇小说。但这回流出的是一款 AI 产品 Fable 5.1 的全套系统提示词，据 36kr 等媒体报道，该产品遭黑客破解，提示词被完整扒出。事件细节有待官方进一步确认，但讨论已经跑起来了：提示词凭什么值得黑客惦记？泄露的到底是“配方”还是“命门”？普通开发者又能从中学到什么？这篇把它拆开讲清楚。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-02/c61adfda914eed50.png)

## 一、27 万字的提示词，到底是什么

先补个背景。系统提示词（system prompt）是产品方在用户开口之前，预先写给大模型的“岗位说明书”：

- 它定义了产品的几乎一切：人设与语气、能做什么、不能做什么、调用哪些工具、参数怎么传、输出什么格式、遇到越界请求怎么转
- 为什么能膨胀到 27 万字：以 agent 类产品为例，里面塞满了每个工具的完整接口规范、几百条边界情况的处置规则、few-shot 示例、安全合规条款、品牌话术。模型哪里“不听话”，就往里加一条规则，补丁摞补丁，最后摞成一部辞海
- 对比一下行业演化速度：2023 年初各家产品泄露的系统提示词普遍只有几百到几千个词；两年多过去，主流 agent 产品的提示词已经膨胀到几十万字量级。这次的 27 万字未必是行业之最，但很能代表现状

一个不太严谨但好用的类比：它像一份新员工手册，从“怎么回邮件”写到“遇到记者怎么办”，厚得能砸脚。

## 二、它是怎么被“撬开”的：只讲原理

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-02/8d62b0ef3e460062.png)

根因一句话：**大模型无法真正区分“指令”和“数据”。** system prompt 和用户输入最终进的是同一条 token 流，模型靠概率续写来“执行”指令，而不是像操作系统那样做权限校验。提示词天然是明文，且在推理链路上必然完整存在，模型要读它才能执行它。

常见泄露路径，概念上分三类：

1. **直接套话**：诱导模型“复述上文”“翻译全文”，或用角色扮演、编码变换等话术绕开限制
2. **间接注入**：污染模型会读到的外部内容（网页、文档、检索结果），让它在处理时顺带执行“外带”指令
3. **侧信道提取**：更常见也更尴尬，不少产品把提示词直接打包进前端代码，打开浏览器开发者工具就能看，根本不需要“黑”进任何系统

行业里有个著名旧闻：2024 年底，OpenAI 的 o1 被用户反复要求逐字复述系统提示词时，回了一句大意是“我的系统提示词是价值连城的珍珠”——头部厂商能做的，暂时也只是“求你别念”级别的软防御。所以这不是某一家的问题，是这一代 LLM 产品的结构性软肋。

## 三、泄露的损失有多大：拆成三层看



很多人第一反应是“配方被偷了，产品完了”。冷静拆一下，损失分三层，权重完全不同：

1. **产品能力层：损失有限。** 提示词更像“配方说明书”，不是“厨艺本身”。竞品拿到这 27 万字，还得配上同等水平的底层模型、工具链和工程集成，才能跑出接近的效果。抄配方容易，复制厨房难。
2. **安全层：最实在的危害在这里。** 攻击者拿到完整规则，等于拿到安保布防图——哪里有门禁、哪里没锁门一目了然，可以精准绕过护栏。泄露提示词比泄露一般源码更麻烦，因为它直接暴露了防御边界。
3. **信任与合规层：看运气。** 如果提示词里写着“遇到某类问题如何淡化”“不要承认 XX”，被公开就是公关事件；更糟的是，如果里面混进了 API key、内部接口地址、真实用户样例，那就是事故级。

给一个判断框架，三个问题自测：提示词里有没有真正的秘密？有没有能被针对性绕过的护栏规则？有没有不该以明文存在的数据？三个都答“没有”，损失主要是面子；有一个答“有”，就得按安全事故流程处理。

## 四、为什么“提示词护城河”注定越来越窄

- **能力侧**：o1、R1 这类推理模型崛起，function calling 标准化，长上下文普及，都在降低产品对“咒语”的依赖。提示词正在从魔法咒语退化为普通的工程文档
- **技术侧**：对文本做 DRM 几乎无解，模型必须读到才能执行，能读到就可能被“念”出来。密码学里一百多年前就有柯克霍夫原则（Kerckhoffs's principle，1883）：系统的安全性不能依赖算法保密，只能依赖密钥。翻译到 LLM 语境：不能指望“提示词没人看过”，只能指望验证与过滤环节足够硬
- **商业侧**：Web 时代的前端代码从来没真正保密过，二十年来没人靠 JS 源码保密做成生意。AI 产品的真壁垒同理：数据飞轮、评估集（evals）、工具生态、集成深度、品牌信任。提示词只是这堆资产外面的一层皮

## 五、写给开发者的防御清单

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-02/4a88161e257b6bdd.png)

1. **威胁建模反着来**：设计之初就假设 system prompt 100% 会公开。任何“因为没人知道所以安全”的假设，都删掉
2. **敏感逻辑出提示词**：权限判断、内容审核交给服务端代码和独立分类器去做。提示词负责引导行为，不承担安防职责，它也承担不了
3. **提示词里禁放秘密**：API key、内部地址、真实用户数据，一律不进 prompt
4. **输入输出双侧过滤**：输入侧对“复述上文”类模式做检测，输出侧对疑似提示词片段做匹配拦截，再配定期红队测试
5. **给提示词瘦身**：27 万字里大概率七成是历史补丁。版本化、写测试、定期重构，把它当代码管理，而不是当密文供着

## 最后，三条冷思考



1. **保密不是安全策略。** 把核心安全寄托在“提示词没人看过”，等于把钥匙藏门口垫子底下，还发动态告诉别人藏得很好。安全要建在验证、过滤和最小权限上
2. **27 万字本身就是管理信号。** 提示词膨胀到小说体量，通常说明团队在用话术补工程。每次想往提示词里塞新规则之前，先问一句：这个问题能不能在模型层或代码层解决？
3. **对独立开发者：别把提示词当护城河。** 它迟早会被念出来。把精力投到数据、评估和工作流上，这些东西，模型念不走。
