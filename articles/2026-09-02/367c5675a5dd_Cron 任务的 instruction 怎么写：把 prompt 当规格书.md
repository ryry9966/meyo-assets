## 背景

OpenClaw 里的 cron 任务和聊天最大的区别是**无人值守**：到点触发、执行一条 instruction、把结果送到某个出口，全程没有追问的机会。聊天里指令写糊了可以来回澄清，定时任务不行——instruction 就是全部需求文档，写糊了任务就糊着跑，而且每周准时糊一次。

本文记录我给几个日报/巡检类任务调 instruction 的过程，以及最后沉淀下来的一套写法。

## 问题：聊天体 prompt 的三个典型病

1. **指令含糊**："帮我整理一下今天的资讯"——"今天"是哪个时区的今天？"资讯"什么范围？模型只能猜。
2. **没有输出契约**：结果写到哪、什么格式、多长，全靠发挥。跑一周后格式漂移得亲妈都不认识。
3. **没有失败分支**：数据源空了、工具超时，模型怎么办？没有约定时，它多半会"好心"地编一条凑数。

## 做法：把 instruction 当规格书写

我现在的模板是六段结构：

1. **运行上下文**：绝对时间语义。框架支持运行时注入日期（如 `{{date}}`）就用注入，绝不让模型猜。
2. **任务目标**：一句话，单一职责。一个 cron 只干一件事。
3. **输入与边界**：数据从哪个工具/文件来，允许处理什么、禁止碰什么。
4. **输出契约**：目的地 + 固定格式骨架 + 长度上限。
5. **异常分支**：空数据输出约定标记、部分失败如实记录、拿不准就跳过。
6. **禁止项**：不追加任务、不改格式、不做指令外的事。

一个日报任务的骨架示例：

```markdown
# 任务：每日技术日报
## 运行上下文
运行日期：{{date}}（Asia/Shanghai）。"今日"仅指该日期。
## 目标
读取 reads/today.json，筛选评分 >= 4 的条目生成日报。
## 输出契约
写入 reports/{{date}}.md，固定骨架：## 头条 / ## 其余 / ## 数据说明，全文 <= 500 字。
## 异常
- today.json 不存在或条目为 0：只写"## 数据说明：今日无数据"，禁止虚构条目。
- 工具部分失败：在"数据说明"中列明失败项。
## 禁止
不要执行本文件描述之外的操作。
```

## 踩坑点

- **相对时间是头号杀手**。"昨晚""最近三天"一律换成注入的绝对日期，否则时区和统计边界全靠运气。
- **"没数据就自己补充"等于明示幻觉**。改成"输出约定的空标记"。
- **每次运行是无状态的**。要实现"别重复推送"，就得让任务读写一个状态文件（如 `last_sent.txt`），并把这条约定显式写进 instruction。
- **输出不设上限**，第一周就能把频道刷穿。
- **prompt 里的示例会过期**。改格式时把样例一起改，模型会忠实复刻过时样例。
- **上线前手动 dry-run**：同一份 instruction 当一次性任务跑 3–5 次，输出稳定再挂 cron。

## 可复用建议

- 按"日报类 / 巡检类 / 同步类"沉淀 instruction 模板库，新任务从模板复制再改，不从头写。
- 输出能上 schema 就上 schema，配一个十来行的后置校验脚本，校验失败单独告警——这是发现 prompt 退化的第一信号。
- instruction 进版本管理，每次改动写一行 changelog。排查"这周输出怎么变了"全靠它。
- 复杂流程拆成多个小 cron + 状态文件接力，别写 300 行的全能 instruction，那是灾难的温床。

## 总结

Cron 任务的 prompt 不是聊天，是规格书。核心就三件事：**时间语义绝对化、输出契约固定化、异常路径显式化**。写完先手动跑几次，稳定了再交给调度器——调度器只会准时执行你的含糊，不会替你澄清。
