## 背景

在 OpenClaw 的插件与自动化流程里，只要下游要执行工具调用、写库或联动 MCP，就绕不开把 LLM 自由文本转成结构化数据这一步。理想输出是一行干净的 JSON，现实是同一个 prompt 今天包 `<json>` 标签，明天给 Markdown 围栏，后天在 JSON 前多一句"以下是结果"。解析层如果只写一个 `json.loads`，上线第一天就开始收告警。

## 问题

实际观察到的混合格式大致五类：

- 同一回复里标签、围栏、裸 JSON 混用，甚至出现两个代码块（先解释、后结果）；
- JSON 前后带自然语言前后缀；
- 语法瑕疵：尾逗号、单引号、字符串内未转义换行、中文全角引号；
- `max_tokens` 截断导致的半截 JSON；
- 格式对了但字段缺失或类型漂移。

前四类是"解析失败"，最后一类是"解析成功但校验失败"，必须分开处理。

## 做法：分层管道

把解析收敛成一个中间件，按**抽取 → 修复 → 校验 → 重试**四层走：

**1. 抽取层：多候选提取，不赌单一格式**

```python
PATTERNS = [
    r"<json>\s*(.*?)\s*</json>",
    r"```json\s*(.*?)\s*```",
    r"```\s*(.*?)\s*```",
]

def candidates(text):
    for pat in PATTERNS:
        for m in re.finditer(pat, text, re.S):
            yield m.group(1)
    yield balanced_scan(text)  # 字符串感知的括号配对扫描
    yield text.strip()         # 裸 JSON 兜底
```

**2. 修复层：只做可证明无损的修复。** 依次尝试：剥前后缀噪声、删尾逗号、全角引号替换、`True/None` 转 `true/null`。所有候选项逐个过 `json.loads`，第一个成功者胜出。

**3. 校验层：Pydantic / JSON Schema 兜底。** 解析成功不等于数据可用，字段缺失、类型漂移在这里拦截，报错要带上具体字段路径。

**4. 重试层：把错误喂回去。** 失败时将"原始输出 + 具体报错"拼进重试 prompt，限 2 次；仍失败就抛结构化错误给上层，绝不返回空对象静默吞掉。

## 踩坑点

1. **贪婪正则跨块吞并**：`r"```(.*)```"` 会把两个代码块之间的说明文字一起捕获，必须非贪婪并遍历所有匹配逐个尝试。
2. **括号配对不看字符串**：`{"a": "}"}` 会让朴素计数法当场翻车，扫描器必须维护"是否在字符串内"的状态。
3. **修复改变语义**：尾逗号可以放心删，盲目把单引号换双引号可能改掉字符串内容，所有修复动作必须打日志、可审计。
4. **截断 JSON 硬修**：自动补括号"修好"的半截数据往往字段不全。识别到截断（长度贴着 max_tokens）直接走重试，不要修。
5. **只盯解析率**：直通率、修复率、重试成功率要分开统计。修复率悄悄上涨，通常意味着上游 prompt 在退化。

## 可复用建议

- 解析逻辑只放一个模块，业务代码里禁止出现裸的 `json.loads(llm_output)`；
- 运行时若支持原生结构化输出或工具调用强约束，优先用它，标签协议只做兼容层；
- prompt 与解析器同步版本化，改格式契约两边一起动；
- 把解析失败以结构化错误回传给 agent，给它自纠机会，而不是兜底空对象；
- 建立格式回归集：把线上真实脏输出存下来，每次改解析器全量跑一遍。

## 总结

防御性解析的本质不是把解析器写得更聪明，而是承认输出不可控，把不确定性拆进四层分别隔离：抽取层解决"JSON 在哪"，修复层解决"语法瑕疵"，校验层解决"数据不可用"，重试层解决"整体失败"，再配上分层指标，问题出现时你能立刻定位是哪一层在漏水。记住一条原则：宁可 loud fail，不要 silent fallback。
