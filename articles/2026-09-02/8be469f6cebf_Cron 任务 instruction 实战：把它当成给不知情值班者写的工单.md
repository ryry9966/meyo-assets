## 背景

OpenClaw 的 cron 能力本质是两件事的组合：一个调度时间（cron 表达式），一份 instruction（到点后喂给 agent 的 prompt）。很多第一次用的同学会把 instruction 写成一句话，比如"每天早上给我发个日报"，然后发现第一次触发就翻车。

原因很简单：**cron 触发的会话是一次性的、无上下文的**。它不像平时和 agent 聊天，有历史记录可以援引。到点醒来时，agent 手里只有那份 instruction，别的什么都没有。所以 cron instruction 的写法，本质上是一种受限条件下的 prompt 工程。

## 问题

举几个我见过的典型翻车：

1. **时间写了两遍**。cron 表达式已经定了 9 点，instruction 里又写"每天早上 9 点"。轻则冗余，重则 agent 在时区上自行理解，跑出和预期差 8 小时的结果。
2. **依赖不存在的上下文**。"接着昨天的进度继续"——cron 会话里没有"昨天"。
3. **没有失败兜底**。数据源挂了，agent 为了"完成任务"开始编造，你收到一份看起来很正常的假日报。

共同点是：把 instruction 当成了给熟悉情况的同事发的一条微信，而不是给一个不知情的值班者派的工单。

## 做法

我固定用一个"工单模板"，六段：**任务、输入、规则、输出、异常、禁止**。以每日 issue 巡检为例：

```text
任务：仓库 issue 每日巡检（定时任务，不要向用户提问）
输入：用 github 工具列出 my-org/my-repo 近 24h 内新增或更新的 open issue
规则：
- 只关注 label 含 bug 或 help wanted 的 issue
- 每条一行：编号、标题、是否有新评论
输出：汇总不超过 10 行，发送到频道 dev-alert
异常：工具调用失败或超时，直接发送"今日巡检失败：<原因>"，禁止编造数据
禁止：不做任何写操作（不评论、不改状态），不修改任何配置
```

几点说明：

- **"不要向用户提问"要显式写**。定时会话里没人接话，agent 一旦停下来等回复，任务就静默失败了。
- **输入必须落到具体工具和参数**。"看一下仓库"和"用 github 工具列出近 24h 的 open issue"是两个难度级别的任务。
- **异常分支比成功路径更重要**。明确"失败时报告失败"，能挡住大部分幻觉输出。
- **写完先手动触发一次再挂调度**。别让第一次真实触发变成测试。

## 踩坑点

- **时区**。先确认调度器用哪个时区，instruction 里不要再出现模糊时间词（"早上""下班前"）。
- **输出目标不写清**。不指定频道或会话，agent 会发到默认会话，早晚出事故。
- **指令写成小作文**。超过一屏的 instruction，agent 大概率跳步。复杂任务拆成多个 cron，或让主任务调子 agent。
- **一次触发做太多事**。巡检 + 汇总 + 清理 + 通知塞进一个任务，排查会很痛苦。一个 cron 只做一件事。

## 可复用建议

1. 把 instruction 当工单写：谁、在什么前提下、用什么工具、做什么、输出到哪、失败怎么办。六要素缺一个补一个。
2. 输出用固定模板。固定格式的消息后续好解析、好回溯，也能直接喂给下游脚本。
3. instruction 放进配置文件走版本管理，改一次提交一次，出问题能回滚。
4. 每月 review 一遍：数据源可能换了、工具名可能改了，instruction 不会自己更新。

## 总结

Cron instruction 的核心认知就一条：**到点醒来的 agent 对你的世界一无所知**，你写给它的那几行字是它唯一的信息来源。用"给不知情的值班者写工单"的标准去写——具体、无歧义、有兜底、有边界——大部分翻车都能提前避免。
