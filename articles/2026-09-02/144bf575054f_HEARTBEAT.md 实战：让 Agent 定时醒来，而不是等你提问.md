## 背景

大多数 Agent 的交互模型是拉式的：你提问，它回答，会话结束就沉寂。OpenClaw 里有一条容易被忽略的机制——心跳（heartbeat）。Gateway 按固定间隔（默认约 30 分钟，可配置）唤醒主 Agent，让它读一次工作区里的 `HEARTBEAT.md`：文件为空就保持沉默，有内容就把条目当成本轮要做的事。

这意味着 Agent 可以"主动做事"，前提是你把任务写清楚。

## 问题

我最初的用法很粗糙：把七八条监控和日报全塞进去，间隔用默认值。两周内暴露三类问题：

1. 每次心跳全量跑一遍，token 消耗随任务数线性上涨；
2. "没有异常"的检查也照常汇报，消息流被刷屏；
3. 某条任务里放了 API key，直接进了模型上下文。

## 做法

现在的结构稳定成这样：

**1. 任务分两类写。**"条件触发型"写明阈值和输出规则，如"检查磁盘水位，超过 85% 才通知"；"定时推送型"（每日摘要等）不放心跳里，改用系统 cron 定时发 prompt，避免心跳间隔取整带来的时间漂移。

**2. 控制面和数据面分离。**HEARTBEAT.md 只写"何时看、看什么、什么算异常"，采集动作交给脚本或 MCP 工具，心跳时 Agent 只调用并读结果。文件控制在 20 行以内。

**3. 显式写沉默规则。**文件开头第一行就声明"若无异常，本轮不发送任何消息"。这句话比任何配置都管用。

一个当前在跑的精简示例：

```markdown
# Heartbeat

若无异常，本轮保持沉默。

## 巡检
- 磁盘水位：使用率 > 85% 时通知，附最大的三个目录
- 收件箱：未读 > 20 或含 urgent 时汇总，否则跳过

## 禁止
- 不重复发送上一轮已汇报且无变化的结论
```

**4. 调参验证。**测试期把心跳间隔临时调到 1 分钟，观察几轮行为再恢复 30 分钟；夜间不需要巡检就用 `activeHours` 限时段。注意每个 Agent 有独立工作区，改的是对应 workspace 下的那份文件。

## 踩坑点

- **长任务不要放进心跳**：一次心跳被阻塞，后续轮次会堆积。采集逻辑下沉到脚本，心跳只读状态文件。
- **秘钥绝不写进 HEARTBEAT.md**：它会被注入上下文，用环境变量或 MCP 凭据。
- **沉默规则不写，Agent 默认"有活干就要汇报"**，刷屏几乎必然发生。
- **过期任务及时删**：这是热路径文件，不是备忘录。

## 可复用建议

- 把 HEARTBEAT.md 纳入 git，每次只改一处，行为变化可回溯；
- 每周复盘一次：统计心跳轮次里"沉默/输出"的比例，输出占比高于三成，说明任务写得不够克制；
- 新任务先放到测试 Agent 的心跳里跑三天，确认输出格式和阈值再上主 Agent。

## 总结

HEARTBEAT.md 的价值不在于"自动化"三个字，而在于把 Agent 的职责从应答器扩展成巡检员。核心就三条：任务分层、沉默优先、重活下沉。文件很短，但它决定了你的 Agent 是一个工具，还是一位同事。
