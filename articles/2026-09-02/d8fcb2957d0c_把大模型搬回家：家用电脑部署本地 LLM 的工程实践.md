# 背景

Agent 和 MCP 工作流跑起来之后，一个现实问题很快浮出水面：后端模型选什么。云 API 按量计费，长 Agent 任务跑一晚上花几十块很正常；而很多自动化场景——本地文件整理、隐私数据摘要、常驻监控——本来就不该把数据送出去。本地部署不是替代云，而是给 Agent 体系补一层「便宜、离线、可控」的底座。

# 问题

大部分人卡在三个认知偏差上：

1. 把「能跑」当成「能用」。7B 模型能加载，不代表它能稳定完成多轮工具调用。
2. 忽略上下文长度的显存开销。KV cache 随上下文近线性增长，标称 32K 拉满时显存占用可能直接翻倍。
3. 低估运行时和模型的配合——工具调用能否被正确解析，取决于模型和推理框架两边都支持。

# 做法

我的环境参考：Ryzen 7 + RTX 4070 Ti Super 16G + 64G 内存。步骤如下：

1. **选运行时**。Ollama 上手最快，llama.cpp 控制粒度最细，vLLM 适合显存充裕要并发。推荐从 Ollama 开始，它自带 OpenAI 兼容端点（`localhost:11434/v1`），OpenClaw 侧只需改 `base_url` 即可接入。
2. **选模型和量化**。中文 + 工具调用场景，Qwen 系列是目前性价比最稳的选择。起步建议 Q4_K_M 量化的 14B，显存占用约 9-10GB，16G 卡还能给 KV cache 留余量。7B 只适合做路由、分类这类轻任务。
3. **压上下文**。Agent 场景别贪 32K，8K-16K 覆盖大多数 MCP 工具往返，显存和速度都健康。
4. **最小验证**。写一个最小 Agent 流程：一个工具、五轮对话，确认工具调用格式被正确解析、参数合理，再上真实任务。
5. **参数固化进配置**：temperature 0.2-0.4，`num_ctx` 显式指定，`keep_alive` 拉长避免反复冷加载。

# 踩坑点

- **n_ctx 默认值坑**：部分运行时默认上下文只有 2K/4K，Agent 跑几轮就截断，典型症状是「模型忘了系统提示」。一定要显式设置。
- **工具调用幻觉**：小模型会编造不存在的参数名，或把 JSON 参数写成字符串套字符串。14B 以下慎用于多工具 Agent。
- **并发退化成串行**：本地推理默认排队，Agent 并行调三个工具会变成串行叠加耗时。要么改串行编排，要么上 vLLM。
- **量化降级不均匀**：Q4 对闲聊几乎无损，但对严格 JSON 输出的影响可感知。工具调用报错率上升时，先升到 Q5/Q6，再怀疑提示词。

# 可复用建议

1. **建自己的评测集**：从真实 Agent 任务抽 10-20 个 case，每次换模型或量化跑一遍，记录工具调用成功率、tokens/s、首 token 延迟。比看榜单有用得多。
2. **做路由而非替换**：本地模型接简单任务（分类、摘要、格式转换），复杂推理留给云 API，一层简单 router 即可。
3. **写模型卡**：量化版本、运行时版本、ctx 设置、实测性能都记下来，三个月后你会感谢自己。

# 总结

本地 LLM 的价值不在「跑通了 demo」，而在稳定融入 Agent 工作流。硬件门槛比想象中低——16G 显存加 14B Q4 就是可用的起点，但上下文、工具调用、并发这些工程细节决定了它是玩具还是生产力。建议小步上线，用真实任务数据驱动每一次换挡。
