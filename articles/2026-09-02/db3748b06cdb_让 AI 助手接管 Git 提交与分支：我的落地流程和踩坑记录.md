## 背景

写提交信息、清理已合并分支、给 PR 补描述，这些事单次成本很低，架不住天天做。我的做法是把这几个高频动作交给常驻的 AI 助手（OpenClaw + 受控 shell 工具 / MCP git server），让它读仓库状态、生成提交信息、执行低风险操作。跑了一个多月，下面是实际的落地方式和遇到的问题。

## 问题

直接把 git 权限丢给 Agent 是不行的：它会 `git add -A` 把 `.env` 带进暂存区，会在你不想动的时候 rebase，生成提交信息时也可能编造 diff 里根本不存在的改动。核心矛盾是：**自动化程度和风险控制要成正比**，不能一刀切。

## 做法

### 1. 权限分三层

在我给 Agent 的 skill 文件里写死了边界：

```text
- 只读操作：status / diff / log，直接执行
- 本地写操作：commit、branch -d，先输出摘要，确认后执行
- 远程写操作：push / force / rebase，硬性要求人工确认
- 禁止 git add -A，必须逐文件确认暂存内容
- 提交信息用 Conventional Commits，正文中文
```

原则是：读随意、本地写要过目、远程写必须人拍板。

### 2. 提交流程

我对 Agent 的指令是固定三步：先 `git status` + `git diff --staged` 拿到真实改动；再基于 diff 生成提交信息，并要求信息里的每一条都能在 diff 中找到出处；最后把文件列表 + 信息一起展示给我，我回个"确认"才执行。改动大时会要求它分文件摘要，而不是硬塞进一次调用。

### 3. 分支清理

每周让 Agent 扫一遍本地仓库：列出已合并到 main 的分支、超过两周无提交的分支，先给清单不动手。我勾选后才执行 `branch -d`（不是 `-D`），删不了的留着人工处理。

## 踩坑点

- **diff 太大导致摘要失真**。几百行的 diff 让 Agent 一次总结，提交信息会含糊其辞。改成超过 200 行就分文件摘要，质量明显回升。
- **`git add -A` 是事故源头**。第一次试跑就把本地的调试脚本和构建产物提交了。之后改成逐文件确认，虽然多一步，但值得。
- **编造提交信息**。早期的输出里出现过"优化了性能"这种 diff 里找不到依据的描述。加了"每条描述必须对应 diff 中的具体改动"这条约束后基本杜绝。
- **确认疲劳**。所有操作都要确认，人会开始无脑回"确认"。后来把纯只读操作改成静默执行，只在写操作时打断，确认的含金量才回来。
- **token 成本**。大仓库频繁 diff 比想象中烧 token，控制扫描频率（提交时触发而非定时轮询）后降了一半以上。

## 可复用建议

1. **把 skill 文件当代码维护**，进版本库，改规则走提交，出问题可回溯。
2. **所有 Agent 执行的 git 命令落日志**，出事后能还原现场。
3. **删分支、改历史一律先 dry-run**，输出计划再执行。
4. 用 Conventional Commits 不只是为了规范，下游的 changelog 生成和 Agent 理解历史都受益。
5. 权限边界靠工具层限制（比如只暴露白名单命令），不要指望提示词自觉。

## 总结

AI 管 Git 的价值不在"全自动"，而在把写提交信息、挑分支名、扫过期分支这类重复判断外包出去，人只保留真正需要判断的环节。安全边界要靠权限分层和工具层约束来兜底，提示词只是第一道防线。跑通之后，每天的提交质量比手写稳定，仓库也干净了不少——这笔账是划算的。
