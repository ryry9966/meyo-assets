## 背景

Agent 的价值在于“能动手”。OpenClaw 本身负责规划与决策，但真正产生业务效果的往往是外部服务：查工单、发通知、读写数据库、触发 CI。对接外部服务，是每个 OpenClaw 实践者绕不开的一步，也是区分“玩具 demo”和“能上生产”的分水岭。

## 问题：让模型直接拼 HTTP，为什么不划算

常见的偷懒做法是在提示词或脚本里直接塞 API 调用逻辑。短期跑得通，长期一定出事：

- 密钥散落在提示词、脚本、聊天记录里，随时可能泄漏；
- 没有超时和重试策略，服务一抖 agent 就挂死；
- 返回的大 JSON 直接灌进上下文，几次调用后 token 就爆了；
- 接口一改版，全链路静默失败，模型还在一本正经地编造结果。

## 做法：把握手拆成四步

**1. 选对接路径。** 优先用现成的 MCP server，社区维护过的通常更稳；没有就自己写一个薄封装，只把目标服务 3~5 个高频操作暴露为工具。不要把整个 REST API 平铺成几十个工具——选择太多，模型反而容易选错。

**2. 认证收敛。** 密钥放环境变量或 secret 管理，MCP server 启动时注入。配置文件里只留引用名，不留明文。

**3. 定义工具边界。** 每个工具的 description 写清楚“什么时候用、什么时候别用”、参数含义、返回结构。写操作（发消息、建工单）显式标注，方便在权限层拦截。

**4. 验证与限流。** 上线前先用只读凭据跑一轮；设置超时（比如 10 秒）和有限次数的重试；对返回结果做截断或分页，避免一次查询撑爆上下文。

## 踩坑记录

- **工具描述太模糊**，模型把“查询”工具当“删除”用。description 是给模型看的接口文档，值得花时间写。
- **重试无幂等**：网络抖动重发，导致重复下单、重复发消息。写操作必须带幂等键，或在服务端去重。
- **密钥进了日志**：MCP server 打日志前先脱敏，尤其是请求头。
- **schema 漂移**：上游 API 升级后工具校验失败，表象是 agent 反复重试。排查顺序应该是：先怀疑 schema，再怀疑模型。
- **权限给太大**：拿到 write token 就全量使用，出事后无法追溯。按最小权限拆分凭据。

## 可复用建议

- 一个服务一个 MCP server，单一职责，坏了单独重启，互不拖累。
- 工具命名用“服务_动作”格式（如 `tickets_create`），能明显降低模型混淆的概率。
- 给每次外部调用留一条结构化日志：工具名、参数摘要、耗时、状态码。排障效率差一个量级。
- 维护一份“能力清单”：接了哪些服务、认证方式、限流额度、负责人。新人上手和事故复盘都靠它。

## 总结

Agent 与外部服务的对接，本质是一次**受控的握手**：模型只负责决定“调什么、什么时候调”，认证、超时、幂等、限流这些工程约束全部下沉到 MCP server / 插件层。把边界画清楚，OpenClaw 才能长期稳定地“动手”，而不是每接一个新服务，就把踩坑史重演一遍。
