## 背景

Agent 的能力上限，往往不取决于模型本身，而取决于它摸得到哪些服务。OpenClaw 里的 agent 要真正干活，就得调用外部 API：查工单、发消息、读数据、触发 CI。这一步做不好，前面所有提示词工程都是空转。

## 问题

常见的错误做法有两类：一是把 API 文档整段塞进 system prompt，指望模型自己“看文档写请求”；二是给 agent 一个万能的 `http_request` 工具让它自由发挥。结果都差不多——端点瞎编、鉴权头丢失、响应把上下文撑爆、重试时重复下单。本质上，Agent 与 API 的握手需要一层**契约**，而不是一次性的自由对话。

## 做法：窄工具 + 厚中间层

1. **选对接路径。** 目标服务有现成 MCP server 就直接挂载；内部 API 或需要定制逻辑的，用 OpenClaw 插件机制自己包一层。别为省事让 agent 裸调 HTTP。
2. **把工具定义写窄。** 一个工具只做一件事，参数用 enum 和取值范围兜底。工具的 description 是给模型看的接口文档，要写清楚“什么时候该用我、不该用我”——这比堆 few-shot 更有效。
3. **鉴权收在工具层。** API key 放配置或环境变量，由插件注入请求头，永远不出现在 prompt 或工具参数里。模型只描述意图，不接触凭证。
4. **错误返回结构化。** 把 401/429/超时这类原始报错，翻译成 agent 能推理的一句话，比如“凭证过期，请提示用户重新授权”。写操作强制带幂等键，重试才不会出事故。
5. **截断响应。** 工具返回前做字段筛选和长度裁剪，只给 agent 需要的 JSON 片段，全量数据落日志。

## 踩坑点

- 工具描述含糊，agent 会把 `update_status` 当 `create_ticket` 用。描述里写清动词边界。
- 返回整页原始 JSON，几轮对话后上下文直接爆炸。
- 写接口没做幂等，网络抖动一次重试就重复扣款。
- 工具注册太多（超过一屏），agent 开始选错工具；按场景分组或动态挂载。
- 忽略对方服务的限流，批量调用被 429 打崩且没有兜底退避。

## 可复用建议

- 每个工具上线前问三个问题：谁该用我？失败时模型能看懂吗？重试安全吗？
- 先跑 dry-run：工具调用只打印不执行，人工核对 agent 的决策序列，再放开真实执行。
- 所有调用记日志：时间、参数摘要、状态码、耗时，排障基本全靠它。

## 总结

对接外部服务的核心不是“让 agent 会调 API”，而是把协议适配、鉴权、错误翻译、重试控制这些脏活沉淀在工具层，给模型留一个窄而清晰的握手面。中间层做得越厚、越诚实，agent 的行为就越稳定——这也是 OpenClaw 插件和 MCP 生态真正该发力的地方。
