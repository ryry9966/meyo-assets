## 背景

大部分 agent 交互是问答式的：你发消息，它响应。但 OpenClaw 的架构——常驻网关、插件和 MCP 工具链、可持续运行的后台进程——天然具备另一个可能性：助手可以定时醒来、可以接收事件、可以在你没开口时就把事办了。

问题在于，多数人把 proactive 简单理解成"加个 cron，让模型定期看一圈再汇报"，跑两周就放弃了。

## 问题

这个朴素做法会同时踩中三个坑：

1. **噪音**：模型为了显得有用，把不重要的事也报出来，一周后你开始无视它的所有消息；
2. **成本**：每次心跳都全量扫描上下文，token 账单先于价值到达；
3. **越界**：它主动执行了写操作——改文件、发消息给同事——而用户并没有授权这种"贴心"。

主动性的核心不是"多做"，而是**在正确的阈值上做正确的事，其余时间闭嘴**。

## 做法

我把它拆成四层来搭：

**1. 触发层。** 三种触发源：cron 心跳（粗粒度，比如每天两次）、事件 webhook（CI 失败、PR 更新、邮件到达）、状态监听（日志关键词、文件变化）。原则：便宜的事件源先行，昂贵的 LLM 判断只在有信号时触发。

**2. 判断层。** 写一个独立的 proactive policy skill，明确回答三件事：什么算"值得打扰"（阈值）、什么情况必须沉默、哪一级动作允许自动执行。关键一条：prompt 里明确写"**沉默是合法且优先的输出**"——不写这句，模型一定会硬找话说。

**3. 状态层。** 本地状态文件记录已报告过的事件 ID 和静默期。没有去重，同一个 CI 失败会提醒你五遍，然后你直接关掉整个功能。

**4. 执行层。** 动作分四级：只读分析 → 打草稿 → 通知你 → 直接执行。默认授权只到"通知"，写操作逐项解锁。所有主动行为落日志，用户回一句"这事别再报了"，就写回策略文件。

举一条真实链路：CI 失败 webhook 进来 → 判断层只拿错误堆栈和最近一次成功 commit 的 diff（短上下文）→ 命中已知模式且满足阈值（主分支、阻塞他人）→ 执行"通知"级动作，把摘要和候选修法发到会话；否则输出沉默，什么都不发生。

## 踩坑点

- **心跳间隔照抄别人的配置。** 我的教训：从每天两次起步，观察一周信噪比再加密，而不是反过来。
- **判断和执行放同一次调用。** 拆开后判断用小模型、短上下文，执行才挂全量工具，成本降一个量级。
- **多入口各自记状态。** 手机端和桌面端重复通知，状态必须收敛到网关一处。
- **策略写进 prompt 就不管了。** 策略是会演化的，放进版本控制，像改代码一样改它，每次调整留 commit message。

## 可复用建议

- **唯一 KPI 是信噪比**：统计每条主动消息是否被点开或回复，低于阈值就收紧策略，而不是加功能。
- **让"什么都不做"成为一等公民**：判断层输出三态——行动 / 通知 / 沉默，沉默占大头才算健康。
- **渐进授权**：新类型的主动任务先跑两周"只通知不执行"，用户认可后再解锁下一级。
- **每类任务独立开关**：永远不要给用户一个总的"关闭主动性"的理由。

## 总结

Proactive 不是加一个定时任务，而是一套触发、判断、状态、执行分离的小型系统工程。它是否成功的标准只有一个：一个月后，你有没有重新开始无视它的消息。
