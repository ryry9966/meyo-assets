## 背景

在 OpenClaw 里，cron 任务是最容易被低估的功能：配一行调度，写一段 instruction，agent 就定时自己跑。我最初把聊天里用得顺手的 prompt 直接粘过去，结果连续翻车：任务显示“已执行”但什么也没发生，或者输出格式每次都不一样。调了十几个任务之后，我确认了一件事——cron instruction 和普通对话 prompt 是两种东西，它是写给一个**无人值守、冷启动、没人回答问题**的执行者的。

## 问题出在哪

三个结构性差异：

1. **没有上下文**。cron 触发的是全新会话，你在聊天里攒下的约定、偏好、别名，它一概不知道。
2. **没有人兜底**。对话里模型不确定会追问你，cron 里它只能猜，猜错就静默跑偏。
3. **输出没有落点**。聊天里回复天然给人看，cron 里 agent 干完活，结果如果没有明确去处，等于没干。

## 做法：五段式模板

我现在每个 cron instruction 都按这个骨架写：

```
【目标】一句话说清做什么、给谁看。
【来源】写死要用的工具/MCP 名字和参数，不写"查一下"。
【步骤】1/2/3 有序列表，每步可判定完成与否。
【输出】结果写到哪（文件路径/频道/消息格式），给出示例结构。
【异常】工具失败或数据为空怎么办；明确禁止事项。
```

举例，一个每天汇总仓库 issue 的任务：

> 【目标】汇总仓库近 24h 新增 issue，发到 #daily 频道。
> 【来源】用 GitHub MCP 的 list_issues，state=open，按 created_at 过滤。
> 【步骤】1) 拉取列表 2) 按 label 分组 3) 每条取标题、编号、链接 4) 生成不超过 15 行的摘要。
> 【输出】发到频道，格式为“日期 + 分组列表”；没有新 issue 时只发一行“今日无新增”。
> 【异常】接口失败重试一次，仍失败则在频道报告原因，**不要编造数据**。

关键在最后两段。空结果路径和失败路径写清楚了，任务才算有生产环境的样子。

## 踩坑点

- **时区**。“每天早上八点”是含糊的，我在 cron 表达式和 instruction 里都写死时区，两边对齐。
- **幂等**。任务重跑会不会重复发消息？我加一条“发送前检查今天是否已发过”，或让结果先落文件再决定是否推送。
- **指令漂移**。给 agent 留太多“自由发挥”空间，跑两周输出格式会慢慢变形。格式约束越死越耐久。
- **一次做太多**。一个任务塞拉数据+分析+发报告+清理，任何一环失败全链路报废。拆开，各自独立可测。
- **先手动触发**。任何 cron 上线前先手动 run 一次，看完整执行日志，逐个确认工具调用符合预期。

## 可复用建议

- 把 instruction 当代码管理：存 git，改动能 diff，坏了能回滚。
- 项目里留一个模板文件，新任务复制改参数，别每次从零写。
- 让每次运行留痕：输出顺带写一份到日志文件，排障不用猜。
- 用到 MCP 工具的，先在对话里手动试一遍工具的失败模式，再把应对写进异常段。

## 总结

Cron instruction 的本质，是给一个没有记忆、不会提问、干完就走的执行者写交接文档。把目标、来源、步骤、输出、异常五段写死，先手动验证，再交给调度器，它就能稳定跑很久。检验标准很简单：一个从没见过这个任务的人，拿到这份 instruction 能不能一次跑对。能，就说明你写的是任务说明；不能，你写的只是聊天记录。
