## 背景

OpenClaw 的 cron 功能，本质是"到点唤醒 agent，执行一段 instruction"。听起来很简单，但大多数人第一次写时，都会把 instruction 当成一条聊天消息："帮我看看今天的 issue，有新的就告诉我。"上线后的结果往往是：要么收不到消息，要么同一条内容连推三天，要么彻底沉默。

原因只有一个：**定时任务的执行环境和你创建它时的对话完全隔离**。cron 触发那一刻，agent 没有聊天历史，没有你脑子里的背景，只有 instruction 本身和它手上的工具。

## 三个典型翻车现场

1. **失忆执行**。instruction 里写"之前说的那个仓库"，执行时这是空引用，agent 只能猜，猜错就跑偏。
2. **静默失败或刷屏**。不写输出去向，结果落在默认会话里；或者空结果也发一句"今天没有内容"，一周后你开始无视这个频道。
3. **无状态重复**。"过去 24 小时的新 issue"如果不记录已推送项，同一条 issue 会被推到天荒地老。

## 做法：六段式模板

我现在所有 cron instruction 都按这个骨架写：

1. **目标**：一句话说清"现在执行什么"。时间归 cron 表达式管，instruction 里别再写"每天早上"。
2. **来源**：写死要用的工具和资源名（repo、URL、MCP 工具名），不让 agent 猜。
3. **步骤**：2–4 条，每条一个动作。
4. **输出**：发到哪个会话、什么格式、上限几条。
5. **异常**：区分三种结局——有数据、没数据、执行失败，每种都有明确行为。
6. **状态**：需要去重的，先读后写 workspace 里的状态文件。

一个实际例子：

```text
任务：汇总新 issue。
1. 用 github 工具列出 <org>/<repo> 过去 24 小时新建的 issue，
   时间以当前系统时间（Asia/Shanghai）为准。
2. 读取 workspace 下 state/issues_seen.json，过滤已推送编号；
   文件不存在视为空。
3. 无新 issue：直接结束，不发消息。
4. 有新 issue：按「编号 + 标题 + 链接 + 一句话摘要」整理，最多 10 条，
   发送到 Telegram 默认会话。
5. 完成后把本次编号写回 issues_seen.json。
6. 工具调用失败重试一次，仍失败则发送一行简短错误说明，不贴完整报错。
```

## 踩坑点

- **"今天""最近"是模糊词**。改成"以当前系统时间为准的过去 24 小时"，并点名时区——服务器时区和你的时区经常不一致。
- **空结果和失败要分开**。没数据可以静默，失败必须留痕，但兜底消息一行就够。
- **别塞业务逻辑**。instruction 超过五步，就该把流程沉淀成 skill 或脚本，cron 只负责触发和汇报。
- **上线前手动触发两遍**，再连跑两天确认去重生效，再信任它。

## 可复用建议

- 把六段式模板存进 workspace，新建任务直接抄骨架。
- 每条 instruction 都假设执行者是"第一次接手这个任务的同事"，只看文档就要能干活。
- 输出格式越死板越好：列表、链接、条数上限，别让它自由发挥写小作文。
- 每月清一次 cron，删掉连续失败或你已经不看的任务，僵尸任务比没有任务更扰人。

## 总结

Cron instruction 的本质，是给一个没有上下文、看不见你、只有工具的同事写交接文档。任务跑得稳不稳，几乎完全取决于这份文档是否自包含：时间交给 cron 表达式，行为写进 instruction，三种结局都给出明确行为，状态落盘到文件。按这四条来，定时任务基本不会翻车。
