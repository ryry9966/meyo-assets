## 背景

跑自动化的人迟早会接受一个现实：任务一定会被重复执行。定时任务上一轮没跑完下一轮又触发；Agent 循环里模型对同一个工具调用了两次；MCP 请求超时后客户端自动重试；上游 webhook 重复投递。重试不是异常路径，而是自动化的常态。

幂等性就是针对这个常态的设计约束：**同一个操作执行一次和执行 N 次，最终状态一致**。做到这一点，重试就从"事故风险"变成"无害动作"。

## 问题

非幂等操作在单次测试里几乎不暴露，典型翻车形态：

- 同步脚本用追加而不是覆盖，重跑一次数据翻倍；
- Agent 调用发消息、建工单类工具，重新规划时重复执行；
- 计数、累加类更新叠加执行，账对不上；
- 任务跑到一半崩溃，重启后从头再来，前半段的副作用重复发生。

共同点是：操作语义是"做一次加一件事"，而不是"把状态推进到某个目标"。

## 做法

按投入从低到高，几个层次：

1. **优先选天然幂等的操作形态。** 用覆盖写代替追加写，用 upsert 代替 insert，用"设置目标值"代替"增减多少"。调 API 时优先 PUT 或带唯一键的 upsert。
2. **用稳定标识定位目标。** 按 external_id、路径、主键这类稳定标识寻址，避免"最新一条""上次的文件"这种相对定位——重跑时它指向的对象会漂移。
3. **给非幂等的外部调用加幂等键。** 发送、支付类接口天然不幂等。键必须从任务身份派生，比如 `hash(任务ID + 业务日期 + 输入摘要)`，而不是任务内部随机生成——随机 UUID 每次重试都不同，等于没防。
4. **先记意图，再执行。** 执行前先把"我要做什么"写入本地台账（带唯一键），完成后标记。重试时先查台账：已完成就跳过。这是对不支持幂等键的下游的通用兜底。
5. **长任务按步骤记状态。** 五步任务崩在第四步，一个总的完成标记不够。要么让每一步独立幂等（最省心），要么按步记录进度，恢复时从断点续跑。

## 踩坑点

- **"先检查再执行"有竞态。** 两个并发实例同时查到"未执行"，然后都执行。检查必须落在原子操作上：数据库唯一约束、SETNX、文件锁，而不是应用层的 if。
- **幂等键里混入了时间戳。** 键 = 任务ID + 时间戳，每次重试键都变。键只由"逻辑任务"决定，和"第几次执行"无关。
- **只读不等于无副作用。** 有些"查询"工具会消耗配额、触发下游回调或写审计日志。判断幂等看全部副作用，不只是主数据。
- **Agent 重规划会改参数。** 用参数 hash 做键时，模型第二次调用哪怕只差一个字段就防不住。键要么绑在任务层，要么让工具本身做成 upsert 语义，从根上幂等。
- **锁不是幂等性的替代品。** 锁会过期、机器会挂。锁解决"同时跑"，幂等解决"重复跑"，两个都要。

## 可复用建议

- 自己写 MCP 工具或插件时，默认接受一个 idempotency_key / external_id 参数，内部统一走 upsert。
- 描述任务用目标状态（"让配置等于 X"），不用动作指令（"把 X 加进去"）。
- 把幂等写进测试：同输入连跑两遍，断言终态一致、副作用只发生一次。这比任何代码审查都有效。
- 评审时问一句："这个任务被误触发三次会怎样？"答不上来，就是没设计完。

## 总结

自动化的可靠性不来自"确保只跑一次"——这做不到，也不来自更精确的调度，而来自让每一次执行都可以安全地重复。把幂等当作默认设计约束而非事后补救，重试、重叠、误触发这些日常噪音，就都变成了无害事件。
