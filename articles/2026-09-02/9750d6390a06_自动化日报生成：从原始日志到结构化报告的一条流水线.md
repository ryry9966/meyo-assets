## 背景

团队每天需要一份日报：服务运行情况、异常统计、待办进展。过去是人工登录各系统、翻日志、抄数字、写摘要，一份要 30–40 分钟，还经常漏项。本文记录我们把它做成自动流水线的过程，核心思路一句话：**确定性的事全部交给脚本，LLM 只负责把算好的数据讲成人话。**

## 问题

原始状态有四个明显痛点：

- 日志散落在多个来源，格式不统一（有的 JSON，有的纯文本）
- 手动统计易出错，尤其是计数、比例这类口径敏感的数字
- 直接把原始日志丢给 Agent 会超长，且模型会“编数字”
- 定时任务失败无人知晓，报告悄悄断更好几天

## 做法：五段式流水线

1. **归集**：cron 每天 07:00 拉取前一日各来源日志，原样落盘到 `raw/`，按日期归档，不做任何清洗。
2. **结构化**：解析脚本把日志转成统一 JSON schema（时间戳、来源、事件类型、数值），校验失败的单条进 `reject/`，不阻塞整体。
3. **聚合**：纯脚本/SQL 统计指标——错误数、P95 延迟、新增工单数——产出 `metrics.json`。**所有数字在这一步定死。**
4. **摘要**：Agent 通过 MCP 工具读取 `metrics.json` 和少量异常样本，按固定模板生成中文摘要。prompt 里明确约束：不得引用输入之外的任何数字。
5. **投递**：渲染成 Markdown，发到 IM 群和邮件，同时归档到 `reports/YYYY-MM-DD.md`。

每一步中间产物都落盘，任何一天的结果都可以回放和 diff。

## 踩坑点

- **格式漂移**：上游某次升级改了字段名，解析器静默丢数据。加 schema 校验 + 每日日志条数阈值告警后才兜住。
- **日期边界**：日志是 UTC，报告按本地时区切天，第一天口径对不上。统一内部用 UTC，切窗时再转时区。
- **让 LLM 算数**：早期让模型直接“总结故障率”，数字不可靠。改成模型只写叙述、数字全部来自 `metrics.json` 后才稳定。
- **静默失败**：cron 挂了没人发现。现在无论成败都发一条心跳通知，失败时内容为错误摘要——宁可收到一条“日报生成失败”，也不要无声断更。
- **上下文超长**：不要喂原始日志。喂聚合结果，异常样本每类至多给 3 条代表性的。

## 可复用建议

- 先跑通最小闭环：一个日志来源、一条投递渠道，稳定后再横向扩展来源。
- 把 Agent 定位为“解释层”，不做计算层，也不做过滤层。
- 模板和 prompt 进版本控制，改统计口径时能 diff。
- 给流水线自己做监控——日报工具自己不能是黑盒。
- `reject/` 数据别删，攒一段时间能反推 schema 该怎么演进。

## 总结

这套流水线的价值不在于“用了 AI”，而在于分工清晰：脚本负责采集、校验、算数，Agent 只做语言组织和收尾。跑稳之后，日报从每天 30 分钟人工降到 0 分钟介入，口径一致、可回溯。下一步计划让周报和告警摘要复用同一个聚合层，边际成本很低。
