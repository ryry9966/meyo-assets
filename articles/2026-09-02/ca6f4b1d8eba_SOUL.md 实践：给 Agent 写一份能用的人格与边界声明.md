## 背景

OpenClaw 的工作区里有一组以 Markdown 组织的启动文件：AGENTS.md 管行为约定，TOOLS.md 管工具用法，而 SOUL.md 管“这个 Agent 是谁”。每次会话开始（包括 heartbeat 触发的任务），它们都会注入上下文。SOUL.md 是唯一专门描述人格、语气和底线的位置——它不是配置项，而是一份写给模型看的人物设定。

## 问题

很多人装完就直接用，SOUL.md 留着默认模板甚至空着。后果很典型：

- 同一个助手在 Telegram 里啰嗦、在 CLI 里又冷又短，人格随渠道漂移；
- 过度顺从：你说“把这段转发到群里”，它真发了，事后才发现不合适；
- 长会话语气不稳：上午正经、下午玩梗，越聊越谄媚。

这些不是模型 bug，而是缺少一份明确的、可维护的人格与边界声明。

## 做法

我把 SOUL.md 拆成四段，每段控制在几行：

1. **身份**：一两句说明它是谁、为谁服务、不做什么。例：“你是我的个人工作助理，主要处理日程、草稿和信息整理，不是通用聊天机器人。”
2. **语气**：别写“要友好、要有帮助”这类废话，写可执行规则。“默认简洁，先结论后理由；不确定就说‘我不确定’，不要编。”
3. **红线**：绝对不做的事，逐条列。比如：不主动向第三方发消息、不执行任何付款操作、不删除超过一天的历史记录。
4. **先问再做**：介于两者之间的操作要求先确认。“修改任何对外可见的内容前，先把改动贴给我确认。”

写完用 git 管理。之后 Agent 表现不对，就补一条具体规则，而不是重写整个文件。

## 踩坑点

- **写太长**。SOUL.md 每轮占上下文，上千字的人设会稀释真正重要的规则。我的版本稳定在一页以内——规则越少，越被执行。
- **人格和权限混为一谈**。SOUL.md 是提示词，模型可能忽略。真正的红线必须在系统层兜底：MCP 工具做白名单、支付类插件走人工审批、消息发送加确认流。文本管人格，系统管边界，别指望一份 Markdown 拦住误操作。
- **规则互相矛盾**。AGENTS.md 写“主动整理每日摘要”，SOUL.md 写“不主动做事”，行为就会抖动。改 SOUL.md 时顺手检查其他启动文件。
- **只测 happy path**。不同渠道、不同时段差异很大，至少在两个渠道各跑一周再定稿。

## 可复用建议

- 用“身份 / 语气 / 红线 / 先问再做”四段式起步，之后按事故增量修订；
- 每条规则写成“场景 + 行为”，避免形容词堆砌；
- 三层递进兜底：提示词（SOUL.md）→ 约定（AGENTS.md）→ 硬约束（工具权限与审批流）；
- 每月回顾一次，删掉长期没触发过的规则，保持文件瘦。

## 总结

SOUL.md 的价值不在“让 Agent 更像人”，而在把你的预期变成模型每次都能读到的稳定输入。人格写得具体，行为才可预测；边界写得清楚，才敢把它接进真实工作流。先写十行，跑两周，再补十行——这比一次写一份完美人设靠谱得多。
