## 背景

团队日报大多是"人肉流程"：早上有人去翻前一天的日志，挑几条报错，粘进文档再发到群里。信息不一定全，格式也不稳定，换个人写就是另一种味道。我们把它改造成一条由 OpenClaw Agent 驱动的自动化流水线，每天固定时间产出结构化日报，人工只负责审一眼。

## 问题

两条极端路线都走不通：

- 纯脚本聚合能算出数字，但写不出"今天的异常比昨天有没有恶化"这类判断；
- 直接把原始日志丢给 LLM 总结，token 爆炸、成本高，而且模型会把数字算错——它擅长叙述，不擅长精确统计。

结论很朴素：**统计归脚本，叙述归模型。**

## 做法

流水线分五步，前四步是确定性代码，只有第四步交给 Agent：

1. **采集**：定时任务触发 OpenClaw 任务，通过 MCP 工具拉取各服务日志（文件、API、数据库各对应一个 tool），统一落成本地 JSONL。
2. **解析归一化**：按 logfmt/JSON 规则解析成统一 schema：时间戳、级别、服务名、错误码、耗时。解析失败的行进 fallback 桶，不静默丢弃。
3. **聚合统计**：脚本算出错误 Top N、各服务请求量与 P95 延迟、环比前一日与前七日均值。只输出几百字节的结构化摘要。
4. **Agent 叙述**：把聚合摘要（不是原始日志）交给 Agent，模板固定为"概况 / 异常 / 趋势 / 待关注"四节，输出 JSON 并做 schema 校验，不通过就重试，temperature 调低。
5. **投递与归档**：渲染成 Markdown 推到群 webhook，中间产物和最终报告按日期路径存到对象存储，方便回溯和 diff。

## 踩坑点

- **时区与边界**：最初用入库时间切"昨天"，日志自带时间戳和服务端时钟有偏差，凌晨的报错被算进了前一天。后来固定用日志时间戳，并显式指定时区。
- **schema 漂移**：某服务升级后日志字段改名，解析失败率从 0.2% 悄悄涨到 30%，报告"看起来正常"但少了数据。现在解析失败率超阈值会单独告警。
- **LLM 数字失真**：早期版本让模型"顺便算个环比"，四舍五入后对不上账。现在所有数字由脚本算好、以字符串塞进模板，模型只负责措辞。
- **流水线自身静默失败**：最大的坑是流水线挂了没人知道，第二天才发现"今天没有日报"。加了心跳上报：任务无论成败都发一条状态消息。

## 可复用建议

- **确定性优先**：解析、统计、校验全用代码，LLM 只做最后一公里的叙述，输出必须过 schema。
- **中间产物持久化**：JSONL 落盘后重跑只要几秒，也方便核对"报告里的数字从哪来"。
- **模板版本化**：报告结构变更时升版本号，历史报告才可比。
- **先接一个日志源跑稳**，再横向扩展，别一上来接五个。

## 总结

上线后，日报从"半小时人工整理"变成"早上一条消息 + 一分钟复核"。核心思路就是：精确的事交给脚本，表达的事交给模型，用 Agent 和 MCP 做胶水。它不惊艳，但每天早上八点半准时出现在群里——自动化工具最好的品质，就是让人忘记它的存在。
