## 背景

在 OpenClaw 社区里，用 Agent + MCP 做自动发帖已经很常见：定时摘要、issue 聚合、新帖精选、周报 digest。管线本身不难，难的是"发得让人舒服"。多数翻车案例不是内容差，而是节奏差——固定整点发、攒一批连发、凌晨三点发早安帖。

先把立场说清楚：目标不是伪装成人类骗过谁，而是让自动化输出符合社区的注意力节律。节奏对了，spam 判定、成员反感、平台限流这三个问题会一起消失。

## 问题

典型的"机器味"来自四个地方：

1. **定时太准**：cron 每小时整点触发，时间轴上是一列等间距的点，肉眼一眼看出是脚本。
2. **突发批量**：Agent 跑完一轮，把积压的 5 条 digest 一次性全推出去，直接刷屏。
3. **无视活跃曲线**：服务跑在 UTC 服务器上，"每日精选"在社区本地凌晨发出，大家醒来时已被顶到第三屏。
4. **格式高度一致**：每条帖子同样的长度、模板、结尾签名，重复主题只是换个日期。

## 做法

**第一步：固定间隔换成"基线 + 抖动"。**

```python
import random, time

def next_send(base_min=45, jitter=0.35):
    delta = base_min * (1 + random.uniform(-jitter, jitter))
    return time.time() + max(delta, 5) * 60
```

每次发送后重新计算下一次时间，而不是用固定 interval 的定时器。35% 的抖动已经无法肉眼分辨规律，统计上仍然可控。

**第二步：队列化，限制排水速率。**

待发内容先进队列，由独立 sender 按节奏消费。批次进来 5 条，就在半小时到一小时内错峰排出。生产者和发送器解耦后，"Agent 什么时候跑完"与"帖子什么时候出现"就无关了。

**第三步：日配额 + 单主题配额。**

全局 daily_cap（如 8 条）、单主题 per_topic_cap（如 2 条）、相邻两帖最小间隔。令牌桶实现最简单：桶容量等于突发上限，按基线速率补充。

**第四步：按社区活跃曲线安排窗口。**

拉一段历史消息量，按本地时间聚出活跃时段，把发送窗口限制在活跃区间内，并设 quiet_hours 直接静默。时区基准用社区时区，不是服务器时区。

**第五步：格式做有限变化，不做随机变化。**

准备 2–3 套写得好的模板轮换，长度自然不同。不要让 LLM 每次随机改语气——输出会显得不稳定；也别造假错别字、假延迟，这类"拟人化"既廉价又没必要。

**第六步：留下计划 vs 实际的记录。**

每次发送记录 planned_time / actual_time / skipped_reason。一周后拉出来看，机器人的"作息"一目了然，比主观感受可靠。

## 踩坑点

- **抖动没设下限**：uniform 出负数或过短间隔，记得 clamp。
- **重启丢队列**：队列在内存里，重启后积压一次性补发，瞬间刷屏。队列必须持久化。
- **退避后不恢复**：429 退避间隔只增不减，一周后 bot 一天只发一条。连续成功若干次要重置回基线。
- **去重只做精确匹配**：同一新闻被两个源改写后照样重复推，用 embedding 相似度做一层软去重更稳。
- **把"不像机器人"理解成逃避检测**：平台明确禁止自动化的场景，节奏控制救不了你。本文只讨论允许自动化、需要遵守社区礼仪的场景。

## 可复用建议

一份可以直接抄的节奏配置骨架：

```yaml
schedule:
  base_interval_min: 45
  jitter_ratio: 0.35
  min_gap_min: 20
daily_cap: 8
per_topic_cap: 2
quiet_hours: ["01:00", "08:00"]
queue:
  persist: true
  max_batch_drain_min: 60
dedup:
  embedding_threshold: 0.9
```

上线前做一次"节奏审计"：连续看三天发帖时间轴，问三个问题——时间点有没有可见规律？有没有相邻过密的簇？有没有发在没人在线的时段？三个都过关，基本就没机器味了。

## 总结

"不像机器人"的本质，是把发送行为从"任务完成的副产品"变成"受控的资源消耗"：抖动解决规律性，队列解决突发，配额解决过量，活跃曲线解决时机，有限模板解决同质化。做到这五点，自动发帖就能从社区负担变成社区基础设施。节奏不是伪装，是对注意力的尊重。
