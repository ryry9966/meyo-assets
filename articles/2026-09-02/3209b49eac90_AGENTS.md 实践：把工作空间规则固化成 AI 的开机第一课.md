## 背景

用 OpenClaw 做日常自动化的人大多遇到过类似场景：gateway 配好了，插件跑通了，但 agent 每次开新会话都像新来的实习生——不认识目录结构、用错包管理器、把临时文件扔在仓库根目录。你反复在对话里交代同样的约定，它反复忘。

OpenClaw 对这个问题的官方答案是 workspace 里的 `AGENTS.md`：每次会话启动时，这个文件会被注入上下文，相当于 agent 的入职手册。很多部署教程把它一句话带过，但实际用下来，这个文件写得好坏，直接决定 agent 是“稳定可用”还是“每轮开盲盒”。

## 问题

根因很简单：模型没有跨会话的持久规则记忆。你脑子里的默认约定——“Python 一律用 uv”、“不要主动 push”、"scripts 放 scripts/"——如果只存在于聊天记录里，对下一个会话来说等于不存在。结果就是：

- 同样的任务，换个会话做法不同；
- 踩过的坑下次还踩；
- 自动化流程里，某一步靠“上次跟它说过”来保证，随时可能断。

## 做法

`AGENTS.md` 放在 workspace 根目录，纯 Markdown。建议按四层写：

```markdown
# 工作区说明

## 目录结构
- notes/     长期笔记
- scripts/   可执行脚本一律放这里
- tmp/       临时产物，可随时清空

## 硬性约定
- Python 统一用 uv，不要直接 pip install
- 改代码前先跑 git status，别动未提交内容
- 不要主动 git push

## 常见流程
- 周报：读 notes/weekly/ 最新文件，按既有格式追加
- 部署：只跑 scripts/deploy.sh，不要手敲 rsync

## 禁止事项
- 不读取 .env
- 不在仓库根目录创建文件
```

操作步骤：

1. **盘点**：翻最近两周和 agent 的对话，把重复交代过的约定列出来，这些是最高优先级的内容。
2. **分层写**：目录结构 / 硬性约定 / 常见流程 / 禁止事项，一条一句祈使句。
3. **冷启动验证**：新开会话，直接问它“根据 AGENTS.md，你在这个工作区有哪些限制？”看复述是否准确。不准就说明写法有问题。
4. **进 git**：当配置文件维护，有变更记录，不要当一次性文档。

## 踩坑点

1. **把密钥写进去**。AGENTS.md 会整篇进模型上下文，任何密钥、token、内网地址都别放，走环境变量或 secret 管理。
2. **写太长**。几百行的手册会稀释注意力，关键规则反而被淹没。控制在 100~150 行，长内容拆成独立文件，在 AGENTS.md 里指路让 agent 按需读。
3. **写成给人看的文档**。“我们团队一般使用 uv 作为包管理工具”这类描述句效果差，直接写“用 uv”。祈使句 + 一条一事。
4. **指令冲突**。比如既写“不要动 scripts/”，又在流程里让它改脚本。冲突时 agent 行为不可预测，写完通读一遍。
5. **只写不改**。把“agent 又踩同一个坑”当作信号：同一个坑出现第二次，就该沉淀成一条规则。

## 可复用建议

- **当配置，不当文档**：进版本库、走 review、有 commit message。
- **模板化**：新工作区复制上一份改路径，十分钟起步，比从零回忆省一半时间。
- **和其他文件分工**：AGENTS.md 管“规则”，MEMORY.md 管“事实和进度”，SOUL.md 管人格，别把进度记录混进规则文件，否则每周都要手动清理。
- **修完 bug 顺手问一句**：这个坑值不值得变成一条永久规则？值得就当场加进去。

## 总结

AGENTS.md 的价值不在文件本身，而在于把“你默认它应该知道的事”显式化。判断写没写好有一个简单标准：新会话里，你是否还需要重复交代任何约定。它不会让 agent 变聪明，但会让它稳定——而对自动化场景来说，稳定比聪明更稀缺。
