36kr 的标题把两件事放在了一起：Fable 5.1 发布，"号称全球最强"；以及 Anthropic 开始卷"缓存价格"。前者是 benchmark 层面的常规操作，后者才是值得从业者坐直的信号——大模型竞争的焦点，正在从"每百万 token 多少钱"，转向"重复的内容能便宜多少"。这篇讲清楚三件事：缓存到底缓存了什么，它为什么突然值钱，开发者怎么吃到这波红利。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-02/7588b8fe10602392.png)

## 一、读懂新闻：这次卷的不是单价，是"命中率经济"

- 据公开信息，Fable 5.1 的升级重点在 coding、agentic 与长上下文任务上，标准 input/output 单价大致延续原有档位；真正松动的是 prompt caching 这一栏——读缓存的价格进一步下探，TTL（缓存有效期）也更有竞争力。
- 为什么这一栏重要？因为应用形态变了。2023 年大家调 API 是"一问一答"；现在的主流是 Agent：一次任务几十上百次调用，每次都拖着同一套 system prompt、工具定义和挂载的文件内容。
- 这类工作流的输入 token 里，80%~90% 与上一次请求重复。账单的大头不在"新内容"，而在"重复内容"。
- 一句话总结：模型目录页看单价，月底账单看命中率。

## 二、缓存到底缓存了什么：从 KV Cache 说起

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-02/555fe2de5b6f4fc9.png)

- Transformer 生成文本是自回归的：每产出一个 token，都要对前面整段内容做 attention。为了不每次重算，推理引擎会把每个 token 在每一层的 Key/Value 向量存进显存，这就是 KV Cache。它和大模型同龄，但"跨请求复用"是近两年才被产品化的能力。
- 推理分两段：prefill 阶段吃下全部输入、一次性建立 KV Cache，算力密集；decode 阶段逐 token 生成，受显存带宽限制。Prompt caching 复用的正是 prefill 的成果。
- 它以"前缀"为单位：system prompt、工具 schema、知识库文档这类稳定前缀，只在第一次请求时完整计算，后续请求直接读结果。这也是命中率对 token 顺序极其敏感的原因——前缀里混进一个变化的字节（比如一个时间戳），从那个位置往后全部作废，等于给整段前缀办了注销。
- 显存账不能不算：一个 70B 量级的模型，FP16 精度下每 token 的 KV Cache 约 0.3MB；一个 128K 的完整上下文，缓存约占 40GB——接近半张 H100 的显存。缓存不是"白送的记忆"，它占的是推理服务器上最稀缺的 HBM。

## 三、定价的三段式：write、read、TTL 各管一件事

- 主流厂商把缓存定价拆成三段，以行业公开定价为参照：cache write 约 1.25× 基础输入价（补偿首次计算与存储成本）、cache read 约 0.1×（把省下的 prefill 算力让利给用户）、TTL 常见 5 分钟，命中可续期。
- 厂商之间的差距就在这三段系数上：OpenAI 的自动缓存约 0.5×，不收写入溢价；DeepSeek 命中价约 0.1×；Google 支持显式缓存、按存储时长另计费；Anthropic 此前维持 1.25×/0.1× 的组合。Fable 5.1 的调整，等于把"读价和有效期"这两个对 Agent 最敏感的参数继续往下压。
- 商业逻辑有两层。第一层是成本：命中一次就少做一次 prefill，边际成本确实更低，有让利空间。第二层是粘性：前缀缓存越深、TTL 越长，重度 Agent 应用迁移到别家时的"冷启动成本"就越高。降下去的不只是价格，还有你的切换意愿。

## 四、开发者怎么吃红利：token 顺序就是钱

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-02/438b8ae679d3ce11.png)

1. **稳定内容放最前，易变内容放最后。** system prompt、工具定义、长文档打头阵；用户提问、时间戳、随机 ID 一律收尾。缓存按最长公共前缀匹配，顺序错了等于没写。
2. **用显式缓存断点划清边界。** Anthropic 提供 cache_control 标记，OpenAI 走自动缓存但要求前缀至少 1024 token 且逐字节一致；在长文档和对话历史之间手动打断点，命中率通常更高。
3. **把命中率变成一等监控指标。** 响应体里的 cache_read_input_tokens（OpenAI 侧是 cached_tokens）应该进监控面板；命中率长期低于 50% 的 Agent，大概率是前缀设计出了问题，而不是模型不行。
4. **算综合账，别只看单行价格。** 举例：50K token 的稳定前缀、调用 1000 次——全量计费约 5000 万输入 token；走"1 次写入 + 999 次命中"大约只等效 500 万 token，输入成本直接降一个数量级。Blended cost（各类单价 × 实际用量）才是真实成本，可以说 Agent 时代的账单，一半是模型写的，一半是你的 token 顺序写的。
5. **区分两种"缓存"。** prompt caching 是前缀级精确复用，结果与重新计算完全一致；semantic caching 是"语义相近就返回旧答案"，省得多但有正确性风险，生产环境要非常谨慎。

## 五、写在最后：三条冷思考

1. **命中率是新的北极星指标。** 过去优化 prompt 只为效果，现在还得为钱——同样的任务，命中率从 30% 提到 90%，成本差异可以是三到五倍，比任何砍价谈判都实在。
2. **看定价表要看四行，不是一行。** input、output、cache write、cache read，外加 TTL。一款模型对 Agent 应用"实际贵不贵"，多半由后两行决定。
3. **福利背后是软锁定。** 更便宜的读价和更长的有效期是真实让利，但也意味着你的工作流和某一家的缓存结构绑得越来越深。关键业务留一份"可迁移性预算"：前缀设计保持中立、定期用第二家模型做对照测试——别让省下来的钱，变成将来搬家的成本。
