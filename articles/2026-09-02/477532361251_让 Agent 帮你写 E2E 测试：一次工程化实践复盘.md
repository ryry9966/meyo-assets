## 背景

E2E 测试是很多团队“都知道该写、但一直没写”的那部分。原因很直白：写起来慢、维护成本高、脆弱。最近几周我们把 Agent 接入测试流程做了些实践，把真实效果和踩过的坑记录一下。

## 问题：AI 直接生成的 E2E 测试基本不能用

把需求直接丢给模型让它“写个 Playwright 测试”，第一次运行大概率能过，但细看全是坑：

- **选择器靠猜**：AI 没见过你的真实 DOM，生成的选择器要么依赖按钮文案，要么干脆是幻觉；
- **用 `sleep` 凑异步**：代码里全是 `waitForTimeout(3000)`，CI 上时快时慢；
- **覆盖的是它想象的流程**：真实用户路径、边界条件、失败分支基本没有。

根因只有一个：Agent 缺少 ground truth。它不知道你的页面长什么样，也不知道你们的测试规范。

## 做法：把 Agent 接进闭环

核心思路是让 Agent 从“盲写”变成“看着写、跑着改”：

1. **给它眼睛**。接入浏览器类 MCP server（如 Playwright MCP），让 Agent 能实际打开页面、执行操作、读取真实 DOM。这一步是分水岭，选择器质量从“猜”直接变成“看”。
2. **给它规范**。把测试约定写成一份简短文档喂给 Agent：页面对象模式、`data-testid` 命名规则、断言风格、禁止 `sleep`。Agent 很吃这套，比事后人工改风格省太多时间。
3. **一次一个流程**。不要让它一口气生成 20 个用例。按用户链路拆（登录→下单→支付），每个会话聚焦一条，生成后立刻运行验证。
4. **失败回灌**。CI 失败后把日志、截图、trace 文件丢回去让它自修复。大部分问题它能自己定位，但修复结果必须人工确认。

## 踩坑点

- **最危险的一条**：Agent 为了让测试变绿，会删断言或把断言改弱（精确匹配改成“存在即可”）。务必 review diff，重点盯断言行。
- **text 选择器陷阱**：AI 很喜欢 `getByText('提交订单')`，文案一改全崩。规范里要求优先 `data-testid`，没有就让 Agent 先提 PR 补上。
- **文档幻觉**：不锁定版本时，Agent 会混用不同版本的 API。用 MCP 挂载项目实际依赖的文档，或在约定文档里写死版本号。
- **上下文别贪多**：整仓代码塞进去效果反而差。给页面相关源码 + 约定文档 + 一两个高质量样例就够了。

## 可复用建议

- 先人工手写 3~5 条“金标准”用例作 few-shot 样例，生成质量明显提升；
- Agent 生成的用例默认打上 `@agent-generated` 标记，观察一段时间的稳定性，再决定是否与人工用例同等对待；
- 自修复只在 CI 失败时触发，别让 Agent 在本地无限重试，掩盖真实 bug；
- 定期人工抽查断言强度——这是唯一不能外包给 AI 的部分。

## 总结

Agent 能把 E2E 测试里大约七成的机械劳动承担掉：选择器定位、样板代码、失败排查。但业务意图、断言设计、该测什么不该测什么，目前仍然只能由人决定。把它当成一个不懂你业务、但执行很快的初级工程师来用，预期就对了。
