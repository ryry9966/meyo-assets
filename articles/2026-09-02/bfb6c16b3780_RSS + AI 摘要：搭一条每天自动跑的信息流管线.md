## 背景

我的信息源长期处于“订阅了很多、真正读的很少”的状态。RSS 依然是最稳定的结构化订阅协议，但几十个 feed 每天几百条更新，人工全读不现实。这个管线的动机很朴素：让 Agent 做粗筛和压缩，把最终判断留给自己。

## 问题

动手前明确了三个痛点：

1. **Feed 质量参差**：有的只有 summary 没有全文，有的更新时间字段是错的；
2. **成本**：对每条都调模型摘要，大部分 token 花在不值得摘要的条目上；
3. **重复**：同一篇文章被多个源转载，去重不做，信息密度会很低。

## 做法

整体分四段：**抓取 → 粗筛 → 摘要 → 投递**，每段是独立可运行的脚本，状态存 SQLite。

1. **抓取**：自建一个 FreshRSS 做源池（OPML 导入约 40 个 feed），cron 定时爬，脚本只消费它的 API，把脏活隔离在外。也可以把这一步包成 MCP 工具注册给 OpenClaw，让 Agent 按需调用。
2. **粗筛**：先去重——对 guid/link 做 hash（剥掉 utm 等跟踪参数）写入 seen 表；再做关键词黑名单 + 来源权重的简单打分。大约七成条目死在这一步，是整条管线最大的省钱点。
3. **摘要**：只把剩下的约 30 条喂给模型。所有正文塞进**一次**请求做批量摘要，输出按来源分组的清单，比逐条调用省一个量级的 token。Prompt 强调两点：“只基于给定文本摘要”，以及“给每条输出 1–5 的值得读评分，低于 3 的写明理由”。
4. **投递**：每天固定时间生成 Markdown 摘要，commit 到笔记仓库，同时推一份到 IM webhook。摘要控制在 50 行以内，碎片时间扫一遍标题和一句话结论，评分 ≥4 的再点原文。

Agent 在这里承担两件事：定时跑批量摘要任务，以及支持交互追问——“展开今天清单里的第 3 条”。

## 踩坑点

- **只有摘要的 feed 是最大的幻觉来源**。模型面对 200 字的 summary 会很乐意替作者把论点编完整。我的规则：readability 抽全文不足 300 字的，跳过摘要，只列标题和链接。
- **日期字段各种坑**：未来时间、缺时区、格式混乱。日报窗口一律用抓取时间，否则会漏收或重复。
- **不要只靠标题去重**。转载后标题常被改写，link 规范化（剥参数、统一协议）更可靠。
- **批量摘要的长度上限**。单批 20 篇以内稳定，再长中段条目会被模型忽略，宁可拆批。
- **别给模型删除权限**。第一版允许模型直接丢弃低分条目，结果误杀过几篇好文章。改成“只打分、不删除”之后明显稳了。

## 可复用建议

- 四段各自可独立运行、可重放，排障效率完全不同；
- 每次模型调用都记 token 消耗，跑一个月就知道该优化哪里；
- 从 10 个 feed 起步跑两周再扩，管线最常见的死法是一开始就想建全；
- 预期要摆正：摘要是**筛选用**，不是阅读的替代品，重要结论回原文核对。

## 总结

这条管线没有任何前沿技术，核心代码不到 400 行，一个 cron 加一个 SQLite 文件做配角。真正起作用的是两个设计决策：**先粗筛再摘要**，以及**只打分不删除**。对需要长期无人值守跑的任务，依赖模型判断的环节越少越稳——用模型压缩信息就够了，判断留在自己手里。
