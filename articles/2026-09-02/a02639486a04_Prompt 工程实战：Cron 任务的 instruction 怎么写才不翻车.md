## 背景

OpenClaw 的 cron 任务本质是**无人值守的 prompt 执行**：到点触发、通常新开会话、跑完即止，触发那一刻没有人在场补上下文。这和交互式对话完全是两回事——对话里你说一句模糊的话，Agent 会反问你；cron 里没人反问，模型只能按字面意思加上自己的脑补去执行。

## 问题

我见过不少定时任务翻车的案例，症状集中在三类：

1. **产出没头没尾**：任务跑了，结果只留在会话里，没落盘也没推送，等于白跑；
2. **行为不可控**：指令写"帮我盯一下仓库"，Agent 每次自行发挥，范围越跑越大；
3. **失败静默或刷屏**：工具报错时模型编数据交差，或者每天准时发一条"今日无异常"。

根因只有一个：把交互式对话的 prompt 写法，直接搬到了 cron 上。

## 做法：一个可复用的指令骨架

我的做法是把 cron instruction 当"作业说明书"写，固定六段：

```text
[触发说明] 这是定时任务 <名称>，无人值守执行。
[目标] 一句话说清本次要做的事。
[输入] 数据来源、读取路径、时间窗口（写死时区，如：以执行时刻为基准的过去 24 小时，Asia/Shanghai）。
[步骤] 1. … 2. … 3. …（每步可判定，不写"酌情处理"）。
[输出] 结果写到哪个文件、发到哪个渠道、什么格式。
[边界与异常] 不要做什么；工具失败重试 1 次，仍失败则记录错误并停止；无可报告内容时不发消息。
```

举个实际例子：每天汇总通知的任务，`[输出]` 段我会写成"追加写入工作区 notes/digest.md；仅当出现被提及或构建失败时才推送摘要，其余情况保持静默"。

## 踩坑点

- **相对时间词**：指令里写"昨天"，跨时区或触发延迟就会漂移。一律改成相对执行时刻的明确窗口，并写明时区。
- **目标当地址**："让它保持我的收件箱干净"这类写法等于把调度权交给模型，要拆成具体步骤。
- **空结果行为没定义**：不写"无内容则静默"，就会天天收到空汇报。
- **幂等性**：任务重叠触发会重复发消息。我在指令末尾固定加一句"执行前检查当天文件是否已存在，存在则跳过"。
- **指令越长越乱**：改了十几版后没人看得懂。稳定流程应沉淀成 skill / SOP 文件，instruction 只留调度参数和当次差异。

## 可复用建议

1. **当代码管理**：cron instruction 进版本库，改动 diff 一遍再上线；
2. **先手动 dry-run**：上线前手动触发一次，逐项核对每个落点——文件、消息、日志；
3. **留观测点**：每个任务的最后一步固定为"把执行结果或错误写入日志文件"，无人值守才有据可查；
4. **一个任务一件事**：多目的任务拆开，别让一条指令既做日报又做清理。

## 总结

写 cron instruction 的核心转变，是从"和模型对话"改成"给一个没有上下文的值班员写交接单"。**自包含、可判定、有边界、可观测**——四点做到，定时任务才能长期无人值守地稳定跑下去。
