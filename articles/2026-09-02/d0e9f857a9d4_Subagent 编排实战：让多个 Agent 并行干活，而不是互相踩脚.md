## 背景

单 Agent 跑长任务的痛点很典型：上下文越滚越大，工具调用串行排队，一个调研没跑完，后面所有事都得等。Subagent 模式是当下比较务实的解法——主 Agent 派生若干子 Agent，各自持有独立上下文和工具权限，跑完只交回摘要。在 OpenClaw 里，这套编排可以很轻量地通过内置的 subagent 能力加 MCP 工具组合出来，不需要额外的框架。

## 问题

我最初的认知是"能并行就并行，开得越多越快"。实际跑下来摔了三个跟头：一是子 Agent 返回的全文把主 Agent 的上下文撑爆，合并质量反而下降；二是几个子任务并发改同一个文件，互相覆盖；三是任务之间本来有依赖，硬拆并行后结果错乱。教训很明确：**编排的价值在拆分得当，不在开得多。**

## 做法

1. **先做任务分诊。** 判断三个问题：子任务之间有没有数据依赖？是不是以读操作为主、或写操作范围互不重叠？单个任务是否小到不值得拆？三条都过关才进并行队列，否则老老实实串行。
2. **给每个 subagent 一个窄 prompt。** 只写清三件事：目标、输入在哪、产物写到哪。明确告知"不要做范围外的事"。
3. **用文件系统当通信介质。** 子 Agent 把结果写到独立产物文件（如 `reports/<task-id>.md`），返回时只允许一段几行以内的摘要。主 Agent 合并时读文件，不读对话。
4. **限流、超时、重试。** 并发控制在 2–4（看 API 配额），每个子任务设超时，失败重试一次，仍失败就标记跳过，不阻塞整批。
5. **主 Agent 只做三件事：拆分、派发、合并。** 别让它下场干细活，否则上下文被污染，合并环节最先崩。

## 踩坑点

- **并发写同一文件。** Prompt 里写了"别碰别人的文件"也没用。改成每个 subagent 分配独立子目录、主 Agent 统一合并后，冲突直接消失。
- **子 Agent 返回全文。** 一轮调研五个子任务各回两三千字，主上下文立刻见底。固化"摘要契约"后稳定。
- **伪并行。** 任务 B 依赖 A 的产出，硬并行纯属烧 token。分诊阶段就该把它们串成链。
- **权限继承。** subagent 默认继承了主 Agent 的全部 MCP 工具，包括写生产配置的那个。现在派发时显式收窄，只挂必需的工具。
- **排障困难。** 并行日志混在一起没法读。按 subagent 维度分开记录，每条带任务 ID，出问题能直接定位到单个分支。

## 可复用建议

- 把摘要契约做成模板：每个 subagent 必须返回**结论、关键路径、遗留问题**三段，超过字数视为违约。
- 扇出/扇入是最稳的编排形状：一个 orchestrator、N 个窄职责 worker、文件系统做交接区，不引入复杂状态机。
- 先写串行版跑通全流程，再拆并行。编排是对已验证流程的加速，不是设计工具。
- 子任务产物做幂等：重跑同 ID 不产生副作用，失败恢复成本会低一个量级。

## 总结

Subagent 编排真正解决的是两个问题：上下文稀缺和串行等待。它不是展示并发能力的玩具——**拆得准、传得少、权限窄、可重跑**，四点做到位，多 Agent 并行才省时间；任务本身没拆好时，编排只会把混乱放大几倍。建议从一个小而独立的读密集型任务开始试，跑通一轮再扩展。
