## 背景

跑过一段时间 OpenClaw 自动化的人基本都遇到过：定时任务重复触发、webhook 重推、agent 因为超时自己重试、MCP 工具明明调用成功了但响应丢了又被调一次。调度器和网络层的重试是常态，不是异常。麻烦在于：重试是基础设施替你做的决定，副作用却是你的任务自己产生的。

## 问题

一个典型事故：每天早上往群里发日报的 cron 任务，某天上游响应慢，调度器判定超时又触发一次，群里出现两条日报。更隐蔽的是 agent 场景：LLM 输出不确定，重试时参数可能被重新生成，两次执行走的是不同代码路径，事后你甚至很难确认"到底执行了几次"。不幂等的任务，重复执行等于埋雷。

## 做法

核心思路一句话：把"执行一次"改写成"确保达到目标状态"。

1. **用业务语义构造幂等键**。键来自任务本身的含义，比如 `hash(任务类型 + 规范化参数 + 业务周期)`，日报就是"日期 + 日报"。不要用每次运行随机生成的 UUID。
2. **先查后做，且以存储约束兜底**。执行副作用前按键查一次；但应用层 check-then-act 有竞态，真正可靠的是数据库唯一索引或 KV 的原子 setnx。
3. **落盘任务状态**。SQLite、文件、KV 都行，记录 pending/done，重跑时 done 直接跳过。
4. **优先选天然幂等的写法**。upsert 优于 insert，"把状态设为 X" 优于 "追加一条 X"，这是成本最低的一层防线。

```python
key = f"daily-report:{date}:{target}"
if store.setnx(key, "done", ttl=86400 * 2):
    send_report(target)
# setnx 抢不到说明已执行过，直接跳过
```

5. **对天然不可幂等的外部动作单独处理**。发消息、发邮件这类动作没法"做两遍结果一样"，只能在入口用幂等键挡住，或者让消费方按消息 ID 去重。

## 踩坑点

- **幂等键里混入时间戳或随机数**：每次执行键都不同，等于没做。
- **重试时键漂移**：agent 重试时让 LLM 重新生成参数，键就变了。键应该在入队时固定下来，而不是执行时现算。
- **只做整体幂等，不做条目级幂等**：批量 10 条跑到第 6 条崩了，重跑应跳过前 5 条，而不是全做或全不做。
- **副作用和状态写入之间崩溃**：做完了但没标 done，重跑会重复。这个窗口消除不了，正确姿势是接受 at-least-once，把去重放在消费端。
- **指望 LLM"重试时会输出一样的"**：不会的。

## 可复用建议

- 给 MCP 工具定个约定：create 类工具一律接受 `idempotency_key` 参数，同键已存在就返回既有实体而不是报错，把"创建"语义升级为"确保存在"。
- 写一个通用幂等包装器，任何任务接入时只需声明键的构造方式，不重复造轮子。
- 验收标准很简单：同一任务连跑两遍、重放同一事件，副作用数量不变。把它写成固定的测试用例，进回归。

## 总结

幂等性不是锦上添花，它决定了重试是"自愈"还是"事故放大器"。在 agent 这种不确定性和重试都属常态的环境里，正确的心智模型是：默认每次执行都可能重复发生，然后用幂等键和 ensure 语义，让这个假设变得无害。
