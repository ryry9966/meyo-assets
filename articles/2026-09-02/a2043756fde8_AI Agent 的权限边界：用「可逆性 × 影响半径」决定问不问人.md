## 背景

Agent 从"只会聊天"进化到"能动手"——通过 MCP 和插件接入文件系统、数据库、消息通道、外部 API 之后，一个现实问题立刻浮出水面：它到底可以自己干到哪一步？

第一代实践往往在两个极端之间摇摆。要么全放开，效率高，但一次误删、一次误发就足以翻车；要么每步都问人，安全，但 agent 沦为需要全程陪跑的实习生，自动化价值归零。

## 问题

真正的矛盾是确认疲劳和事故风险。每步都确认，人会很快进入"无脑点允许"状态，确认机制形同虚设；全部放开，则把不可逆操作的开关交给了概率模型。所以问题从来不是"要不要问人"，而是：哪些操作永远不用问，哪些必须问，哪些根本不该给 agent 开口子的机会。

## 做法：两个维度分三档

给每个工具、每类动作打两个标：

- **可逆性**：能不能撤销？只读查询完全可逆；沙箱内写文件（有版本控制）可逆；发消息、调外部接口、删数据基本不可逆。
- **影响半径**：只波及 agent 工作目录，还是触及生产环境、真实用户、真金白银。

据此分三档：

1. **绿档（自动执行）**：可逆且出不了沙箱，比如只读操作、临时目录里的读写。事后留审计即可，不必事前打扰。
2. **黄档（确认后执行）**：不可逆，或影响半径超出沙箱。要求 agent 提交结构化确认请求：动作、目标对象、关键参数、预期后果、回滚方式——而不是一句"我要执行某个操作"。
3. **红档（收走工具）**：删除生产数据、批量对外通讯、大额资金操作。不设"请求—批准"路径，直接不给工具，或走独立于 agent 的审批流。

落地步骤（OpenClaw + MCP 场景）：

1. 盘点全部工具，标注 read / write / external / destructive 四类属性；
2. 在工具网关层实现分级拦截，而不是写在 system prompt 里；
3. 黄档调用强制先产出确认卡片，人批准后才透传参数；
4. 全量落审计日志：时间、工具、参数、是否人工批准；
5. 写类操作尽量提供 dry-run，先看 diff 再落地。

## 踩坑点

- **只在 prompt 里写"请谨慎操作"**：防线约等于零，模型会忘，间接注入也可能绕过。权限必须在调用层强制。
- **确认弹窗信息量不足**："Agent 想执行 delete_record，允许？"用户看不懂参数只能瞎点。确认请求必须人类可读。
- **高频确认训练出批准机器**：某操作一天被确认三十次，说明分级错了，应降级加事后审计，而不是让人麻木。
- **权限自升级路径**：如果 agent 能写自己的配置文件，等于能给自己发通行证。配置文件必须划入红档。
- **长任务一次性总授权**：任务开头要"总授权"没有意义，人根本不知道后面会发生什么。确认点要绑定在具体危险动作上。

## 可复用建议

- 一句话原则：**可逆且沙箱内→自动；不可逆或出沙箱→确认；无法补救→收权。**
- 默认从严，跑一段时间后依据审计日志逐步放宽，而不是反过来。
- 确认通过率接近 100% 的操作，是下一批降级候选；频繁被拒的操作，要么收紧参数约束，要么下线。
- 分级策略写进工程文档，随工具变更一起维护——权限配置也是代码。

## 总结

权限边界不是一次性配置，而是随 agent 能力扩展持续校准的机制。判断标准保持简单：可不可逆、影响多大、出错能否补救。让 agent 在安全区跑得快，在危险区慢下来、问清楚，自动化才立得住。
