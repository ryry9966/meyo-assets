## 背景

把模型放在云端 API 上当然省事，但当你想让 Agent 处理本地文件、家庭相册、自动化日志这类不想出门的数据时，"数据不出家门"就从洁癖变成了需求。另外两条理由更实际：长期跑自动化任务时 API 费用会累积；断网时家庭自动化流程不该整体瘫痪。这篇记录我在一台家用台式机（12GB 显存 + 64GB 内存）上部署本地模型、并接入 Agent 工作流的完整过程。

## 问题

动手前要想清楚三件事：一、这块硬件到底塞得下多大的模型；二、哪些模型在量化后还能稳定完成工具调用（Agent 场景的硬指标）；三、长期挂机跑任务，吞吐和稳定性够不够。

## 做法

**1. 先算显存账。** 经验公式：量化后权重 + KV cache + 1~2GB 运行开销，再留 20% 余量。Q4_K_M 量化下，7~8B 约占 6GB，14B 约 10~11GB，32B 需要 20GB 以上——12GB 卡的合理上限就是 14B。

**2. 选运行时。** 从 Ollama 起步，一行命令拉模型，自带 OpenAI 兼容接口（`localhost:11434/v1`），Agent 侧几乎零改动。需要精细控制上下文长度、Flash Attention 时再换 llama.cpp 的 server 模式。有 24GB+ 显存才考虑 vLLM。

**3. 选模型。** 对 Agent 而言工具调用是第一优先级，优先选官方确认支持 function calling 的系列（Qwen、Llama 3.1+ 等），量化别低于 Q4——精度再低，JSON 输出损坏率会明显上升。

**4. 接入与调参。** base_url 指向本地端点，显式设置上下文长度（别吃默认值），工具调用场景 temperature 压到 0.1~0.3，超时放宽到 120 秒以上。

**5. 冒烟测试。** 写个 20 行的脚本，循环发起 30 次带工具定义的请求，统计 JSON 解析成功率。低于 90% 就换模型或升精度，不要带病上线。

## 踩坑点

- **KV cache 才是隐形杀手。** 权重塞得下不代表跑得动：8GB 卡装 8B 模型后再开 32k 上下文直接 OOM。上下文按实际需求设。
- **"支持 tools" ≠ "tools 好用"。** 宣传页写着支持，实际可能格式对不齐、JSON 偶发缺字段。冒烟测试是唯一可信的验收方式。
- **Ollama 默认 5 分钟卸载模型。** Agent 每隔十几分钟触发一次任务就冷启动一次，用 `keep_alive` 把模型钉在显存里。
- **笔记本注意热节流。** 实测从 40 tok/s 掉到 15，插电加散热垫才稳住。长期挂机优先台式机。
- **Windows + Docker 的网络坑。** 容器里的 Agent 访问宿主机模型服务要用 `host.docker.internal`，别用 localhost。

## 可复用建议

1. **维护模型卡。** 每换一个模型记录：量化版本、上下文、temperature、实测吞吐、工具调用成功率。一个月后你会感谢这份表格。
2. **双层路由。** 简单任务和隐私任务走本地，复杂推理走云端 API，在 Agent 配置里做成开关，不用重构。
3. **先监控再优化。** nvidia-smi 加一个简单的 token/s 日志，有数据才能判断瓶颈在显存带宽还是模型本身。
4. **别追榜单。** 对 Agent 场景，工具调用稳定性的权重远高于 benchmark 分数。

## 总结

消费级硬件跑本地 LLM 在今天已不是玩具：12GB 显存跑 14B Q4、接入 Agent 做日常自动化，是完全现实的组合。它本质是一道工程取舍题——显存预算、工具调用可靠性、长期在线稳定性三者互相牵制。建议路径：先用 Ollama + 8B 验证整条链路，再按显存上限逐级放大。Agent 框架的价值不依赖最大的模型，依赖的是那条跑得稳的链路。
