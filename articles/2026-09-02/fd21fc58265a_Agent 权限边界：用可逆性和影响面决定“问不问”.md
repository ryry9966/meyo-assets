## 背景

跑了一段时间 OpenClaw / MCP 类自动化之后，很多人会卡在同一个问题上：工具越接越多，agent 能干的实事越来越多，但“它到底什么时候该自己动手、什么时候该停下来问人”，一直靠感觉。靠感觉的代价是两种失败轮流出现：要么事事请示，人沦为盖章机器；要么放手太多，某天发现它替你给客户发了消息、删了分支、或者花了一笔不该花的钱。

## 问题

“该不该问”如果靠模型自己的自信程度来决定，是很不可靠的——同一个动作，它状态好的时候觉得自己能行，上下文被注入污染的时候也觉得自己能行。更工程化的思路是：不依赖 agent 的判断，先看**动作本身的属性**。三个属性基本够用：

- **可逆性**：做错了能不能低成本回滚？
- **影响面**：只动你的工作区，还是会触达外部世界（别人看得见、钱会动、线上会变）？
- **恢复成本**：出错后修复要多久，谁来兜底？

## 做法

1. **给动作分四档，写进清单**：
   - T0 只读（搜索、列目录、GET）：直接干，不必汇报；
   - T1 可逆写（工作区内改文件、建分支）：自己干，但必须留日志；
   - T2 不可逆或对外（发消息、删除、部署、花钱）：带着预览来问人；
   - T3 高危（批量删数据、资金操作、公开发布）：不提供“确认后自动执行”，只在人类主动发起的会话里做。
2. **双层落地**：系统提示里写明边界，但真正的执行点放在 MCP 网关 / 插件层做策略校验——allowlist、参数级规则、dry-run。提示词是建议，工具层才是 enforcement。
3. **问就问得可执行**。不要问“我可以继续吗”，而是给出 diff、完整命令、影响范围和回滚方式，让人扫一眼就能回“ok / 改一下 / 拒绝”。
4. **全量留痕，定期放权**。T1 的自动动作全部记录输入输出；跑一两周做一次十分钟复盘，把“每次都被批准且可逆”的动作升档，出过问题的降档。

## 踩坑点

- **确认疲劳**。问得越频繁，“确认”越接近条件反射，问询退化成安全剧场。宁可少问，问必值得看。
- **只在提示词里约束**。网页抓取、工具返回内容都可能夹带注入，模型层的判断会被当场翻掉；硬边界必须落在工具层。
- **粒度太粗**。按“工具”分级不够，`shell` 这一个工具里 `ls` 和 `rm -rf` 是两回事，策略要做 到参数级。
- **等待确认没有兜底**。要显式定义：无人应答时中止并汇报，而不是让 agent 自己找个“更稳妥”的变通——变通往往更糟。

## 可复用建议

一句话版规则：**可逆且影响面小 → 自己干并留日志；不可逆或对外 → 带预览来问；涉及钱、删数据、对外发布 → 只在人主动发起时做。**分类拿不准时，回答一个问题即可：这个动作做错了，恢复成本是多少，谁能看见。

## 总结

权限边界不是一次性的配置，而是人和 agent 之间一份需要持续维护的契约。目标不是“零打扰”也不是“零自主”，而是：每一次打扰都值得人看一眼，每一次自主都在出事后能廉价撤销。
