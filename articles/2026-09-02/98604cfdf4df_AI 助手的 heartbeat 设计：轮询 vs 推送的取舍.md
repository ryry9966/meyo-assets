## 背景

OpenClaw 的 Agent 默认是被动响应的：有人发消息才干活。但很多自动化场景需要 Agent "自己醒着"——定时巡检、主动汇报、发现新任务。社区里常见的两条路线：**心跳轮询**（每隔 N 分钟唤醒一次 Agent，检查待办与状态）和**事件推送**（外部系统通过 webhook 直接把事件灌给 Agent）。两者没有绝对优劣，取舍取决于事件来源和时效要求。

## 问题

- 轮询太密：1 分钟一次心跳，token 消耗和输出噪音都会失控，还容易触发上游限流；
- 轮询太疏：事件发生后最多要等一个周期才被处理，实时性差；
- 推送门槛高：需要公网可达的入口、事件源适配、鉴权和重试逻辑；
- 推送不可靠时没人兜底：webhook 丢了就是丢了，Agent 不知道自己错过了什么。

## 做法：分层混合

1. **先盘点事件源，按时效分类**：秒级重要的（监控告警、CI 失败）走推送；分钟级可接受的（邮件摘要、日程提醒）走轮询。
2. **心跳做基线**：保持宽松间隔（15–30 分钟），心跳逻辑尽量便宜——先读一个待办清单文件（类似 HEARTBEAT.md），没内容就直接退出，不进推理、不产出消息。
3. **高价值事件加推送链路**：一个极简 webhook 接收器，收到事件后做两件事——按事件 ID 去重、落盘到队列文件，再注入 Agent 会话或直接触发。
4. **心跳兼任对账员**：每次心跳除检查待办外，扫一遍"已落盘但未确认"的事件，兜住推送丢失。
5. **用完即清**：处理完的事件标记/删除，避免重复消费。

## 踩坑点

- HEARTBEAT.md 里留了过期内容，Agent 每次心跳都重复执行同一动作。清单必须有"已完成即清除"的机制。
- webhook 接收器静默失败（端口不通、证书过期），表面一切正常，事件链路其实早断了。给推送通道加个最简单的健康探针或每日自检。
- 事件风暴：一次批量操作触发几十个 webhook，Agent 疯狂输出。在接收器侧做合并限速，同源事件按时间窗口聚合。
- 幂等缺失：接收器重试导致同一告警发两遍。所有处理以事件 ID 去重。
- 心跳间隔写成固定值，忘了闲时可以放宽，白烧 token。

## 可复用建议

- 一句话原则：**推送管"快"，心跳管"稳"**。推送负责实时事件，心跳负责兜底对账和时间型任务（每日摘要这类）。
- 心跳设计成"便宜检查 + 按需升级"：没事就退出，有事才拉起完整推理。
- 事件处理统一幂等 + 落盘，推送和轮询共享同一套队列语义，两条链路可以互相替换。
- 把"心跳失败/超时"本身当监控指标，它是 Agent 的存活信号。

## 总结

轮询和推送不是二选一。对自托管的个人 Agent，一个宽松心跳打底、按需加推送通道、心跳兼做对账，是小成本且抗故障的组合。先量清楚你的事件需要多快被处理，再决定造哪条链路，别为不需要的实时性付出永久成本。
