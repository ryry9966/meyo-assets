# 背景

OpenClaw 的 agent 不是一次性调用，而是长期驻留：挂着 Telegram/WhatsApp 等消息渠道，跑 cron 和 heartbeat，通过 MCP 和插件直接操作你的机器。开箱默认人格是“通用助手”——礼貌、啰嗦、没有记忆点，也没有明确的边界。

SOUL.md 是 workspace 根目录下的人设文件，每次会话作为系统上下文加载，回答两个问题：这个 agent 是谁；什么该做，什么不该做。很多人知道这个文件，但要么不写，要么当装饰品写几行，白瞎了它的作用。

# 问题

不调 SOUL.md，实践中会遇到三类麻烦：

1. **语气漂移**：今天话痨明天冷漠，同一件事两个会话给出两种回答风格；
2. **边界缺失**：agent 自作主张替你回消息、改配置、执行破坏性命令；
3. **人设与工具冲突**：SOUL.md 要求简洁，插件输出模板却让它每次长篇大论。

自动化场景会放大这些问题：凌晨 heartbeat 无人值守时，错误的人格就是错误的行为。

# 做法

1. **定位文件**：workspace 根目录下的 SOUL.md，建议连同 workspace 一起纳入 git。
2. **分四段写**：身份与语气（你是谁、默认语言、回复长度）；价值观（诚实优先于讨好，不确定就直说）；红线（外发消息需确认、不碰哪些目录、涉钱必须二次确认）；风格（拒绝时给理由和替代方案）。
3. **控制长度**：30–60 行足够。它每次会话都进 context，越长稀释越严重。
4. **与 AGENTS.md 分工**：SOUL.md 管“是谁”，AGENTS.md 管“怎么干活”，同一件事只写一处。
5. **迭代**：每次出现意外行为，补一条具体规则，开新会话验证生效。

一个可以直接抄的最小骨架：

```markdown
# 身份
你是我的工作台助理，默认中文，回复尽量三行以内。
# 红线
- 外发消息先给我草稿，我确认后才发
- 付款、删文件、改公网配置：一律停下问我
# 风格
不确定就直说不知道，不编造。
```

# 踩坑点

- **写成愿望清单**：“要有同理心”不可执行。改成“用户情绪激动时，先承认情绪再谈方案”。
- **红线一刀切**：要求所有外发都人工确认，heartbeat 自动化就全卡死。正确做法是分级：高风险需确认，低风险白名单直通。
- **人设过重**：让 agent 假装有情感、动不动拒绝正常任务，在自动化消息里非常怪异。
- **规则冲突**：SOUL.md、AGENTS.md、TOOLS.md 三处都写风格要求，冲突时行为不可预测。保持单一事实源。

# 可复用建议

- 固定五段骨架：身份 / 语气 / 价值观 / 红线 / 风格，换 agent 只换内容不换结构；
- 规则一律用行为动词描述可观察的行为，不写抽象形容词；
- workspace 上 git，人格也能 diff 和回滚——改坏了能退回上一版；
- 少即是多：40 行精确规则，胜过 200 行抒情散文。

# 总结

SOUL.md 不是玄学，它是给一个长期运行系统写的接口契约：定义输入输出的风格、不可逾越的边界、出错时的默认行为。花一小时认真写它、再花两周持续迭代，换来的是 agent 在无人值守场景下可预期的行为。这笔投入，比事后排查“它为什么半夜给我客户发了条奇怪的消息”划算得多。
