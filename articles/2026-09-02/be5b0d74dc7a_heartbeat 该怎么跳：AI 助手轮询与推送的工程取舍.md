## 背景

OpenClaw 的 agent 平时是事件驱动的：消息进来，agent 醒来处理，然后休眠。这个模型省 token,但覆盖不了另一类需求——没有人发消息时，agent 也应该自己“活着”：定时巡检邮箱、盯着 CI 状态、早上汇总日报。heartbeat 就是为这类场景设计的机制：每隔 N 分钟唤醒一次 agent,让它检查任务清单(HEARTBEAT.md),决定做点什么。

但 heartbeat 本质是轮询，而很多场景更适合推送。这篇文章记录我在配置过程中的取舍思路，给同样在搭自动化的人一个参考。

## 问题：两类事件，两种驱动方式

把需求拆开看，事件源其实分两类：

- **周期性关注**：比如“每小时看一眼磁盘占用”“每天早上汇总待办”。这类任务没有明确触发点，只能靠定时唤醒——轮询是自然选择。
- **外部事件**：GitHub 来了 PR、监控告警触发、外部服务回调。这类事件有明确源头，等下一次心跳再处理就是白白增加延迟——推送更合理。

问题在于，很多人(包括最初的我)把所有自动化都塞进 HEARTBEAT.md,让心跳承担一切。结果要么间隔太短、token 烧得心疼，要么间隔太长、告警滞后半小时。

## 我的做法

**第一步：盘点任务，按事件源分类。** 把堆在心跳里的任务全部列出来，标成三类：巡检类(轮询)、定时类(改用 cron)、事件类(改用推送)。我当时盘点的结果是，80% 的任务其实不该走心跳。

**第二步：心跳只留轻量巡检。** HEARTBEAT.md 里只保留“检查类”任务，并明确写上：无事可做时按约定返回固定标记(如 `HEARTBEAT_OK`),不要输出正文，框架会静默吞掉这条回复。这样空转心跳只消耗极少 token。间隔从默认值调到 30–60 分钟，对巡检类足够。

**第三步：事件类改推送。** 有公网条件的，用 webhook 插件接收外部回调，转成消息投给 agent;没有公网的，用 cron 定时跑本地脚本，有产出才通过 CLI 把结果注入会话——这等效于“脚本侧的推送”，比盲轮询省得多。

**第四步：组合兜底。** 最终形态：推送做主干，保证实时性；低频心跳做兜底，防止推送链路挂掉后任务静默失效。可以在心跳清单里加一条“核对最近一次推送是否正常落地”。

## 踩坑点

- **空转心跳不免费。** 每次心跳都是一次模型调用，哪怕只是“看一眼清单”。我一度把间隔设成 5 分钟，一天下来 token 是原来的好几倍。先跑一周看日志，再定间隔。
- **心跳会话可能被长任务占住。** agent 正在跑耗时任务时，下一次心跳要么排队要么跳过，表现是“心跳偶尔失踪”。重任务不要放在心跳里触发。
- **推送需要防抖。** CI 短时间连挂三次，webhook 就触发三次模型调用。在插件/脚本层做合并，比如 60 秒内的同类事件合并成一条再投递。
- **公网端点的鉴权别裸奔。** webhook 至少加 secret 校验和来源限制，否则等于给陌生人开了个能指挥你 agent 的入口。

## 可复用建议

一个简单的判断标准：

| 任务特征 | 选择 |
|---|---|
| 无明确触发点、容忍分钟级延迟 | 心跳轮询，间隔 ≥ 30min |
| 有明确触发点、要求秒级响应 | webhook / cron 推送 |
| 关键链路 | 推送为主 + 低频心跳兜底 |

另外两条经验：心跳清单保持极简，写清“无事返回”的约定；所有自动化上线前先观察一周日志，确认实际调用次数和成本，再决定调频。

## 总结

轮询和推送不是二选一，而是分工：心跳负责“没人管时也要看一眼”的兜底巡检，推送负责“有明确事件就该立刻动”的实时响应。把心跳当成万能定时器，是我在这个设计上踩过的最大的坑——拆开之后，成本和实时性反而都变好了。
