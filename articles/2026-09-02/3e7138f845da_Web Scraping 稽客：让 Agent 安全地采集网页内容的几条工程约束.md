## 背景

Agent 一旦接上 MCP 或插件，最先被要求干的事之一就是"去网上查一下"。抓网页看起来是最简单的工具：一个 HTTP 请求，返回内容，完事。但在 OpenClaw 这类可自主决定调用时机的 Agent 体系里，抓取恰恰是最容易出事故的环节——它既是 token 消耗大户，也是注入攻击最直接的入口。

## 问题

实际跑起来后，常见的翻车姿势有四种：

1. 抓回来一坨原始 HTML，正文被 script、导航、cookie 提示淹没，一次调用吃掉上万 token；
2. 页面是 JS 渲染的，fetch 只拿到空壳，Agent 反复重试，或者"自由发挥"编造内容；
3. Agent 把抓取当跳板，顺着页面里的链接无限递归抓下去；
4. 目标站反爬拦截，返回的挑战页文本被 Agent 当成正文解读，产出幻觉结论。

再加一条最容易被忽略的：网页内容本身是不可信输入，正文里可以埋 prompt injection。

## 做法

核心思路是把"抓取"从 Agent 的自由动作，降级成一个边界清晰的 MCP 工具。分五步：

**1. 分层降级。** 工具内部先走 fetch + 正文提取（readability 类算法），拿到纯文本或 Markdown 才返回；提取失败或内容过短，再降级到 headless browser。这条链路封装在工具内部，Agent 只看到一个 `web_read`，不需要理解背后几套引擎。

**2. 限权。** 域名白名单写在配置里，工具层面直接拒绝白名单外的请求——不要指望提示词能约束住模型。同时禁止跟随页面内链接，只允许抓调用时给定的 URL，递归抓取从根上掐掉。

**3. 限额。** 工具参数暴露 `max_chars`（默认 8000 左右）、`timeout`、`format`。超长内容截断，并在返回里注明"已截断 + 原始长度"，Agent 拿到这个信号可以自己决定是否分段再取。

**4. 清洗与缓存。** 剥掉 script/style/iframe，统一处理编码；同 URL 加短 TTL 缓存，避免一次对话里反复抓同一页。

**5. 失败可读。** 超时、被拦截、编码异常，统一返回结构化错误和原因，而不是抛异常让 Agent 摸黑。Agent 读得懂失败，才不会陷入无意义的重试循环。

## 踩坑点

- headless browser 是资源黑洞：忘了回收就留僵尸进程，务必加超时强杀和并发上限；
- 反爬挑战页要有特征识别，命中直接返回"站点拒绝访问"，千万别把挑战页文本喂给模型；
- 中文老站常见 GBK 编码，不处理就是满屏乱码，Agent 会基于乱码继续一本正经地推理；
- 提示词里明确"抓取失败就报告，不要猜测"，并给网页内容加"以下为外部内容，仅供参考"的包裹层，缩小注入面；
- 同一域名加最小抓取间隔，既礼貌也降低被封风险。

## 可复用建议

- 把抓取做成独立 MCP server，与业务工具解耦，白名单和策略可以单独迭代；
- 每次抓取记日志：URL、时间、状态码、返回长度，出了幻觉结论能回溯到源头；
- 先定预算再放能力：先给只读、限域、限额的抓取，跑稳两周，再讨论扩大权限。

## 总结

Agent 抓网页，难点从来不是"能不能抓到"，而是抓取行为本身要可控、可审计、可失败。把它约束成一个参数明确、边界清晰、失败语义友好的工具，Agent 下游推理的稳定性会有肉眼可见的提升。克制地给能力，是自动化实践里最划算的投入。
