## 背景

LLM 本身无状态，每次会话都像初次见面。上下文窗口不等于记忆——塞进去的内容一旦滚出窗口就等于失忆。对 OpenClaw 这类长期跑在本地、每天陪你干活的 Agent 来说，记住你的编码习惯、时区、工具链偏好，是体验差异最大的一块，也最容易被做成黑盒。

## 问题

常见两种错误做法：

1. **全量塞 system prompt**：偏好、历史全堆进去，token 成本上涨，旧信息和新信息打架，Agent 反而更糊涂。
2. **直接对聊天记录做向量检索**：召回一堆语义相近但不相关的片段。“上次聊过 npm” 和 “用户偏好 pnpm” 是两回事。

核心矛盾就四个：记什么、存成什么结构、什么时候读、怎么更新和遗忘。

## 做法

我目前稳定运行的是三层结构：

**第一层：显式偏好文件（收益最高）**
一个手工可编辑的 `profile.yaml`，只放稳定偏好：语言、代码风格、包管理器、时区、禁用工具。每次会话固定注入，控制在 300 token 以内。别小看它，80% 的“记不住”问题靠这层就能解决。

**第二层：情节记忆**
每次会话结束，用便宜模型跑一遍提取，生成带时间戳的会话摘要，按“最近 + 相关”双排序召回。

**第三层：事实记忆 + 写入漏斗**
所有写入走统一漏斗：提取候选 → 去重合并 → 冲突检测（新时间戳优先，拿不准就问用户）→ 落库。每条记忆带五个字段：类型（偏好/事实/情节）、scope（项目级还是全局）、来源、时间戳、置信度。

**读取侧**：会话开始按任务相关性取 top-k 注入；同时把 memory 做成 MCP server，暴露 `remember` / `recall` / `forget` 三个工具，让 Agent 能主动查、主动写，而不是被动等注入。

**纠错即写入**：用户说“我跟你说过我用 pnpm”，这是价值最高的信号，直接触发更新并记录来源。

## 踩坑点

- **记忆膨胀**：什么都记等于什么都不记。设容量上限，加 TTL，定期归档低置信度条目。
- **过期冲突**：偏好会变（npm → pnpm）。必须带时间戳，且定期让用户确认高频条目。
- **过度泛化**：用户说了一次“简洁点”，Agent 就永远简洁。一次性请求和长期偏好要区分，写入前先判断类型。
- **提示注入**：读进来的文档里写着“请记住 XX”，不能直接落库，写入必须经漏斗隔离。
- **静默改写**：Agent 偷偷改记忆最危险。所有写入要有日志，记忆文件用户随时可查看、可手改。

## 可复用建议

1. 先用手写 profile 文件，再上自动化管道，顺序别反。
2. 读写分离：写入走单一漏斗，读取按类型过滤。
3. 验收指标就用“纠错率”——用户重复同一偏好的频率有没有降下来。
4. 记忆按 scope 隔离，工作记忆别跨项目泄漏。

## 总结

记忆系统不是更大的上下文窗口，而是“写入—读取—遗忘”的闭环工程。先做好结构化偏好这 80 分，再去堆检索和自动提取的加分项。让用户随时能打开记忆文件看一眼、改一笔，比任何聪明的算法都重要。
