## 背景

LLM 本身无状态。在 OpenClaw 上跑长期 agent 时，今天纠正过的东西明天就忘——上下文窗口再大，也装不下几个月的交互历史。所以"记住偏好"本质上是一个**存储 + 检索 + 更新**的工程问题，不是往 system prompt 里加一句"请记住我"能解决的。

## 问题

最常见的错误做法：把聊天记录全文写进一个 `memory.md`，每次请求整体注入。跑两周后通常出现三个症状：

- 检索靠运气，噪声淹没了本次真正需要的两条偏好
- 只增不删，三个月前的旧偏好还在影响行为
- context 预算被记忆吃掉一半，工具调用反而没空间

## 做法：三层记忆 + MCP 工具化

我的方案是把记忆拆成三层，写入和读取策略分开：

**1. 偏好层（profile）**：慢变化的结构化事实——语言、代码风格、回复长度、常用工具链。用 JSON/YAML 存，字段带 `source`（来源会话）、`confidence`、`updated_at`。每次请求固定注入，控制在几百 token 内。

**2. 情节层（episodic）**：单次会话中有价值的事实——项目背景、临时决定、踩过的坑。向量库 + 标签，按需检索，只取 top 3-5 条并附带时间戳。

**3. 工作记忆**：当前会话内的事，会话结束即清理，不落盘。

关键设计是把记忆做成 **MCP 工具**暴露给 agent，而不是框架里偷偷做：

- `remember(content, scope, tags)`：写入，默认需要用户确认
- `recall(query, scope)`：检索，偏好层直接返回结构体，情节层走向量
- `forget(id)` / `list()`：删除与审计

写入权交给模型、确认权留给用户，这个分工很重要——agent 主动记的往往比规则匹配准，但未经确认的记忆是污染源。

**写入时机**：显式纠正（"以后别用表格"）立刻写偏好层；隐式信号（连续三次拒绝某类建议）在会话结束统一提炼，不实时写。

**冲突处理**：新偏好不 append，而是 supersede 旧条目并保留历史版本，出问题可回滚。

## 踩坑点

1. **隐式抽取太激进**。"帮我用英文写这封邮件"不等于用户偏好英文回复。把一次性指令写成永久偏好的事故我遇到过两次——隐式信号必须观察重复次数。
2. **向量相似 ≠ 偏好相关**。查"部署"召回了三个月前一次闲聊。情节层查询必须叠加结构化过滤（scope、时间窗）。
3. **缺来源标记**。记忆错了却说不清从哪来，无法定位是哪次对话污染的。`source` 是审计的最低要求。
4. **没有 TTL**。设备、项目、团队都会换。情节层给 30-90 天衰减；偏好层靠 `updated_at` 提示模型复核。
5. **注入不设上限**。偏好层建议硬编码 token 上限，超限按 confidence 截断。

## 可复用建议

- 先用文件，别急着上向量库；偏好少于 50 条时检索收益趋近于零
- 每条记忆必须带 `source / confidence / updated_at` 三件套
- 写入默认要确认；删除工具和写入工具同等重要
- 每周跑一次审计脚本：看注入了什么、占多少 token
- 把"你记住了哪些关于我的事"做成可随时调用的命令——透明度决定信任

## 总结

记忆系统的难点不在存，而在取舍：什么值得写、什么该过期、错了怎么退。把它当成一个带版本控制的数据库来设计，而不是越写越长的日记本，agent 才会在第七十次对话时表现得像真的认识你。
