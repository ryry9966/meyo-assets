## 背景

LLM 本身是无状态的。OpenClaw 这类常驻 Agent 如果每次会话都从零开始，用户就得反复交代"我用 Python""部署走 Docker Compose""commit message 别加 emoji"。这些需求不复杂，但散落在对话里，指望模型自己"记得"是不可靠的——记忆必须是系统设计出来的，而不是提示词里恳求出来的。

## 问题：三种常见错误做法

1. **全量塞上下文**：把历史对话全放进 system prompt，token 成本线性增长，关键偏好被淹没。
2. **只靠模型自觉**：提示词里写"请记住用户偏好"，模型口头答应，下个会话照样忘。
3. **上来就上向量库**：偏好类信息数量少、要求逐字保真，embedding 检索反而容易漏召回或召回近似项。

## 做法：分层记忆 + 结构化存储

**1. 先分类型。** 我把记忆拆成三层：

- 工作记忆：当前会话上下文，不持久化；
- 情景记忆：会话摘要（做了什么、改了哪些文件），按时间存，检索按相关性取；
- 语义记忆：用户长期偏好和事实，结构化存储。

**2. 抽取走独立通道。** 每次会话结束后，用便宜模型跑一遍抽取 pass，按固定 schema 输出候选条目：

```json
{"type": "preference", "content": "测试统一用 pytest", "confidence": 0.8, "source": "session_042", "updated_at": "..."}
```

关键约束：type 只允许 preference / fact / event 三类，防止抽取器自由发挥。

**3. 写入前过闸门。** 候选条目与现有记忆做去重和冲突检查：同主题新条目覆盖旧条目并保留版本号；confidence 低于阈值、或与现有记忆冲突且来源只有一次的，先进"待确认区"，不直接生效。

**4. 注入分两种。** 偏好条目少（几十条以内）就全文注入 system prompt，保证逐字保真；情景记忆量大，才用检索按需取。

**5. 让用户看得见、改得动。** 记忆文件用人类可读的 YAML/JSON，提供"列出记忆 / 删掉这条"的显式命令。用户主动纠正的条目标记为 pinned，抽取器不可覆盖。

## 踩坑点

- **一次性表述被固化成永久偏好**："今天先不跑测试"被抽成"用户不跑测试"。解法：偏好类条目要求出现频次或显式确认；事件类表述只进情景记忆。
- **冲突条目并存**：新旧偏好同时注入，模型行为随机。解法：同主题 upsert，不留两份。
- **注入位置导致偏好失效**：偏好块放 system prompt 末尾容易被后文覆盖。建议放靠前位置，并明确"以下为长期偏好"的边界。
- **Agent 静默改记忆**：会话中途模型自己写记忆且不留痕，出错无从排查。写操作单独走日志，可回放。
- **隐私**：记忆文件含敏感信息，保持本地存储，提供导出与全量删除。

## 可复用建议

- 从一个 `memory.yaml` 开始就够：`preferences` + `facts` 两段，别急着上向量库。
- 读写分离：抽取 → 校验 → 写入是独立流水线，不要在主对话循环里顺手写。
- 建一个最小评测集：十条"助手是否记得 X"的用例，每次改记忆逻辑跑一遍，防回归。
- 每条记忆带 `updated_at` 和来源会话 ID，排查"它为什么这么以为"时能定位到原始对话。

## 总结

记忆不是提示词技巧，而是存储 + 管线问题。核心三件事：**分类**（偏好/事实/事件分开）、**结构化**（偏好逐字注入优于向量检索）、**可审计**（用户可见可改，写入留痕）。先用最土的 YAML 跑通闭环，等情景记忆检索真成为瓶颈，再引入向量方案也不迟。
