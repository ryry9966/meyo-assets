## 背景

绝大多数 Agent 的用法是"你问它答"：提醒要手动设，日报要手动触发，盯磁盘要自己想起来去问。OpenClaw 里有一个容易被忽略的小机制——心跳（heartbeat）：Agent 每隔一段时间自动醒来，读取工作区根目录的 `HEARTBEAT.md`。文件里有可执行的内容就干活，没有就静默跳过。一个 Markdown 文件加几行配置，Agent 就从问答工具变成了有"脉搏"的东西。

## 问题

把"主动做事"做成工程，核心矛盾有两个：一是频率与成本的平衡——心跳太密烧 token，太疏失去意义；二是指令模糊——"帮我看看新闻"这种写法，跑起来要么没输出，要么每天刷屏。我之前用外部 cron 加脚本调模型做过定时任务，但上下文是割裂的：脚本不知道对话历史，Agent 不知道 cron 存在。HEARTBEAT.md 的价值在于把"什么时候做什么"放进 Agent 自己的上下文里，判断逻辑和执行在一个会话里完成。

## 做法

1. 在工作区（默认 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`；
2. 用清单式写法，每条任务写清三件事：触发条件、动作、输出格式。例如：
   - 工作日早上 8 点：汇总日历 + 天气 + 未读消息，输出不超过五行；
   - 每周一：检查磁盘剩余空间，低于 20% 才上报；
3. 按需调整间隔：配置项 `agents.defaults.heartbeat.every` 控制心跳周期，默认约 30 分钟；
4. 利用静默约定：文件为空、或只有 `# HEARTBEAT` 标题时，Agent 直接跳过本次心跳，不发起模型调用。不想让它主动做事，清空文件即可；
5. 调试期把间隔临时调到 2-3 分钟验证行为，确认后再改回去；检查类任务还可以给心跳单独指定一个便宜的模型。

## 踩坑点

- **文件变垃圾场**。任务堆到十几条后，每次心跳都是一次完整的模型调用，月底账单会教育你。控制在 3-5 条以内，做完的立即删除或注释。
- **没有静默时段**。凌晨三点收到磁盘报告并不有趣。新版支持 `activeHours` 配置，至少也要在任务文本里写明"22:00-08:00 不发送"。
- **输出不设上限**。不写"三行以内"，Agent 会给你写小作文。格式约束必须落在文件里。
- **重复上报**。心跳报过的事，你又手动问一遍，可能触发重复消息。让 Agent 维护一个状态标记，或写明"上次已汇报则跳过"。
- **心跳跑在主会话里**。别塞长任务，会挤占正常对话的上下文。心跳任务应该短平快，重活拆出去单独触发。

## 可复用建议

- 把 `HEARTBEAT.md` 当代码维护：进 git、改动留说明、每月清理一次过期任务。
- 任务分层：高频低耗（检查类）和低频高耗（汇总类）分开，触发条件写在任务文本里，靠 Agent 判断是否到达触发点。
- 明确边界：它适合"带判断的软任务"（要不要报、报多少），不适合精确调度——需要准点的场景老老实实用 cron 触发，别硬塞进心跳。

## 总结

HEARTBEAT.md 不是一个复杂的功能，但它改变了交互模型：从"拉"变成"推"。实际价值完全取决于纪律——任务少、条件清楚、有静默时段、定期清理。建议从一条任务开始（比如早报），观察一周的输出质量和 token 消耗，再决定是否扩展。主动性是有持续成本的，别让它变成一个安静的账单生成器。
