## 背景

OpenClaw 的定时任务（cron）机制很简单：到点后，把任务里配置的 instruction 交给 agent，在一个独立会话里执行，再把结果投递到指定频道。听起来像"定个闹钟"，实际更像"雇一个每天定点上班、但完全没有你聊天记录的同事"。

很多人把 cron instruction 当备忘录写，跑起来才发现问题百出。这篇帖总结我近期把十几个定时任务跑稳之后的经验。

## 问题

一个典型的失败指令长这样：

```
每天早上 8 点给我发个日报
```

它在对话里能成立，是因为人可以现场澄清：哪个日报？发到哪？什么格式？而 cron 是无人值守的，没有澄清机会。常见翻车方式：

- agent 不知道"日报"指什么，自由发挥，每次格式都不一样；
- 发错频道，或时间跑偏（时区按服务器算）；
- 数据源挂了，它为了"完成任务"自己编了一份数据。

## 做法

我的原则：**把 instruction 写成一份自包含的岗位说明书**，包含六个要素。

1. **目标与时间**：做什么、几点做，时区写死（如"北京时间 08:00"），别让 cron 表达式的时区靠猜。
2. **数据来源**：指定用哪个工具或 MCP server 取数，并写死兜底——"取不到就标注'数据缺失'，禁止推测"。这一句是防幻觉的关键。
3. **判断逻辑**：什么算异常，给出可执行的标准，而不是"帮我看看有没有问题"。
4. **输出模板**：字段、顺序、长度上限。下游要解析或想跨天对比，格式漂移就是灾难。
5. **投递与静默规则**：发到哪个频道；高频任务是每次都发，还是只在异常时提醒。
6. **失败策略**：报错时发一条错误摘要还是跳过本次；重试如何避免重复投递。

改造后的版本：

```
任务：每天北京时间 08:00 发送昨日日报。
数据：调用 github 工具读取昨日 commit 与 PR；调用系统命令获取服务器负载。
格式：三行以内——提交数、PR 状态、一句风险提示。
投递：发到 Telegram 的"工作"会话。
兜底：任一数据源失败，对应字段写"数据缺失"；全部失败则只发一条"数据源不可用"。
静默：无风险时仍按模板发送，用于确认任务存活。
```

对比能看出区别：第一版是写给你的便签，第二版是交给 agent 的工单。

## 踩坑点

- **依赖上下文**："老规矩""和上次一样"，cron 会话里没有"上次"。
- **时区想当然**：本机 UTC+8，服务器 UTC，任务每天早跑八小时。
- **没有防编造兜底**：API 一挂，它给你一份"看起来很全"的假日报，比不发更糟。
- **高频任务每次都发言**：15 分钟一报的监控改成只在异常时提醒，信噪比立刻上去。
- **instruction 里写死 token**：凭据走环境变量或凭据配置，别塞进 prompt。
- **与主会话混用**：长对话上下文会干扰任务判断，任务输出也会污染主会话，保持隔离。

## 可复用建议

把六要素存成模板片段，新增定时任务先套一遍再微调：

> 目标 / 数据来源（含兜底）/ 判断逻辑 / 输出模板 / 投递与静默规则 / 失败策略

另外两条：每个任务只做一件事，别在指令里"顺便也……"；上线后人工跟两三天日志，确认数据源和投递都对了，再放手。

## 总结

Cron instruction 的质量，取决于你是否把它当成写给"一个没有你们聊天记录、会严格照字面执行、但不会替你补全信息"的同事的岗位说明书。写清楚来源、格式、兜底和静默规则，定时任务就能从玄学变成可靠的基础设施。
