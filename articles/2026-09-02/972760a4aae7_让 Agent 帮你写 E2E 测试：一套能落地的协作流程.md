## 背景

E2E 测试是价值最高、也最贵的一层：覆盖率难看、选择器随 UI 改版腐烂、写一条用例的时间够写三条单测。最近我们试着把 Agent 接上浏览器类 MCP 工具，让它参与 E2E 用例的生产，跑了一个多月，有些经验值得记录。

先说结论：直接丢一句"帮我写 E2E 测试"给模型，产出的东西基本不能用。有效的做法是把 Agent 当成一个**权限受限的初级工程师**——能探索、能起草、能自修，但不能直接提交。

## 直接问模型的三个典型翻车姿势

1. **幻觉选择器**：模型凭想象写出 `.submit-btn.primary`，页面上根本不存在。
2. **断言空心化**：测试全绿，但只断言了页面跳转，核心业务状态完全没验证。
3. **一次性生成 50 条**：全部红着，没人有动力修，最后整个 PR 被扔掉。

## 我们的流程

**第一步：喂上下文，不喂任务。** 仓库里放一份 `TESTING.md`，写清命名规范、fixture 用法、选择器优先级（`data-testid` > role > 文本），再加一条人写的"黄金用例"作参考。Agent 每次先读这份文件。这是整个流程里 ROI 最高的一步。

**第二步：先探索，后书写。** 通过浏览器 MCP 工具让 Agent 真实打开页面、做 DOM 快照、记录真实选择器，再开始写。禁止跳过探索直接生成——这一条要写进系统提示词。

**第三步：一次一条，立即运行。** 生成一条就跑一条，失败时把报错和截图喂回去，允许自修，最多 3 轮。超过 3 轮说明用例本身设计有问题，转人工。

**第四步：人只审 PR。** Agent 的产出以 PR 形式提交，永远不进 main。人审的重点是断言语义，而不是"绿了就行"。

**第五步：隔离观察期。** 新生成的用例打独立标签，前两周跑在独立 job 里观察稳定性，不阻塞主干。

## 踩坑点

- **等待策略**：模型酷爱 `waitForTimeout(3000)`，必须强制改成 auto-wait / `expect` 轮询，否则产出的全是 flaky 测试。
- **测试数据污染**：Agent 跑得勤，共享环境很快被脏数据塞满。改成独立账号 + 数据工厂后才消失。
- **假通过**：Agent 有时把异常吞掉后标记"通过"，这比失败更危险。review 时重点检查有没有 try/catch 包住断言。
- **循环成本失控**：自修循环不设上限，一次任务烧掉的 token 很可观。硬编码 3 轮上限，别信"再试一次就好了"。

## 可复用的建议

- `TESTING.md` 规范文件 + 一条黄金用例，是给 Agent 最好的输入，比任何花哨的 prompt 模板都管用。
- 让 Agent 做"从 0 到 0.6"：骨架、遍历路径、选择器收集；人做"0.6 到 1"：断言语义和稳定性调优。
- 产出物永远是 PR，人只在 review 环节介入，其余环节不盯。
- flaky 隔离机制要提前建好，否则 Agent 产能上来后，CI 会被劣质用例淹没。

## 总结

一个多月下来，E2E 用例的编写时间大约省了 40%~60%，但省的不是"写"的时间，而是"查元素、起骨架、修编译错"这些机械劳动。断言该验证什么、哪些路径值得测，判断权始终在人。别指望全自动，指望把人从体力活里捞出来——这才是 Agent 协作在测试这件事上的正确姿势。
