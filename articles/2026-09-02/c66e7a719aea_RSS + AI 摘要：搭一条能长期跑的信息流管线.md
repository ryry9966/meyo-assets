## 背景

我订阅了三十多个 RSS 源，每天真正值得点开的内容不到十分之一。筛选本身是纯重复劳动，天然适合交给自动化管线：抓取、去重、摘要、推送，每一环都是确定性的工程问题，不需要什么魔法。

## 问题

直接用阅读器有两个痛点：一是噪声大，部分源更新频繁但信噪比很低；二是无法按个人兴趣加权排序。引入 AI 摘要后又冒出新问题——怎么去重、怎么控制 token 成本、摘要结果推到哪里、模型会不会编内容。

## 做法

整条管线分四段，每段落盘中间结果，方便单独排查：

1. **抓取**：cron 每 6 小时跑一次脚本，拉取 OPML 里所有源的 feed，用 feedparser 解析。
2. **去重入库**：SQLite 存 `entry_id / link / published`，只把新条目放进下一环。优先用 guid 去重，guid 缺失时退回 link 归一化后的 hash。
3. **摘要**：把 24 小时内的新条目按源分组，拼成带编号的 prompt，要求模型只输出严格 JSON：`[{index, one_line, why_read}]`，并禁止引用编号之外的任何条目。Schema 校验失败重试一次，再失败就跳过这批。
4. **推送**：把摘要渲染成 Markdown，按源分节，每条附原文链接，推到 Telegram bot 或写入笔记目录。摘要只做筛选辅助，不替代原文。

在 OpenClaw 里可以把第 3 步包成 agent 任务：定时触发，agent 负责摘要 prompt，MCP 工具负责读写状态库和推送。脚本版和 agent 版我都在用——脚本版更稳，agent 版胜在改 prompt 不用重启。

## 踩坑点

- **guid 不稳定**：个别源每次刷新 guid 都变，产生大量“假新条目”。退到 link 归一化后再 hash 才压住。
- **摘要幻觉**：模型偶尔给不存在的条目写一句话。prompt 里强调只允许引用编号条目，再校验 index 是否在输入范围内，越界直接丢弃。
- **成本失控**：per-item 摘要的 token 消耗是批量的好几倍。改成按源批量、只喂 title + summary（长文截断 500 字）后，日成本降了一个数量级。
- **时区坑**：按“最近 24 小时”过滤时，本地时间与 feed 的 UTC 时间差 8 小时，第一天全部漏抓。统一转 UTC 再比较。
- **调度重叠**：模型响应慢时下一次 cron 已启动，导致重复推送。加文件锁解决。

## 可复用建议

- 各阶段解耦，中间结果落盘（JSON 文件就够），出问题时能单独重跑某一段。
- 让模型输出结构化 JSON 而不是散文，渲染和过滤都放在自己的代码里做，管线才可维护。
- 摘要结果按 entry hash 缓存，重跑不重复计费。
- 先跑一周“影子模式”（只落盘不推送），确认摘要质量和误报率，再接入推送。

## 总结

这条管线没依赖任何复杂框架，核心就是：cron + feedparser + SQLite + 一次结构化 LLM 调用。现在每天早上收到一份十来条的摘要，花在信息筛选上的时间从半小时降到几分钟。RSS 没死，只是缺一层自己的过滤逻辑——而这层逻辑值得自己写，因为规则和数据都在你手里。
