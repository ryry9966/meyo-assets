## 背景：为什么自动化任务一定会重复执行

在 OpenClaw / Agent / MCP 这类自动化环境里，任务不是“跑一次就结束”的。定时任务可能重叠，Agent 可能因为模型输出不稳定或工具超时重试，MCP 工具可能被上游重复调用，用户也可能手动重跑一个看起来“没成功”的流程。网络抖动、队列重投、客户端超时，都会把同一个业务动作再送一次。

问题不在于“重复执行会不会发生”，而在于“重复执行之后，数据、外部系统、通知、账单会不会出问题”。这就是幂等性要解决的事。

幂等性的定义不是“不会重复执行”，而是：**同一个业务意图，重复执行一次或多次，产生的副作用和只执行一次一致。**

## 问题：一个常见的翻车现场

假设你有一个 OpenClaw 自动化任务：从邮件或 webhook 里解析订单，然后写入表格或 CRM，再调用 MCP 工具发通知。

某次执行到一半，MCP 工具返回超时。自动化框架认为失败了，于是重试整个任务。由于没有幂等保护，订单被插入两次，通知也发了两遍。用户看到两条重复记录，还要手动清理。

更隐蔽的情况是：两个相同的定时任务因为调度重叠同时启动，或者上游事件至少一次投递，把同一条 webhook 推送了两次。这类问题不是偶发 bug，而是分布式系统里的常态。

## 做法：四件套落到入口

### 1. 先确定一个幂等键

给每个业务动作确定一个稳定、唯一的键。优先使用上游事件 ID，比如 webhook 的 `event_id`、消息队列的 `message_id`、订单号。如果没有，就在任务首次创建时生成 UUID，并把它持久化到输入参数里。

键的粒度要对应“一次业务意图”。比如“同步订单 1001”是一个键，“给订单 1001 发通知”可以是另一个键。过粗会导致不同动作互相去重，过细则失去保护。

### 2. 数据库唯一约束兜底

不要在应用层只做“先查再插”。并发重试时，两个请求都会查到“不存在”，然后都插入成功。

正确做法是在数据库加唯一索引，例如：

```sql
UNIQUE KEY uniq_source_entity (source, external_id)
```

插入时使用 `INSERT ... ON CONFLICT DO NOTHING`，或者捕获唯一约束冲突错误。冲突就当成“已处理过”，直接返回成功。

### 3. 状态机 + 条件更新

对于更新类操作，不要无条件覆盖。用状态机或版本号控制：

```sql
UPDATE tasks
SET status = 'done', updated_at = now()
WHERE id = ? AND status = 'pending';
```

如果影响行数为 0，说明任务已经被处理过，直接跳过。这样即使重复执行，也不会把已完成的记录拉回处理中，或者覆盖更新的数据。

### 4. 外部副作用先落记录

如果任务要调 MCP 工具发通知、写外部系统，无法用数据库唯一约束保护，就加一张“执行记录表”。在执行副作用之前先插入一条 `pending` 记录，写完外部系统后更新为 `done`。重试时先查这条记录：

- 不存在：第一次执行，插入 `pending` 并继续；
- 存在且 `done`：直接返回成功；
- 存在且 `pending`：说明上一次可能执行到一半，按业务决定等待、补偿或查询外部状态。

在 OpenClaw 的 MCP 封装里，可以把这套逻辑放在工具服务端。工具描述里声明需要 `idempotency_key`，服务端按 key 去重。客户端重试时携带同一个 key，而不是每次生成新的。

## 踩坑点

### 1. 只查再插，不加唯一索引

这是最常见的错误。并发窗口内两个相同请求都会通过检查，最终产生双份数据。唯一索引是最后一道防线，不能省略。

### 2. 部分成功被当成未执行

比如主库写入成功，但通知失败。重试时如果只看“任务失败”，会把主库操作再做一遍。解决方法是把事务性操作和非事务性操作拆开，每步都有自己的状态记录。重试时从失败的那一步继续，而不是从头再来。

### 3. 用自然时间窗口当幂等键

“每天只跑一次”不代表幂等。如果任务在 23:59 和次日 00:01 各触发一次，它们属于不同业务周期，但看起来像重复。应基于业务键，比如“日期 + 业务类型 + 实体 ID”，而不是简单按小时或分钟去重。

### 4. 键的粒度不对

键太粗，比如只用 `task_type`，会导致不同实体互相误去重。键太细，比如加入随机数或时间戳，又会让重复执行无法被识别。键必须来自业务意图，而不是执行环境。

### 5. 忘了返回明确状态

自动化任务如果只返回 `success` 或 `failed`，重复执行被跳过时，调用方无法区分“这次是新建了资源”还是“命中了幂等”。应返回 `created`、`updated`、`skipped` 等明确状态，方便日志和监控。

## 可复用建议

1. **默认采用幂等键**：所有写路径都要求传入或生成一个 `idempotency_key`，在入口统一校验。
2. **数据库先加约束**：唯一索引、条件更新、状态字段，比应用层判断可靠得多。
3. **封装一个 `withIdempotency(key, action)`**：在 OpenClaw 任务或 MCP 工具服务端统一处理去重，业务代码只写正常逻辑。
4. **测试重复执行**：每个自动化任务至少跑三遍相同输入，断言副作用数量为 1，数据状态一致。
5. **记录幂等命中日志**：当请求被跳过时，记一条 `idempotency_hit` 日志，带上来源和键。这能帮你发现上游重复投递的规律。
6. **对 MCP 工具做幂等声明**：工具描述里明确参数含义和返回状态，让 Agent 能正确判断要不要重试。

## 总结

自动化任务一定会遇到重复执行，这不是异常，而是常态。真正能防止事故的，不是祈祷调度器不重试，而是在入口处做好四件事：**确定幂等键、加数据库唯一约束、用状态机条件更新、把外部副作用落到执行记录表。**

有了这四件套，重复执行不会产生双份数据、重复通知或覆盖更新。它反而会变成一次免费的巡检，帮你验证系统在“至少一次投递”下依然稳定。

在 OpenClaw 的自动化实践里，不建议把幂等性做成每个任务各自发挥。最好在插件或 MCP 工具层提供统一封装，让业务开发者默认就具备幂等能力，而不是出了问题再补。
