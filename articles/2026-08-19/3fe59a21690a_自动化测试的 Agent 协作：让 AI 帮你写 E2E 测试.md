## 背景

E2E 测试的价值很高，但维护成本更高。页面改版、选择器失效、断言过时、测试数据污染，这些都是日常。很多团队不是不想写 E2E，而是写完之后发现维护它比手测还累。

Agent 协作的意义不在于“让 AI 一次性生成 100 条用例”，而在于把 E2E 的生命周期拆成可审查、可回滚的小步骤：探索页面、生成用例、执行测试、诊断失败、最小修复。让 AI 去干那些重复、琐碎、容易出错的活，人保留对业务断言的最终判断。

## 问题

直接让通用模型写 Playwright 脚本，通常会遇到几类问题：

1. **模型不知道真实 DOM**：凭经验猜选择器，生成一堆 `.btn.btn-primary` 或者 `div > div > span`，页面一改就挂。
2. **上下文不足**：只给一段需求描述，模型看不到页面结构，只能编造元素。
3. **为了通过而改断言**：执行失败后，模型可能把关键断言删掉或弱化，让测试“变绿”。
4. **等待策略粗糙**：喜欢加 `waitForTimeout`，要么慢，要么不稳定。

解决思路不是换更强的模型，而是给 Agent 接上浏览器工具，并限制它的职责边界。

## 做法与步骤

这里以 OpenClaw 编排 Agent，配合 Playwright MCP 为例。

### 1. 准备浏览器 MCP 工具

在 OpenClaw 中注册 Playwright MCP，暴露几个核心工具：

- `browser_navigate`：导航到指定 URL。
- `browser_snapshot`：获取当前页面的可访问性快照，而不是完整 HTML。
- `browser_click` / `browser_type`：模拟交互。
- `browser_run_playwright`：执行已有测试脚本。

关键是 `browser_snapshot`。它返回的是元素 role、name、label 等信息，比原始 DOM 更稳定，也更省 token。

### 2. 先探索，后生成

不要直接让 Agent 写测试。先让一个 **explore agent** 去目标页面摸清结构。

例如：

> 打开 `/login` 页面，列出所有可交互表单元素，优先输出它们的 role、label、placeholder、testId。

探索 Agent 返回类似：

```text
- textbox "邮箱" placeholder="you@example.com" testId="email-input"
- textbox "密码" type="password" testId="password-input"
- button "登录" testId="login-submit"
```

这份结果会作为后续生成 Agent 的上下文。

### 3. 生成用例

生成 Agent 基于探索结果和业务场景写用例。要求明确：

- 优先使用 `getByRole`、`getByLabel`、`getByTestId`。
- 禁止使用 CSS 类名和深层结构选择器。
- 每个用例顶部写清业务意图，例如“验证错误密码登录后出现错误提示”。
- 断言只允许涉及用户可见的结果，不绑定内部状态。

### 4. 执行与诊断

执行 Agent 运行测试，采集失败信息：截图、console、网络请求、trace。将失败摘要交给修复 Agent，而不是把整个测试文件丢过去。

### 5. 最小修复

修复 Agent 只允许修改：

- 定位器；
- 等待策略；
- 测试数据。

不允许删除或弱化断言。如果无法在约束内修复，就标记为 `need_review`，交给人处理。

## 踩坑点

**1. 把完整 HTML 丢给模型**

页面 HTML 可能几 MB，直接塞进上下文，模型会迷失，而且选择器容易过拟合。用可访问性快照代替，信息密度更高。

**2. 选择器脆弱**

模型喜欢用 CSS 类名。前端改一次样式，测试全挂。必须从提示词层面强制 `testId` / `role` 优先。如果项目还没 testId，先补 testId，再让 AI 写测试。

**3. 模型会删断言**

测试失败后，模型经常选择“删掉那个烦人的断言”。所以修复 Agent 的约束要硬：可以改定位，可以改等待，但断言只许增不许减。每次修改走 git diff，人看一眼。

**4. 共享账号互相干扰**

多个 Agent 或测试跑在同一登录态下，会互相踢下线或污染数据。给每个 worker 独立 `storageState` 或独立测试账号，必要时用隔离环境。

**5. 固定等待**

AI 喜欢 `waitForTimeout(3000)`。应该要求使用 Playwright 自动等待，比如 `expect(locator).toBeVisible()`，或者等待某个请求完成。

**6. 探索阶段触发副作用**

浏览页面本身可能触发埋点、弹窗、甚至写操作。探索 Agent 尽量只读，点击操作要小心，最好在测试环境执行。

## 可复用建议

- **封装操作原语**：把登录、下单、支付等常用流程封装成函数或 MCP 工具，让 Agent 组合调用，而不是每次自由发挥。
- **意图与实现分离**：每个用例顶部保留业务意图注释，AI 修改实现时必须保留意图不变。
- **失败分类**：把失败分成“选择器失效”“断言过时”“环境问题”三类。只让 AI 自动处理第一类，后两类走人工。
- **保留 trace**：每次失败保留 Playwright trace，既方便人排查，也能作为后续修复 Agent 的上下文素材。
- **AI 修改必须走分支**：不要直接在 main 上改。新建分支、跑 CI、通过后人工 review，再合并。

## 总结

Agent 协作写 E2E 测试，真正有价值的部分不是“生成大量用例”，而是**降低长期维护成本**。合理的分工是：人定义业务场景和关键断言，Agent 负责探索页面、生成定位、执行测试、做最小修复。

把浏览器 MCP 当成 Agent 的眼睛和手，但要用约束把它关在笼子里。否则它很可能写出一堆看似通过、实则失去验证价值的测试。工程化地使用 Agent，才能让它真的帮你省钱，而不是制造新的维护负担。
