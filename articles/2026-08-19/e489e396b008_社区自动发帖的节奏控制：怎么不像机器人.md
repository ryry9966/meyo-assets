## 背景

在 OpenClaw / Agent / MCP 场景里，社区自动发帖不难做：定时任务触发、生成内容、调用平台接口发送，流程很快就能跑通。难的是跑了一周之后，账号开始频繁验证码、删帖、限制曝光，甚至直接被封。

多数时候不是因为平台“见不得自动化”，而是节奏太机械。固定间隔、固定句式、固定回复速度，这些特征叠加起来，风控系统和普通用户都很容易判定这是机器人。

## 问题

自动发帖像机器人，通常不是单一原因，而是几个机械性同时存在：

- 发帖时间间隔完全固定，形成可预测模式；
- 文案模板化，换个关键词就是新帖，但语义重复；
- 回复触发太敏感，关键词命中就秒回；
- 没有任何“收手”机制，遇到异常也不知道暂停；
- 只控制发布，不控制活跃时段、内容池和审核流程。

很多人第一反应是把随机延迟调大，但只做随机抖动并不解决根本问题。节奏控制需要同时覆盖时间、内容、上下文和熔断。

## 做法/步骤

### 1. 节奏参数化，不要硬编码固定间隔

把发帖节奏设计成“最小冷却 + 随机抖动 + 活跃时段约束”。例如用 YAML 配置：

```yaml
posting:
  min_interval_sec: 1800
  max_interval_sec: 7200
  daily_limit: 3
  active_windows:
    - "09:00-12:00"
    - "14:00-17:00"
    - "20:00-23:00"
```

实际延迟可以这样计算：

```python
delay = max(
    MIN_INTERVAL,
    base_interval * random.uniform(0.75, 1.5)
)
if not is_active_hour():
    delay *= 2
```

关键是让间隔分布不规律，同时避开社区明显不活跃的时间段。

### 2. 内容池与语义去重

不要每次生成全新内容，也不要长期复用同一批文案。更好的做法是维护一个内容池，用模板或 Agent 生成多个候选，发布前做两层过滤：

- 与最近已发布内容做文本相似度计算，低于阈值才允许发；
- 同一天内不重复使用同一内容标签或开头句。

这样可以在保证内容多样性的同时，降低“换关键词就是新帖”的观感。

### 3. 回复前先读上下文

自动回复最容易暴露机器属性。建议用 MCP 工具读取帖子正文、已有回复、作者近期表达，再判断是否回复、回复什么。不要只做关键词触发。

同时给回复动作加冷却时间。例如同一用户 24 小时内最多自动回复一次，帖子发布后至少 10 分钟再回复，避免“秒回”。

### 4. 设置行为预算和熔断

给每个账号设置每小时、每日硬上限，一旦达到上限，不再接受新任务。预算包含发帖、回复、点赞等动作，而不是只限制发帖。

还要监听异常信号：删除、验证码、登录失败、平台返回风控提示、权限变化。出现这些信号时，自动暂停所有任务，并输出告警，等待人工确认恢复。熔断不到位，随机延迟做得再好也容易被一次性处理掉。

### 5. 人工审核队列

全自动发布看起来省事，但长期容易被风控和社区管理员注意。更稳妥的方式是：Agent 生成内容后先进入草稿箱或内部审核队列，人工抽检后再发布。对重要帖子、活动帖、外部链接帖强制人工确认。

## 踩坑点

- **固定 cron + 固定文案**：这是最容易翻车的组合，一周内就会形成明确模式。
- **抖动范围太小**：比如 30 分钟间隔加 30 秒随机，本质上还是固定节奏。
- **只控制发帖，不控制活跃行为**：账号每天都只发帖、不浏览、不回复别人，行为画像不一致。
- **相似度阈值设得太低**：内容重复度高，社区用户比风控系统更快发现。
- **熔断只监控异常日志，不监控规则变化**：平台调整外链政策、禁止某些标签，自动化仍按旧规则发。
- **多账号共用同一 UA / Token / 出口 IP**：单点维度很容易被归因，节奏控制再好也白费。

## 可复用建议

把发布、生成、回复、熔断拆成独立模块，节奏控制作为一个可插拔的调度器。配置外置，不同社区使用不同参数，不要写死。

保留完整决策日志，记录每次发布前的等待时间、内容相似度、触发来源和平台返回结果。这样被限制后可以回放分析，而不是靠猜。

优先内容质量，自动化只负责辅助执行。观察社区真实用户的活跃节奏，把参数贴近正常行为，但不要追求完美模拟真人，这会带来合规风险。

## 总结

社区自动发帖像不像机器人，核心不在于模拟得多逼真，而在于有没有判断、会不会收手、内容是否有上下文。工程上最有效的做法是：硬上限 + 非均匀节奏 + 语义去重 + 上下文回复 + 熔断审查。比无限调大随机延迟更值得投入的是把“停止条件”做好。
