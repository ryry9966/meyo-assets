## 背景

OpenClaw 的 Agent 日常要处理很多混合任务：消息解析、MCP 工具调用、文件整理、定时自动化、长文档问答、代码生成。很多人在接入模型时容易走两个极端：要么所有请求都打给 GPT，token 账单和延迟慢慢失控；要么全部切到本地模型，复杂指令和多步工具调用频繁翻车。

多模型路由不是为了“省钱”，而是让合适的模型做合适的事。尤其当 OpenClaw 同时接入云端模型和 Ollama/LM Studio 这类本地推理服务后，如果没有明确策略，系统会变得越来越不可预测。

## 问题

本地模型适合的典型场景：

- 高频率、低复杂度任务：意图分类、命令解析、关键词抽取
- 结构化输出：日志清洗、字段提取、格式转换
- 隐私敏感内容：本地文件路径、密钥片段、个人聊天原文
- 对延迟敏感且结果容易验证的步骤

云端 GPT 更适合：

- 长上下文理解与综述
- 多步 planning 和工具调用编排
- 模糊指令拆解、代码生成、异常兜底
- 最终回复生成，尤其是需要自然语言质量的场景

如果反过来用，本地模型硬扛复杂任务会输出不稳定、工具调用格式错乱；GPT 处理所有高频简单任务则会让成本和延迟都变得不合理。

## 做法 / 步骤

1. **先盘点 OpenClaw 的任务类型**  
   把实际运行的任务分成：分类、抽取、短摘要、工具调用、规划、代码生成、长问答等。不要凭感觉，最好从日志里找真实的请求样本。

2. **确定路由规则**  
   建议在 OpenClaw 的模型适配层或统一请求入口做策略，不要散落在各插件里。规则可以很简单，例如：

   - 输入预估 token 小于 500，且任务类型属于 classify/extract/short_summary → 本地模型
   - 需要调用 MCP 工具，且工具数量大于 2 → GPT
   - 涉及本地路径、密钥、私人文件内容 → 本地模型
   - 明确要求低延迟或离线执行 → 本地模型
   - 多轮复杂推理、长文档、代码生成 → GPT

3. **落地配置**  
   如果本地用 Ollama，可以在 OpenClaw 的模型 provider 里配置本地 endpoint，例如 `http://localhost:11434/v1`，然后接入 Qwen2.5-7B-Instruct、Llama 3.1 8B 等。GPT 作为 fallback 或复杂任务模型。  
   可以在 OpenClaw 中加一个小 router 节点：先做一次轻量分类，再决定走哪条模型路径。不要只靠模型名判断，要按任务特征匹配。

4. **设置兜底**  
   本地模型解析失败、JSON 格式坏掉或超时，先重试一次；如果还不行，再转 GPT。不要让错误静默吞掉，否则后面排查会很痛苦。

## 踩坑点

- **本地模型输出不稳定 JSON**  
  只靠 prompt 里写“只输出 JSON”基本没用。要用 grammar/constrained decoding，比如 llama.cpp 的 JSON grammar 或 Outlines，或者选择支持严格输出的推理框架。

- **工具调用格式不兼容**  
  OpenClaw 的工具调用通常是 OpenAI 风格，很多本地模型会输出错字段、漏 `tool_calls` 或把参数写进文本。需要写一层转换，或者用专门做过 function calling 微调的模型。

- **上下文长度估算错误**  
  只看用户输入不够，工具返回结果可能很大。本地模型 8k/32k 窗口容易被撑爆。路由时要估算 total context，包括系统提示、历史消息、工具结果。

- **重试导致延迟翻倍**  
  本地模型超时后转 GPT，总耗时会明显增加。建议限制重试次数，或对部分任务做异步处理。

- **用模型名判断能力不可靠**  
  同一个 7B 模型，不同量化、不同 prompt 模板表现差异很大。必须建立自己的小规模测试集，而不是看榜单。

## 可复用建议

- **路由规则配置化**：把阈值、模型名、fallback 策略写成 yaml/json，方便调整和回滚。
- **建立 eval set**：准备 20-50 条典型任务，覆盖意图分类、工具调用、抽取、代码生成。每次换本地模型都跑一遍，记录失败率。
- **监控三个指标**：路由命中率、本地模型失败转云端比例、单位任务平均 token 成本。没有监控的路由很快会退化。
- **敏感数据本地优先**：日志清洗、密钥脱敏、文件名提取等先本地处理，不要把原始内容直接发给云端。
- **把 GPT 当审查者而不是默认执行者**：本地模型先产出草稿，GPT 做终审或异常兜底，能明显降低成本。

## 总结

OpenClaw 多模型路由的核心不是判断“哪个模型更强”，而是给每个任务匹配可接受的成本、延迟和能力边界。先把高频、简单、隐私敏感的任务本地化，再把复杂推理和长上下文保留给 GPT，同时做好失败回退、格式约束和指标监控。这样跑一段时间后，你会比单纯切换模型省下不少成本，也能减少很多半夜被 Agent 错误唤醒的麻烦。
