千问办公这次开源的，不是一个新的模型权重，而是一套上下文基础设施。消息出来后，开发者圈子讨论的重点很少是“参数多大”，更多是“上下文怎么管”。过去两年，行业把大部分注意力放在模型能力上：窗口从 2k 拉到 32k、128k，甚至百万 token。可 Agent 一落地就发现，瓶颈往往不在模型智商，而在上下文工程。模型是大脑，上下文是工作台。现在工作台开始被开源、被标准化，Agent 的下一个战场就此打响。



## 一、把“上下文”从玄学变成工程


上下文不是把资料塞进 prompt 那么简单。它是 Agent 在任务执行期间的完整工作记忆：哪些文档、哪些历史对话、哪些工具输出、哪些权限边界、哪些临时结论。把这套东西管好，才是上下文基础设施的核心。

- 一个直观例子：让 Agent 分析一份 100 页年报并写纪要。直接全量丢进去，模型可能漏掉关键表格，还可能把无关段落当成重点；如果先抽取财务指标、业务摘要、风险提示，再按问题按需展开，token 消耗和准确率都会更稳。
- 上下文窗口大不等于用得好。从 2048 token 到 128k、1M，窗口越宽，噪声、成本、延迟越容易失控。标准注意力机制下，计算量会随序列长度平方级增长，即使靠稀疏注意力优化，超长输入仍有压力。
- 上下文基础设施要解决的，是一组很具体的工程动作：采集、清洗、压缩、检索、注入、隔离、刷新。

如果把模型比作厨师，上下文基础设施就是后厨的备菜台和分菜流程。台面再大，食材乱堆，出菜也不会快。

## 二、开源释放了什么信号


过去，上下文工程散落在各家产品和内部框架里。A 公司做了一套文档分块，B 公司写了一套记忆策略，但大多不公开。千问办公这次开源，等于把办公场景下长期积累的上下文处理能力摆到台面上。

- 办公场景是上下文最密集的试验场：文档、表格、邮件、日程、审批流天然需要长链条、多来源、权限敏感。
- 开源降低可观测性门槛：上下文如何被裁剪、注入、排序，不再是黑盒，团队可以复现和调试。
- 从“模型即产品”转向“上下文即产品”：模型 API 可以切换，但上下文策略一旦形成产品体验，就很难被复制。

从 RAG 到 Agent，第一代上下文工程往往是一个粗糙的拼接层；现在开源基础设施，可能像 Kubernetes 对容器编排的推动：Kubernetes 没有发明容器，却定义了编排层的标准接口，改变了云原生生态。

## 三、为什么 Agent 的下一个战场在这里


单轮问答已经卷到头，Agent 的核心指标从“能不能答对”变成“能不能完成一个长任务”。长任务中，上下文问题会被快速放大。

- 上下文污染：工具返回的无关网页、历史报错信息、重复代码片段，都会把模型带偏。
- token 爆炸：多轮循环不断追加中间结果，几百轮下来，单次请求可能从几万 token 涨到几十万，成本与延迟同步上升。
- 时间衰减：旧信息和新信息权重不分，模型可能拿着过期结论做决策。
- 办公场景原生就是长任务：从“整理上周会议纪要”到“汇总三份合同风险点并生成周报邮件”，涉及跨文档、跨应用、跨权限。

当模型能力趋同，产品差距会越来越来自上下文策略：谁能用更少 token 保持更准的状态，谁就在成本、延迟和稳定性上拉开身位。

## 四、这套基础设施里有哪些关键组件


拆开看，上下文基础设施通常包含以下模块：

- 缓存与复用：前缀缓存、KV cache 复用，避免对相同的系统提示或长文档重复编码。
- 分层记忆：工作记忆放当前任务，短期记忆放会话，长期记忆放用户偏好与项目背景。
- 上下文压缩：用摘要、分块、关键词提取替代粗暴截断，保留语义密度。
- 检索与重排：按需把最相关的片段注入，而不是全量灌入。
- 权限与隔离：跨文档访问要遵守数据权限，不能把 A 部门的预算摘要注入 B 部门的会议。
- 协议与回放：通过标准化接口让不同工具、Agent 交换上下文，并支持事后回放排错。

这些组件单看都不新鲜，难的是把它们打包成一套可复用、可观察、可替换的工程底座。开源之后，团队不用再每个项目从零写一遍。

最后，给关注这件事的人三条冷思考：

1. 把上下文预算当钱看。每个项目先建一个 token 账本，记录哪些上下文被保留、被压缩、被丢弃，否则优化无从谈起。
2. 选型先看可观测性和回放能力。上下文基础设施的价值不在 star 数，而在出错时能不能快速定位是哪一段上下文带偏了模型。
3. 办公 Agent 落地前，先做一份“上下文边界清单”。哪些文档可跨权限使用、哪些临时结论不能被长期记忆、哪些工具输出必须隔离，比直接堆组件更重要。
