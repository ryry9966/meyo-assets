## 背景

在 OpenClaw 这类 Agent 自动化环境里，Cron 任务经常被当成“定时触发一次对话”。很多人直接把平时聊天用的 prompt 塞进定时任务，结果线上跑起来问题不断：该执行的时候不执行、重复执行产生副作用、输出格式飘忽、失败也没有任何记录。

本质原因是：**交互式 prompt 允许模糊，Cron 任务不允许。** 交互时你说“帮我看看今天的数据”，Agent 可以追问、人类可以纠正；但定时任务触发时没有人在回路，指令里的每一个歧义都会被放大。

## 问题

常见的 Cron 任务失败模式有几类：

- 时区不明确，导致“每天早上 8 点”实际在 UTC 凌晨跑；
- 没有幂等设计，任务重试或重复触发会重复写入、重复发送；
- 输出格式随意，下游 MCP / 插件解析失败；
- 同一 session 长期复用，历史上下文污染本次执行；
- 外部依赖没有超时和重试，网络抖动后任务卡死或静默失败。

这些问题大部分不是 Agent 能力不够，而是 instruction 写得像聊天，而不是像 spec。

## 做法：把 instruction 写成可执行规格

我建议 Cron 任务的 instruction 至少包含五个固定段落：**Goal / Context / Steps / Output / Failure**。下面是一个每天抓取 API 并写文件的示例：

```text
Role: 定时数据采集任务
Trigger: 0 8 * * * (Asia/Shanghai)

Goal:
从指定 API 获取最新 10 条记录，写入 data/daily.md，并输出 JSON 摘要。

Context:
- API: https://api.example.com/items?limit=10
- 鉴权: 使用环境变量 API_KEY
- 工作目录: /workspace

Steps:
1. 检查 data/daily.md 最后写入日期。若今天已写入且状态为 success，直接返回 {"status":"skipped"}。
2. 调用 API，超时 10 秒；失败后重试 2 次，间隔 5 秒。
3. 按固定模板将结果写入 data/daily.md。
4. 输出 JSON 摘要。

Output:
只输出一个 JSON 对象，不要输出 Markdown 或自然语言解释。
格式: {"status":"success|error|skipped","items":0,"written_at":""}

Failure:
- 若 API 连续失败，输出 {"status":"error","error":"api_failed"}，不要写入空文件。
- 不要删除或修改其他文件。
- 不要根据自然语言猜测 API 字段，以实际响应 JSON 为准。
```

这个写法有三个关键点：

**1. 触发条件显式声明时区。** 不要只写 `0 8 * * *`，要写 `(Asia/Shanghai)`，或者把时区写进 instruction 正文。跨时区服务器上这是高频事故。

**2. 用状态输出替代“成功了就完事”。** 每次运行都输出机器可读的 JSON，让调度平台、下游插件或日志系统能判断本次运行结果。`skipped` 状态尤其重要，它是幂等的信号。

**3. 把幂等逻辑写进步骤，而不是靠 Agent 自觉。** 步骤 1 明确检查是否已写入，避免 Cron 重复触发或手动补跑时产生重复数据。

## 踩坑点

我在实际使用中遇到过的坑：

- **相对时间表达**：“今天”“明天”“最近一次”在跨日任务里经常出错。定时任务运行在半夜 0 点附近时，“今天”可能已经切换。尽量使用绝对日期或基于文件状态判断。
- **上下文污染**：如果 Cron 任务绑定了一个长期存在的 session，上一轮对话的输出、工具调用记录都可能影响下一轮。建议每次运行使用独立 session，或在 instruction 里明确要求“忽略历史消息，只依据当前输入和文件系统状态执行”。
- **散文式 failure 处理**：写“如果失败就再试试”不如写“失败后重试 2 次，间隔 5 秒；连续失败输出 error JSON”。Agent 需要明确的边界，否则可能无限重试或直接放弃。
- **输出格式会被模型自由发挥**：即使要求 JSON，有些模型还是会在外面包一层 Markdown 代码块。可以在 instruction 里写“只输出 JSON 对象，不要输出代码块标记”，必要时在 MCP 或插件层做一层 strip。
- **副作用操作没有前置检查**：发送通知、写数据库、调 webhook 这类副作用操作，一定要有“是否已经执行过”的判断。Cron 平台的重试机制可能让任务重复跑，幂等不是可选项。

## 可复用建议

1. **固定 instruction 模板**：Goal / Context / Steps / Output / Failure 五段式，避免自由发挥。
2. **先写 dry-run 模式**：在 instruction 里加一个 `DRY_RUN` 环境变量判断，dry-run 时只打印执行计划，不产生副作用。上线前先跑一遍。
3. **输出机器可读状态**：统一 JSON，字段固定，包含 status / error / timestamp。
4. **时区写进 trigger 和正文**：两处都写，减少歧义。
5. **独立 session / 清空上下文**：Cron 任务不要和日常对话共用 session。
6. **给外部依赖设置超时和重试**：网络请求、文件读写、MCP 调用都应有超时和重试次数。
7. **写运行日志**：输出文件带时间戳，或把 JSON 状态追加到日志文件，方便事后排障。

## 总结

Cron 任务的 instruction 不是“表达意图”，而是“约束行为”。交互式 prompt 可以依赖人类兜底，定时任务必须自己兜底。把 instruction 当成一份可执行的 spec，明确时区、幂等、输出格式和失败策略，才能让定时任务稳定运行，而不是每天早晨起来看它有没有抽风。
