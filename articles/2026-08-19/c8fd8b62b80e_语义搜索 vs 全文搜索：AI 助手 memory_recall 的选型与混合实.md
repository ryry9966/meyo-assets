# 语义搜索 vs 全文搜索：AI 助手 memory_recall 的选型与混合实践

## 背景

在 OpenClaw 这类 Agent 框架里，`memory_recall` 通常是记忆模块的读路径入口：Agent 收到新消息后，需要从长期记忆库中召回相关的历史片段、用户偏好或任务上下文，再交给 LLM 做后续推理。

工程上最常见的两种召回方式：

- **全文搜索**：基于 BM25 或数据库 FTS（如 SQLite FTS5、PostgreSQL tsvector），做关键词匹配。
- **语义搜索**：用 embedding 模型把记忆片段和查询编码成向量，再按余弦相似度检索。

一开始我也以为语义搜索是“银弹”，但实际跑了几周测试，发现问题没那么简单。

## 问题

全文搜索的优点是精确、快、可解释。用户问“上周那个 OAuth 报错怎么解决的”，如果记忆里有完全匹配的“OAuth 报错”关键词，FTS 能直接命中。但缺点也很明显：换个说法“认证失败那个错”就召回不到。

语义搜索恰好补上这个短板，它能理解“登录不上”“认证失败”“unauthorized error”之间的语义关联。但它也有硬伤：

- 对专有名词、ID、代码片段、路径等精确字符串，向量相似度经常瞎匹配。
- 中文 embedding 模型选错，效果急剧下降。
- 相似度分数高不代表真的相关，容易把噪声塞给 LLM。

单独用任何一种，召回质量都不稳定。

## 做法/步骤

我在 OpenClaw 的 memory 模块里做了混合召回。思路是两条路径并行召回，再用 RRF（Reciprocal Rank Fusion）融合，最后交给 LLM 或轻量重排模型裁剪。

### 1. 存储阶段

记忆片段写入时，同时做两件事：

- 全文索引：把原始文本写入 SQLite FTS5 表，使用 trigram 分词以支持中文。
- 向量索引：用 `bge-small-zh-v1.5` 生成 embedding，写入本地向量库（如 Chroma 或 Qdrant）。

```yaml
memory:
  recall:
    strategy: hybrid
    fulltext:
      engine: sqlite_fts5
      tokenizer: trigram
      top_k: 20
    vector:
      model: bge-small-zh-v1.5
      top_k: 20
    fusion: rrf
    rerank:
      model: bge-reranker-base
      top_n: 5
```

### 2. 召回阶段

查询进来后，分别执行：

- 全文搜索：对查询做同样的分词，跑 FTS，取 top 20。
- 语义搜索：将查询编码为向量，取 top 20。

然后做 RRF 融合。RRF 的直觉是：一个文档在多个排序列表里排名越靠前，最终得分越高。公式：

```
score(d) = Σ 1 / (k + rank_i(d))
```

`k` 一般取 60。最后把融合后的 top 8～10 条送到重排模型，只保留 top 3～5 条作为最终上下文。

### 3. 空结果兜底

如果两条路径都返回空或得分极低，不要硬塞无关内容。给 LLM 一个明确的空记忆信号：

```
[memory_recall] no relevant memory found.
```

这比给一堆噪声更安全。

## 踩坑点

1. **中文分词坑**  
   SQLite FTS5 默认 unicode61 分词对中文不友好，基本把整句当成一个 token。必须用 trigram 或接入 jieba 分词。否则全文搜索形同虚设。

2. **embedding 模型语种不匹配**  
   用英文模型编码中文，向量检索基本失效。我试过 `all-MiniLM-L6-v2` 跑中文记忆，召回率不到 40%。换 `bge-small-zh-v1.5` 后提升到 80% 以上。

3. **元数据过滤顺序**  
   如果记忆带元数据（用户 ID、会话 ID、时间范围等），一定要在向量搜索前先过滤向量库，或者使用带过滤条件的查询。否则语义搜索会把其他用户的相似内容也捞出来，轻则污染上下文，重则泄露隐私。

4. **相似度分数不可靠**  
   向量搜索返回的相似度是相对值，不能跨查询比较。比如“今天吃什么”和“昨天登录报错”的相似度可能是 0.85，而“OAuth 报错”和“认证失败”只有 0.78。所以不要硬设阈值，用 RRF + 重排更稳。

5. **chunk 大小影响召回质量**  
   记忆片段切得太长（比如 2000 token），embedding 会稀释关键语义；切得太短又丢失上下文。我目前用 200～500 token 作为记忆片段长度，效果最好。

6. **延迟和成本**  
   每次写入调 embedding 模型有成本，尤其记忆频繁更新时。可以批量生成 embedding，或在本地缓存已编码的片段。查询侧的语义搜索也要控制 top_k，避免过大的重排开销。

## 可复用建议

- **先跑全文搜索基线**。很多精确匹配场景（报错码、文件名、用户原话）用 FTS 就够了。加语义搜索前，先记录 FTS 的 recall@5/10。
- **建立一个 50～100 条真实查询的小型评估集**，标注相关记忆 id。每次改 chunk 大小、换 embedding 模型、调融合参数，都跑一遍召回率。
- **RRF 的 k 值不用过度调**，60 是通用值，很多实现默认这个值，效果稳定。
- **重排只处理候选 top 10 以内**，LLM 直接看原始片段比只看相似度分数更可靠。如果资源紧张，可以用 `bge-reranker-base` 这类轻量模型。
- **记忆内容敏感时，优先本地 embedding 模型和本地向量库**。不要为了省事把用户记忆丢给外部 API。
- **保留原文**。全文搜索需要原始文本，向量检索也需要原文作为最终展示；只存向量会导致无法做 FTS 和人工排查。

## 总结

没有哪个单一方案能通吃 memory_recall。全文搜索擅长精确匹配，语义搜索擅长模糊关联。工程上最务实的做法是混合召回 + RRF 融合 + 轻量重排，再配合元数据过滤和空结果兜底。

如果你正在用 OpenClaw 做记忆召回，不妨先从 FTS 基线开始，逐步引入向量检索。别一上来就上语义搜索，那样你会被“高相似度但完全无关”的结果折磨到怀疑人生。
