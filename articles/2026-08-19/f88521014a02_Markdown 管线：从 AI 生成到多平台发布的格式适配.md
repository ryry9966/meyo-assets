## 背景

在 OpenClaw / Agent / MCP 的自动化发布链路里，Markdown 常被当成“万能中间格式”：AI 生成 Markdown，插件或脚本再推到 GitHub、知乎、公众号、Notion、Mastodon 等平台。但实际上 Markdown 并不是严格标准，每个平台支持的语法子集都不一样。更麻烦的是，AI 生成的内容经常混用 GFM、Obsidian、LaTeX、Mermaid、脚注、相对路径图片等扩展语法，直接发布很容易出现渲染失败、内容丢失或排版错乱。

与其在 prompt 里反复强调“不要用表格”“不要用公式”，不如在生成和发布之间加一条可复用的 Markdown 管线，把不可控的 AI 输出约束到可移植子集，再按平台做适配。

## 问题

多平台差异通常集中在这些点：

- GitHub / MkDocs 对 GFM 表格、代码块、脚注支持较好；
- 知乎对 Markdown 支持有限，表格、脚注、部分行内 HTML 会被过滤；
- 微信公众号不支持原始 Markdown，需要转 HTML 并上传图片素材；
- Notion 需要转成 Blocks API，对表格、公式有自己的结构；
- Mastodon / Discord 有长度限制，复杂元素需要降级或摘要。

AI 生成侧的问题则更隐蔽：frontmatter 字段不一致、列表缩进混用空格和 Tab、代码块漏语言标注、图片用本地相对路径、公式有时用 `$...$` 有时用 `$$...$$`。这些细节单靠 prompt 修正不稳定，必须用工程化手段兜底。

## 做法 / 步骤

### 1. 定义可移植 Markdown 子集

先给源稿定一个“安全子集”，只允许：

- 标题、段落、有序/无序列表、加粗、斜体、行内代码；
- 代码块，且强制语言标注；
- 链接、图片（必须绝对 URL）；
- 引用、简单表格（可选）。

禁止或降级：脚注、LaTeX、Mermaid、内嵌 HTML、iframe、高亮语法。这样后续适配器不用面对无限种输入。

### 2. 管道结构

把处理链路拆成独立阶段：

```text
Agent 输出 → 语法规范化 → frontmatter 抽取 → 平台适配器 → dry-run 预览 → 发布
```

每个阶段只做一件事，方便单独测试和替换。

### 3. 规范化规则示例

- 统一换行为 `\n`，避免 CRLF 混用；
- 列表缩进统一为 2 或 4 空格，禁止 Tab；
- 代码块没有语言标注时自动补 `text`；
- 相对路径图片转换成 CDN 绝对地址；
- LaTeX 公式降级为纯文本或转图片；
- Mermaid 图转为图片或保留代码块，由适配器决定。

### 4. 平台适配器

适配器按目标平台处理差异：

- **GitHub / MkDocs**：基本保留，校验图片 alt 和链接；
- **知乎**：表格转 HTML 或图片，脚注转成括号注释；
- **公众号**：Markdown 转 HTML，内联样式，上传图片到素材库并替换 URL；
- **Notion**：转成 Blocks API，注意列表嵌套和公式包裹；
- **Mastodon / Discord**：按长度截断，去掉表格、代码块等复杂元素，保留摘要。

### 5. 挂到 OpenClaw / MCP

把整条管线封装成 MCP server，对外提供 `convert`、`preview`、`publish` 三个工具。发布节点先调 `convert` 得到平台专用产物，再走各平台 API。这样 Agent 只负责生成内容，格式适配完全交给管线。

## 踩坑点

- **公众号图片防盗链**：外链图片在公众号里会显示失败。必须上传到微信素材库，再替换成返回的 URL。适配器要做成异步上传并重试。
- **表格在移动端过宽**：公众号和知乎移动端表格容易溢出。建议限制列数，超过则转成图片。
- **脚注不兼容**：多数内容平台不支持原生脚注，转换时要把脚注内容合并到文末“附注”或括号内。
- **公式渲染**：公众号不支持 LaTeX，需要转图片或用 Unicode 近似；Notion 需要 `$$` 包裹，且不能混用行内公式。
- **代码块转 HTML**：公众号转换时用 `<pre><code>`，不要用 `<p>` 加 `<br>`，否则空格和换行会丢失。
- **相对路径图片 404**：AI 生成时经常给出本地路径如 `![](./image.png)`。管线必须拦截并替换为绝对 URL，否则发布后全是坏图。
- **frontmatter 解析容错**：模型可能输出 YAML、JSON，或者干脆漏掉。解析器要做容错和默认值，不要让整个流程崩溃。

## 可复用建议

维护一张平台能力矩阵，标明每个平台对表格、公式、脚注、代码块、Mermaid 的支持程度和降级方式。适配器做成可插拔模块，不要写死 if-else。保留原始 Markdown 源稿，发布产物只是衍生品，方便回退和重发。CI 里加 `markdownlint` 或类似 linter，提前发现缩进、换行、链接问题。日志里记录转换前后的 diff，方便快速定位平台渲染异常是哪一步引入的。

## 总结

Markdown 管线的核心不是“再写一个转换器”，而是把 AI 生成的不确定性关进一个可控范围：先约束到可移植子集，再用适配器做平台级降级。把这套逻辑做成独立服务或 MCP 工具，比在 prompt 里反复强调格式更可靠，也更便于复用和排查。
