## 背景

在 OpenClaw 里同时接入 GPT 和本地模型之后，很容易走两个极端：要么所有请求都走 GPT，成本高、延迟大，敏感数据还容易出域；要么全部压给本地模型，复杂任务频繁失败，工具调用输出一堆不合法 JSON。

我自己在 OpenClaw 中同时挂了一个云端 GPT 端点和一个本地 Ollama 端点。经过一段时间的 Agent 和 MCP 工具联调，发现“哪个模型更强”并不是核心问题，真正影响稳定性的是：你有没有把合适任务放到合适执行环境里。

## 问题

多模型并存后，系统不会自动判断任务难度。Agent 的典型工作负载里，有些任务非常简单：

- 摘要、改写、意图分类
- 结构化字段抽取
- 日志异常初筛
- 代码补全草稿

这些任务用本地 7B/14B 模型通常够用，且成本低、数据不出本机。

但另一些任务必须交给 GPT 或更强的云端模型：

- 多步工具编排与规划
- 长上下文问答
- 复杂 JSON 输出与函数调用
- 需要强推理的排障或代码调试

如果没有路由，简单任务也会占用云端额度，复杂任务又可能被本地模型的上下文窗口和推理能力拖垮。

## 做法/步骤

### 1. 配置两个模型端点

在 OpenClaw 中，我把云端模型配置为 GPT 系列，本地模型通过 Ollama 暴露 `/v1` 兼容接口。命名上区分清楚：

```text
gpt-4o-mini
local/qwen2.5:14b
local/llama3.1:8b
```

避免在 Agent 里直接写死模型名，后续切换会很难。

### 2. 增加一个轻量路由层

可以在 MCP 工具入口或插件前置逻辑里放一个 `route_task` 函数。它不负责推理，只做规则判断，输入是任务描述、上下文长度、数据敏感标记，输出是目标模型名。

我目前使用的规则大致如下：

```text
summary / classify / extract / rewrite / code_completion -> local
plan / debug / multi-step-tool / long-context-qa       -> gpt
包含 PII / internal / secret                           -> local
上下文长度超过本地模型窗口 80%                        -> gpt
包含“规划 / 下一步 / 根据结果再调用”等复合指令      -> gpt
```

规则不需要很复杂，先解决 80% 的明显分流问题。

### 3. 本地先跑，失败升级

对于中等难度任务，我会先让本地模型执行，再做输出校验。校验项包括：

- JSON 是否能解析
- 工具调用参数是否完整
- 是否缺少必要字段
- 输出是否包含无关解释

如果校验失败，自动升级到 GPT 重试一次。这个“本地先跑 + 失败升级”的策略，比一开始就上 GPT 要省很多。

### 4. GPT 限流或异常时降级

云端模型也可能超时、限流或返回错误。对于低风险任务，可以降级到本地模型，并在结果里标记：

```text
degraded: true
```

这样调用方知道这次输出可能质量下降，后续可以决定是否重试或人工确认。

## 踩坑点

### 本地模型工具调用不稳定

这是最常见的坑。很多本地模型会输出类似：

```text
好的，我来帮你查询天气。
{"tool": "weather", "city": "Beijing"}
```

前面多了解释文字，导致 JSON 解析失败。解决方法是：

- Prompt 里强制“只输出 JSON，不要解释”
- 解析时截取第一个 `{` 到最后一个 `}`
- 用 JSON Schema 约束输出格式

### 本地模型上下文窗口不够

长会议记录、长代码文件、多轮工具结果汇总，很容易撑爆本地模型窗口。解决方法是先切块再送本地，或者直接路由到 GPT。不要硬塞，否则漏信息比慢更可怕。

### 路由规则误判

仅靠关键词容易把混合任务分错。例如：

```text
“帮我总结这段日志，并给出下一步排查建议”
```

这里面既有“总结”也有“排查建议”。如果只匹配“总结”，就会错误走本地。规则里要增加“是否包含复合指令”“是否需要工具调用”的判断。

### 模型选择被全局状态污染

不要把当前模型名存在全局变量里。多个 Agent 并发时，会互相覆盖配置。每次请求都应显式传递模型名，路由函数返回后立即生效。

### 本地模型冷启动慢

Ollama 首次加载模型可能耗时 5-15 秒。如果每次任务都冷启动，延迟会很差。建议在服务启动时预热模型，或让本地模型常驻内存。

## 可复用建议

1. **先统计再定规则**：跑一周日志，统计任务类型分布、平均上下文长度、失败率，再定阈值，不要拍脑袋。
2. **路由规则外部化**：把规则抽成 YAML/JSON 配置，而不是硬编码在插件里。后续调整不用改代码。
3. **关键任务强制成功**：对重要任务设置 `must_succeed` 标志，失败时优先 GPT 重试，而不是直接返回本地结果。
4. **记录路由元数据**：每次记录命中模型、是否升级、是否降级、耗时、成本。没有这些数据，调优就是盲调。
5. **固定本地模型版本和 Prompt**：本地模型升级后行为可能漂移，固定版本、量化参数和 Prompt 模板，保证可复现。

## 总结

多模型路由的本质不是“哪个模型更好”，而是把合适任务放到合适执行环境里。我的经验是：先用简单规则做粗分流，再用“本地先跑 + 校验升级 + 云端降级”做兜底。这样既不会因为省成本而牺牲稳定性，也不会因为无脑上 GPT 而浪费资源。

对 OpenClaw 用户来说，路由层完全可以做成一个普通插件或 MCP 前置逻辑，不需要重框架级改动。先把简单规则跑起来，比一开始就设计复杂路由要可靠得多。
