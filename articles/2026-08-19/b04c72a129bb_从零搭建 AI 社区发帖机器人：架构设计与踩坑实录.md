## 背景

我维护一个 OpenClaw 相关技术社区，需要定期发布实践、答疑和更新公告。纯人工撰写耗时且容易断更，所以我们尝试用 Agent 自动生成并发布帖子。目标不是“全自动灌水”，而是把重复劳动压缩到“人工审核一步”。

这个项目本质上是一条“生成—审核—发布”流水线：LLM 负责选题和正文，OpenClaw 负责流程调度，MCP server 负责社区接口抽象，SQLite 记录状态。

## 架构设计

整体分四层：

1. **触发层**：cron 或手动触发，每天最多跑 1–2 次。
2. **Agent 调度层**：OpenClaw 负责调用工具、处理重试、维护任务状态。
3. **能力层**：MCP server 暴露社区接口，例如 `create_draft`、`list_drafts`、`publish_draft`、`check_login`、`fetch_trending`。
4. **存储层**：SQLite 保存任务记录、草稿、历史指纹和发布结果。

核心流程如下：

```text
定时触发
  -> 读取话题池与历史指纹
  -> LLM 生成标题和正文
  -> create_draft 写入社区草稿箱
  -> 通知人工审核
  -> 人工确认或修改
  -> publish_draft 发布
  -> 记录结果并更新指纹
```

MCP 工具统一返回 JSON：

```json
{ "ok": true, "data": {}, "error": null, "code": 0 }
```

这样做是为了避免 LLM 从自然语言里猜测失败原因。发布工具默认 `require_confirm=true`，不提供“直接发布”的快捷路径。

## 内容生成与防重

避免机器人重复发帖，我们维护了一个话题池，并对每条帖子计算“标题 + 正文”哈希。生成前会检查 hash 是否已存在，存在则换话题重新生成，最多尝试 3 次。

Prompt 里做了硬约束：

- 禁止生成任何外链，非白名单域名直接删掉；
- 标题不超过 40 字；
- 只使用社区编辑器支持的 Markdown 子集；
- 不编造数据、不引用不存在的公告。

## 踩坑点

### 1. 登录态失效

社区 Cookie/Token 有效期短，Agent 经常在发布时才报登录失败。后来我们在每个任务开始前先调用 `check_login`，失效就走刷新逻辑或直接告警。不要试图用截图识别验证码，优先找 API；如果只有网页，建议用插件模式把登录流程独立出来。

### 2. Markdown 渲染差异

LLM 生成的 Markdown 经常包含表格、HTML、脚注或嵌套列表，社区编辑器不支持。解决方法是生成后过一遍 sanitizer，只保留标题、列表、代码块、链接、加粗，其余内容降级为普通段落。

### 3. 限流与风控

发布接口有频率限制，连续发帖很容易触发风控。我们默认每 6 小时最多生成 1 条草稿，遇到 429 做指数退避，避免在任务里循环重试导致更严重的封禁。

### 4. LLM 幻觉链接

模型会“自然地”编造官方文档或 GitHub 链接。即使 prompt 禁止，仍可能偶尔出现。我们在 MCP 层做了链接白名单过滤，非白名单域名直接删除，而不是依赖模型自觉。

### 5. MCP 工具返回不稳定

网页解析路径或字段变更会导致工具返回裸 HTML 或缺失字段。后来要求 MCP server 返回前校验关键字段，缺字段就返回 `ok=false` 和明确错误码，不要把裸 HTML 交给 LLM。

### 6. 上下文爆炸

如果为了“参考社区趋势”把整站 trending 都塞给 LLM，上下文会迅速膨胀，生成速度变慢且输出漂移。现在只取前 10 条标题摘要，并限制历史消息轮数。

## 可复用建议

- **先草稿，后发布**：人工确认是底线，不要一开始就全自动。
- **状态落库**：每个任务有 `task_id`，状态包括 `pending/generating/draft/published/failed`，失败可重跑。
- **统一工具返回 schema**：减少 LLM 误判，排障更简单。
- **记录工具调用日志**：保存入参、返回码、耗时，失败时保留完整草稿。
- **小步迭代**：先只跑 1 个版块、每周 2 条，稳定后再扩大范围。

## 总结

这个机器人的难点不在模型能力，而在平台接入、格式约束和状态管理。OpenClaw + MCP 的价值是把社区接口抽象成工具，让 Agent 更关注流程调度；但真正的工程重点，应该放在错误处理、可观测性和生成约束上。

它没有完全替代人工，但确实把“从零写一篇帖子的时间”压缩到了“花两分钟审核一个草稿”。
