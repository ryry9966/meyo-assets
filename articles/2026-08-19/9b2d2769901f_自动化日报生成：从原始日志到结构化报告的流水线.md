## 背景

日报的价值不在于“写”，而在于从原始日志里提取出今天到底发生了什么。我们团队之前每天要整理 Git commits、CI 失败、监控告警、项目群消息，人工耗时 30–40 分钟，而且口径经常不一致。

后来尝试直接把日志丢给大模型生成日报，结果出现几类典型问题：上下文超长截断、日期错乱、事件重复、来源无法溯源。最终我们换成分层流水线：用 OpenClaw 做编排，通过 MCP/插件拉取日志，Agent 只负责语义提取，脚本负责清洗、聚合和渲染。跑了几周后，人工只做最后确认。

## 问题拆解

原始日志不适合直接生成报告，主要有三个原因：

1. **来源分散**：Git、CI、监控、IM 各有格式，时间口径也不一致。
2. **噪音过大**：心跳日志、自动评论、重复通知会干扰模型判断。
3. **生成不稳定**：自由生成容易漏事件、编事件，格式也时好时坏。

因此，核心思路不是“让 Agent 更聪明”，而是把问题拆小，让每一步可验证。

## 做法：五段式流水线

### 1. 采集层：只拉近 24 小时窗口

用 MCP server 或插件连接 GitLab/GitHub、Drone/Jenkins、监控 Webhook、IM 导出接口。按时间窗增量拉取，避免一次拿全量。

关键点：每个事件都要带稳定唯一 ID，例如 commit hash、pipeline id、alert id。后续去重和溯源都靠它。

### 2. 清洗与切分：先降噪，再截断

对原始日志做基础清洗：

- 去除自动评论、心跳、重复通知；
- 脱敏 IP、手机号、内部 hostname；
- 统一时间为 ISO 8601，并标注时区 offset；
- 单条日志超过 2000 字符就截断，但保留原始链接。

这一步不需要模型参与，用脚本或 Agent 的确定性工具完成即可。

### 3. 语义提取：固定 schema，分批送入

将清洗后的日志分批送入 Agent，每批 8–15 条。要求只输出 JSON，不输出解释。schema 固定为：

```json
{
  "source": "git | ci | alarm | im",
  "event_type": "feat | fix | deploy | ops | incident | discussion",
  "title": "...",
  "summary": "...",
  "related_ids": ["..."],
  "risk": 0
}
```

低温度运行，并要求不要用 Markdown 代码块包裹 JSON。如果模型仍输出包裹，可以用 json repair 做一次兜底。

### 4. 聚合与去重：先脚本，后模型

提取完成后，先用脚本按 `source + related_ids` 做去重，再按项目/事件类型分组。异常类事件优先排序，部署类事件按时间顺序排列。

只有分组后的内容需要生成摘要时，才让 Agent 再做一轮简短概括。不要把聚合逻辑完全交给模型，脚本能解决的问题不要消耗 token。

### 5. 渲染与投递

用固定 Markdown 模板渲染日报。格式建议包含：

- 今日概览；
- 按项目分组的变更与进展；
- 故障/风险项；
- 未确认或冲突事件。

每条摘要后保留原始链接或 ID。最后推送 IM 或邮件时，只发渲染结果，不带中间 JSON。

## 踩坑点

- **上下文超限**：不要一次投喂全量日志。先估算 token，控制在模型窗口的 60% 以内，宁可多分批。
- **JSON 不稳定**：固定 schema、降低温度、要求纯 JSON 输出。必要时做 json repair，不要假设模型一定听话。
- **时区错乱**：日志可能 UTC，日报窗口按本地时区。统一转 ISO 8601 并标注 offset，否则晚上 23 点的事件会漂到第二天。
- **幻觉与漏报**：要求每个事件必须附 source id；对无有效内容的批次允许返回空数组，避免模型为了填内容而编造。
- **重复生成**：增量运行建议用状态文件或数据库记录上次抓取游标，不要每次全量重跑。
- **工具权限收窄**：MCP server 只授予读权限，避免 Agent 误触发操作类接口。

## 可复用建议

- 把流水线拆成独立命令或工具：`collect`、`clean`、`extract`、`aggregate`、`render`，单独可测。
- 提取阶段先跑 50 条样本，人工校准 schema 和阈值，再全量运行。
- 保留中间 JSON 文件。出问题时，你能立刻判断是哪一层坏了，而不是重跑整条链路。
- 日报末尾增加“未确认项”。低置信度事件、来源冲突的事件单独列出，由人工判断。
- 渲染模板与提取逻辑分离。以后换报告格式、接新推送渠道时，不需要重做提取。

## 总结

从原始日志到结构化日报，难点不在“生成”，而在稳定。分层处理、固定 schema、保留溯源、增量游标，这些工程化手段比换更强模型更有效。

OpenClaw / Agent / MCP 适合做这类流水线，但不要让单个 Agent 承担全部智能。每层职责单一，中间结果可查，日报才能从“偶尔可用的 demo”变成“每天可靠地跑”。
