## 背景

OpenClaw 把 Agent、MCP 工具、插件和自动化流程串起来之后，模型选择会直接影响稳定性、成本和响应速度。很多人在配置里只填一个 GPT 模型，简单省事，但很快会遇到三类问题：

- 高频简单任务消耗大量 token，成本上升；
- 涉及本地笔记、密钥、内部文件时，数据外发带来隐私顾虑；
- 某些离线或低延迟场景，云端模型响应不够快。

反过来，如果全部切到本地模型，复杂推理、代码生成、长文档理解又经常掉链子。于是问题变成：**不是 GPT 和本地模型谁更好，而是什么任务该交给谁。**

## 问题

OpenClaw 本身不会自动帮你做这个判断。常见的错误做法有两种：

1. 用一套固定提示词让模型自己判断“你行不行”，结果模型经常高估自己，或者把简单任务也往复杂模型上送；
2. 规则写得太粗，比如所有工具调用都走本地模型，结果本地模型的 function calling 输出不稳定，整个 Agent 流程中断。

工程化的做法是把路由规则建立在**可观测信号**上，而不是靠模型临时判断。

## 做法 / 步骤

我在 OpenClaw 的配置中采用两级路由：先按任务特征选模型，再做失败回退。

### 1. 建立任务分类信号

不依赖模型输出，而是看这些字段：

- 触发来源：哪个插件、MCP 工具或自动化规则；
- 数据源：是否读取本地文件、环境变量、私有笔记；
- 上下文长度：token 估算值；
- 用户指令特征：是否包含“写脚本”“分析”“规划”等强推理词；
- 是否需要工具调用。

这些信息在 OpenClaw 的请求上下文中通常都能拿到，适合作为路由条件。

### 2. 设计路由表

示例配置：

```yaml
model_routes:
  - id: local-first
    match:
      data_sources: ["local_notes", "env", "private_files"]
    model: local_qwen_14b

  - id: narrow-task
    match:
      intents: ["summarize", "extract_entities", "classify"]
      max_estimated_tokens: 2500
    model: local_qwen_14b

  - id: complex-task
    match:
      patterns: ["写一个.*脚本", "分析.*代码", "多步规划", "代码审查"]
    model: gpt-4.1

  - id: long-context
    match:
      min_estimated_tokens: 8000
    model: gpt-4.1
```

这里用的是“白名单式”路由：先满足本地条件的走本地，剩下的默认走 GPT，避免本地模型硬撑复杂任务。

### 3. 本地模型负责窄任务

适合交给本地模型的工作：

- 意图识别、实体抽取、情绪分类；
- 摘要、格式整理、关键词提取；
- 简单问答、memory 搜索；
- 不需要复杂工具调用的文本处理。

这些任务输入输出边界清晰，对推理深度要求不高，本地模型足以稳定处理。

### 4. GPT 负责复杂任务

适合继续走 GPT 的工作：

- 多步 Agent 规划；
- 代码生成、调试、代码库分析；
- 跨文档推理；
- 长上下文理解；
- 强 tool calling 稳定性要求高的场景。

这类任务的共同点是：一旦模型输出不可靠，整条链路会失败，人工修复成本比模型调用成本更高。

### 5. 做失败回退

本地模型不是永远可靠。我在路由层加了两个回退策略：

- 本地模型 JSON 解析失败或工具调用格式错误时，自动回退到 GPT 重试一次；
- GPT 超时或限流时，降级到本地模型执行只读操作，并明确告知用户结果可能不完整。

回退必须记录日志，否则出了问题无法定位是路由错误还是模型能力问题。

## 踩坑点

1. **本地模型 function calling 稳定性差**  
   不要让本地模型自由生成工具调用 JSON。尽量使用受限解码、JSON Schema 或预设工具名匹配。否则你会看到大量“差不多对但解析失败”的输出。

2. **上下文窗口不够**  
   很多本地模型只有 8k 或 32k 上下文。路由规则里一定要加 token 阈值，超过阈值直接走 GPT，不要赌本地模型能处理。

3. **路由规则越写越复杂**  
   一开始就上十几条规则，最后自己都说不清哪个请求走了哪条。建议先做 3 到 5 条核心规则，稳定后再逐步增加。

4. **忽略模型提示词差异**  
   同一个 system prompt 在 GPT 上表现很好，放到本地模型上可能完全失效。本地模型需要单独维护精简版提示词，避免过多角色设定和复杂指令。

5. **隐私边界被破坏**  
   如果先调用云端模型做预处理，再把结果交给本地模型，隐私保护就失效了。隐私敏感数据必须在入口处就锁定本地路由。

## 可复用建议

- **从两条规则开始**：涉及本地私有数据走本地模型；代码生成/多步规划走 GPT。先跑通，再细化。
- **记录路由日志**：每次请求记录 `model_used`、`route_reason`、`fallback_count`、`latency_ms`。没有日志，路由就是黑盒。
- **用 feature flag 控制**：路由策略变更不要直接改配置上线，用开关灰度验证。
- **定期看回退率**：如果某类任务本地回退率持续超过 20%，说明它不适合放在本地模型，要么优化提示词，要么直接改走 GPT。
- **本地模型也要升级**：本地模型不是一成不变。定期换新版本测试，尤其是在工具调用和 JSON 输出方面有明显改进的版本。

## 总结

OpenClaw 的多模型路由本质上是把“能力”和“成本/隐私/延迟”做分离。我的原则是：**本地模型处理窄、高频、隐私敏感的任务；GPT 处理难、长、需要稳定推理的任务。** 路由规则保持简单，依赖可观测信号，搭配强制回退和日志记录，才能真正稳定落地。

模型路由不是为了省 token 而省 token，而是让每类任务回到它最合适的执行环境里。
