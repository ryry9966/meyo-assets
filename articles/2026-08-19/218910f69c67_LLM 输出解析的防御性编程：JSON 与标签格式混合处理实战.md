## 背景：为什么 LLM 输出解析需要“防御性编程”

在 OpenClaw、Agent、MCP 以及各类自动化工作流里，我们经常让 LLM 直接返回结构化数据，最常见的是 JSON。理想情况下，模型应该输出：

```json
{"action": "search", "query": "OpenClaw MCP"}
```

但真实场景中，输出可能是：

```
好的，我已经为你处理。
```json
{"action": "search", "query": "OpenClaw MCP"}
```
```

或者：

```
<result>
{"action": "search", "query": "OpenClaw MCP"}
</result>
```

甚至还会出现：

```
Here is the output: <tool_call>{"action":"search","query":"OpenClaw MCP"}</tool_call> and some extra text.
```

如果你直接 `json.loads()`，大概率会抛出 `JSONDecodeError`，整个流水线中断。在 Agent 循环里，一次解析失败可能意味着一次工具调用丢失，或者需要重新生成回复，消耗 token 和时间。这就是为什么我们需要防御性解析：不是指望 LLM 每次都遵守格式，而是假设它会“不守规矩”，并做好容错。

## 问题：混合格式的典型形态

经过多次实际踩坑，我们把混合输出归纳为几类：

1. **Markdown 代码块包裹**：` ```json ... ``` ` 或 ` ``` ... ``` `
2. **自定义标签包裹**：`<json>...</json>`、`<result>...</result>`、`<tool_call>...</tool_call>` 等
3. **前缀/后缀文本**：解释性文字加 JSON 主体
4. **嵌套或半嵌套**：标签里有代码块，代码块里又有标签，或者多个 JSON 片段
5. **大小写和空白差异**：`<JSON>`、`< Json >`、标签前后多余空格换行
6. **JSON 内部包含看起来像标签的字符串**：例如 `{"text": "</result>"}`

直接写一个简单的正则去匹配第一个 `{` 到最后一个 `}` 是危险的，因为字符串中可能包含大括号，或者输出里有多个 JSON 对象。

## 做法/步骤：一个稳健的 `extract_json` 函数

核心思路：**逐层剥离，最后用 JSON 解析器兜底，而不是用正则提取大括号**。下面给出一个经过工程验证的解析流程，Python 示例。

```python
import json
import re
from typing import Any, Optional

def extract_json(text: str) -> Optional[Any]:
    if not text:
        return None

    # 1. 先尝试直接解析（最理想情况）
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass

    # 2. 去除首尾空白，并尝试剥离常见的 Markdown 代码块
    cleaned = text.strip()
    fenced_pattern = r"^```(?:json)?\s*(.*?)\s*```$"
    match = re.search(fenced_pattern, cleaned, flags=re.DOTALL | re.IGNORECASE)
    if match:
        try:
            return json.loads(match.group(1))
        except json.JSONDecodeError:
            pass

    # 3. 处理自定义标签：查找所有形如 <tag>...</tag> 的内容
    # 注意使用非贪婪匹配，并且允许标签名包含字母数字下划线
    tag_pattern = r"<([a-zA-Z_][\w-]*)>(.*?)</\1>"
    matches = re.findall(tag_pattern, cleaned, flags=re.DOTALL | re.IGNORECASE)
    for _, inner in matches:
        try:
            parsed = json.loads(inner.strip())
            return parsed
        except json.JSONDecodeError:
            continue

    # 4. 如果标签内还有代码块，或者内容被前缀文本干扰，尝试定位第一个 '{' 或 '['
    # 但要保证 JSON 字符串完整，这里用一个简单的括号平衡法
    json_start = min(
        [pos for pos in (cleaned.find('{'), cleaned.find('[')) if pos != -1],
        default=-1
    )
    if json_start != -1:
        # 用栈来匹配括号，防止字符串内干扰
        stack = []
        in_string = False
        escape = False
        for i in range(json_start, len(cleaned)):
            ch = cleaned[i]
            if in_string:
                if escape:
                    escape = False
                elif ch == '\\':
                    escape = True
                elif ch == '"':
                    in_string = False
            else:
                if ch == '"':
                    in_string = True
                elif ch in '{[':
                    stack.append(ch)
                elif ch in '}]':
                    if stack and ((ch == '}' and stack[-1] == '{') or (ch == ']' and stack[-1] == '[')):
                        stack.pop()
                        if not stack:
                            candidate = cleaned[json_start:i+1]
                            try:
                                return json.loads(candidate)
                            except json.JSONDecodeError:
                                break
                    else:
                        break

    # 5. 最后尝试处理被转义的情况，例如输出包含 \n 等
    try:
        # 有些 LLM 会把 JSON 转成带转义符的字符串
        unescaped = cleaned.encode().decode('unicode_escape')
        return json.loads(unescaped)
    except Exception:
        return None

    return None
```

这个函数并不是完美的正则魔法，而是按优先级尝试：直接解析 → 剥离代码块 → 提取标签内容 → 括号平衡截取 → 反转义。每一步失败后进入下一步，最终返回 `None` 而不是抛出异常，由调用方决定如何处理。

在实际 OpenClaw 场景中，你可以把它封装成一个 utility，然后在解析工具调用参数、MCP 返回结构化数据、插件配置文件生成等地方统一使用。

## 踩坑点：几个容易忽略的细节

1. **不要用 `text[text.find('{'):text.rfind('}')+1]` 这种粗鲁切片**。如果 JSON 中有字符串包含大括号，或者输出末尾有解释文字，会截断或包含多余内容。括号平衡法虽然复杂一点，但能处理嵌套。

2. **标签匹配要允许属性或命名空间**。有些模型会输出 `<tool_call name="xxx">`，上文的标签正则只匹配无属性的简单标签。如果有属性，需要扩展正则或先去掉属性部分。

3. **多段 JSON 或 JSON 数组外的对象**。如果 LLM 输出 `[{...}, {...}]` 外面套了标签，或者输出两个独立 JSON，函数只会返回第一个合法 JSON。这通常符合预期，但要清楚行为，不要误以为解析了全部。

4. **大小写和空白**。标签名大小写不敏感，但正则里用了 `IGNORECASE`；代码块标记 ` ```json ` 有时写 ` ```JSON `，也做了忽略大小写处理。但 ` ``` ` 后面可能有空格，例如 ` ``` json `，建议在剥离时用更宽松的匹配。

5. **`unicode_escape` 是双刃剑**。如果 JSON 里本身包含 `\n` 作为换行转义，`unicode_escape` 会正确解码；但如果原始输出里包含了非 ASCII 字符或已经解码过的内容，再解码可能产生乱码或异常。这一步建议放到最后，并且一定要捕获异常。

6. **性能问题**。在 Agent 循环里频繁调用时，应缓存编译后的正则，或者限制文本长度，避免恶意超长输出拖慢系统。

## 可复用建议

- **统一出口**：在 OpenClaw 项目中，所有需要解析 LLM 结构化输出的地方都调用同一个 `extract_json`，不要散落各处的临时正则。
- **失败时的降级策略**：如果解析失败，不要直接崩溃。可以返回一个默认值、记录日志、触发重试，或者让 LLM 重新生成。在 Agent 里，可以设计一个“修复提示词”，把原始输出和错误信息发给模型让它修正。
- **日志记录原始输出**：解析失败时，完整保存原始文本，方便事后分析模型行为，改进提示词。
- **结合提示词约束**：防御性解析不是万能药，最好在提示词中明确要求“只输出 JSON，不要任何解释或标签”。但即便这样，仍然要做防御性解析，因为大模型有随机性。
- **测试用例**：为 `extract_json` 写单元测试，覆盖上述所有混合形态，包括嵌套、转义、多标签、字符串内大括号等，确保修改正则时不会引入回归。

## 总结

在 OpenClaw/Agent/MCP 生态里，LLM 输出解析的健壮性直接影响自动化流程的稳定性。混合 JSON 和标签格式是最常见的坑，但通过“逐层剥离 + 括号平衡 + 兜底解析”的防御性编程思路，可以大幅降低失败率。核心不是写出一个超级正则，而是承认模型输出不可控，用工程手段逐步降级，把不确定性消化在解析层。希望这个 `extract_json` 的思路和踩坑点，能帮你在自己的自动化项目里少走一些弯路。
