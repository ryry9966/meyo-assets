## 背景

在 OpenClaw 里跑自动化时，单个 Agent 处理复杂任务常见问题：上下文越来越长、工具调用串行等待、一旦某步失败整个链路重来。尤其涉及多源抓取、多文件分析、多接口校验时，单 Agent 容易在第三步就开始遗忘约束，或者把不同粒度的任务混在一起。

一个更可控的做法是引入 subagent 编排：主 Agent 只负责规划、派发和汇总，具体执行交给多个子 Agent 并行处理。

## 问题

并行不是简单把 prompt 复制几份同时跑。需要明确：

- 哪些任务可以并行，哪些有依赖；
- 子 Agent 之间如何交换数据；
- 如何限制子 Agent 的行为，避免工具滥用和 token 爆炸；
- 结果如何合并、校验，失败如何隔离。

## 做法/步骤

### 1. 主控与子 Agent 分层

在 OpenClaw 里定义一个主控 Agent（orchestrator），它不直接操作具体工具，只做三件事：拆任务、发任务、收结果。子 Agent 只拿单一目标和明确输入，例如“读取这三个 URL，提取正文和发布时间，返回 JSON”。

### 2. 任务拆成 DAG

先把流程画成有向无环图。比如一个报告生成任务可拆成：

- 抓取新闻列表（A）
- 抓取详情页（B1/B2/B3，依赖 A 的结果）
- 汇总去重（C，依赖 B 系列）
- 输出 Markdown（D，依赖 C）

B1、B2、B3 可以并行。不要在主 Agent 里直接循环调用，而是用任务队列派发，每个子 Agent 拥有独立上下文。

### 3. 子 Agent 返回结构化结果

每个子 Agent 的 system prompt 里固定输出 schema，例如：

```json
{
  "status": "ok",
  "data": {},
  "errors": []
}
```

主控收到后用 JSON Schema 校验，不合格的返回一次修正指令。这样避免自由文本导致合并困难。

### 4. 工具权限做减法

子 Agent 只挂载完成任务必需的工具。对于 OpenClaw/MCP 环境，优先给子 Agent 只读工具（如 fetch、read_file、search），写操作统一由主控完成。这样能避免多个子 Agent 同时写同一文件或同一数据库记录。

### 5. 并发控制与超时

用信号量限制同时运行的子 Agent 数量，例如最多 4 个。每个子 Agent 设置 max_steps 和 max_tokens，以及 wall-clock 超时。超时或步数耗尽时，返回结构化错误，而不是让主控无限等待。

## 踩坑点

- **输出格式漂移**：子 Agent 有时会输出“好的，我已经完成……”这种自然语言，或者把 JSON 包在 Markdown 代码块里。需要解析层做兼容，并且 prompt 里强调“只输出 JSON，不要解释”。
- **并行写冲突**：两个子 Agent 同时写同一个 collection 或文件，后写覆盖先写。解决方法是把写操作收归主控，或者给每个子 Agent 分配独立输出路径，最后统一合并。
- **工具限流**：并行请求过多会触发上游 API 限流。建议在子 Agent 内部对高频工具调用做退避重试，或降低并发度。
- **成本估算错误**：子 Agent 独立上下文导致 token 消耗比串行更高。需要提前估算：串行总 token vs 并行总 token，有时小任务并行反而更贵。
- **子 Agent 递归失控**：如果子 Agent 还能再派发子 Agent，容易形成多层嵌套。第一版建议只做一层 subagent，递归派发留到稳定后再开放。

## 可复用建议

- 把子 Agent 模板化：角色、输入、输出 schema、可用工具、终止条件。
- 主控只做编排，不替子 Agent 做具体推理。
- 记录每次子任务执行的 trace：输入哈希、耗时、token、输出状态。这样排障时不用翻完整日志。
- 失败隔离：单个子 Agent 失败不应终止整个流程，主控可以重试一次，仍失败则用占位结果继续，最后统一标记。
- 先在低风险任务上验证并行收益，再逐步提高并发度。

## 总结

Subagent 编排的价值不在于“同时跑多个 AI”本身，而在于把复杂任务切成边界清晰、失败可隔离、结果可校验的执行单元。OpenClaw/MCP 环境下，好的编排是：主控做规划与收敛，子 Agent 做单一目标执行，工具权限最小化，输出结构化，并发可控。这样一套下来，复杂自动化不再是一团乱麻，而是可复用的流水线。
