“涨价是DeepSeek的原罪？”这个话题最近在开发者圈里炸开了。不少人第一反应是：说好的极致性价比呢？怎么模型还没捂热，价格先动了。但把“涨价”简单等同于“作恶”，很容易错过真正重要的东西：AI API 的定价正在从补贴期进入成本校准期。这篇文章不站队，只拆账。



## 一、“涨价”不是一张价目表，而是一套计价规则

很多人看到“涨价”，以为只是每个token单价上调。实际DeepSeek这类API的价格由多个维度组成，不同用户感受到的涨幅可能完全不一样。

- **输入 token**：分缓存命中（cache hit）和未命中（cache miss）。命中时系统直接复用已缓存的 Key/Value 状态，成本低；未命中则要重新计算。
- **输出 token**：通常定价更高，因为生成阶段是逐 token 解码，访存和算力压力大于输入。
- **错峰折扣 / Batch API**：非实时、低优先级任务往往有折扣，高峰时段或者在线推理则要按标准价。
- **免费额度与速率限制**：部分开发者感受到“变贵”，可能不是单价上调，而是免费额度缩减或并发限制变化。

举例：一个客服机器人，system prompt 有 2000 token，用户问题 200 token，模型回答 600 token。如果 system prompt 能长期缓存命中，成本主要来自输出；如果每次都没命中，输入成本会高出数倍。所谓“涨价”，在很多场景下其实是“缓存未命中价格上调”。这更像把计价颗粒度变细，而不是无差别提价。

## 二、为什么“白菜价”一定走不远？

这里要算三笔账：显存账、电力账、研发账。



- **显存账**：Transformer 推理时，KV cache 会随序列长度线性增长。长上下文请求不是“读更多字”那么简单，而是要占用大量显存带宽。HBM 带宽有限，高并发长上下文会让成本急剧上升。以 7B 模型为例，单请求长上下文可能占用数 GB 显存，并发一高，显存瓶颈立刻显现。
- **电力账**：GPU 满载功耗不是小数目，数据中心还需要制冷、配电、网络。单位 token 能耗虽然持续优化，但在规模扩大时，电费不会被营销口号抹掉。
- **研发账**：模型从训练、对齐、红队测试到持续更新，都需要摊入 API 价格。低价可以拉新，但若长期低于边际成本，服务质量和迭代速度必然下降。

早期“白菜价”更像互联网补贴：先让开发者用起来、形成生态、收集真实负载。但 AI 推理不是纯软件分发——每多一次调用，都有真实的硬件和电力消耗。边际成本不为零，补贴就注定有终点。把促销价当成永恒低价，是一种危险的会计错觉。

再做一道简单的算术：假设输入每百万 token 2 元，输出每百万 token 8 元，一次任务输入 3000 token、输出 500 token，单次成本约 0.01 元。看起来很低，但如果日调用量达到一亿次，单日成本就是 100 万元级别。对于规模化的 AI 服务来说，任何单价微调都会被调用量放大成巨大的现金流变化。

## 三、定价趋势：从“统一价”走向“分层计价”

涨价背后，更值得关注的是计价方式的结构性变化。

1. **缓存分层**：cache hit 和 cache miss 分开定价，鼓励开发者把 system prompt、工具定义等稳定内容固定下来。
2. **时间分层**：高峰期与低谷期不同价，把可延迟任务引导到低峰，提升数据中心利用率。
3. **优先级分层**：Batch API 适合离线标注、报表生成、大规模评测；在线 API 保障低延迟，价格更高。
4. **模型分层**：旗舰模型和轻量模型价差拉大，简单任务用便宜模型，复杂推理才上大模型。

这类玩法在云计算行业并不新鲜。云厂商早年也经历过从“按小时简单计费”到“按 vCPU、内存、存储、流量、请求次数多维计费”的演进。目的不是多收钱，而是让价格信号引导用户更高效地使用资源。AI API 正在复刻这条路。涨价表面是价格上调，本质是让价格更贴近“资源消耗结构”。

## 四、开发者如何判断“贵不贵”？

只盯单价容易被情绪带着走。更实用的做法是把成本拉回到“单位任务成本”。

公式可以简化为：

> 单次成本 ≈ 输入 token 数 ×（缓存命中率 × 命中价 + 未命中率 × 未命中价） + 输出 token 数 × 输出价

- **先看命中率**：system prompt 是否固定？是否频繁改变工具定义？命中率从 0% 提到 90%，成本可能下降一半以上。
- **再看输出长度**：模型是否习惯性输出冗余内容？限制 max_tokens、优化 prompt 要求“简洁回答”，能直接降低最贵的输出开销。
- **最后看任务分级**：离线任务能否走 Batch？夜间任务能否错峰？简单分类能否用小模型？

如果调整后单位任务成本仍然下降，涨价就没有撼动 ROI；如果业务只靠“极端低价”活着，那问题可能不在价格表，而在商业模型本身。

## 五、冷思考：原罪不是涨价，而是锚定效应



心理学上有个词叫锚定效应。当 DeepSeek 以“极低价格”进入市场时，用户心中形成了一个锚点：AI 推理就值这个价。后来价格上调，哪怕仍低于多数同类服务，也会触发“损失厌恶”。

但技术史反复证明：新技术早期的价格曲线很少单调下降。它会经历“补贴—回调—再优化—再下降”的循环。存储、带宽、云计算都走过类似路径。AI 推理还在成本优化的上半场，远没到价格稳态。

真正值得追问的不是“凭什么涨价”，而是：

- 价格是否公开透明？
- 计价是否反映真实资源消耗？
- 开发者是否有足够手段优化成本？

如果这三点成立，涨价就不是原罪，而是市场从狂热回归理性的一个信号。

## 实用建议

1. **建立成本看板**：不要把 API 账单当黑盒，至少按场景记录 token 消耗、缓存命中率和单次成本。
2. **把缓存当优化项**：固定 system prompt、工具 schema、few-shot 示例，尽量让输入命中缓存，这是成本优化中杠杆最高的动作。
3. **按场景分流模型**：简单任务不必全上旗舰模型，离线任务优先 Batch API，实时任务保留在线 API，用价格信号倒逼架构更健康。

涨价不可怕，怕的是我们从未认真算过账。冷静拆解，比一句“原罪”更有建设性。
