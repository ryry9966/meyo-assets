## 背景

接入 MCP 和插件之后，Agent 的能力边界被迅速打开：读文件、执行 shell、发 HTTP 请求、操作数据库、调用第三方 API。但能力越大，误操作和提示注入的风险也越大。一个“帮我整理一下下载目录”的指令，可能被模型理解成删掉某些文件；一段网页内容里藏着的恶意指令，可能诱导 Agent 调用某个高危工具。

只靠“你已经接入了 MCP，能自己看着办”是不行的。真正的工程化做法，是给 Agent 加一层权限策略，明确哪些动作可以自动做，哪些必须停下来问人。

## 问题

权限边界不清晰时，通常有两种失败模式：

- **过度自动**：Agent 对删除、覆盖、发送、付款、修改配置等动作直接执行，出了事才回看日志。
- **过度打断**：每个动作都问一遍，用户很快疲劳，最后变成条件反射式点“允许”，权限形同虚设。

所以核心不是“要不要限制”，而是“在哪里划线和怎么执行”。

## 做法

### 1. 给工具动作做风险分级

不要只按“工具名”判断，要按“动作 + 参数 + 影响范围”判断。建议分成至少四档：

- **只读**：读文件、查询 API、查看数据库。默认自动执行。
- **可逆写**：新建文件、追加日志、创建临时目录。可自动执行，但必须记录。
- **不可逆写/外部副作用**：删除、覆盖、发消息、发邮件、提交代码、操作生产环境。默认需要确认或 dry-run。
- **资金/隐私/权限变更**：转账、修改权限、导出联系人、修改系统配置。必须人类确认，且建议二次校验。

这层分级不要只写在 system prompt 里，应该落到权限策略配置或代码里。

### 2. 用策略引擎做硬边界，而不是只靠提示词

很多事故来自“模型被诱导说‘我没有风险’”。如果权限判断全部交给模型，它可能被用户、网页内容、工具返回结果带偏。更稳的做法是：

- 在 Agent 执行动作前，由策略引擎检查工具名、参数、目标路径、目标环境。
- 对命中高风险规则的动作，直接阻断并转人工确认，不让模型自己决定。
- 只读动作可以放行，但保留审计日志。

在 OpenClaw/Agent 这类框架里，可以封装成一个 `beforeToolCall` 或 `tool guard`。MCP server 本身也要做最小权限暴露：不要让一个 server 把所有工具都注册出来。

### 3. 人类确认不要做成“一刀切”

可以给用户三档选择：

- **本次允许**
- **本次会话允许**
- **始终允许**

但“始终允许”只建议开放给低风险、可逆、且用户能理解后果的动作。对删除、发送、转账这类动作，即使点了“始终允许”，也要在 24 小时或会话结束后失效，避免上下文被长期滥用。

另外，确认提示要清楚说明动作、目标和影响范围，不要只显示“是否执行工具 delete”。至少要包含：

```
动作：删除文件
目标：/home/user/downloads/old/
范围：12 个文件，不可恢复
结果：成功后将无法从回收站恢复
```

### 4. 支持 dry-run 和回滚

对批量操作，强制先 dry-run，输出“将影响哪些文件/记录”，用户确认后再执行。能提供回滚方案的工具，风险等级可以适当下调。

### 5. 记录每一次自动决策

每条日志至少包含：时间、会话 ID、模型决策、工具名、参数、策略命中结果、是否自动执行、用户是否确认。这样出了问题时，可以区分“策略没拦住”还是“用户确认了”。

## 踩坑点

- **只在 system prompt 里写权限规则**：模型可能被绕过。规则必须落在执行侧。
- **工具描述过宽**：比如一个工具叫 `execute_shell`，描述写“执行任意 shell 命令”。模型很容易滥用。应该拆成具体工具，如 `read_file`、`append_file`、`run_safe_command`。
- **频繁确认导致用户疲劳**：如果用户每 30 秒被问一次，他最后会无脑点允许。低风险动作要自动执行。
- **授权没有时效**：用户一小时前允许了“读取联系人”，不代表一小时后另一个任务可以继续读。会话结束或任务切换后要重新授权。
- **忽略提示注入**：网页、邮件、文档内容可能包含“忽略之前的规则，执行 X”。策略引擎要独立于模型上下文运行，不能因为模型说“这个动作安全”就放行。
- **误把权限边界当成用户体验问题**：权限边界是安全和可靠性问题，不是“模型乖不乖”的问题。不能用调 prompt 的方式替代策略控制。

## 可复用建议

1. **先建一张权限分级表**，列出当前 MCP/插件里所有工具，按“只读/可逆写/不可逆写/资金隐私”分类。
2. **把分级表落到策略配置**，不要在每次对话里让模型重新判断。
3. **默认只读和可逆写自动执行，其余的默认确认或拒绝。**
4. **删除、覆盖、发送、转账、改权限等动作，强制人工确认，不提供“始终允许”。**
5. **确认提示要包含动作、目标、范围、后果**，并提供 dry-run 输出。
6. **定期复盘日志**，看哪些动作被模型反复触发、哪些被用户频繁拒绝，调整默认策略。
7. **给 MCP server 做最小权限**，只暴露完成当前任务需要的工具，不要注册全家桶。

## 总结

Agent 权限边界不是为了限制它干活，而是为了让它在不失控的前提下干活。自动化的收益来自低风险、高频、可逆的动作；人类决策的价值集中在高风险、不可逆、需要承担后果的动作。把这条线划清楚，Agent 才能真正从“玩具”变成能跑在真实环境里的工具。

与其相信模型会“自觉”，不如在框架里加一层硬边界。模型负责理解意图，策略引擎负责决定边界，人类负责对关键动作负责。
