## 背景

跑 Agent 自动化时，外部 API 是最大的不稳定源。搜索、网页抓取、通知、支付、数据源，甚至模型网关，都可能超时、429、5xx、返回非预期 JSON。很多 Agent/MCP 工具默认把异常直接抛给上层，任务中断，重跑又可能重复扣费或产生副作用。

## 问题

单一外部故障常常影响整条链路。常见现象：

- 一次搜索接口 503 导致整个日报流程失败；
- Agent 看到报错后开始“自由发挥”，编造降级结果；
- 重试无上限，把对方服务打挂；
- 失败信息混入主上下文，后续判断被污染。

本质不是“让 Agent 更聪明”，而是要在工具层建立错误分类和恢复策略。

## 做法/步骤

### 1. 给工具加一层 adapter，不直接调裸 API

在 MCP server 或插件里封装一个 `callExternalApi`，统一处理：

- 超时：建议 3-8 秒，别用默认无限等；
- 错误分类：`retryable`（429、502、503、504、超时）、`fatal`（401、403、422、参数错误）、`degradable`（非核心数据源）；
- 返回结构固定：`{ ok, status, data?, error?, fallbackUsed? }`。

示例：

```ts
const res = await callExternalApi({
  name: "web_search",
  url: "...",
  timeoutMs: 5000,
  retry: { max: 2, backoffMs: 800, jitter: true },
  allowFallback: true,
});
```

Agent 拿到的不是异常堆栈，而是结构化结果。

### 2. 重试只给可重试且幂等的请求

GET、搜索、读取类可以重试；写入、发送通知、触发任务要谨慎。重试参数建议：

- 最大 2-3 次；
- 指数退避 + 随机抖动，避免惊群；
- 对 429 优先读 `Retry-After`，读不到再用退避；
- 不重试 4xx 业务错误，除非明确可重试。

### 3. 熔断器放在工具内，而不是等 Agent 判断

连续失败超过阈值，比如 30 秒内 5 次，就打开熔断。后续请求直接走 fallback，不调真实 API。半开状态定时探测一次，成功再恢复。这个逻辑对 Agent 透明，Agent 只看到 `fallbackUsed: true`。

### 4. 降级策略要可解释

降级不是“失败了就返回空”。建议：

- 搜索失败 -> 返回本地缓存/历史结果，并标记 `stale: true`；
- 通知失败 -> 写入待发送队列，后续补发；
- 数据源失败 -> 用上一个成功快照，并带 `asOf` 时间；
- 模型 API 失败 -> 切备用模型，或直接返回明确错误让上层暂停。

关键：把降级路径作为返回值的一部分，告诉 Agent“这是旧数据”，而不是无感知替换。

### 5. 错误上下文隔离

不要让 Agent 看到完整堆栈或 HTML 错误页。给它的错误信息控制在：

- 哪个工具失败；
- 错误类型：timeout / rate_limit / 5xx / auth；
- 是否已重试、是否降级；
- 下一步建议：稍后重试 / 调整参数 / 终止。

错误详情写入日志或 `__error_detail` 字段，供调试，不进主推理上下文。

## 踩坑点

- **无差别重试非幂等接口**：可能重复下单、重复发消息。凡是写操作，默认不重试；
- **超时设太长**：Agent 卡住，用户体验比快速失败差；
- **熔断阈值过灵敏**：一次网络抖动就打开，反而降低可用性。建议用滑动窗口，不要用累计失败次数；
- **降级数据污染**：缓存结果没打时间戳，后续 Agent 当成实时数据用；
- **把异常文本直接喂给模型**：容易诱导模型“脑补”结果或产生错误总结。

## 可复用建议

- 工具返回统一 `ToolResult` 结构，所有 MCP server 共用；
- 为每个外部依赖配置独立超时、重试、熔断参数，别用全局默认值；
- 做本地 mock 和故障注入测试：手动模拟 429、超时、畸形 JSON，验证 Agent 走的是降级而不是崩；
- 对外部 API 做健康检查或定时探测，提前感知服务可用性；
- 记录重试次数、熔断状态、fallback 命中率，作为稳定性指标。

## 总结

外部 API 挂掉不是偶发事故，是常态。Agent 的可靠性不来自提示词里多写几句“如果失败请重试”，而来自工具层的明确错误分类、有限重试、熔断和可解释降级。把错误恢复做成结构化工程，Agent 才能在故障时做出合理决策，而不是把一次 503 放大成整条链路的失败。
