## 背景

很多 OpenClaw 用户在给 Agent 接文件工具或 MCP 文件服务时，第一反应是：**“它会不会把我的资料删了？”**  
这个担心很合理。Agent 执行文件操作不像人一样有“后悔”和“常识”，一条模糊的指令、一次路径拼接错误、一个被 cmd 展开的通配符，都可能变成宿主机上的真实删除。

OpenClaw 的沙箱（sandbox）不是简单套一层容器，它由四个部分构成：**权限边界、写时复制、删除重定向、操作审计**。默认策略下，Agent 发出的删除请求不会直接落到宿主文件系统，而是被沙箱拦截并转向可回滚的路径。这就是“Agent 不会误删文件”的工程化基础。

---

## 问题：误删通常是怎么发生的？

在裸接文件工具的情况下，以下场景非常常见：

- 用户说“清理旧的临时文件”，Agent 理解过宽，把 `*.tmp` 扩展到了整个家目录。
- 路径拼接出错，例如 `/data/project` 被拼成 `/data/project /`，rm 命令出错。
- Agent 调用 Python 的 `shutil.rmtree` 或系统 `unlink`，没有经过用户确认。
- 提示词中说“删除无用的图片”，但“无用”没有明确定义。

所以安全模型的核心不是“让 Agent 更聪明”，而是**默认不信任任何删除动作**。

---

## 做法 / 步骤

### 1. 目录角色拆分

把文件系统访问分成三类：

| 角色 | 权限 | 示例 |
|---|---|---|
| 工作区 | 可读写 | `/home/user/openclaw-workspace` |
| 参考数据 | 只读 | `/home/user/documents`、`/mnt/datasets` |
| 系统目录 | 默认拒绝 | `/etc`、`/usr`、`~/.ssh` |

不要给 Agent 整个家目录的写权限，工作区应是一个独立小目录。

### 2. 配置沙箱策略

OpenClaw 的沙箱配置通常使用“默认拒绝 + 白名单”模式。一个最小示例：

```yaml
sandbox:
  default: deny
  writable:
    - /home/user/openclaw-workspace
  readonly:
    - /home/user/documents
    - /mnt/datasets
  trash_dir: /home/user/.openclaw/trash
  command_guard:
    - pattern: "rm -rf"
      action: ask
    - pattern: "unlink"
      action: deny
    - pattern: "shutil.rmtree"
      action: ask
```

关键点：`default: deny` 意味着不在白名单里的路径一律不可见。Agent 即使生成了删除命令，也会因为路径不可达而失败，而不是误删宿主文件。

### 3. 删除重定向

把“删除”变成“移动到回收站”。沙箱会拦截 unlink/rm 调用，将其重定向到 `trash_dir`。这样即使 Agent 真的删了工作区里的文件，文件仍然保留在回收站里，可随时恢复。

### 4. 对参考数据启用只读挂载 / 写时复制

如果你希望 Agent 处理一份数据但又不想改动原文件，可以把参考目录只读挂载。Agent 看到的是快照，写入会落到 overlay 层，原文件不受影响。任务完成后可以丢弃 overlay，或人工合并。

### 5. 审计验证

故意给 Agent 发一条“删除 documents 下的所有 .txt”指令，观察日志：

- 请求命中了哪条策略？
- 是 deny 还是 ask？
- 如果是 deny，Agent 是否收到“无权限”反馈？
- 如果是 ask，是否真的暂停等待用户确认？

只有跑通这个流程，才能说安全模型真正生效。

## 踩坑点

- **工作区路径开太大**：把 `/home/user` 设为可写，等于取消了沙箱。务必将工作区限定为独立目录。
- **只读挂载导致任务失败**：有些工具需要写临时文件或缓存目录。此时需要额外给 `/tmp/openclaw-cache` 或工作区内的 `.cache` 开写权限，否则 Agent 会尝试绕过只读限制。
- **trash 目录不可见**：如果 trash 目录不在沙箱可见范围内，Agent 可能无法完成“移动到回收站”操作，从而退回直接删除。需要保证 trash 目录对 Agent 可写。
- **command_guard 覆盖不全**：只拦 `rm -rf` 不够，还要拦 `unlink`、`truncate`、Python 的 `Path.unlink()`、`os.remove()` 等。
- **overlay 层堆积**：长时间运行后写时复制层会变大，需要定期清理或 commit，否则磁盘占用会悄悄上升。

## 可复用建议

1. **永远用白名单，不用黑名单。** 默认 deny，显式允许才是安全的。
2. **删除不等于真删。** 默认进回收站，重要目录设置 `ask` 二次确认。
3. **参考数据走只读快照，工作区走独立小目录。** 两者物理或逻辑分离。
4. **审计日志至少保留 7 天。** 对任何 deny 事件设置告警，不要等到文件丢了才查日志。
5. **定期做“误删演练”。** 手动构造危险指令，确认沙箱拦截和回收站恢复都正常。

---

## 总结

OpenClaw 的沙箱安全模型并不是让 Agent 变得绝对安全，而是把“不确定的文件操作”变成“可拦截、可回滚、可审计”的工程问题。默认拒绝、白名单工作区、删除重定向、写时复制和审计日志，这五件事组合起来，才能让 Agent 在文件操作上不会直接误删宿主机文件。

真正靠得住的不是某个开关，而是你配置清楚目录角色和权限边界。沙箱给了你这个能力，剩下的就是花半小时把策略写清楚。
