## 背景

现在大多数 AI 助手还是被动模式：你问一句，它动一下。但在 OpenClaw、MCP、插件和自动化实践里，很多场景其实等不起“你开口”——证书快过期、CI 挂了一夜、依赖出现新漏洞、磁盘临时文件膨胀。这类事情如果能由 agent 主动处理，确实能省不少事。

但 proactive 很容易走向两个极端：要么只是定时发个提醒，没真正“办事”；要么让模型自己决定什么时候动手，结果误删资源、循环触发、疯狂打扰。工程上更务实的做法是：**把 proactive 从“预测用户意图”降级为“条件触发执行”**——触发条件明确、动作白名单化、可回滚、可审计。

## 问题

真正的难点不是“让模型主动”，而是：

- 模型自行决定触发条件太发散，不可复现；
- 写操作一旦误执行，回滚成本高；
- 主动任务容易变成通知噪声；
- 自动修复可能触发新事件，形成循环。

所以我在 OpenClaw 里没有直接给 agent 一个大权限的“自主运行”提示词，而是拆成：外部调度器触发 → policy 约束 → agent 调用 MCP 工具 → 审计与通知。

## 做法 / 步骤

### 1. 从只读巡检开始

先不碰写操作。配置一个定时任务，每天早上 9 点触发 OpenClaw 的巡检链，只调用只读 MCP 工具：

- `github_list_ci_failures`
- `check_cert_expiry`
- `list_large_temp_files`

让 agent 汇总结果，按严重级别输出。如果证书剩余天数小于 7 天，生成一条高优先级提醒；CI 失败只聚合仓库名和失败分支，不逐条贴日志。

这一步的目的是跑通“触发 → 执行 → 汇总 → 通知”的链路，同时积累审计日志。

### 2. 把写操作包装成可预览的 MCP 工具

比如要自动清理临时文件，不要直接暴露 `rm -rf`。可以做成：

```
cleanup_temp_files(path, dry_run=true)
```

工具内部先扫描、计算可释放空间，返回将被删除的文件列表。只有 `dry_run=false` 时才真正执行，并在删除前自动打一个 `.tar.gz` 备份到指定目录。

类似地，自动续期证书可以包装为 `renew_cert(domain, dry_run=true)`，先输出当前证书信息和预执行命令，不直接调用 certbot。

### 3. 用 policy 约束 agent 行为

在 OpenClaw 的 agent prompt 或插件配置里写清楚：

- 只允许调用白名单内的 MCP 工具；
- 所有写操作默认 `dry_run=true`，需要二次确认或满足明确阈值才能落地；
- 同一资源 24 小时内最多执行一次主动操作；
- 每次执行必须输出 JSON 结果，包含工具名、输入摘要、输出摘要、是否实际写操作。

例如：

```yaml
proactive_policy:
  max_actions_per_resource_per_day: 1
  write_default_dry_run: true
  require_confirmation_for:
    - cleanup_temp_files
    - renew_cert
  notify_on:
    - high_severity
    - write_action
```

### 4. 接入通知和审计

通知不要全部进 IM 群。低风险巡检结果可以聚合为日报；只有高风险或写操作才实时通知。审计日志单独存文件或数据库，记录触发时间、输入、工具调用、结果、是否回滚。

## 踩坑点

**误把“主动”当“自主”**  
让模型自行决定“什么时候该干活”很像智能，但实际会变得不可控。触发条件必须由外部调度器或明确事件决定，模型只负责在给定条件下执行。

**上下文膨胀**  
定时巡检如果每次全量拉取 GitHub issues、CI 日志，token 消耗会很快。先做轻量筛选，比如只拉近 24 小时失败、只检查证书到期时间，再让 agent 处理结构化后的数据。

**循环触发**  
自动修复操作产生了新事件，又被触发器捕获，导致反复执行。一定要给每个资源加冷却窗口和去重键。比如 `cleanup_temp_files` 执行后，同一路径 24 小时内不再触发。

**通知打扰**  
proactive 系统最容易死于“什么都报”。按严重级别路由：高优先级实时通知，低优先级聚合日报。写操作单独发一条带结果摘要的消息，但不刷屏。

**凭据与权限过大**  
给 agent 的 GitHub token、服务器 SSH key 如果权限太大，一旦误操作影响面会很大。按任务拆 MCP server，使用只读令牌做巡检；写操作使用独立权限，并且只能通过白名单工具调用。

**并发与幂等**  
cron 可能上次还没跑完，下一次又启动。加执行锁，或者让任务本身幂等。比如清理前先检查是否有相同任务正在运行。

## 可复用建议

- **先做只读巡检 + 人工确认**，跑稳两周后再考虑自动写操作。
- **强制 dry-run**：首轮执行不落地，只返回预览结果，确认无误再放行。
- **每个 proactive 任务必须有审计记录**：触发时间、输入摘要、调用工具、输出、是否实际写操作、是否回滚。
- **把 proactive 任务当代码管理**：配置文件进 git，变更走 PR，不要直接在 UI 上点来点去。
- **优先选择可逆操作**。不可逆操作要么不做，要么加延迟执行和人工确认。
- **监控误报率和成功率**。如果某个主动任务每周误报超过一次，先停掉修条件，不要硬撑。

## 总结

Proactive 能力不等于“AI 有了主动性”，更不等于“让模型自己决定一切”。在 OpenClaw 这类 agent 框架里，比较稳的路线是：**外部触发 + 白名单工具 + 策略约束 + 审计日志 + 可回滚**。它真正适合的场景是高频、低风险、条件明确的琐事，而不是高风险的一次性决策。

跑通一条“证书到期提醒 + 临时文件清理预览”的链路，比空谈“AI 主动干活”更有价值。先把主动神经接上，再一点点放宽权限，比一开始就追求全自动要可靠得多。
