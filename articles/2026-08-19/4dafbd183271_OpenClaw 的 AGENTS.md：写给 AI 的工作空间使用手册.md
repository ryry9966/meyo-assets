## 背景

OpenClaw 的 Agent 不只是聊天，它会调用 MCP 工具、执行命令、读写文件、驱动插件。工作空间一旦复杂起来，默认行为就会开始“靠猜”：测试命令跑错、产物写到错误目录、反复尝试不存在的脚本、误用 MCP 工具。

这些问题通常不是模型能力不够，而是没有给 Agent 一份明确的“工作空间使用手册”。在 OpenClaw 里，这个手册就是根目录下的 `AGENTS.md`。它可以被 Agent 在任务开始前读取，用来建立目录、命令、工具边界和验证方式的基本认知。

## 问题

没有 `AGENTS.md` 时，常见现象包括：

- Agent 对目录结构和命令约定没有稳定认知，每次会话都要重新摸索。
- MCP 工具一多，Agent 容易选错工具，或者用 shell 绕过更合适的插件。
- 自动化任务换一个会话、换一台机器，行为就发生漂移。
- 规则散落在聊天记录、插件配置、README 里，Agent 不会主动去翻。

## 做法与步骤

### 1. 在工作空间根目录创建 `AGENTS.md`

先让它短小、明确。一个最小可运行的模板如下：

```markdown
# AGENTS.md

## 项目概览
- 用途：数据清洗与报表生成
- 入口：src/main.py
- 包管理：uv

## 常用命令
- 安装：uv sync
- 测试：pytest -q
- 类型检查：mypy src

## 路径约定
- 原始数据放 data/raw
- 中间产物放 .cache/
- 最终输出放 output/
- 不要写入系统临时目录之外的位置

## MCP/插件规则
- 优先使用 local-fs 插件读写工作空间内文件
- 涉及外部 API 时，先读 .env.example，不读 .env 内容
- 不要用 shell 执行未列出的全局安装命令

## 禁止事项
- 不修改 .git/ 和 AGENTS.md 本身
- 不执行 git push --force
- 不安装全局依赖

## 验证方式
- 改动 src/ 后运行 pytest -q
- 生成文件后确认路径和行数
```

### 2. 让 Agent 先读

如果 OpenClaw 版本支持自动注入，优先在工作空间配置里开启。如果不支持或不确定，可以在任务首条消息里写一句：

> 先阅读根目录 AGENTS.md，再开始执行。

不要默认 Agent 会自动注意到它。

### 3. 持续维护

凡是 Agent 走偏后被你纠正的内容，都应该沉淀进 `AGENTS.md`，而不是每次口述一遍。这样下一轮会话行为才会收敛。

## 踩坑点

- **写太长**：超过 200 行后，Agent 容易忽略关键内容。保持短小，必要时再拆分。
- **规则太模糊**：像“按需执行测试”基本无效。要写成“改动 `src/` 后执行 `pytest -q`”。
- **误写密钥**：不要把真实 API key、数据库密码写进 `AGENTS.md`。只写变量名，指向 `.env`。
- **使用绝对路径**：换一台机器就失效。用相对于工作空间根目录的路径。
- **过度禁止**：禁止项太多，Agent 可能连正常任务都不敢做。给出禁止项时，尽量附带替代方案。
- **文件名或位置不对**：确认 OpenClaw 对 `AGENTS.md` 的自动加载策略，避免大小写、路径层级导致不生效。
- **与系统提示冲突**：不要假设 `AGENTS.md` 永远覆盖内置行为。遇到冲突时，优先在文件里写明“仅在当前工作空间内适用”。

## 可复用建议

- **纳入版本管理**：`AGENTS.md` 放 git 里，修改走 PR，方便追溯约定变化。
- **模块化拆分**：如果单个文件膨胀，可以拆成 `AGENTS.d/commands.md`、`AGENTS.d/mcp.md`，主文件引用。
- **与 `.env.example` 配合**：只描述变量名和用途，不写真实值。
- **写校验脚本**：例如 `check_agents.sh`，检查文件中引用的路径是否存在、命令是否可执行，避免规则失效。
- **记录失败模式**：每遇到一次 Agent 走偏，就把正确做法追加到“常见错误”小节。
- **维护基础模板**：多工作空间场景下，维护一份基础 `AGENTS.md`，按项目裁剪，而不是每次从零开始。

## 总结

`AGENTS.md` 不是给模型堆更多提示词，而是把工作空间约定从隐式变成显式。对 OpenClaw 的 Agent 来说，一份短小、明确、可验证的手册，常常比增加更多工具描述更有效。它的核心目标是减少来回试错，让自动化任务可重复、可交接。
