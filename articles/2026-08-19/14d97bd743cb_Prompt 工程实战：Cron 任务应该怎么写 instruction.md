## 背景

在 OpenClaw 里配置 Cron 任务时，很多同学会直接把交互式 prompt 搬进去，例如“每天早上帮我整理行业新闻”。结果往往出现三类问题：输出刷屏、任务静默失败、重复执行产生副作用。

这不是模型能力问题，而是 Cron 任务的性质和普通对话不同。Cron 是无人值守批处理，Agent 没有实时反馈机会，指令必须写得更像一份可执行的 runbook，而不是一段愿望描述。

## 问题

常见的 Cron instruction 问题包括：

- **上下文空白**：每次触发可能是新的执行环境，不能假设 Agent 记得上次结果。
- **目标不清**：没有指定输出到哪里、以什么格式返回，Agent 可能直接回复一大段文本。
- **副作用不可控**：写文件、发消息、写数据库等操作没有幂等约束，重跑会重复副作用。
- **失败语义缺失**：工具调用失败后，Agent 可能自行发挥、降级处理，或者反复重试。

## 做法/步骤

一个适合 Cron 任务的 instruction，建议按“任务目标、输入/工具、执行步骤、输出契约、约束与失败处理”五部分来写。

示例：

```text
你是 OpenClaw 的定时任务执行器。

任务：每天 08:00 抓取 Hacker News 前 10 条高分内容，写入 /data/hn_daily.md。

执行步骤：
1. 调用 MCP 工具 fetch_hn_top(limit=10)。
2. 只保留 title、url、score 三个字段，过滤 score < 100 的条目。
3. 按 score 降序排列。
4. 将结果写入 /data/hn_daily.md，格式如下：
   # HN Daily YYYY-MM-DD
   | title | url | score |
5. 完成或失败后，只返回一行 JSON。

输出契约：
{"status":"ok|skipped|error","count":N,"file":"/data/hn_daily.md","reason":""}

约束：
- 不要将全文输出到对话中，只输出结果 JSON。
- 如果目标文件已存在且文件名包含今天日期，跳过写入，返回 status=skipped。
- 如果工具调用失败或返回空，停止执行，返回 status=error 和 reason。
- 不要重试超过 2 次。
- 不要调用未列出的工具。
```

这份 instruction 的关键点在于：

- **输出契约**：强制 Agent 返回结构化 JSON，方便后续监控和日志分析。
- **幂等约束**：明确“今天已写过就跳过”，避免重复执行产生重复文件。
- **失败即停**：不允许 Agent 在工具失败后自行猜测结果。
- **工具白名单**：避免 Agent 调用无关工具带来额外副作用。

## 踩坑点

1. **时区不明确**  
   Cron 表达式可能按 UTC 执行，而业务预期是按本地时区。Instruction 里要写明“按 Asia/Shanghai 时区”或“使用服务器本地时区”。

2. **依赖上次运行状态**  
   如果任务需要基于上次结果继续处理，必须在 instruction 中要求先读取状态文件或数据库，而不是默认 Agent 记得。

3. **重试导致重复副作用**  
   网络抖动可能触发重跑。如果没有“已处理则跳过”的逻辑，发消息、写文件、写库都很容易被重复执行。

4. **MCP 工具冷启动失败**  
   Cron 环境里 MCP 工具可能尚未连接或会话失效。Instruction 应写明“如果工具不可用，返回 error，不要降级为手工猜测”。

5. **输出长度失控**  
   抓取网页或 API 时容易把整页内容带回来。要限制字段、条数，并要求只返回摘要 JSON，而不是原文。

6. **上下文窗口被撑爆**  
   分页抓取时如果没有限制，可能一次拉取几百条数据。Instruction 要写清最大条数、截断规则和分页上限。

## 可复用建议

- 给所有 Cron instruction 加统一结尾：**一行 JSON 返回契约**，包含 `status`、`count`、`reason` 等字段。
- 把副作用操作拆开：先 dry-run 输出执行计划，确认无误后再正式写文件或发消息。
- 敏感信息不要直接写在 instruction 里，使用环境变量引用。
- 给任务设置超时，例如“如果 60 秒内未完成，停止并返回 timeout”。
- 定期查看任务日志，把高频失败原因回写进 instruction 的 constraints，让它越来越稳定。

## 总结

Cron 任务的 instruction 不是对话提示词，而是无人值守的批处理作业说明书。把目标、输入、步骤、输出契约、失败处理和幂等逻辑写清楚，任务才能从“偶尔能用”变成“可以长期挂机”。

工程化的 prompt，本质上是把不确定的 Agent 行为约束成可观测、可复现、可排障的流程。
