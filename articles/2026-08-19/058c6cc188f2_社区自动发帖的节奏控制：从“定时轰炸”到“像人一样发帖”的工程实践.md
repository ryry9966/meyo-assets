## 背景

在 OpenClaw/Agent 自动化实践里，内容生成已经不算难点。真正容易被忽略、但直接决定账号能不能活下来的，是发布节奏。

我们用 Agent 做社区内容同步时，第一版实现很简单：候选内容进队列，定时任务每 60 分钟取一条发布。结果账号很快出现验证码、限流和帖子仅自己可见。内容本身没问题，问题出在行为序列太“干净”。

平台风控不一定逐条审内容，但一定会看行为模式。固定间隔、整点触发、每天固定条数、发完就走，这些都像机器人。

## 问题

自动发帖不像机器人的核心，不是内容写得像人，而是节奏像人。

典型的机器人特征：

- 固定间隔发布，例如每小时整点一条；
- 发布时间集中在整点、半点这类可预测位置；
- 每天发布数量完全一致；
- 发帖前后没有浏览、停留、阅读等前置行为；
- 内容结构高度一致，每篇都是标准 Markdown 长文；
- Agent 重启后状态丢失，又开始高频发帖。

这些特征不需要复杂模型，平台用简单的滑动窗口和行为序列聚类就能识别。

## 做法/步骤

我把节奏控制设计成独立于内容生成的一层，专门回答两个问题：**现在能不能发？下次要等多久？**

### 1. 定义发布窗口，而不是固定时间点

先按目标社区活跃时段设置窗口。例如技术社区通常工作日活跃度更高：

```yaml
windows:
  - start: "10:00"
    end: "12:00"
  - start: "14:30"
    end: "17:00"
  - start: "20:00"
    end: "23:00"
```

窗口内再随机选点，避免整点。这样发布行为在统计上会落在正常活跃区间，而不是均匀分布在 24 小时里。凌晨和午休这类低活跃时段尽量少发。

### 2. 用滑动窗口限流，而不是只限总量

总量控制是底线，短时爆发更容易触发风控。我的基础约束是：

```text
daily_limit: 2
hourly_limit: 1
min_interval: 1200s
```

每次发帖前检查过去 24 小时、过去 1 小时和上次发布时间。任一约束不满足就进入等待。这里用 Redis 或本地 JSON state 都行，关键是 Agent 重启后状态不能丢。

### 3. 抖动延迟，但不要均匀随机

固定间隔加固定 jitter 还是太规律。例如每次都是 1h±5min，方差太小，反而形成另一种模式。

实际做法是多层抖动：

```text
base_interval = 3600s
jitter = uniform(-900, 1800)
actual_interval = base_interval + jitter
```

这个分布会向右偏，更像真实用户“想起来就发一下”，而不是精确的钟表。更进一步的，可以根据目标社区历史活跃数据，把发布时间拟合成一个偏态分布，再抽样。

### 4. 发帖前后加入轻量行为模拟

光发帖不浏览也很可疑。但不要一上来就模拟点赞、收藏、关注全家桶，新号做这些动作风险更高。

我先只做浏览行为：

- 打开发帖目标版块；
- 随机浏览 1-3 个帖子；
- 每个页面停留 5-20 秒；
- 偶尔滚动页面；
- 然后进入发帖流程；
- 发帖后停留 10-30 秒，再关闭。

浏览概率不是 100%，有时直接发，有时浏览后再发。动作间隔做随机，避免固定 3 秒一个步骤。

### 5. 内容和结构也要有节奏

内容节奏同样重要。不要每篇都是标准 Markdown 长文。可以设置内容类型模板池：

```text
- 短观点：50-150 字，纯文本为主
- 问题讨论：200-400 字，带一个问题
- 资源分享：链接 + 100-200 字说明
- 经验复盘：600-1000 字，结构化
```

每次发布按概率抽样，避免连续三次发同一种类型。标题也不要固定格式，有时直接纯文本，有时带 emoji，有时用问句。重点是避免所有帖子看起来像同一个模板生成。

### 6. 建立反馈闭环和冷却机制

发布后记录帖子的浏览、回复、点赞，以及账号状态。如果出现验证码、操作频繁、帖子审核异常，就进入冷却：

```text
cooldown_hours = 24
```

冷却结束后降频恢复，例如从每天 2 条降到每天 1 条，观察 3-5 天再判断是否恢复。

这个闭环不复杂，但能让自动化系统从“只会发”变成“会收手”。

## 踩坑点

1. **随机不等于像人**：完全随机会造成短时间内两条、或长时间一条都没有。过度随机本身就是异常信号，需要基于真实分布而不是均匀分布。
2. **状态不持久化**：Agent 重启后 last_post_at、daily_count 都丢了，等于重新开始高频发帖。状态一定要落盘或放 Redis。
3. **时区混乱**：容器默认 UTC，目标社区是北京时间，导致你以为避开深夜，实际上在发帖。窗口时间要明确指定时区。
4. **固定 jitter 会被识别**：所有间隔都在 1h±5min，方差太小。宁可有时候隔 3 小时，有时候隔 40 分钟，让分布更自然。
5. **新号过度模拟互动**：点赞、收藏、关注这类社会行为，平台对自动化判断更敏感。新号前期只做浏览和发帖，等账号稳定后再逐步增加。

## 可复用建议

把节奏控制做成独立插件或 MCP 服务，不要和具体发帖逻辑耦合。它的输入是候选内容队列，输出是：

```json
{
  "can_post": true,
  "wait_seconds": 0,
  "reason": "ok"
}
```

配置集中在几个参数：daily_limit、hourly_limit、min_interval、active_windows、jitter_distribution、cooldown_threshold。

每次决策都写日志，记录时间、随机延迟、冷却状态、发布结果。这样出了问题能复盘，而不是盲目调参数。

新账号建议灰度：前两周只浏览不发帖，第三周低频发帖，第四周逐渐接近目标频率。用真实账号历史行为做参照，而不是拍脑袋定参数。

## 总结

社区自动发帖的节奏控制，不是一个 `sleep(random)` 能解决的问题。它需要发布窗口、滑动窗口限流、偏态抖动、轻量行为模拟、内容结构变化、反馈冷却和状态持久化共同配合。

目标不是让每篇帖子都“看起来完美”，而是让自动发布的行为序列在统计上接近一个普通用户：有时活跃，有时沉默，有时发长文，有时只冒个泡。稳定、可观测、可降级，比追求发布量更重要。
