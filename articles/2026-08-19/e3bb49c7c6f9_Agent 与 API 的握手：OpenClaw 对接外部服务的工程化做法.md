## 背景

很多 Agent 项目到后期不是卡在模型能力，而是卡在外部服务对接。OpenClaw 作为 Agent runtime，提供了工具扩展和 MCP 接入能力，但直接把一个外部 API 暴露给模型调用，往往会出现参数乱填、超时卡死、错误重试失控、甚至模型编造 API 返回结果的问题。

外部 API 通常有自己的鉴权方式、错误码、限流策略和分页结构。模型擅长生成调用意图，不擅长处理传输层和协议层的不确定性。所以“握手”应该发生在受控的工具层，而不是让模型在 prompt 里裸调 HTTP。

## 问题

常见的失败模式有几类：

- 工具描述太笼统，模型不知道该在什么场景调用、该传哪些参数。
- 密钥、token 被写进 prompt 或日志，模型可能复述出来。
- API 超时没有控制，一个慢接口拖垮整个 run。
- 429、5xx 直接返回给模型，模型容易把错误当成成功结果继续输出。
- OpenAPI 自动导入生成几十个工具，模型选择困难，token 消耗暴涨。

这些问题的本质是：外部服务没有被工程化成适合 Agent 消费的稳定接口。

## 做法/步骤

以一个“订单查询 API”接入 OpenClaw 为例，建议按下面步骤做。

### 1. 把外部服务封装成明确工具

不要直接把 API 文档塞进系统提示词。在 OpenClaw 中定义一个工具，包含清晰的 `name`、`description` 和 JSON Schema 参数定义。

`description` 要写清楚三件事：什么时候用、返回什么、不做什么。例如：

> 根据订单号查询订单状态。只用于查询已支付订单，不负责创建、取消或修改订单。返回订单状态、金额和物流单号。

参数 schema 尽量具体，能加枚举就加枚举，能限制长度就限制长度。模型对明确边界的遵守程度远高于对自然语言描述的遵守程度。

### 2. 鉴权放在工具实现层

API key、secret、token 放在环境变量或 secret store 中，由工具的 handler 读取。不要在 prompt、工具描述、日志里出现明文密钥。

OpenClaw 的工具 handler 通常运行在 runtime 侧，这一层做鉴权是安全的。比如：

```ts
const apiKey = process.env.ORDER_API_KEY;
const res = await fetch(`${baseUrl}/orders/${orderId}`, {
  headers: { Authorization: `Bearer ${apiKey}` },
  timeout: 8000,
});
```

### 3. 统一错误分类和返回结构

工具层要把外部 API 的响应处理成模型容易理解的结构。建议统一返回：

```json
{
  "ok": true,
  "data": { "status": "shipped", "amount": 129.0 },
  "error": null,
  "retryable": false,
  "hint": ""
}
```

如果失败：

```json
{
  "ok": false,
  "data": null,
  "error": "rate_limited",
  "retryable": true,
  "hint": "稍后重试，不要连续发起请求"
}
```

这样模型能够区分“业务失败”和“技术失败”，不会把 500 当成正常业务返回。

### 4. 超时、重试和幂等放在工具层

给所有外部调用设置显式超时，通常 5-10 秒。对于可重试错误，可以在 handler 里做一次指数退避，例如 429 时等待 1 秒后重试一次，仍然失败再返回结构化错误。

不要让模型自己决定“再试几次”。模型的重试策略不稳定，容易在限流时放大请求量。

### 5. 优先用 MCP 封装成熟外部服务

如果外部服务已经有 MCP server，可以让 OpenClaw 作为 MCP client 接入。MCP server 常驻进程可以复用连接、管理会话，比每次工具调用都重新建连更稳定。

但接入后要裁剪：只保留当前任务需要的 2-5 个工具，不要全量导入。全量导入会让模型选择困难，也会增加每轮上下文长度。

## 踩坑点

- **密钥暴露**：排查日志、错误堆栈、工具返回里是否带出 Authorization header。模型有时会把 `process.env` 里的内容当普通文本输出。
- **工具描述太泛**：一个只有“查询订单”四个字的工具，模型可能传错订单号格式，或把用户 ID 当订单号。
- **超时缺失**：外部 API 一旦变慢，Agent 会一直等，导致整条链路卡住，用户以为死了。
- **错误直接透传**：把原始 HTML 错误页、堆栈信息返回给模型，模型会产生幻觉，比如“查询成功，订单已发货”。
- **工具数量失控**：OpenAPI 自动生成工具时，连内部调试接口也会暴露出来。只保留面向任务的最小集合。
- **流式输出下的工具调用**：确保 OpenClaw 在流式生成中能正确中断并执行 tool call，否则模型可能一边输出文本一边假装调用了工具。

## 可复用建议

1. **统一网关层**：多个外部 API 不要各自为政，可以加一个薄网关，统一做鉴权、限流、重试、日志和缓存。
2. **短 TTL 缓存只读接口**：对查询类接口加 30-60 秒缓存，能明显降低重复调用。
3. **给工具加 trace id**：把一次模型调用和它触发的所有外部 API 调用关联起来，方便排查。
4. **先 mock 再真调**：工具定义完成后，先用 mock 返回验证模型调用参数是否稳定，再切换真实 API。
5. **监控工具调用成功率**：统计每个工具的调用成功率、平均时延、错误类型分布。外部服务变差时，先看工具层指标，而不是猜模型问题。

## 总结

OpenClaw 对接外部服务，不是把 API key 丢给模型，而是把外部服务封装成一个稳定、可观测、边界清晰的工具或 MCP 入口。模型负责生成调用意图，工具层负责协议、鉴权、超时、重试和错误转译。

稳定握手的关键在于：让模型只看到它需要的结构化信息，让外部 API 只收到合法的请求。这个边界越清楚，Agent 的可靠性越高。
