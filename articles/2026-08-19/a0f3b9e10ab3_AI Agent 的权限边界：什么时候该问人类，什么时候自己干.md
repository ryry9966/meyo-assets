## 背景

Agent 从“对话”走向“执行”之后，权限边界就不再是产品体验问题，而是工程安全问题。在 OpenClaw 这类环境里，Agent 可以通过 MCP、插件、脚本直接操作文件系统、发请求、执行命令。只要工具一接上，Agent 就具备了真实世界的写入能力。

如果没有明确边界，会出现两种极端：一种是事事都问人类，Agent 退化成一个带壳的命令行；另一种是无差别自动执行，一旦遇到删除、覆盖、调用付费 API 或误操作生产环境，代价会非常高。

因此需要一套可以在工程上落地的权限策略，让 Agent 在“自己干”和“问人类”之间有一个稳定、可审计的决策机制。

## 问题

权限判断的难点在于：风险不只取决于“做了什么动作”，还取决于“操作什么资源”“在什么上下文里”“影响范围有多大”。

例如同样是 `fs.write`：

- 写入 `/tmp/agent-draft.md` 风险很低；
- 覆盖 `~/.zshrc` 风险中等；
- 写入 `deploy/credentials.json` 风险很高。

如果只按工具名做粗粒度控制，很容易放过高风险参数，或者把低风险操作卡得很死。真正需要的是“动作 + 资源 + 上下文”的组合策略。

## 做法

### 1. 建立动作风险分级

先把 Agent 可能调用的工具按风险分成几个等级。一个可参考的分层如下：

| 级别 | 典型动作 | 默认策略 |
|------|----------|----------|
| L0 只读 | `read`、`list`、`search`、`diff`、`get` | 自动执行 |
| L1 低风险写 | 写临时文件、草稿、本地缓存 | 自动执行，但记录日志 |
| L2 中风险写 | 修改项目文件、发消息、提交 git、更新配置 | 需确认或会话级预授权 |
| L3 高风险 | 删除、覆盖、执行 shell、付费 API、生产环境操作 | 默认拒绝或必须人工确认 |

这个分级不是给用户看的，而是给权限中间件用的。Agent 在计划阶段就应该标记每个步骤的风险等级。

### 2. 在工具调用前做策略拦截

在 OpenClaw/MCP 场景里，建议不要把权限判断散落在各个插件里，而是做一个统一的策略层。所有工具调用都先经过这个中间件，再决定放行、拦截或询问。

一个简化的策略配置可以这样表达：

```json
{
  "default": "ask",
  "rules": [
    { "tool": "fs.read", "action": "allow" },
    { "tool": "fs.write", "resource": "/tmp/**", "action": "allow" },
    { "tool": "fs.write", "resource": "/project/**", "action": "ask" },
    { "tool": "shell.exec", "pattern": "rm -rf", "action": "deny" },
    { "tool": "http.post", "host": "api.internal", "action": "ask" }
  ]
}
```

这里的核心是 `default: ask`，也就是默认拒绝自动执行，只对明确允许的动作放行。这个做法比“默认允许，危险命令黑名单”要可靠得多。

### 3. 计划预判 + 执行前确认

对于 L2/L3 操作，不要只依赖调用前的即时询问。让 Agent 在制定计划时，就把将要执行的步骤列出来，包括：

- 使用哪个工具；
- 操作什么资源；
- 预期结果；
- 风险等级；
- 是否需要人类确认。

人类可以在计划阶段一次性批准低风险步骤，但高风险步骤仍然在执行前单独确认。这样既避免了一步一问，也保留了关键节点的控制权。

### 4. 提供 dry-run 和可回滚能力

只要有可能，先让 Agent 输出一个 dry-run 预览。比如要修改配置文件，先展示 diff；要执行命令，先展示完整命令列表；要发消息，先展示接收人和内容摘要。

执行完成后，保留审计日志。日志至少包含：时间、工具名、参数、资源路径、执行结果、是否经过人类确认。对于可回滚的操作，提供撤销或回滚入口。

## 踩坑点

**只读工具并不绝对安全。**  
很多团队容易把“只读”当成免死金牌。但某些读操作可能暴露敏感信息，例如读取环境变量、全局配置、密钥文件。`fs.read` 能自动执行，不代表它可以读取任意路径。需要对资源路径做限制。

**MCP 参数级权限容易被绕过。**  
最常见的错误是：只允许 `shell.exec` 工具，但没有限制可执行的子命令。Agent 或提示注入攻击者可以通过参数拼接执行任意命令。应该在参数层做白名单，比如只允许 `ls`、`cat`、`git status` 等明确命令。

**确认时没有展示具体内容。**  
如果用户只看到“Agent 想要修改文件，是否允许？”，而看不到具体 diff 或命令，这种确认几乎等于盲批。确认界面必须带变更摘要，否则不具备实际意义。

**确认疲劳导致机械点击。**  
低风险操作如果频繁询问，用户很快就会对确认弹窗脱敏。解决办法是引入会话级预授权，比如“本次会话允许对 `/tmp/**` 的写入”，但同时设置有效期，避免永久放宽。

**没有审计日志，出了问题无法回溯。**  
自动执行越多，审计越重要。没有日志，就无法判断是规则漏洞、Agent 误判还是参数注入。

## 可复用建议

1. **默认拒绝，显式授权。** 不要依赖黑名单，黑名单永远补不全。
2. **动作与资源组合控制。** 不要只限制工具名，要限制到参数、路径、主机名等粒度。
3. **MCP 工具做参数级限制。** 禁止将原始用户输入直接拼进 shell、SQL、命令参数。
4. **高风险操作采用两阶段确认。** 计划批准一次，执行前最终确认一次，并设置确认超时。
5. **保留审计日志。** 记录工具、参数、结果、是否经人类确认，最好支持回放。
6. **定期复盘权限规则。** 把频繁确认且确实低风险的动作降级，把偶发高风险动作升级。权限策略不是一次性配置。

## 总结

Agent 权限边界的本质，是把人类确认投入到“风险不对等”的地方：自动执行低风险、可回滚、可审计的操作；在高风险、不可逆、影响面大的操作上保留人工卡点。

在 OpenClaw/MCP/插件这类执行型环境里，最实用的做法不是做更聪明的 Agent，而是做一个稳定的权限中间件，配上清晰的风险分级和审计日志。这样无论 Agent 能力怎么演进，边界始终是可控的。
