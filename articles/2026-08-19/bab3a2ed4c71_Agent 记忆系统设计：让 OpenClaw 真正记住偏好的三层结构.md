# Agent 记忆系统设计：让 OpenClaw 真正记住偏好的三层结构

## 背景

很多 Agent 的“长期记忆”做不好，不是因为模型不够强，而是因为把记忆当成了无限上下文。常见错误是：用户一次次说“记住我偏好中文回复”，开发者就把所有对话历史、偏好、临时指令全部塞进 system prompt。结果上下文越来越长，旧信息覆盖新偏好，最后连用户都搞不清 Agent 到底记了什么。

在 OpenClaw / Agent / MCP 这类工程化场景里，记忆系统应该像代码仓库一样：结构清晰、可检索、可人工修改、有更新记录。

## 问题

偏好不是简单的键值对。比如用户说“我不喜欢用 emoji”，这是稳定偏好；用户说“今天先别用 emoji，我想正式一点”，这是临时指令。如果把两者都写进长期记忆，下次会话就会被污染。

还有冲突：用户以前说“回答精简”，后来又说“多解释背景”。怎么更新？直接覆盖可能丢历史，不覆盖又会读到旧偏好。

所以，记忆系统要解决的三个核心问题是：

1. 什么信息该进入长期记忆？
2. 长期记忆怎么存储和检索？
3. 偏好冲突如何更新和撤回？

## 做法：三层记忆结构

我把 Agent 记忆分成三层：

### 1. 工作记忆
只存当前会话或当前任务状态，比如“用户正在调试 MCP 插件，目标文件是 `config.py`”。这层存上下文变量或 session 文件，任务结束就清理，不进长期记忆。

### 2. 偏好记忆
用户长期偏好，人类可读、可编辑。在 OpenClaw 项目里，可以建一个 `memory/preferences.md`，让 Agent 启动时加载进 system prompt。示例：

```markdown
# 偏好
- 回复语言：中文
- 代码注释：中文，解释算法意图
- 不要自动执行 git push
- 任务完成后给出下一步建议
```

这样用户可以直接改文件，比让模型自己写记忆安全得多。偏好文件不要太大，几十条以内直接全量注入；超过这个量级再考虑检索。

### 3. 事实/程序记忆
存实体信息、路径、规则、常用工具配置等。用 SQLite 或 JSON 通过 MCP memory server 暴露给 Agent。比如：

```json
{
  "namespace": "fact:project",
  "content": "后端服务在 192.168.1.20:8080，使用 FastAPI",
  "source": "user_explicit",
  "updated_at": "2026-01-14T10:00:00Z",
  "ttl": 86400
}
```

MCP 工具提供 `remember(content, namespace, ttl)` 和 `recall(query, namespace)`，Agent 自主决定读写。所有写入必须带来源和过期时间。

## 写入时机

不是每一句用户纠正都值得写进长期记忆。建议这样区分：

- **显式记忆**：用户说“以后都这样”“记住” → 写入偏好层或事实层。
- **隐式记忆**：用户在多个会话里重复纠正同一件事 → 先生成“候选记忆”，下次会话前让用户确认，或标记为低优先级。
- **临时指令**：只写工作记忆，任务结束丢弃。

## 冲突处理

同一命名空间下出现冲突偏好时，不要直接覆盖。保留最新一条，同时记录来源和时间：

```yaml
- preference: "回答精简"
  updated_at: 2026-01-14T10:00:00Z
  source: user_explicit
  supersedes: "2025-12-01:回答详细"
```

这样即使最新一条写错了，也可以回退。

## 踩坑点

1. **敏感信息进偏好文件**：API key、密码、token 不要写进 memory，应该用环境变量或 secret manager。
2. **全量注入导致 prompt 膨胀**：偏好文件超过几十条就开始影响指令遵循，需要做命名空间过滤。
3. **隐式抽取不可靠**：模型可能把用户一次抱怨当成永久偏好。对策：隐式记忆必须经过确认。
4. **记忆放进插件黑盒**：不可编辑、不可清理，一旦写错很难修正。尽量用文件或可查询数据库。
5. **TTL 缺失**：事实类信息（服务器 IP、项目状态）会过期，必须带 `ttl` 或 `expires_at`。
6. **没有“忘记”机制**：要提供 `forget(id/namespace)` 工具，让用户能撤销错误记忆。

## 可复用建议

- 命名空间统一：`pref:`、`fact:`、`rule:`、`session:`，避免混在一起。
- 每条记忆都要有 `source` 和 `updated_at`。
- 偏好用 Markdown，事实用 SQLite，不要把结构化数据塞进自然语言。
- 给 Agent 一个明确规则：写下记忆前先问自己——这条信息下周还成立吗？
- 定期清理过期事实，别让记忆库变成垃圾堆。

## 总结

Agent 记忆设计的关键不是模型能力，而是存储边界和更新策略。把记忆分成工作、偏好、事实三层；偏好人工可编辑，事实带 TTL 和命名空间；写入区分显式/隐式，保留冲突历史。这样 OpenClaw 才能真正“记住你”，而不是把上下文越塞越乱。

工程上，一个小而可控的记忆文件，远比一个复杂的向量数据库更可靠。
