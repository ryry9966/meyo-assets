## 背景：调度器的“天真”假设

OpenClaw 的调度引擎按 cron 表达式准时触发任务，每个 Worker 接到指令后立即执行。这种模型天然假设“任务执行时间远小于调度间隔”——在多数快速查询或轻量插件场景下成立。但一旦接入需要调用外部 API、执行 MCP 工具链、或者操作较重 Agent workflow 的任务，一次执行用掉 3–7 分钟很常见。如果恰好是每 5 分钟触发一次，就会出现典型的 **“定时任务撞车”**：前一实例还在跑，后一实例已经启动，两个相同任务重叠执行。

“撞车”不只是日志里多一个 PID，实际生产环境中会导致：

- 重复调用 LLM/API 造成 token 与配额浪费
- 目标服务看到瞬时并发升高，被误判为爬虫或被限流
- 本地状态文件或数据库记录被双写，出现竞态条件
- 下游 Agent 收到重复指令，产生不可预期的连锁反应

OpenClaw 本身没有在调度层强制互斥，因此需要我们自己实现**防重入锁**，给任务加一道“信号灯”。

## 问题还原：5 分钟任务怎么打起来的

假设有一个“舆情监控 Agent”，定时询问某 MCP Server 的最新文章，再调用本地模型做摘要，最终写入 SQLite。预设间隔 5 分钟，实际执行时间波动于 4–8 分钟。

观测到的时间线如下（OpenClaw 日志片段）：

```
[topic-monitor] 10:00:01 start
[topic-monitor] 10:05:01 start
[topic-monitor] 10:06:23 finish (first)
[topic-monitor] 10:08:45 finish (second)
```

10:05 的调度触发时，10:00 的任务还在跑。Worker 毫不客气地新建了第二个实例，两份 LLM 调用同时进行，最终写入的记录里出现两条时间戳相隔不到 1 分钟的重复摘要。问题根源在于缺少“运行中则跳过”的判断。

## 做法：给任务加一把可过期的锁

OpenClaw 支持通过插件或自定义脚本来增强任务逻辑，我们可以在任务体的开头插入锁逻辑。推荐使用 Redis 实现分布式锁，因为它轻量、具备原子操作和过期能力，即使未来水平扩展 Worker 也不会失效。

### 步骤

1. **任务开始时尝试获取锁**  
   使用 Redis 的 `SET resource-name my-random-value NX EX 600`。  
   `NX` 保证只有当 key 不存在时才成功（互斥），`EX` 设置超时，防止任务意外崩溃后锁永不释放。

2. **检查获取结果**  
   若命令返回 `OK`，代表拿到锁，正常执行任务；若返回 nil，表示已有实例在运行，可以记录一条 INFO 日志后直接退出，或推迟到下一次执行。

3. **任务结束时释放锁**  
   不能简单地 `DEL` 掉 key，因为可能锁已经过期并被其他实例获取。应采用 Lua 脚本比对持有者：
   ```lua
   if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1])
   else
       return 0
   end
   ```
   只有当前实例持有的随机值匹配时，才删除。

4. **与 OpenClaw 集成**  
   在 OpenClaw 的 task 定义中，添加前置钩子。例如使用 `pre_execute` 脚本调用上述逻辑。若未获取到锁，可通过抛出特定异常或设置退出标记，让调度器视为“跳过”而非“失败”，避免产生无谓的告警。

如果暂时没有 Redis，也可以用 SQLite 或文件锁，但需要注意多进程并发和锁释放的健壮性。

## 踩坑点

- **锁超时短于任务执行时间**  
  TTL 必须大于任务可能的最长执行时间（含网络重试）。可设置得宽松一些（如任务间隔的 2 倍），并通过监测锁续期（watchdog）动态延长。

- **异常退出未释放锁**  
  Worker 被 kill -9 或 OOM 时，清理代码不会执行。如果没有过期机制，锁就会变成“死锁”。`EX` 是底线，同时对关键任务增加手动解锁的管理接口。

- **单机锁的幻觉**  
  用 `fcntl` 文件锁或内存标志在单机上没问题，但若 OpenClaw 配置了多个 Worker 或跨容器部署，锁作用域不足，仍会撞车。从一开始就采用 Redis/etcd 这类网络可见的锁，可免去后续迁移之苦。

- **锁粒度设计**  
  不要用同一个锁 key 覆盖所有任务。可以按 `task_name` 甚至 `task_name:parameters_hash` 来区分，避免不同任务互相阻塞。

- **重试风暴**  
  如果锁冲突后选择重试而不是跳过，可能在多 Worker 间引发大量竞争，消耗 Redis CPU。优先采用“跳过并等待下一次调度”的策略，除非任务对实时性要求极高。

## 可复用建议

1. **封装成 OpenClaw 插件**  
   编写一个 `lock_guard` 插件，接受 `lock_key`, `ttl`, `redis_url` 等参数，在 `pre_execute` 阶段统一做互斥判断。社区中很多任务都可以直接引用。

2. **幂等设计兜底**  
   即使锁偶尔失效（网络分区、Redis 切换），通过业务表上的唯一约束或版本号检查，让重复写入不会污染数据。这是最后的保险。

3. **监控与告警**  
   统计每个 task 的 `lock_skip_count`，当跳过次数持续高于阈值，说明任务执行效率已跟不上调度频率，需要扩容或降低频率。用 OpenClaw 的 metrics 端点输出，供 Prometheus 采集。

4. **周期性清理**  
   陈旧锁 keys（TTL 已过却仍残留）定期扫描删除，避免 Redis 内存堆积。

## 总结

“5 分钟任务撞车”不是 OpenClaw 的 bug，而是任何调度系统在任务时长不确定时的常态。加一把带过期和原子释放的防重入锁，就相当于给定时火车的站台装上了信号灯，成本极低，收益却覆盖了数据准确性、资源利用率和运维心智。

如果你已经遇到了日志里熟悉的两行 `start`，不妨现在就翻出 Redis，花 20 行脚本给任务戴上这个“安全帽”。社区里的很多灵异事件，其实缺的只是一把锁。
