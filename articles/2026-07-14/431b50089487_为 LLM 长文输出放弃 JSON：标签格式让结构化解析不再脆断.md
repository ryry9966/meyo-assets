## 背景：当自动化流水线卡在“半个花括号”上

在基于 OpenClaw 搭建 Agent、MCP 插件或自动化报告管道的实践中，我们经常需要让模型输出一段**带有结构化信息的长文本**，再由下游解析器提取字段。比如：

- 从长文档中提取摘要、关键词列表、情感倾向；
- 多步推理后返回最终答案 + 可信度 + 引用；
- 工具调用返回的复杂参数体（尤其是需要多行内容时）。

直觉上，JSON 是首选。它生态成熟、schema 明确，但实际使用中，让 LLM 稳定输出**合法、完整的长 JSON**，比预期困难得多。尤其是当输出超过几百 token，又包含换行、引号、嵌套对象时，坏掉的比例会迅速上升。

站在工程化的视角，我们不关心模型有没有“理解” JSON 语法，我们只在意**从模型输出到下游消费的成功率**。这篇文章会复盘我们为什么开始放弃 JSON，怎样用类标签格式替代，以及实施过程中踩过的坑。

## 问题：长 JSON 输出的三种典型脆断

在经过上百次自动化调用后，我们总结了三种最典型的坏 JSON 模式：

1. **未闭合与多余逗号**  
   模型在高强度生成中，容易在数组或对象的最后一个元素后多加一个逗号，或者在字符串内插引号导致提前闭合。例如：
   ```json
   {"summary": "他说："你好"", "tags": ["AI", "agent",]}
   ```
   这类错误对标准 `json.loads()` 致命，修复逻辑也很难写完备。

2. **多行字符串截断与换行符处理**  
   当要求模型输出包含段落文字的字段时，若 Prompt 未强调转义，模型会直接输出物理换行，而 JSON 标准要求用 `\n`。即使模型能正确处理，长生成容易遇到 API 截断——我们收到的 JSON 可能就缺一个闭合 `}`。

3. **嵌套对象在长生成中的生成压力**  
   如果 schema 包含 3 层以上嵌套，模型需要在缓存中维护精确的括号栈。一旦注意力分散，就会多一个 `]` 或少一个 `}`，且这类错误难以通过后处理自动修复。

这些问题的共同后果是：**一个 Agent 链的某个环节因为解析失败挂起，整个工作流回退或产出空结果，而不是优雅降级。** 在生产环境中，这比偶尔的输出质量下降更致命。

## 转向标签格式：为什么它更稳

标签格式（类 XML/HTML 的标记对）本质上把结构化信息嵌入在自然语言流中。它的优点很明显：

- **无需转义物理换行**：内容直接写在标签之间，多行文本天然合法。
- **解析容错性强**：即使整体输出没有被完整接收，已出现的标签对仍可被提取，不会整个塌方。
- **模型生成负担小**：训练语料中大量存在带标签的文本（HTML、XML、论坛标记等），语法几乎零成本。
- **调试友好**：原始输出对人类可读，出问题时肉眼更快定位。

缺点也有：对于深层嵌套结构，标签格式不比 JSON 更优雅；极端情况下内容里可能包含同名字符串干扰解析。但这些缺陷在实际自动化 pipeline 中可以通过**约定**轻松规避，比 JSON 的硬性语法错误更容易处理。

## 实施步骤

### 1. 设计干净的标签 schema

以“摘要 + 关键词 + 可信度”抽取任务为例，我们把原来的 Prompt 从要求输出 JSON：

```
输出以下 JSON 格式：
{
  "summary": "多行摘要...",
  "keywords": ["词1","词2"],
  "confidence": 0.85
}
```

改为要求输出标签块：

```
请将结果按以下格式输出，不要添加额外解释：
<summary>
这里写完整摘要内容，可包含任意多行。
</summary>
<keywords>
词1, 词2, 词3
</keywords>
<confidence>
0.85
</confidence>
```

关键点：**标签名要独特**，避免与可能出现在内容中的普通单词冲突，可以在内部统一加前缀，如 `<llm_summary>`。简单场景下直接用 `summary` 也够用，只要提醒模型不要在摘要正文中出现 `</summary>`。

### 2. 解析器实现（Python 示例）

解析不依赖 XML 库，直接用正则去贪婪匹配最外侧标签，再处理内容去首尾空白：

```python
import re

def extract_tag(text: str, tag: str) -> str | None:
    pattern = rf'<{tag}>\s*(.*?)\s*</{tag}>'
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1) if match else None

# 批量提取多个标签
def extract_from_tags(text: str, tags: list[str]) -> dict:
    result = {}
    for tag in tags:
        content = extract_tag(text, tag)
        if content is not None:
            # 根据标签进一步解析类型
            if tag == 'keywords':
                result[tag] = [k.strip() for k in content.split(',') if k.strip()]
            elif tag == 'confidence':
                try:
                    result[tag] = float(content)
                except ValueError:
                    result[tag] = None
            else:
                result[tag] = content.strip()
    return result
```

如果模型偶尔在标签外写多余文字，正则仍然可以正确捕获，天然具有鲁棒性。

### 3. 兜底策略

即使标签格式大幅降低失败率，也不能假设 100%。我们通常加入两层兜底：

- **尝试 JSON 后备**：如果指定标签一个都没提取到，则用 `json.loads()` 尝试整个输出，再不行用正则修复（如去除尾逗号）后重试。
- **部分提取**：有些标签失败但另一些成功，不中断流程，放入日志并继续；下游根据空字段做降级处理。

这样整体解析成功率可以从原来的 70% 左右提升到 95% 以上（基于内部 3000 次调用统计，任务长度在 800-2000 token 之间）。

## 实际踩过的坑

- **标签名正则泄露**：当内容本身包含形如 `<summary>` 或 `</summary>` 的文本时，非贪婪匹配会过早闭合。解决方法：在 Prompt 中明确规定“摘要中请不要出现 `</summary>` 字符串”，并辅以后处理：如果匹配到的内容富含尖括号，再尝试用更保守的闭合检测。
- **多段输出的提取**：如果一次生成中包含多个实例（例如批量抽取），应使用包裹标签，如 `<item>...</item>` 嵌套，解析时先用正则拆分，再分别提取子标签。
- **特殊字符与截断**：标签内部出现了 `</tag>` 缺失闭合，可能因为模型生成中断。我们通过检查最后一个标签是否闭合，若未闭合则用 `.find('</tag>', start)` 向前查找，实在找不到则丢弃该字段。
- **不同模型的遵循度差异**：虽然标签格式比 JSON 友好，但某些小模型可能会在标签外添加“好的，按照要求输出”之类的废话。通过在 Prompt 里强调“只输出指定块”并给出 few-shot 示例，大幅减少这类问题。

## 可复用建议

对 OpenClaw / MCP / Agent 使用者的具体建议：

1. **在要求模型输出结构化内容时，优先评估是否可以用标签格式替代 JSON**。尤其是目标字段含多行文本、列表简单、嵌套不超过两层时，标签格式的维护成本明显更低。
2. **在 OpenClaw 的 tool result 或 A2A 消息管道中，统一使用一套约定的标签命名规范**，比如 `llm_result`、`llm_items`，并封装一个 `extract_tag` 工具函数放在公共库。
3. **记录解析失败样本，持续优化 Prompt 和正则**。你会发现，绝大多数失败不是因为标签格式本身，而是模型输出多了“预备起”或“完毕”之类的礼貌用语。
4. **大型嵌套结构仍可退回 JSON**，但可用标签做外层包裹，例如 `<json_block>{...}</json_block>`，这样至少外层提取鲁棒，内部解析失败也能定位。

## 总结

从坏 JSON 切换到标签格式，核心收益是**将结构化解析从“需要完整且语法完美的输出”降级为“对连续流的部分提取”**。这在长文生成、不稳定网络、低成本小模型等场景尤为明显。

它不是一个颠覆性技术，而是一个务实的选择：用极小的改动，在自动化管道里消灭一大类最恼人的中断源。如果你正在构建 OpenClaw 自动化流程，并且被 JSON 解析错误折磨，不妨花一小时把关键 prompt 和解析器改成标签版本——这个投入的回报会在第一个稳定的深夜无人值守运行中体现出来。
