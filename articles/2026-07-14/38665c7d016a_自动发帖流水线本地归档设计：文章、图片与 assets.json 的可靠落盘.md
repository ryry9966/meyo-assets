## 背景

在基于 OpenClaw、Agent 或多工具编排的自动化发帖流水线中，一次任务通常会产出多种资源：Markdown 正文、多张配图、与平台发布相关的元数据。如果不做归档，这些产物要么堆积在临时目录，要么仅存在内存或外部存储的缓存中。后续无论是排查发布失败、回溯生成上下文，还是复用某次产出的图片与文案，都会变得困难且不可靠。

因此，一套可复用的本地归档策略，是工程化内容管线的基础组件。

## 问题

常见痛点有三方面：

1. **版本混乱**：多次运行后，文章与图片分散在不同文件夹，难以将某次发布的完整输出一键回溯。
2. **引用断裂**：生成 Markdown 中的图片引用往往是本地临时路径。一旦目录变更或清理，预览和回放在开发环境中立即失效。
3. **元数据丢失**：生成时的模型参数、提示词、生成时间等信息若不随资产一并存储，后期几乎无法复现同风格内容。

## 做法与步骤

### 1. 设计归档目录结构

采用「批次」作为最小归档单位。每次完整的生成任务产生一个批次目录，内部结构如下：

```
archive/
└── 20250513_0915_a3f2c/
    ├── post.md
    ├── images/
    │   ├── cover.png
    │   └── img_01.png
    └── assets.json
```

批次目录命名规则：`YYYYMMDD_HHMM_短哈希`，保证时间有序且防止并发碰撞。

### 2. 生成批次 ID 与目录

在 Agent 或脚本入口，利用时间戳和随机哈希生成目录名。OpenClaw 插件或 MCP 工具均可完成。例如使用 Python 工具：

```python
import datetime, uuid, os

def create_batch_dir(base: str = "archive") -> str:
    ts = datetime.datetime.now().strftime("%Y%m%d_%H%M")
    hash_suffix = uuid.uuid4().hex[:5]
    batch_dir = os.path.join(base, f"{ts}_{hash_suffix}")
    os.makedirs(os.path.join(batch_dir, "images"), exist_ok=True)
    return batch_dir
```

如果是纯 CLI 环境，也可通过 MCP shell 工具创建。

### 3. 保存 Markdown 与图片

文章 Markdown 直接写入 `post.md`，图片保存到 `images/` 子目录。关键点是**确保 Markdown 中的图片引是相对路径**，避免绝对路径导致归档后不可读。如果生成工具返回的是绝对路径或临时 URL，需要先处理。

推荐在生成流水线中加入一个后处理步骤：

- 下载远程图片（如 DALL·E 生成的 URL）到本地 `images/`；
- 将 Markdown 中的图片引用替换为 `images/xxx.png` 相对路径。

这里可以用自定义函数或 OpenClaw 的 `process_result` 钩子实现。

### 4. 构建 assets.json

`assets.json` 记录一次生产的所有元信息。建议包含以下字段：

```json
{
  "batch_id": "20250513_0915_a3f2c",
  "created_at": "2025-05-13T09:15:22Z",
  "model": "gpt-4o",
  "prompt_hash": "sha256:...",
  "images": ["images/cover.png", "images/img_01.png"],
  "post_file": "post.md",
  "parameters": {
    "style": "technical",
    "target_length": 1000,
    "tone": "克制"
  },
  "status": "published"
}
```

其中 `images` 数组按生成顺序记录相对路径，`post_file` 指向正文，`parameters` 为快照生成时的关键参数，便于后续筛选和对比。

### 5. 生成索引文件（可选）

当批次积累较多时，可在 `archive/` 根目录动态维护一个 `index.json`，记录所有批次 id、时间与状态。可以是简单数组，每次新批次追加一行，避免全量扫描目录。

```json
[
  {"id": "20250513_0915_a3f2c", "date": "2025-05-13", "status": "published"},
  ...
]
```

## 踩坑点

- **相对路径与工具链兼容性**：某些 Markdown 渲染器（如 VS Code 预览）可能将相对路径解释为相对于源文件的位置。因此归档后的 `images/` 必须与 `post.md` 保持在同一层级，否则预览图片会 404。另外，如果后续需要将归档内容上传到 S3 或 CDN，路径映射需要批量重写，归档时引入绝对路径会徒增麻烦。
- **并发任务文件名碰撞**：多个流水线实例同时运行时，若仅用 `%Y%m%d_%H%M` 而不用随机后缀，同一分钟内创建的目录可能冲突。务必加上短哈希或 UUID 片段。
- **assets.json 序列化陷阱**：注意 JSON 中避免放入不可序列化对象（如 datetime 需转字符串），否则在插件/工具链中回写文件时会静默失败。
- **图片非本地化**：如果直接从生成 API 返回的 URL 引用，而不下载到 `images/`，后续该 URL 可能过期。建议在归档函数中统一下载并转为本地存储。

## 可复用建议

1. **封装归档工具**：将上述创建批次、保存文件、写 assets.json 打包成一个通用函数或 MCP 工具，供不同流水线复用。例如提供一个 `archive_assets` 的 MCP 工具，入参为 `markdown_content`、`image_urls`、`parameters`，输出批次 ID。
2. **快照生成参数**：在每次生成请求时，对 prompt 和参数取哈希存入 `assets.json` 的 `prompt_hash`，方便回归测试场景快速定位批次。
3. **自动清理策略**：当归档目录超过设定容量或天数，可以通过 cron 任务清理旧批次。建议清理前先同步到持久存储（如对象存储）。
4. **与 OpenClaw 集成**：如果你在为 OpenClaw 写自定义插件，可以在 `on_post_generated` 事件中挂载归档逻辑，实现零感知归档。

## 总结

本地归档看似是一件不起眼的小事，但在自动发帖流水线进入高频运行时，它直接决定了可观测性和可恢复性。一个稳定的文章、图片与 `assets.json` 归档结构，让每次生成都有迹可循，也让调试、迭代和迁移成本大幅降低。对工程习惯而言，花半小时写好归档模板，远比日后在混乱目录中恢复丢失内容合算。
