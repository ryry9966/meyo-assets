## 背景

在构建基于 Agent 的自动化内容发布系统时，我们会遇到这样的场景：LLM 根据需求生成 Markdown 文章，另一个工具链生成配图，最后通过 API 将内容同步到多个平台（个人博客、社交媒体、邮件通讯等）。整个过程高度自动化，但也带来了一个新问题——你找不到一条帖子的“原始版本”了。

Agent 生成的内容往往经过多次修改：提示词调整、图片重新生成、格式化修正。如果只在发布前临时保留，很容易出现以下情况：

- 内容丢失，想复盘或复用某篇高质量帖子，发现原始 Markdown 已被覆盖
- 图片链接使用的是临时云存储 URL，几天后失效，本地没有备份
- 不同平台需要的格式不同，但缺少一份统一的“信源”来转换
- 协作时别人不知道某篇内容的历史素材放在哪里

因此，在一个工程化的 Agent 流水线中，**本地归档**不应是事后补救，而应该作为关键中间步骤内建到流程中。

## 问题拆解

具体来说，我们需要解决三个问题：

1. **内容版本混乱**：多次生成导致不同版本散落，没有明确的“最终版”
2. **资源丢失或不可追溯**：AI 生成的图片没有元数据记录，时间久了不知道对应的提示词和生成参数
3. **分发困难**：发布到平台时需要重新整理格式，却找不到干净的 Markdown 和本地图片路径

## 归档方案设计

我们采用**每帖一目录**的归档结构，核心是 Markdown 文件、图片文件夹以及一个 `assets.json` 元数据文件。

推荐的目录结构：

```
local_archive/
└── 2024-12-11-automation-archiving/
    ├── index.md              # 最终版 Markdown
    ├── images/
    │   ├── cover.png
    │   ├── diagram.png
    │   └── workflow.png
    └── assets.json           # 元数据及资源清单
```

**命名规范**：目录名采用 `YYYY-MM-DD-slug`，避免重名且便于排序。slug 来自标题的英文缩写，如果标题是中文，则可用拼音或自定义英文关键词。

`assets.json` 的作用是结构化记录所有资源，足以支撑后续的搜索、重发或格式转换。一个最小示例：

```json
{
  "id": "2024-12-11-automation-archiving",
  "title": "自动发帖流水线的本地归档方案",
  "date": "2024-12-11",
  "tags": ["agent", "automation", "archiving"],
  "status": "published",
  "versions": [
    {
      "version": "1",
      "timestamp": "2024-12-11T10:00:00Z",
      "note": "initial generation"
    }
  ],
  "assets": {
    "images": [
      { "file": "images/cover.png", "prompt": "A minimalistic archiving pipeline diagram", "size": "1024x1024" },
      { "file": "images/diagram.png", "prompt": "Flowchart of local archiving process", "size": "1024x768" }
    ],
    "markdown": "index.md"
  }
}
```

有了这份清单，后续任何下游脚本都能直接读取 `assets.json` 来获取图片路径、原始提示词和版本记录，而不必解析 Markdown 或依赖文件名。

## 实现步骤

将归档逻辑整合到 Agent 工作流的“生成后、发布前”阶段。

### 1. 定义归档根目录

在部署 Agent 的环境中设置环境变量 `ARCHIVE_ROOT`，例如 `/data/content_archive`。所有归档操作都基于这个路径。

```bash
export ARCHIVE_ROOT=/home/user/openclaw-archive
```

### 2. 创建文章专属目录

在 Agent 的流程中，生成 Markdown 正文和图片后，先确定 slug。简单脚本：

```python
import os
from datetime import datetime

slug = "2024-12-11-automation-archiving"
post_dir = os.path.join(os.environ['ARCHIVE_ROOT'], slug)
os.makedirs(os.path.join(post_dir, "images"), exist_ok=True)
```

### 3. 保存 Markdown 并修正图片路径

Agent 生成的 Markdown 中图片可能使用临时 URL 或绝对路径。归档时必须替换为相对路径，并将图片文件移动到 `images/` 下。

流程：

- 解析 Markdown 中的图片链接（正则 `!\[.*\]\((.*)\)`）
- 将每个图片下载（如果是远程 URL）或复制（如果是本地临时路径）到 `images/` 文件夹，并赋予规范名称，如 `01_cover.png`, `02_diagram.png`
- 替换原链接为 `./images/xxx.png`

示例 Python 代码片段：

```python
import re, shutil, requests
from pathlib import Path

def archive_images(md_text, images_temp_dir, dest_images_dir):
    image_urls = re.findall(r'!\[.*\]\((.*?)\)', md_text)
    for i, url in enumerate(image_urls):
        if url.startswith('http'):
            resp = requests.get(url)
            filename = f"img_{i+1}.png"
            with open(os.path.join(dest_images_dir, filename), 'wb') as f:
                f.write(resp.content)
        else:
            # 本地临时文件
            src_path = Path(images_temp_dir) / url
            filename = f"img_{i+1}.png"
            shutil.copy(src_path, os.path.join(dest_images_dir, filename))
        # 替换路径
        md_text = md_text.replace(url, f"./images/{filename}")
    return md_text
```

### 4. 生成 assets.json

利用生成文章时的上下文（标题、日期、标签、图片提示词等），写入统一的元数据文件。确保 JSON 格式合法，便于程序读取。

```python
import json

asset_data = {
    "id": slug,
    "title": title,
    "date": datetime.now().strftime("%Y-%m-%d"),
    "tags": tags,
    "status": "draft",
    "versions": [{"version": "1", "timestamp": datetime.now().isoformat(), "note": "first archive"}],
    "assets": {
        "images": [{"file": f"images/img_{i+1}.png", "prompt": prompt} for i, prompt in enumerate(image_prompts)],
        "markdown": "index.md"
    }
}
with open(os.path.join(post_dir, 'assets.json'), 'w') as f:
    json.dump(asset_data, f, indent=2, ensure_ascii=False)
```

### 5. 发布适配器读取归档

在发布步骤中，不再依赖 Agent 内存中的临时数据，而是直接从本地归档读取。可以编写一个通用的 `Publisher` 基类，根据平台需求将 Markdown 转换为 HTML、纯文本或适配特定格式，图片路径则自动处理为平台要求的格式。

## 踩坑记录

在真正跑通这套方案时，有几个实际痛点：

- **图片反代与缓存**：如果图片由云端 AI 服务生成，直链可能被限制访问或短期有效。必须第一时间下载归档，不要只保存 URL。
- **路径转义**：Markdown 中的图片路径如果含有中文或空格，在部分发布平台会出错。归档时统一重命名为 ASCII 短名称，并避免特殊字符。
- **Git 大文件处理**：很多人会把归档目录纳入 Git 管理。图片多时仓库膨胀很快，建议搭配 Git LFS 或仅归档文本元数据，图片另外存储并做增量备份。
- **版本冲突**：归档步骤如果被多次触发（重试、二次生成），可能覆盖已有文件。我们采用先检查目录是否存在，若已有则自动创建带时间戳的版本子目录，并在 assets.json 增加版本记录。

## 可复用建议

1. **将归档逻辑封装为 MCP 工具或独立脚本**，让 Agent 只需调用一个 `archive_post(markdown, images, metadata)` 接口，降低耦合。
2. **assets.json 模板化**：根据项目需求定义标准字段，例如增加 `platforms` 字段记录已发布状态，方便后续重发。
3. **增加归档校验步骤**：归档完成后自动检查 assets.json 中声明的图像文件是否存在、Markdown 内引用的相对路径是否正确，避免“归档了但实际残缺”的情况。
4. **扩展为多业态归档**：如果同时做视频脚本、播客 shownotes，可扩展目录结构为 `video/`, `audio/` 子目录，对应的 assets.json 中增加媒体类型字段。

## 总结

自动发帖流水线很容易让人们沉迷于“一键发布”的快感，却忽视了内容资产本身的管理。引入本地归档机制，并不会增加太多工程成本，但能显著提高内容生产的可维护性和可复用性。一个清晰、机器可读的 `assets.json` 加上标准化的文件组织，让自动化不再是黑盒，而是可追溯、可信赖的工程实践。

在 OpenClaw 社区中，我们提倡把每个 Agent 步骤都做得“有迹可循”，本地归档正是这一理念的落地方式之一。
