## 背景：一条消息推出去之后，你还剩什么

如果你已经搭过基于 OpenClaw、MCP 服务或多 Agent 协作的内容发布流水线，大概率经历过这样的状态：Agent 调用完 Notion、飞书或 WordPress API，文章发出去了，通知也到了企业微信，但本地什么也没留下。下一次想回溯某篇推送的完整上下文，或者将一篇图文复用到另一个平台，只能从线上重新抓取。

更麻烦的是图片。大多数流水线里，图片要么以 URL 形式在 body 中传递，要么临时生成后直接上传到三方 CDN。几乎没有流水线会把这些二进制资产在本地做结构化归档。当图片链接失效、CDN 目录被清理、或者服务侧进行资源迁移时，你的内容生态就多了一批“有文无图”的残本。

这就引出一个工程问题：如何在不增加 Agent 调用成本和流程复杂度的前提下，让一条自动发布流水线在“推出去”的同时，也在本地留下完整、可离线重建的归档——包括正文、图片，以及描述它们关系的元数据文件？

## 问题拆解：要归档的不仅仅是 `.md`

自动发帖流水线的产出物通常包括：

- 一篇完整的文章正文（Markdown 或 HTML）
- 正文中引用的本地图片（或已上传后的远程 URL）
- 标题、摘要、标签、发布时间等元信息
- 可能存在的多平台适配版本（例如公众号版、Twitter 版、社区帖子版）

如果只保存一个 `.md` 文件，图片依然是脆弱的，而且后续处理时必须重新解析图片引用关系。因此一个合理的归档目标应该是一个**自包含目录**，其中包含：

1. `post.md` —— 文章正文，图片引用由远程 URL 替换为本地相对路径。
2. `assets/` —— 所有引用的图片，按原始文件名或哈希命名存放。
3. `assets.json` —— 描述文章与图片的映射关系，用于下游工具读取和重建。

这样一来，归档目录本身成为一个可交互的静态快照，可以直接交给其他 Agent 或脚本使用，而不依赖任何外部服务。

## 做法与步骤：让归档成为流水线的内置步骤

这里给出一个可复用的实现思路，基于 Node.js 脚本或 OpenClaw 的本地工具链，核心步骤四步走。

### 1. 定义归档任务为流水线的显式阶段

在现有流水线中（例如 GitHub Actions、自建 cron 触发的 Agent 调用脚本）增加一个 `archive` 步骤。不要在发布逻辑里隐式做归档，因为发布可能失败，归档必须是“只依赖已成功发布的内容”的后置行为。一个典型的流程：

- Agent 生成内容 → 内容审核通过 → 推送平台 → 平台返回成功状态 → 触发本地归档脚本。

如果发布失败，流水线直接终止，不产生归档垃圾。

### 2. 构建归档目录结构

为每篇文章生成一个基于日期和 slug 的唯一目录名，例如 `2025-04-12-topic-slug/`。脚本从发布成功的 payload 中提取标题、正文 Markdown、标签、平台 URL、发布时间等字段，写入 `post.md`。

此时正文中的图片引用大概率是远程 URL（例如 `https://cdn.example.com/images/abc.png`）。不要急于替换，先完成下载。

### 3. 图片下载与本地化引用

用正则提取文章内所有 `<img src>` 或 Markdown `![alt](url)` 中的图片 URL。对每个 URL：

- 发起 HEAD/GET 请求，检查响应状态码和 Content-Type，只下载 `image/*` 的资源。
- 使用原始文件名或基于 URL 路径/哈希生成唯一文件名，保存到 `assets/` 目录。
- 在内存中建立 URL → 本地文件路径 的映射。
- 下载结束后，遍历整个 `post.md` 文本，将所有图片 URL 替换为 `./assets/文件名` 的相对路径。

这一步要注意去重：同一张图片可能在文中出现多次，不要重复下载。

### 4. 生成 `assets.json`

`assets.json` 的结构应尽量简单但清晰。推荐格式：

```json
{
  "id": "2025-04-12-topic-slug",
  "title": "xxx",
  "created_at": "2025-04-12T10:30:00Z",
  "platform": "wechat",
  "platform_url": "https://...",
  "tags": ["automation", "openclaw"],
  "images": [
    {
      "original_url": "https://cdn.example.com/abc.png",
      "local_path": "assets/abc.png",
      "alt_text": "图片描述",
      "checksum": "sha256:..."
    }
  ]
}
```

这里的 `checksum` 字段在归档时计算（如 SHA-256），用于后续完整性校验。这个 JSON 同时也是其他工具的消费接口，你的“旧文重发器”、“多平台适配器”都可以通过只读取这个文件和对应目录来还原内容，而不用解析 Markdown。

## 踩坑点

**跑不通的下载与 403 限流**  
一些图片 CDN 会对非浏览器 UA 或高频请求返回 403，并限制单 IP 并发。建议下载时设置合理 UA，并使用串行请求或控制并发数为 2，避免触发风控。另外，如果某种原因确实下载不了，不要中断整个归档，本地化失败时保留远程 URL 并在 `assets.json` 的 `local_path` 标记为 `null`，防止丢失信息。

**大图与超时导致流水线卡死**  
曾经遇到过一张 20MB 的无压缩截图，下载耗时超过 30 秒，导致整个流水线日志超时。解决方案是设定下载超时（如 10 秒）和文件体积上限（如 5MB），超过时跳过并在 metadata 里记录警告。归档不是 CDN 备份，牺牲全量比流水线不可用更重要。

**相对路径的跨平台问题**  
在 Windows 和 Linux 混合环境下跑流水线时，注意路径分隔符一致性。替换路径时统一为正斜杠 `/`，并使用 `path.posix.join` 来构造输出，防止出现反斜杠导致的 Markdown 渲染问题。

**增量归档的混乱**  
如果流水线重跑历史数据，要小心已有归档目录。建议归档前检查目录是否存在，如果存在则保留旧文件并重命名，比如加上 `.old` 后缀或创建带时间戳的子目录，避免旧数据被静默覆盖，方便事后比较差异。

## 可复用建议

- **把归档逻辑做成 MCP 工具或独立脚本**。不要和发布脚本耦合，让它成为一个接受 JSON 输入、输出归档目录的通用工具。你可以直接把它注册到 OpenClaw 的工具链里，让 Agent 完成发布后自行调用：“归档这篇文章，把所有图片拉到本地”。
- **利用 `assets.json` 做下游自动化**。一旦有了这个结构化元数据，构建“从本地归档一键发布到其他平台”的流程就很简单。下游脚本读取 `assets.json`，拿图片文件直接上传到目标平台的图床，并替换回 Markdown 图片引用，无需重新解析正文。
- **版本化归档目录**。把归档目录纳入 Git 管理（例如放到 `archives/` 下），就可以得到每篇文章的修改历史。结合 CI，可以在每次 commit 时用 `assets.json` 的 `checksum` 做完整性校验，捕捉无声的图片损坏。
- **保持最小依赖**。图片下载和 JSON 构建完全可以用 Node.js 内置 fs、path、https 模块实现，不需要引入额外库，方便在受限环境中部署。

## 总结

自动发帖流水线的本地归档，本质是将发布行为从一个单向的输出动作，变成一个“可回放、可审计、可复用”的工程闭环。文章的正文是主资产，图片是易损的依赖，`assets.json` 则是连接它们并使归档可编程的关键抽象。

不需要一个庞大的内容管理系统，一个轻量的脚本加上明确的目录约定，就能让每一条自动发出的帖子在本地留下完整的影子。当你的 Agent 不仅能发帖，还能归档，你实际上是在为整个自动化内容系统构建一个可靠的离线语料库。

下一次你想让 Agent 翻出半年前的一篇推文，改改图片重新发到 Discord，你只需要指给它一个文件夹路径，以及一个 `assets.json` 文件。
