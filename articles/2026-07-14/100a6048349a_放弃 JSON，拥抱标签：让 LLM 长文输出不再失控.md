## 背景：当 JSON 成为自动化链路的“堵点”

在 OpenClaw / Agent / MCP 这类自动化系统中，LLM 的输出往往需要被下游程序消费。最自然的选择是让模型输出 JSON——机器的“母语”。然而一旦输出变长，JSON 就开始频繁出错：少一个引号、多一个逗号、括号不匹配、文本中的换行未转义，甚至直接在中途截断。结果就是解析器报错，整个 pipeline 崩溃，重试成本极高。

多次重试后我们开始反思：JSON 的严格语法可能是与 LLM 自回归生成模式天然冲突的。当模型逐 token 生成上百行字符串时，它没有全局视野来保证每个括号成对、每个逗号位置正确——尤其当内容中包含代码、对话、列表等复杂文本时。

## 问题：为什么 JSON 在长文中尤其容易“坏掉”？

LLM 生成 JSON 失败的根本原因在于：

- **状态不可回溯**：模型在生成第 500 个 token 时，无法回看第 3 个 token 的引号是否闭合。
- **转义地狱**：内容里出现 `"` 或 `\n` 是家常便饭，要求模型每次都完美转义，是强人所难。
- **缺少容错空间**：JSON 解析器遇到一个错误就全盘拒收，即使后面 90% 的数据是好的。
- **流式输出加剧截断**：在实际部署中，我们常把 LLM 输出接入 stream，chunk 边界可能恰好切断 JSON 结构体，导致解析器看到半截的数组或对象直接失败。

这些痛点并非“提示词没写好”，而是格式特性与生成过程的根本矛盾。在自动化场景中，我们要的不是一个漂亮的工程示范，而是 `99.9%` 的可解析率。

## 做法：用标签格式构建容错“安全网”

我们最终将输出格式从 JSON 切换为 **基于标签的结构化文本**，类似于 XML 但更自由。例如：

```
<summary>
这是一段摘要，内容可以包含任意字符，甚至 <bold> 这样的尖括号。
</summary>

<steps>
<step>
<title>安装依赖</title>
<code>pip install openclaw</code>
</step>
<step>
<title>配置 MCP</title>
<pre>
{
  "server": "example.com"
}
</pre>
</step>
</steps>
```

核心思路是**不要求整个文档是一棵合法语法树，只要求每个区块有明确的起止标记**。这样解析器可以按标签提取内容，单个区块的损坏不会污染其他区块。

### 步骤 1：设计标签体系

根据业务需要定义一套正交的标签名，避免与内容产生冲突。例如：

- `<analysis>` 包裹分析过程
- `<tool_call>` 包裹工具调用参数
- `<result>` 包裹最终返回给用户的文本

标签名尽量生僻或在 prompt 中要求模型用大写或固定前缀，如 `OC_FINAL_ANSWER`，减少与内容中的自然语言标签碰撞。

### 步骤 2：编写 prompt 模板

不再要求模型输出 JSON，而是要求它按给定标签结构回答。示例：

```
你需要用以下格式回复，不要省略任何标签：

<reasoning>
你的推理过程
</reasoning>

<answer>
最终答案
</answer>

重要：内容中若出现尖括号，请转义为 &lt; 和 &gt;。
```

提示词越明确，标签闭合率越高。实测中，复杂嵌套可以折叠成扁平结构，降低模型记忆负担。

### 步骤 3：实现容错解析器

放弃标准 XML 解析，自定义一个基于正则或状态机的轻量级解析器，核心逻辑：

1. 用正则 `r'<tag>(.*?)</tag>'` 提取内容（开启 `re.DOTALL`）。
2. 处理标签不闭合的情况：若找不到结束标签，则从起始标签后截取到文档末尾，并标记“可能未完整”。
3. 流式解析时维护一个标签栈和缓冲，当 `</` 出现时触发回调。

在 Python 中可以封装一个简单的类，提供 `extract_section(text, tag)` 方法，内部处理未闭合、重复标签等异常，返回 `Optional[str]` 及完整性标志。这样上层可以决定是重试还是使用部分结果。

## 踩坑点实录

- **标签冲突**：模型有时在回答里写入 `<`, `>` 等字符，未转义。解决方案：在 prompt 中要求转义成本太高时，改用 `[[summary]]` 这种双括号格式，或使用 `##|` 作为前缀。另一种方式是用后处理扫描内容，对已知标签名外的尖括号自行转义。
- **嵌套深度过深**：如果结构是 `<list><item><value>` 这种深层嵌套，模型很容易漏掉结束标签。实践建议：**最多两层嵌套**，复杂数据用标记列表逐项输出。
- **流式截断**：chunk 边界恰好切在标签名中间（例如 `</summ` 然后下一个 chunk 是 `ary>`）。解析器需要在缓冲中保留未完成的标签片段，采用滑动窗口匹配，并设定超时避免阻塞。
- **模型不“听话”**：少数情况下模型会忽略标签直接输出纯文本。此时需要检测输出中是否包含必需的起始标签，若无则直接终止并重试，或者回退到纯文本处理。

## 可复用建议

1. **为 OpenClaw/MCP 动作定义标签模板**：比如 `<tool name="search">` 可以包裹参数，然后用解析器提取，比 JSON 容错得多。
2. **提供解析器组件**：封装成一个插件或工具函数，供所有 agent 节点调用，统一容错逻辑。
3. **结合约束采样（constrained sampling）**：像 `guidance` 或 `outlines` 这类库能保证标签闭合，但会增加延迟。对实时要求不高的长文生成，可以在关键节点使用。
4. **混合模式**：对短小的工具调用参数依然使用 JSON（因为成功率高），而对长文本输出（如报告、对话生成）切换为标签格式。
5. **监控闭合率**：在日志中记录每类标签的闭合成功率，持续优化 prompt 边界。

## 总结

JSON 是机器间的完美格式，但不是 LLM 长文输出的最佳选择。改用标签格式后，我们的解析成功率从 `~85%` 提升到 `99%` 以上，重试次数降低了一个数量级。这项改动成本极低：只改了 prompt 和解析逻辑，却使整个自动化管线的鲁棒性跃升。

对于每个正在用 LLM 构建可靠系统的工程师而言，或许该重新审视那个看似“标准”的 JSON 输出策略了。给模型一个更“宽容”的结构，往往比逼它生产完美 JSON 要聪明得多。
