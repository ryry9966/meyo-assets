# 背景

在搭建 OpenClaw 或 Agent 驱动的自动发帖流水线时，大多数人的关注点都放在内容生成、多平台分发、定时调度上。每次跑完一批帖子，本地往往只留下一串控制台日志，然后所有内容都“飘”在远端。等到需要回溯某条帖子用的是哪张图、某个提示词产出的效果如何、或者想拿历史帖子做二次加工和微调用，才发现手上根本没有结构化的本地副本。

对于自动化这条链路，本地归档不是“锦上添花”的存储，而是工程化最基本的可观测性与可复用基础。这篇文章给出一个具体、可落地的本地归档方案：每次发帖任务生成一个文件夹，里面统一存放 Markdown 正文、图片资源以及描述文件 `assets.json`。

# 问题拆解

不归档或随手存，会遇到几个典型痛点：

1. **图片丢失或不可追溯**：远端图片链接可能过期，或者发帖后 CDN 链接未被保存，无法本地复查。
2. **内容与元数据分离**：帖子正文在一个 txt 里，图片在另一个目录，提示词、模型配置在脚本参数里，想复盘一条帖子需要打开三四个地方。
3. **无法作为数据集复用**：当你想拿历史帖子做 fine-tune、作为 few-shot 示例、或者跑回归测试时，缺少结构化的原始数据。

因此，一个合理的归档方案需要把文章、图片和任务元信息以 **自包含** 的方式存放在一起，并且能用极低的成本解析和读取。

# 目录结构设计

每次发帖任务生成一个归档文件夹，命名建议用 `{日期}_{slug/uuid}`，例如 `20250321_how-to-build-agent`。内部结构固定如下：

```
20250321_how-to-build-agent/
├── post.md            # Markdown 格式的帖子正文
├── images/
│   ├── cover.png
│   └── diagram.png
└── assets.json        # 描述文件，记录所有素材和元信息
```

`post.md` 里图片引用使用相对路径，方便本地直接预览，例如：
```markdown
![架构图](./images/diagram.png)
```

`assets.json` 的 schema 类似这样：
```json
{
  "id": "uuid-or-slug",
  "title": "How to Build an Agent",
  "created_at": "2025-03-21T10:30:00Z",
  "content_file": "post.md",
  "images": [
    {
      "local_path": "images/cover.png",
      "original_url": "https://cdn.example.com/abc.png",
      "description": "cover image",
      "prompt": "a futuristic architecture diagram, clean style"
    },
    {
      "local_path": "images/diagram.png",
      "original_url": null,
      "description": "generated by code",
      "prompt": null
    }
  ],
  "metadata": {
    "source": "openclaw-agent-v2",
    "model": "claude-3.5-sonnet",
    "generation_prompt": "Write a technical blog post about...",
    "post_targets": ["twitter", "wechat"]
  }
}
```

`images` 数组保留原始 URL，便于日后迁移或重新下载；`metadata` 里可以塞任何你想存档但不需要硬解析的键值，尽量把生成参数塞进去。

有了这种结构，无论你用 Python、Node.js 还是 OpenClaw 的工具链，后续读取都只是一次 `json.load` + 一次 `open`。

# 实现步骤

在自动化脚本或 Agent 插件里落地归档，可以抽象成一个函数：

1. **确定任务文件夹**：根据任务 ID 或标题生成文件夹名，创建目录。
2. **处理正文**：拿到生成的 Markdown 文本，扫描出所有图片链接（正则或 AST 解析），先不替换。
3. **下载图片**：遍历图片链接，依次下载到本地 `images/` 文件夹。文件名用原 URL 的哈希（比如 MD5 前 8 位）加正确的扩展名，避免重名和注入。如果原 URL 无扩展名，要根据响应的 `Content-Type` 追加。
4. **替换图片引用**：将 Markdown 里的远端图片链接一次性替换为相对路径 `./images/filename`。
5. **写出 post.md**。
6. **构造 assets.json**：填充图片对象列表、metadata 等，写出文件。
7. **返回归档路径**，日志里记一条。

如果用 Python，大致逻辑如下（简化演示）：

```python
import os, json, hashlib, requests
from pathlib import Path

def archive_post(post_md: str, images_urls: list[str], metadata: dict, root="archives"):
    # 生成文件夹名，假定 metadata 里提供 id
    folder = Path(root) / f"{metadata.get('date', 'no-date')}_{metadata.get('id', 'tmp')}"
    folder.mkdir(parents=True, exist_ok=True)
    img_dir = folder / "images"
    img_dir.mkdir(exist_ok=True)

    image_entries = []
    for url in images_urls:
        try:
            resp = requests.get(url, timeout=10)
            resp.raise_for_status()
            ct = resp.headers.get("Content-Type", "")
            ext = guess_extension(ct, url)  # 自己实现的后缀推断
            filename = hashlib.md5(url.encode()).hexdigest()[:8] + ext
            local_path = img_dir / filename
            local_path.write_bytes(resp.content)
            image_entries.append({
                "local_path": f"images/{filename}",
                "original_url": url,
                "description": "",
                "prompt": None
            })
            # 替换 Markdown 链接
            post_md = post_md.replace(url, f"./images/{filename}")
        except Exception as e:
            print(f"[WARN] download {url} failed: {e}")
            # 保留原链接，记录到 assets 里标记为 missing

    (folder / "post.md").write_text(post_md, encoding="utf-8")

    assets = {
        "id": metadata.get("id"),
        "title": metadata.get("title", ""),
        "created_at": metadata.get("date"),
        "content_file": "post.md",
        "images": image_entries,
        "metadata": metadata.get("extra", {})
    }
    (folder / "assets.json").write_text(json.dumps(assets, ensure_ascii=False, indent=2), encoding="utf-8")

    return str(folder)
```

在 OpenClaw 的 Agent 上下文里，你可以把这个逻辑封装成 MCP 工具，让 Agent 在发帖成功后调用。如果不想自己写，可以用 `run_python` 等内置能力直接执行上述函数。

# 遇到的坑

1. **图片下载失败不阻塞**：远端链接可能短暂 503、DNS 问题，超时后应记录异常并保留原始链接，而不是让整个归档中断。否则你会因为一张图片下载失败丢整篇帖子存档。
2. **文件名冲突和注入**：不要直接用原始文件名（包含空格、中文、`../` 等），统一用哈希或 UUID。扩展名根据 `Content-Type` 映射，比如 `image/png` => `.png`，否则某些图片打开会出错。
3. **Markdown 图片链接未完整替换**：如果 Markdown 里同一个 URL 出现多次，需要全部替换；如果用 `replace` 可能误伤其他地方的相同字符串，最好用更准确的 Markdown 解析（如 `mistune`）定位图片节点，直接修改 AST 再导出。对大多数简单场景，全局替换即可，但需注意。
4. **assets.json 编码**：务必 `utf-8` + `ensure_ascii=False`，否则中文标题会被转义，后续直接阅读体验极差。
5. **并发写目录**：如果你的流水线是多进程并发发帖，归档写入时要避免两个任务共用同一文件夹名。用唯一 ID（UUID）作为文件夹名最稳妥，日期只做前缀方便检索。

# 可复用建议

这套归档方案可以提炼成一个独立模块或 OpenClaw 社区插件，只需暴露出一个标准接口 `archive(post_data)`。内部可配置项：

- 归档根目录路径
- 图片下载重试次数与超时
- 是否在归档后清理临时缓存
- 输出日志级别

建议给归档过程加一个 `dry_run` 选项（仅模拟，不写磁盘），方便在流水线测试阶段验证路径和文件非冲突。

另外，如果你的发帖流水线是多语言的，`assets.json` 里可以加 `lang` 字段；如果某些图片是 AI 生成而非网络下载，`original_url` 可以为 `null`，并在 `prompt` 字段记录生成提示词，这个习惯对后续复盘提示词效果极有帮助。

# 总结

本地归档这件事几乎没有技术门槛，但它决定了你半年后能不能迅速翻出某条帖子的完整上下文去做复盘、二次创作或合规审计。对于每天都在运行的自动化内容系统，缺少结构化的本地存档，就像开车没装行车记录仪——平时无所谓，出事就想哭。

方案的核心就三点：

- 一个自包含的文件夹，包含正文、图片和元描述文件
- 将图片远程链接替换为相对路径，让本地方便打开
- 把生成参数、模型、目标平台等信息收录进 `assets.json`

把这个流程内嵌到你的 Agent 或脚本里，每次发完帖自动多一个归档文件夹，几乎零维护成本。等下次需要“重发三个月前那篇帖子但换一套配图”，你直接找到 `assets.json` 里的 `generation_prompt` 跑一遍新模型，就能快速闭环。
