## 背景

Agent 编排、MCP 工具链和各类自动化插件，让脚本能够直接读写本地文件系统。能力越强，风险越大。一个模型驱动的 Agent 完全可能在指令或提示词的引导下，去读取 `/etc/passwd`、遍历 `.ssh` 目录，甚至写入关键配置。即便只是内部测试环境，失控的文件访问也可能导致数据泄露或环境破坏。

单纯靠“信任模型输出”并不现实，最早期的沙箱方案往往直接给 Agent 挂载一个隔离的 Docker 容器或临时目录，但对于需要频繁访问固定项目目录的自动化场景，这种一刀切的办法会降低效率。更实用的做法是：在文件系统调用链路上，加入一层**目录白名单检查**，确保 Agent 只能访问你授权过的目录及其子目录。

## 问题拆解

我们以一个典型的 Python MCP 文件工具为例：它通过 `read_file`、`write_file`、`list_directory` 等工具函数与本地文件交互。如果不加限制，任何一个路径参数都可能指向系统任意位置。

我们希望实现：

- 定义一个或多个允许访问的**白名单根目录**（如 `~/project/data`、`/var/agent-output`）。
- 任何文件操作前，将传入的路径解析为**绝对路径**，并展开所有符号链接。
- 仅当解析后的路径以白名单根目录开头时，才允许继续执行，否则抛出权限错误。
- 处理 `..`、`~`、软链接等常见的目录穿越手法。

## 实现步骤

### 1. 定义白名单配置

使用环境变量或配置文件，方便运维时调整，不硬编码：

```python
import os

DEFAULT_WHITELIST = [
    os.path.expanduser("~/allowed-data"),
    "/var/agent-workspace",
]
WHITELIST = [
    os.path.realpath(p)
    for p in os.getenv("AGENT_FILE_WHITELIST", "").split(":")
    if p
] or DEFAULT_WHITELIST
```

通过 `os.path.realpath` 把白名单本身规范化，避免符号链接导致误判。

### 2. 路径规范化与校验函数

核心函数要实现三步：展开用户目录 → 绝对路径 → 解析符号链接，然后检查是否在任意白名单前缀内。

```python
import os
from pathlib import Path

def is_path_allowed(user_path: str) -> bool:
    # 1. 展开 ~ 等用户快捷路径
    expanded = os.path.expanduser(user_path)
    # 2. 转为绝对路径，注意 join 以 cwd 为基准
    abs_path = os.path.abspath(expanded)
    # 3. 解析所有符号链接
    real_path = os.path.realpath(abs_path)

    # 4. 检查是否以任一白名单开头
    for allowed in WHITELIST:
        # 防止部分匹配：allowed=/var/data, real_path=/var/database
        # 通过 commonpath 判断
        if os.path.commonpath([real_path, allowed]) == allowed:
            return True
    return False
```

这里用 `os.path.commonpath` 比较公共前缀，能准确防止 `/var/data` 和 `/var/database` 的误判，比字符串 `startswith` 更安全。

### 3. 集成到文件工具

在每一个 MCP 工具函数的入口处调用 `is_path_allowed`，拒绝即抛出异常，让外部捕获并转换成标准的错误响应。

```python
def safe_read_file(file_path: str) -> str:
    if not is_path_allowed(file_path):
        raise PermissionError(f"Access to {file_path} is not allowed by whitelist")
    with open(file_path, 'r') as f:
        return f.read()
```

同样地，`list_directory` 也需要对传入的目录进行校验，而不是只校验返回的文件列表（因为目录本身可能就是越权的入口）。

### 4. 处理 Windows 兼容

如果 Agent 运行在 Windows 上，需要额外注意：

- 大小写不敏感：`os.path.realpath` 在 Windows 上会保留系统实际大小写，可以用来做匹配，但比较时应使用 `os.path.normcase`。
- 盘符与分隔符：使用 `pathlib.PureWindowsPath` 统一处理，并确保白名单目录也用 normcase 处理。

可以通过条件分支针对不同平台规范化路径，核心逻辑保持不变。

## 踩坑记录

### 坑1：符号链接瞒天过海

某次测试中，我们在白名单目录下创建了一个指向 `/etc` 的软链接，Agent 通过 `list_directory` 遍历并读取了该软链接指向的文件。根本原因是：我们起初只在检验时用了 `os.path.abspath`，未调用 `realpath` 解析链接目标。解决方案就是如上强制使用 `realpath`。

### 坑2：路径拼接中的相对路径攻防

如果工具允许“相对路径”传入，攻击面更大。比如，Agent 传入 `./../../etc/passwd`，若直接 `os.path.join(allowed_dir, user_path)` 再检查，可能因为拼接后才越权。正确的顺序：**基于当前工作目录解析用户输入，得到绝对路径并 realpath，然后才做白名单校验**，而不是与白名单目录拼接。

### 坑3：白名单配置热加载被忽略

部分团队把白名单写在代码常量里，部署后需要改目录就得重新构建镜像。建议一定从环境变量或配置中心读取，且支持多个路径。同时提供启动时的校验日志，打印出实际生效的白名单，方便排错。

## 可复用建议

- **封装成独立中间件**：检查逻辑不要散落在每个工具函数里，抽成 `FileAccessGuard` 类，统一入口，方便测试和复用。
- **审计日志**：在拒绝访问时记录日志，包含请求路径、解析后路径、匹配到的白名单（或未命中），便于安全审计。
- **白名单最小化原则**：只允许必要的目录，并定期审查。可以用 `tree` 或脚本导出目录结构，确认没有误放出敏感文件。
- **与 Agent 权限体系结合**：如果你的 Agent 支持“角色”或“环境标签”，可以结合白名单实现更细粒度的访问控制。
- **提供只读/读写模式**：除了目录白名单，还可以加入访问模式（r/rw），进一步降低风险。

## 总结

给自动化脚本加本地目录白名单，不是银弹，但它是 Agent 安全实践中最基础也最容易被忽视的一环。用规范化的路径解析 + 真实路径解析 + 公共前缀匹配，就能抵御大部分目录穿越和符号链接绕过。结合工程化的配置管理和审计日志，可以低成本地提升文件访问安全。

代码量很小，却能为你的 Agent 增加一道实实在在的护栏。值得在下一个自动化项目里立即落地。
