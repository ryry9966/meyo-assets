## 背景：一个每天都在发生的“解析失败”

在 OpenClaw 这类多 Agent 或插件自动化系统中，我们经常要求大语言模型输出结构化数据——可能是多段摘要、分类标注、步骤规划，或者一份包含多个部分的报告。为了让下游流程可消费，最直接的想法往往是：“让它输出 JSON”。

于是你精心设计了 schema，在 prompt 里强调“只返回 JSON，不要解释”，还加上 JSON Mode、function calling。前几次测试一切正常。一旦任务变长——比如要求模型分析完一整篇几十 KB 的文档并输出多层次结构——噩梦就开始了：

- 某个对象的 `}` 缺席，整个文档无法 parse。
- 文本中出现的未转义引号撞坏 JSON 结构。
- 模型在数组最后一个元素后面多加了一个逗号。
- 在长文本中间突然插入了一句“Here is the requested JSON:”，污染输出。

更棘手的是，有些错误不是每次都发生。一次成功率在 85-90%，但对于无人值守的自动化流水线，这 10-15% 的失败意味着你要写一大堆重试、修复、正则后处理，甚至还要引入另一个模型做“JSON 修复员”。工程成本直线上升。

根本原因不只是模型不够严谨，而是 JSON 本身作为一种输出格式，对长文、多层级、含自由文本的场景来说**过于严格且不具容错性**。我们真正需要的，是一种既能承载结构化信息，又允许部分错误、容易恢复、模型更不易出错的格式。经过几个项目的反复试错，我发现使用**自定义标签格式**（类似 XML 但更宽松）是一个务实且稳定的替代方案。

## 问题拆解：为什么 JSON 容易在长输出中崩坏？

把问题摊开看，大致有这几个层面：

1. **上下文窗口长，注意力稀释**：当模型需要输出数百行 JSON 时，早期生成的 `{` 可能被后期注意力“遗忘”，导致括号无法闭合。
2. **嵌套深度大，模型计数困难**：多层对象和数组的括号匹配对于自回归模型来说并不轻松，尤其在自由文本穿插时。
3. **转义负担重**：如果 JSON 内部包含代码、引号、换行符，转义处理稍有不慎就导致无效 JSON。
4. **缺少自然分割边界**：JSON 是一个整体，只要一个字符出错就可能全盘皆输，很难部分恢复有用信息。
5. **提示词干扰**：模型在生成过程中容易“跳出角色”，输出类似“好的，下面是你需要的 JSON：”这样的前言，直接破坏格式。

这些问题并非不能缓解——例如通过结构化生成约束（grammar-guided decoding）可以大幅降低括号错误。但在实际工程中，我们不一定都能使用受限解码（比如 API 不支持，或需要快速切换模型）。此时，换一种“更宽松但结构清晰”的格式，往往能事半功倍。

## 做法：用标签格式替代 JSON

核心思路很简单：用自定义的标签头尾标记每个字段或段落，像这样：

```
<SECTION type="summary">
模型在这里输出总结内容，可以是多行，允许包含各种字符。
</SECTION>
<SECTION type="action_items">
- 第一项动作
- 第二项动作
</SECTION>
```

这种格式有一些明显优势：

- **有明确开始和结束标记**，解析时只需按标签分割，局部错误不影响其他部分。
- **不需要转义引号和换行**，只要内容不包含 `</SECTION>`（可选用更独特的标签名避免），就不会破坏结构。
- **模型更容易维持格式**：标签以 `<` 开头、`>` 结尾，对模型的 token 边界友好，且比 `{}` 和 `[]` 的平衡更容易学会。
- **允许自由文本和 Markdown 共存**，非常适合需要混合输出的场景。
- **容错解析很容易写**：如果某个标签未闭合，只需丢弃该段或取到下一个标签开始处，不会让整个结果报废。

实践中，我通常会设计两层标签：外层类似 `<OUTPUT>`，内层按语义定义 `<SECTION>`、`<KEY>`、`<VALUE>`，甚至可以用属性传递元数据，比如 `<STEP id="1">...</STEP>`。对于需要列表或多次重复的块，直接用同一标签名重复即可，解析端读到一个收集一个。

## 实施步骤与解析策略

以一个文档分析流水线为例，模型需要输出：整体摘要、关键发现、后续行动建议。我的 prompt 大概这样子：

```
基于以下文档，以标签格式输出分析结果，不要使用 JSON。
严格遵循格式：
<OUTPUT>
<SUMMARY>
这里写摘要
</SUMMARY>
<FINDINGS>
每条发现用一行，以减号开头
</FINDINGS>
<ACTIONS>
每条行动建议用一行，以减号开头
</ACTIONS>
</OUTPUT>
现在开始输出，不要添加任何额外说明。
```

解析部分（以 Python 为例）采用一个简单的状态机或正则即可：

```python
import re

def parse_tagged_output(text: str):
    # 提取 <OUTPUT> 块
    outer = re.search(r"<OUTPUT>(.*?)</OUTPUT>", text, re.DOTALL)
    if not outer:
        # 容错：如果缺少外层标签，尝试直接解析内层
        inner_text = text
    else:
        inner_text = outer.group(1)

    result = {}
    # 提取所有 SECTION 类型的标签
    for match in re.finditer(r"<(\w+)>(.*?)</\1>", inner_text, re.DOTALL):
        tag = match.group(1).lower()
        content = match.group(2).strip()
        if tag in result:
            # 如果同标签出现多次，自动转为列表
            if isinstance(result[tag], list):
                result[tag].append(content)
            else:
                result[tag] = [result[tag], content]
        else:
            result[tag] = content

    return result
```

这个解析器不关心标签顺序，也不要求所有标签都存在；缺失的字段就返回 None，上层的编排逻辑可以自行补默认值或告警。更重要的是，即使某个标签内部内容被截断（比如因为 token 限制），也只会影响该字段，不影响其它字段的提取。

## 踩坑点与注意事项

虽然标签格式大幅降低了解析失败率，但实践中有几个点仍然值得留心：

1. **标签名冲突**：内容中如果出现 `</SUMMARY>` 字符串会提前闭合。通过使用少见的标签名（如 `_@SUMMARY_@`）或基点的 UUID 后缀可以规避，但会降低可读性。我的经验是，用有语义的英文大写标签，同时要求模型“如果内容中需要出现标签本身，请用 `&lt;` 和 `&gt;` 转义”，模型通常能遵守。

2. **标签不闭合**：模型可能在达到 max_tokens 时停在 `</...` 中间。解析程序需要能容忍最后一个标签没有闭合，直接丢弃并记录日志。此外在 prompt 中强调“务必以 `</OUTPUT>` 结束”也能减少截断发生在关键位置。

3. **模型仍可能输出前言/后语**：虽然比 JSON 时的前言少，但仍有可能。解决方法是解析时只提取已知标签块，忽略其他文本。

4. **嵌套结构**：如果需要嵌套，标签格式会变得冗长且不易阅读。此时可以考虑浅层嵌套，或者结合 YAML 的方式（缩进敏感），但对于复杂嵌套关系，回到 JSON 并配合结构化约束可能是更佳选择。标签格式最适合**扁平或一层嵌套**的结构化输出。

5. **对上游工具的影响**：如果你构建的 Agent 下游接的是严格 JSON 接口，使用标签格式需要增加一个转换层。这个成本通常可以接受，因为稳定的解析远比格式转换消耗小。

## 可复用建议

经过多个自动化管线的打磨，我总结了几条可以复用的实践：

- **用顶层 `<OUTPUT>` 包裹所有内容**，这样解析时就有一个明确的提取范围。
- **字段名用大写英文名词，避免空格**，如 `<KEY_FINDING>` 而不是 `<key finding>`，减少模型漏写引号或空格的问题。
- **在提示词中给出一个完整示例**，并强调“严格遵循标签格式”。示例能让模型更稳定。
- **解析端永远做容错设计**：允许部分字段缺失，允许最后一个标签未闭合，记录异常但不中断流水线。
- **对于特别长的输出，考虑分段流式解析**。当接收 chunk 时，按标签缓冲，积累满一个闭合标签就向后续节点发送，这样还能降低首字节延迟。
- **建立标签注册表**：在一个项目内统一标签词汇，并形成文档，让不同 Agent 之间看到的输出结构一致，降低沟通成本。

## 总结

从 JSON 转向自定义标签格式，本质上是在模型输出的**严格结构化需求**与**自回归生成的非确定性**之间寻找一个更优平衡点。它并不试图让模型变成严格的序列化器，而是顺应模型的生成方式，用一种更宽松、更健壮的方式表达结构。在 OpenClaw 的自动化流程中，这种转变帮我将结构化输出的可靠率从约 90% 提升到 99% 以上，而付出的代价仅仅是编写一个几十行的标签解析器。

当你下一次被坏掉的 JSON 折腾得焦头烂额时，不妨试试给模型一些尖括号，说不定会柳暗花明。
