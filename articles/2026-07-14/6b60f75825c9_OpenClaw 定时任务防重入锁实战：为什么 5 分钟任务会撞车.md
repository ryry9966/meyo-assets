# 问题背景

在 OpenClaw 的自动化编排中，定时任务（Cron Job）常用于周期性触发 Agent 流水线，例如每 5 分钟同步一次外部数据源，再交给 MCP 工具链做处理。看上去间隔足够长，似乎不会出现并发执行，但在实际生产环境中，我们发现同一任务的两个实例会同时运行，造成数据错乱、下游工具调用竞争，甚至触发限流熔断。

这一类“撞车”现象的根因并不复杂：**任务的执行时间 > 调度间隔，且调度器没有做防重入保护**。当一次任务因为网络抖动、外部 API 延迟、Agent 推理耗时等原因刷过 5 分钟边界时，新的调度周期仍然会准时触发，最终形成两个或多个实例并行。

本文会从一个真实的 OpenClaw 生产案例出发，拆解问题的发生路径，给出基于 Redis 的轻量级防重入方案，并总结可复用的工程实践。

# 问题复现与定位

以 OpenClaw 内置的 `cron` 模块为例，配置如下：

```yaml
jobs:
  - name: data-sync
    schedule: "*/5 * * * *"
    action: run_agent_pipeline
```

正常情况下，每次执行耗时在 2 分钟以内，5 分钟间隔绰绰有余。但在最近一次上游数据源性能退化后，`run_agent_pipeline` 的平均耗时上升到了 6～7 分钟。结果我们很快在日志中看到同一 job 的两个 PID 同时存在，Agent 对同一批数据做了重复处理，MCP 工具调用也出现了幂等性异常。

我们可以简单画出时间线：

- 10:00:00 – 实例 A 启动
- 10:05:00 – Cron 触发实例 B，此时 A 仍在运行
- 10:06:30 – 实例 A 结束
- 10:07:00 – 实例 B 结束

两个实例在 10:05 – 10:06:30 之间是并行的。在传统后台任务系统中，这可以通过“互斥执行”来解决，即同一任务同时只能有一个实例在跑。

# 方案选型

在 OpenClaw 生态里，常见的防重入手段有三种：

1. **进程级文件锁**：简单但不适合多节点部署，且无法跨越 worker 容器。
2. **数据库乐观锁/悲观锁**：可靠但会引入额外 I/O，对高频任务不够经济。
3. **Redis 分布式锁**：性能好、易实现，与 OpenClaw agent 的 Redis 连接天然契合，也能为 MCP 服务提供一致的锁视图。

考虑到集群化部署和现有基础设施（通常 OpenClaw 已经依赖 Redis 作为消息队列或状态存储），我们选择 **Redis 锁**。

# 实现步骤

## 1. 约定锁键与超时

为每个定时任务定义一个唯一锁键，格式建议 `lock:cron:<job-name>`。锁的超时时间应该覆盖任务的**最大可能执行时间**，并加上一定缓冲。比如任务常态 2 分钟，但异常时可达 10 分钟，可以设置锁超时为 15 分钟，防止死锁。

```
key: lock:cron:data-sync
ttl: 900  # seconds
```

## 2. 获取锁的原子命令

使用 `SET key value NX EX ttl` 完成加锁。如果返回 OK，说明抢锁成功；如果返回 nil，说明锁已被持有，当前调度应跳过执行。

伪代码：

```python
def acquire_lock(redis_client, lock_key, instance_id, ttl):
    return redis_client.set(lock_key, instance_id, nx=True, ex=ttl)
```

## 3. 执行与释放

获取锁成功后，正常执行 Agent 管道；执行完成后主动释放锁，通过 Lua 脚本保证原子性：检查 value 是否匹配，避免错误释放其他实例的锁。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

## 4. 集成到 OpenClaw 任务定义

在 OpenClaw 的 cron 任务包装器（wrapper）中添加锁逻辑：启动时先尝试加锁，失败则记录日志并 return，不再执行实际管道。

## 5. 监控与告警

一段时间后，我们根据“锁跳过次数”设置告警：如果连续 3 个周期都因锁未释放而跳过，说明任务可能阻塞或死锁，需要人工介入。

# 踩坑点

## 1. 锁超时设置不当

默认设置 5 分钟的锁超时，结果某次下游延迟暴涨，任务跑了 8 分钟，锁自动过期，第二个实例闯入，再次撞车。最终改成 15 分钟才稳住场面。**经验**：锁超时必须 > P99 执行时间，并留有 buff。必要时可以在任务内部起一个守护线程“续期”锁，但这会大幅增加复杂度，在 OpenClaw 轻量化场景中一般用长 TTL 替代。

## 2. 锁释放误伤

早期实现直接 `DEL lock_key`，没有校验 value，导致实例 A 执行完毕后删除了实例 B 刚拿到的锁（因为 A 的锁超时刚过期，B 成功加锁）。改成 Lua 脚本按 instance_id 校验后再删除才安全。

## 3. 时区与系统时钟漂移

Redis 服务器与 OpenClaw 运行节点的系统时钟不同步，可能导致 TTL 判断不准。好在 Redis TTL 使用服务器自身时间，影响较小，但仍然值得统一 NTP 对时。

## 4. 任务的幂等性不是可选项

即使加了锁，仍然不能保证绝对无重复执行——例如锁提前过期、Redis 暂时不可用等边界情况。**因此下游的 Agent 操作、MCP 工具调用必须设计成幂等**，否则防重入锁只能减少概率，无法根治。

# 可复用建议

- **锁命名规范化**：`lock:cron:<job-name>`，并让所有节点使用相同的 Redis 实例。
- **封装库**：在 OpenClaw 内部将“获取锁、释放锁”的代码抽象为公共的 `CronLockManager`，供所有定时任务复用。
- **配置化**：锁超时、是否启用等参数放在 job 描述中，方便调整而无需改代码。
- **结合 OpenClaw 的 context**：利用 agent context 传递 instance_id（例如 `uuid4` 或者 `hostname+pid`），保证锁持有者标识唯一。
- **日志与可观测性**：在跳过执行时打印 `LOCK_SKIP` 级别日志，记入 metrics，配合 Prometheus 或 Loki 构建“跳过率”仪表盘。

# 总结

定时任务防重入锁在 OpenClaw 自动化实践中是一种低成本的可靠性提升手段。5 分钟间隔的任务撞车并非调度器 bug，而是工程中常见的时间重叠问题。通过引入 Redis 分布式锁，我们几乎无侵入地保证了同一任务串行执行，避免资源竞争和数据出错。

但锁不是银弹：合理的超时、安全的释放、幂等的下游操作，三者缺一不可。在 OpenClaw 社区的后续版本中，可能将这种锁机制内嵌到 cron 运行时里，以降低用户的实现成本。在此之前，按本文提供的模式封装即可在生产中稳定运行。
