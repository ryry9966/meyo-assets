## 背景

在自动化内容分发链路里，把图文同步到微博超话是一个高频需求。无论用于运营、数据分析回流还是 Agent 驱动的社交发布，都需要一个可靠的“发超话”执行单元。  
但微博的接口并不开放，图片上传流程、反爬策略和调用频率控制都比想象中要棘手。之前几次尝试用简单的 HTTP 请求拼凑，都卡在图片上传失败、触发 429 或者状态管理混乱上。  
后来基于 OpenClaw 的工具链重新梳理了一遍流程，把图片上传、限流和状态归档做了工程化拆分，现在稳定性达到可长期无人值守的水平。以下记录关键要点。

## 问题拆解

1. **图片上传路径不透明**：发帖需要先上传图片到微博图床，获取 `pid`，然后把 `pid` 拼进正文/元数据里。这个上传接口有独立的鉴权和频率规则。
2. **超话发帖需要特殊参数**：必须有超话的 `fid`，且正文格式要包含 `#超话名称#` + 特定标记，否则不会出现在超话时间线。
3. **限流严格**：不仅返回 429，一些看似正常的 200 响应里也会包含“操作频繁”的提示，不解析 body 就会误判成功。
4. **状态管理缺失**：并发场景下容易重复发帖或漏发，需要持久化记录每条内容的状态并保证幂等。

## 做法与步骤

### 1. 登录态维持与超话参数抓取

- Cookie 直接从浏览器导出（推荐手动更新，避免频繁登录触发验证码）。
- 超话 `fid` 可通过超话页面 URL 或搜索接口获取，写入配置文件。  
- 在每次任务开始前，做一次轻量探测请求（如访问个人主页），验证 Cookie 是否有效；失效则告警，不继续执行。

### 2. 图片上传

抓包得到的上传流程：

- 接口地址：`https://picupload.weibo.com/interface/pic_upload.php`
- 请求方式：`POST`，`multipart/form-data`
- 字段：`pic1`（文件流）、`app`（固定值）、`s`（固定值）等
- 响应 JSON 包含 `data.pics.pic_1.pid`

工程化实现注意点：

- 必须携带与浏览器一致的 `User-Agent`，同一 IP 地址下频繁更换 UA 会被提前限频。
- 图片需先转换为 JPEG 格式且控制在合理尺寸内（如宽度不超过 2048px），否则可能上传成功但后续发帖时被过滤。
- 上传成功后返回的 `pid` 有时效性，建议在获取后 5 分钟内完成发帖，否则可能失效。
- 将上传封装为独立函数，返回 `pid`，发帖函数只负责消费 `pid`，降低耦合。

### 3. 构造发帖请求与限流控制

发帖接口参数较复杂，核心字段：

- `text`：包含 `#超话名称#` + 超话入口标记（格式类似 `&#x0D;\nhttps://...`）
- `pic_id`：上一步得到的 `pid`
- `fid`：超话的 `fid`

限流策略采用**固定窗口 + 指数退避重试**：

- 通过 Redis/内存计数器控制每分钟最多 5 次发布（根据实测调整）。
- 请求返回 429 或 body 中出现“操作频繁”字样时，启用退避：首次重试等待 30s，逐次翻倍，最大等待 5 分钟；超过 3 次重试仍失败则标记为 `FAILED` 并触发通知。
- 为避免雪崩，所有发帖任务共用同一个限流器实例。

### 4. 状态归档

用 SQLite 维护一张 `post_tasks` 表：

```
id | content_hash | text | image_path | status | pid | fid | created_at | updated_at | retries
status: PENDING / UPLOADING / POSTING / SUCCESS / FAILED / DUPLICATE
```

- 任务生成时计算 `content_hash`（文本+图片路径的组合哈希），插入前检查是否已存在相同哈希且状态为 `SUCCESS`，若是则直接跳过，保证幂等。
- 状态流转用显式状态机，各步骤更新 `status` 和 `updated_at`，避免并发混乱。
- 定期清理一个月前的 `SUCCESS` 记录，控制库文件大小。

## 踩坑点

- **图片上传的跨域问题**：在浏览器环境调试通过，但在后端直接请求时，部分 header 缺失会导致 403。必须完整携带 `Referer` 和 `Origin`，模拟页面来源。
- **限流误判**：有些请求返回 200 但 body 里是操作频繁提示，需要做关键词检测，不能仅靠状态码。
- **超话 `fid` 变化**：某些超话可能在改名后 `fid` 不变，但少数会变动，需要提供自动更新的手段（如定时爬取搜索结果页同步）。
- **Cookie 时效**：如果不做定时健康检查，可能在任务堆积时突然全部失败。建议每 30 分钟自动校验一次，失效则暂停队列并告警。
- **图片格式**：上传前必须统一转为 RGB JPEG，勿带 alpha 通道，否则发布后可能只有文字没有图。

## 可复用建议

可以把这个发帖单元封装成一个 MCP 工具（`weibo_super_topic_post`），输入接受 `text`、`image_path`、`super_topic_name`，内部自动完成图片上传、限流等待和状态记录，返回 `{success, message, post_id?}`。  
在 OpenClaw 的 Agent 编排中，只需将生成好的内容作为参数传入，配合条件分支处理失败重试或人工审核，就能构建一个闭环的内容发布流水线。  
另外，限流器和状态机可抽象为通用模块，复用到其他需要频率控制和幂等保障的社交平台工具上。

## 总结

微博超话同步的自动化，难点不在“发一条”，而在长期稳定、不触发风控和可追踪。通过精细化的接口处理、主动限流设计和严格的状态管理，可以把它从“调试能跑”变成“线上可用”。这份实践同样适用于多数封闭式 UGC 平台的自动化接入，希望能给做类似尝试的同学一些参考。
