## 背景

日常运营中，经常需要把内容同步分发到微博超话。一条帖子从撰写完成到最终出现在目标超话里，中间隔着手动上传图片、补话题词、顾及发布频率等机械操作。为了把这些重复劳动交给 Agent，我在 OpenClaw 里接了一套针对微博超话的发帖流程：通过自定义工具调用微博 Web 接口，完成图片上传、文本发布与状态归档，同时用限流策略避免触发风控。

## 问题拆解

微博超话同步的核心工作可以拆成三块：

1. **图片上传**：微博发帖需要先上传图片获取 `pid`，再携带 `pid` 发起发表请求。上传接口与普通图床不同，对 cookie、referer、参数格式都有要求。
2. **接口限流**：微博对发帖频率敏感，连续高频调用会直接返回错误码，或触发验证码，导致后续请求全部失败。
3. **状态归档**：Agent 自行发帖后，需要记录哪些成功、哪些失败、失败原因，方便补发和回溯。没有状态归档，自动化就变成了“黑盒”，出问题只能人工翻微博主页核对。

## 做法与步骤

### 1. 图片上传工具

微博上传图片的入口是 `pic_upload.php`，关键点在于保持会话、传递正确的 `Referer` 和 `Content-Type`。

以 Python 为例，封装成一个 OpenClaw tool：

```python
import requests
from pathlib import Path

def upload_image_to_weibo(cookie_str: str, image_path: str) -> str | None:
    url = "https://picupload.weibo.com/interface/pic_upload.php"
    headers = {
        "Referer": "https://weibo.com/",
        "User-Agent": "Mozilla/5.0 ...",
        "Cookie": cookie_str,
    }
    with open(image_path, "rb") as f:
        files = {"pic1": (Path(image_path).name, f, "image/jpeg")}
        data = {
            "s": "txt",
            "app": "miniblog",
            "cb": "http://weibo.com/aj/static/upimgback.html",
            "mime": "image/jpeg",
            "data": "1",
        }
        r = requests.post(url, headers=headers, files=files, data=data, timeout=30)
    # 从返回的 script 标签中提取 pid
    ...
    return pid
```

- 使用 `requests.Session` 可以减少 cookie 手动拼接的麻烦，但 agent tool 中通常直接传入 cookie 字符串更可控。
- 返回结果不是标准 JSON，而是一段 JavaScript 回调。需要通过正则提取 `pid`。
- 图片大小最好控制在 5 MB 以内，过大会被拒绝。

### 2. 发帖到超话

发帖接口使用 `aj/mblog/add`，需要携带 `topic_id` 或直接在文本中插入超话话题词。

```python
def post_to_topic(cookie_str: str, content: str, pid: str, topic_id: str) -> dict:
    url = "https://weibo.com/aj/mblog/add"
    headers = {
        "Referer": "https://weibo.com/",
        "Content-Type": "application/x-www-form-urlencoded",
        "Cookie": cookie_str,
        "X-Requested-With": "XMLHttpRequest",
    }
    data = {
        "text": f"{content}#你的超话#",
        "pic_id": pid,
        "topic_id": topic_id,
        "pdetail": "",
        "rank": "0",
        "type": "json",
    }
    resp = requests.post(url, headers=headers, data=data, timeout=15)
    return resp.json()
```

- `topic_id` 可以提前从超话页面 H5 版 URL 中抓取并缓存。
- 注意添加 `#超话名#` 双井号，否则微博不认为发到超话内。
- 返回 JSON 中的 `code` 为 `"100000"` 表示成功，其他需根据具体错误信息处理。

### 3. 限流策略

微博接口限流并非公开的固定阈值，实测连续发帖间隔低于 30 秒时，第 3～4 条就会开始返回 `100001`（操作太频繁）。处理方案：

- **固定间隔**：每发一条休眠 45～60 秒，简单可靠。
- **带退避的重试**：遇到限流错误码，等待 90 秒后重试一次；仍失败则主动延迟 5 分钟，同时降低后续请求频率。
- **Agent 侧感知**：tool 返回限流状态时，可以附带建议等待时间，让上层调度决定是否暂停队列。

### 4. 状态归档

每条帖子执行完毕后，写入 SQLite 或本地 JSON 行文件：

| 字段 | 说明 |
|------|------|
| post_id | 微博返回的 mid |
| status | success / fail / rate_limited |
| content_hash | 内容简短哈希，用于去重 |
| pid | 图片 pid |
| timestamp | 发帖时间 |
| error_msg | 失败时的原始错误信息 |

这样，Agent 在下次需要补发时，可以读取未成功的条目，跳过已成功的内容，实现“至少一次”的交付语义。同时，人工也可通过简单 SQL 查询当天成功数量，不必登录微博核对。

## 踩坑点

1. **Cookie 有效期**：微博 Web 端 cookie 稳定性差，部分字段（如 `SUB`）短则几小时、长则几天。建议每隔 24 小时手动刷新一次，或者通过手机扫码登录页面获取长票，但不要完全依赖自动化换取。
2. **图片上传接口变化**：`pic_upload.php` 可能会间歇性返回空响应或 302，多与 `Referer` 或 UA 检测有关。保持头信息与浏览器一致可降低失败率。
3. **话题词匹配**：超话话题词如果写错（比如少一个“#”），帖子只会变成普通微博，接口不会报错。需要预先从超话列表抓取标准话题名，并做格式校验。
4. **验证码触发**：频繁发帖即使设置了 60 秒间隔，有时仍会弹出滑块验证码。目前只能暂停整个流程，人工过一下。可以实现“检测到验证码 → 发送通知 → 等待用户处理后再继续”的半自动机制，但不建议硬机器过。

## 可复用建议

- 将上传图片和发帖分别封装为两个独立的 OpenClaw tool，入参只暴露 `cookie`、`image_path`、`text`、`topic_id`，返回统一的 `{"status": ..., "result": ...}` 结构。
- 限流逻辑放在 tool 内部，避免 Agent 需要理解重试策略。tool 对外表现为同步调用，Agent 只需等结果。
- 状态归档可以做成一个共享的本地存储，所有工具都往里写，然后配合另一个只读工具 `get_failed_posts` 实现自动补发。
- 如果同时管理多个微博账号，务必把 cookie 与账号 ID 绑定，归档表也加上 `account` 字段。

## 总结

在微博超话同步这个场景里，工程上的挑战不是“能不能发出去”，而是“如何在可控的代价下发得稳、失败可恢复”。通过封装图片上传、限流退避和状态归档三个模块，我实现了一套可交付 Agent 使用的微博发帖工具。经过两周运行，成功率稳定在 95% 以上，剩余失败主要来自 cookie 过期和偶然验证码。对希望用 OpenClaw 管理社交分发的同学，这个实践可以参考：把脏活藏在 tool 里，把决策留给 Agent，把状态暴露给日志。
