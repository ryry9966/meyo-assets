## 1. 背景

在内容分发自动化里，同步到微博超话是个高频需求。对很多 OpenClaw 用户来说，Agent 生成的图文内容需要自动灌入垂直社区，超话是绕不开的一环。微博没有给个人开发者开放超话发布 API，只能通过模拟网页或客户端的请求来完成这一步骤。

结合 OpenClaw 的工具链，我们可以把“发布到超话”封装成一个 MCP 工具（或者简单的自动化脚本），由 Agent 在合适的时机调用。这个工具需要处理三个老大难问题：**图片上传**、**限流对抗**，以及**同步状态归档**——否则帖子要么被吞，要么重复发送，要么账号进小黑屋。

这篇文章记录我在真实工程中实现这三部分的路径、踩过的坑，以及可复用的思路。

## 2. 核心问题

把一条图文帖子发到一个指定超话，拆开后是下面这些子任务：

- 获取一个有效的登录态（Cookie）
- 上传若干张图片，拿到图片 ID（pid）
- 构造发布请求，携带文本、超话 ID、图片 pid
- 处理限流响应，合理安排发布节拍
- 将每次发布结果持久化，避免重复、追溯失败

每个环节都有微博接口的非文档化规则和隐性限制。

## 3. 实现步骤

### 3.1 整体工具形态

如果用 OpenClaw，我会把发布逻辑写成一个 MCP Server 里的 tool，参数很简单：

```json
{
  "content": "帖子正文 #超话名称#",
  "images": ["/path/to/img1.jpg", "/path/to/img2.png"],
  "topic_name": "超话名称"
}
```

工具内部完成取 Cookie、上传、发布、归档。Agent 只负责决策何时调用。

### 3.2 图片上传

微博网页版上传图片的接口本质仍然是 `multipart/form-data`。请求大致形态：

```
POST https://picupload.weibo.com/interface/pic_upload.php
params: app=miniblog&data=1&url=...
mime: multipart/form-data
body: file binary data
```

关键点：

- **Cookie 要求**：必须有 `SUB` 和 `_s_tentry` 等核心字段，最好从扫码登录后导出完整的 cookie jar。
- **图片预处理**：尺寸建议控制在 1200px 宽以内，格式统一转成 JPEG，体积小于 5MB。直接用 Pillow 做 resize/convert，避免微博侧压缩导致菊花转圈。
- **pid 提取**：返回的 JSON 里取 `data.pics.pic_1.pid`，9 位字母数字组合，后续发布时需要带上。

我踩过一个坑：多张图片上传时，不能用并发请求同时传多张。微博要求串行上传，否则可能触发风控，返回 `-100` 或者直接空白页。做法是顺序上传，之间间隔 300~500ms。

### 3.3 发布到超话

发布超话的接口与普通发博略有不同，需要在请求中注入 `topic_id` 和相应的 `extparam`。具体请求形如：

```
POST https://weibo.com/aj/mblog/add?ajwvr=6
Content-Type: application/x-www-form-urlencoded
body包含：
  text: 正文（必须包含超话双#话题#）
  pic_id: pid1|pid2|...
  topic_id: 数字id
  isReEdit: false
  ...
```

超话的 `topic_id` 可以通过搜索接口或者从超话主页 HTML 里提取。

**注意事项**：

- 正文必须包含该超话的标准话题格式 `#超话名称#`，否则提示“不能为空”或直接发布失败。
- 如果发布按钮变灰，大概率是 `pic_id` 缺失或格式错误（比如 pid 之间不是 `|` 分隔）。
- 返回 JSON 里 `code == "100000"` 表示成功，`data` 中会带有 `mid`（微博 ID），必须拿到并归档。

### 3.4 限流处理

微博对单个账号的发布频率有硬限制，普通账号大约 3~5 分钟一条。更严格的是**超话频控**，一个账号在多个超话之间是共享限额的。

我的对抗策略：

- **令牌桶 + 响应头探测**：每次发布后解析响应头的 `X-RateLimit-Remaining`、`X-RateLimit-Reset`（大多数时候没有……），退而求其次用固定冷却时间。
- **固定间隔**：目前比较稳定的做法是硬间隔 `280s`（约 4 分 40 秒）。用 `asyncio.sleep` 或简单的定时器实现。
- **失败重试**：遇到 `-100` 或 `20010` 错误码（常见的风控码），等待 10 分钟并切换 User-Agent 再试。连续失败 3 次则中止，标记故障并告警。

值得一提的是，Cookie 老旧也会加剧限流现象。微博的风控会把低频老号当成可疑号进行更严格的限制，所以维持一个“活跃”的登录态（偶尔手动点点赞）能显著降低发布失败率。

### 3.5 状态归档

为了避免重复同步同一个内容，以及追溯失败原因，我用了一个本地的 SQLite 表：

```sql
CREATE TABLE IF NOT EXISTS post_archive (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    content_hash TEXT NOT NULL,
    topic_id TEXT NOT NULL,
    mid TEXT,
    images TEXT,
    status TEXT DEFAULT 'pending',
    error_msg TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(content_hash, topic_id)
);
```

流程：

1. 发布前计算 `content+images` 的 SHA256，检查 `content_hash + topic_id` 是否存在，存在则跳过。
2. 发布成功：更新 `status='success'`，记录 `mid`。
3. 发布失败：记录 `error_msg`，状态 `'failed'`，后续定时重跑。

这个小归档表也是 Agent 可以查询的，比如“已同步列表”，方便做增量决策。

## 4. 踩坑汇总

- **Cookie 丢失**：网页版 Cookie 有效期实际非常短（1-2天），需要模拟手机扫码登录或用 App 抓取的 token 来延长周期。建议定期自动刷新登录，或者使用一个“主控浏览器”配合 Playwright 定期导出 cookie。
- **图片上传大作战**：某些图片上传看似成功，实际上 pid 为空。原因是图片被微博认定为“异常图片”（例如纯文本截图可能被当成广告）。增加轻微噪声或裁剪白边可解决。
- **并发导致乱序**：如果同时跑多个进程，可能同时上传图片，造成同一个 Cookie 的登录态冲突。用单线程队列，或者请求锁来解决。
- **超话 ID 变更**：偶尔超话主题合并或改名，`topic_id` 会失效。可以通过搜索接口动态查找，而不是硬编码。
- **限流误判**：有时候并不是限流，而是请求体字段格式错误导致报 `-100`，迷惑性很强。每改一个参数都要严格核对上一步抓包的值。

## 5. 可复用建议

- **队列异步化**：把发布请求丢进消息队列（如 Redis + RQ），消费者按固定频率消费。失败可以重入队列。这样 Agent 调用只负责“投递”，不用等待结果。
- **监控与日志**：记录每次发布请求的完整请求头和响应体，接入简单的监控（比如 Prometheus + Grafana），观察成功率、冷却时间异常等。
- **MCP 标准化**：在 OpenClaw 中，这个发布工具可以做成 `post_to_weibo_supertopic` 的 MCP tool，返回 `{success, mid, error}` 的标准化结构，方便 Agent 解析。
- **灰度降级**：如果图片上传失败，降级为纯文本发布；如果再失败，归档后发通知人工介入，避免整个流水线阻塞。

## 6. 总结

在无官方 API 的情况下，自动化同步超话是一个需要耐心逆向和工程化打磨的过程。核心是封装好图片上传的串行逻辑、制定保守但可靠的重试机制，以及用轻量归档表来管理状态。配合 OpenClaw 的工具调用能力，这套方案可以在无人值守的情况下，稳定地将内容分发到多个超话。只要能容忍一定的发布延迟，就能把一个人手需要 10 分钟的操作，变成 Agent 一句话调度的事情。
