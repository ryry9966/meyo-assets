## 背景

在围绕 OpenClaw 构建自动化 Agent 时，常常需要将生成的内容推送至社交媒体，微博超话是许多垂直场景的重要阵地。相比普通的微博发布，超话同步涉及图片上传、话题标签格式、频率控制以及同步状态的持久化追踪。直接用微博开放平台的 API 调用虽然可行，但如果不做工程化封装，很快就会被限流、重复发布或图片上传失败等问题淹没。

本文基于 OpenClaw 的 MCP 生态，实现了一个可被 Agent 调用的微博超话同步工具，重点处理图片上传的稳定性、接口限流的可控性，以及每一次同步操作的状态归档。

## 问题分解

接入微博开放平台后，主要会碰到三类工程问题：

1. **图片上传链路脆弱**：微博要求先通过 `statuses/upload` 上传图片获取 `pid`，再将 `pid` 填入发微博的参数。上传接口对图片大小、格式、并发处理都很敏感，出错时只会返回千篇一律的 error，难以快速定位。
2. **限流毫无反馈**：未认证的普通应用每天发博总数、每小时发博数和连续发博间隔都有默认限制。一旦触碰限制，接口会直接拒绝服务，但没有明确的配额回显，自动化过程极易变成“盲打”。
3. **状态无法回溯**：同步成功或失败后，没有日志归档，难以判断某条内容是否已发出，重试时容易造成重复发布，也阻碍了运维排障。

## 做法与步骤

### MCP 工具设计

在 OpenClaw 的 MCP Server 中，我们使用 Python + `fastmcp` 封装两个工具：`upload_image` 和 `post_to_supertopic`。Agent 在规划同步任务时，先调用图片上传获取 `pid`，再调用发帖工具拼接 `#超话名称#` 标签完成发布。

```python
from fastmcp import FastMCP
mcp = FastMCP("weibo-sync")

@mcp.tool()
async def upload_image(image_path: str) -> dict:
    # 压缩、校验、上传，返回 pid 和原始尺寸
    ...

@mcp.tool()
async def post_to_supertopic(content: str, topic: str, pid: str) -> dict:
    # 拼接标签，调用 statuses/update，归档结果
    ...
```

Agent 只需要组合这两个 API，就能完成一次超话图文同步。MCP Server 自身维护 access_token 的自动刷新（使用环境变量中的 `WEIBO_APP_KEY` 和 `WEIBO_APP_SECRET`，通过 `oauth2/access_token` 续期），对外部透明。

### 图片上传的健壮处理

上传接口地址为 `https://upload.api.weibo.com/2/statuses/upload.json`，采用 `multipart/form-data` 方式。踩坑后的稳定做法是：

- **前置压缩**：用 Pillow 将图片长边限制在 1280px，大小压缩至 5MB 以下，并统一转换为 JPEG。微博对 PNG 透明度支持不稳定，且上传 GIF 会变成静态图。
- **校验**：检查图片 MD5，避免因代理或缓存导致重复上传。
- **重试与退避**：上传失败时，先等待 2 秒再重试，最多 3 次，并将每次的 HTTP 状态码和响应体记入日志，便于排查是否是 token 失效或图片违规。

### 限流状态机

微博发博接口 `statuses/update` 没有公开确切的频率阈值，但实测规律是：同一用户两次发博间隔小于 30 秒时容易触发「操作太频繁」错误；连续发博超过 5 条后，下一小时会被临时限制。因此工具内部实现了一个基于时间的槽位限流器：

- 每次发博前，记录上一次发博时间戳。
- 如果距上次不足 45 秒，则 Agent 侧的调用会自动 sleep 补齐缺口。
- 对每小时内的发博数做计数，达到阈值后抛出明确的 `RateLimitError`，由 Agent 决定是否排队等候或降级为草稿。

这种显式限流避免了“静默失败”，让 Agent 能够依据错误类型规划后续行为。

### 状态归档

每一次 MCP 工具调用返回前，都会在本地文件系统写入一条 JSON 记录：

```json
{
  "ts": "2025-04-07T10:32:01Z",
  "tool": "post_to_supertopic",
  "input": {"content":"...","topic":"OpenClaw日常"},
  "status": "success",
  "weibo_id": "5222345678901234",
  "pid": "b3a4f..."
}
```

采用年-月-日滚动的 JSON Lines 文件，结合 `logrotate` 形式管理。归档的另一个用处是：在发起发布前，Agent 可以查询近 1 小时内的归档，通过比较内容哈希避免发布重复内容，实现轻量的去重。

## 踩坑记录

1. **超话标签规则**：`#超话名称#` 必须出现在微博文本开头或结尾，否则可能被识别为普通话题，导致同步到个人主页而非超话广场。工具会强行将标签预置在文本最前面，并移除多余空格。
2. **图片 pid 时效**：上传得到的 `pid` 仅在短时间内有效，若上传后超过 5 分钟未使用，发博时会返回「图片不存在」。因此 Agent 必须将上传和发博作为原子流程调用，中间不宜插入长耗时操作。
3. **应用权限**：测试阶段使用的 app 未通过文案审核时，发博接口会返回“应用没有发博权限”，需要去开放平台添加“测试账号”白名单，不要在正式使用时踩坑。
4. **Error 语义模糊**：微博 API 的错误码经常笼统，例如 `10022` 可能是 IP 限制或内容含有敏感词。我们在 MCP 工具中增加了一层映射表，将常见 error_code 转换为 OpenClaw 可理解的描述，提升 Agent 决策质量。

## 可复用建议

- **限流组件独立化**：将限流器抽象成一个通用的 `RateLimiter` 类，支持令牌桶和滑动窗口，可以复用给所有微博 API 调用，甚至用于其他 MCP 工具。
- **采用结构化日志中间件**：在 `fastmcp` 的工具装饰器中加入请求/响应拦截，自动记录每次调用，避免手动在业务中穿插 print。
- **健康检查端点**：MCP Server 增加一个只读工具 `health_check`，返回当前 token 状态、限流余量、最后归档时间，方便 Agent 在开始同步前进行预检。
- **容器化部署**：将整个 MCP Server 打包为 Docker 镜像，通过环境变量注入密钥，可以快速在不同 OpenClaw 实例间迁移。

## 总结

微博超话同步的工程化重点不在于 API 调用本身，而在于对图片上传脆弱性、隐式限流和状态不可见这三个痛点的治理。通过 OpenClaw 的 MCP 机制，我们将这些治理逻辑封装为可组合的工具，使 Agent 能以可控、可观测的方式完成同步。这套实践同样适用于其他需要对接社交媒体平台的自动化场景，只需替换相应的 API 接口与限流参数即可复用。
