## 背景

在内容分发场景里，微博超话仍然是一个不能被忽视的半封闭阵地。我们有一批技术向的短内容，需要定时同步到多个超话，配上封面图或截图，既为了曝光，也为了形成可检索的信息沉淀。手动一条条发帖，遇到图片压缩、格式报错、频繁拦截，非常消耗精力，于是决定用 OpenClaw 的能力把整个流程自动化。

这个同步链路看起来很简单：拿到内容→处理图片→发帖→记录结果。但实际落地时，图片上传的隐性规则、接口的限流策略、以及长时间运行下的状态管理，才是真正的工程难点。下面把这三个核心问题的拆解和最终落地方案记录下来。

## 问题定义

1. **图片上传**：微博的图片上传不是简单的 multipart/form-data 就可以搞定，它要经过一个预埋的图床上传流程，需要特定的 Cookie、Referer、以及图片格式校验，稍有不符就会返回模糊的错误码。
2. **限流**：超话发帖接口有严格的频率和单日总量限制，不同超话的策略还不一样。单纯 sleep 固定的时间，不是被夹就是触发验证码，最终被封 IP / 封号。
3. **状态归档**：自动化任务一旦跑起来，可能会因为网络抖动、Cookie 失效、限流触发等原因中断。如果没有可靠的状态记录，重跑时不是漏帖就是重复发帖，清理起来很痛苦。

## 做法与步骤

### 整体架构
我们用 OpenClaw 的 **Agent + MCP 工具** 模式，把发帖能力封装成一个微博超话发布工具，接受 Markdown 内容、图片 URL 列表和目标超话参数，内部完成图片上传和发帖，把结果返回给 Agent 并写入本地 SQLite 状态库。

* 内容准备：Agent 解析 Markdown 中的图片链接，如果是外链先下载到临时目录。
* 图片上传：调用图片上传工具，模拟微博 PC 端或移动端上传流程，获取 `pid`。
* 发帖：拼接文案 + 图片 pid，请求超话发帖接口，处理响应。
* 状态归档：无论成功还是可重试失败，都写入 `task_log` 表，包含状态、时间戳、错误信息、重试次数。
* 重试 & 退避：被限流时按指数退避等待，状态置为 `waiting`，到期后由调度器重新触发。

### 图片上传踩坑点

- **Cookie 与登录态**：上传必须携带有效的登录 Cookie，Cookie 会定期过期。我们在工具里增加了 Cookie 预热和有效性检查：每次任务前先访问一次微博首页，如果被重定向到登录页则刷新 Cookie（通过手动预置的更新接口）。
- **Content-Type 与 Referer**：上传接口要求 `Content-Type: multipart/form-data`，同时要求 `Referer` 必须为 `https://weibo.com/` 或超话内页，否则返回 `100005` 这种非标准错误。需要把图片重命名为符合微博规则的格式（如 `.jpg`）并设置正确的 MIME 类型。
- **图片大小与尺寸**：超过 5MB 的图片会被拒绝，返回“图片过大”，同时某些接口对宽度 <= 2000px 的图片会进行更强的压缩。我们统一在前置处理阶段用 Pillow 将图片缩放至宽 1200px 以内并转为 JPEG 质量 85。

### 限流应对策略

微博超话的发帖限制并不是简单的“每 N 秒一次”。实践中发现同账号在同 IP 下高频发帖，大概在第 3~5 次后会触发较长时间的限流（非 429，而是返回“操作频繁”的 HTML 页面）。我们采用了 **令牌桶 + 动态退避** 的组合：

- 默认每个超话发帖间隔不低于 120 秒；
- 如果收到限流响应，等待时间翻倍，状态置为 `rate_limited`；
- 相同超话失败 3 次后，标记为 `blocked` 并告警；
- 全局维护当天已发总量，超过每个超话的日上限后自动暂停。

限流期间不能空转等待，Agent 可以切换到其他超话或执行其他任务，最大化利用时间片。

### 状态归档设计

状态表结构很简单：

```sql
CREATE TABLE task_log (
    id INTEGER PRIMARY KEY,
    content_hash TEXT,      -- 内容唯一标识
    super_topic TEXT,
    status TEXT,            -- pending/uploading/posting/success/rate_limited/failed
    retries INTEGER DEFAULT 0,
    error_msg TEXT,
    created_at DATETIME,
    updated_at DATETIME
);
```

- `content_hash` 用于幂等，避免同一条内容被重复提交；
- 每次状态变更都会更新 `updated_at`；
- 重试时只选取 `status IN ('pending', 'rate_limited', 'failed') AND retries <= 5` 的记录；
- 成功的记录保留，用于统计和回溯。

这个归档方式足够轻量，不需要额外的消息队列，所有任务状态在本地 SQLite 文件中一目了然。

## 可复用建议

1. **抽象为标准插件**：把微博上传和发帖封装成 MCP 工具，对外暴露 `post_to_super_topic` 这一个 action，内部处理图片上传、Cookie、限流。如果你的 Agent 需要跨平台分发，这层抽象非常重要。
2. **Cookie 池化**：如果有多个账号，可以设计一个小型 Cookie 管理器，自动检测失效并切换。
3. **退避策略配置化**：退避时间、重试次数、每日上限等都做成可配置参数。不同超话差异很大，写死在代码里维护噩梦。
4. **增加干运行模式**：先不实际发帖，只走通上传和生成请求体，输出等待审核，方便调试。
5. **监控与告警**：将状态归档数据接入 Healthchecks 或简单的 Webhook，一旦 `blocked` 或大量失败及时通知。

## 总结

这个微博超话同步链路从“写个脚本调用 API 就行”的初步设想，到最后变成一个能稳定运行数周的 Agent 工具，经历最多的就是边界条件打磨。图片上传的合规性、限流的不可预测、状态丢失导致的漏发，这些都不是技术难点，而是工程完备性的考验。用 OpenClaw 的好处是，当这些能力被封装成可控的工具后，后续任何需要微博发布的 Agent 都能直接调用，不必再重复踩坑。

如果你也在做类似的社交平台自动化，希望这篇记录能帮你少走一些弯路。
