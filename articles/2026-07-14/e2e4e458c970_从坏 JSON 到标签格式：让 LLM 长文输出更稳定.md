# 从坏 JSON 到标签格式：让 LLM 长文输出更稳定

在自动化流水线、OpenClaw Agent 或多步工具调用中，我们经常依赖 LLM 输出结构化数据。JSON 看似是天然的选择，但在长文本、嵌套结构或流式输出场景下，JSON 的稳定性会急剧下降。本文将分享一种工程上被反复验证的替代方案：使用自定义标签格式作为中间表示，再可靠地转换为 JSON。

## 一、坏 JSON 的真实来源

JSON 格式对 LLM 并不友好，原因包括：

- **括号配对压力**：长输出中遗漏一个 `}` 或 `]`，整个解析立即失败。
- **转义混乱**：文本内容中包含引号、反斜杠时，LLM 经常忘记转义或过度转义。
- **截断风险**：流式输出或上下文窗口边界处，JSON 通常被截断为无效片段。
- **嵌套深度**：深层嵌套对象容易让模型“迷失”层级。

在 OpenClaw 插件或 MCP 工具中，一次 JSON 解析失败可能导致整个工作流退出，且错误难以优雅降级。与其不断加固 JSON 重试逻辑，不如换一种更适合 LLM 的结构化表达方式。

## 二、标签格式的设计原则

标签格式本质上是一种轻量标记，类似 XML 或自定义 Tag。LLM 在处理标签时有天然优势：

- 开始和结束标签成对出现，但容错性高，哪怕缺少闭合，也能用正则尽量提取。
- 标签名可以自描述，降低模型输出错误标签的概率。
- 文本内容只要避开标签分隔符即可，转义需求极低。

示例输出结构：

```
<response>
  <summary>这是一个分析结果</summary>
  <details>
    <item>要点一</item>
    <item>要点二</item>
  </details>
</response>
```

这在长文输出中远比 JSON 容易被 LLM 正确生成。

## 三、实施步骤

### 1. 设计标签 Schema

根据业务需要，定义唯一、不易冲突的标签名。建议使用统一前缀，如 `o_` 或项目名缩写，避免与文本中的自然语言混淆。例如：

```
<otask_summary>...</otask_summary>
<oitems>
  <oitem>...</oitem>
</oitems>
```

### 2. 编写 Prompt 与示例

在系统提示中明确要求使用标签格式，并提供 1-2 个完整示例。关键点：

- 强调“只输出标签结构，不要任何额外解释”。
- 展示嵌套如何正确闭合。
- 如有流式需求，提示可以分块输出，但必须完整闭合标签后暂停。

### 3. 实现标签提取器

从 LLM 响应中提取标签内容，推荐用非贪婪正则或简单状态机。核心逻辑：

```python
import re

def extract_tag(content: str, tag: str) -> str | None:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    match = re.search(pattern, content, re.DOTALL)
    return match.group(1).strip() if match else None
```

对于嵌套结构，可以递归提取。若标签缺失闭合，可以回退为提取从 `<tag>` 到文本末尾的内容，并记录告警。

### 4. 转换为下游 JSON

提取到结构化文本后，再按约定映射为 JSON。这种分步处理最大好处是：标签解析和 JSON 构造完全解耦，即使标签内容还需二次解析，也能在可控的局部处理。比如 `<item>` 列表可直接拼接为数组。

## 四、踩坑记录

- **标签名与内容冲突**：如果标签名恰好出现在正文中，会导致误匹配。解法是使用长且唯一的标签名，如 `<openclaw_result_v1>`。
- **模型不遵守格式**：偶尔输出缺少结束标签或把标签名写错。务必在提取时做模糊匹配，例如查找所有类似 `<tag>` 的模式，取内容首尾。
- **流式标签不完整**：流式输出时标签可能被分割在多个 chunk 中。需在接收端缓冲，直到匹配到闭合标签或超时。
- **特殊字符**：如果内容包含 `<` 或 `>`，LLM 可能意外生成标签。可以在后处理中将正文区域的非法标签符号转义，但更建议在 prompt 中提示模型用实体引用或避免使用尖括号。

## 五、可复用的工程建议

- **统一标签解析适配器**：为 OpenClaw 工具写一个通用标签解析层，输入预期标签结构，自动提取并校验。
- **多级回退策略**：先尝试完整标签解析，失败后尝试 JSON 解析，再失败返回原始文本供人工处理。这比单靠 JSON 脆弱得多。
- **测试集覆盖边界**：在开发阶段，构建包含截断、缺失标签、深度嵌套、特殊字符的测试样本，确保解析器鲁棒。
- **日志标注**：当发生标签不完整时，记录原始输出和提取位置，方便后续优化 prompt。

这种标签格式方案已经在多个内部 Agent 长时间运行中表现稳定，特别是需要输出 2000+ token 的结构化报告时，JSON 失败率从约 15% 降低到 1% 以下。

## 六、总结

标签格式并不是要取代 JSON，而是作为 LLM 输出的“可靠结构化媒介”。它降低了模型在长文本下的认知符合，封装了格式解析的复杂度。在 OpenClaw/Agent 这类对自动化稳定性要求极高的场景中，这种务实的小改进常常能省去大量的重试与异常处理逻辑。与其花时间修补坏 JSON，不如一开始就选择更适合 LLM 的格式。

下次当你的流水线又因为一个意外的 `\` 或缺失的 `}` 中断时，不妨试试标签格式。
