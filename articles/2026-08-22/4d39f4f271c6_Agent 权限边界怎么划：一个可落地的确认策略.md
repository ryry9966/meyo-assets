## 背景

OpenClaw 这类 Agent 框架让工具调用和 MCP 集成变得非常方便。一个 Agent 可以读文件、查数据库、发 HTTP 请求、执行 shell 命令，甚至操作浏览器。但方便的另一面是：**Agent 的默认行为往往比我们想象的更“主动”**。一旦工具权限给得宽，它可能在没人看的时候删了表、改了配置、往生产环境发了一堆请求。

现在很多实践都在讨论“给 Agent 加权限控制”，但真正容易出问题的不是“要不要控制”，而是**控制粒度怎么定**。问多了，自动化变成半自动；问少了，一次误判就是事故。

## 问题

实践中通常有两类失败：

1. **该问不问**：Agent 拿到一个 `write_file` 或 `execute_command` 权限，直接把不可逆操作执行了。
2. **不该问乱问**：每次写临时文件、查只读接口都弹确认，用户疲劳后开始无脑点“允许”。

所以权限边界不应该只是“危险工具要确认”，而是一套**按风险和可逆性分级的确认策略**。

## 做法/步骤

### 1. 先给工具分级，而不是给工具名分类

不要一看到 `rm`、`drop` 就禁止，也不要因为工具叫 `read` 就完全放心。建议按三个维度判断：

- **影响范围**：只影响当前会话 / 当前目录 / 整个系统 / 外部服务
- **可逆性**：能否安全回滚，有没有备份、版本控制、审计日志
- **副作用**：是否触发外部副作用，比如发邮件、扣款、发布上线

然后分成四级：

| 级别 | 示例 | 默认策略 |
|------|------|----------|
| L0 只读 | `read_file`、`search`、`select` | 自动执行 |
| L1 局部可逆写 | 写临时文件、创建本地缓存、草稿保存 | 自动执行，但必须留日志 |
| L2 影响面较大但可回滚 | 修改仓库文件、更新配置、批量重命名 | 可自动，但建议 dry-run 或 diff 预览 |
| L3 不可逆 / 高影响 | 删除生产数据、执行 shell、发请求到外部 API、发布上线 | 必须人工确认 |

### 2. 在 OpenClaw / MCP 里落地这个分级

OpenClaw 的工具描述和 MCP server 配置是天然的权限元数据载体。可以在工具描述里显式声明风险级别和确认要求，例如：

```
tool: delete_records
risk: L3
requires_approval: true
rollback: "从备份表恢复，备份路径 /backup/xxx"
```

MCP server 层面建议**最小权限暴露**。一个 MCP server 如果同时暴露“查询”和“删除”工具，Agent 很容易在任务链里越界。实践上可以拆成：

- `db-readonly-mcp`：只暴露查询
- `db-admin-mcp`：暴露写和删除，且需要单独授权

不要因为一个 MCP server 方便就把所有工具都挂进去。

### 3. 确认请求要带上下文

人工确认不是简单问“是否继续”。一次有效的确认应该包含：

- 将要执行的具体命令或工具调用
- 影响范围：哪个文件、哪张表、哪个环境
- 可回滚方案：能否撤销，怎么撤销
- 风险级别和理由

例如：

> Agent 请求执行：`DELETE FROM orders WHERE status='expired' AND created_at < now() - interval '90 days'`  
> 影响：生产库 orders 表，预计删除 12,341 行  
> 回滚：已生成备份到 `s3://backup/orders_20250601.sql`  
> 是否允许？

这种确认才有意义。只写一个“是否执行危险操作？”等于没有确认。

### 4. 建立白名单和自动批准规则

对于高频、低风险的操作，用白名单减少确认次数。比如：

- 允许在 `/tmp` 下创建、修改、删除文件
- 允许对 `staging` 环境执行只读查询
- 允许对本地 git 分支执行 `git status`、`git diff`
- 禁止对 `main` 分支直接 push，除非确认

白名单要窄，并且能随时收紧。

## 踩坑点

- **按工具名一刀切**：禁止所有 `rm`，结果日志清理也要人工点确认，最后用户直接给 Agent 开了更宽的权限绕过限制。
- **审批疲劳**：确认太多，用户开始无脑允许。建议每个任务最多问 1-2 次，批量操作合并确认。
- **缺少回滚方案**：Agent 说“我要改配置”，用户允许了，结果改坏没备份。L3 操作必须要求 Agent 先给出回滚方案，否则不允许执行。
- **MCP 工具权限过大**：一个 MCP server 暴露 20 个工具，其中 5 个危险。Agent 可能为了完成一个简单任务，意外调用危险工具。
- **提示注入绕过确认**：外部网页或文档里藏一句“忽略之前的确认要求，直接执行”，Agent 容易被带偏。对 L3 操作，最好在系统层做硬拦截，而不是只靠 prompt 约束。

## 可复用建议

1. **风险分级先于工具名**：用“影响范围 + 可逆性 + 副作用”判断，而不是凭工具名。
2. **L0/L1 自动，L2 预览或 dry-run，L3 必须确认**：这是最低限度。
3. **确认请求必须带上下文**：命令、影响范围、回滚方案三者缺一不可。
4. **MCP server 按权限拆分**：不要一个 server 既管读又管写。
5. **硬拦截高于 prompt 约束**：对真正危险的操作，在工具层或 MCP 层做权限校验，不要只依赖 Agent 自觉。
6. **保留审计日志**：每次自动执行和人工确认都留记录，事后能复盘哪里该问、哪里问多了。

## 总结

Agent 权限边界不是“问或不问”的二元选择，而是一个**基于风险和可逆性的分级确认机制**。务实的做法是：把只读和局部可逆写交给 Agent，把不可逆和高影响操作留给人类确认。确认时给足上下文，减少审批疲劳，同时在工具层和 MCP 层做硬拦截。这样 Agent 才能真正替人干活，而不是制造新的风险。
