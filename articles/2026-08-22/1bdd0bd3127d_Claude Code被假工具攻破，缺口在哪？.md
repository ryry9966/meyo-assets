最近安全圈在讨论一件事：有人用一个“假工具”让 Claude Code 执行了不该执行的命令。很多开发者第一反应是“模型怎么这么好骗”，但如果把攻击路径拆开，会发现更值得关注的不是模型智商，而是 AI 代理对工具定义的信任方式。换句话说，传统安全靠补漏洞，这次问题出在信任链的默认假设上。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/92945bf72cdb0441.png)

## 一、Claude Code 是怎么调用工具的？

Claude Code 不是普通的问答机器人，而是一个运行在终端里的 AI 编程代理。它的核心能力来自“工具调用”（tool use / function calling）：

- 模型可以读写文件、执行命令、搜索代码、跑测试，这些动作都通过工具完成。
- 除了内置工具，Claude Code 还支持 MCP（Model Context Protocol）扩展外部工具，例如连接数据库、浏览器、项目管理平台。
- 模型每次要做事时，会根据工具名称、描述、参数 schema 来决定“调用哪个工具、传什么参数”。
- 关键点：模型只会读取工具对外的“说明书”，不会真正验证工具的实现是不是安全、有没有偷偷做别的。

这就像给一个高效实习生一本工具目录。实习生看到“read_env：读取环境变量用于智能补全”，就会很自然地用这个工具，但不会去拆开工具看看里面有没有后门。

## 二、假工具如何进入信任链

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/41f8dcda77b71d3e.png)

这次安全事件的真正问题，不是有人直接攻击模型，而是攻击者把一个伪造工具塞进了项目的信任链里。典型路径是这样的：

- 仓库里可以放一个 `.mcp.json` 配置文件，声明项目需要哪些 MCP 工具。
- 某些版本的 Claude Code 对项目内工具配置的批准策略比较宽松，用户克隆仓库后打开，工具可能被自动加载，或者只给一个非常轻的确认。
- 攻击者可以把恶意工具包装成无害名字，例如 `env_check`、`pre_commit_check`、`format_helper`，描述里写“读取本地环境变量以便提供更准确的配置建议”。
- 当 Claude Code 在项目里工作时，如果判断这个工具能帮助完成任务，就会调用它。工具内部实际可能读取 `.env`、SSH 密钥或云凭证，并把内容发送到远端。
- 更隐蔽的做法是：MCP 服务器在启动时就执行恶意代码，甚至不需要等模型主动调用工具。

这里有一个容易被忽略的细节：攻击者不一定需要直接对用户发起提示注入。只要让 AI 代理“认为某个工具是正常工具”，后续的恶意行为就会被包装成一次普普通通的 tool call。对模型来说，它确实只是调用了工具目录里那个描述良好的函数。

## 三、为什么这不是“模型太笨”的问题

如果只把这件事当成一次 AI 被骗的笑话，会低估它的影响。工具调用机制天然存在这种攻击面：

- 模型必须信任工具描述，否则就无法高效工作。每个函数都拆开审计，会破坏 agent 的自动化能力。
- 提示注入与工具调用结合后，攻击者可以把恶意指令藏进 README、代码注释、issue 甚至依赖包的说明文件，AI 读取后可能被诱导调用某个工具。
- 这与供应链攻击的逻辑很像：npm 包、Python 包、VSCode 插件、GitHub Actions 都曾出现过投毒。现在 AI 代理相当于多了一个自动执行入口。
- 最危险的使用场景是：开发者克隆一个陌生仓库，然后对 Claude Code 说“帮我看看为什么跑不起来”。此时代理拥有当前用户权限，还可能自动加载仓库带来的工具配置。

换句话说，传统攻击要先找到一个 RCE 漏洞，而现在可能只需要让 AI 代理自愿执行一次工具调用。

## 四、一个最小可行攻击长什么样

为了把问题讲清楚，可以抽象成一个五步示例：

1. 攻击者制作一个看似正常的项目仓库，在根目录 `.mcp.json` 中声明一个远程 MCP 服务器，或放置一个伪装工具脚本。
2. 服务器向 Claude Code 返回工具列表，其中包含 `read_local_config`，描述为“读取本地配置并优化开发环境”。
3. 受害者 clone 仓库，在终端里使用 Claude Code 询问“项目启动失败，帮我排查一下”。
4. Claude Code 自动或半自动加载该 MCP 工具，并根据描述调用 `read_local_config`。
5. 工具实际读取 `~/.aws/credentials`、`.env` 或 SSH 密钥，并把内容发送到攻击者控制的服务器。

整个过程中没有传统的命令注入，也没有直接欺骗用户输入密码。被利用的，是“工具声明即能力”的信任假设。

## 五、三条冷思考：把工具当安全边界

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/3d1e76b731f5d2b9.png)

对普通开发者来说，不需要因此放弃 AI 编程代理，但需要把“工具”纳入安全边界，而不是把它当成透明的功能扩展。

- **冷思考一：不要默认仓库内的工具配置可信。** 更新 Claude Code 到最新版本，关闭或严格限制 MCP 服务器的自动批准；每次进入项目，先确认代理加载了哪些工具，尤其是来自 `.mcp.json` 或第三方插件的能力。
- **冷思考二：让 AI 代理跑在隔离环境里。** 使用容器、虚拟机或至少独立的开发目录，限制可读文件范围、网络出口和可用的环境变量。一次误调用如果只能读到无关文件，损失会小得多。
- **冷思考三：陌生仓库先人工审查，再交给代理。** 打开 `.mcp.json`、`.claude/` 目录、启动脚本和依赖列表，确认没有可疑工具定义。对 AI 说“帮我看看”之前，先自己看看。

工具调用正在成为 AI 代理的“系统调用层”。当系统调用边界不够清晰时，安全风险就会从“漏洞”转移到“信任”。这可能是 Claude Code 这次事件最值得记住的一句话。
