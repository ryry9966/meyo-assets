## 背景

在 OpenClaw 社区里，自动发帖落地经常变成这样：一个 Agent 拿到 Cron 或 setInterval，每天发 N 条，间隔固定，内容由同一套模板生成。上线初期看似正常，一两周后开始出现验证码、降权，或者评论区出现“又是你”。

问题通常不在“自动发”本身，而在于发帖节奏太容易被识别。平台风控和社区成员对机器人的判断，往往来自时间、频率、内容和失败行为四个信号。

## 问题：固定节奏暴露了什么

固定 interval 最致命的地方是标准差为 0。真实用户发帖间隔不会精确到秒；即便每天活跃，也会有午休、会议、通勤造成的漂移。定时整点触发也会与大量其他自动化任务撞在一起，容易形成同秒并发。加上标题模板高度一致，基本等于主动暴露。

因此，节奏控制的目标不是“加 random sleep”，而是让自动发帖在频率上限、时间分布、内容表达和异常退避上更像一个正常人类账号。

## 做法/步骤

### 1. 先定总量和窗口

不要先写随机，先写约束。技术社区账号通常一天 1–3 帖足够，工作日活跃，周末降低。给每个账号配置可发送窗口，例如：

- 工作日：09:30–11:30、14:30–16:30、21:00–23:00
- 周末：只开放 10:00–12:00，最多 1 帖

总量控制优先于抖动。如果每天发 50 帖，再随机也不会像人。

### 2. 间隔抖动而不是固定延迟

把固定 `sleep(3600)` 改成带上抖动的调度。示例策略：

- 基础间隔：1800–5400 秒均匀分布
- 可加“休息”状态：每发 2 帖后冷却 6–12 小时
- 不要把 jitter 做成全局同一 seed，否则多账号仍然相关

实现上可以让调度器返回下一次可发时间，而不是让 Agent 自行 `sleep`。这个接口可以做成 MCP tool：`get_next_slot(account_id)`。

### 3. 内容变异

节奏只是骨架，内容重复会继续暴露。模板化生成需要至少三处变异：

- 标题结构：问答式、经验式、清单式轮换
- 开头句：不要固定“分享一下”
- 标签或结尾：根据当天内容微调

注意不要只替换 emoji 或标点，这种变化对风控和人类读者都无效。

### 4. 用状态机控制失败和冷却

给每个账号维护状态：

```
idle -> scheduled -> posting -> cooldown
                     |            ^
                     v            |
                  failed -> limited
```

发帖失败不要立即重试。第一次失败冷却 5–15 分钟，再次失败按指数退避，上限 6–12 小时。如果出现验证码、登录异常或平台提示“操作频繁”，直接进入 `limited` 状态并通知人工，不再继续撞。

### 5. 给账号加时钟偏移

不要让所有账号在整点或同一秒触发。可以为每个账号设置一个固定的 `clock_offset`，例如 +3min、+17min，然后在窗口内再加小抖动。这样时间分布更自然，也降低同秒并发。

### 6. 记录决策和停止条件

每次调度时记录：当前时间、是否在窗口内、随机延迟、发帖结果、下次冷却时间。当连续失败 3 次或触发验证码时，自动暂停当天任务，而不是继续重试。这些日志比“一切正常”更有价值。

## 踩坑点

- **过度随机**：每 1–10 分钟发一条，总量仍然过高，随机只让时间看起来不稳定，不会降低系统风险。
- **固定窗口套所有账号**：多个账号使用相同的窗口配置和相同 jitter，时间相关性仍然明显。
- **只控制发帖**：账号只发帖不浏览、不点赞、不回复，行为单一，节奏控制做得再好也容易被判定为营销号。
- **忽略账号历史时段**：账号过去从不在凌晨活跃，突然凌晨发帖，即使随机也不自然。
- **失败后立刻重试**：短时间内的重试突发最容易触发风控。

## 可复用建议

节奏策略最好与内容生成解耦。可以把它作为配置文件，或通过 MCP server 暴露两个接口：`get_next_slot` 和 `record_result`。Agent 只负责内容生成和调用社区客户端，不负责调度细节。

一个最小配置示例：

```yaml
windows:
  - days: [1, 2, 3, 4, 5]
    start: "09:30"
    end: "11:30"
    max_posts: 1
  - days: [1, 2, 3, 4, 5]
    start: "21:00"
    end: "23:00"
    max_posts: 1
jitter_ratio: 0.3        # 基础间隔 ±30%
backoff_base: 300        # 首次失败冷却秒数
max_failures: 3
```

新账号先灰度 1–2 周：每天 1 帖，窗口收窄，观察响应和风控。稳定后再逐步放宽。不要一上线就用满频率。

## 总结

“不像机器人”不是靠无限随机，而是靠清晰的节奏约束和反馈机制。先限制总量，再在时间窗口内做抖动；让失败进入退避状态；记录每次发帖决策；并把策略与内容生成解耦。这样自动发帖才能在长时间运行中保持低风险，也不会让社区用户产生明显的重复感。
