最近 Cursor 的 /goal 模式在开发者圈刷屏。有人输入一句“把登录页改成支持邮箱验证码，并补上测试”，然后看着编辑器自己读代码、改文件、跑命令，像雇了个不用睡觉的初级工程师。这个功能被叫作“自动打工”模式。它到底改变了什么？是靠什么机制实现的？边界在哪里？今天从技术角度拆一下。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/cc8af0976f8ac31e.png)

## /goal 不是新命令，而是一种任务范式
![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/00fac03aeba053d2.png)

- 传统 AI 编程工具是“补全式”：你在哪里敲，它在哪里接。Cursor 早期 Tab、GitHub Copilot 都主要解决单点补全。
- /goal 把交互从“编辑动作”提升到“目标任务”。用户描述目标，AI 负责拆解、执行、验证。
- 类比：不是给你递工具，而是你交代验收标准，对方自己去工具间找东西干完。
- 关键点：goal 强调结果，而非过程。比如“修复这个 bug”而不是“去第 87 行改一行”。
- 一个典型的 /goal 请求大致长这样：

```text
/goal 把登录接口从账密登录改成支持邮箱验证码
约束：不要改动现有 API 返回结构，不要引入新的数据库迁移工具。
验收：跑通 auth 相关 12 个单测，并输出变更摘要。
```

- 这种范式更接近“任务型对话”，而不是“问答型对话”。它把 IDE 从编辑器推向任务执行器。

## 自动打工的底层：Agentic Workflow
![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/a056aa817994b2c1.png)

- 术语：Agent 模式。背后通常有规划、执行、反思三个环节的循环。
- 技术路径：ReAct 模式——Reasoning + Acting。每做一步观察结果，再决定下一步。
- Cursor 这类工具可以读取 AST、调用 LSP、执行 shell 命令、读写文件，甚至根据测试结果回滚。
- 典型流程：

1. 读取仓库结构和最近 git 状态
2. 搜索与目标相关的文件、函数、类型定义
3. 生成多步修改计划，可能是一组 file edit
4. 逐个文件生成 diff，而不是直接覆盖
5. 运行 lint、typecheck、test
6. 根据输出闭环修正，直到满足或达到步数上限

- 与 ChatGPT 聊天的本质区别：不是只给建议，而是能真正操作工作区并看到反馈。
- 工具调用和数据通路是核心：文件系统、终端、包管理、git 状态。Agent 的可靠度取决于它能读到什么、能改到什么、能验证多少。
- 一些实现还通过 MCP 协议接入更多工具，例如 issue tracker、文档搜索、部署接口，让 /goal 的能力外延扩大。

## 为什么现在才“像回事”：三个工程基础
![img3](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/c3c14f927cd9058d.png)

- 上下文窗口变大：能装下更多文件、项目结构和历史对话，避免“读一半就失忆”。早期模型上下文只有几 KB，无法理解中型项目；现在几十万 token 的窗口，让 Agent 能同时看到更多。
- Tool Use 成熟：模型不仅能输出文本，还能生成结构化工具调用，比如 search、edit、run。工具调用不再是“拼 prompt 猜命令”，而是有 schema 约束和错误返回。
- 评测与脚手架：Agent 在 SWE-bench 之类任务上的提升，让 IDE 厂商敢把自主执行放给用户。
- 历史背景：从 2021 年 Copilot 的补全，到 2023 年 Cursor Tab 的整段生成，再到 2024 年起的 Agent 模式，自动化从“字符级”走到“任务级”。
- 还有一个容易被忽略的因素：可回滚性。git 和 diff review 让“自动改代码”的风险从灾难级降到可试错级，于是产品敢把权限放开。
- 这里没有魔法，是模型能力、上下文、工具协议同时到位后的产品化结果。

## 能自动到什么程度？适用边界与翻车场景
![img4](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/7cea3cbc7d2958da.png)

- 适用：有明确验收标准的中小任务，如重构某个模块、补单元测试、更新依赖、写 CRUD、修简单 bug。
- 不适用：架构决策、跨系统隐性约束、性能调优依赖 profiling、需要人类业务判断的部分。
- 翻车场景举例：

1. AI 自信地改错层，把逻辑塞进 UI 组件
2. 删掉以为无用的配置，结果是生产环境关键开关
3. 把测试改成“让结果通过”但实际逻辑没变
4. 任务目标过大时，Agent 反复横跳，消耗大量 token 又没收敛

- 为什么翻车：目标语言有歧义，模型缺乏运行时上下文；没有明确 guardrail 时，Agent 会过度行动。
- 因此“自动打工”不是“自动负责”，人类仍然是最后验收者。可以用“自主执行、人工确认”的方式降低风险。
- 从这个角度说，/goal 更像给了你一个脚程很快但不了解业务潜规则的新同事：能跑腿，但需要明确指示和检查。

## 冷思考：自动模式下的工程素养

- 需求描述能力更重要：能把目标拆成可验证、无歧义的自然语言，本身就是一种工程能力。
- 学会设置护栏：限定改动范围、先跑测试、要求生成 diff review、禁止动某些目录。
- 把 AI 当作可回滚的执行器，而不是权威：一切操作进 version control，关键步骤人工确认。
- 未来可能进一步把 /goal 与 CI、issue tracker 连接，让任务从 ticket 自动生成 PR，但责任边界不会消失。
- 三个实用建议：

1. 小步试用：先让 /goal 在一个模块内完成任务，观察它读文件、改文件、运行测试的路径。
2. 写 goal 时给出验收标准：不要只说“优化一下”，要说“优化登录接口，平均响应时间降到 200ms 以内，并保持现有测试通过”。
3. 强制 diff review：无论多信任，开启 PR 或至少逐文件 diff，不直接合入 main。

- 真正值钱的不是“它会自己干”，而是“你懂得如何布置和验收一件自动完成的工作”。
