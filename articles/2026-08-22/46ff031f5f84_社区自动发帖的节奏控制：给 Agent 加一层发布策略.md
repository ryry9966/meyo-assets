社区自动发帖最容易被看穿的不是内容质量，而是节奏。我们之前用 OpenClaw 挂了几个论坛号的自动发布，内容由 Agent 生成，质量不算差，但账号仍被管理员警告。复盘后发现一个共同点：发帖时间太“整”，格式太稳定，失败后无脑重试。后来我们把发布逻辑从“定时任务”改成“策略层 + 执行层”，机器感明显下降。

## 一、问题不是不会发，而是节奏太干净

固定整点发布，比如每天 09:00、12:00、18:00，是最典型的机器特征。真实用户的时间分布有抖动，有时早几分钟，有时晚一刻钟。除了时间，还有三个容易被忽略的问题：

1. **内容结构固定**：标题都像“关于 XX 的 5 点建议”，正文永远三段式。
2. **失败行为机械**：限流或验证码后，Agent 仍按原计划重试，甚至连续打同一接口。
3. **只有发帖，没有其他行为**：账号只做发布，不回复、不编辑，行为序列单一。

这些特征叠加起来，社区管理员或风控系统很容易识别。

## 二、做法：把节奏控制做成独立策略

我们的方案是把“何时发、发什么、出错怎么办”从发帖执行中拆出来，统一由策略配置控制。在 OpenClaw 里，策略层可以做成独立插件，只向执行层给出发帖指令；执行层通过 MCP 调用社区接口。这样策略调整不影响发帖实现。

### 1. 基础节奏模型

不使用固定 cron。我们定义一个基础间隔、抖动比例、日上限和静默时段：

```yaml
schedule:
  base_interval_min: 180        # 基础间隔 3 小时
  jitter_ratio: 0.3             # 上下浮动 30%
  max_daily_posts: 3
  quiet_hours: [1, 6]           # 凌晨 1-6 点不发
content:
  template_variants: 4          # 同主题标题/结构变体数
  max_repeat_days: 7            # 同内容指纹 7 天内不重复
safety:
  human_review_ratio: 0.15      # 15% 转人工抽检
  error_backoff_min: 30
  max_consecutive_failures: 2
  kill_switch: true
```

实际调度时，下一次执行时间用基础间隔乘一个均匀抖动：

```python
next_delay = base_interval_min * (1 + uniform(-jitter_ratio, jitter_ratio))
```

这样间隔均值稳定，但单次间隔不会完全一致。光加随机 sleep 不够，日上限和静默时段也要一并管住。

### 2. 内容去重与变体

Agent 生成内容后，我们会先计算文本指纹（如 SimHash 或 MinHash），与最近 7 天的已发帖子比对。如果太接近，就换一个模板变体或触发重写。标题池和段落顺序也做成可插拔模块，避免每次输出同一结构。我们要求每条帖子至少包含一条具体可执行细节，防止 Agent 输出“正确但空洞”的长文。

### 3. 失败退避与熔断

接口错误要分类处理。限流、验证码、权限错误不是“再试一次”能解决的。我们的规则是：

- 限流：指数退避，从 30 分钟开始，最多 2 次。
- 验证码/权限：暂停当日发布，转人工。
- 连续失败 2 次：触发熔断，停止该账号当日任务。

熔断状态放在 Redis，OpenClaw 任务启动前先检查熔断标记，避免一批任务同时重试。

### 4. 人工抽检与灰度

发帖后按比例进入人工复核队列，确认格式、语气、版块匹配度。新策略先在小号或非核心社区灰度 7 天，观察管理员警告率和互动率，再逐步放开。

## 三、踩坑点

- **只加随机 sleep 不够**：如果日上限和静默时段没管住，凌晨发帖仍然一眼假。
- **同账号高频发布**：节奏再合理，单账号一天发太多也容易被标记。我们控制在 1-3 条/天。
- **忽略社区规则**：有些社区明确禁止脚本发布。自动化前先读规则，避免工具性风险。
- **一次性批量排队**：提前生成 10 条并排队发布，失败后很容易形成机械重试。应该动态决策下一次发不发、发什么。
- **生成内容结构太稳定**：标题和段落顺序的重复，比时间重复更隐蔽，但也更容易被长期观察识别。

## 四、可复用建议

1. 把“像人”参数化：间隔均值、抖动比例、日上限、静默时段、模板变体数都做成配置，而不是散落在代码里。
2. 建立审计日志：每次发帖记录 trace_id、模板版本、内容指纹、接口返回、是否人工抽检。
3. 保留 kill switch：配置中心或环境变量一键暂停，不必改代码。
4. 关注非发帖行为：Agent 偶尔回复、点赞、编辑旧帖，能显著降低行为序列的单一性。
5. 先小流量观察：至少 7 天，关注警告率、删除率、互动率，再决定扩大。

## 总结

社区自动发帖的节奏控制，本质上是风险管理，而不是伪装技巧。稳定的间隔、合理的日上限、可观测的失败退避和人工兜底，比一味追求“像真人”更可持续。OpenClaw 的优势在于可以把这些策略做成可配置、可灰度的工程模块，但前提是别让 Agent 变成整点打卡机。
