## 背景

在 OpenClaw 的 Agent/MCP/插件链路里，很多自动化节点会把 LLM 输出直接当作结构化数据使用。典型场景是让模型返回 JSON，再由下游 MCP 工具、插件或脚本消费。实际工程中，模型经常不按要求返回纯净 JSON：可能包在 ` ```json` 围栏里、夹在前后说明文字里、用 `<result>` 一类标签包一层，甚至一次返回多个候选块。如果节点里直接 `json.loads(raw)`，遇到这些情况就会抛异常，整条自动化链路被打断。

因此需要一个防御性解析层，把“不可信输出”转换成可验证的结构化对象。这个解析层不负责理解内容，只负责从混合文本中稳定、可诊断地提取 JSON。

## 问题形态

混合输出通常有几类：

- 围栏：` ```json { ... } ``` `
- 标签包裹：`<result>{ ... }</result>`、`<output>{ ... }</output>`
- 前后文字：`Here is the output: { ... }`
- 多块混合：先输出 `<thinking>...</thinking>`，再输出 `<result>{ ... }</result>`
- 标签内不是 JSON：`<result>ok</result>`
- JSON 损坏：尾逗号、单引号、缺少闭合括号、字符串被截断

标签格式混合处理的难点在于：既要提取标签，又不能假设标签内一定是纯净 JSON；同时要避免正则或 `rfind` 误判，尤其是字符串值里出现花括号的情况。

## 防御性解析步骤

可以按一个固定 pipeline 做，不需要引入复杂依赖。

**1. 归一化清洗**

去掉 BOM、零宽字符，将常见中文引号替换为 ASCII 引号。不要全局替换太多字符，避免破坏字符串值。

**2. 候选提取**

按优先级提取，而不是直接解析全文。

- 先匹配 fenced block：` ```json ... ``` ` 或裸 ` ``` ... ``` `，提取内部内容。
- 再匹配信任标签：`<result\b[^>]*>(.*?)</result>`。标签名可配置，优先 `result`、`output`、`json`。
- 如果前两步没拿到，做全文字符级括号扫描：找到第一个 `{` 或 `[`，跳过字符串内容，按深度配对到最后一个闭合括号。

括号扫描比 `rfind('}')` 更可靠。核心逻辑：

- 遍历字符，遇到 `"` 时跳过字符串；
- 遇到 `{` 或 `[` 深度加一；
- 遇到 `}` 或 `]` 深度减一；
- 深度回到 0 时即为完整 JSON 末尾。

**3. 解析与修复**

候选内容先尝试 `json.loads`；失败后按需修复尾逗号、截断、单引号。可以使用 `json_repair` 或轻量实现，但修复后必须再过 schema，避免“修错”。

**4. 结构归一化**

如果解析结果是 `{"data": {...}}` 而调用方期望 `{...}`，根据 schema 解包 `data`/`result`/`items` 等常见字段。如果全文有多个 JSON 块，优先返回第一个通过 schema 校验的候选，而不是第一个候选。

**5. 失败返回**

解析失败不要只返回 `None`。返回错误类型、失败原因和一段截断的原始文本，便于排查和决定是否重试。

## 踩坑点

- **标签正则过窄**：标签可能带属性、换行或命名空间。用 `\b` 和 `[^>]*` 更稳。
- **`rfind('}')` 误判**：字符串值里若有 `}`，会截断 JSON。必须用字符级 scanner。
- **多重候选**：模型可能先输出一个用于解释的 JSON，再输出真正结果。不要只取第一个，按 schema 过滤。
- **过度重试**：格式问题可以在解析层修复；内容缺失或字段类型错误才应触发重试，否则浪费 token。
- **全角符号**：中文引号、全角括号会让键名不合法。清洗要在解析前做，但避免影响字符串内部内容。
- **`json_repair` 的边界**：它可能把残缺 JSON 修成一个奇怪对象，所以 schema 校验不能省。

## 可复用建议

- 在公共 utils 里放一个 `parse_llm_json(text, schema=None)`，所有 MCP/插件入口统一调用，避免每个节点各自写脆弱逻辑。
- 提供配置项：`TAG_PRIORITY`、是否允许部分解析、最大扫描深度。
- 记录解析失败率与修复路径；线上坏样本保存为单测 fixture，后续加 parser 规则时先跑一遍。
- MCP 工具描述和 prompt 里给明确 JSON 示例，但不要把 prompt 约束当成唯一保障，解析器是最后防线。
- 解析完成后交给 Pydantic/dataclass 做字段类型校验，再进入业务逻辑。

## 总结

LLM 输出解析是一个独立的容错层，不应散落在每个调用点。用“候选提取 + 括号扫描 + 修复 + schema 校验”的顺序处理 JSON 与标签混合输出，能显著降低 Agent/MCP 链路里因格式问题导致的断裂。更关键的是，把失败信息保留下来，才能持续根据真实坏样本改进解析器。
