过去一年，大模型世界的明面竞赛是参数规模与上下文窗口，但真正的暗线发生在 token 账本上。当 AI 从“聊天工具”变成能调用工具、读写记忆、多步规划的 Agent，token 消耗结构发生了质变。OpenClaw、Hermes 到本地自研 Agent 的演进，不只是一条产品路线，更是一场关于“单位智能成本”的重构。这件事值得每个做应用的人重新拿起计算器。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/d84711ce19218595.png)

## 一、旧账本失效：Agent 让 token 从成本项变成设计变量

对话时代的 token 经济是线性的：用户输入多少、模型回复多少，API 按量计费，优化点主要是压缩提示词和限制 max_tokens。但 Agent 把这条直线掰弯了。

1. 一个 Agent 任务往往由多轮模型调用组成：规划一次、判断工具一次、工具返回后再总结一次、失败重试一次。
2. 工具返回的 JSON、网页片段、代码 diff 会被反复塞回上下文，token 呈阶梯式增长。
3. 更隐蔽的是 memory：为了保持一致性，开发者倾向于保留完整历史，导致第 10 轮调用仍为前 9 轮重复付费。
4. 例如，一个“读取 3 封邮件并生成摘要”的简单任务，用对话模型可能只需 800 token；用未优化 Agent 可能消耗 15,000–30,000 token，而最终有效输出仍只有 200 字左右。

关键结论是：在 Agent 阶段，token 不再是单纯的账单数字，而是影响任务成功率、延迟、上下文注意力衰减的设计变量。继续用旧思路“省 token”会牺牲智能，但放任爆炸则会让产品在商业上不可持续。

## 二、OpenClaw 的启示：把 token 当库存来管理

OpenClaw 作为开源 Agent 运行框架，受到关注的原因不是它发明了什么新模型，而是它把 token 消耗当成了一个可显式管理、可审计的工程问题。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/4fd2abc84642ff81.png)

它的做法可以归纳为三类：

1. **工具输出压缩**：不让 API 原样返回大段 JSON 或 HTML，而是在进入上下文前先做字段裁剪、去冗余、转为紧凑结构。比如一个电商查询工具返回 40 个字段，实际 Agent 只用到价格、库存、链接三个，那么就只传递这三个。
2. **状态摘要代替历史回放**：维护一个跨步骤的状态对象，每次新调用只携带“目标 + 当前状态 + 相关前置事实”，而不是把整个聊天记录重新喂给模型。这很像视频压缩里的关键帧策略——只保留决策所需的最小信息。
3. **失败路径显式建模**：把“工具不存在”“超时”“结果为空”等异常用短码表示，而不是把完整报错堆栈塞给模型。模型只需识别短码就能决定下一步，既省 token 又降低误判。

这带来的不只是省钱。token 每减少一倍，长上下文中关键信息的注意力密度就提高一些，对多步推理的稳定性有直接帮助。OpenClaw 的实践指向一个判断：Agent 框架的竞争，正从“能接多少工具”转向“每完成一件事消耗多少 token”。

## 三、Hermes 模型线：Agent 能力开始可拆解、可分层

如果说 OpenClaw 解决的是“怎么省着用”，Hermes 系列模型则提出了另一个问题：是不是每个环节都需要最大、最贵的模型？

Hermes 系模型以函数调用、结构化输出和指令跟随见长，很多开发者在 Agent 的“执行层”使用它，而不是只在云端超级模型上硬扛。这背后是一种能力分层思路：

1. **规划层**：用强推理模型分析任务、拆解步骤，调用次数少但要求高。
2. **执行层**：用 7B–14B 的开源或本地模型完成工具选择、参数填充、JSON 生成，这些任务模式相对固定，中等模型可胜任。
3. **反思层**：用中等偏上模型检查结果是否符合目标，决定是否重试或终止。

这种拆解让 token 消耗结构从“全包大套餐”变成“按需点餐”。规划层可能只占总 token 的 15%，执行层占 70%，反思层占 15%。执行层是成本大头，如果能用本地模型消化，整体边际成本会显著下降。

需要澄清的是，Hermes 不只是一个模型名称，它代表一种“Agent 能力可工程化”的转向：函数调用不是大模型的附属赠品，而是可以被独立优化、评分、替换的模块。这也为本地自研提供了可行性基础。

## 四、本地自研 Agent 的工程现实与冷启动成本

本地自研 Agent 被很多团队提上日程，来源不难理解：

- 云 API 按 token 计费，高频 Agent 任务会形成持续现金流压力。
- 本地推理的边际成本接近零，延迟更可控，数据也不出内网。
- 开源函数调用模型和量化工具，使消费级显卡能跑起可用的执行层模型。

但现实不是免费的：

1. 一台 24GB 显存的显卡，可以跑 7B–13B 的量化模型，函数调用延迟做到 200ms 以内，但复杂多步规划的准确率会明显下降。
2. 自研需要投入数据标注、微调、评估集、部署监控，这些前期成本往往高于短期 API 节约。
3. 工具生态碎片化：不同模型对 function calling 的格式兼容性不同，换模型可能意味着重写解析器。

因此，本地自研 Agent 的合理切入点不是“把整个 Agent 搬到本地”，而是**混合路由**。比如：

- 本地小模型负责意图分类、信息抽取、格式化输出。
- 云模型负责开放域推理、复杂规划、长文总结。
- 只有当本地模型在子任务上的成功率超过某个阈值，才逐步放大其职责。

## 五、实用建议：先算清账，再谈进化

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/12807ac1e9c7b790.png)

我不太喜欢“全面转向本地”这种口号，更建议从三个动作开始：

1. **建立任务账本**  
   对每个 Agent 任务记录：总 token、工具调用次数、重试率、有效产出字数。没有这套数据，“优化”只是感觉。

2. **先压缩上下文，再考虑换模型**  
   检查 tool schema 是否过宽、历史回放是否必要、错误信息是否过长。很多场景下，仅做字段裁剪和摘要化，就能把 token 降 40%–60%。

3. **用分层路由做小规模实验**  
   选一个高频、模式固定的子任务，让 7B–14B 本地模型接管，线上对比成功率、延迟、成本。成功一个再扩一个，不要一次性替换。

冷思考：Token 经济转点并不意味着终结云 API，也不意味着开源模型全面胜利。它更像一场从“买算力”到“买智能密度”的迁移。能活下来的 Agent 团队，未必是模型最大、工具最多的，而是最清楚每 1,000 token 换来多少有效动作的。
