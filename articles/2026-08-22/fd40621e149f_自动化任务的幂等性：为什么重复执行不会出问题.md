## 背景

在 OpenClaw、Agent 和 MCP 工具链里，重复触发不是异常，而是默认情况：Webhook 超时重发、定时任务重叠、Agent 重试同一个 tool call、插件热加载后重新处理旧消息。如果任务不幂等，重复执行就会产生重复消息、重复资源、重复外部请求。很多人问“为什么重复执行不会出问题”，答案不是系统有魔法，而是任务在设计时就把“重复”当成了正常输入。

## 问题：非幂等任务的表现

典型问题如下：

- 收到两条相同 `event_id`，创建两条相同任务。
- 定时任务两个实例重叠，处理同一批数据。
- 调用支付/发送接口超时后重试，换了新 key，造成重复扣款或重复发送。
- 旧的重试把状态从 `done` 回写成 `processing`。

这些问题往往不报错，日志看起来也正常，但业务状态已经出错。

## 做法：让重复执行变成安全操作

### 1. 入口先确定幂等键

每个自动化任务入口先解析唯一标识，如 `event_id`、`message_id`、`task_id`，或者从业务参数拼出确定性 key。没有唯一键的任务，要先补上唯一键，而不是用自增主键或时间戳。

```python
idem_key = event.get("event_id") or sha256(event["payload"])
if not already_processed(idem_key):
    process(event)
```

### 2. 用存储约束兜底

应用层判断存在竞态，更可靠的是让数据库或缓存拦截：

- 数据库：`UNIQUE KEY (idempotency_key)`
- Redis：`SET idem_key 1 NX EX 86400`

冲突时不要直接报错，可以返回已有记录或走冲突处理。

### 3. 用状态机代替布尔标记

任务状态至少包含 `pending`、`processing`、`done`、`failed`。重复触发时按状态决定：`done` 直接返回结果；`processing` 判断是否超时；`failed` 按策略重新入队。

### 4. 条件更新，避免状态回退

更新语句必须带状态条件：

```sql
UPDATE tasks
SET status = 'done'
WHERE id = ? AND status = 'processing';
```

影响行数为 0，说明状态已经变化，跳过。

### 5. 外部副作用外置并携带幂等键

发消息、调 API、扣库存等副作用不要埋在处理逻辑深处。先完成本地状态变更，再执行外部调用，并把同一个幂等键传给外部服务。大多数支付、短信、云 API 都支持 `Idempotency-Key`。

## 踩坑点

- **先查后写**：并发下两个请求都查到“不存在”，都执行插入。唯一索引才是最终防线。
- **把“没报错”当幂等**：重复执行可能日志正常，但业务上已经产生重复副作用。
- **删除重建式更新**：删除旧资源再创建，新 ID 会让下游引用失效。优先使用 upsert 或目标状态更新。
- **外部 API 不支持幂等键**：超时重试时先用业务单号查一次，确认没成功再重试。
- **定时任务重叠**：没有锁或租约，多个实例处理同一时间段。可以用分布式锁或租约保证单实例运行。

## 可复用建议

1. 默认所有自动化任务都会被重试，先问“重复执行会怎样”。
2. 入口统一封装幂等处理，做成 middleware、helper 或插件。
3. 写操作优先使用唯一约束 + `ON CONFLICT` / `INSERT IGNORE`。
4. 所有外部副作用都要求或模拟幂等键。
5. 测试用例固定加两条：“同一事件重放两次”和“两个并发重放”。

## 总结

幂等性不是靠一段代码实现，而是入口唯一键、存储约束、状态机、条件更新、副作用外置组合起来的结果。重复执行不会出问题的前提是：你已经把重复当成正常输入，而不是意外。对于 OpenClaw/Agent/MCP 这类自动化场景，这是基本要求，不是过度防御。
