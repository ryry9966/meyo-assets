## 背景

在 OpenClaw 这类 Agent 框架里，模型不只是生成文本，还会通过 MCP/插件调用工具：读文件、发请求、改配置、执行 shell。权限边界决定它在这条链路上什么时候必须停下来等人，什么时候可以继续。

一个常见误区是：把“权限”当成模型自觉。你可以在 system prompt 里写“不要执行危险操作”，但模型在长上下文里仍然可能误判，或因为一次诱导就绕过。真正能起作用的，是在插件层、MCP 网关层或 OpenClaw 的工具调用入口做统一拦截。权限边界不是提示词问题，是工程策略问题。

## 问题

权限边界模糊通常表现为三类：

1. **该问不问**：删除生产数据、给外部发 webhook、修改数据库 schema，这些不可逆或对外部有影响的操作被自动放行。
2. **不该问乱问**：读日志、查状态、格式化文件也要弹确认，用户机械点“继续”，确认机制逐渐失效。
3. **按工具名一刀切**：比如把 `shell` 整个设为高风险，Agent 连 `git status` 都要问；或者 MCP server 声明了 write 权限，结果 `read` 操作也触发确认。

核心问题是：权限不能只按“工具名”分，也不能只按“命令内容”分。需要结合**动作类型、参数、目标资源、环境、可回滚性**综合判断。

## 做法/步骤

我建议在 OpenClaw 的插件或 MCP 入口加一层 policy，而不是在模型侧判断。把动作分成四个风险等级：

- **L0 只读/纯查询**：自动执行，只记录日志。例如 `fs.read`、`db.select`、`git status`。
- **L1 可逆写操作**：自动执行，但必须写审计日志。例如创建临时文件、生成草稿、可回滚的配置修改。
- **L2 不可逆/外部影响/生产环境写操作**：默认 `ask_human`。例如删除文件、发送消息、webhook、`git push --force`、修改数据库 schema。
- **L3 禁止自动执行**：任何情况下都不自动做，只能人工操作。例如删除生产数据库、批量关停服务。

风险不是按工具名判断，而是按 `tool + 参数 + 目标资源 + 环境` 判断。比如同一个 `shell` 工具：

```yaml
policy:
  - match: {tool: "shell", pattern: "git status"}
    level: L0
  - match: {tool: "shell", pattern: "git push --force"}
    level: L2
  - match: {tool: "fs.write", path: "prod/**"}
    level: L2
  - match: {tool: "http.post", target: "external"}
    level: L2
  - match: {tool: "db.query", type: "write"}
    level: L2
```

对于 L2 操作，确认不能只问“是否继续”。要给出 **dry-run 结果、影响范围、回滚方式**。比如删除操作先列出文件列表和预计释放空间；发消息先展示渠道、接收人、内容预览。这样人类有信息做判断，而不是凭感觉点确认。

同时保留审计：每次工具调用都记录 decision、risk level、是否 dry-run、是否 human confirmed、最终结果。这样出问题能回溯，也能发现哪些 L0/L1 操作其实应该升级。

## 踩坑点

1. **确认疲劳**：每步都问，用户机械点“继续”，确认机制实际上失效。解决方式是用 L0/L1 放行大部分低风险操作，只把 L2 留给人类。
2. **环境不分**：测试环境和生产环境用同一套策略。生产环境的写操作应该整体提高一级，测试环境可以放宽。
3. **策略过粗**：按工具名整工具拦截，导致 Agent 无法做只读操作，或者绕过策略。需要参数级匹配。
4. **模型越权**：只靠 prompt 说“不要做危险操作”没有约束力。需要在框架层拦截，模型无法绕过。
5. **没有回滚**：只问“是否继续”，但没有回滚方案。一旦确认后出问题，无法快速恢复。L2 操作应该尽量要求可回滚或提供 rollback 脚本。
6. **忽略外部影响**：发消息、webhook、外部 API 调用不属于传统“文件写”或“shell”，但对外部系统有真实影响，风险等级应该提高一级。

## 可复用建议

- **默认 deny 写操作**：只读和可逆操作白名单放行，写操作默认走 risk 判断。
- **策略声明式配置**：用 YAML/JSON 管理，按环境覆盖，不要写死在代码里。
- **预演优先**：对 L2 操作先 dry-run，输出预期变更，再决定是否执行。
- **给有限授权**：用户可以选“本次允许”“始终允许此模式”“仅允许当前参数”，减少重复确认，同时保留控制。
- **审计日志**：记录每次工具调用的 risk level、decision、human confirm、执行结果。定期拉出来看有没有危险操作被低风险管理。
- **熔断与降级**：连续失败、超时、异常时，Agent 自动降级为只读模式，停止写操作，避免连锁影响。

## 总结

AI Agent 的权限边界不是“所有敏感操作都问人”，也不是“先放开跑通再说”。它应该是一个分层策略：低风险自动做，中风险预演后确认，高风险强制人工，禁止项直接拦截。

在 OpenClaw/Agent/MCP/插件实践里，真正的安全来自**入口拦截、参数级分级、dry-run 预演、审计回滚**，而不是依赖模型自觉。把权限边界做成工程策略，而不是 prompt 里的希望。
