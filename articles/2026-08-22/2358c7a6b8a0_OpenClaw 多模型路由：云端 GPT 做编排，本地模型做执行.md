## 背景

在 OpenClaw 里跑 Agent，模型调用很容易变成“一刀切”。要么所有请求都走 GPT 类云端模型，成本高、延迟飘、敏感数据出域；要么为了离线把本地模型顶上去，结果多步工具调用、MCP 插件编排经常失败。

实际工程中，多模型路由比单纯选一个模型更重要：把不同负载分给不同模型，用规则和回退保证稳定性。我在 OpenClaw 上接了几类自动化：日志摘要、工单分类、客户邮件草稿、内部知识库问答、MCP 工具调用（查数据库、发通知、建任务）。早期全用 GPT，单日 token 消耗高，且部分批量任务根本不需要强推理。后来把分类、摘要切到本地 Qwen/Llama，延迟和成本下降明显，但一旦涉及多工具选择、复杂 JSON 参数、长上下文指令跟随，本地模型经常把 MCP 工具名写错、参数丢字段、输出里夹带解释文本，导致流程中断。

## 问题

核心不是“哪个模型更好”，而是“什么任务该交给谁”。云端模型擅长规划、工具调用、长文档理解，但成本高、有合规风险；本地模型擅长批量、可校验、低敏感任务，但复杂推理和函数调用不稳定。如果路由策略缺失，要么浪费资源，要么线上翻车。

## 做法/步骤

**1. 先按任务类型做粗路由**

把任务分成三类：

- **高决策/低容错成本**：多步规划、插件编排、代码生成、开放域问答 → 云端 GPT 类模型。
- **高容错/可校验**：文本分类、情感分析、实体抽取、摘要、改写、批量数据清洗 → 本地模型。
- **混合**：先本地初筛，置信度低或格式校验失败再升级云端。

**2. 路由规则做成显式条件，不要只写在 prompt 里**

在 OpenClaw 的流程节点中判断：

- 消息元数据 `task_type` 属于 `[classify, extract, summarize]` → 本地模型。
- 消息包含 `tool_call` 或 `mcp` 且需要多工具协作 → 云端模型。
- 输入包含 PII 或内部敏感字段 → 本地模型，除非已脱敏。

**3. 本地模型启用结构化约束**

不要光靠“请只输出 JSON”这种提示。用 llama.cpp 的 grammar、vLLM 的 guided decoding 或 outlines 把输出限制成 JSON Schema。这样分类、实体抽取的稳定性会明显提高。

**4. 设置校验与回退**

对本地模型输出做 schema 校验，失败重试 1 次（降低 temperature），再失败自动升级到云端。云端超时或限流时，降级到本地只做只读任务，不执行写操作。

**5. 记录成本、延迟、错误率**

把每次路由的模型、token、耗时、是否回退写入日志，跑一周就知道哪些规则需要调整。

## 踩坑点

- **本地模型工具调用能力差异大**。别指望 7B/13B 模型在 MCP 多工具场景下稳定选工具。即使工具描述写得再清楚，也可能选错或漏参。这类任务直接走云端，或使用专用微调模型。
- **“输出 JSON”不等于合法 JSON**。一定要上 grammar/guided decoding，否则本地模型容易在 JSON 前后加 markdown 代码块或解释。
- **路由规则别写太死**。固定用 `task_type=summarize` 走本地模型，但输入是 30 页长文档时，本地模型长上下文推理又慢又差。后来增加上下文长度判断，超过阈值升级云端。
- **本地模型吞吐高不等于单请求延迟低**。批量任务适合本地跑批，但交互式请求如果用户等着，本地小模型可能比云端还慢，要按场景区分。
- **云端模型版本变化会影响 prompt 表现**。不要依赖某个模型的“话术”，路由规则和校验逻辑要保持模型无关。
- **敏感数据上云前先做识别和脱敏**，路由层面直接拦截更稳。

## 可复用建议

- **分层策略**：云端负责“决策和编排”，本地负责“执行和批量”。不要让本地模型做需要多步推理的规划，也不要让 GPT 跑几千条文本分类。
- **可校验输出**：为本地模型定义明确的 JSON Schema、枚举值、长度限制，校验失败再升级。
- **把 MCP 工具调用与文本生成解耦**。即使本地模型生成文本，工具选择和执行也尽量由云端或规则引擎完成。
- **灰度切换**：新任务先并行跑云端和本地模型，对比结果差异，稳定后再切换。
- **模型选择做成配置**，而不是硬编码。新增模型时只改路由表，不改业务逻辑。

## 总结

OpenClaw 的多模型路由本质是把任务按“容错成本、推理复杂度、数据敏感度、延迟预算”分开。云端 GPT 类模型适合高价值决策和插件编排，本地模型适合可校验的批处理和隐私数据。关键不是选哪个模型，而是把校验、回退、成本日志做起来，让路由策略可以被观测和调整。这样既不用为简单任务付云端账单，也不会在关键时刻被本地模型的 JSON 错误打断流程。
