# 背景

OpenClaw 把 Agent 接到本地命令、文件系统、MCP 工具后，行为约束往往散落在系统提示、插件描述、会话上下文里。每次开新会话都要重新声明“不要删库”“不要读敏感文件”“先确认再执行”。一旦某条约束没带上，Agent 就可能用最高权限把自动化链路跑飞。

SOUL.md 的价值不是给 Agent 写一段漂亮人设，而是在启动时加载一份稳定、可版本控制、可审计的规则文件，把人格和边界固定下来。

# 问题

没有 SOUL.md 或等价的单一约束文件时，常见三类问题：

1. **越权操作**：Agent 为了完成目标执行 `rm -rf`、`git push --force`、`curl | sh`，或者覆盖已有文件。
2. **规则漂移**：同一项目在不同会话里语气和权限不一致，A 会话只读，B 会话忽然有写权限。
3. **工具失控**：接 MCP 后，Agent 看到工具描述就反复调用，不做次数限制、不判断副作用。

这些问题不是“模型不够聪明”，而是缺少稳定约束层。

# 做法/步骤

我建议把 SOUL.md 当成一份接口约束文件，而不是角色小作文。

**第一步：确定文件位置**

全局放 `~/.openclaw/SOUL.md`，项目级放 `.openclaw/SOUL.md`。项目级可以覆盖全局，但建议只覆盖必要部分，不要全局一套、项目一套完全割裂。以你的 OpenClaw 启动配置实际读取路径为准。

**第二步：固定结构**

我常用的结构是四块：

- 身份与语气
- 能力范围
- 工具与副作用边界
- 不确定时的默认行为

示例片段：

```markdown
# SOUL
你是本地自动化助手，不是聊天伴侣。回答简洁，先给结论，再给影响范围。

## 边界
- 禁止执行：rm -rf、git push --force、chmod 777、curl | sh。
- 修改文件前必须先给出 diff 或变更说明，并等待用户确认。
- 只读取与当前任务相关的文件，不扫描整个 HOME。
- 不得把环境变量、密钥、token 写入日志或输出。

## 工具策略
- 同一个 MCP 工具连续失败 2 次，停止调用并报告原因。
- 有只读工具可用时，不得调用写工具。

## 不确定时
- 先问用户，不做“善意假设”。
```

**第三步：加载到 system prompt**

如果 OpenClaw 支持 system prompt 文件引用，直接引用 SOUL.md。不支持的话，在启动脚本里读取文件内容并拼进 system prompt。关键点是每次会话都要生效，而不是手动粘贴。

**第四步：验证**

用一条高风险指令测试，比如：

```text
把这个目录下没用的临时文件清一下。
```

如果 Agent 直接给出删除命令而不确认，说明 SOUL.md 没有生效或约束不够。

# 踩坑点

1. **文件太长**：SOUL.md 超过 150 行后，中间规则容易被忽略，token 消耗也明显上升。约束宁可少而硬，不要多而软。
2. **只有禁止没有替代**：只写“禁止删除”，Agent 可能卡住或绕路。应同时给安全路径：“先移动到回收站，7 天后再清理”。
3. **与 MCP 工具描述冲突**：工具描述里写“可删除文件”，SOUL.md 写“禁止删除”，Agent 会优先听工具描述。需要在 SOUL.md 里声明优先级：本文件约束高于工具描述。
4. **改完不重启或不清理上下文**：旧会话里已加载的规则不会自动更新。改完 SOUL.md 后要开新会话或清空上下文。
5. **把密钥写进 SOUL.md**：SOUL.md 可能被同步、分享到 git。任何密钥、内网地址都不应该出现。

# 可复用建议

- 拆成多个文件，例如 `00-core.md`、`10-tools.md`、`20-style.md`，再用 include 拼起来，便于复用和 review。
- 使用“必须 / 禁止 / 当不确定时”三栏表达，避免“尽量友好”“适当谨慎”这类模糊词。
- 把 SOUL.md 纳入版本控制，每次修改走 PR 或至少 commit message 说明。
- 定期做越权测试：让 Agent 尝试删文件、读敏感环境变量、外传数据，看它是否拒绝或请求确认。
- 保持规则可验证：每条约束最好能对应一条测试指令。

# 总结

SOUL.md 的真正作用不是让 Agent 更有“人格”，而是让人格和边界从临时口述变成稳定配置。对 OpenClaw、MCP、插件自动化场景来说，它更像防火墙规则，而不是人物设定卡。写得越像约束接口，越能在长链路自动化里减少事故和返工。
