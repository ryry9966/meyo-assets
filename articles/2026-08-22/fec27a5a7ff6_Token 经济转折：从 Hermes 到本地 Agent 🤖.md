过去两年，Token 经济经历了一次不易察觉的转向。大模型刚开放 API 时，按 Token 计费被看作云原生时代的“用多少付多少”——简单、透明、零门槛。但当 Agent 工作流开始替代单轮问答后，一个任务不再是一次 inference，而是几十次带工具调用的推理链。账单逻辑随之改变。OpenClaw、Hermes 到本地自研的讨论升温，与其说大家突然想买显卡，不如说 Agent 的规模化暴露了按 Token 付费的结构性问题。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/95110a0199a759bb.png)

## 一、Token 为什么在 Agent 时代变贵了

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/66b7aa17163a73df.png)

Token 是模型处理文本的最小计量单位，通常英文 1 个单词约 1-2 token，中文 1 个字约 1-2 token。单价看起来便宜，但 Agent 任务改变了消耗结构。

- 单轮变多轮：传统问答只有输入问题和输出答案，可能几百到几千 token；Agent 任务“预订机票”要拆成查日历、查航班、比价、调用支付、写回执等 8-15 步，每步都要把上一轮结果拼入上下文。一个 15 步的 Agent 调用，输入总量可能从 2k token 涨到 60k token，消耗增长是数量级级别。
- 上下文不断膨胀：为了保持多步一致性，系统会把工具 schema、历史消息、检索片段、系统提示全部塞进 prompt。每多一个工具，就会多一段 JSON schema；每多一轮，历史消息就线性增长。模型处理长上下文的注意力计算成本并不是线性，尤其自回归解码时输出每个 token 都要对已有序列重新计算 KV，长序列显存和算力涨幅更陡。
- 隐藏输出与重试成本：结构化输出、JSON 校验失败会触发重采样；一次格式错误可能浪费前序几百到几千 token。并行 Agent、反思机制、多候选投票，也会成倍放大 token 消耗。

因此，Agent 真正的问题不是“单 token 太贵”，而是“单位任务消耗的 token 太多”。按 token 计费在短问答时代友好，在长链路 Agent 时代就会变成不可预测的成本中心。

## 二、OpenClaw 与 Hermes：两条不同的“去计费表”路线

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/3d9cc4847369f641.png)

OpenClaw 和 Hermes 在技术社区频繁同屏出现，但两者解决的问题并不同。

- Hermes：模型侧。它是 Nous Research 推出的开源模型系列，早期基于 Llama、Mistral 等底座微调，重点强化指令跟随、函数调用、JSON 输出、角色扮演和 Agentic alignment。对开发者来说，它的价值是“可以在本地跑一个更听话、更擅长工具调用的模型”，而不用把所有请求都发给云端闭源接口。
- OpenClaw：框架/运行时侧。可以理解为面向 Agent 的开源编排层，把记忆、工具调用、多步任务、环境交互和模型接口解耦。它关心的是：Agent 如何长期运行、如何管理上下文、如何挂载外部工具。模型可以被替换，控制流不必绑定某一家 API。
- 组合逻辑：Hermes 类模型提供推理与函数调用能力，OpenClaw 类框架提供任务编排与工具执行环境。两者加起来，刚好覆盖“本地自研 Agent”的两个关键层：inference 和 orchestration。

这里有个容易被忽略的点：开源不等于免费。省下的主要是按量计费的边际成本，换成的是模型部署、环境适配和版本升级的固定成本。但在高频场景里，这种替换是有意义的。

## 三、本地自研 Agent：不是“不花钱”，而是成本结构改变

![img3](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/33341d8ff709d2c4.png)

很多人把“本地自研”理解为省钱，其实更准确的说法是成本结构从 OpEx 切换为 CapEx。

- 云端 API：按 token 付费，是运营支出（OpEx）。调用越多，支出越大，而且单价下降不等于总成本下降。
- 本地推理：一次性投入 GPU 服务器、显卡折旧、电力和运维，是资本支出（CapEx）。在利用率足够高时，单 token 平均成本可以低于 API。
- 盈亏平衡示例：假设某 API 价格为每百万 token 20 元，本地一台 8 卡服务器折旧、电费、网络和人力折算每天 2000 元。那么当每天总消耗低于 1 亿 token 时，API 更便宜；高于 1 亿 token 时，本地推理开始占优。这组数字只用于展示计算逻辑，不同模型和硬件差异很大。

除了成本，本地自研还有两个收益：

- 延迟与数据边界：敏感数据不必出域，工具调用不经过第三方 API，端到端延迟更可控。
- 可控性：可以针对业务数据做领域微调、裁剪上下文、定制系统提示，减少大模型“自由发挥”。

也必须看到隐性成本：模型升级慢，闭源模型发布新版本后，本地模型可能要重新微调、评测、部署；GPU 利用率波动大，高峰不够用，低峰空转；还需要 MLOps、推理优化、工具链维护的人力。所以本地自研不是万能解药，而是一种适合特定负载结构的工程选项。

## 四、转点信号：为什么现在才谈本地自研

![img4](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/bc0179b1fa3287f5.png)

“本地自研 Agent”并非新概念，过去落地难，是因为三个条件不成熟。现在开始出现转点。

1. 模型能力分层更清晰：小参数量模型在 function calling、代码生成、工具调用等垂直任务上已经接近更大模型。很多 Agent 任务不需要百科全书式世界知识，只需要稳定地按照 schema 调用工具。这给 7B-30B 级别的本地模型留出空间。
2. 推理系统明显成熟：vLLM、SGLang 等推理框架支持 continuous batching，显著提高 GPU 吞吐；AWQ、GPTQ 等量化方法把显存占用和推理成本压低，精度损失在多数 Agent 任务中可接受；投机采样、前缀缓存、KV cache 复用等工程手段，让本地长上下文任务不再那么昂贵。
3. 工具与协议走向标准化：Function calling、JSON schema 减少模型输出解析成本；MCP 等协议让工具接入更统一，Agent 框架不必为每个 SaaS 单独写插件；开源模型权重可获得，企业可以做领域适配，避免核心流程依赖单家闭源接口。

这些信号叠加，意味着一个公司不再必须“全用大厂 API”或“全自研大模型”二选一，而是可以按任务负载分层路由。

## 五、冷思考与实用建议

热潮里更需要冷静。Token 经济的转折并不意味着本地自研适合所有团队。

1. 用“单位任务成本”做决策，而不是“单 token 价格”。记录一个真实 Agent 任务从开始到结束消耗多少 token、调用几次模型、出错重试几次。单 token 降价 30%，如果任务整体 token 量涨了 5 倍，最终仍然更贵。
2. 先上混合路由，不要一步到位全自研。简单任务交给本地小模型，复杂推理或低频长尾任务继续用云端大模型。混合路由可以先用 API 积累日志、识别负载分布，再决定哪些场景值得下沉到本地。
3. 买卡之前，先把负载量化清楚。需要知道峰值 QPS、平均上下文长度、输出长度分布、日活 Agent 数量、任务失败率。没有这些数据，GPU 采购很容易变成“为一次想象中的峰值买单”。可以先租 GPU 云实例试跑 1-2 周，得到真实吞吐和成本曲线，再评估是否采购硬件。

Token 经济的转折点，不是 API 消失，而是 Agent 负载终于复杂到让“按 token 计费”和“本地固定成本”可以放在同一张表上比较。OpenClaw、Hermes 这些项目只是这条路上不同位置的标志物。
