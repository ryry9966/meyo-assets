## 背景

在 OpenClaw 这类 Agent/MCP 自动化环境里，外部 API 已经不是“偶尔不可用”，而是日常要面对的变量。搜索、天气、支付状态、OCR、模型推理、向量库，任何一个外部依赖都可能超时、限流、返回 5xx，甚至返回半截 JSON。很多 Agent 默认把工具调用当作成功路径，一旦上游挂了，任务不是中断就是污染上下文：模型可能把错误信息当成事实继续跑，或者直接编一个合理但错误的结果。

## 问题

常见的问题不是“没有 try-catch”，而是错误处理没有结构化。具体表现：

- 4xx、5xx、超时、限流混在一起，重试策略一刀切。
- 无限重试或立即重试，导致线程池、连接池被占满，甚至触发上游更严厉的限流。
- 外部依赖失败后没有降级路径，整个 workflow 直接失败。
- 任务没有状态持久化，重跑从零开始，可能重复产生副作用，比如重复发消息、重复创建订单。
- MCP server 内部异常没有结构化返回，Agent 只拿到空字符串或堆栈，无法决定下一步。

## 做法 / 步骤

**1. 先定义错误契约**

每个外部 API 适配器不要往上层抛裸异常或字符串。统一返回结构化错误类型，例如：`RETRYABLE`、`NON_RETRYABLE`、`RATE_LIMITED`、`TIMEOUT`、`INVALID_RESPONSE`。这样 Agent 或编排层可以根据类型做决策，而不是靠关键词匹配。

**2. 分层设置超时和重试**

在工具调用层设置短超时，通常 3–8 秒；HTTP 客户端单独设置 connect/read timeout。只对 `RETRYABLE` 和 `RATE_LIMITED` 做重试，使用指数退避加随机抖动，最大重试 2–3 次。4xx 不要重试，直接返回可读错误。遇到限流优先读取 `Retry-After`，不要固定间隔硬撞。

**3. 加熔断和隔离**

对每个外部 API 部署熔断器。连续失败 N 次后打开熔断，后续请求快速失败，避免资源被挂起请求拖垮。熔断可以和一个短 TTL 的半开状态配合，既保护自己，也给上游恢复时间。

**4. 设计降级路径**

关键工具必须准备 fallback。比如搜索 API 挂了，可以切到备用 provider，或者使用本地缓存/静态索引；支付状态查询失败时，不要擅自标记为失败，而是进入 `pending` 队列等待定时重试或人工介入。MCP 工具返回降级结果时，要明确告诉 Agent：这是缓存结果、时间戳是什么、是否可能过期。

**5. 做状态持久化和幂等**

任务执行前写入 step 状态，外部调用前携带 `idempotency key` 或 `request_id`。恢复时先检查是否已经产生副作用，避免重复下单、重复发信。长任务建议用异步队列 + 状态机，而不是在单次 Agent run 里无限等待。

**6. 可观测性和故障演练**

记录每个外部 API 的延迟、错误率、熔断状态。用故障注入模拟 5xx、慢响应、超时、半截 JSON，观察 Agent 是否还能做出合理决策。日志里要能看到工具调用参数、原始错误、重试次数、最终降级动作。

## 踩坑点

- **把重试当万能药**：对非幂等 POST 盲目重试，可能重复扣款或重复发信。
- **不让 Agent 知道失败**：吞掉异常后返回空字符串，模型可能编造结果。
- **没有超时**：LLM 调用或 MCP 工具卡住，整个任务挂死。
- **降级数据不标注**：过期缓存被当成实时结果，还不告诉 Agent，最后得出错误结论。
- **对限流立即重试**：没有读取 `Retry-After`，反而加重限流。
- **MCP server 错误未结构化**：返回堆栈或空响应，Agent 无法判断下一步。

## 可复用建议

- 封装统一的 API Client，内置超时、重试、熔断、日志和指标，不要在每个工具里重复写。
- 用错误预算或 SLO 决定何时切换 provider 或启动降级。
- 工具返回结构里包含 `status`、`error`、`fallback`、`ts` 字段，方便 Agent 判断返回数据的新鲜度和可信度。
- 为外部依赖建立 runbook：哪些错误可以自动恢复，哪些必须人工介入，哪些需要暂停任务。
- 对长任务和关键写操作，优先考虑异步化，避免把重试压力全部集中在一次 Agent run 内。

## 总结

外部 API 挂掉不是异常，而是常态。Agent 的错误恢复不应该只是加 try-catch，而是围绕“快速失败、安全降级、可恢复状态、可观测”来设计。把错误分类清楚、重试有边界、降级有路径、副作用可幂等，才能让 Agent 在上游抖动时仍然可控，而不是把一个小故障跑成一个大事故。
