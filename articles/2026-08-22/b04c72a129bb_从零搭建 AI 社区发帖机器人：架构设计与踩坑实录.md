# 背景

社区运营里有大量重复性内容工作：资讯速递、案例复盘、活动帖、问答整理。人工写帖成本高，但完全交给 LLM 自动发布又容易产出低质内容或触发平台风控。

我们的目标不是做一个全自动发帖机，而是做一个半自动机器人：自动完成选题、草稿生成、排版、发布到草稿箱或待审核队列，人工确认后再发布到公开版块。全程可回滚、可审计。

# 问题

主要困难不在“让 LLM 写一段话”，而在工程链路：

- 社区平台多数没有稳定开放 API；
- Markdown 与社区富文本不兼容；
- Agent/MCP 工具权限过大时容易误操作；
- 定时任务并发和登录态失效会导致重复发布或发布失败。

# 做法/步骤

## 1. 总体架构

整体分四层：

调度器 -> 内容生成 -> 审核队列 -> 发布适配器

调度器用 cron 或 agent 定时任务触发。候选内容进入 SQLite，状态流转：

draft -> pending_review -> approved -> published -> failed

任何发布动作都先落到 pending_review，由人通过 CLI 或内部 bot 确认。

## 2. 内容生成

不直接让模型自由发挥，而是维护一套模板，例如：

- 资讯速递：来源 + 摘要 + 原文链接 + 社区讨论点
- 案例复盘：问题 + 方案 + 效果 + 可复现步骤
- 活动帖：时间 + 形式 + 参与方式

模板使用版本号管理。生成时传入模板 ID 和素材 JSON，要求 LLM 返回 JSON：标题、摘要、正文 Markdown、标签。这样便于校验和重试。

## 3. 发布器抽象

定义统一的 Publisher 接口：

```go
type Publisher interface {
    Publish(ctx, Post) (PostID, error)
    Update(ctx, PostID, Post) error
    Preview(ctx, Post) (string, error)
}
```

如果有官方 API 就实现 API Publisher；没有就用 Playwright 实现 Browser Publisher。两种实现输出统一结果，上层不关心平台差异。

## 4. MCP/Agent 集成

发布器封装成 MCP tool 后，可以让 OpenClaw/Agent 通过工具调用完成“生成草稿 -> 预览 -> 发布到草稿箱”。关键是把工具参数收窄：只暴露 draft 发布、preview、status 查询，不直接暴露发布到公开版块。发布到正式版块必须在审核队列里人工确认。

## 5. 审核与状态回写

审核通过后，调度器从队列里取 approved 任务，调用发布器发布，并把平台返回的 URL 回写。失败则进入 failed 并保留原始草稿，方便重试。

# 踩坑点

## 1. Markdown 与富文本不匹配

LLM 输出的 Markdown 在社区编辑器里经常出现标题层级丢失、代码块无法渲染、列表间距异常。不要只存 Markdown，同时保留平台格式或渲染后的 HTML。Publisher 里必须提供 Preview 方法，发布前拿到平台侧预览结果。

## 2. 登录态和风控

浏览器自动化最常见的问题是登录态失效、验证码、地区风控。对策：使用持久化浏览器 profile，限制发布频率，不在公开版块做高频测试。遇到验证码直接人工介入，不要尝试自动过验证码。沙箱测试账号非常重要，先在测试版块跑通全流程。

## 3. LLM 输出不可控

即使要求 JSON，模型偶尔还是会返回额外字段或错误类型。使用结构化输出或 JSON Schema 约束，并在代码里做字段校验。但约束过严会导致内容变呆板，所以只校验必要字段，不要求“完美格式”。

## 4. 重复发布和并发

cron 任务可能拉起多个实例，导致同一条草稿被发布两次。在状态表上增加唯一约束或乐观锁，状态从 approved -> publishing -> published 必须是原子更新。单机可用 SQLite 事务，多机部署需要分布式锁。

## 5. MCP 工具范围过大

如果 MCP tool 直接暴露“发布到公开版块”，Agent 很容易误判上下文后直接发布。把发布权限拆成 draft/publish 两个工具，且 publish 工具在默认配置里关闭，只通过审核队列调用。

# 可复用建议

- 发布器适配器保持统一接口，平台变化只改适配层；
- 内容模板版本化，避免每次调 prompt；
- 审核队列永远保留，不要追求全自动；
- 全链路记录 audit log：谁生成、谁审核、谁发布、失败原因；
- 先做沙箱账号，再上真实社区；
- 定时任务要有幂等和锁，防止重复发布。

# 总结

这个机器人最终并没有自动产出“高质量内容”，它只是把重复的排版、发布、回写工作自动化，把判断权留给人。AI 适合生成草稿和格式，审核和发布策略必须工程化约束。对 OpenClaw/Agent/MCP 用户来说，把发布器做成受限工具，比直接让 Agent 控制浏览器可靠得多。
