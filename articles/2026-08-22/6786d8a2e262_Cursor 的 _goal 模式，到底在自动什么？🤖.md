最近，Cursor 的 `/goal` 模式在开发者圈里刷了屏。有人说它把“自动打工”从段子变成了产品功能：输入一个目标，剩下的交给工具自己去拆解、改文件、跑命令、修错误。事情当然没有“AI 替你上班”那么玄，但这次变化确实值得认真拆一拆。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/99df69848884a155.png)

## /goal 是什么：从“补全一行”到“交付一个目标”

如果把 AI 编程工具的发展拉长来看，`/goal` 并不是凭空出现的。

- 2021 年 GitHub Copilot 上线，主要做行级、函数级补全，帮人少敲几行代码。
- 2022—2023 年，ChatGPT、Claude 这类对话式模型流行起来，开发者开始把报错贴进去、把需求描述一下，再复制粘贴代码。
- 2024 年起，Cursor 的 Composer、Agent 模式已经能跨多个文件修改代码、执行简单命令。
- 到了 `/goal`，入口进一步从“具体指令”变成“目标描述”。用户不再一步步指挥 AI 做什么，而是给一个目标，系统自己负责拆解任务、调用工具、检查结果。

举一个比较典型的例子：你在一个 React 项目里输入：

`/goal 给设置页增加深色模式，并确保现有测试通过`

理想情况下，它的执行流程是：先检索样式体系和测试脚本，定位相关文件；然后改写主题变量、补上测试；再运行 test 或 lint；如果失败，就根据报错继续修改，最后给出变更清单和 diff。

这里的关键不是模型突然变强了，而是执行结构变了。它不再只回答“你可以这样写”，而是尝试自己把任务做完。

## 为什么说它像“自动打工”：Agentic loop 在起作用

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/c870823db61197b3.png)

很多人觉得 `/goal` 像“自动打工”，本质是因为它背后不是一问一答，而是一个可以操作环境的循环结构，也就是常说的 agentic loop。

这个循环通常由四步组成：

1. **Plan**：把目标拆成子任务，比如“找文件 → 改主题 → 补测试 → 跑命令”。
2. **Act**：调用工具执行，包括文件编辑、终端命令、代码搜索、运行 linter 或 test。
3. **Observe**：读取工具输出，比如终端报错、测试失败信息、diff 内容。
4. **Revise**：根据观察结果修正动作，失败就重试，必要时回滚到上一个状态。

传统对话式编程更像一个“只动嘴不动手”的顾问，而 `/goal` 则像真去工位上敲键盘的初级工程师。它会真正读写文件、跑命令、看输出，然后继续改，直到满足条件或撞到边界。

当然，这里有一个重要的工程前提：执行环境通常是受限的沙箱或本地工作区，并且对不可逆操作需要授权。否则“自动打工”很容易变成“自动闯祸”。

## 能力边界：哪些活能放心交，哪些必须人盯

并不是所有任务都适合丢给 `/goal`。它的能力强在执行速度快、不怕重复、能根据报错迭代，但判断力仍然有限。

比较适合交给它的事情：

- 验收标准明确、可以自动验证的任务，例如“测试通过、构建成功、lint 零告警”。
- 范围有限的重复性修改，例如批量替换 API、统一错误处理、迁移配置文件。
- 样板代码生成、脚手架搭建、简单重构等结构化工作。

需要谨慎甚至避免的场景：

- 架构选型、核心模块设计、安全敏感逻辑。
- 支付、权限、数据库迁移等一旦出错代价很高的部分。
- 需求模糊、隐性约束多的任务，比如“把性能优化一下”。
- 不可逆操作：删除数据、直接 push 到主分支、操作生产环境。

一个很现实的反例是：如果你只写“优化性能”，它可能给出一堆看起来合理但不必要的缓存改动，测试也过了，却引入了新的资源竞争。自动验证通过，不等于设计合理。

## 对开发流程的真正冲击：人从“打字员”变成“审核员”

这类工具普及之后，开发者的一部分工作确实会被替代，但更多是工作重心的转移。

过去，写代码是主要产出；现在，写清楚目标、验收条件、边界，会变成更重要的能力。因为 AI 可以快速产出大量代码，但需要人来确认意图、长期维护性、安全边界和业务正确性。

代码 review 的权重会继续上升。`/goal` 一次可能生成几百行 diff，如果一个团队没有合理的 review 流程，很容易被大量变更淹没。更建议小批量提交、要求 AI 给出可解释的步骤，并且每个关键动作都留痕。

这并不等于程序员失业，更像是工作内容从纯执行向系统设计、需求澄清、质量把关移动。自动化测试出现以后，QA 也没有消失，而是转向了更高层的测试策略。

## 实用建议：把 /goal 用成工具，而不是甩手掌柜

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-22/94c8158ccea42580.png)

如果你准备尝试 `/goal`，下面几条可能比“让它跑起来”更重要。

1. **把目标写成可验证的验收条件**。不要写“让代码更好”，而是写“新增暗色主题；所有现有测试通过；通过 ESLint；不引入新的依赖”。
2. **先小范围试跑，给关键动作加确认**。对安装依赖、修改配置、git 操作这类动作设置审批，尤其不要允许自动 push。
3. **永远做 diff review**。把 AI 当成一个速度快但偶尔想岔的初级同事：可以信任它的执行力，但要检查它的判断。
4. **复杂任务先要求出计划**。让它先列出步骤，确认后执行，能省下大量回滚和返工时间。

一句话冷思考：自动化的真正收益，不在于少敲了多少键盘，而在于你是否能把目标定义得足够清晰。工具越自动，模糊需求造成的浪费反而越大。
