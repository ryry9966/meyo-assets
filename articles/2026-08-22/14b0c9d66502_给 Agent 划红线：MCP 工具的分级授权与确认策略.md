## 背景

当 OpenClaw 通过 MCP、插件或自定义工具接入真实环境后，Agent 就不再只是“聊天”，而是能操作文件、调接口、发消息、改配置。比如一个常见的需求：让 Agent 每晚整理 Downloads 目录下的截图，按日期和来源归档。它会遍历文件、重命名、移动、删除重复项，甚至调用通知插件告诉你结果。

问题在于：哪些步骤它可以自己干，哪些必须停下来问你？

没有清晰的权限边界，结果要么是 Agent 每动一个文件都弹确认，自动化名存实亡；要么是它默默执行了一次高风险操作，等你发现时文件已经没了、消息已经发错了。

## 问题

实践中通常会同时踩到两类失败：

- **过度询问**：所有工具调用都要求人工确认，用户很快疲劳，最后习惯性点“允许”，确认流变成形式。
- **过度自主**：为了“顺滑体验”把工具全部设为自动批准，Agent 可能因为一条模糊指令或上下文里的诱导内容，执行了删除、群发、修改配置等不可逆操作。

安全边界不能只靠模型“自己判断”。模型在长上下文或工具描述中被注入误导信息后，判断力会下降。所以权限边界必须落在工具层和策略层，而不是模型层。

## 做法：按风险等级分层授权

我习惯把 Agent 能接触到的工具按副作用和可逆性分成四级，然后映射到不同的确认策略。

| 等级 | 典型操作 | 策略 |
|------|----------|------|
| L0 只读 | 读文件、查状态、搜索、列表 | 自动执行 |
| L1 可逆写 | 创建文件、重命名、移动、生成草稿 | 自动执行，但记录审计日志 |
| L2 外部副作用 | 发消息、调第三方 API、修改在线文档 | 本会话内授权一次，过期收回 |
| L3 不可逆/高风险 | 删除、覆盖、支付、权限变更、发布 | 每次确认，或默认禁用 |

在 OpenClaw 的工具/插件配置里，可以抽象成类似这样的策略（字段名仅供参考，具体以你使用的版本为准）：

```yaml
tools:
  filesystem:
    policy: auto
    allow_actions: [read, write, move]
    deny_actions: [delete, chmod]
  message:
    policy: session_approve
  shell:
    policy: require_approval
    allowlist: ["ls", "pwd", "cat"]
```

这里的核心不是把某个工具写死，而是让每个工具入口都有明确的默认动作：自动、会话授权、每次确认、禁用。

## Dry-run 先行

对于 L2/L3 操作，尤其是批量任务，最好先让 Agent 输出执行计划，而不是边执行边问。计划可以是一个简单的 JSON：

```json
{
  "actions": [
    {"action": "move", "target": "Downloads/img_001.png", "dest": "archive/2025-06/"},
    {"action": "delete", "target": "Downloads/img_002.png", "reason": "duplicate"}
  ]
}
```

用户确认计划后，Agent 再批量执行。这比每一步都弹窗高效，也比完全自动安全得多。对于 L3 操作，即使计划已确认，执行前仍应逐条确认，因为没有“撤销”的可能性。

## 踩坑点

1. **全局 `auto_approve: true`**  
   这是最常见的事故来源。一旦开启，Agent 可能把 `rm -rf`、群发消息也当成普通操作执行。OpenClaw 接入 MCP 后，工具能力往往比想象中大，全局自动批准等于把所有钥匙都交给模型。

2. **依赖模型判断风险**  
   模型看到“删除文件”这个工具描述后可能会拒绝，但如果工具名叫 `cleanup_old_files`，它可能认为足够安全就调用了。工具描述容易被命名误导，不能作为安全依据。必须在工具入口做参数校验，比如禁止路径包含 `~`、`/`、`..` 的删除操作。

3. **MCP 工具粒度过粗**  
   很多 MCP server 暴露的是一个大而全的工具，比如 `run_command`，没有细分权限。这种情况下，光靠 MCP 自带描述不够，需要在 OpenClaw 这层加一层代理，按命令或路径做 allowlist/denylist。

4. **授权不设过期时间**  
   用户在某个会话里授权 Agent 访问某个目录，但会话结束或任务完成后授权没有回收。后续会话继续沿用旧授权，一旦上下文被污染，风险就会被放大。

5. **把“只读”当绝对安全**  
   读取敏感信息也有风险。Agent 可能把内部文档、密钥、用户数据读到上下文里，再通过其他工具或回复泄露出去。只读工具也需要区分“可公开读”和“敏感读”。

## 可复用建议

- **默认拒绝，按需授权**：新接入的工具先禁用或只读，确认使用场景后再放开。
- **给工具分风险等级**：不用很复杂，L0–L3 四级足够覆盖大部分场景。
- **区分“操作”和“资源”**：授权时明确“可以对哪个目录、哪个频道、哪张表执行什么操作”，不要笼统授权整个工具。
- **Dry-run 优先于边问边做**：批量任务先出计划，确认后执行；L3 操作执行前仍单独确认。
- **审计日志不可省**：记录每次工具调用、参数、结果、审批状态。出问题时能快速定位是哪一步、谁授权的。
- **授权要过期**：会话结束、任务完成或超时后回收授权，避免长期权限残留。

## 总结

Agent 的权限边界不是一次设置就完事，而是三层叠加的工程实践：工具层做硬限制，策略层做风险分级，交互层做恰到好处的确认。目标不是“让 Agent 什么都不问”，也不是“让 Agent 什么都自己干”，而是让它在可逆、低风险的操作上自动执行，把真正需要人类判断和负责的操作留在人手里。

当边界清晰时，你才敢把更多任务交给 Agent；边界模糊时，每一次“自动执行”都可能变成下一次排障的起点。
