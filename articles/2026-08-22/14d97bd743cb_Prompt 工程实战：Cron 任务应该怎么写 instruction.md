## 背景

在 OpenClaw 里配置 Cron 任务很容易：写一个 cron 表达式，配一段 instruction，到点触发 Agent 执行。但很多同学直接把交互式 prompt 搬进定时任务，比如“帮我关注一下 XX，有异常处理一下”。这种写法在聊天里有追问和确认机会，但在 Cron 场景里没有。一次模糊指令会被反复执行，输出越来越漂移，甚至误操作。

定时任务的关键不是“触发”，而是“无人值守下的稳定执行”。instruction 需要承担原本由用户澄清、上下文、确认共同承担的责任。

## 问题

Cron instruction 最常见的毛病不是“没写”，而是“写了但不可靠”。具体表现包括：

- 每次运行格式不一样，下游脚本解析失败
- 任务重复处理同一条数据
- 失败后没有日志，不知道哪一步出错
- 模型自由选择工具，偶尔调用到不该用的插件
- 依赖上一轮对话上下文，但 Cron 每次是独立进程
- 时区混乱，日志时间对不上

这些问题在交互式会话里还能靠人肉兜底，在定时任务里会直接放大。

## 做法/步骤

### 1. 写成标准作业程序，而不是目标描述

不要写“帮我看看服务状态，有问题处理一下”。改成明确的步骤、输入、输出、异常处理。一个可用的 instruction 模板如下：

```text
角色：你是 OpenClaw 定时运维助手。
目标：检查 /data/state.json 中 status != ok 的条目并生成摘要。
输入：只读取 /data/state.json，不要依赖对话历史。
步骤：
1. 读取 /data/state.json；
2. 筛选 status != ok 的条目；
3. 为每条生成不超过 20 字的描述；
4. 将摘要追加写入 /data/cron_log.md。
输出：最后只输出 JSON，不要输出任何额外解释。
异常：文件不存在时记录错误并退出，不要创建新文件。
```

### 2. 固定输出 schema

如果下游要解析，必须约束输出结构。例如：

```json
{"run_at":"2026-01-01T08:00:00+08:00","status":"ok","failed_count":1,"summary":"..."}
```

要求“只输出 JSON，不要代码块前后缀”，否则多一行 ``` 都会让解析失败。

### 3. 默认只读，变更要显式拆开

Cron 任务尽量只读。如果涉及写操作，要求先 dry-run 并输出计划，不直接执行。比如：

```text
禁止删除任何文件。需要变更时，只输出变更列表，等待人工确认。
```

敏感操作可以拆成两个任务：第一个生成建议，第二个在人工确认后执行。

### 4. 加幂等设计

任务可能因为重试或执行时间过长而重复运行。instruction 里要写清楚去重规则：

```text
如果同一 ID 已经在当天处理过，跳过，不要重复写入。
```

可以使用 run_id、日期、哈希等作为幂等键。

### 5. 显式指定时区

cron 表达式通常使用服务器时区，但 instruction 内涉及“今天”“昨天”时必须显式声明：

```text
所有时间使用 Asia/Shanghai 时区。
```

### 6. 定义失败策略

不要只写“失败就重试”。要明确哪些错误可以重试，哪些需要停止并记录：

```text
网络错误可重试一次；文件不存在则直接退出并写入错误日志。
```

## 踩坑点

- **模糊词**：“适当处理”“相关更新”“尽量简洁”会导致每次输出不同。改成“只汇总 status=failed 的项，每条不超过 20 字”。
- **依赖前次上下文**：Cron 每次可能是独立进程，不要写“继续上次的操作”。要写“读取上次状态文件”。
- **没有防重入**：任务执行时间超过 cron 间隔，可能并发运行。可加锁文件或使用 flock。
- **输出混入解释**：如果下游用正则解析，一定要写“不要输出代码块外的任何文字”。
- **忽略环境变量**：cron 环境可能缺少 PATH、密钥或 MCP 配置。instruction 可以要求先检查必要环境变量。
- **工具选择随机**：如果接入了多个插件/MCP，应指定用哪个工具。例如“使用 GitHub MCP 的 list_issues，不要使用网页搜索”。

## 可复用建议

- 建立 instruction 模板库，把可变部分参数化，例如 `{{state_file}}`、`{{threshold}}`，不要每次手写。
- 正式启用前，用短周期如每 5 分钟测试，观察 3-5 次输出是否稳定一致。
- 所有 Cron instruction 放进 Git，变更可回溯。
- 每次运行写日志文件，并保留最近 N 条，方便排障。
- 对会发消息、写数据库的任务，加一个全局 dry_run 开关。
- 如果任务关键，拆成“诊断”和“执行”两个 Cron：第一个只读输出，第二个带 guard 执行。

## 总结

Cron instruction 不是聊天，是无人值守的作业定义。写得好不好，不看一次运行成不成功，而看第 50 次、第 200 次是否还能产生稳定、可解析、可追踪的结果。把目标拆成步骤、约束、输出、异常，才能让定时 Agent 真正可维护。
