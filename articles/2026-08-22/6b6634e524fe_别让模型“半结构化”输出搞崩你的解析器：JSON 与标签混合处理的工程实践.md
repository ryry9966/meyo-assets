## 背景

在 OpenClaw、Agent、MCP 以及各类插件开发里，我们经常要求 LLM 返回严格的 JSON，然后用 `json.loads()` 直接解析。理想很美好，现实是模型经常输出“半结构化”内容：JSON 前后夹着解释文字、被 ```json 代码块包住、或者用 `<result>`、`[JSON]` 这类标签包裹，甚至 JSON 中间某个字段值里还藏着换行或未转义引号。

直接严格解析，轻则抛异常导致流程中断，重则让你的自动化任务在半夜挂掉，第二天只能对着日志发呆。防御性编程不是让模型更听话，而是让你的解析器更抗造。

## 问题本质

模型输出不可控，但你的下游逻辑必须可控。常见的混合输出形态有：

1. **前缀/后缀闲聊**：`好的，这是结果：{"name": "test"} 希望对你有帮助`
2. **代码块包裹**：` ```json\n{"name": "test"}\n``` `
3. **自定义标签**：`<result>{"name": "test"}</result>`
4. **多段 JSON**：`{"a":1} 另外 {"b":2}`（有时候只想要第一个）
5. **JSON 内部格式问题**：尾随逗号、单引号、字段名未加引号（YAML 风格混入）

如果你只处理了其中一种，换一个模型或者换一个 prompt，解析照样崩。所以需要一套分层的提取策略。

## 做法 / 步骤

我通常封装一个 `extract_json(text)` 函数，按以下顺序尝试，返回解析后的 dict 或 None。核心思路：先清理外层干扰，再定位首尾花括号，最后做容错修复。

```python
import json
import re

def extract_json(text: str):
    if not isinstance(text, str) or not text.strip():
        return None

    original = text.strip()

    # 1. 去掉代码块标记
    if original.startswith("```"):
        original = re.sub(r"^```(?:json|JSON)?\s*", "", original)
        original = re.sub(r"\s*```$", "", original)

    # 2. 尝试直接解析（运气好）
    try:
        return json.loads(original)
    except Exception:
        pass

    # 3. 定位第一个 { 和最后一个 }，截取子串
    start = original.find("{")
    end = original.rfind("}")
    if start != -1 and end != -1 and end > start:
        candidate = original[start:end+1]
        try:
            return json.loads(candidate)
        except Exception:
            # 4. 常见容错：去掉尾随逗号、单引号转双引号
            fixed = re.sub(r",\s*([}\]])", r"\1", candidate)
            fixed = fixed.replace("'", '"')
            try:
                return json.loads(fixed)
            except Exception:
                pass

    # 5. 如果存在自定义标签，提取标签内内容（按需扩展）
    tag_match = re.search(r"<(result|json|output)>(.*?)</\1>", original, re.DOTALL | re.IGNORECASE)
    if tag_match:
        return extract_json(tag_match.group(2))  # 递归提取

    # 6. 最后回退：正则提取关键字段（根据业务调整，或返回 None 触发重试）
    return None
```

上面代码是一个精简版骨架。实际项目里我会根据业务字段增加更具体的回退逻辑，比如提取 `{"status": "ok"}` 里的 status，而不是依赖整个 JSON 解析成功。

**关键顺序**：从最严格的直接解析开始，逐步放宽到截取、修复、标签提取。不要一上来就用正则大杂烩，否则容易误伤。

## 踩坑点

1. **嵌套 JSON 或字符串里包含 `}`**：`rfind("}")` 可能截到内部对象的结尾，导致候选串不完整。比如 `{"a": {"b": 1}}` 用 `rfind` 没问题，但如果值是 `"text } here"` 且没有正确转义，`rfind` 会截错。更好的做法是写一个简单的括号匹配扫描，统计 `{` `}` 的深度，找到最外层闭合位置。
2. **多个 JSON 对象**：`find` 和 `rfind` 会把中间所有内容都当成一个 JSON，可能解析失败。如果业务只需要第一个，找到第一个 `{` 后用深度匹配找到对应的 `}` 即可。
3. **尾随逗号和注释**：JSON 标准不允许尾随逗号，但模型经常输出。除了去掉 `,}` 和 `,]`，**不要**直接移除所有逗号，否则会破坏值内部的逗号。
4. **单引号替换的风险**：如果 JSON 字符串值里本身包含单引号（如 `"name": "O'Brien"`），全局 `replace("'", '"')` 会把它变成 `"O"Brien"`，反而更糟。更安全的做法是先用正则匹配键值对，只替换键和值的引号，但复杂度高。建议优先让模型输出标准 JSON，修复只作为兜底。
5. **空响应或纯文本**：模型可能返回“抱歉，我无法生成 JSON”。如果 `extract_json` 返回 None，不要直接崩溃，而是记录原始输出，触发重试或降级逻辑（比如返回默认值）。
6. **截断输出**：当 `max_tokens` 不够，JSON 可能被截断，没有闭合 `}`。此时 `rfind` 找不到，截取失败。可以在 prompt 里要求先输出 JSON 再输出解释，并预留足够 token。

## 可复用建议

- **封装统一入口**：所有需要解析 LLM 输出的地方都调用同一个 `parse_llm_output(text, schema=None)`，不要在业务代码里到处写 `json.loads`。
- **记录解析失败样本**：把失败时的原始输出、模型名、prompt 版本写入日志或一张表。定期分析，调整 prompt 或提取规则。这是工程化最关键的一步。
- **结合 JSON 模式或结构化输出**：如果所用 API 支持 `response_format={"type": "json_object"}` 或工具调用（function calling），优先使用，能大幅减少混合格式问题。但即使开了 JSON 模式，仍然可能有外层代码块，防御性解析依然值得保留。
- **分层重试策略**：第一次解析失败后，可以让模型重新生成一次，并在 prompt 里附上错误信息：“上次输出无法解析为 JSON，请只输出纯 JSON 对象，不要包含任何其他文字。” 很多时候第二遍就干净了。
- **写单元测试**：准备一组真实的混合输出样例（包括代码块、标签、尾随逗号、截断等），对 `extract_json` 做回归测试。每次修改提取逻辑后跑一遍，避免引入新问题。
- **字段级容错**：如果业务只关心部分字段，即使完整 JSON 解析失败，也可以尝试用正则提取目标字段。比如 `r'"status"\s*:\s*"(ok|error)"'`，这样能救回一部分数据。

## 总结

LLM 输出解析的防御性编程，核心不是追求 100% 解析成功，而是把失败从“程序崩溃”降级为“可捕获、可记录、可重试”的状态。JSON 与标签格式的混合处理，本质是分层清理 + 括号定位 + 容错修复 + 失败兜底。在 OpenClaw、Agent 和 MCP 这些自动化场景里，解析器的鲁棒性直接决定你的流水线能跑多稳。别把希望全寄托在 prompt 上，写一个抗造的 `extract_json`，比一百句“请只输出 JSON”更实在。
