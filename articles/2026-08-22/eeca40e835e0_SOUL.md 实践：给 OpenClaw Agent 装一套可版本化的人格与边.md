## 背景

在 OpenClaw 里跑 Agent，最怕的不是能力不够，而是行为不可预期。同一个 Agent，昨天还能按项目规范输出，今天就开始自由发挥；遇到 MCP 工具时，有时只读查询，有时却直接执行写操作。这些问题通常不是模型变笨了，而是缺少一份明确、可版本化的“人格与边界”文件。

SOUL.md 就是用来做这件事的：它把 Agent 的身份、原则、工具边界、输出风格固化下来，放在项目或用户级目录里，每次会话加载。这样 Agent 的行为不再依赖临时的系统提示词，而是有一套稳定的约束。

## 问题

没有 SOUL.md 或边界模糊时，常见几类问题：

- **风格漂移**：同一任务在不同会话中回答结构、语气不一致，难以复用。
- **越权调用**：Agent 通过 MCP 或插件执行了未预期的写操作，例如修改文件、发请求、删除数据。
- **规则冲突**：用户级配置和项目级要求不一致，Agent 随机选一个执行。
- **不可审计**：行为没有来源，出了问题很难定位是哪条规则没写清楚。

## 做法/步骤

### 1. 确定 SOUL.md 的位置和加载顺序

建议按以下优先级加载：

1. 项目级：`./.openclaw/agents/<agent-name>/SOUL.md`
2. 用户级：`~/.openclaw/agents/<agent-name>/SOUL.md`
3. 全局默认：`~/.openclaw/SOUL.md`

加载时先读全局，再读用户级，最后读项目级；后加载的覆盖先加载的同名字段。这样项目可以覆盖个人默认，但不会完全丢失基础约束。

### 2. 定义 SOUL.md 的结构

一份可用的 SOUL.md 建议包含以下区块：

```markdown
# SOUL.md

## Identity
- 名称：ops-agent
- 角色：负责本地自动化任务，不主动对外部服务写操作。

## Principles
- 先解释，再执行。
- 只做用户明确要求的事，不扩展任务范围。
- 遇到不确定操作先问，不猜测。

## Boundaries
### 允许
- 读取文件、查询只读 API。
- 执行幂等的 shell 命令（如 `ls`, `cat`, `git status`）。

### 需确认
- 写入本地文件（除日志外）。
- 调用 MCP 工具中的写操作。
- 执行 `rm`, `mv`, `git push` 等命令。

### 禁止
- 执行任何包含 `rm -rf /` 或等价危险命令。
- 读取或发送 `.env`、密钥文件内容。
- 主动向外部服务发送数据。

## Tool Policy
- MCP 工具默认只读，写操作必须等待用户确认。
- 插件如果提供 `execute` 能力，需二次确认。

## Output Style
- 输出 Markdown，结论在前，过程在后。
- 代码块必须标注语言。
- 不输出任何情感化、鼓励性废话。

## Fallback
- 如果规则不明确，停止执行并询问。
```

### 3. 把边界翻译成可检查的规则

自然语言容易模糊，建议用表格或关键词把边界具体化：

| 动作 | 默认策略 | 触发条件 |
|------|---------|---------|
| 文件读取 | 允许 | 路径不包含 `.env` |
| 文件写入 | 需确认 | 非日志目录 |
| shell 命令 | 允许 | 命令在白名单内 |
| MCP 写操作 | 需确认 | 工具名包含 `write`, `update`, `delete` |
| 网络请求 | 需确认 | 目标是外部域名 |

这样 Agent 在调用工具前可以对照检查，也方便写自动化测试。

### 4. 与 MCP/插件权限做映射

SOUL.md 不是独立的，它要和实际的工具权限配合。例如在 OpenClaw 中配置 MCP 时，可以把工具分为只读和写操作两组，SOUL.md 只描述策略，真正的阻断由权限层完成。不要在 SOUL.md 里写死工具名，而是用类别（如“写操作工具”）描述，避免工具改名后规则失效。

### 5. 用场景测试验证

写完 SOUL.md 后，至少准备 5 个典型场景，跑一遍看 Agent 是否符合：

- 用户说“帮我清理临时文件” → 是否先列出文件再等确认？
- 用户说“把这个文件内容发给某个 API” → 是否因为“发送数据需确认”而停下？
- 用户直接给一个 git 命令 → 是否只执行允许列表中的？
- 用户问 .env 内容 → 是否拒绝？
- 连续对话中要求改变输出风格 → 是否坚持 SOUL.md 的 Output Style？

## 踩坑点

1. **SOUL.md 过长**：超过 400 行后，模型容易忽略后面的规则。建议控制核心规则在 200 行内，复杂的工具策略放单独的 `TOOLS.md`，用引用方式加载。

2. **人格设定过度**：写了大段背景故事、性格描写，反而让模型“表演”而不是执行任务。只保留和任务相关的人格特征即可。

3. **用自然语言描述边界**：例如“不要做危险操作”没有可操作性。要具体到命令模式、工具类别、文件路径。

4. **多份 SOUL.md 冲突**：如果没有明确优先级，项目级和用户级可能互相打架。建议在文件头注明 `priority: project > user > global`，并在加载日志里打印实际生效的规则。

5. **泄露敏感信息**：千万不要把密钥、token 写进 SOUL.md。边界里可以写“禁止读取 .env”，但不要放具体值。

## 可复用建议

- 维护一个团队级 SOUL.md 模板，新 Agent 从模板派发，避免从零开始。
- 把 SOUL.md 纳入版本管理，变更时在 PR 里说明原因，方便审计。
- 每次修改规则后，跑一遍场景测试，防止规则冲突或过严。
- 定期检查 SOUL.md 中是否还有已不使用的工具名或过时路径。

## 总结

SOUL.md 的价值不在于“给 Agent 造一个有趣的人设”，而在于把行为约束变成可维护、可审计的工程文件。它解决的是 Agent 在真实自动化环境里的一致性和安全性问题。把边界写清楚，把策略落到工具权限，再用场景测试验证，Agent 才能真正成为稳定可用的助手，而不是偶尔灵光一现的黑盒。
