## 背景：当 Agent 拥有文件系统的写权限

在 OpenClaw 这类自主 Agent 框架里，最常见的操作之一就是读写本地文件。代码生成助手需要落盘，数据处理流水线要写入中间结果，甚至简单的自动化脚本也要按日滚动日志文件。一旦你把系统提示词写好、工具函数注册完、事件循环跑起来，Agent 就开始频繁触碰你硬盘上的真实数据。

问题在于：**默认情况下，Agent 几乎拥有和当前进程同等的文件系统访问能力。** 如果它通过 MCP filesystem server 或 `subprocess` 调用了不加限制的 `write_file`，它既可以往 `/tmp` 写临时文件，也可以意外（或被诱导）修改 `~/.ssh/config`。对于把 Agent 作为本地生产力引擎的开发者来说，这就像给实习生直接开 root shell——信任的前提是约束。

## 问题拆解：我们需要怎样的护栏

理想的文件访问护栏不是简单的 “禁止写入”，而是精细到**目录级别的最小权限**。一个工程上可用的方案需要满足：

1. **白名单语义**：只允许读写显式声明的目录，其余路径一律不可见或不可写。
2. **路径规范化**：防止 `../../` 穿越，阻止符号链接绕过。
3. **与现有工具链兼容**：不破坏 MCP server、OpenClaw 的 Action 注册、以及 LLM 生成的路径参数。
4. **低侵入**：不需要重写 Agent 全部逻辑，也不要求 root 权限。

下面我以 OpenClaw + 本地 Python 插件为例，给出一种基于路径决议 + 白名单过滤的实践方案。

## 实现步骤：封装一层安全文件代理

### 1. 定义白名单配置

在 OpenClaw 的配置文件中增加一个 section，声明允许读写的目录列表：

```yaml
security:
  filesystem:
    allowed_dirs:
      - /home/user/projects/myagent/workspace
      - /tmp/agent_sandbox
    readonly: false  # 若为 true，则禁止一切写入
```

在运行时，将配置解析成一个 `list[Path]`，并全部解析为绝对路径。

### 2. 实现路径安全校验函数

核心是一个 `_resolve_safe_path(user_path: str, allowed_dirs: list[Path]) -> Path` 函数：

```python
import os
from pathlib import Path

def resolve_safe_path(user_path: str, allowed_dirs: list[Path]) -> Path:
    # 1. 基础解析，展开 ~ 和 ..
    raw = Path(os.path.expanduser(user_path)).resolve()
    
    # 2. 如果使用了符号链接，追踪到真实路径
    try:
        real = raw.resolve(strict=False)
    except OSError:
        raise ValueError("Invalid path")
    
    # 3. 检查是否位于任一白名单目录下
    for base in allowed_dirs:
        try:
            real.relative_to(base)
            return real
        except ValueError:
            continue
    
    raise PermissionError(f"Access denied: {user_path}")
```

这里的关键是 `resolve()` 会消除路径中的 `..` 和符号链接，避免常见的穿越攻击。注意 `strict=False` 允许路径暂不存在（写入新文件场景），之后创建文件时再使用安全返回的 `Path` 对象。

### 3. 替换工具函数中的文件访问

在注册给 OpenClaw 的文件操作工具（如 `read_file`、`write_file`）中，用安全函数包裹原有逻辑。

以 `write_file` 为例：

```python
from pathlib import Path

ALLOWED_DIRS = [Path("/home/user/projects/myagent/workspace").resolve()]

def safe_write_file(filepath: str, content: str):
    safe_path = resolve_safe_path(filepath, ALLOWED_DIRS)
    safe_path.parent.mkdir(parents=True, exist_ok=True)
    safe_path.write_text(content)
    return f"Written: {safe_path}"
```

对于 MCP filesystem server，如果使用的是 `@modelcontextprotocol/server-filesystem` 实现，可以直接利用其内置的 `--directory` 参数来限制可访问目录。启动时指定多个 `--directory` 即构成白名单：

```bash
npx -y @modelcontextprotocol/server-filesystem \
  --directory /workspace \
  --directory /tmp/sandbox
```

MCP server 自身会处理路径遍历，但如果你自定义了 MCP 工具，记得在工具层再次验证，防御深度。

## 踩坑记录

### 符号链接绕过

即便做了 `resolve()`，如果白名单目录本身包含指向外部的符号链接，Agent 仍可能顺着链接触碰到外部文件。**解决办法**：在解析白名单目录时也调用 `resolve()`，保证基准路径本身无符号间接引用。同时在构建容器化环境时，避免将敏感目录挂载到沙盒内。

### 相对路径的默认定向

LLM 生成的路径经常是相对路径，比如 `logs/run.log`。你必须明确相对路径的解析原点。建议强制将相对路径解析到白名单的第一个目录下，并在系统提示词中告知 Agent “所有相对路径都基于工作区 /workspace”。

### 权限回退混乱

当白名单包含 `/tmp/agent_sandbox` 时，该目录可能全局可写。在多用户环境下，这会引入进程间干扰。更稳妥的做法是使用 `mkdtemp` 创建唯一的子目录作为实际写入区，并将其纳入白名单，任务结束后清理。

## 可复用建议

- **白名单配置化**：通过环境变量 `AGENT_ALLOWED_DIRS` 注入，格式用 `:` 分隔，方便 CI/CD 中动态切换。
- **只读基础层 + 可写覆盖层**：用 `overlayfs` 将工具链的基础目录挂载为只读下层，Agent 只能修改上层工作目录。这对防止误改 SDK 或配置非常有效。
- **审计拒绝日志**：当 `resolve_safe_path` 抛出 `PermissionError` 时，把请求的原始路径、真实路径和时间写入日志，便于发现越权尝试和提示词注入攻击。
- **最小化 MCP 暴露**：如果你使用的是通用 filesystem MCP server，只挂载必要的目录，不要暴露整个家目录。可以把 MCP server 进程运行在独立的容器/用户下，进一步缩小 blast radius。

## 总结

给自动化脚本加本地目录白名单不是一个炫酷的功能，而是工程化 Agent 的必选项。通过一层轻量的路径安全封装，不改变 Agent 核心逻辑，就能把文件访问限制在可控范围内。结合 MCP server 的原生能力、合理的目录结构和日志监控，你可以在享受 Agent 自动处理文件的同时，把误操作和注入风险降到最低。

下一步，我会在 OpenClaw 的工作空间管理里加入 per-agent 的白名单模板，让每个不同任务的 Agent 从启动时就只看见它该看见的目录。
