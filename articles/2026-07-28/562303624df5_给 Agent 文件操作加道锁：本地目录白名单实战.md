## 背景

越来越多的 Agent 落地场景中，我们需要让脚本真正“动手干活”——读写日志、生成报告、整理本地文件。无论是通过 OpenClaw 的 exec 工具、MCP 的 filesystem 服务，还是直接在 Python 插件里调用 `open()`，一旦 Agent 能够触达文件系统，风险就随之而来。

一个配置不当的批量重命名脚本，可能因为一段拼接错误的路径把整个项目目录删得干干净净；一个外部 MCP 服务如果没有边界，理论上能读到任意用户目录下的敏感文件。遗憾的是，不少开发者只为“功能跑通”而忽略安全边界，等到误操作发生才后悔。

我在最近的一次自动化文件处理实践中，给 Agent 加入了本地目录白名单机制，下面把方案、细节和踩过的坑整理出来，供有同样需求的同学复用。

## 问题

假设我们通过 OpenClaw 暴露了一个自定义工具 `run_local_script`，内部会在当前机器上执行 bash 命令或 Python 代码。Agent 被允许在某个临时目录生成文件，但脚本里的一次 `os.remove()` 可能因为路径未过滤而意外删除了 `/home/user` 下的配置文件。如果工具没有任何护栏，等于给 Agent 发了 root 权限。

我们希望达到的效果：**所有文件写操作（读操作同理）都被限制在一个或多个指定的目录内，任何企图逃逸出白名单的操作直接拒绝。**

## 实现方案

### 1. 利用 OpenClaw 内置工作目录

如果你只依赖 OpenClaw 的 `exec` 工具（底层调用 shell），在项目根目录的 `openclaw.json` 里可以配置：

```json
{
  "exec": {
    "workspace": "/home/user/myproject/sandbox"
  }
}
```

这样 `exec` 的运行根目录就被限制在 `sandbox` 内，相对路径均以其为基准。但它的局限也很明显：它只约束了 `exec`，如果你引入了其他自定义工具（如 Python 函数工具），这些工具并不会自动继承该限制，需要单独处理。

### 2. 在 Python 工具中实现白名单校验

更通用的做法是封装一个路径校验函数，在所有文件操作前调用。核心逻辑只有一行：判断解析真实路径后的目标是否以白名单目录开头。

```python
from pathlib import Path

def is_allowed(path: str | Path, allowed_dir: Path) -> bool:
    target = Path(path).resolve()                # 解析成绝对路径，消除符号链接
    base = allowed_dir.resolve()
    try:
        target.relative_to(base)                # Python 3.9+
        return True
    except ValueError:
        return False
```

在实际工具函数里这样使用：

```python
ALLOWED = Path("/home/user/myproject/data").resolve()

def safe_write_file(filename: str, content: str):
    filepath = Path(filename)
    if not is_allowed(filepath, ALLOWED):
        raise PermissionError(f"Access to {filepath} is forbidden")
    ALLOWED.joinpath(filepath).write_text(content)
```

可以进一步封装为装饰器，在所有需要保护的工具函数上加 `@restrict_paths(ALLOWED)`，统一拦截首参数（如文件名）——这样减少漏加的风险。

### 3. MCP filesystem 服务的配置化白名单

如果你直接使用 `@modelcontextprotocol/server-filesystem` 官方服务，它已经提供了 `--allowed-directories` 参数，在启动时显式指定即可：

```bash
npx @modelcontextprotocol/server-filesystem /Users/me/safe-dir
```

该服务内部会强制校验，任何对目录外路径的请求都会返回错误。如果你自己实现 MCP 文件服务器，请务必在 `read_file`、`write_file` 等 handler 中加上上述校验逻辑。

## 踩坑清单

在实践中，下面三个问题最容易忽略：

1. **符号链接绕过**  
   即使目标文件通过符号链接挂在白名单目录内，只要链接指向外部，`resolve()` 会将其真实路径暴露出来，校验就会失败。但如果你有业务需求必须保留符号链接，需要自己实现“允许符号链接但校验目标”的递归逻辑。不过从安全出发，建议一律用 `resolve()`。

2. **路径穿越 `../`**  
   用户或 Agent 可能输入 `../../etc/passwd`。单纯用字符串前缀匹配 `if path.startswith('/safe')` 会被绕过。务必先转绝对路径再比较。哪怕你使用白名单基准目录拼接用户输入，也要在拼接后再次校验，防止用户输入包含 `..`。

3. **大小写与盘符（Windows）**  
   在 Windows 上 `D:\safe` 和 `d:\Safe` 可能被视为不同字符串。可用 `os.path.normcase` 统一成小写再比较，或使用 `pathlib.Path.resolve()`，它在 Windows 上也会规范化盘符大小写。另外注意 NTFS 的替代数据流等特性，不过一般 Agent 场景不易碰到。

4. **TOCTOU（检查与使用的时间差）**  
   在我们的场景中一般不是主要威胁，但如果你的 Agent 在高并发下操作同一文件，可能出现校验通过后文件被替换为符号链接的竞态。解决方案是使用 `openat` 类系统调用或先 `chdir` 到白名单根目录再使用相对路径操作，但对绝大部分自动化脚本，能在代码层面做好防御就够了。

## 可复用建议

- **封装一个统一的 `PathSecurity` 类**，包含 `allowlist` 列表、`validate()` 方法和便捷的 `safe_open()`，供所有工具模块引用。
- **新建项目模板里就带上这个模块**，哪怕一开始只有一个工作目录，也强制所有文件操作走校验函数，防止后续功能扩展时遗漏。
- **在日志中记录所有被拒绝的路径访问**，以便发现配置错误或 Agent 的越权尝试，方便快速定位。
- **白名单目录尽量具体**，如 `project/data/output`，而不是用户的家目录或 `/tmp`（`/tmp` 全局可写，会被其他进程干扰）。

## 总结

给 Agent 加文件访问护栏，本质上是在授权和风险之间划一道清晰的边界。它不需要复杂的技术栈，几行代码就能大幅降低误操作和恶意利用的概率。无论是 OpenClaw 工具的开发者，还是自建 MCP 服务器的工程师，都应该把“目录白名单”当作基础设施的一部分，而不是事后补丁。下次你在写 `open(filename, 'w')` 之前，不妨先问一句：这行代码真的应该拥有访问整个文件系统的自由吗？
