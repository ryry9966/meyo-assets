周末的一则业内消息，像一颗小石子砸进了深水池：Anthropic 的 Claude 模型，在 AMD 的最新 GPU MI300X 上成功跑通了推理与训练流程。一时间“CUDA 护城河一个周末崩了”的说法刷遍技术社区。我盯着那几条推送看了半天，脑子里只有一个念头——这事儿得好好拆解，不能被情绪带着跑。护城河是不是真的崩了？AMD 凭什么一夜之间能接到大模型厂商的单？对于每天对着 GPU 写代码的工程师来说，这到底意味着什么？

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-28/b9359816563552b8.png)

## CUDA 为什么能统治 20 年

要看清这次“裂缝”的成因，必须先理解 NVIDIA 用 CUDA 垒起的城墙到底有多厚。不是靠一块好显卡，而是一套让开发者几乎无法挣脱的生态。

- **硬件先发与全覆盖**：2006 年 CUDA 诞生，比任何竞争对手都早了至少五年。等到别人追上来，NVIDIA 已经从消费级的 GeForce 到数据中心级的 H100，用一套统一的编程模型覆盖了所有产品线。开发者学会一次，就能在所有 NVIDIA 卡上部署。
- **软件栈的“水泥加固”**：cuDNN 做深度学习卷积、cuBLAS 搞矩阵乘法、TensorRT 做推理优化，还有 NCCL 处理多卡通信。这些库不是随便写的，是针对每一代架构用汇编级别的 kernel 调出来的。任何替代方案想达到同等性能，都得经历同样漫长的打磨。
- **学术与工业界的惯性**：2012 年 AlexNet 用 CUDA 跑出 ImageNet 冠军后，几乎所有深度学习框架的第一后端都是 CUDA。论文里的实验、开源模型的官方实现、云厂商的默认镜像，全部默认 NVIDIA。没人会因为“可能省钱”去踩一个不成熟的生态坑——这是典型的路径依赖，却异常牢固。

简单说，CUDA 护城河不是一道墙，而是由硬件、库、工具链、开发者习惯和行业标准浇铸成的钢筋混凝土层。过去十年，AMD 不是没尝试挖角，但每次挖到一半就发现铁锹断了。

## AMD 这次凭什么撬动了 Anthropic

AMD 的 MI300X 并不是突然从石头里蹦出来的救世主，但它和几股关键力量合流，才让这场“穿墙行动”有了实质进展。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-28/c88572c89adb1a97.png)

- **硬件规格终于对齐**：MI300X 拥有 192GB 的 HBM3 显存，带宽 5.3TB/s，单卡就能装下 70B 参数的模型做推理，而 H100 的 80GB 版本得组双卡。在大模型推理这种对显存容量极度饥渴的场景下，AMD 第一次在硬指标上占了上风，给软件适配提供了值得投入的理由。
- **ROCm 不再是摆设**：AMD 的 ROCm 6.1 版本其实默默补了很多课。HIP 转译工具可以让不少 CUDA 代码自动迁移，MIOpen 库对标 cuDNN 的算子覆盖率大幅提升。虽然仍远谈不上丝滑，但至少从“完全不可用”变成了“值得一试”，尤其当你有一个强悍的工程团队愿意做底层调优的时候——没错，Anthropic 就有这样的团队。
- **大客户协同开发的动力**：这次不是 AMD 自己喊“我又行了”，而是 Anthropic 主动投入资源。为什么？算力采购成本。NVIDIA 的卡又贵又稀缺，作为 AI 独角兽，把全部赌注押在一家供应商上，风险太高。Anthropic 需要谈判筹码，也需要真实的第二供应商。于是他们和 AMD 的工程师一起，针对 Claude 的推理管线做定向优化，直接绕开了一些尚不成熟的通用接口，用最暴力的方式打通了链路。
- **版本答案是“推理先行”**：注意，Anthropic 公开的进展更侧重于推理。推理管线相对训练更干净，不需要处理那么复杂的分布式梯度同步，对算子的完备性要求也低一些。从推理切入，是打破垄断最务实的路径。

所以这不是 AMD 一夜之间追平了 CUDA，而是一个顶级甲方带着明确的业务压力，在一套边际成本可接受的硬件上，完成了一次工程上的“硬闯”。

## 真正的裂缝：软件栈正在被重新定义

如果只有 AMD 硬件变强和 ROCm 变好，那护城河最多是被水冲刷出几个小坑。真正导致结构性松动的，是大模型时代软件栈的重心正在脱离裸 CUDA。

- **编译器中间层的崛起**：PyTorch 2.0 引入的 `torch.compile`，背后依赖 Triton 这样的开源编译器。Triton 能让你用类似 Python 的语法写 GPU kernel，然后自动编译到 NVIDIA 或 AMD 硬件上。OpenAI 自己就用 Triton 来写一些定制 kernel，因为它可以跨硬件部署。这意味着框架层面正在形成一个新的抽象层，把底层是 CUDA 还是 ROCm 的差异给屏蔽掉。开发者写模型代码时，不再需要直接跟 cuBLAS 打交道，PyTorch + Triton 就能帮你生成 AMD 可执行的代码。
- **LLM 推理框架的原生异构支持**：vLLM、TensorRT-LLM 这类推理框架，越来越多地把硬件适配做成插件化。vLLM 已经有了 AMD ROCm 的后端分支，尽管性能和稳定性还在追赶，但架构上已经证明异构是可行的。当框架开始不绑定硬件，用户选卡的灵活性就指数级上升。
- **模型架构的收敛**：目前主流的 Transformer 结构，算子类型其实很有限：矩阵乘、注意力、LayerNorm、激活函数。只要 AMD 能把这些“黄金算子”狠狠优化好，就能覆盖 80% 以上的大模型负载。不像过去，各种稀奇古怪的网络结构让生态适配无穷无尽。现在靶子变少了，想丢飞镖就更容易命中。

说白了，CUDA 的护城河并没有消失，但它阻挡的那片战场正在从“每一行 kernel 代码”往上层迁移。当胜负的关键变成编译器和中间表示时，NVIDIA 的底层锁定能力就被削弱了。

## 别急着喊“崩了”：冷思考与三条务实建议

这件事的分寸感很重要。过度渲染“CUDA 完了”和完全漠视变化，同样有害。Anthropic 跑通 MI300X 的确在护城河上打出了一条可观测的裂缝，但 NVIDIA 的生态根基依然深厚：一整套经过出厂验证的分布式训练工具、全球数十万计的 CUDA 工程师、以及因为规模效应而来的单位算力能效优势，并不会因为一家客户的单点突破就烟消云散。对普通开发者来说，明天你打开 GitHub 克隆一个开源项目，大概率还是看到 `device = cuda` 和 `nvidia-smi` 的截图。变化是真实的，但扩散需要时间。

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-28/12ecb2c41ff892d0.png)

基于这个现实，我整理三条不虚不空的行动建议：

1. **学 Triton，不站队**  
   无论未来是 NVIDIA 继续称霸还是 AMD 突然雄起，Triton 这类编译器语言都会是跨硬件的核心技能。花一周时间看完 Triton 官方教程，试着把一段自定义 attention 用 Triton 重写，你就能同时为 CUDA 和 ROCm 生成优化 kernel。这是目前成本最低的“护城河免疫针”。

2. **推理场景优先评估 AMD 方案**  
   如果你所在的团队正在做大规模 LLM 推理部署，而且对显存容量极度敏感（比如要跑 70B 模型又在乎吞吐），可以拿单块 MI300X 做一次成本核算。不要指望开箱即用，要给至少两名工程师留出 2-4 周的适配时间，但一旦跑通，硬件成本可能比同场景 H100 方案低 30% 以上。前提是你们能容忍一定的不稳定性和调优投入。

3. **盯紧开源框架的硬件后端更新**  
   关注 vLLM、SGLang、PyTorch 的 ROCm 分支更新频率和 issue 数量。当这些框架的 AMD 后端开始被标注为“稳定”而不是“实验性”时，就是大规模迁移的临界点。在那之前，保持观察、偶尔上手测一测，比到时手忙脚乱要强得多。

最后说一句个人体会：工程师最大的护城河，从来不是某个公司的 SDK，而是对计算本质的理解。GPU 的本质是并行计算模型和内存层次结构，万变不离其宗。把这一点吃透，无论 CUDA 还是 ROCm，都只是你工具箱里的不同扳手而已。
