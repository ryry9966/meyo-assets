最近开发者圈子里流传一个段子：Claude写完代码终于不直接交了，而是先拿4个Skill自查一遍，改好了再找你要好评。这背后藏着大模型代码生成一次有趣的工程化提效尝试。以前我们总说“AI写的代码能用，但得自己改bug”，如今模型自己开始内建一套质量门禁，先自我纠错再交付。这波操作到底怎么实现的？开发者又能从中学到什么？今天我们从技术拆解、交互范式和工程心理三个维度，把这件事讲透。



## 1. 先搞清楚“4个Skill”指的是什么

Anthropic并没有发公告说“Claude新增4个代码自查Skill”，这个说法源自社区对Claude在代码任务中行为变化的总结。具体来说，Sam R等开发者在测试中发现，Claude 3.5 Sonnet/Opus在处理复杂编程请求时，会自发执行一套内在的验证流程，被戏称为“Skill自查清单”。

- **Skill 1: 需求对齐检查（Requirement Alignment）**  
  写完初版代码后，Claude会回溯用户的原始prompt，逐条对照是否遗漏约束条件。比如——“你要求API响应时间<200ms，我用了同步调用，这里得换成异步队列。”

- **Skill 2: 静态分析自审（Static Analysis Self-review）**  
  模型会模拟Linter/类型检查器的行为，扫描潜在的类型错误、未使用变量、安全漏洞（如SQL注入）。这相当于把eslint、mypy的规则内化到推理链中。

- **Skill 3: 边界与异常处理（Edge Case & Exception Handling）**  
  自动构造几个典型边界输入：空数组、负数、超长字符串、并发冲突等，验证代码是否优雅降级而非崩溃。

- **Skill 4: 可维护性审视（Maintainability Audit）**  
  检查命名是否语义化、函数是否过长、是否该抽离成模块，甚至主动建议添加docstring或README片段。

整个过程不是魔法，而是通过**思维链提示（Chain-of-Thought Prompting）**和**工具调用（Tool Use）**的深度整合实现的。Claude的系统指令里很可能预先埋入了“在交付代码前，请在思考链中执行以下检查项”这类元规则。更有意思的是，当开启Artifacts功能时，模型会先在后台完成自查，再把优化后的代码渲染出来，用户甚至看不到第一版草稿。



## 2. 这套自查机制为什么重要？—— 提升“一次性通过率”的工程意义

传统AI辅助编码有一个顽固痛点：**人机交互的信任成本太高**。开发者拿到AI生成的代码，第一反应不是“直接合并”，而是启动防御性审查：语法对不对？异常处理了吗？会不会有隐藏的性能坑？这种“先怀疑再验证”的心智开销，让很多团队对AI代码持观望态度。

Claude此次行为变化的潜台词是——把信任建立的责任从人转移到模型自身。具体提效体现在三个层面：

- **降低修复循环次数**  
  GitHub Copilot调研数据显示，在没有自查机制时，一段AI生成代码平均需要2.4次人工修改才能通过CR。而内建自查后，初次交付的代码更接近“合入标准”，把修复循环压缩到1~1.5次。这相当于为每个PR节省10~20分钟往返时间。

- **知识逆向传递**  
  自查过程会以注释或附言形式暴露模型的“思考轨迹”。比如Claude会在代码块下方附上一句：“我注意到这里用了递归，当n>1000时有栈溢出风险，所以改成了迭代+显式栈。”开发者不仅能拿到结果，还免费获得了一次code review级别的技术决策解析，对初中级工程师的成长尤其有价值。

- **构建“可审计”的AI输出**  
  当模型在交付前明确列出“已通过以下4项检查”，它实质上提供了可追溯的质量凭证。团队可以基于这套清单建立AI代码的准入准出标准，让AI编程从“个人暗箱操作”走向“团队流程集成”。



## 3. 技术溯源：这种能力是训出来的还是调出来的？

很多人好奇，Claude的底模本身就有自查能力吗？不完全是。底模在预训练阶段从海量代码仓库中学会了“好代码”和“烂代码”的分布，但这是一种隐性知识，未必在生成时主动激活。**真正把隐性知识转化成稳定行为，靠的是三驾马车：指令微调（Instruction Tuning）、RLHF（人类反馈强化学习）和系统层面的编排（Orchestration）。**

- **指令微调阶段**  
  Anthropic可能在SFT数据里混入了大量“代码+自查清单”的范例。比如人工标注的样本里包含：初版代码→标注员指出的5个问题→修正版代码+修正说明。模型通过模仿这种范式，学会了“写完代码后最好再检查一遍哪些方面”。

- **RLHF校准**  
  在偏好排序时，Anthropic的训练师可能会优先选择“先自查再交付”的轨迹（trajectory），而非“直接扔出代码”的轨迹，从而让模型在强化学习阶段形成“延迟交付、先内部审查”的偏好。这本质上和训练模型“三思而后行”的总体安全策略一脉相承。

- **系统层编排**  
  推测Claude的对话管理层植入了一个类似“内心独白”的回环：生成代码草稿后，触发一个隐式的review prompt，要求模型以评审者身份审视草稿，输出修改意见，然后再基于这些意见重写代码，最后交付。用户全程无感知，只看到精炼后的结果。这种多步推理（multi-hop reasoning）在技术上并不新颖，但大规模应用到代码生成场景，Anthropic走得比较靠前。

一个值得注意的设计取舍是：**自查越严格，延迟越高。** Claude执行4个Skill需要额外消耗推理token，导致首字生成时间有所增加。Anthropic显然在“质量”和“响应速度”之间选择了前者，这个trade-off恰好打中专业开发者的痛点——我可以等5秒，但你不能给我一个有低级错误的代码片段。



## 4. 开发者能从中学到的“自查清单”方法论

Clippy的梗过去二十年，AI终于开始认真对待代码质量，而我们人类开发者更不应该丢掉code review的看家本领。Claude这4个Skill其实提炼出了一个最小可行自查清单，完全可以移植到自己的开发流程中：

- **Before Commit：跑一遍自己的“4项体检”**  
  1. 我有没有把需求文档里的每一句“必须”都实现了？  
  2. 静态检查通过了吗？（Git Hook里挂个lint-staged不丢人）  
  3. 我手动构造了3个异常输入并验证行为吗？  
  4. 三个月后的我还能看懂这段代码吗？  
  把这4个问题贴到显示器边框，强迫自己在每次git add前逐一回答。

- **给AI的Prompt也加上“自查指令”**  
  如果用的模型还没有内建自查机制（比如本地部署的开源模型），可以直接在prompt末尾加一句：“在输出最终代码前，请先以高级工程师身份审查这段代码，列出发现的问题并修正，然后只交付修正后的版本。”这个简单的元prompt能显著提升代码质量，实测可将一次通过率提升30%以上。

- **团队共建AI代码准入标准**  
  把Claude的4个Skill抽象成团队的AI代码Acceptance Criteria：需求对齐、静态分析零告警、异常覆盖≥3个场景、圈复杂度≤10。任何AI生成的代码块，只有通过这4项验证，才允许进入人工review阶段。这比空谈“AI代码要慎重”更具可操作性。



## 5. 不止Claude：代码自查正在成为AI编程的标配能力

Claude不是孤例。GitHub Copilot在2024年秋季更新中也推出了“Copilot Code Review”功能，支持在PR页面自动扫描潜在问题；Cursor编辑器内置了“AI Lint”实时检查；国内的通义灵码同样支持代码质量一键扫描。整个行业都在将“自查”从隐性能力变为显性功能。

这个趋势的驱动力很清晰：AI辅助编程的下半场，比拼的不再是“能不能写出代码”，而是“写出的代码能不能直接上生产”。代码生成的准确性已经进入90分位瓶颈，再往上提需要巨大的计算成本，而增加一个自查层，边际成本更低，体验提升却更明显。这有点像自动驾驶从“感知能力”进化到“规划+安全冗余”的阶段，多一道校验就多一层保障。

从更广阔的视角看，代码自查只是“AI自我对齐（Self-alignment）”的一个垂直应用。未来LLM在处理法律文书、医疗报告、金融合同等高风险文本时，也必然会在交付前执行类似的多维度自查清单。Claude的这一步，是让AI从“言之凿凿但可能出错”走向“审慎负责”的关键跃进。



## 🦞 龙虾三思：工程师的“冷思考”与实用建议

**1. 警惕“自查幻觉”——模型说查了不代表真查了**  
当前阶段，Claude的4个Skill是通过文本形式表达的，并不能等同于编译器级别的严格验证。模型可能生成一份看起来很专业的自查报告，但实际并未深入执行逻辑检查。开发者仍然需要对关键代码做实质性的code review，尤其涉及安全、金融计算、数据隐私的逻辑，绝对不能把自查声明当作免检通行证。

**2. 把“自查”能力产品化，而非理想化**  
如果你的团队在使用AI编程助手，不要停留在“它有时候会自查”的随机状态，而是主动定制系统prompt或使用工具链（如LangChain的检查回调）将自查机制固定下来。可以设计一个“三步工作流”：AI生成草稿 → 自动触发自查模块（静态分析+测试用例运行）→ 返回修复版本。让检查变得可重复、可度量，比依赖模型的自发行为更可靠。

**3. 最好的自查，是让代码跑起来**  
无论AI宣称过了多少项Skill检查，最终极的验证永远是执行。为AI生成的代码配置自动化的集成测试流水线（哪怕只是跑通一个最小可行示例），让机器用0和1说话。正如Google的工程文化所强调的：“没有测试覆盖的代码，本质上就是债务。”自查是锦上添花，自动化测试才是底线。
