# 给 Agent 脚本套上缰绳：本地文件访问白名单实战

## 背景：当自动化脚本开始“四处乱逛”

随着 OpenClaw、MCP 以及各种 LLM Agent 插件生态的成熟，让大模型操作本地文件已经变得非常容易。你只需要接一个文件系统 MCP 服务器，或者在 Python 脚本里调用 `open()`，Agent 就能帮你整理文档、处理日志、生成报告。

但能力越强，风险越大。一个没有任何约束的 Agent 进程，可能会因为 prompt 偏差或模型幻觉，把 `/etc/passwd` 当成日志文件解析，或者删掉存放 SSH 密钥的目录。即便调用者是可信的，模型输出的具体路径本身是不可完全预测的——把文件操作权限暴露在整个文件系统上，本质上是在用一种昂贵的随机数生成器赌你的磁盘内容。

因此，我们需要给自动化脚本加一道护栏：只允许在预设的本地目录白名单内进行读写操作，越界即拒。

## 问题拆解：白名单校验到底要防什么？

直观方案是在每个文件操作前检查路径是否以白名单目录为前缀。但现实比这复杂：

1. **符号链接逃逸**：白名单目录下某个符号链接指向外部敏感路径，如果不做解析，攻击者（或失控提示）可以通过它访问禁地。
2. **路径规范化**：`/data/../etc/shadow`、`/data///secret`、相对路径 `../../root/.ssh` 都可能绕过简单的前缀匹配。
3. **竞态条件**：检查时路径正常，检查后通过符号链接替换或目录重命名实现了逃逸（TOCTOU）。这在 Agent 并发操作场景下不是理论问题。
4. **平台差异**：Windows 的盘符、大小写不敏感、`\` 与 `/` 混用都需要统一处理。

真正的文件访问护栏，需要在一个可靠的安全边界内完成：**解析真实路径 → 判定是否落在白名单内 → 以安全的原子方式打开**。

## 实践：用 Python 实现可复用的目录白名单装饰器

我们以 OpenClaw 生态常用的 Python 自动化脚本为例，提供一个可以直接嵌入工具函数或 MCP 服务器内部的解决方案。目标：任何试图进行文件 I/O 的自定义函数，都能通过一个装饰器自动完成准入控制。

### 第一步：定义白名单与辅助函数

```python
import os
from pathlib import Path
from functools import wraps

# 白名单目录列表，所有路径都会被规范化存储
ALLOWED_DIRS = [
    Path("/home/user/agent_workspace").resolve(),
    Path("/tmp/agent_sandbox").resolve(),
]

def is_path_allowed(target: Path) -> bool:
    """校验真实路径是否落在任一白名单目录下"""
    try:
        real_path = target.resolve(strict=False)
    except Exception:
        return False
    for base in ALLOWED_DIRS:
        try:
            real_path.relative_to(base)
            return True
        except ValueError:
            continue
    return False

def sanitize_path(user_input: str, base_dir: Path = None) -> Path:
    """
    将用户提供的相对路径安全地映射到允许的基础目录内，
    若未指定 base_dir 则默认使用第一个白名单目录。
    """
    base = Path(base_dir) if base_dir else ALLOWED_DIRS[0]
    base = base.resolve()
    # 只取相对路径的纯文件名部分，防路径穿越
    safe_name = Path(user_input).name
    return (base / safe_name).resolve()
```

关键点：`resolve(strict=False)` 会消除所有 `..` 和符号链接，得到最终的真实路径。`relative_to` 用于判断归属关系，比字符串 `startswith` 安全得多。

### 第二步：装饰器实现文件操作拦截

```python
def file_guard(func):
    """装饰文件操作函数，自动对第一个路径参数进行白名单校验"""
    @wraps(func)
    def wrapper(*args, **kwargs):
        # 假设文件路径是第一个位置参数，或通过 file_path 关键字传入
        path_arg = args[0] if args else kwargs.get("file_path")
        if path_arg is None:
            raise ValueError("文件路径参数缺失")
        target = Path(path_arg).resolve()
        if not is_path_allowed(target):
            raise PermissionError(f"拒绝访问: {target} 不在允许目录内")
        return func(*args, **kwargs)
    return wrapper

@file_guard
def read_agent_file(file_path: str):
    with open(file_path, "r") as f:
        return f.read()
```

如果需要同时约束读和写，可以在装饰器中注入更细粒度的模式检查，例如通过参数 `mode` 判断是否允许写入。

### 第三步：应对 TOCTOU 的强化方案（可选项）

在不考虑内核级审计的脚本场景中，最务实的加固方式是在 `open()` 之前使用 `os.open()` + `O_NOFOLLOW` 打开文件描述符，然后用 `os.fdopen()` 获得文件对象。这样可以防止符号链接被替换：

```python
import stat

def safe_open(path: Path, mode: str):
    # 确保上级目录没有被路径穿越
    if not is_path_allowed(path.parent.resolve()):
        raise PermissionError("父目录不在白名单内")
    flags = os.O_RDONLY if 'r' in mode else os.O_WRONLY | os.O_CREAT
    flags |= os.O_NOFOLLOW
    fd = os.open(str(path), flags, 0o644)
    return os.fdopen(fd, mode)
```

不过，如果 Agent 需要支持创建符号链接本身的操作，则需要更复杂的安全策略，这超出了基本护栏的范畴，建议直接禁止 Agent 创建符号链接。

## 踩坑记录：那些看似安全的写法

**坑 1：用字符串前缀判断归属**

`"/var/log".startswith("/var")` 会返回 `True`，但当我们把白名单改成 `/var/app`，`/var/log` 仍然会通过。必须用 `Path.relative_to` 或在字符串比较后追加一个路径分隔符进行校验——即便如此也不如 `Path.resolve()` 可靠。

**坑 2：忘记解析符号链接**

白名单目录本身可能就是通过符号链接创建的挂载点，如果不对最终路径做 `resolve()`，一个指向 `/etc` 的符号链接可以轻松突破。

**坑 3：`os.path.realpath` vs `Path.resolve`**

二者行为类似，但 `Path.resolve` 在 Python 3.6+ 中对 Windows 支持更一致，且返回 Path 对象，可读性更好。建议统一使用 `pathlib`。

**坑 4：Windows 上的盘符与长路径**

在 Windows 下，`C:\Users` 和 `C:/Users/../Users` 解析后可能因大小写产生不同的字符串表示。务必用 `resolve()` 归一化，必要时还可以加入 `os.path.normcase` 处理大小写。

## 可复用建议：把护栏变成基础设施

1. **封装成库**：将白名单校验、安全打开函数、装饰器打包成一个内部 Python 包，直接在各个 Agent 工具实现中引用，避免重复造轮子。
2. **集成到 MCP 服务器**：如果你在维护一个自定义 MCP 文件服务器，在 `read_file`、`write_file` 等工具入口处调用白名单校验，而不是依赖每个客户端自觉遵守。
3. **日志与告警**：对每一次拒绝访问记录完整的目标路径、归一化结果、堆栈信息。这些日志能帮你快速发现是模型幻觉还是真实的恶意尝试。
4. **配置化管理**：将白名单目录列表通过环境变量或配置文件注入，而非硬编码。当需要给另一个 Agent 实例分配不同工作区时，无需修改代码。
5. **最小权限原则**：即便在白名单目录内，也可以根据 Agent 职责分离读写权限（例如只允许在 `/tmp/agent_output` 写，在 `/data/corpus` 读）。

## 总结

给自动化脚本加上文件访问白名单，不是过度防御，而是让 AI 工具变得“可投产”的必要一步。路径解析、归属判定、TOCTOU 缓解这三板斧，配合装饰器和配置化封装，可以在不牺牲开发效率的前提下构筑一条清晰的物理边界。

在工程里，护栏的价值不在于杜绝所有攻击，而在于把事故爆炸半径限制在可以承受的范围内——对于自动操作本地文件的 Agent 来说，这道白名单就是最重要的第一道防线。

文中的代码片段均为生产可用的简化版，你可以根据实际工具链进行扩展，但核心思路保持不变：**永远不信任未解析的路径，永远不在白名单之外打开文件句柄。**
