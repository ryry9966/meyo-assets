# 给自动化脚本系上安全带：Agent 文件访问白名单的工程实践

## 背景：当 Agent 学会了“自由行走”

OpenClaw 这类 Agent 框架让 LLM 不仅能对话，还能通过 MCP 工具或自定义插件执行本地脚本。典型场景是：用户给 Agent 一个目标，它生成 shell 或 Python 脚本，借助 `execute_in_process` 这类能力在宿主机上直接运行。这带来了生产力和风险的双重放大——一个看似无害的 `rm -rf`，一个路径拼接错误，就可能让 Agent 从助手变成破坏者。

传统做法是依赖操作系统级沙箱，如 Docker 容器、chroot 或 macOS 的 sandbox-exec，但在开发验证环境或非容器化部署中，我们往往需要在“裸机”上为 Agent 脚本加上一道轻量护栏。本文聚焦一种更小粒度、更易集成的方案：**为脚本进程施加本地目录白名单**——只允许它读写我们事先划定的安全目录。

## 问题定义

我们希望达到的效果：

- Agent 发起的每一个文件 I/O（读、写、创建、删除）只能发生在指定白名单目录内，例如 `/tmp/agent-workspace`、`./data` 等。
- 尝试访问白名单以外的路径应被拒绝，并产生可审计的日志。
- 方案要对现有脚本侵入性小，最好作为 wrapper 层嵌入到 OpenClaw 的工具调用栈中，无需改动 Agent 本身的提示词或推理逻辑。

## 方案设计

核心思路是在 Python 层拦截文件系统调用。我们不追求 hook 系统调用（strace/ptrace 那太重），而是提供一套安全的路径检查函数，要求脚本通过这些安全的封装来操作文件。具体做法：

1. **定义白名单集合**：由配置文件或环境变量指定若干绝对目录。
2. **路径规整与校验**：使用 `os.path.realpath()` 将路径解析为绝对路径，消除符号链接、相对路径、`..` 等干扰；然后检查规整后的路径是否以任一白名单目录开头。
3. **安全文件操作包装器**：提供 `safe_open()`、`safe_remove()`、`safe_rename()` 等，内部先校验，再委托给标准库函数。
4. **集成到 Agent 工具**：对于 Python 脚本，可用导入钩子或显式替换 `open`；对于外部 shell 脚本，则用 Python 进程包装器作为 `execute` 的前置检查层，在启动子进程前验证参数中出现的文件路径。

## 实现步骤（Python 版最小可用架子）

```python
import os
import functools

# 从环境变量读取白名单目录（逗号分隔的绝对路径）
_raw = os.environ.get("AGENT_SAFE_DIRS", "/tmp/agent-workspace")
SAFE_DIRS = [os.path.realpath(d) for d in _raw.split(",")]

def is_path_safe(target: str) -> bool:
    """校验规范化后的目标路径是否落在白名单目录内。"""
    resolved = os.path.realpath(target)
    for safe_dir in SAFE_DIRS:
        if resolved.startswith(safe_dir + os.sep) or resolved == safe_dir:
            return True
    return False

def safe_open(file, mode="r", *args, **kwargs):
    if not is_path_safe(file):
        raise PermissionError(f"Agent 未授权路径: {file}")
    return open(file, mode, *args, **kwargs)

def safe_remove(path):
    if not os.path.exists(path):   # 避免绕过校验
        raise FileNotFoundError(path)
    if not is_path_safe(path):
        raise PermissionError(f"Agent 未授权路径: {path}")
    os.remove(path)
```

把这个模块做成一个工具，Agent 调用文件操作时统一 import。在 OpenClaw 的工具注册中，可以提供 `safe_file_write`、`safe_file_read` 这类 MCP 工具，内部强制走安全接口。

## 集成到非 Python 脚本

如果 Agent 要执行 Shell 脚本，可以在执行前用 Python 包装器解析命令字符串，提取路径参数并预检。一个更稳健的方式是：把 shell 脚本的 `CWD` 限制在白名单目录，并配合操作系统权限（如用 `setfacl` 或临时用户）只给该目录读写权限。但本文主题是本地目录白名单层，不做展开。

## 踩坑记录

1. **符号链接绕过**  
   必须使用 `os.path.realpath()` 而非 `abspath()`。`abspath` 只是拼接当前目录，不展开符号链接。攻击者可以在白名单目录下创建一个指向 `/etc/passwd` 的符号链接，如果校验不充分，就可能被绕过。`realpath` 会一直追溯到物理路径。

2. **路径缀加陷阱**  
   简单的前缀匹配 `resolved.startswith(safe_dir)` 需要小心：`/tmp/agent-workspace` 和 `/tmp/agent-workspace2` 可能造成错误放行。规范做法是要求匹配后下一个字符是路径分隔符，或完全相等。

3. **相对路径的欺骗**  
   如果脚本传入 `../../etc/passwd`，依赖工作目录的白名单可能失效。因此校验时必须使用解析后的绝对路径，而与进程当前工作目录无关。同时建议将脚本的 `cwd` 设置为白名单目录，作为纵深防御。

4. **Windows 兼容性**  
   盘符和大小写不敏感可能让 `startswith` 出错。可统一转换为小写并加上 `os.path.normcase`；也可以用 `os.path.commonpath` 来校验归属关系。

5. **性能与可维测试性**  
   频繁调用 `realpath` 会有系统调用开销，但对于 Agent 工具调用频率通常可接受。测试时必须覆盖各种恶意路径样本，包括空字符串、特殊字符、超长路径等。

## 可复用建议

- **配置化白名单**：通过环境变量或 OpenClaw 的 agent 配置注入，不同任务可设置不同白名单。
- **审计日志**：每次校验失败都记录完整路径、调用栈和时间，便于回溯 Agent 的越界企图。
- **与 MCP 工具深度结合**：把 `safe_open` 等封装成标准的 MCP `tools`，让 Agent 只能通过它们访问文件，从入口屏蔽裸调用。
- **通用拦截层**：如果团队大量使用 `subprocess` 执行脚本，可编写一个 `execute_safe` 函数，在接受命令列表后先扫描参数中的路径并校验，再调用 `subprocess.run`。
- **边界测试集**：准备一组已知的风险路径（包括空格、Unicode、NULL 字符等），作为持续集成的一部分，确保护栏不会被裁剪或绕过。

## 总结

为 Agent 的自动化脚本增加本地目录白名单，是一项低成本、高回报的安全加固手段。它不能替代完整的沙箱，但在开发调试和中等风险场景下，能有效防止模型产生的破坏性文件操作。实现的核心在于路径规范化和严格的归属校验，陷阱多但可逐一化解。以包装器形式嵌入工具链，既能维持现有脚本的灵活性，又能让护栏透明且可审计。在你的下一个 Agent 工具里，不妨先加上这个“安全带”。
