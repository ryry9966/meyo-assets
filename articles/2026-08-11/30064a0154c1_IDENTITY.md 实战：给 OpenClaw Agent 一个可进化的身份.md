## 一、背景：被“失忆”的 Agent 逼出来的需求

在 OpenClaw 生态里，Agent 的生命周期经常是这样的：你精心设计了一段系统 prompt，定义好它的角色、底线、工具使用方法。第一个会话跑得不错，第二个会话你重启容器，Agent 又回到出厂状态——所有对话中沉淀的经验、用户偏好、临时学到的规则全部消失。于是你开始往 prompt 里塞“记住 xxx”，每次都要在对话开头复述上下文，Agent 行为变得不稳定且 token 消耗直线上升。

更麻烦的是，一旦 Agent 通过 MCP 调用外部服务或者插件，学习到的交互模式（比如某个 API 今天返回结构变了，Agent 临时调整了解析逻辑）完全没有地方持久化。下次遇到同样的接口变化，它又会重新犯错。

这就是 **IDENTITY.md** 想要解决的核心问题：让 Agent 的身份不仅是初始 prompt，而是一个**可持久化、可安全进化的文件**，Agent 自己能够基于真实交互记录去更新这一文件，同时保持骨架不出轨。

## 二、IDENTITY.md 不是什么高深的魔法

在 OpenClaw 的实现里，IDENTITY.md 就是一个放在 `.openclaw/identity/` 下的 Markdown 文件。Agent 启动时会将其注入系统消息的最前端，对话结束后，根据策略，Agent 可以通过内置的 `identity_update` 工具（本质是一个受限的文件写入器）修改该文件。

它的价值不在格式本身，而在于**更新机制的设计**：

- **骨架固定，记忆生长**：文件用 YAML front matter 区分不可变元数据（角色定义、安全约束、工具白名单）和可变记忆区（user_profile、learned_rules、skill_levels）。
- **带版本和签名的写入**：每次更新都会自动生成一个 `.openclaw/identity_history/` 下的备份，并且支持 diff 回滚。
- **Agent 触发的更新需满足约束**：例如只能修改 `## Memory` 下的内容，且必须通过结构化的 `<identity_patch>` 标签输出，防止 Agent 一顿胡写把角色改崩。

也就是说，IDENTITY.md 是一个**受控的、可审计的自我进化载体**，而不是一个开放给 Agent 随便写的记事本。

## 三、从零构建一个可进化的身份

下面是一个工程化落地的步骤，假设你已经有一个跑在 OpenClaw 上的 Agent，并且希望它随着使用越来越懂你。

**1. 初始化 IDENTITY.md**

在项目根目录创建 `.openclaw/identity/agent_identity.md`，最小结构如下：

```markdown
---
id: agent-001
role: "ClawBot 技术助手"
constraints: ["不回答非技术问题", "使用中文", "优先引用官方文档"]
created: 2025-03-15
---
# Core Identity

你是一个专注于 Linux 运维与 Python 开发的助手。

## Memory
<!-- 以下区域可由 Agent 通过工具更新 -->
- 用户偏好: 未记录
- 学到的规则: 无
```

**2. 配置 Agent 加载该文件**

在 OpenClaw 的 agent 配置中（如 `agent.toml` 或通过 MCP 的 `openclaw://identity` 资源），指定 identity 文件路径。Agent 启动后，系统消息会拼接成：

```
[IDENTITY]
... 文件内容 ...
[END IDENTITY]

当前对话开始。
```

**3. 实现“进化”工具调用**

Agent 在一次对话中识别到可沉淀的信息时，会调用 `update_identity` 工具，参数是一条 patch 指令。Agent 内部生成类似：

```
<identity_patch>
{
  "section": "Memory",
  "operation": "append",
  "content": "- 用户偏好: 输出命令结果时使用 table 格式，不要用 json"
}
</identity_patch>
```

框架收到后，会校验该 patch 是否在允许更新的区域内，以及格式是否正确，然后写入文件，同时备份。

**4. 引入人工审核（可选但强烈建议）**

生产环境中，不要让 Agent 自动变更身份而不经过确认。可以设置 `require_approval: true`，更新内容会先保存到一个 `.pending_update` 文件，待人工或审核脚本签入后才真正生效。这样可以避免错误记忆导致角色漂移。

## 四、踩坑与排雷

实际跑了一段时间，有几个点很容易出问题：

**角色漂移**  
Agent 积累了大量“学到的规则”后，容易偏离核心角色。比如技术助手开始记录用户闲聊偏好，导致在解决技术问题时语气过于随意。**解法**：把记忆区继续细分，如 `## Memory / Technical` 和 `## Memory / Style`，并给不同区域设权重，系统消息中可控制注入记忆的字数和优先级。

**Token 爆炸**  
IDENTITY.md 不断膨胀，每次系统消息中都塞入全部记忆，成本扛不住。**解法**：只注入上一次对话中活跃的记忆，或通过 RAG 方式检索相关记忆条目，IDENTITY.md 本身作为“记忆仓库”而非直接注入的全文。

**并发写入冲突**  
如果同一个 Agent 多个实例并行更新 IDENTITY.md（比如通过不同终端同时对话），会发生写入竞争。**现实做法**：在单用户场景下，使用文件锁；在多租户场景下，每个用户/会话维护自己的 `identity_<user>.md`，主身份文件由运维维护。

**Agent 倾向“过度记录”**  
有时 Agent 会把每次交互的细枝末节都写进去，产生大量噪声。可以在 tool prompt 中加入审查指令，例如“只有当信息对后续至少 3 次交互可能有价值时才记录”。

## 五、可复用的工程建议

1. **骨架与血肉分离**  
   身份定义（不可变部分）放在单独的 `identity_base.md`，记忆和进化部分放在 `identity_memory.md`，Agent 只能写入后者，前者只由人类修改并用 diff 工具比对。

2. **用 Git 管理身份历史**  
   打开 `.openclaw/identity_history/` 的 git 仓库，每次更新自动 commit，这样你能看到 Agent“成长”的全过程，也方便回退到某个健康版本。

3. **结合技能树（Skill Levels）**  
   如果你用 OpenClaw 的能力插件管理工具，可以在 IDENTITY.md 里维护 `## Skill Levels`，例如 `docker: intermediate`。Agent 根据技能水平选择合适的工具使用策略，并随着成功交互逐步提升等级（需人工 gate）。

4. **周期性的记忆蒸馏**  
   设定一个 cron 任务，每周对记忆区进行总结，将冗长的条目压缩成高密度摘要，删除过期信息（如临时的接口异常处理），这能有效防止文件膨胀。

## 六、总结

IDENTITY.md 看起来只是一种文件约定，但它把 Agent 的身份从一次性的 prompt 工程升级为了**长生命周期的资产管理**。对于需要持续运行的自动化 Agent、MCP 助手、运维 Copilot，可进化的身份意味着：

- 跨会话行为一致性
- 学习到的经验不会丢失
- 身份变更可审计、可回滚
- 多人协作时能基于同一个身份基线工作

它不是银弹，引入的成本主要是更新策略的设计和安全的制约。如果你已经厌倦了每次重启都教 Agent 同一件事，不妨从骨架固定、记忆进化的 IDENTITY.md 开始，让 Agent 慢慢长出自己的“肌肉记忆”。
