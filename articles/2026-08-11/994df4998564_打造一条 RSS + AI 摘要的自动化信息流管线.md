## 背景：当 Feedly 用不过来时

我订阅了大约 80 个 RSS 源，涵盖技术博客、漏洞预警、学术论文和几个行业公众号的净化版。每天新增条目 200+，如果全部点开扫一遍，至少占用 40 分钟。现实是：只有约 15% 的文章值得精读，其余只需知道“讲了什么”。

过去试过关键词过滤、按来源优先级排序，效果有限。直到把 LLM 接入管线做自动摘要，才真正把信息筛选从“人工扫标题”推进到“机器预读 + 人工决策”。

这篇文章记录在 OpenClaw 生态下搭建这条管线的过程——面向已经熟悉 Agent/MCP/插件机制、想要把自动化能力应用到信息消费侧的同学。

## 问题拆解

需要解决的核心链路只有四步：

1. **定期拉取**：从多源 RSS 获取最新条目，去重。
2. **内容萃取**：把 HTML 正文转为适合 LLM 处理的纯文本。
3. **AI 摘要**：调用 LLM 生成中文摘要（50–80 字），并打上可配置的标签。
4. **投递**：结果推送到通知渠道（邮件、Webhook、飞书/Lark），或写回本地笔记库。

可选增强：只对未读或未处理过的条目执行摘要，避免重复消耗 token。

## 选型与架构

我用了一套非常薄的组合，尽量复用 OpenClaw 已有的基础设施：

- **RSS Backend**：Miniflux（Go 编写、自带 API、支持抓取全文），跑在 NAS 上的 Docker 里。
- **编排**：OpenClaw 的 `scheduler` + `task` 机制，每 30 分钟触发一次管线。
- **MCP 服务**：通过 `rss-reader` MCP server 查询 Miniflux API，拿到最近 1 小时内新增的条目。
- **内容清洗**：`trafilatura` 封装成一个本地 function tool，由 Agent 调用。
- **摘要与标签**：OpenClaw 的 LLM 调用链，prompt 统一管理在 `prompts/summarizer.md`，标签集来自 `config/tags.yaml`。
- **投递**：摘要结果通过 `notify` 插件发送到飞书群机器人，同时写入本地 Markdown 文件（备查）。

整体架构示意：

```
Miniflux ← rss-reader MCP
         ↓
    OpenClaw Scheduler
         ↓
Agent 决策: 选取未处理条目 → 调用 trafilatura tool 清洗
         ↓
    LLM 摘要 (prompt 模板)
         ↓
notify 插件 → 飞书 / Markdown
```

没有引入队列、数据库或额外前端，状态全靠 Miniflux 的“已读/星标”和本地 `processed_ids.json` 维护。

## 实践步骤

### 1. 准备 RSS 源与 Miniflux

在 Miniflux 中导入全部 OPML，开启“抓取原文”选项。新建一个 Category 叫“待摘要”，将所有需 AI 处理的源归入其中。这样 MCP 查询时可以按 category 过滤，减少无关条目干扰。

### 2. 配置 rss-reader MCP

`rss-reader` community MCP server 支持列出未读条目并按时间、分类过滤。关键配置片段：

```yaml
mcp_servers:
  - name: rss
    command: npx
    args: ["-y", "@anthropic/mcp-server-rss-reader"]
    env:
      MINIFLUX_URL: "http://192.168.1.x:8080"
      MINIFLUX_TOKEN: "${MINIFLUX_API_KEY}"
```

### 3. 创建摘要 task

在 OpenClaw 中定义 task，核心是给 Agent 一个明确的决策流程：

```yaml
tasks:
  summarize_rss:
    schedule: "*/30 * * * *"
    agent_prompt: |
      1. 调用 rss-reader 获取过去 1 小时内“待摘要”分类下未读条目。
      2. 过滤掉已处理 ID（从 processed_ids.json 读取）。
      3. 对每个条目：
         a. 调用 trafilatura 提取正文纯文本；
         b. 若正文超过 3000 字符，取前 2000 + 后 500；
         c. 使用 summarizer 模板生成中文摘要和标签；
         d. 调用 notify 发送格式化消息；
         e. 将 ID 写入 processed_ids.json。
```

### 4. 编写摘要提示词

要点是限制长度、强调提取事实而非评价，并要求结构化输出。模板 `summarizer.md` 示例：

```
你是一个信息筛选助手。请根据以下文章内容生成：

- 一句话摘要（中文，不超过 80 字）
- 3 个关键词标签（从 {{tags}} 中选择，若无匹配则用“其他”）

仅输出 JSON：
{"summary": "...", "tags": ["..."]}

文章内容：
{{content}}
```

标签集 `tags.yaml` 包含诸如“LLM”、“安全漏洞”、“工具链”、“开源”、“基础设施”等，方便后续分类阅读。

### 5. 投递与归档

飞书机器人消息采用绿色标记摘要，附带原文链接和标签；同时在同目录下生成 `yyyy-mm-dd-summaries.md`，按时间倒序追加，便于 Obsidian 检索。

## 踩坑与优化

**字幕幻觉**  
初期对英文技术文章生成中文摘要时，偶现捏造人名、版本号。解决办法是在 prompt 中明确“只使用文中出现的信息，不要推断”，并将温度调至 0.1。

**大内容截断**  
trafilatura 提取的正文偶尔超过 10k token（如长文教程），直接送入 LLM 会超出上下文窗口。我们采用的策略是：按段落切分，保留开头 2000 字符、结尾 500 字符，并在中间加一句 `[中段已省略]`。对摘要质量影响不大，但一定能塞进 4k 上下文。

**API 速率限制**  
30 分钟内可能新增 20–30 条条目，逐个调用 trafilatura 和 LLM 会触发速率限制。因此在 task 中加入了 2 秒间隔和最大处理数限制（每次最多 10 条），未处理的留到下一轮。

**重复处理**  
仅靠 `processed_ids.json` 不可靠，Miniflux 条目标记“已读”作为辅助状态。一旦摘要完成，通过 API 将条目标记为已读，并从“待摘要”分类移除，双重保险。

## 可复用建议

- **从少到多**：先选 5 个高质量高频源跑通管线，稳定后再批量导入。
- **监控 token 消耗**：摘要任务看似轻量，但一个月处理 3000 篇文章的消耗可达数百万 token。定期查看用量，必要时过滤掉垃圾源。
- **考虑本地模型**：如果网络条件允许，可换成 Ollama 部署的 7B 模型做摘要，成本几乎为零，但需要接受质量略降。
- **与笔记系统打通**：摘要写成 Markdown 并引入双向链接，能让阅读从被动推送变为可检索的知识积累。
- **避免过度自动化**：摘要管线很容易变成另一个信息焦虑源。设置“仅在工作时间推送”和“每日摘要上限”，让它服务人，而非奴役人。

## 总结

这条管线并未引入复杂架构，只是把 RSS 阅读、内容清洗和 LLM 摘要通过 OpenClaw 的任务调度与 MCP 服务串了起来。核心收益很直接：每天能少看 200 个标题，却不错过真正重要的文章。对于已经在使用 Agent 和插件体系的团队，复制成本大约半天到一天。

如果你手中也有一套 OpenClaw 环境，不妨试试把信息流入也纳入自动化范畴——可能比想象中更安静，也更有效。
