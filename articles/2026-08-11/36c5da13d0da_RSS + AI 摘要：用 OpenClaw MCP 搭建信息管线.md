## 背景

信息源越来越多，RSS 订阅动辄上百条未读。每天手动过滤、提炼核心观点，很快会耗尽注意力。单纯用 AI 对文章做摘要并不新鲜，难点在于把它做成一条**无人值守、稳定运行的管线**——从抓取、去重、摘要生成，到最终推送到笔记系统或通知，每一步都需要可观测、可恢复、成本可控。

这次我用 OpenClaw 的 MCP 工具链，搭了一条端到端的信息摘要管线。整体方案偏工程化，没有魔法，重点在踩坑和复用。

## 目标与约束

- 输入：RSS 源（博客、技术周刊、公告页面）
- 输出：每篇文章生成 ≤150 字的中文摘要，推送到 Logseq 日 journal 或飞书通知
- 运行环境：本地 Python 脚本 + OpenClaw MCP 插件，定时触发
- 硬约束：不重复处理同一条目，非关键错误不阻断管线，成本单次低于 $0.002

## 管线架构

```
[Cron / Agent Timer]
       │
       ▼
[Python 抓取 & 去重模块]
       │
       ▼
[截断 + Prompt 封装]
       │
       ▼
[OpenAI 兼容 API 摘要]
       │
       ▼
[MCP 工具调用：存储 / 通知]
```

每一步都抽象成函数，方便单独测试和替换组件。抓取和摘要部分完全脱离 OpenClaw，只把最终输出通过 MCP 工具交给 Agent 分发，这样即使未来换调度框架，核心逻辑也不用改。

## 关键步骤

### 1. 抓取与去重

使用 `feedparser` 解析 RSS 源，主要处理 Atom 和 RSS 2.0。解析后提取 `title`、`link`、`published`、`summary` 或 `content` 全文。全文优先取 `content:encoded`，再降级到 `summary`。

去重用 SQLite 维护一个简单的 `processed_items` 表，联合唯一键 `(feed_url, item_link)`。每次抓取前先查询该条目是否已处理。注意：有些 RSS 源的 `link` 可能带有 tracking 参数，需要先做 normalize（strip UTM、hash 前固定长度）。如果遇到同一篇文章返回不同 GUID，改用 `(feed_url, normalized_title)` 作为备用唯一键，避免遗漏。

踩坑：部分 WordPress 站点的 RSS 会把“阅读全文”按钮当成文章正文，导致全文变成“阅读全文...”。处理办法：检测到原文长度 ≤ 200 字符且包含“阅读全文”字样时，自动 fetch 文章原始 URL，用 `trafilatura` 抽提正文。

### 2. 摘要生成

摘要模型用 `gpt-3.5-turbo`，成本低、延迟可接受。Prompt 经过反复调整，最终成了一套模板：

```
你是一名技术摘要助手。请将以下文章的主要观点提炼为一段不超过150个汉字的中文摘要。
要求：
- 保留关键技术名词、产品名称、版本号
- 不使用"本文""作者"等主观表述
- 如果原文是英文，中文回复
- 只输出摘要，不要前言后语

文章内容：
{text}
```

模型温度设为 0.2，减少幻觉。长文处理：如果截断到前 4000 个 token 仍不完整，改用分块摘要策略——将文章切成 3000 token 的块（重叠 200 token），先对每一块生成要点，再对要点做总摘要。这种方法成本大约翻倍，但保证关键信息不丢失。

需要留意 OpenAI API 的 rate limit。设置重试策略：指数退避，最大重试 3 次，且添加 jitter，避免定时任务在整点同时触发造成拥塞。

### 3. MCP 分发

OpenClaw 的 MCP 生态允许自定义 MCP 服务器暴露工具。我写了一个极简的 Python MCP 服务，用 `mcp` 库暴露两个工具：

- `log_daily_summary`: 接收标题、摘要、来源链接、日期，写入 Logseq 的 pages/journal 对应日期的 Markdown 文件中。
- `send_feishu_notification`: 按指定 webhook 发送飞书富文本消息。

管线脚本在生完摘要后，通过 `openclaw run` 调用对应的 MCP 工具。比如：

```bash
openclaw run "使用 log_daily_summary 记录以下摘要：标题 'xxx'，摘要 'xxx'，链接 'xxx'，日期 2025-03-29"
```

Agent 自动解析并执行。这样做的好处是：存储和通知逻辑完全交给 MCP 工具，管线本身不触碰任何特定应用的 API，未来替换输出端只需要换一个工具实现。

### 4. 定时调度

在 OpenClaw 中配置了一个 Recurring Task，每天早上 8 点和下午 6 点各运行一次。用 Agent 的 skill 能力调用一个简短的 prompt，让 Agent 运行上述 Python 脚本。脚本执行完成后，Agent 再向 MCP 工具写入结果。如果某次运行失败，Agent 会记录错误日志到本地文件，下一次运行时可以先检查并重试失败的条目。

## 踩坑记录

- **RSS 源不稳定**：部分云厂商技术博客的 RSS 偶尔返回 502。抓取模块必须设置超时 (10s) 和重试，同时捕获 `ETIMEDOUT` 和 SSL 错误，记录失败但不阻断整个管线。
- **token 计数不准**：用 `tiktoken` 精确计数，不要依赖字符数估算。中文文章截断时按 token 数切，否则可能浪费大量额度。
- **摘要内容漂移**：早期 prompt 未要求保留技术名词，导致“Kubernetes 1.29”被简化成“容器管理工具”。必须在 prompt 中明确约束。
- **Logseq 写入冲突**：MCP 工具写 journal 时，如果用户在另一处编辑同一天的文件，可能造成文件冲突。解决办法是写入前检查文件锁或直接使用追加模式，不覆盖整个文件。
- **重复条目漏网**：有些站点的文章标题会悄悄更新（补错字），导致 normalized_title 变化。因此增加了基于 link 的唯一保证，title 只做辅助。

## 可复用建议

1. **把摘要管线做成无状态的纯函数**：输入文章文本，输出摘要。所有副作用（网络请求、文件写入）都放在外围的 orchestration 层，方便单元测试。
2. **统一去重存储**：用 SQLite，简单可靠。表结构包含 `feed_url`、`item_unique_key`、`processed_at`、`status`。方便后续统计分析哪些源质量高。
3. **成本监控**：每次摘要请求后记录 `usage.total_tokens`，按 $0.002/1K token 估算成本，汇总到每周的 MCP 通知里。成本透明才能放心扩展源。
4. **灰度发布**：新增 RSS 源先跑 3 天静默模式（只抓取不去重，生成摘要但不分发），人工抽检摘要质量后再接入正式管线。
5. **可插拔的 AI 后端**：通过环境变量切换 `OPENAI_API_BASE`，轻松切到 localai、vLLM 或任何兼容接口，避免被单一供应商锁定。

## 总结

这条管线运行两周，处理了 14 个 RSS 源的 320 篇文章，有效摘要 308 条，错误率约 3.7%（主要来自源不可达），单次成本稳定在 $0.0015。每天早上的通知能让我在 5 分钟内扫完前 24 小时的技术更新。

RSS + AI 摘要的自动化，本质上是用机器处理“信息过载”中那些高度重复、消耗认知的低价值工作。配合 OpenClaw 的 MCP 执行动作，整个流程不需要打开任何前端，信息自动流入知识库，这比任何炫酷的 AI 应用都更实在。
