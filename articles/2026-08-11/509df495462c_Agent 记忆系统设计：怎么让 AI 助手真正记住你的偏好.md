## 背景：除了“一次性对话”，Agent 还缺什么

在 OpenClaw 这类可挂载 MCP 工具、可编程、可长期运行的 Agent 环境里，“记忆”是一个被反复提起、却很少系统化解决的工程问题。

典型场景：

- 你告诉 Agent 你喜欢 TypeScript 的函数式写法、接口命名用 PascalCase、错误处理用 Result 模式，每次新对话它都像第一次听到。
- 你在 OpenClaw 里接了 GitHub MCP Server，处理了三次 issue，但它不会记得上次你选的是 `feat` 还是 `fix` 分支命名习惯。
- 你用一个自定义插件跑了半年的日报生成规则，某天换了个 agent 实例，所有隐性约定全部丢失。

这些问题的本质不是模型能力不足，而是**记忆没有独立于对话存在**。  
一个真正有用的 Agent 记忆系统，至少要做到三件事：

- 跨会话的偏好持续性
- 可演化的用户画像（偏好会变）
- 低侵入性的记忆提取与检索

## 问题拆解：记忆系统的四个核心矛盾

在实际设计里，你会在下面四个地方反复翻车：

1. **抽取 vs 噪音**  
   从对话里自动抽取记忆，很容易把单次情绪表达（“这把用 any 只是临时一下”）当成长期偏好固化下来。

2. **检索 vs 上下文窗口**  
   把所有记忆一股脑塞进 system prompt，很快会撑爆 token 上限，且与当前任务无关的偏好会干扰推理。

3. **写入 vs 冲突**  
   同一条偏好可能被多次写入，比如你开始说“用 Zod”，后来改说“直接用 TypeScript 类型推断好了”，简单追加会导致两条矛盾信息共存。

4. **长期维护成本**  
   每次对话都触发全量记忆更新，API 调用量会失控；但更新不及时又会劣化体验。

## 工程化做法：一个能落地的记忆架构

我以 **OpenClaw + MCP Memory Server** 的组合为例，给出一个可以直接复用的设计。

### 1. 记忆分层：短期 / 长期

| 层级 | 作用 | 存储方式 | 生命周期 |
|------|------|---------|---------|
| 短期记忆 | 当前对话的上下文 | 滑动窗口（最近 N 轮消息） | 单次会话 |
| 长期记忆 | 用户偏好、事实、工具使用习惯 | 向量库 + 元数据存储 | 跨会话持久化 |

长期记忆是重点。我把长期记忆再拆成三类：

- **偏好类**：代码风格、语言、回复详细程度、工具选择偏好等。
- **事实类**：你常用的仓库、项目路径、工具配置等事实信息。
- **模板类**：你重复执行的任务模式，如“创建新 feat 分支 → 写代码 → 跑 lint → 创建 PR 草稿”，这些可以固化为可调用的模板。

### 2. 存储：向量 + 结构化过滤

单纯用向量检索会遇到一个问题：偏好是有作用域的。比如“用中文回复”是一条全局偏好，“Zod 做入参校验”是仅针对 TypeScript 项目的。这时候就需要元数据过滤。

推荐方案：

- 向量库：Chroma / Qdrant / 简单场景直接 pgvector
- 元数据字段：`type`（preference / fact / template）、`scope`（global / project / tool）、`updated_at`、`importance`
- 每条记忆文本做 embedding 存向量，同时存一份结构化元数据

检索时做两步过滤：

1. 先按 scope 缩小候选集（比如当前在 Node.js 项目里，就不召回 Python 相关偏好）
2. 再在候选集里做向量相似召回，时间衰减加权

### 3. 抽取：用“确认”换取准确性

最常踩的坑是自动抽取跑得太激进。我会加一个轻量确认机制：

- 每次对话结束后，由记忆管理器（一个 LLM 调用）分析差异，生成 `memory_diff`，例如：
  ```json
  {
    "add": [
      { "type": "preference", "scope": "project:/xxx", "content": "使用 pnpm > npm", "importance": 0.8 }
    ]
  }
  ```
- 对于 `importance > 0.7` 的新增或冲突记忆，在下一次对话开始前，以一条系统消息的形式让 Agent 做一次低成本的用户确认，比如：“我注意到你在这个项目里开始用 pnpm 了，以后都默认用 pnpm 吗？”
- 冲突解决：一旦新的偏好被确认，旧的那条做软删除或标记 `deprecated`。

这种做法既避免了频繁打扰，又不让噪音固化。

### 4. 检索注入：按需拼合上下文

不把所有记忆放进 prompt，而是根据当前意图动态注入：

- 从用户消息和最近几轮对话中提取“当前意图”（用一个小 LLM 调用或关键词提取）
- 用意图检索相关长期记忆，只取 top-3 且 relevance > 阈值的结果
- 拼接到 system prompt 的特殊区段，如：

```
[User Preferences - Injected]
- 项目 /xxx: 用 pnpm 管理依赖，禁止使用 npm
- 全局: 回复语言为中文，代码注释用中文
```

这样 token 用量可控，且不会干扰当前推理。

### 5. 结合 OpenClaw / MCP 的落地方式

最简单的方式是把记忆系统打包成一个 MCP Server：

- 提供 `memory.retrieve(context)` 和 `memory.update(diff)` 两个工具
- 在 OpenClaw 的 agent 配置里，把这个 MCP Server 加入 tool 列表
- Agent 在处理用户请求前主动调用 `memory.retrieve`，并在结束对话后调用 `memory.update`

也可以用 OpenClaw 的插件机制，把记忆更新挂在会话生命周期钩子上，这样对现有工作流侵入更小。

## 踩坑记录：这些坑你大概率会碰到

1. **记忆爆炸**  
   不及时清理过时记忆，向量库会越来越脏。建议定期（按周）运行一次记忆清洗，把超过 30 天未确认且 importance 低于阈值的条目归档。

2. **确认机制失效**  
   用户连续跳过确认，会导致新偏好一直处于“待确认”状态，记忆停滞。可以设一个上限：同一条偏好连续 3 次未被确认，自动采用但标记低置信度。

3. **检索不准**  
   靠单一 embedding 模型召回效果可能很差，特别是中英混合场景。建议用一个通用性好的多语言模型（如 bge-m3），并在检索时同时做关键词匹配和向量召回，取并集。

4. **成本控制**  
   不要每次对话都触发全量更新。可以设一个最小间隔（如 5 轮一次），并只在 conversation turn > 3 时才运行抽取逻辑。

## 可复用建议

- **先从显式记忆开始**：提供 `/remember` 或对话中明确说“记住我习惯用 bun”的方式，让用户主动写入。自动抽取作为补充，降低初期噪音。
- **定义清晰的记忆 schema**：`type + scope + content + importance + timestamp` 五字段足够覆盖绝大多数场景。
- **用 MCP 做接口边界**：一旦把记忆做成 MCP Server，你的 OpenClaw Agent、ChatGPT 插件、甚至未来换到其他框架都能复用同一套记忆后端。
- **写一个简单的管理面板**：能够手动查看、编辑、删除记忆，用户信任感会极大提升，同时也是一个调试入口。

## 总结

Agent 记忆不是“让模型更智能”的魔法，而是一套信息管理系统。  
真正好用的记忆系统，应当做到：用户感知不到它的存在，但 Agent 的行为却越来越“懂你”。  
从分层存储、可控抽取、按需注入这三个工程点入手，你完全可以用 MCP + 轻量向量库，在 OpenClaw 上搭出一个可长期维护的记忆层，而不是每次新对话都从零开始教 AI 你喜欢什么。
