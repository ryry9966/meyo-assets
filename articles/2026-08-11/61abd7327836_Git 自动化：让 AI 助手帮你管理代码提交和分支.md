# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

在日常开发中，大多数人都有过这样的经历：写完代码、`git add .`，然后面对一个空白的提交信息输入框发呆。匆忙间敲下 “update”、“fix bug” 或更糟糕的 “WIP”，等几个月回看项目历史时，这些无效提交信息几乎只能靠 `git blame` 来猜当时的意图。同样，多人协作时分支命名随意（`dev2`, `test-branch`, `feature/xxx-final-v2`），让仓库逐渐失去可维护性。

单靠规范文档和 CR 约束往往收效甚微，属于典型的 “重复且容易出错的低价值劳动”。如果有一个 AI 助手能在提交前替你生成符合规范的消息、在创建分支时根据 Issue 内容给出建议名，同时仍然保留你的最终审批权，这样的自动化才有工程落地的价值。

这并不是要交给 AI 去“写代码”，而是让它分担事务性操作，降低团队走向规范化的摩擦成本。

## 问题定义

我们需要解决两个具体问题：

1. **自动生成 Conventional Commits 风格提交信息**：根据 `git diff --staged` 的内容，产出类似 `feat(parser): add support for YAML front matter` 的结构化消息。
2. **基于任务编号自动创建规范分支**：当一个新 Issue 开启（或手动触发），AI 提取标题和类型，生成形如 `feat/OPEN-123-add-yaml-parser` 的分支名。

两个功能都要 **非侵入**，不改变现有 Git 工作流核心，只辅助，不强制。AI 输出仅作为建议，提供接受/编辑/拒绝的交互。安全方面，只处理开发者主动暂存的变更，不会自动提交、推送或破坏仓库历史。

## 实现方案

这里以 OpenClaw 生态的 Agent 能力为执行基础。思路是：**把 Git 事件转换成 Agent 的输入，让 Agent 根据定义好的 Skill 调 LLM，再将结果写回 Git 流程**。

### 1. 自动生成提交信息（prepare-commit-msg hook）

Git 提供了 `prepare-commit-msg` 钩子，在打开提交信息编辑器前运行。钩子会收到提交信息文件的路径及来源（message、merge、commit 等）。我们可以在这里插入 AI 调用：

- **脚本**（`prepare-commit-msg`，放在仓库的 `.git/hooks/` 中或通过 `core.hooksPath` 管理）：

```bash
#!/bin/bash
COMMIT_MSG_FILE="$1"
COMMIT_SOURCE="$2"

# 仅在常规提交且用户未通过 -m 指定信息时介入
if [ "$COMMIT_SOURCE" = "message" ]; then exit 0; fi

DIFF=$(git diff --staged -- . ':(exclude)package-lock.json' ':(exclude)*.lock')
if [ -z "$DIFF" ]; then exit 0; fi

# 调用 OpenClaw Agent 的本地 HTTP API（示例端口 3711）
RESPONSE=$(curl -s -X POST http://localhost:3711/agent/run-skill \
  -H "Content-Type: application/json" \
  -d '{
    "skill": "git-commit-msg",
    "input": { "diff": '"$(echo "$DIFF" | jq -Rs .)"' }
  }')

SUGGESTION=$(echo "$RESPONSE" | jq -r '.output.commit_message // empty')
if [ -n "$SUGGESTION" ]; then
  echo "$SUGGESTION" > "$COMMIT_MSG_FILE"
  # 保留原模板并添加建议注释
  echo "" >> "$COMMIT_MSG_FILE"
  echo "# AI suggested commit message above." >> "$COMMIT_MSG_FILE"
fi
```

- **OpenClaw Skill 定义**（YAML 片段）：

```yaml
skills:
  git-commit-msg:
    description: Generate conventional commit message from staged diff
    model: gpt-4.1-mini
    prompt: |
      You are a commit message generator. Given a `git diff --staged` output,
      generate a single commit message in Conventional Commits format.
      Focus on WHAT and WHY, not HOW. Limit to 72 chars subject, wrap body at 72.
      Do NOT include any markdown, backticks, or meta-commentary.

      Examples:
      <input diff example> → "fix(auth): handle expired JWT gracefully"
      <input diff example> → "feat(api): add pagination to list endpoints"

      Now given this diff:
      {{ .input.diff }}
    output_format: json
    output_schema:
      commit_message: string
```

钩子脚本中做了几项工程化权衡：

- 排除 lock 文件，避免无意义的 diff 噪声进入 prompt。
- diff 内容过 JSON 转发前用 `jq -Rs` 正确转义，防止注入破坏。
- Skill 输出仅一个字段 `commit_message`，脚本将它写入消息文件，并在下方追加一条提示注释，开发者在编辑器中仍可修改或舍弃。

### 2. 智能分支命名（post-checkout 或自定义 CLI）

更安全的做法不是 hook `post-checkout`，而是提供一个小型 CLI 工具（或 OpenClaw 工作流），在开发者打算创建分支时主动调用。流程：

1. 用户输入 `git-ai-branch <issue-id>` 或从当前 Issue 管理工具同步标题。
2. Agent 提取类型（feat/fix/docs 等）和核心描述，去除特殊字符，截断长度，生成符合 Git 标准的分支名。
3. 用户确认后执行 `git checkout -b <name>`。

核心 Skill 类似， `input` 变为 Issue 标题与 ID。推荐在团队中包装成一个简单的 `git alias`，例如：

```
git config --global alias.ab '!f() { git checkout -b $(ai-branch "$1"); }; f'
```

使用时 `git ab OPEN-456`，便自动拉取或构造分支名并切换。

## 踩坑记录

在多个项目落地这套辅助流程时，有几个实际痛点：

1. **diff 过大导致 token 超限**  
   大型 PR 暂存数百个文件时，原样发送 diff 会超出模型上下文。解决方式：在 Skill 中或钩子脚本里对 diff 做截断，比如只保留前 200 行和非空行，并附上 “[truncated]” 标记。同时 Skill 的 system prompt 要明确告知上下文有截断。

2. **生成信息包含敏感路径或误读业务逻辑**  
   AI 有时会将文件路径或包名误当作功能描述，产出怪异的消息（如 `feat(index.tsx): index.tsx`）。需要通过 few-shot 示例强化 “禁止直接复制文件名作为 subject” 的规则，并在 Skill 的 prompt 中明确强调：**描述功能影响，而非改了什么文件**。

3. **本地 Agent 服务不可用时卡住提交**  
   钩子中 CURL 调用必须设置超时（例如 `--max-time 5`），并在失败时静默退出，不能阻塞 `git commit`。此时应当 fallback 到空白信息或传统模板，而非报错中止。

4. **编码与转义问题**  
   中文文件路径、emoji 在 JSON 传输中可能被错误转义，导致 Skill 收到乱码。使用 `jq -Rs` 或将 diff 文件 base64 编码传输更可靠。在我们的场景里，统一约定提交信息使用英文，避开了多语言陷阱。

5. **分支名长度和特殊字符**  
   AI 可能生成过长的分支名或包含空格、标点。需要后处理：用 `tr` 将空格替换为 `-`，删除 `[^a-zA-Z0-9/-]` 之外的字符，截断到 50 个字符。

## 可复用建议

- **从最小可用开始**：先只在本地启用 `prepare-commit-msg`，团队试用两周，收集反馈再推广。不可直接引入共享钩子强制所有人使用，避免抵触。
- **模板化 Skill**：将要遵循的提交规范（类型列表、scope 约定）写到 Skill 的 system prompt 中，而不是依赖大模型 “记住” 公司规范。
- **提供显式编辑机会**：建议的提交信息写入文件后，一定要保留开发者编辑和取消的可能。我们的脚本通过注释提示，用户仍可以 `git commit -e` 完全重写。
- **监控调用成本**：在 Agent 侧记录每次生成消耗的 token 和时间，当项目 diff 类型单一（小修小补）时，可考虑用缓存或更小模型降低成本。
- **结合 git template 使用**：可以让 AI 生成的内容作为 `COMMIT_EDITMSG` 的模板一部分，顶部是建议，下方保留标准注释区（分支名、关联 Issue 等）。

## 总结

将 AI 集成到 Git 流程中对团队最大的收益不是 “提交信息有多漂亮”，而是**降低规范执行的认知负荷**。当开发者知道有一个可靠的工具能随手生成合理消息时，无形中提高了大家遵守规范的意愿。这项自动化并不神秘，本质是利用 Git 原生的钩子机制和 Agent 的任务编排能力，将琐事转化为一条可复用的 Skill。

上述方案已经在多个内部仓库中运行数千次提交，人工修正率不到 15%，且明显减少了 “fix”、“update” 这类退化提交。对于已经使用 OpenClaw 进行日常编码与文档辅助的团队，把这套能力下沉到版本控制层，是自动化实践的合理延伸。
