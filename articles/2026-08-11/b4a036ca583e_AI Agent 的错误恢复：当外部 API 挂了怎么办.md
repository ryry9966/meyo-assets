# AI Agent 的错误恢复：当外部 API 挂了怎么办

## 背景：Agent 也是“外部依赖”的集合体

我们把 Agent 做得越来越自主：调用搜索 API、查数据库、发邮件、操作内部系统。但这些能力的底座，是一堆随时可能“罢工”的外部服务。超时、5xx、限流、返回格式突变——每个开发者都不陌生。差别在于，当一个普通应用遇到 API 故障，用户能看到错误页面并手动重试；而对于一条正在执行长任务的 Agent，一个未处理的异常可能直接让上下文全部丢失，导致整条链功亏一篑。

在基于 OpenClaw 或 MCP 工具调用构建的 Agent 里，这种脆弱性尤其突出：Agent 不只是单次调用，而是多步推理→动作→观察的循环。中间任何一步的外部依赖异常，如果不能妥善恢复，就会产生“半成品”状态，甚至让 Agent 陷入错误重试的循环，白白浪费 token 和时间。

## 核心问题：不是“会不会挂”，而是“挂了之后怎么办”

从工程实践来看，外部 API 的异常可以归纳为三类：

1. **瞬时性错误**：网络抖动、临时超时、偶发 503。通常重试可解决。
2. **持续性不可用**：服务宕机、配置错误、认证过期。重试无效，反而加剧拥塞。
3. **逻辑性错误**：返回数据格式变更、空结果但并非真正的失败。需要 Agent 自行判断上下文。

如果只是简单 `try-except` 然后抛出，等于把难题丢给了最外层的调用方，Agent 会在无任何补偿信息的情况下中断。好的错误恢复应该做到：**让 Agent 感知到“发生了什么”，并赋予它有限的决策权**，同时保护系统不因重试风暴而雪崩。

## 做法：构建一套可组合的容错层

以下步骤不依赖特定框架，可以用在 OpenClaw 的 tool wrapper 或 MCP server 的工具实现里。

### 1. 错误分类与结构化上下文

不要在工具函数里直接返回 `"Error: timeout"` 这种字符串。Agent（背后的 LLM）需要结构化的故障信息来决定下一步。建议工具返回一个统一结构：

```json
{
  "success": false,
  "error_type": "TEMPORARY_SERVER_ERROR",
  "message": "Upstream search API returned 503 after 3 retries",
  "retryable": true,
  "fallback_available": true,
  "fallback_hint": "Use cached results from 10 minutes ago"
}
```

`error_type` 可设计为枚举：`TIMEOUT`, `RATE_LIMITED`, `UPSTREAM_5XX`, `INVALID_RESPONSE`, `NOT_FOUND` 等。Agent 后续可根据这些类型做不同处理，而不是盲目重试或直接报错。

### 2. 指数退避 + 有限重试 + jitter

在工具包装层实现重试逻辑，而非让 Agent 自己重复调用。参数建议：

- 最大重试次数：3（不可重试错误直接为 0）
- 基本延迟：1 秒，指数增长，上限 30 秒
- 加入随机抖动（±25%）避免惊群效应
- 对 429 限流错误，使用 `Retry-After` 头部的建议等待时间

谨记：重试必须无副作用，或工具本身幂等。例如，发邮件工具千万不能无脑重试。

### 3. 断路器：让快速失败成为一种保护

当同一工具在短时间内连续失败（比如 5 次中有 4 次失败），直接打开断路器，后续调用立即返回降级结果，不再实际访问外部服务。间隔一段时间（如 30 秒）后进入半开状态，允许一次探测请求，成功则关闭，失败则继续保持开路。

开源库如 `pybreaker` 或自己用 Redis 计数器实现都可以。对于 OpenClaw 插件，可以把断路器状态放在进程内存或共享存储中，保证多 Agent 实例间一致。

### 4. 降级策略：不是所有任务都等得起

为关键工具准备降级方案：

- **搜索结果降级**：返回前一次成功的缓存数据，并标记 `stale: true`
- **数据查询降级**：返回空列表并说明“当前无法获取实时数据，请基于已有信息继续”
- **非必需工具**：直接跳过，让 Agent 在推理中注明“跳过了某步骤”

例如，一个研究 Agent 需要搜索最新论文，当 API 不可用时，可以降级为告诉 Agent：“无法访问 Arxiv，建议基于你记忆中的知识回答，或稍后手动补充”。LLM 可以据此生成一个不完整的报告并提醒用户。

### 5. 让 Agent 看到错误并参与决策

这是最关键的一步。在工具返回错误信息后，Agent 的下一轮推理循环中会包含该结构化错误。你可以这样设计提示词：

> 如果工具调用失败，你会收到一个包含 error_type 和 suggestions 的结构化对象。请根据错误类型决定：重试（须说明理由并最多重试 2 次）、使用降级结果、询问用户、或跳过该步骤继续执行。

这样就把错误恢复的内聚性保持在了 Agent 内部，而不是把它当成一个无法恢复的终点。

## 踩坑点

1. **无限重试却不改变参数**：尤其是遇到 400 类错误（请求格式有误），重试 100 次也没用。必须在第一次失败后判断不可重试。
2. **无超时控制**：外部调用不加超时，Agent 会永远挂起。为每个工具调用设置绝对超时（如 15 秒），并在 Agent 总任务上设置整体超时（如 5 分钟）。
3. **降级太过安静**：缓存数据陈旧可能导致 Agent 给出错误结论。务必在降级时向 Agent 透传“这是陈旧数据”，并在最终输出中向用户透明。
4. **断路器恢复太快**：外部服务还在启动期间，大量半开探测请求把服务再次打挂。保持半开状态的探测频率要低。
5. **把 LLM 当成万能的错误处理机**：虽然有决策能力，但面对真正的系统性故障，LLM 也只会“反复尝试”。建议在 Agent 循环外层加一个最大步数限制，异常退出时保留上下文以便人工介入。

## 可复用建议

- 将所有外部调用封装成统一的 **`ToolExecutor`**，内建重试、断路器、超时、降级逻辑。每个具体工具只需提供核心业务逻辑和降级实现。
- 为常见错误类型定义标准 `error_type` 枚举，并在内部文档中约定每种错误对应的 Agent 策略。
- 记录结构化错误日志，带上工具名、耗时、重试次数、最终结果，方便排障。
- 在 OpenClaw 的插件开发中，利用共享的 state 保存断路器状态和缓存，多个 tool 共享同一套容错机制。

## 总结

外部 API 挂掉不是异常，而是常态。让 Agent 能够“优雅地失败”和“在有限信息下继续前进”，是生产级 Agent 必须拥有的能力。在工程实现上，把重试、断路、降级这些成熟的稳定性模式搬到工具调用层，再用结构化的错误信息赋予 Agent 决策权，就能大幅降低故障时的上下文损失和糟糕的用户体验。

做 Agent 开发，不妨把这样一句话当成基本假设：“每一个工具随时都可能返回一个错误，而 Agent 必须知道该怎么办。”
