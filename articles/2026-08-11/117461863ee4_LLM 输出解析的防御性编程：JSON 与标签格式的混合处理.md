## 背景

在 OpenClaw 这类 Agent 框架或自动化流程中，我们经常要求 LLM 输出结构化数据，以便后续节点解析执行。纯 JSON 是最常见的选择，但实际运行时，模型输出很容易被“污染”：

- 开头多一句“好的，结果如下：”
- 结尾补充“希望对你有帮助”
- 使用 markdown 代码块包裹（```json ... ```）

直接 `json.loads()` 往往会崩掉整个链路。

为了更鲁棒地提取结构化信息，很多工程师改用**自定义标签**包裹 JSON，例如：

```
<action>
{
  "tool": "search",
  "query": "天气"
}
</action>
```

然而，标签格式同样会出现各种“不干净”的输出。本文记录在实际构造 Agent 的工具调用、多步推理时，对这类混合输出进行防御性解析的设计思路、完整处理步骤与踩坑点。

## 问题拆解

当我们约定 `<action>` 标签内为纯 JSON 时，实际收到的文本可能出现以下情况：

1. 标签外存在杂讯：“我选择执行以下操作：\n<action>{...}</action>”
2. 标签内不完全是 JSON：“<action>参数设置：{...}</action>”
3. JSON 自身格式瑕疵：尾随逗号、单引号、未转义换行符
4. 字符串内部意外包含 `</action>`，导致常规正则提前截断
5. 一次回复中出现多个 `<action>` 块，需要决定取第一个还是全部
6. 标签嵌套（极少出现，但如果 prompt 示例中有说明性文字可能被复述）

要稳定应对以上情况，单纯靠 prompt 约束不够，必须在解析侧建立多层防御。

## 做法与步骤

### 1. 规范输出格式

在 system prompt 或工具描述中明确要求：

- 使用 `<action>` 和 `</action>` 包裹 JSON，标签独占一行
- 标签内部只能是合法的 JSON 对象，不允许任何额外说明
- 若需要多个动作，则输出多个 `<action>...</action>` 块

同时提供符合要求的示例，这对小模型尤其重要。

### 2. 核心提取流程

实现一个 `parse_tagged_json(text, tag="action", first_only=True)` 函数，串联以下步骤：

#### 2.1 正则提取所有标签块

使用非贪婪正则，配合 `re.DOTALL` 处理换行：

```python
import re
pattern = rf"<{tag}>(.*?)</{tag}>"
matches = re.findall(pattern, text, re.DOTALL)
```

如果没有任何匹配，可以尝试退化为在全文中寻找第一个 `{` 和最后一个 `}` 截取（即假设用户可能忘记加标签）。但这种退化可能会引入更多噪声，根据业务接受度选择。

#### 2.2 裁剪 JSON 片段

对于每个 `match`，先 `.strip()`，然后定位第一个 `{` 和最后一个 `}`，截取中间部分：

```python
start = match.find('{')
end = match.rfind('}')
if start != -1 and end != -1:
    json_str = match[start:end+1]
else:
    continue  # 无法定位，尝试下一个
```

这样即使标签内出现了“参数设置：”等前缀，也能自动去除。

#### 2.3 JSON 修复

对截取的 `json_str` 依次尝试：

- 修复尾随逗号：在 `}` 或 `]` 前多余的逗号
    ```python
    import re
    fixed = re.sub(r',\s*([}\]])', r'\1', json_str)
    ```
- 单引号转双引号（简单安全版本：先假设所有单引号都是键值界定，但字符串内容中可能存在撇号，故只在键和值的明显位置替换；更稳健的方法是先 `json.loads` 失败后，用 `ast.literal_eval` 尝试解析 Python 字面量，注意安全性需限制输入）
- 有时 LLM 会输出 `True/False/None` 而非 JSON 的 `true/false/null`，执行字符串替换
- 对于极端情况，可以使用 `json5` 库进行宽松解析（需评估依赖引入成本）

```python
import json
try:
    obj = json.loads(fixed)
except json.JSONDecodeError:
    try:
        import json5
        obj = json5.loads(json_str)
    except:
        obj = None
```

如果仍然失败，可以保留原始 `json_str` 作为回退，记录日志并走异常处理分支（例如交给人工或者另一个 LLM 再次修正）。

#### 2.4 多块选择

根据业务需求，`first_only=True` 时只返回第一个成功解析的对象；否则返回列表。注意，多个 `<action>` 块之间可能存在重复或矛盾，应在调用侧增加过滤逻辑。

### 3. 处理字符串中的标签误闭合

如果 JSON 的字符串值内包含 `</action>`，非贪婪正则 `<action>(.*?)</action>` 会提前截断。这是此方案的一个硬伤。规避方式：

- 在 prompt 中明确禁止在 JSON 字符串中使用 `</action>` 子串
- 若无法避免，可将标签名称设计为更独特的 UUID 前缀，如 `<a7f3b2c></a7f3b2c>`，降低冲突概率
- 或者实现轻量状态机扫描：遇到 `<action>` 开始记录，逐字符扫描，跟踪是否在字符串内（通过 `"` 和转义判断），直到找到不在字符串内的 `</action>`。代码复杂度会上升，但鲁棒性更好。对于复杂场景，可以考虑引入部分 JSON 流式解析库。

## 踩坑点汇总

1. **`re.DOTALL` 使 `.` 匹配换行，但非贪婪仍然可能跨越多块边界**：如果文本中存在多个标签，`.*?` 会分别捕获，这是期望行为；但如果标签内容内包含 `</action>` 则会出错。务必测试真实模型的异常输出模式。
2. **尾部逗号修复可能误伤字符串内容**：正则 `,\s*([}\]])` 会删除 `"key": "value,}"` 中的逗号。这种情况少见，但出现过。可以加一步启发式检查：统计双引号个数，仅当当前上下文不在字符串内时才替换。实现难度略高，可以先用简单正则兜底，毕竟真正在字符串末尾出现 `,}` 的概率较低。
3. **单引号替换需谨慎**：比如 `"message": "It's ok"` 中的 `'` 不该被转成双引号。大部分宽松解析器（如 `json5`）已经支持单引号字符串，不必自行替换。
4. **性能与成本的平衡**：多层修复会增加解析时间，如果应用在高吞吐量场景，尽量在 prompt 工程上减少错误输出，减少修复链的触发频次。
5. **不要盲目信任“纯 JSON 模式”**：即便有些模型支持 JSON mode，偶尔仍会出现外层多余字符，因此保留最少一层标签提取仍然有价值。

## 可复用建议

将以上逻辑封装为独立函数，并配置化：

```python
extract_json(text, tag="action", fallback_to_raw_json=True, first_only=True)
```

放入团队内部工具库，并在所有需要解析 LLM 结构化输出的 Agent 节点中使用。可配合日志记录每次解析的原始片段和修复动作，便于监控模型退化或 prompt 漂移。

若要进一步提升可靠性，可对解析结果进行 schema 校验（例如使用 Pydantic），一旦校验失败即触发二次修正或人工审核，确保自动化链路不会因为畸形数据而中断。

## 总结

让 LLM 在自动化流程中稳定输出结构化数据，不能寄希望于“完美遵守指令”。JSON 标签混合格式是一种中间地带：既保持了对人的可读性，又为程序提取提供了锚点。防御性编程的核心在于 **“先提取、后清洗、再修复、最后校验”** 的分层策略，而非追求一步到位解析成功。这套方法在 OpenClaw 的 tool call 解析、多步骤 Agent 调度等场景已被反复验证，能显著降低线上异常率，同时保持代码的可维护性。
