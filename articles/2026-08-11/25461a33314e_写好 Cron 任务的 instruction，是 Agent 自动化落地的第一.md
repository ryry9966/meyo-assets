## 背景：自动化不是“给它一句话”就完了

OpenClaw、MCP 插件以及各种 Agent 框架都开始支持通过 Cron 表达式触发任务。表面上，这是把定时执行的能力交给了 Agent —— 你可以写一句自然语言，让它每天帮你拉报表、巡检服务、同步数据，似乎比传统的 crontab + shell 脚本更灵活。

但真正落地时，很多人会发现：同样一个“每天早上 9 点拉取数据”的意图，用自然语言写第一次勉强能跑，跑到第三天就开始出现诡异的行为——Agent 有时不执行、有时重复执行、有时输出格式错乱导致下游解析失败。根因在于，Cron 环境对指令的确定性、容错性和环境假设的要求，远高于一次性的对话指令。

如果把一次性的对话指令比作“跟同事随口交代一件事”，那 Cron 任务的 instruction 就是“写一份交给夜班操作员的标准化作业书”。它必须预判各种异常，明确每一步的输入输出和边界条件，并且能够脱离人工干预自行闭环。

## 问题：自然语言指令在 Cron 下为什么会失败

简单归因，矛盾集中在以下几点：

1. **隐性上下文丢失**。Agent 的一次性对话可以依赖历史上下文、用户补充纠正，但 Cron 触发时通常是一个干净的 session，没有前文可追溯。类似“用昨天的那个模板生成报告”这样的依赖，会在定时环境下直接失效。

2. **错误处理缺位**。一句“拉取数据并保存到数据库”没有说明当数据库连接失败、数据源返回 429、网络超时等该怎么办。Agent 的默认行为往往是抛一个错误然后结束，而定时任务需要的是可重试、可降级、可通知的恢复流程。

3. **时间与幂等语义不清**。“今天”是触发时间所在日，还是实际执行时间所在日？“运行一次”是指无论执行多久只触发一次，还是严格防止重叠？自然语言对这些关键约束的表达极度模糊。

4. **工具调用顺序与依赖未显式声明**。Agent 在自由发挥时可能调整调用顺序、省略某个非关键步骤，在一次性场景下可以接受，在定时流水线里就是灾难。

因此，Cron 任务的 instruction 必须从“表达意图”转向“规定流程”。

## 做法：把 instruction 当作一个“可复现的 runbook”

在 OpenClaw 这类环境中，我将 Cron 任务的 instruction 写成四个固定段落，几个月跑下来非常稳定：

**第一步：声明任务边界与执行前提**

开头告诉 Agent 当前正在执行的是一个定时任务，并给出任务名称（用于日志和通知标识），明确本次执行的时间窗口和幂等要求。例如：

> 你正在执行每日定时任务 `daily_sales_report`，本次执行触发时间为 {trigger_time}。请先检查是否存在未完成的同任务实例，如果存在则直接退出，不作任何操作。

这里把运行时注入的触发时间作为上下文变量传入，避免 Agent 自行猜测“现在是什么时候”。幂等检查通过一个内部的任务状态工具或简单的文件锁实现。

**第二步：列出精确的工具调用链与参数**

将每个工具调用写成一个步骤，并用序号强制顺序执行。每个步骤包含工具名、参数（尽可能使用变量而非模糊值），以及期望的输出格式。

> 1. 调用 `query_sales_data`，参数 start_time = "2025-03-13T00:00:00Z", end_time = "2025-03-14T00:00:00Z"。  
> 2. 如果返回 status_code != 200 或没有 records，跳转到步骤 4。  
> 3. 调用 `format_report`，参数 template = "weekly_sales_v2"，数据来自步骤 1 返回体。  
> 4. 无论成败，调用 `log_execution` 记录本次执行状态。

关键是将自然语言中的“大概”消灭掉，让 Agent 没有自由解读的空间。

**第三步：内置错误处理分支**

不要依赖 Agent 的通用异常处理。要为每一个可能的非预期结果写出显式的跳转或重试逻辑。重试要写明次数、间隔时间，以及最终失败时的行为（通知、写日志、降级输出一条空报告）。

> 如果 `query_sales_data` 调用返回 HTTP 429，等待 30 秒后重试，最多重试 3 次。3 次后仍失败，调用 `notify_admin` 发送渠道 `#alerts`，内容包含本次执行 ID 和失败原因，然后终止任务。

这种写法虽然啰嗦，但能在凌晨三点无人值守时帮你省下巨大的排障时间。

**第四步：规定最终输出与结束动作**

定时任务输出往往被后续流水线消费（例如写文件、发消息、入库）。必须明确最终输出的格式、存放位置，以及任务结束的显式标志，防止 Agent 输出多余的内容污染下游。

> 最终输出只包含 JSON 对象，字段为 { report_path, record_count, execution_duration }，存在 `latest_daily_sales.json` 中。输出完成后不要附加任何解释文字。

## 踩坑记录

- **时区幻觉**：很多 Cron 调度器使用 UTC，而业务端期望北京时间。如果 instruction 里不写明所有时间参数的时区（一律用 UTC 或显式转换），报表会在隔天中午才出来。**解法**：指令中一律使用 `+08:00` 或 ISO8601 带时区格式，并让工具端也强制按照声明解析。
- **超时未处理**：Agent 调用工具时如果长时间挂起，Cron 调度器可能已经启动下一个实例，导致任务堆积。**解法**：在 instruction 开头加入“本次执行最大耗时 300 秒，超时则主动终止并通知”。
- **“无意义成功”**：工具调用看似成功返回，但数据为 0 条或模板为空。Agent 仍会得意地发一条“报告生成成功”，实际上是一份空白报告。**解法**：增加结果合理性校验步骤，0 条数据时仅记录日志，不发送成功通知。
- **变量注入污染**：直接用 trigger_time 之类的运行时变量拼到指令里时，如果变量包含特殊字符，可能错误截断指令。**解法**：用结构化模板，变量经过 escape 后再嵌入。

## 可复用建议

下面的结构可以直接套用到你的下一份 Cron instruction 中：

```
你现在执行定时任务 [TASK_NAME]。
前提检查：[幂等检查，时区声明，超时限制]
执行步骤：
1. [工具A 调用，参数明细，预期结果]
2. [根据结果分支：成功执行B，失败重试A]
3. [错误处理明细，通知人，通知渠道]
结束动作：[清理，最终输出格式，显式退出信号]
```

只要把这四个部分填满，Agent 在 Cron 模式下的可靠性会从“靠运气”提升到“可以睡觉不挂机”。

## 总结

Cron 任务的 instruction 本质上是一份“给机器的操作手册”。它不追求简洁和优雅，追求的是对所有异常路径的详尽覆盖。在自动化落地过程中，越早接受这个事实，把 instruction 写成可复现、可排障、可恢复的形式，越能减少凌晨三点被报警叫起来的次数。

Agent 提供了自然语言交互的自由，但 Cron 生产环境反逼我们必须收回一部分自由，去换取确定性。这或许就是工程化落地的真正面目。
