## 背景

维护技术社区时，定时发布更新、同步变更日志或推送精选内容，几乎成了日常的自动化需求。很多团队基于 OpenClaw 搭建 Agent，通过 MCP 的浏览器或 HTTP 工具自动发帖，只要内容质量过关，本应相安无事。

现实是，脚本跑了没多久，账号就触发风控，轻则要求验证码，重则直接限制登录。排查一圈，内容没问题，IP 是住宅代理，甚至 User-Agent 也做了轮换——唯独忽略了最核心的一个特征：**操作节奏**。即便每个动作之间都加上了 `sleep(30, 60)`，发帖序列仍然被平台的反自动化模型轻松揪出。

本文聚焦于**节奏控制**这一环节，分享一套在 OpenClaw Agent 中落地、经过多次被迫调参后沉淀下来的工程化做法。不会过度抽象，只谈可复现的调度策略。

## 问题拆解：为什么 `random()` 不够

多数平台的行为分析系统，不仅看单次间隔，更关注**间隔序列的统计特征**。纯粹在某个区间内均匀随机，虽然单个延迟难以预测，但序列整体的分布形态、方差、自相关性等，与人类操作日志的差距依然显著。

真实用户的操作节奏往往具备以下特征：

- **长尾而非均匀**：阅读、思考、打字耗时服从偏正态或对数正态分布，而非平坦的均匀分布。
- **阶段性停顿**：浏览标题 → 点开编辑器 → 斟酌措辞 → 中途想起去看其他帖子再回来 → 最后发布，这些阶段之间的停顿时长有明显差异。
- **微操抖动**：键盘输入、鼠标移动引入毫秒级随机性，累积形成宏观上的非平稳节奏。

因此，节奏控制的起点不是「加一个随机延迟」，而是为整个发帖动作链建模，让每一个原子步骤都携带合理的、可变的耗时。

## 工程化做法

### 1. 基于截断正态分布的基础间隔生成器

放弃 `random.uniform`，改用 `scipy.stats.truncnorm`（或裁剪后的正态分布）。给每个操作类型预设均值和标准差，并设置严格的上下界，防止出现极端异常值。

```python
from scipy.stats import truncnorm

class DelayProfile:
    def __init__(self, mean: float, std: float, low: float, high: float):
        a = (low - mean) / std
        b = (high - mean) / std
        self.dist = truncnorm(a, b, loc=mean, scale=std)

    def sample(self) -> float:
        return self.dist.rvs()
```

不同动作对应的配置示例（单位：秒）：

| 动作          | mean | std | low | high |
|---------------|------|-----|-----|------|
| 页面间切换    | 3.2  | 1.0 | 1.5 | 10   |
| 打开编辑器    | 2.0  | 0.8 | 1.0 | 5    |
| 输入一个汉字  | 0.15 | 0.05| 0.05| 0.5  |
| 发布前停顿    | 5.0  | 2.5 | 2.0 | 20   |

单个动作调用时按配置文件获取数值，不再写死常量。

### 2. 动作链拆分与分心注入

在 OpenClaw 的 Agent 定义中，将发帖拆成多个步骤（Action），每个步骤完成后由 DelayManager 决定停顿时长。随后，以概率 P（建议 0.2~0.3）插入一个「分心动作」：随机点击首页某个帖子、滚动浏览数秒、再回到编辑流程。

分心动作自身的耗时也由独立分布生成，这样可以打破固定步骤间的线性节奏。此时即便将整个发帖流程的时序视图绘制出来，也难以找到明显的阶段边界。

### 3. 基于反馈的动态节奏适配

当平台返回 429（Too Many Requests）或出现 CAPTCHA 时，Agent 应主动放大所有延迟的均值参数（如将全局 multiplier 从 1.0 调整为 1.5~2.0），并在连续成功若干次后缓慢恢复。这种类似 TCP 拥塞控制的退避策略，能避免在风控边缘被彻底封停。

在 MCP 工具层封装一个 `update_pacing_factor` 的接口，Agent 根据响应状态码自动调整，无需人工干预。

## 踩坑记录

- **同时使用固定均值和固定标准差**：很快被识别。需要为不同账号、不同时段、不同帖子长度微调参数，至少使用三个不同的 DelayProfile。
- **忽略编辑器的字符级耗时**：直接用 `page.fill` 一次性填入整段文本，耗时几乎为零，与人类差异巨大。可选方案是逐字输入（带上毫秒级随机停顿），或者在 MCP 工具层模拟多次 `type` 事件，效率下降可以接受。
- **所有动作都用同一个分布**：浏览帖子的停顿和发布的停顿明显不同，混用会导致长尾拖得过长或过短，整体节奏失真。
- **没有跟踪累积空闲时间**：有时脚本因异常退出后重启，立即以高频率发帖。应当在启动时读取上一次操作时间，若间隔较短，主动插入冷却期。

## 可复用建议

1. **抽象成独立的 DelayManager 服务**：通过 MCP 暴露 `get_delay(action_type)` 接口，供任何 Agent 调用，所有策略集中维护。
2. **收集真实时序数据做参考**：在不侵犯隐私的前提下，可从社区后台导出活跃用户的操作间隔统计（例如回帖时间差），拟合出更贴近实际的分布参数。
3. **与身份伪装层配合**：不同的 User-Agent、屏幕分辨率、时区，对应的操作习惯也需要微调，节奏控制只是整体反检测编排中的一环。
4. **增加可观测性**：输出每次延迟的采样值和当前 multiplier，便于事后分析是否因节奏问题被限流。

## 总结

自动化发帖的机器人痕迹，很少来自内容本身，更多源于操作序列的机械感。工程化的节奏控制，不是简单加一个随机数，而是对发帖全链路进行拟人化调度：合理的延迟分布、语义化的阶段停顿、随机的分心动作以及动态反馈调节。

在 OpenClaw + MCP 的自动化实践里，把延迟策略作为一等公民来设计，远比事后补救账号来得划算。希望这些血泪换来的参数和结构，能让你少踩几个封号的坑。
