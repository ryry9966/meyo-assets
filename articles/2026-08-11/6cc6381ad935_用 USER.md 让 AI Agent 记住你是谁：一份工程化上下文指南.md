## 背景

在 Agent 驱动的自动化流程里，任何需要“理解你”的工作——从生成代码、整理笔记，到操作 MCP 工具链——都绕不开一个重复动作：每次对话开头先把自己的习惯、环境和约束喂给模型。即使 OpenClaw 这类工具已经极大降低了接入成本，“我是谁、我用什么、我偏好怎样输出”这几行上下文，依然要在每个会话或每次新任务里冷启动。

一部分开发者会把这类信息写进 system prompt；另一些会在 git 仓库放一份 `CONTEXT.md`，手动复制粘贴。这两种方式都容易导致版本散乱、更新停滞，最后变成一段过时的废话。更关键的，Agent 并没有一个持久化的、可被程序读取的“用户镜像”，导致输出风格不一致，或低估了你本已成熟的配置。

## 问题拆解

缺少结构化的用户档案，常见痛点有四个：

1. **Token 浪费**：每次将相同的信息塞进 prompt，消耗额度且稀释了真正需要推理的上下文。
2. **偏好漂移**：Agent 忘记你的缩进风格、包管理器、测试命令，换一个会话就重新猜测，出现 2 空格与 4 空格混用的场景。
3. **安全边界模糊**：开发者容易随手把含密钥的 `.env` 片段贴进去，泄露风险陡增。
4. **团队协作困难**：每个人的偏好不同，若无统一约定，Agent 在不同成员手下表现天差地别，CI/CD 中更难收敛。

## 方案：把“我是谁”写成 `USER.md`

灵感来自很多 CLI 工具的 `.xxxrc` 文件，我给自己和团队定了一个轻量规范：**在项目根目录或用户级配置目录放置 `USER.md`，Agent 启动/会话初始化时自动加载并注入 system prompt 的顶部**。这并非某个框架的强制要求，而是利用 OpenClaw 灵活的 prompt 模板与资源机制实现的自定义层。

### 1. 文件放哪里？

推荐两级：

- **项目级**：`<project_root>/.openclaw/USER.md`  
  记录与本项目直接相关的上下文（语言版本、框架、lint 规则、构建命令）。
- **用户级**：`~/.openclaw/USER.md`  
  跨项目通用信息（称呼、时区、shell、编辑器、常用工具别名、MCP server 默认地址等）。

Agent 读取时可以合并两份文件，项目级优先级高于用户级，防止全局配置覆盖项目特定行为。

### 2. `USER.md` 写什么？

原则：只写 **Agent 需要但无法从环境推导** 的上下文，不写废话。一个经过迭代的模板：

```markdown
# 个人
- 称呼：Alex
- 时区：Asia/Shanghai
- 工作语言：中文/English

# 技术栈
- 主要语言：Python 3.11, TypeScript 5.x
- 包管理：uv (Python), pnpm (TS)
- 测试：pytest, vitest
- Lint/Format：ruff, eslint+prettier
- Shell：zsh，别名 gs='git status'

# 编码偏好
- 缩进：2 空格（TS），4 空格（Python）
- 注释风格：必要时写 why，不写 what
- 提交信息：conventional commits

# 项目结构
- monorepo: packages/ 下按领域拆分
- 本地运行端口：3000 (web), 8080 (api)
- 环境变量文件：.env.local（切勿将值写入此处）

# MCP 资源
- 通常使用 @openclaw/mcp-server-filesystem 访问当前项目
- 默认浏览器工具：playwright
```

该文件只包含可公开的元数据，敏感信息一律由 Agent 通过环境变量或专用 secret manager 获取。

### 3. 如何在 OpenClaw 中挂载？

OpenClaw 的 system prompt 支持 `{{include "path/to/file"}}` 语法（取决于配置语言）。在 `openclaw.yaml` 或 Claude Desktop 对应的 MCP 配置中：

```yaml
system:
  template: |
    {{include "~/.openclaw/USER.md"}}
    {{include "./.openclaw/USER.md"}}
    # 原有 system prompt...
```

也可以利用 **MCP Prompt 资源**，将 `USER.md` 注册为 `resource://user-profile`，在需要时由工具调用返回，避免每次都占据 prompt 窗口。如果架构不支持模板渲染，那就写一个简短脚本，在启动前把文件内容拼接到环境变量 `OPENCLAW_USER_PROFILE`，然后在 system prompt 中引用该变量。

## 踩坑与避雷

1. **别让它变成垃圾桶**  
   起初我把所有常用命令、API 文档摘要、甚至会议记录都塞进去，`USER.md` 膨胀到 800 行。Agent 表现明显变慢，且开始混淆优先级。严格控制在 **40 行以内**，其余内容应通过工具按需检索。

2. **编码与路径**  
   跨平台时 Windows 的路径与 UTF-8 BOM 会给 include 带来麻烦。统一使用 UTF-8 without BOM，并优先使用相对路径（项目级），用户级使用 `~` 展开前确保程序支持。

3. **版本控制策略**  
   用户级 `USER.md` 不宜直接提交到团队仓库，应加入 `.gitignore`，但提供 `USER.example.md` 作为模板。项目级则可提交，作为团队开发契约的一部分。

4. **与 system prompt 其他部分冲突**  
   如果你的 Agent 自带编程规范，USER.md 中的冲突项（如缩进宽度）可能导致模型迟疑。建议在 system prompt 末尾明确优先级：“USER.md 中的偏好覆盖默认设置”。做过一次测试，ESLint 配置要求单引号，而全局 system prompt 指定了双引号，导致代码生成反复横跳，加上优先级声明后才收敛。

5. **用户变量注入的延迟**  
   有些配置在首次 prompt 构建时载入，一旦会话已开始，再修改 `USER.md` 不会生效。需要重启会话或使用 `/reload` 指令（如果支持）。这是预期行为，但容易让新用户怀疑文件未生效。

## 可复用建议

- **模板化**：在团队内部维护一个 `user-profile-template.md`，列出必填字段，并附带简短注释。新成员入职 10 分钟内就能配好。
- **CI 中的 Agent 使用**：在 CI 场景下，Agent 的身份是“自动化管道”，无需个人偏好。可放一份单独的 `CI_USER.md`，仅包含工作目录、工具路径等无风格化的信息。
- **定期用 Agent 更新**：每过一个月，可以让 Agent 分析最近的会话并建议更新 USER.md。例如：“我注意到你最近改用 pnpm 而非 npm，是否要更新？”这比手动维护更靠谱。
- **分层设计**：如果你的上下文非常复杂，引入 `ROLE.md`（定义 Agent 角色）和 `USER.md`（定义用户特征）解耦，两者在 prompt 中先后加载。

## 总结

给 AI Agent 配一个档案文件并非新鲜概念，但其价值在工程化实践中才会凸显——它降低了每次上下文编排的心智成本，让 Agent 行为从“一次性问答”向“长期协作”演进。用一份简洁、受版本控制的 `USER.md` 承接用户镜像，配合合理的加载策略和避坑约定，能够在不增加复杂度的前提下，显著提升自动化输出的稳定性和个人化程度。它不解决所有问题，但能让你的 Agent 更少猜忌，更多专注在任务本身。
