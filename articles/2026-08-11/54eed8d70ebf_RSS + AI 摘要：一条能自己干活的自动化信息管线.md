## 背景：为什么还在折腾 RSS

在算法推荐和社交分发的时代，RSS 看起来像个古董，但它仍然是最可控的信源接入方式。没有平台过滤，没有标题党权重加成，只要你订阅了，更新就一定送达。问题在于：订阅越多，阅读负债越重。每天打开 Inoreader 或 Miniflux，看到三位数的未读条目，第一反应不是阅读，而是疲惫。

AI 摘要似乎是一剂解药，但“手动复制链接 -> 扔给 ChatGPT -> 等结果”的模式根本不可持续。我们需要一条自动化水管：RSS 更新流入，AI 处理后流出简洁的摘要，我们只消费成品。这篇文章就是我在 OpenClaw 环境下搭建这条管线的工程记录，不卖课，只聊实现与踩坑。

## 问题拆解：管线到底要做什么

目标很明确：将“订阅源更新”到“可读摘要”之间的所有步骤交给程序。具体链路如下：

1. 可靠地获取 RSS 更新，处理重试、去重与内容提取。
2. 对每篇文章调用 LLM 生成指定风格的摘要（通常 150 字以内，带关键要点）。
3. 将摘要存回可检索的数据库，并推送到日常使用的终端（Telegram、手机通知、Markdown 日报）。
4. 整条管线自动运行，无需人工介入，且能应对 API 限流和成本控制。

在 OpenClaw 的语境下，这套管线非常适合封装成一个 **Agent + 工具链** 的组合，或者以 MCP Server 的形式提供标准化能力，让社区成员可以复用到自己的自动化工作流中。

## 实现步骤：从零搭建一条可跑的管线

### 1. RSS 后端选型与接入

选了一个轻量的自部署方案：**Miniflux**（单二进制，PostgreSQL 存储，自带 RESTful API）。它没有花哨的 AI 功能，但胜在稳定、API 设计清晰。部署在低配 VPS 上，用 Docker 一行命令启动。

导入所有订阅后，我写了一个 Python 脚本 `fetch_unread.py`，通过 Miniflux 的 API 获取过去 1 小时内新增的未读条目：

```python
resp = requests.get(f"{MINIFLUX_URL}/v1/entries",
                    params={"status": "unread", "after": since_iso},
                    headers={"X-Auth-Token": API_KEY})
entries = resp.json()["entries"]
```

这里踩的第一个坑：Miniflux 的 `after` 参数接受的是条目**发布时间**，而非 **抓取时间**，有些源会补发旧文，导致一次性涌入大量条目。后来改为按 `changed_at` 过滤，并在数据库层面维护一个已处理条目的 ID 集合，避免重复生成摘要。

### 2. AI 摘要函数：Prompt 与模型选择

摘要的质量取决于 Prompt 和成本控制。我设计了一个工程化的 Prompt 模板，要求只输出结构化 JSON，方便后续程序消费：

```
请阅读以下文章，用中文生成摘要。要求：
1. 摘要长度不超过 120 字。
2. 提取 3 个关键点，每个不超过 10 字。
3. 判断文章是否与技术、工具、自动化相关（relevant: true/false）。
输出 JSON: {"summary": "...", "keypoints": ["...","...","..."], "relevant": true/false}
```

条目正文使用 `html2text` 提取纯文本，截断至 2500 字符再送入 LLM，既保证上下文，又控制 Token 消耗。

模型选择上，最初用 GPT-3.5-turbo，响应快但相关性判断不稳定。后来切到 **本地部署的 Qwen2.5-7B-Instruct**（通过 Ollama 提供 API），成本归零，延迟 1-3 秒，足够满足非实时的摘要需求。对于重要源的英文长文，则路由到 GPT-4o-mini，平衡质量与花销。

踩坑点：本地模型对 JSON 格式的遵循度稍弱，偶发输出尾部截断。解决方法是在 Prompt 末尾加上 `只输出 JSON，不要解释。` 并在代码中增加 JSON 解析异常兜底，失败时记录日志，不阻断管线。

### 3. 组装管线并接入 OpenClaw

我把上述逻辑封装成一个标准的 Python CLI，接收 `--dry-run` 等参数。让它在 OpenClaw 的自动化体系里跑起来，有两种方式：

- **直接作为定时任务**：cron 每 15 分钟调用一次，适合自用。
- **构建 MCP Server**：将“获取未读条目”和“生成摘要”封装为 MCP 工具 `fetch_rss_entries` 和 `summarize_entry`，然后由 OpenClaw 的 Agent 通过 MCP 协议调用，未来可以和其他工具（如笔记写入、消息推送）自由编排。

我选择了后者，写了一个最小化的 MCP Server（基于 `mcp` 库），暴露上面两个工具。Agent 配置为每获取一批新条目就依次调用摘要工具，最后将结果写入一个每日 Markdown 文件，并通过 Webhook 推到 Telegram Bot。这样一来，整个流程变成 Agent 的原子任务，可观测、可中断、可复用。

### 4. 输出与消费

摘要最终汇入一份 `daily_digest.md`，按源分类排版，不相关的条目自动过滤。每天早上打开这个文件，花 3 分钟就能掌握昨日重要动态。关键代码片段如下：

```python
if item["relevant"]:
    digest += f"## [{source_title}]({entry_url})\n"
    digest += f"> {item['summary']}\n"
    digest += f"要点：{'、'.join(item['keypoints'])}\n\n"
```

Telegram 推送采用分批发送，每次最多 3 条摘要，避免刷屏。用简单的 Redis 计数器控制发送节奏，防止 API 被临时限制。

## 踩坑总结与可复用建议

在 3 个月的运行中，这条管线踩过的坑主要集中在以下几点：

- **RSS 内容完整性**：部分源只在 RSS 中提供摘要，需用 `full-content-rss` 类工具补全。但补全质量参差不齐，引入的 HTML 噪声反而影响摘要。最终只对少数重要源开启。
- **LLM 调用超时与重试**：Ollama 在高并发时偶发超时，通过设置 15 秒超时 + 指数退避重试（最多 2 次）解决。
- **成本与算力**：本地 7B 模型需要约 6GB 显存，对于纯 CPU 环境可使用 Q4 量化版，摘要速度略慢但可接受。如果完全使用 OpenAI，按每天处理 100 篇文章计算，月成本约 3-5 美元。
- **噪声过滤**：相关性判断的准确率约 85%，仍有少量误判。可增加关键词黑名单，或在 Agent 中接入用户反馈回路进行微调。

**复用建议清单：**

1. 从少量高质量源开始（5-10 个），跑通全链再扩量，避免陷入调优地狱。
2. 摘要模板与模型放一起管理，用环境变量切换，方便 A/B 测试。
3. MCP Server 设计时尽量无状态，状态外挂到数据库或 KV 存储，这样 Agent 重启不会丢进度。
4. 一定要加 `dry-run` 模式，调试 Prompt 时不炸通讯软件。
5. 如果你已在用 OpenClaw 做自动化，建议把这条管线作为插件贡献回社区，附带示例 Agent 配置，能降低其他人的复现成本。

## 总结

RSS + AI 摘要不是什么新概念，但工程上把“能用”变成“稳定无人值守”需要填不少细节。这套方案的价值在于：**把信息筛选的成本从“人工逐篇判断”降低到“扫一眼摘要”**，并且完全融入现有的自动化工作流。对于 Agent 类应用，这是一个极易落地的高频场景。你可以在已有 RSS 后端的基础上，花一个周末搭出 MVP，之后就是持续打磨 Prompt 和过滤规则的过程。没有魔法，只有持续改进的管线。
