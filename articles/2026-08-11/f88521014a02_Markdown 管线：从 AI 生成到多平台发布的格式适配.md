## 背景

AI 辅助内容创作越来越普遍，多数 Agent、MCP 服务或自动化脚本输出的都是 Markdown。问题出在发布侧：微信公众号、知乎、掘金、Notion、GitHub Discussions 等平台对 Markdown 的支持并不一致。直接把同一份 .md 贴过去，轻则排版混乱，重则图片丢失、公式不渲染、代码块变成纯文本。

手工逐平台调整严重拉低自动化程度，也让“AI 写完就算发布”的流畅体验断裂。我们需要一条从 AI 生成到多平台发布的 Markdown 格式适配管线，让内容在源端保持通用，在目标端自动转换成各平台能正确消费的形态。

## 问题拆解：Markdown 的平台差异

以一份典型 AI 输出为例，它可能包含：

- 标题（`#` ~ `######`），某些平台要求第一级标题不能出现多个（如微信公众号）；
- 图片链接（`![](url)`），绝大多数平台不支持直接引用外部图片，需要先上传到素材库并替换为平台专用格式；
- 代码块（fenced code block），知乎不支持带语言标识的 fenced code block，需要转为缩进代码块，或接受无高亮的展示；
- 数学公式（`$...$` / `$$...$$`），知乎只支持行内公式且渲染引擎不太稳定，掘金需要特殊插件标记；
- 表格、脚注、高亮（`==`）、任务列表（`- [ ]`）等扩展语法，多数平台不支持或支持不完整。

除此之外，不同平台的换行语义（是否需要两个空格+回车才是真正换行）也会导致意外的段落合并。

## 做法：构建可扩展的 Markdown 管线

核心思路是把 Markdown 当成一个中间表示（IR），解析成 AST，再根据目标平台的规则进行渲染或转换。技术选型上，推荐使用 unified 生态（remark/rehype）配合插件体系，因为它的处理流是分步且可插拔的，方便为每个平台定制规则。

一个典型的管线包含三部分：

1. **源格式规范化**  
   AI 生成的 Markdown 经常存在多余空白行、标题层级混乱等问题。先用 remark-preset-lint 系列做一次标准化，确保 AST 结构清晰。例如统一用 ATX 风格标题（`#`），清除行尾空白，将制表符转为空格等。

2. **平台适配转换**  
   这是核心步骤。我们为每个平台定义一套 remark 插件或 transform 函数，在 AST 级别做改写：
   - 图片处理：扫描所有 `image` 节点，对每个外部 URL，调用平台 API（如微信公众号的素材上传接口）获取新的 `media_id` 或图片 URL，然后改写 AST 节点的 `url` 属性。对于不支持外部图片的平台，替换为占位符并生成上传任务清单。
   - 代码块处理：如果目标平台不支持 fenced code block，将 `code` 节点的 `lang` 信息丢弃，并将内容转换为缩进代码块（每行开头加四个空格）。
   - 数学公式：对于不支持 `math` 节点（remark-math）的平台，可将公式转换成图片（提前渲染为 SVG 并上传），替换为 `image` 节点。
   - 特殊语法降级：例如表格可以转为列表或纯文本，任务列表转为普通无序列表，脚注直接内联到段落末尾。
   这些转换全部操作 AST，避免了正则替换带来的边缘 case 问题。

3. **渲染输出**  
   对于仍接受 Markdown 的平台（如掘金、GitHub），直接用 remark-stringify 或其他序列化器输出即可；对于需要 HTML 的平台（如微信公众号），改用 rehype-stringify 输出 HTML，并根据平台的前端环境注入必要的样式（比如代码块的高亮 class）。对于富文本编辑器平台（如飞书、Notion），可以进一步将 HTML 转为平台支持的 JSON 格式（例如 Notion block JSON）。

整个管线可以用脚本串联：`AI 输出 .md → 规范化 → 平台适配（多个分支）→ 渲染为平台格式 → 发布`。

## 踩坑点与工程实践

- **微信公众号图片上传**  
  微信的“素材管理”接口返回的 `url` 并不是永久可访问的，需要使用“图文消息内的图片”接口上传，获取的 url 才能在图文消息里直接引用。而且接口有频率限制，需要加入重试与并发控制。另外，如果图片过大，可能会在上传时被压缩丢失细节，建议先压缩为 2MB 以下的 JPEG 或 PNG。

- **知乎的数学公式**  
  知乎编辑器对行内公式 `$...$` 的渲染容易与货币符号等冲突，建议在转换阶段把不包含数学内容的 `$` 转义为 `\$`，并限制每个段落中数学插件的开启方式。更复杂的公式建议直接渲染为 SVG 图片嵌入。

- **代码块 vs 缩进代码块**  
  知乎的 fenced code block 支持极不稳定，推荐转为缩进代码块。但缩进代码块会丢掉语言信息，无法高亮。如果想保留高亮，可以转为带 class 的 `<pre><code>` HTML 并借助知乎允许的 style，但会被知乎后台过滤一部分 CSS，最终效果依然不可控。需要根据内容重要程度决定降级策略。

- **多平台并行发布**  
  不要在一个 Script 里串行完成所有平台的转换与发布，否则一个平台接口出错就会阻塞后续步骤。建议用 Promise.allSettled 或任务队列，每个平台一个独立处理函数，错误只影响单平台，不影响其它。

## 可复用建议

1. **统一 Markdown 源，配 front-matter**  
   在源 .md 文件顶部用 YAML 声明本篇内容的平台发布意向（如 `platforms: [wechat, zhihu, juejin]`），平台专属内容（如微信公众号的封面图链接、摘要）也放在 front-matter 里，避免污染正文。

2. **插件化平台适配器**  
   将每个平台的 AST 转换逻辑封装成一个独立插件，通过配置文件注册。新增平台时只需实现 `transform(ast, meta)` 和 `render(node)` 两个接口，不修改核心管线。

3. **使用 GitHub Actions 或 OpenClaw Task 进行编排**  
   把整个流程抽象为一个可调度的 Task：AI 生成完内容后，把 .md 推送到仓库的特定目录，触发 Action，依次执行规范化、平台适配、发布。发布结果（含最终链接、错误日志）回写到 Issue 或 Commit Comment 中，方便验证。

4. **灰度发布和人工校验点**  
   完全自动发布有风险，可以加入“生成 HTML/Markdown 版本 → 保存为草稿 → 通知人工检查 → 确认后发布”的环节，降低格式事故的概率。

## 总结

AI 生成 + Markdown 管线本质是把“内容生产”和“格式分发”解耦。当适配逻辑沉淀为一套可复用的工程组件，每接入一个新平台或新 AI 工具，只需要做少量配置，而不必重复踩格式的坑。对 OpenClaw 用户来说，这条管线完全可以用 MCP 服务实现，让 Agent 直接调用图片上传、格式转换等功能，形成一条真正的“写完即发布”自动化流水线。不要把 Markdown 当成最终格式，而是把它当成需要合理编译的源文件，用工程化的方式处理，才是避免手工反复调整的唯一出路。
