# OpenClaw 多 Agent 并行实战：Subagent 编排的坑与复刻路线

## 背景：当串行 Agent 撞上多步长任务

在 OpenClaw 的实际使用中，经常遇到一个典型场景：用户给出一个复合指令，比如“把最新日志分析完，整理成周报，同时检查三个微服务健康状态，再把结果发到飞书”。如果用一个单体 Agent 串行处理，不仅总耗时线性叠加，还容易出现上下文污染——前面的工具调用结果挤占后段任务的 token 配额。

更糟的是，许多工具调用本身具有独立性：捞日志、查健康检查、生成图表、推送消息，它们之间没有严格的先后依赖。串行处理是一种浪费，并行才是正道。

于是 Subagent 编排被提上日程。OpenClaw 支持通过 `task` 工具动态创建子 Agent，每个子 Agent 独立运行，持有自己的上下文、工具集和 completion 生命周期。理论上，这能实现多路并行。但实际落地时，问题远比想象中多。

## 问题定义：并行不是简单的多开 Task

最初我们尝试直接在主 Agent 的 prompt 里写：“当你需要并行处理多个独立任务时，同时发起多个 task 子代理。” 但实际运行结果经常是：

- 主 Agent 仍然按顺序调用 `task`，第一个子代理执行完毕才启动第二个；
- 或者子代理全部启动，但主 Agent 傻等一个结果，导致其他子代理超时被 service 层回收；
- 上下文管理混乱，子代理之间无法共享中间产物（如数据库连接池、公共参数）；
- 错误隔离不足，一个子代理因模型限流抛出 429，整个编排流程直接崩塌。

我们需要的不只是“创建多个子代理”，而是一套**有交付保证、可观测、支持部分失败降级**的并行编排模式。

## 做法与步骤：设计一个稳定的并行编排器

我们没有直接改 OpenClaw 框架，而是在 tool 层和 prompt 层做了约束，形成一套未经框架侵入的编排规范。

### 1. 主 Agent 角色收敛为调度器

主 Agent 的 system prompt 被精简到只做三件事：
- 拆解用户意图为独立任务单元；
- 为每个任务单元生成明确的 `task` 调用（含独立 instruction、工具白名单、预期输出 schema）；
- 使用 **async 收集模式** 等待所有子代理结束后汇总，而非阻塞在第一个。

关键 prompt 设计：

```
当你需要获取多个独立结果时，应一次性发起所有 task 调用，而不等待中间返回。
在发起所有 task 后，使用 wait_all 语义收集结果：
- 成功的子结果按 task_id 聚合
- 失败子任务记录错误原因，不影响其他结果输出
```

### 2. 子代理的工具隔离与契约

每个子代理只授予完成任务所必需的工具，这点在 OpenClaw 里可以通过 `tools` 参数白名单实现。例如，负责日志分析的儿子只给 `read_file` 和 `grep`，飞书通知子代理只给 `send_feishu`。

更重要的是，我们为每个子代理约定了一个**结构化的返回契约**，prompt 末尾强制要求输出：

```json
{"status":"ok|partial|failed","data":{...},"error":null|"reason"}
```

主 Agent 后续只解析这个结构，不再尝试“理解”子代理的自由文本，极大降低归纳出错率。

### 3. 并行启动与超时回收

实际测试中，同时启动超过 4 个子代理时，模型 API 的并发限流会明显加剧。我们引入一个简单的**并发窗口控制**：主 Agent 在 prompt 中被告知“最多同时启动 3 个 task，剩余的待窗口空出后再启动”。这通过在 prompt 中嵌入类似 `max_concurrent=3` 的规则实现，并未修改框架代码。

同时设置子代理超时 `timeout` 参数为 120 秒，防止僵尸代理占用 session。主 Agent 在收集结果时主动忽略超时或报错子代理，生成部分失败报告而不是整体崩溃。

### 4. 共享上下文与中间产物

子代理之间不直接通信。需要共享的数据（如公共参数、数据库连接字符串、临时文件路径）由主 Agent 在创建 task 时注入到各子代理的 instruction 里。对于大段中间结果（比如日志分析完的摘要），我们让子代理写入一个临时文件，主 Agent 在汇总阶段读取，而不是在子代理返回体中传递，避免超出 max_tokens。

## 踩坑实录

### 踩坑1：工具调用冲突
并行子代理同时操作同一个资源（如读写同一个文件）导致文件锁或数据截断。解决方法是**命名空间隔离**：每个子代理使用的文件路径、数据库 key 都加上 task_id 前缀，汇总阶段再做合并。

### 踩坑2：模型幻觉“已完成”
子代理输出 `{"status":"ok"}` 但实际未调用任何工具。我们在子代理 prompt 中硬性要求：**至少产生一次工具调用** 才可返回 ok，否则强制返回 failed。主 Agent 还会抽查关键子代理的工具调用日志（通过 OpenClaw 的 session 事件记录）做验证。

### 踩坑3：成本爆炸
并行子代理每个人都要消耗 token，尤其在长上下文的场景下一次并行 3 个子代理可能同时烧掉几十万 token。我们的经验是，子代理的 instruction 必须**极度精简**，只传必要上下文，不附加大段背景文档，背景由主 Agent 在拆解时压缩成一两句关键信息传递。

### 踩坑4：OpenClaw 的早期 task 生命周期 bug
某些旧版本 OpenClaw 中，子代理结束后 tool 结果不回传主 Agent。升级到 1.5.0+ 版本后修复。如果复现中可以检查 ~/.openclaw/logs 的 task 事件流，看到 `task.completed` 但主 Agent 未收到，可考虑升级。

## 可复用建议

1. **先做单任务稳定再并行**。每个子代理在串行模式下通过充分测试，才投入并行编排。
2. **强制结构化输出契约**。这是并行编排能稳定运行的基础，避免自然语言歧义。
3. **引入轻量级状态机**。在主 Agent 的 prompt 中内建一个状态机概念（init → dispatch → collect → report），防止 Agent 在某个阶段“迷失”。
4. **监控成本**。在 OpenClaw 工具层增加一个简单的 token 计数器，当单次并行消耗超过阈值时降级为串行。
5. **部分失败优先**。接受部分任务失败是常态，设计输出格式时留好占位符，让主 Agent 总能产出可用报告，而不是全有或全无。

## 总结

Subagent 并行编排不是“多开几个 task”那么简单，而是一整套工程化约束的叠加：任务拆解、工具隔离、契约收敛、并发控制、资源命名空间、错误隔离和成本感知。OpenClaw 提供了底层的 task 机制，但真正让并行可靠工作的，是我们在 prompt 层和 tool 层建立的这层“并行编排器”逻辑。目前这套模式已经在日志巡检、多服务健康检查、日报生成等场景稳定运行，日均处理并行任务组 40+，整体耗时相比串行降低 60% 以上。

对于想快速上手的朋友，建议从一个最简单的二并行场景开始（比如同时查两个 API 返回），逐步叠加契约规范、窗口控制和降级策略。不要在第一次就追求全自动复杂的并行编排，那样坑只会更深。
