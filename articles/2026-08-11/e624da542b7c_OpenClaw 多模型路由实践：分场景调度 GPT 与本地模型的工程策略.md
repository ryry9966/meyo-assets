## 背景：为什么需要多模型路由

在 OpenClaw 驱动的 Agent 或自动化流程中，模型选择直接决定成本、延迟与任务成功率。一个典型场景：你构建了一个代码审查 Agent，日常需要处理大量简单的格式检查、命名规范校验，偶尔也需要对复杂逻辑重构给出建议。如果所有请求都丢给 GPT-4，Token 消耗和响应时间会让工具在生产环境难以长期维持；若全部改用本地部署的 Llama3/Qwen2，则遇到需要深度推理或多步工具调用的任务时，成功率会断崖式下降。更麻烦的是，某些包含敏感代码片段的请求，直接从本地模型走更符合数据安全要求。

OpenClaw 本身允许为不同 Agent 或 Task 绑定不同模型，但没有内置“按任务特征动态选模型”的路由层。我们需要在 Agent 逻辑中植入一个轻量的模型路由器，把高成本模型的算力花在真正需要的地方，把高频低难度请求安全地交给本地模型处理。

## 路由设计要点

多模型路由并非简单地判断“复杂度高低”，需要综合考虑：

1. **任务类型**：是否涉及多步工具调用、复杂数学推理、长上下文聚合。这类任务 GPT-4 系列优势明显，本地模型容易在中间步骤丢失格式或逻辑。
2. **数据隐私**：请求中是否包含内部代码、密钥片段、未脱敏用户数据。此时强制走本地模型，避免数据离开受控环境。
3. **成本阈值**：预估 Token 用量。例如当对话历史已积累超过 4k Token，继续用 GPT-4 会推高单次调用成本，此时可降级到 GPT-4o-mini 或高质量本地模型完成信息抽取、摘要等任务。
4. **延迟要求**：同步的户交互场景（如 IDE 内联补全）要求毫秒级响应，本地模型即使准确率稍低也可接受；异步批处理则可以承受更高延迟，换取 GPT 的准确性。

## 在 OpenClaw 中的落地做法

以 OpenClaw 的 `Tool` 或 `Step` 抽象为例，可以创建一个 `ModelRouter` 工具，在 Agent 实际执行前由路由器拦截并决定最终调用的模型。大致的步骤：

**1. 定义模型池与能力标签**

为每个可用模型建立 profile，例如：

```python
models = {
    "gpt-4": {"cost_high": True, "reasoning": 9, "tool_call": 9, "local": False},
    "gpt-4o-mini": {"cost_high": False, "reasoning": 7, "tool_call": 8, "local": False},
    "qwen2-72b-local": {"cost_high": False, "reasoning": 7, "tool_call": 5, "local": True},
    "llama3-8b-local": {"cost_high": False, "reasoning": 5, "tool_call": 2, "local": True},
}
```

这些评分可以根据实际跑测结果调整，不必追求绝对精确。

**2. 实现轻量分类器**

在 `ModelRouter` 的预处理函数中，对当前请求进行快速分类。工程上推荐使用规则+简单关键词匹配以避免额外调用模型：

- 检查是否有“编写代码”“重构”“解释原理”等关键词，标记为高推理。
- 统计历史消息的 Token 总长，超过阈值认为属于长上下文任务。
- 用正则检测请求中是否包含工具调用声明（如 OpenClaw 的 `tool_choice` 字段），标记为 Tool Use 场景。
- 提供白名单决策：凡匹配敏感模式（如“API_KEY”“password”）的请求，强制路由到本地模型。

**3. 路由决策表**

将上述特征映射为一个决策树：

```
if sensitive: → best_local
elif tool_call required:
    if long_context: → gpt-4
    else: → gpt-4o-mini or qwen2-72b-local (cost-based)
elif high_reasoning and not local_only: → gpt-4
else: → local cost-efficient model
```

实际项目中可以用一个简单的 `match-case` 或配置文件表达，方便后续调整。

**4. 集成到 OpenClaw 流程**

将路由器作为 Agent 执行链的第一个 Step。例如，OpenClaw 的 Task 定义：

```yaml
steps:
  - id: route_model
    tool: model_router
    inputs:
      user_query: "{{input}}"
      history: "{{conversation_history}}"
    outputs:
      model: "{{routed_model}}"
  - id: execute
    agent: main_agent
    model: "{{route_model.outputs.model}}"
    inputs: ...
```

这样就可以实现无侵入的动态选模。

## 踩坑与经验

- **本地模型对 JSON mode 的兼容性参差不齐**。许多本地模型即使宣称支持 function calling，实际输出仍可能多出解释文本或丢失闭合括号。必须在解析前做清洗，必要时用 `json_repair` 类库兜底。
- **上下文窗口短**：8B/7B 模型的上下文往往仅有 4k–8k，路由判定为长上下文任务时需提前截断历史或仅保留关键轮次，否则会报错或产出幻觉。
- **本地模型推理阻塞问题**：如果本地服务使用单线程推理，当多个 Agent 同时请求本地模型时容易排队超时。建议为本地模型增加一个请求队列，并设置短超时时间（3 秒），超时后自动降级到小型云端模型（如 gpt-4o-mini）兜底，确保流程不被卡死。
- **路由规则不宜过度拟合**：初期容易把分类规则写得过于复杂，试图覆盖所有边缘情况。建议保持规则简单，并结合 A/B 日志观察真实流向。一个有效的方法是：在路由器里记录每次决策的理由和后续任务是否成功，每周对失败案例进行回溯调整。

## 可复用建议

- **维护一份“任务-模型”匹配日志**，记录每个路由决策是否正确，用于迭代规则。
- **将路由器做成无状态的插件**，接收请求并返回模型名，方便在不同 Agent 间复用。
- **对本地模型使用更严格的 system prompt**，明确要求输出格式（如“只输出合法 JSON，不要加其他文字”），部分弥补指令遵循能力的不足。
- **成本敏感场景，设置模型降级链**：例如优先 gpt-4o-mini，若失败或超时则 fallback 到本地模型，反之亦然。OpenClaw 的 `retry` 机制可以辅助实现。
- **隐私保护优先**：对于所有敏感检测命中请求，务必做硬路由到本地，不能因降级逻辑而将数据发送到云端。

## 总结

OpenClaw 多模型路由不是一个“一劳永逸”的配置项，而是需要根据任务特征持续调优的工程实践。核心思路是把GPT级别的推理能力当作稀缺资源，仅在复杂推理、工具调用等真正需要可靠逻辑的场景使用；将本地模型用于高频、低难度或隐私敏感任务，从而在性能与成本之间取得平衡。路由器的实现可以非常简单，关键是定义清晰的决策边界，并保持足够的可观测性来修正错误分配。最终，你要的是让 Agent 在合适的场景用合适的脑子，而不是让 GPT 扛下所有。
