# LLM 输出解析的防御性编程：混合处理 JSON 与自定义标签

## 背景

在 OpenClaw、Agent 或 MCP 等自动化项目中，我们频繁要求大模型输出结构化数据——无论是工具调用的参数，还是带语义标签的中间推理。常见的格式有两类：**JSON** 和**自定义标签**（类似 XML，如 `<tool_call>` `</tool_call>`）。理想情况下，模型会严格按照 prompt 给出干净的 JSON 或标签封装的内容。但工程实践中，输出往往是两者的混合体：JSON 被塞进 Markdown 代码块，标签内嵌着未转义的 JSON，或者因为上下文截断导致标签不闭合。

如果解析器只做最简单的 `JSON.parse` 或正则匹配，线上会高频触发解析异常，进而让整个 Agent 流程中断。防御性编程的目标不是信任模型，而是**在尽可能多的失真情况下仍然提取出可用数据**。

## 问题分类

我们投产的 Agent 系统观察到的典型问题包括：

1. **Markdown 污染**：JSON 被包裹在 ```` ```json ```` 代码块中，有时还附带语言标注的变体（如 `jsonc`）。
2. **JSON 语法瑕疵**：尾部多余逗号、字段名未加引号、字符串内出现未转义的双引号或换行符。
3. **标签/JSON 混合**：输出可能是 XML 风格标签，但标签内部的内容却是 JSON，例如：
   ```
   <action>
   {"tool":"search","query":"today's weather"}
   </action>
   ```
   或者相反，JSON 的值中包含未转义的 `<tag>`。
4. **不闭合、截断**：流式输出或长上下文里，`<response>` 没有结尾标签，或者 JSON 缺少闭合括号。
5. **干扰文本**：模型在输出首尾附加了礼貌语、解释性文字，使得纯粹的结构化提取失败。

## 防御性解析做法

### 1. 提取最可能的 JSON 块

不要直接对整个字符串做 `JSON.parse`，而是**先清洗**。推荐步骤：

- 尝试匹配 Markdown 代码块：`/```(?:json)?\s*([\s\S]*?)```/`，提取内部内容。
- 若无代码块，使用首个 `{` 和最后一个 `}` 截取子串（可能仍需处理嵌套对象和数组中出现的 `}`）。
- 对截取后的字符串做“宽容修复”：
  - 移除尾部多余逗号（正则 `/,(\s*[}\]])/g` 替换为 `$1`）。
  - 简单处理无引号的 key（仅当风险可控且 prompt 已明确要求 JSON 模式时才启用）。
  - 使用 `json5` 等宽松解析库代替原生 `JSON.parse`，它们能容忍注释、尾部逗号、单引号等。
- 如果仍然失败，则记录原始字符串并回退到 fallback（如重试、让模型自修正）。

```python
import re
import json5

def extract_json(text: str):
    # 尝试匹配代码块
    m = re.search(r'```(?:json)?\s*([\s\S]*?)```', text)
    if m:
        text = m.group(1)
    else:
        # 取第一个 { 和最后一个 } 之间的部分
        start = text.find('{')
        end = text.rfind('}')
        if start != -1 and end != -1:
            text = text[start:end+1]
    # 用 json5 解析，容忍尾部逗号、注释等
    return json5.loads(text)
```

### 2. 标签格式的健壮解析

当输出使用自定义标签（如 `<tool>...</tool>`）包裹内容时，简单的正则 `/>(.*?)<\/tool>/` 容易在内容含有其他标签或特殊字符时失效。更稳健的方式是**基于栈的简单状态机**：

- 扫描字符串，遇到 `<tag>` 时压栈，遇到 `</tag>` 时弹栈，同时记录对应的内容区间。
- 对非闭合标签，可以设定最大深度或容忍未闭合，将剩余部分作为最佳尝试内容。
- 提取标签内部内容后，再递归调用 JSON 提取逻辑（如果内部是 JSON）。

一个实用的简化：如果确定输出以特定起始标签开头且结束标签应唯一，可以先查找对应的结束标签位置，做 Stub 提取，并用启发式补全。

### 3. 混合格式的策略

处理“标签包裹 JSON”的场景时，按以下顺序：

1. 先尝试直接提取纯 JSON（忽略标签）。
2. 若失败，定位最外层的预期标签（通过 prompt 约定的固定标签名），提取内部原始字符串。
3. 对内部字符串再次调用 JSON 提取。
4. 若以上均失败，尝试用正则匹配所有可能标签并移除标签本身，获得裸 JSON 再解析。

重要的是，**不要假设输出只有一个结构**。有时模型会输出 `<thinking>...</thinking><tool_call>...</tool_call>`，需要按优先级提取。

## 实际踩坑点

- **嵌套 JSON 中的 `}` 导致截断**：简单的 `rfind('}')` 无法应对对象内部的多层嵌套。可以计算括号平衡，找到真正的结束位置。
- **流式输出下标签被拆分**：例如收到的 chunk 是 `<tool`，下一个 chunk 是 `_call>`。解析器需要在半成品标签前缓存，确定收到完整标签后再提取内容。
- **模型产生自定义标签的大小写变体**：`<Tool_Call>` vs `<tool_call>`，需考虑大小写不敏感匹配，或在 prompt 里强调格式。
- **JSON 内部字符串含未转义的 `<` 或 `>` 导致标签误识别**：若 JSON 值中包含 `<summary>` 这类文本，简单的标签正则会把 JSON 内部当作新标签。最好先提取 JSON，再解析标签；或者将非标签的 `<` 替换为占位符，解析后还原。
- **双引号内的 unicode 控制字符**：某些模型会输出 `\u0000` 等不可见字符，直接 JSON.parse 会报错，需要过滤控制字符或使用宽松解码器。

## 可复用建议

- **封装为独立解析器**：将上述逻辑抽象为一个 `parse_llm_output(text, format_hint)` 工具，内部包含 JSON 修复、标签栈解析、fallback 策略。在整个 Agent 代码中统一调用，避免各地重复脆弱解析。
- **与 Prompt 协同设计**：在提示词中明确要求“仅输出 JSON，不要添加代码块标记”或“使用 <result>...</result> 包裹，内部必须是合法 JSON”。这样可从源头减少污染。
- **Schema 验证**：解析得到对象后，用 JSON Schema 或 Pydantic 模型验证必填字段和类型。验证失败时也可以作为触发重试的信号。
- **重试与自修复**：解析失败时，把错误信息和原始输出交给另一个轻量级模型，要求它返回合法 JSON，这比直接丢弃结果更可靠。设置最大重试次数防止死循环。
- **监控与日志**：记录解析失败时的原始字符串，统计失败率，帮助迭代 prompt 和解析规则。

## 总结

LLM 输出解析不能依赖模型完美遵守格式约定，防御性编程是把解析逻辑本身当作容错系统来设计。在 JSON 和自定义标签混合的场景下，通过“清洗 → 宽松解析 → 标签栈提取 → 内容再解析 → schema 验证”的多层防线，可以显著降低线上断点，提升 Agent 的鲁棒性。花时间打磨一个健壮的解析器，远比反复调整 prompt 追问“为什么模型不听话”收益更高。
