## 背景：你需要一个“定时器”，但 OpenClaw 给了你两个

在 OpenClaw 的 workflow 配置里，如果想让某个任务自动重复运行，你一定会碰到两种触发方式：  
- `cron`：使用标准的 cron 表达式，指定“在什么时刻运行”；  
- `heartbeat`：用一个固定的时间间隔，循环触发，“每隔多久运行一次”。

很多刚接触 OpenClaw 做 Agent 自动化、MCP 工具链或插件开发的朋友，第一反应是“都一样嘛，反正都是定期跑”。但在工程落地时，选错触发方式轻则导致任务错时、漏触发，重则引发并发堆积、状态污染，甚至让上下游系统雪崩。

本文不讨论“哪个更好”，而是结合真实踩坑经历，给出两者在 OpenClaw 里的正确用法边界、配置示例、排障策略和可复用的选型建议。

---

## 问题：看似相同，实则语义天差地别

最容易混淆的地方在于：表面上看，cron 表达式 `*/5 * * * *` 和 heartbeat `interval: 300s` 好像都是“每 5 分钟执行一次”。但它们的执行语义完全不同：

- **cron** 锚定的是**绝对时间**。`0 9 * * 1-5` 一定是在每个工作日 09:00:00 触发，即使服务在 09:00:05 才启动，这次任务也会被跳过（除非配置了“追赶”策略）。  
- **heartbeat** 锚定的是**相对启动时间**。`interval: 10m` 表示服务启动后，每 10 分钟执行一次，重启后计时器重置。它不关心现在是几点几分，只关心“距离上次启动或上次执行过去了多久”。

这意味着，如果你的任务是“每天 23:00 生成日报并推送”，用 heartbeat 就会彻底跑偏——今天是 23:00 推送，后天因为重启变成了 08:15，完全不可控。反之，如果任务是“持续监控某个事件队列，希望尽快处理”，用 cron 最小粒度只有分钟级（且受系统负载影响），而 heartbeat 可以做到秒级甚至毫秒级轮询。

## 做法 / 步骤：在 OpenClaw 中如何选择和配置

### 1. 场景分类——先问自己三个问题

在写 YAML 之前，先判定任务的时间属性：

| 问题 | 倾向 cron | 倾向 heartbeat |
|------|------------|----------------|
| 触发时间是否依赖人类日历（如工作日、节假日）？ | ✓ | ✗ |
| 是否需要高频率（秒级）执行？ | ✗ | ✓ |
| 任务是否要求“自服务启动后立即开始循环，且不受重启影响”？ | ✗ | ✓ |

### 2. 配置示例

一个典型的 cron 任务（每日数据归档）：
```yaml
workflows:
  - name: daily-archive
    trigger:
      type: cron
      spec: "0 2 * * *"        # 每天凌晨 2 点
      timezone: "Asia/Shanghai"
    job:
      type: script
      command: "python3 archive.py --date yesterday"
```

一个典型的 heartbeat 任务（实时拉取外部告警）：
```yaml
workflows:
  - name: alert-poller
    trigger:
      type: heartbeat
      interval: 30s          # 每 30 秒轮询一次
      initial_delay: 5s      # 启动后延迟 5 秒再开始
    job:
      type: http
      method: GET
      url: "https://api.example.com/alerts"
```

### 3. 混合使用——高级玩法

在复杂 Agent 场景中，我习惯用 heartbeat 做“健康检查 + 兜底”，用 cron 做“精准业务动作”。例如，一个数据管道 Agent：  
- heartbeat 每 60 秒检查任务队列长度，若堆积超过阈值则触发扩容通知；  
- cron 每小时整点汇总处理量并写入统计表，生成报表。  
两者互不干扰，且 heartbeat 避免了 cron 在秒级检查上的尴尬。

## 踩坑点：这些坑我都替你掉进去过

### 坑 1：cron 时区陷阱

OpenClaw 的 cron 默认采用 **UTC 时间**。如果你在国内服务器上写了 `0 9 * * *`，却不指定 `timezone: Asia/Shanghai`，那任务实际会在北京时间下午 5 点执行。大量数据同步任务因此错过了上游的时间窗口。  
**修复**：始终显式声明 `timezone`，并在 CI 中增加时区断言测试。

### 坑 2：heartbeat 重叠执行与并发控制

heartbeat 不会等待上一次任务结束。如果 `interval: 10s`，但任务偶尔需要 12 秒才能完成，就会出现任务实例并发堆积，最终打爆数据库连接池。  
**修复**：在 job 定义中设置 `concurrency: 1` 或使用分布式锁，保证同一 workflow 同一时刻只运行一个实例。

### 坑 3：cron 的“错过即跳过”

如果服务在 cron 时间点正好宕机或正在重启，当次触发会被永久跳过（除非开启 `catchup: true`，但该特性在某些版本中不稳定，容易造成启动后立即并发执行大量历史任务）。  
**折中**：对关键任务，我会在任务内部增加一步“补偿检查”——执行前先查数据库看最近一次成功执行的时间，如果距离预期偏差过大，自动补执行并告警。

### 坑 4：heartbeat 的漂移

heartbeat 的计时器在系统负载高时可能出现“前一次执行耗时过长，导致下次触发延迟”的漂移现象。  
**缓解**：用 `fixed_delay: true` 参数（部分版本支持），保证两次执行开始时间的间隔恒定，而不是从结束时间开始计算，减少漂移。

## 可复用建议：给生产环境的选型清单

1. **能用 cron 就不要用 heartbeat 模拟日历时间**。这是最常见的坏味道。  
2. **heartbeat 适合高频、非严格定时的轮询和保活**。如果间隔需要 <30 秒，选 heartbeat。  
3. **所有 cron 配置必须显式设置 timezone**，并建立告警规则：若连续两次未触发，立即通知。  
4. **给 heartbeat 任务加并发上限**，默认 `concurrency: 1`，除非你明确需要并行。  
5. **统一监控**：不管是哪种触发器，一定要输出 `last_run_status` 和 `next_run_time` 到监控系统，不要靠“感觉”判断任务是否跑了。  
6. **在文档中标记触发语义**：每次写完 workflow，在注释里写明为什么选 cron 或 heartbeat，方便接手同事理解。

## 总结

OpenClaw 的 cron 和 heartbeat 不是可互相替代的糖衣，而是两种完全不同的调度原语。  
- **cron 回答“什么时候做”**——它有日历、有时区、有“错过”的风险。  
- **heartbeat 回答“隔多久做”**——它更简单、更密集，但要求你不关心绝对时间点。

工程上，我从不追求只用一种；根据任务的“时间锚定需求”和“频率需求”明确选型，并做好并发控制、时区处理和补偿监控，才能让 Agent 定时任务真正可靠。下次再打开配置文件时，别急着复制粘贴，先想清楚：你的任务是需要一把瑞士军刀，还是一个准确的闹钟。
