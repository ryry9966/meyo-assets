## 背景

在 OpenClaw 这类支持 MCP 插件扩展的 Agent 框架里，`memory_recall` 几乎是个刚需工具——让 Agent 能按上下文召回历史对话、任务记录或外部知识。当你准备实现这个工具时，第一个工程决策就是：**用语义搜索（向量）还是全文搜索（关键词）？**  

社区里常见的做法是直接上一层向量数据库，认为“语义搜索更 AI”。但在真实项目中，这个选择会因为数据规模、查询模式和召回语义要求产生很大差异。本文用一套可复现的 `memory_recall` 实现，做个工程化的对比。

## 问题：语义搜索不是“更聪明”的全文搜索

两种检索模式的本质差异：

- **全文搜索（BM25 / FTS5）**：靠词频和逆文档频率匹配关键词，对专有名词、错误拼写敏感，但能精准命中精确字符片段。
- **语义搜索（embedding + 向量索引）**：把文本映射到高维空间，按语义距离召回，能扛住同义词和表述变化，但可能丢掉精确字符串匹配，且对短查询或冷僻命名实体不可靠。

Agent 的 `memory_recall` 调用经常混合两类意图：
1. “查一下我之前和用户讨论过 `OpenClaw slow tool timeout` 的处理方案” —— 精准关键词。
2. “我记得之前有个关于连接超时的问题，后来怎么解决的？” —— 模糊语义。

如果你只用向量搜索，第一条可能召回一堆不相关的“性能问题”，反而把 exact match 漏掉；只用全文搜索，第二条可能因为没出现“连接超时”这几个字而空召回。真实场景下，往往是**互补缺口**比单纯优劣更值得关注。

## 做法：一个 MCP 插件里的双模式 memory_recall

下面给出一个为 OpenClaw 实现的 MCP 工具 `memory_recall` 的最小可行设计，同时内置两种检索模式，并允许 Agent 显式选择或使用自动混合模式。

### 1. 内存索引结构

- 全文索引：基于 SQLite FTS5，在 `memory` 表中为 `content` 列建立全文索引。
- 语义索引：使用轻量级本地向量库（如 Chroma 的持久化客户端），用 `all-MiniLM-L6-v2` 生成 384 维 embedding。

每条记忆存储时，同时写入 FTS5 表和向量库，并保留相同的 `memory_id` 与元数据。

### 2. MCP 工具定义

```json
{
  "name": "memory_recall",
  "description": "按查询召回历史记忆，支持语义搜索和全文搜索两种模式",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "mode": {
        "type": "string",
        "enum": ["semantic", "fulltext", "hybrid"],
        "default": "hybrid"
      },
      "limit": { "type": "integer", "default": 5 },
      "filter": {
        "type": "object",
        "description": "按 metadata 过滤，例如 { \"agent_id\": \"...\" }"
      }
    },
    "required": ["query"]
  }
}
```

### 3. 混合模式实现要点

混合模式的关键不是“把两套结果拼起来”，而是做一个轻量级融合：

- 分别从向量库和 FTS5 获取 `top_k = limit * 2` 个候选，赋予初始分数（向量用余弦相似度，FTS5 用 BM25）。
- 对分数做归一化（例如用 min-max 缩放到 [0,1]）。
- 对于同时出现在两个列表中的记忆，给予小幅加权（比如 +0.1），因为双端命中信号更强。
- 按最终分数排序，截取前 `limit` 条返回，同时返回每条记忆附带 `match_type` 标记，方便 Agent 判断。

代码不贴全量，核心融合逻辑约 60 行 Python，可以直接嵌入 MCP 服务插件。

## 踩坑点

1. **短查询的向量搜索失效**  
   用户输入 “502 错误”、“db timeout” 时，embedding 模型往往无法给出有意义的表示，召回几乎随机。这类查询必须 fallback 到全文搜索，或由 Agent 在调用前先判断查询是否太“关键词化”。

2. **混合排序的分数尺度不一致**  
   直接拿余弦相似度与 BM25 分数加权，往往因为分布范围不同导致全文得分被淹没。一定要做分数归一化，最简单的就是 min-max 或基于排名的倒数融合，两者工程代价极低但效果提升明显。

3. **embedding 模型冷启动与成本**  
   每次存储记忆都要调用 embedding 服务（本地或远端），在高频写入时会成为性能瓶颈。建议缓存常用短语的向量，或对批量写入用流水线异步处理。

4. **元数据过滤的缺失导致多租户混乱**  
   务必将 `agent_id`、`session_id`、`memory_type` 等作为过滤条件，否则混合召回在多 Agent 共享记忆库时会引入噪声。在 Chroma 里用 `where` 参数，在 FTS5 里用附加列并 WHERE 过滤。

5. **Agent 如何选择模式？**  
   直接把 `mode` 交给 LLM 判断有风险，容易滥用 `semantic`。实践中用规则更好：查询长度 > 20 字符且包含疑问结构时启用语义模式，否则用全文或混合。可以在工具 description 里给出启发式建议，或干脆固定为混合模式，省去决策。

## 可复用建议

- **小规模记忆（<5k 条）直接用全文搜索就够了**，复杂度低且不依赖嵌入模型。加入 `hybrid` 反而增加维护成本。
- **当记忆量级上升，且 Agent 需要跨对话理解意图时**，引入语义搜索。但保留全文搜索作为保底，并用上述融合方法。
- **评测时构造两类测试用例**：精确关键词查询（检验全文召回）和改写查询（检验语义覆盖）。没有测试的检索调优通常是在凭感觉。
- 工程落地时尽量将 `memory_recall` 做成无状态工具，索引持久化依赖 SQLite 和 Chroma 的本地文件，方便和 OpenClaw 的 MCP server 一起打包部署。

## 总结

语义搜索和全文搜索在 Agent 记忆召回里不是二选一，而是**输入-输出对齐的两种路径**。当你给 Agent 的 `query` 更像关键词时，用全文；当它更接近自然语言描述时，用语义。最终，一个好的 `memory_recall` 应当让 Agent 不必关心底层到底是向量还是倒排索引，而是拿到一条“像是它想要的”记忆。混合策略加上分数归一化，基本可以覆盖 80% 以上的实际场景，剩下的 20% 留给元数据过滤和 Agent 自己对召回结果的二次筛选。
