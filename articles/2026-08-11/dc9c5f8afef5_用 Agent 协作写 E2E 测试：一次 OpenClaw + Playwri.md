## 背景

端到端（E2E）测试是保证关键用户路径不被回归破坏的重要手段，但编写和维护成本高得让人头疼。选择器脆弱、页面操作步骤繁琐、异步逻辑处理不到位——每个写过 Playwright/Cypress 的人都能体会到，写测试的精力有时比写业务代码还多。

AI 能生成测试代码，但直接丢给 GPT 的产出往往像个刚入职的实习生：大体方向对，一跑就崩。错误横飞、选择器不存在、步骤遗漏，反复兜底调试仍然要花不少时间。于是我们开始想：能不能让 AI 不只生成代码，而是像一个真正的测试工程师那样，能看到页面、能执行、能从错误里学习、循环改进？Agent 协作的方式正好匹配这个需求。

OpenClaw 社区已经在用 Agent 框架编排复杂任务，配合 MCP（Model Context Protocol）协议接入浏览器自动化工具，使得“让 Agent 帮你写 E2E 测试”这件事变得工程上可行。

## 问题拆解

目标：给定一个页面 URL 和测试目标描述，Agent 自主完成分析页面、生成测试脚本、执行、排错、修正的闭环。

核心挑战：
- 页面状态不可见，初始代码生成容易与真实 DOM 脱节；
- 执行报错后需要有效诊断，而不是无脑重试；
- 多轮修改要保持在同一个测试意图上，不偏离原始需求。

## 实现做法

我们基于 OpenClaw 定义了一个 `e2e-tester` agent，并通过 MCP 接入了 Playwright 服务器（`@anthropic/mcp-server-playwright`），提供了以下关键工具：

- `browser_navigate` / `browser_snapshot`：获取页面的可访问性树结构（axe-core snapshot），而非原始 HTML，这能提供语义化的元素描述；
- `browser_click` / `browser_type`：基础交互；
- `browser_run_code`：执行任意 Playwright 代码片段，用来运行生成的测试脚本；
- `browser_take_screenshot`：错误时抓取页面截图，供 Agent 视觉分析。

Agent 的系统提示强调：“你是一名严谨的测试工程师。不要假设选择器，必须基于 snapshot 中的元素引用定位。编写测试前先梳理步骤，执行后如果没有通过，分析截图与错误栈，定位到具体的操作或等待问题，修正后重试，最多重试 3 次。”

**典型工作流长这样：**

1. **用户输入**：“为 https://example.com/login 编写测试：使用邮箱 `test@example.com` 和密码 `123456` 登录，验证跳转到仪表板并显示‘欢迎’字样。”
2. **探索页面**：Agent 调用 `browser_navigate` 到登录页，再调用 `browser_snapshot`，得到一份结构清晰的页面元素列表，比如“textbox ‘邮箱’”、“textbox ‘密码’”、“button ‘登录’”。
3. **制定计划**：Agent 输出测试步骤的自然语言列表：
   - 导航到登录页
   - 在邮箱输入框填入 test@example.com
   - 在密码输入框填入 123456
   - 点击登录按钮
   - 等待导航完成，检查 URL 包含 /dashboard
   - 验证页面文本包含 “欢迎”
4. **生成测试代码**：基于上述计划，Agent 生成 Playwright 测试脚本（使用 `browser_run_code` 执行）。注意，代码中会直接引用 snapshot 中出现的可访问性选择器，例如 `page.getByRole('textbox', { name: '邮箱' })`。
5. **执行与排错**：Agent 调用 `browser_run_code` 执行测试。若成功，报告通过；若失败，读取错误栈，并调用 `browser_take_screenshot` 获取失败瞬间的页面状态，分析原因。常见原因：登录后跳转较慢，缺少 `waitForURL`；或者验证文本时页面还没有渲染完，需要等待元素可见。
6. **迭代修改**：修复代码后重新执行，直到通过或达到最大重试次数。Agent 会保留每次尝试的记录，避免重复犯同一个错误。

实际跑下来，对于中等复杂度的登录流程，Agent 平均 1-2 次重试就能给出可以通过的测试脚本。相比人工从零写，节省的时间主要在“选择器挖掘”和“失败调试”环节。

## 踩坑点与避坑指南

1. **Snapshot 比 HTML 更适合作为上下文**。直接给 Agent 扔一大段 HTML 既浪费 token，也会让选择器变得随意。accessibility snapshot 的语义化元素（role + name）能天然与 Playwright 的 `getByRole` 对应，生成的脚本鲁棒性更好。
2. **`browser_run_code` 执行上下文问题**。每次调用 `browser_run_code` 是在当前活跃的浏览器上下文中执行。要确保测试开始前有一个干净的状态（cookies、localStorage 清空），否则多次执行会相互污染。我们的做法是在测试脚本开头通过 Playwright 代码清除状态，而不是依赖 `browser_navigate` 新建上下文。
3. **等待策略不能交给 Agent 自己猜**。Agent 倾向于在代码里只写固定 `waitForTimeout`，一旦网络抖动就会失败。我们在系统提示里明确要求优先使用 `waitForURL`、`waitForSelector` 等条件等待，并限制了 `waitForTimeout` 的使用。只保留截图让 Agent 看到界面状态，它就能更好判断需要等待的目标。
4. **复杂交互还需人工预置步骤**。像 OAuth 第三方登录、文件上传等，目前的 snapshot 表达能力有限，很难自动处理。这类场景建议将其抽象为可复用的函数（通过 MCP 提供自定义工具），在 Agent 内部当作一个“动作”来组合，而不是让生成脚本里硬写原始流程。
5. **多 Agent 协作的边界**。我们尝试用一个 Agent 探索页面并生成测试意图，另一个 Agent 负责编代码，这样两者解耦后意图 Agent 不会被低层次的代码错误干扰。但实际中，两个 Agent 之间传递意图信息时容易产生理解偏差，反而增加回归次数。现阶段更推荐单 Agent 的内循环，足够解决大部分单页面流程。

## 可复用建议

- **将测试动作工具化**：把常用的登录、注册、表单提交封装成 MCP 工具，让 Agent 直接调用，而不是每次从零生成 Playwright 代码。这既能提高成功率，也能保证业务语义的一致。
- **保留成功的测试脚本为资产**：Agent 最终通过的测试脚本直接存入仓库，作为标准 E2E 测试用例。你可以用另一个定时触发的 Agent 定期重跑历史生成的脚本，并在失败时自动申请修复 PR，形成“生成—维护”的闭环。
- **结构化输出测试报告**：在 Agent 操作结束时，要求其输出一份 JSON 报告，包含测试步骤、通过状态、失败截图链接、建议修复。方便集成到 CI 通知里。
- **利用 Agent 记忆**：在 OpenClaw 中为 Agent 配置持久化记忆，记录某项目常用选择器、页面结构特点，下次生成测试时可以直接复用，大幅降低重复探索的成本。

## 总结

通过 Agent 协作实现 E2E 测试自动编写和维护，并不是要替代测试工程师，而是把“写测试代码”这种机械劳动变成 Agent 可以迭代完成的工作。你只需把注意力放在“应该测什么”，并让 Agent 站在 MCP 提供的工具链上，像人一样观察页面、尝试、修复。

目前这套流程在登录、表单、权限跳转等典型场景下已经比较稳定。更具挑战性的流程（多标签页协同、跨域、iframe）仍然需要持续打磨工具链和提示策略，但这正是 OpenClaw 社区值得投入的方向——当工具接得足够好，Agent 的上限会远比我们想象得高。
