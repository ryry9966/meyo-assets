## 背景：E2E 测试为何总在“修脚本”

端到端测试（E2E）是回归效率的底线，也是自动化负债的重灾区。常见困境：

- **手工用例转代码成本高**：一个登录流程可能要写 30 行，反复调试选择器、等待策略。
- **AI 单次生成不可靠**：即使让 LLM 直接产出一份 Playwright 脚本，也容易因为动态 DOM、异步渲染或页面状态错误而直接挂掉，且修复成本接近重写。
- **跨页面流程脆弱**：购物车→结算→支付这类跨页面场景，状态依赖强，单一 agent 很容易“看着像对，一跑就崩”。

过去一年，社区围绕 AI 辅助测试做了不少尝试。真正让脚本稳定可用的，不是更强的模型，而是**让多个专精 Agent 协作**，并引入人的判断节点。

本文分享基于 OpenClaw 生态，用 Agent + Playwright MCP 搭建 E2E 生成管线的一次实践。不吹“全自动”，只讲能落地的工程化思路。

## 问题拆解：哪些事情单 Agent 做不好

把“写一份测试脚本”拆开，会看到三类差异很大的任务：

1. **页面探索与状态理解**：需要实际打开浏览器、触发交互、观察 DOM 变化和网络请求。这要求 Agent 能实时获取页面快照，而非仅凭静态 HTML 片段推理。
2. **测试逻辑生成**：从自然语言需求（例如“验证商品加入购物车后总价正确”）转换成操作序列和断言，涉及对业务语义的判断，容易缺漏边界条件。
3. **执行与自修复**：当脚本失败时，判断是页面改动导致选择器失效，还是环境问题（如数据过期），再决定如何修。

单一 Agent 夹带这三种能力，往往会顾此失彼。例如让它边探索边写用例，探索过程会让上下文膨胀，生成的代码里混杂大量无关选择器；而让它只管写不加执行反馈，则“幻觉式断言”几乎不可避免。

因此我们引入了三个协作角色，通过 OpenClaw 的任务链串起来。

## 做法：三 Agent 协作管线

协作流程如图所示（见封面图）。核心工具链是基于 OpenClaw 的 Agent 编排 + Playwright MCP 服务器，MCP 将浏览器操作抽象为标准化工具（navigate、click、screenshot、get_dom 等），Agent 可直接调用。

### Agent A：浏览器探索员
**职责**：理解目标页面的交互结构和关键状态变化。

- 接收任务描述，如：“从首页登录，搜索‘蓝牙耳机’，进入商品详情页”。
- 通过 Playwright 逐步执行操作，每一步都获取简化后的 DOM 快照（过滤 script/style，仅保留可交互元素和 data-testid）。
- 输出**结构化的交互路径**，包含每一步的元素特征（优先 data-testid、文本内容、ARIA 角色）、触发后出现的可观察状态（如元素可见性、URL 变化、加载完成标志），以及可能的等待条件。

这一步禁止 Agent A 写任何断言，只做观察和记录。因为一旦让它同时考虑“验证什么”，就会漏掉关键状态，让后续测试生成失之毫厘。

### Agent B：用例生成员
**职责**：依据探索记录和业务验收条件，生成完整的测试脚本与断言。

- 输入：Agent A 产出的交互路径 + 人类给出的验收条件（例如“购物车图标数字变为 1，总价显示 99 元”）。
- 利用 LLM 将交互路径转为代码骨架，然后**只在骨架中插入具体断言**。提示词要求逐条引用观察状态，并检查页面文本节点、元素属性或 API 响应载荷。
- 输出标准的 Playwright 测试文件，包含明确的 `expect` 语句和合理的超时配置。

这里的关键是“隔离创造力”：让 Agent B 只负责组装与验证，不重新探索，从而避免凭空发明选择器。

### Agent C：执行与自修复员
**职责**：运行生成的脚本，在失败时尝试受限修复，并将无法修复的问题标记为人工介入。

- 执行脚本，如果某一步失败，Agent C 会重新打开页面，定位失败步骤，做有限的策略调整：
  - 优先尝试替代选择器（如改用 text= 或 role=），但仅限于 playbook 内预先约定的后备方案；
  - 如果页面出现意外弹窗或加载延迟，插入智能等待（如 `waitForLoadState('networkidle')` 或轮询特定元素）；
- 修复后的脚本如果想合入代码库，必须人工 review diff。我们不允许 Agent 自动将其标为“通过”，只输出修复建议和差异。

通过这种明确的职责划分，每次执行后都可以获得两类产物：可直接保留的稳定用例，以及需要人工介入的“问题单”。

## 踩坑点与避坑建议

### 1. 选择器脆弱性依然是大头
哪怕用了 MCP 获取简化 DOM，Agent A 有时还是会倾向于 `div:nth-child(3) > span` 这类脆弱选择器。我们的约束是：**优先输出 data-testid，缺省则用文本匹配，再缺省用 ARIA 角色**。这就要求被测应用有意识地补充 data-testid 属性，不依赖 UI 框架的自动生成类名。

### 2. 跨页面上下文丢失
Agent A 探索过程中可能会变更页面（如从列表跳转到详情），Agent B 在生成代码时需要理解页面上下文切换。如果 Agent A 直接给出整条路径，Agent B 容易生成一个巨大的测试函数，难以维护。更好的做法是让 Agent A 把跨页面交互拆成子步骤，每个子步骤标注进出页面 URL，Agent B 据此生成多个 `test.step` 或独立的测试用例。

### 3. 断言过于模糊或过于死板
Agent B 容易生成“页面包含 99”这样的弱断言，或“innerText === '¥99.00'”这样因格式变化而爆炸的硬断言。实际中，我们会在验收条件里要求校验数值范围或正则，比如“总价大于 0 且小于 10000”，并将这些约束写进提示词模板。

### 4. 维护期的人类信任问题
同事会问：“AI 写的测试，坏了谁修？” 所以我们把 Agent 生成的所有用例都放在独立目录，标记 `@ai-generated`，CI 中同等执行，但只有经过人工 review 合并到主干后才成为回归卡点。这样可以积累信任，同时不阻塞迭代。

## 可复用建议

- **建立标准化的交互描述 schema**：让 Agent A 输出固定 JSON 格式，包含 step、selector、actions、observedState、waitCondition 等字段，减少解析偏差。
- **将 Playwright MCP 包装成“受控工具”**：比如禁止页面随意跳转到外部域，限制截图频率，防止 Agent 把 token 浪费在大量 base64 图像上。
- **人工验收条件模板化**：让产品/测试提供“Given-When-Then”自然语言，Agent 解析后填充到代码模板，保持用例结构一致。
- **构建修复回放库**：把 Agent C 的每一次修复记录成补丁，定期清洗成通用修复规则，逐步减少人工介入。

## 总结

目前这套三 Agent 协作方案在我们内部的项目上，新页面 E2E 用例的生成时间从 2 小时/条缩短到约 20 分钟（含人工 review）。不过，它仍然不能替代测试工程师的分析能力——Agent 擅长处理可枚举的交互和明确的状态，但对“这个流程是否合理”没有判断力。

如果你也在用 OpenClaw 做类似尝试，建议从一个简单的单页面流程开始，先跑通探索→生成→执行的闭环，逐步引入自修复。等三个 Agent 的职责边界清晰了，再扩展到多页面场景，收益会更明显。
