## 背景

在 OpenClaw 这类自动化编排工具里，工作流或 Agent 经常需要调用外部 API、写入数据库、发送通知。这些操作很容易被重试——可能是网络抖动触发了重试策略，也可能是上游消息队列重复投递，甚至是手动补数据时不小心跑了两次同样的脚本。

如果任务不具备**幂等性**，重复执行会造成脏数据：重复扣款、重复创建资源、重复发送消息。幂等性就是“无论执行多少次，最终结果和执行一次完全一致”的保证。对于自动化系统来说，它不是锦上添花，而是最基本的工程底线。

## 问题：非幂等任务会怎样

假设有一段 OpenClaw 脚本，用途是“收到用户注册事件后，在数据库创建对应账户，并调用支付平台开通试用”。如果消息被消费了两次，又没有做幂等控制，就会发生：

- 第二个账户创建失败（唯一键冲突还好），但可能被异常处理吞掉，导致部分逻辑跳过；
- 支付平台接口被调了两次，如果该平台未做幂等，用户会被重复扣费或创建两条订阅；
- 状态记录变得混乱，后续流程无法正确执行。

这类问题往往不会立即暴露，几个月后才被财务或者用户投诉发现，排查成本非常高。

## 做法：如何让操作幂等

以“根据业务编号创建用户”这个典型操作为例，场景是 OpenClaw 触发的 PostgreSQL 写入。

### 1. 确定幂等键
幂等键必须是**操作自身的自然唯一标识**，通常来自上游业务系统，比如：

- 用户注册事件中的 `event_id` 或 `user_id`
- 订单创建请求中的 `order_no`
- 支付回调的 `transaction_id`

绝不能用随机生成的值（如 `uuid4()`）、时间戳或自增 ID 作为幂等键，因为每次调用都会产生新值，失去幂等意义。

### 2. 利用数据库唯一约束（推荐）
最可靠的幂等实现依赖数据库的强一致性。以创建用户为例：

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    external_user_id VARCHAR(128) NOT NULL,
    name TEXT,
    created_at TIMESTAMPTZ DEFAULT now(),
    CONSTRAINT uq_external_user_id UNIQUE (external_user_id)
);
```

在 OpenClaw 的任务函数中，可以直接执行：

```python
def create_user_if_not_exists(cursor, external_id, name):
    cursor.execute("""
        INSERT INTO users (external_user_id, name)
        VALUES (%s, %s)
        ON CONFLICT (external_user_id) DO NOTHING
    """, (external_id, name))
```

`ON CONFLICT DO NOTHING` 保证重复执行时不会抛异常，也不会产生重复行。如果需要返回已有记录，可以改用 `DO UPDATE SET ... RETURNING`，但要注意**不要修改业务数据**，只更新时间戳等非关键字段，或者仅返回已有 ID。

### 3. 对外部 API 的重试防护
如果 OpenClaw 调用第三方服务，且该服务自身不支持幂等，可以在调用前插入一条“请求记录”，以请求唯一键做数据库唯一约束，状态流转为 `PENDING -> SUCCESS/FAILED`。伪代码：

```python
def call_payment_api(request_id, user_id):
    # 插入请求记录，唯一约束保证只插一次
    insert_request(request_id, status='PENDING')
    try:
        # 实际调用
        resp = pay_api.create_trial(user_id)
        update_request(request_id, status='SUCCESS')
        return resp
    except Exception:
        update_request(request_id, status='FAILED')
        # 可以留待后续重试，但下次重试会先检查状态
        raise
```

后续重试时，先查询 `request_id` 的状态，如果是 `SUCCESS` 就直接返回之前的结果（可能需要缓存），`FAILED` 则可以再次调用。这本质上是“本地状态表 + 幂等键”的模式。

## 踩坑点

1. **幂等键选择太宽泛**  
   比如用“用户名”做幂等，但业务允许用户改名，后续再创建同名用户就会被错误拦截。幂等键必须是不可变且全局唯一的。

2. **并发请求导致重复**  
   即便使用唯一约束，两个并发请求同时走到 `INSERT`，第一个成功，第二个会报唯一冲突。如果后续代码没有正确处理冲突（例如不做 `ON CONFLICT` 而直接捕获异常），可能仍然会执行副作用逻辑。所以应在数据库层面就完成幂等判断，并将副作用操作放在事务内编排。

3. **外部服务不能回滚**  
   典型场景：数据库写入成功，但调用支付 API 失败。如果采用“本地事务 + 外部 API”模式，一旦支付成功而后续步骤失败，需要补偿操作。此时幂等键可以帮助识别哪些支付已经生效，避免重复补偿。工程上尽量让外部接口支持幂等，或使用转账单号等自然键。

4. **误用 `UPSERT` 更新关键字段**  
   有些人会用 `ON CONFLICT DO UPDATE SET amount = amount + 1` 来处理重复请求，这会把幂等操作变成累加操作，反而放大了问题。幂等的核心是“结果不变”，而不是“操作重复执行无妨”。

## 可复用建议

- **封装通用幂等装饰器**：在 OpenClaw 的 Python 执行器中，可以编写一个装饰器，基于请求 ID 和 Redis `SETNX` 实现轻量幂等（但要评估 Redis 断连时的降级策略）。
- **坚持“数据库唯一约束是最后防线”**：不管上层做了多少检查，最终写入处必须用唯一索引兜底。这是防御编程的基本思路。
- **状态机 + 幂等键**：对于长流程任务，使用严格的状态机（如 `INIT -> PROCESSING -> DONE`），避免逆向跳转，配合幂等键防止状态被重复推进。
- **测试：刻意重放**：在 CI 中构建重放测试，用相同参数反复调用自动化任务，检查是否产生重复数据或异常。

## 总结

自动化任务的幂等性不是靠“感觉已经去重”实现的，而是一整套以**业务唯一键**为核心，数据库唯一约束为保障的工程策略。在 OpenClaw 这类编排工具中，只要我们养成“先幂等，再执行”的习惯，重试就不再是隐患，反而可以放心地用它来增强系统鲁棒性。下次写任务前，不妨先问自己一句：如果这段脚本被一模一样的参数调了两次，世界会不会变坏？
