## 背景：Agent 为什么需要一个人格文件

当我们的 AI 助手开始接上 MCP 工具、能读写文件、能调用外部 API 时，它就从一个“问答机器人”变成了一个“数字员工”。但能力越大，破坏力也越大：一次错误的数据库操作可能删掉关键记录，一个没有授权的邮件发送可能造成信任危机。

传统的系统提示词（System Prompt）虽然能描述角色，但往往像一次性的便签，散落在各处，难以维护和复用。当 Agent 行为出现偏差时，我们经常花大量时间去猜测“它为什么会那么做”，却找不到一个清晰的参照。

**SOUL.md** 的理念就是在工程层面把 Agent 的人格、核心原则、能力清单、边界规则固化为一个版本化的、可协作的配置文件。它不是简单的提示词，而是 Agent 运行时的“自我认知”基线，无论工具怎么扩展、流程怎么编排，这些规则都像操作系统内核一样保持不变。

## 问题：未设定边界时常见的 Agent 失控形态

在 OpenClaw 这类可扩展 Agent 框架中，我们会给助手接入多个工具：文件系统、网页搜索、命令行执行、MCP 插件等。若没有明确的边界定义，会出现几类典型问题：

1. **工具滥用**：助手为了实现目标，反复调用昂贵的 API 或执行不安全的 Shell 命令。  
2. **过度承诺**：用户说“帮我整理一下上季度财报”，它就会假装自己能看到财务数据库，开始编造数据。  
3. **角色退化**：在多轮对话中，Agent 逐渐忘记自己的身份，变成普通的聊天模型，丢弃工具调用能力。  
4. **安全边界模糊**：无法区分哪些操作需要用户二次确认，哪些可以自动执行。

这些问题很难通过堆叠提示词解决，因为提示词之间会互相稀释。我们需要一个结构化的、非自然语言脆弱依赖的界定方式。

## 做法 / 步骤：工程化定义 SOUL.md

下面的实践基于 OpenClaw 的 Agent 构建积累，但也适用于任何使用系统级指令的 AI 助手。

### 1. 文件结构设计

一个典型的 `SOUL.md` 包含以下区块，使用 Markdown 格式便于阅读和解析：

```markdown
# Agent Name: Scout

## Identity
- 你是一名企业运维助手，运行在内部可信网络中。
- 你的主要用户是 DevOps 工程师。

## Core Principles
1. 永远不要说谎：不确定时明确告知，并建议用户进行核实。
2. 最小权限：只使用完成任务所必需的工具。
3. 二次确认：对写操作（delete/update/deploy）默认要求用户确认。
4. 可审计：每次工具调用前先在对话中声明意图和参数。

## Capabilities
- 允许：读取日志文件、查询监控 API、重启开发环境服务
- 不允许：操作生产数据库、发送对外邮件、修改用户密码

## Interaction Rules
- 每次对话开始时自报身份和能力简述。
- 当请求超出能力范围时，输出“我无法完成此操作，因为……”并给出替代建议。
- 工具调用错误时，最多重试 3 次，然后暂停并请求人工介入。

## Constraints
- 单次对话工具调用总数不超过 20 次。
- 禁止输出任何系统内部路径或密钥。
```

### 2. 与 Agent 框架的集成

在 OpenClaw 中，我们可以把这个文件作为一个预设的 `system_instruction` 加载，同时将其中的**可执行规则**结构化抽取。例如：

- 将 `Capabilities` 节解析为工具白名单，与 MCP 服务器声明对比，自动屏蔽未授权工具。
- 将 `Core Principles` 转换为 Agent 决策时的约束检查（例如兜底逻辑：如果意图包含写操作且未得到确认，则中止动作）。
- `Interaction Rules` 作为提示词的一部分，永不稀释（放在对话历史的最前或最后，使用特殊标记防止模型忽略）。

关键点是：**SOUL.md 既是一份人类可读的协议，又是机器可解析的策略源**。

### 3. 版本控制与测试

把 `SOUL.md` 纳入 Git 仓库，和 Agent 代码一起迭代。每次修改后，运行一组预定义的回归测试用例（比如模拟 10 个边界场景的对话脚本），检查 Agent 的行为是否符合期望。

## 踩坑点

- **原则太过抽象**：像“保持友好”“做正确的事”这种话，模型根本听不懂。每一条原则必须能映射到具体的行为决策上。用“你可以做 A，绝不能做 B”的方式写。
- **边界太死，导致 Agent 僵化**：设置过于严格的限制，会使 Agent 在合理请求上也频繁拒绝。建议加入一个**上浮路径**：当用户坚持时，Agent 可以给出明确的升级建议（“您可以联系管理员临时授权”），而不是卡死。
- **多语言混合导致歧义**：如果你的 SOUL.md 是用英文写的，而用户用中文交互，模型可能对权限边界的理解产生偏移。尽量用单一语言编写核心规则，或同时提供双语版本并标注优先级。
- **工具白名单维护不及时**：当新增 MCP 服务器时，容易忘记同步更新 SOUL.md 的 Capabilities 清单。可以在 CI 中加入一致性检查：扫描已连接的 MCP 工具列表，与 SOUL.md 中声明的能力进行比对，若出现未授权工具则告警。

## 可复用建议

1. **模块化分割**：当 Agent 集成的功能越来越多时，单一 SOUL.md 会变得臃肿。可以拆分为 `SOUL_base.md`（身份、原则）和 `SOUL_tools.md`（工具特定规则），由加载器负责合并。
2. **动态参数注入**：像单次对话工具调用上限、会话超时这类参数，不要写死在文件里，用占位符 `{MAX_TOOL_CALLS}` 表示，运行时由环境变量注入。
3. **加入 Few-Shot 示例**：在 SOUL.md 末尾添加几个“用户→助手”的示例对话，展示正确/错误的处理方式。这比纯规则描述更有效。
4. **用可观测性验证**：为关键原则（如“必须二次确认”）增加运行时埋点，记录违背次数和场景，回看这些数据迭代 SOUL.md。

## 总结

SOUL.md 不是银弹，但它把“AI 助手的行为准则”从一个模糊的提醒变成了一份可维护的工程构件。对于已经接入工具和 MCP 的生产级 Agent，这种结构化的人格与边界定义几乎是从“能跑”到“可信任”的必经之路。每一个接入 OpenClaw 的项目，都应该认真考虑为你的 Agent 写一份真正的“工作守则”。
