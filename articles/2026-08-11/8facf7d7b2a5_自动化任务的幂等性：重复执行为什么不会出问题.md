# 自动化任务的幂等性：重复执行为什么不会出问题

## 背景：重试是把双刃剑

在 OpenClaw、Agent 和 MCP 插件的日常运行中，任务是围绕“触发—执行—产出”这条链路跑的。无论是一次定时抓取、一条 Webhook 回调，还是内部 Agent 之间的消息传递，执行环境天然不可靠：网络抖动、第三方 API 超时、模型推理失败、下游服务限流，都可能让一次任务在中途折断。

常见的应对策略是**重试**。但重试一旦缺乏约束，很快就会变成重复执行——同一条消息被处理两次，同一个订单被重复创建，同一个通知被重复推送。轻则数据冗余，重则造成资金或状态错乱。要让重试安全落地，任务必须具备**幂等性**。

## 问题：没有幂等性会发生什么？

用一个真实的自动化场景举例：我们有一个 MCP 插件，监听 OpenClaw 中消息通道的“新消息”事件，一旦收到带特定标签的消息，就自动调用外部 CRM 系统创建客户工单。

- 场景 A：消息到达后，插件收到事件，开始创建工单。CRM 接口响应慢，HTTP 库触发超时重试。结果重试导致两次创建请求都被 CRM 成功接收，最终**同一客户生成两条重复工单**。
- 场景 B：Agent 在执行多步任务时，某个步骤因为策略重启被重新触发，之前已经发送过的通知又发了一遍，工作群里**收到两条一模一样的消息**。

本质原因在于：**操作不是幂等的**。重复执行产生了额外的副作用。而幂等任务的定义是：**同一个操作，执行一次和执行多次，结果相同且副作用只会发生一次。**

## 做法与步骤：如何让自动化任务幂等化

### 1. 给每次任务一个唯一“身份证”

确保每次业务的触发都有一个全局唯一的标识符，这可以是上游消息的 message_id、事件 ID、请求的幂等键（Idempotency-Key）。不要让任务去猜测唯一性，而要让它变成任务输入的一部分。

```json
{
  "idempotency_key": "evt_20250322_order_1001",
  "payload": { ... }
}
```

### 2. 用状态记录“是否已成功执行”

在任务逻辑的入口处，根据唯一键查询执行状态。如果已经标记为成功，直接返回缓存的结果或跳过执行。典型模式是数据库中的一张“幂等记录表”：

```sql
CREATE TABLE idempotency_records (
    idempotency_key VARCHAR(255) PRIMARY KEY,
    status ENUM('processing','completed','failed'),
    result TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

任务执行时的流程：
1. 尝试插入一条 status='processing' 的记录（利用主键防重）。
2. 如果插入失败，说明该 key 已经存在，检查状态：completed → 直接返回 result；processing → 等待或抛出正在处理；failed → 根据策略决定是否重试。
3. 业务执行成功后，更新状态为 completed 并写入 result。

### 3. 将业务操作本身设计成幂等的

即使没有中间记录，操作本身也应尽量支持幂等性：

- **资源创建类 API**：优先使用 PUT 而非 POST，或者传入 client-side id，让服务端利用唯一键保证创建一次。
- **数据库写入**：使用 `INSERT ... ON DUPLICATE KEY UPDATE`，或唯一索引约束防止重复数据。
- **消息去重**：利用消息队列的 message deduplication，或 consumer 端在本地维护“最近已处理 ID”的滑动窗口。

### 4. 在 OpenClaw 和 MCP 插件中的落地

以 OpenClaw 插件为例，可以抽象一个 `IdempotentAction` 函数装饰器：

```python
@idempotent(key=lambda ctx: ctx.message.id)
def handle_message(ctx):
    # 业务逻辑
    return result
```

装饰器内部：
- 通过 `ctx.message.id` 生成幂等键。
- 在 Redis 中执行 `SET key value NX EX 3600`（如果没有 Redis，则用数据库行锁）。
- 如果 SET 失败，说明已经在处理或已处理过，直接返回旧值或丢弃。
- 执行成功后更新值。

对于 MCP Tool 调用，可以在调用外部服务前检查“请求去重缓存”，并将幂等键传递给第三方服务，如果第三方也支持幂等，那就是双重保障。

## 踩坑点

1. **唯一键选错了**  
   用时间戳或随机 UUID 作为幂等键是无效的——每次重试都会生成新键。唯一键必须来自上游业务事件或请求本身的固有属性（如事件 ID、消息 ID、订单号）。

2. **“处理中”状态未处理**  
   当并发重复请求同时到达，两者都会看到 idempotency_key 不存在，然后都去执行业务逻辑。解决方法：在插入幂等记录时使用数据库唯一约束或 `INSERT ... ON DUPLICATE`，让只有一个请求能成功插入“处理中”，其他请求重试等待或快速失败。

3. **只记录状态不记录结果**  
   如果任务成功但未持久化结果，后续重复调用会因为找不到结果而再次执行。幂等记录的 completed 状态必须携带上一次成功的结果，才能做到“直接返回”。

4. **忽略资源清理与补偿逻辑**  
   某些业务前半部分成功，后半部分失败，即使状态标记为 failed，也可能留下脏数据。需要配合事务或补偿操作（如 Saga 模式），确保幂等重试后达到最终一致性。

5. **过度依赖本地缓存**  
   在多实例部署的 Agent 或插件中，用内存做去重毫无意义，重复请求会落在不同节点。必须依赖集中式存储（Redis、DB、分布式锁）。

## 可复用建议

- **抽象统一的幂等执行器**：在团队内部提供一个轻量级库或内部服务，只需传入 idempotency_key 和要执行的函数，即可获得幂等保护。避免每个插件都自己实现一遍。
- **优先使用业务自然键**：尽量用上游系统提供的不可变 ID，减少额外的映射和存储。
- **为外部 API 调用预留幂等键字段**：封装 HTTP 客户端时，约定统一参数，即使是简单请求也能带 idempotency_key。
- **监控执行重复率**：设置告警，当短时间内大量 idempotency_key 出现重复执行尝试时，说明依赖方可能在疯狂重试，需要排查上游。
- **定期清理幂等记录**：记录表会随时间膨胀，按 TTL 或定时任务清理已完成且超出业务窗口的记录。

## 总结

自动化任务的幂等性不是锦上添花，而是工程可靠性的底线。当任务因为各种原因被重复触发时，只要幂等键选对、状态持久化到位、业务操作本身尽量无副作用，重复执行就不会翻车。

在 OpenClaw 和 MCP 的插件生态里，任务边界往往跨越多个服务，幂等做在任务入口一处，收益会辐射到整条链路。把幂等能力沉淀为可复用的中间件，比每次出问题后打补丁要可靠得多。**宁可让任务因为幂等检查而跳过，也绝不让它因为无保护的重试而制造混乱。**
