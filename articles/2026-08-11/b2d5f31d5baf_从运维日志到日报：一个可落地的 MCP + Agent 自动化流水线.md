## 为什么需要自动化日报

过去半年，我们的基础设施监控团队一直在处理一个“老但烦”的问题：每天早晨，值班同事需要从多个系统（Kubernetes event、CloudWatch、Prometheus alert、部署变更记录）中捞出过去 24 小时的关键事件，用自然语言写成日报，发到工单和即时通讯群。这个过程大约占用 40–60 分钟，且容易遗漏低频但严重的异常（比如凌晨 3 点的一个 OOMKill，如果人工扫日志时没留意就跳过了）。

我们尝试过几个现成方案：ELK scheduled export、Grafana 的 PDF 报告、若干个 script + cron 推送。问题在于这些工具输出的是图表或原始表格，不是结构化的、可按需定制的自然语言总结，也无法做“聚合 + 归因 + 行动项”这种推理。当团队引入 OpenClaw 作为 Agent 编排底座后，我们重新设计了这条流水线，利用 MCP 统一数据源，让 Agent 实现从原始日志到结构化报告的自动化生成，目前已经稳定运行了三个月。

## 要解决的核心问题

一个日报流水线不仅仅是“定时发一堆日志”。实际工程化的时候，需要解三个问题：

1. **多源异构数据聚合**：日志分布在多个系统，格式不同，部分系统只有 HTTP API，部分需要 kubectl 或 SDK 访问。
2. **事件筛选与噪声压缩**：一天可能产生数万条日志，但真正值得写进日报的可能只有几十条。Agent 需要根据规则和上下文压缩、去重，而不是无脑全量喂给 LLM。
3. **结构化输出与人工可控性**：日报需要固定的段落（概述、P0/P1 事件、变更记录、待处理告警、行动项），而非一大段自由文本。同时人需要能调整规则，甚至临时添加备注。

## 流水线设计与实现

我们的流水线由三个模块组成：MCP 数据源 → Agent 处理引擎 → 输出适配器，全部在 OpenClaw 中通过 pipeline 编排，时间触发由内置 cron 插件完成。

### MCP 层：标准化数据供给

我们为每个数据源写了 MCP server（或复用社区已有的，如 `mcp-server-k8s`、`mcp-server-prometheus`）：

- **K8s events**：通过 `mcp-server-k8s` 暴露 `list_events` tool，按 namespace 和时间范围查询，返回结构化 JSON。
- **CloudWatch logs**：自己封装了一个轻量 MCP server，使用 AWS SDK 封装 `filter_log_events`，加入模式过滤（过滤掉 DEBUG/INFO 的一般日志，只保留 ERROR、WARN 及自定义 pattern）。
- **Prometheus alert**：直接用 Prometheus MCP 拿 firing/resolved alerts，并附带 alertname、severity、description。
- **部署变更**：从内部 CI/CD 平台的 API 拉取，输出 JSON。

每一个 MCP tool 输入参数统一为 `start_time`、`end_time`，返回列表。这样 Agent 在下游调度时可以统一调用，不必关注数据源细节。

### Agent 处理引擎：分段压缩 + 结构化模板

这是最关键的环节。直接把原始数据扔给 LLM 会严重超 token，且输出不稳定。我们采用了两步法：

1. **数据预处理与分段**  
   Agent 依次调用各 MCP tool，获取原始列表。然后按事件类型（告警、错误日志、变更）分组，对每组做本地规则压缩：相同错误消息按计数归并，低严重度告警在无异常上下文时丢弃，K8s event 中 Normal 类型仅保留与调度/重启相关的。这一步完全在 Agent 的 Tool 编排中完成，不消耗 LLM token。

2. **逐段总结 + 组装**  
   压缩后的数据送入 LLM，但不是一次给所有。我们为每个段落编写了独立的 prompt 模板（OpenClaw 中的 template 节点）：
   - 概述：基于所有压缩数据，生成 3–5 句整体评价。
   - P0/P1 事件：要求每个事件包含时间、对象、现象、初步原因、是否自动恢复。
   - 变更记录：列出变更标题、发起人、结果状态。
   - 待处理告警：列出未自动恢复的告警，附带建议。
   - 行动项：如果出现特定 pattern（如反复重启），建议拉起巡检。

   每个模板都指定输出为纯文本，不要求 JSON，因为日报最终是给人看的。但为了让输出稳定，我们在每个模板中给出了 1–2 个 few-shot 示例，并限制格式。

   最终 Agent 将各段拼接为完整日报。

### 输出适配器

生成日报后，同时推送到飞书/钉钉（通过 plugin 发送消息）和内部 wiki 页面（通过 HTTP API）。为了便于人工补充，日报尾部附带一句“若有补充，请编辑 wiki”，并给出链接。这样既自动化，又保留人工修订的入口。

## 踩过的坑

1. **LLM 幻觉导致“编造事件”**  
   早期我们没有做好分段压缩，直接把几千条日志摘要给 LLM，它会“创造性”合并不同事件，甚至编造一个不存在的“磁盘慢 I/O 告警”。解决方案是先压缩、后分段落，严格禁止 LLM 推断未在原始数据中出现的结论。我们还在 prompt 中明确：“If no related evidence, do not fabricate.”

2. **Token 消耗与成本**  
   全量日志不经处理扔给 LLM，单次生成消耗 30k+ token。通过本地规则压缩和分段调用，现在单次生成控制在 5k token 以内，成本大幅下降。另外，如果某天日志特别多，我们的规则会主动降级，仅生成 P0 事件摘要，防止超限。

3. **时区和时间窗口偏差**  
   cron 触发时间和各数据源的时区不一致，导致部分事件漏抓或重复。后来统一要求所有 MCP tool 接受带时区的 ISO8601 参数，Agent 调度时明确传入昨天 00:00-23:59（服务所在地时区），避免了“8 小时偏移”问题。

4. **输出格式不稳定**  
   即使有 few-shot，有时 LLM 仍会输出不一致的标题层级。最终我们放弃了让 LLM 生成 Markdown 标题，而是由输出适配器根据段落标识强制添加固定标题，LLM 只负责段落内容。

## 可复用建议

如果你也想在自己的环境里落地类似的东西，以下几点是我们的实际经验：

- **优先用 MCP 标准化数据出口**：不要为每个数据源写自定义 connector。用 MCP 可以让你随时替换数据源，Agent 调用方式不变。
- **不要在 LLM 里做数据清洗**：预处理、过滤、去重、压缩在 tool 层完成，LLM 只负责“根据压缩事实写总结”。这既是成本优化，也是防幻觉的关键。
- **设计模板化的日报结构**：定义固定段落，每个段落独立 prompt，方便调优和修改。如果某段不需要了，直接去掉对应模板节点即可。
- **保留人工入口**：即使是全自动流水线，也要允许人工补充和微调，否则遇到模糊事件，系统可能硬写一个不太对的结论。
- **监控输出质量**：我们另外加了一个“日报质量检查” Agent，它会定期抽样检查日报内容与原始告警是否一致，若发现可能幻觉，自动告警到值班群。虽然加重了整体流程，但提升了可信度。

## 总结

从原始日志到结构化日报，本质上是一个“信息压缩 + 语义重组”的过程。用 MCP 解决数据源异构问题，用 Agent 编排实现分段总结、模板化输出，能让这条路走得比较稳。目前我们的日报每天早上 8:30 自动发出，值班同事只需花 3 分钟检查并补充个别备注，人工参与度从 90% 降到了 10% 左右。

这并不是一个宏大方案，只是一套用社区现成组件拼出来的实用流水线。如果你想尝试，可以从一个数据源开始，跑通 MCP → Agent → 输出的最小闭环，再逐步添加更多数据源和段落。
