## 背景

团队日常站会、周报需要汇总当天的工作进展。信息散落在 Git 提交记录、Jira 任务状态、Slack 技术讨论和监控告警里，手动拼接这些碎片日志至少花费每人 15–20 分钟。更麻烦的是，不同成员整理习惯不同，输出的日报格式五花八门，管理者难以快速比对。

我们尝试过用脚本抓取 Jira 接口生成固定模板，但一遇到自然语言描述的需求变更、Slack 里的临时决策，脚本就无能为力。直到在 OpenClaw 社区看到 Agent 通过 MCP 工具与外部系统交互的模式，我们开始思考：能否让 Agent 扮演“日报秘书”的角色，自主收集多源日志，理解上下文，生成统一的结构化日报？

## 问题拆解

这个流水线要解决三个核心问题：

1. **异构数据源的统一访问**：Git 用命令行，Jira 用 REST API，Slack 用 Web API，监控系统用 Prometheus。Agent 不能硬编码每种接入方式。
2. **非结构化信息的提取与摘要**：Slack 里的技术讨论可能长达上百条消息，需要提炼出决策结论和待办事项，而不是全文塞进日报。
3. **稳定的输出格式与高质量的汇总**：日报必须包含“本日完成”、“遇到的问题”、“明日计划”等固定板块，且不能出现幻觉，虚构任务。

## 做法：构建 Agent + MCP 流水线

我们使用 OpenClaw 作为 Agent 宿主，通过 MCP（Model Context Protocol）将各个数据源封装为标准化工具，让 Agent 在规划-执行循环中调用。整体步骤：

### 1. 实现数据源 MCP Servers

为每个数据源编写 MCP Server，暴露少量高内聚工具：

- `git-log` 工具：接受 `--since` / `--until` 参数，返回指定时间范围的 commit 摘要列表。
- `jira-issues` 工具：接受 JQL 过滤条件，返回当天更新的 Issue 标题、状态、负责人。
- `slack-channel` 工具：接受频道 ID 和时间窗口，返回消息列表（已做去敏和去重）。
- `monitor-alerts` 工具：查询当天触发的告警及处理状态。

这些 Server 均使用社区提供的 MCP SDK（如 Python `mcp` 包）快速构建，各自独立部署，通过 STDIO 或 HTTP 与 OpenClaw 通信。

### 2. 设计日报生成 Prompt 与模板

在 OpenClaw 中我们新建一个 Skill，命名为 `daily-report`，Prompt 明确约束：

- 角色：你是团队日报助手，只基于工具返回的真实数据生成日报，不得编造任何信息。
- 工作流程：先调用所有必要工具获取当日数据，再按“完成事项”、“讨论决策”、“风险与阻塞”、“明日计划”四板块汇总。对 Slack 讨论必须提炼摘要，每条摘要不超过 40 字。
- 模板：使用固定 Markdown 结构，最后附上数据源摘要（如“今日 6 次 commit，关闭 3 个 Jira 任务”）。

### 3. Agent 执行编排

OpenClaw 采用 plan-and-execute 架构。对于日报任务，规划阶段生成固定步骤：

1. 调用 `git-log` 获取当日提交
2. 调用 `jira-issues` 获取更新项
3. 调用 `slack-channel` 获取指定技术频道消息
4. 调用 `monitor-alerts` 获取告警
5. 汇总信息写入日报草稿
6. 根据草稿检查是否有工具调用遗漏，必要时补调
7. 输出最终 Markdown

执行时 Agent 会并行调用无依赖的工具，减少整体耗时。实测完整一次日报生成（含数据分析）约 12–18 秒。

### 4. 定时触发与分发

我们使用 OpenClaw 的 Cron 触发器，工作日上午 9:50 自动执行 `daily-report` Skill，生成日报后通过企业微信机器人 Webhook 发送到团队群。同时将 Markdown 文件存入 Git 仓库备份，方便对比回溯。

### 5. 人工反馈闭环

日报未读代发前，配置了“审核节点”：Agent 生成草稿后暂停，等待人工在 OpenClaw 对话界面对草稿进行修改或确认，确认后再发送。这避免了一个错误的摘要影响全天的信息同步。

## 踩坑记录

- **Token 消耗失控**：刚开始我们没有限制 Slack 消息条数，一次拉取 500+ 条记录，导致上下文超限。后来改为先拉取消息梗概（仅时间戳与用户），再由 Agent 决定展开哪些线程的细节，Token 占用降低 70%。
- **时间边界问题**：有的数据源服务器时区是 UTC，Agent 使用的系统时间是北京时间，导致“当天”定义错位。统一要求所有 MCP 工具接受 ISO 格式时间参数并标明时区，避免歧义。
- **摘要遗漏关键决策**：早期 Prompt 要求“简洁”，结果把“决定将数据库连接池从 50 提升到 200”提炼成“调整了连接池”，丢失关键信息。后来在 Prompt 中增加了约束：“涉及数字、配置参数、具体人名的决策必须保留原值，不可缩减”。
- **工具异常未妥善处理**：某次 Jira 服务临时 503，Agent 直接回复“今天没有 Jira 更新”，造成日报虚假空置。改进为工具异常时返回结构化错误信息，Agent 必须在日报中显式注明“Jira 数据获取失败”，而不是静默忽略。

## 可复用建议

1. **将数据源标准化为 MCP 工具**：即使暂时不用 Agent，MCP 化的数据接口也让其他自动化脚本可查阅，降低耦合。
2. **设计可配置的日报模板**：我们在 Skill 中抽离了模板文件，不同团队只需修改板块名称和顺序，降低推广成本。
3. **保留人工审核环节**：全自动日报在信息可靠度上仍有风险，单点人工确认是成本最低的容错手段。
4. **利用 OpenClaw 的 Skill 存储为复用模块**：将整套流程打包成 `daily-report` Skill，新项目只需配置数据源连接参数即可启用。

## 总结

通过 Agent + MCP 的流水线，我们将分散在多个系统的原始日志自动转化为格式统一、内容精炼的日报，每个成员每天节省约 15 分钟整理时间，同时消除了因个人习惯差异导致的报告碎片化。更重要的是，这套机制将隐性知识（Slack 里的临时决策、监控告警的处理链）显性化记录，为团队留下了可追溯的每日快照。对于 OpenClaw 用户，此模式可以轻松扩展到周报、项目里程碑摘要等更多结构化报告场景。
