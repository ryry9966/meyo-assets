## 背景

给基于 OpenClaw 搭建的助手写系统提示时，我陷进了一个再熟悉不过的坑：角色的身份描述写在 `system-prompt.ts` 里，工具调用的限制散落在各个 MCP 工具的配置中，回复语气的要求又单独记在 Notion 里。几周后想微调一句自我介绍，不得不翻遍三个项目才改全。更糟糕的是，模型换个小版本，原本克制、务实的助手突然开始满嘴跑火车，因为它对碎片化指令的权重感知完全不一样了。

类似的问题在有多个 agent 协作或长期运行的自动化流程中会被急剧放大。SOUL.md 就是从这个混乱中生长出来的解决方案——用一个单一的 Markdown 文件集中定义 agent 的“人格”与操作边界，让提示词变得可维护、可评审、可版本化。

## 我们要解决什么

1. **行为漂移**：同一套配置在不同模型甚至同一模型的不同调用里，语气、角色、规则权重不稳定。
2. **安全边界模糊**：agent 能调用系统命令、读写文件，如果没有清晰的禁止项，一个幻觉就可能造成真实破坏。
3. **维护噩梦**：人格描述、规则、工具使用策略分散在代码、环境变量和文档里，修改时极易遗漏。
4. **团队认知不对齐**：产品、开发、安全对“这个助手该做什么、不该做什么”各有一本账，冲突不断。

## SOUL.md 的结构与加载方法

我在这几个月的实践中收敛出一套可复用的结构。一个典型的 SOUL.md 至少包含以下几个区块（用二级标题分隔）：

- **Identity**：名字、角色、背景设定、服务对象。
- **Voice**：语气（克制/温暖/专业）、句式风格、禁用词汇。
- **Principles**：不可妥协的核心原则，如“不编造事实”“不确定时必须明确说明”“安全优先”。
- **Tool Policy**：允许使用的 MCP 工具白名单，以及每个工具的触发条件、典型用例和硬性禁止场景。例如：
  - `shell_exec`：允许执行只读命令，禁止任何写操作，禁止 `rm`、`shutdown`。
  - `browser`：允许访问公开文档，但不得填写表单、不得提交任何数据。
- **Response Guidelines**：何时引用来源、何时说“我不确定”，输出格式（如必须用 Markdown 表格呈现数据）、是否需要主动披露能力边界。
- **Boundaries**：决策权限的边界，例如涉及用户文件删除、外部 API 调用、资金操作时必须二次确认，绝不代替用户做最终决策。

在 OpenClaw 里，我采用这样的加载方式：在 agent 初始化的入口文件里读取 `SOUL.md`，将其内容与少许动态变量（如当前日期、用户偏好）一起注入到 system prompt 中：

```yaml
system_prompt: |
  You are an AI assistant whose full definition is given in the following SOUL.md document.
  Treat every line as a hard constraint unless explicitly marked as a suggestion.

  ---
  {soUL_content}
  ---
  Today: {current_date}
```

用 `{soUL_content}` 占位符替换整个文件内容，避免硬代码分裂。版本化方面，把 SOUL.md 放进 git 仓库，修改时用 diff 仔细审查，配合几个固定的回归对话用例（比如：“帮我删除临时文件夹”看是否正确拒绝）作为冒烟测试。

## 踩坑记录与应对

1. **长篇大论失效**  
   最开始我把所有想得到的原则都写进去，结果超过 3000 字。模型经常忽略靠后的指令，尤其是工具调用前几乎不看 Tool Policy 的细节。后来精简到 800 字以内，每条原则一针见血，并将最关键的安全禁令放在文档最前面。

2. **与工具自带描述的冲突**  
   很多 MCP 工具的 description 会声称“可以执行任意系统命令”，但 SOUL.md 明确禁止。这让模型在推理时左右为难。我的解决办法是双重保险：一方面 SOUL.md 中写上“当工具描述与本文件冲突时，以本文件为准”；另一方面在工具调用的预处理函数中加入硬校验，如果检测到命令匹配危险模式，直接拦截并返回错误给模型，让它重新规划。

3. **语气约束过于僵硬**  
   曾要求助手“绝对专业、零幽默”，结果在报错场景下回复像台冰冷的自动售货机，用户体验极差。之后改为分层：日常交互保持专业但有温度，错误恢复时可以适当共情。关键是在 SOUL.md 中为不同场景定义差异化的 Voice 模式，而非一刀切。

4. **多 agent 场景下的边界渗透**  
   当一个 master agent 调度多个子 agent 时，如果子 agent 各自有 SOUL.md，很容易出现权限混淆。现在的做法是：master 的 SOUL.md 显式声明每个子 agent 的能力范围和转交规则，子 agent 的 SOUL.md 只保留自己特有的工具和规则，并严格遵守 master 分配的任务边界，不越权。

## 可复用建议

- **先硬后软**：安全边界（如文件删除、网络写操作）必须在代码层有硬拦截，SOUL.md 只是软约束，用于引导模型自纠和向用户解释。
- **用 YAML 头部携带元数据**：在 SOUL.md 顶部用 YAML 定义版本号、生效日期、负责任工程师，方便自动化处理。
- **动态与静态分离**：角色定义、原则是静态的，直接写在 SOUL.md 里；用户偏好、时间信息是动态的，在注入模板时填充，不要混进去。
- **持续微调而非大改**：每次只改变一两个规则，通过对话记录回顾行为变化，避免一次性改崩。
- **共享认知**：把 SOUL.md 打印出来贴到团队看板上，让产品、安全、开发都能随时对照，减少“我以为助手的规则是……”这类沟通成本。

## 总结

SOUL.md 不是银弹，它只是一份被老老实实维护的 Markdown 文件，但它把散落的提示词变成了一个有结构的、可协商的“人格与边界配置”。在工程上，它让 agent 的行为变得可调试、可审计，也让团队对助手的边界有了同一份文本的依据。

如果你也在 OpenClaw 或类似的 agent 框架里遭受提示词混乱之苦，不妨从新建一个 `SOUL.md` 开始。先定义身份和三条原则，再慢慢扩展。给 agent 一份清晰的“灵魂”文件，远比往代码里塞几十行零散的指令要靠谱。
