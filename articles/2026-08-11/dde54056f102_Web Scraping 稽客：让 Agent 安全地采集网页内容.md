# Web Scraping 稽客：让 Agent 安全地采集网页内容

## 为什么需要“稽客”

Agent 工作流中，从网页获取实时信息已经成为刚需——无论是阅读最新文档、抓取商品价格，还是聚合新闻内容。初期大家习惯于直接在 Agent 里调用 `requests` 或 `playwright`，但随着自动化深度嵌入业务，几个问题反复出现：

- **合规踩雷**：Agent 无视 `robots.txt`，爬了不该爬的路径，甚至触发法律风险。
- **IP 被控**：高频无节制抓取导致出口 IP 被目标站拉黑，影响其他正常服务。
- **内容污染**：未脱敏的抓取结果混入了跟踪脚本、恶意重定向，污染下游知识库。
- **不可审计**：谁、在何时、因为什么 prompt 触发了抓取？出了问题完全回溯不了。

这些坑并非个例。当 Agent 具备了“行动能力”后，如果没有一个坚实的安全中间层，它就是一头跑进瓷器店的公牛。我将这块中间层称为 **稽客（Audit Scraper）**——一种带有审计、预算、策略控制的网页采集网关。它不是简单封一层 API，而是让每一次抓取都变得可观测、可遏制、可追溯。

## 问题拆解：Agent 抓取的脆弱点

如果你已经给 Agent 接了搜索 API，为什么还需要额外的稽客层？因为 Agent 的 prompt 是不可预测的。用户的一句“帮我把这个页面里所有的链接都打开看看”，就可能造成级联抓取。传统做法（比如在 Agent 系统指令里加一句“不要乱爬”）效果极差，治标不治本。

核心脆弱点有三：

1. **缺乏契约式基线**：没有强制执行 `robots.txt`、`sitemap` 策略，一切依赖开发者的自觉。
2. **无成本感知**：Agent 不知道每次 HTTP 请求的真实代价（IP 信誉、服务器压力、被反爬的风险），容易过度优化。
3. **结果未净化**：抓到的 HTML 可能含 XSS 载荷、外链资源，直接送入 LLM 上下文或存储，引发安全与存储膨胀问题。

## 实操：搭建一个稽客 MCP 工具

我在最近的项目里，基于 MCP（Model Context Protocol）实现了一个轻量的稽客组件，让 Agent 只能通过它来触碰 Web。下面给出核心实现思路，可复用到任何 OpenClaw 或类似 Agent 框架中。

### 1. 策略定义层

在 MCP 工具的初始化阶段，加载一份 YAML 策略文件：

```yaml
global:
  user_agent: "AuditAgent/1.0"
  max_concurrent: 2
  default_delay_ms: 3000

policies:
  - domain: "openclaw.cn"
    allow_paths: ["/docs/*", "/blog/*"]
    deny_paths: ["/admin/*"]
    respect_robots_txt: true
    max_depth: 2
  - domain: "*"
    respect_robots_txt: true
    max_depth: 1
    max_req_per_min: 5
```

工具暴露的唯一方法 `safe_fetch(url: str)` 会先匹配策略：域名白名单、路径许可检查，解析该域的 `robots.txt` 并缓存（TTL 1h）。如果请求被拒绝，直接返回结构化错误，Agent 会收到明确信号——“这条路不通”，而不是一个模糊的超时或 403。

### 2. 审计和限速

每次请求生成一个 `trace_id`，写入审计日志（本地 jsonl 或远程存储），记录：

- 触发该请求的 Agent 会话 ID、上游 prompt 摘要
- 目标 URL、方法、响应状态码、内容长度、耗时
- 匹配的策略规则
- 是否命中缓存

限速器基于令牌桶实现，按域名隔离。这块的坑在于**异步并发下的状态共享**，如果用 asyncio，务必使用 `asyncio.Lock` 包裹 per-domain 的桶操作，否则会出现计数错乱。

### 3. 内容净化与缓存

抓取成功后，对 HTML 做一次“手术”：用 `bleach` 剥离 `<script>`、`<iframe>`、`<object>`、事件属性等危险标签和属性，保留文本、链接和基础结构。注意，不要过度净化——保留 `class` 和 `id` 有时对后续解析有帮助，可通过白名单控管。

净化后的纯文缓存于本地 SQLite，key 为 `sha256(url + 净化策略版本)`，过期时间由策略定义（一般 1-6 小时，文档类可更长）。这一层缓存不仅降低重复抓取，还让 Agent 在离线调试时仍能回放历史内容。

### 4. 集成到 OpenClaw Agent

在 Agent 的工具声明中，将 `safe_fetch` 注册为唯一可用的网页抓取工具，移除任何裸的 `web_browser` 或 `fetch`。同时，在稽客层对返回内容做截断（默认 64K tokens），防止超长页面撑爆上下文窗口。Agent 会自然学会“先提问、再深挖”，因为返回信息被约束在摘要级。

## 踩坑记录

- **robots.txt 解析需兼容性处理**：有些站点给 `*` 设置很长的 `Crawl-delay`，还有些用非标准指令。建议解析后先做一次合理性校验（比如延迟上限 10 秒，否则拒绝该域），避免冻结整个流程。
- **无头浏览器资源泄漏**：对于 SPA 页面，我选择使用 Playwright 的 `headless` 模式，但务必在 browser context 级别设置空闲回收（比如 30 秒无请求自动关闭），并为每个 domain 维护 browser 连接池上限（默认 2）。否则会导致内存暴涨。
- **大文件 URL 的风险**：稽客层必须在收到响应头时检查 `Content-Length`，超过设定的最大体积（例如 10 MB）立即断开连接并返回错误，防止下载 PDF、视频等非预期资源。
- **法律合规的最后一道防线**：即使遵循了 `robots.txt`，某些页面条款仍然禁止自动化采集。稽客层可在请求中添加 `X-Automated-By` 头，声明采集方身份与用途，但最终还需要人工审核敏感域。此层无法替代法律咨询。

## 可复用建议

- 将策略配置外置，支持热加载，方便运维动态调整。
- 为稽客组件提供一个简单的 dashboard（哪怕只是基于 Streamlit），显示各域被拒次数、延迟 P95、缓存命中率，便于发现异常爬取模式。
- 如果团队使用 OpenClaw 这类多 Agent 框架，尽量将稽客作为一个独立的 MCP 服务部署，而不是嵌入 Agent 进程，这样能实现集中审计与跨 Agent 共享限速状态。
- 对于公开数据，考虑优先使用结构化 API（如 GitHub API）替代网页抓取，在策略中配置“优先 API”规则，进一步降低风险。

## 总结

Agent 的网页采集不能继续停留在“脚本小子”的阶段。稽客的思路本质上是将**信任边界**前移：让每一次 HTTP 请求都经过可配置、可审计、可终止的中间层。既不抑制 Agent 获取信息的能力，又守住了安全与合规的底线。

当我们教 Agent 如何操作浏览器时，也别忘了同时教会它边界在哪里。稽客就是那条边界的具体化身。
