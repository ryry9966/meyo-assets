## 背景

团队日常需要汇报工作进展，信息散布在 Git 提交、工单系统、监控告警、任务看板、临时文档里。手动收集并整理成日报，既重复又容易遗漏。我们希望构建一条自动化流水线：每日定时采集原始日志与状态数据，通过 Agent 做摘要与重组，最终输出一份结构清晰、可读性强的日报草稿，再由人工微调后发出。

这篇内容面向已在使用 OpenClaw、Agent、MCP 或类似自动化工具的技术读者，分享一套经过验证的工程做法，避免重复踩坑。

## 问题拆解

日报生成的核心难点不在“调用大模型写一段话”，而在于：

- **数据源分散且异构**：Git、Jira、自建日志、Slack 线程，API 格式、认证方式各不相同。
- **上下文噪音大**：一天可能产生上百次提交和大量流水线日志，直接塞给模型会超出窗口，且关键信息容易被淹没。
- **时效性要求**：日报需在固定时间产出，不能因为某个源拉取慢导致整体失败。
- **Agent 幻觉与格式不稳定**：自由发挥容易产出不可靠内容，需要约束结构和事实边界。

## 做法与步骤

### 1. 数据采集层：统一通过 MCP 工具暴露接口

我们使用 OpenClaw 的 MCP 客户端能力，连接多个 MCP 服务器：

- `git-mcp-server`：获取指定分支的当日 commit 信息，过滤 merge commit，提取 subject、author、timestamp。
- `jira-mcp-server`：查询当前用户当日状态变更、已完成的 issue 列表。
- `self-hosted-logs`：自建 MCP 服务，查询应用按日聚合的错误次数、关键事件。
- `slack-mcp`：抓取指定频道的当日公告摘要（可选）。

每个 MCP 服务封装认证与重试逻辑，返回统一的 JSON 结构：`{source, entries: [{summary, detail, time, link}]}`。采集层保持轻量，只做数据抽取，不做语义理解。

**关键策略**：为每个源设置独立超时（15-30s），失败则跳过该源并记录 warning，避免单点拖垮整个流水线。

### 2. 聚合与去噪：用规则加轻量模型先做粗筛

将所有采集到的条目按时间排序，执行规则过滤：

- 自动 merge、bot 自动提交标记为低优先级。
- 同类重复性 log 聚合为“重复 N 次”一条。
- 忽略长度小于 5 个字符的无意义 commit 消息。

规则过滤后，通常能将原始条目减少 60%-70%。剩余条目按来源打包成一个结构化 JSON 数组，作为 Agent 的输入上下文。

### 3. Agent 生成结构化日报

在 OpenClaw 中定义一个专用 Agent，系统指令约束输出格式。我们采用分步提示策略，将任务拆解为四个子步骤：

1. **分类**：按项目模块或工作主题将条目归类。
2. **提炼**：每个归类下用一句话概括产出。
3. **标记异常**：识别报错、回滚、重要告警，单独输出。
4. **输出 Markdown**：填入预设模板，包含“今日完成”“待跟进”“风险/异常”三部分。

模板示例：

```text
## 今日完成
- [模块A] 修复订单金额精度问题 (#1034)
- [模块B] 完成 OAuth2 鉴权改造联调

## 待跟进
- 监控面板查询慢问题，已定位索引缺失，明日提交优化

## 风险/异常
- 10:23 支付网关 504 错误共 12 次，已自动恢复，待排查日志
```

通过严格限定输出段落，模型不容易跑偏，且后续人工粘贴后无需大量删改。

**指令设计中踩过的坑**：

- 如果让 Agent 直接自由撰写，容易根据某条 commit 消息虚构“完成了某某优化”，而实际只是做了拼写修复。
- 解决办法：要求每条总结必须附带原条目的 id 或 commit hash，并强制引用原文关键短语。必要时可加一条规则：“若无法确认细节，只写‘进行中’或‘相关改动’，不得推断结论”。

### 4. 分发与人工闭环

Agent 生成的 Markdown 通过 OpenClaw 的 `send_markdown` 插件（自开发，适配飞书/钉钉/企业微信）推送到指定群或个人会话，同时上传到内部 Wiki 的日志目录作为备份。

**人工环节必不可少**：我们在消息末尾附加一行小字：“以上由自动化 Agent 生成，请人工审核确认后转发。”每天只需 1-2 分钟快速核对和补充私人事项。

## 踩坑记录

- **时区与日期边界**：所有数据源必须归一化到同一时区，并以“昨天 00:00 - 今天 00:00”作为查询窗口，避免遗漏跨日工作。曾因 Git server 返回 UTC 时间、Jira 返回本地时间，导致部分提交被漏记。
- **大模型上下文爆窗口**：即使过滤后，有些日子仍然条目过多。我们设置硬阈值：最多提供 60 个条目，超出则按重要性排序截断（错误日志优先于常规 commit）。
- **格式漂移**：偶尔模型会忽略指令，直接输出带 emoji 的自由文本。加上 `output_format: markdown_template` 参数，并在提示中混入格式样例后，问题基本消除。
- **Token 成本控制**：每次日报约消耗 1500-3000 token，日均成本可控。但如不设上限，某日抓入大量 CI 日志时曾突破 12000 token。现在强制每个源最多取前 20 条。

## 可复用建议

1. **使用 MCP 封装数据源，不要直接写在 Agent 内部**。数据源会变化，MCP 工具可独立维护、测试，也便于其他 Agent 复用。
2. **Agent 只做摘要，不做事实推断**。坚持事实引用原则，可大幅降低幻觉风险。
3. **分步提示 + 强约束模板比单次自由生成更稳定**。必要时甚至可分两个轮次：先分类，再在第二轮填充模板。
4. **保留原始数据副本**。日报归档时附上采集到的 JSON 原文，方便回溯某条解释的来源。
5. **监控流水线健康度**。为采集失败、生成失败、超时设置告警，避免某天悄悄断掉未发现。

## 总结

自动化日报生成看起来是一个简单的“总结”任务，实际涉及多源异构数据整合、上下文去噪、严格格式约束与人工闭环等多个工程化环节。在 OpenClaw 生态中，配合 MCP 工具与可控的 Agent 提示设计，可以搭建出一条稳定、低成本、且不易产生幻觉的日报流水线。这条流水线运行三个月以来，每人每天省去约 10-15 分钟手工整理时间，并显著改善了报喜不报忧的信息遗漏问题。

希望这套做法能为同样在捣鼓自动化报告的同行提供一些实在的参考。
