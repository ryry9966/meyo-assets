## 背景

端到端（E2E）测试始终是保障业务核心链路稳定的最后一道防线，但编写和维护成本极高。面对频繁迭代的页面、复杂的用户交互流程，手工编写 Playwright 或 Cypress 脚本往往跟不上产品节奏。大模型的出现让“用自然语言生成测试”成为可能，但直接让一个 LLM 输出完整脚本，成功率并不理想——它不了解当前页面的真实 DOM、不清楚元素实际定位符、更无法感知动态加载与环境差异。

于是，我们开始尝试将 Agent 协作引入测试流程：让多个拥有不同能力与工具的 Agent 分工协作，通过 MCP（Model Context Protocol）连接真实的浏览器与测试执行环境，形成“需求→探索→生成→执行→修复”的闭环。本文分享的是基于 OpenClaw Agent 编排与 Playwright MCP Server 的一套工程实践，重点在于可复现的流程、踩过的坑，以及让生成结果真正可用的经验。

## 单 Agent 的瓶颈

最朴素的做法：把需求文档或一条用例描述喂给 GPT，让它输出一个 `.spec.ts` 文件。问题立刻暴露：

- **选择器凭空捏造**：模型可能会生成 `.login-btn` 这类从来没出现在页面上的选择器，因为它是根据常见命名习惯猜的，而不是真实 DOM。
- **无法感知页面状态**：缺少真实浏览器环境，生成的操作序列没有考虑 loading 态、骨架屏、异步渲染、鉴权重定向等。
- **断言脆弱**：经常会写出比对全量文本或固定索引的断言，稍一改动就失败。
- **维护无闭环**：即使测试失败，也不会自动定位原因或修复，只能手动修改。

这意味着“裸用”LLM 只能得到一个看起来像测试的草稿，距离可执行的可靠用例还有巨大鸿沟。要弥合鸿沟，需要实时感知真实页面，并根据反馈自我修正——这正是多 Agent 协作擅长的。

## 多 Agent 协作方案设计

我们把任务拆解为四个角色，每个角色对应一个 OpenClaw Agent，它们通过任务描述、工具（Tool）以及 MCP 连接的外部服务交互：

1. **需求分析 Agent**：接收用户故事或功能描述，输出结构化测试步骤（如 Given/When/Then）。
2. **浏览器探索 Agent**：通过 Playwright MCP Server 打开目标页面，获取可访问性树或完整 DOM 快照，提取所有可交互元素及其属性（data-testid、aria-label、CSS 选择器唯一性等）。
3. **测试生成 Agent**：结合结构化步骤与探索 Agent 提供的元素信息，生成可执行的 Playwright 脚本，强调使用稳定选择器。
4. **执行监控 Agent**：运行生成的测试，捕获失败截图、日志和错误堆栈，分析失败原因，将修复建议或直接重新生成测试的请求反馈给前序 Agent。

整个流程用 OpenClaw 的 Task 模板串联，Agent 之间通过共享上下文传递中间产物（结构化步骤、元素映射表、测试脚本）。MCP 让浏览器操作变成了标准化工具调用，不必自己封装 Playwright 接口，让构建成本大幅降低。

## 步骤实现提要

1. **环境准备**
   - 启动 Playwright MCP Server（例如 `@anthropic/mcp-server-playwright` 社区实现），对外暴露 navigate、click、snapshot 等工具。
   - 在 OpenClaw 中配置该 MCP 连接，并为浏览器探索 Agent 和测试生成 Agent 授予对应工具权限。

2. **定义 Agent 与工具**
   - 需求分析 Agent：仅使用 LLM 能力，将自然语言转换为 JSON 格式的步骤列表。
   - 浏览器探索 Agent：挂载 MCP 工具 `browser_snapshot` 和 `browser_navigate`，任务是获取页面元素清单，并标注推荐的定位策略。
   - 测试生成 Agent：挂载“执行代码”工具（或沙箱），可调用 Playwright 的 `page.goto`、`page.click` 等进行验证性运行，确保生成的选择器确实能命中元素。
   - 执行监控 Agent：挂载运行测试命令的工具，并具备读文件、截图比对的能力。

3. **工作流示例**
   - 输入：“用户可以使用邮箱和密码登录，成功后跳转到仪表盘”。
   - 需求 Agent 输出：1. 打开登录页；2. 输入邮箱；3. 输入密码；4. 点击登录；5. 断言页面包含“仪表盘”。
   - 探索 Agent 打开 `https://example.com/login`，snapshot 发现两个 `<input>` 分别有 `data-testid="email-input"` 和 `data-testid="password-input"`，按钮为 `data-testid="login-button"`。
   - 生成 Agent 创建脚本：

     ```typescript
     test('login with email', async ({ page }) => {
       await page.goto('/login');
       await page.fill('[data-testid="email-input"]', 'user@example.com');
       await page.fill('[data-testid="password-input"]', 'secret');
       await page.click('[data-testid="login-button"]');
       await expect(page.locator('text=仪表盘')).toBeVisible();
     });
     ```

   - 执行 Agent 运行并回传结果。若失败，提取错误（如超时），分析是因为登录后需要等待仪表盘加载，增加 `waitForLoadState` 或更稳健的等待策略，重新请求生成 Agent 修正。

## 踩坑实录

**脆弱的选择器**  
即使有 snapshot，生成 Agent 仍可能倾向使用 CSS 路径或文本选择器。“请输邮箱”这类文本在改版后消失，导致测试再失败。解决方法是强制要求：当页面元素存在 `data-testid` 时，必须使用该属性；否则使用 `getByRole` 并补充 aria-label。如果都没有，生成 Agent 应主动请求前端团队补上稳定属性，而不是硬写脆弱选择器。

**动态内容等待**  
第一次执行经常因为网络慢或动画未完成而超时。我们在生成脚本时加入“自动等待最佳实践”——每个交互后显式添加 `await page.waitForLoadState('networkidle')` 或针对核心元素使用 `waitFor({ state: 'visible' })`。执行 Agent 若检测到超时错误，会提取当前页面的状态截图和 DOM 快照，发给生成 Agent 让其增加等待逻辑。

**认证与环境差异**  
本地运行 MCP 浏览器时可能已登录，但 CI 环境没有 Cookie，导致测试全部跑红。我们的做法是：让探索 Agent 在执行前先检测是否需要认证，若需要，调用预设的“登录工具”注入 session token，或引导生成 Agent 在脚本开头增加登录步骤（从环境变量读取凭据）。这需要 Agent 能感知环境，是一个典型的工程化适配点。

**生成代码的可维护性**  
全自动生成的脚本可能冗长且缺少断言分层，阅读体验差。我们设了一道人工审核栅栏：执行 Agent 只运行测试但不直接合并；所有生成的脚本先推送到临时分支，通知负责人 review，确认思路和选择器质量后再合入。未来可以训练 Agent 遵循团队的 Page Object 模式，但这块目前还在试验阶段。

## 可复用建议

1. **推广 data-testid 规范**  
   这是提升可自动化测试性的前提。“巧妇难为无米之炊”，没有稳定标识，Agent 也无能为力。把“必须有 testid”写入组件开发规范，能显著提升生成成功率。

2. **缓存元素映射**  
   动态页面频繁 snapshot 会增加延迟。可让探索 Agent 缓存元素映射，仅当页面结构变更（如 Git commit 触发）时重新生成，平时复用缓存，节省 token 和时间。

3. **建立失败自愈闭环**  
   不要只把 AI 当成生成器，还要用它来做维护。执行监控 Agent 的反馈链路是核心，让它自动捕获失败并生成修复 PR。即便修复不完美，也提供了一个极速的起点。

4. **渐进式引入**  
   从单一简单页面开始验证协作管线，跑通后逐步覆盖核心业务场景。避免一开始就追求全自动，可以先用 Agent 辅助生成草稿，再由测试工程师调整，收益同样明显。

## 总结

Agent 协作让 E2E 测试编写从“手工敲选择器”转向了“描述意图 + 真实页面感知 + 自动纠错”的模式。它并没有完全替代人，但把最重复、最易出错的部分（定位元素、等待、初始脚本组织）交给了机器，让人专注于测试策略与复杂场景设计。在 OpenClaw 生态下，借助 MCP 连接真实浏览器环境，这个工作流变得异常顺滑。

当然，工程化护城河仍然在于稳定的属性规范、可靠的执行环境和持续的自愈机制。没有这些，AI 生成再多测试也只是“纸上脚本”。把这些配套建设到位，才是让 Agent 真正为你写 E2E 测试的正确姿势。
