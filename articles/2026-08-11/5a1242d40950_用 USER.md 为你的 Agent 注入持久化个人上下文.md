## 背景

在与基于大模型的 Agent 协作时，最常遇到的摩擦并非工具不够强大，而是 **Agent 记不住“你是谁”**。每次新开一个对话、新建一个任务，都得重复交代操作系统、工作目录、常用命令、技术栈偏好甚至代码风格，这些信息对完成任务至关重要，却无法在对话之间自动保留。

OpenClaw 这类 Agent 框架已经具备读取文件、调用 MCP（Model Context Protocol）工具的完整能力，但大多数使用方式仍集中在处理任务本身的输入，忽略了任务主体的“元信息”。一个工程化的解决方案是：**为 Agent 写一份 `USER.md`，把它放进可访问的文件系统，让 Agent 在需要时自动加载这份个人上下文配置。**

## 问题定义

无状态的 Agent 每次执行任务都面临“冷启动”——它不知道你的宿主环境是 Windows 还是 Linux，不记得你更习惯用 `pnpm` 而非 `npm`，也不了解你某个项目的嵌套结构。这带来的后果是：

- 需要频繁使用自然语言重复描述个人设置，消耗 token 和时间；
- Agent 产出结果可能与实际环境不匹配（例如给出 APT 命令而你在用 Fedora）；
- 多个项目、多台机器之间上下文混用，错误率上升。

我们希望构建一种低成本、可维护、可跨会话共享的个人配置，使 Agent 在接到任务时能主动读取，并据此调整行为。

## 设计 USER.md

`USER.md` 本质上是一份遵循约定目录规范的结构化文档。可以放在两个位置之一：

1. **全局用户级**：`~/.openclaw/user.md`，适用于跨项目共用的个人设置。
2. **项目级**：`<project>/.agent/user.md`，覆盖特定仓库的工具链、路径和约束。

文件内容应按段落组织，便于 Agent 按需检索部分内容。一个典型模板如下：

```markdown
# User Profile
- Name: Alex
- OS: Ubuntu 22.04 (x86_64)
- Shell: zsh
- Editor: nvim
- Preferred package manager: pnpm

# Technology Preferences
- Backend: Rust (preferred), Go
- Frontend: React + TypeScript
- Testing: jest, cargo test, pytest
- Prefer functional composition over class inheritance.

# Project Contexts
- Path: ~/repos/opencore
  - Stack: Rust (actix-web) + SQLite
  - Build: cargo build --release
  - Deploy target: Ubuntu server, systemd

# Constraints
- Never modify .gitignore without explicit request
- Do not change README.MD without approval
- Avoid suggesting npm if pnpm-lock.yaml exists
```

这份文件不必一次写全，可以在实践中逐步丰富。

## 让 Agent 读取 USER.md

实现读取需要两步：**提供给 Agent 可调用的文件读取工具**，以及**在系统提示中植入使用规则**。

以 OpenClaw 内置的 File System MCP 插件为例，只需在 Agent 的配置中启用 `filesystem` MCP 服务器，并授权读取对应目录：

```yaml
mcp_servers:
  - name: user-context
    type: filesystem
    config:
      directories:
        - ~/.openclaw
        - path: ~/repos/opencore
          read_only: true
```

然后在 System Prompt 中加入类似指令：

> When starting any task, you may read `~/.openclaw/user.md` to load user preferences. If a project-specific `.agent/user.md` exists, read it to adjust tool choices, paths, and constraints.

一旦配置完成，Agent 会在任务初期自发地提取这些上下文。比如当用户说“帮我在 opencore 项目里跑测试”，Agent 会主动从 `user.md` 中找到该项目路径、Stack 信息，然后直接组合出 `cd ~/repos/opencore && cargo test`，不再需要额外解释。

## 踩坑与优化

在实际工程中会遇到几个典型问题：

**1. 上下文过长导致注意力分散**

如果 `user.md` 动辄几百行，Agent 读取全文会塞满上下文窗口，反而降低精确度。解决办法是让 Agent 分段读取，比如根据任务只查询 `# Project Contexts` 下对应条目，或使用 MCP 搜索工具按关键词检索。或者干脆拆分为 `user-profile.md`、`projects.md`、`constraints.md`，每个文件长度可控。

**2. 信息过期未更新**

修改了个人设置后，已启动的 Agent 会话不会自动感知。建议在开始重要任务前手动命令或提供一个 `reload` 机制，比如在 prompt 中指定：“If in doubt, re-read user.md”。也可以给 Agent 一个 `check_mtime` 工具来判断文件修改时间。

**3. 隐私泄露风险**

如果 `user.md` 中包含 API key、密码等敏感内容，经由 MCP 读取后可能被送入模型。应严格避免在文件中存放明文凭据，只保留环境变量引用或占位符，并由执行侧注入。可利用 `.gitignore` 确保该文件不会意外提交到公开仓库。

**4. 跨平台路径问题**

在多台机器共用 dotfiles 时，要注意路径差异。可以按 hostname 组织文件（如 `user-ubuntu.md`），再由 Agent 根据当前 OS 动态选择读取。

## 可复用建议

- **模板先行**：在团队内部统一 `USER.md` 模板，并作为 `init` 脚本的一部分自动生成。
- **分级覆盖**：全局定义通用偏好，项目目录定义工具链和目录路径，后者优先级更高。
- **与 dotfiles 联动**：将 `~/.openclaw/user.md` 纳入版本管理，跟随环境同步。
- **自动化检查**：可编写脚本定期检查 `user.md` 是否存在，并在初次运行 Agent 时提示创建。
- **团队级共享**：除了个人配置，项目内可增加 `TEAM.md`，描述代码规范、评审流程等，让 Agent 在协作场景下遵守团队约定。

## 总结

`USER.md` 的本质，是把“关于我的一切”从每次临时描述提升为持久化、可被工具性访问的上下文。它体积极小，却能在每一次 Agent 交互中显著降低沟通成本、提高输出准确度。对于已经拥有 MCP 环境和文件系统插件的用户，实现成本接近于零。

如果你正在使用 OpenClaw 或类似框架来构建日常工作流，不妨从一份最小化的 `user.md` 开始，让 Agent 真正从工具进化为了解你的协作者。
