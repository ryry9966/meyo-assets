## 背景：AI 生成的 Markdown 离“发布”还有多远

在 AI 辅助内容生产的流程里，Markdown 几乎是最常见的中间产物。无论是直接让大模型输出，还是通过 OpenClaw Agent 跑完一串工具调用后生成的文章草稿，都是以 `## 标题`、代码块、列表等形式落盘的 `.md` 文件。问题在于：这些 Markdown 的下游往往不是同一个平台，可能是 GitHub Pages、飞书知识库、Notion、微信公众号后台，甚至要通过 MCP 插件直接发布到 WordPress。每个平台对 Markdown 方言的支持程度不同，对图片、标注、元数据的要求也有差异。直接把 AI 的原始输出丢过去，轻则排版错乱，重则功能丢失（比如 GitHub 的警告语法在飞书里显示成一串 `> [!NOTE]` 原始字符）。

于是，一条让 Markdown 自动适配目标平台的管线就变成了刚需。这篇文章会结合我实际踩过的坑，梳理一条可工程化落地的 Markdown 格式适配管线，并以 OpenClaw Agent + MCP 插件的方式串联起整个自动化流程。

## 问题拆解：平台差异到底卡在哪里

经过几次“全自动发布”翻车之后，我把平台间的冲突归为三类：

1. **方言语法差异**  
   GitHub Flavored Markdown (GFM) 支持脚注、任务列表、`[!NOTE]` 警告块、删除线等，但飞书文档除了基础 Markdown 外只支持少量扩展，Notion 则有自己的 block 结构，导入时需转换语法。最典型的翻车现场是 Notion 导入含 `mermaid` 代码块的 Markdown 时直接变成纯文本代码块。

2. **资源引用方式**  
   AI 生成的 Markdown 经常包含相对路径图片，或直接输出图片的语义描述（“这里应该有一张架构图”）。这些引用必须根据目标平台替换为可访问的 URL，或自动触发图片生成后上传。

3. **元数据与排版习惯**  
   微信公众号强调段前空两格、需要特定的摘要字段；GitHub README 则依赖 YAML frontmatter 的 `title` 和 `description` 来生成社交预览。没有一个中间层适配的话，流程必然要反复人工介入。

## 做法：构建可配置的 Markdown 适配管线

我设计的管线核心是：**一份源 Markdown + 目标平台配置 → 适配引擎 → 符合平台规则的 Markdown/富文本**。整个流程通过 OpenClaw Agent 调度，使用自定义 MCP 服务器处理转换逻辑。

### 1. 定义源 Markdown 规范

先对 AI 生成的内容做一次轻度清洗，确保源文件保持一致的方言（我选的是 GFM 扩展集）。清洗脚本主要做三件事：

- 把 AI 偶尔产出的不标准分隔符（如 `---` 前后没有空行）格式化；
- 将图片占位符统一为 `![alt](url)`，如果是本地占位则用 `file://` 占住；
- 剔除 open-ai 风格的特殊标记（例如 `````response`），避免后续解析出错。

这一步可以用一个很小的 Python 脚本或 OpenClaw 的内置插件完成，关键是将“收口”尽可能提前。

### 2. 适配引擎设计

适配引擎按“目标平台 → 规则集”的方式运作。我用的是 Python 的 `mistune` 解析 Markdown 为 AST，然后为每种平台写一个渲染器插件，比如 `feishu_renderer`、`notion_renderer`、`wechat_renderer`。不同渲染器在遍历 AST 时动态替换节点：

- **飞书**：把 `[!NOTE]` 文本块转换成飞书的告警容器语法（多维表格块），把 `mermaid` 代码块替换为“飞书不支持，已外链到图片”的提示，并自动调一个图片生成接口生成 mermaid 图表托管到图床。
- **Notion**：使用 notion SDK 通过 block-by-block 的方式创建页面，而不是依赖 Notion 的 Markdown 导入。因为 Notion 对 Markdown 导入的兼容性奇差，直接 API 调用反而更可控。
- **微信公众号**：将 Markdown 转换成微信兼容的 HTML 片段，处理缩进、颜色标记（用 `wechat-format` 工具），然后通过 MCP 插件推送到草稿箱。

### 3. 用 MCP 串联发布动作

每个平台的发布都被封装成一个 MCP 工具（比如 `publish_to_feishu`、`publish_to_notion`），这些工具接收适配后的内容及其元数据。OpenClaw Agent 在拿到原始 Markdown 后，按照配置中的目标平台列表，依次调用适配引擎和对应的 MCP 工具。工作流大概是这样：

```
AI 生成 → 清洗 → 源 Markdown
→ Agent 读取平台列表（.yaml）
→ 遍历平台:
   → Adapter.render(md, target='feishu')
   → MCP.publish_to_feishu(rendered_content)
```

所有步骤均可以扔进一个 GitHub Actions 的 workflow 里，当某个目录下的 `.md` 文件变更后自动触发。

## 踩坑点

- **Notion API 的 block 嵌套限制**  
  Notion 允许的 block 嵌套层数只有 3 层，用列表嵌套引用块时很容易越界。解决方案是在适配阶段就做一次“平展化”处理：将深度超过 3 层的列表拆分为独立 block，牺牲一部分视觉层级。

- **图片上传的时机和缓存**  
  多平台发布时，图片通常需要上传到不同 CDN（飞书、公众号各有自己的素材库）。如果每篇文章都重新上传，浪费配额且慢。我加了一层图片缓存：用图片的 URL+尺寸做 key，如果之前处理过同一张图，就直接返回已有的平台图片 ID，避免重复上传。这个逻辑放在一个叫 `media_cache` 的 MCP 工具里。

- **文内锚点链接失效**  
  GitHub README 经常用的 `[跳转](#某个标题)` 在飞书和 Notion 中完全失效。适配时要做一次锚点重映射，将 Markdown 内部链接替换为平台自己的书签 ID（需要通过 API 获取）。这一步比较麻烦，一般我会直接在清洗阶段去掉所有内部锚点，用*粗体*或平台自带高亮代替。

## 可复用的建议

1. **让 AI 输出带结构标记的内容**：在和 LLM 交互时，明确要求关键结构使用标准语法（如 “用 GFM 告警块表示注意事项”），从源头避免后期大量修复。
2. **适配规则写成 YAML 配置**：不要硬编码转换逻辑。例如用配置文件描述不同平台对告警块的处理方式（映射为红框 / 蓝框 / 忽略），这样新增平台时只需要增加一个配置文件，而不必改动引擎代码。
3. **先发布到草稿，再人工校验**：全自动发布很美，但误操作成本很高。我的管线默认输出到各平台的草稿箱或私有仓库，人工确认后再手动点发布，同时把差异 diff 记录到日志里，方便回溯。
4. **与 OpenClaw 的插件生态结合**：如果你已经在用 OpenClaw 的 Agent 管理内容生产，将这条管线作为一个“发布技能”挂载到 Agent 上，就可以实现“订阅读者想看什么平台，Agent 自动生成并适配发布”的体验。除了 MCP，也可以直接写成 OpenClaw 的插件，利用其任务队列管理多步转换。

## 总结

Markdown 适配管线的本质不是“写一个万能转换器”，而是建立一个清晰的差异处理流程，让 AI 产出的内容能低成本地流向多个终点。通过结合 OpenClaw Agent 的任务编排和 MCP 的工具化能力，这条管线可以被工程化为一个持续运行的自动发布服务，把人的精力留在更高级的创作和校验上。希望本文的踩坑记录和设计思路能给正在做类似尝试的同学一些参考，少写几个救火的脚本。
