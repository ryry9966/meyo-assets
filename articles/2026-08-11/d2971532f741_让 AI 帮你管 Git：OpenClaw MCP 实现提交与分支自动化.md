# 让 AI 帮你管 Git：OpenClaw MCP 实现提交与分支自动化

## 背景：重复的 Git 操作正在吃掉你的注意力

不管你是一个人维护 side project，还是在多人协作的主分支上频繁切 feature 分支，日常的 Git 操作都高度重复：`git status`、`git add`、`git commit -m "fix: ..."`、`git checkout -b feat/xxx`、`git push`。这些小动作本身不难，但它们频繁打断思维流，累积起来对效率的侵蚀不容小觑。

过去的做法是写一些 alias 或 shell 脚本，但灵活性始终受限——你没办法让脚本理解这次改动的语义，生成贴合上下文的 commit message，更不可能根据任务描述自动决定分支命名策略。直到大模型走向本地工具调用，事情开始有了变化。

在 OpenClaw 生态里，我们可以通过 **MCP (Model Context Protocol)** 把大模型连接到本地 Git 仓库，让 AI 助手真正“看懂”你的 diff，完成从提交到分支管理的重复工作。下面是一套可落地的工程方案，已经在多个项目中跑了两个月，整体可用但远非银弹，把这过程中的真实体验和坑点一并记录下来。

## 问题拆解：不是替代，是卸载负担

首先要明确一点：Git 自动化不是为了替代开发者的判断，而是把那些已经形成肌肉记忆、不需要深度思考的动作卸载掉。在这个前提下，我们需要解决三个核心问题：

1. **安全边界**：AI 绝对不能误操作导致未推送代码丢失，或搞乱分支历史。
2. **语义理解**：生成的 commit message 要准确概括变更内容，不能是“update code”这种废话。
3. **工作流集成**：自动化必须自然嵌入现有开发节奏，而不是另起一套仪式感流程。

## 做法：三步搭一个 Git 自动化助手

### 1. 配置 OpenClaw MCP Git 服务

OpenClaw 原生支持通过 MCP 接入外部工具。我这里使用社区维护的 `mcp-server-git`，它能以标准协议暴露常用 Git 操作。配置很简单，在 OpenClaw 的 MCP 配置里添加：

```yaml
mcpServers:
  git:
    command: uvx
    args:
      - mcp-server-git
      - --repository
      - /path/to/your/repo
```

启动后，AI 助手（OpenClaw 中的 Agent）就可以通过 `git_status`、`git_diff_unstaged`、`git_add`、`git_commit`、`git_create_branch` 等工具直接与仓库交互。**关键安全设置**：我只开放了 `--repository` 指定的那个目录，并且禁止 `push` 和 `reset --hard` 等高风险操作的直接调用，通过在 MCP 层做工具白名单过滤实现，这部分配置可以参考 OpenClaw 的 MCP 过滤文档。

### 2. 设计提交与分支自动化的 Prompt 工作流

在 OpenClaw 里我创建了一个专用 Agent，它的系统指令大致是：

- 定期检查工作区状态，当发现有未暂存修改且文件变动包含实质逻辑时，生成一条合乎 [Conventional Commits](https://www.conventionalcommits.org/) 规范的 commit message。
- 如果当前分支是 `main` 且变更量超过一个阈值（比如修改了 3 个以上文件），提示我是否需要创建新分支，并根据最近一次 issue 或对话上下文建议分支名。
- 任何写操作（`git add`、`git commit`、`git checkout -b`）执行前，必须在 OpenClaw 对话界面里打印 **dry-run 计划** 并等待我的确认。

这样做的好处是：AI 不会静默提交，所有动作都可视可控。经过一段时间的磨合，我甚至会把一些日常清理工作（如合并已完成的 feature 分支后删除远程分支）也交给它，但这类操作仍然需要显式授权。

### 3. 集成到实际开发节奏

我没有把它做成常驻后台的守护进程，而是作为一个 OpenClaw 会话固定窗口。每完成一个小功能的开发或修改，我会切过去看一眼 AI 生成的 commit message 草案，确认无误后说“执行”。分支创建场景下，当我提到“开始做用户登录模块的权限优化”，AI 会建议分支名 `feat/user-auth-optimize`，我同意后自动切过去。

另一个高频用法是**阶段性自动存档**：有时候调试代码会做大量微调，改到后面完全忘记中间的状态。我让 Agent 每当我手动触发“存档一下”，它就 `git add -A && git commit -m "chore: WIP autosave"`，但用自动生成的详细 body 记录当前 diff 摘要。回头 squash 的时候这些 commit 能提供很好的上下文。

## 踩坑记录

1. **commit message 质量波动**  
   简单的单文件修改 AI 总结很好，牵涉多文件、跨模块改动时，生成的 subject line 容易泛化。解决方法是在 prompt 中要求“先列出每条 diff 的核心变更，再浓缩成 50 字以内的标题”，并给几个好的范例，效果提升明显。

2. **MCP 工具超时与资源限制**  
   对大仓库（几千个文件）执行 `git_status` 或 `git_diff_unstaged` 时，首次扫描可能超时。我在工具描述里加了限制：只返回变更文件的路径列表，不取完整 diff，commit 时再获取具体内容，避免一次性加载全量。

3. **环境差异导致路径问题**  
   在不同机器上开发时，仓库路径可能不同。最好用相对路径或环境变量注入，不然每次换环境都要改 OpenClaw 配置。

4. **忌讳静默 `git add`**  
   即使 AI 生成 commit 本身没问题，`git add -A` 这种无差别暂存会带入临时文件或调试日志。所以在 prompt 里强制要求“先逐文件展示待暂存文件，让用户勾选”，这样杜绝了意外提交。

## 可复用建议

- **权限最小化**：只给 Agent 必需的 Git 工具权限，通过 OpenClaw 的工具过滤和白名单机制，永远不要开放 push 权限。推送仍然手动，这是最后的安全阀。
- **用 dry-run 对话代替脚本自动执行**：让 Agent 始终在对话流中行动，而非变成黑盒 cron job。这样每一步都有迹可循，出问题能快速定位。
- **复用 pre-commit hooks**：如果项目本身有 lint、测试等 hook，AI 提交时会触发这些检查。如果失败，Agent 会把错误信息带回对话，你可以立即处理，不用切换终端。
- **从提交延伸至分支策略**：可以进一步让 AI 关注分支生命周期，例如当它检测到某个 feature 分支已合并到 main，会提醒你清理本地和远端分支，甚至生成归档 tag。

## 总结

这套方案的本质是用大模型的语义理解能力，接管开发过程中那些“机械化”的 Git 操作，但它并非集成了神奇的黑盒，而是一个需要仔细设计边界和交互流程的半自动助手。一旦打磨好，它能帮你把注意力更多地留在代码本身，而不是在命令行里反复敲那些已经刻在手指上的命令。

在 OpenClaw 的 MCP 生态下，构建这类工具的门槛已经很低了，关键不是技术实现，而是找到哪些重复工作对你而言是真正的摩擦点，然后只针对这些点做自动化。少即是多。
