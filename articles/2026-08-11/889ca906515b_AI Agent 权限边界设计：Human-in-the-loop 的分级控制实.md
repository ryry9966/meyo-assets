# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

在使用 Agent 框架（如 OpenClaw）构建自动化工作流时，常见的一个场景是：Agent 通过 MCP 或插件获得了工具调用能力，可以操作文件、发送 HTTP 请求、执行 Shell 命令，甚至在 CI/CD 中触发部署。

这些能力一旦放开，就面临一个现实问题——**如何控制 Agent 的自主决策范围？**  
如果每次都询问人类，自动化吞吐量上不去，开发者体验也差；如果完全自主执行，一次 prompt 注入或模型幻觉就可能引发事故。

因此，我们需要一套工程化的权限边界方案，既保证安全，又不会把人变成“审批机器人”。

## 问题拆解

权限边界问题可以从两个维度来理解：

1. **操作风险等级**：某类操作出错后的影响有多大？
2. **上下文可信度**：当前请求是否来自可信会话？是否有校验信号？

由此引出核心设计问题：**如何对不同工具、不同场景设置不同的“询问人类”策略，让 Agent 在安全区内自主执行，在安全区外强制确认？**

## 实践方案：三级权限模型

下面是在 OpenClaw 类型 Agent 框架里可以落地的一套分级控制模式，核心思想是将每一个工具调用划分为三个“自主等级”。

### Level 1：静默执行 (Auto)

适用于只读、幂等、低风险操作，例如：

- 读取本地文件（限定目录）
- 查询数据库（只读账号）
- 调用内部 API 的 GET 接口
- 获取当前时间、环境变量等无副作用操作

这些工具在 Agent 内部直接执行，不需要打断人类。

**实现要点：**

- 在 OpenClaw 的工具注册时打标签 `risk: low`、`mutate: false`
- 权限中间件检测到此类标签时直接放行
- 可选：记录审计日志，但不阻塞流程

### Level 2：自动批准但可回溯 (Auto with Audit)

适用于低风险写入操作，或者影响范围可控、可逆的操作。例如：

- 写入临时文件
- 往 Slack 开发者频道发送消息
- 修改草稿状态下的配置
- 在沙箱环境中执行构建

这类操作不需要实时打断人类，但需要**事后可回溯**，并在异常时可撤销。

**实现要点：**

- 增加标签 `risk: medium`，同时传递 `session_id`、`run_id`
- 执行后将操作摘要 + 回滚信息推送到审计频道（如日志系统或 Slack `#agent-audit` 频道）
- 配合定时任务检查异常模式，支持一键回滚

### Level 3：人类审批 (Human Approval)

适用于高影响、不可逆或涉及生产环境的操作。典型例子：

- 合并 PR
- 修改 DNS 记录
- 执行数据库 DDL
- 触发生产发布

这类操作需要在 Agent 流程中**阻塞并等待人类确认**。

**实现要点：**

- 标签：`risk: high`，`approval: required`
- 在 OpenClaw 中通过一个“审批 MCP Server”来实现交互
- 审批消息携带上下文摘要（操作内容、影响范围、风险点），通过 Slack/Discord 按钮或 CLI 回车确认
- 超时机制：如 30 分钟内无响应，自动拒绝并通知

## 踩坑记录

在实践中，以下几个问题反复出现，值得特别注意。

### 1. “低风险”定义随时间漂移

一开始认为安全的操作（如读取 env），后因 env 中包含 token 而被判定为高风险。**建议：** 建立工具注册表评审机制，任何新增工具必须标注风险等级，并在代码 review 中确认。

### 2. 上下文缺失导致审批者“盲目批准”

审批消息只写了一句“Are you sure?”没有上下文，人类很容易形成机械点击的习惯。**解决方案：** 审批消息必须包含：操作描述、影响范围、风险等级、相关日志链接、回滚方案。甚至可以在审批前由 Agent 生成一段 Dry-run 结果。

### 3. 过度依赖人类审批，自动化收益被耗尽

如果一个工作流中每 3 步就触发一次审批，人类很快就会疲劳，最终要么关掉 Agent，要么习惯性点“同意”。**建议：** 定期复盘审批率，如果一个 Level 3 操作在最近 50 次执行中 100% 被同意且无事故，应评估是否可以降级为 Level 2 并加强审计，而不是继续打断人类。

### 4. 审批通道本身需要容灾

如果审批依赖 Slack，而 Slack 宕机，Agent 流程就会永久阻塞。**实践：** 增加 fallback 审批方式（例如 CLI 命令 `agent approve <id>`），并设置全局超时策略，超时后自动拒绝。

## 可复用建议

1. **用标签而非硬编码判断权限**  
   所有的工具定义上都带上 `risk` 和 `approval` 元信息，Human-in-the-loop 逻辑统一在中间件或 MCP 网关中处理，不要散落在各 tool handler 里。

2. **构建审批上下文生成器**  
   实现一个函数 `build_approval_prompt(tool_name, args, risk_analysis)`，规范输出格式，保证每个审批都携带足够信息。

3. **动态调整信任等级**  
   可在会话维度记录操作错误率，如果某一会话短时间内出现 3 次执行失败，自动提升其后续操作的审批要求，直到人工介入确认。

4. **审计日志是底线**  
   即使 Level 1 操作也应有结构化日志，包含 `session_id`, `run_id`, `tool`, `args`, `timestamp`, `result`。出问题时，这是唯一能回溯的线索。

## 总结

AI Agent 的权限边界不是一个静态开关，而是一套**基于风险和上下文动态调整的控制面**。  
工程化的做法是：

- 给每个工具打上风险标签
- 在框架层实现三级执行策略
- 确保审批信息可读、可回溯
- 通过复盘不断调整边界，而不是一成不变

这样，Agent 才能真正做到“能自己干的自己干，该问人的一个不落”，在安全与效率之间找到平衡。
