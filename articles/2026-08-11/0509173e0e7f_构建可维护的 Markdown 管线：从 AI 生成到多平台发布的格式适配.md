## 背景：AI 生成内容的最后一公里

在 OpenClaw 生态里，用 Agent 批量产出技术文章、周报、产品说明越来越普遍。通常这些 Agent 通过 MCP 调用大模型，以 Markdown 作为交换格式。但当你真正要把内容发布到 GitHub Pages、知乎、微信公众号、小红书、Notion 等十几个渠道时，Markdown 的“通用性”很快消失了。每个平台支持的语法子集不同，对图片、链接、代码块、表格、数学公式、脚注的处理方式千差万别。如果只靠后期手动调整，不仅低效，还会让自动化闭环断裂。

## 问题：不是 Markdown 不标准，是平台太分裂

常见的冲突点包括：

1. **图片引用**：本地相对路径、图床直链、微信公众号需要先上传到素材库并获得 media_id。
2. **代码块高亮**：GitHub 支持语言标识，但微信公众号会直接吞掉 ``` 语法，需要转成带样式的富文本。
3. **表格**：少数平台要求表格前后有空行，有的限制列宽，有的完全不支持多行表头。
4. **数学公式**：标准 LaTeX 分隔符 ($$/ $) 在知乎上可用，在公众号上需要转成图片或 Unicode 近似方案。
5. **链接与引用**：有些平台不允许裸链接，必须加文案；脚注链接在公众号里会丢失。
6. **元数据管理**：标题、摘要、封面图、发布时间等在不同平台有不同的注入方式。

纯靠前端编辑器或 LLM 生成的一次性 Markdown 无法覆盖这些差异。你需要一个中间处理层，把“源 Markdown”适配为各平台的“目标 Markdown”或“富文本片段”。

## 做法：设计一条可插拔的 Markdown 管线

我们在实际维护中形成了如下工程结构，适合以 Agent 或插件方式嵌入到 OpenClaw 工作流中：

```text
[AI 生成] -> 源 Markdown（遵守统一中间规范）
      |
      v
[规范化器]  统一换行符、缩进、清理多余空行、检查 front matter
      |
      v
[规则引擎]  根据目标平台调用对应适配器
      |
      v
[输出阶段]  生成平台 Markdown + 元数据文件 + 图片上传任务
```

### 1. 定义中间 Markdown 规范

选一个严格子集，禁止使用平台特定扩展。比如：
- 图片只允许远程 URL，不允许本地路径。
- 表格必须包含对齐分隔行，列数固定。
- 代码块必须带语言标识。
- 不用 HTML 标签。
- 数学公式统一用 `$$...$$` 块级，`$...$` 行内。
- 脚注转换为内嵌括号引用。

这样保证从 LLM 出来的内容通过简单的 linter 就能进入管线，不必为了适配多个平台而修改生成逻辑。

### 2. 构建适配器引擎

每个平台对应一个适配器模块，接收规范化后的 markdown AST，输出平台版 markdown 字符串和附带操作（如图片上传任务）。我们用 `unified` + `remark-parse` + 自定义 visitor 来做 AST 遍历，比正则替换稳健得多。

示例适配器逻辑：
- **GitHub**：几乎直出，保留代码块、表格，只处理图片 URL 绝对化。
- **微信公众号**：转换代码块为 `<pre><code>` 包裹的 HTML，交由后端富文本渲染；表格转 HTML table；图片调用微信素材上传接口替换为 `media_id` 后的占位符。
- **小红书**：限制标题长度，将代码块转为截图（预留接口），对 Emoji 做平台兼容处理。
- **知乎**：数学公式保留，但需在开头注入 `<!--more-->` 分割摘要等。

### 3. 图片上传任务分离

管线不直接执行上传，而是生成一个待处理队列（JSON 文件）。另由专门的小型 Agent（或 MCP 工具）消费队列，执行上传并回写结果，再触发第二次渲染。这样可以让管线本身保持无副作用，便于调试和重试。

### 4. 元数据层

源 Markdown 顶部用 YAML front matter 存放标题、摘要、标签、封面图、预计发布时间等。每个适配器实现自己的 metadata 映射规则，生成平台所需的具体字段（如公众号的 `digest`、知乎的 `title_image` 等）。

## 踩坑点

**坑1：表格对齐符被误判为非法语法**  
有些解析器在表格分隔行允许两侧的 `:` 有空格，有些不允许。中间规范必须明确规定无空格，避免在适配时重复修整。

**坑2：微信公众号代码块转 HTML 后样式丢失**  
公众号后台对 `<pre>` 有一定的清洗逻辑，直接嵌入复杂 style 会被过滤。需采用 `white-space: pre-wrap` 加 `<br>` 折中方案，同时保留缩进。更稳妥的方式是代码截图，但会增加图片负载。

**坑3：连续发布时的幂等性问题**  
如果管线在发布环节被重试，同一条内容可能重复上传图片，造成素材库膨胀。需要为每个图片生成内容哈希，上传前查询去重。

**坑4：LLM 生成的内容包含不可见字符**  
零宽空格、特殊 Unicode 控制字符会使某些平台报错。规范化器应增加 NFC 归一化及不可见字符过滤。

## 可复用建议

- **用 AST 而不是正则**：Markdown 嵌套较多时正则极易出错，引入 `mdast` 能清晰遍历节点类型并处理。
- **配置平台规则，不要硬编码**：每个适配器的差异点（是否允许 HTML、图片宽度限制、摘要长度等）抽成 JSON 配置文件，方便新增平台。
- **自动化测试 pipeline**：为每条规则准备 fixture，用平台官方编辑器实际预览，形成 golden samples，CI 里每次改动跑对比。
- **Agent 集成**：把整个管线封装成 MCP 工具，让 OpenClaw 的主 Agent 在生成内容后自动调用 “publish_markdown” 工具，传入目标平台列表，获得发布就绪的文档包。

## 总结

Markdown 管线不是一次性的小脚本，而是长期维护的内容基础设施。它的价值在于把“AI 生成 - 人工校对 - 多平台适配”这个链路中的重复劳动消除干净，让 Agent 和人类各司其职。当你用 OpenClaw 搭建自动化内容工作流时，花两天打磨这条管线，比事后为每个平台手动改格式要划算得多。后续还可以扩展到自动缩短链接、自动生成摘要图、自动同步到 CMS 等，真正把 Markdown 变成数据的“统一表达层”。
