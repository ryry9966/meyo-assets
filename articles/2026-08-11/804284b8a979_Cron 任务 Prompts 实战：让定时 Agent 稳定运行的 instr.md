# Cron 任务 Prompts 实战：让定时 Agent 稳定运行的 instruction 设计

在 OpenClaw 这类 Agent 编排环境中，Cron 触发器是最常见的自动化入口。用自然语言写定时任务听起来很美好，但真正把「每天 9 点汇总昨日工单并发送通知」这类需求稳定跑起来，instruction 的写法会直接决定它是可靠的生产管线还是隔几天就静默失效的定时炸弹。

## 1. 问题出在哪里

很多人第一次接入 Cron 任务时只会给 Agent 一句模糊指令：

> 每天早上 9 点，整理昨天未处理的客户消息，发邮件给负责人。

实践中的结果往往很糟糕：

- Agent 会产生多余的解释文本，输出「好的，我已整理完，现将结果以 JSON 格式附上：...」，下游工具解析失败。
- 时区不对，UTC 9 点执行，而非 Asia/Shanghai。
- 前一次任务还没跑完，新一次又触发，导致重复操作或状态污染。
- 外部 API 不可用时，Agent 只是返回错误信息，没有重试或告警机制。

本质上，这些都不是 Agent 能力问题，而是 instruction 没有用「代码思维」去约束行为。

## 2. 设计的核心原则

把定时 Agent 的 instruction 看作一段生产代码的配置：它必须定义输入、行为、输出、异常处理和幂等性。

我把它收敛成 5 个必须回答清楚的问题：

- **任务边界**：本轮需要处理的具体数据范围是什么？时间窗口从哪里到哪里？
- **执行动作**：操作步骤是否可以由 Agent 自主裁剪？如果不是，必须显式限定工具调用顺序。
- **输出契约**：期望的输出格式、内容，以及绝不允许输出的内容。
- **并发与幂等**：如果任务重叠该怎么办？能否安全重入？
- **异常路径**：任何一次外部调用失败后的降级行为。

## 3. 实战步骤

以「每日 9 点生成昨日客服团队响应时长报告并保存到 Knowbase」为例，逐步构建 instruction。

### 3.1 固定上下文，消除歧义

将执行时变量完整注入，而不是让 Agent 自己推断。

```
现在是 {{current_iso_time}}，时区 Asia/Shanghai。
你的工作目录为 {{work_dir}}。
Knowbase 写入工具为 write_knowbase。
邮件发送工具为 send_email。
```

在 OpenClaw 中，这些占位符由运行时引擎替换，确保 Agent 拿到的就是精确值。

### 3.2 严格限定时间窗口

不要让 Agent 自己理解“昨天”。直接计算并给出明确的起止时间戳：

```
本轮任务处理的时间范围：
开始：{{yesterday_start_iso}}
结束：{{yesterday_end_iso}}
只处理该窗口内创建且状态为 closed 的 ticket。
```

这样可以避免因自然语言理解偏差，把“昨天”处理成了“过去 24 小时”。

### 3.3 强制输出格式与静默原则

要求 Agent **只输出**工具调用，不添加任何自然语言陈述。推荐使用 OpenClaw 的 `response_format` 约束，但在 instruction 中也要强调：

```
你的响应必须是标准工具调用体，不能包含任何解释、问候语、Markdown 说明。
执行完成后，只需输出一个确认结构的 JSON：
{
  "status": "ok",
  "processed_count": <number>
}
若任何步骤失败，也采用同样的结构，status 字段置为 "error"，并在 errors 数组中列出原因。
```

### 3.4 内置幂等逻辑

Cron 任务最常见也最棘手的场景是前一实例未退出，新调度又触发。instruction 中必须提供决策依据：

```
在开始前，先检查临时标记文件 {{work_dir}}/report_running.lock。
如果该文件存在，且修改时间在 10 分钟内，直接退出，输出：
{"status":"skipped","reason":"previous instance still running"}
否则创建该文件，并在任务结束后删除。
```

对没有文件系统权限的环境，可以改为查询某个状态记录。

### 3.5 异常与重试策略

每个外部依赖都可能失败，需要给出简洁明确的行为树：

```
调用生成报告的 API 若返回 5xx，等待 30 秒后重试一次。
若仍然失败，则通过 send_email 将错误详情通知 {{oncall_email}}，
任务标记为 failed 但不创建报告。
不允许无限重试。
```

这种指令避免了 Agent 在失败时自行「发挥创造力」，也保护了后端不被打崩。

### 3.6 Dry-run 模式

所有 instruction 模板都应内建一个 dry-run 开关：

```
如果环境变量 DRY_RUN=true，则只打印计划执行步骤和将要操作的数据量，不执行任何写操作，
也不发送邮件。
```

这让你在正式上线前可以手动触发一次测试，观察 Agent 的推理路径。

## 4. 踩坑笔记

- **时区不一致**：容器默认 UTC，而计算“9点”使用系统时钟时 Agent 容易混淆。永远在 instruction 中显式声明时区，并让上游注入对应的时间变量。
- **工具名称变化**：即便 MCP 工具重命名，Agent 也可能仍然调用旧名。保持 instruction 与当前工具列表的同步，并在测试时故意置入不存在的工具名看 Agent 的反应。
- **输出中夹带思考**：尤其在使用支持 chain-of-thought 的模型时，需要在系统 prompt 层关闭中间推理的输出，或明确禁止。
- **忘记关闭循环**：如果不限定任务结束条件，Agent 可能在分页查询时进入无限循环。明确最大页数或总条数上限。

## 5. 可复用的指令模板骨架

```jinja2
## 任务上下文
- 当前时间：{{current_iso}}
- 时区：Asia/Shanghai
- 工作模式：{{env.DRY_RUN | default("false") | lower}}
- 超时限制：必须在 4 分钟内完成所有操作

## 任务目标
{{task_description}}

## 数据范围
- 时间窗口：[{{window_start}}, {{window_end}}]
- 对象类型：{{entity_type}}
- 过滤条件：{{filters}}

## 执行步骤（严格有序）
1. 检查并发锁 {{lock_key}}
2. 若锁未过期，查询符合条件的 {{entity_type}} 列表
3. 使用工具 {{analysis_tool}} 生成摘要
4. 通过 {{write_tool}} 持久化结果至 {{output_location}}
5. 释放锁并输出确认 JSON

## 错误处理
- 任何步骤失败后，释放锁，输出 error JSON，通知 {{oncall_channel}}
- 不允许进行未在步骤列表中列出的操作

## 输出要求
你的最终输出必须且仅为一个 JSON 对象，不得包含其他内容。
```

使用时，Fill-in 的变量由 OpenClaw 的 plan 阶段注入真实值，instruction 本身保持纯声明式。

## 6. 总结

让 Cron 任务在 Agent 体系中稳定运行，关键不是给 AI 更多自由，而是用 instruction 把它的行为空间收束到确定的边界里。把每一次定时任务都当成一个没有 UI 的后台 Job，用环境变量注入上下文，用输出契约确保下游可解析，用锁和重试策略兜底故障。当 instruction 开始读起来像一份微服务的配置时，它就差不多对了。
