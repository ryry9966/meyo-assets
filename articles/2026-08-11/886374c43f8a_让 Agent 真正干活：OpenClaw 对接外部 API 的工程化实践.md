# 让 Agent 真正干活：OpenClaw 对接外部 API 的工程化实践

## 背景

现在的 Agent 框架早已不是“只动嘴皮子”的大模型，通过工具调用（Tool Calling / Function Calling）连接真实世界才是落地的起点。OpenClaw 作为面向 Agent 与自动化的开源框架，天然通过 MCP（Model Context Protocol）支持与外部服务握手，让 Agent 能够查询数据库、调用 SaaS 应用、操作物理设备。

但“对接”二字说起来轻松，做完一个 demo 和把它放进长期运行的生产链路，中间隔着无数隐形小坑。本文记录我们在一线对接过程中沉淀的实践，涵盖从第一个 API 工具到稳定运行的工程化要点。

## 问题定义

理想情况是 Agent 看到用户说“帮我查一下北京天气”，自动识别意图并调用天气 API。但实际上我们遇到的是：

- 工具描述写了，Agent 不调；
- 参数传错，API 返回 400，Agent 却复述错误 JSON；
- 外部服务超时，Agent 傻等 30 秒后直接回答“抱歉，我无法完成”；
- API Key 不知怎么就出现在日志里。

本质问题：**Agent 与 API 的握手不是一次简单的函数调用，而是一段需要处理协议、错误、安全和可观测性的分布式交互。**

## 做法：用 MCP 让 Agent 看见外部能力

OpenClaw 中，外部服务通常以 MCP Server 或内联工具函数的方式暴露。这里以最常见的“为 Agent 添加天气查询工具”为例，走通全流程。

### 第一步：定义工具描述 Schema

工具描述是 Agent 调用 API 的唯一“说明书”，要包含明确的意图触发条件、参数语义和返回格式。切忌直接拷贝 API 文档。

```yaml
tools:
  - name: get_weather
    description: >
      查询指定城市的实时天气。当用户询问某个城市的天气、温度、降水等信息时使用。
      返回包含天气状况、温度（摄氏度）、风速的简短摘要。
    parameters:
      type: object
      properties:
        city:
          type: string
          description: 城市名，尽量使用中文，例如"北京"。
      required: ["city"]
```

### 第二步：实现可靠的处理函数

函数里要处理的远不止 `requests.get`。我们抽象了一个轻量包装：

1. **认证**：API Key 从环境变量读取，绝不出现在描述或日志中。
2. **参数验证与清洗**：例如 API 要求英文城市名，我们在函数内做一个简单的中英文映射兜底；参数类型做显式转换。
3. **超时与重试**：设置连接超时 5 秒，读取超时 15 秒；对 5xx 或网络异常进行最多 2 次退避重试。
4. **错误格化**：将异常包装成人类可读的文本返回给 Agent，而不是直接抛出 traceback。例如：`"天气服务暂时不可用，请稍后重试。（错误类型：超时）"`。这样 Agent 可以将这一信息自然地传递给用户，而不是胡乱编造。

```python
def get_weather(city: str) -> str:
    api_key = os.getenv("WEATHER_API_KEY")
    if not api_key:
        return "工具配置错误：缺少 API Key。"
    # 参数转换、重试逻辑、超时处理...
    # 最后返回结构化纯文本
```

### 第三步：注册并注入 Agent 上下文

在 OpenClaw 的配置中将该函数注册为 MCP 工具，并确认 Agent 的 system prompt 中有引导它主动使用工具的说明。例如：

> “你可以使用 `get_weather` 工具查询城市天气。当用户询问天气相关问题时，务必调用该工具而不是凭记忆回答。”

### 第四步：意图路由测试

用一组测试 prompt 触发：“今天北京热吗？”“上海会不会下雨？”“杭州气温多少度？”观察 Agent 是否每次都正确选择工具、参数是否符合预期。这一步尤其重要，甚至可以作为一个CI检查点。

## 踩坑记录

1. **工具描述太“技术化”**  
   早期贴了 REST 接口的原始字段名，Agent 看不懂，导致不调用。后来全部改写为自然语言、面向意图的描述，触发率立刻上升。

2. **隐式类型不匹配**  
   Agent 输出参数总是字符串，而 API 可能需要整数。我们在 handler 内统一做 `int()` 转换并捕获异常，返回友好提示让 Agent 重新生成正确的参数。

3. **超时不处理，上下文污染**  
   一次外部 API 无响应整整 60 秒才超时，Agent 的整个对话卡死。设置合理的超时和快速失败，并且超时时返回明确错误，Agent 可以改用备用方案或如实告知用户。

4. **鉴权信息泄露**  
   日志中曾打印出包含 API Key 的请求 URL。解决方案：在发请求前统一过滤敏感头部，并在日志级别屏蔽。

5. **工具返回过大导致上下文溢出**  
   某次 API 返回了大量未过滤的 JSON，Agent 直接“看花眼”，后续回答完全跑偏。我们的做法是 handler 只返回摘要，如果需要详细数据，再提供另一个“分页查询”工具。

## 可复用建议

- **提取工具 BaseWraper**：所有工具 handler 继承同一个基类，内置超时、重试、错误格化、敏感信息过滤，只让业务方写核心逻辑。
- **工具描述规范**：制定内部 checklist，每个工具必须写明“何时使用、参数含义、异常情况下的返回示例”。
- **中间件观测**：添加一次工具调用切面（AOP），记录调用耗时、参数、成功/失败状态，不记录敏感信息，方便排障。
- **配置外置**：所有密钥、URL 等通过环境变量或配置中心注入，杜绝硬编码。

## 总结

让 Agent 真正“干事”，就得把它和外部 API 的握手当作一个正式的服务集成来看待。OpenClaw 通过 MCP 给出了标准化的接口，但工程化的质感在于：**描述要让人（以及模型）读懂，执行要兜得住故障，数据要守得住隐私，链路要看得见痕迹。** 这样对接出的外部服务才不会成为 Agent 的“阿喀琉斯之踵”，而是它稳定伸向真实世界的触角。
