## 写在前面
当 AI 助手需要处理的任务越来越复杂，我们会自然地往里面塞工具、知识、提示词。很快就会发现，把所有能力一股脑塞进上下文，既费 token 又拖慢推理，agent 还经常选错工具。OpenClaw 的 Skills 机制提供了一种工程化的思路：把能力拆成独立的 Skill，让 agent 在执行时按需加载，既保持上下文的精悍，又保证了能力的可扩展性。这篇文章围绕实际落地过程中的设计、踩坑与优化展开，不堆概念，只谈能复用的经验。

## 背景：一个臃肿的 agent 有多痛
起初我们只有一个 agent，直接通过 system prompt 挂上十几个工具、几段长文档。跑一阵子后问题暴露得很明显：
- **Token 消耗失控**：即使当前任务只需要 1 个工具，全量提示也占掉几千 token，长对话尤其明显。
- **模型分心**：工具太多时，模型容易选错，尤其名称相似或描述接近的工具。
- **迭代困难**：新增一个能力就得改全局 prompt，影响已有行为的稳定性，测试回归成本很高。

我们需要的不是更长的 prompt，而是一个动态加载机制，让 agent 只携带“当前任务可能用到的最小能力集合”，用到时再激活，用后能释放。OpenClaw 的 Skills 正是来解决这个问题的。

## 什么是 OpenClaw Skills
在 OpenClaw 里，一个 Skill 是一个自包含的能力单元，通常包括：
- `manifest.json`：声明 skill 的名称、版本、能力描述、触发条件、依赖和暴露的工具列表。
- 工具实现：Python/TypeScript 函数，遵循统一的接口。
- 可选的系统指令片段：当 skill 被激活时注入的专用 prompt。

Skills 不直接绑定到 agent，而是通过注册表（Skill Registry）统一管理。agent 启动时不加载任何具体 skill，只在接到用户任务后，由调度层根据意图匹配需要的一个或多个 skill，动态拼装出当次运行的 agent 环境。

## 实现步骤：让 skill 按需生效
下面是在 OpenClaw 中落地 Skills 的典型流程，我尽量脱敏成通用步骤。

### 1. 定义 Skill 的声明
每个 skill 放在独立目录，核心是 `manifest.json`，至少包含：
```json
{
  "name": "weather",
  "description": "Get real-time weather and forecasts",
  "triggers": ["weather", "temperature", "forecast", "rain"],
  "tools": ["get_current_weather", "get_forecast"],
  "prompt_snippet": "You can provide weather for any city...",
  "max_tokens_estimate": 350
}
```
`triggers` 用于快速匹配，`max_tokens_estimate` 帮助调度器计算累计的 token 预算，超出阈值时进行降级或要求用户确认。

### 2. 注册与发现
所有 skill 目录被扫描并注册到一个 `SkillRegistry`。注册表对外暴露两个关键接口：
- `match(user_input) -> List[Skill]`：基于意图或关键词做粗筛。
- `resolve(skill_name) -> Skill`：返回完整的 skill 对象供加载。

实际项目中，匹配逻辑不止靠关键词，还可以接轻量级分类模型，或直接用 LLM 做一次“意图→skill”路由，但需要注意这一跳本身也不能太重。

### 3. 动态装配 agent 上下文
执行的关键一步是“拼装”。拿到匹配的 skill 列表后，调度器做以下动作：
- 将各 skill 的 `prompt_snippet` 插入 system prompt 的指定位置。
- 将工具列表合并，遇到同名工具时按命名空间重命名或报错退出。
- 把最终的上下文发送给 LLM，执行完本轮任务。

任务结束后，skill 相关的临时上下文会被丢弃，下次任务重新匹配、重新注入。这样保证每次对话回合的提示都尽量短，且和当前意图高度相关。

## 踩过的坑
实践中遇到几个很容易忽视但影响巨大的问题。

**1. 匹配时机与上下文污染**
早期我们在每一轮对话都重新匹配 skill，发现当用户连续追问时，第二轮可能因为少匹配了某个技能而丢失上下文。正确的做法是：在一个任务“会话”的整个生命周期内，保持已加载的 skill 不变，直到用户明确开启新任务（或由检测模块判断话题跳转）。否则 agent 会因工具突然消失而报错。

**2. 工具名冲突与副作用**
两个 skill 分别有同名工具 `search`，合并后 LLM 不知道该调用哪一个。解决方案是强制为每个工具加上 skill 命名空间，如 `weather__get_current_weather`，并在 prompt 里清晰说明这种命名规则。副作用是 prompt 变长了一点，但避免了执行错误，反而更稳定。

**3. Token 预算估算不准**
max_tokens_estimate 很容易拍脑袋，上线后要么超预算导致截断，要么过于保守造成频繁降级。我们最终使用“实际工具定义 + 示例参数”的运行态字节数，乘上一个安全系数来计算。部署后通过监控日志持续微调，才收敛到一个合理值。

**4. 热加载与启动延迟**
在 agent 启动时一次性加载所有 skill 配置问题不大，但如果每次请求都去磁盘读取 manifest，高并发下 IO 抖动明显。解决方法是用进程内缓存，并监听文件变更做热更新，而非每次都走文件系统。

## 可复用的工程建议
- **声明式设计**：所有 skill 必须包含明确的能力边界与触发词，方便自动化匹配，也方便后期做审计。
- **命名空间隔离**：工具、变量、prompt 片段都带上 skill 前缀，避免冲突。
- **Token 预算管理**：为每个 skill 标注 token 开销，并为每次 agent 运行设定总量上限，超过时间则择优删减或要求拆分任务。
- **懒加载+会话保持**：按任务会话加载 skills，会话内保持稳定，切换主题时再重置。
- **可观测性**：记录每次加载了哪些 skills、耗费 token、匹配耗时，用于后续优化路由策略和 skill 拆分粒度。

## 总结
Skills 机制本质上是把“静态的巨型 agent”重构为“一套调度器 + 一组轻量能力包”。它的价值不在于某种黑科技，而在于让能力的管理、加载和迭代变得可控。对于已经在使用 OpenClaw 或类似多工具 agent 框架的团队，引入按需加载是降低 agent 维护成本、提升模型表现的有效手段。在实际推进中，多花些精力在声明规范、隔离和监控上，会比追求自动匹配的炫技更重要——工程落地，决定成败的往往是这些不起眼的细节。
