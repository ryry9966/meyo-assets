## 背景：E2E 测试为什么总是被牺牲

端到端测试能捕捉真实用户路径，但大多数团队只在口头上重视它。原因很现实：编写慢、维护痛、环境依赖重。一段登录流程的测试可能需要处理表单、弹窗、验证码绕过、等待时机，调试一次往往耗费半小时以上。

随着 Agent 框架（尤其是 OpenClaw）与浏览器自动化 MCP 服务的成熟，我开始尝试让多个 Agent 协作完成“探索页面 → 生成测试 → 执行验证 → 修复”的闭环。这不是靠一句 prompt 直接吐出完美代码的魔法，而是通过角色划分和工程约束，把生成结果控制在**可审计、可修正**的范围内。

## 问题：一次性生成的幻觉成本

如果只用一个 Agent 去“看”页面截图再写测试，很容易出现两类问题：

1. **选择器脆弱**：生成的定位策略过于依赖当时 DOM，缺乏容错。
2. **断言空泛**：往往只检查页面是否包含某个文字，业务路径覆盖不足。

这些问题源于 Agent 没有**交互反馈**。它无法感知动态内容加载、过渡动画、网络延迟。因此需要引入协作结构：一个 Agent 专门与真实浏览器交互，另一个负责将交互记录转译成测试代码，第三个负责运行并反馈错误。

## 实践：利用 OpenClaw + Playwright MCP 构建协作环

环境很简单：本地运行 OpenClaw 实例，挂载 Playwright MCP Server（支持 browser_navigate、browser_click、browser_snapshot 等工具）。然后配置一个“测试生成任务”，包含三个 Agent 角色。

### 角色与流程

- **Explorer**：拥有浏览器工具调用权限。接收高层任务（例如“探索登录流程并记录关键步骤”），操作 Chrome，通过 `browser_snapshot` 获取可访问性树和截图，输出一个结构化的交互日志（Markdown 表格，包含步骤、选择器、预期反馈）。
- **Coder**：接收交互日志和目标测试框架（如 Playwright Test），生成 `.spec.ts` 文件。要求：使用 `page.waitForSelector` 代替固定 `sleep`，断言基于 Explorer 记录的预期内容，并在关键步骤后附加注释。
- **Reviewer**：拿到 Coder 的测试文件和浏览器工具权限，执行 `npx playwright test`（通过 shell 工具），收集失败信息（栈跟踪、截图），用简洁的格式回传错误给 Coder；Coder 根据错误修复，再次提交。循环上限设为 3 次。

流程通过 OpenClaw 的任务编排完成，每个 Agent 的输出作为下一个的输入，上下文通过共享消息历史传递。整个会话记录在 OpenClaw 的工作区中，方便回溯。

### 具体步骤

1. 启动 OpenClaw 并加载 Playwright MCP 配置。
2. 在会话中定义系统消息，明确每个子 Agent 的职责、输出格式、停止条件。
3. 发送第一条指令：“请探索 http://localhost:3000/login 的登录流程，用户名 testuser，密码 Test@1234，注意验证登录成功后的跳转与欢迎语。”
4. Explorer 生成交互日志后，手动确认一次（这是第一次人工卡点），然后交给 Coder。
5. Coder 生成测试文件后，Reviewer 直接执行。如果失败，自动进入修复循环。
6. 最后生成的文件由人工复制到项目中，提交前做必要的参数化（如把硬编码凭证改为环境变量）。

## 踩坑点

1. **DOM 快照噪声**  
   `browser_snapshot` 会返回大量可访问性节点，Explorer 容易记录太多无关元素，导致 Coder 生成多余的断言。需要给 Explorer 明确约束：“只记录与任务路径直接相关的交互节点，保持步骤数 ≤ 8”。

2. **动态元素等待失败**  
   自动生成的 `waitForSelector` 默认超时不够，或者选择器过于具体（如带有动态 hash），Reviewer 执行时常因超时而失败。改进方案：让 Coder 优先使用 role-based 选择器（`page.getByRole`），并提供 fallback 逻辑，这部分需要在 Coder 的 prompt 中示例。

3. **循环修复陷入死胡同**  
   有一次 Reviewer 反馈的错误是“测试环境数据库未重置”，Coder 无法在测试代码层面解决，却不断尝试修改断言。为此设定了硬规则：Reviewer 必须区分“测试代码问题”和“环境/业务逻辑问题”，对后者直接终止循环并通知用户。

4. **Token 爆炸**  
   浏览器截图和快照信息量很大，多轮对话容易超出上下文窗口。解决方法是让 Explorer 输出摘要性的交互日志，而不是原始 JSON，并将 Coder 的每次生成结果持久化为文件，后续只用文件路径引用。

## 可复用建议

- **预设测试骨架**：为项目提供一份固定的 Playwright fixture 模板（包含登录态维持、baseURL 配置），Agent 只负责填充测试用例 body。这减少了生成偏差。
- **Prompt 片段模块化**：把 Explorer 的探索指令、Coder 的选择器策略、Reviewer 的错误分类标准都作为可复用 snippet，存储在项目仓库中，随 MCP 配置一起加载。
- **MCP 隔离环境**：Playwright MCP 连接到一个独立浏览器上下文，与日常开发浏览器隔离，避免 Cookie 污染或配置冲突。
- **人工关门控制**：Agent 产出的测试应作为 PR 的一部分，需经过人类 review。不建议直接接入 CI 触发部署，除非已有基线通过率验证。
- **版本锚定**：生成的测试文件顶部注释记录生成时的应用版本、Agent 配置哈希，便于未来回溯失效原因。

## 总结

Agent 协作让 E2E 测试的生成从“一次性预言”变成了“可修正的草案”。真实性的提升不来自于模型更强，而来自于**给了它反馈通道**。目前这套流程仍需人类在关键节点把关，但已经能把一个测试文件的前期探索和编写时间从小时级压缩到 10-15 分钟。对于快速迭代的项目，这种工程化的 AI 辅助，比单纯追求全自动更务实。
