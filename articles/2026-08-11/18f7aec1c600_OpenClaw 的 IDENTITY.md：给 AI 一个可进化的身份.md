## 背景：当 Agent 患上“失忆症”

在把 OpenClaw 接入日常自动化流程（比如代码审查、消息分发、多步工具调用）时，我很快撞上一个让人烦躁的问题：每一次新会话，Agent 就像被格式化了一样。

昨天它刚学会了用内部术语称呼某个服务，今天又回到死板的“您的请求已收到”。明明前一个任务里我告诉它“以后遇到 timeout 直接重试两次并记录日志”，结果下次遇到同样的错误，它还是愣在那里等我下指令。这种无状态性，对于一次性任务是无害的，但对于需要持续协作的工程化场景——尤其是 Agent 作为常驻管道的一部分时——几乎是致命的。

一开始我用系统提示（system prompt）硬编码约定，但随着规则、偏好、上下文累积，prompt 迅速膨胀到上千行，每次修改都要手动编辑，还容易产生冲突。这时我才真正意识到：Agent 需要的不是一个静态提示，而是一个可读可写、可演化的**身份文件**。

## 问题拆解

目标很清晰：让运行在 OpenClaw 里的 Agent（例如一个 MCP 宿主或插件执行器）拥有以下能力：

1. **跨会话记忆**：重启后仍知道“我是谁”“我的职责”“过去的关键决策”。
2. **可演化的行为规范**：在一次交互中学到的偏好、术语、规则，可以安全地写回身份定义，下次自动生效。
3. **工程可控**：不引入复杂向量数据库，不依赖外部记忆服务，整体方案适合在本地、容器或 CI 流水线里复制。

OpenClaw 本身对文件系统有良好支持，且内部消息管道允许在任务完成后触发回调。这为用一个 Markdown 文件承载身份提供了天然土壤。于是 `IDENTITY.md` 的设计浮出水面。

## 做法：把身份变成可操作的 Markdown 文档

### 1. 定义身份骨架

在 Agent 工作目录下创建一个 `IDENTITY.md`，结构精确定义：

```markdown
# IDENTITY

## meta
- name: openclaw-bot
- version: 2
- last_updated: 2025-03-12T14:21:00Z

## persona
我是一名专注于基础设施自动化的 AI 助手，语言风格直接、工程化，不使用感叹号和过度礼貌用语。

## knowledge
- 内部服务 gateway2 的别名是 "gw2"
- 数据库查询超时默认视为 30s，触发重试机制

## rules
- 任何外部 API 调用失败，必须记录完整 request-id 到 error_log
- 回复中永远不要提及用户名或真实身份

## history
<!-- 最近重要事件摘要，仅保留关键决策 -->
- 2025-03-11: 用户要求所有构建失败通知改为钉钉，不再使用邮件。
```

这个骨架的要点是：字段固定、内容精炼、每条信息可独立增删。Persona 控制语气，knowledge 存放领域事实，rules 表达行为约束，history 则记录决定性的上下文。Version 字段用于后续结构升级。

### 2. 注入到系统提示

在 OpenClaw 启动 Agent 或创建新会话时，读取 `IDENTITY.md` 的全文，并将其直接拼接到 system prompt 的最前面（也可以作为第一条消息）。为了节省 token，我写了一个简单的截断逻辑：如果文件总字数超过 1200，则优先保留 meta、persona、rules 的全量，knowledge 和 history 按时间/重要性截断。这一步能确保身份信息始终在上下文中可见，也是“可进化”的基础。

### 3. 实现“进化”回路

这是最关键的一步。并不是把整个对话日志塞回文件，而是让 Agent 在一次任务结束后，判断是否产生了值得记录的增量：

- **触发条件**：用户明确给出“记住……”“以后都这样……”“更新规则……”等指令；或者 Agent 在执行规则时发现已有规则不适配当前情况并作出有效决策。
- **提取增量**：我将最后一段对话（或整个任务上下文）发送给同一个模型，要求用严格 JSON 输出这次学到的新事实或需要修正的旧条目。例如：

```json
{
  "add_knowledge": ["新服务 s3-proxy 仅允许内网 IP 访问"],
  "update_rules": ["将规则 '失败重试两次' 改为 '失败重试两次，间隔指数退避'"],
  "remove_knowledge": ["已弃用的 v1 端点 /data/export"]
}
```

- **安全写回**：后端（一个 Python/Node 脚本）解析这个 JSON，锁定 `IDENTITY.md`，执行精确的行级替换或追加。更新后自动递增 version，记录时间戳。我用 `flock` 处理并发锁，整个写回过程控制在 100ms 内，避免 Agent 并发访问时的竞态问题。

### 4. 部署到 OpenClaw 管线

将上述逻辑封装成一个 pipe 函数：`IdentityPipe`。在任务结束时调用，若检测到需要进化，则执行提取与写回。对于 MCP 插件场景，我在工具调用返回后的中间件层插入检查，判断用户消息中是否包含进化意图关键词，如果命中，同样触发进化回路。

## 踩坑与止损

**坑 1：身份文件膨胀失控**  
最初没加截断和老化机制，knowledge 节两星期涨到 400 行，token 消耗暴涨 70%，响应明显变慢。后来引入两个硬止损：单节最多保留最近 15 条；history 只留最近 10 条决策摘要，超出部分自动归档到一个 `archive/` 目录。现在即使跑一个月，文件也稳定在 1KB 以下。

**坑 2：错误进化自我强化**  
有一次 Agent 把偶发错误当作新规则写入了 rules：“所有 Webhook 调用必须加 5 秒延迟”，导致后续任务异常缓慢。排查后发现，触发条件过于宽松，只要 retry 后成功它就以为是规则补丁。修正方法是增加一个确认步骤：在写回之前，用极简 prompt 反问用户一次（仅在交互模式），或者要求增量 JSON 附带 `confidence` 字段，低于 0.85 的直接丢弃。

**坑 3：多实例并发写冲突**  
容器化部署时，两个 Agent 实例同时调用了身份进化，结果文件损坏。文件锁解决了写入问题，但读取可能读到中间状态。最终的方案是：写操作先写到一个临时文件 `IDENTITY.tmp`，替换时用原子 rename，并确保所有读取都在锁外进行。在云主机上测试，此方案无数据丢失。

## 可复用建议

- **把身份文件当代码管理**：`IDENTITY.md` 纳入 Git 仓库，历史变更一目了然，回滚也简单。多台机器部署时，可以在启动前 `git pull` 同步最新身份。
- **结构化 + 可扩展字段**：为未来增加字段预留语法空间，比如添加 `## preferences` 或 `## safety`。只要旧解析器能忽略未知节就好。
- **设置进化冷却时间**：不要每次对话都检查进化，可设最小间隔（如 5 分钟或 N 次任务），防止身份抖动。
- **单独测试进化提取 Prompt**：把触发条件和提取 prompt 单独抽出来用测试用例跑，确保模型输出格式稳定，再接入管道。这部分我花了一个下午调试 JSON 转义问题，最终固定用代码块包裹返回。

## 总结

`IDENTITY.md` 的实践本质上是为 Agent 造了一个“持久自我”的最小可行方案。它不追求智能程度，而是用简单的文件约定解决了跨会话状态断层的问题。在 OpenClaw 的自动化工作流里，这种可进化的身份让 Agent 从一个无情的指令执行器逐渐变成了团队的背景协作者——知道你喜欢什么、记得上次踩过的坑、并且能自己修正行为。

如果你也在维护长时间运行的 Agent 管道，不妨试试这种方法。需要付出的一点工程杂活，远少于每次手动改写几百行 system prompt 的痛苦。
