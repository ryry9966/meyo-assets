## 背景

在 OpenClaw 里为 Agent 或插件编写自动化任务时，最先碰到的一个选择就是：用 **cron** 还是用 **heartbeat** 来触发任务？两者都能在后台周期性地启动你的逻辑，但行为模型完全不同。选错不但会让任务执行次数出现偏差，还可能引发并发冲突或监控盲区。

如果你已经在 OpenClaw 的 `plugin.yaml` 里写过类似配置，一定见过这种结构：

**cron 触发**
```yaml
triggers:
  - type: cron
    expression: "0 */10 * * *"  # 每 10 分钟整点执行
    handler: sync_calendar_task
```

**heartbeat 触发**
```yaml
triggers:
  - type: heartbeat
    interval: 600s               # 每隔 600 秒执行一次
    handler: health_check_task
```

从表面看，它们都会「每 10 分钟跑一次」，但在实际运行时，两个任务的行为会出现本质分歧。

## 问题：行为差异藏在哪？

假设一个任务执行耗时不定，可能 2 分钟，也可能 12 分钟。  

- **cron** 定时器是基于**日历时间**触发的。到点就启动一个新实例，完全不管上一个是否还在跑。
- **heartbeat** 的间隔是基于**上次执行结束时间**的。它会等你跑完，再开始计时下一个间隔。

用一个时间轴对比，差别立刻显现：

```
cron (每 10 分整): 10:00→10:10→10:20…
心跳 (间隔 600s): 上次结束 + 600s → 下次启动
```

如果任务第一次从 10:00 跑到 10:12，cron 仍会在 10:10 启动一个新实例，出现两个任务重叠执行。而 heartbeat 会在 10:12 结束后计时 600 秒，下一次启动大约在 10:22。

## 做法：如何正确选型

### 1. 任务有严格的时间边界（日历点）
需要「每天 9:00 提前 5 分钟发提醒」「每小时 30 分抓一次数据」这类场景，**cron 表达式的语义天然匹配**。它保证无论任务执行快慢，触发时刻固定在日历墙上的刻度。  
但你必须处理前一个实例未退出的情况——cron 不提供内置的互斥机制。

### 2. 任务需要固定间隔，且不能重叠
像「上次同步完成后等 30 分钟再同步」、执行健康检查、拉取消息队列时，heartbeat 是更安全的选择。它天然避免并发，且下一次执行时间依赖实际完成时间，不会因为任务变慢而疯狂堆积实例。

### 3. 权衡精度与资源
cron 会带来更高的瞬时资源占用（可能同时跑多个实例），heartbeat 则可能随时间累积偏移（任务执行 5s、间隔 600s，实际周期 605s，越来越晚）。

## 踩坑点

### 坑 1：cron 并发实例爆炸
如果一个 cron 任务因为上游慢、网络抖动，执行时间突然从 30s 涨到 12 分钟，下一个触发点到来时依然会启动新实例。默认无保护，可能瞬间打满 OpenClaw 的 worker 池，甚至造成内存溢出。  
**解决**：在 handler 入口加分布式锁（如 Redis `SETNX` + 过期时间），或配置 OpenClaw 的 `max_concurrent: 1`（如果框架支持）。

### 坑 2：heartbeat 任务被「卡死」拖垮调度
heartbeat 缺乏绝对时间检查。如果任务内部死循环不返回，或者被 sql 查询永久阻塞，调度器会一直等它结束，下一个周期永远无法开始。这比 cron 更隐蔽——cron 至少会在下个整点再试。  
**解决**：给 heartbeat handler 加超时 context，并在外层设置 `timeout`（例如 heartbeat 间隔 600s，handler 超时设为 500s），强行中断异常任务。

### 坑 3：cron 时区陷阱
OpenClaw 容器默认 UTC，但业务常按北京时间理解 cron。`0 9 * * *` 会被解析成 UTC 早上 9 点，北京下午 5 点。很多故障就是「为什么任务没在预想时间触发？」  
**解决**：显式声明时区，例如 `timezone: Asia/Shanghai`，或在表达式中直接写 UTC 偏移。

### 坑 4：heartbeat 间隔不是精确周期
如果你的任务是「每分钟执行」，但执行本身耗时 5s，heartbeat 会变成 65s 一次。这种累积误差在长时间运行后会明显偏移，不适合需要严格均匀采样的场景。

## 可复用建议

- **统一套用 Execution Wrapper**：无论选哪种触发方式，都在 handler 外层包裹统一的日志记录、异常捕获、指标上报。可以写一个 `safe_wrap` 装饰器，记录 `start_time`, `end_time`, `duration`, `success` 等字段，这样两种触发方式的监控基线能复用。
- **外部依赖缓存连接**：无论是 cron 还是 heartbeat，不要在每次触发时重新建立数据库连接或 HTTP 客户端。利用 OpenClaw 插件的 `on_load` 生命周期初始化连接池，handler 内直接取用。
- **幂等性设计前置**：cron 的重复执行风险，要求任务逻辑必须幂等。最简单的方法是引入业务唯一键（如执行窗口标识 “2025-03-17-14:00”），结合数据库去重写入。
- **混合使用场景**：有时需要 cron 做「整点同步」，heartbeat 做「异步后处理」。不要试图用一个触发类型覆盖所有需求，复杂 Agent 可以配置多个触发器，互相独立。

## 总结

cron 与 heartbeat 不是「哪个更好」的问题，而是你对任务时间语义的承诺。  
- 承诺按绝对时间执行，并愿意付出并发控制成本 → cron。  
- 需要自然的串行、固定冷却间隔 → heartbeat。  
- 如果任务必须并发，但又要绝对时间，可以用 cron + 队列解耦：cron 触发只是投递消息，实际处理由消费者排队执行。

最重要的是，在插件文档或 `README` 里把任务的触发语义写清楚，避免后续维护者误把 cron 任务改成 heartbeat 后，整个系统的时序崩溃。

在 OpenClaw 生态中，理解这两种触发器的根本区别，能让你的自动化脚本从「能跑」进化到「生产可依赖」。
