## 背景

OpenClaw 社区的内容质量一直靠人工维护，但最近我们想尝试让一部分“常规动作”自动化，比如：每日精选帖子摘要、插件发布提醒、常见问题的自动回复模板。最初的想法很简单——写一个发帖机器人，每天定时从数据库或 API 拉取内容，格式化后发到社区。看似不复杂，但实际落地时踩了不少坑，尤其是在权限、内容格式化、上下文保持和多步骤编排这几个环节。

下面我会完整记录我们基于 OpenClaw + Agent + MCP 插件思路搭建这套机器人的过程，重点分享架构设计、调试时的非直觉问题，以及可复用的经验。

## 问题拆解

发帖机器人需要解决几个核心问题：

1. **认证与权限**：社区没有开放 API Key，只有浏览器 Cookie/Session 校验。
2. **内容生成与格式化**：需要把非结构化的通知转化成适合社区显示的 Markdown，同时符合版块风格。
3. **发帖流程编排**：进入版块 → 点击发帖按钮 → 填写标题/正文 → 提交，这中间涉及页面等待、防抖、验证码等。
4. **稳定运行**：长时间无人值守时如何处理 Session 过期、网络抖动、页面改版等问题。

我们没有选择直接写 Node.js/Python 脚本硬编码点击逻辑，而是想用 **Agent 思维**：把浏览器看成一个环境，让 Agent 根据指令自主完成发帖。这样后续扩展（比如改版块、改格式）只需修改自然语言指令，而不用改代码。

## 做法与步骤

### 1. 浏览器自动化基座：Playwright + MCP Server

我们使用 Playwright 作为浏览器驱动，并封装成 MCP Tool，让 Agent 通过 Tool Calling 操作浏览器。这部分参考了 OpenClaw 生态里的 `mcp-playwright` 思路，但自己实现了轻量版，重点增加了：

- **Cookie 持久化**：首次手动登录后，将 storageState 保存到文件，后续启动复用。
- **智能等待**：对关键元素（编辑器 iframe、提交按钮）加了 `waitForSelector` 和重试。

### 2. Agent 顶层编排：基于 OpenClaw 的任务 Agent

Agent 收到类似“帮我在‘工具分享’版块发一篇关于 MCP 插件更新的介绍”的任务后，会按如下计划执行：

- 步骤 1：打开社区首页，检查登录态（通过页面右上角用户名判断）。
- 步骤 2：导航到目标版块，点击“发布新主题”按钮。
- 步骤 3：填充标题和正文。正文由上游内容生产模块提供，Agent 负责调用 Markdown 预处理器，插入固定的签名和标签。
- 步骤 4：提交前截图，发送到管理员确认（可选，初期用于人工审核）。
- 步骤 5：点击提交，等待页面跳转，记录生成的主题链接。

所有步骤通过 Function Calling 的方式调用 Playwright 工具，Agent 本身只做决策和参数传递。

### 3. 内容生产与格式化

内容源来自 GitHub Webhook（插件更新通知）和内部看板。为了避免“机器人味”，我们加了一层轻量 LLM 做风格转换，但严格控制 prompt 长度，防止生成幻觉。模板示例：

```
你是一个技术社区的内容编辑。请将以下发布说明转换成一篇社区帖子：
要求：
- 标题简洁，包含核心更新点
- 正文采用 Markdown，分“更新内容”、“使用影响”、“参考链接”三个小节
- 语气专业但不生硬，不添加无关信息

输入：{{ changelog }}
```

## 踩坑实录

### 坑 1：编辑器 iframe 导致内容输入失败

社区的发帖编辑器是基于 iframe 的富文本，Playwright 默认的 `page.fill(selector, text)` 无法直接作用。需要先定位 iframe，切换到其内部，再对 `body` 执行 `fill` 或 `type`。我们一开始没注意，导致标题填上了、正文空白。解决方案是在 Agent 的工具描述里明确：对富文本编辑器，要使用“输入富文本内容”专用 Tool，内部封装 iframe 切换和 `contenteditable` 元素处理。

### 坑 2：Session 过期判断不准确

我们用 Cookie 复用时，一小时后发帖突然失败，页面返回 403。排查发现社区 Session 实际有效期只有 30 分钟，但页面依然显示登录状态，因为前端有缓存的用户信息，但后端已拒。解决方案：每次发帖前触发一个非缓存的 API（比如打开发帖草稿列表），根据返回码决定是否重新登录。Agent 会检测到 401 后自动触发 Cookie 刷新流程（调起手动登录或通知管理员扫码）。

### 坑 3：Agent 的自由度过高

一开始我们让 Agent 自行决定发帖时机和内容，结果它某天突然把“插件版本更新”的草稿加上了一段“我们可以用它来颠覆…”的营销腔。经验：必须用强约束 prompt 限定输出边界，且所有发帖内容经格式化模板后不应让 Agent 再“润色”。我们最终把 Agent 职责缩窄为“执行既定的步骤”，内容由专门的内容管线生产，Agent 仅做搬运和格式核对。

### 坑 4：发布按钮的防抖与不可点击状态

社区发布按钮在标题或正文为空时为 `disabled`。Agent 在填写完内容后立即点击，有时因编辑器仍处于 composing 状态（中文输入法）导致按钮未激活，点击无效。解决方法：Tool 内增加等待，监测按钮的 `disabled` 属性消失后再点击，并引入“点击后等待时间窗口”防止二次提交。

## 可复用建议

- **将浏览器操作原子化**：登录、导航、填标题、填正文、提交，每个工具只做一件事，Agent 负责组合。这样即使页面改版，只需修改工具内部定位符。
- **Cookie 管理独立成模块**：包含自动续期逻辑，对外暴露 `ensureLogin()` 接口。
- **发帖内容与 Agent 行为分离**：内容生成单独流水线（模板 + LLM 轻量格式化），Agent 不干预文本，避免风格漂移。
- **增加“预览墙”与人工闸门**：正式发送前截图推送到管理员通知渠道，稳定后再考虑全自动。
- **可观测性**：每个步骤记录耗时、页面 URL、截图和错误信息，便于排查。我们使用独立的 MCP 日志工具，将 Agent 的决策链完整记录。

## 总结

这套方案落地后，每日可稳定发出 2~4 篇质量一致的技术公告或摘要，人工仅需抽查。核心价值在于用 Agent 抽象了浏览器操作流程，使得发帖逻辑脱离硬编码，易于维护和扩展。但过程中也深刻体会到，现阶段 Agent 在细节控制上仍需要大量工程约束，真正的“自主”仍需要严密的护栏设计。

如果你也在用 OpenClaw 做类似的事，建议从最小闭环开始：先实现含人工确认的发帖，再逐步去掉人工节点。同时重视 Cookie 管理和富文本交互这两个“脏活”，它们往往是稳定性的最大敌人。
