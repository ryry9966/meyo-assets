# AI Agent 的权限边界：从自动执行到人工介入的工程化框架

## 1. 背景：自动化失控的代价

在 OpenClaw 等 Agent 编排环境中，Agent 通过 MCP 工具调用执行文件操作、发送 HTTP 请求、修改数据库甚至控制本地进程。能力越强，越容易触达一条隐形的红线：**哪些操作 Agent 应该自主完成，哪些必须被人类拦截？**

一个真实的教训：某自动化 pipeline 中，Agent 在清理临时数据时错误解析了路径变量，直接删除了项目根目录下的 `.env` 和部分配置文件。恢复成本远高于自动化带来的收益。同样常见的还有 Agent 擅自向外部 API 发送带有敏感信息的 payload，或者重复触发不可逆的付费调用。这些事故的根因并不是模型能力不足，而是**缺少清晰的权限边界与干预机制**。

## 2. 问题定义：二分法失效

将决策简单地划分为 “AI 干的” 和 “人类干的” 在实践中根本行不通。真实场景下，操作的自主性取决于三个维度的组合：

- **风险等级**：操作是否可逆？是否涉及敏感资源？
- **上下文置信度**：Agent 对当前意图的理解是否足够确定？
- **业务容忍度**：中断等待人类审批所带来的延迟是否可接受？

如果用硬编码 if-else 管理边界，随着工具数量增长，规则会迅速膨胀为不可维护的 spaghetti config。我们需要一套**可泛化、可观测、可插拔的决策管道**，让 Agent 在运行时动态决定：立即执行、执行但通知、挂起等待确认。

## 3. 工程落地：三级决策管道

我们基于 OpenClaw 的 MCP Client 实现了一个 **Triage Pipeline**，将每次工具调用推入三个连续的决策阶段。

### 阶段一：静态风险标记（MCP Tool Manifest）
在 MCP Server 注册工具时，为每个工具增加自定义 annotations：

```json
{
  "name": "delete_file",
  "annotations": {
    "risk": "high",
    "reversible": false,
    "category": "filesystem"
  }
}
```

Agent 启动时将这些元数据加载到策略引擎（一个驻留内存的规则集）。高风险工具默认进入“请求确认”队列。

### 阶段二：上下文置信度计算
在工具调用前，Agent 将当前任务目标、历史上下文和待执行参数一起送入一个轻量评估器（可以是基于规则的，也可以是同一 LLM 的自省提示）。输出 0-1 的置信度分数。

```
Prompt: "你即将调用 delete_file，目标是清理临时缓存。
         当前路径解析为 /project/.cache/tmp/，操作是否安全且必要？仅返回置信度 0-1。"
```

如果 `risk=high & confidence<0.9` 或 `risk=medium & confidence<0.6`，则路由到人工确认节点。

### 阶段三：执行与降级
对于通过的调用，Agent 直接执行并异步写入审计日志（包括决策理由）。对于需要确认的调用，通过 OpenClaw 的 `ask_user` 原语中断当前流水线，在 UI 中以卡片形式呈现工具名、参数、风险摘要，等待人类批准/拒绝/修改参数。

踩坑提醒：不要让 `ask_user` 无限期阻塞整个编排流程。建议配置超时策略，到期后选择最安全的降级动作（如跳过该步骤或使用只读替代方案）。

## 4. 踩坑与反模式

### 坑一：“always ask” 策略的麻痹效应
为求安全，把所有写操作都设为需确认，结果 Agent 每执行两步就中断一次，用户变成“点击批准机器”，自动化名存实亡。**纠正：**引入风险分级后，仅高风险 & 低置信度组合才挂起，低风险的文件写入（如写入 `/tmp/log`）直接放行。

### 坑二：忽略工具的隐式副作用
有些 MCP 工具看起来无害（如 `run_shell` 携带限定命令），但实际上允许传参。Agent 可能注入 `&& rm -rf` 之类的链式调用，绕过参数检查。**对策：**永远在 MCP Server 侧做参数白名单校验，而不是仅依赖 Agent 自主约束。

### 坑三：审计日志形同虚设
记录了大量 JSON 却不包含决策理由，事后无法定位为何某个高危操作被执行。**要求：**每条日志附上 `risk_level, confidence, policy_version, final_decision` 字段，并保留快照。

## 5. 可复用建议

- **从 MCP annotations 开始**：这是你控制边界的唯一真源。用 `risk`、`reversible`、`category` 建立工具元模型。
- **用开放世界假设设计降级**：当置信度处在灰色区域时，提供“执行但只读”或“执行但限制速率”的选项，比二选一更灵活。
- **在 OpenClaw 内实现可观测的决策点**：把决策管道抽象为一个 `PolicyMiddleware`，包裹在 MCP Client 的 `callTool` 外层，便于单测和回放。
- **定期回放日志来校准阈值**：收集被拒绝但实际合理的操作案例，微调置信度阈值或补充工具的白名单场景。
- **让人类审批携带“缘由”**：不只是 Yes/No，允许人类附加一条简短指令（如“可以删，但只删 .log 文件”），让 Agent 从干预中学习。

## 6. 总结

AI Agent 的权限边界不是静态配置文件，而是一个需要持续运行的**决策服务**。通过 MCP 工具风险标注、上下文置信度评估和分级确认机制，我们能够在自动化效率与安全可控之间找到动态平衡点。在 OpenClaw 生态里，你可以用少量代码实现这一模式——它比事后补救的护栏更廉价，也比完全信任模型更可靠。

**关键提醒：**界限的最终评判者仍是人类，但人类不该充当“机械式审批者”。设计系统时，请确保每一次打断都是高价值、有上下文的，否则 Agent 很快就会沦为穿着自动化外衣的远程遥控器。
