## 背景：被动对话的局限

现在大部分 AI 助手仍工作在“提问-回答”模式。用户给出指令，模型调用工具、返回结果，然后继续等待。这在很多场景下已经够用，但在持续维护类任务中（例如监控仓库状态、收集晨间信息、处理周期性告警），被动式交互会拖慢整个工作流，让人被迫充当“传话人”。

OpenClaw 这类 Agent 平台天然支持多步执行与工具编排，但多数实践仍止步于响应式。事实上，配合事件触发器与 MCP（Model Context Protocol）工具，完全可以构建出 **proactive**——不等你开口，根据条件主动完成任务的助手。本文就基于真实工程踩坑经历，拆解一条可复用的路径。

## 问题：主动触发时该做什么、怎么做安全

核心矛盾不在于“能不能自动调用工具”，而在于三点：

1. **何时触发** —— 靠轮询还是事件推送？
2. **触发后做什么** —— 如何避免模型在无上下文时执行低质量或危险操作？
3. **如何收束** —— 怎样防止大批量误操作，并保留必要的确认机制？

下面以“GitHub 新 Issue 自动分诊与预回复”为例，说明如何在 OpenClaw 中落地一个真正的 proactive agent。

## 做法与步骤

### 1. 感知：从事件到触发器

选择事件源：我们使用 GitHub webhook 监听新建 issue 事件，将其推送到一个轻量服务，该服务把事件打平成统一格式，写入 OpenClaw 的触发队列。避免直接暴露 webhook 给 Agent，因为需要做去重和格式归一化。

去重上，为每个事件计算 `repo_full_name + issue_id + action` 的幂等键，缓存 5 分钟，防止网络重复投递。

### 2. 能力：用 MCP Server 暴露工具

需要主动操作的 GitHub 接口封装成 MCP 工具，例如：
- `get_issue_detail(owner, repo, issue_number)`
- `add_labels(owner, repo, issue_number, labels)`
- `comment_on_issue(owner, repo, issue_number, body)`
- `assign_user(owner, repo, issue_number, username)`

所有写操作工具的描述中明确标注“必须经过安全检查才可调用”。MCP Server 本身运行在与 Agent 分离的进程里，持有 least-privilege 的 GitHub token（仅限指定仓库，且无删除权限）。

### 3. 代理逻辑：从触发到决策

在 OpenClaw 里创建一个 proactive agent，配置：
- **触发器**：绑定上述队列的 issue 创建事件。
- **系统提示**：要求模型先调用 `get_issue_detail` 理解内容，再按规则输出 JSON 格式的 `action_plan`，包含建议标签、是否需要回复、回复模板变量填充等。
- **执行链**：agent 调用 MCP 工具之前，需经过一个内置的安全过滤器，检查操作类型。只允许白名单标签、只能使用预置回复模板，禁止自由撰写可能产生误导的内容。

安全过滤器的实现很简单：解析 agent 产出的工具调用参数，如果标签不在预定义集合，或想自行拼接 commit message/回复内容，则拒绝执行，并记录告警。

### 4. 安全与反馈回路

对于首次出现的低置信度决策（模型自己判断信心分 < 0.8），agent 不直接写操作，而是通过 MCP 工具向即时通讯（例如 Slack）推送一条卡片消息，让维护者一键确认或驳回。这样保留了“人机回路”，但不要求人时刻在线。

## 踩坑点

- **重复事件导致刷屏**：没做好幂等去重时，一次 webhook 可能触发多次执行，瞬间一堆重复评论。除了幂等缓存，还要在 agent 里判断 issue 是否已被它处理过（检查有无特征标签）。
- **权限过热**：给了写权限后，模型幻觉输出了一个 `close_issue` 调用，幸好 MCP 工具根本不含该能力，否则会直接关 issue。最小权限原则是最后一道防线。
- **上下文缺失**：agent 只看单个 issue 标题和正文，缺乏项目级元信息（如 CONTRIBUTING、已有标签体系）。解决方法是增加一个 `get_repo_meta` 工具，在分析前拉取规则文件，注入到临时系统提示。
- **触发风暴**：当外部系统批量迁移 issue 时，瞬间涌入大量事件，打爆 OpenAI API 速率限制。需要实现任务队列限流，同一仓库每分钟最多处理 3 个事件。

## 可复用建议

1. **把 proactive 行为看作状态机**：每个事件经历“接收→去重→分析→决策→安全校验→执行或转人工”，状态可追溯，方便排错。
2. **冷却与静默**：给每个自动化动作设置冷却期，同一操作（如同一标签添加）在 10 分钟内不重复触发。
3. **先读后写，能快照就快照**：调用写工具前，强制要求 agent 先获取最新状态（如当前已有标签、已有评论列表），避免覆盖人工操作。
4. **审计日志**：把所有自动执行的动作和对人发出的确认请求集中在一条 dedup key 下，方便复盘。
5. **逐步放权**：新 proactive 规则先以 dry-run 模式运行一周，只观察并记录计划操作，验证无奇奇怪怪行为后再放开执行。

## 总结

一个工程上可用的 proactive agent，不是“模型够聪明就会自己做事”，而是通过事件去重、最小权限、人机确认回路、冷却机制和可追溯设计，把能力放进安全的笼子。用 OpenClaw + MCP 的组合，你可以像搭积木一样把各种触发源和工具拼在一起，但安全边界必须自己筑起。

主动式助手真正的价值在于把重复的判断和操作从人的时间里剥离，而不是追求 100% 自动。当它能默默替你分诊 issue、汇总状态、监控关键指标，你就能把精力留给设计、决策和更高阶的工作。这就是 proactive 在工程里的恰当位置。
