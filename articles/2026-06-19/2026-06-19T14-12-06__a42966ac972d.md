最近社区里炸开锅的一条消息：OpenAI 的 Codex 开始具备"自动生成 skill"的能力——也就是说，AI 不再只是按你的指令一次次重新思考，而是可以把重复性的任务**沉淀成一个可复用的技能**，下次遇到类似场景直接调用。听起来好像没什么了不起？但这背后其实牵涉到一个相当根本的转变：从"会聊天的 AI"，到"会自己造工具的 AI"。今天就来掰开揉碎聊聊这事儿。

## 什么是 "skill"，以及它和 prompt、function、agent 的区别

在大模型生态里，"skill"这个词已经被用得有点泛滥了，先做个梳理：

- **Prompt**：一段提示词，告诉模型这一次该做什么。一次性的，写完就扔。
- **Function / Tool calling**：开发者预先定义好的函数（比如查天气、发邮件），模型根据上下文决定调用哪个、传什么参数。
- **Agent**：一个能感知环境、规划步骤、调用工具的循环执行体。
- **Skill**：介于 prompt 和 function 之间的一种"中间产物"。它通常包含三部分——**触发条件**（什么时候该用）、**执行流程**（一套打磨过的提示词或代码片段）、**输入输出契约**（怎么调用、返回什么）。

举个具体例子：你让 Codex 帮你写代码，发现每次调试 Python 异常的时候，它的套路都差不多——先复现、再二分定位、最后给修复方案。如果把这个套路固化成一个名为 `debug_python_traceback` 的 skill，下次它直接调用，不用每次重新"想"一遍。

这就是 skill 的价值所在：**把模型每次都要重新推理的隐性流程，变成显式可复用的资产**。

## Codex 自动生成 skill，到底"自动"在哪

以前要做一个 skill，基本流程是这样的：

1. 工程师观察到一个高频任务
2. 手写一份 prompt 模板或工作流
3. 测试、调参、加 few-shot 样例
4. 上线，监控效果，再迭代

这一套走下来，少则几小时多则几天。Codex 这次更新的关键，是把这条链路"内化"了。根据公开信息，它的自动生成机制大致包含以下几个环节：

- **行为观测**：在沙箱中执行任务时，记录每一步的 reasoning trace、工具调用、错误回滚
- **模式提取**：识别出在多次任务中反复出现的相似子流程（比如"读 README → 装依赖 → 跑测试"）
- **技能蒸馏**：把这些子流程压缩成一段更紧凑、更通用的执行模板，并自动写一段自然语言描述说明它干嘛用
- **注册与索引**：把生成的 skill 存入一个可检索的库，下次任务规划时优先匹配
- **效果反馈**：调用过的 skill 如果失败率上升，自动降权或触发重写

这个闭环最有意思的地方在于第 4 步和第 5 步：**模型不仅在使用工具，还在管理自己的工具库**。这有点像一个程序员一边写业务代码，一边顺手把通用逻辑抽成 utils 包——只不过这次抽包的是 AI 自己。

## 为什么这件事值得重视：从"思考"到"沉淀"

你可能会问：这跟传统的缓存、记忆机制有啥区别？我觉得有几个本质差异：

**1. 抽象层级不一样**

- 缓存：记住"上次问 X，答案是 Y"
- 记忆：记住"这个用户喜欢简洁回答"
- skill：记住"遇到这类问题，应该走这套流程"

前两者是"事实"和"偏好"，skill 是"方法论"。方法论的复用价值远高于单点事实。

**2. 推理成本结构变了**

大模型的算力消耗，很大一部分浪费在重复推理上。同一个用户每天问 10 次类似问题，模型每次都要从零开始组织思路。如果把高频路径固化成 skill，命中后等于走一条"高速公路"，token 消耗和延迟都能显著下降。有团队的内部测试显示，引入 skill 缓存后，常见任务的端到端延迟可以降到原来的 30%~50%。

**3. 它让 AI 系统具备了"经验积累"的雏形**

人和动物的智能优势，很大程度来自经验沉淀——婴儿学会抓握之后，不需要每次重新发明一套手指控制算法。过去的 LLM 每次对话基本是"失忆状态"，而 skill 机制相当于给它配了一本不断增厚的"工作笔记"。这不是 AGI，但确实在朝那个方向挪了一小步。

## 风险与边界：自动生成不等于自动正确

吹完了得泼点冷水。自动生成 skill 听起来很美，工程上其实有几个相当头疼的坑：

- **错误固化**：如果某次任务用了一个**碰巧能跑通的烂方案**，被蒸馏成 skill 之后，未来所有类似任务都会走这条歪路。坏习惯比没习惯更难改。
- **组合爆炸**：skill 库无限膨胀，检索和选择本身会变成新的瓶颈。这就像你电脑里装了 200 个 VS Code 插件，启动反而变慢。
- **安全面扩大**：如果 skill 中混入了对敏感命令的调用（比如 `rm -rf`、对外发请求），且权限边界没设好，相当于给攻击者开了一个新的注入入口。Prompt injection 在 skill 时代会变成 "skill injection"。
- **可解释性下降**：人类很难审计一个 AI 自己生成的 skill 库——条目太多、措辞太"AI 味"，出了问题排查极其痛苦。
- **版本治理**：模型升级后，旧 skill 还兼容吗？这是软件工程里 API 兼容性问题的 AI 版。

业界目前的应对思路，主要是**沙箱执行 + 引入人工 review 关卡 + skill 评分淘汰机制**。但这些都还远未成熟，可以预见未来一两年会出现一波"AI skill 治理"相关的工程实践和工具链。

## 普通开发者和重度用户该怎么看

这事不只是大厂的游戏。对一线开发者和深度使用 AI 的人来说，有几个直接影响：

- 编辑器里的 AI 助手会越来越"懂你的项目"，因为它会沉淀针对你代码库风格的 skill
- 同样的订阅费，未来能完成的复杂任务量会显著上升（高频任务走快速通道）
- 但反过来，**调试 AI 的成本也会上升**——出问题时你得搞清楚是模型本身的问题，还是某个 skill 的问题

## 三条冷思考

1. **不要神化"自动"**。AI 自动生成 skill，本质上是把人类工程师做过 N 次的归纳工作搬到了模型内部，并不意味着它生成的就比人写的好。短期内，**人写的高质量 skill + AI 自动补全长尾 skill** 才是最优组合。

2. **关注"可观测性"胜过关注"能力上限"**。下一阶段 AI 工程的真正难点，不是模型多聪明，而是当它的行为越来越复杂时，你能不能看清它在干什么。如果你正在构建 AI 应用，现在就该把日志、trace、skill 调用链这些基础设施补上。

3. **重新审视自己的工作流**。AI 既然能从重复任务里提炼 skill，你也应该问自己：**我每天有哪些工作是值得被"skill 化"的？** 哪怕不交给 AI，把它写成 checklist、脚本或模板，本身就是生产力的复利。

skill 这套机制最终会跑多远还很难说，但有一点可以肯定——AI 已经从"回答问题"的阶段，走到了"为自己造工具"的阶段。下一步是什么？也许是 AI 开始为自己造"项目结构"、造"团队协作模式"。听起来还挺科幻，但回头看，两年前的我们也想象不到现在的样子。
