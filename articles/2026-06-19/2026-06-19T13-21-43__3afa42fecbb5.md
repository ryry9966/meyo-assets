最近 36kr 报道了一家做了 21 年的老牌企服公司，把 AI Agent 接进自家业务流程跑了一轮实验。这事儿在朋友圈刷了一波，但讨论大多停留在"AI 替代人"的口水仗上。其实更值得聊的是：一家有历史包袱的传统软件公司，为什么要做这件事？Agent 在真实企业流程里到底能干什么、卡在哪里？这篇我们抛开口号，把里面的工程问题掰开聊。

## 老企服公司为什么要折腾 Agent

先说背景。一家做了 21 年的企服公司，意味着它身上至少压着这么几座山：

- **庞大的存量代码**：老系统通常是 Java/Spring 全家桶 + 关系数据库，业务逻辑散落在几十个微服务里，重写成本极高。
- **客户的合同惯性**：To B 客户一旦签下来，每年续费、定制开发，不会轻易迁走，但也意味着你不能随便改产品形态。
- **定制化债务**：每个大客户都有几十上百个"特殊需求"，沉淀在配置项、工作流、报表模板里，活的文档几乎没有。

在这种背景下，Agent 是"性价比最高的一次升级"。原因有三：

1. **不需要重构底层**：Agent 调用的是已有 API、已有数据库视图，本质是套了一层"会自然语言的壳"。
2. **客户感知强**：从输入表单变成对话，演示效果立竿见影，销售好讲故事。
3. **沉淀客户知识**：客户和 Agent 的每次交互，都是一次对真实业务流程的"反向标注"，对老厂商来说是金矿。

所以这不是赶时髦，是商业上算得过来的账。

## Agent 跑流程，到底在跑什么

很多人对 Agent 的理解还停留在"会聊天的 ChatGPT"。在企业流程场景里，Agent 的工作其实更像一个"会用键盘鼠标的实习生"。

一个典型的企服 Agent，至少包含以下几层：

- **意图理解层**：把"帮我把上个月华东区销售前 10 的客户拉个回款分析"翻译成结构化任务。
- **规划层（Planner）**：把任务拆成子步骤——查客户表、过滤区域、聚合销售额、Join 回款表、生成图表。
- **工具调用层（Tool Use）**：通过 Function Calling 调内部 API、SQL、报表引擎，甚至直接 RPA 操作浏览器。
- **记忆与上下文**：维护对话历史、用户偏好、组织权限。
- **反思与纠错（Reflection）**：上一步报错了，自己读 traceback、改参数、重试。

以那家老企服公司的实验为例，他们让 Agent 跑通的是一个"客户报销审批"的全流程：员工提单 → 自动校验票据 → 匹配预算科目 → 路由到对应审批人 → 入账。原本需要 3~5 个角色协作、平均 2 天完成的事，Agent 全自动跑完一个 case 花了大约 6 分钟。

但注意——这是"演示 case"。真实场景里的坑，下面再说。

## 真正的难点：不在模型，在"上下文工程"

业内有个说法：2023 年大家拼 Prompt Engineering，2024 年拼 RAG，2025 年拼的是 **Context Engineering**——也就是怎么把对的信息、在对的时机、以对的格式喂给 Agent。

企服场景的硬骨头集中在这几块：

- **权限边界**：财务总监能看到的数据，普通员工不能看。Agent 必须在每一次工具调用里都带上正确的身份令牌，否则就是合规事故。
- **数据语义**：同一个字段"客户名称"，在 CRM 里叫 `cust_name`，在 ERP 里叫 `customer_full_name`，在合同系统里是中英混写。Agent 需要一份"语义层"（Semantic Layer）来做翻译。
- **流程的隐性规则**：报销超过 5000 要走总监，超过 50000 要走 CFO，跨部门项目还要加签——这些规则有的写在制度里，有的只存在于老员工脑子里。
- **失败成本不对称**：Agent 多查一次数据没事，但错误地批了一笔款、删了一条订单，代价是真金白银。

这家公司的实验里，他们做了一件挺聪明的事：**把 Agent 的"动作"分成三档**——只读（直接执行）、可逆写（执行但记录补偿事务）、不可逆写（必须人工二次确认）。这其实就是数据库 ACID 思路在 AI 时代的翻版。

## 数字背后：Agent 的真实 ROI 长什么样

聊点干的。结合公开报道和行业里几个类似案例，企服 Agent 的 ROI 大致呈现这样的分布：

- **重复性高、规则明确的流程**（报销、考勤、工单分派）：人效提升 40%~70%，是目前最容易落地的甜点区。
- **需要跨系统取数的分析任务**（经营报表、客户画像）：节省 50% 以上的取数时间，但生成结论的准确率仍需要人复核。
- **需要判断和谈判的环节**（合同审核、客户投诉处理）：Agent 目前只能做"初稿"，最终决策仍在人。准确率从纯人工的 ~95% 掉到 Agent 草稿 + 人复核的 ~92%，但总耗时下降。
- **强创意类工作**（品牌策划、战略规划）：基本帮不上忙，别硬上。

还有一个容易被忽略的成本项：**Token 成本不是大头，运维和数据治理才是**。一次复杂任务平均消耗几万 Token，按现在的 API 价格算下来不到一块钱；但为了让 Agent 跑得稳，你需要补齐数据字典、API 文档、测试集、Eval 框架——这些隐性投入往往是 Token 费用的 10~50 倍。

## 历史的回声：这不是第一次"流程自动化"

往回翻历史，这种"用新技术重写流程"的事情其实发生过好几轮：

- **2000 年代的 ERP 浪潮**：把纸质流程电子化，号称提效 50%，但很多公司付出了"按 SAP 的流程改自己业务"的代价。
- **2010 年代的 BPM/工作流引擎**：让流程可配置、可视化，但配置复杂度本身又成了新的门槛。
- **2018 年前后的 RPA**：脚本机器人模拟人操作，灵活但脆弱，UI 一变就崩。
- **现在的 LLM Agent**：理论上能理解意图、自适应变化，但确定性比 RPA 差。

每一次浪潮，最后落地最好的，都不是"全替换"，而是"和上一代共存"。Agent 也一样——未来三年大概率会出现一种混合架构：**Agent 做意图理解和编排，RPA/API 做确定性执行，BPM 做合规审计**。

## 三条冷思考

最后给三条不太会出错的判断：

1. **别迷信端到端 Agent**：在企业流程里，端到端意味着失败时无法定位。把 Agent 拆成"规划 + 多个确定性工具"，可观测性、可回滚性、可审计性都会好得多。
2. **先建 Eval，再建 Agent**：没有评测集，所有"看起来很厉害"的 Demo 都不能进生产。先花两周时间从历史工单里抽 200 个 case，定义"什么算成功"，再开始迭代。
3. **老厂商的优势在数据和客户，不在模型**：21 年的客户行为数据、定制化经验、合规 know-how，这些才是护城河。模型可以租，业务上下文租不到。

这家老企服公司的实验，本身没什么颠覆，但传递了一个信号：**当一家做了 21 年的公司都开始动手了，说明这件事已经从 demo 阶段，走到了"必须算账"的阶段**。这对所有还在观望的同行来说，不是焦虑信号，是工程信号。
