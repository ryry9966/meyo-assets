OpenAI 这周干了两件大事。

第一件：GPT-5.5-Cyber 完全体上线，配合 Codex Security 插件和 "Patch the Planet" 计划，号称要用 AI 给全球开源项目修漏洞。听起来很燃。

第二件：Codex 被开发者扒出一个史诗级 bug——SQLite 日志疯狂写入，一年能吃掉 640TB 写入量，把一块消费级 SSD 直接写报废。

同一个星期，同一个 OpenAI。矛和盾同时出故障，有点尴尬。但这个故事比 "OpenAI 翻车了" 要深刻得多。

## GPT-5.5-Cyber：专治网络安全的「特种兵」

先说第一件事。GPT-5.5-Cyber 不是 GPT-5.5 的简单升级，而是一个专门为网络安全场景训练的模型变体。

- **定位明确**：面向关键基础设施防御者（电力、水利、金融系统），不是给普通用户用的玩具
- **能力评级**：OpenAI 内部定级为 "High"（未到最高级 Critical），在 CyberGym 基准上得分 85.6%，高于 GPT-5.5 的 81.8%
- **访问机制**：通过 Trusted Access for Cyber（TAC）项目分发，目前约 200 家早期合作伙伴在用

它能干什么？简单说：代码审计、漏洞分诊、恶意软件分析、检测工程、红队测试——凡是防守方需要的，它都能帮忙加速。

更猛的是配套推出的 "Patch the Planet" 计划。OpenAI 联合安全公司 Trail of Bits，用 GPT-5.5-Cyber 扫描全球关键开源项目。第一周就交出了这样的成绩单：

- 19 个项目中发现数百个 bug
- 提交 64 个 Pull Request，51 个 Issue
- CVE 变体分析、加密库差异测试、模糊测试——一周干完以前几个月的活

Trail of Bits 的原话很有意思："AI 找 bug 的成本已经降下来了，贵的部分变成了确认、定级、打补丁、协调披露。" 换句话说，发现漏洞不是瓶颈，处理漏洞才是。

## Codex 的「史诗级」日志 bug：640TB/年的写入量

说完了光鲜的一面，来看翻车现场。

GitHub Issue #28224 被开发者 1996fanrui 在 6 月 14 日捅了出来。核心发现很简单：

> Codex 在运行时，会以约 5MB/s（峰值 16MB/s）的速率往本地 `~/.codex/logs_2.sqlite` 写入 TRACE 级别日志。

换算一下：

- 21 天写入 37TB
- 年化约 640TB
- 一块 1TB 消费级 SSD 的标称写入寿命（TBW）约 600TB

也就是说，你什么都不干，光是开着 Codex 跑任务，不到一年就能把一块 SSD 的终身写入配额用光。

而且这个 bug 最恶心的地方在于——**它不会让你感到任何异常**。构建照常通过，Codex 照常回答问题，磁盘空间显示充足，但底层的闪存耐久度正在被悄悄抽干。就像一个慢性病，不疼不痒，等你发现的时候已经晚了。

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-06-23/c9bbbf9d660a411d.jpeg)

## 根因分析：TRACE 级别的「全量记录」失控

这个 bug 不是新问题。最早的相关报告出现在 2026 年 4 月 10 日的 Issue #17320，标题叫 "Excessive SQLite WAL writes during streaming due to TRACE logs ignoring RUST_LOG"。之后一路有人补刀：#24275、#22444、#24223……至少 8 个 GitHub Issue 描述了同一个根因的不同症状。

根因是什么？一句话：**SQLite 日志 sink 使用了全局 TRACE 默认级别，且无视 `RUST_LOG` 环境变量**。

技术细节：

- Codex 的 Rust 代码里，SQLite 反馈日志 sink 的配置是 `Targets::new().with_default(Level::TRACE)`——最高日志级别
- 正常情况下，开发者会通过 `RUST_LOG=warn` 来控制日志输出。但 SQLite 这个 sink 跑在标准 `tracing` 过滤器之外，完全不听 `RUST_LOG` 的
- 结果就是：无论你怎么设置环境变量，TRACE 级别的日志照样往数据库里灌

写入内容有多无聊？根据 Issue #28224 的分析：

- 70.7% 是 TRACE 级别日志
- 加上 `codex_otel.log_only` 和 `codex_otel.trace_safe` 两个 OpenTelemetry 类别，**96% 的写入量是普通用户永远不会打开的数据**
- 包括：inotify 事件、locale 查找、WebSocket 原始 payload、tokio-tungstenite 内部日志……

更离谱的是写入模式——"写入再删除、写入再删除"，每分钟上万次插入与清理。文件不大，但实际砸到闪存上的写入量远超肉眼所见。

## OpenAI 的修复：慢了两个月，但终于来了

在 Issue #28224 获得 285 个 👍 被 Hacker News 顶上热帖之后，OpenAI 研究员 Vaibhav (VB) Srivastav 在 6 月 23 日回应：

> "这一问题已得到修复，并随着最新 Codex 版本一同发布了。所有人务必通过 npm 或 bash 安装脚本将 Codex 升级到最新版本。"

但从时间线来看，这个修复来得确实不算快：

- **4 月 10 日**：Issue #17320 首次报告
- **4 月 ~ 6 月**：陆续 8+ 个 Issue 报告相关问题
- **6 月 14 日**：Issue #28224 附上 640TB 数据引爆舆论
- **6 月 22 日**：OpenAI 发布修复版本
- **6 月 23 日**：官方研究员公开确认

从首次报告到官方修复，两个多月。从引爆舆论到回应，不到 48 小时——舆论倒逼的效率，远高于社区自发报告的效率。这个现象本身就值得玩味。

## 对开发者的 3 条冷思考

**1. 安全模型的安全问题：当修补者自己有 bug**

GPT-5.5-Cyber 的使命是给全球代码修补漏洞，但 Codex 自身的日志系统却是个安全隐患。这不是第一次了——2023 年 Codex 发布初期就出过安全分类器误报问题（至今仍有 Issue 在报告 "正常的本地开发被标记为网络攻击"）。

给所有依赖 AI 编程工具的团队一句话：**AI 工具的代码也是代码，也会有 bug，也需要审计**。不要因为它是 OpenAI 出品就盲目信任。

**2. 日志系统设计的「经典坑」**

TRACE 级别全量输出 + SQLite 持久化 + 绕过标准日志控制——这三个要素凑在一起，就是一个经典的性能定时炸弹。社区已经给出了清晰的修复方向：

- 把 SQLite sink 从 TRACE 降到 INFO
- 对低价值依赖噪声设置过滤阈值
- 默认不持久化原始 WebSocket payload，改存摘要
- 增加全局日志数据库大小/写入量上限

如果你的项目里也有 SQLite 日志 sink，值得检查一下自己的日志级别配置。

**3. 「Patch the Planet」的真正价值不在于找到 bug**

Trail of Bits 说得很清楚：AI 找 bug 已经不是瓶颈，真正的价值在于后续的确认、定级、补丁开发、协调披露。Patch the Planet 的模式是 "AI 做初步筛选 + 人类专家做终审"，而不是 "AI 全自动修漏洞"。

这才是当前阶段 AI 安全工具的正确打开方式：**让 AI 做重复性的苦力活，把人类的判断力留给真正需要决策的地方**。
