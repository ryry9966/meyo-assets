36kr 最近报道了一条消息：Claude Code 的工程一号位（Anthropic 高管）公开给 Agent 热潮泼了盆冷水——狂烧 Token 的时代已经过去，现在该算 ROI 了。

这不是在唱衰，而是在说一个很多团队已经开始感受到的事实：Agent 很强，但强不等于划算。当你的 token 账单从每月几百刀涨到几万刀，老板问你"这东西到底帮我们赚了多少钱"的时候，你才发现——哦，原来能力 ≠ 生产力。

## Token 账单：一场没有终点的军备竞赛

先说一组直观的数据：

- GPT-4 级别的模型，输入 token 成本约 $30/百万，输出约 $60/百万
- 一个典型的 Agent 调用循环（规划 → 执行 → 观察 → 修正），单次任务平均消耗 2000~10000 token
- 如果是多轮对话、多工具调用的复杂 Agent，单次任务可以轻松烧掉 50000+ token
- 粗算一下：一个 Agent 每天处理 100 个任务，每月 token 成本在 $3000~$15000 之间

这个数字本身不算离谱，问题是：这还只是 API 成本。你还有基础设施、运维、监控、安全审计……全算上，一个 production-grade 的 Agent 系统的 TCO（Total Cost of Ownership）可以是纯 API 成本的 3~5 倍。

所以 Claude Code 团队说的"该算 ROI"，本质上是在说：**别只看 Agent 能做什么，要看它帮你省了什么、赚了什么。**

## Agent 为什么这么贵？Token 乘数效应

很多人对 Agent 的成本结构有个误解，觉得"不就是多调几次 API 吗"。实际上，Agent 的成本膨胀有一个核心机制——**Token 乘数效应**。

具体来说：

1. **规划层**：Agent 拿到任务后，要先把目标拆解成子任务，这一步本身就是一轮 LLM 调用，消耗 token
2. **执行层**：每个子任务可能需要调用工具（搜索、代码执行、API 调用），每次工具调用的结果要回传给 LLM 做判断，又是一轮 token
3. **观察层**：Agent 检查执行结果是否符合预期，不符合要重新规划，又是 token
4. **纠错层**：如果工具调用失败、返回异常，Agent 要分析错误原因并重试，继续烧 token

一个看似简单的任务——比如"帮我查一下某公司的最新财报数据并整理成表格"——在 Agent 模式下的 token 消耗可能是普通聊天模式的 10~50 倍。这还没算上你给 Agent 配的 system prompt（通常 1000~3000 token）、工具描述、历史上下文等固定开销。

更隐蔽的成本在于**上下文窗口的管理**。随着对话轮次增加，Agent 需要把越来越多的历史信息塞进 context window。如果管理不当，可能会：

- 触发 context window 上限，被迫截断历史信息，导致 Agent "失忆"
- 每轮都重新发送完整上下文，成本线性增长
- 出现"token 垃圾"——大量无用的中间步骤信息占据宝贵的上下文空间

所以问题不是"Agent 能不能做"，而是"Agent 做这件事的成本是否值得"。

## ROI 思维：从"能不能"到"值不值"

Claude Code 团队提出的 ROI 视角，其实是一个非常好的框架。我们可以把它拆解成几个维度：

### 1. 时间 ROI

- Agent 做一个任务花了 30 秒，人类做需要 30 分钟 → 节省 29.5 分钟
- 但如果这个任务每天只发生 2 次，一个月节省的时间约 29 小时
- 假设人力成本 $50/小时，月节省 $1450
- 而 token 成本 $5000/月 → **负 ROI**

### 2. 质量 ROI

- Agent 生成的代码有 5% 的 bug 率，人类有 10% → 质量提升一倍
- 但 Agent 的 bug 可能更隐蔽（看起来合理但逻辑有问题），调试成本可能更高
- 关键指标：Agent 产出的"一次通过率"是多少？需要人工修改的比例是多少？

### 3. 规模 ROI

- 如果同一个任务要执行 10000 次/月，即使单次成本高，规模效应也可能让 ROI 为正
- 但如果任务是低频的、非标准化的，Agent 的固定投入（prompt 工程、工具开发、测试）就很难摊薄

所以 ROI 计算的核心不是"Agent 能不能做这件事"，而是"这件事的频率×单次节省的成本 > Agent 的运行成本 + 固定投入的摊销"。

## 效率优先：让 Agent 从"奢侈品"变成"日用品"

既然算清楚了账，下一步就是优化。以下是一些已经验证有效的策略：

**1. 分层模型策略**

- 简单任务用小模型（GPT-4o-mini、Claude Haiku），复杂任务才上大模型
- 根据任务难度动态选择模型，成本可以降低 60~80%
- 关键：建立任务难度评估机制，别一刀切

**2. Tool-use 优化**

- 精简工具描述的 prompt，去掉冗余说明
- 对工具调用结果做预处理，只把关键信息回传给 LLM
- 实现工具调用的结果缓存，相同输入直接返回缓存结果

**3. Context 管理**

- 实现滑动窗口策略，只保留最近 N 轮的关键信息
- 对历史信息做摘要压缩，用更少的 token 表达相同的信息
- 在 system prompt 中明确"不需要重复说明的内容"

**4. 人类-in-the-loop 的精准介入**

- 不是所有步骤都需要 Agent 自主决策，关键节点引入人类确认
- 减少无意义的"探索性"尝试，让 Agent 在已知路径上执行
- 用规则引擎处理确定性高的任务，只把模糊的、需要判断的留给 LLM

**5. 建立成本监控仪表盘**

- 实时追踪每个 Agent 的 token 消耗、任务成功率、平均耗时
- 设置成本阈值告警，防止单次任务失控
- 定期复盘，找出高成本低回报的 Agent 并优化或下线

## 三个冷思考：Agent 时代的务实指南

最后，给正在用或准备用 Agent 的团队三条建议：

### 冷思考 1：先问"需不需要 Agent"，再问"怎么用 Agent"

不是所有问题都需要 Agent 解决。很多场景下，一个简单的 rule-based 自动化、一个 RPA 脚本、甚至一个写死的 shell 脚本就能搞定。Agent 的优势在于处理**模糊的、需要推理的、非结构化的任务**。如果你的任务是确定性的、结构化的，用 Agent 就像用核弹打蚊子——技术上可行，经济上离谱。

### 冷思考 2：Agent 的真正价值是"编排"，不是"执行"

很多人把 Agent 当成万能执行器，让它干所有活。但 Agent 最擅长的其实是**理解意图 → 拆解任务 → 调度工具 → 整合结果**。如果你让 Agent 亲自去写每一行代码、处理每一个 API 返回值，那它的效率大概率不如直接写代码。正确的用法是：让 Agent 做"大脑"，让确定性的工具做"手脚"。

### 冷思考 3：ROI 是动态的，要持续优化

今天的负 ROI，可能因为模型降价、你的 prompt 优化、任务频率提升而变成正 ROI。反之，今天的正 ROI 也可能因为竞争加剧、成本上升而变成负 ROI。所以不要做一次 ROI 计算就完事了——建立持续的成本监控和优化机制，才是 Agent 能否长期落地的关键。

**Claude Code 团队给 Agent 热潮降温，不是泼冷水，而是在提醒大家：技术热度终会过去，留下来的一定是算清楚了账的人。** 别让 Agent 成为"技术正确但经济错误"的项目，那才是真正的浪费。
