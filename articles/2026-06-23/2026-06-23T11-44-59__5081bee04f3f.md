这两天，DeepSeek 负责人密集发布 Agent 方向招聘信息，引发了不少讨论：为什么大模型公司不只招算法岗，反而开始急着找会做 Agent 的人？表面看是岗位缺口，底层其实是大模型从会回答，走向能办事的产业拐点。这里面有技术债，也有产品债，还有一堆工程现场的锅，锅盖一掀，味儿很熟。

## Agent不是聊天机器人，而是任务执行系统
很多人把 Agent 理解成更会聊天的 bot，这个理解少了一半。真正的 Agent 至少要具备四件事：

- **理解目标**：把用户一句话拆成可执行任务，比如订行程不是生成攻略，而是查时间、比价格、校验规则、生成方案。
- **规划步骤**：使用 ReAct、Plan-and-Execute 等思路，边推理边行动，必要时重规划。
- **调用工具**：搜索、数据库、代码执行器、浏览器、企业 API、RPA 流程，都可能成为工具。
- **记住状态并验收结果**：知道现在做到哪一步，失败后如何回滚，最终结果是否满足约束。

历史上，Agent 并不是突然冒出来的概念。2022 年 ReAct 论文把 reasoning 与 acting 结合起来；2023 年 AutoGPT、BabyAGI 让大众看到自动执行任务的雏形；2024 年后，function calling、workflow engine、MCP 等工具协议逐渐成熟，Agent 才有了落地的管线。换句话说，Agent 不是一层皮肤，而是一套把 LLM 接进真实世界的操作系统。

一个简单算式能说明难点：如果一个流程有 20 步，每步成功率 95%，全链路成功率约为 0.95^20≈36%。单步看着都挺稳，串起来就容易翻车。工程师的幽默是：bug 不会消失，它只是排队等你点运行。

## 为什么Agent人才突然变稀缺
DeepSeek 这类大模型团队急招 Agent 人才，本质上是供需错位。模型能力上涨很快，但能把模型变成可用产品的人没那么多。

1. **岗位交叉度太高**  
   Agent 工程师既要懂 LLM 的上下文窗口、prompt、tool use，又要懂后端架构、异步任务、权限、缓存、队列，还要理解产品流程。单纯会调 API 不够，单纯会写模型训练代码也不够。

2. **评测方法还在变化**  
   传统 NLP 看准确率，Agent 要看端到端成功率、成本、耗时、稳定性。SWE-bench Verified、WebArena、τ-bench 这类基准都在强调真实任务完成，而不是一句答案像不像。

3. **业务场景正在抢跑**  
   编程助手、数据分析、客服工单、游戏 NPC、办公自动化、供应链查询，都想要能自动办事的系统。需求一多，人才池就显得浅。尤其是既写过 production 代码，又踩过 LLM 不确定性坑的人，市场上本来就不多。

4. **大模型公司也需要产品化能力**  
   预训练和推理优化解决的是发动机问题，Agent 解决的是把发动机装进车里，还要刹车、仪表盘、保险杠。没有这些，参数再漂亮也很难跑进日常工作流。

## 合格Agent工程师要会什么
如果把 Agent 岗位拆开看，它不是一个技能点，而是一张能力网。

- **模型侧基础**：理解 token、context window、temperature、embedding、RAG、function calling。知道模型什么时候会幻觉，什么时候会偷懒，什么时候会一本正经地胡说。
- **工具编排能力**：会设计 tool schema、参数校验、错误重试、超时控制。比如调用航班 API 时，不能让模型随便编一个机场代码。
- **状态管理**：长任务需要 memory、session、checkpoint。用户改需求后，系统要知道哪些步骤要保留，哪些要重做。
- **后端工程能力**：队列、限流、日志、灰度发布、监控告警都不能少。Agent 一旦能自动操作，稳定性要求比聊天窗口高得多。
- **安全与权限意识**：什么工具能调用、什么数据能读取、什么动作需要人工确认，必须有边界。比如删库、转账、批量发消息，这些动作不能只靠模型一句我觉得可以。
- **产品抽象能力**：不是所有任务都适合 Agent。有些适合固定 workflow，有些适合人机协同，有些只需要一个表单。好工程师不会把所有螺丝都用电锯拧。

举个例子，做一个代码修复 Agent，不只是让模型写 patch。它要能复现 issue、阅读仓库、定位文件、修改代码、运行测试、解释风险，失败后还要换策略。这背后是 IDE 插件、沙箱、包管理、测试执行、日志解析一起配合。

## 热度背后，门槛在评测和交付
招聘热闹，不代表 Agent 已经到处开花。真正让团队头疼的，是从 demo 到 production 的距离。

- **评测要贴近业务**：不能只看模型答得是否流畅，要看任务完成率、平均步骤数、人工接管率、单位成本。一个 Agent 每次任务花 5 分钟、调用 30 次模型，可能技术上很酷，账单上很凉。
- **失败要可解释**：Agent 出问题时，要能追踪是哪一步的 prompt、工具、数据或模型判断出了偏差。没有 trace，排查就像在黑箱里捞虾，捞到最后只剩壳。
- **体验要可控**：用户不喜欢完全失控的自动化。更合理的形态往往是 Copilot：系统先建议，人类确认关键动作，再由 Agent 执行低风险步骤。
- **组织要配套**：Agent 涉及数据权限、业务流程、工程平台、质量验收，不是一个算法同学单兵突进就能完成。团队要有平台化思维，把工具、记忆、评测、监控沉淀成公共能力。

收尾给三条冷思考：

1. **求职者别只学 prompt**：补齐 Python、后端、数据库、API 设计、测试工程，再做 2 个能跑通真实流程的项目，比堆概念更有效。
2. **团队别急着全自动**：先从高频、低风险、可验证的任务切入，比如报告生成、数据查询、工单分流，再逐步放权。
3. **判断Agent价值看三项**：是否减少人工步骤，是否降低错误率，是否能稳定复用。如果只能演示一次，那更像烟花，不像基础设施。

DeepSeek 抢 Agent 人才不是个孤立事件，而是行业信号：大模型下半场，竞争点正在从模型会不会说，转向系统能不能做。谁能把不确定的模型，接成可靠的工具链，谁就更接近真正可用的智能应用。
