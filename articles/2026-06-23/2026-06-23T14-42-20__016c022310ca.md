最近科技圈被一条消息刷屏了——百度低调开源了 **Unlimited OCR**，一个总参数才 3B、实际激活参数仅 500M 的小模型，却在 OmniDocBench 基准测试中拿下 93.23%（v1.5）和 93.92%（v1.6）的综合得分，直接刷新端到端 OCR 的全球 SOTA。

更要命的是，论文里技术总监署名「YY†」，致谢栏把 DeepSeek-OCR 和 DeepSeek-OCR-2 排在前两位，行业观察者纷纷指向一个人：DeepSeek OCR 团队前核心负责人魏浩然。这位从 GOT-OCR2.0 到 DeepSeek-OCR 一路走来的大神，似乎把他在 DeepSeek 积累的全部认知，带到了百度的实验台上。

模型和代码已同步上线 GitHub 和 HuggingFace，完整开源。今天这篇文章，我们就来拆解这个模型到底做对了什么，以及它对 OCR 技术走向意味着什么。

## 1. 一个 500M 模型凭什么打过 Gemini？先看成绩单

很多人的第一反应：500M 参数的模型，怎么就 SOTA 了？先拉数据说话。

- **OmniDocBench v1.5**：综合得分 **93.23%**，比 DeepSeek OCR（87.01%）高出 6.22 个百分点
- **OmniDocBench v1.6**：综合得分 **93.92%**，端到端 OCR 全球第一
- **超越的对手**：Qwen3-VL、Gemini-2.5 Pro 等参数规模大数十倍的模型
- **长文档能力**：一口气解析 **40+ 页** PDF，不失忆、不降速、不复读

更直观的对比：当输出 6144 个 token 时，Unlimited OCR 的解码速度（TPS）维持在 **7847**，而 DeepSeek OCR 已经掉到 **5822**——差距高达 35%。这不是微调优化能解释的差距，这是架构级别的碾压。

一个 500M 激活参数的模型，用标准 32K 上下文窗口，一次前向推理就能完成数十页文档的完整转录。这种效率在工业部署中意味着什么？意味着推理成本大幅下降，意味着单卡就能跑，意味着可以真正大规模落地。

## 2. R-SWA：把「抄书的注意力方式」写进了模型

OCR 领域有一个困扰了所有模型的根本问题：**逐页失忆**。

传统 OCR 模型处理多页文档时，每处理完一页就清空上下文记忆，跨页信息直接丢失。这就像一个抄书的人，每抄完一页就把前面的内容忘得一干二净——你让他抄第 30 页的时候，他已经不知道第 1 页写的是什么了。

这个问题的技术根源在于标准 Multi-Head Attention（MHA）机制：KV 缓存随输出长度**指数级增长**。解码 100 个 token 和解码 10000 个 token，内存占用完全不同。为了维持运行效率，模型不得不牺牲连贯性。

Unlimited OCR 提出了一种叫 **Reference Sliding Window Attention（R-SWA）** 的新机制，精确模拟了人类抄书时的认知模式：

- **视觉输入端**：始终保持对完整文档图像的全面感知——眼睛始终能看到整张纸
- **文本输出端**：只保留最近 128 个 token 的上下文记忆——就像你抄书时只瞄一眼刚写的那几行

这个设计的精妙之处在于：KV 缓存变成了一个**固定容量的队列**。每生成一个新 token，最老的那个就被挤出去，内存占用始终恒定。无论文档有 1 页还是 100 页，显存开销是一样的。

Flash Attention v3 的延迟测试结果非常直观：DeepSeek OCR 的标准 MHA 随解码步数增加，每步耗时稳步攀升；而 Unlimited OCR 的 R-SWA 从头到尾一条平线，纹丝不动。

技术细节补充：Unlimited OCR 把**所有注意力层**全部替换为 R-SWA，没有保留任何标准 MHA 层。这种「all-in」的设计选择在工程上是相当大胆的，但从结果看，效果非常干净。

## 3. DeepEncoder：16 倍视觉压缩的秘密武器

光有 R-SWA 还不够。模型要处理长文档，还需要在输入端就把信息密度提上去。这就是 **DeepEncoder** 的作用。

DeepEncoder 最初在 DeepSeek OCR 中登场，是一个专门为文档解析设计的视觉编码器：

- **压缩能力**：将 1024×1024 分辨率的 PDF 页面压缩到仅 **256 个视觉 token**
- **压缩率**：**16 倍**
- **关键特性**：在 R-SWA 机制下，视觉 token 不参与状态转移——无论文档多长，图像信息永远清清楚楚，不会随解码过程退化

打个比方：传统模型看一页 PDF，需要记录数万个视觉 token；Unlimited OCR 只需要 256 个。这就好比别人用 16K 蓝光格式存电影，你用了一个极致压缩的编码器，体积小了 16 倍，但画质反而更好——因为去掉了冗余信息，保留了核心语义。

DeepEncoder 还有一个巧妙的设计：它使用了 **SAM（Segment Anything Model）** 的视觉编码器作为骨干，再接一个压缩模块。SAM 本身就是为高分辨率图像分割设计的，用它来提取文档的视觉特征，天然适合处理密集的文本布局。

配合 DeepEncoder 的极致压缩和 R-SWA 的恒定缓存，Unlimited OCR 在标准 32K 上下文里，一次前向推理就能转录数十页文档。论文里还提到一个测试数据：同时输入 20 页文档，转录与原文逐字比对的编辑距离仅 **0.057**；输入 40 页以上，依然控制在 **0.11** 以下，衡量重复输出的 Distinct-35 高达 **97%**——几十页一口气转录，几乎没有复读。

## 4. YY 是谁？一个技术人的「认知轨迹」

技术讲完了，聊聊这个人。

Unlimited OCR 的核心贡献者三位：Youyang Yin、Huanhuan Liu*（项目 leader）、YY†（技术总监）。其中 YY 用双字母缩写署名，论文正文没多提，但 GitHub 致谢栏把 DeepSeek-OCR 和 DeepSeek-OCR-2 排在致谢前两位——线索已经够明显了。

顺着这条线往回找：

- **DeepSeek OCR 从一代到二代**，核心作者始终三个人：魏浩然、孙耀峰、李宇琨，同一支小队伍从无到有
- **今年 4 月 DeepSeek 发 V4**，魏浩然名字后面多了星号——已离职
- **魏浩然的履历**：阶跃星辰出身，主导开发了端到端 OCR 最早跑通的开源标杆 **GOT-OCR2.0**（580M 参数，第一个真正意义上的端到端通用 OCR 模型）
- 到 DeepSeek 后，一手搭起整条 OCR 线：DeepEncoder、MoE 解码器，一代到二代都是他的团队

国内 OCR 圈不大，能做出 R-SWA 这种级别突破、还对 DeepSeek OCR 架构有「亲手做过」级别熟悉的人，一只手数得过来。魏浩然是其中最显眼的那一个。

如果 YY 真的是魏浩然，那这件事就不仅仅是「百度又开源了一个模型」那么简单。它更像是一个技术人把自己对 OCR 领域的全部认知——从 GOT-OCR2.0 的端到端一次解析，到 DeepSeek-OCR 的视觉压缩，再到 R-SWA——系统性地重新实现了一遍。

## 5. R-SWA 可能不只是 OCR 的事

论文展望里留了一句耐人寻味的话：R-SWA 是「通用解析任务的免费午餐」。

这句话暗示了更大的野心：R-SWA 机制可以推广到 **ASR（语音识别）** 和 **机器翻译** 等长序列任务。想想看，语音识别的本质就是把一段连续音频流「抄」成文字——这和抄书的认知模式几乎是同构的。如果 R-SWA 能在 OCR 上做到恒定缓存，那理论上它对任何「输入序列长、输出序列也长」的任务都适用。

论文下一步计划也很明确：

- **上下文窗口扩展到 128K**：从 32K 到 128K，意味着模型可以一次性处理一整本书
- **构建 prefill pool**：让模型学会自动翻页，不需要人工预处理 PDF
- **跨模态应用**：探索 R-SWA 在语音、翻译等领域的迁移效果

这就不只是一个 OCR 模型的问题了。如果 R-SWA 被证明是通用的，它可能改写所有长序列任务的架构设计范式。

## 冷思考：三条实用建议

看完这些亮点，作为务实的工程师，我给你三条冷静的建议：

**1. 消融实验还不够干净，精度提升归因存疑**

Unlimited OCR 是在 DeepSeek OCR checkpoint 基础上继续训练的，使用了约 200 万 PDF 数据训练 4000 steps。但 Table 1 的对比中同时引入了 R-SWA 和额外训练数据两个变量，无法区分精度提升到底来自 R-SWA 本身，还是来自额外数据的继续训练。GitHub 上已经有研究者提出了这个疑问，作者团队承诺会补充消融实验。在结果出来之前，对 R-SWA 在精度上的贡献保持审慎。

**2. 500M 激活参数不等于 500M 模型**

总参数 3B，激活 500M——这是 MoE（Mixture of Experts）架构的特性：参数量大但每次只激活一小部分。这意味着部署时显存占用并不像听起来那么小，64 个 routed experts 加 2 个 shared experts 都需要加载到显存里。真正的好处是推理速度快（计算量小），但显存需求和一个 3B 密集模型差不多。

**3. 别急着在生产环境上**

模型刚开源，社区还处于兴奋期。但真实生产环境中的 PDF 文档质量参差不齐——扫描件模糊、表格嵌套、多语言混排、手写体混入——这些边界情况远比 OmniDocBench 基准测试复杂。建议先在自己的数据集上做一轮评估，确认实际场景的精度和延迟满足需求，再考虑生产部署。毕竟，SOTA 是在基准测试上拿的，不是在你的业务数据上拿的。
