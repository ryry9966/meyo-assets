## 背景

最近在 OpenClaw 里跑批量任务，撞上单 agent 串行的典型瓶颈：让主 agent 把 docs 下 15 个页面统一做术语校对，它一页页读、一页页改，二十多分钟跑完，而且上下文越堆越满——后半段它开始"忘记"前半段定下的规则。subagent 机制正好对症：每个子任务有独立上下文，互不污染，还能并行跑。

## 问题

但从串行改成并行，不是调个并发数就完事。实际要回答三个问题：**任务怎么拆才真的独立？subagent 的结果怎么收回主 agent？出错怎么兜底？** 这三个答不好，并行带来的不是提速，是返工。

## 做法

我的流程分四步：

1. **拆任务。** 先让主 agent 只干一件事：输出任务清单，每条含输入路径和明确指令。判断标准是子任务之间不共享可变状态。
2. **定契约。** 规定每个 subagent 把产出写到独立文件，格式固定：

```text
input:  docs/api.md
instruction: 按术语表校对，只输出修改建议
output: results/api.md
```

关键点是产出**落盘、不回吐长文本**——这是保住主 agent 上下文的核心。

3. **并行派发。** 主 agent 通过 subagent 能力并发拉起任务，初始并发设 3，稳定后再加。
4. **汇总收口。** 主 agent 只读产出文件做合并与裁决，自己不做具体工序。

## 踩坑

- **假独立**：两个子任务都要改同一个文件，后写覆盖先写。后来把写操作收敛到主 agent，subagent 只产出建议。
- **上下文泄漏**：一开始把整个父任务背景塞给 subagent，子任务变成小号主任务，又慢又贵。只给最小必要信息。
- **并发失控**：一口气拉到 8，直接撞上游速率限制。3–5 起步，观察排队和报错再加。
- **静默失败**：某个 subagent 超时返回空，主 agent 拿着残缺结果照常汇总。必须有超时、重试和显式的失败标记文件。
- **工具下放过宽**：MCP 工具全量开放给 subagent，一个子任务误改了共享配置。按任务裁剪白名单。

## 可复用建议

- **分工原则**：subagent 干"读和算"（检索、审阅、转换），写操作由主 agent 收口。
- **落盘优先**：中间产物全部写文件，汇总时有结构可解析，排查时有留痕。
- 把"拆分→派发→汇总"沉淀成一个 skill，并发数、超时、重试做成参数，下次直接复用。
- 先用 2–3 个 subagent 的小场景验证契约，跑顺了再扩规模。

## 总结

subagent 编排本质是工程问题，不是模型问题：拆分是否真独立、契约是否清晰、失败是否兜底，决定了并行是提速还是返工。OpenClaw 的价值在于这些环节都能用配置和 skill 固化——跑顺一次，后面就是复制。
