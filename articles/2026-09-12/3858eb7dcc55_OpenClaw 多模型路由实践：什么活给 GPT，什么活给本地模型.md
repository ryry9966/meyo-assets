## 背景

OpenClaw 的价值之一是把模型当成可替换零件：同一个 agent 网关，上可以挂 GPT-4o 这类云端旗舰，下可以挂 Ollama/vLLM 起的本地模型。跑一段时间后大家都会遇到同一个问题——不是"能不能接多个模型"，而是"每个请求该发给谁"。

全走云端旗舰，账单和延迟都难看；全走本地，复杂任务的工具调用成功率和推理质量明显掉。路由本质是在成本、延迟、质量、隐私四个维度上做取舍。

## 问题：按什么分？

常见第一反应是按关键词路由：消息里带"总结"走本地，带"分析"走 GPT。实践下来这条路不太行——用户表述不可控，误判率高，而且 agent 任务的真实难度藏在工具依赖度里，不在表面措辞里。

更可靠的做法是**按任务分层，在 skill / agent 配置层显式指定模型**，而不是让运行时去猜。

## 做法

**Step 1：任务分层。** 按我自己日志的统计，大致三类：

- 高频低风险：消息清洗、转写整理、格式转换、简单摘要。占请求量六成以上，本地 7B–14B 足够。
- 工具调用密集：需要稳定的 function calling、多步 MCP 工具链。这是本地小模型最容易翻车的区域，建议走云端中档模型。
- 规划与复杂推理：多步 plan、跨会话上下文整合。交给旗舰模型，请求量占比低，但决定体验下限。

**Step 2：配置 provider 与默认路由。** 示意结构（字段名以你所用版本为准）：

```json
{
  "providers": {
    "gpt":   { "model": "gpt-4o", "fallback": "local" },
    "local": { "model": "qwen2.5:14b-instruct-q4_K_M", "fallback": "gpt" }
  },
  "routing": {
    "default": "local",
    "skills":  { "plan": "gpt", "mcp-orchestration": "gpt" }
  }
}
```

原则：`default` 给便宜的本地模型，把贵的云端模型显式挂到少数高价值 skill 上。反向配置（默认 GPT、个别走本地）通常省不下多少钱。

**Step 3：失败升级。** 本地模型输出格式错误、工具调用解析失败时，fallback 到云端重试一次。注意限制重试层级，避免"本地失败→云端失败→再循环"。

**Step 4：记录与回归。** 每次路由落一条 tag（模型名、skill、耗时、token 数），攒两三周数据再调分层边界。

## 踩坑点

- **本地模型的 tool calling 是重灾区。** Q4 量化后的 14B 看着回答流畅，实际有 10–20% 概率输出纯文本而不是工具调用，agent 表现为"卡住不动作"。一定要用你自己的真实工具链测，别信公开榜单。
- **上下文长度陷阱。** 本地模型常见 8k–32k 窗口，长会话历史被截断后表现为"健忘"，很容易误判成模型变笨。
- **本地 ≠ 低延迟。** 消费级显卡跑大模型，首 token 延迟经常不如云端中档模型，还有冷启动。路由别想当然。
- **隐私初衷会被 fallback 打破。** 一旦配了"本地失败升级云端"，敏感渠道的对话就可能上云。隐私敏感的 channel 应禁用升级或单独配置。

## 可复用建议

- 从日志抽 30–50 条真实任务做私有评测集，每次换模型或量化版本跑一遍，十分钟的事，比拍脑袋可靠。
- 按 skill 而不是按会话覆盖模型：同一个 agent 里可以"摘要走本地、规划走 GPT"。
- 给每条路由决策留 tag，策略靠数据迭代，不靠感觉。
- 本地选型保守一点：优先选官方标注支持 function calling 的 instruct 版本；工具链场景量化别低于 Q5。

## 总结

多模型路由不是炫技，是成本结构问题：让八成的简单请求跑在便宜模型上，把预算留给两成决定体验的复杂请求。OpenClaw 的 provider 加 skill 级覆盖机制足够支撑这套玩法——先跑起来、记数据，再逐步收紧分层边界。
