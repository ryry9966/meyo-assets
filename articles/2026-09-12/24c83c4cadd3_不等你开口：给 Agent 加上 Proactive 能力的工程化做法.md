## 背景

绝大多数 Agent 目前仍是"应答式"的：你提问，它回答，会话结束即失忆。但从工程角度看，把 Agent 从被动应答升级为主动服务的技术条件已经齐了——MCP 让 Agent 能稳定接入外部数据源，hook 和定时调度让"感知"不再依赖用户输入，工具调用机制让"执行"有了划安全边界的可能。

问题在于，proactive 不是加一个 cron 就完事。做得粗糙，产出的只是一个每天推十条废话的通知机器。

## 问题：三个典型失败模式

复盘社区里几个 proactive 实验，失败基本集中在三类：

1. **噪声失控**：Agent 定时全量扫描并推送，用户第三天开始忽略，第七天直接禁用技能。
2. **成本失控**：每 5 分钟跑一次 LLM 判断，月底 token 账单比订阅费还贵。
3. **权限失控**：Agent 在无人确认的情况下自主调用写操作工具，产生不可逆副作用。

共同根源是：把 proactive 当成"模型能力问题"，而它其实是"系统工程问题"。

## 做法：感知—判断—提议—执行 四段式

建议把 proactive 拆成四段独立链路，每段单独可测：

**1. 感知层：事件驱动优先于轮询。** 优先用 webhook、文件变更监听、MCP 资源订阅拿状态变化；没有事件源才退化为轮询，且轮询前先做本地 diff（内容 hash 不变就不触发下游）。这一层的目标是"便宜"，不碰 LLM。

**2. 判断层：规则兜底，模型补刀。** 用简单规则（阈值、关键词、时间窗）过滤掉约 80% 候选事件，剩下的交给便宜模型做相关性打分，高分事件才进入下一步。输出必须结构化：事件、证据、置信度。

**3. 提议层：默认只提议，不执行。** Agent 生成"建议做 X，理由是 Y，预计影响 Z"的提案推给用户。这是同时控制噪声和风险的关键——主动 ≠ 自作主张。

**4. 执行层：分级权限。** 只读操作可自动执行；写操作默认需确认或先 dry-run；不可逆操作永不自动执行。每个 proactive 技能单独配权限档位，不要全局一个开关。

外加反馈回路：每条提议记录 accepted / dismissed / ignored，每周看接受率，低于阈值就收紧触发条件或下线该技能。

## 踩坑点

- **定时任务静默失败**：后台任务挂了没人知道。加心跳，失败通知本身也要克制，一条就够。
- **上下文过期**：定时触发时拿到的缓存可能是几小时前的，执行前必须 re-fetch 关键状态。
- **时区与静默时段**：真实发生过 Agent 凌晨三点推"每日简报"的事故。每个技能配静默时段，默认按用户本地时区。
- **冷启动太激进**：新技能先跑"低频 + 只提议"模式，接受率稳定后再放开频率。
- **判断层误杀**：规则过滤太狠会漏掉真正有价值的事件，留一条人工抽检通道定期看被过滤样本。

## 可复用建议

- 感知和判断层做到"零 LLM 成本"是底线，LLM 只处理候选事件。
- 提议消息必须结构化（建议 / 理由 / 影响 / 一键执行入口），别写成一段散文。
- 所有主动行为落 structured log，接受率是你唯一该看的北极星指标。
- 把每个 proactive 技能当成独立实验：有假设、有指标、有退出条件。

## 总结

Proactive 的本质不是"让模型更聪明"，而是让"何时打扰用户"变成一个可度量、可调节的工程决策。感知做便宜、判断做分层、执行做保守、反馈做闭环——先做提议者，跑通数据后再谈自动执行。这比一上来就追求全自主 Agent 务实得多。
