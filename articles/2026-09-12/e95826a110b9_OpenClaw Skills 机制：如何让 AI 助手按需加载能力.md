## 背景

Agent 用得越久，你要它干的事就越多：周报模板、数据清洗流程、内部 API 调用规范、部署脚本……最直觉的做法是把所有说明全部塞进系统提示词。能力少的时候没问题，一旦超过十几个任务，提示词膨胀、指令互相干扰、token 成本上去，模型反而开始"串戏"。

OpenClaw 的 Skills 机制本质上是一个**渐进式加载**方案：启动时只加载每个技能的元数据（名称 + 描述），技能正文和引用的脚本资源只在模型判断相关时才读入。它解决的不是"模型会不会"的问题，而是"什么时候让模型知道"的问题。

## 问题

全量预加载的真实代价体现在三个层面：

1. **上下文预算被常驻指令吃掉**，留给实际任务的空间变小；
2. **指令冲突**，写周报时，部署规范的条目也在影响输出风格；
3. **评估困难**，改一条无关指令可能影响另一个任务的评测分数，问题难以归因。

## 做法

一个最小可用的 Skill 就是工作区里的一个目录加一个 `SKILL.md`：

```
skills/
└── weekly-report/
    ├── SKILL.md          # 描述 + 使用说明
    ├── template.md       # 正文模板（按需读取）
    └── collect_stats.sh  # 可执行脚本
```

`SKILL.md` 头部用 frontmatter 声明名称和描述：

```markdown
---
name: weekly-report
description: 当用户要求写周报、汇总本周工作或生成交际汇报时使用
---
## 步骤
1. 先运行 collect_stats.sh 拉取提交记录
2. 按 template.md 的结构填充
3. 输出前自查：是否覆盖了三个项目、是否有量化数据
```

关键点有三个：

- **description 是触发器，不是说明书。** 它常驻上下文，要写成"什么情况下用我"，让模型能准确路由。
- **正文保持精炼。** `SKILL.md` 控制在一屏内，长内容拆到 `template.md` 这类参考文件里，让模型按需再读一层。
- **脚本自带说明。** 告诉模型怎么调用、依赖什么环境，而不是指望它猜。

## 踩坑点

- **描述写得太泛**（"处理文档相关任务"），模型永远不触发；太窄则该用时想不起来。写完可以换个措辞问模型"这个任务该用哪个 skill"，验证路由是否命中。
- **把高频内容做成 Skill。** 每个会话都要用的东西（如代码风格约定）应该放常驻配置，按需加载的价值在于"不常用但要用时很重"的能力。
- **Skill 之间隐式依赖。** A 技能假设 B 技能的输出格式，单独触发就翻车。依赖要在正文里显式声明，或者干脆合并。
- **脚本在沙箱里跑。** 路径写死、依赖本地 Python 版本，换个环境就挂。脚本要幂等、无副作用假设，首次上线前手动跑一遍。

## 可复用建议

1. 一个 Skill 只做一件事，超过两个触发场景就考虑拆分；
2. 在正文末尾放一个自查清单，让模型输出前自检，比事后人工纠错便宜；
3. Skills 目录进 git，像对待代码一样 review 和版本化；
4. 记录哪些 Skill 实际被触发过，一个季度没命中的就删掉——技能列表本身也是上下文成本。

## 总结

Skills 机制可以概括为一句话：**元数据常驻、正文按需、资源执行时加载**。它不是什么新模型能力，而是把提示词工程落到了文件系统纪律上。建议从两三个高频、流程稳定的任务起步，跑通"触发 → 加载 → 执行 → 自检"的闭环后再铺开。技能库的可维护性，最终决定 Agent 能力的上限。
