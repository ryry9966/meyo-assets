## 背景

OpenClaw 里的 Agent 和自动化流程，几乎都依赖外部 API：模型供应商、搜索、MCP 工具、自建服务。本地代码写得再稳，也挡不住远端的 429、5xx、超时、DNS 抖动和 schema 变更。做久了会发现：API 故障不是异常路径，而是常态路径的一半。

## 问题在哪

常见的两种坏结局：

1. 一次工具调用抛异常，直接击穿整条任务链，前面跑了一半的上下文全部作废；
2. 把原始报错塞回模型上下文，模型开始"自由发挥"——编造 fallback 结果、无脑循环重试、成吨烧 token。

根源是同一个：没有把错误恢复当成调用层的系统设计，而是寄希望于模型自己"想办法"。

## 我的做法：分层恢复

**1. 先分类，再谈重试。** 失败先归两类：可重试（超时、429、5xx、网络抖动）和不可重试（401/403、参数错误、schema 变更）。对 400 重试三次纯属浪费，对 503 不重试直接放弃又太可惜。分类错了，后面全错。

**2. 重试要有纪律。** 指数退避 + 随机抖动（jitter），上限 3 次左右。加 jitter 是为了防止多个 worker 同时醒来重试，形成同步风暴。

**3. 熔断。** 连续 N 次失败就把该工具标记为 down，冷却期内不再打远端，直接走降级路径。这件事放在插件/工具层做，比让模型"自己决定要不要再试"可靠得多。

**4. 降级与兜底。** 每个关键工具提前定义"没有我怎么办"：主 API → 备用供应商 → 缓存的旧数据 → 跳过该步骤并明确告知。降级结果必须显式标注，不能悄悄返回过期数据。

**5. 把错误翻译给 Agent。** 返回给模型的不该是堆栈，而是结构化信封：

```json
{
  "status": "unavailable",
  "retryable": false,
  "hint": "search tool down, use cached index or ask user"
}
```

模型拿到 `retryable` 和 `hint` 才能做合理规划；只给它一串模糊报错，它只会开始猜。

**6. 幂等与预算。** POST 类操作（下单、发消息、扣费）重试前先上幂等键，否则重试成功一次、副作用发生两次。另外给整个任务设总 deadline，工具超时要小于任务预算——单次调用卡 60 秒就能拖死一条 90 秒的链路。

## 踩过的坑

- 对非幂等接口盲目重试，消息重复发送，用户收到两条一样的通知；
- 无限重试 4xx，烧完配额才发现是 key 过期；
- 原始堆栈直接进上下文，模型开始幻觉式"修复"不存在的 bug；
- 多 worker 无抖动同步重试，把半死的 API 彻底打死；
- 熔断状态只存在单进程内存，横向扩容后每个实例各自再打一遍；
- 最隐蔽的一类：降级返回旧缓存但没告诉模型和用户，产出看起来正常，数据是错的。

## 可复用建议

- 把"分类 → 退避重试 → 熔断 → 降级 → 结构化错误"封装成统一的 `resilient_call` 工具层，所有 API 调用走同一入口，别让每个插件各写一套；
- 定一个通用的错误信封格式，Agent 侧的解析逻辑只写一次；
- 用 mock 注入 500、超时、慢响应，把故障路径当正常用例来测；
- 监控三个指标：错误分类分布、平均重试次数、熔断开启时长占比——它们比"成功率"更能提前暴露问题。

## 总结

外部 API 挂掉，从来不靠 prompt 解决，靠的是调用层的工程设计：先分类、有纪律地重试、及时熔断、明确降级，最后把真实状态如实告诉 Agent 和用户。可靠性不是让模型更聪明，而是让系统在部分失效时，行为依然可预期。
