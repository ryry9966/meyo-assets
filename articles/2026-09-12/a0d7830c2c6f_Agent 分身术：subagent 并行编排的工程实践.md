## 背景

用 OpenClaw 做自动化久了，最先撞到的墙不是模型能力，而是"串行"：主 agent 一次只干一件事。让它重构三个模块，它就一个一个来；中途想插别的事，得等当前任务跑完，或者打断重来。上下文也越滚越长，早期任务的关键信息被慢慢冲淡。

subagent 编排就是冲着这个问题来的：主 agent 把可拆分的任务派给独立的子 agent 并行执行，自己只负责拆分、派发和汇总。这篇帖子记录我日常用 subagent 的做法和教训。

## 问题：哪些任务值得拆

不是所有任务都适合并行，我的判断标准就两条：

1. **任务之间没有写冲突**：改不同目录、不同分支，或者纯读操作（检索、调研、测试分析）。
2. **单任务足够独立**：子 agent 拿到一段描述就能开工，不需要反复回主对话追问。

典型场景：同时给三个仓库升级依赖并跑测试；并行调研几个 MCP 工具的用法再汇总对比；一边生成文档一边补测试。

## 做法

**第一步：先串行验证任务描述。** 最容易被省略但最重要的一步。先让主 agent 串行跑一个子任务，确认描述里信息完备，再拆成并行。描述不全时串行还能靠追问补救，并行只会各错各的。

**第二步：任务描述自包含。** 子 agent 看不到主对话。每个描述我强制写成四段：目标、输入（路径、分支、相关文件）、约束（不许动什么、超时多少）、输出格式（写到哪里、汇总什么字段）。

**第三步：控制并发。** 并发 2~4 个起步。子 agent 各自独立会话，token 是真金白银，一口气开八个很容易把额度烧完，结果还不一定更好。

**第四步：用文件系统做汇合点。** 让每个子 agent 把结果写到约定路径（如 `/tmp/task-xxx/result.md`），主 agent 最后统一读取。这比在对话里来回传长文本稳定得多，也方便事后排查。

**第五步：想好失败路径。** 派发时就定好：子 agent 超时或报错，主 agent 是重试、降级为串行、还是跳过并汇报。不写这条，编排就会挂在那里等你人工救火。

## 踩坑点

- **子 agent 各自为政**：描述里没写"只改这个目录"，两个子 agent 同时动了同一个文件，git 冲突解了半小时。必须写同一份代码时，用 git worktree 分工作区，或改回串行。
- **子 agent 过度发挥**：让它"顺便优化一下"，它重构了半个仓库。约束段必须写死边界。
- **主上下文被结果撑爆**：子 agent 返回几千行日志直接塞回主对话，上下文立刻爆。让子 agent 只返回摘要和结论，原始输出落盘。
- **并行掩盖串行问题**：任务描述本身有错时，并行会让四个子 agent 朝错误方向各跑各的，烧完 token 才发现。所以第一步永远是先串行验证。

## 可复用建议

- 把四段式任务描述（目标/输入/约束/输出）存成模板，每次派发直接填空。
- 子 agent 产出一律先落文件，主 agent 只读摘要——这是 agent 间最可靠的通信方式。
- 并发数从 2 开始加，观察 token 消耗和错误率，别一上来拉满。
- 排查编排问题时，先看子 agent 自己的会话记录，而不是主 agent 的转述。

## 总结

subagent 编排的本质不是"更多 AI"，而是工程上的任务拆分：可并行的才并行，描述必须自包含，结果通过文件汇合，失败路径提前想好。做好这四点，原本要等一小时的批处理任务十分钟内能跑完，主对话还保持干净。建议从把一个现有的长任务拆成两个并行子任务开始，比直接设计复杂的编排图有用得多。
