## 背景

OpenClaw 用户大多从云端 API 起家，但几个场景会让人认真考虑本地模型：隐私敏感的日志和文档处理、批量任务的跑量成本、内网/离线环境，以及给 Agent 做低延迟的辅助调用。本文记录我在一台 32GB 内存 + RTX 4070 TiS（16GB 显存）的家用机上部署本地 LLM 并接入自动化工作流的完整过程，结论先行：可行，但要放弃"完全替代云端"的幻想。

## 问题：先纠正三个预期

1. **"内存够就能跑"**，内存装得下模型文件 ≠ 能流畅推理。真正的判断标准是显存（或统一内存带宽），不是容量。
2. **"量化就是原模型打折"**，Q4 量化在日常对话上几乎无感，但在长上下文、代码生成、工具调用上退化更明显。Agent 场景要留余量。
3. **"本地能完全替代云端"**，现实的定位是分工：结构化输出、分类、摘要、简单工具调用交给本地；复杂推理和长链路 Agent 留给云端。

## 做法

**硬件基线**：16GB 显存是舒适线，8GB 也能跑 7-8B Q4。

**模型选择**：Qwen 系列 14B Q4 做主力（中文能力好、工具调用支持尚可），8B 级别模型做轻量兜底。

**服务化**：Ollama 起步最快，自带 OpenAI 兼容端点；要压并发再换 llama.cpp server 或 vLLM。

**接入 OpenClaw**：把 provider 的 `base_url` 指向 `http://localhost:11434/v1`，模型名用对应的 tag。接入后重点验证三件事：工具调用（function call）是否稳定、流式输出是否正常、长 system prompt 下是否丢指令。

**压测**：不要用聊天测速，直接拿真实 Agent 任务跑 20 轮，记录 tokens/s 和工具调用成功率，这组数字才是部署质量的真相。

## 踩坑点

- **上下文静默截断**：Ollama 不少版本默认上下文很短（2048 级别），Agent 的长 system prompt 会被悄悄砍掉，表现为"模型忘了规则"。必须显式设置 `num_ctx`。
- **KV cache 吃显存**：14B Q4 + 32K 上下文可能直接 OOM，宁可退到 16K。
- **小模型工具调用参数格式易崩**：输出 schema 加严格校验 + 一次自动重试，能救回大半失败案例。
- **笔记本混合显卡**：默认可能走核显，要在驱动面板强制独显。
- **显存被后台占用**：浏览器挂几个页面就吃 1-2GB 显存，推理前清掉。

## 可复用建议

- **给自己留一张决策表**：8GB 显存 → 7-8B Q4；12-16GB → 14B Q4；24GB → 32B Q4。别越级硬上。
- **配置写成脚本或 compose 文件**，换机器可复现；模型下载配好国内镜像和 `HF_ENDPOINT`。
- **本地/云端做路由**：OpenClaw 里给不同子任务配不同 provider，本地跑量、云端兜底，故障时能自动降级。
- **锁定基准任务**：每次换模型版本，重跑同一套 Agent 任务，数据才有可比性。

## 总结

本地 LLM 不是云端的替代品，而是给 Agent 工具箱加了一档"便宜、离线、可控"的选项。家用 16GB 显存的机器跑 14B Q4，处理日常结构化任务已经够用。把验证、压测、配置复现这三件事做扎实，本地模型才能真正进入你的自动化链路，而不是装完吃灰。
