## 背景

RSS 常被认为过时，但对自动化管线来说，它是最省心的结构化输入：有 GUID 做幂等键、有发布时间、更新语义明确，不需要对抗反爬。真正的问题是订阅量上来之后，一天几百条，人读不完；而"每条直接喂给 LLM 写摘要"又贵又慢，产出往往没法用。

## 问题拆解

摘要质量差，多数情况不是模型问题，而是管线问题：正文没抓全、重复信息没合并、没有分级过滤就全量总结。所以这条管线的核心不是"接个模型"，而是把脏活尽量分摊到模型调用之前。

## 做法

**1. 抓取层**：cron 脚本或现成聚合器定时拉 feed，只落库 GUID、标题、链接、原始 XML。这一层不做任何智能处理，保证出问题时能快速定位。

**2. 正文补全**：很多源只给摘要，需要回源抓页面，用 readability 类库做正文抽取。抽取失败就打标 skip，不要硬塞给模型。

**3. 去重与分级**：先按 GUID / 规范化 URL 去重；再用 simhash 或 embedding 合并同一事件的多源报道；最后用便宜模型对条目打分，只有高分条目进入摘要环节。

**4. 摘要层**：结构化输出。要求模型返回固定 schema——一句话结论、3 个关键点、是否有操作价值、置信度。不要自由文本，方便下游渲染和检索。

**5. 分发层**：聚合成每日 digest 推到 IM 或邮件，原始条目永远落库存档，摘要只是视图。

放到 OpenClaw 的语境里：抓取可以做成一个 MCP server 暴露的 tool，摘要是带 schema 约束的 agent 调用，调度用系统 cron 就够，不必引入消息队列。

## 踩坑点

- **幻觉的根源常在管线**：正文抽取失败后，模型仍会输出流畅的摘要。防护做双保险：正文长度低于阈值时走"仅标题"分支，prompt 里明确要求内容不足时输出 `insufficient`，下游据此降级展示。
- **成本失控**：全量摘要是新手最常见的坑。两级模型（便宜模型 triage + 强模型摘要）能把强模型的调用量降一个数量级。
- **时区与 pubDate 不可靠**：漏抓、重抓多半因此。以 GUID 为幂等键，不要依赖发布时间排序。
- **源会悄悄坏掉**：改字段、改编码、CDATA 坑，都见过。抓取层要有失败告警，否则停更一周你才发现。

## 可复用建议

- 先存原始数据，再谈处理：摘要可以重跑，正文丢了就没了。
- schema 加版本号，prompt 改版之后旧数据仍可解析。
- 每个环节保持幂等，任何一天都可以删掉下游重放。
- 摘要是入口不是替代：digest 里保留原文链接，别追求全自动零人工。

## 总结

这条管线没有一步是新技术，价值在于每一层只做一件事、层层可降级：RSS 提供稳定输入，去重和分级控制成本，结构化摘要保证输出可用。跑稳之后，把它接进 agent 做问答或自动日报，都是顺手的扩展。先让它安静地跑两周，再谈智能化。
