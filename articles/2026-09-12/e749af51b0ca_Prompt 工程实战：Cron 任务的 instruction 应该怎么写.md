# 背景

OpenClaw 的 cron 任务本质上是**无人值守的 agent 运行**：你写一段自然语言 instruction，框架按计划触发，agent 独立完成并输出结果。它和日常聊天最大的区别是——执行时你不在场，没有上下文，也没有追问的机会。instruction 写得好不好，直接决定任务是「省心的自动化」还是「每天定时生产垃圾信息」。

# 问题

社区里见过太多这样起步的指令：

> “每天早上帮我总结一下 AI 新闻发给我。”

跑起来通常三天内出问题：发到错的会话、时区差八小时、新闻源挂了 agent 自己编几条补上、或者同一批内容每天重复发。根因都一样：这条指令是**对话语气**，不是**任务规格**。

# 做法：把 instruction 当一次性工单写

我的习惯是保证四要素齐全：

1. **时间语义**：写清时区和边界。“每天 08:00（Asia/Shanghai）”比“每天早上”可靠；数据处理类任务要加锚点，比如“只处理今天的数据”。
2. **数据来源**：明确用哪个工具 / MCP 获取输入，不要让 agent 自由发挥找源。
3. **输出契约**：发到哪里、什么格式、多长。例如：“发到 #daily，3–5 条要点，每条不超过 40 字，末尾附来源链接。”
4. **失败分支**：必须显式写。“如果抓取失败或结果为空，不发送任何消息，只记录失败原因。”这一条能挡掉大部分幻觉式输出。

一个我实际在用的骨架：

```
任务：每日晨报（一句话说明职责）
步骤：1) 用 xxx 工具取数据  2) 按规则过滤  3) 按模板整理
输出：发到 #daily，3–5 条，每条 ≤40 字，含来源
异常：数据为空 / 工具失败 → 不发送，仅记录原因
```

写完后先**手动触发**跑两三次，确认输出稳定再挂调度；前几个周期盯一下结果，再逐步放手。

# 踩坑点

- **时区坑**：先确认 cron 调度用的是服务器时区还是你配置的时区，“8 点”到底是谁的 8 点。
- **输出目标缺省**：不写目标就会发到默认会话，轻则刷屏，重则发错地方。
- **没写失败分支**：工具挂了，agent 倾向于“完成任务”而不是报告失败，编内容是 cron 场景里最危险的模式。
- **依赖上下文**：instruction 里写“按我们之前聊的方案”，cron 执行时根本不存在这个“之前”。指令必须自包含。
- **指令太长**：约束堆到几百字，关键条件容易被稀释。核心规则放前面，细节能删则删。
- **任务太重**：一条指令串五六个工具，失败点太多、难排查。拆成小任务，各自可验证。

# 可复用建议

- 用固定骨架写，格式统一，别人接手也看得懂。
- 给每个任务起名，并在指令开头自我声明，日志排查时能对上号。
- 改指令保留旧版本，输出异常时回滚对比，快速区分是指令问题还是数据源问题。
- 定期清理：跑了一个月没有价值的任务直接删。通知疲劳的结局往往是你把所有任务一起关掉。

# 总结

Cron 的 instruction 不是提示词技巧题，是**规格书写题**：自包含、确定性强、有失败分支、有输出契约。按“交给实习生的一次性工单”标准来写，agent 无人值守的可靠性会上一个台阶。
