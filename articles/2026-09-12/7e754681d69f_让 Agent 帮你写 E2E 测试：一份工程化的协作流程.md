## 背景

E2E 测试大概是自动化测试里"性价比最难看"的一层：写起来慢、挂起来玄学、维护成本高。最熟业务的人往往最没时间写，新人则是先写功能再补测试，覆盖质量可想而知。

Agent 的能力恰好卡在这个空档上：它能读页面结构、能跑命令、能根据报错自我迭代。最近几个月我们在内部项目里用"Agent 起草 + 人工把关"的方式补了几十条 E2E 用例，把流程和坑整理如下。

## 核心问题：直接让 Agent 写，会得到什么

最常见的结果不是写不出来，而是写出"看起来很对"的测试：

- **断言空转**：只检查元素存在，不验证业务结果，下单流程跑完连订单状态都没断言；
- **选择器脆弱**：从渲染后的 DOM 抄一长串 CSS 路径，重构第一天就挂；
- **API 幻觉**：混用不同版本的测试框架 API，或写出根本不存在的匹配器；
- **硬编码等待**：大量 `sleep` 掩盖时序问题，CI 上随机挂。

根本原因是 Agent 缺两样东西：对应用真实行为的观察，以及你们团队的测试约定。它只会按训练数据里"典型测试长什么样"去补全。

## 做法：探索 → 起草 → 执行 → 回填

1. **先让它看，再让它写。** 用浏览器类 MCP 工具（如 Playwright MCP）让 Agent 实际操作应用：走完一条核心用户路径，记录每个关键页面的结构和可用语义选择器。这一步产出的是"页面事实"，不是测试代码。
2. **喂约定，不喂猜测。** 给一页纸的测试规范：选择器优先级（data-testid > role > 可访问文本）、fixture 写法、禁止使用的 API。比让它自己猜靠谱得多。
3. **分角色生成。** 让一个会话负责探索并产出用例描述（步骤 + 预期结果的自然语言清单），另一个会话只负责把清单翻译成代码。职责分开后断言质量明显更好——写用例的脑子在思考业务，不是在凑语法。
4. **执行与回填。** 测试在独立环境跑，失败日志原样喂回起草会话，让它修自己的用例。关键是**禁止 Agent 改业务代码让测试变绿**，失败根因必须在人工确认后处理。
5. **人工只审断言和清理逻辑。** 选择器、样板代码可以放给 Agent。这是投入产出比最高的一道关。

## 踩坑点

- **别把整个代码库塞进上下文。** 相关页面组件 + 路由定义 + 一两个存量测试范例就够。上下文越杂，它越倾向于模仿杂乱的部分。
- **警惕"自我修复"循环。** Agent 既写测试又能改应用代码时，一定选阻力最小的路——改代码。工具权限要物理隔离。
- **CI 随机挂先查等待策略。** Agent 很爱写固定 sleep，直接在规范里禁掉，强制用框架的条件等待。
- **存量测试也要给它看。** 不然它会自创风格，review 成本翻倍。

## 可复用建议

- 测试规范做成仓库常驻文档，Agent 会话冷启动时先注入；
- 用 lint 规则固化约束（禁 XPath、禁 `waitForTimeout` 等），比在 prompt 里反复强调可靠；
- 把 data-testid 当作前端、测试、Agent 之间的"契约"来管理，选择器稳定性会大幅提升；
- 把 Agent 产出的测试当新同事的 PR：能合，但必须有人签字。

## 总结

Agent 写 E2E 测试，瓶颈不在生成能力，而在协作结构：谁能观察应用、谁定义断言、谁对失败负责。探索交给 Agent，约定交给人，翻译成代码交给 Agent，失败定性留给人——这条流水线跑顺之后，覆盖率的提升是稳定可预期的。它替代不了你对业务的理解，但能把你从最不想干的活里捞出来。
