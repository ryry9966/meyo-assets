# 背景：agent 也需要一份入职文档

在 OpenClaw 里，agent 并不是每次会话都从零开始。每次启动，它会把工作空间里的 `AGENTS.md` 读进上下文——这份文件相当于工作空间的常驻说明书：你是谁、文件放哪、哪些事要先问人。可以把它理解为写给 AI 的 README，或者新员工第一天拿到的那份 onboarding 文档。

# 它解决什么问题

没有 AGENTS.md 的 agent，行为完全取决于模型默认习惯和零散的对话记忆。实际用下来常见三类问题：

- 记忆文件命名随意，今天是 `memory/2025-06-01.md`，明天变成 `note.md`，检索时全是噪音；
- 破坏性操作没有确认环节，一句"清理一下"可能直接删目录；
- 回复风格漂移，昨天精炼今天啰嗦，用户被迫反复重复同样的要求。

本质上是把"应该长期生效的约束"错误地寄托在了会话记忆上。

# 怎么写

我的结构固定为五块，总共控制在 60 行以内：

```markdown
# 定位：这个工作空间的用途，agent 的角色边界
# 目录约定：memory/ 按主题组织，临时文件放 scratch/，用完即删
# 工具规则：什么情况用浏览器；cron 任务改动前先确认
# 安全边界：不改动 skills/ 下的文件；删除超过 10 个文件先列清单等人确认
# 回复规范：默认中文，先结论后细节，不用 emoji
```

两个写法原则：

1. **规则要可判定。** "删除前先确认"比"要小心"有用得多。写完自己问一句：agent 能机械地判断自己是否遵守了吗？
2. **迭代式补充。** agent 犯了两次同样的错，就把纠正写成一条规则，而不是在对话里再说一遍。AGENTS.md 是沉淀错误的缓冲区。

# 踩过的坑

- **写太长。** AGENTS.md 每次会话都占上下文，几百行的"完整手册"会稀释真正关键的几条规则。我裁到一屏之后，规则遵循率明显上升。
- **和系统提示词冲突。** 同一件事两处都写，措辞稍有出入 agent 就会摇摆。系统级的事交给系统提示词，工作空间的事才写进 AGENTS.md。
- **把它当记忆用。** 事实进 `memory/`，规则进 AGENTS.md，混在一起之后，想让 agent 忘掉一条过时规则比忘掉一个事实难得多。
- **放任 agent 自改不审查。** 它确实有权限改自己的说明书，但不做版本控制的话规则会悄悄漂移。我用 git 管着，每次改动 diff 一眼。
- **写敏感信息。** 它是工作空间里的纯文本文件，密钥、内网地址别往里放。

# 可复用的建议

- 一屏原则：超过一屏就删或拆；
- 全部用 if-then 句式，删掉形容词；
- 每个独立工作空间一份，不要指望一份通吃；
- 定期 review，过时的规则比没有规则更糟。

# 总结

AGENTS.md 不是文档，是接口。你给 agent 的约束越具体、越可判定，它的行为就越稳定。这份文件值得像代码一样对待：小、准、有版本、常审查。
