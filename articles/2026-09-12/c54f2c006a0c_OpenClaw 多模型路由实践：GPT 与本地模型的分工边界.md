## 背景

OpenClaw 本身不锁定单一模型。通过 `models` 配置，可以同时挂云端 provider 和本地推理端点（Ollama / LM Studio / vLLM 暴露的 OpenAI 兼容接口）。我见过的两种典型姿势：要么全部流量走一个云端旗舰模型，账单里一半 token 花在"把这段话总结一下"上；要么为了省钱全切本地，agent 多步工具链质量肉眼可见地下降，调 bug 的时间远超省下的 API 费。

## 问题

多模型路由的核心不是"能不能配"，而是"哪些任务值得上云、哪些必须留在本地"。判断粗糙，结果要么浪费钱，要么把敏感上下文（本地文件、个人日程）随请求送出了机器。

## 做法与步骤

**第一步：给任务分层。** 我用三个问题过一遍：吃推理能力吗？数据能出机器吗？调用频率多高？

- 规划、多步工具调用、代码生成 → 云端旗舰模型，作为主链路
- 会话摘要、消息分类、格式转换、草稿润色 → 本地模型
- 涉及隐私的读写 → 本地，或明确风险后上云
- 云端限流、网络抖动 → 本地兜底

**第二步：配置多 provider。** 示意结构（字段名以你所用版本的实际配置为准）：

```jsonc
{
  "models": {
    "providers": {
      "ollama": {
        "baseUrl": "http://127.0.0.1:11434/v1",
        "api": "openai-completions",
        "models": [{ "id": "qwen3:14b", "name": "Qwen3 14B (local)" }]
      }
    }
  },
  "agents": {
    "defaults": {
      "model": {
        "primary": "anthropic/claude-sonnet-4-5",
        "fallbacks": ["ollama/qwen3:14b"]
      }
    }
  }
}
```

**第三步：按 agent 绑定模型，而不是靠手动切。** 我专门跑一个"摘要 agent"固定用本地模型，由主 agent 以子任务形式调用；主 agent 保持云端。会话内的 `/model` 切换适合临时调试，不适合当长期策略。

**第四步：留路由日志。** 在插件或 hook 里记一条：时间、agent、任务类型、命中模型、token 数。每周扫一眼，错误路由和成本大头一目了然。

## 踩坑点

- **本地模型的 tool calling 兼容性是第一坑。** 部分推理栈对 function calling 支持不完整，表现为模型不发起调用或参数格式错乱。接入前先跑一个最小工具调用用例验证，别等 agent 卡死在循环里才发现。
- **上下文窗口差异。** 本地 8k/32k 的模型接长会话会静默截断，表现为"它好像忘了前面的约定"。长上下文任务不要下沉。
- **首 token 快 ≠ 整体快。** 本地小模型响应快是错觉，长输出时吞吐常常被云端反超。
- **fallback 条件要明确。** 只在超时、错误码、限流时降级；不要把"模型质量差"也当降级理由，否则问题会被兜底模型掩盖。
- **参数风格不一致。** 同一任务在两个模型间切换时，温度和 system prompt 版本要在各 agent 配置里固定，否则输出风格会跳。

## 可复用建议

1. 本地模型的定位用四个词概括：预处理、摘要、兜底、隐私沙箱。别让它承担最终交付质量。
2. 云端调用尽量收进独立的子 agent，主链路和工具链解耦，方便单独换模型、单独计费。
3. 建一个 10~20 条固定任务的回归清单，每次调整路由后跑一遍。靠感觉调路由，一定会来回震荡。
4. 显存吃紧时优先降参数量、保上下文长度，截断带来的隐性损失比慢更难排查。

## 总结

一句话：按任务路由，而不是按心情路由。云端模型买的是规划与工具链的可靠性，本地模型买的是成本、延迟与数据边界，把两者各自擅长的事想清楚，OpenClaw 的多 provider 配置才有价值。先小范围验证，再固化到 agent 配置里，比一步到位更稳。
