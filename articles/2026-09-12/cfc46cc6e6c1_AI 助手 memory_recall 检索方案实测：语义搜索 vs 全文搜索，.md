## 背景

在 OpenClaw 里，`memory_recall` 是决定"它到底记不记得你"的关键一环。agent 用了几个月之后，memory 目录会积累几百上千条笔记，recall 的检索质量直接决定助手回话是"秒懂"还是"装傻"。我最早用的是纯语义检索（embedding + 余弦相似度），用了一阵发现精确信息经常丢，于是把语义搜索和全文搜索做了组对比实验，最后落成了一个混合方案。

## 问题

两个典型的失败案例：

1. **纯语义的翻车**：我问"root 密码改过的那台服务器是哪台"，相似度排前面的是一堆泛泛的运维总结，真正包含 `ssh root@10.0.0.3` 的原始记录反而挤不进 top-5。embedding 对专有名词、IP、路径、错误码这类"高信息密度 token"不敏感。
2. **纯全文的翻车**：我写"上次部署脚本踩的那个坑"，FTS 按字面匹配，而当时记录里写的是"发布脚本"，召回直接为空。

结论很清楚：**语义赢在换说法，全文赢在精确名词，单选必翻车。**

## 做法

最终方案是混合检索 + RRF 融合，步骤如下：

1. **入库规范**：每条 memory 记录是带 frontmatter 的 Markdown，包含 `created_at`、`tags`、`session_id`；超过 500 字的按段落切 chunk。
2. **全文索引**：SQLite FTS5，中文走 trigram 分词器（默认的 unicode61 不切中文，这是第一个坑，后面细说）。
3. **向量索引**：本地跑 `bge-small-zh` 出 embedding，存 sqlite-vec，查询时算余弦相似度。
4. **融合**：两路各取 top-20，用 Reciprocal Rank Fusion 合并，权重取语义 0.6 / 全文 0.4，再叠加时间衰减（30 天半衰期）。
5. **截断**：按 token 预算取 top-5 塞进 prompt，每条附上时间戳，让模型自己判断新旧。

改造完在自建的 30 条测试集上跑，命中率从纯语义的 68% 提到 87%，精确 token 类问题的提升最明显。

## 踩坑点

- **FTS5 默认分词器不切中文**，整段会变成一个 token，全文索引形同虚设。trigram 或 jieba 预分词二选一，前者省事后者省空间。
- **embedding 模型换版本必须全量重算**。我在每条记录的 metadata 里存了 model 版本号，迁移时按版本灰度重算，避免新旧向量混在一个空间里比相似度。
- **没有时间衰减时旧记忆霸榜**。半年前的过时配置长期排第一，模型会把它当现状输出，加半衰期因子后才正常。
- **置信阈值别卡太死**。低分时段宁可多召回两条让模型在 prompt 里自己过滤，也比漏掉关键记录强。

## 可复用建议

- **原文永远保留**，索引只是派生物，随时可重建，别把 chunk 当唯一存储。
- **建一个小的"记忆回放测试集"**：20~30 条"问题 + 期望命中的记录 ID"，每次调检索参数跑一遍，比凭感觉调靠谱得多。
- **先全文兜底，再叠语义**。全文检索便宜、可解释、零外部依赖，语义是增量收益不是地基，顺序反了会浪费时间。

## 总结

语义搜索和全文搜索不是二选一，是互补：语义负责"换个说法也能找到"，全文负责"精确 token 一击命中"。混合 + RRF + 时间衰减这套组合，改造量一个下午，收益是实打实的命中率提升。建议任何 memory 超过 200 条的 agent 都上混合检索，测试集越早建越好。
