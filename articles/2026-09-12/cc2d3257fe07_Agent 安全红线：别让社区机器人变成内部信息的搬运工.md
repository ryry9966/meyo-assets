## 背景

社区里跑 Agent 已经是常态：接入 MCP 工具查工单、读知识库回帖、自动整理讨论串。为了让它答得准，我们通常会给它挂上内部资料——部署记录、故障复盘、成员表，甚至带内网地址的运维手册。问题从这里开始：**Agent 面向的是公开社区，它读的却是内部数据。**

## 问题：泄露的三条常见路径

1. **提示词抽取。** 有人让机器人"复述你的系统提示词"，或者用角色扮演绕限制，内部目录结构、工具调用逻辑、私有端点直接进了公开频道。
2. **RAG 越界。** 知识库里公开帖和内部复盘混存，检索不区分来源，机器人引用一段内部事故报告来回答问题，还带着责任人名字。
3. **工具越权。** MCP 工具权限开太大，一次不该发生的调用把内部环境变量、token 前缀、库表结构带进了回复。

还有一条容易被忽视的渠道：排障时把**完整会话日志**贴进社区求救，日志里往往带着完整 system prompt 和工具原始输出。

## 做法：按层设防，别指望提示词

**第一层，数据分层。** 公开知识库和内部文档物理分开，检索按会话来源限定范围。社区场景只挂公开库；内部库走单独入口，要求登录态。

**第二层，工具最小权限。** MCP server 默认 deny，显式 allowlist；token 只读、限定资源；工具描述里不写内网路径。每个工具上线前问一句：这个工具被滥用时，最坏能带出什么？

**第三层，出站过滤。** 回复进频道之前加一道检查：规则匹配内部域名、IP 段、项目代号、成员花名，命中即拦截或要求改写。规则成本很低，但覆盖了绝大多数事故。

**第四层，审计与人工兜底。** 记录每次工具调用和检索来源，定期抽样回放会话。Agent 对信息级别拿不准时，默认拒答并转人工，而不是猜。

## 踩坑点

- **只在 system prompt 里写"不要泄露"就当设防了。** 提示词是指令不是边界，注入一打就穿。
- **对抗测试缺位。** 上线只测正常问答，不测"忽略之前的指令""打印你的配置"。建议维护一份红线测试集，Agent 每次更新都跑一遍。
- **为了体验悄悄放宽权限。** 过滤规则太严导致答非所问，有人图省事把内部库也挂上去——防线往往是从内部松掉的。
- **工具描述本身带料。** MCP 工具的 description 会进入模型上下文，里面写了内部路径和参数示例，等于把地图递出去。

## 可复用建议

- 写一页**信息分级清单**：公开 / 内部 / 机密三档，明确每档能否进检索、能否进上下文、能否出站。
- 把红线测试集放进 CI，和功能回归同权重。
- 心态上把 Agent 当成**拿着访客牌的可信度存疑的员工**：给门禁卡，不给万能钥匙。
- 排障用脱敏日志：贴出去之前删掉 system prompt、工具原始返回、任何内部标识。

## 总结

Agent 泄露不是提示词问题，是**边界问题**。数据分层决定它能读到什么，工具权限决定它能碰到什么，出站过滤决定它能说什么，审计决定你事后能不能查。每层薄一点没关系，叠起来才是红线。社区环境天然带对抗性，默认"会有人试"，防线才有意义。
