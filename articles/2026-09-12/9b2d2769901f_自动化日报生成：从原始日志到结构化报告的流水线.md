## 背景

团队每天要交一份"日报"，内容大多来自散落各处的日志：服务运行日志、定时任务输出、告警记录。手动整理费时且容易漏。我用 OpenClaw 的定时任务加一个自定义工具，搭了一条从原始日志到结构化日报的流水线，稳定跑了一个多月，把过程记录下来。

## 问题

最初的做法很直接：把当天日志原样丢给 Agent，让它"总结成日报"。跑几次就暴露三个问题：

1. 日志动辄几十万 token，成本高，经常超上下文；
2. 模型会对原始日志"脑补"，报出根本没发生的事故，也会漏掉真正的异常；
3. 输出格式每次不一样，没法自动投递，也没法做逐日对比。

结论：LLM 适合做最后一层的归纳与措辞，不适合做前面的采集与对账，中间需要一层确定性的结构化处理。

## 做法

流水线分五步，每步一个独立脚本，由 Agent 串联：

1. **采集**：cron 定时拉取当天各来源日志到统一目录，文件名带日期。原始日志只增不改，作为事实底稿。
2. **归一化**：用 jq / Python 把 JSON lines、nginx access log 等不同格式转成统一 schema：`{ts, source, level, module, event, count}`。这一步纯规则，不进模型。
3. **聚合降噪**：按 module + event 分组计数，过滤 DEBUG 和心跳类噪音，"同一错误重复 500 次"压成一条带次数的记录。几十万行日志在这里缩成几百行摘要。
4. **模型归纳**：把结构化摘要喂给 Agent，prompt 里固定输出 schema（章节标题、字段、字数上限），temperature 调低。模型只解释异常、生成措辞，不负责计数。
5. **渲染投递**：模板引擎渲染成 Markdown，推送群 webhook 并归档到 `reports/2025-xx-xx.md`。

## 踩坑点

- **不要让模型碰原始日志**。哪怕截断输入，也保留幻觉风险。数字必须来自聚合层，模型只做表达。
- **时区问题**。日志里 UTC 和本地时间混着，第一版日报实际覆盖的是"昨天早八到今天早八"。统一在归一化层转时区。
- **schema 要在代码里校验**。模型偶尔漏字段或自创章节，投递前用 JSON Schema / pydantic 校验，不合格重试，两次仍失败就发告警而不是发半成品。
- **失败要有痕迹**。每一步的中间产物（原始日志、聚合结果、模型输入输出）都落盘，第二天可重跑，而不是从头排查。
- **日志级别不等于重要性**。有一次某服务连续 WARN 被降噪规则过滤，而那才是当天最大的问题。降噪规则必须留白名单兜底。

## 可复用建议

- schema 先行：日报字段结构先定下来，prompt、校验、模板都围绕它写；
- 原始日志保留 7–30 天，日报内容存疑时随时回溯验证；
- prompt 当代码管理，改动带版本号，出问题能 diff；
- 每周人工抽查一次日报与日志的一致性，这个环节暂时不建议省。

## 总结

这条流水线的核心思路是"确定性归一层 + 受限的模型层"：规则能做的绝不给模型，模型只做它擅长的归纳和表达。整体代码不到 300 行，大部分精力花在归一化和降噪规则上。如果你还在手动拼日报，建议先把归一化这一层做出来——它不依赖任何模型，做完之后再接 Agent 就是顺水推舟的事。
