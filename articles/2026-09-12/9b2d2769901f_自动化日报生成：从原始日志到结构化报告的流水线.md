## 背景

团队每天要发日报，素材散落在 git 提交、CI 记录、监控告警和工单系统里。手写日报的问题不是难，而是重复、容易漏，质量取决于当天谁在写。我们用 OpenClaw 的定时任务加 MCP 工具搭了一条流水线，让 agent 每天早上自动产出结构化日报，跑了一个多月，稳定可用。

## 问题

核心问题有三个：

1. 原始日志量大且异构，直接塞给模型会撑爆上下文，且噪声远大于信号；
2. 模型自由发挥时会"补写"日志里不存在的内容，日报一旦夹带幻觉，信任就没了；
3. 流水线无人值守，静默失败比失败更危险——你以为有日报，其实早就停了。

## 做法

流水线分四段：

**1. 采集与归一化。** 不让 agent 直接碰原始日志。先用脚本把 git log、CI 结果、告警数据各自收敛成统一的 JSONL，每条记录固定字段：`source`、`time`、`type`、`actor`、`summary`、`raw_ref`。这一步用普通脚本而非 LLM，稳定且零成本。

**2. 预过滤。** 按"昨日 00:00 至今日 00:00"的时间窗过滤，去掉重复项和纯噪音（比如重试成功的 CI 空跑）。实测这一步能把 token 量砍到原来的十分之一左右。

**3. 生成。** 固定时间由 OpenClaw 定时任务触发 agent，过滤后的 JSONL 通过 MCP 工具喂入。Prompt 里明确约束：只允许引用输入数据中存在的条目，每条结论必须携带 `raw_ref` 溯源，输出固定 JSON schema——今日变更、异常与风险、待跟进三段。

**4. 校验与投递。** 用 jsonschema 做输出校验，`raw_ref` 对不上输入日志的直接打回重试（温度设 0.1，重试两次仍失败则降级发送"原始数据附件 + 失败原因"）。通过后经 webhook 推送到群和邮件。

## 踩坑点

- **上下文溢出**：起初图省事投喂全量日志，第二天就撞了窗口上限。预过滤必须做，采集层还要限制单条 `summary` 长度。
- **溯源形同虚设**：只要求"带引用"没用，模型会编一个看起来合理的 `raw_ref`。必须程序化校验 ref 确实存在于输入中，校验不过就重试。
- **时区坑**：cron 按 UTC 跑，"昨天"的窗口错位八小时，凌晨告警被切到了前一天。窗口计算放在采集脚本里，用本地时区显式指定。
- **静默失败**：cron 悄悄挂了两周才被发现。之后加了心跳——流水线跑完向监控端点发一个 ping，超时未收到即告警。

## 可复用建议

- 报表 schema 保持稳定，下游才好归档和对比；改 schema 要当成接口变更对待，提前通知。
- 采集与生成彻底分离：采集失败不触发生成，宁可发一封"今日数据缺失"的降级日报。
- 原始 JSONL 落盘保留 30 天，方便回溯模型当时到底引用了什么。
- 留 10–20 天人工整理的"金标准"日报，评价新 prompt 或新模型时抽样比对，比肉眼感觉靠谱。

## 总结

这条流水线的价值不在"让模型写日报"，而在把不稳定的人工整理拆成：确定性的采集与过滤 + 受约束的生成 + 程序化校验。LLM 只做它擅长的归纳与措辞，事实和结构由工程保障。没有黑魔法，一个下午能搭出最小版本，之后按踩坑点逐个加固即可。
