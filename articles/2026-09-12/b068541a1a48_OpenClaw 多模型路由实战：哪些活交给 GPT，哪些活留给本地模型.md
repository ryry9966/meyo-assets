## 背景

OpenClaw 的典型用法是把微信 / Telegram / 网页等渠道接到一个常驻 Agent 上。很多人起步时只配一个模型，全部请求都走 GPT 级云模型。跑两周后通常遇到三件事：账单超预期、首 token 延迟不稳定，以及私有数据出域的合规顾虑。OpenClaw 本身支持多 provider 共存（云模型 + Ollama/vLLM 起的 Qwen、Llama 等），真正的问题是：路由策略怎么定。

## 问题

“什么任务用 GPT、什么任务用本地模型”不能拍脑袋。我自己踩过的两类坑：

- 把主 Agent 循环整个换成本地 7B，工具调用格式频繁出错，表现为“看起来回答了，但工具根本没触发”；
- 反过来，把所有预处理也丢给云模型，统计 token 消耗后发现，超过一半其实花在重复性的摘要、分类、脱敏上。

## 做法

核心原则一句话：**强模型管决策，小模型管体力活。**

1. **主循环用云模型。** 凡是涉及工具调用、多步规划、跨会话上下文推理的请求，走 GPT（或同级云模型）。这是质量底线，不建议省。
2. **辅助任务下沉到本地：**
   - 消息预处理：意图分类、是否需要唤醒 Agent、敏感信息脱敏；
   - 历史压缩：memory 定期摘要、旧会话归档；
   - 高频简单回复：闲聊兜底、模板化问答。
3. **路由实现：** 在插件 / hook 层加一个前置分类器。先用规则（消息长度、是否含工具意图关键词、是否命中已知模板），规则判断不了的，再让本地小模型做一次轻量分类，决定走 A 还是 B。
4. **兜底：** 本地服务超时或挂掉，自动回退云模型——宁可多花钱，不丢消息。

配置思路（示意）：

```yaml
models:
  primary: gpt-4o         # 主循环
  aux: ollama/qwen2.5:7b  # 摘要/分类/脱敏
routing:
  fallback: primary       # aux 异常时回退
```

## 踩坑点

1. **工具调用能力。** 很多本地模型对 function calling 的 schema 支持不稳。换模型前先跑一遍所有 MCP 工具的调用用例，别只看聊天质量。
2. **上下文窗口。** 本地 7B/14B 常见 8k~32k，长会话直接塞会被静默截断，表现为“忘了前面聊过什么”。摘要压缩策略要按目标模型的窗口来设计。
3. **冷启动。** Ollama 默认几分钟不活跃就卸载模型，首次请求慢 10 秒以上。常驻场景把 `keep_alive` 拉长，或直接换 vLLM。
4. **只按成本路由。** 省了钱但错一次工具调用，返工成本更高。任何路由改动都要先过评测。

## 可复用建议

- 先全量跑云模型一周，导出调用日志，统计哪些任务其实“本地也能过”（短输入、无工具、模式化），这些就是下沉候选；
- 本地模型优先选带 tool-calling 微调的版本（如 Qwen2.5-Instruct 系）；
- 每个模型单独记 token 数和延迟，一周后数据自然会告诉你路由对不对；
- 分层不要超过两层。三层路由（云强 / 云便宜 / 本地）看着精细，维护成本远超收益。

## 总结

多模型路由不是省钱技巧，而是资源分层：把推理预算花在决策上，把确定性高的体力活留给本地。路径很清晰：用日志找下沉空间，用评测集守住质量底线，用兜底机制保住可用性。三步走完，账单和延迟都会明显回落，而且全程不需要改动 Agent 本身的逻辑。
