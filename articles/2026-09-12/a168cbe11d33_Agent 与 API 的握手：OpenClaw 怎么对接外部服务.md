## 背景

Agent 的价值不在"会聊"，而在"能动手"。OpenClaw 里一条典型链路是：模型决定调用哪个工具 → 框架把请求转成实际的 API 调用 → 把结果回灌给模型继续推理。这条链路里，模型只负责"决定"，真正和外部服务握手的，是你写的适配层。这一层做不牢，前面再强的模型也是空中楼阁。

## 问题

实际对接时最常见的三类麻烦：

1. **认证与凭据**：API key 放哪、怎么轮换、过期了谁兜底；
2. **参数可信度**：LLM 生成的参数不一定符合 schema，直接透传就是事故源；
3. **失败语义**：超时、限流、部分成功，这些信号如何让模型"看懂"并自我纠正，而不是被静默吞掉。

## 做法

以把一个内部查询服务接进 OpenClaw 为例，我的步骤是：

**第一步：先手写最小客户端，别急着接 Agent。** 用普通脚本把鉴权、分页、错误码跑通。API 本身的问题在这一步暴露最便宜。

**第二步：把工具注册成显式 schema。** OpenClaw 的工具描述会直接进入模型上下文，所以 description 要写清"什么时候该用我"，参数要标明类型、枚举和默认值。宁可少暴露参数，也不要把原始 API 全量搬进来。

**第三步：在适配层做校验和裁剪。** 用 JSON Schema 先校验 LLM 产出的参数，非法就立刻返回结构化错误让模型重试，而不是打到线上。返回值同样要裁剪——大段原始 JSON 既挤占上下文，又稀释关键信息。

**第四步：接 MCP。** 如果这个服务要被多个 Agent 或多个客户端共用，包一层 MCP server 更划算：工具定义和凭据集中管理，客户端只管调用。

**第五步：灰度验证。** 先用 dry-run 模式跑一轮（只生成请求不真正执行），人工核对无误后再放行写操作。

## 踩坑点

- **token 过期不重试**：凭据过期返回 401，模型看到错误文本后开始瞎编参数硬试。鉴权类错误要在适配层拦截并触发刷新，不要下放给模型。
- **写操作没做幂等**：模型重试导致重复下单、重复建单。写接口务必带幂等键，或在适配层做去重。
- **错误信息太"人类"**：把整段 HTML 错误页丢回给模型，它解析不动。返回 code + message + hint 的三段式结构化错误，模型纠错成功率明显提升。
- **限流靠碰运气**：客户端没做本地限速，一并发就 429。加个简单的令牌桶，比事后收拾省心。
- **schema 漂移没人管**：外部 API 改了字段，工具还按老结构返回。关键工具建议加契约测试，CI 里定期跑。

## 可复用建议

- 适配层薄一点：只做校验、鉴权、裁剪三件事，业务逻辑留在 API 侧；
- 所有工具返回统一结构（success / data / error），模型处理起来最稳；
- 敏感操作加 confirm 钩子，写操作默认人工过一道；
- 日志里记 request id 和工具名，出问题能回放。

## 总结

对接外部服务的本质，是在一个不可靠的"决策者"（LLM）和一个不可靠的"执行者"（外部 API）中间，垫上一层确定性的代码。OpenClaw 的工具体系和 MCP 让这层垫片有了标准形状，但鉴权、幂等、错误语义这些工程细节，仍要自己一寸寸铺。慢一点，反而稳。
