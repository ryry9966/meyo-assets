## 背景

我们用 OpenClaw 搭自动化任务流有一段时间了。单 Agent 工作流跑熟之后，瓶颈很快暴露：让一个 Agent 同时处理「扫描代码库 + 整理文档 + 生成测试报告」这类复合任务时，上下文被工具输出塞满，Agent 开始遗忘早先设定的约束，串行执行也让总耗时线性增长。

Subagent 编排是最直接的解法：主 Agent 只负责拆解和汇总，每个子 Agent 带独立上下文去做一件具体的事。

## 问题

单 Agent 模式有三个痛点：

1. **上下文污染**：目录扫描、日志抓取这类原始输出直接进入主对话，几十轮之后早期约束被稀释，行为开始漂移；
2. **串行等待**：互不依赖的任务排队执行，总时长等于各任务之和；
3. **失败传染**：一个环节的报错混进上下文，影响后续所有判断。

## 做法

我们的编排结构分三步：

**1. 拆解与依赖分析。** 主 Agent 先产出任务清单，明确每个子任务的输入、预期产出和依赖关系。关键原则：只拆「只读」任务做并行，涉及写同一资源的任务保持串行。

**2. 并行派发。** 每个子 Agent 收到的是一份**自包含的任务描述**，不依赖主对话历史。子 Agent 完成后不回传大段文本，而是把结果写入约定路径（如 `workspace/results/task-03.md`），只返回摘要和文件路径。

**3. 汇总校验。** 主 Agent 收齐摘要后读取结果文件做交叉核对，决定是否补派任务，而不是盲目相信返回值。

## 踩坑点

- **子 Agent 缺上下文**。最初直接复制主对话片段给子 Agent，它拿着残缺信息自由发挥。解法是给每个子任务写完整 brief：目标、边界、产出格式、禁止事项，缺一不可。
- **并行写冲突**。两个子 Agent 同时改同一配置文件，后写覆盖先写。现在按资源分片，同一资源只归一个子 Agent 处理。
- **成本失控**。并行意味着 token 消耗也是并行的。一次 8 个子 Agent 同时全库扫描，一轮费用抵平时一天。此后每个子 Agent 都加工具调用次数和输出长度上限。
- **失败静默**。子 Agent 内部报错后返回空结果，主 Agent 当作正常继续。必须让子 Agent 显式返回状态（成功/失败/部分完成），失败任务单独重试。

## 可复用建议

- 判断是否值得并行的标准：子任务之间是否只通过**文件/数据**交互，而不需要来回协商。需要讨论的任务，并行反而更慢。
- 产出走文件不走对话，上下文隔离才算真正落地。
- 先串行跑通，再逐个任务并行化，保留串行版本做对照，方便区分是拆解问题还是执行问题。
- 给每个子 Agent 设预算（步数、时长、token），超限即中止并上报。

## 总结

Subagent 编排不是「更多 Agent = 更强」，本质是用上下文隔离换稳定性、用并行换时延。拆解质量决定上限，边界控制决定下限。建议从两个互不依赖的只读任务开始试，跑通汇总链路后再扩展到写场景。
