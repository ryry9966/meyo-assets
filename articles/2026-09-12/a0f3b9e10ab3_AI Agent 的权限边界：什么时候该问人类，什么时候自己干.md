## 背景

跑过一段 Agent 都有体感：工具权限给少了，它变成一问一答的傀儡，自动化名存实亡；给多了，它会在你泡咖啡的时候把测试库清了。OpenClaw 这类能挂 MCP、插件、执行 shell 的框架，让"加能力"变得很容易，"划边界"却没有现成答案。

## 问题

多数人的第一版方案是写进系统提示词："危险操作先问我。"跑几天会发现两点：一是模型对"危险"的判断和人不一样，它觉得删个分支不算事；二是长会话里提示词约束会漂移，第 200 轮它已经"忘了"。本质原因：**权限边界是系统工程问题，不是提示词工程问题。**

## 做法：按"可逆性 × 爆炸半径"分四档

我把所有工具调用分四档，硬边界做在工具网关层：

- **T0 只读**：查询、搜索、读文件。直接放行。
- **T1 工作区内可逆写**：改代码、写文件，有 git 兜底。自动执行，但必须落审计日志，会话结束给 diff 摘要。
- **T2 影响共享状态**：发 PR 评论、提 issue、调测试环境接口。默认自动，走白名单 + 配额（比如每小时 N 次外部调用、单次 diff 超 X 行就降级为询问）。
- **T3 不可逆 / 对外 / 花钱**：生产部署、删数据、真实发消息给人、付费 API、动凭证。一律停下来问。

判断标准就三个维度，比笼统的"危不危险"好用得多：

1. **可逆吗**——git revert 能救回来的不算大事；
2. **爆炸半径**——只影响自己沙箱，还是波及别人、线上、钱包；
3. **成本**——一次调用花多少钱、占多少配额。

工程上三个落地件：

1. **工具描述写清副作用**。MCP tool 的 description 里明确写"只读"还是"写生产库"，模型分档准确率会明显提升。
2. **确认接口结构化**。别让 Agent 发一句"我能执行吗？"，而是网关把 diff、影响范围、成本摘要打包，人的选项只有执行 / 改参数 / 取消。问得便宜，人才会认真看。
3. **凭证分层**。Agent 持有的 token 天然不含 T3 权限，让它想做也做不了，人工通道单独走。这比任何提示词都可靠。

## 踩坑点

- **确认疲劳**：问得太频繁，人会养成无脑点"同意"的习惯——这比不问更糟，因为它制造虚假的安全感。宁可少问，问就要有价值。
- **批量授权**：批一次等于批了 50 个删除。T3 必须按批次写明范围，不接受"以上全部"。
- **超时默认值**：人没及时回复时，Agent 必须默认取消（default deny），否则确认流程只是个装饰。
- **边界写在 prompt 里**：长任务、上下文压缩、多 Agent 传递之后必失效。硬约束全部下沉到工具层，prompt 只做软引导。

## 可复用建议

- 接入新 MCP / 插件时先问一句：它的每个工具落在哪一档？答不上来就先按 T2 处理。
- 危险操作拆成独立工具，别和高频只读操作挤在同一个接口里靠参数区分。
- 审计日志和分档策略一起设计，出了事要能回答"它哪一步、经没经过我"。
- 每周翻一次审计日志：问了但答案永远是"同意"的操作降档，没问但事后心惊的操作升档。

## 总结

权限边界不是一个开关，而是一张按"可逆性、爆炸半径、成本"划出的分级表：T0/T1 完全放开，T2 有约束地自动，T3 停下来认真问。问得少、问得准、问得有结构，效率和安全感才能同时成立。记住一条：**边界做在系统里，别只写在提示词里。**
