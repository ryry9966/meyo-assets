## 背景

OpenClaw 的 cron 能力适合跑那些"到点就该发生"的事：每天早上汇总工作区变更、每周整理一次笔记索引、定期检查某个数据源并在异常时提醒。配置一个任务本身不难，难的是 instruction——很多人第一版都是从聊天里复制一句话过去，结果任务跑出来的东西时好时坏。

社区群里关于 cron 的高频问题，一半以上不在调度本身，而在 instruction 的写法。这篇帖把我的实践沉淀一下。

## 问题：cron 任务和对话是两种东西

交互式对话有上下文、有即时反馈，你说得含糊，agent 还会追问。cron 任务是冷启动：agent 在调度时刻醒来，手里只有那段 instruction，没有上一轮对话，也没有你在线纠正的机会——跑偏了要等人工查看才发现。

所以 cron instruction 的本质不是 prompt，而是一份**无人值守的交接单**。

## 做法：把 instruction 当交接单写

我的模板分六段：

```
【目标】一句话说清任务存在的原因
【输入】数据从哪来：哪个工具、哪个文件路径、哪个 API
【步骤】按序号列动作，每步只做一件事
【输出】发到哪个 channel，用什么格式，附固定模板
【禁止】不做什么：不扩展话题、不改配置、不调用某类工具
【异常】工具失败或数据缺失时怎么办：报告而不是编造
```

几个关键点：

**输出格式要锁死。** 结果要给下游（脚本、另一条自动化链）消费时，就在 instruction 里给出严格模板：固定字段、固定分隔符，并写明"除模板内容外不输出任何解释"。否则 agent 每次措辞不同，解析必然失败。

**状态外置。** 需要"上次跑到哪"的任务（比如增量同步），别指望 agent 记得上一轮。让它结束时把水位写进一个文件，instruction 里写明读写路径。agent 是无状态的，文件才是记忆。

**幂等。** 写清"若发现本次内容已处理过，直接跳过并报告"。cron 偶发重跑不罕见，没有幂等约束就会重复发消息、重复改文件。

**失败降级。** 一定要写"数据源不可用时输出失败说明，不要猜测或补全"。没这句，agent 为了"完成"会编。

## 踩坑点

1. **相对时间歧义。** 写"昨天"，agent 对"昨天"的计算可能和你想的不一致，尤其跨时区、跨午夜触发。改成"以系统当前日期为准，取前一自然日"。
2. **塞太多步。** 一个 instruction 塞七八个环节，任何一步的歧义都会被放大。超过四五步就拆成多个 cron，agent 只负责需要判断力的部分。
3. **没写输出通道。** 只说"汇总给我"，agent 可能回在会话里而不是你守着的 channel。投递目标、要不要 @人，都要写明。
4. **高频任务裸跑。** 每 5 分钟一次的任务，一次异常就是一天 288 条垃圾输出。先写好异常分支，再提频。
5. **改了不测。** 任何改动先手动触发验证一次，别等第二天早上才发现格式变了。

## 可复用建议

- instruction 存 git，像代码一样 review 和回滚，出问题能 diff 出"从哪天开始变的"。
- 要求任务结束时输出一行状态摘要：成功/失败、处理条数、耗时，排查效率完全不同。
- 从每天一次起步，稳定观察一周后再提频。
- 沉淀模板库：日报类、监控类、整理类各留一份底稿，新任务改参数即可。

## 总结

Cron instruction 的质量，取决于你把它当"聊天消息"还是"值班交接单"。目标、输入、步骤、输出、禁止、异常，六段写全，冷启动的 agent 就有了稳定的执行边界。定时自动化的真正收益不在"它跑了"，而在"它每次都跑出你能预期的结果"——这基本只取决于那几十行 instruction 够不够工程化。
