## 背景

在 OpenClaw 里，`memory_recall` 是 Agent 日常调用频率最高的工具之一：会话摘要、用户偏好、项目决策都散落在 memory 文件里，召回质量直接决定"助手懂不懂你"。目前记忆检索有两条常见路径：基于 SQLite FTS5 的全文检索（BM25），以及基于 embedding 的向量语义检索。我过去几个月一直跑混合模式，但两路各自贡献多少，心里没数，于是做了一次小规模对比。

## 问题

我的记忆库约 400 条 markdown 记录，日常遇到的失败案例分两类：

- **全文检索败给转述**：笔记里写"部署窗口周二上午"，用户问"周一晚上能不能上线"，关键词零重叠，BM25 直接空手而归。
- **语义召回漂移**：查"数据库连接池配置"，向量检索拉回一堆"数据库优化讨论"，语义相近但不是要的东西。

核心问题：两条路径各在什么场景下可靠，参数怎么配才划算。

## 做法

没有追求抽象指标，而是从真实使用里抽了 30 条查询，人工标注期望命中的记录（每条 1–2 篇），然后测三种配置：

1. 纯全文（BM25）
2. 纯向量（bge-m3 做 embedding，每块 512 token）
3. 混合：两路各召回 8 条，用 RRF（倒数排名融合）合并

统计口径是 hit@3，即期望记录是否出现在前三。

结果（个人数据，仅供参考）：

- 纯全文：21/30。关键词型查询基本全中，转述型查询丢了 7 条
- 纯向量：17/30。转述类明显改善，但"近似但不相关"导致 6 条误召回
- 混合 RRF：26/30。转述被向量路兜住，精确词被 BM25 兜住

两路的错误集合几乎不重叠，这是混合方案能拿高分的原因。

## 踩坑点

- **中文分词是最大的坑**。FTS5 默认 tokenizer 处理中文表现很差，整句会被切碎或粘连，BM25 命中率严重靠运气。换用 jieba 类分词后，纯全文从 14/30 提到 21/30。
- **embedding 模型对中文差异巨大**。换过两个模型，同一查询集差了 4 次命中。换模型意味着全库重嵌入，成本要提前算进去。
- **分块大小影响召回**。1024 token 一块时，长笔记里的关键决策段被向量"稀释"，一直召回不上；回到 512 后恢复。
- **索引新鲜度**。向量索引是批处理的，新写入的记忆要等一轮才能被召回；BM25 写入即时可见。"刚记下、马上要用"的场景，全文是保底。

## 可复用建议

- 直接上**混合 + RRF**，别纠结单选。参数空间很小：每路召回 8–10 条，融合收益已经接近上限。
- 写记忆时**主动留关键词钩子**：笔记头部列一行别名和关键词。这是最便宜的检索优化，比反复调向量参数管用。
- **留一份 30 条的评测集**，每次换模型、换分词、改分块后跑一遍回归，防止"升级即降级"。
- 记忆条目少于 100 条时，纯全文就够；小语料上向量收益有限，反而增加一条需要维护的索引链路。

## 总结

语义和全文没有胜负，它们错在不同的地方：全文精确但僵硬，语义灵活但漂移，混合 RRF 取长补短。我现在的配置是：混合检索 + jieba 分词 + 512 分块 + 30 条回归集守底。对 Agent 的 memory_recall 而言，检索算法只排第二，第一重要的是你的记忆笔记本身是不是按"可被检索"的方式写的——关键词、别名、独立成段，这些笔记层面的功夫，往往比换任何检索方案都值钱。
