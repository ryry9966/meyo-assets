## 背景

给 Agent 配上 shell 和文件工具之后，效率提升是实打实的，但很多人心里都悬着一件事：它会不会哪天手滑，把不该删的东西删了。LLM 的输出本质是概率性的，它会以很高的置信度犯一些人类不会犯的错。所以这个问题的正确解法不是“把提示词写得更凶”，而是承认模型一定会出错，然后在系统层保证出错的代价可控。OpenClaw 的 sandbox 模型就是围绕这个思路设计的。

## 问题：误删实际长什么样

真实场景里，“误删”很少是模型突发奇想要搞破坏，通常是三种形式：

1. **路径理解偏差**：你说“清理一下 tmp 下的东西”，它对工作目录的感知和你不一致，理解成了 `/tmp`；
2. **变量展开事故**：执行 `rm -rf $BUILD_DIR` 时变量为空，命令退化成灾难形态；
3. **顺手的级联操作**：在目录重构过程中“清理”了它认为无用的文件。

这些不是模型“坏”，是概率输出的正常副作用。纯靠 prompt 约束，等于把安全边界建在概率上。

## OpenClaw 的做法：四层防线

**1. 路径越狱。** 所有文件工具经过统一解析层：先 `realpath` 解析出真实路径，再判断是否落在 workspace 内，界外默认拒绝。这是工具层的硬拦截，不是 prompt 约定，模型“想到”界外路径也没用。

**2. 最小权限运行时。** Agent 进程以专用 sandbox 用户运行，系统目录只读挂载。即使前一层被绕过，物理上也没有删除权限。两层独立生效，不互为前提。

**3. 破坏性命令闸门。** Shell 执行层对 `rm`、`shred`、`dd` 等模式做识别，命中后强制人工确认，或降级为移入回收站。回收站带保留期，到期才真正清理。

**4. 快照兜底。** 批量改动前自动打快照或 git commit，让“删除”变成可回滚事件。这是最后一道，也是最实用的一道。

## 踩坑点

- **symlink 逃逸**：只检查路径字符串的话，Agent 可以在 workspace 内建软链指向外部，再“合法”地穿过去删。必须用解析后的真实路径做判断，并对 symlink 创建本身设限。
- **字符串匹配会被绕过**：base64 编码再管道给 sh、变量拼接，都能绕开命令黑名单。闸门要落在执行层（身份、路径、权限），文本过滤只能算辅助。
- **挂载破坏隔离**：为了图省事把宿主机 home 目录挂进 sandbox，所有隔离瞬间失效。目录挂载要走白名单加只读标志。
- **过严导致被关掉**：闸门太激进，用户烦了直接关 sandbox，安全性反而倒退。默认策略应该是“回收站替代删除”这种低摩擦方案，而不是逢删必拦。

## 可复用建议

- 默认拒绝，再按需开白名单，别反过来；
- 安全边界永远不放在 prompt 里，prompt 是效率工具，不是安全机制；
- 破坏性操作先做“可逆”，再做“拦截”：回收站加快照能覆盖九成场景；
- 定期做恢复演练，没验证过还原流程的快照不算数；
- 审计日志记录解析后的真实路径，而不只是模型的原始输入，否则排查时对不上号。

## 总结

Agent 不误删，靠的不是模型听话，而是四层各司其职：路径越狱管“够得着哪”，最小权限管“有权删什么”，闸门和回收站管“删了能否反悔”。任何单层都不是绝对可靠，但叠加起来，破坏性操作的落地成本远超收益。对自动化的合理预期是：允许它犯错，但让错误可逆。这也是我们建议每个 OpenClaw 用户保持 sandbox 默认开启的原因。
