## 背景

模型本身是无状态的。每次新会话，你的 Agent 对你而言都是陌生人——不知道你用 2 空格缩进、讨厌废话式回答、默认走某个部署流程。很多人的解法是把聊天记录整个塞回上下文，结果 token 成本线性膨胀，噪声还淹没了真正有用的信息。如果想让 OpenClaw 的 Agent 长期当助手，记忆必须是一个独立的子系统来设计，而不是上下文的堆料。

## 问题拆解

落地前先想清楚三件事：

- **记什么**：偏好（代码风格、回复详略、常用工具链）和事件（上周聊过什么）是两类东西，混在一起存必然乱；
- **怎么写**：全自动提取容易污染记忆库，全手动没人坚持得下来；
- **怎么读**：检索不准的记忆等于没记，还浪费 token。

## 做法：分层存储 + 一条写入管道

**1. 分四层：**

- 工作记忆：当前会话上下文，不落盘；
- 情景记忆：会话结束后由 LLM 生成摘要，按时间归档；
- 语义记忆（核心）：结构化偏好条目，schema 建议 `category / key / value / scope / confidence / source_session / updated_at`；
- 程序记忆：验证过的工作流，存成可复用的 recipe。

**2. 写入管道：** 会话结束触发提取，只抽「明确表达的稳定偏好」→ 与现有条目做冲突检测 → 高置信度覆盖、低置信度进待确认队列 → 落 SQLite，同时建向量索引供语义检索。

**3. 读取策略：** 会话启动时注入 top-k 高频核心偏好，预算硬编码（比如 300 token）；会话中通过 MCP 工具 `memory_recall(query)` 按需检索。把记忆直接暴露成 MCP tools（`recall / update / forget`），任何客户端和插件都能复用，这是我认为最划算的一步。

## 踩坑点

1. **全自动写入等于慢性中毒。** 跑两周后上下文里全是过时琐碎信息。限制写入口径：用户显式说「记住/以后都」，或同一偏好出现 ≥3 次才落库。
2. **偏好冲突不是 bug。** 工作仓库用 tabs、私人项目用 spaces 很正常。`scope` 字段（全局/项目/话题）必须第一天就有，事后清洗成本极高。
3. **提取 prompt 改版后新旧数据格式不一致**，召回会乱。给记忆条目加 `schema_version`。
4. **记忆回灌**：检索出的记忆被再次当新事实提取，套娃。写入时标记来源，来源是 memory 的条目不再回写。
5. **遗忘必须是一等公民。** 没有显式 `forget` 命令和时间衰减，用户记错一次就会直接关掉功能——记错比不记更伤信任。
6. **安全别漏**：记忆是持久化的用户数据，召回注入上下文前走一遍和普通输入相同的过滤，防投毒常驻。

## 可复用建议

- 先做窄：只记三类（代码风格、沟通偏好、工具链），比大而全可用性高一个量级；
- 每条记忆可追溯，`source_session` 排障时救命；
- 读取永远 top-k + 固定预算，不搞全量注入；
- 提供一个查看记忆的命令，让用户能看到并手动删除，透明度决定留存率。

## 总结

记忆系统的难点不在存储，而在治理：写入门槛、冲突策略、遗忘机制。建议的路线是——结构化 schema、窄范围、半自动写入先跑起来，观察一两个月的实际召回质量，再逐步放开自动提取。先让它「记得准」，再谈「记得多」。
