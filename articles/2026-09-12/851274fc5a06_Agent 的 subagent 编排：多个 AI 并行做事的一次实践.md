## 背景

用单 agent 干活久了，会遇到一个很自然的瓶颈：任务一重、一多，串行执行又慢又容易丢信息。比如让 agent 同时整理十几个网页、汇总成一份报告，串行跑下来不仅耗时长，中间结果还会把上下文塞满，越到后面越"记不住前面的东西"。

OpenClaw 这类框架本身支持 agent 循环加 MCP 工具调用，天然适合把重活下放给 subagent：主 agent 负责拆解和汇总，子 agent 各自独立干活。下面是我把一批"批量阅读 + 汇总"类任务改成并行编排的过程记录。

## 问题

"多开几个 agent"听起来简单，实际落地是三个工程问题：

1. 任务怎么拆，拆到什么粒度；
2. 子结果怎么收，主 agent 的上下文装不装得下；
3. 出错了怎么办，一个分支挂掉要不要拖垮整体。

## 做法

我的编排结构大致分六步：

1. **主 agent 只做两件事**：拆任务、收结果。抓取、长文阅读、批量处理全部下放，主 agent 不干重活。
2. **定义固定的子任务接口**：输入是结构化参数（目标、范围、输出格式），输出统一为 JSON 摘要，并且限制长度。
3. **上下文隔离**：每个 subagent 用独立会话，工具权限按需收敛——只读任务绝不给写权限。
4. **并发控制**：并行度压在 3~5，用队列跑。先用串行模式跑通一轮验证 prompt，再切并行。
5. **聚合规则**：主 agent 只接收每个子任务不超过三百字的结构化摘要，不收原始全文；信息冲突的地方标记出来，不擅自裁决。
6. **失败降级**：子 agent 超时或输出不合法就重试一次，再失败就标记"该部分缺失"，绝不让单分支卡死整体。

## 踩坑点

- **上下文传染**。早期图省事让子 agent 共享主会话历史，结果子任务被无关信息带偏，输出质量明显下降。改成独立上下文后才恢复。
- **汇总爆炸**。直接把子任务全文丢回主 agent，两轮就把上下文打满。子结果必须在子会话内先完成摘要。
- **并行写冲突**。两个 subagent 同时整理同一个文件，互相覆盖。共享写资源要么串行，要么拆成"并行只读 + 一次统一写入"。
- **假成功**。子 agent 偶尔会在失败时"编一个看起来合理的结果"。我在接口里强制加了来源和置信字段，聚合时校验，能兜住大部分。
- **成本放大**。并行不是免费的，token 消耗近似任务数的线性放大。拆之前先估一下：这个任务值不值得拆。

## 可复用建议

- 子 agent 的 prompt 全部模板化，只替换任务参数，方便做回归测试；
- 保留每个子会话的完整日志和 trace，出问题能复盘到具体分支；
- 拆分粒度以"一个子 agent 一次能独立完成、结果可校验"为准，拆太碎协调成本反而更高；
- 先并行只读任务，所有写操作收敛到一个分支统一执行；
- 并行度是最后调的旋钮，不是第一步。

## 总结

这轮实践下来，最大的体会是：subagent 并行的收益主要来自**上下文隔离 + 结果结构化**，而不是单纯"多开"。隔离让每个分支不被污染，结构化让汇总可控，并行度才真正转化为速度。先把单分支跑稳，再放大并发，工程上才算站得住。
