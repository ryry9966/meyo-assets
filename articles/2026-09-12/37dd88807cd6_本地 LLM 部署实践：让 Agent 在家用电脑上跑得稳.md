## 背景

社区里不少人用 OpenClaw 搭 Agent、挂 MCP 工具做自动化。这类任务经常涉及本地文件、聊天记录、内部文档，丢给云端 API 总有点不放心；而且自动化脚本一跑就是几百次调用，token 费用也不小。所以我把主力 Agent 的"日常档位"切到了本地模型，云端只兜底难题。这篇记录一下过程和踩坑，给有同样想法的人省点时间。

## 问题

本地部署的难点不是"跑起来"，而是"在 Agent 场景里跑得稳"：

- 消费级显卡显存有限，长上下文 + 工具调用结果很容易撑爆显存；
- 量化后的小模型在多轮 tool calling 上明显比云端模型脆，一个 JSON 格式错误就断掉整个循环；
- 交互式聊天能跑，不代表 Agent 循环（几十轮、每轮塞工具返回）能跑。

## 做法

1. **选推理引擎。** 图省事用 Ollama，一条命令起服务，自带 OpenAI 兼容接口；要压吞吐和并发用 llama.cpp server 或 vLLM（后者显存要求高）。我的路径：Ollama 起步验证可行性，稳定后再迁 llama.cpp。
2. **按显存选模型。** 8GB 显存跑 7B/8B 的 Q4_K_M；12–16GB 上 14B；24GB 可以试 32B 低量化。中文场景优先 Qwen 系列原生 tool calling 版本，避开加过自定义模板的社区魔改版。
3. **量化档位。** Q4_K_M 是性价比默认值，有余量上 Q5_K_M。低于 Q4 的多轮工具调用错误率明显上升，不建议给 Agent 用。
4. **上下文。** Ollama 默认 `num_ctx` 很小，必须显式拉到 16K 以上——Agent 历史 + 工具输出吃 context 非常快，同时把 KV cache 的显存预算算进去。
5. **接入 Agent。** 在 OpenClaw 配置里把 base_url 指向本地端点，先跑一个只挂单个 MCP 工具的最小 Agent：验证能否正确发起调用、能否解析返回。通过后再逐步加工具。
6. **加降级路由。** 本地模型连续两次工具调用失败就切云端兜底，别让自动化任务卡死在弱模型上。

## 踩坑点

- **上下文静默截断：** 忘调 `num_ctx`，Agent 聊到一半"失忆"，工具结果被裁掉后开始瞎编参数。这是最高频的坑。
- **KV cache 吃显存：** 权重 8GB 不代表总占用 8GB，长上下文能把 16GB 卡打爆，表现为推理中途 OOM。建议留 20–30% 余量。
- **温度参数：** 聊天用 0.7 没问题，Agent 工具调用务必压到 0.1–0.2，否则参数幻觉概率翻倍。
- **并发排队：** Ollama 默认串行处理，Agent 并行发多个工具调用会排队，吞吐直接掉。需要的话调 `OLLAMA_NUM_PARALLEL`。
- **漏算 embedding 模型：** 记忆 / RAG 插件还需要一个本地 embedding 服务，显存要一起预算。

## 可复用建议

- **用自己的 Agent 循环做 benchmark**，别信通用榜单——同一个模型在公开评测上不错，可能在你那套 MCP 工具链上频繁输出格式错误。
- **版本全部进 git：** 引擎版本、模型 hash、启动参数、Modelfile 都固化下来。本地部署最怕"上周还好好的"。
- **分层路由是长期最优解：** 本地处理隐私、高频、廉价任务，难题上云端，两者用同一套 OpenAI 兼容接口做抽象，切换零成本。

## 总结

本地 LLM 在家用硬件上已经可用，但它的定位是 Agent 栈里的"经济档 + 隐私档"，不是云端模型的平替。核心功课集中在三处：显存预算（权重 + KV cache）、上下文配置、工具调用稳定性验证。先用最小 Agent 跑通闭环再谈规模，能少走很多弯路。欢迎在评论区交流你们的显存配置和模型选型。
