## 背景

用 OpenClaw 做自动化一段时间后，常见的瓶颈不在模型能力，而在编排方式：所有事都压在一个主会话里串行执行。查十个仓库、跑一批 MCP 数据源核对、给插件做回归——这些任务彼此独立，但主 agent 只能一件件做，而且中间产物全堆在上下文里，几轮之后上下文被污染，后续判断质量明显下降。

## 问题

具体表现是三个：

1. **串行慢**：天然独立的任务被迫排队；
2. **上下文膨胀**：中间结果挤占有效上下文，主 agent 开始"忘事"；
3. **单点阻塞**：一个长任务卡住，后面全部干等。

## 做法

我的方案是经典的 fan-out / fan-in：主 agent 只做拆解、派发、汇总，执行全部下放给 subagent。

**Step 1：判定可并行性。** 只拆满足三个条件的任务：输入独立、产出有界、失败可单独重试。不满足就老实串行。

**Step 2：写任务卡。** 每个 subagent 的 prompt 用固定模板：目标、范围边界、可用工具、输出格式（严格 JSON 或固定段落结构）、禁止事项。subagent 上下文必须干净——只给这一张卡，不继承主会话历史。

**Step 3：并行派发。** 主 agent 一次 spawn 3~5 个 subagent，各自跑完后把结果写入独立文件（如 `results/01.json`），不在会话里长篇汇报。

**Step 4：汇总。** 主 agent 逐个读文件、去重、合并、给结论。此时主会话里只有摘要，原始细节留在文件中按需取用。

举个实际例子：给一个 MCP 插件做数据源回归，主 agent 把 12 个数据源拆成 4 组，spawn 4 个 subagent 各查一组，每个只返回"通过/异常 + 证据路径"，主 agent 汇总成一张表。原来串行约 40 分钟的活，8 分钟跑完，主会话上下文占用不到原来的三分之一。

## 踩坑点

- **subagent 返回自由文本**：汇总时格式各异，逼主 agent 再解析一轮。输出格式必须在任务卡里写死，优先结构化 JSON。
- **并发写同一个文件**：两个 subagent 往同一文件追加，内容互相覆盖。改为一 subagent 一文件，汇总阶段才合并。
- **不设超时**：一个 subagent 卡死，整批干等。spawn 时给每个任务设 timeout，超时标记失败、可单独重派。
- **权限给太多**：subagent 拿到全量工具后自作主张改配置。按任务卡最小授权，只开必须的 MCP 工具。
- **并发开满**：一上来 10 个并发直接撞速率限制，全部重试反而更慢。从 3~5 起步，观察限流再调。
- **无证据结论**：subagent 说"检查通过"但拿不出依据。任务卡里强制要求附带证据（文件路径、命令输出摘要）。

## 可复用建议

1. 任务卡模板沉淀成项目内固定文件，每次 spawn 直接填充；
2. subagent 保持无状态，一切中间产物落盘，主 agent 通过文件系统掌握全局；
3. 记录每次 subagent 的会话 ID 和耗时，方便复盘和重放；
4. 并发数、超时、重试次数写进配置，不要硬编码在 prompt 里；
5. 涉及顺序依赖或共享写状态的任务，不要强行并行。

## 总结

subagent 并行编排的本质不是"多用几个模型"，而是**上下文管理**：把执行细节从主会话隔离出去，主 agent 只保留拆解与判断。拆得干净、卡写得严、超时兜得住，这套 fan-out / fan-in 就能稳定复用。建议从一个真实的批处理任务开始试，跑通一次完整闭环后再扩大并发。
