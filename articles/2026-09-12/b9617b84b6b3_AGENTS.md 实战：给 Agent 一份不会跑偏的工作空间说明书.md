## 背景

用 OpenClaw 跑自动化任务久了，一个感受越来越明显：Agent 的表现上限往往不取决于模型，而取决于你有没有把工作空间的"隐性约定"交代清楚。人进一个新仓库会翻 README、问同事；Agent 进来只有代码本身，其他全靠猜。

AGENTS.md 就是解决这个问题的社区约定：在仓库根目录放一个纯 Markdown 文件，Agent 进入工作空间时优先读取，当作行为准则。可以理解为"写给 AI 的 CONTRIBUTING.md"。

## 没有它会发生什么

以下场景我们都真实撞过：

- **启动命令猜错**：仓库实际用 pnpm，Agent 憋出一条 `npm install`，lockfile 被改得面目全非；
- **动了不该动的目录**：把 `generated/` 下的代码当业务逻辑"修复"了一遍；
- **每次会话重复口述**：同一个项目，团队每个人都在 prompt 里手抄注意事项，还不一致。

这些不是模型问题，是上下文缺失。补一份 AGENTS.md，成本几十分钟，收益覆盖之后所有会话。

## 我们的写法

模板分六段，按 Agent 的决策顺序排：

1. **一句话定位**：这个工作空间是什么，技术栈与版本；
2. **环境与命令**：包管理器、启动/构建/测试的确切命令，直接给可复制的命令行，不写描述性语言；
3. **目录地图**：核心目录职责，明确标注"生成物，勿改"区域；
4. **工具环境**：任务依赖的 MCP 服务或插件，写明名称、用途和调用时机，避免 Agent 现场试探；
5. **硬性约束**：禁止事项用命令式写，如"不要提交 .env""不要升级 lockfile 中已有依赖的大版本"；
6. **验证闭环**：改动后必须跑哪组测试、如何确认成功。

关键技巧是**分层**：根目录放全局约定，子目录（如 `packages/core/`）放局部约定，Agent 会就近读取，避免一份巨型文件塞满低相关内容。

## 踩过的坑

- **写成散文**。早期写了大段项目历史，token 花了，指令密度极低。后来砍到 60 行内，每行都是可执行信息。
- **与 README 漂移**。README 面向人讲背景，AGENTS.md 面向 Agent 讲操作，职责分开后两边反而不打架。
- **模糊表述无效**。"尽量注意代码风格"约等于没写；"所有 Python 文件用 ruff format 处理"才有效。
- **塞敏感信息**。全文会进模型上下文，密钥、内网地址一律不写。
- **当成万能药**。文档挡不住所有事故，关键约束还要靠 hook 或 CI 兜底，AGENTS.md 只是第一道防线。

## 可复用的建议

- **让 Agent 参与维护**：发现 Agent 犯了某类错，就把纠正规则补进 AGENTS.md，下次会话直接生效——这实质是在沉淀团队错误集。
- **纳入版本控制**：AGENTS.md 的改动走和代码一样的 review 流程，防止有人随手改坏全局行为。
- **定期核对命令**：依赖变更时顺手检查对应段落；拿不准就写"以下命令失败时先停下询问"，别让 Agent 自作主张。

## 总结

AGENTS.md 的本质是把团队隐性知识显性化、命令化，让 Agent 第一次接触工作空间就拿到正确决策依据。写起来极便宜，却直接决定自动化任务的稳定性与可复现性。建议每个 OpenClaw 工作空间都从最小模板起步——宁可先写五条硬约束，也不要留白。
