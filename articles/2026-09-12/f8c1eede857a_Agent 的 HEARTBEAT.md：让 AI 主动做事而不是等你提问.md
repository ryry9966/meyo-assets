## 背景

OpenClaw 里的 agent 默认是纯被动模型：你不发消息，它一整天不会有任何动作。这个模型在"问答"场景没问题，但一旦你想让它当真正的个人助理——早上整理一份简报、盯一下某个目录有没有新文件、定期检查订阅源——被动模型就不够了。

OpenClaw 为此内置了一个很轻的机制：heartbeat（心跳）。Gateway 按固定间隔唤醒 agent，让它读工作区根目录下的 `HEARTBEAT.md`，文件里写了什么任务，它就按条件执行；没什么可做的，就静默返回。主动和空转之间，只隔一个 markdown 文件。

## 问题

用外部 cron + API 也能拼出定时任务，但有两个麻烦：一是 agent 的会话记忆、工具权限、消息通道都收在 gateway 里，外部脚本每次都要重新拼上下文；二是任务逻辑散落在脚本里，改一次需求动一次代码。理想状态是：主动性本身也是配置的一部分，写个 markdown 就能生效。

## 做法

1. **建文件**。在 workspace（默认 `~/.openclaw/workspace/`）下创建 `HEARTBEAT.md`。文件存在且非空，心跳才会干活；删掉或清空相当于关闭。
2. **写成可判定的清单**。每条任务给"触发条件 + 动作 + 静默出口"，不要写散文。示例：

```markdown
# Heartbeat Tasks

## 规则
- 没有条目命中时，只回复 HEARTBEAT_OK，不要输出其他内容
- 单次执行只挑最紧急的一条，不要串联多个任务

## 任务
- [ ] 工作日 08:00-10:00 的第一次心跳：汇总日历和未读消息，发一段不超过 200 字的早报
- [ ] ~/inbox/ 出现新文件时：列文件名并附一句话摘要
- [ ] 距离我上次提到"周报"超过 5 天：提醒一句
```

3. **调频率和时段**。默认间隔约 30 分钟，配置里有 heartbeat 相关字段（间隔、activeHours 等，具体键名以你版本文档为准）。把活跃时段设成醒着的时间，能省一半以上的无效调用。
4. **压成本**。心跳每次都是真实的模型调用。除了"没任务就返回 HEARTBEAT_OK"这条约定，可以考虑给心跳单独指向更便宜的模型，主对话模型留给真正需要推理的场景。
5. **看日志验证**。改完配置重启 gateway，在日志里确认心跳按预期触发、静默时确实没有产出。

## 踩坑点

- **忘设活跃时段**：早报在凌晨三点发出来了。时段限制应该是第一个配置的项。
- **任务写太重**：心跳里塞"爬数据 + 总结 + 发三个群"，一次跑一两分钟还贵。心跳适合做判断和轻动作，重活让它调脚本或子任务。
- **写成自由文本**：agent 每次理解不一致，行为飘。条件句、可判定，是心跳任务稳定的底线。
- **污染主会话**：心跳跑在主会话里，每次输出都会进上下文。让它克制输出、静默优先，否则后续对话会变贵。
- **放交互型任务**：心跳里发起"要不要我帮你做 X"这类问题，容易一直挂着没有回应。心跳适合"做完发结果"，需要来回确认的留给正常对话。

## 可复用建议

- 把"条件 + 动作 + 静默出口"做成 HEARTBEAT.md 的固定模板，新任务只往里加条目。
- 从低频起步（如 60 分钟），观察一周日志和账单，再决定加密或降频。
- 心跳只负责"发现该做的事"，执行尽量下沉到 MCP 工具或脚本，保持心跳本身便宜。
- 定期清理：过期的任务条目留着只会白烧 token。

## 总结

HEARTBEAT.md 本质上是一份极简的"定时意图清单"：不引入新框架、不写代码，把 agent 的主动性变成一个可以被 review、被 git 管理的文本文件。真正的工程量不在机制本身，而在成本控制和输出纪律——时段、频率、静默约定配好了，心跳才是一个安静的助理，而不是一个定时烧钱的噪声源。
