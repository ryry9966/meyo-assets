## 背景

大多数 Agent 的工作模式是"一问一答"：你不发消息，它就闲着。但运维和个人助理场景里，最有价值的动作往往发生在"没人问的时候"——磁盘快满了要提醒、证书要到期、监控指标异常需要有人看一眼。

OpenClaw 用一个很轻的机制解决这个问题：心跳（heartbeat）。Gateway 按固定间隔（默认约 30 分钟，可配置）触发一次 agent 轮次，agent 会读取工作区里的 HEARTBEAT.md。文件为空或缺失时直接短路返回 HEARTBEAT_OK，几乎零成本；文件里有任务清单，就逐项执行，需要时主动把消息推到你的聊天渠道。

## 问题

光有机制不够。我最初把 HEARTBEAT.md 当待办清单写，结果体验很差：agent 每 30 分钟报一次"一切正常"，主动消息比订阅号推送还烦。核心问题是：心跳清单不是待办清单，它需要明确的触发条件和静默规则，否则 Agent 会从"助手"退化成"噪音源"。

## 做法

1. **定位文件**：`~/.openclaw/workspace/HEARTBEAT.md`，这是心跳轮次每次都会读的入口。
2. **按"条件式检查"写清单**，例如：

```markdown
# 每次心跳检查

- 检查服务器磁盘占用，超过 85% 才报告，附 df -h 输出
- 每天 09:00（Asia/Shanghai）汇总一次待办，其余时间保持沉默
- git pull 笔记仓库，有新提交才通知

# 报告规则

- 没有事就不说话，不要输出"无事发生"
- 单次心跳最多发一条消息
```

3. **调频率**：在 `openclaw.json` 里改 `agents.defaults.heartbeat.every`（或环境变量 `HEARTBEAT_INTERVAL_MS`）。提醒类任务 30 分钟足够，监控类可以更密。
4. **验证**：观察 gateway 日志确认心跳会话在跑。心跳走独立的 isolated session，不会污染你的主对话上下文，可以放心调试。

## 踩坑点

- **心跳刷屏**：早期我写了"每天报告天气"，结果每半小时一条。教训：每条检查都必须自带"什么条件下才说话"。
- **Token 成本被低估**：空文件会短路，但只要有内容，每次心跳就是一次模型调用。清单写得啰嗦，一个月下来成本可观，控制在几行内。
- **任务不可判定**：写"关注一下博客评论"，agent 每次都要猜。改成"有未回复评论才报告，附链接"，才能稳定收敛。
- **长任务别塞进来**：心跳轮次应当短平快。要跑爬虫、备份，让心跳只负责"触发 + 报告状态"，执行交给 cron 或插件。
- **状态没落盘**：agent 不记得上次心跳做了什么，容易重复报告。让它在工作区维护一个 state 文件记录上次检查时间。

## 可复用建议

- 把 HEARTBEAT.md 当 SLA 文档写：每条 = 触发条件 + 判定方式 + 输出格式 + 静默规则。
- 检查逻辑下沉到脚本：md 里只写"运行 check_disk.sh，exit 1 才报告"，agent 只负责判断和表达。
- 设配额：在文件里明示"每日主动消息不超过 N 条"，给刷屏上保险。
- 用 MCP 工具或插件扩展"查"的能力——心跳的价值上限取决于检查的覆盖面。

## 总结

HEARTBEAT.md 的本质是把 Agent 从被动应答器变成低频巡检器。它不炫技，收益完全取决于清单质量：条件写得越可判定，主动打扰越少，价值越高。建议从一两条"只在新事件发生时才说话"的检查起步，跑一周看日志，再逐步扩充。
