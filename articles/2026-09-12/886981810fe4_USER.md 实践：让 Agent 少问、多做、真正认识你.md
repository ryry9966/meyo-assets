## 背景

用 OpenClaw 这类常驻 Agent 时，一个反复出现的摩擦是：模型不认识你。每次会话它都不知道你主力语言是 Go 还是 Python、部署偏好 systemd 还是容器、回答要详尽还是点到为止。于是每段协作都从"我先说明一下我的环境"开始——说多了烦，说少了答非所问。

OpenClaw 工作区里预留的 USER.md 正是为此设计：一份随上下文注入的用户自述文件。它的杠杆率极高，写一次，所有后续会话受益。

## 问题

多数人对 USER.md 的用法停在两个极端：要么空着不用，要么写成个人简历。前者浪费了最便宜的个性化手段；后者全是"热爱技术、追求卓越"式的形容词，对模型没有任何可执行价值。模型需要的是**事实和约束**，不是自我介绍。

## 做法

我现在的 USER.md 约 60 行，分四段：

1. **身份与环境**：操作系统、主力语言及版本、常用框架、部署方式。只写模型会据此改变答案的事实。
2. **协作偏好**：默认中文回复、代码优先于解释、不确定时直说不要编、给方案时附权衡而非只给结论。
3. **禁区**：不改哪些配置、不自动执行哪类命令、哪些目录不要碰。
4. **动态上下文**：当前在做的一两个项目，一行一个，过期就删。

初稿完成后让 Agent 自己读一遍，问它"哪些信息你会用到、哪些没用"，据此删减。之后每月让 Agent 基于近期对话提炼"建议更新的偏好"，人工审核后合并，人把关，机器做归纳。

## 踩坑点

- **形容词堆砌无效**。"严谨、高效"不改变任何输出；"回复控制在 300 字内、先给命令再解释"才有效。
- **塞敏感信息**。密钥、住址、真实手机号不要写。工作区文件可能被工具读取或进入日志，按"随时会被上传"的假设来写。
- **与 MEMORY.md 抢职责**。稳定事实进 USER.md，会话中沉淀的动态记忆进 MEMORY.md，两边重复很快会互相矛盾。
- **写完就忘**。过期信息比没有更糟，我删掉一条三个月前弃用的框架描述后，相关建议立刻恢复正常。
- **太长**。几百行档案会稀释有效上下文，超过一屏就该做减法。

## 可复用建议

- 把 USER.md 放进私有 git 仓库：改动可回溯，多台设备也好同步。
- 用"正例 + 反例"代替纯否定式，例如："要给出可复现的命令步骤，而不是'建议查阅官方文档'"。
- 每条偏好加粗关键词，模型锚定更稳。
- 团队场景可派生一份团队基线文件，个人差异才留在 USER.md。

## 总结

USER.md 本质上是一份面向模型的接口文档：你是调用方，Agent 是被调用方，档案就是你的 spec。它不神秘，也不需要写得漂亮，只需要事实准确、约束明确、定期修剪。花半小时写第一版，之后每月让 Agent 提议修订——你会发现"它懂我"不是玄学，只是一份维护得当的 Markdown。
