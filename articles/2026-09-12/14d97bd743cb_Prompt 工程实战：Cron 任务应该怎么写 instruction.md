# Prompt 工程实战：Cron 任务应该怎么写 instruction

## 背景

在 OpenClaw 里，定时任务和交互对话是两种完全不同的运行形态。交互时 agent 能追问、能带上下文；cron 触发则是无人值守：到点拉起会话，塞入预先写好的 instruction，跑完即止，没人回答“你指的是哪个库”。所以 cron instruction 的写作标准应该向“程序规格说明”靠拢，而不是聊天消息。以下是我维护多个定时任务（每日汇总、监控巡检、同步提醒）踩坑后的总结。

## 问题：对话式写法会翻车

典型的失败 instruction：

> 每天早上帮我看看 CI 情况，整理一下发出来。

交互场景能跑，定时场景有四个问题：

1. **不自包含**：没说用什么工具、查哪些来源，agent 每次自由发挥，结果漂移；
2. **没有输出契约**：发到哪、什么格式、多长全靠猜，下游无法稳定消费；
3. **没有异常路径**：数据源挂了或查询为空时，agent 倾向于“编一个像样的结果”，这是最危险的；
4. **边界不清**：“整理一下”可能触发它发消息、改文件，权限超出任务实际所需。

## 做法：五段式模板

我现在的模板固定五段：

```text
[定时任务] 每天 08:00（Asia/Shanghai）自动触发。
目标：汇总过去 24h 的 CI 失败并通报。
步骤：
1. 调用 <MCP 工具> 查询失败记录，统计截止昨日 24:00；
2. 按仓库分组，统计次数与首次出现时间。
输出：
- 发送到 #ci-daily 频道；
- 固定三段：总数 / Top 失败 / 与前日对比；
- 记录为空时只发一行："过去 24h 无 CI 失败"。
约束：
- 只读查询 + 频道消息，不改文件、不发私信；
- 工具报错重试一次，仍失败则发送"任务失败：<原因>"，不要推测数据；
- 不要向用户提问，缺信息在输出中标注即可。
```

要点：开头交代触发语境和时区，给“昨天”这类相对时间一个锚点；目标一句话，让它跑偏时能自查；步骤宁啰嗦勿省略——任务要跑一年，多写五十字很划算；输出契约里的**空结果路径**尤其重要，不写它大概率硬编内容；约束段定义最小权限、失败动作、禁止追问。

## 踩坑点

- **时区与数据延迟**：cron 触发时间和 agent 理解的“今天”可能差一天，务必写明时区和统计截止点；
- **“无事发生”场景**：监控类任务不定义空结果输出，空闲几天后你会收到一份格式正常、内容是编的报告；
- **格式漂移**：不锁格式，三周后输出变散文。固定字段还有个好处：后续加统计脚本可以直接解析；
- **静默失败**：必须写失败时的动作。我有任务连续失败四天才被发现，就因为漏了这条；
- **重复触发**：任务重跑会重复发消息，可加一句“发送前检查频道是否已有今日结果”。

## 可复用建议

- 把 instruction 当“给值班同事的交接文档”写：他独立执行、不看历史聊天、不许问你问题；
- 按类型沉淀模板：监控、汇总、同步提醒各一份，新任务复制改参数即可；
- 上线前手动“立即执行”一次，对照输出契约逐项检查；改 instruction 后同样重跑验证；
- 别把大段背景塞进 instruction，定时任务按次执行很费 token，需要的信息让 agent 现场用工具查。

## 总结

Cron instruction 的本质是无人值守环境下的行为规格说明，核心四件事：**自包含、输出契约、异常路径、最小权限**。写完自查一句：“如果我是凌晨三点独自执行它的 agent，这段话够不够我完成任务且不出格？”够了，就算合格。
