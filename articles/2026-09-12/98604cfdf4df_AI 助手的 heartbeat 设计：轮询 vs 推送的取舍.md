## 背景

OpenClaw 的 agent 默认是被动的：有消息进来才跑。要让助手具备"主动性"——定时巡检、提醒、跟进挂起事项——就得先解决驱动源问题。OpenClaw 内置的 heartbeat 是其中一条路线：按配置的间隔 tick 一次，agent 检查任务文件（如 `HEARTBEAT.md`），决定"无事可做"还是触发动作。另一条路线是推送：日历、Git、监控、邮件等事件源通过 webhook 或 MCP 主动把事件递给 agent。两条路线代价结构完全不同，选错方向，要么 token 账单失控，要么时效性垮掉。

## 问题

- **轮询的真实成本不是 CPU，而是 LLM 调用**。每次 tick 都可能唤醒模型，哪怕结论只是"没事发生"。5 分钟一次意味着一天 288 次心跳，成本与噪音都不可忽略。
- **推送的代价在基础设施**。agent 可能离线或休眠，事件会丢；webhook 暴露公网需要鉴权；事件风暴需要合并与限流。
- **最隐蔽的是重复**。同一件事，heartbeat 巡检发现一次，推送又来一次，用户收到两条一样的提醒。

## 做法

我们的实践是分层混合，原则一句话：**能推就推，轮询兜底**。

1. **盘点事件源并分类**：有 webhook 能力的（代码托管、告警、日历）走推送；没有推送能力又需周期检查的（本地文件、低优先级订阅）归入 heartbeat sweep。
2. **在唤醒 LLM 之前加一道"廉价门"**：用确定性脚本先判断条件是否成立（mtime、状态字段、阈值比较），不成立就返回 no-op，不进模型。这一步通常能砍掉 90% 以上的无效心跳成本。
3. **推送侧做幂等**：每条事件带"来源 + 时间戳"组成的 key 写入去重表，heartbeat sweep 处理同一事件前先查表。
4. **心跳配静默模式**：tick 只跑本地检查，仅当存在候选任务时才构造 prompt 唤醒 agent。
5. **时间敏感事件只走推送**，并在 agent 离线时落盘队列，上线后由下一次心跳完成对账。

## 踩坑点

- 心跳间隔过短又没有廉价门，token 花费成倍增长，产出几乎为零。
- webhook 无签名校验直接暴露，等于给公网开了一个能操纵 agent 的接口。
- 一次 CI 故障产生几十条事件，未做合并导致 agent 连环触发；加 1–2 分钟的 coalesce 窗口即可缓解。
- 设备休眠导致 tick 堆积：唤醒后只做一次最近状态对账，不要补跑全部错过的周期。

## 可复用建议

- **按时效分层**：分钟级时效走推送，小时级容忍度走轮询。
- 主动性动作一律设计成**幂等的 sweep**，而非一次性 trigger。
- 记录每次心跳的决策日志（触发/跳过 + 原因），成本审计和间隔调优都靠它。
- 起步配置建议：heartbeat 15–30 分钟 + 廉价门，事件源具备推送能力的逐步迁移。

## 总结

轮询和推送不是二选一：推送解决"准和快"，heartbeat 解决"活性与兜底"。真正的工程量在两者之间——廉价的前置判断、幂等去重、离线对账。把这三件事做扎实，助手的主观能动性才不会变成成本黑洞。
