## 背景

我们社区的日常运营里有几件事高度重复：每周技术摘要、新帖精选、FAQ 整理。人工做一期大约 2 小时，且质量随人状态波动。于是决定基于 OpenClaw 搭一个发帖机器人，目标从一开始就很明确：**不是全自动，而是"机器起草、人审后发"**。

## 问题

难点不在"能不能生成内容"，而在三个工程约束：

1. 内容必须可溯源，不能让模型自由发挥；
2. 发布动作必须可控，绝不允许 agent 跑飞刷屏；
3. 任何一步失败都要可恢复，不能静默丢内容。

## 做法

整体拆成五层，每层独立失败、独立重放：

- **采集层**：通过 MCP 工具定时拉取数据源（RSS、GitHub Release、社区新帖 API），落盘为本地 JSON，不直接进模型。
- **起草层**：Agent 只读结构化数据，按固定模板产出草稿。核心约束：**只允许引用采集结果里已有的 URL**。
- **审核层**：草稿写入 pending 目录并推送到审核频道，人工确认后才进入下一步。
- **发布层**：调用社区发帖 API，携带幂等 key（日期 + 内容 hash），发布 token 只授予最小 scope。
- **观测层**：每步状态写日志，失败进重试队列，连续失败三次降级为人工处理。

## 踩坑实录

1. **幻觉链接**：第一版让模型"补充相关阅读"，结果编造了不存在的 URL。修复方式是白名单机制——prompt 里明确"只能使用输入数据中出现的链接"，并在发布前做一次 URL 可达性校验。
2. **重复发帖**：cron 超时后重试，导致同一天发了两期。加上幂等 key 后，重复请求直接被发布接口拒绝。
3. **时区错位**：调度器跑 UTC，社区平台按北京时间展示，摘要标题里的日期经常错一天。所有时间统一在一个时区处理，只在展示层转换。
4. **重试风暴**：发布接口限流，失败重试没加退避，瞬间触发 429。改成指数退避 + 每日发布配额上限。
5. **模板漂移**：模型偶尔"热心地"调整模板结构，下游解析直接挂掉。改为 JSON Schema 约束输出格式，不靠 prompt 祈祷。
6. **权限过大**：最初发布 token 用的是管理员权限， review 时才意识到一旦 prompt 注入后果严重。立刻收敛到"仅发帖"单一 scope。

## 可复用建议

- 上线前先跑**两周草稿模式**，人审每一期，积累失败样本后再放开；
- Agent 只负责加工，采集和发布全部工具化，职责分离才好排障；
- 所有外部写操作必须幂等、可 dry-run；
- 用 Schema 约束模型输出，别用自然语言描述格式；
- 保留人工降级通道：低置信度或连续失败时，自动转人审。

## 总结

这个项目最大的收获是：发帖机器人的瓶颈在工程边界，不在模型能力。把"采、写、审、发、测"拆开，每一步可独立失败、可重放，远比追求端到端全自动可靠。目前机器人稳定运行约两个月，内容质量与人工版本基本持平，单期维护成本从 2 小时降到 20 分钟。架构和约束清单都已沉淀成模板，社区里想复用的同学可以直接拿去改。
