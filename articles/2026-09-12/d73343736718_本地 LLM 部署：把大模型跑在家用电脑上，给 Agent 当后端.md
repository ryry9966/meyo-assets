## 背景

用 OpenClaw 搭 Agent 自动化之后，很快会撞上两个现实问题：一是云端模型 API 的成本随任务量线性上涨；二是很多自动化场景涉及本地文件、内网服务，数据不想出网。务实的折中方案是：本地跑一个够用的模型，让它承担"结构化提取、工具调用"这类高频简单任务，复杂推理再回落云端。

## 问题

家用硬件跑大模型，核心矛盾是显存。我的环境是单卡 12GB 显存 + 32GB 内存，目标很明确：跑一个 7B–14B 级别的模型，通过 OpenAI 兼容接口接入 OpenClaw，稳定完成 MCP 工具调用和 JSON 输出，推理速度不低于 15 tokens/s。

## 做法

1. **选运行时**。对比了 Ollama、llama.cpp、vLLM。个人机器首选 Ollama：安装简单、自带 OpenAI 兼容端点、模型管理省心；追求极限吞吐再考虑 vLLM，但它对显存要求更高。
2. **选模型和量化**。实测 Qwen2.5-14B-Instruct 的 Q4_K_M 版本在 12GB 卡上刚好能跑，工具调用成功率明显优于同尺寸的 Llama 3.1。再备一个 7B 模型当"兜底快枪手"。
3. **改上下文窗口**。Ollama 默认 `num_ctx` 只有 2048，Agent 场景下系统提示词加工具描述很快截断，必须显式设到 8192 或更高。
4. **接入 OpenClaw**。`base_url` 指向 `http://localhost:11434/v1`，先跑一个最小的 MCP 工具调用测试（比如读本地文件），确认 function calling 链路通了，再逐步挂更多工具。
5. **压测**。用脚本并发发 10 个带工具调用的请求，观察 tokens/s 和排队情况，确定自己场景的并发上限。

## 踩坑点

- **量化档位别贪小**。Q4 以下的模型（Q3、Q2）做 JSON 输出容易漏字段、格式错乱，工具调用成功率掉得厉害。7B 以下模型建议 Q5 起步。
- **KV cache 吃显存超预期**。上下文开到 32K 后显存占用接近翻倍，直接 OOM。上下文按 Agent 实际需要给，别一上来拉满。
- **工具描述要精简**。本地模型上下文金贵，MCP 工具的 description 写太长会挤压推理空间、拖慢首 token，控制在两三句话。
- **并发默认是串行的**。Ollama 单请求排队，Agent 并发开多个子任务会互相阻塞，注意配置并行数或调整任务编排。
- **别指望本地模型做复杂规划**。多步推理、长链规划这类任务 14B 也会频繁跑偏，应路由给云端大模型。

## 可复用建议

- **明确分工**：本地模型干结构化提取、格式转换、简单工具调用；复杂任务路由云端。成本和隐私都可控。
- **配置进版本管理**：模型名、量化版本、`num_ctx`、温度等参数记录下来，复现问题有据可查。
- **持续监控**：盯 tokens/s 和显存占用，性能突然下降往往是别的进程抢了显存。
- **用 JSON Schema 约束输出**，比纯 prompt 约束稳定得多。

## 总结

本地部署的价值不在"替代云端"，而在给 Agent 体系补一层低成本、可离线、数据不出网的执行层。12GB 显存的家用机跑 14B Q4 模型，足以覆盖大部分工具调用类任务。先跑通最小链路，再逐步扩大工具集，是这类实践最稳的推进方式。
