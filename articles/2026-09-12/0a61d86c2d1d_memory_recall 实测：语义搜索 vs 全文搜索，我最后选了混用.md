## 背景

OpenClaw 的 memory_recall 是 agent 回答"我之前说过什么"的关键路径。记忆文件积累到几百条之后，召回策略直接决定助手是"记得住"还是"一本正经地编"。社区里常见两派：一派认为 embedding 语义搜索是标配，另一派坚持 grep/全文搜索够用且快。我把两条路径在自己跑了两个月的实例上做了对照测试，结论是：没有谁全面胜出。

## 问题

两条路径各有明显的失效场景：

- **语义搜索**：问"之前那个数据库迁移的结论"能召回；但查 `pg_port_5432` 这类精确标识符时经常排不进 top-k——向量空间里标识符和普通词的区分度很低。
- **全文搜索**：精确词、ID、路径一查一个准；但换个说法就抓瞎，记录里写的是"迁移 PostgreSQL"，搜"数据库搬家"什么都出不来。
- 隐性成本：语义检索要调 embedding 接口，冷启动和内网环境都不友好。

## 做法

1. **建测试集**：从 memory 目录抽 30 条真实记忆，按三类写 query——精确标识符（配置项、路径、工单号）、同义改写（"搬家"vs"迁移"）、模糊时间（"上周说的那个"）。
2. **分别测两条路径**：语义走 memory_search（换成中文效果较好的 embedding 模型后重建索引）；全文通过 exec 走 ripgrep 直接搜 markdown 记忆文件。
3. **记录三个指标**：top-5 命中率、平均召回耗时、误召回（返回但无关）比例。

结果简述：精确标识符类，全文 90%+，语义只有 50% 左右；同义改写类，语义 80%+，全文不到 30%；模糊时间类两者都不行，靠记忆文件按日期命名兜底。延迟上全文明显更低。

## 踩坑点

1. **embedding 模型选错**：早期用英文为主的模型，中文 query 召回质量很差，换中文友好模型后明显改善。换模型必须重建索引，否则新旧向量不在一个空间。
2. **分块粒度太粗**：整天的日记文件整段向量化，召回一大段但只需要一句，agent 很容易被无关内容带偏。改成按条目分块后噪声明显下降。
3. **别迷信 top-k**：top-5 里前两条无关时，agent 会硬套。宁可选 top-3 并配更高的相似度阈值。
4. **记忆写入不规范，什么检索都救不回来**：没写日期、没写关键词的记忆，召回参数怎么调都低。检索侧的上限由写入质量决定。

## 可复用建议

- 记忆里精确标识符多 → 全文优先；自然语言回忆多 → 语义优先；两者都有 → **混合策略**：先全文精确匹配，未命中再走语义，语义结果用关键词二次过滤。
- 记忆文件保持结构化：每条带日期和主题关键词，等于给全文搜索免费铺路。
- 检索策略调整后，先在测试集上跑一遍再上线，不要凭感觉改。

## 总结

语义搜索解决"换个说法还记得"，全文搜索解决"精确词必命中"，两者失效场景几乎互补。memory_recall 的工程价值不在于站队，而在于看清自己记忆库的内容构成，选择合适的组合方式。花半天建一套 30 条的测试集，比反复调参数划算得多。
