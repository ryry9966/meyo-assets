## 背景

Agent 自动化跑得越久，外部依赖就越多：LLM 网关、搜索接口、各类 MCP server、第三方业务 API。对长任务来说，“某个依赖会挂”不是概率问题，而是时间问题。真正的分水岭在于：故障发生时，你的 Agent 是体面降级，还是重试到天亮、烧光 token。

## 问题：错误是怎么被放大的

实际跑下来，最常见的几种放大路径：

- 一次 429 触发重试，退避没设上限，任务永久卡死；
- 工具抛出原始异常，LLM 看到一坨 stack trace，开始自由发挥，编一个“看起来合理”的答案；
- 重试打在非幂等的写接口上，同一条消息发出去两遍；
- 几十个定时 Agent 同时恢复，把刚缓过来的上游又打挂一次。

共同点：错误没有被结构化地传递和决策，而是被吞掉，或被放大。

## 做法：把失败变成可处理的数据

**1. 先分类，再重试。** 只有两类：可重试（429、503、超时、网络抖动）和致命（400、401、404、参数非法）。致命错误直接终止该步骤、把原因写回任务状态，绝不进重试循环——对 401 重试十次也不会让它变对。

**2. 退避 + 抖动 + 超时。** 指数退避配随机抖动，基数 1s、单次上限 30s、总预算 3 次；连接超时和读取超时分开设。预算用完就走下一步，不要恋战。

**3. 熔断与降级。** 连续 N 次失败后熔断，冷却期内直接走 fallback，不再探测。降级返回的数据必须带 `stale` 标记，让 Agent 分得清这是缓存还是实时值。

**4. 让 Agent 看懂错误。** 所有工具调用统一错误信封，例如 `{ok:false, error_type, retryable, hint}`，`hint` 直接写给 LLM 看：“上游限流，已自动重试 3 次，建议 10 分钟后重跑或跳过此步”。LLM 拿到明确选项才会重新规划，而不是对着 stack trace 编数据。

**5. 幂等与断点。** 写操作带幂等键；长任务每完成一步落盘状态，恢复时从断点续跑，而不是从头再来。

## 踩坑点

- **无抖动的退避**：定时任务天然扎堆，恢复瞬间形成重试风暴；
- **catch-all 后无脑重试**：把鉴权失败也重试，白烧配额；
- **超时拍脑袋**：慢接口设 3s 全是假失败，快接口设 60s 一步卡住整条流水线；
- **熔断恢复太快**：半开状态一放流量，上游还没好，反复震荡；
- **降级返回和正常返回长得一样**：Agent 拿昨天的缓存汇率算今天的账，还觉得自己没错。

## 可复用建议

1. 每个外部依赖做一个统一封装（adapter / 工具包装层）：错误信封 + 重试预算 + 熔断，业务代码不接触原始异常；
2. 每个依赖配 kill switch，出事时人工一键摘除，Agent 自动走降级路径；
3. 开发环境 mock 429 / 500 / 慢响应，把失败路径当正常用例测；
4. 监控看错误率而不是单次报错，用 trace id 把 Agent 决策日志和工具调用日志串起来。

## 总结

错误恢复的目标不是“不失败”，而是失败得清晰、有界、可续跑。把上游故障当成一等公民的输入来设计，你的 Agent 才能在凌晨三点没人盯着的时候，依然表现得像一个靠谱的工程系统。
