## 背景

OpenClaw 跑起来之后，模型调用是成本和体验的核心。我现在的常驻 agent 每天处理几百次工具调用，早期图省事全走 GPT，月底账单不好看；后来一刀切全上本地模型，复杂任务又频繁翻车。最后落到一套混合路由方案，稳定跑了两个多月，把思路整理出来。

## 问题：两个极端都不对

全云端的问题不只是钱：内网日志、私有文档这类内容不适合出网，高峰期限流还会打断长任务。

全本地的问题在能力边界：小参数模型在多步工具编排、长上下文总结时错误率明显上升，而且失败的代价往往不是报错，而是"看起来执行了，结果是错的"——这种静默失败最难排查。

所以核心问题不是选哪个模型，而是定义分工边界。

## 做法：三层路由

我的配置把任务分三层：

1. **云端主力层**：复杂推理、多步工具编排、超过 8k token 的任务，走 GPT，设为默认模型。
2. **本地经济层**：简单改写、格式转换、分类打标、敏感数据预处理，走本地 Ollama 起的模型（OpenAI 兼容端点接入）。
3. **降级链**：云端限流或断网时 fallback 到本地，保证 agent 不直接停摆。

配置步骤简述：

- 在 OpenClaw 的 models 配置里同时登记两个 provider：云端 API + `http://127.0.0.1:11434/v1`。
- 主模型设云端，fallback 设本地；本地模型务必显式声明真实上下文窗口，别依赖虚高的默认值。
- 结构化输出要求高的 MCP 工具链，锁死走云端，不参与降级。
- 日志里记录每次调用的模型标识，方便事后对账。

## 踩坑点

- **本地上下文虚标**：某 14B 模型标称 32k，实际超过 12k 就开始丢工具定义，表现为"工具没被调用"而非报错。压缩上下文或换模型才解决。
- **降级后行为漂移**：fallback 到本地后温度和 system prompt 没同步，同一 agent 输出风格突变，下游解析脚本直接挂了。两套模型的采样参数要一起管。
- **降级循环**：本地返回格式非法 → 云端重试 → 又被限流 → 再降级，日志刷屏。给降级加冷却时间才停住。
- **中文成本被低估**：同一段中文，部分本地模型的 token 切分效率差不少，估配额别按英文经验套。

## 可复用建议

- 按"错误代价"而不是"任务难度"分层：错了要返工的走云端，错了能被校验拦住的走本地。
- 本地模型只接你能写校验器的任务（JSON schema、正则、断言），校验不过自动重试或回传云端。
- 每周看一次按模型维度统计的调用量和成本分布，路由规则不是一次配完的。
- 换模型先灰度：复制一套 agent 跑影子流量，对比一周再切主线。

## 总结

多模型路由的本质是风险管理：云端买能力，本地买成本和隐私，降级链买可用性。OpenClaw 的配置足够灵活，但边界要自己定义。我的经验是先让所有调用可观测，再逐步把低风险任务迁到本地——顺序反过来很容易翻车。欢迎在评论区交流你们社区的分层策略。
