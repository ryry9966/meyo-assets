## 背景

OpenClaw 的 cron 任务本质上是"无人值守的 prompt"：到点之后，Agent 拿着你写的那段 instruction 独立执行——没有对话上下文，没有人在旁边补充说明。日常对话里你可以随口说"照昨天那样来"，cron 里这么写必挂。最近帮几位社群朋友排查定时任务，发现大部分问题不在调度配置，而在 instruction 本身，于是整理成这篇。

## 问题：三种典型翻车

1. **上下文缺失**。instruction 写"汇总最近的告警"，但 Agent 执行时不知道"最近"是多久、去哪个频道取、用什么工具。
2. **静默编造**。数据源拉不到内容，instruction 又没写失败分支，Agent 为了"完成任务"开始自己编数据——这是最危险的一类。
3. **输出失控**。不限长度、不限渠道、动辄 @所有人，一次执行刷屏几十条，最后被用户手动关掉。

共同根源：把 instruction 写成了给自己的备忘录，而不是给执行者的作业说明书。

## 做法：五要素模板

我的习惯是把每条 cron 的 instruction 按 SOP 来写，固定五个部分：

```
【触发】每天 09:00（Asia/Shanghai）
【输入】读取 #dev-alerts 频道昨天 00:00–24:00 的消息
【步骤】按服务归类 → 统计条数 → 摘出 P0/P1
【输出】发到 #daily-standup，仅一条，200 字以内，不 @所有人
【失败】取不到数据就发"数据源异常"，禁止推测和编造
```

对应的写法要点：

1. **自包含**。假设 Agent 执行瞬间失忆：频道名、工具名、MCP 服务名、时间范围全部写死，不留代词和"上次说的那个"。
2. **单一职责**。一条 cron 只干一件事。日报归日报，巡检归巡检，改一个不会牵连另一个。
3. **输出契约**。发到哪、几条、多长、什么格式，写得越死越好。Agent 的创造力应该留给内容，不该留给格式。
4. **失败策略显式化**。明确"拿不到就报异常并停止"，比让 Agent 自由发挥安全得多。
5. **先手动后定时**。写完先手动触发两三次，确认输出符合预期，再挂 schedule；周期先短后长。

## 踩坑点

- **时区**。调度表达式按 UTC 算，instruction 里又写"每天早上"，两者对不上，任务在错误的时间跑。时间和时区只在定义一次。
- **幂等**。调度重试导致同一条日报发两遍。指令里加一句"若今天已发送过则跳过"，能省很多麻烦。
- **改动不走小步**。一次改五处，坏了不知道是哪句引起的。instruction 和代码一样，一次只改一段，观察一个完整周期。
- **任务只加不减**。每条 cron 都有 token 和打扰成本。季度清一次列表，没人看的任务直接删，不要留恋。

## 可复用建议

- 心法一句话：**把 instruction 写给一个聪明、但不了解你上下文的外包同事**。
- 五要素模板（触发 / 输入 / 步骤 / 输出 / 失败）可以直接抄，覆盖 90% 的定时任务场景。
- 复杂任务拆成"采集 cron + 汇总 cron"两段，各自简单、各自可测。
- 涉及发群的输出，第一阶段先发私聊给自己，稳定跑一周后再切到群。

## 总结

cron instruction 的质量，决定了无人值守自动化到底是"省时间"还是"制造新工作"。核心就两点：执行时**无上下文**，所以必须自包含；执行时**无监督**，所以必须显式定义输出和失败行为。把 prompt 当 SOP 写、当代码维护，定时任务才真正靠得住。
