## 背景

在内容分发自动化场景中，将生成或编辑好的图文同步到微博超话是一个常见需求。无论是基于 OpenClaw 的任务编排，还是通过 Agent 触发多平台发布，超话同步的稳定性直接决定整条链路的可用率。然而，微博开放平台的图片上传接口与社区发帖接口在限流规则、参数构造和状态反馈上都比较“古典”，很容易踩坑。

本文复原一次基于 Python 的同步实践，重点分析图片上传、频率控制和任务状态归档三个关键环节，并给出可嵌入 OpenClaw 或 MCP 工具的工程化建议。

## 问题拆解

一次完整的超话同步流程可以拆解为：

1. 获取超话 ID 和发帖权限（cookie 或 token）；
2. 上传图片，获得 `pid`；
3. 构造发帖请求，关联图片 `pid` 和超话 `topic_id`；
4. 处理返回结果，记录状态；
5. 对限流、网络错误等异常进行退避重试。

主要难点集中于 **第 2 步的图片上传** 和 **整体链路的频率控制**，以及 **失败任务的归档与回溯**。

## 图片上传的实现与坑点

微博图片上传接口为 `https://picupload.weibo.com/interface/pic_upload.php`，采用 `multipart/form-data` 方式。需要携带登录态 cookie，并构造合法的 `data` 字段。

一个可工作的 Python 请求片段：

```python
import requests

def upload_image(image_bytes, cookie_str):
    url = "https://picupload.weibo.com/interface/pic_upload.php"
    data = {
        "data": "1",
        "p": "1",
        "url": "",
        "markpos": "1",
        "logo": "1",
        "nick": "0",
        "app": "miniblog",
        "s": "json",
    }
    files = {"pic1": ("image.jpg", image_bytes, "image/jpeg")}
    headers = {"Cookie": cookie_str}
    resp = requests.post(url, data=data, files=files, headers=headers, timeout=30)
    return resp.json()
```

实际运行中踩到的坑：

- **`data` 字段不能省**，部分工具会省略该字段导致返回 `-100` 或空响应。特别注意 `p` 参数：`1` 表示以图片形式展示，`0` 为附件形式，超话发帖一般需要 `p=1`。
- **图片大小限制**：单张图片超过 5MB 会直接失败，且接口不返回明确错误码，需要本地预检。
- **`pic1` 字段名固定**：即使只上传一张图也必须用 `pic1`，不可改为其他名。
- **响应结构不稳定**：成功时返回格式类似 `{"code":"1","data":{"pics":{"pic_1":{"pid":"..."}}}}`，但偶尔会出现 `code` 为字符串 `"1"`、无 `data` 的异常情况，必须做兼容处理。

## 频率限制与退避策略

微博图片上传接口虽然没有文档化的 QPS 说明，但实测单账号 **连续上传超过 3 张/10 秒** 就会触发软限流，表现为返回空响应或 `{"code":"100005"}`（服务内部错误）。发帖接口同样存在 **每超话每分钟 1 帖** 的隐性限制，超过后表现为 `{"code":"100001","msg":"发送失败"}`。

我们采用两级限流：

1. **上传队列延迟**：每张图片上传前至少间隔 5 秒，若返回异常则指数退避（2、4、8… 秒），最大等待 30 秒。
2. **发帖全局频率控制**：使用时间窗口计数器，单超话 60 秒内只允许 1 次发帖请求。可以将时间戳存入 Redis，每次发帖前检查。

退避逻辑的简化代码：

```python
import time

def upload_with_backoff(image_bytes, cookie_str, max_retries=3):
    delay = 5
    for attempt in range(max_retries):
        result = upload_image(image_bytes, cookie_str)
        if result.get("code") == "1":
            return result
        time.sleep(delay)
        delay *= 2
    raise Exception("图片上传重试耗尽")
```

额外收获：在 OpenClaw 的 action 封装中，把限流和退避做成一个统一的 `RateLimitedAction` 基类，方便不同平台复用。

## 状态归档与可观测性

纯脚本运行往往忽略任务状态的持久化，导致失败后无法追溯。这次实践强制引入了归档层：

- **任务状态表**（SQLite 或 Postgres）：记录 `task_id`、`platform`、`topic_id`、`content`、`image_pids`、`status`（pending/uploading/posting/success/failed）、`retry_count`、`last_error`、`created_at`、`updated_at`。
- **每步更新**：图片上传成功后立刻更新 `image_pids` 和状态；发帖完成后更新 `status` 与 `platform_post_id`。
- **死信队列**：超过 5 次重试仍失败的任务移入死信表，单独排查。避免无限重试堵塞队列。

这样一来，通过简单的 SQL 查询就能回答“昨天有多少同步任务失败”“当前待重试的任务量”等运营问题，也为后续对接告警打下基础。

## 可复用的工程建议

- **独立出图片上传模块**：将其封装成可独立调用的 MCP tool，输入图片二进制和 cookie，返回 `pid` 列表。这样 OpenClaw 里的其他 Agent 也可以直接调用。
- **配置化 cookie 管理**：不要在代码中硬编码 cookie。使用环境变量或专门的凭证插件定期刷新，因为微博 cookie 有效期约 24 小时，过期会导致 `-101` 错误。
- **增加预检环节**：发帖前先校验图片尺寸、数量（超话单帖最多 9 张），文本长度（微博 140 字限制，超话实际可能放宽但建议保守），减少无效请求。
- **使用本地代理或固定出口 IP**：长时间高频调用可能会触发微博风控，导致验证码或账号限制。建议生产环境使用固定 IP 并降低并发。
- **与 OpenClaw 工作流集成**：将同步逻辑封装为一个独立的 sync 插件，暴露 `sync_to_topic` action，其余流程（内容生成、审核）由其他 agent 完成，通过消息队列串联，降低耦合。

## 总结

这次微博超话同步的工程实践表明，图片上传的稳定性是整条链路的基础，而限制往往隐藏在“无文档”的接口行为中。通过引入上传退避、发帖频率控制和持久化状态归档，可以将同步成功率从初期的约 70% 提升到 98% 以上，且具备可观测性。对于 OpenClaw 用户，这些经验可以沉淀为通用的 `RateLimiter` 和 `TaskArchiver` 模块，后续接入其他平台（如小红书、B站）时直接复用，避免重复试错。
