## 背景

在 OpenClaw 的 Agent 编排、MCP 工具调用以及自动化报告生成流程里，我们经常要求大模型产出结构化内容——一份包含摘要、多段分析、建议列表的长篇输出。JSON 往往是第一反应：生态完备、解析器随手可得。但当输出长度超过数百 token，JSON 的稳定性就开始崩塌，轻则解析失败，重则整个流程中断。这条笔记记录一次从“坏 JSON”切换到自定义标签格式的真实实践，以及从中沉淀下来的工程化做法。

## 问题：为什么长 JSON 这么容易翻车

大模型本质上是自回归预测下一个 token，没有任何全局语法校验。短 JSON 靠强大的统计模式足以兜底，但一旦结构复杂、层次加深、长度延伸，模型会逐渐“忘记”还欠着一个闭合括号，或者在某处提前写出了 `\` 转义符，又或在字符串里未转义的双引号。

在实际场景中，我让 Agent 生成一份 800 字左右的分析报告，结构类似：

```json
{
  "title": "...",
  "sections": [
    {"heading": "...", "content": "..."}
  ],
  "footer": "..."
}
```

实测结果：超过 60% 的长输出至少出现一次括号不匹配、未转义换行符、或字符串内嵌套引号导致 `JSON.parse` 直接抛错。尝试过 instruct 强调“只输出合法 JSON”、增加括号计数验证、用 json-repair 库修复，但仍然有约 12%~15% 的不可恢复损坏（例如 `content` 内部意外闭合了整个 JSON 结构）。对于无人值守的自动化链路，这个失败率不可接受。

## 解决思路：用标签格式换取容错性

与其让模型迁就 JSON 的严格语法，不如换一种对自回归友好的结构化格式。XML/HTML 风格的标签天然具备“有开始、有结束”的视觉锚点，即使中间内容有点脏，解析器也能借助标签边界提取想要的部分。关键是不需要完美的语法树，只要求标签对大致完整。

于是设计了一个轻量标签 Schema：

```
<report>
<title>...</title>
<summary>...</summary>
<sections>
<section>
<heading>...</heading>
<content>...

---
