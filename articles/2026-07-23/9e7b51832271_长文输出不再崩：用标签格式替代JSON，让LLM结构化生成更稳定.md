## 背景：JSON 在长文本场景下的连环翻车

在 OpenClaw、Agent、MCP 等自动化实践中，我们经常要求大模型输出结构化数据——工作流定义、文档摘要、配置文件、多步骤 SOP 等等。直觉上选 JSON 似乎是标准答案：几乎所有语言都能解析，schema 明确，生态成熟。

但现实是，当待生成的内容中包含多段落自然语言、代码块、列表或复杂嵌套时，JSON 就频繁“炸掉”。笔者在内部几个 Agent 项目中统计过，长文摘要直出 JSON 的一次成功率不到 85%，剩下的 15% 需要重试、修复或降级。为此不得不加一层“JSON repair”逻辑，但治标不治本。

真正让我们放弃单纯依赖 JSON 的，是三类高频故障：
1. 字符串转义失控：摘要里出现双引号、反斜杠，模型偶尔遗漏转义，整段 JSON 报 `Expecting ',' delimiter`。
2. 尾部残留逗号：LLM 在数组或对象的最后一个元素后多加一个逗号，导致解析失败。
3. 非闭合括号：长输出时注意力衰减，少一个 `]` 或 `}`，直接报废整个 payload。

这些问题在短 JSON 里很少出现，一旦输出 token 超过 500，错误率陡增，重试还消耗大量算力和时间。于是我们开始寻找一种对模型更友好、容错性更高的结构化格式。

## 转向标签格式：像 XML，但更宽容

经过几次实验，我们切换到类 XML 的标签格式作为中间表示。它的核心思路很简单：用自定义标签包裹每个字段，而不是用逗号和花括号。例如原本要求输出：

```json
{
  "summary": "这是一段很长的摘要……包含换行和\"引号\"",
  "keywords": ["AI", "自动化"],
  "sentiment": "positive"
}
```

改为：

```
<analysis>
<summary>
这是一段很长的摘要……包含换行和"引号"
</summary>
<keywords>AI, 自动化</keywords>
<sentiment>positive</sentiment>
</analysis>
```

解析时，用正则或轻量 XML 解析器读取每个标签内容。哪怕模型漏掉了 `</analysis>` 闭合，我们仍然能拿到已完整闭合的 `summary`、`keywords` 等字段。JSON 那种“一个字符错误全局毁灭”的脆弱性在这里被局部化。

我们在系统提示中明确要求模型：“严格使用上述标签格式输出，不要使用 JSON”。配合 2-3 个 few-shot 示例，模型能很快适应。实际测试中，同样长文场景下一次成功率从 85% 提升到 98% 以上。

## 实施步骤

### 1. 设计标签 schema
根据业务字段定义标签名，建议扁平结构为主，避免深度嵌套。如果必须嵌套，可以引入父标签，但尽量不要超过两层。标签名带命名空间前缀（如 `o:`）能降低与内容冲突的概率。

例如工作流定义：
```
<o:workflow>
<o:step id="1">
<o:action>调用API</o:action>
<o:params>{"url": "..."}</o:params>
</o:step>
</o:workflow>
```

### 2. 编写解析器
用 Python 的 `re.findall` 处理扁/平字段最简单：
```python
import re
def parse_tag(text, tag):
    pattern = rf'<{tag}>(.*?)</{tag}>'
    return re.findall(pattern, text, re.DOTALL)
```
对于嵌套结构，可以先用正则在父标签内提取子串，再递归解析。若想更稳健，可使用 `xml.etree.ElementTree`，但注意它对非法字符比较严格，需要包裹在容错函数内。

### 3. 注入系统提示与示例
将格式要求写入系统提示，并展示完整示例。建议把示例输出做得稍长一些，让模型领会“标签内可以自由书写长文本”。例如：
> 你必须按以下格式输出分析结果：
> ```
> <analysis>
> <summary>文本摘要，可包含多段落，任意标点</summary>
> <keywords>逗号分隔关键词</keywords>
> </analysis>
> ```

### 4. 集成到 OpenClaw / MCP
在 OpenClaw 中，可以编写一个自定义 output formatter 插件，将模型的原始文本输入解析为 dict，供后续节点消费。MCP 工具同样可以要求 LLM 返回标签格式的结构化内容，再由客户端解析。

## 踩坑记录

**标签名冲突**：内容中出现 `<summary>` 这种字面文本。解决办法是指示模型对内容中的 `<` 和 `>` 转义为 `&lt;` 和 `&gt;`，或者使用全角尖括号 `〈〉`。我们更推荐后者，因为对模型来说更自然，不易遗忘转义。

**闭合遗漏**：长文本末尾模型可能漏掉闭合标签。通过后处理检测缺少的闭合标签，并插入补全。简单的栈式检查：记录开放标签，在输出末尾补上缺失的 `</tag>`。这点在工程上很容易做到。

**嵌套陷阱**：一旦引入嵌套，简单的正则就无法正确匹配（如多个同名子标签）。必须切换为递归下降解析器或使用 `html.parser`。因此，除非业务必需，尽量只用一层标签。

**性能与 token 消耗**：相比 JSON，标签格式会多消耗约 10-15% 的 token（多余标签名）。但比起反复重试和 JSON repair 的成本，这点消耗完全可以接受。

**大模型的“创新”**：有时模型会在标签内再加一层 JSON，混合使用。需在提示中强调“标签内直接放置目标文本，不要再嵌入 JSON”。

## 可复用建议

- **制定内部标签规范**：推广 `o:` 前缀，避免与常见词汇冲突。团队统一 schema 文档。
- **提供标准解析器**：在代码库中放置一个 `parse_tag_output(text, schema)` 函数，支持字段提取、类型转换、缺失字段默认值。
- **充分边界测试**：测试超长文本（>3000 字符）、多语言、emoji、代码块、URL 等。标签格式对这些内容的鲁棒性远超 JSON。
- **兼顾人类可读**：标签格式的输出比 compact JSON 更易阅读，这在日志排查、人工审核时非常有用。
- **与 JSON schema 互转**：如果外部系统必须接收 JSON，可以在解析后内部转成 dict，再序列化为 JSON。标签格式是“从模型获取结构化数据的稳定性界面”，JSON 是“内部流转标准格式”。

## 总结

标签格式不是要取代 JSON，而是作为大模型长文输出场景下的一种更稳定的“运输容器”。它牺牲了一点优雅和紧凑，换来了极高的容错和解析成功率。在 OpenClaw 这类强依赖 LLM 自动化的工作流中，减少一次重试往往就省下几秒延迟和若干 API 费用，积累起来的收益非常可观。

在下一次设计 Agent 的输出结构时，不妨试试定义一组简单的标签，你会惊讶于它带来的可靠性提升。
