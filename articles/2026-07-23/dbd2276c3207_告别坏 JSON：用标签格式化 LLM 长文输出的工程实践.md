## 背景

在 OpenClaw 这类可组合 Agent 框架里，LLM 经常需要输出**结构化长文本**——比如多段分析报告、分组配置、分级摘要。大家的第一反应往往是要求模型输出 JSON。

问题在于，长文本天然会包含换行、引号、特殊符号，模型即使学会了 JSON 语法，也极容易在生成过程中**漏掉一个逗号、忘记转义引号、或把嵌套层次写乱**。结果就是一个“坏 JSON”直接导致整个自动化流水线——Agent 链、MCP 工具调用、插件调度——卡死在解析阶段。

## 为什么 JSON 不适合长文结构化

- **语法零容忍**：JSON 解析器不接受任何微小错误，一个 `\n` 没有正确转义就会抛异常。
- **模型注意力稀释**：大段文本里维持括号、逗号、引号的平衡性，对模型是额外负担。
- **修复成本高**：即便用 `json_repair` 等库，也只能覆盖常见模式，在多层嵌套或内容含代码块时仍会失败。

在工程中，我们需要的不是“理论上正确”的格式，而是**极端情况下仍能被正确切分的格式**。

## 替代方案：标签格式

思路很简单：放弃强制类型约束，用**自定义标签**把文本分块，后端再做有容错性的解析。

例如，我们要求模型输出以下格式：

```
[REPORT]
这是一段报告摘要，可以包含任意字符，包括引号 " 和换行。
[/REPORT]

[RECOMENDATIONS]
- 建议 A：描述内容
- 建议 B：另一段描述，甚至可以有 [某标签] 字样，只要上下文清晰
[/RECOMENDATIONS]
```

解析时只需用正则或状态机匹配 `[TAG]...[/TAG]` 即可。即使模型少写了一个闭合标签，我们也能通过贪婪匹配到文档末尾或下一标签来处理，而不至于整个输出报废。

## 实现步骤

### 1. 设计标签集

根据业务需求，约定 3~6 个块标签，例如：

- `[FINDINGS]` → `[/FINDINGS]`
- `[RECOMMENDATIONS]` → `[/RECOMMENDATIONS]`
- `[RISKS]` → `[/RISKS]`

标签名用大写字母和下划线，避免与普通文本混淆。

### 2. 在 Prompt 中给足示例

不要只描述规则，**必须给出完整输入输出示例**：

```
请严格按照以下格式返回分析结果：

[FINDINGS]
（这里填写发现的问题，可包含多段文字）
[/FINDINGS]

[RECOMMENDATIONS]
（这里填写建议，每行一条，用 - 开头）
[/RECOMMENDATIONS]
```

并且在 Prompt 末尾加一句：“如果某个块内容为空，仍请保留空标签，如 `[RISKS][/RISKS]`。”

### 3. 解析器实现（Python 示例）

```python
import re

def parse_tagged_output(text: str, tags: list[str]) -> dict:
    result = {}
    for tag in tags:
        pattern = rf"\[{tag}\]\s*(.*?)\s*\[/{tag}\]"
        match = re.search(pattern, text, re.DOTALL)
        result[tag.lower()] = match.group(1).strip() if match else None
    return result
```

对未闭合标签增加容错：

```python
# 如果没有闭合，尝试匹配到字符串末尾或下一个标签
pattern = rf"\[{tag}\]\s*(.*?)(?:(?=\[\/?[A-Z_]\])|$)"
```

### 4. 集成到 Agent 工具链

把解析器封装为一个 MCP 工具（比如 `tag_parser`），接收原始 LLM 输出和标签列表，返回结构化字典。这样任何下游 Agent 都可以通过工具调用直接获取分块内容，无需关心解析细节。

## 踩坑与防御

### 内容中意外包含标签

用户输入或模型生成里可能出现 `[REPORT]` 这种字面量。解决办法：

- 在 Prompt 中要求：如果内容本身需要出现标签，应写成 `\[REPORT\]` 或替换为 `【REPORT】`。
- 解析端对未注册的标签或转义符号做一次清洗。

### 未闭合标签导致内容粘连

可以设置**最大匹配长度**或使用**区块边界检测**：当遇到下一个起始标签时，自动闭合前一个块。

### 嵌套需求

尽量避免嵌套标签设计。如果必须表达层级，可以用**标记前缀**扁平化，如 `[FINDINGS_ITEM]...[/FINDINGS_ITEM]`，而不是在 FINDINGS 内再嵌套。

## 可复用建议

- **做进项目基建**：在 OpenClaw 的插件或 MCP 服务里预制 `parse_tagged_output`，让所有 Agent 共享同一套解析逻辑和容错策略。
- **与 JSON 共存**：不要一刀切。简单结构（如只有几个字段）继续用 JSON；复杂长文本用标签。可以在系统配置里做“输出格式策略”切换。
- **配合重试**：当标签解析得到的必填块为空时，触发一次带修正指令的重试，而不是直接崩溃。

## 总结

标签格式没有 JSON 的类型系统优雅，但它**在 LLM 长文输出场景下远更鲁棒**。它是一种“降低期望、提升交付”的工程选择——你不再和坏 JSON 死磕，而是用少量自定义标记换回稳定的解析体验。

对于 OpenClaw 用户，内置一套轻量标签解析能力，能让你的自动化链路在真实世界中少死 80% 的解析故障。
