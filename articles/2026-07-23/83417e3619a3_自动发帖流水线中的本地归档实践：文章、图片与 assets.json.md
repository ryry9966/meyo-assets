## 背景

在基于 OpenClaw 或 Agent + MCP 搭建的自动发帖流水线里，流程通常以“提交发布”收尾。但发布＝终点吗？如果不做本地归档，每次生成的内容就像一次性消耗品——一旦平台侧被删除、链接失效或需要二次编辑，只能重新生成，无法回溯原始输出。更麻烦的是，文章引用的图片往往来自 DALL·E 生成、截图工具或外链图床，源头分散，极易断链。

因此，在流水线中增加一个“本地归档”环节，将文章、图片及元数据打包存盘，是一件性价比很高的工程习惯。本文围绕这一需求，梳理一套轻量、可脚本化的归档方案。

## 问题分析

自动发帖流水线的输出通常包含三样东西：

1. **文章正文**（Markdown 或 HTML）
2. **引用图片**（本地生成或远程 URL）
3. **元数据**（标题、标签、发布时间、生成参数等）

归档要解决的核心问题是：**如何把这些离散产物组织成一个自包含目录，让任何人在未来都能直接打开文章，看到完整图文，无需联网或依赖原始平台。** 这要求我们做到：

- 将所有远程图片下载到本地；
- 将文章内的图片引用改为相对路径；
- 用一份描述文件记录资源清单和生成上下文，方便后续脚本或 Agent 读取。

## 具体做法

### 1. 目录结构约定

每个帖子一个独立文件夹，以发布日期与 slug 组合命名：

```
posts/
└── 2025-04-08-automated-post-archiving/
    ├── article.md
    ├── images/
    │   ├── cover.png
    │   ├── diagram.png
    │   └── screenshot.png
    └── assets.json
```

### 2. 文章保存与图片落地

在流水线的发布步骤之后（或之前，视预览需求而定），增加一个 **archive** 步骤：

- 将生成好的 Markdown 字符串写入 `article.md`；
- 用正则提取所有 `![alt](url)` 中的 `url`，过滤出远程资源（`http://` 或 `https://` 开头）；
- 对每个远程 URL 逐一发起下载请求，将响应体写入 `images/` 目录，文件名使用 URL 的 hash 或 slug + 序号，保留原始扩展名；
- 替换 Markdown 中对应图片链接为相对路径：`![](./images/filename.png)`；
- 下载失败的图片保留原 URL，同时在日志中标记。

这一步建议用流式写入，避免大图撑爆内存，并发数控制在 3~5 以避免被图床限流。

### 3. 生成 assets.json

`assets.json` 是归档的“索引卡”，推荐最小字段如下：

```json
{
  "title": "自动发帖流水线中的本地归档实践",
  "slug": "automated-post-archiving",
  "date": "2025-04-08",
  "tags": ["automation", "openclaw"],
  "images": {
    "cover.png": "https://example.com/original-cover-url",
    "diagram.png": "https://example.com/diagram",
    "screenshot.png": "https://example.com/screenshot"
  },
  "generation_params": {
    "model": "gpt-4o",
    "prompt_hash": "abc123",
    "temperature": 0.7
  }
}
```

- `images` 字段记录本地文件名与原始远程 URL 的映射，方便溯源和换链；
- `generation_params` 留存生成参数，为后续复现或分析提供依据。

对于 OpenClaw 用户，可以将 `prompt_hash` 替换为 agent 任务 ID 或 workflow run ID，便于与日志系统打通。

### 4. 脚本化与 MCP 集成

上述逻辑很容易封装为一个 Node.js 或 Python 脚本，接收 Markdown 文本与图片 URL 列表，输出归档路径。之后可通过两种方式集成到自动化链路：

- **CLI 工具**：在流水线脚本中直接调用；
- **MCP server**：例如实现一个 `local-archiver` MCP 服务，暴露 `archive_post` 工具，供 OpenClaw 的 Agent 在发布后调用。该工具可复用 filesystem 和 fetch 能力，无需额外网络依赖。

这样，归档不再是手工操作，而是 Agent 可编排的标准步骤。

## 踩坑记录

1. **图片引用变体**：Markdown 图片语法存在 `![](url)`、`<img src="url">` 甚至前端框架的 `![alt](url?w=800)` 形式。提取正则需覆盖常见情况，并处理 URL 查询参数。简单做法是统一规范：要求生成阶段只输出标准 Markdown `![]()` 形式，否则归档脚本会跳过未知格式并告警。

2. **路径替换的坑**：避免在代码块或注释内的图片 URL 被误替换。可先用 Markdown AST 解析（如 unified/remark）定位图片节点，只替换正文中的有效图片。

3. **文件名冲突与特殊字符**：使用 URL 的 SHA256 前 8 位作为文件名可以有效去重并避免特殊字符；扩展名需从 Content-Type 或 URL 后缀推断，遇到未知时保存为 `.bin` 并记录。

4. **大文件与超时**：有些截图高达 10 MB 以上，下载时要设置超时和重试机制（建议 2 次重试，间隔 1 秒），避免因网络抖动导致整个归档步骤失败。对于长期存储，可考虑用 `sharp` 或 `imagemagick` 做有损压缩，但本次实践未强制执行，由用户按需处理。

5. **assets.json 的更新问题**：如果流水线支持“编辑后重新归档”，需考虑文件覆盖和 images 映射合并，而非简单重写。一个稳妥做法是以 slug 为唯一键，新旧合并时以最新为准。

## 可复用建议

- **从归档反哺发布**：若发布平台是基于 Git 的静态站点（Hugo、Hexo 等），归档目录本身就可以作为内容源，省去二次导出。
- **作为 Agent 上下文**：当需要修改旧帖子时，Agent 可直接读取 `assets.json` 和 `article.md`，不必重新从平台抓取，减少请求并提高可控性。
- **与版本控制结合**：将归档目录纳入 Git 仓库，每次发布产生一个 commit，形成可审计的内容历史。
- **扩展为离线审核流**：可在归档步骤前插入人工校验——将 `article.md` 和本地图片通过本地预览服务（如 `live-server`）打开，确认无误后再发布。

## 总结

本地归档在整个自动发帖流水线中只占很小的代码量，却承担了“内容资产固化”的关键角色。它将一次性生成物转化为可持续编辑、可版本追溯、可离线查看的独立单元。对 OpenClaw 用户来说，借助 MCP 工具将其沉淀为可复用能力后，每一个自动发帖任务都会自动形成一份完整存档，这种“无声自动化”正是工程上最安心的存在。
