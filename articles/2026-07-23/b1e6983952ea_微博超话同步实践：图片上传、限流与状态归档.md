## 背景

前段时间我用 OpenClaw 搭建了一个内容分发助手，其中一个固定环节是把每日生成的知识卡片自动发布到指定微博超话。需求看起来不复杂：文本 + 一张图片，调用接口发帖即可。但实际落地时，图片上传流程、接口限流、任务状态管理这些看似细枝末节的问题，逐步把一次简单的“调接口”变成了一个需要仔细设计的子系统。

这篇文章记录我在 OpenClaw 下实现微博超话同步的整个过程，重点放在图片上传链路、限流处理以及任务的状态归档上，希望能给有类似需求的同学一些可参考的工程思路。

## 问题拆解

微博开放平台对外提供 `statuses/share` 接口可以发布图文微博，但在超话场景下有几点不同：

1. **图片必须先上传**，拿到 `pid` 后才能与文本一起提交，不是直接把图片二进制塞进发帖请求。
2. **超话发帖需要额外参数**（如超话 ID、`visible` 等），实际调试时发现部分接口需要带上超话的 `topic_id`，并且签名验证比普通发博更严格。
3. **接口限制非常具体**：图片上传接口每小时有次数限制，`statuses/update` 类接口也有用户级频率控制，返回 429 时如果没有合理的重试策略，任务很容易大面积失败。
4. **任务状态难追踪**：一次发帖涉及至少三个步骤（上传图片、发帖、可选地获取帖子链接），任何一个环节失败都需要知道当前进度、失败原因，并决定是立即重试、延迟重试还是标记为不可恢复错误。

没有状态归档和限流保护，跑几天就会出现重复上传、重复发帖或者静默丢失任务的情况，这在自动化流程里是不可接受的。

## 做法与步骤

### 1. 整体架构

围绕 OpenClaw 的 Skill 机制，我把微博超话同步拆成一个独立的 skill，内部包含三个动作：`upload_image`、`post_to_super_topic`、`archive_status`。外部工作流只需要把“今日卡片文本+图片路径”作为输入提给这个 skill，其余由 skill 内部的有限状态机接管。

状态持久化选用了 SQLite（单文件，免去额外服务依赖），每条任务记录包含：

- `task_id` (唯一)
- `status` (pending / uploading / uploaded / posting / done / failed / retry)
- `pid` (上传成功后填充)
- `post_id` (发帖成功后填充)
- `retry_count`、`last_error`、`next_retry_at`

### 2. 图片上传

微博开放平台的图片上传接口是 `https://upload.api.weibo.com/2/statuses/upload.json`，要求 `multipart/form-data`，参数 `access_token`、`status`（可为空，但部分 SDK 要求传递）、`pic` 文件字段。返回的 JSON 中取出 `pic_id`（即 `pid`）即可。

实际工程中遇到的几个处理：

- **图片自动压缩**：超话场景下图片显示尺寸通常不超过 1200px 宽，原图过大不仅浪费流量也更容易触发上传限制。skill 内置了一个 `preprocess_image` 步骤，使用 Pillow 将图片长边缩至 1200px、保存质量为 85 的 JPEG，并确保文件大小 < 5 MB（微博上传限制）。
- **上传失败重试**：网络波动导致的超时直接重试 1 次；如果返回错误码表明图片格式非法，则转为 `failed` 状态并写入明确的错误信息。
- **pid 使用注意**：不同应用类型获取的 pid 有时不能跨接口使用，这里通过同一 access_token 下的 `statuses/upload` 和 `statuses/share` 配合，保证 pid 可以被后续 `statuses/share` 消费。

### 3. 超话发帖

发帖使用 `statuses/share` 接口，额外需要带上超话对应的 `topic_id`，参数大致如下：

```
access_token=xxx
status=文本内容
pic_id=上传得到的pid
topic_id=超话ID
visible=0
```

发帖返回 `id` 字段即为该条微博的 mid，可拼接成 PC 端链接存档。

这里踩了一个坑：超话发帖的权限校验依赖于当前 token 对应的用户是否加入了该超话，以及超话本身的发帖限制（等级、关注时长等）。如果检测到返回错误码 `10024`（权限不足），skill 会直接标记为 `failed` 且不会重试，避免无意义的重复请求。

### 4. 限流处理

限流场景主要有两类：

- **图片上传限流**：独立于微博发帖频率控制，一般每小时 150 次（具体和 App Key 权限有关）。短时间内连续大量上传图片会收到 `10022` 或 HTTP 429。
- **发帖接口限流**：同一用户每小时发博数量、两次发帖最小间隔等限制。

应对方式很传统但有效：

1. **拦截 429 并解析 Retry-After**：微博部分 429 响应会返回 `Retry-After` 头（单位秒），skill 在捕获到 429 后会将当前任务状态置为 `retry`，计算 `next_retry_at = now + Retry-After`，然后结束本次执行。
2. **固定退避 + 斜率控制**：如果响应中没有 Retry-After，则采用指数退避，初始等待 60 秒，最大不超过 600 秒，且重试次数超过 3 次后降级为每 30 分钟检查一次。
3. **任务节流**：在 OpenClaw 的层面，对同一 skill 增加最小执行间隔 90 秒，从源头降低触发频率。

### 5. 状态归档与重试

所有任务状态更新的 SQL 操作都放在 `archive_status` 步骤中，保证最终一致。skill 执行结束时，工作流会读取最新状态，对于仍处于 `retry` 状态的任务，写入一个 OpenClaw 的定时任务队列，到 `next_retry_at` 时间后再触发执行，只执行尚未成功的子步骤（通过 status 值跳过已完成的环节）。

这样即使整个 OpenClaw 进程重启，也不会丢失任务进度。同时状态归档也方便后期手动排查：哪些帖子因为权限问题永久失败、哪些因为网络抖动自动恢复，都有据可查。

## 踩坑点

1. **pid 跨接口失效**  
   部分应用使用 `statuses/upload_url_text` 获取的 `pic_id` 不能直接用于 `statuses/share`，必须用 `statuses/upload` 接口。如果在控制台调试时发现图片明明上传成功但发帖提示“图片不存在”，大概率就是 pid 来源不一致。

2. **超话 ID 与数字 id 混用**  
   微博超话的 `topic_id` 是数字字符串，但有时文档或工具会给带文字标识的 `sina_ent_id`，需要提前转换，否则 `statuses/share` 会返回“超话不存在”。

3. **图片内容审核导致的上传失败**  
   微博上传接口本身可能返回图片审核不通过的模糊错误（通常是 `error_code: 20019` 或 `content illegal`），这不属于重试可恢复错误，需要在状态机中归类为 `failed`，并给出提示人工干预。

4. **限流粒度不是全局唯一**  
   同一 IP 多账号时，IP 也可能被限频，但错误信息与用户级限流一致，日志中需要带上账号和出口 IP 以便区分。

## 可复用建议

- **把超话同步封装成 OpenClaw Skill**，使用标准 MCP 接口暴露，其他 Agent 只需提供文本和图片路径即可复用，免去反复处理微博 API 的细节。
- **状态存储采用 SQLite** 单文件部署简单，适合单节点场景；如果任务量大，可替换为 PostgreSQL，只需要修改 `archive_status` 里的连接配置，不影响状态机逻辑。
- **限流模块独立为装饰器**，抽离出 `@throttle_aware` 机制，未来对接其他平台 API（如头条、B站）时可直接复用，只需注入对应的错误码映射和限流参数。
- **任务重试归入 OpenClaw 的计划任务机制**，避免额外依赖 Celery 等调度组件，降低整体复杂度。

## 总结

微博超话同步看起来只是“发一条带图微博”，但工程落地过程中，图片上传链路稳定性、限流的层层处理、任务状态的完整追踪才是决定长期运行质量的关键。通过 OpenClaw 的 Skill 封装，结合简单的状态机模式和任务调度，可以把这个看似杂乱的问题整理成一个小而美的自动化模块，稳定运行数周无异常。

如果你也在做类似的社媒同步工具，建议不要放过任何一次 429 和任何一次静默失败，把状态归档做扎实，后面能省下大量排查时间。
