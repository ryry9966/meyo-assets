## 背景

内容创作者或开源维护者经常需要在多个技术社区（掘金、SegmentFault、知乎、公众号、Twitter、Discord 等）发布同一篇文章或通知，以覆盖不同受众。随着 OpenClaw、Agent 与 MCP 插件生态的成熟，不少人已经实现了“一次撰写、Agent 自动同步分发”。但自动化在带来效率的同时，往往忽略了一个真实的问题：**多平台密集推送会造成强烈的刷屏感**。关注者在半小时内看到你三条一模一样的帖子，体验极差，甚至可能取关或被平台降权。

我们团队自己维护着一个开源项目的宣传渠道，用 OpenClaw 编排 Agent，通过 MCP 连接了 GitHub Discussions、Twitter API、飞书、Discord Webhook 和掘金开放接口。最初直接做“写完即全量同步”，很快收到社区反馈“能不能别一次性轰炸”。经过三次迭代，我们沉淀出一套**有人味儿的跨社区发布策略**，核心原则是：**内容一致、时间错峰、平台适配、可解释**。

## 问题拆解

刷屏的根本原因不是同步这个动作本身，而是**瞬时并发 + 完全同质化 + 缺少反馈调节**。自动化的边界在于：

- **时效性的误用**：技术文章不是突发新闻，不需要三分钟内全网覆盖。
- **忽略平台上下文**：掘金读者看的是长文摘要，Twitter 用户需要一句话钩子，Discord 更喜欢讨论开场。直接复制粘贴只会制造噪音。
- **缺乏冷却机制**：连续发布后即使间隔了几分钟，在用户信息流里也可能因为排序算法而扎堆出现。

我们的目标不是不发布，而是让关注者在每个平台看到的内容**像独立发送的**，而不是一个机器人的批量任务。

## 做法与步骤

### 1. 设计发布计划元数据

在内容创作完成后，Agent 首先生成一份 `publish_plan.json`，包含基础内容、核心摘要、长版简介、短版钩子、标签建议。结构大致如下：

```json
{
  "base_content": "## 正文 Markdown...",
  "abstract": "本文介绍了一种用 Rust 优化 MCP 服务启动时间的方法...",
  "short_hook": "Rust + MCP: 冷启动降低 60%",
  "long_intro": "我们在生产环境遇到 MCP 客户端频繁超时，分析后发现...",
  "tags": ["Rust", "MCP", "OpenClaw"],
  "platforms": ["juejin", "twitter", "discord", "zhihu"],
  "publish_window_hours": 48
}
```

### 2. Agent 生成平台适配版本

利用支持函数调用的大模型（通过 OpenClaw Agent 编排），针对每个目标平台生成**结构化差异内容**，而不是单纯替换变量。

- **Twitter**：只取 `short_hook` + 一条链接 + 1-2 个 hashtag，转换为不超过 280 字符的文本。
- **Discord**：发出 `long_intro`，末尾带一个讨论问题，例如“你们会在本地开发环境使用 MCP 吗？”。
- **掘金**：用 `abstract` 作推荐语，`base_content` 作为正文，添加平台要求的标签格式。
- **知乎**：提取 `base_content` 前三分之一作为文章概要，并在开头插入引导语。

所有生成结果存入 `platform_payloads` 对象，Agent 仅做“改写”不做论断性修改，避免偏离原意。

### 3. 延迟队列与冷却控制

我们将发布任务放进一个简单的延迟队列，由 OpenClaw 的任务调度器管理。每条任务定义最早执行时间，各平台间隔设置为 4–12 小时不等，全部平台完成发布总时间控制在 `publish_window_hours` 内（默认 48 小时）。

具体实现中，我们用 Redis 的 sorted set 保存任务时间戳，Agent 的定时动作每分钟拉取到期任务。同时引入**全局冷却计数器**：24 小时内最多发布 3 个不同内容的主体（避免多个文章同时启动同步窗口造成重叠）。

### 4. 发布前检查与回退 Hook

在真正调用 MCP 发布工具前，执行两个关键检查：

- **去重比对**：检查目标平台最近一段时间的发文记录（通过各平台 API 或本地缓存），如果已经存在高度相似标题或摘要，则自动取消并记录日志。
- **健康度抽样**：对 Twitter 等平台，抽样当前账号的最新互动率，如果近期连续多篇互动低于阈值，Agent 会建议跳过该平台，并在日志中给出理由：“前 3 篇互动中位数 < 10，建议推迟”。

发布完成后，Agent 将平台返回的 post_id、时间戳写入本地记录，用于后续分析和防重复。

## 踩坑点

- **平台 API 限流极端不一致**：Twitter 免费层级发帖数量非常有限，Discord Webhook 几乎无限制。如果调度器同时触发，Twitter 很容易被限流，必须为每个平台单独设置最大并发数。
- **Agent 生成质量波动**：短钩子的吸引力受模型温度影响大，有时会生成营销味过重或夸大标题。我们增加了一个简单规则过滤器：禁止使用“炸裂”“天花板”等词汇，否则要求重写。
- **知乎发布格式陷阱**：知乎文章源码粘贴 Markdown 可能出现格式错乱，需要先将 Markdown 转换为 HTML 再提交。Agent 要调用一个专门的转换工具（通过 MCP 包装 Pandoc），并处理代码块高亮问题。
- **重叠窗口的连锁反应**：如果两篇不同文章在 48 小时内同时进入队列，冷却机制必须能识别 topic 粒度，而不是笼统限制所有发布。我们加入内容 hash 作为分组 key，防止误伤。
- **可观测性不足**：一开始只记录了发布成功/失败，后来发现需要记录每一步的决策理由（为什么跳过了某个平台），否则出问题时排查困难。所有 Agent 决策都写进结构化日志。

## 可复用建议

1. **发布计划与内容工厂分离**：不要在一个 Agent 步骤里同时生成内容和发布决策。可以定义三个独立 Agent：ContentGenerator、PublishPlanner、Distributor，各司其职，易于调试和复用。
2. **将敏感配置环境变量化**：平台 Token、冷却阈值、时间窗口等通过环境变量注入，方便在不同项目间复用同一套编排逻辑。
3. **建立平台抽象层**：用 MCP 工具抽象多平台发布接口，统一为一个 `post_to_platform(platform, payload)` 调用，后续新增平台只需增加工具描述，不改变 Agent 流程。
4. **增加人工确认节点（可选）**：对于重要内容，可以在延迟队列前插入一个审核步骤，由人在 OpenClaw 的通知通道确认后再进入分布式调度，降低风险。
5. **保留“紧急发布”旁路**：为突发公告设置白名单开关，允许绕过冷却和延迟限制，但不能滥用，每次使用会要求附加原因日志。

## 总结

自动化同步的目标不是“第一时间塞满所有渠道”，而是**让正确的内容在合适的时间以恰当的形式到达读者**。通过 Agent 生成平台适配版本、延迟队列分片、冷却控制与回退检查，我们几乎消除了多社区刷屏的投诉，同时发布成功率保持在 98% 以上。这套实践对 OpenClaw 的用户来说可以直接移植——在已有的 Agent + MCP 框架下，只需约束时间与形式的边界，就能让自动化发布更有人味儿，而不是一台失控的群发机。
