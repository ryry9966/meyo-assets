## 背景：不起眼的“5 分钟任务”

在 OpenClaw 里挂一个定时拉取外部数据、调用 Agent 做分析的工作流，是非常典型的自动化场景。cron 配成 `*/5 * * * *`，预期每 5 分钟跑一次。任务体量不大，通常 2–3 分钟跑完，看起来岁月静好。

直到某天上游接口偶尔从百毫秒掉到 20 秒，LLM 推理也因为排队多耗了 1 分钟，任务总耗时悄悄超过了 5 分钟。于是下一次调度如期而至，而前一个实例还在跑——两个同一任务同时执行，脏数据、重复通知、API 限流警告接踵而来。

这就是 **任务重入（re-entry）**，也是所有定时系统里最容易被“以为没事”击穿的坑。

## 问题拆解：重叠执行的代价

“偶尔撞一下又怎样？”——如果你的任务涉及到以下任何一项，代价就不仅是日志乱掉：

- **幂等性缺失**：下游不是天然幂等的操作（比如重复发送通知、重复插入记录）。
- **外部资源竞争**：调用第三方 API 超额导致账号被封或计费飙升。
- **共享状态覆盖**：多个实例同时更新某个状态文件/数据库行，后完成的任务覆盖前一个任务的正确结果。
- **上下文污染**：在 OpenClaw 中，如果使用了会话级上下文或共享 memory，并行执行会让 Agent 读到混乱的历史。

一个真实的故障路径：任务 A（10:00）开始处理文件，10:03 还在写结果；任务 B（10:05）启动，读到尚未写完的中间文件或者被锁占用的资源，直接 crash 或产出半成品，连锁触发监控告警。

## 防重入的做法：以锁为“入口守卫”

核心思路简单：**执行前抢锁，抢到才干活，做完释放**。在 OpenClaw 体系里可落地的方式主要有三种。

### 1. 基于 Redis 的分布式锁（推荐）

如果你的 OpenClaw 与 Redis 已经打通（很多 MCP 服务都会依赖 Redis 做缓存），直接用 `SET key value NX EX 300` 实现互斥锁。伪代码：

```
lock_key = f"task_lock:{workflow_name}"
acquired = redis.set(lock_key, instance_id, nx=True, ex=300)
if not acquired:
    log("上一次任务未完成，跳过本次触发")
    return
try:
    execute_workflow()
finally:
    # 只有锁的持有者才能释放，避免误删
    if redis.get(lock_key) == instance_id:
        redis.delete(lock_key)
```

设置 `ex=300`（5 分钟）是为了防止进程异常退出后锁永不释放，但这也带来了第一个坑——超时时间怎么定。

### 2. 数据库状态位（适合无 Redis 场景）

在任务控制表里加 `status` 字段（`idle` / `running`），执行前用乐观更新抢状态：

```sql
UPDATE task_control SET status='running', start_time=now()
WHERE task_name='poll_orders' AND status='idle';
```

根据 affected rows 判断是否抢到。务必配合 `start_time` 做超时兜底（例如超过 10 分钟强制释放），否则一次 crash 就会让任务永远空闲。

### 3. 工作流级别的幂等键

OpenClaw 的一些 workflow 引擎支持 `deduplication_key` 或 `idempotency_key`。如果调度平台本身支持，可以直接在触发时传入带时间戳的 key（比如 `task_name:2025-03-15-10:00`），这样即使重复投递也只会创建一次运行实例。缺点是如果上一次跑太久，合法的下一个周期也会被丢弃，需要权衡。

## 踩坑点：锁不是加了就万事大吉

### 坑 1：锁超时而任务仍在跑

这是最常见的事故。任务实际耗时 7 分钟，锁的 `EX` 设了 300 秒，5 分钟后锁自动过期，下一个实例抢到锁开始执行，于是又回到重叠执行。

**解法**：引入锁续期（watchdog），在任务执行过程中定期刷新锁的过期时间（例如每 60 秒 `EXPIRE lock_key 300`），但要确保最终释放锁的只有持有者。或者干脆把锁的过期时间设成任务允许的最大时长，配合超时 kill 机制。

### 坑 2：锁被错误释放

如果不用 instance_id 校验就直接 `delete`，A 的锁过期后被 B 抢到，A 执行完毕会误删 B 的锁。因此释放时必须比对持有者。

### 坑 3：单点 Redis 成核心依赖

如果 Redis 挂了，所有定时任务都会因为抢不到锁而停摆。这需要在业务上决定策略：是选择“宁可空转也不丢锁”的安全侧，还是在锁服务不可用时降级为本地文件锁？工程上更稳妥的做法是：Redis 异常时直接 fail fast 并告警，而不是悄悄放行。

### 坑 4：开发环境与生产环境的锁键冲突

多人共享 Redis 时，`task_lock:my_workflow` 可能被多个环境抢占。建议 key 中加入环境前缀，如 `lock:prod:my_workflow`。

## 可复用建议

- **抽象出通用装饰器/中间件**：对于所有定时任务入口，封装 `@with_lock("my_task", ttl=600, extend_interval=60)`，把抢锁、续期、释放、异常处理一并收敛。
- **监控重叠指标**：在每次因未抢到锁而跳过的路径上打点，格式为 `schedule_overlap{task="xxx"}`，当该指标非零且持续出现时告警。
- **先保幂等，再谈防重入**：防重入锁会极大降低重叠概率，但不能保证绝对不发生（例如锁误释放、主从切换瞬间）。所以核心流程本身需要是幂等的，或者至少能检测到“重复操作”而报警。
- **为长时间 Agent 任务单独做超时控制**：如果 OpenClaw Agent 里调用了多个 LLM 步骤，总耗时可能剧烈波动，固定 `EX` 容易失配。使用增量续期 + 硬超时（context deadline）双保险。
- **文档化任务运行边界**：在 Readme 中说明“如果任务耗时可能超过调度间隔，请务必开启防重入锁，并将锁 TTL 设定为最大允许执行时长的 1.5 倍”，这会在团队协作中减少误解。

## 总结

“5 分钟任务会撞车”，看起来是调度间隔和执行时长之间的简单算术问题，但它暴露的是任务可靠性设计的缺位。在 OpenClaw 这类把工作流调度与 Agent 运行时深度绑定的系统中，任何一个长时间推理的步骤都可能打破原本平稳的时间假设。

防重入锁属于廉价的保险，实现成本极低，但能避免很多凌晨 3 点的紧急修复。加锁、续期、释放、监控四步走，配合业务幂等，就能把“偶尔撞车”变成“优雅跳过”。
