## 背景

在自动化运营场景中，将内容定时同步到微博超话是一个常见但容易踩坑的需求。我们基于 OpenClaw 的 MCP (Model Context Protocol) 插件体系，搭建了一条从本地 Markdown 源到微博超话的发布流水线。整个管道需要处理：多图上传、OpenAPI 限流窗口的准确控制、发帖失败时的状态归档与重试，以及本地-远端状态的最终一致性。本文将围绕这几个核心挑战展开，还原一个可复现的工程方案。

## 问题拆解

1. **图片上传的隐式约束**  
   微博开放平台的 `statuses/share` 接口虽然支持传多图，但底层实际上会先走一个隐式的图片上传流程。官方文档对图片大小、格式、上传方式的描述分散在多个接口中。如果直接在 `share` 里传本地文件 ID，容易出现 `pic_id` 无效或图片丢失的问题。

2. **限流处理不当导致任务雪崩**  
   未充分理解限流规则（如每个应用每小时的发帖次数、图片上传独立限频），盲目使用固定间隔调用，极易触发 `10024` 或 `10022` 错误。一旦触发限流，如果没有合理的退避，后续排队任务会全部失败。

3. **状态跟踪缺失**  
   只关注“发没发出去”是不够的。图片是否上传成功、帖子是否进入审核态、超话分类是否正确，都需要持久化记录。否则问题回溯只能靠翻后台和手动比对。

## 做法与步骤

### 1. 图片预处理与上传分离

为了避免 `share` 接口内部的图片处理超时，我们选择先手动调用 `statuses/upload` 完成图片上传，获取 `pic_id` 后再组合发帖。

```python
# 伪代码：独立上传图片
pic_ids = []
for img in imgs:
    with open(img.path, 'rb') as f:
        res = weibo.upload(img_type='json', file=f)
        if res.get('pic_id'):
            pic_ids.append(res['pic_id'])
```

需要注意的点：
- 图片必须小于 5MB，建议在本地用 Pillow 压缩到 1920px 宽以内，JPEG quality 85。
- 上传时显式指定 `Content-Type: multipart/form-data`，用 `requests` 的 `files` 参数构造，否则容易遇到 `pic_desc` 解析错误。
- 上传接口本身也有频控，我们实测稳定间隔为每张图 3s 以上。

### 2. 基于窗口的限流控制

微博发帖接口的限流规则通常为“每应用每用户每小时 N 次”。我们实现了一个简单的滑窗限流器，将发帖、图片上传的请求统一管理，避免在小范围内突发调用。

核心逻辑：
- 以秒为单位的本地时间窗口，记录最近 1 小时内各接口的调用次数。
- 在下一次请求前，计算剩余配额。如果配额不足，根据最近一次成功调用的时间推算需要等待的秒数，并主动 sleep。
- 图片上传接口和发帖接口维护两个独立的计数器。

这种提前控频的方式，比遭遇限流后再退避更稳定，也避免因并发导致的配额争抢。

### 3. 发帖与多图参数

发帖时，超话需要指定 `domain` 或 `topic` 参数。我们采用的 payload 如下：

```json
{
  "status": "这是帖子正文 #超话名称#",
  "visible": 0,
  "pic_id": "pic_id1,pic_id2",
  "domain": "超话域名"
}
```

注意 `pic_id` 是逗号分隔的字符串，不是数组。如果带上 `pic_id` 但未预先上传，接口可能返回成功但图片不显示。所以务必确保上传成功后再发帖。

### 4. 状态归档与重试

我们使用 SQLite 作为本地状态存储，设计了两张表：
- `sync_log`：记录每次发帖的创建时间、微博返回的 `id`、状态（pending/success/failed/review）。
- `media_map`：记录原始本地图片路径、上传后的 `pic_id`、上传时间。

发帖后如果返回 `10024` 或其他限流错误，将任务标记为 `failed` 并记录错误码，同时写入到延迟队列（例如 15 分钟后重试）。重试前重新检查限流窗口，避免再次撞墙。

对于返回 `200` 但实际进入审核态的情况，我们通过定时回查 `statuses/show` 接口，对比 `text` 和 `pic_ids` 是否与发帖参数一致，并更新状态为 `review` 或 `success`。

## 踩坑记录

- **图片 Content-Type 小细节**：使用 `requests.post(url, files={'file': ('image.jpg', open(...), 'image/jpeg')})` 时，若文件名包含中文，微博服务器可能解析为乱码，导致 `pic_id` 为空。建议使用纯英文数字命名。
- **限流窗口“冒烟”测试**：文档中的次数可能包含 IP 维度限制。我们曾以为应用级限额还未用完，实际在同一出口 IP 上已经因其他任务触发限制，导致发帖报错。最终方案是在机房出口前增加应用+IP 双维度计数器。
- **超话 domain 查找**：`domain` 不是超话名称，需要通过搜索接口查询，一次查询后缓存到本地。若 domain 错误，帖子会发布到个人主页而非超话，极易漏掉。
- **归档时区问题**：微博返回的 `created_at` 是北京时间，但系统默认 UTC。存储时必须转换为 UTC 或用带时区的时间格式，否则依赖时间排序的监控面板会错乱。

## 可复用建议

1. **分离关注点**：将图片上传、发帖、状态查询拆为独立 MCP tool 或 Agent action，每个 tool 只处理一个接口，组合成 workflow。出错时容易定位。
2. **滑窗限流中间件**：为所有微博 API 调用封装一个统一的 `rate_limited_call` 函数，内部维护应用级、IP 级、用户级三层计数器。
3. **幂等设计**：发帖前根据内容哈希检查 `sync_log` 是否已经存在相同成功记录，防止因重试导致重复发帖。
4. **可观测性**：将每次 API 调用的耗时、限流等待秒数、错误码打入日志，并接入 OpenClaw 的监控钩子，生成每周成功率报表。
5. **备用渠道**：当超话发帖连续失败超过阈值时，降级为发布普通微博并记录 `domain` 缺失原因，方便人工补发。

## 总结

微博超话同步的难点不在于接口本身，而在于对图片上传链路的完整控制、限流窗口的精准处理以及全生命周期的状态归档。通过 OpenClaw MCP 将各个步骤拆分为独立、可观测的模块，我们实现了从图片压缩到发帖归档的闭环。过程中积累的滑窗限流器和状态表设计，可以低成本迁移到其他社交平台的自动化管道中。

> 稳定自动化不是消灭错误，而是让每一个错误都有迹可循、可重试、可恢复。
