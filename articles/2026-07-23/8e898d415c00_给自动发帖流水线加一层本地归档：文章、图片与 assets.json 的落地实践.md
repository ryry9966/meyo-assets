## 背景：为什么流水线需要本地归档

不少同学用 OpenClaw + Agent 搭起了自动发帖流水线——创作、配图、多发平台，整套流程跑得很顺。但跑了一段时间后，一个问题会慢慢浮现：平台上的内容并不真正属于你。

文章可能被吞、账号可能受限，甚至平台调整 API 后，旧内容就拉不回来了。更现实的需求是，后续如果想基于已发内容做 RAG、重新编辑、跨平台同步，总不能每次都靠爬自己。

所以要给流水线加一层本地归档，而且得是**结构化、可查询、对后续 Agent 友好**的那种。

本文基于我自己的实践，聊聊如何用 `assets.json` 做文章与图片的本地归档，适合已经用 OpenClaw、MCP 或自建 Agent 跑自动发帖的同学参考。

## 问题拆解

看上去就是“把文章和图片存下来”，实际上有几个点必须想清楚：

1. 一篇文章可能有多张图片，图片可能被多篇文章复用。
2. 生成阶段的本地图片和发布后的远程图片 URL，如何关联？
3. 归档结构要能方便后续 Agent 工具直接消费，比如搜索、统计、重新发布。
4. 流水线可能多次触发，归档操作必须幂等，不能越存越乱。

直接散落存文件肯定不行，需要一个清单文件作为索引。

## 设计方案

核心思路：**一个帖子一个目录，一份 `assets.json` 作为这个帖子的全部资源清单。**

目录结构：

```
archive/
└── posts/
    └── {post_id}/
        ├── index.md          # 文章正文（Markdown）
        ├── assets.json       # 资源清单
        └── images/
            ├── cover.png
            ├── body_01.png
            └── ...
```

`assets.json` 的 schema 大致如下：

```json
{
  "post_id": "20250321-001",
  "title": "xxx",
  "created_at": "2025-03-21T10:00:00Z",
  "platforms": [
    {
      "name": "twitter",
      "post_url": "https://...",
      "published_at": "..."
    }
  ],
  "content_md": "index.md",
  "images": [
    {
      "file": "images/cover.png",
      "role": "cover",
      "content_hash": "sha256:abc123...",
      "source_url": "https://cdn.example.com/xxx.png",
      "alt_text": "..."
    }
  ],
  "tags": ["automation", "openclaw"]
}
```

关键字段解释：

- `post_id`：唯一标识，建议带日期，方便按时间分片。
- `platforms`：记录各平台发布后的 URL，方便回溯。
- `images[].content_hash`：对图片内容取哈希（SHA256），用于去重和完整性校验。
- `images[].source_url`：生成/发布时获得的远程 URL，之后如果需要清理远程 CDN 也能按图索骥。

## 在流水线中落地的步骤

### 1. 确定何时归档

推荐在两个时机：

- **生成完成时**：文章 Markdown 确定、图片生成完毕，此时立刻本地归档。优点是不依赖任何平台，内容最“纯净”。
- **发布完成后**：补充 `platforms` 字段，记录各平台的实际 URL 和时间。

我用的是 OpenClaw 的 `after_publish` hook，在里面调用一个本地归档 action。如果你的流水线是脚本驱动，就在发布函数的 finally 块里执行归档逻辑。

### 2. 图片去重与存储

图片是归档里最容易出问题的部分。同一个素材可能在多篇文章里出现，如果每篇都存一份太浪费磁盘。

我用**内容寻址存储（CAS）**的思路：

- 计算图片内容的 SHA256，作为基准文件名存入 `images/`。
- `assets.json` 里记录真实文件名（可以带语义，如 `cover.png`）。
- 实际存储时，用硬链接或符号链接指向一个全局 `blobs/` 目录，避免重复数据。

简化版直接用文件复制也可以，几百篇文章内磁盘压力不大。

### 3. 生成 assets.json 与幂等性

归档脚本的核心逻辑（伪代码）：

```python
def archive_post(post_id, markdown_text, images, platforms):
    post_dir = ARCHIVE_ROOT / "posts" / post_id
    post_dir.mkdir(parents=True, exist_ok=True)

    # 写文章
    (post_dir / "index.md").write_text(markdown_text)

    # 处理图片
    img_list = []
    for img in images:
        data = img["bytes"]
        h = hashlib.sha256(data).hexdigest()
        dest_name = f"images/{img['role']}_{h[:8]}.png"
        dest_path = post_dir / dest_name
        dest_path.parent.mkdir(exist_ok=True)
        if not dest_path.exists():
            dest_path.write_bytes(data)

        img_list.append({
            "file": dest_name,
            "role": img["role"],
            "content_hash": f"sha256:{h}",
            "source_url": img.get("source_url"),
            "alt_text": img.get("alt_text")
        })

    # 合并平台信息
    existing = {}
    assets_path = post_dir / "assets.json"
    if assets_path.exists():
        existing = json.loads(assets_path.read_text())

    record = {
        "post_id": post_id,
        "title": existing.get("title", extract_title(markdown_text)),
        "created_at": existing.get("created_at", now_iso()),
        "platforms": merge_platforms(existing.get("platforms", []), platforms),
        "content_md": "index.md",
        "images": img_list or existing.get("images", []),
        "tags": existing.get("tags", [])
    }

    assets_path.write_text(json.dumps(record, ensure_ascii=False, indent=2))
```

重点：先检查 `assets.json` 是否存在，存在则合并字段，保证幂等。

## 踩坑实录

**坑1：图片文件名冲突**

如果只用原始文件名或简单序号，跨目录迁移或合并归档时很容易覆盖。用 `role + 哈希前8位` 的方式可以显著降低冲突概率，且语义可读。

**坑2：assets.json 被并发写坏**

如果多个流水线实例同时执行归档，可能会同时读写 `assets.json`。最简单的解法是利用文件锁，或者在 Agent 的队列层面保证同一 `post_id` 只有一个 worker 操作。我用的是 SQLite 作为锁中介，轻量又稳。

**坑3：图片远程 URL 失效**

发布后过段时间，CDN 上的图片可能被清理，`source_url` 就变成了死链。本地归档就是为了兜底，所以 `source_url` 只是辅助字段，不参与核心逻辑。如果之后需要恢复线上图片，可以根据 `content_hash` 重新上传。

**坑4：文章更新覆盖**

同一篇文章可能会修改后重发，此时归档需要版本化。简单做法是 `post_id` 不变，`assets.json` 里加一个 `revision` 字段递增，历史版本另存为 `index.v1.md` 等。

## 可复用建议

如果你的流水线是基于 OpenClaw 或类似 Agent 框架，可以将归档逻辑封装成一个 **MCP tool**，方便在任何工作流节点调用。tool 的定义：

- 名称：`archive_post`
- 参数：`post_id`, `markdown`, `images` (base64 数组), `platforms`
- 返回：归档路径与 assets.json 内容

这样无论是手动调试、定时任务还是事件驱动，都能直接复用。

对于图片去重要求较高的场景，推荐引入全局 blob store，将图片 blobs 单独管理，然后通过 `content_hash` 关联，整体目录结构更干净。

## 总结

自动发帖流水线加上本地归档，本质上是在为你自己的内容主权做一个确定性兜底。结构不用复杂，`assets.json` 作为资源清单 + 按帖分目录的方式，足够应对多数个人或小团队的使用强度。

重要的是**从一开始就设计好幂等和可扩展的 schema**，否则后续补救会很疼。完整的归档之后，你可以轻松接上本地搜索、再发布、数据统计分析等需求，让你的 Agent 真正拥有“记忆”。
