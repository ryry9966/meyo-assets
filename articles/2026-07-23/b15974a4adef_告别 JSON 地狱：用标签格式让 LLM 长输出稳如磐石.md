## 背景

在构建 Agent 工作流或基于 OpenClaw 的自动化管线时，我们频繁要求 LLM 输出结构化数据，例如一篇文章的不同章节摘要、多轮对话的意图分类，或者一份包含标题、正文、结论的长文。过去我习惯用 JSON 承载这些内容，因为下游程序可以无缝反序列化。但实践下来，只要输出超过 3000 token，JSON 就开始变得脆弱：偶尔缺一个闭合花括号、字符串里没有正确转义引号，或者凭空多出一个逗号——直接导致 `JSON.parse` 失败，整个自动化流程中断。

这个问题在长文生成场景尤其突出。LLM 在生成文本时更像一个自回归的“续写机器”，它对嵌套结构的平衡感远远不如人类。随着输出长度增加，括号不匹配的概率迅速上升。反复在 Prompt 里强调“确保输出合法 JSON”、甚至加入修复逻辑，依然无法根治。

## 问题：JSON 的刚性束缚

JSON 的理想用途是数据交换，格式规整、无歧义。但 LLM 面对两大挑战：
1. **长文本内的特殊字符**：文章内容中天然的引号、换行、反斜杠，必须手动转义，很容易漏掉；
2. **深层嵌套时的注意力衰减**：当 JSON 层级深、键多，模型很容易丢失某个花括号或方括号，尤其在生成几百行之后。

更麻烦的是，即便只有一次解析失败，整个流程就卡住，必须靠重试或者昂贵的二次修复 prompt。而我们真正需要的往往不是严格的树状数据，而是“把一段长文本切分成几个有意义的部分”。这完全可以靠更宽松的格式实现。

## 做法：自定义标签格式

借鉴 XML/HTML 的思路，用成对的标签来包裹不同内容块。比如要输出一篇文章的摘要、正文和结论，可以约定如下格式：

```
<SUMMARY>
这里放摘要内容……
</SUMMARY>
<BODY>
这里放正文，可以有任意字符，包括换行和引号。
</BODY>
<CONCLUSION>
结论内容……
</CONCLUSION>
```

LLM 只需记住“用标签包起来”，而不需要关心引号转义，也不需要维护外层花括号的平衡。因为标签是人为定义的固定字符串，模型更不容易遗忘。即使某一对标签漏了闭合，通常也只会影响它所在的那一块，不会让整个输出报废。

**具体步骤：**

1. **定义标签协议**  
   根据输出结构，设计唯一且不易与正文内容混淆的标签名。建议使用全大写、加上领域前缀，例如 `[ARTICLE_TITLE]...[/ARTICLE_TITLE]` 或 `<OPENCLAW_INTENT>...</OPENCLAW_INTENT>`。标签名称应足够特异，降低内容冲突的概率。

2. **修改 Prompt 模板**  
   在 System 或 User Prompt 中明确给出标签格式示例，并强调“即使内部有换行或特殊符号，请不要转义，只需原样放在标签之间”。示例应完整展示一对标签，让模型有样可循。

3. **后处理提取函数**  
   使用正则或简单的字符串扫描来提取标签内的内容。注意采用非贪婪匹配 `(?s)<TAG>(.*?)</TAG>`，防止嵌套错误。如果标签可能自嵌套，需要用栈式解析或预先规定不允许嵌套。

4. **容错设计**  
   对于缺失闭合标签的情况，设置 fallback 规则，比如将剩余内容归入最后一个成功匹配的块内，或标记为未完成并触发轻量重试。

## 踩坑点

- **标签与正文冲突**  
  即使标签名再特殊，正文中仍然可能出现相同的字符串。解决方案是增加随机后缀，或在 prompt 中要求正文不能包含标签，但这在长文中不现实。更工程化的做法是，提取时先检查内容中是否存在未被转义的标签，如果存在，则提示 LLM 更换标签名重新输出（通常只需要一次重试）。

- **贪婪/非贪婪提取的陷阱**  
  如果用 `.*` 去匹配标签内容，容易在多对同名标签时一次吞掉中间所有内容。一定要用 `.*?` 并配合 `re.DOTALL`，确保每个标签对单独提取。当需要提取多个同层级切片时，可以用 `re.findall` 一次性收集。

- **LLM 有时会“创新”格式**  
  没有严格按照示例格式输出，比如把标签写成 `<summary>` 小写、忘记斜杠等。解决方式是做标签提取时忽略大小写，并进行归一化（`<summary>` 也当作有效），但更可靠的是在 prompt 中重复强调标签的精确性，必要时加入 few-shot 示例。
