在 Agent 和自动化流水线里用 LLM 生成结构化长文时，我们习惯了要求输出 JSON。但一旦上下文变长、字段嵌套变深，或者模型需要同时维护对话和格式，JSON 就会开始“坏”——缺括号、多逗号、幻觉 key，甚至中途截断。几个月前我们在 OpenClaw 的自动化报告生成管线里踩遍了这些坑，后来索性放弃了强迫模型写合法 JSON，改用自定义标签格式，稳定性和可恢复性强了很多。这篇文章把背景、做法、踩坑点和可复用建议整理出来，供有类似痛点的同学参考。

## 背景：JSON 不是为长文而生的

在 Agent 工作流中，很多任务都需要模型输出长结构化内容：会议纪要分层整理、自动化分析报告、多段摘要与行动项列表。最简单的方式是定义 JSON Schema，让模型严格输出。这种做法在短文本、简单结构下效果不错，但到了 2000+ token 的复杂结构时，问题频频：

- **生成中断**：输出到一半超过 max_tokens，JSON 结构直接断裂。
- **嵌套转义混乱**：长文本中包含引号、换行符时，模型经常忘记转义，或错误地多加反斜杠。
- **幻觉 key**：模型擅自添加不在 schema 里的字段，导致解析失败。
- **修复成本高**：用正则或状态机修 JSON 是场噩梦，尤其是结构中含代码块、JSON 内嵌字符串时，几乎不可能完美恢复。

更致命的是：在流式场景下，你无法等完整 JSON 返回后再校验，而部分解析的容错能力极差，一个语法错误就会阻塞整个下游管道。

## 做法：从 JSON 迁移到标签格式

我们最后采用的方案是用自定义的类 XML 标签来包裹不同的结构化部分，而不是用 JSON。例如，一篇文章分析输出可以设计成：

```text
<report>
<title>季度回顾</title>
<summary>
这里是多段摘要...
</summary>
<insights>
- 洞察1
- 洞察2
</insights>
<actions>
- 行动1
- 行动2
</actions>
</report>
```

并将这种格式直接写入 system prompt，告诉模型使用标签而非 JSON。解析时通过简单的标签匹配提取内容，不依赖严格的 JSON 语法。几个核心设计点：

**1. 标签名要有唯一性，避免与正文冲突。**  
我们用全大写或特定前缀（如 `rpt_title`），并在 prompt 里明确禁止在正文中出现相同标签字符串。为避免误用，可以增加一个“保留标记列表”。

**2. 流式解析采用状态机。**  
在 OpenClaw 的管道里，我们用一个轻量级 SAX 风格的解析器，逐 token 检查当前是否处于某个开标签内。一旦捕获到完整标签内容，立即触发下游节点，不需要等整个输出结束。这对 Agent 的实时性至关重要。

**3. 在 prompt 里允许“部分截断恢复”。**  
如果因 token 限制截断在某个标签中间，管道可以自动闭合该标签并丢弃不完整内容，或者回退到上一个完整标签。相比断裂的 JSON，这种恢复逻辑简单可靠。

**4. 嵌套用显式标签而非依赖缩进。**  
该扁平化就扁平化，采用序列化标签如 `<item>`...`</item>` 重复，能避免深度嵌套引发遗漏闭合。

## 踩坑点

- **标签注入问题**：用户输入里可能意外包含你的标签字符串。必须在上游对输入进行清洗，替换或转义特殊标签。如果不行，就改用少见的 Unicode 符号或自定义占位符，并在解析前做一次映射。
- **模型偶尔会“加戏”**：某些模型仍会试图在标签内部输出 Markdown 代码块，例如 `` ``` `` 包住整个标签结构，导致解析认为最外层多了一个异常块。我们的解决办法是在 prompt 里强调“不要用代码块包裹最终输出”，并在后处理里自动剥离最外层代码块标记。
- **标签嵌套深度控制**：模型有时会错误地将标签顺序搞错（比如先关后开）。需要用简单的栈匹配来校验，一旦检测到交叉闭合，就使用启发式算法（如丢弃到最近稳定点）修复，而不是整体丢弃输出。
- **长列表的 token 浪费**：标签格式比 JSON 略耗 token，因为多出了结束标签。对于千条级别的列表项，这是一个权衡。实践中我们会对超过一定长度的列表改用简化的无标签分隔格式（如行分隔），由下游解析。

## 可复用建议

整套方案可复用性很强，总结成几个工程原则：

1. **把结构约定从“语法正确”转移为“标记明确”**。标签格式不像 JSON 那样依赖复杂语法，它只要简单的文本匹配即可提取内容，容错空间大得多。
2. **尽量在 prompt 里给出正反例**。展示完整输出格式样例和错误格式的反例，能显著降低标签嵌套错误和注入问题的概率。
3. **解析器要容忍空白和换行**。标签名前后允许空白，支持跨行属性（如果用属性的话），但不要走 XML 标准的老路，越简单越好。
4. **应对截断的策略前置化**。在 prompt 里提醒模型“如果必须截断，请保证在一个完整标签内结束”，这比事后修复可靠。
5. **日志记录原始输出**。曾有一次因为标签解析异常，我们错过了关键的信息片段，后来在管道里加了完整的原始输出存储，方便回溯和调试。

## 总结

在 LLM 的长文结构化输出场景中，追求合法 JSON 往往是一种“工程师本能”，但它带来的脆弱性远大于收益。标签格式将问题从“生成正确语法”简化为“生成正确分隔”，大幅降低了修复成本，也让流式解析和截断恢复变得可行。在 OpenClaw 的实践中，替换为标签格式后，因格式错误导致的管道失败率下降了超过 70%，下游节点的延迟也更可控。

如果你的 Agent 也在与坏 JSON 斗争，不妨试一下：给模型一套清晰的标签规则，把解析的复杂度留给简单的文本处理，而不是寄望于模型每次都能写出完美语法。
