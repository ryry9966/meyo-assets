## 背景

在基于 OpenClaw、Agent 和 MCP 构建的自动化内容流水线中，一条常见的链路是：选题 → Agent 生成正文与配图 → 自动发布到目标平台。对运营和技术同学来说，仅把内容推送到平台远远不够——必须有本地归档，方便回溯、二次编辑、存档和未来再加工。

我们团队在跑 Agent 生产图文内容一段时间后，立即遇到了几个典型问题：

- 文章 Markdown 与配图散落在不同目录，甚至图片存成了无意义的哈希名
- Meta 信息（生成时间、prompt、模型版本、标签等）放在代码注释或零散日志里，无法程序化读取
- 想要用同一批内容生成静态网站或作品集时，需要重新整理，浪费大量人力

为此我们抽象出了一套通用、非侵入、可被 MCP 工具直接调用的本地归档方案，核心是 **统一目录 + index.md + images/ + assets.json**。

## 问题拆解

自动化发帖流水线中，归档要解决三个核心诉求：

1. **文件组织**：单篇文章对应的所有资源放在一个独立目录，命名可读、可排序。
2. **元数据固化**：标题、标签、生成时间、prompt、图片 alt、使用状态等，需要结构化存储，而不是注释或文件名。
3. **自动化对接**：能被 Agent 或流水线脚本无缝调用，不依赖人工操作。

另外，归档必须在发布之前完成（或同步完成），确保发布出去的内容和本地存档完全一致，避免“线上有、本地丢”的情况。

## 做法与步骤

### 1. 定义目录结构

我们选择按日期 + slug 组织目录，同时保持兼容不同操作系统：

```
posts/
└── 2025-03-21-auto-posting-archive/
    ├── index.md
    ├── images/
    │   ├── cover.png
    │   └── diagram.png
    └── assets.json
```

`index.md` 存放正文（可直接渲染），`images/` 存放所有配图，`assets.json` 是结构化元数据。

### 2. assets.json 设计

为兼容未来扩展，我们定义了一个最简 schema，同时保留扩展字段：

```json
{
  "slug": "auto-posting-archive",
  "date": "2025-03-21",
  "title": "自动发帖流水线的本地归档方案",
  "tags": ["automation", "mcp", "archive"],
  "model": "claude-3.5-sonnet",
  "generated_at": "2025-03-21T10:30:00Z",
  "published": true,
  "images": [
    {
      "file": "images/cover.png",
      "alt": "归档流程图",
      "prompt": "A minimal tech illustration of an automated posting pipeline with archive node..."
    }
  ],
  "extras": {}
}
```

这样，无论是前端构建脚本还是未来的分析工具，都能直接读 `assets.json`，不用解析 Markdown 元头部。

### 3. 流水线中的归档动作

在 Agent 生成完文章和图片后，通过一个独立的 MCP 工具或 Shell 脚本执行以下归档步骤：

```bash
#!/bin/bash
SLUG="$1"
TITLE="$2"
DATE="$3"
POST_DIR="posts/${DATE}-${SLUG}"

mkdir -p "$POST_DIR/images"

# 1. 写入正文
cp generated_content.md "$POST_DIR/index.md"

# 2. 复制图片并重命名
cp -R generated_images/* "$POST_DIR/images/"

# 3. 生成 assets.json（可从环境变量或 Agent 输出解析）
cat > "$POST_DIR/assets.json" <<EOF
{
  "slug": "$SLUG",
  "date": "$DATE",
  "title": "$TITLE",
  ...
}
EOF
```

在基于 MCP 的工作流里，可以封装一个 `archive-post` 工具，接收文章对象作为参数，内部完成上述操作。这样可以由 Agent 在确认内容后直接调用，无需人工键入命令。

### 4. 集成到发帖管线

不管你的发布工具是 Selenium、Playwright 还是 API 调用，归档步骤最好作为 **发布前必过步骤**。我们通常的流程是：

```
Agent 输出 → 人工/自动审核 → MCP archive-post → 发布平台
```

一旦归档失败，发布就中止，避免内容丢失。归档工具本身的返回值也会被 Agent 检测：成功返回目录路径，失败返回错误原因。

## 踩坑点

- **图片路径引用**：`index.md` 中的图片引用需统一为相对路径 `images/xxx.png`，否则迁移目录后预览会找不到图片。可以在归档脚本里做一次正则替换。
- **slug 与中文文件名**：Windows 和某些文件系统对中文目录名不友好，建议 slug 只保留英文小写 + 连字符。中文标题存在 `assets.json` 即可。
- **图片命名冲突**：如果多篇文章生成时图片默认都是 `image_1.png`，归档到不同目录没问题，但如果未来想合并图片索引，需要保证唯一性。我们采用 `{slug}-cover.png` 的命名规则，在归档时重命名。
- **assets.json 向后兼容**：随着字段增加，老归档的 assets.json 可能缺少新字段。所有消费者代码必须做缺省值处理，不能直接假定字段存在。
- **Git 管理**：大体积图片不适合频繁提交，建议在 `posts/` 下加 `.gitignore` 忽略图片，或使用 Git LFS。版本控制的主体是 Markdown 和 assets.json。
- **权限问题**：如果 Agent 运行在容器中，需确保写入目录有足够权限，且路径不要写成绝对 home 目录，避免跨环境失效。

## 可复用建议

1. **封装成 MCP 工具**：提供 `archivePost` 和 `queryPosts` 两个工具，Agent 可以直接归档和检索，门槛最低。
2. **提供 CLI 接口**：方便非 MCP 流水线直接调用，如 `npx archive-post --from ./output`。
3. **定义 schema 与校验**：使用 JSON Schema 校验 `assets.json`，在归档阶段就发现字段缺失。
4. **增量归档**：支持传入已有的 `posts/` 根目录，自动找到未被占用的 slug 变体，避免重名。
5. **预览生成**：作为可选步骤，在归档后自动生成一个静态 HTML 预览，方便直接浏览器打开检查。

如果团队已经有模版化的 Agent 流程，**强烈建议把归档做成一个独立节点**，而不是塞在发布逻辑里。独立才能被复用和单独测试。

## 总结

自动发帖流水线不能只管发不管存。一个规范化的本地归档结构（目录 + index.md + images/ + assets.json）几乎零成本，但能解决大量后续问题：回溯某天的内容、查看生成 prompt、批量生成作品集等。结合 MCP 工具化后，Agent 可以将归档当成标准动作，就像 commit 代码一样自然。

工程上不追求大而全，先跑通最小闭环：目录建对、文章存好、图片不丢、meta 可读。后续再按需加上 search、sync 等功能。这个方案我们已经用了四个月，从没有因为归档问题丢过一篇 Agent 生成的内容。
