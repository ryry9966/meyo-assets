## 背景

作为独立开发者或技术内容创作者，我们大多会在 Twitter、Discord、Telegram、Reddit、GitHub Discussions 甚至知乎等多个社区发布更新、技术短文或项目公告。自动化同步可以省下大量重复劳动，但简单粗暴地“一次撰写、全平台广播”很快会演变成一场灾难：同样的话在多个频道短时间内反复出现，读者感到被冒犯，社区氛围被破坏，帐号甚至会被平台降权或标记为 spambot。

在 OpenClaw 这类 Agent 框架中，我们很容易通过 MCP 服务器集成各个平台的 API，实现一条命令就推到所有渠道。但如果不想变成一个惹人厌的“刷屏机器人”，就必须在设计阶段就划出边界：**自动化发布 ≠ 无差别同步**，它应该是一套有节奏、有取舍、尊重社区语境的编排系统。

## 问题拆解：刷屏的本质

“刷屏”不完全是频率问题，本质是**信息冗余 + 语境错配**。  
- 你把自己的 Changelog 同时推送到 Discord 闲聊群、Twitter 时间线和 Reddit 子版块，但每个平台的读者对内容的期待完全不同。  
- 短时间内在多个平台发布完全相同的文案，会让同时关注你多个账号的粉丝被迫重复消费同一条信息。  
- 某些平台（如 Discord）支持更丰富的嵌入内容，而 Twitter 有严格的字数限制，直接用一份稿子生搬硬套会显得不专业。

因此，边界在于：**能否让同一条原始信息，按各平台的交际节奏分时、差异化地抵达目标受众，同时避免在短期内密集推送相同内容。**

## 做法 / 步骤

在工程上，我用 OpenClaw + 两个 MCP 服务器（Twitter 与 Discord）搭建了一个小型的“发布编排器”，核心思路是把“发布”变成一个有状态的流水线，而不是一次性动作。

### 1. 内容源与平台能力建模
把所有待发布内容抽象成一个统一结构：
```yaml
source_content:
  id: "release-v2.1.0"
  type: "announcement"   # announcement | blog | quick_tip | dev_log
  body: "完整的更新说明正文（Markdown）"
  summary: "一句话摘要"
  links: [url1, url2]
```
同时为每个平台定义能力文档：字符上限、是否支持 embed、支持的话题标签体系、活跃时段等。这一步的产出是一个“发布策略配置”，例如：`announcement` 类型的内容适合发到 Discord #announcements 频道和 Twitter，但不适合发到 Reddit。

### 2. 去重与指纹
用内容 ID + 内容体 MD5 + summary 向量相似度生成一组指纹。发布前，在 Redis 里检查过去 48 小时内是否有相同指纹的发布记录。如果检测到重复，跳过或合并发布，而不是强行再发一条。

### 3. 分时调度与窗口控制
将发布队列化，Agent 不直接执行推送，而是把任务写入调度器：
```
post_task:
  platform: twitter
  content_id: "release-v2.1.0"
  scheduled_after: "2025-04-10T10:00:00Z"
```
调度器会保证**同一条 content_id 在不同平台之间至少有 30 分钟的间隔**，且每个平台每天发布总数不超过预设阈值（例如 Twitter ≤ 5 条，Discord 公告频道 ≤ 2 条）。窗口控制还能结合时区优化：北美用户活跃时段优先发 Twitter，亚洲时段优先发中文社区。

### 4. 差异生成而非简单转发
用 LLM 根据平台风格对摘要进行重写，同时保留原文链接。例如一次更新公告：
- **Twitter**：提取关键功能点，压缩到 260 字符以内，加上 #buildinpublic 标签。
- **Discord**：生成嵌入卡片，正文使用项目符号列出变化，附注改动动机。
- **Telegram**：使用简短的要点 + 链接，更偏向即时推送风格。

这个过程通过 Agent 的一次对话完成：将原始 body 输入给 LLM，传入不同平台的角色提示词，产出三个版本，并填入调度任务。

### 5. 反馈闭环与熔断
收集每个平台的互动数据（点赞、转发、评论数），如果某条内容在某个平台 2 小时内几乎没有正向互动，会在下次同类内容发布时自动降低该平台的优先级，甚至提醒人工介入。此外，任何一次因速率限制导致的 API 报错都会被记录并触发熔断，暂停该平台发布 1 小时。

## 踩坑点

- **平台 API 的隐性限制**：Twitter API v2 的免费 tier 发推频率极其有限，Discord webhook 在短时间内连续发消息可能被限流。必须在调度器中真正尊重这些硬限制，不能仅依赖返回的 HTTP 429 做重试。
- **格式转换的边界情况**：Discord embed 有严格的字段长度限制，如果 summary 超过 256 字符就会被截断。需要在生成阶段就做校验，并留足截断后的语义完整性。
- **上下文缺失**：自动化发布有时会误发没有足够上下文的片段，例如在 Discord 里只发了一个链接而没有说明，看起来像钓鱼。需要确保每个平台的发布内容都能自洽，即使脱离原上下文也能被理解。
- **紧急撤回困难**：全自动一旦发出错误信息，撤回非常麻烦，尤其是 Twitter 没有编辑权限的免费账号。重要公告务必保留人工审核节点。

## 可复用建议

- **将编排逻辑抽象成内部 MCP 服务器**：对 OpenClaw 来说，对外暴露 `orchestrate_publish` 一个工具即可，内部完成指纹检查、调度排队、差异生成。平台团队可以复用这个 MCP 工具，无需关心底层细节。
- **维护统一的发布日志表**：记录每一条内容在每个平台的状态（pending/scheduled/sent/failed），方便回溯和排查。
- **非对称同步策略**：不要追求所有平台都要有相同内容，允许某些内容只在特定社区出现。比如开发日志只更新在 GitHub Discussions，技术短文只发 Twitter 和 Telegram。
- **渐进式自动化**：先半自动运行（Agent 生成草稿，人工一键确认），跑通一个月确认无事故后再逐步放开全自动。

## 总结

多社区同步的边界，不是技术能不能做到同时推送，而是**发布者愿不愿意放弃“一次写完，到处张贴”的便利，换取读者在每个社区中得到的干净、恰当的阅读体验**。借助 OpenClaw 这样的 Agent 平台，我们完全有能力构建一套编排层，让自动化发布做到有节奏、有差异、有节制，这样既节省了精力，也不会把社区变成无人想看的公告板。
