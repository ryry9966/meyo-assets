## 背景

如果你用 OpenClaw、Agent 或 MCP 搭建了一条内容自动发布流水线——可能是从知识库生成稿件，也可能是经过 LLM 润色后一键推送到多个平台——很快就会遇到一个尴尬问题：**发完就忘，想回溯时只有散落的文件和无尽的日志。**

这背后是自动化发布常见的三大痛点：

1. **文章与图片散落各处**：一篇推文可能包含多张本地截图、AI 生成的封面、引用图，流水线运行多次后，文件系统变成灾难现场。
2. **发布状态不可追溯**：你不知道某篇文章到底发出去没有，发到了哪些平台，失败了有没有重试记录。
3. **调试与迭代成本高**：当你需要复盘“上周那篇爆款为什么转化好”时，只能凭记忆和平台后台一条条翻，徒增心智负担。

因此在把内容“推出去”之前，**先让流水线把成果“留下来”**——做一套简单、可靠、工程化的本地归档机制，是自动化内容系统的必备模块。本文分享我在 OpenClaw 生态里落地这套机制的具体做法，不依赖特定 SaaS，只用目录结构和 JSON 元文件搞定。

## 问题聚焦

自动化发布链路通常是：**内容生成 → 资源处理 → 发布执行 → 通知/记录**。本地归档的介入点最好在“发布执行”前后，具体要解决：

- 如何将一篇文章及其关联图片**捆绑管理**？
- 如何记录必要的上下文，如标题、摘要、生成时间、发布平台、状态？
- 如何避免图片引用失效，保证离线查看时依然可读？

我们选择的载体是文件系统，不使用数据库或对象存储，因为对于个人或小团队自动化而言，**本地文件是成本最低、可移植性最强的方案**。

## 做法与结构

### 1. 约定目录结构

每一篇内容视为一个独立单元，统一存放在 `posts/` 下，以 `slug` 作为唯一标识：  

```
posts/
├── hello-openclaw-agent/
│   ├── index.md           # 文章正文（Markdown）
│   ├── images/            # 本篇文章关联的所有图片
│   │   ├── cover.png
│   │   └── diagram.png
│   └── assets.json        # 元数据与发布记录
└── another-post/
    └── ...
```

`index.md` 内部的图片引用使用相对路径，保证离线可读：`![cover](images/cover.png)`。

### 2. assets.json 的结构设计

这是整个归档的核心。我定义了一份最小可行的 JSON Schema：

```json
{
  "slug": "hello-openclaw-agent",
  "title": "Hello OpenClaw Agent",
  "summary": "A quick start guide...",
  "tags": ["agent", "mcp"],
  "createdAt": "2025-04-01T10:00:00Z",
  "updatedAt": "2025-04-01T10:05:00Z",
  "source": "local-draft",
  "publish": {
    "platforms": [
      {
        "name": "wechat",
        "status": "published",
        "publishedAt": "2025-04-01T12:00:00Z",
        "url": "https://mp.weixin.qq.com/s/xxxx"
      },
      {
        "name": "zhihu",
        "status": "failed",
        "reason": "rate limit",
        "retriedAt": "2025-04-01T12:05:00Z"
      }
    ]
  }
}
```

要点：
- `source`：标记内容来源（`local-draft`、`ai-generated`、`imported`），方便区分管道类型。
- `publish.platforms`：数组形式记录多平台状态，每个平台独立记录 `status`、`url`、失败原因，支持再投递。
- 时间统一使用 ISO 8601 格式，便于排序和比对。

**敏感信息不要写入**，如 Token、API Key，这些应在运行时从环境变量注入。

### 3. 流水线中的集成方式

在 OpenClaw 的 Agent 流程或 MCP 工具链中，可以封装一个“归档器”函数：

1. **接收内容**：从上游拿到 Markdown 字符串、标题、slug、图片路径列表。
2. **创建目录**：`posts/{slug}/images/`
3. **写入正文**：将 Markdown 内容里的图片路径替换为相对路径（`./images/xxx`）后写入 `index.md`。
4. **复制图片**：将上游指定的图片拷贝/移动到 `images/` 下。
5. **生成/更新 assets.json**：先读取旧文件（如果有），合并新状态，再回写。
6. **发布执行后更新状态**：发布插件完成操作后，再调用归档器更新 `publish.platforms` 对应项。

这样归档逻辑与发布逻辑解耦，任何平台插件都可通过更新 `assets.json` 来留下痕迹。

## 踩坑与对策

### 图片引用路径频繁出错

问题：不少 AI 生成的内容会使用绝对路径或在线 URL 作为图片引用，归档时如果直接写入，离线就无法查看。

对策：在归档阶段强行**重写图片链接**为相对路径，并保证实际文件已拷贝到 `images/` 下。可配合正则匹配常见的图片 URL 模式处理，同时保留一份原始引用供 assets.json 记录，方便线上发布时还原。

### assets.json 并发写入不安全

问题：如果多个工作流或异步任务同时更新同一篇文档的发布状态，可能出现数据覆盖丢失。

对策：使用**单进程写入 + 乐观锁**。在 Agent 的 orchestrator 中设计互斥队列，确保同一 slug 的写操作串行化；或写入前重新读取最新文件做合并再覆盖，防止竞态。

### 大量文章后目录臃肿

问题：累计几千篇后，同级目录 `posts/` 下文件系统查找变慢。

对策：按年月分层，如 `posts/2025/04/hello-openclaw/...`，在生成 slug 时就注入时间信息作为前缀。脚本检索时利用文件系统自然分区，性能无忧。

## 可复用建议

- **封装成 MCP server 或插件**：将上述归档模块抽象为 `local-archive` 服务，提供 `create_post` 和 `update_publish_status` 两个工具，所有发布流水线共享。
- **结合 git 做版本回溯**：`posts/` 目录初始化为 git 仓库，每次归档自动 commit，不费力获得内容变更历史。
- **加入校验环节**：归档后自动运行一个 script 检查 `index.md` 中所有引用图片是否真实存在于 `images/` 下，早期发现异常。
- **前端展示辅助管理**：用简单的静态站点生成器（如 VitePress）读取 `posts/` 和 `assets.json`，你可以得到一个本地的内容看板，快速筛选失败重投或查看历史。

## 总结

自动发帖流水线的可靠性，不仅体现在“能发出去”，更在于“发出去的东西能随时找回来、能说清楚”。用目录结 构 + assets.json 做本地归档，看似朴素，却是将混沌变为工程化的关键一步。没有引入额外基础设施，直接利用文件系统和 JSON，任何支持 Node.js/Python 的 Agent 环境都能轻松落地。当你复盘内容策略、二次分发旧文、调试发布失败时，这套机制会让你庆幸当初多花了几个小时。

希望这个方案能为你的 OpenClaw 自动产线补上缺失的那一环。毕竟，在自动化领域，**可见性和可恢复性，往往比速度更重要。**
