## 背景：为什么要做多社区同步

内容创作者经常需要将同一篇文章分发到掘金、SegmentFault、知乎、公众号、CSDN、少数派等多个技术社区。手动逐个平台登录、粘贴、调整格式、添加标签、发布，极度消耗精力。于是很自然地想到用 OpenClaw Agent 搭配 MCP 插件，调用各平台的开放或逆向接口，实现“一次撰写，一键发布”。

但第一个版本上线后，立刻踩到了明显的红线：当你在短时间内将同一篇内容推送到五六个平台，每个平台的关注者都会在信息流里同时看到你的帖子——这就叫刷屏。轻微的情况下会被读者嫌弃，严重时可能触发平台风控，导致账号被限流甚至封禁。

这篇帖子记录我在 OpenClaw 上构建一个“不扰民”的自动化发布调度器的完整过程，包括流程设计、MCP 插件的组合、延迟策略的工程实现，以及在生产中遇到的一些真实限制。

## 问题拆解：刷屏是如何发生的

刷屏并不是简单的“发太多”，而是发布行为在**时间维度**和**平台维度**上同时表现为瞬时高密度。具体来说有三个典型场景：

1. **同平台连续发布**：对同一个平台连续 POST 多篇文章，即便间隔只有 5 分钟，在关注列表里依旧会形成“霸屏”。
2. **跨平台同时间戳**：文章在多个平台几乎同一时刻发出，如果你的读者同时关注了你的知乎和掘金，会看到一条信息的多次重复出现。
3. **机器人特征暴露**：所有请求来自同一 IP、同一 User-Agent、固定间隔触发，很容易被反爬/风控系统判定为自动化操作。

因此，避免刷屏的本质是：**让自动化发布的行为模式尽量接近一个合理人类的正常操作节奏，并且在读者感知层面形成错开的效果**。

## 工程做法：基于 OpenClaw 的调度器设计

整个调度器运行在 OpenClaw Agent 之上，利用现有的 MCP 插件体系对接平台。我的实现并不复杂，核心步骤如下。

### 1. 发布任务队列与延时引擎

将每次“一键发布”拆分成一个任务队列，每个任务包含目标平台、文章元数据、正文等内容。调度器引入两个关键延迟参数：

- `base_gap`：平台之间的最小发布间隔（默认 30 分钟）
- `random_offset`：在 0 到 15 分钟内随机增加额外偏移

这样一来，同一篇文章在掘金发布后，至少要等 30–45 分钟才会发送到 SegmentFault，微信公众号可能安排到下一个小时。不同平台的读者不会同时在信息流里看到相同标题。

如果当天需要发布多篇文章，还会增加一个 `cooldown_per_platform` 字段，规定同一个平台在 6 小时内最多只发一篇，避免单日霸屏。

### 2. MCP 插件统一接口与分发逻辑

我在 OpenClaw 里定义了一个名为 `publisher-mcp` 的 MCP 服务，内部封装了各个社区的发布能力（部分通过官方 API、部分通过 Playwright 操控浏览器）。Agent 调用时只需要传递目标平台枚举值和标准化的文章对象，无需关心底层实现。

分发逻辑上增加了一个简单的“风控感知层”：在每次调用前查询该平台近期的发布记录，如果短时间内失败次数过多（例如连续 3 次返回 403 或验证码），则自动将该平台置为冷却状态，并记录到本地 SQLite 里，等待人工介入。

### 3. 发布状态机与幂等保证

为了防止重复发布，引入发布状态机：

- `pending` → `scheduled` → `running` → `published`
- 任何异常跌入 `failed`，且支持手动重试
- 每次发布前使用 `(article_id + platform)` 做唯一性校验

这样做的好处是，即使 Agent 因为某种原因重启，也不会把同一篇文章重复推到同一平台。

### 4. 可视化预览与人工闸门（可选）

并不是所有场景都需要全自动。对于重要文章，我在调度器里增加了一个 `require_review` 标志。开启后，任务只会进入 `scheduled` 状态，需通过一个简单的 TUI 面板或 OpenClaw CLI 输入确认，才进入实际发布。这个设计特别适合处理公众号这种不可逆发布的平台。

## 实际踩坑点

- **时间窗口的陷阱**：最初设定凌晨 2 点自动发布，本以为对读者影响最小，但部分平台（如知乎）在流量低谷期的内容审核反而更严，延迟发放甚至误判为垃圾内容。后来改为工作日上午 10:00–11:00 的窗口，效果更稳定。
- **验证码无法完全绕过**：即使通过 Cookie 和 session 维持登录状态，长时间不操作后依旧会弹出滑块或图形验证码。我的折中方案是：对强验证平台（如 CSDN）只做“草稿箱填充 + 人工一键确认”的半自动流程，而不是强行全自动。
- **内容格式适配不能偷懒**：Markdown 直接映射到富文本编辑器往往会出现格式错乱。必须为每个平台维护一个渲染模板规则表，否则发布出去后图片错位、代码块丢失高亮，读者体验极差，这比刷屏更容易流失关注。
- **API 限流远比想象中小**：某些平台的“开放 API”实际 QPS 极低（如每日最多 50 次写入），当你有几十篇存量文章需要初次同步时，稍不注意就会触发 429。解决方式是分批迁移，并用指数退避重试。

## 可复用的建议

1. **先做观测，再定节奏**：花一周时间手动发布，记录下各平台审核时间、推荐流的刷新周期、粉丝活跃时段，用这些数据反向设定调度参数。
2. **将调度器内嵌到 OpenClaw 的 Decision Loop 中**：不要写独立的 cron 脚本。利用 Agent 上下文，可以在发布前检查当日已发数量、是否处于节假日、甚至读取近期重大事件（避免在热点期发无关内容）。
3. **MCP 接口设计尽量返璞归真**：只暴露 `publish_post` 和 `get_status` 两个主要能力，平台差异隐藏在服务端。否则 Agent 可能会尝试“创造性”地调用底层接口，引发不可预期的行为。
4. **保留人工干预的入口**：在调度器的配置里永远留一个 `manual_override`，允许随时暂停所有自动化任务。一键暂停比事后道歉成本低得多。

## 总结

自动化发布的目标不是替代人，而是把重复的机械操作转移到机器上，让人专注于创作和审核。在这个前提下，避免刷屏本质上是一个工程伦理问题——你的 Agent 必须学会“节制”，而不是尽可能快地完成所有任务。

利用 OpenClaw 的 MCP 插件体系、简单的队列延迟、平台风控感知和人工闸门，完全可以在不影响读者体验的前提下，优雅地完成多社区同步。希望这个实践对你构建自己的内容发布 Agent 有所帮助，也欢迎在社区分享你的调度策略。
