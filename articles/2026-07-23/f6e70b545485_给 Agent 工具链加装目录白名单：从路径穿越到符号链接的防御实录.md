## 背景

当 Agent 获得读写本地文件的能力后，安全问题会立刻浮出水面。无论是通过 OpenClaw 插件、MCP 服务器，还是自定义 Function Calling 工具，只要 Agent 能指定路径并触发 `open()`、`shutil` 等操作，它就具备了越权访问的潜力。典型的攻击面包括：

- 读取 `/etc/passwd`、`~/.ssh/id_rsa` 等敏感文件
- 写入系统关键配置或覆盖用户数据
- 跟随符号链接逃逸到白名单之外的目录

纯提示词的约束不可靠，工程上最直接的办法就是**目录白名单**：只允许 Agent 操作预先定义好的几个目录，其余路径一律拒绝。这篇文章会给出一个轻量但足够防绕的实现方案，并记录踩过的坑。

## 问题画像

假设你为 OpenClaw 写了一个文件助手工具，支持 `read_file` 和 `write_file`，调用方式如下：

```json
{
  "tool": "read_file",
  "path": "~/workspace/report.txt"
}
```

初版为了快速验证，直接把 `path` 拼进 `open()`。很快你会发现，只要传入 `../../../../etc/passwd`，工作目录的便宜就被占尽。即便你要求路径必须以 `~/workspace` 开头，攻击者也可以用符号链接或其他绕过手法让字符串前缀匹配失效。

我们需要的是一个**路径归属检查**，它必须做到：

- 解析所有 `..`、`.`、`~`、多余斜杠
- 跟随符号链接，并依据解析后的真实路径判断
- 避免字符串前缀匹配导致的绕过（比如 `/etc/passwd` 被 `/etc/passwd_backup` 匹配）

## 实现步骤

### 1. 定义白名单

配置中只保留绝对路径，并使用 `resolve()` 消除符号链接，得到规范化的根目录列表：

```python
from pathlib import Path

ALLOWED_ROOTS = [
    Path("/home/user/agent-workspace").resolve(),
    Path("/mnt/data/reports").resolve(),
]
```

### 2. 安全解析用户路径

接收用户传入的路径字符串后，必须立即标准化：

```python
def safe_resolve(raw: str) -> Path:
    # 禁止空路径和相对路径
    if not raw or not Path(raw).is_absolute():
        raise ValueError("Only absolute paths are allowed")
    # 展开 ~ 并解析 symlink/.././多余斜杠
    return Path(raw).expanduser().resolve(strict=False)
```

这里跟随符号链接是**故意为之**：如果白名单内存在指向外部的符号链接，最终路径会落在白名单外，随后被拒绝，这正是我们想要的效果。而外部符号链接指向白名单内的情况会被允许，因为最终落地符合白名单。

### 3. 前缀判断（组件级别）

用路径组件而非字符串前缀进行比较，避免 `/etc/passw` 误伤 `/etc/passwd_backup`：

```python
def is_allowed(requested_path: str) -> bool:
    try:
        full_path = safe_resolve(requested_path)
    except (ValueError, OSError):
        return False

    full_parts = full_path.parts
    for root in ALLOWED_ROOTS:
        root_parts = root.parts
        if full_parts[:len(root_parts)] == root_parts:
            return True
    return False
```

### 4. 集成与结果处理

在工具入口调用 `is_allowed()`，不通过则返回结构化错误或直接抛异常：

```python
def read_file(path: str) -> dict:
    if not is_allowed(path):
        return {"error": f"Access denied: {path}"}
    # 后续安全的 open()...
```

每一次拒绝都需要记录原始路径、解析后路径和时间戳，既方便排错，也能发现潜在的恶意试探。

## 踩坑记录

**坑一：大小写文件系统**

macOS 默认 APFS 不区分大小写，Windows 同样如此。`resolve()` 不会做大小写折叠，可能导致同一实体被当作不同路径。如果环境中大小写敏感不可控，建议在对比前通过 `os.path.normcase` 或调用平台 API 获取真实大小写路径。对于大多数 Linux 部署场景，可暂时搁置。

**坑二：符号链接与 TOCTOU**

检查通过后、打开文件前，目标可能被替换为指向白名单外的符号链接。对于非高安全的内部自动化，概率极低。若实在不放心，可以在打开前附加一次 `os.lstat()` 检查，但成本较高，按需取舍。

**坑三：当前工作目录泄露**

如果允许空字符串或 `"."`，解析后是进程当前工作目录，它往往不在白名单内。必须强制要求绝对路径，并禁止 `~` 之外的特殊短名。

## 可复用建议

- 将白名单与检查逻辑抽成独立模块/中间件，MCP Server、插件公用同一份实现
- 白名单列表外部化到配置文件，方便运维增删
- 搭配文件大小、类型限制（如禁止执行文件写入），形成纵深防护
- 编写单元测试覆盖常见穿越 payload：`../../`, `..\..\`, 符号链接, `file://` 协议等
- 在资源极其敏感的场景，可配合操作系统用户权限，让 Agent 进程以受限用户运行，双重制约

## 总结

目录白名单是成本极低、效果明显的 Agent 安全护栏。核心在于：**规范路径解析 + 组件级前缀判断**，同时正视符号链接和文件系统差异带来的边界情况。一旦这套检查融入工具层，Agent 就只能在限定目录内活动，数据泄露和系统破坏的风险会大幅收窄。

如果你的 Agent 已具备文件访问能力，但尚未做任何路径限制，不妨花半小时把这层白名单加上——它会成为你最不后悔的一次代码提交。
