## 背景

作为工具项目的维护者，更新日志、使用指南或讨论帖常常需要同时出现在 GitHub Discussions、Discord 频道、飞书群、Twitter 甚至 Reddit。手工逐个复制粘贴不仅低效，还容易因格式混乱导致社区吐槽。自动化发布看似是“懒人”的正义，但一旦越界，刷屏、被禁言、触发反 spam 机制就是家常便饭。

我用 OpenClaw 搭配 MCP 插件搭建了一个跨社区发布代理，目标是从“脚本轰炸”变成“有分寸的同步”。下面记录其中的设计、踩坑与可复用的边界控制手法。

## 问题拆解

多社区同步的自动化，难点不在于调用 API，而在于：

- 不同平台对频率、格式、机器人身份的容忍度差异巨大；
- 重复内容的机械推送会迅速耗尽社区的耐心；
- 自动化缺少对社区隐形规则的感知，容易显得冒犯。

因此，我们要的不是全自动、零人工的“刷屏机”，而是一个**尊重节奏、可中断、可解释的发布代理**。

## 做法与步骤

### 1. 以消息为单元建立全局唯一标识

每条待发布内容，先计算一个逻辑指纹。可以用“内容文本 + 目标平台 + 版本号”拼接后取 SHA256，存入本地 SQLite 表。后续所有决策都基于该指纹，避免同一条内容在同一个平台被重复推送。

```python
fingerprint = hashlib.sha256(f"{text[:200]}|{platform}|{version}".encode()).hexdigest()
```

### 2. 为每个平台编写规则文件

用 YAML 定义各平台的行为约束，而不是硬编码在逻辑里。示例片段：

```yaml
discord:
  min_interval_seconds: 120
  max_daily_posts: 8
  max_length: 2000
  supports_markdown: true
  needs_approval: false

reddit:
  min_interval_seconds: 600
  max_daily_posts: 3
  max_title_length: 300
  supports_markdown: false
  needs_approval: true   # 高风险平台必须人工确认
```

### 3. 构建发布代理的工作流

基于 OpenClaw Agent，利用 MCP 社区提供的 Discord、GitHub、Twitter 等 MCP 服务器，实现如下流程：

- **接收任务**：输入 markdown 文本、目标平台列表、优先级。
- **去重与相似检测**：先查库判断是否已存在相同指纹；若无，则与对应平台最近 20 条记录做文本相似度（余弦相似度 > 0.9 视为重复），避免格式化微调导致绕过。
- **格式适配**：根据规则将 markdown 转为平台原生格式。Discord 保持原样，但超长时自动分段；Twitter 截取摘要并附链接；Reddit 将 markdown 转成纯文本。
- **速率控制**：使用基于令牌桶的全局限速器，确保任意 1 分钟内总请求不超过阈值，并错开平台间的发布间隔。Agent 异步排队，不阻塞。
- **人工闸门**：对于 `needs_approval: true` 的平台，Agent 暂停并发送确认卡片到我所在的飞书群，只有我回复“go”后才继续。
- **发布与日志**：调用对应 MCP 工具（如 `discord_send_message`、`github_create_discussion`），记录状态、响应时间和可能错误。若平台返回 429 或异常，自动退避并将该平台标记为暂停。

### 4. 审计与回退

所有操作落日志，并挂在每日自动生成的摘要里推送到私有不公开的日志频道。当发现某个平台的帖子被投诉或折叠，我可以一键“撤销同步”（删除帖子），并让 Agent 在该平台静默 24 小时。

## 踩坑点

- **API 文档与现实不符**：Reddit 的 API 对同一用户短时间内发帖会进入 shadowban，而官方文档并未明确这个阈值。最终通过实测得出，两帖之间至少间隔 10 分钟且日发帖不超过 3 个比较安全。
- **内容相似度误判**：我最初只用编辑距离，但遇到“v1.2.0 发布”和“v1.2.1 发布”只差一个数字就被判成重复。后来改成先提取关键词，再对比语义向量，成本高但风险小。
- **Discord 分段陷阱**：长消息切分时，必须保证代码块和 Markdown 语法不跨段破裂，否则渲染报错，排查了很久。
- **社区文化差异**：有个子论坛禁止“营销帖”，即使带上说明文字也被删。最终在规则里加了一个 `pre_text`: "来自项目维护者的技术同步，无推广意图。"
- **节奏不易察觉**：即便满足最小间隔，如果每天都在同一时刻发帖，也会被误认为定时刷屏。我在 Agent 中添加了 ±15 分钟的随机抖动。

## 可复用建议

1. **规则外置**：把所有平台偏好放入独立配置文件，改规则时无需动代码。
2. **静默模式**：实现一个全局“暂停-恢复”开关，当收到平台警告时可以一键冻结所有自动同步。
3. **利用 MCP 的动态工具发现**：新增平台只需提供对应的 MCP Server，核心代理逻辑不需要大变。
4. **保留人工出口**：不追求零人工，重要的、敏感的首次发布一定走确认流。
5. **建立简易仪表盘**：用 htmx 或轻量前端展示每个平台的状态、最近发布内容、限速余量，方便快速排查。

## 总结

多社区同步的自动化不是为了炫耀技术，而是让维护者能专注于内容本身。但技术必须尊重社区的社交边界。通过唯一指纹、速率控制、平台规则适配和人工确认点，我把一个可能招人烦的“刷屏机器人”改造成了安静且可控的同步代理。工程上的信条是：**自动化不是替代判断，而是放大克制。**
