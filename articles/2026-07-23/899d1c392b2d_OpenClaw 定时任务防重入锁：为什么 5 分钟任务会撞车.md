## 一、背景

在 OpenClaw 平台上，定时任务是串联 Agent、MCP 工具和自动化流程的核心能力。一个典型的场景是：每 5 分钟调用大模型生成舆情摘要，或者在固定间隔内拉取 API 数据写入存储。

初期调试时，一切正常——任务总能在 2–3 分钟内完成，5 分钟的间隔显得绰绰有余。但当网络抖动、数据量变大或下游服务响应变慢时，任务的真实执行时间悄悄从 2 分钟爬到 4 分半，甚至偶尔超过 5 分钟。

此时，前一实例还在运行，新的调度已经触发。两个（甚至更多）实例同时操作同一份文件、同一张数据库表或同一组共享资源，就像两辆车在同一时间挤进同一个车位——这就是“撞车”。

这个问题在工程上被称为“定时任务重入”，而解决它的典型手段是**防重入锁**。

## 二、问题复现：一个 5 分钟间隔的 Agent 工作流

假设我们在 OpenClaw 中配置了一个 Agent：

- 每 5 分钟调用一次外部 API，抓取最新新闻，存入 SQLite 数据库。
- 正常运行耗时约 2 分钟。
- 某天外部 API 返回大量 429，重试逻辑导致总耗时超过 5 分钟。

会发生什么？

12:00:00 — Agent 实例 A 开始执行。  
12:05:00 — Cron 触发器再次点火，Agent 实例 B 启动，此时 A 还在跑。  
12:05:30 — A 完成写入，关闭数据库连接；B 正在写同一张表。  
12:06:00 — 数据库出现 `database is locked` 错误，或更隐蔽的数据重复、状态覆盖。

检查日志会发现两条执行记录几乎重叠，但结果却不符合预期。这就是“5 分钟任务撞车”的典型现场。

## 三、做法：在任务入口处加一把防重入锁

OpenClaw 本身没有内置跨实例的锁机制（其调度器主要负责触发，不感知任务的生命周期结束）。防重入锁需要由任务的执行逻辑自行实现。下面给出三种工程上可复现的方案，按场景选择。

### 方案 1：Redis 分布式锁（推荐）

若环境中已有 Redis，这是最可靠、跨进程跨机器的方式。

**核心步骤：**

1. 任务开始时，用 `SET lock:{workflow_id} {unique_value} EX 300 NX` 尝试获取锁。  
   - `unique_value` 可以是 UUID，用来区分锁的持有者。
2. 若返回 `nil`，说明锁已被持有，记录日志并直接退出，不做任何业务操作。
3. 若获取成功，执行正常的 Agent 逻辑。
4. 任务完成（无论成功或异常）后，用 Lua 脚本原子性地比较 `lock` 的值并删除，避免误删其他实例的锁：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

5. 锁的超时时间 `300` 秒需要大于任务的最大可能执行时间，确保即使进程崩溃，锁也能自动失效。

**嵌入 OpenClaw 的方式：**  
可以在 Agent 的 Python 或 Node.js 脚本入口处实现上述逻辑，也可将其封装为一个独立的 “Pre-check” 节点，放在工作流最前端。若锁获取失败，直接终止当前运行并发送通知（如 Slack/钉钉），防止静默跳过。

### 方案 2：数据库锁（适合无 Redis 场景）

如果你的 Agent 只操作同一张业务表，可以利用数据库本身的乐观锁或唯一索引。

做法：

1. 新建一张 `task_lock` 表，包含字段：`task_name`、`started_at`、`locked_until`。
2. 执行任务前，先尝试插入一条记录，`task_name` 设置为工作流名称，`started_at` 为当前时间，`locked_until` 为当前时间 + 最大执行时长。
3. 利用 `task_name` 的唯一索引：`INSERT ... ON CONFLICT(task_name) DO NOTHING`。若插入失败，说明已有活跃锁。
4. 任务结束后 `DELETE` 该记录。
5. 额外创建一个后台清理任务，定期删除 `locked_until < now()` 的过期锁，防止死锁。

### 方案 3：文件锁（单机轻量场景）

适合 Agent 在固定的一台机器上运行，且业务容忍偶尔的文件锁残留。

使用操作系统级别的独占锁，而非简单地检查文件存在性（后者的“检查和创建”不是原子操作）。

Python 示例关键片段：

```python
import fcntl, os

lock_file = '/tmp/my_agent.lock'
fp = open(lock_file, 'w')
try:
    fcntl.flock(fp, fcntl.LOCK_EX | fcntl.LOCK_NB)
    # 获取锁成功，执行业务
    do_work()
finally:
    fcntl.flock(fp, fcntl.LOCK_UN)
    fp.close()
```

若进程被 `kill -9`，系统会自动释放文件锁，不会残留。缺点是无法跨主机，且无法设置超时，只能等锁释放。

## 四、踩坑点：别以为加锁就万事大吉

实际落地中，下面几个坑会让防重入锁形同虚设。

### 1. 锁残留与超时时间设置不当
超时太短：任务还没跑完锁就自动释放，新实例成功获取锁，造成并行。  
超时太长：进程崩溃后，下一个周期内任务完全无法执行，直到锁自动过期。  
**解法：** 基于历史监控数据，将锁超时设为 `P99 执行时间 × 1.5`，并让监控覆盖锁获取失败次数，及时发现异常死锁。

### 2. 锁误删
实例 A 拿到锁，执行超时后锁自动过期；实例 B 顺利获取锁；此时 A 的 `finally` 块执行，直接删除锁，实际上删的是 B 的锁。  
**解法：** 必须用唯一值（如 UUID）标记锁持有者，删除前做值对比。Redis 方案中的 Lua 原子检查就是这个目的。

### 3. 依赖库的原子性假象
很多人以为在 Python 中 `os.path.exists` + `open` 就能实现文件锁，其实在并发下会出现检查通过但写入时已被占用的竞态。**必须用操作系统提供的文件锁（`fcntl`/`flock`）或分布式锁原语。**

### 4. 忽略任务幂等性
即使有锁，仍需假设极端情况下（脑裂、网络分区）可能有两个实例同时执行。任务必须设计为幂等：重复执行不会产生副作用或错误数据。例如用 `INSERT OR IGNORE`、唯一业务键，或状态机配合条件更新。

## 五、可复用建议

- **将锁逻辑抽象为 OpenClaw 可复用组件**：开发一个“防重入锁”节点，支持 Redis / 文件锁配置，暴露给其他工作流直接拖拽使用。
- **命名规范**：锁的 Key 包含工作流名称、环境、版本，比如 `lock:prod:news-summary-agent`。
- **失败策略**：获取锁失败不一定是异常，但必须被记录。可以输出到日志、发送一条“任务被跳过”的通知，方便后续追查。
- **与队列解耦**：如果任务的并发容忍度极低，考虑将定时触发改为生产消息到队列，由固定的 worker 串行消费。防重入锁可以作为队列方案之前的过渡方案。

## 六、总结

5 分钟任务撞车的本质，不是 5 分钟不够用，而是**调度间隔与真实执行时间的假设被打破**。无论是 Redis 锁、数据库锁还是文件锁，防重入设计的核心在于：让任务在执行前先确认“没有另一个我在跑”。

这看似只加了几行代码，却要求你同时考虑崩溃恢复、时间漂移、分布式一致性以及业务逻辑的幂等性。对于 OpenClaw 上的自动化实践者来说，防重入锁是工作流走向生产的第一道闸门——装对了，就能避免一大类令人头疼的幽灵重复问题。
