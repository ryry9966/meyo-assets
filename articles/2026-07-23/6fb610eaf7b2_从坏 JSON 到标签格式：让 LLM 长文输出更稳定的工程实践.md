## 背景

在 OpenClaw 社区做 Agent 流程编排、MCP 工具开发时，我们经常需要从大模型拿到结构化数据——比如总结长篇文档后给出关键信息、提取任务步骤、生成多轮对话的意图分类。最直接的做法是让模型输出 JSON，然后 `json.loads` 一把梭。

短文本、简单结构下这么做没问题。但一旦输出内容是长文（报告、多步推理、代码块），JSON 就开始频繁翻车：缺最后的大括号、字符串没转义、换行符炸了、尾部的双引号被截断……解析器直接抛异常，整个自动化流水线中断。

更要命的是，很多场景用的是流式输出（stream=True），JSON 解析必须等到流结束才能尝试，中途无法容错。你接到的可能只是一串不完整的字节，`json.loads` 连补全的机会都不给。

## 问题分析

JSON 天生要求**完整性**——哪怕差一个字符，标准解析器就不认。LLM 长文输出恰好有两个致命特征：

1. **尾部截断概率高**：受 max_tokens 限制、网络波动、提前停止生成等影响，长输出很容易缺尾巴。
2. **内容自身容易破坏 JSON 结构**：文本里自然包含引号、换行、转义符，模型即便受过指令调优，也常忘掉正确转义，输出 `"summary": "他说"没问题""` 之类的无效 JSON。

这些因素叠加，使得 JSON 格式在长文场景成了阿喀琉斯之踵。我们需要一种即使被截断也能“部分可用”的格式。

## 做法：切换到类标签格式

方案很简单：放弃纯 JSON，改用自定义的 XML/标记语言标签来包裹各个输出块。例如想让模型输出文章摘要和步骤列表，可以要求它输出：

```
<summary>
这里是摘要内容，可以有多行文字……
</summary>
<steps>
- 第一步：读取配置
- 第二步：调用 API
</steps>
```

而不是 `{"summary": "...", "steps": [...]}`。

这样做的好处是：

- **部分可解析**：即使输出在 `</steps>` 之前被截断，你仍然能提取到完整的 `<summary>` 块。
- **内容自由度更高**：不用操心转义问题，除非内容本身包含同名标签（见踩坑）。
- **解析逻辑轻量**：不需要引入完整的 XML 解析器，简单正则就能应对大部分情况。

### 解析实现

在 Python 端，可以直接用 `re.findall` 提取标签内容，结合一些防御性处理：

```python
import re

def extract_tag(text: str, tag: str) -> str | None:
    # 非贪婪匹配，DOTALL 让 . 匹配换行
    pattern = rf"<{tag}>(.*?)</{tag}>"
    match = re.search(pattern, text, re.DOTALL)
    if match:
        return match.group(1).strip()
    # 尝试提取未闭合的起始标签到文末的内容（降级策略）
    open_pattern = rf"<{tag}>(.*?)$"
    fallback = re.search(open_pattern, text, re.DOTALL)
    return fallback.group(1).strip() if fallback else None

# 使用
raw = """
<summary>
这是摘要……
</summary>
<steps>
- step1
- step2
"""
summary = extract_tag(raw, "summary")  # 成功获取
steps = extract_tag(raw, "steps")       # None，但至少拿到了 summary
```

如果你的场景需要多个同标签出现，可以将 `re.findall` 配合缓冲区使用。

### 提示词设计

修改系统/用户提示词，直接要求模型用标签格式，并给出示例。关键点：

- **禁止 Markdown 代码块**：强调不要用 \`\`\`包裹输出，直接输出纯文本标签。
- **展示一个完整样例**：让模型模仿结构。
- **声明“标签内不要包含同名标签”**：减少嵌套麻烦。

示例 prompt 片段：

```
你的输出必须严格遵循以下格式（不要用代码块包裹）：

<thinking>
你的内部推理过程
</thinking>
<final_answer>
最终回答的完整文本
</final_answer>
```

## 踩坑点

### 1. 标签内部出现非转义的尖括号

如果模型在 `<summary>` 里写入类似“`if a < b`”的代码，`<` 会破坏标签识别。对策：

- 在提示词中要求，如果内容本身包含 `<` 或 `>`，请用 `&lt;` `&gt;` 转义（类似 XML）。
- 更务实的做法：选择不易冲突的标签名，比如 `<|summary|>` 或使用 custom token，但这在某些模型上不稳定。

### 2. LLM “画蛇添足”

模型常在标签前后加上解释性文本，例如“好的，以下是输出：<summary>...”，甚至套一层 \`\`\`xml。这会导致正则匹配时多出垃圾前缀。解决办法：在 prompt 中强调“只输出指定标签，不要任何额外说明”，并在解析前用 `strip()` 清理空白，必要时用 `split` 的方法去除前缀。

### 3. 流式输出的缓冲区管理

流式场景中，数据按 chunk 到达，标签可能被切分在两个 chunk 里。简单的逐行解析会失效。解决方式是维护一个缓冲区，累积到至少一个完整标签闭合后再提取。如果缓冲区最后内容是一个未闭合的 `<xxx>...`，要么等待下一个 chunk，要么在流终止后采用降级提取。

### 4. 嵌套标签的需求

如果确实需要嵌套结构（如步骤中又有子步骤），标签格式的复杂度会增加。建议尽量扁平化设计，或者改用 `JSON` + 标签混合：用单独标签包裹一段 JSON，这样在截断时 JSON 仍可能破损，但至少你能拿到其他标签的内容。

## 可复用建议

1. **事先约定标签名和闭合规则**：在 prompt 里明确写出完整示例，让模型模仿。
2. **善用唯一分隔**：在输出最外层加上明确的开始/结束标记，如 `<out>...</out>`，能有效抵抗“多说话”的毛病。
3. **解析时先清理后提取**：`text.strip()` + 去掉可能包裹的 \`\`\` 标记 (例如用 `re.sub(r'```\w*\n?', '', text)`)。
4. **做一次完整性检查**：统计设计的标签数量，对比解析出的数量，不符合预期时执行降级逻辑（只取已完成的块，并记录告警）。
5. **避免完美主义**：不要试图实现完美的标签解析器，用正则处理 90% 的场景，剩下的用日志 + 人工兜底。

## 总结

从 JSON 转向标签格式，本质上是在结构化输出的**完备性**和**鲁棒性**之间做了取舍：牺牲了不需要额外解析的便捷，换来了对截断和内容混乱的高容忍度。在 OpenClaw、MCP 插件的长文生成管道里，这种保底手段能大幅降低生产环境的解析异常率。如果你正在为 Agent 流程中反复出现的 `JSONDecodeError` 头疼，不妨试试让 LLM 输出“标签汤”，用十几行正则代码换来整条管线的稳定。
