## 背景

在基于 OpenClaw 构建的 Agent 工具链中，Gateway 作为统一入口，负责把请求路由到后端的 MCP 插件、内部 API 或外部服务。为了保障整个调用链的可用性，Gateway 会持续性对上游服务发起健康检查（health check）。当一切正常时，这些日志就像白噪声，几乎无人留意；可一旦某个 MCP 插件异常掉线或响应变慢，日志里就会突然刷满 `health check failed`，甚至触发大规模告警。此时，能否快速从日志中提取有效信息，直接影响排障速度和线上稳定性。

本文不讨论健康检查协议本身的设计，而是聚焦一个更具体的问题：**Gateway 健康检查日志到底该怎么看？** 我们会结合实际场景拆解日志结构、踩坑点，并给出可复用的观测建议。

## 问题

工程师在排查 OpenClaw Gateway 健康检查相关故障时，常会陷入三个困境：

1. **信息过载**：日志被重复的探针记录淹没，关键错误一闪而过。
2. **语义模糊**：相同状态码（如 503）可能对应“上游端口未监听”“超时”“主动拒绝连接”等不同根因，日志却不够直观。
3. **上下文缺失**：单条健康检查日志往往只包含自己的状态，缺少与流量、部署事件的关联，导致“明明健康检查失败，用户请求却正常”或相反的现象。

如果只是 grep 一下错误量就重启服务，很可能会掩盖真正的问题。

## 做法与步骤

### 1. 先确认健康检查的配置基线

在动手看日志前，要明确 Gateway 对每个 upstream 到底配置了哪种检查：

- **检查端点**：HTTP 路径（如 `/healthz`、`/readyz`）或 gRPC health 标准调用。
- **探测间隔与超时**：例如 `interval: 10s, timeout: 2s`。
- **失败阈值**：连续多少次失败才标记为不可用。

这些参数可以在 OpenClaw Gateway 的配置文件中确认，或者直接通过管理 API 拉取。它们决定了日志出现的频率和“失败”的定义，是后续解读的基础。

### 2. 读懂单条健康检查日志

典型的 Gateway 健康检查日志会包含以下字段（以结构化 JSON 为例）：

```json
{
  "time": "2025-03-15T10:23:14.456Z",
  "level": "warn",
  "msg": "health check failed",
  "service": "mcp-db-connector",
  "upstream": "10.0.1.5:8080",
  "check_type": "http",
  "status_code": 503,
  "latency_ms": 1501,
  "error": "context deadline exceeded"
}
```

重点关注：

- **`service` / `upstream`**：哪个 MCP 插件或后端实例出了问题。
- **`check_type`**：路由规则是否匹配对了探针类型。
- **`status_code`**：HTTP 检查时，除 2xx 外都属失败，但 503 通常表示上游主动返回“不可用”（可能是就绪检查未通过），而连接拒绝或超时则更接近网络层问题。
- **`error`**：`connection refused` 说明端口没开或 Pod 还没启动，`context deadline exceeded` 说明超时，`dial tcp: i/o timeout` 可能与网络抖动有关。
- **`latency_ms`**：接近超时阈值的延迟往往意味着上游正在“挣扎”——可能线程池或连接池耗尽了。

### 3. 通过聚合发现模式

单条日志价值有限，聚合后的模式才是关键。推荐在 Gateway 所在节点上用 **jq + awk** 或直接接入日志平台进行统计：

```bash
# 最近5分钟内，每个上游的失败次数
cat gateway.log | jq -r 'select(.msg == "health check failed") | [.service, .error] | @tsv' \
  | awk '{count[$1" "$2]++} END{for(c in count) print count[c], c}' | sort -nr
```

这会快速暴露：哪个插件失败最频繁、主要错误是什么。若发现某个 MCP 插件的 `connection refused` 占比突然升高，往往与其刚重启或部署有关；若出现周期性超时，则可能与外部服务弹性不足、线程池设置相关。

### 4. 关联上下游事件

健康检查日志不应孤立看待。定位根因时，需要将其与以下信息做时间线对齐：

- **部署/变更记录**：插件镜像更新、配置变更的时间点。
- **上游插件自身日志**：检查是否出现 OOM、`too many open files` 等。
- **Gateway 自身指标**：失败的检查是否会立即触发熔断，或者 Gateway 是否有重试队列堆积。

将上述信息拼合后，多数故障原因会浮出水面。

## 踩坑点

- **健康检查路径配置“一刀切”**：为所有 MCP 插件统一设置 `/health`，但部分插件只暴露了 `/ready`，导致所有检查都失败。务必按插件实际能力配置独立端点。
- **探针频率过高引发雪崩**：测试环境为追求快速发现不可用，把间隔设为 1s，结果上游插件出现瞬时高负载，探针超时又触发更多检查，最终拖垮 Gateway 自身。应使用合理的退避策略，并给探针独立的轻量端点。
- **日志级别误用**：部分团队将所有健康检查失败都打成 `error`，一旦出现间歇性网络抖动就会触发大量报警。建议将临时失败保持在 `warn`，仅将连续失败超出阈值提升为 `error`，并依靠告警规则追踪触发次数。

## 可复用建议

1. **标准化健康检查端点**：要求每个 MCP 插件同时暴露存活（`/healthz`）和就绪（`/readyz`）检查，并返回一致的 JSON 负载（如 `{"status":"ok","details":{}}`），方便 Gateway 统一解析并记录在日志中。
2. **结构化日志与追踪**：让 Gateway 打印 JSON 日志，并注入 `trace_id`，即使健康检查本身不承载业务流量，也可以与 OpenClaw Agent 的全链路追踪关联，出现异常时能一路回溯。
3. **转化为指标并设置告警**：将健康检查失败次数、延迟分位数导出为 Prometheus 指标。告警规则基于“最近 5 分钟内失败率 > 50%”而非单次失败，从而抑制抖动误报。
4. **定期演练日志解读**：把常见的日志样本（如超时、拒绝连接、503）纳入团队 Runbook，并进行故障演练，让所有成员都能在 2 分钟内定位到出问题的上游。

## 总结

OpenClaw Gateway 的健康检查日志不是负担，而是通往可观测性的“第一层信号”。理解单条日志的含义、懂得聚合模式、学会关联上下游事件，就能在代理链路的复杂性中始终保持清醒。下次当 Gateway 打出 `health check failed` 时，希望你不只看到失败，更能看到它的“话外音”。
