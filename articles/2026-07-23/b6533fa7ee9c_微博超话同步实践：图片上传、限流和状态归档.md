## 背景

我们在维护一个自动化内容推送项目，需要将每日生成的图文内容自动发布到微博超话。整套流程跑在 OpenClaw 的任务链里，前端由一个定时触发器驱动，背后依赖微博的开放接口和本地图像处理管线。

最初几天效果不错，但很快就暴露出一系列工程问题：图片上传间歇性失败、触发频率控制不精确导致被限制、发帖状态丢失后重复推送。这些问题单靠“请求-重试”的简单逻辑无法彻底解决，于是我们重新梳理了发布链路，用状态机、冷却队列和结构化日志把流程拉直。本文就是在该过程中积累的实践笔记，所有方案都已稳定运行超过两周。

## 问题拆解

1. **图片上传成功率低**  
   微博图片上传接口对文件格式和尺寸较敏感，部分图片明明在本地预览正常，上传却返回模糊的错误码。另外，接口偶尔会返回 HTTP 200 但响应体中的 `pid` 为空，导致后续发布流程缺图。

2. **频率限制不可见**  
   开放平台文档里只给了笼统的“接口调用频率限制”，没有精确数值。实际连续发布时，很容易触发 429 或直接丢弃请求。缺少本地冷却控制，出问题后只能盲目加长间隔。

3. **任务状态丢失**  
   之前的同步脚本只是顺序执行，失败后没有记录已完成的步骤。重新触发会导致重复发帖，或不发帖直接跳过，最终归档信息完全缺失，排查困难。

## 做法

我们把一次完整的“超话发帖”抽象为一个有限状态机，通过 OpenClaw 的任务节点串联，并用 Redis 缓存状态与冷却时间。

### 1. 图片预处理标准化

在进入上传步骤前，先对所有图片执行归一化处理：

- 统一转为 JPEG ，质量 85%；
- 长边限制为 1080px，保持宽高比；
- 使用 `sharp` 进行检查，若文件体积仍超过 1MB，则进一步降低质量，强制压到 1MB 以下。

这样几乎消除了因格式/尺寸导致的接口报错。

### 2. 上传重试与 pid 校验

上传图片的 API 调用封装为一个 Agent，内部逻辑：

- 先检查是否有已缓存的有效 pid ，有则直接使用；
- 无缓存则发起上传，并校验响应：若 `pid` 字段缺失或格式不匹配，进行最多 3 次重试，重试间隔递增；
- 成功后写入 Redis 并设置 24 小时过期（避免脏数据占用）。  
  这样解决了间歇性 `pid` 为空的问题。

### 3. 本地冷却与远程限流协同

针对接口频率限制，我们没有单纯依赖 API 返回的 Retry-After，而是在本地维护一个发布冷却队列：

- 每次发布完成后，记录时间戳，后续发帖请求必须等待固定冷却间隔（实际观察为 90 秒较稳定）；
- 使用令牌桶思想，一个微信号（或 app key）每分钟最多 1 次、每小时最多 15 次，超出后 Sleep 等待；
- 如果依然收到 429，采用指数退避重试，同时暂停整个发布时间线 5 分钟，并在监控中打点。

由此将被动挨打变成主动控制，发布成功率提升到 99% 以上。

### 4. 状态归档与幂等

每个待发帖生成一个 `task_id`，在 MySQL 中建 `weibo_post_tasks` 表，字段大致包括：

- `task_id` 主键
- `status`（`pending` → `images_uploading` → `posting` → `done` / `failed`）
- `image_pids`（JSON 数组）
- `post_id`（成功后的微博帖子 ID）
- `retry_count`、`error_log`

OpenClaw 工作流状态转换时，事务性更新该表。重试时先检查当前状态，若已 `done` 则直接跳过，防止重复发帖。所有错误日志都归档，方便后期人工补偿。

## 踩坑点

- **超话 ID 的动态获取**：超话 ID 在不同环境（测试/正式）不同，且会因微博侧调整而变化。我们通过定时任务查询最新 ID 并写入配置缓存，而不是硬编码。
- **图片 pid 格式**：发布接口要求 `pic_id` 参数为逗号分隔的字符串，如 `pid1,pid2`，若多传空格或直接用数组格式会失败，排查了很久才定位。
- **每日发布总量上限**：除了短时间频率，微博对单日总发帖量也有限制，一旦超量当天所有请求都会失败。我们在每天首次运行时检查剩余配额，不足时自动暂停并告警。
- **图片上传 Content-Type**：接口要求 `multipart/form-data`，但部分 HTTP 客户端库默认不带 `Content-Type`，需显式设置，否则返回通用错误。

## 可复用建议

- **抽象发布适配器**：把“发布到微博超话”封装成一个实现 `Publisher` 接口的模块，之后如果要支持其他平台（如小红书、头条），只需替换适配器即可，状态机和归档逻辑完全复用。
- **用 MCP 插件包装接口**：将微博鉴权、图片上传、发帖等 API 分别做成 OpenClaw MCP 工具，便于在不同工作流中组合调用，也能独立测试。
- **状态机与监控对齐**：状态转换时同步推送 metrics，比如 `posting_failed` 事件，方便在监控系统里设置告警阈值。
- **生成测试用沙盒**：专门申请一个测试超话，所有接口变更先在测试环境中全链路验证，避免直接伤害正式账号。

## 总结

经过这轮改造，微博超话同步从“大概率成功、偶尔翻车”变成一套稳定、可观测的无人值守管道。图片上传成功率超过 99.5%，频率控制不再靠运气，失败任务能被清晰记录和补偿。对于使用 OpenClaw 做自动化发布的同学，这套状态归档与冷却协同的思路同样适用于其他受限平台的同步场景。
