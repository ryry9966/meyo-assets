# 别再硬修 JSON 了：用标签格式让 LLM 长文输出稳如老狗

## 背景：当 Agent 的 pipe 开始崩溃

OpenClaw 这类 agent 框架里，我们经常让 LLM 输出结构化的长文本——比如生成一份多章节报告、编排一组步骤计划、甚至直接吐出工具调用的参数。为了“标准化”，大多数人的第一反应是：让模型输出 JSON。

于是 prompt 里拼命加“你必须输出合法 JSON”“不要尾随逗号”“用 ```json 代码块包裹”。但真跑到生产环境，尤其当回复超过 800 token 或嵌套层级超过三层，坏 JSON 来的比天气预报还勤——截断、注释里的换行、未转义的双引号、突然换成了 YAML 风格……然后整个流水线断掉，retry 又浪费 token 又超时。

其实问题根源不在于模型不够强，而是 **JSON 对于长篇幅、多段落、需要内嵌自然语言的内容，本身就是一种反人性的序列化格式**。尤其 GPT-4 这类模型，它生成 token 的本质是自回归预测，天然倾向于行文连贯、标记简洁的结构，而不是精准维护括号配对和逗号位置。

## 问题定位：JSON 的长文诅咒

在过去几个项目里，我统计了一下：当让 LLM 输出超过 500 字的纯 JSON 结构，且内部包含大段 Markdown 文本、代码块、列表时，首次生成合法 JSON 的概率约为 62%～70%（gpt-4-turbo，temperature 0.3）。剩下的要么解析失败，要么字段缺失。修复成本高，因为正则补丁、ast 修复都不可靠，还得防幻觉。

更致命的是在 **Agent 链式调用** 中：第一步 LLM 规划输出给第二步工具使用，如果 JSON 坏了，错误会向后传导，甚至污染记忆。很多团队的做法是加一个校验重试节点，但这意味着延迟翻倍，用户体验断崖式下降。

有没有办法，既保持结构化，又让模型在长文输出时足够松弛？**标签格式** 是我验证下来最务实的一条路。

## 方案：XML-like 标签化输出

核心思路：用类似 XML 的标签包裹每个结构化字段，取代 JSON 的 `{}[]`。例如要生成一份带摘要、步骤、注意事项的报告，可以约定如下输出格式：

```
<report>
<title>项目迁移方案</title>
<summary>
这里是一段自由文字，可以包含任何标点、换行。
</summary>
<steps>
<step>
<name>备份数据库</name>
<detail>
执行 pg_dump...
```sql
SELECT 1;
```
</detail>
</step>
<step>
...
</step>
</steps>
<notes>
- 第一条注意事项
- 第二条
</notes>
</report>
```

这个格式对模型极其友好：标签成对出现，嵌套关系由缩进和标签名自然体现；文本可以随意换行、带代码块，不易产生转义冲突。解析时只需用正则提取最外层标签内容，再递归提取子标签即可，代码不到 20 行。

我在 OpenClaw 的 `custom_prompt` 节点中强制要求 LLM 使用标签格式输出，不再要求 JSON。实验中对同样复杂度的任务，**标签格式的一次生成合规率提升到 93%+**，即便在 gpt-3.5-turbo 上也稳定在 87% 左右。更重要的是解析失败时我可以根据已闭合的标签进行**部分消费**——哪怕输出被截断，我也能取到前几个完整字段，降级使用，而 JSON 解析通常全有或全无。

## 实践步骤（与 OpenClaw 集成）

1. **设计标签 schema**  
   标签命名用英文小写 + 下划线，禁止属性，只依靠嵌套关系。每个文本域允许任意内容，但约定不要出现与闭合标签相同的字符串（选特殊的名称基本不会误匹配）。

2. **编写 system prompt 示例**  
   不要只说“用标签”，直接给出完整仿真实例，包括边界情况：代码块、多行文本、特殊符号。示例长度至少 300 token，才能让模型真正学会。

3. **轻量解析器实现**  
   我用 Python 写了个通用提取器：
   ```python
   import re

   def extract_tag(text, tag):
       pattern = rf"<{tag}>(.*?)</{tag}>"
       match = re.search(pattern, text, re.DOTALL)
       return match.group(1).strip() if match else None
   ```
   对于嵌套标签，先取外层，再在外层内递归取。注意 `re.DOTALL` 让 `.` 能匹配换行。生产环境建议加入标签平衡性检查（简单计数 `count("<tag>") == count("</tag>")`），失衡时降级或重试。

4. **调整重试策略**  
   标签格式的另一个优势：你可以在 prompt 里教模型“如果内容中包含与标签相同的字符串，请用转义变体”。实际上极少发生，万一发生，可降级为提取到第一个闭合标签前的所有内容作为字段值，不会整个流程失败。

5. **在 OpenClaw 中注册为输出格式**  
   将解析逻辑封装成一个 `OutputFormatter`，配置到你的 pipe 中。上游 agent 输出原始标签文本，下游节点用 `formatted_data` 直接取字段，对下游工具完全透明。

## 踩坑记录与真实教训

- **标签名不要用常见单词**  
  我最早偷懒用了 `<summary>`，结果模型偶尔在文本里写“see the summary below”，被误解析。改成 `<report_summary>` 后根除。

- **不要忽略缩进**  
  LLM 喜欢在闭合标签前加换行和缩进，比如 `</step>\n  </steps>`。解析时 `strip()` 可以去除，但如果正则用了过于严格的边界匹配会丢失内容。建议用 `re.DOTALL` 且 pattern 中的 `(.*?)` 足够宽容。

- **特殊情况：模型输出多个同级标签**  
  比如 `<step>` 出现多次，应该用 `finditer` 遍历而不是 `search` 只取第一个。解析逻辑要返回列表。

- **截断处理**  
  当 `finish_reason` 是 `length` 时，标签格式允许我们拿到最后一个完整闭合的字段。我的做法：从尾部向前扫描找到第一个 `</tag>`，截取完整的文本块，忽略后续的不完整部分。这一招在生产中救了至少 3 次关键任务。

## 可复用建议

- **优先标签而非 JSON**，当输出包含大段自由文本、代码、多步骤内容时；如果只是简单键值对，JSON 仍然更紧凑。
- **标签 schema 与 prompt 绑定**：把示例做成一个可注入的模板，避免每次手动重写。
- **增加“不完整输出”处理层**：别只依赖总 try/except，要在解析器内部做标签平衡检查并返回 `{field: partial_value, _truncated: true}`，上游决定降级还是重试。
- **集成监控**：记录标签格式合规率、截断率，如果合规率突然下降，通常是 prompt 被改坏了或者模型切换。

## 总结

让 LLM 输出稳定，不是逼它更“逻辑”，而是给它最自然的表达方式。标签格式轻量、解析简单、对长文本和嵌套极其宽容，在 agent 管道中能显著降低断裂点。尤其在 OpenClaw 这类高度模块化的自动化环境里，少一个 retry 节点就少一个超时坑。如果你正在被坏 JSON 折磨，不妨花半小时切到标签方案，很可能从此告别“逗号警察”的角色。

顺便说一句，这个思路也可以复用到 function calling 的备选方案中——当函数参数包含大段文本，直接用标签包裹传参，用简单的提取逻辑代替复杂的 JSON Schema 校验，效果往往比想象中好。
