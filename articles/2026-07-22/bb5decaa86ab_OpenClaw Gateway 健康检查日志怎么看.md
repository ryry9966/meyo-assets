# OpenClaw Gateway 健康检查日志怎么看

在 OpenClaw 的日常工程化使用中，Gateway 承载了 Agent、MCP 工具以及插件的统一入口。无论是生产巡检还是自动化流水线里的部署验证，健康检查日志几乎是我们最先翻看的一类记录。但很多同学的用法还停留在“看状态码是否为 200”，一旦状态码正常就认为万事大吉。实际上健康检查日志里藏着大量一线故障信号，本文整理了一套在工程中反复验证过的读日志方法。

## 一、背景：Gateway 的健康检查不只是“活着”

OpenClaw Gateway 对外暴露的健康端点（比如 `/health` 或 `/healthz`）不仅要报告网关进程本身是否存活，还通常会汇总下游各组件的状态，例如：

- Agent 管理服务是否可达；
- MCP 后端是否在线；
- 已注册插件的最新健康结果；
- 各上游节点的延迟与错误率。

因此，一次健康检查的日志，往往同时包含了网关自身状态和全部依赖的“体检结果”。只用 `200` 或 `503` 来判断，无异于只看了体检报告封皮。

## 二、典型问题：那些被忽略的日志细节

在我参与的几个 OpenClaw 落地项目里，经常遇到这样的场景：

- 网关返回 200，但部分 Agent 调用一直超时——细看健康检查日志才发现 `agent-manager` 被标记为 `degraded`，延迟已经接近阈值；
- CI/CD 流水线中部署新插件后，健康检查始终 200，但插件实际不可用——因为健康检查配置了缓存，实际探测到的是旧结果；
- 偶发的 502 被直接忽略，几天后累积成上游雪崩。

本质原因都是：**没有把健康检查日志当作可观测性数据来消费**。

## 三、怎样看：一套可复用的阅读框架

下面以常见的 OpenClaw Gateway 日志行为基础（假设输出为 JSON 结构化日志），给出具体步骤。不同部署环境字段命名可能略有差异，但思想是通用的。

### 1. 找到对应的日志流

如果 Gateway 以容器化方式运行：

```bash
docker logs -f openclaw-gateway 2>&1 | grep health
```

如果是 Systemd 服务：

```bash
journalctl -u openclaw-gateway -f | grep health
```

**建议**：在生产环境里，健康检查日志访问频率高，直接 `grep` 会产生大量输出。尽量先用采样或聚合工具（比如 Loki + LogQL）进行过滤，避免被日志量淹没。

### 2. 理解一条完整日志的样子

一条典型的健康检查日志可能长这样：

```json
{
  "ts": "2025-01-15T10:23:45.123Z",
  "level": "info",
  "msg": "health check completed",
  "path": "/health",
  "status": 200,
  "latency_ms": 12,
  "upstream": {
    "agent-manager": "ok",
    "mcp-server": "degraded",
    "plugin-sandbox": "ok"
  }
}
```

重点关注四个维度：

- **status**：最终返回给调用方的状态码。200 代表网关认为整体健康，但这可能是部分降级的结果。
- **latency_ms**：健康检查本身的耗时。如果基线是 10ms，突然变成 200ms，说明要么网关自身资源紧张，要么某个上游探测严重超时。
- **upstream 对象**：直接列出每个依赖的健康状态，`ok` / `degraded` / `unhealthy` 等。`degraded` 通常意味着该组件仍然可用，但响应变慢或部分失败，是拖慢整体系统的元凶。
- **error 字段（有时出现）**：当某个上游不可达，日志可能附加具体的连接拒绝、超时、HTTP 503 等错误详情。

### 3. 根据日志信号定位问题

常见模式及其对应的排查方向：

| 日志特征 | 初步判断 | 下一步动作 |
|---------|---------|----------|
| `status` 为 503，`upstream` 中某组件为 `unhealthy` | 该组件完全不可用 | 登录对应组件查看日志，确认进程是否存活、端口是否监听 |
| `status` 为 200，但某个组件为 `degraded` | 组件部分故障，例如只读副本延迟过大 | 检查该组件的资源使用率、慢请求、连接池情况 |
| `latency_ms` 整体升高，但 upstream 都正常 | 网关自身 CPU/内存瓶颈，或健康检查逻辑变重 | 检查网关资源，回顾近期是否有配置变更导致更重型的探测 |
| 同一时刻多条日志，status 在 200/503 之间跳动 | 上游存在间歇性故障，或网络抖动 | 使用 `jq` 聚合分钟级错误率，结合监控链路追踪定位 |

### 4. 构建简单的自助诊断指令

假如日志文件为 JSON Line 格式，可以快速过滤异常：

```bash
# 查找所有非 200 的健康检查
cat gateway.log | jq 'select(.msg == "health check completed" and .status != 200)'

# 统计每分钟 degraded 出现次数
cat gateway.log | jq -r 'select(.upstream[]? == "degraded") | .ts[0:16]' | sort | uniq -c
```

将这些指令写成脚本，可以随时在问题现场快速拉出“异常画像”。

## 四、踩过的坑

1. **把 Gateway 自身的 `/healthz` 和业务健康检查混为一谈**。Gateway 通常还暴露一个仅表示进程存活的轻量端点，它的日志只有进程基本信息，不包含上游状态。排查依赖问题一定要看聚合型健康检查的日志。

2. **健康检查缓存导致误判**。为降低负载，健康探测结果可能缓存几秒。某次部署后立刻查看日志，看到的仍是旧状态。排障时要注意 `ts` 字段的时间戳是否新鲜，有必要时可调用刷新端点的强制更新能力。

3. **非 200 就立刻认为是故障**。当上游正在滚动重启时，偶尔的健康检查失败是预期内的。需要结合**连续失败次数**和**持续时间**来判断，而不是单条日志报警。

4. **信息不全时为看详细错误盲目开启 `debug` 级别**。这会瞬间放大日志量，造成磁盘 I/O 压力和日志聚合成本飙升。更稳妥的做法是只对特定可疑路径临时调整级别，或者依赖已有的 `error` 字段携带的摘要信息。

## 五、可复用的工程建议

- **为健康检查日志设定专门的告警规则**：在 Prometheus/Loki 中，当某个上游连续 3 次被标记为 `unhealthy`，或延迟超过基线的 3 倍，应触发低风险告警。
- **在部署流水线中增加健康验证步骤**：部署后执行一个简单的脚本，轮询健康检查日志 30 秒，要求期间所有上游均为 `ok` 且无异常波动，否则回滚或暂停。
- **制作巡检小抄**：将上文表格打印出来，贴在团队知识库里，让新人也能在 5 分钟内对照日志完成初步判断。

## 六、总结

OpenClaw Gateway 的健康检查日志，是系统可观测性里成本最低、信息密度最高的一类信号。从只看 HTTP 状态码，进阶到关注延迟、上游详细状态和错误趋势，能在少侵入业务的情况下快速缩小故障范围。

工程中，我们只需要做三件事：  
1. 结构化存储和查询这些日志；  
2. 为几个关键字段（status、upstream、latency）建立常态化的监控与告警；  
3. 在排障流程中把它作为第一个“切口”。  

养成这个习惯，很多原本需要半小时才能定位的问题，可能几分钟就能从日志中看出端倪。
