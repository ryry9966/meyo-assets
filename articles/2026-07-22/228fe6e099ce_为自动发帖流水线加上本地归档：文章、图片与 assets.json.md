## 背景：流水线跑完，本地什么都没留下

在 OpenClaw 生态里，很多人已经把内容生成与多平台发布串成了一条自动化流水线。典型做法是：

- 用 Agent（或 MCP Server）生成文章正文；
- 自动配图（DALL·E / Stable Diffusion）；
- 调用平台 API 发到 Twitter、小红书、Telegram 等。

这类流水线的问题在于**只管发，不管留**。一旦发出去的帖子需要修改、二次分发，或者在平台被吞了需要补发，你手里往往没有直接的本地资产。要么去平台后台一条条翻，要么重新生成，浪费 token 也打断了节奏。

更严重的是，当流水线规模变大——比如你同时维护三个语种的账号、每周自动产出多篇技术帖——缺少本地归档会让追溯、复用和纠错都变得困难。文章和图片散落在不同服务里，甚至配图与文章之间的对应关系都不清楚。

所以我给手头的自动发帖流水线加了一层**本地归档**：每生成一篇文章，就在本地目录里落下一组文件，并用一个 `assets.json` 记录完整的元数据和关联关系。

## 问题拆解：需要归档哪些东西？

自动发帖流水线的核心产物是：

- **Markdown 正文**：已经格式化好的帖子内容；
- **图片**：封面、内嵌配图等，通常由 AI 生成；
- **元数据**：标题、标签、生成时间、平台分发状态、所用模型、prompt 等。

如果只把 Markdown 和图片文件随便扔进文件夹，长期下来还是会乱。所以还需要一个结构化索引文件，让本地归档是可查询、可批量操作的。我选择用 `assets.json`，内容可以按需扩展，但至少包含：

- 文章唯一 ID（或 slug）
- 标题
- 生成时间
- 语种
- 正文文件路径
- 图片文件路径列表
- 平台发布状态（`draft`, `published`, `failed`）
- 使用模型名 / prompt 快照（便于后面复现或 debug）

## 做法：在流水线尾部插入归档步骤

假设你的流水线已经有一个 Agent（比如一个 MCP Server 工具）负责生成内容。归档并不需要改动核心生成逻辑，只需在“生成-发布”之间插入一个本地归档步骤。我把这个步骤抽象成一个独立函数 / Tool，这样任何 Agent 都能调用。

**步骤 1：确定归档目录结构**

我最终用的目录结构如下：

```
content_archive/
├── 2025-01-08-quick-local-archive/
│   ├── article.md
│   ├── cover.png
│   ├── assets.json
├── 2025-01-10-deploy-mcp-server/
│   ├── article.md
│   ├── diagram.png
│   ├── assets.json
└── ...
```

每个帖子一个子文件夹，用日期和 slug 命名。这样做的好处是不依赖数据库，直接用文件管理器也能快速浏览。`assets.json` 只存在于子文件夹内，如果以后想生成全局索引，可以用一个脚本遍历所有子文件夹合并。

**步骤 2：流水线中的最小化归档 Tool**

在我的设置里，Agent 执行完内容生成和配图后，会拿到：

- `markdown_content`：文章正文字符串
- `image_paths`：本地图片路径列表（图片已经生成并保存到临时位置）
- `metadata`：标题、标签、平台等元数据

我写了一个 `local_archive_tool`，接收这些参数，做：

1. 根据日期和 slug 创建子文件夹（如 `2025-01-08-quick-local-archive`）。
2. 将 `markdown_content` 写入 `article.md`。
3. 将图片从临时路径复制/移动到子文件夹内，并重命名为 `cover.png`、`img_1.png` 等。
4. 构建 `assets.json` 对象，包括上述所有信息，并写入。
5. 返回归档路径，供后续发布步骤读取（比如发布时可以直接引用本地图片路径）。

这个 Tool 的实现本身可以是一个普通的 Python 函数，或者包装成 MCP Server 的一个 tool。关键是接口要稳定且无副作用，不能因为归档失败而影响发布步骤。

**步骤 3：与发布步骤解耦**

归档必须在发布**之前**完成，因为发布过程可能会引用本地图片文件（例如 Twitter API 上传图片需要从本地路径读取）。归档完成后，发布函数直接读取子文件夹内的文件即可。

为了保持灵活性，`assets.json` 里预留了 `publish_status` 字段。归档时记为 `draft`；发布成功后由发布步骤更新为 `published`，失败则标记 `failed` 并记录错误信息。这样就形成了一个简单的状态机，后续可以通过脚本扫描所有 `assets.json` 补发失败内容。

## 踩坑点

**1. 图片路径跨平台问题**

配图生成工具（如 DALL·E API）可能直接返回 URL 而非本地文件。如果流水线运行在云函数或容器里，需要先把图片下载到临时目录再归档，否则 `assets.json` 里记录的 URL 过几天就失效了。我统一在归档前强制将图片变成本地文件，哪怕多一次下载开销。

**2. 文件名冲突**

同一篇文章可能有多张图片，如果都用时间戳命名，在不同环境下可能有重复。我直接用归档函数内部递增计数命名（`cover.png`, `img_1.png`, `img_2.png`），并在 `assets.json` 里记录原始文件名或生成来源，方便回溯。

**3. 归档失败不应阻塞发布**

初期我把归档和发布写在同一个 try-except 里，结果文件写入权限问题导致整个帖子发不出去。后来改成：归档失败时 log 错误但不中断流水线，发布步骤仍然可以用内存里的内容继续（图片退化为 URL 或不带图）。事后可以根据日志手动补归档。

**4. 多 Agent / 并发写入**

如果同一时间有多个 Agent 分别处理不同帖子，归档目录可能发生并发写入冲突。因为每个帖子使用独立的子文件夹，实际上冲突概率很低。但为了保险，我在创建子文件夹时用了 `exist_ok=True` 并且写入文件时使用原子写入（先写临时文件再 rename），避免写一半被其他进程读到。

## 可复用建议

- **把归档做成一个标准 MCP Tool**。输入是内容+图片数组+元数据，输出是归档路径。这样任何 Agent 或流水线编排工具都能直接调用，不用重复实现。
- **`assets.json` 尽量保持可扩展**。除了基本字段，可以加 `custom_metadata` 对象，方便不同项目自定义。后期如果要做全球索引，可以写一个 scanner 脚本合并所有子文件夹的 `assets.json`。
- **归档目录本身也是一个版本库**。可以考虑对整个 `content_archive/` 做 git 管理，每次生成新帖子自动 commit。这样文章迭代历史也一目了然。
- **发布状态更新要幂等**。标记 `published` 或 `failed` 时，判断是否已处于该状态，避免重复操作导致状态错乱。

## 总结

给自动发帖流水线加上本地归档，本质上是用很小的工程代价，换取了长线运营中非常宝贵的资产可控性。你不再依赖平台后台去翻找历史帖子，也不再因为临时重发而重新生成内容。一个清晰的 `assets.json` 加上按日期和 slug 组织文件，能让你对本地所有生成内容了如指掌。

在 OpenClaw 这类 Agent 驱动的内容管线里，稳定性往往不是靠某一步完美，而是靠每一步都有兜底。本地归档就是那个你平时感知不到，但一出了事就分外感激的步骤。
