## 背景

在 OpenClaw 及类似 Agent 工作流中，我们常常让 LLM 输出结构化数据——提取长文档中的实体、总结多步骤操作，或者生成可直接写入插件的配置。JSON 是第一反应，但实际上，在长文场景下，JSON 的可靠性远不如想象。

当输出长度超过 1000 token，复杂嵌套变多，模型很容易出现：
- 少写一个引号或括号，导致整个 JSON 解析失败；
- 在字符串内意外闭合引号；
- 最后字段后多余逗号；
- 截断输出，结构不完整。

这些问题在自动化链路里是致命的。下游解析器直接报错，整个 pipeline 中断，重试消耗 token 且结果不一定更好。我们需要一种对模型更友好、容错性更强的格式。

## 问题拆解

典型的坏 JSON 案例：让 LLM 从一篇项目文档中提取所有 API 端点信息，输出为 JSON 数组。结果可能是：

```json
[
  {"method": "POST", "path": "/api/users", "description": "Create a new user."}
  {"method": "GET", "path": "/api/users", "description": "List users"}
]
```

缺少逗号，或者最后多一个逗号。如果是几百个对象，人工检查几乎不可能。

还有一种更隐蔽的问题：模型在长输出时“遗忘”了顶层结构。比如需要输出 `{"endpoints": [...]}`，结果直接输出了数组，或者多了一层无用的包装。这些在结构化提取中很常见。

## 为什么不用 Function Calling / Structured Output？

OpenAI 的 Structured Output、JSON mode，或者一些推理引擎的结构化解码能力，确实能保证 JSON 语法正确。但在实际落地时，有几个阻碍：
- 不少自部署模型（尤其通过 vLLM、Ollama 等）的结构化输出尚不稳定或未实现；
- Agent 工作流中经常需要在一次生成中混合自然语言和结构化块，强制全 JSON 会丢失解释、推理过程；
- Long context 下，结构化解码对显存和延迟的压力更大；
- 我们有时需要模型输出**多个独立可解析的块**（例如先总结，再分类，最后提取细节），用纯 JSON 包裹不灵活。

因此，需要一种更宽容、更适合长输出、且对解析器友好的替代方案。

## 解决方案：标签格式

标签（Tag）格式是一种借助 XML/HTML 风格标记来划分结构的文本格式。例如，让 LLM 输出 API 提取结果时，我们不要求 JSON，而是这样的格式：

```
<endpoint>
  <method>POST</method>
  <path>/api/users</path>
  <description>Create a new user.</description>
</endpoint>
<endpoint>
  <method>GET</method>
  <path>/api/users</path>
  <description>List users</description>
</endpoint>
```

### 为什么有效？
1. **局部容错**：一个 `<endpoint>` 块内部出错，不会影响其他块的解析。只要我们能根据开始/结束标签提取片段，再对片段内做修复或按字段提取，比修复整个 JSON 容易得多。
2. **模型熟悉的格式**：预训练数据中大量 XML/HTML，LLM 对标签配对、自闭合等规则掌握得比 JSON 的逗号地狱好。
3. **流式解析友好**：在 token 流式到达时就能开始提取，无需等到完整结构闭合。当看到 `<endpoint>` 开始时就可以缓存，看到 `</endpoint>` 就落盘一个完整记录，即使后续输出中断，已完成的块依然可用。
4. **混合内容无压力**：模型可以在标签块前后添加自然语言解释、思考过程，下游只提取需要的标签即可。

### 实现步骤（以 OpenClaw 插件为例）

1. **定义标签模式**  
   与下游解析约定好：每个实体用什么标签包裹，内部用哪些子标签。例如：`<task><id>...</id><summary>...</summary></task>`。

2. **写 Prompt 时给示例**  
   在 system prompt 或 few-shot 中展示完整的标签输出，而不是 JSON。强调“请严格使用标签格式，每个 `<task>` 块独立出现”。例如：

   ```
   输出格式：
   <task>
     <id>1</id>
     <summary>用户请求重置密码</summary>
   </task>
   <task>
     <id>2</id>
     <summary>系统执行校验流程</summary>
   </task>
   ```

3. **后处理解析器**  
   不依赖完整 XML 解析器（因为模型可能输出不规范的 XML）。可以使用正则或简单状态机，按 `<tag>` 和 `</tag>` 提取内容。对于字段值，可再做 trim、转义处理。如果内部再用标签嵌套，递归处理即可。

   示例 Python 伪代码：
   ```python
   import re
   def parse_tasks(text):
       tasks = []
       for match in re.finditer(r'<task>(.*?)</task>', text, re.DOTALL):
           block = match.group(1)
           id_match = re.search(r'<id>(.*?)</id>', block)
           summary_match = re.search(r'<summary>(.*?)</summary>', block)
           if id_match and summary_match:
               tasks.append({
                   'id': id_match.group(1).strip(),
                   'summary': summary_match.group(1).strip()
               })
       return tasks
   ```

4. **在 OpenClaw 工作流中集成**  
   由于 OpenClaw 采用工具调用和消息流式处理，我们可以在收到模型响应后，将 raw content 传入自定义的后处理节点，把标签块转化为结构化数据并写入上下文，供后续步骤使用。还可以设计一个“容错回退”：如果某个块解析失败，跳过或保留原文，并把错误信息传回 Agent 进行修正。

## 踩坑点

- **标签名称冲突**：模型可能在普通文本中也使用了同样的标签名。建议使用前缀或有点特殊的名称，例如 `<oc-task>`，降低冲突概率。
- **自闭合与属性**：避免让模型使用 `<tag attr="value" />` 这种复杂写法，尽量用开闭标签包裹值。属性解析会增加复杂度，模型也容易写错。
- **嵌套层级**：可以嵌套，但不要超过两层。太深的嵌套会让模型丢失闭合标签。
- **字段值中的标签符号**：如果字段内容可能包含 `<` 或 `>`，需要在 prompt 中要求模型进行转义（如 `&lt;` `&gt;`），并在后处理中反转义。
- **输出截断**：如果在长列表中间被截断，最后一个不完整的标签块应被丢弃，已完成的块照常使用。所以设计时每个块应是自包含的。

## 可复用建议

- **先从 JSON 迁移到标签格式的成本很低**。只需修改 prompt 和后处理脚本，不需要改变 workflow 的核心逻辑。
- **建一个小型标签解析工具库**，可以复用：通过配置 schema（标签名、子标签名、是否列表）自动生成解析器。类似一个轻量级的“容错结构化提取器”。
- **混合使用**：有些字段确实需要结构化的值（如数组），可以在标签内部再用简单的 JSON 片段，但外层用标签保护。这样即使内部 JSON 出错，也只影响单个字段，降低风险。
- **测试策略**：用同一段长文本，分别跑 JSON 模式和标签模式几十次，比较可解析的成功率和一致率。我们实践下来，标签模式的第一次成功解析率明显高于 JSON。

## 总结

LLM 长文输出下的结构化提取，追求 100% JSON 正确率得不偿失。标签格式利用了大模型对标记文本的自然偏好，在容错、流式解析、混合内容方面具有显著的工程优势。在 OpenClaw/Agent 这类自动化链路中，这种“宽容解析”的思维比盲目追求格式严格更重要。下次当你的 Agent 因为坏 JSON 卡住时，不妨试试换成标签格式，让管道重新畅通。
