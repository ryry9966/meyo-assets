## 背景

在内容多平台分发的场景里，微博超话是一个容易被低估但实际量级不小的渠道。我维护着一个垂直领域的日更账号，每天需要把其他平台生成的图文同步到指定超话。手工操作重复且容易漏，于是决定用 OpenClaw 的插件机制搭一条自动同步流水线，利用 Agent 决策何时发、发什么、如何跟踪结果。

这个同步流程本身不复杂，真正难的是图片上传的隐蔽限制、频繁触发限流后的重试策略，以及必须可追溯的“发布状态归档”。以下记录整个实践过程和踩坑点，希望对需要对接微博开放能力或构建类似同步管线的同学有所参考。

## 问题拆解

我们将需求拆成三个核心问题：

1. **图片上传**：微博超话发帖需要先上传图片获取 `pid`，接口有严格的格式、大小限制，且报错信息往往不明确。
2. **限流处理**：连续发布或上传会触发 429 或“操作太频繁”，需要一套可配置的重试与等待机制，不能简单阻塞整个任务队列。
3. **状态归档**：每次发布任务需要有明确的最终状态（成功/失败/限流放弃），并能溯源接口返回的原始信息，否则重复排查会耗费大量精力。

这些问题通过一个 OpenClaw 自定义插件串联起来：插件内封装了上传、发布与状态持久化逻辑，对外暴露为可被 Agent 调用的工具，让决策层只关心“何时调用”而不用关心“如何重试”。

## 做法与步骤

### 1. 插件骨架：从 OpenClaw 的 Tool 定义开始

基于 OpenClaw 的插件模版创建一个 `weibo-sync` 插件，定义了三个工具：

- `upload_image_for_weibo`：接收本地图片路径，返回 `pid`。
- `post_to_topic`：携带文本内容和一组 `pid` 发布到指定超话。
- `query_task_status`：根据任务 ID 查询归档状态，用于 Agent 做后续决策。

每个工具内部不直接做重试，而是委托给一个统一的 `Executor`，这为限流策略的统一管理打下基础。

### 2. 图片上传的隐蔽限制与处理

微博图片上传接口 `/photo/upload` 看似标准，实际有不少约束：

- **格式陷阱**：JPG/PNG 都支持，但 JPEG 必须为非渐进式（progressive JPEG 会静默失败，返回的 `pid` 无法用于发布）。用 `pillow` 读图时自动检测，如果是 progressive 则重新保存为 baseline。
- **尺寸与大小**：单张 ≤ 5MB，长宽不超过 4096px。超过自动等比压缩至安全阈值。
- **防盗链与 Referer**：上传接口需要携带 `Referer` 头，并且必须是 `https://weibo.com` 域，否则会报 302 到错误页。直接在请求中设置固定 header。
- **Cookie 与登录态**：超话发帖需要有效的登录 cookie，设置定时刷新机制，将 token 存储在插件配置中，Agent 可触发刷新工具。

对这些处理的封装，让上传工具变成“扔一张图进去，吐一个有效 `pid`”，大幅减少调用方的顾虑。

### 3. 限流策略：识别信号与退避重试

限流是最大的坑。微博的限流并不是每次都返回 429，有时是：

- 发布接口返回 `{"ok":0,"msg":"操作太频繁，喝杯茶休息一下吧"}` 且 HTTP 200。
- 上传接口返回空 `data`，但无明确错误码。

针对这些，我们在执行器层实现了一个基于令牌桶思想的自适应退避器：

- 维护一个 `last_request_time` 记录上一次请求时间戳，强制两次请求间隔至少 1.5 秒。
- 若遇到“频繁”关键词或 `ok=0`，递增 `backoff_level`，等待时间 = `base_delay * 2^(backoff_level)`，上限 5 分钟。
- 任何工具调用抛出限流错误时，整个发布任务置为 `RATE_LIMITED` 中间状态，并在等待后自动尝试恢复，而不是直接标记失败。
- 同时维护一个全局的 `rate_limit_until` 时间戳，当一级退避触发后，同账号的其他任务全部暂停，避免雪崩。

这样，当 Agent 连续调度多个发布任务时，同一账号不会互相踩踏，重试过程可控且可观测。

### 4. 状态归档：一棵清晰的审计树

为了做到每次发布都有迹可循，我们在 SQLite 中设计了两张表：

- `sync_jobs`：记录任务级信息（任务ID、目标超话、文本内容摘要、创建时间、最终状态、重试次数、错误信息）。
- `job_details`：记录每个子步骤（上传图片、发布）的请求与响应细节（包括接口原始返回、请求耗时、使用的 pid 列表等）。

所有接口响应，无论成功与否，全部以 JSON 存入 `details` 字段。同时设置一个定时清理任务，将超过 30 天的成功记录归档到压缩的 `.parquet` 文件供离线分析——既不浪费磁盘，又保留长期数据。

Agent 可以通过 `query_task_status` 查看任何一条同步记录，甚至从中分析出哪个时间段限流最严重，从而调整调度间隔。

## 踩坑点整理

- **Progressive JPEG 上传无声返回**：没有错误，但导致发布时图片不显示。通过强制转 baseline 解决。
- **Cookie 过期无明确提示**：发布接口会返回一个看似成功的响应，但帖子在超话页面不可见。增加了 Cookie 有效性检查步骤。
- **限流与反爬策略耦合**：有时同一 IP 多次请求会被封 IP，最终在 VPS 上配置了代理池轮换，将网络层与业务层解耦。
- **状态更新并发问题**：Agent 可能同时发起多个发布任务，更新同一账号的 `rate_limit_until` 时出现竞争。通过 SQLite 的 `IMMEDIATE` 事务和简单的文件锁解决。

## 可复用建议

- **将重试逻辑从业务工具中抽离**：使用装饰器或中间件统一处理限流异常，易于调整且不影响工具代码的可读性。
- **结构化归档比日志更重要**：不要只在日志里打印接口响应，结构化存入可查询的表，未来排查问题时能省下大量时间。
- **为 Agent 暴露状态查询工具**：让大模型能主动判断重试是否值得，而不是硬编码逻辑。比如当返回 `RATE_LIMITED` 且 `retries > 3` 时，Agent 可决定放弃该任务，改为手动处理。
- **图片预处理器做成独立服务**：如果同步量增大，图片压缩、格式转换可以挪到消息队列中异步处理，避免阻塞上传流程。

## 总结

微博超话同步看似是个简单的自动化场景，但图片上传的细节、限流的鬼魅表现、以及状态可追溯的要求，把它变成了一个典型的工程化问题。借助 OpenClaw 的插件体系，我们可以将不同关注点分离到独立工具中，再由 Agent 统一编排，既保持了灵活性又不失稳定性。

自动化不是消灭所有人工，而是让重复性决策和重试变得可追溯、可恢复。记录好每一次发布的状态，就是在为未来的自己节省数小时的排障时间。
