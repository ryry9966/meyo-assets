# OpenClaw 定时任务防重入锁：为什么 5 分钟任务会撞车

## 背景：定时器带来的“意外并发”

在 OpenClaw 里用定时任务插件驱动 Agent 或 MCP 工具链是一种很自然的自动化模式。比如你想每 5 分钟查一次数据源，然后通过 Agent 清洗后写入共享存储，或者定时调用一个耗时的批量处理工具。

按照直觉，Cron 每隔 5 分钟触发一次，任务理应一个一个顺序执行。但实际情况往往是：上一个实例还在跑，下一个调度又触发了，结果同一种任务的两个（甚至更多）实例同时运行，相互踩踏。这就是标题里说的“5 分钟任务会撞车”。

这并不是 OpenClaw 特有的问题，但 OpenClaw 作为任务编排中枢，会把这种并发风险直接放大到 Agent 调用和 MCP 资源访问上，稍不注意就会导致 API 限流、脏数据、重复写入甚至是死锁。

## 问题表现：一个具体例子

我在一个舆情监控的工作流里设置了每 5 分钟运行一次的任务：抓取某数据源 → 交给 Agent 提取结构化字段 → 写数据库。任务正常情况下可以在 3 分钟左右完成，5 分钟间隔绰绰有余。

但有一次数据源返回延迟到了 8 秒，加上 Agent 调用了外部模型，出现一次偶发重试，整个任务跑了将近 7 分钟。此时第二个定时周期已经到来，OpenClaw 又启动了一个新实例，两个实例同时去抓数据、调用模型、写库。结果：

- API 配额瞬间打满，后续请求被限流。
- 数据库中出现大量重复行，因为两个实例拿到的数据高度重叠。
- Agent 模式异常终止，部分 MCP 工具因为并发调用报错退出。

这种问题在开发阶段几乎不可见，一到生产环境，网络波动、上下游抖动一上来，就变成周期性“自残”。

## 根因：调度周期 ≠ 执行耗时

任何调度器都只负责“到点就触发”，它不会自动判断上一次是否结束。在 OpenClaw 里，如果一个工作流的 `cron` 设置为 `*/5 * * * *`，而工作流执行时间超过 5 分钟，重叠运行就是必然的。即使你都用异步、非阻塞设计，资源竞争依然存在。

更要命的是，在 OpenClaw 这类以 Agent 调度为特色的平台上，任务的执行时长往往是不可预测的 —— 网络调用、模型思考时间、外部工具响应时间都会让总耗时波动。你把间隔调到 10 分钟，下次碰上一个慢模型可能又撞车。静态区间不能解决根本问题，必须引入防重入锁。

## 做法：用分布式锁实现互斥

OpenClaw 的工作流节点天然支持自定义脚本和外部工具调用，所以实现一把轻量级防重入锁并不复杂。核心思路：在任务开始前先获取一把锁，只有拿到锁的实例才允许继续执行，任务完成后释放锁。

### 基于 Redis 的实现步骤

1. **选定锁标识**  
   对每个定时任务定义一个唯一键，格式推荐 `lock:task:{workflow_name}` 或 `lock:task:{task_uuid}`，确保同一逻辑任务共享同一把锁。

2. **获取锁**  
   使用 Redis 的 `SET key value NX EX seconds` 命令原子性创建键并设置过期时间。示例如下（假设 OpenClaw 节点可运行 JS/Lua）：
   ```
   const lockKey = "lock:task:news_monitor";
   const lockValue = Date.now() + Math.random(); // 唯一持有者标识
   const acquired = await redis.set(lockKey, lockValue, "NX", "EX", 300);
   if (!acquired) { return skip(); }
   ```

3. **安全释放锁**  
   一定要校验当前实例就是锁的持有者，防止误删其他实例刚获得的锁。可以用 Lua 脚本原子判断：
   ```
   if redis.call("GET", KEYS[1]) == ARGV[1] then
       return redis.call("DEL", KEYS[1])
   else
       return 0
   end
   ```
   在 OpenClaw 工作流的 finally 分支（或 node 的 onError 流程）中执行这套释放逻辑。

4. **锁超时设计**  
   过期时间需要覆盖任务可能的最长执行时间。如果任务历史最大耗时 8 分钟，锁 TTL 可以设成 600 秒（10 分钟），给异常处理留出安全窗口。宁可保长也不要因为锁提前过期而失去保护。

5. **无锁时的处理策略**  
   最简单的是直接跳过这次调度，下一轮再试。也可以加入短暂延时重试，但要注意避免放大后续拥堵。

### 替代方案：OpenClaw 内部状态标记

如果你用的是一个单实例 OpenClaw 部署，也可以用内存标志位或本地文件锁。但不推荐，因为将来一旦扩展为多实例或多工作进程，本地互斥就会失效。分布式锁从一开始就解决集群问题。

## 踩坑点

1. **锁超时比任务实际跑的时间还短**  
   这是最常见的问题。任务还在跑，锁自己过期了，后续实例进来拿到锁，再次导致并发。**解决方案**：定期（如任务运行每 1 分钟）为锁“续期”刷新过期时间，或用 Redis `EXPIRE` 延长，但要防止无限续期造成死锁，可以用最大续期次数限制。

2. **本地开发多用单线程，锁根本不会撞**  
   本地跑得好好的，一上线就炸。因为在开发环境都是顺序执行，锁可有可无。建议在本地通过环境变量模拟多实例，或者用工具同时触发两次任务来验证。

3. **误删其他实例的锁**  
   有些实现直接用 `DEL key` 释放锁，这在并发下会误杀后续实例刚获取的锁。务必用 Lua 原子删除。

4. **网络闪断导致锁释放失败，任务永久阻塞**  
   虽然 Redis 锁最终会过期恢复，但如果是关键任务，最好加入失败重试和告警。

5. **对同一 workflow 的不同参数实例未区分锁键**  
   有的任务 timer 带不同参数（如不同项目 ID），需要生成独立的锁键，否则一把锁会误杀合法并行任务。

## 可复用建议

- **锁键必须有 namespace**：用 `{env}:{service}:lock:task:{name}` 隔离环境和功能。
- **TTL 根据实际耗时统计动态调整**：可以取 p99 执行时长的 1.5 倍作为锁超时，写入配置中心。
- **兜底释放一定要放在 finally 逻辑中**：无论正常结束、异常中断还是节点超时，都必须走到锁释放。
- **双检查**：在获取锁后、执行业务前，可以再查一次状态（如数据库状态），降低重复执行概率。
- **在 OpenClaw 中抽象成公共节点**：把“获取锁→执行任务→释放锁”封装成一个可复用的子工作流或工具，避免每个场景重复实现。

## 总结

定时任务防重入锁是自动化流水线从小规模实验走向稳定交付的第一道防线。在 OpenClaw 的生态里，它保护的不只是计算资源，更关键的是 Agent 调用链路和 MCP 工具的稳定可用。一把轻量的 Redis 锁、一个对锁键的唯一命名规约、以及周全的异常释放策略，就可以让“5 分钟任务撞车”这类问题在生产环境里消失。

**简单，但容易漏掉；加了，就能省掉很多半夜的告警。**
