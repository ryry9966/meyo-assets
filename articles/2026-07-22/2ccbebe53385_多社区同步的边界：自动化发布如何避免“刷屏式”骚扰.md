## 背景：一人维护多社区，自动化的诱惑与代价

做过开源项目、技术产品或者独立开发的同学，大概率都会遇到同样的困境：内容产出一篇，需要同步到 GitHub Discussions、Discord、Telegram 频道、知乎、V2EX、开发者社区，甚至还要转成推文发 Twitter。手动操作重复、低效，于是很自然会想到自动化——一条命令触发，所有渠道同时发出。

但这个“同时”，恰恰是问题所在。当你作为社区成员时，突然在 5 个平台看见同一段话、同一时间戳、甚至同一个错别字，观感只有两个字：**刷屏**。平台算法也会把这种行为判定为机器操控，轻则降权，重则封禁。

真正需要的不是“一键群发”，而是有策略、有边界、能适配社区调性的自动化发布。这篇文章就基于 OpenClaw 的 Agent 能力，聊聊如何设计这样一套系统，让它既提升效率，又不招人烦。

## 问题拆解：为什么自动化发布容易变成刷屏

典型的翻车现场有三个特征：

1. **时间高度集中**：所有平台在同一时刻收到同样的内容，社区成员在多个渠道产生重复信息流。
2. **内容完全一致**：没有针对平台语境的调整，长文扔到微博超限，emoji 丢到技术论坛显得不专业。
3. **频率不可控**：自动化脚本每次变更都触发，一天能在同一频道发七八条更新日志，比广告还让人想退群。

这些问题的本质，是缺少一个**发布决策层**。传统 CI/CD 或 webhook 只管“能不能发”，不管“该不该发”。而 Agent + MCP （Model Context Protocol）的组合，正好可以补上这一层判断。

## 做法与步骤：用 Agent 构建有判断力的发布调度器

以下方案基于 OpenClaw 的 Agent 框架，配合 MCP 工具实现。整个流程不是“发布工具”，而是一个**发布仲裁器**。

### 1. 定义平台画像（Platform Profile）

为每个目标社区定义一份结构化配置，示例：

```yaml
platform: discord
channel: announcements
max_posts_per_day: 2
min_interval_minutes: 120
allowed_windows:
  - "09:00-12:00"
  - "14:00-18:00"
timezone: Asia/Shanghai
content_rules:
  max_length: 2000
  allow_emoji: true
  tone: casual
```

这样就把“能不能发、什么时候发、发成什么样”统一成了可查询的规则集。

### 2. 设计发布 Agent 的决策链路

Agent 并不直接调用发布 API，而是作为仲裁者。收到一条待发布内容后，执行以下 checklist：

- 解析内容元信息：类型（公告/技术帖/碎碎念）、紧急度、是否有重复历史。
- 对每个候选平台，检查当前时间是否在 `allowed_windows` 内。
- 检查当天已发布次数与最近一次发布间隔，未通过则自动进入**等待队列**，而非强行发送。
- 通过 MCP 工具（如一个时间查询 server 和本地日志分析工具）获取判断依据，避免 Agent 幻觉。

通过 MCP 的好处在于，Agent 不编写平台 SDK，只做自然语言决策，实际执行命令由 tool 完成，安全性更高。

### 3. 内容变体生成，但保持“可控”

不是所有平台都要看到同样的字句。Agent 根据 `content_rules` 生成变体：

- 对 Discord 保持轻松，但对 GitHub Discussions 删减语气词、添加复现步骤。
- 对 Twitter 自动生成一个 280 字符内的摘要，附带主帖链接。
- 变体生成后，写入日志，并由人工可选的审批步骤确认（例如在本地终端输出 diff，等待 y/n）。

这里不建议让 Agent 凭空发挥，语境偏移容易被当成账号被盗。规则约束下的微调，风险可控。

### 4. 速率限制器：最后一道防线

即使规则判定可以发，仍然在工具层施加全局速率限制。例如封装一个 `publish_to(platform, content)` MCP tool，内部实现基于滑动窗口的限速：1 小时内全局发布不超过 6 次，单平台不超过 2 次。超出直接返回错误原因，Agent 可以据此将任务重新排队。

## 踩坑记录：这些地方最容易翻车

- **发布时间窗口遇到跨时区 DST**：配置中的 `timezone` 必须在每次比较时动态计算当前偏移，而不能写死 UTC+8。一个小技巧是使用 `zoneinfo` 库并始终基于平台所在地的 `now()` 做判断。
- **API 频率限制远比文档写的严格**：Twitter、Telegram 等平台除了明确给出的 Rate Limit，实际还会根据行为模式加隐式限制。即便自己遵守规则，连续发布仍可能触发。**随机延迟 5-15 秒**是最低成本的保护手段，Agent 在决策通过后，再 sleep 一个随机窗口后才调 tool。
- **有群管理员会手动移动或删除帖子**：自动化系统需要感知“已发布”状态的真实性。如果只依赖 API 返回 success 就标记完成，容易造成日志记录失真。最好在发布后 10 分钟再通过查询 API 确认消息存在，若不存在则告警而非重发。
- **变体生成导致链接追踪混乱**：如果变体里自动修改了链接参数（比如加了不同 utm_source），需要确保唯一映射关系，否则后续数据复盘会非常痛苦。

## 可复用建议：适合 OpenClaw 生态的模块化实践

1. **MCP 工具分层**：把“发布执行”和“发布决策”拆开。发布决策由 Agent 完成，发布执行由稳定、无状态的 MCP server 完成，不在 Agent 内写重试与鉴权逻辑。
2. **将平台画像作为知识库注入**：通过 OpenClaw 的 memory 或知识库功能，将平台规则持久化，避免每次对话都要重新交代。
3. **引入“冷静期”模式**：对于非紧急内容，默认所有渠道延迟发布至少 30 分钟。这 30 分钟里如果发现问题，可以人工撤回队列消息，避免事故扩散。
4. **日志即审计**：所有决策原因（时间窗口未通过、频率限制触发、等待审批）输出结构化日志，做成一个简单的 dashboard，方便回溯为什么某条内容没有出现在预期平台。

## 总结

自动化发布的价值不在于“快”，而在于“永远不用惦记”。当系统懂得在正确的时间、用合适的语气、以克制的频率出现时，社区成员感受到的不是刷屏，而是持续、靠谱的存在感。用 Agent + MCP 做一层决策缓冲，远比写一个粗暴的群发脚本划算得多。

与其被平台算法惩罚后再补救，不如在设计之初就设定好边界——这就是工程上常说的：克制是一种高级的能力。
