## 背景

最近在维护一套基于 OpenClaw 的任务调度管线，上游插件负责向 Gateway 推送待消费的事件，Gateway 再分发给下游 Agent。一切看上去都正常运行——直到某天所有任务突然卡在「待处理」状态，监控没报错，只是队列不往下走了。

排掉这个坑花了我两小时，最后定位在一个看似无害的小细节：插件传出去的 `appId` 应该是字符串，结果因为上游序列化问题，变成了数字类型，Gateway 的 schema 校验静默失败，消息既没被消费，也没进死信队列。

这篇文章把排查过程、分析和修复方案记录下来，给同样会在 OpenClaw 生态里写插件的朋友做个参照。

## 问题现象

- 插件侧日志显示消息发送成功（HTTP 201），但 Gateway 侧没有任何消费记录。
- 开放的 `/health` 和 `/metrics` 端点都正常，看上去 Gateway 本身没挂。
- 重新触发事件依然无效，死信队列里也找不到这些消息。
- 用户侧的感知就是「定时任务没跑，也没有任何通知」。

如果没有提前打好结构化日志，这种问题最容易变成猜谜。

## 排查步骤

### 1. 确认 Gateway 接收到了请求

先看 Gateway 的 access log，发现插件发过来的请求已经到达，返回码确实是 201，但 payload 并没有进入后续的 dispatcher 模块。这说明错误发生在请求体校验或反序列化阶段。

### 2. 开启 Gateway 校验日志

OpenClaw 的 Gateway 默认不会把 schema 校验失败的信息打到应用日志里，需要临时在配置中打开：

```yaml
gateway:
  schema_strict: true
  log_validation_errors: true
```

重启后，日志里马上出现了一行：

```
Validation error: /appId: expected string, got number
```

再看插件发送的原始 JSON：

```json
{
  "appId": 1042,
  "eventType": "schedule.trigger",
  "payload": { ... }
}
```

问题已经很清楚了：定义上 `appId` 是 `string`，但这里传的是 `number`。

### 3. 溯源字段定义

在插件与 Gateway 共用的 schema 定义里，`appId` 的类型被标记为 `string`，因为早期的设计允许非纯数字的 app 标识（比如带前缀的 `app-1042`）。插件的数据源来自一个内部的配置中心，返回的 JSON 中 `appId` 确实是数字，而发送逻辑直接用 `JSON.stringify` 原样透传，没有做类型转换。

这种场景在弱类型语言的上下游对接中很容易出现，尤其是在跨团队协作时。

## 修复方案

修复分两层：

**临时止血**：在插件的发送函数中显式转换类型。

```typescript
const message = {
  appId: String(rawConfig.appId),
  eventType: 'schedule.trigger',
  payload: transformed,
};
```

**长期治理**：在共享的 schema 仓库中加上转换层，并打开 Gateway 的 `coerce-types` 能力（OpenClaw 版本 >=2.3 支持），对数字→字符串做自动转换。

```yaml
gateway:
  schema_strict: false
  coerce_types: true
```

同时，把 `appId` 的 schema 定义加上一条显式注释，避免再次出现分歧：

```json
{
  "appId": {
    "type": "string",
    "description": "应用标识，字符串类型，即使数字也要以字符串传递"
  }
}
```

## 踩坑点小结

1. **HTTP 201 不等于消息被处理**。Gateway 在请求体校验失败时，默认行为是返回 201 并丢弃消息（不进入死信）。这个设计是出于性能考虑，但会让调用方误以为一切正常。
2. **schema 校验失败默认不记录**。需要显式开启 `log_validation_errors`，否则大量静默丢消息。
3. **数字与字符串的类型混淆是高频故障点**。尤其在 JSON 序列化透明过度的系统中，类型信息很容易丢失。
4. **死信队列不一定能兜底**。如果校验直接在接入层失败，传统死信机制可能还没启动。

## 可复用建议

- **在接入 Gateway 的插件侧强制做一层类型保护**。不要相信上游数据源的字段类型一定与 schema 一致，`toString()` 并不过分。
- **主动开启 `log_validation_errors`**，可以把它加进生产默认配置中，除非对日志量有极严苛的要求。
- **在集成测试中加入 schema 合规检查**。模拟一次完整的消息流，检查 Gateway 的消费日志，而不只是判断 HTTP 状态码。
- **利用 OpenClaw 的 `coerce_types` 能力**，但仅作为最后防线，不建议完全依赖它，因为类型混淆在复杂对象嵌套时可能产生意料之外的行为。
- **为 `appId` 这类关键字段写清晰说明**，放在共享 schema 仓库中，纳入团队 review checklist。

## 总结

`appId` 的数字类型问题看起来很小，但在 OpenClaw 的 Gateway 管道中，一旦校验层静默丢弃，排查链路会比较隐蔽。因为这个坑踩得够深，我们用一次故障演练把整个团队对「消息成功」的定义纠正了一遍：不再只看 HTTP 状态码，而是在核心链路上抓消费记录作为唯一成功指标。

插件写起来快，但涉及消息传递时，数据契约的严格性会直接决定调试成本。把类型边界钉死，是在自动化工程里的最小成本长期保险。
