## 背景

在维护一个技术内容聚合流时，我们希望通过 OpenClaw 将每日精选文章自动同步到微博超话。整个链路大致为：RSS/API 抓取 → 内容去重与格式化 → 生成配图 → 发布到超话。看上去是一条标准的自动化流水线，实际落地时，图片上传、接口限流和发布状态管理成了最耗精力的三个环节。本文记录在 OpenClaw 生态内解决这些问题的过程，适合正在用 Agent/MCP/自动化脚本构建内容管线的同学参考。

## 问题拆解

1. **图片上传**：微博发布带图微博需要先通过 `statuses/upload` 拿到 `pic_id`，再调用 `statuses/update`。官方对图片格式、大小、尺寸有隐性约束，文档描述不够细致。
2. **限流**：开放平台有应用级和用户级频率限制，超话还有隐形的“灌水”检测。短时间内发布过多内容会触发验证码甚至禁言。
3. **状态归档**：不能让同一篇文章被重复发布。内容源可能更新、删改，归档方案要能识别“已处理过的实体”，而非仅靠标题判重。

## 做法与步骤

### 1. 封装微博 API 为可复用的 Tool

在 OpenClaw 中，我们用 Python 编写了一个 MCP 工具 `weibo_publisher`，暴露两个 Action：

- `upload_image(image_path)` → `pic_id`
- `post_status(text, pic_id, topic)` → `weibo_id`

内部使用 `requests` 直接调用微博 V2 API，不依赖第三方 SDK。认证使用 `access_token`，通过定时刷新机制保证长期有效。

关键代码片段（图片上传）：

```python
def upload_image(access_token, image_path):
    url = "https://api.weibo.com/2/statuses/upload.json"
    with open(image_path, 'rb') as f:
        files = {'pic': f}
        data = {'access_token': access_token}
        resp = requests.post(url, data=data, files=files, timeout=30)
    resp.raise_for_status()
    return resp.json()['pic_id']
```

### 2. 图片预处理的踩坑与规范

- **格式限制**：接口文档说支持 jpg/gif/png，实际测试 webp 直接报“图片格式不支持”。所以我们在工具里强制将任何图片转为 JPEG。
- **大小限制**：官方标注小于 5MB，但超过 2MB 时容易超时导致上传失败。统一用 Pillow 将长边限制在 1280px，质量设为 85，单张控制在 1MB 以内。
- **尺寸下限**：太小（如宽度<200px）会返回“图片尺寸不符合要求”，但错误码模糊，容易误判为 token 失效。我们在预处理中加了一个断言：宽高至少 300px。

### 3. 限流与重试策略

微博接口的 `X-RateLimit-Remaining` 头部并不可靠，发布超话时还受“用户级别反垃圾”限制。我们的策略：

- **发布间隔**：硬性限制每小时不超过 5 条，且每次发布后休眠随机 180–300 秒。用 Redis 记录上一次发布时间戳。
- **错误码处理**：
  - `10022` / `10023`（含有敏感词/超限）：跳过当前内容，标记到审核队列。
  - `20019`（重复内容）：触发归档更新，将该内容 ID 与已有记录关联，避免后续再次尝试。
  - `20104`（验证码）：立即停止当前批次，通知人工介入。
- **重试**：只对网络超时和 `5xx` 错误进行最多 3 次指数退避重试，其余错误直接归档为失败。

### 4. 状态归档设计

使用 SQLite 存储发布状态，表结构：

```sql
CREATE TABLE publish_log (
    source_id TEXT PRIMARY KEY,
    weibo_id TEXT,
    status TEXT,          -- 'success','failed','skipped'
    error_code INTEGER,
    published_at TIMESTAMP
);
```

每次获得新内容时，先以 `source_id`（如 RSS guid 或 API 返回的 uuid）查询是否已存在。若状态为 `success`，直接跳过；若为 `failed` 且错误码为不可重试类型（如敏感词），也跳过；对于临时性错误（如网络超时），允许重试。这样既避免了重复发布，又能防止死循环重试。

### 5. 集成到 OpenClaw 工作流

在 OpenClaw 的 Skill 中，我们定义了一个定时任务（每 6 小时执行），完整流程：

1. 调用内容源获取新文章列表。
2. 过滤已归档的 `source_id`。
3. 逐条通过模板生成微博文案（含超话标签）。
4. 从文章配图或截图生成一张 JPEG 封面图。
5. 调用 `weibo_publisher.upload_image` 上传。
6. 调用 `weibo_publisher.post_status` 发布。
7. 写入 `publish_log`，同时将链接与状态通过 Webhook 推送到团队飞书群。

全程记录详细日志，便于回溯和监控。

## 可复用建议

- **图片处理独立成函数**：不要和发布逻辑耦合，方便单独测试和调参。
- **限流控制放在调度层**：利用 OpenClaw 的 Cron 任务天然间隔，再加一次额外休眠，比依赖 API 限流头更可靠。
- **归档保留扩展字段**：除了 `source_id`，可加上 `source_updated_at`，方便未来实现“原文更新后重新发布”功能。
- **监控失败率**：接入简单的飞书/钉钉通知，当连续 3 次任务中失败率超过 30% 时发送告警，可以快速定位是否 token 过期或触发风控。

## 踩坑速查

- **图片格式鬼故事**：Canvas 生成的 image/webp 后缀正确，但实际编码不符，上传必错。统一转换 JPEG 彻底解决。
- **错误码 10006**：官方解释是“缺少图片”，实际场景是图片字段名错误或文件句柄被提前关闭，检查 `files` 参数中的 key 是否为 `'pic'`。
- **限流误判**：有时看似触发频率限制，实际是超话管理员设置了发帖权限（如仅限粉丝）。发布前可用 `statuses/update` 带 `visible` 参数发一条私密微博测试权限。
- **归档数据一致性**：不要仅用文本 hash 判重，内容源可能只改了一个标点，用 `source_id` 作为主键最稳妥。

## 总结

将微博超话同步做成一条稳定运行的自动化管线，核心不在于“调用 API”本身，而在于对边界条件（图片格式、限流、异常码）的充分防御和可观测的状态归档。在 OpenClaw 框架下，将发布能力封装为 MCP Tool，配合 SQLite 做轻量状态管理，可以让整个流程既清晰又健壮。这套思路同样适用于其他社交平台的自动化内容分发。
