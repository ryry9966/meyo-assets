# 多社区同步的边界：用 OpenClaw Agent 建一条“知进退”的发布流水线

## 背景：一次推送，多处战场

维护一个开源项目或社区，常常需要同时照看 Discord、Telegram、Twitter、GitHub Discussions，甚至 Slack 和论坛。每次版本更新或公告，最怕两件事：手动搬运到多个平台，遗漏或格式错乱；而上了自动化脚本，稍不注意就成了“消息轰炸”——同一条内容在五分钟内刷遍所有频道，用户体验直线下降。

我们需要的不只是“群发机器人”，而是一个能判断时机、合并信息、尊重平台差异的**发布代理**。这也正是 OpenClaw + MCP + Agent 模式的用武之地。

## 问题定义：自动化为何会变成“信息喷子”

多数脚本只关注“能发出去”，却不管“该不该发”和“怎么发合适”。典型问题包括：

- **没有冷却期**：同一 commit 的 CI 状态变更会触发多条告知，五分钟内连发四次。
- **无去重机制**：dev 分支推送一条，main 分支合并又一条，内容高度重叠。
- **忽略平台特征**：280 字的 Twitter 硬塞长文，Discord 的 embed 格式丢失，链接不会被聚合。
- **紧急与普通不分**：重要安全公告被普通更新埋没，或反之，安全修复也需要遵守发布窗口。
- **缺乏人工覆盖**：运营人员临时追加消息时，被自动化规则吞掉或冲突。

## 做法：用 OpenClaw 搭一条智能发布流水线

### 整体架构

我们将发布过程拆成 4 个阶段，全部在 OpenClaw 中编排成一个 Agent Skill：

1. **内容源接入**  
   通过 MCP 连接 GitHub Webhook、CI 事件、RSS 源，或社区内的人工提交通道（例如 `/announce` 指令）。所有内容统一为标准化结构：摘要、正文、标签、紧急度（0-3）。

2. **去重与合并**  
   Agent 调用一个基于文本相似度的去重服务（可用 embedding + 向量数据库）。最近 30 分钟内已经发布过的内容，相似度超过 0.85 的视为重复。重复时策略为：
   - 如果是完全同源（同一 commit），直接丢弃；
   - 如果是相似但补充性强（如 CI 阶段更新），则合并进上一条消息的更新笔记，而非另发新帖。

3. **策略引擎**  
   这是防止刷屏的核心。策略引擎维护一组规则：
   - **冷却窗口**：同一频道最少间隔 15 分钟。若紧急度为 3（如安全公告），可绕过。
   - **频率上限**：任一平台每小时不超过 4 条推送，全天不超过 12 条（可配）。
   - **优先级调度**：高优先级插入发送队列头部，但不会打断正在进行的普通发布，而是下一轮优先。
   - **平台适用性检查**：如果本次内容标记为“仅开发者”，则不推送到 Twitter 这种泛用户平台。
   
   规则用 OpenClaw 的 `Memory` 组件记录每条发布的时间戳，并用 `Tool` 调用规则检查器。

4. **多平台适配**  
   MCP 提供各平台的发布接口（Discord webhook、Telegram bot、Twitter API 等）。适配层根据平台特性生成不同版本：
   - Twitter：从正文提取关键词生成 2-3 句，附带链接和 hashtag。
   - Discord：生成 embed，正文分段，支持颜色条（普通绿色/警告橙色/安全红色）。
   - Telegram：保持 MarkdownV2 格式，但去掉不支持的 complex embed。
   - 论坛/GitHub Discussions：完整 Markdown，不截断。
   
   所有适配由 Agent 调用的 `platform_adapter` skill 完成，维护一个模板库。

### 运行流程

1. 新内容到达 → 规范化 → 去重检查 → 若合并，更新历史消息（Discord 编辑已发 embed、Telegram 编辑消息文本）；若全新，进入策略引擎。
2. 策略引擎判断当前是否可发，若不可，加入延迟队列（通知提交者已排期）。
3. 可发时，调用各平台适配器并行发布，但串行执行 API 写入（用一个 mutex queue 避免限流）。
4. 发布完毕写入 Memory，提供日志供复盘。

## 踩坑记录

- **相似度阈值是个玄学**  
  最初设为 0.9，结果 CI 状态从“running”到“success”的差异被当成独立事件，依旧发了两次。调到 0.85 后合并成功，但偶尔会把 changelog 生成的摘要合并到无关的讨论帖。最终按频道内容类型分别设置阈值：公告类 0.85，日常讨论 0.75。

- **平台消息编辑的限制**  
  Discord 和 Telegram 支持编辑已发消息，但 Twitter 和某些论坛并不支持。合并更新到已发消息时，若该平台不能编辑，只能选择跳过或单独发一条简短更新。我们增加了一个 `editable` 标记，让策略引擎决定是否做合并。

- **API 限流的连锁反应**  
  并行调用 Twitter 和 Discord 时，Twitter 返回 429，导致队列重试，却因 Discord 已发出，形成内容不同步。解决方案是引入“事务性发送”——所有平台成功视为一次事务，任一失败则全部回滚（Discord 通过删除消息回滚），人工介入。但这只适用于紧要内容，普通内容采用异步最终一致。

- **人工覆盖的权限设计**  
  紧急按钮用 `/force-announce` 实现，但需双重确认防止误触。初期有人随意使用，导致刷屏再次出现。改为按角色限制：拥有 `maintainer` 角色的成员才可触发，并且冷却期间带警告提示。

## 可复用建议

- **在 OpenClaw 中封装为一个 Skill**：`community-announce`，支持参数 `--priority`、`--platforms`、`--cooldown-override`。其他 Agent 可直接调用。
- **MCP Server 化你的去重和适配服务**：将去重引擎做成 MCP 资源，供多个 Agent 共享，避免每个工具重复实现。
- **可观测性**：所有发布动作产出结构化日志（时间、平台、消息ID、去重得分），接入 OpenClaw 的 tracing 面板，便于排查为什么该发的没发，或不该发的重复了。
- **灰度运行**：先在低频社区（如内部测试频道）运行一周，观察误拦截率和用户反馈，再推广到公共频道。

## 总结

多社区同步的自动化，本质上不是技术上的“打通”，而是对用户注意力的管理。用 Agent 来定义发布边界——何时发、发什么、怎么收束——比写死脚本更灵活、也更负责任。OpenClaw 的 Memory 和策略引擎刚好提供了这种“知进退”的能力。守住冷却窗口和去重这两道门，大多数刷屏问题就消失了，剩下的是打磨平台适配的细致活。

如果你的社区仍在用简单脚本转发一切，不妨试试让 Agent 来做一次“发布守门员”。
