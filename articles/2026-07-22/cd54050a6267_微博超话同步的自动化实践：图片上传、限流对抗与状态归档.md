## 背景

在 OpenClaw 社区里，经常有朋友问：如何将 Agent 生成的内容稳定地同步到微博超话？虽然微博的开放 API 已经收紧，但在自动化工作流中利用浏览器模拟操作，依然可以实现可靠的同步。本文将分享一套基于 Playwright MCP 的微博超话同步实践，重点剖析图片上传、限流应对与状态归档三个工程难点。

## 问题

1. **图片上传路径**：微博发布图片时，前端会先调用上传接口获取 `pid`，再将 `pid` 随文本一起提交。直接调用上传接口容易被风控标记；如果完全靠页面交互，如何稳定捕获上传成功后的 `pid`？
2. **限流处理**：频繁发布会触发“操作频繁，请 N 秒后再试”，需要自动等待并重试。
3. **去重与归档**：同步任务可能被重复触发，必须有可靠的状态记录，避免重复发帖。

## 做法与步骤

我们使用 OpenClaw 内置的 **Playwright MCP** 完成页面操作，不直接调用微博后端接口，从而降低风控概率。整个流程分为四个阶段：

### 1. 登录态维护
- 首次手动登录后，用 `page.context.storageState()` 保存 cookie/localStorage 到一个 JSON 文件。
- 自动化任务启动时，先 `loadStorageState` 恢复登录态。若检测到需要重新登录（例如页面跳转至登录页），则发送通知等待人工介入，或通过配置好的用户名密码模拟登录。

### 2. 超话发布页导航
- 超话 ID 可通过搜索超话名称后从页面地址获取。例如 `https://weibo.com/p/100808/xxxxx`，将超话 ID 写入配置文件。
- 在 Playwright 中直接用 `page.goto` 打开超话页面，然后点击页面内的“发帖”按钮。微博超话的“发帖”按钮通常是一个 `a[action-type="feed_list_add"]` 或带有 `title="发微博"` 的元素，MCP 中可调用 `click(selector)`。

点击后页面会弹出一个发布浮层，其中内容输入框、图片上传按钮均在同一个 iframe 或 shadow DOM 内，需要注意选择器作用域。

### 3. 图文发布
- 在内容输入框填入文本（其中自动包含超话标签 `#超话名称#`，无需额外拼接）。
- 上传图片步骤是核心坑点。直接使用 Playwright 的 `fileChooser`：先点击“添加图片”按钮，MCP 会触发文件选择对话框，再通过 `page.waitForEvent('filechooser')` 拿到 chooser 并执行 `chooser.setFiles(paths)`，即可将本地图片传给浏览器。
- 上传完成后，页面 DOM 中会出现已上传图片的缩略图元素，其属性中可能包含 `pid`。通过 `page.evaluate` 在页面上下文中提取所有已选图片的 `pid` 数组。若无法提取，也可以通过拦截网络请求响应来获取（但需要提前开监听）。
- 确认文本、图片无误后，点击“发布”按钮。

### 4. 限流应对
- 发布按钮点击后，我们需要监听发布结果。微博浮层发布成功后会自动关闭或在当前页出现新微博，事件监听比较麻烦，可采取轮询：每隔 1 秒检查浮层是否消失，或页面是否出现新微博元素。
- 如果页面出现“操作频繁，请 XX 秒后再试”的提示，解析等待秒数，并使用指数退避（第一次等待指定秒数，第二次加倍，最多等待 120 秒），等待结束后自动重试。
- 同时，全局的发布调用需要加入**并发控制队列**，保证同一时间只有一个任务正在操作发布，避免因为并发操作导致限流计数叠加。

### 5. 状态归档
- 发布成功后，从当前页面 URL 提取微博的 `mid`（格式：`https://weibo.com/{uid}/{mid}`）。如果页面没有跳转，可以从发布时间链接的 `href` 中解析。
- 用 SQLite 数据库存储 `mid`、文本内容哈希、发布时间戳、发布状态（成功/失败/重试中）。
- 每次同步前，先对要发布的内容计算哈希，查询 SQLite 是否已有 `status='成功'` 的记录。若已存在则跳过，避免重复发布。
- 对于发布失败的记录，可以设定重试上限，超过上限后标记为 `failed` 并通知运维。

## 踩坑清单

1. **cookie 过期**：微博 cookie 失效时间约 24 小时，自动化任务如果每天多次运行，建议在每次执行前先访问微博首页验证登录态，失效则触发人工扫码流程。
2. **验证码**：滑块验证码无法自动解决，可以在 OpenClaw 中设置失败通知，人工协助后任务继续。
3. **图片大小限制**：微博单张图片不超过 5 MB，超限则上传静默失败。使用 `sharp` 库将图片重采样、转为 JPEG 并限制质量，保证每张低于 4 MB。
4. **浮层元素选择器不稳定**：微博前端频繁更新，选择器应尽量使用固定的属性如 `action-type` 而非 class。定期维护选择器列表。
5. **限流误判**：微博偶尔返回“发布成功”但提示过于频繁，实际上是内容审核未通过。需要区分审核失败（通常伴随敏感词提示）与频率限制，避免误重试。

## 可复用建议

- **封装为 MCP Tool**：将上述流程封装成一个 `weibo_super_topic_publish` 工具，输入参数为文本、图片路径列表、超话名称。该工具内部完成所有交互与状态记录，OpenClaw Agent 可以直接调用。
- **状态存储独立**：SQLite 文件放在持久化卷中，与工作流分离，方便跨任务复用。
- **图片预处理管道**：在调用发布 Tool 前，Agent 可以先调用一个本地的图片处理工具（如基于 `sharp` 的 MCP Server）统一压缩与格式转换。
- **日志与监控**：为每次发布生成结构化的日志，包含耗时、重试次数、成功与否，接入简单的 webhook 通知。

## 总结

通过 Playwright MCP 模拟用户操作，并配合工程化的限流策略与状态归档，可以在 OpenClaw 环境中构建一个较为鲁棒的微博超话同步流水线。全程不依赖非公开接口，可维护性和风控友好度都优于直接请求 API。对于同样需要内容自动分发至社交平台的场景，这套思路（浏览器操作 + 任务队列 + 状态持久化）也具备较强的可迁移性。
