# 自动发帖流水线的本地归档设计：从文章、图片到 assets.json

## 背景

在 OpenClaw 社区，不少人正在用 Agent 搭配 MCP 工具或自定义插件搭建内容自动生产流水线：输入话题或关键词，生成一篇完整文章，配上封面图或段落图，然后自动发到多个平台。这套流程跑通之后，很快会遇到一个工程上绕不开的问题——每一次运行生成的内容，究竟「在哪里」？

默认情况下，很多流水线只管生成和发送，不做本地保存，或者在临时目录里随手写个文件就不管了。一旦某次发布失败、平台改接口限流，或者需要稍后人工润色再发，就只能重新跑一遍完整的生成流程，甚至再也找回不到刚才那版“还不错的草稿”。更进一步，如果要复盘生成效果、统计图片引用关系、追踪哪些内容已经发布成功、哪些还在待办队列，缺少结构化的归档就是个硬伤。

本文面向已经动手做过自动发帖流水线的同学，介绍一种轻量的本地归档方案：把每次生成的文章 Markdown、所有配图文件，以及一份描述资源关系的 `assets.json`，按照一套固定的目录结构持久化到本地。整个做法纯粹基于文件系统和 JSON，不需要引入数据库，方便集成进已有的 OpenClaw/Agent 工作流，也适合与 Git 搭配做版本控制。

## 问题拆解

把需求拆开看，一个本地归档模块需要解决三件事：

1. **文章落盘** —— 生成后的 Markdown 原文必须原样保存，便于重发或人工编辑。
2. **图片本地化** —— AI 生成的配图通常是临时 URL，必须拉到本地，否则过一会儿链接失效，归档就白做了。
3. **资源关系与状态记录** —— 需要一张“清单”，知道这一次生成包含哪些文件、它们分别代表什么角色，以及后续在哪些平台的发布状态是成功、失败还是待处理。

如果不做结构化记录，就只能靠人肉维护目录名和文件名，很快就乱掉。`assets.json` 就是这份清单。

## 做法与步骤

### 1. 约定目录结构

我推荐的归档根目录结构如下，每次生成作为一个独立子文件夹：

```
archive/
  2025-03-18-twitter-ai-trends/
    post.md
    images/
      cover.png
      body-1.png
    assets.json
```

文件夹命名采用 `{日期}-{slug}` 形式，slug 可以由生成阶段根据标题自动生成，也可以手动传入。如果担心 slug 冲突，可以在末尾追加短随机串。所有与单次生成相关的东西，都装在这一个文件夹里，迁移、打包、删除都很清晰。

### 2. 保存文章

文章生成后，不要急着直接扔给发布模块，先以 `post.md` 为名写入归档目录。如果文章中的图片还是远程 URL，这里先保持原样，后面统一做替换。

一个要注意的细节：写入操作必须用同步或 await 确保落盘完成后再进入下一步。遇到过因为磁盘 I/O 延迟，还没写完文件就去读的情况，会导致后续步骤读到空文件或部分内容。所以这一步要显式 `fs.writeFileSync` 或 `await fs.promises.writeFile` 并 flush。

### 3. 图片下载与路径替换

图片下载是整个流程里最容易出错的一环，主要是网络不稳定、格式异常、防盗链等问题。我当前的做法：

- 使用 `axios` 下载图片流，设置 15 秒超时，失败自动重试 2 次，间隔 2 秒。
- 下载完成后，检查 Content-Type 是否与后缀匹配（仅允许 `image/png`、`image/jpeg`、`image/webp`），不匹配则抛出错误、记下日志并跳过。
- 图片统一存到 `images/` 下，文件名用内容哈希后六位 + 序号，避免重名，例如 `a3f2c1-1.png`。
- 下载成功后，用正则遍历 Markdown 中的图片引用 `![alt](url)`，将远程 URL 全部替换为相对路径 `![alt](images/a3f2c1-1.png)`。

这里有一个踩坑：有些生成工具输出的是 HTML 标签包裹的图片，比如 `<img src="...">`，正则可能会漏。所以替换阶段最好也兼容一下 HTML 标签写法，或者在前置步骤就把全部图片引用统一成 Markdown 语法。

### 4. 生成 assets.json

当文章和图片都已经落盘，就可以写 `assets.json`，结构大致如下：

```json
{
  "title": "AI Trends on Twitter This Week",
  "slug": "twitter-ai-trends",
  "created": "2025-03-18T10:30:00Z",
  "post_file": "post.md",
  "images": [
    "images/cover.png",
    "images/body-1.png"
  ],
  "platforms": {
    "twitter": "pending",
    "blog": "pending"
  }
}
```

`platforms` 字段在归档时可以先统一设为 `"pending"`，待真正调用发布接口并得到结果后，再去更新对应的值（`"success"`、`"failed"` 等）。如果你有多个 Agent 或进程同时在修改同一个 `assets.json`，会有并发写冲突的风险。我的实践是，将归档阶段设计成“一次性生成，只读追加”，发布状态另存到一个小型 SQLite 或直接复用流水线的日志系统，尽量减少对同一个 JSON 文件的竞争写。如果必须写同一个 JSON，推荐使用 `proper-lockfile` 或者简单的文件锁机制来控制。

### 5. 集成到流水线

把归档步骤包装成一个独立的函数或 MCP 工具，放在“文章生成”之后、“调用发布 API”之前。如果有任何一步归档失败（比如磁盘写满），直接终止流水线并告警，不要带着残废状态去发布。这样保证了“要么完整归档并发布，要么什么都不做”。

对于 OpenClaw 用户，可以把归档函数注册为一个可被 Agent 调用的 Action，这样无论是用 GPT、Claude 还是其它模型作为核心，都可以用 tool call 的形式调用归档。

## 踩坑记录

实际落地中踩过几个坑，值得单独拿出来说：

- **图片 CDN 返回 403/302**：有些图床会校验 Referer 或 User-Agent，下载时必须带上合适的请求头，甚至需要模拟一次页面访问拿临时链接。遇到这种情况，优先在生成阶段就要求模型返回直接可下载的 URL，否则链路会变得很重。
- **Markdown 中图片 URL 已过期**：如果生成和归档之间间隔太久，某些临时 URL 其实已经失效。所以一定要在生成完文章后立刻下载图片，不要延迟。
- **Windows 路径分隔符**：若希望在 Win/Mac/Linux 都能用，路径拼接请用 `path.join`，并且在 `assets.json` 中记录的正斜杠相对路径，避免 `\` 带来的跨平台问题。
- **大尺寸图片导致内存溢出**：最好不要把整个图片读进内存再写盘，用 stream pipeline（`response.data.pipe(writer)`）的方式直接落盘，保护长期运行的 Agent 进程。

## 可复用的建议

如果想让这个归档方案更容易在不同项目里复用，可以做几件事：

1. **抽成独立 npm 包或插件** —— 暴露出 `archivePost(postContent, images, meta)` 这样的接口，内部处理好目录创建、图片下载、路径替换、JSON 写入，不耦合具体生成器。
2. **提供 CLI 入口** —— 方便在非 Node.js 流水线中通过 shell 调用：`npx post-archiver --dir ./output --title "..." --post-file ./post.md`。
3. **assets.json 的 Schema 做版本字段** —— 增加一个 `"version": "1"` 字段，后续如果扩展字段，可以做到向前兼容的解析。
4. **与 Git 挂钩** —— archive 目录初始化成 Git 仓库，每次归档后自动 commit，日志就是天然的审计线索，还能很方便做 diff 看每次生成内容的变化。

## 总结

本地归档这件事，在自动发帖流水线的最初阶段很容易被忽略，但它决定了这条流水线到底是一个“一次性的黑盒玩具”，还是一个可以持续运行的工程化系统。把文章、图片和 `assets.json` 老老实实落盘，后面无论是要做批量重新发布、效果分析、还是接入人工审核，都有了一个稳固的基座。

实现上并不复杂，核心就是用文件系统模拟了一个轻量对象存储，并在关键环节做足异常处理。如果你正在折腾自动发帖的 Agent，不妨花一个下午把这部分补上，回报会比你预想的大得多。
