## 背景

在 OpenClaw、MCP 以及多 Agent 协作的发帖流水线中，内容生成链路往往由多个步骤组成：选题、写作、配图、格式校验、发布。每一环都可能产出中间稿件，但大多数落地实现只关注“发出去”这一终点，忽略了素材的**可回溯性**与**可复用性**。

没有本地归档时，常见问题包括：
- 发过的文章找不到原始 Markdown，只能去发布平台反查，格式可能已经变形；
- 文章中的图片是临时 URL 或 Base64 内联，一旦过期或上下文丢失，素材变得不可用；
- 想复盘某次生成质量、统计配图信源、复用某篇模板时，发现关键元数据早已丢失。

因此，我们需要一个轻量且可靠的本地归档机制，将**文章正文、图片文件与元数据**稳定沉淀到文件系统里，作为流水线的收尾环节。

## 目标归档结构

为每篇待发布内容生成一个以其 `slug`（唯一标识）命名的目录，例如：

```
posts/2025-03-24-agent-archiving/
├── article.md
├── assets/
│   ├── cover.png
│   ├── diagram-01.png
│   └── ...
└── assets.json
```

- `article.md`：最终文章，图片引用都改为**相对路径**指向 `assets/`；
- `assets/`：从各个来源下载的图片文件，使用稳定命名；
- `assets.json`：一张清单，记录原始资源信息与本地文件的映射关系。

这 3 部分文件耦合在一起，`git clone` 后就能立刻获得一个完整的静态副本，不依赖任何外部链接。

## assets.json 的结构设计

目的不是做“大而全”的资源管理系统，而是服务**自动化回溯**。建议字段精简，示例如下：

```json
[
  {
    "id": "cover",
    "original_url": "https://img.example.com/abc123.png",
    "local_path": "assets/cover.png",
    "mime_type": "image/png",
    "downloaded_at": "2025-03-24T14:20:00Z",
    "checksum_sha256": "e3b0c4...",
    "prompt_used": "英文 prompt ..."
  }
]
```

- `id`：在 Markdown 中可能作为锚点引用，但非强制；
- `original_url`：便于追溯图片来源，即使链接已失效；
- `local_path`：相对归档目录的路径；
- `downloaded_at` 与 `checksum`：辅助排障与去重；
- `prompt_used`：如果图片由生成模型产出，记录生成指令，方便后续复盘。该字段可选。

## 流水线实现步骤

假设流水线在最终发布前，将文章内容以字符串形式传递，并附带一份图片映射表（{引用名：图片URL或Base64}），以下步骤可以写成独立脚本、MCP 工具，或者 OpenClaw 中的归档 Agent。

**1. 生成 slug 与目标目录**

由文章标题或时间戳生成 slug，例如 `2025-03-24-agent-archiving`，创建目录并初始化 `assets.json` 为空数组。

**2. 处理图片资源**

遍历图片映射表，对每个条目：
- 如果 URL 是远程链接，发起下载，添加重试机制（3 次，间隔递增）。下载时携带合理的 User-Agent，避免被反爬。
- 如果是 Base64 数据，解析并写入二进制文件。
- 使用内容 SHA-256 作为文件重名时的去重标识；若文件已存在（相同 checksum），直接复用现有文件，避免冗余存储。
- 将下载成功的图片信息追加到 `assets.json` 数组中，然后**立即**将整个 JSON 写盘（防止意外中断导致元数据丢失）。

**3. 替换文章内的图片引用**

这一步要处理 Markdown 中两种常见图片格式：
- `![alt](url)`
- `<img src="url" ...>`

最稳健的方式是：先正则匹配所有 src 属性，提取 URL，与之前已下载图片的 `original_url` 或 Base64 原串做精确映射；对于 Base64 内联，通过 hash 比较来定位。将原 URL 全部替换为 `./assets/文件名` 的相对路径。替换后再用一次全文字符串比对，确保没有遗漏原始链接。

**4. 写出 article.md**

将替换完毕的 Markdown 文本写入 `article.md`，编码统一为 UTF-8 without BOM。

**5. 最终锁定归档**

对 `assets.json` 做一次最终写入，并在根目录下生成 `.archive-complete` 空标记文件，供后续扫描程序判断归档是否已完成。

## 踩坑点

- **图片 URL 是动态生成的临时链接**
  如果文章生成与归档之间存在时间差（例如到人工审核），很可能原本的图片 URL 已经失效。因此下载必须**尽早执行**，最好紧跟在内容渲染完成后，而不是等整条流水线结束。必要时让图片生成 Agent 直接返回 Base64，由归档环节负责落地。

- **文件名冲突与特殊字符**
  图片原始文件名可能包含空格、中文或特殊字符，直接用作本地文件名会带来跨平台问题。建议统一按“前缀_uuid.扩展名”重命名，例如 `diagram_a1b2c3d4.png`。该映射必须完整记录入 `assets.json`。

- **并发场景下的覆盖风险**
  如果流水线可能多实例并发，目录写入要有基本锁机制。轻量实现用文件锁（如 `flock`），或直接用 UUID 作为 slug 的一部分，降低冲突概率。

- **JSON 写入不完整**
  大量图片时，`assets.json` 逐步追加可能因为中途异常导致 JSON 断裂。解决办法是**先写临时文件，重命名替换**，保证原子性。同时务必每次 append 后写入合法 JSON（即闭合 `]`），避免最后才补括号。

- **Markdown 图片替换遗漏**
  如果文章里混入了一些非标准的 HTML 写法（例如 `<img ... />` 缺闭合、属性顺序不一），正则容易漏掉。建议使用 HTML 解析器（如 `cheerio` 或 Python 的 `BeautifulSoup`）先做标准化预处理，再替换 `src`。

## 可复用建议

如果把这段逻辑封装为 MCP 工具，只需暴露一个接口：
```
archive_post(slug, markdown_content, image_map[])
```
返回归档目录路径与 `assets.json` 内容。这样任何 OpenClaw Agent 或流水线脚本都可以在发布前调用，实现统一的“最后一步归档”。

另外，可以配合一个轻量扫描器，在目录树中查找所有包含 `.archive-complete` 的文件夹，快速重建文章索引，支持本地全文搜索与素材复用。

## 总结

为自动发帖流水线增加本地归档并不复杂，核心是在**正确的时间点**完成图片下载、引用替换与元数据持久化。一套简单的约定（`article.md` + `assets/` + `assets.json`）就能让生成内容摆脱对平台的强依赖，既服务于个人创作的可维护性，也为后续的审核、统计与二次生成提供坚实基础。工程实践上，注重原子写入、去重与容错，即可在极低成本下获得高可靠性的自动归档能力。
