## 背景：一次同步引发的“社死”

团队维护着 GitHub 仓库、Discord 频道、飞书群和两个技术论坛。最初我们用 GitHub Actions 配合 webhook，每当有新 Release 或博客更新，就把同一段 Markdown 公告丢到所有渠道。结果是用户在五分钟内从三四个平台看到同样的消息，社群被刷屏，管理员私聊警告，还有人默默退群。

自动化发布不是简单的“一发多投”。当同步速度超过社区消化能力，就是噪声。我们需要一套带有边界控制的同步机制，让信息准时抵达，但避免造成重复轰炸。

这篇文章记录我基于 OpenClaw 构建多社区同步 Agent 的过程，重点在如何通过队列、节流与去重，把“群发”做成“节奏发布”。

---

## 问题拆解：为什么直接同步会刷屏？

先把问题摊开：

1. **零延迟等同于叠加**：所有渠道几乎同时收到相同内容，上下游用户如果同时存在于多个社区，就会看到重复通知。
2. **平台没有频率收敛**：Discord 允许短时间发多条，飞书群也有类似特性，API 本身不帮你控制。
3. **没有上下文化**：不同社区对通知的容忍度差异很大。GitHub Discussions 适合长文公告，Discord 更适合短摘要加链接，直接扔全文就是污染。
4. **撤回困难**：一旦全渠道发出，想修改或撤回，得挨个平台操作，非常狼狈。

所以核心需求是：**一个内容源，多渠道分发，但以符合社区节奏的方式推送，并允许中心化撤回。**

## 做法与步骤：构建一个带“触觉”的同步 Agent

整体思路是在 Agent 内部维护一个发布计划队列，由策略控制每个通道的延迟和速率。技术栈：OpenClaw Agent + 各平台 API + Redis 存储状态。OpenClaw 负责编排逻辑和调用工具，这里把它当成可编程的发布编排器。

### 1. 梳理渠道与格式模板

花时间整理了 5 个渠道的属性：

- GitHub Discussions：支持 Markdown，可发长文，频率容忍度低（一天一篇已是上限）。
- Discord 公告频道：Markdown 受限，适合 500 字符以内的卡片式消息，频率可接受每小时 2-3 条。
- 飞书群机器人：富文本，但群成员对非关键通知敏感，建议降级为简报模式。
- Twitter/X：280 字符限制，需要提炼核心信息加链接。
- 内部团队 Slack：只需一条摘要 + 链接，不需要全文。

为每种渠道写好消息转换函数，同一份内容源经过适配器产出不同的 payload。

### 2. 发布策略与节流队列

用一个简单的调度器来控制节奏：

- 核心公告渠道（如 GitHub Discussions）作为首发，立即发布。
- 即时通讯渠道（Discord、飞书）延迟 5 分钟，错开首波刷新。
- 社交媒体再延迟 15 分钟。

具体实现：Agent 收到“发布”指令后，不直接发，而是生成一个发布计划，每一项带有目标渠道、理想执行时间（`scheduled_at`）和内容负载。然后再由一个轮询 worker 按时间执行。

为了避免瞬时密集执行，对每个渠道加了最小间隔控制，例如 Discord 同一频道至少间隔 3 分钟。这个逻辑写在一个 MCP 工具 `schedule_publish` 里，Agent 规划后调用。

### 3. 内容去重与摘要合并

如果短时间内有多篇文档需要同步（比如修了几个小 bug 连续发版），全部发出去依然是刷屏。因此增加了近 24 小时的发布指纹去重：

- 将每条待发内容的标题 + 前 200 字符做 SHA256 摘要。
- 与 Redis 中已发布记录的指纹库比对。
- 如果相似度超过阈值（近重复），则将新内容合并到上一条仍在缓冲期的消息里，用“同时更新了以下内容”的摘要形式发出。

这里踩过一个坑：简单 Hash 无法感知句子改写。后来换成对文本做分词后计算 Jaccard 相似度，效果好很多，足以应对微调标题的情况。

### 4. 可撤回机制

每条消息在平台发布成功后，都会返回一个 remote_id（如 Discord 消息 ID、飞书 message_id）。Agent 把这些 ID 存储到发布日志里，并提供 `recall_all` 工具，可以一键删除过去 30 分钟内发布的所有渠道消息。虽然部分平台如 Twitter 撤回有延迟，但至少 Discord 和飞书能快速清除，避免错误公告扩散。

---

## 踩坑点

- **平台速率限制的隐性成本**：Discord webhook 看似宽松，但全局每通道每秒 5 条，连续爆破会进入冷却。必须用令牌桶做客户侧限流。
- **飞书消息撤回需要 msg_id 且在 24 小时内**，超过时间无法撤回，所以紧急撤回必须及时发现。
- **去重过于激进**：有一次把两个标题相似但内容完全不同的公告合并，用户看懵了。后来要求标题+前 200 字双重相似才合并，并增加人工确认选项。
- **不同时区的时间展示**：GitHub Discussions 显示 UTC，Discord 默认本地时间，如果公告里写了“今天20:00”，不同社区可能误解。Agent 需要统一使用相对时间（如“2 小时后”）或带上时区。

## 可复用建议

可以把上述控制逻辑抽象成一个 OpenClaw 插件或 MCP 服务，核心参数可配置：

```yaml
publish_policy:
  channels:
    - id: github_discussion
      delay_seconds: 0
      min_interval_seconds: 86400
    - id: discord
      delay_seconds: 300
      min_interval_seconds: 180
    - id: feishu
      delay_seconds: 300
      min_interval_seconds: 300
  dedup_window_seconds: 86400
  similarity_threshold: 0.8
```

Agent 的 prompt 只需描述任务：“将本次发布按策略分发，合并近重复内容，并在失败时通知管理员而非重发。” 所有边界控制由工具层保证，降低 Agent 自由发挥的风险。

---

## 总结

多社区同步不是群发接口的简单封装，而是一个需要节奏感、同理心和工程约束的系统设计。通过队列延迟、渠道间隔、内容去重和集中撤回，我们可以在不骚扰用户的前提下保持信息同步。这套方案运行三个月后，社群投诉归零，也再没出现过“机器人刷屏”的尴尬。对于任何正在用 Agent 做自动化发布的团队，控制同步边界应是第一个被认真对待的需求。
