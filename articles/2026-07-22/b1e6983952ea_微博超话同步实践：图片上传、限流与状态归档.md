## 背景

在基于 OpenClaw 搭建的自动化内容分发链路上，微博超话作为垂直社区入口，常被用于同步技术周报、日常分享或项目宣发。手动跨平台搬运成本高，且容易遗漏或重复发布，因此我们将“超话发帖”抽象为一个可编排的 Agent 任务。

初期我们曾考虑直接复用现成的社交平台封装库，但很快发现：超话发帖的图片上传路径、反爬策略与普通发微博存在明显差异，缺少开箱即用的稳定方案。本文将梳理我们在纯工程侧落地这一能力时，碰到的图片上传机制、限流控制和状态归档问题，并给出在 OpenClaw 框架下的轻量实现思路。

## 问题拆解

整个同步动作可简化为三步：

1. 获取待发布内容（文本 + 图片 URL 列表）
2. 上传图片 → 获取服务端 PID
3. 携带 PID、文本与超话标签，调用发帖接口

乍看只是顺序调接口，但实际工程化后有四个关键矛盾：

- **图片上传链路复杂：** 微博主站与移动端的上传接口存在差异，超话发帖要求图片先进入相册再引用，还是可以直接 `multipart/form-data` 上传？
- **限流规则不透明：** 普通用户日发博上限、超话每日发帖频率、验证码触发阈值均未公开，需通过工程手段柔性应对。
- **任务幂等要求高：** 同一内容不应因重试、重启而重复发布，必须对“已发状态”做可靠归档。
- **与现有调度框架兼容：** 希望复用 OpenClaw 的定时、重试、状态管理等能力，而非另起炉灶。

## 实现步骤

### 1. 封装微博超话发帖为 MCP 工具

为了便于其他 Agent 调用，我们将超话发帖能力封装为一个 MCP (Model Context Protocol) 工具 `weibo_super_topic_post`。工具接收文本、超话 ID、图片 URL 列表和可选的定时参数，内部完成登录态维护、图片上传和发帖。这样在 OpenClaw 的 Agent 编排里，只需将这个工具插入任务链即可。

登录态基于微博移动端 `m.weibo.cn` 维护，因为其接口相对稳定且反爬成本较低。`cookie` 通过定期刷新存储于环境变量，工具启动时自动校验是否过期。

### 2. 图片上传的真正路径

经过抓包验证，使用移动端发帖接口直接上传图片是可行的，无需提前上传至相册。关键点如下：

- **接口：** `POST https://m.weibo.cn/api/mblog/image_upload`
- **Body：** `multipart/form-data`，字段为 `image`（文件流）和 `type`（值固定为 `pic`）
- **响应：** JSON 中包含 `data.pic_id`，即后续发帖要用到的 PID

文件必须为合规图片格式（实测 JPG/PNG 均可，建议远端图片先下载到本地，检查尺寸与体积）。上传时需携带完整的移动端 Cookie 和 `Referer: https://m.weibo.cn/`，否则会被拦截。

如果上传失败，日志会记录具体的错误码。常见异常为 `100002`（session 过期）、`100005`（图片违规），需在工具内部根据错误码做分支处理：过期则刷新登录态并重试一次；违规则直接标记失败，不再重试，并通知上层。

### 3. 发帖并注入超话标签

拿到 PID 后，调用发帖接口 `POST https://m.weibo.cn/api/statuses/update`。请求体示例：

```json
{
  "content": "#超话名称# 正文内容",
  "pic_ids": "pid1,pid2",
  "topic_id": "超话ID",
  "visible": 0
}
```

注意超话标签需以 `#超话名#` 形式出现在 `content` 中，且 `topic_id` 参数保证帖子真正绑定到超话。缺少后者会导致帖子仅在个人主页可见，不会进入超话时间线，这个是早期踩过的隐坑。

### 4. 限流控制与重试机制

微博对同一账号的连续发帖极其敏感。我们的做法是在 MCP 工具内建一个简单的请求队列，基于令牌桶算法控制每分钟不超过 2 次发帖请求，且两次发帖间插入 15~35 秒的随机等待。

若接口返回频率限制错误（如 `100010`），工具会将当前任务置为“等待”，并返回一个 `retry_after` 参数给调度器。OpenClaw 的任务引擎能够识别这类临时失败，自动在指定时间后重新调度。

对于每日发帖总量，我们通过配置硬上限（如 45 条）提前阻断，防止触发微博侧的高压警戒。

### 5. 状态归档设计

为防止重复发布，我们选用 SQLite 作为轻量状态存储，表结构如下：

```sql
CREATE TABLE IF NOT EXISTS post_archive (
    source_id       TEXT PRIMARY KEY,  -- 内容源唯一标识，如 CMS 文章 ID
    super_topic_id  TEXT,
    weibo_post_id   TEXT,
    status          TEXT CHECK(status IN ('posted','failed','ban')),
    extra           TEXT,               -- 存储 PID、错误信息等 JSON
    created_at      TEXT,
    retries         INTEGER DEFAULT 0
);
```

每次准备发帖前，工具先查询 `source_id + super_topic_id` 是否存在 `posted` 记录，若存在则直接跳过，实现幂等。发布成功后更新 `weibo_post_id` 和 `status`；失败则记录重试次数，超过阈值后标记为 `ban` 并通知运维。这样即便工具重启，已发内容也不会被误判为“未发”。

## 踩坑记录

- **图片体积与格式：** 直接扔一张 5MB 的 PNG 大概率失败，需预先将图片压缩到 2MB 以下，宽度控制在 1200px 以内。可在上传前用 `PIL` 或 `sharp` 做预处理。
- **Cookie 安全：** 长时间运行下，移动端 Cookie 也会自动过期，务必在 MCP 工具中实现过期检测和自动刷新，否则会出现“静默失败”——接口返回某个未文档化的错误时，工具若不加区分地重试，可能加快账号风控。
- **超话审核：** 部分超话开启发帖审核，帖子不会立刻出现在时间线。此时微博返回的状态仍是成功，但在我们的状态归档里，`weibo_post_id` 会为空或 post 后端可见。这种情况通过定时查询博文状态可补充验证，但会增加接口访问量，需权衡。
- **IP 限制：** 多账号跑在同一台服务器，可能被微博标记为“非正常操作”。建议搭配低并发的住宅 IP 代理，或分散到不同 Worker 节点执行。

## 可复用建议

将上述能力抽象为一个通用“社交平台同步”插件，可遵循以下模式：

- **接口抽象：** 定义 `SocialPlatform` 基类，含 `upload_image`、`post_status`、`archive_check` 三个核心方法，通过派生类适配不同平台。
- **与 OpenClaw 集成：** 插件的出入口统一为 MCP 工具形式，平台特有的限流、重试策略封装在内部。OpenClaw 的 Agent 只需关注任务编排和异常处理。
- **配置驱动：** 账号 Cookie、发帖上限、超话列表等全部放入配置文件或环境变量，避免硬编码，方便扩展多个账号和超话。
- **状态可观测：** 工具内部输出结构化日志，包含 `task_id`、`platform`、`action`、`latency`、`status`，即可快速接入现有监控体系。

## 总结

微博超话同步并不是“调一下接口就完事”的简单脚本。图片上传的细节、频率约束的动态博弈、状态的持久化归档，共同构成了一个典型的工程化难题。在 OpenClaw 框架下，通过将其封装为独立 MCP 工具，并在工具层内置严格的限流、重试和归档逻辑，我们可以获得一个稳定、可审计、可复用的同步能力，而不必让每个 Agent 开发者重复踩坑。

这背后体现的思路也适用于其他强反爬、重限流的平台自动化：**将平台约束内聚到最底层的执行单元，让上层编排专注于业务逻辑**，是一种可长期维护的架构选择。
