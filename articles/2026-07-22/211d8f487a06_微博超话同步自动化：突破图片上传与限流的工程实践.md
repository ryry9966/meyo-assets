## 背景

在 OpenClaw 社区中，越来越多的自动化工作流开始接入社交平台。其中一个高频需求是将本地内容（每日精选、RSS 摘要、AI 生成图文）定期同步到微博超话，实现多平台分发。微博超话的发布接口看似简单，实际落地时却会遇到图片上传限制、接口限流、状态不可追溯等问题，尤其是当同步任务以 Agent 或 MCP 工具形式运行时，原本“调个 API”的事会迅速演变成异常处理的深坑。

这篇文章结合作者在 OpenClaw + 微博 MCP 上的实战，梳理从图片上传到状态归档的完整链路，重点解决两个核心痛点：**图片上传的非标准化约束**和**发布接口的限流对抗**。

## 问题拆解

微博超话同步流程可以抽象为三步：

1. 获取待发布内容（文本 + 图片链接）
2. 上传图片到微博图床，得到 `pid`
3. 调用发微博接口，附带超话参数和图片 `pid`

每一步都有隐藏障碍：

- 图片链接可能来自第三方 CDN，微博上传接口要求图片为本地文件或特定格式的二进制流，且单张不超过 5MB，分辨率建议 1200px 以上以免压缩劣化。
- 微博图片上传接口有独立的频率限制（约 30 次/分钟），而发微博接口同样有窗口限制（普通用户约 3-5 条/分钟），二者叠加后，大批量同步极易触发 429 错误。
- 不同超话的发帖权限、是否需要超话等级、是否需要关注超话等规则各异，错误码不统一，给自动化判断带来麻烦。
- 长时间运行的 Agent 如果没有状态归档，无法知道哪些内容已成功同步，哪些被限流延迟，排查问题只能翻日志。

## 实践方案

我们基于 OpenClaw 的定时调度器 + 微博 MCP Server 构建了同步流水线。整体架构如下（见图 1）：

1. **内容准备**：源数据来自本地 Markdown 仓库，通过 OpenClaw 的 `fs` 工具读取，提取出当日待同步条目。
2. **图片预处理**：检测条目中的图片 URL，如果非微博域图片，则由 OpenClaw 调用下载工具（如 `download` MCP）保存到临时目录，并校验尺寸与格式。
3. **上传图片**：调用微博 MCP 的 `upload_image`，传入文件路径，返回 `pid`。该步骤内置了重试器，遇到 429 时执行指数退避（1s-4s-16s），最大重试 3 次。
4. **组装微博正文**：将文本与超话标签（例如 `#超话名称#`）拼接，注意超话标签必须放在文案末尾才能正确关联超话，这是一条容易被忽略的规则。
5. **发微博**：调用 `statuses/update`，传入 `status` 和 `pic_id`。同样集成退避器，不同的是，这里除了 429 还要处理 `10024`（发帖过快）、`10017`（图片审核未通过）等特定错误码，后者需要标记图片异常并跳过。
6. **状态归档**：每处理一条内容，记录一个 JSON 状态行到归档文件，包含时间戳、内容 ID、图片上传结果、微博接口返回的 `id` 或错误码、重试次数。同时，OpenClaw 的 memory 或内置 KV 可存储最后成功同步的游标，避免重复发布。

伪代码示例（OpenClaw 中通过组合 MCP 工具实现）：

```yaml
- name: sync-weibo-chaohua
  schedule: "0 9 * * *"
  steps:
    - tool: fs.read
      params: { path: "today_content.md" }
    - tool: parse_content
    - for: { item: content.items }
      steps:
        - tool: download_image
          params: { url: item.image, dest: "/tmp/wb_img.jpg" }
        - tool: weibo.upload_image
          params: { file: "/tmp/wb_img.jpg" }
          retry: { max: 3, backoff: exponential }
        - tool: weibo.post_status
          params:
            status: "{item.text} #超话名称#"
            pic_id: "{{ prev.pid }}"
          retry: { max: 2, on_error_codes: [429,10024] }
        - tool: archive.append
          params:
            entry:
              id: item.id
              status: "ok"
              weibo_id: "{{ prev.id }}"
```

## 踩坑实录

**1. 图片上传的隐秘规则**

微博图片上传对格式要求较宽松（jpg/png/gif），但如果源文件是 WebP，直接上传会静默失败，返回 `pid` 但实际发帖时图片不显示。解决方案是预处理时统一转换为 JPEG。另外，部分超话会强制压缩图片，建议上传前将图片缩放至 1200px 宽（高度等比），能显著提升清晰度。

**2. 限流的 “小时级窗口”**

除了每分钟限制，微博还有一个小时级别的发帖总量限制（普通用户约 50 条），连续高强度同步会触发隐形封禁——接口返回正常但内容仅自己可见。我们通过监控已发帖的公开可见性（定期用 `statuses/show` 抽样）来探测这种软限流。一旦发现可见性异常，Agent 立即停止当日同步并报警。

**3. 超话 ID 的获取陷阱**

部分超话名称存在别名或合并情况，直接使用中文标签有时无法命中目标超话，需要预先通过 `search/topics` 接口查询正确的超话 ID（`topic_id`），然后在 `statuses/update` 中传入 `topic_id` 参数，而非仅依赖文本中的 `#tag#`。这个参数在官方文档中并不明显。

**4. Cookie 与 Session 维护**

第三方 MCP 通常使用微博 cookie 鉴权。长时间运行的 Agent 会遇到 cookie 过期（约 24-48 小时），需要在 MCP 中实现自动刷新逻辑，或每天人工 / 通过环境变量更新 cookie。我们采用 OpenClaw 的 secret 管理注入最新 cookie，并在任务前增加一次 `account/profile` 校验，失败则终止同步并通知。

## 可复用建议

- **将图片处理、上传、发帖封装为独立的 MCP 动作**，每个动作自带重试策略和错误分类，这样在 OpenClaw 编排时可以像搭积木一样组合。
- **状态归档采用追加式 JSONL**，便于后续分析同步成功率、限流频率，也能作为数据回溯的依据。
- **对限流不要硬顶**，合理利用“匀速器”（rate limiter），在每次请求后 sleep 固定的间隔（如 15 秒），可大幅降低触发风控的概率。如果仍收到限流，退避策略优先使用“带 jitter 的指数退避”。
- **监控比修复更重要**，设置简单的健康检查（比如每天同步后检查最后 10 条的可见性）能帮你提前发现账号异常。

## 总结

微博超话的自动化同步并不复杂，难在细节的堆叠与异常处理的健全性。通过 OpenClaw 的调度 + MCP 工具的组合，我们可以将原本手动操作的零散步骤收敛为可靠的工作流。核心收益在于：**图片约束可前置解决，限流对抗可自动化控制，状态归档让每一次同步都有据可查**。希望这些实战经验能为社区中正在尝试社交平台自动化的朋友们提供一些参照，少走一些图片“发了不显示”、限流“封了不知道”的弯路。
