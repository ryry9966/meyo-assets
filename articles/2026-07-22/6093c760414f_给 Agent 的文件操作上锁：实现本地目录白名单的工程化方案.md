# 给 Agent 的文件操作上锁：实现本地目录白名单的工程化方案

OpenClaw 这类 Agent 框架允许 LLM 直接操控文件系统，这在自动化脚本、代码辅助等场景中非常高效。但能力越大，危险也越大——Agent 可能在一次错误的推理中读取敏感配置文件、覆写关键项目文件，甚至在工作区外执行任意写入。在给 Agent 开放文件能力之前，我们必须先问自己：**它能碰哪些目录？碰不了的该如何兜底？**

答案就是给文件访问加一道护栏：**本地目录白名单**。本文将给出一套可落地的做法，结合我在 OpenClaw + MCP 插件环境下的踩坑经验。

## 背景：为什么简单的路径检查容易失效

直觉上，很多人会在工具执行前加一个 `allowed_dirs` 检查：

```python
def read_file(path):
    if not any(str(path).startswith(d) for d in ALLOWED_DIRS):
        raise PermissionError("Not allowed")
    with open(path) as f:
        return f.read()
```

这段代码看起来能工作，但实际跑起来容易被绕过：

- **符号链接**：攻击者可以在白名单目录内创建指向 `/etc/passwd` 的符号链接，`startswith` 检查会通过。
- **路径规范化**：`/workspace/../etc/passwd` 展开后可能跳出白名单。
- **相对路径**：当前工作目录不确定时，`config.yml` 可能指向意想不到的位置。
- **多级写入**：Agent 可能先写入脚本，再执行脚本去访问外部路径，白名单仅限制文件操作反而形同虚设。

因此，一个工程上可用的白名单不仅要检查路径，还要**在路径解析之后**做范围校验，同时**禁用符号链接跟随**，并明确定义允许的操作类型。

## 做法：基于解析路径的目录沙箱

### 1. 核心校验逻辑

不要依赖字符串匹配，而应在所有操作之前执行**路径规范化 + 真实性检查**。Python 里可用 `Path.resolve()` 消解所有 `..` 和符号链接，然后检查其是否仍位于白名单内。

```python
from pathlib import Path

class FileGuard:
    def __init__(self, allowed_roots: list[Path]):
        # 将所有白名单根目录也 resolve 为绝对路径
        self.allowed_roots = [root.resolve() for root in allowed_roots]

    def check(self, target: Path) -> Path:
        """返回安全的绝对路径，若不安全则抛出异常"""
        resolved = target.expanduser().resolve()
        # 检查是否落在任一白名单根目录下
        for root in self.allowed_roots:
            try:
                resolved.relative_to(root)
                return resolved
            except ValueError:
                continue
        raise PermissionError(
            f"Access denied: {target} resolves to {resolved}"
        )
```

`relative_to` 会正确处理目录前缀关系，不依赖字符串比较。注意必须先 `expanduser()` 再 `resolve()`，否则 `~` 展开可能被绕过。

### 2. 包装文件操作工具

在 OpenClaw 中，文件工具通常以函数或工具类形式注册给 Agent。以 `read_file` 和 `write_file` 为例，包装后的版本：

```python
def safe_read_file(path: str, guard: FileGuard) -> str:
    allowed_path = guard.check(Path(path))
    # 额外约束：只允许读取纯文件，拒绝管道、设备文件等
    if not allowed_path.is_file():
        raise IsADirectoryError("Only regular files are allowed")
    return allowed_path.read_text(encoding="utf-8")

def safe_write_file(path: str, content: str, guard: FileGuard) -> None:
    allowed_path = guard.check(Path(path))
    # 写入前检查父目录是否存在，或直接要求已存在
    if not allowed_path.parent.exists():
        raise FileNotFoundError(
            f"Parent directory does not exist: {allowed_path.parent}"
        )
    allowed_path.write_text(content, encoding="utf-8")
```

**只允许读写常规文件**，禁止操作目录、设备节点或管道，缩小攻击面。同时，**不自动创建父目录**，避免 Agent 通过创建多级目录悄悄写入非白名单区域（如果某个父目录恰好是符号链接的话）。

### 3. 注入到 Agent 运行时

在 OpenClaw 中，通常通过环境变量或配置文件指定工具白名单。例如，可以在 Agent 初始化阶段：

```python
import os
from openclaw import Agent

workspace = os.environ.get("AGENT_WORKSPACE", "/tmp/agent-workspace")
guard = FileGuard([Path(workspace).resolve()])
agent = Agent(
    tools=[safe_read_file, safe_write_file],
    tool_kwargs={"guard": guard}
)
```

对于 MCP 插件，服务器端也应执行同样的沙箱逻辑。如果 MCP 服务器暴露了文件访问工具，建议在其实现中复用 `FileGuard`，而不是在客户端信任调用方。

## 踩坑点

### 1. `resolve()` 在文件不存在时失效
`Path.resolve()` 会尝试查找真实路径，如果目标文件不存在，它只解析已有目录部分，最后的非存在部分保留原样。这是对的，但要注意：恶意路径 `workspace/dangling` 本身可能是一个符号链接，即使未被创建，也可能解析到外部。好在 `resolve()` 会最大限度地消除中间的 `..`，只要白名单根路径本身是安全的，这种情况仍可接受。更严格的做法是 `lstat()` 中间组件，但负担过高，此处不建议。

### 2. Windows 盘符与网络路径
如果你在 Windows 上运行 Agent，`resolve()` 的行为略有差异，比如可以解析到 `\\server\share`。还需要注意 `C:` 的当前目录问题。设计白名单时建议只允许单个盘符下的某个目录，并禁用 UNC 路径。

### 3. 并发写入的 TOCTOU
检查路径和实际写入之间，文件系统状态可能改变。不过 Agent 运行环境多为单用户场景，TOCTOU 风险相对可控。若要求更高安全，可使用基于文件描述符的 `os.open` + `os.fdopen`，但这会牺牲跨平台便利性。

### 4. 白名单范围过于宽松
常见反例是将整个 `$HOME` 加入白名单，这将包含 `.ssh`、`.aws` 等敏感目录。正确做法是为每个 Agent 任务创建独立工作区（如 `/tmp/agent-run-uuid` 或项目子目录），并只授权该目录。

## 可复用建议

- **提炼为独立模块**：将 `FileGuard` 抽象成一个与 Agent 框架无关的库，通过依赖注入提供给工具函数，可以在不同 Agent、MCP 服务器间复用。
- **配合日志审计**：每次 `check()` 调用都记录原始路径和解析后路径，方便事后排查 Agent 的越权尝试。
- **与容器化叠加**：本地方案适合开发/调试场景，生产环境建议结合 Docker/K8s 的挂载白名单实现纵深防御。
- **定期使用符号链接扫描**：即使是白名单目录内部，也可能被其他程序留下恶意链接，定期扫描并清理风险。

## 总结

给 Agent 的文件能力套上本地目录白名单，核心不在于“限制”，而在于**明确边界**。一个好的护栏设计，既是安全底线，也是信任基石——它让你敢于把更复杂的自动化任务交给 Agent，而无需时刻提心吊胆。

实施时记住三个关键点：
1. 路径一定要 `resolve()` 后再做前缀检查；
2. 仅允许操纵常规文件，且不自动创建目录；
3. 白名单越窄越好，结合独立工作区使用。

当你的 Agent 走出“只能看”的演示阶段，真正开始改文件、跑脚本时，这道护栏就成为了工程可靠性的第一道防线。
