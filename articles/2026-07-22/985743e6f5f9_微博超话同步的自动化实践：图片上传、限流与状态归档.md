## 背景

微博超话签到、发帖是不少自动化爱好者的日常需求，特别是带图的超话帖，既能维持活跃度又有经验加成。早期的实现大多是一个简单的 Python 脚本，模拟登录后调用发帖接口。但把这件事放进一个长期运行的 Agent 里（比如基于 OpenClaw 的自动化助手），就会暴露出几个工程化问题：

- 图片上传格式、大小、比例处理不当时直接失败，错误信息含糊；
- 发帖接口会有**隐式限流**，连续请求会突然收到 429 或静默丢帖；
- 帖子发布状态（成功、失败、待重试）没有持久化记录，一旦 Agent 重启或网络抖动，根本不知道“上次发到哪了”。

本篇文章记录了一次实际改造过程：用 OpenClaw 的 MCP 插件结构封装微博动作，处理图片上传、限流退避，并引入本地状态归档，让同步任务从“跑一次看运气”变成可以审计、可恢复的长稳服务。

## 问题拆解

微博超话发带图帖的关键流程如下：

1. 登录获取有效 Cookie/Token；
2. 上传图片，获取 `pic_id`；
3. 调用发帖接口，填入超话 ID、文本、`pic_id`；
4. 检查返回，记录状态。

每个环节都可能出问题，尤其是在 Agent 长时间无人值守时：

- **图片上传失败**：大多数失败来自格式与大小。微博图片上传接口对 `Content-Type` 和文件名后缀敏感，部分客户端上报的 MIME 类型会被拒绝。超过 5MB 的图会被直接丢弃，不返回明确错误。
- **限流**：同一用户短时间内连续发帖或上传会有频率限制，返回 `{retcode: 100001}` 或 HTTP 429。若没有退避，连续失败会把账号风控拉满。
- **状态丢失**：原来脚本把状态存在内存里，进程一重启就忘光。如果恰好发帖成功但记录丢失，会导致重复发帖，触发抄袭检测和降权。

## 方案与结构

基于 OpenClaw 的 MCP 能力，我把“微博超话发帖”封装成一个 MCP 工具 `weibo_super_topic_post`，并在上下文管理上用 Agent 自身的状态文件做持久化。整体结构：

- **MCP 工具层**：接收参数（超话名、图片路径、文案），内部执行三步：图片预处理 → 上传 → 发帖。每次调用返回结构化结果，包含成功与否、错误码、使用的 `pic_id` 等。
- **限流控制器**：在工具内部维护一个本地的 token bucket，按账号维度限制上传和发帖的速率（例如每分钟不超过 1 次发帖，每 30 秒上传一张图）。并发任务通过 asyncio 锁串行化，保护 Cookie 不被登出。
- **状态归档**：每次工具调用都在 `$OPENCLAW_DATA/weibo_sync_state.json` 中追加一条记录，包括时间戳、超话 ID、帖子内容哈希、图片哈希、发布结果。任务重启时读取最后一条成功记录，跳过已完成的帖子。

## 图片上传的踩坑细节

图片上传是整个流程中最不透明的环节。我们踩过的坑包括：

1. **文件名与 MIME 类型**  
   微博上传接口接受 `multipart/form-data`，字段名 `file`。有些客户端默认用 `image/jpeg` 但后缀是 `.png` 会被拒绝。实践发现最好的做法是：读取图片二进制后，用 Pillow 转存为 JPEG 格式，强制后缀 `.jpg`，并显式设置 `Content-Type: image/jpeg`。同时忽略 EXIF 旋转信息，先对图片做 `ImageOps.exif_transpose`，否则竖屏照片发上去会是躺着的。

2. **像素与体积限制**  
   超过 5MB 必挂，尺寸无明确上限但过大图片会加大上传耗时，且容易被 CDN 反爬。我们将图片统一压缩到 1080px 宽（等比缩放），质量 85%，生成体积约 200~800KB，成功率 100%。

3. **上传接口域名的 `Referer` 检查**  
   微博上传需要匹配 `Referer: https://weibo.com/`，否则可能返回 `{"code":"100001","msg":"no referer"}`。这一点在浏览器自动化和直接 HTTP 请求中都要留意。

4. **`pic_id` 的时效**  
   上传返回的 `pic_id` 并不永久有效，实测超过 30 分钟未使用会失效。所以我们在工具内部将上传和发帖做成原子调用，避免先上传一堆图再慢慢发。

## 限流与错误恢复

我们遇到的限流主要有两类：**发帖频率限制**和**连续失败惩罚**。前者是常规限制，后者需要谨慎处理。

工具做法：
- 本地维护一个 `rate_limiter`，发帖前检查上次发帖时间，若间隔不足 `MIN_INTERVAL_SEC`（默认 90 秒），则 `sleep` 等待。这样避免触发硬限流。
- 遇到 429 或 `retcode=100001` 时，采用指数退避，初始等待 60 秒，最大 10 分钟。重试 3 次仍失败则标记为 `failed_need_manual`，并通过 Agent 通知用户检查账号。
- 对于非永久性网络错误（如连接超时、DNS 解析失败），退避后重试；对于非 2xx/3xx 且无明确限流特征的响应，也做重试，但在归档中记录详细响应体，方便排查。

错误恢复依赖状态文件：Agent 重启时，遍历归档中所有 `status=pending_retry` 的记录，按时间顺序重新执行。这样即使在发布过程中掉电，也能在恢复后自动补发，不会重复已成功的帖子（通过图片哈希去重检查）。

## 状态归档设计

归档文件采用 JSON Lines 格式，方便追加和人眼查看。每条记录结构：

```json
{
  "ts": "2025-02-14T09:02:10Z",
  "super_topic_id": "100808xxxx",
  "text_hash": "md5...",
  "image_hash": "sha256...",
  "pic_id": "abc123",
  "post_id": "4987xxx",
  "status": "success",
  "error": null
}
```

关键字段的作用：
- `text_hash` 与 `image_hash`：用来去重，避免重复发相同图文的帖子，同时在手动排查时可以快速定位。
- `pic_id` 与 `post_id`：用于事后回溯和可能的删除操作。
- `status` 枚举：`success`、`failed_rate_limited`、`failed_image_upload`、`failed_other`、`pending_retry`。只有 `success` 和 `pending_retry` 会被重新加载执行。

这种归档方式成本极低，即便积累几千条也不会影响查询速度，而且可以随时用 `jq` 或脚本做统计。

## 可复用建议

如果你在 OpenClaw 生态下做类似的异步自动化：

1. **把副作用（上传、发帖）放到 MCP 工具里**，Agent 只负责编排，不直接接触 Cookie 或表单细节。这样登录状态、限流控制都在工具层内聚。
2. **永远用结构化文件记录状态**，不要依赖内存。选择 JSON Lines 或 SQLite 都行，关键是能在重启后重建任务队列。
3. **处理多媒体文件时先标准化**：统一转格式、压缩尺寸、固定元数据。不要直接上传用户给的原图。
4. **限流逻辑必须包含退避和降级**，并为“连续失败超过阈值”设置熔断，避免账户被长时间封禁。
5. **把图片上传和发帖绑定为原子操作**，避免 `pic_id` 过期造成资源浪费。

## 总结

微博超话同步看似简单，但跑在长期 Agent 里时，图片上传的隐式规则、限流的随机触发、状态的易丢失，三个问题足以让任务变成“薛定谔的发帖”。通过 MCP 工具封装、本地限流控制器和 JSON 状态归档，我们把这个过程从一个不可靠脚本升级为生产可用的自动化任务。在 OpenClaw 提供的工具调度与上下文管理之上，这类带复杂副作用的自动化得以被清晰地建模和监控。希望这次拆解能为你的自动化实践提供一些避免踩坑的参考。
