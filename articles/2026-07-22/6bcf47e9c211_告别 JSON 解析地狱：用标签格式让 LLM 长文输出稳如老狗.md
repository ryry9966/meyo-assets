在给 OpenClaw 链上挂 Agent 做自动化处理时，有一个绕不开的场景：让大模型输出**结构化、可解析的原文片段**。最直接的方案是要求模型返回 JSON，可一旦内容变长、字段变多，解析失败的概率会直线上升——尤其是当你让模型同时生成摘要、标签、翻译、多轮对话等的复合输出。实践下来，把 JSON 换成**自定义标签格式**，在长文场景下稳定性提升非常明显。这篇帖子记录下我们踩过的坑和可复用的方案。

---

## 背景：为什么长文 JSON 容易炸

在 OpenClaw 的 MCP 管线里，典型需求是让 LLM 对一篇文章生成结构化的分析结果，例如：

```json
{
  "title": "标题",
  "summary": "一段较长的摘要，可能包含换行和特殊符号……",
  "tags": ["tag1", "tag2"],
  "sentiment": "positive"
}
```

模型一次生成几百到上千 token 的 JSON 时，出问题的概率比你预想的高很多，具体表现为：

- 忘记转义字符串内的双引号、反斜杠
- 多行字符串里混入了未转义的换行，直接破坏 JSON 结构
- 数组最后多一个逗号
- 模型突发奇想，在 JSON 前后加一段解释性文字
- 大括号不闭合，或嵌套深度出错

这些问题在短 JSON 里还能用 `json.loads` 的严格模式兜底，实在不行重试一两次。但长文输出时 token 消耗大，重试成本高，而且即使加上“请输出合法 JSON”的 prompt 也很难根治。

核心矛盾在于：**JSON 格式对字符级正确性要求极高，而 LLM 天然是概率模型，无法保证 token 级完美一致性。**

---

## 做法：从 JSON 迁移到自定义标签格式

思路很简单：用**开始/结束标签**把每个字段包裹起来，让解析变得容错且不依赖引号转义。例如：

```
<TITLE>如何提升 Agent 管道稳定性</TITLE>
<SUMMARY>
本文讨论了在 Agent 自动化管道中使用标签格式替代 JSON 的实践经验……
</SUMMARY>
<TAGS>Agent, 自动化, 解析</TAGS>
<SENTIMENT>positive</SENTIMENT>
```

### 1. 设计标签规则

- 标签名尽量用全大写，避免与正文内容重名
- 每个字段用成对标签包裹，开始和结束标签之间换行不影响解析
- 对列表/数组，直接用逗号分隔的字符串，避免嵌套结构
- 禁止在字段值中出现与结束标签相同的字符串（如 `</SUMMARY>`），如果担心，可以在 prompt 里加约束，或后处理简单做一次转义

### 2. Prompt 工程

在 system 或 user prompt 中明确要求模型“只输出标签块，不要带任何其他说明”，并给出示例。例如：

> 请严格使用以下标签格式输出结果，**不要使用 Markdown 代码块，不要添加任何额外解释**：
> <TITLE>标题</TITLE>
> <SUMMARY>摘要内容</SUMMARY>
> <TAGS>标签1, 标签2</TAGS>
> <SENTIMENT>positive/negative/neutral</SENTIMENT>

实践中加上“不要使用代码块”这一点很重要，否则模型可能会把整个标签内容包在 ` ``` ` 里，增加解析步骤。

### 3. 解析器实现

我们用简单的正则来提取，容忍标签间有空白符：

```python
import re

def parse_tagged_output(text: str) -> dict:
    pattern = r'<(\w+)>(.*?)</\1>'
    matches = re.findall(pattern, text, re.DOTALL)
    result = {}
    for tag, value in matches:
        value = value.strip()
        if tag == 'TAGS':
            value = [t.strip() for t in value.split(',') if t.strip()]
        result[tag.lower()] = value
    return result
```

`re.DOTALL` 保证跨行捕获，这对长摘要至关重要。需要注意标签名可能大小写混乱，统一转小写后再存进字典，方便后续处理。

### 4. 在 OpenClaw 工作流中集成

典型的调用链是：

`OpenClaw 任务 -> 调用 LLM -> 得到原始文本 -> 标签解析 -> 下个节点消费字典`

可以把上面的解析函数封装成一个 MCP tool 或直接在 Python 节点里用。如果解析失败（例如某个必需字段缺失），可以触发一次单字段补全的轻量重试，而不是整个长文重新生成。

## 踩坑点

1. **标签内出现“假结束标签”**  
   比如摘要内容本身包含字符串 `</SUMMARY>`。解决办法是在 prompt 中提醒模型转义，或要求对正文中的 `<` 进行 HTML 实体化（如 `&lt;`）。大多数情况下，告诉模型“请将文中出现的所有 `<` 替换为 `&lt;`”即可。

2. **模型在标签外加“废话”**  
   即使 prompt 里严禁，仍然可能输出“当然，这是分析结果：”之类的前缀。解析器需要足够鲁棒：只提取标签块，忽略标签外的内容。我们的正则已经能做到，因为在文本中查找所有 `<TAG>...</TAG>`，前后废话自然会被跳过。

3. **列表字段的逗号混杂**  
   如果标签值本身包含逗号（例如 TAGS 中有“AI, 机器学习”），按逗号 split 就分错了。权衡后我们的做法是要求模型用中文顿号或竖线分隔，或者干脆把 TAGS 改成多个标签行：  
   ```
   <TAG>Agent</TAG>
   <TAG>自动化</TAG>
   ```
   这样更稳定，解析时收集所有同名标签即可。

4. **模型只输出部分标签**  
   当要输出的字段多到 6、7 个，模型可能漏掉一个。建议在关键字段上做校验，缺失则直接丢弃或回退到默认值，并在日志中告警，方便监控。

---

## 可复用建议

- **长文结构化输出优先考虑标签格式**，除非下游系统强制要求 JSON。标签方案牺牲了少许可读性，换来极高的解析成功率。
- **永远不要完全信任模型的输出格式**，解析器必须写成容错模式，而非严格模式。
- **字段设计越扁越好**，避免嵌套。需要层次化数据时，考虑拆成多个独立标签块，由管道后续节点组装。
- **将标签方案沉淀为团队内部规范**，例如 OpenClaw 的 Step 节点统一用 `<FIELD_NAME>...</FIELD_NAME>` 结构，减少认知负担。
- **与 MCP 工具打通**：可以把标签解析做成一个 MCP Server 工具，OpenClaw 节点随时调用，错误处理标准化。

---

## 总结

从“追求标准 JSON”到“拥抱自定义标签”，本质上是一次工程思维的转变：**不再把 LLM 当成确定性序列化引擎，而是把它看成一个可能输出噪音的生成器，在自己可控的解析层消化掉不确定性**。

在 OpenClaw 的实际跑道上，这个转变极大缓解了长文生成的焦虑。JSON 没有错，只是不适合这种需要高容错的生成式场景。标签格式简单、粗暴、有效，尤其在 Agent 自动化管道里，稳定远比优雅重要。

下次你被奇怪的转义和花括号折磨时，不妨试试这一招。
