在构建 Agent 或自动化管线时，一旦需要 LLM 输出长文（如报告、合同、代码文档），并从中提取多个结构化片段，第一个反应往往是“让它输出 JSON”。这个选择很快会变成噩梦：解析失败、截断、幻觉添加注释……每次失败都是 token 和时间的浪费。本文记录我们从“坏 JSON”切换到自定义标签格式的实战经历，涵盖设计、解析、踩坑和可复用方案，适合在 OpenClaw/MCP 等环境中需要稳定提取长文本的场景。

## 为什么 JSON 在长文里这么脆？

JSON 天生适合短程、严格的数据交换，但 LLM 是概率生成器，长文输出中容易出现：

- **截断**：max_tokens 限制导致 JSON 在中间断开，缺括号或缺引号。
- **转义地狱**：正文中本可能出现双引号，模型有时忘记加反斜杠，甚至连续转义混乱。
- **多余文本**：模型会在 JSON 前后加说明、Markdown 代码块标记，或者写 `// 注释`。
- **嵌套失衡**：长篇 JSON 里的括号容易遗漏，一个 `]` 缺失就让整个对象不可解析。
- **流式困局**：传统 JSON 解析必须等待完整响应，无法利用流式片段提前提取。

我们在一个日报摘要生成 Agent 里统计过，使用 JSON 方式时，长文（>2k tokens）的直通解析成功率仅约 82%，其余都需要重试或手动修复，严重影响管线稳定性。

## 转向标签格式：核心思路

我们不再要求模型输出一个完整的 JSON 树，而是用类似 XML 的自定义标签划分不同语义块。例如：

```
<summary>
今天讨论了接口优化方案，包括缓存策略…
</summary>
<action_items>
- 实现 Redis 缓存层
- 更新监控面板
</action_items>
<risks>
缓存穿透风险需要额外限流
</risks>
```

解析侧不再用严格的 JSON 解析器，而用**轻量级标签提取器**，用正则或状态机按标签名捞出对应内容。即使整体输出不完美，只要目标标签完整，就能成功提取；一旦标签未闭合，也能做“最佳努力”恢复。

## 实施步骤

### 1. 设计不易冲突的标签名
避免使用可能出现在正文中的普通单词。推荐三种策略：
- 用项目前缀，如 `<oc_summary>`、`<oc_actions>`。
- 用特殊分隔符，如 `<::summary::>`、`<||key_points||>`。这能极大降低误匹配概率。
- 在提示中明确指示：**如果正文中需要出现标签本身，请替换为全角符号或转义**，但不强制，否则增加模型负担。

### 2. 修改 Prompt，给出清晰示例
在系统提示中加入结构化指令：

```
请严格按以下格式输出，不要添加额外解释，不要将标签包裹在代码块中：
<oc_summary>
...你的摘要...
</oc_summary>
<oc_items>
- 事项一
- 事项二
</oc_items>
```

示例比文字描述重要得多。给出真实、简短的例子，模型对格式的遵守度会显著提升。

### 3. 实现健壮的标签提取器
别直接上 XML 解析库（太严格且易抛异常）。实用方案是**基于正则 + 最小匹配**，或写个简单的状态机：

```python
import re

def extract_tag(text: str, tag: str) -> str | None:
    pattern = rf'<{tag}>(.*?)</{tag}>'
    m = re.search(pattern, text, re.DOTALL)
    return m.group(1).strip() if m else None
```

如果要处理流式场景，可以维护一个缓冲区，每收到新 token 就检查是否有刚闭合的标签，有则立即 yield 该片段。

### 4. 错误恢复策略
当所有闭合标签都不完整时（比如因 max_tokens 截断），可以：
- 将 `<oc_items>...` 未结束的部分当作最后一个标签的内容读出来。
- 尝试自动插入缺失的闭合标签，然后再次提取。
- 若 Tag 格式严重损坏，回退为“返回整个原始文本”，由人工或二次 LLM 修复。

## 踩坑笔记

- **标签注入**：哪怕用 `<oc_` 前缀，仍有极低概率在代码片段或高亮文本中出现相同串。我们遇到过一个案例，`<oc_items>` 出现在示例代码里。解决：在 Prompt 中增加约束：“如需展示标签，请用 `&lt;` 和 `&gt;` 替代”。模型基本能遵守。
- **Markdown 代码块干扰**：模型固执地在输出前后包裹 ````xml ... ````。采用先去代码块外套，再提取标签。
- **流式中的半截标签**：一定要区分“未闭合”与“永久丢失”。设置一个等待阈值（如 5 秒无新 token），超时后按未完内容提取。
- **多标签顺序依赖**：不要假设标签出现顺序固定。解析器应独立提取各标签，容忍顺序错乱。
- **与 function calling 共存**：某些场景需要同时用 tool call 和长文提取。我们让模型在完成 tool call 后，用标签格式发送最终结果，互不干扰。

## 可复用建议

- 封装一个 **TagExtractor** 工具，输入原始文本，返回 `dict[str, str]`，内部处理 Markdown 脱壳、流式缓冲、自动闭合。
- 在 OpenClaw 的 Agent 配置中，将“长文输出格式”项设为 `tag-based`，让开发者无需逐个处理。
- 监控标签完整率（如 `sum(extracted_length) / total_length`），低于阈值时触发一次温和重试（“请修正格式后重新输出”），因为我们发现模型在被告知“格式不完整”后修复率很高。
- 避免嵌套太深。标签设计尽力扁平化，每层只取一个列表或段落。确实需要嵌套时，可以用不同前缀区分：`<oc_section name="intro">...</oc_section>`，再通过属性名聚合。

## 结果与总结

在相同日报生成任务上，切换自定义标签方案后，解析成功率从 82% 提升到 99.3%，重试次数下降 80%，并成功支持了流式提取，平均延迟降低了约 1.8 秒。它的原理其实很简单：**将解析复杂度从 LLM 转移到工程侧**，用更宽容的格式吸收概率生成的不确定性。

当你在 OpenClaw 的 Agent 或 MCP 工具链中，需要一个既稳定、又能流式提取的长文输出方案时，不妨试试标签格式。它不是什么银弹，但一定比光靠 JSON 和祈愿要好得多。
