## 背景

在 OpenClaw、Agent、MCP 组合的自动化内容流水线里，我们很容易把精力放在“生成”和“发布”环节，却忽略一个关键操作：**把生成物可靠地存下来**。文章推送到平台、图片上传到 CDN 后，本地往往只剩下零散的临时文件，或干脆什么都没有。等需要复盘生成质量、重新编辑、或切换发布平台时，才发现原始内容早已无处可寻。

这时候需要一个轻量的本地归档机制，它不应引入重型数据库，但要能记录：

- 文章 Markdown 原文
- 关联的图片文件（封面、内嵌插图）
- 生成元数据（时间、prompt、标签、发布状态等）

一个行之有效的做法是**以文件夹为单元，用 `assets.json` 充当索引**。

## 要解决的问题

1. **内容散失**：生成结果仅存活在平台缓存或临时目录，本地无法回溯。
2. **图片外链不可靠**：直接引用远程 URL，链接可能过期、被替换，归档时图片未下载将导致信息不完整。
3. **缺乏结构化元数据**：只有文章本身，没有记录生成条件，后续难以复现或审计。
4. **与现有流水线松散集成**：归档不能成为新的维护负担，必须对自动流程几乎透明。

## 做法与步骤

### 1. 归档目录结构设计

按日期或主题划分归档单元，每个单元一个文件夹：

```
archive/
└── 2025-01-17_how-to-build-pipeline/
    ├── article.md
    ├── img/
    │   ├── cover.png
    │   └── diagram.png
    └── assets.json
```

所有与这篇文章相关的资源都圈在同一命名空间下，迁移、备份、版本管理都直接操作文件夹即可。

### 2. assets.json 字段规范

`assets.json` 是核心索引文件，建议最小字段如下：

```json
{
  "id": "2025-01-17_how-to-build-pipeline",
  "title": "How to Build an Automated Content Pipeline",
  "markdown": "article.md",
  "images": [
    "img/cover.png",
    "img/diagram.png"
  ],
  "created": "2025-01-17T10:30:00Z",
  "tags": ["automation", "openclaw"],
  "prompt": "Write a technical post about...",
  "source": "agent:writer-alpha",
  "status": "published"
}
```

可以根据实际需要扩展方言字段，但保持核心字段一致，方便跨项目读取。

### 3. 在流水线中实现自动归档

以典型的 Python 脚本为例，在内容生成、图片下载完成后插入归档步骤：

```python
import json
import shutil
from pathlib import Path
from datetime import datetime, timezone

def archive_post(base_dir, markdown_text, image_paths, meta):
    unit_dir = Path(base_dir) / meta["id"]
    unit_dir.mkdir(parents=True, exist_ok=True)

    # 1. 写入 markdown
    article_path = unit_dir / "article.md"
    article_path.write_text(markdown_text, encoding="utf-8")

    # 2. 拷贝/下载图片到 img/
    img_dir = unit_dir / "img"
    img_dir.mkdir(exist_ok=True)
    relative_images = []
    for src in image_paths:
        dest = img_dir / Path(src).name
        shutil.copy2(src, dest)  # 也可用 requests 从 url 下载
        relative_images.append(f"img/{dest.name}")

    # 3. 生成 assets.json
    assets = {
        **meta,
        "markdown": "article.md",
        "images": relative_images,
        "created": datetime.now(timezone.utc).isoformat()
    }
    (unit_dir / "assets.json").write_text(
        json.dumps(assets, ensure_ascii=False, indent=2),
        encoding="utf-8"
    )
```

在 OpenClaw 的 agent 里，可以将这段逻辑封装为 post-process step；如果使用 MCP，可以暴露一个 `write_archive` 工具，让 Agent 通过标准协议触发归档。

### 4. 与 OpenClaw / MCP 的集成建议

- **Agent 侧**：将归档作为一个可选的 `finally` 动作——无论发布是否成功，都尝试保存本地副本。
- **MCP 工具侧**：定义一个资源写入接口，接收对应参数，由服务端落地文件。
- **Git 版本控制**：将 `archive/` 目录纳入 Git 仓库（或使用 `git-annex` 管理大文件），自动获得历史版本追溯能力。

## 踩坑点

1. **图片路径混乱**  
   最初图片可能来自临时目录、远程 URL 或 Base64 内嵌。要统一处理：先判断图片来源，再决定是 `shutil.copy`、`requests.get` 还是解码写入。注意文件名冲突，可用内容哈希重命名避免覆盖。

2. **JSON 序列化陷阱**  
   Markdown 正文可能携带特殊字符，`json.dumps` 时务必使用 `ensure_ascii=False`，并注意转义。不要把整个 Markdown 塞进 `assets.json` 里（放在单独文件更干净）。

3. **并发写入**  
   如果多个 Agent 进程可能同时创建同一个 `unit_dir`，`exist_ok=True` 只能解决目录已存在，但无法防止文件写冲突。最好用基于时间的唯一 ID（例如 `20250117T103000Z-slug`），或在归档前加锁。

4. **大图片与磁盘占用**  
   连续运行流水线会产生大量图片，建议定期清理过期归档，或对图片做有损压缩，再写入归档目录。

5. **索引一致性问题**  
   如果下载图片中途失败，`assets.json` 里记录的图片列表与实际文件不匹配。应在所有图片成功落盘后再写入 `assets.json`，失败时整体回滚（删除已拷贝的临时文件）。

## 可复用建议

将上述归档逻辑封装为一个独立工具（命令行或 MCP 工具），使其对任何内容流水线可用。例如：

- `archive-cli --base-dir ./archive --id "post-slug" --md article.md --images img/*.png --meta '{"title":"..."}'`
- 或提供一个 MCP server：`archive-tool`，暴露 `archive_post` 资源。

这样不同的 Agent 或流水线编排工具（如 n8n、Temporal）都可以复用同一套归档规范，避免每个项目重复造轮子。

另外，结合 `assets.json` 的索引，可以写一个简单的本地查看面板（静态 HTML），遍历所有归档单元，按时间、标签过滤，极大地提升回溯体验。

## 总结

本地归档不是一次性的脚本补丁，而是自动化内容生产闭环的必备环节。以文件夹 + `assets.json` 为基本单元，兼顾了可读性、可迁移性与可扩展性。实现简单，但对提升工程可靠性帮助巨大。

将其固化为流水线的标准步骤后，你会发现：出了问题有现场可查，改稿时有原稿可依，迁移平台时有完整素材在手——这几点，就足够支撑一个严肃的内容自动化系统。
