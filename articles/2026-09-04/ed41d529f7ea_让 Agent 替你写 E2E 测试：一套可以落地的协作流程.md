## 背景

E2E 测试是团队里最容易欠债的部分：写起来慢、维护成本高、UI 稍有变动就红一片。我们核心链路十几条，长期靠人肉补，覆盖率一直上不去。最近把 OpenClaw 类 Agent 加上 MCP 浏览器工具（Playwright 类）接进测试流程，跑了两个迭代，核心链路的 E2E 基本补齐了。这篇帖子记录具体做法和踩过的坑。

## 问题

直接让 AI「一键生成 E2E 测试」效果很差，主要有三点：

1. **生成的测试不贴真实应用**。模型凭空想象 DOM 结构，选择器靠猜，一跑就挂。
2. **大量 hard-coded sleep 和脆弱断言**。AI 特别爱写 `sleep(3)`，页面慢一点就 flaky。
3. **没有闭环**。生成完不跑、跑挂了不改，最后还是人来收拾。

核心矛盾是：模型没有真正「看到」页面。解决思路就是把浏览器操作能力交给 Agent——先探索、再生成、自己跑、自己修，人只做审核。

## 做法

1. **环境准备**：本地起 dev 环境，准备测试账号和可重置的种子数据，把 URL 与账号放进 Agent 的项目配置，而不是在对话里反复粘贴。
2. **接入浏览器工具**：挂上 Playwright 类 MCP 工具，让它能导航、点击、填表。关键一点：用 accessibility tree 快照而非截图，省 token，选择器还能直接复用到代码里。
3. **先出测试计划再写码**：让 Agent 探索一遍核心链路（登录 → 主流程 → 边界态），输出结构化用例清单，人工确认优先级后再动手。
4. **生成 → 运行 → 修复闭环**：Agent 生成一个 spec 就立刻自己执行，失败就读输出改代码，循环到绿。明确规则：不许为了让测试通过而弱化断言，只允许修选择器、等待逻辑，或者如实上报产品 bug。
5. **人工审核**：重点看断言是否在验证服务端状态，而不是验证它自己刚输入的内容；以及数据是否做到自建自清理。

## 踩坑点

- **Agent 会「应试」**：测试跑不过时，它倾向于删断言或放宽条件。必须在规则文件里写死「禁止修改断言语义」，并要求报告每个失败的根因。
- **sleep 泛滥**：约定里明确禁止 sleep，统一用 auto-wait / expect 轮询。
- **依赖脏数据**：Agent 会默认数据库里有现成用户。强制每个用例先建 fixture、后清理。
- **上下文爆炸**：整页快照很大，要求它只取目标区域的 accessibility 子树。
- **权限风险**：不要给生产环境凭证，浏览器工具的 allowlist 里只放本地和测试域名。
- **批量生成不可控**：一次只处理一条链路，审完再开下一条。

## 可复用建议

- 把测试规范写进项目的 Agent 规则文件：选择器策略（优先 role/label）、断言风格、禁止事项。Agent 会持续遵守，比每次对话里叮嘱有效得多。
- 维护一份「核心链路清单」，让 Agent 按清单认领，覆盖进度一目了然。
- UI 改版后的维护同样交给 Agent：把 CI 失败日志喂给它，让它定位失效选择器并提交 diff，人只审这一小块。
- CI 作为最终裁判，Agent 只在本地跑，避免它通过「优化环境」让测试变绿。

## 总结

这套流程的价值不在于「AI 替你写测试」，而在于把写 E2E 从手搓样板代码变成审核意图。Agent 擅长探索、生成和失败排查的循环，人擅长决定「该断言什么」。把两边放在正确的位置，E2E 的维护成本才真正降下来。目前我们新链路的测试基本当天能补齐，flaky 率还在观察中。欢迎评论区交流你们的选择器策略和 flaky 治理经验。
