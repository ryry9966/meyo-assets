## 背景

OpenClaw 用上三个月，我的 memory 目录积累了 140 多条 markdown 记忆：部署记录、个人偏好、项目上下文、踩坑笔记。`memory_recall` 是这些记忆进入上下文的唯一闸门——检索质量差，助手不是“忘了”就是“记错”。社区里反复被问的一个问题：记忆检索该用语义搜索还是全文搜索？

我的结论先放这里：这不是二选一，而是一道分诊题。下面是实测过程。

## 问题

两种检索各有明确的失效场景：

- **语义搜索**靠 embedding 理解意图，“我之前怎么处理过证书过期”能召回一年前那条笔记，但对精确标识符（命令、路径、版本号）容易漂移。
- **全文搜索**（BM25/LIKE）精确命中关键词，但中文分词和同义改写基本不管。

单看描述选不出来，只能跑数据。

## 做法

**1. 建评测集。** 从自己的记忆里抽 40 条，配 40 条查询，人工标注期望命中的片段 ID。查询分三类：

- 精确型（含命令/组件名，如“pgbouncer 那次超时”）
- 模糊型（如“之前证书过期怎么处理的”）
- 时效型（如“上周部署了什么”）

**2. 三种模式各跑一遍。** 语义：中文 embedding 模型 + cosine，取 top-5；全文：BM25，中文用 ngram 分词；混合：两路各取 top-10，RRF 融合回 top-5。

**3. 看三个指标。** Top-5 命中率、MRR、无效召回比例（返回了不该进上下文的片段）。

**结果：** 模糊型语义明显赢（78% vs 41%）；精确型全文赢（86% vs 52%），语义常把 pgbouncer 混成其他连接池；时效型两边都差，语义分不清“上周”和“上个月”写的两条部署记录。混合方案综合最高，无效召回略增但可控。

## 踩坑点

- **中文全文检索默认分词器基本不可用**，ngram 或 jieba 是前提，否则整句匹配一个词都命中不了。
- **嵌入模型别只看榜单**：记忆是中英代码混杂文本，通用英文模型效果很差，换多语模型后命中率直接 +15%。
- **分块按 markdown 标题切**，比固定 512 token 强——记忆本来就是一条一事。
- **混合检索的 k 别贪大**：top-5 之后噪音开始污染上下文，助手反而答非所问。
- **换 embedding 模型必须全量重建索引**，两代向量混在一个库里的召回是灾难。

## 可复用建议

1. **记忆质量大于检索算法。** 写入时一条一个主题、带日期和标签，检索时先按元数据过滤再排序，收益比调任何检索参数都大。
2. **直接上混合检索（BM25 + 向量 + RRF），不要单选。** 若你手头版本的 OpenClaw 记忆检索只支持单一模式，宁可在外面包一层检索脚本，把融合结果喂回工具调用。
3. **评测集是资产。** 每次换模型、改分块后重跑一遍，三分钟避免一次“感觉不对但说不出哪不对”。
4. **时效类查询靠元数据不靠语义。** 给记忆条目加时间字段，召回后按时间加权，embedding 模型解决不了时间感。

## 总结

语义负责意图，全文负责标识符，元数据负责时效，RRF 把三者缝起来。这轮调优最大的教训不是选了哪个检索器，而是：先花半天建一个 40 条的评测集，之后所有关于记忆的争论都能用数据终结。记忆系统没有银弹，只有持续维护的管线。
