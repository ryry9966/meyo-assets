## 背景

我们团队用 OpenClaw 跑内容自动化：Agent 负责选题和写稿，产出统一是 Markdown；下游要发到博客、掘金、公众号三个地方。写稿环节跑顺之后，瓶颈反而变成了格式适配——同一篇稿子，三个平台三种渲染逻辑，人工搬运既慢又容易漏。

## 问题

核心矛盾是：AI 生成端只认一种 Markdown，发布端各说各话。

- 公众号编辑器不收 Markdown，只吃内联样式的 HTML，`class` 属性会被剥掉；
- 图片外链在公众号常被防盗链拦截，必须走素材库重新上传；
- 代码高亮库默认输出 `class`，同样要内联；
- 表格在移动端溢出、软换行语义差异、公式和图表各平台支持参差；
- 自动化链路里没人逐篇盯渲染结果，错了就是事故。

## 做法

管线分五步，核心原则：**在 AST 层做转换，正则只做兜底**。

1. **源头约束**。Agent 的 system prompt 里限定 CommonMark + GFM 子集：禁内联 HTML、禁脚注、禁图表语法，列表和代码块结构从简。源头守住，下游少一半逻辑。接收侧再用 markdownlint 卡一道，防 prompt 漂移。
2. **解析为 AST**。用 remark 把 Markdown 解析成 mdast，后续所有变换都作用在节点上。字符串级替换在嵌套代码块面前必翻车，这条是学费换来的。
3. **平台适配器**。定义统一接口 `render(mdast, ctx) → 平台载荷`，每个平台一个 adapter：公众号走 md→内联样式 HTML（shiki 配置成内联输出高亮），掘金基本透传加 front-matter，博客补元数据。适配器用注册表挂载，新增平台不动主线。
4. **资源处理**。图片统一下载、按内容 hash 命名、上传到目标平台素材库，本地缓存 hash→URL 映射。重跑管线不重复上传，也顺便解决防盗链。
5. **校验与暴露**。每个平台维护一组 golden file 做快照测试；输出侧再跑一次 lint（无 `<script>`、无外链 CSS）。最后把整条管线包成 MCP tool，Agent 只需 `publish(content, target)`。

## 踩坑点

- **正则替换代码块**：最早用正则调标题层级，遇到代码块里的 `#` 注释直接改写原文，之后才切到 AST。
- **公众号吃标签**：`<div>` 部分场景被吞，`section` 更稳；单个换行不渲染，转换时要显式补 `<br>`。
- **AI 越界输出**：偶尔把整段 HTML 包在代码块里交回来。我们的处理是后处理检测 + 打回重写，而不是静默剥离——静默剥离会让上游以为格式没问题。
- **幂等性**：图片没做内容寻址时，重跑一次就传一批重复素材，平台配额很快烧完。

## 可复用建议

1. 源头约束永远比下游修补便宜，prompt 约束 + lint 双保险；
2. 任何格式转换先上 AST，正则留给最后清洗；
3. 资源与内容分离，图片用内容寻址缓存；
4. 适配器即 MCP tool，Agent 侧不感知平台差异，管线侧迭代不惊动上游。

## 总结

多平台发布本质上是个编译问题：Markdown 是源码，各平台是目标架构，适配器是后端。把格式适配从 Agent 的职责里剥离成独立管线，Agent 专注内容，格式问题变成可测试、可回滚的工程对象。这条管线我们跑了两个月，发布环节从每篇半小时人工降到全自动，翻车率基本归零。欢迎在社区交流各平台的适配器实现细节。
