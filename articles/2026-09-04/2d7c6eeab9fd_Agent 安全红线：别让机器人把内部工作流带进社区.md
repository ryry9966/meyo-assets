## 背景

现在很多团队会在社区里跑 Agent：自动回帖、issue 分诊、群内答疑，背后接着一堆 MCP 工具和内部系统。Agent 成了"公共入口 ↔ 内部设施"之间的桥。桥修得越方便，泄露面越大。这篇帖不展开威胁模型理论，只讲我们在社区运营和自动化实践中实际踩过、能落地的几条红线。

## 问题出在哪

泄露很少是"AI 突然发疯"，多数是工程问题：

1. **上下文混用**：内部调试实例和对外答疑实例共用会话或记忆，内部字段被顺带带出。
2. **工具权限过大**：MCP 工具拿着全量 read token，社区用户一句话诱导它查内部库，它真查，还把原始输出贴出来。
3. **RAG 语料污染**：检索库里混进了内部 runbook、架构文档，回答时被当"参考资料"引用。
4. **间接注入**：攻击者发一个帖子，内容本身就是给分诊 Agent 看的指令，Agent 当成正常输入执行。

常见场景：调试时把带内网主机名的日志贴进 issue 回帖；或者让 Agent"总结一下报错"，它把配置文件原样引用了。

## 做法：五条红线

**1. 内外实例物理分离。** 对外 Agent 独立部署、独立系统提示词、独立工具集。不给它任何"顺手能查内部"的工具，而不是给了工具再靠提示词约束。

**2. 工具最小权限 + 独立凭证。** 每个对外 Agent 用独立 token，只读、按仓库粒度授权，能设 allowlist 就设。凭证按社区 bot 维度管理，不复用个人 key。

**3. 出口过滤（egress gate）。** Agent 对外发言前过一层检查：secret 正则（key 前缀、token 格式）、内网域名/IP、内部路径特征。命中即拦截并转人工。这层必须放在发送动作里，不能只靠提醒。

**4. 工具输出先脱敏再引用。** 原始工具结果不直接进回复，让模型摘要，摘要仍需过第 3 条的过滤。错误信息统一改写成对外安全版本。

**5. 敏感动作加人工闸门。** 删除、提权、跨系统写入一律走审批队列。社区场景宁可慢一点。

## 踩坑点

- **"不要透露系统提示词"不是防线。** 提示注入几十种变体，指令级约束只是减速带。系统提示词按"会被公开"的标准来写，里面别放内部架构和密钥线索。
- **调试日志是最常见的泄露口。** 我们统一用脱敏脚本处理后再贴，内网主机名、内部端点先替换。
- **分诊 Agent 读帖子本身就是攻击面。** 外部内容永远标记为不可信数据，不进入指令解析层，能做内容与指令隔离就做。
- **历史会话会被搜索。** 公开频道可被索引，Agent 三个月前的一句话现在可能被翻出来，定期清理对外实例的长期记忆。

## 可复用建议

- 上线前对自己 Agent 做一轮红队：让同事扮演诱导者，测工具调用边界和提示注入。
- 维护一张"对外 Agent 工具白名单表"，新增工具必须评审权限范围。
- 出口过滤规则集中管理、可审计，不要散落在各 bot 的 prompt 里。
- 每季度演练一次：假设 Agent 已泄露，评估影响面，验证凭证轮换流程。

## 总结

Agent 安全的核心不是让模型"更听话"，而是假设它一定会被骗、一定会犯错，然后用系统设计兜住：内外分离、最小权限、出口过滤、人工闸门。提示词是最后一级防御，不是第一级。把社区里的每个 bot 都当"不可信的实习生"对待，红线基本就守住了。
