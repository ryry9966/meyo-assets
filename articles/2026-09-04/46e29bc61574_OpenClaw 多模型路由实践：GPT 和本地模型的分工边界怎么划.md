## 背景

OpenClaw 的一个 Agent 跑起来，背后其实是几十种不同性质的子任务：规划拆解、工具调用、批量摘要、格式化输出、简单分类。如果全部走云端 GPT，账单和延迟都难看；如果全部切到本地模型，复杂任务的质量又撑不住。多模型路由就是为了解决这个“一刀切”的问题——让每个子任务落到合适的位置。

## 问题

路由本身不难配，难的是**边界**。我们团队最初的困惑是：哪些任务值得花 GPT 的钱，哪些用本地 7B/14B 就够？判断标准靠感觉，结果要么省钱但重试爆炸，要么质量稳定但成本没降下来。

## 做法

我们的落地方案分四步，供参考：

1. **给任务打标**。在 Agent 的任务描述里加两类标签：`sensitive`（涉及私有数据，强制本地）、`complex`（规划/多步推理，强制云端）。其余任务进入动态路由。
2. **配置路由规则**。在 OpenClaw 的 model pool 里注册云端和本地端点（本地走 Ollama/vLLM），路由规则按优先级排：标签规则 > token 长度阈值（超过 8K 走云端）> 默认云端兜底。
3. **设 fallback 链**。本地模型调用失败或输出解析失败两次，自动升级到云端并记录原因。这一步很关键，是本地模型“敢用”的前提。
4. **小评测集回归**。攒 50~100 条真实任务样本，每次调路由规则后跑一遍，看三个数：成功率、平均成本、P95 延迟。不跑评测就调规则，等于盲调。

## 踩坑点

- **本地模型的 function calling 不稳**。小模型生成工具调用参数经常格式漂移，修复输出的代码比省下的 API 费还贵。后来我们把工具调用一律收归云端，只把摘要、改写、分类留给本地。
- **路由器自身误判**。用便宜的小模型做任务分类确实省成本，但它会把伪装成简单任务的复杂活儿分给本地，重试链路反而更烧钱。分类器宁可保守一点。
- **长上下文陷阱**。本地模型上下文窗口小，静默截断后任务悄悄丢失关键信息，且不易察觉。凡是依赖长文档的任务，直接排除在本地候选之外。
- **embedding 混用**。本地和云端各自用不同的 embedding 模型，向量库检索质量莫名其妙下降。统一 embedding 服务，别混。
- **尾部延迟**。夜间批处理把本地 GPU 占满后，白天交互任务卡成幻灯片。给本地推理加并发上限，交互任务优先。

## 可复用建议

- **按任务性质路由，不要按模型价格路由**。性质稳定，价格会变。
- 每条路由记录 model、token、cost、latency、retry 次数，两周数据就能看清边界在哪。
- 默认云端兜底，逐步下放本地，而不是反过来。
- 路由规则进版本控制，改动必须过评测集。

## 总结

多模型路由不是“选哪个模型”的问题，而是一个持续运维的工程问题。从最简单的标签规则开始，用真实数据划边界，比任何攻略都可靠。省钱和质量的平衡点，是跑出来的，不是拍出来的。
