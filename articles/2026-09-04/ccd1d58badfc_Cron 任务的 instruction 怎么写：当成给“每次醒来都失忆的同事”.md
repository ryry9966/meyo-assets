## 背景

OpenClaw 的 cron 任务，本质是“定时唤醒一次 agent，塞给它一段 instruction，跑完即散”。这段 instruction 就是唯一接口：没有上下文可查，没有你在线答疑。所以它不该是一句日常对话，而更像一张写给“每次醒来都失忆的同事”的工单——假设它什么都不记得，把该交代的都写清楚。

## 问题

实践中最常见的三种翻车：

1. **太模糊**。“帮我看看仓库有没有动静”，agent 不知道看什么、什么算“有动静”、看完发给谁。要么瞎跑一通工具，要么反过来向你提问——而定时任务没人接话，这次运行就废了。
2. **没有输出契约**。跑完往哪儿发、什么格式、没结论要不要说话，全没定义。结果往往是该响的时候没响，不该响的时候刷屏。
3. **没有静默路径**。多数定时任务 90% 的运行结果是“无事发生”，但 instruction 里没写这种情况，agent 为了“完成汇报”会硬凑内容。

## 做法

我现在的模板固定五段：

```text
【目标】一句话说清这次运行要产出什么。
【上下文】当前时间以系统时间为准；涉及相对时间先换算成绝对日期再执行。
【步骤】允许使用的工具、执行顺序、最多调用次数。
【输出契约】结果发送到哪个会话/频道、什么格式、超过 N 行只发摘要。
【静默与失败】满足什么条件才发送；无更新则不发送；工具失败时发一行错误说明。
```

举个对比。反例：`每天早上 8 点总结一下昨晚的 issue`。

改成：`读取 GitHub 工具中 repo X 过去 24 小时（以系统时间为准）新增或关闭的 issue；仅当有新增或状态变化时，向 #dev-daily 发送不超过 5 行的摘要（编号+标题+状态）；无变化则不发送；工具调用失败时发送一行错误信息。`

关键变化就三点：相对时间被钉死、输出目标显式、补上了静默条件和失败行为。

## 踩坑点

- **时区**：cron 表达式按网关时区触发，instruction 里再写“早上”容易对不上，表述统一换成绝对时间或“以系统时间为准”。
- **状态假设**：别指望这次运行记得上次干了什么。需要去重或增量，就把状态写到文件里，instruction 中明确“先读后写”。
- **一个任务干五件事**：拆开。合并任务中任何一步失败，整体语义就崩了，排查也困难。
- **写死日期和路径的 instruction 会腐烂**：把可变部分收拢到单独一段，改起来不用通读全文。
- **只测了“有货”的路径**：上线前手动触发一次有数据的运行，再触发一次没数据的运行——翻车的往往是后者。

## 可复用建议

把每条 cron instruction 当 API 设计：输入（触发时能拿到什么）、处理（允许哪些工具、调用预算多少）、输出（发到哪、什么格式）、边界（什么时候闭嘴）。写完自问三个问题：**它知道现在几点吗？它知道结果发给谁吗？它知道什么时候可以什么都不做吗？**三个都能答上来，这条任务基本就稳了。

## 总结

Cron instruction 的质量不取决于长短，而取决于有没有把“时间、目标、输出、静默”四个变量钉死。它是写给失忆同事的一次性工单，不是聊天。按接口的标准去写，定时任务才能从“偶尔灵”变成“可依赖”。
