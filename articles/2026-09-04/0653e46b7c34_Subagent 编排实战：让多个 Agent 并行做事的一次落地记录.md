## 背景

OpenClaw 里的主 agent 在长会话中有两个老问题：上下文越长越"钝"，以及工具调用全串行，一个跑完才能跑下一个。框架支持派生 subagent——每个子 agent 有独立上下文，跑完把结果交回主 agent。听起来很美好，但真正编排起来有不少细节要处理。这篇记录一次实际任务里的做法和踩坑。

## 问题

场景：对一个小型 monorepo 做每周例行体检，包含三个独立子任务：

1. 扫描最近一周的 diff，总结风险点；
2. 检查 CI 日志中 warning 的变化趋势；
3. 核对文档与实际配置是否漂移。

之前让一个 agent 顺序做完，耗时 15 分钟以上，而且扫描 diff 产生的大量中间内容撑满了上下文，最后写总结时质量明显下滑。三个任务彼此独立、以读为主，天然适合并行。

## 做法

1. **拆分原则**：任务间无共享可变状态，输出可结构化。三条子任务互不写同一批文件，输出统一约定为 JSON：

```json
{ "task": "diff_scan", "risk_items": [...], "evidence": ["path:line"] }
```

2. **子 agent 的 prompt 必须自包含**。主 agent 的上下文不会自动带给子 agent，仓库路径、时间范围、输出 schema 都要写全，不能指望它"知道"背景。
3. **并行派发**：主 agent 在同一轮发起多个 subagent 调用，三个子任务同时跑，总耗时压到最慢子任务的水平，约 5-6 分钟。
4. **汇总单独做**：主 agent 收齐三份 JSON 后只基于结构化结果写周报，不让子 agent 直接输出散文——散文没法可靠合并。
5. **兜底**：每个子 agent 设超时；失败时返回明确的 error 结构，汇总时标注"该项缺失"，而不是静默跳过。

## 踩坑点

- **上下文继承想当然**：第一次没写仓库路径，子 agent 自己猜了个目录，结果全错。子 agent 是"失忆"的，prompt 自包含是硬要求。
- **写冲突**：有次顺手让两个子 agent 同时修复各自发现的 issue，恰好改了同一个配置文件，后写的覆盖先写的。结论：并行只给读任务，写任务串行或按文件分区。
- **成本失控**：子 agent 里再派生子 agent，层层嵌套，token 消耗翻了几倍。现在限制嵌套一层，并对子任务输出长度设上限。
- **轻信子 agent 的结论**：它偶尔会"声称"完成但实际没做。现在要求返回证据（文件路径 + 行号），主 agent 抽查。

## 可复用建议

- 先给任务分类：只读、互相独立 → 放心并行；有写入 → 串行，或按文件/资源分区。
- 给子 agent 定输出契约（schema），汇总阶段只处理结构化数据。
- 限制并发数和嵌套深度，显式定义超时与失败语义。
- 保留子 agent 的原始输出日志，出问题时能回放定位，不必整批重跑。

## 总结

subagent 编排的价值不在于"多开几个 AI"，而在于用隔离上下文换主 agent 的注意力、用并行换时间。它适合读多写少、可拆分、可结构化的任务；不适合强顺序依赖、频繁写同一资源的场景。把拆分、契约、兜底这三件事做扎实，编排才能稳定产出。
