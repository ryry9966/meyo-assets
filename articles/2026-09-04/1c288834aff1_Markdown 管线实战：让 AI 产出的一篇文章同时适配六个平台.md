## 背景

我们的内容工作流里，大部分初稿由 Agent 生成：调研、写稿、配图建议都在 OpenClaw 的 skill 里跑完。但"写完"离"发布"还有一段路——同一篇 Markdown 要发公众号、掘金、知乎、自建 Hugo 站和 Notion，每个平台对 Markdown 的支持都不一样。人工逐篇改格式既耗时又不稳定，于是我们把格式适配做成了管线。

## 问题

AI 生成的 Markdown 有三个典型毛病：

1. **结构不稳定**。有时从 h1 开始，有时直接 h3，列表嵌套层级随机。
2. **方言混用**。正文夹 HTML 标签、数学公式一会儿 `$$` 一会儿 `\(...\)`、表格对齐语法时有时无。
3. **平台差异被低估**。公众号不认 frontmatter、知乎图片外链有防盗链、掘金对脚注式链接渲染不一致。这些问题不碰真平台根本发现不了。

## 做法

管线分四层，核心原则：**中间表示只有一份，平台差异全部推到最后一层**。

**第一步：统一解析。** 用 unified/remark 生态把 Markdown 解析成 mdast（AST）。所有后续操作基于 AST 节点，不碰原始字符串。

**第二步：规范化。** 跑 remark-lint 加自定义规则：标题强制从 h2 开始（h1 留给元信息）、连续空行压成一个、HTML 节点按白名单转换或降级为文本。AI 输出经过这一步，风格就收敛了。

**第三步：平台 transform。** 每个平台一个 remark 插件。公众号版：剥离 frontmatter、公式转图片占位、代码块语言标签降级；Hugo 版：保留 frontmatter、相对链接重写为绝对路径。

**第四步：校验发布。** 输出前对渲染结果做 golden file 快照比对，变更超阈值就拦截人工确认。发布动作由 MCP tool 触发，管线本身不直接碰平台 API。

## 踩坑点

- **别用正则改 Markdown。** 早期我们用正则替换标题层级，结果代码块里的示例 Markdown 也被改了。换 AST 后这类问题自然消失——remark 会把 fenced code 当作整体节点。
- **图片外链必挂。** 微信和知乎都有防盗链，管线里加了转存步骤：发布前把所有图片拉到自有图床，替换 URL。
- **公式是重灾区。** `$$...$$` 在掘金可用、在公众号必须转图片。建议在规范化阶段就把公式统一成一种语法，transform 层只做格式转换、不做语法判断。
- **脚注语法 `[text][1]` 兼容性差**，我们在规范层直接内联展开成 `[text](url)`。

## 可复用建议

1. 把每套 transform 做成独立 npm 包，Agent 通过 skill 调用，参数只传目标平台名。
2. 每个平台维护一篇 golden 样例文章，覆盖标题/列表/代码块/表格/公式/图片六类节点，CI 里跑快照测试。
3. 新平台接入只写一个 transform 加一份 golden，不碰前三层。
4. 规范层规则宁可保守，转换逻辑宁可在 transform 层重复，也不要在规范层埋平台判断。

## 总结

这件事的本质，是把"格式适配"从一次性手工劳动变成有测试、有版本、可被 Agent 调用的工程资产。AI 负责生成内容，管线负责让它以正确的形态出现在每个平台。分工划清之后，我们新增一个发布渠道的成本从半天降到了一小时以内——这个数字比任何框架选型都更能说明管线的价值。
