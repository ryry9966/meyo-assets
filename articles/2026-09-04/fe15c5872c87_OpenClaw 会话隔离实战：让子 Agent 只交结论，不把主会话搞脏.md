## 背景

OpenClaw 里每个聊天渠道默认对应一个主会话（main session），日常对话、记忆、工具调用历史都在这条上下文里滚动。任务一复杂，模型会通过 `sessions_spawn` 派生子 Agent 去干活：查资料、跑脚本、批量整理文件。子 Agent 拥有独立的 session ID、独立的上下文窗口和独立的 transcript，理论上它的过程再吵，主会话也听不见。

理论上。

## 问题

实际跑下来，主会话被污染通常走三条路：

1. **返回物过大**。子 Agent 把完整日志、报错栈甚至整段网页原文塞进最终回复，作为 tool result 全量回到主会话，几轮之后上下文窗口被垃圾占满，触发压缩，早期对话细节被压掉。
2. **绕过父级直发消息**。子 Agent 如果保留了 messaging 类工具权限，会自己往群里播报进度，用户看到重复、时序错乱的消息。
3. **共享文件互踩**。上下文隔离不等于文件系统隔离，多个并行子 Agent 同时写 `MEMORY.md` 或同一个临时脚本，后写覆盖先写，主会话后续读到的就是脏数据。

## 做法

我们团队现在跑任务前有四条约定：

1. **派生 prompt 里写死返回格式**："最终回复只给不超过 10 行的结论 + 产物路径，过程细节留在你自己的 session 里"。这条最有效，成本最低。
2. **裁剪子 Agent 的工具**。执行型子 Agent 只给 exec + 文件工具，不给消息渠道工具，回复只能走 tool result 回父会话。
3. **文件交接，路径引用**。完整产物写到 `/workspace/out/<task-id>/`，主会话只记路径，需要细节时再 `cat`，不把内容常驻在上下文里。
4. **一任务一目录**。并行子 Agent 各自写独立子目录，避免同名临时文件竞争。

## 踩坑点

- **"隔离"只隔离上下文**。子 Agent 默认仍可写共享 `MEMORY.md`，探索性任务如果放任它写记忆，中间猜想会混进长期记忆，这个坑最深。
- **报错原样回传**。子 Agent 失败时把完整 stack trace 塞回 tool result，正确姿势是让它自己总结一行根因，日志落盘给路径。
- **僵尸 session**。子 Agent 异常中断后，session 文件会留在 `~/.openclaw/agents/<name>/sessions/` 里，偶尔用 `/sessions` 清点一下，别让它们悄悄吃盘。
- **base64 / 大 JSON 返回**。一次就够把主会话窗口顶爆，凡是大数据一律走文件。

## 可复用建议

- 把"只交结论 + 产物路径"做成子 Agent 的系统提示模板，新任务直接复用。
- 按任务类型拆 agent 定义（研究型、执行型），各自裁剪工具与权限，而不是一个通用子 Agent 打天下。
- 约定固定的产物目录结构，主会话只认路径不认内容。
- 每周 `/sessions` 巡检一次，配合日志归档。

## 总结

上下文隔离是框架给的默认，会话干净是使用者自己设计的。隔离解决的是"过程不可见"，而真正决定主会话寿命的，是你允许子 Agent"传什么回来"——交摘要和产物路径，而不是全程流水。把这条立成约定，主会话才能长期保持可用。
