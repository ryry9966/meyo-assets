## 背景

Agent 接上 MCP、文件系统和浏览器自动化之后，能力边界和责任边界开始不对等。社区场景尤其微妙：你让 agent 帮忙答疑、写教程、复盘故障，它的上下文里往往堆着内部配置、私有工具链甚至客户数据。模型并不理解"哪些能说"，它只知道"上下文里有什么、工具能取到什么"。

## 问题的三条典型路径

1. **上下文污染**：排查问题时把 `.env`、日志、带 token 的 curl 命令贴进会话，事后让 agent"总结成帖子"，敏感字段原样输出。
2. **工具过权**：社区答疑用的 agent 挂了全量文件系统或内部知识库的 MCP，它为了"答得准"顺手引用内部文档。
3. **持久化记忆**：memory 功能把内部架构细节写进长期上下文，下一次公开会话里被间接带出。

## 做法：四层闸门

**第一层，资产盘点。** 先列清单：这个 agent 能读哪些目录、挂了哪些 MCP、浏览器带着哪些凭据、memory 里存了什么。看不到边界就谈不上收敛。

**第二层，权限收敛。** 社区助手用独立 profile，与内部助手物理隔离；MCP 默认只读、默认白名单目录，token 按最小范围签发。

**第三层，上下文卫生。** 密钥、内网地址、客户标识不进上下文；排查记录先脱敏再喂；内部调试和社区产出分两个工作区，别混用。

**第四层，出站过滤。** 所有发往公开频道的输出统一过一道闸：正则拦截 key 前缀、内网域名、路径特征；首次发布走人工确认，稳定后再降为抽检。工具调用与输出留审计日志，每周回看。

## 踩坑点

- **指望模型"懂事"**：system prompt 里写"不要泄露机密"不构成边界，模型对"机密"的判定和你不一致，实测容易翻车。
- **历史文件比想象的多**：shell history、编辑器备份、`config.bak` 都在 agent 可达范围里，盘点时最容易漏。
- **复制粘贴是最后漏洞**：过滤器再严，也拦不住你手动把排查记录贴进帖子，发布前的人审环节别省。
- **deny-list 不是万能**：内部代号、自建域名没法靠正则穷举，真正兜底的是隔离，过滤只是缓冲。

## 可复用建议

- 一个 agent 一个身份：不共享 profile、memory、凭据。
- 默认拒绝：权限先收到最小，用到了再开，并记录开启原因。
- 出站必过闸：公开频道输出统一走过滤器加人工确认。
- 定期演练：每月让 agent"复述你能看到什么"，用输出反推权限是否过宽。

## 总结

Agent 泄露不是模型"嘴不严"，而是权限设计和上下文管理的欠账。红线不是 prompt 里的一句话，而是三件事：能不能访问（权限）、上下文里有没有（卫生）、发出去过不过滤（出站闸门）。三层做实，社区分享与内部安全可以共存。
