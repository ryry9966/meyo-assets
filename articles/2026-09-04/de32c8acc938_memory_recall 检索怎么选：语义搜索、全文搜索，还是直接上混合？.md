## 背景

OpenClaw 的长期记忆大多落在一堆 markdown 文件里：memory 目录、daily notes、会话摘要。`memory_recall` 是 Agent 往回翻这些笔记的唯一入口。笔记量小的时候随手 grep 都能命中，但攒了半年、几百个文件、上万行之后，“上次那个连接老断的问题是怎么解决的”这类提问开始频繁翻空。于是我把 recall 的检索层重构了一遍，语义和全文两条路都跑了一遍，记录结论。

## 问题

两类检索干的不是同一份活：

- **全文搜索（BM25 / FTS5）**：关键词精确命中，擅长错误码、函数名、ID 这类强信号词，几乎零成本。
- **语义搜索（embedding 向量）**：按意思召回，“连接老断”能召回写着“WebSocket 重连”的笔记，哪怕一个字都对不上，但要维护 embedding 和向量库。

我的语料规模和查询习惯，到底配得上哪一种？这是本次要回答的问题。

## 做法

1. **先建全文基线**：SQLite FTS5 + BM25，中文接 jieba 分词后再入索引，改动最小。
2. **加语义通道**：本地跑 bge-small-zh-v1.5，笔记按标题层级切成 300–500 字的 chunk，向量写入 sqlite-vec，各召回 top-20。
3. **混合融合**：两路结果用 RRF（倒数排名融合）合并取 top-8 喂给模型，融合权重先 1:1 起步，不急着调参。
4. **建评测集**：从历史会话挑 30 个真实回忆问题，人工标出应命中的笔记，算 hit@5，之后每改一版都跑回归。

## 踩坑点

- FTS5 默认的 unicode61 分词器对中文基本不可用（连续汉字被当成一个 token），不接 jieba 等于没建索引。
- 纯语义对精确标识符很弱：查 `ERR_12007` 时向量召回一堆“大概相关”的段落；反过来，口语化提问全文搜索几乎全空。谁也替代不了谁。
- chunk 切太大（整篇日记一个向量）召回粒度糊，切太小丢上下文，按标题层级切最稳。
- Agent 发来的 query 经常是一整段话，直接 embedding 效果差。先让 Agent 把问题改写成一句简短检索词，命中率明显上升。
- 一年前的旧方案和新笔记同权竞争，翻出来的常是过期结论，最后按时间做了衰减加权才像样。

## 可复用建议

- 语料不到几百个文件、查询偏关键词：只上全文搜索，别过度工程。
- 查询偏口语、意图模糊：语义通道收益最大。
- 拿不准就直接混合 + RRF，这是工程上最不后悔的默认解。
- 评测集是唯一裁判：30 条标注问题比任何直觉都管用，recall 层的所有改动都靠它做回归。如果你把记忆检索做成了独立的 MCP server 或插件，这套方法原样适用。

## 总结

“语义 vs 全文”不是二选一，而是覆盖面互补：全文兜住精确词，语义兜住意图差。在我的记忆语料上，混合 RRF 的 hit@5 从纯全文的 55% 左右提到约 80%，代价是多维护一个本地 embedding 服务。建议路径：先全文打基线 → 建评测集 → 语料涨上去再加语义通道 → 最后做时间衰减。memory_recall 的上限不在换更大的模型，而在检索层的老实迭代。
