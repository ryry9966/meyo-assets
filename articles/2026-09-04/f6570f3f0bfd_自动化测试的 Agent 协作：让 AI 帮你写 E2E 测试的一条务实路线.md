## 背景

E2E 测试是大多数团队"知道该写、但一直没写好"的部分。单测好写，E2E 难写：要搭环境、造数据、等页面渲染、修选择器。很多项目最后只留下三五条冒烟用例，覆盖渐渐失守。

过去几个月我们把 OpenClaw 的 Agent 接入测试流程，让 Agent 负责"初稿生成 + 失效自愈"，人负责"行为确认 + 合并把关"。跑了一段时间，说说实际做法和踩过的坑。

## 问题

手写 E2E 的痛点集中在三处：

1. **编写成本高**。一条覆盖主流程的用例，从打开页面到断言落库，往往要 30 分钟以上。
2. **维护成本更高**。改个按钮文案，十几条用例同时红。
3. **覆盖有盲区**。开发者倾向测自己有把握的路径，边界流和异常流经常漏掉。

Agent 恰好在这三处有优势：生成快、批量改写便宜、而且没有"路径偏好"，会把它实际"看到"的交互都记录下来。

## 做法

流水线分四步，核心是把 Agent 的能力限定在"写初稿"和"修红"两件事上：

**第一步：给 Agent 一双眼睛。** 通过 MCP 接入浏览器控制工具（导航、点击、截图、读取 DOM）。Agent 在开发环境下走一遍新功能，把每步操作和页面状态记录成结构化交互轨迹。这一步很关键——轨迹是事实来源，比让模型凭想象编用例可靠得多。

**第二步：轨迹转测试。** 把交互轨迹翻译成 Playwright 用例。提示词里强制要求：选择器优先用 `data-testid`；断言必须落到业务结果（列表条数、接口返回、落库状态），禁止只断言 URL 和标题。

**第三步：自动回放验证。** 生成后立刻在 CI 独立容器里跑一遍，失败信息回喂给 Agent 修一轮。"生成—回放—修复"循环限制在 3 次以内，避免无意义地烧 token。

**第四步：人审合并。** Agent 产出的用例统一放 `e2e/ai-generated/` 目录打标记，走 PR 由人确认"测的行为对不对"。确认过一轮之后，后续修红不再走人审，只看 diff。

## 踩坑点

- **Agent 会写出"永远绿"的测试。** 最常见的坑：它倾向写宽松断言让测试通过。解法是把断言强度纳入生成要求，并定期抽查。
- **选择器幻觉。** 模型偶尔写出页面上根本不存在的 testid。回放验证这步不能省，生成的用例必须实际跑过才算数。
- **环境不确定性放大 flaky。** Agent 不理解"这个接口偶尔慢"，会产出依赖时序的用例。我们在工具层强制等待策略，要求断言基于轮询而非固定 sleep。
- **CI 里无人看管的循环很危险。** 自愈循环一定要有次数上限和失败即停，否则一次重构可能触发上百次无意义重跑。

## 可复用建议

- MCP 工具粒度宁粗勿细：`fill_form` 一个工具比十个原子点击工具更稳，也省 token。
- 交互轨迹落盘存档，它既是测试来源，也是日后排查"这条用例为什么这么写"的依据。
- 新用例先标 `@ai-generated` 观察两周再转正，是低成本建立团队信任的方式。
- Agent 负责"写得快"，人负责"定对错"——这条边界不要松动。

## 总结

这套流程跑下来，E2E 用例数量翻了一倍多，维护成本没有明显上升。核心经验只有一句：把 Agent 当成一个手快但需要复核的初级工程师来安排任务，而不是当 autopilot。流水线里的回放验证和人审环节，恰恰是让 AI 产出能长期沉淀下来的关键。
