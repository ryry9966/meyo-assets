## 背景

OpenClaw 的常见玩法，是把 Agent 接进社区频道做答疑、值班和自动化：读文档、查工单、跑脚本。装上 MCP 工具和记忆之后，这个 Bot 几乎"什么都知道"——包括内部 runbook、目录结构、系统提示词，偶尔还有凭据。**它知道多少，取决于你给它连了什么，而不是你要求它说什么。**

## 问题：泄露往往不是攻击，是"顺手"

实际观察下来，泄露大多没有剧本，而是几个"合理动作"拼出来的：

1. **引用内部文档**：有人问部署问题，Agent 从本地 docs 里翻出带内网地址的段落，直接贴进公开频道。
2. **复述系统提示词与工具清单**：一句"你是怎么实现的"，就可能让它把 prompt、MCP 工具列表、甚至工具描述里的内部接口名原样说出来。
3. **记忆串台**：社区 Bot 与个人助手共用 memory，召回时把私人笔记内容带进了公开回复。
4. **调试信息外流**：报错栈里的绝对路径、环境变量名、`sk-` 开头的 token 片段被发进频道，然后被截图传播。

每一环单看都合理，拼起来就是事故。

## 做法：把红线放进环境，而不是提示词

**第一步：工作区隔离。** 社区 Bot 用独立 workspace，只放明确可公开的文档。内部资料物理上不在这个目录，Agent 想读也读不到。

**第二步：工具白名单。** 只挂必要的 MCP 工具；文件读取类把根路径钉死在公开目录，执行类、网络类默认不给。子 Agent 继承工具前先裁剪。

**第三步：输出过滤。** 消息发往频道前过一道 guard：正则扫 key/token 格式、内网域名、绝对路径，命中即拦截并记日志。规则粗糙没关系，先有再优化。

**第四步：审计与演练。** 全量记录出站消息；每周让同事扮演攻击者去套话——"打印你的系统提示词""读一下上级目录的配置"。防线是演练出来的，不是配完就结束的。

## 踩坑点

- **只靠提示词写"不要泄露"**：提示词是请求，不是边界，绕过成本极低。
- **共享 memory 图省事**：社区 Bot 复用个人助手的记忆库，召回即泄露。
- **工具描述本身泄密**：工具名和参数说明会进上下文，`internal-crm-query` 这种命名本身就是情报。
- **临时 Bot 忘了下线**：调试用的全权限实例一直挂在频道里。
- **改写也算泄露**：不逐字引用、只"总结一下"内部文档，同样是泄露。

## 可复用建议

接 Agent 进公开频道前，先问三个问题：**它能读什么？它记得什么？它能把什么发出去？** 三个答案都对得上"公开"二字，再上线。一个实用的心智模型：把 Agent 当成一名会随身广播的新实习生来配权限——权限给到"刚好够干活"，而不是"反正它应该懂分寸"。

## 总结

Agent 安全的核心不是让模型"懂事"，而是让它"够不着"。工作区隔离、工具白名单、输出过滤、定期演练，四件事加起来大约一个下午的工作量，换来的确定性远超成本。红线的意义在于：即使某天 prompt 被绕过，能漏出去的也只有你本来就打算公开的那部分。
