## 背景

现在的 AI 助手大多还是被动模式：你发消息，它回复，然后各自安静。但在 Agent + MCP 的技术栈下，助手其实已经具备查数据、调工具、发消息的完整执行链路，缺的只是一个"什么时候出手"的触发层。所谓 proactive，本质上不是让模型更聪明，而是在 agent 循环外面加一套事件驱动的唤醒机制。

## 问题

把 proactive 直接理解成"定时调 LLM"很快会翻车，通常有三类坑：

1. **噪音失控**：助手每小时汇报一次"没有异常"，三天后用户必然静音它。主动消息一旦变成打扰，信任度下降是不可逆的。
2. **上下文断裂**：被定时任务唤醒的 agent 没有会话记忆，每次都重新探索环境，成本高、动作慢。
3. **权限越界**：被动模式下用户盯着它操作；主动模式下没人盯，一旦误执行写操作（发消息、改文件），后果比聊天出错严重得多。

## 做法

我在自己的 OpenClaw 实例上跑了一套三段式结构，稳定运行几周后整理如下：

**第一步：定义触发源。** 分三类接入：时间型（cron 定时，如每天早上汇总日程）、事件型（webhook / MCP notification，如收到邮件、CI 失败）、状态型（阈值判断，如磁盘占用超限）。前两类直接推送，第三类建议由轻量脚本轮询，只有越过阈值才唤醒 agent。

**第二步：组装唤醒 prompt。** 触发时不要只发一句"该干活了"，而是由路由层拼好最小上下文：触发原因、相关数据快照、本次允许的工具范围。这一步决定主动行动的质量，也决定 token 花销。

**第三步：加一道决策门（gate）。** 唤醒后先让 agent 自评：这个事件是否值得打扰用户？给出判断依据和置信度。低于阈值就走静默通道——写日志，不推送。判断标准要显式写进 prompt，比如"只有需要人在 24 小时内决策的事才允许推送"。

**第四步：分级执行。** 读操作（查询、汇总、草拟）直接做；写操作（发消息、改配置、调外部 API）默认生成草稿等确认，只有白名单动作允许自动完成。

**第五步：闭环。** 所有主动行为落一份 action log，记录触发源、token 消耗、用户是否采纳。每周回顾一次，砍掉一半没人理的触发规则。

## 踩坑点

- **自我唤醒死循环**：agent 的写操作（往监听目录写状态文件）又触发了事件监听，一晚上跑了几百轮。解法：给事件打来源标记，来自 agent 自身的动作不再唤醒。
- **时区漂移**：cron 按机器时区跑，容器里默认 UTC，"每天早上 8 点"变成了下午。容器化部署务必显式设置时区。
- **静默通道没人看**：日志写了但不回顾等于没写。静默事件要有低频摘要（比如每周一条），否则会漏掉真正重要但当时置信度不够的事。
- **上下文膨胀**：为了省事把全部历史快照塞进唤醒 prompt，单次成本翻十倍。快照只保留与触发直接相关的字段。

## 可复用建议

- **先读后写**：前两周把 agent 限制在只读 + 汇报，观察误报率后再逐步放开写权限。
- **权限分离**：MCP 工具拆成 observe 和 act 两组，唤醒场景默认只挂 observe。
- **给主动行为设预算**：每天最多 N 次推送、单次 token 上限，超了就降级为静默记录。
- **用采纳率调优**：一条主动消息如果用户从不回复，说明触发条件太松，直接收紧或删除。

## 总结

Proactive 能力的核心不是模型问题，而是工程问题：触发层决定"何时出手"，决策门决定"是否打扰"，权限分级决定"敢不敢自动做"。把这三件事拆开做、分别调优，AI 助手才能从"问一句答一句"变成真正省心的协作方——而不是一个更吵的提醒机器。
