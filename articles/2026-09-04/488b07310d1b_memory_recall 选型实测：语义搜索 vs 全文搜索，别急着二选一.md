## 背景

给 Agent 挂记忆已经是标配操作：对话摘要、用户偏好、项目决策写进 memory store，新请求进来时靠 memory_recall 捞几条塞回上下文。捞得准不准，直接决定助手“记不记事”。

检索常见的两条路线：语义搜索（embedding + 向量库）和全文搜索（FTS/BM25）。社区里经常争论哪个更好，我们的结论是：问题本身问错了——该问的是“哪类查询配哪类检索”。

## 问题

我们在一个跑了三个月的助手项目里做了小规模评测（40 条真实 recall 查询 + 人工标注应命中的记忆条目），两种方案各有明确的失败模式：

- **全文搜索输在“说法不一致”**：用户问“之前那个发布卡住的事”，记忆里写的是“部署超时”，词面对不上就捞不到。
- **语义搜索输在“精确 token”**：错误码、变量名、文件路径这类内容，向量相似度会把一堆“看起来差不多”的条目排到前面，真正那条反而被 top-k 截掉。

更隐蔽的是中文问题：FTS 默认分词器按空格切，中文基本失效；多数通用 embedding 模型对“中文混代码”的内容编码质量也明显下降。这两点不处理，选哪种都白搭。

## 做法

我们的落地步骤，可以直接抄：

1. **先治写入**。记忆条目改成原子化短句，每条带元数据（时间、来源、类型：偏好/决策/事实/报错）。检索质量的上游是写入质量。
2. **FTS 打底**。SQLite FTS5 或 PG tsvector，配 zhparser/jieba 处理中文分词，成本近零。
3. **语义补位**。选双语 embedding 模型，只对概念型记忆（偏好、决策、总结）建向量索引。
4. **混合 + 融合**。两路都查，用 RRF 合并，再乘时间衰减系数——三个月前的相似记忆必须打折。
5. **用评测说话**。跑 recall@5，每次调参测一遍，不靠感觉。

结果：混合方案 recall@5 约 0.87，纯语义 0.72，纯 FTS 0.63。语义的提升主要来自同义改写类查询，FTS 保住了精确 token 类查询的底线。

## 踩坑点

- 中文分词别用默认配置，FTS5 对中文是整句切分，命中率惨不忍睹。
- embedding 里混大量代码/ID 会拉低整体编码质量；把含精确 token 的条目从语义索引剔除后，纯语义那路反而升了 3 个点。
- top-k 别贪大，k=5 以上再往上下文塞，模型开始引用过期记忆，宁缺毋滥。
- 时间衰减必须有，否则语义搜索总爱捞半年前的旧偏好，用户改了想法它还守着。
- 评测集别只用改写样例，要覆盖精确 token、时间限定（“上周说的”）、否定性查询，否则结论是偏的。

## 可复用建议

- 别从语义搜索起步：先 FTS + 元数据过滤，评测显示改写类查询不达标再上语义，能省一半运维成本。
- 精确 token 类记忆额外建精确索引，比任何检索算法都可靠。
- 每周抽查一次 recall 日志里的 miss 样例，是最便宜的质量迭代手段。

## 总结

语义搜索擅长“换了说法也能找到”，全文搜索擅长“一个字符都不能错”，记忆场景两者都要。真正的分水岭不在检索算法，而在记忆怎么写、元数据怎么打、时间怎么加权。先把写入治理好，用小评测集驱动选型，比在向量库选型上纠结一周有用得多。
