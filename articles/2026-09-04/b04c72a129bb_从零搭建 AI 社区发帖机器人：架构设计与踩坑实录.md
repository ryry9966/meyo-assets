# 背景

社区内容有个尴尬的现实：想把讨论沉淀成帖子，靠人肉整理节奏跟不上；纯自动生成又容易变成低质灌水。我们想做的不是“全自动发帖机”，而是一条半自动流水线：Agent 负责选题、起草和格式化，人负责最后一道审。本文记录用 OpenClaw + MCP 搭这条流水线的过程和踩过的坑。

# 问题定义

动手前明确了三个约束：

1. 不无人值守直发，所有帖子必须过人工确认；
2. 不能和社区近期内容撞车；
3. 任何单点失败，不能导致重复发布或漏发。

这三条决定了架构核心：**状态必须外置，Agent 每次只做一件事。**

# 架构

整体分三层：

- **触发层**：cron 定时任务，每天固定时间唤起 OpenClaw，把当天日期作为种子传入；
- **Agent 层**：OpenClaw 挂载一组 MCP 工具——查最近 N 天帖子标题、检索社区高频问题、写草稿、提交审阅；
- **状态层**：SQLite 一张任务表，状态机为 `draft → pending_review → approved → scheduled → published`，失败就停在原地，可重跑。

关键设计是 Agent 无状态：每次运行只根据当前状态决定下一步动作，做完立即落库。幂等键用“日期 + 主题 slug”，同一个键重复触发不会生成第二条任务。

# 实施步骤

1. **MCP 工具做薄**。四个工具：`list_recent_posts`、`search_topics`、`save_draft`、`submit_for_review`，每个只读写一小块，返回结构用 JSON Schema 校验，不合规直接报错让 Agent 重试。
2. **起草分两段**。先只让 Agent 输出选题和提纲，确认后再写正文。两段式比一次成文的返工率低很多。
3. **审阅走文件**。草稿落成本地 Markdown，带 frontmatter 元数据，审完改状态。人用编辑器看，不额外做界面。
4. **发布独立成插件**。读 `scheduled` 状态的草稿，调社区 API，成功后回写状态和帖子链接。

# 踩坑实录

- **一次跑全链路必然翻车**。最初版本让 Agent 一口气“选题→写→发”，中途 API 超时，重跑后同一篇发了两遍。教训：没有状态落库的自动化等于没有自动化。
- **查重不能只看标题**。出现过“老话题新表述”，标题不同但内容高度重合。后来加了基于向量的相似度检查，和最近 30 天帖子比对，超阈值直接打回。
- **MCP 工具返回要强约束**。模型会“脑补”字段，比如给帖子列表自己加摘要。Schema 校验加上拒绝多余字段是必须的。
- **时区问题**。cron 用了 UTC，发帖时间漂移 8 小时，被社区成员当场指出。容器里显式设置 TZ，调度和落库统一用带时区的时间戳。
- **审阅疲劳真实存在**。连续人工审两周后标准明显松动，放过了一条平庸的帖子。后来在 frontmatter 里加自动质检分（长度、代码块、相似度），低于阈值标黄提醒，把人的注意力集中在真正需要判断的地方。

# 可复用建议

1. **先 dry-run 一周**：所有“发布”改成写文件，确认选题和成文质量稳定后再接真实 API。
2. **Agent 无状态 + 状态机落库**，是所有自动化流水线的通用骨架，不只发帖场景适用。
3. **MCP 工具小而钝**：不做智能、不做兜底，校验失败就抛错，让上层决定重试还是放弃。
4. **记录每次 Agent 决策的输入输出**：排查问题全靠它，改 prompt 后还能用来做回归对比。

# 总结

流水线跑了一个多月，稳定产出每周 3-4 篇，单篇人工审阅耗时从 20 分钟降到 5 分钟左右。最大的收获不是省时间，而是把“生成”和“发布”在结构上拆开后，每一环都能单独替换和测试。自动化做得好不好，看的不是跑得多快，而是失败时停在哪里。
