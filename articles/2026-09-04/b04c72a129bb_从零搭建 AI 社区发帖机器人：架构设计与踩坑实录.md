## 背景

社区运营里有一类高频低难度的活：每周汇总 issue 和讨论整理成周报帖、摘出热点问题。人肉做两周之后我就想把它自动化了。选型上没有造新轮子，直接基于 OpenClaw 搭：cron 触发 agent，工具走 MCP，跑了一个多月，本文记录架构和一个多月里踩过的坑。

## 问题定义

- **输入**：GitHub issues / discussions + 站内 RSS
- **输出**：每周一篇周报帖 + 热点问题摘要，自动发布到论坛
- **硬约束**：不能乱发；失败可重试；随时可切回人工兜底

## 架构：四层，模型只管写

```
cron 定时器
   → 采集层（Python 拉数据源，落 SQLite）
   → Agent 层（OpenClaw agent + 3 个 MCP 工具）
   → 审核层（草稿队列 + 格式/域名校验）
   → 发布层（独立消费者进程，调论坛 HTTP API）
```

关键决策只有一条：**Agent 只负责“写”，不直接“发”**。MCP 工具拆成 `fetch_db`、`draft_post`、`submit_post` 三个，生成与发布解耦后，审核、重试、幂等都在模型外面用普通代码做，简单得多。

## 踩坑实录

**1. 幻觉链接。** 早期让模型直接引用 issue 链接，它编了不存在的编号，格式还挺像。解法：提示词里明确“只能使用输入中提供的 URL”，校验层再用正则做域名白名单，双保险。

**2. 重复发帖。** cron 误触发 + 失败重试叠加，同一篇周报发了两遍。解法：内容 hash 作幂等键，发布前先查库，命中即跳过。

**3. MCP 工具粒度太粗。** 最初 `submit_post` 里塞了鉴权、格式化、发布三件事，模型经常把格式化参数写错。拆成小工具后错误率明显下降——经验是**一个工具一个动作，参数越少越好**。

**4. 输出不稳定。** 同一段提示词，有时多出一段“以下是本周汇总”之类的开场白。强制 JSON 输出 + schema 校验，不合格重试一次，仍失败就进人工队列。

**5. 定时漂移。** 容器重启后 cron 静默丢失，两周后才被发现。解法：启动时检查“距上次成功发布是否超过一个周期”，超了就补跑。监控别只盯进程，要盯**结果**。

## 可复用建议

- 先 dry-run 一周：草稿进队列人工审，稳定后再放开自动发布
- 所有副作用操作（发帖、回复）必须有幂等键
- 校验放模型外：URL 域名、JSON schema、敏感词，都别指望提示词兜底
- 日志记全：每次 run 的输入摘要、token 消耗、工具调用链、最终状态，出事能回放
- 失败路径要显式设计：重试两次仍失败 → 人工队列，而不是无限重试

## 总结

“低频、有模板、可审核”的任务是 agent 自动化的甜点区。架构上最值钱的原则就一条：**模型做生成，代码做发布**。模型负责写得像样，工程负责不出事故。目前机器人周报稳定产出，人工介入率从每天一次降到每周抽查一次，下一步计划把回复常见问题也接进来，但依然会保留人工队列这个兜底口。
