## 背景

社区每周都要整理 GitHub Release 动态、论坛精华帖和 MCP 生态更新。之前靠人肉搬运，耗时且格式不统一，断更是常态。于是花两周写了一个基于 OpenClaw 的定时发帖机器人，本文记录整体设计与踩坑过程，供有类似需求的同学参考。

## 目标与约束

- 定时聚合多源内容：RSS、GitHub Releases、论坛 API
- LLM 生成草稿，人工确认后发布
- 可中断可恢复，绝不重复发帖，不碰社区风控红线

## 架构：四个模块，一条队列

整体拆成四段，用 SQLite 表做任务队列串联：

1. **采集器**：每个源一个 fetcher 插件，统一输出 JSON 结构（标题、链接、时间戳、原文摘要）。
2. **生成器**：OpenClaw agent 挂 MCP 工具，输入结构化数据，按 JSON Schema 输出草稿。
3. **审核队列**：草稿落库，简单 Web 页上人工点通过/驳回。
4. **发布器**：独立进程消费已审核草稿，调用社区发帖 API。

核心决策只有一条：**生成与发布彻底分离**。LLM 永远不直接接触发布接口，最坏情况也只是草稿质量差，不会酿成事故。

## 踩坑实录

**坑 1：重复发帖。** 上线第一天同一内容发了三次——生成器超时重试，每次重试都新建了任务。修复：以「源内容哈希 + 目标板块 + 日期」为幂等键，入库前先查重。

**坑 2：LLM 编造链接。** 摘要里出现了源数据中不存在的 URL。修复：prompt 明确只允许引用输入字段，发布前正则校验所有链接必须存在于原始数据中，失败即打回。

**坑 3：输出格式漂移。** 模型偶尔在 JSON 前加一句「好的，以下是草稿」，解析直接崩。修复：structured output 强约束 + temperature 降到 0.2，解析失败时带错误信息重试一次，仍失败则告警并跳过。

**坑 4：触发限流。** 补发积压草稿时打爆社区 API，账号被临时禁言。修复：发布器加令牌桶，每分钟最多两帖，遇到 429 指数退避。

**坑 5：时区错位。** cron 跑在容器默认 UTC 上，帖子全在凌晨发布。显式指定 Asia/Shanghai 解决。

## 可复用建议

1. 先跑两周 dry-run，草稿只写日志不发帖，人工评估质量后再放量
2. 原始 LLM 输出永久留存，出问题可以回放定位
3. 幂等键第一天就要设计，事后补极其痛苦
4. 审核环节别省，账号有封禁风险的场景尤其如此
5. 用 Schema 约束输出，别指望 prompt 里一句「请输出 JSON」

## 总结

目前机器人每周稳定产出 3-5 篇汇总帖，人工只做最后确认。最大的体会：LLM 那部分反而是最简单的，真正决定系统能否长期运行的，是幂等、限流、审核这些「无聊」的工程链路。四个模块彼此独立，换一个目标社区只需要重写发布器。
