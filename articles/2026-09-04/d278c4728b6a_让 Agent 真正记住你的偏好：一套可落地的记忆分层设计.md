## 背景

LLM 本身无状态，上下文窗口不是记忆——会话结束就清零。在 OpenClaw 这类常驻助手场景里问题更明显：你通过 IM 渠道跟它聊了几周，每次新会话还是得重复"我用 pnpm、时区 UTC+8、回复要短"。偏好反复陈述的体验，比功能缺失更劝退。

## 问题

三种常见朴素做法都不太行：

1. **全塞 system prompt**：token 膨胀，过期信息无法删除；
2. **依赖聊天记录回捞**：噪声大、成本高，捞回来一堆无关上下文；
3. **记忆 = 不断追加的 txt**：只有 append 语义，没有更新和冲突处理，两周后自己都读不下去。

真正的设计问题其实是四个：记什么、什么时候写、怎么读、怎么改/删。

## 做法：三层结构 + 一条写入纪律

**分层**：

- L1 会话内状态：跟着上下文走，不落盘；
- L2 工作记忆：当前任务的草稿和中间产物，落文件即可；
- L3 长期记忆：结构化偏好库 + 情节式笔记，本文重点是 L3。

**L3 每条记忆带元数据**：

```json
{
  "key": "package_manager",
  "type": "preference",
  "value": "pnpm",
  "confidence": 0.9,
  "source": "user_explicit",
  "updated_at": "2025-06-01T10:00:00+08:00"
}
```

**写入走两条通道**：

- 显式：用户说"记住 xxx"，或通过 MCP 暴露的 `memory_write` 工具（配套 `memory_search` / `memory_delete` 三个工具就够用）；
- 隐式：会话结束后跑一个抽取器，只挑 `type=preference` 且 confidence 达标的候选；影响较大的写入前向用户确认一次。

**读取**：会话启动时注入 top-N 高频偏好；会话中用关键词（SQLite FTS5）+ 向量做混合检索，按相关度、频次、新鲜度加权，注入上限设 8 条左右。

**更新**：按 key 覆盖而不是追加；用户纠正（"不对，换 npm 了"）永远优先级最高。存储起步用 SQLite 一张表足够，别急着上独立向量库。

## 踩坑点

- **自动抽取太激进**：把"今天下雨"这类一次性事实存成偏好，记忆库迅速被污染。先收紧阈值再逐步放宽。
- **只增不改**：同一个 key 留着新旧两个值，模型检索到矛盾信息后开始随机站队。
- **全量注入**：记忆越多越贵也越乱，无关记忆会稀释模型注意力，务必设注入上限。
- **纯向量检索丢精确词**：模型名、路径、版本号必须精确命中，别指望 embedding 兜住。
- **隐私**：记忆库明文落盘，至少对密钥类内容脱敏；"忘掉这条"必须真删，用户预期就是如此。

## 可复用建议

- 先做扁平 JSON/SQLite + 显式写入，跑两周看命中率，再决定要不要上向量检索；
- 每条记忆必须带 `source` 和 `updated_at`，否则出问题无法审计；
- 给用户一条 `/memory` 命令，能看、能改、能删全部记忆——信任感来自可见性；
- 记忆 schema 加 `version` 字段，后续迁移不抓瞎。

## 总结

记忆系统本质是数据工程问题，不是 prompt 技巧。原则一句话：**写入保守、读取激进、更新有规则**。先把结构化偏好做扎实，情节式记忆和衰减策略都可以后置——能稳定记住十条偏好并正确覆盖它们的助手，已经比大多数方案好用了。
