## 背景

订阅源重新变回主流之后，我手里的 RSS 列表涨到了一百多个源。阅读器能解决“聚合”，解决不了“读完”。于是把 OpenClaw 的定时任务和 MCP 工具串起来，搭了一条每天跑两次的摘要管线，稳定运行一个多月，每天产出一份几百字的日报。这篇记录做法和踩过的坑。

## 问题

- 源多、更新频率不一，人工扫一遍成本高；
- 大多数 feed 只给摘要甚至只有标题，信息量不够做判断；
- 直接把 feed 丢给 LLM 总结，会遇到幻觉、多源重复和费用失控。

## 做法

**1. 源头与抓取。** 优先原生 RSS；没有的站用 RSSHub 或自写解析脚本。抓取层单独一个脚本，负责 ETag/Last-Modified 增量拉取，解析后的条目写入本地 SQLite，包含 url、标题、发布时间、原始内容。任何一次重跑都不产生重复记录——幂等是整条管线的地基。

**2. 正文抽取。** 对只有摘要的条目，再抓一次页面，用 readability 类库抽正文。失败的条目标记状态，摘要阶段降级为“仅基于 feed 摘要”，不要硬编。

**3. 摘要与打分。** 用 OpenClaw agent 的定时任务触发，通过 MCP 的 fetch 工具读取 SQLite 待处理条目，批量送给便宜模型，prompt 要求输出严格 JSON：一句话摘要、三个要点、分类标签、信息密度评分。取分高的少数条目再用强模型深读，输出“是否值得展开”的判断。

**4. 去重与分发。** 先做 URL 规范化（去 utm、统一域名），再做标题相似度合并——同一事件多源报道只留信息最全的一条。最终生成 Markdown 日报，webhook 推到自己的 IM，同时归档到 git 仓库，方便回溯。

## 踩坑点

- **编码与日期。** 少量老源是 GBK，发布时间的时区五花八门，解析失败不要静默跳过，先记日志再修。
- **幻觉。** 只允许模型基于抓到的正文总结，明确要求“内容不足时输出 insufficient”，比笼统说“客观总结”有效得多。
- **费用。** 第一版全量用强模型，一晚跑掉不少 token。改成两段式（便宜模型粗筛 + 强模型精选）后，成本降了一个量级。
- **RSSHub 公共实例不稳。** 限流严重，高频源自己部署或加缓存。
- **别全自动发布。** 摘要推给自己看没问题；要公开发布的摘要，务必人工过一眼。

## 可复用建议

- 五个阶段（抓取/抽取/摘要/去重/分发）拆成独立步骤，状态落库，每步可单独重跑；
- 原始正文永远留存，换 prompt 或换模型时只重跑摘要层；
- 结构化 JSON 输出比自由文本好校验，解析失败重试一次，仍失败就告警；
- 留一份“点开率”记录：日报里哪些条目真的被点开了，用这个信号回头调评分权重，比拍脑诜调参靠谱。

## 总结

这条管线没用到什么稀奇的东西：cron、SQLite、一个 fetch 工具、两段式模型调用。价值在于把“读”变成“筛”，把注意力集中在少数真正值得展开的条目上。LLM 在这里的定位是过滤器而不是替读者，关键内容仍然要点开原文——这一点最好写进 prompt，也写进自己的使用习惯。
