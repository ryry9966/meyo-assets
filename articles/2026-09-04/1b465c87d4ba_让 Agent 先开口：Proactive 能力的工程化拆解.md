## 背景

现在大多数 AI 助手是纯响应式的——你不发消息，它就是一块石头。但真实自动化场景里，很多有价值的事是事件驱动的：早上的日报汇总、监控指标越线、日历冲突出现。这类事用户往往想不起来主动问，等想起来已经晚了。Proactive（主动式）能力，就是让 Agent 在没有用户输入的情况下也能被触发、决策、行动。

## 问题

把响应式助手改造成主动式助手，难点不是"让它动起来"——写个 cron 谁都会——而是三个更工程化的问题：**什么时候该动**（触发）、**动了之后知道什么**（上下文）、**该不该真的动手**（边界）。多数失败案例不是没做出来，而是做出来后天天推送垃圾信息，一周内被用户静音。

## 做法：拆成四层

**1. 触发层。** 三类触发源分开管理：时间型（cron/日历）、事件型（webhook、MCP 事件订阅）、状态型（轮询指标）。在 OpenClaw 里建议把每类封装成独立 trigger 插件，统一输出一个唤醒事件结构，带上 trigger_id、来源和时间戳。

**2. 上下文装配。** 被唤醒的 Agent 是冷启动的，没有进行中的对话。必须在唤醒事件里显式声明装配哪些上下文：相关文件、最近一次相关会话的摘要、任务配置本身。上下文不够就别让它猜。

**3. 决策门。** 唤醒 ≠ 行动。加一层轻量判断，输出三档：立即执行（只读操作）、生成草稿等确认（写操作）、静默（不重要）。规则先行、模型兜底，别一上来就让模型自由裁量。

**4. 行动与反馈闭环。** 每次主动行为落日志：触发 → 决策 → 动作 → 用户反馈（有用/噪音）。这份日志是后续调阈值和 prompt 的唯一依据。

## 踩坑点

- **推送洪水**：没做频控的任务必然被静音。给每个任务设每日唤醒预算，低优先级消息合并成摘要。
- **冷启动瞎干**：不装配上下文就行动，Agent 会基于过期信息写文件。写操作务必带确认门槛。
- **重复触发**：webhook 重试 + cron 重叠导致同一任务并发执行，动作侧要做幂等键。
- **成本失控**：状态型触发轮询太密，token 账单先爆。防抖、批量、拉长间隔。
- **时区漂移**：cron 在容器里默认 UTC，"日报早了八小时"这种事，踩一次就记住了。

## 可复用建议

- 先做只读的主动任务（汇总、提醒、巡检报告），跑稳两周再考虑写操作。
- 任务配置声明式化：触发条件、上下文清单、行动范围、通知策略写进一个 config，别散在代码里。
- 静默时段是刚需：夜间只攒不推。
- 把决策门的规则命中和模型输出都记日志，方便回放"当时为什么动了手"。

## 总结

Proactive 能力 = 触发层 + 上下文装配 + 决策门 + 受限行动 + 反馈闭环。技术门槛不高，真正的难点在于克制——知道什么时候**不动**，比知道什么时候动更值钱。先从每天一条可靠的晨报开始，比一次上线十个会骚扰你的自动化强得多。
