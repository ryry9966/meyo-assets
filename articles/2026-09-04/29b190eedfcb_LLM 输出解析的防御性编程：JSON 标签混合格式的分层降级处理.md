## 背景

在 OpenClaw 插件和 MCP 工具链里，让模型输出结构化数据是高频操作：约定 agent 返回 `<json>{...}</json>`，或让子任务用 ```json 围栏包住结果。提示词写得再清楚，真实流量里模型总会即兴发挥——尤其当你同时接了不同供应商、不同量化本地模型之后，输出风格差异非常大。

## 问题

最初的实现很朴素：正则 `<json>(.*?)</json>` 一把抓，`json.loads` 失败就抛异常。上线后陆续遇到：

- 模型有时用标签，有时用围栏，有时两者都不用、直接裸 JSON；
- 先解释一段话再给 JSON，或一次输出多个代码块；
- JSON 字符串值里本身含 `</json>`（比如总结一段 HTML），非贪婪匹配直接截断；
- 中文语境下的全角引号、全角冒号、尾逗号、`//` 注释；
- 流式输出时标签被 chunk 切开，逐块解析必然失败。

任何一条命中，agent 循环就中断。解析层成了整条链路最脆的一环。

## 做法：分层降级提取

核心思路是不押注单一格式，按成本从低到高依次尝试，拿到能解析的结果就停：

```python
def extract_json(text: str):
    # 1. 标签层：find('<json>') + rfind('</json>')，防值内嵌闭标签
    # 2. 围栏层：匹配 ```json / ```JSON / 裸 ```，多块时倒序取能解析的
    # 3. 括号层：定位首个 {，做字符串感知的括号配平后截取
    # 4. 每层候选进入 clean_and_parse：去 BOM、全角转半角、
    #    去尾逗号与 // 注释，再 json.loads
    # 5. 全失败：返回 None + 元信息（走到哪层、失败原因）
```

几个实现要点：

1. 标签层用 `find` + `rfind` 而不是非贪婪正则，天然规避值内嵌闭标签。
2. 括号扫描必须跳过字符串内部的花括号（跟踪引号与转义状态），否则 `{"a":"}"}` 会被截错。
3. 解析成功后仍要用 schema 校验（pydantic / jsonschema），缺字段给默认值或走重试，别直接塞给下游。
4. 全部失败时不要抛异常打断 agent 循环：把原始输出（截断）与失败原因写日志，向上返回结构化错误，可选地带错误信息重问模型一次（限制重试次数）。

## 踩坑点

- 非贪婪正则截断、贪婪 `.*` 吞掉中间解释文字，是两个方向的经典事故，务必实测多块输出场景。
- `ast.literal_eval` 看似能兜底单引号 JSON，但它直接拒收 `true/false/null`，别当万能后手。
- json_repair 类工具好用，但会静默修数据（比如数字修成字符串），一定要在元信息里标记"经过修复"，防止脏数据无声进入下游。
- 流式场景先缓冲到闭标签或流结束，再走同一套提取逻辑；边收边 parse 等于维护两套解析器。
- 提示词侧防御（few-shot 示例、明确"只输出标签内内容"）能大幅降低命中率，但替代不了解析层——换个模型就失效。

## 可复用建议

- 在插件仓库沉淀统一的 `extract_json(text) -> (data, meta)`，所有工具共用；`meta` 记录命中层级与是否修复，方便统计哪一层最常兜底，反哺提示词优化。
- 把线上真实的坏输出（脱敏后）沉淀为回归用例，每次换模型跑一遍，比凭空构造测试准得多。
- 运行时支持 function calling / JSON mode 时优先用，但保留这套降级链——模型和工具都会换。

## 总结

对 LLM 输出的合理预期是"大概率对、偶尔离谱"。解析层的目标不是消灭异常，而是让异常可观测、可降级：分层提取 + 清洗修复 + schema 校验 + 受控重试，四层下来，绝大多数格式事故从致命错误降级成一条 WARN 日志。
