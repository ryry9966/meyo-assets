## 背景

OpenClaw 的 cron 任务本质上是**定时触发的一次性 agent 会话**：到点后，框架把 instruction 作为完整 prompt 发给一个全新会话，agent 跑完、投递结果、结束。它和在聊天窗口里对话完全不同——agent 是冷启动的，没有你们之前聊过的任何上下文。

## 问题

多数人写 cron instruction，是在照搬自己脑子里对任务的理解。典型几种：

- 「照常整理今天的日报」——什么算"照常"？格式、来源、发到哪，全靠 agent 猜。
- 「继续盯着那个仓库」——哪个仓库？盯什么？
- 「帮我看看有什么新闻」——没来源、没条数上限，agent 自己搜一圈，跑得又长又偏。

这类指令在有上下文的对话里没问题，因为人会补全；cron 会话里没人补全，结果就是跑空、跑偏、重复推送、消息格式混乱。

## 做法

我的经验：把 cron instruction 当成**给一个能力很强但完全不了解背景的新同事的交接文档**来写。能稳定跑的任务，instruction 通常包含五段：

1. **任务一句话 + 数据源。** 具体到 URL、文件路径或工具名。别写"那个 GitHub 项目"，写 owner/repo。
2. **时间锚点。** agent 不一定可靠地知道"现在"，让它先取一次当前时间再算范围："先获取当前时间，只处理过去 24 小时内的条目"。时区写死。
3. **状态与幂等。** cron 反复执行。若任务是"汇总新内容"，必须让它先读固定状态文件（如 `state.json`），跳过已处理条目，处理完写回。这步不写，重复推送几乎必然。
4. **输出格式与投递目标。** 最终消息长什么样、留几条、发到哪。下游是推送渠道时，格式约束尤其重要。
5. **失败分支。** 数据源不可达时是跳过还是告警？不写清，agent 默认可能每次失败都推一条带堆栈的消息，很吵。

可直接套用的骨架：

```
任务：<一句话>
数据源：<具体 URL / 文件 / 工具>
时间：先获取当前时间，只处理过去 N 小时内的内容
状态：读取 <固定路径>/state.json，跳过已处理条目，结束后更新
输出：按 <模板> 整理，最多 N 条
异常：来源不可达则跳过，最终消息中不要输出报错详情
```

**上线前先手动验证一遍。** 把 instruction 原样丢进普通会话跑一次，观察它调了哪些工具、读了哪些文件，比开一堆短间隔测试 cron 更快发现问题。

## 踩坑点

- **相对时间歧义**：「昨天的新闻」在凌晨触发的 cron 里，含义和你的直觉不一样，务必让 agent 先取时间再算范围。
- **把知识塞进 instruction**：任务背景、长期偏好这类稳定信息应放 workspace 固定文件，instruction 只写"参考 <路径>"。塞太长每次都浪费，还容易顾此失彼。
- **没有输出约束**：不限定条数和格式，agent 会给你写小作文，推送出去没人看。
- **指望它记得对话**：cron 会话不带历史，任何"上次说的那个"都是赌博。
- **任务越界**：开放性指令会让 agent 调用一堆你没预期的工具。范围收得越窄，跑得越稳。

## 可复用建议

- 心法一句话：**cron instruction 是交接文档，不是备忘录。**
- 每个定时任务配一个状态文件，做到可重跑、可幂等。
- 稳定背景进文件，易变时间范围进 instruction。
- 新任务先手动跑一次再启用；改了 instruction 也重跑一次。
- 失败要静默还是要告警，提前在 instruction 里定死，别让 agent 自己选。

## 总结

Cron 任务的问题，九成不在调度，而在 instruction。调度只负责"到点叫人"，instruction 决定"叫来的人能不能干活"。自包含、有时间锚点、有状态、有输出格式、有失败分支——五样齐了，定时任务才能从"偶尔抽风"变成"可以放心忘了它"。
