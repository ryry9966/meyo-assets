## 背景

跑 Agent 做自动化时，两个痛点很明显：一是任务常带敏感数据（聊天记录、代码库、内部文档），全丢给云端 API 不放心；二是 Agent 循环调用频繁，token 费用累积很快。本地部署一个中等规模模型当"干活的"或"兜底的"，是社区里不少同学在折腾的方向。这篇帖记录我在一台 32GB 内存 + 16GB 显存显卡的家用机上，从零部署并接入 Agent 工作流的完整过程。

## 问题

动手前先回答三个问题：
1. 我的硬件到底能跑多大的模型？
2. 量化到什么程度，质量损失可接受？
3. 怎么以标准接口接入 Agent/MCP 工作流，而不是只满足于"能聊两句"？

## 做法

**第一步：算显存账。** 粗略公式：显存需求 ≈ 参数量 × 每参数字节数 + KV Cache。Q4_K_M 量化下每参数约 0.6 字节，7B 模型权重约 4GB；上下文开到 16k，KV Cache 还要再吃 1–2GB。我的 16GB 显存跑 14B Q4 模型 + 8k 上下文刚好。

**第二步：选推理栈。** 直接上 Ollama，理由是默认暴露 OpenAI 兼容接口，Agent 框架改个 `base_url` 就能用。对性能和并发敏感的场景可以换 llama.cpp 的 `llama-server`，控制粒度更细。

**第三步：选模型。** 别只看榜单。Agent 场景重点验证两件事：工具调用（function calling）是否稳定、长指令是否遵循。实测下来，14B 级别里挑一个明确支持 tool use 的模型，比盲目上更大但工具调用不稳的模型体验好得多。

**第四步：接入 Agent。** `base_url` 指向 localhost，temperature 压到 0.2–0.4；MCP 工具描述尽量精简——小模型的上下文利用率低，塞太多工具描述会显著拉低调用准确率。

**第五步：压测。** 用真实任务跑 20 轮，记录 tokens/s、工具调用成功率、是否跑飞。没有这一步，前面的调参都是自我感觉。

## 踩坑点

- **上下文长度是显存杀手。** 我一开始开 32k 上下文直接 OOM。KV Cache 随上下文线性增长，按实际任务需要设置，别无脑拉满。
- **小模型工具调用不稳是常态。** 参数格式错、幻觉出不存在的工具名都遇到过。解法：工具数量砍到 5 个以内、描述写短，失败重试时把错误信息喂回上下文。
- **tokens/s 卡在内存带宽。** 有次漏设 GPU offload 层数，模型全跑在内存里，速度只有 3 tokens/s。检查 GPU 层数参数是否拉满。
- **量化不是越小越好。** Q4 以下做闲聊还行，做结构化输出错误率明显上升。Q4_K_M 是我的下限，再低只留给嵌入模型。

## 可复用建议

1. 显存预算：Q4 量化下按「参数量 B × 0.6 + 2」GB 起步估算。
2. Agent 用本地模型，7B 起步，14B 是甜点位；再大性价比骤降。
3. 混合路由：简单任务（分类、抽取、路由）走本地，复杂推理走云端，成本能降一个量级。
4. 把 tokens/s 和工具调用成功率写进日志。没有指标，就没有调优。

## 总结

本地部署的价值不在"替代云端"，而在给 Agent 工作流增加一层可控、低成本、可离线的执行层。14B + Q4 + OpenAI 兼容接口这套组合，一个晚上就能从零跑通。真正的瓶颈不在部署，而在小模型的工具调用可靠性——这个话题值得单独开一帖细聊，欢迎跑通过的同学在评论区交换模型选型数据。
