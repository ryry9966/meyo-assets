## 背景

OpenClaw 的长期记忆本质是一堆 Markdown 文件，agent 通过 memory_search 做记忆召回（memory_recall）。默认走全文搜索（关键词倒排索引），配置了 embedding provider 之后可以叠加语义搜索（向量相似度）。于是问题来了：到底该用哪个？我见过两种极端，要么一直没开语义，要么开了语义就把关键词当过时技术扔了，两种我都踩过坑。

## 问题

我的日常场景大致两类：

- 问“上次那个 ECONNREFUSED 的报错后来怎么解决的”，记忆原文里就有报错关键词，全文搜索一击命中；语义搜索因为措辞不同反而漏召回。
- 问“之前聊过部署成本相关的事吗”，原文写的是“token 花销”“账单”，关键词根本对不上，语义搜索能召回，全文搜索翻车。

单用任何一种，都会在另一半场景里翻车。

## 做法

1. **先建小评测集**：从自己的记忆文件里挑 20 条，每条手写 2~3 个“用户实际会怎么问”的 query，记录期望命中的文件。半小时的事，别省。
2. **分别单测**：只开 FTS 跑一遍，只开语义跑一遍，统计 top-3 命中率。
3. **我的结果**（记忆库约 400 条）：纯 FTS 命中约 60%，纯语义约 70%，但两者命中的条目重叠不到一半，说明二者是互补关系，不是替代关系。
4. **最终方案**：开混合检索。配置好 embedding 后，memory_search 走关键词 + 向量双路召回再融合排序。embedding 我选的本地中文向好的模型（无 API 延迟、无按次费用），召回阈值没调激进，宁多召回靠排序兜底。

## 踩坑点

- **专有名词、路径、命令行参数**：语义模型经常把它们当普通词模糊处理，FTS 才是硬通货，千万别关。
- **中文 embedding 差异极大**：用偏英文的通用模型，中文 query 召回率明显下滑；换多语言/中文模型后立竿见影。
- **记忆条目太长**：切块后语义召回全是碎片，缺上下文。改成“一天一文件、一事一 bullet”的写法后，召回质量才稳定。
- **换 embedding 模型必须重建向量索引**，否则新旧向量混存，相似度排序全部失真，这个问题非常隐蔽。
- **语义检索的延迟和费用**：接远程 embedding API 的高频 agent 要考虑缓存或本地化。

## 可复用建议

- 默认结论：**混合检索 > 单语义 > 单全文**，不要二选一。
- 写记忆时就想着检索：保留原始关键词（报错码、命令、路径、组件名），别只写自然语言转述。
- 20 条 query 的评测集足以避免凭感觉调参，成本极低。
- 把“换模型必重建索引”写进自己的运维 checklist，一次性教训不该出现第二次。

## 总结

语义搜索解决“换了说法也能找到”，全文搜索解决“精确名词必命中”。memory_recall 不是单选题，工程上最省心的路线是：FTS 常开打底，叠加中文向好的 embedding，再用一份自己的小评测集持续验证。先测量，再调参，比任何文章的结论都可靠，包括这篇。
