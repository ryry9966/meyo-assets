## 背景

OpenClaw 的价值不止在对话，更在于让 Agent 真正"动手"：查工单、调内部服务、触发自动化。对接外部服务是绕不开的一步。OpenClaw 提供两条主要路径：MCP 服务器，以及插件/技能形式的自定义工具。两者本质相同——把一个 HTTP 接口翻译成模型能理解、能正确调用的工具。

## 问题

直接把 API 丢给 Agent 通常不好使，常见三类问题：

1. **模型不知道怎么调**——工具描述含糊、参数命名随意，模型靠猜；
2. **调了也不敢用**——鉴权放哪、超时重试谁负责，没有约定；
3. **调了也白调**——返回一大坨 JSON 把上下文塞爆，或报错信息模型读不懂，陷入无意义的重试循环。

## 做法

以对接一个内部工单 API 为例，我的步骤：

1. **选路径**。服务是标准的、团队多端复用，就包一个 MCP server；只是自己用、逻辑简单，写个轻量插件更快，别为了协议而协议。
2. **写薄封装**。不要原样暴露 API。一个工具对应一个明确动作，比如 `search_tickets(query, status)`，参数控制在 3–5 个以内。工具描述用模型视角写：什么时候该用它、参数格式、边界情况。
3. **鉴权与配置**。密钥放环境变量或 OpenClaw 的配置项，绝不写进代码或提示词。启动时校验一次，缺失就明确报错。
4. **错误也要"可读"**。返回给模型的错误要短、结构化、带下一步建议，比如 `{"error": "rate_limited", "retry_after": 30}`，而不是抛完整堆栈。
5. **控制返回体积**。列表接口默认截断（如 top 10），大字段做摘要。上下文是稀缺资源。
6. **超时、重试与幂等**。超时设 10–15 秒；读操作可自动重试，写操作必须带幂等键——否则 Agent 重试一次，你就多一条重复工单。

## 踩坑点

- 工具描述只写"查询工单"，结果模型在已知工单 ID 时还去调 `search_tickets`。描述里必须写清"知道 ID 时用哪个、模糊检索时用哪个"。
- 上游 500 的整段 HTML 被原样返回给模型，它看不懂就开始自由发挥。永远在封装层先把错误规范化。
- 长任务同步等结果，Agent 主循环被卡死。改成提交任务返回 `job_id`，再配一个 `check_status` 工具轮询。
- 调试日志里打了完整请求头，密钥跟着进了日志。加一层脱敏，越早越好。

## 可复用建议

- 把工具封装当独立模块写，配最小单测；别用提示词堆补丁去纠正行为。
- 新接口先只放开只读操作跑一周，看调用日志再决定是否放开写操作。
- 多服务注册时，工具名加前缀（如 `ticket_search`、`crm_search`）避免撞名。
- 给每个工具记录调用成功率、延迟和参数分布，问题会自己浮出来。

## 总结

对接外部服务的核心不是"能调通"，而是让模型调得准、错得明白、失败得可控。薄封装、清晰的工具契约、规范的错误返回、克制的重试策略——这四件事做扎实，OpenClaw 的 Agent 才算真正和外部服务握上了手。
