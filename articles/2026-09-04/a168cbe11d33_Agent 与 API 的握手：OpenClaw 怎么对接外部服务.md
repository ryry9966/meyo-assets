## 背景

OpenClaw 的价值不在会话本身，而在于 Agent 能不能真正"动手"：查数据库、调内部服务、触发工单、同步状态。这些动作的终点几乎都是外部 API。所以"怎么对接外部服务"不是可选项，而是日常工程里出现频率最高的一类需求。目前主流有两条路：直接给 Agent 注册 HTTP 工具（插件 / 自定义 tool），或者通过 MCP 接一个现成的 server。两条路各有适用场景，选错路径往往比实现本身更费时间。

## 问题

实际对接中，坑往往不在"调不通"，而在三个层面：

1. **协议层**：鉴权方式（Header / Query / OAuth）、超时、重试策略没有统一约定，每个工具一套写法，维护成本指数上涨；
2. **语义层**：工具描述写得含糊，Agent 面对十个工具分不清该调哪个；或者参数幻觉——schema 没约束清楚，模型自己编字段；
3. **上下文层**：接口返回 50KB 的 JSON 原样塞给模型，几轮对话下来上下文爆掉，成本和效果同时崩。

## 做法

以"给 OpenClaw 接一个内部订单查询 API"为例，我们团队的实际流程：

**第一步，先选路径。** 只有一个简单接口、团队内部用，直接写一个薄插件就够了；如果服务要跨项目复用、需要标准化的资源与工具描述，或上游已提供 MCP server，才走 MCP。不要为了 MCP 而 MCP——自建 server 的维护成本不低。

**第二步，定义窄接口。** 不把原始 REST 全部暴露，而是按 Agent 的任务视角拆工具：`query_order(order_id)`、`list_recent_orders(status, limit)`。每个工具的 description 写清"什么时候用、什么时候不该用"，参数用严格类型和枚举，不给模型自由发挥的空间。

**第三步，处理鉴权与配置。** API key 走环境变量或密钥管理服务，绝不写进进仓库的配置文件，OpenClaw 侧只读环境变量注入。

**第四步，加防御。** 每次外呼设超时（建议 5–15 秒）；失败重试最多 2 次，且只对幂等请求；返回前做裁剪——只取 Agent 需要的字段，长列表强制分页，单次返回控制在 2KB 以内；错误返回结构化的 `{"error": "...", "hint": "..."}`，而不是裸堆栈。

**第五步，灰度验证。** 先用固定输入跑 dry-run，对比工具返回与直接 curl 的结果；再放进真实会话，观察 Agent 的调用决策对不对，而不是只看接口通不通。

## 踩坑点

- **description 只写"查询订单"四个字**：多个相似工具并存时 Agent 会选错，描述里应写明边界，比如"仅支持近 90 天订单"；
- **写操作没做幂等**：Agent 重试一次，订单创建了三笔。写接口务必带幂等键；
- **危险操作缺确认环节**：删除、退款这类工具，建议拆成"预览 + 执行"两步，中间留人工确认；
- **日志打印了完整请求头**：鉴权信息进了日志。脱敏要在插件层做好，别指望事后清洗。

## 可复用建议

- 工具粒度宁细勿粗：一个工具一个明确动作，组合逻辑交给 Agent 或上层编排；
- 返回结构稳定比字段全更重要，下游 prompt 依赖这个结构；
- 为每个外部依赖做本地 mock，CI 里不碰真实 API；
- 把超时、重试、裁剪做成公共封装，新接一个服务只写业务逻辑。

## 总结

对接外部服务的本质，是替 Agent 做一次"接口翻译 + 风险收口"。接口越窄、约束越硬、失败路径越明确，Agent 表现就越稳定。先从薄插件跑通一个最小闭环，再考虑抽象成 MCP server 复用，是性价比最高的路径。有具体的对接场景欢迎在评论区讨论。
