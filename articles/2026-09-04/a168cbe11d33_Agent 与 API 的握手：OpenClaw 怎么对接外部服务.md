## 背景

Agent 真正有价值的地方不在聊天，而在“能动手”。OpenClaw 的工具层（插件 / MCP）就是那只手：模型决定“做什么”，工具负责“真的去做”。但外部服务不会因为你是 Agent 就变得好说话——认证、超时、幂等、返回值体积，每一个都会在真实环境里变成事故。这篇帖记录我们对接几个内部服务和第三方 API 时沉淀的一套做法。

## 问题

实际对接时最常见的三类翻车：

1. 模型“自信地”调用了工具，参数是编的：不存在的订单号、拼错的枚举值，API 返回 4xx 后 Agent 又开始一轮脑补重试。
2. 网络抖动触发自动重试，但操作是写入型，结果下了两笔一样的单。
3. 接口返回 200KB 的 JSON 直接塞进上下文，几轮之后 token 爆掉，关键错误信息还被淹没。

## 做法与步骤

**1. 先选接入形态。** 只读、无状态、单个 Agent 用的接口，直接写成插件工具函数即可；需要跨 Agent 复用、有会话状态、或实现会频繁变的服务，包成独立 MCP server，边界更干净，也方便单独升级。

**2. 把工具描述当文档写。** 模型选参数完全依赖描述和 schema。参数能用枚举就别用自由字符串，description 里写清“什么时候该用、什么时候不该用”，比在 system prompt 里反复叮嘱有效得多。

**3. 凭证与配置分离。** key 走环境变量或独立配置文件，绝不写进工具描述，也不打进日志；每个服务单独一份凭证，出问题好 revoke。

**4. 超时、重试、幂等三件套。** 每个外部调用显式设超时；只有幂等操作才允许自动重试；写入型接口尽量带幂等键，或先查后写。长任务拆成“提交任务 + 轮询结果”两个工具，别让 Agent 同步干等阻塞循环。

**5. 裁剪返回值。** 工具层做字段过滤、分页、截断，只返回模型决策需要的内容；错误统一返回结构化的 `{code, message, hint}`，给 Agent 一条能走的路，而不是一堆原始堆栈。

**6. 每次调用留痕。** 记录工具名、入参、出参摘要、耗时、trace id。出问题时你能回答“Agent 到底干了什么”，这比任何 prompt 调优都救命。

## 踩坑点

- 描述写得含糊，模型就开始“发明”参数——大部分幻觉调用的根源都在这，不在模型本身。
- 重试逻辑藏在 HTTP 客户端默认行为里，业务层的非幂等很容易被忽略。
- 把 500 的原始堆栈丢给模型，它会把堆栈当数据继续推理，越走越偏。
- 上线即放开写权限。我们现在的节奏是：先只读跑两周，再开 dry-run 模式看入参是否合理，最后才真正放写。

## 可复用建议

- **统一适配层**：一个服务一个文件，统一的错误格式、统一的超时默认值，新服务接入基本控制在半小时内。
- **工具也写契约测试**：固定入参 → 断言出参结构，API 改版时先红后修，别等 Agent 在线上替你发现。
- **上线前人工过一遍固定清单**：凭证在哪、超时多少、最坏情况重试几次、返回值最大多大、日志里有没有敏感字段。

## 总结

对接外部服务的本质，是把“模型的判断力”和“工程的安全性”分好工：模型负责决定，工具层负责兜底。OpenClaw 给了足够的自由度，代价是这些边界要自己画。把描述写准、把超时设死、把返回裁小、把日志留全，Agent 和 API 的握手就稳了。欢迎在评论区交流你们踩过的坑。
