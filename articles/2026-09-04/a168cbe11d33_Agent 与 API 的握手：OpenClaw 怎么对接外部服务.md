## 背景

Agent 的价值在于能动手。在 OpenClaw 里，一个 agent 光会推理不够，真正"干活"的时刻几乎都是它调用外部 API 的时刻：查库存、建工单、拉报表、触发部署。对接外部服务常见三条路：

1. **MCP server**：适合标准化程度高的服务，社区已有不少现成实现，接上就能用；
2. **薄适配层封装成 tool**：适合内部 API，把鉴权、字段映射都消化在自己的插件里；
3. **直接 HTTP tool**：适合一次性脚本或快速验证，快但糙。

三条路殊途同归，最终落到同一件事：让模型"看懂"接口，让接口"扛得住"模型。

## 问题

实际对接中最常见的不是"调不通"，而是调通了但不可靠：

- 工具描述含糊，agent 传参基本靠猜；
- 没有超时和重试，一次网络抖动让整轮任务挂死；
- 接口返回巨大 JSON 被原样塞进上下文，token 直接爆炸；
- 对非幂等接口盲目重试，造成重复下单、重复建单。

## 做法与步骤

1. **选路径**：标准服务优先找现成 MCP server；内部 API 写薄适配层；验证阶段用 HTTP tool 快速试错。
2. **定契约**：每个 tool 只做一个动作，参数带类型、范围和默认值；description 要写"什么时候该用我"，而不只是"我是什么"。
3. **管凭证**：密钥走环境变量或密钥管理服务，不进配置文件、不打日志。
4. **加护栏**：设置超时（10–30 秒视接口而定），仅对幂等操作做指数退避重试，必要时携带幂等键。
5. **裁剪响应**：只返回字段摘要加状态码，原始大 payload 落盘或传引用，绝不直接进上下文。
6. **先跑 dry-run**：用 mock 或测试环境验证 agent 的完整调用路径，再切生产。

## 踩坑点

- description 写"调用用户接口"，agent 不知道何时该调用。应写清触发场景和前置条件，例如"当用户询问某用户权限时使用，需要先有 user_id"。
- 重试 POST 导致资源重复创建。加重试前先问自己：这个操作做两次会怎样？
- 外部 API 改版引发 schema 漂移，agent 悄悄传错参数。需要契约测试兜底，接口变更时能第一时间报警。
- 工具越挂越多，agent 出现选择困难，调错工具的概率上升。定期下线低频 tool，按场景拆分。
- 错误只抛一段异常字符串，agent 无法自纠。应返回结构化错误码加人类可读的原因描述。

## 可复用建议

- **薄适配层原则**：外部 API 的所有怪癖——鉴权方式、分页、脏数据——都消化在 adapter 里，agent 眼中永远是干净的 tool。
- **全量记录调用**：每个 tool 调用记录时间、参数摘要、状态、耗时，出问题时能完整回放定位。
- **控制工具数量**：单 agent 挂载的 tool 控制在 10 个以内，超出就按业务场景拆子 agent，让每个 agent 的"工具箱"足够小、足够专。

## 总结

对接外部服务的本质不是"接上"，而是建立一份双方都能遵守的契约：模型看得懂描述，接口扛得住重试，错误能被消化，凭证不会泄漏。把功夫花在契约和护栏上，agent 才能在生产环境里和外部服务稳定握手——一次调用是一笔交易，而不是一次抽奖。
