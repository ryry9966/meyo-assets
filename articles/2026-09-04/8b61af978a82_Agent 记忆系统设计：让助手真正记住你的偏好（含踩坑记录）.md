## 背景

用 Agent 做日常自动化，最常见的不满不是"不聪明"，而是"不长记性"：昨天明确说过接口风格用 REST，今天它又给你生成一遍 GraphQL。模型本身无状态，上下文窗口再大也装不下所有历史。记忆系统本质上是个工程问题：在有限的 token 预算里，把"该记住的"在"该用的时候"注入提示词。

## 问题：为什么"塞进 system prompt"会失效

- **全量写入**：三天后 prompt 比任务还长，大量记忆与当前任务无关，反而稀释指令权重；
- **只靠对话历史**：召回靠模型"顺带想起"，极不稳定；
- **没有更新机制**：新旧偏好冲突时（"我不吃辣" vs "今天想试试辣的"），要么永远旧值，要么长期偏好被一句话覆盖。

## 做法：三层存储 + 异步写入 + 混合检索

我在 OpenClaw 侧用 MCP 工具实现了一套轻量记忆，步骤如下：

1. **分层**。核心偏好（稳定、每次必注入：语言/代码风格/部署习惯，上限 20 条）；情景记忆（会话中产生的事实，带时间戳，按需检索）；会话记忆（本 session 工作状态，结束即弃）。
2. **异步写入**。回复完成后用小模型跑一遍抽取，产出结构化记录：key、value、scope、confidence、source、updated_at。不阻塞主回复，低置信度记录先挂起，重复出现再落库。
3. **写入门控**。key 冲突时不直接覆盖：区分"稳定偏好"和"一次性请求"（看措辞和重复次数），后者只进情景记忆。敏感字段默认拒绝写入，除非显式确认。
4. **混合检索**。组装 prompt 时核心偏好直接注入；情景记忆走"embedding top-k + 关键词精确匹配"双路合并，总预算 800 token，超出按 confidence × 时效衰减截断。
5. **可见可删**。提供 memory_list / memory_delete 工具，用户随时查看和清理。这比检索算法更重要——不透明的记忆会迅速失去信任。

## 踩坑点

- 早期"什么都记"，两周后检索精度明显下滑。记忆系统的第一指标是精度不是召回，宁可漏记，不能记错。
- embedding 对 ID、路径、短代码这类精确串几乎无效，关键词通道必须保留。
- 抽取模型太小会产出大量废话记录，换成严格 schema 输出才稳定下来。
- 忘做 TTL，半年前的过期偏好（旧项目规范）一直被召回。现在情景记忆默认 90 天衰减。

## 可复用建议

- 先定 schema 再写代码：scope / confidence / source / updated_at 四个字段是冲突处理和调试的地基。
- 从"规则 + grep"起步，别一上来上向量库，20 条核心偏好一个 JSON 就够。
- 用 MCP 把记忆做成独立工具服务，任何 Agent 都能挂，别耦合进某个客户端。
- 攒 20~30 条"该记得/不该记得"的测试用例，每次改策略跑一遍，比手感靠谱。

## 总结

记忆系统不是"给模型加个数据库"，而是写入策略、检索预算、冲突处理、用户可见性四件事的组合。先用最土的办法管好核心偏好，再逐步加语义检索，比一步到位搭"记忆中台"务实得多。欢迎在评论区贴出你们的 memory schema，互相抄作业。
