## 背景

我们团队每天的日报来源很散：OpenClaw agent 的运行日志、若干定时任务、MCP 工具调用记录、几个插件的错误输出。以前的流程是一个人早上翻四处日志，手写一段总结发群里。问题不只是费时间——人对日志的注意力是递减的，第 1000 行之后的异常基本靠运气。

## 问题

直接把原始日志丢给 LLM 总结这条路我们试过，不成立：日志量动辄超上下文；更麻烦的是模型会把数字"顺滑地改对"，失败次数、耗时分布这类关键指标不能交给概率性环节。

结论是：**确定性的部分交给代码，不确定性的部分才交给模型。**

## 做法

流水线分四层，每层落盘中间产物（raw / normalized / aggregated / report）：

1. **采集层**：各来源统一写成 JSONL 到 staging 目录，字段固定为 `ts / source / event / level / metrics`。异构格式在各自的 adapter 里抹平。
2. **结构化层**：脚本解析 + schema 校验，格式不符的条目进 reject 文件并计数，不静默丢弃。
3. **聚合层**：纯代码统计任务数、失败率、耗时分布、Top 错误，输出一份中间 JSON。这一步没有任何模型参与。
4. **叙述层**：把聚合 JSON 交给 OpenClaw agent 生成 300 字以内的日报正文。agent 挂了 MCP 查询工具，遇到需要解释的错误可以按需回查明细，而不是凭摘要猜。
5. **分发层**：webhook 推送前做断言校验（失败率在 0–100%、总数与聚合层一致等），不过就走人工通道。cron 调度，带 `--dry-run` 参数可随时重放。

## 踩坑点

- **时区与跨天边界**：踩过一次 UTC 和本地时间混用，导致日报漏了晚间时段。现在统一 UTC 存储、展示层转本地，统计窗口 `[00:00, 24:00)` 写死在配置里。
- **格式漂移静默失败**：上游改了一个字段名，流水线"成功"产出空报告。修复方式是给"当日事件数为 0"加告警——空报告比错误报告更危险。
- **重试导致重复推送**：推送记录落本地状态文件，幂等键用 `日期+渠道`。
- **报告越写越长**：LLM 天然爱展开。模板强制固定结构：三行结论在前，明细链接在后，字数写进提示词约束。

## 可复用建议

- schema 和报告模板都进版本库，改动走 PR，方便回溯某天报告"为什么长这样"。
- 叙述层提示词里明确一条：**不得出现聚合 JSON 中不存在的数字**。这条是可信度的底线。
- 切自动之前先 dry-run 跑一周，逐日和人工日报对比校准，别一步到位。

## 总结

日报自动化的核心不是让模型"读懂日志"，而是分层：采集、解析、统计交给代码保证数字可信；叙述交给模型保证可读；中间用校验和告警兜住边界。搭好后维护成本很低，收益是每天省下的半小时，以及异常能在一个固定时间点被确定性地看见——而不是被人翻日志时的运气决定。
