# 背景

在 OpenClaw 里做自动化，最后都会落到两个原语上：**cron** 和 **heartbeat**。新人常见的误区是二选一，把所有事情塞进其中一个，结果要么定点任务不准点，要么 token 账单很难看。这篇把两者的适用边界讲清楚。

# 两者到底是什么

- **cron**：确定性调度。给一个 cron 表达式加一段指令，到点触发，跑完即止。时间驱动，语义是"**什么时候做什么**"。
- **heartbeat**：周期性唤醒。agent 每隔 N 分钟被拉起一次，读自己的 HEARTBEAT.md 清单，自行判断有没有值得做的事，没有就静默跳过。状态驱动，语义是"**看看有没有事要做**"。

| 维度 | cron | heartbeat |
|---|---|---|
| 触发语义 | 时间到就跑 | 醒来自行判断 |
| 适合 | 定点、固定动作 | 条件触发、按需动作 |
| 时间精度 | 高（精确到分钟） | 尽力而为，可能延迟 |
| Token 开销 | 仅运行时 | 每次唤醒都消耗 |

# 判断标准

一句话：**时间固定、动作固定用 cron；条件满足才动作用 heartbeat。**

典型 cron 场景：每天 9 点发日报、每小时拉数据落盘、每周一生成周报。触发时机和输出都确定。

典型 heartbeat 场景：盯目录有没有新文件、监控服务状态变化、提醒滞留超过 3 天的待办。你不知道何时触发，只知道条件。

# 实操步骤

1. 把手头的自动化需求列成表，逐条标注"触发时机是否确定"。
2. 确定型注册 cron：`openclaw cron add --name daily-digest --cron "0 9 * * *" --message "..."`，**显式指定时区**，输出投递到固定 session 或频道。
3. 非确定型写进 HEARTBEAT.md：清单要短，每条写清"什么条件下做什么、否则什么都不做"，把 no-op 设为默认路径。
4. heartbeat 间隔从 30–60 分钟起步，观察一两周再调。
5. 两种机制都把跨次状态持久化到文件（JSON/Markdown）。cron 每次运行是新上下文，不落盘等于失忆。

# 踩坑点

- **用 heartbeat 做定点任务**：heartbeat 是尽力而为的调度，设备休眠、队列繁忙都会延迟，别指望它 9:00 整发消息。
- **cron 时区坑**：默认跟宿主机走，服务器在 UTC 而你以为在东八区，日报会晚八小时。
- **HEARTBEAT.md 写太长**：每次唤醒都烧 token，且模型容易误判触发条件。条目宁可少而清晰。
- **长任务重叠**：cron 任务运行时间超过间隔，下一轮会再起一个实例，注意加锁或拉长间隔。
- **双通道重复通知**：cron 和 heartbeat 都往同一个频道发，用户会收到两遍，职责必须切干净。

# 可复用建议

- 口诀记一句："**问几点用 cron，问要不要用 heartbeat。**"
- 更稳的架构是协作而非二选一：cron 负责"取数/生成"，heartbeat 负责"判断/提醒"，通过共享状态文件衔接。
- 给每个 cron 任务起名字、输出落日志文件，排障时能对上每一次运行。
- 心跳清单控制在 3–5 条以内，超了就该拆成 cron 或独立脚本。

# 总结

cron 和 heartbeat 不是竞争关系，是两类问题的答案。前者把"何时"写死，后者把"是否"交给 agent 判断。分清触发时机是否确定，再补一层共享状态文件，绝大多数自动化需求都能干净落地。
