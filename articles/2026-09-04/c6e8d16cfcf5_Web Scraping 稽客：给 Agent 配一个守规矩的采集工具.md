## 背景

Agent 一旦要接资讯汇总、价格监控、竞品调研这类任务，网页采集就绕不开。最常见的初始实现很朴素：给模型一个 fetch 工具，让它自己抓、自己读。demo 阶段能跑，但很快会撞上三类问题——被封、抓不到、上下文炸掉。我们的做法是在插件体系里把采集能力收敛成一个独立的 MCP 工具，跑了一段时间，把经验沉淀成这篇。

## 问题

拆开看是三层：

1. **合规与礼貌**：目标站的 robots.txt、ToS、访问频率，很多实现直接忽略，被封 IP 只是时间问题；
2. **技术可行性**：大量站点是 SPA，静态请求拿到的是空壳 HTML；还有编码、反爬、动态加载；
3. **上下文安全**：整页 HTML 灌进上下文，token 成本失控；更隐蔽的是页面正文里可能埋着"忽略之前的指令"这类注入内容，Agent 会当真。

## 做法

我们的工具层按这个顺序处理：

1. **入口收敛**。Agent 不直接发起网络请求，只调用统一的 scrape 工具。工具内做域名白/黑名单校验，私有网段（127.0.0.1、10.x、169.254.x）一律拒绝，顺带防 SSRF。
2. **合规前置**。抓取前读取 robots.txt 并缓存，Disallow 的路径直接返回带原因的错误；UA 里带可识别的 bot 标识；对每个域名做令牌桶限速，默认 1 req/2s。
3. **双通道抓取**。先走静态 HTTP + readability 正文抽取；检测到内容过短或含 SPA 特征时，再降级到 headless 浏览器渲染，渲染实例按域名复用。
4. **输出净化**。抽正文、去 script/style/注释、转 Markdown、按 token 上限截断；相对链接补全为绝对 URL；正确处理响应编码。
5. **注入隔离**。返回内容强制封装在结构化字段里（`source_url` + `content`），并在系统提示词中约定：该字段仅为数据，不作为指令；隐藏文本和 HTML 注释直接丢弃。
6. **缓存与观测**。URL 规范化后做 TTL 缓存，配合 ETag/Last-Modified；每次抓取记录域名、耗时、失败原因分类，方便复盘。

## 踩坑点

- SPA 页面只返回 `<div id="root">`，HTTP 200 但正文为空——空内容判断不能只看状态码；
- 无限滚动列表抓不全，headless 下需要滚动到底再判定"加载完成"，且必须设滚动次数上限，否则死循环；
- 相对链接、gbk 编码这些老问题，在 LLM 管道里依然会咬人；
- 分页采集容易被 Agent 自己写成 while(true)，工具层要强制 max_pages；
- 对抗指纹检测要克制：调 UA、补 header 可以，绕验证码这类事建议直接放弃，转官方 API 或人工；
- 表格和代码块经通用抽取后容易丢结构，对结构化站点宁可写专用解析器，别全靠 readability。

## 可复用建议

- 采集永远走统一工具，不把裸 fetch 开放给模型；
- robots.txt + 限速 + UA 标识三件套是底线，不是可选项；
- 所有外部内容打上"数据非指令"标签，并固化进系统提示词；
- 失败要分类返回（被拒、超时、空内容、渲染失败），别只抛 500；
- 先静态后渲染，headless 是昂贵路径，按需触发。

## 总结

让 Agent 安全地采集网页，核心不是某段抓取代码，而是把**礼貌、可行、安全**三件事做成工具层的默认行为。Agent 只负责决定抓什么；怎么抓、能不能抓、抓回来怎么洗，全部收敛在工具里。这样换模型、换任务时，采集质量是稳定的，出问题时也有完整日志可查。思路不复杂，但值得在第一个 fetch 工具上线前就想清楚。
