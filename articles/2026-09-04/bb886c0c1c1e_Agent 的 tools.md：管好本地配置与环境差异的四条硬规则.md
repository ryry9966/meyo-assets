## 背景

让 Agent 在自己机器上干活，第一道坎往往不是能力，而是它不了解你的环境：你让它重启服务，它敲 `systemctl`，而你的 macOS 上只有 `brew services`；让它跑脚本，它翻出一个废弃已久的 conda 环境。这不怪模型——它只是缺一份关于“这台机器”的说明。

tools.md 就是为此存在的：工作区（默认 `~/.openclaw/workspace/`）里一份由用户手工维护的纯文本，Agent 执行本地操作前会读到它。它的定位很朴素：**你机器的 README，读者是 Agent**。

## 我见过的四种反模式

1. **环境信息写进系统提示词**：换机器要重写，每个会话都在烧 token。
2. **指望记忆**：静态事实交给记忆文件，随上下文滚动被压缩、漂移，某天 Agent 开始“记错”甚至编造路径。
3. **多机共用一份**：笔记本和家里服务器路径、包管理器、代理端口全不同，Agent 自信地用错。
4. **把密钥写进去**：tools.md 会进入上下文，等于把 secret 复制进每一份会话记录。

## 我的做法

- **只写事实，不写流程**。“Docker 是 rootless 的”“Python 统一用 uv”“代理在 `127.0.0.1:7890`”这类一句话条目；“如何部署 X”这种多步流程做成 skill 或脚本，tools.md 里只留一行指路。
- **控制在 100 行以内**，按「路径 / 运行时 / 服务管理 / 网络 / 已知坑」分五段，条目式，不写散文。这份文件要进上下文，长度即成本。
- **不放 secret，只放“去哪找”**：写“API key 从 shell 环境变量读取”，不写值本身。
- **机器本地，不进同步盘**。它和 `/etc/hosts` 是同类东西。多机需求用「模板 + 覆盖」：git 里维护一份 `tools.base.md`，一个十几行的脚本按主机名生成各自的 tools.md，公共项只改模板。
- **一次纠错，一条记录**：每次你手动纠正了 Agent 的环境错误，当场往 tools.md 加一行。这条纪律保证文件里每一条都来自真实踩坑，比任何定期整理都可靠。

## 踩坑点

- **越写越长**：从 30 行涨到 200 行后，Agent 反而抓不住重点。我的自查标准：某条目三个月没“起过作用”，删。
- **与 skills 重复**：某能力一旦有 skill 承载，tools.md 里的对应条目立刻删，否则两处信息漂移时 Agent 不知道信谁。
- **迁移后忘更新**：conda 换 uv、pipx 换 brew，旧条目还在，Agent 会继续用旧环境。重大迁移时，把过一遍 tools.md 列进迁移 checklist。
- **坑不在 tools.md**：有些问题出在你自己脚本里写死的 `/Users/xxx/...`，Agent 照着执行照样挂。tools.md 治不了硬编码。

## 可复用的建议

- 把 tools.md 当名词手册：路径、版本、端口、别名，全是一句话事实，不出现“先……然后……”。
- 多机用 base + 覆盖生成，不手工维护多份全文。
- 验证生效很简单：开个新会话问一句“这台机器跑脚本用哪个 Python”，答案对了就说明读到了。
- 写个 lint 脚本定期检查文件里引用的路径是否存在，防止它烂成一份过期文档。

## 总结

tools.md 便宜、朴素，却是 Agent 与真实环境之间成本最低的契约。四句话：只写事实、保持短小、不放密钥、机器本地。流程交给 skills 和脚本，事实交给 tools.md，记忆交给对话——各归其位之后，Agent 在你机器上的行为会稳定得多。
