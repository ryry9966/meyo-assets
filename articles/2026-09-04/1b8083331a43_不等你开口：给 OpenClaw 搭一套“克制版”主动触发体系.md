## 背景

我们用 AI 助手的方式基本是拉模式：提问、回答、结束。但真正省时间的往往是推模式的活——定时摘要、异常预警、到点提醒。这类事不需要你记得去问，需要的是有人盯着。OpenClaw 常驻在消息通道旁边，7x24 在线，天然适合做这件事。它提供了三个现成的触发源：heartbeat（心跳）、cron（定时任务）、webhook/MCP（事件驱动）。

## 问题

最容易踩的坑是“让 agent 自己决定什么时候说话”。结果通常两个极端：要么永远沉默，要么每小时汇报一次“一切正常”。要把它做成可靠的工程系统，得拆成三件事：触发从哪来、每次触发的上下文预算多少、什么情况才配打扰你。

## 做法

**1. 心跳：用 HEARTBEAT.md 定义检查项。** OpenClaw 默认按固定间隔（约 30 分钟）唤醒一次 agent，读取工作区的 HEARTBEAT.md。写法要具体，且必须给沉默出口：

```markdown
# Heartbeat Checks
- 检查 ~/inbox/ 是否有超过 2 小时未处理的文件
- 磁盘占用超过 85% 时发消息提醒
- 无事发生时回复 HEARTBEAT_OK，不要输出任何内容
```

`HEARTBEAT_OK` 是约定信号，agent 返回它时不会转发到你的聊天窗口。

**2. cron：确定性时间任务。** 日报、周报、定时拉数据。关键是把输出通道和格式写死在任务描述里，否则两周后你会收到五个版本的“日报”。

**3. 事件驱动：webhook 敲门，agent 判断。** CI 失败、指标越线这类事件，触发器只负责说“有事”，细节让 agent 用 MCP 工具自己查，避免在触发器里堆业务逻辑。

**4. 通知分级。** urgent 直发；其余进 digest，固定时间一次汇总。分级标准写进系统提示，不要靠 agent 临场判断。

## 踩坑点

- **心跳太密。** 见过 5 分钟一跳的配置，一天几百次 LLM 调用，成本和噪音双爆炸。检查项少于三条，间隔就调到 30 分钟以上。
- **弱模型把心跳当聊天许可。** 即使写了“保持沉默”，某些模型仍会冒一句“一切正常”。硬约束 + HEARTBEAT_OK 出口，缺一不可。
- **重复告警。** agent 没有跨次记忆，同一条磁盘告警能连发三遍。让它把状态写入 `checks/last-alert.json`，触发前先读。
- **时区。** cron 按服务器时区跑，凌晨三点收到日报体验极差。配置前先确认时区，通知策略里明确 quiet hours。
- **上下文稀释。** 主动任务注入的文件越多，正式交互任务的质量越容易掉。单次心跳控制在两三个文件以内。

## 可复用建议

1. **先只读，后写入。** 第一周只允许 proactive 发消息、禁写操作，观察误报率再逐步放开。
2. **写一份主动行为准则。** 什么级别直接打扰、什么级别进 digest、什么级别忽略，一页纸放进系统提示。
3. **所有触发落日志。** 时间、触发源、是否真的打扰了你。一周后回看日志，就知道该调哪个旋钮。

## 总结

Proactive 不是开关，是旋钮：触发源决定它能不能动，上下文预算决定它划不划算，通知策略决定你留不留它。从一条心跳检查项开始跑一周，比一次配十条再关掉八条强得多。
