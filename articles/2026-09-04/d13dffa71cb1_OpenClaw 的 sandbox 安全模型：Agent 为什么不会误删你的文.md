## 背景

让 Agent 直接操作文件系统和 shell,是自动化收益最大的场景，也是风险最集中的场景。OpenClaw 的设计立场很明确：不指望模型永远不犯错，而是让单次错误的影响被限制在可恢复的范围内。它的 sandbox 不是一个开关，而是几层防线的叠加。

## 问题：误删到底怎么发生的

复盘真实的 agent 事故，几乎都不是“恶意”，而是几种机械性错误：

- **幻觉路径**：模型拼出一个不存在的目录，却笃定地执行删除；
- **cwd 漂移**：子进程继承的工作目录和模型假设的不一致；
- **变量为空**:`rm -rf "$DIR"/*.log` 里 `$DIR` 没被赋值，命令语义完全改变；
- **glob 失控**：递归通配符的实际覆盖面比模型预想的大得多。

这类错误 prompt 管不住，工具层校验也只能算第二道闸。

## 做法：四层防线

1. **OS 层隔离**。Agent 的工具调用运行在独立容器/用户命名空间中，非 root、独立 UID,与宿主机进程完全隔离。这是唯一“模型绕不过去”的一层。
2. **文件系统边界**。只有一个 workspace 以可写方式挂进沙箱，系统路径全部只读 bind mount(记得加 `:ro`),home 下的敏感目录默认不挂载。模型看到的世界里，本来就没有你的文件。
3. **路径守卫**。所有写/删操作执行前先 resolve 真实路径(展开 symlink),落在 workspace 外一律拒绝。守卫必须放在 symlink 解析**之后**，否则软链接就是现成的逃逸通道。
4. **操作分级与回收站**。读操作放行；workspace 内写放行；删除先进沙箱内 trash 目录，可整体回滚；workspace 外的写/删、`git clean` 类命令、批量 rm,统一走人工确认通道。确认消息要带上下文(命令、目标路径、影响面)，而不是一句“要继续吗”。

## 踩坑点

- 只在工具层做路径校验，忘了 agent 拉起的子进程、脚本里的 `mv`/`cp` 同样要过闸——校验必须落在沙箱边界上，而不是某个工具函数里。
- 给容器挂了 `docker.sock` 或给了 sudo,前面所有隔离等于零，这是最常见的“自我击穿”。
- 只读挂载漏写 `:ro`,排障半天发现是挂载参数问题。
- 确认策略太粗：什么都问，用户会形成“无脑通过”的肌肉记忆，高危确认反被稀释。
- trash 目录也在沙箱里，要设容量上限并定期清理，否则磁盘会被安静地写满。

## 可复用建议

- 沙箱永远放 OS 层，prompt 和工具校验只当第二道防线；
- 收敛到“单一可写根”，其余路径默认不可见或只读；
- 删除一律先入回收站，把不可逆变成可逆；
- 维护一份高危命令模式清单(`rm -rf`、`git clean`、`chmod -R`、`shutil.rmtree`……),命中即确认；
- 上线前做一次演练：故意诱导 agent 执行危险命令，验证边界真的拦得住。

## 总结

Agent 安全的正确问法不是“怎么让它不犯错”，而是“犯了错之后损失有多大”。OpenClaw 的 sandbox 把答案压到很小：错误被圈在 workspace 内、删除可回滚、越界必确认。信任模型，但让每一次信任都有边界——这才是敢把自动化交给 agent 的前提。
