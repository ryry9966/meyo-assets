## 背景：重试不是异常，是常态

跑过一段时间自动化的人都会遇到：定时任务重叠触发、webhook 被重推、Agent 因工具调用超时而重试、进程崩溃后被调度器再拉起一遍。在 OpenClaw 这类 Agent/插件体系里，重放几乎是设计使然——你没法保证"只执行一次"，只能保证"重复执行也安全"。这就是幂等性要解决的问题：**同一个操作执行 N 次，效果与执行 1 次相同。**

## 问题：副作用只该发生一次

不幂等的操作很常见：往文件追加一行、创建工单、插入记录、发一条群通知。它们在重试场景下会变成重复工单、双倍通知、越滚越大的日志文件。更隐蔽的是"半成品"状态：任务跑到一半挂了，前半段副作用已经落盘，重试再跑一遍就叠加了。幂等性不是"尽量别重复"，而是承认重复必然发生，然后让状态收敛。

## 做法：四个步骤

1. **先分类**。把操作分成天然幂等（按 ID 覆盖写、按 ID 删除、"确保存在"式写入）和天然不幂等（追加、自增、创建、发送），改造重点放在后者。
2. **定义稳定的幂等键**。键要来自任务语义，比如 `digest-{日期}-{频道ID}` 或输入内容的哈希，而不是执行时随机生成的 UUID——后者每次重试都变，等于没设。注意用任务的逻辑日期（本次统计窗口），别用"当前时间"。
3. **落一个执行记录**。SQLite、Redis 甚至带锁的 JSON 文件都行：执行前查键，已成功则跳过；开始时写 `running`，完成后写 `done`。让存储层的唯一约束兜底，而不是只靠应用层判断。
4. **优先"对账式"写法**。把"创建一个资源"改成"对比目标状态与当前状态，缺什么补什么"。声明式的 ensure 风格天然幂等，也更容易做断点续跑。

## 踩坑点

- **并发竞态**：两个实例同时查到"不存在"，然后都执行。解法是数据库唯一索引或 Redis `SETNX` 做原子占位；文件方案要配锁加临时文件原子重命名。
- **只记整任务，不记子步骤**：中途挂掉后重试会把已完成的前半段重做。要么按子任务拆幂等键，要么让每一步本身幂等。
- **状态记录无限增长**：旧键要设 TTL 或归档，否则一年后每次启动都要扫几万条。
- **卡死的 `running` 记录**：崩溃留下的 running 状态要有超时回收逻辑，否则一次故障就把后续重试永久挡在门外。
- **把幂等当无限重试的许可证**：网络超时可以重试，参数校验失败重试一百次也一样，要区分可重试与不可重试错误。
- **外部 API 不支持幂等键**：那就带一个稳定的外部引用号，先查后建，配合服务端唯一字段。

## 可复用建议

- 写工具/插件时默认按 `ensure(X)` 而非 `do(X) once` 的语义实现，并在 MCP 工具描述里写清幂等行为——Agent 重放调用的频率比你想象的高。
- 沉淀一张统一的 `runs` 表（key / status / updated_at），所有 skill 共用，别每个脚本自造一套。
- 加一条验收标准：**同一任务连跑两遍，第二遍必须是 no-op**。能在 CI 或冒烟测试里验证的幂等性才算数。

## 总结

自动化系统的可靠性不来自"保证不重复执行"，而来自"重复执行也无害"。定时器、webhook、Agent 重试都会让代码比你预期的跑更多次；把幂等键、执行记录和对账式写法变成默认习惯，重试就从风险变成了普通的容错手段。
