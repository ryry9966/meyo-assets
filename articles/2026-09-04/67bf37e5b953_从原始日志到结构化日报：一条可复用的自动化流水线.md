## 背景

团队日常运行中会产生大量"日志型"信息：Agent 任务执行记录、CI 构建结果、部署事件、插件调用失败、异常上报……日报本该是这些信息的汇总，但现实往往是有人手动翻日志、复制粘贴、凭记忆补内容。我们基于 OpenClaw 搭了一条自动化流水线，把"原始日志 → 结构化日报"固化下来，稳定跑了两个多月，把做法整理如下。

## 问题

直接把日志丢给 LLM 总结，会遇到三个典型问题：

1. **Token 爆炸**：一天的原始日志动辄几十万 token，直接喂不现实，截断又会丢关键事件。
2. **幻觉与不稳定**：模型会"脑补"数字、漏掉低频但重要的报错，且每次输出格式不一致，下游没法消费。
3. **失败静默**：流水线半夜挂掉没人知道，第二天站会才发现日报是空的。

所以核心思路是：**LLM 只做最后一公里的叙述层，前面的采集、清洗、聚合全部用确定性代码完成**。

## 做法

流水线分四段，每段独立可测：

**1. 采集层**。定时任务 + MCP 工具拉取各数据源（git 提交、CI 运行、Agent 任务日志），关键动作是在入口统一 schema，转成 JSON Lines：

```
{ts, source, type, level, project, payload}
```

**2. 清洗与聚合**。去重、按 project/type 分组、计算错误数、成功率和耗时分布。产出一份中间聚合 JSON，落对象存储缓存——重跑和排障都依赖它。

**3. 结构化摘要**。把聚合 JSON（不是原始日志）交给 Agent，prompt 中固化输出 schema，temperature 调低，要求缺失字段显式写 `"missing"` 而不是猜。输出过 JSON Schema 校验，不过就退回规则模板兜底。

**4. 渲染与分发**。Markdown 模板渲染，推送群 webhook 和 wiki，按日期键归档。同一天重跑是覆盖而非追加（幂等）。

## 踩坑点

- **时区**。cron 用 UTC、日志时间戳用本地时区，导致日报"分家"。现在在采集入口统一归一到东八区。
- **LLM 输出带 markdown 围栏**。JSON 前后包了代码块标记，解析前必须剥离，别信模型"我保证输出纯 JSON"。
- **幂等**。早期重跑会产生两份日报、指标翻倍。改为以日期为主键 upsert 后才解决。
- **空数据要显式**。"没有事件"应输出"今日无异常"，而不是渲染一张缺字段的空壳，更不是流水线直接失败。
- **schema 漂移**。下游按字段消费，字段随手改一次就断一次。schema 跟代码一起版本化，变更走 review。

## 可复用建议

1. 先用纯规则模板跑通全链路，LLM 摘要作为增量加进去，别一开始就把叙述层当天花板。
2. 中间聚合产物务必缓存，排障时能快速定位问题出在采集、聚合还是总结哪一段。
3. 留三五天的"金标准"日报做回归集，改 prompt 或换模型后跑一遍对比。
4. 加心跳告警：流水线成功推日报才算完成，失败或超时主动通知，别依赖人肉发现。

## 总结

这条流水线的本质是：**确定性的部分交给代码，概率性的部分交给模型，两者之间用 schema 隔离**。日报只是产出物之一，同一套采集—聚合—校验骨架，换成周报、事故汇总、版本变更说明都能直接复用。建议从最小闭环开始：一个数据源、一个模板、一条定时任务，先让它每天准时出现，再逐步演进。
