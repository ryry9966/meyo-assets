## 背景

跑 Agent 做自动化的人大概都遇到过：同一套任务脚本，在家里的服务器上跑得好好的，换到笔记本上 Agent 开始反复尝试不存在的命令；或者它自作聪明调了 `python3.12`，而你机器上只有 3.10。根源不在模型，而在于 Agent 对"这台机器长什么样"没有可靠的认知来源，只能靠猜。

在 OpenClaw 的 Agent 体系里，模型能读到的上下文质量直接决定行为质量。与其在提示词里零散叮嘱"注意 macOS 和 Linux 路径不一样"，不如把本地工具和环境差异收敛到一个文件——这就是我在实践中的 tools.md。

## 问题

没有环境清单时，典型故障有三类：

1. **工具幻觉**。Agent 假设环境里有 docker/ffmpeg/jq，调用失败后连环试错，烧掉大量 token 和时间。
2. **配置漂移**。两台机器工具版本、路径不同，任务 A 机通过、B 机报错，排查全靠人肉 diff。
3. **上下文污染**。把 `.zshrc`、环境变量一股脑塞进提示词，混着密钥和无关内容，既危险又浪费上下文窗口。

## 做法

我的方案分四步：

**第一步，盘点真实依赖。** 翻最近一个月的 Agent 会话记录，统计它实际调用过的命令和 MCP 工具。没被用到的不要写，清单只为真实负载服务。

**第二步，定骨架。** tools.md 固定几个小节：`主机概况`（系统、架构、网络约束）、`已装工具`（名称、版本、绝对路径、调用注意事项）、`调用约定`（超时、沙箱、哪些命令需二次确认）、`已知坑`。每条工具记录不超过三行。

**第三步，区分静态与动态。** 提交进仓库的只有模板和约定；每台机器的真实状态由一个 probe 脚本生成，输出到 `tools.local.md`，进 `.gitignore`。脚本做的事很简单：遍历工具清单，`command -v` 加 `--version`，把结果填进固定格式。

**第四步，接入 Agent。** 系统提示里只写一句：执行工具调用前先读 tools.md 与 tools.local.md；发现文档与实际不符时，汇报差异而不是自行修改。变更走人工评审，防止 Agent 把错误自我固化。

## 踩坑点

- **写太长**。tools.md 本质是在吃上下文预算，我第一版写了 200 多行，压到 60 行以内后效果反而更好。它是指南针，不是百科全书。
- **手写动态部分**。凡是靠人手维护的版本号，三个月内必然过期。过期信息比没有信息更糟——Agent 会基于错误事实行动。
- **把密钥写进去**。tools.md 只允许出现环境变量的名字，不允许出现值，这条要在模板注释里写死。
- **语义不清**。要明确告诉 Agent：tools.md 是描述性的，没列出的工具不代表禁止使用，只是"未验证可用"。否则它会在该用的时候不敢用。
- **忽略平台差异**。macOS 和 Linux 的 sed、readlink 行为不同，这类差异值得单独列在"已知坑"里，比反复踩省事得多。

## 可复用建议

- 每条工具记录带上"上次验证时间"，超过阈值就标记为待确认。
- probe 脚本放进仓库，bootstrap 新机器时跑一遍，五分钟出一份可用的 tools.local.md。
- CI 环境单独一份清单，不要假设和本地一致。
- 会话中发现的新工具，由 Agent 提议、人确认后合并，保持清单收敛。

## 总结

tools.md 解决的不是技术难题，而是一个容易被忽视的工程问题：Agent 需要一份可信、精简、随环境更新的本地事实清单。把"环境认知"从提示词里的零散叮嘱，变成仓库里可评审、可生成、可版本化的资产，Agent 的行为稳定性和 token 效率都会明显改善。先从 20 行的模板开始，让 probe 脚本接管日常维护，比一次性设计完美方案更重要。
