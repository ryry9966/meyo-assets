## 背景

日常开发里，Git 操作占了大量碎片时间：写 commit message、切分支、清理废弃分支、提 PR 前做 rebase。这些事不难，但重复、琐碎、容易漏。OpenClaw 这类 agent 接上 MCP 的 Git 工具后，可以把这套流程交给助手托管——前提是你把安全边界设计好。

## 问题

我自己项目里最突出的三个痛点：

1. **commit message 质量不稳定**。回看历史经常是一串 `update`、`fix`、`改一下`，完全没法追溯。
2. **分支生命周期没人管**。`feature/x-y-z` 攒了十几个，不敢乱删，也不敢问哪个还能要。
3. **拆提交全凭心情**。改动横跨三个模块时懒得拆，最后单条提交巨大，revert 的时候后悔。

这三件事本质上都是"重复判断"，正适合交给 agent。

## 做法

我的配置分三层：

**第一层：工具接入。** 用 MCP Git server 暴露仓库操作，只开读操作（status / diff / log）加受控写操作（add / commit / branch），push 单独做成一个需要显式确认的工具。

**第二层：规则模板。** 在 agent 的系统提示里写死提交规范：Conventional Commits 前缀、单次提交只做一件事、message 必须基于 `git diff --staged` 的实际内容生成，不允许凭记忆写。

**第三层：流程编排。** 典型循环是：

- 先跑 `git status` + `git diff --stat`，了解改动范围
- 按模块拆分 staging，分别生成 message 并提交
- 每次提交后输出一行摘要给我确认，确认后才允许 push

分支管理上，让 agent 每周跑一次巡检：列出所有本地分支的最后提交时间和合入状态，超过两周未合入的列出来问我，我点头才删；已合入的直接清掉。

## 踩坑点

1. **diff 太大导致 message 失真。** 几百行的 diff 会写出空泛描述。后来加了"diff 超大必须先建议拆分"的规则，流程反而变细了。
2. **agent 自作主张 push。** 早期没隔离 push，有次它提交完直接推了远端。现在工具层就拦，确认动作不可跳过。
3. **删分支误伤。** 规则里限定只能用安全删除，强制删除一律人工执行，agent 只有建议权。
4. **rebase 中断残留。** 冲突处理中途出错会留下进行中的 rebase 状态。规则明确：失败即中止并原样报告，禁止自行恢复或强推。

## 可复用建议

- **权限分层**：读操作自动跑，写操作受限，破坏性操作（强推、硬重置、强制删分支）永远人工
- **规范显式化**：提交规范写成模板给 agent，别指望它从仓库历史里自己悟
- **留一层确认**：每个自动化动作先输出一行人类可读的摘要再执行
- **定时任务从低频起步**：分支巡检先周跑，稳定一两周再提频

## 总结

AI 助手管 Git 的价值不在"全自动"，而在把重复判断——怎么拆提交、message 怎么写、哪些分支该清——变成结构化流程，人只在关键节点点头。权限边界画清楚之后，这套流程出错率很低，省下来的心智负担是实打实的。建议从"自动生成 commit message"这一件事切入，跑顺了再扩展到分支和 PR 流程。
