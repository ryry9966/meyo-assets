## 背景

玩 OpenClaw 这类常驻 Agent 的朋友大多遇到过同一个尴尬：Agent 记得你上周让它部署的服务，却不记得你用 zsh 不用 bash、时区是 UTC+8、代码注释偏好中文。AGENTS.md / SOUL.md 解决的是「Agent 该怎么行为」，但「你是谁、你的环境长什么样」长期没有固定载体。我们的做法是在 Agent 工作区里维护一份 `USER.md`，作为会话启动时的用户上下文注入源。

## 问题

没有 USER.md 时，通常出现三种症状：

1. **重复自我介绍**：每个新会话都要交代一遍技术栈、目录习惯，说漏了 Agent 就按默认假设来。
2. **偏好漂移**：今天让你写 Python 用 venv，明天给你建议 pip 装全局包，因为它根本没有稳定依据。
3. **过度提问**：Agent 不确定你的环境，把可以查证的常识性问题反复抛回来，打断自动化流程。

## 做法

### 1. 建文件，放在固定位置

在工作区根目录建 `USER.md`，并在 `AGENTS.md` 里加一行声明：「会话开始时先读取 USER.md」。位置固定，Agent 和插件都能按约定找到。

### 2. 分层写内容

按「稳定 → 易变」分四段，控制总长度在 500 token 以内：

- **身份与环境**：语言偏好、时区、操作系统、常用 shell、编辑器。
- **技术偏好**：代码风格、包管理器、注释语言、命名习惯。
- **协作边界**：哪些操作需要确认（如删文件、git push），哪些可以直接做。
- **当前状态**：在做的项目、近期目标，这段最容易过期，单独放最后。

### 3. 让 Agent 参与维护

在 AGENTS.md 里补一条规则：「对话中确认到的新用户信息，主动提议写入 USER.md」。我的体感是，Agent 比我自己更勤快——它每次复述你的偏好时，就是最自然的落盘时机。

### 4. 用 git 管起来

USER.md 本质是配置文件，放进版本库。改坏了可以回滚，也能 `git diff` 看出这段时间 Agent 对你的「认知变化」。

## 踩坑点

- **写成简历**。初期我塞了两千字背景，结果注入后 Agent 回答变得啰嗦且讨好。压缩到关键事实后明显好转。
- **敏感信息入库**。API key、真实住址不要写。这份文件会被所有会话读到，也会进 git 历史。
- **偏好写死导致僵化**。「只用 pnpm」这类表述会让 Agent 拒绝配合偶发场景。改成「默认 pnpm，特殊项目跟随项目配置」。
- **和运行时记忆冲突**。如果同时用了长期记忆插件，同一事实两处记录会打架。约定：USER.md 只放「我确认过的稳定事实」，记忆里放过程性信息，冲突时以 USER.md 为准。
- **当前状态段不清理**。三个月前的项目目标还挂在里面，Agent 会引用过时上下文。建议每月 review 一次。

## 可复用建议

- 把 USER.md 当**产品文档**而非日记：短、准、可执行。
- 团队场景可以衍生 `TEAM.md`，放仓库级协作约定，和 USER.md 分开注入。
- 写一条自检 prompt：「列出 USER.md 中已过时的条目」，每月跑一次，让 Agent 自己做清理。
- 如果你的 MCP 插件能读文件，可以让工作流按 USER.md 里的环境字段做分支，比如 CI 脚本自动适配你的 shell。

## 总结

USER.md 不是什么高级功能，就是一份约定格式的文本文件，但它把「Agent 了解你」从玄学变成了可版本化、可 review 的工程资产。花半小时写初版，之后交给 Agent 协同维护，收益会随使用时间持续放大。建议从四段结构起步，宁短勿长，定期修剪。
