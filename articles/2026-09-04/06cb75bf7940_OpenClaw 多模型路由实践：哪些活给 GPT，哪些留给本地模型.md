## 背景

跑 Agent 做自动化，最常见的两种极端：一种是全用 GPT-4 级云端模型，一个长任务跑下来 token 账单很感人；另一种是全押本地模型，结果规划步骤频繁翻车，工具调用格式错误率居高不下。OpenClaw 的多模型路由就是为这个准备的：不同步骤发给不同模型。但这套机制用得好和用得差，效果差距很大，这篇把我们落地过程中验证过的做法和踩过的坑整理出来。

## 问题

实际项目里有三个具体矛盾：

1. **成本与质量**：Agent 大约 90% 的步骤是摘要、格式转换、简单工具调用，真正需要强推理的可能只有一两步，却按最贵的模型付费。
2. **隐私与合规**：日志、内部代码、客户数据一旦进入上下文，发给云端 API 就等于出去了。
3. **延迟**：本地小模型在短任务上明显更快，批量场景差距更大。

## 做法：按任务类型分流，而不是按心情分流

**第一步：把工作流拆成粗粒度的四类任务。**

- 规划与多步推理（拆解目标、决定调用哪个 MCP 工具）
- 结构化输出（函数调用、JSON、固定 schema）
- 文本加工（摘要、翻译、改写、模板填充）
- 敏感数据处理（含密钥、内部路径、客户信息的上下文）

**第二步：在路由配置里绑定模型**（示意结构）：

```yaml
routing:
  planning: cloud-large    # GPT-4 级
  tool_call: cloud-mid     # 结构化能力可靠的中档模型
  text_process: local-7b   # 本地 Qwen/Llama 级
  sensitive: local-only    # 强制本地，云端直接拒绝
```

再配 fallback 链：云端限流或超时 → 降级到本地并标记低置信；本地连续失败 N 次 → 升级云端重试。

**第三步：给每条路由加护栏。** 结构化输出这条必须挂 schema 校验加重试；sensitive 这条要在路由层做关键词/正则拦截，而不是指望模型自觉。

**第四步：观察一周再调。** 记录每类任务的路由命中数、token 消耗、失败率、平均耗时，让数据告诉你哪些规则是拍脑袋想出来的。

## 踩坑点

1. **本地模型的结构化输出不可信。** 7B~14B 模型的 JSON 格式错误率明显更高，挂上 schema 校验才发现重试率到 30%。工具调用这条路要么留在云端，要么用针对 function calling 微调过的本地模型。
2. **上下文长度没检查就路由。** 长对话历史塞给 8k 窗口的本地模型会静默截断，Agent 表现"变笨"但没人知道为什么。路由前先算 token。
3. **隐私路由只看当前输入没用。** Agent 上下文包含全部历史，只要有一条敏感信息在历史里，发云端就全带出去了。敏感判定必须针对整条上下文。
4. **降级链没有超时。** 云端挂了本该降级，结果 fallback 本身没设 timeout，整个 Agent 卡死在等响应。
5. **换了 chat 模型忘了 embedding 模型。** RAG 场景里检索和生成用了不一致的 embedding，召回质量下降，还以为是路由的锅。
6. **路由规则越写越细。** 从 4 类拆到 12 类，两周后自己都维护不动。粗粒度完全够用。

## 可复用建议

- **先全云端跑一周**，拿到每步成本/耗时/失败率的基线，再决定降级哪些步骤。没有基线的路由优化都是猜。
- **建 20~50 条真实任务样本的最小评测集**，每次调整路由后跑一遍。公开 benchmark 和你的任务分布没有关系。
- 模型能力用"能否稳定通过 schema 校验"这类可测指标衡量，不靠榜单印象。
- 敏感数据走**白名单机制**：默认可疑，显式标记可出网的才发云端。
- 路由决策要打日志，出问题能回放"当时为什么选了这个模型"。

## 总结

多模型路由的本质不是省钱，而是把模型能力对齐到任务需求：强推理给云端，格式化给可靠的中档模型，批量文本给本地，敏感数据不出门。落地顺序建议：先度量、再粗分、加护栏、留兜底、持续看数据调规则。社区里已经有人在 text_process 路由上把成本降到原来的三分之一，同时规划路由保持云端后任务成功率基本没掉，这大概就是这套机制该有的样子。欢迎在评论区贴你们的路由规则和数据。
