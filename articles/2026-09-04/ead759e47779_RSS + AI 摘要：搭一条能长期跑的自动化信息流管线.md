## 背景

RSS 看似过时，但对做 Agent 和自动化的开发者来说仍是最干净的信息源：无算法干预、结构化、可自托管。问题在于源一多——我这边 60 多个 feed，每天几百条 entry——人肉根本读不完。于是就有了这条管线：RSS 拉取 → 清洗去重 → 分级摘要 → 日报推送。

## 问题

直接把所有 entry 丢给 LLM 总结，会遇到三个现实问题：

1. **成本不可控**：长文全文 + 高频调用，token 消耗很快失控；
2. **摘要质量低**：逐条摘要信息密度差，且同一事件被多个源报道后会被反复总结；
3. **不可运维**：没有去重、缓存和重试，跑一周就废。

## 做法

管线分五段，由定时任务驱动，也可以封装成 MCP tool 让 Agent 按需调用：

1. **拉取与清洗**。用 Miniflux/FreshRSS 聚合订阅，脚本按 feed 增量拉 entry。很多博客的 feed 只带 summary，需要用 readability 类库抓正文兜底；顺手处理 CDATA、相对链接、pubDate 时区，这些脏活写好一次终身受益。
2. **去重与过滤**。先做标题 + 正文的 hash 粗去重，再对近 N 天 entry 做标题相似度（simhash 或 embedding 余弦）细去重。然后按每条 feed 的权重和关键词规则打分，只把 Top K 送进 LLM——这一步是成本的闸门。
3. **两级摘要**。第一级逐条产出一句话要点，强制 JSON schema 输出（title / one_liner / url / tags）；第二级把当天去重后的条目按主题分桶，做一次日报式汇总。map-reduce 结构比一篇大 prompt 稳定得多。
4. **汇总与推送**。日报模板固定：主题分组，每条附原文链接。推到 Telegram、飞书或邮件都行，保留原文链接是底线，避免"摘要即真相"。
5. **缓存与观测**。摘要结果按内容 hash 落库，重复 entry 不再调用模型；记录每次的 token 数、去重命中数，方便后续调阈值。

走 Agent/MCP 路线的话，可以把 `fetch_feeds / dedupe / summarize / push_digest` 暴露成四个 tool，让 Agent 决定何时调用、何时追问——但定时批处理仍是主干，Agent 只做编排和交互层。

## 踩坑点

- **全文抓取别省**：只摘要 RSS 里的 summary，产出常常是空话，readability 兜底值得写；
- **结构化输出必须上 schema**：不约束格式，跑三天 prompt 就会漂移，JSON schema + 失败重试一次到位；
- **去重阈值要按源调**：技术博客和新闻源的重合度完全不同，全局一个阈值会在某一类源上大量误杀；
- **别在单次 prompt 里塞太多条目**：超过 20 条后中间内容明显被忽略，先分桶再汇总比硬塞强；
- **注意调度重叠**：上次任务没跑完新任务又启动，会导致重复推送，加个简单的文件锁。

## 可复用建议

- feed 列表做成配置文件，每条带权重、关键词、语言字段，别硬编码；
- 摘要 prompt 里明确"只压缩原文出现的信息，不得推断"，并强制保留 URL；
- 成本敏感时第一级摘要用小模型，日报汇总再上大模型；
- 先跑一周人工审核模式（日报先发给自己），确认信噪比后再放开自动化。

## 总结

这套管线没有黑科技，核心就三个工程决策：**去重前置、摘要分级、链接回源**。落地后每天一份几分钟读完的日报，信息摄入的焦虑明显下降。整体代码量两百行上下，欢迎在评论区贴你们的阈值配置和踩坑补充。
