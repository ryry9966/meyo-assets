## 背景

Agent 接上 MCP 工具和插件之后，能力上限往往不再取决于模型，而取决于我们愿意给它开多大的口子。实践里最容易翻车的不是模型不够聪明，而是权限配置走极端：要么事事请示，人沦为点确认的机器；要么全程放权，一条跑偏的指令删掉数据、发错邮件、把测试配置推上生产。

## 问题

"该不该问人"这件事，目前大多靠 prompt 里的语气词解决，比如"谨慎操作""重要操作请确认"。这不可靠：模型对"重要"的判断和业务方经常不一致，而且写在 prompt 里的规则随时可能被注入绕过。权限边界本质是工程问题，应该落在代码和配置里，而不是指望模型的自觉。

## 做法

1. **盘点工具清单。** 把 agent 能触达的所有动作列出来：MCP 工具、插件、shell 命令，以及"间接可达"的——比如有只读数据库凭证，但某个插件能拼 SQL 执行，这也算写权限。
2. **按两个维度分类：** 可逆性（能不能撤销）和爆炸半径（影响谁、影响多大）。
3. **划四档：**
   - 自动执行：可逆且影响面小，如查询、读取、本地草稿；
   - 自动执行 + 护栏：可逆但影响共享状态，如写文件、提交分支。护栏指 dry-run、路径白名单、强制留 diff；
   - 必须确认：不可逆或对外可见，如删除、支付、给真实用户发消息、生产部署；
   - 禁止：如自改权限配置、绕过审计的操作。
4. **分档写进配置而非 prompt**，工具调用前由框架层拦截校验。
5. **让确认足够便宜：** 确认时展示将要执行的具体内容（命令、参数、影响对象），而不是一句"是否继续"；支持批量审批和超时策略，超时默认安全侧——不执行。
6. **全量审计日志：** 记录工具名、参数、结果、触发确认的原因，事后可回放。

## 踩坑点

- **确认疲劳。** 问得太频繁，人就会盲点"同意"，确认机制名存实亡。宁可收窄自动档，也别滥用请示。
- **模糊请示。** "我可以继续吗？"没有信息量。确认请求必须带完整上下文，否则人只能凭心情决策。
- **权限写在 prompt 里。** 改一个词就可能放权，注入风险还高。分档规则进配置、走版本管理、像代码一样 review。
- **链式越权。** A 工具只读，但它的输出被可写的 B 工具消费，等于变相拿到写权限。要按最终效果评级，不是按单个工具。
- **异步卡死。** agent 凌晨发起确认，人不在，任务挂一整天。必须有超时和降级路径。

## 可复用建议

- **默认拒绝，逐步放权。** 先全部要求确认，跑两周，把日志里反复出现且零事故的动作降级为自动档。
- **评级看四个问题：** 可逆吗？影响外部吗？出错波及多大？模型这次置信度如何？前三项是配置级的，只有最后一项交给模型。
- **权限清单进版本库**，变更走 review，和生产代码同等待遇。
- **每月回看一次自动档清单。** 权限收回来比放开难，所以要定期审视，而不是等出事。

## 总结

权限边界不是"信不信任模型"的问题，而是把业务风险翻译成可执行的拦截规则。该问人的时机就三条：不可逆、对外可见、或 agent 自己拿不准；其余时候，用护栏换效率。判断标准进配置、确认请求带上下文、全量留痕可回放——做到这三点，自动化才真正让人睡得着整觉。
