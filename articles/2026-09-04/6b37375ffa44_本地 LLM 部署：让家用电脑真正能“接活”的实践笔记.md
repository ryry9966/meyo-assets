## 背景

接入 OpenClaw 做自动化和 Agent 之后，token 消耗增长很快：循环推理、工具调用、长上下文，一轮任务下来 API 开销肉眼可见。加上一些场景（个人笔记、家庭照片、内部文档）本身不适合上云，本地跑模型就不再是极客玩具，而是刚需。

## 问题

本地部署的门槛不在“能不能跑起来”，而在“跑起来之后能不能干活”。常见的落差：

- 下载了 7B 模型，聊天没问题，接进 Agent 后工具调用格式经常崩；
- 显存/内存预估不足，加载即 OOM；
- 上下文一长，生成速度掉到不可用。

所以这篇的重点是：如何让本地模型达到**“能被 Agent 稳定调用”**的标准，而不是停留在能对话。

## 做法

1. **先盘点硬件**。显存是硬约束，经验公式：模型显存 ≈ 参数量 × 量化位数 ÷ 8 × 1.2。7B Q4 大约 5–6GB 显存（或等价统一内存），13B Q4 需要 10GB 以上。纯 CPU 也能跑，但吞吐低一个量级，适合离线批处理，不适合交互式 Agent。
2. **选运行时**。Ollama 是接入成本最低的方案：一条命令拉模型，自带 OpenAI 兼容接口；想精细控制的可以上 llama.cpp 或 LM Studio。
3. **选模型时把工具调用放第一优先级**。优先选经过 function calling 微调的版本（如 Qwen 系列），比“跑分更高但工具格式没对齐”的模型实用得多。中文场景尤其建议先验证 Qwen。
4. **接入 OpenClaw**：把 provider 指向 `http://localhost:11434/v1` 这类本地 endpoint，模型名填运行时里的 tag。先手动测一轮工具调用，确认 JSON 输出稳定，再挂进自动化流程。
5. **压测自己的任务**：用真实 prompt（系统提示词 + 工具 schema）跑 10 轮，看成功率，别只看通用榜单。

## 踩坑点

- **KV cache 吃显存**：上下文开到 32k 后，显存占用远超模型本身。交互场景建议 8k–16k 起步，够用再加。
- **工具调用格式不统一**：不同运行时对 function calling 的实现差异很大。遇到“模型不调工具”，先查运行时有没有正确透传 tools 参数，而不是急着换模型。
- **采样参数**：本地推理默认参数偏保守，Agent 循环里容易出现重复的工具调用，适当调高重复惩罚。
- **并发是串行的**：本地推理默认排队处理。多个自动化任务同时打过来会堵，要么限流，要么把轻任务路由到本地、重任务走 API。

## 可复用建议

- **分层路由**：格式转换、摘要、分类这类高频低难度任务走本地；复杂推理走远端。长期省下的成本很可观。
- **模型常驻**：Agent 场景避免频繁加载卸载，首次加载后保持驻留，响应延迟会稳定很多。
- **固化一份本地模型验收清单**：工具调用成功率、长上下文速度、显存峰值三项，每次换模型都跑一遍，五分钟就能避免后期返工。

## 总结

本地 LLM 的价值不在于替代云端，而在于给 Agent 体系加一层可控、廉价、可离线的底座。先想清楚让它干哪类活，再用工程化的验收标准去筛模型，比追新模型发布有效得多。欢迎在评论区贴你的硬件配置和实测吞吐，攒一份社区真实的对照表。
