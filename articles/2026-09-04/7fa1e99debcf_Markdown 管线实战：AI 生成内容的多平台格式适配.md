## 背景

社区里不少同学已经在用 Agent 批量产出技术内容：周报、踩坑笔记、教程初稿。AI 输出的默认格式基本都是 Markdown，但真正发布时问题才冒出来——公众号编辑器会剥掉 class 和大部分 HTML，知乎不认 GFM 脚注，静态站点全兼容却用相对路径引图。同一份稿子发三个平台，往往要手动改三遍。

## 问题

痛点集中在三处：

1. **方言差异**。各家的"Markdown"其实是不同子集，任务列表、脚注、公式、callout 的支持度参差不齐。
2. **AI 输出不可控**。模型时不时塞进内联 HTML 或裸 LaTeX，越界内容只能人工清理。
3. **图片链接**。本地路径发出去就是裂图，各平台图床上传方式还不一样。

## 做法

核心思路一句话：**把 Markdown 当 AST 处理，不要当字符串**。整条管线基于 unified/remark 生态，五步走完：

1. **约束生成端**：在 Agent 的 system prompt 里限定"纯 GFM 子集"——禁内联 HTML、禁脚注、代码块必须标语言、图片用 `![](img:xxx)` 占位。生成端越收敛，后端越省事。
2. **统一解析**：用 remark-parse 解析成 mdast，后续全在 AST 上操作，这是整条管线的地基。
3. **按平台写 transform 插件**：每个目标平台一个转换器，本质是 AST 到 AST 的映射。以公众号为例：标题和引用块转成带内联样式的段落（公众号只认 style 属性）、代码块用 shiki 高亮后输出行内样式、YAML frontmatter 直接剥掉。
4. **发布前 lint**：每个平台维护一份"方言清单"配置（声明支持哪些节点类型），产物过一遍扫描，遇到不支持节点直接报错，而不是渲染时静默丢失。
5. **包成 MCP 工具**：把 `publish(source, platform)` 暴露给 Agent，写完稿自己调，人只负责看最后的预览。

## 踩坑点

- **别用正则处理 Markdown**。我们最早用正则删 frontmatter、转表格，代码块一多就误伤——围栏代码块里完全可以长得像 Markdown，AST 解析能天然避开这类问题。
- **公众号样式必须内联到每个标签**，class 一律被剥。shiki 选行内样式输出，别选 CSS class 版本。
- **图片链路是异步的**：传图床、拿 CDN 地址、回填 AST、再渲染，这个顺序不能反。上传失败要有降级，宁可留占位符让人工补，也别发裂图出去。
- **中英文混排**：模型输出的空格和标点宽度不稳定，管线里加一步 pangu 规范化，比发布后手调省心得多。
- **黄金样本测试**：备三五篇覆盖表格、代码、公式的样稿，每次改 transform 跑 diff，防止"修好知乎、弄坏公众号"。

## 可复用建议

- 方言清单做成纯配置（JSON/YAML），新平台只需加一个 profile + 一个 transform，解析和 lint 层全部复用。
- 原始稿是唯一事实源，平台版本永远由管线生成，不要手改产物——改了下次重跑就丢。
- transform 写成纯函数：输入 mdast、输出 mdast，单测好写，组合自由。

## 总结

这套管线没有炫技成分，核心就是：**生成端约束、AST 层转换、发布端校验**。跑通之后，同一份 AI 稿发三四个平台的边际成本趋近于零，Agent 也从"写字的"变成"能直接交付的"。如果你还在手动复制粘贴调格式，建议从"放弃正则、改用 remark"这一步做起——投入很小，收益立现。
