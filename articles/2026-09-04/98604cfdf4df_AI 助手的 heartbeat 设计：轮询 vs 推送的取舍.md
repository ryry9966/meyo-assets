## 背景

OpenClaw 的 agent 默认是"被动"的：你不说话，它不动。heartbeat（心跳）是让它周期性醒来的机制——每隔一段时间跑一轮轻量检查，看看 HEARTBEAT.md 里有没有到期任务、有没有值得主动汇报的变化。另一条路是推送：外部系统主动打过来，比如 GitHub webhook、监控告警、cron 触发器。两条路都能让 agent"主动"起来，但成本模型和故障模式完全不同。

## 问题

实际部署里常见的三个纠结：

1. **心跳设多密？** 默认 30 分钟一轮是保守值，调到 5 分钟，token 消耗直接翻数倍——每轮心跳都是一次真实的模型调用。
2. **只靠推送行不行？** webhook 会超时、重试、丢事件，而且要求你的网关能被外网访问，NAT 后的家庭环境很麻烦。
3. **推送风暴：** 一次 push 带 50 个 commit，如果逐事件触发 agent 会话，成本立刻失控。

## 做法

我稳定下来的方案是"**推送进队列，心跳做合并**"，四步：

1. **事件源分类**。能主动调你的（GitHub、监控、邮件）走推送；只能靠"看一眼"才知道的（本地文件变化、deadline 扫描、日报汇总）走心跳。
2. **推送侧做薄网关**。webhook 只做三件事：验签、按幂等键去重、写入本地队列文件或 SQLite。绝不直接触发 agent 会话。
3. **心跳侧做消费**。心跳醒来时先读队列，再读 HEARTBEAT.md，把积压事件合并成一次处理。没有值得汇报的就静默返回。
4. **分级间隔**。默认 30 分钟；deadline 类任务密集的时间段临时调密（比如交付前一天改 10 分钟）；深夜拉长到 2 小时。

一句话分工：推送负责"不丢"，心跳负责"不吵、不贵"。

## 踩坑点

- **心跳带全量上下文**：最初我把主会话的 system prompt 原样给心跳用，一轮 8k token，一晚上烧掉一周额度。心跳 prompt 必须单独裁剪，只留 HEARTBEAT.md 内容和必要工具声明。
- **"没事找事"**：早期逻辑写成"总要产出点什么"，结果每半小时收到一条废话播报，一周后我把通知全关了。规则改成：无事 → 静默。
- **裸奔的 webhook**：验签没做之前，乱扫段的请求也能触发 agent 跑起来。推送入口必须有鉴权 + 速率限制。
- **只信推送**：见过 webhook 服务端静默失败、本地重启后队列文件还在但没人消费的情况。哪怕全走推送，也保留一个低频兜底轮询做对账。
- **并发写冲突**：心跳和主会话同时改同一工作区文件，出现过互相覆盖。约定队列文件只允许心跳侧写，或加简单文件锁。

## 可复用建议

- 选型判断：**要实时、有生产方、需逐事件处理 → 推送；要发现状态、可合并、无入站连通性 → 轮询**。多数个人助理场景是两者的混合。
- 心跳是"合并器"不是"触发器"：让它消费事件，而不是让事件直接唤醒模型。
- 幂等键 + 本地队列是所有推送方案的保底配置，成本几乎为零。
- 心跳间隔不是常量，是随任务日历变化的参数。
- 给心跳留"沉默权"：一次心跳的最好结局，是什么都不发生。

## 总结

轮询和推送不是二选一，而是分工：推送解决事件到达，心跳解决事件消化。对跑在自己机器上的 OpenClaw agent 来说，"薄网关收推送 + 低频心跳做合并 + 无事静默"这套组合，是我踩完 token 账单和通知疲劳两个坑之后稳定下来的形态。它不酷，但账单和睡眠质量都会感谢你。
