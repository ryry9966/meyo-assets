## 背景

OpenClaw 的 Agent 本质上是无状态的：每次调用模型，上下文从零开始。MCP 和插件解决了"能力"问题，能读文件、能调 API，但"记性"问题一直悬着。用户上周说过"回复用中文、代码注释要英文"，这周新会话里 Agent 又变回默认风格，体验割裂。这不是模型问题，是架构问题：缺一层持久化的记忆设计。

## 问题拆解

先摆三个常见误区：

1. **把对话历史当记忆**。全量历史塞回上下文，token 涨得快，关键偏好被淹没在闲聊里。
2. **只做向量检索**。所有聊天记录 embed 进向量库，召回相关性不稳定。偏好这类"事实型知识"用相似度召回经常漏。
3. **写入无门槛**。什么都说"我记住了"，两周后记忆库全是噪声和过期信息。

## 做法：三层记忆 + 受控写入

**结构分三层：**

- **会话内记忆**：当前上下文，不持久化。
- **偏好库（核心）**：结构化存储，SQLite 一张表就够，字段大致是 `user_id / key / value / confidence / updated_at / source`。例如 `key=代码注释语言, value=英文, confidence=0.9`。事实型记忆走精确匹配 + 模糊匹配，不依赖向量。
- **事件记忆**：项目背景、历史决策这类长文本，embed 后存向量库，走 RAG 召回。

**写入侧三条规则：**

1. **显式优先**：用户说"记住：xxx"直接写入，confidence 拉满。
2. **隐式提取要过审**：Agent 推断出的偏好先写入 `confidence=0.5` 的候选区，下次命中同样行为再升级，或由用户确认。
3. **冲突覆盖**：同 key 新值覆盖旧值，但保留历史版本，出问题可回滚。

**读取侧**在 prompt 组装阶段做：偏好库按 key 精确注入；事件记忆按当前任务相似度召回 top-k，k 别超过 3。两路结果拼接后进 system prompt。

## 踩坑点

- **记忆污染最难缠**。一次误判（用户随口抱怨）被写进偏好库，之后每次对话都被注入，很难自愈。隐式写入必须低置信起步，且注入时标注来源，让用户可见。
- **过期偏好**。"用 Python" 是半年前的事，现在换 Go 了。加衰减逻辑：超过 90 天未验证的条目降权，必要时 Agent 主动反问确认。
- **检索过载**。top-k 调到 8 那两天，prompt 长了一倍，回答反而变差。宁可少召回。
- **MCP 工具化要干净**。把 memory_read / memory_write 包成 MCP tool 时，write 必须带 source 字段，否则排查污染源头时抓瞎。

## 可复用建议

- 偏好走结构化、事实走向量，别混一个池子。
- 写入比读取重要：宁缺毋滥，候选区 + 置信度升级是性价比最高的设计。
- 让用户能看、能删：一条 `memory_list` 命令成本很低，信任收益很高。
- 每条记忆带时间戳和来源，排障时这是唯一线索。

## 总结

Agent 记忆的本质不是"存得多"，而是"存得准、取得少、能纠错"。结构化偏好库 + 受控写入 + 低召回，三个约束加起来代码不到三百行，体验差异却非常明显。建议从偏好库起步，事件记忆等真有需求再加。
