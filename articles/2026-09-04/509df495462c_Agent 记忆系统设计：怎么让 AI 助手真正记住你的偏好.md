## 背景

用 OpenClaw 这类 Agent 框架跑日常任务，最明显的体感割裂是：会话能力越来越强，但每次开新会话都像换了个实习生。你上周说过"commit message 用中文、别加 emoji"，这周它照样给你写 `feat: add xxx ✨`。上下文窗口不等于记忆，模型不会自己跨会话记住任何东西——这件事必须由工程侧解决。

## 问题：三种常见做法为什么不行

1. **全塞 system prompt**：偏好一多，提示词膨胀到几千 token，行为互相冲突，成本也失控。
2. **只上 RAG**：检索对显式偏好召回还行，但对"用户纠正过我两次"这种隐性信号几乎无能为力。
3. **指望模型自己记**：没有持久化存储，一切都是幻觉。

核心矛盾就一句：写多了是垃圾，写少了没用，检索不到等于没写。

## 做法：分层存储 + 保守写入 + MCP 化

我的方案四步，单文件起步即可：

**1. 分类型存储**。SQLite 一张表够用（key / value / type / confidence / source / updated_at），先分两类：

- profile：稳定偏好（语言、代码风格、时区），量少，永远注入；
- episodic：事件性事实（项目背景、上次部署到哪），按需检索。

**2. 写入路径分显式和隐式**。显式是用户说"记住……"，直接写；隐式是检测纠正信号——同一类纠正出现两次以上才升级为候选记忆，由模型按严格 JSON schema 输出，confidence 起步给低分。

**3. 注入策略**。profile 全量注入（控制在 500 token 内），episodic 用关键词 + embedding 混合检索，每次最多取 5 条。宁可漏，不可灌。

**4. 用 MCP 把记忆做成工具**。写一个薄薄的 MCP server，暴露 `memory_write` / `memory_search` / `memory_list` 三个 tool。这样任何 Agent、任何模型都能挂载，记忆独立于具体助手存在。

## 踩坑点

- **隐式抽取太激进**是最大垃圾来源。模型会把"用户随口提过一嘴"写成强偏好，必须设次数阈值，且低置信度不允许覆盖旧值。
- **冲突不处理**：旧的"喜欢简洁回复"和新的并存时，行为会抽风。按 key 覆盖 + 记录 updated_at，历史保留但不再注入。
- **重复写入**：同一偏好的五种变体占满存储，写入前按 key + 语义相似度去重。
- **忘了给用户控制权**：必须有列表和删除入口，否则用户不敢让它记。另外密码、token 这类内容要硬编码排除，永远不落盘。

## 可复用建议

- 别一上来就上向量库，一个 JSON 文件能跑通闭环后再升级；
- 每次写入记录 source（来自哪一轮对话），排查"它为什么这么干"全靠这个；
- 写入宁缺毋滥，删除零成本——这是记忆系统不烂掉的唯一秘诀；
- 花一周人工统计"偏好命中率"，比任何自动评估都直观。

## 总结

记忆不是模型能力问题，是工程问题。分层存储、保守写入、可控生命周期、MCP 化暴露，四件事做到位，助手才会从"每次重来的工具"变成"越用越顺的同事"。先跑通最小闭环，再谈智能化。
