## 背景

LLM 本身无状态。上下文窗口再大，跨会话的一切都会归零。对 OpenClaw 这类常驻自动化 Agent 来说，记住用户偏好（代码风格、回复语言、常用项目路径、部署习惯）直接决定体验。但很多实现止步于"把历史对话塞进 system prompt"，很快就会撞墙。

## 问题

实践中最常见的三类失败：

1. **记忆膨胀**：什么都存，system prompt 越来越长，成本上升，指令之间开始互相打架；
2. **记忆冲突**：用户三个月前说"用 TypeScript"，上周改口"改用 Go"，append-only 的存储让旧偏好继续生效；
3. **黑箱失忆/乱记**：用户不知道 Agent 记了什么、为什么行为突然变了，信任直接崩塌。

## 做法

按"写、读、管"三条路径设计，原则是先结构化，后向量检索。

**1. 定 schema。** 每条记忆至少包含：key（如 `code_language`）、value、scope（user/project/session）、confidence、source（显式指令/会话抽取/纠错信号）、updated_at。禁止存自由文本长段。

**2. 设计写入触发器，三种来源分开处理：**
- 显式指令（"以后都用 pnpm"）→ 高置信度直接 upsert；
- 会话后抽取 → 会话结束时用一次独立的 LLM 调用按 schema 抽取，只保留稳定、可复用的事实，宁缺毋滥；
- 纠错信号 → 用户否定了 Agent 的行为时，更新或降低对应记忆的置信度。

**3. 冲突与生命周期。** upsert 按 scope+key 覆盖，不做 append-only；低置信度记忆加 TTL 和时间衰减；定期跑去重合并任务。

**4. 读取策略。** Prompt 组装时按 scope 过滤 + 相关性排序 + 硬性 token 上限（比如 500 tokens）。偏好类记忆优先精确匹配 scope，向量相似度只作补充，不要当主力。

**5. 可观测。** 用 MCP 暴露 `memory_list` / `memory_update` / `memory_forget` 工具，让用户能看、能改、能删。这一步不是锦上添花，是信任基础。

**6. 评估。** 准备 20~50 条"黄金问题"（例如"我的默认分支命名规范是什么"），每次改动跑一遍召回率和误注入率。

## 踩坑点

- **抽取太积极**：会话里的临时上下文（"今天先不部署"）被当成永久偏好存下来。给抽取 prompt 加一道"是否长期有效"的判断。
- **把记忆当可信输入**：记忆内容源自对话，可能被注入恶意指令。读回 prompt 时要和系统指令隔离，并标注来源。
- **上来就上向量库**：90% 的偏好场景就是结构化 key-value，一张表就够，向量检索是后期优化。
- **忘了"遗忘"**：没有删除和过期机制的记忆系统，三个月后就是负资产。

## 可复用建议

- 先做结构化偏好表，再考虑会话摘要和向量检索；
- 写入要保守，读取要有预算，展示要透明；
- 把"用户可编辑的记忆列表"当作产品功能交付，而不是 debug 接口。

## 总结

Agent 记忆系统的本质是三条路径：**写**（低频、保守、结构化）、**读**（有 scope、有预算）、**管**（可查看、可删除、可过期）。先用一张表加三个触发器跑起来，再按评估结果逐步加复杂度。记住的目的永远是让行为更准，而不是存得多。
