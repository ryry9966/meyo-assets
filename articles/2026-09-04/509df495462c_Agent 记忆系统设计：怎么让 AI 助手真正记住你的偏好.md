## 背景

Agent 默认无状态：每个新会话，模型对“你是谁、你偏好什么”一无所知。跑了一段时间 OpenClaw 之后，最明显的痛点往往不是模型不够聪明，而是它每天都在重复问同样的问题——部署目录、代码风格、通知渠道，每次都要重说一遍。记忆系统的目标很朴素：把说过一次的偏好，变成之后所有会话的默认上下文。

## 问题

第一版实现通常是“把想记的都写进一个文件，会话开始时塞进 system prompt”，很快会遇到四类问题：

1. **记太多**：token 成本上升，关键信息被稀释；
2. **记错**：一次性指令（“这次用 pnpm 装”）被升级成永久偏好；
3. **记旧**：偏好变了，旧条目还在且优先级不明；
4. **检索不到**：文件越长，agent 越读不到相关段落。

所以真正要设计的是三条路径：怎么写、怎么读、怎么更新。

## 做法

### 1. 分层存储

- 会话层：当次上下文，不落盘；
- 工作层：结构化偏好记录，字段至少含 `type`（偏好/事实/约定）、`scope`（全局/项目）、`updated_at`、`confidence`；
- 长期层：embedding 检索的笔记库，沉淀对话中的经验。

### 2. 写入过闸门

别让 agent 在对话中随手写记忆。在会话结束或定时任务里跑一个专门的抽取步骤：候选事实先分类（永久偏好 / 项目约定 / 一次性指令），只有前两类且置信度够高才落盘。用户纠正 agent（“我说过别用 any”）是最高优先级的写入信号，应立即更新对应条目，而不是追加一条新的。

### 3. 读取有排序

会话启动时只注入全局偏好中按最近使用排序的前几条；其余做成 recall 工具（用 MCP 暴露 `memory_search` 即可），让 agent 在不确定时主动调用，而不是每次全量注入。检索用 embedding + 关键词混合——偏好类短文本纯向量召回的误命中不低。

### 4. 更新有生命周期

新旧记忆冲突时按“时间新 + 出现频次高”仲裁，旧条目标记 superseded 而非直接删除；每月跑一次清理：去重、降级长期未命中的条目。记忆是数据，要有 schema，也要有垃圾回收。

## 踩坑点

- **只加不减**：记忆文件三个月涨到几千行，注入即爆 token；
- **scope 混用**：项目 A 的“不写测试”被带进项目 B；
- **缺时间戳**：冲突时无法仲裁新旧；
- **自由文本存储**：回头连自己都看不懂当初为什么记这条；
- **敏感信息入库**：密钥、家庭地址一旦进记忆，会被注入所有会话，写入闸门里要做黑名单和脱敏。

## 可复用建议

1. 宁可少记，不可记错：写入门槛调高，靠用户纠正来补；
2. 结构化字段 + 混合检索，比一个大 md 文件可靠得多；
3. 给用户一个查看和编辑记忆的入口，记忆必须可见、可改；
4. 维护 10~20 条偏好问答的小评测集，每次改检索策略后跑一遍，拒绝“感觉变好了”。

## 总结

记忆系统不是“多加一个向量库”，而是一套带写入闸门、检索排序、冲突仲裁和清理机制的数据管道。先做小：一个结构化的偏好文件 + 一个 recall 工具 + 纠正即更新，已经能覆盖大部分“它怎么又忘了”的场景；剩下的复杂度，等真实痛点出现再补。
