## 背景：大多数 Agent 是台“应答机”

我们的使用惯性是：不发消息，Agent 就不动。OpenClaw 的 agent 默认也是如此——gateway 常驻，但只有收到你的输入才跑一轮模型。问答场景这样够了，但“助理”这个词意味着主动性：磁盘快满了、关注的仓库来了新 PR、早上该给你一份摘要。这些事没人问，就永远不会发生。另一条路是自己在 crontab 里定时调 API，但那样任务逻辑和 agent 的会话上下文是割裂的。

OpenClaw 给了一个很轻的答案：HEARTBEAT.md。

## 原理：按节拍被注入的待办文件

heartbeat 机制一句话说清：agent 默认每 30 分钟被唤醒一次，读取 workspace 里的 HEARTBEAT.md，把里面的条目当作指令执行；文件不存在时，唤醒退化为一次轻量检查（提示词要求它没事就回一个跳过标记），但依然是一次模型调用。关键在于心跳跑在主会话里——它能带着你之前聊过的上下文去判断“要不要说、说什么”，这是裸 crontab 给不了的。

## 做法与步骤

1. 找到 agent 的 workspace 目录（`agents.defaults.workspace`，默认在用户目录下，以你的配置为准）。
2. 新建 `HEARTBEAT.md`，先只写“两条规则 + 两个检查项”，别贪多。
3. 确认间隔。默认 30m，可在配置里调：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": { "every": "30m" }
    }
  }
}
```

4. 看两三轮 gateway 日志确认每轮有 heartbeat run，然后根据噪音情况迭代规则。

我的模板，固定三段：

```markdown
## 规则
- 没事不发消息；同一件事只在状态变化时报一次
- 23:00–08:00 保持沉默，紧急告警除外

## 常驻
- df -h 查根分区，使用率 > 85% 时提醒我
- cd ~/proj && git fetch，有新提交就列一行 log

## 一次性
- [ ] 周报截止前两天提醒我收集素材（做完删掉本行）
```

## 踩坑点

1. **通知疲劳**。最先出现的问题一定是它每半小时汇报“一切正常”。必须在文件里写死“无变化不输出”，这条是 heartbeat 体验好坏的分水岭。
2. **文件膨胀**。HEARTBEAT.md 每轮都注入，写长了就是常驻 token 成本。经验值：控制在 20 行以内，复杂逻辑挪进脚本，心跳只负责触发和汇报。
3. **心跳不是精确调度器**。间隔有漂移，gateway 重启会重新计时。“每天 9:00 整发日报”这种需求请交给 cron 触发，别指望心跳。
4. **重活堵门**。心跳串行执行，一轮里跑大扫描会拖垮后续节拍。重任务写成脚本落盘，agent 只读结果。
5. **上下文共享是双刃剑**。心跳能利用主会话上下文，但也会让上下文和账单一起涨。定期 `/new` 重置会话，或把判断所需的关键背景直接写进文件本身。

## 可复用建议

- 所有检查项写成“条件 + 动作”格式（“如果 X 超过 Y，则做 Z”），不要写成散文，模型执行稳定性明显更高。
- 让心跳调 MCP 工具：GitHub MCP 查 issue、filesystem MCP 扫目录，由 agent 自己决定何时调用，这是 heartbeat 最有意思的玩法。
- 一次性任务用 checkbox，并明确指示 agent“处理完删除该行”，避免过期任务永久循环。
- 心跳只做“发现与转述”，执行类动作落到脚本或子任务，保持每轮轻量。

## 总结

HEARTBEAT.md 的本质，是把“你想到要问”变成“它到点去看”。代价是一轮轮真实的模型调用，收益是那些没人问就没人管的事终于有人管了。建议从一个 30 分钟间隔、两三个检查项的最小版本跑一周，再决定加减什么。主动性的价值不在多，而在准。
