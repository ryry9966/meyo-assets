## 背景

跑了一段时间 OpenClaw 之后，多数人会撞到同一个账单问题：agent 循环里上下文反复重放，一次看起来简单的任务，背后可能是几十次模型调用。全走 GPT 这类云端模型，费用和延迟都难受；但全换成本地模型，工具调用经常崩，复杂任务质量明显下滑。多模型路由就是为了在两者之间找平衡——OpenClaw 的 provider 抽象允许在配置里声明多个模型来源、设置主备（primary + fallbacks），也支持按 agent 覆盖模型，这给了我们做分层路由的空间。

## 问题

我最初的配置是“一把梭”：主 agent 和所有工具调用全走云端。一个月下来，token 账单的大头其实是摘要、日志整理、消息分类这类“管道活”。反过来试过全本地，结果小参数模型在多步工具调用上稳定性不够，agent 偶发死循环，排障花的时间比省下的 API 费还贵。

## 做法

**1. 先分层，再谈路由。** 把 agent 干的活分成三类：需要规划和多步推理的“决策活”、纯文本变换的“管道活”（摘要/分类/格式化）、涉及隐私数据的“敏感活”。

**2. 主备配置打底。** 在 `openclaw.json` 里给 agent 配 primary + fallback（具体字段以你版本文档为准）：

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4.1",
        "fallbacks": ["ollama/qwen3:14b"]
      }
    }
  }
}
```

这一层解决的是可用性：云端故障时降级到本地兜底，不是为了省钱。

**3. 把管道活拆出去。** 摘要、分类这类步骤拆成独立子 agent，单独指定本地模型（Ollama 起的 Qwen，确认开启工具调用支持）。主 agent 拿到的是压缩后的结果，主模型的上下文消耗也跟着降。

**4. 敏感活写死走本地。** 涉及私人文档、聊天记录预处理的环节，直接在路由规则里固定本地模型，不做动态判断。

**5. 加观测。** 每步记录模型名、token 数、耗时，跑一周再决定路由表要不要调。

## 踩坑点

- **本地模型必须原生支持 function calling。** 不支持的话，agent 会“幻觉出”工具调用或直接卡死。选 Qwen3、Llama 3.1+ 这类明确支持工具调用的模型，别拿纯 chat 模型硬上。
- **上下文长度陷阱：** 本地模型常见 8k–32k，agent 轨迹很容易超限。超了之后要么报错、要么静默截断，症状是“忘了前面的工具结果”。工具输出先在管道层压缩再回填。
- **别用 LLM 当路由器。** 让小模型判断“这条消息该走谁”，等于在链路里新增一个故障点和延迟源。按工具名/任务类型写死规则，确定性远比“智能路由”靠谱。
- **fallback 要设重试上限。** 否则云端抖动时会反复重试，本地兜底又慢又差，用户体感极差。
- **embedding 别混用。** 本地换了 embedding 模型，旧索引等于作废，检索质量会莫名其妙下降。

## 可复用建议

- 一句话原则：**决策花大钱，管道不花钱。** planner 和工具编排用云端强模型，摘要、分类、格式化下沉到本地。
- 灰度迁移：先 100% 云端跑出质量基线，再把出现频率最高的三个“管道活”挪到本地，用观测数据对比回归，达标才继续迁。
- 路由表当配置管理，进版本库，别散落在代码里。

## 总结

多模型路由的本质不是“能省则省”，而是承认不同环节对模型能力的需求密度不同。OpenClaw 的多 provider 配置让这件事不用改代码，真正的难点在于任务分类和持续观测。先把账单和调用日志按任务类型拆开看，你大概率马上就能找到第一个值得迁去本地的任务。
