## 背景

OpenClaw 的能力边界，基本由它能调用的工具决定。模型本身不会"查库存""发工单"，这些动作都要落到外部 API 上。社区里反复出现的问题不是"接不上"，而是"接上了但 Agent 用不好"——参数猜错、报错看不懂、长调用卡死会话。这篇文章基于我们对接几个内部服务的实际经验，梳理一条可复用的路径。

## 问题出在哪

先说一个常见误区：对接不是把 API 文档塞给模型。模型上下文有限，也不会真的去"读"文档。真正决定调用质量的是三样东西：

1. 工具 schema 的描述质量；
2. 错误信息是否结构化、可被 Agent 理解；
3. 鉴权与超时是否在框架层处理好。

这三点任何一处薄弱，表现都是"时好时坏"，排查成本远高于接入成本。

## 做法：三层结构

我们的做法是把对接拆成三层：MCP server 做标准协议层，adapter 做业务转换，外部 API 本身保持不动。

**第一步：起一个 MCP server。** OpenClaw 原生支持 MCP，外部服务无需改造，包一层即可。一个进程承载一组相关工具，避免工具散落多处难维护。

**第二步：收敛工具粒度。** 不要把 REST 的每个 endpoint 都暴露成工具，而是按"业务动作"封装：`create_order`、`query_status`、`cancel_order`。工具数量控制在十几个以内，每个工具的 description 用一句话讲清"什么时候该用我、什么时候不该用"。这一步对调用准确率的影响，比换模型还大。

**第三步：参数与错误结构化。** inputSchema 写紧：枚举就写枚举，必填就标 required。错误统一返回 `{code, message, hint}` 结构，hint 是写给 Agent 看的，比如"订单号应为 ORD 开头的 12 位字符串，请向用户确认后重试"。Agent 拿到这类错误，大多能自我修正，而不是反复重试。

**第四步：鉴权下沉到配置层。** API key 通过环境变量或密钥配置注入，MCP server 启动时读取。不要把 key 写进工具描述，也不要让任何工具的参数里出现凭证字段。

**第五步：灰度验证。** 先在本地会话里逐个调用工具，观察参数回填是否符合预期，确认无误后再放进定时任务或自动化流程。

## 踩坑点

- **工具描述写得太"全"**：description 塞了半篇文档，模型反而抓不住重点。一句话 + 参数说明足够。
- **长耗时调用阻塞会话**：一个报表接口要跑 40 秒，会话直接卡住。改成"提交任务 + 查询状态"两个工具，异步轮询。
- **错误直接透传 HTTP 状态码**：Agent 看到一个"500"就开始瞎猜。必须翻译成结构化信息。
- **写操作没做幂等**：定时任务重试导致重复创建工单。所有写操作工具务必带幂等键。
- **schema 太宽松**：类型全 string、无 required，模型自由发挥。宁可让 Agent 拿到报错后重试，也不要让脏参数进系统。

## 可复用建议

- 把 MCP server 模板化：统一的错误结构、日志、超时处理，新服务接入时只写 adapter。
- 每个工具配套一条冒烟用例存进仓库，升级依赖后跑一遍。
- 为工具调用留日志（时间、参数摘要、结果码），排查"Agent 为什么这么做"时，这是唯一依据。
- 工具命名用动宾结构，多个工具之间避免语义重叠——重叠会导致模型随机选择。

## 总结

OpenClaw 对接外部服务，工程量不大，但质量取决于细节：schema 收紧、错误可读、鉴权下沉、写操作幂等。把这四件事做成团队默认规范，Agent 调用外部 API 的稳定性就会从"看运气"变成"可预期"。欢迎在社区帖子里补充你们遇到的具体 case。
