# OpenClaw 的多模型路由：什么时候用 GPT 什么时候用本地模型

## 背景

在实际 Agent 与自动化工作流里，大模型的选择常陷入两难：全用 GPT-4 成本太高且延迟不可控，全用本地部署的 Llama/Qwen 又容易在复杂推理或工具调用上掉链子。OpenClaw 作为面向 Agent 与 MCP（Model Context Protocol）的插件化框架，内置了多模型路由能力，允许开发者根据任务特性将请求分流到不同的后端。本文记录我在实际项目中沉淀的路由策略、配置方法以及踩过的坑，供社区参考。

## 问题：如何划定 GPT 与本地模型的“分工边界”

多模型路由的核心不是简单地在代码里 if-else，而是要让决策可量化、可扩展。我们需要回答三个问题：

- 哪些任务必须走 GPT（或同等能力的闭源模型）？
- 哪些任务本地模型能稳定承接？
- 边界任务如何兜底？

一个典型错误是把路由交给一个模糊的“复杂度”指标，以为加了提示词就能让分类器自行判断，结果分类器本身消耗的 token 和延迟比任务还大。

## 做法与步骤

### 1. 建立任务-模型矩阵

先抽取出工单中的典型意图，用少量样本统计每个意图的核心特征：

| 意图类别         | 是否需要多步工具调用 | 输入平均长度 | 对格式严苛度 | 推荐模型     | 理由                                   |
|------------------|----------------------|--------------|--------------|--------------|----------------------------------------|
| 长篇文本摘要     | 否                   | 高           | 低           | GPT-4        | 本地 7B 模型长文本摘要易丢关键信息     |
| SQL/代码生成     | 是（需要查 schema）  | 中           | 高           | GPT-4        | 需要精确语法，本地模型幻觉率高         |
| 客服对话分类     | 否                   | 低           | 低           | 本地 7B      | 意图清晰，速度快，可离线处理           |
| 隐私文档脱敏     | 否                   | 高           | 高           | 本地模型     | 绝不允许数据出域                       |
| 工具参数填充     | 是                   | 低           | 高           | GPT-4        | 需要理解工具描述与 JSON 模式           |
| 简单 FAQ         | 否                   | 低           | 低           | 本地模型     | 确定性回复，可缓存                     |

这步不依赖模型，靠人工标注或历史日志统计。

### 2. 在 OpenClaw 的 Router 配置中声明规则

OpenClaw 的 Agent 定义支持 `routing` 块，可以基于任务元信息分流。示例配置：

```yaml
agent:
  name: doc-assistant
  routing:
    - name: privacy
      when: task.meta.privacy == true
      model: local-mistral
    - name: tools
      when: task.meta.requires_tool == true
      model: gpt-4
    - name: simple_qa
      when: task.intent in ["faq", "greeting"] and task.estimated_tokens < 200
      model: local-llama3
    - name: fallback
      model: gpt-4
```

这里没有让模型来判断复杂度，而是依赖上游的轻量意图识别（可以用 1B 级别分类模型或规则）提前为任务打上 `intent` 和 `meta` 标签。

### 3. 实现分类器前处理

使用一个极轻量的分类器（如 fastText 或 quantized tinyBERT）作为入口，不会引入明显延迟。分类器只需输出意图和是否含敏感信息、是否需要工具。这一步骤在 OpenClaw 的插件链中可以挂载为 `preprocessor`：

```python
# Example preprocessor plugin
def classify_task(prompt: str) -> dict:
    intent = intent_model.predict(prompt)
    privacy = privacy_detector.match(prompt)
    return {"intent": intent, "meta": {"privacy": privacy, "requires_tool": False}}
```

后续 Router 直接消费这些标签，决策路径完全透明。

### 4. 添加 Fallback 与缓存

即使本地模型被选中，也需要在 prompt 中增加防御性指令，如“如果问题涉及代码运行，请返回 `FALLBACK_TOOL`”。当本地模型输出特定标记时，OpenClaw 的 Fallback 机制会自动切换至 GPT-4 重试。同时，对所有本地模型的标准回复，通过相似度缓存减少计算。

## 踩坑点

- **本地模型格式不稳定**：即使使用 grammar constrained decoding（如 llama.cpp 的 GBNF），处理复杂 JSON 输出时仍可能遗漏字段。补救办法是本地模型只返回自然语言，由后端 Parser 提取结构化信息，避免让本地模型直接生成 API 调用参数。
- **延迟叠加**：分类器 + 本地模型 + 可能的 GPT 重试会导致首字延迟达到 3-5 秒。务必将分类器设计为同步且极轻，否则整体体验劣化。
- **路由规则膨胀**：当意图超过 15 类后，静态规则开始泛滥。建议引入决策树或简单评分函数，并定期用 A/B 测试验证每个路由的准确率与成本。
- **本地模型资源占用**：同时加载两个不同尺寸的本地模型（如一个分类小模型、一个生成大模型）在低配 GPU 上容易 OOM。推荐统一使用 7B 级别的模型，通过 LoRA 适配不同任务，或者采用 serverless 离线推理队列。

## 可复用建议

1. **路由规则库**：将经过验证的路由规则沉淀成社区模板，供不同场景快速复用。例如“客服分流模板”“代码助手模板”。
2. **成本感知埋点**：在 OpenClaw 的 Telemetry 中记录每次模型选择的成本与被拒绝次数，形成报表，便于优化阈值。
3. **隐私第一**：任何涉及 PII、内部文档的任务，硬编码走本地模型，不在 Router 中开放给条件判断，避免误配置。
4. **小模型兜底**：即使使用 GPT，也可本地部署一个 3B 模型做结果格式校验或安全性过滤，这是成本很低的附加层。

## 总结

OpenClaw 的多模型路由不适合“全自动自适应”的幻想，而应通过**上游分类 + 规则路由 + 兜底机制**的组合实现成本、性能与可靠性的平衡。GPT 负责高附加值推理与工具编排，本地模型处理确定性、高频、敏感任务，两者明确分工才能让 Agent 应用从 Demo 走向生产。每次调整路由策略前，先问自己：这个决策能不能用规则清晰描述？如果不能，先收集数据，而不是交给另一个模型去猜。
