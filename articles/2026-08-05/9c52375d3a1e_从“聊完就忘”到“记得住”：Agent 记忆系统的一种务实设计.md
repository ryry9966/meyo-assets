在 OpenClaw 这类 Agent 框架里跑通工具调用和流程编排并不难，真正难的是让 AI 助手“记得你”。不少人在 demo 阶段就遇到同一个问题：用户每次开新会话，都得重新交代一遍自己的习惯——输出格式要什么、代码偏好怎么写、报告多长合适。助手不是不聪明，而是没有记忆系统。

## 问题

LLM 天然无状态，context window 有限。最粗暴的方案是“把历史全塞进 context”，但很快会撞上三堵墙：

- **token 爆炸**：上下文越长越贵，越容易触发长度限制；
- **噪音淹没信号**：一万字聊天记录里真正有用的偏好可能就三行；
- **旧偏好覆盖新偏好**：用户改主意了，但历史里两条矛盾信息都被注入，模型无所适从。

记忆系统本质上要解决三件事：**记什么、存哪里、怎么取**。

## 做法

我不建议一上来就上向量数据库，对多数个人 Agent 场景，分层设计更务实。

1. **分清短期与长期记忆**
   短期记忆是会话内的上下文摘要，随 session 结束即失效；长期记忆是跨会话沉淀的事实与偏好，必须持久化。

2. **用结构化 Schema 存长期记忆，别存聊天原文**
   每条长期记忆记录建议包含：`type`（偏好/事实/指令）、`content`、`source`（来自哪次会话）、`confidence`（置信度 0-1）、`updated_at`。存原文只会让检索变难，存结构化记录才能查询、更新、淘汰。

3. **会话结束时做一次轻量抽取**
   在会话收尾时，调用一个小模型或一条 prompt，让模型输出 JSON patch，只记录“增量”。例如用户说“下次报告用中文写”，就抽取为一条 `{type: "preference", content: "report_language:zh", confidence: 0.6}`。存量更新优于全量重写。

4. **存储走 MCP 工具或本地 SQLite**
   把持久化封装成一个 memory MCP server 或直接存本地 SQLite 文件。好处是数据自己可控，不锁在某个云服务里，后续想迁移或导出都很方便。OpenClaw 的插件生态里做这样一个小工具并不复杂。

5. **制定取回策略**
   会话开始时注入 top-k 条高置信偏好（按 `updated_at` 和 `confidence` 排序）；会话中途如果用户纠正了之前的偏好，更新对应记录并追加一条 correction。不要每次把所有记忆都灌进 context。

## 踩坑点

- **把聊天记录全倒进向量库**：检索质量差，经常召回无关信息，还让 vector DB 里塞满垃圾。
- **偏好没有版本和置信度**：用户改主意后旧值还在被注入，模型表现得“记性太好”反而更糟糕。
- **只写不更新**：记忆变成“事实墓地”，越积越多，且无人清理。
- **过度记录**：用户随口一句话都当偏好存，结果真正重要的信息反而被埋没。记忆不是流水账，是档案。

## 可复用建议

- 每条偏好记录带 `confidence` 和 `updated_at`，用户明确纠正时才把置信度调高，模糊表达只给低分。
- 定义一层很薄的 memory policy：哪些类型的对话内容能进入长期记忆，用意图白名单或关键词控制，从源头减少噪音。
- 给用户一个“查看/清除记忆”的入口——既是隐私需求，也是调试手段。记忆不可见，问题就不可排查。
- 把记忆读取做成显式工具调用，而不是纯靠 prompt 注入。这样 Agent 在不确定时能主动查询，而不是猜测。

## 总结

记忆系统不是“装个向量数据库”就完事了。工程上更可行的是分层设计 + 结构化抽取 + 显式更新。把记忆当存档而非流水，Agent 才能真正积累用户偏好，而不是每次对话都从零开始。
