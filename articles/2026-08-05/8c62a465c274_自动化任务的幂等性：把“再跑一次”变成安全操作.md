## 背景

自动化世界里有个绕不开的事实：**不存在不会重复执行的系统**。LLM 调工具超时会重试，MCP 连接闪断会重连，定时任务漏跑要补跑，用户也可能手滑点两下。这些情况加起来，同一段任务逻辑被触发多次是常态，不是例外。

如果这段逻辑只读数据，问题不大。但自动化任务大多带副作用：发通知、写数据、建工单、调外部 API。任何一次重复执行，都可能变成事故。

## 问题

幂等性说的是：**同一操作执行一次和执行多次，系统最终状态一致**。不是禁止重复执行，而是重复执行不会产生额外副作用。

举个具体例子。你的 OpenClaw 定时任务每天把销售数据推送到工作群，某次网络抖动，插件在传输层重试了三次，群里瞬间刷出三份日报，相关人员被 @ 三遍。再比如一个 MCP 工具负责创建工单，Agent 因为上下文不确定把同一个工具多调了一次，工单系统里出现两个内容相同的工单，维护者得手动删一条。

小事故是烦，大事故是资损。重复扣费、重复发货、重复审批，本质都是同一个问题：任务没有幂等性设计。

## 做法

给自动化任务补幂等性，推荐分四步落地。

**第一步：为每个写操作定义幂等键。**
幂等键是“这次任务实例”的唯一标识。可以是 `sha256(任务名 + 业务主键 + 执行日期)`，也可以是 UUID。关键是同一个逻辑重复执行时，生成的幂等键必须完全一致。

**第二步：在执行入口统一检查。**
在 OpenClaw 插件里，可以做一个通用装饰器，所有带副作用的函数都走这一层：

```python
def with_idempotency(key_fn, storage):
    def decorator(fn):
        @wraps(fn)
        def wrapper(*args, **kwargs):
            key = key_fn(kwargs)
            if storage.exists(key):
                return storage.get_result(key)
            result = fn(*args, **kwargs)
            storage.save(key, result)
            return result
        return wrapper
    return decorator
```

重复请求不会真正执行副作用函数，直接返回第一次执行的结果。

**第三步：持久化幂等记录。**
幂等记录不能只存在进程内存里。进程一重启，记录就丢了，等于没做。用 SQLite、Redis 或本地文件都行，关键是存储本身要可靠，且写入和任务结果在同一个事务边界内。

**第四步：定义“同一次执行”的判定维度。**
对 Agent 自动化，建议用复合键：`(tool_name, args_hash, task_instance_id)`。task_instance_id 区分不同轮次的计划运行，args_hash 区分同一运行内的不同参数。只有两者都一致，才判定为重复调用。

## 踩坑点

- **“先查后写”有竞态。** 两个任务同时检查“是否已执行”，都发现没执行过，然后同时执行。幂等判定不能依赖应用层先查再写，要落到目标系统的原子约束上：数据库唯一索引、第三方 API 的 Idempotency-Key、消息队列的去重机制。

- **幂等键生成规则不稳定。** 键里带了 `datetime.now()` 或随机数，同一任务每次生成的键都不一样，等于没做。幂等键必须是确定性的。

- **只做了传输层重试。** MCP 连接断开后重连，上一条请求到底有没有被服务端处理过，客户端完全不知道。所以业务请求必须带幂等键，不能只依赖连接层的重试机制。

- **逆操作不幂等。** 补偿、退款、删除这些“取消动作”同样需要幂等。补偿一次和补偿两次，最终状态必须是同一个。

- **把工作流层面重试当成幂等。** Agent 编排层的重试只解决“任务没跑”，不解决“任务跑了一半”。部分写入的场景，重试单独处理不了，必须配合幂等键做结果合并。

## 可复用建议

- 插件里每个写操作，从第一版就带上幂等键设计，别等出事故再补。
- 统一幂等键生成约定：`hash(tool_name + primary_params + task_instance_id)`，写成一个公共函数。
- 优先用目标系统的原生幂等能力兜底，应用层的幂等表只能作为辅助。
- 日志里记录幂等键，排查问题时能快速关联同一任务的多份日志。
- 任务评审时加一条问题：“这个任务连续执行两次，会发生什么？”答不上来，就不要上线。

## 总结

幂等性不是锦上添花的工程洁癖，而是自动化系统的基础约束。Agent 自动化尤其如此——LLM 的行为天然不可完全预测，你无法保证它不会在某次推理中把同一个工具多调一次。与其祈祷不重复，不如把“重复执行安全”变成默认要求。设计任务时就把“再跑一次”当作必然会发生的事，你的自动化才真正扛得住生产环境。
