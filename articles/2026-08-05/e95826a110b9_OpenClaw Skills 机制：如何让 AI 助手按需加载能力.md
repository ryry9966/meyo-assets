## 背景：当"全都要"变成"全都慢"

用过 OpenClaw 的朋友都有过这种体验：`claw` 跑着跑着，上下文窗口被一堆用不到的插件说明塞满，响应逐字变慢，甚至触发截断。Agent 框架的演进方向很明确——从"加载所有工具"转向"按需取用"。OpenClaw 的 Skills 机制解决的就是这个问题：把能力拆成小块，需要时再挂载到当前会话，用完即走，不给上下文添堵。

## 问题：插件体系的两个硬伤

在说 Skills 之前，先说我们被卡住的两个点：

1. **上下文通胀**：MCP 服务器一旦接入，所有工具的 schema 都会注入系统提示词。接了五六台 server 后，光工具描述就吃掉上万 token，而真正用到的可能只有两三个。  
2. **配置耦合**：传统插件要预先在配置里写好启用条件，改动一个插件的依赖就可能牵连其他任务，排障成本高。

我们需要的不是"多装"，而是"该装的时候才装"。Skills 正是为此设计的。

## 做法：用 Skills 实现按需加载

### 第一步：把能力拆成 Skill 目录

OpenClaw 会在 `~/.openclaw/skills/` 下扫描子目录，每个子目录就是一个 Skill。一个标准的 Skill 结构：

```
skills/
└── pdf-report/
    ├── SKILL.md        # 能力描述 + 触发条件 + 使用说明
    ├── schema.json     # 工具入参定义（可选）
    └── script.py       # 实际执行逻辑
```

**关键在 SKILL.md 怎么写**。它不是给人看的文档，是给模型看的"触发开关"。要写清楚三件事：

- **When to use**：什么任务下应该调用这个 Skill  
- **How to use**：执行步骤和参数含义  
- **Cost note**：一旦加载会占用多少 token、会产生什么副作用

比如我们的 `pdf-report` Skill：

```markdown
# PDF Report Generator

## When to use
仅当用户明确要求"生成 PDF 格式的报告"时使用。  
日常问答、Markdown 输出等场景不要加载本 Skill。

## How to use
1. 调用 script.py，传入输出路径和报告标题
2. 该脚本依赖 wkhtmltopdf，使用前检查 PATH

## Cost note
加载后占用约 800 token 的上下文空间。  
耗时为秒级，如需处理大量 PDF 请改用 batch 模式。
```

### 第二步：用 Lazy Load 声明触发条件

OpenClaw 支持在 `claw.json` 里配置 Skill 的加载策略：

```json
{
  "skills": {
    "pdf-report": {
      "lazy": true,
      "triggers": ["生成PDF", "导出报告", "pdf", "report"]
    }
  }
}
```

`lazy: true` 意味着该 Skill 不会默认进入系统提示词。模型通过关键词或语义判断触发后，OpenClaw 才把 `SKILL.md` 注入当前会话，并在任务完成后（或上下文压力超阈值时）自动回收。

### 第三步：Skill 与 MCP 的分工

实践中我们的划分是：

- **MCP 负责"常驻数据面"**：比如数据库查询、文件系统操作，这类高频且 schema 稳定的工具留在 MCP 里。  
- **Skill 负责"低频能力面"**：PDF 生成、定时任务编排、外部 API 对接，这类低频高成本的操作全走 Skill。

这样设计后，基础会话的 token 消耗从 11k 降到 4.2k，首字响应时间缩短了约一半。

## 踩坑点

1. **SKILL.md 写得太泛**。最初我们把描述写成"可以生成报告"，结果模型在用户说"总结一下上周数据"时也触发加载，白白浪费上下文。后来把触发条件收窄到"PDF"、"格式导出"等强信号词，误触发率显著下降。

2. **Skill 内依赖的运行时版本不一致**。不同机器上的 `wkhtmltopdf` 版本不同，导致技能执行结果不稳定。现在的做法是在 SKILL.md 里固定版本号，并在 `script.py` 开头做环境校验，不通过就直接报错，避免 AI 继续硬跑。

3. **回收时机不好把握**。一开始用"任务完成后立即回收"，但多轮对话中用户常常临时追加需求，导致反复加载。改成了"上下文占比超过阈值时回收"，兼顾了连续性和资源控制。

## 可复用建议

- 为每个 Skill 设定明确的 token 预算，写进 `Cost note`，这既约束了模型的使用频率，也方便你审计上下文开销。  
- 用 `openclaw skills list --verbose` 定期检查哪些 Skill 频繁加载、哪些从不触发。从不触发的要么改描述，要么删掉，别让死代码躺在仓库里。  
- 把 Skill 作为团队共享资产放进 git 仓库，通过 CI 做 `SKILL.md` 格式校验和脚本 smoke test。AI 是迭代出来的，Skill 也一样。

## 总结

OpenClaw 的 Skills 机制本质上是把"能力注册"从静态配置变成了动态协商：模型根据任务语义决定加载什么、卸载什么。它不解决所有问题——高频工具还是得靠 MCP，复杂的编排逻辑依然需要外部服务——但作为上下文治理的第一道闸门，它把我们从"上下文通胀"里拉了出来。

如果你的 Agent 也开始出现"越来越慢、越来越笨"的迹象，先别急着加模型上下文长度，试着把低频能力拆成 Skills。少即是多，按需即是高效。
