让一个 agent 串行处理复杂任务，越往后越难受：会话越来越长，中间结果堆在主上下文里，前面的结论可能被挤掉，还慢。subagent 编排解决的是这件事——把大任务拆成可独立执行的小任务，并行跑，再合并。这篇文章记录我在 OpenClaw 里做 fan-out/fan-in 编排的工程实践和踩坑。

## 一、编排模型

主 agent 负责拆和并，子 agent 只认任务契约。拆解阶段，主 agent 产出子任务清单，每个子任务包含三件事：目标描述、数据来源、输出 schema。

```json
[
  {
    "id": "task_commits",
    "goal": "提取最近 30 条 commit 的主题分类",
    "input": {"repo": "xxx", "range": "last_30"},
    "output": {"schema": "list[{topic, count}]"}
  },
  {
    "id": "task_issues",
    "goal": "统计 open issue 里的高频关键词",
    "input": {"repo": "xxx", "state": "open"},
    "output": {"schema": "list[{keyword, mentions}]"}
  }
]
```

执行阶段控制并发度。实测并发不超过 3 个，不是怕 API 限流，而是结果回收时容易乱，3 路以内好追踪。

## 二、合并策略

合并优先走确定性逻辑，少用 agent：先按 id 去重，同一数据源按时间戳取新；冲突字段按来源优先级裁决。只有确定性规则处理不了的语义冲突，才交给合并 agent，而且 prompt 只贴冲突片段，不要贴全部结果——这是最容易踩的坑。

## 三、踩坑记录

1. **子任务拆分重叠**。有次拆到一半，task_commits 和 task_issues 都在读同一批文件，产出大量重复。解法：拆分前先列数据源清单，一个数据源只分给一个子任务。
2. **结果回收 token 暴涨**。7 个子 agent 每个返回 3000 token 结果，主上下文直接爆掉。解法：输出 schema 强制压缩，子 agent 只返回统计结果不返回原始文本；原始数据落盘，主 agent 按需取。
3. **单个 agent 卡死拖垮整体**。最初设 120 秒超时，有个子 agent 连续调工具跑满 120 秒，整个流程陪着等。改成：超时 60 秒，超时即标记失败，不重试，合并阶段标注"部分缺失"。宁可结果不完整，不要整体超时。
4. **并发太高触发限流**。同一个 provider key 下，3-4 路并发就可能吃 429。建议 2-3 并发起步，看报错再调。

## 四、可复用建议

- 子任务必须有输出 schema，没有 schema 的任务不要并行。
- 超时、重试预算在编排层统一配置，不要让子 agent 自行决定。
- 合并先跑确定性去重，再决定是否动用合并 agent。
- 记录每个子任务的 token 消耗、耗时、返回条数，跑完看日志能发现拆分质量问题。
- 从 2-3 个子 agent 起步，验证合并逻辑稳定后再往上加。

## 五、总结

subagent 并行编排的价值不在"同时跑多个 AI"，而是通过拆分把长会话变成可控的短任务，让主上下文可预期、整体延迟可接受。真正的成本都在编排边界上：任务怎么拆、结果怎么并、失败怎么收。这些是工程问题，不是模型能力问题。
