## 背景

用 OpenClaw 跑了一段时间后，大多数人会面临同一个问题：默认配置走云端 API 又贵又慢，全换本地模型又经常在处理复杂任务时"掉链子"。多模型路由不是你要不要配的问题，而是你迟早要面对的选择。

这篇文章不聊抽象概念，只说 OpenClaw 里实际怎么分流、什么时候该用 GPT 级云端模型、什么时候本地模型反而是最优解。

## 问题

我最初的做法很粗暴：所有请求都走一个模型。结果两边都不满意——

- 全部走云端：一次含 MCP 工具调用的多步 Agent 任务，token 消耗轻松过万，日积月累成本可观
- 全部走本地：Qwen 或 Llama 处理简单对话没问题，但一旦涉及复杂工具链（多个 MCP server 协同）、长上下文推理，输出质量明显下降，还容易陷入重复循环

问题的核心不是"哪个模型更强"，而是**你没有按任务维度做分流**。

## 做法/步骤

OpenClaw 支持在 agent 配置中定义多个模型，并在运行时通过路由规则切换。我的实践分三步：

**第一步：列出你的任务类型**

我通常按这几个维度拆：

| 任务类型 | 特征 | 示例 |
|---------|------|------|
| 复杂推理 | 需要多步逻辑、工具调用链 | 跨 MCP server 的数据汇总分析 |
| 代码生成 | 需要严谨语法 | 写脚本、改配置 |
| 日常问答 | 单轮、低风险、无工具 | 解释概念、闲聊 |
| 隐私敏感 | 本地文件、密钥相关 | 处理本地配置、读日志 |
| 高频低延迟 | 频繁触发、等待敏感 | 定时任务、状态检查 |

**第二步：配置模型池**

在 OpenClaw 的 agent 配置中为同一个 agent 声明多个模型：

```yaml
models:
  primary:
    provider: openai
    model: gpt-4o-mini
    # 用于复杂推理和高风险任务
  local_fast:
    provider: ollama
    model: qwen2.5:7b
    # 用于闲聊、简单问答、隐私敏感任务
```

**第三步：设定路由规则**

OpenClaw 的 intent routing 或手动函数内切换都是可行的：

```python
def route_to_model(task):
    if task.requires_tool_chain or task.complexity_score > 0.7:
        return "primary"       # 云端模型
    if task.contains_sensitive_data or task.latency_budget < 2:
        return "local_fast"    # 本地模型
    return "primary"
```

关键判断依据：

- **涉及两个以上 MCP 工具协作** → 云端
- **单论对话、不需要工具** → 本地
- **任务有明确正确/错误答案（如代码）** → 云端，错误成本太高
- **任务只是格式处理、抽取** → 本地，本地模型足够

## 踩坑点

以下都是实际踩过的坑，写出来省得你重走：

**1. 本地模型的 tool calling 不稳定**

用本地模型走 MCP 工具时，工具名和参数有时会编造或漏传。最直接的方案：**给本地模型只暴露数量少、参数简单的工具**，复杂工具链全部留给云端模型。不要指望 7B 模型能稳定驱动 5 个 MCP server 的复杂编排。

**2. 模型名写错导致静默 fallback**

OpenClaw 如果找不到配置的本地模型，会触发 fallback 到另一个 provider，表面上看"能用"，实际走了云端，成本全都漏了。配置后务必在日志里确认实际使用模型。

**3. 上下文窗口差异导致的截断**

本地小模型的 context 有限，长对话历史会静默截断，导致"一句话前面是对的后面逻辑断了"。我现在的做法：**简单对话超过 5 轮就强制走云端**，或者用 summarizer 压缩历史后回到本地。

**4. 路由逻辑不要做在 prompt 里**

"请根据复杂度选择模型"这种方案不可靠——模型对自己的能力边界没有准确认知，实际效果就是随机。要么用规则判断，要么用框架层路由。

## 可复用建议

1. **先本地后云端是默认策略**。70% 的流量属于日常问答和简单任务，本地模型能承接大部分，成本降幅明显。
2. **给复杂任务一个"高阈值触发器"**。例如：MCP 工具调用数 > 1、任务描述含"总结/分析/对比"关键词，直接走云端，不过度纠结。
3. **做模型健康检查**。定期跑一组固定测试集（如 3 个复杂推理题 + 3 个简单问答），分别走两个模型对比输出质量，发现本地模型因版本更新变差就及时调整路由比例。
4. **敏感数据默认本地**。涉及密钥、本地文件路径、内网信息的一律不过云端，这不是性能问题，是原则问题——用路由规则强制，不要依赖模型自觉。

## 总结

多模型路由的价值只有在真实使用中才会放大。核心思路很朴素：**简单高频的任务给本地，复杂低频的任务给云端**。OpenClaw 的灵活之处在于路由层可以完全自定义，把策略从代码里抽出来，随时调整。

别追求一步到位的"智能路由"，先用规则跑起来，观察日志，再逐步优化阈值。稳定优先于聪明。
