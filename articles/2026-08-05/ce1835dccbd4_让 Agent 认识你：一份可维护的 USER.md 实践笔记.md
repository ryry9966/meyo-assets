## 背景：Agent 的“失忆症”从哪来

用过一段时间 OpenClaw 的朋友应该都有体会：单个任务里，Agent 表现得相当聪明，能根据上下文猜出你的意图。但一旦开启新会话，它对你的了解几乎归零——不知道你用哪种包管理器、偏好什么代码风格、最烦哪些邮件、常用哪些 API Key 对应哪个项目。

这不是模型能力缺陷，而是上下文管理的结构性问题。我们在 `.clawrc` 或环境变量里配置的是“运行参数”，而不是“用户侧信息”。Agent 在每次会话中都靠 prompt 临时拼凑对用户的认知，自然时灵时不灵。

## 问题：为什么“自我介绍”不生效

我最早的做法是在每次任务的 prompt 开头写一段“我是谁、我喜欢什么、避免什么”。效果一般，原因有三：

1. **不完整**：想起来才写，写出来的是碎片，不是画像。
2. **不可复用**：每个任务都要重新输入，Agent 无法跨会话积累。
3. **有噪音**：大段描述挤占上下文窗口，真正关键的约束反而被稀释。

直到我接触到 `USER.md` 这个模式——把用户画像落到文件里，通过 OpenClaw 的上下文注入机制在每次会话时自动加载。这才把“Agent 认不认识你”从概率问题变成工程问题。

## 做法：从零构建你的 USER.md

### 第一步：决定放置位置

OpenClaw 支持按层级划分的上下文文件，`USER.md` 一般放在会话根目录。我自己用两级结构：

```
~/.openclaw/
  USER.md          # 全局用户画像，所有项目通用
  projects/xxx/
    USER.md        # 项目特定偏好，覆盖或补充全局配置
```

这样既保证通用约束不丢，又能针对特定项目做微调。让 Agent 在启动时自动加载对应层级的 USER.md。

### 第二步：内容组织，按“决策频率”排序

我踩过的最大坑是把 USER.md 写成个人简历。真正有效的内容不是“我是谁”，而是“当你遇到 X 类决策时，应该怎么选”。以下是我当前模板的骨架：

```markdown
# USER.md - [你的名字/昵称]

## 核心偏好（高优先级）
- 代码风格：TypeScript 严格模式，禁止 any
- 包管理：项目内优先 pnpm，其次 npm
- 错误处理：不吞异常，必须有日志输出

## 工作流习惯
- Git 提交：遵循 Conventional Commits，scope 必填
- 代码审查：关注性能 > 可读性 > 风格
- 自动化任务：优先用现有 MCP 工具，不要自造轮子

## 明确避雷（不可违反）
- 不要自动执行 `rm -rf`
- 不要修改未明确要求的配置文件
- 不要在代码中硬编码 API Key

## 项目背景（用于理解上下文）
- 当前主要维护 3 个仓库：xxx（数据管道）、yyy（API 服务）、zzz（CLI 工具）
- 常用服务：xxx 平台的 MCP 网关，yyy 的调度中心

## 当前关注（会过期，定期更新）
- 正在评估：将 xxx 服务从 REST 迁移到 gRPC
- 待办：清理 yyy 仓库的遗留分支

## 元信息
- 最后更新：2025-06-xx
- 变更记录：简短写明最近改了哪些偏好
```

关键是把“偏好”和“事实”分开。偏好是 Agent 必须遵守的约束，事实是帮助 Agent 理解上下文的背景信息。混在一起会导致 Agent 分不清优先级。

### 第三步：写“反例”比写“正例”更高效

Agent 的默认行为往往偏向“稳妥但平庸”。如果你不告诉它你不想要什么，它就会用最通用、最保守的方式完成任务。比如：

- 默认会生成 README？→ 明确写“不要自动创建文档文件”。
- 默认用 `fetch` 发请求？→ 明确写“统一用 MCP 的 http 工具”。
- 默认以为你有权限访问某个服务？→ 明确写“生产环境的 xxx 服务只有只读权限”。

我见过不少 USER.md 靠愿景驱动，写得很宏大，结果 Agent 每次都在无关紧要的小事上反复试探边界。反例清单就是边界本身。

### 第四步：建立“更新触发点”

USER.md 是活文档，但很容易写完就忘。我给自己定了几个触发点：

- 每个迭代周期结束，花 5 分钟清理“当前关注”部分
- 当发现 Agent 连续两次在同类决策上做出错误选择时，立即补充该反例
- 每次新增 MCP 工具或插件时，评估是否需要在 USER.md 中登记

## 踩坑点

**踩坑 1：把 USER.md 塞进项目仓库**
你个人的使用偏好不一定适合团队成员。USER.md 更适合放在个人配置目录，而不是和代码一起提交。如果要团队共享，至少抽出一个独立文件，别混进业务代码的 README。

**踩坑 2：优先级冲突没有说明**
项目级 USER.md 覆盖全局级时，Agent 可能混淆。我建议在文件顶部写明“本文件适用于：当前会话，优先级：高”。如果冲突，以最近的显式指令为准。

**踩坑 3：试图用 USER.md 替代系统 prompt 或 MCP 配置**
USER.md 描述的是“你是谁、你要什么”，不是“Agent 应该怎么运行”。如果你发现自己开始写“请使用 gpt-4o 作为默认模型”这类内容，说明放错地方了。模型选择、工具开关属于 OpenClaw 的配置文件职责。

**踩坑 4：过度追求完整**
我第一版 USER.md 写了 300 多行，结果上下文占用过高，Agent 反而忽略了关键信息。现在压缩到 50-80 行，只保留“没有它 Agent 就会做错”的内容。

## 可复用建议

1. **用模板起步**：先复制上面的骨架，只填前两节，用起来再迭代。别一开始就追求完备。
2. **用 git 管理你的 USER.md**：即使它不在项目仓库里，也建议纳入版本控制，方便回滚和回顾偏好变化。
3. **做一次“冷启动测试”**：删掉所有会话历史，开启新会话，只靠 USER.md 和 OpenClaw 的基础配置，看 Agent 是否能正确回答关于你的三个问题：我的代码风格、我最常用的包管理器、我禁止哪些操作。过不了就继续补。
4. **结合 MCP 工具链**：如果你的 OpenClaw 实例已经接入了文件系统 MCP 或笔记类 MCP，可以把 USER.md 的变更记录自动追加到你的周报里，形成反馈闭环。

## 总结

USER.md 的实质，是把你作为用户的长期偏好从“任务窗口”中剥离出来，固化到 Agent 的启动上下文中。它不解决模型能力问题，但能显著减少重复的 prompt 调优，让多会话、多项目的 Agent 行为更稳定，也更像“在为你工作”。

值得花一个下午，仔细想想你希望 Agent 记住你什么。
