## 背景

把 OpenClaw 跑起来之后，最常遇到的尴尬是：Agent 上线了，但它只是安静地等你提问。你忘了问，它就不动。真正的 Agent 不该是“高级百度”，而应该像值班同事——自己盯着数据、自己判断、自己动手。这就是 HEARTBEAT.md 要解决的问题：给 Agent 装一个“心跳”，让它按自己的节奏主动工作，而不是被动应答。

## 问题

纯 prompt 驱动的 Agent 有几个硬伤。一是用户不记得什么时候该找它，错过时机等于没有监控；二是 Agent 没有跨会话状态，每次对话都像失忆；三是“凌晨数据更新后需要处理”“每天收盘后要出摘要”这类场景，靠人手动触发根本不现实。cron 能解决“定时跑”，但解决不了“跑之前该看什么、跑完之后该做什么”——这才是心跳文件存在的理由。

## 做法 / 步骤

1. 在 Agent 工作目录建一个 `HEARTBEAT.md`，固定字段：`status`（当前状态）、`last_run`（上次执行时间）、`next_check`（下次检查项）、`rules`（判定规则）、`log`（执行历史）。
2. 把“每次唤醒后，先读 HEARTBEAT.md，再按 rules 行动”写进 system prompt 或 pre-action 钩子。
3. 用容器级 cron 或调度器定期触发工作流，例如每 30 分钟一次轻量检查、每天一次重任务。
4. 每次跑完，把结果、决策依据、执行动作追加到 `log` 段，作为下一次判断的上下文。
5. 把动作接到 MCP 工具上——查数据库、发通知、写 issue、调用内部 API，让心跳真正产生外部效果。

## 踩坑点

- **心跳无状态**：Agent 第二次跑会把上次的活重干一遍。解决方法是让它只处理 `last_run` 之后的变化，而不是全量扫描。
- **Agent 自己改规则**：它可能顺手把 HEARTBEAT.md 里的阈值改了。把 `rules` 区标记为只读，或在写入前加校验。
- **过度自治**：没有确认门槛，Agent 半夜给全员发消息。必须在 rules 里写明“影响面大于 X 时等人工确认”。
- **冷启动失效**：新环境下的模型没读过心跳范式，第一次触发会忽略它。首次运行时需要用显式指令 cue 一次“你的心跳文件在哪里”。

## 可复用建议

- 心跳文件只允许追加 `log`，其余字段由外部控制，保证审计可追溯。
- 所有动作幂等：消息、issue 都带 `run_id`，重复执行不产生重复副作用。
- 先让心跳只做“检查 + 记录”，稳定运行一周后再放开执行权限。
- 把 HEARTBEAT.md 纳入 Git 版本管理，diff 就是 Agent 行为的完整审计轨迹。

## 总结

HEARTBEAT.md 的本质不是把决策权全部交给 AI，而是给它装上“时钟和备忘录”。它把 Agent 从被动应答变成主动值班，同时保留人在关键节点上的控制权。在 OpenClaw 体系里，这个模式比堆插件更值得先落地——因为它直接改写了 Agent 的默认行为方式。
