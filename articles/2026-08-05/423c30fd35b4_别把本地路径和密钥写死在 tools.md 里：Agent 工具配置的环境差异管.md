## 背景：tools.md 为什么成了“环境敏感文件”

在 OpenClaw 和类似的多工具 Agent 架构中，`tools.md` 承担着声明可用工具、定义调用约束的任务。它就像一份“能力说明书”，告诉 Agent 有哪些外部工具可以调用，每个工具的参数、环境要求、权限边界是什么。

但在实际工程中，`tools.md` 很容易变成一个巨大的技术债来源。原因很简单：**本地开发环境和目标运行环境之间，路径、端口、凭据、网络可达性几乎不可能一模一样。** 但很多实践者直接把本地绝对路径、开发用 API Key 甚至数据库连接串写进了这份声明文件里。当 Agent 被部署到生产环境或分享给其他人时，这些硬编码的差异就变成了运行时故障的触发器。

这篇文章不讨论某个特定框架，而是总结一套在 OpenClaw/Agent/MCP/自动化插件实践中，管理 tools.md 内本地配置和环境差异的工程方法。不会出现“你应该用 XXX 工具”这类推销，只讲可复现的操作思路和踩过的坑。

## 问题的具体形态

典型的灾难场景包括：

- **路径写死**：`command: python /home/me/projects/my_script.py`，到容器里变成 `/app` 或 Windows 的 `C:\...`，直接找不到脚本。
- **凭据外露**：API Key、token 直接写在 `tools.md` 里，提交到 Git 后泄露。
- **端口冲突**：本地调试用 `http://localhost:8080`，生产环境服务在另外一台机器上，Agent 需要调用动态发现的服务地址。
- **环境差异导致的工具不可用**：比如 `tool_name` 在 dev 环境注册了，但 staging 没有，Agent 按声明去调用时返回失败。
- **多平台路径分隔符**：`path/to/file` 在 Windows 的某些工具调用中可能解析失败。

Agent 框架本身不会替你解决这些问题，它只是忠实地按照 `tools.md` 中的指令去执行。所以配置文件中的“环境假设”必须被显式管理。

## 怎么做：可维护的 tools.md 管理方案

### 1. 将 tools.md 变为模板，而非静态配置

不要直接维护一份“最终形态”的 `tools.md`，而是维护 `tools.md.template`。模板中使用明确且可替换的占位符，例如 `{{PROJECT_ROOT}}`、`{{API_BASE_URL}}`、`{{DEV_API_KEY}}`。然后通过脚本、Makefile 或 Docker 入口点在运行时生成实际的 `tools.md`。

这样做的好处：同一个模板在不同环境下，通过不同的变量注入生成适配文件，而不需要维护多份拷贝。

### 2. 从环境变量注入路径与网络参数

所有与环境强相关的值，一律不在模板中写死，而是从环境变量读取。例如，一个本地脚本执行工具，不应该写绝对路径，可以约定在 `tools.md.template` 中写：

```yaml
command: python ${AGENT_SCRIPT_HOME}/data_fetch.py
```

部署时通过环境变量 `AGENT_SCRIPT_HOME` 指定根路径。对于 API 端点，写成 `${SERVICE_ENDPOINT}/v1/query`。

注意：这里的环境变量是注入到 Agent 运行时进程的，不是直接在模板里硬编码。也就是说，替换过程发生在生成 `tools.md` 时，而非让 Agent 运行时去解析环境变量（除非框架支持，但为了通用性，建议提前生成好静态文件）。

### 3. 分离敏感凭据与工具声明

绝对不要把 API Key、token 直接写入 `tools.md` 模板。即使模板里用了占位符，如果构建脚本不慎将这些值打印到日志或留在中间文件中，也是风险。更安全的做法：

- 工具声明只描述需要什么凭据，但不携带值。比如在 `tools.md` 中写 `auth_header_name: X-API-Key`，并说明 Agent 在调用时从安全存储（如密钥管理服务、环境变量、`.env` 文件）中动态注入。
- 如果框架允许在工具调用时动态传入环境变量，可以利用这一点。OpenClaw 支持在工具定义上注入 `env` 字段吗？如果不支持，可以在调用脚本里读取环境变量，比如 `script.sh` 内部访问 `$SECRET_TOKEN`，这样工具声明只指向脚本，密钥不进入配置。

### 4. 使用条件工具注册或动态发现

如果某个工具只在特定环境存在（比如本地调试工具），不要在面向所有环境的 `tools.md` 里统一声明。可以使用**分层配置**：

- `tools.base.md`：包含所有环境通用的工具。
- `tools.dev.md`：仅包含开发/调试用的工具。
- 通过合并工具生成最终文件。

更自动化的方式是让 Agent 启动时动态扫描可用工具（如 MCP 的 ListTools），而不是依赖于静态的 `.md` 文件。但如果必须用静态文件，就采用分层生成。

### 5. 跨平台路径的防呆设计

路径在 WSL、原生 Linux、macOS、Windows 下差异很大。在模板中尽量使用 POSIX 风格并统一使用正斜杠，然后通过环境变量指定完整路径，避免手动拼接。另一个保险措施：在启动脚本中添加路径存在性检查，提前失败而不是让 Agent 在运行中出错。

### 踩过的真实坑点

- **占位符替换遗漏**：部分值在模板中用 `{{VAR}}`，生成脚本里忘了替换，最终 `tools.md` 里留下了模板语法，Agent 解析失败。建议生成后加一个校验步骤，用 grep 检查是否存在 `{{`。
- **环境变量没有默认值导致空字符串**：某次部署时忘记设置 `API_ENDPOINT` 变量，生成出的工具调用 URL 变成 `http:///path`，整个 Agent 挂了半小时。必须在生成脚本里对必需变量做非空校验。
- **在 docker-compose 中把 .env 文件也挂载了进去**：.env 里包含的本地密钥在不经意间被打进了镜像或挂载到容器，虽然 `tools.md` 没写死，但 `docker-compose.yml` 写了 `env_file: .env`，等于全量注入。需严格区分开发用和部署用的环境文件。
- **Windows 换行符 CRLF**：生成脚本如果在 Windows 编辑，可能导致 `tools.md` 出现 `\r\n`，某些 Linux 上的调用工具可能误解析。约定仓库 `.gitattributes` 强制 LF。

## 可复用的工程建议

1. **建立一个 `tools/` 目录**，结构清晰：
   ```
   tools/
     templates/
       tools.base.md
       tools.dev.md
     scripts/
       generate_tools.sh
     output/
       tools.md (生成产物，加入.gitignore)
   ```
2. **在 CI/CD 或启动脚本中始终调用 `generate_tools.sh`**，保证每次部署的 `tools.md` 都是根据当前环境新鲜生成的。
3. **为不同的部署目标维护不同的 `.env.tools` 文件**（例如 `.env.tools.staging`），但**永远不提交到版本库**，只通过安全分享或密钥管理服务分发。
4. **加上工具清单一致性校验**：在 CI 中加入一步，比较代码中实际实现的工具和 `tools.md` 中声明的工具是否匹配，防止声明了但实际上已经废弃的工具残留。
5. **将 Agent 的启动脚本中加入一个 dry-run 模式**：仅检查工具的可达性（例如 HTTP 工具 ping 一下 endpoint，脚本工具检查文件是否存在），而不是直接执行任务，这样可以快速发现配置错误。

## 总结

`tools.md` 作为 Agent 与外部世界的契约，如果硬编码了本地配置和环境假设，就会变成一处脆弱的耦合点。正确的姿势是：模板化、环境变量注入、凭据外置、分层注册、生成校验。它们并不复杂，但需要在一开始就形成约定，否则随着工具数量增长，差异会像藤蔓一样缠住每一次发布。

把环境差异关进笼子里，你的 Agent 才能在任意机器上自由呼吸。
