## 背景

用过一段时间 OpenClaw 的人都会遇到同一个场景：每次新会话，Agent 都会重新问你「你的环境是什么」「错误日志贴一下」「要不要先跑一下测试」。不是模型不够聪明，而是它没有你的记忆。会话一关，上下文清零，你的偏好和工作习惯被丢得干干净净。

很多人把缓解措施放在系统提示词里，或者全塞进 `claw.md`。但系统提示词会膨胀，`claw.md` 本质是项目记忆，塞入个人偏好后，Agent 分不清哪些规则是「这个仓库的」、哪些是「这个人的」。结果就是上下文被浪费，优先级错乱。

## 问题

核心问题是：Agent 知道怎么用工具，但不知道「你是谁」。它不了解你用什么包管理器、讨厌什么写作风格、允许它执行到什么程度。你把时间花在重复描述上，而不是真正的任务本身。

## 做法：一份分层描述的 USER.md

推荐在 OpenClaw 的全局配置目录下创建一个 USER.md，与项目级的 `claw.md` 分开，各司其职。

步骤：

1. 创建 `~/.openclaw/USER.md`。
2. 按固定结构写，建议五个区块：
   - 身份：你的角色、常用语言、时区偏好。
   - 沟通偏好：回复长度、是否允许反问澄清、术语习惯。
   - 工具与环境：shell、编辑器、包管理器、已知不可用的工具。
   - 工作流：任务的默认执行顺序、哪些操作需要先确认。
   - 红线：明确禁止的行为列表。
3. 让 Agent 每次会话加载它。在 OpenClaw 中，可以把 USER.md 引入到 persona/instructions 文件里，或用 `-i USER.md` 显式注入；如果你是 MCP 用户，也可以让 filesystem 工具按需读取，但主动注入比让 Agent「想起来去读」可靠得多。

保持克制：一开始写 20 行就够，后续按真实纠错记录逐步扩充。

## 踩坑点

- 文件过长。每个 token 都在挤占上下文窗口，超过 1.5k tokens 的 USER.md 基本失控，先把最高频的规则写进去。
- 写成空话。「要 helpful」「要专业」这种描述，Agent 无法执行。用「always/never」+ 具体行为，例如：「永远不要直接执行 `git push`，先给出 diff」。
- 内容过期。三个月前的规则可能已不符合你的工作方式，过期的规则比没有规则更有害。直接编辑，每月审一遍。
- 越权存放敏感信息。USER.md 会被注入到每次会话，不要放 API key、密码、隐私数据。
- 和项目配置混淆。USER.md 是全局的，`claw.md` 是项目级的，混在一起会导致 Agent 把个人规则套用到无关项目上。

## 可复用建议

- 模板化：把上述五区块做成骨架，换机器、换项目时直接复用。
- 版本化：放进 dotfiles 仓库用软链同步，改动可追溯。
- 验证：开一个新会话，直接问「根据 USER.md，我的工作环境是什么」，检查是否被正确加载。
- 分层：团队场景下，共享规范放团队级文件，个人偏好放 USER.md，两层叠加。

## 总结

USER.md 的本质是用最小的上下文成本，绕过每次会话的「重新认识你」过程。它不解决 Agent 的所有问题，只是一个结构化的、持续维护的自我描述。写一次，维护一年，每次会话的起点都高一大截。
