## 背景

在 OpenClaw / Agent 的插件开发中，我们经常让 LLM 返回结构化数据——无论是工具调用的参数、MCP 响应的元数据，还是自动化流程中的中间结果。理想情况下，模型会返回标准的 JSON，我们用 `JSON.parse()` 一行解决。但真实场景远没有这么乐观。

接入过三个以上不同基座模型后，你会发现 `json` 格式的"方言"多到令人头疼：有的模型习惯用 ```json 代码块包裹，有的会在 JSON 前后附加自然语言说明，还有的在系统提示词里写了 `输出 <result> 标签` 就真的把 JSON 塞进了自定义标签里。这些格式变体稍有偏差，解析器就会抛异常，轻则当前工具调用失败，重则整个 Agent 工作流中断。

这不是模型能力问题，而是输出侧的结构漂移。防御性编程在这里不是可选项，是插件能稳定跑起来的前提。

## 问题定义

以我最近在 OpenClaw 插件里处理的真实案例为例，模型在上下文里同时看到了 JSON 示例和标签约束后，返回了混合体：

````
好的，这是你要的结果：
<result>
```json
{"status": "success", "data": {"count": 42}}
```
</result>
````

单纯用 `JSON.parse()` 必挂；用正则提取 `<result>` 中间内容，还会多出代码块围栏（code fence）。更隐蔽的是另一种模式——JSON 字段里混入了一段被截断的标签，比如 `"description": "见 <note> 里的说`，这类情况没法靠简单清洗解决。

## 做法：设计一个"宽容"的解析层

与其每次遇到异常就修补正则，不如把解析逻辑收敛成一个独立的解析函数，统一处理所有格式变体。核心策略分三步：

### 1. 优先提取封闭标签内容

如果输出中同时存在自定义标签（如 `<result>`、`<output>`、`<tool_response>`）和 JSON/代码块，**优先信任封闭标签内的内容**。这段内容通常是最新的、最结构化的。

```python
import re
import json

def extract_structured_content(raw: str, tag: str = "result") -> str:
    """优先提取封闭标签内容，再剥离代码块围栏，最后兜底取首个JSON片段."""
    if not raw:
        raise ValueError("空输入")

    # 1. 提取封闭标签内的内容（支持递归匹配，避免闭合标签丢失）
    pattern = rf"<{tag}\b[^>]*>([\s\S]*?)</{tag}>"
    match = re.search(pattern, raw)
    if match:
        candidate = match.group(1)
        # 2. 剥离可能的代码块围栏
        fence_match = re.search(r"```(?:json)?\s*([\s\S]*?)```", candidate.strip())
        if fence_match:
            return fence_match.group(1).strip()
        return candidate.strip()

    # 3. 无标签时，尝试剥离所有代码块围栏再取JSON
    stripped = re.sub(r"```(?:json)?\s*([\s\S]*?)```", r"\1", raw.strip())
    return stripped
```

### 2. 反向扫描 JSON 边界

很多模型会在 JSON 末尾追加括号或注释。`json.loads()` 失败时，不要急着抛异常，从候选字符串的末尾反向扫描，找到最后一个合法的 `}` 或 `]`，截断后重新解析。

```python
def robust_json_parse(candidate: str):
    """尝试多种策略解析JSON，均失败则抛异常."""
    try:
        return json.loads(candidate), "direct"
    except json.JSONDecodeError:
        pass

    # 策略A：从末尾往前扫，截断到最后一个 '}' 或 ']'
    for close_char in ("}", "]"):
        last_idx = candidate.rfind(close_char)
        if last_idx != -1:
            try:
                return json.loads(candidate[:last_idx + 1]), "truncated"
            except json.JSONDecodeError:
                continue

    # 策略B：尝试提取大括号/方括号层级平衡的完整JSON
    # （实现较长，此处省略，核心逻辑是模拟栈匹配）
    raise ValueError("无法解析模型输出为JSON")
```

### 3. 归一化与再解析

如果模型返回的是 YAML 风格（因为系统提示词示例里混入了 YAML），不要徒增解析器负担。将其先归一化为 JSON 再处理——用 `yaml.safe_load()` 转 dict 后 `json.dumps()` 回来，然后在业务层统一消费 JSON。

```
   输出 → 尝试封闭标签提取 → 剥离围栏 → json.loads
                                      ↓ 失败
                           反向截断再解析 / YAML归一化
                                      ↓ 失败
                           记录原始输出 + 抛业务异常（可重试）
```

## 踩坑点

1. **多行字符串里的括号误判**。反向扫描 `}` 时，如果 JSON 字段值里含有未转义的大括号（如模板字符串），截断点会出错。解法是先用 `ast.literal_eval` 或正则校验 `\\{` 与 `\\}` 的配对，再决定截断位置。
2. **HTML/XML 实体转义**。模型有时会把 `<result>` 写成 `&lt;result&gt;`，或把 `"` 包装成 `&quot;`。解析前先 `html.unescape()` 一遍，代价极低，收益明确。
3. **正则的贪婪匹配**。`[\s\S]*?` 必须用非贪婪模式，否则多个 `<result>` 标签存在时会吞掉中间内容。如果你用的是 Go/Rust 的标准库正则，注意它们默认不支持反向预查，需要调整提取策略。

## 可复用建议

- **把解析器封装为独立模块**，不要在业务代码里原地写正则。版本化维护，换模型时只需回归测试解析器。
- **为解析器写一张 golden 样例表**（正常 JSON、Tag+代码块、截断 JSON、空壳标签），每次升级模型或改提示词后跑一遍。
- **在捕获的异常中保留原始输出**。解析失败时，把原始文本写入日志或临时文件，方便复现和补测试用例。这是工程上最重要的习惯。
- **上层调用方设置重试 + 提示词微调**。如果解析连续失败两次，让 Agent 主动附加 "仅输出 JSON，不要使用任何标签或代码块" 再请求一次——效果显著。

## 总结

LLM 输出解析的防御性编程，本质上是对"模型输出是离散概率采样"这一事实的尊重。格式漂移无法消灭，只能通过分层兜底来减少故障半径。上述方法在 OpenClaw 插件、MCP 工具链和自动化脚本中均适用。核心收获归纳为一句话：**不要假设模型会严格遵循你的格式要求，去解析它实际输出里最像结构数据的那个片段**，而不是强求格式本身。
