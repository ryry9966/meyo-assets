## 背景

定时任务（Cron）在 OpenClaw 里是个高频但容易被低估的功能。日常摘要、关键词监控、报表推送，看起来只是把一段 prompt 丢给定时器。但实际用下来你会发现：同一段指令，手动触发时很靠谱，进了 Cron 之后输出质量明显下降。

原因不复杂。手动场景里有人在回路中：跑偏了你会打断，格式不对你会纠正，上下文缺失你会补一句「只看昨天的」。Cron 场景没有这个回路。指令是唯一的控制面。

## 问题

典型的失败案例：

```
每天 9 点把我关注的几个源的最新文章整理成摘要发给我
```

手动执行时它也许能出结果，放进 Cron 后会暴露出几个问题：

- 内容一多，agent 不知道保留什么、舍弃什么
- 输出格式不稳定，这次是列表，下次是段落
- 「最新」没有定义，和上一轮结果大量重复
- 某个源站挂了，agent 可能直接给你编一个参考链接

根源在于：指令没有定义边界。所有没说明的事项，agent 都会用「最大熵」方式自行补全——而这种补全通常不符合你的预期。

## 做法

把 Cron 的 instruction 当 API contract 写。我目前用的模板分五个部分：

```
1. 角色与边界  一句话限定工作范围
2. 输入说明    数据来源、读取方式、源失效时怎么办
3. 输出契约    格式、字段、长度、语言
4. 增量逻辑    什么算「新」，如何基于上次运行去重
5. 自检与兜底  输出前检查什么，失败时返回什么
```

一个实际示例：

```
你是信息筛选助手。每天 10:00 检查以下三个 RSS 源。
若某源无法访问，跳过该源并在输出中注明「源不可用」，不要编造内容。

输出为 Markdown 无序列表，最多 10 条，每条格式：
- [来源] 一句话摘要 (含原文链接)

去重：读取上次运行产生的文件 output/last_urls.txt，
其中出现过的 URL 一律跳过。运行结束后，
将本次全部 URL 覆盖写入该文件（每行一个）。

输出前自检：
1. 所有条目都来自给定源？不得引用源外信息。
2. 条目数是否 ≤ 10？
3. 是否包含旧链接？若有，重新去重。
```

这套模板的核心是：把「不确定性」逐项转换成「确定性」。数据源挂了怎么办、和上次重复怎么办、格式是什么——每件事都有明确回答，agent 就不需要自己猜。

## 踩坑点

**状态文件要处理并发。** 如果 Cron 间隔小于任务耗时，两次运行可能同时读写同一文件。别在指令里写复杂锁逻辑，agent 执行不好。指令里写一句「若读不到上次文件，视为首次运行」就够了。

**过度约束会杀死判断力。** 有人把规则细化到「标题必须 15 字以内」，结果 agent 纠结格式，忽略了内容质量。输出契约盯住结构，内容取舍交给 agent 判断。你写的是护栏，不是轨道。

**定期回看输出。** Cron 任务的输出不会自我改进。建议每周人工浏览一次历史记录，把反复出现的问题（比如永远漏掉某个指定源）回写进指令的新版本。指令要版本化管理，不要直接在线上改，否则你根本记不住改了什么。

**时间表述要显式。** 「今天」「本周」这类词在 agent 的时间上下文里可能与你预期的不一致。涉及时间时，写明时区和具体日期格式。

## 可复用建议

- 输出尽量用结构化格式（Markdown 或 JSON），方便后续管道继续消费
- 指令前三行就说明「失败时返回什么」，这是最容易被忽略的部分
- 用「排除法」补充说明，例如「不要包含电商促销内容」，比正面描述更有效
- 首次上线时手动触发一次，验证输出符合契约，再挂到 Cron 上

## 总结

Cron 任务写 instruction，本质是把「意图」翻译成「边界」。明确数据来源、输出契约、去重逻辑和失败行为，任务才能从「能跑」变成「稳定可用」。这套方法论不限于 OpenClaw——任何 Agent 定时任务的指令设计，都可以按同样的思路来写。
