# 自动化任务的幂等性设计：重复执行不翻车

## 背景：为什么一个“只跑一次”的任务会被执行两次

在 OpenClaw 这类 Agent 编排平台里，自动化任务通常串联了多个 MCP 工具、自定义插件和外部 API。任务的触发来源很杂：定时 scheduler、消息队列（如 Kafka/NATS）的重投、Webhook 重复推送，甚至人工在面板上点了两次“Run”。即使上游号称 exactly-once，落到 Agent 引擎这一层也经常变成 at-least-once。

没有幂等保护的自动化链路，就像没有刹车的传送带：每次重复执行都会累积副作用。一个发送通知的 Agent 可能给用户连发 5 条相同告警；一个工单创建插件可能生成一排重复 ticket；一个调用计费 API 的 MCP 工具可能重复扣款。这类问题在测试环境很难暴露，上了生产却频繁出现。

## 问题：三个典型反例

**案例 1**：一个监听 GitHub webhook 的 Agent，收到 `push` 事件后，通过 MCP 工具在 Notion 创建一条开发日志。因为 webhook 超时重试，同一事件被投递了两次，Agent 两次调用 MCP 工具，结果 Notion 里出现两条完全相同的页面。

**案例 2**：定时任务每小时拉取一次监控数据，调一个外部 API 生成报告。API 超时后 Agent 的重试逻辑没有检查上次调用是否已部分成功，直接重试，导致同一时段生成了两份报告，一份完整、一份截断，数据打架。

**案例 3**：OpenClaw 插件市场的一个“发送企微消息”插件，内部用消息队列异步消费。消费失败重试时，没有在插件层做去重，只是简单重发 HTTP 请求，用户持续收到重复卡片。

这些问题的共同根因：**任务缺少基于业务标识的幂等性设计**。

## 做法：为你的 Agent/Plugin/MCP 加上幂等保护

幂等性的本质是：同一个操作执行多次，产生的副作用和执行一次完全一样。实现路径有好几条，可以根据你的场景组合使用。

### 1. 优先选用天然幂等的操作

如果操作本身是幂等的，就不需要额外设计。比如：

- 数据库的 `INSERT ... ON DUPLICATE KEY UPDATE`，用业务唯一键做约束。
- Redis 的 `SET key value NX` ，只有不存在时才写入。
- REST API 更新资源，用 `PUT` 而非 `POST`，并传入资源 ID。

设计 MCP 工具时，尽量把接口定义成资源级的“创建或更新”（upsert），而不是只能创建。

### 2. 增加业务去重键（Idempotency Key）

为每个任务生成一个稳定的业务去重键，比如 `{event_source}_{event_id}` 或 `{task_type}_{business_key}`。执行前，先检查该键是否已处理过。

在 OpenClaw 里，这个逻辑可以放在 Agent 的记忆（memory）模块里，也可以用一个轻量的状态表：

```sql
CREATE TABLE task_execution_log (
    idempotency_key VARCHAR(255) PRIMARY KEY,
    status VARCHAR(20) NOT NULL,          -- PROCESSING, DONE, FAILED
    executed_at TIMESTAMP DEFAULT NOW()
);
```

执行流程变成：

1. 生成或提取幂等键。
2. 尝试插入一条状态为 `PROCESSING` 的记录（利用主键约束防止并发重复）。
3. 如果插入成功，执行业务逻辑；如果主键冲突，说明已有处理记录，直接返回根据状态处理（等待完成或读缓存结果）。
4. 业务成功后将状态更新为 `DONE`，失败则标明 `FAILED`，后续可触发人工修复或自动重试。

这个模式可以用一个通用的**幂等装饰器**（idempotent decorator）包裹关键函数，避免每次手写。

### 3. 分布式锁兜底，但不轻易当作主力

Redis 分布式锁（`SET lock_key unique_value NX PX 30000`）可以保证同一时间只有一个执行者。但它适合短时互斥操作（如避免并发更新同一资源），不建议作为全局幂等方案——锁超时、锁释放异常、网络分区都会让“保护”失效。把它用在**去重检查与业务执行之间**，弥补状态表方案未覆盖的极小时间窗口，会更实际。

### 4. 外部 API 调用的幂等

对接外部系统时，留意其是否支持幂等键。例如 Stripe 的 `Idempotency-Key` 请求头，AWS 的部分 API 有 ClientToken。即便对方不提供，我们也可以在调用方维护一个请求日志，把“已发起请求但未知结果”的状态记录下来，用定时查询对方系统来确认真正结果，而不是盲目重试。

## 踩坑点

- **幂等键不稳定**：如果业务 ID 会因为重新处理而变化（比如用时间戳生成），那去重就完全失效。幂等键必须从业务上下文里提取，比如上游消息的 offset、webhook 的 delivery ID，或者组合固定字段后 hash。
- **标记成功与实际完成不一致**：如果业务执行成功后，还没来得及更新去重表的状态，进程就崩溃了。下次检查发现状态还是 `PROCESSING`，可能误认为需要重新执行。解决方式有三种：一是业务操作本身设计成幂等，这样重复执行也无害；二是在业务操作里同时原子化地更新状态（如使用事务）；三是增加“处理超时”机制，将超时的 `PROCESSING` 记录重新入队。
- **唯一键冲突被静默吞掉**：使用 `ON CONFLICT DO NOTHING` 或异常捕获后直接返回成功，但没有检查原有记录的状态。如果上一个相同键的执行是失败的，直接返回成功会掩盖错误。务必处理冲突情况下的状态分支。
- **过度依赖全局状态**：幂等状态表如果是单点，会成为性能瓶颈。可以考虑按键分片，或者用本地缓存 + 分布式存储的混合方案，但是要注意一致性问题。

## 可复用建议

1. **抽象出一个幂等执行工具箱**：在 OpenClaw 的插件或自定义代码库里，实现一个 `IdempotentRunner`，接受业务函数和幂等键生成函数，内部自动处理检查、插入、状态更新。
2. **统一错误处理策略**：对于“已处理成功”的重复请求，直接返回缓存的执行结果（如果结果可以被缓存）；对于“正在处理中”的请求，要么返回 409 Conflict，要么轮询等待。
3. **监控幂等异常**：为跳过执行（hit）的次数、锁超时、状态不一致等情况增加指标，确保你设计的幂等保护没有悄悄把错误吞掉。
4. **MCP 工具设计审查**：在社区贡献 MCP 工具时，把幂等行为写进工具描述。例如 `create_page` 工具应说明“如果 page 已存在，返回已有对象”，而不是“报错”。

## 总结

给自动化任务加上幂等性，成本往往只在设计阶段多花几十分钟，但它能避免生产环境里大量“幽灵操作”和半夜被叫起的救火。核心思路很简单：**识别出稳定的业务身份，用状态表或唯一约束来保证相同身份只产生一次副作用。** 把这条原则落实到你的 Agent、MCP 工具、插件中，重复执行就不再是事故，而是安全的重试。
