## 背景

OpenClaw 的自动化任务里，重复执行是一件很常见的事：网络抖动导致工具调用重试、上游 webhook 重复推送、定时任务与手动触发叠加。很多插件写的时候"执行一次没问题"，一旦放进 agent 循环里跑，就会出现重复下单、重复发消息、重复创建记录。

这不是 agent 的错——重试是分布式系统的常态，幂等性才是任务要承担的责任。

## 问题

一个典型场景：你的 MCP 工具负责创建工单。OpenClaw 调用时超时了，于是重试了一次。此时第一次调用其实已经成功，第二次调用又创建了一张新工单。用户看到的是两张内容完全相同的工单，而你的日志里只有一条 timeout。

另一个场景：定时任务每 5 分钟同步一次外部数据源。某次同步耗时超过 5 分钟，下一个 tick 又启动了。两个进程同时写同一个文件，数据错乱。这类问题的共同点是：**操作不是幂等的**。

## 做法

幂等设计的核心是：让每次操作都携带一个"业务上唯一"的标识，服务端或本地存储只认第一次。

以 OpenClaw 插件为例，一个幂等的 MCP 工具可以这样设计：

```python
# 伪代码：幂等的 create_ticket 工具
def create_ticket(ctx, title, desc, idempotency_key=None):
    key = idempotency_key or hashlib.sha256(f"{title}:{desc}".encode()).hexdigest()
    existing = store.get(key)
    if existing:
        return existing  # 返回第一次的结果，不重复创建
    ticket = db.insert(title, desc)
    store.set(key, ticket, ttl=24h)
    return ticket
```

要点有三个：

1. **幂等键**：由调用方生成，或由内容哈希推导。不要用时间戳——同一秒内的连续调用会冲突。
2. **先查后写**：写入前通过唯一索引或状态存储检查。注意"检查-写入"之间要有原子性保障，否则并发下仍会重复。最稳妥的是数据库唯一约束，靠存储层兜底。
3. **任务级幂等**：在 OpenClaw 的 workflow 里用任务内容哈希作为 job ID。同一个输入，永远只产生一个执行记录。

## 踩坑点

- **webhook 的投递语义**：很多平台是 at-least-once，即"至少一次"。不要幻想上游只会推一次，一定要自己去重。
- **TTL 设置**：幂等键的存储要设过期时间，但别太短。MCP 工具的重试可能延迟到几分钟后，TTL 设 5 分钟很容易翻车。建议至少 24 小时，配合定期清理。
- **分布式锁不要乱用**：插件跑在单实例上时，文件锁就够了。多实例场景下文件锁会失效，优先用数据库唯一约束而不是 Redis 锁——锁有脑裂风险，唯一约束没有。
- **清理逻辑要幂等**：清理任务本身也会被重跑。删除操作天然幂等，但"删除后重建"不是。

## 可复用建议

- 在工具 schema 里显式暴露 `idempotency_key` 参数，并写清楚"重复调用会返回首次结果"。
- 对所有写操作先问一句：如果被执行两次，结果是否一致？不一致就需要幂等设计。
- 用固定格式的日志记录幂等键（如 `idem=key`），排障时能快速定位重试链路。
- 在 OpenClaw 配置文件里把超时重试次数调低，宁可失败人工介入，也不要静默重复。

## 总结

幂等性不是"高可靠系统"的专属话题。只要你的自动化任务涉及外部副作用——写库、发消息、调 API——重复执行安全就应该是一等公民。设计上无非是"唯一标识 + 先查后写 + 存储兜底"，但它能救你很多个深夜。
