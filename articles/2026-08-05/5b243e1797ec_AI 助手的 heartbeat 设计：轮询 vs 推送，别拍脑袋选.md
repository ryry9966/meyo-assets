## 背景

OpenClaw 这类 agent 真正部署起来，大部分时间是"等着有事发生"：盯一个共享目录、等队列里的任务、收 webhook 事件。这个"感知有事"的机制就是 heartbeat。设计不好，轻则空转浪费配额，重则漏事件、雪崩重连。这个选择没标准答案，但有一些务实的经验可以复用。

## 问题

轮询（Polling）简单：固定间隔去查。代价是 latency 和开销互为掣肘——间隔 1s 响应快，但上游可能限流；间隔 60s 省资源，但慢任务就达不到 SLA。

推送（Push：webhook/SSE/WebSocket）实时、省电，但引入连接生命周期管理：断线重连、消息顺序、丢事件。更麻烦的是，很多 agent 场景下推送事件到达时，handler 还在跑上一个任务，你不得不用队列缓冲——这本质上把推送变成了"带事件的轮询"。

## 做法

1. **先盘点触发源能力**。能发 webhook 的用推送；只能被查的（文件、老系统、无公网回调）用轮询，强行包装推送只会徒增复杂度。
2. **归一化事件**。不论哪种 transport，进 agent 前统一转成标准事件 schema（id、type、payload、时间戳）。agent 逻辑不感知轮询还是推送，切换只改适配器。
3. **混合兜底**。推送为主、轮询为辅。例如 WS 设 30s ping，另加 5 分钟轮询对账，找回断线期间漏掉的事件。
4. **参数化 heartbeat**。interval、timeout、backoff factor 三个参数暴露成配置，别写死。不同触发源对延迟的容忍度完全不同。
5. **消费与触发解耦**。事件进队列，worker 慢慢消费；heartbeat 只负责"知道有事"和"塞进队列"，绝不阻塞。

## 踩坑点

- **轮询间隔拍脑袋**：设 1s 被上游限流，比老老实实 10s 更糟。观察 upstream 的 rate limit 头再定。
- **重连不加退避**：服务重启时所有 client 同时重连，直接雪崩。指数退避 + jitter 是底线。
- **推送不是 exactly-once**：断线期间的事件，没有 replay 或对账机制就永久丢失。
- **忘记幂等**：at-least-once 下同一事件处理两次，副作用重复执行。agent 场景极易炸：重复扣费、重复发消息。
- **心跳被长任务阻塞**：一个 tool call 跑 60s，期间推送的 ping 全积压，连接被判定死。transport 层必须独立于业务执行，放单独线程/异步任务。

## 可复用建议

- heartbeat 三参数 + jitter（取 0.5~1.0 随机倍率）是底线配置。
- 事件生产端生成 UUID 幂等键，消费端去重（内存 Set 或 DB unique key）。
- 插件里暴露 heartbeat 状态：`last_poll_at`、`last_event_at`、`queue_depth`，排障时能省半天。
- 别过度设计。单人单机工具场景，30s 轮询 + 指数退避完全够用；只有快速响应是硬需求才上推送。

## 总结

推送和轮询不是二选一，是同一问题的两端。务实做法：触发源支持推送就用推送，默认配一个可配置的轮询对账兜底，统一成标准事件，参数化 heartbeat，加 jitter，加幂等。OpenClaw 生态里 agent 常跑在不可靠的个人设备上，越简单越不容易挂。
