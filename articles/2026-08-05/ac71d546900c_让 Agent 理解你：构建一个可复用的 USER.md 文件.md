## 背景：Agent 的“盲区”

今天的 Agent 工具链（OpenClaw、MCP 服务器、自动化工作流）已经可以读取文件、操作终端、调用 API，但它们普遍缺少一个关键信息：**“你是谁”** ——不是你的登录名，而是你的工作方式、代码偏好、项目上下文、沟通风格。

很多时候，我们在不同工具里反复配置类似的提示词：让 Cursor 不要自作主张拆分文件，让 Claude 用中文回答但保留技术术语英文，让终端助手记住我习惯用 `pnpm` 而不是 `npm`。这些信息分散在 `.cursorrules`、系统提示、项目 README 或临时对话里，一旦迁移工具、更换环境，就得重新“教”一遍。

更细的问题是：当 Agent 通过 MCP 读取你的代码仓库时，它能看懂代码，却不知道你最近在重构哪一部分、你为什么用某个诡异的临时方案、或者你希望别人接手时的解释方式。Agent 缺少一个稳定、跨会话、跨工具的自我描述入口。

## 方案：一个全局的 USER.md

灵感来自 GitHub 的 `profile/README.md`，但面向 Agent。我实践下来的做法是：在本地维护一个 `USER.md` 文件，作为个人向 AI 助手的“用户手册”。它不是项目层面的规则文件（那是 `.cursorrules` 或 `CONTRIBUTING.md` 的事），而是**关于你这个开发者的元信息**。

文件存放在一个固定路径，比如 `~/.agent/ USER.md`，然后通过各种机制让 Agent 在会话开始时加载，或按需引用。

## 步骤：构建并接入你的 USER.md

### 1. 写什么——内容的四个维度

经过几次迭代，我把内容收敛成这几个部分，避免变成流水账：

**身份与工作域**
- 主要技术栈（例如 Go / TypeScript，需注明常用版本）
- 当前关注领域（例如“云原生可观测性”），而不是笼统的“后端开发”
- 你在这个环境里的角色（个人开发者 / 团队 lead / 开源维护者）

**交互偏好**
- 回答语言（中文，但代码注释用英文）
- 输出风格（直白、少用比喻、不要先道歉再回答）
- 代码生成规则（默认使用 `async/await`、不随意拆分函数、擅自增加文件前先确认）

**环境与工具链**
- 包管理器、格式化工具、测试运行器
- 常用 shell alias（Agent 调用终端时可能会用到）
- 硬件/系统约束（比如无 GPU、磁盘空间有限）

**项目上下文**
- 当前活跃的 Git 仓库及粗略角色（主开发 / 临时调试）
- 最近关注的改动（“正在把认证模块从 JWT 迁移到 session”）
- 已知技术债务与临时妥协，避免 Agent 在错误的方向上重构

一个坏例子：“我喜欢用 React”。好例子：“React 项目默认函数组件 + hooks，状态管理用 zustand，避免在 render 内创建函数。”

### 2. 让 Agent 读得到——四种接入方式

以 OpenClaw 这类支持 MCP 和插件体系的环境为例，有几种接入路径：

**a) 静态系统提示注入**

在 OpenClaw 配置文件（如 `openclaw.yaml`）中，将 USER.md 的路径注册为一个静态资源，要求每次对话初始化时追加到系统提示。例如：

```yaml
prompts:
  user_context:
    type: file
    path: ~/.agent/USER.md
    inject: prepend
```

优点是全自动，缺点是每次 token 开销固定。

**b) MCP 资源服务**

写一个简单的 MCP server，把 USER.md 作为一个可读取的静态资源暴露。Agent 可以在需要时通过 `read_resource` 获取。适合只在用户明确要求个性化时才加载的场景，省 token。

**c) 按需 @引用**

在支持 `@file` 的客户端中，手动引用 `@USER.md`，适用于一次性对话或新工具测试。缺点是依赖人工操作，容易遗忘。

**d) Git 子模块包含**

如果 USER.md 放在 git 仓库中并作为子模块引入项目，CI/CD 或自动化 Agent 可以在上下文中直接读取。我为每个长期维护的项目都 `ln -s ~/.agent/USER.md ./docs/agent/` 这样本地引用。

实践中，我采用 a + b 组合：默认最小化注入（仅身份 + 交互偏好，约 200 tokens），复杂上下文通过 MCP 资源按需拉取。

### 3. 踩过的坑与应对

- **内容膨胀**：起初把所有工具的配置习惯都塞进去，迅速变成 2000 行。Agent 容易在长上下文中迷失重点。现在我只保留跨工具通用的部分，工具特定配置仍放在对应工具的配置文件里。
- **隐私泄露**：第一次写时不小心记录了某台内网服务器的 IP 和路径，虽然本地文件，但对话记录可能被云服务存储。建议用模板变量或占位符，并在同步时用 `.gitignore` 排除。
- **语言不一致**：Agent 看到中文环境可能切换为全中文回答，但我希望代码块注释保持英文。解决方案是在 USER.md 中明确：“**回答**用中文，**代码、注释、终端命令输出**保持英文。”
- **Agent 误解“当前关注”**：我曾写“重点优化数据库查询”，结果 Agent 在新的前端需求里也硬塞 SQL 建议。后来改为限定时间：“[短期] 优化用户表查询（至 2025-03-20）”，过期手动删除。
- **跨机器同步**：使用 private gist 或 dotfiles 仓库同步 USER.md，但要处理不同机器差异（工作机 vs 个人笔记本）。我采用分层：`USER.md` 放通用部分，`USER.local.md` 放特定于该机器的路径、alias，`USER.md` 在机器上生成时 `source` 本地文件。

## 可复用的工程建议

1. **模块化拆分**：用注释标记不同 section，方便脚本按需裁剪，比如一个脚本提取“交互偏好”注入轻量 Agent。
2. **自动生成片段**：写一个 cron 或 launchd 任务，每天拉取最近的 git commits 摘要、Jira 任务标题，追加到“当前关注”章节，减轻维护负担。
3. **版本控制与回滚**：USER.md 放在 git 里，每次修改都是 commit，能追溯何时引入了让 Agent 跑偏的规则。
4. **测试 Agent 理解度**：用专用对话测试“我的主要语言是什么”或“我用什么测试框架”，定期验证 USER.md 是否生效。
5. **社区互操作性**：尝试让 OpenClaw、Continue、Aider 等工具都能用同一份文件，避免维护 N 份。我们需要的是一份 “Agent 可读的 README”，不是又一门方言。

## 总结

USER.md 的思路不是新鲜事，但在 Agent 工具链碎片化的今天，它提供了一种低耦合、高复用的个人上下文方案。与其在每个新工具里逐步调教 AI，不如一次性把你的工作方式写成结构化文档，然后让 Agent 自己去读。关键是克制：只写真正影响决策的信息，保持更新，做好隐私控制。当 Agent 真的通过 300 行 markdown 了解了你的怪癖和偏好，你会觉得那些配置时间没白费。

目前这套方法在 OpenClaw + MCP 的组合上运行稳定，也给跨团队协作带来意外好处——新同事接手项目时，通过 USER.md 能快速理解我留下的技术决策背景，而不必考古聊天记录。
