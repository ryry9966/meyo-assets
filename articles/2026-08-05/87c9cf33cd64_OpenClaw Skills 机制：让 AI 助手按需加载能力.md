## 背景

OpenClaw 的 Skills 机制，本质上是把一组工具、脚本与提示词打包成独立单元，通过运行时注入上下文来扩展 Agent 能力。但很多人在初期会把所有技能一股脑丢进配置里，结果模型上下文越塞越满。

## 问题

技能全量注入会带来几个实际困扰：

- **上下文膨胀**：所有 SKILL.md 和示例脚本都进入系统提示，token 消耗线性上涨。
- **注意力稀释**：模型要在几十个技能声明中分辨当前任务该用哪个，误选率明显升高。
- **副作用冲突**：多个技能同时声明对同一目录的写权限，运行时互相覆盖。
- **响应变慢**：本地模型推理时，过长的系统提示直接拉高首token延迟。

所以问题不是“如何加更多技能”，而是“如何让模型只在需要时加载对应技能”。

## 做法：按需加载的配置路径

OpenClaw 的 Skills 加载可以拆成两层：**声明期**与**触发期**。

### 1. 技能目录结构

每个技能是一个独立目录，至少包含：

```
skills/
├── git_status/
│   ├── SKILL.md
│   └── run.sh
└── docker_clean/
    ├── SKILL.md
    └── clean.py
```

`SKILL.md` 中最重要的字段是 `description`，它不用于展示，而是给语义匹配器当**路由接口**使用：

```yaml
name: git_status
description: |
  查询当前仓库状态，包括分支、未提交修改、未跟踪文件。
  仅在用户询问仓库状态、改动、分支时触发。
load: on-demand
```

### 2. 触发方式

推荐组合使用两种加载策略：

- **语义匹配**：模型根据用户请求文本与 `description` 的相似度决定是否注入该技能。适合自然语言驱动的场景。
- **显式工具名**：在请求中直接提到技能名（如 `use git_status`）或匹配到预设关键字时强制加载。适合高确定性操作。

在配置中可以指定加载白名单，防止任意语义命中：

```yaml
skills_load:
  mode: selective
  preload: [basics, logger]       # 常驻技能
  on_demand_allow: [git_*, docker_*, file_ops]  # 只允许特定前缀技能按需加载
  deny: [admin_purge]              # 永远不自动加载
```

### 3. 运行时行为

当某个技能被触发，OpenClaw 会将整个技能目录作为临时上下文注入，并在本次会话结束时回收。这样既保有工具的全部能力，又不长期占用上下文窗口。

## 踩坑点

- **description 写得太宽泛**：比如只写“处理Git操作”，结果用户问“怎么看改动”也触发，加载了一堆无关脚本。建议写明触发边界：做什么、不做什么、在什么状况下不要触发。
- **技能目录塞了非必要文件**：扫描器会把目录内所有文本文件当作上下文注入，包括 README、旧笔记、日志。目录里只留声明文件和可执行脚本。
- **本地小模型语义匹配不稳定**：如果跑的是 7B 以下模型，语义匹配经常漏触发。这时候优先依赖显式关键字和工具名，而不是自然语言描述。
- **缓存导致旧技能残留**：修改 SKILL.md 后不重建上下文，模型仍按旧声明调用。在开发阶段建议关闭技能缓存或加版本号强制刷新。
- **忽略副作用冲突**：两个技能同时涉及写入 `.env` 时，必须在 SKILL.md 里声明 `conflicts`，否则随机覆盖难以排查。

## 可复用建议

1. **技能命名加前缀**：如 `git_status`、`git_diff`，便于在日志里按前缀过滤加载记录。
2. **为加载行为加审计日志**：记录每次技能被加载的时间、触发方式、是否成功执行。定期筛出“从未被触发”的技能，删掉或合并。
3. **把技术性行为外置**：技能脚本只做“获取数据/改变状态”，任何依赖模型决策的步骤写成独立提示词注入，而不是混在 SKILL.md 里。
4. **先白名单后扩权**：初期把 `on_demand_allow` 收缩到最少，再根据日志逐步放开，不要一开始就全量允许。
5. **预载技能控制在三个以内**：常驻技能只保持基础对话和通用工具，其余全部按需加载。

## 总结

Skills 按需加载的本质，是把“能力清单”变成“可检索的临时上下文”。设计技能时，最重要的不是脚本本身，而是描述和触发边界的准确性。先把命中率调好，再谈技能数量。
