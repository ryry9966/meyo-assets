## 背景：被动的工具，等不来主动的价值

大部分 AI 助手的使用方式仍然是“一问一答”：你扔一个问题，它给一个回复。即使接入了 MCP、把数据库和外部 API 暴露给了模型，本质上模型仍然在等待用户发起对话。这种被动模式在信息获取、代码解释等场景里够用，但一旦涉及**持续关注、事件驱动、提前干预**，就明显不够了。

举个工程化的例子：团队有多个仓库，每天的 Pull Request 需要有人盯着——是否长时间无人 review、CI 是否挂掉超过半小时、关键路径上的改动是否缺少测试。这些事情不是“用户想起来才去问 AI”，而应该是“AI 发现异常后主动通知甚至执行预案”。这就是 proactive 能力：**不等你开口，就把事情办了**。

下面是在 OpenClaw + MCP 环境下让 Agent 从被动变主动的一套工程化实践，包含架构、关键步骤、踩过的坑和可复现的建议。

## 问题拆解

要让 Agent 主动，需要解决三个核心问题：

1. **触发机制**：什么时候该行动？定时轮询还是事件驱动？
2. **决策与工具链**：Agent 如何判断“该做什么”，并通过 MCP 安全地操作外部系统？
3. **交付通道**：结果怎么推送到人（或自动执行），而不停留在对话界面里。

在具体实现中，这三个问题分别对应调度层、Agent 执行层和通知层。

## 实现步骤

### 1. 调度层：给 Agent 一个心跳

最简单的 proactive 触发方式是定时轮询。我们用系统 cron 或者 Airflow 这类调度器，每隔一段时间（例如每 5 分钟）向 OpenClaw 的 Agent API 发送一条固定消息，比如：“检查当前需要关注的事项并执行必要操作”。这条消息相当于给 Agent 一个“思考理由”，让它主动运行内部预置的检查流程。

对于事件驱动的场景（如 GitHub webhook、Prometheus AlertManager 告警），则可以用一个轻量 HTTP 触发器把事件结构化后注入到 Agent 的上下文里，例如：

```
事件：新 PR #342 已打开
要求：检查是否需要立即通知 review，并评估风险
```

Agent 接收到这条消息后，就可以基于其系统 prompt 里的规则来决定下一步行为。

### 2. Agent 执行层：让模型带着工具去巡检

在 OpenClaw 中为 proactive 任务设计的 Agent，其系统 prompt 需要明确三个部分：

- **角色和行为边界**：举例，“你是一个主动运维助手，可以读取 GitHub、发送 Slack 消息，但所有写操作（合并、关闭 PR）必须明确标注为‘建议’并等待人工确认。”
- **巡检清单**：列出每次触发后需要检查的事项，比如仓库列表、CI 状态、超过 2 小时无人 review 的 PR、数据库慢查询等。
- **工具使用规则**：通过 MCP 集成好的工具（GitHub API、数据库查询、Slack 通知）按顺序调用，每次只调用必要的数据，避免过度拉取。

一次典型的巡检流程如下：

1. Agent 接收到定时触发消息。
2. 调用 `list_open_prs` 获取所有开放 PR。
3. 对每个 PR 检查 `updated_at`、CI 状态、review 评论数。
4. 发现一个 CI 失败超过 30 分钟的 PR，并且没有近期的 review 活动。
5. Agent 调用 `send_slack_message` 发送一条包含 PR 链接和失败原因的通知到指定频道。
6. 生成一条摘要回复，记录本次巡检结果，便于后续审计。

这里的关键是 **Actionable 输出**：Agent 不能只生成一段分析文本，而是要把分析结果转化为工具调用，实际执行通知或标记操作。

### 3. 交付通道与安全护栏

通知层需要独立于对话界面。Slack、邮件、飞书等渠道是常见选择，但必须加上防骚扰逻辑：

- 同一类事件在 X 分钟内不重复告警（去重）。
- 高风险操作（如自动合并、重启服务）默认只给建议，不直接执行，除非在 prompt 中明确设定了自动化规则并且通过代码层做了二次确认。

我们在工具层封装了一个 `proactive_notify` MCP 工具，内部自带去重缓存和频率限制，避免 Agent 因为幻觉反复发送消息。

## 踩坑记录

**1. Agent 容易“过度主动”**
初期没有加去重时，Agent 在每次触发后都会对同一 PR 发送通知，十分钟内发了 8 条。解决方式是在工具层做幂等性判断，根据事件指纹（如 `pr_number + ci_status`）去重，并设置最小告警间隔。

**2. 上下文膨胀导致误判**
长时间运行的 Agent 如果不清理上下文，旧信息会影响判断。例如昨晚的 CI 失败已修复，但 Agent 仍基于历史上下文认为仍在失败。需要在每次巡检开始时重置核心上下文，或强制工具调用获取最新状态，而不是依赖对话记忆。

**3. MCP 工具调用耗时长，触发间隔需调优**
如果巡检一次需要调用 10+ 个 MCP 工具（例如检查 20 个仓库的 PR），总耗时可能超过 30 秒。触发间隔必须大于执行耗时，否则会造成任务堆积。使用异步队列或在 Agent 内部做并发控制可缓解。

## 可复用建议

- **从“只读 + 通知”开始**：让 Agent 只做信息收集和告警，不做任何写操作。跑通后再逐步放开低风险写操作。
- **使用结构化触发消息**：不要只发“运行巡检”，而是在消息里嵌入必要的参数（如时间窗口、仓库范围），方便调整巡检范围而不需改变系统 prompt。
- **把 proactive 逻辑做成可配置的“技能包”**：将巡检项、阈值、通知模板外挂为配置文件或 MCP 资源，Agent 在运行时读取。这样无需每次改 prompt 即可调整行为。
- **建立 Agent 执行日志**：每一次主动动作都应记录触发时间、调用工具、输出结果。这些日志既能用于调试，也能作为“AI 操作审计”的基础。

## 总结

Proactive 能力是把 AI 助手从“对话玩具”拉进“团队自动化工具链”的关键一步。在 OpenClaw + MCP 的架构下，实现它并不需要复杂的算法，而是需要工程化的设计：可靠的调度、明确的工具边界、安全的通知管道和充分的可观测性。

当 AI 开始在你开会时默默检查所有仓库的 CI，并在发现问题的第一时间弹出 Slack 通知时，你才会真正感受到 Agent 的工具价值——它不再是一个等命令的盒子，而是一个住在系统里的值班同事。
