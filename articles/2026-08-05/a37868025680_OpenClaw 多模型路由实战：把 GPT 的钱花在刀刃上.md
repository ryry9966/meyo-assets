## 背景

OpenClaw 这类 Agent 框架在真实自动化场景里，最终瓶颈往往不是 Agent 能力上限，而是单模型"既要又要"的成本困境。GPT 这类云端模型推理和工具调用可靠，但每次请求都是钱，且长上下文任务延迟明显；本地 7B-14B 模型免费、隐私可控，却在结构化输出和多步规划上频繁翻车。问题不是"哪个更强"，而是"什么时候用哪个"。

## 问题

多数人的默认姿势是全局配置一个 GPT 模型，所有任务都走云端 API。自己部署了本地模型的人，也只是手动切换，没有形成路由策略。结果就是：标题生成、标签分类这类小任务花了大钱；多步工具协作任务被本地模型搞崩。本质上是缺少一个"按任务特征分配模型"的决策层。

## 做法/步骤

1. **盘点任务类型**。把实际跑过的 OpenClaw 任务列出来，标注三个维度：token 消耗、容错率、隐私敏感度。
2. **起本地模型服务**。用 Ollama 或 llama.cpp 跑一个 8B-14B 的 Qwen 系模型，暴露本地端口，在 OpenClaw 的 settings 里注册为备选 provider。
3. **设硬路由规则**，按优先级判断：
   - 输入含密钥、客户数据、内网信息 → 强制走本地
   - 单步工具调用 / 短文本提取分类 → 走本地
   - 多步规划、跨工具编排、复杂代码生成 → 走 GPT
4. **加请求日志层**。记录每次请求走了哪个模型、token 消耗、是否重试，这是后面调优的唯依据。

## 踩坑点

- **本地模型工具调用格式不稳定**。OpenClaw 依赖 function calling 的结构化输出，7B 模型经常漏字段或把 JSON 注释掉。必须在路由层加 JSON schema 校验，失败就重试一次或升级到 GPT。
- **延迟错觉**。本地模型首次加载权重和 prompt 处理很慢，短任务和云端差不多，长上下文反而更慢。别迷信"本地更快"。
- **上下文窗口静默截断**。本地模型窗口小，配长日志时最危险——模型会"假装知道"截断后的内容。日志层要主动比对输入长度。
- **路由别做太重**。不要为规则引擎引入额外代理服务，OpenClaw 配置层的 if/else 完全够用，重路由本身会成为新的故障点。

## 可复用建议

- 决策可以用一句话概括：**任务需要超过 3 步推理，或输出必须被其它工具消费 → 用 GPT；否则先用本地。**
- 每周看一次 token 路由日志。如果 GPT 请求占比超 60%，说明路由太保守，把提取、分类类任务下放给本地。
- 本地模型优先选 Qwen 系，工具调用微调比通用 Llama 系在场控上省事得多。
- 不要把路由规则写进 prompt 让模型自己选。Agent 会倾向于一致选最强模型，必须做硬路由。

## 总结

模型路由不是"本地 vs API"的立场问题，而是成本与可靠性的约束优化。在 OpenClaw 里实现为硬路由 + schema 校验 + 日志回顾，约一周就能稳定下来。衡量指标只有一个：单任务综合成本（金钱 + 失败率 + 重试时间）降了多少。
