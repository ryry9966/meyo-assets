把 Agent 挂上 OpenClaw 的 Cron 调度，以为从此解放双手，结果第二天早上收到的不是日报，而是一句"我无法访问数据"或一段格式混乱的 JSON。问题往往不在模型，而在你给 Cron 写的 instruction。

Cron 任务和普通对话的差异在于：普通对话里用户在场，上下文可以补充，错了可以追问；Cron 触发时，Agent 是独自运行的。如果 instruction 没有把上下文、输入、输出、失败路径写清楚，Agent 就只能靠猜。下面是我踩过坑之后沉淀的写法，附一个可直接复用的模板。

### 一、先想清楚：Agent 在 Cron 里缺什么

- **时间上下文**：Cron 触发时 Agent 知道"现在几点"，但通常不知道自己该覆盖哪个时间段。
- **数据来源**：它不知道去哪拿数据。你说"汇总昨天的数据"，它可能去翻聊天记录，也可能自己编。
- **交付方式**：输出给谁看、用什么格式、发到哪个频道。
- **失败路径**：拿不到数据时，它应该停下来报警，还是编一个结果？

### 二、可复用的 instruction 模板

按六个区块来写：

```
角色：你是运营数据分析助手。

任务：生成一份昨天的业务日报，覆盖 00:00-23:59（UTC+8）。

数据来源：
- 主数据源：通过 MCP 工具 query_orders 拉取 orders 表
- 备用数据源：主库不可用时，调用 query_orders_backup
- 禁止从对话历史或记忆里推断数据

输出格式：
- 用 Markdown,包含三小节：总订单量、Top5 商品、异常波动（环比>20% 才列出）
- 数字保留两位小数；某商品无数据时写"无"，不要填 0
- 全文控制在 800 字以内

交付：发送到频道 #ops-daily，开头 @ops

失败处理：
- 两个数据源都不可用时，不要生成报告，只发一行告警
- 查询报错时原样打印错误，不要自己"修"数据
- 每个数据源最多重试 2 次
```

要点：每条都写"如果出现什么情况，应该做什么"，把决策权交给 Agent，而不是让它自由发挥。

### 三、踩过的坑

1. **时区问题**。服务器是 UTC，用户在国内。第一次跑出来的"昨天"永远差 8 小时。后来我在 instruction 里显式写明"昨天 = UTC+8 时区的自然日"。
2. **上下文残留**。某些场景下 Cron 任务会复用之前的会话，若上次对话是别的任务，Agent 会混淆。我在首行加了一句"忽略此前所有对话背景"。
3. **指令过细导致僵化**。输出格式写太死，数据字段一旦变化 Agent 就拒绝输出。改成"如果字段不存在，用'无'占位并注明"之后灵活多了。
4. **成本失控**。没写工具使用边界，Agent 会反复调用付费 MCP API 重试。现在我会显式写明重试上限。
5. **交付被截断**。日报在桌面端正常，在聊天工具里被截断。这不算 instruction 的锅，但写上"全文 800 字以内"能省很多事。

### 四、可复用建议

- **版本化**：instruction 放在项目目录下的 `cron_prompt.md`，用 git 管理，改一行有记录。
- **先手动触发一次**：上线前用同样的 instruction 手动跑一遍，过滤掉 80% 的问题。
- **留日志**：让 Agent 每次执行后输出一行 `EXEC OK/SKIP/FAIL` 到日志文件，方便排查。
- **用占位符传参**：不要把路径、时区硬编码在 instruction 里，用 `{{DB_PATH}}` 这类占位符，部署时替换。

### 五、总结

Cron 任务的核心不是"让 Agent 干活"，而是"让 Agent 在没有你的情况下把活干对"。把模板存下来，每次开新任务先填空、再手动验证，翻车率能降一个量级。
