## 背景

OpenClaw 的 memory 系统会把对话历史、用户偏好、任务状态持久化，`memory_recall` 就是检索这些记忆的入口。它的质量直接决定 Agent 是"记得"还是"假装记得"——用户说"上次我改过那个超时配置"，如果召回不到对应记忆，后面所有下游动作都是盲猜。

写这篇是因为群里反复有人问：召回到底该用语义搜索还是全文搜索？很多讨论把它当成二选一，但实际工程里根本不是这对关系。

## 问题拆解

先明确两种检索的适用边界：

- **全文搜索**（SQLite FTS5 / BM25）：做的是字面匹配，擅长精确值——参数名、文件路径、API key、命令。
- **语义搜索**（embedding + 向量检索）：做的是"意思匹配"，擅长模糊表达——"上次那个缓存问题"、"之前提过的降本方案"。

真实对话里两种需求同时存在，且会出现在同一个 recall 请求里。

## 测试方法与步骤

1. **搭两条链路**：全文用 SQLite 自带的 FTS5（避开额外依赖）；语义用 embedding 模型 + sqlite-vec 落地，不用单独起向量库。
2. **构造测试集**：从真实对话日志抽 50 条 recall 请求，分三类——精确型（含文件名/参数/路径）、语义型（只描述意思、不含原词）、混合型（既有精确词也有模糊描述）。
3. **定指标**：Top-5 命中率、首条命中准确率、P95 延迟。别只看"有没有召回"，要看"排在第一的是不是对的"。

## 实测结果

- 全文搜索在精确型请求上几乎 100% 命中；语义搜索在这类场景经常给出"意思对但名字错"的结果——比如把 `MAX_RETRY_TIMEOUT` 召回成长得很像的其他配置项。
- 语义搜索在语义型请求上明显占优，全文搜索基本报废。
- 混合检索（两路召回合并 + 轻量重排）在三种类型上的 Top-5 命中率比单独用任一方法高 15-20 个百分点，首条命中率的提升更明显。

结论很直接：单用任何一种，都会在你最需要它的时候翻车。

## 踩坑点

1. **别把向量检索当精确匹配用**。embedding 是近似搜索，对精确值做语义检索属于错误建模。
2. **时间衰减必须显式处理**。三天前和三个月前的记忆权重不该一样，纯向量检索没有这个维度，得自己在得分里加衰减因子。
3. **Chunk 大小直接决定质量**。OpenClaw 里一段对话切多大，比选哪个模型影响还大。块太大语义被稀释，块太小上下文丢失，实测 256-512 token 比较稳。
4. **FTS5 自带分词对中文不友好**。中文专有名词不自定义 tokenizer，匹配率会很难看，建议先跑一遍真实查询再决定要不要换 n-gram。
5. **重排阶段不能省**。两路结果直接拼接会导致某一路的高分噪声霸榜，加权合并 + 时间衰减后稳定很多。

## 可复用建议

- **做 hybrid，不做选边**：精确类记忆走全文，语义类记忆走向量，再合并重排。
- **按记忆类型定策略**：配置/凭证/路径类强制全文优先；用户偏好、历史决策类语义优先。不用统一走一条管道。
- **给每条记忆打时间戳**，在最终得分里乘一个衰减系数，简单线性衰减就够用。
- **把真实 recall 请求沉淀为回归测试集**，每次改检索逻辑或换 embedding 模型时跑一遍，避免"变好了还是变坏了"靠感觉判断。

## 总结

语义搜索和全文搜索是互补关系，不是竞争关系。OpenClaw 这类 Agent 的记忆类型天然混杂，单用任何一种都会在某个场景下静默失败。务实做法是混合检索 + 重排 + 时间衰减，先把链路跑通，再用真实请求持续回归调优。别追求花哨的模型和框架，检索工程里稳定 > 惊艳。
