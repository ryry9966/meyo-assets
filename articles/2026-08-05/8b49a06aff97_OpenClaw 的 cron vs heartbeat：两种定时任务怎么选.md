## 背景

OpenClaw 的自动化能力在很大程度上依赖定时任务机制。很多用户在配置好 Agent 后，第一件事就是想让它可以"主动干活"，而不是被动等指令。这时候，cron 和 heartbeat 就变成了两个绕不开的配置项。

但它们很容易被混为一谈——因为它们都干"定时"这件事。实际上这是两种语义不同的调度方式，选错了不会报错，但行为会非常别扭：要么任务不跑，要么反复跑。

## 问题：它们到底有什么区别

**cron** 是时间点触发，类似"每天上午 10 点跑一次"，用标准 crontab 表达式表达，核心是"日历时间"。

**heartbeat** 是周期轮询，类似"每 300 秒检查一次拉取请求"，核心是"间隔时长"。

一个典型的混淆场景：用户希望 Agent 每隔 5 分钟检查一次 GitHub issue，于是写了 cron 表达式 `*/5 * * * *`。表面看没问题，但 cron 依赖系统时钟的分钟对齐，如果你的进程在 `10:03:27` 启动，那第一次触发要等到 `10:05:00`，而不是启动后 5 分钟。更麻烦的是，如果 Agent 因为某种原因暂停了 10 分钟，cron 不会尝试补偿错过的任务；而 heartbeat 会，因为它在恢复后立即重新开始计算间隔。

## 两种方案的配置示例

以 OpenClaw 的配置文件为例：

```yaml
# cron：定义在具体的时间点执行
cron:
  - schedule: "0 9 * * *"        # 每天早上 9 点
    action: daily_report_generate

  - schedule: "0 */6 * * *"      # 每 6 小时的整点
    action: clean_temp_files
```

```yaml
# heartbeat：定义轮询间隔
heartbeat:
  interval: 300                  # 每 300 秒执行一次
  action: check_inbox_and_reply

  interval: 3600                 # 每小时
  action: sync_remote_context
```

## 踩坑点

**坑 1：heartbeat 是"尽力而为"**  
heartbeat 的触发依赖 Agent 的主循环处于活跃状态。如果 Agent 正在处理一个长任务，heartbeat 会被排队延迟。这不是 bug，而是设计如此——它不保证精确的周期。如果你的任务对时间敏感（比如必须在整点发报告），选 cron。

**坑 2：cron 不会兜底**  
cron 错过一个时间点之后就过了，不会补执行。如果你希望"错过也要补跑"，heartbeat 更合适，因为它的逻辑是"我睡醒了就再看一眼"。

**坑 3：把 cron 挂载在基于 heartbeat 的架构上**  
有些 OpenClaw 的插件内部用的是 heartbeat 循环，但插件配置里却暴露了 cron 字段。这会导致用户配了 cron 感觉"生效了"但实际是插件内部的 heartbeat 碰巧在那个时间段跑了一次。排查时一定要确认调度器真正消费的是哪个字段。

**坑 4：注意时区问题**  
cron 表达式依赖系统时区，而 heartbeat 不依赖。如果你在 Docker 容器里跑 OpenClaw，容器时区默认是 UTC，和宿主机可能不一致。建议在配置里明确 `TZ` 环境变量，或者直接让 cron 匹配 UTC 时间、不要写"9 点"这种依赖本地时区的值。

## 可复用建议

一个简单的选型标准：

- 任务需要指定"某个时刻"执行 → **cron**
- 任务需要持续监控/轮询 → **heartbeat**
- 任务必须在某个时间窗口内完成，且错过可接受 → **cron**
- 任务可以随时补跑，但不能漏 → **heartbeat**
- 一次配置、长期稳定，不想纠结时区 → **heartbeat**

另外提两个操作层面的建议：

1. **心跳周期别太短**。`interval: 30` 这种值会让 Agent 一直处于待唤醒状态，日志刷屏，CPU 占用升高，但对实际价值提升有限。建议最小 120 秒起步。
2. **两种机制可以混用**。比如用 cron 在每天凌晨做数据归档，再用 heartbeat 做白天的快速响应。这不冲突，但别让两类任务的 action 互相争抢同一个资源，注意加锁或让 Agent 任务编排时做好互斥。

## 总结

cron 和 heartbeat 是 OpenClaw 定时任务的两条腿，各有明确的适用场景。选型时先问自己："这个任务错过一个周期会怎样？"如果无所谓 → cron；如果有所谓 → heartbeat。关注语义差异，而不是纠结表达式怎么写，能帮你避开大部分坑。
