## 背景

OpenClaw 这类 Agent 框架的核心价值，在于把 LLM 从“聊天机器人”变成“能干活的主体”。但一个长期被低估的问题在于：**能力越多，系统越笨**。

当 Agent 挂载了文件读写、网络请求、数据库查询、浏览器控制等几十个工具时，模型每次推理都要把这些工具的描述塞进上下文。结果就是：token 被工具描述占满，注意力被稀释，指令遵循质量下降，响应延迟上升。这不是模型能力问题，是架构设计问题。

OpenClaw 的 Skills 机制为解决这个问题提供了一种路径：把能力拆分为可索引、可描述、按需激活的模块。本文将结合实际使用经验，梳理做法、踩坑与可复用建议。

## 问题

社区里常见的做法是“把一个 Agent 做成瑞士军刀”——所有能力常驻挂载，靠模型自己在推理时选择调用。这在工具少于 10 个时没问题，一旦超过 20 个，会出现三种典型症状：

1. **指令混淆**：模型把“生成周报”误触发为“调用日历工具”，因为工具描述在长上下文中相互污染。
2. **决策退化**：从“先思考，再调用”退化为“先调用，再后悔”，模型倾向于选择描述最长的工具，而非最合适的。
3. **成本失控**：每次请求携带所有工具定义的 token 开销，在 prompt caching 未生效时，成本线性上涨。

Skills 机制的核心思路是：**把工具和指令打包成“技能单元”，不常驻，而是在需要时通过检索将相关技能注入当前会话**。

## 做法

以 OpenClaw 工程实践为例，我建议按以下步骤落地 Skills：

### 1. 重新定义“技能”的粒度

不是把一个 Python 脚本塞进 Skills 目录就算完事。一个 Skill 应由三部分组成：

- **技能描述**（一句话说明能做什么、不能做什么）
- **触发条件**（明确告诉 Agent 什么场景该调用）
- **执行体**（脚本 / MCP 工具链 / 多步工作流）

粒度原则：**一个 Skill 只解决一类问题**，宁可拆细不要揉大。

### 2. 通过注册机制实现按需加载

在 OpenClaw 的配置中，将 skill 注册到对应的 profile 或 agent 配置里。加载时不是把全部 code 塞进上下文，而是将**描述文件（manifest）**注入，真正执行时才拉取完整实现。

自定义场景下，我常写的 manifest 结构：

```yaml
name: report_generator
description: 生成周报与月报，支持从 git log 或飞书文档提取数据
trigger: 用户说“周报/月报/report”时，或请求中提到“汇总本周工作”
deps: [git, feishu_mcp]
run: python generate_report.py --format=$1
```

关键在于：**描述文件要写成模型容易匹配的形式，而不是给人看的规范文档**。

### 3. 用路由规则承接技能加载

OpenClaw 的 Skills 加载不是靠 LLM 自己猜，而是靠一套路由规则。我在实践里通常把规则拆成两层：

- 第一层：关键词 + 意图匹配，命中后自动注入技能描述；
- 第二层：模型判定兜底，当规则不确定时，交给模型决定是否启用。

这种“规则优先、模型兜底”的设计，大幅降低了“模型临时想不出来调用什么技能”的尴尬。

### 4. 技能内外联动，保持状态隔离

在技能实现里，不要假设上一轮任务的状态还在。正确做法是：**每个技能独立读取输入文件、获取必要上下文、输出结构化结果**，然后由主 Agent 决定下一步动作。技能内不要自己维护“全局状态”——那是 Agent 主流程的职责。

## 踩坑点

以下问题我都在实践中踩过，写出来供参考：

**1. 技能描述写得太“幽默”**
一开始我给技能写描述时带了点比喻，比如“这个技能像瑞士军刀一样万能”。结果模型在遇到无关任务时也去匹配它——因为 LLM 对描述中的“万能”产生了误解。技能描述要**严肃、边界清晰**，不要用营销话术。

**2. 把常驻逻辑塞进技能**
Skills 机制解决的是“按需加载”，不是“另起炉灶”。如果你在技能里又跑了一个 HTTP server、常驻轮询、或全局消息监听，那等于把常驻恶果换了一个马甲。

**3. 过度拆解导致路由风暴**
有人把一个 git 操作用 6 个 skills 实现（commit、checkout、branch、merge、diff、log）。结果加载逻辑本身比执行逻辑还复杂。拆分的标准是**行为差异明显**才拆，git 系列只需要一个“git_operation”技能即可。

**4. 技能之间互相踩文件**
多个技能共用一个临时目录且不清理，会导致任务串台。一定要让每个技能工作在独立的临时目录中，并在结束时负责清理。

## 可复用建议

总结几条可以复用的经验：

- **Skills 数量控制在 15～20 个以内**，触发平均时长不应超过 1 秒；
- **描述文件优先覆盖“不做什么”**——负面示例比正面示例更有效，能显著减少误调用；
- **对每个技能写一个 3 行以内的测试用例**，验证“当用户说 X 时，是否加载技能 Y”；
- **把静态指令（如“说话语气”）放常驻配置，把动态操作（如“拉取数据”）放技能里**——这两者混在一起是常见反模式；
- 使用 OpenClaw 时，优先用 **MCP 作为技能的执行端，而非在技能里直接 curl**，前者有连接池和鉴权收敛，更稳定。

## 总结

OpenClaw 的 Skills 机制本质上是在做一件事：**把“模型需要什么”与“模型现在能用什么”解耦**。它不是传统意义上的插件系统——插件是给用户提供功能，Skills 是给模型提供“决策时的最小上下文”。

在实际使用中，这套机制的收益有两个层面：第一层是显性的，token 成本下降、响应速度提升；第二层是隐性的，模型在减少了干扰项之后，指令遵循质量明显变好，特别是面对复杂多步任务时。

工程化提示：从全量挂载到按需加载，切换初期要忍耐一段“模型偶尔找不对技能”的磨合期。此时优先检查描述文件，而不是急着加更多技能。少一点，往往就是多一点。
