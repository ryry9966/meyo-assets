## 背景

运营过社区的人都知道，定时发布内容是一件重要但极其枯燥的事。手动发帖不仅浪费时间，还容易漏发、错发。为了把这部分工作自动化，我基于 OpenClaw 搭建了一个 AI 发帖机器人，负责定时抓取本地知识库内容，生成帖子并发布到社区平台。

整个过程没有用到任何商业化的发帖工具，全部基于开源组件和 MCP 协议自己组装。下面分享整个架构设计和过程中比较棘手的踩坑经验。

## 问题定义

在动手之前，先明确要解决的核心问题：

1. **内容从哪来** —— 需要一个内容源，不能每次现编
2. **内容怎么生成** —— 需要 AI 将素材改写为适合社区传播的帖子格式
3. **怎么定时触发** —— 需要可靠的调度机制，而不是写死 cron
4. **如何发布** —— 需要处理平台登录态、接口调用、风控等问题
5. **如何防重复** —— 要保证同一个素材不会重复发两次

## 整体架构设计

机器人分为三层：

```
调度层 (Trigger) → 生成层 (Generator) → 执行层 (Publisher)
```

- **调度层**：使用 OpenClaw 内置的 Scheduler 能力，配置每日固定时间触发任务。任务触发后创建一个任务上下文，传入当天的日期参数。
- **生成层**：通过 MCP 连接本地 Ollama 模型，将知识库中的原始素材（技术笔记、FAQ）改写为社区帖子格式。这层不直接对接外部 API，而是通过 MCP Tool 调用。
- **执行层**：封装了社区平台的 HTTP API，负责登录、发帖、校验结果。

三个层次通过 OpenClaw 的 Agent 编排逻辑串联：调度事件触发 → Agent 调用生成 Tool 产出内容 → 写入待发布队列 → 调用发布 Tool 执行发送。

```python
# 核心编排逻辑（简化）
async def run_daily_post_job():
    materials = await mcp_knowledge.fetch_material(days_ago=1)
    post_content = await mcp_ollama.generate_post(materials)
    result = await publisher.send(post_content)
    await state.mark_posted(post_content.fingerprint)
```

## 关键踩坑点

### 1. 平台登录态是最大隐患

社区平台的 API 并不支持长期有效的 Token，登录态大约几小时就会过期。第一次部署时，早上八点调度任务正常运行，但到了下午任务就提示 401。

**解决方案**：把登录逻辑放在执行层内部，每次发帖前先检查凭证有效性；同时用独立文件存储 Token，配合过期前 10 分钟自动刷新机制。不要在 Agent 指令中硬编码 Token，也不要让 Agent 去处理登录，这会让调试变得非常困难。

### 2. 发帖失败是常态，必须做失败重试

一开始图省事，发帖失败就直接抛异常，让整个任务失败。实际上社区平台的 API 经常有 5xx 错误，尤其是发帖高峰期。直接失败会导致当天内容丢失。

**解决方案**：加入三级退避重试（1 分钟、5 分钟、30 分钟），超过三次才标记失败。同时将失败邮件内容保存到本地，方便人工补发。

### 3. 内容质量不稳定

用 Ollama 生成的帖子经常会出现"过度标题党"的问题——原素材是很平静的技术描述，生成的帖子却变成"震惊！这个技巧居然如此高效"这种风格。这对于技术社区很不合适。

**解决方案**：在 Prompt 中加入明确的风格约束，并且将约束条件放在 system prompt 而不是 user prompt 中。另外增加一个后处理步骤：用正则检测禁用词列表，命中则重新生成。

### 4. 并发调度问题

如果调度任务执行时间过长（比如 Ollama 推理慢），而下一个触发时间到了，会出现两个任务同时运行的情况，导致内容重复发布。

**解决方案**：在任务开始时写入一个 lock 文件，结束时删除。调度器执行前先检查 lock 是否存在，存在则跳过本轮。

### 5. 帖子指纹去重不彻底

最初用标题做去重键，但 AI 生成时标题常有微小变化（标点、空格、大小写），导致同一素材生成的两篇帖子标题不完全一致，去重失效。

**解决方案**：对正文内容做 SimHash 计算，生成 64 位指纹，两两比较汉明距离，小于等于 3 视为重复。

## 可复用的建议

1. **分层设计不要耦合**：调度、生成、执行三个模块完全解耦，任何一个模块可以独立替换。后续想换 Claude 或其他模型，只需要改生成层的 MCP 配置。
2. **所有外部依赖都要幂等**：无论是发帖还是内容生成，都要设计成可重试且不产生副作用的操作。
3. **做好日志和状态记录**：每个任务都输出结构化日志（JSON Lines），便于事后排查。任务状态写入 SQLite，方便查询。
4. **灰度上线**：先在一个低流量平台试运行两周，确认稳定后再推广到主平台。我在测试过程中至少发现三个只在真实环境中暴露的问题。
5. **充分利用 MCP 协议**：不需要自己写复杂的 Agent 逻辑，把能力做成 Tool，交给 OpenClaw 编排，可以省下很多开发时间。

## 总结

整个项目从零到稳定运行大约花了三周时间。架构本身并不复杂，真正的复杂度来自外部系统的不确定性——登录态过期、接口限流、返回格式变化、平台风控策略调整。这些坑很难通过看文档避免，只能在真实环境中逐步暴露并修复。

这套机器人的核心价值在于：把"人工重复劳动"替换为"可配置的自动化流程"，同时保留了对异常情况的人工介入通道。如果一个自动化系统不能优雅地失败，那它就不应该上线。
