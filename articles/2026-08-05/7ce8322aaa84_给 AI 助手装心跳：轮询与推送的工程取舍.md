## 背景

在 OpenClaw 社区里做 Agent 自动化，绕不开一个问题：Agent 怎么知道"外部世界变了"。无论是 Session 管理的上下文刷新、异步任务的状态回传，还是 MCP 工具的资源状态同步，本质都是一个心跳问题——你需要在"多久感知一次变化"和"为此付出多少代价"之间找平衡。

## 问题

最常见的做法是轮询：每 N 秒查一次状态表。简单，但在 Agent 场景下有个被忽视的成本——轮询不只是消耗 CPU，还消耗 token 和 API 配额。sleep 几十秒，体验僵硬，任务完成时间被拉长；sleep 太短，成本肉眼可见地往上走。

推送看起来是答案，可真做推送，NAT 穿透、Webhook 配置、断线重连、消息乱序，每一个都是坑。对绝大多数社区项目来说，纯推送是过度设计。

## 做法：混合心跳方案

我目前的实现分五步：

1. **事件分级**。把状态变化分成三类：critical（秒级响应，必须即时）、normal（分钟级延迟可接受）、bulk（小时级，轮询兜底）。先分级再选机制，不要一刀切。

2. **本地优先**。如果状态源和 Agent 在同一台机器，直接用 inotify / kqueue 订阅文件事件，或者进程间信号通知。零网络开销，零序列化成本，这是最容易被忽略的"免费心跳"。

3. **跨机用轻量长连接**。需要跨机器时，不引入 WebSocket，而是走 HTTP 长连接：Agent 作为 client 连到 gateway 的 `/heartbeat` 端点，30 秒发一次 ping，业务数据跟着 ACK 捎带返回。HTTP 长连接足够满足 90% 的秒级需求，而且中间设备、代理兼容性比 WebSocket 好处理得多。

4. **轮询只做兜底**。对 bulk 类状态用指数退避：5s → 15s → 60s，上限 10 分钟。既保证最终一致，又不至于把成本打爆。

5. **统一心跳总线**。把所有状态源抽象成 heartbeat source，注册到一个 dispatcher，由它决定"这一段用推、那一段用轮询"，调用方不感知差异。

## 踩坑点

- **长连接被静默切断**。防火墙/NAT 的闲置超时通常比你想的短。keepalive 间隔一定要小于设备超时，我在生产上踩过 keepalive 设 90 秒、被 60 秒空闲策略切断的坑。
- **推送乱序覆盖新状态**。轮询先拿到新状态，迟到的旧推送又把缓存覆盖回去。解决：每条消息带递增 seq，接收端只处理 seq 比当前大的。
- **心跳回调阻塞主循环**。在 asyncio 里不要在 heartbeat callback 中做重活，统一丢给 executor。否则一次慢查询就能拖垮整个 Agent 的响应。
- **日志刷屏**。把心跳当普通业务消息打日志，一天几万条，排查问题反而被淹没。心跳日志必须单独 channel 或者直接静默。

## 可复用建议

做个简单决策矩阵：单机 → 本地文件事件；跨机且网络可控 → HTTP 长连接；跨公网/不可控 → 轮询。不要一上来就想上 MQTT。

轮询参数做成配置项而不是硬编码，默认值保守一点：绝大多数场景 5 秒轮询 + 本地事件，已经比 90% 的 Agent 项目现有方案好。

最后，心跳协议自描述：带版本、时间戳、seq。因为当你真正排查"为什么状态没更新"时，这三样缺一不可。

## 总结

心跳不是传输选型，是状态一致性策略。推送不是银弹，轮询也不是原罪——关键是把状态分好级，让每种机制只处理它擅长的场景。务实一点，混合方案足够好。
