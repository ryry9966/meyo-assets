## 背景

随着 OpenClaw、MCP 协议和各类自动化插件的普及，Agent 不再只是“聊天助手”，而是能直接操作本地工具、访问内部知识库、甚至代表用户在社区发言的自主实体。这一能力大幅提升效率的同时，也带来一条极易被低估的安全红线：**Agent 完全可能在毫无恶意的情况下，将你的敏感工作流、内部配置甚至未公开的认知片段，原样输出到公共社区。**

问题并不在于模型本身“想”泄密，而在于工程链路上的疏忽。我们团队在逐步把内部运维、Issue 分类和部分社区回复交给 Agent 处理的过程中，多次踩坑——从 MCP Server 无差别透出本地文件，到 Prompt 中误嵌临时 Token，再到输出审查放行了一段包含内部服务名称的“礼貌回复”。本文不聊理论威胁模型，只谈**可复现的工程化防护做法**。

## 问题场景：信息是如何逃逸的？

典型泄密路径有四种：

1. **知识库过度暴露**  
   Agent 对接了内部 Wiki 或 Confluence 后，用户在社区提问“这个功能怎么实现”，Agent 可能直接引用内部设计文档，甚至把仅有内部可见的 API 端点粘贴出来。

2. **工具调用结果直出**  
   通过 MCP 工具链调用本地脚本、查询数据库后，Agent 将原始结果未经脱敏就插入回复。比如执行 `kubectl get secrets` 后把 base64 字段打印出去。

3. **Prompt 中携带临时凭据**  
   一些自动化流程会把动态生成的 Token、Session ID 作为参数拼进 System Prompt，Agent 在回复时可能顺带输出这些信息。

4. **社区回复模板泄漏内部语境**  
   为“省事”预先写好的回复草稿含有团队内部黑话、未发布项目代号或组织架构信息，Agent 只是按规则匹配并发送，却没想到语境不对。

真正的危险在于，这些问题代码中没有任何报错，Agent 行为看起来完全正常——直到有人发现内部信息已经出现在公网。

## 做法：构建三层防护

我们采用的方案不是限制 Agent 能力，而是在数据流动的关键节点上加入显式检查。

### 第一层：MCP 工具侧“最小输出”

MCP Server 在暴露工具时，不直接返回原始数据，而是做**结果脱敏**。例如一个查询内部服务列表的 tool，只返回 `service_name` 和 `status`，绝不让 `internal_ip`、`secret_name` 等字段穿过 tool response。

具体实现上，我们在 MCP 工具的 handler 里加了一层 `sanitize_output` 函数，通过 JSON Schema 定义白名单字段。同时，对可能包含路径、密钥格式的输出做正则检查，匹配到疑似敏感内容时替换为 `<REDACTED>`。

**踩坑点：** 起初对脱敏强度估计不足，以为只去掉 `password` 字段就行。后来发现日志里也会记录 HTTP Authorization 头，而 Agent 恰好会把日志摘要当成上下文。因此脱敏不仅针对 tool 返回，还要考虑日志、异常信息等旁路通道。

### 第二层：提示词与知识库隔离

内部知识库和面向社区的提示词必须物理分离。我们在 OpenClaw 中设计了两个独立的 Agent 角色：
- `internal-analyst`：可访问内部知识库、运维 MCP，输出仅走内部审计频道。
- `community-responder`：只加载公开文档片段和脱敏后的结构化信息，完全不感知内部地址。

二者之间通过一个**受控的摘要管道**通信：内部分析 Agent 产出的结论先经过人工/脚本审核，再转为一条“外部可用的简短答案”推给社区 Agent。这样即便是自动化链路，也始终存在一次显式的“信息降级”。

**踩坑点：** 直接用同一份提示词模板，仅仅把 `context` 替换为脱敏版本是不够的。因为内部对话历史可能已经泄露了线索。必须保证 community-responder 的会话上下文是完全独立的，每次回复前清空与内部 Agent 的关联记忆。

### 第三层：输出端实时检查

社区回复在真正发送前，强制走一个轻量级检查器。这个检查器不是依赖 LLM，而是规则 + 模式匹配：

- 检验是否包含内部域名（如 `*.internal.corp`）。
- 检验是否出现 base64 长度超过阈值的连续字符串。
- 检验是否出现了已知的私密环境变量键名。
- 对比内部文档指纹列表，如果回复段落与内部文档高度相似则阻断。

这一层直接集成在 OpenClaw 的输出管道中，作为 `before_send` hook 运行。命中任何一条规则，消息会被保留在草稿箱并告警，等待人工确认。

**踩坑点：** 检查过于严格会导致正常回复频繁被误杀。调整方式是把规则分为“硬阻断”和“软提醒”。例如包含 `internal` 字样直接阻断；而长度稍长的 base64 只做软提醒，结合上下文进行二次判断。

## 可复用建议

经过多次事故复盘，有几点可以快速落地到任何使用 Agent 的项目中：

1. **永远不在 Prompt 中拼接明文凭据**  
    用短期 Token，且通过环境变量注入并在构建 Prompt 时显式排除。我们的做法是在渲染 Prompt 前统一过滤所有包含 `SECRET_` 前缀的变量。

2. **MCP 工具遵循“返回能力而非数据”原则**  
    工具输出应偏向查询结果的状态摘要，而不是完整数据行。比如返回“共 12 条记录，状态正常”，而不是直接吐出 12 行详情。

3. **社区 Agent 使用独立的沙箱环境**  
    网络出口应限制为仅能访问公开 API，不能反向连接到内网服务。在 Docker/K8s 部署时，通过 NetworkPolicy 严格隔离。

4. **审计日志保存所有发送内容**  
    无论是否阻断，所有通过社区 Agent 发出的消息都要持久化，方便事后追溯。这比事后去翻 CDN 快照靠谱得多。

5. **定期做“红队演练”**  
    自己扮成用户，诱导 Agent 泄露信息，验证防护是否生效。我们在演练中发现了至少两次可以通过“假装是新同事”来套取内部流程说明的缺口，后续针对性地限制了回复范围。

## 总结

Agent 安全不是给模型戴上镣铐，而是在自动化流程中明确界定信息的可达范围。实践下来，最有效的方法仍然是古老的原则：**最小权限、分层控制、审计兜底**。要让 Agent 在社区里聪明地回答问题，就必须确保它在开口之前，已经不具备吐出内部信息的能力。构建一套可复用的脱敏与审查管道，远比赌模型能“自觉”保密可靠得多。
