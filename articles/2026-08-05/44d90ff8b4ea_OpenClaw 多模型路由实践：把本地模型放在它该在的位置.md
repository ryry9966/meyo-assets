## 背景

OpenClaw 的 Agent 链路里，模型调用是最大的变量：既影响响应质量，也影响成本。全量走 GPT，一个小型分类任务就花掉几美分，一天下来成本可观，而且数据都要过云；全量走本地模型，复杂推理质量又撑不住。所以需要路由——这不是"选哪个模型"的问题，而是"什么任务该花这个钱"的问题。

## 问题定义

OpenClaw 里有三类典型任务：

1. **低复杂度**：文本分类、关键词提取、JSON 清洗、标题生成——GPT 和 7B 本地模型差别不大。
2. **中复杂度**：摘要、情感分析、结构化抽取——本地模型能跑，但需要足够的 prompt 约束和输出校验。
3. **高复杂度**：多步规划、工具选择、代码生成、跨上下文推理——本地模型目前顶不住。

路由的本质，是把任务准确分进这三档，并让系统在本地失败时能无害升级或降级。

## 做法

我目前的配置分四步：

**1. 双 Provider 配置**
OpenClaw 里同时启用 OpenAI 和 Ollama 两个 provider。OpenAI 负责主对话和 planner，Ollama 负责工具链内的小模型调用。

**2. 按 Tool 粒度绑定模型**
OpenClaw 支持为不同 skill/tool 指定独立的 model 配置。我把网页抓取、RSS 解析、文本预处理相关的 skill 全部绑到本地模型（qwen2.5:7b-instruct），因为这些任务对输出质量要求不高，速度才是刚需。

**3. 写一个 routing plugin**
以 Plugin 方式注入工具链，做两级路由：
- 先走规则：能用正则 / JSON Schema 解决的文本操作，直接本地处理，甚至不调模型。
- 再走本地模型：分类、实体识别、格式转换，交给 Ollama。
- 输出校验失败或本地模型超时，自动升级到 GPT-4o 重跑一次。

**4. 设置超时和降级**
本地模型在纯 CPU 机器上跑 7B，单次推理可能要 5-10 秒。我给本地调用设了 15 秒超时，超时直接走 GPT，防止一个分类任务拖垮整条链路。

## 踩坑点

- **本地模型输出格式不稳定**。最典型的坑：让 7B 模型输出 JSON，十次里有两三次会多出反引号或换行，直接传给下游插件就崩。必须加 schema 校验 + 最多两次重试。
- **上下文窗口限制**。qwen2.5:7b 的 32K 上下文在长网页截取后经常不够用。做法是处理前按段落切 chunk，只把相关片段送入模型。
- **知识时效性问题**。本地模型的常识和能力明显落后，让它处理"今天是什么日期"或需要最新资讯判断的任务，结果不可信。
- **不要让本地模型做 tool planning**。我实验过让本地模型决定调用哪个 MCP server，结果一半时间选错工具，不如规则 + 关键词匹配靠谱。

## 可复用建议

1. **按任务类型路由，而不是按模型能力路由**。先给任务分类（规则可解 / 本地可解 / 必须云端），再落到模型。
2. **本地模型区只放"格式敏感度低 + 上下文短"的任务**：分类、抽取、格式化、简单改写。
3. **云端模型区放"推理链长 + 需要最新知识"的任务**：规划、调试、代码生成、工具选择。
4. **所有本地模型输出都要过一道校验层**，不要直接信任原始输出。
5. **记录路由日志**：每次调用的模型、耗时、token、重试次数。跑两周后你会得到数据：哪些任务本地模型在反复失败，哪些任务其实白白浪费了 GPT 的额度。

## 总结

OpenClaw 的多模型路由没有银弹，核心原则是：能规则就不调模型，能本地就不上云，必须用云的就别省。把 80% 的高频低价值任务压到本地模型，把 20% 真正需要推理深度的任务留给 GPT，成本和质量可以同时保住。
