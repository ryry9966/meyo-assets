## 背景

用 OpenClaw 跑自动化任务的人，迟早会面对同一个疑问：我给了它 shell 权限，它就差一把真正的"核弹开关"了。尤其是那些让 Agent 操作文件、批量改名、清理日志的朋友，深夜盯着终端，心里难免打鼓——它会不会一个 `rm -rf` 把我三年的项目干没了？

这个担心合理，但多虑。OpenClaw 的安全模型在设计上把"致命操作"挡在了最外层，原理值得每个自动化玩家搞清楚。

## 问题：Agent 的破坏半径

大部分人对 Agent 文件安全的想象是"信任边界"。你在本地写了四五个自动化任务，Agent 上下文一长，可能自己都忘了刚才在哪个目录。而传统 CLI 工具的破坏半径 = 当前用户权限，`rm -rf /some/typo` 就是一场事故。Agent 比人更不可靠的地方在于：它不会手抖，但会"想当然"。

## 做法/步骤：三层模型拆解

OpenClaw 的 sandbox 不是一层，而是三层叠加。

### 1. 文件系统围栏（Jail）

OpenClaw 会给每个 Agent 实例分配一个独立工作目录，作为它的"虚拟根"。Agent 感知到的 `/` 并不是宿主机的 `/`，而是 jail 目录。目录映射在配置里显式声明：

```yaml
sandbox:
  jail: ./workspaces/agent-a
  mounts:
    "/data/ref":  { host: "~/refs", mode: "ro" }
    "/tmp/out":   { host: "~/outputs", mode: "rw" }
```

jail 之外，Agent 不可见、不可枚举、不可写入。它以为自己删了 `/etc/config`，实际上只是删掉了 jail 里的同名文件。

### 2. 权限分层

文件操作被分为三级：

- **read-only**：默认只读，能看不能写；
- **write**：可写，需会话内授权或白名单路径；
- **destroy**：删除、覆盖、格式化，必须每次显式批准。

换句话说，Agent 想干"坏事"，必须先经过一次人机确认。除非你把权限调成 auto-approve，并且路径是真实挂载的宿主目录，否则它跨不过这道门。

### 3. 挂载即边界

jail 里只有你显式挂载的目录是真实的。凡是 `mode: ro` 的挂载，Agent 连 `touch` 都做不到；`mode: rw` 挂载下的删除，依然受 destroy 权限拦截。所以"Agent 无法删除文件"更准确的说法是：**Agent 无法删除任何未经你双重确认的宿主文件**。

## 踩坑点

- **坑 1：符号链接逃逸**。Agent 可能尝试在 jail 里创建 symlink 指向宿主真实路径，配合 write 权限写入。对策：不要绕过 sandbox 的 symlink 解析校验，升级到最新版本，并定期检查配置。
- **坑 2：把 `rw` 当成"安全"**。rw 挂载目录里 write 权限确实能覆盖文件。正确的做法是把 rw 目录缩小到最小范围，而不是把整个 home 挂进去。
- **坑 3：自动批准的积木效应**。为了跑批处理把 destroy 设为 auto，等于亲手拆掉了最后一道保险。临时需求用一次性的会话级授权，别写进全局配置。
- **坑 4：多实例共享 jail**。两个 Agent 共用一个工作目录，A 的"清理临时文件"可能把 B 正在写的中间产物删掉。每个任务应独立 jail。
- **坑 5：恢复预期**。jail 内的删除是真实的，不会进宿主回收站。务必在宿主侧给重要目录做快照或版本控制。

## 可复用建议

1. **默认只读，按需升权**。挂载时先给 `ro`，跑挂再升级为 `rw`，而不是反过来。
2. **每个自动化任务独立 jail + 独立日志**，出问题好定位。
3. **destroy 永远走会话确认**。批量删除场景，让 Agent 先输出待删清单，再逐项确认。
4. **在 CI 里加一个"权限审计"任务**，检查配置里有没有意外出现的 rw / auto-approve 挂载。
5. **对关键路径做宿主侧保护**（目录只读、版本控制），防 Agent 也防人。

## 总结

OpenClaw 的沙箱把"破坏能力"变成了一项显式授权的特权，而不是默认环境变量。它删不掉你的文件，不是因为它善良，而是因为架构上就不允许它跨过那道门。理解这三层模型——jail、权限分层、挂载边界——你就能在"放权"和"安全"之间找到自己的平衡点。
