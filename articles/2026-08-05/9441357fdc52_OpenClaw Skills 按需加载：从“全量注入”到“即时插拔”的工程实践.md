## 背景

用 OpenClaw 跑 Agent 一段时间后，一个共性问题浮出水面：`skills/` 目录里攒了十几个技能，但 Agent 的 system prompt 被撑得越来越臃肿。命令调用变慢、上下文被无意义消耗，更关键的是，Agent 在规划时开始“乱点技能”——明明只需要查日历，它却把文件整理的 skill 也读了一遍。

OpenClaw 默认的行为是把所有启用的 skill 定义注入上下文，让 Agent“知道”自己有哪些能力。这在技能少的时候没问题，技能一多，就成了噪声。

## 问题：全量注入的三个成本

1. **Token 成本**：每个 skill 的描述、参数 schema、触发条件都占用上下文窗口。技能越多，留给实际对话和工具输出的空间越少。
2. **决策成本**：Agent 的规划器需要在更多选项中做选择，无关 skill 的存在会显著增加错误调用的概率。
3. **维护成本**：改一个 skill 的描述，你要重新评估它对所有其他 skill 的影响，因为 Agent 是同时看到全部的。

## 做法：配置按需加载

OpenClaw 在 skill 的 `SKILL.md` 中支持元信息配置，核心思路是**让 Agent 只看到与当前任务相关的 skill**。

最简配置如下：

```yaml
---
name: weather_query
description: 查询指定城市的实时天气。当用户提到天气、气温、降雨、出行准备时使用。
autoExecute: false
---
```

关键字段：

- `name`：唯一标识符
- `description`：写清楚“何时用”和“何时不用”，这是按需匹配的判定依据
- `autoExecute: false`：关闭自动执行，改为按需加载

在 `openclaw.yaml` 中开启按需模式：

```yaml
skills:
  mode: on-demand
  registry: ./skills
```

这里有一个隐藏配置项，`lazyLoad: true`，它会延迟 skill 的加载时机，直到意图匹配成功。

## 踩坑点

**1. 关键词匹配过于粗糙**

早期我把 description 写成“处理天气相关请求”，结果用户说“今天适合穿什么”也触发了天气查询。改成意图化描述后（“查询城市实时天气，涉及降雨、气温、风速”），误触发率明显下降。

**2. 按需加载后 Agent 不知道“怎么用”**

`autoExecute: false` 后，Agent 确实只在需要时加载 skill，但它加载完并不知道内部逻辑。坑在于：**每个 skill 需要在 SKILL.md 里写清“包含哪些脚本/命令/参数”**，否则 Agent 加载了定义却不知道怎么执行。别省这一步。

**3. 依赖关系被裁剪**

某个 skill 依赖另一个 skill 提供的 Python 工具函数。按需加载后，被依赖的 skill 没被触发，运行时直接报 ModuleNotFoundError。解决方法是把共享工具抽到 `scripts/` 或独立 MCP 服务里，别藏在 skill 内部。

**4. 切换配置后没重启**

改完 `openclaw.yaml` 的 `lazyLoad` 后，热重载并不总是生效。CLI 里确认配置加载完毕后再跑任务，省去无意义的排障时间。

## 可复用建议

1. **统一描述格式**：每个 skill 的 description 采用“能力 + 触发场景 + 反例”三段式。例如：“查询 GitHub 仓库信息。当用户提及仓库、star、issue、PR 时触发。不处理代码搜索。”
2. **按领域分目录**：`skills/communication/`、`skills/devops/`、`skills/data/`，配合按需匹配，避免同名冲突。
3. **优先走 MCP**：如果是成熟的外部工具，优先包装成 MCP server 而不是 skill。MCP 的工具调用协议更稳定，且天然支持按需加载。
4. **写一个测试清单**：每次改动 skill 配置后，用固定的几个测试句子验证触发行为。偷懒的后果就是上线后才发现匹配逻辑坏了。
5. **提供降级路径**：按需加载偶尔会漏匹配，建议保留一个“兜底技能”——当多次未能匹配时，Agent 能用它列出所有可用技能并请求用户明确。

## 总结

OpenClaw 的 Skills 机制本质上是一套“能力注册表”。全量注入是简单但粗糙的方案，按需加载才是真正适合生产环境的做法。配置本身不难，难点在于把每个 skill 的描述写成“意图匹配器”，以及管理好技能间的依赖边界。

当你把技能从“常驻内存”变成“按需拉起”，Agent 的响应速度和决策质量都会有可感知的提升。工程上没有银弹，但合理的加载策略是小成本换大收益的务实选择。
