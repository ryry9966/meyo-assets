## 背景

OpenClaw 这类 Agent 系统的价值在于把任务编排自动化，但前提假设是外部依赖可用——MCP 工具、HTTP 插件、LLM 服务商、知识库接口。现实往往不成立：免费 API 限流、供应商 5xx、网络闪断、上游接口悄悄改版。我最近在维护一个用 OpenClaw 做定时信息聚合的自动化流程，被第三方 API 的间歇性 503 折腾到怀疑人生，也因此沉淀了一套错误恢复的工程思路。

## 问题

Agent 遇到 API 挂掉时，典型的表现是灾难性的：

1. **错误被当成正常响应**：插件把 `{"error": "rate_limit"}` 当作工具返回值传给 Agent，模型一本正经地解析这个错误结构，得出一堆自洽但错误的结论。
2. **无限重试不重试**：部分插件内置的重试循环没有退避策略，直接把任务卡死，直到超时。Agent 不具备“等了 5 次都失败就换路”的判断力。
3. **编造成功**：最恶劣的情况是模型在工具调用失败后，为了完成用户目标，强行生成了一个“看起来像成功”的结果，造成数据污染。

## 做法/步骤

我的核心思路是：把错误恢复当作工程问题，而不是指望模型随机应变。具体分层做：

### 1. 错误信号规范化

写一个统一异常中间件，把所有插件和 MCP 工具返回的错误结构标准化：

```
status: "error" | "fallback_result" | "success"
error_type: "http_5xx" | "rate_limit" | "timeout" | "malformed"
retryable: boolean
```

这样 Agent 不需要自己猜测错误含义，**系统提示词里明确告诉模型**：看到 `retryable: true` 时输出“该步骤暂时不可用”，不要编造结果。

### 2. 内置 fallback 机制

每个关键外部依赖都配一个备用方案：

- 天气用 A 服务，备选 B 服务
- 搜索用 Bing MCP，挂掉后回退到本地函数计算
- LLM provider 配多 key 多模型自动切换

在 OpenClaw 插件层做路由，而不是在 workflow 层做。这样 Agent 无感，只是响应时间上去了。

### 3. 重试与退避

对可重试的错误（5xx、超时、限流）实现指数退避重试：

```
第一次失败后等 1s，第二次等 2s，第三次等 4s，最多 3 次
```

**关键点**：Agent 场景不能做标准指数退避（那可能等 30 秒），每次重试前要把“当前是第几轮失败”作为上下文喂给 Agent，让它决定是等待还是改道，而不是无脑让工具层重试到死。

### 4. 语境感知恢复

上一轮失败信息不能只存在于日志里，要作为下一轮动作的输入。我在插件返回值里附加 `recovery_hint` 字段，例如：

- 限流 → 建议 30 秒后再试
- 网络错误 → 建议直接切换备用源
- 数据格式异常 → 建议换一种查询参数

Agent 看到 hint 后，能做出合理的后续决策，而不是把同一请求再发十遍。

### 5. 记账与熔断

给每个外部源维护一个健康计数器：连续失败 N 次（比如 5 次）就熔断 5 分钟，期间所有请求直接路由到 fallback。熔断状态暴露成一个可查询工具，让 Agent 一上来就知道哪些源不可用。

## 踩坑点

- **重试工具选错**：有个插件内部用 `retry()` 递归实现重试，失败后抛出的异常会带着之前的执行上下文，我在日志里看到的不是最近一次错误，是第一次的错误，误导了排查方向。
- **无限退避卡死整个队列**：重试策略要设上限，否则 agent 卡在一个步骤，后续的所有步骤排队等待，整个自动化流程挂死。
- **错误信息被过度清洗**：有一次我把异常包装得过于干净，Agent 拿到的信息根本不足以判断是限流还是超时，也就无法选择正确的恢复策略。
- **跨工具的错误传染**：一个工具返回的错误结构直接传给了下一个工具做参数，下游工具疯狂报 schema 解析失败，排查很久才发现源头。
- **假恢复**：重试成功后，旧数据被当成新结果写入，没有验证数据的时间戳是否匹配当前任务，严重误导后续分析。

## 可复用建议

给社区朋友一份可以直接抄的实践清单：

1. **统一错误 schema**，把错误类型和可重试性显式告诉模型，禁止模型在错误面前自由发挥。
2. **关键依赖必须配 fallback**，优先级：同 API 换 key > 同类型备选服务 > 本地兜底逻辑 > 放弃该步骤继续执行。
3. **重试要分层**：工具层做快速重试（1-2 次），Agent 层做策略性决策（改道还是等待或跳过），Workflow 层做最终熔断。
4. **恢复上下文必须进 System Prompt**，否则模型不知道上一步是怎么失败的。
5. **维护一个健康状态工具**，让 Agent 在规划动作时主动查询哪些服务可用，从源头上减少失败。
6. **建立一次失败演练**：人为拔掉某个 API，观察 Agent 的行为是否符合预期，很多问题只有实操才能暴露。

## 总结

AI Agent 面对外部 API 故障时，最危险的行为是“幻觉式成功”。我们的目标是让 Agent 在外部依赖不确定的情况下，依然保持**行为可预期、失败可追踪、步骤可降级**。错误恢复不是事后补丁，而是 Agent 系统架构的一等公民——把失败处理设计好，Agent 才能真正长期稳定跑在自动化流水线上。
