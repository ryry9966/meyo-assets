## 背景

在 OpenClaw 的日常使用里，Agent 产出 Markdown 草稿只是第一步。真正的最后一公里是把这份草稿发到公众号、知乎、语雀或者团队 Wiki。问题是：**同一份 Markdown，换个平台就烂了。**

不是语法不规范，而是平台之间的 Markdown 方言差异 + LLM 生成的格式习惯不兼容。试过把 ChatGPT/Claude 生成的文章直接粘到公众号后台的人，大概率见过代码块崩掉、表格错位、TOC 全军覆没的场面。

这篇文章记录我在 OpenClaw 里搭的一条 Markdown 发布管线，核心思路是：**AI 负责写，管线负责收拾形态，平台适配放在最后一层做。**

## 问题拆解

实际踩下来的问题有三类：

**1. AI 生成内容的格式坏味道**

- 标题层级跳跃：`##` 之后直接 `####`
- 滥用粗体和行内代码，一段话里 40% 是粗体
- 无意义表格：两列三行也画个表
- 分点嵌套太深，三四层列表混用 `-` `1.` `*`

**2. 平台方言差异**

| 特性 | 公众号 | 知乎 | 语雀 |
|---|---|---|---|
| 行内代码 | 支持弱，样式不清 | 支持 | 支持 |
| GFM 表格 | 样式可用但窄屏崩 | 解析有 bug，列错位 | 支持好 |
| 脚注 | 不支持 | 部分支持 | 支持 |
| LaTeX | 不支持 | 支持 | 要开开关 |
| TOC | 不支持 | 支持（语法有差异） | 插件渲染 |

**3. 图片路径问题**

Agent 生成图片时经常给出相对路径或 `![](./images/xxx.png)`，直接粘贴进平台编辑器，全部挂掉。这是个比格式更深的问题，必须在管线里拦截。

## 做法

不追求一份 Markdown 通吃所有平台，而是：**中间格式用 GFM，平台差异靠后处理脚本补。**

管线长这样：

```
LLM 输出 → 临时.md → 规范校验（lint）→ 清洗修复 → 平台适配脚本 → 各平台目标文件
```

**第一步：生成时加约束**

OpenClaw 的 system prompt 里明确要求：

- 标题从 `##` 开始，最多到 `####`
- 禁止四级以上列表嵌套
- 表格只用于真正的对比场景，至少 3 列
- 代码块必须带语言标签

这一层能把后面 50% 的修修补补省掉。不要指望模型自觉，要在 config 里写死。

**第二步：用脚本做规范性清洗**

写了一个 Node.js 脚本 `md-lint.js`，主要做这几件事：

- 合并连续空行为一个
- 重排标题层级：把所有标题下移一位，保证从 `##` 开始
- 把不规范的三级列表拆成段落或二级列表
- 检查代码块是否带语言标识，缺失则补 `text`

在 OpenClaw 里注册为 MCP tool：

```json
{
  "toolName": "md_lint",
  "command": "node /path/to/md-lint.js"
}
```

每次 Agent 生成后自动调用，输出一个 `clean.md`。

**第三步：平台适配在最后一步做**

`clean.md` 永远不动。每次发布时跑对应的适配脚本：

- **公众号**：转换 `code fence` 为带背景色的行内样式（因为后台编辑器对代码块支持最差），图片转为 URL 直链并确保 HTTPS，移除所有表格并转成列表
- **知乎**：把 GFM 表格转换为 HTML `<table>` 后再粘贴（知乎富文本编辑器对原生表格解析有 bug），脚注语法重写为知乎支持的格式
- **语雀**：基本可以直接粘，但要手动检查 LaTeX 开关

每个适配脚本只做一件事，互相独立，用目录区分：

```
pipeline/
  lib/lint.js
  adapters/
    wechat.js
    zhihu.js
    yuque.js
```

**第四步：图片路径做兜底**

Agent 生成的图片，管线在处理时统一做两件事：

1. 把相对路径替换为已上传 CDN 的绝对 URL
2. 缺失的图片引用（404）直接置为占位符文本，避免平台端出现裂图

## 踩坑点

1. **不要指望 Pandoc 一把梭**

Pandoc 的转换强在严谨文档，但公众号后台的编辑器只认自己的内部格式，Pandoc 产物照样会崩。Pandoc 适合做 docx/PDF 的底线兜底，不适合做 Web 平台的最终输出。

2. **不要用 LLM 做格式转换**

在管线里让 Agent 自己"格式化后输出"是最不稳的。LLM 做格式转换时会出现字符被吞、转义反复、`&` 变 `&amp;` 的问题。格式整理是确定性工作，交给正则和脚本。

3. **表格是移动端重灾区**

公众号在手机上渲染超过 4 列的表格就是一场灾难。即使脚本转换后没问题，手机上用户看到的是横向滚动条。**长表必须拆**——要么拆成多个小表，要么直接改成列表结构。

4. **GitHub 能渲染 ≠ 目标平台能渲染**

GFM 能跑的 markdown 在语雀和知乎上大概率有细节差异。这条认知要写在每个适配脚本的注释里，防止后人"优化"掉适配层。

## 可复用建议

梳理成 SOP 如下：

- **生成前约束比生成后修复重要**——System Prompt 里写明头部标题层级、表格准入条件、代码块必须带语言标签
- **中间格式锁定为 GFM**，不针对平台定制源文件
- **源文件永远不动**，平台适配全部走派生副本
- **维护一个平台差异映射表**（README.md），新平台接入时先补表再做脚本
- **管线里加一个校验步骤**：发布前跑一遍 `markdownlint`，检查是否有被适配脚本搞坏的残留语法

## 总结

做这套管线的核心收益是：**内容产生和内容发布解耦。** AI 生成的草稿进入管线后，所有平台适配都是确定性脚本干的事，不消耗模型 token、不引入随机性、出了问题可以直接修代码。

如果你也在 OpenClaw 里跑内容类 Agent，建议别只停留在"让 Agent 生成 Markdown"这一步，多花半天时间把发布管线搭起来，ROI 会非常明显——你的 Agent 从"会写字"变成了"能把字发出去"。
