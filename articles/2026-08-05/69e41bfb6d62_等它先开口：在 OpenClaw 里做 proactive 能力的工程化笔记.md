## 背景

目前的 AI 助手大多是被动应答的：用户敲一行字，它回一段话。但真实需求里，最值钱的往往是“不等你说”——早上九点前把今日会议整理好推给你，客户邮件进来先草拟一版回复，线上接口挂了主动把日志翻出来。OpenClaw 这类本地运行的 agent，能挂 MCP、有持久记忆、能访问文件与外部服务，具备做“主动”的硬件基础。但主动不是改几行 system prompt 就能实现的。LLM 本身不会自己醒来，它需要被触发、被注入、被约束。

## 问题

把“让它自己跑”落地时，遇到的三个现实问题：

1. **没有可靠触发源**。进程挂在后台没人喊它，它永远处于空转状态。
2. **没有触发上下文**。即便被推了一下，不知道此刻发生了什么、用户在看什么，跑起来也是瞎跑。
3. **容易乱动**。一旦开始主动，就忍不住过度揣测，推了一堆用户并不想要的消息。

## 做法

proactive 的关键不是让模型更聪明，而是把它从“等输入”的循环里拿出来，放进一个会随时间变化的环境。在 OpenClaw 里做，本质是搭一条管道：

**事件源 → 触发决策 → 输出动作**

我把整件事拆成三层来做。

**第一层：事件源层。**

让 agent 通过 MCP 挂上日历订阅、邮件收件箱或 IM webhook。不需要一次全挂，先挑一个高频场景，比如 CalDAV 日历，或者一个会往里写文件的目录。事件源只负责把外部世界的事实拉进来，不参与任何判断。

**第二层：触发层。**

写一个后台循环，每 15 分钟做一次低成本的“检查”：

- 当前时间是什么？
- memory 里有没有未完成的用户请求？
- 外部事件里有没有新增的近场日程？

满足预设条件时，把这三类信息拼成一个决策 prompt，交给 agent 判定“要不要行动”。这里的关键是：**决策规则必须写死在 system prompt 里，不能靠模型自由发挥**。比如只允许触发两条规则：“每天早上 9 点输出今日要事”和“收到新邮件时输出邮件摘要”。其余场景一律不做猜测式主动推送。

**第三层：输出层。**

行动结果写回 memory，同时通过 notifier（Telegram bot、企业微信机器人、本地通知）推给用户。每次执行后必须留一个状态位，比如 `brief_sent_today: true`，保证同一任务不会重复执行。

## 踩坑点

实际跑起来，有三个坑值得讲清楚。

**坑一：真·主动变成打扰。** 允许 agent“发现新鲜事就汇报”之后，第一天推了 40 条消息。后来定了规矩：只对写死的触发规则负责，不做意图猜测。“觉得用户可能想看点什么”不是一个合法触发条件。

**坑二：触发上下文污染主对话。** 加了日程/时间注入后，正常对话的回复都会莫名带一句“现在是下午 3 点”。解决方法是把触发决策和主对话彻底隔离开：决策走独立的 system prompt，不混入用户的日常会话。

**坑三：外部服务不可靠。** 日历 MCP 偶尔超时，推送服务偶尔限流，整个定时任务会跟着挂掉。给每个外部调用加超时和失败容忍，拉取失败时跳过本轮，但要把失败原因记进 memory，下轮再补。

## 可复用建议

1. **外部调度优于进程内 sleep**。用系统 cron 或 OpenClaw 支持的外部调度器，避免机器休眠把循环打断。
2. **事件源与决策逻辑分离**。MCP 模块只负责拉数据，判断逻辑只属于 agent 的 prompt。
3. **消息模板化输出**。固定推送格式，方便后续自动化动作（比如直接进待办应用）。
4. **从两个场景起步**：早报、例会前提醒。这两个场景有明确时间点、明确输入、明确输出，最容易跑通。
5. **每个主动动作都留可追踪状态**。什么时间触发、触发原因、结果如何，全部落库，便于事后复盘。

## 总结

让 agent 主动干活，本质上不是在等它突然变聪明，而是承认它永远需要一套外部机制来告诉它：“现在是时候了，这些是现状，去做那件约定好的事。”

OpenClaw 的价值不在聊天，而在于它是少数能把“常驻后台 + 长期记忆 + MCP 生态”组合在一起的东西——这给了 proactive 能力一个难得的落点。AI 主动帮忙最好的形态，永远是那个到点递上茶的程序。前提是它得知道该在哪里停下，把剩下的事留给你。
