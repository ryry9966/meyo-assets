# OpenClaw 多模型路由实战指南：何时调用 GPT，何时用本地模型

在构建基于 OpenClaw 的智能体工作流时，很多团队会陷入一个两难选择：全部使用 GPT-4 等级云端模型带来高昂成本与延迟，而全部切换为本地部署的开源模型又会在复杂推理任务上频频翻车。真实生产场景的需求从来不是二选一，而是如何让合适的任务找到合适的模型。本文分享我们在 OpenClaw 中落地多模型路由的经验，包括设计思路、配置方法、踩坑复盘以及可复用的实践原则。

## 背景：为什么需要模型路由

OpenClaw 是一个面向任务编排的多智能体框架，典型的工作流会同时包含不同粒度的步骤——例如意图识别、参数提取、代码生成、结果润色、函数调用等。并非每个步骤都需要 GPT-4 级别的“智力”。一个简单的“识别用户输入是退出指令还是聊天消息”分类器，用本地 7B 模型甚至 1B 模型即可在 50ms 内完成，而调用云端 API 可能耗时 1.5s，成本却多出数十倍。

反过来，对于需要多步推理、复杂指令跟随或结构化输出严格符合 schema 的任务，本地模型（哪怕是精心微调的 70B+）依然容易出现幻觉或格式错误，此时就必须让云端强模型接手。模型路由的核心就是根据任务特征动态决策，将轻量步骤分流到本地模型，重型步骤留给云端强模型，从而在质量、延迟和成本之间取得工程上的平衡。

## 问题拆解：路由判断的维度

我们实际梳理了三类关键路由因子：

1. **任务复杂度与容错率**  
   - 低复杂度、高容错：如对话历史截断、情绪二分类、简单实体抽取 → 本地模型  
   - 高复杂度、低容错：如多步骤工具调用、JSON Schema 严格约束的结构化输出、长文档关键信息提取 → GPT-4o / Claude 3.5 Sonnet

2. **延迟要求**  
   - 需要实时流式返回的轻量判断（< 200ms）→ 本地模型  
   - 可容忍 2–5 秒等待的深度推理 → 云端模型

3. **数据隐私等级**  
   - 包含 PII 或内部业务数据的处理，除非有合规的私有化部署 GPT 方案，否则优先走本地模型，避免数据出境。

## OpenClaw 中的实现方式

OpenClaw 本身提供了灵活的 `RouterNode` 组件，支持基于规则、关键词、小型分类模型甚至 LLM 作为路由决策器。我们的实践是将路由逻辑抽象成一个轻量决策器，而不是让 GPT 去决定“该用哪个模型” ——那样做既贵又慢，且引入额外的决策延迟。

**做法 / 配置步骤：**

1. **定义模型端点**  
   在 OpenClaw 的 `model_registry` 中注册本地和云端多个模型：
```yaml
models:
  local_fast:
    provider: ollama
    model: qwen2.5:7b-instruct-q4_K_M
    endpoint: http://localhost:11434
  local_medium:
    provider: vllm
    model: meta-llama/Llama-3.1-70B-Instruct
  cloud_strong:
    provider: openai
    model: gpt-4o
```

2. **构建路由规则**  
   采用 `RuleBasedRouter`，用简单关键词/长度/意图标签进行第一步分流。示例：
```yaml
router:
  type: conditional
  branches:
    - condition: intent == 'truncate_summary' or intent == 'sentiment'
      target: local_fast
    - condition: input_length < 200 and task_type == 'classification'
      target: local_fast
    - condition: task_type == 'code_generation' or task_type == 'structured_extraction'
      target: cloud_strong
    default: local_medium
```

3. **引入轻量级意图分类器**  
   为提升路由准确度，我们在工作流入口放置一个本地小模型专门做意图识别（如 qwen2.5:1.5B），一次推理 30ms，将分类结果写入 context，后续路由直接读取 `intent` 字段。这样避免了每步均判断，也保证了路由决策的低延迟。

4. **复用路由节点**  
   在工作流中将 `RouterNode` 放在多个步骤前，形成通用的“模型选择器”。必要时可以为不同的子流定制不同的路由策略。

## 踩坑记录与应对

**坑1：本地模型同 prompt 表现差异大，路由后输出不一致**  
例如同样的结构化提取 prompt，GPT-4o 能稳定输出正确 JSON，但本地 70B 模型偶尔添加解释前缀。解决方案：为不同目标模型微调 system prompt，并捕捉解析异常时自动升级到云端模型重试。OpenClaw 的错误处理节点可以设置为回退时切换至 `cloud_strong` 进行重试。

**坑2：本地模型上下文窗口不足**  
很多轻量本地模型只支持 4K 或 8K，路由到它处理较长历史时会被截断，导致信息丢失。实践上我们加入 `input_length` 判断，超过 2K token 的文本任务直接避开 7B 以下模型，或者做滑动窗口预处理。

**坑3：决策器自身成为瓶颈**  
我们一开始曾尝试用一个 GPT-3.5 调用来判断“该任务难不难”，结果决策本身消耗了 1.2s 和约 200 token，抵消了省下来的成本。后来坚决改为基于规则+小模型分类的亚毫秒级决策。

**坑4：模型版本漂移**  
云端模型 api 版本更新可能改变行为，本地模型也可能切换量化格式。需要在路由节点后埋点记录所用模型及版本，以便排查质量波动。

## 可复用建议

- **从三个档位开始**：`local_fast`（1–7B，纯分流/分类），`local_medium`（20–70B，通用中等任务），`cloud_strong`（GPT-4o/Claude，难任务），避免过度拆分。
- **兜底策略**：任何本地模型输出无法通过校验时，自动升级到云端模型重试，关键路径需要这样设计。
- **监控与预算控制**：记录每次路由选择、模型响应时间、token 消耗和重试次数。结合 OpenClaw 内置的 trace 功能，可以清晰看出云端模型调用的比例是否合理。
- **本地模型选型**：优先选择与云端模型 prompt 兼容的指令微调模型（如 Qwen 系列），减少 prompt 工程上的割裂。
- **渐进式切换**：先在非关键链路试验路由规则，收集 1–2 周数据再推广到核心链路上，避免回退事故。

## 总结

多模型路由并不是为了炫技，而是为了在可控成本下保证智能体工作流的稳定性及响应速度。OpenClaw 灵活的模型注册与路由机制让这种组合变得工程化，而不再是手动维护一堆 if-else。核心思路是：**用最快的模型做最轻的决策，用最强的模型啃最硬的骨头，并始终保留一条云端回退通路。** 在技术成本敏感的当下，这种混合推理策略将成为生产级智能体系统的标配。

着手在你的 OpenClaw 项目中建立一套路由规则吧，从一个简单的意图分类+规则分流开始，逐步优化，你可能会惊讶于成本降低的幅度。
