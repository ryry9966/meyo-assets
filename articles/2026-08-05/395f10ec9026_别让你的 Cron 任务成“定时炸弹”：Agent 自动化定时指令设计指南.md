## 背景

在 OpenClaw 这类智能体编排平台里，Cron 触发器是把工作流推向“无人值守”的关键一步。通过定时触发 Agent，你可以实现每日报告生成、数据巡检、漏洞监控、库存同步等真正自动化的闭环任务。然而，绝大多数指令仍按照“对话式 Prompt”的习惯来写——提出问题、等待回答、人工判断，这种风格直接移植到 Cron 场景，往往导致任务悄悄失败、重复执行、上下文失控或输出石沉大海。

这篇文章不讨论 Cron 表达式怎么写，只聚焦于：**当 Agent 被时间唤醒，而不是被用户消息唤醒时，该给它一份什么样的 instruction。** 我们将基于 OpenClaw 生态（支持函数调用、多步任务、MCP 工具等）梳理实用的设计规范与避坑指南。

## 核心问题：定时任务里的 Agent 和对话场景有什么不一样？

1. **没有即时纠偏** —— 人类不在旁边看，Agent 一旦理解偏差，会带着错误一路走到黑。
2. **无状态需要自我闭环** —— 每次触发都是独立的一次 invocation（除非你显式记录状态）。Agent 无法默认知道上一轮跑到哪里了。
3. **失败是静默的** —— 没有用户因为等不到结果而追问，往往过了几天才发现任务悄无声息地停了。
4. **上下文极易膨胀** —— 如果每轮都保留历史，Cron 任务会迅速积累大量无用的对话上下文，消耗 token 并及时触发截断。

因此，Cron 任务中的 Prompt 工程必须重点解决**幂等性、状态管理、错误可见性和上下文约束**这四个维度。

## 做法与步骤：给 Cron 任务写 instruction 的五个固定环节

根据我们在 OpenClaw 内部自动化维护任务中的实践，一份“可用的 Cron instruction”至少应包含以下五个段落，缺一不可。

### 1. 启动自检与时间窗口（Timebox）

避免因系统延迟、任务堆积或时区理解错误导致的误执行。指令开头明确要求 Agent 进行一次时间校验：

```text
检查当前系统时间，如果已经超过 23:59 UTC 但尚未生成今日报告，则继续，
否则直接返回 "skipped: outside execution window" 并终止。
```

注意，如果你使用了 `工具调用（Function Calling）`，确保有获取可信时间源的工具（如透过 MCP 或内置时间工具），不要依赖 Agent 自己凭记忆估算。

### 2. 显式幂等性标记（Idempotency Key）

定时任务或多或少都会遇到重复触发（重试、调度抖动等）。最稳妥的方式是要求 Agent 在执行关键操作前检查“标记文件”或数据库记录。

```text
步骤 A: 检查文件 /cron_state/daily_report_2025-05-22.done 是否存在。
如不存在，继续执行；如存在，输出 "already completed" 并退出。
步骤 B: 任务完成后创建该文件，内容为完成时间戳。
```

若你通过 MCP 连接了外部服务（例如 Notion、数据库、S3），也可使用远程 key 作为幂等锁。关键是**让 Agent 执行前主动验证，而不是假设它只执行一次**。

### 3. 强制分段执行与自我检查点（Checkpointing）

一次 Cron 任务如果步骤较多（拉取数据→清洗→分析→推送到多个渠道），最怕中间一步失败后整个任务被重试从头再来，造成重复操作或不一致。

我们在 instruction 中要求 Agent 明确划分 Phase，并在每步的输出摘要中报告进度。例如：

```text
Phase 1/3: 数据抓取完成，获得 142 条记录。
Phase 2/3: 异常分析完成，发现 3 个异常项。
Phase 3/3: 报告已发送至 Slack #monitoring 频道。
```

结合工具调用，可以让 Agent 在完成每个 Phase 后更新一个状态文件。这样即便中途重启，下一轮也能读回状态并从断点继续（或选择跳过已完成部分）。

### 4. 总是产生结构化日志输出（Structured Output）

Cron 任务不能“无输出”。你的 instruction 必须要求 Agent 在最后返回一个明确的结果摘要，格式固定，便于后续日志抓取或告警配置。

我们常用的最小可用结构：

```json
{
  "status": "success|skipped|failed",
  "summary": "一句话描述",
  "details": { ... },
  "checkpoint": "last_phase_completed"
}
```

让 Agent 尽量在一次推理中输出此 JSON。如果 Agent 生态支持原生的 `response_format` （如结构化输出），直接开启；否则在 Prompt 里强调“最终回复只能包含上述 JSON，不要多余文字”。

### 5. 错误处理与“优雅降级”规则

Cron 任务不应因一个非致命错误就崩溃退出，也不应在遇到预期异常时无限重试。你需要在指令里明确异常分支：

```text
如果 API 返回 429，等待 60 秒后重试 1 次，仍失败则将状态设为 "degraded" 并继续下一步。
如果关键步骤失败（如数据库不可用），立即停止并输出 status=failed，不得执行后续写操作。
```

这里可以结合 OpenClaw 的 `max_retries` 或自定义函数来封装，但 Prompt 中的行为约束决定 Agent 如何决策哪些步骤可以跳过、哪些必须报错中止。

## 踩坑实录

在实际使用中，下面这些坑几乎每个人都会踩一遍：

- **用自然语言描述“一天一次”**：Agent 无法准确判断是否已经执行过，很依赖上下文记忆。必须引入显式的幂等标记或外部状态存储。
- **Cron 间隔比任务执行时间还短**：如果任务执行需要 5 分钟，Cron 每 3 分钟触发一次，必然并发冲突。需在 instruction 中增加“执行锁”检查，或者调大间隔，并在 Prompt 中注明预期执行时长。
- **输出没有显式退出条件**：Agent 完成任务后仍可能继续“观察”或“等待下一步指令”，造成不必要的 token 消耗。应明确要求“一旦产生最终输出即认为任务完成，无需继续交互”。
- **忽略时区**：服务器 UTC 时间和你期望的“早上 9 点”可能是两回事。在指令里加上对时区的说明，并让 Agent 使用工具获取特定时区时间，而不是模糊计算。
- **上下文泄露**：长期运行的 Cron 会话可能因 OpenClaw 配置保留了历史消息，导致每一轮 Prompt 越来越长。建议在高级配置中将 Cron 任务 context 设为最小（例如仅 system + 当前指令），或者在 instruction 开头声明“忽略之前所有历史对话，仅以本消息为准”。

## 可复用模板（极简版）

为了便于快速落地，这里给出一个适用于多数汇报类 Cron 任务的 instruction 骨架，可根据实际工具替换 `<>` 内内容：

```text
[System]
你是自动定时任务执行者。忽略之前所有历史。严格按以下步骤顺序执行。

1. 获取当前时间（工具: get_current_time, timezone=Asia/Shanghai）。若时间不在 09:00-09:05 区间，输出 skipped 并停止。
2. 检查幂等标记：调用 <check_task_status> 查看今日任务是否已完成。如已完成，输出 already_completed 并停止。
3. 执行主任务：<fetch_data> -> <analyze> -> <send_report>，分阶段更新检查点状态。
4. 结果必须严格输出以下 JSON，无其他文本：
{ "status": "...", "summary": "...", "checkpoint": "..." }
5. 任何非致命异常（如超时、限流）记录到 summary 并继续；致命异常立即 failed 且不执行后续写入。
```

你只需要把这个骨架塞进 OpenClaw 的 Cron 任务 prompt 区域，再把尖括号里的工具名替换为你实际注册的函数/MCP 工具，即可得到一个行为可控、失败可追踪的自动化任务。

## 总结

定时任务中的 instruction 书写，核心是把“人在回路”的默认假设替换为“机器闭环”的工程约束：**引入时间窗口、幂等锁、分步检查点、结构化日志和异常分支**。这五点不必每次都全部复杂实现，但缺少任何一项，都可能在某一刻导致任务悄悄失效或产生脏数据。

在 OpenClaw 日渐丰富的 MCP 工具和函数调用能力的加持下，我们完全有能力把 Cron 任务写出生产级的稳定度——前提是摒弃那种“像跟人说话一样写 Prompt”的习惯，转而像写一个可靠的守护进程一样去设计指令。
