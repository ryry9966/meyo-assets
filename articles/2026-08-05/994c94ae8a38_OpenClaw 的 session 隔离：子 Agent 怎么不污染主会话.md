## 背景

OpenClaw 在承担真实任务时，几乎不可避免地要把活拆给子 Agent：查资料、跑脚本、整理日志、调 MCP 工具。刚开始大家都会踩同一个问题——子 Agent 干完活，主会话里全乱了。

乱在哪：子 Agent 的中间推理、失败的 MCP 调用、一段段原始工具返回，都被当成主会话的历史喂了回来。对话一长，主 session 的上下文窗口被无效内容塞满，模型开始"记住"子任务的中间错误，后续指令都带偏。

这不是玄学，是会话上下文边界没有划清楚。

## 问题：污染具体是什么

拿一次实际的排查举例。主会话里让子 Agent 去读一沓日志并归纳异常。如果没有隔离，会出现三件事：

1. 子 Agent 调了三次日志工具，三次的原始 JSON 全部回流到主会话历史；
2. 子 Agent 第一次归纳错了，它把纠错过程也写进了历史；
3. 主会话接着做下一个任务时，模型在长上下文里翻到这些噪音，回答开始引用子任务的中间产物。

直接后果是 token 消耗涨、回复质量掉。更隐蔽的是：如果接了向量存储做记忆，这些噪音会被向量化，后续检索全部被污染，排查起来非常头疼。

## 做法：隔离的两个边界

session 隔离要做两件事：**上下文隔离** 和 **记忆隔离**。只做一个不够。

我现在的做法：

**1. 子 Agent 永远开新 session。**
在主会话里通过 task / agent 类工具派生子任务时，显式创建一个新的 session 实例，不要复用主 session id。子 Agent 的对话轮次、工具调用、状态，全部落在这个子 session 里。

**2. 结果只回传"产物"，不回传"过程"。**
子 Agent 干完活后，只允许向主会话回传一个结构化结果块：结论、产出文件路径、退出状态、一句话注意事项。所有中间日志留在子会话里，需要时按 session id 单独去查。

**3. 内存写入做命名空间隔离。**
如果你用 memory / MCP 插件做持久化，给子 Agent 写入的记忆加上独立 namespace 或前缀标记。主会话的检索默认只查自己的 namespace，子 Agent 的记忆只在显式引用时才会被检索进来。

**4. 设一个"提交闸口"。**
不靠自动同步，而是让子 Agent 产出一个 summary 对象，由主会话侧的流程脚本检查 schema 合法后再写入主会话上下文。这一步通常写在插件或自定义工具里，也是最容易被省略的一步。

## 踩坑点

- **以为 session 独立就万事大吉**。子会话历史确实干净了，但两边共享同一个全局 memory store，照样串味。记忆隔离必须单独配置，不能跟着会话默认走。
- **摘要格式不给约束**。直接让子 Agent"简洁总结"，它回传的还是夹带私货的长段落。必须给固定 schema：`{conclusion, outputs, status}`，字段不合格就重跑。
- **子会话不回收**。session 开了一堆不关，之后按时间线恢复主会话时，系统把历史子会话也拉进来，等于绕过了隔离。
- **手动把子 Agent 输出粘回主会话**，还粘了两次——一次在消息里，一次存进记忆。主会话上下文直接多出一倍冗余。

## 可复用建议

1. **给每个子任务生成独立 session key（UUID）**，并把 parent id 写进 session 元数据。定位问题的时候一条链路拉出来，肉眼可查。
2. **主会话只认"产物契约"**。固定三字段，字段校验不过就不算完成任务，避免"看起来干完了"的假成功。
3. **做一个 gateway session 模式**：所有子任务结果先进一个网关会话，由网关统一打分、压缩、再决定是否提交给主会话。OpenClaw 的插件层完全能承担这个角色。
4. **监控两项指标**：主会话 token 增长速度、子 session 数量。子 session 超过两位数还没回收，基本是有会话泄漏，优先查自动同步逻辑。
5. **在子 Agent 的 system prompt 里写死边界**："你的输出是最终产物，不是对话记录。"一句话能省掉 80% 的噪音回传。

## 总结

session 隔离要解决的不是"多开会话"这种表面问题，而是**上下文边界与记忆边界的双重划分**。子 Agent 可以拥有完整的推理空间，但向主会话交出的只能是可校验的产物。做到这一点，多 Agent 编排才算真正可控，而不是靠运气运行。
