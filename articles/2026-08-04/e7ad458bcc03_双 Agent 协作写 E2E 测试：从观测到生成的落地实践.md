**背景**

E2E 测试的价值没人否认，但维护成本让它成了很多团队的「僵尸项目」——CI 上天天飘红，没人愿意接盘。用 Agent 写 E2E 的常见做法是直接丢一个「帮我写个测试」，结果它凭想象生成一堆 selector，跑起来全废。问题不在 Agent 能力，在工作流：你让它在一个没有上下文的环境里猜。

**问题拆解**

写 E2E 测试需要两类信息：页面真实结构（DOM 长什么样）和业务操作意图（用户怎么走完一条路径）。单个 Agent 会话往往兼顾不了这两件事——它既没有浏览器视野，也没有稳定的中间状态。正确做法是把任务拆成「观测」和「生成」两个角色，通过 MCP 连接真实浏览器，让 Agent 不再凭空想象。

**做法：三步协作**

当前跑通的方案是：OpenClaw 编排两个 Agent + Playwright MCP server。

第一步，观测。配置浏览器 MCP（`@playwright/mcp`），暴露 `browser_snapshot`、`browser_click`、`browser_type` 等工具。给 Agent A 一段业务描述（如「注册 → 登录 → 创建项目 → 邀请成员」），让它逐步操作，每一步把 accessibility snapshot 和操作动作记录成 JSON 轨迹。这条轨迹是唯一事实来源，生成侧无权修改。

第二步，生成。Agent B 读取轨迹 JSON，为每步生成 Playwright 断言。硬性约束：优先 `getByRole`/`getByLabel` 定位；每个操作前判断页面是否稳定，补上 `waitFor` 或 `toBeVisible()`；每条用例只测一个业务路径。

第三步，回放。把生成的测试真实跑一遍，拿 CI 失败信息 + 对应 DOM 片段喂回 Agent B 修补。两三轮之后错误率会有质的变化。

**踩坑点**

- **Selector 幻觉**：Agent 没看过真实 DOM 时会编 selector。解决：轨迹里必须包含操作前后的 snapshot 片段，禁止 Agent 凭空写定位。
- **异步不稳定**：Agent 生成的测试经常过早断言。强制在轨迹 schema 里加 `preActionState`（页面是否已稳定），让生成侧据此推导等待条件。
- **上下文污染**：多个跑批共用一个浏览器 context，Agent 拿到的是脏状态。给每轮 Agent 会话分配独立 context，用完即弃。
- **一次别生成太多**：之前试过一轮生成 30 个断言，后半段明显出现「补全式幻觉」。控制在 5-8 个断言一轮，质量稳定很多。

**可复用建议**

1. 轨迹即接口。把观测轨迹定义成稳定 schema（action、snapshot、url、timestamp），观测和生成彻底解耦。以后换模型、换框架（Cypress、WebdriverIO）都不用重写链路。
2. 反馈优先于 prompt。失败回放比任何「请仔细一点」的指令都有效。把失败堆栈和 DOM 上下文直接贴回去，Agent 能自己定位问题。
3. 引入第三位评审。生成完用 git diff 审查，检查是否改动了非测试代码、是否引入无关重构。成本低，收益明显。
4. 沉淀断言插件。定位方式、等待模式这类高频逻辑抽成测试工具插件，Agent 生成时会优先调用，而不是每次重新发明。

**总结**

别指望 Agent 一次写对。把它当成一个能快速产出初稿并自我迭代的协作者，人负责定边界、做评审、管验收。先挑一条小而真实的业务路径跑通，再逐步扩大覆盖。这样出来的测试，至少 CI 不会天天见红。
