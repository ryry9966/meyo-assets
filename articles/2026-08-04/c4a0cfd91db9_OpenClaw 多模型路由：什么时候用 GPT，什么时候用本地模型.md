## 背景

用 OpenClaw 跑自动化时，最容易被忽略的决策是：默认给 Agent 绑哪个模型。很多人直接绑定 GPT-4o 类云端模型，图省事；也有人换成本地 Qwen/Llama 想省钱，结果复杂任务质量崩了，来回返工。多模型路由不是炫技，是成本、延迟、隐私和输出质量之间的工程折中。

## 问题

单一模型路线的两个典型症状：

- 全是云端大模型：高频工具调用（网页抓取、日志解析、邮件分类）每个请求都走 API，一个月下来成本可观，链路延迟也明显。
- 全是本地模型：规划、调试、意图模糊的指令处理不好，Agent 经常跑偏，你花在核对纠正上的时间远超省下的 API 费用。

## 做法：先做任务分类，再配路由规则

核心思路是给任务分三档：机械型、推理型、混合型。

1. 机械型（低风险）
   特征：输入结构稳定、输出有明确格式。比如文本改写、摘要、分类打标、JSON 提取。
   方案：本地模型（Qwen2.5-7B / Llama 3.1-8B，Ollama 或 vLLM 部署）。

2. 推理型（高风险）
   特征：需要多步规划、代码排错、理解模糊指令、跨工具状态推理。
   方案：GPT-4o 或同档云端模型。

3. 混合型
   特征：任务中既有机械步骤又有判断步骤。
   方案：拆成多个子任务，按子任务分别路由，而不是让一个模型做完全程。

在 OpenClaw 里，实际做法是给不同 Agent 和工具绑定不同模型：

- 日常工具类 Agent（抓取、格式化）绑本地模型，配置里收敛 temperature 和 max_tokens，保证输出格式稳定；
- 规划类 Agent 绑云端大模型；
- 在任务流程里把「判断」和「执行」拆开，先让大模型产出步骤计划，再让本地模型执行具体动作。

## 踩坑点

1. 本地模型指令遵循能力弱一档。长提示词 + 多要求时，输出格式经常跑偏。对策：提示词收紧到 3 条以内要求，并且用代码校验输出格式，不合法就重试一次。
2. 按关键词路由不稳。比如遇到「分析」「总结」就转 GPT，会把大量简单任务送去云端。建议先把任务类型做成显式枚举，再写路由规则，不要靠模型猜。
3. 忽略本地推理冷启动。CPU 或小显存跑 8B 模型，首 token 延迟可能几秒，高频任务反而比 API 慢。先测延迟再决定。
4. 回退链不要只回退一次。本地模型失败后直接丢给 GPT-4o 成本高，中间加一档 mini 模型做垫底更经济。
5. 没有评估集就调路由。凭感觉调规则容易来回改。抽 50 条真实任务，记录每次路由的模型和结果，再调阈值。

## 可复用建议

- 先跑通全 GPT，稳定后再逐步下放任务，每次只下放一类任务，观察一周再扩展。
- 建立你自己的评测集（50 条真实 prompt 即可），本地模型质检不过关就降级，不用纠结。
- 默认回退链：本地 → GPT-4o-mini → GPT-4o，每档只做一件事：本地做机械执行，mini 做修正，大模型做最终兜底。
- 所有路由决策写日志，字段至少包含：任务类型、目标模型、成本、是否重试。没有日志就没有调优依据。
- 隐私敏感任务强制本地，别把「省成本」当唯一理由——本地模型的真正价值是数据不出域。

## 总结

多模型路由的本质是任务分级 + 容错设计。机械任务本地跑，推理任务交云端，中间用回退链兜底。不要追求完美的路由算法，先把日志和评估集建起来，让数据告诉你答案。
