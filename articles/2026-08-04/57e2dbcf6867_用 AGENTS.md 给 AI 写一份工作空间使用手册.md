## 背景

OpenClaw 在自动化任务里表现很好——计划拆解、工具调用、任务执行都能到生产级。但跑一段时间后，你大概率会遇到一个典型问题：**Agent 对工作空间的认知，和项目实际情况对不上**。

它会把旧日志当成新数据、在错误目录里找配置、反复做已经做过的处理步骤，甚至在你辛苦整理好的目录结构外新建一堆"自己的"文件夹。根因很简单：Agent 每次启动都是无状态的。你对项目的了解，它没有。

## 问题

我们习惯用自然语言表达需求，比如"处理一下数据目录"，然后指望 Agent 自己理解一切。但 LLM 在推理时依赖的上下文是高度碎片化的。**你在 README 里写给人类看的说明，和 Agent 需要的操作手册，完全是两回事。**

人类看 README 能推断出"data/ 应该是输入目录，output/ 是产物"；Agent 没有历史经验，它只是在猜。猜测多了，就出事故。这会直接导致：

- 读取了过期的缓存文件当事实
- 修改了不该动的生成物
- 用错误的相对路径执行命令
- 因为"感觉差不多"跳过了关键步骤

## 做法：写一份 AGENTS.md 放进工作空间

核心思路：**把项目上下文显式编码成 Agent 可读的文档，放在它每次开工前必经的入口位置。**

### 步骤

1. **确定工作空间根目录**，新建 `AGENTS.md`。不要放在子目录里，Agent 通常从工作区根目录开始扫描上下文。

2. **按以下结构编写内容：**

```
# AGENTS.md

## 空间地图
- /input: 原始数据，只读，勿写
- /work: 临时处理区域，可自由写
- /output: 交付产物目录，写入前需确认命名规范

## 状态记录
每次任务结束前，在 /work/STATE.md 写入本次完成的事项和下一步建议

## 命令与工具
- 数据处理统一用 scripts/process.sh
- 禁止直接调用 python -m 执行不在 scripts/ 下的代码
- 涉及外部 API 的操作，先检查 .env 是否存在

## 禁止事项
- 不要读取 /archive 下任何文件
- 不要修改 /input 内原始数据
- 不要在根目录创建新文件夹，有问题先看 /work

## 工作流入口
收到任务后：
1. 先读 /work/STATE.md
2. 确认输入文件清单
3. 按 scripts/run.sh 的流程执行
4. 结果统一写入 /output
```

3. **在 Agent 任务提示词里引用它**。在 OpenClaw 中，给任务消息加上一句："开工前先读工作空间根目录的 AGENTS.md，严格遵守其中的规范。"

4. **让 Agent 自己维护它**。当 Agent 发现某个操作导致重复错误时，允许它把规则补充进 AGENTS.md——前提是任务要求它这么做，避免主动行为。

### 一个实际例子

某个批量文档转换任务，Agent 连续三轮在 `/output` 生成了 `report_final_v2_v3.pdf`，导致下游系统混乱。排查后发现 Agent 根本不知道目录里已有两版旧文件。

在 AGENTS.md 中加入：

```
## 输出规范
- 写入 /output 前必须列出该目录现有文件
- 文件名不追加版本标记，统一用任务 ID 加日期
```

之后该问题没有再出现。原因不是 Agent 变聪明了，而是它的行动被事先约束在了具体、可验证的规则里。

## 踩坑点

- **写得像给老板看的汇报，而不是操作指令**。"请合理使用资源"这种话毫无价值，规则必须具体到文件和命令级别。
- **一次塞太多规则，Agent 注意力不够用**。实测超过 40 条规则，后面的失效率明显上升。保持精简，控制在 20~30 条。
- **用了歧义词**。比如"临时文件放 tmp 目录"，但 Agent 可能找不到 tmp 又不敢问，自己建一个。直接用绝对路径或相对根目录的路径。
- **忽略 MCP 工具的行为**。如果工作区挂载了 MCP 工具，会绕过文件系统直接读外部资源。AGENTS.md 也需要规定工具的使用边界。
- **放错文件位置**。OpenClaw 从工作区根目录读取上下文，放子目录等于没放。

## 可复用建议

- **AGENTS.md 用清单体，不用散文**。每行一个规则，方便 LLM 检索。
- **把人工判断的规则也写进去**，比如"如果输入文件和上次一致，跳过处理并告知用户"。
- **设置一个"遇到不确定事项时"的兜底策略**。例如：停止执行并列出选项，而不是瞎猜。
- **定期让 Agent 审计自己是否遵守了 AGENTS.md**。一个简单的定时任务就能完成。
- **版本化维护**。AGENTS.md 本身就值得纳入版本管理，每次修改都带一个简短提交说明。

## 总结

OpenClaw 越往深水区走，越会意识到一个问题：Agent 能力的天花板，往往不在推理层，而在**上下文设计**。AGENTS.md 不是魔法，但它把"Agent 应该如何理解这个空间"这件模糊的事，变成了一份明确可执行的规范。

对于跑批量任务、挂 MCP、接多插件的工作流，AGENTS.md 是一个提升稳定性、降低返工率的基建级投入。花二十分钟写好，它能省下后面无数个"为什么又跑错了"的排查时间。
