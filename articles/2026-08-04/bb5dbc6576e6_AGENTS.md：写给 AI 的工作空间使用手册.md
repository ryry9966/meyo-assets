### 背景

OpenClaw 的使用者通常会挂几个 MCP server、接一组插件、再配一些自动化任务。能力多了之后，工作区里堆满了脚本、配置和输出文件。问题在于：每次新会话开始，agent 对工作区几乎是零认知，路径靠猜，命令靠试，规则靠人反复口述。口头交代一两次还行，十几次之后必然走样。

AGENTS.md 就是解决这个问题的：在项目根目录放一份给 agent 读的说明书，让每次会话都有同样的上下文起点。

### 为什么需要它

没有 AGENTS.md 时，典型场面如下：

- agent 找到 `scripts/`，但不知道哪个是入口，挨个试探；
- MCP 工具权限没界定，agent 顺手调用了写接口；
- 你明确说「用构建脚本」，agent 却执行了 `npm run dev`；
- 换一台机器，环境变量路径变了，agent 依然按旧地址运行。

这不是 agent 能力不行，是工作区缺少上下文锚点。AGENTS.md 就是那个锚点。

### 做法

1. **放在工作区根目录**。文件名固定为 `AGENTS.md`，不要放进子目录。以工作区根为基准，方便后续所有工具统一加载。
2. **结构控制在四节内**：概览（一两句话）、目录说明（路径和用途）、常用命令（参数写死）、禁止项与决策规则。
3. **写明工具边界**。在文件里区分哪些 MCP 工具可自动执行、哪些需要确认。例如：`sqlite_query` 允许只读；`fs_write` 执行前必须询问用户。
4. **挂钩子校验**。用 `git pre-commit` 检查 AGENTS.md 中列出的关键路径是否仍然存在，防止文档与实际结构漂移。
5. **纳入版本控制**。AGENTS.md 随代码一起提交、一起走 review，规则变更本身就是代码变更。

一个可用的起始模板：

```markdown
# AGENTS.md

## 概览
本工作区是自动化实验室，所有脚本只处理本地数据。

## 目录
- scripts/ -> 可执行脚本，禁止修改
- data/    -> 输入数据，只读
- output/  -> 运行结果，允许覆盖

## 常用命令
- 构建：python scripts/build.py --prod
- 测试：pytest tests/

## 规则
- 路径不确定时，先列出候选再执行
- MCP 写操作必须先征求用户同意
```

### 踩坑点

- **写太长**：一份几百行的规则文档会被 agent 当噪声忽略。200 行以内，把最高频操作放在前 30 行。
- **规则太抽象**：「小心处理数据」不如「不要运行 `scripts/cleanup.py`」。大模型对模糊指令的泛化结果不可控。
- **权限一刀切**：完全开放会让 agent 做出危险操作，完全锁死则让它没法干活。按工具分级别写，比一句「谨慎使用」有效得多。
- **只写做什么，不写为什么**：缺了原因，规则无法迁移到相似场景，agent 换个问法就不会了。
- **忘记同步**：目录改名后 AGENTS.md 失效，agent 按旧路径一路报错，排查半天才意识到是文档过期。

### 可复用建议

- 把 AGENTS.md 当作公开 API 来设计：面向未来可能接入的任意 agent 实例，而不是只适配当前这个。
- 准备一份 `AGENTS.md.template`，新工作区直接从模板复制，而不是从空白开始。
- 在 MCP 配置里维护「只读 / 可写」清单，与 AGENTS.md 中的规则一一对应。
- 改规则时留一行变更记录，方便排障时回到「上次改了什么」。
- 定期用不同 agent 实例跑一遍核心任务链，验证说明书是否仍然有效。

### 总结

AGENTS.md 没什么神奇的，它只是把「你希望 agent 如何理解这个工作区」变成可评审、可版本化的文本。少写形容词，多写路径、命令和边界。每踩一次坑，就把经验浓缩回文件里，坑变成文档，下个会话的 agent 就不会再踩一次。
