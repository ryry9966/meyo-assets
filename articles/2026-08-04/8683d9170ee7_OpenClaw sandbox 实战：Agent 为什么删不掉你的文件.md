把 Agent 接进终端后，很多人第一反应是：它会不会顺手执行一条 `rm -rf ~`，把家目录清空？这种担心不算过度——大模型生成命令是概率性的，面对符号链接、通配符展开、带空格的文件名时，误操作概率比我们想象的高。OpenClaw 的 sandbox 机制就是为了解决这个问题存在的，但它的定位、边界和正确用法，值得从工程角度重新梳理一遍。

## 问题本质

直接给 Agent 终端权限，等于把系统完整性交给一个“大多数时候正确”的黑盒。指望模型“别犯错”是不现实的，现实的做法是：即使它生成了有害命令，系统层面也要让它执行不了。这个思路叫“故障止损”，而不是“AI 驯化”。OpenClaw sandbox 做的是后者。

## OpenClaw 的三层防护

**第一层：命令分类。** OpenClaw 对命令做了三类划分：

- `ls`、`cat`、`pwd` 这类只读命令：直接放行；
- `rm`、`mv`、`curl 管道到 sh` 这类破坏性或不可逆命令：要么要求人工确认，要么直接拒绝；
- `sudo`、磁盘分区、内核参数修改等：默认禁止。

这层拦截发生在命令执行前，是最快的一道闸门。

**第二层：文件系统隔离。** 当启用 sandbox 后，Agent 看到的文件系统是“裁剪过的”。它只能访问工作目录及显式授权的路径，`/etc`、`/usr`、家目录里的其他位置对它来说不存在。即使模型真的生成了 `rm -rf ~/.ssh`，沙箱会在路径解析阶段直接报 permission denied——因为它根本看不到那个目录。

**第三层：审计日志。** 每次命令执行、访问尝试（包括被拒绝的）都会记录到 `~/.openclaw/logs/`。后续复盘 Agent 行为时，这里是最可靠的证据来源。注意：审计不是为了追责，是为了定位配置问题。

## 配置步骤

以本地 Linux 环境为例：

1. 编辑配置文件 `~/.openclaw/openclaw.json`：

```json
{
  "enable_sandbox": true,
  "sandbox": {
    "work_dir": "~/projects/agent-workspace",
    "allowed_paths": [
      "~/projects",
      "~/Downloads/input_data"
    ]
  }
}
```

2. 确保 `work_dir` 已存在，并且里面只放 Agent 任务需要的文件。
3. 重启 OpenClaw 服务，然后在会话里让 Agent 尝试 `rm -rf /tmp/testfile`，观察它如何被拒绝。

## 踩坑记录

**坑 1：npm install 报 EACCES。** 某些任务需要全局安装 CLI 工具，sandbox 默认禁止写 `work_dir` 之外的位置，于是报权限错误。这不是 bug，是约束在起作用。解决方案是：在 sandbox 外预先安装好，或者把目标目录加进 `allowed_paths`——但谨慎评估必要性。

**坑 2：无法读取网络配置。** 有的任务需要读 `/etc/hosts` 或 `/etc/resolv.conf`，被 sandbox 挡住导致异常。先问自己：Agent 真的需要这个信息吗？如果只是常规自动化任务，多半不需要。如果确实需要，把它拷贝到工作目录里再让 Agent 读，比直接开放系统目录更安全。

**坑 3：把 sandbox 当保险箱。** 有人开了 sandbox 之后，把 API key、数据库密码直接放进 `work_dir`。这是非常危险的误解。sandbox 只约束 Agent 的“越界访问”，但 `work_dir` 内的文件对 Agent 是完全透明的，它可以随意读取和删除。**sandbox 不是安全边界，只是故障边界。**

**坑 4：Windows 上的行为差异。** 目前 sandbox 在 Linux 下的隔离最完整，Windows 受文件权限模型限制，部分命令的拦截粒度不如预期。生产环境建议优先跑在 Linux 容器或 WSL 2 里。

## 可复用建议

1. **始终开启 sandbox**，包括本地单机环境，这能拦截 90% 的误操作。
2. **保持 work_dir 独立**，不要把整个家目录设为工作区。任务结束、确认结果有效后，及时归档或清理。
3. **用白名单，不用黑名单。** `allowed_paths` 只列必要目录，多写一个路径就多一块风险面。
4. **关键数据依靠版本控制。** Agent 要操作的重要文件，先提交到 Git。这样即使 sandbox 失手，也能低成本回滚。
5. **定期翻阅日志。** 看被拒绝的命令类型，调整配置。日志里往往藏着 work_dir 设计不合理、命令分类误判等线索。

## 总结

OpenClaw 的 sandbox 不是魔术，它是一套务实的工程约束：把“模型可能犯错”的概率事件，通过命令分类、文件系统隔离、审计日志三层结构，变成系统层面的低风险事件。但它的作用域有限——保护的是 `work_dir` 之外的东西，而不是 `work_dir` 之内。理解这一点，就不会神话它，也不会误用它。Agent 自动化的风险不是靠一个开关消除的，而是靠层次化的约束设计，逐层递减。
