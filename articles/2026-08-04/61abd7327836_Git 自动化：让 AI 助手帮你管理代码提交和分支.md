## 背景

很多 AI 编程实践者用 OpenClaw 帮写代码、修 bug，但代码改完之后的工作流——git add、commit、push、切分支、合分支——仍然停留在手敲命令的层面。如果你和我一样，一天在 IDE 终端和 AI 对话窗口之间来回切换几十次，会发现这块机械劳动虽然不费脑，却非常打断心流。

更现实的情况是：AI 生成的代码往往横跨多个文件，如果一股脑 `git add -A` 提交，commit 记录里会混杂大量不相关的改动，后期 bisect 或者 code review 的时候要花双倍时间去梳理。于是我开始尝试让 OpenClaw 代理帮我完成 Git 的日常操作。

## 问题

直接把 Git 操作丢给 AI 助手，会遇到几个明显问题：

- **全量暂存**：AI 默认倾向执行 `git add -A`，把工作区所有改动推到一个 commit 里，粒度不可控。
- **上下文丢失**：AI 不知道一条 commit message 该怎么写，除非你显式告诉它当前改动的业务背景和模块边界。
- **远程同步失败**：代理跑在容器或远端环境里，SSH key 未挂载、用户未配置，push 静默失败或报错不直观。
- **分支策略混乱**：在没有明确规则时，AI 可能切出一个命名随意的分支，或在不该直接提交的分支上提交。

## 做法 / 步骤

我目前的方案是：**用 OpenClaw 的 Agent 原生能力，加一套显式的 Git 操作规则，用自然语言驱动 MCP/内置工具完成日常工作。** 核心分以下几步。

### 1. 先让 Agent「看清楚」再动手

在让 Agent 操作 Git 之前，先配置环境级别规则，让每个会话默认执行：

```text
先运行 git status 和 git diff --stat，明确当前工作区改动，再根据下方规则决策：
- 只 stage 与你本次任务相关的文件
- 无关改动保持不动，并在回复中提示我
```

这条规则直接写进项目的 `AGENTS.md`（OpenClaw 会默认读取该文件），并不需要额外写代码。每次会话开始，Agent 就会先自查状态，而不是直接 `add -A`。

### 2. 定义提交信息生成模板

AI 生成的 commit message 往往太「营销」，比如 `feat: enhance user experience`。我在规则里加入了严格的模板约束：

```text
提交信息格式：
- 主题行：<type>(<scope>): <subject>，不超过 50 字符
- 正文：列出关键改动点，每条不超过一行
- 结尾：标注关联的 issue/task ID（如有）
- 禁止使用 "fix bugs"、"improve" 等模糊词汇
```

给一次 few-shot 示例比抽象描述有效得多。在 `AGENTS.md` 中给一个正例和一个反例，Agent 很快能对齐格式。

### 3. 批量提交的「逻辑分组」策略

当一次开发活动涉及多个文件的多个逻辑改动（比如修了一个 bug 同时加了一个小功能），我让 Agent 按以下顺序操作：

```text
1. git diff 当前改动，按文件归属划分逻辑组
2. 每组分别 stash、stage、commit
3. 完成后提交一条汇总信息给我确认
4. 我确认后才 push
```

这一步的价值最大——它把「提交」从手动清单变成了 AI 可以理解的任务单元。实现上主要靠 prompt 约定，不需要专门写插件。

### 4. 分支操作的约束规则

分支管理是另一个容易失控的领域。我的规则是：

```text
- 新分支命名遵循：<type>/<short-description>，如 fix/login-timeout
- 不允许在 main/master 分支上直接提交
- 如需创建分支，先问用户确认分支名和基分支
```

实际使用中，让 AI 去查当前 Git 工作树状态、计算前后分支关系并不太可靠，所以分支创建和切换的动作，我都会让 AI 通过 `git branch` 展示候选分支名，由我确认后再执行——人机各守一道，出错的概率低很多。

## 踩坑点

- **Shell vs MCP 工具的选择**：OpenClaw 内置的 Shell 工具可以跑任何命令，但权限过大。我遇到过 Agent 误把 `git clean -fd` 当成无害命令的情况——幸好有确认机制兜底。如果你用 MCP Git Server，建议限制写操作需要人工审批。
- **工作区「脏」文件**：AI 判断「是否我的改动」是通过文件名匹配的，但如果你有其他进程生成的文件（如日志、编译产物），Agent 会犹豫或误包含。解法是在规则里强制 `.gitignore` 审查。
- **SSH 认证的坑**：OpenClaw 跑在容器里时，git push 会因找不到 SSH key 报错。需要确认 `~/.ssh/config` 和 `known_hosts` 正确挂载，或者改用 HTTPS + token 的方式。
- **交互确认必须显式**：Agent 不会主动反问。你必须在 prompt 规则里写明「push 前必须询问用户同意」，否则它会自作主张，把半成品推到远端。

## 可复用建议

- **把 Git 工作流写进 `AGENTS.md`**，而不是依赖记忆。规则文件是项目的一部分，新人加入时也能复用。
- **先小范围试水**：先在个人仓库或 side project 上跑一周，看日志复盘 Agent 的决策，再移到团队仓库。
- **给 Agent 一个「干跑」模式**：在规则中让 AI 先输出要执行的命令清单（不执行），人工确认后改为「执行模式」，兼顾安全和效率。
- **每两周清理一次分支**：让 Agent 列出超过 30 天未合并的本地分支，由你决定删除与否——这条规则可以替代手动的 `git branch -d` 清理。

## 总结

Git 自动化不是把人类踢出循环，而是把机械动作交给机器，把决策留给人。OpenClaw 的 Agent 在理解项目上下文方面比脚本更强，但也更需要你给出清晰边界。目前这套流程给我的感觉是：日常琐碎操作确实解放了，但关键节点（push、merge、分支创建）保持人工确认，是长期稳定运行的前提。值不值得做？如果你和我一样每天 commit 超过 5 次，就值得。
