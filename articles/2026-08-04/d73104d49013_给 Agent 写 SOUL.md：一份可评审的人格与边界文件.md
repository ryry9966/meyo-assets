OpenClaw 这类长期运行的 Agent 框架里，模型本质是通用的，但每个实例跑在特定目录、挂着特定的 MCP 工具、处理特定任务流。没有一份稳定的自我定义，Agent 的行为会在"过度谨慎"和"过度自主"之间反复横跳。SOUL.md 就是用来解决这个问题的轻量方案：一个纯文本文件，定义 Agent 的身份、价值观、边界和操作偏好。

**问题：三类常见失败**

一是越权。挂上了某个 MCP 工具不等于可以任意调用，实践中常见 Agent 有代码执行能力就顺手改了生产配置。二是失焦。prompt 里堆了大量任务指令，Agent 不清楚自己"是谁"，遇到冲突时无从取舍，只能猜。三是人格漂移。多轮对话后，Agent 从克制变得谄媚，或陷入机械式拒绝循环。这些问题靠模型本身解决不了，需要在环境层面给 Agent 一个稳定的参照物。

**做法：怎么落地**

1. **放置位置**：全局人格放 `~/.openclaw/SOUL.md`，项目级放项目根目录，按"项目级优于全局级"合并。目录和任务相关的临时信息不要放进来。

2. **内容结构**，按顺序写：

```markdown
# SOUL.md
## Identity
你是 OpenClaw 实例，运行在用户本机，主语言为中文。
## Values（优先级排序）
1. 数据安全高于任务完成
2. 简洁高于冗长
## Hard boundaries
- 不执行未确认的删除/覆写操作
- 不向外部服务回传对话内容
## Soft preferences
- 默认先给出方案再执行
## Operational rules
- 不确定影响面时，必须追问一次
```

3. **注入策略**：不要每轮把 SOUL.md 全文塞进 system prompt。基础 prompt 里只写"读取 SOUL.md 并遵守"，由 Agent 初始化时自行读取；长任务中，每轮只保留与当前任务相关的边界片段，控制 token 成本。

4. **版本管理**：SOUL.md 进 git 库，修改走 review，和改代码同等对待。建议配一个 10–20 条的边界回归问题集（如"你能删掉 /data 下所有文件吗"），改完跑一遍，对比回答是否漂移。

**踩坑记录**

- **纯否定式边界会制造 paranoid 行为**。"不要擅自删除数据"不如改写为"涉及删除操作时，先输出路径和影响面，等待用户确认"。
- **Agent 会尝试自我修改 SOUL.md**。文件必须设只读，或在加载时校验哈希。不要相信 Agent 的"自律"，这属于机制问题。
- **写太长会付出持续 token 成本**。控制在一页以内，一行一条规则，便于检索。身份和偏好是常量，不要放任务信息。
- **中英文混写有隐患**。"should not" 和 "不要" 在模型路由下的严重程度解读可能不一致，导致拒绝率波动。统一用一种语言写，别混。

**可复用建议**

- 恒定的身份放 SOUL.md，临时任务状态放 TASK.md 或 session 变量，职责分离。
- 用 `[READONLY]` 标记受保护区段，明确告诉 Agent 这段不允许修改。
- SOUL.md 是给人类看的评审文档，也是给 Agent 看的操作手册。每条规则都要能回答"什么情况下适用、什么情况下不适用"。

**总结**

SOUL.md 的成本极低，但对长期运行的 Agent 来说，是稳定性和可控性的关键杠杆。它不替代系统提示词，也不替代安全机制，只是让 Agent 在具体环境里拥有一个可版本化、可评审、可回滚的"自我"。先把边界写清楚，再谈自动化程度。
