## 背景

平时维护一个中型前端仓库，分支常年保持在二十个以上。feature 分支合并后忘删是常态，过时分支和 main 的 diff 越漂越远，等真正需要切过去看的时候，rebase 的成本已经高到不想动。

之前试过持续集成里挂分支清理脚本，但效果一般——规则太死（按时间一刀切容易误删），规则太活（全靠人工确认）又等于没自动化。

后来把 Git 接入 OpenClaw 的 MCP 工具集之后，发现正确的姿势不是让 AI 替你拍板删哪条分支，而是让 AI 先建立分支全景视图，把"哪些分支确实死了、哪些还活着"这件事搞清楚，然后你只需要在它的建议列表里打个勾。

## 问题：人工巡检 Git 分支的静态盲区

人工检查分支状态，通常是 `git branch -a` + `git log` 的组合拳，整个过程有两个痛点：

一是信息分散。分支的提交时间、与主干的分歧程度、对应的 MR 是否已合并，分散在不同的命令和页面里，凑齐这些信息需要来回切上下文。

二是判断依赖经验。一条分支该不该删，不仅要看时间，还要看 diff 规模、是否已经被 MR 合并、有没有未推送的 commit。这些判断规则写死在脚本里很别扭，但让 AI 穷举一下却很合适。

## 做法：用 OpenClaw 搭一个"分支体检 + 清理建议"管线

我用的交互端口是 OpenClaw 的 Git MCP 工具，流程拆成三步。

**第一步，让 AI 汇总仓库分支状态。**

给 OpenClaw 的指令类似：

```
请先执行 list_branches 获取所有本地和远端分支，
再对每条分支执行 get_branch_commits 拿最近提交时间，
最后统计每条分支相对 main 的分歧 commmit 数。
按"已合并可删 / 分歧过大需关注 / 长期未动"分组输出。
```

这个指令的价值不是让它执行命令——命令我都会敲，**价值在于它把三个维度的信息聚合进同一份报告**，分组方式比人肉记要清晰。

**第二步，要求 AI 遵循默认的 dry-run 策略。**

真实环境里最重要的是别让 AI 手滑把分支推上生产。我在提示词里显式声明：

```
除非我明确说"执行清理"，否则只输出删除建议，
每个删除操作必须以 dry-run 形式展示
（提示删除分支后会导致哪些 commit 不可达）。
```

OpenClaw 的 Git MCP 工具里如果支持 `dry_run` 参数，务必传 true；如果不支持，就用 `git branch -d` 这种自带安全校验的形式代替 `-D`。

**第三步，对 AI 识别出的"危险分支"做人工确认。**

实际执行时，AI 报出三条已经合并进 main 的旧分支，以及一条 diff 了 300+ commit 的僵死分支。前三条直接让 AI 执行删除，僵死分支保留了——但保留下来的同时，让 AI 为它生成了一份"是否 rebase 到 main"的决策备忘，挂在 issue 里备查。

## 踩坑点

**1. MCP 工具是只读视角，干不了重活。**

部分 Git MCP 实现只暴露查询类工具，没有 `delete_branch` 这种写操作。这时候别硬想用自然语言让 AI 变出写权限——正确做法是把 AI 的输出（分支清理清单）通过 OpenClaw 的自动化流程接到 CI 脚本或本地 shell 执行。AI 负责判断，脚本负责执行，各干各的。

**2. 分支时间不等于分支健康度。**

早期版本我用 `get_branch_commits` 取最近提交时间，然后让 AI 删除"90 天未更新"的分支。这个规则引发了误伤：有一些分支只是暂时冻结，下个迭代还要复用。后来改成对比 MR 合并状态（脚本里查 merge commit 里是否包含该分支的 head commit），准确率高很多。

**3. AI 对歧义分支名会自作主张。**

有个分支叫 `fix/login-style`，实际内容是一整套登录流程重构。AI 根据名字判断成小改动，建议直接合并删除。人工确认时发现 diff 有 40+ 文件，果断拉回来。所以 Git 自动化必须保留人工 confirm 环节——至少对 diff 规模大于 20 文件的分支，强制要求人工介入。

## 可复用建议

- **提示词里要显式要求 AI 先列信息、再下结论。** 比如让它区分"哪些分支仅领先 main 几个 commit（可快进合并）"和"哪些分支有大量分歧"。
- **默认所有删除操作都走 dry-run。** 不管 MCP 工具有没有实现这个参数，给 AI 的指令里都加一句"删除前先输出影响范围"。
- **分支状态汇总报告做成可复用提示词。** 我存了一个 `/git_summarize` 的自定义命令，每两周跑一次，输出直接贴进周报，顺带完成一次仓库健康巡检。
- **如果想让 AI 顺手改代码，请把 Git 仓库单独挂一个 MCP 实例。** 不要让 AI 在一个既管文件读写又管 Git 操作的实例里同时工作，一旦上下文被长输出刷掉，分支状态容易失真。

## 总结

这件事做下来，最大的体感变化是"分支管理"从一个需要定期腾出半小时的维护动作，变成了一个随时可调用的监控服务。AI 的价值不在于替你做删除决定，而在于它把人肉巡检时的信息聚合成本降到了零——你只需要在它生成的清单上做最后的判断。

Git 的自动化没必要一上来就想做到全自动推送、自动合并、自动发版。先把"分支体检 + 清理建议"这个低频高风险的场景跑顺，把 AI 的权限边界和人工确认点定义清楚，后续再往上游推进就会自然很多。
