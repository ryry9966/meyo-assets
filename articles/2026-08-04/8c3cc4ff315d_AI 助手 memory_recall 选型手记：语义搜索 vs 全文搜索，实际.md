## 背景

Agent 的记忆子系统，本质是把历史对话转成可持续检索的索引。memory_recall 决定「该翻哪段旧账」：一类做法是把对话切成 chunk 后 embedding 进向量库，靠语义相似度召回；另一类是建倒排索引，用关键词精确匹配。很多团队在没有对照实验前就默认「语义搜索一定比全文搜索好」，实际工程里结论没那么干净。

## 问题

Agent 场景的 query 有两类，分布很不均匀：

- 精确片段：方法名、error code、commit hash、配置项、文件名
- 语义表达：同义改写、跨话题联想、指代消解

语义搜索对后者有效，但前者的关键信息一旦被 embedding 泛化，精确字符就丢了。全文搜索精确匹配没问题，却在同义改写和跨话题上直接漏检。选型不能拍脑袋，要回到自己的对话数据上做对照。

## 做法 / 步骤

我拿 2000 条真实对话记录做了个对照实验：

1. 同一份数据写两条索引：向量库（bge-m3）和 FTS5 全文索引。
2. 构造三类 query 各 20 条：精确复现（原句重现）、改写复现（同义换词）、跨话题（只含语义关联）。
3. 按 top-5 命中率打分。

结果很典型：

| query 类型 | 全文搜索 top-5 命中率 | 语义搜索 top-5 命中率 |
|---|---|---|
| 精确复现 | ~95% | ~60% |
| 改写复现 | ~30% | ~85% |
| 跨话题 | ~0% | ~70% |

数据说明：没有绝对优劣，只有适用边界。

## 踩坑点

1. **切块大小影响召回**：512 token 和 128 token 的 chunk 在语义检索里结果差异很大，必须跟你 prompt 里实际使用的上下文长度对齐，别沿用默认值。
2. **FTS5 对中文不友好**：默认 unicode61 tokenizer 会把中文按单字切，必须换 trigram 或提前用 jieba 预分词，否则全文搜索基本失效。
3. **别用 metadata filter 做时间衰减**：在向量库上过滤的效率低，用独立字段或 score 修正项更直接。
4. **score 量纲不同，不能直接加权**：语义检索和全文检索的分数分布差异大，先 min-max 归一化，或者干脆用 rank-based fusion。

## 可复用建议

- **默认用 RRF 做 hybrid**：`RRF = Σ 1/(k + rank)`，k 取 60。不需要调参，稳定兜底。
- **加一个 query 类型探测器**：如果 query 含代码符号、hash、错误码、文件名，优先走全文检索；纯自然语言才走语义。这是一个简单的正则或规则分支，别一上来就上分类模型。
- **增量同步索引**：监听对话落盘文件增量写索引，避免每次全量 reindex。
- **做一个 recall 回归测试集**：挑 50 条历史 query 存成 fixture，每次换 embedding 模型或改分词器后跑一遍，防止隐性退化。

## 总结

语义搜索和全文搜索不是替代关系，是互补关系。全文搜索保底，语义负责泛化，RRF 做融合，再按 query 特征走分支。别迷信模型提供商的宣传语，回到自己的数据上做对照实验，成本不高，收益是确定的。
