## 背景

用了 OpenClaw 一段时间后，你会发现一个尴尬的事实：Agent 真正危险的时候不是它不懂，而是它太懂了。

跑一次任务链，Action Server 上十几个工具待命，MCP 接好了文件系统、数据库、浏览器、IM。一个 LLM 调用重试三次，它就认为自己理解了意图，顺手把过期的测试数据覆盖了。这种事发生了，你才会意识到——权限设计不是在写配置文件，是在给 Agent 划安全线。

## 核心问题

“该问人类还是自己干”不是一个主见问题，是一个安全模型问题。

我们在 OpenClaw 里定义 Agent 行为时，实际上在定义三件事：
1. Agent 对外部世界的**影响半径**（能碰什么）
2. 影响不可逆时的**中断条件**（什么时候必须停）
3. 用户信任的上限（什么操作可以事后追认）

如果这三个问题没有显式确定，Agent 的行为就会退化成“听 prompt 的”。而 prompt 是可以被污染的——来自网页内容、来自文件名、来自一封邮件。这不是假设，是每天都在发生的事。

## 我的做法：事件灵敏度 + 行动分级

我做了一套简单实用的分级方案，核心就两条：

### 1. 先做敏感度分级，而不是做“重要程度”分级

“重要”是主观的，AI 判断不了。但**敏感度是客观的**，可以通过规则枚举。

在 OpenClaw 的 agent 配置里我加了一层前置过滤器，对工具调用做事件分类。关键判断标准就一条：

> 这个操作在 10 秒后还能不能撤销？

**可以撤销的，自己干：**
- 读取文件、搜索、爬取公开页面
- 生成草稿、写入临时目录
- 创建新文档（非覆盖）
- 对某个服务发起只读请求

**不可撤销的，停下来问：**
- 覆盖/删除任何已有文件
- 给外部发送消息（IM、邮件）
- 修改配置、切换分支、推送代码
- 花钱（调用付费 API、下单）

### 2. 采用“先做后报”和“先问后做”的混合策略

对于大部分**具体数据操作**（重命名一组文件、批量格式转换），走“模拟执行 → 输出 diff → 用户确认”。对于**链式决策**（依赖不确定上下文的多步推理），走“先执行只读部分 → 给出下一步计划 → 等确认”。

实际操作里，我会在 OpenClaw 的 workflow 里插入一个 human-in-the-loop 节点，放在不可逆操作的紧前面。这个节点不要求用户输入自然语言，只要求一个 `confirm` 或 `deny`。问题越简单，用户越愿意确认；问题越复杂，用户越容易跳过——所以确认信息必须包含：要做什么、影响哪些对象、预计恢复方式。

## 踩过的坑

### 坑一：Agent 自己确认了自己的输出

之前给 OpenClaw 接了浏览器自动化。Agent 通过 MCP 调 browser 工具，执行完自己生成的 JS 脚本后，拿到返回结果就算“验证通过”。

后来发现网页上有动态加载的内容，脚本执行时元素还没渲染出来。Agent 把空结果当成正常结果，继续走下一步，直接覆盖了本地快照文件。

教训：**Agent 的自我验证闭环是不可信的。** 需要人类确认的节点，不能用同一个 Agent 的判断结果来替代。

### 坑二：确认机制太频繁，导致用户麻木

一开始我把所有写操作都设成“每次都要问”。结果 10 分钟的任务弹出 20 次确认框，用户直接点了“全部允许”。等于没有权限控制。

教训：确认要集中在真正的决策点上。清理临时文件、下载缓存这种，直接开白名单放行。只保留对不可逆操作的确认。

### 坑三：多层 LLM 架构下，上下级之间没有约束

OpenClaw 允许 workflow 里嵌套子 Agent 调用。如果子 Agent 能直接操作父 Agent 的工具，那父级的权限控制就是摆设。

我们发生过一次：一个负责信息提取的子 Agent 拿到了一段脱敏要求不严格的文本，直接把临时文件内容发到了协作群里。因为子 Agent 继承了父级全部工具权限。

教训：如果架构有多层 Agent，权限要做**逐层收敛**，而不是共享同一套凭证。子 Agent 只能拥有完成任务所需的最小权限集。

## 可复用建议

1. **把“确认”设计为带上下文的卡片，而不是弹窗**。展示操作对象、影响范围、预估恢复方式。上下文越清楚，误点的概率越低。
2. **每次任务结束后导出审计日志**。OpenClaw 的任务跑完了，记下哪一步有确认、哪一步自动执行了。日志是复盘权限配置是否合理的唯一依据。
3. **给不同的工作区不同的敏感等级**。比如 `~/workspace` 下可以自动折腾，`/data/prod` 下所有写操作必须确认。不要用同一套策略管所有目录。
4. **新集成的 MCP 或插件，默认先设为“全部操作需确认”**。跑几轮没问题后，逐步放开一部分明确安全的操作。

## 总结

权限边界这件事，不应该是模型靠“理解”来把握的。越是能力强的 Agent，越需要外部硬约束。

在 OpenClaw 这样的系统里，权限边界不是一层，而是两层：技术层决定 Agent 能做什么，交互层决定它在什么条件下会停下来问人。前者是接口配置，后者是产品设计。

你不需要一个更聪明的 Agent。你需要一个知道自己在什么时候不够聪明的 Agent。

而这件事，只能靠我们做配置的人来保证。
