## 背景：Agents 都在等指令，但用户已经累了

过去一年里，社区里跑得通的 Agent 工作流，绝大多数是 reactive 的：用户发消息，Agent 回消息，用户再补充，Agent 再执行。这个循环最大的问题不是模型能力不够，而是交互疲劳——你为了拿一个摘要，要打字告诉它去哪拿数据、用什么格式、发到哪。

OpenClaw 这类本地优先的 Agent runtime 给了我们一个机会：既然 agent 常驻本地、有完整的工具调用栈和 MCP 通道，它理论上可以看到文件系统变化、收到 webhook/消息事件、感知日历和 Git 活动。换句话说，`proactive` 能力的工程基础已经成熟，只是很少有人系统性地把它组装起来。

## 问题：proactive 不是"定时说早安"

很多人的第一个尝试是 cron 式触发：每天早上 8 点让 agent 汇报天气和日程。这确实是 proactive，但只是最浅的一层。真正的 proactive 是 **不等用户下达指令，Agent 从环境事件中自行判断"现在做这件事对用户有价值"，然后执行并交付**。

要完成这个闭环，需要回答三个问题：

1. **什么时候该动？** 触发条件要从哪来，怎么避免误报导致用户反感？
2. **该做成什么样？** 执行策略是让 LLM 自由发挥，还是模板化、规则化？
3. **怎么让用户信任它？** 如果 Agent 自作主张发了邮件、改了文件，风险怎么兜底？

## 做法：从事件驱动到策略执行

我的做法分三层：事件接入层、策略决策层、执行与兜底层。

### 第一层：事件接入（MCP + 文件监听 + 消息通道）

不要用 cron 做唯一触发器。真正的 proactive 通常来自"变化"：

- **文件系统事件**：用 `chokidar` 或系统级的 `fswatch` 监听任务目录，发现新文件即刻推送给 agent。
- **消息通道**：接 Telegram/邮件 webhook（通过 MCP server 暴露为工具），收到特定类型消息（比如客户邮件、付款通知）即触发。
- **定时作为兜底**：cron 只用来做"检查是否该动"，而不是"直接执行"。比如每小时检查一次收件箱里是否有 24 小时未回复的重要邮件。

### 第二层：策略决策（先规则，后 LLM）

让 LLM 每次判断"要不要主动做事"很危险，不可控且浪费 token。更稳妥的策略是：

- 写一个轻量的**策略引擎**（一个 JSON 或 YAML 文件即可），定义触发条件映射到动作建议。
- 例如：`{"trigger": "new_file_in_inbox", "action": "analyze_and_summarize", "target": "feishu_notification"}`。
- LLM 只参与执行环节，不参与触发判断。判断用确定性逻辑完成（文件 mtime、proactive 关键词匹配、MCP 返回的 event schema 的字段）。

### 第三层：执行与兜底（批准、隔离、幂等）

proactive 最怕的是执行错动作。我的约束是：

- **低风险动作直接执行**：生成摘要、整理文件、打日志通知，不需要用户确认。
- **中高风险动作进 pending 队列**：发邮件、修改远程仓库、删除文件——至少要在 notification 里给一个 30 秒内可撤回的确认按钮。
- **所有动作落盘为专用目录**：`~/.openclaw/proactive_logs/`，每一条记录触发事件、决策链、执行结果，方便回溯。

## 踩坑点

1. **触发条件太松导致"狼来了"效应**。第一次跑通时，我配置了"邮件中含 invoice 就自动提醒"，结果一个 50 人的邮件列表每天触发 20+ 次。后续加了白名单发件人 + 主题关键词双条件过滤。
2. **LLM 做判断时的延迟不可忽略**。直接把事件喂给 LLM 决策，响应时间要在 2~10 秒，放在实时链路里体验极差。现在触发判断完全走规则路径，LLM 只在执行阶段出现。
3. **时间类触发的坑比事件类多**。"每两小时检查一次"在实际运行中会漂移，因为 agent 进程可能被挂起。建议每次循环末尾自校正下一次触发时间，而不是依赖系统的定时器。
4. **策略文件最开始用纯文本维护**，后来发现条件多了容易冲突。建议从一开始就按 `trigger_id` 做索引，并加一个简单的 condition 优先级字段。

## 可复用建议

- **先跑日志，再跑动作**。第一步只让 agent 把"检测到的变化 + 它打算做什么"写进日志，看一周，再放开执行权限。这一步能帮你校准触发条件的准确率。
- **偏好文件要版本化**。agent 的 proactive 策略本质上是你个人偏好的编码，建议用 Git 管理。回滚成本低，试错意愿就会高。
- **执行动作的 prompt 是模板，不是散文**。给出固定的执行格式（输入字段+输出 schema），LLM 的输出会自动对齐你的后续自动化管线。
- **把执行结果回写为 MCP 事件**。这样即使你换前端或换客户端，事件流不会被锁死在某一个 UI 里。

## 总结

Proactive 能力的核心壁垒不在模型，而在工程链路。OpenClaw 社区里最实用的做法是：用确定性的规则做触发，用 LLM 做执行，用日志和回滚机制兜底。等你跑通第一个"新邮件进来自动生成摘要并发到 IM"的流程后，你会意识到——Agent 的价值不只是回答得更准，而是开始替你盯着那些本该盯着的信号。
