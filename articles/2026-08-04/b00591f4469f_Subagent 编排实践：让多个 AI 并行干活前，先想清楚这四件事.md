# 背景：串行是最大的隐性成本

单 Agent 处理复杂任务时，最常见瓶颈是"串行"。无论是一次多源调研、批量文件处理，还是信息汇总，所有步骤挤在同一个上下文窗口里依次执行——既慢，又容易在中途丢失状态。Subagent 编排的思路很直接：把任务拆开，让多个 AI 各干一段，并行推进再汇总，最终由主 Agent 收口。

OpenClaw 里落地这条路有几种方式：通过 orchestrator 规划任务清单并分发到多个 subagent；或者结合 MCP 工具，让不同 subagent 访问不同数据源，减少上下文互相挤占。实践中真正难的不是"把任务发出去"，而是任务拆分的质量。

# 问题：拆出来的任务，往往并不独立

不少第一次做 subagent 编排的人会踩同一个坑：拆出来的子任务看起来相互独立，运行中却有隐性依赖。比如三个 subagent 分别做资料检索、市场分析和竞品对比，表面并行，实际上分析需要检索结果，竞品对比又依赖分析结构——执行时被迫等待，最终退化成串行，还白搭一层调度开销。

另一个常见问题是输出不设约束。Subagent 返回自由文本，主 Agent 解析时反复失败，重试成本直接翻倍。没有 schema，就没有稳定的程序化消费方式。

# 做法：五步落地并行编排

我建议按以下步骤实施：

1. **先画依赖图，再写 prompt。** 把目标拆成最小可独立执行单元，用 `A -> B: 数据格式约定` 这样的标注记录依赖。依赖越少，并行度越高；并行度不高的任务，不要强行编排。

2. **为每个 subagent 定义 I/O 契约。** 输入输出都用 JSON Schema 描述，输出不允许出现 schema 之外的字段。这能极大减少下游解析成本，也便于主 Agent 校验。

3. **orchestrator 只做调度，不做业务。** 主 Agent 的职责是拆任务、下发、收集、校验、合并。具体内容生成全部下沉到 subagent，主 Agent 上下文保持干净——这也直接缓解了长任务里的上下文污染问题。

4. **实现超时、重试与熔断。** 每个子任务设置明确超时。失败重试一次；连续失败则标记该子任务失败，由主 Agent 决策降级策略：跳过、换路径或整体终止。

5. **保留可观测性。** 每个子任务带唯一 task_id，记录开始时间、结束时间、token 消耗和最终状态。没有这层数据，调试编排问题基本靠猜。

# 踩坑点

- **上下文投喂过度**：把完整背景文档发给每个 subagent，看似贴心，实际浪费 token 且干扰输出。只传该子任务真正需要的片段。
- **幂等性缺失**：重试时子任务重复执行，副作用不可控——重复写文件、重复调外部 API 都是真实事故。Subtask 要设计成幂等，或重试前先检查执行痕迹。
- **层级过深**：subagent 再开 subagent，三层以上后错误定位和成本归属都会失控。建议最多两级，超出就拆流程。
- **对输出稳定性期望过高**：并行模式下的 LLM 输出质量波动比单线程更大。同一任务跑两次，结果可能不一致。需要稳定产出的场景，必须加校验层。

# 可复用建议

- 先做小规模验证：3 个子任务并行，量好耗时与 token 成本，再决定是否扩大规模。
- 把任务拆分逻辑和 subagent 定义写成可配置的清单文件，而不是硬编码在 prompt 里。这样调整并行策略不动代码。
- 保留一条逃生通道：编排失败时能一键退回单 Agent 顺序执行，确保核心任务不被调度复杂度阻塞。

# 总结

Subagent 编排的价值不在"多个 AI 一起干活"这件事本身，而在于通过工程手段把任务结构化，让并行成为自然结果。核心是四件事：拆分质量、I/O 契约、调度隔离、可观测性。这四件做到位，并行编排就稳定可用；做不到位，它只是把串行问题换了个更复杂的形式重演一遍。
