## 背景

OpenClaw 的 cron 调度看起来简单：写一段 instruction，定好时间，跑起来。但很多同学的定时任务跑一两周后开始"摆烂"——要么输出格式混乱，要么直接空跑，要么把编造的数据写进报告。问题大多不在调度器，而在 instruction 的写法。

交互式会话里，agent 拿不准会问你；cron 里没人在线，prompt 就是唯一且最终的输入。所以 cron 的 instruction 本质上是一个函数签名：明确的入参、明确的输出、明确的失败行为。

## 问题

常见的三种翻车：

1. **澄清式翻车**：instruction 里写了"如果有疑问请先确认"，凌晨三点没人确认，任务挂死。
2. **兜底式幻觉**：数据源拿不到，agent 为了"完成任务"编数据。因为 prompt 里写了"今天必须出报告"。
3. **格式漂移**：第一天输出 Markdown 表格，第二天输出 JSON，下游取数脚本直接炸。

## 做法

我给 cron 任务写 instruction 的标准结构是五段：

**1. Goal（一句话）**：明确这次执行要产出什么，不写过程。

> 例：生成昨日各渠道订单环比分析，并写入指定 Notion 页面。

**2. Inputs（显式列出可用输入）**：把数据文件、数据库表、上游接口明确列出来，并说明"只允许使用这些输入"，防止 agent 自己脑补来源。

**3. Steps（编号步骤）**：最多 5 步，每一步是一个动作，不是建议。步骤里写明顺序依赖。

**4. Output Contract（输出契约）**：最关键的一段。指定格式（Markdown 表格 / JSON Schema）、字段名、写入目标（哪个文件/页面/bucket），并附一个样例输出。样例的价值在于把"格式"从抽象变成具体。

**5. Failure Behavior（失败行为）**：明确写"如果拿不到 X，停止并输出错误报告，不要编造数据"，以及"如果本次无数据更新，输出 no-op 即可，这属于正常情况"。

## 踩坑点

- **cron 没有上下文**。不要在 instruction 里写"根据上次的结果"，除非你确认持久化记忆真的可靠。我给每个 cron prompt 写死"本次执行独立，忽略历史对话状态"。
- **时区和"昨天"**。cron 触发时"昨天"是什么，取决于服务器时区。直接用日期参数替代相对时间词，例如 `DATE=$(date -d "yesterday" +%F)` 传入 instruction。
- **不要写"请尽力完成"**。这句话会让 agent 在失败时选择补全而不是上报。成功标准要写清楚：什么算完成，什么算部分完成，什么算失败。
- **指令里不要留破绽**。我见过有人写"输出 JSON"，但没指定字段，agent 按自己的习惯输出，下游解析失败。指定字段名并附上"严格按此 Schema，不要增减字段"。

## 可复用建议

1. 把 cron prompt 和代码一样管：写进 git，每次修改记变更原因。cron 任务出问题时，第一件事是看 prompt 改过没有。
2. 上线前做干跑测试：手动触发同一份 prompt，检查输出契约是否严格满足，再挂到 cron 上。
3. 设计一个"对账"机制：任务执行后写一行执行摘要（耗时、输入来源、成功/失败状态）到日志文件。不需要复杂，够排障就行。
4. 不要复用交互式 prompt。交互式 prompt 追求对话质量，cron prompt 追求确定性。宁可多写 200 字约束，也不要在凌晨三点收到一份编造的报告。

## 总结

Cron 任务的 instruction 写得好的标志是：任何一个刚接手的人（或一个全新的 agent 实例）读到它，不需要任何补充说明，就能稳定产出符合预期的结果。把 prompt 当函数签名来写——输入明确、行为确定、失败可观测。这比任何"高级 prompt 技巧"都管用。
