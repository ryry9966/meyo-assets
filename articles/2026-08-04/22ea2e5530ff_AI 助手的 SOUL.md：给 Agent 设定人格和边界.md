## 背景

把 Agent 接进自己的工作流之后，最先发现的往往不是它不够聪明，而是它不够稳定。同一个任务，上午执行得很干净，下午就开始自作主张；换个上下文窗口，连说话口气都不一样了。OpenClaw 这类 Agent 框架本质上是把模型、上下文和工具粘在一起，但模型的默认行为是"通用"，不是"你的"。

所以问题不是"怎么让 Agent 更聪明"，而是"怎么让 Agent 按你的规则工作"。SOUL.md 就是为此存在的：一个项目级的 Markdown 文件，显式定义 Agent 的自我认知、沟通风格和边界，每次会话都会随上下文加载。

## 问题

只靠系统提示词（system prompt）不够，原因有三：

1. **会被淹没**：系统提示词经常被长上下文挤到后面，模型对靠前内容的关注度会下降；
2. **不可版本化**：改了没法回滚，团队协作时也没法 review diff；
3. **边界模糊**：你写了"要遵守用户指令"，但没写"哪些指令不该遵守"。

我的经验是：边界不是靠措辞"劝"出来的，是靠结构化规则显式定义出来的。

## 做法

SOUL.md 的标准结构，建议四块：

```markdown
---
name: work-agent
version: 1.2.0
load: always
---

# 身份
你是服务于个人开发者的工作流 Agent，不是通用助手。

# 沟通风格
- 回答不超过 5 句话，除非用户要求展开
- 不使用 emoji，不主动寒暄
- 先给结论，再给依据

# 边界（硬性）
- 绝不执行涉及删除、覆盖用户数据的命令，除非用户显式确认
- 绝不安装未经用户审阅的第三方依赖
- 遇到拿不准的请求，用一条 message 说明风险并等待确认

# 优先级
1. 硬性边界 > 用户指令 > 通用模型偏好
2. 当用户指令与边界冲突时，边界优先，并明确告知
```

关键点是**优先级**。模型不是不会读规则，而是规则冲突时它不会自行裁决。你写清楚"边界 > 用户指令 > 模型偏好"，它就有了裁决依据。

加载方式上，我在 OpenClaw 的扩展机制里写了个简单的 loader：会话启动时读取 `SOUL.md`，作为上下文前置注入。改动文件后需要新会话才能生效，这一点要提前知道并留出调试窗口。

## 踩坑点

**坑一：写太长。** 第一版我写了 400 多行，结果模型在长任务里频繁"失忆"。不是没加载，是加载后注意力被稀释。现在控制在 120 行以内，每条规则一行，能用一个动词绝不用两个。

**坑二：只有正向规则。** 只写"应该做什么"，模型对"不该做什么"完全没有概念。必须显式写负面清单：不执行什么、不推断什么、不自动做什么。

**坑三：规则自相矛盾。** 比如既写"保持主动"又写"不要自作主张"。模型会在每次决策时随机二选一，表现出来就是行为漂移。解法是给规则编号并声明优先级，冲突时有明确的胜出者。

**坑四：没有重载机制。** 调试期改完 SOUL.md 发现会话里没生效，以为是 bug，其实是要新会话。建议把版本号写进 frontmatter 并在日志里输出，能省掉大量排查时间。

**坑五：把密钥类信息放进去。** 有人会把 API key 或内网地址写进 SOUL.md，因为"反正是本地文件"。但 Agent 的上下文一旦被导出或上抛给模型服务商，这些就全泄露了。敏感配置一律走环境变量。

## 可复用建议

1. **规则分级用词**："必须/绝不"=硬性规则，"尽量/通常"=软性偏好，这两类词在模型那里的遵守率差异极大；
2. **留一条兜底**：最后一栏写"当所有规则都不适用时，停下来问用户"——这比让模型自由发挥安全得多；
3. **把 SOUL.md 纳入 code review**：改规则本质上是改行为，要像改代码一样评审；
4. **记录行为漂移**：每次会话后简单记录一次"本次有没有违反边界"，每周回看，规则会越改越少而不是越来越多。

## 总结

SOUL.md 不是玄学，它就是一个给 Agent 用的 README——只不过 README 写给人类看，SOUL.md 写给模型看。它解决的是 Agent 的长期一致性问题：人格稳定、边界清晰、行为可预测。写的时候克制一点，把规则当代码维护，比任何提示词技巧都管用。
