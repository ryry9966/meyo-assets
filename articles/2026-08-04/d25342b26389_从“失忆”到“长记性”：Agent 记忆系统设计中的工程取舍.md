### 背景

在 OpenClaw 或各类 Agent 框架的实践中，最常听到的抱怨是：“它又忘了。”不是模型能力不够，而是 Agent 的短期工作上下文和长期用户数据之间，缺少一条稳固的通道。你告诉它“以后汇报用表格”，下一轮它又回到纯文本。这种“失忆”本质不是缺陷，而是系统设计缺了一层。

### 问题：记忆不是聊天记录

很多人把记忆做成“把历史消息全塞进上下文”。这在 token 成本、检索效率、响应质量三个维度上都会迅速劣化。核心难点有三个：

1. **结构缺失**：对话流里混着寒暄、任务指令、临时数字和真实偏好，难以区分“一次性输入”和“长期规则”。
2. **更新困难**：用户说“改成每周五发”，系统若只追加不覆盖，旧的“每周一”依然在上下文里干扰判断。
3. **时机模糊**：什么时候该主动回忆用户偏好？每次调用都做语义搜索？显然开销太大。

### 做法：三层记忆带锁存

我们最终在 OpenClaw 实践里落地了一套三类缓存模型，供你参考：

**第一层：会话短期记忆（Working Memory）**

只保留当前任务相关的状态变量。用结构化的 `task_context` 字段替代原始聊天记录。比如：

```
task_context: {
  report_format: "table",
  send_time: "friday 17:00",
  recipients: ["ops@corp", "lead@corp"]
}
```

每一轮对话结束时更新这个字段，而不是把新消息追加进历史。

**第二层：用户长期偏好（Long-term Preference）**

以 `user_id + preference_key` 作为键，写入键值存储（Redis 或 SQLite 均可）。关键是定义一个“偏好提取器”，它只在用户明确表达倾向时触发写入：

- 出现对比型表达：“用 X 方式，别用 Y”
- 出现频率型表达：“每次都”“以后都”  
- 出现修改型表达：“改成”“调回”

**第三层：压缩归档（Episodic Archive）**

每晚自动跑一次总结任务，把当天的会话记录压缩成“任务摘要 + 关键结论 + 遗留事项”三条核心记忆，写回独立表。原始日志移到冷存储，不参与在线检索。

**记忆带锁存**：所有写入动作都带 `updated_at` 和 `source_session_id`。用户一旦说“不对，改回去”，直接按时间戳回溯覆盖，避免新旧脏数据并存。

### 踩坑点

1. **把记忆做成纯单向写入**。只存不读等于白做；但每个请求都触发语义检索，延迟暴涨。解决：靠“意图路由”把关，只有用户提及“之前、上次、按老规矩”等唤起词时才触发检索。
2. **偏好提取用大模型自由发挥**。模型的输出风格不稳定，今天存 `"时间": "周五"`，明天存 `"time": "Friday"`。必须枚举 schema 并做值归一化，或直接用规则+NER 提取，LLM 只做验证。
3. **忽略陈旧性**。用户的偏好三个月前可能就变了。检索时要带时间衰减权重，或用“最近 N 条明确偏好覆盖旧值”的简单策略，我们实际选了后者，工程上更稳。

### 可复用建议

- **记忆模板先于模型定**。先把用户档案的表结构、枚举值、更新策略定死，再谈模型如何写入。
- **用 MCP server 封装记忆模块**，而不是散落在业务代码里。这样 Agent 更换主模型时，记忆层不受影响。
- **定期手动“对答案”**。每两周跑一次复盘，把模型记住的偏好打印出来和用户确认。真实系统里，自省比优化更重要。

### 总结

Agent 的“记性”不是更多 token 或更大 context window 能解决的，它是一个有边界的系统问题：需要分层、需要锁存、需要过期机制。在 OpenClaw 社区里做记忆能力，最有价值的思路不是做“全知全能”，而是做一个可靠、可回滚、可审计的偏好事实表。先做到不遗忘，再谈理解和主动。
