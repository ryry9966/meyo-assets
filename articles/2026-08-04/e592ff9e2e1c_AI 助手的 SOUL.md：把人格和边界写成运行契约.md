## 背景

当 Agent 从"问答机器人"变成"执行者"——能通过 MCP 调用工具、读写文件、发消息、触发自动化流程时，行为一致性就成了工程问题。OpenClaw 等框架把 SOUL.md 作为 Agent 的"人格+边界"载体。它不是提示词装饰，而是运行时的行为治理层。不写 SOUL.md，Agent 就像一台没有操作系统约束的机器：有算力，没准头。

## 问题

没配 SOUL.md 的 Agent 通常有三个典型症状：

1. **语气漂移**——同一件事，今天解释、明天嘲讽，用户无法建立信任。
2. **决策随机**——遇到冲突场景没有优先级依据，比如"用户让我做的事"和"安全规则"打架时，模型随机选一个。
3. **越界行为**——有工具权限但无行为约束：删文件、群发消息、绕过确认直接执行写操作。

前两个影响体验，第三个是事故。

## 做法

我建议按五段结构写 SOUL.md：

**1. Identity（身份）**：一句话定义 Agent 是谁、服务谁。例如："你是运行在用户个人电脑上的自动化助手，默认本地优先、数据隐私优先。"

**2. Principles（决策原则）**：3-5 条可执行规则。不是"要负责任"，而是"当工具返回不确定结果时，先读回输出再向用户汇报；不编造成功"。

**3. Style（风格）**：限定语气和格式，关键写"反例"："不使用感叹号，不卖萌，不输出 JSON 以外的闲聊内容当结果。"

**4. Boundaries（边界）**：硬性红线，最重要的部分。每条写成"触发条件+动作"：例如"当命令涉及删除目录或批量覆盖时，必须输出受影响文件清单并二次确认"。

**5. Operations（操作规则）**：与 MCP 工具的协同约定。例如"查询类工具出错重试一次即上报，不自动升级为写操作"。

写完做对抗性测试：请朋友扮演恶意用户尝试越权，记录失败模式，迭代修改。

## 踩坑点

- **规则过多反而失效**：SOUL.md 超过 800 行后，模型对靠后规则的遵循率显著下降。核心行为规则放文件头部。
- **自相矛盾**：写了"始终直接回答"又写"不确定时先反问"，模型会随机选一个。要显式声明优先级。
- **把 SOUL.md 当安全机制**：它只是提示层约束。真正的权限控制、沙箱、审批流必须落在 MCP 服务器和系统层面。
- **只写人格不写操作**："你是个谨慎的助手"毫无用处。要写"自动化任务执行到一半遇到非预期输出时，立即暂停并上报"。

## 可复用建议

- 固定五段式模板（Identity/Principles/Style/Boundaries/Operations），头部放 Top 10 硬性规则。
- 纳入 Git 版本管理。Agent 行为异常时，可回查是哪次改动导致。
- 每条边界写成"Given X, do Y"格式，便于做回归测试。
- 对 OpenClaw 用户：SOUL.md 只是入口。MCP 工具描述需同步收敛，移除与任务无关的工具暴露面。

## 总结

SOUL.md 的本质，是人与 Agent 之间的一份运行契约。写它的过程，就是逼自己想清楚：这个 Agent 在什么场景、以什么原则、在什么边界内替我决定和执行。想清楚了，Agent 才谈得上可靠。
