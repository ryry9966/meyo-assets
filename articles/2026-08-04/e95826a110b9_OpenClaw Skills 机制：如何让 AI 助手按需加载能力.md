## 背景：模型再强，也背不动所有招式

Agent 落地中最头疼的问题之一：能力越多，模型越乱。早期我做的 MCP Server 接多了之后，OpenClaw 每次对话都要把所有工具描述塞进上下文——token 费用高，模型还频繁选错工具。工具描述互相干扰，意图识别准确率明显下滑。

后来我花了接近一周时间重构，核心思路只有一句话：**把能力拆成可独立加载的 Skills，让模型根据当前任务动态决定加载什么**。最终效果是工具请求量减少了约 60%，复杂任务的完成率反而提升。

## 问题：为什么技能不能全部常驻？

大模型遵循 "What you see is what you can do"。你把它能看到的东西列得越长，它的注意力越分散：

- 50 个工具描述同时暴露，模型对每一个工具的"信任度"都会降低
- 工具之间的功能边界模糊（比如 `read_file` 和 `read_workspace_file`），模型会随机选择
- 每次请求的 prompt 成本线性增长，高频 Agent 场景下很快烧钱

OpenClaw 的 Skills 机制本质上解决的是"功能显隐"问题：相似功能按域聚合，模型感知到了，才会注入具体实现工具。MCP 解决"怎么连"，Skills 解决"什么时候连"。

## 做法：分层设计 Skills

### 第一层：Skill 本体

每个 Skill 是 OpenClaw 工作区目录下的一个文件夹，包含 `SKILL.md` 作为元信息描述，以及可执行逻辑文件。核心是 `SKILL.md` 里的 `description` 字段——它决定了模型"何时感知到这个 Skill 存在"。

```yaml
---
name: git-integration
description: >
  Git 操作能力。当任务涉及版本管理、提交代码、查看 diff、创建分支、回滚提交、处理 merge conflict 时使用。
---
```

注意 `description` 不是给人看的，是给模型的。必须写清**触发场景**，比如"当用户说 rebase 但实际意图是合并分支时"，也要能覆盖。

### 第二层：按域聚合命名

Skill 命名要按"功能域"划分，才能让模型做粗粒度路由。我当前的分法：

- `git-integration`（代码协作）
- `filesystem-ops`（文件读写、目录监控、快照）
- `issue-tracking`（任务/缺陷系统绑定）
- `container-ops`（Docker/Compose 管理）
- `release-pipeline`（构建、发布、回滚编排）

粒度太细会导致模型加载多个重叠 Skill；粒度太粗又会导致一个 Skill 内部工具箱过于庞杂。

### 第三层：内部工具函数轻量暴露

同一个 Skill 里的工具函数不需要全部暴露。以 `git-integration` 为例，共 9 个内部函数，但依赖模型上下文动态选择的只有 `git_commit_all`、`resolve_conflict`、`list_branches` 三个高频入口。其余操作统一走 `git_command_execute` 这个"万能入口"，由模型写出实际命令。

这样做的原因在于：OpenClaw 每次只注入 Skill 的元信息和三个入口函数签名，而不是九份详细参数说明。

## 踩坑点

### 坑一：描述写得太抽象

最开始我把 `description` 写成"包含 Git 操作相关工具"，模型在需要提交代码时并没有触发加载。排查发现是 description 缺少关键词："提交""push""commit""冲突"都不在描述里。模型没有捷径，唯一判断依据就是这个字段。

**解法：** 把描述当成搜索引擎索引页写，把所有动词、名词、短句变体全塞进去，宁可冗余不可遗漏。

### 坑二：Skill 内部互相引用导致循环加载

模块 A 的代码依赖模块 B，但 A 的 description 也包含了 B 触发的关键词。这会导致一次任务同时拉起两个 Skill，反而是上下文膨胀的源头。

**解法：** 明确规定 Skill 之间的依赖关系必须在 `SKILL.md` 里显式声明 `dependencies` 字段，description 里不出现跨域名词。

### 坑三：不加验证机制就全量切换

我之前直接把一个运行中的 OpenClaw 实例的全部 MCP 工具切换成 Skills，结果 Agent 连续三天行为不稳定。最后定位到是两个 Skill 的触发边界有重叠。这个教训是：新机制先在隔离环境跑，别在生产 Agent 上做一次性大迁移。

## 可复用建议

1. **先写索引，再写实现。** 动手开发 Skill 前，把"模型在什么用户意图下加载它"这件事写清楚。写不清晰，这 Skill 就不该存在。
2. **强制单一入口。** 同域能力提供一个总入口函数，其余函数尽量设为 Skill 私有的子步骤，避免模型在工具间摇摆。这对工具调用准确率提升明显。
3. **监控 Skills 加载热力图。** 跑一周后统计每个 Skill 的加载频率。加载频率小于 1% 的 Skill 要么合并，要么删除。这说明它的触发场景不存在，或者被其他 Skill 覆盖了。
4. **日志里打印 Skill 加载结果。** 在开发阶段，每次加载时输出一行结构化日志，方便确定"模型是否正确识别了技能边界"。
5. **容错优先。** 同一类操作，Skiils 机制应该允许模型"找不到对应能力时直接退出识别"，而不是强行返回一个相关但不正确的 Skill，这一点我们在实现里通过 confidence 阈值完成了。

## 总结

OpenClaw Skills 机制的核心价值是，把"决策哪些能力可用"这一逻辑从开发期转移到了推理期。它和 MCP 的区别不在传输层，而是**认知层**。MCP 定义了工具如何被调用，Skills 定义了工具何时出现在模型的视野里。

如果你还在把一个巨大的 prompt 或者几十个 MCP 工具一股脑塞给 Agent，可以试试这个思路：拆业务域、写描述、做监控、收敛边界。输出会肉眼可见地稳定。
