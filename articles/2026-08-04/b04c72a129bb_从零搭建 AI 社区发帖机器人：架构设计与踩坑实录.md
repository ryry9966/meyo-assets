# 背景

社区运营中，内容发布是高频且重复的工作。手动复制摘要、排版、定时上传，既慢又容易出错。尤其是当你有多个社区需要维护时，一个能自动生成内容并完成发布的 Agent 可以显著降低人力成本。

这篇文章记录了我用 OpenClaw + Agent + 插件体系搭建发帖机器人的完整过程，重点讲架构设计和实际踩过的坑，不做原理性说教。希望给正在做类似自动化实践的朋友一些参考。

# 问题

目标很明确：让 Agent 自动完成“内容生成 → 发布到社区”。但具体拆分后，问题并不简单：

1.  **内容生成与发布耦合**：如果 Agent 直接生成 HTML 然后 post 出去，一旦生成格式不稳定，发布内容就会排版混乱。
2.  **重复发布风险**：网络超时导致重试，重试时如果不做幂等处理，同一个帖子可能被发三遍。
3.  **登录态裂化**：社区接口的鉴权方式杂，Cookie 过期或 Token 失效会导致发布失败甚至账号异常。
4.  **附件处理**：图片、文件上传往往需要单独接口，而 Agent 默认只处理文本，这会导致图文帖发布失败。

# 做法/步骤

架构上遵循一个原则：**Agent 只做决策，不碰执行细节**。发帖动作交给专用插件（Plugin），内容缓存用本地队列（Queue），并塞入幂等去重逻辑。

**Step 1：抽象发布器接口**

定义统一的发布接口（PublishPost(title, content, tags, attachments)），不同社区实现各自的 adapter。Agent 不需要关心目标平台是 Discuz、NodeBB 还是自研 API，内部只需要维护一个目标平台枚举值。

**Step 2：内容生产与审核分离**

Agent 负责撰写内容，输出结构化 Markdown 文本，不经渲染。插件侧维护一个简单的格式检查器，校验标题长度、正文非空、标签数量等，不合格则回退给 Agent 重写。审核后再做渲染。

**Step 3：幂等层**

架构核心是 `content_hash`。Agent 生成内容后，在发布前对该内容取 SHA-256。每次发布尝试都带着这个 hash 去插件内查重。如果重试前已经成功发布，直接返回既有 post URL，不做二次发包操作。

**Step 4：队列与重试**

每次发布请求先进本地队列，然后由独立的 Worker 线程处理。失败时使用指数退避（1min → 5min → 30min），超过三次则写入 error.log 并不再自动重试，防止把服务商的风控系统打爆。

# 踩坑点

最典型的坑有三个：

1.  **Cookie 过期引起的串号**：我最初把登录凭据硬编码在配置中，Cookie 失效后插件不会报错，只是用未登录状态发帖，结果被系统当成另一个匿名用户处理。后来通过每次发布前做一次轻量的鉴权探活（比如请求 /user/profile 接口），返回 302 就唤醒 Agent 重新登录取 Cookie，问题才解决。

2.  **重试导致的重复帖**：这个用 Step 3 的幂等层修正了。但注意 hash 要去掉动态字段（如 createdAt），否则二次生成的内容 hash 不同，幂等失效。

3.  **LLM 直接生成 DOM 标签引发的样式问题**：一开始让 GPT 输出 HTML，结果经常漏掉闭合标签、属性名大小写错乱，导致站内渲染错位。改成生成纯 Markdown + 插件内部用统一模板渲染后，样式稳定性明显提升。

# 可复用建议

-  **所有接口调用都加幂等键**：不要觉得多此一举，网络异常远比想象中频繁。
-  **登录态独立于业务逻辑**：做成中间件/插件，在发布前统一处理鉴权刷新。
-  **内容生成与格式渲染解耦**：Agent 只输出结构化内容，HTML 渲染交给插件侧统一模板，避免返回内容“花式创新”。
-  **做好日志审计**：记录每一次发布的请求头、返回体、耗时和 hash，排障效率提高一个量级。
-  **先跑通一个最小闭环**：用最简单的一个社区先跑通全链路，再扩展适配器，不要一开始就追求多平台。

# 总结

整体来看，AI 发帖机器人的技术门槛不在“调用大模型生成文案”，而在工程化兜底：幂等、鉴权、格式稳定和日志可观测。把 Agent 和具体操作解耦，并构建轻量级的发布中间层，才能让它在真实社区环境中稳定运行而不添乱。
