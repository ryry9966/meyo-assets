## 背景：每个人都想要 6 点的邮件，但 Agent 在等你说「早上好」

如果你的 Agent 使用频率足够高，大概率会碰到一个尴尬场景：你坐下来打开电脑，它先弹出一条「早上好，今天有什么可以帮你？」——**它比你女朋友更早，但也比你想象中的智能助理更晚。**

传统 Agent 架构（包括 OpenClaw 的常规用法）是典型的 Pull 模式——User turn → model inference → tool call → response。这套循环稳定、可控、易于构建，但天花板也很明显：你永远在指挥，它永远在等待。

而「Proactive 能力」之所以被频繁谈起，核心原因是：**当 Agent 从工具变成伙伴，主动输出是分水岭。** 但脱离工程实现来谈 proactive，最终只会变成「早报推送机器人」——每天定点告诉你温度 26°C，和智能没有半毛钱关系。

## 问题：为什么主动那么难？

一句话总结，难在三个地方：

1. **触发时机不确定**——你不知道用户什么时候需要你，只能靠猜测。
2. **上下文稀疏**——被动模式下上下文自带（用户发消息），主动模式下你需要自己去收集。
3. **误判代价高**——错误打扰比不打扰更招人烦。

所以，真正值得写的不是「做个定时任务」。

## 做法：在 OpenClaw 里搭一套可控的 Proactive 管道

下面这套方案不依赖任何独有 API，用 OpenClaw 已有的事件钩子、MCP 工具外加一层简单的调度逻辑就能落地。

### 第一步：定义触发源（Triggers）

我把主动场景分成三类，对应不同实现方式：

| 类型 | 典型场景 | 触发方式 |
|------|---------|---------|
| 时间型 | 每日早晨的工作摘要 | Cron / Ticker 事件 |
| 状态型 | 下载任务完成 / MCP 工具返回异常 | 工具调用后置钩子（Post-Hook） |
| 规则型 | 特定关键词出现（如「赶不上了」） | 监听聊天上下文的关键词匹配器 |

OpenClaw 里最省事的是在 Agent 配置中加入 Cron 插件，再配合 MCP 的 Resource 订阅来感知工具状态。关键不是触发方式多高级，而是把触发的表达从「几点了」升级为「发生了什么」和「接下来是什么」。

### 第二步：组装 Proactive Context（核心）

触发之后，不要让模型直接写「早安类」内容。先做一件事：**拉取上下文包。**

我建议预设一个 `context_builder` MCP Tool，内部通过几个已有工具组合实现：

```text
get_user_context()    → 今日日历前五条、最近 3 条对话摘要
get_reminders()       → 未过期提醒
get_system_status()   → 待处理任务 / 网络 / 队列状态
```

然后组装为一段结构化片段，交给 LLM 生成主动输出。这样做有三重好处：输出内容不是凭空捏造，模型有足够信息做判断，错误率显著降低。

### 第三步：加入去重与优先级

Proactive 输出最怕三连：重复、堆砌、互相冲突。最简单的方案是引入一层轻量 **dedup 缓存**（Redis 或内存 Map 均可），Key 为 `(触发源 + 日期 + 主题)`，30 分钟内相同主题不在重发。

优先级上建议硬编码：状态型（任务完成/异常） > 时间型（晨会前 10 分钟） > 规则型（关键词）。让 AGENT 自己判断优先级属于过度设计。

### 第四步：留一个「自问按钮」

即使做了再好的上下文收集，也会有信息不足的时候。所以我在 Agent 配置里加了一个 `self-ask` 模式：当 LLM 判断当前信息不足且触发场景重要时，先调用 `send_followup_question()` 问一句简短确认，再执行。注意，这只保留在低误判代价场景；高代价场景（如自动发邮件）永远保持纯被动。

## 踩坑点

- **「被忽略的早安」场景**：刚开始做主动推送时，我设了早 9 点推送，结果 80% 内容用户没看。直到把推送时间改为会议前 10 分钟且只推送与下一场会议强相关的内容，打开率才够看。**主动不是频率，是相关性。**
- **上下文组装出的幻觉**：LLM 在信息不全时倾向于「自由发挥」。比如没拉到 TASK 状态就编一个「顺利完成」——一定要在 prompt 里写死一句「没有获取到的情况不要猜测」。
- **对 Tools 的依赖**：Context builder 依赖 MCP 工具，如果 MCP 服务偶发超时，整条链路会阻塞。建议为 context_builder 单独设置 5 秒超时，超时降级为「无上下文直接触发默认输出」。
- **关闭按钮的虚伪性**：很多 Agent 设置「is_proactive_active: false」就完事了，但用户真正想关的是「特定类型」而非全部。建议提供分通道关闭粒度，否则容易因一次误打扰被全盘禁用。

## 可复用建议

1. **渐进式放权**：先从只读场景开始（摘要、提醒），稳定运行两周后再开放写操作（自动状态更新）。
2. **日志记录一切**：每次 proactive 输出都留痕（触发源、上下文摘要、LLM 输出、用户反应），用真实行为数据来迭代触发规则。
3. **人不是开关，是裁判**：用户不想要的是被动接受，给一个快捷「忽略/调整」操作入口，比永远精准预测更容易得到宽容。
4. **模块解耦**：Trigger、Context Builder、Policy、Executor 分开独立的插件或 MCP 服务，避免 Agent 升级时互相牵连。

## 总结

Proactive 能力不是「把定时推送接到 LLM」就算完成，它本质上是**在正确的时间，用充分的上下文，做一个高相关性的低风险决策**。从 Trigger 到 Context 到 Policy 再到 Executor，每一层都在损耗主动性，也在过滤误判。真正合格的判断标准是：**用户不觉得被打扰，也不觉得它消失了。**

工程上没有银弹，但把控制权分层交给用户和代码，比让 LLM 自由发挥要可靠得多。
