### 背景

OpenClaw 等 Agent 工具让"AI 生成内容 → 存储 → 发布"的链路变得极顺滑。输出几乎是清一色的 Markdown——这格式看似通用，实则每个平台（微信公众号、Notion、知乎、Obsidian、语雀）的解析规则和扩展语法都不尽相同。结果是：对话里的 Markdown 完美，发布后碎一地。本文记录一条面向多平台发布场景的 Markdown 管线设计，重点在格式适配，不谈语义优化。

### 问题

AI 训练语料里占比最高的 Markdown 风格是 GitHub Flavored Markdown（GFM），但 GFM 的若干特性在多数内容平台不可用：表格在微信公众号原生不支持；`[#anchor]` 锚点链接在知乎和微信端会失效；`<br>`、`<center>` 这类宽限 HTML 标签在多数平台会被过滤；GFM 的删除线、任务列表在 Notion 里有自己的映射，粘贴过去要么失效要么变成块对象，后期整理成本极高。

如果让不同平台各写一套 Prompt 约束，上下文会严重膨胀，且维护成本随平台数量线性上涨。最终方案不是让 AI 感知平台，而是在发布前置阶段做分级适配。

### 做法

管线分三层，从生成到发布：

**第一层：源头规范化（生成阶段）**

在 Agent 的指令模板中固定一套"最低通用 Markdown 子集"：

- 标题仅使用 ATX 风格（`#`），不用 Setext（`===`）和 closed ATX（`# 标题 #`）
- 禁用内联 HTML（含 `<br>` 换行，一律用两个空格结尾或空行实现软换行）
- 链接和图片必须使用标准行内格式 `[text](url)`，禁止引用式链接 `[text][ref]`
- 表格只允许简单表头+分隔行，不启用 GFM 的列对齐（`:---`）
- 高亮使用**加粗**代替 `==高亮==`（后者仅 Obsidian/Notion 支持）

这条约束放在系统提示里，不针对具体平台。

**第二层：发布前静态转换（适配阶段）**

写一个小的 Node 脚本（或 Python 脚本），在 git commit 前由 pre-commit hook 触发，做以下几件机械转换：

- 将 `^[脚注]` 转为文末参考列表（对不支持脚注的平台直接透传其 Markdown 源码）
- 将本地图床的相对路径替换为 CDN 绝对地址，并生成与各平台尺寸要求匹配的变体
- 对标题增加自定义 ID（如 `## 核心概念 {#core-concept}`），自动清除后作为纯文本
- 如果检测到推送目标为微信公众号（通过目录约定），将内嵌表格的说明文字抽离为 HTML 注释，避免"表格源代码直接透出"的丑态

**第三层：发布兜底**

不追求一条命令发布全网。脚本只负责输出"平台相性报告"——列出该平台不支持的语法片段、建议手动检查项（如图片 alt 文本空置），再由人工确认或 API 发布。流程保持半自动，预留人工介入空间。

### 踩坑点

几个实践中的细节问题：

**中文标点冲突。** `#` 标题后跟中文内容没有问题，但若中文行内含半角括号 `(...)`，部分平台（知乎）会将其识别为 wikilink 语法从而误解析。建议在规范化阶段对全文执行半角→全角括号的转换（仅限中文上下文中）。

**代码块的"语言标注"陷阱。** AI 经常输出 ` ```python ` 这种带语法高亮的代码块。Notion 粘贴时有时会丢失语言标注变成纯代码块，这不是脚本问题，是剪贴板内容类型的问题。方案是不在源头禁止语言标注，而是发布后不依赖高亮效果，保持代码内容本身的完整性。

**图片路径的 `%20` 转义。** 本地文件名带空格时，标准 Markdown 要求 URL 编码，但 Obsidian 粘贴时总是保留字面空格。如果管线里没做 URL encode，发布后图片必裂。这个坑最隐蔽，因为源文件里看着正常。

**AI 幻觉出的"伪通用语法"。** 比如 `[:emoji:]`、`{.class}` 这类 Pandoc 扩展语法，AI 会基于训练数据脑补出来。本地渲染没问题，发布到其他平台直接暴露文本。建议在适配脚本里用正则加一道"陌生语法告警"：凡是 `{.` 或 `[:` 开头的 token 一律列入报告。

### 可复用建议

1. **不要试图做一个万能转换器。** 各平台差异不可消除，目标是让 AI 输出在"适配前"已经是干净的通用 Markdown，而不是针对某平台做特化。
2. **把各平台的语法差异写成测试用例（fixtures），而不是文档。** 比读文档管用，直接在脚本里跑断言比对输出结构。
3. **控制在"发布前"转换，而不是"生成时"改写。** 生成时约束平台细节会让 AI 上下文浪费在格式上，且生成的文本审美会向"安全"倾斜，牺牲表达力。
4. **交付物是"报告 + 半自动"，不是全自动。** 一个只在错误时输出的 CLI 值得维护；一个整天静默越权的机器人程序不适合自己团队用。
5. **沉淀一张"适配矩阵"表格**：语法特性 × 平台支持程度，放在仓库 README 里，作为后续增补新平台时的检查清单。

### 总结

Markdown 不是终点，它只是最接近"结构化纯文本"的交界地带。要让 AI 生成的内容在多平台稳定落地，管线设计的核心不是"翻译"，而是"约束源头 + 机械转换 + 人工兜底"三层配合。克制地使用技术手段，保留人工确认的余地，这比构建一个庞大但脆弱的自动化发布系统更可维护、更可排查。
