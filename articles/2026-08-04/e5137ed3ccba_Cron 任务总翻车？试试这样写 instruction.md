## 背景

把 Agent 挂到 Cron 上，是很多 OpenClaw 用户「从玩具到工具」的第一步：每天定时抓取信息、生成周报、巡检服务状态。但跑上一周你就会发现——**对话里好用的 Prompt，放到 Cron 里完全不是一回事**。

对话模式有你来我往，错了可以立刻纠正；Cron 任务则是「发射后不管」。Agent 在无人值守时遇到歧义，往往会自作主张或干脆罢工。这不是模型不行，而是我们给的 instruction 没有为「无人值守」这个场景设计。

## 问题

给 Cron 任务写 instruction，最常见的三类问题：

**缺执行上下文。**「抓一下 Hacker News 的热门帖子」——哪个时间段的？抓多少条？按什么排序？输出成什么格式？Agent 每一步都在猜。

**语义含糊。**「整理成简洁的报告」——什么叫简洁？300 字还是 3 句话？是否包含原始链接？要不要结论先行？你说不清楚，Agent 就发挥不稳定，今天是列表，明天是段落。

**没有终止条件。** 指令只说做什么，不说做到什么程度算完。Agent 可能陷入循环、无限深挖某个细节，或者在异常输入上反复重试直到超时。

## 做法

Cron 任务的 instruction 不是写「提示词」，是写**操作规范**。下面给出一个经过验证的结构模板：

```
任务声明：一句话说明这个任务是什么、为谁做。
执行步骤：编号排列的具体操作序列，每步只做一件事。
终止条件：明确什么情况下结束任务、什么是可接受的产出。
输出格式：规定标题、段落、列表的样式，给定量级要求。
异常处理：数据源不可用、内容为空、解析失败时怎么办。
```

以「每日 AI 资讯摘要」为例：

```
任务：生成一份今日 AI 领域的资讯摘要，面向技术管理者。

步骤：
1. 依次抓取以下 4 个来源：Hacker News（AI 板块）、ArXiv（cs.AI 分类）、Product Hunt（AI 分类）、36Kr（AI 标签）。
2. 对每个来源，筛选出 24 小时内发布、且与 AI 直接相关的内容。排除纯产品推广文。
3. 将筛选后的内容按主题聚类，选取最核心的 5-8 条，写入正文。
4. 检查正文中是否存在来源名称和日期，补充缺失信息。

终止条件：正文包含 5-8 条资讯，全部带来源链接和发布日期，即可结束。

输出格式：使用 Markdown。标题为「AI 资讯日报 YYYY-MM-DD」。每条资讯
格式为「一句话概括 + 为什么值得关注（一两句）+ 原文链接」。总字数不超过 800 字。

异常处理：若某个来源无法访问，跳过该来源，在文末注明。若全部来源
均不可用，只输出「今日暂无数据」并结束，不要尝试编造内容。
```

注意步骤 4：它是内置的自检环节。Cron 任务的产出没人校对，**必须让 Agent 在任务结束时做一次自查**。

如果你要写的是「持续观察型」任务，比如每隔 1 小时检查一次某个页面是否更新，模板需要调整：核心不是「怎么抓」，而是「什么变化值得触发后续动作」。这时要给出判断基准——「和上次抓取的结果对比，出现新条目且满足 XX 条件时，才算『有更新』」——否则 Agent 每次都会觉得「有变化」，你的通知会被刷屏。

## 踩坑点

- **指令里写「尽可能」「详细一点」这类程度副词。** Agent 对程度的理解每次都可能不同，请给出可量化的标准：条数、字数、时间范围。
- **时间上下文缺失。** 只说「今天」不够，Agent 的系统时间有时区问题。明确写「以 UTC+8 的当前日期为准」，或直接在指令里给出具体日期。
- **没有自检逻辑。** 步骤里加一步「检查输出是否包含 X、Y、Z 要素」，能显著减少缺胳膊少腿的产出。
- **把 conversation history 当记忆用。** Cron 每次触发大多是干净上下文，Agent 不会记得上次干了什么。需要跨次状态，请写入文件或走 MCP 工具持久化。

## 可复用建议

再精简一下，用三个问题自检你的 instruction：

1. **如果我今天离职了，新人能照着这份指令把活干完吗？** 如果不能，说明上下文还不够完整。
2. **这项工作有没有明确的「完成」标准？** 没有终止条件的任务，自动跑起来就是个无底洞。
3. **出错了会怎样？** 无人值守场景下，预设好失败路径，也好过让 Agent 自由发挥。

给社区的两个具体建议：

- 在 Cron 任务第一次上线前，先用对话模式把 instruction 完整跑 2-3 遍，观察 Agent 在哪个环节容易歪。把修正后的结果反哺回指令文本。
- 在指令中加入一行「本次执行时间: {{datetime}}」，让 Agent 明确知道自己在什么时间点运行，避免时间错位（实际跑下来，这个字段很管用）。

## 总结

Cron 任务的 instruction，本质上是**把「期望的反复执行」固化成「确定的操作规范」**。它不是在教模型聊天，而是在教模型按流程办事。写的时候时刻提醒自己：这个指令没有第二次解释的机会。做到这一点，你的自动化任务跑一个月不翻车，不是问题。
