## 背景

在 OpenClaw 这类 agent 框架里，heartbeat（心跳）通常指两件事：一是 agent 会话进程持续监听外部指令的存活信号；二是 agent 对外部系统状态的周期性感知。社区里不少自动化实践（定时任务、MCP 工具轮询、外部 webhook 接入）都会在某个环节卡在同一个问题上：**怎么让 agent「知道该干活了」**。

用轮询实现简单直接，用推送则能显著降低延迟，但各自都有隐藏的成本。这篇文章基于我在多个插件和自动化任务中的实测，梳理一下两者的取舍和可落地的做法。

## 问题

先定义清楚。把 heartbeat 视为「 agent 的状态感知通道 」，它有两种典型实现：

- **轮询（Polling）**：agent 按固定间隔主动询问「有活干吗」。典型实现是 `while True: sleep(interval); check_something()`。
- **推送（Pushing）**：外部事件发生时主动通知 agent。典型实现是 webhook 端点、消息队列订阅，或者监听某个 channel。

两者不是简单的「更好」或「更差」的关系。选择取决于三件事：**时间敏感度、运行成本、系统复杂度**。

## 取舍与做法

### 场景 1：低频任务 → 轮询

如果任务是分钟级或小时级的（比如每小时检查一次某个 API 的速率限制、每天抓一次 RSS），直接轮询即可。实现成本最低，出问题也好排查。

设置间隔时留意一个**反直觉的坑**：`interval` 只是「两次检查之间停留的时间」，如果你的检查本身耗时不稳定（比如调用了外部 MCP 工具，响应时长波动大），实际频率会漂移。正确做法是采用固定节奏：

```python
import time

def heartbeat_loop(interval=60):
    next_tick = time.time()
    while True:
        check_once()          # 每次执行的独立任务
        next_tick += interval # 按绝对时间推进，避免漂移
        time.sleep(max(0, next_tick - time.time()))
```

### 场景 2：事件驱动任务 → 推送

如果任务是秒级响应（比如聊天插件收到消息后立即唤起 agent、外部系统变更触发工作流），推送是唯一合理的方案。在 OpenClaw 里，最轻量的做法是暴露一个本地 HTTP 端点：

```python
from flask import Flask, request
app = Flask(__name__)

@app.post("/hook/agent/run")
def trigger_agent():
    payload = request.get_json()
    # 校验签名，然后异步唤起 agent 任务
    enqueue_agent_task(payload)
    return {"status": "ok"}, 202  # 快速返回 ack
```

推送的核心原则是**「接收即确认」**：webhook 收到事件后只入队并立刻返回 202，不要让事件源等待你的 agent 跑完。否则事件源超时会重发，造成事件风暴。

### 关键取舍：推送 ≠ 低延迟，轮询 ≠ 高延迟

一个常见误解是「用了推送延迟就低」。在单机、单进程的 agent 场景里，如果任务队列积压，推送和轮询的**实际任务开始时间**可能几乎一样。推送的优势不是降低任务执行延迟，而是**消除空转成本**——没有事件时 agent 不耗资源。选型时可以按这个标准来判断：如果任务本身耗时 > 5 秒，推送的延迟优势可以忽略，轮询更省事。

## 踩坑点

1. **轮询的「空响应」不一定是坏事**。我在一个自动化任务里发现，某些外部 API 对频繁的空轮询做了限流，导致后续真实请求被 429。解法不是加长间隔，而是给循环里面加「指数退避」：连续 N 次空响应后半休眠。
2. **推送端点必须是幂等的**。agent 任务执行失败后通常会重试，如果目标操作不支持天然幂等（比如「发送一条消息」），要在入队时做去重。建议生成事件 ID，记录已处理过的 ID，重复事件直接 ack 丢弃。
3. **不要用数据库轮询模拟推送**。如果数据源是数据库，有人会用「每 1 秒 SELECT 新记录」来实现类推送。这在单节点可以跑，但一旦 agent 多实例部署，多个实例会同时 SELECT 到同一批记录，导致重复消费。除非加 `SELECT ... FOR UPDATE SKIP LOCKED`，否则别这么干。
4. **webhook 的认证不能省略**。家里/办公网暴露的端点，默认被扫描器盯上是常态。哪怕只监听 127.0.0.1，也建议头部校验一个静态 token，成本忽略不计。

## 可复用建议

把决策写成一个简单的选择标准：

- 任务频率 ≥ 1 次/分，且事件来源可控 → **轮询**。用固定节奏循环，加空转退避。
- 任务频率 < 1 次/分，或事件来源外部不可控 → **推送**。用 webhook 入队，快速 ack，入口做幂等。
- 任务频率不固定但可预测波动（如工作时段密集、夜间空闲）→ **自适应轮询**：检测到空转时逐步拉长间隔，检测到事件时立即触发并缩短间隔。这个模式在 OpenClaw 插件里非常实用，可以先把基础版实现再调参数。

另外，如果未来计划把 agent 水平扩展成多实例，**一开始就选推送**。轮询在单实例比较简单，但多实例下会放大重复处理的问题；推送的消费端天然支持多实例竞争消费（只要队列是共享的）。

## 总结

Heartbeat 设计的本质是**响应性 vs 复杂度的交易**。对 OpenClaw 社区的大多数插件和自动化脚本来说，轮询是默认选择——它简单、可观测、好调试。推送是加速法宝，但要付出一套额外的基础设施成本（HTTP 端点、入队机制、认证）。

我的建议是：先按轮询跑通逻辑，再根据实测延迟和资源占用决定要不要切推送。判断标准很简单——如果轮询的间隔缩到 5 秒以内才满足需求，就该认真考虑推送了；否则，保持简单。
