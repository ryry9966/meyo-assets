## 背景

在 OpenClaw 上跑 Agent 跑久了，你会发现真正让你加班的不是 prompt 写得不好，而是外部 API 不稳定。天气查询、航班接口、LLM 供应商、MCP 工具——任何一环抽风，整个工作流就断了。最常见的现象是：Agent 调完工具，憋了半天，吐出"抱歉，我暂时无法完成您的请求"——没有原因，没有恢复，没有退路。这周我们把 Agent 的失败路径整体重做了一遍，这里记录下思路和踩过的坑。

## 问题本质

Agent 框架天然是"成功导向"的：编排层把工具结果塞给模型，模型基于结果决定下一步。当外部 API 返回 500 或超时，这个错误只是作为一段文本进了上下文，模型只能猜。更要命的是，框架很少区分"临时故障"和"永久失败"——于是 Agent 要么傻乎乎重试，要么编造一个看似合理的失败原因。

## 做法

**1. 错误分类。** 把所有外部 API 错误归为四类：网络超时、4xx（参数/鉴权）、5xx（服务端）和 429（限流）。只有 5xx 和超时值得重试，4xx 重试一万次也是白搭。

**2. 指数退避重试。** 按 1s/2s/4s/8s 递增，最多 4 次，加随机 jitter 防止雪崩。注意：非幂等操作（支付、下单）绝不能盲目重试，必须先确认上一次请求到底成没成功。

**3. 熔断器。** 某个供应商 API 连续失败率超过阈值就熔断，直接走降级路径，不再发请求；冷却期后进入半开状态，放少量流量探测恢复。这比单纯重试有效得多。

**4. 降级设计。** 能接受降级的场景就降级：天气用上次成功拉取的缓存并标注时间戳；航班查询从数据源 A 切到 B；LLM 调用在网关层面做供应商切换。

**5. 上下文恢复。** API 恢复后，不要假设之前的本地操作和远端已经同步。在 OpenClaw 工作流里安排一次"状态同步"工具调用，重新拉取关键资源，再继续后面的步骤。

## 踩坑点

- **重试了不该重试的请求。** 订单接口重试导致重复扣费/重复入库。必须先去查状态，而不是看有没有拿到响应。
- **静默降级比大声失败更危险。** Agent 吞掉异常后回复"一切正常"，比直接告诉用户"暂时不可用"后果严重得多。要给模型结构化的错误类型，让它能如实说明。
- **缓存兜底没带时间戳。** API 挂了两个小时，缓存还在返回两个小时前的旧数据，业务方以为是实时的。降级缓存必须携带时间和有效期。
- **同步/异步混用导致状态分叉。** 外部 API 失败时本地工作流依然跑完，后续对账非常痛苦。

## 可复用建议

- 在工具返回值里标准化错误字段：`success / transient_error / permanent_error / circuit_open`，别让模型从文本里猜。
- 封装统一的 API 适配层，内部处理重试、熔断和结构化报错，所有工具共用。
- 设定降级策略：报表、通知类容忍降级；资金、状态变更类必须大声失败。
- 故障恢复后，让 Agent 主动汇报受影响的步骤，而不是默默继续。

## 总结

外部 API 挂掉不是"会不会"的问题，而是"什么时候"。Agent 的设计目标不是永不失败，而是失败时可观测、可降级、可恢复。少一点幻想，多一点检查。
