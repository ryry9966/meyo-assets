## 背景

团队里每天写日报是个固定动作，但大多数人不是不想写，是懒得从聊天记录、Git commit、监控平台、工单系统里翻找“今天到底干了什么”。结果就是日报变成流水账，或者干脆复制昨天的内容改个日期。

后来发现，其实日报所需的信息大部分已经存在于系统中：代码仓库的提交记录、任务看板的状态变更、日志平台的关键告警、IM 群里的讨论片段。缺的只是一个把散落信息“捞起来、过滤、组织成文”的过程。

这篇文章分享一个我自己在用的日报生成流水线，基于 OpenClaw 的 Agent + 外部脚本实现，逻辑简单，胜在稳定。我尽量不堆术语，把每一步的取舍和踩过的坑写清楚。

## 问题定义

先明确要解决什么问题。日报生成不是“用 AI 写一篇作文”，而是完成四件事：

1. **采集**：从多个数据源收集当天的原始动作记录。
2. **过滤**：去掉噪音，比如依赖包升级、格式化提交、无效告警。
3. **结构化**：按项目/任务归类，标注类型（开发、排查、会议、文档）。
4. **成文**：生成适合直接粘贴到飞书/钉钉/邮件里的纯文本或 Markdown 日报。

## 做法与步骤

### 第一步：设计原始日志模型

先别急着写代码。我建议先定义一份统一的“当日活动”JSON 结构，所有数据源都转换为这个格式再进入后续处理：

```json
{
  "time": "2025-06-11 10:23",
  "source": "gitlab",
  "project": "gateway",
  "type": "code",
  "summary": "修复连接池泄漏问题",
  "detail": "fix: resolve connection pool leak in http client"
}
```

有了这个统一结构，后面所有处理环节（过滤、聚合、摘要）都不需要关心数据来自哪里。

### 第二步：采集——用脚本代替 Agent

这里是我的核心建议：**Agent 只做编排，不要让它去“记住”怎么连各平台的 API**。我在 OpenClaw 里注册了三个普通 Python 脚本作为工具：

- `collect_git_activity.py`：拉取当天 GitLab/GitHub 提交，筛选当前用户，提取 commit message。
- `collect_tasks.py`：读取飞书/禅道任务状态变化，包括完成、进度更新。
- `collect_alerts.py`：从夜莺/Prometheus 拉取当天告警，去掉 recovery 消息。

用脚本的好处是：出错时可单独调试、重跑，不占用 Agent 的上下文窗口。

### 第三步：过滤与聚合

这一步在脚本里做，不用 LLM。规则很简单：

- 去掉以 `chore(deps)`、`docs:`、`Merge branch` 开头的提交。
- 告警只保留 severity >= warning 的条目。
- 同一项目 10 分钟内的多条操作合并为一条。

过滤规则写成 YAML 配置，方便按团队习惯调整。

### 第四步：生成摘要——这里才用 LLM

将过滤后的数据组装成如下提示词，调用 OpenClaw 内置的 LLM 工具生成日报：

```
你是后端组的工程师。根据以下当日活动记录，生成一段 100 字以内的日报。
要求：按项目分组，突出结果而非过程，语气客观，不要使用“赋能”、“抓手”等词汇。

记录：
{"project":"gateway","events":[...]}
{"project":"report-service","events":[...]}
```

这里有个关键设计：**LLM 只做最后一步——把结构化数据变成口语化总结**。不要让 LLM 面对原始 commit message 列表，否则它大概率会编造细节。

### 第五步：输出与投递

生成结果写到 `daily-report-2025-06-11.md`，同时通过飞书 webhook 推送到“团队日报”群。最后在 OpenClaw 里留一个人工确认步骤——Agent 先发预览再发送，避免“直接自动发错上下文”的尴尬。

## 踩坑点

这条流水线改了三版才稳定，说一下最典型的几个坑。

**坑一：时区和“当天”边界**
一开始直接按 `date +%Y-%m-%d` 过滤，结果凌晨 0 点跑任务时漏掉了昨天 23:50 的提交。后来统一用 `TZ=Asia/Shanghai` 指定时区，且过滤范围为 `[当天 00:00, 次日 00:00)`，不再用“近 24 小时”。

**坑二：commit message 质量太差**
很多团队提交信息写的是 `fix bug`、`update`、`wip`。这种信息直接喂给 LLM 只会得到废话。解决办法是：从 commit 里提取**关联的任务 ID**（比如 `#1234`），再去任务系统里拿任务标题作为 summary 兜底。实测效果提升明显。

**坑三：LLM 输出不稳定**
同一份输入，有时候生成 50 字的日报，有时候生成 200 字。约束方式不是靠提示词“要简短”，而是在代码里做后处理：如果超过 150 字，按句号截断到第一条完整句为止；如果少于 30 字，重新用更详细的提示词生成一次。

**坑四：不要把 API 调用做成同步阻塞**
我最初把所有采集脚本串行执行，碰到某个源超时（比如 GitLab 5 秒无响应），整个流程卡死。后来全部改为并行执行 + 超时兜底：单个源失败时，在日报里标记“该数据源采集失败”，而不是中断全流程。

## 可复用建议

如果你也想搭类似的东西，我提这几条建议：

1. **数据源抽象成 JSON 先行**。不要一开始就想做一个“完美的 Agent 自动化”，先看看能不能在终端手动跑通一条 `collect -> format -> output` 的管道，再加 Agent。
2. **日报生成是典型的“脚本为主，Agent 为辅”场景**。Agent 的价值是编排和异常处理，不是替代脚本。
3. **保留中间产物**。每天生成的 `daily-report-*.md` 保留 30 天，方便追溯“为什么那天日报说在做 A，但代码提交只有 B”。
4. **为失败设计**。团队成员的 Git 用户名和 IM 昵称不一致、分支名带前缀、任务系统状态值是中文——这类脏数据一定会出现。提前写一个 `normalize.py` 集中处理。
5. **不要追求全自动**。加一个人工确认步骤，比“Agent 全自动发送然后翻车”体验好得多。

## 总结

自动化日报并不需要多复杂的架构。无非是：**统一格式 -> 脚本采集 -> 规则过滤 -> LLM 成文 -> 人工确认**。整个流水线用 OpenClaw 一个 Agent 外壳加几个 Python 文件就能落地。

真正的收益不在“省了写日报的 5 分钟”，而在于它倒逼团队规范了 commit message 和任务关联——这些才是日报之外的长期价值。

如果读完觉得有参考价值，可以先把第一步的 JSON 结构定义好，跑通一个数据源再说。自动化这件事，从最小闭环开始最不容易烂尾。
