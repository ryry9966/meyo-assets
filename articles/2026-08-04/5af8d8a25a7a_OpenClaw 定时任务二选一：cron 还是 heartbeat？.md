## 先说背景

OpenClaw 里做自动化，定时任务是绕不开的一环。很多人第一反应是 cron——设个时间点或间隔，到点触发一次。但实际用一段时间后会发现另一个机制：heartbeat。它也在定时跑，行为却完全不同。选错了，轻则空转烧 token，重则该干活的时候没干活。

## 两种机制的本质差异

**cron 是"到点执行"**。配置里写死触发时刻或周期，比如每天 09:00，或每 5 分钟一次。它不关心当前状态，时间到了就触发。确定性很强，适合"不管怎样都得跑"的任务：日报生成、数据归档、定时通知。

**heartbeat 是"周期性醒来检查"**。循环逻辑是：醒来 → 评估当前状态 → 决定要不要动作 → 继续睡。心跳本身不保证做什么，只保证"有机会检查"。适合触发条件不确定、但需要持续关注的任务：盯某个网页是否下线、等一封邮件、监测文件是否出现。

判断标准就一句话：**能预测"什么时候该跑"，用 cron；需要"一直盯着直到条件成立"，用 heartbeat。**

## 实操要点

两者都在 OpenClaw 设置文件中声明。cron 给 agent 挂上 schedule 和任务描述即可；heartbeat 通常按较短间隔（如 60~120 秒）配置，关键是系统提示里写明每次醒来该检查什么。

## 踩过的坑

1. **cron 任务重叠**。任务执行时间超过周期，下一次触发进来，造成并发重复执行。建议在任务描述里加"先检查是否有未完成实例"，或引入简单锁。
2. **heartbeat 空转**。系统提示写得含糊，agent 每次醒来不知道查什么，就自己编动作。解决：把检查条件写死成具体路径 / URL / 关键词。
3. **时区陷阱**。cron 跟随服务器时区，别拿 UTC+8 的脑子写 UTC 的配置。统一在配置里显式声明时区。
4. **双机制互踩**。cron 和 heartbeat 挂同一 agent 时，同一个动作可能被两个机制各触发一次。我的做法：cron 只负责硬性任务，heartbeat 只做状态检查，不执行带副作用的动作。

## 可复用建议

- 默认用 cron，除非你明确需要"条件触发"。
- heartbeat 间隔从 60~120 秒起步，跑一天看日志再调。
- 任务描述里把"什么情况下不做"也写清楚，能省一半 token。
- cron 和 heartbeat 分别记录日志，观察触发时间与实际动作，尽早发现重叠。
- 状态检查类任务，用 heartbeat + MCP 工具组合：心跳负责唤醒，具体查询交给工具。

## 总结

cron 是闹钟，heartbeat 是哨兵。闹钟定好就行；哨兵得一直站岗，站岗成本必须算清楚。新任务我一般先问自己：它该在某个时刻发生，还是该在某个条件下发生？答案出来，选型就完成了。
