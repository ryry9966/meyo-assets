## 背景

现在市面上的 AI 助手，绝大多数本质上是 reactive（被动响应）的。你发一句，它答一句；你不发，它就沉默。但真正有价值的工作流往往是：问题还没成型、你还没打开对话框，事情已经被处理掉了。这轮大家都在卷 agent 的主动执行能力，但 `proactive` 的关键不在模型本身，而在你如何把它接进入口、触发器和业务流。

## 问题

被动助手再聪明，也解决不了以下场景：

- 你早上打开 Slack，发现昨晚的 CI 挂了，但你不知道
- 你下午 2 点开会，但 1 点还没拿到上个环节的交付材料
- 你的服务器磁盘跑到 85%，但因为监控告警在邮件垃圾箱里，你等到业务报警才知道

这些场景的共同点是：**你缺的不是问答，是有人替你盯着状态，并在合适时机用合适方式告诉你**。

## 你的做法/步骤

我以 OpenClaw + MCP 为例，做一个最小的 proactive 配置。

**1. 建立状态源**

先得有一个可轮询的状态源，Proactive 不是凭空猜测，而是基于已知状态判断。我用的是已有的 MCP server（比如监控/仓库/邮件），把这些做进 OpenClaw 的上下文里。

**2. 定义一个轮询任务**

在 OpenClaw 里加入一个定时触发任务。不需要复杂的调度框架，一个简单的 cron 表达式就可以。触发之后，Agent 会去调用 MCP 工具拉取状态，然后判断——不是每次都输出，而是只有在“异常/需关注”时才发起 notice。

**3. 设置输出通道**

把 notice 推到你想被通知的地方。OpenClaw 现在可以配合钉钉/飞书/Slack webhook。简单来说：

- 正常状态：静默
- 异常状态：发一条结构化信息（事件 + 影响 + 建议动作）

**4. 让用户在被通知时能直接下发指令**

这是 many 项目常忽略的一步。通知里带上可执行的指令选项，比如：“回复 `修复` ”或“已处理”。这一步把 proactive 和 reactive 闭环连起来，不用你二次打开工具。

## 踩坑点

**坑 1：先别急着做“自动执行”**

很多人的第一次尝试是让 agent 发现问题后直接“搞定它”。这个想法很危险。如果你让 agent 自己去重启服务、改配置，一旦上下文错误或工具操作失误，后果不可控。**先做到“会通知”，再谈“会替你做”**，这是一个从 notice 到 action 的渐进过程。

**坑 2：没做去重和状态判断**

通知做出来后，cron 每 5 分钟跑一次，结果同一个磁盘告警发 10 次。用户第一反应是拉黑。需要在 agent 的 prompt 里明确告知：只报告**状态变化**和**升级事件**的维护逻辑，或者给 MCP 加一个简单的 cache。

**坑 3：忽略上下文导致的“噪音”**

有的系统为了显得智能，把同一个事件配上不同的措辞输出。看起来聪明，反而让用户困惑。请保持输出模板的稳定性，人更信任一致性强的信息。

## 可复用建议

如果你也想给自己的 agent 加上 proactive 能力，我的建议是：

1. **先选一个明确场景**：不要追求全知全能，先盯一件事，比如“定时轮询 CI 状态”。
2. **端口要有一个业务判断逻辑**：加上“发生什么才值得报告”的阈值条件，这是 proactive 和“骚扰”的分界线。
3. **通知的形式要比内容重要**：高频低噪的通道（如 Slack 频道）比短信/电话好得多，因为噪音能被频道消化，而不是打断用户。
4. **给自己留一个逃生门**：设计一个“停止提醒”的指令，这对用户和 agent 本身都是保护。

## 总结

Proactive 能力本质上不是 AI 的“灵光一现”，而是一套基于监听、状态判断、通知分发的工程系统。它让 agent 从“问答工具箱”变成了“值守工程师”。需要的能力不是更大参数的模型，而是一个合理的触发源、克制的判断规则，和一个不打扰人的出口。

Agent 不该等你说“帮我看看”，它可以一直看着。
