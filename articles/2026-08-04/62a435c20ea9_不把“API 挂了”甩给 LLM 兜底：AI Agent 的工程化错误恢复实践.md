## 背景

Agent 应用的可靠性瓶颈，往往不在模型推理，而在其外围依赖。一个典型的 OpenClaw 工作流里，Agent 需要同时编排搜索 API、代码解释器、MCP 工具。只要其中任何一个外部服务出现抖动，你看到的结果不是“服务暂时不可用”，而是 Agent 开始自说自话：要么反复重试同一个请求直到超时，要么直接声称“搜索完成，未找到结果”，要么抛出半截 JSON 导致整个流程中断。

许多人在搭建 Agent 时默认了“工具永远可靠”，这是最危险的前提。本文不讨论如何让 API 变稳，只讨论一个实际问题：当外部 API 挂掉时，Agent 如何体面地失败，而不是失控。

## 问题：Agent 依赖外部 API 时的三类典型故障

结合 OpenClaw 场景，故障可分为三类：

1. **瞬时故障（网络抖动、503）**：请求没发出去，或服务端明确表示“请稍后重试”。这类故障具备自愈可能。
2. **确定性故障（400、401、403）**：请求本身有问题或密钥失效，重试一万次也没用。
3. **静默失败（返回 200 但响应内容为空/畸形）**：最阴险。Agent 把它当成正常结果处理，误报数据不存在。

很多实践者试图通过修改 system prompt 来纠正错误，比如“如果你遇到 API 错误，请重试”。这会带来两个副作用：LLM 并不知道该重试多少次、退避多久（可能造成重试风暴），而且 Agent 在失败后倾向于编造“代替性输出”来满足用户的请求，这在业务中可能比报错更危险。

## 做法：把错误处理写成协议，而非塞进 Prompt

以下方案假设你正在 OpenClaw 中自定义一个工具或插件。核心思路是：**工具的错误结果，本身应该是一种结构化数据，而不是一坨文本异常。** Agent 策略层只负责根据结构化错误码做决策。

### 第 1 步：为工具定义统一错误返回协议

在你的 MCP 工具返回体中，增加如下字段：

```json
{
  "ok": true,
  "data": {},
  "error": null
}
```

失败时统一返回：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "E_UPSTREAM_TIMEOUT",
    "message": "GET https://api.external.com/v1/search timed out after 5s",
    "retryable": true,
    "fallback_used": true,
    "fallback_source": "cache_snapshot_20240501"
  }
}
```

这里的关键是 `code` 和 `retryable`。不要直接让 Agent 阅读原始堆栈或 HTTP 状态码，LLM 对 HTTP 状态码的“重试直觉”极差。

### 第 2 步：在工具描述中写明“错误策略契约”

在 MCP 工具的 `description` 字段中，明确告诉 Agent：

```
注意：该工具返回 retryable=false 时，不得重试，应报告最终失败；返回 retryable=true 时，最多等待 2 秒后重试一次；同一任务内重试次数上限为 3 次。若第 3 次仍失败，使用 response 中的 fallback 字段数据作为结果，并在回复中注明数据来源。
```

这不算 Prompt 工程，这是协议约定。LLM 遵循的能力有限，但你给它一个精确的有限状态机，它通常能照着走。

### 第 3 步：在 OpenClaw 策略层实现重试状态暴露

不要把所有重试逻辑都放在工具内部。在 OpenClaw 的 Agent 循环中，给当前“任务上下文”增加一个简单的计数器字段，例如 `retry_map: {"toolA": 2}`。你的插件可以在每次工具调用后读取 `conversation.memory` 中的计数，超过阈值时直接拒绝再次执行并输出明确最终错误。这需要自定义插件逻辑，但可以避免 LLM 陷入无意义的死循环。

### 第 4 步：做一次“错误恢复演练”

找一台与生产环境隔离的测试机，使用 `tc`（流量控制）或直接配置一个 mock server（如 Prism / WireMock）模拟以下场景，观察 Agent 行为：

- 模拟 503：Agent 是否按预期重试 2-3 次？
- 模拟 401：Agent 是否立即放弃并报告配置错误，而不是反复重试？
- 模拟返回残缺 JSON：Agent 是否能识别 `ok:false` 并触发 `E_UPSTREAM_FATAL` 分支？

这一步的目的是检验你的“错误契约”是否被 Agent 真正遵循。你会发现一个现象：**如果契约足够清晰，各模型的表现差别不大；如果契约模糊，最聪明的模型反而更能编造错误原因。**

## 踩坑点

1. **不要在 `description` 里让 LLM 自己决定重试间隔和次数**。它会把“重试”理解为“循环调工具直到成功”，导致在 OpenClaw 中触发巨额 API 账单。
2. **捕获异常后不要丢失原始错误信息**。有节点把 `error` 字段截断到 20 字再传给 LLM，导致无法区分“超时”和“认证失败”。
3. **不要无脑缓存 fallback**。如果你把“上次调用成功的返回”当作兜底数据，必须让 Agent 知道数据是旧的。否则，你可能在错误修复后仍向用户展示过期信息——这正是“静默失败”的升级版。
4. **慎用工具自身的自动重试 SDK**。不少 HTTP 客户端默认开启 3 次自动重试，再叠加 Agent 层重试，实际请求数会变成 9 次。建议在工具内部关闭 SDK 自动重试，统一由策略层调度。

## 可复用建议

以下是可直接抄走的检查清单：

- **每个外部调用工具必须返回 `ok` 字段**，失败时必须返回 `error.code`、`error.retryable`。
- **人工规定重试上限**：`E_UPSTREAM_TIMEOUT` 可重试 1 次，`E_HTTP_5xx` 可重试 2 次，`E_AUTH` 永不重试。写成表格放在 OpenClaw 项目 README 中，让所有参与者统一口径。
- **兜底数据必须打标**：在使用缓存或默认数据时，在结果中显式携带 `fallback_source` 字段。
- **任务中断时写入 pending 状态文件**：长任务调用外部 API 时，受网络波动影响，Agent 进程可能被杀。建议将当前请求参数和已执行步数写入一个 `.pending` 的 JSON 文件，重启时优先检查并恢复。
- **定期做“混沌测试”**：每月随机注入一次 API 故障，核对 Agent 是否按预期降级，而非仅依赖上线前的演练。

## 总结

AI Agent 的错误恢复，本质上是一个分布式系统的可用性问题。LLM 的上下文窗口再大，也解决不了“上游什么时候恢复”这样的外部约束。务实的做法是：**将工具的失败结果结构化，将重试策略形成硬性的数字与字段约定，并在策略层强控次数，同时在降级路径上保留可解释性。**

在 OpenClaw 这类偏工程化的 Agent 框架中，稳定性的提升更多来自你对工具返回契约的打磨，而非对 Prompt 的修辞。记住：如果你的 Agent 在 API 挂掉时还能给出明确、可溯源、不撒谎的回答，它就已经比大多数生产环境中的 Agent 可靠了。
