在 Agent 的记忆系统里，recall 决定了模型能想起什么。社区里很多人默认用 embedding + 向量库做语义搜索，觉得“更智能”。但跑过真实数据的工程实践会发现，全文搜索（BM25/FTS）在某些场景下反而更可靠。

## 问题

“用语义搜索啊，精度高”“全文搜索太原始了”这类说法经常出现。我们做了一个对照实验：在 3000 条混合记忆（代码片段、配置文件、自然语言日志、命令记录）上，用同一组查询对比两种检索方式。

## 测试设计

- 语义：all-MiniLM-L6-v2 嵌入 + FAISS（HNSW32）
- 全文：SQLite FTS5（BM25），默认 unicode61 tokenizer，中文另做空格分词
- 查询集：30 条，包含精确技术词（如 `brew install`）、同义改写（“安装” vs “setup”）、代码 ID（如 `config.yaml`）、中文对话式提问

## 结果与解读

- 精确/代码类查询，全文搜索结果评分平均高 32%。向量召回容易把 `v2` 和 `v1` 混在一起，embedding 对数字后缀不敏感
- 对话式查询（“上次那台机器怎么配置的”），语义搜索显著占优
- 延迟：全文搜索平均 <2ms；语义搜索含嵌入生成 >50ms，batch 场景更糟
- 存储：FTS 索引约原始文本 1/3；向量库还要加载模型，首次约 80MB 内存

## 做法：混合检索

1. 记忆写入时同时维护两份索引：FTS5 字段和 embedding 向量
2. 查询时先跑 FTS5 用 BM25 取 top 20
3. 将 query 嵌入，对 top 20 做语义重排
4. 用 RRF 合并：`score = 1/(60+rank_fts) + 1/(60+rank_sem)`。权重稳定，不用调 alpha

## 踩坑点

- 嵌入模型对代码/URL/特殊字符不敏感：`dev-api.example.com` 和 `prod-api.example.com` 的距离可能很近，FTS 一眼命中
- 语义阈值陷阱：设 0.75 会漏掉真正相关的结果，0.5 又引入噪声。改用相对阈值（top_k 中最小距离与中位数比值）
- FTS5 默认 tokenizer 不适合中文，需要装 simple tokenizer 或手动给文本分好词再写入
- 向量库冷启动：小数据量（<1 万条）直接暴力检索，不要上 IVF，否则聚类训练时间比查询还长
- 别在检索阶段就截 top 5：语义重排需要候选池，建议 top 20 起步，重排后再截断

## 可复用建议

- 默认记忆底座用 FTS5 做召回，语义搜索只做重排，不要颠倒
- 精确实体（命令、版本号、文件名、ID）落到全文索引里，并给 title 字段加权
- 查询分流：如果 query 包含 `[/.#_-]` 或近似纯英文数字组合，直接走全文；自然语言走混合
- 记录日志：标注哪些结果由 FTS 产出，哪些被语义重排提升，方便调参
- 用 RRF 而不是加权分融合，少一个超参数就少一个坑

## 总结

语义搜索不是银弹，全文搜索也不落伍。在 Agent 记忆场景中，全文搜索提供确定性，语义搜索弥补泛化，两者结合才是真正可用的 memory_recall。
