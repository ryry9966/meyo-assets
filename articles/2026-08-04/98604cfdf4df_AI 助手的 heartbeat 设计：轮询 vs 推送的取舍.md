## 背景

OpenClaw 这类 agent 框架在跑自动化任务时，经常需要监听外部状态：协调者派发的任务队列有没有新条目、MCP 工具连接是否存活、长时间运行的 tool call 结果何时返回。这层"感知机制"就是 agent 的 heartbeat 设计。它直接决定了两件事：任务的响应延迟，以及空闲时段的资源占用。

写这篇是因为我在实际集成 MCP transport 和任务队列时，在轮询/推送之间反复横跳过，踩了一些坑，记录一下思路。

## 问题

轮询的思路很简单：每个固定周期发一次请求，检查状态有没有变化。代价是延迟和负载之间的平衡很难调——间隔大了，任务到达后要多等好几秒才被感知；间隔小了，空闲时段大量空请求打到上游，纯粹浪费。

推送（WebSocket/SSE）解决了延迟问题，但引入了连接管理复杂度：断线重连、半开连接检测、代理空闲超时。尤其对于 MCP，不是所有 transport 都天然支持服务端主动推送，很多场景下你不得不用 HTTP 轮询去模拟。

## 做法

我的建议是三步走，**不要一开始就上推送**。

**第一步：量化需求。** 先回答两个问题：任务到达的峰值频率是多少？从事件发生到 agent 感知，可容忍的延迟是几秒？如果任务频率低于每分钟一次、延迟容忍度超过 5 秒，轮询完全够用。

**第二步：轮询起步，但要做自适应间隔。** 固定间隔是最常见的错误。正确做法：从 1 秒起步，连续 N 次无新事件后逐步退避到 5 秒、15 秒、60 秒封顶。每次请求加 ±20% 的 jitter，避免多个 agent 实例在同一时刻打满上游。当退避间隔已经很大时，可以主动降低探测频率，把 heartbeat 当作"保活 + 查状态"二合一。

**第三步：按需引入推送。** 只有当轮询延迟无法满足需求、或空闲请求开销已经影响上游成本时，才考虑 SSE。SSE 比 WebSocket 更适合 agent 场景：单向服务端推送、协议简单、客户端自动重连（Node 的 EventSource 客户端成熟）。但你需要服务端配合。MCP 的 HTTP+SSE transport 在部分 nginx 网关下会因为空闲连接超时被断开，客户端必须定期发 ping 保活。

## 踩坑点

- **WebSocket 重连不做退避。** 断线瞬间客户端每 100ms 重连一次，直接把服务端连接池打满。必须加指数退避 + 最大重试次数。
- **忽略半开连接。** 网络断开不通知应用层，长连接处于假死状态，任务到了也感知不到。需要应用层心跳 ping/pong 来探测，间隔建议小于代理超时时间的 1/3。
- **心跳和业务消息混在一起**。一旦出问题，你分不清是网络抖动还是业务异常。日志里要能区分。
- **轮询和推送代码耦合。** 两边状态互相影响，比单模式难排查得多。

## 可复用建议

1. 心跳消息带递增 seq 序号，客户端可以检测消息丢失或乱序。
2. 记录 `heartbeat_gap` 指标——连续两次有效心跳的间隔，如果超过设定阈值的 2 倍，立即告警。这个指标对轮询和推送都适用。
3. 推送失败自动降级为轮询，这是最稳的兜底策略。
4. heartbeat 逻辑做成独立组件，与业务逻辑解耦，方便单测和服务集成测试。

## 总结

不要为了"实时"而实时。多数 agent 自动化场景下，自适应退避的轮询已经足够，代码简单、调试容易、故障模式清晰。推送更适合高频事件、低延迟要求的场景，但必须同时处理断开检测、重连退避和降级策略。工程上的正确路径是：先轮询跑起来，用指标说话，数据证明延迟不够再上推送。
