社区里跑 OpenClaw 或各种 MCP agent 的朋友，大概率都遇到过同一个场景：你告诉助手"代码提交前先跑 lint""用中文回复技术细节"，下次新会话它照样忘得一干二净。LLM 本身无状态，上下文窗口是临时纸带，不是硬盘。把偏好全塞 system prompt 不现实——塞多了窗口不够，塞少了效果差，而且维护成本高。真正该做的是外置记忆系统。

先拆解问题，其实只有三件事：**记住什么**（抽取）、**存在哪**（存储）、**什么时候用**（检索）。大部分实现死在第一步——把全程对话日志当记忆，查询时整段塞进上下文，噪音远大于信号。

下面是我在 OpenClaw 插件里跑通的分层方案：

**1. 偏好抽取层**

任务结束后，用低成本模型调用做一次结构化抽取，输出固定的 schema，而不是自由文本。建议字段：`domain`（coding / travel / writing）、`type`（style / workflow / constraint）、`content`、`confidence`、`source_session`、`expires_at`。例如用户说"以后提交前记得跑 lint"，抽取为 `{domain: "coding", type: "workflow", content: "commit 前跑 lint", confidence: 0.9}`。

**2. 存储层**

两层结构：确定性偏好（明确的祈使句、否定句）落 JSONL，键值索引快速精准匹配；语义类偏好（"喜欢简洁的代码注释风格"这类模糊表达）做 embedding，进本地向量库。sqlite-vss 或 LanceDB 够用了，别一上来就追重型数据库。重点是每条记忆必须有元数据，不能只有纯文本。

**3. 检索与融合层**

新会话初始化时做两件事：按 key 精确拉取该 domain 下的高置信度偏好；对用户当前输入做向量检索，召回 top-3 语义相关记忆。不要一次性全量注入。我的做法是分两级注入：一级偏好（确定性规则）随系统提示初始化给模型，二级偏好（语义相似）在任务进行中按需注入。

**4. 冲突处理**

同一条目两版冲突时，取时间新、置信度高者；旧记录保留但降权，防止反复横跳。

踩坑点，都是实际踩出来的：

- **把"用户说过一次"当成偏好。** 用户随口一句"这个翻译不错"，抽取器很容易记成"用户喜欢这种风格"。解法：只对祈使句、否定句、重复出现的表述做高置信度抽取，加阈值过滤。
- **记忆越多越糟。** 语义检索匹配到一堆低频噪音，注入后模型反而困惑。要加时间衰减和 `usage_count` 加权，让活跃偏好排前面。
- **多用户共用一个记忆文件。** 用户 A 的偏好串到 B 的会话里，隐私直接崩。记忆读写必须带 `user_id` 隔离字段。
- **抽取出错时机碰不到任务边界。** OpenClaw 里如果你把抽取 hook 挂在 `on_message`，任务没结束时调 hook，读到的是半截状态。要挂在 `session:complete` 事件后，数据才完整。

可复用的建议，直接抄：

- schema 设计走约定大于配置，先少字段后扩展。别一开始搞十几个实体关系，维护成本会压垮你。
- 记忆注入用提示模板槽位，比如渲染成 `<memory>` 块，让模型明确这是记忆来源，和普通上下文区分开。
- 每周跑一次合并任务：把旧的高置信度记忆压缩成概要，减少后续 token 消耗。
- 所有记忆操作必须走 MCP tool 暴露：`memory.add`、`memory.delete`、`memory.search`。用户可以直接说"忘掉我上次设的偏好"，agent 自己调删除工具。可解释性和可控性比存储技术本身更重要。

总结：记忆系统的核心难点不是存储，而是"什么值得被记住"的定义。先跑通抽取 + 结构化存储 + 分级注入，比一上来砸向量库有效得多。记住一句话：记忆的目的是减少重复沟通，而不是变成模型的又一段上下文。
