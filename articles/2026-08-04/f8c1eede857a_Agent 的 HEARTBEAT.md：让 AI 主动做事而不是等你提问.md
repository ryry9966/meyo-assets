如果你把 OpenClaw 当成一个高级 REPL，那你只用了它 20% 的能力。剩下的 80%，是让它脱离你的回车键，自己去定期巡检、清理、汇总、提醒。

这就是所谓的“主动 agent”。实现方式很多，我推荐一个极简、可验证、可维护的方案：**HEARTBEAT.md**。

## 背景：被动响应是默认状态

OpenClaw 这类 agent 框架，默认运行模式是“用户提问 → agent 回答”。对话有上下文，但生命周期短。一旦会话结束，agent 就失忆了。

你想让它每天检查一次磁盘空间、 RSS 是否有新条目、GitHub 有没有突发 issue——这些事本身不难，难在**它不知道上次什么时候干的、干到哪一步**。单纯挂个 cron 调 agent，你会发现它像新入职的员工，每天都问一遍完全相同的问题。

## 问题：定时 ≠ 主动

很多人试过“cron + agent 提示词”的组合，结果是：

- 重复执行：任务没有去重，每天生成 10 遍同样的日报；
- 上下文丢失：agent 不知道昨天已经处理过某个告警；
- 状态不可查：任务执行结果散落在 stdout 日志里，没法沉淀。

核心问题不是没有定时器，而是**没有持久化状态**。任务清单、上次运行时间、完成标记、备注——这些如果只在对话里，那 agent 永远无法真正“记得”。

## 做法：用 Markdown 当状态机

方案很简单：在一个固定路径放一个 HEARTBEAT.md，它就是 agent 的“长期记忆 + 任务清单 + 状态记录”。每次 agent 被唤起，**先读这个文件，再决定做什么**，最后把结果写回。

### 步骤

1. 规定文件路径，例如 `~/.openclaw/heartbeat.md`。

2. 写好文件骨架，结构固定，不要随意增删字段：

```markdown
---
last_run: "2025-06-08T02:00:00Z"
---

# 任务清单

## 每小时
- [ ] 检查临时目录大小，超过 5G 则清空，写备注

## 每日
- [ ] 拉取 RSS 更新，生成摘要到 notes/daily.md
- [ ] 查 GitHub 未处理 issue，汇总到 inbox

## 每周
- [ ] 轮转日志，只保留最近 30 天
```

3. 在 agent 的 system prompt 或每次会话的上下文注入里，加一段固定指令：

> 启动时先读取 HEARTBEAT.md。解析 front matter 中的 `last_run` 和每段任务。仅当 `last_run` 距今超过该任务周期（1h/24h/7d），且任务状态为 `[ ]` 时，才执行该任务。执行完毕后，将该任务标记为 `[x]`，在末尾追加一条执行记录，并更新 `last_run` 为当前 UTC 时间。

4. 用 cron 每 15 分钟唤起一次 agent：

```
*/15 * * * * openclaw run --prompt-file heartbeat.md >> /var/log/heartbeat.log 2>&1
```

5. 所有执行结果都追加到 HEARTBEAT.md 底部的“运行记录”小节。这样状态可以回溯，也可以交给别的工具消费。

这套流程跑通之后，agent 就不再是等人提问的门童，而是一个有办事清单、会写工作日志的巡检员。

## 踩坑点

这一节是实际跑了两周才明白的。

**绝对时间不可靠。** 任务里写“每天早上 9 点统计”，但 cron 可能因为休眠、网络原因错过。agent 醒来时已经 10:40，它就不知道“今天”算哪天的。解决方案：不要用“今天 9 点”，用 `last_run` 相对时间判断，“距今超过 24 小时才执行”。

**LLM 会“创造”格式。** 你让它维护格式，它会自行添加字段、改结构、变成另一种风格。这是常态。缓解手段：任务清单极其简短且固定，用列表而不是 prose；并且在指令中强调“不要修改任务清单的结构，只修改 `[ ]` 标记和追加记录”。

**不是幂等的。** 如果执行到一半被中断，任务还挂着，下次启动又跑一遍。加一个简单的锁文件：执行前创建一个 `.heartbeat.lock`，执行完删除。cron 启动时检测锁文件存在则跳过本次。

**忘记写回。** 只读不写是 agent 的习惯。必须把“更新 `last_run`” 作为强制步骤，否则老任务会反复执行。

**日志无限增长。** 追加记录没问题，但要限制只保留最近 100 条，或在记录区写明“超出则截断”。

## 可复用建议

- 把 HEARTBEAT.md 放进一个 git 仓库。这样 task 的变更历史、每次执行的 diff 都能看到，出问题可以直接回滚。
- 任务分区不要过多，三档足够：hourly / daily / weekly。每个分区保持 3~5 个任务，清单太长 LLM 会忽略后面的。
- 结合 MCP 工具时，把“读邮件”“查数据库”“发通知”这些能力写进执行指令里，但**不要写在任务本身**，只写在 system prompt 中，让 agent 自己决定怎么调用。
- 如果以后需要更精细的状态，可以在 HEARTBEAT.md 之外增加一个 `events.db` 记录历史；HEARTBEAT.md 始终只做入口和摘要，避免文件变重。

## 总结

让 agent“主动做事”的关键不在于定时器的频率，而在于**你是否给了它一个可读、可写、可持续的状态空间**。HEARTBEAT.md 用最朴素的方式实现了这一点：一群 markdown 里的勾选框，配合一个 `last_run` 时间戳，足以让 agent 从一个对话工具，变成一个真正意义上会自我驱动的执行者。

先跑起来，再优化细节。不用在意方案是不是过于简单——工程上，能稳定工作的简单约定，永远好过华丽但难以维护的架构。
