### 背景

用 OpenClaw 跑复杂任务时，我一度把需求全塞给同一个 agent。任务一长，它就开始「先做 A，再做 B，然后回头改 A」——不是它笨，是单线程架构下，所有子任务挤在同一个上下文窗口里，互相污染，Token 越烧越多，输出质量直线下降。

### 问题

典型的场景：一次要「调研三个竞品 + 整理发布渠道 + 写一份对比报告」。单 agent 顺序执行，小模型扛不住长上下文，强模型又贵得肉疼。更深的问题是**错误不隔离**——中间某一步出错，后面所有步骤都被带偏，重跑成本极高。

解决思路很朴素：把任务拆开，交给多个 subagent 并行做，主 agent 只做编排和汇总。

### 做法

我在 OpenClaw 里的实践分四步：

**1. 拆任务，定边界**
只拆「相互独立」的子任务。调研竞品 A/B/C 可以并行，但「先调研再写报告」不能并行——有依赖关系。每个子任务写成一句话契约：输入是什么、输出是什么、边界在哪里。

**2. 子任务模板化**
每个 subagent 的任务描述用固定模板，重点写清输出格式。我用 JSON Schema 约束返回结构，比如 `{source, findings[], confidence}`。格式固定，主 agent 汇总时才好处理。

**3. 并行派发，限时回收**
一次性派发所有子任务，每个 subagent 拿到的是裁剪过的上下文，不是全量对话历史。设超时（比如 60 秒），超时按失败处理，不阻塞其他任务。

**4. 主 agent 汇总 + 交叉校验**
回收结果后，主 agent 做交叉比对：两个 subagent 的结论冲突时，标出来让用户决策，而不是自作主张。汇总报告里保留每个子任务的来源，方便回溯。

### 踩坑点

- **拆得过细**。一个 20 分钟能做完的任务拆成 8 个 subagent，编排和上下文切换的开销超过并行收益。我的经验：子任务耗时 ≥ 主 agent 单步调度耗时的 5 倍，才值得拆。
- **上下文给太少**。subagent 没有主对话历史，任务描述里不带背景，它就会在自己的真空里瞎猜。任务模板里必须内置必要背景信息。
- **出错重试太粗暴**。并行场景下，某个 subagent 返回格式错误，不要整体重跑。只重发失败的那个子任务，保留其他结果。
- **Token 爆炸被忽略**。并行 = 同时打多个请求，上下文裁剪没做好，费用是线性翻倍的，并不会省下来。

### 可复用建议

1. **先手工拆一次再写配置**。用笔记画出任务依赖图，确认没有隐藏依赖，再配置到 OpenClaw。
2. **输出格式优先于输出内容**。先定 JSON Schema，再写任务描述。格式对齐了，编排逻辑就成功了一半。
3. **给每个 subagent 加独立 role 标识**。日志里能区分是谁产出的结果，排障时省一半时间。
4. **从 2 个子任务起步**。先把主 agent 的汇总逻辑跑通，再加并行度。一上来就 6 个并行，失败时你会同时面对 6 份错误日志。

### 总结

Subagent 编排不是「越多越快」，而是**用工程设计换并行度**。拆解、契约、隔离、汇总——每个环节都在做同一件事：把「一个 agent 的脑子」变成「一个可运维的分布式系统」。做对了，复杂任务的速度和稳定性都会上一个台阶；做错了，不过是用更贵的方式排队而已。
