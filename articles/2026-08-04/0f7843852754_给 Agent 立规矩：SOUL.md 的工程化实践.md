## 背景

在 OpenClaw 这类 Agent 平台上，模型本身没有长期人格：每次会话都是全新上下文。没有 SOUL.md 的 Agent，像个没入职培训的新员工——昨天回答简洁，今天长篇大论；该拒绝高危操作时直接执行。SOUL.md 就是给 Agent 的"员工手册 + 操作边界"，在会话启动时被注入 system prompt，持续约束行为。

## 问题

默认情况下，Agent 普遍存在三类不一致：

1. **风格漂移**：同一任务在不同会话中输出格式、语气差异很大。
2. **边界缺失**：对删除文件、调用高成本 API、访问外部资源等操作缺乏确认机制。
3. **上下文浪费**：没有明确规则时，Agent 把大量 token 花在试探性输出上。

SOUL.md 解决的不是"让它更像人"，而是让行为可预测、可审计、可控制。

## 做法

**1. 放置位置**  
对 OpenClaw，把 SOUL.md 放在项目根目录或 Agent 的 memory 目录，OpenClaw 会在会话启动时读取并拼入 system prompt。放错路径 Agent 根本看不到。

**2. 文件结构**  
建议分 5 个区块：

- 身份：你是谁，面向谁
- 行为准则：回答方式、输出格式
- 硬边界：绝对禁止的事 + 例外条件
- 确认清单：哪些动作必须先向用户列出计划
- 成本限制：单次任务 API 费用上限、速率上限

**3. 写作语言**  
用可测试的祈使句，不用形容词。例如：

- ❌ Be helpful and concise.
- ✅ MUST 用要点输出，除非用户明确要求，否则不超过 200 字。

**4. 联动 MCP**  
在 MCP tool 的描述中引用 SOUL.md 的规则编号，例如：*"This tool MUST call confirm_plan before execution per SOUL.md §3.2"*。这比单纯依赖模型自觉可靠。

**5. 验证**  
写 5 个 probe 输入：模糊请求、高成本操作、删除操作、超长输出请求、重复请求。运行后检查输出是否符合每条规则。

## 踩坑点

- **写太长**。超过 1000 token 后模型注意力明显下降，规则越多越容易被忽略。控制在 300-700 token。
- **规则矛盾**。"绝不拒绝用户"和"高风险操作必须确认"同时出现时，模型会随机选择。用 MUST/SHOULD/MAY 标注优先级。
- **过度禁止**。把合法动作也禁掉，反而逼用户绕过 Agent。优先用 "must confirm before" 替代 "never"。
- **不纳入版本控制**。SOUL.md 和代码一样要 git 管理，每次改动都能看到 diff 并回滚。
- **多文件冲突**。base 和项目级 SOUL.md 同时存在时规则叠加，冲突处要用明确的优先级声明。

## 可复用建议

- 准备一份 base SOUL.md 放在 `~/.config/openclaw/`，内容是通用约束（格式、成本、确认机制）。
- 每个项目放一份 project SOUL.md，叠加项目特有的目录结构、命名规范、禁止访问路径。
- 规则写成断言式句式，方便日后写脚本自动化校验。
- 会话结束后让 Agent 反馈"本次是否遵守了全部规则，哪条最接近违反"，作为迭代依据。
- 每次修改记录 changelog，与功能发布绑定，方便回溯行为变化是由哪次改动引起的。

## 总结

SOUL.md 不是玄学，是一份被注入上下文的配置文件。目标不是"赋予人格"，而是把 Agent 的行为收敛到可预测、可管理的范围。保持精简、用祈使句、纳入版本控制、定期用 probe 验证。先在本地跑两周，再决定是否推广到团队。
