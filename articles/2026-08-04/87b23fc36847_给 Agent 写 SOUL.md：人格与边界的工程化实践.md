## 背景

在 OpenClaw 这类本地优先的 Agent 框架里，能力边界完全由用户自己定义：挂哪些 MCP 服务、开哪些插件、给工具多大执行权限。这种自由度带来的隐患是行为一致性全靠 prompt 设计去兜底——但 system prompt 经常被框架覆盖或截断，上下文一长，Agent 就开始飘。

SOUL.md 解决的是这个：把人格和边界固化成一份独立、持久、可版本管理的文件，每次会话启动时稳定注入，而不是让 Agent 在聊天记录里"记住自己是谁"。

## 问题：没有 SOUL.md 的三个典型症状

1. **角色漂移**：会话超过十几轮后，语气和立场会偏离初始设定，甚至出现"假装自己是另一个产品"的幻觉。
2. **权限失据**：工具调用边界模糊。该自动执行的步骤反复询问，真正危险的操作却可能被直接执行。
3. **行为黑盒**：出了问题无法快速定位"它为什么这么干"，因为没有任何一份文件记录了 Agent 的默认行为契约。

## 做法：SOUL.md 怎么写

我目前的 SOUL.md 分五段，每段条目控制在 5 条以内：

```markdown
# 身份
你是运行在本地环境中的自动化助手，服务于**维护者本人**。
默认语气：直接、精炼；给出结论再补解释。

# 行为规则（按优先级排序）
1. 每轮任务结束，必须用一句话总结已执行的动作。
2. 读取或修改本地文件前，先说明影响范围。
3. 除非显式授权，不得向任何远程端点发送日志。

# 工具边界
- 可自动执行：文件搜索、日志查看、只读 API 调用。
- 必须二次确认：删除、覆盖、git push、安装依赖、发送网络请求。
- 禁止执行：格式化磁盘、修改系统级配置。

# 失败处理
- 工具报错：记录错误码，重试一次；失败则停止并输出可复现的命令。

# 变更记录
- 2025-08-30: 增加工具边界第二项（覆盖操作需确认）。
```

文件放到 Agent 的持久记忆目录，启动时注入到 system prompt 前缀。关键一步：纳入 git 管理，每次改动可以 diff 出"Agent 行为为什么变了"。

## 踩坑点

- **写了抽象规则等于没写**。比如"要负责任"这种话，Agent 无法判定。必须写成可判定的条件句："删除文件前必须输出将被删除的路径列表"。
- **规则之间打架**。"优先自动化"和"高危操作需确认"并存时，Agent 会随机选择一个解释。解法是明确标注优先级顺序。
- **规则与插件脱节**。你写了"不调用外部 API"，但挂载的 MCP 服务已经暴露了 HTTP 工具，等于没约束。SOUL.md 必须和插件清单同步审查。
- **把 SOUL.md 当成一次性文件**。插件升级、工作流变更后，边界文件不更新，很快就会发现 Agent 重新开始瞎搞。

## 可复用建议

1. 每条规则都要能通过"可测试性测试"：你能不能写出一个触发场景来验证它被遵守了？写不出来就删掉重写。
2. 变更走 PR + 评审流程，哪怕只是改一句话。不要在对话流里说服 Agent"内部记住"，那不可追溯。
3. 每次增删 MCP 插件，顺手过一遍工具边界段。
4. 验证加载：启动时打印 SOUL.md 前几行，确认注入成功，否则你以为设了规则，实际没有。

## 总结

SOUL.md 不是玄学，也不是给 Agent 写人设小作文。它是把"这个 Agent 应该是什么样"从隐式上下文变成显式文件的过程——可审计、可回滚、可测试。一份好的 SOUL.md 不会让 Agent 更聪明，但能让它稳定地不犯错，而这恰恰是自动化场景里最稀缺的品质。
