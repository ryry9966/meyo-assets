## 背景

在 OpenClaw 生态里跑自动化，最常见的是三类触发：cron 定时、事件订阅（webhook/inbox）、以及失败重试机制。你大概率遇到过类似情况：某个 MCP 插件因为网络抖动触发超时重试，结果同一笔操作被执行了两次；或者定时任务在数据库迁移、服务重启后补跑，导致重复发通知、重复扣费、重复创建资源。

问题不是"任务是否会被重复触发"，而是"重复触发后系统是否还能保持正确"。这，就是幂等性（Idempotency）要解决的。

## 问题

幂等（Idempotent）的定义很简洁：**同一个操作执行一次和执行 N 次，系统状态保持一致**。服务端天然幂等的有：Redis 的 `SET`、对象存储的 `PUT`（覆盖写）、MySQL 的 `DELETE by id`。天然不幂等的有：`INSERT`、`APPEND`、发送邮件、调用 Stripe 扣款、往队列里 push 消息。

很多 Agent 开发者把精力花在 prompt 和工具调用上，却忽略了一个事实：**没有幂等保护的自动化，等于把业务正确性交给了运气**。尤其在 OpenClaw 这种多工具编排的场景下，一个任务可能串联了十几个 MCP 工具，任何一个环节的重复执行都可能产生级联副作用。

## 做法

实战中最有效的是"两层防御"：**业务层找唯一键，执行层加幂等令牌**。

**第一步：找出每个操作的自然幂等键**

先问自己：这个操作完成后，系统里留下了什么"不可重复"的事实？例如：

- 创建工单 → 用 `task_uuid` 作为外部 ID
- 发送通知 → 用 `event_id + channel` 做去重
- 同步外部数据 → 给数据源加一个 `updated_at` 游标，只处理增量

**第二步：引入幂等令牌（Idempotency Key）**

对不天然幂等的操作，在调用侧生成一个 UUID，把它作为参数传给目标系统。OpenClaw 的 MCP 工具调用链中，你可以在自定义插件层拦截：

```python
def run_with_idempotency(func, *args, idem_key=None, **kwargs):
    key = idem_key or f"{func.__name__}:{uuid4().hex}"
    if redis.exists(key):
        return redis.get(key)  # 直接返回上次结果
    result = func(*args, **kwargs)
    redis.set(key, result, ex=86400)  # 1 天有效
    return result
```

**第三步：先查后写变成条件写**

更可靠的做法是把"检查-执行"合并为原子操作。例如 MySQL 用 `INSERT ... ON DUPLICATE KEY UPDATE`，Postgres 用 `INSERT ... ON CONFLICT DO NOTHING`，避免"先查询再插入"之间的竞态窗口。

**第四步：重试时复用同一 key**

重试逻辑必须携带原始请求的 idem_key，而不是每次重新生成。这一点在 OpenClaw 的异步任务队列中尤其要谨慎——很多人在重试回调里新建了参数对象，把 key 丢了。

## 踩坑点

1. **把"网络幂等"当"业务幂等"**。HTTP GET 是幂等的，但它的副作用可能是后端的 POST。测试时对同一个 endpoint 多打几次，看看数据库里多了什么。理想做法是给读操作也加 trace ID，方便排查。

2. **时间窗口陷阱**。如果你的幂等键是 `hour + user_id`，那么 23:59:59 和 00:00:00 触发的两次调用就是两个不同 key——尽管业务上它们应该是同一个批次。建议粒度拆成 `时间戳对齐的窗口` 而不是自然小时。

3. **分布式环境下的持久化**。在单进程里用 `dict` 记 key 很简单，但 OpenClaw 的 agent 可能在多 worker 下运行，内存态不共享。必须把 key 存在 Redis 或数据库中，且注意设置 TTL，避免 key 无限膨胀。

4. **失败后的状态残留**。一个任务执行到一半失败，数据库里已经有了部分记录，重试时"幂等检查"发现 key 存在就返回旧结果——但旧结果是半成品。需要在步骤中记录状态机（pending/done/failed），只在 `done` 时命中幂等返回。

## 可复用建议

- **所有写操作默认生成唯一 external_id**，这个 id 由调用方生成，服务端只存储不生成。这让任何一个 MCP 插件都天然支持幂等。
- **把幂等检查放在 Agent 编排层，而不是每个工具内部**。工具是底层，往往不知道上层语义；编排层知道"这是同一个任务的第几次重试"，更适合做判断。
- **记录每次执行的 hook 明细**。OpenClaw 允许给工具调用加中间件，建议在中间件里记录 request/response hash，复现问题时能立刻定位是否是重复执行。
- **测试幂等性的方式很简单**：手动同一参数调用两次，断言第二次的副作用为零（或者结果一致）。把它写进 CI。
- **优先用系统已有的幂等能力**。Stripe、GitHub API、Slack API 都有官方 idempotency-key 支持，直接用；Redis Lua 脚本可用于原子化多步操作。

## 总结

幂等性不是"锦上添花"，而是自动化系统从 demo 走向生产的分水岭。在 OpenClaw 生态里，agent 执行任务的路径越长、调用的工具越多，重复执行的概率越高，但只要我们为每个关键写操作设置合理的幂等键、以原子条件写代替先查后写、并在重试时复用同一个 key，绝大多数重复执行问题都能从机制上消除。

给读者的建议就一句话：**下次写插件时，先问自己——同一份入参执行两次，系统会怎样？如果答案是"会出问题"，就停下来补幂等。**
