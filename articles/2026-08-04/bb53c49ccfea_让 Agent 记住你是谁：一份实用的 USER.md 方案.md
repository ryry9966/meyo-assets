## 背景

用 OpenClaw 一段时间后，我发现一个尴尬的事实：模型上下文越给越长，但每次会话它还是像第一次认识我。它会问「你用什么语言栈」「你偏好的代码风格是什么」——这些我在上次对话里已经回答过五遍了。

问题不在模型能力，而在记忆。Agent 启动时是"无状态"的，MCP 工具再多，它也不了解使用者的环境、习惯和边界。除非我们主动给它一份「用户说明书」。

## 问题

我最初的做法是在每轮 Prompt 里重复背景信息，结果有两个问题。

一是浪费。每次重新叙述，Token 消耗大；而且写多了，Agent 分不清哪些是本次任务要点，哪些是长期偏好。

二是不一致。不同会话里我的描述有细微差异——今天是「Go + PostgreSQL」，明天是「Go 和 PG」——模型接收到的信号是噪声，无法形成稳定的偏好判断。

后来我把长期信息整理成一份 `USER.md`，放在 OpenClaw 启动时自动加载的配置目录里，效果明显改善。下面是具体做法。

## 做法

### 1. 确定加载位置

OpenClaw 支持在会话启动阶段读取用户级配置文件。把 `USER.md` 放在它默认扫描的用户目录下，确保每次会话开头自动注入，而不是靠手动引用。

### 2. 结构化内容

我的 USER.md 分五个区块：

- **身份信息**：称呼、时区、工作角色。别写客套话，Agent 需要的是可操作的约束。
- **技术环境**：常用语言、数据库、部署平台、版本偏好。例如「生产环境一律用 Docker Compose，不用 K8s」。
- **沟通偏好**：回答要多详细、要不要代码示例、能否反问。我写的是「先给结论再展开，示例代码必须可运行」。
- **常用任务模板**：例如「部署 = 写 Dockerfile → compose up → 写迁移脚本」。这相当于给 Agent 一份作业指导书，它会按你的流程走。
- **禁忌列表**：明确写「不要改动全局配置」「不要建议用 Redis 做消息队列」这类硬约束。

### 3. 版本管理

USER.md 放进 git 仓库，保留修改历史。多台机器共用同一份文件，避免 Agent 行为漂移。

### 4. 定期校准

每周或每两周过一遍，删掉过时条目。「当前项目」这类易变信息不要写进 USER.md，应通过会话内临时上下文传递。

## 踩坑点

- **写太长**。我第一版写了 600 行，Agent 在大段噪声里抓不住重点。压到 150 行以内后效果明显变好。
- **写太抽象**。「写出高质量代码」毫无指导意义。要写「函数超过 30 行就拆分，命名用动词+名词」这种可判断的规则。
- **隐私问题**。USER.md 可能随上下文发给模型服务商，密码、Token、内部系统地址一律不写。
- **忽略冲突**。当项目级文档和 USER.md 冲突时，我明确约定「项目级配置优先于用户级」，避免 Agent 无所适从。

## 可复用建议

1. **给 Agent 一段「角色设定」**，可以让推理风格更一致，比如「你是资深 Go 工程师，回答偏保守，不追逐新框架」。
2. **把反复粘贴的 Prompt 片段收敛进 USER.md**，而不是每次重写。
3. **让 USER.md 变成工作流的一部分**，我习惯在每周复盘时顺手更新它。
4. **写清楚「何时不要用」**。Agent 不会拒绝指令，明确边界比多加鼓励更重要。

## 总结

USER.md 的本质，是把人与协作者之间「他应该了解我」的隐式假设，显式化成 Agent 可读取的配置文件。它不神奇，但能把 Agent 从「聪明的陌生人」变成「靠谱的同事」。关键在于内容精炼、边界清晰、定期维护。如果你也在重度使用 OpenClaw，值得花半小时建立自己的 USER.md，收益是长期的。
