## 背景

日常使用 OpenClaw 时，一个隐蔽的瓶颈不是模型能力，而是"它不知道你是谁"。每次新会话，Agent 对用户身份、偏好、禁忌的认知都是零。上下文窗口再大，如果关键信息不在里面，模型就只能靠通用假设来生成回复。

这个问题的根源是：我们把应该固化的个人画像，当成了每次对话都要重新输入的临时信息。

## 问题

和 Agent 协作时，最常出现三类低效：

1. 重复描述自己（"我是后端工程师，技术栈 Go + PostgreSQL"），每个会话说一遍，且经常遗漏。
2. 风格不一致。Agent 默认输出模板化内容，你偏好代码带注释、回复要短、选型要保守——但 Agent 不知道。
3. 隐性知识丢失。你讨厌 YAML、习惯用 Makefile、项目里有不可动的 legacy 模块。不写下来，Agent 就会踩坑。

这些信息本来就不该依赖模型"猜"。

## 做法

我的方案：在工作目录维护一份 USER.md，作为 Agent 的个人档案，并让它在会话启动时主动读取。

1. **文件位置**：全局档案放 `~/.openclaw/USER.md`，项目档案放 `docs/agent/USER.md`，按作用域区分。
2. **核心结构五段**：
   - 身份：一句话说清职业、技术栈、常用工具
   - 环境：本机 OS、Shell、包管理器、编辑器
   - 偏好：代码风格、回复长度、选型倾向
   - 禁忌：明确不做什么（不用 Redis、不上云、不发营销文案）
   - 活跃上下文：当前项目、本周目标、已知约束
3. **显式引用**：在 OpenClaw 的 agent 系统提示词里加一句"会话开始时读取 USER.md 并遵守其中所有偏好"。多数框架不会自动加载，不写死引用它就是个死文件。
4. **多角色场景**：用 `user-{role}.md` 分文件，对应角色的 prompt 引用对应文件；也有团队通过 MCP/插件把 USER.md 暴露给外部工具做同步，但核心始终是这份文件本身。

## 踩坑点

- **写成简历**。堆技术名词没有用，"熟悉 K8s" 不能指导 Agent 任何行为。要写成约束："生产环境变更一律先出 diff 给我确认"。
- **过长**。超过 150 行，注意力被稀释，最重要的偏好反被忽略。控制在 80~120 行。
- **不更新**。你换了数据库、改了口味，文件没变，Agent 按旧画像工作。用 git 记录变更，至少每季度审一次。
- **权限边界**。USER.md 本质是"写给模型的指令"，不是密码本，别放 API key 和机密凭证。
- **优先级颠倒**。不少人先写身份后写禁忌，实际上禁忌最影响行为。顺序应为：禁忌 > 偏好 > 环境 > 身份。

## 可复用建议

1. 用五段模板起步，不要从零写，模板已覆盖 80% 场景。
2. 将 USER.md 纳入 git 管理，变更可回溯，换机器也能同步。
3. 每周花五分钟，根据本周真实对话补充一条偏好。这是性价比最高的迭代方式。
4. 项目级 USER.md 覆盖全局级，避免通用偏好与项目约束冲突。
5. 动态信息（本周目标、进行中任务）单独放一节，定期刷新，别和静态偏好混在一起。

## 总结

USER.md 的本质，是把个人上下文的构建从"每次会话重复劳动"变为"维护一份可版本化的文档"。它对 Agent 输出的改善，往往比换更强的模型更直接、更可预期。上下文质量决定 Agent 效果的上限，而这份质量，恰恰是我们自己能控制的。
