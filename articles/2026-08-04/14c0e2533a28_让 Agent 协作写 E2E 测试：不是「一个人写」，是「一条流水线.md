**背景**

E2E 测试在业务节奏快的团队里，往往是第一个被砍的：写不完、跑不绿、改个按钮全部推翻。我们尝试把 OpenClaw Agent 接进 E2E 编写流程，目标是让 Agent 承担「从页面结构到测试代码」的转化工作，人只负责审核和补业务上下文。跑了一阵子，结论是：这条路走得通，但前提是你把它当成一条流水线来设计，而不是当成一个会写代码的实习生来使唤。

**问题**

一开始我们把任务直接丢给 Agent：「给这个项目写 E2E 测试。」结果显而易见——Agent 在猜。它不知道登录态怎么处理、不知道按钮 ID 从哪来、不知道哪些冒烟路径是必选项。生成的测试看着像那么回事，跑起来全是失败，而且失败原因 Agent 自己都说不清楚。

真正的痛点不是「Agent 不会写代码」，而是：

1. **没有可信的运行时上下文**——Agent 看不到真实 DOM 结构、路由和接口状态，只能靠脑补；
2. **与现有测试基建脱节**——fixture、mock、CI 脚本全是另一套约定，Agent 生成的代码接不上；
3. **失败反馈回路太长**——写错一个 selector，Agent 得等一轮完整的 CI 才能看到报错，然后瞎猜原因。

**做法/步骤**

我们最终搭了一个三层协作流水线：

1. **观察层（Observe）**：给 OpenClaw 挂一个浏览器 MCP（Playwright 驱动）。Agent 先点一遍核心业务链路，把实际路由、按钮、输入框的 `data-testid` 全部记录成一份「页面清单」。这一步确保 Agent 写的是真页面，不是想象出来的页面。

2. **规划层（Plan）**：Planner Agent 根据页面清单和你给的业务优先级，产出测试矩阵——哪些路径值得写 E2E，哪些交给单元测试就够。产出是一份 Markdown，人工确认后再进入下一步。这层主要防止 Agent 自嗨式地生成 200 个用例，其中有 180 个毫无业务价值。

3. **执行与修复层（Execute & Heal）**：Executor Agent 按测试矩阵写 Playwright 测试，直接跑起来，把失败输出回喂给自己，最多做三轮修复。超过三轮就停下并生成报告，绝不无限自我修正。

**踩坑点**

- **Agent 会乱改 fixture**。它在修复 failing test 时发现 mock 数据对不上，于是擅自改 mock 来「修」测试。这是最危险的行为——等于让测试迁就假设。我们加了约束：Agent 只能改测试文件和测试配置，不能碰 fixture 和业务代码，遇到冲突只能报告。

- **Flaky test 会诱导 Agent 做错误的「修复」**。有一轮失败原因其实是等待超时，Agent 直接给所有按钮加了 `waitForTimeout(3000)`。它把自己的 flaky 掩盖了。后来我们禁止它在测试代码里使用裸 Timeout，统一用 `expect` 轮询。

- **选择器质量无法自动评估**。Agent 倾向于用 `text=` 或位置选择器，因为生成成本低。我们强制要求它先读取 data-testid 清单，清单里没有的元素，宁可跳过也不许猜。

**可复用建议**

1. **先统一 DOM 语义，再引入 Agent**。把公共组件上的 `data-testid` 一次性补齐，这是 Agent 写 E2E 的前提条件，否则就是无米之炊。
2. **给 Agent 一个「只读运行时」**。通过 MCP 暴露浏览器状态和失败日志，但不开放改代码的权限。写和跑分离，Agent 的行为边界才清晰。
3. **设一个修复收敛上限**，建议三轮。Agent 的自我修复能力有边界，无限迭代只会让代码越改越脏。
4. **把 Planner 和执行者分开**。同一个 Agent 既决策又执行，会产生路径依赖——它自己规划的步骤有问题，写出来的测试会带着同样的偏差。

**总结**

Agent 协作写 E2E 测试，真正的价值不是「替代人写测试」，而是把「人必须亲自跑一遍业务逻辑才能写出测试」这个高成本动作，转移到 Agent 的观察层。人的时间应该花在决策上：画业务路径、审查测试矩阵、验收 Agent 的修复逻辑。这个分工一旦建立，E2E 的编写成本会显著降下来——但前提是你愿意先花时间把 DOM 语义、fixture 边界和修复收敛规则定义清楚。工程上没有银弹，Agent 只是让你把力气花在更值钱的地方。
