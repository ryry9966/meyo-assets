## 背景

OpenClaw 类 Agent 框架依赖 LLM 做意图识别、工具调用和结果归纳。云端 API 稳定，但有三件事绕不开：单次调用延迟受网络影响，按 token 计费在长时运行任务里成本累积明显，对话数据必然经过第三方。

近半年开源模型量化版本——尤其 Qwen2.5 系列和 Llama 3.1——在 7B-14B 量级已能稳定完成结构化输出和基础 function calling。本地部署的定位不是替代云端大模型，而是给 Agent 架构加一个低延迟、零边际成本、可审计的"本地推理通道"。

## 问题

把本地模型接进 Agent，不是把聊天窗口搬到本地。Agent 场景对模型有额外要求：

- 必须兼容 OpenAI 的 /v1/chat/completions 接口，否则要写适配层
- 需要可靠的 tool calling，而不是"偶尔输出一段 JSON"
- 上下文窗口要够用，MCP 工具返回结果动辄几千 token
- 延迟和吞吐要匹配 Agent 的循环调用频率

很多人在 Ollama 里跑通了对话，一接 MCP 就发现工具调用全崩，问题基本都出在上面四点。

## 做法与步骤

以 Ollama 为例：

1. **安装与选型**：安装 Ollama，拉取带工具调用支持的模型。实测 Qwen2.5-7B-Instruct 的 function calling 比同量级 Llama 3.1 更稳定，推荐优先试。
2. **硬件基线**：16GB 内存起步；8GB 显存跑 7B Q4 量化比较顺。纯 CPU 也能跑，约 8-12 token/s，能干活，但别期待流畅交互。
3. **接入 Agent 框架**：把 LLM 供应商配置指向 `http://localhost:11434/v1`。OpenClaw 的 MCP 工具同理，将原来指向外部服务的端点换成本地地址，一行配置即可，Agent 代码零改动。这一步最关键：本地模型对你的意义是替换"推理后端"，而不是重写 Agent。
4. **关键参数调整**：设置 `num_ctx` 为 8192，否则 MCP 返回的长结果被截断，模型会开始编造内容。温度设为 0.1-0.3，Agent 场景要确定性，不要创造力。
5. **降级路由**：让本地模型负责意图分类、内容过滤、日志浓缩等高频低难任务；复杂推理继续走云端。路由逻辑本身做成一个 MCP 工具，向后兼容所有 Agent。

## 踩坑点

- **JSON 输出不稳定**：7B 模型在复杂 schema 下容易丢字段。Ollama 支持 `format: json` 约束，但更稳的做法是让模型输出简短片段，由代码解析和重排。
- **量化等级**：q4 和 q8 在闲聊上差距不大，一遇到多步工具调用就明显退化。显存允许时优先 q8。
- **chat template 不匹配**：手动拼 prompt 而非调用官方 API 库时，容易漏掉 function calling 所需的特殊 token。务必让推理服务使用模型内置 template，不要自己拼。
- **并发冲突**：本地推理没有排队机制，多个 Agent 同时调用会互相挤占。前面加一个简单请求队列，或限制并发上限。
- **显存不足硬上大模型**：14B Q4 需要约 9GB 显存，剩余空间不足时 KV cache 会溢出到 CPU，延迟反而比 7B 更差。

## 可复用建议

- **用真实 Agent 日志做回归测试**，不要用聊天 benchmark 评估。把你的 MCP 工具调用 trace 重放给本地模型，检查输出结构是否完整、字段是否对应工具 schema。
- **建立混合路由**：意图分类、敏感词过滤、日志浓缩走本地；代码生成、长文档推理走云端。这层路由抽成通用配置，任何 Agent 都能复用。
- **量化不是免费午餐**：降级是工程选择。先跑通链路，再根据显存余量逐级上调精度，而不是一步到位追求最大模型。

## 总结

本地 LLM 对 Agent 用户的价值在于：高频小任务延迟降到毫秒级、数据不出内网、长时间运行不怕账单累积。它不是云端的替代品，而是架构里的一个可靠组件——用工程手段管理它的上限和边界，比一句"完全本地化"更有实际生产力意义。
