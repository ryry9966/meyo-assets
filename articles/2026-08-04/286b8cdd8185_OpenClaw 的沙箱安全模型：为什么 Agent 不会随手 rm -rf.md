## 背景

让 Agent 跑自动化，最怕的不是它不够聪明，而是它在某个环节"发挥过度"。社区里最常见的焦虑是：Agent 会不会在某次对话里顺手把项目目录清空？这个担心并非空穴来风——LLM 本身没有"文件系统危险"的概念，真正决定安全边界的，是外层的权限沙箱。

## 问题

Agent 误删文件的本质不是"模型抽风"，而是权限边界太宽。如果你的 Agent 进程可以随意写任意路径，那么一次工具调用参数错误、一次路径拼接失误，都可能造成不可逆的破坏。OpenClaw 的沙箱模型要解决的正是这个问题：让 Agent 有足够自由度完成任务，同时把破坏半径锁死。

## 做法：三层沙箱

OpenClaw 的沙箱大致分三层，理解了这三层，你就能自己判断某个 Agent 配置安不安全。

**第一层：文件系统 scope。** Agent 的默认工作区是一个独立沙箱目录。所有文件操作的路径在解析后必须落在沙箱根目录内，越界访问一律拒绝。相当于给 Agent 发了一张"只在园区内活动"的工牌。

**第二层：工具权限分级。** 读类工具（读取文件、列出目录）默认放开；写类工具需要任务上下文明确启用；销毁类操作（删除、覆盖、批量移动）默认拒绝，需要人为授权。这层把"能看"和"能改"彻底分开。

**第三层：确认与审计。** 即便已授权的写操作，若匹配到高危模式（如删除非空目录、批量覆盖），会触发交互确认。同时所有文件系统操作都写审计日志，事后可以回溯是哪一步、哪个工具、由哪条消息触发。

## 验证方法

空谈安全不如动手测试。建议在测试环境给 Agent 一个明确会越界的指令，比如"把 /etc 下的所有 .conf 文件备份到工作区"。观察它是如何被拒绝的、日志里记录了哪个拦截点。一次实验建立的直觉，比读十篇文档都有用。

## 踩坑点

1. **符号链接逃逸。** 沙箱防的是路径，不防链接。如果你图方便把宿主机目录 `ln -s` 进工作区，Agent 通过软链就能读写宿主机数据——这等于自己把围墙拆了个门。定期检查工作区里的 symlink，尤其来自外部挂载的。
2. **自定义 MCP 工具绕过安全层。** 自己写的 MCP 工具如果直接 spawn 系统命令，那么你代码里的权限就是 Agent 的权限，原生沙箱管不到。自定义工具必须自己实现参数校验和路径白名单。
3. **容器挂载过宽。** 如果用容器部署，别把宿主机根目录挂进去。沙箱是逻辑隔离，挂载是物理暴露，两者是叠加关系，不是替代关系。

## 可复用建议

- **默认最小权限**：沙箱目录只放任务需要的输入文件，输出单独放一个目录。
- **文件操作走框架提供的工具**，避免在自定义工具里直接拼 shell 命令。
- **定期翻审计日志**，关注越界拦截记录——这是白嫖的入侵检测。
- **高危任务前临时提升权限，结束后立刻恢复**，别为了省事保持永久授权。

## 总结

OpenClaw 沙箱的价值不是"阻止 Agent 犯错"，而是把错误的代价从"全盘崩溃"降到"一次可恢复的拒绝"。它不是完美无缺的墙，而是一套可配置、可审计、可验证的边界。真正危险的从来不是 Agent 的意图，而是我们给它划定的权限——花十分钟验证自己的边界，比花一晚上打补丁划算得多。
