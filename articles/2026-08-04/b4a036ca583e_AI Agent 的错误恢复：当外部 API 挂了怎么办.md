Agent 的价值在于把多个外部能力串成一条完整链路，但这也意味着我们把控制权交给了不太可控的下游。LLM 供应商限流、搜索 API 超时、MCP 工具端服务重启——任何一个环节抖动，整条任务链就可能中断。OpenClaw 里挂的 tool 越多，这个风险越大。

**问题**

很多人对 API 故障的处理是"重试三次就放弃"。这在 agent 场景下不够用：

- 策略粗暴：固定间隔重试，高并发下会放大故障，把瞬时抖动变成系统性雪崩。
- 不分类：把 429、5xx、401 一视同仁，永久性错误也在傻重试，浪费时间和 token。
- 无状态：任务执行到一半挂了，恢复后从头再来，中间上下文全丢。

**做法**

1. **给错误分类**。以 MCP 工具调用为例，在错误对象上标注状态码，区分瞬时故障（429 限流、5xx、网络超时）和永久故障（401、403、参数非法）。只有瞬时故障才值得重试。

2. **指数退避加抖动**。基础间隔 1s，每次翻倍，上限 30s，再叠加 0~500ms 随机抖动。SDK 自带的重试默认配置往往偏激进，要显式覆盖。

3. **引入熔断器**。连续 5 次失败将对应 provider 熔断 60 秒，期间直接走备用路径。熔断后定期放少量探测流量，恢复成功再逐步放开。

4. **多 provider 降级**。主用 OpenAI，限流时切到 Anthropic 或本地模型。注意：failover 链里不要接同一家供应商的多个 endpoint，它们往往共享同一套限流配额。

5. **任务检查点**。长任务每完成一个关键步骤，就把对话历史和工具调用结果序列化到本地磁盘或 KV 存储。恢复时从检查点继续，而不是推倒重来。

**踩坑点**

- **重试了非幂等操作**。支付类或"创建订单"接口重试会出重复记录。要么在请求头带 idempotency key，要么这类操作只告警、不自动重试。
- **超时设置不合理**。LLM 流式响应有时 30 秒才吐第一个 token，超时设 5 秒会导致大量误判。
- **降级链共享后端**。以为做了双活，实际两个端点共用上游基础设施，一挂全挂。降级前要确认备用路径的真实隔离度。
- **从没测过故障路径**。只跑 happy path，第一次真实故障就是线上演练，代价很高。

**可复用建议**

- 用 chaos 工具定期注入故障，模拟 API 挂掉，验证降级路径是否真的能走通。
- 把"重试 + 熔断 + 降级"封装成统一的调用中间层，不要散落在各个 tool 里各自实现。
- 日志带上 request_id 和 failover 路由信息，事后复盘才有据可查。

**总结**

外部 API 故障是常态而非异常。Agent 的健壮性不在于"不失败"，而在于失败后能快速识别、优雅降级、无损恢复。把错误处理当成工程基建来做，而不是事后补丁——这套机制不会让 agent 变得更快，但能让它活得更久。
