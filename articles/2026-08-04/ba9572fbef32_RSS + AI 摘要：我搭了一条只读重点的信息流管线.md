先说结论：RSS 没死，只是默认的“标题流”形态跟不上信息密度了。把 AI 摘要插在 RSS 和阅读器之间，你能用每天 10 分钟，完成过去一小时才能做完的扫描工作。

## 背景：订阅太多，等于没订阅

我订阅了大约 120 个源，包括技术博客、券商研报、海外媒体和几个高质量 Newsletter。过去一年里，我发现自己打开阅读器的次数越来越少——不是不想看，是看不过来。几百个未读标题堆在那里，每条标题都要点开才知道值不值得读，这个成本太高。

后来我意识到：**问题不是信息源太多，而是缺一道预处理工序**。我需要一个“信息过滤器”，在到达我眼前之前，先完成去重、摘要和分级。

## 问题：RSS 阅读器的三个痛点

1. **标题无法承载判断信息**：很多优质文章的标题是营销导向的，和内容价值脱节
2. **全文展示效率低**：滚动阅读长文，大部分时间花在无关段落上
3. **跨源主题分散**：没有统一视角，同一个话题在不同源里重复出现，浪费阅读时间

## 做法：三层管线

整套系统分三层：**抓取层 → 摘要层 → 分发层**。全程跑在一个低配 VPS 上，成本约等于一杯咖啡。

### 层 1：RSS 聚合（RSSHub + Miniflux）

我用 RSSHub 补全了那些不提供原生 RSS 的站点（微信公众号、微博、少数派等），再把所有源统一喂给 Miniflux。Miniflux 胜在轻量、有 API、支持过滤规则，适合做管线底座。

### 层 2：AI 摘要（OpenClaw + MCP 定时任务）

这是整条管线的核心。我在 OpenClaw 里配置了一条定时任务：每隔 2 小时调用 Miniflux API，拉取新增条目，然后通过 MCP 接入 LLM 做结构化摘要。

摘要 Prompt 有几个关键约束：

- 输出固定 5 个字段：一句话结论 / 三个关键点 / 相关数据 / 我的判断（可选）
- 限制 150 字以内，避免摘要比原文还长
- 对重复同一事件的跨源文章做聚类，只保留最详实的那篇

### 层 3：分发（Telegram Bot）

摘要结果推送到一个私密 Telegram Channel，带原文链接。我在地铁上扫一眼摘要，只有当下需要深读的才点开原文。这改变了我的阅读模式：从“被动刷标题”变成“主动挑文章”。

## 踩坑点

**1. RSSHub 路由失效是常态。** 我原本依赖某条第三方路由，结果两周后上游改了页面结构。后来把高频源做了本地镜像，低频源失败就自动跳过，不影响主流程。

**2. token 费用是隐性成本。** 一开始我对每条全文都跑一次摘要，一个月下来 token 费用高得离谱。后来加了增量读取和长度截断，只摘要前 2000 字 + 小标题。成本降了 80%，效果几乎不变。

**3. 摘要幻觉在技术类内容上尤其明显。** LLM 经常会把“可能”说成“一定”，或者把作者的推测写成定论。我的对策是在摘要模板里强制加入“原文语气”维度，并用系统提示约束“不确定的信息必须标注”。

**4. 定时任务的时区问题。** Cron 默认 UTC，我有一次观察发现任务总在本地时间下午 4 点跑，以为出 bug 了，其实是时区没配。

## 可复用建议

1. **按频率分桶**：日更源进默认队列，周更源进低优先队列，避免高峰期打爆 API 配额
2. **摘要长度设上限**：80–150 字最佳，超过 200 字人不会看
3. **留全文存档**：摘要只是索引，原文要落库（SQLite 就够了），方便关键词回溯
4. **关键词路由**：命中“安全漏洞、裁员、融资”等词条的直接置顶推送，这类信息时效性最强
5. **控制订阅数**：100 个源是舒适区上限，超过 150 个，摘要管线会因噪音过多而失真

## 总结

这套管线跑下来三个月，我的未读数从 800+ 降到 50 以内，深读率提升明显。真正有价值的不是“AI 摘要”这个噱头，而是**你重新定义了自己和信息的距离**——不是把更多内容推到眼前，而是让更少但更相关的内容抵达大脑。

RSS 的老传统从来不是问题，缺的只是现代人需要的那道“筛选工序”。
