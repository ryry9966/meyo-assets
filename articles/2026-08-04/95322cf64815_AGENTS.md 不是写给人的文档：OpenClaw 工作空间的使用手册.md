如果你在用 OpenClaw 管理多个自动化项目，大概率遇到过这种场景：AI 每次启动时对工作空间一脸茫然，反复读取目录结构、猜测哪些文件可以动、哪些目录是缓存、脚本之间依赖关系是什么。你在 `.env` 里写满了注释，在 README 里详细说明了架构，但 AI 依然我行我素。

问题不在于 AI 笨，而在于你给 AI 的说明书用错了格式。README 是写给协作者看的，`.env` 注释是写给未来的自己看的，而 AGENTS.md 是唯一一个 AI 会真正主动读取、并以此调整行为的文件。

## AGENTS.md 到底是什么

简单说，AGENTS.md 是放在工作空间根目录（或子目录）下的 Markdown 文件，OpenClaw 的 Agent 在进入该目录时会自动加载它，将其内容作为行为约束和上下文参考。它不是一份文档，而是一份运行时配置。

这意味着两件事：

1. 你不需要在每次会话里反复向 AI 解释项目背景；
2. AI 可以基于文件内容自行判断哪些操作允许、哪些操作禁止、哪些路径需要谨慎。

## 我的推荐结构

经过几个项目的实践，我建议 AGENTS.md 保持这样的结构，顺序很重要：

```markdown
# 项目名

## 工作空间地图
- `src/` 源码，可读可写
- `scripts/` 临时脚本，可创建可删除
- `data/` 原始数据，只读，禁止修改
- `output/` 生成结果，可覆盖
    
## 常用操作
- 测试：`npm test`
- Lint：`npm run lint`
- 构建：`npm run build`
- 提交前：必须通过 test + lint

## 禁止事项
- 不修改 `.env` 或任何配置文件中的密钥
- 不删除 `data/` 下任何文件
- 不提交 `output/` 到 git

## 当前任务
（由 Agent 每次会话开始更新，记录最近一次做到哪里）
```

这个结构的核心思路：地图（静态规则）在前，状态（动态信息）在后。AI 需要先知道边界在哪里，再了解当下进行到哪里。

## 三个实际踩坑点

**第一个坑：规则写得太抽象。** 最早的 AGENTS.md 我写的是“不要随意修改数据文件”，结果 AI 把 `data/cache.json` 当成了可以改的缓存。后来我改成“`data/` 下的任何文件不可修改，包括 cache/ 子目录”，问题就消失了。规则必须具体到路径级别。

**第二个坑：把 AGENTS.md 当成 README 来写。** 你用大量篇幅介绍项目背景、技术选型、架构图——这些内容 AI 并不会真正“理解”，只是被当成文本读取，反而稀释了真正的操作规则。AGENTS.md 的价值在于指令性地告诉 AI “做什么、不做什么”，而不是“这个项目是什么”。

**第三个坑：任务状态没有回写机制。** 一开始 AGENTS.md 里写了“当前进度：已完成 xx 模块”，但 AI 不会主动更新它。必须在规则里显式声明：“每次会话结束时，将本次完成的工作和下一步计划更新到 `## 当前任务` 小节，删除过时内容”。这样 AGENTS.md 才能变成一个活文档。

## 一些可复用的建议

- **OpenClaw 插件目录下的 AGENTS.md 要单独写。** 比如你开发了一个 MCP 插件，插件目录里应该有自己的、面向插件维护场景的 AGENTS.md，核心工作空间的 AGENTS.md 不应该包含这些细节。
- **每个子目录可以有自己的 AGENTS.md。** OpenClaw 支持逐级加载规则。如果你项目足够大，在 `scripts/` 下放一个说明“这些是废弃脚本，可以清理”会比在根 AGENTS.md 里强行描述所有子目录更清晰。
- **结合 `.cursorrules` 或 Claude Code 的 `CLAUDE.md` 类比。** 如果你在多工具间切换，AGENTS.md 的定位和它们一致，都是“给 AI 看的说明书”，只是 OpenClaw 的加载机制不同。规则可以互抄，但路径一定要改。

## 最后一点

AGENTS.md 本质上是在做一件事：把隐性知识显性化。你的项目里很多约定从未被写下来——哪些目录是缓存、哪个脚本有副作用、哪些操作不可逆。AI 不知道这些，它只会按照文件系统的外观做出最直接的判断。

花半小时写好 AGENTS.md，省下的是之后无数次“不要动那个文件”的纠正对话。或者换个角度想：这不是在给 AI 写手册，而是在给自己项目的操作边界做一次完整的盘点。这个过程本身就有价值。
