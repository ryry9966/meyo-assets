## 背景

OpenClaw 真正产生价值的地方，不是对话，而是执行。规划得再好，落不了地就是空转。把 OpenClaw 接上外部服务——GitHub、企业 IM、工单系统、内部 API——是让它从"聊得好"变成"干得了"的关键一步。

MCP 把外部能力标准化成工具，OpenClaw 通过 MCP 注册工具后，模型就能在合适的时机调用。但标准化只是起点，工程问题都在握手之后。

## 问题

对接外部服务时，最常见的故障不是模型不会调用，而是：

- **鉴权混乱**：Token 过期、没有 refresh 续期逻辑，Agent 中途断供
- **超时与重试**：LLM 调工具时失败一次就放弃，接口偶发 5xx 被当成最终结果
- **Schema 漂移**：第三方 API 返回字段变化，Agent 还按旧字段做决策
- **安全边界**：Token 直接暴露在模型上下文中，或者混进了日志

这些问题不解决，"能调 API"和"稳定地用 API"是两回事。

## 做法

以对接一个内部工单 API 为例，推荐走 MCP 服务包装：

1. **独立进程部署 MCP server**。不要把鉴权和调用逻辑写死在 OpenClaw 配置里，用一个薄层服务封装第三方 API，暴露给 OpenClaw 调用。

2. **注册工具时明确参数约束**。给模型声明 `workspace_id`、`cursor` 这类字段，尽量用枚举和必填约束，减少自由发挥导致的 400。

3. **统一错误返回结构**。MCP 工具返回结构要固定，例如：

   ```json
   { "ok": true, "data": { ... } }
   { "ok": false, "error_code": "RATE_LIMITED", "retry_after": 13 }
   ```

   让模型看到可行动的错因，而不是一串 stack trace。

4. **接入前做一次"握手验证"**。用一个最小 prompt 强制调用所有工具各一次，确认鉴权、字段映射、超时都正常，再把完整任务交给 Agent。

## 踩坑点

- **重试策略放在 MCP server 侧**，不要指望模型做重试。LLM 看到第一次失败往往会换一种思路，而不是重试同一个调用，反而引入不确定性。
- **Token 不走模型上下文**。用环境变量注入 MCP server 进程，OpenClaw 只感知工具调用，不感知密钥。
- **小心超时叠加**。LLM 推理时间 + MCP 调用时间 + 第三方接口时间，总耗时很容易超网关限制。MCP server 侧对第三方请求要设 10s 内的硬超时，长任务尽快返回"进行中"状态，转成异步查询。
- **留意 JSON 里的非 ASCII 转义**。部分 API 返回 `\uXXXX`，模型容易误解内容，建议在 MCP server 里统一 decode 后再返回。

## 可复用建议

- 建一个 `healthcheck` 工具，随时直接调用，验证整个链路可用性
- 所有外部调用打 structured log，带 request_id 和耗时，方便事后排查
- 每个外部服务独立 MCP server，隔离故障域，一个挂了不影响其他工具
- 先做异步化设计。能返回 job_id 的绝不阻塞等待，减少 Agent 的空转时间

## 总结

OpenClaw 对接外部服务的本质，是把不可靠的第三方世界做一次可靠化封装。模型负责决策，MCP server 负责执行和容错。把鉴权、重试、超时、错误结构这些脏活都挡在工具层，Agent 层才可能稳定。
