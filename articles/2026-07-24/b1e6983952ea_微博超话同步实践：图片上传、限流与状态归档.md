## 背景

在构建内容分发自动化时，将图文同步到微博超话是一个高频需求。我们基于 OpenClaw 的 Agent 与插件机制，实现了一个稳定运行的超话同步工具。这个过程中，图片上传链路、请求限流策略和任务状态归档是三个最大的工程挑战。本文梳理了整个落地过程，重点说明这些模块的取舍与踩坑，给同样用 OpenClaw 做社交平台自动化的同学一个可直接复用的参考。

## 问题拆解

我们面对的核心场景是：上游系统产出帖子（标题+正文+图片），需要自动发布到指定的微博超话，并记录发布状态，避免重复或遗漏。看似简单，实则卡点很多：

1. **图片上传链路**：微博的图片上传并非一次 HTTP POST 就能完成，需要预申请、分阶段携带 Cookie，且不同账号的 cookie 域与有效期差异明显。
2. **严格的限流**：超话发帖接口对同一账号、同一 IP 都有较高的频率限制，误判后容易被静默 ban，必须实现精确的退避与重试。
3. **状态归档**：由于同步是异步任务，必须持久化每条帖子的“待发布/已发布/失败”状态，并在重启后能准确续传，不能重复发送。

下面逐一展开做法与踩坑点。

## 做法与步骤

### 1. 图片上传：从预申请到 multipart

微博图片上传并不是直接 POST 图片二进制就能得到 pid，我们采用的流程如下（基于抓包与部分公开资料验证）：

- **Step 1：获取上传 token**  
  请求 `https://picupload.weibo.com/interface/pic_upload.php?m=upload&app=miniblog&data=1` 这一类的预上传接口，需要携带登录后的 Cookie（`SUB` 等）。返回一个 `upload_id` 和临时上传地址。
- **Step 2：multipart/form-data 上传图片**  
  将本地图片文件拼装成 `multipart/form-data`，字段包括 `Filename`、`UploadID`、`pic1` 等。注意这里的 `Content-Disposition` 要求严格，`name` 和 `filename` 必须与抓包一致。我们选择直接还原移动端的请求头，否则容易被 WAF 拦截。
- **Step 3：获取 pid**  
  上传成功后返回一组图片 id（如 `pid`），这个 pid 就是发微博时引用的图片标识。

在 OpenClaw 中，我们将上述过程封装为一个 `upload_image_to_weibo` 的 Action，使用内置的 HTTP 客户端（`openclaw.http`）完成请求。Cookie 统一从 Secrets 中读取，定期通过模拟登录接口刷新。

**坑点：**
- Cookie 的域必须与上传接口一致，跨域会导致 302 重定向到登录页。
- `multipart` 的 boundary 最好随机生成，不要硬编码。
- 某些账号需要前置请求 `https://passport.weibo.com/sso/login` 保持会话高温，否则会上传失败但不报明显错误。

### 2. 限流策略：令牌桶 + 错误码退避

微博超话发帖接口（如 `statuses/update` 或移动端对应的 mblog 接口）对频率极为敏感。我们观察到几种典型限制：

- 同一账号两次发帖间隔 < 60 秒会被提示“操作太频繁”；
- 一小时内发帖超过 15 条左右会触发较长时间的限制；
- 部分网络出口 IP 可能被黑白名单，与该账号历史行为有关。

应对方案：

- **本地令牌桶**：设置每分钟最多 1 次发帖，每发一次等待令牌恢复。通过 OpenClaw 的 `sleep` 工具引入间歇，避免无意义的快速重试。
- **错误码识别**：当返回的 JSON 中包含 `error_code: 10021`（发帖过于频繁）或 `10022`（内容重复）时，进入退避流程。对于 10021，采用指数退避（2s → 4s → 8s ...）并最高上限 10 分钟；对于 IP 维度的限制，切换代理出口或等待。
- **随机抖动**：在每次发帖前增加 1~5 秒随机延迟，避免形成固定模式。

这些逻辑被写入一个 `rate_limited_post` 函数，通过 OpenClaw 的 Task 调度器反复调用，直至成功或彻底失败。

**坑点：**
- 有些错误码文档缺失，需要根据实际返回的 `msg` 做正则匹配判断。
- 代理切换时需注意 Cookie 与 IP 属地的一致性，否则易触发安全校验。

### 3. 状态归档：轻量 SQLite + 幂等键

为了避免重复发帖，我们为每一条上游帖子生成唯一幂等键（使用上游系统的消息 ID），在 SQLite 中建表：

```sql
CREATE TABLE IF NOT EXISTS sync_status (
    source_id TEXT PRIMARY KEY,
    weibo_mid TEXT,
    status TEXT,  -- pending/success/failed
    attempt_count INT,
    last_error TEXT,
    created_at DATETIME,
    updated_at DATETIME
);
```

每次发帖前先查 `source_id` 如果已经 `success` 则跳过。发帖成功后更新 `weibo_mid` 和 `status`。失败则记录错误信息，后续可通过 OpenClaw 的定时重跑机制再次尝试。

由于可能存在多个 Agent 实例并发查询/更新，我们使用 SQLite 的 WAL 模式并配合文件锁（`fcntl`）来保证并发安全。在 OpenClaw 的插件架构中，状态数据库路径统一通过 Config 管理，方便挂载和备份。

**坑点：**
- `weibo_mid` 并非永远唯一，某些场景下微博会返回临时 mid，需要二次确认，我们通过紧接着的查询接口校验。
- 定时重跑时需设置最大重试次数，防止死循环消耗资源。

## 可复用建议

如果你在 OpenClaw 生态中也需要类似的超话同步能力，建议：

1. **封装成 MCP 工具**：将“图片上传 + 发帖 + 限流”打包为一个 MCP Server，暴露 `weibo_super_topic_post` 工具，让任何 Agent 都能调用，无需关心内部细节。
2. **配置化**：超话 ID、账号 Cookie、频率上限、代理设置等全部通过 OpenClaw 的 Config 体系注入，提高可移植性。
3. **健康监控**：为同步任务增加心跳上报，当连续失败次数超过阈值时主动告警，而不是静默丢弃。
4. **跨平台复用**：图片上传和限流模块抽象成通用层，后续扩展到小红书、知乎等平台时可直接继承。

## 总结

微博超话同步的工程化落地，挑战不在主要功能，而在异常处理的完备性。图片上传的多步状态、限流的动态平衡、归档的幂等设计，这些细节构成了自动化系统的稳定性边界。基于 OpenClaw 的插件体系，我们能将这些能力标准化成可组合的积木，大幅降低后续的维护成本。希望本文的实践能为你构建类似的社交媒体同步工具提供一份真实的参考。
