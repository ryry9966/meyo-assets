## 为什么需要文件访问护栏

当 Agent 开始真正“动手”操作本地文件系统（比如通过 OpenClaw 的 `exec` 动作，或 MCP 工具提供的文件读写能力），安全边界就变得非常现实。一个被恶意提示注入的 Agent，可以轻易地读取 `~/.ssh/id_rsa`、覆盖 `/etc/hosts`、或直接 `rm -rf` 破坏工作目录外的数据。即使没有恶意注入，自动化脚本的 Bug 或 Prompt 的歧义也可能让 Agent 做出意料之外的文件操作。

硬件隔离（容器、虚拟机）是终极解法，但并非所有场景都方便承载。对于很多本地自动化任务，我们实际只需要 Agent 访问一个明确的项目目录——比如 `~/my-automation-project/`。给这类自动化脚本加上一个简单但可靠的**本地目录白名单**，就可以用极低成本拦住大部分文件访问风险。

## 问题拆解：路径校验远不止字符串前缀

初看需求，很多人第一反应是：

```python
if not request_path.startswith("/allowed/root"):
    raise PermissionError
```

这在工程上几乎处处漏风。现实中的路径会以各种形态出现：

- 相对路径：`../../etc/passwd`
- 符号链接：`/allowed/root/link_to_secrets` -> `/home/user/.ssh`
- 不同规范化形式：`/allowed/root/../root/subdir`
- Windows 下的盘符、分隔符、8.3 短名
- 通过挂载点或硬链接实现的间接访问

真正可用的白名单校验，必须在路径解析后的**正则化真实路径**上做判断，并且要考虑文件不存在的场景（此时无法 `realpath`）。

## 一个可复用的路径安全校验实现

下面是一个适用于 Linux/macOS 的 Python 实现，可在 OpenClaw 自定义 action 或 MCP server 工具里直接嵌入。核心思路：

1. 将允许的目录列表全部转为绝对路径并解析符号链接。
2. 对用户请求的目标路径，先构造一个“可能还不存在”的规范化路径（解决 `realpath` 要求文件存在的问题）。
3. 校验规范化后的路径是否处于任一白名单目录下。

```python
import os
from pathlib import Path

class FileAccessGuard:
    def __init__(self, allowed_roots: list[str]):
        # 提前将白名单目录转为解析符号链接后的绝对路径
        self.allowed_real = []
        for root in allowed_roots:
            rp = os.path.realpath(os.path.abspath(root))
            self.allowed_real.append(rp)

    def _resolve_request_path(self, request_path: str) -> str:
        # 先处理为绝对路径，但不要求文件存在
        abs_path = os.path.abspath(request_path)
        # 对于已存在的部分，尽力解析符号链接
        try:
            # 递归解析存在的父目录
            head = abs_path
            while True:
                parent = os.path.dirname(head)
                if os.path.exists(parent):
                    real_parent = os.path.realpath(parent)
                    head = os.path.join(real_parent, os.path.basename(head))
                    break
                head = parent
            return os.path.normpath(head)
        except Exception:
            return os.path.normpath(abs_path)

    def is_allowed(self, request_path: str) -> bool:
        resolved = self._resolve_request_path(request_path)
        for allowed in self.allowed_real:
            # 确保是子路径或完全相等
            if resolved == allowed or resolved.startswith(allowed + os.sep):
                return True
        return False
```

对不存在的路径，`os.path.realpath` 会直接抛出异常，所以 `_resolve_request_path` 尽可能向上一层层找到存在的父目录去解析符号链接，然后拼回剩余部分。这在大多数场景下已经足够健壮。

## 接入 OpenClaw 或自定义脚本

假设你在 OpenClaw 里有一个“读取文件”的自定义 action，只需在真正 `open()` 前插入一行校验：

```python
guard = FileAccessGuard(allowed_roots=["./workspace"])

def read_file_action(args):
    path = args.get("path")
    if not guard.is_allowed(path):
        return {"error": "Access denied: path outside allowed workspace"}
    with open(path, "r") as f:
        return {"content": f.read()}
```

如果白名单目录需要动态配置，可以把 `allowed_roots` 从配置文件中注入。对于 MCP server 开发者，同样的逻辑可以放到每个 tools handler 的入口，也可以直接写成一个装饰器。务必将拒绝访问的事件记录到日志，方便审计和调试。

## 踩坑记录

在实践中这层薄薄的护栏挖出过不少隐藏问题：

**坑1：`os.path.realpath` 要求路径存在**  
这是最常见的翻车点。当 Agent 要写入一个新文件，路径还不存在，`realpath` 直接报错。我的解决方法是上面代码里的“向上查找存在父目录”的技巧。还有一种更保守的做法是仅校验已存在父目录的 `realpath`，然后拼接剩下部分，但要留意符号链接在中间层的影响。

**坑2：符号链接指向白名单外**  
即便请求路径在白名单内，如果它本身是一个指向白名单外的符号链接，直接 `open` 会跟随链接，从而突破白名单。上面的 `_resolve_request_path` 在已有父目录部分解析了符号链接，但如果请求路径的最后一个组件是符号链接且尚未创建，则会漏掉。严格的做法是：在文件操作之前 `lstat` 判断是否符号链接，并拒绝或要求其 `realpath` 也在白名单内。这在自动化脚本中需要权衡：过度苛刻可能影响正常功能（例如项目内使用符号链接组织资源）。建议至少对关键目录（如 `.ssh`、`/etc`）在更高层加强防御。

**坑3：工作目录变更**  
如果你的 Agent 在执行过程中切换了工作目录（`os.chdir`），那么相对路径解析的基础会变化。建议在 `FileAccessGuard` 初始化时传入一个固定的 `base_dir`，所有相对路径解析都基于该目录，而不是依赖全局 `cwd`。

**坑4：Windows 的特殊性**  
路径分隔符、盘符大小写、短名（8.3）都会让简单的字符串前缀匹配失效。如果必须支持 Windows，建议引入 `pathlib.PureWindowsPath` 进行比较，并使用 `os.path.normcase`。不过目前大部分 Agent 框架的重度使用环境仍是 Linux/macOS，可以为 Unix 系统优先实现，Windows 作为扩展项。

## 可复用建议：把护栏做成基础设施

- **集中配置**：把允许目录列表写成环境变量或配置文件，不要散落在每个脚本里。
- **双层防护**：在应用层做路径白名单校验，在基础设施层（如 Docker 的 `-v` 挂载只读、`chroot`）再做一层。多重防护不会多余。
- **测试先行**：写单元测试覆盖符号链接、相对路径、`..` 穿越、大小写变化、不存在的文件等场景。这是最容易写测试的安全组件之一。
- **默认拒绝**：一旦发现路径解析异常，不要默默放行，应当直接拒绝并记录事件。白名单策略的原则永远是“不信任不确定的输入”。

## 总结

文件访问护栏看起来是“简单代码”，但真正工程化落地需要仔细处理文件系统语义。上面这套方案已经在多个本地自动化 Agent 中稳定运行，拦下了数次由不完美 prompt 导致的越权文件访问。把它作为 Agent 项目初始化的一部分，能让你在享受自动化便利的同时，多一重安稳。

如果你已经在用 OpenClaw 编写复杂的自动化流程，建议现在就检查一下：你的文件操作 action 有白名单吗？如果没有，花半小时把护栏加上，值得。
