在 OpenClaw 这类 Agent 编排管线里，我们经常需要让 LLM 输出一段**结构化长文本**——比如总结报告、代码审查、批量提取结果。直觉上很多人会选择 JSON，因为它“标准、可解析、易于机器消费”。但在实际工程中，长文 + JSON 的组合几乎必然引发一场**解析灾难**。

## 背景：Agent 管线的“最后一公里”卡点

典型场景：你写了一个 MCP 工具，它调用 LLM 生成一份包含多个段落、列表、代码片段的周报。下游是一个自动化通知节点，需要把“摘要”“待办事项”“风险点”分别推送到不同频道。你会怎么做？定义 JSON schema，如下：

```json
{
  "summary": "...",
  "actions": [...],
  "risks": "..."
}
```

prompt 里反复强调 “输出纯 JSON，不要带 markdown 代码块，不要添加注释”。模型也答应得很好，甚至示例都完美。但跑到 100 条真实输入时，你会发现 pipeline 会频繁被 `json.decoder.JSONDecodeError` 打断。

## 问题：长文 JSON 为什么这么脆弱？

1. **嵌套结构与转义地狱**  
   长文本中难免出现双引号、反斜杠、换行符。LLM 有时会忘记转义，或者在嵌套对象里混入未转义的 JSON 特殊字符。更隐蔽的是它会在文本里插入看不见的 Unicode 控制字符（如零宽空格）。

2. **尾逗号与注释惯性**  
   模型在很多训练数据里见过 JavaScript/JSON5 风格，会习惯性在数组最后一项后加逗号，或者用 `// 这是一段说明` 添加注释。纯 JSON 解析器对此零容忍。

3. **代码围栏污染**  
   即使 prompt 明确禁止，部分模型仍会输出 ` ```json ... ``` `。你可能在解析前做了 strip 处理，但遇到多段代码围栏、或者内部嵌套反引号时，正则清理就会失败。

4. **输出截断（尤其流式）**  
   长输出在流式返回时极易被截断，得到的 JSON 直接缺少结尾 `}` 或 `]`，连修复的机会都没有。

你可能会尝试各种「防御性解析」：先找最外层花括号、用 `json.loads` 带 `strict=False`、集成 `json5`/`json_repair`，甚至在失败时重试请求。但这些补丁增加了延迟与复杂度，且仍无法覆盖所有边界情况。

## 做法：转向基于标签的结构化格式

在 OpenClaw 社区的 Agent 实践中，一个被反复验证有效的方法是：**放弃 JSON，改用自定义 XML 式标签**。

格式示例：

```
<report>
<summary>
这里是摘要，可以包含任意字符，包括引号"和换行。
只要不包含 </summary> 标签本身。
</summary>
<actions>
- 任务一：升级依赖
- 任务二：review PR #42
</actions>
<risks>
可能存在性能退化，需监控 QPS。
</risks>
</report>
```

只需要让模型在标签内输出内容，解析时用**非贪婪正则**提取即可，完全避开 JSON 的结构性陷阱。

## 步骤：从 prompt 到稳健提取

### 1. 设计简单、无二义的标签名
避免使用常见英文单词（如 `<content>`），以免与正文冲突。推荐加上前缀，如 `<agent_summary>`、`<step_result>`。标签名中不要包含特殊正则元字符。

### 2. 在 prompt 中给出严格约束
清晰的指令可以大幅降低后续处理成本。示例片段（实际 prompt 需根据模型调整）：

```
将输出组织为以下格式，严格按标签划分：

<summary>
在此处写摘要，不要包含标签本身。
</summary>
<actions>
在此处列出待办事项，每行一个，以“- ”开头。
</actions>
...
只输出上述标签结构，不要添加任何额外解释或代码围栏。
```

关键点是**用正向示例**，而非只告诉它“别做什么”。

### 3. 使用非贪婪正则安全提取
Python 解析核心可以很简单：

```python
import re

def extract_tag(text: str, tag: str) -> str | None:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1).strip() if match else None
```

`re.DOTALL` 让 `.` 匹配换行，非贪婪 `*?` 防止跨标签截取。即使模型在标签外多输出了说明文字，正则也能正确捕获目标内容。

### 4. 构建结构化字典
根据业务需要，把提取到的字段拼装成 dict 或 Pydantic model，就可以像处理 JSON 一样传给下游。

## 踩坑点与应对

- **标签嵌套**：如果一段内容里确实需要包含 `<actions>` 字符串本身（例如介绍 HTML），模型可能会意外产生嵌套。可以要求模型对冲突字符做转义，如 `&lt;actions&gt;`，但最好还是选择生僻标签名，从源头避免。
- **大小写不一致**：部分模型会输出 `<Summary>` 或 `</SUMMARY>`。正则匹配时建议设置 `re.IGNORECASE`，或在提取前统一转换为小写。
- **缺失结束标签**：流式场景截断时，`</tag>` 可能丢失。可以补一个“最佳努力”逻辑：如果没有匹配到闭合标签，就提取从 `<tag>` 到文本末尾的内容，并打上截断标记。
- **多个同名标签**：比如多次思考过程出现多个 `<thought>`。可以用 `re.findall` 返回列表，或要求模型只输出一次。
- **标签作为分隔符的自污染**：如果输出内容本身就会包含 `</risks>`，就会截断。一般业务文本很少自然出现这种组合，风险较低。保险方案是让模型输出前扫描并转义，但实践经验中几乎不需要。

## 可复用建议

1. **先尝试标签，而不是 JSON 修复器**  
    我曾在 Agent 管道里加装 `json_repair`，但依然遇到无法修复的截断数据。切换到标签模式后，解析失败率从约 12% 降到了 <1%。

2. **为每种节点定义标签模板**  
    可以做成 YAML/JSON 配置文件，让 Agent 按照模板 schema 自动生成 prompt 和解析逻辑，减少重复代码。

3. **保留原始输出日志**  
    即使解析成功，也把原始 LLM 响应完整保存。当出现提取偏差时，可以回溯分析是 prompt 问题还是模型遵循问题。

4. **将标签提取做成一个独立 MCP 工具**  
    如果你的 OpenClaw 管线上频繁使用标签格式，可以封装为一个“按标签提取内容”工具，作为 LLM 输出的后处理节点，不必在每个脚本里重复写正则。

## 总结

JSON 在数据交换中无可替代，但在 LLM 生成长文本时的脆弱性让我们不得不寻找更适合的“线缆格式”。标签格式**放弃了严格的树状结构与数据类型强制，换取了极高的容错与简洁的解析**，非常契合 Agent 管道里“把模型当成一个不可靠但强大的信息源”这一核心假设。

并不是说要彻底告别 JSON——在短小、嵌套深、需要类型校验的接口契约中，JSON 依然首选。但当你的管道因解析失败反复重试、costs 飙升时，不妨试试回归原始的 `<tag>`。它看起来不那么“现代”，却能在自动化流水线里稳定地跑下去。
