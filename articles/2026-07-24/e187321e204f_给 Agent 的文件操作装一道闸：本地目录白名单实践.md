## 背景

有读者问：我在本机跑 Agent，让它帮我整理下载目录、生成周报草稿，偶尔还要读几个配置模板。给它的工具里直接挂了一个“读写整个家目录”的口子，每次看日志都有点后怕。是不是可以只开放几个特定文件夹？

这其实是本地 Agent 实践里的常见痛点。OpenClaw、MCP 工具链、各种插件式的自动化脚本，大多以“能访问文件系统”为前提。开放权限过大，误操作、prompt 注入、链式调用带来的连带风险都会增加；权限收得太紧，又怕影响正常任务——比如同一份脚本既要在 workspace 下写 markdown，也要从 templates 目录读 Jinja2。

这篇文章给出一个工程化程度足够、又不依赖外部重沙箱的方案：在文件操作函数入口加一层目录白名单防护，只允许读写指定的本地目录树。代码用 Python 实现，可复用，适合嵌入到自定义 MCP server、OpenClaw 工具函或任何跑在本地的 Agent 脚本里。

## 问题

Agent 调用文件系统的入口通常是封装过的工具函数，比如 `read_file(path)`、`write_file(path, content)`、`list_directory(path)`。如果不加校验，传入 `../../.ssh/id_rsa` 或跟随符号链接逃逸到白名单外都是可能的。常见实现常见坑：

- 只做简单前缀匹配，没解析 `..` 和符号链接
- 在路径拼接后才检查，给了相对路径可乘之机
- 未处理大小写不敏感的文件系统（macOS 默认就是）
- 允许多个工具间路径不一致，比如一个工具拒绝，另一个工具因实现疏忽放行

我们需要的是一个可靠的“是否在允许目录内”的判断函数，且能在不同操作系统上行为一致。

## 实现与步骤

核心思路：对所有上游传入的路径，先规范化解析为绝对路径，再检查解析后的路径是否以某个白名单目录为前缀。对于写操作还可以额外限制必须落在某个可写白名单内。

```python
import os
from pathlib import Path

class FileAccessGuard:
    def __init__(self, allowed_read: list[Path], allowed_write: list[Path] = None):
        # 统一为已解析的绝对路径
        self._read_roots = [p.resolve(strict=True) for p in allowed_read]
        self._write_roots = [p.resolve(strict=True) for p in (allowed_write or allowed_read)]

    def _resolve_check(self, path: str | Path, roots: list[Path]) -> Path:
        # 1. 将用户路径拼到安全基础路径，再 resolve
        #    防止 '~' 或相对路径逃逸。这里与操作系统当前工作目录无关。
        given = Path(path).expanduser()
        if not given.is_absolute():
            # 不允许纯相对路径，强制基于一个安全 root 拼接，再解析
            raise ValueError("相对路径必须显式拼接，不能依赖 CWD")
        resolved = given.resolve(strict=False)
        # 2. 前缀检查
        for root in roots:
            try:
                resolved.relative_to(root)
                return resolved
            except ValueError:
                continue
        raise PermissionError(f"路径 {path} 不在允许的目录内")

    def guard_read(self, path: str) -> Path:
        return self._resolve_check(path, self._read_roots)

    def guard_write(self, path: str) -> Path:
        return self._resolve_check(path, self._write_roots)
```

在工具函数端集成时会是这样：

```python
guard = FileAccessGuard(allowed_read=[Path.home() / "workspace", Path("/opt/templates")])

def tool_read_file(filepath: str) -> str:
    safe = guard.guard_read(filepath)
    return safe.read_text()

def tool_write_file(filepath: str, content: str) -> None:
    safe = guard.guard_write(filepath)
    safe.write_text(content)
```

如果你的 Agent 工具使用了多个不同函数（比如 `os.listdir`、`shutil.copy`），建议统一通过一个 `_safe_path` 转换入口，避免重复实现校验逻辑。

## 踩坑点

1. **符号链接逃逸**  
   `Path.resolve()` 会跟随符号链接，解析到真实的物理路径。如果你的白名单目录内部允许符号链接指向外部，那么即使真实路径在外部，也会被拒绝。这是符合安全预期的。但需要注意：如果你的工作流依赖白名单目录内的链接（比如 `latest -> /data/v2`），你需要显式把目标目录加入白名单，或关闭 resolve（用 `realpath` 不行就用 `lstat` 单独处理，但复杂度大增）。

2. **macOS 的大小写不敏感**  
   在一些卷上 `Path.relative_to` 是大小写敏感的，但文件系统访问时不敏感。攻击者可能通过大小写变化绕过前缀检查。解决方案：在 macOS 上可以额外做 `str.lower()` 对比。更彻底的是在检查后尝试访问并获取真实路径（`resolved` 已经拿到真实大小写），但这也依赖系统调用。简单场景加一层 `path.lower()` 即可挡住多数误操作，但不足以抗恶意利用。

3. **相对路径与 CWD 依赖性**  
   上述实现直接拒绝相对路径，要求调用方显式拼接安全基路径。例如允许用户输入 `reports/week1.md` 时，工具函数应构造 `guard.guard_read(os.path.join(base_dir, user_path))`，而不是靠 `os.getcwd()`。Agent 运行时 CWD 可能被其他调用修改，导致窗口。

4. **多线程/多进程下的竞态**  
   如果 Agent 内多个工具同时修改文件系统（创建目录、移动文件），在检查与使用之间可能发生 TOCTOU 问题。仅靠路径检查不能完全防御，但对于常规自动化任务风险较低。若需要强安全，考虑操作系统级沙箱（seccomp、AppArmor）。

## 可复用建议

- **拆分读/写白名单**：很多任务只需要读取模板，应禁止写操作。
- **记录审计日志**：在 guard 解析成功时打印 `resolved` 路径，方便回溯 Agent 到底读了什么文件。
- **统一入口**：如果你用 MCP 服务器，把所有文件相关的 tool handler 都走同一个 `safe_path` 函数，避免漏掉某个函数。
- **结合容器或 sandbox-exec**：在 macOS 下可以直接用 `sandbox-exec` 配置只读、读写范围，作为第二道防线。本文的 guard 更像是应用层软防护，适合快速迭代时防止意外，不能替代强隔离。

## 总结

本地 Agent 的文件访问护栏没必要一上来就上虚拟机或内核级隔离。一个仔细实现的白名单路径检查器，能消除绝大多数“不小心碰到敏感文件”的风险。核心是做好路径规范化、明确拒绝未解析的相对路径、理解符号链接和跨平台差异。在大部分自动化脚本场景中，这一层就足够让开发者安心睡觉，同时保持工具链的轻量和可调试性。
