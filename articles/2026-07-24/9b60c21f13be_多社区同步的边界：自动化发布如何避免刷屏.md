## 为什么需要控制同步边界

同时维护 GitHub Discussions、Discord 频道、微信机器人和飞书文档的人，迟早会面对一个现实问题：一条更新到底该推到多少个地方？在 OpenClaw 这类 Agent 项目里，常见做法是用 MCP 插件串联通知渠道，一旦有新版本或新文档，就一键同步。初看上去效率拉满，可副作用很快就来——同一段内容在不同社区重复出现，时间线上全是自己的头像，轻则被群友调侃“刷屏机器人”，重则触发平台风控甚至被举报。

工程师思维很容易把“同步”抽象成一次广播，但社区并不是消息队列。每个渠道有自己的阅读节奏、折叠机制和社交规范。Discord 里可接受频道内相对高频的通知，而微信技术群如果连续三条都是同质公告，管理员大概率会私聊提醒。问题的本质并非“能不能自动发”，而是你是不是把同一份 payload 不加裁剪地扔给了所有 Consumer。

## 提炼一个最小化发布策略

先明确一条原则：**一条核心更新，只在一个主阵地首发，其他渠道做差异化的二次分发。** 我们团队在 OpenClaw 相关插件维护中沉淀出一套规则，核心步骤是这样的：

1. **标记内容类型**  
   把要发布的内容分为三类：  
   - A 类：版本发布、安全补丁、重大功能上线。  
   - B 类：例程、教程、踩坑记录。  
   - C 类：讨论性话题、RFC、社区征集。

2. **确定主阵地**  
   - A 类以 GitHub Releases 和项目官方文档站为主，Discord 的 `#announcements` 发布一条摘要并附上链接。  
   - B 类主发社区论坛（或 Discussions），再由插件生成一个简短的知识卡推送到微信群，内容不超过 200 字，且带一个 `[阅读全文]` 标记。  
   - C 类仅在即时聊天渠道（Discord/微信群）发起，其他静态平台不同步。

3. **设置内容裁剪层**  
   在 Agent 的任务流中加入一个“格式化器”（Format Adapter），根据目标渠道生成不同的 payload。例如针对 Discord 使用 `**标题**`+GitHub 链接的形式，微信群则转成纯文本+艾特特定角色，飞书文档直接更新一个“更新日志”页面而非群发消息。

4. **添加冷却与聚合**  
   在调度节点（比如 MCP 触发动作）中定义冷却窗口：同一个触发源 30 分钟内不重复向同一群组发送消息。如果短时间内需要同步多条 B 类内容，改为汇总成一条“本周更新”的聚合消息，只在周五推送一次。

这个策略落地后，你就不必纠结“这条该不该发”，规则替你做了权衡。

## 具体实现：MCP 动作链的改造

我在 OpenClaw 的本地调度里挂了一个自定义 MCP 插件，大致流程如下：

```yaml
trigger: on_release_published
actions:
  - name: content_classifier
    type: script
    script: classify_release.py   # 返回 A/B/C
  - name: format_router
    type: switch
    cases:
      type_A:
        - discord_announce
        - zhihu_column
      type_B:
        - aggregator
        - wechat_knowledge_card
      type_C:
        - discord_thread
        - wechat_group_poll
```

这里有几个值得注意的坑：

- **Discord 消息长度限制**：embed 的 description 字段限制 4096 字符，releases body 一不小心就超。需要做一个 trimmer，截断后用 `...` 加原文链接收尾。
- **微信群机器人的频率控制**：企业微信机器人的 webhook 有 20 条/分钟的限制，连续推送极易被丢弃。实现了一个本地队列 + 延时发送，最小间隔 3 秒。
- **同一个内容的“伪装”**：避免不同渠道的内容被判定为完全相同文本，可以在每条末尾加上渠道标记（例如 `via Discord`），但这在微信里显得多余。折中方案是为每个渠道生成不同的摘要角度，Discord 强调功能，微信强调场景和收益。

## 踩坑记录

**GitHub Actions 触发循环**  
曾经在 Releases 事件上挂了自动发公告的 Action，公告里又引用了新的 Discussion，Discussion 又被 Watching Bot 检测到变成二次触发。解决方法是在 Action 的第一步检查 `github.event.release.prerelease`，并且强制要求只有手动 review 通过的分支才触发广播链。

**多语言社区的重复感**  
如果中外社区都要覆盖，绝对不要直接机器翻译中英版本分别发送。英文版的受众在 Discord，中文在微信群，消息角度要重新组织。英文侧倾向于技术细节和迁移指南，中文侧更关心“对你有什么用、要不要升级”。

**不要低估“@所有人”的厌恶度**  
无论在哪个社区，除非是严重安全漏洞，否则不要使用全局提醒。消息末尾加上“不想看这类更新可以回复 mute”是一个低成本的情绪缓冲，维持通知权限的透明感。

## 可复用的工程建议

- 把 **同步策略写成一份 markdown 并放在项目 docs/ 里**，方便新贡献者理解发布规则，而不是藏在某个 bot 的配置文件中。
- 为 Agent 的发布链预留一个 **dry-run 模式**：实际发消息前先输出到本地日志或一个测试频道，确认没问题再 release。
- **保留人工干预入口**：有些 A 类内容也需要人工判断是否需要在微信群里推送，可以在 Actions 中设置一个 `manual_approval` 环境，只有负责人点击后才执行微信分发。

## 总结

自动化发布解决的是“从 0 到 1”的触达，但多社区同步的边界问题要求你做“从 1 到 0.6”的克制。好的同步不是更多人看到，而是对的人在对的地方看到对的东西。用内容分类、渠道适配、冷却聚合这套组合，你能在不打扰社区的前提下，维持关键信息的有效流动。或许比技术选型更重要的，是承认群聊里的耐心是一种稀缺资源，任何自动化都不应该过度消费它。
