## 背景

在运营自动化场景中，将内容定时同步到微博超话是一个常见需求。相比普通博文，超话发帖需要显式关联话题、更严格地处理图片上传，且容易触发平台限流。过去手动维护不仅效率低，状态也难以追溯。我们希望基于 OpenClaw 的 Agent 体系构建一条可靠同步链路，使其能够在无人值守的情况下，完成“上传图片 → 组装帖子 → 发布到超话 → 归档状态”的全流程，并对限流、失败做工程化处理。

## 问题分解

实际落地时面临三个核心问题：

1. **图片上传**：微博开放平台要求先通过 `multipart/form-data` 上传图片，获取 `pic_id`，才能在发博时引用。如果直接使用简单 HTTP 节点容易忽略签名与 Content-Type 细节。
2. **限流应对**：接口存在 IP/用户维度频率限制，超话发帖还有独立配额。盲目重试可能加剧封禁，需要退避与状态暂存。
3. **状态归档**：每次发布结果（成功/失败/被限流/敏感词拒绝等）必须记录，方便回溯和补偿。并发场景下需保证记录不丢失、不覆盖。

## 做法与步骤

整体方案以 OpenClaw 工作流编排为主，结合自定义脚本节点处理签名和状态持久化。流程如下：

### 1. 凭证与配置管理

使用 OpenClaw 的环境变量存储微博应用的 `App Key`、`App Secret`、`Access Token` 和 `Access Secret`（OAuth1.0a 的四元组）。超话的 `topic_id` 与文案模板通过工作流变量传入，便于复用。

### 2. 图片上传

图片上传采用微博 API `statuses/upload`。由于接口要求 OAuth1.0 签名并附带图片二进制，在 OpenClaw 原生 HTTP 节点无法直接生成签名，我们封装了一个轻量脚本节点：

- 接收图片本地路径或 URL（如先通过内置下载节点拉取远程图片到 `/tmp`）；
- 使用 `crypto` 和 `request` 库完成 HMAC-SHA1 签名字符串拼接（包含 `oauth_consumer_key`、`oauth_nonce`、`oauth_signature_method`、`oauth_timestamp`、`oauth_token`、`oauth_version` 以及请求参数）；
- 以 `multipart/form-data` 形式提交图片字节流；
- 解析响应，返回 `pic_id` 字符串。

脚本节点输出 `pic_id` 供后续节点使用。注意保存完整的请求/响应日志，以便排查签名错误。

### 3. 发布超话博文

调用 `statuses/update`，传入 `status`（文本）、`pic_id`（图片，可选）、`topic_id`（超话 ID，作为参数附加）等。文本中通过 `#话题名#` 占位，微博会自动识别超话关系，但提前传入 `topic_id` 能提高归属稳定性。同样需要脚本节点生成签名，并将所有参数编码为 `application/x-www-form-urlencoded` 格式。

该节点设置**条件分支**：根据响应码判断结果。

- `200`：发布成功，将 `id`（微博 ID）、`created_at` 等写入输出。
- `10022` 或 `10023`（频率限制）：触发限流处理分支。
- 其他错误码：记录并终止，或进入人工处理队列。

### 4. 限流处理

当遇到频率限制时，错误响应中通常包含 `error_code` 和 `request` 标记，有时也会在 Header 附带 `X-RateLimit-Remaining`。我们的策略：

- 捕获限流码，解析剩余时间（若接口提供了 `retry_after` 则按指示等待；否则默认退避 5 分钟）。
- 将当前任务（图片、文本、超话 ID）序列化为 JSON，推入一个**延迟队列**。
- 工作流中设置一个定时触发器，每 10 分钟从延迟队列消费任务，检查冷却时间后重试。
- 重试上限设置为 3 次，超过则归档为“永久失败”并通知。

队列实现可基于本地 SQLite + 文件锁，或依赖 OpenClaw 内置的持久化状态（如 `$state`）。简单场景下，使用文件作为队列，每个任务独立 `.json`，通过文件名标注重试次数和处理时间戳。

### 5. 状态归档

每次发布完毕后，无论成功与否，都要记录结构化日志。我们定义了统一的归档对象：

```json
{
  "timestamp": "2025-03-15T10:00:00Z",
  "weibo_id": "4921387654321092",
  "content_hash": "aef34...",
  "topic_id": "100808...",
  "image_pic_id": "bcd12...",
  "status": "success",
  "retry_count": 0,
  "error_code": null,
  "error_msg": null
}
```

归档写入使用追加模式（如 JSONL 文件），避免并发竞争。加上文件锁确保原子写入。同步结束后，可定期将归档同步到外部数据库或通知渠道，实现可视化。

## 踩坑点

- **OAuth1.0 签名中的参数排序与编码**：签名基底必须按字典序拼接、参数需 RFC 3986 编码。图片上传时，参数 `pic` 不参与签名，但其他 query string 如 `status` 即使在 POST body 中也需体现在签名中。很多失败源于编码不严格导致签名验证失败。
- **超话话题 ID 的隐性依赖**：微博对超话发帖有独立的侧边权限，若应用未申请超话相关 Scope，即使普通发博成功，超话发帖也可能返回“无权限”错误。需确认应用中已开启“超话社区”权限。
- **图片格式与大小**：透明通道的 PNG 可能导致压缩失败，建议提前用 OpenClaw 图片处理插件统一转为 JPG（<5MB）。图片宽度最好大于 500px，否则展示异常。
- **不要用纯文本 #话题# 模拟**：部分场景只加双井号能成功，但 API 发帖时可能被识别为舆情内容而丢失超话归属，务必携带 `topic_id` 参数。

## 可复用建议

1. **将签名与上传封装为可复用的 OpenClaw 工具节点**：可以发布为内部 MCP 服务器（`weibo-uploader`），提供 `upload_image`、`post_to_topic` 等 Tool，多个工作流直接调用，避免重复造轮子。
2. **构建通用限流补偿器**：抽象一个“延迟重试”通用工作流，接受任务 JSON 和最大重试次数，可复用于微博、抖音等其他平台同步。
3. **归档标准化**：统一所有社交平台发帖的归档结构，便于后续做跨平台曝光分析；归档文件定期轮转，并接入 OpenClaw 的监控告警。
4. **本地测试优先**：微博开放平台提供沙箱环境，先在沙箱验证签名和接口，再切生产 token，可减少无效重试。

## 总结

微博超话同步的核心难点在于图片上传的签名细节、限流退避策略和持久化归档。利用 OpenClaw 的脚本灵活性、工作流条件分支和状态管理能力，可以搭建出一条稳健的全自动化管线，既减少人工介入，也让每次发布有据可查。建议把整个流程抽象为一组可复用的工具或 MCP 服务，在其他内容同步项目中快速部署。
