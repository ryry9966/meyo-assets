## 背景

当一条自动发帖流水线跑起来之后，很快就会遇到一个工程问题：Agent/ MCP 产出的文章和配图应该怎么落盘保存？如果不做归档，日志和调试只能靠运行时的上下文，出一版细微异常的生成结果几乎无法精确回溯。如果归档结构混乱，复现问题就像在没有 commit 历史的仓库里找人名一样痛苦。

OpenClaw 社区里不少用户的流水线已经接入了 MCP 工具和 Agent 调度，但“本地归档”这个环节往往是最后才被补上的——甚至一直没有。这篇帖子会给出一个工程化、可复用的归档实现思路，核心围绕三个产物：**文章（Markdown）、图片文件、以及一份 assets.json 清单**。

## 问题拆解

一个典型的自动发帖流水线大致流程是：Agent 根据话题生成正文 → 调用绘图工具/ API 生成配图 → 组装发布。落到本地归档时，常见痛点包括：

- 文件和元数据分散在不同目录，找不到对应关系
- 同一主题多次生成时文件名冲突
- 文章中图片引用路径是外链或绝对路径，归档后无法本地预览
- 缺少生成参数记录（模型、提示词、温度等），事后没法复现

如果每次发帖后能自动生成一个自包含的归档单元，以上问题就迎刃而解。

## 归档结构定义

推荐采用以 `task_id` 或时间戳命名的目录作为归档单元，目录内结构固定：

```
archive/
└── 20250321-153045-3f2a/
    ├── article.md
    ├── images/
    │   ├── cover.png
    │   └── illustration_01.png
    └── assets.json
```

- **article.md**：最终版正文，所有图片引用使用相对路径 `./images/xxx.png`，方便本地 Markdown 阅读器直接渲染。
- **images/**：存放所有配图，文件名使用内容哈希或 uuid 避免冲突。
- **assets.json**：本次生成的全部元数据。

`assets.json` 最小可行结构如下：

```json
{
  "task_id": "20250321-153045-3f2a",
  "created_at": "2025-03-21T15:30:45Z",
  "pipeline": "tech-news-daily",
  "article": {
    "file": "article.md",
    "title": "xxx",
    "word_count": 850,
    "language": "zh-CN"
  },
  "images": [
    {
      "file": "images/cover.png",
      "prompt": "...",
      "provider": "dall-e-3",
      "size": "1024x1024"
    }
  ],
  "generation": {
    "model": "gpt-4o",
    "temperature": 0.7,
    "system_prompt_hash": "abc123"
  }
}
```

加入 `generation` 字段是性价比极高的选择——未来想复现某次效果时可以直接拿到当时的提示词哈希和模型参数，而不是去翻聊天记录。

## 在流水线中集成归档

流水线中 Agent 通常已经产出了三种数据：Markdown 字符串、图片的本地临时路径或 URL、以及生成配置。我们只需要在“发布”步骤之前或之后插入一个归档步骤。

如果使用 OpenClaw 的 Agent 框架，可以简单封装一个归档 MCP 工具，工具接口示意：

```
tool archive_content(
  article_md: string,
  images: { local_path: string, metadata: object }[],
  metadata: object,
  base_dir: string
) -> { archive_path: string }
```

工具内部执行以下逻辑：

1. 生成 `task_id`（结合时间戳和短 UUID）
2. 创建 `base_dir/task_id/images/` 目录
3. 将 Markdown 内容中的外链图片 URL 替换为本地相对路径（如果 Agent 之前未处理）
4. 将图片文件拷贝/移动到 `images/` 下，统一命名为 `img_01.png` 等，或保留原始名
5. 写入 `article.md`
6. 组装元数据并写入 `assets.json`（使用原子写：先写临时文件再 rename）
7. 返回归档路径供后续步骤引用

Agent 在流程中只需在生成完文章和图片后，调用一次该工具即可完成归档。对于非 OpenClaw 的自动化场景，上述逻辑完全可以用一个几十行的 Python/Node 脚本实现。

## 踩坑记录

**图片文件名冲突**  
哪怕用时间戳命名，高并发下仍可能碰撞。直接用内容的 SHA-256 前 8 位作为文件名更稳妥，既去重又防冲突。工具内部拷贝文件时检测重名，若已存在则跳过或加序号。

**文章中的图片路径漂移**  
Agent 输出 Markdown 时可能直接填入临时本地路径（如 `/tmp/abc.png`）或外链。归档工具必须先做路径标准化：如果是本地临时文件，拷贝到归档 `images/` 并改写为 `./images/xxx.png`；如果是外链，可选择下载到归档目录（注意异常处理和超时），然后替换路径。

**多次生成同一内容导致归档膨胀**  
如果不加控制，每次重试都产生完整归档，磁盘占用会快速增长。建议在工具层增加“覆盖写入”或“仅保留最近 N 次”的策略，或者将归档与发布状态绑定：只有真正发布成功的才归档。

**assets.json 写入不完整**  
直接写 JSON 可能因进程崩溃导致文件损坏。原子写三步走：写入临时文件 → fsync → rename。

**Windows 路径兼容**  
如果归档目录可能在 Windows 上使用，路径分隔符统一用 `/`，避免反斜杠问题。

## 可复用建议

1. **封装为独立服务或 MCP 工具**  
   即便目前只有一个流水线用到归档，也值得把它抽成可配置的工具，方便后续所有 Agent 调用。输入参数包括归档根目录、命名规则、是否下载外链图片、是否保留历史版本等。

2. **与版本控制结合**  
   归档目录直接初始化为一个 Git 仓库，每次生成后自动 commit，写上 task_id 和标题作为 commit message。这样连回溯生成历史都省了。

3. **提供校验脚本**  
   另一个容易被忽略的点：事后需要验证归档完整性。写一个脚本检查每个归档目录是否包含必需的三项内容，并且 `assets.json` 中记录的图片文件都在 `images/` 下真实存在。可以定期跑一遍，防止因清理磁盘导致的不一致。

4. **模板化 assets.json 的 schema**  
   不要每次都拼 JSON 字段，定义一个 TypeScript 接口或 JSON Schema，生成时用库做校验，不然半年后你会发现同一个字段有时叫 `provider`，有时叫 `model_name`。

## 总结

对自动发帖流水线来说，本地归档不是一个炫技的功能，而是长期维护和问题复现的基础设施。把文章、图片和一份结构清晰的 `assets.json` 打包成一个自包含目录，成本很低，收益却很大——你可以随时回到某个时间点看当时的生成结果，可以对比不同参数下的输出，也可以在迁移存储时不丢失任何关联信息。

如果你的流水线里还没有这一环，不妨先用一个脚本最小实现跑起来，然后再考虑封装成 MCP 工具。工程味的东西，永远先求有，再求优雅。
