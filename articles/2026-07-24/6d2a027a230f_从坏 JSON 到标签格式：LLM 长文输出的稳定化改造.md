## 背景
在基于 OpenClaw 搭建的 Agent 与 MCP 工具链里，常需要让大模型生成结构化长文——比如多章节报告、分步骤操作指引、文档拆分块，然后交给下游插件或自动化流程继续处理。早期我们习惯用 JSON：约定 `{"summary": "...", "steps": ["..."]}` 格式，以为模型输出天然可解析，现实却频频打脸。长文场景下，模型产出的“JSON”往往体无完肤，动辄导致整个流水线断裂。本文复盘从坏 JSON 迁移到自定义标签格式的过程，给面向稳定性设计的工程实践提供一个低依赖、高容错的替代方案。

## 问题：为什么长文 JSON 这么容易坏？
模型生成 JSON 时，下面几类问题反复出现，且文本越长越严重：
- **字符逃逸混乱**：内容中偶尔出现的双引号、反斜杠未经转义，导致解析器直接报错；
- **结构性错误**：多一段落时，模型容易多打一个逗号、漏掉闭合括号，或者把数组写成对象；
- **注意力稀释**：提示要求严格输出 JSON，但模型一旦进入长文创作，上下文窗口中的格式约束会变弱，尤其当要生成大段自然语言夹杂代码时，格式控制几乎失效；
- **修复成本高**：经典的“检查 JSON 是否合法，不合法就丢回模型修”循环，既拉高延迟又烧 token，在自动化生产环境里完全不可接受。

在多次被凌晨告警吵醒后，团队决定放弃在长文输出上强求 JSON 原生合法性，转而采用**自定义标签格式**作为契约。

## 做法：把结构化需求“写”在标签里
方案思路朴素：用类似 XML 或 markdown 定界符的标签代替 JSON 的括号体系。例如，需要模型输出三个部分（主题、摘要、正文），就定义：

```
<TOPIC>...</TOPIC>
<SUMMARY>...</SUMMARY>
<BODY>...</BODY>
```

要求模型严格按照这个模板输出，但不要求内部字符转义。下游解析时，通过正则或简易状态机抓取不同标签之间的内容。

### 步骤拆解
1. **设计唯一标签**  
   为防止与正文内容冲突，标签名加一段随机短码作前缀，例如 `__LLMOUT_TOPIC__`、`__LLMOUT_SUMMARY__`。可使用 `uuid4().hex[:8]` 并在每次会话动态注入到提示词里，既能提高唯一性，也不依赖特定词汇。

2. **改造提示词**  
   在 system prompt 或 user prompt 末尾给出清晰格式示例：
   ```
   请严格按以下格式输出，标签大小写和顺序勿改动：

   __LLMOUT_TOPIC__
   （在此填写主题）
   __LLMOUT_SUMMARY__
   （在此填写摘要）
   __LLMOUT_BODY__
   （在此填写正文，可包含多段，可含代码块）
   ```
   如果模型默认支持 xml 格式，可进一步说明“行为类似 XML，但内容无需转义”。

3. **解析端实现（Python 示例）**  
   ```python
   import re
   from typing import Dict, Optional

   def extract_tagged_sections(text: str, tag: str) -> Optional[str]:
       """提取两个同名标签之间的内容（非贪婪，忽略大小写）"""
       pattern = rf"<{tag}>\s*?(.*?)\s*?</{tag}>"
       match = re.search(pattern, text, re.DOTALL | re.IGNORECASE)
       return match.group(1).strip() if match else None

   def parse_llm_output(text: str, prefix: str = "__LLMOUT_") -> Dict[str, str]:
       sections = {}
       for tag_base in ["TOPIC", "SUMMARY", "BODY"]:
           full_tag = prefix + tag_base
           sections[tag_base.lower()] = extract_tagged_sections(text, full_tag) or ""
       return sections
   ```
   实际部署建议将两个标签的闭合情况做容错：如果缺失闭合标签，则取本标签之后、下一个标签出现之前的内容，保证不把全部正文丢掉。

4. **整合到 OpenClaw/MCP 流程**  
   将上述解析函数封装为一个 MCP 工具节点或 Agent 自带的后处理 step。大模型输出后，先尝试 JSON 解析；若失败则走标签提取逻辑，最后返回字典。对于必须获得完整结构的任务，可再加一层轻量校验（如检查必填标签是否为空）。

## 踩坑点
- **标签内容里再次出现“类标签”字符串**  
  即便加了前缀，少数时候模型会把标签名无意间生成在正文里（尤其是描述代码时）。**解法**：进一步提高唯一性，如将分隔符改为 `##==[OUTPUT TOPIC START]==##` 这种不太可能自然出现的模式，并确保 prompt 里要求模型不要重复输出分隔符本身。

- **标签顺序不确定**  
  如果对顺序依赖较强，可把标签设计成主动关闭的 `<SECTION name="topic">`，然后在解析时按顺序收集。但复杂度增加后，模型出错率又会升高。**建议**：尽量让每个标签独立，无顺序要求；如果必须维持顺序，就用数字序号强制标注。

- **长文本跨越多标签导致误截断**  
  正则默认贪婪，使用非贪婪 `.*?` 并加 `re.DOTALL` 可解决多数情况。但若模型漏写一个标签，后续提取会移位。此时采用“取到下一个开始标签”的过渡策略来兜底，能在部分缺失时保住部分结构。

- **多层级结构的局限**  
  标签方案适合扁平或至多两级的信息，嵌套三层以上时，编写可靠解析器的工作量已与实现一个简版 XML 解析相当，不值得。此时可考虑降级为使用 Markdown 标题（`#`、`##`）拆分，再在各区块内应用标签提取。

## 可复用建议
1. **优先使用“每次动态生成的唯一分隔符”**  
   避免固定标签名造成的冲突，这在高频调用或开放域内容中尤为重要。
2. **保留 JSON 解析作为首选，失败后回退标签**  
   短文本、简单结构仍用 JSON，只有长文或历史解析失败次数超过阈值时才自动切换标签模式——这种自适应策略兼顾了效率和可靠性。
3. **对标签内容做最小化后处理**  
   提取后简单 `strip()` 或去掉首尾多余换行即可，不要过度“清洗”破坏原始文本的完整性。
4. **把标签模板写进 versioned prompt**  
   格式定义随同 prompt 版本管理，避免模型行为随微调变化导致格式漂移。
5. **专门构建异常输出集进行测试**  
   刻意构造缺闭合标签、标签名拼错、内容包含干扰串等样本来验证解析器的鲁棒性，这是上线前的必要步骤。

## 总结
从坏 JSON 切换到标签格式，本质是承认长文生成场景下“完全符合语法规范”是一个过强的假设，转而采用一种更宽松、但人能轻易读取且机器能可靠分割的约定。在 OpenClaw 的自动化流程中，这一改动让因格式错误导致的 pipeline 中断降低了 90% 以上，同时不必引入复杂的修复循环。如果你的 MCP 工具还在被长文 JSON 折磨，不妨尝试把契约从大括号换成自定义标签，把稳健性握在自己手里。
