## 背景

微博超话仍然是不少垂直领域运营或小圈子信息分发的有效渠道。我们曾经用 OpenClaw 搭了一条轻量流水线，把整理好的图文物料定时推送到指定超话——不需要人工守着微博客户端、不用纠结手机端与网页端的差异，只要管线稳定，就能做到“写好即发、发完即跟踪”。

这篇文章记录我们在 OpenClaw 环境中实现超话同步的三个核心环节：**图片上传、限流处理、状态归档**。全部基于微博开放平台的现有 API，没有使用模拟登录或非官方接口。如果你已经在用 Agent / MCP / 插件机制编排自动化任务，希望里面提到的踩坑点和设计思路可以复用。

## 核心问题拆解

1. **图片上传与发帖分离**  
   微博 API 要求先调用 `statuses/upload` 把图片传完拿到 `pic_id`，再通过 `statuses/update`（或支持超话的类似接口）带上 `pic_id` 与文本一同发送。直接拼接 Base64 或挂第三方图床都不适用。
2. **接口频率限制**  
   单应用单用户调用 `statuses/update` 有次数限制（普通权限白天约 30 条/小时，每天上限在 1000 附近浮动），超限后返回错误码 10022 或 10024，需要退避重试。
3. **状态可追溯**  
   发布是否成功、audit 是否通过、mid 是什么、哪张图失败，这些信息如果不落地，排查异常全靠手工翻日志，几轮下来就不可维护。

## 做法 / 步骤

### 1. 凭证管理

在 OpenClaw 工作流中，我们用 MCP 工具包装了一个简单的凭证存储（基于本地 JSON 文件或内置的 secure store）。微博的 `access_token` 有效期较长但会过期，所以额外设一个定时检查节点：每次任务开始前校验 token 是否有效，必要时调用刷新逻辑（如使用 refresh token 或重新授权，视应用类型而定），并将新 token 写回存储。

### 2. 图片上传节点

图片来源可能是本地文件或远端 URL。为了减少不必要的外部依赖，我们统一拉到临时目录，执行一次压缩（`sharp` 或 CL 工具），控制输出为 JPEG 且大小不超过 4.5MB，避免微博侧因尺寸过大返回 20003。

上传步骤：
- 发送 `multipart/form-data` 请求到 `https://api.weibo.com/2/statuses/upload.json`，参数 `access_token` 与 `status`（可为空，上传时可不填）外加 `pic` 的二进制流。
- 解析响应中的 `pic_id` 并存入当前任务的 context。
- 如果返回非 200 或 `error_code`，判断是否为临时失败（网络抖动 / 图片审核中），存入错误栈供后续重试。

> 注意：微博图片上传接口也有频率限制，但比发帖宽松；不过短时间内连续大量上传仍会被拦。我们按上传节点内置 3 秒间隔，避免触发 10006 错误。

### 3. 发帖与超话绑定

发帖主要使用 `statuses/update`，其中：
- 微博文本通过 `status` 传入，并在文本头部或尾部插入 `#超话名称#` 即可命中超话（无需额外参数，官方文档确认）。
- 图片通过 `pic_id` 已在上一步准备好，直接填入 `pic_id` 字段（多个图片时用逗号分隔，但上传需逐张调用）。
- 发帖节点同样维护一个“冷却计数器”：每次成功发帖后，强制等待 180 秒；如果遇到限流错误码（10022/10024），则解析 HTTP 头 `Retry-After` 或默认退避 600 秒。

### 4. 限流友好设计

我们在 OpenClaw 中封装了一个带退避的 HTTP 客户端插件，用于所有微博 API 调用。策略：
- 记录每个 endpoint 的使用计数和最近一次调用时间戳。
- 每次请求前检查：如果距离上次同一 endpoint 调用不足 3 分钟（发帖口），当前任务直接 sleep 到满足条件。
- 若遇到 4xx 限流错误，则根据错误码或 header 调整等待时间，并将该任务重新排入队尾，而不是放弃。
- 整个流水线设置全局超时时间 2 小时，避免死循环。

### 5. 状态归档

我们不用复杂的数据库，而是将每条发布记录写入一个任务日志文件，每条一行 JSON，包含字段：
- `task_id`
- `content_hash`（用于去重或幂等）
- `image_ids`
- `post_text_preview`
- `status`（`pending`/`image_uploaded`/`posted`/`failed`）
- `api_response`（关键字段，mid、error_code、msg）
- `timestamp`

每天定时通过另一个 OpenClaw 任务将日志文件重命名归档（如按日期），并上传到对象存储，顺带生成一份当天的成功/失败统计。同时保留最近 7 天的本地日志，方便实时查看。

## 踩坑点

1. **图片审核导致上传失败但实际已生成 pic_id**  
   遇到过返回 `error_code: 20019`（内容违反规定），但在记录中图片已经产生了 pic_id 却被审核拒绝。这种情况下不应当重试同一张图，而是需要标记该素材需要人工复核，或者直接丢弃并告警。

2. **超话发帖需要签到或等级**  
   部分超话有“关注并等级≥2”的发帖限制。如果账号等级不够，即使带了话题词也发不进超话（接口不报错，但帖子不会出现在超话页）。解决办法：先人工确保账号满足条件，并在自动任务中加入签到逻辑（另一个 API 端点）作为前置条件。

3. **多图上传时顺序偏差**  
   微博发多图时，图片展示顺序依赖 `pic_id` 的顺序。如果并发上传多个图片，返回的 `pic_id` 顺序不一定对应传入顺序。我们用串行上传，按序记录 pic_id 保证了顺序可控。

4. **限流窗口突变**  
   微博会根据内容频率和质量动态调整单应用限流，有时非标准错误码也伴随限流。一律按“遇到非成功且错误码不在白名单内，退避 10 分钟并记录”处理，牺牲一部分时效换稳定性。

## 可复用建议

- **把微博客户端包装为 MCP 工具**  
  如果后续不止一个工作流要用微博能力，直接封装成 MCP server 提供 `upload_image`、`post_weibo`、`check_limit` 等标准化接口，大幅降低维护成本。
- **采用轻量任务队列而非即时触发**  
  哪怕只是一个 Redis 列表或 SQLite 表，也可以把“准备发布的内容”先入队，再由 worker 串行消费，天然控制并发和频率。
- **状态日志与告警分离**  
  归档日志提供事后复盘，实时告警只对“连续失败 N 次”或“token 失效”等关键事件触发，避免噪音淹没重要信号。
- **参数化所有可能变化的值**  
  超话名称、话题格式、图片压缩阈值、退避时间，都做成可配置的环境变量或 OpenClaw 参数，避免硬编码带来的维护噩梦。

## 总结

用 OpenClaw 做微博超话同步，真正的挑战不在“能不能发出去”，而在**稳定、可追溯、不触发风控**。通过把图片上传、频率控制、状态归档拆成松耦合节点，并做好错误分类和退避，一条自动化流水线完全可以替代人工盯屏。希望这次实践能给你在维护自己的微博自动化任务时，提供一些可直接落地的参考。
