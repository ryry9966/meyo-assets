# 让 Agent 真正了解你：用 USER.md 沉淀个人上下文

## 背景

在 OpenClaw 这类可长期运行、能编排 MCP 工具和插件的 Agent 环境里，模型本身并没有关于你的可靠记忆。每次新会话，它通常只知道系统提示、项目规则和可用工具。于是你会反复遇到同一类问题：

- 每次都要重新交代“我习惯用 pnpm，别用 npm”；
- Agent 总给出你不喜欢的默认方案；
- 自动化任务里，它做出不符合你工作流的判断；
- 跨项目任务中，个人偏好完全丢失。

项目级的 `AGENTS.md` 或 `CLAUDE.md` 解决的是“这个项目怎么干”，但没有解决“你是谁、应该怎么配合你”。这就是 `USER.md` 的位置。

## 问题

个人偏好往往散落在聊天记录、插件配置、脚本注释里。上下文窗口有限，不可能每次都全量携带。如果缺少用户级记忆文件，Agent 在跨会话、跨项目和长期自动化任务中的行为会不稳定，你需要不断重复纠正。

`USER.md` 的核心价值，不是让 Agent 变“聪明”，而是减少重复交代，把稳定的个人上下文显式化。

## 做法 / 步骤

### 1. 先确认加载机制

在 OpenClaw 中，用户级上下文的加载方式因配置而异。先别着急写文件，而是启动后直接问 Agent：

> 当前加载了哪些用户级指令文件？

如果支持自动读取用户目录下的 `USER.md`，那最好；如果不支持，可以在全局启动配置里显式引用：

```text
include: ~/.openclaw/USER.md
```

或者在全局 system prompt 中注入该文件。关键是先验证文件是否被读到，再开始维护内容。

### 2. 建立结构化骨架

`USER.md` 建议控制在 80–150 行以内，按区块组织。一个可复用的模板如下：

- **身份与角色**：职位、技能边界、常用语言、希望被如何称呼；
- **目标与当前优先级**：短期目标、长期目标、本周重点；
- **工作流**：代码提交偏好、文档风格、是否先计划后执行；
- **沟通风格**：简洁还是详细、是否给多种方案、是否主动提醒风险；
- **工具与环境**：常用 MCP 服务、包管理器、测试命令、默认 shell；
- **约束**：不要做什么、哪些目录不可动、敏感信息边界、审批策略；
- **决策记录**：最近的重要决定，避免反复讨论。

### 3. 写具体、可执行的信息

不要写“我喜欢简洁”，而要写：

```markdown
回复默认用要点列表，先结论后细节；代码改动前先说明影响范围。
```

不要写“用 git”，而要写：

```markdown
提交信息使用 conventional commits，示例：fix(oauth): handle expired token
```

能被 Agent 直接执行的描述，才是有价值的上下文。

### 4. 绑定加载并验证

把 `USER.md` 放到确认会加载的路径后，重启会话或刷新配置。然后新开一个会话测试：

> 根据 USER.md，我默认的测试命令是什么？

如果回答不准确，说明文件位置不对、没有加载，或者内容被其他规则覆盖。

## 踩坑点

- **文件太长**：超过 5KB 后，Agent 容易抓不住重点，还会占用 context。核心偏好建议控制在 500 字以内，细节和示例可以拆到单独文件，需要时再引用。
- **敏感信息**：不要把 token、密码、身份证号写进 `USER.md`。必要时用环境变量名或 MCP secret 引用，避免明文落地。
- **与项目指令冲突**：`USER.md` 说“任何改动必须先生成计划”，但项目 `AGENTS.md` 说“小修直接执行”，会导致行为不一致。建议明确优先级：项目级规则通常高于用户级偏好，除非用户级写明强制约束。
- **只写不更新**：如果连续两次纠正同一件事，就值得把纠正内容回写进 `USER.md`。否则它会逐渐变成历史文件。
- **共享污染**：如果 `USER.md` 被同步到团队机器，个人偏好可能影响他人。个人 `USER.md` 和团队 `PROFILE.md` 应该分开维护。

## 可复用建议

- **分层记忆**：系统级、项目级、用户级、会话级各司其职。`USER.md` 只管跨项目稳定的个人层。
- **用命令维护**：可以写一个小脚本或 OpenClaw 命令，例如 `/my-profile` 查看当前内容，`/update-user "以后默认使用 pnpm"` 追加一条偏好。
- **加版本与更新时间**：在文件头部记录 `updated_at`，便于判断是否过时。
- **通过 MCP 共享给子 Agent**：如果日历代理、邮件代理等子 Agent 也需要了解你的偏好，可以把 `USER.md` 的相应段落通过 MCP resource 暴露出去，而不是复制多份。

## 总结

`USER.md` 不是“让 AI 更懂你”的玄学，而是一个低成本的用户级上下文工程。它的作用很具体：减少重复交代、让 Agent 在跨会话和自动化任务里行为更稳定、降低个人偏好与项目规则之间的摩擦。

务实的做法是：先验证加载，再逐步填充；控制长度，保持结构化；遇到反复纠正时回写；不要让敏感信息落地。工程化地维护 `USER.md`，比一上来写几千字更有效。
