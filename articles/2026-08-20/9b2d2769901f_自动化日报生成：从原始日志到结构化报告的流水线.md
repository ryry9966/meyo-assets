## 背景

团队里每天要花 15–20 分钟整理日报：从 Git、工单、日历、监控告警里翻前一天记录，再拼成“昨天做了什么、今天计划什么”。这个动作机械、重复，而且容易漏掉跨系统的上下文。我们尝试用 OpenClaw 的定时任务 + Agent 自动生成日报，但直接让模型读原始日志效果很差——要么超 token，要么输出结构不稳定，偶尔还会脑补没发生过的事。

后来我们把问题拆开：不是“让 Agent 写日报”，而是“把原始日志变成结构化事件，再交给 Agent 做摘要和排版”。下面记录这条流水线的做法和踩坑点。

## 问题

原始日志有几个典型特征：

- 来源分散：Git commit、工单状态变更、日历事件、告警通知，格式各不相同。
- 粒度不齐：一条告警可能只是一行 JSON，一次代码评审却包含大段 diff 和评论。
- 噪声多：自动关闭的告警、机器人 commit、重复通知会稀释有效信息。
- 缺少上下文：单条日志看不出“这件事是否完成、是否阻塞”。

直接把这些塞给 LLM，会出现上下文超限、幻觉、日报变成流水账等问题。

## 做法 / 步骤

我们把流水线分成四层：采集、清洗、聚类、渲染。

### 1. 采集：用 MCP 封装数据源

在 OpenClaw 中接入了几个 MCP server，分别对应 Git、工单、日历和监控。每个 MCP 工具只负责返回原始数据，不参与判断。统一事件格式：

```json
{
  "ts": "2025-01-15T09:30:00+08:00",
  "source": "git",
  "actor": "alice",
  "action": "commit",
  "target": "repo/daily-report",
  "meta": { "message": "fix timezone in summary" }
}
```

这一步的关键是屏蔽不同数据源的返回差异。比如有的 MCP 返回 markdown 表格，有的返回纯文本，我们在 adapter 层统一转成上面的 JSON 结构。

### 2. 清洗：规则先行，别都交给模型

每天早上 8:00 由 OpenClaw 定时任务触发，拉取前一天 00:00 到 23:59 的事件。先用规则做预过滤：

- 去掉机器人账号的 commit（如 dependabot、renovate）。
- 去掉自动关闭且无人工操作的告警。
- 把时间戳统一为 ISO8601 带时区，避免 UTC 和本地时区混用。
- 合并重复通知：同一告警的多次状态变更只保留最终状态。

清洗完后，事件量通常能减少 30%–50%。

### 3. 聚类与预摘要：分而治之

按 `target`（仓库/项目/模块）分组，对每组事件用 LLM 生成简短摘要。这里有两个约束：

- 每组事件控制在 15 条以内，避免上下文过长。
- 提示词明确：“只依据给定事件生成摘要，不超过 2 句。若信息不足以判断完成状态，使用‘未记录’。”

输出用 JSON Schema 约束：

```json
{
  "group": "repo/daily-report",
  "summary": "完成日报流水线中时区统一处理",
  "status": "done",
  "blockers": [],
  "sources": ["git:abc123", "ticket:456"]
}
```

`sources` 字段很重要，后面排障和人工核验都靠它。

### 4. 结构化日报：模板固定，避免自由发挥

最后一步把预摘要按模板组装：

- 昨日完成
- 进行中
- 阻塞 / 风险
- 今日计划

Agent 只负责基于预摘要填充模板，不再直接接触原始日志。这样输出结构稳定，也方便后续替换模板。

## 踩坑点

**MCP 返回格式漂移**  
同一个 MCP server 升级后，返回字段可能从 `content` 变成 `text`。我们的做法是在 adapter 里做防御性解析，拿不到预期字段就返回空数组，而不是让流水线崩溃。

**上下文超限**  
一开始想一次性把所有日志丢给 Agent，结果 4k token 直接爆掉。后来改成先聚类、每组只传摘要阶段的事件，问题解决。如果某组事件依然太多，就按时间切分再合并。

**幻觉编造**  
模型看到不完整数据时会“合理补全”，比如根据一次 commit 推断“已完成联调”。我们在提示词里加了硬约束：“禁止推测未在事件中出现的行为。若无法确认，输出 status 为 unknown。” 同时在 JSON Schema 中要求填写 `sources`，一旦核实发现无来源，就回炉重跑。

**时区导致日期错位**  
Git 的 commit 时间是 UTC，日历是本地时区。如果清洗阶段不做统一转换，日报会出现“昨天的 commit 算到今天”。所有事件在进入流水线时统一转成团队本地时区，再按日期切分。

**任务失败静默**  
定时任务偶尔因为 MCP 超时或鉴权失效而失败，但 OpenClaw 的任务状态没有主动通知。我们加了一个降级逻辑：如果某个数据源不可用，日报中显式标注“Git 数据源不可用（超时）”，而不是留空。同时把失败信息写入日志文件，方便排查。

## 可复用建议

1. **中间产物落盘为 JSONL**。采集和清洗的结果都存成 JSONL，重跑时不用重复拉取，排障也能直接 grep。
2. **每个数据源写独立 adapter**。不要在一个脚本里处理所有格式，否则维护成本会随数据源数量指数上升。
3. **用 JSON Schema 约束 Agent 输出**。自由文本只能用于摘要，结构化字段一定要有 schema，否则后面没法自动化处理。
4. **模板与流水线解耦**。日报格式经常变，但流水线逻辑稳定。把模板放在单独配置里，改格式不用动核心代码。
5. **保留人工确认环节**。前期先让日报生成后发到群里，人工确认无误再标记为可信。逐步迭代，不要一上来就全自动发布。

## 总结

可靠的日报生成不靠一个“万能 prompt”，而是靠分层流水线：先把原始日志变成受控的结构化事件，再让 LLM 做它擅长的摘要和排版。在 OpenClaw 里，这套流水线用 MCP 采集 + 定时任务触发 + JSON Schema 约束即可落地。稳定运行后，每天能省下 15–20 分钟，而且日报不再依赖记忆力。
