## 背景

Agent 类工具越来越多地通过 MCP、插件或自动化流程直接操作本地文件、执行命令。一个常见担忧是：Agent 为了完成“整理目录”“批量重命名”“清理临时文件”等任务，会不会顺手执行 `rm -rf`、覆盖写入或批量移动，导致不可逆损失。

OpenClaw 的 sandbox 不是单纯靠提示词约束 Agent“不要删文件”，而是把文件操作放进受限环境里，让越权删除变成一条不可达路径。它的核心思路是：**默认只读、显式授权可写、删除动作独立确认、操作可回滚可审计**。

## 问题：误删风险来自哪里

在未加限制的情况下，Agent 执行的命令或文件操作通常继承当前用户权限。这意味着：

- `rm -rf /home/user/project` 与用户自己在终端执行等效；
- 覆盖写入可能悄悄破坏备份文件；
- 批量重命名、`mv` 到错误路径可能造成目录结构混乱；
- 提示词层面的“不要删除”并不可靠，模型可能误判任务目标或工具描述边界。

因此需要进程级、文件系统级或配置级隔离，而不是只依赖 Agent 的“自觉”。

## 做法/步骤

### 1. 启用默认 sandbox 并限定工作目录

以 OpenClaw 配置为例，通常需要显式指定沙箱生效范围：

```yaml
sandbox:
  enabled: true
  workspace: /home/user/openclaw-workspace
  readonly_root: true
  allowed_writes:
    - /home/user/openclaw-workspace/**
    - /tmp/openclaw/**
```

这里的含义是：Agent 看到的根文件系统为只读视图，只有 `workspace` 和临时目录允许写入。即使 Agent 尝试写 `/etc`、`/home/user/.ssh` 或其他系统路径，也会被沙箱拦截。

### 2. 删除操作单独打开确认

很多误删不是通过 `rm`，而是通过覆盖写、`truncate`、`rename` 或移动操作。建议将删除类动作与普通写入分开控制：

```yaml
sandbox:
  allow_delete: false
  delete_confirmation: true
  dangerous_actions:
    - unlink
    - rmdir
    - truncate
    - rename
```

这样普通文件写入可以自动放行，但涉及删除、截断、重命名时，需要人工确认或二次授权。

### 3. 回收站/快照先行

更稳妥的做法是让“删除”本身不直接发生。OpenClaw 可以在写入前对目标文件做 copy-on-write 快照或硬链接到回收目录，Agent 的删除操作变成移动到 `.openclaw-trash`。即使任务执行失败或误判，也能从回收站恢复。

### 4. 命令白名单与参数过滤

如果 Agent 通过 shell 插件执行命令，不建议直接允许裸 `bash -c`。可以限制命令白名单，并对参数做路径遍历检测：

- 允许 `ls`、`cat`、`grep`、`python script.py` 等明确的只读或受限命令；
- 拦截 `..`、绝对路径越界、`;`、`&&` 等危险拼接；
- 将对 `rm`、`dd`、`mkfs`、`shutdown` 等命令默认阻断。

### 5. 审计与事件监控

每次文件操作记录 `{action, path, from, to, hash, timestamp}`。发生异常时，至少能知道 Agent 在哪个步骤、对哪些文件做了什么。也可以在系统层用 `inotify` 或 auditd 监控批量删除事件，触发即终止进程。

## 踩坑点

- **只配 workspace 不给 tmp，任务频繁失败**：很多库和插件需要写临时文件、缓存，导致 Agent 执行中断。应显式允许 `/tmp/openclaw/**`。
- **`readonly_root: true` 不是万能**：有些 Agent 会尝试 `cp` 敏感文件到 workspace 再处理，或者用 `mv` 跨目录移动。需要配合路径遍历拦截，不能只靠只读根。
- **回收站目录可能被 Agent 写入或清空**：回收目录应放在沙箱外，或只允许追加、不允许 Agent 直接访问，定期清理由宿主进程完成。
- **每次写入都确认会让人工成本爆炸**：按风险分级更实际。workspace 内小文件自动允许；workspace 外、系统路径、删除/覆盖类操作才确认。
- **快照对数据库和二进制文件不一定适用**：硬链接快照可能破坏一致性，需注意磁盘占用和对特殊文件类型的处理。

## 可复用建议

- **最小权限**：给 Agent 单独的用户或容器，文件系统权限与宿主用户隔离。
- **敏感目录不暴露**：代码、文档、下载目录不要直接挂载给 Agent，只挂载必要 project。
- **先 dry-run 再放行**：让 Agent 输出将要执行的文件操作列表，人工确认后再执行。
- **危险操作分级**：普通写入自动放行，删除/覆盖/系统路径操作必须确认。
- **定期演练恢复**：验证回收站或快照真的能恢复，而不是等到出事再测试。

## 总结

OpenClaw 的 sandbox 安全模型不是让 Agent 变得更聪明、不会删错文件，而是让它**没有能力直接删到不该删的东西**。通过只读根、可写白名单、删除独立授权、回收站和审计日志，把 Agent 的破坏范围压缩到受控工作区。对工程化用户来说，关键是配置最小可写面、危险操作分级，以及保留一条可回滚路径。
