## 背景

在 OpenClaw、Agent、MCP 这类自动化项目里，默认接入云端 LLM 通常最省事。但实际开发中经常会遇到几类情况：要处理内部系统数据或敏感信息，不方便发到外部 API；批量测试工具调用时云端成本上升；离线或网络受限环境需要兜底；调试阶段需要固定模型输出，避免频繁切换模型版本。

这些场景下，在家用电脑上部署一个本地 LLM，把它作为开发验证、敏感任务分流或离线后备，是工程上可行且成本可控的做法。本文不讨论跑分，只讲如何在 OpenClaw/Agent 技术栈里把本地模型跑通。

## 问题

家用电脑的硬件限制是首要问题。普通机器可能只有 8GB 显存、16GB 内存，甚至没有独显。本地模型部署不只是“能不能跑”，还要考虑推理速度、上下文长度、并发能力，以及最关键的——工具调用是否稳定。很多本地模型能聊天，但一到 Agent 的多工具选择、JSON 输出就退化，这比单纯生成文本更影响自动化流程。

## 做法/步骤

### 1. 先评估硬件，再选模型规格

一个粗略的显存估算：Q4 量化的 7B 模型约需 4-6GB 显存；13B 约 8-10GB；34B 约 20-24GB。如果纯 CPU 推理，32GB 内存可以跑 7B-13B，但速度会明显下降，适合非实时任务。

建议从 7B/8B 指令模型开始，先跑通流程，再根据显存余量换更大模型。

### 2. 推理引擎选 Ollama，备选 LM Studio/llama.cpp

家用环境首推 Ollama。原因不是它最快，而是它默认提供 OpenAI 兼容 API，管理模型简单，配置项足够日常使用。LM Studio 适合需要 GUI 观察 token 速度的场景；llama.cpp 适合追求极限量化或极端硬件环境；vLLM 更适合高吞吐服务端，不太适合家用单卡交互。

安装后启动服务：

```bash
ollama pull qwen2.5:7b-instruct-q4_K_M
ollama serve
```

默认 API 端点：

```text
http://localhost:11434/v1
```

### 3. 配置 OpenClaw/Agent 使用本地模型

在 OpenClaw 的 LLM 配置里，把 `base_url` 指向本地 Ollama 地址，`api_key` 可填任意字符串，`model` 填已拉取的模型名。例如：

```yaml
llm:
  base_url: http://localhost:11434/v1
  api_key: ollama
  model: qwen2.5:7b-instruct-q4_K_M
  temperature: 0.1
```

这一层配置要抽象出来，方便后续切换本地/云端。

### 4. 与 MCP/插件联调

MCP 工具能否被正确调用，取决于模型是否理解工具描述并返回稳定结构。建议先只暴露 1-2 个工具，把工具描述写清楚，说明输入输出格式、使用条件。将 `temperature` 设到 0 或 0.1，减少随机性。测试时重点看模型返回的是不是合法的 `tool_calls`，而不是把工具名混在普通文本里。

## 踩坑点

**工具调用不稳定**  
小模型在多工具、长上下文中容易只选第一个工具，或者输出 JSON 缺字段。解决方式是限制单次可选工具数量、给工具描述加示例、使用明确支持 function calling 的模型。必要时不要让模型自由选择工具，改为固定流程，模型只负责抽取参数。

**上下文长度不足**  
Ollama 默认 `num_ctx` 较小，Agent 多轮对话容易被截断。需要通过环境变量或 API 参数设置：

```bash
export OLLAMA_CONTEXT_LENGTH=8192
```

注意上下文扩大后显存占用也会增加，要量力而行。

**并发导致 OOM**  
家用电脑不要并发跑多个 Agent。设置：

```bash
export OLLAMA_NUM_PARALLEL=1
```

避免多个请求同时争抢显存。

**量化对工具调用影响明显**  
Q4 量化对聊天影响可接受，但涉及严格的 JSON 输出和函数调用时，错误率会上升。如果显存允许，工具调用场景优先用 Q5_K_M 或 Q6_K。

**Windows GPU 未启用**  
Ollama 在 Windows 上可能默默落到 CPU。检查启动日志，确认加载了 CUDA/ROCm 后端。如果速度异常慢，先检查这里，而不是直接换模型。

**端口与模型格式**  
11434 端口被占用时，通过 `OLLAMA_HOST` 换端口。模型文件使用 GGUF 格式，不要误下成 vLLM 需要的 HF 原始格式。

## 可复用建议

1. **用一套本地 API 服务多个前端**  
Ollama 的 OpenAI 兼容端点可以同时供 OpenClaw、其他 Agent 脚本、调试工具使用，不要为每个项目单独起服务。

2. **建立“本地-云端”两级策略**  
开发调试、离线、隐私数据走本地；复杂任务、长上下文、高强度工具调用走云端。配置里保留切换入口。

3. **固定采样参数**  
Agent 场景不要使用默认的高温度。推荐 `temperature=0.1` 或更低，关闭随机性。

4. **记录模型-任务匹配表**  
哪些模型能稳定调用 MCP 工具、哪些只能做文本分类摘要，形成自己的工程笔记，避免反复踩坑。

5. **监控资源占用**  
用 `nvtop` 或任务管理器观察显存、内存和 GPU 利用率。速度骤降时先查资源，再查配置。

## 总结

家用电脑部署本地 LLM 不是替代云端，而是给 OpenClaw/Agent 自动化项目增加一层可控、私密、低成本的执行后端。要把它当成一个工程组件来对待：模型规格、量化方式、上下文长度、并发限制、工具调用稳定性，这些因素直接决定它能不能在真实流程里用起来。先跑通最小闭环，再逐步替换到关键链路中，是更稳妥的路径。
