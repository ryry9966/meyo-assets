## 背景

在 OpenClaw 这类 Agent 自动化环境里，Cron 任务经常被低估。很多人以为设置好 cron 表达式，再写一句“每天早上帮我总结昨天 GitHub 动态”就够了。实际上，定时任务没有交互澄清的机会，指令里的每一个模糊点都会在无人值守时被放大。

结果是：输出格式忽明忽暗、重复发消息、时区算错、工具调用失败后无人知晓。更麻烦的是，很多问题只在凌晨执行时才暴露，排查成本很高。

这篇文章不讨论“如何写一个更好的提示词”，而是把 Cron 任务当成一个**无人值守的运行手册**来写 instruction。

## 问题

定时任务和交互式对话最大的区别在于：没有第二次确认。你写下的 instruction 必须同时承担目标描述、参数定义、输出约束、失败处理四件事。

常见失败模式：

- 指令只有目标，没有数据范围，Agent 自行决定“最近”是多近。
- 输出位置不明确，结果只出现在日志里，第二天被自动清理。
- 任务失败不通知，连续失败一周才发现。
- 重复执行产生副作用，比如重复推送、重复创建文件。
- 时间词“今天/明天”在跨午夜时产生歧义。

## 做法

### 1. 先写 spec，再写 prompt

不要一上来就写 natural language instruction。先写下任务的运行规格：

```text
trigger: 每天 09:00 Asia/Shanghai
intent: 生成过去 24 小时代码提交摘要
input: GitHub MCP list_commits
output: 写入 ./reports/daily-YYYY-MM-DD.md，并发送到 #daily 频道
failure: 重试 1 次，仍失败则通知 #ops
idempotency: 若当日报告已存在且非空，则跳过
```

这张 spec 比 instruction 本身更重要。它迫使你把隐式假设显性化。

### 2. 指令模板

有了 spec 后，再套用固定结构写 instruction：

```markdown
你是一个负责每日代码仓库摘要的自动化助手。
目标：生成过去 24 小时的提交摘要。
输入：使用 GitHub MCP 的 list_commits 获取仓库 owner/repo 的 commits，since 参数为当前时间减 24 小时。
步骤：
1. 调用 list_commits，参数 owner=...，repo=...，since=触发时间-24h。
2. 过滤 merge commits。
3. 按作者聚合提交数。
输出：将 Markdown 摘要写入 ./reports/daily-YYYY-MM-DD.md 文件，并发送到 #daily 频道。
失败处理：如果 GitHub API 返回 403 或超时，重试 1 次；仍失败则发送错误通知到 #ops，并停止执行。
忽略之前对话，只使用本指令提供的上下文。
```

关键点：时间参数写成“触发时间减 24 小时”，而不是“昨天”。Cron 触发时刻可能跨天，相对时间词非常不可靠。

### 3. 明确时区和 cron 表达式

在 spec 中使用 IANA 时区，例如 `Asia/Shanghai`，不要依赖服务器本地时间。如果团队跨时区协作，统一用 UTC 并在指令中说明换算方式。

### 4. 幂等设计

如果任务会推送消息、创建 PR 或写文件，必须在指令中加入幂等检查。例如：“如果当日报告文件已存在且非空，则跳过本次执行”。否则一次手动补跑就可能造成重复内容。

### 5. 输出格式约束

明确要求输出到指定位置：文件路径、消息频道、或者数据库。同时指定格式，例如“输出 JSON，字段为 date、summary、authors”。不要让 Agent 把结果打印在 stdout 里就结束。

## 踩坑点

1. **相对时间词歧义**：夜间执行的“今天”可能已经变成昨天。永远用触发时间 + 偏移量。
2. **输出丢失**：未指定输出通道，结果只存在日志里。
3. **长上下文污染**：定时任务如果继承了历史对话，可能读取无关信息。指令中注明“忽略之前对话”。
4. **工具无约束**：Agent 可能调用多余工具或错误工具。写明可用工具名称和参数范围。
5. **失败无通知**：定时任务不会有人盯着。必须有失败通知通道。
6. **重复副作用**：重复发消息、重复创建文件、重复建 issue。一定要做存在性检查。

## 可复用建议

- 维护一个 Cron Job Spec 模板，每个任务入库：`trigger, timezone, intent, input, steps, output, failure, idempotency, owner`。
- 新任务先手动 dry-run 一次，检查输出和副作用。
- 指令版本化，修改后记录变更原因。
- 在指令末尾加固定尾部：

```text
执行前先输出计划，执行后输出完成状态；如遇工具错误，不要自行尝试替代方案，直接停止并报告。
```

- 把常用工具调用封装成 MCP，指令中引用工具名而不是自然语言描述，减少 Agent 自行解释的空间。

## 总结

Cron 任务的 instruction 不是聊天，而是运行手册。它的目标不是“让 Agent 理解你的意图”，而是“让任务在任何情况下都能按预期执行或安全失败”。

把时间范围、输出目标、失败策略、幂等条件写清楚，自动化才能从“定时提醒”进化成真正可靠的定时执行。
