## 背景

在 OpenClaw 这类自动化环境里，任务“只跑一次”往往是不成立的。定时 trigger 可能上次没跑完下次又启动；webhook 回调可能因网络超时被平台重发；Agent 调用 MCP 工具时，可能因为响应丢失或结果不确定而再次调用同一个工具；消息队列默认 at-least-once，消费端重试更是常态。

如果任务不是幂等的，重复执行会产生重复记录、重复发消息、创建重复资源，甚至把已经完成的状态回退。真正可靠的自动化，不应该假设执行环境会保证“恰好一次”，而是要把“重复执行也不会出问题”作为默认前提。

## 问题：重复从哪里来

自动化链路里的重复来源通常有这几种：

- 定时任务重叠：上一次运行还没结束，下一次 cron 已经触发。
- 回调/事件重试：webhook 因 5xx、超时或网络抖动被平台重发。
- Agent 工具重试：MCP 工具实际执行成功，但结果返回失败，Agent 再次调用。
- 队列消费重试：消费者处理成功但提交 offset 前崩溃，消息被重新投递。
- 人工重跑：补数据、回放日志、调试时手动触发同一任务。

这些场景下，任务输入可能完全相同，也可能只有部分重叠。如果没有幂等设计，重复执行会累积副作用。

## 做法：把幂等性拆成可落地的步骤

### 1. 先确定幂等范围

不需要让整个自动化链路每一步都强幂等，但要明确哪些步骤是写操作、哪些是副作用、哪些可以安全重复。比如“生成日报并推送”，生成报表可以重复执行，但推送通知不能重复。幂等重点应该放在写库、调外部 API、发送消息、创建资源这些有副作用的步骤。

### 2. 给每个关键任务分配稳定幂等键

幂等键是重复执行时判断“是不是同一件事”的依据。好的幂等键通常来自业务自然键或调用方生成的 UUID。

例如：

- 日报任务：`report:{date}:{workspace}`
- 创建 issue：`repo:{owner}/{repo}:issue:{title_hash}`
- webhook 事件：`event:{source}:{event_id}`
- MCP 工具调用：客户端生成的 `idempotency_key`

关键点：幂等键必须稳定。不要用时间戳、随机数、自增 ID 作为幂等键，因为每次重试都会生成新值，无法去重。

### 3. 写入路径使用唯一约束或条件更新

数据库层是幂等性最可靠的兜底。不要只做“先查再插”，因为并发下两个相同请求都可能查到不存在，然后都插入成功。

推荐做法：

- 对幂等键加唯一索引，插入时使用 `ON CONFLICT DO NOTHING` 或 `INSERT ... ON DUPLICATE KEY UPDATE`。
- 更新状态时使用条件更新，例如 `UPDATE tasks SET status='done' WHERE id=? AND status='running'`，通过受影响行数判断是否重复。
- 状态机设计成单向流转，`pending -> running -> done`，重复的 `done` 请求直接返回成功，不产生副作用。

### 4. MCP 工具和外部 API 要支持幂等键

MCP 工具是 Agent 调用最频繁的边界。如果工具内部不处理幂等，Agent 重试就会直接造成重复副作用。

设计 MCP 工具时：

- 在参数中提供 `idempotencyKey` 或 `clientToken`。
- 工具内部先根据该 key 查询是否已处理过，如果存在则直接返回缓存的结果。
- 对没有官方幂等键的第三方 API，可以在请求里带自定义 `requestId`，配合本地记录去重。
- 在工具描述里明确写清 `Idempotent: yes, key=idempotencyKey`，方便 Agent 判断是否可以安全重试。

### 5. 管理副作用和重试

副作用要尽量放在状态确认之后。例如发送通知前，先确认任务状态成功，并且用唯一约束保护通知记录。重试时使用指数退避 + jitter，避免短时间大量重复请求。

## 踩坑点

- **只用“先查再插”没有唯一约束**：并发下仍然重复。
- **把时间戳、随机数带进幂等键或文件名**：每次重试都变成新任务。
- **部分成功被误判为重复**：资源创建成功但状态更新失败，重试时只看“资源已存在”就跳过，可能丢失后续处理。
- **重复旧消息回退状态**：没有版本号或状态条件，旧事件可能把 `done` 改回 `pending`。
- **幂等键只存在内存**：进程重启后丢失，无法跨重启去重。
- **Agent 重试工具时，工具不支持幂等键**：MCP 工具没有提供 key 参数，Agent 只能盲重试。

## 可复用建议

1. 对每个写操作记录 `idempotency_key`，并写入日志和监控，方便排查重复来源。
2. 数据库唯一约束是最后一道防线，不要只依赖应用层逻辑。
3. 外部 API 尽量使用官方幂等键；没有的话使用客户端生成的 `requestId` 并持久化。
4. 测试时显式重复触发同一任务 2-3 次，检查副作用数量是否仍然为 1。
5. 在 MCP 工具描述中声明幂等性，帮助 Agent 在重试时作出正确决策。
6. 对定时任务使用锁或 `running` 状态防止重叠，而不是依赖“上次应该跑完了”。

## 总结

自动化任务里的“重复执行”不是异常，而是常态。幂等性的核心不是让任务只执行一次，而是让任务在执行多次之后，结果仍然正确、副作用不累积。落实到工程上，就是稳定幂等键、数据库唯一约束、条件更新、状态机保护，以及在 MCP 工具边界上显式支持幂等。把这几点做好，重试、补跑和 Agent 的重复调用才不会变成事故。
