## 背景

在维护 OpenClaw 相关技术笔记时，我经常需要把本地写好的 Markdown 文档同步到社区。手动复制、改格式、配图、发布，一套流程下来至少 5 分钟。于是我想做一个“半自动发帖机器人”：让它帮我整理草稿、生成摘要、调用社区接口发布，但最终点击“发布”前必须经过我确认。

这个需求很常见，但真正落地时发现：难点不在“让 AI 写内容”，而在如何把它接入现有工具链，并保证不翻车。

## 问题拆解

我的目标分三层：
1. **内容生成层**：从本地 Markdown 提取标题、摘要、标签，生成适合社区格式的正文。
2. **执行层**：通过 MCP（Model Context Protocol）暴露社区发帖工具，让 Agent 能调用。
3. **控制层**：定时触发、状态记录、失败重试、人工审核。

最核心的约束是：**不能让模型直接拥有“最终发布”权限**，必须走草稿 + 人工确认。

## 架构与实现步骤

### 1. 内容准备

我的内容源是本地 `notes/` 目录下的 Markdown 文件。Agent 只读取文件名、frontmatter 和正文前 500 字，避免 token 爆掉。

```python
# 伪代码：读取本地笔记元数据
def load_notes(path):
    for md in glob(path + "/*.md"):
        meta = parse_frontmatter(md)
        yield {
            "title": meta.get("title"),
            "tags": meta.get("tags", []),
            "draft": md,
            "excerpt": read_first_n_chars(md, 500)
        }
```

### 2. 接入 MCP 工具

我用一个轻量 MCP Server 封装社区 API。工具定义如下：

```json
{
  "name": "create_draft",
  "description": "Create a draft post in OpenClaw community",
  "inputSchema": {
    "type": "object",
    "properties": {
      "title": {"type": "string"},
      "content": {"type": "string"},
      "tags": {"type": "array", "items": {"type": "string"}}
    },
    "required": ["title", "content"]
  }
}
```

Agent 生成草稿后调用 `create_draft`，返回草稿 ID。此时草稿仅保存在社区后台，不会公开。

接着用一个单独的 `publish_draft` 工具执行发布，但我在 Agent 配置里**禁用了该工具的自动调用**，只允许人工触发。

### 3. 半自动流水线

整体流程：

```
定时任务 -> 扫描本地 notes -> Agent 生成草稿 -> MCP create_draft
-> 返回草稿链接 -> 人工检查 -> 确认后 publish_draft
```

触发方式我选择 cron + 一个简单的 CLI 脚本。每次运行只处理“新增或修改过”的笔记，用 SHA256 记录文件哈希，避免重复生成。

## 踩坑实录

### 坑 1：Markdown 与社区格式不一致

社区编辑器支持 Markdown，但代码块、表格、图片链接的解析有差异。比如本地 `![img](local.png)` 直接发上去是死链。解决办法是：在 Agent 提示词里明确要求“不要引用本地图片，必要时用占位符”，并在草稿阶段自动检测 `![` 且路径不以 `http` 开头时告警。

### 坑 2：Agent 过度发挥导致标题党

第一版让模型生成标题，结果出现“震惊！OpenClaw 竟然……”这种风格。我后来把标题生成改为“从 frontmatter 读取，如果缺失才用模型生成，且要求不超过 30 字、禁止感叹号和夸张词”。Prompt 约束比后处理更有效。

### 坑 3：状态管理混乱

一开始用 JSON 文件记录已处理笔记，结果并发或异常退出后容易脏写。后来改成 SQLite 单表单线程写入，简单可靠。关键字段：`file_hash, draft_id, status, created_at`。

### 坑 4：MCP 工具权限过大

如果 Agent 能直接调用 `publish_draft`，一旦 prompt 被注入或上下文误导，就可能发错内容。我的做法是：MCP Server 里 `publish_draft` 需要额外传一个 `confirm_token`，而这个 token 只在人工确认时由脚本注入，Agent 本身无法获取。

## 可复用建议

1. **发布与生成解耦**：永远保留草稿步骤，不要端到端全自动。
2. **哈希去重**：用内容哈希而不是文件名，避免重命名导致重复发帖。
3. **Dry-run 模式**：先跑一遍只输出草稿 JSON，不调 MCP，确认格式后再实跑。
4. **最小权限**：MCP 工具只暴露必要操作，发布类工具加二次确认。
5. **日志留痕**：记录每次 prompt、模型输出、工具调用参数，方便回溯。

## 总结

这个机器人目前已经稳定运行两周，帮我处理了 10 篇草稿，实际人工发布 6 篇。最大的感受是：**自动化最大的价值不是替代人，而是把重复的格式整理和状态跟踪交给机器，把判断权留给自己。** 如果你也在做类似的事，建议先从“草稿生成 + 人工发布”开始，跑通后再考虑是否放开更多环节。
