## 背景

在 OpenClaw 里跑 Agent，时间一长会碰到一个很实际的问题：不是所有请求都值得发给 GPT。

任务形态差别很大。有的只是抽取、摘要、分类、格式整理；有的则是多步规划、代码生成、连续调用多个 MCP 工具。如果一刀切全部走 GPT，成本、首 token 延迟、数据出域风险都会累积。如果全部走本地模型，又会发现复杂工具调用、长上下文推理、指令遵循不够稳，Agent 容易在循环里打转。

所以需要一层多模型路由：把简单、确定、低风险的任务交给本地模型；把复杂、高风险、需要强工具调用的任务交给 GPT。路由不是「省钱的 trick」，而是把可靠性、成本、隐私放到同一层显式控制。

## 问题

什么时候用 GPT，什么时候用本地模型？

不能只看模型能力强弱，而要结合四件事：

1. 任务复杂度：是否涉及多步规划、多个 MCP 工具联动。
2. 失败成本：输出格式错误是否会导致后续流程连锁失败。
3. 数据敏感度：是否包含 PII、内部数据、客户内容。
4. 延迟与预算：能否接受远程模型的首 token 延迟和调用费用。

一个常见误区是：把「是否提到某个词」当路由判据。比如只看到「总结」就丢给本地模型，但实际任务可能是「读取三个 MCP 数据源，总结本季销售异常」。这种任务本地模型往往扛不住。

## 做法/步骤

### 1. 先做任务分类，而不是先选模型

我会先把 OpenClaw 的常见任务分成两类：

**本地模型优先**：文本摘要、实体抽取、情感分类、格式转换、简单改写、模板填充。特征是无工具或单工具、输出结构固定、失败可重试。

**GPT 优先**：多步规划、代码生成、复杂推理、需要连续调用多个 MCP 工具、需要强指令遵循、结果不可轻易重试的任务。

关键是看「任务是否需要模型自己决定下一步」。如果一个任务需要模型自己判断该调用哪个 MCP 工具、调用顺序、参数怎么组合，本地模型失败概率会明显上升。

### 2. 在 OpenClaw 中配置多个模型 profile

可以在 agent 配置里维护多个模型后端，类似下面的结构：

```yaml
model_profiles:
  gpt:
    provider: openai
    model: gpt-4o-mini
  local:
    provider: ollama
    model: qwen2.5-14b-instruct
```

然后通过策略配置做路由，思路如下：

```yaml
routing:
  default: local
  rules:
    - if: task.tool_calls > 1 or task.planning_depth > 1
      then: gpt
    - if: task.contains_pii
      then: local
    - if: task.output_schema is strict
      then: local_with_grammar
  fallback:
    local_parse_error: gpt
    gpt_timeout: local_simple
```

键名以你实际使用的 OpenClaw 版本为准，重点是把「路由规则」和「模型能力」解耦。

### 3. 给本地模型加结构化约束

本地模型最大的坑是 function calling 不稳定。我的做法是：不要让本地模型直接决定调用哪个 MCP 工具，而是先让它做意图分类，用固定模板生成工具参数。工具选择和复杂参数组装交给 GPT，或者交给代码侧完成。

如果必须让本地模型输出 JSON，尽量开启 grammar 约束或 JSON schema 约束，不要只写在 prompt 里。

### 4. 设置超时、熔断和降级

路由层必须能降级，否则本地模型一次失败会导致整个 Agent 卡死。

建议加三件事：

- 首 token 超时：本地模型超过阈值直接切 GPT。
- 解析错误熔断：同一个本地模型连续 3 次输出格式错误，短时间内不再路由到该模型。
- 降级链路：本地解析失败 → GPT 重试；GPT 超时或限流 → 本地只做无工具任务。

## 踩坑点

**本地模型 function calling 不稳定**

这是最常踩的坑。OpenClaw 的 Agent 如果依赖本地模型自己选择 MCP 工具，经常出现参数缺失、工具名幻觉、JSON 不合法。解决方式是缩小本地模型的职责，工具调用尽量由 GPT 或代码完成。

**上下文无脑膨胀**

把长 memory、大量工具描述、历史消息全部塞给本地模型，质量会快速下降。需要先做检索、压缩或只保留必要上下文。长上下文本地模型不是不能用，而是需要更严格地裁剪输入。

**路由判据太粗**

只靠关键词路由，容易出现「看山是山」的误判。建议把任务特征结构化，比如是否包含工具调用、规划深度、输出 schema 严格程度、数据敏感标记，而不是只判断用户输入里的动词。

**静默失败**

本地模型输出格式错误，OpenClaw 可能重试多次后不再报错，最终给出一个错误结果。路由层一定要把 `parse_error`、`fallback_reason`、`model_used` 写进日志，并设置最大重试次数。

## 可复用建议

1. **维护任务-模型基线表**：每类任务跑 20-50 条样本，记录成功率、耗时、成本。不要凭感觉决定「本地模型能不能做」。

2. **路由规则纳入版本管理**：规则文件要和代码一起走版本控制，改规则要能回滚。路由规则是影响线上稳定性的配置。

3. **日志里记录路由原因**：至少包含 `route_reason`、`model`、`fallback`、`parse_error`。没有这些字段，出问题只能靠猜。

4. **敏感数据默认走本地**：涉及 PII、内部数据、客户内容的，远程模型只发脱敏后的文本。这不是性能优化，是边界问题。

5. **先求稳，再求省**：初期可以默认走 GPT，只把最有把握的简单任务切到本地。稳定之后再逐步扩大本地模型范围。

## 总结

OpenClaw 的多模型路由，最终是把「模型能力」和「任务风险」对应起来。GPT 适合复杂规划、多步 MCP 工具调用、强指令遵循；本地模型适合简单抽取、分类、脱敏场景下的低风险任务。

工程上更重要的是：路由规则要可解释、可回滚、可降级，并且有日志可查。不要只把路由当成本优化手段，它同时是可靠性控制和隐私边界控制的一部分。
