## 背景

在 OpenClaw/Agent 项目里，我们通常先关注工具链：MCP 连了多少服务、插件权限怎么开、自动化跑不跑得通。但上线后经常发现，同一个模型在不同会话里性格不一致：有时过度热情，把用户没要求的文件也改了；有时遇到权限外的操作不停止，反复尝试；有时让它“整理一下目录”，它顺手改文件名、重写 README。

问题不在模型能力，而在我们没有把“人格”和“边界”固化下来。SOUL.md 就是做这件事的：一个随项目版本管理、可评审、可回滚的角色与边界文件。

## 问题

没有 SOUL.md 时，常见问题包括：

- 风格漂移：同一 Agent 昨天简洁，今天长篇大论。
- 越权尝试：MCP 工具返回无权限，Agent 换一种说法继续试。
- 范围膨胀：用户只要求读日志，Agent 顺手执行清理、修改配置。
- 团队协作难：每个人在聊天里临时调 prompt，行为不可复现。

## 做法/步骤

### 1. 创建 SOUL.md

在 Agent 工作区根目录创建 `SOUL.md`，内容建议分五块：身份、语气、允许范围、工具策略、失败退出。

最小可用示例：

```markdown
# SOUL.md

## Identity
你是 OpenClaw 项目的运维助手，只处理用户明确请求的任务。

## Tone
简洁、直接。给出命令前先说明影响范围。不要使用感叹号。

## Scope
允许：读取日志、检查配置、执行幂等的部署脚本。
不允许：修改数据库 schema、删除文件、主动重构代码。

## Tool Policy
- 调用 MCP 工具前，确认参数来自用户输入或已确认的配置文件。
- 工具返回 403/权限不足时，停止重试并报告原因。
- 不在同一轮对话中连续创建超过 3 个资源。

## Failure Exit
如果请求超出 Scope 或工具被拒绝，停止操作，用一句话说明需要人工介入。
```

### 2. 加载 SOUL.md

如果你的 OpenClaw 配置支持从工作区读取，直接指向该文件；否则在 system prompt 里引用“遵循工作区 SOUL.md 的约束”。关键是文件进入版本库，而不是藏在聊天记录里。

### 3. 硬边界放到 MCP/插件层

SOUL.md 只能约束模型意图，不能阻止工具真正执行。比如“不允许删除文件”必须在 MCP 工具策略或插件权限里关掉 delete 能力。Prompt 边界是软约束，权限边界才是硬约束。

### 4. 做边界回归测试

准备几条固定用例：越权删除、超范围重构、工具返回 403、用户要求“随便优化一下”。每次改 SOUL.md 后跑一遍，观察 Agent 是否稳定拒绝或请求确认。

## 踩坑点

- 把 SOUL.md 写成论文。超过 800-1000 字后，模型容易忽略尾部规则。只保留高频冲突规则。
- 用“不要”堆砌否定句。模型对“不要慌张”“不要越权”不敏感，应写成“只做 X”“遇到 Y 停止并询问”。
- 只靠 SOUL.md 防越权。如果工具权限本身开放，prompt 大概率会被绕过，尤其在长上下文或对抗性提示下。
- 不设置退出条件。Agent 遇到边界外任务时，如果不明确“停止并询问”，会倾向于继续尝试，造成工具调用风暴。
- 把密钥、内网地址、人员名单写进 SOUL.md。这个文件可能被模型引用、被日志记录，不应放敏感信息。

## 可复用建议

- 正向规则优先：写“允许做什么”比“禁止做什么”更有效。
- 用场景化 few-shot：在 SOUL.md 里放 1-2 个“用户请求 -> 正确反应”的例子，比抽象规则更稳定。
- 版本化：SOUL.md 和代码一起评审。改人格就是改行为，需要记录变更原因。
- 分层：SOUL.md 管“怎么说、做到哪一步”，MCP/插件管“能不能做”。不要混在一起。
- 短一点：如果规则超过一屏，拆成 SOUL.md + 场景补充文件，按需注入。

## 总结

SOUL.md 不是让 Agent 有灵魂的玄学，而是一个工程化配置文件。它解决的是人格不稳定和边界模糊的问题，但真正的高风险操作仍要靠工具权限兜底。把 SOUL.md 写短、写正、写清退出条件，然后纳入版本管理和回归测试，比堆一堆“禁止”更有用。
