## 背景

我们团队每天要汇总 Git 提交、CI 失败、线上告警、工单变更和 IM 讨论，生成一份日报。最开始的版本用 OpenClaw 的 Agent 直接把原始日志丢给模型，结果报告看起来流畅，但时间线错乱、漏掉关键告警，甚至出现“可能原因”与日志无关。后来我们把重点从“让模型写得好”转到“把日志处理成模型能可靠消费的结构化事件”，日报才从“能看”变成“敢用”。

## 问题

原始日志有三个典型问题：

1. **异构且噪声大**：不同来源字段、格式、时区不统一，里面有 bot 提交、自动关闭、重复告警。
2. **上下文不可控**：一天日志很容易超过几十万 token，不能直接塞给模型。
3. **不可追溯**：模型会补充看似合理但未发生的事实，报告没有证据链，团队不敢用。

## 做法 / 步骤

我们最终落地了一条四段式流水线。

### 1. 定义 schema，而不是定义“日报模板”

先确定结构化字段，而不是让模型自由发挥。比如：

```json
{
  "date": "2025-06-10",
  "timezone": "Asia/Shanghai",
  "changes": [
    {"id": "evt_001", "source": "git", "title": "修复登录超时", "url": "https://...", "priority": "high"}
  ],
  "risks": [
    {"id": "evt_002", "source": "oncall", "title": "支付回调延迟", "evidence": "告警编号 12345", "status": "open"}
  ],
  "todos": [
    {"owner": "@alice", "task": "确认夜间 CI 失败原因", "due": "2025-06-11"}
  ]
}
```

字段不必复杂，关键是每个结论都能引用证据 ID。

### 2. 采集与归一化

通过 MCP 工具把各源数据拉下来，统一成事件 JSONL。比如 Git MCP 只读拉取 commits、PR；CI MCP 拉取失败任务；oncall MCP 拉取告警；IM 通过搜索导出讨论。没有现成 MCP 的源，可以写一个只读插件或脚本暴露成 MCP tool。每条事件变成：

```json
{"fingerprint":"abc123","source":"git","ts":"2025-06-10T09:32:00+08:00","actor":"alice","action":"merge","title":"修复登录超时","url":"...","priority":"auto"}
```

这里建议在 OpenClaw 的 MCP 客户端配置里只用只读工具，避免 Agent 误操作写数据。

### 3. 清洗、脱敏、分组

预处理脚本做几件事：

- 过滤 bot 提交、自动关闭、测试通知；
- 按 fingerprint 去重，合并多源重复告警；
- 脱敏手机号、token、密钥；
- 按 source 和时间窗口分组，限制每个组的事件数。

### 4. 分层汇总，不一步到位

我们不让模型直接读全部事件生成最终报告，而是先按来源生成“摘要块”。例如 Git 块只让它从 commits 中提取三类变更：功能、修复、重构；CI 块只提取失败任务、失败阶段、是否已恢复；oncall 块只提取新增告警、升级、关闭。这样每个块的输入上下文可控，输出也容易校验。

### 5. 组装与生成

把摘要块和 schema 注入最终 prompt，让 Agent 只负责填充字段。要求：

- 所有 `changes` / `risks` 必须来自给定事件，并保留 `id`；
- 不能新增事件 ID 以外的事实；
- 日期和时间必须使用事件里的 `ts`，不要使用模型自身知识推断。

最终输出 Markdown，并通过 webhook 发到飞书/钉钉群，同时附上原始事件索引链接。

## 踩坑点

1. **直接把当天原始日志丢给模型**：模型会“平衡篇幅”，把半夜的严重告警和普通提交同等对待，导致漏报。必须分层、裁剪、按优先级加权。
2. **时间线错乱**：模型经常把昨天的告警当成今天，或者把 UTC 时间当成本地时间。解决办法是事件里显式带 `ts` 和 `timezone`，并在 prompt 中强调只使用事件时间。
3. **幻觉原因分析**：模型看到 CI 失败会自动补“可能由近期重构导致”。我们要求：没有证据就写“未定位”，不允许自由归因。
4. **格式漂移**：要求模型输出 JSON 但偶尔会多出解释字段或少了逗号。加 schema 校验，失败时重试一次，仍失败则降级为人工模板填充。
5. **敏感信息泄漏**：日志里经常混入测试 token。预处理阶段必须脱敏后再调用外部模型，尤其是多租户环境。

## 可复用建议

- **保留 JSONL 中间产物**：每条事件一行，便于回放、调试和重跑某一天。
- **先跑单源**：先接入 Git 一个源，跑通 schema 和报告输出，再扩展 CI/oncall/IM。
- **报告是可追溯摘要，不是文学创作**：每个结论要能点回原始链接。
- **不要全自动发布**：先发到测试群或给自己 preview，稳定一周后再开放给团队。
- **把 prompt、schema、脚本一起版本化**，日报流水线也要像代码一样可回滚。

## 总结

自动化日报的关键不在模型能力，而在流水线是否把原始日志处理成模型可可靠消费的结构化事件。模板约束、证据 ID、schema 校验和分层汇总，比调 prompt 更重要。这样产出的日报不是“看起来合理”，而是可追溯、可复用、可追责的工程产物。
