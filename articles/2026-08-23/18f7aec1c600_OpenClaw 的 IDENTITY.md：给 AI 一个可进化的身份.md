## 背景：Agent 不是缺能力，是缺“自己”

长期用 OpenClaw 做自动化的人，大概率遇到过这类问题：同一个 agent，昨天还能按你的习惯输出，今天换条会话就变了个风格；插件和 MCP 工具越接越多，规则散落在不同配置里，最后谁也不服谁；或者你想调整 agent 的行为，却发现根本找不到一个权威入口。

IDENTITY.md 要解决的就是这个：给 OpenClaw 一个稳定、可版本化、可演进的“身份基线”。它不是简单的一坨 system prompt，而是把散落在 prompt、插件配置、决策偏好里的信息，收敛到一个文件里，并允许它随着项目迭代被有记录地修改。

在 OpenClaw 里，IDENTITY.md 通常放在项目根目录或全局配置目录，由启动器在会话创建时注入系统上下文。不同版本路径可能略有差异，先看 `openclaw config` 或启动日志确认加载位置。

## 问题：身份不稳定，自动化就跑不远

如果只是写一个一次性 demo，静态 prompt 足够。但一旦进入长期自动化场景，问题会集中爆发：

- **会话间割裂**：每次新会话都像失忆，重复解释项目约定。
- **风格漂移**：同一个任务，不同会话给出的方案结构、严谨程度不一样。
- **规则冲突**：MCP 插件带了各自的指令，和你的主 prompt 打架。
- **迭代失控**：你想调整 agent 行为，但改了 prompt 后不知道影响了哪些旧逻辑。
- **不可回滚**：agent 跑偏后，你找不到上一个“正常版本”的身份配置。

这些问题的本质是：身份没有被当作工程资产来管理。

## 做法/步骤

### 1. 先建最小可用骨架

不要一上来就写成“人格指南”。初始 IDENTITY.md 建议控制在 100 行内，只保留能影响行为的关键信息：

```markdown
# IDENTITY
- role: OpenClaw 自动化助理，负责仓库内脚本、MCP 工具编排与排障
- bounds: 只允许在 workspace 内读写；不主动修改外部系统
- tools: 优先使用 MCP filesystem、shell、browser 三类工具
- preferences:
  - 所有写操作前先做 dry-run 或备份
  - 输出方案时给出前提假设、风险点、验证步骤
- rules:
  - 日志中不输出任何密钥、token、内网地址
  - 遇到不确定的插件行为，先查 MCP 工具描述，不要臆测
- evolution: 重大身份变更记录在 decision-log.md
```

### 2. 确认 OpenClaw 真的读到并生效

文件建好后，别默认它会生效。做一次显式验证：启动会话，先问 agent“你现在的工作边界和禁止事项是什么？”让它复述关键条目。如果复述不全，检查：

- 文件路径是否在 OpenClaw 的加载链里；
- 是否被其他 system prompt 覆盖；
- 文件编码/格式是否导致解析失败。

如果 OpenClaw 支持 MCP filesystem，也可以让 agent 自己读一遍 IDENTITY.md，再对比它生成的摘要是否对齐。

### 3. 让身份可进化，而不是一成不变

可进化的关键不是“写得全”，而是“改得动、记得住”。建议增加一个轻量的决策日志：

```markdown
## 2025-03-21
- 原因：MCP filesystem 只读权限导致自动化写日志失败
- 变更：bounds 中增加 `允许在 ./logs 下追加写`
- 验证：跑通日志轮转任务
```

每次身份变更都写一行：日期、变更原因、具体修改、验证结果。这样 IDENTITY.md 就从“静态说明书”变成了“带记忆的演进记录”。

## 踩坑点

- **文件膨胀**：主文件超过 300～500 行后，模型注意力会稀释，关键规则反而不被遵守。尽量把项目特定配置拆成 `profile/` 下的分文件，主文件只留核心身份。
- **写不可验证的目标**：“回答尽量专业”“尽量准确”这类描述没有约束力。应改成可观察行为，例如“输出结论前先列出假设和证据来源”。
- **硬编码敏感信息**：路径、token、内网域名不要进 IDENTITY.md。用环境变量或 secret 插件注入，身份文件只写“敏感信息通过 env 注入，不做明文展示”。
- **多 agent 共用一个身份**：如果 OpenClaw 里跑了多个不同职责的 agent，别让它们共用同一份身份。权限边界和价值排序不同，强行复用会造成越权或互相干扰。
- **没有回滚机制**：身份变更必须进 git。否则 agent 行为跑偏后，你无法快速回到上一个稳定版本。

## 可复用建议

- **用“可观察行为”写规则**。少写形容词，多写动作和边界。例如“禁止修改 `src/` 外的文件”比“操作谨慎”有效得多。
- **分层加载**：核心身份放 `IDENTITY.md`，项目偏好放 `profile/project.md`，临时任务上下文放会话笔记。不要让一个文件承担所有职责。
- **把身份变更当代码审查**。每次修改 IDENTITY.md 都提交 PR，写清楚“为什么改、影响哪些行为、如何验证”。
- **用固定任务集做回归**。准备 3～5 个典型任务，身份变更后跑一遍，检查输出格式、边界遵守、工具调用是否异常。
- **定期清理失效条目**。插件下架、路径变更、旧偏好失效后，及时删除相关描述，避免 agent 被过时信息带偏。

## 总结

IDENTITY.md 的价值不在于写得漂亮，而在于它让 AI 的身份从“临时口述”变成“可版本化、可审计、可回滚”的工程资产。对 OpenClaw 这类要长期跑自动化、接 MCP 和插件的环境来说，这一层稳定性往往比堆更多工具更实际。

先把最小身份跑起来，再让它在真实任务里演进。身份不是一次设计出来的，是迭代出来的。
