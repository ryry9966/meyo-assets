在 OpenClaw 里，Cron 任务看起来只是“定时触发 + 一段 instruction”，但实际是最容易翻车的 prompt 场景之一。原因很简单：定时任务运行时没有用户澄清、没有上下文，Agent 只能靠你留下的那段文字做判断。写得像“每天早上帮我看看有没有什么重要的事”，基本就等于让 Agent 自由发挥。

我最近把几个重复性检查任务改成 Cron 后，踩了不少坑。这里整理一套比较稳的 instruction 写法。

## 问题：Cron instruction 为什么不能按普通对话写

普通对话里，用户会追问、纠正、补充上下文。Cron 任务不会。它可能面对空结果、过期 token、工具限流、时区漂移，甚至重复触发。如果 instruction 没有定义这些边界，Agent 会倾向于“完成任务”，而不是“正确完成任务”。常见症状包括：

- 时区不对，8 点任务变成 16 点跑
- 输入数据为空时，Agent 编造一条“看起来合理”的摘要
- 同一个任务重复发送消息
- 工具调用失败后无限重试，或直接把错误贴到频道

所以 Cron instruction 的目标不是“写得聪明”，而是“把假设显式化”。

## 做法：用五段式模板写 instruction

我现在的固定模板包含五段：触发信息、任务目标、输入、执行步骤、输出与失败处理。

下面是一个真实可复用的例子：每天 08:30 汇总指定 GitHub 仓库过去 24 小时新增或更新的 issue。

```text
[触发信息]
时区：Asia/Shanghai
频率：每天 08:30

[任务目标]
从仓库 owner/repo 的 GitHub issues 中，提取过去 24 小时内新增或被更新的 open issue，生成不超过 300 字中文摘要。

[输入]
- 使用 GitHub API，仓库：owner/repo
- 时间窗口：当前时间减去 24 小时
- 状态：open
- 仅处理 created_at 或 updated_at 落在窗口内的 issue

[执行步骤]
1. 获取 issue 列表。
2. 按时间窗口过滤。
3. 如果结果为空，直接输出：“过去 24 小时无新增 issue。”，不要编造。
4. 如果超过 10 条，只保留最近 10 条，并在开头注明总数。
5. 摘要字段：标题、标签、负责人、链接。

[输出与失败处理]
- 发送到 Slack #dev-daily。
- 格式：一行总结 + 列表。
- 如果本次 run_id 已发送过，则跳过。
- API 失败重试 2 次，每次间隔 30s；仍失败则写日志，不推送到频道。
```

这个模板的关键不是长度，而是每一段都在压缩 Agent 的自由发挥空间。

## 踩坑点

1. **时区必须写死**。不要写“早上”，要写 `Asia/Shanghai`。很多 Agent 默认 UTC，差 8 小时是常态。
2. **时间窗口要明确**。“最近”会被理解成各种范围，直接用“当前时间减 24 小时”或“昨天 00:00 到 23:59”。
3. **空结果分支不能省**。不写的话，Agent 为了完成任务很可能补一条假的。明确允许“无结果”并给出固定文案。
4. **限制输出通道和长度**。Cron 任务不受人实时干预，如果输出到群聊，容易被长文本刷屏。把摘要限制在 300 字以内，并指定单条消息。
5. **重试必须有上限**。工具失败时 Agent 可能会反复调用，甚至打爆 API。写清重试次数、间隔、失败后的行为。
6. **注意重复触发**。如果 cron 平台可能补跑或重试，最好让 Agent 生成一个 run_id（例如 `20250615-0830`），输出前判断是否已发送。

## 可复用建议

- **把 instruction 外置到文件或变量**。OpenClaw 的 cron 配置里只放引用，不要让长指令堆在调度器里。这样改 prompt 不用改 cron 配置。
- **先手动跑一次，再挂 Cron**。把同一段 instruction 作为普通对话任务手动执行一次，观察输出和工具调用是否符合预期。
- **保留 dry-run 模式**。在任务目标里加一句：“如果 input 中包含 dry_run=true，只输出执行计划，不发送消息。” 这对调试非常有用。
- **失败优先静默 + 日志**。定时任务失败时，很多人希望它能通知到频道。但工程上更稳的是失败写日志，只有成功才发消息。否则你会被重复错误刷屏。
- **小步验证时区和数据源**。先用一个最简单的任务验证触发时间和数据源，再逐步加业务逻辑。

## 总结

Cron 任务的 instruction 是写给“未来某个没有上下文的 Agent”看的，不是写给人看的。它需要把时区、输入范围、空结果、输出通道、重试策略、幂等条件都写清楚。写得越长不一定越好，但边界越明确，跑起来越省心。五段式模板 + 空结果分支 + 失败静默，基本能覆盖大部分定时 Agent 任务。
