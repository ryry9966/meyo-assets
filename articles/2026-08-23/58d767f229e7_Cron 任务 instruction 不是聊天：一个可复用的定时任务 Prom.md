# Cron 任务 instruction 不是聊天：一个可复用的定时任务 Prompt 模板

## 背景：定时任务为什么更容易翻车
在 OpenClaw 里，很多自动化任务最终会被挂到 cron 上：早上巡检、定时收集信息、周期同步数据。交互式对话中，Agent 可以追问“你说的是哪个仓库？”“频率是多少？”；一旦改成 cron 触发，就没有这种澄清机会。每次运行都像一次无人值守的作业，instruction 里任何含糊都会被放大为执行偏差。很多时候任务失败不是工具能力不够，而是我们把聊天式指令直接搬进了定时任务。

## 问题：典型错误写法长什么样
举个例子：

> 每天早上 9 点帮我检查服务状态，有异常发给我。

这句话在对话里没问题，但作为 cron instruction，至少有三个隐患：
1. 输入源不明确：Agent 可能去翻聊天记录、打开错误页面，甚至自己补一个服务列表。
2. 异常标准模糊：什么是异常？构建失败、接口超时、磁盘占用高，还是只要响应体里出现 error 就算？
3. 失败策略缺失：如果工具调用失败、网络不可用，它应该重试、跳过，还是静默退出？静默退出最危险，因为你会以为一切正常。

## 做法：把 instruction 写成五段式 runbook
我目前在 OpenClaw 的 cron 任务里会固定使用下面五个字段，效果比自由文本稳定得多。

1. **任务目标**：只写这次运行要产出什么结果，不写过程。
2. **运行假设**：时区、执行环境、可用工具、是否只读。
3. **输入来源**：明确 URL、文件路径、数据库或 MCP 工具，禁止从对话记忆推断。
4. **执行步骤**：按顺序列出，每步给确定参数，并说明工具调用失败时怎么办。
5. **输出与收尾**：发到哪个渠道、格式、失败时是否通知、成功时写状态。

一个改写后的例子：

```text
[任务目标]
检查生产环境 3 个服务的健康状态，如有异常向 #ops 发送一条告警。

[运行假设]
- 当前时区：Asia/Shanghai
- 只读运行，禁止修改任何配置或触发部署
- 可用工具：http.fetch, mcp.monitor.get_status

[输入来源]
- 服务列表接口：https://example.internal/api/services?env=prod
- 超时阈值：5 秒
- 异常判断：HTTP 状态码非 2xx/3xx，或响应时间 > 2000ms，或返回体包含 "DEGRADED"

[执行步骤]
1. 获取服务列表，解析 service_id 与 health_endpoint
2. 对每个服务调用 health_endpoint，超时 5 秒
3. 将每个响应与异常判断条件比较，生成异常列表
4. 如果有异常，按下方格式发送到 #ops；如果全部正常，不发送
5. 将本次结果写入 state/cron_health.json，包含 run_id、timestamp、异常数量

[输出格式]
⚠️ 服务健康告警
- 时间：{{timestamp}}
- 异常服务：{{service_id}} | {{status_code}} | {{latency_ms}}
- 完整结果：{{result_url}}

[边界与失败]
- 如果服务列表接口失败，重试 1 次；仍失败则发送“健康检查任务失败：无法获取服务列表”并退出
- 单个服务超时记为异常，不中断整体流程
- 如果 #ops 发送失败，将失败原因写入 state/last_error.log
```

这个 instruction 不追求聪明，它追求的是：换一个模型、晚一天运行、从空上下文启动，结果仍可预期。

## 踩坑点
1. **时区陷阱**：cron 表达式可能按 UTC 触发，而 instruction 里写“早上 9 点”没指明时区。一定要在运行假设里固定 TZ，并和 cron 表达式对齐。
2. **任务重叠**：如果上次运行 10 分钟，cron 每 5 分钟触发一次，会出现并发执行。最好在任务开头检查 lock 文件，存在则直接退出。
3. **状态不可见**：每次运行都是新上下文，看不到上次结果，容易重复告警。让任务把结果写入持久化状态，并在下一轮读取。
4. **输出噪音**：成功时也发消息会让人麻木。明确“无异常不通知”，或只发每日摘要。
5. **工具误用**：Agent 可能“顺手”重启服务或修改配置。写明“只读运行，禁止修改/重启/部署”，必要时限制可用工具。
6. **失败重试风暴**：任务失败后 cron 继续频繁触发，会加重故障。可以在失败时写 sentinel 文件，让下一次直接跳过并通知。

## 可复用建议
- 每个 cron 任务都要能在对话里手动跑一次，观察输出是否稳定，再决定是否上定时。
- 给每次运行注入 run_id 和时间戳，避免日志与上下文混淆。
- 对会修改数据的任务，先做 dry-run 预览，再通过参数确认开启实际操作；或者限制只能操作白名单内的对象。
- 避免让模型猜时间范围。例如“检查最近 24 小时”会因运行延时产生边界漂移，应写“从上次成功时间到本次开始时间”。
- 把定时任务当作小型运维脚本维护，任何变更都重新跑一遍手册。

## 总结
Cron 任务的 instruction 本质是把 Agent 当无监督的运维脚本使用。关键不是让模型更聪明，而是用清晰边界减少它自由发挥的空间。越是无聊、可复现的 instruction，越适合挂到时间轴上。真正好的定时任务 prompt，是你三个月后回来看，仍然不用想就能知道它每一步会做什么。
