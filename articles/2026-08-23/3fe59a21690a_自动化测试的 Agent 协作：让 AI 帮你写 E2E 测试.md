## 背景

E2E 测试的维护成本通常比编写成本更高。页面一改版，选择器失效；测试数据一变，断言失败；跑完一堆用例，最耗时的不是看业务结果，而是从截图和日志里判断“到底哪里挂了”。

在 OpenClaw 这类 Agent 编排环境里，与其让一个模型从需求文档直接生成 Playwright 脚本，不如把 E2E 维护拆成几个可约束的协作环节：理解页面、生成用例、修复失败。每个环节由一个 Agent 承担，工具通过 MCP 接入，人保留最终审批。

## 问题

直接让 AI 生成 E2E 测试，常见的问题是：

- 选择器靠猜：模型会编造不存在的 `testid`，或者写出一堆脆弱 xpath。
- 对动态加载处理不足：不清楚页面需要等待哪个元素、哪个接口返回。
- 失败后没有闭环：脚本挂了就挂了，AI 不会自己看截图、DOM 快照去修复。
- 容易掩盖业务缺陷：如果让 AI 自动修改断言，测试就失去了回归意义。

所以关键不是“让 AI 写测试”，而是让 Agent 在受控工具和规则下协作。

## 做法：三段式 Agent 流水线

### 1. 准备 MCP 工具层

在 OpenClaw 中接入 Playwright MCP 或 Browser MCP，给 Agent 提供原子能力：`navigate`、`click`、`type`、`screenshot`、`read_dom`、`wait_for_selector` 等。

写操作必须加二次确认，避免 Agent 在错误环境里乱点。

### 2. 探索 Agent：只读理解页面

输入目标页面 URL 和关键路径，让探索 Agent 以只读方式浏览页面，输出：

- 页面主要区域和语义结构；
- 关键控件的 `role`、`name`、`testid`；
- 动态元素的等待条件；
- 候选操作序列。

输出形式可以是 JSON 或页面对象草稿，不直接生成测试代码。这一步的核心价值是把“页面长什么样”固化成可复用信息。

### 3. 用例 Agent：生成可维护用例

基于探索结果和需求描述，生成 E2E 用例。约束如下：

- 优先使用语义定位器：`role`、`text`、`testid`；
- 禁止使用绝对 xpath；
- 明确断言内容，不允许模糊校验；
- 用例输出为 YAML/DSL，而不是直接生成 JS/TS 代码。

这样生成的用例更稳定，也方便人工 review。

### 4. 执行与修复 Agent：只修定位，不改断言

在隔离测试环境运行用例。失败后，把失败步骤、错误信息、DOM 快照、截图交给修复 Agent。

修复 Agent 必须遵守硬规则：

- 只允许修改定位器和等待策略；
- 不允许修改业务断言；
- 断言失败直接转人工，不自动修复；
- 修复后必须重跑相关测试套件，而不是只跑单条。

这样既能降低选择器维护成本，又不会让测试失去业务保障。

### 5. 人工 review 提交

Agent 修复后的 diff 需要人工检查。重点确认：

- 有没有删除关键断言；
- 有没有把严格校验放宽成宽松校验；
- 是否只改了定位或等待，没有动业务逻辑。

## 踩坑点

### 1. 选择器仍然脆弱

AI 很容易偷懒，生成 `div > div > span` 这类绝对路径。必须在 prompt 中明确禁止，并在 code review 时重点检查。优先使用 `testid`、`role`、可访问性名称。

### 2. 全自动修复会掩盖缺陷

如果 Agent 可以自动修改断言，回归测试就会逐渐失效。必须区分两种失败：

- 定位失败：可以自动修。
- 断言失败：必须人工确认。

这是保证测试可信度的底线。

### 3. MCP 上下文爆炸

整页 DOM 和全屏截图很容易占满上下文，导致工具调用超时或被限流。需要限制快照大小，只提取失败步骤相关区域，对 DOM 做截断处理。

### 4. 测试数据污染

Agent 可能在错误环境里创建、删除或修改数据。需要隔离测试租户，写操作加二次确认，并避免在共享环境直接执行。

### 5. 探索阶段误操作

即使声明“只读”，Agent 也可能点到危险按钮。更好的做法是配置写操作白名单，只允许调用明确允许的工具，而不是依赖 Agent 自觉。

## 可复用建议

- **建立页面对象仓库**：把探索 Agent 的结果固化成页面对象，避免每次测试都重新理解页面。
- **用例用 YAML/DSL 管理**：不要直接生成 Playwright 代码。DSL 更易读、易 diff、易 review。
- **给修复 Agent 设置权限边界**：只读失败上下文，只能修改测试仓库，不直接操作业务环境。
- **让截图、DOM、控制台错误作为 MCP 资源暴露**：统一截断规则，避免上下文污染。
- **每次修复后跑全量相关套件**：防止局部修复破坏其他路径。

## 总结

这套 Agent 协作方案，不是让 AI 一键写完所有 E2E 测试，而是把探索、生成、修复拆成可约束的工程流水线。

探索 Agent 负责“页面长什么样”，用例 Agent 负责“要验什么”，修复 Agent 只处理“怎么定位”。人保留业务判断和最终审批。

落地后，选择器维护成本会明显下降，失败定位效率也会提高。但不要期待零人工——业务正确性，始终需要测试人员把关。
