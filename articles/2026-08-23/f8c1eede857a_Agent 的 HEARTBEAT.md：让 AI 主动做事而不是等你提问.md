## 背景

多数 AI Agent 的工作模式是被动响应：你问，它答；你下指令，它执行。即使接了 MCP、插件和长期记忆，很多 Agent 仍然像一个等待唤醒的查询接口。但运维、项目管理和工程质量里，真正有价值的工作往往发生在“没人提问”的时候——依赖过期、错误日志突增、队列堆积、磁盘水位上升。

HEARTBEAT.md 的思路是把 Agent 从“问答终端”改造成“周期性自检节点”。它不是 Prompt 技巧，而是一份放在项目或 OpenClaw 工作区里的轻量契约文件，定义 Agent 每隔一段时间应该主动看什么、怎么报告、何时升级。

## 问题

被动模式有三个明显代价：

1. **上下文断裂**：每次提问都是全新会话，Agent 不了解上次检查结果，也无法形成趋势判断。
2. **问题发现滞后**：只有你想起问“今天有异常吗”才会去查，很多小问题已经发酵。
3. **重复人工投入**：周期性巡检本来是脚本和机器人更擅长的事，却一直靠人肉跑 checklist。

如果 Agent 能按固定节拍主动巡检，你只需要处理差异和例外，而不是每次从零开始。

## 做法

### 1. 先定边界，再写文件

不要一上来让 Agent 什么都查。先从低频、只读、可验证的检查开始，例如每天一次或每六小时一次。范围建议控制在 5 项以内，避免心跳本身变成噪音。

### 2. 在工作区放置 HEARTBEAT.md

在 OpenClaw 的 agent workspace 或项目根目录创建 `HEARTBEAT.md`，作为 Agent 每次触发生效前必须读取的“心跳契约”。它内容应该短、明确、可执行，而不是大段自然语言描述。

一个最小模板：

```markdown
# HEARTBEAT.md
cadence: daily
mode: read-only
last_run: 2025-04-01T09:00:00Z

## Checks
1. 检查近 24 小时错误日志，按类型聚合，只报告新增类型或数量突增。
2. 检查任务队列深度，队列积压超过阈值时输出 top 3 阻塞任务。
3. 检查依赖更新，只列出安全相关更新，不自动升级。

## Output
- 写入 .heartbeat/YYYY-MM-DD.md
- 只保留最近 7 份
- 每项输出：证据路径、判断、建议动作

## Escalation
- 仅当错误率翻倍或队列深度超过 500 时通知。
- 不自动执行任何写操作。
```

### 3. 接入触发机制

触发方式根据你的环境选择：

- OpenClaw 自带定时任务或插件调度；
- 外部 cron / CI 定时调用 Agent 入口；
- MCP scheduler 触发一个轻量任务，让 Agent 读文件、执行检查、写摘要。

核心不是“跑一次脚本”，而是每次触发时 Agent 必须重新读取 `HEARTBEAT.md`，避免把上一次的检查逻辑固化在上下文里。

### 4. 输出要可对比

让 Agent 每次只写增量变化，而不是完整报告。比如：

- 错误类型 A 出现 17 次，较昨日增加 12 次；
- 队列深度 480，接近阈值 500；
- 发现 1 个安全相关依赖更新。

这样你扫一眼就能决定是否处理。

## 踩坑点

**上下文膨胀**：如果让 Agent 每次读取大量原始日志或长历史记录，心跳会越来越慢。只给它必要的查询入口和摘要文件，不要喂原始数据。

**重复执行**：检查项必须幂等。用 `last_run`、状态文件或数据库记录上一次结果，避免每次重复报告同一问题。

**告警疲劳**：心跳不是越勤越好，通知必须设置阈值。只有变化或恶化才上报，否则你会很快静音它。

**权限越界**：先只读，不自动修复。哪怕 Agent 判断“这个依赖需要升级”，也要你确认后再执行。写操作可以单独放白名单或审批流。

**幻觉与误报**：要求 Agent 报告时附上证据路径，例如日志文件片段、API 返回的行号、PR 链接。没有证据的结论不要进入通知链路。

## 可复用建议

- 把 `HEARTBEAT.md` 当 runbook 维护，不写具体实现，只写目标、边界和输出格式。
- 先影子模式跑一周，把 Agent 的检查结果和人工巡检对比，再决定是否接管。
- 心跳结果不要只存在 Agent 上下文里，要落到文件或任务追踪系统，便于复盘。
- 每次发现 Agent 漏报或误报，不要只改 Prompt，先改 `HEARTBEAT.md` 的检查项或阈值。
- 如果你的 Agent 接入 MCP，尽量用专门的查询工具，而不是让 Agent 自己解析网页或抓取终端，这能显著减少误判。

## 总结

HEARTBEAT.md 的本质是给 Agent 加一个可维护的“自主节拍”。它不追求让 AI 更聪明，而是让 AI 的行动范围、频率和输出方式变得可预期、可审计。对 OpenClaw 用户来说，这是一条低成本的路径：从一个文件开始，让 Agent 真正开始主动做事，而不是等你提问。
