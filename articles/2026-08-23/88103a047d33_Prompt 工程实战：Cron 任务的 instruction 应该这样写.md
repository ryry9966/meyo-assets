## 背景

在 OpenClaw / Agent / MCP 的自动化实践里，Cron 任务很容易被当成“定时执行一句话”。但实际跑起来会发现，Cron 触发的 Agent 没有机会追问澄清，也没有长期记忆。它只会拿到一段 instruction，然后在一个很短的上下文窗口里做判断。如果这段 instruction 写得太像人类需求，定时任务往往变成定时翻车。

常见的翻车方式包括：Agent 不知道“当前时间”到底是什么、重复发送告警、调用错工具、输出一堆无法排查的自然语言，或者失败后继续编造完成状态。

所以 Cron 任务的 instruction 不能只是“帮我检查一下服务”，而是要把执行边界、上下文、成功标准和失败策略都写进 prompt。换句话说，要把 instruction 当成没有交互机会的“单次执行规范”。

## 问题

我在实践里遇到的几类实际问题：

1. **时间盲区**：Cron 表达式会触发任务，但 Agent 不知道触发时刻。写“今天”“昨天”“最近一小时”很容易出错，尤其是跨时区运行。
2. **目标模糊**：只写“检查首页是否正常”，Agent 可能随便请求一下，返回 200 就算完成，甚至不看内容是否匹配。
3. **没有幂等约束**：任务重复触发时，会重复创建工单、重复发通知、重复写文件。
4. **工具使用不稳定**：给了 MCP 工具清单，但不给参数约束，Agent 可能自己发明参数或漏调用关键工具。
5. **失败后没有停止条件**：某个工具报错后，Agent 继续往下走，最后输出“已完成”，实际什么都没做成。

这些问题大多不是 Agent 能力不够，而是 instruction 没把上下文补齐、没把边界写清楚。

## 做法/步骤

以一个典型例子说明：每小时检查一次目标 URL 的可用性，异常时发送告警。

### 1. 使用固定五段式 instruction 模板

不要写自由段落，建议固定为：

```markdown
[角色] 你是运维巡检 agent。

[输入]
- 当前执行时间：{{EXEC_TIME}}
- 上次执行摘要：{{LAST_SUMMARY}}
- 目标 URL：https://example.com
- 超时阈值：10s

[步骤]
1. 使用 http_check 工具访问目标 URL，超时 10 秒。
2. 根据状态码判断：2xx/3xx 为正常，其余为异常。
3. 若异常，连续重试 2 次，间隔 5 秒。
4. 仍异常才调用 notify 工具发送告警。

[约束]
- 只允许使用 http_check、notify 两个工具。
- 不得修改任何生产配置。
- 同一错误 fingerprint 在 30 分钟内只允许告警一次。
- 不要输出与任务无关的自然语言解释。

[失败策略]
- 工具不可用、超时或返回格式异常时，立即停止，并输出 ERROR 摘要。
- 不要在失败后继续后续步骤。
```

这个模板的核心是：每次执行只解决“这一次该做什么”，不把调度频率、长期策略混进来。

### 2. 显式注入时间与上次状态

Cron 任务天然没有记忆。所以要在调度层填充变量，比如：

```text
当前执行时间：2025-03-25T09:00:00+08:00
上次执行摘要：{"status":"ok","checked_at":"2025-03-25T08:00:00+08:00"}
```

OpenClaw 里可以用任务包装器，把上次输出摘要或状态文件路径传进去。如果没有这样的机制，至少要注入当前时间，并写清“请只依据当前执行时间判断，不要使用系统时间以外的信息”。

### 3. 要求输出可解析的 JSON 摘要

自然语言输出不利于下一次执行和排障。可以要求 Agent 最后输出：

```json
{
  "status": "ok | error | skip",
  "checks": [
    {"url": "https://example.com", "status_code": 200, "latency_ms": 230}
  ],
  "notified": false,
  "error": null,
  "next_hint": "上次正常，本轮无需额外动作"
}
```

这样既方便日志采集，也方便下一次把 `LAST_SUMMARY` 传回去。

### 4. 限制工具和动作边界

明确可用工具，并给出参数模板。例如：

- 只允许使用 `http_check`、`notify`
- 禁止调用 `shell`、`file_write`、`browser`
- `notify` 的 channel 固定为 `ops-alert`

这一步能有效降低 Agent 在定时任务里的“自由发挥”。

### 5. 先 dry-run 再上线

把 Cron 表达式暂时设成短间隔，例如 `*/2 * * * *`，观察 instruction 是否稳定。连续跑几次没有异常后，再恢复正式频率。dry-run 时可以让 Agent 只输出执行计划，不真正发告警或写文件。

## 踩坑点

- **写“今天”而不是注入时间**：定时任务跑在凌晨时最容易出错。务必用变量注入明确时间。
- **不传上次摘要**：Agent 每次都是“失忆”状态。没有上次摘要，幂等和去重就无从谈起。
- **工具层重试与业务重试叠加**：如果工具自身有重试，instruction 里又要求重试，容易重复执行。要在 instruction 里明确“工具内部重试即可，Agent 不再额外重试”。
- **输出过长污染上下文**：不要要求 Agent 输出完整响应体。只保留状态码、延迟、关键错误摘要。
- **把调度策略写进 instruction**：“每小时执行一次”不是 Agent 的职责，Cron 表达式才是。instruction 只负责单次执行逻辑。
- **失败后没有停止条件**：工具报错后 Agent 可能继续推断、继续调用其他工具。必须写清楚“失败即停止并输出现场”。

## 可复用建议

1. 沉淀一个 instruction 模板库，把检查、备份、清理、巡检类任务抽象成五段式。
2. 时间、目标、阈值、上次摘要都做成变量，避免手写固定值。
3. 每个 Cron 任务配一个 `last_run.json`，记录运行时间、状态、关键输出 hash，作为下一次输入。
4. 固定 JSON 摘要 schema，后续接入日志、告警、统计都会更顺。
5. 所有会修改状态的任务，先做 `dry_run`，确认指令可重复执行后再放开。
6. Cron 任务的 instruction 也要版本化，改 prompt 要像改代码一样留记录。

## 总结

Cron 任务里的 instruction，不是需求描述，而是一份“无询问、单次、可观测的执行规范”。把上下文补全、目标量化、工具限定、失败策略和输出格式写清楚，定时 Agent 才能从“能跑”变成“跑得稳”。

对 OpenClaw 这类 Agent 调度场景来说，最好的 prompt 工程并不是把句子写得更聪明，而是把不确定性从定时边界里赶出去。
