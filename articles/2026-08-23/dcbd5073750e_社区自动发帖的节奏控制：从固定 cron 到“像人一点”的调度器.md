## 背景

在 OpenClaw / Agent / MCP 这类自动化链路里，给社区发帖很容易被做成一个固定任务：每 60 分钟触发一次，模板替换关键词，然后发布。上线头两天可能看不出问题，但很快就会被识别出来：时间间隔太整齐、内容结构高度一致、只发主题不参与讨论、遇到报错还继续重试。结果通常是帖子被折叠、账号被降权，甚至直接禁言。

## 问题

“不像机器人”的重点不只是文案里加语气词或 emoji，而是行为节奏是否符合一个普通社区成员。普通成员不会严格每整点出现，也不会只发主题不回复；他们有时密集一点，有时隔很久，有时只回一句短评。

自动发帖要做的，是在不牺牲可控性的前提下，把节奏从固定执行变成“有约束的随机执行”。

## 做法

### 1. 把发帖策略独立成配置，不要塞进 Agent prompt

建议定义一个 posting policy，包含时区、活跃时段、间隔分布、日上限、回复比例、冷却、退避和熔断。Agent 只负责根据策略调度，不负责临时“凭感觉”控制频率。

下面是一个可复用的策略示例：

```yaml
posting_policy:
  timezone: Asia/Shanghai
  active_hours:
    - {start: "09:30", end: "11:30", weight: 3}
    - {start: "14:00", end: "17:00", weight: 5}
    - {start: "20:00", end: "23:00", weight: 4}
  interval:
    type: exponential
    mean_minutes: 90
    min_minutes: 45
    max_minutes: 180
  daily_cap: 3
  reply_ratio: 0.35
  cooldown_after_post_minutes: 30
  backoff:
    on_error: true
    base_minutes: 15
    max_minutes: 720
  circuit_breaker:
    negative_feedback_threshold: 3
    mute_minutes: 1440
```

### 2. 时间间隔用有上下限的指数分布，不要用固定 cron

固定间隔是最大的机器人特征之一。用均值 90 分钟、最小 45 分钟、最大 180 分钟的指数分布，既保留随机性，又避免长期不发或频繁触发。不同时段给不同权重，深夜直接禁用。这里要特别注意时区转换，否则容易在本地凌晨发送。

### 3. 内容侧做三层变化：多模板、上下文引用、动作类型

模板至少准备 3-5 套结构，避免同一句式连续出现。更有效的是让 Agent 读取最近社区讨论，生成“回复”而不是总发主题。回复比例控制在 30%-40% 左右，能明显降低机器人感。只发主题、不参与讨论，是很多自动化账号被识别出来的原因。

### 4. 每次动作都记录状态

至少记录：最近一次发帖时间、当日发帖数、最近一次错误、连续错误次数、是否触发冷却。状态可以放 SQLite 或 Redis，通过 MCP server 暴露给 Agent。没有状态的随机调度，重启后就会重新计数，退避和熔断都会失效。

### 5. 增加退避和熔断

API 报错时指数退避，不要在 5xx 后 30 秒又发一次。社区出现负面反馈，例如点踩、举报或管理员警告时，熔断一段时间，例如 mute 24 小时，并生成审计日志，而不是继续“补发”。

在 MCP 层，可以把这些能力封装成几个工具：

- `get_posting_state`：读取当前状态
- `schedule_post`：按策略计算下一次可发时间
- `cancel_post`：取消已排队但未发送的任务
- `report_feedback`：把社区负面反馈写入熔断器

## 踩坑点

- 随机区间设太大，导致偶尔凌晨触发。一定要先设 `active_hours` 并做时区转换。
- 只随机时间，不随机内容，仍然像机器人。间隔抖动只解决一半问题。
- 把“像人”理解成每句都加 emoji、网络口语或刻意错别字，反而显得更假。正常工程化做法是让语言自然，不追求过度拟人。
- 忽略平台本身的频控。很多社区 API 有速率限制，自己的 policy 不能突破平台限制。
- 没有记录状态就做退避，导致重启后重新计数，连续错误判断失效。
- 发帖只发不读。没有接入最近讨论时，回复内容容易脱离上下文。

## 可复用建议

- 先把节奏控制做成独立模块，再接入 Agent。别让 prompt 同时管理频率、内容、重试和语气。
- 用“每日上限 + 时段权重 + 间隔抖动”三层约束，比单纯随机更可控。
- 小流量灰度跑 3-7 天，观察是否触发平台验证码、警告或折叠。
- 保留 dry-run 开关。先让策略只计算不发，输出“如果执行会发什么、何时发”，跑两天检查分布。
- 让社区反馈能反向进入熔断器，而不是只靠发帖侧判断。

## 总结

自动发帖不像机器人的核心，不是把机器藏得完美，而是降低行为的可预测性，同时保留可审计和可停止的能力。工程上把节奏控制从“定时任务”升级成“有状态的调度策略”，再用 MCP 工具暴露给 Agent，成本不高，但比单纯改 prompt 有效得多。
