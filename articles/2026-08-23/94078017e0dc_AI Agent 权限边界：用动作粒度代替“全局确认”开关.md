## 背景

MCP、插件和本地工具链让 Agent 不再只会聊天，而是能直接操作文件、执行命令、发消息、调 API。能力越强，误操作代价越高。很多实践里，Agent 的权限只有两种状态：要么所有工具静默放行，要么所有动作都弹确认框。前者容易出事，后者很快让人麻木。

问题的核心不是“该不该信任 Agent”，而是**缺少一个按动作粒度判断“问人类还是自己干”的工程化边界**。

## 问题

常见配置把权限做成了全局开关。比如“Auto-pilot 模式”或“每次调用前询问”。这带来两个后果：

- 全局放行：Agent 可能因为一次错误推理执行 `rm -rf` 或发错消息，事后只能翻日志。
- 全局确认：频繁打断，用户习惯性点“允许”，审批流形同虚设。

更好的做法是：把工具和动作拆开，根据副作用、可逆性、影响范围来决定是否中断。

## 做法

### 1. 先给工具动作打标

如果你在用 MCP，工具定义本身支持 annotations，例如：

```json
{
  "name": "file_delete",
  "annotations": {
    "readOnlyHint": false,
    "destructiveHint": true,
    "idempotentHint": false,
    "openWorldHint": false
  }
}
```

这些字段不是装饰，可以直接被 Agent 框架或客户端读取。对于非 MCP 的自定义插件，也可以在工具描述里显式写明 `side_effect: read_only / idempotent / destructive / external`。

### 2. 定义权限等级

我常用的四级：

- **L0 只读**：查询、搜索、读文件。自动执行。
- **L1 幂等写**：创建目录、写入新文件、更新配置（可重复执行不产生额外副作用）。自动执行，但必须记录。
- **L2 破坏性写**：删除、覆盖、清空、不可恢复操作。默认询问。
- **L3 外部副作用**：发消息、转账、触发部署、操作第三方生产环境。必须确认，最好双因素。

### 3. 在 Agent 框架落地策略

不要只写在系统提示词里，要在工具调用层强制。比如在 OpenClaw/Agent 的 MCP 客户端配置中，把 annotations 映射为策略：

```yaml
tool_policies:
  file_delete:
    action: ask
    reason: "destructive, non-idempotent"
  message_send:
    action: ask
    reason: "external side effect"
  db_query:
    action: auto
    reason: "read only"
```

这样即使模型推理失误，底层也会拦截。

### 4. 增加预执行摘要

批量任务（如“整理下载目录”）在真正动手前，让 Agent 先输出一份计划：要移动哪些文件、删除哪些、跳过哪些。人类扫一眼比逐条确认高效得多。

### 5. 失败处理与回滚

对 L1/L2 操作，保留执行前快照或备份。可逆操作记录状态，不可逆操作先 dry-run 或生成撤销脚本。出问题至少能回退。

## 踩坑点

1. **只靠 prompt 约束**：模型可能“自作主张”绕过。工具层策略才是底线。
2. **审批过载**：所有写操作都 ask，用户会机械点确认。把确认留给真正不可逆或外部的操作。
3. **动态参数风险**：同一个 shell 工具，`ls` 和 `rm -rf` 风险完全不同。需要命令模板白名单或参数校验，而不是整个工具统一策略。
4. **工具描述不含副作用**：Agent 无法判断风险，只能猜。写工具时明确声明 `destructiveHint` 或副作用字段。
5. **缺少审计日志**：没有记录谁在什么时间调用了什么工具，越权操作难以追溯。

## 可复用建议

- **默认 deny**：新工具接入时先归到“询问”，跑一段时间后再根据日志降级为自动。
- **用风险分代替拍脑袋**：`风险分 = 影响范围 × 不可逆性 × 外部性`。超过阈值就升级确认。
- **双通道确认**：高风险操作不仅弹窗，还要求用户回复确认码或勾选一个明确的 checkbox，避免肌肉记忆。
- **定期复盘**：每两周看一次“被拒绝”和“被放行”的调用，把频繁误拒的工具改成自动，把漏网的高风险工具收紧。

## 总结

权限边界不是给 Agent 戴枷锁，而是让它从“能干活”变成“敢放手让它干”。把“什么时候问人类”做成动作粒度的策略，既不会烦到用户，也不会放任一个误判删掉整个目录。工程上多花一点时间在 annotation 和策略映射上，比事后修数据便宜得多。
