## 背景

在 OpenClaw 这类 Agent 环境里，很多自动化跑不通，不是模型不够强，而是模型每次都像第一次见面。比如你在一个项目里反复说“默认分支是 main”，Agent 下次还是问；或者你随口提了一句“以后可以试试 UTC 时间”，它却当作硬性规则写进后续所有任务。

这时候大家容易做一个动作：把聊天记录、任务日志全量塞进 prompt，当作“记忆”。结果窗口很快爆掉，或者模型被旧信息干扰。实际需要的是一个可控的记忆系统：分层、结构化、可检索、可回滚。

## 问题

Agent 记忆通常有三种朴素做法：

1. 每次都带全量历史：token 成本高，注意力稀释，旧信息容易覆盖新指令。
2. 让模型自己总结长期记忆：没有固定结构，格式漂移，后续很难解析。
3. 只存最近几轮对话：跨会话丢失，自动化任务一多就失忆。

偏好的记忆更难处理：它有时效、有范围、有歧义。“这个仓库用 pnpm”可能只适用于当前项目；“回复尽量短”可能是用户随口一说，不一定需要变成永久规则。

所以记忆系统的目标不是“存更多”，而是“在合适时机注入最小必要状态”。

## 做法

### 1. 分层记忆

我倾向把记忆分成四层：

- 工作记忆：当前 session 内，临时变量和进行中任务。
- 短期记忆：最近 N 轮交互或最近 24 小时内重要事件。
- 长期记忆：用户偏好、稳定事实、项目规则。
- 程序性记忆：某类任务怎么执行，比如发布步骤、目录约定。

用户偏好主要落在长期记忆，但要去掉情境依赖，否则会误用。

### 2. 用结构化 schema，不依赖自然语言段落

偏好记忆建议存 JSON 或 SQLite 表，而不是一段总结文字。一个最小 schema 可以这样：

```json
{
  "id": "pref:timezone",
  "type": "preference",
  "content": "UTC",
  "scope": "user",
  "source": "explicit",
  "confidence": 1.0,
  "created_at": 1700000000,
  "updated_at": 1700000001,
  "status": "active"
}
```

其中 `source` 区分显式指令、观察推断、总结生成；`scope` 区分 user/project/session；`status` 允许逻辑删除而不是物理删除。这样后续检索、回滚、冲突判断都有依据。

### 3. 读写走 MCP server，不要让 Agent 直接改文件

在 OpenClaw/MCP 环境里，可以把记忆做成一个 memory server，暴露 `search`、`get`、`store`、`list` 几个工具。Agent 需要读取记忆时调用工具，而不是直接读取某个 markdown 文件。好处是：

- 可以有权限和 scope 控制；
- 可以记录每次写入的来源和版本；
- 可以多会话复用，不用每个插件自己实现一套。

工具描述里要写清楚：写入前必须区分 `explicit` 和 `inferred`，低置信度不要直接写偏好。

### 4. 写入时机：显式优先，隐式观察降级

不要让模型因为用户随口说一句“我不喜欢红色”就永久写入偏好。可以这样设计：

- 用户显式说“以后默认 X”“记住 Y”：直接写入，`source=explicit`。
- 用户反复执行同一选择 2-3 次：写入但 `confidence=0.6`，`source=inferred`。
- 只出现一次或语气不确定：只放短期记忆，等后续确认。

任务结束后，可以让 Agent 对比旧记忆和新对话，生成一个 diff：哪些需要新增、修改、删除。这个整理步骤最好跑在低成本模型或专门脚本里，避免每次主任务都做复杂记忆管理。

### 5. 注入时做预算控制

记忆注入不是全量注入。偏好类可以放在 system prompt 的固定段，但要有 token 预算，比如最多 800 token 或最多 10 条活跃偏好。事实类记忆放工具检索，需要时再取。

这个预算需要根据模型上下文和任务复杂度调整。关键是让 Agent 知道“有记忆可以查”，而不是“把所有记忆都背下来”。

### 6. 冲突与回滚

记忆条目更新时不要物理删除，旧版本保留。冲突规则可以非常简单：

- 最近 explicit 优先；
- 同 source 下，updated_at 最新优先；
- 低置信度不能覆盖高置信度；
- 项目 scope 优先于 user scope，但需要在 schema 里明确。

这样就算某次写入错误，也能回退到上一个版本。

## 踩坑点

- 全量历史当记忆：token 爆炸，模型开始“读旧闻”而不是做任务。
- 没有 schema 的总结：第一次输出 JSON，第二次输出 markdown，后续没法程序化处理。
- 写入过于激进：用户随口一提变成永久规则。
- 记忆不过期：临时偏好永远生效，比如“这次先跳过测试”被记成项目规则。
- 并发写入覆盖：多会话同时更新同一偏好，没有 updated_at 或版本判断，旧数据覆盖新数据。
- 密钥进了记忆：长期记忆里不要保存 API key、token。如果要存，只存引用或环境变量名。

## 可复用建议

1. 记忆做成 MCP server，所有插件/Agent 共用，避免每个项目一套。
2. 最小 schema 先跑起来：`id, type, content, scope, source, confidence, created_at, updated_at, status`。
3. 每次修改记操作日志，而不是直接改 rows；出问题可回滚。
4. 在 Agent 系统提示里固定几条记忆规则：读取时只取相关条目；写入时区分显式和推断；低置信度不写偏好。
5. 每 N 个任务或固定周期跑 memory audit：清理过期、合并重复、标记冲突。
6. 设置注入预算，建议 800 token 或 10 条以内，先窄后宽。

## 总结

Agent 记忆不是“把东西记住”，而是让模型在正确的时间拿到最小但足够的信息。相比折腾超长上下文，更实际的是把记忆设计成结构化、可检索、可回滚的分层系统，并通过 MCP 工具隔离读写。做到这一步后，用户偏好才能真正从“每次都要重复”变成“默认可用”。
