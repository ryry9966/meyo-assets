## 背景

在 OpenClaw、Agent、MCP、插件组合的自动化链路里，任务很少只执行一次。定时任务可能因为调度抖动重复触发；Agent 调用 MCP 工具失败后会重试；Webhook 回调可能被第三方重复投递；用户也可能手动补跑一个“看起来没成功”的任务。

重复执行本身不可怕，可怕的是任务不具备幂等性。很多线上问题不是“没执行”，而是“多执行了一次”。

## 问题

不幂等的典型症状：

- 同一封邮件被拉取后重复创建工单；
- 同一条消息触发两次机器人回复；
- Webhook 重试导致权益重复发放；
- Agent 超时重试后，下游 MCP 工具被重复调用；
- 定时补跑把同一批数据再次处理，产生重复通知。

更隐蔽的是：第一次执行实际成功，但调用方超时了。重试时如果不用同一个幂等键，系统会当成一次新任务，于是产生第二条记录。

## 做法

### 1. 给任务一个确定性的幂等键

不要每次执行都生成随机 ID。优先使用业务单号、消息 ID、事件 ID。没有天然 ID 时，用内容做确定性哈希，例如 `UUIDv5(namespace, payload_hash)`。

### 2. 用状态表记录执行历史

建一张 `automation_runs` 表：

```sql
CREATE TABLE automation_runs (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  idempotency_key VARCHAR(128) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending',
  result JSON NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uniq_idem (idempotency_key)
);
```

处理前先插入或抢占这条记录。如果记录已处于终态，直接返回已有结果，不再执行业务逻辑。

### 3. 状态流转必须是原子操作

先查后写存在竞态：两个并发请求都查到 `pending`，然后都继续执行。建议用条件更新：

```sql
UPDATE automation_runs
SET status = 'processing'
WHERE idempotency_key = ?
  AND status = 'pending';
```

受影响行数为 0，说明已有其他执行者，当前直接返回或进入等待。

### 4. 数据库唯一约束兜底

业务表也要加唯一索引，不要只靠应用层判断。比如工单来源和来源 ID：

```sql
UNIQUE KEY uniq_source (source, source_id)
```

插入冲突时捕获 duplicate key，然后查询已有记录返回。数据库才是最后一道防线。

### 5. 外部副作用独立控制

发通知、扣款、调第三方 API 这类副作用，要在本地先记录“准备发送”，发送成功后再更新状态。重试时先查 `side_effect_status`，已经成功就不重复发送。调用第三方服务时，尽量传对方支持的幂等键。

### 6. MCP / 插件接口支持幂等参数

OpenClaw 插件或 MCP 工具应把 `operation_id` 或 `idempotency_key` 作为推荐参数。工具内部维护短期幂等表或缓存：同一个 `operation_id` 直接返回已有结果，而不是再调下游。否则 Agent 重试一次，下游就被打一次。

## 踩坑点

- **只在内存里做去重**：重启、多副本部署后失效。
- **用时间窗口近似去重**：并不是真正幂等，边界数据会重复。
- **唯一约束含可空字段**：MySQL 的唯一索引允许多个 `NULL`，需要加 sentinel 或生成列。
- **状态更新不是原子操作**：先查后写仍然会竞态。
- **超时误判为失败**：第一次可能已经成功，重试必须复用同一个幂等键。
- **Webhook 乱序重放**：第三方可能先重试后补单，幂等应基于事件 ID，而不是时间顺序。
- **随机 ID 当幂等键**：每次执行都不同，无法识别重复。

## 可复用建议

- 自动化任务统一走 `automation_runs` 表，至少包含 `idempotency_key`、`status`、`result`、时间戳。
- 关键业务表加唯一索引，不要只依赖代码判断。
- 重试策略使用指数退避 + 抖动，并且每次重试必须复用同一个幂等键。
- OpenClaw 内部调用 MCP 时，把 `operation_id` 贯穿上下文，避免下游重复执行。
- 上线任务前做一次“重复投递测试”：同一输入投两次，断言副作用只发生一次。
- 保留执行日志，记录输入哈希、状态、耗时、结果，便于排障。

## 总结

幂等性不是“重复执行不会出错”的承诺，而是一种设计约束。它让重试、补跑、重复回调变成安全操作，而不是线上事故来源。在 OpenClaw / Agent / MCP 场景里，从幂等键、状态机、唯一约束、外部副作用四个方面入手，比事后修重复数据划算得多。
