在 OpenClaw 这类 Agent 运行时里，外部 API 通常被封装成 MCP 工具或插件。搜索、天气、支付、CRM、通知、模型供应商，任何一环挂掉都可能让整条自动化链路中断。更常见的是限流、超时、5xx、数据格式变更。很多时候 Agent 崩溃不是模型能力不足，而是错误恢复没有做工程化处理。

## 问题

先看几个高频失败模式：

- 工具把原生 HTTP 异常直接冒泡给模型，模型拿到堆栈后开始乱试；
- 重试逻辑写在 prompt 里，模型反复循环，消耗 token 和时间；
- 没有超时和熔断，任务被一个慢 API 卡死；
- 没有降级路径，非关键 API 故障拖垮整个流程。

本质上，这些问题的共同点是：**把“外部依赖不可用”当成了意外，而不是常态设计。**

## 做法与步骤

### 1. 收口外部调用，返回结构化错误

在 MCP/插件内部不要直接抛原始异常。统一返回结构，例如：

```json
{
  "ok": false,
  "error": {
    "type": "timeout",
    "retryable": true,
    "message": "upstream timeout after 3s"
  },
  "degraded": false
}
```

让 Agent 读到结构化信息，而不是堆栈。模型更容易基于这个结构做后续决策。

### 2. 错误分类与有限重试

将错误分为：`timeout`、`rate_limit`、`upstream_5xx`、`contract_error`、`empty_data`。只有 `timeout`、`429`、可重试的 `5xx` 才做自动重试。

重试采用指数退避加抖动：500ms、1s、2s、4s，最多 3 次。`4xx` 和协议错误不要重试，否则问题会被放大。

### 3. 设置超时和熔断

每个外部调用都要有明确超时，经验值 2–5 秒。熔断器在连续失败 N 次后短路一段时间，直接返回降级结果或失败，避免把已经不可用的上游继续打挂。

### 4. 设计降级路径

按接口重要性分级：

- **关键路径**：支付、发送消息等，失败即停，但保留状态；
- **可缓存路径**：查询类、天气、汇率等，返回最近一次成功缓存，并标记 `stale: true`；
- **可切换路径**：模型供应商、搜索等，切换备用 provider；
- **可忽略路径**：日志、分析、推荐等，失败后写入 events，不阻断主流程。

### 5. 把失败显式注入上下文

工具返回失败时，应该在 observation 中明确写：

> 外部 API 不可用，已重试 3 次，建议使用缓存或跳过。

让 planner 决策，而不是让模型猜测发生了什么。

### 6. 状态持久化与断点续跑

长流程在关键步骤前保存状态。API 恢复后可以从断点继续，避免从头发起重试导致重复副作用。

### 7. 可观测性

记录每次外部调用的成功率、延迟、重试次数、降级原因。在 OpenClaw 日志或指标体系中增加类似 `api_failure_total` 的统计，方便事后排障。

## 踩坑点

- 在 prompt 里写“失败就重试”，模型容易无限循环；
- 不区分错误类型，对 `400/401` 也重试；
- 降级返回旧数据但不标记 `stale`，用户把缓存当实时结果；
- 超时设置过长，任务队列被一个慢 API 堵死；
- MCP 工具异常直接抛到上屏，模型开始发散；
- 重试风暴导致上游限流升级，甚至封 key；
- 切换 provider 但参数或格式不兼容，产生更隐蔽的错误。

## 可复用建议

- 给所有外部工具包一层 `safeCall` 或 `withRecovery`，统一重试、超时、熔断、降级逻辑；
- 建立“能力降级表”，将接口与降级方式写成配置，不散落在代码里；
- 对写操作慎用自动重试，除非上游明确支持幂等；
- 用故障注入测试：手动让 API 超时、返回 500 或坏数据，验证 Agent 能否按预期降级；
- 在 system prompt 中只保留“按工具返回的结构化错误进行决策”，不要让模型负责底层重试。

## 总结

外部 API 挂了不是偶发事件，而是必须按常态设计的场景。把错误恢复从 prompt 移到工具层，做到结构化错误、有限重试、分级降级、状态可恢复、指标可见，Agent 才能在真实环境里跑得稳。比模型聪明更重要的，是系统在依赖不可用时仍能体面地失败和恢复。
