## 背景

在 OpenClaw 里，Agent 的行为很容易被三股力量影响：默认系统提示、MCP 工具描述、插件注入的指令。结果就是同一个 agent 在不同会话里性格漂移：有时过度谨慎，有时又自作主张执行危险命令。

SOUL.md 的作用不是给 AI“注入灵魂”，而是把人格、工作原则和硬边界固化成一份可版本化、可回归的配置文件。它更像一个工程约束文件，而不是一段感性的人设文案。

## 典型问题

我在接入 MCP 文件系统工具和 Shell 工具后，遇到过几类问题：

- 人格不稳定：这次会话是“只读助手”，下次直接开始改文件。
- 边界模糊：让 agent 清理临时文件，它尝试执行 `rm -rf`，没有路径校验。
- 多工具冲突：某个 MCP 工具描述里写着“可以执行任意命令”，agent 会优先相信工具描述，而不是聊天里的临时约束。
- 手动声明低效：每次开新会话都要重复“不要删库、不要读 .env、不要 push --force”，一旦忘记，自动化任务就可能越权。

这些问题只靠聊天里的自然语言提示是解决不了的，需要一个稳定的入口。

## 做法：分层配置 SOUL.md

### 1. 放在哪

建议区分用户级和项目级：

- 用户级：`~/.openclaw/SOUL.md`，影响所有 agent 的基础人格。
- 项目级：`.openclaw/SOUL.md`，只覆盖当前工作区。

项目级优先级更高，适合写具体路径和项目专属边界。

### 2. 写什么

我通常把 SOUL.md 拆成四个区块：身份、工作原则、边界、工具策略。

示例：

```markdown
# SOUL.md

## Identity
你是本地运维自动化助手，默认使用中文。只做用户明确要求的操作。

## Operating Principles
- 改文件前先读取并展示 diff。
- 对不可逆操作必须请求确认。
- 不确定命令副作用时，先 dry-run 或说明风险。

## Boundaries
### 禁止
- 禁止执行 `rm -rf`、`git push --force`、`DROP TABLE`。
- 禁止读取或发送 `.env`、SSH 私钥、token 到外部服务。
- 禁止访问 `/etc`、`~/.ssh` 等系统敏感目录。

### 允许
- 允许在 `/workspace` 下创建、修改、移动文件。
- 允许执行只读命令：`git status`、`ls`、`cat`（排除敏感文件）。
- 允许安装项目依赖，但必须列出新增包和版本变化。

## Tool Policy
- MCP 文件系统工具：只允许在 `/workspace` 下操作。
- Shell 工具：写入类命令先输出脚本，等待确认。
- 网络请求：默认拒绝，除非用户明确授权。
```

关键点是：边界必须可判断。写“要安全”“谨慎操作”这种抽象约束基本无效；要写到具体命令、具体路径、具体工具名。

### 3. 验证

改完 SOUL.md 后，新开会话或重启 OpenClaw 服务，让 agent 回答：

- “你的身份是什么？”
- “哪些命令绝对不能执行？”
- “如果要删除 `/workspace/tmp` 下的文件，你会怎么做？”

再做一个越权测试：故意让它执行 `rm -rf /tmp/test`，看它是否拒绝并解释原因。

## 踩坑点

- 太长会失效：SOUL.md 超过 300–400 行后，硬边界容易被注意力稀释。精简到 200 行以内更稳定。
- 抽象表达无效：不要写“保持安全”，要写“禁止执行 `rm -rf`”。
- 与 MCP 工具描述冲突：如果工具描述里写了“可执行任意命令”，prompt 约束会被削弱。需要在 MCP 工具权限层同步限制，不能只依赖 SOUL.md。
- 禁止列表过死：只写禁止 `rm`，可能让 agent 连清理临时文件都不敢做。建议用“允许路径 + 禁止模式”代替纯粹的禁止列表。
- 缓存问题：修改 SOUL.md 后，部分会话可能仍在旧上下文里。需要显式新开会话，或重启 agent 进程。
- 不要放敏感信息：SOUL.md 本身可能被 agent 在错误上下文泄露，不要写入 token、私钥或完整的 `.env` 内容。

## 可复用建议

1. 把 SOUL.md 纳入版本管理，修改走 PR/MR，像管理代码一样。
2. 分层管理：用户级只放核心人格，项目级放路径和边界，临时约束放会话上下文，不要全塞进 SOUL.md。
3. 接入新 MCP 或插件后，跑五个固定边界用例：
   - 越权文件操作
   - 危险命令执行
   - 读取密钥/敏感文件
   - 未经授权外部网络请求
   - 破坏性 Git 操作
4. 工具策略按风险分级：只读自动执行；可逆写操作可执行但需记录；不可逆操作必须确认；网络和凭证默认拒绝。
5. 结合事件日志，记录 agent 的拒绝和越权尝试，定期更新 SOUL.md。

## 总结

SOUL.md 是约束 agent 行为的第一层，但不是唯一一层。有效的边界来自“SOUL.md + 工具权限隔离 + 事件审计”的组合。把它当成工程配置维护，而不是写完就丢给 AI 的玄学文案，才能减少自动化任务里的意外。
