## 背景

在 OpenClaw 或类似 agent 自动化环境里，Cron 任务通常用来做定时巡检、抓取、报表、清理。很多人习惯把交互式对话里的说法直接塞进 instruction，比如“每天早上检查一下服务状态，有异常提醒我”。这种写法在有人追问的场景下还能用，但 Cron 是冷启动、无追问、无人值守，instruction 的模糊会被快速放大。

## 问题

定时任务和对话任务有三个关键差异：

- 没有追问窗口，不能等用户澄清；
- 没有上下文积累，每次都是冷启动；
- 失败不一定有人立刻看到，容易静默积累。

所以 Cron instruction 必须足够完整、可判定、可追溯，不能只写目标，不写边界。

## 做法 / 步骤

建议把 instruction 写成“可执行规格”，至少包含这些字段：目标、时区、输入、允许工具、执行步骤、分支条件、输出格式、失败策略、幂等策略、通知策略。

模板如下：

```text
你是 OpenClaw 的定时巡检 agent。
任务：每个工作日 09:00 Asia/Shanghai 执行一次。
输入：读取环境变量 TARGET_URL，缺失则立即告警并退出。
允许工具：http_get, notify, log。

步骤：
1. 使用 http_get 请求 ${TARGET_URL}/health，超时 10 秒。
2. 如果状态码不是 2xx 或响应时间超过 2000ms，执行第 3 步；否则执行第 4 步。
3. 调用 notify 发送告警，标题包含日期、状态码、耗时。
4. 使用 log 输出一行 JSON，字段：ts, status_code, latency_ms, alert_sent。

约束：
- 只读健康检查，禁止重启、部署、修改配置。
- 失败后最多重试 1 次，间隔 30 秒。
- 不要输出自然语言分析，只输出结果和结构化日志。
```

这个模板里每句话都有作用：目标约束任务边界；时区避免 UTC 和本地时间混淆；输入明确来源，不用模型猜；允许工具缩小动作面；步骤和分支让执行可判定；输出 JSON 便于排查；失败策略避免无脑重试；幂等约束减少副作用。

## 踩坑点

- 只写“检查一下”，模型会自己发明工具，比如去读不相关页面或调用不该用的接口。
- 不写输出格式，每次返回自然语言，日志很难 grep。
- 不限制写操作，可能因为“顺手”执行了重启、清理，造成不可逆副作用。
- 忽略时区，任务在 UTC 或容器默认时区执行，报告时间错位。
- 重试不幂等：失败后重复插入数据、重复发送短信或重复创建工单。
- 失败静默：没有 notify 或日志落盘，任务挂了一周无人发现。

## 可复用建议

1. 把 instruction 字段化：触发时间/时区、输入来源、允许工具、执行步骤、输出 schema、失败策略、幂等策略、通知策略。新建 Cron 按这个 checklist 过一遍。
2. 增加 dry-run 模式：指令里写“如果传入 DRY_RUN=1，只打印计划，不产生副作用”，上线前先验证。
3. 输出 JSON Lines 而不是自然语言，尽量包含 run_id、ts、task_name、status、error。
4. 幂等设计：让任务显式使用唯一键或状态文件，例如“发送告警前检查当天是否已发送过相同 status_code 的告警”。
5. 敏感信息用环境变量或 secret 注入，不要把 token 写进 instruction。
6. 如果任务可能重叠，设置执行锁或把 cron 间隔拉长，避免上次未结束下次又启动。
7. 关键写入操作先预检再执行，例如“先列出待清理文件，确认数量大于 0 且都是 .tmp 结尾，再执行删除”。

## 总结

Cron instruction 的目标不是“AI 能理解”，而是“每次冷启动都能做对，并且出错可追溯”。好的定时任务指令应当把模糊决策压到最少，同时保留必要的执行灵活性。把所有关键条件写清，比事后分析为什么 agent 乱跑更省时间。
