## 背景

在 OpenClaw / Agent / MCP 体系里，大部分助手仍然是被动响应式：用户发消息、提指令，它才开始干活。但很多真实场景需要“发生即处理”：监控告警、GitHub issue 状态变化、定时巡检、依赖更新提醒。如果每次都要人盯着再手动触发，Agent 的价值会大打折扣。

最近我把几条主动链路接到 OpenClaw 里跑通了一遍：Prometheus 告警、GitHub webhook、定时巡检三类事件进入同一个 proactive 通道。中间踩了不少坑，整理成可复用的做法。

## 问题

直接给 Agent 接上 cron 或 webhook，让它“主动干活”，通常会出现几类问题：

- 告警抖动导致推送轰炸，群消息刷屏；
- 模型误判，把“可能有问题”理解成“现在去重启服务”；
- 每次主动触发都带上大量历史，上下文被迅速塞满；
- 权限过大，proactive 通路复用了管理员级凭据；
- 主动动作执行后没有审计，出了问题很难回溯。

所以 proactive 的核心不是让模型更激进，而是提供一条**受控的事件通道**：事件能进来，但不会直接到达执行层。

## 做法 / 步骤

### 1. 先做“通知型 proactive”，不做自动执行

第一版不要一上来就自动改配置、重启服务。让 Agent 只读事件、整理上下文，推送到群或频道，并在消息里附一个“我来处理”的入口。观察一周，看哪些事件真正值得进入下一级。

### 2. 统一事件入口，使用结构化 JSON

在 MCP server 或插件里实现一个统一入口，例如 `proactive.event`。cron、webhook、监控回调都转换成同一种结构：

```json
{
  "source": "prometheus",
  "type": "alert.firing",
  "severity": "high",
  "fingerprint": "abc123",
  "payload": {},
  "timestamp": "2025-01-01T09:00:00+08:00"
}
```

不要让自然语言直接进入决策层，否则模型很容易被噪声带偏。

### 3. 规则层先过滤，再给 Agent

在 Agent 前面加一层规则过滤：白名单事件类型、去重窗口、静默时段、最小间隔。例如同一个 `source + type + fingerprint` 在 5 分钟内只允许触发一次；凌晨 2 点到 7 点只记录不推送；低严重度事件先聚合，不实时打扰。

### 4. Agent 只读优先，写操作默认 dry-run

决策层给 Agent 的工具要少而明确。诊断、查询类工具可以直接调用；变更、重启、发布类工具默认带 `dry_run=true`，先返回执行计划，不直接落地。

### 5. 所有主动动作落审计

每次主动触发记录：事件 ID、决策摘要、执行结果、耗时。最好加一个 `correlation_id`，从告警到执行结果能一路串起来。

## 踩坑点

- **推送轰炸**：没有去重和静默窗口时，一个抖动的指标就会刷屏。按 `source + type` 做短窗口聚合，能有效压制。
- **上下文膨胀**：不要给 Agent 塞大段历史日志。用摘要和最近片段代替全量上下文，事件里可以带 `context_hint` 指定最小需要的工具或知识。
- **时区问题**：容器跑在 UTC，定时任务配置成“每天 9 点”，实际变成本地 17 点。统一 ISO8601 带时区，由 gateway 做时区转换。
- **webhook 安全**：外部回调要验签，避免伪造事件触发 Agent。
- **误执行风险**：Agent 容易把“疑似异常”理解成“立即修复”。写操作必须显式确认，或采用双通道确认。

## 可复用建议

- **成熟度分三级**：L1 通知、L2 建议、L3 自动执行。别跳级，尤其不要在第一周就进入 L3。
- **给 proactive 设每日预算**：最多 N 条主动消息，超过只记录不推送，避免失控。
- **双通道确认**：关键动作先推卡片，用户点击确认后才执行；超时未响应自动放弃。
- **保留 replay 能力**：把原始事件 payload 存下来，方便复现问题。
- **独立最小权限凭据**：proactive 通路不要复用管理员 token，单独建一个只读优先、最小权限的凭据。

## 总结

proactive 能力不是让 Agent 猜测你的意图，而是把“事件驱动、规则过滤、克制执行”工程化。在 OpenClaw / MCP 体系里完全能承载，但关键在约束，不在放开。先把通知做好，再谈自动执行；先让 Agent 解释它想做什么，再让它真正动手。
