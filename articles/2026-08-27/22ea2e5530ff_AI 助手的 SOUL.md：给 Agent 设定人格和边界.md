## 背景

在 OpenClaw 这类 Agent 框架里，模型不再是单轮问答，而是会连续调用工具、读写文件、操作插件和 MCP 服务。工程上最麻烦的问题往往不是“模型不够聪明”，而是行为不可预测：该停的时候继续跑、遇到权限不足就换工具硬试、同一件事每次语气和结论都不同。

SOUL.md 的价值，是把“人格”和“边界”从口头约定变成可版本管理的行为契约。

## 问题

很多 SOUL.md 有两种失败形态。

一种是太软：只写“你是友好的 AI 助手”，没有工具约束、失败策略和输出规范。Agent 在自动化流程里会过度发挥，例如看到写权限就直接改文件，或者把一个查询任务扩展成多步操作。

另一种是太杂：把身份、语气、安全规则、工具说明、项目背景全塞在一起。规则之间互相冲突，模型只记住前半部分，后面的硬限制被忽略。

核心问题不是提示词写得不够多，而是没有分层、没有优先级、没有测试。

## 做法/步骤

我会把 SOUL.md 分成五个区块：

- Identity：角色名、定位、语气。
- Principles：3～5 条不可妥协原则。
- Tool Policy：允许、谨慎、禁止的工具；调用上限；重试策略。
- Failure Handling：连续失败、权限不足、不确定结果时的动作。
- Output Contract：输出顺序、格式、变更说明。

一个缩减版示例如下：

```markdown
# SOUL.md

## Identity
你是 OpenClaw 的运维机器人。语气简洁、诚实，不假装成功。

## Principles
1. 不猜测执行结果。
2. 涉及删除、发布、付费操作必须先列出计划并等待确认。
3. 不确定时降级为提问，而非继续尝试。

## Tool Policy
- 允许：read_file, search, git_status
- 谨慎：write_file, run_command
- 禁止：读取凭据、修改权限

## Failure Handling
- 同一工具连续失败 2 次：停止并报告。
- 权限不足：不要绕过，不要尝试替代工具。
- 结果不确定：不要编造成功。

## Output Contract
- 先给结论，再给步骤。
- 涉及变更时，输出 plan 和 diff。
```

关键是把“人”和“事”分开。SOUL.md 管长期行为，项目规则、MCP 工具说明、安全策略放独立文件。入口处可以声明：当任务指令与 SOUL.md 冲突时，以 SOUL.md 为准。

## 踩坑点

1. 文件太长导致末尾失效。核心边界要放在前 50 行，或直接标注为硬边界。
2. 规则互相冲突。例如“尽量少调用工具”和“必须验证结果”同时出现，模型容易选择更容易的一条。
3. 把语气规则写得太死。错误场景里如果还要求“友好”，Agent 可能用礼貌语气掩盖失败。
4. 边界过严导致无法执行。完全禁止写操作，可能连报告文件都生成不了。应区分“需要确认”和“完全禁止”。
5. 把 SOUL.md 当安全边界。这是最危险的一点。提示词约束可以被忽略或绕过，真正限制必须落在工具层、系统层和权限控制上。

## 可复用建议

- 保持 SOUL.md 小而稳定，细节放外部规则文件。
- 给任务设置完成定义，例如“只有工具返回 0 且日志校验通过才算成功”。
- 准备 3～5 个边界测试场景：越权操作、连续失败、含糊指令、错误工具、权限不足。
- 每次 Agent 违规后，把具体上下文补进禁止项，而不是只加一句“以后注意”。
- 区分长期 SOUL.md 和会话级 SESSION.md。临时目标、当前任务边界不要写进长期人格文件。

## 总结

SOUL.md 不是给 AI 写人设，而是给 Agent 建立可预测的行为契约。好的 SOUL.md 应该短、分层、可测试，并且与工具权限、项目规则分开。提示词边界只能约束常规行为，真正不可突破的限制必须在工具层和系统权限里实现。
