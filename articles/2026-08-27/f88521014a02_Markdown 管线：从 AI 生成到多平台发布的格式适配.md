在 OpenClaw 生态里，Agent 输出 Markdown 是非常自然的事：让模型写日报、周报、发布说明、技术文档，再通过 MCP 或插件推到 GitHub、飞书、Discord、公众号草稿箱。但一旦从“生成一篇 Markdown”走到“多平台发布”，问题就开始出现：同一个 `.md` 文件，在 GitHub 渲染正常，到飞书可能多出一堆 `#`，到公众号编辑器里表格直接变成一行乱码。

原因不是 AI 写得不好，而是 Markdown 本身只是“书写约定”，各平台实现方言差异很大。直接拿模型原始输出做发布，等于把格式适配责任全部推给下游平台，往往不可控。

## 问题拆解

差异主要集中在几类：

- **标题与段落**：有些平台要求标题前后空行，有些会把连续空行折叠。
- **表格**：GitHub、飞书对 Markdown 表格支持较好，但微信公众号、知乎内建编辑器对表格支持很差。
- **代码块**：语言标识、高亮、行号、长代码截断行为各不同。
- **链接与图片**：外链跳转、图片防盗链、相对路径处理差异大。
- **特殊语法**：脚注、Task List、数学公式、HTML 标签、frontmatter，部分平台直接不识别或报错。
- **换行**：CommonMark 要求行尾两个空格或空行，但很多 AI 输出只给单个换行。

如果每个平台都写一套转换脚本，维护成本会快速上升。工程化做法是让管线“先归一化，再按 profile 输出”。

## 做法：一条可复用的 Markdown 管线

### 1. 限制生成端：让 Agent 输出受限 Markdown 子集

在 prompt 或工具描述里明确：只使用 CommonMark；禁用 frontmatter；表格尽量不超过 4 列；代码块必须标注语言；不要使用脚注、HTML 块、Task List。对 OpenClaw 这类可编排工具，可以在 Agent 配置层加一个 `md-normalize` 处理器，而不是只靠提示词约束。

### 2. 解析为 AST，而不是正则

用 `unified` + `remark-parse`（或 `markdown-it`）把 Markdown 解析为 AST。不要用正则去删 `#`、`|` 或 ``` ``` ```，遇到嵌套列表、代码块里的表格符号、转义字符时正则很容易误伤。AST 层可以安全剥离 frontmatter、识别表格和代码块、统一换行。

### 3. 定义平台 profile

维护一个平台能力表，例如：

| 能力 | GitHub | 飞书 | 公众号 | 知乎 |
|------|--------|------|--------|------|
| 表格 | 支持 | 支持 | 弱 | 弱 |
| 代码块 | 支持 | 支持 | 支持但易截断 | 支持 |
| 脚注 | 支持 | 不支持 | 不支持 | 不支持 |
| 数学公式 | 部分 | 不支持 | 不支持 | 部分 |
| 相对图片 | 支持 | 不支持 | 不支持 | 不支持 |

每个 profile 声明“支持/降级/移除”策略。例如：表格不支持时降级为列表；图片相对路径在发布前替换为图床绝对 URL；脚注直接内联或删除。

### 4. 分平台渲染与后处理

- **GitHub**：保留 frontmatter 给 Jekyll/Hexo 使用，其余直接输出。
- **飞书**：去掉 HTML 标签，表格前补空行，代码块避免嵌套在复杂列表之后。
- **公众号**：表格转图片或列表，代码块控制行数，段间距用空行而不是 `<br>`。
- **知乎**：公式封装为知乎支持的格式，外链改短或改为引用说明。

这一步可以用插件机制：`platform/feishu.ts`、`platform/wechat.ts` 等，每个导出 `transform(ast, ctx)`。接入 MCP 发布工具时，发布前调用对应 profile。

## 踩坑点

- **微信公众号后台粘贴 Markdown 源码不会自动渲染**，需要先用“Markdown 转微信 HTML”再复制。不要直接把源码发给运营。
- **飞书文档的表格**在 Markdown 中可能被相邻列表吞掉，建议发布前在飞书侧做一次表格回归检查。
- **代码块语言标识**：部分平台对未知语言当作普通文本处理，不会报错，但高亮缺失。需要把语言映射到平台支持列表。
- **图片相对路径是最容易漏的**：AI 生成的 `![](./imgs/a.png)` 在本地渲染正常，推到远端平台时全部 404。应在管线里用统一图床替换成 `https://...`。
- **frontmatter 别直接发给非静态站点平台**，否则文章开头会出现 `---` 和 YAML 字段。
- **连续空行**：AI 有时输出多个空行，部分平台折叠，部分保留。归一化时把三个以上空行折叠为一个。

## 可复用建议

- 建一个 `markdown-pipeline` 仓库，把 profile 做成 YAML/JSON 配置，而不是散落在各脚本里。
- 为每个平台准备固定 fixture：输入一份带表格、代码块、脚注、相对图片、嵌套列表的样本，断言输出符合预期。这样新增平台或升级依赖时能快速回归。
- 发布动作与校验分离：先用转换器生成目标格式，再调用平台 API；发布后抓取返回内容 diff 一次，避免“显示结果”和“预期 Markdown”不一致。
- 如果使用 OpenClaw 的 Agent 流程，把 `md-normalize` 作为固定节点插入在“生成”和“发布”之间，不要在 Agent 内部同时做生成和格式调整，职责分开更容易调试。

## 总结

Markdown 管线不是把 AI 生成内容直接复制到各个平台，而是在生成之后加一个可观测、可测试、按平台 profile 转换的中间层。核心是：限制生成端、解析 AST、声明平台能力、统一后处理。对 OpenClaw/Agent/MCP 实践来说，这条管线能把“多平台发布”从一个易碎的人工操作，变成可复用、可回滚的自动化流程。
