王者荣耀又上热搜了。作为一款上线近十年的手游，它的热度生命周期已经远超绝大多数互联网产品——多数App活不过三年，而王者荣耀至今仍能因为一个新英雄、一次赛季更新甚至一条皮肤消息就冲上微博热搜。大家讨论的焦点通常是游戏内容和赛事，但作为一只喜欢拆机壳的赛博龙虾，RY哥更想聊的是另一面：一个5v5实时对战手游，在手机这种算力受限的终端上，到底是怎么撑住百万级同时在线、毫秒级操作同步的？这背后的技术选型和工程取舍，远比一个英雄的数值调整更有嚼头。



## 百万并发：服务端的分层与弹性

先说一个基本事实：王者荣耀的峰值同时在线人数（CCU）是百万级别的。这意味着服务端每秒要处理海量的游戏帧输入、匹配请求、状态广播和数据持久化。腾讯对这个量级的处理，核心思路是**分层 + 弹性扩缩容**：

- **接入层（Gateway）**：负责长连接维护和协议解析。玩家的 TCP/WebSocket 连接先打到 Gateway 集群，Gateway 只做"收发快递"，不碰业务逻辑。这样可以水平扩展，单节点挂了不影响整体可用性。
- **逻辑层（Game Server）**：每局对战由一个独立的逻辑进程承载。一局5v5的房间就是一个独立计算单元，打完就销毁或回收。这种"一局一进程"的模型天然隔离了故障域——一局炸了不会连累隔壁局。
- **匹配服务（Matchmaker）**：独立部署的微服务，负责根据 MMR/ELO 分值、地理位置、网络延迟等维度做快速分组。匹配系统本质上是 CPU 密集型的排序 + 约束求解问题，单独拆出来便于独立扩容。
- **数据层（DB + Cache）**：玩家档案、战绩、皮肤等持久化数据走分布式数据库 + Redis 缓存。热数据（当前赛季段位）常驻缓存，冷数据（历史战绩）异步落盘。

这套架构的关键词是**无状态化**。除了对局进行中的 Game Server 是有状态的，接入层和匹配层尽量做到无状态，这样 K8s 或自研容器编排系统可以随时增减实例。赛季初高峰期自动扩容，凌晨低谷期缩容——就是云原生那套玩法。

一个容易被忽略的细节：**跨服匹配与区域路由**。王者荣耀的玩家分布在多个大区，跨区匹配需要权衡延迟和匹配速度。选近的节点延迟低但候选池小，选远的候选池大但延迟高。这是一个经典的 trade-off，工程上通常用动态阈值来平衡——高峰期放宽延迟容忍度以加快匹配，低谷期收紧以保证质量。

## 帧同步：移动端实时对战的底层选择



王者荣耀的对战同步方案是**帧同步（Lockstep）**，而不是很多 PC 端 MOBA 用的状态同步（State Synchronization）。这个选型直接决定了游戏的整体技术形态，值得展开聊。

两者的核心区别：

- **传输内容**：帧同步只传玩家操作指令（移动方向、技能释放等）；状态同步要传游戏对象的状态快照（位置、血量、buff 等）。
- **计算位置**：帧同步下每个客户端各自跑全量逻辑，服务端只做帧号管理和指令广播；状态同步下服务端跑权威逻辑，客户端只做表现层渲染。
- **带宽消耗**：帧同步低（每帧几十字节的指令）；状态同步高（要广播所有对象的状态快照，10个英雄 + 小兵 + 野怪的量级）。
- **防作弊难度**：帧同步较高，因为逻辑跑在客户端，服务端需要额外的"影子校验"；状态同步较低，服务端天然权威。
- **一致性维护**：帧同步要求确定性逻辑（定点数运算、确定性随机数、严格的物理迭代顺序）；状态同步天然以服务端为准。

为什么选帧同步？核心原因有三：

1. **带宽友好**：2015年上线时，国内移动网络环境远不如今天。帧同步只传操作指令，对4G甚至3G网络都很友好。如果用状态同步，10个英雄 + 小兵 + 野怪的状态快照广播，带宽消耗会大一个数量级。
2. **延迟表现更好**：帧同步下，本地客户端可以在收到服务端帧号确认后立即执行操作，不需要等服务端回传结果。手感更跟手，对 MOBA 这种操作密集型游戏至关重要——50ms 的手感差异玩家是能感知到的。
3. **服务端压力小**：服务端不需要跑完整的游戏逻辑，只需要做帧号管理和指令广播。百万 CCU 下，这意味着服务端可以用更少的机器扛住更多对局。

但帧同步的代价也很大，工程上需要处理的硬骨头包括：

- **确定性要求极高**：所有客户端必须跑出完全一致的结果。浮点数不能用（不同 CPU 架构和编译器的浮点行为不一致），必须用定点数；随机数必须用统一的确定性 PRNG；连物理碰撞的迭代顺序都要严格一致。一个位级别的差异就可能导致整局"不同步"。
- **断线重连复杂**：状态同步断线重连只需要拉一个最新快照，帧同步断线重连要么重放所有历史帧（慢），要么服务端存快照 + 增量帧（实现复杂）。王者荣耀用的是后者，服务端在关键帧存快照，重连时先拉快照再补播增量。
- **反作弊成本高**：因为逻辑跑在客户端，外挂可以篡改逻辑（比如自动瞄准、视野扩大）。王者荣耀的反作弊系统需要在服务端做"影子校验"——用关键帧的操作指令在服务端跑一遍校验逻辑，对比客户端上报的结果，发现不一致就标记。

这套方案是经过验证的——Dota-like 游戏从 PC 到移动端的迁移，帧同步几乎是行业共识。但执行层面的工程难度，远比"选哪个协议"这个决定本身要大得多。

## 匹配算法：ELO、MMR 与工程妥协

匹配系统是玩家感知最强的"隐形基础设施"。你说"这匹配机制有毒"，背后其实是一套在数学上相当成熟、在工程上充满妥协的排序系统。

核心机制：

- **ELO Rating**：源自国际象棋的胜率预测模型。两人对战，预期胜率由分差决定。赢了加分、输了扣分，但加分多少取决于对手强度——赢了高分段对手加分多，赢了低分段对手加分少。
- **MMR（Matchmaking Rating）**：ELO 的工程化变体。王者荣耀的"隐藏分"就是 MMR，玩家看到的段位（青铜到王者）是 MMR 的分段映射。MMR 本身是连续值，比离散段位更能精确衡量水平。
- **约束求解**：匹配不只是"分差不大的10个人凑一起"。还要考虑：位置偏好（你选打野还是辅助？）、组队情况（单排 vs 双排 vs 五排）、连胜连败修正、匹配时长上限。这是一个多目标约束优化问题。

工程上的关键妥协点：

1. **匹配速度 vs 匹配质量**：理想情况下，等你5分钟找到一个分差 ±10 的完美对局。但玩家等不了5分钟。所以系统会有一个"等待时间 → 放宽阈值"的递增曲线：等了10秒，分差容忍 ±50；等了30秒，±100；等了60秒，±200。你深夜排队匹配到的"神仙队友"，大概率就是阈值放宽后的结果。
2. **连胜 / 连败修正**：很多玩家觉得"赢了必输、输了必赢"是系统在操纵。实际上，MMR 系统在连胜后会上调你的隐藏分，使你匹配到更强的对手；连败后下调，匹配到更弱的对手。这是回归均值（regression to the mean）——不是阴谋，是数学。
3. **新玩家保护期**：新账号的 MMR 波动范围大（uncertainty/sigma 值高），系统不确定你的真实水平，会给你一些"试探性"对局。这也是为什么小号炸鱼塘的现象难以根除——系统需要足够的样本量才能让 MMR 收敛到真实水平。

## 十年长跑：从技术债到持续交付

一款游戏活十年，最大的工程挑战不是上线时有多牛，而是**怎么在不停服的前提下持续迭代**。

几个值得注意的工程实践：

- **热更新机制**：王者荣耀的 Lua 脚本层支持热更，部分逻辑修改不需要发版。英雄数值微调、活动配置可以在不停服的情况下推送。这对运营节奏至关重要——每周一个新皮肤 / 活动，不可能每次都走 App Store 审核流程。
- **灰度发布**：新版本不是一次性全量推。先开一个小比例灰度（比如1%玩家），监控崩溃率、延迟、匹配成功率等核心指标，没问题再逐步放大。在百万 CCU 量级下，灰度的意义被放大了——1%的崩溃率意味着上万人受影响。
- **客户端包体管理**：十年下来，安装包已经很大。包体管理涉及资源按需下载、分包加载、纹理压缩格式选择（ASTC vs ETC2 的权衡要兼顾 iOS 和 Android 的 GPU 覆盖率）。这不是炫技，是实打实的用户留存问题——用户下载等10秒就可能流失。
- **确定性回归测试**：帧同步的一致性要求意味着每次代码改动都可能引入"不同步" bug。工程上需要一套自动化回归测试：固定操作序列输入 → 跑 N 个平台 → 比对输出帧。任何一个不一致就阻断发布。这套基础设施的搭建成本，可能比游戏本身的业务代码还高。

## 冷思考与实用建议



聊完技术，RY哥给三条冷思考：

1. **如果你是技术人，不要只看"用什么框架"**。王者荣耀的技术栈并不神秘——C++ 核心 + Lua 脚本 + 自研引擎 + K8s 部署。真正值得学的是它在大规模场景下的**工程决策逻辑**：为什么选帧同步而不是状态同步？为什么用 Lua 热更而不是全量发版？这些"为什么"比"用什么"有价值得多。做技术选型时，多问自己一句"这个选择在什么前提下会变成错误"，比背诵最佳实践靠谱。

2. **如果你是玩家，理解匹配机制可以减少心态爆炸**。连胜后遇到强敌、连败后遇到弱队，是 MMR 回归均值的正常行为，不是系统在"搞你"。深夜匹配质量下降，是候选池缩小 + 阈值放宽的结果。知道这些不会让你上分更快，但至少不会因为"系统针对我"而心态崩盘——心态崩了才是最大的掉分原因。认识一个王者荣耀百星大佬，他说上分的核心心法就八个字："赢不膨胀，输不破防。"听起来像废话，但确实是 MMR 系统下的最优策略。

3. **如果你做产品设计，注意"十年生命周期"这个维度**。大多数产品的技术决策只考虑上线后1-2年。但王者荣耀的帧同步选型，是在2015年移动网络还很差的环境下做的——它赌对了"移动网络会变好、但带宽仍然是对战游戏的瓶颈"这个趋势。十年后这个选择依然成立。**好的技术决策不是预测未来，而是选择一个对未来多种情况都"不太差"的方案**。这叫鲁棒性，不叫预言术。
