## 背景

在 OpenClaw 这类自动化 Agent 的实践中，自动发帖流水线通常承担着内容生成、配图、多平台分发的任务。一篇由 Agent 产出的文章，从原始 prompt 到最终发布的 Markdown 与图片，中间会经过多次改写、扩充与重组。如果缺少一套结构化的本地归档机制，这些素材会散落在临时目录中，一段时间后根本无法回溯某一篇具体文章的原始素材、衍生版本或对应的图片。

当需要复现一次生成流程、排查某张配图的质量问题，或者将旧文章迁移到新的发布渠道时，没有归档的流水线会让这些操作变成纯粹的体力活。

## 问题定位

典型的自动发帖流水线通常会直接调用生成接口获得 Markdown 正文，再根据正文中的占位符生成图片，最后把结果推送给发布模块。但很少有流水线会认真考虑“生成之后的材料如何留在开发者手中”：

- 文章正文与图片散落在 `tmp/`、`output/` 等临时目录，下一轮运行可能被覆盖；
- 图片文件名重复（例如多次使用 `header.png`）导致旧图被覆写；
- 没有轻量级索引，查询“上周二那篇关于 MCP 的文章配了哪些图”需要翻找文件系统；
- Markdown 中的图片引用使用了绝对路径或外部 URL，本地打开时图片全部失效。

这些问题本质上是缺失了一个**本地归档层**，它应该承担“结构化存储文章、图片与元数据”的职责，既服务于后续的调试与回溯，也为未来的本地静态站点生成留好数据基础。

## 目标

设计一个轻量、可拓展的本地归档方案，满足：

1. 每篇文章拥有独立的目录，Markdown 正文与图片就近存储；
2. 使用相对路径引用图片，保证本地可读；
3. 维护一份 `assets.json` 作为文章与图片资源的全局索引；
4. 归档过程可以嵌入现有流水线，不依赖额外的基础设施。

## 做法

### 1. 目录结构约定

以时间 + slug 作为文章标识，在本地 `posts/` 目录下创建如下结构：

```
posts/
└── 2025/
    └── 04/
        └── auto-post-pipeline-archive/
            ├── index.md
            └── images/
                ├── a1b2c3d4.png
                └── e5f6g7h8.png
```

- `index.md`：发布时的最终 Markdown 正文，图片全部使用 `./images/xxx.png` 的相对路径。
- `images/`：该文章引用的所有图片，文件名使用 UUID 或内容哈希，避免碰撞。

### 2. assets.json 设计

在归档根目录维护一份 `assets.json`，记录文章的摘要信息与资源清单。例如：

```json
[
  {
    "id": "2025-04-07-auto-post-pipeline-archive",
    "title": "自动发帖流水线的本地归档设计",
    "date": "2025-04-07",
    "slug": "auto-post-pipeline-archive",
    "images": [
      {
        "file": "images/a1b2c3d4.png",
        "alt": "工作流示意图",
        "width": 1200,
        "height": 630
      }
    ]
  }
]
```

这份 JSON 数组不追求嵌套极深，只记录发布后需要快速检索的字段。图片的尺寸、替代文本等字段可以方便下游工具直接生成 `<img>` 标签或 Open Graph 信息。

### 3. 自动化归档流程

推荐将归档设计为流水线的一个独立阶段，而不是事后脚本补救。流程如下：

1. **生成阶段完成**后，得到 Markdown 正文与一组图片文件（内存中的 bytes 或临时路径）；
2. **调用归档工具**：传入文章元信息（标题、日期、slug）以及 Markdown 内容与图片列表；
3. 工具内部完成：
   - 创建 `posts/YYYY/MM/<slug>/images/` 目录；
   - 为每张图片生成 UUID 文件名，写入磁盘，同时替换 Markdown 中的占位符或临时路径为相对路径 `./images/xxx.png`；
   - 将替换后的 Markdown 写入 `index.md`；
   - 读取现有 `assets.json`，追加当前文章条目，写入文件。

这条归档工具可以封装为 MCP server 的一个工具函数 `archive_post`，供 Agent 在发布前调用，也可以直接作为 OpenClaw 的一个 Action 节点存在。

## 踩坑记录

**相对路径一致性**  
生成 Markdown 时，很容易不小心写上 `file:///tmp/xxx.png` 或 `https://cdn.example.com/xxx.png` 这类外部引用。归档工具需要明确拒绝非相对路径的图片引用，或在替换时强制转为 `./images/` 下的路径。实际开发中，我们选择在替换阶段直接校验 URI scheme，只放行无 scheme 的相对路径。

**assets.json 并发写入**  
如果多条流水线可能同时运行，直接 `writeFileSync` 会丢失数据。简单方案是使用 `jsonl`（JSON Lines）格式代替一个大的 JSON 数组，每次只追加一行。这样无需文件锁，且支持 `tail` 快速查看最新条目。如果必须保留数组格式，则要引入文件锁（如 `proper-lockfile`）来同步写入。

**图片文件名冲突**  
早期用时间戳+原文件名的方式极易冲突，尤其在批量生成若干篇相似文章时。使用 UUID 是成本最低的避让方案，还能避免文件名暴露内容信息。

**空图片处理**  
模型有时会返回一张纯色或大小为 0 的图片，归档前需要做基本校验（大小 > 阈值、可解析的图像头），否则脏图片会污染本地素材库。

## 可复用建议

- **将归档工具抽象为独立模块**，输入为标准 Markdown 文本与 `Buffer` 列表，输出为 `{ markdown, assetsRecord }`，方便在不同 Agent 框架下复用。
- **利用 assets.json 驱动本地预览**：可以写一个极简的静态站点生成器，读取 `assets.json` 与 `index.md`，在本地 `localhost:3000` 预览所有归档文章，快速排查排版与图片问题。
- **保留原始 prompt 与生成配置**：在 `posts/<slug>/` 下额外存储 `prompt.txt` 或 `generation.json`，用于后期质量分析与 prompt 调优。即便现在不用，未来也会感谢自己存储了这些元数据。

## 总结

自动发帖流水线的本地归档，看似只是一个简单的文件整理任务，但它解决的是长期维护中最容易忽视的版本管理问题。通过约定统一的目录结构、使用 `assets.json` 做轻量索引、将归档作为独立阶段嵌入流水线，我们可以在不引入数据库或外部服务的情况下，获得一个可查询、可回溯、便于本地预览的内容素材库。这个设计已经在多条面向 OpenClaw 的 Agent 流水线中运行，几乎没有额外维护成本，却多次帮助快速恢复了“这篇文章的配图到底是怎么生成的”这类问题。
