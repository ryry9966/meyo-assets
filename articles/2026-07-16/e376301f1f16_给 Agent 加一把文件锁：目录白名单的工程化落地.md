## 背景：当 Agent 变成「匿名文件浏览器」

最近在用 OpenClaw 串联 MCP 工具链做自动化巡检时，踩了一个不大不小的坑——一个本应只读写 `/data/reports` 的脚本，因为依赖库的临时文件策略，悄悄在 `/tmp` 下创建了软链，最终把宿主机的敏感配置目录暴露给了下游插件。虽然最终没有造成实质影响，但这暴露了一个很容易被忽略的安全面：**我们往往只控制了 Agent 的意图，却很少约束其文件访问半径。**

不管是 MCP 的 `filesystem` server，还是自己写的本地工具插件，一旦交给 Agent 调用，就等于把文件系统的一部分操作权交了出去。如果没有明确的访问护栏，一条路径拼接错误、一个第三方库的临时文件行为，都会让 Agent 轻易越界。在工程化落地时，最务实的做法就是给自动化脚本加上**本地目录白名单**，让所有文件 IO 操作都在可控范围内完成。

## 问题建模：我们要约束什么？

从安全角度看，目标很明确：一个脚本进程只能读写白名单目录集合内的路径，其他路径（哪怕可读）也应拒绝。但工程上不能只靠文档约束，需要做到 technical enforcement。

现实中，脚本通常会通过以下渠道接触文件系统：

- 内置 `open()` / `os` 系列函数
- 第三方库（如 `json.load` 传入文件路径、`pandas.read_csv` 等）
- MCP 文件工具暴露的接口
- 动态执行环境（如 `eval`、`exec`，不过那是另一个话题）

因此，一个可靠的护栏不能只限制顶层调用，必须**拦截进程内的一切文件访问入口**，至少是 Python 侧的主流路径。

## 工程方案：基于路径规范函数 + Monkey-Patch 的白名单护栏

我们选择在 Python 脚本入口处，通过替换关键的内置函数来实现访问检查。基本思路：

1. 定义白名单目录列表（支持绝对路径）。
2. 实现一个路径检查函数：解析路径（使用 `os.path.realpath` 处理符号链接和相对路径），判断是否位于白名单目录树内。
3. 重写内置 `open()` 和 `os.open()`，在真正调用前做检查。
4. 考虑第三方库可能直接 C 扩展操作文件（极少），对多数数据分析工作负载，拦截 Python 层面的入口已足够。

示例实现：

```python
import os
import builtins

WHITELIST = ['/data/reports', '/opt/app/logs']

def _is_allowed(path: str) -> bool:
    real = os.path.realpath(os.path.abspath(path))
    for allowed in WHITELIST:
        allowed_real = os.path.realpath(allowed)
        if real.startswith(allowed_real + os.sep) or real == allowed_real:
            return True
    return False

def _safe_open(file, mode='r', *args, **kwargs):
    if _is_allowed(str(file)):
        return builtins._orig_open(file, mode, *args, **kwargs)
    raise PermissionError(f"Access denied to {file}")

# 保存原始 open
builtins._orig_open = builtins.open
builtins.open = _safe_open
```

同理可以覆盖 `os.open`。如果在 MCP server 内使用，可以在 server 启动后立刻注入，以防早期调用绕过。

## 踩坑记录

### 1. 符号链接和 `..` 穿越
不要用 `os.path.abspath` 直接比较字符串。必须 `realpath` 解析到底，否则一个形如 `/data/reports/../../etc/passwd` 的路径就能绕过前缀匹配。同时注意 `realpath` 会触发文件存在性检查，如果文件不存在，`realpath` 仍能解析符号链接直到最后的路径段（即最后一段不做存在验证）。这在大多数场景下是可接受的：企图访问 `/data/reports/nonexistent/../../secret` 会被解析为 `/data/secret` 并拒绝。但如果你有允许创建新文件的需求，需要用 `os.path.normpath` 结合目录存在的部分判断。我们的做法是，对于写模式，先用 `os.path.dirname` 的 `realpath` 做父目录检查，确保不会通过不存在的中间路径绕过。

### 2. 相对路径的「锚点」
`open('report.csv')` 没有绝对路径，会依赖当前工作目录。你需要明确检查 `os.getcwd()` 是否在白名单内，还是在解析时将相对路径与工作目录拼接。**更稳妥的做法是：始终在 `_is_allowed` 内，如果传入路径不是绝对路径，就与 `os.getcwd()` 拼接后再解析。** 这样，即便后续工作目录被修改，检查依然基于当前进程环境，防止动态 `chdir` 造成的误判。

### 3. 第三方库的「隐蔽文件操作」
Pandas 的 `read_csv` 内部调用 `open()`，因此猴子补丁对其生效。但如果是用 `os.system('cat ...')` 或 `subprocess` 调用外部命令，护栏完全被绕过。如果脚本内有子进程调用，必须对命令参数做同样白名单检查，或者直接禁止子进程。在我们的场景中，Agent 脚本不允许 `subprocess` 调用，这也作为整体安全策略的一部分。

### 4. 临时文件目录
很多时候脚本需要写入临时文件。一种做法是将系统临时目录 `/tmp` 也加入白名单，但这等于开了一个口子。我们的解决方法是：在脚本启动时创建专用临时目录（如 `/data/reports/.tmp`）并加入白名单，同时设置环境变量 `TMPDIR` 指向它，让 `tempfile` 模块自动使用。这样既满足需求，又不暴露系统 `/tmp`。

## 可复用建议

**1. 以装饰器或上下文管理器形式提供**  
封装成一个 `DirectoryScope` 上下文管理器，进入时注入补丁，退出时恢复，便于在不同脚本中复用且不污染全局。

**2. 白名单配置外部化**  
使用环境变量或配置文件指定白名单，避免硬编码。配合 Agent 部署工具，可以在编排时动态注入任务专属目录。

**3. 提供审计日志**  
在拒绝访问时，不仅抛出异常，同时记录完整调用栈到日志中。这能帮助发现脚本试图访问的非预期路径，可能是配置错误或依赖库的隐式行为。

**4. 不要忘记 `os.listdir`、`glob` 等遍历操作**  
如果使用 `os.scandir` 或 `glob` 返回了白名单外的路径，需要过滤。一个轻量的做法是重写 `os.scandir`，过滤结果中的子项，但实现成本较高。在我们的实践中，这类操作通常仅用于白名单内部，因此暂时仅保护文件打开，遍历操作通过代码约定保证。

**5. 单元测试检查绕过**  
写几个针对符号链接、`..`、绝对/相对路径、不存在的文件等场景的单元测试，确保护栏健壮性。这些测试也能作为文档，展示哪些行为是被阻止的。

## 总结

给 Agent 脚本加目录白名单不是一个防黑客的高强度沙箱（那是容器和 seccomp 的活），而是**工程上约束自动化行为的第一道围墙**。它可以避免大量无心之失：日志文件写错目录、缓存误删、配置文件误读等。在 OpenClaw 这种高度自动化的环境下，这样做并不会增加太多开销，却能显著降低放飞自我后的排查成本。

在真正的安全隔离层面，你还应该结合容器化、只读根文件系统和 seccomp 等措施。但如果你只是想让一个预定任务「老老实实待在它的目录里」，上述基于猴子补丁的白名单方案，足以用几十行代码提供可靠的访问护栏。
