在 Agent 流程、插件开发或 OpenClaw-CN 这类自动化实践里，我们经常需要 LLM 输出结构化内容：解析邮件、提取摘要、生成报告、编排多步操作。JSON 看起来是最自然的选择——几乎所有语言都能直接解析，schema 清晰，生态完善。但如果你试过让模型生成超过 500 字的嵌套 JSON，大概率遇到过这类令人头疼的问题：

- 输出被意外截断，括号没有闭合，`json.loads()` 直接抛异常；
- 字段里多了一个逗号、少了一个引号，导致整个对象反序列化失败；
- 模型在字符串中混入未转义的特殊字符，修复成本高；
- 更糟的是，看似合法的 JSON 实际上字段含义偏移，测试环境未必发现。

这些问题在长文本、多字段、含自然语言片段的场景下尤为突出。LLM 是自回归的，它在生成 JSON 时必须时刻维持括号栈、逗号状态、引号转义等全局约束，一旦输出长度增加，注意力分散，错误率就会上升。对工程实践来说，我们需要一种结构性足够、但对出错更宽容的输出格式。回到简单明了的标签体系，往往能有效降低解析失败的概率。

## 问题：JSON 在 LLM 输出中的脆弱性

以下几点是导致 JSON 输出不稳定的关键原因：

1. **上下文长度与注意力衰减**：当模型需要生成长 JSON 时，开头的 `{` 与结尾的 `}` 可能间隔上千个 token，每一步都在预测下一个字符，括号闭合错误的风险线性增大。
2. **嵌套深、字段多**：多层嵌套对象或数组，对逗号、引号的正确放置要求极严，一处断裂全局无效。
3. **截断灾难**：如果 `max_tokens` 设置不当或中途触发截断，得到的 JSON 几乎无法自动修复。
4. **修复成本高**：常见的 auto-fix 方法（如用 stack 补括号、用 lib 尝试修复）在长文本上并不可靠，甚至会引入更隐蔽的语义错误。

Agent 或插件流程中，如果 JSON 解析失败，通常只能让 LLM 重新生成，但重试不仅消耗 token，而且没有根本性保证下一次就会成功。如果连续失败，工作流直接中断，影响用户体验。

## 做法：用标签格式代替 JSON 承载结构化输出

**核心思路**是放弃严格 JSON 语法，改用自定义 XML/HTML 风格的标签来分段和结构化信息。例如，原来期望的 JSON：

```json
{
  "summary": "会议讨论了...",
  "action_items": [
    {"assignee": "张三", "task": "更新文档", "deadline": "2025-04-01"},
    {"assignee": "李四", "task": "联系供应商", "deadline": "2025-04-03"}
  ]
}
```

改为标签格式：

```
<summary>
会议讨论了版本发布计划与风险项……
</summary>
<action_items>
- 张三｜更新文档｜2025-04-01
- 李四｜联系供应商｜2025-04-03
</action_items>
```

解析时，我们不再依赖 JSON 解析器，而是用简单的正则或栈式标签匹配：

```python
import re

def extract_tag(content: str, tag: str) -> str:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    match = re.search(pattern, content, re.DOTALL)
    return match.group(1).strip() if match else ""
```

如果需要列表结构，让模型输出 Markdown 表格或竖线分隔的行，再在代码端拆分即可。你会发现，即使输出被截断，只要标签是闭合的，就能提取到部分有效信息；即使部分标签缺失，仍可回退策略。

### Prompt 调整步骤

1. **用示例明确格式**：在 system prompt 或 few-shot 中展示完整示例，强调「使用标签包裹内容，不要输出 JSON」。
2. **约束标签名**：提前定义好合法标签，避免模型自行发明。例如：`<thought>`、`<result>`、`<error>`、`<steps>`。
3. **处理特殊字符**：要求模型对标签本身的 `<`、`>` 进行转义（如使用 `&lt;`），或者约定内容中不得出现与标签同名的未转义符号。实践中很少遇到，因为标签名可设计为不太常见的组合。
4. **解析时做防御**：采用非贪婪匹配 `.*?`，并在捕获不到内容时提供默认值，避免单个标签缺失导致整体流程崩溃。

## 踩坑点与应对

- **标签名冲突**：模型可能在自然语言描述中使用了与标签同名的词，比如描述“步骤”时说「下一步骤是发布」，如果 `<step>` 是标签，就容易被误捕获。解决方案：给标签加特殊前缀，如 `!step` 或使用自封闭特性，或者在内容中要求模型显式转义。
- **嵌套情况**：如果仍然需要嵌套信息，简单的正则就不够了。可以引入轻量的堆栈解析，但更建议在 prompt 中避免嵌套，使用平铺结构。例如不要 `<parent><child></child></parent>`，而是用 `<parent>` 和独立的 `<child id="1">` 再通过 id 关联。
- **模型不爱遵守格式**：有时模型会混合输出 JSON 和标签，或擅自添加代码块标记。可以在后处理阶段先用多个正则容错提取：如果检测到 JSON，尝试解析后备；如果检测到标签，用标签逻辑；如果都没有，触发重试。
- **截断仍可能发生**：标签格式的优势是**部分可解析**。比如全文末尾缺失了 `</summary>`，那我们可以捕获到已经完整生成的其他标签，并标注 summary 缺失。这往往比 JSON 的“全毁”好得多。

## 可复用建议

- **建立统一的标签 schema**：为你的 Agent 或插件定义标准输出标签，每次需求不同就复用，形成内部约定。这有助于写通用解析器和监控。
- **配合 validator 做两层校验**：先用标签提取，再对每个字段做类型校验（如日期格式、枚举值）。这样既保证鲁棒，又不失结构化校验。
- **提供轻量解析库**：写一个 `TagParser` 类，实现 `get_string(tag)`, `get_list(tag)`, `get_dict(tag)`，内部封装正则和容错。后续所有 LLM 输出都用同一套解析，降低维护成本。
- **结合少量重试**：如果标签提取失败或关键字段缺失，才让 LLM 仅重试那一段，而不是全篇。可以设计标签级重试机制，比如缺失 action_items 时，prompt 追加「请完善 action_items 标签的内容」。
- **性能对比**：如果你在做输出稳定性优化，可以留统计：同一批任务下 JSON 模式 vs 标签模式的解析成功率、重试次数。多数情况下，标签模式能将解析成功率提升至 95% 以上，显著减少中断。

## 总结

在 LLM 长文输出的工程化实践中，盲目追求 JSON 的“标准”往往带来更多崩溃和不必要的重试。标签格式利用 LLM 更容易维持的局部一致性，允许部分失败而不整体无效，容错性更好。它不是银弹，对于强类型、深层嵌套、需要交给下游系统直接消费的复杂 schema，可能仍需 JSON 和后处理工具。但对于 Agent、内部自动化、报告生成等场景，结构简单、对容错要求高的输出，标签格式是一套务实、低维护成本的方案。与其花精力写复杂的 JSON 修复器，不如从一开始就让模型输出更宽容的结构。
