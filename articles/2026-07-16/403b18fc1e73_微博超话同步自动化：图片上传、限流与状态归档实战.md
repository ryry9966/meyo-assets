## 背景

维护多个技术超话时，每天需要将同一份长文手动搬运到不同超话社区，包括提炼摘要、上传配图、粘贴话题标签，过程机械且容易遗忘。我们已经在本地用 Markdown 管理所有待发布内容，借助 OpenClaw 的自动化能力，可以构建一条完整的内容同步管线，自动完成发帖、图片上传、错误重试和状态记录。

本文记录一条轻量级的微博超话同步实践，重点不在于「黑科技突破」，而在于工程化地处理图片上传、请求限流和任务归档这三件容易翻车的环节。

## 整体设计

管线分为四个核心模块：

1. **内容输入**：遍历本地 Markdown 目录，提取待发布文章的标题、摘要、正文前 140 字以及引用的本地图片路径。
2. **媒体准备**：压缩并上传图片到微博图床，返回 `pid` 列表。
3. **发帖执行**：携带超话 `topic_id`、文本内容和图片 `pid` 调用发帖接口，内置频率控制与错误重试。
4. **状态归档**：使用 SQLite 记录每次发帖的来源文件哈希、发布时间、微博 ID 和状态，避免重复发布。

整个调度由 OpenClaw 的定时任务驱动，每天固定时间扫描新内容并自动同步，异常情况通过日志告警。

## 图片上传：绕过踩坑点

微博图片上传接口虽然结构简单，但稳定性差。主要接口为 `/aj/static/upimg` 或旧版 `picupload` 服务，需要构造 `multipart/form-data` 请求并携带有效 cookie（`SUB`）。

```
POST https://picupload.weibo.com/interface/pic_upload.php
Content-Type: multipart/form-data; boundary=...
```

**踩坑记录**：

- **上传域名被屏蔽或限速**：部分服务器或代理环境下 `picupload.weibo.com` 偶发超时，返回空 `pid`。解决方案是内置多个备用上传通道，例如 `ws.sinaimg.cn` 相关上传点，并实现失败自动切换。
- **图片格式与大小限制**：接口仅接收 JPG/PNG，且文件大小建议在 5MB 以内，否则极易触发无意义错误码。我们通过 Pillow 在上传前统一将图片转为 JPEG，质量设为 85，并等比缩放长边到 1280px。
- **返回码解析**：上传成功会返回形如 `{"code":"1","data":{"pics":{"pic_1":{"pid":"006bVH3lgy1h..."}}}}` 的 JSON，但部分旧格式会用 HTML 包裹，必须兼容正则提取。

重试策略采用指数退避，最多尝试 3 次，每次退避 5s、15s、30s。

## 发帖与限流

发帖接口需要预先获取超话的 `topic_id`，可通过搜索接口或页面抓取。发帖请求大致为：

```
POST https://weibo.com/aj/mblog/add?ajwvr=6
Content-Type: application/x-www-form-urlencoded

text=摘要+#话题#&pic_ids=pid1,pid2&topic_id=1022:...
```

**限流处理**：

- 微博对单账号发帖频率有严格限制，通常一小时不超过 10 条，短时间高频会触发 `100005` 或 `100001` 错误。
- 我们使用令牌桶实现本地限流器，设置每 120 秒允许通过一次请求。当请求返回频率限制错误时，自动暂停 5 分钟，并将当前任务标记为 `retry`。
- 特别注意，限流不仅基于账号，还可能绑定 IP。若使用固定出口 IP，多账号并发也容易被识别，需要为不同账号分配独立的时间窗口。

## 状态归档

为避免重复发布同一篇文章，每次发帖前计算 Markdown 文件内容哈希（SHA256），存入 SQLite 表：

```sql
CREATE TABLE IF NOT EXISTS post_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_file TEXT NOT NULL,
    content_hash TEXT NOT NULL,
    posted_at TEXT,
    weibo_id TEXT,
    status TEXT DEFAULT 'pending'
);
```

流程：

1. 扫描文件并计算哈希，查询是否已有 `status='success'` 的记录，若有则跳过。
2. 发帖成功后，用返回的微博 ID 更新 `weibo_id` 并将 `status` 改为 `success`。
3. 失败时设为 `failed`，记录错误信息，便于后续人工补发或自动重试。

由于微博发布后可能进入审核状态（返回成功但实际不可见），我们会延迟 3 分钟后通过微博 API 查询 `weibo_id` 是否可访问，若 404 则标记为 `review`，提醒人工确认。

## 可复用建议

- **封装为 OpenClaw Tool**：将整个发帖功能封装成一个 Tool 或 MCP Server，暴露 `post_to_supertopic(content, image_paths, topic)` 接口，其他 Agent 可直接调用。
- **dry-run 模式**：正式发布前支持预览生成的文本和图片链接，打印而不实际请求。
- **配置与密钥管理**：Cookie 和超话 ID 等敏感信息存入环境变量或 `config.yaml`，避免硬编码。
- **监控**：异常次数超过阈值时通过 Webhook 发送通知，避免断更无人知晓。

## 总结

这不算一个酷炫的项目，但它是那种「做好以后可以长期遗忘」的自动化基础设施。核心挑战不在于逆向接口，而在于图片上传的鲁棒性、限流的温和退避，以及状态归档的可靠性。在 OpenClaw 环境下，这些模块很容易与其他内容发布管线组合，真正做到一次写作，多端同步。
