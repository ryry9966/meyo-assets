## 背景

在 OpenClaw 插件和 Agent 链路中，让 LLM 输出结构化数据是一个高频需求。比如自动生成一篇技术博客的章节与正文、提取长文档的摘要和关键点、或者按模板组装一份分析报告。开发者第一反应往往是要求模型输出 JSON——标准化、生态工具多、看起来“就应该是这样”。

但当内容变长、嵌套变深、字段里塞进大段 Markdown 或代码块时，JSON 就成了不稳定性的放大器。截断的字符串、未转义的双引号、多行文本里意外出现的逗号或方括号，随便一个都能让 `JSON.parse()` 直接抛异常，整个输出报废。在需要流式推送中间结果的场景下，JSON 解析器更是无从下手。

## 问题不是模型不够好，是约束本身就是坑

我们踩过的典型坑包括：

- 长篇正文里含有自然语言中的双引号，模型忘了转义，导致整段 JSON 解析失败。
- 输出超过 `max_tokens` 时截断在一个对象中间，比如数组的最后一个元素还没闭合，`]` 永远等不到。
- 模型在 JSON 前后附加解释性文字，比如“好的，下面是 JSON：```json …”，即便用 system prompt 强调“只输出纯净 JSON”，在长上下文下仍会偶尔复发。
- 嵌套对象中的多段落文本需要严格换行控制，否则 JSON 解析器报错，但模型天然擅长写出流畅的多行内容。
- 流式返回时，必须等整个 JSON 都到齐才能做反序列化，上游只能干等，无法边生成边消费。

你可能会想到用 `json_mode` 或约束采样，但这些手段只能确保语法正确，并不能保证内容不截断、不跑偏。而且当需要输出长文本段落时，强制语法约束反而可能让模型变得局促，导致文风生硬或提前终止。

## 转向标签格式：放弃完美解析，换取工程容错性

我们尝试了另一种思路：用**自定义标签**来界定结构区块，类似轻量级 XML 但更宽松。核心思想是——把“解析器是否存活”与“内容是否完整”解耦。

以一个生成技术文章的场景为例，我们设计了一套标签：

```
<|doc|>
<|title|>安全地关闭 LLM 输出<|/title|>
<|abstract|>短摘要……<|/abstract|>
<|sections|>
<|section|>
<|heading|>为什么 JSON 不行<|/heading|>
<|content|>
这里写大段 Markdown，可以随意换行，
包含代码块，甚至写下标记本身只要转义成 <|lt|>
<|/content|>
<|/section|>
<|/sections|>
<|/doc|>
```

在 system prompt 里明确给出这个模板，并强调：

> 请严格使用上述标签结构，不要输出任何额外 JSON 或解释文字。内容中如必须出现 `<|` 或 `|>`，请替换为 `<|lt|>` 或类似的占位符。

解析端使用一个简单的状态机或正则，按开始/结束标签切分字符串，匹配失败时还可以做降级处理：例如缺失 `</|doc|>` 闭合，就取最后遇到的标签内容作为结束。对比 JSON，这种“部分成功”的特性在长文生成时价值巨大。

## 实践步骤

1. **设计标签集**：选择一组不容易与正文内容冲突的符号，如 `<|tag|> </|tag|>` 或 `<<<tag>>> <<</tag>>>`。最好加上命名空间前缀避免与现有标记语言冲突（例如 `<|oc_section|>`）。
2. **编写提示词**：在 system 或 user prompt 里放置一个“输出格式示例”，同时声明标签内容的自由度和转义规则。对于必选、可选标签加以说明，并用具体内容演示。
3. **实现解析函数**：  
   - 先用正则去掉可能包裹的外层三引号或无关前缀，定位第一个 `</?<\|` 或自定义标签。  
   - 按顺序扫描标签，将中间的内容存入有序列表或字典。  
   - 对于没有闭合的标签，可从起始标签后截取到底，标记为 incomplete，供下游决定是否使用。  
4. **流式适配**：标签相比 JSON 的优势在于，只要检测到闭合标签，就可以立即把已缓冲的段落推向下游，不必等待全部输出完成。这对实时展示标题、逐段渲染文章非常实用。
5. **容错脚本**：针对常见异常编写修复逻辑，比如模型习惯性在末尾加一个句号或空行，可以自动 trim；如果多个标签嵌套错误，可用栈匹配矫正部分结构。

## 真实踩坑与规避

- **模型把标签本身当作文本输出**：尤其是一些指令遵循稍弱的模型，会输出“<|title|>标题<|/title|>”以外还附赠 “这是文章标题：” 之类的文字。解决办法是提高标签的“异样性”并降低温度，同时解析端支持跳过标签前的任意文本，只提取第一个有效标签块。
- **内容里意外出现分隔符**：即便标签很怪，长文本仍可能撞上。除了做转义约定，也可在解析时检查标签内容中是否包含下一条开始标签，若发现，将该内容视为非法并做修复（如合并）。另一种做法是要求模型对内容使用 base64 编码，但这会牺牲可读性，仅适合非人类可读的场景。
- **解析性能**：简单正则在大文本上表现不错，但如果有非常多的嵌套章节，建议使用 streaming XML 解析器并配合自定义实体。不过标签格式的精髓正是控制复杂度，不建议嵌套超过两层。
- **下游仍需要 JSON**：没问题。解析标签得到结构化数据后，在本地再组装成 JSON。这样模型的输出不直接承担 JSON 语法责任，所有容错在标签层完成。

## 可复用建议

- 把标签约定沉淀为项目内部的“结构化交换格式”，并附几个语言的解析模块（Python/JS），减少重复造轮子。
- 在 Agent 的 MCP 工具里，如果返回给 LLM 进一步处理，可以同时保留标签格式和解析后的 JSON，供不同链路选择。
- 测试模型时，可以刻意制造截断场景，验证解析器的降级能力，确保不会因一个缺失的结束标签而丢失所有信息。
- 对于需要严格 schema 校验的场景，在标签解析后执行 JSON Schema 验证，把校验失败的原因反馈给模型进行二次修正，而不是直接让模型输出 JSON 赌运气。

## 总结

从 JSON 转向标签格式，本质上是一种工程上的务实妥协：承认 LLM 不擅长生成严格语法的长文本，转而用更宽容、更易流式提取的自定义标记来承载结构信息。在我们的 OpenClaw 插件和自动化管线中，这个改变让长文输出的解析成功率从之前的约 75% 提升到 98% 以上，流式表现也更平稳。

如果你的 Agent 也在为 JSON 截断、转义、多余解释文字而头疼，不妨试试抛开对 JSON 的执念，给自己设计一组切合业务的标签语汇。很多时候，一个“不标准”的格式，反而是最稳定的约定。
