## 背景

运营超话需要保持一定的内容密度，但手动发帖会消耗大量碎片化时间——选图、压缩、添加话题、检查是否发送成功，重复操作几十次后，很容易漏发或错发。我们希望在 OpenClaw 这类 Agent 编排环境下，用一套可控的自动化管线解决这些问题：素材准备好后，由工具链完成图片上传、文案组装、发布及状态记录，人工只做最终审核或完全托管。

但在微博生态下直接调用公开 API 或模拟请求，会立刻碰到三类工程问题：**图片上传的限制**、**接口频率控制（限流/风控）**、以及**失败与成功的状态持久化**。下面围绕这三块，给出我们在 OpenClaw 下用 MCP 工具实现“微博超话同步器”的做法和踩坑记录。

## 问题拆解

1. **图片上传不可靠**  
   微博开放平台上传接口 `https://upload.api.weibo.com/2/statuses/upload.json` 对格式、大小、请求头有严格校验。直接使用 `requests` 或 `fetch` 很容易因为缺少关键 Header 或文件 MIME 类型错误而被拒绝。同时获取到的 `pic_id` 有时会因 session 状态问题在后续发微博时不生效，需要重新上传。

2. **频率限制与风控**  
   发微博接口（`statuses/update`）有基于用户维度的调用频率限制，通常为 10 次/分钟（个人应用级），短时间内密集请求会触发 10023/10024 等错，甚至导致账号临时封禁。另有多层反爬机制，对请求时序、`User-Agent`、`Referer` 有隐性要求。

3. **状态归档缺失**  
   自动化运行期间可能出现网络抖动、token 过期、部分图片上传成功但发布失败等情况。如果没有落地的状态记录，只能猜当前进度，重复发帖或丢失素材。

## 实现做法

我们选择给 OpenClaw 扩展一个本地 MCP 服务器（使用 `@anthropic/mcp` 的 Python SDK），暴露两个工具：

- `upload_weibo_image`：接收本地图片路径，处理后返回可用的 `pic_id` 和对应元数据。
- `post_weibo_with_images`：接收文案、超话名、`pic_id` 列表，拼接话题并发布，返回微博 ID 和发布时间。

MCP 工具内部并不是直接调微博 SDK，而是基于 `httpx` 会话封装了完整的请求签名与头部模拟，以绕过部分限制。整体作业步骤：

1. **准备阶段**  
   - 将待发图片统一调整到 5MB 以下，且仅保留 JPEG/PNG 格式，避免 GIF 在第一帧静止时被误判为无效。  
   - 从环境变量或本地 TOML 配置中读取微博应用的 `access_token`（提前通过 OAuth 授权获得，并设置了自动刷新）。

2. **图片上传流程**  
   - 构造 multipart 请求，显式指定 `Content-Type: multipart/form-data`，并带上 `User-Agent: WeiboOAuth2/2.0` 以及 `Referer` 为应用回调域。  
   - 对返回的 `pic_id` 立即做一次有效性验证：用 `statuses/querymid` 接口尝试关联，或本地进行格式校验（长度为 32 位十六进制）。若无效则重试，最多 2 次。  
   - 上传成功后记录 `task_id + image_path -> pic_id` 的映射到 SQLite 表中，防止重复上传同素材。

3. **发布与限流控制**  
   - 所有发帖任务进入基于 `asyncio.Queue` 的队列，一个固定的 Worker 协程以 8 秒/条的节奏消费。这保证了每分钟不会超过 7 篇，给自己留足缓冲。  
   - 遇到限流错误（HTTP 429 或 Weibo 错误码 10023），Worker 执行指数退避：1s → 4s → 16s → 64s，超过 5 次失败则标记任务为 `blocked`，并推送通知到管理员。  
   - 文案中自动拼接 `#超级话题名#` 和分隔符，避免跨话题混用。

4. **状态归档与幂等**  
   - 用一张 `post_log` 表记录每条帖子的：`schedule_time`、`image_task_ids`、`weibo_id`、`status (pending/sent/failed/blocked)`。  
   - 每次 Worker 启动时先查询 `pending` 且 `schedule_time <= now` 的任务，不会重复发同一批次。  
   - 对于上传成功但发布失败的任务，支持人工修改状态为 `pending` 重试，或直接丢弃。

## 踩坑点

- **图片上传 400 错误但没有具体说明**  
  最终发现是因为 `pic` 字段名必须用小写，并且文件流不能带 `Content-Type` 子头（让库自动生成）。如果使用 Python `requests` 的 `files` 参数，需要以 `('pic', (filename, f, 'application/octet-stream'))` 方式传递，而不能用自定义 MIME。  
- **pic_id 失效谜之现象**  
  `pic_id` 上传成功后，如果间隔超过 30 分钟再发帖，图片大概率变成裂图。解决方法是上传与发帖保持在同一 session 有效期内，并尽可能缩短间隔（队列延迟不要超过 15 分钟）。  
- **风控触发点不只是频率**  
  连续发布文案高度相似的帖子（例如只有序号不同）也会被静默限制。引入轻微随机扰动：在文案末尾或超话后添加不可见的零宽空格（U+200B），或给每条加上不同的短句模版，可有效降低风控命中率。  
- **Token 刷新逻辑**  
  微博 Access Token 有效期为 24 小时，必须实现自动刷新。在 MCP 工具中，每次调用前检查过期时间，若剩余不足 5 分钟则同步刷新，并将新 token 回写到本地文件，供后续进程共享。

## 可复用建议

1. **将微博操作封装为 MCP 工具是正确方向**  
   Agent 只需要看到“上传图片”“发布帖子”这两个语义，不必关心签名、重试、排队。未来替换为其他平台（如小红书、B站）时，只需实现相同的 tool schema。

2. **状态外置、异步归档**  
   不要依赖 Agent 的记忆。所有进度写入 SQLite/Redis，这样 OpenClaw 挂掉重启也不影响任务继续。

3. **本地素材预处理流水线**  
   可结合 ImageMagick 或 sharp 在 MCP 工具内对图片进行自动压缩、加水印、尺寸调整，将合规性问题前置，而不是等到上传时才报错。

4. **监控与人工接管接口**  
   在 post_log 中添加 `review` 状态，配合一个简单的 Web 面板（可根据 MCP 工具提供的资源接口暴露），让运营同事在批量发布前可以预览图文，通过勾选后才进入队列，安全系数大幅提升。

## 总结

微博超话同步并不是一个简单的“调个 API” 就能解决的问题，真正的工程量在于处理上传的坑、设计平滑的限流退避，以及让自动化过程可观测、可恢复。利用 OpenClaw 的 MCP 工具做界面封装，搭建一个健壮的发布管道后，每日数十篇超话帖都可以做到无人值守。上述实践不仅适用于微博，类似架构可以平滑迁移到其他需要复杂交互与风控对抗的平台自动化场景下。
