## 背景

在 OpenClaw 中搭建自动化流程时，定时触发器是最常用的组件之一。常见的场景是：每 5 分钟拉取一次外部 API 数据、每隔一段时间清理过期日志，或者周期性调用 Agent 做批量处理。一切看起来都很美好，直到某天你发现：下游数据突然出现重复写入，Agent 处理队列里冒出两条一模一样的任务，甚至看到“锁等待超时”这种不该出现的错误。

**根本原因只有一个：任务的实际执行时间，超过了 Cron 间隔。**

举个例子：你设定了一个 `*/5 * * * *` 的触发规则，期望每 5 分钟运行一次。但某次运行因为网络抖动或处理数据量增加，实际耗时 6 分半。第 6 分钟时，第二次触发来了，而上一次还没结束——两辆车挤进了单行道，开始“撞车”。在工程上，这叫作**任务重入（Re-entry）**。

## 问题分析：为什么 OpenClaw 没拦住它？

很多自动化和低代码平台，包括 OpenClaw，在定时触发器层面并不会检查上一轮实例是否还在执行。它们的设计理念是：“到了时间就点火”，而不负责判断跑道上是否还有未起飞的航班。这是合理的设计，因为是否允许并发执行本是业务决策，不应由引擎一刀切。

但如果你没有显式采用防重入手段，这种并发就会无声无息地出现。典型症状包括：

- 日志里出现两条相同 ID 的处理记录，时间相差几分钟。
- 对同一资源（文件、数据库行、API 限流窗口）并发修改，导致状态错乱。
- 依赖外部系统的操作被重复提交，比如发了两封相同的邮件或重复扣款。

更隐蔽的是，当任务执行时间在大部分情况下都小于间隔时，这种碰撞只在极少数超时场景发生，极难复现。很多团队直到线上出现数据异常才开始排查，而这时已经错过了最佳的防御窗口。

## 做法 / 实施步骤

在 OpenClaw 中杜绝重入，核心思路是为每个定时任务引入**分布式锁**——执行前尝试拿锁，执行后释放；拿不到锁就直接退出本次触发。

### 第 1 步：量化任务执行时长

别靠感觉。先让流程输出每个步骤的耗时日志，统计多次运行的实际耗时分布。可以从 OpenClaw 的执行历史里找到峰值和 P99 值。这个数字会决定锁的超时时间。

### 第 2 步：选择锁的实现方式

OpenClaw 默认没有内置全局锁功能，但可以通过它的代码节点或外部存储配合实现。推荐两种工程化方式：

**方案 A：基于 Redis 的分布式锁（推荐）**

优点：响应快、超时机制天然支持、跨 Worker 有效。若你的 OpenClaw 实例已经有 Redis 连接，直接复用。

示例伪代码（Python 代码节点中使用 redis-py）：

```python
import redis
import time

LOCK_KEY = "task:my_job:lock"
LOCK_TIMEOUT = 600  # 锁有效期 10 分钟，需大于任务最大执行时间

r = redis.Redis(host='redis-host', decode_responses=True)

# 尝试获取锁
acquired = r.set(LOCK_KEY, "running", nx=True, ex=LOCK_TIMEOUT)
if not acquired:
    print("上一轮任务仍在执行，本轮跳过")
    return

try:
    # 这里是你的业务逻辑
    do_actual_work()
finally:
    # 关键：释放锁，需要原子化（用 Lua 脚本）
    release_script = """
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
    else
        return 0
    end
    """
    r.eval(release_script, 1, LOCK_KEY, "running")
```

**方案 B：基于数据库的乐观标记**

如果没有 Redis，可以在业务库中维护一张 `task_locks` 表，用唯一键约束防止重复插入记录。适合执行频率不高（分钟级）的场景。

```sql
INSERT INTO task_locks (task_name, locked_at) VALUES ('my_job', NOW());
-- 若插入失败（主键冲突），说明已有锁，则退出
```

### 第 3 步：超时与死锁保护

锁必须有过期时间，并且这个时间**至少是任务最大执行时长的 1.5 倍**。我曾踩过一个坑：以为任务最多跑 5 分钟，就设了 300 秒过期。一次数据库慢查询导致任务耗时翻倍，锁提前过期，第二台 Worker 以为没锁就成功抢到，于是三车并发，数据乱得一塌糊涂。

释放锁时绝对不能简单 `DEL key`，因为可能你的锁已经过期且被其他实例拿走了，你会误删别人的锁。必须用 Lua 脚本验证 value 后再删除，上面代码已经展示。

## 踩坑点

1. **时间不同步**：多个 Worker 的时钟如果不一致，基于时间戳的锁方案会完全失效。优先使用 Redis 的 `SET EX NX`，由服务端统一计时。  
2. **锁未释放导致死锁**：如果在 `try` 块里发生进程崩溃，锁无法正确释放。这就是为什么必须依赖 `EX` 过期机制，而不是手动清理。  
3. **重试风暴**：有些同学拿到锁后任务失败，想当然地在 `finally` 中释放锁后立刻重试。在分布式环境下这会导致瞬时大量重试，反而不如让下一轮周期自然触发更安全。  
4. **忽略 Redis 故障**：当 Redis 不可用时，你的 `set` 调用可能会抛异常。如果不做降级处理，整个流程会中断。应当捕获异常，并决定是“放弃本次执行”还是“降级为无锁执行”，根据业务容忍度来定。

## 可复用建议

- **抽成通用锁节点**：在 OpenClaw 中把这个锁逻辑封装成一个独立的“防重入”代码模块或宏，让所有定时流程直接在开头调用。  
- **监控锁争抢**：对 `acquired = False` 的次数进行指标上报。如果某段时间频繁发生，说明执行时长恶化，需要扩容或优化业务。  
- **自文档化任务容量**：在流程描述里注明：该任务最坏执行时间是 X 秒，Cron 间隔是 Y 秒，是否存在重入风险。这比事后查日志高效得多。  
- **压测**：新任务上线前，人工制造一次长耗时（比如在代码里加 sleep），验证锁逻辑是否如期生效，而不是等生产环境帮你验证。

## 总结

“5 分钟任务撞车”本质上是分布式系统里最常见的并发控制缺失问题。OpenClaw 给了我们灵活编排的能力，但也把这类安全细节交给了使用者。好在只需要一套轻量的锁机制，就能彻底消除重入风险，避免数据诡异错误和团队半夜救火。

工程世界里，定时任务的稳健性从来不靠祈祷“它应该能跑完”，而是靠明确的拒绝策略：**没拿到锁，就安静退出，等待下一次真正的机会**。
