## 背景

有多个微博超话需要维护，日常任务包括签到、发布图文内容、按话题分类归档。这些操作重复且容易遗漏，因此想到用自动化链路接管，并接入 OpenClaw 的 Agent 调度体系。需求很明确：通过一套可观测、可恢复的流程，完成图片上传、超话发帖、异常处理与状态归档，整体跑在个人服务器上，不依赖第三方托管平台。

本文记录一次工程化落地的过程，涉及限流控制、任务持久化、MCP 工具封装等细节，适合正在用 OpenClaw/MCP/Agent 做社交平台自动化同步的开发者参考。

## 问题拆解

微博超话发帖接口要求先上传图片获得 `pid`，再携带 `pid` 与超话 `topic_id` 调用发帖接口。表面上两个 HTTP 请求就能完成，但实际会遇到：

- **登录态易失效**：Cookie 有效期短，需定时刷新或使用扫码登录持久化。
- **上传限制**：单日上传图片有总量上限，单次上传大小、格式受限。
- **发帖限流**：同一账号短时间频繁发帖会被限制，返回 `100005` 等风控错误。
- **超话 ID 与用户关系**：需要确认账户已关注超话，否则发帖失败。
- **任务丢失风险**：若脚本中途崩溃，不知道哪些任务已完成、哪些待重试，可能造成重复发帖或漏发。

因此，不能仅靠一个简单脚本，需要设计包含状态机、限流器和任务持久化的流程。

## 方案设计

整体架构分为三层：

1. **MCP Server 层**：把微博的关键操作封装为 MCP 工具，供 Agent 调用，包括 `weibo_upload_image`、`weibo_publish_to_topic`、`weibo_checkin_topic`、`weibo_get_rate_limit_status`。
2. **任务调度层**：一个基于 SQLite 的任务队列，记录待发内容、图片路径、目标超话、状态（`pending` / `uploaded` / `published` / `failed`）、重试次数、下次可重试时间。
3. **OpenClaw Agent 层**：通过 Plan-Execute 模式驱动工作流，根据任务状态决定下一步操作，处理错误并归档。

### 图片上传与限流

上传工具内部使用令牌桶算法控制请求频率。桶容量设为每分钟 3 次，既避免触发接口级限流，也为异常重试留出余量。当上传返回风控错误时，工具会返回一个结构化错误，包含建议等待时间，Agent 据此将任务置为 `rate_limited` 并设定 `retry_after`，不会无脑重试。

上传前对图片做预处理：统一转为 JPEG、尺寸不超过 2048 像素宽、文件大小控制在 3 MB 以内，使用 Pillow 完成。这样可避免因格式问题导致上传失败。

为应对登录态失效，MCP Server 内部维护一个 Cookie 刷新逻辑：每隔 30 分钟用已保存的 refresh token 或通过扫码回调更新 Cookie，并在工具调用前检查有效性。如果还是出现 401，则触发告警并暂停任务队列，等待手动介入。

### 发帖与状态流转

发帖工具接收 `pid_list`、`topic_id`、`content` 等参数。接口调用成功后，任务状态变为 `published`，同时记录发帖时间、微博 ID 等元信息。如果返回限流错误，同样标记 `rate_limited` 并设置冷却时间。对于其他错误（如内容审核不通过），标记为 `failed` 并记录错误原因，避免反复重试浪费配额。

### 状态归档

每次状态变更都会写入 SQLite，同时通过 OpenClaw 的日志通道发送事件。归档不仅是为了排障，还用于生成每日同步报告。Agent 在每日定时任务末尾会读取过去 24 小时的任务记录，汇总成功/失败/跳过数量，并输出到本地 Markdown 文件，方便查看。

## 踩坑记录

**坑 1：超话签到与发帖接口共用限流额度**
开始时以为签到是独立接口，可以高频调用。实际测试发现，签到接口也计入发帖限流窗口，连续签到多个超话后立刻发帖会被拦截。解决办法是把签到动作统一纳入令牌桶，与上传、发帖共享速率控制。

**坑 2：图片 `pid` 时效性**
微博的图片 `pid` 并非永久有效，超过一定时间未使用会失效。我们的任务队列中，`uploaded` 状态如果长时间没有推进到 `published`，会因 `pid` 过期导致发帖失败。对此增加了一个检查：对于 `uploaded` 超过 1 小时的任务，重新上传图片获得新 `pid`，再继续发帖。

**坑 3：登录态刷新与多进程并发**
使用 MCP Server 的 stdio 传输时，如果 Agent 同时发起多个工具调用，MCP Server 内部状态（Cookie）可能被并发修改。解决方法是使用 `asyncio.Lock` 保护 Cookie 更新过程，并确保刷新期间其他调用进入等待队列而非直接失败。

**坑 4：微博内容长度计算**
微博正文长度限制为 140 字（会员更长），但 URL 会被自动缩短，图片不占字数。需在发布前精确计算文本长度，超长则截断或拆分多条。工具中预置了长度计算函数，并返回 `truncated` 标志，供 Agent 决定是否拆分发布。

## 可复用建议

如果你的自动化场景也涉及类似社交平台发布，可以考虑以下几点：

- **封装 MCP Server 时遵循单一职责**：每个工具只做一件事，错误码结构化，便于 Agent 做决策。
- **状态机优于硬编码分支**：任务的状态流转清晰，重试、冷却、失败等逻辑集中管理。
- **限流器与业务解耦**：令牌桶或滑动窗口可作为中间件，配置化控制，便于不同平台复用。
- **任务队列持久化优先考虑 SQLite**：比 Redis 简单，适合单机轻量场景，配合 WAL 模式提升并发。
- **日志和事件驱动归档**：Agent 的每次操作都产生事件，归档只是事件的汇总，比事后查询数据库更灵活。
- **Cookie 刷新需要全链路监控**：一旦刷新失败，整个自动化停摆，务必有明确的告警和手动恢复入口。

## 总结

将微博超话同步接入 OpenClaw Agent 体系后，日常维护的人工介入频率从每天几次降低到每周一两次，主要处理登录态异常。自动化的核心难点不在于发帖本身，而在于把各种意外情况收敛进可控的状态机里，并保证任务不丢失、不重复。这套基于 MCP 工具 + 任务队列 + 限流器的模式稍作修改，也可以复用到其他 UGC 平台的自动化同步上。

实际运行中仍有一些改进空间，比如增加图形化任务面板、接入更稳定的登录方案等，但就目前需求而言，一个工程化、可观测的自动化链路已经足够用了。
