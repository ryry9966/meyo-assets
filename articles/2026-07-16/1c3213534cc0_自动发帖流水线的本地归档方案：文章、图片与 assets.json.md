## 背景

在用 Agent + MCP 搭建自动发帖流水线之后，内容生产速度会明显提升。但很快你会发现一个新问题：生成的文章、封面图、配图散落在临时目录、远程存储或浏览器下载夹里，过两周就完全想不起某篇帖子到底用的哪张图、原文有没有被覆盖。对于需要反复迭代提示词、复用素材、回溯发布历史的工程化实践，没有结构化的本地归档是不可接受的。

我们需要的不是“偶尔手动另存为”，而是一条在流水线末端自动执行的归档链路：无论文章由哪个 Agent 产出、图片由哪个模型生成，最终都落到统一的本地目录，并附带一份记录元数据的 `assets.json`。

## 问题拆解

归档的核心诉求很明确：

1. **可追溯**：给定任意一篇已发布或待发布的帖子，能立刻定位到原始 Markdown、使用的图片、生成时间。
2. **可复用**：历史图片和文案片段能快速检索，而不是重新生成。
3. **与发布解耦**：归档不依赖特定平台，即使发布失败或延迟，本地资产必须完整。
4. **结构化**：目录和索引文件适合用脚本、MCP 工具或 grep 处理。

常见半成品的做法：自动保存 Markdown 到某个文件夹，图片另存为 `image1.png`。但没有索引文件，时间久了连文件名都看不懂，更不用说图片和文章的对应关系。另一个隐性问题：流水线中可能同时有多条内容并行生成，写入同一 `assets.json` 时容易发生冲突。

## 做法

我们设计了一个最小可行的本地归档流程，分三层：目录约定、文件保存、索引更新。

### 1. 目录约定

按日期组织，每篇帖子一个独立目录：

```
~/.openclaw/archives/
  2025-04/
    2025-04-10-how-i-automate-daily/
      article.md
      images/
        cover.png
        diagram.png
      assets.json
```

日期前缀保证排序友好，slug 部分来自标题规范化。`images/` 存放该帖所有配图，`article.md` 是最终渲染前或渲染后的 Markdown 正文，`assets.json` 记录这篇帖子相关的全部元数据。

### 2. 文件保存

在 Agent 流水线中，我们将“生成内容”和“写入归档”拆成两个可复用的 MCP 工具调用。我们使用的是自定义的 `local-archive` MCP server，暴露两个 tool：

- `save_markdown(content, path)`：将文章写入指定路径。
- `save_image(image_data, path)`：将 base64 或 URL 图片写入目标路径。

实际调用时，Agent 会先规划好目录结构，然后依次调用这两个工具。图片的引用路径在 `article.md` 中统一使用相对路径 `images/xxx.png`，保证文章在本地 Markdown 预览器中能直接查看。

为了保证幂等性，写入前会检查目标文件是否存在；如果存在，根据 `overwrite` 参数决定是覆盖还是自动追加序号。

### 3. assets.json 更新

这个文件是整个归档的灵魂。单篇的 `assets.json` 结构如下：

```json
{
  "title": "How I Automate Daily Posts",
  "slug": "2025-04-10-how-i-automate-daily",
  "created_at": "2025-04-10T14:30:00Z",
  "tags": ["automation", "openclaw"],
  "status": "draft",
  "files": {
    "article": "article.md",
    "images": [
      "images/cover.png",
      "images/diagram.png"
    ]
  },
  "meta": {
    "prompt_hash": "a1b2c3",
    "model": "claude-sonnet-4-20250514"
  }
}
```

流水线在文章和图片全部写入完成后，调用 `update_asset_index` 工具，生成或更新这个 JSON。如果该目录下已经存在 `assets.json`，则合并字段（例如追加新图片记录、更新 status）。

我们还在顶层 `~/.openclaw/archives/assets.json` 维护了一份全局索引，内容是一个按日期倒序的数组，每项仅含 `slug`、`title`、`created_at`、`tags` 和目录路径。这个全局文件用于全文检索和批量操作，例如找出所有带 `#prompt` 标签的帖子。更新时采用“读取—合并—写入”模式，并用基于文件锁（flock）的简单机制避免并行写入冲突。

## 踩坑点

1. **图片路径的跨平台坑**  
   Windows 上路径分隔符与 Markdown 相对路径的解析有时不一致。统一在归档工具里强制使用 POSIX 风格路径 `/`，写作时相对路径一定以 `images/` 开头，不带 `./` 前缀。

2. **JSON 并发写入冲突**  
   如果同时跑两条流水线，同时更新全局 `assets.json`，不加锁会丢数据。即使使用简单的 `flock`，也要注意 NFS 等网络文件系统可能不支持，建议将全局索引放在本地文件系统，并做好失败重试（最多 3 次，间隔随机退避）。

3. **大图片与 base64 传输**  
   在 MCP tool 调用中，图片如果通过 base64 传递，单次请求体可能超过某些 transport 的限制（如 stdio JSON-RPC 的隐式大小限制）。建议：① 对于从 URL 下载的图片，由 Agent 传递 URL，归档工具直接下载；② 对于生成的图片，如果数据量超过 2MB，先写入临时文件，再通过文件路径传递。

4. **文件名非法字符**  
   标题 slug 化时，除了英文、数字和连字符，可能出现 Unicode 空白符、emoji 等。务必在 slug 生成函数中严格过滤，只保留 `[a-z0-9-]`，并限制长度不超过 64 字符。

5. **归档时机**  
   不要等“发布成功”才归档，因为发布可能因为 API 限流而延迟。我们采取的策略是：内容生成完毕、图片全部下载后即归档，`status` 记为 `draft`；发布成功后通过另一个工具调用将状态更新为 `published`。这样即使发布中断，本地资产也是完整的。

## 可复用建议

- **将归档拆成独立 MCP server**：不耦合到特定 Agent 逻辑，任何能调用 MCP 工具的工作流都可以复用。
- **全局索引满足 80% 的检索需求**：不必一上来就上数据库，一个 JSON 数组 + `jq` 命令就能实现按标签、日期、状态筛选。
- **保留 prompt_hash 字段**：记录生成时使用的完整提示词的哈希值，未来回溯提示词迭代时很有价值。实际可以将 prompt 文本也存入文章目录中的 `prompt.txt`。
- **与发布步骤解耦**：归档工具完全不知道“发布”的存在，只负责本地存储。发布逻辑通过外部调度器或者另一个 MCP tool 完成，从 `assets.json` 读取状态为 `draft` 的帖子上报。
- **备份**：`archives/` 目录纳入常规备份（git 或云同步），保证内容不会因本地磁盘故障丢失。

## 总结

本地归档看起来是一件“小事情”，但它决定了自动化内容流水线的长期可维护性。用结构化的目录、一份 `assets.json` 和两个 MCP 工具，就能把散乱的内容资产变成可追溯、可检索的素材库。实践中真正花时间的往往不是写保存文件的代码，而是想清楚哪些元数据真正有用、并行写入如何处理、路径规范如何统一。一旦这套约定稳定下来，后续无论是切换发布平台、重跑旧提示词，还是分析历史帖子效果，都有了坚实的基础。
