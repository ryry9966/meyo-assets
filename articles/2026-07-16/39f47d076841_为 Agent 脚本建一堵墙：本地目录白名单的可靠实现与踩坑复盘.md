# 为 Agent 脚本建一堵墙：本地目录白名单的可靠实现与踩坑复盘

## 背景

在 OpenClaw 生态里，我们越来越依赖 Agent、MCP 服务器或自定义插件去操作本地文件系统——读取配置文件、写入日志、导出报表，甚至批量重命名素材。一旦赋予 Agent 文件访问权限，潜在风险也随之而来：一条失控的指令可能误删系统文件，或者读取到 `.env`、SSH 密钥等敏感数据。

典型的防御思路是对可访问目录做**白名单限制**，也就是“文件访问护栏”。但很多时候，开发者只做了最简单的路径前缀匹配，这在符号链接、路径穿越和大小写问题上基本形同虚设。本文会以 Python 实现为例，讨论一个可复用的目录白名单方案，以及实际踩过的坑。

## 问题拆解

给 Agent 加文件访问护栏，本质上要解决三个问题：

1. **什么是合法路径？** 只有指定白名单目录及其子孙节点允许访问，其他路径一律拒绝。
2. **如何可靠判断“路径在目录内”？** 简单的 `startswith` 可能被 `../`、符号链接、短路径名（Windows）绕过。
3. **如何集成到现有工具链？** 护栏逻辑需要能嵌入到 OpenClaw 脚本、MCP 服务器或者插件入口，而不大量改动业务代码。

下面我们围绕这三个问题，构建一个生产可用的文件访问白名单模块。

## 做法与步骤

### 1. 构建白名单配置

我们将允许访问的目录列表存为一个 `set`，每个目录在加载时就解析成绝对路径并做规范化处理，避免运行时重复计算。

```python
import os
import pathlib
from typing import Set

class FileAccessGuard:
    def __init__(self, allowed_dirs: list[str]):
        self._allowed: Set[pathlib.Path] = set()
        for d in allowed_dirs:
            p = pathlib.Path(os.path.realpath(d)).resolve()
            self._allowed.add(p)

    def is_allowed(self, target: str) -> bool:
        target_path = pathlib.Path(os.path.realpath(target)).resolve()
        for base in self._allowed:
            # 检查 target_path 是否在 base 目录下，或者是 base 本身
            try:
                target_path.relative_to(base)
                return True
            except ValueError:
                continue
        return False
```

要点：使用 `os.path.realpath()` 解析所有符号链接，再调用 `Path.resolve()` 得到规范化的绝对路径。`relative_to()` 可以准确判断一个路径是否属于某个父目录树。

### 2. 在文件操作入口嵌入护栏

为了避免开发者在每个文件调用处手动判断，可以封装一个安全的文件操作代理。例如：

```python
import builtins

class GuardedFileOps:
    def __init__(self, guard: FileAccessGuard):
        self._guard = guard

    def safe_open(self, file, mode='r', *args, **kwargs):
        if not self._guard.is_allowed(str(file)):
            raise PermissionError(f"Access denied: {file}")
        return builtins.open(file, mode, *args, **kwargs)
```

对于更复杂的应用场景（如 MCP 服务器的工具定义），可以将护栏前置，在工具函数入口先调用 `guard.is_allowed(path)`，合法后再执行后续逻辑。

### 3. 集成到 OpenClaw 脚本

假设我们有一个 OpenClaw 脚本 `batch_renamer.py`，需要只允许操作 `/data/agent_workspace` 及其子目录：

```python
guard = FileAccessGuard(allowed_dirs=['/data/agent_workspace'])
ops = GuardedFileOps(guard)

with ops.safe_open('renamed_files.log', 'a') as f:
    f.write("done")
```

对 MCP 服务器同理，只需在工具函数内部创建或共享 `guard` 实例即可。

## 踩坑记录

在实际工程中，这个方案还会遇见几个不易察觉的陷阱：

- **挂载点与绑定挂载**：Linux 下的 `mount --bind` 或 Docker 卷挂载可能让白名单目录的 `realpath` 和用户看到的路径不一致。建议在服务启动时预先探测白名单目录的规范化路径，并在监控中记录，避免运行时反复解析产生不一致。
- **符号链接环路**：`os.path.realpath()` 会处理符号链接但可能受最大递归深度影响，极端情况下可能抛出错误。增加 try/except 并记录异常路径，不要默默放过。
- **Windows 下的短路径名**：如果你的 Agent 可能运行在 Windows 上，还需额外调用 `GetLongPathNameW` 或使用 `pathlib.Path.resolve()`（Windows 下会调用 `GetFinalPathNameByHandle`），注意这要求文件实际存在。对尚未创建的路径，可以用前瞻性的父目录进行白名单判断。
- **竞态条件**：检查路径合法和实际文件操作并非原子操作，可能在检查后白名单目录变更或被替换成符号链接。对于高风险场景，可以在安全面使用 `openat`/`open` + `O_NOFOLLOW` 等标志，但复杂度陡增。一般 Agent 场景下，确保护栏逻辑与文件操作在同一个进程里且没有其他写入者，可基本规避。

## 可复用建议

1. **将护栏做成独立模块**，对外暴露 `is_allowed` 和 `safe_open` 两个最小接口，方便测试和替换。
2. **配置化白名单**，通过环境变量或配置文件加载白名单目录，便于在不同环境切换（开发/生产）。
3. **为拒绝访问行为加全量日志**，记录 `timestamp、pid、请求路径、白名单` 等信息，方便审计 Agent 行为。
4. **与 OpenClaw 的权限声明结合**：如果你的插件在 `manifest.json` 或 MCP 配置中有 `capabilities` 字段，可以把文件访问白名单写进去，做到自描述，同时让平台侧对权限一目了然。
5. **测试用例要覆盖**：相对路径（`.`、`..`）、符号链接、软链接指向文件及目录、Unicode 路径、大小写敏感/不敏感文件系统等。

## 总结

文件访问护栏不是一个“加个 if 就能完事”的特性，它需要深入理解路径解析的底层行为，并处理跨平台细节。上述白名单方案已在多个 OpenClaw 内部工具中稳定运行，能有效拦截绝大部分路径穿越和误操作，且对业务代码侵入性低。

安全工程化的本质是“低摩擦 + 可验证”。有了这堵墙，你可以更放心地让 Agent 代替你搬运文件，而不必半夜被报警叫醒。
