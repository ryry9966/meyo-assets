## 背景

把文章、周报或创作内容自动推到微博超话，是不少独立维护者的刚需。常见做法是手工粘贴，或者用商业化分发工具，但这些方案要么依赖第三方黑盒，要么在超话场景下支持有限。在 OpenClaw 的自动化管线上，我们希望把“Markdown 文档 + 封面图 → 指定微博超话帖子”做成一个可审计、可恢复的同步过程。

本文记录一次基于微博移动端接口的同步实践，会覆盖图片上传的真实约束、接口限流的工程化应对，以及用什么结构把同步状态归档下来。如果你也在用 agent 或 MCP 工具做内容自动分发，这份记录也许能帮你少走弯路。

## 问题拆解

微博超话没有公开的 REST API，但它的移动端 Web 接口相对稳定。要完成一次“图片+文案”的超话发帖，至少需要解决这几个问题：

1. **身份认证**：如何获取并维护 cookie，避免被重复登录流程打断。
2. **图片上传**：先上传得到 `pic_id`，再携带 `pic_id` 去发帖，上传接口对图片格式、尺寸有隐式要求。
3. **超话载体**：发帖时如何正确携带超话标识，让微博判定帖子归属对应超话。
4. **限流处理**：频繁调用会被 429 或静默降权，需要退避机制。
5. **状态记录**：异步同步容易丢任务，必须记录每次同步的状态和关联的微博 ID，方便事后回溯。

## 做法与步骤

### 1. 获取可用 cookie
不去折腾密码登录，直接用扫码登录后的 cookie。在移动端接口场景下，需要的主要是 `SUB` 或 `M_WEIBOCN_PARAMS` 这类关键字段。我的做法是一次性扫码后把 cookie 字符串存入配置文件，脚本启动时校验是否过期。

校验方式很简单：请求 `https://m.weibo.cn/api/config`，看返回是否包含登录用户信息。

### 2. 图片上传：注意隐式约束
上传接口用的是 `https://m.weibo.cn/api/statuses/uploadPic`，multipart/form-data 形式，参数 `type=json`，文件字段名 `pic`。上传成功会得到 `pic_id`，用于后续发帖。

这里踩了第一个坑：**图片必须是正方形的？** 实测如果上传宽高比过度横向或纵向的图，超话帖子可能无法正常展示，甚至上传成功但发帖后被微博静默抛弃。稳定经验是 **裁剪为 1:1，分辨率 1000×1000 左右，JPEG 质量 ≤ 90%**，文件大小不超过 3MB。另外上传时的文件名最好带 `.jpg` 后缀，否则偶尔会被返回格式错误。

### 3. 发帖并关联超话
通过 `https://m.weibo.cn/api/statuses/update` 发送，参数 `content`（文案），`pic_id`（上一步得到的），以及额外参数控制可见范围。超话的关联要靠 **文案中显式包含超话标签**，例如 `#超话名称#`，并且该超话需要是当前账号已关注且可发帖的。如果账号未关注该超话，发帖会变成普通微博，不会归入超话。

脚本会先检查超话关注状态：调用 `https://m.weibo.cn/api/container/getIndex` 带入 `containerid` 相关的超话逻辑，不过最省事的办法还是手动确认关注，并在配置里写死标签名称。

### 4. 限流与退避
微博接口限流以请求频次和账号风控两种形态出现。请求频次的典型表现是返回 `{"ok":0,"msg":"发布频率过快"}` ，此时需要强制等待。我的策略是 **指数退避 + 随机抖动**：

```
if response indicates rate limit:
    backoff = min( backoff_base * (2 ** retry_count), 600 )  # 不超过10分钟
    wait = backoff + random(0, 5000)  # ms 级别抖动
    sleep(wait)
```

风控层面的静默截断更难处理：帖子表面成功，但实际在超话里不出现，或者仅自己可见。这时需要降级逻辑，把这类“虚拟成功”也标记为需人工复查。

### 5. 同步状态归档
不记录状态就无法做重试和审计。我用了一张简单的 SQLite 表（也可用 JSON 行文件），核心字段：

- `task_id`：每次同步的唯一标识
- `source`：来源文档路径或 ID
- `content_hash`：文案哈希
- `pic_path` / `pic_id`
- `weibo_id`：成功后返回的微博 ID
- `status`：`pending/uploaded/posted/rate_limited/failed/manual_review`
- `retry_count`
- `created_at` / `updated_at`

同步流程里每个环节都更新状态，比如图片上传成功后进入 `uploaded`，发帖成功后标记 `posted` 并填入 `weibo_id`。这样即便脚本中断，翻一下数据库就能接着跑未完成的任务。

## 踩坑点与应对

1. **图片比例不自适应**：超话时间线对非正方形图片的处理不一致，裁剪为 1:1 是最稳妥的选择。
2. **Cookie 过期静默失败**：接口不会直接返回 401，而是返回空数据或无权限错误码。需要每次同步前主动探测登录态。
3. **超话标签格式**：必须是完整的中文标签 `#xxx#`，且前后最好有空格，避免文案粘连。标签不得包含非法字符。
4. **发送间隔**：即便在没有 429 的情况下，也建议 **最低间隔 10–15 秒**，连续快速请求容易触发风控降权。
5. **网络超时重试时不幂等**：发帖接口超时后，重试可能导致重复发帖。虽然概率不高，但重试前最好检查一下是不是已经有相同内容刚发布，通过比对近期微博时间戳。

## 可复用建议

这套逻辑可以作为 OpenClaw 的一个 MCP 工具模块：暴露 `publish_to_weibo_supertopic` 工具，接收文案、图片路径、超话标签，内部完成上传+发帖+归档，并返回 `status` 和 `weibo_id`。归档表不仅可以用于当前同步，还能对历史帖子做二次扫描，检测哪些被微博移除或降权。

如果你的 agent 需要处理多账号，cookie 配置和归档表按账号隔离即可。此外，配上简单的 Web UI 查看归档状态（哪些在 `manual_review`），可以把人工介入成本降到最低。

## 总结

微博超话的“自动化坑”藏在图片约束、限流策略和静默失败里。通过显式裁剪图片、有序退避和严格的归档记录，可以把一个不可靠的自动化发布过程，变成可控、可追溯的同步管道。这套方案没有依赖任何不可控的第三方库，只用了 requests 和 sqlite3，轻量且易于移植。对 OpenClaw 社区而言，它刚好填补了自动化内容管道在微博端“最后一公里”的落地空白，也证明了 agent 工具在真实社交平台约束下仍能稳定工作。
