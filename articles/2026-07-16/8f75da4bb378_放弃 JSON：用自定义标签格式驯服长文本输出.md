## 背景

在 OpenClaw 搭建 Agent、MCP 工具链或自动化流水线时，我们总希望能从模型拿到格式确定的结构化数据，以便直接进入后续的工程管道。JSON 是直觉首选——标准、可解析、工具链成熟。但实际落地后你会发现，当输出长度超过几百 token，或需要生成多级嵌套结构时，JSON 很容易变成一坨坏掉的字符串。

最常见的场景：让模型输出一份带章节、步骤、备注的多级计划；Agent 的 Planner 需要返回任务拆解结果；或 MCP 工具要求返回包含多个字段的诊断报告。一旦模型开始“发挥”，多一个逗号、少一个引号、用中文冒号代替英文、在嵌套层级里偷偷插入一段解释性文字——整个 JSON 就不可逆地损坏了。修复成本极高，regex 补丁越打越多，最后还是需要人工兜底。

## 问题：为什么长文 JSON 如此脆弱？

不是因为模型不会 JSON，而是 JSON 的**容错性极差**。一行错，全文件解析失败。在长上下文生成中，下面几个效应会成倍放大：

- **注意力衰减**：长输出时，模型对前面的括号、引号配对失去准确记忆，容易出现不闭合或错位。
- **嵌套疲劳**：三层以上的数组、对象嵌套，模型在流式生成时很容易丢失 `},]` 或把 `}` 写成 `]`。
- **语法洁癖**：JSON 要求最后一个元素后面不能有逗号，但模型有时会在多层嵌套的最后多写一个逗号。
- **解释性噪音**：模型有时会在 `{...}` 前后加上自然语言，比如“这是你需要的结果：{...}”，纯 JSON 提取需要额外清洗。

传统的修复手段（重试、正则补丁、使用 `json_repair` 库）治标不治本，重试会浪费 token，正则面对复杂嵌套往往力不从心。我们需要一种**更宽松、更易分块、解析成本更低**的结构化方式。

## 方案：转向自定义标签格式

思路很简单：放弃 JSON 的严格语法，改用一组自定义的**成对标签**来标记结构化字段。例如：

```
<OUTPUT>
  <STEP>
    <TITLE>环境检查</TITLE>
    <SCRIPT>check_deps.sh</SCRIPT>
    <NOTE>需要 root 权限</NOTE>
  </STEP>
  <STEP>
    <TITLE>部署应用</TITLE>
    <SCRIPT>deploy_app.sh</SCRIPT>
    <NOTE>确保端口 8080 未被占用</NOTE>
  </STEP>
</OUTPUT>
```

标签格式的优势在于：

1. **容错性强**：标签可以在一段自由文本中任意穿插，多一个换行、少一个空格都不会影响解析。哪怕部分标签没闭合，我们也能按已成功的部分提取，而不是整体丢弃。
2. **分块友好**：长输出可以要求模型每生成一个 `SECTION` 就停止，或流式读取时按起始标签切分。对 OpenClaw 的流式处理极有利。
3. **解析逻辑极简**：用正则 `re.findall(r'<TAG>(.*?)</TAG>', text, re.DOTALL)` 即可，无递归解析压力。
4. **可读性好**：对人调试也比 JSON 更直观，尤其当中间包含代码块或长文本时。

代价是丢失了标准工具生态的直接支持，但大多情况下我们只需要消费数据，不必担心 OpenAPI 校验。

## 做法与踩坑记录

### 1. 设计标签约定

尽量让标签名语义化，不需要 DTD。对于重复项（如多个步骤、多个章节），让模型自由生成同名的 `STEP` 标签，解析时找出所有。避免属性，所有信息放在子标签或内容中。

示例系统提示：

```
你必须用以下标签格式输出计划：
<PLAN>
  <STEP>
    <NAME>...</NAME>
    <ACTION>...</ACTION>
    <REASON>...</REASON>
  </STEP>
</PLAN>

规则：每个 STEP 三个字段齐全；如果无法完成，输出 <ERROR>...</ERROR> 并解释。
```

### 2. 解析器实现（Python）

解析器核心很简单，但要处理几个边界情况：

```python
import re

def extract_tag_content(text: str, tag: str) -> list[str]:
    # 忽略标签嵌套，只取最内层非贪婪匹配
    pattern = rf'<{tag}>(.*?)</{tag}>'
    return re.findall(pattern, text, re.DOTALL)

def parse_steps(text: str):
    steps = []
    for block in extract_tag_content(text, 'STEP'):
        step = {}
        for f in ['NAME', 'ACTION', 'REASON']:
            vals = extract_tag_content(block, f)
            step[f.lower()] = vals[0].strip() if vals else ''
        steps.append(step)
    return steps
```

### 3. 常见踩坑点

- **标签重名时的顺序依赖**：当有多个 `NOTE` 子标签时，用索引区分就很脆弱。建议设计成唯一子标签，或用 `NOTE1`、`NOTE2` 明确编号。
- **标签内容中的尖括号**：如果内容包含类似 `<code>` 的片段，会造成假闭合。要么要求模型对标签本身转义（`&lt;`），要么使用更小众的分隔符，如 `[%TITLE%]...[/%TITLE%]`。我习惯用 `###TITLE###` 和 `###END###`，彻底避开 XML 冲突。
- **模型不听话**：部分模型会在 `STEP` 外丢弃闭合标签，直接输出下一个 `STEP`。可以在 prompt 里增加“如果无法完整生成所有标签，请只生成已确认部分并加上注释”的兜底指令，然后在外层捕捉 `PLAN` 标签不存在时，直接按 `STEP` 标签提取。
- **流式场景下的截断**：标签不闭合就返回，流式消费器需要缓存片段并等待闭合。可以在 prompt 中要求模型首先生成 `PLAN` 的开始标签，每生成完一个 `STEP` 就立即刷新。OpenClaw 的流式接口可直接对 `>` 做边界判断。

## 可复用建议

在 OpenClaw 的 ToolAgent 或 MCP 工具开发中，凡是需要模型输出结构化的长内容，都推荐将标签格式作为默认约定，而 JSON 仅保留给短小、固定字段的指令集（如 function call）。

一套可复用的实践：

1. **Prompt 模板固化**：将标签规范写入工具的 `description` 或系统提示，附上一个真实示例。
2. **防御性解析**：实现一个 `parse_or_fallback(text, tag_rules)`，先尝试严格解析，失败则做最小提取并告警，绝不中断流水线。
3. **分块输出 + 标签**：通过 `stop` 序列控制模型在 `</STEP>` 后暂停，等待工具执行结果再继续，既保证稳定性也实现了 ReAct 风格。
4. **监控指标**：记录标签解析成功率，当某个工具长期低于 99% 时，优化 prompt 或返回格式。

我自己的经验：把 Agent 的 Planner 输出从 JSON 迁移到 `###PLAN### ... ###END###` 后，解析失败率从 7% 降到了 0.2%，而且剩下的失败几乎全是网络中断导致的截断，而非格式问题。token 浪费也明显减少，因为不再需要重试。

## 总结

JSON 不是长文本结构化的好选择。当我们追求工程稳定性和低维护成本时，自定义标签格式是更务实的方案。它牺牲了一点标准化，换来的是更低的解析脆弱性、更自然的分块能力和更简单的调试体验。如果你正在 OpenClaw 上构建需要稳定输出的自动化链路，不妨试试在下一个工具里用标签替代 JSON，可能会发现整个世界都清净了。
