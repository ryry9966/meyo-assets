## 背景：被坏掉的 JSON 消耗掉的工程时间

在 OpenClaw 这类 Agent 框架里，我们用大模型生成结构化长文——可能是每日简报、代码审查报告、甚至一个完整的 Markdown 文档。为了让下游自动化工具（比如 MCP 插件、发布流水线）消费这些内容，最常见的做法是要求模型输出 JSON：

```json
{
  "title": "...",
  "content": "...长文内容...",
  "tags": ["..."]
}
```

然而当 `content` 超过 1500 字、包含代码块、双引号、换行和特殊符号时，这种约定就变成了“猜谜游戏”。模型会在某个嵌套的花括号处丢失配对、转义漏写 `\`、或悄悄把最后一个 `}` 吞掉。解析失败，自动化中断，重试又烧掉大量 token，整个过程毫无工程愉悦感。

## 问题：为什么要和“坏 JSON”正面交锋

常见的痛苦场景：

- **长文内自然包含 JSON 片段**。比如技术文章里贴一段配置示例，LLM 输出时可能会错误地转义或丢失闭合括号，出来的东西 `json.loads` 直接抛异常。
- **分段流式输出叠加 JSON**。Agent 先输出一半，补全时结构错位，即便用增量解析器也难保不崩。
- **校验成本高**。修复坏 JSON 需要复杂的启发式逻辑（补括号、找缺失引号），而且根本没保证下次会好。
- **重试陷入死循环**。LLM 的错误模式有惯性，多次重试仍拿到同样的格式错误。

这些问题在一些 MCP Server 需要返回结构化长文时尤其突出：上游工具对数据格式有假设，一旦解析失败，整个链路静默失败或抛出令人困惑的错误。

## 做法：从严格 JSON 迁移到标签分隔

我们最终采用的方案非常简单：抛弃对“合法 JSON”的依赖，改用自定义标签包裹字段。模型输出长文只需要遵守一个宽松的标记协议，不必处理转义噩梦。

### 步骤 1：选择不会与内容冲突的标签

为每个字段定义开始和结束标签。采用全大写 + 特殊符号组合，让它几乎不可能出现在正常文本中。例如：

```
[!!!TITLE!!!]
多模态 Agent 在运维中的误区
[!!!TITLE_END!!!]

[!!!CONTENT!!!]
（任意长度的 Markdown 长文，可以包含代码块、引号、花括号）
[!!!CONTENT_END!!!]

[!!!TAGS!!!]
Agent, MCP, 运维
[!!!TAGS_END!!!]
```

也可以使用类似 XML 的结构，比如 `<__TITLE__>`，但必须保证标签不和大模型的 markdown 或代码块混淆。

### 步骤 2：在提示词中植入零样本/少样本约束

提示词模板要点：

1. 明确要求：“你的回答必须严格使用下面的标签格式，不要包裹在 markdown 代码块内。”
2. 给出完整示例，展示标签和实际内容。
3. 强调边界行为：“不要在标签前后添加解释文字；如果内容本身需要包含类似标签的文本，请用 `\` 转义开始标记。”
4. 设置兜底：“如果内容中包含 `[!!!` 字样，替换为 `[！!!` 或使用其他替代。”

经过 3-5 组 few-shot 示例，大部分模型（从 GPT-4o 到 DeepSeek-V3）能稳定遵循，甚至比 JSON 模式更少出错。

### 步骤 3：实现容错解析器

解析代码不依赖任何重量级库，用正则非贪婪提取即可。核心逻辑如下：

```python
import re

def parse_tagged_output(text: str):
    title_m = re.search(r'\[!!!TITLE!!!\]\s*(.*?)\s*\[!!!TITLE_END!!!\]', text, re.DOTALL)
    content_m = re.search(r'\[!!!CONTENT!!!\]\s*(.*?)\s*\[!!!CONTENT_END!!!\]', text, re.DOTALL)
    tags_m = re.search(r'\[!!!TAGS!!!\]\s*(.*?)\s*\[!!!TAGS_END!!!\]', text, re.DOTALL)
    
    title = title_m.group(1).strip() if title_m else None
    content = content_m.group(1).strip() if content_m else None
    tags = [t.strip() for t in tags_m.group(1).split(',')] if tags_m else []
    
    # fallback: 如果缺少字段，返回部分结果并记录警告
    return {"title": title, "content": content, "tags": tags}
```

关键设计：

- 使用 `re.DOTALL` 匹配跨行内容。
- 允许标签前后有空白，提高容错。
- 当任意字段提取失败时不抛异常，由上层根据需求决定重试或缺省处理。

### 步骤 4：构建闭环纠错

在 Agent 编排中，如果解析器返回空 `content` 或缺少标题，可以触发一次轻量纠正请求：“你的输出缺少 `[!!!CONTENT!!!]` 标签，请严格按照格式重新生成整个回答。” 因为标签格式明确，模型很快修正，比修复坏 JSON 的经验成本低得多。

## 踩坑点与应对

1. **标签意外出现在内容中**
   - 选择低频字符组合（如全角符号 `【【CONTENT】】` 或加入 UUID）。也可以要求 LLM 主动转义，但多一层出错可能。推荐使用 `<|content|>` 这类 token 极小概率出现的序列，结合正则匹配时忽略出现在代码块 ` ``` ` 内的内容（先剥离代码块再匹配）。

2. **模型“自作主张”添加 markdown 代码块**
   - 在系统提示中反复强调“不要用三个反引号包裹整个输出”。有时需要在解析器中预先去除最外层的 ` ``` ` 代码块包裹。

3. **长文分段输出时的标签截断**
   - 若流式场景必须切分，约定每个分段都是一个完整的标签块，或者使用特殊的续传标记。我们实践中尽量让模型一次性生成完整结果，避免流式切割标签。

4. **大小写敏感或标签变体**
   - 模型可能输出 `[!!!TITLE!!!]` 或 `[!!! Title !!!]`。正则统一 `re.IGNORECASE`，并允许标签内空白。

## 可复用建议

- **标签模板化**：为不同任务（简报、报告、对话摘要）建立标签结构库，MCP 工具的 `description` 里直接写清楚输出格式，远胜每次都拼 JSON Schema。
- **与 MCP 工具协作**：如果 MCP Server 的输出是长文，建议在工具的返回定义中采用标签包裹的多字段文本，而不是强行返回 `structuredContent` 的 JSON 对象，降低客户端解析复杂度。
- **混合策略**：对纯结构化元数据（如数值、枚举）依旧用 JSON；对包含大段自由文本的内容，切换到标签格式。两者通过一个 wrapper 字段区分。
- **测试清单**：每次更改标签设计，用包含标签片段、代码块、特殊 Unicode 的测试用例跑一遍，确保正则匹配稳定。
- **兼顾人类可读**：标签格式本身是纯文本，调试时可以直接阅读原始输出，比起压缩成一行的 JSON 更友好。

## 总结

在很多 Agent 和自动化工程里，我们过度依赖 JSON 作为衔接语言，却忽视了 LLM 并不天然是“JSON 打印机”。当输出内容越来越长，结构化需求与自由文本之间的张力就暴露出来。使用标签分隔格式，是一种务实的降级策略：牺牲一点点格式的规范性，换来显著的解析稳定性和工程可控性。

它不替代 JSON 在 API 契约中的位置，但在需要模型吐出一篇完整文章、一段分析报告、一个包含多段代码的文档时，让标签说话，比修理坏掉的 JSON 划算得多。
