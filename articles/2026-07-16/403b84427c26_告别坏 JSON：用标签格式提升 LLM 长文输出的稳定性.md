## 引言：一个反复出现的解析噩梦

在构建基于 LLM 的自动化流程时，几乎所有开发者都会遇到同一个痛点：让模型输出结构化数据（通常是 JSON），然后解析失败。不是少个引号，就是多一个花括号，或者嵌套内容里的换行符没有被正确转义。尤其当生成的内容是长文章、多段落、带有特殊字符的文本时，JSON 的脆弱性会被放大，直接导致下游 Agent 或插件崩溃。

我在维护一个 OpenClaw 内容生成管线时，碰到大量这类问题。模型需要同时输出文章标题、摘要、正文、关键词、分类标签，常规思路是定义如下 JSON schema：

```json
{
  "title": "文章标题",
  "summary": "摘要文本",
  "body": "正文内容可以很长，包括换行、双引号\"、反斜杠\\等",
  "tags": ["标签1", "标签2"]
}
```

但在实际运行中，大约 15%–20% 的响应会出现 JSON 格式错误，比如 `body` 中的未转义双引号、模型自作主张添加的注释、或者结尾缺失 `}`。即使加入 retry 和修复逻辑，也无法做到 100% 稳定。这让我重新思考：是否一定要用 JSON 来承载长文本？

## 问题分析：为什么长文本 + JSON = 不稳定

- **转义地狱**：长文章天然包含引号、反斜杠、换行等字符，LLM 很难保证每次都正确转义。即便在 prompt 中强调，仍可能忘记对嵌套引号进行转义。
- **结构复杂度**：JSON Schema 越复杂，模型越容易漏掉逗号或括号。尤其在单次生成多个字段时，注意力分散。
- **解析容错低**：JSON 解析器相对严格，一处错误会导致整个对象无法反序列化。正则打补丁式的修复并不总是可靠。
- **跟模型的“思维模式”不匹配**：LLM 是序列生成器，更适合标记分隔的线性结构，而不是严格嵌套的树形结构。

## 替代方案：自定义标签格式

我发现，使用类似 XML 或轻量标记的自定义标签来组织长文本输出，可以在很大程度上规避上述问题。具体做法是：为每个需要的字段定义一对标签，让模型把内容包裹在标签内。例如：

```
<title>从零搭建本地 Agent 环境</title>
<summary>本文介绍如何在本地部署...</summary>
<body>
正文内容可以自由包含引号"、换行、特殊字符，
甚至可以直接嵌入简单的代码块。
只要不包含 </body> 标签本身，就不会破坏结构。
</body>
<tags>OpenClaw,Agent,本地部署</tags>
```

解析时，只需用简单的正则或字符串匹配提取标签之间的内容。我用 Python 的 `re.findall` 加上非贪婪匹配，就可以稳如老狗地拿到所有字段。

## 具体实施步骤（以 OpenClaw 内容生成为例）

### 1. 设计标签命名与结构
- 使用全小写单词、避免与内容关键词冲突。建议加上项目特定前缀，如 `<oc_title>`、`<oc_body>`。
- 对于列表类数据，直接用逗号分隔，不嵌套次级标签，降低复杂度。

### 2. 构建 Prompt 模板
在系统提示词中明确要求使用标签格式，并给出完整示例：

```
你现在是一个内容生成助手。请严格按照以下格式输出，每个字段用指定的标签包裹：

<oc_title>文章标题</oc_title>
<oc_summary>100字以内的摘要</oc_summary>
<oc_body>
正文内容（允许多段落）
</oc_body>
<oc_tags>标签1,标签2,标签3</oc_tags>

务必确保每个标签成对出现，不要在标签之外输出任何多余内容。
```

### 3. 解析与容错
- 用 `re.search(r'<oc_title>(.*?)</oc_title>', text, re.DOTALL)` 提取每个字段。
- 对可能缺失的字段设置默认值，并记录日志。
- 如果正文内容本身可能包含 `</oc_body>`，可要求模型将标签名称转为大写，如 `<OC_BODY>`，或采用 base64 编码，但这会牺牲可读性。我选择在 prompt 中要求模型避免写入与标签完全一致的字符串（几乎不会发生）。

### 4. 在 OpenClaw 管道中集成
将上述解析逻辑封装成一个 `TaggedContentParser` 工具，作为 Agent 数据处理的一个标准步骤。后续步骤只接收解析后的字典，完全不接触原始 LLM 输出，极大降低了耦合。

## 真实踩坑点与解决记录

- **标签截断**：当生成被 max_tokens 截断时，可能缺少结束标签。解决方案：检查是否存在闭合标签，如果缺失，则对最后一个标签做内容截断，或者丢弃该字段并触发轻量重试（带降低长度限制）。
- **标签嵌套**：模型偶尔会在正文里“创造性”地插入假设性的子标签，比如 `<oc_title>嵌套标题</oc_title>`。通过 prompt 明确“禁止在任何字段内部使用本协议定义的标签”，并配合解析时只取第一个匹配的闭合标签可以缓解，但最根本还是 prompt 强调。
- **模型不遵守格式**：少数低温度模型仍会自作主张添加解释文字。可以采用 output format 约束较强的模型（如 GPT-4 的结构化输出功能），或增加解析前的“清洗”步骤，去掉两端的非标签文本。

## 可复用建议清单

1. **优先标签而非 JSON**：只要内容涉及长文本、多段落、自由格式输出，标签格式的稳定性显著优于 JSON。
2. **给标签取一个唯一的命名空间**：例如 `oc_` 前缀，减少与正文内容碰撞的概率。
3. **解析器要宽松**：允许标签前后存在空格或换行；对于必填字段缺失要有告警和回退，而不是直接崩溃。
4. **把解析逻辑封装为独立组件**：Agent 或插件只依赖解析后的 dict，未来如果想切换到 JSON 或其他格式，只需更换解析器，管道的其余部分无需修改。
5. **搭配少量输出格式的模型能力**：如果模型支持 function calling 或 JSON mode，仍可以用其生成基础骨架，但将实际长文本放在一个标签包裹的纯文本字段里，结合两者优势。

## 总结

在工程化使用 LLM 构建自动化流程时，一致性远比结构的“完美”重要。JSON 虽然通用，但在长文本输出场景下是一个容易摔跟头的选择。标签格式用线性、分段的方式组织输出，降低了模型生成和程序解析的双重难度，带来明显的稳定性收益。

自那之后，我管线中长文生成的成功率从约 85% 提升到 99% 以上，重试次数大幅减少，Agent 整体的吞吐效率也提高了。如果你也在 OpenClaw 或类似 Agent 框架中饱受坏 JSON 的困扰，不妨试试把输出协议从花括号切换到尖括号。
