## 背景

在基于 Agent 的自动发帖流水线里，一条内容的生命周期通常会经过选题生成、正文撰写、图片生成或匹配、多平台分发几个阶段。对于需要长期运营的自动化项目，仅仅把内容推送到目标平台是不够的，必须保留一份结构化的本地存档。

没有归档的流水线一旦出现内容偏差、图片丢失或平台审核失败，几乎没法回溯当时到底产出了什么。尤其在图片由 AI 生成或从素材库动态组合的场景下，文章文本和图片文件分离，时间一长，对应关系就彻底断裂。于是我们开始在所有自动发帖流水线中强制实现本地归档：文章 Markdown、图片二进制文件，外加一份描述关联关系的 `assets.json`。

## 问题拆解

看似简单的“保存一下”其实会遇到三个具体问题：

1. **文章与图片的关联如何保持**  
   流水线内部可能使用临时 URL、base64 或内部 ID 引用图片，这些标识一旦离开运行时环境就失效。归档时需要把引用关系固化到一份机器可读的清单文件里，方便未来检索或重新上传。

2. **图片实体如何可靠落地**  
   网络图片可能下载失败、格式不一致、重名；本地生成的图片需要从临时目录移动出来并重命名。如果不对文件名做规范，以后几乎没法按日期或文章标题找回。

3. **流水线中断后归档的完整性**  
   如果归档步骤放在发布之后，发布失败可能导致归档缺失；如果放在发布之前，又可能浪费存储。需要选择合适的提交点，并处理原子性问题。

## 做法与步骤

我们的自动发帖流水线大致结构是：选题 → 生成文章 Markdown → 生成或选择配图 → 多平台发布。在“生成文章 Markdown”和“多平台发布”之间插入一个独立的归档步骤。

### 1. 约定目录结构

每条内容按日期和文章 slug 组织：

```
archives/
  2025/
    01/
      15-my-article-slug/
        article.md
        assets.json
        images/
          cover.png
          body_01.png
          body_02.png
```

日期和 slug 来自内容生成阶段产出的元数据，slug 由英文标题简化而成，保证可读性和唯一性。如果同一天产生多篇相同 slug 的文章，可以追加小时分钟，或者用内容哈希区分。

### 2. 生成 article.md

将 Agent 产出的 Markdown 原文直接写入，不做任何二次加工，保留所有原始 front matter 和链接，哪怕其中有临时 URL。这样后续复盘时可以准确看到当初准备发布的是什么。如果 Markdown 中插入了非本地的 HTTP 图片链接，不要删除，下一步会统一处理。

### 3. 处理图片并生成 assets.json

这是最关键的一步。首先遍历 Markdown 中的所有图片引用（`![](...)`），区分本地文件路径和远程 URL。远程图片统一下载到 `images/` 目录，本地图片（比如由 ComfyUI、Midjourney 等生成的临时输出）复制或移动到 `images/`。

文件命名规则：用图片在 Markdown 中的出现顺序或自定义的 `alt text` 决定。例如第一张图固定为 `cover.png`，后续插图命名为 `body_01.png`、`body_02.png` 等。同时记录原始 URL、下载成功状态、文件大小、宽高（可选）到 `assets.json`。

`assets.json` 结构示例：

```json
{
  "article": "15-my-article-slug/article.md",
  "generated_at": "2025-01-15T10:23:00Z",
  "images": [
    {
      "index": 0,
      "alt": "cover image",
      "original_url": "https://cdn.example.com/temp/a1b2c3.png",
      "local_path": "images/cover.png",
      "size": 102400,
      "width": 1200,
      "height": 630,
      "downloaded": true
    }
  ]
}
```

如果下载失败，`downloaded` 置为 `false`，并记录错误信息，方便后续人工补图。不因一张图失败中断整个归档流程，保证文章文本至少存档下来。

### 4. 原子性写入

为了不产生半成品目录，先在临时目录组装完整内容（如 `/tmp/archives/15-my-article-slug/`），确认所有文件写好后，用 `mv` 或 `os.rename` 整体移动到正式归档路径。这样可以避免流水线崩在半路时留下残缺目录。如果语言是 Python，可以使用 `tempfile.mkdtemp()` 和 `shutil.move`。

### 5. 集成到流水线

将归档步骤包装成一个独立函数或 cli 工具，输入为 Markdown 字符串和图片源列表，输出为归档路径。在发布步骤前调用，归档成功后才继续发布。归档失败则可以配置为是否阻断流水线（建议阻断，因为存储通常比第三方平台可靠）。

## 踩坑点

- **远程图片下载不稳定**：CDN 图片可能有防盗链、临时签名过期等问题。需要带 UA 头和重试逻辑，并且超时时间不宜过长，否则会阻塞流水线。可以设定单张图片下载超时 10 秒，整个下载环节总超时 30 秒，超时则跳过该图片，记录失败。
- **图片重名与扩展名缺失**：AI 生成的图片经常没有扩展名或叫 `output.png`。归档时必须通过文件头魔数判断真实格式，或解析 Content-Type 回退，统一补上正确的扩展名。否则后期看图片打不开。
- **JSON 中的相对路径**：`local_path` 统一使用相对于归档根目录的路径，不要写绝对路径，保证归档目录整体移动后仍然可读。同时 `assets.json` 本身放在文章同级目录。
- **并发写入同一 slug**：如果流水线支持并发处理多篇文章，可能同时产生相同日期 slug 的归档。需要加上毫秒时间戳或 uuid 后缀保证不冲突。但并发场景下归档通常不是瓶颈，尽量在线程维度排队写入。

## 可复用建议

把归档逻辑抽成独立模块，对外暴露一个简单接口：

```
archive(article_md: str, image_sources: dict[str, bytes|str]) -> str
```

`image_sources` 的 key 可以是 `cover`、`body_01` 等逻辑名称，value 为图片字节流或本地路径。模块内部完成目录创建、文件写入、下载重试、assets.json 生成和原子移动。这样不管是 Python 脚本、Node.js 进程还是 MCP 工具调用，都能服用同一套归档能力。

归档目录可以定期按年打包压缩（如 `2025Q1.tar.gz`），上传到对象存储或 NAS，保证低成本长期留存。不建议把大量小文件直接留在本地 SSD 上，容易 inode 耗尽。

另外，如果未来需要重新播放或迁移到新平台，可以从 `assets.json` 还原文章-图片映射，批量上载图片并替换 Markdown 中的链接，实现一键回放。

## 总结

自动发帖流水线的本地归档常常被当作“锦上添花”，但在实际运营中，它是唯一能在内容出错时给你提供原始现场的东西。方案核心很简单：约定好目录结构，用 `assets.json` 固化文章与图片的关联，采用原子写入避免脏数据。这部分实现不复杂，但需要把下载容错、命名规范和并发安全都考虑到位。一旦稳定运行，你会发现它能极大降低自动化内容运营的调试成本和心理负担——起码每一次自动发布都有迹可循。
