## 背景：自动化同步，离刷屏只有一步之遥
做过内容分发的开发者大多经历过这一幕：写完一篇技术文章，想同步到 Twitter、Discord、Telegram 频道、Reddit 和开发者社区。最直接的做法是写个脚本，调用各平台 API 一次性推送。结果常常是——

- 多个频道在同一分钟收到几乎相同的消息，被群友标记为 bot；
- Reddit 帖子被自动移除，Discord 服务器弹出警告；
- 不同社区的评论区各说各话，发布者根本没精力逐一回复，最后变成单向信息倾倒。

自动化发布如果缺少边界控制，很容易从效率工具沦为“刷屏引擎”。社区不是 RSS 订阅器，它有节奏、规范和上下文。我们需要让发布自动化具备礼貌感，而 OpenClaw 社区常用的 Agent + MCP 组合，恰好提供了工程化的约束手段。

## 问题拆解：为什么同步会演变成刷屏
在实践中，刷屏本质是三个维度的失控：

1. **内容冗余**：同一段长文无差别透传，Twitter 上显示不全，Discord 里撑满一屏，Reddit 标题过长被截断。
2. **时间集中**：所有平台几乎同时推送，叠加时区因素，部分社区正好在活跃高峰，形成瞬时信息冲刷。
3. **上下文割裂**：不感知社区当前讨论热点，一条冷冰冰的发布链接丢进去，缺乏本地化的开场或解释。

单纯加入 `sleep` 延迟只能缓解问题，无法解决结构性的不体面。我们需要一套可配置、可观测、可干预的发布流水线。

## 做法：一个具备边界感知的 Agent 发布流水线
基于 OpenClaw 框架，我们将发布流程拆成四个可编排的步骤，核心是用 Agent 模拟“编辑判断”，而 MCP connector 负责统一连接不同平台。

### 1. 建立社区发布档案（Community Profile）
为每个目标社区定义一份结构化配置，例如：

```yaml
twitter:
  max_length: 280
  prefer_summary: true
  allowed_tags: 2
  best_hours: "14:00-18:00 UTC"
discord_dev:
  max_length: 2000
  prefer_embed: true
  summarize_before_link: true
  cooldown_min: 30
reddit_programming:
  title_max: 300
  body_format: markdown
  require_community_notes: true
```

这份档案作为 Agent 决策的依据，避免硬编码逻辑散落各处。

### 2. 内容变形 Agent：一源多发，但形态各异
主 Agent 接收原始 Markdown 正文后，会调用子 Agent（或使用 LLM 工具）针对不同社区生成变形版本：

- **Twitter**：提取核心观点，生成 2 条串推，附带视觉图。
- **Discord**：生成 200 字以内的摘要 + 原文链接，使用 Embed 格式。
- **Reddit**：生成适合社区风格的标题，正文补充创作背景，末尾附可交互提问。
- **Telegram/微信**：提供短文本 + 关键词标签，不使用 `#` 刷屏。

这个过程中，Agent 会对比变形后内容与原始内容的语义相似度，若低于阈值（如 0.85）会要求重新生成，防止失真。

### 3. 调度与限流 Agent：节奏就是边界
发布 Agent 使用优先级队列，根据 `best_hours` 和 `cooldown_min` 安排发送顺序。引入以下规则：

- **每日上限**：每个社区每日最多 N 条原创发布（N 可配置）。
- **最小间隔**：同一社区至少间隔 X 分钟，跨社区至少间隔 Y 秒。
- **去重指纹**：计算内容哈希（忽略格式），24 小时内相同指纹不发第二次。

Agent 在发送前还会通过 MCP 查询目标社区最近 10 条消息的主题向量，如果发现同一话题正在被激烈讨论，自动降级为“暂缓”，等待下一个合适窗口，或切换为纯评论互动而非新开贴。

### 4. 闭环监控：发布不是结束
发布后，Agent 会监听目标社区的回复，利用预设的意图识别（感谢、提问、反对等），自动回复感谢或引导至原文评论区。如果收到负面反馈（如“spam”举报），立即暂停该社区本月其余自动发布，并通知人工介入。

## 踩坑实录
- **API 速率限制不是简单的 429**：Discord 会对单个 Webhook 有 5 次/2s 的限制，Reddit API 对标题相似度有隐式去重。需在 MCP connector 中实现指数退避和请求合并，避免连续撞墙。
- **Markdown 到平台的适配成本**：Reddit 支持表格，Discord 不完全支持；Discord Embed 有字段数量限制。Agent 变形时容易出现格式混乱。建议先输出纯文本版，再按平台规则注入格式化。
- **时间窗口的误伤**：配置的最佳时段若使用静态字符串，可能因为夏令时或服务器时区偏差失效。应统一转为 UTC 并基于真实活跃度数据动态调整。
- **“发布太少”与“体面过载”的平衡**：团队容易走向两个极端——要么担心刷屏而什么都不敢发，要么忽略所有边界强行推送。建议先在 2-3 个社区灰度运行 2 周，收集真实反馈后调参。

## 可复用建议
1. **渐进式上线**：先跑一条“仅发给我自己”的调试通道，检查变形结果和时间表是否符合预期。
2. **保留手动按钮**：在 Dashboard 中为每条待发内容留一个“批准发送”按钮，自动化只做预投递。
3. **决策日志透明**：Agent 每次跳过、延迟或修改内容时，输出结构化 reason，方便回溯。
4. **指纹去重不仅是文本**：加入 URL、图片 OCR 文本的哈希，避免换了推文文字但仍然是同一篇文章的重复发布。
5. **社区反馈回路**：将用户反应（点赞、点踩、回复情绪）回写到社区档案中，让调度策略持续进化。

## 总结
自动化发布的目的不是让作者从社区中消失，而是帮助内容触达那些处在不同信息渠道的读者。边界控制不是限制效率，而是延续社区对你的信任。通过 Agent 感知上下文、变形内容、控制节奏，我们可以在多社区同步中保持“在场又不扰民”的分寸感。用工程化手段管住推手的冲动，才是长期可用的自动化。
