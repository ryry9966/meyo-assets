## 背景

使用 Agent 或自动化脚本生成文章并推送至社交媒体、博客平台，已成为不少开发者的日常。这类流水线通常以 Markdown 为输出格式，正文链接云端图片，最后通过 API 完成发布。但整个过程中，一个容易被忽视的环节是**本地归档**：生成的内容散落在临时目录或只在目标平台留存，过段时间回头看，素材消失、版本难追溯、调试时反复生成相同内容，既浪费 token 也影响质量评估。

本文将介绍一种轻量的本地归档方案，用一篇文章、一组图片和一个 `assets.json`，以目录形式把每次产出的成果固定下来。

## 问题

典型的发帖流水线大致如下：

- Agent 调用 LLM，根据 prompt 生成 Markdown 正文  
- 同时可能通过图片生成服务产生配图（返回临时 URL）  
- 将这些内容通过 WordPress、Twitter 等 API 发布  
- 发布成功后，本地无任何残留，或仅在数据库里存一个链接

这里至少有三个麻烦：

1. **图片链接时效性**：多数 AI 图片服务的生成结果只在短时间内可访问，一两天后链接失效，想在本地重现文章视图就缺图了。  
2. **内容回溯困难**：文章曾用哪个版本的 prompt、什么模型、生成了多少 token 都无从查证。  
3. **团队协作/审核需求**：多人共用一套流水线时，缺乏结构化的资产清单，很难对历史产出做审计。

理想的状态是：每次运行完成后，自动在当前工作区创建一个以日期和标题命名的文件夹，里面包含最终版 Markdown、所有配图的本地副本，以及一份记录完整上下文的元数据文件。

## 做法与步骤

我采用的归档结构如下（以一次发布文章为例）：

```
post-archives/
└── 2025-01-01-how-to-debug-agents/
    ├── index.md
    ├── images/
    │   ├── img1.png
    │   └── img2.webp
    └── assets.json
```

其中 `assets.json` 的定义大致为：

```json
{
  "post_id": "20250101-debug-agents",
  "title": "How to Debug Agents",
  "generated_at": "2025-01-01T08:30:00Z",
  "model": "gpt-4o",
  "prompt_key": "agent-debugging-v2",
  "content_file": "index.md",
  "images": [
    {
      "local_path": "images/img1.png",
      "remote_url": "https://img.example.com/gen/abc123.png",
      "alt_text": "错误排查流程图",
      "width": 1200,
      "height": 800
    }
  ],
  "tags": ["agents", "debugging"],
  "status": "draft"
}
```

集成到 Agent 流水线的步骤：

**1. 抽取图片 URL**  
在 Agent 拿到 Markdown 正文后，用正则提取所有 `![...](url)` 中的 URL。注意区分已经是本地相对路径的图片（跳过）。

**2. 下载图片到本地 images/**  
遍历提取到的远程 URL，使用 `requests` 或 `httpx` 下载二进制流，用 UUID 或递增序号重命名（保持扩展名）。这里建议设定 5~10 秒超时，失败时记录错误信息并在 `assets.json` 中标记 `download_error`。

**3. 生成 assets.json**  
收集本次运行的环境变量（模型名称、prompt 版本、时间戳等），将图片映射填入，连同文章元数据一并写入 JSON 文件。为了保持可读性，JSON 需要格式化，建议用 2 空格缩进。

**4. 重写 Markdown 中的图片链接（可选）**  
为了让本地归档完全自包含，可以将 Markdown 里的远程图片 URL 替换为 `images/img1.png`，新文件存为 `index.md`。如果仍需保留原始链接以便发布，可另存一个 `original.md`，或在 `assets.json` 中记录一次转换映射。

**5. 归入日期命名的文件夹**  
用一个工具函数将上述文件移动到 `post-archives/` 下约定好的路径。整个归档过程可以作为 Agent 工具链中的一个 MCP 工具或独立 CLI 脚本，在任何“发布前”步骤被调用。

## 踩坑点

- **图片下载的健壮性**：外链可能很快失效，一次性下载成功率不是 100%。需实现重试和错误队列，失败图片用本地占位图（如 `missing.png`）代替，防止归档中断。  
- **大图片与 Git 仓库**：图片过多或过大会撑大 Git 历史，可配合 `.gitignore` 或 Git LFS，或者将归档目录放在 Git 之外。  
- **并发安全**：如果多人流水线同时在同一归档目录下写文件，可能出现文件名冲突。建议用 `post_id` 或时间戳加随机后缀保证唯一性，避免直接使用标题作为目录名。  
- **图片格式兼容性**：某些 AI 生成的图片可能是 `.webp` 或 `.bmp`，本地预览工具未必支持，归档时不用强制转换格式，保留原始文件，仅在 `assets.json` 里记录 format 即可。  
- **markdown 相对路径处理**：替换图片链接时需要注意基础目录，如果归档后的 `index.md` 引用 `images/img1.png`，必须确保相对路径在归档目录内有效。

## 可复用建议

- **封装为最小化工具**：做成一个接收 `markdown_content` 和 `remote_image_urls[]` 的函数或命令行工具，输出归档目录路径与 `assets.json` 的路径。这样可直接嵌入任何 Python / Node.js 流水线。  
- **与 MCP 集成**：如果使用支持 MCP 的 Agent 框架，可以将归档工具注册为一个工具服务，大模型能在合适的时机主动调用，例如“内容生成完毕，请保存归档”。  
- **生成本地预览页面**：可选地，从 `assets.json` 和 `index.md` 生成一个简单的 `preview.html`，方便在文件管理器中直接双击查看。  
- **加入版本控制**：建议对归档目录启用 Git，每次归档后自动 commit，commit message 包含 post_id 和标题，实现完整的时间线追溯。

## 总结

自动发帖流水线的本地归档并不是复杂的工程，但能显著提升耐用性与可审计性。用三个简单的元素——Markdown 文件、本地图片、`assets.json`——就能把一次生成固化成可随时查看和复用的资产。对于追求工程化和长期维护的自动化内容管线，这几十行代码的投入是相当值得的。
