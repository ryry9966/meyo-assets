## 背景

在社区运营或内容分发链路中，将长文、每日播报同步到微博超话是一项重复但必要的动作。手动操作不仅耗时，还容易因疏忽导致漏发。引入自动化后，稳定性和可观测性就成了工程重心。最近基于 OpenClaw Agent 搭建了一条微博超话同步流水线，核心挑战聚焦在三点：图片上传链路的处理、不透明的接口限流，以及同步任务的状态归档。这篇记录分享整个踩坑与收敛过程，面向有类似自动化需求的 Agent / MCP / 插件开发者。

## 问题拆解

微博开放平台的超话发帖流程并不算复杂，但工程化后需要直面几个现实问题：

1. **图片上传环节**：开放平台 `statuses/upload` 对图片大小、格式有隐性限制。传图失败时错误码模糊，上传成功的 `pic_id` 在后续发帖接口中若未正确拼接，图片会静默丢失。
2. **超话发帖约束**：发帖必须携带超话标识字段，且不同超话的 ID 需要事先固化，动态搜索可能触发风控。
3. **限流规则不透明**：除开放平台文档标明的频率外，实际运行中会出现 10022 类“操作太频繁”错误，触发条件可能是用户级、IP 级甚至内容模式关联。
4. **状态管理缺失**：一旦自动任务中断，无从知晓哪些内容已发、哪些因限流等待，恢复成本高。

## 做法

### 1. 整体流水线设计

流水线由 OpenClaw Agent 驱动，内容来源为上游系统下发的 Markdown 文本与图片列表。Agent 编排三个核心工具：图片预处理、上传与发帖、状态落库。工具通过 MCP Server 提供标准化调用，便于在不同 Agent 间复用。

```
[内容清单] -> [图片预处理] -> [上传获取 pic_id] -> [超话发帖] -> [状态归档]
                                                           |
                                               (限流时进入退避队列)
```

### 2. 图片预处理与上传

考虑到开放平台限制，上传前对图片做本地净化：

- 使用 Pillow 将图片统一转为 JPEG（质量 85%），长边不超过 2000px，体积严格控制在 4.8MB 以内。
- 对 GIF 图转为静态首帧，避免动图导致的意外审核。
- 上传时通过微博开放平台 `statuses/upload` 接口，采用 `multipart/form-data` 上传，并解析返回的 `pic_id`，存入临时上下文。

关键代码片段（Python 示意）：

```python
def upload_image(access_token, img_path):
    url = "https://api.weibo.com/2/statuses/upload.json"
    with open(img_path, 'rb') as f:
        files = {'pic': f}
        data = {'access_token': access_token}
        resp = requests.post(url, data=data, files=files, timeout=30)
    return resp.json().get('pic_id')
```

### 3. 超话发帖与参数组装

微博发帖接口 `statuses/update` 支持通过 `topic` 字段关联超话，但官方文档建议使用超话 ID 并以特定格式拼入 `status` 文本，例如：`#超话名称#[超话ID]#`。为保证兼容，我们同时传入 `topic` 参数并在文本嵌入双井号格式。图片 ID 通过 `pic_id` 参数传入（多图使用逗号分隔）。

```python
status_text = f"#每日播报# 来了 {content[:100]}... #超话名称[123456]#"
params = {
    'access_token': access_token,
    'status': status_text,
    'pic_id': ','.join(pic_ids),
    'topic': '超话名称',
}
```

### 4. 限流处理机制

沿用经典的令牌桶 + 指数退避策略：

- 发帖频率限制设为 60 秒 1 次（远低于官方报错阈值），用 `asyncio` 队列排队。
- 当接口返回错误码 10022 或 10024 时，进入退避逻辑：首次等待 5 分钟，指数增加至最大 30 分钟，连续失败 3 次后任务转入人工待处理状态。
- 分布式场景下通过 Redis 锁控制同一账号的唯一发帖令牌，防止多实例并发触发风控。

### 5. 状态归档设计

使用 SQLite 建任务状态表，记录每一条待发内容：

```sql
CREATE TABLE sync_task (
    id TEXT PRIMARY KEY,
    content_hash TEXT,
    images TEXT,
    status TEXT,           -- pending/uploading/posted/failed
    pic_ids TEXT,
    weibo_id TEXT,
    retry_count INTEGER DEFAULT 0,
    last_error TEXT,
    created_at INTEGER,
    updated_at INTEGER
);
```

每次发帖成功后将 `status` 置为 `posted`，保存微博 id。任务启动时仅捞取 `pending` 或 `failed` 且 `retry_count < 3` 的记录，确保断点续传。归档日志同时输出到 OpenClaw 的运行面板，便于实时观测。

## 踩坑点

- **图片上传返回空 pid 不报错**：某些边缘格式（如 CMYK JPEG）上传成功但 `pic_id` 为空，导致发帖时图片丢失。解法是上传完立刻检查 `pic_id` 是否非空，否则归类为失败并转人工。
- **超话 ID 固化**：依赖动态搜索接口经常因限流而失败。预先通过「超话搜索」接口或人工确认将目标超话 ID 写入配置文件，长期稳定。
- **文本长度计算陷阱**：超话格式串 `#话题名[ID]#` 会占用部分字符，微博正文上限 140 字（已逐步放宽至 2000 字），但超话附加文本若截断可能使链接失效，需在构造 `status` 时动态计算剩余可用长度。
- **限流粒度深于预期**：除了发帖频率，连续发相同内容的图片也会触发内容重复检测，导致账号被临时限制。加入随机微调（末尾添加 Unicode 零宽空格等）虽不推荐，但可降低死板模板的风险——更推荐让内容本身具备差异。

## 可复用建议

1. **封装为 MCP 工具**：将图片上传、发帖、状态查询暴露为三个 MCP 工具，支持 OpenClaw Agent 或其他 LLM 编排器直接调用，降低接入成本。
2. **状态表作为可靠性锚点**：无论自动化程度多高，持久化的状态表都能在异常后复原，建议字段包含 `idempotency_key`，防止重复提交。
3. **限流策略可配置化**：将频率、退避时间、最大重试次数做成配置文件或环境变量，方便在不同账号或测试环境切换。
4. **做轻量审计面板**：在 OpenClaw 工作区添加一个展示最近 50 条发帖状态的卡片，醒目提示失败项，避免「静默丢帖」。

## 总结

微博超话同步的自动化，难点不在单次调用，而在如何让链路在图片、限流、状态这三个维度都足够抗揍。把流程固化到 Agent 工具链里，并加上严谨的状态归档，就能从一个脆弱的脚本升级为可长期运行的工程组件。以上实践均已在社区自动化项目中平稳运行两周，掉帖率降至零。如果你也在做类似跨平台同步，希望这些经验能提供一些可落地的参考。
