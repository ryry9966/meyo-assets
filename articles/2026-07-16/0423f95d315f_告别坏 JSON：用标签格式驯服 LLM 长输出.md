## 一、背景：被坏 JSON 支配的恐惧

在构建 OpenClaw 这类 Agent 时，向 LLM 要结构化数据是家常便饭。任务执行器需要从模型输出中提取下一步动作、参数、中间思考，再用这些结果驱动 MCP 工具、操作浏览器、读写知识库。最开始大家几乎都选 JSON——生态完善，几乎所有语言一行 `json.loads()` 就能拿到字典。

问题出在**长文输出**。一篇分析报告、一份多页表格、一段持续迭代的设计稿，输出长度轻松超过 2000 token。实际跑起来你会发现：

- 长 JSON 在一次生成中被意外截断（如 token 限制、流式提前关闭），得到 `{"key": "value` 这种半截字符串。
- 字符串内出现未转义的双引号、换行符，直接把结构破坏。
- 模型输出嵌套很深的 JSON 时，偶尔会丢失某个括号或逗号。
- 使用 `response_format: json_object` 等约束会放大“幻觉”风险：当模型必须填充一个过大的结构时，容易出现重复填充、遗漏字段。

更头疼的是，这些东西在长文场景里几乎没法通过简单的 prompt 工程根治。重试会浪费 token 和耗时，而且重试样本的截断位置可能每次都不同，让解析器变得无比脆弱。

## 二、问题本质：JSON 为什么在长文里“水土不服”

根本原因是自回归生成与 JSON 的严格语法之间存在张力。

1. **不可恢复的语法破坏**：JSON 要求整个字符串从第一个字符到最后一个字符都是合法语法。只要中途出错，整个文档废弃。
2. **流式输出与闭包冲突**：很多场景需要边生成边消费，但 JSON 的括号必须闭合才能解析。`]}` 一旦迟到，前面已经生成的 8000 字符全卡在 buffer 里。
3. **嵌套深度带来的“括号债”**：模型不是编译器，不会压栈计数。长 JSON 中嵌套超过三层后，括号配对错误率明显上升。

解决方向其实很朴素：**降低语法耦合度，让解析可以分段进行，允许部分失败时仍能抢救有效信息。**

## 三、做法：转向自定义标签格式

我目前在项目里采用的替代方案是用 **类 XML 标签 + 段落式分隔**，本质是把一个长输出拆成多个包含独立语义的区块，解析时按区块提取，不依赖全局语法。

### 3.1 设计输出合同

以“分析一篇文档并生成摘要、关键词、待办”的长文任务为例，定义如下标签：

```text
<ANALYSIS>
...自由文本，允许任意字符，包括引号、换行...
</ANALYSIS>

<SUMMARY>
...摘要内容...
</SUMMARY>

<KEYWORDS>
keyword1, keyword2, ...
</KEYWORDS>

<TODOS>
- [ ] todo item 1
- [ ] todo item 2
</TODOS>
```

标签名不与常见自然语言冲突即可，比如用 `@RESULT_START` / `@RESULT_END` 也行，可以进一步降低误识别。

### 3.2 Prompt 模板核心

```text
You will output the result using the following format EXACTLY. 
Do not wrap with ``` or any other markdown fences. 
Output raw text.

<SECTION_TAG>
content...
</SECTION_TAG>

Your task: ... (任务描述)
```

关键是要给一个带真实内容的完整示例，让模型照猫画虎。最好把示例中的长文本用占位符代替，避免模型简单复制。

### 3.3 解析器实现（可用 Python 示意）

```python
import re

def parse_tagged_output(text: str) -> dict:
    pattern = r"<(\w+)>\s*(.*?)\s*</\1>"
    matches = re.findall(pattern, text, re.DOTALL)
    result = {}
    for tag, content in matches:
        result[tag.lower()] = content.strip()
    return result
```

这个解析器故意用非贪婪匹配 `.*?`，即使模型多输出了空格或换行，仍能正确提取。如果某个标签未闭合，它只会丢失该块，不会影响其他已闭合标签的提取。

### 3.4 流式处理增强

当输出以 chunk 到达时，可以维护一个标签栈。遇到开始标签时开启缓冲，遇到闭合标签时触发解析回调。这样即使连接断开，已闭合的区块也能被上层消费，避免全局阻塞。

## 四、真实踩坑与应对

1. **标签名冲突**  
   模型可能在分析正文中引用“标签”这个概念，写出 `<TAG>` 字样。解决方法是选更冷门的分隔符，如 `@!SECTION!@`，或要求模型用全大写的唯一 UUID 后缀：`<RESULTS_7A3F>`。实践中，全大写英文单词加下划线基本不出问题。

2. **标签嵌套错乱**  
   避免设计嵌套标签，因为模型几乎不会正确处理嵌套闭合。所有区块扁平化排列，顺序固定。需要层级关系时，用多个独立标签并在解析层组合。

3. **内容中的特殊字符干扰**  
   如果区块内容可能包含 `</TAG>` 这样的文字，需在 prompt 中明确要求转义，或让模型用单字拆分（比如 `<` 写为 `&lt;`），但这是双刃剑——要求转义可能引入新的错误。权衡后我选择不转义，而是在解析时采用严格的标签结束匹配：`</TAG>` 必须单独成行，或前面有特定前导空白。这种方式降低了误判概率。

4. **模型“忘记”关闭标签**  
   在长文生成尾部，注意力漂移会导致尾部的 `</TODOS>` 被省略。处理方式是：在 post-processing 中，允许最后一个标签即使不闭合，也把剩余内容捕获为原始文本，做降级处理；同时配合重试策略，若关键标签（如 SUMMARY）缺失，则重新生成。

## 五、可复用建议

- **选择分隔符**：优先考虑 `@SECTION_NAME@` 或 `[SECTION_NAME]`，避免 XML 惯用尖括号可能被模型误认为是 HTML 而自行补全。
- **分段验证**：解析后对每个字段做轻量校验（如非空、长度合理），失败字段做 fallback，不必全盘丢弃。
- **组合 JSON 使用**：对于短小且结构固定的数据（如配置项），仍然用 JSON，因为生态工具成熟。标签格式主要解决长文、非固定长度、多段文本的稳定性。
- **把标签格式固化到系统提示**：在 agent 的 system prompt 里约好输出协议，并在对话历史中用 few-shot 示例强化。可以显著提升长对话场景下的一致性。
- **容错解析器原则**：宁可多捞，不可崩。先尝试提取所有可能标签，再用业务规则裁剪多余内容，比要求输出绝对清洁更务实。

## 六、总结

从坏 JSON 转向标签格式，本质上是用**工程上易于恢复的分段结构**取代**必须全局正确的树形结构**。它让 LLM 在长文输出时更像一个 obedient 的作家，而不是一个需要每一步都编译通过的编译器。对于 OpenClaw 这类需要稳定编排多个步骤的 Agent 系统，这种降维式的结构化方式，往往比死磕 JSON 性价比高得多。

下次你的插件因为一个缺失的 `}` 而整段垮掉时，不妨试试标签格式——它不能解决所有问题，但能让你的解析器从“全或无”变成“少失多捞”。
