## 背景

在基于 Agent 的自动发帖流水线中，一条完整的内容链路通常包含：选题 -> 撰写 -> 配图生成 -> 发布。不少开发者会把重心放在内容生成和平台适配（如 OpenClaw 的发布插件或 MCP 工具），但往往忽略本地归档这一环。

笔者在维护一个基于 OpenClaw + 多 Agent 协作的自动内容项目时，发布侧已经稳定，但几周后发现有几个严重问题：曾经生成过的一篇技术解读文章再也找不回原始 markdown；一张花费 token 生成的解释性插图丢失了；想复现某个失败发布任务的上下文，只能翻日志，素材早已被下一次运行覆盖。

既然整条流水线已经自动化，归档也不该是人工操作。我们需要一个轻量、易复现、与平台解耦的本地归档方案，让每一篇生成的内容连同配图和元数据一起落地保存。

## 问题拆解

流水线产出的可归档对象有三种：

1. **文章正文**：可能是纯文本、markdown 格式，或者是经过平台适配后的最终内容。
2. **配图文件**：AI 生成封面、插图，或从图库选取的图片，通常以临时路径存在，面临被清理的风险。
3. **资产关系**：哪张图对应哪篇文章？图床链接是什么？本地路径是什么？生成时间、prompt 等元信息。

没有记录这些关系，图片就成了散落的二进制文件，难以被二次利用。因此需要一个 `assets.json` 来描述这种对应关系，并确保整个归档步骤幂等、不阻塞发布流程。

## 方案与步骤

### 1. 目录结构约定

所有归档文件放在项目根目录的 `archive/` 下，按日期子目录组织：

```
archive/
  2025-03-27/
     article.md
     assets.json
     img/
       20250327_cover.png
       20250327_diagram.png
```

日期采用内容生成时间，保证同一批发布的内容集中管理。

### 2. 设计 assets.json 结构

记录文章关联的所有图片资产，同时保留生成上下文，方便后续复现或交接：

```json
{
  "post_id": "20250327-tech-pipeline",
  "title": "自动发帖流水线的本地归档设计",
  "created_at": "2025-03-27T10:15:00+08:00",
  "platform": "xiaohongshu",
  "markdown_file": "article.md",
  "assets": [
    {
      "id": "cover",
      "original_url": "https://cdn.example.com/img/abc123.png",
      "local_path": "img/20250327_cover.png",
      "alt_text": "归档流水线架构图",
      "prompt": "An isometric technical diagram...",
      "mime_type": "image/png"
    }
  ],
  "metadata": {
    "generated_by": "openclaw-content-agent",
    "model": "gpt-4o",
    "tags": ["归档", "自动化"]
  }
}
```

字段选择上有一条原则：**最少必要记录，但保证可追溯**。`original_url` 保留图床链接，即使本地文件丢失也可重新下载；`prompt` 保存最初的生成 prompt，供未来优化配图用。

### 3. 文章内容捕获

大多数 Agent 流水线会产出 markdown 格式的文章。如果是直接在内存中拼接后发布，可以在发布前将最终文本写入归档文件。关键点是内容要与发布时完全一致，不能包含归档时才添加的调试信息。

如果项目中使用 OpenClaw 的插件体系，可以在发布动作之前注入一个 `pre-archive` hook，把原文写入 `article.md`。如果流水线是脚本形态，就更简单——直接由主流程写入。

### 4. 图片下载与重命名

AI 生成的图片通常会先上传到图床，但本地没有副本。归档步骤需要从 `original_url` 下载图片并存入 `img/` 目录。可复用的做法：

- 统一文件名：`{YYYYMMDD}_{asset_id}.{ext}`，避免特殊字符。
- 使用 `uuid` 作为 fallback，确保无重名冲突。
- 下载时加入重试逻辑（3 次，指数退避），网络波动是常态。
- 下载完成后写 assets.json 的 `local_path`。

为了不阻塞发布，图片归档可以异步进行，但必须确保 `assets.json` 最终包含准确的 `local_path`。如果下载失败，也应记录错误状态，而不是丢弃整个条目。

### 5. 集成到流水线

整体流程调整为：内容生成 -> 图片生成/上传 -> （归档步骤） -> 发布。归档步骤严格放在发布之前，但失败不应阻断发布，否则就是过度工程化了。

一个稳健的集成方式是把归档模块设计为 MCP 工具（archiver），暴露一个 `archive_post(article, assets_list)` 接口。流水线 Agent 在发布前调用该工具，工具内部完成目录创建、文件写入、下载、json 更新，全部包裹在 try/catch 中，异常只记日志并降级，不向上抛出。

## 踩坑实录

1. **路径穿越**：用户输入的文章标题可能包含 `../`，构造文件路径时必须做 sanitize，否则会导致写入意外目录。解决办法：直接使用 `post_id`（自定义 ID）或时间戳作为目录名，不用标题。
2. **并发写入**：多条流水线同时运行时，对 `assets.json` 的写入需要考虑原子性。如果用 Node.js，可以采用写临时文件再重命名的原子写入模式；Python 用 `tempfile` + `os.replace`。理论上同一日期目录下的 `assets.json` 可以是一篇文章一个 json 文件（如 `assets_20250327-a.json`），再按需聚合，避免锁竞争。
3. **图片下载超时**：有些图床对非浏览器请求会限速，直接用默认超时会频繁失败。建议设置 HTTP 超时为 20s，重试后仍失败时保留 `original_url` 作为唯一引用，`local_path` 留空并标记 `download_failed: true`。
4. **JSON 逃逸混乱**：prompt 文本里经常包含双引号、换行符，序列化时必须正确处理。如果手动拼字符串很容易出错，必须使用标准 JSON 库，不要图省事搞模板字符串拼接。
5. **储存空间膨胀**：配图体积可能很大，长期运行会撑满磁盘。建议图片格式统一转为 webp 并限制最大宽度（如 1200px），归档步骤就能兼任简单的压缩。或者在 strategy 中设置定期归档清理，但这是后话。

## 可复用建议

- **与发布平台解耦**：归档逻辑不应包含任何平台特有的 API 调用，只接收标准化输入（article_markdown, assets_list）。这样无论是小红书、Twitter 还是博客，都能复用同一套档案系统。
- **作为独立模块/库**：如果把归档封装成 `post-archiver` 包，可以用在各种 Agent 项目中，通过环境变量或配置文件指定归档根目录。配合 Git 一起使用，还能获得版本历史。
- **元数据驱动未来用途**：`assets.json` 中的 prompt、模型、时间戳等信息，未来可用于训练数据整理、复盘发帖效果、重建图片等。多记录一点不会增加多少负担，但缺失了就永久丢失。
- **与 Obsidian 等本地知识库联动**：归档目录可直接被 Obsidian 打开，形成可视化的内容地图，进一步提升本地工作流的价值。

## 总结

自动发帖流水线中加入本地归档，不是“锦上添花”的额外开销，而是防止资产流失的基础设施。通过约定目录结构、用 `assets.json` 记录资产关系、将归档逻辑做成可插拔的模块，我们可以实现一个低耦合、高可靠的归档步骤，完整地保留每个生成内容的原始印记。

当某天你需要复盘某个爆款笔记是怎么生成的，或者想重新利用一张曾经生成的信息图时，那个本地的 `archive` 目录就是最好的答案。
