## 背景

最近在做内容分发管线时，需要将 AI 生成或人工创作的内容同步到微博超话。由于发布频率不高但持续稳定，手动操作性价比很低，于是决定用脚本来兜底。

选型上，没有使用第三方商业工具，而是直接基于 HTTP 请求构建最小自动化：用 Python + requests 维护一个会话，调用微博的图片上传与发帖接口，再通过本地 SQLite 做状态归档。整个流程集成到 OpenClaw 的任务编排里，作为 Agent 的一个可调用插件运行。

这篇文章不讨论“全自动养号”“矩阵爆款”，只从一个工程化实践的角度，记录在图片上传、限流应对和状态追踪三个环节踩过的坑、采取的方案以及可复用的思路。

## 问题拆解

同步一个超话帖子，本质上只有两步：上传图片 → 发送帖子。但在工程实现中，会遇到三类核心问题：

1. **图片上传**：接口限格式、限大小，有时需要特殊 referer 或登录态，上传得到的 `pid` 可能过期或无效。
2. **接口限流**：短时间大量请求会被直接拒绝，甚至出现“发送成功但仅自己可见”的隐性限流。
3. **状态不可见**：脚本返回的成功不代表帖子真的公开可见；没有归档就无法追踪哪些已发、哪些待重试。

下面按工序说明我是怎么解决的。

## 1. 图片上传：预处理与接口适配

微博图片上传接口通常会校验文件类型和尺寸。实际测试发现，即使接口没有明确报错，非 JPEG/PNG 图片或过大文件也可能导致发布后图片不显示。

因此第一步是本地预处理：

- 统一转换为 JPEG，质量 85。
- 限制长边最大 1280px，降低文件体积同时保留足够清晰度。
- 使用 Pillow 进行重采样，保留 EXIF 信息。

处理后的图片通过 `requests.Session` 上传，维持 `Referer: https://weibo.com`，携带完整的 cookie（从浏览器手动导出后再定期刷新）。上传接口返回的 JSON 中提取 `pid`，并在发帖时将 `pic_id` 参数带上。

踩坑记录：
- 部分超话要求图片数量至少 1 张，所以纯文本贴需额外处理，脚本逻辑中会增加一个默认配图占位。
- 若上传接口返回 `-100` 或空 pid，通常是 cookie 失效，需要在归档里标注“登录态过期”，并触发告警。

## 2. 限流应对：频率控制 + 隐形降权检测

微博的限流至少有两个层级：

- **显性限流**：接口返回“发布过于频繁，请稍后再试”，通常会带上等待秒数。
- **隐性限流**：接口返回成功，帖子也存在，但未登录状态下不可见，或者只在“仅自己可见”下出现。

针对显性限流，我在发帖请求中建立了指数退避：首次遇到 429 时 sleep 60s，连续出现则依次加倍，最长等待 15 分钟。每发完一条也会故意休息 90~120 秒，加一个随机抖动的间隔。

隐性限流更加隐蔽。检测手段是：发帖成功约 3 分钟后，通过无登录 cookie 的独立 session 访问帖子详情页，检查是否能正常获取内容。如果得到“抱歉，此微博已被作者删除”等字样，或者状态码异常，就判定为“发布异常”，归档时标记为 `shadow_ban`，等待人工复核。

这个检测步骤对时效性要求不高，所以在 OpenClaw 中作为异步后置任务执行，不影响主流程吞吐。

## 3. 状态归档：让每一次发布可追溯

之前用脚本跑的时候，经常会忘记哪些发过、哪些失败，翻日志很痛苦。后来专门设计了一个 sqlite 表来归档：

```sql
CREATE TABLE weibo_posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL,
    content TEXT,
    image_paths TEXT,
    pid_list TEXT,
    post_url TEXT,
    status TEXT CHECK(status IN ('pending','success','failed','shadow_ban','token_expired')),
    retry_count INTEGER DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

每次发布任务创建一个 `task_id`，记录原始内容与图片路径。上传完成后更新 `pid_list`，发帖成功后保存 `post_url` 和公开可见性检查结果。

重试逻辑上，仅对 `failed` 或 `token_expired` 状态自动重试，最多 2 次，且需要更换 cookie。`shadow_ban` 状态不自动重试，而是收集后统一在巡检时人工处理。

归档的价值不止于重试，还可以用于统计最佳发布时间、内容长度与互动关系等后续分析。

## 可复用的建议

1. **不要依赖脚本运行结果表面上的“成功”**，一定要加入隐性降权检测。
2. **把登录态管理做成可外部刷新的**，比如从环境变量读取 cookie 字符串，方便过期后快速替换。
3. **控制总速率**，单日总量限制在 20 条以内，脚本本身远比手动更稳定，但不等同于更安全。
4. 如果你的自动化框架是 OpenClaw，可以将这套逻辑封装为 Tool/Plugin，配合任务队列和通知通道，形成一个内容分发节点。
5. 图片上传处理建议放在本地独立函数，方便单独测试和横向复用。

## 总结

微博超话的自动化发布并不复杂，复杂的是处理好“不完美的接口”和“不透明的规则”。图片上传、限流与状态归档这三件事，看似独立，其实共同决定了一套自动化系统的可靠性。

工程化就是：不要让系统在未知状态中沉默，哪怕是一条帖子的“仅自己可见”，也应当被记录、被预警、能被追溯。

以上实现完全基于对公开接口的合规使用，仅用于个人低频内容同步场景。
