# 多社区同步的边界：自动化发布如何避免刷屏

## 背景

如果你维护着一个需要同时触达多个社区的项目（如开源工具、开发日志、技术文档），大概率遇到过这样的困境：一篇内容写好后，希望在 GitHub Discussions、Discord、Telegram、自建论坛、Slack 等多个渠道同步推送。手动操作不仅繁琐，还容易遗漏；而一旦引入自动化脚本或 Agent，稍有不慎就会在短时间内对同一群用户造成信息轰炸——不同平台的消息最终汇聚到同一个人的手机屏幕上，体验极差，甚至触发平台的频率限制或封禁。

在 OpenClaw、Agent、MCP 这类可组合自动化的技术栈中，我们完全可以构建一个“有边界感”的多社区同步管道。本文基于实际踩坑，梳理一条工程化思路。

## 问题拆解

“刷屏”的来源主要有三个层面：

1. **时间密集**：多个渠道在数秒内集中推送，用户在同一时间轴看到高度重复的信息。
2. **内容雷同**：直接全文搬运，没有考虑各平台的信息消费习惯。
3. **缺乏去重**：对已经通过其他渠道触达同一受众的情况无感知，造成重复曝光。

从平台风控角度看，短时间内高频发布相似内容也可能被判定为 spam，导致账号受限、Webhook 被禁用，甚至 IP 进入黑名单。

## 设计思路：发布节奏 + 内容分层 + 去重窗口

我们基于 OpenClaw 搭建了一个发布调度 Agent，用 MCP 封装了各平台的发送工具（Discord Webhook MCP、Telegram Bot MCP、GitHub API 封装等）。核心策略不是“一次性全发”，而是**基于受众重叠度与信息密度的异步管道**。

### 做法与步骤

**1. 注册发布意图与冷却队列**

内容首次进入系统时，不是直接推送，而是写入意图队列：
```json
{
  "id": "post-20250511-001",
  "canonical_url": "https://example.com/blog/xxx",
  "summary": "新版 OpenClaw MCP Hub 上线...",
  "full_text": "...",
  "priority": "normal",
  "created_at": "..."
}
```
Agent 读取该意图后，进入一个全局冷却检查：当前是否有同源内容在最近 **N 分钟内** 已经通过任一渠道发出？如果有，抑制本次发布，只记录日志。

**2. 分渠道差异化构造消息体**

不同平台对内容格式、长度、语气的容忍度不同。为每个渠道定义独立的渲染模板，例如：
- **Discord**：短摘要 + 主链接 + 特色 emoji，控制在 200 字符内。
- **Telegram**：可稍长，支持 MarkdownV2，带预览图，但避免过多链接。
- **GitHub Discussions**：直接引用原文摘要，强调讨论引导。
- **邮件列表**：完整摘要 + 行动号召，格式干净。

在 Agent 中，通过调用一个 `ContentAdapter` 工具，根据 target 渠道返回对应的消息体。

**3. 错峰分时发布**

按渠道的受众活跃时区与信息密度设定发布间隔。例如：
- 技术社区（Discord/GitHub）：工作日上午 10:30（UTC+8）
- 即时通讯（Telegram）：晚间 20:00，避免会议高峰
- 异步渠道（邮件）：任意时间，但需与其他渠道间隔至少 2 小时

实现上，Agent 将待发送条目放入延时队列，使用简单的 `setTimeout` 或 Redis 的 `ZSET` 做延迟任务调度。

**4. 去重与冲突消解**

关键点：如果同一用户在多个平台出现，如何避免他看到三条一模一样的提醒？最简单的工程手段是**以 canonical URL 作为去重键**，配合一个“全局最近发布窗口”（如 4 小时）。窗口内，同一个 canonical URL 最多通过 2 个渠道发布，且优先选择用户已表达偏好的渠道（如果可获取该信息）。

对于无法获取用户级别的渠道，退化为基于时间窗口的硬限制：同一内容在任意 3 小时内，至多推送 2 个渠道。

**5. 失败重试与熔断**

任何推送都可能失败。设计重试时，需要带上指数退避，并且熔断器在单位时间内失败超过阈值（如 5 分钟内 3 次），则暂停该渠道 30 分钟，并通知运维。避免因为重试风暴放大刷屏问题。

## 踩坑点

- **时间窗口的粒度选择**：一开始我们用了“10 分钟内不重复发”的硬规则，结果当内容修改后需要紧急更新时，被自己的规则卡死。后来改为分级冷却：常规内容 4 小时窗口，紧急修正如安全公告只冷却 15 分钟。
- **MCP 工具的异常返回值**：某些社区 API 在限流时返回 429，但 MCP 工具可能只抛出通用错误，导致 Agent 无法区分是限流还是内容违规。需要对工具返回做 status code 透传，Agent 根据状态码决定重试策略。
- **消息格式与平台渲染差异**：Telegram MarkdownV2 对特殊字符转义非常严格，而 Discord 的 Markdown 又不完全兼容。我们曾因为一个 `_` 导致整段消息在 Telegram 上解析失败。后来统一用更安全的“纯文本 + 链接”作为兜底。
- **跨渠道用户去重的幻觉**：除非用户主动绑定多平台身份，否则很难准确判断两个 ID 是否属于同一真实人。不要在此投入过度工程，时间窗口机制已经能解决大部分刷屏感知。

## 可复用建议

1. **抽象发布管道**：将“发布意图 -> 冷却检查 -> 适配 -> 分时调度 -> 执行”做成可复用的 Agent skill，方便接入新渠道。
2. **把冷却和去重逻辑放在服务端，而不是每个发送脚本里**，否则多人协作的自动化体系会出现漏洞。
3. **始终保留手动干预接口**：紧急情况需要全渠道速发时，可以绕过队列直接推送，事后记录原因。
4. **监控发布频率与失败率**：建一个简单的 Dashboard，统计每个渠道每小时推送量、去重拦截次数、重试成功率。刷屏不仅伤害用户，也伤害你的服务可达性。

## 总结

自动化的目标不是“把所有渠道当成同一个输出端”，而是尊重每个社区的信息节奏和用户上下文。通过引入**全局冷却窗口、内容分层适配、错峰调度**以及**可观测性**，可以让你的发布 Agent 在不扰民的前提下，完成多社区的有效触达。

在 OpenClaw + MCP 的生态下，这些能力可以被组合成标准化的“发布边界控制器”，让自动化真正服务于连接，而不是制造噪声。

> 少就是多，尤其是在通知栏里。
