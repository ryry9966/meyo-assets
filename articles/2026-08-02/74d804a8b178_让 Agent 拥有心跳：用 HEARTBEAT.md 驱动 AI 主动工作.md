# 让 Agent 拥有心跳：用 HEARTBEAT.md 驱动 AI 主动工作

## 背景：从“等提问”到“自己干”

当前大多数 AI Agent 的运行模式仍然是“提问-回答”的被动循环。用户通过聊天界面发一条消息，Agent 调取工具、推理、回传结果，然后陷入沉寂，直到下一次被唤醒。这种模式在对话式助手场景下很自然，但在自动化运维、持续监控、定时报告等工程场景中，就显得格外乏力。

最近半年，社区里关于“让 Agent 主动做事”的讨论越来越多。无论是 OpenClaw 的定时触发，还是 MCP 服务器的后台能力，都在为 Agent 赋予脱离对话窗口的自主性。但自主性的落地还需要解决一个关键问题： **Agent 凭什么知道“现在该做什么”？**

工程师会使用 cron 定时触发某个脚本，但 Agent 的状态远比脚本复杂：它可能有多个并行任务，需要记住上次执行到哪一步，还要根据环境变化调整行为。于是我们发现，一个简单到极致的方案可以解决大部分问题——给 Agent 一个能自己读写的“心跳文件”。

## 问题：Agent 的自主执行缺少“状态锚点”

如果只靠外部定时器触发 Agent，Agent 每次被唤醒时都是“失忆”的。它不知道上一次检查了什么，不知道是否有任务正在处理，也不知道自己是否应该停下某个持续动作。强制把所有状态写回环境变量或数据库当然可行，但成本太高，而且与 Agent 熟悉的“读写文件”工具调用模式格格不入。

我们需要一种轻量的、让 Agent 自然理解并维护的状态载体。一个 Markdown 文件，放在工作区里，Agent 能够用文件系统工具（或 MCP 文件服务器）读取、解析、更新。这就是 `HEARTBEAT.md`。

## 做法：三步构建 Agent 自主心跳

### 1. 设计 HEARTBEAT.md 结构，让 Agent 一眼看懂“我在哪”

我们不靠隐式的记忆，而是把状态显式化。一个可用的心跳文件大概长这样：

```markdown
---
last_heartbeat: "2025-03-20T09:15:00Z"
status: idle
active_jobs:
  - id: server-watchdog
    last_run: "2025-03-20T09:10:00Z"
    next_run: "2025-03-20T09:20:00Z"
pending_actions:
  - action: check_disk_usage
    threshold: 80
    notified: false
failures: 0
---
# Session Context
上次检查时 dev-server 的 CPU 正常，但 /data 分区已使用 79%，接近阈值。
若本次检查超过 80% 且未通知，则发送 Slack 告警。
```

这里用了 YAML frontmatter 存放结构化信息，方便 Agent 只解析头部就能获取关键字段。正文部分留给自然语言，承载上下文备注、临时笔记。Agent 被定时触发时，prompt 指令可以简单定义为：“读取 HEARTBEAT.md，根据 frontmatter 和 session context 判断当前应执行的动作，执行后更新文件。”

### 2. 绑定定时触发器，让 Agent 按心跳节奏苏醒

OpenClaw 支持通过内置调度或外部 cron 调用 Agent。适合的做法是用一个极轻的触发任务，例如每分钟调用一次 Agent，但 Agent 内部根据 `last_heartbeat` 判断是否真的需要执行工作。这样避免了高频无效唤醒的资源浪费。

典型的触发指令可以是：

```
请读取工作区根目录下的 HEARTBEAT.md。
如果距离上次心跳超过 5 分钟，且状态为 idle，则执行待处理动作列表中最早的一项。
执行后更新 frontmatter 中的 last_heartbeat、相关 job 的 last_run 和 next_run。
若无可执行动作，仅更新 last_heartbeat 并结束。
```

Agent 调用文件系统 MCP 工具的读取、解析、修改、写回，整个过程在几秒内完成。由于心跳文件非常小，负载几乎可以忽略。

### 3. 让 Agent 自主管理动作队列

`pending_actions` 是主动性的核心。它可以来自上一次检查的遗留、用户预约的任务，甚至是 Agent 自己根据正文内容追加的提醒。例如，磁盘使用率接近阈值的检查项，Agent 运行后若发现未超标，则增大 `next_run` 间隔；若超标，将 `notified` 置为 true，并追加一个新动作：“1 小时后复查”。这样系统就形成了一个自维持的控制循环。

动作执行时，Agent 可能调用通知类 MCP 服务器（Slack、邮件等）、执行 shell 命令、查询 API。所有工具的输出可以简要总结后追加到 HEARTBEAT.md 的正文区域，作为下一次运行的上下文，形成“记忆”。

## 踩坑点：这些细节会让心跳变成心梗

**无限自触发。** 如果 Agent 每次运行都追加新动作，而旧动作从不消失，队列会在几小时内膨胀到让文件难以解析。必须预设清理策略：例如已通知的动作在 24 小时后自动移除，或设定最大条目数。

**文件读写冲突。** 如果触发器设置不当，可能出现两个 Agent 实例同时读取并写入同一 HEARTBEAT.md，导致状态丢失。解决方案是限制并发，例如在 frontmatter 加一个 `lock: true` 字段，Agent 执行前先检查，执行后释放。更稳健的做法是使用单线程的任务队列。

**Agent 对 Markdown 结构的鲁棒性不够。** 有些模型在生成更新的文件时，可能意外破坏 YAML 格式或多出无用的解释文字。需要在 prompt 里强调“只输出完整的、格式严格的文件内容，不要包含额外说明”，并做一次解析验证。如果解析失败，回退到上一次备份。

**状态迷航。** 心跳文件容易变成“垃圾场”——什么都往上记。建议明确区分三个区域：结构化状态（frontmatter）、可执行上下文（正文上半部分）、运行历史（正文下半部分）。在 prompt 中要求 Agent 保持正文不超过 50 行，超出则自动归档历史记录。

## 可复用建议：把心跳做成插件化模块

- **模板化。** 为不同场景准备不同的 HEARTBEAT.md 初始模板，比如服务器监控型、团队日报型、数据管道检查型。Agent 的能力差异只在于它能调用的工具集，心跳逻辑基本不变。
- **结合 MCP 文件服务器。** 如果 Agent 运行在无状态容器中，可以将 HEARTBEAT.md 存放在挂载的持久化卷，或通过 MCP 的 remote-filesystem 服务器访问，确保心跳不丢失。
- **用标签驱动分时策略。** 在 frontmatter 里定义 `schedule_rules`，比如工作日的每小时检查，夜间降低频率，这样 Agent 读取后可以自行跳过非活跃时段，减少无效运行。
- **监控心跳本身。** 另设一个独立脚本，定期检查 HEARTBEAT.md 的 `last_heartbeat` 时间戳，若超过预定阈值（如 15 分钟无更新时间），说明 Agent 可能卡死或调度失效，触发告警。这就是心跳的心跳。

## 总结

HEARTBEAT.md 并不是一个复杂的技术方案，它只是一个 Agent 能读写的 Markdown 文件。但它解决了自主 Agent 系统里最关键的一个问题：**在没有用户参与的循环中，Agent 如何持续感知自己的位置和意图。** 通过结构化状态、动作队列和定时触发，我们让 Agent 从“一问一答”的工具，变成了一个能在后台持续运转的数字同事。

在 OpenClaw + MCP 的体系下，这种模式几乎零额外依赖，所有组件都是文件系统和 prompt。对于正在探索 Agent 落地的团队而言，先把心跳做稳，再谈复杂的多 Agent 协作，是一个被反复验证过的务实路径。
