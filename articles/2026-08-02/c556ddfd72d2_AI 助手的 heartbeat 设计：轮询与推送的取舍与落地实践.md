## 背景：为什么 AI 助手需要心跳

在 OpenClaw 这类 Agent 框架中，AI 助手往往不是一次性调用的函数，而是长时间运行的进程、插件或者 MCP 服务器。典型场景包括：

- 一个长期驻留的 Agent，需要监听任务队列并上报自己的存活状态
- MCP 服务器与客户端之间需要维持双向通知能力，例如资源变更、进度反馈
- 分布式部署的多个 OpenClaw 实例，要通过心跳判断对端是否在线以进行故障转移

在这些场景下，“heartbeat”（心跳）既是健康检查，也是状态同步的触发器。设计上的核心问题就变成了：**用轮询去“打听”，还是用推送来“被告知”？**

## 问题：轮询与推送的本质矛盾

轮询（polling）的本质是客户端主动、定时向服务端请求最新状态。推送（push）则是服务端在事件发生时，主动通知已经建立连接的客户端。

**轮询的问题：**

- 无效请求多：绝大多数轮询请求得到的结果都是“无事发生”
- 延迟与资源消耗相互制约：想缩短延迟就要提高频率，资源消耗指数上升
- 在 OpenClaw 插件模型下，高频轮询很容易触发第三方 API 的速率限制（429），或者把 MCP 服务器的 stdio/HTTP 通道打满

**推送的问题：**

- 连接状态复杂：WebSocket/SSE 需要处理断线重连、心跳维持、多实例下的连接路由
- 客户端可能处于无法直接接收推送的环境（如某些 serverless 函数执行完成即销毁）
- 推送通道需要额外基础设施（如 Redis Pub/Sub、消息队列），整体架构变重

在 Agent 和自动化插件开发中，我们经常面临“既要简单又要实时”的拉扯。下面结合 OpenClaw 实践，给出可复用的取舍框架。

## 做法：基于场景的决策与实现步骤

### 1. 先明确心跳承载的语义

不要只把心跳当成“我还在”，而是区分两种用途：

- **存活检测（Liveness）**：判断进程/插件是否卡死或无响应，一般 30–60s 一次足够，即使有几十秒延迟也不会造成严重后果
- **状态同步（State sync）**：任务进度、配置变更、外部事件，这类对延迟敏感

决定技术选型时，把两种心跳分离开来：存活检测用粗粒度轮询或简单 TCP/HTTP 健康检查端点；状态同步再根据实时性要求进一步决策。

### 2. 当延迟要求 > 10s 时，选择轮询

对于大多数 Agent 的任务监控，比如等待一个 Llama 模型的推理结果，轮询间隔 3–10 秒完全满足体验需求，且实现成本极低。

**在 OpenClaw 插件中的落地方式：**

```yaml
# openclaw-plugin.yaml 片段
heartbeat:
  mode: polling
  endpoint: /api/task/{task_id}/status
  interval_seconds: 5
  backoff:
    on_error: true
    max_interval: 30
```

插件侧只需用 setInterval 或 cron 表达式，配合指数退避处理暂时性错误。一个关键设计是**加上 “If-Modified-Since” 或 ETag 机制**，让服务端能快速返回 304，避免每次全量拉取状态。这在 MCP HTTP 传输中尤其有效，可以把无效轮询的 CPU 和带宽消耗降低 90% 以上。

### 3. 当延迟要求 < 1s 且连接可保持时，选择推送

如果 Agent 需要近乎即时地响应外部事件（如用户在前端手动取消任务、文件系统 watcher 触发重新索引），且部署环境允许长连接，那么 WebSocket 是更合适的方案。

**实践步骤：**

1. 在 OpenClaw 的 gateway 层添加 WebSocket 端点
2. 客户端（如浏览器插件、本地 Agent 进程）建立连接后发送 `subscribe: task:{task_id}` 消息
3. 服务端使用内存通道或 Redis Pub/Sub 将内部事件桥接到对应 WebSocket 客户端

**简化故障恢复的关键：** 客户端必须实现自动重连，并在连接恢复后重新拉取一次全量状态，避免丢失期间的事件。这种“快照 + 增量推送”模式，把一致性问题降到最低。

### 4. 复杂场景：混合模式

真实项目中，一种策略往往不够。我们常用的组合是：

- 用粗粒度轮询（30s）作为兜底存活检测与状态校正，防止推送管道静默失效
- 用 WebSocket/SSE 推送任务进度、日志等高频增量数据
- 在插件初始化时拉取一次全量快照，之后只取增量

这种设计兼顾了可靠性、实时性和实现成本。OpenClaw 中可以通过插件配置的一级字段选择 heartbeat 模式，内部自动处理降级和升级，对外暴露统一的 `onHeartbeat(callback)` 接口，调用者不需要关心底层是轮询还是推送。

## 踩坑点

1. **轮询间隔的“雪崩”**
   多个 OpenClaw 插件各自独立轮询同一个上游 API，极易在不经意间把请求时序重叠，导致瞬时 QPS 超过限制。解决方法：在初始化时引入随机抖动（jitter），将实际间隔变更为 `interval * (1 + random(0, 0.3))`，打散请求窗口。

2. **WebSocket 连接泄漏**
   在插件热重载或 Agent 生命周期结束时，没有正确关闭 WebSocket 连接，导致服务器侧堆叠大量半开连接。一定要在插件的 `shutdown` 钩子中执行 `ws.close()` 并等待关闭完成。

3. **推送状态的“断层”**
   仅依赖推送，某次断线重连期间的事件永久丢失。必须强制重连后调用一次全量查询，再进行增量订阅。业界常见的 “resume token” 或 “序列号” 方案能更好处理，但工程成本稍高，初期用全量拉取兜底足够。

4. **用 HTTP health endpoint 假心跳**
   很多插件只检查主事件循环是否仍在转动，但实际上异步任务已经全部卡死。存活检测应该包含关键的内部任务队列深度、最后一次成功处理时间等业务信号，而不是只返回 200 OK。

## 可复用建议

- **为插件抽象统一心跳接口**：不管底层用轮询还是推送，插件代码只依赖 `heartbeat.on('alive', callback)` 和 `heartbeat.on('state_change', callback)`，方便未来切换模式而不改业务逻辑。
- **配置驱动，按场景切换**：在 `openclaw.yaml` 中支持 `heartbeat_mode: polling|websocket|hybrid`，并提供默认的最佳实践参数，降低使用门槛。
- **自建轻量心跳网关**：如果团队内多个 Agent 都需要心跳服务，可以抽出一个单独的心跳网关（基于 Node.js 的 `ws` 或 Go 的 gorilla/websocket），对外吐标准 `Server-Sent Events`，和 Redis Stream 对接，成本不高但复用性极强。
- **监控与告警**：不管哪种模式，都要对心跳失败率、重连次数、推送丢包数量做埋点，才能在下游感知前发现问题。

## 总结

AI 助手的心跳设计没有银弹，轮询和推送之间的取舍，本质是在“实现复杂度”与“延迟需求”之间做权衡。OpenClaw 社区的实践倾向于：**用粗粒度轮询保证必达性，用推送提升关键路径的实时性，再用混合模式覆盖复杂长尾场景。** 只要做好抖动、重连、全量兜底和资源清理，就能在插件和 Agent 系统中打造稳定且可维护的心跳机制。
