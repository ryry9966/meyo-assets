## 1. 背景：memory_recall 到底要解决什么问题

在 OpenClaw 这类 Agent 框架中，`memory` 插件会把用户偏好、历史任务上下文、甚至工具调用记录持久化下来。这些数据散落在会话片段里，当用户说“上次那个 Python 脚本再改一下”，Agent 需要从几十上百条记忆里找出“上次那个 Python 脚本”——这就是 `memory_recall` 的核心任务。

召回（retrieval）方式直接影响回答质量。最常见的两种路线是全文搜索（FTS，比如 SQLite FTS5、Elasticsearch）和语义搜索（向量相似度，如 Chroma、Qdrant + embedding）。很多同学上来就全押向量，但工程中往往没那么简单。这篇帖子基于我们在 OpenClaw 生态里实际接入 memory recall 的经验，聊聊两者的真实差别和混合方案。

## 2. 全文搜索 vs 语义搜索：为什么不能二选一

**全文搜索**擅长精确匹配：程序包名、错误码、文件名、代码片段、时间戳。但对“那个跑在 GPU 机器上的任务”这种自然语言表达几乎无效，因为原始记忆里可能写的是“使用 Tesla T4 的推理服务”。

**语义搜索**能理解“GPU 机器”和“Tesla T4”的关系，但它有两个工程上的软肋：
- 对**专有名词、代码模式、ID**等低语义信息，向量相似度不可靠。比如 `user_id=10001` 和 `user_id=10002` 语义上非常接近，但业务上完全不该召回。
- 计算成本高，每次查询都要生成 embedding，且向量索引的内存占用不小。

更坑的是，两者会**相互漏召回**：全文漏掉的同义表达，语义能补上；语义漏掉的精确标签，全文能找到。所以我们从单纯选型转向了混合检索。

## 3. 实践做法：在 OpenClaw 插件中搭建混合 memory recall

我们的方案是**先并行召回，再合并精排**，具体步骤：

### 3.1 记忆存储与索引
- **内容**：每条记忆存储为 `{id, session_id, text, metadata, created_at}`。
- **全文索引**：使用 SQLite 的 FTS5，对 `text` 字段建表。中文场景用 `jieba` 离线分词后写入一个专用列，FTS5 直接索引分词结果。
- **语义索引**：将 `text` 通过本地 embedding 模型（`moka-ai/m3e-base`）转为 768 维向量，存入 Chroma。

### 3.2 查询流程
1. 用户输入 query，分别执行：
   - FTS5：`SELECT * FROM memory_fts WHERE text MATCH ? LIMIT 20`（使用分词后的 query）
   - 语义搜索：`collection.query(query_embedding, n_results=20)`
2. 合并两个结果列表，按记忆 ID 去重。
3. 用 `bge-reranker-base`（cross-encoder）对所有候选统一精排，返回 TopN（通常 3-5 条）。
4. 将召回记忆按时间、相关性组装成 prompt，注入 LLM 上下文。

在 OpenClaw 里，这套流程封装成一个 MCP server，提供 `recall_memory` 工具，Agent 可以像调用普通函数一样使用。

## 4. 踩坑记录

### 坑1：中文全文分词的“最后一公里”
SQLite FTS5 没有内置中文分词。直接写中文会被当作单一“词”。我们试过用 ICU tokenizer 配合 `zh` 语言，效果很差。最后采用离线分词：存储时用 jieba 切词，空格拼接存入 `tokens` 列，建索引。查询时对 query 同样分词后送入 FTS5。缺点是无法即时分词新内容，但记忆写入是可控异步任务，可以接受。

### 坑2：语义搜索的阈值陷阱
不同 embedding 模型输出的相似度分布差异巨大。`m3e-base` 相似度集中在 0.6~0.9，阈值设 0.7 可能带回大量噪声；而 OpenAI `text-embedding-3` 的阈值需要 0.85 才有同等精度。不校准阈值就会发生“明明向量召回了很多但 rerank 后都扔掉”的浪费。我们在精排前不做阈值截断，让 reranker 全量判断，避免误杀。

### 坑3：增量更新导致索引碎片
Chroma 的 `upsert` 比 `add` 慢，频繁更新会让响应时间毛刺严重。我们改为批量写入，每 5 分钟或累积 50 条记忆后重建临时 collection，然后做 `rename` 原子替换，避免在线毛刺。SQLite 侧使用 WAL 模式，写入性能足够。

### 坑4：元数据过滤需前置
现实查询往往带条件：“只搜索最近一周的记忆”或“只搜某类任务”。我们在向量和全文查询时都下推了元数据过滤，否则合并后才发现时间不符合要求，大量浪费重排计算。

## 5. 可复用建议

- **先评估数据规模**：记忆量 < 5000 条时，直接用 FTS5 加 `jieba` 分词 + BM25 排序就够了，不必引入向量库。
- **优先选支持混合检索的向量数据库**：如 Qdrant（1.10+ 支持文本索引）或 Milvus，可以在一次请求中完成全文本+向量召回，简化架构。
- **本地化 embedding 模型更经济**：`m3e-base` 或 `bge-small-zh` 用 ONNX 量化后，CPU 推理单条耗时 < 15ms，完全满足 Agent 的召回延迟要求。
- **reranker 是性价比最高的提升手段**：比单纯加大 k 值便宜得多，可显著提高最终结果准确率。
- **用 MCP 封装 recall 能力**：让 Agent 开发者无感切换搜索引擎，未来升级索引后端也不用改 Agent 代码。

## 6. 总结

在 AI 助手的 memory_recall 场景里，语义搜索和全文搜索不是替代关系，而是互补关系。全文搜索兜底精确匹配，语义搜索补全模糊意图，再配合 reranker 做“最终裁判”，是在工程上最稳妥的组合。不要迷信单一方案，也别因为向量时髦就放弃传统的 FTS——毕竟，用户问“上周的那篇报告”时，倒排索引可能比你花式调参的向量模型更快更准。
