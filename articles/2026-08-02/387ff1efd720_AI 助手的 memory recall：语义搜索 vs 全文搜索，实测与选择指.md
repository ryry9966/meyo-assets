## 背景
在 OpenClaw 这类需要长期记忆的 AI 助手中，memory recall 直接决定了 Agent 能否在聊天中将过去的信息准确地捡回来。我们把用户偏好、任务记录、错误日志、配置片段等，持续存入记忆库，对话时再从中检索相关的条目注入上下文。

实际操作中，有两个极端路线：
- **全文搜索**（关键词匹配，如 Elasticsearch/MeiliSearch/whoosh）
- **语义搜索**（基于 Embedding 的向量相似度，如 Chroma + OpenAI embedding）

到底哪种更适合 memory recall？我们在一套内部自动化工具上做了对比实验，以下记录做法、踩坑与混合策略。

## 问题：选全文还是语义？
我们的场景：助手记忆库约 5000 条，日增量约 200 条，需要让 Agent 在 200ms 内找到最相关的记忆。初步观察：
- 全文搜索对命令名、项目 ID、固定术语（如“订单导出”）命中极准，但对“上次那个导出 CSV 的任务”这类口语化提问无能为力。
- 语义搜索能理解“导出 CSV”和“export_orders_20250409.csv”的关系，但容易过度泛化，把一堆语义接近却无关的历史记录排到前面，而且调用 embedding API 的延迟和费用都不低。

于是我们决定量化两种召回效果的差异，并寻找组合方式。

## 做法与实验步骤
### 1. 构建测试集
从生产数据中取 200 条记忆，手工标注 30 个真实提问及其相关记忆（合计 70 对）。这些提问覆盖精确匹配、模糊意图、跨语言和时间限定等多种情况。

### 2. 搭建两种检索器
- **全文检索**：Elasticsearch 7.x，中文使用 IK 分词器，对 `content` 字段做 `match` 查询，取 top-K。
- **语义检索**：OpenAI `text-embedding-3-small` 生成向量，存入 Chroma，查询时用相同模型编码后取 top-K（阈值 0.7）。

简化伪代码：
```python
def fulltext_recall(query, k=10):
    res = es.search(index='memory', body={
        'query': {'match': {'content': query}},
        'size': k
    })
    return [h['_source'] for h in res['hits']['hits']]

def semantic_recall(query, k=10):
    emb = get_embedding(query)
    docs = chroma.query(query_embeddings=[emb], n_results=k)
    return docs['documents'][0]
```

### 3. 评估指标
- **召回率@K**（K=5, 10）
- **精确率@5**
- **平均检索延时**

### 4. 结果速览
| 方法        | Recall@5 | Recall@10 | Precision@5 | 平均延时 |
|-------------|----------|-----------|-------------|----------|
| 全文搜索    | 0.62     | 0.78      | 0.68        | 15ms     |
| 语义搜索    | 0.74     | 0.87      | 0.55        | 80ms     |

语义搜索的召回率更高，但精确率反而不如全文，印证了“过度联想”的问题。延时差异主要来自 embedding API 调用（即便用了 OpenAI，batch 场景下仍有改善空间）。

## 踩坑点
### 1. 中文分词与混合语言
ES 默认分词无法关联“导出 CSV”与“export_orders”，IK 分词解决了中文，但对中英混合、缩写效果仍然有限。维护同义词表成本高，且冷启动时覆盖不全。

### 2. 语义搜索的泛化陷阱
查询“昨天的错误”，语义搜索可能带回所有包含“错误”的日志，却不看时间。而全文检索可以结合时间范围查询精确命中。根本问题：向量相似度没有结构化的维度。

### 3. 更新实时性
语义索引新增记录需重新生成 embedding 并插入，频繁写操作可能引发性能抖动；全文索引则可近实时更新。

### 4. Embedding 模型选择与成本
OpenAI embedding 在延迟和费用上不适合超高并发；本地模型（如 bge-large-zh）效果不错，但部署维护成本上升。混合架构中，高速缓存和本地粗筛可能是更经济的方案。

### 5. 冷启动
记忆条数极少时，语义搜索的相似度不易稳定，全文则基本不受此影响。

## 可复用建议
- **按记忆类型分流策略**：事实性/结构化记忆（配置、命令、ID）优先用全文+字段过滤；模糊意图或偏好类记忆用语义搜索。
- **混合召回+重排序**：先用语义搜索粗筛（top-50），再用全文关键词重叠度或规则打分重排；或者先全文缩小范围，再用语义排序。实测混合后 Recall@5 提升至 0.92。
- **元数据过滤先行**：无论是 ES 还是向量库，都为记忆标注 timestamp、category、user_id 等字段。检索前先过滤，可显著减少候选集，提升准确率和速度。
- **缓存与批处理**：高频查询的 embedding 预计算并缓存；批量生成嵌入以减少 API 开销。
- **监控与自适应**：记录每次 recall 之后用户是直接引用还是纠正，据此动态调整策略权重。例如连续 3 次全文结果被忽略，就自动降低其优先级。

## 总结
在 AI 助手的 memory recall 中，语义搜索与全文搜索不是单选题。我们走过的弯路表明，一味追求“智能”的语义检索，反而可能引入噪音和延迟；而单纯的全文匹配又无法理解用户自然语言的变化。合理的方案是根据记忆的类型和用户意图，分而治之，在必要时用混合策略取长补短。

如果你的助手也面临类似选择，不妨先用上述测试流程跑一遍自己的真实数据，再用简单的规则融合，就能在成本和效果之间找到平衡点。
