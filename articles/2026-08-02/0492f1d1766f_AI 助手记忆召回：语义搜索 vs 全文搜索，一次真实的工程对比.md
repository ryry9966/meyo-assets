## 背景

在给 Agent 加上记忆能力时，几乎所有人都会遇到同一个决策点：**查询历史记忆时，用语义搜索还是全文搜索？**

这个问题在 OpenClaw 体系里尤其突出，因为你可以通过内置的 `memory` 插件（比如 `chroma`、`mem0`、`weaviate` 等后端）直接启用语义召回，也可以自己在工具中手搓一套 SQLite FTS 全文索引。两种路径都能跑通，但体验和坑位完全不一样。

过去几个月，我在一个面向内部团队的知识问答 Agent 上分别试了这两种方案，下面把具体做法和对比结果整理出来，供同类场景参考。

## 问题定义

我们假设 Agent 需要记住两类信息：

1. **结构化事实**：用户偏好、项目截止时间、人名映射等。
2. **非结构化的对话片段**：上一次沟通的摘要、用户随口提到的想法。

查询场景也很典型：“我之前说的那个方案B的截止日期是？”“关于咖啡的偏好是什么？”“上次我们聊到的那个 Python 内存泄漏问题，结论是啥？”

面对这些查询，全文搜索和语义搜索会给出看起来相似的返回，但实际召回质量差距很大。

## 方案与步骤

### 1. 全文搜索方案（SQLite FTS5）

在 Agent 的工具里挂了一个自己实现的 `memory` 工具集，表结构大致如下：

```sql
CREATE TABLE memories (
    id INTEGER PRIMARY KEY,
    content TEXT,
    metadata JSON,
    created_at TIMESTAMP
);

CREATE VIRTUAL TABLE memories_fts USING fts5(content, content=memories, content_rowid=id);
```

写记忆时同步插入 `memories` 和 `memories_fts`，查询时用：

```sql
SELECT content, metadata
FROM memories_fts
WHERE memories_fts MATCH ?
ORDER BY rank
LIMIT 5;
```

关键词 `MATCH` 自动进行分词（默认按字分隔，中文需要额外处理），返回包含查询词条的记录。

### 2. 语义搜索方案（OpenClaw memory + Chroma）

在 `openclaw.yaml` 中启用 `memory` 插件，选用 `chroma` 后端，嵌入模型用 `text-embedding-3-small`：

```yaml
memory:
  enabled: true
  backend: chroma
  chroma:
    persist_directory: ./chroma_db
    collection_name: agent_memory
  embedding:
    provider: openai
    model: text-embedding-3-small
```

使用内置 `memory.save` 和 `memory.search` 工具写入和召回，配置 `top_k: 5`。

### 3. 测试数据与查询

向两份存储同时写入 30 条记忆，包含：

- 事实类：“用户 prefer 冰美式而非热美式，加一份浓缩。”
- 模糊描述类：“昨天聊到后端日志切割方案，结论是用 logrotate 配合 systemd timer，暂不引入 ELK。”
- 干扰项：“用户吐槽周末爬山晒伤了。”

用 10 条中文查询进行召回，例如“冰美式偏好”、“日志切割结论”、“周末运动相关”。

## 对比结果与踩坑

**全文搜索的强项与软肋**

全文搜索对“冰美式”等精确词命中率极高，且返回速度稳定。但遇到“日志切割”与“logrotate”这类同义不同词的情况时，FTS5 直接哑火——它不理解词义，只认词袋。

另一个坑是中文分词。FTS5 默认没有内置中文分词器，如果不集成比如 `jieba` 分词插件，它会把“日志切割”切成“日”“志”“切”“割”，导致“日志”一个词无法匹配。我是通过在应用层用 `jieba` 分词后再拼接成空格分隔的“已分词文本”存入 FTS 表解决的，这增加了一层维护成本。

**语义搜索的惊喜与翻车**

语义搜索对同义表达的鲁棒性确实好，“日志切割”能轻松匹配到包含“logrotate”的记录，“周末运动”也能把“爬山晒伤”召回。但问题在于它经常“想太多”：比如查询“冰美式偏好”时，它不仅命中了咖啡记录，还把“吐槽周末晒伤”排在第三位——因为语义角度“偏好”和“吐槽”都带情感倾向，噪点明显。

另外，embedding 模型的选择对中文是真敏感。试过几个免费的 HuggingFace 模型，召回简直是灾难，明明写着 multilingual 结果中文语义距离算得一塌糊涂，最后只能换回 OpenAI 的付费嵌入才达到可用水平。这也意味着如果大量使用语义搜索，token 开销不可忽略。

另一个工程坑：Chroma 的 `persist_directory` 在容器环境下很容易因为权限挂掉，退出时不 flush 还会丢 collection 元数据，要记得显式 `persist()` 或确保退出信号处理。

## 可复用建议

1. **按记忆类型分路**  
   对结构化事实、精确匹配需求高的记忆，使用全文搜索（SQLite FTS5 + 自定义分词）。  
   对对话摘要、零散想法等非结构化记忆，用语义搜索（向量数据库 + 质量可靠的 embedding）。

2. **先全文，后语义，加阈值**  
   查询时默认先用全文搜索，若命中数低于阈值（如小于 2 条）再用语义搜索兜底。语义搜索结果建议加一个 `score` 阈值过滤，比如余弦相似度低于 0.75 的直接丢弃，减少噪声。

3. **Embedding 成本控制**  
   如果记忆体量不大（<10k），可以考虑本地模型如 `bge-small-zh`，但务必先在自有数据集上评估召回@5。体量上去后再切 OpenAI 或同级别服务，记得做结果缓存。

4. **定期评估召回质量**  
   写一个简单的回归脚本，在每次记忆结构变更后跑一遍固定的 `query -> expected_id` 对，计算 `recall@k`。这个习惯能帮你及时发现 embedding 模型退化或分词配置错误。

5. **考虑轻量重排序**  
   在两条管线融合后，可以接一层 Cross-Encoder reranker（比如 `rerankv2`），对 Top-10 候选做一次精排，精度提升明显，尤其在中文问答场景。

## 总结

没有“语义搜索一定比全文搜索好”这回事。在 Agent 的记忆召回里，全文搜索精确但脆弱，语义搜索鲁棒但容易引入噪声且成本高。工程上最务实的方案永远是：**根据记忆属性分而治之，用全文兜底精确事实，用语义补充模糊查询，并通过阈值和重排序控噪**。

你不需要一步到位把记忆系统设计得无懈可击，先从少量记忆开始，跑通两条管线，再用上面的评估方法迭代，比直接选边站队靠谱得多。
