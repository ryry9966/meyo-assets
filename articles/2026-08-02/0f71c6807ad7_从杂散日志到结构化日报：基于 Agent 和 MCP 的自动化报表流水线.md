# 从杂散日志到结构化日报：基于 Agent 和 MCP 的自动化报表流水线

## 背景与问题

日常开发或运营过程中，我们常常面对来自 Slack、GitHub、Jira、CI/CD 输出甚至自建监控系统的「杂散日志」。这些日志半结构化、时间戳格式不一、粒度混杂，却承载着每天必须交付的日报信息。手动拼凑日报，不仅耗时，还容易因遗漏关键变更而被诘问。

在 OpenClaw 生态里，我们手头已有 Agent 编排能力和日渐成熟的 MCP（Model Context Protocol）插件体系——只要设计合理，完全可以将这一流程自动化：**把原始日志管道化为一份结构清晰、可直接发送的日报**。

这篇帖子不讨论宏大叙事，只讲如何用工程化思路落地一条「从原始日志到日报」的流水线，并分享踩过的坑。

## 核心挑战

- **多源异构**：Slack 消息、GitHub commit、Jira issue 的三观完全不同。
- **时间炸弹**：各源时间戳可能涉及 UTC、本地时区、Unix 时间戳，甚至缺失。
- **长度失控**：某次部署的日志洋洋洒洒几千行，直接塞给 LLM 必超 token 窗口。
- **幻觉与格式飘移**：Agent 有时会臆造「看起来合理」的数据，或输出非结构化白话文而非 JSON 报告。

## 流水线设计

下图概括了从数据接入到最终报告的整体流程。

```
[Slack]──┐
[GitHub]─┼── MCP Servers ── Preprocessing ── Agent (LLM) ── Aggregator ── Report
[Jira]───┘
```

### 1. 数据接入：用 MCP 统一「口径」

为每个数据源实现或复用现有 MCP server。例如：
- `slack-mcp-server`：拉取指定 channel 最近 24 小时的消息；
- `github-mcp-server`：获取某仓库当日 commits 与 PR 摘要；
- `jira-mcp-server`：查询 assigned issues 当天更新。

所有 MCP server 返回统一的结构化描述（`tools/list` 和 `resources/read` 保持一致），后续链路只依赖标准 MCP 交互协议，不关心来源实现。

### 2. 预处理：去噪、时间归一、分块

原始日志进入预处理模块（可复用 OpenClaw 的 `pipeline` 节点或自建脚本）：
- **去重**：按内容 hash 剔除相同日志（如重试消息、重复 webhook）；
- **时间归一**：将所有条目的时间戳转为 ISO 8601 UTC，并保留原始时区字段，防止跨时区日报日切错误；
- **长文本分块**：对超过 3000 token 的单条日志（例如全量部署输出）按语义段落切分并编号，用于后续合并。

### 3. 智能提取：LLM Agent 生成结构化条目

清洗后的日志按时间排序，分批调用 LLM。关键是**强制结构化输出**：

```json
{
  "date": "2025-03-28",
  "sections": [
    {
      "title": "代码变更",
      "items": [
        { "summary": "...", "refs": ["commit/abc123"], "severity": "normal" }
      ]
    }
  ]
}
```

使用 function calling 或 response format（如 `json_schema`）约束输出模式，且要求每个条目必须关联原始引用（如 commit SHA 或 message permalink），方便人工回溯核实。

对于切分后的长文本，采用「摘要-合并」策略：先让 Agent 独立处理每个 chunk，产出 mini-report，再由一个轻量级合并 Agent 消重、融合成完整节段。

### 4. 报告聚合与渲染

结构化日报对象交由模板引擎渲染为 Markdown 或飞书消息卡片，直接推送到日报 Channel。如果需要在发送前审批，可插入「人工确认」节点，挂起流程直至响应。

## 踩坑实录

- **LLM 幻觉**：Agent 有时会在一堆部署日志中「看到」并没发生的回滚。解决办法：强制要求 `items` 中每个条目必须填写 `refs` 字段，缺省视为无效并二次调用 LLM 修正；同时还引入一个独立的校验 Agent，检查 `severity` 不离谱。
- **token 窗口超限**：一开始直接把某条 8000 行的日志丢给 LLM，直接报错。后来采用分块摘要合并，但合并时偶有丢失子细节。调优方案是：第一次提取时保留更多的 key-value 对而非长句摘要，合并时再重组，准确率明显提高。
- **时区混乱**：午夜交替时，Slack 消息的本地时间和 GitHub 的 UTC 时间可能跨天，导致日报漏掉接近零点的条目。修复方法是在预处理统一 UTC，并将日报的「一天」定义为 `[昨日 00:00 UTC, 今日 00:00 UTC)`，无视本地时间。

## 可复用建议

1. **用 MCP 解耦数据源**：把每个数据源封装成 MCP server，便于独立测试、替换或复用。即使数据源增减，主流水线逻辑不变。
2. **提前做时间归一和分块**：不要把这口锅全甩给 Agent，预处理越充分，LLM 的产出质量越高。
3. **严格约束输出 schema，并做校验**：利用 JSON Schema 进行静态校验，并设一个轻量级 LLM 做语义审查，可显著降低幻觉风险。
4. **流水线模块化，允许部分失败**：若某个源挂掉，不应阻塞整个日报生成。设计缺失占位符并标记 `status: "unavailable"`，事后人工补全即可。

## 总结

这条「原始日志→结构化日报」的自动化流水线并不需要重型 ETL 平台，在 OpenClaw + MCP 的架构下，通过清晰的预处理、结构化的智能提取和合理的校验兜底，就能稳定产出及时可用的日报。如果你已经在用 OpenClaw 编排日常工作流，不妨从接入一个 MCP 日志源开始，逐步拼接出属于自己的日报机器人——也许明天早上一杯咖啡的时间，就能收到一份干净的报告。
