## 背景

在基于 OpenClaw 构建 Agent 或自动化流程时，我们很快会面临一个现实问题：所有请求都走 GPT-4o 成本太高，而全部切到本地模型又担心能力不足。OpenClaw 作为支持多模型后端的能力编排框架，天然允许我们在同一个 execution graph 里为不同步骤指定不同模型。这就引出了一个工程问题：**到底什么时候该用 GPT，什么时候该用本地模型？**

本文从实际踩坑经验出发，给出可复现的决策路径和配置方法，不推销任何单一方案，重点在于让路由策略“可解释、可观测、可回退”。

## 问题拆解

选择模型不是非黑即白，通常要考虑四个维度：

1. **任务复杂度** – 是否需要多步推理、长上下文、复杂工具调用？
2. **延迟要求** – 能否接受本地模型的推理延迟（尤其在 CPU 环境下）？
3. **数据敏感性** – 数据是否允许出网？是否需要私有化部署？
4. **成本预算** – 单次调用成本、每日调用量预估。

一个常见的误区是：用一个小本地模型做路由判断，再决定调 GPT 还是本地模型。这很容易引入新的瓶颈——路由模型本身可能误判，而且增加了延迟。因此，**路由逻辑应尽量用规则而非模型**。

## 做法与步骤

### 1. 在 OpenClaw 中注册多个模型后端

OpenClaw 的模型配置一般通过 provider 声明，比如在 `openclaw.yaml` 或 Agent 定义中：

```yaml
llm_providers:
  - id: gpt-4o
    type: openai
    model: gpt-4o
    api_key: ${OPENAI_API_KEY}
  - id: local-qwen
    type: ollama
    model: qwen2.5:14b
    base_url: http://localhost:11434
```

关键点：给每个 provider 一个明确的 id，后续 action 或 task 引用时不会混淆。

### 2. 将任务拆解为可独立分配模型的步骤

把一次完整的 Agent 执行看成多个 step：意图分类、信息检索、推理合成、最终回复等。每个 step 可以在 OpenClaw 中映射为不同的 action。例如：

- **意图识别 / 简单实体抽取** → 本地模型（任务简单、调用量巨大）
- **复杂指令跟随 / 多步工具编排** → GPT-4o（需要强大的 function calling 和对复杂 prompt 的理解）
- **文本摘要 / 低风险翻译** → 本地模型（数据量大，但逻辑直白）
- **最终用户交互输出** → 根据上下文复杂度和语气要求，可能用 GPT，也可能用本地模型精调后的版本

在 OpenClaw 的 action 定义中，显式指定 `llm_provider_id`：

```yaml
actions:
  - id: classify_intent
    llm_provider_id: local-qwen
    prompt: "Classify the user intent into: order_status, refund, technical_support... Input: {user_input}"
  - id: solve_issue
    llm_provider_id: gpt-4o
    prompt: "You have access to tools {...} to resolve the issue. Issue: {classified_intent}"
```

### 3. 设计确定性的路由规则

路由判断最好基于结构化的前置条件，而不是再调一个模型。例如：

- 如果 `classified_intent == 'technical_support'` 且上下文长度 > 2000 tokens → 强制走 GPT。
- 如果时间窗口（9:00-18:00）且涉及客户敏感信息 → 走本地模型，防止数据出境。
- 默认路由：非对话核心链路（如日志总结、内部标注）一律用本地模型。

这些规则可以直接写在 OpenClaw 的条件分支（condition node）中，不增加推理成本。

### 4. 增加 fallback 与超时控制

本地模型可能因为 OOM、量化精度问题突然失败或返回错误格式。必须设置：

- 超时时间（例如 `timeout_seconds: 15`），超时后自动切换到 GPT，并记录事件。
- 重试策略：先重试一次本地模型，失败再切 GPT，同时触发告警。
- 返回校验：若本地模型输出不符合预期 JSON schema，视为失败，走 fallback。

### 5. 成本与延迟观测

OpenClaw 支持通过 tracing 或自定义中间件记录每个步骤的模型调用。可以计算：

- 本地模型用量占比、成功率、P99 延迟。
- GPT 调用次数与花费曲线。
建议每周 review 一次，逐步优化路由阈值。

## 踩坑点

* **本地模型不支持可靠的 function calling**：很多开源模型（包括 7B/14B）的工具调用能力不稳定，容易输出错误的 JSON 或者忽略参数。解决方案是仅将需要工具编排的步骤分配给 GPT，或者在本地模型外包裹一层结构化解码（例如 constrained decoding），但这会增加工程复杂度，需要评估。
* **量化后能力退化**：INT4/INT8 量化后的本地模型在长上下文上表现骤降，可能丢失关键信息。测试时需要重点考察目标场景的上下文长度，不要只跑几个样例就上线。
* **延迟差异导致用户体验割裂**：本地模型推理可能在 2-10 秒之间波动（取决于硬件），如果路由结果导致用户交互中混用 GPT 和本地模型，可能让用户感知到“时快时慢”。建议：同一条对话链路内尽量固定一种模型，或在切换时用 loading 状态过渡。
* **忽略上下文窗口上限**：本地模型的上下文窗口一般比 GPT-4o 小，如果不做截断，可能会出现截断丢失关键信息。路由时需根据输入 token 数动态选择模型。

## 可复用建议

- **维护一张决策矩阵**：用表格把任务类型、典型上下文长度、延迟容忍度、成本约束写清楚，贴在团队 Wiki 里，避免每次拍脑袋。
- **渐进式迁移**：先让 GPT 承担 100% 流量，然后在低风险环节逐步切换到本地模型，观察失败率和延迟，稳定后再扩展。
- **监控规则覆盖率**：确保 fallback 的触发次数可追踪。如果某条规则经常迫使系统退回 GPT，说明本地模型在该任务上仍需优化或替换更大参数版本。
- **不要在路由逻辑中用重模型**：规则 + 轻量正则/关键词匹配是最稳定的路由方式，不要搞出一个用 GPT 判断要不要用 GPT 的循环。

## 总结

没有一种模型能通吃所有场景。用 GPT 解决“能不能做对”的问题，用本地模型解决“能不能便宜、能不能快、能不能私密”的问题。在 OpenClaw 的编排能力下，把决策逻辑清晰固化，保持可观测和可回退，远比追求极致的某个单一指标更重要。

多模型路由不是炫技，而是一种务实的成本与能力平衡术。
