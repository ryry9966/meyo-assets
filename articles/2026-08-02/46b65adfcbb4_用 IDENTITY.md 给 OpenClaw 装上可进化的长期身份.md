## 背景：无状态的智能体，有状态的需求

在 OpenClaw 生态里搭建自动化工作流时，一个很常见的模式是：每次运行 Agent 都从头开始，系统提示里写死角色定义、偏好、约束。对于单次、无上下文的操作（比如“把这条 Issue 总结成三句话”）这完全够用。

但一旦你把 Agent 挂到定时任务里，让它长期维护一个知识库、处理一连串彼此关联的工单，或者持续优化某个目录下的代码结构时，“每次都从空白开始”就成了问题。Agent 会在不同执行之间忘记它曾经做过的决策、学到的教训，甚至忘记自己在这个项目里到底是什么角色。你会在日志里发现，它昨天采用了方案 A，今天没人干预又推出了完全相反的方案 B，行为反复横跳。

根本原因不是说模型不够好，而是**身份和记忆没有固化在协议层**。OpenClaw 自身提供了工具链和 MCP 插件的接驳能力，但并未强制你如何管理长期上下文。大多数实践者仍然把“身份”嵌在不可变的 prompt 文件里，或者随手写在启动命令里，这就导致 AI 永远像个第一天上班的新人。

## 问题拆解：我们需要什么样的持久身份

根据在两个项目（一个内部文档分类 Agent、一个自动处理客户反馈的助手）上的实操，我归纳出三点刚性需求：

1. **一致性角色约束**：什么人该做什么、不该做什么，必须跨会话保持。
2. **可积累的决策历史**：上次选择某个工具的理由、避开的坑，不应该靠人工再次注入。
3. **自我修正能力**：运行中如果发现某条行为准则不适用了，Agent 应当能提出或自动修订，而不是被原先的僵化描述卡死。

这三条本质上要求身份文件不仅是静态“人设”，还得是一份**活的配置文件**，随项目一同演进。

## 做法：把 IDENTITY.md 作为可读写的单一事实源

OpenClaw 本身支持在 agent 配置里引用外部文件作为系统提示的一部分。我们利用这一机制，用 `IDENTITY.md` 作为身份的唯一来源，并允许在某些特定动作之后更新它。

### 第一步：建立初始 IDENTITY.md

文件结构刻意保持简洁，分段式 Markdown，方便人类和大模型都能直接消费。大致长这样（依项目不同会有增减）：

- `# Role`：角色名与一句话定位
- `# Principles`：3–5 条不可轻易变更的原则（例如“只能入库检索到的文档，绝不凭空编造”）
- `# Constraints`：工具、动作、输出格式的硬限制
- `# Context Snapshot`：当前阶段的项目背景，一段话以内
- `# Lessons Learned`：最近执行中积累的经验，每条以 `- date: ...` 打头

初始化内容由开发者手写，不要偷懒让 AI 自己生成第一版，否则容易起点就偏。

### 第二步：在 OpenClaw 配置中挂载

在 agent 的 YAML 或 JSON 配置里，将系统提示指向该文件：

```yaml
system_prompt:
  type: file
  path: "./config/IDENTITY.md"
```

这样每次会话开启，模型都会得到同一份身份声明。注意不要同时存在两条以上系统提示来源，避免角色定义冲突。

### 第三步：定义“更新身份”的可控路径

这里是关键——持续进化的能力不能做成 Agent 随意改自己的身份，否则一夜之间角色设定就可能被污染。我们实践里用了一个受限机制：

- 只在某一类**重要操作完成后**（例如：完成一次知识库重构、处理完一批高优先 Ticket），由 Agent 调用一个 `update_identity` 的工具（自己用 MCP 封装或脚本实现）。
- 工具内部不是粗暴覆盖整个文件，而是只允许在 `## Lessons Learned` 小节追加不超过 3 条带时间戳的新条目，并在 `## Context Snapshot` 更新上下文简述。
- 每次修改后自动做一次 lint 检查：条目不能为空，不能重复，总行数不超 150 行，否则拒绝写入并发回警告。

这样 Agent 在多次迭代后，《Lessons Learned》会从空白逐渐变成一份浓缩的经验库：“`2025-01-14: 不要对缺少 version 字段的 API 结果做缓存，易导致脏数据`”这类的教训会被继承下来。

## 踩坑点：进化过头、身份污染、文件冲突

几个真实碰过的坑：

1. **身份通胀导致 token 爆炸**  
   Lessons Learned 不加修剪，两个月后 IDENTITY.md 膨胀到 800 行，每次会话系统提示直接占掉一半上下文。对策：设置行数上限，同时在月度清理时把久远条目归档到 `ARCHIVE.md`，仅在需要时检索。

2. **前后身份指令互搏**  
   某次 Agent 写入了一条“优先使用新接口 B”；但 Principles 里还保留着“必须使用接口 A”。执行时模型左右为难，表现时好时坏。之后规定：任何动态写入的条目不得与 Principles 冲突，否则写入工具报错，并促发人工介入。

3. **并发竞态**  
   同时间段多个任务试图更新 IDENTITY.md，直接造成文件内容交错损坏。修复很简单：写入工具用文件锁（`flock`），并规定更新操作必须串行排队。

4. **身份泄露到外部链**  
   自动发信或生成对外报告时，模型把内部经验“上次客户 XX 的方案很蠢”也带了出来。补救是在 Constraints 里追加：所有对外内容不得引用 Lessons Learned 里的经验条目。

## 可复用建议

- **版本控制**：IDENTITY.md 一律纳入 Git，更新历史可追踪，出问题能快速回滚。
- **定期「记忆体检」**：每周跑一个只读分析任务，让 Agent 检查身份文件内有无明显矛盾、已过时的上下文。
- **分层记忆**：静态的身份约束（Principles/Constraints）放一个文件，动态经验放另一个文件，降低互相污染的概率。
- **设置记忆衰减**：每追加一条新经验时，移除最旧且无星标的那条，防止无限成长。
- **别把身份做成“神谕”**：关键原则要少而精，更多留给 Agent 根据实际情况自主判断，否则会让它变得僵硬。

## 总结

在 OpenClaw 的自动化实践里，真正持久的不是某次成功的执行，而是如何把每次执行积累的认识**结构化、安全地写回身份本身**。IDENTITY.md 这个简单机制让 Agent 从“每次归零”变成了“慢慢学会干活”的协作者，但它需要有意的治理——允许它写什么、多久修剪一次、如何避免指令冲突——这些工程化细节决定了这个做法是长期资产还是定时炸弹。
