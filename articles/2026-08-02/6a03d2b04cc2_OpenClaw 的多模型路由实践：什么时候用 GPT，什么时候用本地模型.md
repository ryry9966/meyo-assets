## 背景：一边是能力，一边是成本

在 OpenClaw 的 agent 工作流里，常会出现两类需求：

- 复杂推理、多步规划、代码生成、长上下文理解，需要 GPT-4o 级别的能力。
- 大批量文本分类、结构化提取、关键词识别、简单问答，用本地模型就能胜任，且零延迟、零 token 花费。

如果所有请求都走 OpenAI，成本会线性膨胀；全部退回本地模型，复杂任务的成功率、鲁棒性又明显下降。**手动切换模型**只能在开发阶段靠自觉，一旦进到自动化流水线就不可持续。我们需要一个工程化的多模型路由策略。

OpenClaw 的模型后端本身支持 OpenAI、Ollama（本地模型）等多种 provider，并且内置了一个轻量的路由层，允许根据任务类型、复杂度指标或上下文长度动态选择模型。下面把我们在一个实际数据管道 agent 中的做法和踩坑记录下来。

## 问题：路由决策该依据什么？

起初我们尝试用 prompt 长度做简单规则：token > 2000 走 GPT，否则走本地。结果在不规则文本处理任务里频繁翻车。例如一条短 prompt 要求“从财报表格中提取非经常性损益并推算同比增速”，本地模型（Qwen2.5-7B）经常丢字段，而 GPT 一次就能给出结构化结果。

反过来，对大量微博短文本做情感三分类，GPT 的延迟和成本累积下来不可接受，而本地 7B 模型准确率与 GPT 只差不到 2 个百分点。

结论：不能只凭长度，要考虑**任务复杂度**和**可靠性要求**。我们把这个拆成了三个维度：

1. **任务类型**：简单抽取 / 分类 → 本地；推理 / 规划 / 合成 → GPT。
2. **结构性要求**：需要严格 JSON 结构输出且容忍度低 → GPT。
3. **上下文规模**：4K tokens 以下 → 本地可尝试；超过 8K → 倾向于 GPT。

## 做法：在 OpenClaw 里实现条件路由

OpenClaw 的配置方式是在 agent 的 YAML 中为不同 skill 或 tool 指定模型 provider。关键点是它支持一个 `router` 配置段，你可以声明多个模型后端，并给每个路由规则写一个简单的匹配器。

我们采用的配置骨架大概如下（简化后）：

```yaml
models:
  gpt:
    provider: openai
    model: gpt-4o
    api_key: ${OPENAI_API_KEY}
  local:
    provider: ollama
    model: qwen2.5:7b
    base_url: http://localhost:11434

router:
  - name: high_reasoning
    match:
      any:
        - skills: [deep_analysis, code_gen, multi_step_plan]
        - context_length_gte: 8000
        - require_structured_output: true
    model: gpt
  - name: bulk_simple
    match:
      all:
        - skills: [text_classify, keyphrase_extract, simple_qa]
        - require_structured_output: false
    model: local
  default_model: local
```

这种声明式路由的好处是，**不需要在每次 prompt 调用时加一堆 if-else 判断**。OpenClaw 在调用 LLM 前根据当前 skill 名称、上下文 token 数、以及请求中是否要求 `structured_output` 来决定走哪个后端。

对于动态判断的场合，我们还增加了一个轻量预检步骤：在正式执行前，用一个极短 prompt（“评估任务复杂度，输出 low/medium/high”）先跑一次本地模型，如果返回 high 就升到 GPT。这种两级路由额外增加约 200 ms 延迟，但很好地平衡了成本与质量。

## 踩坑点

**1. 本地模型输出格式不稳定**

即使不需要 structured_output，只需一段文本，某些本地模型在长上下文下会截断或重复。我们在 prompt 末尾加入明确的终止符（如 `[END]`），并在 agent 层做了输出完整性检查：如果输出末尾没有结束符，或长度明显异常，则退回到 GPT 重试。这个 fallback 机制救了无数次深夜报警。

**2. 路由规则配置过细会变成噩梦**

一开始我们为每个 skill 都手工指定模型，结果 YAML 膨胀到几百行，新增 skill 时经常漏配。后来收敛到按任务类别（抽取类、生成类、推理类）分组匹配，减少维护成本。

**3. 上下文长度基准不一**

Ollama 的本地模型上下文窗口可能是 4K、8K 或 32K（取决于模型），GPT-4o 则有 128K。如果路由只看请求长度，不考虑实际模型窗口，就可能把超窗口请求发给本地模型导致截断。我们在 router 里加入了每个模型的实际窗口大小，并在 match 条件中使用百分比而非绝对值。

**4. 异步调用下的线程安全**

OpenClaw 的模型调用是异步的，如果本地模型是单进程部署，在高并发时会排队严重。我们在 Ollama 启动时设置了 `OLLAMA_NUM_PARALLEL=4` 并独立进程运行，同时限制了本地模型并发数，超过并发上限的任务直接路由至 GPT，避免堆积。

## 可复用建议

- **先测后路由**：把过去一周的典型任务跑一个基准测试，统计本地模型和 GPT 在各任务类型的准确率和成本，基于数据决定路由边界，而不是凭感觉。
- **用结构化输出做质量门**：对必须输出 JSON 的任务，在设计时就要求 OpenClaw 开启 structured output（支持 json_schema），这样解析失败能立即反馈并触发 fallback。
- **路由策略尽量粗粒度分组**：按任务类别分组，而不是按具体 skill 名，降低维护负担。
- **监控模型分布**：导出每次调用的模型标签、延迟、token 数和成本，定期检查是否有本该走本地却走了 GPT 的“漏网”高频任务，随时调整路由。
- **保留一键全 GPT 的逃生舱**：通过环境变量或配置项，可以快速关闭路由，让所有请求走 GPT，用于紧急排查本地模型故障或集群宕机时。

## 总结

在 OpenClaw 上做多模型路由，本质上是用一层薄薄的决策逻辑把“便宜但能力有限的本地模型”和“昂贵但可靠的 GPT”组合成一条平滑的性价比曲线。关键在于找到真正能区分任务难度的特征，而不是依赖单一指标；以及做好充分的 fallback 与监控，让路由切换对业务透明。

这样搭建起来的 agent，既保住了复杂场景的可靠性，又能把大批简单任务留在本地，账单好看，延迟也低。多模型路由不是银弹，但它确实是我们从原型走向稳定流水线的重要一步。
