## 背景：当 Agent 需要“记住”你

在 OpenClaw 社区的 Agent 实践里，无论是通过 MCP 调用工具链，还是用自定义插件做自动化，一个绕不开的需求是让助手拥有**可召回的记忆**。不再是单次问答，而是从以往交互、文档片段、调试记录中精确捞回上下文，形成连贯体验。

多数框架（包括我们在 OpenClaw 里自建的 memory 插件）都会提供 `memory_recall` 能力。但很快你会发现，核心问题不是“存哪里”，而是“怎么查”。工程上主流两条路：

- **全文搜索（FTS）**：基于倒排索引，依赖精确词匹配或模糊匹配。
- **语义搜索**：用 embedding 向量做余弦相似度检索，捕捉意图而非字面。

过去半年我们在内部几个 Agent 上交替或混合使用二者，填了不少坑。下面结合实际场景，聊聊两种方案的差异、落地做法以及可复用的选择建议。

## 问题：为什么“搜得到”比“存了”更难

以 OpenClaw 的一个典型 Agent 为例：助手会长期维护一份用户偏好、历史任务结论、常用代码片段，总量约 10k 条记忆。用户提出类似“上次那个修复 CI 的脚本再跑一下”时，仅凭关键词 “CI” “脚本” 很难命中那条“在 GitHub Actions 中通过缓存 node_modules 解决超时”的记录——除非你恰好记得原文用词。

这就是全文搜索的短板：**精确匹配对表达变化的容忍度极低**。即便用 FTS5 加前缀匹配，中文环境还得单独配置分词器，否则“修复 CI”和“持续集成”互相查不到。

换成语义搜索，向量表示能够将“修 CI”与“解决 GitHub Actions 超时”关联起来。但代价也明显：embedding 有噪音，会召回字面无关但语义相近的冗余信息（例如“修复超时”把网络超时的记忆也带出来），且需要额外计算和存储，冷启动时还得处理 embedding 模型的延迟与成本。

我在一次 A/B 测试里统计了 200 个真实 query：纯 FTS recall@10 约 62%，纯向量 recall@10 达到 83%，但精确率跌到 57%（很多干扰）。最终决定采用混合策略。

## 做法：从实验到集成

1. **本地 benchmark**  
   抽取 100 条脱敏对话，人工标注 10 个 query 的理想召回集合（最小 1 条，最多 5 条）。准备三个检索后端：
   - SQLite FTS5（内置分词器 + 自定义 tokenize，中文用 jieba 简单切词）
   - Chroma 向量库，使用 text-embedding-3-small 生成 1536 维向量
   - 混合：先用 FTS 过滤 top-20，再对候选集计算余弦相似度并重排序

   在每个后端上跑 query，测量 recall@5、precision@5 和 P95 延迟。

2. **初步结论**  
   - FTS 对代码片段、纯英文命令效果不错，但中文长句歧义严重。
   - 纯向量在模糊口语上回召率高，但容易把“不要红色”的意思解成“红色”，否定词丢失。
   - 混合重排序在 recall 和 precision 上折中最优，代价是两阶段检索多出约 40ms。

3. **集成到 OpenClaw**  
   将上述搜索封装为一个 MCP 工具 `search_memory`，接受 query 与可选 `filter`（时间范围、标签），返回结构化的记忆条目。在 memory 插件里，新增记忆时同步写入 SQLite 表和向量库（后台异步更新 embedding）。工具通过环境变量切换模式：`FTS_ONLY`、`VECTOR_ONLY` 或 `HYBRID`，方便按场景调试。

   流程示意：
   ```
   User -> Agent -> MCP tool search_memory(query, mode=HYBRID)
                -> FTS 初筛 (limit 20)
                -> 向量重排 -> 返回 top_k
   ```

## 踩坑记录

- **中文分词缺失**：SQLite FTS5 默认按 Unicode 字符边界分词，中文变成单字索引，误匹配极多。必须引入 jieba 并自定义 tokenizer，写进 `tokenize` 插件才能正常使用。向量方案则无此困扰。
- **chunk 大小陷阱**：记忆条目若按原始对话切分，一条多轮对话可能上千 token，embedding 容易稀释关键意图。实践中每段控制在 200-500 token，必要时按 QA 对拆分。
- **否定/排除词不可靠**：语义搜索无法保证排除“不要”、“除了”这类词。解决方法是提取否定意图后，在重排序阶段增加规则负加权，或在提示词里显式强调。
- **向量冷启动**：首次加载 embedding 模型耗时明显（本地模型更甚），因此在工具启动时预加载并保持常驻，避免每次调用重新初始化。
- **混合权重漂移**：靠直觉设定 BM25 和向量分数的权重不稳定，推荐用一个小规模验证集做网格搜索，或干脆让 LLM 作为重排序器（代价更高但灵活）。

## 可复用建议

1. **先全文，后补语义**：如果记忆量不到一千条，且查询多为精确匹配（如命令、文件名），直接用 FTS 足够，延迟低且易维护。
2. **结构化过滤是免费午餐**：无论哪种搜索，务必加入时间、会话 ID、标签等元数据过滤，能将候选集缩小两个数量级，显著提升精确率。
3. **保留原始文本，支持回溯**：embedding 不适合展示原文，FTS 文档也需要原始内容。存储时勿删除原始记忆，便于降级或重排序时引用。
4. **为 Agent 设计分层记忆**：短期记忆用 LRU 缓存，长期记忆才走检索。避免高频调用 search_memory 拖慢交互。
5. **在 OpenClaw 配置中可切换后端**：利用环境变量切换 FTS/向量/混合，方便在一台机器上对比 A/B 效果，用数据决定最终方案。

## 总结

语义搜索和全文搜索在 memory_recall 里不是替代关系，而是互补工具。在 Agent 记忆量爆涨、查询口语化的场景下，纯关键词力不从心；而纯向量又可能把回忆变成噪声生成器。混合策略加结构化过滤是当前性价比最高的路径。

最重要的是**不要过早优化**：从最简单的 FTS 开始，用真实日志评估命中率，当发现“明明存了却搜不到”的比例超过可接受范围时，再引入 embedding 和重排序。工程决策应当由数据驱动，而非追逐热点。
