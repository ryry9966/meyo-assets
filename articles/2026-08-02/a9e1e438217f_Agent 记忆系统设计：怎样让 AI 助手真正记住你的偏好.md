## 背景：AI 助手为什么总在“重新自我介绍”

大多数 Agent 或自动化助手，每一次对话都像第一次见面。哪怕你花了三十分钟纠正它的输出风格，下次新会话一开，它又回到出厂人设。

这背后的技术矛盾是很明确的：

- 大语言模型本身是无状态的，一次推理只能看到当前上下文窗口里的东西。
- 为了控制 token 消耗和延迟，我们不可能把所有历史记录全部塞进 prompt。
- 用户的真实偏好往往是**潜藏的、分层的、跨会话的**，比如“用中文回复但代码变量必须用英文”“不要在周五下午发总结报告”“提到竞品时不评价”。

市面上常见的“记忆”实现，本质上只是把最近几次对话摘要塞入 system prompt，或者用 RAG 粗暴检索相近对话。结果就是：助手看起来记性不错，其实只是**复读历史片段**，无法抽象出稳定的用户模型，更做不到根据场景动态取舍。

本文面向在 OpenClaw 生态里自己动手搭 Agent 的开发者，探讨一套可落地的记忆系统设计，让助手实现**工程级可用的长期偏好记忆**，而不是 demo 里的“你好，我们又见面了”。

## 问题拆解：记忆系统到底要解决什么

如果只是把对话历史存入向量数据库，然后检索相关内容，那只是“对话考古”，不是真正的记忆。一个工程上合理的 Agent 记忆系统，至少要处理三个层面的问题：

1. **偏好提取与抽象**  
   从自然语言交互中剥离出稳定的、可操作的偏好条目。例如用户说“这个回复太啰嗦了”，抽象为 `response_style.conciseness = high`。

2. **冲突消解与老化更新**  
   用户偏好会变。三个月前要求“每封邮件开头加问候语”，后来觉得太机械，新指令应该覆盖旧偏好。系统必须有改写、衰减和合并机制，而不是简单追加。

3. **按场景精准注入，而不是全量喂给模型**  
   记忆的用途是让模型在**该想起的时候想起**。在设计时，要区分“永久身份级信息”（角色、语言、时区）、“任务上下文偏好”（代码风格、输出格式）和“临时会话约束”，并独立管理其生命周期。

这些问题不解决，记忆系统做得越多，冗余和冲突越严重，反而会污染 prompt，让模型行为变得更不稳定。

## 做法与步骤：一个可落地的三层记忆架构

在实际项目中，我习惯将 Agent 记忆拆成三层，每一层用不同的存储和召回策略。

### 1. 身份层 —— 确定性 profile

这一层存储几乎不变或极少变化的用户事实，例如：

- 称呼偏好
- 时区 / 地点
- 母语与常用语言
- 角色（开发者、管理者、写作者）

存储方式直接用结构化 JSON，例如 `user_profile.json`，通过 OpenClaw 的 `user` 对象或 session 元数据挂在每轮请求里，始终全量注入 system prompt。因为字段少且稳定，不会造成 token 压力。

关键做法：**写入必须通过显式的“更新 profile”工具调用**，而不是从对话中自动推测。防止助手自作主张把一次性的情绪化表达（“叫我天才少年吧”）写入永久身份。

### 2. 偏好层 —— 可变长记忆

这是记忆系统最复杂的部分。用户的输出风格、工作习惯、对特定话题的禁忌等，都以**结构化偏好条目**存储。

**存储设计**  
每条偏好记录包含：

- `category`：如 `communication_style`, `code_convention`, `report_format`
- `key`：精确定义的属性，如 `verbosity`, `technical_depth`
- `value`：可以是枚举、数值区间或自然语言描述
- `confidence`：0–1 之间的确信度
- `source`：来源会话 ID
- `last_updated`：时间戳
- `status`：`active / deprecated / conflicted`

这些记录存储在支持 JSON 的文档数据库或向量库中（如 Postgres pgvector, Chroma 等），以 `(user_id, category, key)` 作为唯一标识，方便点更新。

**写入时机**  
- 用户在对话中显式表达喜好时，Agent 调用 `update_preference` 工具。
- 在会话结束阶段，用一个小模型（或同模型但低温度）对该轮对话做一次摘要，提取潜在偏好作为候选，**仅当确信度高于阈值且用户未反对时，创建 `confidence` 低的条目，并在下次会话开头主动确认**。这样做既避免骚扰用户，又能逐步丰富记忆。

**冲突处理**  
当新条目的 key 相同但 value 冲突时，不是覆盖，而是：

- 把旧条目标记为 `deprecated`
- 创建新的 `active` 条目，并在 `metadata` 中记录替代关系
- 定期运行清理任务，对于长时间未再更新的陈旧冲突条目，自动清理或降级

### 3. 会话上下文库 —— 近因缓冲

这是大家最熟悉的“RAG 记忆”，只保留最近 N 次对话的高质量摘要，用于回答类似“上次我们聊到哪了”。与偏好层不同，这一层不抽象为概念，而是保留当时的任务上下文和决策结论。

在 OpenClaw 中可借助内置的 `MessageStore` 或自定义 MCP 记忆服务，把每条会话的总结以时间序列存储，检索时加权近期。

三层记忆在每次对话中的注入方式：

- 身份层：始终全量注入 system prompt
- 偏好层：用当前对话的 **意图检测** 结果，动态选择相关 category 的 active 条目，以简洁的列表形式注入（例如“用户偏好：输出简洁，技术深度高，避免行尾注释”）
- 会话上下文库：仅在用户提出“继续上次”或明显引用历史任务时，检索前几次会话摘要注入

这样既保证记忆精准度，又避免了 context bloat。

## 踩坑记录

在实际推代码过程中，下面几个坑几乎每个都会遇到：

1. **把对话摘要直接当偏好**  
   用户说“我最近在学 Rust”不是偏好。偏好是“解释概念时多用 Rust 举例”。不加区分的记忆提取会让系统充满噪音，真正要用时反而被淹没。

2. **偏好注入过于积极**  
   即使是相关偏好，一次注入过多也会让模型产生“被迫营业”的感觉，回复僵化。通常限制在 5–8 条以内，并根据 relevance score 排序。

3. **缺少确认机制导致信任崩塌**  
   自动提取偏好的功能，如果直接写入而不在适当时机向用户确认，一旦出错，用户会觉得“这助手乱记东西”，信任成本极高。稳妥的方案是：低确信度偏好先挂起，在下一次会话开头用自然语言征求同意：“我注意到你之前倾向于看短答案，是否将这个作为默认偏好？”

4. **版本控制缺失**  
   偏好是动态演进的。没有记录历史版本，就很难排查“为什么助手突然不用 Markdown 了”。可以在每次更新时打一个快照，提供回滚能力。

## 可复用建议

- **工具化记忆操作**：把“记住”“忘记”“更新偏好”都作为 Agent 的标准工具（OpenClaw 中通过 Tool/Plugin 注册）。让记忆操作对用户透明，也能生成审计日志。
- **用意图路由决定记忆注入**：不要每次请求都去检索全部记忆。根据当前 query 的 intent，只拉取相关 category 的活跃偏好，能显著降低注入噪声。
- **设置遗忘策略**：偏好如果长时间未被引用或使用，自动降低权重或标记为过期。避免用户一年前的要求一直困扰助手。
- **坚持最小化原则**：记忆系统是一个放大器，好的偏好配置可以大幅度提升体验，但一旦记忆错误，代价也极大。设计上宁可少记、确认后再记，也不要贪多。

---

## 总结

真正让 AI 助手“记住你”，不是靠塞入更多历史消息，而是通过一套有分层、有冲突管理、有遗忘机制的记忆架构，把用户的意图和习惯抽象为可操作的结构化知识。工程上的核心挑战不在于“存”，而在于在合适的时间以合适的方式让模型想起合适的信息。

对于用 OpenClaw 做深度定制的工程师来说，把记忆系统视为一个独立组件，定义好它的写入/召回/更新/遗忘生命周期，远比堆 RAG 检索重要得多。
