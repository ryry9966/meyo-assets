## 背景：信息过载的日常解法

RSS 仍然是最可靠的信息获取方式之一，但它带来的噪音不比社交媒体少。订阅源一多，几百条未读里真正值得点开的往往只有个位数。我们想要的不是“更多消息”，而是在对的时间看到对的关键信息。

去年开始，我在自己的 OpenClaw 实例上搭建了一条自动化管线：定时抓取 RSS → 去重 → 调用 LLM 生成一句话摘要 → 推送到任务栏或聊天工具。运行至今，每天大约能节省 40 分钟的信息筛选时间。这篇文章记录整个搭建过程、踩过的坑和一些可复用的设计思路，适合正在用 OpenClaw、Agent、MCP 或类似工具做自动化实践的朋友。

## 需要解决的问题

- 多个 RSS 源更新频率不同，手动翻看成本高。
- 标题党文章在未读列表里很难辨别质量。
- 本地阅读器和推送渠道割裂，摘要要么太短看不懂，要么太长失去提炼价值。
- 管线需要稳定运行，不能因为某个源解析失败就整体中断。

## 做法 / 步骤

### 1. 整体架构

```
RSS 源 → OpenClaw Workflow (定时触发) → HTTP/RSS 节点获取 → 去重判断 → AI 摘要节点 → 推送节点 (飞书/Telegram/邮件等)
```

全程在 OpenClaw 内用低代码节点拼接，不引入外部调度器。如果你习惯用 MCP，可以把 RSS 获取封装成一个 MCP 工具，再由 OpenClaw 的 Agent 节点调用，扩展性会更好，但入门阶段用内置节点足够。

### 2. 核心工作流设计

**触发器：** Cron 节点，设置比如每 30 分钟运行一次。如果源更新频繁可缩短，但注意避免被源站限流。

**RSS 获取：** 使用 OpenClaw 的 RSS Read 节点，配置多个源的 URL。建议把所有源维护在一个 JSON 数组变量里，方便批量管理。示例：

```json
[
  {"name": "Hacker News", "url": "https://hnrss.org/frontpage"},
  {"name": "Arxiv cs.AI", "url": "http://arxiv.org/rss/cs.AI"}
]
```

通过循环节点逐个读取，每个源返回最近 5 条 entry，避免一次拉取太多导致后续 AI 节点 token 溢出。

**去重：** 这是管线能不能长期跑的命门。我用了一个简单的方案：在 OpenClaw 内置的全局变量里维护一个“已处理链接”的集合，每次新条目进来先判断链接是否已在集合中。条目处理成功后把链接加入集合并保留最近 2000 条，防止变量无限膨胀。也可以改用外置数据库节点，但初期用内置变量更轻量。

**AI 摘要：** 连接 OpenClaw 的 OpenAI 节点（兼容任何 OpenAI API 格式的服务，包括本地模型）。使用的 system prompt 很克制：

> 你是一个信息总结助手。请用中文给出以下文章的一到两句话摘要，只保留核心论点和关键事实，不要添加评价。如果内容为纯技术教程，请指出它解决了什么问题。

用户消息部分传入 `{feed.name} - {entry.title}\n{entry.contentSnippet}`。为了控制 token，contentSnippet 截取前 1500 字符。温度设为 0.2，以保证输出稳定。

**推送：** 摘要生成后，拼成“**源名称**：摘要 [原文链接]”的格式，通过飞书机器人 Webhook 或 Telegram Bot 发送。OpenClaw 的 HTTP Request 节点可以直接 POST JSON 到 Webhook URL。如果某条发送失败，用错误处理分支记录到 Webhook 日志并继续处理下一条，避免单点阻塞。

### 3. 进阶：串接 Agent 做二次过滤

如果你用 OpenClaw 的 Agent 节点，可以在摘要之后再挂一个判断步骤。例如用 Agent 分析摘要文本，判断是否与“大模型编排”“RAG 性能”等关键词相关，只推送高相关度的条目。这样可以把每日推送从 40 条降到 10 条以内。Agent 的能力通过 MCP 增强后还可以自动归档到你的笔记软件，这部分可以自行扩展。

## 踩坑记录

- **RSS 格式不规范：** 有些源 contentSnippet 为空或编码异常，导致摘要节点收到空输入。解决方式是在循环内加一个条件判断，如果 contentSnippet 长度小于 20 字符，则使用 title 作为摘要输入。
- **AI 调用限流与成本：** 30 分钟跑一次，10 个源各取 5 条，每次最高 50 次 API 调用。用便宜的模型（如 deepseek-chat、gpt-3.5-turbo）日成本可控在 0.5 元以内。关键在于设置 API 节点的并发和重试策略，遇到 429 错误自动等待 5 秒重试一次。
- **去重变量被清空：** OpenClaw 实例重启后，未持久化的变量会丢失。需要把已处理链接集合落盘。我后来改用 Workflow 静态数据存储，每次更新时写入 JSON 文件，重启后恢复。
- **链接失效：** 有些摘要里的原文链接会随时间失效，所以推送消息里最好带上源名称和发布日期，方便回溯。

## 可复用建议

1. **配置外置化：** RSS 源列表、API key、Webhook URL 均通过 OpenClaw 环境变量或工作流凭证管理，不要写死在节点里。切换环境或分享工作流给他人时会省很多事。
2. **先跑一周再优化：** 初期不要追求完美去重和精确摘要，先让管线稳定跑起来，根据实际推送结果调整截断长度、提示词和推送频率。
3. **错误分级处理：** 区分“源级错误”（某个 RSS 源挂了）和“条目级错误”（某条摘要失败）。源级错误连续出现 3 次后自动静默跳过该源并发送一条告警给自己，避免管线被一个坏源卡死。
4. **保留原文缓存：** 如果希望摘要可点击回原文，但原网站需要登录或有反爬，可以在获取 RSS 时把条目正文全文缓存到临时空间，再传给摘要节点。注意法律合规，仅用于个人阅读摘要。

## 总结

RSS + AI 摘要这条管线在搭建成本和使用收益之间达到了一个很舒服的平衡点。OpenClaw 的低代码能力让整个流程在一两个小时内就能上线测试，而引入 Agent 和 MCP 后，信息过滤的灵活度可以远超传统 RSS 阅读器。如果你也在维护自己的信息输入管道，不妨先用最小配置跑一个周末，看看它能帮你滤掉多少噪声。
