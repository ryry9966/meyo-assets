## 背景

在多人协作的软件项目中，Git 操作的规范性直接影响代码追溯、发布日志质量以及团队协作效率。然而，现实是：

- **commit 信息随意**：`fix bug`、`update` 满天飞，回溯时根本不知道改了什么；
- **分支命名混乱**：`dev-123`、`myfix`、`zhece-test`，无法关联需求或问题；
- **重复机械操作**：每次提交都要手写 Conventional Commits 格式、创建分支时要先查 Jira 编号再拼分支名。

这些问题本质上是“规范需要额外心智负担”，而人类在高压开发节奏下难以持续遵守。Git 自动化正是为了把这种规范性成本转嫁给工具，让开发者专注代码本身。

对于已经使用 OpenClaw、MCP、Agent 或各类插件进行工作流自动化的团队来说，让 AI 助手接管 Git 操作是一个低门槛、高回报的切入点。

## 痛点分析

1. **commit 信息质量不稳定**  
   即便团队约定了 Conventional Commits，开发者仍会忘记 type/scope，或者在改了一堆文件后随手写个 `WIP`。

2. **分支创建需人工中转**  
   拿到一个需求编号，需要打开终端、切回主分支、`pull`、再 `checkout -b feature/XXX`，路径长且容易打错。

3. **上下文丢失**  
   很多 commit 只描述“做了什么”，不关联“为什么做”，导致合并冲突或重构时缺乏决策背景。

4. **与 AI Agent 的割裂**  
   团队可能已经用 Agent 分析需求、拆任务，但最后落实到代码仓库时又回到手动操作，链路中断。

自动化目标不是完全替代人类，而是让 AI 生成**高概率可用的草稿**，由开发者确认；同时在分支、标签等策略性操作上提供一键式指令。

## 方案与实现步骤

### 1. 基于 Git Hooks 的自动 commit 信息生成

最轻量的切入点是在本地仓库配置 `prepare-commit-msg` hook，在提交时调用 LLM 根据 `git diff` 生成规范的 commit 信息，并预填写到编辑器中供确认。

**步骤：**

- 在仓库 `.git/hooks/prepare-commit-msg` 中写入脚本（此目录不会被跟踪，建议使用模板同步脚本）。
- 脚本逻辑：
  1. 获取暂存区 diff：`git diff --cached`
  2. 将 diff 截断至合理长度（避免 token 超限），并加入系统提示词，要求按照 Conventional Commits 格式生成 type(scope): description 以及可选的 body。
  3. 调用 OpenAI 兼容 API（或本地模型），例如通过 `curl` 或 Python 请求。
  4. 将返回的 commit 信息写入 `$1` 参数文件（即 `.git/COMMIT_EDITMSG`），并附带注释提示用户可修改。

**关键代码片段（Python 简化版）：**

```python
import sys, subprocess, requests, os

diff = subprocess.check_output(['git', 'diff', '--cached']).decode()
if not diff.strip():
    sys.exit(0)

prompt = f"Generate a conventional commit message for this diff:\n{diff[:4000]}"
resp = requests.post("https://api.openai.com/v1/chat/completions",
    headers={"Authorization": f"Bearer {os.environ['OPENAI_API_KEY']}"},
    json={"model": "gpt-4o-mini", "messages": [{"role": "user", "content": prompt}]})
msg = resp.json()['choices'][0]['message']['content'].strip()

with open(sys.argv[1], 'w') as f:
    f.write(msg + "\n# Generated by AI, edit if needed\n")
```

### 2. 用 Agent + MCP 实现智能分支管理

对于已接入 OpenClaw 的团队，更彻底的自动化是通过 MCP (Model Context Protocol) 让 Agent 直接操作 Git。可以部署一个 Git 操作的 MCP 服务器，对外暴露工具如 `create_branch`、`commit`、`push`、`create_pr` 等。然后 Agent 根据用户自然语言指令执行操作。

例如，用户对话：
> “帮我把 JIRA-3344 的需求改成分支 feature/JIRA-3344-fix-payment，并基于 main 新建”

Agent 解析意图后，调用 Git MCP 工具：

- `create_branch(base="main", name="feature/JIRA-3344-fix-payment")`
- 若需要，还可自动 `fetch`、`rebase` 等。

**MCP 服务器的关键实现点：**

- 使用 `simple-git` (Node.js) 或 `GitPython` (Python) 封装仓库操作，注意处理工作目录路径。
- 工具返回结构化结果（分支名、当前 HEAD 等），供 Agent 校验。
- 加入安全检查：不能允许自动强推、禁止删除受保护分支等。

### 3. 结合 pre-push 钩子做最后防线

在 `pre-push` 钩子中校验即将推送的 commit 信息格式，不满足 Conventional Commits 的直接拒绝推送，并给出修正提示。这一步确保即使开发者忽略了 AI 生成的建议，也不会把不合格的 commit 推向远程。

```bash
#!/bin/bash
# 检查每个待推送的 commit
while read local_ref local_sha remote_ref remote_sha; do
    for sha in $(git rev-list $remote_sha..$local_sha); do
        msg=$(git log --format=%s -n 1 $sha)
        if ! echo "$msg" | grep -qP '^(feat|fix|docs|style|refactor|test|chore|perf|ci)(\(.+\))?: .+'; then
            echo "Error: commit $sha does not follow Conventional Commits."
            exit 1
        fi
    done
done
```

## 踩坑点与排障

1. **API 延迟导致 `git commit` 卡顿**  
   如果每次提交都要等 LLM 返回结果，会显著拖慢节奏。**解法**：使用异步调用或流式返回，先填充默认信息，在编辑器等待期间持续更新；或者预生成候选列表供 `commit` 时选择。

2. **diff 过大导致 token 超限或输出不准确**  
   直接丢整个 diff 会浪费 token 且生成质量下降。**解法**：对 diff 做智能截断（只保留文件路径和主要变更摘要），或仅发送变更统计 `git diff --stat --cached`，让模型推断。

3. **API Key 泄漏风险**  
   不要把密钥硬编码在 hook 脚本中，使用环境变量或密钥管理器注入。同时注意不要将敏感代码 diff 发送到外部 API，可配置忽略文件或用本地模型。

4. **hooks 在不同操作系统不兼容**  
   Windows 的 shell 脚本执行问题，**解法**：可以统一用 Python/Node 脚本，并通过 Git 勾子调用解释器，如 `#!/usr/bin/env python`；或使用 Docker 化的开发环境统一执行环境。

5. **MCP 操作权限过大**  
   Agent 直接调用 Git 工具存在误操作风险。**解法**：工具设计采用确认步骤，或设定“试运行”模式，仅输出预期命令，由用户确认后再真正执行。

## 可复用建议

- **将 hook 脚本模板化**：放入项目 `scripts/git-hooks/` 中，并通过 `git config core.hooksPath` 指向该目录，使得 `git clone` 后可通过脚本一键安装。
- **采用分层自动化**：AI 负责**生成候选**，钩子负责**格式校验**，CI 负责**最终质量门禁**（如检查 commit 是否关联 issue），不要只依赖单点。
- **结合 changelog 自动生成**：有了规范的 commit 信息，可以用 `standard-version` 或 `semantic-release` 直接生成发布日志，形成从 commit 到 release 的完整链路。
- **离线场景**：当无法访问云端 API 时，可降级到本地规则模板（如基于文件路径推断 scope），确保核心流程不受影响。

## 总结

Git 自动化不是“用 AI 替人写 commit”，而是将机械且易出错的规范工作下沉到工具链，让开发者的决策精力只花在真正需要判断的地方。通过 Git Hooks + LLM 的轻量集成，以及 Agent + MCP 的深度整合，可以显著降低团队遵守规范的成本，同时提升代码历史的可读性。

对 OpenClaw 用户而言，这套实践很容易与现有的 Agent 工作流结合——把 Git 当作另一个可操控的工具，对话式管理仓库就在眼前。起步时，别追求一步到位，先从 “commit 信息预填” 这个单点切入，跑通后再逐步纳入分支管理、PR 创建，最终形成闭环。
