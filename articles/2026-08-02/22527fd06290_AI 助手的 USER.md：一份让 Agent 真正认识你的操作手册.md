# AI 助手的 USER.md：一份让 Agent 真正认识你的操作手册

## 背景

在 MCP 工具链和 Agent 自动化的场景里，我们习惯花大量时间优化 system prompt、调 function call schema、给 tool 写 README，却极少花时间系统化地告诉 Agent **你是谁**。

直接结果是：
- 你每次新开一个会话，都要重新描述自己的工作环境、代码风格、项目结构。
- Agent 给出的建议偏向通用最佳实践，而不是“你本人的实践”。
- 工具调用时参数填错目录、记不住你之前踩过的坑、重复踩同样的环境问题。

这其实不是 Agent 不够聪明，而是 **上下文被会话边界切断，缺乏持久化的用户画像**。

解决这个问题的工程化方案之一，就是维护一份 `USER.md`。

## 问题

Agent 会话里常见的问题模式：

1. **环境不一致**  
   你告诉过 Agent 你的项目在 `~/lab/project-a`，但下次新对话它又默认为 `./` 或 `/workspace`。因为每次对话都重置了环境根。

2. **风格偏好丢失**  
   你上次纠正过“别给我写 class，保持纯函数”，但下次它对同样场景又产出面向对象方案。

3. **工具链信息缺失**  
   你分明在用某个自建 MCP server，但 Agent 不知道你的常用命令、别名、甚至本地的 API key 是环境变量命名。

4. **你踩过的坑没有沉淀**  
   某个项目的依赖必须在 Python 3.10 且不能高于 3.11，你给 Agent 讲过一次，但下个会话它忘了，又给你推荐用 3.12。

这暴露出一个问题：**我们缺少一份持久化的、可被 Agent 直接消费的用户上下文。**

## USER.md 是什么

`USER.md` 是一份独立于具体项目的 Markdown 文件，**专门写给 AI Agent 读取**，用来快速建立对你的持久认知。

它不是简历、不是个人 wiki，而是 **Agent 的引导文件**。它的目标：  
即使你是第一次和某个 MCP host 会话，Agent 也能通过读取 USER.md 获得工作基线。

结构上它和 `README.md` 很像，但内容面向 Agent，而不是人类协作者。

## 做法 / 步骤

### 1. 确定 USER.md 存放位置

最佳实践是放在 **可被 Agent 轻松访问的工作区根目录或全局配置路径**。

例如在 OpenClaw 的会话里，你可以这样约定：

- 项目级：`~/projects/my-agent-stack/USER.md`
- 全局级：`~/.agent/USER.md`

然后通过 system prompt 或插件的“启动时预加载文件”能力，让 Agent 每次会话都读取它。  
如果你在用类似 OpenClaw 的持久上下文特性，也可以直接把它加入全局记忆片段。

### 2. USER.md 的核心结构（模板示例）

下面是一个经过多轮调试后稳定的模板，建议按区块组织，方便 Agent 理解。

```markdown
# USER.md — Persistent context for AI agents

## 1. Identity & Role
- 角色：独立开发者 / 后端为主，偶尔做 infra
- 工作语言：中文语境，但技术术语用英文原词

## 2. Environment Baseline
- OS：macOS 14，Shell 为 zsh
- 默认工作区根：~/lab （非 /workspace）
- 包管理：pip 全局用 pipx，项目级用 rye
- Node.js 默认版本：20 LTS；Python 默认版本：3.11

## 3. Project Layout Convention
- 项目管理采用 ~/lab/<project-group>/<project-name>
- 每个项目根有 Makefile，主要入口：
  - make dev：启动开发环境
  - make test：运行测试套件
  - make lint：代码检查
- 非 Docker 项目优先用 venv + rye sync

## 4. Code Style & Preferences
- Python：只用 3.10/3.11；避免用 class，写纯函数
- TypeScript：禁止 any；prefer interface 而不是 type
- 注释语言：中文解释业务逻辑，英文解释技术细节
- 配置管理：用 .env + pydantic-settings，不加多层 config

## 5. Common Command Aliases
- ga = git add -A && git commit -v
- gp = git push
- tl = tmux ls
- venv = source .venv/bin/activate

## 6. MCP & Tooling Preferences
- 本地 MCP server 配置在 ~/mcp-config/servers.json
- 自定义工具调用时，不要启用 Docker，本地直连
- 涉及 API key 时永远从环境变量读取，不要写死

## 7. Known Pitfalls
- pnpm 在 monorepo 下和 turbo 有版本锁定问题，强制用 pnpm@8
- Python 3.12 兼容性问题：fastapi 的某些中间件在 3.12 下会报 deprecation warning，不做生产使用
- 项目 X 必须用 venv，不能使用 conda，因为会引入系统库冲突
```

每一个分区都对应 Agent 容易出错的地方。  
你不会在一个会话里把以上信息说全，但 `USER.md` 能一次性填平这些坑。

### 3. 让 Agent 消费 USER.md

不同的 Agent 框架消费方式略有差异，可复用的模式：

- **在 system prompt 里注入 `preload:USER.md` 指令**  
  例如 OpenClaw 的全局 system prompt 增加一句：  
  `Always read the USER.md in the project root before acting.`

- **作为记忆插件的种子文件**  
  如果你的 Agent 有记忆/知识库插件（类似 MCP 的记忆 server），可以将 `USER.md` 分割为语义块存入，会话启动时自动检索相关片段。

- **在自主工作流里做上下文初始化步骤**  
  对于复杂 Agent，可以定义一个 `init` step，让 Agent 自己 `cat USER.md` 并提取关键字段（角色、环境根、常见别名等）填入工作记忆。

踩坑点：  
- 只放一份 `USER.md` 但未在 prompt 里强制读取 → Agent 经常忽略，导致效果时好时坏。  
- 用中文和英文混写，但没注明“技术术语保留英文”，导致 Agent 在代码注释时全部翻译成中文，破坏可读性。需在 Language 部分明确说明。

## 踩坑点与优化

1. **文件过长导致 Agent 忽略后半段**  
   如果 `USER.md` 超过 500 行，Agent 可能在注意力窗口前部就终止阅读。建议控制在 150 行以内，只保留关键偏差信息，通用信息不要放。

2. **未经测试就写进 USER.md 的“偏好”实则干扰**  
   比如写下“尽量写尽可能少的注释”，结果 AGent 在复杂逻辑处完全不写注释，给后续调试带来麻烦。应该写成：“注释解释为什么，不解释是什么”。

3. **与项目 README.md 冲突**  
   项目 README 描述项目本身，USER.md 描述你作为用户的工作习惯。不要让 USER.md 替代 README，也不要让 README 包含你个人的全局偏好。

4. **别名信息过时没更新**  
   USER.md 是活的文档，你改变了终端别名、升级了默认 Python 版本后必须同步更新，否则 Agent 会延续旧的环境假设，产生难以排查的隐形错误。

## 可复用建议

- 为 `USER.md` 建立一个版本号字段，通过 agent 指令可以读到版本，从而在需要时提示你更新。
- 对多人协作的 Agent 场景，可以考虑 `TEAM.md` 代替 `USER.md`，记录团队的共同约定、工具版本、项目布局。
- 结合 MCP 工具，编写一个 `read_user_md` 工具，专门在会话初始化时被调用一次，返回摘要给系统提示，而不是把全文塞进上下文。
- 如果你的 Agent 支持 profile 切换，可以维护多份，如 `~/.agent/profiles/work.md` 和 `personal.md`，通过启动参数选择。

## 总结

`USER.md` 不是银弹，但它是**目前工程化成本最低的个人上下文持久化方案**。

在 Agent 还无法真正跨会话长期记忆的阶段，它能显著减少重复沟通，把宝贵的上下文窗口留给真正的业务逻辑。

如果你已经开始重度使用 OpenClaw、MCP 或自定义 Agent 工作流，不妨花 15 分钟把自己的第一份 `USER.md` 写出来，然后把它植入到 system prompt 里。很快你会察觉——Agent 似乎“更了解你”了。
