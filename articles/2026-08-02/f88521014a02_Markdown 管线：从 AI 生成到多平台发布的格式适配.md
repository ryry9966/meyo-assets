## 背景

AI 辅助写作已进入工程化阶段——你用 Agent 生成一篇技术文章，可能只需要半分钟，但把它发到公众号、知乎、GitHub、CSDN 等平台，却要花上数倍时间调整格式、替换图片、修复公式和代码块。根本原因在于，各平台对 Markdown 的支持子集完全不同：公众号依赖富文本，知乎能渲染 LaTeX 数学公式但对 Markdown 方言挑剔，GitHub 擅长 GFM 却不支持内联样式，而 CSDN 在代码高亮上又有自己的别名体系。

如果你和团队正在用 OpenClaw 搭建内容自动化流程，或者通过 MCP 串联 AI 写作与发布工具，建成一条“Markdown 管线”是阻止格式问题向上游扩散的唯一办法。

## 问题拆解

直接出问题的点集中在四方面：
1. **图片**：AI 生成的 Markdown 里放的往往是本地路径或临时链接，而公众号需要把图片上传到微信素材库，知乎需要存放到自己的图床或第三方图床，且不同平台对图片尺寸和格式有隐形限制。
2. **数学公式**：LLM 习惯输出 `$$...$$` 或 `$...$`，但公众号富文本完全不支持，知乎虽然支持但需要更严谨的 LaTeX 转义。
3. **代码块**：语言标识别名混乱，例如 `js` / `javascript`、`shell` / `bash`，有些平台遇到未识别的标识会直接不渲染高亮。
4. **链接与元数据**：某些发布渠道会自动在链接后附加统计参数，还可能修改 `title`、`author` 等 front matter 的显示规则，导致最终呈现与设计不一致。

如果每次都靠手改，就不是自动化。

## 管线设计：从源到五个发布端点

我基于 OpenClaw 的能力，搭建了一条可复用的管线，流程如下：

**1. 规范源文件**
要求所有 AI 产出物使用统一模板，基于 CommonMark 扩展，但额外约定：
- 图片使用 `<figure>` + `<img>` 的 HTML 写法，方便后续替换。
- 公式用 `$$` 包裹，且公式内部不混用 Markdown 语法。
- front matter 以 YAML 书写，标明标题、作者、标签、目标平台列表。

**2. 基础渲染与中间表示**
选用 Pandoc 作为转换引擎，将规范后的 Markdown 转为 AST（文档对象模型）。Pandoc 支持 Lua 插件，可以在 AST 层面做平台无关的变换：比如把标准化公式节点提取出来，把图片节点的 `src` 统一替换为可配置的占位符。

**3. 平台适配器**
针对不同平台，编写轻量的适配模块：
- **公众号**：将 AST 渲染为符合微信规范的内联样式 HTML（不要用外部 CSS），同时通过 MCP 调用公众号素材上传接口，把图片逐一上传，再回写图片链接。代码块转为带灰色背景的 `<pre>` 标签，并关闭微信的自动链接识别。
- **知乎**：输出标准 Markdown 文本，但事先对公式做两件事：把 `_`、`&` 等字符转义；如果公式块被平台限制，降级为图片（提前用 MathJax 渲染并通过图床上传）。链接不做任何附参处理。
- **GitHub**：直接输出 GFM Markdown，保留原始代码块标识，由 GitHub 自己的渲染器处理。
- **CSDN**：和知乎类似，但在代码块语言标识上做一次映射（`js` -> `javascript`，`sh` -> `bash`），且额外处理目录锚点。
- **通用图床**：所有适配器都依赖一个统一图床服务（例如通过 MinIO 或阿里云 OSS），该服务也封装为 MCP 工具，提供上传、裁剪、获取公开 URL 的功能。

**4. OpenClaw 接入**
在 OpenClaw 中，我把上述整套流程打包成一个 MCP 服务：接收 agent 生成的 Markdown，根据 front matter 中的平台列表，并行触发对应的适配器，最后返回各平台的发布内容或直接写入平台草稿箱。Agent 的唯一任务就是确保初始 Markdown 符合源文件规范。

## 踩坑记录

- **公众号素材接口限频**：短时间内大量上传图片会触发 `45009` 错误，必须在适配器内加入重试和速率控制，同时缓存已上传图片的 URL，避免重复上传。
- **知乎公式渲染差异**：`\begin{aligned}` 环境在移动端容易溢出，需要为公式额外设定 `\small` 并限制宽度；不建议使用 XML 标签包裹公式，只用纯 `$$`。
- **Pandoc 版本差异**：部分团队本机安装的 Pandoc 版本较老，对 `pipe_tables` 或 `fenced_code_blocks` 支持不一致，最好在 CI 中固定版本（如 3.1.9）。
- **额外空格导致断行**：在某些平台，全角字符与 Markdown 标记之间会自动插入 `<br>`，需要预处理阶段移除不必要的零宽空格。

## 可复用建议

1. **单一源原则**：永远只保留一份规范 Markdown 源文件，平台差异只在适配层解决。
2. **插件化适配器**：每个平台用独立函数或 module 实现，统一接口为 `(markdownAST, options) -> result`，便于增删平台。
3. **图片托管与域名白名单**：提前配好图床的防盗链白名单，保证各平台都能正常加载图片；推荐通过 MCP 工具暴露上传能力，避免暴露密钥。
4. **利用 OpenClaw 的流水线重试**：当某个适配器失败时，只重跑该任务，不影响其他平台发布。可在 agent 里设置条件分支，检查图片上传状态后再启动渲染。
5. **持续校验**：用 Golden Test 验证渲染输出，例如公众号 HTML 是否符合格式规范、公式图片是否生成等，作为 CICD 的一环。

## 总结

Markdown 管线本质上是对“多平台非对称支持”的消歧义层。AI 写作减少了内容生产的心智负担，但如果不把格式适配自动化，发布环节反而会成为瓶颈。利用 Pandoc 的 AST 操作和 OpenClaw 的 Agent/MCP 调度，你可以将“从写好到发好”的时间从几小时压缩到几分钟，且保持输出一致。这条管线已经在我们团队稳定运行数月，值得任何从事多平台内容分发的实践者复用。
