# AI Agent 的权限边界：分级控制与人类确认的工程化实践

## 背景：当 Agent 不再只是“只读”助手

随着 MCP (Model Context Protocol) 和插件化 Agent 框架的成熟，AI Agent 的能力已经从“查资料”扩展到“做事”——修改配置文件、触发 CI/CD、操作数据库、调用支付接口。在 OpenClaw 这类平台上，我们可以通过挂载几十个 MCP Server 让模型直接操控真实系统，但同时也会面临一个尖锐的问题：**什么时候该让 Agent 自己干，什么时候必须停下来问人类？**

没有边界设计的 Agent 要么形同虚设（动辄请求确认），要么成为安全隐患（悄无声息地删资源）。这篇文章不讨论抽象的“对齐伦理”，而是聚焦在工程层面，给出可落地的权限分级方案和踩坑记录。

## 问题拆解：安全与效率的平衡点在哪？

理想中，我们希望 Agent 能快速完成无风险的机械操作，而对于可能造成严重后果的动作，则强制插入人工确认。现实中，有几个典型的困境：

- **粒度难把握**：读操作可以全自动，但“读取全部客户数据”算低风险吗？
- **上下文丢失**：确认请求如果太慢，用户注意力早已移开，回来随手点“允许”，确认形同虚设。
- **连锁风险**：单个操作看似安全，但一连串低风险动作组合后可能造成生产事故（例如先删旧文件再写新文件，中间中断）。
- **多环境差异**：在测试环境可以随便造，但在生产环境必须谨慎。同一个工具在不同环境下的风险等级完全不同。

因此，我们需要一套**可配置、可感知上下文、支持组合判断**的权限边界机制，而不能简单地在工具层写死一个 boolean。

## 做法：三级权限模型与确认流程

以下方案适用于任何基于工具调用（function calling / MCP）的 Agent 框架，以 OpenClaw 中的实践为例。

### 1. 在工具定义中标注风险等级

在 MCP 工具的描述或自定义元数据中增加 `risk` 字段，建议使用三级：

- **`LOW`**：纯查询、无副作用、不泄露敏感信息（如 `get_current_time`, `search_docs`）
- **`MEDIUM`**：修改非关键状态、生成文件、触发可回滚的学习任务（如 `update_issue_label`, `create_tmp_file`）
- **`HIGH`**：修改生产配置、删除资源、调用账单接口、发送批量消息（如 `delete_user`, `deploy_prod`）

示例 MCP 工具声明（简化）：

```json
{
  "name": "delete_k8s_pod",
  "description": "Delete a pod in a given namespace. Risk: HIGH - requires confirmation.",
  "inputSchema": { ... },
  "meta": {
    "risk": "HIGH",
    "requires_confirmation": true,
    "human_approval_timeout": 120
  }
}
```

### 2. Agent 主循环中插入“权限守卫”

Agent 在决定执行工具前，增加一个 Guard 环节。伪代码：

```python
def guard_tool_call(tool_name, params, risk_level):
    if risk_level == "LOW":
        return True  # 直接放行
    if risk_level == "MEDIUM" and session.is_first_in_batch(tool_name):
        return ask_user("中等风险操作: 执行吗？", timeout=30)
    if risk_level == "HIGH":
        return ask_user("高风险操作: 请确认。附上下文详情。", timeout=120)
```

### 3. 引入“会话信任期”减少疲劳

对于 `MEDIUM` 操作，可以采用**短时缓存确认**：如果用户在过去 5 分钟内已批准过同一类操作，且参数模式相似（如相同仓库、相同 namespace），则自动放行。这样既不会每个 PR 加标签都弹窗，也避免了完全绕过确认。

### 4. 模拟模式与回滚预留

高风险操作可以先提供“模拟执行” `--dry-run` 选项，Agent 在真正执行前必须调用一次 `dry-run` 并将输出展示在确认页面。同时，对不可逆操作强制生成回滚计划（如备份原始配置），即便人类最终批准，也留有退路。

## 踩坑实录：实际落地时遇到的真实问题

**坑 1：工具标注不统一，后期失控**

初期团队每个人对风险的判断不同，有人说“修改域名解析是 MEDIUM”，有人说是“HIGH”。后来我们制定了明确的分类矩阵：以“影响面”和“可逆性”二维打分，0-2 为 LOW，3-4 为 MEDIUM，5 以上为 HIGH。每个新工具必须经过评审打入 meta。

**坑 2：确认弹窗被用户“肌肉记忆”点掉**

某 Agent 在帮用户批量重命名文件时，连续弹出 15 个确认框，用户不耐烦地快速点“允许”，结果第 7 个本应是 HIGH 风险（删除原文件）也一并通过了。改进方法是：对批量操作进行**聚合提示**，一次列出全部待执行项，并高亮其中风险差异。同时，在任何连续确认超过 3 次后，强制增加一个“全选信任”或“全选拒绝”的二次确认，打破机械点击。

**坑 3：异步场景下的确认超时导致任务悬挂**

Agent 在深夜触发了一个 MEDIUM 操作，等待人类确认，但用户已离线。默认超时机制直接返回“拒绝”，导致整个 workflow 中断丢失。最终我们将超时后的行为改为：挂起任务并发送异步通知（如 Slack），用户可在合理时间内回复继续。超时超过 24 小时则自动回滚相关临时资源。

**坑 4：忽略组合操作的累进风险**

每个独立工具都是 LOW 或 MEDIUM，但 Agent 编排了这样一串：读敏感表 → 写入临时文件 → 用临时文件调用内部 API → 删除临时文件。单独看每一步似乎无害，但整体完成了数据外传。我们后续在 Guard 层增加了**序列风险检测**：当短时间内涉及多个不同域的资源访问时，即使每个工具单独为 LOW，也会升级为 MEDIUM 并要求确认。

## 可复用的工程化建议

1. **风险矩阵标准化**：定义“影响面（scope）×可逆性（reversibility）”表格，避免主观争论。
2. **在工具注册时强制声明风险**：MCP Server 的 manifest 中缺乏标准风险字段，可以扩展 `meta` 来承载，并让 Agent 框架在启动时校验。
3. **多级确认策略**：LOW 自动；MEDIUM 会话缓存+聚合提示；HIGH 强制人类确认+模拟预览+回滚方案。
4. **可编程的确认接口**：不仅支持同步弹窗，还支持异步通知、双人审批（针对 production HIGH），以及基于时间/角色的动态策略。
5. **审计日志不可少**：每次 Agent 执行中/高风险操作，即便自动放行，也要记录完整的上下文、用户信任期状态、决策原因，方便事后复盘。
6. **测试环境的权限“降级”设计**：在 staging 环境里，即使是 HIGH 也可配置为自动放行，但必须发送监控告警，确保不被滥用到生产。

## 总结

AI Agent 的权限边界不是二元开关，而是一个需要结合风险等级、用户上下文、操作组合和疲劳度控制的**动态决策系统**。在 OpenClaw 这类插件化 Agent 平台上，我们可以通过简单的风险标注 + Guard 机制，快速搭起一套既安全又不牺牲效率的权限控制层。关键点在于：**不要迷信自动决策，也别让人类成为瓶颈；让确认有意义，让自动有底线。**

尽早把权限设计纳入你的 Agent 架构，它会是你未来规模化落地时最值得投入的工程基础设施之一。
