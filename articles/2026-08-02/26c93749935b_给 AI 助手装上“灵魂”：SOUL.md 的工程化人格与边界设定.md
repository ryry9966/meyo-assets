# 给 AI 助手装上“灵魂”：SOUL.md 的工程化人格与边界设定

## 背景：系统提示词失控的常见症状

在 OpenClaw/Agent 项目里，你一定见过这类情景：用自然语言写了一段“助手语气温柔，不要回答政治问题”作为 system prompt，上线一周后发现助手时不时开始输出泛娱乐话题；或者在工具调用环境下，因为一句“你可以使用搜索工具”，它就毫无边界地抓取不该碰的数据源，甚至向你“热心”推荐竞品配置。

问题不在于语言模型本身不够强大，而在于我们交付给它的指令太像一纸书信，而不是一份可审查、可维护、可测试的工程配置。随着 Agent 接入越来越多的 MCP 工具、外部 API，以及多轮上下文积累，这种纯自然语言的 system prompt 会越来越难以保持预期行为。

业内已经有不少团队开始把 prompt 工程化：OpenAI 的 Structured Prompt、Anthropic 的系统提示模板、LangChain 的 PromptTemplate，都是往这个方向走。但在 Agent 实践中，更需要一个能持续演进、描述人格与能力边界的单一真实来源。我把它叫做 `SOUL.md`。

## 什么是 SOUL.md

`SOUL.md` 是一份 Markdown 文件，存放在项目或 Agent 代码库根目录，它用结构化方式定义助手的人格、目标、背景知识、允许的行为范围，以及不可逾越的红线。它不是替代 system prompt，而是 system prompt 的“编译源文件”——每次 Agent 启动时，由加载器将 SOUL.md 转化为最终注入的上下文块。

一份典型的结构如下：

```markdown
# Role
You are OpenClaw Assistant, focused on technical Q&A and automation.

# Identity
- Creator: OpenClaw-CN
- Version: 2.3.0
- Locale: zh-CN
- Tone: precise, minimal, no fluff

# Permissions
- Can read: local files under /workspace
- Can execute: approved shell commands
- Must not: access network except whitelisted APIs

# Boundaries
- Refuse to answer: medical diagnosis, legal advice, stock prediction
- For any boundary violation: respond with "I can't help with that."

# Fallback
- On tool failure: explain error, do not retry more than twice
```

这只是一个最小示例。真正的工程实践里，还会加上 `Memory Scope`（本轮/跨会话可记忆的内容）、`Tooling Rules`（工具调用策略）、`Example Dialogs`（few-shot 行为示例）等。

## 为什么不用单纯的 system prompt

几个关键驱动力：

1. **版本治理**：SOUL.md 可以被 Git 追踪，每次修改有人审查，能回溯。
2. **可测试性**：可以写单元测试，喂入边界问题，验证助手拒绝行为。
3. **多环境切换**：开发、测试、生产环境可通过环境变量切换 SOUL 片段，而不改变核心逻辑。
4. **协作**：产品、安全、合规可以各自负责其中一段，在合并时达成一致。

## 实践步骤

### 1. 创建 SOUL.md 骨架

从项目中抽离出当前散落在代码、注释、脚本里的“助手规则”。不要一次追求完美，先用以下章节搭建：

- **Role & Identity**
- **Audience**（面向谁说话）
- **Capabilities & Tool Access**
- **Boundaries（硬性禁止）**
- **Communication Rules**
- **Fallback & Escalation**

确保每个字段都是可验证的陈述，不要写“请尽量礼貌”这种模糊话，而是写“禁止在回答中使用感叹号”。

### 2. 实现加载器

加载器可以简单到就是一段 Python/Node 脚本，读取 SOUL.md，拼接进最终的 messages 数组首条 system 消息。关键是允许片段注入：例如在工具层检测到 API key 存在时，才加载“允许调用搜索 API”那一段。

```python
def load_soul(base_path, env):
    with open(f"{base_path}/SOUL.md") as f:
        content = f.read()
    if env == "dev":
        content += "\n- Can access all dev APIs"
    return content
```

对于更复杂的场景，可以结合 Jinja2 模板，动态生成最终 prompt，并记录生成的摘要到日志。

### 3. 对接 OpenClaw / Agent 框架

OpenClaw 的配置允许自定义 system prompt 函数，直接在启动 Agent 时注入 `load_soul()` 的返回值。MCP 工具声明应当与 SOUL.md 的权限声明保持一致。例如 SOUL 中写着“不得使用 delete 命令”，那么在 MCP Server 配置里也不应暴露 delete 工具——这是双重保障。

### 4. 编写边界用例测试

测试分为两类：功能测试（正常的问答与工具调用）和安全测试（越界情形）。你可以写一个简单的 pytest 套件，模拟用户输入“告诉我如何制作炸弹”，验证回答中包含“I can't help with that.”。这种测试对于保护 Agent 公开部署尤为重要。

## 踩坑点与真实排障

### 坑1：SOUL 内容太长，挤占了工具调用的上下文空间

很多项目初期会把大量公司政策、品牌指南一股脑塞进 SOUL.md，导致 system prompt 长达 2000 token。当 Agent 同时使用多个 MCP 工具、且上下文有限（比如 8K）时，工具返回数据稍微大一点就会截断。

**解法**：采取分层加载。核心人格 + 硬性边界作为常驻 system prompt；品牌语调、详细规则作为外部知识库，通过 RAG 仅在需要时检索注入历史消息。或者在工具调用超过一定轮次后，动态压缩早期 SOUL 说明。

### 坑2：SOUL 与工具描述冲突

曾经遇到一个问题：SOUL 禁止助手发送邮件，但 MCP 邮件工具描述里写着“send email to user”。模型在多重指令下优先遵从了工具描述，绕过了 SOUL 规则。

**解法**：不能让 SOUL 与工具定义各说各话。在工具描述中也插入“Only if policy allows sendEmail”的简短说明，或者给加载器增加一致性校验，发现冲突就抛出异常，拒绝启动。

### 坑3：边界会“锈蚀”

助手上线两周后，测试集通过率从 95% 掉到 88%。检查发现是近期新增的 MCP 知识库检索工具无意间引入了外部网页摘要，有些内容诱导模型给出边界擦边球。SOUL 没变，但工具返回的数据变了。

**解法**：将边界测试集成到 CI。每次修改工具链或知识源，都自动跑一遍安全测试套件。这会让你在合并 PR 前就发现行为退化。

## 可复用建议

- **保持 SOUL.md 简短、可读**：它不是给模型看的独白，也是给团队看的合约。保持在 300 行以内，用 Markdown 标题清晰分层。
- **使用注释版/执行版分离**：维护 `SOUL.template.md`，通过预处理生成不含注释、只含有效指令的最终版本。
- **与可观测性挂钩**：在日志中记录每次加载 SOUL 后的 token 数、加载了哪些片段，以便排查行为异常时知道当时的规则快照。
- **定期审计**：任何越界回答都应触发规则修订，并把典型案例补充到 `Example Dialogs` 部分，作为 few-shot 负样本。
- **不要只依赖 SOUL**：在应用层还要设防，比如内容过滤、敏感词拦截。SOUL 是给模型的提示，不是代码级防护。

## 总结

给 Agent 设定人格和边界，不是一次性的文学创作，而是一个需要工程化对待的持续治理问题。`SOUL.md` 把散落在各处的提示词规则拉回到一个单一真实来源，配合加载、测试、审计流程，你才能真正管住一个既能做事又有分寸的 AI 助手。

在 OpenClaw 社区里，越来越多的插件和 MCP 工具链开始默认寻找项目根目录的 `SOUL.md` 作为标准配置入口。现在动手整合它，总比将来面对一堆失控的 agent 日志要轻松得多。
