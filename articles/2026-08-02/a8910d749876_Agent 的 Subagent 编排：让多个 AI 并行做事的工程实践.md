## 背景：单 Agent 的能力边界
在 OpenClaw 社区中，我们常构建自主 Agent 来处理检索、开发、自动化运维等任务。单个 Agent 通过链式调用工具能解决不少问题，但在面对复杂项目时，它的局限性很明显：

- **上下文窗口拥挤**：所有中间结果、工具输出都塞进同一个上下文，越往后推理越慢，且容易丢失早期信息。
- **串行执行耗时**：多个独立子任务只能先后排队，总延迟累加。例如，“分析用户需求”与“检索相关文档”本来可以并行，串行却白白增加等待时间。
- **职责混杂导致幻觉**：一个 Prompt 既要负责规划，又要执行细节，极易出现目标偏移或忘记中间步骤。

于是，多人协作的思路被引入 Agent 设计：将一个“超级大脑”拆成多个专注的子 Agent（Subagent），让它们并行工作，最后汇总结果。这就是 Subagent 编排的核心动机。

## 问题：如何设计可落地的并行 Subagent 编排？
真实工程中，不像 demo 那么简单。需要回答几个具体问题：

- 如何划分子任务，才能让结果可机械合并？
- 如何在 OpenClaw 这类框架中启动多个子 Agent 并管理生命周期？
- 如何处理并发 API 限流、结果冲突和异常重试？
- 合并阶段如何保证最终输出的质量？

下文就给出一个经过验证的实践方案。

## 做法：以“技术文档自动评审”为场景
假设我们要构建一个 Agent，自动评审一份需求文档。可以拆成三个并行子任务：
1. **安全合规检查**：检查是否涉及敏感操作，是否符合安全规范。
2. **技术可行性分析**：评估技术方案是否可行，依赖是否合理。
3. **术语一致性审查**：检查文档内部术语是否前后统一，与外规是否冲突。

在 OpenClaw 中，我们不再让一个 Agent 顺序执行三个工具，而是为每个子任务定义一个专门的 Subagent（各自有独立的系统提示和工具集）。主 Agent 负责拆分、分发、等待并合并结果。

### 步骤 1：定义 Subagent 协议
为每个 Subagent 定义清晰的输入输出 Schema。例如安全合规检查的输入为文档全文，输出必须是一个 JSON：
```json
{
  "risk_level": "low/medium/high",
  "issues": ["具体问题1", "具体问题2"],
  "suggestions": ["改进建议"]
}
```
其他两个 Subagent 也有类似结构，保证合并时无需二次猜测。

### 步骤 2：分发与并行执行
在主 Agent 的策略中，使用异步调用同时启动三个 Subagent。以 Python 伪代码为例（OpenClaw 可基于类似机制）：
```python
import asyncio

async def review_document(doc):
    sub_tasks = {
        "safety": safety_subagent.run(doc),
        "feasibility": feasibility_subagent.run(doc),
        "terminology": terminology_subagent.run(doc),
    }
    results = await asyncio.gather(*sub_tasks.values(), return_exceptions=True)
    return dict(zip(sub_tasks.keys(), results))
```
通过 `asyncio.gather` 真正并行执行，避免串行等待。`return_exceptions=True` 确保个别 Subagent 失败不会阻塞整体。

### 步骤 3：结果合并与二次决策
主 Agent 收集到三个结构化结果后，执行合并函数。这一步也可以用 LLM 进行摘要，但更推荐先用规则合并，降低不确定性。例如：
- 取最高的风险等级作为整体风险。
- 将所有问题去重、归类后生成统一列表。
- 若三个 Subagent 结论冲突（如安全认为可行，但技术可行性分析认为不可行），则触发一次“复审”调用，将冲突点发给一个更中立的判断 Agent。

### 步骤 4：最终输出
主 Agent 将合并结果格式化为 Markdown 报告，附上各子模块的原始结论（可折叠），保留可追溯性。

## 踩坑点
1. **上下文复制导致 token 爆炸**  
   若每个 Subagent 都接收完整的原始文档，且文档很长，并发三个会导致 token 消耗乘 3，极易触发限流。解决方法是：对原始文档做一次“预摘要”，仅将摘要传给子 Agent；或者让子 Agent 按需通过工具检索原始文档的特定部分，而不是一次性读取全文。

2. **结果重叠与冲突**  
   前例中，安全检查和合规检查可能给出相似的冗余问题。合并阶段必须做聚类去重，否则报告冗长且重复。可对每个 issue 做向量嵌入，基于相似度合并。

3. **并发 API 限流**  
   同时启动多个 LLM 请求可能超过服务商速率限制。应在主 Agent 中加入令牌桶或信号量控制，例如限制最大并发数为 3，并将超额请求排队。

4. **子 Agent 挂起无响应**  
   网络波动或推理超时会导致某个 Subagent 永久挂起。必须为每个异步任务设置超时（如 120 秒），超时后捕获异常，并用降级结果（如“此检查因执行错误未能完成”）填充，保证主流程不被卡死。

5. **结果格式不遵守 Schema**  
   即使 Prompt 中明确要求 JSON，LLM 有时还是会输出多余文字或错误格式。合并前要对每个结果做结构校验与修复，必要时重试。

## 可复用建议
- **子任务粒度的黄金法则**：每个 Subagent 应“独立可验证”，即其输出可以被单独评审是否正确，不需要依赖其他 Subagent 的中间状态。
- **使用轻量协议进行通信**：所有 Subagent 的输入输出强制走 JSON 或 YAML，拒绝自由文本格式，降低解析成本。
- **构建合并算子库**：把常见的合并模式（投票、取最高优先级、去重摘要）抽象为可配置的算子，避免每次都手写合并逻辑。
- **监控每一条 Pipeline**：记录每个 Subagent 的执行耗时、成功/失败率、输出 token 数，帮助后续优化子任务拆分和模型选择。
- **考虑最终输出的人工确认**：在高风险场景中，不要完全自动采纳合并结果，可加入“人工确认节点”，由用户审查后再执行后续动作。

## 总结
Subagent 编排并不是简单地多开几个 LLM 调用，而是一种工程上的“分治”策略。在 OpenClaw 生态中，这种模式非常适合与 MCP 工具结合，将复杂工作流拆成多个可观测、可插拔的并行单元。关键收益是：**显著降低端到端延迟**，**提高单一 Agent 的专注度和可靠性**，并且让团队可以并行开发和迭代不同的子 Agent。

代价是增加了编排层的复杂度。但只要控制好协议、异常处理和合并规则，这套模式就能在真实项目中稳定运行。如果你正在构建需要多步骤复杂推理的 Agent，不妨试试从“串行超脑”转向“并行专家团”。
