## 背景：重复执行是常态，不是异常

在 OpenClaw 这类 Agent 自动化平台中，任务被触发的方式远比想象中复杂：

- MCP 工具调用可能因网络抖动而重试
- 定时触发器与手动触发可能同时命中同一条数据
- 插件链路上的多个步骤，其中一个失败后，上游可能已经完成部分副作用
- 事件驱动的 webhook 常常发送多次（没有 exactly-once 语义）

如果你设计的自动化脚本假设“一次触发一次执行”，那在实际环境中迟早会出现重复创建资源、重复发送通知、重复扣减积分之类的问题。

让重复执行不产生副作用，就是**幂等性设计**要解决的问题。

## 问题：没有幂等性的自动化长什么样

以一个典型的 OpenClaw 工作流为例：监听 GitHub issue，自动分配标签、指派负责人、发送 Slack 通知。

如果没有幂等性：

- webhook 重复投递 → 同一条 issue 被多次打标签（API 可能报错，但 Notion 类的系统会直接追加重复标签）
- 重试机制 → Slack 通知连发三次
- 定时扫描未处理 issue 时，因状态未及时更新，同一条又被抓取处理

结果不仅是脏数据，还可能触发风控、浪费配额、骚扰同事。

## 核心做法：让操作“可安全重放”

### 1. 引入幂等键（Idempotency Key）

在每次任务执行前，基于业务上下文生成一个唯一标识，比如：
- GitHub webhook 的 `X-GitHub-Delivery` + event type
- 订单号 + 操作类型
- 实体 ID + 版本号

将这个 key 与操作绑定，执行前先检查是否已处理过。可以用一张轻量的数据库表或 Redis 记录：

```sql
CREATE TABLE idempotency_records (
  idempotency_key VARCHAR(255) PRIMARY KEY,
  state VARCHAR(50),        -- 'processing', 'completed'
  result TEXT,              -- 可选，记录执行结果用于返回
  created_at TIMESTAMP DEFAULT NOW()
);
```

首次执行插入 key 并标记为 `processing`，执行完改为 `completed`。重复请求发现 key 已存在且为 `completed`，直接跳过或返回缓存结果。

### 2. 利用数据库约束做“被动幂等”

对于创建类操作，将幂等键设计为唯一约束，依赖 `INSERT ... ON CONFLICT DO NOTHING` 或 `INSERT IGNORE`。比先去查一次再决定插入更安全——避免了查和插之间的竞态窗口。

```sql
INSERT INTO task_logs (task_id, idempotency_key, status)
VALUES ('task-123', 'evt_abc123', 'processing')
ON CONFLICT (idempotency_key) DO NOTHING;
```

### 3. 状态机前置检查

如果操作对象有明确的状态流转（如“待处理 → 处理中 → 已完成”），在执行任何副作用前先检查当前状态：

```python
if current_state != "pending":
    return  # 已经处理过或不需要处理
```

这层检查结合数据库行锁（`SELECT ... FOR UPDATE`）可以有效防止并发重复执行。

### 4. 分离不可逆副作用

有时最头疼的不是数据重复，而是对外部系统的调用——发短信、发邮件、推送通知。对于这类操作，建议：

- 先做状态检查与幂等键登记，再执行外部调用。
- 为通知类动作设置防重窗口（如 5 分钟内同一用户同一事件只发送一次），可以通过 Redis `SETNX` 简单实现。
- 对于必须保证到达的通知，使用延迟队列 + 确认机制，而不是在工作流步骤里直接触发。

## 踩坑点：看似简单，细节容易错

### 坑1：幂等键过期时间

很多团队把幂等键存 Redis 并设 24 小时过期。如果某个合法操作在 24 小时后因用户手动再次触发，系统会当成新操作再执行一次。需要明确业务窗口：对订单支付类事件，幂等键可能需要永久保存或至少覆盖退款周期。

### 坑2：幂等键生成时机

幂等键必须由**上游不可变参数**生成，不能依赖随机数或当前时间戳。如果在 handler 内部 `uuid4()` 生成，那每次重试都是新 key，幂等退化为无保护。

### 坑3：并发下的“幽灵处理”

只在应用层加锁不够。当两个进程同时收到请求，同时查询“无记录”，会都执行副作用。数据库唯一键配合错误重试是更可靠的屏障。OpenClaw 分布式执行场景尤其需要注意，不能只依赖内存锁。

### 坑4：部分失败的回滚错觉

如果先执行了外部调用，再更新幂等记录，结果更新失败，下一次重试会再次执行外部调用。应该用事务或先占位符再执行：先插 `processing` 状态，再执行业务，最后改为 `completed`。外部调用若有成本，增加超时卡在 `processing` 状态的恢复策略（定时清理或自动重试）。

## 可复用建议

- **统一幂等中间件**：将幂等键的解析、登记、冲突处理抽象为一个 OpenClaw 插件或 MCP 工具，所有自动化节点共用。
- **让幂等键标准化**：在所有 MCP 工具的参数中，增加可选的 `idempotency_key` 字段。即使工具本身不完全幂等，调用方能传入控制。
- **默认开启重试保护**：在 OpenClaw 的工作流设置中，对每个 action 节点提供“重试前检查幂等键”的开关，引导开发者习惯使用。
- **监控重复执行**：无论是否被拦截，在日志中记录“潜在重复请求已跳过”事件，方便事后发现上游重复投递问题。

## 总结

幂等性不是“加个防重表”就能解决的问题，它需要从任务触发、状态检查、外部调用到落库提交的整个链路去设计。核心原理很简单：**在执行任何有副作用的动作之前，先安全地确认这个动作是否已经完成过。**

在 OpenClaw 这类以 MCP + 插件为主的自动化环境里，重复触发是系统健壮性的副产品，而不是设计缺陷。如果你把幂等性当作第一公民去处理，未来扩展定时任务、事件回放、失败重试时，系统就不会积累隐形的数据债务。
