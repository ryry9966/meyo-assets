## 背景

用 OpenClaw 搭个人 Agent 跑自动化任务时，最常遇到的痛点不是工具不够，而是它“记不住事”。比如我习惯用 pnpm 管理依赖，测试一律用 vitest，代码注释用英文，可每次新会话都要重复一遍。Agent 默认无状态，依赖上下文窗口，一旦会话重置，之前的交互细节全部丢失。

想让助手真正“懂你”，必须在 Agent 架构里加一层可控的记忆系统。这层系统需要处理记忆的提取、存储、检索和更新，而且不能做得太重，否则偏离了自动化的本意。下面给出一个工程上可落地的轻量方案，面向 OpenClaw + MCP 工具链，经实际踩坑后提炼而成。

## 问题拆解

记忆系统要解决的核心问题：

1. **记忆如何表示**：用户偏好往往是键值或结构化 JSON，比如代码风格、工具选择、命名习惯等。
2. **何时提取**：不能每次都问用户“要记住吗”，最好在对话结束或特定触发条件下由 Agent 自己提取。
3. **存在哪里**：要跨会话持久化，存取速度快，不引入过重依赖。
4. **怎么用**：在新会话里注入记忆，且不占用过多 token。
5. **更新与冲突**：偏好会变，旧的该覆盖还是保留历史？重复提取怎么去重？

## 做法与步骤

### 1. 定义偏好 Schema

先用一个 JSON 文件承载所有偏好，存放在用户主目录下 `~/.agent/prefs.json`。数据模型按域划分，加 `last_updated` 时间戳：

```json
{
  "code_style": {
    "language": "TypeScript",
    "indent": 2,
    "use_semicolons": true,
    "last_updated": "2025-03-15T10:00:00Z"
  },
  "tool_prefs": {
    "package_manager": "pnpm",
    "test_runner": "vitest",
    "last_updated": "2025-03-18T14:00:00Z"
  }
}
```

保持扁平，避免嵌套过深。

### 2. 记忆提取

在 OpenClaw 的 Agent 执行流程中，增加一个后处理步骤：当用户与 Agent 完成一轮有意义的交互（比如生成完一个项目结构），触发记忆提取。这一步通过 LLM 分析当前对话，用严格的 JSON Schema 约束输出，只提取本次暴露的新偏好或变更。

提示词模板要点：
- 明确只提取用户**明确表达**的偏好，不臆测。
- 要求输出与当前偏好合并后的完整 JSON，或仅输出变更项（我用变更项，然后程序合并）。
- 给出少量样本（few-shot），降低幻觉。

然后把提取结果与现有 `prefs.json` 进行深度合并，更新时间戳，写回文件。

如果不想依赖额外 LLM 调用，也可以设计成用户主动说“记住我用 pnpm”这样的显式指令，由 MCP 工具直接处理。但从实际体验看，被动提取更自然，而准确性依赖提示词质量。

### 3. 记忆存储与检索

存储就是本地文件，无需数据库。同时封装为一个 MCP 工具，提供 `get_preferences` 和 `update_preferences` 两个接口。这样任何通过 MCP 连接的 Agent 都能读写记忆，避免耦合到 OpenClaw 内部。

在新会话启动时，Agent 会先调用 `get_preferences` 获取完整偏好 JSON，将其转化为自然语言摘要，注入到系统提示词开头：

```
Current user preferences known from past interactions:
- Code language: TypeScript, indent 2 spaces, with semicolons
- Package manager: pnpm, test runner: vitest
...
```

这样后续对话中，模型就能自然遵守这些偏好，而无需重复说明。

### 4. 更新策略与去重

对于同一个偏好项，后提取的值直接覆盖旧值，更新 `last_updated`。用时间戳即可保证最新有效。若需要保留历史版本，可以在文件里加一个 `history` 数组，但初期不必要。

如果偏好项过多，可以按 `last_updated` 淘汰长期未更新的项，或设置一个最大条目数（比如 20 条），避免注入的提示词变长。

## 踩坑点

**提取不准确**  
LLM 有时会把一次性的项目路径或临时变量当成偏好记下来。解决方法是在提取提示里强调“仅提取长期稳定偏好”，并要求输出理由字段，便于调试。

**过度膨胀**  
用户随口说“今天试试 vitest”不应立即覆盖长期偏好。可以加一个阈值：同一偏好必须出现至少两次才记入，或设计为“暂存区”，下次出现时再确认。

**并发写入与文件锁**  
当多个 Agent 进程同时更新 `prefs.json` 时可能出现数据错乱。建议用文件锁（如 `flock`）或直接用 SQLite 的单写多读特性。SQLite 也不重，文件级别存储，可作为下一步方案。

**隐私与泄露**  
偏好文件可能包含内部项目名或路径，要确保文件权限 600。如果记忆需要跨机器同步，应端到端加密后再传输。

**注入 token 膨胀**  
如果偏好太多，系统提示词会占用过多上下文。可只注入本次任务最相关的类别，比如通过简单关键词匹配（当前对话提了“测试”，就注入 test_runner 偏好），不需要语义搜索就能省 token。

## 可复用建议

- 把记忆模块做成独立 MCP 工具，配置即可接入任何 Agent，不用改业务代码。
- 提取提示词尽量参数化，方便适配不同领域（如写作风格、运维习惯等）。
- 不要过早引入向量数据库，个人助手偏好数据量通常不到 100 条，JSON 文件足够，维护成本极低。
- 每次更新偏好后，可以让 Agent 用一句话向用户确认“已记住你喜欢…”，用户无感知时也不用打扰，提升可信度。

## 总结

通过“JSON 文件 + LLM 提取 + MCP 工具化”这组轻量组合，我们让 Agent 从每一次 “失忆” 的状态进化到具备跨会话记忆能力。实现成本低，依赖少，且完全在用户自己控制下。Agent 记住的偏好越多，重复说明越少，自动化才能真正体贴。这套方案已经在日常的个人项目搭建、文档生成等场景中稳定运行，后续计划加入简单的遗忘机制和多层级注入策略，使记忆系统更耐久用。
