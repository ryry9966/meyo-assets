# 构建幂等的自动化任务：让重复执行不再危险

**背景：自动化世界里，没有“只执行一次”的保证**

在 OpenClaw、Agent 编排、MCP 工具链或任何插件化自动任务中，触发器随时可能重复：消息队列的重投、工作流的重试、定时任务的错过补偿、用户双击按钮、甚至 Agent 自主决策的“再确认一遍”。如果你写的任务不是幂等的，重复执行就会造成数据重复、状态错乱、重复计费、用户收到多条通知……这些问题一旦扩散，修复成本远高于预防。

幂等性（idempotency）是指同一个操作执行一次和执行多次，系统最终状态一致且副作用相同。在 HTTP 世界里，GET/PUT/DELETE 常被设计为幂等，但在业务自动任务中，我们需要自己实现这层防护。

---

## 问题：非幂等任务的典型翻车现场

假设你用 OpenClaw 创建了一个“订单支付成功”自动化流程，Agent 监听到支付事件后执行两步：更新订单状态、发放虚拟权益。由于网络波动，回调消息被 MQ 投递了两次。如果没有幂等控制，权益可能发放两次，订单状态却还是“已支付”——后续人工对账才发现损失。

更隐蔽的是 Agent 链路中的工具调用：某个 MCP 工具向第三方 API 提交资源创建请求，第一次因超时未拿到响应，Agent 重试，结果创建了两个相同资源。外部 API 可能支持幂等键，但你没传；或者你传了，键却每次随机生成——这跟没传一样。

---

## 做法：四层幂等防线，从轻到重

### 1. 定义并传递幂等键（Idempotency Key）

每个可能产生副作用的操作，都应由调用方生成一个业务上有识别度的幂等键，例如：
```
订单号 + 操作类型 + 业务版本
order_12345 + capture_payment + v1
```
在 OpenClaw 插件中，可以从事件上下文里提取这些字段组合成键，而不是用 `uuid4()` 随机生成。相同的业务意图必须产生相同的键。

### 2. 执行前检查 + 原子写入

不要“先查后写”——在并发下必然失效。推荐两种模式：

- **数据库唯一约束**：为幂等键建唯一索引，插入执行记录时使用 `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` 或 `ON DUPLICATE KEY UPDATE`。如果冲突，说明已处理，直接返回已有结果。
- **状态前置条件**：在更新操作中使用条件语句，例如：
  ```sql
  UPDATE tasks SET status='processing' WHERE id=? AND status='pending'
  ```
  如果影响行数为 0，说明状态已变更，放弃本次执行。

对于无持久层的临时任务，可以用 Redis 的 `SETNX` 作为轻量占位，但要考虑 TTL 和宕机恢复。

### 3. 外部服务调用携带幂等键

调用第三方 API 时，如果对方提供 `Idempotency-Key` 头部或类似字段，务必使用我们生成的幂等键透传。没有该机制的服务，则需先查询“是否已存在相同资源”，例如按唯一业务标识（如 `external_ref`）查一次，再做决定。可以在插件中封装统一的 `call_with_idempotency()` 工具函数。

### 4. 响应缓存与结果复现

幂等不只是防重复写，还包括重复读到的结果一致。当重复请求到达时，理想做法是返回首次执行的成功/失败结果，而不是再次执行。可以在执行成功后，将幂等键与响应对应存储，后续相同键直接返回缓存。这在 Agent 重试时尤其有用——它拿到的不是新执行的结果，而是“上次已经得到的结果”，避免状态判断偏差。

## 踩坑点：工程细节里的魔鬼

1. **幂等键的粒度与时效**  
   键太粗（只用订单号）会阻止合理重复操作，比如“支付”和“退款”不能共享同一个键。键太细（精确到毫秒级时间戳）又无法匹配重复请求。时效上，如果你的任务能人为触发重跑历史数据，幂等键可能需要包含业务日期，否则历史任务会被已有记录拦截。

2. **并发写入时的冲突处理**  
   数据库唯一约束冲突时，不要简单报错。应捕获异常，然后查询已有记录并返回结果。对于“处理中”的记录，可以选用自旋等待或快速失败，但避免无限循环。

3. **分布式一致性问题**  
   如果幂等检查和业务操作不在同一个数据库事务里，可能检查通过后业务操作失败，而下次重试时检查又显示已存在（因为没有清理机制）。解决办法是让任务状态机覆盖这三种状态：`pending -> processing -> done/failed`，并且对 `processing` 超时的任务提供恢复或重试入口。

4. **读操作的“幂等”错觉**  
   查询类操作天然幂等，但有些读操作会附带副作用，比如生成一次临时访问令牌、递增计数器。要明确区分哪些是纯读，哪些应加幂等控制。

---

## 可复用建议

- **封装幂等中间件**：在 OpenClaw 的 Action 或 MCP 工具调用层加一层 decorator，接收 `idempotency_key` 生成函数和存储后端，自动化上面四层逻辑。
- **统一日志与追踪**：所有任务日志都应包含幂等键，方便排障时按“同一操作”聚合查看重复执行的原因。
- **测试要真模拟重复**：编写集成测试时，用相同参数并发调用多次，验证最终状态和副作用数量。
- **默认开启，按需配置**：为所有写操作插件提供默认的幂等键策略（基于事件关键字段），只在特殊场景下允许关闭。

---

## 总结

自动化任务的幂等性不是锦上添花，而是一开始就该焊进执行骨架里的防呆设计。它的核心就是用**识别相同操作 + 保证一次效果**的组合，把“不确定的重试”变成“确定的结果”。当你下次在 Agent 流程里添加一个“发送通知”或“创建资源”的步骤时，先问自己：如果这一步被执行两次，系统能扛得住吗？
