# Prompt 工程实战：Cron 任务应该怎么写 instruction

## 背景

在 OpenClaw 这类 Agent 自动化平台里，“定时触发 + 执行任务指令”是高频需求。用户创建 Cron 触发器，希望在指定时间让 Agent 自动完成某项重复性工作：数据巡检、报表生成、消息监控、库存同步等等。

然而，一个尴尬的现状是：大多数 Cron 任务在运行几次后就悄悄“坏掉”，或输出结果完全不可用。根源往往不在触发器配置，而在**那条被视作理所当然的任务指令（instruction）上**。

很多朋友直接把和人聊天时的自然语言搬进指令框：“每天上午帮我检查邮件，然后把重要内容总结一下”。这句话对人来说足够，但对一个无人值守的 Agent 而言，既没有定义“重要”的判断标准，也没有说明输出到哪里、格式如何、失败时该怎么办。这类模糊指令就是定时任务失控的起点。

## 问题：定时指令的特殊性

Cron 任务与人机对话最大的区别在于：无人交互、需自闭环、长期运行。因此，一条合格的 Cron instruction 至少要回答五个问题：

1. **做什么**（具体可验证的行动）  
2. **如何判断完成**（输出什么、存在哪里）  
3. **异常如何处理**（重试、告警、降级）  
4. **如何保证确定性**（时间、格式、范围严格定义）  
5. **如何与历史状态打交道**（是否需要读写文件/数据库）

省略任何一个，都可能让一次自动化变成一次“静默失效”。

## 做法：从一段差指令到一段好指令

假设我们想让 Agent 每个工作日上午 9:30 检查公司某数据看板，并生成摘要发送到指定频道。下面演示如何一步步加固指令。

### 1. 明确任务范围和可验证的输出

❌ 坏例子：
> 早上检查数据，把异常数据找出来发给我。

✅ 改进第一步：
> 每周一至周五 09:30，访问 https://example.com/dashboard（只需读取，不要操作）。找到表格“当日流水”中“成功率”低于 98% 的行。  
> 将筛选后的行整理为 Markdown 表格，列依次为：时间、服务名、成功率、错误信息。  
> 把这份表格通过 send_message 工具发送到 Slack 频道 #ops-daily。

要点：**路径、指标阈值、输出格式、目标渠道全部写死**，不给 Agent 留“自行发挥”的空间。

### 2. 加入异常处理与重试逻辑

网络抖动、登录态失效、页面结构变动都会导致任务中断。如果没有容错策略，一次失败就可能让后续所有定时执行哑火。

继续补全：
> 如果页面加载失败或超时（超过 15 秒），记录失败原因到 /data/logs/dashboard-check.log，然后等待 3 分钟重试一次。仍失败则直接发送带有失败日志的告警消息到 #ops-alerts，并将本次任务标记为 failed。

这样的指令让任务具备了**自愈和可观测性**。实际应用中，还可以要求 Agent 在日志文件末尾追加时间戳和错误堆栈。

### 3. 指定数据结构的硬约束

Agent 生成的自然语言虽然漂亮，但用于多任务串联时很容易格式漂移。例如，下游脚本期望读 JSON，而某次 Agent 输出了纯文本。

因此，对于可结构化的输出，必须在 instruction 中要求精确格式：
> 将筛选结果保存为 /data/daily_report.json，结构为 `{"date": "YYYY-MM-DD", "alerts": [{"service": "...", "rate": 98.5, "error": "..."}]}`。若当日无异常，alerts 为空数组。

**硬约束**：明确 filename、路径、JSON schema。甚至可以附带一个范例对象，减少格式歧义。

### 4. 维护状态和上下文

普通对话中我们依赖记忆，但 Cron 任务每次启动通常是全新会话。如果任务需要跨天累计信息（例如“统计本周累计故障时间”），就必须通过文件或数据库传递状态。

> 每次执行时先读取 /data/weekly_metrics.json，更新当日数据后写回。读取时如发现文件不存在，则初始化为默认结构。严格锁定该文件路径，不做其他读写操作。

这样就避免了 Agent 因“想当然”而写了不同路径，或者误操作其他关键文件。

## 踩坑实录

在实际使用中，有几个很容易被忽视的坑：

- **时间描述不精确**：“每天一早” 这类指令，Agent 可能解读为 06:00、07:00 或其他时区，最终触发时间混乱。统统使用 Cron 表达式对应的固定时刻，并在 instruction 中用 24h 制明确时间。
- **权限和工具范围溢出**：如果 Agent 拥有过多工具权限，某次解析错误可能让它执行了危险操作（如删除文件）。建议给 Cron 专用 Agent 一个最小权限的独立角色，指令中也应显式限制“只读”“不要修改配置”。
- **未设置超时**：有些页面响应很慢，如果没有强行超时，任务会卡死，导致后续 Cron 堆积。instruction 中应明确“超过 XX 秒视为失败”。
- **忽略环境变量的生命周期**：Token 过期、API Key 轮换会让指令悄无声息地失效。可以在指令中加入“如果收到 401/403，立刻发送告警并终止”的判定逻辑。

## 可复用建议

我习惯为每个 Cron 任务维护一份**指令清单**，包含以下固定条目：

1. **触发时间与频次**（Cron 表达式 + 自然语言说明）
2. **任务目标**（一句话 + 可检验的成功标准）
3. **输入/数据源**（URL、文件路径、API 端点，含鉴权方式）
4. **处理逻辑**（分步描述，允许条件分支）
5. **输出规范**（格式、存放位置、推送渠道）
6. **异常策略**（重试间隔、降级操作、告警路径）
7. **权限与边界声明**（只读限制、工具白名单）

同时，所有 Cron instruction 都建议先以手动触发的方式跑通 3-5 次，观察输出和日志，确认稳定后再正式上线为定时任务。这种方式不依赖平台的特定功能，本质是一种工程化的习惯。

## 总结

写好 Cron 任务的 instruction，本质上是用**确定性的规范语言去消解 Agent 的随机性**。好的指令不会假设 Agent “懂我的意思”，而是把路径、阈值、格式、边界和处理意外的方式全部显式声明。对自动化实践者而言，这不是花哨的技巧，而是保证系统长期安静运行的基本功。

下次新建定时任务时，不妨对着那几条 checklist 再打磨一遍你的 instruction —— 那些凌晨三点不再响起的告警，就是最好的回报。
