# OpenClaw 的 cron vs heartbeat：两种定时任务怎么选才不翻车

在使用 OpenClaw 搭建 Agent 自动化流程时，你一定遇到过这样的需求：每隔一段时间触发一次任务，比如定时抓取数据、周期性检查状态、或按固定节奏推进长链路工作流。OpenClaw 内置的两种定时机制——**cron** 和 **heartbeat**——恰好分别对应这类场景，但新手很容易混用，导致任务堆积、资源浪费甚至逻辑错误。

本文将基于 OpenClaw 的插件与 MCP 实践中真实的工程踩坑经历，梳理二者的差异、适用场景、配置方法以及一套可复用的选型决策思路。

## 1. 背景：两种“定时”的本质不同

在 OpenClaw 的任务调度模型里，`cron` 和 `heartbeat` 虽然都按时间触发，但设计意图完全不同：

- **cron**：基于绝对时间的调度器，使用标准 cron 表达式，在**指定时刻**触发一次任务执行，常用于“每天 9 点生成报表”“每周五清理缓存”这类固定时间点动作。
- **heartbeat**：基于固定间隔的心跳触发器，会在**上一个执行完成之后**再等待一段固定时长，然后开启下一轮。它更像一个后台守护循环，适合持续监控、滑动窗口检查或需要避免任务堆叠的长耗时工作。

OpenClaw 中对这两种触发器的支持已经内化到 Agent 运行框架中：你可以在 Agent 配置里通过 `triggers` 字段声明，也可以在插件或 MCP 工具中通过调度装饰器直接使用。这意味着从简单的自动化脚本到复杂多 Agent 协作，都需要你对这两个机制有清晰认知。

## 2. 问题：选错触发器会带来什么麻烦？

在早期的一些 OpenClaw 实战项目中，经常能看到两类典型故障：

- **cron 任务执行超时导致实例堆积**：比如每分钟执行一次大模型调用 + 数据库写入的 cron 任务，当某次执行因为 token 限制或网络抖动运行了 80 秒，cron 依然会在第 60 秒时无情地启动一个新实例，最终 3 个实例并发抢资源，产生脏数据。
- **heartbeat 被当做精确时钟使用**：希望“每小时整点执行一次”却使用 heartbeat 间隔 3600 秒。假设任务开始时是 08:00:05，执行耗时 10 秒，那么下一次将在 09:00:15，逐步漂移，完全丢失整点语义。

根本原因在于：cron 是**时间触发**，不关心任务完成与否；heartbeat 是**执行间隔**，不保证绝对时间点。

## 3. 做法：正确配置两者的工程实践

### 3.1 cron 配置示例
在 OpenClaw 的 Agent 描述文件中，通过 `triggers.cron` 字段定义：

```yaml
triggers:
  - type: cron
    expression: "0 9 * * mon-fri"
    action: generate_morning_brief
```

如果你是插件开发者，可以利用 `@cron` 装饰器直接写在 Python 插件里：

```python
@cron('0 */2 * * *')
def sync_external_calendar(ctx):
    # 每两小时同步一次日历，适合快速完成的轻量任务
    ...
```

**关键点**：cron 任务必须设计成**幂等**且**执行时间远小于触发间隔**。如果任务本身执行时间不确定，应内置超时保护，并考虑在任务内加分布式锁避免并发。

### 3.2 heartbeat 配置示例
heartbeat 通常用于持续性“观察-行动”循环，例如在 Agent 中轮询 MCP 工具的状态变更。配置时使用 `triggers.heartbeat`：

```yaml
triggers:
  - type: heartbeat
    interval: 30s
    action: check_sensor_alerts
```

在插件中：

```python
@heartbeat(interval=15.0)
def watch_filesystem_changes(ctx):
    # 每轮执行完后等15秒再启动，适合可能跑很久的任务
    ...
```

**关键点**：heartbeat 间隔是从上一轮**结束后**开始计算的，天然避免了实例堆叠。如果要确保单实例运行，可以结合 OpenClaw 的任务队列能力设置 `max_concurrency: 1`。

## 4. 踩坑点：并发、漂移与优雅关闭

1. **cron 并发雪崩**：如前所述，如果 cron 间隔小于任务最长执行时间，一定要加并发控制。OpenClaw 提供了 `concurrency_limit` 参数，但更稳妥的做法是在业务层面自己实现“下次执行前检查上一次是否结束”。
2. **heartbeat 时钟漂移**：别拿 heartbeat 做对绝对时间敏感的事。如果需要整点触发，应该使用 cron，并在 heartbeat 任务里通过比较当前时间戳来实现“最近一分钟内是否已执行过”的逻辑。
3. **Agent 重启时的行为差异**：cron 在恢复后会根据时间差判断是否补跑（取决于 `missed_policy`），而 heartbeat 总是先等待一个完整间隔才开始第一轮，容易造成启动后有较长的“空窗期”。可通过配置 `initial_delay: 0` 让 heartbeat 立即执行首次任务。
4. **与 MCP 长连接结合的死锁**：heartbeat 循环内若持有 MCP 资源（如 WebSocket 连接）不放，而 agent 关闭时未正确释放，会导致资源泄漏。建议在 heartbeat 函数内使用 `ctx.call_tool` 这类每次重新连接的方式，或在插件卸载时主动清理。

## 5. 可复用建议：一张决策表搞定选型

在工程中，你可以按下面这个决策顺序快速判断：

- **步骤 1**：需要严格按“时钟时间”触发吗？（如每周一 8:00、每小时 00 分）  
  → 是 → 用 **cron**，并必须保证任务能在下一触发点前完成。  
  → 否 → 进入步骤 2。

- **步骤 2**：任务执行时间是否可能超过间隔？或者你需要一个永不停止的后台循环？  
  → 是 → 用 **heartbeat**。  
  → 否 → cron 和 heartbeat 都可以时，优先选 **cron**（可观测性更强）。

- **步骤 3**：任务是否需要处理“从上次执行到现在的增量数据”？  
  → 需要 → 用 **heartbeat** 配合持久化游标，每次处理完更新位点。  
  → 不需要 → cron 即可。

实际项目中，你会经常混合使用：用 cron 触发一个总体工作流，工作流内部用 heartbeat 实现分步骤的长时间轮询。例如每日 9 点 cron 启动数据清洗 Agent，清洗 Agent 内部用 30 秒 heartbeat 持续调用 MCP 工具检查数据管道状态，直到所有分片完成。

## 6. 总结

OpenClaw 的 cron 和 heartbeat 不是简单的“定时”替代，而是面向不同运行语义的抽象。记住两个核心原则：  
- **时间点语义 → cron**  
- **执行间隔语义 → heartbeat**  

结合合理的并发控制、幂等设计和优雅关闭，你就能在 Agent 自动化、MCP 插件开发和复杂工作流编排中彻底告别定时任务带来的诡异故障。

下次再遇到“我这个 Agent 为什么任务会重复跑”或者“心跳怎么越来越偏了”，回看这张决策表，你心里应该就有数了。
