# Prompt 工程实战：给 Cron 任务指令装上“刹车”和“导航”

---

## 背景：自动化尽头，自然语言开始接管调度

在 OpenClaw、Agent 和 MCP 插件的实践里，越来越多的定时任务不再由 Crontab 配置文件驱动，而是直接写在给模型的 instruction 里——一句“每 5 分钟跑一次”就希望 Agent 稳定地驱动外部工具。  
门槛变低了，但**问题从配置漂移变成了自然语言的不精确**。我们的任务不是教会模型理解 cron 表达式，而是设计出让人类和模型都不容易出错的指令结构。

---

## 问题：一条脆弱的 cron prompt 长什么样

几个真实、可复现的故障模式：

- **重复执行与堆积**：上一次任务还没结束，新周期又触发，导致同一条数据被处理多次，甚至触发 API 限流。
- **没有时区声明**：“每天早上 8 点”默认按 UTC 执行，实际在 UTC+8 的日志里永远看不到期望的结果。
- **失败静默**：外部 API 超时、权限过期，指令里没有要求模型判断退出码或检查返回值，Agent 以为自己执行成功。
- **永不终止**：while True 式的逻辑被“每天检查直到条件满足”触发，最终占用上下文窗口直至崩溃。

本质是：**我们只给了模型“做什么”，却没给“什么情况下不做”“做不完怎么办”和“出错时怎么通知”。**

---

## 做法 / 步骤：一条合格的 cron instruction 应该包含六个要素

在多次调试后，我固定了一个轻量模板，每一条定时任务指令都补满这六个字段。下文以 OpenClaw 中调用数据同步工具为例说明。

### 1. 触发时间：精确且带时区
不要写“每 5 分钟”，而是直接给出 cron 表达式并限定 IANA 时区：
```
schedule: "*/5 * * * *"
timezone: "Asia/Shanghai"
```
允许模型理解的是这个结构化字段，而不是自然语言描述。如果环境不支持 cron 字符串，就退而求其次用“每 300 秒从触发时刻起”，但**必须指定基准时间**。

### 2. 执行动作：签名式描述
动作部分应像函数调用一样明确，减少模型自由发挥空间：
```
action:
  tool: data_sync
  params:
    source: "prod_db"
    target: "warehouse"
    mode: "incremental"
```
“调用 data_sync 工具并传入以上参数”胜过“同步一下生产数据”。

### 3. 幂等窗口：防止并发叠加
这是最容易落地的排重机制。要求模型在每次执行前读取一个轻量状态，例如：
```
idempotency:
  key: "sync_prod_warehouse"
  ttl_seconds: 240
  check_before_run: true
```
如果上次任务在 240 秒内尚未完成，本次跳过并记录一条 “skipped due to active lock”。Key 可以用 Redis、文件锁，甚至模型自己的短期记忆，只要能**原子性地检查并设置**。

### 4. 失败处理：有限重试 + 退避 + 明确终点
别指望“重试几次”能自动生效，指令里一定要画边界：
```
retry:
  max_attempts: 3
  backoff: "exponential"   # 或 fixed:10s
  on_final_failure: "notify"
```
同时要求模型把每次重试的真实错误消息**原封不动**传给通知通道，不要让它“总结错误”。

### 5. 运行报告：日志与通知的契约
无论成功失败，模型都应返回一条结构化报告：
```
report:
  on_success: "log_only"
  on_failure: "send_alert"
  channel: "ops_warning"
```
在实际排障中，“没报警”比“报错”更可怕，所以这个字段必须存在，哪怕设为 silent。

### 6. 终止条件：显式的安全阀
给每项任务设定绝对超时和上下文长度限制：
```
termination:
  max_runtime_seconds: 600
  max_iterations: 100
```
某些循环型任务还需增加“连续 N 次相同失败则永久停止”的条件，防止资源被死循环吃光。

---

## 踩坑点：那些让你凌晨三点起床的问题

- **“上次没跑完就再触发”的保护缺失**是最常见的故障源。哪怕你写了 `check_before_run`，也要确认 Agent 环境在更新锁和执行业务逻辑之间不会出现竞态。在分布式 Agent 中，建议使用外部原子锁（如数据库唯一键或 Redis SETNX）。
- **时区问题不只在触发时间**。日志、报告和参数里的时间戳如果默认 UTC，会让按天切分的数据出现跨天偏移。明确所有时间输出格式为 `YYYY-MM-DD HH:mm:ss+08:00`。
- **重试风暴**容易发生在 API 短暂不可用时。如果 3 次重试都集中在 0.1 秒内，等于给上游加压。**指数退避不只是一个词，需要指定 base（如 2 秒）和 max（如 60 秒）**。
- **测试阶段不要直接连生产**。在指令里加一个 `dry_run: true` 标记，模型只做参数检查和状态报告，不真正执行写操作。这个字段在联调期是救命稻草。

---

## 可复用建议：把 cron 指令当成“声明式配置”

1. **用结构化 YAML/JSON 块代替散文**。自然语言做注释可以，但可解析的部分要独立成块，便于 Agent 解析和人类 review。
2. **建立一份 team 级别的指令模板库**，新任务从模板继承，只改参数，而不是从空白开始写 prompt。
3. **在监控侧校验**：哪怕 Agent 内部有锁，监控系统也要定时检查“同一时段是否存在两条以上同 key 任务”，双重保险。
4. **把“禁止的行为”写进全局约束**，例如：永远不允许模型修改自己的 schedule 字段，避免越权扩展开销。

---

## 总结

写出能稳定运行的 cron 任务指令，本质上是在**用 prompt 工程弥补调度框架的缺位**。我们不是要把模型训练成 crontab 解析器，而是通过可靠的结构、明确的退出策略和必要的安全阀，让自动化行为可预期、可诊断、可恢复。  
下一次当你准备写下“每 10 分钟同步一次数据”的时候，不妨问自己：如果它连续失败三次且没有人注意到，系统会在多久之后以什么方式坏掉？回答这个问题的过程，就是你补齐那六个要素的过程。
