## 背景：一个需要等待的 MCP 工具调用

最近在给内部支持团队搭建一个基于 OpenClaw 的运维助手，它通过 MCP 协议对接了几个远程沙箱和审批服务。一次典型的交互是：用户说“帮我在测试环境跑一下上周的 SQL 脚本”，助手会调用一个 `submit_sql_task` 的 MCP 工具，几秒后得到 `task_id`，然后……就没有然后了。因为那个沙箱工具是异步的，执行短则 20 秒，长则三四分钟，客户端需要自己等结果。

这就要求助手内部必须有一种“等待完成”的机制——也就是我们聊的 **heartbeat 设计**：是用轮询不断去问“好了没”，还是等后端推一个通知回来。

这个选择看起来是经典架构题，但落到 AI 助手/OpenClaw 的插件开发场景里，会有一些有趣的工程约束，我把踩过的坑和最终取舍整理出来，希望能给做类似自动化的同学一个清晰的参考。

## 问题拆解：不是简单的“推与拉”

首先要明确，这里的 heartbeat 不是用来检测 MCP 服务是否存活，而是**任务状态同步**。在 AI 助手的上下文里，有几个特殊需求：

1. **调用链路不透明**：用户通过助手 → OpenClaw → MCP 客户端 → MCP 服务端 → 实际执行环境，中间每一层都可能超时断开，而传统长连接很难一路穿透。
2. **助手实例可能是无状态/短生命周期的**：如果用 OpenAI 的 Assistants API 或类似 Serverless 部署，run 在等待结果时被挂起，等结果回来再继续，这本质上需要持久化等待状态。
3. **成本与延迟的平衡**：轮询太频繁会增加下游服务压力，而推送需要更复杂的网络可达性设计，二者没有一刀切的优劣。

## 实践过程：从纯轮询到“能推则推，否则拉”

### 1. 基线方案：指数退避轮询

最初的实现很直接：MCP 工具返回 `task_id` 后，助手内部进入一个轮询循环，每 2 秒请求一次任务结果，直到状态变为 `done` 或 `failed`，设 5 分钟超时后友好降级。

```python
# 伪代码：基本的 polling 逻辑
def wait_for_result(task_id, initial_interval=2, max_interval=30, timeout=300):
    start = time.time()
    interval = initial_interval
    while time.time() - start < timeout:
        status = mcp_client.call_tool("get_task_status", {"task_id": task_id})
        if status.state == "done":
            return status.result
        if status.state == "failed":
            raise TaskFailed(status.error)
        time.sleep(interval)
        interval = min(interval * 2, max_interval)  # 指数退避
    raise TimeoutError("Task did not complete in time")
```

**效果**：绝大多数任务都能在这个窗口内完成。但遇到了几个具体问题：
- 有些沙箱在并发轮询时会触发节流，返回 HTTP 429，导致超时前都拿不到结果。
- 当助手同时处理多个用户请求时，每个轮询循环都占用一个线程/协程，内存和上下文切换开销变大。

于是改进了轮询策略：**添加随机抖动**和**最大轮询次数限制**，同时把所有等待任务注册到一个全局的 `TaskWaiter` 服务里，复用少量协程分担。

### 2. 尝试推送：Webhook 回调

既然轮询有资源浪费，那自然想到让执行环境在完成时主动通知。我给沙箱服务加了一个 Webhook 字段，任务完成后向助手的回调地址 POST 结果。

**卡住的点**：
- **网络可达性**：开发环境里助手跑在本机，没有公网 IP，沙箱在云端回调不了。生产环境虽然反向代理可通，但需要额外证书和鉴权。
- **回调可靠性**：临时网络抖动或助手重启会导致通知丢失，还不得不加一层重试，而重试逻辑又类似于轮询，复杂度上去了。
- **OpenClaw 的 MCP 会话模型**：MCP 是请求-响应协议，没有内置的推送通道。如果你不在一个持久运行的进程里维护 HTTP 端点，回调根本收不到（比如用 Serverless 实现的 Run）。

最后我们在内网部署了一个专门的“通知网关”，提供持久化回调队列，给那些明确需要推送的场景用。但这对于一个小助手来说，维护成本已经过重了。

### 3. 混合策略：场景化取舍

总结下来，我们形成了这样一套决策路径：
- **任务耗时 < 30 秒**：直接用工具同步返回结果（一次 MCP 调用），不引入异步等待。
- **30 秒 < 耗时 < 5 分钟**：采用**自适应轮询**，根据历史执行时间动态调整起始间隔，加上退避和 jitter，保证下游服务负载可控。
- **耗时不可预估、或跨系统交互**：如果调用方能提供一个 Webhook 端点且网络可达，优先使用推送 + 轮询兜底（推送失效后降级为轮询）。
- **多用户高并发场景**：将等待逻辑从助手主循环中剥离，下沉到一个独立的 `Poller` 服务，该服务复用长连接或批量查询，大幅降低连接数。

## 踩坑实录

- **403/429 风暴**：轮询频率太高时，下游服务限流返回 429，如果在循环里直接抛出异常，等待流程被中断，用户感知为“卡住”。解决办法是捕获限流状态码，重置间隔，并设置最大重试次数。
- **时钟偏差**：任务服务与助手的时钟不一致，导致基于绝对时间的超时判断不准。统一改成相对时间 + 服务端返回的 `estimated_duration` 做辅助。
- **连接泄漏**：为了降低延迟，最开始用了长连接轮询（HTTP keep-alive），但忘记在某些库中关闭响应体，大量 CLOSE_WAIT 堆积。最终统一使用 `session` 并显式释放。
- **推送认证轮替**：Webhook 的 secret 过期后，推送失败无日志，后来加了 HMAC 签名和定期轮换，并在服务端记录最近一次推送状态，通过管理端可查。

## 可复用建议

1. **封装一个通用的 `AsyncTaskWaiter` 组件**，对外暴露 `wait(task_id, strategy)`，内部可切换 Polling / Webhook / Mock，便于测试切换。
2. **在 MCP 工具描述中明确异步语义**：如果工具返回的是 `task_id`，务必在工具的 `description` 中写明轮询接口或回调参数，这样 AI 模型也能生成更准确的等待逻辑。
3. **轮询策略一定要加退避和抖动**，即使间隔再小也要考虑突发流量，不然下游一个告警就能让你吃不了兜着走。
4. **监控等待时长和失败原因**：在 `TaskWaiter` 中埋点统计平均等待时间、超时比例和轮询次数，有助于优化间隔和提前发现后端变慢。
5. **优先采用支持长连接的反向代理推送**：比如用 Cloudflare Tunnel 让沙箱回调到本地开发机，降低推送实现的门槛。

## 总结

对大多数面向内部、运行在可控网络里的 AI 助手而言，**自适应轮询完全可以胜任**，投入产出比最高。推送虽然在延迟和资源利用上有优势，但往往需要额外的网关、认证和持久化机制，除非你的助手已经天然有公网可达的端点（比如基于 WebSocket 的前端），否则不要为了推送而推送。

heartbeat 设计本质上是**在不确定性中建立一种有节律的等待契约**。把策略做成可配置、可观测的组件，远比追求“推送至上”更重要。
