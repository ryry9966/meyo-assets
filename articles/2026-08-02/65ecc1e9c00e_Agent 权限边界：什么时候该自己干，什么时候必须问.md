## 背景：当 Agent 从“建议”走向“执行”

OpenClaw 的自动化链路中，Agent 已经不止于生成文本，而是直接调用 MCP 工具改文件、发请求、操作数据库。这种能力越强，“该不该拦住它”就越成为一个工程问题。

不少实践者初期会走两个极端：要么让 Agent 完全自主，结果凌晨三点收到“误删 production 表”的报警；要么所有操作都弹窗确认，自动化根本没跑起来。权限边界不是一个泛安全话题，而是一套需要设计、可配置、带反馈的运行时决策机制。

下面以 OpenClaw + MCP 工具链为背景，分享一个可落地的 Agent 权限分级方案。

---

## 问题：决策粒度应该放在哪一层？

常见的想法是“危险操作问人，安全操作自己干”。但实现时马上会遇到三个具体问题：

1. **谁定义危险？**  单纯按工具名（如 `run_shell`）判别太粗，参数里 `rm -rf /` 和 `ls` 风险完全不同。
2. **怎么问？**  如果每次确认都要人工盯着终端，自动化窗口直接缩到零。
3. **被问的人真的理解 Agent 要干什么吗？**  仅展示工具名和参数列表，上下文缺失，很容易误批。

所以方案不能只靠“拦截”，还得带上下文摘要、时效策略和自动降级。

---

## 实践方案：三级边界 + 上下文审批卡

### 1. 权限分级模型（基于工具调用意图）

在 OpenClaw 的 `pre_tool_call` 钩子中实现三层判定：

- **allow（自动放行）**  
  条件：工具在白名单内，且参数满足安全约束。例如 `read_file` 限制 `max_size < 1MB`、路径在 `/workspace` 下；`web_search` 允许，但禁止带内网地址。

- **confirm（人工确认）**  
  条件：工具超出白名单，或白名单工具的参数超出限制（如 `write_file` 目标在 `/etc` 下，或包含 `eval` 的动态脚本执行）。此时生成“操作审批卡”，推送至审批接口（IM/webhook），并挂起当前步骤。

- **block（直接拒绝）**  
  条件：命中硬黑名单（如 `drop_database`、`run_shell("rm -rf /")`），或操作对象为预定义的高保护资源。无需等待，直接终止该 Action，返回可读原因。

以下是一个简化的 `pre_tool_call` 实现框架：

```python
def pre_tool_call(tool_name, arguments, context):
    decision = classify(tool_name, arguments)
    if decision == "allow":
        return {"allowed": True}
    if decision == "block":
        return {"allowed": False, "reason": "Blocked by safety policy."}
    # confirm
    card = build_approval_card(tool_name, arguments, context)
    approved = request_approval(card, timeout=120)
    return {"allowed": approved}
```

### 2. 上下文审批卡

仅推送 `要执行 run_shell 吗？` 是不够的。审批卡必须包含：

- **当前任务摘要**  Agent 正在完成什么目标（由 OpenClaw 的 task context 提取）。
- **工具调用详情**  工具名、关键参数美化展示（例如对长命令做截断和语法高亮）。
- **潜在影响评估**  自动标注是否涉及外部网络、持久化写入、权限变更。
- **决策选项与时效**  “批准一次 / 本次会话全部批准 / 拒绝”，并显示超时后默认拒绝。

审批通道可以选择企业微信/Slack Bot。OpenClaw 的任务循环在 `confirm` 状态挂起，等待回调，不会占用额外轮次。

### 3. 时效与降级

如果审批人 120 秒无响应，默认拒绝。但某些批量自动化任务可能因此卡死，所以引入“会话级批准”：用户在一次审批中选择“本次任务全部批准同类操作”，Agent 将信任边界扩大到当前 session，直至任务结束或用户主动撤销。

## 踩坑记录

**坑 1：参数约束太死，自动放行变成瓶颈**  
初期把 `write_file` 限制在固定目录，但 Agent 出于需求生成了临时脚本到 `/tmp`，每次触发确认，效率极低。后来改为对白名单工具设定“安全上下文路径”（如项目根目录 + `/tmp`），减少非必要审批。

**坑 2：审批超时导致工作流超时**  
长时间等待人工审批，上游 HTTP 请求/消息队列早已超时断开，重试后产生重复操作。解决方案：Agent 层加幂等键，并在进入 confirm 状态前先持久化检查点，批准后恢复执行，避免重试副作用。

**坑 3：上下文摘要太简略，用户乱批**  
摘要只写“正在运行自动化任务”，用户习惯性点批准。改进为展示最近两轮 Thought/Action/Observation 的压缩记录，用户能实际感知进度，批得也更谨慎。

## 可复用建议

- **白名单驱动**：用 YAML/JSON 维护工具-参数约束表，便于非开发人员审计和修改，规则示例如下：
  ```yaml
  allow_list:
    - tool: read_file
      constraints:
        path_prefix: ["/workspace", "/tmp"]
        max_size_bytes: 1048576
  ```
- **黑名单正则**：针对 `run_shell` 等通用工具，维护危险模式正则列表，如 `rm\s+-rf\s+/`、`curl.*\|\s*bash`，命中直接 block。
- **审批疲劳监控**：统计单个 session 的 confirm 次数，若超过阈值，主动暂停任务并通知用户调整自动化策略，避免无意义的确认流。
- **可观测性**：每次 block/confirm 事件输出结构化日志（包含决策原因、涉及的规则 ID），方便事后复盘，持续优化边界。

---

## 总结

Agent 权限边界不是“开关”，是一套可以演进的策略系统。工程上值得投入的点是：形成 **allow/confirm/block 分层**、**带上下文的审批卡**、**时效与降级机制**，而不是试图一次性穷举所有危险场景。

在 OpenClaw 这类高度可定制的自动化框架下，我们可以用很少的代码把这几层串起来，既守住底线，也尽可能不牺牲自动化效率。后续值得探索的方向是把部分 confirm 场景交给一个更小、更便宜的“审查模型”来做裁定，进一步压缩人工介入频率。
