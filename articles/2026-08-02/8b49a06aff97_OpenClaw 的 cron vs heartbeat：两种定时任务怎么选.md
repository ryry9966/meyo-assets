# OpenClaw 的 cron vs heartbeat：两种定时任务怎么选

在 OpenClaw 的自动化链路里，定时任务几乎是每个 agent 项目都会遇到的刚需——每天拉取报表、每 30 分钟检查一次状态、每周清理过期日志。OpenClaw 在触发方式上提供了两种内置的定时机制：**cron** 和 **heartbeat**。很多人会在建任务时随手选一个，但跑了一阵才发现任务行为不符合预期，要么重复执行，要么长时间空转，甚至在关键节点漏触发。

这并不是哪种机制更好，而是它们的设计语义不同。真正工程化的做法，是先理解这两种定时模型分别**解决什么问题**，再看自己的场景落在哪个边界内。

## 背景：两种定时模型的本质差异

在 OpenClaw 的触发器配置中，`cron` 和 `heartbeat` 是两类独立配置，不能混用一份任务同时启用两种触发。

- **Cron 触发**：基于日历时间调度，使用标准 cron 表达式（如 `0 8 * * *`）。它关心的是“在什么时间点执行”，无论任务当时是否空闲。
- **Heartbeat 触发**：基于完成后的相对时间调度，配置一个间隔时长（如 `30m`）。它关心的是“上一次完成之后，等多久再执行下一次”。

关键区别在于：**cron 按墙上时间触发，heartbeat 按任务结束时间作为计时起点。** 这就导致它们在任务执行时间不可预测时，行为完全不同。

比如一个耗时 10–90 分钟不定的数据同步任务，如果你设 cron 每 30 分钟触发一次，势必会在某些时间点出现重叠执行；而 heartbeat 会等待当前任务完全退出后才开始计时 30 分钟，绝不会堆叠。

## 问题场景：三种典型困境

在社区和实际部署中，以下三类困惑最多：

1. **任务堆积**：cron 任务执行时间超过了触发间隔，导致旧实例未退出，新实例又被拉起，资源撑爆。
2. **间歇期不对**：需要任务执行完毕后再冷却一段固定时间，但用 cron 无法做到——冷却时间被墙上的固定时刻截断。
3. **心跳监控失效**：本意是想“每 5 分钟发送一次心跳”，用了 cron 后却发现一段时间没发出来，因为上次任务因外部 API 超时还没结束，cron 在这个整分钟点跳过了（如果策略是 skip）。

## 做法：怎么正确配置和判断

在 OpenClaw 的任务定义中，你只能选择一种触发器。假设任务 ID 为 `daily-report`，你可以通过 `trigger` 字段配置。

**cron 配置示例**（每天 7:00 执行）：
```yaml
trigger:
  cron: "0 7 * * *"
  # 重叠策略（可选），默认 skip，可改为 allow_parallel
  overlap: skip
```

**heartbeat 配置示例**（每次完成后等 30 分钟再开下一轮）：
```yaml
trigger:
  heartbeat: "30m"
```

选择路径非常直接：问自己“触发点是否必须对齐具体时间刻度”。

- 需要对齐时间刻度（每天开盘前、每小时整点推送）→ 用 cron。
- 不需要对齐任何墙上时间，只关心“做完后隔多久再做” → 用 heartbeat。
- 既要对齐时间，又担心任务拖尾太长导致堆积 → 用 cron 但设置 **overlap: skip**，牺牲一次执行换取稳定。

还有一种折中场景：你希望任务尽量在整点开始，但如果上一个任务还没结束，就不要同时跑。这是 heartbeat 办不到的，因为 heartbeat 不会主动对齐墙上时间；但 cron 配合 `overlap: skip` 可以做到，代价是可能丢弃某些启动。

## 踩坑实录

### 1. Heartbeat 的首次启动陷阱
heartbeat 的间隔从上次任务**完成**开始计时，而任务第一次启动是“立即执行”还是“等间隔”？在 OpenClaw 中，heartbeat 任务会在系统启动后立即执行一次，然后等待完成后进入间隔循环。这没问题，但在你重启部署时，heartbeat 会立刻跑起来——如果服务端刚启动还不稳定，容易引发连锁故障。建议给这类任务加上初始化预热或依赖检查。

### 2. Cron 的时区与机器时间
cron 表达式使用运行环境的系统时区。不少云实例默认 UTC，而你的业务逻辑按北京时间写 `0 8 * * *`，结果变成了 UTC 0 点。这导致“定时任务不执行”或者“时间不对”。解决办法：显式设置容器时区，或在 cron 表达式里做时区偏移（不推荐，可读性差）。

### 3. Heartbeat 被长时间阻塞的“假死”
如果 heartbeat 任务内部有死循环或永久阻塞的外部调用，计时永远不会开始，看起来就像是任务只执行了一次就停了。监控上要注意区分“任务在运行中”和“任务已完成但没触发下一个周期”。可以在任务逻辑内加上最大执行超时，超过后强制退出并报错。

### 4. Cron 的 overlap 策略并非银弹
`overlap: allow_parallel` 允许多个相同任务并发，对于无状态任务可以接受，但对于有状态逻辑（写入同一个文件、占用端口）会造成冲突。`skip` 模式虽然安全，但可能让你在监控上看到莫名其妙的“丢任务”。一定要结合业务容忍度评估。

## 可复用建议

- **如果任务执行时间远小于间隔**（例如 10 秒任务，间隔 5 分钟），用 cron 或 heartbeat 差别不大，但 cron 更直观。
- **需要冷却等待**：严格冷却场景必须用 heartbeat，否则外部系统可能因为你连续调用而限流。
- **需要整点触发但可丢弃**：用 cron + skip。
- **需要连续跑但绝不允许堆叠**：heartbeat 就是专为此设计的。
- **两个都要**：OpenClaw 不支持同一任务同时启用两种触发器，但你可以创建两个独立任务指向同一个 agent 逻辑，但注意隔离副作用。一般更推荐拆分关注点，例如用 cron 任务生成一个“触发信号”，实际耗时逻辑由另一个 heartbeat 消费者处理。
- **增加可观测性**：无论用哪种触发，都在日志中记录任务开始时间、结束时间、触发类型，便于事后排查是调度问题还是执行问题。

## 总结

cron 和 heartbeat 不是哪个更高级，只是对“时间”这个变量的两种建模方式。记得在配置前先画一张简单的时序图：任务是像闹钟一样被时刻表叫醒，还是像个工人做完一单歇十分钟再接下一单。一旦画清楚，触发器选择就几乎不用犹豫。

工程实践中，大多数“定时任务异常”并不是平台 bug，而是我们默认了“任务一定会在下次触发前完成”。把这个假设前置检查，你就已经避开了最大的坑。
