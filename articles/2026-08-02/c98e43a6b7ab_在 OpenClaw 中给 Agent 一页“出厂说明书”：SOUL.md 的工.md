# 在 OpenClaw 中给 Agent 一页“出厂说明书”：SOUL.md 的工程化实践

## 背景：Agent 的“系统提示词”在膨胀

使用 OpenClaw 或类似的 Agent 框架时，我们很快会养成一个习惯：在项目根目录放一个 `system_prompt.txt`，里面写满对助手的要求——“你是一个专业的 Python 后端开发助手，请使用 FastAPI，不要写前端代码，不要解释基础概念，优先使用异步语法，遵守 PEP8……” 几周后，这个文件轻松超过 200 行，夹杂着技术约束、语气要求、工具调用规则、甚至项目特定的数据库表名。

当我们需要调试某个回复偏差时，必须在冗长的提示词里逐行排查。团队成员修改提示词时也常常冲突：有人加了一句“拒绝回答无关问题”，有人写了“如果用户问天气就调用 get_weather 工具”，两者都没有明确的边界，Agent 行为越来越难以预测。更麻烦的是，如果同时维护多个 Agent（一个负责代码生成，一个负责文档撰写），提示词片段难以复用，复制粘贴导致不一致。

这就是引入 **SOUL.md** 的动机：将 Agent 的人格、技能边界、行为约束以结构化、可维护的方式固化下来，成为项目的一部分，像 README.md 说明项目一样，SOUL.md 说明这个 Agent “是谁”、“会什么”、“不做什么”。

## 问题：模糊的“人格”与失控的“边界”

在没有明确规范时，Agent 的 prompt 通常有三大类问题：

1. **角色模糊**：提示词只说“你是一个助手”，但没有定义技术栈偏好、上下文长度、回答粒度，导致输出不稳定。
2. **工具越权**：Agent 可能滥用 MCP 工具或插件，比如在没有必要的时候调用文件系统工具，或把本该用 A 工具的任务用 B 工具完成。
3. **安全边界缺失**：没有显式声明哪些话题必须拒绝、哪些数据不能输出，在本地开发环境可能只是尴尬，但在生产环境就是风险。

在 OpenClaw 这类以“工具调用”为核心的架构下，Agent 的行为边界不止体现在聊天内容中，更直接关联到它能调用的工具集合和调用方式。如果把 tool set 看作是硬边界，SOUL.md 就是软边界——它指导 Agent 在硬边界内如何做选择。

## 做法：从“一个文件”开始，逐步结构化

### 1. 创建 SOUL.md 骨架
在项目根目录创建 `SOUL.md`，建议至少包含以下板块：

```markdown
# Agent 身份与边界定义

## 角色
- 名称：CodeBuddy
- 定位：专业的 Python 后端开发助手
- 语气：简洁、克制，不废话，不卖萌

## 技术偏好
- 框架：FastAPI > Django
- 数据库：PostgreSQL，默认使用 asyncpg
- 代码风格：PEP8，类型标注完整，优先使用 dataclasses

## 能力范围（可以做什么）
- 生成后端 API 代码
- 编写 pytest 单元测试
- 分析 traceback 并给出修复建议
- 使用 MCP 工具读取项目文件结构

## 边界（绝对不能做什么）
- 不生成任何前端代码（HTML/CSS/JS）
- 不主动建议变更数据库 schema
- 拒绝回答与项目无关的闲聊，简单回答“请保持专业讨论”
- 不自行调用写操作工具（如文件写入、命令执行），除非用户明确要求

## 工具使用规则
- 读取文件只使用 `read_file`，不要用 `cat` 或直接路径拼接
- 代码搜索优先使用 `grep`，大数据量时才用 `code_search` MCP 工具
- 运行命令前必须列出将要执行的命令并请求确认

## 项目特定上下文
- 项目名称：my-api
- 主模块：`app/main.py`
- ORM：SQLAlchemy 2.0，async session
- 环境变量：见 `.env.example`
```

### 2. 在 Agent 入口加载并注入
在 OpenClaw 的 agent 配置或启动脚本中，读取 `SOUL.md` 内容，将其作为 system prompt 的前缀。如果框架支持模板变量，可以在 SOUL.md 中使用 `{{ variable }}`，再由启动脚本渲染。例如：

```python
from jinja2 import Template
import os

with open("SOUL.md") as f:
    soul_template = Template(f.read())

soul_prompt = soul_template.render(
    project_name=os.getenv("PROJECT_NAME", "my-app"),
    user_name=os.getenv("USER", "developer")
)

agent = OpenClawAgent(
    system_prompt=soul_prompt,
    tools=[...],
    ...
)
```

这样做的好处是 SOUL.md 保持纯文本、版本可控，变量在运行时注入，不会把敏感信息写进仓库。

### 3. 与 MCP tool 声明对齐
SOUL.md 里的工具使用规则必须和实际注册的 MCP 工具名、参数严格对应。建议在 SOUL.md 的**工具使用规则**节中直接引用真实 tool name，避免 Agent 自行猜测。在更新工具集时，务必同步更新 SOUL.md 中的规则，否则会出现 Agent 尝试调用不存在的工具，或者用错误的方式调用。

## 踩坑点：从文字到行为，距离比想象中大

1. **长文本导致 token 浪费**  
   200 行的 SOUL.md 直接塞进 system prompt，每次对话都会消耗大量 token。解决方式是**分层加载**：将相对稳定的部分（角色、技术偏好）作为系统级注入；将动态的、项目感知的部分（如文件路径、环境名）作为上下文在必要时注入。OpenClaw 可以在 `session_start` 钩子中注入长文本，后续对话只保留摘要。

2. **规则互相矛盾**  
   比如“使用异步语法”和“把所有数据库操作放在同步函数里”会冲突。Agent 在抉择时会出现随机行为。建议在 SOUL.md 中增加“冲突处理原则”一节，声明优先顺序。

3. **工具权限边界与 SOUL.md 不匹配**  
   在工具层面对 Agent 禁止了 `shell_exec`，却在 SOUL.md 里写“可以执行命令检查环境”，导致 Agent 反复尝试然后失败。务必将硬边界（注册的工具列表）和软边界（SOUL.md 中的描述）保持同步，不一致是行为异常的最常见原因。

4. **多人协作时 SOUL.md 随意增改**  
   团队可能在不同的分支上修改提示词，合并后产生冗余内容。建议对 SOUL.md 启用 review 流程，并限制只允许特定角色修改，同时用 pre-commit hook 检查是否包含未授权工具名或敏感路径。

## 可复用建议：从单 Agent 到 Agent 家族

- **模板化复用**：提取通用部分成为 `SOUL.base.md`，每个 Agent 继承并覆盖特定部分。例如“后端 Agent”继承基础角色，添加上下文。
- **目录约定**：在仓库中统一存放于 `agents/<name>/SOUL.md`，与对应的 MCP 配置、工具定义同目录，方便维护。
- **自动化校验**：写一个简单脚本，检查 SOUL.md 中引用的工具是否都存在于注册列表，并在 CI 中运行；检查是否有未闭合的模板变量。
- **版本标记**：在 SOUL.md 头部加一行 `<!-- version: 1.2.0 -->`，配合 changelog，方便回溯行为变化。
- **边界测试**：利用 OpenClaw 的测试框架，模拟用户输入“帮我写一个登录页面”，看 Agent 是否因为 SOUL.md 中的“不生成前端代码”而拒绝。这类测试可以直接验证软边界是否生效。

## 总结

给 Agent 设定人格和边界，不是一次性写完系统提示词就大功告成。它更像为一个新加入团队的工程师写 onboarding 文档——需要随着项目演进而更新，需要团队对其内容达成共识，需要与工具权限、代码规范协同作用。SOUL.md 把这件事从隐性经验变成显性制品，让 Agent 的“灵魂”变成仓库里一个可讨论、可版本化、可测试的文件。

在 OpenClaw 生态里，当你把 MCP 工具约束为 Agent 的“身体”，SOUL.md 就是它的“大脑使用说明书”。让每一个接手项目的同事都能打开这个文件，快速理解这个数字同事的脾气和底线——这才是工程化 AI 助手的正确姿态。
