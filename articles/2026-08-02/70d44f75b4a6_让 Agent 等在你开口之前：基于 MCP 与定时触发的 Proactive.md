## 背景：从“你问它答”到“它做完再告诉你”

目前绝大多数 AI 助手仍然在被动响应模式下工作：你给它一段上下文、一个指令，它才做出反应。对于深度接入工具链的 OpenClaw/Agent 用户来说，这种模式在信息监控、周期性检查、异常预警等场景中存在明显局限——你仍然需要自己充当那个“记得去问”的调度者。

**Proactive（主动式）能力**，就是让 Agent 不等待显式指令，而是根据时间、事件或上下文变化，自行触发分析或操作，并将结果推送给你。它不等你开口，就把事情办了。

这类能力在工程实践中的核心挑战并不是“能不能调用一个定时任务”，而是：如何保证触发时的上下文有效？如何避免过度打扰？如何在自主决策和人类确认之间找到边界？

本文围绕 OpenClaw 生态（Agent + MCP + 插件体系），给出一个可复现的 Proactive 实践方案。

## 问题拆解

要让 Agent“主动”，至少需要解决三个子问题：

1. **感知时机**：什么时候该干活？是固定时间，还是外部事件（Webhook、日志告警）？
2. **获取上下文**：触发时，Agent 如何自己拉取所需数据，而不依赖人工喂入？
3. **执行与收敛**：分析完成后，如何动作（报告、操作、提问），并避免重复或错误扩散？

在 OpenClaw 架构下，第一条可以由定时器或外部触发器解决；第二条可以交给 MCP（Model Context Protocol）提供的工具集；第三条则需要 Agent 自身的流程控制与安全边界设计。

## 做法：构建一个“项目风险早报”Proactive Agent

以一个真实场景为例：每天早 8 点，Agent 自动扫描项目 issue 列表、CI 状态和依赖库安全公告，生成一份风险早报推送到企业微信。

### 步骤 1：明确主动场景与边界

- **触发条件**：每个工作日 08:00（cron）。  
- **数据来源**：GitLab API、Dependency-Track 或 Snyk API、内部 CI 系统状态接口。  
- **输出形式**：Markdown 摘要，通过企业微信 Webhook 发送。  
- **人工兜底**：Agent 不直接执行合并代码或关闭 issue，只做信息整合与风险提示。

这一步的关键是**显式声明“只读+通知”的主动边界**，防止 Agent 在无人监控时执行破坏性操作。

### 步骤 2：通过 MCP 暴露工具

为 Agent 配备三个 MCP 工具（实际是本地或远程 MCP Server）：

- `get_open_issues()`：查询近 7 天未更新的 high/critical issue。  
- `get_ci_status()`：返回主干分支最近一次 pipeline 状态和失败原因。  
- `get_vulnerability_summary()`：从依赖扫描服务拉取新发现的严重漏洞列表。

每个工具都设计为**无状态、幂等**，并明确返回结构化 JSON，便于模型解析。工具描述里写清楚参数、返回格式和可能的异常码。

MCP Server 可以用 Python/TypeScript 快速搭建，通过 STDIO 或 HTTP 接入 OpenClaw 的 MCP 客户端。

### 步骤 3：配置定时触发器

在 OpenClaw 的插件或工作流配置中，定义一个基于 cron 的触发规则：

```yaml
triggers:
  - name: daily_risk_briefing
    schedule: "0 8 * * 1-5"
    task: project_risk_briefing
```

触发后，系统自动以 `project_risk_briefing` 这个预置任务唤起 Agent，并注入一段固定的系统指令：“你现在执行每日风险扫描，使用可用工具获取数据，生成摘要后发送到指定 Webhook。”

注意：这里的系统指令需要包含**明确的终止条件**和**最大工具调用次数**，防止模型在信息不全时反复尝试。

### 步骤 4：Agent 执行流程

Agent 被唤醒后，按指令执行：

1. 并行调用三个 MCP 工具，获取原始数据。  
2. 将 JSON 结果纳入上下文，进行结构化分析：是否有新增阻塞性 issue？CI 是否持续失败？有无可被利用的严重漏洞？  
3. 用预定义的 Markdown 模板生成早报，清晰标出风险项和建议行动。  
4. 调用 `send_wecom_message` 工具（也是 MCP 工具）将内容发出。  
5. 记录执行日志：成功/失败、各工具调用耗时、生成摘要的 token 消耗。

整个过程用户没有参与，醒来就能看到桌上的一条消息。

### 步骤 5：异常与降级

- 如果某个 MCP 工具调用超时（如 API 暂时不可用），Agent 会在早报中标记“无法获取”并继续执行剩余部分，而不是整体失败。  
- 若 Webhook 发送失败，Agent 会将消息正文存到本地文件，并在下一次任务中提醒“上次发送失败”。  
- 通过日志持久化，可以事后回溯 Agent 在无人值守时的决策路径。

## 踩坑点

1. **上下文过期与幻觉**  
   主动触发时模型可能基于过期的训练数据做判断。必须强制它先通过工具获取实时数据，再进行分析。可以在 prompt 中明确：“在没有调用相关工具前，不得假设任何数据。”

2. **频率控制与防打扰**  
   人天生对“被主动通知”敏感。如果 CI 每 10 分钟告警一次，Agent 不断推送，会导致通知疲劳。建议在主动任务里加入**去重/静默逻辑**：同一告警在一个窗口期内只推送一次，或仅在状态变化时通知。

3. **工具权限蔓延**  
   主动 Agent 的运行环境可能拥有较高的工具权限（如读写 GitLab、操作生产环境）。最佳实践是为 Proactive 任务使用**独立、受限的 API Token**，并限制其只能执行预设的安全操作集。

4. **模型成本与延时**  
   定时任务如果每次都调用大模型做重分析，token 消耗可观。可以考虑先用本地脚本做数据预处理和筛选，只在需要生成自然语言摘要时才调用 LLM。

## 可复用建议

- **渐进式自动化**：从“只读监测 → 生成报告 → 推荐操作 → 自动执行”逐步放开，每一步都要经过足够的人工复核验证。  
- **显式声明主动行为**：让用户清楚知道哪些 Agent 会在什么时候自发行动，并提供一键暂停/关闭的开关。  
- **记录决策痕迹**：每一次主动行动都生成审计日志，包含输入、工具调用序列、输出和最终动作。这在排查“为什么会发这条消息”时至关重要。  
- **用 MCP 解耦工具与逻辑**：将数据源和动作都封装为 MCP 工具，Agent 只负责调用和自然语言处理。这样工具变更不会影响 Agent 核心逻辑，反之亦然。

## 总结

Proactive 能力不是简单的“加个 cron”，而是在被动响应的 Agent 基础上增加**时间/事件驱动、自主上下文获取和安全执行边界**三个维度。在 OpenClaw + MCP 的技术栈下，这一能力已经可以落地到日常的监控、摘要、巡检等场景中。

当你的 Agent 不再等你开口，它并不能替你做所有决定，但可以让那些需要“记住去做”的琐事，从你的清单上彻底消失。关键始终是：**该做的做，不该碰的别碰，做了要留痕，打扰要有度。**
