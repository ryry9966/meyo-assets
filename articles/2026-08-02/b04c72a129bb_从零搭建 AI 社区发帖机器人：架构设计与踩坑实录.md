## 背景

社区运营里有一个老问题：信息流动太慢。优质外部动态、内部讨论的自动摘要、定期话题引导，如果都靠人手搬运，很快就会变成体力活。我所在的 OpenClaw 中文社区一直鼓励用自动化手段解决重复劳动，因此我尝试用社区内已有的 Agent + MCP + 插件能力，从零搭一个能分析上下文、自主决策、定时或事件驱动发帖的机器人。

目标很简单：
- 能在指定板块自动发帖，内容可以是 AI 生成的摘要、RSS 提炼或本地知识库问答。
- 行为可观测、可干预，绝不能变成“灌水机器”。
- 架构允许后续接入更多工具（搜索、图片生成等），不要焊死在单个脚本上。

这篇记录从架构设计到上线前踩坑的全过程，希望能为同类需求提供可复用的工程参考。

## 问题拆解

看似是“调个 API 发帖”，实际分解后至少涉及五层决策：

1. **内容源**：信息从哪来（RSS、网页抓取、人工触发）？
2. **处理管线**：如何清洗、去重、总结，避免重复低质内容？
3. **策略控制**：多久发一次？什么情况下不发？是否需要审核？
4. **行动执行**：调用社区接口实际发帖。
5. **自保机制**：错误重试、频率限制、异常告警。

这些模块如果揉在一个长脚本里，改一个策略就可能牵动全局。因此我选择以 Agent 为决策核心，通过 MCP 把各个能力拆成可组合的“工具”，再用插件机制管理生命周期。

## 架构设计

整体架构分为三层：

- **Agent 层（决策中枢）**：基于 OpenClaw 的 ReAct agent，负责接收触发信号（定时、手动指令），规划需要调用哪些工具，解析结果并生成最终行动。
- **MCP 工具层**：提供标准化的资源访问能力，包括：
  - `community_api`：封装社区登录、发帖、编辑、上传图片等动作。
  - `content_fetcher`：RSS 抓取、网页正文提取。
  - `summarizer`：调用 LLM 对长文进行结构化摘要。
  - `knowledge_base`：对接本地向量库，供内部问答类帖子使用。
- **插件/调度层**：用一个轻量调度器（如 `node-cron`）管理定时任务；人工触发通过一个小型 HTTP 服务暴露 Webhook，供社区管理员即时调用。

关键数据流：定时器/Webhook → Agent 接收上下文 → Agent 按需调用 MCP 工具 → 聚合结果 → 审核策略（可选）→ 调用 `community_api` 发帖 → 记录日志。

一个额外设计：所有工具输出都带上 `metadata`，包括时间戳、来源、置信度标记，便于后续审计。

## 实现步骤（简记）

1. **初始化 OpenClaw Agent 项目**，配置基础能力模型和系统提示词。提示词明确禁止连续发布、要求先检查最近帖子避免重复。
2. **编写社区 API 的 MCP 服务**：逆向社区使用的 headless API，封装登录态维护（cookie/refresh）、CSRF token 处理、富文本拼接逻辑。这里的难点不是调用本身，而是错误语义处理（比如 429、账号被临时限制时的指数退避）。
3. **编写内容获取工具**：RSS parser + readability 提取正文，输出统一结构 `{title, summary, source_url, full_text}`。
4. **组合策略**：用 Agent 决定“今天是否值得发”。策略引擎是几层 if-else 不丢人，关键是可调试。我用了简单的规则：同源内容 24h 内不重复；摘要质量分低于阈值则丢弃；优先挑选与社区近期讨论相关的话题（基于本地博文向量相似度匹配）。
5. **接入调度与通知**：定时任务每天 9:00、15:00 触发分析，Webhook 路径用于管理员即时上传链接让机器人总结后发帖。异常会被推送到内部通知频道。

## 踩坑实录

- **坑1：内容去重比生成难**  
  即使 LLM 摘要质量稳定，相似事件的重复报道很容易被当成新内容发布。单靠 URL 去重不够，必须做标题+摘要的语义去重，并保留最近一周发布记录。我在 MCP 工具里额外加了向量索引，每次发帖前做一次 top-3 相似检测。

- **坑2：社区接口的反爬升级**  
  刚开始用的直接 HTTP 请求经常被限流，即使频率很低。后来发现社区对新账号的 UA 和请求序列有非显式检测。最终解决方式是复刻正常浏览器的请求链，包括先请求首页取 token，再模拟一次“预览”步骤，最后提交。这个流程完全放在 MCP 工具里，对 Agent 透明。

- **坑3：Agent 过度自信**  
  有几次 Agent 认为“摘要很短但信息重要”，结果发了空洞帖子。修复方式是在提示词里加入硬约束：有效内容少于 50 字且无外部链接，直接放弃发布。工程上不要只靠模型的自控力，关键路径必须加护栏。

- **坑4：时区和夏令时**  
  定时任务按 UTC 设置，但社区活动以北京时间为准。跨时区配置 cron 时容易遗忘，直接用 `tz` 参数显式指定 Asia/Shanghai，避免手动换算出错。

## 可复用建议

1. **能力全部 MCP 化**：不要让 Agent 直接操作社区接口或数据库，工具化后单独测试、限流、降级都极为方便。
2. **给策略留“不发布”选项**：机器人的价值不仅仅在于“发了什么”，更在于它懂得何时闭嘴。强制 Agent 在每个决策路径上考虑 `do_nothing`。
3. **所有输出需可追溯**：保存每一次生成、决策、发布的完整日志及对应的 prompt+response，便于复盘和优化。
4. **逐步放开权限**：初期可以只发到草稿箱或测试板块，手动审核后再发布，跑通流程后再逐步自动化。

## 总结

从零搭建一个 AI 社区发帖机器人，本质上是在做一套“信息获取-理解-决策-执行”的小型自动化流水线。选择 Agent + MCP 的架构，让每个环节都可替换、可观测，很大程度降低了维护成本。踩过的坑大多与“真实世界的不可靠性”有关：不稳定的社区接口、时区误差、内容重复的隐性边界。把这些问题提前约束在工程护栏里，远比事后补救省力。希望这篇实录能为同样想在 OpenClaw 生态里做自动化实践的同伴，提供一份可落地的参考。
