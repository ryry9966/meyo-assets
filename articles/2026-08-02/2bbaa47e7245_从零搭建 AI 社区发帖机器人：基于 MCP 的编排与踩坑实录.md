# 从零搭建 AI 社区发帖机器人：基于 MCP 的编排与踩坑实录

## 背景

OpenClaw 社区每周有固定的内容发布需求：项目周报、插件更新日志、最佳实践汇总。这些帖子有明确的格式化模板，信息来源分散在代码仓库、Issue 讨论、内部知识库。人工整理耗时且容易出现格式不一致、漏掉关键变更的情况。我们尝试引入一个 AI 发帖机器人，让它自动完成“信息采集 → 内容生成 → Markdown 排版 → 社区发布”的完整流程，减少维护负担。

这个机器人的核心是：**Agent 负责任务理解与编排，MCP 工具层统一对接外部能力，社区 API 作为最终执行出口。** 下面按照实际搭建顺序，拆解架构、关键决策和踩过的坑。

## 问题定义

需要解决三个主要问题：

1. **信息聚合**：如何从 GitHub、内部文档等异构源中准确抽取本周有效变更。
2. **内容质量控制**：生成的内容必须符合社区模板、无幻觉链接、语言风格一致。
3. **发布可靠性**：直接调用社区接口时，如何应对格式拒绝、重复提交、网络波动。

## 架构设计

整体采用 **Agent + MCP** 的轻量编排模式，不引入沉重的 RPA 或全自动流水线，保留人工确认节点。

```
[用户指令: “生成本周 OpenClaw 生态周报”]
         │
         ▼
    ┌────────────┐
    │   Agent    │  (OpenClaw 自带的 plan & execute)
    └─────┬──────┘
          │ 调用 MCP 工具
    ┌─────▼──────────────────────┐
    │  MCP Server                │
    │  ├─ github_search_issues   │
    │  ├─ docs_fetcher           │
    │  ├─ content_summarizer     │
    │  └─ markdown_formatter     │
    └─────┬──────────────────────┘
          │ 返回结构化数据
    ┌─────▼──────┐
    │ Draft 草稿 │ (写入本地文件或临时 note)
    └─────┬──────┘
          │ 人工检查
    ┌─────▼────────────┐
    │  Community API   │ (Discourse / 自定义论坛)
    └──────────────────┘
```

Agent 本身不做复杂推理，只负责按预设流程调用 MCP 工具。MCP 工具统一封装外部数据源和格式化逻辑，避免 Agent 直接处理原始 API。发布前生成 Markdown 草稿，人工确认后再调用社区 API 创建帖子。这个额外的“干预算点”在踩坑后被证明是必需的。

## 关键实现步骤

1. **MCP 工具集搭建**  
   基于 `mcp` Python SDK 编写三个工具：
   - `list_recent_merged_prs(days=7)`：调用 GitHub API，过滤出指定仓库的合并 PR，返回标题、作者、链接、标签。
   - `fetch_doc_changelog(source)`：读取内部文档仓库最新 changelog 条目。
   - `format_weekly_post(title, sections)`：将结构化数据注入 Jinja2 模板，输出最终 Markdown。

   每个工具都暴露为 MCP resource 或 tool，Agent 通过标准 MCP 协议发现并调用。

2. **Agent 配置**  
   使用 OpenClaw 自带的 Agent 配置文件，定义任务步骤：
   - step1: 并行调用 github 与 doc 工具。
   - step2: 将结果结构体传给格式化工具。
   - step3: 输出草稿到指定文件，等待人工确认。
   - step4: 收到“确认发布”指令后，调用社区 API 创建帖子。

   Agent 使用 `gpt-4o-mini` 仅做简单判断（例如识别本周是否为空），所有核心逻辑下沉到工具。

3. **社区 API 对接**  
   以 Discourse 为例，API 创建帖子需要 `title`、`raw` (Markdown)、`category`。我们封装一个 Python 脚本 `community_post.py` 作为“MCP 后的最后一步”，因为 MCP 工具不适合直接暴露密钥（社区 API key）。脚本从本地草稿 JSON 读取内容，进行最终格式清洗，再发送请求。

## 踩坑实录

### 坑1：Agent 幻觉导致 PR 链接错误
最初让 Agent 直接用 `requests` 抓取 GitHub Search API，结果模型时常“修正”返回的 URL，造成链接 404。**解决：** 改为在 MCP 工具侧完成所有数据拉取和清洗，Agent 只收到工具返回的字典列表，不得自行拼接 URL。幻觉立刻归零。

### 坑2：Markdown 渲染社区侧不一致
Discourse 对嵌套列表、连续空白行敏感，工具生成的 Markdown 在预览正常，发布后出现多余空行或代码块未闭合。**排查发现**：Jinja2 的 `-` 去除空白控制与模板格式化有冲突。**对策**：增加一个后处理步骤，在 `community_post.py` 中统一对 `raw` 文本执行 `re.sub(r'\n{3,}', '\n\n', raw)` 并验证代码块标记配对。

### 坑3：重复发布与幂等性
人工确认发布后，偶尔因网络波动 API 返回超时，但帖子实际已创建。重试导致重复帖子。**解决**：在草稿阶段生成唯一 `idempotency_key`（由日期+标题哈希组成），写入草稿 JSON。发布脚本先检查该 key 是否已有成功记录（本地 SQLite 状态表），有则直接返回已有帖子链接，不再重复创建。

### 坑4：社区 API 频率限制
Discourse 免费版 API 限制为 20 请求/分钟。高峰期 Agent 并行调用多个工具后再连续调发布接口，容易触发 429。**缓解措施**：发布脚本内置指数退避重试，并将非紧急发布延迟到低频时段（通过 crontab 制定固定窗口）。

### 坑5：模板强制约束被绕过
Agent 有时会“创造性”地改变周报段落顺序。我们尝试在 prompt 中严格限定，但 Agent 仍有 10% 概率不遵守。最终方案：**完全从 Agent 手中剥离最终排版控制**。Agent 只产生原始 sections 数据，模板渲染由 Python 格式化工具有序完成，禁用 LLM 参与最终排版。

## 可复用建议

1. **让工具承担确定性任务，Agent 只做编排**  
   任何需要精确格式、固定数据源的操作都封装为 MCP 工具，Agent 绝不直接生成最终输出。

2. **为发布操作加入人工确认与幂等机制**  
   即使是自动化流程，也保留一个人工确认点（哪怕是简单的 yes/no）。幂等性设计避免重复发布产生的噪音。

3. **针对目标社区做格式兼容测试**  
   写一个“格式验证器”函数，在发布前模拟社区渲染规则，检查常见问题：未闭合标签、多余空行、链接格式。

4. **记录状态与可观测性**  
   使用轻量日志和状态表记录每次发布 attempt，包含 idempotency_key、状态、返回的帖子 ID、错误信息。这对排障和长期维护至关重要。

## 总结

通过 **Agent + MCP 工具解耦**，我们在 OpenClaw 社区内部成功落地了一个稳定运行的周报发帖机器人。它并非全自动的无人工厂，而是将机械性劳动自动化，保留关键审核点。踩过的每个坑都指向同一个核心原则：**在 AI 驱动的自动化中，越靠近最终产出的环节，越需要确定性与可控性**。如果你也在为社区或团队搭建类似系统，希望这些笔记能让你少走一些弯路。

当前机器人已稳定运行超过 8 周，每周准点发布生态周报，错误率从最初的 40% 降低到 2% 以下。下一步计划将它适配到 OpenClaw 的插件管理面板，让社区成员也能通过简单指令生成符合规范的技术分享帖。
