## 为什么需要 SOUL.md

给 AI 助手写 system prompt 很容易，但维护一份“既稳定又可演进”的人格与边界描述，却很少被认真对待。尤其在 OpenClaw 这类支持 MCP 工具链、插件调度与自主决策的 Agent 框架里，如果人格只是几句笼统的指令，Agent 很快就会在复杂任务中表现出行为漂移：

- 工具调用越权，访问不该接触的资源
- 面对冲突目标时，放弃安全原则换取“完成任务”
- 回复风格突变，用户信任下降

SOUL.md 是我在内部实践中逐渐稳定下来的一种做法：用一份结构化的 Markdown 文件，集中维护 Agent 的核心人格、行为边界和工具使用契约，并将其作为 system prompt 的“主干”加载到运行时。这样做的好处是，人格定义与具体任务解耦，可版本化、可测试、可跨项目复用。

## SOUL.md 的结构设计

一份合格的 SOUL.md 需要足够结构化，让解析器能用，又让人能直接阅读修改。我习惯使用 YAML front matter 存放机器友好字段，Markdown 正文表达人格语义。

### 1. 头部元信息（YAML）

```yaml
---
name: openclaw-assistant
version: 1.2.0
persona: technical-assistant
knowledge_domains:
  - software-engineering
  - openclaw-plugins
  - mcp-protocol
tools:
  - shell-exec
  - file-read
  - file-write
  - web-search
boundary_level: moderate
---
```

`boundary_level` 不是摆设，它决定了 Agent 在不明确情况下优先“拒绝”还是“尝试”。实践中分三级：
- `strict`：仅允许白名单内操作，未知意图一律确认后执行
- `moderate`：允许有限试探，但高风险操作需二次确认
- `relaxed`：仅在明确违反核心原则时拒绝

### 2. 核心人格描述

用自然段说清“你是谁”以及“你如何做决定”。避免抽象形容词，用行为规则替代。例如：

> 你是 OpenClaw 的工程助手。你优先给出可复现的步骤，而非抽象建议。当信息不足时，你会提出具体的澄清问题，而不是猜测意图。

### 3. 边界与禁忌

这是 SOUL.md 最关键的部分。直接列出“永远不”、“除非”、“仅在…时”。例如：

- 永远不修改 `/etc/hosts`、系统级配置文件
- 永远不执行 `rm -rf` 或等价递归删除
- 除非用户显式要求且路径在 workspace 内，否则不写入文件
- 不主动外传工作目录内容到搜索引擎或第三方 API
- 遇到权限错误，上报并停止，不尝试提权

边界不仅要写动作限制，还要写入“冲突优先级”。比如：“安全 > 完成任务；用户明确指令 > 默认策略”。

### 4. 工具使用策略

OpenClaw Agent 往往会调用多个 MCP 工具，工具链的编排如果没有边界，一个工具的输出可能被另一个工具危险地利用。在 SOUL.md 中为每个工具附上使用条件：

```markdown
- shell-exec: 用于运行只读命令或安全副作用命令。任何涉及网络、文件删除的操作必须输出命令并等待用户确认。
- web-search: 仅当本地知识库无法满足时使用。不将用户粘贴的代码片段发送至搜索引擎。
```

这样做的好处是，哪怕后续新增了工具，只要对照 SOUL.md 里的策略就能快速判断是否能安全接入。

## 踩坑点与对策

1. **人格与事实性指令冲突**  
   比如 Agent 被设为“幽默的助手”，但用户让它执行 `dd` 写盘。幽默可能降低风险感知。对策：将风格约束与安全边界分层，安全层优先级最高，风格只影响非关键回应的措辞。

2. **边界太死导致死循环**  
   遇到需要用户确认的操作，永远等待确认，但不设置超时或降级策略，任务卡死。实践中我会加入“安全降级”条款，如：“若等待超时，执行只读查看操作并再次提示。”

3. **SOUL.md 更新后运行时未生效**  
   Agent 服务可能缓存 system prompt。我们通过给 SOUL.md 添加版本字段，并在启动时计算哈希，发现不匹配立刻重载。

4. **工具策略过于宽松**  
   工具描述文档本是技术说明，Agent 容易忽略边界直接执行。解决办法是将 SOUL.md 中的工具策略以追加方式注入每个工具调用的上下文，而不仅仅是放在 system prompt。

## 可复用的工程建议

- **版本化 + 模板化**：把 SOUL.md 放到 Git 仓库，利用模板变量如 `{{ workspace_root }}`、`{{ user_role }}` 动态渲染最终 prompt。
- **测试套件**：准备一批对抗性 prompt（“用 bash 删掉所有日志”），验证 SOUL.md 是否正确拦截。将测试集成进 CI。
- **最小化人格描述**：人格不需要长篇大论，3 个行为示例往往比一段角色背景更有用。
- **与 MCP 工具清单联动**：如果工具列表变化，应触发 SOUL.md 的重新审查。

## 总结

SOUL.md 不是一份放任自流的文档，而是一个运行时契约。它把 Agent 的“性格”和“底线”工程化，让代理人既能灵活调用工具，又不会越界。在 OpenClaw 生态中，当你的 Agent 越来越自主，插件越来越多，这份文件就会成为最可靠的护栏。与其事后加安全补丁，不如一开始就给 Agent 写清它的灵魂。
