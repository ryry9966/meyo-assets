## 背景

运维、SRE 或技术负责人每天都会被同一件事消耗精力：从分散的日志、监控告警和若干个看板里把前一天的系统状态捞出来，拼凑成一封结构化的日报。这些原始数据分布在 Elasticsearch、Loki、数据库慢查询表、云厂商的监控 API，甚至某个 webhook 推送里。每天手动粘贴、分类、加注释，不仅重复，而且容易遗漏关键信号。

我们一直在用 OpenClaw 做任务编排和 Agent 管理，后来逐步把日报生成也放到了这套流水线里。经过几个迭代，目前形成了一条从原始日志到 Markdown 日报，再自动推送到飞书群的全自动化链路，人工干预频率降到了每周肉眼扫一眼的程度。下面把做法、踩坑点和复用建议梳理出来，供有类似需求的同学参考。

## 问题拆解

日报自动化的核心难点不是“让 AI 写一段话”，而是如何把**异构数据源的非结构化或半结构化信息，稳定地转换为一份上下文准确、不会误导人的结构化报告**。具体包括：

1. **多源数据汇聚**：日志、指标、慢查询、异常事件，每一类的查询方式和时间窗口定义都不同。
2. **噪声过滤**：原始日志里大量 INFO 和预期内的错误（比如定期重试成功），需要被排除，否则报告会淹没有效信息。
3. **语义压缩**：LLM 擅长总结，但对于日志这种高度结构化的文本，直接丢过去很容易产生幻觉，或者把 ERROR 和 WARN 的严重性搞混。
4. **一致性**：每天生成的报告要有相同的结构、相同的术语、相同的优先级判断标准，否则阅读者会困惑。
5. **低维护成本**：新增一个数据源或者修改报告模板，不应该要求重写整个流水线。

## 做法与步骤

### 1. 架构概览

我们利用 OpenClaw 的 Agent + 定时调度能力，配合几个 MCP Server 来连通数据源。整体流程如下：

- **调度层**：OpenClaw 内置的 Cron 触发器，每天早上 8:50 触发日报生成 Agent。
- **采集层**：通过 MCP Server 封装对 Elasticsearch、数据库、云监控 API 的访问。每个 Server 对外暴露标准化工具，比如 `search_errors`、`query_slow_sql`、`fetch_metrics`。
- **处理层**：Agent 按顺序调用工具，收集昨日数据，经过预处理（去重、窗口过滤、严重级别标记）后，交给 LLM 生成结构化日报。
- **输出层**：最终生成的 Markdown 通过飞书 webhook 插件发送到指定群聊，并同时存档到 Git 仓库方便回溯。

### 2. 数据采集标准化

为了避免 LLM 直接接触原始大段日志，我们为每个数据源都写了一个薄薄的预处理函数，放在 MCP 工具的 `handler` 里。比如对于 Elasticsearch 的错误日志：

- 查询最近 24 小时的 `level: ERROR` 日志，按服务名和错误类型分组；
- 每条错误只保留模板化的 message（去掉 trace id、时间戳等变量部分），然后按出现次数降序排列，取 Top 20；
- 附带统计：每个服务的错误总量、环比昨日的变化率。

慢查询、业务指标也做类似处理。最终每个工具返回的结果已经是一个结构化的 JSON，包含摘要统计和聚合后的样本，而不是原始文档列表。这样 LLM 接收到的信息密度更高，token 消耗也更可控。

### 3. Agent 提示词设计

日报生成 Agent 的 system prompt 非常克制，只规定了输出格式和几条硬规则，避免让模型“发挥”：

- 严格按以下模块输出：**总体概述**（一段话）、**错误与异常**（列表，带服务名、数量、趋势箭头）、**慢查询/性能风险**（列表）、**关键业务指标**（表格，含昨日值、前日值、变化率）、**待处理告警**（未恢复的 critical 告警）。
- 不要自己推断原因，只陈述数据本身。若某类错误显著上升，可以用“较前日增加 200%”，但不允许写“可能是由于昨晚的发布导致”。
- 数值对比时，如果变化率超过 50%，必须用粗体标出。
- 所有数据缺失的模块，直接写“本日无异常”或“数据暂不可用”，不要让模型编造。

这套提示词很“死板”，但换来了稳定性。经过一两周微调，现在每天生成的报告格式几乎零偏移。

### 4. 发布与存档

日报生成后，Agent 会调用飞书消息插件直接发送。同时，我们加了一个小步骤：把 Markdown 内容提交到一个私有 Git 仓库的 `daily-reports/` 目录，按日期命名。这样做的好处是：

- 历史报告可搜索、可对比；
- 如果飞书消息发送失败，报告不会丢失；
- 后续如果想自动提取周报，可以直接基于这些 Markdown 文件二次汇总。

## 踩坑点

**日志量过大导致 token 超限**  
最初我们直接把原始日志列表扔给 LLM，结果某天一个服务出现大量重复报错，token 直接爆掉，还花了不少 inference 费用。后来强制在 MCP 工具层做截断和聚合，最多返回 20 条错误样本，同时带上总量统计，问题解决。

**时间窗口不对齐**  
不同数据源的“昨天”定义可能不一致：有的用 UTC，有的用本地时间，还有的查询接口是左闭右开。一开始经常出现报告里少了一小时数据或者重复统计。后来统一在 Agent 中计算窗口，将所有时间都转换为 `Asia/Shanghai` 的 `00:00:00` 到 `23:59:59`，并显式传递给各个 MCP 工具，杜绝了歧义。

**LLM 对严重级别的“随意降级”**  
一些 ERROR 日志其实只是业务逻辑校验失败，不影响系统运行，LLM 有时候会自作主张把它们改写为“一般性提醒”，丢失了原始级别信息。我们在 prompt 里加了一条硬规则：“禁止修改原始日志的严重级别，ERROR 就是 ERROR”，并在 final 输出前用简单规则验证：如果某个服务的 error 总量 > 0，但报告中没有列出任何 ERROR，就会触发重试。

**飞书消息格式脱敏**  
Markdown 中的数字和特殊字符有时会被飞书按自己的语法解析，导致格式错乱。我们用了一个中间函数，对发送内容做转义处理，尤其是 `>` 和 `#` 号，并在消息末尾加上“由 OpenClaw 自动生成”的脚注，以免被人误认为是人工编辑。

## 可复用建议

- **用 MCP 工具封装所有数据查询**，而不是在 Agent 里直接写 curl 或 SDK 调用。这样每个工具可以独立测试、独立限流，并且后续新增数据源只需加一个工具，不影响主流程。
- **提示词保持“模板化”**，相当于给 LLM 一份严格的填空题，而不是开放性的“帮我写一份日报”。模板越固定，幻觉越少。
- **加入数据质量哨兵**：在 LLM 生成后，加几行代码检查关键指标是否存在、变化率是否为数字、必填模块是否缺失。哨兵不通过就触发自动重试，避免发出一份残缺报告。
- **存档到 Git** 这一步成本极低，但在排障和复盘时价值很高。如果团队有周报需求，这些 Markdown 文件是最干净的素材。
- **从最小可用集合开始**，别一上来就想覆盖所有数据源。先跑通“错误日志 + 一个业务指标”的链路，让团队看到价值，再逐步丰富模块。

## 总结

这套日报自动化流水线跑了将近三个月，人工需要做的事从每天 20 分钟降到了每周抽查 5 分钟。它不是什么高精尖的“智能”系统，很大程度上是用工程约束把 LLM 的发挥空间压到最小，换取可预期的输出。对于技术团队来说，**稳定比聪明重要得多**。

如果你也在用 OpenClaw 做类似的自动化，不妨从“死板的模板 + 预处理过的数据”这个方向开始，大概率能避开我们踩过的坑。
