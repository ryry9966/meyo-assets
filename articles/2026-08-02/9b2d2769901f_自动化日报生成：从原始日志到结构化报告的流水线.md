## 背景

团队每日站会前，总要有人花 15-30 分钟从 Git、任务面板、监控告警、CI 结果里拼凑昨天到底发生了什么。人工汇总不仅低效，而且容易遗漏或主观偏向。“自动化日报”听起来简单，但落地点在于 **数据源分散、格式杂乱、上下文量大**，用单一脚本很难兜住所有异常情况。

我们尝试用 Agent + MCP 搭建了一条更工程化的流水线：每天定时触发，按顺序捞取原始日志，经过清洗、聚合、总结，最终输出一份可直接发布的结构化日报。底层跑在 OpenClaw 编排下，全程无需人工介入。

## 问题拆解

真正让日报生成“不可靠”的，不是缺少数据，而是：

1. **多源数据隔离**：Git 提交记录在代码托管平台，任务更新在项目管理工具，告警在监控系统，CI 状态在构建平台。各系统 API 鉴权方式、字段语义、分页逻辑都不同，直接胶水脚本耦合严重。
2. **原始数据噪声大**：一次合并请求可能引入几十条自动生成的 commit；告警可能因抖动产生重复通知；任务评论里含有大量非结构化讨论。
3. **时间窗口对齐困难**：日报通常覆盖“昨天 00:00 到 24:00”，但系统时间可能为 UTC，用户本地时区不同，跨时区协作时容易出现边界遗漏或重复。
4. **LLM 摘要不稳定**：直接将混杂的原始文本丢给模型，得到的总结可能忽略关键事项，或凭空编造未发生的事情。

## 做法与步骤

### 1. 抽象统一的数据源接口（MCP 插件）

我们用 MCP 协议封装了四个数据源，每个都是一个独立的 server：

- **Git MCP**：封装 commit 列表查询，支持按分支、作者、时间段过滤，返回结构为 `{repo, branch, commits: [{hash, author, timestamp, message}]}`。
- **Task MCP**：对接任务管理工具（如 Linear），返回指定时间段内创建/更新/完成的任务列表，包含状态流转记录。
- **CI MCP**：对接 CI 服务，返回最近 24 小时内所有流水线状态（成功/失败/进行中），附带失败步骤日志摘要（截断到 2KB）。
- **Alert MCP**：从监控系统拉取告警事件，按严重级别和状态去重，只保留已触发且未恢复或已恢复但属于过去 24 小时的事件。

每个 MCP server 自行处理鉴权、重试、速率限制，对外暴露标准化 JSON schema。Agent 通过 OpenClaw 的工具调用机制，按需并行拉取数据。

### 2. 数据清洗与中间格式化

拉取到的原始数据在进入 LLM 前，必须经过一道**确定性清洗**。我们用了一个轻量级纯函数流水线（非 Agent 环节），只做规则匹配和字段映射：

- 合并同一 merge request 下的 squash commit，只保留最终合并消息与关联任务 ID。
- 对 CI 失败日志提取错误关键词（预定义模式匹配如 `Error`, `exception`, `timeout`），省略完整堆栈。
- 告警按 `alertname + severity + startsAt` 去重，计算持续时长。
- 统一时间戳为日报指定的时区（从配置读取）。

这一步输出一个结构化 JSON `DailyDigestRaw`，作为 LLM 摘要的上下文入口。

### 3. LLM 总结与输出控制

将 `DailyDigestRaw` 送入 LLM，但并非自由发挥。我们给定了严格的输出模板和字段约束：

```markdown
## 昨日回顾（{date}）
### 代码变更
- 仓库A(分支): 要点1, 要点2...
### 任务进展
- TASK-123: 完成[x] 进行中[ ] 阻塞[ ]
  进展: ...
### CI/CD
- 失败流水线: 项目名(错误类型) - 已由xx处理/待处理
### 监控告警
- [P1] 告警名称(持续时长) - 当前状态
```

模型只需填充各节内容，并用开关 `highlight_if_blocked` 控制是否在开头加入阻塞摘要。通过 system prompt 显式要求：**不得编造未在输入中出现的信息**；如果某项无数据，则输出“无”。这样可以有效抑制幻觉，也方便后续解析。

### 4. 编排 & 定时触发

整个流水线在 OpenClaw 中定义为一条 `pipeline`：

```
Cron trigger (每天 8:00) → Data fetching (并行) → Cleaning → LLM summarizer → Output render → Slack/Email publish
```

pipeline 中每个阶段有明确的超时和重试策略（例如数据源失败 3 次后退化输出，不阻断整体发布）。发布通过一个 `notify` 插件实现，可同时发送到 Slack 频道和邮件组。

## 踩坑点

**LLM 上下文窗口被冲垮**  
初期直接把所有原始日志（包括完整 CI 日志）塞入 prompt，动辄 10k+ tokens，不仅成本高，而且模型会混淆细节。必须先在清洗环节强截断、分类、优先级排序，只保留摘要足够推断的必要字段。

**时区混乱导致“昨天”的定义漂移**  
Git 提交的 `author timestamp` 是 UTC，任务系统时间是用户本地时。我们最初直接用 `datetime.now(tz).date() - 1 day` 过滤，结果漏掉跨时区凌晨的推送。改为所有数据源在 MCP 层统一返回 UTC 时间戳，清洗时统一转换为日报时区后按日期分组。

**合并请求 squash 导致重复统计**  
一个 MR 合并后，原始分支上的多条 commit 也会被拉取。如果不加处理，日报会显示“张三提交了 10 个 commit”，实则只是一个 MR。我们通过识别 merge commit 并反向追踪原分支的 commit，将所有相关提交折叠为一条，消息取 MR 标题。

**LLM 忽略任务关联关系**  
有时一个任务同时关联了多个 commit 和一条告警，LLM 在总结时会分散提及，失去了关联性。我们在 `DailyDigestRaw` 中显式用 `related_items` 字段维护连接，并指示模型优先按关联线汇报。

## 可复用建议

- **把数据获取和业务逻辑严格分离**：通过 MCP 插件做数据源抽象，清洗层独立于 Agent，便于替换工具或调整规则。
- **为 LLM 定义最小必要上下文**：宁可多花时间在预处理上，也不要考验模型的推理和记忆极限。裁减必须有明确业务规则。
- **日报模板可配置，而非硬编码**：将模板、分类标题、发布渠道等抽成 YAML 配置文件，让非开发人员也能调整日报结构。
- **监控流水线自身**：日报生成失败时，必须有兜底通知（如发送“日报生成异常”简讯），避免静默缺失。
- **逐步灰度，不要一次性全自动**：先产出草稿，人工快速确认一两天，再转为全自动发布，修复边缘案例。

## 总结

从原始日志到结构化日报，不是一个“用 GPT 总结一下”的简单 prompt 工程，而是一条需要处理多源异构数据、抑制噪声、约束输出的工程流水线。借助 OpenClaw 的编排能力和 MCP 的工具接口，可以将精力放在清洗逻辑和模板设计上，而不是陷入胶水代码的深渊。

上述方案已在内部运行两个月，日报可读性和准确率显著优于纯人工汇总，而且任何团队成员都能看清过去一天的全貌，站会时间缩短一半。如果你已有 OpenClaw 环境，可以尝试用类似方式搭建自己的日志到报告流水线，从最痛的一个数据源开始逐步扩展。
