## 背景：Agent 记忆的软肋

基于 OpenClaw 构建的复合 Agent（工具调用 / MCP 服务 / 插件链）在单次会话里表现稳定，一旦任务跨越多轮对话、多天执行，就会出现“你是谁、你要干什么”的漂移。每次上下文重建时，核心指令、已完成的进展、中间偏好都会丢失，只能靠外部重新注入 prompt，这既麻烦又容易出错。

常见的补丁方案是靠外挂向量库做 RAG，或在 .env 里塞一大堆提示，但这两种都无法让 Agent 即时更新自我认知。我们需要一种**轻量、可自我描述、能被 Agent 写回**的记忆文件——这就是 OpenClaw 设计中引入的 `IDENTITY.md`。

## 问题拆解：为什么需要可进化身份

在一个订单监控 Agent 的长时间运行里，我们观察到三个典型问题：

1. **任务目标静默遗忘**：越复杂的角色（需跨 MCP 服务查库存、调价、发通知），在运行 30 轮后容易把原始目标窄化成“完成最近一次函数调用”，丢失全局监控职责。
2. **偏好孤岛**：用户在某轮对话里调整过告警策略（比如“工作日 10 点前只上报严重级别”），下一轮新上下文里 Agent 又退回默认全量播报。
3. **风格震荡**：Agent 忽而过度解释、忽而偷懒省略，因为没有内化的风格约束。

本质原因在于，传统基于 system prompt 的身份是一次性注入的静态描述，不具备**被 Agent 自主维护的能力**。于是我们让 Agent 自己维护 `IDENTITY.md`，在需要时可回读，形成闭环。

## 做法：让 Agent 管好自己的身份文件

在 OpenClaw 中，`IDENTITY.md` 是一个项目根目录下的 Markdown 文件，Agent 通过文件系统工具（如 `read_file`、`write_file`）直接操作。实现步骤如下：

### 1. 初始化模板：先定义骨架
我们要求 Agent 在首次运行时生成一个结构化模板，核心分三部分：

```markdown
# 身份核心（永不自动修改）
- 角色：订单健康监控助理
- 固定原则：优先安全，再做优化；回复简洁不含糊。

# 动态记忆（Agent 可按需更新）
## 当前任务进展
- 最近已完成：全量补齐昨日 12:30-13:00 缺失的库存同步。
- 下一步：监控今日促销商品调价，等待 MCP/price-service 数据。

## 偏好与上下文
- 用户偏好：工作日 9-18 点仅报告严重告警；非工作时段静默。
- 常用服务：inventory-sync (MCP), price-service, notify-plugin。

# 已知陷阱
- 避免在节假日自动调价，必须人工确认。
```

静态核心约束了 Agent 的基本人格与不可违反的规则；动态记忆则记录进展和习得偏好；已知陷阱是从过往踩坑里总结的规则。

### 2. 更新时机与 prompt 设计
我们不会让 Agent 每轮对话都写文件，否则 token 消耗爆炸且易冲突。更新触发条件设为：

- **任务阶段完成时**（如一轮监控周期结束）
- **用户显式要求更新**（“记住这个偏好”）
- **遇到错误并被纠正后**（将教训写入“已知陷阱”）

更新 prompt 的关键要求是：**只对动态记忆做局部改写，不随便触碰身份核心**。我们使用了一个专门的 `update_identity` 原子工具，其系统指令为：

> 读取现有 `IDENTITY.md`，综合本次会话的进展、用户反馈，小心修改“动态记忆”部分的条目。保持结构不变，不要改动“身份核心”。若新增内容导致动态记忆超过 200 行，列出待淘汰的低价值条目并请求用户确认。

这样保证了文件不会无限膨胀。

### 3. 回溯与自检
在每轮新对话的 system prompt 头部，Agent 会被要求先读取 `IDENTITY.md`，确认“当前上下文是否与身份文件一致”。当发现历史记忆中有矛盾（比如“用户说早上 10 点前不打扰”但此刻是早 9 点紧急事件），则进入询问模式，而不是盲目遵循。

## 踩坑点与磨合

实践过程中积累了几个不太好看的经验：

- **死循环自我强化**：Agent 在某次故障报告中给自己加了“所有价格变动必须二次确认”，导致后续每次调价都变成三次确认链，用户几乎崩溃。最终我们加入了 **“偏好衰减机制”**：每个偏好条目在连续 5 轮对话未被提及后，自动标注为 `stale: true`，下次更新时优先淘汰。
- **窃取权限写坏核心**：开放文件写入权限后，一次权限混乱导致 Agent 误把“身份核心”也改了，把自己改成“幽默风格”，导致监控通知变成冷笑话。解决方案是在 `write_file` 前增加内容校验钩子，用正则检测 `# 身份核心` 区域是否被篡改，若被改动则拒绝写入并告警用户。
- **并发写冲突**：如果多个 Agent 实例共享同一个 `IDENTITY.md`，必然出现覆盖丢失。我们的处理很简单： **IDENTITY.md 属于单一主 Agent，子 Agent 通过专门的消息通道汇报摘要**，只有主 Agent 有写权限。需要多 Agent 协作时走专用记忆服务，不直接操作文件。

## 可复用的工程建议

在非 demo 场景中，粗暴给 Agent 文件读写权限会带来不可控风险。推荐以下实践：

1. **拆分为静态+动态两文件**：核心为 `CORE.md`（只读），演进记忆为 `IDENTITY.md`（可写）。降低误改成本。
2. **结构化存储**：动态记忆部分采用 YAML front-matter 或 JSON 代码块，结构化字段比自然语言更利工具解析与裁剪。例如用 `preferences.alert_level` 清晰表达，而不是散落在段落里。
3. **硬性容量门限**：在 Agent 更新工具中强制检查动态记忆总 token 数（用 tokenizer），超过阈值自动触发摘要压缩，将旧条目浓缩为“历史概要”，丢弃细节但保留教训。
4. **人工回滚点**：每次写入前自动生成 `IDENTITY.backup.{timestamp}.md`，并限制最多保留最近 3 个快照。回滚时只需替换。
5. **隐私边界**：应告知用户，`IDENTITY.md` 中会持久存储偏好，避免将账户凭证、API key 等敏感信息写入动态记忆。技术上可通过脱敏扫描做兜底拦截。

这些做法已被验证可让 Agent 连续运行超过 70 天，无需人工重新注入 prompt，且任务连贯性显著优于每次清零的基线。

## 总结

`IDENTITY.md` 方案本质上是一种**基于文件的自我演化记忆**，成本极低，容易理解和干预。对于长期运行的任务型 Agent，它能解决“每次对话都重启脑子”的根本缺陷。但它也带来了新的工程责任：需要像管理数据库 schema 一样管理身份文件的结构、授权与压缩策略。

在 OpenClaw 生态里，已经有社区实现将动态记忆部分自动与 MCP 的长期向量库做近邻互补（近期进展热数据放 IDENTITY.md，长尾知识放向量库），进一步减轻膨胀并提升检索精度。如果你的 Agent 已经跨过了“一次性玩具”的阶段，值得在项目里认真设计它的身份文件和演进机制。
