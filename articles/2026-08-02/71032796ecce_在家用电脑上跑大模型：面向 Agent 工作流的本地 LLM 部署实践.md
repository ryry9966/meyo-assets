## 背景

把大模型完全跑在本地，对经常折腾 OpenClaw、MCP、插件和自动化流水线的工程师来说，诉求其实非常具体：

- **隐私与数据主权**：API 密钥、内部文档、自动化生成的中间上下文不再离开本机。
- **低延迟与离线可用**：Agent 回路里的推理、工具调用、反思阶段，不需要每次都跨公网。
- **成本可控**：一次硬件投入后，不再按 token 计费，适合高频次的自动化脚本与长链 Agent。
- **可定制性**：可以自由更换量化模型、调整上下文窗口、注入领域微调权重，完全按工程需求裁剪。

不过，把“在家用电脑上跑大模型”具体落地成一个稳定的 Agent 后端，中间有很多工程细节，不是装一个 LM Studio 就能收工的。

## 现实问题

常见的家用环境硬件：一块 RTX 3090/4090（24 GB 显存），或者 Apple Silicon Mac（统一内存 32-64 GB）。这决定了我们不可能原生跑全量 70B+ 模型，必须依赖量化。但也因此面临：

- **模型选型分歧**：7B/13B/30B/量化 4bit/8bit，不同任务（指令遵循、代码生成、长上下文工具调用）需要不同折中。
- **推理性能瓶颈**：并发请求、提示处理速度、上下文预填充时间，都会直接影响 Agent 每一步的耗时。
- **上下文窗口压力**：Agent 在多轮对话和工具调用中，历史消息极易膨胀，超过原生 4k/8k 窗口。
- **API 兼容性**：大多数自动化框架通过 OpenAI-compatible API 接入模型，本地推理服务器能否平滑兼容，决定集成成本。

## 实践步骤

### 1. 选择推理后端

对于 24 GB 显存的家用卡，当前最务实的组合是：

- **llama.cpp**（配合 GGUF 量化模型）：显存利用精准，KV 缓存可量化，支持 CUDA/Metal 加速，社区维护积极。
- **Ollama**：封装了 llama.cpp，安装零门槛，提供 OpenAI 兼容 API，适合快速接入 OpenClaw 这类框架。
- **vLLM**（如有高吞吐需求）：对 PagedAttention 支持好，但显存占用比 GGUF 略高，适合 13B+ 模型在 24 GB 卡上跑 AWQ 量化。

入门推荐 **Ollama**：一条 `ollama run qwen2.5:14b-instruct-q4_K_M` 就能把 14B 模型量化后塞进 24 GB 显存，推理速度可达 30–50 tokens/s。

### 2. 模型选择与量化

**面向 Agent 场景，模型必须擅长函数调用、指令遵循和长上下文**。实践下来比较适合家用卡的几个选择：

| 模型 | 参数量/量化 | 显存需求 | 适用场景 |
|------|--------------|----------|----------|
| Qwen2.5-14B-Instruct | Q4_K_M | ~9 GB | 中文工具调用、代码生成 |
| DeepSeek-Coder-V2-Lite | Q4_K_M | ~10 GB | 代码补全、结构化输出 |
| Mistral-Nemo-12B | Q4_K_M | ~8 GB | 多语言指令、快速原型 |
| Llama-3.1-8B-Instruct | Q4_K_M | ~5 GB | 轻量级 Agent，低延迟 |

如果显存更紧张，8B 模型也是可用的，但复杂工具调用容易出错，需配合严格的 JSON Schema 约束。

### 3. 接入 OpenClaw / Agent 框架

以 OpenClaw 为例，本地模型通过 Ollama 提供服务后，只需在配置中将 `OPENAI_API_BASE` 指向 `http://localhost:11434/v1`，`model` 设置为 `qwen2.5:14b`。这样 Agent 的推理请求就全部走本地，延迟通常比 API 更低。

如果遇到 Ollama 默认 2048 上下文不够用，可以创建自定义 Modelfile：

```dockerfile
FROM qwen2.5:14b
PARAMETER num_ctx 16384
```

然后 `ollama create qwen2.5-16k -f Modelfile`。**注意**：扩大上下文会成倍增加显存占用（KV 缓存），14B 模型在 16k 上下文时显存可达 18 GB+，24 GB 卡勉强可跑，但要预留余量给 Agent 工作内存。

### 4. 做 MCP 服务器时的优化

如果你把本地 LLM 包装成一个 MCP 服务器供其他 Agent 调用，推荐使用 `llama-cpp-python` 直接开发 MCP 工具。这样能精细控制：

- 启用 `flash_attn` 或 `cache_8bit/4bit` KV 量化，降低显存。
- 设置 `verbose=False`，减少日志开销。
- 用 `asyncio` 并发处理推理请求，避免阻塞其他 MCP 调用。

## 常见踩坑点

1. **Ollama 首次加载模型极慢**  
   GGUF 模型文件很大（~8-10 GB），首次启动需要将权重加载到显存，耗时 30–60 秒。解决方案：保持 Ollama 常驻服务，或设置 `OLLAMA_KEEP_ALIVE=24h` 环境变量让模型常驻。

2. **上下文溢出导致 Agent 行为异常**  
   当 Agent 的提示+历史消息超过模型上下文窗口时，Ollama 默认不会报错，而是静默截断早期内容，导致模型“失忆”或工具调用参数错误。务必在 Agent 端记录当前上下文长度，并在接近窗口上限时主动压缩或切换对话。

3. **量化模型的指令遵循能力下降**  
   Q4 量化可能削弱模型对复杂 JSON Schema 的遵循能力。建议用 `outlines` 或 `guidance` 库在推理时强制约束输出格式，而不是完全依赖模型自发产生合法 JSON。

4. **Mac 统一内存的带宽瓶颈**  
   M1/M2 Max 的 GPU 带宽远低于独立显卡，跑 14B Q4 模型时速度会降到 15–25 tokens/s。对于速度敏感的多步 Agent，建议用 8B 模型或使用 MLX 框架优化的版本。

## 可复用建议

- **建立一个“本地模型自检清单”**：每次更换模型后，用一组标准的函数调用测试集（例如包含并行工具调用、必填参数缺失等边界情况）验证性能，避免在自动化流水线中突然崩掉。
- **显存不够时优先压缩上下文而非换更小模型**：Agent 场景下，小模型的工具调用正确率往往比大模型短上下文更差。
- **用 System Prompt 固化工具协议**：将可用工具的 description、入参 Schema 写入系统提示，减少每个 user turn 的 token 消耗。
- **监控指标**：对推理耗时、首次 token 时间、上下文长度设置日志，便于调优流水线吞吐。

## 总结

在家用电脑上部署本地 LLM 为 Agent 工作流服务，可行但需要工程化取舍。核心思路是用 GGUF 量化模型 + Ollama 提供兼容 API，并在上下文管理、输出约束和显存分配上做精细控制。这样构建出的本地推理节点，不仅能无缝接入 OpenClaw、MCP 等自动化框架，还能让整套系统摆脱对云端 API 的依赖，真正做到数据在本地、决策在本地、故障在本地可排查。
