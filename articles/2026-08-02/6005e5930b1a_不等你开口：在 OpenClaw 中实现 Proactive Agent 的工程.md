## 背景：为什么不够“主动”就总差一口气

大多数基于 OpenClaw 搭建的助手，交互模式仍旧是“我问你答”。用户不提问，Agent 就静默；消息框不亮，流程就不走。但在真实生产环境里，很多高价值场景恰恰需要反过来——服务器异常了，助手应该自己张口；日报该出了，不等任何人来敲指令；依赖数据源有了变化，直接驱动下游动作。

在 OpenClaw/Agent/MCP/插件这套生态里，我们已经有能力把助手变成立足后台的服务，而不是一个聊天框。这就是 proactive 能力：基于事件或时间触发的感知—决策—执行闭环。

这篇文章不聊概念，只讲我们在 OpenClaw 上让助手“自己动起来”的工程做法、踩过的坑，以及可复用的设计原则。

## 问题拆解：主动的本质是一套可控的自动机

让 AI 助手主动办事，面临三个核心难题：

1. **触发可靠性**：事件如何不漏、不重、不风暴式涌入 Agent？
2. **决策准确度**：给 Agent 的上下文有限，它怎么在无人追问时做出正确判断？
3. **执行安全性**：自动调用工具、操作外部系统，边界在哪里？误操作怎么兜底？

解决这三个问题，需要的不是换个模型，而是重新设计助手的工作流结构。

## 做法：感知—决策—执行三层分离

下面是我们围绕 OpenClaw 搭建 proactive 助手的一套工程步骤。

### 1. 感知层：用 MCP 把外部事件标准化

我们不直接在 Agent 主循环里搞定时器或轮询，而是把所有事件源统一抽象成一个 **MCP 事件服务**。这个服务可以：

- 通过 MCP 的 `resources/subscribe` 机制，把 Webhook、消息队列、定时 cron 的结果推送到 OpenClaw 的会话调度器。
- 也可以用更简单的方式：实现一个 MCP server，暴露一个 `listEvents` 工具和一个 `waitForNextEvent` 的长轮询工具，由 OpenClaw 的 scheduler 周期调用。

关键是把不规则的外部世界，封装成**结构化的 `Event` 对象**：

```json
{
  "event_id": "evt_20250315_001",
  "source": "monitoring/webcheck",
  "type": "service_down",
  "payload": { ... },
  "timestamp": "2025-03-15T08:22:00Z"
}
```

这样做的好处是：后面所有决策只依赖这个标准化接口，更换事件源不影响 Agent 逻辑。

### 2. 决策层：用精简 Prompt + 工具链做到“有限判断”

在 OpenClaw 中，我们为 proactive 场景单独注册一个 **Background Agent**，它的 System Prompt 很简单：

> 你是后台值守助手。你会接收到一系列事件。对每一个事件，用可用工具收集必要信息，然后判断是否需要执行动作。如果不需要，回复 `NOOP`；如果需要，调用对应工具并说明理由。

这里的要点是：**不要让 Agent 无边界发挥**。只给它几个选项：`alert`（发送告警）、`report`（生成报告）、`ticket`（创建工单）、`NOOP`（忽略）。所有选项都必须通过调用预定义工具来实现，不允许自由生成文本当成执行结果。

同时，为了防止上下文膨胀，我们只让 Agent 在每次决策时携带最近 1–3 个事件加上上一次的动作结果摘要。使用 OpenClaw 自带的 `session.summarize()` 或自定义的内存裁剪，把长期记忆压缩进一个不超过 300 tokens 的状态块。

### 3. 执行层：带确认的自动机 + 干跑模式

真正危险的不是 AI 会说错话，而是它自动调了危险操作。我们对自动执行做了三层防护：

- **分级权限**：只读工具（查询状态、拉取日志）允许自动执行；涉及变更的工具（重启服务、修改配置）必须二次确认或转交工单。
- **干跑模式**：在启动初期，所有写操作先走 `dry-run`，把本应执行的命令发给人类监查通道，观察一天无异常再逐步放开。
- **执行轨迹**：每一次自动动作都记录到审计日志，并关联原始 event_id，方便回溯。

## 踩坑点：以为稳了，结果摔在细节上

**事件风暴导致大模型调用爆炸**

刚开始我们把所有告警直接推给 Agent，结果一次故障瞬间冲入 200+ 事件。Agent 调用费用飙升，并且延迟导致处理积压。后来在感知层加入**去重窗口（5秒合并相同事件）** 和**频率限制（每 Agent 最多 10 事件/分钟）** 才解决。

**上下文悄悄把旧逻辑冲掉**

当事件流和动作历史逐渐变长，Agent 开始漏掉关键前提。例如服务已恢复，它却因为上下文里残留的旧告警又发一条误报。解决办法是强制清理上下文：“每次新事件进来，只保留上一次的决策摘要和当前事件”，即无情地遗忘。

**MCP 传输层里的“假连接”**

MCP server 使用 SSE 推送事件时，遇到网络抖动容易断开，但客户端没有及时感知，造成事件积压后一次性涌入，再次触发风暴。我们改为 **“主动拉取 + 心跳检测”** 模式，放弃纯 SSE 推送，稳得多。

## 可复用建议

- **感知、决策、执行三层解耦**，事件源变更不影响 Agent 逻辑，Agent 逻辑不影响工具安全。
- **让 Agent 做选择题，不做论述题**：把可执行动作限制在一组工具上，输出只能是工具调用结果。
- **一切自动操作先走干跑**，哪怕模型声称“置信度 99%”，工程不相信概率。
- **严格控制上下文大小**，用结构化摘要替代长对话历史，避免干扰。
- **为每个事件打上唯一 ID**，贯穿所有日志与动作，排障时能快速还原因果链。

## 总结

Proactive 不是给 Agent 加一个“自动回复”开关，而是为它加装一套可控的感知—执行系统。在 OpenClaw 和 MCP 的组合里，我们有足够底层的调度与工具能力来支撑这种模式。实现之后你会发现，助手不再只是听令的机器人，而变成了能前瞻、能预警、能闭环的协作节点。前提是：你给它画的边界足够清晰。
