## 背景：为什么“记忆”比“理解”更难

在 Agent 和自动化工作流里，我们很快会撞到一堵墙：每次对话都是全新的开始。你可以让 LLM 理解一次性的指令，但让它记住你喜欢用 `yaml` 而不是 `json` 配置工作流，记得你习惯把日志写到 `/tmp/agent-debug`，或者记住某个 MCP 工具的参数组合偏好，就完全是另一回事。

这不是模型能力的缺失，而是架构上的缺失。大多数 Agent 框架把“记忆”简化为把整段对话塞进上下文窗口，但随着交互轮次增加，窗口会爆，成本会炸，而且长对话里的噪声会让模型产生理解漂移。真正可用的记忆系统，需要被当作独立的工程组件去设计，而不是靠更长的 prompt。

## 问题拆解：你要记住什么

动手之前，先区分三种记忆类型：

1. **会话记忆**：当前任务上下文里的临时状态，比如“刚才那个错误日志再给我看一遍”。  
2. **事实记忆**：可结构化的事实或偏好，比如“用户 A 的默认部署环境是 staging”。  
3. **过程记忆**：跨会话的行为模式，比如“每次创建 PR 前你都会让我先跑一遍 lint”。

多数人只实现了会话记忆，把聊天记录全量回填。这相当于把短期记忆当长期记忆用，既不经济也不精准。工程上需要把事实记忆和过程记忆提取出来，存到可查询的存储里，在需要时按需注入上下文，而不是无脑拼接。

## 做法：基于 MCP 的轻量记忆服务

在 OpenClaw 生态里，最自然的方式是把记忆做成一个 MCP 服务，这样任何 Agent 都可以通过标准协议读写偏好。下面给一个可复现的实现路径。

### 1. 设计记忆条目模型

把记忆条目设计为最小可检索单元，结构大致如下：

```json
{
  "id": "mem-001",
  "type": "preference",
  "scope": "user:alice",
  "key": "deploy_target",
  "value": "staging",
  "metadata": {
    "source": "conversation",
    "confidence": 0.9,
    "updated_at": "2025-01-15T10:00:00Z"
  }
}
```

`scope` 可以区分用户级、项目级、会话级。`type` 区分偏好、事实、工作流模板等。`confidence` 用来支持后续的自动清理和覆写策略。

### 2. 实现 MCP 工具接口

暴露三个工具：

- `remember(scope, key, value, metadata?)` – 显式写入记忆
- `recall(scope, key?)` – 按 key 精确查询，或列出 scope 下所有记忆
- `forget(scope, key)` – 显式删除

关键设计点：**记忆的写入最好不是全自动的**。让 Agent 在判断某条信息值得长期记忆时主动调用 `remember`，而不是把每一轮对话都转成向量存起来。这能极大降低存储噪音和检索成本。你可以在系统 prompt 里加一条指令：

> 当你发现用户明确表达或反复表现出某个偏好、配置习惯、固定工作流时，使用 remember 工具持久化该信息。

### 3. 记忆注入策略

每次新会话启动时，Agent 先用 `recall` 拉取当前 scope 的记忆，然后将其以紧凑格式注入系统消息：

```
[用户偏好]
- deploy_target: staging
- log_path: /tmp/agent-debug
- preferred_config_format: yaml
```

不要直接把 JSON 拍进去，做过一轮范式压缩，可以减少 token 占用。如果记忆条目很多（比如超过 20 条），需要加一层相关性过滤，只注入与当前任务可能相关的那部分。简单做法是用 key 做关键词匹配，复杂做法可以接一个轻量 embedding 检索。

### 4. 自动发现偏好的增强

如果你想让 Agent 具备“被动记忆”能力（即不用用户显式说“记住我”），可以在每次交互结束时做一道离线判断：用廉价模型或规则引擎分析当前对话，发现新的潜在偏好后，以低置信度写入 memory，等后续交互中被确认后再提升置信度。这能大幅提升体感智能，但要小心噪音积累。

## 踩坑点

1. **把偏好当全局事实用**  
   Alice 的 `deploy_target` 在项目 A 可能是 `staging`，在项目 B 可能是 `production`。Scope 设计必须支持项目级隔离，否则 Agent 会在不同项目里串用偏好，造成灾难性后果。

2. **记忆污染**  
   自动记忆很容易写入过时或错误信息。如果用户某次说“先试一下 production”，你不该把它当成长期偏好。解决方案：要求 Agent 在调用 `remember` 时附上合理的 `confidence`，并定期清理低于阈值的低置信度条目，或由用户确认。

3. **上下文窗口膨胀**  
   即使每条记忆很精炼，当 scope 下积累几十条时，注入后的 token 开销依然可观。务必做上限截断（比如最多注入 15 条），并按最近更新时间或使用频次排序，优先注入热门记忆。

4. **遗忘机制缺失**  
   没有遗忘能力的记忆系统会变成垃圾堆。最好实现一种软过期：记忆项超过 N 天未被访问（或未被相关对话引用），自动降低置信度或归档到冷存储，不再注入上下文。

## 可复用建议

- **从显式记忆开始**：先让用户说“记住我习惯用 xxx”，Agent 显式调用工具存下来。这条路成本最低，也最可控。
- **渐进式自动化**：等显式记忆稳定后，再引入规则或模型判断的自动记忆，但始终保留用户可审查、可删除的接口（比如通过一个 `/memory` 命令）。
- **Scope 分层**：至少区分 `user`、`project`、`session` 三级。全局事实尽量少放，大部分偏好绑定到项目 scope。
- **格式压缩**：记忆注入时不要带完整 JSON 结构，用 `key: value` 列表加极简注释，优先节省 token。
- **记忆可解释**：在 debug 模式下让 Agent 输出“当前注入了哪些记忆”，方便排查误读。

## 总结

Agent 记忆系统不是一个 prompt 工程问题，而是一个数据工程问题。把记忆做成 MCP 服务，让 Agent 按需查询和更新偏好，本质上是在 Agent 状态空间里引入了一层结构化持久化。这套做法不需要复杂的外部依赖，一个简单的 key-value 存储加上合理的 scope 和自动压缩策略，就能显著提升 Agent 在长期交互中的一致性和可靠感。

真正好的记忆不是让 AI 知道更多，而是让它在该闭嘴的时候闭嘴，在该出现你偏好时不假思索地做对选择。
