## 背景

在 OpenClaw、Agent、MCP 插件和自动化脚本里，我们经常遇到一个需求：任务提交之后，调用方需要知道它是否还活着、进度如何、什么时候结束。

比如你在 OpenClaw 里触发一个长时间运行的 Agent 任务，或者在 MCP server 里调用一个外部工具，前端/宿主程序不能一直傻等。它需要一个“心跳”机制来同步状态。

这个心跳机制通常有两种实现路径：

- **轮询**：客户端每隔一段时间请求一次状态接口。
- **推送**：服务端通过 SSE、WebSocket 或 webhook 主动把状态变化推给客户端。

两者没有绝对优劣，但选错方向会带来资源浪费、连接不稳定、状态丢失等问题。下面结合实际落地经验，聊聊怎么取舍。

## 问题

轮询的优点是简单、无状态、容易通过网关和负载均衡。缺点是频率不好把握：太慢则状态滞后，太快则空转请求多，服务端压力大。

推送的优点是实时性好，但引入连接管理成本：断线重连、心跳保活、消息丢失、幂等处理、网关超时等。很多团队一开始就上 WebSocket，最后发现大部分时间是在维护连接，而不是解决业务问题。

所以在做 heartbeat 设计时，先问三个问题：

1. 状态变化频率高吗？是几秒一变，还是几十秒甚至几分钟一变？
2. 对延迟敏感吗？必须 1 秒内感知，还是 5~10 秒也可以接受？
3. 部署环境是否对长连接友好？有没有 Nginx、API 网关、Serverless 限制？

## 做法/步骤

### 1. 先设计统一的任务状态结构

无论轮询还是推送，建议任务状态最少包含三个字段：

```
status: pending | running | succeeded | failed
version: 42
updated_at: 2026-01-01T12:00:00Z
```

`version` 是自增版本号或时间戳，用于判断状态是否发生变化。它可以作为轮询的轻量判断依据，也可以作为推送事件的去重标识。

### 2. 低频任务优先用轮询

如果任务执行周期在几十秒以上，且调用方不是强实时场景，轮询是最稳的选择。

例如 OpenClaw 插件触发一个批量数据清洗任务，客户端每 5 秒请求一次 `/tasks/{id}/status`，服务端返回当前状态和 version。客户端发现 version 没变，就继续等待；变了就更新 UI 或进入下一步。

这样做的好处是：

- 接口无状态，容易横向扩展。
- 客户端生命周期好管理，挂起或退出不会影响服务端。
- 不需要维护长连接。

### 3. 高实时性场景用 SSE，而不是 WebSocket

如果任务状态变化快，或者需要把 Agent 内部事件实时推给前端，优先选 SSE。

示例：OpenClaw 里一个 Agent 调用 MCP 工具，前端需要实时看到步骤日志。服务端可以提供一个 `/tasks/{id}/events` 的 SSE 端点，持续输出 `progress`、`log`、`done` 事件。

SSE 比 WebSocket 更适合这个场景，因为：

- 它本质是 HTTP 单向流，过网关和代理更容易。
- 客户端自动处理重连，配合 `Last-Event-ID` 可以续传。
- 服务端实现简单，不需要处理双向消息协议。

只有在客户端还需要向服务端发送指令时，才考虑 WebSocket。

### 4. 做混合模式

一个比较务实的方案是：

- 任务创建后返回 `status_url` 和 `stream_url`。
- 普通状态同步走轮询。
- 关键节点（任务结束、失败、需要人工介入）通过 SSE 或 webhook 推送一次。

这样做可以在延迟和复杂性之间取得平衡。

## 踩坑点

### 1. 轮询过密导致服务端压力

如果轮询间隔设为 1 秒，1000 个客户端就是 1000 QPS。即使没有数据变化，也会产生大量无效请求。

解决方式：

- 客户端做指数退避，比如 2 秒、4 秒、8 秒，最大 30 秒。
- 加上随机 jitter，避免同步请求风暴。
- 支持 ETag/If-None-Match，服务端根据 `version` 返回 304，减少传输体积。

### 2. 推送连接被网关静默断开

很多 Nginx / ALB / Serverless 平台对 HTTP 长连接有超时限制，可能 60 秒或更短。SSE 或 WebSocket 连接会静默断开，客户端还不知道。

解决方式：

- 在 SSE 里定期发送注释行 `: ping` 或空事件作为心跳。
- 调整网关的 `proxy_read_timeout`。
- 客户端侧做超时检测，发现连接无响应则主动重连。

### 3. 推送消息丢失

断线重连后，如果客户端没有记录偏移量，会漏掉中间状态。例如 Agent 刚好在断线期间从 `running` 变成 `failed`，重连后只收到 `succeeded`，就会造成误判。

解决方式：

- SSE 使用 `Last-Event-ID` 和自增 `event_id` 做断点续传。
- 客户端重连后，先拉取一次当前完整状态，再继续接收事件。
- 所有事件处理要幂等，根据 `version` 去重。

### 4. 多实例部署时，推送需要额外基础设施

如果 OpenClaw 或 MCP server 部署了多个实例，客户端可能连到 A 实例，但任务状态由 B 实例更新。此时 A 实例并不知道要推送什么。

解决方式：

- 使用 pub/sub 中间件（如 Redis、NATS）广播任务事件。
- 或者为推送连接做 sticky session，让同一任务的请求落在同一实例。
- 如果暂时没有消息中间件，优先用轮询，因为轮询天然无状态。

### 5. 插件客户端生命周期管理

OpenClaw 插件可能在移动端、桌面端或后台运行，随时会被挂起或关闭。如果推送连接管理不当，会出现连接泄漏。

解决方式：

- 明确连接的所有权，谁创建谁关闭。
- 页面不可见时，可以考虑暂停推送，改为恢复时拉取一次状态。
- 对连接数设置上限，避免爆端口。

## 可复用建议

- **默认轮询，按需推送**。先让流程跑通，再根据实际延迟和资源消耗决定是否加推送。
- **状态接口要轻**。返回数据尽量只含状态、version、updated_at，避免每次把大段任务日志都拉下来。
- **事件设计要幂等**。客户端必须能安全处理重复事件，版本号是最好的去重依据。
- **为 MCP server 增加 healthz 和 events 端点**。healthz 用于快速检测存活，events 用于可选推送。
- **监控三个指标**：轮询空转率、推送重连次数、状态同步延迟 P95。这些指标能帮助你判断是否选错了方案。

## 总结

AI 助手的 heartbeat 设计，核心不是纠结“轮询好还是推送好”，而是根据任务频率、延迟要求、部署拓扑来决定。

一个务实路径是：

1. 低频任务，先用轮询，version + ETag 优化。
2. 高频实时场景，上 SSE，并用 `Last-Event-ID` 和心跳保活。
3. 只有明确需要双向指令时，才切换到 WebSocket。
4. 无论哪种方案，都要处理重连、幂等和网关超时。

先跑通，再优化。很多项目真正需要的，可能只是一个带 version 的轻量轮询接口。
