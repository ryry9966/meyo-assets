最近社区里流传出一组 Claude 两个新模型的实测结果，来源指向 36kr 的报道。最抓眼球的有两件事：空间推理表现强到“封神”，以及测试过程中算力被直接榨干。很多讨论把这两件事当成同一个新闻的两个侧面，但技术上看，它们更像一对因果关系：正是空间推理这种任务形态，把大模型的推理成本和算力消耗推到了一个新台阶。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/87c8f2df1e9a2c67.png)

## 一、空间推理：不是“看图说话”，而是“脑内搭积木”

先厘清一个概念。我们常说的视觉理解，很多模型已经做得不错，比如识别图片里有什么、描述场景、回答“这个人穿什么颜色衣服”。但空间推理（spatial reasoning）是另一层能力。

- 普通视觉问答：识别物体、属性、粗略位置
- 空间推理：理解物体之间的相对方位、旋转、遮挡、支撑关系，甚至从二维图片推三维结构
- 典型问题：把左边的盒子顺时针转 90 度，小球会滚到哪个角落？如果从鸟瞰视角看，这三个积木的堆叠顺序是什么？

为什么难？因为它要求模型在“脑内”维护一个不直接可见的几何状态，并在这个状态上做多步变换。这更像人闭着眼睛想象一个物体转过去之后的样子，而不是简单匹配图片特征。早期视觉语言模型对空间关系并不敏感，经常把左右、前后、遮挡顺序搞混；现在新模型如果确实在未见过的空间任务上大幅提升，说明它正在接近一种更接近“世界模型”的能力。空间推理一旦变强，对机器人抓取、CAD 设计、自动驾驶、具身智能都有直接价值。

## 二、两个新模型“实测流出”：高光表现值得冷静看待

“实测流出”通常意味着有人通过内部 API、灰度版本或第三方代理拿到了未公开模型，并把测试 case 发到网上。这类信息有参考价值，但也要警惕评测噪声。

1. 样本偏差：流出 case 往往只挑成功的高光时刻，失败样本很少传播
2. 测试条件不统一：温度、系统提示、上下文长度、图片分辨率都可能影响结果
3. 版本不确定：所谓的“两个新模型”，可能是两个不同 checkpoint，也可能是同一模型在不同配置下的表现

这不是说流出的结果没意义。恰恰相反，灰测常能提前暴露模型的真实倾向：它是否稳定、是否过度拒绝、是否在空间推理上出现“灵光一现但不可复现”的情况。只是别把几个 case 当成采购依据。

## 三、为什么空间推理会把算力“榨干”？

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/fda0cb59e8badcf0.png)

这是这次讨论里最值得拆开看的部分。空间推理吃算力，不是玄学，而是几件事叠加的结果。

1. 隐式几何模拟：模型处理空间问题时，内部可能在特征空间中不断更新位置和姿态表示。这种隐式模拟每一层都要重新计算，计算量远高于简单识别。
2. 长链推理：空间题往往需要“先旋转、再判断遮挡、最后比较距离”的多步过程。每一步都转化为一串 token，输出长度一上去，Transformer 的 attention 计算量按序列长度近似平方增长。
3. 视觉 token 数量大：一张高分辨率图片经过 patch 切分后，可能产生数千个视觉 token。空间推理又常常需要反复引用图像的局部区域，导致 KV cache 迅速膨胀，显存和带宽都被拉高。
4. 并发灰测放大资源压力：当一群人同时用复杂空间题测试灰度模型，服务端很容易出现排队、限流甚至直接报错。所谓“算力榨干”，部分是模型本身的成本结构，部分是测试方式造成的瞬时高峰。

举一个粗略的估算：一次普通图片问答可能产生几百到一千多个 token；一次多步空间推理，如果模型边思考边输出，很容易超过几千 token。两者对算力的需求完全不在一个量级。所以“算力榨干”不是某个模型的缺陷，而是空间推理作为高计算密度任务的必然结果。

## 四、能力之外：更该关注的三件事

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/8f5b21e485e05aee.png)

空间推理封神固然值得兴奋，但工程和商业上，还有三个更实际的问题。

- 成本结构变化：如果空间推理成为高频能力，API 单价、限流策略、免费额度都会被重新设计。高昂算力最终会传导到使用者。
- 能力与延迟的平衡：空间推理强，但响应时间可能明显变长。实时场景下，能力再强也不能接受几秒甚至十几秒的等待。
- 评测可复现性：灰度阶段的高光表现，在正式版上可能因为服务端量化、安全对齐或推理优化而打折扣。落地前必须用自己的固定评测集重新验证。

这几件事比“封神”更值得记下来。热点会过去，成本曲线和推理延迟不会。

## 收尾：三条冷思考

1. 别把流出 case 当采购依据。拿 20～30 个固定空间推理题，在同等条件下对比不同模型，结果会更接近真实水平。
2. 做空间推理类应用前，先算 token 预算。把单次调用可能产生的输入、输出 token 数和预期并发量代入成本公式，再决定是否用大模型、是否加缓存或规则预处理。
3. 区分“研究版能力”和“生产版能力”。很多惊艳表现来自未量化的高算力版本，正式 API 上线后可能为了成本与延迟做出调整。等官方系统卡和定价出来再下结论，通常比追灰度测试更稳妥。
