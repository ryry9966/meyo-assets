最近社交平台上流传一组 Claude 新模型的黑盒实测：给一张倾斜角度的房间照片问物体相对位置、让模型在网格地图里规划最短路径、把家具布局转成俯视坐标……结果空间任务完成度很高，但 API 响应明显变慢，部分账号并发被限流。"空间推理封神，算力直接榨干"这一说法不胫而走。本文不猜具体版本号，只从技术机制和工程账本聊聊：为什么空间推理这么难？这轮表现传递了什么信号？算力到底花在哪里？

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/9a1e7bf0a035d946.png)

## 空间推理为什么是大模型的短板？

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/813c2b73b468337d.png)

空间推理不等于"看懂图片"。看懂图片很多时候是识别物体、描述场景、提取文字；空间推理要求模型在脑子里建一个可操作的地图。

- 大语言模型的底子是序列预测，文字 token 是一维的。空间关系天然需要二维甚至三维结构：遮挡、距离、旋转、坐标系变换。
- 主流考试长期偏向文字知识与符号逻辑。MMLU、GPQA 这类 benchmark 再难，也没有逼模型判断"从门口进去，左边第三把椅子是否在窗户前方"。
- 多模态模型虽然加了视觉编码器，但图片进入模型前会被切成 patch，再转成 tokens。切块的粒度、排列顺序和位置编码，都会影响模型对整体空间结构的理解。一旦几何连续信息在 patch 化中丢失，模型就只能在"局部纹理"里拼凑关系。
- 一个典型硬例子：要回答"站在书桌后面能不能看到电视"，模型需要估计相机位姿、判断视线遮挡、理解"后面"和"前方"的方向词，最后映射到俯视坐标。这种任务很难靠大规模文本语料死记硬背。
- 从 2023 年 GPT-4V 到后续多模态模型，空间问答屡屡翻车。很多模型能描述图片，却分不清左右、前后、东西南北。这次 Claude 新模型被热议，本质是它似乎在"看图说话"和"空间建模"之间跨过了一个台阶。

## 这轮实测流出的三个信号

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/23a5d659afc2b7c9.png)

社交平台上的零散实测并不严谨，但如果把这些信息拼起来，可以看到三个一致的方向。

1. **少样本空间问答明显变强**：在室内场景问题中，类似"站在书架左前方能不能看到窗边的沙发"这类问题，流出结果显示准确率接近人工标注水平。模型不再给出抖动的坐标，而是能输出稳定的 JSON。
2. **长链路空间规划不崩了**：实测者让模型先解析房间地图，再规划清洁机器人路径，再处理旋转后的布局。多步空间推理中，中间步骤很少出现"东西南北搞反"、坐标跳变或物体位置漂移。
3. **推理时间显著拉长**：相同 prompt 下，新模型的输出明显变慢；当图像 token 数量增加时，部分账号更容易触发限流。所谓"算力被榨干"，从 API 侧看就是并发上限降低、首 token 延迟升高、账单上涨。

这些信号背后有一个共同点：模型不再只靠"猜"，而是开始显式或隐式地构建空间中间表示。

## 算力是怎么被"榨干"的？

![img3](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/b57160412b4e39f1.png)

空间推理进步的同时，资源消耗也在同步上升。这不是简单的"模型更大"，而是任务形态变了。

- 空间推理通常不是一次生成答案，而是先拆任务：图像理解 → 坐标标注 → 关系判断 → 路径搜索。过程中的中间 token 数量会成倍上升。
- 一张高分辨率图片在视觉语言模型里经常被切成一两千个 patch，转化为大量上下文 token。空间任务还需要保留 patch 之间的位置关系，模型不能随意降采样，否则坐标系会糊掉。
- 如果新模型使用了 test-time compute，也就是推理阶段多做搜索、采样或自我校验，那么单个请求占用的 GPU 时间会从"秒级"变成"十几秒甚至几十秒"。
- 算一笔粗账：一次室内 3D 问答若输出 2000 token 推理链，再叠加约 1024 个 image tokens，序列长度轻松到 5k-8k。在高并发下，集群最先爆的可能不是算力本身，而是显存里的 KV cache。
- 业内粗略估计，视觉语言模型的单张图片可相当于约 500-1500 个 text tokens 的上下文开销。具体数字因分辨率、切分策略和编码器结构而不同，但图片越多、分辨率越高，成本上涨几乎是确定的。
- 直观感受上，这就像请一位空间规划师：表格题他扫一眼就答，空间题则需要铺开图纸、画辅助线、反复确认。活是更好了，工时也更长了。

## 给开发者的三条冷思考

![img4](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-26/a0b646f53bbb1213.png)

1. **别盲目上最强模型**：先做任务分级。简单文本、摘要、分类继续用轻模型；空间问答、图纸理解、路线规划再调用强模型。把最贵的算力留给真正需要空间建模的场景。
2. **把空间问题结构化**：不要整张大图直接丢给模型。先做目标检测、裁剪、坐标标注，再让模型做关系推理。减少无效 image tokens，往往比换模型更划算。
3. **给推理设置边界**：如果产品涉及实时路径规划或 3D 场景，设置最大推理步数、缓存常见场景、对高并发请求做降级。算力是物理上限，不是充钱就能无限拓展。

模型越聪明，账单越诚实。空间推理进步是一次能力升维，但工程上的取舍永远不会缺席。下一次当你看到"封神"级实测时，不妨先问一句：这个能力的单位成本是多少？
