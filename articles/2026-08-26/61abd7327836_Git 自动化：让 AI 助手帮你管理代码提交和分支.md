# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

在维护多个仓库或频繁迭代时，Git 操作高度重复：写 commit message、切分支、合并后清理分支、检查 diff。人工处理容易出现提交信息不规范、漏提交、分支堆积。AI 助手可以承担这些低风险、规则明确的部分，但完全放开 Git 权限会引入不可控操作。

## 问题

真的要把 `git` 命令交给 Agent 吗？直接给 shell 权限风险太高。更合理的方式是：把 Git 能力封装成有限工具集，让 AI 只做“读取 + 建议 + 显式确认后的写操作”。本文以 OpenClaw/Agent + MCP Git server 为例，说明落地方式。

## 做法 / 步骤

### 1. 暴露受控的 Git 工具

使用 MCP Git server，或自己写一个最薄的 MCP server，只暴露这些工具：

- `git_status`
- `git_diff`
- `git_log`
- `git_branch_list`
- `git_branch_create`
- `git_branch_delete`
- `git_add`
- `git_commit`
- `git_merge_base`

不建议直接暴露 `git` 原生命令，尤其不要给 `reset --hard`、`push --force`、`clean -fd`、`rebase`。在 OpenClaw 中把这些工具挂到 Agent，并设置工作目录白名单，例如只允许 `/workspace/project-a`。

一个受控 MCP 配置示意：

```json
{
  "mcpServers": {
    "git": {
      "command": "node",
      "args": ["/path/to/mcp-server-git/dist/index.js"],
      "env": {
        "GIT_WORKSPACE": "/workspace/project-a"
      }
    }
  }
}
```

### 2. 定义提交助手规则

给 Agent 写入系统提示词，核心规则如下：

- 先调用 `git_status` 和 `git_diff`，不要自行猜测。
- 只对用户明确确认过的文件执行 `git_add`，未跟踪文件必须单独列出。
- commit message 使用 Conventional Commits 格式：`feat:`、`fix:`、`chore:` 等。
- 如果 diff 超过 8000 字符，先按文件聚合摘要，再生成 message。
- 永远不执行 force push，不删除远端分支，除非用户连续确认两次。

示例流程：

```text
用户：帮我提交当前修改
Agent：
1. git_status -> 发现 modified: src/parser.ts, package.json
2. git_diff -- src/parser.ts package.json -> 摘要：修复解析空字符串时崩溃
3. 建议提交信息：fix(parser): handle empty string input
4. 用户确认
5. git_add src/parser.ts package.json
6. git_commit -m "fix(parser): handle empty string input"
```

### 3. 分支管理自动化

分支清理适合做“建议式自动化”。让 Agent 定期执行：

```text
1. git_branch_list --merged main
2. 排除 main、develop、release/*、hotfix/*
3. 输出可删除分支列表及最后提交时间
4. 用户确认后，逐个执行 git_branch_delete
```

新分支创建可以由 issue 标题映射：例如 issue `feat: add webhook retry` 自动生成分支 `feat/add-webhook-retry`。但这只适合规范命名，不建议自动切换当前分支。

## 踩坑点

- **权限过宽**：一旦 Agent 能执行任意 shell，`git` 可能只是起点。优先用 MCP 工具而不是 shell 插件。
- **diff 过长**：全量 diff 会撑爆上下文，还容易生成空洞的 commit message。必须截断或分文件处理。
- **敏感文件**：`.env`、密钥文件可能被误 `git add`。提交前让 Agent 检查 `git status --porcelain` 中的文件路径，命中 `*.pem`、`.env*`、`secrets*` 时停止。
- **冲突处理**：不要让 AI 自动解决合并冲突。冲突语义需要人判断，AI 只能提示冲突位置和双方差异。
- **本地与远端不同步**：删除分支前检查是否已推送，以及是否合并到默认分支。可以先 `git branch -r --merged` 判断。
- **Hook 中调用 AI 会拖慢提交**：如果把 AI 生成 commit message 放在 `prepare-commit-msg` hook 中，务必设置 3–5 秒超时，失败时回退到模板，而不是中断提交流程。

## 可复用建议

1. **有限工具集**：永远不要让 Agent 面对裸 shell，Git 工具尽量原子化。
2. **读写分离**：读操作自动执行，写操作默认 dry-run 或需确认。
3. **统一提交模板**：Conventional Commits + scope 限制，能减少生成随意 message。
4. **记录操作日志**：把 Agent 的每次 Git 写操作记录到 `git-ai.log`，包含时间、工具名、参数、结果。
5. **白名单目录**：在 MCP server 启动参数中限制 `--repo` 路径，避免误伤其他仓库。
6. **人审兜底**：自动化覆盖 80% 重复工作，但最终 merge、push 到共享分支、rebase 应由人执行。

## 总结

Git 自动化不是把仓库完全交给 AI，而是把“查看 diff、生成规范提交、清理已合并分支”这些规则明确的事交给它。控制在工具层、确认层和日志层之后，AI 可以成为可靠的 Git 副驾驶，而不是风险源。
