## 背景

在 OpenClaw / Agent / MCP / 插件 / 自动化场景里，AI 助手经常需要异步感知外部状态：任务队列是否出了新结果、MCP 工具调用是否完成、插件是否推送了新事件、用户是否在某个通道里回复。heartbeat（心跳）通常承担两类职责：一是维持会话或租约活性，二是拉取或接收这些异步事件。

早期实现最容易做成“每隔 N 秒问一次”，但很快会遇到延迟、限流、资源占用和状态同步问题。本文不讨论哪套方案“更先进”，只记录我在 OpenClaw 插件和自动化任务里实际踩过的坑和可复用做法。

## 问题

纯轮询的好处是简单，不依赖公网回调，调试直观。但坏处很明显：频率高会加重 MCP server、API、消息通道压力，容易被限流；频率低则用户感知延迟变大。

纯推送（Webhook / SSE / WebSocket）延迟低、资源友好，但要求目标服务可达、回调可注册、失败可重试。本地开发或内网环境往往不满足“可推送”条件。

更隐蔽的问题是：把“健康检查心跳”和“业务事件拉取”混在一起，导致心跳包过大、连接数膨胀、重复触发，甚至一个 agent 同时跑多个 timer 互相打架。

## 做法 / 步骤

我目前在 OpenClaw 插件和自动任务里采用“控制面 / 数据面分离 + 混合触发”。

1. **控制面 heartbeat 只做健康检查与租约续期**  
   间隔设为 30~120 秒，包体尽量小，只带 `agent_id`、`last_seq`、`status`。它不负责搬运业务数据。

2. **数据面按任务状态区分轮询频率**  
   - 进行中的任务：默认 3~5 秒短轮询拉取结果，同时注册可用的 Webhook / SSE 推送。  
   - 空闲任务：超过 60 秒没有新事件，自动降级到 30 秒慢轮询。  
   - 收到推送事件后：立即刷新本地状态，并把该任务的轮询间隔重置为短轮询。

3. **统一加 jitter 和退避**  
   所有定时器加 0.8~1.2 倍随机抖动，避免多实例/多任务同时唤醒。拉取接口设置 timeout 与 deadline，超时按指数退避重试，上限 30 秒。

4. **用 AbortController / context 取消任务**  
   避免 agent 关闭后 timer 仍在跑。本地维护一个 `task_id -> { status, version, last_heartbeat_at, next_poll_at }` 状态表，收到推送时校验 version 或 idempotency key，防止旧事件覆盖新状态。

## 踩坑点

- **短轮询触发限流**  
  MCP server 或第三方 API 对同一 IP 短时间轮询很敏感。曾经把间隔设成 1 秒，结果连续 429。建议默认 3 秒起步，并为 429 做退避。

- **推送通道不可达**  
  本地跑 OpenClaw 时没有公网地址，Webhook 根本收不到。可以先跑一个轻量隧道，或者自动降级为轮询，不要硬依赖推送。

- **推送事件乱序 / 重复**  
  Webhook 可能重发，同一个 `task_id` 的完成事件可能到达两次。必须用 version 或 event_id 去重，更新状态时采用“只接受更新版本”的策略。

- **多实例重复心跳**  
  如果同一 agent 部署了两个副本，两边都在轮询同一任务，可能重复触发动作。可以用 Redis 锁或按 `task_id` 做一致性哈希，保证同一时间只有一个执行者。

- **忽略 jitter**  
  多个定时任务同时唤醒，在日志上看起来像毛刺，也容易打满连接池。

## 可复用建议

- 把 heartbeat 做成独立模块，暴露 `start / stop / setInterval / onEvent`，别散落在业务代码里。
- 对支持推送的通道（WebSocket / SSE / Webhook）优先推送，轮询只做兜底；监控推送成功率，连续失败自动切回轮询。
- 心跳包保持最小化，控制面和数据面分开配置，不要用同一个 interval。
- 给所有异步状态更新加版本号或幂等键。
- 关注 p95 端到端延迟、轮询失败率、429 次数、心跳超时次数；这些指标比“心跳间隔”更能说明问题。

## 总结

在 OpenClaw 这类 agent / 插件 / 自动化环境里，heartbeat 设计没有银弹。工程上更稳妥的是混合模式：控制面低频健康检查，数据面优先推送、低频轮询兜底，并用状态机、版本号、jitter 和退避保证可恢复性。与其追求极致低延迟，不如先明确心跳的语义、把可观测性和降级路径做好。
