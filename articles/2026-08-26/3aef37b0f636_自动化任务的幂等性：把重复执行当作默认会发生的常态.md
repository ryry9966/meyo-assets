## 背景：重复执行是常态，不是异常

在 OpenClaw 的插件、定时任务、Agent 工具调用里，重复执行几乎不可避免：消息队列重投、MCP 工具超时重试、进程重启后的补偿任务、用户手滑重复触发。很多自动化任务天然会被执行多次，所以可靠的工程前提不是“保证只执行一次”，而是“重复执行也不会产生额外副作用”。这就是幂等性。

## 问题：不是所有任务都天然安全

读操作通常安全，但写操作很容易出问题。典型非幂等场景包括：

- 创建订单、创建工单、创建文件、创建目录
- 发送通知、推送消息、调用第三方支付
- 累加统计、追加日志、回写 CRM 状态
- 对 MCP 工具进行盲重试

如果这些操作没有幂等设计，重复执行会造成重复单据、重复推送、资金风险、状态覆盖。目标不是消灭重复执行，而是让重复执行的后置结果一致。

## 做法：把幂等性落实到入口和存储

### 1. 显式幂等键

让调用方传入 `idempotency_key`，而不是每次重试都生成一个新的随机 UUID。自然业务键更稳定，例如 `order_id`、`issue_id`、`task_no`。没有自然键时，由插件在任务创建时生成并持久化，重试时复用同一个键。

```json
{
  "idempotency_key": "order-20250618-001",
  "action": "create_order",
  "payload": {}
}
```

### 2. 唯一约束与状态表

不要只做“先查再插”。并发下两个 worker 都可能查不到，然后重复执行。数据库唯一索引是最后的兜底：

```sql
CREATE UNIQUE INDEX uk_plugin_idem
ON plugin_idempotency(tenant_id, idempotency_key);
```

首次请求插入状态行，状态机推进为 `created -> running -> done/failed`。重复请求命中唯一键时，返回已保存结果；如果状态还是 `running`，可以返回冲突或等待，而不是立即重入。外部副作用应放在状态推进之后。

### 3. MCP 工具和插件统一封装

很多外部 API 本身没有幂等设计。建议在 OpenClaw 的 MCP 工具封装层处理：

- 把 `request_id` 或 `idempotency_key` 传给上游
- 对 `409`、`duplicate`、`already exists` 等响应归一为成功
- 超时重试时用同一个 key 查询上游结果，而不是盲目再发
- 插件里提供统一的 `withIdempotency` helper，让所有写工具走同一条路径

## 踩坑点

几个常见但容易忽视的问题：

- 用时间窗口判断“刚刚跑过”，并发下会漏。
- 重试时重新生成 UUID，等于没有幂等键。
- 只做查询去重，没有唯一约束，两个 worker 同时插入。
- PATCH 部分更新接口，重试时缺省字段可能覆盖已有变更。
- 第三方 API 非幂等，Agent 或插件层裸调，出问题难以追溯。
- 异步任务把消息 ID 丢弃，重投后无法识别是同一任务。

## 可复用建议

- OpenClaw 插件入口默认带幂等键和重试策略，不要把责任完全推给工具实现方。
- 对会产生副作用的 MCP 工具，在工具描述里明确要求调用方提供幂等键或自然键。
- 外部调用记录 `request_id`、状态、返回摘要，便于排查重复执行链路。
- 测试时模拟并发和超时重入，而不是只测顺序调用。
- 对无法改造的外部系统，增加补偿任务或对账机制，不要依赖它天然幂等。

## 总结

幂等性不是避免重复执行，而是让重复执行不产生额外副作用。工程上更成熟的做法，是把重复当成持续发生的常态，用显式幂等键、唯一约束和状态机把不确定变成确定。这样 OpenClaw 的 Agent、定时任务和插件重试，才能在长期运行中保持稳定。
