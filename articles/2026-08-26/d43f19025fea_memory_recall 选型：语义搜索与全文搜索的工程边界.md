# 背景

在 OpenClaw 的插件和自动化实践里，memory_recall 是记忆链路中最容易被“神化”的一环。很多实现一开始只有两种选择：基于关键词的全文检索，或者基于 embedding 的语义搜索。一旦接入向量库，很容易默认“语义搜索更智能”，直接把全文搜索替换掉。但实际跑一段时间后，延迟、召回质量、存储成本、可解释性都会出现分歧。

这里的核心不是“哪个更好”，而是你的记忆内容、query 形态、调用方是谁。

# 问题

memory_recall 的典型调用方是 Agent 或 MCP 工具。比如：

- 用户问：“我之前怎么配的代理端口？”
- Agent 需要：“找一下昨天任务失败时的报错日志”
- 自动化脚本要：“读取上次重启服务的命令”

这些 query 差异很大：

- “代理端口”是自然语言，适合语义搜索；
- “报错日志”“重启服务”是半结构化任务描述，两者都行；
- “docker ps -a”“/data/logs/nginx” 这种命令、路径、报错码，语义搜索往往表现糟糕。

如果只上语义搜索，短 query 或专有名词会被 embedding 拉偏，召回一堆“看起来相关但实际无用”的长文本。如果只上全文搜索，同义改写、自然语言回忆就基本失效。

所以工程上要做的是：先评测，再决定默认模式，而不是拍脑袋替换。

# 做法/步骤

我建议把 memory_recall 设计成三种模式，并暴露给上层：

1. **fulltext**：SQLite FTS5 / BM25 / jieba 分词，适合命令、路径、专有名词、短 query。
2. **semantic**：embedding + 向量索引（sqlite-vec、pgvector、faiss 等），适合段落性自然语言回忆。
3. **hybrid**：先各取 top_k，再用 RRF（Reciprocal Rank Fusion）合并排序。

具体步骤：

1. **盘点记忆类型**：先看 memory 里存的是什么。是日志、代码片段、任务摘要、配置、命令历史，还是对话记录。命名实体多还是自然语言多，决定初始倾向。

2. **造一个小评测集**：挑 20～50 条真实 query，标注期望命中的记忆 ID。不需要很大，但要覆盖短 query、长句、路径、命令、同义改写等类型。

3. **跑三种模式的基线**：记录 Recall@k、MRR、P50/P95 延迟、单次召回 token 成本、索引体积增长。

4. **调参**：
   - fulltext：调整分词器，中文不要用默认按空格切，建议 trigram 或 jieba。
   - semantic：设置 min_score 参考值（0.35～0.55），但不要作为唯一截断条件，优先按 top_k 截断。
   - hybrid：RRF 的 k 值常用 60，可以先固定，再看是否需要用加权和替代。

5. **生产策略**：默认 hybrid，top_k=5。当 query 很短或包含明显命令、路径、报错码时，提高 fulltext 权重或直接只用 fulltext 兜底。长句自然语言则让 semantic 发挥主要作用。

# 踩坑点

- **语义搜索对短 query 不友好**。“rm”“docker ps”“/tmp/log” 这类输入 embedding 后，向量很容易被泛化，召回无关长文本。这是最常见的翻车点。

- **中文全文分词是隐坑**。SQLite FTS5 默认 tokenizer 对中文支持差，如果不加 trigram 或外部分词，全文搜索基本等于不可用。

- **混合检索不是简单加权平均**。RRF 对原始 score 不敏感，但如果 k 值不合适，弱结果容易混进 top。建议固定 k 后，针对评测集扫几个参数。

- **min_score 阈值很容易误杀**。不同 query 的 score 分布不同，固定阈值会把一些应该召回的低分真命干掉。工程上优先按 top_k 截断，min_score 只做预警或兜底。

- **embedding 模型更新会导致向量不可比**。切换模型后必须重建索引，不要增量混用。

- **写入侧也要结构化**。如果只存原文，召回时噪音会很大。建议区分标题、摘要、正文、元数据，优先召回摘要和标题，再去原文里取细节。

# 可复用建议

1. **先跑基线，不要直接上语义**。一个小评测集就能暴露很多问题，比上线后被动排障便宜得多。

2. **把 mode 暴露给 Agent 或 MCP 工具**。在工具描述里写清楚：命令、路径、报错码用 fulltext；段落性回忆、任务复盘用 semantic；拿不准用 hybrid。

3. **记录召回的 trace**。把 query、mode、top_k、是否命中、后续是否被采纳记下来。这些负样本是后续调参和切模型的重要依据。

4. **关注成本和延迟**。语义搜索的 embedding 调用和向量检索有额外开销，尤其是高并发时。百万级 768/1536 维向量，存储约 3～6GB，可以用量化或降维控制成本。

5. **保留全文兜底**。即使语义搜索表现不错，也建议保留一条全文检索路径。关键时刻的“确定性召回”比“智能猜”更重要。

# 总结

memory_recall 的语义搜索与全文搜索不是替代关系，而是分工关系。默认 hybrid 更稳，但关键路径要有全文兜底。先做小评测，再切换默认模式，避免被“语义搜索更高级”的工程幻觉带偏。真正可靠的不是某一项技术，而是可观测、可降级、可调参的检索链路。
