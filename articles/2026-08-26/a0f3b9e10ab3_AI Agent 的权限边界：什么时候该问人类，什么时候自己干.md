## 背景：Agent 正在从“问答”变成“执行者”

现在很多 OpenClaw 的 agent 已经不只是调用 LLM 生成文本，而是通过 MCP server、插件、本地工具去读写文件、执行命令、调用外部 API。自动化的收益明显，但风险也同步放大：工具不再是“查询天气”这种只读操作，而是会修改真实环境。

## 问题：权限边界不是“要不要给工具”

常见的错误是只做二元开关：要么完全自动，要么每步确认。前者容易造成不可逆操作；后者让用户疲劳，最终会随手点“允许”，等于没有权限边界。

更隐蔽的是权限传递：Agent 调用 MCP server A，A 再调用 B；或者插件声明了宽泛权限，实际运行时没有二次校验。最后看起来每一步都有确认，实际上权限已经被放大。

## 做法：按风险分级，而不是按工具名称

比较实用的做法是把每个工具/动作事先标成三个风险档：

- 低风险：只读查询、搜索、生成草稿、获取状态
- 中风险：创建/更新文件、发送消息、提交 PR、启动测试
- 高风险：删除、支付、发布、修改权限、执行 shell 命令、变更数据库

然后对应三档策略：

- 低风险：自动执行，不打断用户
- 中风险：满足条件才自动执行，否则请求确认；确认时提供影响面、可回滚性和备选方案
- 高风险：默认要求人类确认，或直接禁止

示例配置可以这样写：

```yaml
tools:
  read_file:
    risk: low
    policy: auto
    allow_paths: ["/workspace"]
  write_file:
    risk: medium
    policy: confirm_if_overwrite
    allow_paths: ["/workspace"]
  execute_command:
    risk: high
    policy: require_human
    allowlist: ["ls", "git status", "pytest"]
    deny_patterns: ["rm -rf", "drop table", "sudo"]
```

注意这里的限制不只在工具名上，还在参数和资源范围上。比如 `write_file` 只允许写 `/workspace`，命令只允许白名单，且显式拒绝高危模式。

## 踩坑点

- 只限制工具名，不限制参数范围。给了 `execute_command` 但不限制 `rm -rf`，等于白做。
- 把“读操作”当成安全操作。某些只读工具也会泄露敏感信息，比如读取 `.env`、密钥文件、客户数据。
- 过度依赖用户确认。确认弹窗太多，用户会形成肌肉记忆，高危操作也可能被随手点掉。
- 长任务中前面确认了，后面环境已经变化，Agent 仍然按旧上下文继续执行。需要在关键步骤前重新检查前置条件。
- MCP server 权限声明过大，Agent 侧没有二次校验。要对 MCP server 暴露的工具做 allowlist，而不是全盘接收。

## 可复用建议

1. 维护一份风险矩阵：每个工具标注风险等级、默认策略、允许参数范围、拒绝模式。
2. 对中高风险操作使用 dry-run 或 preflight。比如先跑 `plan` 或 `--check`，把结果交给用户确认。
3. 让 Agent 在请求确认时带上三样信息：影响面、可回滚性、备选方案。不要只问“是否继续”。
4. 不可逆操作加二次确认，或要求输入人类验证码/环境名。
5. 保留审计日志：记录每次自动执行的输入、工具、参数、结果和决策轨迹。事后可以回放，也可以用来收紧权限。
6. 定期回看 Agent 的实际调用记录，把那些“从没被正常使用过的高风险工具”直接关闭或降级。

## 总结

权限边界不是信任问题，是工程问题。不要试图让 Agent 自己判断“这件事该不该问人类”，而是先在工具层和资源层把风险明确下来。低风险、可回滚的动作让它自己干；高风险、不可逆的动作必须回到人类；中间地带用条件触发和带上下文的确认来平衡。这样既能保持自动化效率，又能避免把风险全部压在用户的一次点击上。
