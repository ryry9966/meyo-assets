## 背景

在 OpenClaw / Agent 自动化场景里，定时任务和普通对话有一个关键区别：没有实时澄清机会。你写“帮我整理今天的行业动态”，在对话里模型可以反问“要哪个源？发到哪里？多少条？”但在 cron 任务里，这条指令会在凌晨无人值守地执行。任何歧义都会变成静默失败、错误输出，或者更糟——污染下游数据。

不少 OpenClaw 用户的 cron 任务跑得不够稳，不是模型能力不够，而是 instruction 写成了“聊天式语句”，而不是“可重复执行的 SOP”。这篇不聊玄学，只写工程上能复用的写法。

## 问题

一个常见失败案例：某定时任务写的是“每天 9 点抓取行业动态，发到群”。第一天输出 40 条，第二天输出 3 条，第三天开始出现“我会继续关注”的结尾。问题出在：

- “行业动态”没有定义来源、时间范围、数量上限。
- “发到群”没有定义格式、去重规则、失败处理。
- 每次运行都是冷启动，模型不会自动继承你上次的偏好。

Cron 任务的 instruction 需要让模型在完全无人干预的情况下，输出可预测、可解析、可监控的结果。

## 做法 / 步骤

建议把 instruction 写成六段式结构：

1. **Context**：告诉模型它在执行定时任务，不是闲聊。
2. **Goal**：用一句话说明完成标准。
3. **Inputs**：数据源、工具、参数。
4. **Steps**：按顺序的工具调用和判断。
5. **Output**：严格输出格式，最好带状态码。
6. **Failure**：失败时怎么降级。

下面是一个可以直接改的模板：

```text
你是 OpenClaw 定时执行助手。现在执行每日 RSS 摘要任务。

目标：从指定 RSS 抓取最近 24 小时的文章，输出 5 条以内的中文摘要。

执行步骤：
1. 调用 rss_fetch 工具获取 https://example.com/feed.xml。
2. 过滤 pubDate 距 now 不超过 24 小时的条目。
3. 按发布时间倒序取前 10 条。
4. 对每条生成一条摘要，只保留关键信息，不展开评论。
5. 如果条目数为 0，直接输出：NO_NEW_ITEMS。

输出格式：
- 每条摘要使用 Markdown 无序列表：`- 标题：一句话摘要`
- 不输出问候语、开头语、结尾语、解释说明。
- 不输出完整原文。
- 不编造发布者、日期、链接以外的信息。

失败处理：
- 如果 rss_fetch 第一次失败，等待 5 秒后重试一次。
- 仍失败则输出：CRON_ERROR: <错误类型> <简短原因>。
- 如果 RSS 内容明显异常，不要推断，按 NO_NEW_ITEMS 处理。
```

说明：这里的 `now` 必须定义。可以补一句：“所有时间按 UTC+8 计算，工具返回的时间若为 UTC 需转换。”

## 踩坑点

**1. 时区偏差**  
cron 表达式可能按 UTC 触发，但业务逻辑按北京时间。不要只写“今天”，要写明时区，或让工具直接传 `since` 参数。

**2. 输出格式不约束**  
每次输出多一个句号、多一行“根据最新消息”，下游解析就可能失败。给样例输出比写“输出摘要”有效得多。

**3. 没有失败码**  
如果任务失败后只输出“我处理不了”，你无法区分是暂时性网络问题还是权限错误。固定 `CRON_ERROR: <类型>`，可以让监控系统按关键字告警。

**4. 让 cron 做不可逆操作**  
例如“低于 100 元就下单”，既没有库存判断，也没有重复下单保护。建议 cron 只做“检测 + 通知”，审批或人工确认后再执行不可逆动作。

**5. 忽视幂等**  
同一条任务可能在手动补跑和自动调度时重复触发。可以在 instruction 里加“若当天已生成同样内容，则跳过输出”，或在调度层加锁。

**6. 指令过长导致注意力漂移**  
instruction 不是越长越稳。常量、URL、关键词可以放进工具参数或环境变量，instruction 只保留流程和约束。

## 可复用建议

- 统一模板：Context / Goal / Steps / Output / Failure / Guardrails。
- 先手动测试：把同一段 instruction 在普通对话里跑 3 次，确认输出稳定。
- 限制工具权限：cron 任务绑定的 Agent 只给最小权限，不接支付、删除、发布等高危工具。
- 把输出当日志：固定状态码 `OK / NO_NEW_ITEMS / CRON_ERROR`，方便后续统计和监控。
- 版本化管理：instruction 放 Git，生产环境不要直接在后台改。

## 总结

Cron 任务的 instruction 本质是写“无人值守的 SOP”，不是和模型聊天。你越把任务当成确定性流程来写，模型越不容易跑偏。时间、输入、步骤、输出、失败处理，这五件事写清楚，比堆一堆“你要认真一点”更有效。工程上，稳定永远比聪明重要。
