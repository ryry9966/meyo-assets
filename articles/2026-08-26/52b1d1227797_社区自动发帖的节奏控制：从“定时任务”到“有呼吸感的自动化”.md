## 背景

在 OpenClaw 这类 Agent 自动化场景里，社区自动发帖已经从“能不能发”进入“发了会不会被当机器人”的阶段。很多实践者把社区发布做成 crontab 或固定间隔 loop，结果很快触发风控、被版主移除，或者被社区成员标记 spam。原因通常不是自动化本身，而是节奏不像人。

## 问题

节奏控制不等于随机 sleep。人的发帖行为有几个特征：时间上会跟随讨论热点、工作时段和回复刺激；内容上不会用同一套结构反复发；互动上不会无差别秒回；遇到异常会停手。

只加 `random.uniform(300, 900)` 的自动化，通常仍会暴露：发布间隔均值过于稳定、回复速度异常、长时段无人值守仍在发。更关键的是，它没有“该沉默时就沉默”的能力。

## 做法：三层节奏控制

### 1. 内容侧：模板拆细，组合而不复用整段

不要把完整帖子存成固定字符串。建议把内容拆成：

- 主题句若干
- 案例、数据、代码片段若干
- 结尾引导若干

每次发布按规则组合，并做同义替换。更稳妥的做法是让 Agent 根据最近社区讨论生成初稿，再进入人工审核队列。这样即使自动化频率略高，也不会因为文本重复被一眼识别。

### 2. 时间侧：事件驱动 + 时间窗 + 抖动

不建议纯定时轮询。可接受的工程做法：

- 用 MCP 工具读取目标社区的活跃时间、最新帖时间、回复增量。
- 设定“可发布窗口”，例如工作日 10:00–12:00、15:00–17:00、20:30–22:30。
- 窗口内不是定时触发，而是当检测到有效讨论事件，例如某个话题新增 N 条回复后，再决策是否发布。
- 实际发布时间加正向偏置抖动：  
  `delay = base_delay + min(30min, exponential(scale=8min))`  
  避免固定间隔。
- 设置每日上限，通常 1–3 条，视社区规则。

### 3. 互动侧：回复冷却与触发阈值

自动回复比自动发帖更容易穿帮。建议：

- 回复前判断：是否被 @、是否涉及自己发布帖的直接提问、是否出现明确可纠正的错误信息。
- 不回复所有内容。每条回复至少间隔 8–15 分钟，同一帖子内回复不超过 2 次。
- 如果检测到负面反馈，例如帖子被标记、收到含 “bot” 关键词的回复，立即停止当日发布，转入只读模式。

### 4. 人工审核与 dry-run

即使 Agent 能自动发帖，也至少保留一条人工审核通道。发布前以 dry-run 输出完整内容、目标板块、预计发布时间。正式发布后记录触发事件和实际间隔，便于回查。

## 踩坑点

- **把随机延迟当节奏**：随机均匀分布本身也像机器，要用有偏分布模拟集中活跃。
- **模板只替换几个词**：社区成员很快识别，且搜索引擎不友好。
- **回复速度过快**：秒回是最强的 bot 信号，必须冷却。
- **忽略社区规范**：某些板块禁止 URL 或要求标签，自动发帖前要校验规则。
- **无人值守长时间运行**：夜间或凌晨发帖会被明显识别。
- **多账号同源**：一个 IP 或多个账号相同 UA、行为模式，节奏控制再好也没用。

## 可复用建议

1. 用 MCP server 把社区状态标准化，输出“活跃度”“最近讨论话题”“是否处于黑名单时间”给 Agent。
2. 发布决策拆成两个阶段：策略层判断“今天是否发、发什么”；执行层负责“何时发、怎么发”。不要混在一个 prompt 里。
3. 所有发布动作写结构化日志：trigger、candidate_time、actual_time、post_id、reply_count。跑一周后回看间隔分布是否接近真人。
4. 设置熔断：连续两次被删帖或被举报，自动切换为人工模式。
5. 先用“影子模式”观察：让 Agent 只生成草稿不发布，持续 3–7 天，看推荐发布节奏是否合理。

## 总结

社区自动发帖不像机器人，核心不是隐藏“我是自动化的”，而是让自动化尊重社区节奏：该出现时出现，该沉默时沉默，遇到风险就停。工程上把内容、时间、互动三层解耦，配合 dry-run、日志和熔断，比单纯调 sleep 有效得多。

最终目标不是零人工，而是让人只做判断，让 Agent 做重复执行。
