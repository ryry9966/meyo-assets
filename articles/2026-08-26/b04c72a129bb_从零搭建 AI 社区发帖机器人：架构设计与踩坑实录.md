## 背景

在 OpenClaw-CN 社区维护自动化工具时，我积累了不少调试记录、MCP 用法和插件踩坑笔记。人工发帖的流程很重：整理 Markdown、改社区排版、选标签、传图、提交后等审核。于是想用 OpenClaw Agent 驱动社区接口，把这些内容沉淀成帖子。

最初尝试让 agent 直接读取草稿并发布，结果问题很多：标题被擅自修改、格式错乱、社区 API 返回成功但前台不可见。最后收敛成一套“本地草稿 + MCP 工具 + 审批层”的流水线。本文记录这个过程中的架构设计和实际踩坑。

## 问题

社区后台有 API，但和公开文档不完全一致；发帖涉及登录态、标签枚举、Markdown 渲染差异；agent 在长上下文里容易把草稿当建议，顺手改写内容。目标不是全自动灌水，而是做一个可审核、可回滚、可复用的发布器。

## 做法/步骤

### 1. 架构分层

- **内容源**：本地 Git 仓库，每篇帖子一个 Markdown 文件，frontmatter 写明 `title`、`tags`、`category`、`summary`、`status`。
- **执行层**：OpenClaw Agent，只负责按流程调用工具。
- **工具层**：通过 MCP server 暴露社区能力，避免 agent 直接处理登录态和接口细节。
- **审批层**：先 dry-run 生成预览，人工确认后才真正发帖，发布记录写入 `publish-log.jsonl`。

封面图不放在正文里，减少外链和上传失败问题。

### 2. MCP server 最小工具集

只暴露 6 个工具：`list_categories`、`get_topic`、`search_topics`、`create_topic`、`reply_topic`、`upload_image`。其中 `create_topic` 入参为 `title`、`category_id`、`tags`、`content_md`、`idempotency_key`。发帖工具内部做编码、截断、标签白名单校验，失败返回结构化错误，不让 agent 自行无限重试。

### 3. Agent 提示词约束

把角色定义为“发布执行器”，而不是“内容创作者”。提示词里明确：

- 只读取指定文件；
- 不得修改 `title`；
- 不得补写正文；
- 遇到工具报错必须停止并输出错误码；
- 任何标签不在白名单就进入人工队列。

同时在工具 schema 层做校验，双保险。

### 4. 发布流程

1. 调用 `list_categories` 获取分类；
2. 检查 frontmatter 和正文；
3. dry-run 返回标题、标签、摘要及社区渲染后的 HTML 预览；
4. 人工确认；
5. 调用 `create_topic` 发布；
6. 成功后把 `topic_id`、URL、时间、内容哈希写入 JSONL。

失败保留原始草稿，不自动重写。

## 踩坑点

- **API 返回 200 但帖子进入审核队列**：一开始以为发布成功，结果前台看不到。后来增加 topic status 轮询，遇到 `visible=false` 标记为 pending，不立即写成功。
- **标签枚举不稳定**：社区标签有时需要 slug 有时需要 display name，中文标签还会被编码。MCP 内做映射，agent 看不到这些差异。
- **Markdown 渲染差异**：社区不支持部分 GFM 语法，代码块里的某些符号被转义。上传前做一次清洗：图片链接统一走 `upload_image`，代码块加 fence 类型，减少行内 HTML。
- **Token 过期**：MCP server 用 API key 调接口，但偶发 401。增加 refresh 和本地缓存，401 时清缓存并重试一次，两次失败就终止。
- **Agent 自行发挥**：有次我把标题写成“草稿-测试”，agent 改成“测试 MCP 社区发帖机器人优化实录”发出去了。后来加硬规则：标题字段只允许原样复制，工具层校验 title hash，不一致直接拒绝。
- **限频**：同一账号连续发帖会被短暂限制。加入发布队列，每帖间隔 45–90 秒，遇到 rate_limit 指数退避。
- **本地记录丢失**：有帖子发了但本地没记录，因为 JSONL 写入失败。改成先写日志再调用工具，日志状态为 pending，成功后再更新。

## 可复用建议

1. 发帖动作必须有幂等键，用 content hash 或 UUID，避免重复发。
2. 内容生成与发布解耦，草稿入库后由固定流程发布，不让 agent 边写边发。
3. 工具返回错误要结构化成 JSON，包含 `retryable` 和 `reason`，否则 agent 会乱解释。
4. 从低风险版块灰度，第一周只让机器人发“工具反馈”分类，人工抽查。
5. 保留所有工具调用日志，作为审计和回溯依据。

## 总结

这套方案在 OpenClaw-CN 社区稳定跑了两个月，发了几十篇技术帖，主要价值不是省时间，而是把发帖动作固化下来，减少人工改格式和重复操作。Agent 仍然只是执行器，真正决定发不发、发什么的边界要留在工具层和审批层。这样即使模型犯错，也不会直接污染社区内容。
