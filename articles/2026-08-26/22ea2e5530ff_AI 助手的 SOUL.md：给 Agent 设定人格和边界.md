## 背景

在 OpenClaw 这类 Agent 项目里，我们经常让模型执行长任务：查日志、调 MCP 工具、改配置、发消息。时间一长就会发现，同一个 Agent 在不同会话里像换了一个人：有时很谨慎，有时随手就装依赖；有时回复很简洁，有时输出一大堆。问题不在于模型能力，而在于我们没有把“人格”和“边界”固化下来。

SOUL.md 可以理解为 Agent 的“岗位说明书 + 行为准则”。它和系统提示不同：系统提示偏一次性指令，SOUL.md 是随项目走、可版本化、可持续调校的约定文件。

## 问题

没有稳定 SOUL.md 时，常见三类故障：

1. **角色漂移**：你希望它是运维助理，聊着聊着开始写产品文案。
2. **权限越界**：让它排查端口占用，它顺手把服务重启了。
3. **风格不一致**：同一类任务，有时输出三行，有时输出三段，不好解析。

这些不是“模型抽风”，而是缺少明确的约束文件和加载机制。

## 做法

### 1. 位置与加载

在项目根目录放 `SOUL.md`，并在 Agent 启动或会话初始化时将其内容注入系统提示。不要只放在文档里，必须进入上下文。OpenClaw/Agent 框架通常支持项目级配置或启动脚本来加载。

### 2. 内容结构

建议用明确的字段，避免长篇散文。以下结构可直接复用：

```markdown
# SOUL.md

identity: 运维排查助理
traits:
  - 先确认，再执行
  - 不确定时停下来问
  - 输出尽量结构化
allowed:
  - 读取 ./logs 目录
  - 执行只读诊断命令
  - 调用已配置的 MCP 工具
forbidden:
  - 不安装未声明的依赖
  - 不修改生产配置
  - 不读取或回传 .env、密钥
decision_order:
  - 安全
  - 用户明确指令
  - 效率
failure_policy:
  - 连续两次失败后停止，并报告原因
```

这种写法比“你是一个乐于助人的助手”更可执行。

### 3. 与 MCP/插件权限对齐

SOUL.md 里的 `allowed` / `forbidden` 要和实际工具权限一致。例如 agent 能调用 shell，但你在 SOUL.md 说“只允许读日志”，那就要在 shell MCP 配置里也限制命令白名单。只靠人格约束是不够的，工程上必须有两层防护。

### 4. 版本管理

把 SOUL.md 纳入 git。每次改变 Agent 行为时，先改文件再跑测试。最好准备几条固定 prompt 作为“人格冒烟测试”：

- 让它尝试执行一个被禁止的操作，看是否拒绝。
- 让它输出身份说明，看是否符合设定。
- 给一个模糊指令，看它是否先提问。

## 踩坑点

1. **写太长**：超过 1500 字的 SOUL.md 会被注意力稀释，模型可能只记住开头和结尾。控制在 800 字以内，用字段表达。
2. **太文艺**：用“你是一个温暖而有边界的工程师”这种描述，不如直接写“回复不超过三句，不主动给建议”。
3. **边界模糊**：要写“禁止修改生产配置”，而不是“请谨慎操作”。禁止项必须是可验证的行为。
4. **只写不测**：很多团队写完 SOUL.md 就结束了，实际跑了几个任务才发现 Agent 还是越界。需要像测试代码一样测试人格。
5. **工具能力和人格冲突**：SOUL.md 说“不安装依赖”，但插件却开放了 pip install，Agent 还是会执行。边界必须落到权限层。

## 可复用建议

- **精简字段**：identity、traits、allowed、forbidden、decision_order、failure_policy 六块足够覆盖大部分场景。
- **按环境分层**：开发环境可以放开只读限制，生产环境必须更严格；可以用模板生成不同 SOUL.md。
- **把边界变成测试用例**：每一条 forbidden 都对应一个测试 prompt，确认 Agent 会拒绝。
- **定期复盘**：每次 Agent 出现异常行为，回到 SOUL.md 看是否没写清楚，而不是去改模型参数。

## 总结

SOUL.md 不是玄学，也不是一次写完美。它是一个持续迭代的工程文件，目的是让 Agent 在长任务中保持稳定、不越界、可预测。把人格写短、把边界写死、把约束落到权限层，比给模型更多“人设”更有效。对于 OpenClaw 用户来说，这比追新模型版本更值得先做。
