# Agent 记忆系统设计：从“每次失忆”到可维护的长期偏好

## 背景

在 OpenClaw 里跑自动化任务时，经常遇到一类情况：同一个偏好你要反复交代。比如“部署用 Docker Compose，不要用裸 docker run”“日志输出只要关键错误，不要整段贴”“代码风格保持简洁，别上设计模式”。每次新会话开始，Agent 像换了个人，你不得不把这些话重新说一遍。

更麻烦的是，有时 Agent 似乎记住了，但它记住的是你上次临时说的“这次先不用 healthcheck”，结果后续所有任务都默认跳过健康检查。这种“伪记忆”比没有记忆更危险。

## 问题

Agent 记忆系统的核心问题不是“能不能存”，而是：

1. **上下文窗口有限**：不能把整个历史一直塞进去。
2. **信息类型混杂**：临时要求、稳定偏好、环境事实、过程经验混在一起，检索时互相干扰。
3. **更新无规则**：新信息会覆盖旧信息，冲突无人处理。
4. **缺乏确认机制**：自动写入的记忆一旦污染，很难排查。

很多实践者一开始直接用向量数据库存所有对话，结果检索回来的片段经常是过时的、矛盾的，Agent 输出反而更不稳定。

## 做法 / 步骤

我的实践经验是分层设计，先把结构固定下来，再考虑检索优化。

### 1. 定义三类记忆

- **短期工作记忆**：当前任务的上下文，会话结束后归档或丢弃。例如正在排查哪个服务、已经试过哪些操作。
- **长期偏好记忆**：用户稳定的偏好、约束、环境事实。例如部署方式、日志级别、代码风格、常用镜像源。
- **过程经验记忆**：完成任务后的经验总结，可复用的操作路径。例如“上次 nginx 502 的原因是 upstream 端口写错，检查 ssl 配置前先确认端口”。

### 2. 存储介质先简单后复杂

不要一上来就上向量数据库。早期用文件系统完全够用：

```
~/.openclaw/memory/
├── profile.md          # 长期用户偏好，人工可编辑
├── facts.json          # 环境事实，例如服务器列表、默认 region
├── sessions/           # 短期会话摘要
└── embeddings/         # 向量索引，可选
```

`profile.md` 用自然语言写，方便你随时打开改。`facts.json` 用结构化数据，字段固定。会话摘要由 Agent 在每次任务结束后自动生成，只保留关键结论和未解决问题。

### 3. 读写流程

关键原则：**写入选代慢，检索精确**。

任务开始时，从长期记忆里检索相关偏好。这里可以用简单的关键词匹配或向量检索，Top-K 设小一点，比如 3~5 条。检索到的内容注入 system prompt。

任务结束后，Agent 提取候选记忆，但不是直接写进去。候选记忆进入一个待确认区，用户确认后才写入长期记忆。或者用规则自动过滤：只存出现两次以上的偏好，一次的临时要求不写。

### 4. 更新机制

建议给每条记忆附上元数据：

```yaml
- content: "部署默认使用 Docker Compose"
  source: user_confirmation
  created_at: 2025-01-12T10:00:00Z
  last_accessed_at: 2025-02-03T14:20:00Z
  hit_count: 7
  status: active
```

这样遇到冲突时，可以根据源、时间、使用次数决定保留哪条。用户显式确认的记忆优先于自动提取的。

### 5. 提供显式命令

在系统里内置几个简单指令：

- `/remember <信息>`：手动写入长期偏好
- `/forget <关键词>`：删除相关记忆
- `/memory`：查看当前生效的长期记忆

不要让用户去手动编辑 JSON 文件，除非他是维护者。

## 踩坑点

1. **记忆污染**：自动提取把一次性要求写成长期偏好。解决：默认只自动写“事实”，偏好类必须用户确认。
2. **检索噪音**：Top-K 设太大，无关记忆注入，干扰输出。建议 Top-K 不超过 5，且设置相似度阈值。
3. **存储膨胀**：长期记忆文件越来越大，每次注入都超 token 限制。解决：定期合并、归档，超过 90 天未命中的记忆降级为候选或删除。
4. **隐私泄露**：敏感信息明文存在 profile.md 里，如果 repo 公开就麻烦。建议敏感字段用环境变量引用，或单独加密存储。
5. **偏好冲突**：新旧偏好并存，Agent 随机选一条。解决：写入时检查同义条目，旧条目标记为 superseded，不直接删除但不再检索。

## 可复用建议

- **先把 schema 定下来**：长期偏好、环境事实、会话摘要三个类别分开，不要混在一个文件里。
- **检索优先于写入优化**：写少一点、确认多一点，比自动写全但检索乱七八糟更可靠。
- **提供遗忘机制**：记忆系统必须有删除和降级能力，做得差的记忆系统就是垃圾回收失败。
- **人工可编辑**：长期偏好文件保持纯文本，方便用户直接打开改。不要把它藏进数据库的黑箱。
- **不要追求完全自动化**：Agent 记忆系统 80% 的价值来自稳定、可预测的上下文，而不是自动学习多少新东西。

## 总结

让 AI 助手真正记住你的偏好，不是往 system prompt 里塞更多内容，也不是上向量数据库存所有历史。它是把记忆分成短期、长期、过程三类，固定读写流程，确认写入，提供遗忘机制。从文件系统开始，跑通流程后再考虑向量检索和自动提取。记忆系统的工程目标不是“记住一切”，而是“在正确时间给出正确且不过量的上下文”。这比任何花哨的记忆框架都重要。
