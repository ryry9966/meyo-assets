## 背景

在 OpenClaw / Agent / MCP 这类自动化环境里，Cron 定时任务最容易出现“第一次跑得像演示，第二次开始抽风”。很多情况下不是模型能力不够，而是 instruction 给了太多自由。

定时任务没有人在回路，任何歧义都会被放大：时区错了、输出写到别处、任务重复执行、工具调用越界。把 Cron 任务的 instruction 当聊天备忘写，基本就是埋雷。

## 问题：常见反模式

- 目标写成自然语言摘要：如“每天帮我整理一下重要信息”。没有定义“重要”，agent 每天可能使用不同过滤标准。
- 时间描述冲突：cron 表达式写 `0 8 * * *`，正文写“晚上八点”，但服务器是 UTC。
- 没有定义输出位置和格式：agent 可能写到聊天窗口、临时目录或随机文件名。
- 缺少幂等约束：重试或重复触发导致重复文件、重复写入。
- 失败策略缺失：某一步失败后继续往下走，产出半成品。
- 权限与边界不明：为完成任务使用高权限工具，误删或覆盖非目标文件。

## 做法/步骤

我建议把每条 Cron instruction 组织成字段，而不是散文。一个最小可用的模板：

```text
Job: <任务名>
Schedule: <cron 表达式> (<IANA 时区>)
Goal: <一句话，可验证的结果>
Inputs: <数据来源、路径、MCP 工具名>
Steps:
1. <具体动作，使用什么工具>
2. <处理逻辑>
3. <写入/发送>
Output: <绝对路径或目标 channel，文件名规则，格式>
Idempotency: <如何避免重复，例如按日期去重、写入前检查>
Failure: <任一步失败即停止并报告，不要自行修复>
Constraints: <只读范围、禁写目录、最大 token、超时>
Acceptance: <如何判断成功>
```

示例，新闻汇总类：

```text
Job: daily-tech-digest
Schedule: 0 8 * * * (Asia/Shanghai)
Goal: 生成当天技术新闻摘要，写入指定 markdown 文件。
Inputs: 仅使用 news-fetch MCP 的 get_top_stories，limit=20。
Steps:
1. 调用 get_top_stories(limit=20, date=today)。
2. 按 title 和 url 去重，排除非技术类。
3. 生成摘要，每条不超过 80 字。
4. 写入 /data/digest/YYYY-MM-DD.md，若文件已存在则跳过。
Output: /data/digest/YYYY-MM-DD.md，UTF-8，frontmatter 含 date 和 count。
Idempotency: 写入前检查目标文件是否存在，存在则直接 report "skipped"。
Failure: 如果 news-fetch 报错或返回为空，停止并报告错误，不要使用其他来源补充。
Constraints: 只允许读 /data/digest/；不允许删除、覆盖其他文件。
Acceptance: 文件存在且包含 10-20 条条目。
```

这个模板把“弹性”留在摘要生成，把关键路径写死。

## 踩坑点

1. **时区问题**：cron 表达式本身不带时区。OpenClaw/容器默认常为 UTC。一定要在 Schedule 字段显式写 IANA 时区，如 `Asia/Shanghai`。能加环境变量 `TZ` 就加。
2. **幂等缺失**：定时任务可能因为队列重试或手动补跑重复触发。写入文件前必须检查存在性；对数据库写操作要定义唯一键或去重键。
3. **路径混乱**：agent 有时会“聪明地”改文件名或目录。Output 字段必须给绝对路径和命名规则，并加 Constraint：不得自行修改。
4. **权限过大**：不要给 Cron agent 开放整个 workspace 可写权限。最好给任务独立的目录/工具白名单。
5. **失败后继续**：最危险的是“某步失败后 AI 找替代方案”。必须写 Failure：任一步失败即停止并报告，不要 improvisation。这是无人值守任务最重要的约束。
6. **自然语言时间冲突**：如果正文有“早上/晚上”等描述，与 cron 不一致时模型可能犹豫。统一以 Schedule 字段为准，正文不重复写时间。

## 可复用建议

- 每个 Cron 任务保存为一份独立 instruction 卡片，版本化管理。
- 上线前先手动触发一次，检查产物路径、格式、运行时长。
- 日志输出固定化：要求任务末尾报告 `status: ok/skipped/failed`，方便后续排查。
- 在 instruction 末尾加一句：`If any step fails, stop and report. Do not improvise, do not use alternative tools.`
- 对敏感任务增加“只读模式”或 dry-run 指令，先输出拟执行的命令，人工确认后再放开。
- 不要把所有定时任务塞进一个 agent，职责越单一越稳。

## 总结

Cron 任务的 prompt 工程不是把话说得更礼貌，而是把歧义和自主性压到最低。把时间、输入、输出、失败、权限写清楚，就是一份“可执行规格”。

好的定时任务指令，应该让 agent 在凌晨三点没人看的时候，也像白天有人在旁边盯着一样执行。
