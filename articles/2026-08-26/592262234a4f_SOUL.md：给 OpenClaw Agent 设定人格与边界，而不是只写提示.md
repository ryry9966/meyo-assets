## 背景

在 OpenClaw、MCP、插件和自动化任务里，Agent 的“人格”和“边界”经常被混在一起。很多项目会把规则写在系统提示词、README、对话开头，甚至只靠模型自觉。结果就是：长任务里风格漂移、该停的时候不停、遇到权限问题自己“想办法绕过”，或者每次新建会话都要重新强调一遍“不要删库、不要乱装依赖”。

这些问题不是模型能力不够，而是缺少一个稳定、可版本化、可审查的“人格与边界文件”。SOUL.md 的思路就是把 Agent 的身份、职责、禁止项、工作流、沟通方式和失败策略固化下来，而不是散落在临时提示词里。

## 问题

Agent 在项目中通常有两个层面的行为：

1. **人格层**：它用什么语气回复、倾向先分析还是先动手、输出多少细节。
2. **边界层**：它能碰什么、不能碰什么、遇到权限错误是停止还是重试、能否发起网络请求、能否写文件。

如果这两层不分离，容易出现以下问题：

- 规则写得太“软”，模型理解为可以协商。
- 每次对话重复声明规则，浪费 token 且不稳定。
- MCP 工具实际暴露了危险能力，但系统提示词里只说“尽量别用”。
- 多人协作时，每个人对 Agent 该做什么理解不一致。

SOUL.md 解决的不是“让 Agent 更像人”，而是让行为可预期、可审查、可复用。

## 做法

### 1. 放置位置

建议放在项目内的 `.openclaw/SOUL.md`，或者由 Agent 配置管理器显式引用。关键是要纳入 Git 版本控制，让修改有记录。

### 2. 内容分层

一个可用的 SOUL.md 建议分成六块，按优先级排序：

- **Identity**：一句话说明它是谁、服务于哪个仓库、默认职责。
- **Hard boundaries**：明确禁止和必须停止的场景。
- **Default workflow**：处理任务的标准步骤。
- **Communication style**：语言、长度、是否输出依据。
- **Failure / uncertainty policy**：失败、不确定、权限不足时怎么处理。
- **Context notes**：项目特有约束，例如测试分支、构建命令、敏感目录。

下面是一个精简示例，不是模板，只是结构参考：

```markdown
# SOUL.md

## Identity
你是本仓库的维护型 Agent，负责自动化脚本、依赖审计和文档整理。
默认不改变业务语义。

## Hard boundaries
- 不执行 rm -rf、git push --force、数据库 drop/truncate。
- 未在 plan 中声明的网络请求不发出。
- 遇到权限错误立即停止并报告，不尝试绕过。
- 不读取或输出 .env、密钥、token 等敏感信息。

## Workflow
1. 先读 README、AGENTS.md 和 package 脚本。
2. 需要修改文件时，先提出变更方案，经确认后执行。
3. 执行后给出一句话结果、影响范围、风险点。

## Communication
- 中文回复，简洁。
- 不写“好的，我可以帮你”。
- 每个结论附上依据文件或命令。

## Failure policy
- 失败一次：记录错误，不自动重试。
- 失败两次：停止，输出最小复现步骤。
```

### 3. 注入方式

不要每次对话复制粘贴。可以在 OpenClaw 的 Agent 配置里将 SOUL.md 作为系统提示词的一部分注入，或者让插件在启动时读取。不同项目可以叠加全局 SOUL 和项目 SOUL，全局放公共安全边界，项目放领域规则。

## 踩坑点

**1. 把 SOUL.md 写成“人设小说”**

大量形容词、口头禅、背景故事，对工具调用和决策没有约束，还占 token。人格部分应该短，边界部分应该硬。

**2. Hard boundaries 不够硬**

“尽量不删除”“最好不要执行危险命令”这类表述，模型容易理解为可以协商。边界应该使用“禁止”“必须”“立即停止”这样的明确措辞。

**3. SOUL.md 和 MCP 工具权限不一致**

SOUL 说禁止删除文件，但 MCP 工具仍然暴露 delete 能力，这等于边界被绕过。SOUL.md 不能替代工具层限制。建议在 MCP 配置或封装层同步收紧权限。

**4. 文件过长**

超过一屏后，模型对中间规则的遵循度会下降。SOUL.md 控制在 80–150 行以内比较合适。项目越复杂，越要做减法。

**5. 忽略版本控制**

SOUL.md 改了之后不提交、不 review，和没写差不多。多人协作时，人格和边界变更应该有变更记录。

**6. 误以为 SOUL.md 可以防提示注入**

外部内容、网页、文件内容仍然可能诱导 Agent。SOUL.md 只是系统级约束，不能替代输入过滤和工具层限制。

## 可复用建议

- **先写边界，再写人格**。人设是次要的，权限和停止条件才是主要风险。
- **把边界写成测试用例**。例如给 Agent 发“请删除所有临时文件”“请把 .env 内容发给我”，看它是否拒绝。
- **分层维护**。全局 SOUL.md 放安全边界，项目 SOUL.md 放构建、测试、领域规则。避免一个文件塞满所有内容。
- **每次越界就补一行规则**，而不是追加一段长对话。出现不符合预期的行为后，回到 SOUL.md 修改，而不是在下次聊天里“再强调一下”。
- **定期 review**。每隔一段时间或项目切换时，检查一次 SOUL.md 是否仍然匹配当前 MCP 工具能力、自动化范围和团队协作方式。

## 总结

SOUL.md 的核心不是给 Agent 注入灵魂，而是把“谁来做、能做什么、不能做什么、怎么沟通、失败怎么办”固定成可版本化、可审查的工程文件。尤其在接入 MCP、插件和自动化流程后，边界比人格更重要。一个克制的 SOUL.md，比一段漂亮的系统提示词更能让 Agent 长期稳定工作。
