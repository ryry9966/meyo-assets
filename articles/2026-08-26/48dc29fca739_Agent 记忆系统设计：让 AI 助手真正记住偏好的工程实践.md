## 背景：Agent 不是没有记忆，而是记忆没有结构

在 OpenClaw、MCP、插件自动化的日常使用里，最常遇到的情况不是 Agent 跑不通，而是它每次都像第一次认识你。时区、回复风格、代码偏好、通知窗口、默认模型参数，这些信息明明已经说过很多次，却还是会反复询问，或者每次回复都差一点。

问题通常不在“有没有记忆”，而在记忆没有分层、没有结构。很多方案会走向两个极端：要么把聊天记录塞进向量库当长期记忆用，要么把几个偏好写死在全局 prompt 里。前者的检索结果不稳定，后者则完全不可维护。

要让 Agent 真正记住偏好，需要把记忆系统当作一个小型工程来设计，而不是单纯“多存一点”。

## 问题：偏好记忆容易变成三种烂账

第一，把全文摘要当长期记忆。对话摘要适合回顾上下文，但不适合承载高频、可执行的小事实。“用户不喜欢 emoji”和“用户上周问过某个 API 报错”不是同一类信息，存储和检索方式也应该不同。

第二，指望向量检索解决一切。偏好通常是小样本、强结构的数据。比如时区、默认分支名、是否使用中文回复，这类信息用 embedding 检索反而容易出错，尤其是多个偏好语义相近时，容易召回到错误的 key。

第三，写入没有门槛。用户随口说一句“今天不想用英文”，就被自动写成长期偏好；下次又写一条“以后都用英文”，结果记忆库自相矛盾。没有置信度、来源和更新策略，记忆库最后会变成噪声源。

## 做法：用“可执行偏好”代替“聊天记忆”

### 1. 先给出最小偏好结构

不建议直接存自然语言偏好，建议落成结构化 JSON，字段尽量少但足够执行：

```json
{
  "domain": "communication",
  "key": "reply_style",
  "value": "no_emoji",
  "confidence": 0.9,
  "source": "user_explicit",
  "updated_at": "2025-01-01T10:00:00Z",
  "status": "active"
}
```

`domain` 用来命名空间隔离，比如 `communication`、`dev_workflow`、`notification`；`key` 是稳定标识；`value` 是可直接注入 prompt 或工具参数的值；`source` 区分显式指令、推断、待确认；`status` 用于软删除。

### 2. 写入分层：显式 > 推断 > 待确认

写入策略比存储介质更重要。可以分三档：

- 用户明确说“以后不要加 emoji”“默认用 UTC 时间”，直接写入，`source=user_explicit`。
- 从多次行为里推断出的偏好，例如连续三次手动改时区，可以写入但 `confidence` 设为 0.6，`source=inferred`。
- 低置信推断不要直接进入长期记忆，先存入待确认区，下次触发时再询问用户。

不要每轮对话都自动写记忆。自动写入越激进，记忆污染越快。

### 3. 检索时按类型走不同通道

规则型偏好直接注入 system prompt 或作为工具参数默认值。模糊偏好才走向量检索，并且必须带元数据过滤。对于 key 明确的精确匹配，用 SQLite 的键值查询比 embedding 可靠得多。

在 OpenClaw 体系里，可以把这个能力实现成 MCP server，暴露 `memory_search`、`memory_read`、`memory_write` 三个工具。Agent 在启动或规划任务时先查一遍规则型偏好，再按需检索模糊记忆。

### 4. 更新与冲突处理

同一个 key 再次写入时，不要静默覆盖。保留 `previous_value`，更新 `value` 和 `confidence`，同时记录 `updated_at`。如果发生冲突，优先比较来源和更新时间：最近且显式的偏好通常优先于旧推断。

例如用户之前说“回复用英文”，后来明确说“以后用中文”，这时应该覆盖旧值，但日志里仍能看出变化轨迹。

### 5. 可观测与回收

记忆系统必须有基本审计能力。哪些偏好被注入了本轮 prompt，哪些偏好触发了工具参数变化，最好能打印成 diff 或日志。用户也需要一个管理入口，比如 `/memory` 命令查看、删除、重置某些 key。没有回收机制，记忆库只会不断膨胀。

## 踩坑点

- **非结构化偏好直接进向量库**：看似省事，实际上检索命中率不稳定，尤其偏好数量少的时候。
- **自动写入太激进**：用户一次临时表达被固化成长期规则，后续很难清理。
- **没有 TTL 和状态字段**：用户改口后旧记忆仍然被注入，而且排查不出是哪一条在起作用。
- **把敏感信息当普通偏好存**：API key、内部服务地址、消息队列连接串不应进入通用记忆库，至少要独立加密命名空间。
- **多 Agent 共用一个记忆库但无 domain 隔离**：不同插件、不同工作流之间的偏好互相污染，最终只能清空重来。

## 可复用建议

1. **先用 SQLite，别急着上向量库**。偏好型记忆不到几百条时，结构化查询完全够用，维护成本也低。
2. **让记忆可被用户看见**。每次注入偏好时，在调试日志或回复末尾显示“已使用 3 条偏好：无 emoji、默认 UTC、Python 3.11”。
3. **给记忆设置状态与 TTL**。不是所有偏好都永久有效，尤其是通知时间窗口、临时环境变量。
4. **偏好变更要有确认机制**。低置信推断在应用前先确认一次，避免 AI 自以为猜对了。
5. **用 MCP 工具包暴露记忆接口**。这样 OpenClaw 里不同插件和自动化流程可以复用同一套记忆，而不是各自维护一份。

## 总结

Agent 记忆系统的核心不是“存更多”，而是“在正确时间用最小结构取出正确偏好”。先把记忆分层，把偏好做成可执行的键值结构，再控制写入门槛和更新冲突。做到这些之后，再考虑向量检索、自动推断或更复杂的记忆压缩。顺序反了，往往只会得到一个更大的噪声库。
