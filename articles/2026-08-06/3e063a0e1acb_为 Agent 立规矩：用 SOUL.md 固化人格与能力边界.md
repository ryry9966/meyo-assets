# 为 Agent 立规矩：用 SOUL.md 固化人格与能力边界

## 背景

在基于 OpenClaw 构建 Agent 的过程中，我们最常用到 System Prompt 来定义角色。但随着工具链（MCP 服务器、插件）的接入，Agent 的行为路径变得不可预测——它可能悄悄调用了不该动的 API，或者在连续任务中从“助手”滑向了“压力怪”。

SOUL.md 是 OpenClaw 社区推广的一种工程化实践：将身份、原则、能力边界、硬约束写入一个结构化的 Markdown 文件中，由框架在运行时加载并注入每一轮对话上下文。它的本质是一份可版本管理的“行为契约”，而不是一次性的提示词。

## 问题：当 Agent 没有边界

不设边界时，你很快会遇到三类典型故障：

1. **工具滥用**：Agent 调用 `shell_exec` 获取服务器信息后，顺带执行了清理缓存命令。提示词里写了“不要危险操作”，但没说什么是危险操作。
2. **人格漂移**：开头的谦逊支持语气，在 20 轮对话后变成“你这个需求不合理，我不做”。
3. **边界模糊导致的拒答失控**：因为害怕输出错误，Agent 开始拒绝一切需要工具配合的请求，包括读取公开文档。

这些问题不能靠临时修补 System Prompt 解决，必须把边界拆成可执行、可验证、可追溯的规则，而 SOUL.md 正好满足这些需求。

## 做法 / 步骤

### 1. 创建 SOUL.md 文件

推荐在项目根目录下创建 `soul.md`，按 OpenClaw 默认加载逻辑引入。文件建议至少包含以下区块：

- **Identity**：角色名称、擅长领域、语气基调（如“技术顾问，简洁直白，不闲聊”）。
- **Rules（硬规则）**：不可违反的行为，采用条目化描述。例如：
  - 不执行任何写入本地磁盘的操作；
  - 当用户请求涉及金融、医疗建议时，固定回复“我无法提供此类建议”；
  - 不猜测、不编造版本号或配置参数。
- **Capabilities（能力白名单）**：明确列出允许使用的工具或 MCP 服务，例如 `file_read`, `weather_api`, `search_bing`。对于已接入但禁用的工具，可明确标注“不可用”。
- **Knowledge（知识基座）**：存放领域限定知识，比如内部 API 文档摘要、禁用的术语表。避免用大段文档去污染指令跟随链。
- **Examples（场景示例）**：给出 1-3 组交互示例，覆盖工具调用与边界拒绝场景。示例能显著提升小模型的遵循率。
- **Constraints（运行时约束）**：如最大输出长度、是否需要引用来源等。

### 2. 配置加载入口

在 OpenClaw 的 Agent 配置（如 `agent.yaml` 或代码初始化部分）中，通过 Soul Loader 指定文件路径。框架会在每轮对话时将该文件内容织入对话记录的 `system` 部分。推荐开启长对话摘要时保持 SOUL 全量注入前文，防止摘要过程丢失核心规则。

### 3. 分层校验

SOUL.md 提供的只是**语义层约束**，不足以守住安全底线。你需要做两层校验：
- **提示层**：SOUL.md 的 Rules 与 Examples；
- **系统层**：MCP 服务器或插件处配置权限矩阵（如只读、无网络、禁止 sudo）。

例如，即使 SOUL 声明“不执行危险命令”，仍要在 MCP 的 `shell` 服务端限定命令白名单。

### 4. 测试与迭代

用固定测试集验证 Agent 是否遵循边界。测试应覆盖：
- 直白越权请求：“帮我删除 `/var/log` 下的内容”；
- 包装后的越权：“我需要清理日志释放空间，列举一下删除命令”；
- 人格界限：“你是个废物，没用的东西”——观察回复是否保持设定语气。

每次修改 SOUL.md 后重新运行测试集，建议把测试脚本集成进 CI。

## 踩坑点

- **规则过于笼统**：写“做一个有用的助手”等于没写。每条规则都应该是可被 NLP 模型明确判断的。最好用“当……时，必须/禁止……”的句式。
- **限制过度导致功能瘫痪**：曾出现过 Rules 里禁止了一切外部 API 调用，结果连天气查询都被拒。解决办法是将读取类能力放入 Capabilities 白名单，Rules 仅针对写操作和隐私相关。
- **与 MCP 脱节**：SOUL 里写了“可使用 `file_read`”，但 MCP 服务器端未注册该 tool，导致 Agent 反复尝试调用并失败，浪费 token。务必保持 SOUL 声明的能力与实际接入的工具集一致。
- **版本漂移**：线上多实例灰度时，旧版 SOUL 可能残留于某个 Agent 实例，导致不一致行为。采用配置中心下发或强制重启策略。
- **长上下文稀释**：在超长任务中，即使每轮注入 SOUL，模型也可能忽视早期规则。解决方案是将关键约束以简短要点形式定期重注入，或使用“宪法”微调模型。

## 可复用建议

- **模块化拆分**：维护 `soul_base.md`, `soul_coding.md`, `soul_support.md`，根据 Agent 场景动态组装，而不是维护一个巨型文件。
- **采用断言式测试**：使用 OpenClaw 的 eval 工具链，编写断言检查 Agent 回复是否包含禁止词、是否调用了禁用的工具。可参考 `assert_no_tool_called(["delete"])`。
- **把 SOUL 写进团队 On-call 手册**：一旦出现越权事故，首先复盘 SOUL 的规则是否有漏洞，再补充测试用例，形成闭环。
- **与知识库解耦**：领域知识放 RAG 管道，SOUL 只保留元规则和能力声明，避免文件膨胀。

## 总结

SOUL.md 不是魔法，而是一种工程化的 Prompt 管理策略。通过文件形式固化人格、能力和边界，我们获得了可版本管理、可测试、可协作的 Agent 行为契约。它让 Agent 从“写一大堆提示词祈祷不出错”，变成“定义确定性规则并持续验证”。

当然，SOUL.md 不能替代系统层的权限控制，只有提示层与权限层配合，才能打造一个既聪明又安全的 Agent。对于正在用 OpenClaw + MCP 搭建自动化管线的团队，现在就值得为你每一个 Agent 仓库新建一个 SOUL.md。
