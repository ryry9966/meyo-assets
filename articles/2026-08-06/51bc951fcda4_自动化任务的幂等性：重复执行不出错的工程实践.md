## 背景：为什么重试和补跑总是带着风险

在 OpenClaw、MCP 工具链或任何自动化管线里，你很难避开这几个场景：

- 任务执行到一半超时，系统触发自动重试；
- 凌晨的定时任务因为上游数据延迟，手动补跑一次；
- Agent 判定结果不确定，重复调用同一个 MCP 工具；
- 插件升级后需要回溯历史数据，脚本需要“安全地再跑一遍”。

如果没有幂等设计，重试就是一场赌博：重复创建资源、重复发送通知、重复扣减配额，甚至污染业务数据。事后修数据往往比写任务本身花更多时间。

这篇内容不谈概念空话，只围绕 OpenClaw/MCP/插件类自动化场景，给出可复现的幂等设计方法和踩坑复验。

## 问题：非幂等执行的具体破坏形式

举几个贴近自动化实践的例子：

1. **重复创建**  
   MCP Server 封装了云资源 API（比如创建临时 token、创建测试环境）。Agent 调用超时后重试，如果没有幂等键，可能会生成两个 token，旧的泄漏，新的覆盖，或两个并存造成混乱。

2. **重复扣费/消耗配额**  
   自动化流程调用一个扣减积分的 MCP 工具，工具端没有做幂等，重试导致多次扣减。用户投诉后，需要人工补回，运维成本陡增。

3. **状态机错乱**  
   一个插件管理任务状态（待处理→处理中→已完成）。重复执行没有判断当前状态，可能把已完成的业务又拉回“处理中”，甚至重复触发下游回调。

4. **通知轰炸**  
   重复调用了发送通知的 Action，用户收到多条一样的消息，体验变差，甚至触发反垃圾机制。

这些问题的共同根源：**操作本身不是幂等的，而调用方又无法保证只调用一次。**

## 做法与步骤：落地的幂等设计模式

下面是在工具/Agent/插件层面可以采用的工程方法，结合具体代码习惯给出推荐。

### 1. 业务天然幂等键 + 唯一约束

最可靠的方式：在产生副作用的操作里，要求调用方传入 `idempotency_key`（幂等键），底层存储做唯一约束。

**示例：创建临时访问凭证的 MCP 工具**

```python
# 工具定义
def create_temp_token(idempotency_key: str, ttl: int) -> Token:
    # 先查是否已存在
    existing = db.query(Token).filter_by(idempotency_key=idempotency_key).first()
    if existing:
        return existing
    token = generate_token(ttl)
    try:
        db.add(Token(idempotency_key=idempotency_key, value=token, ...))
        db.commit()
    except IntegrityError:
        # 并发下唯一键冲突，再次查询返回已创建的
        db.rollback()
        existing = db.query(...).filter_by(idempotency_key=idempotency_key).one()
        return existing
    return token
```

**适用场景**：资源创建类、外部 API 调用（很多支付/云平台都支持幂等键，直接用）。

**落地要点**：幂等键生成策略要稳定（例如 `{task_id}_{action_type}` 或内容 hash），不能每次重试都变。

### 2. 状态前置检查 + 乐观锁

对于状态流转类操作，在修改前必须校验前置状态，并使用条件更新（乐观锁）避免并发覆盖。

**示例：任务状态更新插件**

```sql
UPDATE tasks
SET status = 'processing', version = version + 1
WHERE id = ? AND status = 'pending' AND version = ?;
```

若受影响行数为 0，说明状态已变更，直接返回幂等成功（或者查询当前状态决定下一步）。

**在 Agent 工作流里**：每次调用状态变更工具前，Agent 先查询当前状态，再决定是否继续执行，避免盲写。

### 3. 事务性标记 + 事后清理

有些操作无法天然幂等（比如发送邮件、推送通知），可以采用“先记录意图，再执行，最后标记完成”的 At-Least-Once 模式。

**步骤**：
1. 在数据库中插入一条操作记录，状态为 `pending`，带有幂等键；
2. 执行实际操作（发送通知）；
3. 成功后更新该记录状态为 `done`。

重试时，如果发现已有 `done` 记录，直接返回；如果是 `pending`，检查实际操作是否需要重新执行（可通过查询外部系统状态判断）。这样至少不会重复发送。

**给 OpenClaw 插件开发者的建议**：尽量把副作用操作封装成“意向记录+异步执行”，MCP 工具只负责注册意向，实际执行交给 consumer，这样重试安全性极高。

### 4. 分布式并发下的去重：锁或数据库约束

在多个 Agent 实例或定时任务并发时，仅靠应用层的“先查后写”会有 TOCTOU 问题。解决方案本质上只有两个：

- **数据库唯一约束**（最强，依赖 DB 层原子性）
- **分布式锁**（Redis `SETNX` 加锁，锁的粒度 = 幂等键，执行完释放）

优先使用唯一约束，少一层基础设施依赖。锁只在操作不适合拆分为单一 insert 时使用（例如涉及多个跨服务调用且无法做整体幂等）。

## 踩坑点

1. **幂等键选取太粗或太细**  
   太粗：同一批任务共用一个 key，某次执行成功后，同批其他数据永远无法重跑。  
   太细：每次请求都随机生成 key，幂等设计形同虚设。  
   **建议**：用业务语义组合（用户ID + 操作类型 + 业务单号）或内容指纹（SHA256）。

2. **只做了接口幂等，没做全链路幂等**  
   工具内部保障了，但 Agent 层的重试逻辑没传递同一个幂等键，仍然可能重复调用。  
   **修复**：OpenClaw 的任务调度器在重试一个 task 时，必须将同一个 `idempotency_key` 注入给 MCP 工具调用。可以在 task context 中持久保存这个 key。

3. **幂等返回结果不一致**  
   第一次调用成功返回完整数据，重试时可能只返回空或部分数据，导致调用方逻辑错误。  
   **约定**：幂等返回必须与首次成功返回的结构保持一致（至少关键字段一致），必要时把首次响应存入幂等记录中。

4. **忽略外部服务自身的幂等支持**  
   很多 SaaS API (Stripe, AWS) 直接支持 Idempotency-Key header，用起来比自己造轮子可靠得多。能外包给专业服务就别自己扛。

## 可复用建议

- **在插件/MCP 工具接口层面，强制要求幂等键**。即使工具内部暂时不做去重，也为以后留出扩展点。
- **做自动化任务框架时，将“安全重试”作为一等公民**：所有 task 都应该有一个稳定的 `task_idempotency_key`，它贯穿整个执行链路。
- **建立小的幂等验证脚本**：模拟并发重试（例如同时发送两个相同 payload 的请求），检查是否只产生一次副作用。集成进 CI 比事后发现成本低得多。
- **文档中显式标注“可安全重试”或“不可重试”**，让使用你插件的开发者一目了然。

## 总结

自动化任务的幂等性不是“额外需求”，而是可靠性的一部分。在 OpenClaw/MCP 这类组合式自动化生态里，一次失控的重复执行就可能腐蚀整个管线的数据可信度。

幂等设计的工程成本并不高：一个好用的幂等键、一个唯一约束、一段前置状态检查代码，就能消灭大部分事故。关键是把它作为开发习惯，而不是出了事再补漏。

下次写重试逻辑或手动补跑时，能自信地说一句“再跑十次也不会出问题”——那才说明幂等性真的落地了。
