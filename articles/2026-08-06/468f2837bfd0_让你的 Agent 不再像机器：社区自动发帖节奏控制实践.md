## 背景

基于 OpenClaw / MCP 搭建的自动化流程里，社区发帖是个高频需求。比如拉取监控摘要推到 Discord，把周报同步到 Slack，或者让知识库 Agent 定期在 Discourse 上发布更新。一开始一切正常，但运行几天后普遍会撞上同一堵墙：平台把 Agent 判定为 bot，限流、警告甚至封禁。

这些反作弊系统往往不是看你“发了什么”，而是“怎么发的”。只要发帖节奏与人类行为偏差太大，内容再自然也容易被标记。所以单靠 prompt 优化不够，需要对发帖的时序、频率和交互模式做工程化控制。

## 问题剖解

典型的机器人发帖特征包括：

- 间隔固定，比如每 3600 秒一条，误差小于 5%；
- 发布时间毫无缘由地精确，总是在整点或半点出现；
- 同一模板反复使用，只有数字变化；
- 没有上下文交互，比如发完即走，不读取频道内最新消息；
- 遭遇限流后立即按原频率重试，形成重试风暴。

社区平台通常会综合这些信号打出一个“非人类”分。而我们在 OpenClaw 中很容易把发帖动作写成简单的 `sleep + send`，缺少节奏建模。因此需要引入一套可复用的节奏控制层。

## 做法与步骤

### 1. 用非均匀分布替代固定延迟

不要使用 `random.randint(min, max)`，这会让人觉得时间间隔始终落在某个均匀区间，统计上很容易露馅。应选择类泊松过程或对数正态分布，模拟人类“想起来就去发”的节奏。

示例（Python）：
```python
import random
base_delay = 3600  # 目标平均间隔
jitter = random.expovariate(1.0 / base_delay)
```
如果你想按时间段调整活跃度，可以维护一个小时级的基线倍率。比如夜间乘以 2，早晨乘以 0.8。把因子乘到 `base_delay` 上，再用指数分布产生实际间隔。内部持有一个“下次允许发送时间”，而不是每次等待固定时长。

### 2. 内容去模板化与约束变形

对自动生成的内容做可控变形。假设你每次调大模型输出一段发布文本，就在 prompt 中加入随机种子（日期、频道最新话题、随机选择的语气词），要求以不同句式开头，且穿插一些口语化的连接词。还可以在结尾随机追加类似“顺便问一下…”或“大家怎么看？”的短句，模拟参与感。

关键是为变形设置边界，避免核心数据失真。可以在 MCP 工具链里再加一个校验步骤：提取结构性信息与原始数据比对，偏差超过阈值则驳回重新生成。这样既增加了多样性，又不会把错误数值发出去。

### 3. 模拟浏览与打字延迟

人类在社区发帖前通常会先扫一眼最近的消息。因此发帖 actor 在构造完消息后，不要立刻发送。通过 MCP 工具读取频道最新 5～10 条消息，等待一段阅读延迟（比如每条 2～5 秒），再执行发送。如果平台 API 支持分段发送（例如 Slack 的 typing indicator），可以模拟打字节奏发送逐段消息，让整个交互更像真人。

### 4. 令牌桶 + 自适应限流

在发帖动作前面加一个速率控制器，使用令牌桶算法。令牌生成速率根据近期社区活跃度动态调整：如果频道里其他人发言频繁，可适当提高生成速率；如果只有你的 Agent 在说话，就要降至最低维稳频率。桶的大小设置一个合理突发上限（例如 3），防止令牌积攒后瞬间连发。

若收到 HTTP 429 或平台限速事件，立即停止令牌生成，进入指数退避，并把退避状态通知 OpenClaw 的管理 actor，暂停其他计划任务。恢复时缓慢增加令牌生成速率，不要直接复位。

### 5. 构建反馈闭环

当 Agent 发出的消息获得回复、回应或 emoji 反应时，说明这次发布被社区接纳，可以小幅上调该频道的活跃权重；如果长时间无人回应，则自动降低发布频率，避免成为“自言自语”的信息孤岛。这个闭环可以通过订阅 MCP 事件流实现，在 OpenClaw 的 task 上下文中持续更新频道健康度。

## 踩坑点

- **随机数分布选错**：简单均匀分布很快会被频次分析识别。一定要用无记忆或重尾分布，并且定期用卡方检验自查生成序列，防止随机源退化（例如容器重启后种子重复）。
- **令牌桶设计失误**：没有突发限制导致长时间静默后突然爆发；或者令牌生成速率固定，没有根据社区节奏浮动，白天可能还在“睡觉”，晚上却异常活跃。
- **变形过度**: 追求文本多样化导致数据错误。必须在变形后对数字、专有名词、链接等做确定性校验。
- **不同平台限流语义不一致**：Discord 有全局速率限制，Slack 使用 per-channel 限制，Discourse 的 API 限流看用户级别。统一调度时，需要为每个平台维护独立的令牌桶和退避状态，不可混用。
- **忽视上线后的观察**：初始参数（平均间隔、活跃时段倍率）多半靠猜，上线后必须收集真实频道活动数据，迭代优化。否则很可能两周后又被标记。

## 可复用建议

在 OpenClaw 体系内，可以把上述逻辑抽成一个 **RhythmController 插件**（作为 MCP 工具提供）。它维护每个目标社区的状态机，暴露两个核心方法：

- `request_permit(target, context)`：基于频道健康度、历史令牌情况返回等待秒数或立即放行。
- `report_feedback(target, interaction)`：上报互动事件以调整权重。

发布任务本身变成普通的 OpenClaw task，只是在发送之前调用 RhythmController 获取许可。遇上延迟，task 被挂起并在计时器到期后自动恢复。这样所有社区发帖的节奏逻辑都集中收敛，无需在每个 Actor 里重复实现。

同时，将内容变形、校验流程封装成单独的 MCP 工具，命名为 `humanize_content`，接收原始 payload 和随机种子，返回变形后的文本及校验结果，可以横向复用到其它通知场景。

## 总结

让自动发帖不像机器，本质上不是靠对抗平台，而是把自动化流程嵌入到真实的社区时间感和互动习惯中。通过泊松等非均匀延迟建模、有界内容变形、浏览模拟、自适应令牌桶和闭环调整，Agent 可以在长时间运行后依然维持低调的存在感。工程上，把这些控制抽象为 MCP 工具后，能显著降低在 OpenClaw 生态里多个社区平台协同的维护成本，也让发帖这件事本身变得更健壮、更可持续。
