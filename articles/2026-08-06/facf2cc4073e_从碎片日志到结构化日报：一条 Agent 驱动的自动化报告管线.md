## 背景

日常站立会前，需要汇总前一天的工作进展、风险点和今日计划。数据散落在 Git 提交记录、Jira/Tapd 任务变更、监控告警通知、文档批注甚至对话记录里。手动查找、粘贴、格式化不仅低效，还容易遗漏关键上下文或引入笔误。团队曾尝试用脚本拼接固定模板，但日志来源一多，维护脚本的逻辑分支和正则规则很快就失控。

我们希望构建一条能力更强、容错性更好的管线：**从原始日志自动产出结构清晰、可直接投递到群聊的日报草稿**。核心思路是利用 LLM 的语言理解与摘要能力，结合工具链完成数据抓取、清洗、聚合和规范化输出。

## 问题拆解

这条管线面临的主要挑战不是“能不能生成”，而是：

- **多源异构**：不同系统的 API 返回格式、字段语义不统一，时间戳精度也不同。
- **噪声大**：大量自动提交、合并消息、测试流水线日志混合在工程活动里，直接塞给模型会稀释真正有用的信息。
- **Agent 幻觉**：LLM 容易在总结时“补全”出并不存在的任务或细节，尤其在时间窗口模糊时。
- **输出一致性**：日报的语气、粒度需要稳定，否则团队会觉得“今天像 AI 写的，明天像摘抄”。

## 做法与步骤

我们基于 OpenClaw 搭建了一条轻量级管线，整体流程分了四个阶段。

### 1. 定义日报模板（Markdown + 语义槽位）

将日报结构固定为可解析的骨架，例如：

```markdown
## 昨日进展
- [任务项] 状态：完成 | 进行中 | 阻塞
- [任务项] 关键产出/备注

## 风险与阻塞
- [描述] - 影响范围/期望解除时间

## 今日计划
- [任务项] 优先级：高/中/低
```

模板作为 prompt 的一部分直接传给 Agent，要求**必须严格按此格式输出**。同时为每个段落定义明确的“什么该写、什么不该写”的规则，比如“仅收录有实质代码变更或状态流转的任务，合并自动生成的 bump 类提交”。

### 2. 数据采集 —— MCP 工具化

借助 MCP（Model Context Protocol）将不同系统暴露为统一工具。我们为 GitHub、Jira、PagerDuty 各自搭建了 MCP server（也可直接使用社区已有的 connector），让 Agent 能通过函数调用直接拉取指定时间窗口内的原始日志。

关键配置点：

- **时间窗口**：定义为前一天 00:00 至当天 00:00（伺服器时区），并在请求中显式传入 ISO 格式字符串，避免 Agent 自行猜测“昨天”。
- **分页处理**：部分源（如 GitHub events）有分页，需在工具描述里明确返回方式，或让工具内部聚合后返回摘要列表，减少 Agent 的上下文消耗。
- **去噪预处理**：在工具层做一次简单过滤，比如排除自动标签机器人（如 dependabot）的 PR 和评论，仅保留人为活动。这一步不交给 LLM 判断，因为它既消耗 token 又可能误判。

### 3. 摘要与重组 —— Agent 的核心工作

将清洗后的原始数据连同日报模板和约束规则一同注入 Agent 的系统提示。提示词中强调：

- 仅使用提供的原始日志，**不得虚构任何任务或状态**。
- 若某任务在多次提交中出现，合并为一条，只保留最新状态。
- 如果某个槽位确实无内容，保留空行并标注“本日无”，不要强行生成。
- 语言风格要求：工程化、陈述事实、不带感情色彩。

我们使用了两阶段生成：首先生成 Markdown 草稿，然后由同一 Agent 执行一次自检，检查是否有未在日志中出现的内容，输出修正版本。实测能将幻觉概率从约 8% 降到 1% 以下。

### 4. 投递与备案

生成的日报直接推送到飞书/钉钉群机器人，同时以 YYYY-MM-DD.md 存入 Git 仓库备份。这样可以回溯，也为后续训练或规则优化提供素材。

## 踩坑点

**坑1：时区导致的时间窗口漂移**  
Agent 工具的“昨天”极易被理解为 UTC 的“昨天”，导致比团队所在地晚了 8 小时。解决方式是工具层面只接受绝对时间戳，并在 prompt 中硬编码时区偏移（如 `Asia/Shanghai`），完全不让模型做时间推导。

**坑2：长日志爆上下文**  
遇上频繁发布的系统，Git 日志可能一次几百条。即使过滤后仍可能超出 token 上限。此时需要在采集阶段增加“摘要型工具”——比如只返回 PR 标题+合并时间+责任人，而非完整 diff 或事件流。Agent 需要用摘要数据工作，而不是原始详细日志。

**坑3：模板理解的漂移**  
某天日报突然出现“### 昨日工作”这样的额外标题，导致下游解析失败。根因是模型对 Markdown 语法的创造性发挥。解决方法是在提示末尾加入固定后缀：“**输出时请直接以上述 Markdown 骨架开头，不要添加额外说明或前缀。**”，并加一个格式检查步骤（简单的正则匹配）。

## 可复用建议

1. **将模板和规则版本化**，存放在独立文件中，通过 include 方式注入 prompt，这样变更可以追溯，也方便团队 review。
2. **为每个数据源维护一个“健康检查”工具**，在采集前快速探测 API 可达性、最近事件时间，失败时产出明确告警而不是空数据，避免生成“昨日无事发生”的错误日报。
3. **增加人工校验环节**：管线的最后一步不是直接群发，而是推送到一个“日报草稿”频道，由接口人确认后一键发布。这样既保持自动化，又留有余地。
4. **用结构化日志记录 Agent 的决策依据**——它从哪些数据中提取了哪条结论，万一出现争议可以回溯，不至于成为黑箱。

## 总结

用 Agent 构建日报管线，难点不在生成本身，而在**定义清晰的边界**：什么数据进来、怎么清洗、模型能自主发挥到什么程度、输出失败时如何兜底。把确定性逻辑（过滤、时间计算、格式校验）交给工具和规则，把“理解与重组”交给模型，再用一层轻量级校验和人工确认来兜底，是一种性价比很高的工程实践。

这套方法可以自然延伸到周报、发布通知、客户交付总结等场景，只要将采集源和模板做相应替换，管线的骨架几乎可以复用。
