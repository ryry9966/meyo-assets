## 背景：不止一种模型，不止一个场景

OpenClaw 的多智能体设计让我们可以自由接入不同后端——远端的 GPT-4o/Claude-3.5 系列，以及通过 Ollama、vLLM 等本地部署的 Llama、Qwen 模型。相比“一条路走到黑”的单模型方案，混合使用能更精细地控制成本、延迟和数据驻留。

但在实际工作流里，很多团队会陷入两个极端：
- 所有 Agent 都调 GPT，账单暴涨，延迟累积；
- 全部切到本地模型，碰上复杂推理或需工具调用的任务就频繁翻车。

于是问题变成：**什么时候该用 GPT，什么时候该用本地模型？** OpenClaw 并没有内置“万能路由”，但它把模型选择权留给了节点配置和 Agent 策略，我们可以自己搭一套工程化的多模型路由。

## 问题拆解：不是能力高低，而是分工不同

首先明确，本地模型与远端闭源模型不是“弱 vs 强”的对立。我的经验是：

- **本地模型**：适合低延迟、高吞吐、数据敏感场景；强项在格式转换、摘要、简单问答；弱项在复杂多步推理和工具调用 schema 遵循。
- **GPT-4o 等**：适合需强推理、长上下文理解、稳定 function calling 的场景；代价是延迟波动、成本高、数据需要出站。

因此，路由的关键是 **按任务特征分配**，而不是按模型品牌。

## 做法：在 OpenClaw 中实现低成本模型路由

以我们内部用的邮件处理 Workflow 为例，整个链路包含 3 类节点，分别用到了不同策略。

**步骤 1：能力标签与模型池注册**

在 `model_config.yaml` 中声明可用模型及其能力标签，而不是只写一个默认模型：

```yaml
models:
  - id: gpt-4o
    provider: openai
    capabilities: [reasoning, function-calling, long-context]
  - id: llama3.1:8b
    provider: ollama
    capabilities: [fast, local, summarization]
  - id: qwen2.5:7b
    provider: ollama
    capabilities: [fast, local, multilingual]
```

标签由运维根据实际 benchmark 确定，避免主观。

**步骤 2：在 Agent 节点中编写路由逻辑**

在 `mail_agent` 的 planning 阶段，我们插入了一个简单的路由判断函数：

```python
def route_by_intent(state):
    msg = state["user_input"]
    if len(msg) < 200 and not any(kw in msg for kw in ["投诉", "退款", "合同"]):
        return "local_fast"
    return "gpt_reason"
```

对于短消息且不含敏感关键词，直接走本地模型，处理诸如“查询发货日期”这类高确定性任务。复杂投诉或需要解析多封关联邮件的，交给 GPT。

OpenClaw 的 `@router` 装饰器可以在节点前根据 state 切换执行分支。更细粒度时，可以结合轻量分类器：用本地小模型先对意图打分，置信度高于 0.85 的就地处理，否则升级给远端模型。

**步骤 3：工具调用作兼容层**

本地模型原生的 tool-calling 不如 GPT 稳定。我们做了个薄适配层：将工具定义注入 prompt，并解析本地模型的输出 JSON。出错就捕获异常，自动降级到 GPT 执行该步。

```python
except ToolParseError:
    state["model"] = "gpt-4o"
    return retry_node(state)
```

这样本地模型只需覆盖 70% 的简单调用，剩下 30% 的成本由 GPT 兜底，整体 API 费用下降了近 60%。

## 踩坑点：真实环境不会像 demo 那么干净

**1. 本地模型延迟的假象**

很多人以为本地比 API 快，但其实 CPU 推理的 7B 模型首 token 延迟可能到 2-3 秒，而 GPT-4o 的平均首 token 约 0.8 秒（非流式）。我们的做法是只在 GPU 节点部署本地模型，CPU 实例仅用于非实时批处理。

**2. 上下文窗口被撑爆**

本地模型大多上下文窗口只有 8k 或 32k，强行塞入长邮件链会 OOM。所以在前置节点必须做压缩摘要，仅把关键片段传给本地模型。

**3. 路由策略维护成本**

规则越复杂，越容易变成“又一个 legacy 系统”。建议最多维护 3 条规则：长度、意图关键词、最近 N 轮成功率。超过 3 条就应当用一个小模型做路由而非 if-else。

## 可复用建议：把路由当成数据闭环

- **搭建成本-质量看板**：记录每条请求的模型选择、令牌数、用户评分，定期回溯。一旦发现某类问题本地模型持续低分，就重新划入 GPT 路由。
- **预热与缓存**：对高频模板问题（如“如何重置密码”），本地模型结果加入 Redis 缓存，OpenClaw 节点直接匹配返回，跳过推理。
- **模型微调反哺**：收集掉入 GPT 兜底的问题，作为数据集周期性微调本地模型，让路由中本地模型的覆盖比例逐步走高。

## 总结

多模型路由不是一次性设计，而是一个持续运营的工程问题。OpenClaw 的灵活节点与状态管理提供了很好的基底，但真正的收益来自于对业务任务特征的厘清、兜底机制的完备，以及不断的反馈调优。

把 GPT 当专家顾问，本地模型当一线专员——这才是务实的分工。
