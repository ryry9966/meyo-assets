社区运营离不开内容发布。在 OpenClaw 社区维护周期较长的技术周报和插件更新说明时，靠人工去排版、校对、定时发布非常消耗精力。恰好团队在推广 MCP 插件生态，我把发帖流程做成一个可被 Agent 调度的工具，兼顾定时任务和按需调用。下面分享整个搭建过程和踩到的坑。

**问题定义**

需求本身不复杂：读取 Markdown 素材，定时调用社区 API 发布帖子，失败时需重试并通知。但实际运行中会出现几个隐性难题：

- Markdown 渲染效果与社区后端解析规则不一致，比如代码块被截断、图片链接失效。
- 短生命周期的 Bearer Token 和严格的速率限制。
- 发布内容由 Agent 生成时可能携带调试文本或越界内容。

于是将系统拆成四个模块：内容管道、调度器、API 客户端、监控钩子，后期再封装成 MCP 工具。

**做法与步骤**

*内容管道*
社区使用的平台后端对 ``` 代码块支持不佳，连续换行会导致渲染截断。解决方式是预处理器将所有代码块转成 `<pre><code>…</code></pre>` 形式。嵌入的本地图片必须预先通过附件接口上传，获取平台返回的资源 ID，再替换 Markdown 中的路径。上载图片时需注意并发限制，我选择用单线程队列逐张处理，避免触发风控。

*调度器*
最早在本地用 `schedule` 库跑常驻进程，因为机器休眠和任务队列堆积，发生过漏发和乱序。后迁移到 GitHub Actions，由 workflow_dispatch 和 schedule 触发，每次拉取最新 Git 仓库中的 Markdown 源文件执行发布。该方案免去运维负担，但调试需依赖 Actions 日志，且环境变量中的 Token 要使用 Secrets 管理，避免泄露。

*API 客户端*
社区接口用 Bearer Token 鉴权，有效期仅 2 小时，写端点速率限制为每分钟 5 次。早期因未处理 Token 过期，拆篇发布后半部分全部 401。后续封装了带自动续期的会话管理器：每次调用前检查 Token 剩余有效期，不足 5 分钟则重新获取；遇到 429 响应时读取 Retry-After 头并休眠后重试。另一个容易被忽略的点是话题创建的 category_id 随环境改变，不能直接硬编码数字 ID，必须先通过搜索接口由 slug 动态获取。

*监控钩子与调试模式*
每次发布的状态、消耗 Token 次数、耗时写入 Loki，失败时推送到内部 Slack 频道。同时设置了 dry-run 环境变量，开启后只生成最终的论坛 JSON 保存在本地，不会真正发送请求，满足人工审核需求。

*MCP 集成*
底层稳定后，整个发布管线包装成一个 MCP 服务器，暴露 `create_post` 工具，输入参数为 markdown_content 和 category。工具内部复用了上述所有逻辑，并增加了一层内容审核：用正则匹配 Agent 常见的调试痕迹（如 "As an AI…"），再结合简单的敏感词过滤。命中则返回错误提示用户修改，而不会把问题内容直接发出去。

**踩坑点总结**

1. **Markdown 与平台解析的鸿沟**：前端渲染正常不代表 API 提交就能正确显示。务必在沙箱环境完整走通各种元素（表格、嵌图、代码块）。
2. **状态化的 API 交互必须从第一天就封装成状态机**：Token 刷新、速率限制、重试机制都应内聚在客户端层，补丁式修改只会让后续调试更加困难。
3. **写操作不容犯错**：社区发帖无法撤回，MCP 工具必须具备审核和拦截能力，避免 Agent 幻觉直接发酵成线上事故。

**可复用建议**

如果你的场景类似，不妨先做一个极简的定时脚本验证发布闭环，再逐步添加预处理器、MCP 包装和告警。模块间用环境变量解耦，让每个组件可单独测试。整个项目代码量并不大，真正花时间的是对平台边界行为的理解和容错设计。做好这些，发帖机器人才能稳定地融入 Agent 工作流，而不是变成又一个需要人工擦屁股的半成品。
