## 背景：为什么只是加 sleep 不够

在做社区内容自动化的过程中，大多数人的第一反应是：“在两次发帖之间等一会儿不就行了”。于是出现了一堆 `time.sleep(3600)` 或者 `random.randint(300, 900)` 的实现。但跑上一周就会发现，平台该封还是封，该限流还是限流，甚至会看到某些帖子直接被影藏。

原因很简单：人类的行为不是一条均匀的时间轴。真实用户在社区里的活动是**高度混合且带有上下文关联的序列**——看完帖才回复，浏览几个话题后才发新帖，有时突然离开，有时密集互动。而单纯的固定间隔或均匀随机，在平台的风控特征里就像一张巨大无比的标签：“这是一个 cron job”。

当我们使用 OpenClaw + MCP 这类工具来搭建自动化流程时，控制的粒度已经可以从“调用一次 API” 上升到“模拟一个用户会话”。这给了我们一个真正解决问题的空间：**把节奏控制抽象成一个可配置的工程问题，而不是靠猜。**

## 问题建模：我们要控制什么

要“不像机器人”，本质上是要在三个维度上同时加入可控的熵：

1. **时间节奏**：何时执行下一步动作（发帖、评论、浏览）。
2. **动作序列**：不只是发帖，还包括阅读、点赞、版块切换。
3. **内容痕迹**：帖子本身的语言风格、长度、与上下文的关联。

如果只控制时间，哪怕用最棒的真随机数生成器，也会因为单动作、无上下文而被风控。因此，我们需要一个**基于有限状态机的会话模型**，让 Agent 自己决定“现在该干什么”。

## 实践：用 OpenClaw Agent 构建会话状态机

假设我们的目标是将长文自动分发到某个论坛（如 Discourse 或 Reddit 风格板块），下面的做法可以直接在 OpenClaw 的 agent 框架内落地。

### 1. 定义一个“用户会话周期”

将一次完整的上线行为拆分为若干阶段，例如：

- **WARMUP**：浏览首页、推荐流，随机点击 2~3 个帖子，停留时长符合重尾分布。
- **ENGAGE**：对其中 1 个帖子点赞或简短回帖（由 LLM 生成一句自然评论）。
- **POST**：在冷却时间后，才进入核心动作——发布新帖。
- **COOLDOWN**：发帖后继续浏览几分钟，模拟“回头看”，然后下线。

每个阶段由一个专门的 Tool 实现，OpenClaw 的 agent 根据状态调度对应的 MCP 插件（例如浏览器控制或 API 封装）。

### 2. 时间间距的控制：不要均匀，要爆发

看了大量非工作时间的论坛活跃日志后，会发现人类的上线间隔是**爆发模型（burst model）**：可能连续看 10 分钟，然后下线 3 小时，第二天又来密集操作。而机器人往往每 N 分钟/小时稳定产出，这本身就是很强的特征。

我们的做法是用**两阶段分布**生成间隔：

- 短间隔（`SHORT_PAUSE`）：用于会话内动作之间，如浏览->回复，通常 20~120 秒，使用 Beta 分布生成，让大部分值集中在中间，但允许偶尔极快或稍慢。
- 长间隔（`LONG_PAUSE`）：用于发帖与下一次上线之间，通常 2~24 小时，用对数正态分布结合一天中的活跃时段权重（夜间概率低，早晚高）。

在 OpenClaw agent 中，可以直接用 Python 的 `random.betavariate` 和 `random.lognormvariate` 实现这些分布，然后将结果乘上一个时段系数。时段系数可以做成一个配置文件，标记每小时权重，模拟作者所在时区。

### 3. 动作序列的混合

只发帖太单调。我们让 agent 每次进入 `WARMUP` 时，随机决定本次会话的“目标”，例如：

- 30% 概率：只浏览，不互动。（模拟摸鱼）
- 40% 概率：浏览 + 给 1 个帖子评论 + 发帖
- 20% 概率：浏览 + 发帖，不评论
- 10% 概率：浏览 + 给 2 个帖子评论，不发帖

这样一来，平台看到的不是一个稳定的发布机器，而是一个有时活跃、有时沉默、偶尔话多、偶尔潜水的账号。

### 4. 内容痕迹控制

发帖本身也需要减少模板化。我们让 LLM 在生成帖子标题和正文时，传入一个随机的“语气指令种子”，比如“今天有点丧，用疲惫工作者的语气”、“今天分享欲爆棚，用激动但克制的语气”。同时让内容引用当前社区的近期热帖（可以用 MCP 工具获取首页帖子列表），让新帖看起来是在回应社区动态，而不是无头无尾的公告。

## 踩坑记录

1. **过度随机仍是规律**

   一开始我们只使用了均匀分布和固定时间窗口，结果 log 画出来后，发现间隔几乎是一个完美的平顶分布。换了 Beta 分布后，风控命中率才明显下降。所以**分布的形态比随机更重要**。

2. **会话粘性与 Cookie/Session 管理**

   如果用无头浏览器模拟，必须保持浏览器 profile 不变，让 cookie、localStorage 持续积累，否则每个帖子都像新注册用户发的一样，极易触发限制。OpenClaw 的 MCP 插件如果基于 Playwright，需要长期保存 `user_data_dir`。

3. **平台主动限制的回退机制**

   无论做得再好，平台偶尔还是会要求验证码或临时限制发帖。必须让 agent 能捕获这些信号并执行退避：比如等待 30 分钟、下次上线减少发帖频率、或者暂时只浏览不发帖。OpenClaw 可以通过工具返回值区分“成功”和“需退避”，并在状态机里加入 `BACKOFF` 状态。

4. **不要在同一台 IP 上跑太多活跃账号**

   如果你同时管理多个社区号，做好 IP 隔离和活动时间错开，否则一个号被标定，会连带到其他号。

## 可复用的工程建议

- **将节奏配置外置**：写一个 YAML 描述会话概率、分布参数、时段权重，Agent 每次启动加载。方便不同站点定制，也便于根据监控数据调整。
- **埋点并回放分析**：记录所有动作的时间戳、类型、间隔，每周回放一次日志，检查间隔分布是否在视觉上像自然行为。可以画一个“间隔的滞后图”，如果出现周期性点阵，就需要调整。
- **灰度测试**：先用一个低风险账号跑一周，只浏览、点赞，不发帖，观察是否被验证码拦截。再逐渐开启发帖。
- **利用 OpenClaw 的任务审计能力**：将每次发帖的 plan 和结果保存下来，如果发现平台惩罚增多，可以回溯是哪个参数变化引起的。

## 总结

自动化社区运营很容易落入“我让它等得够久，就是个好人”的误区。实际上，平台识别机器人的特征早已不是“频率高”，而是**行为模式单一、序列可预测、缺少探索性动作**。用 OpenClaw Agent 结合 MCP 工具，我们可以把一个简单的发帖任务拆解成一个多状态、多概率分支的用户会话模拟，把工程精力花在建立可控的“人类噪音”上。这比任何单一的延迟技巧都更经得起风控模型的检验。
