## 1. 背景：一次意外泄露的真实教训

社区里一位开发者分享了他的 Agent 自动化流水线，看起来只是普通的工作流截图，但截图里的一条日志暴露了内部 PostgreSQL 的连接串：`postgres://admin:xxxx@10.0.1.5:5432/production`。几分钟内，这条信息就被多人转发。

这不是个例。Agent 的输出远比传统脚本啰嗦，它可能把环境变量、内网地址、API 密钥甚至完整的 SQL 查询结果都打印出来。当我们把这种输出复制到社区、Issue 或 PR 里时，就等于把内部信息直接投喂给公开互联网。问题是：**Agent 不会主动替你脱敏，它完全按照你的指令和它“看到”的真实数据来回应。**

在 OpenClaw 社区，我们频繁分享 MCP 插件配置、自动化工作流、Agent 思考链路，稍有不慎，红线就被踩穿了。下面是一套经过实战检验的 Agent 输出安全防线，不追求理论完美，只解决“发帖别泄密”这个刚需。

## 2. 问题拆解：敏感信息从哪里来？

Agent 输出泄露的主要来源有三类：

- **环境变量与凭证**：Agent 进程中加载了 `.env`，如果 prompt 要求“把当前配置打印出来调试”，`OPENAI_API_KEY` 或 `DATABASE_URL` 就可能原样输出。
- **内部系统指纹**：真实的内网域名（`order.internal.example.com`）、IP 段（`10.0.1.x`）、表名（`user_payment`）、文件路径（`/home/deploy/.ssh/id_rsa`）出现在日志或返回结果里。
- **工具执行结果**：通过 MCP server 调用内网 API 返回的 JSON 中包含未脱敏的真实用户数据、甚至是 token。

尤其危险的是，Agent 的“解释性输出”会把上述信息自然语言化，看起来无害，但技术读者一眼就能提取出关键路径。

## 3. 三道防线：从 Agent 输出到社区发布

我们没法完全禁止 Agent 输出真实数据，但可以在“发布到社区”之前加三道闸门。

### 3.1 输出过滤中间件

在 Agent 的最后一个环节（通常是返回给用户前）插入一个**脱敏代理**。最简单的方式是写一个正则过滤函数，对最终输出文本进行扫描和替换。Python 伪代码：

```python
import re
import os

SENSITIVE_PATTERNS = [
    (r'(?:password|token|secret|key)=["\']?[^"\'\s]+["\']?', '[CREDENTIAL REDACTED]'),
    (r'postgres://[^\s]+', 'postgres://[REDACTED]'),
    (r'\b(\d{1,3}\.){3}\d{1,3}\b', '[IP REDACTED]'),  # 可放宽
    (r'eyJ[a-zA-Z0-9\-_]+\.(?:[a-zA-Z0-9\-_]+\.[a-zA-Z0-9\-_]+)', '[JWT REDACTED]'),
    # 根据团队内部域名补充
    (r'(?:[a-z0-9]+\.)*internal\.example\.com', '[INTERNAL_HOST]'),
]

def sanitize_output(text: str) -> str:
    for pattern, repl in SENSITIVE_PATTERNS:
        text = re.sub(pattern, repl, text, flags=re.IGNORECASE)
    return text
```

如果使用的是 MCP 插件，可以在插件的响应处理回调中挂载这个过滤器。注意，脱敏规则要在**本地**执行，不要把原始输出传给第三方“脱敏服务”，否则又多了一条泄露路径。

### 3.2 分享前的审计检查点

规则过滤总有漏网之鱼，尤其是非结构化的大段日志。在最终发布到社区之前，增加一个人工/自动审计步骤：

- **自动化检查脚本**：对剪贴板中的待分享文本，检测是否存在 32 位以上的 hex 字符串、`Bearer` 关键词、@ 符号后跟内部域名等。如果命中，弹窗警告并高亮可疑片段。
- **人工复查清单**：这是最低成本且最有效的方法，下面会单独列一份清单。

### 3.3 环境变量隔离：Agent 只看到替身

永远不要让 Agent 直接使用生产环境变量。给 Agent 一个专用的 `.env.agent` 文件，里面所有凭证都是占位符或临时 token。分享工作流配置时，也只需要贴出这个替身文件的内容。更进一步，可以利用 MCP server 的 `description` 字段或注释明确标出“此值为敏感信息，勿分享”，通过 prompt 提醒 Agent 不要在对用户输出中加入这些值。

## 4. 踩坑记录

- **正则误杀导致输出不可读**：初期把 IP 全部替换后，`0.0.0.0` 和 `127.0.0.1` 也被掩码，社区读者根本无法判断服务绑定地址。后来改为只掩码非私有地址或严格的内部 IP 段，但在分享时仍需上下文判断。
- **MCP 插件自带“宝藏”**：某个社区 MCP plugin 的作者在插件示例配置里硬编码了测试环境的真实密钥，下载者未修改便直接运行，然后贴出运行日志，结果测试环境被攻破。教训：任何下载的插件配置，第一次运行前必须全局搜索 `api_key:` 并替换为假值。
- **多次输出拼接泄漏**：Agent 第一次输出掩码了 IP，第二次在解释时又用自然语言把 IP 说出来：“刚刚查询了 10.0.1.5 的结果...”。所以脱敏必须在**最终输出流**上实现，而不是每次工具调用后局部过滤。
- **结构化输出的隐藏字段**：如果 Agent 输出 JSON，程序员常会复制整个对象，而 JSON 里可能存在 `_internal_notes` 等字段。建议在分享前显式删除所有以 `_` 开头或标记 `sensitive: true` 的字段。

## 5. 可复用的安全分享 Checklist

将以下检查点固化为团队习惯，或者做成 pre-commit hook 用于文档仓库：

- [ ] 所有 IP 地址已替换为 `192.0.2.x`（TEST-NET）或移除
- [ ] 域名中不包含 `internal`、`staging` 等字样，已替换为 `example.com`
- [ ] 无长度超过 20 的 base64 或 hex 字符串残留（高概率是 key）
- [ ] 无 `Bearer`、`Basic ` 等认证头
- [ ] 无真实数据库表名、字段名（至少替换为 `users`, `orders`）
- [ ] 无真实用户数据、PII
- [ ] `.env` 内容仅展示键名，值全部为 `****` 或假值
- [ ] 截图重新审查，避免终端标签页暴露路径或 IP
- [ ] 如果是 MCP plugin 或 workflow 文件，移除所有 `default` 中的真实凭证

可以把这个清单写成一个简单的 shell 脚本，集成到分享前的自检流程里。

## 6. 总结

Agent 安全红线的核心不在工具，而在流程。技术方案上的脱敏代理、审计检查和环境隔离只是手段，真正起作用的是每一次“Ctrl+C / Ctrl+V”之前的审慎。把分享安全检查变成肌肉记忆，比多装一个插件更可靠。工程化的 Agent 输出安全，就从这份 checklist 开始落地。
