## 背景与问题

在一个日常需要同步进度的研发团队里，日报通常要汇总代码提交、CI 构建结果、任务看板变更、生产告警等信息，数据源分散且格式各异。手动从 Git、Jira、Jenkins、Prometheus 等系统提取数据再组织成结构化的报告，不仅耗时，还容易遗漏关键事件。我们希望搭建一条自动化流水线：每天在固定时间自动采集原始日志，经清洗、总结，最终输出一份结构清晰、可复用的日报，直接推送到群聊或文档。

此方案面向使用 OpenClaw 进行 Agent 编排、并以 MCP（Model Context Protocol）连接工具链的实践者。整个流水线无需引入额外重型调度平台，可以通过 Agent 的 task 定义、MCP 工具和 LLM 的总结能力快速落地。

## 方案设计

整体架构可概括为四层：

1. **数据采集层**：通过 MCP Server 封装各类数据源的查询接口，如 GitHub MCP Server、Jira MCP Server、自建的 CI 日志查询 MCP Server。Agent 通过这些工具拉取当日增量数据。
2. **清洗与过滤层**：在 Agent 内部对时间范围、关键字段做过滤，剔除无关信息，将长日志截断至 LLM 上下文的合理长度，并做简单的敏感信息脱敏。
3. **结构化总结层**：使用提示词模板，让 LLM 基于采集到的原始信息生成包含“完成的工作”、“风险项”、“明日计划”等固定段落的结构化草稿。
4. **分发与审核层**：生成 Markdown 格式日报，可选择直接通过 Webhook 发布到 IM，或推送到指定 Git 仓库等待人工确认。

## 实现步骤

### 1. 配置 MCP 数据源

在 OpenClaw 中，通过 `mcp_servers` 配置项声明所需的数据源。例如接入 GitHub 和 Jira：

```yaml
mcp_servers:
  github:
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "${GITHUB_TOKEN}"
  jira:
    command: npx
    args: ["-y", "mcp-server-jira"]
    env:
      JIRA_HOST: "https://your-domain.atlassian.net"
      JIRA_EMAIL: "${JIRA_EMAIL}"
      JIRA_API_TOKEN: "${JIRA_API_TOKEN}"
```

自定义 CI 日志工具可以使用 Python 轻量实现，暴露两个核心函数：`get_builds(since, until)` 和 `get_build_log(build_id)`，并通过 MCP 的 `stdio` 传输集成。

### 2. 定义 Agent 任务

创建一个日报 Agent，配置其触发器、工具白名单与系统提示词：

```yaml
agents:
  daily_report:
    trigger:
      type: cron
      expression: "0 18 * * 1-5"   # 每个工作日下午6点
    tools:
      - mcp:github
      - mcp:jira
      - mcp:custom_ci
    system_prompt: |
      你是一名技术日报生成助手。你可以使用 GitHub、Jira 和 CI 工具获取今日（UTC+8 0:00至当前）的数据。
      请先并行调用查询工具获取提交记录、已关闭的 issue、CI 构建状态和告警信息。
      然后根据以下格式生成日报：
      ## 今日完成
      - <要点1>
      ## 风险与阻塞
      - <如有>
      ## 明日计划
      - <从进行中的任务推断>
      注意：所有结论必须基于获取到的数据，不确定的内容需标注[待确认]。不编造任何事实。
```

### 3. 调整提示词与输出解析

为了稳定输出，可以在系统提示中加入 Few-shot 示例，明确日报应包含的条目数量、禁用 markdown 之外的格式。输出后增加解析步骤：使用正则提取各部分结构，若解析失败则触发重试或降级为原始摘要。解析成功后再添加日期、团队名称等元信息。

### 4. 调度执行与分发

Agent 被 cron 触发后，按流程执行。可以在 Agent 末尾增加一个“通知”动作。若平台支持自定义 function call，直接调用 Webhook；否则在外部编写一个轻量脚本，定期通过 OpenClaw API 获取最后一个任务结果，然后推送到企业微信、飞书或 Notion。

## 踩坑点

- **MCP Server 认证过期**：部分实现使用短时效 token，Agent 在非活跃时段可能因 token 失效而静默失败。解决方法是为 MCP Server 封装自动刷新凭据的逻辑，或使用长期有效的凭据并配合 IP 白名单。
- **时区不一致**：GitHub 提交时间默认 UTC，Jira 可能带时区，Agent 提示中需要明确目标时区（如 `UTC+8`），并用工具参数做显式时间范围过滤，避免漏掉提交或重复算入。
- **日志截断导致上下文丢失**：CI 日志可能非常大，直接截断会遗漏失败根因。可以在 MCP 工具中增加关键词过滤（如仅提取包含 `error`, `fail`, `WARNING` 的行），或使用 LLM 分块总结后再汇总，而不是把原始日志全部塞给主 LLM。
- **LLM 编造事件**：即使给出了数据源，模型仍有“幻觉”倾向，特别是当日志信息不足时会脑补任务内容。需要在提示词中反复强调“基于事实，无数据时写‘无’”，并可对生成结果做关键词回检（报出的 issue ID 必须真实存在于工具返回中）。
- **工具调用失败导致流程中断**：一个数据源不可用不应影响其他。Agent 需对每个工具调用设置 try/catch，失败时记录一条「数据缺失」标记，继续剩余步骤。

## 可复用建议

1. **抽象数据源为可替换模块**：将日报所需的数据采集抽象成一个 `DataSource` 接口（Git commits、issues、builds…），每个 MCP Server 实现该接口，团队更换工具栈时只需替换对应 Server，Agent 定义无需修改。
2. **日报模板外置**：将提示词中的报告格式、段落标题、字数限制等抽离为 YAML 模板文件，支持不同团队定制。Agent 通过读取模板拼接最终提示。
3. **加入人工确认节点**：完全自动推送有时不够谨慎，可在流程末尾先生成草稿发送到指定审阅群，由值班人回复“确认”后再触发正式发布，避免错误信息扩散。
4. **监控与告警**：对流水线本身设置监看，例如超过 5 分钟未生成当天日报则触发告警。同时记录每次工具调用耗时，便于迭代优化。

## 总结

通过 MCP 统一工具协议、OpenClaw 的 Agent 编排能力以及 LLM 的总结能力，我们以较低的工程成本搭建了一条从原始日志到结构化日报的自动化流水线。该方案具备良好的可维护性和扩展性，日报、周报甚至版本发布报告只需调整模板和时间范围即可复用。建议在实践中从小范围验证开始，逐步完善错误处理和输出质量控制，让日报真正成为团队可靠的信息基座。
