## 背景：E2E 测试的生成困境

端到端测试（E2E）是保障核心业务流程的最后一道防线，但编写和持续维护测试脚本的成本极高。每次页面改版、DOM 结构微调，都可能让精心编写的定位器集体失效。近两年，让 AI 根据自然语言描述直接生成测试代码的做法层出不穷，但单次提示往往产生“看起来很对，一跑就挂”的脚本——生成式模型缺乏对运行时页面状态的感知，很难一次性给出稳定可用的选择器与断言。

把工作拆开，交给多个 AI Agent 协作，是更务实的路径。一个 Agent 负责探索页面、提取结构化信息；另一个 Agent 负责根据这些信息编写脚本；第三个 Agent 运行并验证结果，必要时触发修复循环。这正是 OpenClaw 多 Agent 编排 + MCP 工具生态擅长的事。

## 问题拆解：为什么需要 Agent 协作？

单纯的“描述场景 → 输出测试文件”存在几个顽疾：
1. **定位器脆弱**：模型只会根据经验臆测 selector，不接触实际页面，永远分不清 `<div class="card">` 在当前渲染结果中是第几个匹配项。
2. **异步状态察觉缺失**：动态加载内容、骨架屏、延迟渲染使得静态分析无法生成有效的等待逻辑。
3. **断言不切实际**：没有页面数据支撑，断言往往只是检查元素可见，很难验证业务数值。
4. **自愈能力为零**：脚本失败后无反馈闭环，修改全凭人工。

Agent 协作的目标是建立一个“感知—生成—验证—修复”的闭环，让测试脚本能够在不依赖人工预览的情况下迭代到可用状态。

## 做法与步骤：搭建 OpenClaw + MCP 的测试工坊

我们在一个真实的内部后台管理项目中做了尝试，所用技术栈：
- **OpenClaw**：多 Agent 任务编排。
- **Playwright MCP server**：提供浏览器操控、DOM 抓取、截图、脚本运行等工具。
- 三个 Agent 角色：Explorer、Generator、Verifier。

### 1. 环境准备
在 OpenClaw 中安装并启用 Playwright MCP server：
```bash
openclaw mcp add playwright -- npx @anthropic/mcp-server-playwright
```
然后创建 Agent 配置文件，为每个 Agent 绑定需要的 MCP 工具。Explorer 拥有 `browser_navigate`、`browser_click`、`browser_snapshot`、`browser_take_screenshot`；Generator 有文件系统读写和 `browser_evaluate`（用于获取具体元素属性）；Verifier 可使用 `browser_run_code` 或直接调用系统命令执行测试。

### 2. 工作流定义
用 OpenClaw 的任务图定义多步协作：
1. **用户输入**：一句话描述测试场景，如“登录后进入订单列表，点击第一个订单的详情，验证订单号与总价不为空”。
2. **Explorer 执行**：按步骤在无头浏览器中操作，每步抓取可访问性快照（`ariaSnapshot`）和截图。输出一份结构化页面模型 JSON，包含每个步骤交互元素的备选定位器（文本、角色、data-testid、CSS 路径）和当时页面的关键文本内容。
3. **Generator 接收模型和用户描述**，生成 Playwright 测试脚本，强制要求优先使用 `getByText`、`getByRole`，并写入待验证的断言（基于模型中的文本内容）。
4. **Verifier 运行脚本**，收集标准输出与错误截图。如果失败，提取失败步骤的上下文（期望元素不存在、超时等），生成修复提示，并请求 Explorer 回放或细粒度抓取该步骤的备用定位器。
5. **循环**：限制最多 3 次重试，最终输出可通过的测试文件或标注仍需人工介入的部分。

### 3. 关键提示设计
Generator 的系统提示中要硬约束：
- “禁止虚构 CSS class 选择器，必须使用快照中出现的 textual content 或 role”
- “测试运行前添加 `await page.waitForLoadState('networkidle')`”
- “每个操作后断言关键文本存在”

Explorer 的提示强调完整性和结构化输出格式，避免跳过动态面板的内容。

## 踩坑记录

- **动态表格与无限滚动**：Explorer 可能只抓取到首屏 20 行，验证时因数据变化导致文本匹配失败。解决：在模型中标记数据集是否“可能动态”，Generator 相应改用宽松的部分文本匹配或计数断言。
- **MCP 工具超时**：连续截图和快照调用容易累积延迟，尤其在 CI 中。引入重试和步骤间 1 秒的强制等待，并限制 Explorer 单次任务总步数。
- **幻觉产物依旧存在**：Generator 有时会编造 Playwright API（如 `page.clickText`）。通过 Verifier 的运行时错误反馈，并补充纠正示例，可大幅降低。
- **登录态复用**：每个任务都重新登录既慢又不稳定。利用 Playwright MCP 的持久化上下文（`storageState`），在开始前加载已保存的状态文件，但要确保测试间不互相污染。

## 可复用建议

1. **建立元素优先级策略**：`data-testid` > 有唯一文本的角色 > 通用文本内容 > aria-label。在页面模型中明确标出优先级密度，Generator 按此选取。
2. **将页面抽象为页面对象模板**：Generator 生成的脚本不是平铺步骤，而是填充 Page Object 骨架，利于人工复核和复用。例如先定义 `DashboardPage` 的 `goToOrderDetail` 方法，再由 Agent 实现方法体。
3. **跨任务缓存页面快照**：用 Redis 或本地文件缓存大版本页面模型的 SHA，当页面未变更时，可跳过 Explorer 部分，只增量生成测试。
4. **人工审核关口**：生成的脚本必须通过 Git 提交进入 review 流程。建议自动创建 PR，附带 Verifier 通过的截图和页面模型链接，让审核可视化。
5. **CI 中的自愈模式**：仅在非主分支开启 Agent 修复，避免自动覆盖线上测试，且设置修复时间窗口（如凌晨 2-4 点），减少浏览器资源竞争。

## 总结

Agent 协作没有让 E2E 测试编写变成“一键全自动”，但把重复性最高的探索、定位器兜底、初版脚本构筑工作转移给了多个专注的 AI。借助 OpenClaw 的任务编排和 MCP 的浏览器实时交互能力，我们得到了一个能接受不完美输入、逐步收敛的工程体系。当前仍不适合完全无人值守，但作为开发者的扩展手脚，已经能省下大量初版编写和回归维护的时间。下一步我们计划加入视觉对比 MCP 服务，让 Explorer 的截图直接参与断言生成，进一步减少人工指定预期的比重。
