## 背景

当单个 Agent 面对多来源数据检索、多站点抓取、多工具调用时，串行执行会带来明显的延迟堆积与 token 浪费。OpenClaw 生态允许通过插件与 MCP 工具扩展 Agent 能力，但如果把五六个独立步骤全塞给一个 long-context 模型慢慢地“咀嚼”，成本和稳定性都不理想。

更合理的做法是将复杂任务拆成多个可并行执行的单元，交给 subagent 同时处理，最后由主 Agent 汇总。这就引出了 subagent 编排的需求——不是简单的 `asyncio.gather`，而是一整套工程方案。

## 真正的问题

并行编排的难点并不在于“怎么跑起来”，而在于跑起来之后：

- **上下文干扰**：子任务间容易相互污染，影响主 Agent 的决策链。
- **结果格式不一致**：不同 subagent 返回的内容差异大，汇聚时清洗成本高。
- **资源争抢**：例如共享浏览器实例、文件句柄，在并发场景下极容易崩溃。
- **单点失败放大**：一个 subagent 挂掉不应该让整个流程停摆，但多数 demo 没有考虑降级。

## 实践做法（基于 OpenClaw 类架构）

我用的是一个“主 Agent 规划 → Subagent 执行 → Result Collector 汇聚”的模式。具体步骤：

1. **定义 subagent 模板**  
   将每个独立任务封装成 MCP 工具或插件函数，固定输入 Schema（任务描述、数据源、参数），输出结构化 JSON，包含 `status`、`data` 和 `error` 字段。

2. **主 Agent 拆解任务**  
   主 Agent 收到复杂指令后，通过一次工具调用生成 N 个子任务描述，每个描述是一个 dict，带上唯一的 `task_id`。

3. **并行调度**  
   在 tool handler 中，用 `asyncio.create_task` 并发执行所有 subagent。使用 `asyncio.Semaphore` 限制并发度（通常 3～5），避免打爆 API rate limit 或本地资源。

4. **结果收集与校验**  
   等待所有 task 完成，按 `task_id` 收集结果。对每个结果做 JSON Schema 校验，不符合的自动重试一次（带指数退避），仍失败则标记为降级数据。

5. **汇聚输出**  
   将有效结果列表传给汇聚函数，这里再调用一次 LLM（能力更强、context 更长的模型）生成最终回答，同时附上降级标记让用户知晓数据完整性。

整个过程始终保持 subagent 无状态：不允许共享内存变量，所有上下文通过参数显式传入。

## 踩坑实录

- **Token 暴增**  
  每个 subagent 都有独立系统提示和上下文窗口。并发 4 个轻量工具调用，单次总 token 轻松破万。我的解法：子任务统一用 8k 上下文的廉价模型（如 gpt-3.5-turbo），只在汇聚阶段用高能力模型。

- **Playwright 并发冲突**  
  多个 subagent 同时通过 Playwright 插件抓取网页时，共享浏览器上下文直接导致进程崩溃。后来改为每个 subagent 申请独立的浏览器实例，并配合连接池限制最大并发数 2，问题消失。

- **乱序结果与日志地狱**  
  并发下完成顺序不确定，最初用列表索引强匹配，调了三天才发现 `task_id` 才是唯一可信锚点。日志则注入 `trace_id` 和 `span_id`，并用结构化 JSON 输出，才能快速定位哪个 subagent 超时。

- **超时拖垮主流程**  
  某个外部 API 长时间不响应，导致整个 `asyncio.gather` 卡住。必须给每个 subagent 套上 `asyncio.wait_for`，并设置合理的超时（如 30 秒），超时直接按失败处理。

## 可复用建议

1. **抽象 Scheduler 层**  
   封装一个 `SubagentScheduler`，提供 `submit(task)` 和 `collect()` 接口，内部维护协程池和信号量。之后任何需要并行工具调用的地方直接复用。

2. **强制标准化 I/O**  
   所有 subagent 返回结构必须包含 `status` 和 `data`，其余字段只能追加，不能随意改变顶层结构。这是多人协作下唯一能避免“字段地狱”的办法。

3. **模型分级使用**  
   子任务用小模型，汇总用大模型。这个分层不仅省钱，还能让每个环节使用最合适的上下文窗口和推理能力。

4. **可观测性前置**  
   在 scheduler 中直接埋入耗时、成功率、重试次数三块监控。没有这些指标，出问题只能靠猜。

## 总结

subagent 并行编排是 Agent 从“能跑”走向“能生产”的关键一步。别被理想化的 demo 带偏，真实环境中的隔离、错误处理和资源控制才是难点。把工程补丁打齐全，多个 AI 并行做事才不再是一句空谈，而是可控、可观测、可降级的系统能力。
