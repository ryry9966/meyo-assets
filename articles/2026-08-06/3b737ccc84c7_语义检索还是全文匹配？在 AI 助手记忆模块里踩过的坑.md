## 背景：记忆模块为什么绕不开“搜索”

在 OpenClaw、Agent 框架和插件定制中，只要给助手接一段长期记忆，就必然面临一个问题：**如何从上千条历史记录里，找出与当前上下文最相关的那些**。常见的做法是把记忆存成文本块，在需要时由 recall 函数拉取。

这个 recall 的实现方式，几乎直接决定了助手接不接得住长对话、能不能在正确时机调用旧知识。而选择只有两大类：

- **全文搜索**：基于关键词匹配，比如 BM25、甚至简单子串查找
- **语义搜索**：基于文本 embedding，用向量相似度召回

两种方案我都深度用过，也把混合形态部署到了实际 agent 里。下面说的，全是工程上的真实感受，不比较学术指标，只看“怎么让助手好用”。

## 问题：两种方案各自在什么情况下翻车

### 全文搜索的尴尬

最明显的是**同义词和句式改写无感**。你问一句“那个关于模型鉴权的讨论”，之前记录里写的是“讨论 OAuth 令牌刷新机制”，全文匹配直接找不到。这对需要自然对话调取记忆的 agent 是致命的。

另一个坑是**长文本场景**。比如聊天记录积到几百条后，光靠 TF-IDF 提特征，噪声会越来越大，什么“好的”“明白了”这种高频词反而占了权重，真正有价值的段落被淹没。

### 语义搜索的盲区

语义搜索靠 embedding 模型把句子映射到高维空间。好处是能跨表层词匹配，但会引入**精确信息的丢失**。代码片段、错误码、日志摘录这类内容用向量召回，往往反而不如直接 grep。比如：

- 用户问：“上次 k8s 里看到 `ImagePullBackOff` 是怎么解决的？”
- 语义理解可能把“镜像拉取失败”这个意图算得很近，但历史里一堆原因相似的错误，它容易把 BackOff 和 CrashLoopBackOff 混在一起，给了一条不相关的建议。

另一个工程现实是**冷启动和更新成本**。语义搜索依赖持续的 embedding ；记忆增量一多，需要重建索引或维护向量库。对于个人部署在 NAS 或轻量 VPS 上的 agent，这部分开销不是零。

## 做法：在 OpenClaw 里搭建可切换的记忆检索

我的环境是 OpenClaw 的 Python 运行时，记忆层通过 MCP 工具暴露 `memory_search` 和 `memory_store`。核心步骤如下：

1. **存储结构**
   每条记忆存为 JSON 行文件，包含 `id`、`content`、`timestamp`、`meta`（含标签、来源）。为保证全文和语义两种方式都能跑，content 字段保留原始文本，不提前清洗掉标点。

2. **全文检索路径**
   直接用 `quickjs` 实现的轻量 BM25 索引，或者更糙的 `str.find` 先行筛选。给 BM25 索引加一个简单的词干化（Snowball stemmer，英文场景），但不做停用词移除——因为“错误”“配置”这类词在记忆里反而是高频信号。

3. **语义检索路径**
   文本块先过本地 Sentence-Transformers，用 `all-MiniLM-L6-v2` 模型转成 384 维向量，存到 LanceDB。召回时默认 top_k=20，再做一轮重排。

4. **混合模式**
   实际部署的时候，我加的是一层**先粗筛再精排**的逻辑：
   - 使用全文检索快速筛出候选集（比如带精确关键词的、日期范围的）
   - 如果全文检索结果少于 5 条，自动切换成语义搜索补充
   - 如果全文结果已经大于 30 条，就在候选集内做语义重排，保留最相关的前 5 条

这样在精确查询和模糊联想之间折中，而且不引入外部 API。

## 踩坑记录

**坑1：语义相似度容易高估语义无关的“讨论类”文本**
历史里有很多“用户问了一个关于权限的问题”，这种泛泛记录和任何技术问题都有 0.7 以上的相似度，抢占了真正有用的信息。解决办法是给内容加一个结构化的 type 字段（如 `issue`、`solution`、`chitchat`），召回时对 `chitchat` 做降权，或者直接用 type 过滤，只召回 `solution` 与 `issue`。

**坑2：embedding 更新不及时**
当你改了记忆库但忘记重建向量索引，会出现“明明存了但还是搜不到”的诡异现象。我的做法是在 `memory_store` 函数内部自动调用一次索引追加逻辑，并且每 50 条记录全量重建一次索引，避免碎片。

**坑3：混合检索的阈值调参**
全文检索评分和语义相似度评分尺度不一样，没法直接线性相加。我是将全文评分映射到 0-1 区间（除以理论最高分），再和向量相似度做加权平均。权重我最后定在 0.6（语义）和 0.4（全文），偏重语义，因为我的用例以对话总结为主。如果你的助手存大量代码块和日志，这个比例可以反过来。

## 可复用建议

- **先定义记忆数据类型**：纯对话、技术排查、代码片段、账单信息。不同类型用不同检索偏好。
- **别把向量数据库当成银弹**：嵌入式向量库维护有成本，对短文本或精确匹配还是全文更稳。小规模（<5000 条）场景下，甚至用 pickle 存 BM25 索引就够了。
- **测试用例驱动决策**：我的做法是从历史记忆中抽取 50 个典型查询，手工标注正确答案，然后对着跑全文、语义、混合三组的 top-5 命中率。有了这个 baseline，再决定产线用什么方式。
- **接口设计要统一**：`memory_search(query, strategy="auto", limit=5)`，`strategy` 可设为 `fulltext`、`semantic`、`hybrid`、`auto`，在 agent 指令里动态切换。比如涉及到具体报错代码时，优先 fulltext。

## 总结

没有绝对的“哪个更好”，只看你的记忆长什么样、用户怎么问、资源有多少。实际工程里，**一个可切换的混合策略远比追求单一高级方案可靠**。全文负责精确锚定，语义负责模糊联想，两者结合才能让 AI 助手在关键时刻“想起”该想起的东西，而不是丢掉关键词或者被无关记忆带偏。

我在 OpenClaw 环境中最终固化下来的方案，就是 LRU 缓存下的轻量混合检索，不需要外部服务，响应延迟控制在 200ms 以内。如果你也在为了让 agent 记得更准而头疼，不妨先把两种方案拆开测试一轮，大概率会有意外发现。
