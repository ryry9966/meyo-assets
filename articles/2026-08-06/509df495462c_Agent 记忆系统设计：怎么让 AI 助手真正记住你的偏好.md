## 背景：为什么记忆是 Agent 落地的最后一公里

在 OpenClaw 这类 Agent 平台上跑了一段时间自动化和插件之后，一个尴尬的瓶颈会很快浮现：你的助手能够调度任何工具，却总是记不住你昨天说过“我不喜欢英文回复”或者“输出 SQL 时永远带上表别名”。每一次新会话都像认识一个新用户。

状态无关的 LLM 调用已经满足不了高强度自动化用户的诉求。我们要的不是“记住这条消息”，而是让 Agent 拥有分层的、可演进的记忆系统——就像人类不会把所有信息都堆在脑海里，而是分清哪些要刻骨铭心，哪些用后即弃。

这篇文章基于我们在 OpenClaw 插件的实战经验，梳理一套轻量但工程可用的 Agent 记忆设计方案，包含存储划分、召回策略、维护机制，以及最容易翻车的几个坑。

---

## 问题定义：不是“记得多”，而是“记得准”

Agent 记忆系统的核心矛盾不是存储容量，而是**检索噪声**。如果把所有历史交互一股脑塞进上下文，不仅烧 token，还会让它错误地认为半年前的临时指示到现在依然有效。

因此，我们必须先明确记忆的用途，再设计存储模型。典型的记忆需求可以分成三层：

- **短期记忆（Working Memory）**：当前会话上下文，帮助多步推理时不需要反复确认。  
- **长期事实记忆（Semantic / Personal Facts）**：用户偏好、习惯、固定规则，比如“我每周五汇总账单”“所有对外邮件以敬语收尾”。  
- **过程记忆（Procedural Memory）**：之前任务的成功路径、工具调用序列，用于省去重复试错。

在工程实现上，我们需要把这三层分开，并且让 Agent 能够按需从长期记忆中检索必要信息，而不是全量注入。

## 实现步骤：三层记忆 + MCP 连接器

### 1. 短期记忆：直接用 `context.activeMessages`

这层最简单，OpenClaw 原生支持。每个 session 维护最近 N 轮的对话，用 `systemPrompt` 中增加“当前会话要点”的自动摘要指令。推荐的做法是每隔 6-8 轮触发一次轻量摘要，将摘要写入短期记忆，同时也为长期记忆提供素材。

**建议 prompt 片段**：
```markdown
每当你和用户完成一个重要话题，请在内部总结不超过三句话的关键内容，并标记是否包含长期偏好。
```

### 2. 长期记忆：profile + 向量库 + RAG

我们采用“结构化标签 + 向量化”的双通道存储：

- **用户 Profile（结构化）**：固定偏好的键值对，如 `language: zh-CN, sql_style: lowercase, timezone: Asia/Shanghai`。这些直接通过工具函数读取，保证绝对准确。  
- **记忆片段（向量存储）**：不固定的、带时间衰减的事实与偏好，存入向量库（我们用的是本地方案 ChromaDB，通过 MCP 暴露查询接口）。每条记忆需携带元数据：时间戳、重要度评分、来源会话 ID。

Agent 每次生成回答前，执行一个预处理步骤：  
1. 读取结构化 Profile 强制覆盖约束。  
2. 使用当前问题生成检索查询（query embedding），从向量库相似度 top_k=3 且重要度≥0.5 的记忆片段中召回。

**MCP 连接器** 承担了记忆的增删查改接口。示例 MCP 工具定义类似于：
```
tool: memory_search(query: string, top_k: int)
tool: memory_store(content: string, importance: float, tags: string[])
```

这种架构的好处是：结构化信息永不丢失，而自由形式偏好可按需提取，避免上下文膨胀。

### 3. 记忆维护：遗忘与强化

没有遗忘机制的记忆系统就是垃圾场。我们实现了一个简单的后台维护：

- **衰减规则**：每次记忆被检索时，重要度+0.05（不超过 1.0）。每 7 天未被访问的记忆，重要度×0.9。低于阈值（0.3）的进入“休眠库”，默认不参与检索，但用户可手动查询。  
- **冲突检测**：当新记忆与已有 profile 或高重要度记忆冲突时，Agent 不会直接覆盖，而是生成确认问题。例如：“检测到您之前的 SQL 风格是 `lowercase`，现在要求 `uppercase`，是否更新为最新偏好？”

## 踩坑记录

**坑 1：检索噪音淹没了指令**  
初期我们直接把向量检索到的历史记忆全部拼到 `system prompt` 里，导致 agent 混淆。后来改为“分层注入”：profile 在 system prompt 顶部强约束，检索到的记忆放到 `context` 最后并包裹标签 `<past_user_preferences>`，降低权重干扰。

**坑 2：冷启动的沉默**  
新用户没有任何记忆时，RAG 返回空，agent 会变得“健忘”。治愈方式是提供一条默认引导：“我目前还没有关于您的长期偏好记录，如果您愿意，可以告诉我常用设置。” 这比假装记住要好得多。

**坑 3：OpenClaw 插件的持久化陷阱**  
用插件本地存储记忆文件时，要注意多实例 / 容器重启问题。我们的教训是：一定要把向量库和 profile 放在外部持久化卷或云存储上，不建议依赖插件工作目录。

**坑 4：隐私与用户可控性**  
所有记忆必须对用户透明。我们在每个 session 开始提供一个 `/memory` 指令，让用户查看、删除、修改记忆。支持“忘记我”一键清除所有长期记录。没有这层控制，产品就别想上线。

## 可复用建议总结

- **三层模型是最小可行架构**：短期会话、长期 profile、碎片化记忆向量库。别一上来就搞图谱或高阶推理记忆，ROI 极低。  
- **结合 MCP 提供记忆工具**，让 agent 自己能决定什么时候读取、存储或更新记忆，而不是硬编码流程。  
- **增加时间衰减和确认机制**，用户偏好是演化的，不是一成不变的。  
- **永远给用户开关和查看入口**。记忆不是黑盒，是助手价值的一部分。

Agent 记忆不是花活，而是高频自动化场景下用户体验的硬分水岭。做好了，你的助手从“工具人”变成“工作伙伴”；做不好，它永远在问“你想用什么语言输出？”。
