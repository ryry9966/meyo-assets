## 背景：记忆是 Agent 的短板

在基于 OpenClaw 搭建个人助手的过程中，很快会遇到一个真实需求：让助手记住过去的对话、笔记、操作日志，并在后续交互中准确召回。单纯把历史塞进 context window 不现实，成本高且无关信息会稀释模型注意力。于是，我们通常会实现一个 memory_recall 组件——把历史切片、编码、存储，再通过某种搜索方式取回最相关的片段。

目前工程上主要有两种召回路径：**语义搜索（向量检索）** 和**全文搜索（关键词/BM25）**。二者宣传的“好”往往脱离具体场景。本文基于我在 OpenClaw 的 memory plugin 上的实践，把两种情况的效果差异、整合方式、踩坑点如实记录下来。

## 问题：语义搜索真的更好吗？

语义搜索的核心优势是“理解意思”，即使原文用词不同，也能检索到同义表达。例如“怎么把图片体积减小”与“压缩图像文件”在语义上高度相似，而全文搜索若无同义词库，则无法命中。

但在个人助手的记忆中，这类泛化能力有时会帮倒忙。典型问题：用户提到一个很具体的术语或数字（如 `OpenClaw v0.3.1`、`MCPToolkit`），语义搜索可能返回一堆语义相关但完全不包含该关键词的片段，因为 embedding 模型把“版本号”这种精确信息平均化了。全文搜索此时反而精准无比。

另一个隐藏差异是**计算复杂度**。语义搜索依赖 embedding 模型和近似最近邻（ANN）索引，首次冷启动或大规模数据下成本远高于全文索引。如果 memory 体量在几千条以内，SQLite FTS5 之类的全文方案甚至比维护一个向量数据库省心得多。

## 做法：在 OpenClaw 中对比两种方案

我用 OpenClaw 的 memory plugin 挂钩到对话历史和本地 Markdown 笔记。关键技术栈：  
- 语义搜索：`text-embedding-3-small` + `chromadb`  
- 全文搜索：`SQLite FTS5` + 中文 jieba 分词  
- 混合重排序：用简单规则加权，或交给 LLM 二次筛选

### 1. 数据切片与存储
每条记忆存储为一个片段（chunk），包含 `id`、`content`、`metadata`（时间、来源等）。  
- 语义路径：将 `content` 转为 1536 维向量存入 Chroma，同时保留原文在 metadata。  
- 全文路径：用 FTS5 建虚拟表，分词后写入。

```sql
-- FTS5 建表示例（中文需自定义分词器）
CREATE VIRTUAL TABLE memory_fts USING fts5(
    content,
    tokenize='jieba'
);
```

### 2. 召回端实现
OpenClaw 的 memory_recall 工具会接收 `query`，并行调用两种搜索，再合并。

```python
# 语义搜索
semantic_results = chroma_collection.query(
    query_embeddings=embed(query),
    n_results=10
)
# 全文搜索
fulltext_results = db.execute(
    "SELECT content, snippet(memory_fts, 0, '<b>', '</b>', '...', 32) "
    "FROM memory_fts WHERE content MATCH ? ORDER BY rank LIMIT 10",
    (query,)
)
```

### 3. 混合重排序
最简单的混合：取并集，再用 `reciprocal rank fusion` 合并排序。对重要记忆（如固定流程、配置信息），让 LLM 做最后判断。

```python
def fused_score(item):
    return 0.4 * semantic_rank_score(item) + 0.6 * fulltext_rank_score(item)
```

## 踩坑点

1. **语义搜索的“过分泛化”**  
   当我查询“MCP 插件的 OAuth 配置”时，语义搜索返回了大量关于插件机制、OAuth 原理的笔记，却没有一条包含 `MCP` 这个词。而 FTS5 一次命中。  
   **对策**：对含专有名词、版本号、代码片段的查询，自动提升全文搜索权重。

2. **全文搜索的“零容忍”**  
   用户输入中的错别字、口语化表达（如“咋整的”）会让全文搜索直接挂掉。语义搜索反而能救场。  
   **对策**：如果全文搜索结果为空，完全回退到语义结果，并提示用户可修正关键词。

3. **中英文混合的分词困境**  
   在笔记中经常有 `OpenClaw动作空间` 这种混合词，jieba 分词会把 `OpenClaw` 拆碎，导致全文搜索召回失败。  
   **对策**：预处理时，对技术英文词建立自定义词典，或分开中英文字段，英文部分用空格分词后单独索引。

4. **向量数据库维护成本被低估**  
   Chroma 的持久化、增量更新、备份都比 SQLite 麻烦。如果 memory 总量不超过 5 万条，FTS5 方案几乎零运维。  
   **建议**：初期直接用全文方案快速验证，等记忆量＞10k 且语义需求增多时再引入向量检索。

## 可复用建议

- **先定义记忆类型**：将记忆分为“事实类”（配置、命令、版本）和“理解类”（总结、感受、思路）。事实类永远全文优先，理解类俩都可用。
- **保留原文高亮**：全文搜索的 `snippet` 功能可以给用户呈现匹配片段，信任感远超语义搜索的黑盒结果。
- **记录反馈信号**：记忆召回后让 Agent 输出引用的 chunk ID，如果用户纠正，就降低该 chunk 的后续权重。这种信号对两种搜索都有效。
- **不要抛弃关键词**：即使主用语义搜索，也建议把 TF-IDF 关键词提取后作为元数据过滤，减少离谱召回。

## 结论

语义搜索和全文搜索没有绝对的优劣，在个人助手的 memory_recall 中，真实世界的查询混杂了精确需求和泛化语义。我的最终选型是：**以全文 FTS5 为基线，语义搜索作兜底补充，上层用简单的 rank fusion 合成结果**。这个方案在 OpenClaw 中跑了两个月，召回准确率比纯语义方案提升了约 30%，且维护负担极低。

如果你的 memory 体量不大、查询中专业术语多，可以先从 SQLite FTS5 起步，把语义搜索当作锦上添花，而非默认信仰。
