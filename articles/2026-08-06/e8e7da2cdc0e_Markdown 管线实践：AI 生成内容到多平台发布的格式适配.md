在 OpenClaw 的自动化内容工作流里，一个常见场景是：用 AI Agent 生成一篇技术文章、周报或社交媒体帖子，输出为 Markdown，然后需要同时发布到微信公众号、知乎、Notion、小红书等不同渠道。每个平台对 Markdown 的解析能力差异巨大——有的只支持最小子集，有的完全不吃这套。不做格式适配，结果往往是标题消失、列表缩进全乱、代码块无法高亮、图片链接被吞。这篇文章记录我在搭建 Markdown 管线过程中的选择、步骤和踩过的坑，供同样在折腾多平台自动发布的同学参考。

## 问题：AI 产出 + 平台差异 = 格式灾难

让大模型输出 Markdown 很容易，但模型产出的 Markdown 往往不够“干净”：可能混用一级标题和二级标题，列表缩进用空格和 tab 混合，引用块里嵌套代码块，偶尔还有反斜杠转义字符残留。再加上不同平台解析器的实现不完全遵循 CommonMark，微信的富文本编辑器连 Markdown 都不认识，小红书的“笔记”本质上是一张图+文字，这些差异让简单的“生成-发布”变成格式层面的连连看。

## 管线设计：四步把 Markdown 喂给不同平台

我先后尝试过多个方案，最终稳定下来的结构分四步：**定义源规范 → 标准化清洗 → 目标格式转换 → 发布**。

### 1. 统一源规范
为所有内容定义一套强制性的 Markdown 写作约定，比如：
- 标题统一用 ATX 风格（`##`），且层级不超过 3 级；
- 列表严格用 `-` 加空格；
- 代码块带上语言标识，避免自动识别偏差；
- 图片使用绝对 URL，并给备选文本；
- Front matter 里标出目标渠道和摘要。

这套规范会在 Agent 生成内容的提示词中直接注入，也会在人工撰写时用 `.markdownlint.json` 来检查。

### 2. 标准化清洗
接到 AI 生成的原始 Markdown 后，用脚本做清洗：
- 去除多余空行，但保留标题前的换行；
- 统一 Emoji 为短代码，避免 Unicode 变体问题；
- 转义多余的 HTML 实体；
- 校验链接是否可达（防止模型编造的 URL 进入发布流）。

这里用一个 Node.js 的 `unified` + `remark-parse` + 自定义插件来处理，也方便直接运行在 OpenClaw 的 MCP 工具里。

### 3. 目标格式转换
这一步最花功夫。我的做法是 **多渲染器 + 平台特殊模板**：

- **微信公众号**：不支持原生 Markdown，需要生成内联样式的 HTML。用 `markdown-it` 加自定义渲染规则，为 `code` 块、表格、图片注入微信兼容的 CSS，并把图片宽度设为 `100%`。特别注意标题前必须有一个空行，否则编辑器会吞掉标题样式。
- **知乎**：走 API 创建文章，支持 Markdown 但表格和数学公式容易翻车。复杂表格转成 HTML 片段嵌入，LaTeX 块保证前后有独立空行。插入 `<!--more-->` 控制折叠位置。
- **Notion**：使用 `@notionhq/client` 将清洗后的 Markdown 结构拆成块（block）逐个创建，保留层级嵌套关系。代码块会转成 Notion 的 `code` 块，并指定语言。
- **小红书**：完全不支持 Markdown，最终的形态是一组可发布的图片。用 Puppeteer 将 Markdown 渲染成卡片，每张 1080×1440 像素，文字区留够安全边距，再生成文案简版附加在图片描述里。

这些转换器各自封装成 MCP 工具，Agent 可以根据 Front matter 的平台列表按需调用。这样整个流程可以被 OpenClaw 的编排能力串起来。

### 4. 发布与回写
发布结果（链接、报错）会回写到内容库，出错的帖子自动标记为“待人工复审”，并附带渲染前的 Markdown 片段和平台错误信息，方便快速定位。

## 真实踩坑，每一个都能让你浪费一个下午

- **微信代码块无高亮**：微信内置样式不给 `code` 块任何颜色，需要在转换时手动加上背景色和字体颜色，或者改用公众号第三方编辑器 API 辅助，但会多一次网络依赖。
- **列表缩进丢失**：微信的 HTML 渲染对嵌套列表的 `padding-left` 支持不一致，我会在 `<li>` 上加硬编码的 `text-indent` 来控制层级。
- **知乎表格列宽失控**：知乎 Markdown 解析器在处理宽表时会强制拉伸，移动端体验极差。要求每列设定固定宽度并移到 HTML 表格，同时用 `text-overflow: ellipsis` 兜底。
- **图片缓存与防盗链**：公众号会自动将图片上传到自己的 CDN，但地址会被替换；Notion 若直接用外部链接，可能因防盗链不显示。所以管线里先把所有本地/外部图片上传到自建的图床，生成统一域名的链接，再由平台自行抓取。
- **Emoji 显示异常**：Windows 和 macOS 的 emoji 字体差异会导致小红书图片生成效果不一致，渲染时换成矢量图标字体（如 FontAwesome）可以稳定呈现。

## 可复用的建议

1. **不要迷信“全功能 Markdown 发布器”**：平台规则总在变，维护一套独立的渲染规则比依靠第三方库更可控。
2. **前端渲染测试很必要**：每个转换器最好配套一个本地预览页，可以直接粘贴 Markdown 实时查看各平台渲染效果。我用 `vite` 搭了简单的测试面板。
3. **把规则写成 MCP 工具**：让 Agent 在生成后自检格式风险，而不是等到发布失败再去修。
4. **版本控制内容原文与转换后内容**：Git 里同时保留原始 Markdown 和主要平台的输出（如 HTML），方便 diff 和回退。

## 总结

从 AI 生成 Markdown 到多平台发布，中间差着一个工程化管线的距离。规范清洗 + 平台特定转换 + 失败回写，这套组合能让你的自动化内容流不再频繁触发“人工抢救”。在 OpenClaw 生态里，这些转换逻辑完全可以作为被 Agent 调用的工具链而存在，做到生成即发布、适配在幕后发生。
