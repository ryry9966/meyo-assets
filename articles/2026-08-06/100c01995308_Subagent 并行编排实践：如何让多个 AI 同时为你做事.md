## 背景：为什么需要 subagent 并行

单 Agent 串行执行任务时，一次对话通常会顺序处理多个子任务：查数据库 → 调用外部 API → 生成报告 → 做内容审查……每一步都是阻塞的，总耗时会线性叠加。当任务涉及十几个独立子查询时，用户等待时间可能超过 1 分钟，这在自动化流水线中是不可接受的。

在 OpenClaw 这类支持插件注册与子 Agent 调度的框架里，我们可以把不同能力拆分成若干独立的 subagent（每一个都有特定的工具和系统指令），然后由主控 Agent 同时调用它们。这样多个“微型 AI”可以并行工作，最后汇总结输出，把整体耗时压缩到最慢的那个子任务附近。

本文分享一套在工程环境中经过验证的并行编排模式，涵盖拆分策略、异步调度、错误处理与可复用的落地建议。

## 核心问题

要让多个 subagent 并行做事，需要解决三个工程问题：

1. **动态拆分**：如何让主 Agent 把用户指令自动转化为一组可并行的子任务？
2. **健壮调用**：如何安全地并发执行这些 subagent，在 API 限流、超时、参数错误时不会整体崩溃？
3. **结果聚合**：如何把格式各异的子结果重组为连贯的最终答案？

如果只是简单地把所有东西丢进一个 prompt 让 LLM 一次性输出，会遇到上下文长度爆炸、顺序混乱和生成幻觉。更合理的方式是：定义 subagent 的能力边界，通过结构化编排来保证可控性。

## 做法与步骤

下面以 OpenClaw + Python 为例，但思路对任何支持异步调用的 Agent 框架都适用。

### 1. 注册可并行的 subagent

为每个 subagent 定义清晰的输入输出 schema，注册为 OpenClaw 的插件。例如：

- `SearchAgent`：输入 `{query: string, max_results: int}`，输出搜索结果列表。
- `AnalyzeAgent`：输入 `{text: string, aspect: string}`，输出分析摘要。
- `ReportAgent`：输入 `{sections: list}`，输出格式化报告。

每个 subagent 内部封装了自己的工具权限和系统提示，保证无共享临时状态，因此天然可以并行执行。

### 2. 主 Agent 生成并行子任务计划

主 Agent 收到用户请求后，不会直接执行，而是先调用一次轻量规划 prompt：

```
你是一个任务拆分器。请把以下需求拆成可以**同时进行**的子任务，每个子任务指定 agent 名称和参数 JSON。

需求：{user_query}
可用 agent 列表：SearchAgent, AnalyzeAgent, ReportAgent
返回 JSON 数组：[{"agent": "SearchAgent", "params": {...}}, ...]
```

这样得到一个依存关系为零的子任务列表。如果某些子任务存在先后依赖，可以在主控逻辑里分批执行，但优先挖掘可并行的部分。

### 3. 并发执行与流水线控制

使用 `asyncio.gather` 或线程池并发调用 subagent，同时加入三个保护机制：

- **并发上限**：用 `asyncio.Semaphore` 限制同时执行的子任务数（通常 5~8 个），避免瞬间爆掉 API rate limit。
- **超时兜底**：为每个子任务设置 `asyncio.wait_for` 超时（例如 30 秒），超时后返回 Fallback 结果，而不是让整个编排卡死。
- **异常隔离**：单个 subagent 出错不影响其他子任务，错误信息会被记录到结果元数据中，供聚合阶段判读。

伪代码示意：

```python
sem = asyncio.Semaphore(5)

async def run_one(task):
    async with sem:
        try:
            return await asyncio.wait_for(
                call_subagent(task["agent"], task["params"]),
                timeout=30
            )
        except Exception as e:
            return {"error": str(e), "agent": task["agent"]}

results = await asyncio.gather(*(run_one(t) for t in plan))
```

### 4. 结果合并

拿到并行输出的结果列表后，再调用一次主 Agent 进行汇总。此时需要注意：结果之间的关联可能丢失。我们通常要求每个 subagent 输出时附带来源标记，合并 prompt 会按原始的子任务编号引用它们，必要时还会让主 Agent 自己调整顺序或补充缺失信息。

## 踩坑记录

在实践中反复碰壁的地方主要集中在三点：

- **规划阶段幻觉**：主 Agent 生成的子任务参数偶尔不符合 subagent 的 schema 要求，比如字段名写错或类型不对。解决办法是在 `call_subagent` 函数入口处做严格的 Pydantic 校验，校验失败立刻返回可读错误，并触发主 Agent 重新规划。
- **API 限流抖动**：高速并发时，即便有 Semaphore，下游 LLM API 仍可能出现 429。我们引入了指数退避重试（最多 3 次），并在重试失败后降级为缓存结果或空占位，避免整次请求失败。
- **结果顺序混乱**：因为各子任务完成时间不一致，直接按 `asyncio.gather` 返回的顺序合并会让最终答案不稳定。必须让子结果携带 task_id，在聚合时显式排序。
- **上下文污染**：切忌让多个 subagent 共享可变会话上下文，否则并行下的写冲突会导致不可预期的行为。每个 subagent 应接收不可变输入并产出独立输出。

## 可复用建议

1. **为每种能力定义最小输入输出合约**：用 JSON Schema 或 Pydantic 严格约束，可自动校验、容易 debug。
2. **将并行编排抽象成可复用模板**：针对常见任务（如竞品分析、多文档摘要），固化拆分逻辑，未来只需传入具体参数即可。
3. **渐进式聚合**：对于子任务很多（>20）的场景，先在并发结束后做一次“分组聚合”，再交由主 Agent 做最终汇总，减少一次 prompt 处理的信息量。
4. **可观测性优先**：记录每个 subagent 的调用耗时、成功/失败状态，便于后续优化拆分策略和并发数。

## 总结

多个 AI 并行做事不再是“花活”，而是提升 Agent 系统吞吐量的刚需。通过注册隔离良好的 subagent、结构化拆分规划、异步并发调度和健壮的错误兜底，我们可以在不增加模型幻觉风险的前提下，大幅缩短多步骤任务的端到端耗时。

工程上，这套模式已经帮我们把一批原本需要 70 秒的复杂分析缩短到 18 秒以内。对 OpenClaw 社区的同学来说，可以立刻基于插件体系搭建自己的并行 subagent 流水线，先从小规模并发开始逐步调整，把稳定性和速度一起拿住。
