## 背景：工具越多，失控风险越高

给 Agent 接入 MCP 或原生插件后，它的能力边界被迅速拓宽：读写文件、查询数据库、操作云资源、发送企微/钉钉消息，甚至直接执行 Shell。与此同时，误操作的代价也在同步放大。半夜一条错误的 `kubectl delete`，或一封发给全员的测试邮件，就足以让团队对 Agent 丧失信任。

工程上，我们需要明确回答两个问题：

- 什么时候 Agent 可以自己干？
- 什么时候必须停下来等人类点头？

这不仅是“安全原则”问题，更是一个可落地的交互设计与架构选择。

## 问题：确认太少危险，确认太多疲劳

一个自然的想法是“所有写操作都确认”，但很快就会陷入确认疲劳。当 Agent 每打开一个文件都弹窗问一次时，用户会条件反射式点“同意”，确认机制形同虚设。

反过来，完全放开又不敢。我们在内部测试时遇到过：Agent 误将“清理临时文件”理解成“清理整个工作目录”，幸亏当时限制了它只能操作沙箱路径。

因此，需要一套分级、可配置、不依赖用户注意力的权限边界模型。

## 做法：风险分级 + 决策拦截 + 可撤销机制

### 1. 给每个工具操作打上风险标签

在工具/插件定义中增加一个 `risk` 字段，例如在 OpenClaw 的插件 manifest 里扩展：

- `low`：只读、无副作用的查询类操作（读取文件元数据、查询日志、查询 API）
- `medium`：有副作用但可回滚/影响范围可控（写入临时文件、发送内部通知、修改非关键配置）
- `high`：不可逆、影响生产环境或资源的操作（删除文件、重启服务、操作生产库、外发邮件、执行任意 Shell）

这种划分可以写在工具的 description 里，也可以由统一策略引擎读取。

### 2. 构建工具调用的拦截中间件

在 Agent 调用工具前，加一层决策中间件（类似 MCP 的 intercept pattern 或自定义 wrapper）：

```
if risk == 'low':
    execute()
elif risk == 'medium':
    execute_with_notification()
    record_for_possible_rollback()
else:  # high
    request_human_confirmation()
    if timeout: reject or fallback
```

关键细节：

- **确认通道**：不是终端弹窗，而是持久化、可异步回复的消息（如 Slack 卡片、钉钉交互消息、或专用审批接口）。保证用户不在线时不会被阻塞，Agent 可以挂起等待，或超时后执行预定义降级（拒绝、暂存为任务、通知值班人员）。
- **确认窗口**：包含足够上下文——Agent 意图简述、将要执行的具体命令/参数、影响范围、风险等级。给用户“同意”“拒绝”“查看详情”三个选项。
- **超时策略**：合理超时（如 5 分钟），默认拒绝并记录，避免 Agent 无限等待。

### 3. 对中风险操作使用“软确认 + 可撤销”

如果每次都打断用户，中风险操作依然会造成打扰。可以采用延迟确认：Agent 先执行，但包含回退手段，并发送通知告知“已执行，点击可撤销”。例如：

- 文件写入：先写入目标文件，同时保存 `.bak`，在通知中带上 undo 链接。
- 发送消息：把消息放入“待发送”队列，设定 30 秒延迟，期间可撤回。

这样在不打断流程的前提下，为人类保留了最后一道防线。

### 4. 根据上下文动态调整风险等级

同一个操作在不同环境下风险完全不同。我们的策略引擎支持动态判定：

- 路径特征：沙箱目录 `/tmp/sandbox/` 内的写操作降为 low；生产配置目录升为 high。
- 时间窗口：工作时间可放宽中风险操作为 low；非工作时间所有写入默认 medium。
- 用户身份与频道：通过管理员触发的高风险操作可执行；普通成员触发的高风险操作必须额外审批。

这可以通过简单的规则表实现，不推荐直接在 prompt 里写一堆 if-else，而是用独立的策略文件或 OPA 进行结构化维护。

## 踩坑点

1. **异步确认的恢复**：Agent 挂起等待人类回复时，需要把当前上下文序列化存储（如存到 KV 存储或数据库）。如果确认回复到达时 Agent 已经重启，要能从上次挂起点继续，而不是重新生成整个行动链。

2. **确认消息的信息安全**：确认卡片里可能包含命令参数、文件路径，注意不要在公开频道泄露敏感信息。我们在卡片中只展示摘要和 hash，详情需在受控环境下查看。

3. **中风险操作的“可撤销”其实不总是可行**：例如 API 调用已经对下游产生副作用，光靠本地的 undo 不顶用。这时要么把该操作升级为 high，要求确认；要么通过幂等设计降低影响。需要在工具设计阶段就评估可逆性。

4. **用户习惯性盲点**：即使只有少数高风险操作才确认，也要定期轮换确认文案和按钮布局，防止用户肌肉记忆直接点“同意”。更进一步的，可以要求输入简短理由（如 “yes-ok” 二次确认），但这也会增加摩擦，只适合极高风险操作。

## 可复用建议

- 在团队内沉淀一份《Agent 操作权限分级表》，明确哪些操作属于 low/medium/high，并随工具集更新迭代。
- 利用 MCP server 的 capabilities 限制 Agent 可调用的接口，从源头缩小暴露面。例如不为 Agent 开启能修改 IAM 权限的接口。
- 实现一个可复用的 `RiskAwareToolWrapper`，在项目中统一拦截，而不是在每个插件里反复写确认逻辑。可配置策略文件，并支持热更新。
- 所有操作和确认决策写入审计日志，格式统一：时间、Agent 标识、操作、风险等级、决策（auto/confirmed/denied/reverted）、结果。出了问题能快速回溯。
- 为每个高风险操作设计“模拟运行模式”（dry-run），在确认前先输出预执行结果，降低用户决策成本。

## 总结

AI Agent 的权限边界不是简单的“开”或“关”，而是一套风险分级、决策拦截、兜底回退的工程体系。合理的边界设计，能让 Agent 在该快的时候全自动运行，在该慢的时候准确等人类决策，而不是让用户在一堆弹窗中逐渐麻木。最终目标很清楚：让自主执行可靠，让人类审批精准。
