# 背景：为什么需要 Subagent 并行

单 Agent 处理复杂任务时，常常陷入“串行诅咒”：先搜索、再阅读、再分析、最后写作，每一步都在阻塞下一步，总耗时是所有步骤之和。如果任务涉及多个独立信息源（如对比三家云厂商的 GPU 实例价格），串行执行会浪费大量时间在 I/O 等待上，同时长链条更容易因上下文膨胀或 API 异常中断。

更理想的方式是**将一个大任务拆成若干可并行的子任务，分派给多个 subagent 独立完成，最后汇总结果**。这不仅能大幅缩短端到端延迟，还能通过不同 subagent 的角色/工具分工，降低单 Agent 的认知负荷。在 OpenClaw 这类支持自定义 Agent 的工具中，实现这种并行编排已经成为可能。

# 问题：单 Agent 长链路的三个痛点

1. **耗时不可控**  
   哪怕是简单的对比类问题，单 Agent 也容易“搜索→读链接→搜索→读链接→整理”，用户看到的是一段漫长的生成过程，TTFB（首字时延）往往超过 20 秒。

2. **上下文掺杂**  
   多个信息源的内容在同一个对话上下文中混合，Agent 很容易张冠李戴，或者在摘要时遗漏关键差异。

3. **失败成本高**  
   如果串行步骤中的某一步工具调用出错或陷入重试循环，整个任务都会失败，前面花费的时间全部作废。

# 方案：在 OpenClaw 中构建主-子 Agent 并行模式

我们基于 OpenClaw 的自定义 Agent 和插件能力，落地的方案是：一个主调度 Agent（Orchestrator）+ 多个只能做一类事情的子 Agent（Subagent）。主 Agent 不直接处理业务数据，只负责“拆任务 → 分发 → 等待结果 → 合并”。

**关键实现步骤：**

## 1. 定义子 Agent 角色与工具边界
为每类子任务创建专门的 Agent，并通过 OpenClaw 的 Agent 模板限制其工具集。例如：
- `SearchAgent`：只能调用 Tavily 搜索，返回结构化搜索结果。
- `PriceExtractAgent`：接收搜索结果的 URL 列表，逐个抓取并提取价格字段，输出 JSON。
- `CompareAgent`：接收多份价格数据，生成对比表格和一句话结论。

每个子 Agent 都要求输出严格符合预设的 JSON Schema，方便主 Agent 解析。

## 2. 设计分解逻辑
主 Agent 收到用户请求（如“比较 AWS、Azure、GCP 的 A100 GPU 每小时价格”）后，利用 LLM 生成一个**无相互依赖的子任务列表**。这一步需要明确的 prompt 约束，例如：

```
你只负责分解任务，不要尝试回答用户问题。
将用户请求拆分为可以完全并行执行的子任务，每个子任务需独立、清晰。
输出格式：
[{"id":"1","type":"search","prompt":"...","engine":"tavily"}, ...]
```

分解的结果会包含多个搜索子任务（每个云厂商一个），且不要求它们先后执行。

## 3. 并发调度与结果收集
主 Agent 使用异步机制同时调用多个子 Agent。在 OpenClaw 中，我们可以通过其内部调度器或直接使用 asyncio + Agent API 实现并发。核心流程伪代码：

```
subtasks = decompose(user_request)   # 得到 3 个搜索任务
results = await asyncio.gather(*[run_subagent(t) for t in subtasks])
final = merge_results(results)
```

通过 `asyncio.gather` 并行等待，整个搜索+提取阶段的耗时由最慢的那个子 Agent 决定，而不是三个任务时间之和。

## 4. 结果合并
所有子 Agent 返回结构化数据后，主 Agent 将原始结果拼接，再交给一个汇总用的 LLM 调用（可以直接用主 Agent 本身）生成最终回复。合并时重点做去重、补全和冲突消解。

# 踩坑记录

**坑1：子任务并非真正独立**  
分解后，某个子 Agent 的 prompt 里隐含了“请参考另一厂商的价格”，导致它期待另一个子 Agent 的产出，直接阻塞。  
**解决办法**：强制每个子任务描述以“你只需要做…”开头，明确禁止引用他人结果；在分解 prompt 中显式要求检查依赖性。

**坑2：并发把 API 配额打满**  
3 个 SearchAgent 同时发起 3 次搜索，再各自抓取网页，瞬间触发工具 API 的频率限制，导致部分任务 429。  
**解决办法**：在最外层增加信号量限制最大并发数（通常设为 3~5），并实现指数退避重试。给子 Agent 设置 `max_steps`，防止回圈。

**坑3：子 Agent 返回格式随意**  
即使要求 JSON，子 Agent 偶发输出“这是结果：{...}”，或字段名不统一，导致解析崩溃。  
**解决办法**：不信任 LLM 的自觉性，用 `response_format` + 强校验。解析失败时，重试该子任务，并附上上一次的错误信息作为 correction prompt。

**坑4：部分成功，整体失败**  
一个子 Agent 超时，主 Agent 直接抛异常，用户什么也看不到。  
**解决办法**：将 `asyncio.gather` 改为 `return_exceptions=True`，收集成功结果，缺省部分用“未获取到数据”占位，保证整体可用。

# 可复用的工程建议

1. **定义清晰的子 Agent 接口**：每个子 Agent 的输入/输出 schema 是唯一契约，变更需要同步更新主 Agent 的合并逻辑。
2. **并发数不要贪多**：初期设置并发上限为 2~3，稳定后根据 API 配额和单 Agent 耗时调整，盲目加大并发只会触发限流且成本陡增。
3. **全链路可观测**：为每个子 Agent 记录启动时间、返回时间、状态码、重试次数，便于后续优化耗时最长的子任务。
4. **降级优先**：任何子任务失败都不应导致“什么也没回”，至少要返回部分结果并注明缺失项。
5. **提前预热**：如果子 Agent 使用了需要初始化的插件或模型，尽量在主流程外部预先加载，避免冷启动拖慢并发。

# 总结

Subagent 并行编排将 Agent 的任务处理模式从“单兵长跑”转变为“小队分工协作”，在我们实际处理的对比、多源检索、批量数据清洗等场景中，端到端耗时普遍压缩了 50%-70%。但它的工程复杂度确实更高：需要良好的任务拆分逻辑、并发控制、结构化输出约束和降级策略。如果你正在用 OpenClaw 构建复杂 Agent 应用，不妨先将一个长链路任务改造成并行子 Agent 实验——你会很快感受到“团队作战”的价值。
