## 背景：为什么 AI 助手需要心跳检测

在 OpenClaw 的实际场景里，我们经常会遇到需要长时间运行的 Agent —— 比如一个负责监听消息流、调用 MCP 工具链的自动化插件，或者一个 7×24 小时待命的审核 Agent。一旦这些进程“假死”、网络抖动或所在宿主环境异常，上层调度器必须尽早感知，否则就会产生静默故障：任务卡住、会话挂起、下游插件无限等待。

于是“heartbeat”就成了标配：让远程组件定期证明自己还活着。但怎么做？最常见的两条路是 **轮询（polling）** 和 **推送（push-based，例如 WebSocket/SSE）**。它们的取舍绝不是“哪个更时髦”，而是受限于你的部署拓扑、资源预算和容忍延迟。

这篇文章会聚焦在 OpenClaw 的 Agent/插件系统里落地 heartbeat 的实践，不卖关子，只讲真实踩过的坑和能带走的方案。

## 问题定义：轮询 vs 推送的核心矛盾

**轮询模式**：控制器定时向 Agent 发 HTTP 请求（或调用 MCP 某个轻量端点），Agent 回应后重置超时计时器。  
优点：实现简单、对中间网络设备友好、能被标准负载均衡器支持、无长连接维护成本。  
缺点：无效请求多 → 浪费 CPU 和带宽，而且延迟受制于轮询间隔。把间隔调到 3 秒，最坏情况下要 3 秒才能发现 Agent 已死，且每多一个 Agent 都会放大请求数。

**推送模式**：Agent 通过 WebSocket 或 SSE 保持与控制器的一条长连接，定时发送 `ping` 帧或业务心跳包；控制器若长时间没收到，判定离线。  
优点：实时性高、服务端压力小（只需管理连接数而无需频繁解析请求）。  
缺点：长连接对代理、网关、防火墙很不友好；断线重连逻辑复杂；在集群扩缩容时需要额外处理会话亲和性；前端（例如浏览器内的插件）还可能受制于页面休眠策略。

在一个多种 Agent（Python 宿主机守护、浏览器侧边栏插件、甚至跑在边缘设备的 Node 进程）共存的 OpenClaw 环境中，单一方案很难全覆盖。

## 做法/步骤：构建一个自适应 HeartbeatManager

我们不依赖任何外部框架，用一段极简的设计来表达思路。目标：**默认尝试 WebSocket 心跳，失败时自动降级到带退避的轮询，并且保持两者间的平滑切换。**

### 1. 抽象 Heartbeat 接口
```typescript
interface HeartbeatChannel {
  start(onAlive: () => void, onDead: (reason: string) => void): void;
  stop(): void;
}
```
两个实现：`WsHeartbeat` 和 `PollingHeartbeat`。

### 2. WebSocket 心跳（WsHeartbeat）
- 连接成功后开启 `setInterval`，每 10 秒发送 JSON：`{type:"PING", seq: counter}`。
- 服务端收到必须立即回 `{type:"PONG", seq: same}`。
- 客户端维护 `lastPong` 时间戳和一个连续丢失计数；如果 3 次 PING 无回应（约 30 秒），触发 `onDead`，并主动关闭连接，把状态汇报给上层管理器，由上层启动降级轮询。

**服务端实现要点**：收到 PING 时更新会话的最后活跃时间，并且每分钟扫描一次所有连接，清理掉超过 40 秒无 PING 的僵尸连接，以避免云负载均衡器超时后端口残留。

### 3. HTTP 轮询（PollingHeartbeat）
- 使用可调节间隔，起始 10 秒，每次收到健康应答时重置为 10 秒；如果连续两次超时或返回非 200，间隔翻倍（最多 60 秒），同时上报降级事件。
- `GET /api/agent/heartbeat?agentId=xxx`，返回 JSON：`{status:"ok", timestamp:...}`。
- 此时必须注意：轮询请求要增加随机抖动（±20%），防止惊群效应——当多个 Agent 同时重启后可能同步发起请求，把控制器打爆。

### 4. 恢复与状态机
定义一个 `HeartbeatManager`，内部状态：`initial -> ws -> polling -> ws`。  
- 启动时先尝试 WebSocket，如果 5 秒内连不上或握手失败，立刻切入 polling。  
- polling 运行期间，后台持续尝试用指数退避重连 WebSocket；一旦重连成功并完成首轮 PONG 验证，切回 `ws` 状态，并清除 polling 定时器。

### 5. 与 OpenClaw 插件系统集成
把 `HeartbeatManager` 挂到插件的生命周期钩子里：`onInit` 时启动心跳，`onDestroy` 时发送一个优雅退出的 `BYE` 消息并关闭连接。如果插件运行在受限环境（如浏览器），强制降级到 polling，因为浏览器后台选项卡会被严重限速。

## 踩坑点实录

- **重复心跳风暴**：WS 断线重连后，旧连接可能还没完全关闭，导致服务端同时看到两个相同 agentId 的连接。必须在服务端维持 “每 agent 单连接” 规则，新连接到来时主动踢掉旧连接并记录告警。  
- **轮询积压**：在某些 Node 事件循环阻塞场景，`setInterval` 会积压大量回调，一旦恢复瞬间发出数十个请求。改用 `setTimeout` 递归调用，并检查前一个请求是否已完成。  
- **负载均衡器静默断连**：AWS ALB 默认空闲超时 60 秒，NGINX 代理默认也类似。如果 PING 间隔是 30 秒，看似安全，但一旦 ALB 执行滚动更新或连接迁移，长连接可能直接断开而不通知客户端。解决方案：发送应用层 PING 的同时开启 **TCP keepalive**，或者把 PING 间隔降到 20 秒以内。  
- **MCP 场景的心跳误判**：MCP 协议本身没有标准心跳，如果我们把 MCP 的 `notifications` 当作心跳，会混淆业务逻辑。务必使用单独的机制或扩展一个 MCP `ping` 工具，避免因为某个大模型响应慢导致误判掉线。

## 可复用建议

1. **分层设计**：控制器侧独立 Heartbeat 服务 + Agent 侧可插拔 Channel。不要将心跳逻辑硬编码进业务代码。  
2. **指标暴露**：为每一次心跳失败、切换、延迟打点，方便后续调优（Prometheus 格式最好）。  
3. **幂等关闭**：停止心跳时，发送一个 “我走了” 的控制帧，避免服务端等待超时。  
4. **高可用考虑**：在多控制器实例环境下，通过 Redis Pub/Sub 或共享存储剔除僵尸 Agent，防止脑裂。  
5. **安全性**：heartbeat 端点需携带签名 token，防止未授权探测。轮询接口实现限流，避免被作为 DDoS 反射点。

## 总结

没有银弹。如果你面对的是一两百个部署在标准容器里的 Agent，WebSocket 推送能给你接近实时的感知，同时省下大量无效 HTTP 请求。如果你有浏览器插件、边缘设备或严格网络策略的环境，轮询几乎是唯一选择。真正健壮的做法是让二者共存，并根据运行时环境自动降级。工程世界不相信“一刀切”，只相信精心治理的状态机。
