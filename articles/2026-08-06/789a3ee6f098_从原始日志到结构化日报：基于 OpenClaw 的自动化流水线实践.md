## 背景

团队维护着多个后端服务，每天早晨都需要一名值班同学翻看前一天的日志，汇总错误频率、关键异常、慢接口、资源使用峰值等信息，然后人工写成一份结构化的日报。这项工作重复性高，任何遗漏或理解偏差都可能影响上游决策。引入自动化日报生成不是为了“炫技”，而是想把这部分机械劳动完全交给流水线，让人专注于异常分析和改进。

## 问题拆解

原始日志通常有这些特点：
- 来源分散：应用日志、网关访问日志、数据库慢查询日志、系统监控日志等，格式各不相同；
- 非结构化：即使有 JSON 格式，字段含义、时间戳形式也存在差异；
- 噪声巨大：一天可能产生数百万行日志，真正需要提炼的信息占比极小；
- 报告期望：最终输出需要结构化，有摘要、分类统计、趋势对比，甚至带有建议。

单纯靠正则或脚本可以完成一部分统计，但面对“从错误堆栈中归纳出是哪个模块出了问题，以及可能影响哪些接口”这样的需求，传统方法捉襟见肘。我们希望利用 LLM 的理解能力，同时又要避免它凭空编造数据。

## 实现思路与步骤

### 1. 让日志查询变成 MCP 工具

在 OpenClaw 的 Agent 工作流里，任何外部能力都建议包装成 MCP 服务或插件。我们实现了一个轻量的 MCP 服务器，对外暴露 `query_logs` 工具，参数包括：服务名、时间范围、日志级别过滤、关键字、最大返回条数。内部根据参数到 Elasticsearch 或日志文件（开发环境）中检索，返回结构化的日志行列表，每条包含时间、服务、级别、原始消息。

这样 Agent 不需要知道日志存储细节，只需要像调用函数一样获取数据。

### 2. 设计日报模板与提取目标

先与团队对齐日报中真正有价值的信息，把它固化为一个 JSON schema，核心字段包括：
- 整体摘要（1-2 句）
- 错误统计（按错误类型分组，包含首次/末次出现时间、出现次数、影响接口）
- 慢请求 TOP 10
- 资源（CPU、内存、磁盘）峰值及时间点
- 关键日志片段（原文引用，用于验证）
- 自动生成的建议（可选，需标注为 AI 生成）

这样做的好处是，后续 LLM 抽取目标明确，也方便人类快速比对。

### 3. 构建 Agent 流水线

在 OpenClaw 中搭建了一条“计划—执行—审查”的流水线：

**Step 1：规划阶段**  
Agent 收到“生成昨日日报”的指令后，先根据模板拆解出需要哪些数据。它会输出一个计划，例如：
1. 获取所有服务的 error 级别日志；
2. 获取慢查询日志；
3. 获取资源监控数据（如果监控数据也通过 MCP 暴露的话）；
4. 分片摘要。

**Step 2：分批获取与预处理**  
由于单次调用可能返回数万行日志，我们要求 Agent 先获取时间段内错误数的大概统计（可以是一个单独的 `stats_logs` 工具），如果数量过大，则按小时或按服务分片获取。每一批日志交给 LLM 进行结构化提取，要求输出符合日报 schema 的片段，并强制要求引用原文中的关键行（作为 evidence）。

**Step 3：汇总与报告生成**  
收集所有片段的提取结果后，进入汇总阶段。这里会合并同类错误、去重、计算时间窗口等，最后填入完整的日报 JSON。然后一个单独的模板引擎（可以是简单的 Mustache 渲染）把 JSON 转成 Markdown 日报。

**Step 4：人工审查节点（可选）**  
在发送日报前，可以插入一个 `approval` 步骤，通过企业微信或邮件发送预览，值班人确认后再发布。这一步极大降低了幻觉带来的信任危机。

## 踩坑记录

**坑1：Token 上限与长日志截断**  
某些异常堆栈可能长达数千字符，如果不加截断直接喂给 LLM，很容易超出上下文。我们的做法是先提取异常类型和首行信息，只在确实需要完整堆栈时才引入原文，并限制不超过 1500 字符。同时要求 Agent 在 evidence 字段中给出精确的日志行号，方便人工回溯。

**坑2：LLM 会“补全”不存在的统计数据**  
曾遇到过 Agent 为了让日报看起来更完整，编造了“CPU 使用率峰值 92%”，而实际监控数据并无此记录。解决方法：强制性约束——任何统计数据必须来自工具返回，如果数据缺失，日报对应字段留空并注明“无数据”，绝对不允许推理生成。同时在 prompt 中加入示例，明确引导负向行为。

**坑3：时间戳的时区问题**  
日志可能 UTC，查询参数传入本地时间，MCP 工具未统一处理导致时间错位。后续规定所有日志存储、查询、报告展示统一使用 UTC，仅在最终展示时转成本地时间，避免猜疑。

**坑4：MCP 服务超时与重试**  
当日志量极大时，Elasticsearch 查询可能超过 MCP 默认超时。我们在 MCP 客户端侧配置了合理超时（30s），并在 Agent 侧加入重试逻辑，失败时自动降级为缩小时间范围重试。

## 可复用建议

- **把日志查询抽象为标准 MCP**：不管底层是 ES、Loki 还是文件，都提供统一的工具签名，后续任何 Agent 都能复用。
- **日报 schema 作为配置文件**：用 YAML 定义日报的结构、提取规则和提示词模板，而非硬编码，便于非开发人员调整。
- **渐进式引入**：先让自动日报与人工日报并行运行一周，对比差异、微调 prompt，再逐步切换。
- **记录每次生成的 evidence**：方便回溯和评估 LLM 提取质量，可定期抽样审查以优化提示。
- **分割确定性统计与 LLM 提取**：能通过规则统计的指标（如错误计数、慢查询数量）直接用代码输出，减少 LLM 任务范围，降本增效。

## 总结

这条流水线本质上就是“获取原始日志→分片提取结构化信息→按模板汇总报告”，技术栈并不复杂，但真正的工程挑战在于抑制幻觉、处理边界情况和确保长期稳定。有了 OpenClaw 的 Agent 编排能力和 MCP 的工具抽象，我们可以把注意力集中在提示词设计和数据校验上，而不是反复写胶水代码。目前这套东西已经在团队内部稳定运行了两个多月，平均每个工作日节省约 40 分钟的人工汇总时间，错漏率反而下降。如果你也有类似的需求，建议从最小闭环开始，跑通一条日志源，再扩展。
