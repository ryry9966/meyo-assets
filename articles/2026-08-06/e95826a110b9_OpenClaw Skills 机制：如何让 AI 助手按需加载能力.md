## 为什么需要按需加载

在构建基于 OpenClaw 的 AI 助手时，一个常见的矛盾是：我们希望助手掌握很多能力（查库存、发邮件、管理日程、调用外部 API），但如果把这些能力全部塞进系统 prompt 和工具列表，每次对话都会带上大量无关上下文，既浪费 token，又拖慢响应速度，还会加剧模型的幻觉。

OpenClaw 的 Skills 机制就是为了解决这个问题而设计的。它的思路很直接：把一组相关的工具、提示词和配置封装为一个 Skill，只有在对话上下文确实需要时，才把这个 Skill 的能力“注入”到当前会话里。

这跟 MCP（Model Context Protocol）的设计哲学有些相似，但 OpenClaw Skills 的粒度更贴近“业务能力包”，并且提供了更细粒度的触发控制、冲突处理与自动卸载策略，适合需要稳定运行的工程化 Agent。

## 问题前置：全量暴露的典型翻车现场

先还原一个真实场景。我们做了一个内部运维助手，具备以下能力：
- 查询服务器状态（`get_server_status`）
- 重启服务（`restart_service`）
- 查看日志（`search_logs`）
- 发送钉钉通知（`send_dingtalk`）
- 查询知识库（`search_kb`）

把所有工具一次性注册后，用户只是随口说了一句“帮我看看 API 网关有没有异常”，模型就开始在后台疯狂思考：要不要重启服务？要不要发通知？最终生成了冗长的回复，并且偶尔会错误地建议“重启生产服务”，非常危险。

根本原因在于：**模型面对过多工具时，选择工具的准确性会明显下降，而且系统 prompt 中充斥了大量与当前意图无关的指令，干扰推理。** 这就是按需加载的出发点。

## OpenClaw Skills 的工作方式

OpenClaw 中的 Skill 是一个自包含的目录，通常结构如下：

```
skills/gateway-ops/
├── skill.yaml
├── prompts/
│   └── system.md
└── tools/
    ├── get_gateway_status.py
    └── restart_gateway.py
```

核心是 `skill.yaml`，它定义了 Skill 的元信息、触发条件、提供的工具列表与优先级。一个简化版的配置：

```yaml
name: gateway-ops
version: 1.0
trigger:
  keywords: ["网关", "gateway", "路由", "限流"]
  require_confirmation: true   # 高危操作需要二次确认
tools:
  - name: get_gateway_status
    description: 获取网关运行状态
  - name: restart_gateway
    description: 重启网关服务
priority: 10
ttl: 120   # 激活后无相关对话超过 120 秒自动卸载
```

当 OpenClaw 的对话管理器检测到用户输入中命中了 `trigger.keywords`，就会把该 Skill 标记为 **已激活**，并将其 `system.md` 的内容追加到当前会话的指令中，同时将 `tools` 列表注入到可调用工具集合里。一旦对话进入其他主题，并且超过 `ttl` 时间没有再次命中触发词，这些注入的工具和提示就会被移除，恢复默认状态。

这种方式既保留了灵活性，又避免了长期占用上下文窗口。

## 实际操作步骤

在 OpenClaw 中启用 Skills 机制，一般需要三步：

**1. 准备 Skill 目录和描述文件**

按上面的结构创建目录，重点是写好 `trigger`。关键词不要贪多，3–5 个精准词足矣。如果条件更复杂，可以使用 `trigger.intent` 配合内置意图分类器来匹配。

**2. 实现工具**

工具可以是 Python 函数，也可以是封装好的 HTTP 接口。注意输出格式最好用 JSON，并在 description 中清晰说明参数和返回结构，这对模型的调用准确率影响非常大。

**3. 注册并调试**

在 OpenClaw 的配置文件中指定 `skills_dir` 路径，重启实例后，对话管理器会自动扫描所有 Skill。可以通过日志查看加载状态，常见的信息有：

```
[SkillsLoader] Loaded skill: gateway-ops (priority=10)
```

调试阶段可以先打开“详细日志”，观察哪些 Skill 被触发、什么时候被卸载，确认行为符合预期。

## 踩坑记录

在实际落地过程中，有几个容易忽略的问题：

- **多个 Skill 同时命中，工具列表爆炸**  
  如果用户一句话同时命中了“网关”和“日志”两个 Skill，就会同时注入两套工具，又回到了全量暴露的状态。解决办法是在 `skill.yaml` 中配置 `group` 和 `mutual_exclusive` 字段，让属于同一互斥组的 Skill 只能激活一个；或者设置全局最大激活 Skill 数量（建议 2–3 个）。
  
- **触发条件过宽，Skill 频繁加载卸载**  
  关键词设置太通用（比如“错误”），几乎每次对话都会被激活，造成系统抖动。这时可以改用“触发阈值”：一个 Skill 需要短时间内命中多次关键词才激活，避免被偶然词语误触发。OpenClaw 的配置支持 `trigger.min_hits: 2` 和 `trigger.time_window: 30s`。

- **工具冲突与权限泄露**  
  不同 Skill 可能定义了同名工具，或某个高危工具被意外注入到不相关的对话里。务必在工具命名时加上 Skill 前缀，并在重启类操作中强制 `require_confirmation: true`，同时通过用户角色权限控制工具的可见性。

- **上下文指令过于冗长**  
  有些 Skill 的 `system.md` 写得像技术文档，动辄上千字，注入后挤占大量 token。建议每个 Skill 的指令控制在 200 字以内，只补充当前场景下的必要行为约束，通用指令留在全局 system prompt 中。

## 可复用的工程建议

1. **划分能力边界，避免大杂烩 Skill**  
   一个 Skill 只负责一类操作，比如“网关运维”和“数据库查询”不要混在一起。拆得越清晰，按需加载的效果越好。

2. **利用优先级与 TTL 控制生命周期**  
   对于高危 Skill，可以设置较高的 `priority`，让它在同时命中时优先激活，并缩短 `ttl`，任务结束后快速退出，减少暴露面。

3. **建立 Skill 加载监控**  
   在日志中记录每个 Skill 的加载次数、平均存活时间、对应的用户意图。这些数据可以帮助你优化触发词和卸载策略，也能及早发现异常调用。

4. **组合而非嵌套**  
   OpenClaw 支持一个 Skill 声明对其他 Skill 的依赖，但不建议层层嵌套。跨 Skill 调用尽量通过顶层的编排逻辑完成，保持扁平结构，便于维护和调试。

## 总结

OpenClaw 的 Skills 机制本质上是一种 **上下文资源的动态调度策略**。它用少量配置，把“什么时候该给模型什么能力”这个问题从模型自身转移到了框架层，让推理更聚焦、响应更快，也降低了高危操作的误判风险。

对于已经深入使用 OpenClaw 构建 Agent 的团队来说，这是一项投入不大、回报明显的优化。与其花大量精力微调模型，不如先检查一下：你的助手是不是装了太多不需要的“默认技能”？
