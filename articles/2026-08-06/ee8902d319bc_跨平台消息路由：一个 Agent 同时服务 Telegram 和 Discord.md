# 跨平台消息路由：一个 Agent 同时服务 Telegram 和 Discord

## 背景

很多基于 OpenClaw 的 Agent 实践都是从单一平台开始的，通常是 Telegram 或者 Discord。当用户基础跨到两个平台，或者团队内部协作需要同时覆盖不同社区的 im 渠道时，复制一套逻辑去维护两个 Bot 很快就变得令人头疼——配置散落、行为偏差、修复要改两处。

更合理的方式是让**同一个 Agent 核心**通过适配层服务于多个平台，消息路由在内部完成，回复能正确返回来源频道。这篇文章就总结一下我们在工程化部署 OpenClaw Agent 跨 Telegram/Discord 双平台时，踩过的坑和最后沉淀下来的可复用方案。

## 问题拆解

跨平台消息路由不单纯是多开一个 poller 或 webhook，真正的难点在于：

1. **消息格式不一致**：Telegram 的 MarkdownV2/HTML 与 Discord 的 Markdown 差异不小，转义字符、链接格式、代码块标注都不同。
2. **回复路由**：Agent 产生响应后，必须知道这条响应对应哪个平台、哪个频道/私信。
3. **平台特性隔离**：Telegram 支持编辑消息、按钮回调、inline query；Discord 有 embed、slash command、反应。如果 Agent 本身想保持简单，适配层需要把这些特性修剪成统一的能力集。
4. **速率限制与可靠性**：Telegram 有 flood control，Discord 有严格的全局速率限制，多平台意味着故障域扩大，随意轰炸会被 ban。
5. **会话连续性**：同一个用户在两个平台上的对话历史需要隔离，避免上下文串扰。

## 做法：统一消息模型 + 适配器路由

### 1. 定义平台无关消息体

先抽象一个内部消息结构，所有入站消息都会被 connector 转换成这个格式：

```
{
  "platform": "telegram" | "discord",
  "channel_id": "string",       // 群组/频道/私信唯一标识
  "user_id": "string",
  "text": "string",
  "attachments": [...],         // 统一文件描述
  "reply_to": "string"          // 原始消息 ID
}
```

出站消息类似，但增加 `target_platform` 和 `channel_id`，让 router 知道该调哪个适配器。

### 2. 实现平台连接器（Connector）

为每个平台写一个轻量适配器，负责两件事：

- **接收**：从 Telegram/Discord 的 API 拿到原始消息，转换为统一消息，投递到 Agent 的处理队列。
- **发送**：从出站队列取出统一响应，转换为对应平台的格式，调用 API 发送。

以 OpenClaw 下的实践为例，两个 connector 可以跑在同一个进程内。Telegram 侧使用长轮询（polling）获取更新，Discord 侧使用 `discord.py` 或底层的 gateway 连接。如果希望更解耦，也可以通过 Redis 或 MCP 协议将连接器变为独立服务，Agent 核心只和内部消息通道打交道。

### 3. Agent 处理逻辑保持不变

Agent 核心只认识统一消息。它被设计成纯函数或流水线：接收输入，产出文本/多媒体/动作指令。处理成功后，出站消息被写入 `outbound` 队列，由消息调度器根据 `target_platform` 路由到对应 connector 执行实际的 API 调用。

这样 Agent 逻辑完全不用感知平台的存在，新增平台只需增加一个 connector 实现。

### 4. 会话隔离

会话存储使用复合键：`{platform}:{user_id}:{channel_id}`。即使用户在 Discord 和 Telegram 使用相同用户名，对话历史也不会交叉，因为 platform 前缀已经做了隔离。如果需要用户跨平台延续对话（这种需求极少），则需要用户主动绑定身份。

## 踩坑实录

以下是在实际运行中必须处理的具体问题。

**Markdown 转换地狱**

Telegram 的 MarkdownV2 对某些字符（`_ * [ ] ( ) ~ > # + - = | { } . !`）都要转义，而且链接格式强制为 `[text](url)`。Discord 的 markdown 相对宽松，但代码块必须注明语言，并且不支持嵌套的实体。我们的做法是：Agent 生成的内容统一使用“弱标记”——仅保留粗体、斜体、代码、链接这几种最通用的格式。平台适配器在发送前根据目标平台做最后一步渲染。为此，我们建立了一个简单的 markdown 转换中间层，只覆盖 80% 常用语法，其余全部 fallback 到纯文本，避免解析错误导致消息发不出去。

**消息拆分**

Telegram 单条消息上限 4096 字符，Discord 是 2000。当 Agent 输出长回复时，必须按段落或句子边界拆分，并且要保留顺序。我们在发送适配器中加入了智能拆分器，还能为拆分后的多条消息加上 `(1/3)` 这样的页码，避免信息断裂。注意：代理式拆分必须考虑代码块不能断在中间，否则 markdown 反而会渲染失败。

**速率限制重试**

Telegram 对群组的消息速率有 20 条/分钟的限制，私聊约 1 条/秒；Discord 的全局限制更复杂。最简单可靠的方式是**串行化发送 + 指数退避**。出站队列按平台分开，每个平台维护一个发送器，发送失败时（状态码 429）根据 `retry-after` 休眠并重试。我们记录每次重试的日志，超过 3 次则丢弃消息并通知管理员，防止积压。

**附件处理**

图片、文件在 Telegram 和 Discord 的上传方式差异很大：Telegram 支持直接发送文件链接或通过 multipart 上传；Discord 一般需要先生成 attachment URL（通常先用 webhook 或 CDN）。我们统一约定：Agent 输出附件时提供可公网访问的 URL，平台适配器负责下载后按平台要求上传。对于大文件，超时和内存控制都要格外注意。

## 可复用建议

- **抽象适配层接口**：将 `receive_message`、`send_message`、`edit_message` 等定义成协议（Protocol），每个平台实现自己的版本，避免 `if platform ==` 的散落判断。
- **使用配置开关**：通过环境变量或配置文件启用/禁用某个平台，方便开发时只测一路，生产再开全平台。
- **统一日志标记**：每条日志带上 `platform` 和 `channel_id` 标签，方便在观测工具中按平台过滤排查。
- **正确处理中断**：两个长连接（或两个轮询器）要注册统一的进程信号处理，确保同时关闭，避免连接泄漏。
- **从最小能力集开始**：只先支持纯文本发送，功能稳定后再逐步加入图片、按钮等。工程上不要一步到位。

## 总结

跨平台消息路由在工程上并没有太多黑魔法，说到底就是把“平台差异”关进适配器的笼子里，让 Agent 核心只用处理一种统一的消息形式。投入几天把转换规则、速率控制、拆分逻辑做扎实，之后的扩展和维护成本会直线下降。如果你的 OpenClaw Agent 已经到了需要服务多社区甚至多产品线的阶段，这个抽象是值得的。

下一步可以考虑将这个路由层封装成可复用的 connector 模板，甚至通过 MCP 工具暴露为标准能力，让更多社区成员直接即插即用。
