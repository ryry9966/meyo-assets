## 背景：当 Agent 开始在没人盯着的时点干活

OpenClaw 里跑定时任务（Cron）不是一个新鲜事，但把任务的“脑子”完全交给一个 Agent 来驱动时，问题会密集暴露。典型场景是这样：

- 用 OpenClaw 内置的 `cron` 触发器，每天早上 9 点调起一个 Agent
- Agent 通过 MCP 工具查询数据库、生成一份 Markdown 运营日报，再通过 IM 插件发送到群聊
- 整个链路零人工干预

看着简单，实际上大部分翻车都发生在“instruction 里的一句话没说清楚”。本文不是教你写 Prompt 的玄学，而是围绕一条真实的 Cron 任务 instruction，拆一下怎么让它稳定跑下去。

## 问题：Cron Agent 的 instruction 容易栽在哪

一封日报的指令，新手可能写成：

> “每天早上 9 点，帮我查询昨天的用户注册数，生成日报发到通知群。”

这种写法在手动测试时大概率正常，但在无人值守的定时调度里会陆续出现：

1. **时间歧义**：Agent 不知道“昨天”基于哪个时区、参考哪个系统时间
2. **工具猜测**：当 MCP 提供多个相似工具时，Agent 可能选错数据源
3. **静默失败**：查询返回为空或工具调用异常时，Agent 自行编造结果（幻觉）
4. **上下文污染**：上一次 Cron 运行的记忆残留，影响本次输出
5. **输出格式不稳定**：群消息有时是纯文本，有时带了不兼容的 Markdown 表格

这些都指向同一个根因：Cron Agent 没有现场纠偏的机会，instruction 必须把 **“在没人看着的时候你也得做对”** 这件事写死。

## 做法：拆成 6 个模块写 instruction

我现在的做法是把 instruction 拆成几个固定模块，每条 Cron 任务都按这个模板填。并不是唯一解，但确实能收敛大部分不可靠行为。

### 1. 硬约束：先固化运行环境
```
你是一个无条件执行每日任务的自动化 Agent。
本次运行由 cron 触发，运行结束后必须停止任何后续行动，不得等待、不得主动追问用户。
你的工作目录为 /data/reports，运行时间为 {{cron_trigger_time}}。
你必须独立完成全部步骤，不向用户提问。
时区固定为 Asia/Shanghai。
```
这里把 Agent 的角色锁死，终止条件写清楚，防止它“等待你确认”。

### 2. 任务清单：用有序列表，别用自然语言描述
```
本次 cron 任务包含以下步骤，必须按顺序执行，不可跳过或合并：
1. 使用 get_order_stats 工具，查询 yesterday 的订单数、支付金额。
   - 日期参数取 {{yesterday_ymd}}，格式 YYYY-MM-DD。
   - 如果工具返回错误，记录到 error_log，并继续下一步。
2. 使用 get_user_stats 工具，查询 yesterday 的新注册用户数……
3. 汇总以上数据，生成日报正文（模板见第5节）。
4. 调用 send_message 发送日报到群聊“运营日报群”。
5. 任务结束，输出“CRON_DONE”，无其他内容。
```
要点：工具调用参数用模板变量而不是自然语言推断，可复用性一下提高。

### 3. 工具约束：限制选择范围
Agent 能看到的 MCP 工具可能多达十几个，不加限制就容易跑偏。每个步骤里都显式给出必须使用的工具名，并在主 instruction 下加一句：
```
你只能使用以下工具：get_order_stats、get_user_stats、send_message。
严禁调用其他任何工具，即使名称相近。
```

### 4. 失败策略：必须显式定义
Cron Agent 最大的坑是失败后什么都不说，或者更糟——自己伪造数据。所以要写清楚“什么算失败、失败时干什么”：
```
任何工具调用如果连续失败 2 次，改为执行以下应急预案：
- 将错误信息写入 err_{date}.log
- 调用 send_message 发送预设的“日报生成失败”通知到群聊
- 输出“CRON_FAILED”后停止
不得在没有数据的情况下编造任何数字。
```

### 5. 输出模板：连换行都别让它自由发挥
日报发到 IM，格式散乱很常见。直接用固定模板锁死输出：
```
日报正文必须严格按以下结构输出：
【运营日报】 {{yesterday}}
- 订单数：{orders}
- 支付金额：{amount} 元
- 新用户：{users}
---
以上数据来自自动化系统，有疑问请检查日志。
模板中的花括号变量必须用实际数据替换，不添加额外文字。
```

### 6. 收尾信号：让调度器好判断状态
最后一行固定输出特定标记，方便 OpenClaw 日志或告警规则抓取：
```
任务完成后只允许输出以下两种字符串之一：
- CRON_DONE
- CRON_FAILED
不要附加任何解释。
```

## 踩坑记录

- **时间变量注入**：不要指望 Agent 自己算“昨天”。用 OpenClaw 的模板变量 `${yesterday_ymd}` 在 Cron 触发时计算好，直接注入 instruction。Agent 只当数据搬运工，不做时间运算。
- **会话隔离**：Cron 触发的会话务必 `newSession: true`，否则遗留记忆会让 Agent 收到历史对话，输出里可能夹带上次日报的片段。
- **时区一致性**：Agent 的运行时容器、MCP 服务、指令中引用的时区必须一致。曾经踩过“Agent 跑在 UTC、工具跑在 CST”的坑，结果查了两天的订单。
- **群聊名模糊**：别写“发到日报群”，Agent 会匹配错群名。用群组 ID 或全名精确匹配，或者用一个专门的 `send_to_daily_report_group` 工具封装掉。

## 可复用建议

1. **做一个 Cron Instruction 模板库**，比如 `daily_report.md`、`weekly_cleanup.md`，把上面的模块固化下来，新任务只修改清单和模板变量。
2. **在 OpenClaw 里打开工具调用日志**，配置关键字告警：只要出现 `CRON_FAILED` 或工具错误码，就推到告警通道，避免长期静默失败。
3. **手动跑不叫测试**：Cron 指令必须用“模拟未来时间”的方式跑完整链路，否则时区和变量问题根本暴露不出来。

## 总结

给 Cron Agent 写 instruction，和给人写 checklist 很像：不要留任何需要“你猜”的空间。Agent 不会累，但会在模糊地带做出奇怪的决定。把你的时间、工具、失败操作、输出格式全写成硬规则，它就能在凌晨 3 点安安稳稳地把活干了，连一条多余的消息都不会发。
