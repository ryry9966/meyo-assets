## 背景：为什么定时触发在 OpenClaw 里值得单独一篇文章

在 OpenClaw 搭建的 Agent 工作流中，很多动作不是由用户消息直接驱动的，而是依赖「时间」来触发：

- 每天早上 9 点拉取数据源生成简报
- 每 30 秒检查一次 MCP 工具返回的任务状态
- 每隔 5 分钟给内部看板推送一次健康指标

OpenClaw 的插件体系里，**cron** 和 **heartbeat** 是最基础的两种定时触发机制。它们都写在 `openclaw.yaml` 或插件的生命周期里，但在工程实践中，选错一个常会带来任务重叠、时区漂移、心跳雪崩等问题。本文不会讲「哪个更好」，而是从真实踩坑经验出发，梳理当你面对一个“需要按时执行”的需求时，该如何在两者之间做出有依据的工程判断。

## 问题：两种触发器的根本差别在哪

我们先把概念对齐。

- **cron**：基于 Unix cron 表达式的定时触发。比如 `0 9 * * 1-5` 表示工作日早上 9 点整执行一次。它关心的是**绝对时间点**，任务本身不关注间隔。
- **heartbeat**：基于固定间隔的周期性触发。比如 `interval: 30s`，就是从插件启动开始，每隔 30 秒执行一次。它关心的是**相对间隔**，与自然时间无关。

在 OpenClaw 里，两者都作为插件的触发器存在，可以同时使用，但各自擅长解决的问题完全不同：

- cron 适合「每天/每周/每月做一次」这种**日历驱动**的任务。
- heartbeat 适合「每隔 N 秒/分钟做一次」这种**持续轮询**的任务。

可是工程上，交叉使用场景很多。比如“每 30 秒检查一次，但只在工作时间内运行”，到底该用 cron 还是 heartbeat？下面就用具体做法来说明。

## 做法：如何在 OpenClaw 插件中配置两种触发器

### 1. cron 的配置与使用范式

在 OpenClaw 插件定义中，cron 触发器可以这样写（简化示意）：

```yaml
triggers:
  - type: cron
    expression: "0 9 * * *"
    timezone: "Asia/Shanghai"
    action: daily_report
```

关键点：

- 必须指定 `timezone`，否则容器内可能默认 UTC，导致“9 点”变成凌晨。
- action 方法需要**幂等设计**，因为 cron 在任何重载、重启时不会自动跳过已过去的时间点。

常见的 cron 使用范式：**一次执行 + 快速完成**。不要在 cron 任务里做长时间阻塞操作，否则下一个周期到来时会怎样？踩坑点见下文。

### 2. heartbeat 的配置与典型场景

```yaml
triggers:
  - type: heartbeat
    interval: 30s
    action: poll_task_status
    run_on_start: true  # 插件启动后立即执行一次
```

heartbeat 非常适合与 MCP 工具或外部 API 打交道，比如轮询异步任务结果、定时采集消息队列长度。  
和 cron 不同，heartbeat 不在乎自然时间，只保证“每隔指定时间触发一次”。这个“保证”在实现上其实依赖事件循环，会受任务执行时长影响——这是最容易踩坑的地方。

## 踩坑点：真实项目中遇到的四个大问题

### 坑 1：heartbeat 任务执行时间超过间隔 → 任务堆积

假设 heartbeat 间隔 30 秒，但你的 `poll_task_status` 因为网络超时每次跑了 45 秒。  
OpenClaw 的触发器默认不会并发执行同一个 heartbeat action（这取决于具体版本和配置），但如果没有做并发控制或防重入，就会出现上一个还没结束，下一个又触发，导致任务叠罗汉，内存、连接池被打满。

**现象**：插件运行一段时间后，响应越来越慢，最终 OOM 或达到 API 限流。

### 坑 2：cron 在时区配置错误时静默偏移

开发机是 Asia/Shanghai，容器里没设 TZ 环境变量，cron 表达式里的 `0 9 * * *` 会在 UTC 09:00 执行，也就是北京时间下午 5 点。这个错误非常低端，但因为没有直接报错，经常被忽略半天。

**教训**：任何使用 cron 的地方，显式声明 `timezone`，不要依赖操作系统时区。

### 坑 3：heartbeat 在长时间阻塞后“丢失心跳”

如果 heartbeat action 内部发生死循环或长时间阻塞（比如监听 WebSocket 不返回），触发器事件循环会被卡住，导致后续间隔完全停止。这在开发阶段很容易误以为是“间隔没到”，其实是卡死了。

**排查技巧**：在 action 开头打一条 `debug log`，连续观察是否稳定输出；或在插件里加一个独立的 health check 端点，由外部监控心跳是否存活。

### 坑 4：cron 与 heartbeat 共用时的优先级误解

有人在同一个插件里同时配置了 cron 和 heartbeat，希望“工作日用 cron 做主要上报，heartbeat 做保活”。结果发现，heartbeat 在工作日也照常运行，导致两份相似逻辑互相干扰。OpenClaw 的触发器是**独立并行**的，不存在相互抑制。如果要根据时间决定是否执行 heartbeat，应当在 action 内部用条件判断，比如检查当前时间是否在工作时段。

## 可复用建议：工程化落地时的 5 条守则

1. **cron + 锁，防止多实例重复执行**  
   如果你的 OpenClaw 会多副本运行，cron 任务需要引入外部分布式锁（如 Redis `SETNX`），避免每个副本在同一时间都触发同样的操作。

2. **heartbeat 内部加超时和熔断**  
   不要把 heartbeat action 当成“一定会及时返回”的函数。所有 IO 调用都设上合理的超时（< 间隔时间的 80%），连续失败后主动降低心跳频率或暂停一段时间，防止资源耗尽。

3. **严格使用异步模型**  
   OpenClaw 的触发器基于异步运行时，你的 action 必须是协程友好的。不要在 heartbeat 里写同步 `time.sleep(10)`，否则会阻塞整个触发器循环。

4. **给两种触发器都加上“手动触发”开关**  
   通过插件配置项（如 `enable_cron`、`enable_heartbeat`）可以在运行时关闭它们，用于紧急止损或调试。这比改 yaml 重启要快得多。

5. **监控任务执行时长和跳过次数**  
   将每次 cron/heartbeat 的执行耗时、结果记录下来，并暴露给 Prometheus 等体系。当心跳间隔偏差超过 20% 或 cron 连续两次未执行时，应及时告警。

## 总结：一张决策表代替“感觉”

| 场景特征 | 推荐触发器 | 关键配置 |
|---------|-----------|---------|
| 需要按自然时间执行，如每日报告 | cron | 指定timezone，分布式锁 |
| 需要以固定频率轮询状态、拉取数据 | heartbeat | interval < 超时阈值，异步 + 超时 |
| 既需要频率又要在特定时间段 | heartbeat + 条件判断 | 在action内部根据时间判断是否执行 |
| 任务执行时间可能超过间隔 | 将任务拆分为“触发”和“执行”，触发器只负责发信号 | 解耦 |

cron 和 heartbeat 在 OpenClaw 里并不是非此即彼的对立选项，而是两种时间驱动范式的工程投影。理清自己业务的「时间需求」究竟是日历事件还是轮询信号，就能少走大半弯路。剩下的，就是把这些防重入、超时、锁和监控老老实实加上去——那才是让定时任务从“能跑”到“可维护”的真正分水岭。
