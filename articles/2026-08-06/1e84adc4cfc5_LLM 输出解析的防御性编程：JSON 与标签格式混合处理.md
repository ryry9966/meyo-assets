## 背景

在 OpenClaw 生态中，无论是开发 Agent 插件、编写 MCP 工具，还是搭建自动化流水线，几乎都会遇到同一个场景：让 LLM 输出结构化数据，然后把结果直接交给下一环节。JSON 是最自然的选择，我们也总会在提示词里强调“只输出 JSON，不要包含额外解释”。然而实际运行中，LLM 的输出经常带着各种“装饰”——Markdown 代码块、语言标记、意外换行、前后废话。用 `json.loads()` 硬接等于制造故障点。防御性编程不是让 LLM 变乖，而是在它“不乖”时系统也不会崩。

## 问题拆解

一个典型的 LLM 输出可能长这样：

```
当然，这是你需要的结果：
```json
{
  "action": "send",
  "target": "user_123"
}
```
希望对你有帮助！
```

也可能是缺少语言标识的 ``` 代码块、单反引号包裹，甚至完全没有任何标记，直接把 JSON 嵌在文字段落中。如果我们在插件里只做了一次 `json.loads(raw_output)`，上述任何一种情况都会导致 `JSONDecodeError`，进而触发重试、报错，甚至让一次任务中断。

更棘手的是，LLM 有时会在 JSON 内留下注释（`//` 或 `/* */`），或者尾部多一个逗号，这些对 JSON 标准来说都是非法的。防御性解析需要在“尽量提取有效 JSON”和“不过度复杂化修复”之间取一个平衡。

## 工程化做法

### 1. 不信任原始输出，建立提取管道

把“解析”抽象成一个工具函数，假设传入的字符串可能包含任何噪声。我通常用以下步骤流水线处理，每一层只解决一类问题：

**第一层：直接解析（侥幸快速路径）**  
先尝试 `json.loads(text.strip())`。如果成功，说明 LLM 这次真的只输出了干干净净的 JSON，提前返回，节省计算。

**第二层：提取 Markdown 代码块**  
用正则搜寻 ` ```(?:json)?\s*\n?([\s\S]*?)\n?``` `。这里的关键点有两个：一是语言标记可选；二是使用非贪婪匹配 `[\s\S]*?`，避免把后面无关内容也吞进去。若同一输出中出现多个代码块，通常只考虑第一个；但如果业务上明确要求最后一个才有效，可以通过配置调整。取出内部内容后，用 `text.strip()` 清理首尾空白，然后送入 `json.loads()`。

**第三层：去代码块标记后整体 JSON 匹配**  
当没有代码块包裹，但输出中明显存在 `{` 和 `}` 时，直接取第一个 `{` 和最后一个 `}` 之间的子串。Python 实现时用 `find('{')` 与 `rfind('}')`，确保提取范围足够大。之后再尝试解析。这一步会处理“一段文字里混着 JSON”的场景。

**第四层：记录并优雅降级**  
如果以上都失败，不要立刻甩出异常。把这轮解析的原始片段、错误类型记录到日志，返回一个缺省的结构（比如 `{"error": "parse_failed", "raw_snippet": snippet[:200]}`），让上游根据业务决定是重试、告警还是脱敏返回。当然也可以配置最大重试次数，但重试往往依赖 LLM 再次生成，成本较高，建议只在“关键路径”使用。

### 2. 设计可配置的容错策略

上述解析器可以加入一个可选参数 `strict`。当 `strict=True` 时，只接受纯 JSON 或标准代码块包裹的 JSON，解析失败直接抛异常。当 `strict=False`（默认）时，按流水线多层提取。这样在初期调试插件时可以用宽松模式快速跑通流程，需要严格约束时才切换到严格模式。

### 3. 与 Pydantic 校验结合

解析出的 dict 最好不要直接消费，而是交给 Pydantic 模型进行字段校验。一旦发现缺少必填字段或类型错误，可以明确区分“解析失败”和“结构不符合预期”两类问题，让监控和修复更聚焦。

## 踩坑记录

- **注释陷阱**：LLM 在代码块里写 `// 此处需要替换`，就算成功提取，`json.loads` 也会报错。可在提取后尝试用正则移除 `// .*$` 行注释或 `/*[\s\S]*?*/` 块注释，但小心别误删字符串内的内容。更务实的做法是，在提示词中强调“禁止在 JSON 内添加注释”，并配合解析失败日志持续优化提示词。
- **多代码块误取**：如果 LLM 在回答中先给了一个示例 JSON，又给了实际使用 JSON，只取第一个可能拿到示例。这时可以改为取最后一个代码块，或者要求 LLM 在指定标记之间输出，例如 `<output>...</output>`，便于精准定位。
- **转义混乱**：有时 JSON 内部的双引号被错误转义，如 `"name": "He said "hello""`。这种修复成本极高，强行补反转义极易引入新 bug。我选择不修，直接触发失败并让上游重试，同时把样本记录到训练集或用于提示词优化。
- **性能考量**：正则提取本身很快，但如果在一个循环里对大量 LLM 响应都执行多层提取，还是建议先测一下 CPU。对批量任务，可以调整提取顺序，把最可能命中的层放前面。

## 可复用建议

- **封装为独立工具**：把上述解析逻辑写成一个 `robust_json_parse(text: str, strict: bool = False) -> dict`，放在项目公共 utils 里。任何需要解析 LLM 输出的插件直接调用，避免散落各处自己的土法解析。
- **日志与可观测性**：每次进入第三层（fallback）或最终解析失败，都应记录一条结构化日志，包含 `model`、`prompt_hash`、`raw_preview`、`error_type`。积累一段时间后，你会发现到底是哪些情况最容易出问题，从而针对性优化提示词。
- **在提示词中约定分隔符**：与其完全依赖事后补丁，不如在提示词里增加类似“请将 JSON 放在 `<<<JSON>>>` 和 `<<<END>>>` 之间”的强约束。这样解析器只需一行正则，稳定性和速度都最高。
- **配合 MCP 工具设计**：如果你在写 MCP 工具，返回值尽量强校验，避免将不确定的结构传到下一节点。可以把 `robust_json_parse` 作为工具调用后的第一道防线，并在 schema 中声明 `fallback` 字段。

## 总结

LLM 输出解析不是一个“一次写对”的问题，而是需要持续对抗不确定性的工程实践。防御性编程的核心不是让解析逻辑完美修复所有畸形输出，而是让系统在大部分情况下能正常工作，并在无法修复时可控地失败。通过分层提取、配置化严格度、结合 Pydantic 校验以及持续日志观测，我们可以让 Agent、插件和自动化流水线更稳定地运行，减少因格式问题导致的断流。最终目标是：不要指望 LLM 天生就输出完美的 JSON，而是让你的解析器足够健壮，让格式问题变成“噪声”而非“故障”。
