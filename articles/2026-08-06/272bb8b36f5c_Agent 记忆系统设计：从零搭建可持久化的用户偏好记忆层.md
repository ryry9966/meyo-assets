## 背景：为什么你的 Agent “健忘”

在 OpenClaw 这类 Agent 框架上，我们很快能搭出一个会查天气、发邮件、调用 MCP 工具的原型。但只要服务重启或对话窗口一换，所有关于“你是谁”“你喜欢什么格式”“上次的偏好”就全丢了。

本质上，LLM 的记忆目前主要依赖上下文窗口。虽然模型上下文越来越长，但静态 prompt 管理不了随时间演化的偏好。真正的“记忆”应该是一种**跨会话、可检索、可更新、可裁剪**的外部状态。工程上，这可以分为三层：

1. **会话记忆**：当前对话中的短期事实（比如刚刚输入的 repo 路径）。
2. **用户档案**：稳定的偏好与知识（总是用中文回复、讨厌某类比喻、常用工具链）。
3. **经验记忆**：从历史交互中提取的模式（比如你每次在提到性能时都要求给出 profiling 命令）。

## 问题：分散的偏好，缺失的召回

在设计记忆系统时，最常遇到的问题不是“存不存得下”，而是“该想起来的时候根本想不起来”。

典型的翻车现场：
- 用户两周前说“以后所有的 Python 示例用 asyncio 写法”，Agent 却因为只依赖最近 10 轮对话，依然给出同步代码。
- 用全文检索匹配简单偏好，但“我不想要长篇大论”和“总结简洁些”因为词汇不匹配而检索失败。
- 记忆越积越多，却没有任何遗忘或总结机制，每次检索都拖出一大堆历史片段，反而污染了 prompt。

所以，我们需要一套**从采集、存储到召回、维护**的闭环设计。

## 做法：一个可落地的四步设计

### 1. 偏好采集：显式 + 隐式双通道

**显式采集**：当用户说“记住，以后输出用 Markdown table”时，触发一个记忆写入工具（通过 MCP server 暴露一个 `remember` 函数，或解析指令关键词）。

**隐式采集**：在每段有意义的交互后（比如任务结束、用户纠错），用低成本模型或规则判断是否包含偏好信号。例如检测到用户连续两次把 JSON 输出手动改成 YAML，就自动提取一条“输出格式偏好 YAML”的记忆。

工程上推荐的做法是：在 Agent 的“观察-思考-行动”循环中加入一个 **`memory_extract` 后处理步骤**，输出结构化偏好条目，而不是把整段对话直接存储。

### 2. 记忆存储：双层结构

我目前的做法是用**用户档案文件 + 向量索引**两层：

- **用户档案**：一个 JSON/Markdown 文件，存储稳定偏好，如 `{"language": "zh-CN", "output_format": "markdown", "avoid_phrases": ["最后但并非最不重要的"]}`。这份文件直接拼入 system prompt 的开头，保证每次对话都能看到最核心的偏好。
- **向量索引**：对于较长的、情境依赖的记忆（例如“上次排查 Nginx 502 时用的那几条命令”），存到向量数据库（如 chromadb 或 Qdrant），以用户 ID + 时间戳为元数据，检索时按语义相似度召回 top-k。

这样，高频核心偏好零延迟生效，低频但关键的细节也能随时检索。

### 3. 记忆召回：多路检索 + 重排序

不要只在对话开头检索一次，而是**每次 LLM 收到用户输入前，先跑一个记忆检索步骤**。

简单但是有效的工程流：
```
用户输入 ->
[关键词匹配用户档案] -> 命中直接返回偏好
[如果没有命中，embedding -> 向量检索top-5] ->
[用LLM做小粒度的重排序，滤除不相关的项] ->
拼入 system prompt 或作为记忆块注入
```

一个踩过的坑：直接检索原始对话片段，容易召回和当前任务无关的记忆。解决办法是在存储时就把对话**总结成抽象的“用户行为描述”**，而非原文。例如存储“用户在 Web 项目中总是优先考虑 Next.js 而非纯 React”，而不是保留整个讨论。

### 4. 记忆维护：遗忘、压缩与冲突解决

记忆如果不维护，最终会变成一个 prompt 膨胀器。

需要三个机制：
- **过期与衰减**：给记忆打时间戳，超过 N 天未强化的偏好降低权重或移入冷存储。
- **定期压缩**：每周/每 N 轮对话，用 LLM 对同类的分散记忆做总结合并，生成一条高信息密度的记忆（类似“记忆的摘要”）。这个操作可以异步跑，不影响主链路。
- **冲突处理**：当新偏好与旧偏好冲突（例如用户这次说“输出纯文本，不要 Markdown”），新记忆要覆盖旧记忆，并在用户档案中标记更新。可以要求模型在提取记忆时同时输出“被修正/删除的记忆 ID”。

## 可复用建议

- **从简单档案开始**：最有效的记忆往往是 20 行 JSON，不要一上来就上向量库和代理总结。
- **MCP 化记忆工具**：把 `remember`、`recall`、`forget` 做成 MCP 工具，OpenClaw Agent 可以像调用其他工具一样操作记忆，而不必侵入核心循环。
- **给记忆打标签**：存储时让 LLM 自动生成 `domain: ["python", "async"]` 等标签，检索时用标签过滤可以极大提高召回精准度。
- **隔离不同 Agent**：同一用户在不同 Agent（编程助手 vs 日常聊天）之间的偏好最好用命名空间隔离，防止编程偏好污染对话风格。
- **保持结构稳定**：记忆条目的 schema 一旦定义好就别频繁改动，否则历史迁移成本巨大。

## 总结

让 Agent “记住你”，在工程上不是某种神秘能力，而是一套**结构化存储 + 语义检索 + 周期维护**的系统设计。从今天开始，你可以在现有 Agent 上做两件事就能看到明显改善：第一，把核心偏好写入一个 JSON 并固定注入 system prompt；第二，给 `remember` 工具加一个简单接口，让用户可以随时显式写入一条事实。后续再逐步引入向量检索和自动提取，就能在不过度增加复杂度的情况下，让 Agent 真正越用越“懂你”。
