# 构建稳健的 Markdown 格式管线：从 AI 输出到多平台一键适配

## 背景

每当用 LLM 生成技术文档、周报或社交媒体推文，出来的几乎都是 Markdown。这份 Markdown 在 GitHub 上预览完美，粘贴到公众号却丢失加粗、代码块塌缩、列表缩进全乱；转到知乎，数学公式渲染异常；扔进飞书，表格消失。如果每次发布都要手动修正格式，自动化的意义就被吃掉了一大半。要让 Agent 或自动化管线真正落地，需要一条可靠的 Markdown 格式适配层——让一份 AI 输出自动变成各平台能直接消费的格式。

## 问题定义

不同平台对 Markdown 的支持是“方言”关系，而不是子集关系。具体差异体现在：

- **标题层级**：公众号编辑器不识别 `#` 标记，需要转为富文本样式；
- **代码块**：知乎要求注明语言，公众号需带高亮样式，飞书文档需要转为其原生代码块组件；
- **行内代码与 HTML**：公众号会过滤掉 `<code>` 标签，或丢掉 `<br>`；
- **表格**：公众号宽表格爆框，GitLab 支持合并单元格而其他平台不支持；
- **图片**：Markdown 内是外链 URL，公众号需要先上传至微信素材库，获得 `media_id` 或新的外链；
- **特殊语法**：GitHub 的 `> [!NOTE]` 警告块、task list 等，其他平台不识别。

这些差异决定了不能简单用一套 converter 通吃，需要建立一条分平台的后处理管线。

## 做法与步骤

我在实际项目中用 Node.js + [unified](https://unifiedjs.com/) 生态搭建了一条可扩展的 Markdown 管线，结构如下：

### 1. 输入标准化
从 LLM 拿到的原始 Markdown 可能存在不规范书写（标题缺空格、列表项前后空行不一致）。先用 `remark-parse` 解析为 MDAST，再写几个小插件做规范化：

```ts
// 示例：强制标题后空格
visit(tree, 'heading', (node) => {
  // 修正逻辑...
})
```

这样保证后续转换器看到的 AST 是干净的。

### 2. 通用转换层
根据目标平台是否需要“净化”，做一层通用过滤：去除不支持的 HTML 标签，将脚本、样式、`<iframe>` 等剔除；将脚注转为行内括号说明；对需要转存图片的平台，统一插入占位符标记。

### 3. 平台适配器
为每个目标平台编写一个 serializer 或 rehype 插件。以微信公众平台为例，核心流程是：

- 将 Markdown AST 转为 HTML（可通过 `remark-rehype` + `rehype-stringify`）；
- 清理 HTML：移除 `class`、`style` 等属性（微信会过滤），仅保留 `pre`、`code`、`strong` 等基本标签；
- 代码块处理：给 `pre` 包裹一个微信允许的 `<section>` 并设置合适的行高和背景色；
- 图片处理：通过一个子流程调用微信公众号素材上传接口，上传图片并获取新的 URL，替换 `src`；
- 输出最终 HTML 片段，可以直接通过 puppeteer 自动化粘贴进公众号编辑器，或配合第三方工具生成排版格式。

知乎适配器则相对简单：保留 Markdown 格式，但需要填补换行规则（知乎编辑器要求段间空行），并对数学公式添加 `$$` 包裹。

### 4. MCP 服务封装
将上述管线打包为一个 MCP server，暴露工具 `render_markdown_for_platform`，参数是原始 Markdown 和平台标识。这样，Agent 在生成内容后可以直调用这个工具获取目标格式，再交给发布工具链。例如：

```json
{
  "tool": "render_markdown_for_platform",
  "arguments": {
    "markdown": "# 标题\n...",
    "platform": "wechat"
  }
}
```

返回可直接使用的 HTML 字符串。发布动作由另一个 MCP 工具完成（比如微信草稿发布接口）。

### 5. 接入自动化流水线
配合定时任务或 Webhook，一条完整的链路可以是：知识库笔记 → 提取 → LLM 润色 → 管线转换 → 多平台发布。这中间格式适配完全由管线承担，人工只需最终审核。

## 踩坑点

- **公众号图片上传**：微信 API 只接受 `jpg/png`，且大小限制 2MB。管线中需检测图片格式和大小，必要时用 sharp 自动压缩转换，否则发布中断。
- **表格适配**：公众号窄屏下超过 4 列的表格体验极差。转换器里加了列数检测，超过阈值自动将表格转为定义列表或分段说明。
- **代码块语言丢失**：有些 LLM 输出的代码块不带语言标记，导致公众号渲染无高亮。预处理插件会检测代码内容尝试推断语言，或默认补齐 `text`。
- **嵌套列表**：公众号编辑器对 `<ul>` 嵌套支持不稳定，深层级会丢失缩进。改用 `blockquote` + 缩进字符的方案来模拟。
- **AST 操作的性能**：如果每次转换都完整解析 AST，单次耗时约 20ms 以内，对 Agent 调用可接受。但如果批量大规模，可考虑缓存转换器实例。

## 可复用建议

- **首选 AST，别用正则**：Markdown 的复杂性用正则处理边界情况会失控，unified 的生态足够健壮。
- **配置化平台规则**：每个平台写一个 JSON 配置文件，描述允许的标签列表、属性白名单、自定义转换规则，方便新增平台。
- **单元测试覆盖平台差异点**：准备一组标准 Markdown 样例（包含各种边界），每次修改转换器后自动校验各平台输出是否符合预期。仅此一项就省去大量反复粘贴验证的时间。
- **与 Agent 解耦**：管线作为独立微服务或 MCP 工具运行，不绑定到特定 Agent 框架，提升复用性。
- **保持最小支持集**：不要试图支持所有 Markdown 扩展。只保证实际要发布的平台上的常见元素，多余的语法大胆丢弃或降级。

## 总结

Markdown 格式管线看似简单，但承载了 AI 生成内容“最后一公里”的落地体验。通过标准化解析、平台适配链和 MCP 封装，可以显著降低多平台发布的格式摩擦。工程上，这套管线一旦建立，后续接新平台只需要新增一个适配器，维护成本很低。对于在 OpenClaw 生态里尝试自动发布的技术实践者，这应该是一个值得早期投入的基础组件。
