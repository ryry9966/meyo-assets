## 背景

在搭建个人文档站、MCP 工具链或开发自动化脚本时，经常会遇到图片托管问题。静态资源如果挂在本地，分享或跨设备访问就变得麻烦；使用公共图床，要么有水印、外链受限，要么随时可能被关闭。用 S3+CDN 当然稳，但哪怕是最便宜的方案，对个人项目来说也是一笔持续性开销。

我需要一个零成本、可编程、速度快，并且能融入已有自动化工作流的图床。考察了几个方案后，最终选择了 **GitHub 仓库 + jsDelivr CDN** 的组合。这套方案的优点很明确：完全免费，全球加速，支持 API 上传，能以极低的维护成本嵌入 OpenClaw 这类 Agent 环境或 MCP 插件。

## 问题拆解

一个稳定的图床至少需要解决三个环节：

1. **存储**：可靠、持久化，最好能版本控制。
2. **上传**：日常使用方便，支持命令行、GUI、API。
3. **分发**：快速、支持 HTTPS、有缓存控制手段。

GitHub 仓库天然满足存储与版本控制；jsDelivr 提供面向开源仓库的免费 CDN，全球 750+ 节点；上传方面，PicGo、uPic 等开源客户端已经封装好 GitHub 上传逻辑，再结合 GitHub Actions 就能做成自动化流水线。

## 实践步骤

### 1. 创建 GitHub 图床仓库

新建一个公开仓库，例如 `image-hosting`，主分支设为 `main`。为了后续 CDN 路径整齐，可以在根目录建一层文件夹，比如 `/blog`、`/screenshots`。

### 2. 获取 Personal Access Token

在 GitHub 设置中生成一个 Fine-grained token 或 Classic token，赋权 `repo` 即可。Token 只授予这个仓库，避免权限过大。后续上传全靠它做认证。

### 3. 配置上传客户端（PicGo 为例）

PicGo 内置 GitHub 图床插件，配置项如下：

- 仓库名：`你的用户名/image-hosting`
- 分支：`main`
- Token：上一步生成的 token
- 路径：`blog/`（可空）
- 自定义域名：`https://cdn.jsdelivr.net/gh/你的用户名/image-hosting@main`

上传后，PicGo 自动返回形如 `https://cdn.jsdelivr.net/gh/user/image-hosting@main/blog/example.png` 的链接。拖拽、截图、剪贴板均可上传，体验和商业图床无异。

### 4. 接入自动化流水线

仅客户端上传还不够工程化。我在仓库里加了一个 GitHub Actions 工作流，每当有新的 push（包含图片文件）时，自动执行：

- 对 PNG/JPG 文件跑 `pngquant` 或 `optipng` 做无损/有损压缩
- 生成 WebP 副本
- 清除 jsDelivr 缓存（调用 purge API）

这样每次上传的图片都自动优化，避免无谓的大体积消耗仓库空间和 CDN 流量。同时，Action 会在 commit 中附加一条消息，方便追溯。

### 5. 在 Agent / MCP 中调用

对于 OpenClaw 这类 Agent 或自定义 MCP 服务端，可以封装一个轻量工具：接收本地图片路径，调用 GitHub Contents API 上传到指定仓库文件夹，再拼装 jsDelivr URL 返回。权限靠环境变量注入的 Token 控制。这样，Agent 在做文档生成、报告输出时，能自动把截图、图表持久化为在线链接，大幅提升可移植性。

## 踩坑记录

### 仓库容量与使用策略

GitHub 官方建议仓库大小不超过 1GB，对于纯图片图床其实很充裕。但需要注意不要把原图、RAW 文件一股脑推上去。通过 CI 压缩后，单张图片体积控制在 200KB 以内，一个仓库可放数千张，足够个人长期使用。如果真的超出，可以使用 Git LFS，但 jsDelivr 对 LFS 文件的支持不稳定，不推荐。

### CDN 缓存刷新

jsDelivr 的缓存很激进，新文件可能几分钟到几小时才在全球节点生效。如果前端已经引用某个 CDN 地址，而图片刚被替换（同名覆盖），旧缓存会一直返回旧内容。解决方案是：

- 文件名带哈希或版本号，避免覆盖
- 主动调用 `https://purge.jsdelivr.net/gh/user/repo@main/path/file.png` 清除缓存，刷新后通常 5 分钟内全网更新
- 在自动化流水线中，上传新文件后附带 purge 请求

### 防盗链与滥用风险

由于仓库是公开的，任何人拿到 CDN 地址都能直接访问。不建议用它托管敏感图片或高流量资源，否则可能导致 GitHub 账号被标记。个人使用场景（博客、文档、开源项目截图）完全没问题，但不要把它当成商用 CDN。

### 名称碰撞与组织结构

多人协作时，如果不约定路径，很容易出现文件名冲突。建议按功能模块建子目录，并在文件名中加入时间戳或随机字符串。PicGo 支持以年月日分文件夹，能有效减少冲突。

## 可复用建议

- **客户端选择**：如果长期只用截图，PicGo 足够；需要从命令行或脚本上传，可直接调用 GitHub API，20 行 Python 代码即可搞定。
- **压缩流水线**：在 CI 中集成 `imagemin` 或 `sharp`，统一输出 WebP 并保留原始 PNG 作为回退；可以节省 60% 以上的体积。
- **安全实践**：Token 务必用 GitHub Secrets 管理，切勿硬编码在代码仓库中。本地客户端用环境变量注入。
- **链接管理**：建议在项目里维护一个 `image-map.json`，把本地路径与 CDN 链接映射，方便批量替换或生成引用。
- **自定义域名（可选）**：如果对速度有极致要求，可以再套一层 Cloudflare Workers 做反向代理并绑定自有域名，但这样做会失去 jsDelivr 多节点回源的优势，非必要不推荐。

## 总结

GitHub + jsDelivr 的图床方案在免费、可控、自动化三方面达到了很好的平衡。它几乎不产生任何维护成本，一键上传、自动压缩、全球加速，完美贴合个人开发者、开源项目以及 Agent 自动化输出的场景。唯一的“代价”是需要对缓存机制和仓库管理有一定了解，但这些坑只要走过一次，就能沉淀出一套可复用的流水线。

对社区内正在构建 MCP 插件或 OpenClaw 工作流的同学，强烈推荐把这套能力封装成标准工具，让图片从“本地临时文件”变成“持续可用的线上资源”，整个链路会更加工程化。
