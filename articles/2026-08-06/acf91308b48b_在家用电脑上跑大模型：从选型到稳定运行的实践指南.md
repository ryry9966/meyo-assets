## 为什么要在本地跑 LLM

做 OpenClaw 和 Agent 开发久了，迟早会遇到这类场景：本地需要一条可离线运行、可控且延迟可接受的指令遵循模型。无论是给自动化流水线兜底，还是驱动 MCP 工具链里的分析节点，或者单纯不想把内部上下文的工具调用日志丢给远端 API，本地部署都已经从“体验项目”变成了工程上的硬需求。

这篇文章不会跟你比跑分，也不谈“消费级显卡跑 70B”这种极限操作。重点放在**在你的家用电脑上稳定跑起一个能做 Agent 工作的模型，并且让它融入工具链**。

## 问题拆解：我们要的到底是什么

在动手之前先想清楚：你的目标是“能跑”还是“能用”？如果是后者，需要考虑：

- 模型能否做**工具调用（function calling）**，能稳定输出符合 schema 的 JSON。
- 上下文窗口是否够长，能否承载多轮对话和工具返回。
- 推理延迟是否在接受范围内。
- 是否易于与 OpenClaw 类框架对接。

满足以上条件，我们其实不需要动不动 70B。实践中，7B-14B 参数的模型搭配合理的工具调用微调和量化，已经可以覆盖不少自动化场景。

## 硬件与选型：别冲动

当前家用电脑的主流三层：

1. **无独显或核显**（MacBook Air / 轻薄本）：跑 4-bit 量化的 3B-7B 模型（如 Qwen2.5-7B-Instruct 的 GGUF 版本），纯 CPU 推理，速度慢但可用。
2. **中端独显**（RTX 3060/4060，8-12GB 显存）：可以跑 4-bit 量化的 7B-14B，或部分 14B 模型的 INT8。
3. **高端或双卡游戏机**（RTX 4090 24GB, 双卡或 Mac Studio 大内存）：14B-34B 量化或部分 70B 低量化。

**给 Agent 用，优先考虑参数适中、工具调用能力明确的模型**。目前值得一试的选项：Qwen2.5-14B-Instruct（工具调用稳定）、Mistral-7B-Instruct（v0.3 以上支持 function calling）、DeepSeek-Coder-V2-Lite-Instruct（代码与结构输出好）。

## 部署工具：选对框架省一年命

如果只是玩一下，你可能用 Ollama。工程化复用建议考虑更可控的方案：

- **llama.cpp**（以及衍生项目如 Ollama 底层）：适合 CPU/混合推理，GGUF 格式，资源占用小，容易嵌入。
- **vLLM**：适合纯 GPU 推理，PagedAttention 快，吞吐高。家用机单卡也适用。
- **llama-cpp-python** 或 **text-generation-webui**：作为 API server 后端，与 OpenClaw 对接方便。

**推荐工程化路线**：
- 快速验证：Ollama + Open WebUI。
- 对接 Agent 框架：用 llama-cpp-python 启动 OpenAI 兼容 API，或直接用 vLLM 的 `--api-key` 模式。这样你的 OpenClaw 配置里只需要改 base_url 和 model 名。

## 可复现部署步骤（以 Qwen2.5-14B-Instruct 为例，RTX 4070 12GB）

1. **准备模型**：从 HuggingFace 下载 `Qwen/Qwen2.5-14B-Instruct-GPTQ-Int4`。模型卡一般已经包含量化文件，不用自己折腾。
2. **安装 vLLM**：
   ```bash
   pip install vllm
   ```
3. **启动兼容 OpenAI 的 API 服务**：
   ```bash
   python -m vllm.entrypoints.openai.api_server \
     --model Qwen/Qwen2.5-14B-Instruct-GPTQ-Int4 \
     --dtype auto \
     --max-model-len 8192 \
     --gpu-memory-utilization 0.90 \
     --api-key your-key
   ```
   注意 `--max-model-len` 不要超过模型支持的上下文窗口，否则 OOM 狂报错。
4. **测试工具调用**：用 curl 请求 `/v1/chat/completions`，带 tools 参数，检查返回的 JSON 结构是否稳定。
5. **对接 OpenClaw**：在 OpenClaw 的模型配置里，将 provider 设为 openai 兼容，填入 `http://localhost:8000/v1` 和 api key。启动后观察工具链调用是否按预期输出。

## 踩坑点实录

- **显存 OOM**：vLLM 里 `gpu-memory-utilization` 别设满。默认 0.90 其实已经比较激进，如果同时运行其他服务（比如 MCP server 或另一个模型），降到 0.80 更安全。如果 OOM 仍频发，换 GGUF 用 llama.cpp 跑，牺牲速度换稳定。
- **工具调用输出不稳定**：部分模型对复杂的嵌套 schema 支持差。对策：在 system prompt 里精简工具定义，避免深层嵌套；必要时后处理清洗 JSON（比如用正则去掉多余的 markdown 代码块标记）。
- **温度参数影响结构化输出**：工具调用时 `temperature=0` 是基础操作，但有些模型在 temperature=0 下仍然偶然出错。可以额外设置 `top_p=0.95` 并加入 `response_format={"type": "json_object"}` 辅助约束。
- **vLLM 与某些量化格式不兼容**：例如 AWQ 在特定版本可能报错。查看 vLLM 文档里支持的量化和模型列表，别自己造轮子。
- **多实例与锁冲突**：不要同时启动两个 vLLM 实例指向同一模型目录，会出文件锁问题。如果同时需要多个模型，分别指向不同目录或使用 Docker 挂载不同卷。

## 可复用建议

- **搭建“本地模型网关”**：无论是 vLLM 还是 llama-cpp-python，统一用 OpenAI 兼容 API 暴露，可以配 LiteLLM 做简单路由。这样在 OpenClaw 里只需一个 endpoint，未来切换模型不影响上层。
- **做一次适配脚本**：写一个 bash 脚本，参数为 model_path、port、api-key，启动服务并打印健康检查 curl，方便在不同机器上复用。
- **监控内存与温度**：用 `nvtop` 或 `nvitop` 监控显存，在 Agent 长时间运行时关注内存泄漏风险。
- **为 Agent 链路预留显存**：如果你还会跑 Whisper 或本地 embedding，总显存分配要平衡，否则工具调用到一半模型 OOM 直接崩溃。

## 总结

家用电脑跑大模型给 Agent 用，核心是**将期望管理在合理范围内**。它不可能替代服务端的高并发推理，但作为离线兜底、本地工具链驱动，以及隐私敏感场景的解决方案，完全够用。关键是把工具调用的稳定性和框架对接的工程化做好，而不是追参数量。

在实践中，我用一台 RTX 4070 的 Windows 台式机和 WSL2 里的 vLLM，稳定驱动着一组 MCP 分析脚本。延迟在 0.5-1.5 秒之间，且完全无网络依赖。这套组合已经融入了日常自动化流程。

如果你也在 OpenClaw 的本地链路里跑模型，不妨从这篇文章的步骤开始，把模型服务当基础组件来搭，而不是实验品。稳定压倒一切。
