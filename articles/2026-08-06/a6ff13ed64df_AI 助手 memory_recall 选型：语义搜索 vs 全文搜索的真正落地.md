## 为什么 memory_recall 突然变得如此关键

在构建需要跨会话记忆的 AI 助手时，上下文窗口的暴力扩展只是缓兵之计。无论你用的是 OpenClaw 还是自己拼装的 Agent 链，一旦助手需要记住几百条用户偏好、历史决策或文档片段，“把一切塞进 prompt”就彻底失效了。那时，**memory_recall** 就从一个 nice-to-have 变成系统可用性的基石。

记忆召回的核心问题可以简化为：给定一句自然语言查询，从成千上万条历史记忆中挑出最相关的几条。工程师面前摆着两条大路：**全文搜索**（Full-text Search）和**语义搜索**（Semantic Search）。社区常把后者捧得很高，但实际落地时，多数系统的记忆召回量还远远没到必须抛弃 BM25 的程度。这篇文章不卖概念，只讲我在实际使用 OpenClaw 的 memory 插件，以及用 MCP 工具把记忆外挂到 Elasticsearch 与 Qdrant 时踩过的坑和最终可用的工程方案。

## 两种召回方式，到底区别在哪里

**全文搜索**依赖倒排索引，核心算法一般是 BM25。它理解“词”但不理解“意思”。如果你的记忆里有“我喜欢深烘焙咖啡”，而用户问“推荐我喝什么咖啡”，全文搜索大概率能找到，因为“咖啡”这个词匹配得很稳。但如果用户问“推荐一款提神饮品”，全文搜索就基本瞎了，除非你手工维护同义词表。

**语义搜索**通过文本嵌入模型（Embedding model）把记忆和查询都映射到高维向量空间，比较的是语义相似度。用户问“提神饮品”时，模型知道“咖啡”和这个短语在空间上接近。代价是：对精确匹配非常不友好。比如记忆里有一条“订单号 INV-20250401 已退款”，用户问“INV-20250401 状态是什么”，语义搜索可能返回一大堆关于退款、订单的泛化结果，唯独漏掉最精确的那一条，因为向量空间更容易捕捉到“退款”这种语义簇，而不是数字字符串的精确对应。

## 实际做法：自建 memory recall 的轻量流水线

下面是我在 OpenClaw 实践中的一套可复用步骤，核心思想是**先用全文搜索保证下限，再用语义搜索提升上限**。

### 1. 索引准备：双写而不是二选一
记忆存储时，同步写入 Elasticsearch 和一个向量数据库（我用的 Qdrant）。对于每条记忆文本，Elasticsearch 侧做标准分词，向量库侧用 `text-embedding-3-small` 生成 1536 维向量并存储。chunk 大小设为 256 token，这是折中后的稳定值，过大影响精确度，过小丢失上下文。

### 2. 查询阶段：并行检索与分数归一化
用户查询进来后，用一个轻量函数判断查询类型。如果查询中包含明显的 ID、日期、邮箱模式，则将全文搜索的权重临时设为 0.8；否则各 0.5。并行请求两个引擎：

- Elasticsearch 返回 BM25 分数，做一个简单的 min-max 归一化到 [0,1]。
- Qdrant 返回余弦相似度得分，原生就在 [0,1] 区间。

### 3. 融合排序：加权倒排合并 (RRF)
我选择 **Reciprocal Rank Fusion**，而不是直接加权分数，因为归一化后的分数来自完全不同的分布，直接相加在边界条件上非常不可靠。RRF 公式简单：`score = sum(1/(k + rank_i))`，`k` 一般取 60。通过调节不同来源结果的参与深度，避免一方完全压制另一方。

最终取 top-5 记忆，注入到助手的系统 prompt 或 function call 的 messages 中。整个召回延迟控制在 180ms 以内（同等量级下）。

## 踩坑实录

**坑 1：嵌入模型对数字与代码的语义坍塌**
几乎所有的通用 Embedding 模型都会把“INV-20250401”和“INV-20250402”映射到几乎重合的向量点。如果你的记忆召回里有大量单号、ID，单纯语义搜索是灾难。必须靠全文搜索的精确匹配兜底，或者对这类实体单独建立关键词索引。

**坑 2：chunk 过大导致“记忆污染”**
早期我把一通对话直接切成 1024 token 的块，认为能保留更多上下文。结果发现召回的记忆里总带着大段无关内容，反而干扰了后续回答。减到 256 token 并加上 10% 的重叠窗口后，质量明显提升。代价是索引条数增加，但 Qdrant 和 ES 都能应付。

**坑 3：查询扩写（Query expansion）的诱惑与陷阱**
有人会在检索前用 LLM 把用户查询改写成多个子查询，看似能提升召回率。但在记忆体量不够大（<10万条）时，这往往引入噪音。除非你清楚自己的信息密度，否则直接用原始查询混合搜索是最稳妥的。

**坑 4：监控指标缺失**
很多人上线 memory 后从不看召回效果。我会在记录中打上轻量标签：用户是否采纳了基于记忆的回答、是否要求“重说一遍”等，作为离线评估的弱监督信号。如果没有这个，你永远不知道是哪一侧的召回在失灵。

## 可复用的工程建议

- **先上全文搜索，数据量过万再上语义搜索。** 在早期，良好配置的 Elasticsearch 足够解决 80% 的记忆召回，省下向量数据库的维护成本。
- **永远保留一个精确匹配通道。** 无论你多爱向量，让 ID、日期、邮箱这类实体落到有通配符或 exact term 匹配的索引上。
- **chunk 大小建议 256–384 token，配上边界意识的切分器。** 推荐用 `RecursiveCharacterTextSplitter` 并设置优先级分隔符。
- **做好搜索来源的日志标记。** 每次返回的记忆附带 `source` 字段（`fulltext` 或 `semantic`），方便回溯诊断。
- **别轻易引入查询扩写，除非你验证过收益。** 信息密度不高时，“原始文本 + 混合检索”性价比最高。

## 总结

memory_recall 没有银弹。语义搜索擅长捕捉模糊意图，全文搜索擅长抓住精确事实。在 OpenClaw 或任何 Agent 实践中，工程上正确的做法永远是**混合检索 + RRF 融合 + 精确字段兜底**。不必因为“向量数据库”听起来更 AI 就全盘倒向语义侧，那只会让你的助手在面对“我的订单号是多少”时变成一个擅长聊哲学却答不对问题的机器。

把这两种方法放在它们该在的位置，你的记忆召回才会真正可靠。
