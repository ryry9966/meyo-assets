## 背景：为什么 memory_recall 会成为瓶颈

在构建长期运行的 OpenClaw Agent 时，记忆管理是一个绕不开的工程难题。Agent 需要根据历史对话、用户偏好和领域知识来生成响应，而这一切都依赖 `memory_recall` 从记忆库中高效地捞出相关片段。你在写插件或者基于 MCP 扩展 Agent 时，很快就会面临一个关键决策：**用语义搜索还是全文搜索？**

这两种召回策略在 OpenClaw 社区里被反复讨论，但大多数资料要么偏向营销式的「向量数据库一统天下」，要么停留在轻量 demo 缺乏实际对比。这会给实际开发带来误导。本文基于真实的插件开发实践，在一个模拟客服 Agent 场景下，把两种方式拉出来硬碰硬，给出可复现的结论。

## 问题：没有银弹，只有取舍

先说本质矛盾：

- **全文搜索**：基于关键词匹配（通常用 BM25 或 match 查询），实现在 Elasticsearch / MiniSearch 甚至 `sqlite3` 的 FTS 上都很直接。它的弱点是处理中文分词、同义词和意图漂移时非常僵硬。用户问“账号怎么注销”，你存的是“永久删除账户”，可能完全召不回。
- **语义搜索**：用 embedding 模型把文本映射到向量空间，按余弦距离排序。能捕捉“注销—删除”之间的语义关联，但需要额外维护向量索引，查询延迟、模型成本和更新策略都比全文方案重一个量级。

在 OpenClaw 的架构里，`memory_recall` 通常作为内部函数被调用，对延迟极其敏感——Agent 一次推理可能触发多次回忆。一旦选型失误，要么召回质量拖垮生成质量，要么运维成本失控。

## 做法 / 步骤：一次公平的对比实验

为了方便复现，我把实验环境总结如下：

1. **数据集**：准备 500 条中文问答对，涵盖账户、支付、退款等常见客服主题，人工为 20 个代表性查询标注了相关记忆片段（作为 ground truth）。
2. **全文搜索插件**：  
   - 使用 Elasticsearch 8.x，配置 IK 中文分词器，字段 mapping 使用 `text` 类型。  
   - 在 OpenClaw 的 `memory_recall` 实现中直接执行 `match` 查询，取 Top 5，用 `_score` 排序。  
3. **语义搜索插件**：  
   - 调用 `text-embedding-3-small` 模型为每条记忆生成 1536 维向量，写入 ChromaDB（本地部署，cosine 距离）。  
   - 同样在 `memory_recall` 中完成向量查询，返回 Top 5。  
4. **评估指标**：  
   - `Recall@5`：理想片段是否出现在前 5 结果中。  
   - `MRR`：第一个相关结果的平均倒数排名。  
   - P95 查询延迟、首 token 前成本（embedding 调用次数）。

跑完一轮后，数据差异非常直观（省略具体数值，着重趋势）：

- 对精确查询（如“重置密码”），全文搜索 `Recall@5` 可达 0.95，与语义搜索几乎持平，而延迟只有后者的 1/6。
- 当查询用词宽松（如“怎么拿回冻结的钱”），全文 `Recall@5` 掉到 0.45，语义搜索维持在 0.83 左右。
- 语义搜索的 P95 延迟约 230ms，加上 embedding API 调用，每次查询额外消耗约 0.002 美元；全文搜索 P95 延迟 35ms，零额外费用。

## 踩坑点：工程落地才暴露出真相

1. **中文分词比你想象的脏**  
   IK 分词对混合中英文、带特殊符号的字段（如“OAuth2.0 登录失败”）经常拆错，导致召回断崖式下跌。必须维护一份业务词典，持续迭代。

2. **Embedding 模型不是“傻瓜相机”**  
   `text-embedding-3-small` 对长文本会截断，记忆片段超过 512 token 时，丢失的细节可能正是查询关键。用本地模型（如 bge-large-zh）虽然能控制截断，但需要 GPU 资源，部署复杂度翻倍。

3. **向量索引的更新债**  
   每次新增记忆都要重新 embedding 并 upsert，批量场景下还要处理并发写入。我们不得不引入一个异步队列，让记忆隔几秒才生效，否则会阻塞 Agent 的主流程。

4. **混合搜索不是简单叠加**  
   尝试过用 BM25 分数和向量相似度加权求和，权重（如 0.3:0.7）调了整整两天，在不同查询类型上表现不一。最终发现，不加归一化的线性组合极易受离群值影响，必须对分数做标准正态化后才稳定。

## 可复用建议：先跑起来，再精准优化

结合这次实践，以下几条规则可以帮你少走弯路：

- **记忆体量 < 1 万条、查询意图相对固定**：直接用全文搜索，配合一份完善的同义词词典，成本极低，召回率完全够用。等你发现用户开始抱怨“问得不对就不清楚”时，再考虑引入语义。
- **开放式问答或知识库类 Agent**：优先走混合搜索。推荐用 Elasticsearch 的 dense_vector 字段 + 自带的 semantic search 功能，避免同时维护 ES 和 ChromaDB 两套系统。
- **在 OpenClaw 中，别把 memory_recall 写成死代码**：把它封装成一个 MCP tool，后端支持多策略。通过查询特征（长度、是否包含特殊符号）动态选择搜索引擎，甚至缓存高频查询的向量，让性能上一个台阶。
- **异步化更新**：记忆的写入不要求强实时，用消息队列解耦，保证 Agent 响应速度不受干扰。

## 总结

全文搜索与语义搜索不是单选题，而是一对可以按需搭配的齿轮。全文搜索提供高可解释、低延迟的基底，语义搜索填补理解层面的空白。在 OpenClaw 的插件化框架下，从最简单的全文方案起步，当召回率成为瓶颈时再用向量扩展，这种渐进式演进远好于一上来就堆一个复杂的混合系统。记住，在工程上，“能用”和“好用”之间，差的就是这些基于真实数据跑出来的取舍。
