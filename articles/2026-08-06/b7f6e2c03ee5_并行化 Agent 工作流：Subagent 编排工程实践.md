## 背景：为什么单体 Agent 不够用

在 OpenClaw 社区的日常自动化实践中，我们会让一个 Agent 同时承担信息检索、文件处理、数据校验等多种职责。当任务链变长，串行执行的两个问题就暴露出来：

1. **延迟累积**：搜索五个数据源，每个等待 5 秒，用户端体验直接崩掉。
2. **上下文膨胀**：所有中间结果塞进同一个上下文窗口，不仅推理质量下降，token 成本也指数级上升。

于是很自然的想法是：**能不能把任务拆成独立子任务，交给多个 AI 并行处理，最后汇总结果？**
这就是 Subagent 编排的起点——用一个 Orchestrator Agent 管理多个专注的子 Agent，让它们同时开工。

## 问题定义：并行编排的边界与权衡

并行并非万能。适合并行化的任务需要满足：**子任务之间没有数据依赖，且都能独立完成自己的工作闭环**。比如：

- 同时调用多个上游 API，取回不同维度的数据。
- 批量分析多个本地文件，提取结构化信息。
- 对同一份文档分别做摘要、关键词抽取、情感分析。

如果子任务之间有依赖关系（如第二步需要第一步的输出），那就不适合简单并行，需要用 DAG 编排或顺序执行。本文聚焦的是**独立可并行的 Subagent 场景**。

另外，并行意味着多个 Agent 实例同时运行，会带来并发控制、上下文隔离、工具竞争、异常传播等工程难题，这些才是实际落地时的真正挑战。

## 做法 / 步骤：一套可复现的并行编排方案

在 OpenClaw 的技术栈中，我们可以基于 MCP 协议来为每个 Subagent 提供工具能力，然后用轻量的编排逻辑实现并发。具体步骤如下：

### 1. 设计 Subagent 的边界与工具集
为每个子任务定义一个专门的 Agent，它拥有清晰的 system prompt 和受限的工具列表。例如：
- `search-subagent`：只能使用 `web_search`、`fetch_page` 两个工具。
- `file-analyzer-subagent`：只能使用 `read_local_file`、`grep`。
这样避免子 Agent 由于工具过多而产生幻觉或越权操作。

### 2. 实现异步并发执行器
绝大多数 Agent 框架的 `run` 方法都是异步的，我们可以直接用 `asyncio.gather` 或线程池执行多个子 Agent。关键点在于**为每个子 Agent 创建独立 session**，确保上下文完全隔离，不会互相污染。

```python
async def parallel_dispatch(subagent_specs, input_data):
    tasks = []
    for spec in subagent_specs:
        agent = build_agent(spec['prompt'], spec['tools'])
        session = create_session()       # 独立会话
        tasks.append(agent.run(spec['query'], session=session))
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return results
```

### 3. Orchestrator 的拆解与汇总逻辑
Orchestrator 本身也是一个 Agent，先分析用户意图，拆解为若干子任务描述，再调用上述并行执行器。获得所有子任务结果后，Orchestrator 进行汇总，可能再做一次最终推理，输出给用户。注意拆解时不要引入子任务间的隐性依赖，比如“先搜索 A 再根据 A 的结果搜索 B”，这种应该拆成串行任务或使用多步编排。

### 4. 结果合并与冲突处理
各 Subagent 的输出最好以结构化 JSON 返回，合并时只需按字段拼装。如果允许 Subagent 写本地文件，必须为每个 agent 指定独立的输出路径前缀，避免文件覆写或竞争写入。

## 踩坑点：这些细节会让你怀疑自己

### 坑 1：LLM API 速率限制
并行跑 10 个 Subagent，每个都要调用 LLM，瞬间并发可能触发平台的 RPM/TPM 限制。解决办法：引入一个**并发令牌桶**，限制同时并发的 LLM 请求数（如最多 3 个），超过部分排队。同时对所有 LLM 调用增加指数退避重试。

### 坑 2：上下文泄露与串扰
如果没有严格隔离 session，A 子 Agent 的思考链可能会“漏”到 B 子 Agent 的上下文中，导致莫名其妙的输出。务必确保每个 subagent 调用都使用独立的 conversation 对象或新实例。

### 坑 3：工具竞争与副作用
如果多个 Subagent 都去操作同一个浏览器实例，或者写同一个数据库记录，就会出现并发冲突。最佳实践是：**Subagent 只使用只读工具 + 独立输出通道**，写操作统一由 Orchestrator 在合并阶段执行。

### 坑 4：异常与超时处理
一个子任务的失败（如网络超时）可能会让 `asyncio.gather` 整体抛出异常，如果没处理好，所有其他成功的结果就丢了。必须使用 `return_exceptions=True`，然后对每个结果判断是否为异常，设计 fallback 逻辑（如直接返回 “该数据源暂时不可用”）。

### 坑 5：成本失控
并行虽然快，但 token 消耗成倍增加。一个优化策略是：让轻量子任务使用更便宜的模型（如混元 lite），只有汇总阶段才用高能力模型。另外，对非必要并行任务果断拒绝拆分，避免过度工程化。

## 可复用建议：工程化地管理 Subagent 编排

- **抽象为“并行子任务组”配置**：用 YAML 或 JSON 定义一组可并行执行的 subagent 列表，包括其 prompt、tools、超时、fallback 文案，便于非开发人员调整编排逻辑。
- **统一追踪与日志**：为每个子任务打上 `trace_id` 和 `span_id`，将执行耗时、token 用量、异常信息都写入结构化日志，方便调试成本与性能。
- **适度引入消息队列**：如果并发量大，Orchestrator 不要直接调用 Subagent，而是将子任务投递到内存队列，由 workers 消费，可以实现更平滑的流控和横向扩展。
- **提前定义好工具资源锁**：对可能冲突的工具（如浏览器、命令执行环境）建立命名锁，Subagent 执行前需获取锁，避免资源竞争。
- **渐进式引入**：一开始不要上复杂的 DAG 引擎，很多场景用简单的 `asyncio.gather` 就足够。当发现频繁出现依赖需求时，再考虑引入 workflow 框架。

## 总结

并行 Subagent 编排是提升 Agent 系统响应速度和吞吐的有效手段，在 OpenClaw 的 MCP 工具生态下实现成本并不高。关键在于：

1. 严格隔离上下文，独立 session 是底线。
2. 控制并发量与异常传播，保护好成本与稳定性。
3. 划清读写边界，只读工具 + 结果汇总，避免副作用冲突。
4. 从简单场景开始，先跑通再优化，不要急于设计复杂调度器。

工程化地使用并行编排，能让你的 Agent 从“一个人慢慢干”变成“一个小团队同时分工”，在自动化实践中真正交付可用性。
