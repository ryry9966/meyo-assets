## 背景：E2E 测试的“最后一公里”

端到端（E2E）测试是保障用户路径完整性的关键，但编写和维护成本极高。一个登录流程的测试就要处理元素定位、等待、状态断言，界面一改，选择器纷纷失效。即使有录制回放工具，产出的脚本往往冗余且脆弱，需要人工重构。

过去一年，代码生成模型的质量有了明显提升，同时 Agent 生态（OpenClaw、MCP 协议）让模型能够直接操作浏览器，听起来“让 AI 写 E2E”似乎可以一步到位。但真正在工程里落地时，我发现事情远比 prompt 一句“帮我生成登录测试”复杂得多。这里记录一个经过验证的协作范式，以及其中必须面对的坑。

## 问题：AI 写出的测试为什么不可靠？

最初我让 Agent（基于 Claude + Playwright MCP）直接根据页面描述生成完整测试脚本，结果常见问题：

- **选择器脆弱**：模型倾向使用复杂 CSS 路径或 text 定位，页面文本或 DOM 结构轻微变动就挂。
- **等待逻辑缺失**：生成的脚本没有处理异步加载、动画完成，测试频繁因时序失败。
- **断言空泛**：只会检查“页面包含某文字”，缺少对状态码、输入框值、请求完成的验证。
- **不理解业务边界**：无法区分哪些交互是核心路径，哪些可以跳过，测试要么覆盖不全，要么罗里吧嗦。

核心原因：模型对动态页面的运行时状态缺乏真实感知，仅靠一次性静态快照或描述产生代码，缺乏验证闭环。

## 做法：让 Agent 成为“边看边写”的测试员

解决思路不是让模型一次性生成脚本，而是将其嵌入一个**观察-操作-验证-生成**的循环中，利用 MCP 工具让 Agent 实时感知页面变化，迭代产出测试代码。整体流程如下：

**1. 工具准备**  
使用 Playwright MCP Server 提供 browser_navigate、browser_snapshot、browser_click、browser_take_screenshot 等工具，Agent 通过 OpenClaw 直接调用。同时挂载一个文件写入工具，用于保存生成的 .spec.ts 文件。

**2. 分步生成，即时验证**  
不要求直接输出完整测试。而是先让 Agent：
- 打开目标页面，获取 accessibility snapshot（Playwright 提供的结构化页面树，比 HTML 更干净）；
- 识别关键交互元素，提出操作步骤计划，让人类确认；
- 逐步执行操作，每步后读取 snapshot 断言预期变化，并记录对应的 Playwright 代码；
- 遇到失败立即重试，调整选择器或等待策略。

这样每一步生成的代码都经过实时执行验证，再拼装成完整测试。

**3. 转化为可维护脚本**  
验证通过后，Agent 把记录的代码段组合成一个 test case，加入 beforeEach / afterEach 清理逻辑，并将脆弱的选择器替换为基于 role、label 的定位方式（遵循 Playwright 最佳实践）。最后输出到指定文件，人工可再做微调。

举个具体例子：测试购物车添加商品。Agent 先导航到商品页，snapshot 发现 “Add to cart” button，用 `page.getByRole('button', { name: 'Add to cart' })` 点击，然后 snapshot 检查购物车图标数字变为 1，确认后生成对应代码，遇到网络慢就自动加入 `waitForResponse`。

## 踩坑记录

实践中几个容易让人摔跤的地方：

**坑 1：Accessibility snapshot 不等于 DOM**  
Playwright 的 snapshot 只展示可访问元素，很多动态更新的 UI 状态（如 toast 消息、加载骨架屏）可能不在其中。需要结合 screenshot 做视觉判断，但截图分析目前还比较慢且消耗 token。**解决方案**：对关键步骤显式用 browser_snapshot 获取 aria-live 区域，或额外执行 `page.locator`.textContent() 辅助断言。

**坑 2：Agent 会陷入无限重试**  
当页面状态不符合预期时，Agent 可能反复执行相同操作却不收敛。比如网络慢导致按钮一直 disabled，Agent 会不断点击然后报错。**解决方案**：在调度层加入最大重试次数和全局超时，并提示 Agent “若连续两次失败，停止并向人类求助”。

**坑 3：生成的 fixture 和数据清理不完整**  
测试往往需要准备前置数据（如登录、创建订单），Agent 生成的脚本可能漏掉清理，导致后续测试环境污染。**解决方案**：在 prompt 中固化模板，要求每个 test 包含 setup 和 teardown 描述，再由 Agent 转成代码。

## 可复用建议

如果你打算在项目里尝试，以下几点可以省去很多调试时间：

- **选择合适的 snapshot 模式**：Playwright MCP 的 `browser_snapshot` 加上 `accessible` 参数能得到更精简的树，减少 token 消耗。
- **预先封装常用断言工具**：比如封装一个 `waitAndAssert` 函数，让 Agent 调用而不是手动写 `expect`，降低出错。
- **人工审核锚点选择器**：要求 Agent 输出代码时必须附上一行注释说明为什么选择这个定位策略，方便 review。
- **结合录制工具做兜底**：复杂的拖拽、Canvas 操作，直接让 Agent 用 Playwright Codegen 录制生成代码片段，再拼装进测试。
- **利用 MCP 的组合能力**：除了 Playwright，你还可以接入日志分析 MCP、API Mock MCP，让 Agent 写测试时能获取完整的系统状态。

## 总结

Agent 协作生成 E2E 测试目前更适合作为“加速脚手架”而非“全自动方案”。核心价值是用实时交互验证取代凭空想象，让模型在环境中试错并修正代码，产出的测试具备更高的执行稳定性。但这仍然需要工程化约束：清晰的步骤确认、重试边界、选择器规范以及人工把关。把 Agent 当成一个能即时运行并观察结果的高级帮手，而不是一个一次性代码生成器——这才是现阶段务实有效的协作方式。
