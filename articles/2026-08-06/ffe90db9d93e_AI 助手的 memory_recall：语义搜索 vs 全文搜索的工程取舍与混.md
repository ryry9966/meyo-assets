## 背景

在给 OpenClaw 插件或 MCP Agent 加“记忆”能力时，memory recall 几乎是一个绕不开的模块。我们希望助手能记住更早的对话、能检索某个知识库里的段落、能从一堆自动化日志里捞出相关上下文。常见的做法无外乎两类：**语义搜索**（embedding + 向量相似度）和**全文搜索**（BM25、FTS 等）。

网上很多讨论会直接说“语义搜索更智能、全文搜索过时了”。但在真实工程里，这两类方案各有非常具体的适用边界，尤其是在中文环境、多轮对话、领域知识库这些场景下，差异会被放大得很厉害。下面基于我们自己在几个 agent 记忆插件上的实践，把两者放在同一个场景里做对比，并讨论一种低成本混合方案。

## 问题：一个检索需求，两种思维

假设我们要为 OpenClaw 的会话记忆做一个 `search_memory` 工具，输入自然语言查询，返回最相关的若干条历史摘要。用语义搜索的话，大概流程是：

1. 将所有记忆片段用 embedding 模型转成向量（如 text-embedding-3-small 或本地 bge-small-zh）。
2. 查询时同样做 embedding，用余弦相似度或内积取 top-k。

用全文搜索的话，流程是：

1. 对记忆片段建立倒排索引（SQLite FTS5 / Meilisearch / Elasticsearch）。
2. 查询时用同样的分词器和匹配算子（如 BM25），按相关性得分排序。

初看语义搜索更聪明，它能搜到“手机没电了”和“设备电量耗尽”这类近义表达。但一旦你的查询里出现一串 API 名称、错误码、或者固定话术时，语义搜索会经常把一些“看起来语义很像但完全不相关”的内容排到前面。反之，全文搜索查“E1001”不会把“E1002”排成第二，除非你开了模糊匹配；但如果你问“告警系统最近有什么异常”，全文搜索在中文分词不好的情况下可能直接找不到任何东西。

真正让人头疼的不是“谁更好”，而是同一个 Agent 在同一个会话里，这两种查询都会出现。

## 做法：用一个实验看清楚差异

我们做了个最小化实验，用来量化两种检索在不同查询类型下的表现，你也可以在 local 环境复现。

**步骤**

1. **准备记忆库**  
   从我们的内部知识库抓取 500 条短文本，每条 50～200 字，涵盖三类内容：
   - 错误信息与排障步骤（如“E1001 磁盘满，请清理 /var/log”）
   - 模糊的自然语言问答（如“为什么服务会在凌晨重启”）
   - 固定短语/命令（如“/health_check 返回 200 OK”）

2. **建立两个索引**
   - 语义索引：使用 `BAAI/bge-small-zh-v1.5` 本地生成 512 维向量，存入 numpy 数组并用 faiss 构建 Flat 索引。
   - 全文索引：用 SQLite FTS5，配置 `jieba` 作为外置分词器，保证中文短语能被合理切分。

3. **构造查询集**
   准备 50 个查询，刻意混合三种模式：
   - 精确匹配型（10 个，如 “E1001 磁盘满”）
   - 近义改写型（20 个，如 “磁盘容量不足导致报错”）
   - 自然语言问题型（20 个，如 “日志里出现 timeout 是什么原因”）

4. **评估指标**
   我们只关心 top-3 命中率（relevant@3），也就是前三个结果里是否有相关记忆。这更接近 agent 在几次检索里拼上下文的实际用法。

**结果摘要**（不是论文，仅反映我们这个 500 条语料的趋势）

- 精确匹配型查询：全文搜索 `relevant@3` ≈ 0.92，语义搜索 ≈ 0.74。语义搜索把一些“磁盘相关”但错误码不对的内容排到了前面。
- 近义改写型：语义搜索 ≈ 0.88，全文搜索 ≈ 0.45。分词后“磁盘容量不足”和原文“磁盘满”之间完全没有交集。
- 自然语言问题型：语义搜索 ≈ 0.80，全文搜索 ≈ 0.52。文本较长时，BM25 的单词匹配几乎无效。

这表明：如果你的 query 天然分布在“精确”与“模糊”两端，任何单一引擎都会拖后腿。

## 踩坑点

1. **embedding 模型的选择是第一个坑**  
   早期用了某个英文为主的通用模型，中文近义词会被映射得很远。本地换用 bge-small-zh 后改善明显，但该模型对代码/日志中的下划线和数字串敏感度一般，需要做一点预处理（比如将 `_` 替换为空格）。

2. **分词器要适配领域**  
   默认 jieba 会把错误码“E1001”拆成“E”和“1001”，导致全文搜索对代码类字符串近乎失效。解决方法是维护一个简单的自定义词典，或在入库时用正则将这些 token 原样保留为专有名词。

3. **语义搜索的“太聪明”问题**  
   给定“如何查看 CPU 使用率”，语义搜索可能把“内存使用率过高”排到第一位，因为两者都涉及系统资源。在没有用户反馈的 agent 场景，这种错误很容易被忽视。需要用简单的规则做后置硬过滤，比如关键词必须包含至少一个名词重叠。

4. **资源开销**  
   faiss + bge 在本地跑没有问题，但如果你计划把 memory 放在 MCP server 中，并提供给多个 agent 共享，请提前评估内存和首次加载时间。对于小型部署，SQLite FTS5 几乎零成本，反而是更具工程鲁棒性的底座。

## 可复用建议

**1. 用混合检索，而不是二选一**

一个低成本且有效的做法是：同时跑两个检索，各取 top-15，然后用一个轻量级重排序（例如基于关键词命中数和简单规则加权）把两个列表合并。逻辑大致像这样：

```
semantic_results = vector_search(query, top_k=15)
fulltext_results = fts_search(query, top_k=15)
merged = reciprocal_rank_fusion(semantic_results, fulltext_results)
```

我们在 OpenClaw 的 memory 插件里实现了这种融合，代码不到 100 行，实际体验比任何单一方案都稳。

**2. 让调用方指定“偏好模式”**

在 MCP 工具定义里，给 `search_memory` 加一个 `search_mode` 参数：`"auto" | "exact" | "semantic"`。如果用户查询里包含双引号或明显标识符，可以自动切到 `exact`；如果全是自然语言，就用 `semantic` 优先。这种显式控制能规避很多“猜不准”的烦恼。

**3. 对冷启动数据用全文索引兜底**

很多自建知识库早期没有足够多的 paraphrase 数据来让语义模型学到相似性，此时全文搜索至少能保证精确匹配可用。等 query 日志积累到一定量，可以再用用户点击数据微调 embedding 模型，逐步提升语义检索的能力。

**4. 中文先做分句，再建索引**

把长文档切成 200～400 字的段落，无论是 embedding 还是全文索引，都会显著提高召回质量。可以直接用 `re.split` 配合句号/换行符粗切，比后来补 chunk-overlap 省事。

## 总结

语义搜索和全文搜索在 memory recall 里不是替代关系，而是互补关系。在一个实际运行的 Agent 系统中，查询模式远比我们想象的复杂，单一引擎的短板很快会变成整个助手的体验短板。用一套轻量的混合检索 + 参数暴露的方案，能让 memory 插件在精确性与模糊泛化之间找到一个可控的平衡点。

在没有用户行为反馈的早期阶段，我倾向于把全文检索当作“安全网”，语义检索当作“加分项”，再通过简单的融合策略让两者在不增加太多复杂度的前提下共存。
