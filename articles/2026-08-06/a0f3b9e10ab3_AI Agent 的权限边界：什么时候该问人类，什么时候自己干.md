## 背景：Agent 的“手”伸得越来越长

在 OpenClaw 这类可组合 Agent 框架里，我们通过 MCP 服务器或插件把数据库、文件系统、APIs、消息通道递给模型，Agent 从一个“只说不做”的顾问变成了能真正执行动作的自动化实体。问题也随之而来：删库跑路的玩笑背后，真实的风险在于**一次无心或误导的工具调用**。

很多团队让 Agent 放开了跑，理由是“我们加了审计日志”。但等到日志报警时，数据可能已经被覆盖、邮件已发出、流水线已触发。另一种极端是每个文件写入都弹窗确认，导致自动化链路轰然“塞车”，人类反而成为瓶颈。

我们需要回答一个很工程化的问题：**在哪些调用上必须等待人类点头，哪些可以默认放行，并且这种决策如何在代码里落地。**

## 问题拆解：模糊的授权模型

常见的授权模糊集中在三个地方：

1. **动作风险不可见**：开发者知道 `delete_user` 危险，但在 Agent 的工具描述里它和 `list_users` 长得几乎一样。
2. **上下文缺失**：Agent 在本次任务中的身份（是以管理员还是访客视角执行？）没有传入权限判断层。
3. **审批时机错位**：同步确认卡住整个任务，异步确认又可能产生竞态——两份相同的危险操作几乎同时被批准。

把这些点压缩成一张表，就是我们常说的“权限边间线”。没有这条线，Agent 的自由裁量权就滑向两个极端。

## 做法：三步构建可落地的权限制裁层

以下方案基于 OpenClaw 的 action/middleware 机制，但对多数类似框架（LangChain 等）思路通用。

### 步骤 1：给每个工具加上“风险等级”和“上下文需求”

不要只用“危险/安全”二分。建议分成 4 级：

- **Level 0 – 只读/无副作用**（如 `search_docs`, `list_files`）
- **Level 1 – 影响当前用户局部数据**（如 `update_profile`, `add_todo`）
- **Level 2 – 影响多用户或关键配置**（如 `change_channel_topic`, `export_members`）
- **Level 3 – 不可逆/组织级影响**（如 `delete_project`, `send_broadcast`, `run_destructive_script`）

在 MCP 工具注册时，扩展一个 `riskLevel` 和 `requireContext` 字段。例如 OpenClaw 里可以在工具声明上附加 metadata，后续由 middleware 消费。

```json
{
  "name": "delete_project",
  "description": "永久删除项目及其所有数据",
  "riskLevel": 3,
  "requireContext": ["project_owner", "reason"]
}
```

### 步骤 2：实现一个 Guard Middleware

在 OpenClaw 的 action 执行链里插入一个 `permissionGuard`，每次工具调用前做三道判断：

1. 当前运行模式是 `auto` 还是 `approval`？如果已经全局要求人工确认，所有 Level > 0 的工具都触发审批。
2. 检查工具的 `riskLevel`。Level 0 直接放行；Level 1 可以设置白天自动放行、夜间/非办公时间要求确认；Level 2/3 默认必须走人工。
3. 检查模型提供的参数是否能证明“它有资格做这件事”。例如 `delete_project` 需要提供当前用户是否为项目 owner，若不匹配，切换到“通知人类并暂停”。

Guard 的伪代码逻辑：

```
if tool.riskLevel >= 2 or (current_mode == "approval" and tool.riskLevel > 0):
    return requestHumanApproval(tool, params)
else:
    return proceed()
```

### 步骤 3：设计不会“堵死”的人工确认流

人工确认可以是同步阻塞，但更推荐**挂起任务并释放 worker**，通过消息通知（Slack/飞书/邮件）把决策权交给指定审批者。关键点：

- **超时自动拒绝**：例如 5 分钟内无响应自动拒绝，并附上拒绝原因“人工未及时确认”。
- **支持“记住这次选择”**：审批者可以在一个上下文范围内（当前 task）批准同一工具多次调用，避免反复弹出相同的确认。
- **批量审批**：如果一个 Agent 任务计划了多个 Level 2 操作，一次审批可以对整个计划生效，而不是打断式的一个一个批。

在 OpenClaw 中可以借助 `task.session` 记录批准过的工具签名与有效期。

## 踩坑点

### 坑 1：工具名称不稳定
模型有时会通过别名或近似名调用工具（如 `delete_project` 写成 `remove_project`），而 Guard 里的白名单匹配不上，结果可能出现“既不审批也不拒绝”的静默放行。解决办法是 Guard 对未识别工具一律降级为 Level 3 并请求确认，日志里记录为“unknown tool”。

### 坑 2：审批疲劳导致“闭眼点通过”
高频 Level 1 操作若总是请求确认，人类很快就会养成无脑点同意的习惯。真正的防线是 **Level 1 自动化 + 异常检测**（如短时间内大量文件删除），而不是让人类去逐条点按钮。

### 坑 3：权限检查缺少角色上下文
Agent 可能在对话前半段以管理员身份执行动作，后期切换到普通用户视图却沿用同一套权限。必须把当前任务的活动角色写入执行上下文，与 Guard 联动。

## 可复用建议

- **把权限策略抽成可配置的 YAML/JSON**：不同环境（开发/生产/演示）切换不同策略，而不是硬编码在 middleware 里。
- **始终保留“强制人工接管”能力**：在任何自动化模式下，给人类一个全局暂停开关；一旦触发，所有 Agent 在下一个工具调用点都会挂起。
- **记录每一次放行决策**：不仅记录“做了什么”，还要记录“为什么无需确认”——方便事后回溯。
- **结合时间窗口和速率限制**：比如夜间 Level 1 操作自动放行但每小时不超过 20 次，超出则临时提升至 Level 2 等待确认。

## 总结

AI Agent 的权限边界不是一张静态的 ACL，而是一套需要持续调优的动态策略。在 OpenClaw 的工程实践中，我们更倾向于用一个轻量的 Guard + 分级工具声明 + 带超时的异步审批流，来代替粗暴的全局开关。这样既能保持自动化效率，又能让人类在真正关键的时刻握紧缰绳——**让 Agent 放手干它该干的，把实在不该干的挡在栏杆后面。**
