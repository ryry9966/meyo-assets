## 背景：memory_recall 为什么总差点意思

现在不少 Agent 都接了长期记忆——对话总结、本地笔记、上次任务的上下文。但“找记忆”这个动作很少被认真聊。典型场景：用户说“把上次那个关于日志采集的 Bug 再分析一遍”，助手需要从几千条记忆里找出真正相关的 3～5 条。

在 OpenClaw 生态里，memory 插件（或 memory MCP server）一般只负责存取，具体怎么召回很大程度上靠工具链自定义。最常见的两条路：

- **语义搜索**（向量检索）：把文本都 embed 成向量存起来，拿 query 的向量去搜。
- **全文搜索**（关键词/倒排索引）：建传统的分词索引，拿 query 分词后匹配。

大多数快速上线的方案直接接一个 embedding + 向量库就完事，但实际跑起来就会发现：“怎么把三个月前的闲聊也拉进来了？”

## 问题拆解：两种搜索的边界在哪

整理一下我们在一个 OpenClaw 内部巡检助手上踩过的典型 case：

| 用户 query | 期望召回的记忆片段 | 语义搜索的问题 | 全文搜索的问题 |
|------------|-------------------|---------------|---------------|
| “容器集群那台节点的 Kernel 版本” | “2024-08-15 日志：node-12 内核升级到 5.15.0-91” | 可能召回其他关于内核讨论的邮件，比如“升级内核注意事项” | 如果用户没记住“node-12”而说成“那台节点”，完全搜不到 |
| “上次部署怎么蓝绿的” | “开发环境蓝绿部署步骤记录（2024-07-22）” | 容易把“灰度发布”“金丝雀”等语义相近的也召回 | 如果记录中写的是“蓝/绿”，可能因为分词断开而丢结果 |
| “账号权限审批流程到哪一步了” | “2024-09 权限审批进度表” | 召回一堆无关的“权限管理讨论” | 如果用户错说成“审批进度”，少了“权限”两个字就可能漏掉 |

结论很明确：语义搜索对模糊表达友好，但容易“想太多”；全文搜索定位精确，但完全靠字面匹配，对自然语言容错很差。只靠一种，Agent 的 memory recall 要么噪音巨大，要么漏得离谱。

## 实践：基于 OpenClaw memory 插件的混合召回

### 环境简述

- OpenClaw 已内置 memory 插件，支持调用 `memory.recall` 工具获取相关记忆。
- 存储层替换为本地 Qdrant（向量 + payload 含原始文本），同时搭建轻量 Meilisearch 做全文索引。
- embedding 模型使用本地的 `bge-small-zh-v1.5`，不过度依赖外部 API。

### 做法步骤

**1. 记忆入库时双写**

每次写入一条新记忆（对话快照、笔记、外部拉取的任务日志），在插件的 save 逻辑中分两步：

- 向量化文本，写入 Qdrant，payload 带上唯一 id、时间戳、来源、原始文本。
- 同时把原始文本推入 Meilisearch，建立字段：id、content、timestamp、tags。

为什么要双写？因为后面混合召回需要两路并行拉取。

**2. recall 实现：多路召回 + RRF 融合**

在 `memory.recall` 工具里，做三件事：

① **语义路**：query embed 后在 Qdrant 取 top_k=20，按相似度阈值 0.7 做一个硬截断，低于阈值的直接丢弃。这一步很重要，不然大量 0.6x 的无关文本会污染候选池。  
② **全文路**：query 分词后交给 Meilisearch，匹配 content 字段，同样取 top_k=20，按 BM25 分数保留。  
③ **融合**：使用 **Reciprocal Rank Fusion (RRF)** 对两路结果加权合并，公式简单：`score = 1/(k + rank_semantic) + 1/(k + rank_fulltext)`，k 取 60。合并后取最终 top_k=5～8 返回给 Agent。

**3. 提供给 Agent 的上下文结构**

从融合结果中抽取原始文本和来源时间，打包成一个结构化的 memory block：
```
memory_block = {
  "query": user_query,
  "results": [
    {"content": "...", "source": "note/2024-08-15", "ts": "2024-08-15T10:30:00Z"}
  ]
}
```
交给大模型时明确提示：“以下是从记忆库中检索到的相关信息，优先使用其中的事实”。

## 踩坑记录

- **语义搜索阈值不好定**。一开始用 0.8 漏掉太多结果，降到 0.7 后噪音略有增加，但配合全文路侧的精确命中，最终效果稳定。建议按业务分档：事实性查询（如版本号、工单号）可开到 0.85，开放式讨论可降到 0.65。
- **中文分词坑**。Meilisearch 默认针对 CJK 用 ngram 分词，会把“蓝绿”切成“蓝”“绿”，导致“蓝绿部署”召回不准。我们后来挂了一个 jieba 分词插件，并把同义词表维护到 Meilisearch 里（“蓝绿” → “蓝绿部署”等同义映射）。否则全文路就是摆设。
- **混合策略的延迟**。双路并行查询 + 融合会比纯语义多大约 30～50ms，但相比于 LLM 的推理延迟完全可忽略。需要注意的是，如果 Meilisearch 是单实例，高并发下可能成为瓶颈，提前做好连接池配置。
- **记忆过时未清理**。时间一长，过期记忆大量堆积，两个索引都变慢。我们加入了一个简单的 TTL 策略：每次 recall 时过滤 30 天前的低交互频度记忆，并定期执行索引瘦身。

## 可复用建议

1. **不要二选一**，工程上永远推荐混合。语义搜解决“大概意思对”，全文搜解决“精确匹配”，RRF 融合几乎没有额外成本。
2. **尽量本地化 embedding 和索引**，避免每次 recall 都走网络，这对 Agent 的端到端耗时非常敏感。尤其是嵌入模型，用 ONNX 推理或 llama.cpp 的 embedding 模式就能跑起来。
3. **给 memory 加标签和时效权重**。入库时打上任务、项目维度标签，融合时可适当提升同标签记忆的分数，效果提升明显。
4. **评估集不可省**。准备 30～50 条典型 query 和对应的 ground truth 记忆，每次调整阈值、权重或分词器后都跑一遍，否则调优全凭感觉。

## 总结

AI 助手的 memory_recall 选哪种搜索，本质不是一个技术倾向问题，而是一个信息检索的基础问题：召回率和精确率必须兼顾。语义搜索和全文搜索很像团队里的通才和专才——单独用都有短板，组合在一起才能扛住真实场景的刁钻提问。基于 OpenClaw 插件 + 双路索引 + RRF 的方案，我们在内部巡检助手上线后，记忆召回准确率从纯语义方案的 0.62 提升到 0.84（评估集 MRR），同时显著减少了“答非所问”的情况。

如果你的 Agent 已经开始用 memory 了，不妨试着跑一下这套混合召回，大概率会发现之前很多奇怪回答的根源就在这里。
