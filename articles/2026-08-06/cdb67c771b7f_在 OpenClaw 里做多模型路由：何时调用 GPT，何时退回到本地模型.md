# 在 OpenClaw 里做多模型路由：何时调用 GPT，何时退回到本地模型

## 背景

OpenClaw 的自动化管线会在一个执行上下文中串联多个 Agent、MCP 工具和插件。每个节点都可能发起模型调用：归纳网页、生成 SQL、提取实体、意图分类…… 如果所有请求都走 GPT-4，月末账单会让你怀疑人生；如果无脑用本地部署的 Llama 3 或 Qwen，一些复杂推理或严格格式输出的任务又会频繁失败。

我们在生产里跑了一段时间多模型路由，整理出一套决策框架：不是“哪个便宜用哪个”，而是根据**任务结构、数据边界、失败成本**动态切换模型。这套规则直接实现在 OpenClaw 的 Triage Agent 里，配合模型优先级表和 fallback 链，把 GPT-4 的调用量压到了原来的 30%，同时任务失败率没有上升。

## 问题拆解

决定模型不应该是拍脑袋的。路由出错时，你面临的不只是多花几分钱：

1. **结构化输出不稳定**：本地 7B 模型在 JSON 补全上偶尔会多一个逗号，下游解析崩溃，整个工作流重跑。
2. **上下文超长截断**：本地模型原生 8k 窗口，长文档摘要时直接丢信息，你得提前切 chunk，但切分策略本身也是一个决策。
3. **数据隐私与合规**：含有 PII 的原始日志不能离开内网，这时即便 GPT-4 效果再好也必须用本地模型或脱敏后再传。
4. **延迟约束**：同步给前端返回结果的场景要求 <500ms，本地模型可能内存不足导致 2s+，反而 API 更稳定。

所以模型路由需要量化这些维度，而不是依赖“感觉”。

## 做法与步骤

我们在 OpenClaw 的配置里定义了一张 **Model Capability Table**，加载到 Triage Agent 的系统提示里。Triage Agent 会在每个子任务执行前依据几个信号决策。

**1. 建立模型能力表（示例片段）**
- `gpt-4o-mini`：高结构化输出可靠性，128k 上下文，低成本，可处理部分 PII（需合规确认），平均延迟 600ms。
- `gpt-4`：最高推理质量，工具调用准确率高，中等延迟，成本高。
- `llama3-70b-instruct`：推理接近 GPT-3.5，8k 上下文，本地部署，零外部传输，延迟 400ms（预热后）。
- `qwen2-7b`：轻量解析、分类任务，延迟 <100ms（TGI 加速），但 JSON 格式偶尔出错，窗口 32k。

这张表就是路由的“菜单”。

**2. 定义路由决策流（实现在 Triage Agent）**
在 OpenClaw 的 `agent_config.yml` 中，我们设置了一个 `model_router_prompt`，强制 Triage Agent 按步骤输出决策理由和选定的模型 ID：

```
你是一个模型路由专家。请按以下步骤决策：
1. 检查任务输入是否包含个人信息（姓名、电话、地址、密钥等）？如有，优先本地模型。
2. 任务是否要求严格 JSON/XPath/正则输出？如是，优先 gpt-4o-mini 或 gpt-4。
3. 输入 token 数是否大于 8000？如是，仅选择支持长上下文的模型。
4. 返回时间是否要求 <500ms？结合负载选择低延迟模型。
5. 其他情况下，对简单分类/摘要使用本地 7B 模型，对复杂推理使用 gpt-4o-mini。
最终输出：“模型: <model_id>”，不接受额外解释。
```

在这个 prompt 约束下，Triage Agent 给出的结果可以被后续的 `model_executor` 插件直接消费，避免二阶段调用。

**3. 配置 fallback 链**
不要寄希望于一次路由就正确。OpenClaw 允许给每个模型配置 fallback：

```yaml
model_fallback:
  llama3-70b-instruct: [qwen2-7b, gpt-4o-mini]
  gpt-4o-mini: [gpt-4]
```

当返回解析失败（如 JSON decode error）或超时，执行器自动尝试下一个模型。这套机制拯救过无数次深夜报警——一次本地模型幻觉导致 JSON 多了个尾逗号，自动 fallback 到 mini 修复，整个 pipeline 不必重试。

## 踩坑点

**坑1：把路由逻辑写死在代码里**
早期我们把规则硬编码成 if-else，结果每新增一个模型就要改动执行器代码，部署、测试成本高。改成 Triage Agent 动态决策后，只需要更新 capability table 的文本描述，模型列表和 fallback 链通过配置热加载完成。

**坑2：本地模型加载延迟没做缓存**
第一次调用本地模型时，需要加载模型权重，耗时可能 3~5 秒，导致整个任务超时。需要让 OpenClaw 的 `model_server` 维持常驻进程，或者至少用 warmed-up 的推理端点，路由决策应感知到模型状态，不要将“冷模型”分配给延迟敏感任务。

**坑3：上下文截断导致的静默失败**
本地模型遇到长度超出窗口时，很多实现不会报错，只是悄然丢弃中间部分。结果摘要看似正确，实则丢失了关键数据。应对方法：在路由时强制计算 token 长度，超出则立刻改用长窗口模型，或提示切分，不能让模型自行截断。

**坑4：忘记对 fallback 结果做一致性校验**
简单的 JSON 解析成功不代表输出正确。一次 fallback 到 GPT-4 后，输出的格式与本地模型不同，导致下游节点参数名不匹配。解决方法是将所有模型输出先经过一个规范化的映射层（我们用的是 OpenClaw 的 `output_adapter`），确保字段一致。

## 可复用建议

- **卡点建模，而非猜测**：用一周时间记录每个任务的真实 token 数、延迟、准确率，再设定切换阈值。
- **把能力表当作代码一样维护**：每次模型升级（如 Llama 3.1 发布）都要更新 capability table，并在测试集中回归。
- **用成本标签反向审计**：在 OpenClaw 的 trace 里给每步模型调用打上成本标签，每周拉一次报表，如果发现大量简单分类任务走到了 GPT-4，返查路由规则是否失效。
- **脱敏优先于模型选择**：在数据流入模型前做 PII 过滤，而不是完全依赖本地模型来兜底隐私，这样路由决策空间更大。

## 总结

多模型路由本质上是一个“决策成本 vs 失败成本”的优化问题。OpenClaw 让我们可以把决策嵌入 Agent 的推理流程中，通过能力表、受限输出和 fallback 链，优雅地在 GPT 和本地模型之间切换。核心原则是：让最便宜的模型处理确定性高、边界清晰的任务，而为复杂推理和高压场景保留最强的模型。同时永远要有 fallback，因为模型的不确定性是常态。
