## 背景
在 OpenClaw 这类 Agent 框架中，模型通过 MCP、插件或自定义工具直接操作文件系统、调用 API、执行 Shell 命令。Agent 愈发自主带来的风险也很直接：一条错误的 `rm -rf`、一次无确认的数据清空、一条发往错误对象的敏感消息，都可能造成不可逆的影响。  
与此同时，完全依赖人工确认又会让 Agent 失去效率优势，让自动化流退回到“每一步都得点一下”的原始状态。于是，**当 Agent 面对一个操作时，什么时候该自己干，什么时候必须找人类确认**，成了实际落地中绕不开的问题。

## 问题定义
权限边界的核心矛盾是：自主性与安全性冲突。我们希望 Agent 能处理大量低风险重复工作，但对高风险动作必须保持人控。问题拆解开包括：
- 如何对操作进行风险分级？
- 如何让 Agent 在决策时感知到风险级别？
- 确认环节如何嵌入流程，又怎么保证上下文不丢失？
- 如何在配置层面灵活调整策略，而非硬编码进 prompt？

下面基于 OpenClaw + MCP 插件的实践，给出一种可复用的方案。

## 方案设计
将权限控制分成三层：
1. **操作分级**：把工具（或工具里的具体 action）划分为低 / 中 / 高三个风险等级。  
   - 低风险：只读查询、获取状态、列出资源。  
   - 中风险：写入非关键配置、触发无害通知、创建临时资源。  
   - 高风险：删除数据、执行宿主机命令、修改权限、发送付款指令。  
2. **策略引擎**：在 Agent 运行时注入一条动态策略，低风险自动执行，中风险在会话内首次出现时确认（可记忆一段时间），高风险每次都必须确认。  
3. **人机交互通道**：通过 MCP 的 `requires_approval` 字段或专门的 `human_confirmation` 工具暂停 Agent 流程，将操作摘要、风险提示、回退选项推给用户，得到明确许可后才继续。

这个分层方案的重点是把“风险判断”从模型认知中剥离出来，放到可配置的策略层，避免模型被越狱或误解指令直接调用高危工具。

## 实践步骤
### 1. 在工具定义中标记风险等级
如果你使用 MCP 服务器，可以在工具返回的 `description` 或自定义元数据中加上 `risk: low|medium|high`。例如在 Python MCP 服务中：
```python
@server.tool("delete_database", risk="high")
async def delete_database(...)
```
客户端（也就是 Agent 运行环境）读取这些标记。

### 2. 配置策略规则
在 OpenClaw 的 Agent 配置文件中声明策略，避免散落在 prompt 里：
```yaml
permissions:
  risk_levels:
    low: auto
    medium: confirm_once_per_session
    high: confirm_always
  cooldown: 300  # 同一 medium 操作 5 分钟内不再重复确认
  timeout: 60    # 确认超时后自动拒绝并告警
```

### 3. 实现确认流程
Agent 遇到需要确认的操作时，调用一个专门的 `confirm_action` 工具，该工具将操作详情推送到消息通道（如 OpenClaw 内置通知或外部 IM），暂停执行并等待用户回复 `approve` 或 `deny`。用户回复后，Agent 携带原始 `action_id` 继续执行，避免重新推理上下文。

关键点：确认时应当携带足够的上下文（什么操作、影响范围、风险等级、建议），让人类在几秒内做出判断，而不是丢回一大段 prompt。

### 4. 处理边界情况
- 如果用户长时间不响应，按策略 `timeout` 自动拒绝，并记录审计日志。  
- 对于批量操作，可批量确认（如“允许这 10 个只读查询”），减少打扰。  
- 在调试/沙盒环境中，允许临时将风险等级全部降为 `auto`，但必须限制在隔离环境。

## 踩坑记录
- **频繁确认导致疲劳**：一开始我们把所有写操作都设为 medium，结果用户每做一步就要点一次。后来改用“会话内首次确认”并加入冷却，大幅改善体验。  
- **模型绕过确认**：如果仅靠 prompt 约束，Agent 可能被诱导直接调用工具而不走确认流程。必须把权限检查放在工具调用层或 MCP 协议层，而非只靠语言指令。  
- **确认上下文丢失**：确认返回后，Agent 可能重新规划，产生不一致。解决方法是把已确认的 `action_id` 和参数冻结，通过插件状态回传，而不是重新生成。  
- **高风险操作定义不足**：运维场景中 `restart_service` 看起来常规，但在生产环境风险极高。需要结合部署环境动态调整分级，不能一刀切。

## 可复用建议
1. **策略与代码解耦**：将权限配置外置为 YAML/JSON，便于不同环境（dev/staging/prod）使用不同规则。  
2. **审计先行**：所有被拒绝或超时的操作都要完整记录，方便事后分析是策略过严还是模型越权。  
3. **分级确认的可组合性**：可以在会话级别、工具级别、参数级别设置不同的确认要求，例如“查询列表自动，查询详情自动，导出名单确认”。  
4. **为用户提供快捷决策**：在确认消息中带上“信任此会话”“总是允许此类操作”的选项，但必须明确告知风险，防止用户习惯性点同意。  
5. **与沙盒联动**：对于不确定是否危险的操作（如用户自定义脚本），先在隔离沙箱中执行，观察副作用，再决定是否放行。

## 总结
AI Agent 的权限边界不是一刀切的开关，而是一套需要结合风险分级、动态策略和人机协作的工程体系。在 OpenClaw 和 MCP 工具链里，利用元数据标记、独立的策略引擎和轻量的确认通道，我们可以在自主执行与安全可控之间找到平衡。**原则很清晰：Agent 负责干事，人类负责在关键节点签字，策略负责让“签字”这件事不反人性。** 随着 Agent 接入更多生产系统，这套边界设计会成为基础设施的一部分，越早工程化，越能避免灾难性的“自主失控”。
