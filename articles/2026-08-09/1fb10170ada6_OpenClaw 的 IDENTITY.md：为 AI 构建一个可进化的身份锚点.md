## 为什么需要一份“活的”身份文件

在 OpenClaw 的默认工作流里，Agent 的“人格”通常来自系统提示词或环境变量。这种方式在小规模、单次会话下够用，一旦 Agent 开始长期运行、跨会话合作，或者需要通过 MCP 调用外部工具，这种静态身份就会出现明显局限：

- **跨会话遗忘**：每次重启都是“新大脑”，不具备从过往交互中调整行为的能力。
- **提示词膨胀**：想把所有偏好塞进 system prompt，结果 token 消耗爆炸，响应质量反而下降。
- **多 Agent 协作时角色模糊**：没有一份统一、可追溯的身份定义，不同 Agent 之间容易行为漂移。

IDENTITY.md 是 OpenClaw 为了解决上述问题提供的一种文件级身份机制。它不只是一个静态角色描述，更像是一份可被 Agent 自身阅读、更新和演化的“元人格”文档。你可以把它理解成代码仓库里的 README，但读者是 AI 自己。

## 不是写一个角色卡，而是定义进化规则

如果只是写“你是一个后端工程师，喜欢用 Rust”，那和写一段 system prompt 没区别。IDENTITY.md 的核心价值在于让身份“可进化”——Agent 在交互中能将关键反馈、偏好修正、新学到的约束写入这份文件，让下一次会话继承改进后的行为。

一个工程上可用的 IDENTITY.md 通常包含三层结构：

1. **核心人格与目标**：角色、沟通风格、硬性约束（永远不做什么）。
2. **领域知识与工具体系**：Agent 主要处理的领域、可调用的 MCP 工具集、对输出格式的要求。
3. **进化指令**：明确告诉 Agent 什么情况下应该更新这份文件、更新哪些部分、以何种格式追加记忆。

### 示例：一份极简但可进化的 IDENTITY.md

```markdown
# IDENTITY: DevOps 助手

## 核心人格
- 沟通风格：直接、给出命令示例、不做长篇解释
- 硬约束：绝不修改生产环境配置，除非在拟定的 dry-run 模式中

## 工具与领域
- 常用 MCP 工具：git, docker, aws-cli-readonly
- 输出格式：优先给出一键可执行的脚本，注释说明风险

## 进化规则
- 当用户纠正某个操作流程时，将纠偏总结追加到 `MEMORY.md`
- 每次会话结束，自动检查 `MEMORY.md` 中是否有新条目需要合并到此处
- 若行为与核心人格冲突，优先遵从硬约束
```

这里的关键是“进化规则”部分的工程化表述。如果不写清楚什么时候触发更新、写到哪、怎么合并，Agent 要么从不更新身份，要么乱写一通导致行为失控。

## 配合 MEMORY.md 实现“渐进式记忆”

IDENTITY.md 负责稳定、长期的人设锚点；动态的短期记忆、纠偏细节更适合放入 MEMORY.md。OpenClaw 的设计里，Agent 在每次响应前会同时读取这两个文件，确保既稳定又可微调。

可复用的工作流如下：

1. 在项目根目录创建 `IDENTITY.md`，写入上述三层内容。
2. 在同目录创建空白的 `MEMORY.md`，并在 IDENTITY.md 的进化规则中指明“将临时偏好、一次性纠偏写入 MEMORY.md”。
3. 使用 OpenClaw 内置的**对话摘要器**（通常是一个轻量级 LM）在每段对话结束时，自动提取关键决策和用户对输出的修正，以统一格式追加到 MEMORY.md 顶部。
4. 定期（例如每 10 次会话）让 Agent 自己比较 IDENTITY.md 和 MEMORY.md，将反复出现的偏好提升写入 IDENTITY.md，并清理 MEMORY.md 中的冗余条目。

这样做的好处是，IDENTITY.md 始终保持精简，不会因为记忆膨胀而稀释核心约束；同时 Agent 又能“记住”你的习惯变化。

## 踩坑记录与排障

### 坑 1：身份漂移
让 Agent 随意修改 IDENTITY.md 是危险的。如果进化规则写得过于宽松，Agent 可能在连续对话中把某个临时偏好当成永久特性，甚至覆盖核心硬约束。

**解法**：为 IDENTITY.md 设置版本控制和人工审核节点。可以将进化规则限制为“只允许追加经用户确认的新约束到进化规则区块，不得删除或修改核心人格部分”。实际落地时，我会用 git 对 IDENTITY.md 做版本管理，每次 Agent 修改后自动提交，人工在合并回 main 分支前 review diff。

### 坑 2：记忆膨胀导致幻觉
当 MEMORY.md 积累过多条目时，Agent 可能过度偏向早期记忆，或无法有效提取相关信息，反而把旧偏好当成当前要求。

**解法**：设定记忆裁剪策略。例如只保留最近 20 条记忆，或要求每条记忆附上时间戳，Agent 读取时优先加权近期条目。也可以在进化规则中写明：“若 MEMORY.md 条目超过 30 条，在下次会话开始前自动压缩为 10 条摘要。”

### 坑 3：多 Agent 共享身份冲突
如果多个 Agent 实例共用一套 IDENTITY.md，交互中可能产生互相矛盾的更新。比如一个 Agent 认为应当更激进地使用缓存，另一个则在会话中被要求保守查询。

**解法**：为不同 Agent 按角色拆分 IDENTITY 文件，如 `IDENTITY-planner.md` 和 `IDENTITY-executor.md`，共用一份核心规范，但允许各自的进化路径。也可以在 MEMORY.md 中加入 Agent 标识，明确记忆来源以避免混淆。

## 可复用建议

- **将身份文件当成代码管理**：IDENTITY.md 与源代码一起上 git，利用 PR 机制审查 AI 的自我修改，避免行为退化。
- **明确进化边界**：在进化规则中声明“可修改域”（如沟通风格的细节、常用工具优先级）和“冻结域”（核心伦理、安全约束）。
- **结合 MCP 工具做外部记忆检索**：当记忆量较大时，可以让 Agent 调用向量数据库 MCP 工具，将 MEMORY.md 段落向量化存储，按语义检索而非线性读取，这对于长期项目特别有用。
- **定期“遗忘”测试**：每隔一段时间，让 Agent 用一个干净环境（临时屏蔽 MEMORY.md）运行，检查 IDENTITY.md 本身是否已经保留了足够好的行为基线。如果行为明显退化，说明核心人格部分需要强化，而不是依赖记忆补偿。

## 总结

IDENTITY.md 的精髓不是写一个好提示词，而是为 AI 设计一套可安全自我迭代的“身份协议”。在 OpenClaw 的生态里，它配合 MEMORY.md、对话摘要器和 MCP 工具链，能让 Agent 从一次性助手平滑过渡到能随项目长期成长的协作者。重要的是带着“工程约束”的思维去设计进化规则——控制边界、保留人工审查点、善用版本控制。你给 AI 的不仅仅是身份，更是一个安全进化的框架。
