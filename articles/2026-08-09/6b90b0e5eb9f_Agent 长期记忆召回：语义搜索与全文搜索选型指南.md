## 背景：memory_recall 的现实需求

在 OpenClaw 这类可扩展 Agent 框架中，memory 插件常被用来存储用户偏好、历史事实或工作流上下文。当 Agent 需要根据自然语言查询回忆相关记忆时，`memory_recall` 就成了关键一环。其本质就是一个小型信息检索任务：给定一句自然语言描述，从记忆库中返回最相关的若干条记录。

目前实现 recall 的主流方向可分为两类：

- **全文搜索（Full-Text Search）**：基于词频统计的 BM25 或其变体，依赖倒排索引，常见方案为 SQLite FTS5、Elasticsearch 或 Meilisearch。
- **语义搜索（Semantic Search）**：基于 Embedding 向量的余弦相似度检索，通常用 Transformer 模型将文本转为稠密向量，然后借助向量索引（如 FAISS、Chroma、pgvector）进行近似最近邻搜索。

两者各有优劣，直接套用任何一方都可能在生产环境翻车。本文结合在 OpenClaw 插件开发中的实践经验，给出一些可复用的选型思路与排坑记录。

## 问题界定：你的记忆“重查词”还是“重语义”？

在动手之前，先明确你的 `memory_recall` 最常面对哪种查询：

**场景 A：指令性或实体明确的记忆**
- 查询如“上次用的 AWS 账号是哪个？”“把 OpenClaw 的日志输出改成 debug 模式”
- 这类查询中，关键词高度精准，用户期望重现相同的短文本片段
- 全文搜索的精确匹配优势明显

**场景 B：意图模糊、跨表述连贯回忆**
- 查询如“之前讨论过怎么处理超时重试的方案”“关于部署安全那次提的问题”
- 用户用不同词表达相同概念，依赖语义相似性来召回记忆
- 语义搜索更能弥补词汇鸿沟

很多实际部署的 Agent 同时面对这两种场景，单靠一种搜索很难同时满足。

## 实践做法：搭建可切换的 recall 层

为避免过早优化，可以采用抽象接口实现可插拔的搜索后端。下面是一个在 OpenClaw 插件 context 中的最小可行方案：

1. **存储层标准化**：记忆条目统一保存 `id`、`content`（原始文本）、`metadata`（时间戳、标签等）。若准备做语义搜索，同时预计算并存储 `embedding` 向量。
2. **全文后端**——SQLite FTS5：
   - 建表时启用 `CREATE VIRTUAL TABLE mem_fts USING fts5(content, ...)`。
   - 召回查询使用 `SELECT *, bm25(mem_fts) AS score FROM mem_fts WHERE mem_fts MATCH ? ORDER BY score LIMIT ?`。
   - 优点：零额外依赖，轻量级，支持布尔查询，离线可用。
3. **语义后端**——本地 Embedding + 向量检索：
   - 选用轻量 sentence-transformers 模型（例如 `all-MiniLM-L6-v2`），在插入/更新记忆时计算向量，存入内存 FAISS 索引或 Chroma。
   - 查询时编码输入得到 query_vec，直接从索引中取 top_k。
   - 优点：理解同义改写，查询与文档词缀不匹配时仍能命中。
4. **混合策略**（推荐长时间运行的生产环境）：
   - 同时从 FTS5 和向量索引取 top_k 候选（如各 10 条）。
   - 使用倒数排名融合（RRF）或轻量级 cross-encoder 重排序（例如 `cross-encoder/ms-marco-MiniLM-L-6-v2`）合并结果。
   - 输出最终排序列表。

## 踩坑与排障

- **全文搜索的中文分词陷阱**：SQLite FTS5 默认 tokenizer 对中文分词效果很差，需要启用 ICU tokenizer 或替换为 jieba 分词等自定义 tokenizer。如果记忆库混合中英文，需分别测试 MATCH 查询在分词后的召回率，否则会大量漏召回。
- **语义搜索阈值难定**：向量余弦相似度没有绝对的好/坏界限，0.7 在某些模型上是强相关，换模型可能已是噪声。建议针对你的业务记忆库，标记一批 (query, 正负例) 数据做阈值校准，或者直接用 rerank 模型取代硬阈值。
- **Embedding 模型冷启动**：本地加载模型增加首次启动延迟和内存占用。若 Agent 运行在边缘设备上，需要做模型量化（ONNX 导出或 int8 量化）并考虑异步预热。
- **向量索引更新成本**：记忆频繁增删时，FAISS 全量重建索引会比较耗时。可以考虑增量方案（如使用可追加的索引结构或定期合并），但会增加复杂度。
- **混合搜索的延迟**：同时调用两个后端会增加显式延迟。实践中可以先并行请求，用 asyncio.gather 聚合结果，总体 P95 延迟可控制在 100ms 内。

## 可复用建议

1. **从全文搜索起步**：如果记忆规模小于 1 万条且查询以实体为主，直接使用 SQLite FTS5 即可，无需引入向量模型。
2. **需要语义理解时，先做离线评测**：用典型查询验证语义搜索相比全文搜索的 recall@K 提升幅度，决定是否值得引入额外复杂性和资源。
3. **混合搜索不能省略重排序**：单纯合并 BM25 分数和余弦相似度分数都会遇到量纲不统一问题，RRF 是最低成本且无参数的融合方法，cross-encoder 精度更高但更慢，适合最终精排阶段。
4. **监控召回质量**：在 Agent 内部埋点，记录每次 `memory_recall` 返回的 top1 是否被用户采纳或被改写，逐步积累判断数据集，用于迭代搜索策略。
5. **注意隐私与持久化**：记忆记录可能包含敏感信息。如果使用外部向量数据库，确保传输和存储加密；如果使用本地 Embedding 模型，检查其数据使用协议。

## 总结

在 Agent 的长期记忆实现里，没有一种搜索方式是银弹。全文搜索精确、可解释、资源消耗低，适合以关键词为核心的重查场景；语义搜索灵活、容错性强，适合含义模糊的回忆需求。工程上务实的路线是：

- 轻量级场景：仅用 SQLite FTS5 全文搜索，配置好中文分词。
- 一般场景：全文搜索 + 向量检索并行召回，RRF 融合。
- 高精度场景：在混合召回基础上追加 cross-encoder 重排序。

最终，记忆搜索质量不仅取决于算法，更取决于你是否为业务设计了合理的记忆组织结构和持续的质量反馈闭环。
