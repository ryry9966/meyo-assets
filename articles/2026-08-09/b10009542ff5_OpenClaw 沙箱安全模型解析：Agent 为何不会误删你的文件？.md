## 背景：Agent 有了“写”的权限，就一定危险吗？

随着 MCP、插件、自动化链路的成熟，Agent 不再只是“动嘴”的聊天机器人——它们可以写代码、改配置、管理项目文件。这带来一个核心的工程化顾虑：**万一 Agent 理解错了意图，把重要文件删了怎么办？**

过去不少工具的做法是“全有或全无”：要么完全禁止 Agent 操作文件，要么给它等同于用户进程的全部权限。前者限制了实用性，后者相当于把 `rm -rf` 的发射按钮交了出去。

OpenClaw 的沙箱模型试图在两者之间找到工程化可行的地带。它不是单纯在 Agent 外面套一层容器，而是从文件系统访问层开始就把“安全边界”做成了可配置的、可审计的。

## 问题拆解：一个“删除”操作到底要经过多少层检查？

先抛开营销话术，直接从一次文件删除请求的链路来看安全模型是如何工作的。

Agent 发出类似 `delete_file(path="/user/projects/config.yaml")` 的指令后，并不是直接调用系统调用 `unlink`。在 OpenClaw 的架构中，文件操作会经过 **FSAL（文件系统抽象层）**，这一层再做下面几个关键动作：

1. **路径规范化（Path Normalization）**  
   `..`、软链接、多余斜杠会被解析成绝对规范路径。如果 Agent 试图通过 `../../etc/passwd` 遍历到工作区外，规范化后会被识别出越界。

2. **工作区边界校验（Workspace Boundary Check）**  
   OpenClaw 只信任你在启动时指定的 `workspace` 目录（以及你显式添加的白名单路径）。任何超出白名单的路径在“写/删”阶段直接拒绝，并且把这次越权尝试记录到审计日志。

3. **操作意图确认（Confirmation Hook）**  
   在生产环境配置中，你可以要求所有删除操作触发**显式用户确认**。这一步是可选的，但对于直接操作重要目录的场景，多一道人审查能拦截大部分意外。

4. **回收站策略（Trash Policy）**  
   即使检查全部通过，默认配置下“删除”并不会立刻 `unlink`。文件会先被移动到工作区内的一个隐藏回收站目录（如 `.openclaw_trash/`），并保留元数据（原路径、时间戳）。你可以在会话结束前恢复，或者设置保留时效自动清理。

5. **事务性回滚（可选）**  
   对多条文件操作组成的步骤，OpenClaw 支持“预执行-后确认”的模式。Agent 在一个临时 snapshot 中修改文件，只有当你检查 diff 并批准后，修改才会应用到真实工作区。若 diff 里包含了意外的删除行，你可以直接拒绝整个事务。

这一连串机制，使得“一句话误删全部代码”在 OpenClaw 的默认配置下几乎不可能发生。

## 实际配置：怎么做才能既安全又不卡住正常任务？

下面给出一个工程中可复现的配置示例（以 sandbox 配置文件为例）：

```yaml
sandbox:
  workspace: "/home/user/projects/my-agent-workspace"
  allowed_read_paths:
    - "/usr/share/dict"       # 只读访问字典文件
  allowed_write_paths:
    - "/tmp/agent-output"
  delete_mode: trash_first    # 可选 direct, trash_first, confirm
  require_confirmation_for:
    - delete
    - overwrite
  trash_retention_days: 3
  enable_transactional_staging: true
```

解释一下踩坑相关的点：

- **workspace 不要设成 `~` 或 `/`**  
  那是把边界搞没了。如果 Agent 只需要处理某个项目，就给它该项目根目录下的一个独立子目录，例如 `~/project/.agent-workspace`。
- **白名单里不要放`.ssh`、`.gnupg`等敏感目录**  
  哪怕只是只读，Agent 的插件万一有内在风险，也不应该让它能读到私钥。
- **`delete_mode: direct` 只适合测试**  
  一旦接入真实文件，就应当用 `trash_first` 或 `confirm`。

## 踩坑记录：这些地方最容易让人放松警惕

1. **符号链接骗过路径检查**  
   如果你在 workspace 内创建了一个指向 `/etc` 的符号链接，旧版本或配置不当时可能被追踪后命中真实系统路径。  
   解决：确保启用了 `symlink_resolution: strict`，所有符号链接解析后必须仍然落在白名单内。

2. **Agent 用 `mv` 代替 `delete`**  
   某些 Agent 倾向于用 `mv file /dev/null` 或 `rm -rf` 等 shell 命令，而不是调用 FSAL 的 delete 接口。如果允许 Agent 直接执行系统命令（比如给了 bash 工具），沙箱的删除保护就可能被绕过。  
   建议：限制 Agent 只能使用声明式文件操作工具，而不是直接裸用 shell。

3. **回收站的体积膨胀**  
   Trash 目录如果不定期清理，可能占满磁盘。  
   建议：设置合理的 `trash_retention_days`，并配置监控，在存储快满时触发告警。

4. **事务 staging 和实时性冲突**  
   如果场景要求实时修改（如日志分流），开启事务预执行会导致延迟。此时可以只对写-删操作开启确认，而对读取不限制。

## 可复用建议

- **最小化原则优先**  
  哪怕沙箱本身已经安全，也不要一次给足所有权限。按任务按需授权。
- **先干后看**  
  开启 `diff-review` 功能，让 Agent 在一个隔离的 staging 里完成修改，人工审查后再 apply。这相当于给文件系统加了“代码审查”环节。
- **审计不是摆设**  
  关注 FSAL 日志中 `ACCESS_DENIED` 的记录，它能告诉你 Agent 到底想触碰哪些它没权限的文件，帮你在优化白名单或发现异常行为时做决策。

## 总结

OpenClaw 的沙箱安全模型并不依赖单一魔法，而是用**路径边界、确认链、回收站、事务隔离**这些工程上可组合的手段堆叠出的防护。它不能百分之百杜绝误删——任何安全模型在配置不当或绕过工具直接运行系统命令时都可能失效——但它在默认路径下已经把意外删除的风险降到了极低水平。

最终，安全是“机制 + 配置习惯”共同的结果。把沙箱配置写进项目的自动化检查里，像对待 CI 流水线一样审视你的 Agent 权限，才能真正让 Agent 变成一个放心的协作者，而不是一颗携带 `rm -rf` 的定时炸弹。
