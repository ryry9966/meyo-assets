## 背景

在基于 OpenClaw 构建 Agent 的过程中，长期记忆的可用性直接决定助手能否“记住该记的东西”。多数实践者会封装一个 `memory_recall` 工具，让模型在每次对话或任务执行时主动检索历史记忆，再拼入上下文。检索质量的上限，往往就是 Agent 表现的上限。

这个工具的核心是一对矛盾：你希望召回与当前意图“相关”的内容，而不是“字符串匹配”的内容；但你又无法接受语义检索在边界条件上的不确定性——关键字明明就在那里，结果却没出来。

这就引出一个绕不开的问题：`memory_recall` 的检索层到底该用**语义搜索**（embeddings）还是**全文搜索**（BM25 等），还是两者兼而有之？

## 问题拆解

先看两类搜索在实际记忆场景中的典型行为。

**全文搜索**（以 BM25 为例）：
- 对实体名、日期、代码片段、特定术语召回非常精准。
- 不依赖外部模型，延迟低且可复现。
- 缺点很明显：换一种说法、同义词、跨语言表达几乎打不出结果。比如记过“模型响应时延要求 ≤200ms”，检索“延迟要求”时可能直接漏掉。

**语义搜索**（基于 embedding）：
- 可以跨表述捕获意图，比如“上游超时”和“调用方 5 秒没收到响应”能关联上。
- 长文本、模糊描述的场景下优势明显。
- 缺点：对专有名词不敏感、阈值难调、同等算力下 QPS 更低；embedding 模型选错，整个检索直接跑偏。

在 OpenClaw 插件环境下，`memory_recall` 通常是 MCP 工具或本地 Function，它要解决的问题既有“找上次调试时那个奇怪的报错日志”，也有“上次我们聊过的延迟优化方案具体是什么”。这天然就是全文 + 语义各自的优势区。

## 做法与步骤

我在实际搭建 `memory_recall` 时，最终走向了**混合检索 + 重排序**，而非二选一。具体链路如下：

### 1. 存储侧同时建立两种索引
- 全文索引：使用本地 SQLite FTS5 或者 Elasticsearch（多实例场景），对记忆的 `content` 字段建倒排索引。
- 语义索引：使用本地 embedding 服务（如 text2vec-base-multilingual）将同一条记忆编码为 768 维向量，存入 Qdrant 或 Chroma。

每条记忆写入时，一步完成双索引入库。为了保证一致性，写入事务先写全文索引，再写向量 DB，失败则整体回滚。

### 2. 召回阶段并发执行
`memory_recall` 工具被调用时，同时执行：
- 全文检索：提取 query 原始字符串，用 BM25 取 Top-50。
- 语义检索：用同一 embedding 模型向量化 query，取相似度 >0.7 的 Top-50。

两路结果一起送入后续重排。

### 3. 重排序与融合
直接简单合并会引入很多噪声。我采用 **RRF（Reciprocal Rank Fusion）** 算法对两路结果做初步融合，再用一个轻量级的 Cross-Encoder 模型（如 `uer/sbert-base-chinese-msmarco` 的蒸馏版）对 Top-30 候选做精细打分排序，最后截断 Top-10 作为最终输出。

这一步的工程细节：
- RRF 的 k 值设为 60，经验值，偏向保留两路都能召回的结果。
- Cross-Encoder 仅在候选 >20 时才触发，否则直接用 RRF 结果，以控制延迟。

### 4. 接入 OpenClaw 工具
插件内暴露一个 `recall_memory` 函数，参数包括 `query`、`top_k` 和 `recency_weight`（可衰减旧的记忆）。返回结构化的记忆片段列表，模型可直接拼入 system prompt 或 user message。

## 踩坑点

1. **embedding 模型的选型不匹配领域**
   早期直接用了通用英文模型，中文专有名词召回极差。后切换到多语言模型并做领域微调，效果才稳定。如果没有微调条件，强烈建议先用 BM25 作为 baseline，再叠加语义检索，不要一上来就全量语义。

2. **阈值设定忽视上下文长度**
   语义相似度阈值 0.7 在小记忆库够用，但记忆膨胀到 10 万条后，Top-50 里混入大量“一般相关”却被误认为是高相关的内容。解决方案是结合记忆的时间衰减和记忆类型（日志、决策、知识）做预过滤，再设定动态阈值。

3. **全文索引的内存碎片**
   SQLite FTS5 在频繁更新时会出现碎片化，导致查询性能波动。通过定期 `optimize` 和限制记忆单条长度（8KB 以下）来缓解。

4. **混合排序的可复现性**
   不同请求之间，语义模型的得分分布可能不同（batch 效应），导致 RRF 融合后排序不稳定。通过在 Cross-Encoder 前做得分归一化（min-max）解决。

## 可复用建议

- **从全文检索起步**：如果你的记忆条目不超过 5000 条，且查询偏向关键词，不要过度设计。一条好的 BM25 基线能解决 80% 的问题。
- **混合检索优先于纯语义**：语义检索的正确使用方式是作为全文检索的补充，而不是替代。即使谷歌搜索也并没有抛弃词法匹配。
- **关注写入路径的开销**：双索引意味着写入延迟翻倍。如果记忆写入频繁，考虑异步队列写入，并接受最终一致性。
- **为记忆设计过期和衰减**：召回结果不仅要看相关度，还要看时间。把记忆的`created_at`和`last_accessed`融入排序因子，效果提升显著。
- **评估一定要用真实查询日志**：不要仅用人工构造的测试集评估，用线上真实 query 做标注回放，才能发现“表面匹配但语义无关”的长尾 case。

## 总结

`memory_recall` 的检索选择不是算法问题，而是场景适配问题。全文搜索给你确定性和可控性，语义搜索给你抽象和泛化能力。工程上的最优解几乎永远是混合检索加上领域适配的重排序。与其陷入选型争论，不如花时间搭建一套可以快速对比的评估流水线——在一个小规模但真实的数据集上跑基准，让数据替你说话。
