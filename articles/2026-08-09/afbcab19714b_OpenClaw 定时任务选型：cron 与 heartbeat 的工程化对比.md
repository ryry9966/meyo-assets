# OpenClaw 定时任务选型：cron 与 heartbeat 的工程化对比

## 背景：为什么定时触发是 Agent 自动化的基石

在 OpenClaw 的插件、MCP 与自动化实践中，几乎所有“无人值守”能力都依赖定时任务去驱动——例如定时抓取外部数据喂给 Agent、周期巡检服务健康状态、定时触发清理流水线。OpenClaw 的任务调度模块提供了两种最常用的定时策略：**cron 表达式**和**heartbeat（间隔触发）**。但实际落地时，很多配置错误都源于对这两种模式理解不透彻：选了 cron 却发现表达式不好调试，选了 heartbeat 结果任务堆积到 OOM。本文从工程化视角拆解两者的差异、适用边界与踩坑点，帮助你在配置文件中做出更稳妥的选型。

## 问题界定：cron 和 heartbeat 到底差在哪？

简而言之，在 OpenClaw 的任务模型中：

- **cron** 使用标准 cron 表达式，以**日历时间**为锚点，精确到秒级，适合“每天 10:00 执行”“每小时第 5 分钟触发”这类固定时刻需求。
- **heartbeat** 以**服务启动时刻为起点**，按固定时间间隔重复执行，适合“每 30 秒检查一次”“每隔 5 分钟同步状态”这类相对时间间隔需求。

从实现上看，cron 依赖系统的定时器在指定的秒数触发，heartbeat 则是每次任务完成后（或直接）等待固定间隔再发起下一次。这意味着两者在**任务重叠、错过补偿与多实例行为**上有本质区别，也是在生产环境最容易踩坑的地方。

## 实践步骤：如何在 OpenClaw 中配置两种定时任务

假设我们在 `openclaw.yaml`（或任务配置模块）中定义一个抓取任务：

```yaml
tasks:
  - name: fetch-stock-data
    type: plugin
    plugin: market-fetcher
    schedule:
      cron: "0 0 9 * * ?"        # 每天 09:00:00 触发
      # heartbeat: 30s           # 若用间隔模式则取消注释
    timeout: 120s
    retry: 3
```

**cron 配置要点：**

- OpenClaw 使用 Quartz 风格的 6 位 cron 表达式（含秒），需要确认你的平台是否支持 7 位（带年），一般 6 位足够。
- 注意时区：cron 默认跟随服务器时区，若容器默认 UTC，会导致“8 点执行”实际在北京时间 16 点触发。可以在全局配置中显式指定 `timezone: Asia/Shanghai`，或在表达式里用 `TZ=Asia/Shanghai` 前缀（取决于调度器实现）。
- 调试技巧：先用每分钟一次的表达式（`0 * * * * ?`）验证任务链路，再改成目标时间，避免等一天才发现写错。

**heartbeat 配置要点：**

```yaml
schedule:
  heartbeat: 5m
```

- 时间单位支持 `s`、`m`、`h`，`heartbeat: 90s` 表示每隔 90 秒执行一次。
- 间隔计算从**任务启动成功（或任务结束后）**开始倒计时，具体要看 OpenClaw 版本的行为标记：有的实现是固定频率（从开始算），有的是固定延迟（结束后算）。这会影响并发控制，下文会详述。

## 踩坑点：三个真实故障场景

### 1. cron 在分布式多实例下的重复执行

如果你的 OpenClaw 服务部署了多个副本（例如 Kubernetes 3 副本），而定时任务没有加分布式锁，那么每个实例都会在同一秒触发同一个 cron 任务，导致重复抓取、重复通知、数据不一致。这是一个经典问题。

- **症状**：数据库短时间内出现大量重复记录，下游服务收到多次相同请求。
- **根因**：cron 调度器是进程内组件，不具备跨实例协调能力。
- **解法**：为任务添加分布式锁注解，或在插件代码开头抢占锁（如 Redis SETNX）。OpenClaw 部分版本内置了基于数据库的 leader 选举，可在任务定义中开启 `singleton: true`。

### 2. heartbeat 任务堆积导致内存暴涨

当 heartbeat 间隔设置为 30 秒，但任务实际执行需要 45 秒（例如外网 API 超时），且调度策略为“固定频率”，则下一个触发时上一个仍在运行。若无并发控制，任务线程池会迅速耗尽，内存上涨。

- **症状**：线程池满、任务日志显示多个相同任务并发执行、服务 OOM。
- **根因**：heartbeat 没有考虑任务实际耗时，形成重叠执行。
- **解法**：
  - 在定义任务时设置 `concurrency: 1`（若框架支持），强制串行执行，后来的触发会被丢弃或排队。
  - 调整 heartbeat 间隔 > 任务最大执行时间（加缓冲）。
  - 如果业务允许跳过，可使用 `skipIfRunning: true` 参数。

### 3. cron 表达式错误导致静默失败

一个低级但高频的问题：写 `0 0 9 * * ?` 想表示“每天 9 点整”，但实际使用了 5 位的非标准 cron，解析器可能报错或按每分钟执行。由于 cron 校验不严，任务静默跳过。

- **经验**：使用在线 cron 调试工具（如 Crontab Guru）验证 6 位表达式，并在测试环境以缩短周期的方式先行验证。OpenClaw 启动日志通常会打印下次触发时间，务必检查。

## 可复用建议：选型决策树与防御措施

根据实际场景总结如下选型原则：

- **需要与人协作、与外部系统时间对齐（如收盘后执行、上班前汇总）** → 用 cron。
- **纯系统内部巡检、心跳检测、实时性要求不高但需周期性执行** → 用 heartbeat。
- **多实例部署、不能接受重复执行** → 优先 cron + 分布式锁 / 单例约束；heartbeat 同样需要单例保障。
- **任务耗时不稳定或可能长于间隔** → 避免短间隔 heartbeat，改用 cron 精确触发，或加并发控制与超时熔断。

另外，无论用哪种模式，都建议给任务添加：

- 明确 `timeout`（避免僵尸任务）；
- 失败重试与死信队列（插件内部或外部监控）；
- 轻量级监控埋点（记录每次执行的开始、结束、状态），便于排障。

## 总结

cron 与 heartbeat 没有绝对的优劣，核心在于你对**时间语义**和**并发模型**的理解。cron 解决“在正确的时间做事”，heartbeat 解决“以正确频率做事”。真实坑位往往不在配置语法本身，而在分布式协调、任务重叠和静默失败这些工程细节。如果你正准备在 OpenClaw 上构建定时驱动的 Agent 自动化流水线，建议先在测试环境用最小化任务跑通选型逻辑，再上线正式业务。
