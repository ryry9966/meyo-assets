## 背景：Agent 自主性是一把双刃剑

当 Agent 通过 MCP、插件、外部 API 获得修改文件、调用后端接口、触发支付或发通知的能力时，它就不再只是一个“聊天管里工”，而是一个确实能产生副作用的自动化系统。

在 OpenClaw 这样的可编程 Agent 实践中，权限问题的核心矛盾很简单：

- 过度询问人类 → Agent 失去自动化价值，人工决策带宽成为瓶颈
- 完全自主执行 → 深夜删库、批量误操作、向客户发送错误消息，事故成本极高

这篇帖子不会告诉你“去问用户就行”。我会给出一个工程上可执行的分层权限模型，以及在 OpenClaw 的 Skill/MCP/Action 体系中真实可落地的做法。

## 问题定义：决定性因素不是操作本身，而是上下文

工程师通常习惯用“操作”来分权限等级：读文件是低危，写文件是中危，删文件是高危。但在 Agent 场景里，这个经验经常失效。

举个例子：Agent 需要删除 `/tmp/test-report-*.log`，这其实很安全。但如果它要删除 `~/.ssh/id_rsa`，就算只是“读取文件后再删除”，也必须询问。

真正的权限边界取决于**操作作用域 + 操作不可逆性 + 操作对人与业务的影响半径**。而这三点只有结合当时的执行上下文才能判定，难以用静态规则穷举。

## 做法：三级权限决策框架

我目前在生产环境使用的是一套“**Risk Level L1–L3 决策模型**”，接入 OpenClaw 的 pre-action hook 中评估每一项工具调用。

### L1：可自动执行（无需询问）

条件（必须 **全部满足**）：
- 操作作用域限制在 Agent 专属的工作区或临时目录内（如 `agent_workspace/`, `/tmp/agent-<session>/`）
- 操作是可逆的，或失败不影响外部资源状态
- 变更后无用户感知、不发通知、不修改系统级配置

示例：
- 读取用户主目录下的公开笔记文件
- 在 Agent 自己的 sqlite 存储中写缓存
- 生成报告草稿到 `agent_workspace/reports/draft.md`

实现方式：在 OpenClaw 里，我将这类允许的工作路径白名单注入到工具调用的 `base_path` 校验器中，如果路径超出白名单自动降级到 L2。

### L2：条件执行（需隐性确认）

条件：
- 操作可能修改用户目录下的文件，或调用只读但存在数据外泄风险的 API
- 后果可控：即使错误操作，用户可以通过撤销、回滚、重新操作来恢复
- 无资金、身份、客户数据影响

行为：
- Agent 必须输出清晰的“**即将执行的动作说明**”，并用 `require_user_ack` 标记
- 若用户在设计时开启了“信任模式”，该动作可直接执行，但会记录审计日志
- 默认情况下，等待用户在对话中发回一个确认信号（如“继续”、“yes”）

工程实现：
- OpenClaw Skill 中所有写入用户文件系统的操作，我都包了一层 `confirmable()` 装饰器，它会检查当前会话是否允许静默执行，否则插入一个 ack 钩子
- 对于 MCP 调用，可在 `tool_call` 前加入 `risk_assessment` 检查，返回 `confirm_required` 标识

### L3：强制人工批准（绝不自动执行）

条件（满足任一）：
- 涉及外部支付、身份变更、权限授权
- 批量操作（循环删除/修改超过 N 条记录）
- 操作对象是系统配置文件、密钥、证书
- 修改用户级环境变量、crontab、systemd unit 文件
- 向外网推送或群发消息

行为：
- 就算用户开启了全部自动化开关，L3 操作也必须停止，并显示“**该操作需要手动批准**”
- Agent 必须提供影响预览和风险摘要，而不是简单描述操作
- 执行入口由人工重新发起（不允许 Agent 排队等待自动恢复）

我在 OpenClaw 中增加了一个全局 `action_gate`，每次工具调用前对比 L3 规则表（基于路径匹配、命令参数和 MCP 端点），命中后直接拒绝执行，并返回结构化风险描述，引导用户自行处理。

## 踩坑点

1. **信任模式被滥用**
   一些用户图省事，对所有工作目录开启了信任。一次由于 Agent 误读了指令，删除了整个本地 git 仓库的未提交文件。最终解决方案是“信任只对 session 临时生效”，且会话结束自动关闭信任，不允许全局持久化。

2. **“隐性确认”变成骚扰**
   初期 L2 操作过度使用 ack，用户很快开始机械点确认，形成疲劳。改进方法：合并相似操作批次，一次确认覆盖一组相关动作；同时让 Agent 输出“如果 30 秒内无反对则自动继续”作为默认策略，真正需要拒绝时再说 no，而不是每次等 yes。

3. **MCP 工具的权限泄露**
   导入第三方 MCP 服务器时，其暴露的工具可能绕过本地权限判断。必须对 MCP 客户端做工具白名单暴露，不要在 Agent 侧直接加载所有工具，而是预先声明一份 `allowed_tools` 列表，并指定每个工具的 L1–L3 等级。

## 可复用建议

- **白名单优于黑名单**：安全策略应基于“哪些可以做”而非“哪些不能做”。白名单路径、命令、API 端点决定安全下限。
- **Risk Level 绑定 Tool 定义，而不是每次 prompt**：将权限等级写在工具的 declaration 中（例如 OpenClaw Skill 的 `risk: L2` 字段），让系统自动处理，而不是靠提示词约束。
- **审计日志与回放**：所有 L2/L3 决策点都记录结构化日志（时间、工具、参数、决策结果）。当出现事故时，回放比复盘 prompt 高效得多。
- **给用户一个覆盖开关，但限制生命周期**：比如 `trust_this_session` 开启 L2 自动执行，会话超时自动关闭。既给效率，又防永久风险。

## 总结

权限边界的本质问题不是“该不该问”，而是“在什么风险条件下、向谁、以什么方式确认”。三层模型配合 pre-action hook 和声明式风险等级，能让你在保持 Agent 自动化能力的同时，将事故压缩到可接受的范围。

在 OpenClaw 体系里，把这些逻辑做进 Skill 执行器和 MCP 工具网关，远比每次写 prompt 祈祷“AI 别乱来”更可靠。
