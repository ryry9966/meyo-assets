# 基于 OpenClaw 的自动化日报流水线：从原始日志到结构化报告

## 背景

团队维护着多个后端服务，每天早晨需要从 Elasticsearch、Grafana 和一些本地日志文件中汇总关键指标、异常堆栈、定时任务执行结果，整理成一份结构化的日报，发送到飞书群。这项重复性工作每周大约花掉初级工程师 30 分钟 × 5 天的时间，且内容质量依赖个人经验，容易遗漏细节或误判严重程度。

为避免人力瓶颈，我们尝试过简单的 cron + shell 脚本，但面对非结构化文本（如错误日志片段）时，规则式的提取总是力不从心。于是引入了 OpenClaw，利用它的 Agent 编排能力和 MCP 插件体系，搭建一条“拉取日志 → 清洗分块 → LLM 提取摘要 → 模板渲染 → 发送”的自动化流水线。

## 核心问题拆解

日报自动化的难点不是单点技术，而是链路拆解：

1. **数据源异构**：Elasticsearch 查询 DSL、Grafana 告警 API、服务器本地文件，接口与格式各不相同。
2. **上下文长度与成本**：一天的原始日志可能超过 10 万行，不可能直接丢给 LLM，需要分段并设计有效的摘要策略。
3. **输出结构化**：日报需要固定的章节（概览、异常事件、性能趋势等），且数据不能幻觉严重。
4. **稳定性与可观测性**：流水线可能因网络抖动、API 限流、LLM 返回格式错误而中断，需要重试与告警机制。

## 实现步骤

我们使用 OpenClaw 作为调度与编排核心，结合自建 MCP 服务器连接日志源，最终通过企业微信 Webhook 投递报告。

### 1. 数据源接入：封装成 MCP 工具

为每个日志源编写一个 MCP 工具。例如 `query_es_errors` 暴露以下参数：`index`, `time_range`, `size`。工具内部构造 Elasticsearch DSL 查询，返回原始 hits 列表。对于 Grafana，使用其 Alerting API 拉取过去 24 小时的告警事件。本地日志文件则通过一个运行在节点上的 agent 侧车（sidecar）定期将内容推送到对象存储，再由 MCP 工具读取。

关键点：MCP 工具只负责数据拉取，不做分析，保持原子化和可测试。

### 2. 日志分块与预处理

拉取到的 raw logs 体量庞大，需要先做一次粗筛。我们写了一个预处理 skill，它调用 `jq` 和正则过滤掉噪音日志（如健康检查、DEBUG 级别），并按服务名称分组。然后使用滑动窗口分段，每段不超过 4000 字符，同时确保段边界不切断完整的 JSON 行或异常堆栈。

### 3. LLM 摘要链：渐进式提取

采用两次调用的链式策略：

- **第一阶段（逐段提取）**：对每个分段调用 LLM，要求输出 JSON，包含 `errors`、`warnings`、`performance_anomaly` 和 `task_result` 四个字段。Prompt 强调只提取事实，不要补充理由。
- **第二阶段（跨段合并）**：收集所有分段的摘要 JSON，再调用一次 LLM 进行去重、合并同类项、按影响范围排序，生成最终的报告骨架。

之所以不一次性合并，是因为分段摘要的并行执行可以大幅缩短墙钟时间（OpenClaw 支持任务依赖与并行编排）。使用 GPT‑4o‑mini 作为默认模型以降低费用，仅在检测到复杂异常时升级到更强模型，这部分由 OpenClaw 的 conditional router 完成。

### 4. 模板渲染与投递

最终的结构化 JSON 通过一个简单的 Jinja2 模板渲染成 Markdown，章节包括：

- 整体状态（红绿灯）
- 异常事件清单（服务、错误类型、次数、样例日志）
- 定时任务执行摘要
- 关键性能指标趋势（由 Grafana MCP 拉取）

渲染后的 Markdown 通过企业微信机器人 Webhook 发送，同时备份到 OSS 用于历史追溯。

### 5. 编排与调度

整体流程定义为 OpenClaw 的一个 Workflow，配置每天早上 9:00 触发，附带 5 分钟随机延迟以避免踩踏。Workflow 内部包含重试逻辑：若某 MCP 工具调用失败，指数退避重试 3 次；若最终 LLM 返回的 JSON 无法解析，则回退到仅发送原始摘要文本并通知人工介入。

## 踩坑记录

- **MCP 连接生命周期**：长时间闲置后，SSE 连接会被反向代理切断。我们在客户端侧增加了心跳 PING/PONG，并设置重连策略。
- **JSON 解析不稳定**：即使 Strong type prompt，GPT‑4o‑mini 偶尔仍会在 JSON 中包含未转义的换行符。解决方案：使用 `json_repair` 库预修复，并在解析失败时重试整个摘要链。
- **日志分段策略**：最初按固定长度切割，经常切断堆栈导致漏报。后来改为识别到 `Traceback` 或类似起始符号时强制保留完整块，边界判断让预处理逻辑复杂度上升了不少。
- **Prompt 维护**：随着服务变更，新增的日志模式需要及时告知 LLM。我们将“已知可忽略错误模式”维护在一个 JSON 文件中，通过 MCP 工具动态注入提示，避免频繁修改工作流定义。
- **时区问题**：所有时间参数字符串统一使用 ISO 8601 加 `+08:00`，并在工具侧内部转换为 API 所需格式，杜绝因服务器本地时区不同导致的查询偏移。

## 可复用建议

- **数据源与处理解耦**：MCP 工具只返回原始数据，总结逻辑全部放在 Agent 中，方便替换底层日志存储。
- **分段摘要模板化**：将第一阶段 prompt 定义为可配置资源，支持按服务动态加载不同的提取重点。
- **输出校验先行**：不要相信 LLM 的结构化输出，务必在后处理中添加 JSON Schema 校验与修复步骤。
- **可观测性**：将每一步的耗时、token 消耗、异常记录发送到团队的内部监控频道，方便发现隐性性能退化。
- **人工兜底**：工作流最后一步检查报告是否生成成功，若连续失败 2 次，自动 @ 值班人员并附上原始日志片段。

## 总结

这条自动化日报流水线已经在生产环境运行了 3 个月，每日从 14 个服务中聚合日志，生成报告平均耗时 47 秒（含 LLM 调用），彻底释放了工程师的早晨时间。投入最大的不是模型，而是日志预处理和输出校验的胶水代码。使用 OpenClaw 的好处在于，当数据源或投递渠道需要变更时，只需修改对应的 MCP 工具或模板配置，核心工作流主体保持稳定，符合我们期望的“足够灵活、可以复现”的工程化目标。

对于同样在用 Agent 框架做自动化报告的同学，强烈建议先花 70% 的精力做好数据清洗和格式强校验，这比换模型效果来得更直接。
