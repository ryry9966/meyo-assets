## 背景

在构建基于 OpenClaw 的自动化助手、Agent 调度器或 MCP 插件时，我们经常需要让 AI 侧感知外部世界的变化——比如收到一条新消息、一次任务状态更新、或者某个长时间运行的子流程结束。此时，“心跳”（heartbeat）机制就不仅仅是维持连接存活的手段，它直接影响助手能否“及时”反应。

最常见的两种实现路线一目了然：**轮询（polling）** 和 **推送（push）**。但在实际的插件和自动化链路中，选错方案会很快从“能用”变成“卡顿、费资源、甚至丢消息”。这篇文章结合几次在 OpenClaw 生态中踩过的坑，聊一聊两种心跳设计的实际取舍，以及一条可以复用的工程化做法。

## 问题是怎样暴露的

最初我们在一个 OpenClaw 插件中做任务状态同步，插件向外部系统发起一个异步任务后，需要定期检查任务是否完成，再通知 Agent 继续后续操作。直觉做法是 `setInterval` 每 500ms 轮询一次状态接口。前期没有任何问题，直到有一天突然接入了 20+ 个并发任务：

- 轮询产生的请求量瞬间把第三方 API 的 rate limit 打满；
- Node.js 事件循环被大量定时器拖慢，Agent 自身的响应延迟从 200ms 飙升到 2s+；
- 偶尔因为网络抖动，某次轮询失败，但没有重试逻辑，任务状态就“卡住”，只能人工介入。

这逼着我们去严肃思考：**什么时候轮询足够好，什么时候必须上推送，以及心跳怎么设计才能保活又不浪费。**

## 两种心跳的工程化实现

### 方案一：基于短轮询的 heartbeat（简单但需克制）

在 OpenClaw 插件中，一个典型的轮询心跳可以这样写：

```ts
const POLL_INTERVAL = 3000; // 3 秒
let timer: NodeJS.Timeout;

function startPolling(taskId: string) {
  timer = setInterval(async () => {
    try {
      const status = await fetchTaskStatus(taskId);
      if (status === 'completed') {
        clearInterval(timer);
        emit('task:completed', taskId);
      }
    } catch (err) {
      // 避免因为一次失败就停止轮询
      logger.warn('polling error, will retry on next tick', err);
    }
  }, POLL_INTERVAL);
}
```

**关键约束：**
- 间隔不要低于 1~2 秒，否则 CPU 和远端压力会非线性增加；
- 必须内置错误容忍，单次失败不应终止整个轮询循环；
- 及时清理 `setInterval`，避免内存泄漏和无效请求。

适合场景：任务通常耗时在分钟级、允许数秒延迟、实例数量少且网络稳定。

### 方案二：基于 SSE/WebSocket 的推送心跳

当助手需要真正“实时”反馈，比如聊天场景中的流式响应、或者 MCP 工具调用的中间结果返回，我们更推荐 **Server-Sent Events（SSE）**。MCP 协议本身在 `streamable HTTP` 传输中也可以利用 SSE 来推送服务器端通知。

OpenClaw 的 Agent 可以这样建立心跳并监听事件：

```ts
const eventSource = new EventSource('/mcp/events?session=xxx');

eventSource.onmessage = (event) => {
  const data = JSON.parse(event.data);
  handlePushEvent(data);
};

// 心跳保活：客户端定时发送 ping，服务端回应 pong
setInterval(() => {
  fetch('/mcp/ping', { method: 'POST', body: JSON.stringify({ ts: Date.now() }) });
}, 30_000);
```

**推送方案带来的收益：**
- 零轮询开销，事件发生瞬间即可触达；
- 减少了大量无意义的网络请求；
- 与服务端的保活心跳分离，心跳仅用于维持连接，不承担业务轮询职责。

## 真实踩坑点

1. **多实例推送路由问题**
   如果你在 OpenClaw 的 Agent 侧做了多副本部署，SSE 或 WebSocket 连接会落在特定实例上。当后台任务在另一实例完成时，推送事件可能找不到正确的连接。解决方案是引入一个轻量的消息通道（比如 Redis Pub/Sub），由每个实例订阅统一频道，再转发给本地持有的连接。

2. **防火墙与代理超时**
   很多企业环境会无提示断开空闲的 SSE/WebSocket 连接。我们遇到过 60 秒无业务消息就被 L4 负载均衡强行断开的情况。解决方法就是 **应用层心跳**：客户端每 30 秒发送一个业务无关的 ping 帧，服务端回复 pong，保持连接活跃。注意这必须发生在应用协议层面，单纯 TCP keepalive 可能不够。

3. **消息丢失与确认**
   推送是实时，但不代表可靠。网络闪断时，服务端推送的事件可能丢失。对于关键任务状态流转，我们在插件里增加了一条轻量级兜底：**在接收 push 事件后，仍会执行一次按 ID 查询的幂等校验**，并把事件序列号记录下来，重连后自动请求缺失区间的事件（类似 MCP 的 `progressToken` 思想）。这避免了引入复杂的消息队列，成本极低。

4. **轮询“共振”现象**
   短时间内启动大量轮询任务，如果所有定时器间隔一致，很容易与远端系统形成同步压力尖峰。一个简单有效的做法是给每个轮询器的初始延迟增加一个随机抖动（jitter），比如 `3000 + Math.random() * 1000`，让请求更加平滑地分散。

## 可复用建议

- **延迟容忍 ≥ 5 秒**，且并发任务数可控（< 50）时，**短轮询** + 随机抖动是完全够用的，维护成本最低；
- **需要近实时交互**（如对话式 Agent、工具调用状态流），优先考虑 **SSE**，而非自己折腾 WebSocket，尤其在 OpenClaw 的 MCP 链路中，SSE 与 HTTP 生态的兼容性更好；
- 无论哪种方案，一定要有**独立的保活心跳**和应用层错误恢复策略，不要将业务轮询和保活混为一谈；
- 在推送场景下，永远加上**兜底查询**作为最后的保障，防止极端情况导致任务“悬空”；
- 监控指标里至少包含：轮询周期实际耗时、推送重连次数、心跳失效率，方便及早发现连接静默问题。

## 总结

AI 助手的 heartbeat 设计，看似是“选轮询还是推送”的二选一，但真正的工程收益来自于对**延迟、资源消耗与可靠性**三者之间的权衡落地。没有银弹：轮询简单但容易浪费，推送实时却需要额外的连接管理和恢复逻辑。好在，在 OpenClaw 插件体系与 MCP 的传输层设计中，已经提供了足够灵活的基座——我们需要做的，是根据自己的实际延迟容忍度和规模，诚实地选择心跳策略，并针对性地填上消息丢失和连接中断的坑。

毕竟，一个在半夜因为轮询风暴被限流的 Agent，比一个迟钝的 Agent 更令人头疼。
