## 背景：为什么要在意 memory_recall 的检索方式

在 OpenClaw 生态里做 Agent 开发，迟早会碰上一个问题：**怎样从“记忆库”里捞出真正有用的上下文**。无论你是把对话摘要、代码片段、文档还是用户偏好写进存储，后续查询时，检索质量直接决定了 LLM 能获得多少有效信息。

最常见的两种检索路线：

- **全文搜索**（关键词匹配 / BM25）：基于倒排索引，对专有名词、代码标识符、日期范围极度友好。
- **语义搜索**（向量相似度）：通过嵌入模型理解语义，能抓住同义表达，但对冷门术语、数字和代码不够敏感。

我在一个 OpenClaw 插件里实现 `memory_recall` 时，曾在二者之间摇摆了很久，最后踩了一圈坑，做了一套“可配置的混合召回 + 重排序”方案。下面把这个过程拆开讲清楚——**不卖银弹，只聊工程上的取舍**。

## 问题：谁更好？其实问题本身就有坑

如果你只做语义搜索，你会发现：

- 用户搜 “error 500 at line 42”，召回的是各种异常描述，偏偏漏掉了带 `500` 的原始日志。
- 询问 “上周三的会议纪要”，语义搜索对时间表达不够敏感，容易把邻近日期的记忆也混进来。

反过来，如果只用全文搜索：

- 用户问 “有什么办法能加快数据库查询”，全文搜 “加快 数据库 查询”，可能错过用 “优化 SQL 性能”“提升 DB 响应” 等不同措辞记录的记忆。
- 多语言环境下，中英文混合搜索更是一场灾难。

结论很简单：**两类方法互补，但直接合并会带来冗余和延迟，需要精心设计融合策略**。

## 做法 / 步骤

### 1. 记忆入库时双写

在 OpenClaw 插件中，每次写入一条记忆（通过 MCP 提供的 `remember` 工具），同时做两件事：

```python
# 伪代码
memory_id = store_fulltext(doc, metadata)    # 写入 Elasticsearch / 自建索引
embedding = embed(doc.content)               # 比如 text-embedding-3-small
vector_store.upsert(memory_id, embedding, metadata)
```

这里关键是 **metadata 统一**——包括来源、时间戳、记忆类型（对话/代码/文档），方便后续过滤。

### 2. 召回阶段：先语义后全文，加权融合

`memory_recall` 被调用时：

1. **语义召回**：用查询的嵌入从向量库取 TopK_sem（比如 K=20）。
2. **全文召回**：用查询拼装关键词搜索，取 TopK_ft（比如 K=15）。
3. **融合排序**：把两队结果合并，用相对分数归一化后线性加权。权重作为插件参数可调，默认语义权重 0.6、全文 0.4。对于代码类记忆查询，我会临时把全文权重提到 0.7。
4. **重排序**：可选接入一个轻量级 cross-encoder 对 TopN（比如 10）重新打分，进一步压制噪声。

工具调用示例（通过 MCP 暴露）：

```json
{
  "tool": "memory_recall",
  "arguments": {
    "query": "用户上传文件大小限制",
    "top_k": 5,
    "strategy": "hybrid",
    "semantic_weight": 0.6,
    "filter": { "memory_type": "policy" }
  }
}
```

### 3. OpenClaw Agent 集成

在 OpenClaw 配置里把 `memory_recall` 注册为自动化工具，Agent 在需要上下文增强时自动调用。不必要让用户感知到底层用的是语义还是全文。

## 踩坑点

1. **语义嵌入模型的选择**  
   `text-embedding-ada-002` 对中文代码混合场景效果一般。换成支持多语言的模型（如 `bge-m3`）后召回质量明显上升，但维度变大，检索延迟增加。需要根据记忆规模做取舍。

2. **全文搜索的 tokenization**  
   CJK 分词是个经典麻烦。我用的是 Elasticsearch 的 `kuromoji`/`ik_max_word` 插件，但代码片段中下划线、驼峰命名需要自定义分词器，否则 `MaxFileSize` 会被切成一堆无意义子词。

3. **权重调参不能靠拍脑袋**  
   我最初用固定 0.5/0.5，发现技术类记忆召回准确率波动很大。后来基于历史查询样本做了一次小规模离线评估，才确定按记忆类型动态调整权重的逻辑。建议你在自己的场景里也做 — 不用很重，一百条标注就足够给出方向。

4. **混合搜索的延迟**  
   并行召回两个后端，总延迟基本由较慢的全文搜索决定。如果对延迟敏感，可以先启动语义搜索，在得到结果后再异步发全文搜索，然后合并 — 代价是增加一点系统复杂度。

## 可复用建议

- **不要一条道走到黑**：让你的 `memory_recall` 工具支持 `strategy` 参数，可选 `semantic`、`fulltext`、`hybrid`。这样可以在不同任务中按需切换，也方便调试。
- **分层存储**：把记忆按“热/冷”分层，热记忆（最近 n 天）用混合搜索，冷记忆可以在低峰期纯语义召回，降低资源消耗。
- **指标监控**：至少记录每次召回的 hit rate（用户是否采纳了某条记忆）。如果发现 semantic 持续在代码查询上垫底，这就是调整权重的信号。
- **利用 OpenClaw 插件机制**：把召回策略、后端选择、权重配置都做成可注入的 component，方便在不同 Agent 间复用，而不是硬编码在工具里。

## 总结

全文搜索和语义搜索不是二选一，而是两种不同材质的锤子。**工程上最高效的方式，是把选择权交给场景驱动的混合策略**，并通过可配置的召回管道与重排序，让 Agent 在各种记忆类型下都能拿到高密度上下文。

在 OpenClaw 这类自动化平台里，一个稳定的 `memory_recall` 往往比炫技的模型更能决定 Agent 产出的底线。希望这篇实践笔记能帮你少走一点弯路，把时间花在真正有价值的地方。
