# OpenClaw 的 AGENTS.md：写给 AI 代理的工作空间操作手册

在 OpenClaw 这类 AI 代理工作台中，我们常常让代理帮我们生成代码、运行命令、修改文件。但每次新建会话，代理都会丢失对当前项目的全部记忆，于是你不得不反复解释：这个仓库是做什么的、用什么构建工具、测试怎么跑、哪些目录不要碰。久而久之，这种“对齐成本”成了自动化流程里最消耗耐心的一环。

OpenClaw 引入了 `AGENTS.md` 机制——一个放在工作空间根目录的 Markdown 文件，作为代理的持久化项目知识库。它不是系统提示，也不是一次性的对话指令，而是一份**被代理在每次任务前自动加载的结构化上下文**。

## 背景：为什么需要 AGENTS.md

在 MCP 插件、Hooks 和自定义技能已经相当丰富的今天，代理能做的事情越来越多：读写文件、执行 Shell、调用外部 API。但这些能力只有在理解“当前环境应该怎么用”时才有意义。比如：

- 一个 monorepo 里，`npm run build` 应该在哪一个子包执行？
- 项目使用了自研的 CLI 工具生成模板文件，代理能不能直接调用？
- 某个目录下有自动生成的代码，代理是否应该完全避免修改？

这些问题无法靠通用常识解决，必须由项目上下文来约束。

## 核心做法：像写 README 一样写 AGENTS.md

`AGENTS.md` 本质上是写给机器的操作手册。它的生效方式很简单：在 OpenClaw 工作空间根目录创建该文件，代理启动任务时会自动读取并纳入上下文。你可以把它理解为“本地优先的 RAG”。

一个工程上可用、不被截断的 AGENTS.md 通常包含以下几个部分：

```markdown
# AGENTS.md

## 项目概览
单行说明项目用途，例如：“企业内部组件库，基于 React + TypeScript + Rollup”。

## 目录结构
- `/packages/*` - 多包体，每个包的入口在 `src/index.ts`
- `/scripts` - 构建与发布脚本
- `/examples` - 示例项目，代理可读取但不要修改

## 常用命令
- 全量构建：`pnpm build`（根目录）
- 单包构建：`cd packages/<name> && pnpm build`
- 运行测试：`pnpm test`
- 生成 API 文档：`pnpm docs`

## 代码规范
- 使用 ESLint + Prettier，提交前必须通过 lint-staged
- 组件导出必须包含 TypeScript 类型声明
- 禁止在 `packages/*/src/__generated__` 下手动编辑

## 关键注意事项
- 代理不要自行升级依赖版本
- 遇到 `peerDependency` 冲突时，优先调整安装策略而非直接修改版本号
- 若需要新建包，请参考 `packages/template` 的结构
```

这种结构不是规范，但足够清晰。你完全可以按自己团队的风格调整，关键是把“在工程中反复口述的信息”一次性沉淀下来。

## 踩坑点与避坑指南

在实际使用中，有几点容易踩坑：

**1. 内容过长导致上下文溢出**  
代理的上下文窗口有限，如果把整个 CHANGELOG、详细构建配置全部塞进去，有效信息反而会被挤占。建议 `AGENTS.md` 控制在 600 个 token 以内，更多细节可以通过文件引用或“按需查阅”的方式引导代理读取，例如“构建配置细节见 `build/README.md`”。

**2. 文件未被代理识别**  
需要确认 OpenClaw 的工作空间感知机制是否已覆盖该文件。典型症状是代理仍然问“这个项目怎么构建”，此时可以在对话开头显式提示“请先阅读工作空间下的 AGENTS.md 并严格遵循”来验证，如果仍无效，则需检查工作空间根目录是否设置正确、文件编码是否为 UTF-8。

**3. 更新不同步**  
项目演进后，AGENTS.md 也需同步维护。建议把它的更新纳入 PR 检查清单，就像维护 CI 配置一样。一个行得通的办法是在代码评审中增加一条：“如果此次变更影响了开发流程或目录结构，请同步更新 AGENTS.md”。

**4. 敏感信息泄露**  
不要在 AGENTS.md 中写入 token、内部地址、密码等。代理会在云端处理上下文，即使本地运行，也有可能通过日志或者错误输出暴露这些内容。敏感信息应通过环境变量或密钥管理工具注入，且在任务中由代理按需调用，而不是写死在静态文件里。

## 可复用的工程建议

- **模板化**：为团队维护一个 `AGENTS.md.tmpl`，新项目直接复制并填充具体内容。
- **版本控制**：将 AGENTS.md 加入 Git 仓库，让每个分支对应自己的操作手册，避免不同分支行为不一致。
- **自动校验**：可以在 pre-commit 中加一条检查，比如“AGENTS.md 是否存在且非空”，防止漏加。
- **按角色分层**：大型项目可考虑拆分 `AGENTS-dev.md`、`AGENTS-deploy.md`，由不同场景的代理引用不同文件，但这需要 OpenClaw 支持对应的文件选择机制。

## 总结

AGENTS.md 看似只是一个简单的 Markdown 文件，但它的本质是把“人向代理解释项目”的过程工业化。当你的项目中有越来越多的自动化代理在工作——无论是代码生成、CI 修复还是文档同步——一份清晰的操作手册会迅速从“锦上添花”变成“基础设施”。

把它当作给新同事（机器同事）的入职文档来写，你会得到更可靠、更低摩擦的自动化体验。
