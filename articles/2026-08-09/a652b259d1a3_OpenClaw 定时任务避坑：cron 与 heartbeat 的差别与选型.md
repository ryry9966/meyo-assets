# OpenClaw 定时任务避坑：cron 与 heartbeat 的差别与选型

## 背景：两种内置定时器，不止是“定时触发”

在 OpenClaw 工作流中，定时执行是最常见的自动化需求之一。平台内置了两种风格迥异的定时器触发器：

- **cron**：基于标准 cron 表达式，按日历时间触发，如 `0 2 * * *` 每天凌晨 2 点。
- **heartbeat**：基于固定间隔（秒）的心跳触发，如每 30 秒执行一次，可配置是否在启动时立即触发。

表面上看，它们都能让工作流周期性运行，但内部行为差异巨大。当 OpenClaw 部署在多实例、长时间任务或 MCP 插件频繁调用等场景下，选择不当会立刻暴露问题：任务重复执行、状态竞争、执行间隔不可控等。

## 问题：选错定时器的真实代价

最近一位社区用户用 heartbeat 模拟 cron：设置 `interval: 86400`（一天）来实现每日任务。结果发现任务有时被跳过，有时时间漂移。原因很简单：heartbeat 从上一轮执行**结束后**才开始计时，而 cron 只看墙上时钟。一天的任务如果执行 3 小时，heartbeat 的间隔会变成 3 小时 + 24 小时，逐渐偏离预期时刻。

反过来，用 cron 做高频健康检查（如 `*/5 * * * *`）时，如果检查对象是外部 MCP 服务，5 分钟内服务可能已经闪断又恢复，而 cron 无法更细粒度地感知瞬时状态。

可见，核心矛盾在于对“定时”的定义不同：cron 是**时刻驱动**，heartbeat 是**间隔驱动**。

## 做法：理解原理，再看场景

### 1. 查看 OpenClaw 配置示例

```yaml
triggers:
  - type: cron
    expression: "0 3 * * 1"        # 每周一凌晨3点
    timezone: "Asia/Shanghai"
    # 多实例环境下建议配合 lock

  - type: heartbeat
    interval: 60                   # 每60秒一次
    run_on_start: false            # 启动时不立即触发
    concurrency: 1                 # 同一时间只允许一个实例运行
```

### 2. 行为差异对照

| 维度         | cron                        | heartbeat                         |
|--------------|-----------------------------|-----------------------------------|
| 触发基准     | 系统时钟的绝对时刻           | 上一次任务结束后的相对间隔        |
| 精度         | 分钟级（依赖进程唤醒）       | 秒级，但受任务时长影响            |
| 重叠执行     | 默认允许，可配置并发控制     | 默认串行，可配置 max concurrency  |
| 分布式行为   | 所有实例同时触发（需锁）     | 每个实例独立，心跳是本地行为      |
| 时区敏感     | 是，可指定 timezone          | 否，仅与运行环境时钟相关          |
| 典型用途     | 日报、备份、定时清洗         | 队列轮询、服务探活、状态同步      |

### 3. 在 OpenClaw 工作流中的集成方式

- **cron 用于上游触发**：在触发器配置中直接定义，工作流在时刻点“被唤醒”，非常适合 ETL、报表生成。
- **heartbeat 用于中间件轮询**：可以将 heartbeat 作为独立触发器，也可以在工作流内部使用 `wait` 节点模拟心跳，但建议用内置触发器以保持日志一致。

## 踩坑点

### 坑1：多实例 cron 的重复执行

OpenClaw 支持多 worker 部署，cron 触发器会被每个 worker 解析并执行。如果没有分布式协调，同一时刻会跑 N 份相同工作流。

**解决**：给 cron 工作流加上资源锁。例如在任务开始时尝试获取 Redis 锁：

```python
# 伪代码：通过 action 节点获取锁
lock_key = "cron:weekly-report"
if not redis.set(lock_key, "1", nx=True, ex=600):
    workflow.skip("Another instance is running")
```

或者在触发器配置里使用 OpenClaw 内置的 `leader_election`（若版本支持）。

### 坑2：heartbeat 间隔小于任务执行时长

假设 heartbeat 间隔 10 秒，但任务需要 15 秒才能完成。如果未限制并发，会产生多个并行实例，可能竞争同一资源（数据库连接、文件句柄），最终超时或数据错乱。

**解决**：强制 `concurrency: 1`，让新触发等待前一次结束，或使用队列缓冲。同时为任务设置超时，避免永久阻塞心跳。

### 坑3：时区导致 cron 时间偏差

cron 表达式默认使用 UTC（或 Host 时区），如果服务器在 UTC+0，而你想在北京时间触发，忘了设 `timezone` 就会错峰执行。

**解决**：显式指定 `timezone`，并在 CI/CD 中加入时区一致性检查。

### 坑4：heartbeat 无法精准“对钟”

需要“每小时第 0 分钟执行”的场景不适合 heartbeat，因为它无法对准时钟。强行用 heartbeat 计算延迟只会让逻辑脆弱不堪。

## 可复用建议

- **决策口诀**：需要“整点/特定时刻” → cron；需要“持续检查、不漏间隔” → heartbeat。
- **幂等设计**：cron 类任务必须在业务层面支持幂等，即使偶尔重复执行也不产生副作用。
- **心跳保活**：对于 heartbeat 轮询外部 API，建议在循环内加入“条件判断”节点，只有状态变化时才全量执行后续步骤，避免空转消耗。
- **混合编排**：一个常见模式是 cron 定时拉取任务列表，heartbeat 逐条处理或检查进度，两者配合提升吞吐。
- **监控覆盖**：为两种触发器分别打上 `trigger_type` 标签，在日志中记录下次理论触发时间，便于发现漂移。

## 总结

cron 和 heartbeat 不是“哪个更好”的问题，而是对时间和节奏的不同抽象。理解它们对任务重叠、分布式协调和时钟精度的处理方式，才能避免在 OpenClaw 自动化场景中踩坑。建议在架构评审时就明确触发器的类型、并发策略和失败重试约定，少走弯路。
