# 当单 Agent 不够快：Subagent 并行编排的工程实践

## 背景：为什么需要并行 Subagent

在基于 Agent 的自动化流程里，一个常见的瓶颈是**串行执行**。比如你需要分析 10 份财报、从 5 个不同数据源抓取信息、同时对一段长文本做摘要和实体抽取——如果让一个 Agent 按顺序调用工具、逐步推理，总耗时等于各步骤之和。对于强调实时性或面向用户交互的场景，这种延迟很难接受。

OpenClaw 这类框架天然支持多 Agent 协作，但很多人依旧习惯“一个主 Agent 调所有工具”的模式。实际上，只要把任务拆成多个独立子任务，**用 Subagent 并行执行，可以显著缩短端到端时间**。本文讲的就是我在实际项目中做并行 Subagent 编排的经验，不含泛热点，只谈工程落地。

## 问题拆解

并行不是“同时多开几个 Agent”这么简单。主要挑战在于：

1. **上下文隔离与共享**：子任务需要知道全局意图，但又不能带着主 Agent 的全部记忆，否则 token 消耗爆炸且容易互相干扰。
2. **结果聚合与一致性**：多个 Subagent 返回结果后，如何准确合并，并处理部分失败的情况？
3. **资源与并发控制**：LLM API 有速率限制，本地工具调用也可能存在竞争条件，必须有节流和重试机制。
4. **可观测性**：并行执行时，日志如果混在一起，排查问题几乎不可能。

下面以 OpenClaw 为例，逐步说明怎么搭一套可控的并行编排模式。

## 做法：三层编排模型

我采用的模式可概括为**三层结构**：

- **编排层 (Orchestrator)**：主 Agent，负责理解用户意图，将任务拆分成若干独立子任务，决定哪些可以并行，并分配 Subagent。
- **工作层 (Worker Subagent)**：执行单一职责的 Agent，只持有该子任务所需的最小上下文和工具集。
- **聚合层 (Aggregator)**：一个轻量级 Agent 或纯函数，负责接收并行结果，做校验、整合、去重，最后生成最终回复。

### 步骤 1：定义 Subagent 角色与工具边界

在 OpenClaw 里，每个 Subagent 就是一个独立的 Agent 配置文件，可以限制它可用的工具列表和系统提示词。比如同时做网页抓取和文本分析，我会定义两个子 Agent：

- `web_scraper`：只挂载 HTTP 请求工具和 HTML 解析工具，提示词明确要求“仅提取原文关键信息，不做加工”。
- `text_analyzer`：挂载文本摘要、实体识别工具，提示词要求“基于上游给的原始文本，输出结构化分析结果”。

关键点：**限制工具权限**——Subagent 不该看到主 Agent 的所有工具，否则容易越权调用，也让调试变复杂。

### 步骤 2：在编排层生成并行任务计划

主 Agent 接到复杂请求后，通过一个 **planning 工具**（可以是 LLM 动态生成，也可以基于固定模板）输出一组子任务定义：

```json
[
  {"id": "1", "type": "scrape", "params": {"url": "..."}},
  {"id": "2", "type": "scrape", "params": {"url": "..."}},
  {"id": "3", "type": "analyze", "params": {"text": "$1.output"}},
  {"id": "4", "type": "summarize", "params": {"text": "$2.output"}}
]
```

这里有依赖声明：任务 3 依赖任务 1 的输出，任务 4 依赖任务 2。编排引擎解析依赖关系，**识别出 1 和 2 可以并行，3 和 4 在对应的抓取完成后可以并行**。这样形成流水线，兼顾并行与依赖。

### 步骤 3：异步调度与结果收集

OpenClaw 底层是异步的，可以直接用 `asyncio.gather` 或框架内的任务管理器来并行启动 Subagent。需要封装一个统一的调度器，对每个子任务：

- 注入最小上下文（只含必要参数和依赖上游的输出摘要，而非全量历史）
- 设置超时（比如 60 秒）
- 返回结果遵循统一 schema：`{ task_id, status, data }`

调度器负责并发限制（例如同时最多 5 个 LLM 调用），并在部分失败时立即触发**降级策略**，比如使用缓存或返回错误标记。

### 步骤 4：聚合与校验

将所有 `status: success` 的结果传入聚合层。聚合层可以是另一个 Subagent，也可以是确定性的脚本。它的核心工作是：

- 检查数据完整性：数量、必须字段
- 合并同类信息：去重、排序
- 探测矛盾：若两个子分析结论冲突，标记不确定
- 生成统一回复或转交主 Agent 进行最终决策

## 踩坑点与对策

**坑 1：过多 token 透传导致上下文爆炸**  
有时把主 Agent 的完整记忆一股脑塞给 Subagent，结果并行 5 个子 Agent，每个输入 8k token，浪费且易产生幻觉。  
**对策**：只注入任务描述和引用数据，例如“请基于以下三段原始文本做摘要：{text}”，禁止携带聊天历史。

**坑 2：工具调用竞争**  
若两个 Subagent 同时操作同一外部资源（如写入同一个数据库记录），会出现状态不一致。  
**对策**：要么让工具幂等，要么在编排时保证互斥（比如专门设一个“写”Agent 串行处理）。

**坑 3：部分失败静默**  
并行任务中一个失败，如果没有妥善标记，聚合层可能把错误输出当正常结果吞掉。  
**对策**：强制所有 Subagent 返回结构化 JSON 含 `status` 字段，聚合层必须检查 status，任何 `error` 都要在最终回复中显式告知用户，并给出可用部分。

**坑 4：日志混乱**  
并行执行让 Log 按时间线交织，排查定位耗时或异常极困难。  
**对策**：在每条日志中带上 `task_id` 和 `session_id`，使用结构化日志，推荐用 ELK 或 Loki 进行查询过滤。

## 可复用建议

1. **从依赖图入手，而不是直接跑并行**：用简单的 DAG 描述任务依赖关系，再寻找并行机会，可大大降低编排复杂度。
2. **给 Subagent 做“微缩版”上下文设计**：把每个子 Agent 看成一个微服务，提示词、工具集、上下文窗口都严格控制，才能安全并行。
3. **重试与超时是必须品**：LLM 调用天生不稳定，每个 Subagent 调用都要有指数退避重试和严格超时，避免拖死整个流水线。
4. **可观测性前移**：在开发阶段就用 `task_id` 标记，配合 OpenClaw 的 session 机制，快速搭建并行调试面板。
5. **渐进式增加并行度**：先跑通 2 个 Subagent 并行，验证上下文隔离和聚合正确性，再逐步扩展，不要一上来就 10 路并发。

## 总结

并行 Subagent 编排不是炫技，而是解决复杂任务延迟问题的实用手段。难点不在于启动多个 Agent，而在于**划分任务边界、控制上下文、处理失败和监控**。通过三层编排模型（Orchestrator / Worker / Aggregator）加上清晰的依赖声明和结构化返回，可以在 OpenClaw 体系内稳定落地。

实际测试中，一个原本需要 45 秒的财报分析链路（抓取 8 个网页 + 分析 + 摘要），通过并行 Subagent 拆解后缩短到 12 秒以内——且结果质量没有下降。如果你正在做自动化 pipeline，不妨试试从少量并行开始，把可控的确定性逻辑留在编排层，把不确定性交给 LLM 并做好兜底。
