## 背景：Agent 普遍还是“问一句动一下”

目前大部分基于 LLM 的 Agent 实践仍是被动式（reactive）的：用户通过聊天界面发出指令，Agent 解析意图、调用工具、返回结果。这种方式在问答、代码辅助等场景下工作良好，但在运维巡检、异常预警、数据补全等需要“提前感知、主动行动”的场景里，始终缺了一环。

我们团队维护着一套内部服务健康监控系统，原本的做法是设置固定阈值的告警规则，再由值班人员手动排查。随着服务数量增加，告警风暴、误报、排查路径长等问题越来越突出。于是我们尝试引入 Agent 来做主动式（proactive）介入：不是等着人问“帮我查下现在数据库连接数”，而是 Agent 自己在异常出现时就去拉日志、查指标、判断严重程度，并把结论推送到沟通渠道。

这篇帖子记录我们在 OpenClaw 框架下落地 proactive Agent 的过程，重点不在框架本身，而在于**如何让 Agent 拥有“主动触发的眼睛”和“经过思考的手”**，以及在工程中踩过的坑。

## 问题拆解：从被动到主动，到底多了什么

一个 reactive Agent 的典型流程是：用户消息 → 意图路由 → 工具调用 → 总结回复。要让 Agent proactive 起来，需要额外解决三个问题：

1. **触发源从哪里来？** 用户不发言时，Agent 必须依赖外部信号：定时任务、消息队列、Webhook 回调、服务日志流等。
2. **上下文怎么构建？** 没有用户对话历史，Agent 需要自己生成初始 prompt：“我现在注意到这个异常，我该查什么？”
3. **行动边界怎么控制？** 主动行为如果没有约束，很容易变成“噪音制造机”。哪些操作可以自动执行，哪些必须经过审批或静默记录，必须提前定义。

这三个问题对应着三种工程能力：**感知接入**、**自主推理启动**、**行动策略控制**。

## 实际做法：一个“慢查询主动诊断”的 Agent

以 MySQL 慢查询监控为例。过去我们会设置慢查询阈值，超过就发钉钉通知，然后 DBA 手动上服务器 `SHOW FULL PROCESSLIST`、`EXPLAIN`、查锁等待。现在用 proactive Agent 来自动完成这条链路。

### 1. 感知层：把系统指标变成 Agent 的输入事件

我们在 OpenClaw 中定义了一个 `cron_trigger` 类型的 skill，每 5 分钟跑一次。脚本从 Prometheus 拉取近 5 分钟的慢查询数量，如果超过预设基线，就触发一次 proactive 任务。

```yaml
triggers:
  - type: cron
    schedule: "*/5 * * * *"
    skill: slow_query_monitor
    params:
      prometheus_endpoint: "http://prom:9090"
      threshold: 10
```

这一步的关键是**把原始指标转化为结构化的“事件卡片”**，而不是直接把一堆 metrics 扔给 LLM。我们用模板生成了这样一段上下文：

```
时间: 2025-03-28 14:25:00
指标: mysql_slow_queries{instance="db-master"} == 23
基线: 10
临近告警: [连接数突增, 磁盘延迟上升]
```

这块内容的可读性和信息密度，直接影响后续 Agent 的推理质量。

### 2. 推理层：从事件出发自动规划排查步骤

Proactive 任务被触发后，Agent 启动一个**无用户对话的会话**。我们为这个会话预设了系统指令：

> 你是一个 MySQL 健康诊断专家。你会收到一条指标异常事件。你必须根据事件内容决定如何排查，并使用工具执行诊断，最后将结论整理成报告。

Agent 可以调用的工具有三类，全部通过 MCP 暴露：

- **只读查询工具**：`run_sql_readonly`（封装了 `pt-query-digest` 的部分能力）、`get_explain_plan`、`show_locks`
- **环境信息工具**：`get_os_metrics`、`read_app_log`（仅限 past 5min）
- **通知工具**：`send_dingtalk_card`（需要显式声明 severity）

工具权限遵循最小可用原则：只读，且限定了可访问的库和表。

实际运行中，Agent 拿到事件卡片后常走的路径是：

1. 调用 `get_explain_plan` 抓出当前 running 状态的慢查询
2. 发现某条 `SELECT` 走了全表扫描，再去拉对应表的索引信息
3. 对比历史执行计划（从我们内部知识库拉取），发现统计信息过期
4. 生成结论：“索引 `idx_order_status` 因统计信息偏差未被使用，建议 `ANALYZE TABLE`”
5. 将严重等级设为 `warning`，并推送到钉钉。

整个过程无需人工介入，从拿到事件到诊断报告发出平均耗时 42 秒。

### 3. 行动策略：哪些自动做，哪些只做笔记

并非所有 proactive 结论都要直接通知到人。我们的分级策略是：

- **info** 级别：仅记录到观察日志，供后续回顾
- **warning** 级别：发送到专项钉钉群，内容包含诊断摘要和关键证据
- **critical** 级别：发送群通知 + @值班人员，同时附带一键 `ANALYZE` 的安全链接（需要二次确认）

在 `warning` 和 `critical` 间，增加了一个“人工 inline 确认”的实验性机制：Agent 在消息卡片里放一个“同意执行”按钮，点击后 OpenClaw 的 webhook 回调触发后续有写权限的工具。这相当于给主动行动加了一道护栏，也避免了之前直接自动执行 DDL 带来的风险。

## 踩坑记录

### 坑1：Agent 在无人类对话时容易跑偏

因为缺少用户持续追问的“纠偏”机制，Agent 可能在某一步调用工具返回大量信息时，陷入无关细节。比如拉取 OS metrics 时，附带了一段系统日志，它就开始去分析 cron 任务失败事件，完全忽略了慢查询本身。

**解决方式**：在系统指令中加了一条“铁律”——“每完成一个工具调用，必须回到主事件，回答：当前发现是什么？下一步还需要什么信息？”并在 Agent 的会话管理里限制最大推理步数（我们设的是 8 步）。

### 坑2：Event Storm 导致上下文撑爆

有一次上游监控出现 spike，产生了大量连续异常事件，每一个都启动了一个 proactive 会话。短时间内并发会话把 LLM 调用额度打满，且部分会话因 token 过长而截断。

**解决方式**：引入**事件去重与合并窗口**。30 秒内相同 `instance` + 同类异常的事件合并为一个，附加 count 字段。同时给 proactive 执行器加了并发限制（最多 3 个并发诊断任务）。合并后的上下文更加紧凑，Agent 也能看到“这已经是 3 分钟内第 7 次慢查询异常”，从而加重严重级别判断。

### 坑3：通知内容缺乏可操作性

早期 Agent 报告写得像教科书：“可能由于锁竞争或索引缺失导致查询变慢”。这种话对 DBA 而言缺乏决策价值。

**改进**：我们为通知卡片设计了固定模板，要求必须包含：
- 受影响的具体查询文本（脱敏后）
- 当前执行计划 vs 历史执行计划差异
- 建议操作（必须是可执行的 SQL 或运维指令）
- 如果判断不需要人工介入，必须写出“已自动静默”的理由

模板化之后，通知质量明显提升，也更容易通过程序统计 Agent 的“有效建议率”。

## 可复用建议

1. **从定时巡检开始，而不是事件流。** Cron 触发比流式事件容易控制节奏，也方便调优。等你对 Agent 的自主行为有了信心，再接入 Kafka/webhook 也不迟。
2. **为 proactive 会话单独设计 system prompt，并内置“回归主线”的元指令。** 无用户对话时，LLM 极易发散，必须反复拉回主任务。
3. **工具必须是确定性、只读优先。** 给主动 Agent 写权限，就像把家门钥匙交给陌生人。先让它在只读环境里跑够 100 个案例，再逐步开放可控的写操作。
4. **行动分级，卡片模板化。** 避免“狼来了”式的通知轰炸，同时让每一条自动推送都带有决策价值，而不是信息转述。
5. **监控 Agent 本身的“健康度”。** 我们建了一个 meta-monitor，统计每 24 小时内 proactive 会话的完成率、无效调用次数、通知静默率，防止 Agent 静默失败。

## 总结

Proactive 能力不是给 Agent 装一个“定时发送消息”的补丁，而是一整套从感知、推理到行动策略的工程改造。当我们把 Agent 视为环境中的智能体，而非对话机器人时，它的价值才会从“回答得好”变成“把事情办了”。

目前我们的 proactive Agent 每天自动处理约 40 个异常事件，其中 65% 被正确分类为无需人工介入，大幅降低了告警疲劳。后续我们计划将这种模式延伸到日志异常检测和自动数据修复场景，但权限控制与风控始终是悬在头上的首要约束。
