## 背景

在 OpenClaw 里搭建 Agent 时，通过 MCP 插件连接外部 API（天气、搜索、数据库、REST 服务）几乎成了标配。Agent 的智能依赖这些工具，但外部服务的不稳定性却常常被忽略。

API 超时、瞬时 5xx、限流 429 等小概率事件，在单次调用中看似无害，但当 Agent 连续执行多步任务时，一次工具调用失败就可能导致整个会话中断，用户只看到一个冰冷的异常，或者更糟——系统卡住几十秒后超时。

要让 Agent 真正用在生产环境，错误恢复能力不是可选项，而是基础要求。

## 问题

API 调用失败对 Agent 的影响有三种典型表现：

1. **工具直接抛异常，未捕获** → 任务终止，Agent 输出错误堆栈或模糊的失败信息。
2. **无超时控制** → Agent 工作线程卡死，用户干等，直到系统级超时才断开。
3. **粗暴重试** → 在网络抖动时不断重试，短时间内给故障 API 施加更大压力，形成「重试风暴」，甚至引发雪崩。

我们需要一种工程化的方式，在保持 Agent 自主性的前提下，优雅地处理失败，提供可接受的降级体验。

## 做法

### 1. 区分可重试与不可重试错误

不是所有失败都值得重试。规则很简单：

- **可重试**：网络超时、503/502/504、429（带 `Retry-After`）、短暂的 DNS 解析异常。
- **不可重试**：400 参数错误、401/403 鉴权失败、404 资源不存在。这些重试毫无意义，应立即返回错误信息给 Agent。

在工具函数中先按状态码或异常类型分类，能避免大量无效重试。

### 2. 在工具层封装重试与退避

OpenClaw 的工具函数本质上就是普通 Python 异步函数。我们完全可以为它们加上重试装饰器，而非在 Agent 的思考逻辑里处理。例如使用 `tenacity` 库：

```python
from tenacity import retry, stop_after_attempt, wait_exponential_jitter
import httpx

@retry(
    retry=retry_if_transient_error,  # 自定义只有 5xx/超时才重试
    stop=stop_after_attempt(3),
    wait=wait_exponential_jitter(initial=1, max=10),
)
async def fetch_weather(city: str) -> dict:
    async with httpx.AsyncClient(timeout=5) as client:
        resp = await client.get(f"https://api.weather.example/{city}")
        resp.raise_for_status()
        return resp.json()
```

指数退避配合 jitter 能有效分散重试压力，避免多个请求同时涌入同一故障后端。

### 3. 加入熔断器

当连续失败达到阈值时，熔断器会短时间直接拒绝请求，防止继续无效调用。可以在装饰器外再包一层简易熔断器（或引入 `pybreaker`）：

- 失败次数超过 5 次 → 熔断打开，30 秒内直接返回降级结果。
- 30 秒后进入半开状态，允许一次探测请求，成功则关闭熔断，失败则重新计时。

对 Agent 而言，这意味着当外部 API 严重故障时，几十秒内都不会再触发耗时调用，用户体感明显变好。

### 4. 准备降级数据

并非所有工具都需要返回最实时的数据。一个天气查询机器人，缓存最近一次查询结果，在 API 不可用时返回缓存并带上时间戳，对用户来说比显示「服务错误」有用得多。

实现上，每次成功调用都把结果写入本地缓存（如内存字典、Redis），并设置较长的过期时间（如 24 小时）。当熔断器打开或所有重试耗尽时，直接返回缓存数据，并附加标记 `status: "stale"`。

### 5. 在 Agent 提示中明确降级行为

工具返回降级数据后，Agent 需要知道该如何向用户表达。在系统提示中增加一段约束：

> If a tool result contains `status: "stale"`, you MUST inform the user that the data may be out of date, when it was last updated, and advise them to try again later. Do not present stale data as current.

这样 Agent 会自然地生成「上一次查询是在今天上午 10 点，现在暂时无法更新，请您稍后再试」这样的话语，用户体验连续且透明。

### 6. 超时与资源控制

每个工具调用必须设置硬超时。OpenClaw 对插件的默认超时可能过宽，建议在装饰器或 HTTP 客户端层面精确控制，例如 `timeout=8`，超过即失败并进入重试逻辑。避免整个 Agent 线程被长时间阻塞。

## 踩坑点

- **重试风暴**：如果多个 Agent 实例共享同一个后端 API，仅靠客户端重试会让故障 API 雪上加霜。必须配合全局熔断器（如通过 Redis 共享状态），或在网关层做限流。
- **缓存穿透与雪崩**：缓存过期瞬间大量请求直达故障 API，会导致短暂熔断抖动。可使用永不过期但后台异步刷新的缓存模式，或给过期时间加上随机偏移。
- **熔断状态丢失**：内存中的熔断器在进程重启后清零，冷启动时可能立刻冲垮尚未恢复的后端。建议将熔断状态持久化到外部存储，或至少文件持久化。
- **Agent 误用降级数据**：如果提示约束不够强，Agent 可能把非实时数据当作实时数据做重要决策。务必在返回降级数据时明确标记，并在提示中反复强调。

## 可复用建议

在 OpenClaw 体系中，你可以把这些策略封装成一个「韧性工具包装器」插件或 MCP 中间件。所有工具只需在注册时声明元数据（`retryable=True`, `circuit_breaker_group="weather"`），就可以自动获得：

- 指数退避重试
- 熔断器保护
- 超时控制
- 降级到 `fallback_handler`
- 统一返回结构化错误信息

此外，接入监控（如记录每次降级/重试事件，输出到日志或指标系统）并设置告警，能让你在 API 健康度恶化时第一时间获知。

配置不要硬编码：重试次数、退避间隔、熔断阈值、超时时间全部通过环境变量或配置文件给出，方便在不同环境微调。

## 总结

AI Agent 的可靠性不在于模型本身永不出错，而在于当外部依赖出问题时，系统知道如何体面地降级并保持可用。把重试、熔断、缓存降级和清晰的提示结合起来，通常可以覆盖 90% 以上的 API 故障场景。

在 OpenClaw 灵活的插件机制下，这些韧性策略完全可以沉淀为一套可复用的模块。下次你的 Agent 再遇到第三方服务宕机，也许用户根本注意不到——而这正是工程优雅的地方。
