# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景：健忘的 Agent 与破碎的体验

大多数基于 LLM 的自动化 Agent（包括用 OpenClaw 搭建的各类助手）在会话之间是没有记忆的。每次新对话都是从零开始的“金鱼模式”：你不知道用户是谁，不知道他的编码风格、命名习惯、技术栈偏好甚至常用的配置路径。用户每次都要手动交代背景，体验割裂，也限制了你把 Agent 真正嵌入日常工作流的可能。

MCP (Model Context Protocol) 的出现，让 Agent 能够调用外部工具和资源，包括读写本地文件、操作数据库甚至连接第三方服务。这为构建一个工程化、可控的记忆系统提供了基础设施。但记忆不是简单的“把聊天记录存起来”，需要分层设计、权衡隐私与效用，并保持可维护性。

## 问题拆解：记忆不是聊天记录回放

实现偏好记忆，核心要解决这几个问题：

- **长短期分离**：对话内即时上下文 vs 跨会话持久偏好，不能混用 context。
- **记忆衰减与纠正**：用户偏好会改变，过时记忆必须能更新，不能成为固化噪音。
- **隐私边界**：本地记忆相对安全，但若通过 MCP 连接外部存储，需要确保脱敏。
- **注入成本**：长期记忆会占用系统提示词 token，影响推理速度和费用，必须精炼。

## 工程做法：三层记忆架构

我会用一个轻量但工程化的三层结构，在 OpenClaw 代理中落地，完全基于本地文件和 MCP 工具。

**1. 短期记忆（会话内）**  
就是当前对话的历史消息，由框架自动维护。不需要额外处理，但注意 OpenClaw 中可通过 `max_context_messages` 控制长度，避免会话过长导致的上下文膨胀。

**2. 中期记忆（会话摘要）**  
每次会话结束或达到一定轮次时，用 LLM 压缩对话为结构化摘要，保存到本地 JSON 文件。摘要包含：本次对话涉及的项目、修改的关键配置、用户提到的习惯（比如“我喜欢用 yarn 而不是 npm”）、待办事项。

**3. 长期记忆（用户档案）**  
这是持久化偏好层，存为 `~/.openclaw/agent/user_profile.json`，内容高度结构化：

```json
{
  "preferences": {
    "package_manager": "yarn",
    "editor": "cursor",
    "language": "typescript",
    "code_style": "no semicolons, single quotes"
  },
  "projects": {
    "/Users/john/work/api-server": {
      "stack": "Express + Prisma + PostgreSQL",
      "env_file": ".env.local"
    }
  },
  "recent_topics": ["MCP server 权限控制", "本地 RAG 搭建"]
}
```

这个结构不是一次性填满，而是通过会话摘要逐渐聚合。

## 具体步骤（OpenClaw + MCP 落地）

1. **注册 MCP 工具：记忆读写**  
用一个小型本地 MCP 服务器，暴露两个工具：`get_user_profile` 和 `update_user_profile`。服务器直接读写上面的 JSON 文件，加入简单的加解密（如用 `crypto` 模块基于机器 ID 做对称加密），防止明文泄露。

2. **在系统提示中注入记忆摘要**  
在 OpenClaw 的 `system_prompt` 模板中，动态插入：

```
当前用户档案：
- 偏好：使用 yarn，代码风格无分号单引号，常用 TypeScript
- 近期项目：api-server (Express + Prisma)
- 最近关注：MCP 权限控制
```

这部分内容需严格控制长度（建议不超过 300 tokens），通过摘要提取关键条目，而不是倾倒全部原文。

3. **会话结束时的记忆更新钩子**  
利用 OpenClaw 的事件回调（比如 `on_session_end`），触发一个“反思”动作：
- 调用 LLM 生成本次会话的结构化摘要（仅提取新偏好或变更）。
- diff 现有档案，仅更新变化的字段，避免重复写入。
- 自动清理超过 30 天未确认的临时偏好（标记为 `stale`，下次使用时询问用户）。

4. **用户可主动管理记忆**  
提供 `/profile` 命令，Agent 会输出当前存储的档案，并允许用户直接纠正：“把我的 package manager 改成 pnpm” 会直接写入长期记忆。这比纯自动推理可靠得多。

## 踩坑实录

- **记忆污染**：Agent 误把闲聊中的假设当成偏好固化。  
  **解法**：长期记忆仅通过显式确认或反复出现的模式才写入，而不是单次提及就记录。可设置一个置信度阈值（比如 3 次观察到统一行为才写入）。

- **注入 token 爆炸**：档案体积增大后，每次都全量注入系统提示，成本骤升。  
  **解法**：基于上下文相关性动态选择记忆注入。比如当前对话路径匹配到某个项目目录，才注入该项目相关的偏好几条，其他忽略。或者使用 `mem0` 这样的轻量向量检索库，把记忆条目向量化，按相似度取 top-k。

- **多设备同步**：本地 JSON 无法跨机器。  
  **解法**：如果多设备需求强，可将 MCP 服务器改为读写加密后的远程存储（如 S3 + 客户端加密），但复杂度上升。初期建议单机为主。

- **隐私泄露风险**：日志或错误信息中可能打印出明文档案。  
  **解法**：在 MCP 工具返回时，仅返回必要片段，禁止完整 dump。对日志系统设置脱敏规则。

## 可复用建议

1. **从最低可行记忆开始**：只记录三个字段（名称、技术栈偏好、常用编辑器），验证流程跑通再扩展。
2. **把记忆和配置分离**：项目级信息（如 `.env` 路径）属于“项目上下文”，不要和个人偏好混存。
3. **提供遗忘机制**：用户输入类似“忘记我喜欢用的包管理器”，应该即时移除对应条目，并写入审计日志。
4. **版本化记忆结构**：`user_profile.json` 加 `"version": 1`，方便未来迁移，避免字段冲突。

## 总结

为 OpenClaw Agent 添加偏好记忆，本质是构建一个“可写、可检索、可遗忘”的用户模型。借助 MCP 的小工具和本地文件，不需要引入重型数据库就能实现分层、可控的记忆系统。关键在于：用结构化替代全文、用确认机制兜底、用衰减策略保持新鲜。一旦 Agent 能记住你的编码习惯和项目上下文，它会从偶尔的玩具变成日常流水线里真正可信赖的节点。
