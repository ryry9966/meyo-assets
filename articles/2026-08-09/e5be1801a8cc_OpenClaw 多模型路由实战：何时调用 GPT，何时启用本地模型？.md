# OpenClaw 多模型路由实战：何时调用 GPT，何时启用本地模型？

## 背景：多模型并存的必然难题

在基于 OpenClaw 搭建 Agent 或自动化流程时，你能同时接入云端大模型（如 GPT-4o、Claude 3.5 Sonnet）和本地模型（通过 Ollama、llama.cpp 等部署的 Qwen、Llama 系列）。云端模型能力强大，几乎可以胜任所有任务，但成本高、有网络延迟，还可能涉及数据隐私风险；本地模型完全免费、低延迟且数据不外泄，但能力上限较低，复杂推理容易胡言乱语。

单一模型无法同时满足所有场景。因此，在 OpenClaw 里做一套“按任务特征动态选择模型”的路由机制，就成了平衡性能与成本的关键。

## 问题：路由策略难在哪里？

理想很丰满，具体实现中会碰到这些现实问题：

- 任务复杂度难以量化，写几条规则远不能覆盖所有边缘情况。
- 本地模型响应质量不稳定，容易在错误路由下生产出不可用的输出。
- 频繁切换模型可能引入额外延迟（本地模型冷启动、API 握手等）。
- 路由逻辑容易和业务代码耦合，后期难以调整和维护。

我们需要一套轻量、可观测、易于迭代的路由方案。

## 做法：在 OpenClaw 中实现智能路由的步骤

### 1. 注册多个模型后端

在 OpenClaw 配置文件中定义好云端和本地后端，并为它们分配唯一标识：

```yaml
models:
  gpt-4o:
    provider: openai
    model: gpt-4o
    api_key: ${OPENAI_API_KEY}
  local-qwen:
    provider: ollama
    model: qwen2.5:7b
    base_url: http://localhost:11434
```

### 2. 定义路由规则

OpenClaw 的 Router 模块允许你根据条件表达式指定目标模型。常用分流维度包括：

- **任务意图**：闲聊、翻译、摘要 → 本地模型；多步推理、代码生成、复杂计算 → GPT
- **隐私要求**：涉及敏感数据时强制走本地模型（或先本地脱敏，再视需要调 GPT）
- **上下文长度**：超过本地模型可靠窗口（如 4k tokens）则切换到 GPT
- **用户指定**：允许通过指令或标签手动选择模型（例如“用本地模型回答”）

示例规则配置：

```yaml
routes:
  - condition: "intent in ['code_generation', 'multi_step_reasoning']"
    model: gpt-4o
  - condition: "intent in ['chitchat', 'translation', 'summarize']"
    model: local-qwen
  - condition: "contains_sensitive_data == true"
    model: local-qwen
  - condition: "context_tokens > 3000"
    model: gpt-4o
```

### 3. 在 Agent 流程中集成路由判断

一种工程化实践是在消息到达 Agent 核心逻辑前，加一层“意图分类器 + 路由决策”。这个分类器本身也可以用一个极轻量的本地模型来做，快速给输入打上意图标签和难度评分，几乎不增加延迟。

### 4. 建立回退机制

本地模型输出结果后，通过自动评估器（如输出格式是否合法、与允许回答的语义相似度等）给出置信度。若低于阈值（例如 0.7），自动回退到 GPT 重新生成，并将该次回退记录到日志。

```yaml
fallback:
  condition: "local_quality_score < 0.7"
  model: gpt-4o
```

## 踩坑点与应对

1. **本地模型能力错觉**  
   同一个 7B 模型对英文指令很听话，遇到中文复杂提问可能完全跑偏。路由规则中一定要限制本地模型的任务范围，不要放手让它处理长链条推理。

2. **冷启动延迟**  
   本地模型第一次推理需加载权重，可能耗时数秒。建议在 OpenClaw 服务启动时就预加载模型并保持长连接，或使用 keep-alive 机制，避免用户请求踩到冷启动坑。

3. **分类器本身会出错**  
   意图分类器置信度不高时，可能导致高级任务被错误路由到本地模型。解决方法是：分类器输出置信度也要评估，当置信度低于某个下限（如 0.8）时，直接上 GPT，或对用户追问以获得更明确意图。

4. **成本估算偏差**  
   即使本地模型处理了大部分任务，复杂 GPT 调用仍可能因长文本或思维链推理消耗大量 token。设置项目级每日预算告警，路由模块在额度快耗尽时自动降级到本地模型并通知维护者。

## 可复用建议

- **任务分级体系**：将任务按复杂度分为 L1～L3 三级，L1（闲聊、事实回答）默认本地，L2（摘要、翻译、简单问答）本地优先但允许回退，L3（推理、代码）强制 GPT。
- **日志驱动优化**：记录每一次路由决策、最终执行的模型、用户反馈（点赞 / 点踩）、回退次数。定期分析这些日志，调整规则，甚至训练一个专门的分流模型。
- **模型热替换**：本地服务故障时，路由自动切换到 GPT（成本上升但服务不中断）；GPT 额度耗尽或超时时，降级到本地模型并发出告警，保证可用性。
- **配置外部化**：将路由规则、阈值参数放在配置文件或环境变量中，避免硬编码，便于快速调整无需重新部署。

## 总结

多模型路由不是“要么用 GPT，要么用本地”的二选一，而是一套基于任务特征、成本、隐私的动态调度系统。在 OpenClaw 中，通过清晰的规则定义、轻量级意图分类和自动回退机制，你可以用较小的工程代价实现高效的模型调度，让强模型处理高价值任务，本地模型消化日常简单流量，最终在能力与成本之间找到符合业务需求的平衡点。

持续监控和规则迭代是这套系统长期可靠运行的关键，不要指望一次配置就万事大吉。
