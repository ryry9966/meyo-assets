## 背景：为什么需要多模型路由

在构建 Agent 或自动化流程时，单一模型很难同时满足成本、延迟、隐私和质量的要求。GPT-4o 能力强但调用成本高、延迟偶尔不可控；本地部署的 Llama、Qwen 等模型推理几乎零成本、数据不出域，但在复杂推理任务上容易翻车。

OpenClaw 的设计目标之一就是解耦模型接入与任务调度。它内置了可配置的路由层，允许我们在同一个 pipeline 里根据条件把不同的请求分发给不同的模型。经过几个项目的压测，我们逐渐摸出一套“什么时候该用 GPT、什么时候留给本地模型”的经验规则。

## 问题：没有一刀切的模型选择

刚接入多模型路由时最常见的错误是两极分化：一种是把所有任务无脑扔给 GPT，结果在 QPS 上来后账单直接炸开；另一种是出于成本或者数据安全考虑全部走本地模型，结果摘要、翻译等简单任务吞吐尚可，但一旦遇到需要多步骤推理的 Agent 任务，模型就开始“胡言乱语”，业务指标雪崩。

真正的问题不是选哪个模型，而是怎么在一个统一的入口里，根据任务特征自动做出合理的、可解释的决策。这就回到了 OpenClaw 路由能力的核心：条件路由 + 回退策略。

## 做法：用可观测信号驱动路由规则

我们的路由配置并不是拍脑袋写的，而是从真实流量里提取了几个关键信号，然后映射成规则。下面是一个可复现的实施路径：

1. **划分任务类型**  
   先对当前业务里的典型 prompt 做一遍标注，分成几个大类：闲聊/问候、简单事实问答、文档摘要、翻译、代码生成、多步推理 Agent、包含个人数据的请求等。这些类可以直接作为路由条件。

2. **提取路由信号**  
   OpenClaw 的路由配置支持基于 prompt 内容进行匹配，你可以定义多个 `matcher`：
   - 关键词匹配：例如 prompt 中出现“病历”“身份证号”“工资”等词，直接标记为敏感数据类，强制走本地模型。
   - 复杂度估算：通过 prompt 长度、是否包含“分析”“比较”“为什么”等词来粗略判断推理深度。
   - 上下文窗口需求：超过 4k token 的上下文，本地低配模型可能定位精度下降，适合切换到 GPT 或长窗口本地模型。
   - 显式指令：允许用户在 prompt 中用 `/gpt` 或 `/local` 主动指定模型（作为最高优先级）。

3. **配置 OpenClaw 路由规则**  
   在 OpenClaw 的配置文件中定义 `routers`，一个典型的简化示例：
   ```yaml
   routers:
     - name: main_router
       rules:
         - condition: "prompt.contains('PII_KEYWORD')"
           model: local_qwen_14b
           priority: 100
         - condition: "prompt.estimated_complexity >= 0.7"
           model: gpt-4o
           priority: 80
         - condition: "prompt.token_count > 3000"
           model: gpt-4o
           priority: 70
         - condition: "prompt.contains('/local')"
           model: local_qwen_14b
           priority: 100
         - condition: "true"
           model: local_qwen_14b
           priority: 10
   ```
   最后一条 `true` 作为默认兜底，保证任何请求都不会被拒绝。

4. **加入回退与缓存**  
   当 GPT 因为 rate limit 或网络抖动返回 5xx 时，配置自动回退到本地模型（同时触发告警）。对于幂等的查询类请求，我们在 OpenClaw 上游加了一层 Redis 缓存，命中后直接跳过模型调用，既降低延迟又省成本。

5. **数据驱动迭代**  
   路由规则上线后，我们会持续收集每条路由的“跳转原因”“模型耗时”“用户终止率”“后验评分”等数据，每周复盘调整阈值。例如初始设定的 `estimated_complexity >= 0.7`，可能因为本地模型升级成更强版本而提高至 0.85。

## 踩坑点

- **本地模型“不够听话”**  
  Qwen2.5 或 Llama3 系列在零样本格式下容易出现输出格式不稳定的问题，尤其当 prompt 中混合了系统指令和用户输入时。建议对本地模型统一做 few-shot 或 system prompt 模板化处理，否则路由过去的结果不可控，下游解析直接爆炸。

- **敏感信息匹配误判**  
  基于关键词的 PII 检测很容易出现漏杀或误杀。比如“血压”“年龄”本身不算隐私，但混在上下文里可能触发规则，导致本可走 GPT 的高质量分析被本地模型草草处理。补救方式：引入轻量 NER 模块作为前置过滤器，而不是仅依赖字符串匹配。

- **上下文窗口差异导致截断**  
  本地模型原生的 4096 窗口在复杂 Agent 场景里常不够用。虽然可以开启 RoPE 插值扩到 8k，但实际测试发现中间位置的信息检索衰减明显。所以一旦 prompt token > 3000，不管复杂度如何，我们宁愿走 GPT（128k 窗口）省去调试片段丢失的时间。

- **延迟预期不一致**  
  GPT-4o 首 token 延迟在某些区域可能超过 2s，而本地模型在低负载时 200ms 就能出字。这导致纯同步的 Agent 逻辑里用户体验跳变剧烈。我们的解法是对所有路由后的调用统一加超时控制和流式输出，并让业务侧按模型类别调节等待动画时长。

## 可复用建议

1. **先量化任务特征，再动手写规则**  
   不要凭直觉直接写“复杂就用 GPT”。花一周时间线上采样，标注 500–1000 条真实 prompt 的难度、长度和是否含隐私，然后基于数据分布设定阈值，比盲目配置有效得多。

2. **构建一个轻量级评估器**  
   可以在 OpenClaw 前面套一层极简的评估服务（甚至是一个 0.5B 的小模型或正则脚本）来计算复杂度分数，避免在路由配置里写过于冗长的逻辑。

3. **成本与质量的可视化监控**  
   用 Grafana 建两个核心面板：每个模型处理的任务量/成本占比、以及人工抽检的评分趋势。有了这两张图，产品和研发就能在同一套数据上讨论策略调整，不至于拍脑袋。

4. **以“本地优先”为基线，GPT 作为加速器**  
   如果没有强烈的实时推理要求，建议默认路由到本地模型，只有明确的条件触发才升至 GPT。这样既可以保证预算安全，也能倒逼本地模型的 prompt engineering 能力成长。

## 总结

OpenClaw 的多模型路由本质上是把“成本/隐私”和“推理能力”之间的权衡自动化。没有通用策略，但可以通过对业务信号的持续测量和一种“守门员+升级”的机制，让系统在大多数时候既快又省，关键时候又能调用 GPT 兜底。工程上最重要的不是选哪个模型，而是建立一套能够解释、调整、回滚的路由治理框架。
