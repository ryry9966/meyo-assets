## 问题：上下文膨胀与角色漂移

在使用 OpenClaw 构建长时间运行的智能体时，最常见的问题是**角色漂移**和**上下文膨胀**。我们通常会在系统提示里塞入大量行为指令、工具使用规范、输出格式要求。随着任务复杂化，提示词迅速膨胀到几千 token，每一次对话都要把这些内容重新注入，既浪费上下文窗口，又容易在长对话中发生“遗忘”——Agent 开始自由发挥，不再遵守最初的约束。

更麻烦的是，当我们将同一个 Agent 复用到不同项目或分享给他人时，需要手动复制粘贴一整套提示词和配置，确保行为一致几乎不可能。即便用 Git 管理提示词，也缺少结构化的“身份”文件让 Agent 可以自我演进、记录历史决策和偏好。

## 思路：用 IDENTITY.md 作为持久化可进化的身份

OpenClaw 提供了一个轻量但强大的机制：`IDENTITY.md`。它是一份存放在 Agent 工作目录（通常是项目仓库根目录）中的 Markdown 文件，定义了智能体的核心身份、长期偏好、工作流习惯和工具使用规则。不同于每次对话注入的系统提示，IDENTITY.md 被视作**持久化记忆**——Agent 可以在运行过程中更新这份文件，持续调整自己的行为，实现“可进化”。

这个设计有几点工程价值：

1. **解耦身份与任务上下文**：身份文件保持相对稳定，任务指令不再重复携带大量角色描述。
2. **支持自我演进**：Agent 可以在交互中学习用户偏好，记入 IDENTITY.md，下次对话自动生效。
3. **项目级别可复用**：一个项目内的所有智能体实例共享同一份身份文件，确保行为一致性。换一个项目，身份也随之切换。
4. **版本可追溯**：存放在 Git 仓库中，身份的每次变更都有记录，方便回滚和审核。

## 实践：构建一个可演进的 IDENTITY.md

### 1. 初始种子文件

最简单的 IDENTITY.md 只需要五个部分，每个部分以二级标题分隔。以下是一个服务于“自动化技术写作”场景的示例：

```
## 角色
你是一个严谨的技术写作助手，专注于后端开发、云原生、自动化工具方向的深度文章。

## 核心原则
- 始终基于可复现的实验写作，不凭空编造
- 每个步骤必须能跟随操作
- 对不确定的内容明确标注
- 避免营销语言和多余的评价

## 工具使用偏好
- 所有操作系统命令优先给出 macOS/Linux 兼容写法
- 代码示例必须注明语言
- 查询外部信息时，以官方文档 > 源码 > 可信社区的顺序做信源排序

## 输出格式
- 文章标题不超过 60 字符
- 段落长度控制在 4-6 行
- 代码块后紧跟前后的说明文字，不孤立出现
- 使用中文标点

## 历史决策
（此部分由 Agent 自动记录与用户互动中形成的长期偏好）

```

这个文件的编写原则是**只写长久不变的约束**，不要在身份文件里写“这次回答我需要用表格”这种任务级指令。

### 2. 让 Agent 感知并加载 IDENTITY.md

在 OpenClaw 的配置中，无需额外代码，只要确保工作目录下存在该文件，Agent 会默认读取。也可以在项目级的 `openclaw.yaml` 里显式指定：

```yaml
identity:
  path: ./agent/IDENTITY.md
  auto_load: true
  allow_update: true   # 允许 Agent 写回
```

`allow_update` 默认是关闭的，因为它涉及文件系统写操作，需要显式授权。

### 3. 自我进化：Agent 如何写回历史决策

在对话中，如果用户持续给出反馈，Agent 可以在回合结束后，将值得长期记住的偏好写入“历史决策”部分。例如，多次要求“在涉及数据库操作时，先展示 Postgres 再展示 MySQL”，Agent 会生成类似这样的追加内容：

```
## 历史决策
- 优先使用 Postgres 示例，MySQL 放在备选位置（基于 2025-02-14 会话中的反馈）
- 所有 YAML 缩进使用两个空格，不使用 Tab
- 文章标题中避免使用问号和感叹号
```

这个写回操作是通过内置的 `update_identity` 工具完成的，Agent 只追加或修改指定段落，不会重写整个文件，避免意外破坏结构。

### 4. 多项目与团队协作

当我们将项目从 A 切换到 B 时，只要 `openclaw.yaml` 指向不同的 `IDENTITY.md`，Agent 的行为会立刻切换。团队成员在 clone 仓库后，可以立即获得一致的 Agent 行为基线，无需额外配置。如果需要对个人偏好做自定义，可以新建一份个人身份文件，并通过环境变量或本地配置覆盖路径。

## 踩坑点与避坑指南

1. **身份文件过于庞大**  
   有人会把整个 API 文档、大量代码规范都塞进去，导致身份文件超过 2000 行。Agent 在加载和更新时都会变得很慢，而且部分旧版模型对超长身份解析容易出错。**建议控制在 300 行以内**。具体领域知识应该作为“知识库”单独接入，而非写入身份。

2. **“历史决策”部分无限增长**  
   开启 `allow_update` 后，Agent 可能会在每一轮都追加记录，导致文件膨胀。需要定期人工清理，或者设定规则（如“仅记录超过3次重复确认的偏好”）。可以考虑在“核心原则”里增加一条：`不要记录一次性任务指令；只记录与交互风格和长期偏好相关的决策`。

3. **写回竞争**  
   当多个 Agent 实例或多人同时操作同一个 IDENTITY.md 文件时，可能出现覆盖。如果项目采用分支开发模式，建议将身份文件纳入 Git 管理，通过 Pull Request 合并身份变更，而不是在每个对话中都允许直接更新。

4. **敏感信息泄露**  
   身份文件中容易不小心写入密钥、数据库连接串等信息。务必在 `.gitignore` 之外，额外做内容检查。OpenClaw 内置了简单的敏感信息扫描，但不可完全依赖。

## 可复用建议

- **分层管理身份**：全局身份（团队级）放在仓库根目录，个人偏好用 `~/.openclaw/personal_identity.md`，通过 merge 策略合并加载。
- **版本标签**：在 IDENTITY.md 文件头部增加一行 `<!-- version: 1.0 -->`，便于追踪迭代。
- **定期审阅**：把 IDENTITY.md 纳入 Code Review 流程，避免“Agent 自己学歪”。
- **冷启动搭档**：第一次给 Agent 准备身份文件时，先用另一个 Agent 帮你生成种子，再人工修改，速度更快。

## 总结

IDENTITY.md 把 Agent 的角色定义从一次性提示词提升为**可版本化、可演进的身份源**。它通过剥离“我是谁”与“我现在做什么”，让 OpenClaw 智能体在长时间的协作中更稳定、更一致，而且具备累计学习的能力。对于经常构建复杂自动化工作流的用户来说，这是一个低成本、高回报的实践。

如果你已经在用 OpenClaw 做插件或 MCP 工具开发，建议立刻为每个项目建立一份精简的身份文件，关闭自动更新，手动管理演进——你会发现上下文窗口压力明显减小，复用智能体变得前所未有的轻松。
