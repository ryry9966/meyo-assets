## 背景：一个自动化巡检项目引发的触发困惑

最近用 OpenClaw 搭建一套面向 Agent 的自动化巡检管线，场景很典型：  
- 每日 9:00 生成前一天的 SLA 报告  
- 每 30 秒探测一次关键服务的健康状态，异常时立即告警  
- 每小时同步一次 MCP 插件的配置快照

刚开始我图省事，所有任务都用 `cron` 触发器。结果两天后就出了问题：健康探测任务偶尔“消失”几分钟，日志里却没有任何错误；报告任务有一天因为时区配置偏差，推到了 17:00 才执行。排查一圈才意识到 —— 不是 OpenClaw 不稳定，而是 **cron 和 heartbeat 两类触发器的设计哲学不同，混用的代价很大**。如果你也在 OpenClaw 里跑定时自动化，这篇帖子或许能帮你少走弯路。

## 问题在哪

OpenClaw 的任务定义允许为每个管线指定触发器类型，常见的有两种：

1. **cron**：基于 UNIX cron 表达式的周期调度，适合“在特定时间点执行”。  
2. **heartbeat**：基于固定间隔的持续心跳触发，适合“以固定频率持续执行，并且需要故障快速感知”。

二者的关键区别不是“能不能定时”，而是 **时间语义** 和 **故障恢复行为**。  
- cron 关心的是“在哪个时刻做”，错过一次要等下一轮。  
- heartbeat 关心的是“每隔多久必须成功一次”，如果上次执行失败或系统暂停，恢复后会立即补跑（取决于配置），更像一个健康守护。

在我那个项目里，健康探测用 cron 的问题就是：如果 OpenClaw 执行器那几秒刚好因为资源争抢被阻塞，cron 认为“当前时间点已过”，就直接跳过本次触发。结果就是探测真空期长达几十秒，线上监控出现盲区。而把心跳任务换成 heartbeat 后，即使单次延迟，引擎仍会尽快补偿触发，恢复连续性。

## 做法：正确配置两种触发器

### 1. cron 配置要点

在 OpenClaw 的任务配置（通常是 YAML）里，一个典型的 cron 调度长这样：

```yaml
trigger:
  type: cron
  expression: "0 9 * * *"
  timezone: "Asia/Shanghai"
  # 任务执行超时保护
  timeout: 600s
  retry:
    max_attempts: 2
    backoff: 30s
```

日常里最容易踩的坑就两个：  
- **表达式错误**：想表达“每小时一次”写成 `* */1 * * *`（实际是每分钟一次），正确的是 `0 * * * *`。  
- **时区被忽略**：默认时区很可能是 UTC，所以 `0 9 * * *` 变成本地 17:00，务必显式设置 `timezone`。

适用场景：日报生成、定期数据同步、MCP 配置定时刷新等“日历驱动”的任务。

### 2. heartbeat 配置要点

心跳触发器关注的是“间隔”而不是时刻：

```yaml
trigger:
  type: heartbeat
  interval: 30s
  # 当连续三次心跳未成功触发时产生告警
  missed_threshold: 3
  on_missed: alert
  # 心跳任务建议设置较短的超时，避免堆积
  timeout: 20s
```

这里有几个工程实践：
- `interval` 不能小于任务平均执行时间的 2 倍，否则会出现执行重叠。  
- `missed_threshold` 能避免因瞬时抖动频繁报警，一般设置为 3~5。  
- 心跳里的 `action` 必须是**幂等**的，因为异常恢复后可能会连续执行多次。

适用场景：服务健康探测、Token 保活、Agent 存活看门狗、流式数据窗口触发。

### 3. 什么时候两个都用？

对于复杂管线，可以 **组合**。比如用 cron 触发一次全量数据同步（每天一次），然后用 heartbeat 监控该同步是否在预定时间完成，如果未完成则升级告警。这样实现了“日历触发 + 健康守护”的双层保障。

## 踩坑记录

1. **cron 的“跳过陷阱”**  
   如果在触发时刻执行器繁忙，cron 不会补跑。所以对于不允许跳过的间隔性任务（如状态上报），务必用 heartbeat。

2. **heartbeat 的“叠加风暴”**  
   如果 heartbeat 间隔 10 秒，任务执行却花了 25 秒，OpenClaw 会不断堆积新触发，可能导致资源耗尽。解决办法是启用 `timeout` 和 `concurrency_policy: forbid`（禁止并发），让超时直接终止慢任务，下一轮健康触发正常进行。

3. **时区不一致导致排查困难**  
   cron 用 `Asia/Shanghai`，heartbeat 日志却打印 UTC 时间，排障时要统一换算。建议在任务级统一打点带上本地时间戳。

4. **忘记 heartbeat 的“首次触发延迟”**  
   heartbeat 并不会在程序启动瞬间就触发，而是等一个 `interval` 后才执行第一次。对于需要立即探活的场景，可以搭配一个 `startup` 触发，或选用其他机制。

## 可复用建议

- **判断清单**：如果任务是“按日历发生”（每早 9 点、每月 1 号），用 cron；如果是“持续检查某条件”（每 N 秒看一次服务是否活着），用 heartbeat。  
- **防错配置模板**：任何 cron 任务必须写 `timezone`；任何 heartbeat 任务必须设 `timeout` 且小于 `interval`。  
- **监控兜底**：对两种触发器都接入 OpenClaw 内置的执行计数器，在监控中比较“预期触发次数”与“实际成功次数”，及时感知跳过或堆积。  
- **幂等是底线**：不论哪种触发器，任务本身要做到至少一次执行幂等，避免补跑造成数据重复。

## 总结

cron 和 heartbeat 看起来只是两种触发方式，但在 OpenClaw 这类面向 Agent/自动化持续运行的系统里，它们决定了任务对延迟、跳过、恢复的行为特性。不敢说哪个更好，只能说选错了修复成本很高。如果你正在运营一个同时包含报告生成和存活探测的项目，建议立刻检查一遍任务清单：该用 heartbeat 的地方，是不是还在勉强用 cron。
