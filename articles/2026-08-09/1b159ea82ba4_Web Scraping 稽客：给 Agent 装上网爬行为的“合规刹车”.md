# Web Scraping 稽客：给 Agent 装上网爬行为的“合规刹车”

## 为什么 Agent 需要一个“稽客”层

在 OpenClaw 的自动化实践中，Agent 越来越频繁地承担信息采集任务：定时抓取竞品更新、聚合多源数据生成报告、为 RAG 管道补充最新网页内容。通常的做法是直接给 Agent 一个 `fetch` 工具或 Playwright MCP server，让它自行决定如何抓取。这样做很快，但很快也会翻车——Agent 可能会在几秒内对同一个域名打出上百次请求，完全无视 robots.txt，直到 IP 被 ban、任务中断，或者更糟，引发合规问题。

问题不在于采集本身，而在于缺少一个**安全稽核层**。Agent 擅长决策，但不擅长约束自己。我们需要在 Agent 和真实网络之间插入一层“稽客”（Scraping Auditor），它不替 Agent 做业务决策，但负责在每一次出站请求前检查合规策略、执行速率控制，并在异常时优雅降级，而不是直接崩掉整个工作流。

## 设计一个可被 Agent 调用的稽客工具

我们以 OpenClaw 典型的工具调用方式为例，把稽客层封装成一个轻量的 MCP server，内部实现两个核心工具：

- `safe_fetch(url: str, options?: FetchOptions) -> FetchResult`  
  执行一次合规的 HTTP GET，返回文本内容与元数据。
- `safe_extract(url: str, schema: dict) -> StructuredData`  
  在 safe_fetch 的基础上，按给定的 schema（如 CSS 选择器或 XPath）提取结构化字段，降低 Agent 直接处理原始 HTML 的风险。

这两个工具让 Agent 不再直接接触网络细节，而是通过一个安全闸门进行采集。

### 稽客层的三条主线

**1. 请求前的合规检查**

每次 Agent 调用 `safe_fetch`，稽客服务首先检查目标域名对应的规则。做法是维护一个基于域名的轻量级策略缓存，规则来源包括：

- 实时解析目标站点的 `/robots.txt`，提取 `Disallow`、`Crawl-delay` 等字段；
- 加载本地配置文件（白名单、黑名单、特殊站点策略），用于补充或覆盖 robots.txt。

实现上需要注意：robots.txt 不能每次请求都重新下载，否则稽客本身变成一种滥用。一个简单的 LRU 缓存，按域名存储解析结果，过期时间设为 30 分钟，就能在合规和性能间取得平衡。对于不支持通配符的粗糙解析器，务必将 `*` 和 `$` 结束符处理正确，否则会漏拦路径。

**2. 请求中的速率与连接控制**

即便 robots.txt 没有声明 Crawl-delay，稽客层也必须内置一个保守的默认策略——对同一域名至少间隔 2~5 秒，控制并发连接数，防止 Agent 在循环中意外发起洪水式请求。

具体实现可以用令牌桶或滑动窗口，按域名独立限流。当 Agent 短时间内重复调用同一域名时，稽客层会延迟响应，直到获得令牌。这保证了即使 Agent 以低效的方式连续调用，也不会伤害目标服务器。

**3. 异常响应与自适应降级**

Agent 最怕的是“卡死”。如果目标返回 429，原生 fetch 可能直接抛异常，Agent 要么盲目重试，要么中断整个任务。稽客层应当内置退避逻辑：遇到 429、503 或带有 `Retry-After` 头的响应，自动等待并重试，最多 3 次，重试间隔指数增长。若仍然失败，返回带 `status: blocked` 的 FetchResult，而不是异常。Agent 看到这个状态，就知道需要更换数据源或向用户求助，而不是无休止地循环。

对于 403、401，稽客层直接标记为不可访问，并附带原因。这样 Agent 的规划器可以设计分支逻辑：`if result.status == 'blocked' then skip`.

## 实战踩坑：别小看动态渲染和反爬指纹

在实际落地中，最大的坑来自“静态 HTTP 请求够不着，动态渲染又太危险”。

很多现代站点依靠 JavaScript 渲染内容，纯 HTTP 拿到的是空壳或加载骨架。Agent 为了提取数据，会倾向使用 headless browser（如通过 Playwright MCP）。但一旦引入浏览器环境，反爬指纹（WebGL、字体、navigator 属性）就暴露出来。即使采用 stealth 插件和代理，也极易被识别为 bot，导致验证码反弹或 IP 直接进黑名单。

在这里我们的建议是保守的：**除非业务确实需要动态交互，否则不要为 Agent 开启 headless 模式**。如果必须有动态内容，应将其隔离到独立的渲染服务中，并配上严格的资源白名单和请求签名，确保不会意外触发反爬机制，也便于监控“重武器”的使用频次。

一个工程化的折中方案是：优先尝试 `safe_fetch`，如果检测到页面内容过短或缺失预期字段，再触发一次带标记的轻量渲染（比如仅执行必要 JS，关闭图片/字体加载），并严格限制渲染超时。同时，为渲染实例绑定独立的、经过指纹混淆的上下文，降低检测风险。

另外，代理池使用也是一个容易忽视的成本点。很多团队以为加上代理就万事大吉，结果代理 IP 质量参差不齐，大量请求超时，反而拖慢 Agent 节奏。应当在稽客层内置健康检查，定期从代理池剔除失败率高的 IP，并允许为关键任务配置直连白名单，减少不必要的跳转。

## 可复用建议：将稽客做成标准化 MCP 插件

为了不在每一个 Agent 项目里重新发明轮子，最务实的做法是将上述稽客逻辑抽离成一个标准化、可配置的 **MCP server**。它提供：

- 声明式站点策略文件（YAML/JSON），支持按域名配置：
  ```yaml
  sites:
    example.com:
      allowed_paths: ["/docs/*"]
      crawl_delay: 10
      proxy_required: true
      render: false
    public-data.io:
      allowed_paths: ["/api/*"]
      proxy_required: false
  ```
- 插件化的解析引擎：默认采用 cheerio/BeautifulSoup 类库，可选集成渲染能力，但须显式开启。
- 统一的调用审计日志：记录每次采集的 URL、时间、耗时、响应码、数据量，便于事后排查和合规自证。

Agent 制作者只需将这个 MCP server 挂载到 OpenClaw 会话中，用 `safe_fetch` 替代原生 `fetch`。Agent 的行为立刻受到约束，但又完全感知不到背后的复杂策略。两者之间的契约很简单：Agent 负责告诉稽客“我要什么数据”，稽客负责“安全地取回来”。

## 总结

给 Agent 加上“稽客”层，本质上是在自动化效率和合规安全之间加了一组可复用的闸门。它不是要限制 Agent 的能力，而是让它可以大胆地规划采集任务，因为这些任务每一次出站，都会被一个冷静的中间层拦截、检查、节流、优雅降级。在真实工程环境中，这样一层看起来“不性感”的基础设施，往往是决定一个 Web 采集 Agent 能否稳定跑过三个月的关键。

如果你正在用 OpenClaw 搭建数据采集管线，不妨从一个小而硬的稽客 MCP server 开始——它可能比你想象中更早地为你挡下一口违规的锅。
