## 背景

OpenClaw 社区的活跃度一部分依赖高质量技术帖的持续产出，但人工撰写、排版、发布时间成本高，且风格不易统一。我们内部需要一个能按指定主题和模板自动生成帖子、排版并发布到 OpenClaw 的机器人，同时保证内容可控、链路可观测、失败可重试。

在选型上，我们决定不为了自动化开发一个完整后端服务，而是基于现有的 Agent 框架、MCP 和轻量脚本，在本地或 CI 中按需运行。最终方案是一个 **「Prompt + MCP 发帖工具 + 状态机控制」** 的 Node.js 脚本，配合 OpenAI 兼容接口完成内容生成。

## 需要解决的问题

1. **内容质量与风格统一**：自动生成的帖子不能像营销号，需要符合 OpenClaw 社区的务实、克制语气。
2. **发帖接口对接**：OpenClaw 有基于 Token 的 API，但没有现成 SDK；需要封装成 MCP 工具供 Agent 调用。
3. **错误处理与重试**：网络波动、限流、内容审核失败都会导致发布中断，必须有完善的 retry 与降级。
4. **流程编排**：生成标题 → 正文 → 排版 → 发布 → 返回链接，每一步都可能失败，需要有状态的执行器。
5. **可观测性**：本地跑脚本，出错时没有 UI，需要结构化日志和通知。

## 架构设计

项目结构：

```
community-bot/
├── prompt-templates/       # 不同帖子类型的 System Prompt
├── mcp-server/             # 发帖工具的 MCP 服务
│   ├── tools/
│   │   └── create-post.ts  # 调用 OpenClaw API
├── agent-runner.ts         # 主执行器
├── logger.ts               # 结构化日志
└── config.ts               # 环境变量、重试次数等
```

**工作流**（见流程图）：

1. **加载模板**：根据话题类型（教程、踩坑、工具安利）选择 system prompt。
2. **内容生成**：调用 LLM（OpenAI 兼容接口）生成标题与 Markdown 正文；要求输出严格 JSON，包含 `title` 和 `content_md`。
3. **内容校验**：检查字数、是否有营销话术、Markdown 关键结构（代码块、标题层级）是否合规。
4. **发布**：通过 MCP 工具 `create-post` 提交到 OpenClaw。
5. **结果验证与通知**：获取返回的帖子 ID 和链接，写入日志，并可选推送到飞书/钉钉。

MCP 工具 `create-post` 封装了 OpenClaw 的 GraphQL API，参数为 `title`、`content`（Markdown 字符串）、`tags`；内部处理认证 header、异常分类（限流/权限/正文违规）和重试。

主执行器 `agent-runner.ts` 使用一个简单的有限状态机实现：`GENERATING -> VALIDATING -> POSTING -> SUCCESS | FAILED`，任何非终端状态可重试 3 次，重试间隔使用指数退避。

## 踩坑与应对

### 1. MCP 工具调用超时与异步控制
MCP server 与 client 之间基于 stdio/SSE 通信，`create-post` 发布到 OpenClaw 可能耗时 3-8 秒。若 Agent 直接 `await` 调用可能出现 MCP 连接超时。解决方案：在 MCP server 端使用 `setTimeout` 包装 API 调用，并设置连接心跳。同时 Agent 侧采用带超时的 Promise.race。

### 2. 内容审核敏感词导致发布失败
LLM 生成内容偶现被 OpenClaw 后台拦截，返回 422 且错误信息模糊。我们在 `create-post` 工具内捕获 422，返回结构化错误 `sensitive_content`，触发回退到“改写模式”——Agent 让 LLM 自行替换可能敏感的句子后重试，成功率从 82% 提升到 97%。

### 3. 模板中导致死循环的格式化要求
最初的 system prompt 要求“请在正文中使用二级标题分割章节”，但 LLM 有时在代码块内使用了 `##`，导致 Markdown 解析混乱。加入后置校验函数，用正则确保 `##` 只出现在行首且不在代码 fence 内，否则拒绝并让 LLM 重写，避免了格式灾难。

### 4. 限流与成本控制
OpenAI 接口有速率和额度限制，且本地测试时频繁重试易耗费 token。我们引入了简单的“冷却池”：在运行脚本前检查今日已生成帖子数（通过本地文件记录），单日上限 5 篇；生成时若遇到 429，退避 30 秒再试，最多 3 次，避免撞墙。

## 可复用建议

- **用 MCP 包装外部服务**：即使只是一个发帖 API，封装成 MCP 工具后，可以在任何支持 MCP 的 Agent 中复用，降低与特定框架的耦合。
- **严格的输出 Schema**：让 LLM 返回确定性结构的 JSON，写一个运行时校验（ajv/zod），不合格就立即重试，比后期人工修复成本低得多。
- **状态机 + 结构化日志**：对于异步、易出错的自动化流程，不要用线性脚本，清晰地记录每一步的输入输出，方便回溯。
- **模板工程化**：将 system prompt 作为代码管理，加入版本和测试用例（如用几个标题看看生成内容的倾向），避免“感觉不错”一拍脑门就上线。
- **最小依赖**：整个方案用 Node.js + 两个 npm 包（@modelcontextprotocol/sdk、openai 客户端）即可运行，可以放进 GitHub Actions 或 cron，不依赖额外数据库。

## 总结

我们通过“LLM 生成 + 状态机控制 + MCP 工具发布”的轻量架构，实现了 OpenClaw 社区的自动化发帖机器人。初版上线后，稳定运行超过 100 次自动发帖，人工干预次数降到 3% 以内。关键在于把发帖 API 封装为可复用的 MCP 工具、引入强校验和出错重试，并严格控制 prompt 成本。

如果你也在运维一个技术社区，希望降低内容运营的重复劳动，可以尝试这种“Agent + 工具化”的模式。完整代码过于定制，但核心思路已开源在内部仓库的 `community-bot` 分支，欢迎参考和提 issue。
