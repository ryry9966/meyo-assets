## 背景

在维护多仓库、多服务 Agent 项目时，最容易被忽视却又最消耗认知资源的，是每日的进展汇总。多个协作工具、命令行历史、CI 结果——信息散落在各处，等你手动缝合。而一旦要整理日报，你才发现自己花在复原上下文上的时间，可能比写报告本身还多。

更典型的场景是：我们的 OpenClaw 实例在后台持续运行任务链，每个 MCP 插件调用、Agent 决策点、外部 API 状态码都有日志留存，但它们是“扁平”的。从这些碎片的、时序错位的原始记录，到一份可交付的日报，中间缺的正是一条结构化抽取与组合的流水线。

## 问题拆解

我们真正要解决的，不是“用大模型写日报”这么笼统，而是以下三个工程问题：

1. **日志聚合与清洗**：多来源（终端日志、MCP 工具返回、数据库记录）如何汇聚成统一 Schema。
2. **任务级切片与归属**：如何把一个工作周期内的多条日志按“任务”聚合，避免时间线被打乱。
3. **可配置的结构化输出**：不同项目对日报的格式需求不同，不能每次改 prompt，需要一个稳定的数据模型。

最后，这套流水线要能作为 MCP 或插件无缝接入现有 Agent 体系，而不是又增加一个外部依赖。

## 做法与步骤

我们设计的流水线分为三个阶段：**采集 → 切片 → 组装**，并以一个 JSON Schema 作为中间表示。

### 1. 采集：统一日志入口

对 Agent 运行时，我们在关键节点注入日志钩子。以 OpenClaw 的任务链为例，在 `on_plan_start`、`on_tool_call`、`on_tool_result`、`on_error` 处写入 JSON lines，每条包含：

- `timestamp`（ISO 8601）
- `session_id`（用于区分同一进程内的不同对话或任务）
- `event_type`（start / tool_use / tool_result / error / complete）
- `payload`（结构化细节，如工具名、参数摘要、结果前 200 字符、错误码）

同时，CI 日志、Git 操作日志也通过简单脚本统一为相同 Schema 并发送到本地的轻量日志文件或 stdout。我们刻意没有引入队列或日志中心，保持零外部依赖，便于调试。

**踩坑点**：多进程或多线程环境下，`session_id` 如果依赖全局变量容易错乱。最佳实践是使用 `contextvars`（Python）或类似机制，在任务创建时绑定会话 ID，并确保所有日志钩子能读取到。

### 2. 切片：按任务聚合

采集到的日志是按时间顺序交错的。切片模块读取 JSON lines，按 `session_id` 分组，并在组内按时间排序。关键是确定“一个任务”的边界。我们的做法是：

- 一个 `session_id` 下，首个 `event_type == start` 标志任务开始。
- 遇到 `complete` 或下一个 `start`（如果上一条任务没有正常结束）作为任务结束。
- 同一会话内，工具调用、错误信息都关联到该任务。

这样我们就得到了一个任务列表，每个任务物化为一个字典，包含：时间线、使用的工具列表、状态（成功/失败）、关键结果摘要等。

**踩坑点**：跨天任务的归属。如果日报是按自然日划分，任务可能跨零点。我们的策略是：以任务结束时间为准，归属到结束那天的日报。同时提供一个选项，允许按开始时间归属，用于周报聚合。

### 3. 组装：从结构化数据到报告

有了任务级中间表示，最后的“组装”就变成了一个简单的模板填充过程，而非推理过程。我们定义了日报 Schema：

```json
{
  "date": "2025-03-28",
  "summary": "string",
  "tasks": [
    {
      "id": "session_xxx",
      "goal": "从日志推断或从 start 事件中提取",
      "status": "completed | failed | partial",
      "tools_used": ["tool_a", "tool_b"],
      "key_results": ["result_1", "result_2"],
      "errors": ["error_detail"]
    }
  ],
  "risks": ["risk_desc"]
}
```

对于大部分项目，直接通过字典键拼接 Markdown 即可。如果需要自然语言润色，我们可以挑选性地调用轻量模型，但**只摘要**，不改动事实结构。我们使用一个固定的 system prompt，输入 JSON，输出一段不超过 180 字的中文总结。这样做的好处是：总结出错不会污染结构化数据，也更容易审查。

最终日报通过模板引擎渲染为 Markdown，可推送到飞书/钉钉或作为 Issue 创建。

### 4. 接入 MCP 或插件

我们把这个流水线封装成一个 MCP server，提供 `generate_daily_report` 工具。参数很简单：

- `log_source`：日志文件路径或 stdin 读取
- `date`（可选，默认当日）
- `output_format`：`markdown` / `json`

OpenClaw 的 Agent 可以在每日末尾自动调用该工具，或者由用户触发。由于全部本地运行，日志不会外泄，适合内部项目。

## 踩坑总结

- **不要过早引入 AI 做结构调整**：先建立严格 Schema，确保人类可读可调。AI 适合“摘要”和“润色”，不是核心管道。
- **时区处理**：所有 timestamp 务必使用 UTC 并加上偏移量，否则跨天切片会错位。一劳永逸的做法是在日志生成时就带上 `tz_offset`。
- **工具结果截断**：日报不需要完整工具输出，但截断策略不当会丢失关键信息（比如状态码）。我们保留前 500 字符，并抽取特殊标记如 `"status": "error"` 作为结构化字段。
- **模板的维护**：日报格式总在变，不要把格式化逻辑硬编码。我们使用 Jinja2 模板文件，用户可以自行修改。

## 可复用建议

1. **先建 Schema，后写代码**：这件事上，数据模型一旦稳定，后面都是管道工作。
2. **把日志注入做成 SDK 级别的能力**：如果你的 Agent 还没有统一日志钩子，建议立即抽象出 `emit_event` 函数，所有插件和 MCP 工具统一使用。
3. **日报只做聚合展示，不要兼任监控**：不要把错误告警逻辑塞进日报生成，职责单一才能稳定。
4. **保留原始日志**：日报是快照，原始日志是来源。生成报告后归档，便于回溯。

## 总结

从原始日志到结构化日报，一条工程上可行的流水线并不复杂。核心在于用**中间 Schema**解耦采集与呈现，用**切片逻辑**解决时间线交错，用**最小化 AI 介入**保证可控性。把它封装成 MCP 工具后，OpenClaw Agent 就有了“自我总结”的能力，而这背后没有黑魔法，只有一条仔细设计的管道。

如果你也在维护多个 Agent 日常任务，不妨试着从标准化日志钩子开始，让日报成为随取随用的产物，而不是每日消耗心力的杂务。
