## 0 前言

一件事越来越常见：你给 Agent 接入了代码库、文档、任务看板，它自主执行任务，顺手还帮你在社区或公开频道发了条消息。那条消息里，可能带着某段内部代码的注释、半成品的 API 密钥，或一段从未对外开放的内部流程描述。这已经不是“AI 有幻觉”的问题，而是你的系统在公开空间里裸奔。

这篇文章面向已经在用 OpenClaw / MCP / 插件做自动化的同学，不讲概念空谈，只聊工程上可以立刻落地的红线规则，以及我亲自踩过的坑。

## 1 问题是怎么发生的

典型的泄露路径不是 AI 故意泄密，而是任务指令边界不清、输出通道混用。

举个例子：你让 Agent “根据最新的日志分析结果，在社群里同步一下最近 24 小时的处理情况”。Agent 去读取了内部监控面板的数据，然后生成一段文本，调用社区发帖工具发出。问题是那段文本里可能直接包含了：

- 未脱敏的主机名、内网 IP、服务端口；
- 内部告警策略的触发阈值；
- 某个客户项目代号与其真实业务细节；
- 数据库连接串或 token（代码里注释没删干净）。

在 MCP server 具备“读取文件”和“发送消息”两种工具时，只要 prompt 里没有严格隔离，这种组合会变成常态。

另一个高发场景是 Agent 被允许“搜索并引用本地知识库”去回答公开频道的问题。它会把内部 FAQ、设计文档的原文直接贴出去，而这些原文的受众原本只是内部同事。

## 2 三条必须写进 Prompt 的安全红线

我把实践中反复撞过南墙的规则精简为三条，直接写在 System Prompt 的最前面，作为强制约束。注意不只是一句“不要泄露信息”，而是给出具体决策边界。

### 红线一：严禁跨域传递未脱敏数据

- **定义**：任何从内部存储（文件系统、数据库、环境变量、私有 API）读出的内容，未被人工或规则明确标记为“可公开”的，一律禁止写入面向外部的通道（社区发帖、公开 PR 评论、公开 issue、外部邮件等）。
- **判断标准**：如果数据来源是 `internal/*`、`secret/`、`env/` 命名空间，或来自非 `public` 标记的知识库条目，就视为内部。Agent 必须拒绝转述。
- **强制动作**：遇到跨域请求时，Agent 必须先输出一行 `[SECURITY_CHECK] 来源:内部，目标:外部，已拦截`，并停止执行。

### 红线二：引用内部文档时必须二次抽象

- **问题**：Agent 经常直接粘贴整段内部文档，尤其是当用户问“解释一下这个流程”时。
- **规则**：可以解释流程逻辑，但禁止原样输出未经脱敏的内部文档段落。任何从内部文档提取的信息，回答时只能给出间接概括，不包含实际路径、配置参数、人员名单、私有 URL。
- **实例**：✅ “我们的发布流程包含三道检查：健康检查通过后，先更新 staging，再灰度到生产。” ❌ “先调用 http://ci.internal.company.com/api/trigger?token=abcd，等待 Jenkins 返回 200。”

### 红线三：工具链输出必须先过过滤器

- 所有可能直达外部频道的工具（发帖、发邮件、创建公开 issue）在调用前，必须把最终消息体交给一个独立的“内容审查”工具或函数检查。
- 这个过滤器需要检查：是否有类似 `token=`、`password=`、`secret=` 的键值对；是否有内网 IP（10./172./192.）；是否有内部代码路径；是否连续出现高 entropy 字符串。
- 过滤器返回“通过”或“拒绝+原因”。Agent 只有收到“通过”才允许真正发出去。

## 3 工程落地的具体做法

只说规则还不够，需要有工程配套，否则 Agent 很容易绕过去。

### 3.1 在 MCP 工具层做权限拆分

不要把“读内部文件”和“发公开消息”的权限放在同一个 MCP server 内，更不要让同一个 tool call context 同时拥有两者。实践方案：

- 创建两个独立的 MCP session：`internal-read` 和 `public-write`。
- 在 Agent 任务执行时，分别通过不同的子代理（sub-agent）承担只读和只写角色，中间由主控 Agent 负责安全检查与脱敏转述。
- 子代理的 system prompt 各自独立，`public-write` 代理没有访问内部知识的权限，只能接收主控传来的、已经经过过滤的纯文本。

### 3.2 给所有外部输出通道加上结构体限制

社区发帖、公开文档编辑等外部写操作，只允许接受结构化的输入体，例如：

```yaml
title: string
summary: string (max 200 chars)
body: string (pre-sanitized, no markdown links to internal domains)
```

强迫 Agent 在生成内容时就做拆分，而不是随意发送一个自由文本 blob，这样可以减少无意中塞进内网地址的概率。

### 3.3 在 CI / 运行时加一层后置检测

即使有前面所有规则，也不要信任 Agent 的输出。在消息真正发送到外部平台之前，插一个轻量级检测步骤（可以是函数调用、webhook）：

- 正则匹配高危模式（密钥格式、内网 IP、内部域名）；
- 调用一个本地大模型做一次快速的“是否包含敏感信息”的二分类判断（消耗很小，但能保住底线）；
- 检测到风险则拦截并记录，发送告警给人工负责人，而不是直接放行。

## 4 我踩过的几个坑

1. **提示词护栏太软**：最早我只写了“不要泄露内部信息”，Agent 直接理解为“可以泄露，但要做总结”。必须给出操作级禁令，且要明确判断标准。
2. **工具描述泄漏**：MCP tool description 如果写得太详细，比如 `query_internal_dashboard(metric_name, host)`，agent 会自己构造参数去拉数据然后贴出去。工具描述本身也需要脱敏，或者工具返回时自动加上 `[INTERNAL ONLY]` 标记让 Agent 识别。
3. **忽略复制粘贴的惯性**：Agent 在回答流程类问题时，会直接复制它刚读取到的内部流程文档，因为那是训练数据里“最佳回答”的模仿模式。必须用 few-shot 示例教它区分抽象解释和原文复制。
4. **社区平台本身的消息体可以绕过审查**：有些平台支持 markdown 链接，Agent 可能用一个链接文字覆盖内部 URL，点击后才会发现。所以后置检测必须对 URL 做解析，拦截明显指向内部的链接。

## 5 可复用的最小安全包

如果你正在搭建自己的 Agent 自动化，可以直接复制这套组合：

- **System Prompt 插入块**：三条红线（上文）直接放在最前面，后面才是角色设定和任务描述。
- **MCP 架构拆分**：内部读取与外部写入独立 server，权限最小化。
- **公开写函数包装**：所有外发动作都走一个统一的 `send_public_message(payload)` 函数，内部先调用检测。
- **运行时正则 + 轻量模型检测**：在发消息前进行 must-pass 检查。
- **日志与告警**：所有被拦截的消息都记录完整上下文，并发送通知到内部监控频道，方便事后改进 prompt 或规则。

## 6 总结

Agent 安全的红利期已经过了，现在进入的是每次公开交互都可能暴露内部资产的阶段。与其被动等出问题再补救，不如从一开始就把安全设计到工具链和 prompt 的骨子里。

三条红线，两层权限拆分，一个后置过滤器，这并不复杂，但能防止大部分让人后背发凉的泄露场景。关键是别只写在安全文档里，要刻进 Agent 每一次 tool call 的执行路径里。
