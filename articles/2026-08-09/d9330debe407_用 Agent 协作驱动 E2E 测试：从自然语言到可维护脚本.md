## 背景

端到端（E2E）测试一直是保障复杂 Web 应用质量的重要手段，但编写和维护 E2E 脚本的成本非常高。界面一变，选择器就失效；异步加载、弹窗、鉴权状态让脚本脆弱不堪。OpenClaw 社区里，大家已经在用 Agent + MCP 完成浏览器自动化、数据抓取、报告生成等任务，这些能力能否直接迁移到测试场景，让 AI 帮我们写 E2E 测试？

答案是能，但需要一套工程化的 Agent 协作流程，而不是简单地向大模型扔一句“帮我测一下登录功能”。最近我基于 OpenClaw 生态和 MCP 插件，尝试了一套双 Agent 流水线：一个负责分析需求和生成测试步骤，另一个负责将步骤转为可执行脚本并自我修复。本文将分享这套方案的落地方案、踩坑经验和可复用的工程建议。

## 问题

手工编写 E2E 测试的痛点显而易见：
- 写用例枯燥，覆盖业务分支容易遗漏；
- 页面改动后，大量选择器需要人工检查修复；
- 测试环境经常被人肉调试污染，数据准备和清理逻辑复杂。

用 AI 直接生成测试代码也有硬伤：大模型不熟悉你的页面 DOM 结构，生成的定位器可能是臆想的 `#login-btn` 或 `.submit`，跑起来直接失败。即使让 AI 读页面快照，它也很难处理动态变化、异步渲染和鉴权跳转。

因此，我们不能期望一个 Agent 完成所有事，需要把“理解需求”“操控浏览器”“生成代码”“修复错误”拆解到不同 Agent 或工具上，形成协作回路。

## 做法：双 Agent + MCP 流水线

### 1. 架构概览

```
用户描述 ──> Agent A（需求分析师）──> 测试步骤（自然语言）
         ──> Agent B（测试执行者）──> 调用 MCP 浏览器工具
             ├── 操作页面，生成选择器
             ├── 输出 Playwright 脚本初稿
             └── 执行失败时启动自愈流程
```

- **Agent A**：根据用户对某个功能的描述，结合预设的页面上下文（如关键路由、页面元素摘要），输出一份分步骤的测试场景，格式为“Given-When-Then”。
- **Agent B**：拥有一个 MCP 浏览器工具（如基于 Playwright 的 `mcp-server-playwright` 或自建的 `browser-mcp`），可以导航、点击、输入、截图、获取页面快照。它读取 Agent A 的步骤，逐步操作浏览器，并在每一步记录真实的选择器、等待策略，最终拼出可执行的 Playwright 代码。

这种协作让生成的选择器来自真实页面，极大降低了幻觉。

### 2. 关键步骤

**步骤 1：准备页面上下文**

让 Agent 了解被测页面的关键结构。可以预先用无头浏览器抓取每个页面的可交互元素（input、button、link 的文字、测试 id），生成一个轻量地图，喂给 Agent A。例如：

```json
{
  "login": {
    "url": "/login",
    "elements": ["input[data-testid=username]", "input[data-testid=password]", "button[type=submit]"]
  }
}
```

**步骤 2：需求转测试步骤（Agent A）**

提示词示例：

> 你是一个测试分析师。根据下面给出的页面元素清单和用户需求，生成 E2E 测试步骤，使用 Given-When-Then 格式。只使用页面清单中存在的元素。

结合结构化页面信息，Agent A 输出的步骤会更靠谱。

**步骤 3：步骤转可执行脚本（Agent B + MCP）**

Agent B 使用 MCP 工具依次执行每个步骤，例如：
- `navigate` 到 URL
- `click` 某个按钮（根据文本或测试 id 定位）
- `type` 输入内容
- `screenshot` 验证状态

在执行每一步前，它会先获取当前页面的可交互元素快照，再把这一步的意图与快照一起交给大模型，由大模型决定使用哪个选择器。这样就能适应每次加载的微小差异。

最终 Agent B 输出完整的 Playwright 脚本，并附带每一步的注释和选择器。

**步骤 4：自愈修复**

第一次生成的脚本可能有因异步超时、弹窗干扰等导致的失败。我们为 Agent B 增加一个“执行-观察-修复”循环：运行脚本，捕获失败截图和日志，再交给大模型分析，并要求输出修复后的脚本。一般经过 2–3 轮即可稳定。

## 踩坑点

1. **选择器稳定性**  
即使有页面快照，大模型仍可能倾向于使用 CSS 类名或文本定位，而这些容易变化。我们在提示词中强制要求优先使用 `data-testid`，若不存在，才使用文本或 ARIA 角色。同时，在生成脚本时注入自动等待逻辑，避免硬编码 `sleep`。

2. **MCP 工具调用的权限与状态管理**  
测试过程中可能需要登录态，而 MCP 服务器是无状态的。解决办法是让 MCP 工具支持 Cookie 注入，或者在启动浏览器上下文时加载保存的存储状态。注意不要将包含敏感信息的存储状态写入日志。

3. **复杂交互处理**  
拖拽、文件上传、iframe 切换等操作，MCP 工具可能未封装。可以扩展自定义 MCP 工具，或在生成的脚本中手动补充这部分逻辑，让 Agent B 仅负责常规 UI 操作。

4. **幻觉复现**  
Agent A 可能虚构不存在的页面元素。除了提供精确的页面地图外，还可以在生成步骤后让 Agent B 执行一次“空跑”，只验证元素是否存在，不执行操作，提前发现不存在的元素。

## 可复用建议

- **MCP 工具设计**  
  将浏览器操作封装为 `browse_navigate`、`browse_click`、`browse_type`、`browse_snapshot` 等语义清晰的工具，并在描述中注明需要测试 id 优先。这样任何 Agent 都能复用同一套工具做测试或数据抓取。

- **测试数据工厂**  
  配合 MCP 工具实现数据准备接口（例如 `db_reset`、`api_seed`），让 Agent B 在测试前调用这些工具达到可重复状态，真正实现无人值守。

- **提示词模板化管理**  
  将 Agent A 和 Agent B 的系统提示、用户提示模板化，并注入项目特有的常量（如基础 URL、公共服务密钥）。这样不同项目只需更换配置文件即可复用流水线。

- **人工抽查关**  
  AI 生成的 E2E 脚本最终应进入代码仓库走 Code Review。可以实现一个 CLI 工具，将 Agent B 生成的脚本作为 PR 提交，由开发者审核选择器的合理性和业务逻辑覆盖度。

## 总结

通过 Agent A 需求分析 + Agent B 浏览器操作加代码生成的协作方式，我们成功将 E2E 测试的编写效率提升了数倍，且生成的脚本因为使用真实页面定位，维护性明显高于纯 LLM 直接输出的代码。搭配 MCP 浏览器工具，这个方案在 OpenClaw 生态中落地性强，不妨一试。当然，目前方案仍然需要人工审查，未来如果加入视觉回归和更智能的自愈机制，有望做到完全自动化的 E2E 测试维护。
