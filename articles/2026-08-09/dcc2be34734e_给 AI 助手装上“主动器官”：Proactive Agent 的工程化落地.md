## 背景：从“你问我才答”到“还没开口就办好”

当下大多数 AI 助手仍然停留在一个默认的交互范式里：用户发出指令 → 模型推理 → 执行动作 → 返回结果。这一请求/响应循环在聊天场景下工作得很好，可一旦把 Agent 放到巡检、运维、研发辅助、个人效率等真实工作流里，就显得笨拙——真正需要自动化的，往往是那些**根本不值得让人主动开口**的事。

一个典型的例子：某服务日志里出现特定错误码超过 3 次，就应该自动重启服务并通知值班人。如果这事每次都要等你自己发现再手工去问 Agent：“帮我检查一下错误日志，看看是否需要重启”，那 Agent 就只是个高级 grep。而如果能做到：**Agent 持续感知环境变化，满足条件时自主完成“感知→决策→执行→通知”闭环**，这就是我们要讨论的“proactive 能力”。

目前 OpenClaw/MCP/插件生态已为 Agent 提供了足够丰富的执行手段，但 proactive 这一环仍缺少开箱即用的范式。本文不推销任何服务，只讲在现有工具链下，如何用工程化手段为自己的 Agent 补上这缺失的一环。

---

## 问题拆分

要构建一个**生产可用的 proactive Agent**，至少需要解决四个问题：

1. **触发源从哪里来？**  
   定时（cron）、文件系统事件（inotify）、消息队列、Webhook、数据库轮询……  
2. **如何可靠地获取上下文？**  
   主动触发时，Agent 面对的不是用户刚提问的上下文，必须自行通过 MCP 工具、系统命令或 API 探查当前状态。  
3. **如何做决策？**  
   是简单规则（阈值触发）还是让 LLM 参与推理？能否在无人工干预时安全执行？  
4. **如何兜底与审计？**  
   误触发怎么办？执行失败如何回滚？谁来为一次自动行为的后果负责？

只有把这些问题都想清楚，proactive 才不会变成“proactive 灾难”。

## 做法与步骤

下面给出一个轻量但可复现的工程方案，基于 **OpenClaw Agent + MCP 工具 + 外部调度器** 的组合，不需要大改现有 Agent 核，就能跑起来。

### 1. 确定一个“无脑安全”的切入点

不要一上来就做“自动修数据库”。推荐从**纯观测 → 主动报告**过渡，例如：

- 每 30 分钟检查一次 API 可用性，连续失败 2 次发告警；
- 监听某个目录，有新文件时自动调用 OCR 提取文字并归档；
- 数据库表行数超过阈值时，主动生成摘要推送到企业微信。

这些场景的共同点：**破坏性低，价值感强，且容易回滚**。

### 2. 选择调度 / 触发机制

根据场景选方案：

- **定时类**：用 `systemd timer`、`cron` 或 Node.js 的 `node-cron` 召唤 Agent；
- **文件事件类**：`inotifywait`（Linux）/ `fs.watch` 监听，防抖后触发 Agent；
- **消息/事件驱动**：Redis Pub/Sub、Kafka、HTTP Webhook 推送给 Agent 入口。

调度器本身不包含智能，只负责在条件满足时，将**标准化的任务描述**送到 Agent。任务描述可以是自然语言 Prompt，也可以是结构化 JSON，例如：

```json
{
  "trigger": "disk_usage",
  "context": { "path": "/data", "usage_pct": 92 },
  "instruction": "检查磁盘空间，如果超过 90%，清理 7 天前的临时文件，并发送通知"
}
```

### 3. Agent 内核的设计要点

OpenClaw 的 Agent 天然适合做这件事，关键是把 **“接收结构化任务 → MCP 探查 → 决策 → 执行”** 这一流程固化成一次推理会话。

示例 Agent Prompt 骨架：

```
你是一个系统运维主动助手。你会收到一个任务描述。你必须按以下步骤执行：
1. 使用可用工具获取当前真实状态（不要仅依赖任务中的上下文）；
2. 如果状态与触发条件不一致，直接回复“误触发，跳过”，并记录原因；
3. 如果需要执行动作，先生成执行计划并解释影响；
4. 仅当影响评估通过后才执行；
5. 将执行结果通过通知工具发送给指定用户或频道。
```

这里最关键的一点是**第 2 步再次确认**，因为调度器给的状态可能已过时。你应该为 Agent 配备能够查询实时状态的 MCP 工具，比如 `mcp-server-commands`、`mcp-server-filesystem` 或自研的监控 MCP。

### 4. 安全与干预开关

在 Agent 真正执行破坏性操作前，设计两层防护：

- **全局 DRY-RUN 变量**：调度器下发任务时可携带 `"dry_run": true`，Agent 在计划阶段停止，不真的动手。测试通过后再打开；
- **人工确认 API**：对于高风险动作，让 Agent 生成一个“待审批”请求，推送到您的移动端，确认后才执行。这本质上是让人待在循环里（Human-in-the-loop），但自动化了前面 90% 的流程。

### 5. 全链路审计

每一条自动行为记录三样东西：触发条件、Agent 决策过程、最终执行结果。我们实践时会直接把 Agent 返回的整条消息持久化到 SQLite，并通过 MCP 日志工具打上标签，方便回溯“为什么当时 Agent 做了这个决定”。

## 踩坑清单

**1. 防抖不足，重复触发**  
文件监听场景下，一次拷贝可能触发多次事件。必须在调度层做 5-10 秒的 debounce，或者通过任务队列去重（以文件路径 + 事件类型做幂等键）。

**2. 上下文窗口膨胀**  
Proactive Agent 每次任务都从冷启动开始，若每次都将大量历史日志塞进上下文，Token 成本和推理时间会爆炸。建议**将历史压缩成结构化摘要**，或只传入触发事件附近的时间窗口。

**3. 权限混乱**  
调度器、Agent 进程、MCP 工具可能跑在不同用户下，导致文件操作、服务重启没有权限。统一用 systemd 服务管理，利用 `User=` 和 `Group=` 明确身份，必要时用 `sudo` 规则收窄权限。

**4. 把 LLM 当规则引擎用**  
如果判断逻辑明确（如硬盘 > 90% 就清理），不要用 LLM 做判断，直接在前置脚本里完成，只把“需要清理”这件事告诉 Agent。LLM 适合处理**模糊或需要编排多步骤**的场景，简单阉值会浪费且不稳定。

## 可复用建议

- **从通知类 proactive 起步**，逐步过渡到带有操作性质的；
- **任务标准化**，调度器和 Agent 之间只用约定好的 JSON 描述，降低耦合；
- **所有 proactive 行为默认带 `dry_run`**，确认后再放开；
- **把 proactive 能力当作一条独立产品线来维护**，而不是临时脚本堆砌。

开源生态已经提供了所有拼图：OpenClaw 负责 Agent 编排，MCP 负责工具连接，再搭配一个几十行的调度器，你就能拥有一个**在你睡觉时依然帮你干活的伙伴**。

---

## 总结

Proactive 能力是 AI Agent 从“对话玩具”走向“数字同事”的关键分水岭。目前的挑战不在模型能力，而在于**工程 discipline**：如何设计触发、如何保证动作安全、如何让系统可观测。一旦把这几块夯实，你会发现，最好的助手正是那些**什么都不用你开口，就能把活干完的**。
