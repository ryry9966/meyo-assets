# AGENTS.md：给 AI Agent 的工作空间说明书

## 背景

OpenClaw 的工作空间不只是给人类准备的目录与文件，它同样是 AI Agent 执行任务时的上下文来源。无论是通过 CLI、插件还是 MCP 工具链驱动 Agent，Agent 都需要理解项目的结构、约束与意图，否则很容易产生两类典型问题：

1. **行为越界** – Agent 误删文件、修改不该动的配置、在错误的分支上操作。
2. **意图错配** – Agent 反复询问已经定义好的规则，或者给出与项目约定相悖的输出。

AGENTS.md 就是为了解决这个断层而设计的。它是一份写给 AI 的手册，让 Agent 在工作空间内“自我定位”，不必每次都从零重建上下文。

## 问题：Agent 为什么需要一本说明书

在没有 AGENTS.md 时，你会不断遇到这些场景：

- 反复在 Prompt 中粘贴“不要碰 .env”、“HTML 统一放在 /templates 下”这类规则，效率低下且容易遗漏。
- 切换工作空间后 Agent 行为不一致，因为上下文没有结构化的迁移方式。
- MCP 工具或插件被错误调用，因为 Agent 不清楚当前项目允许哪些外部能力。

一份规范的 AGENTS.md 刚好能把这些“隐性知识”显式化，降低人机沟通成本。

## 做法与步骤

### 1. 放置位置与加载机制

AGENTS.md 必须位于工作空间的根目录。OpenClaw 在初始化工作空间上下文时会自动扫描根目录下的 AGENTS.md（某些插件还会向下递归查找），并将其注入到 Agent 的系统提示或上下文首部。

你可以用环境变量 `AGENTS_PATH` 覆盖默认路径，但这个功能目前仅在部分后端实现，建议保持根目录默认约定。

### 2. 文件结构模板

一份可落地的 AGENTS.md 应包含七个部分：

```markdown
# 项目概览
简要说明项目是做什么的，面向谁，运行环境。

# 目录约定
- `src/`：核心代码
- `static/`：只读静态资源
- `.env`：敏感配置，Agent 禁止读取或输出

# 硬约束
- 永远不要修改 .gitignore 或 .env  
- 不要执行任何涉及 `DROP`, `TRUNCATE` 的 SQL  
- 修改前端时保持 BEM 命名

# 常用命令
- 本地运行：`make dev`
- 跑测试：`pytest -x`
- 构建静态资源：`npm run build`

# 可使用的外部能力 (MCP / Plugins)
- 已连接的文件系统插件：有权读写 ./workspace
- 已连接的 GitHub MCP：可创建 Issue，但不能 push 到 main

# 输出格式要求
- 所有代码块标注语言类型
- 回答以中文为主，技术术语保留原文

# 当前任务上下文（临时）
- 本次会话聚焦修复 #42 的登录 Bug
```

### 3. 与 MCP 工具的联动

如果你的 Agent 挂接了 MCP 工具，AGENTS.md 里可以明确写出工具的白名单与使用限制：

```markdown
## MCP 约束
- 仅使用 `github` 和 `filesystem` 两个 MCP 服务
- `filesystem` 操作范围限定在 ./workspace/
- 禁止通过 `execute_command` 执行任何 sudo 或网络扫描命令
```

Agent 在读取这段说明后，会更准确地调用工具，避免 MCP 权限越界。

### 4. 多项目仓库的处理

在 monorepo 场景下，可以在每个子包根目录放置一个 AGENTS.md，同时在顶层 AGENTS.md 中定义全局规则。OpenClaw 的部分 Agent 实现会合并这些规则，优先级通常是子目录 > 根目录，冲突时以子目录的约束为准。

## 踩坑点

### 坑1：内容过长导致上下文污染

AGENTS.md 会被注入到每一次对话的上下文头部。如果文件超过 2000 行，会明显挤占有效 token，甚至引发 Agent 丢失中间对话内容。**建议控制在 300 行以内**，把详尽的开发文档放到 `CONTRIBUTING.md`，AGENTS.md 只保留 Agent 决策必需的约束。

### 坑2：格式不被解析

某些旧版插件只认纯文本 Markdown，不支持 YAML frontmatter 或 HTML 注释。如果你在 AGENTS.md 里用 `<!-- 注释 -->` 写备注，Agent 可能忽略或读取失败。安全做法是**全部用标准 Markdown**，结构依赖标题层级。

### 坑3：版本不同步

多人协作时 AGENTS.md 可能落后于实际项目结构。建议把它纳入 PR checklist —— 任何涉及目录重构、命令变更、安全策略调整的 PR 都必须更新 AGENTS.md 相应段落。

### 坑4：用 AGENTS.md 代替系统 Prompt

AGENTS.md 是**工作空间级**的静态说明，不适合放会话级指令（如“当前对话要生成测试用例”）。会话级需求应该放在当前任务上下文段落，并用一个明确标记（比如 `## 当前任务上下文`）隔开，Agent 实现会主动区分这两类信息。

## 可复用建议

1. **模板化**  
   维护一个 `AGENTS.template.md`，新项目复制即用，内容包含常规约束与空白待填项。

2. **与 README 分工**  
   README 写给人类看，AGENTS.md 写给 Agent 看。前者可以有徽章、图片、长段背景；后者只要命令、约束、结构。

3. **引用而非复制**  
   如果团队已有编码规范文档，不要在 AGENTS.md 复刻全文。写一句指向即可：“编码风格遵循 ./STYLE_GUIDE.md（Agent 可自行查阅）”。这样可以控制文件长度。

4. **结构化标记**  
   在每一段规则前用统一标记，例如：
   ```
   // RULE: 禁止修改 .lock 文件
   ```
   这条规则在解析时可以被提取为硬约束列表，目前 OpenClaw 的某些 Agent 后端已支持该语义。

5. **定期“狗粮”测试**  
   让 Agent 自身去审查 AGENTS.md：给它任务“按照 AGENTS.md 的约束，检查当前项目是否合规”。Agent 会指出矛盾或过时条目，形成自闭环维护。

## 总结

AGENTS.md 并不复杂，却能让 AI Agent 从“一次性的提问-应答”升级为可长期共事的工作空间伙伴。把项目潜规则写进一份结构清晰的文件，你会发现 Prompt 长度下降、Agent 行为更可预测，多 Agent 协作时的冲突也明显减少。

它不是一次性文档，而是伴随项目演进的“动态说明书”。把它当成工程基础设施的一部分来维护，收益会在日后的每一次自动化任务中体现出来。
