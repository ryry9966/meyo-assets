## 背景

团队每天需要从至少 4 个系统（CI/CD、生产日志、工单、Git 提交记录）拉取数据，拼成一份研发日报。早期靠人工汇总，后来用脚本硬编码，不出三个月就变成“脚本墓地”：每个数据源的鉴权方式不同、输出格式半年变三次、时区问题反复踩坑。我们需要一条能适应变化的流水线，而不是另一个需要长期维护的临时脚本。

本方案基于 OpenClaw Agent + 若干 MCP 服务器，实现“原始日志 → 结构化事实 → 日报草稿”的自动化链路。目标不是完全替代人，而是把机械汇总工作压缩到 3 分钟内，留出精力做人工复核与调整。

## 问题拆解

生成一份研发日报，实际上被拆成四个独立问题：

1. **数据获取**：多个异构数据源（REST API、数据库查询、日志文件）如何统一接入？
2. **解析与清洗**：原始日志格式混乱（JSON 嵌套、多行堆栈、非标准时间戳），如何稳定提取出“今天发生了什么”？
3. **结构化组织**：不同源的碎片事实如何按业务域归类，形成日报骨架？
4. **输出与分发**：生成 Markdown 草稿后如何自动推送至指定渠道？

直接让一个大 Agent 从零生成报告，幻觉率高且不稳定。我们选择用管道式拆分，每个环节可控可替换。

## 做法与步骤

### 1. 通过 MCP 服务器统一数据接入

我们没有为每个数据源编写独立插件，而是封装了三个轻量 MCP 服务器：

- `log-fetcher`：封装对 ELK/OpenSearch 的查询，返回指定时间窗日志。
- `git-recap`：调用 GitLab API，获取当日项目级别的提交记录、合并请求。
- `ticket-mcp`：拉取 Jira/TAPD 中当天的状态变更及阻塞项。

这些 MCP 服务器在 OpenClaw 中注册为工具。Agent 不直接接触鉴权细节，只通过标准化工具调用获取 JSON 数据。每获取一个数据源，Agent 立即写出中间结果到工作目录，防止上下文窗口溢满。这一步的核心经验是：**不要让 Agent 记得所有原始数据，它只负责调度与短路决策。**

### 2. 分步清洗与事实提取

原始数据进入本地中间文件后，我们调用第二个 Agent 示例（或同一 Agent 的独立任务）进行清洗。规则写成约束提示而非代码：

- 提取时间窗内的事件，时区统一转为 UTC+8。
- 忽略自动化机器人提交（commit author 白名单过滤）。
- 将 CI/CD 失败日志压缩成“服务名+错误摘要+关联工单号”。

此处遇到的典型坑：GPT 类模型有时会把堆栈中的哈希值当作“重要错误码”，反复写入报告。解决办法是增强 System Prompt 中的负面示例——“不要将 `0x7f3a` 类内存地址视为业务错误码”。**负面约束往往比正面描述更有效。**

### 3. 结构化骨架生成

清洗后的数据被汇总为一个 JSON 事实清单，包含：

```json
{
  "date": "2025-03-20",
  "deployments": [...],
  "incidents": [...],
  "code_changes": [...],
  "blockers": [...]
}
```

Agent 根据该清单生成日报骨架，严格遵循指定 Markdown 模板。模板固定四个段落：生产变更、异常与处理、代码推进、风险与阻塞项。模板内支持占位符 `{{range}}` 循环，由简单的 Go-template 引擎渲染——我们没有让 Agent 自行排版，避免每次输出格式漂移。

这里的关键选型：**模板引擎负责格式，Agent 负责“用自然语言润色摘要”**。两者职责分离后，日报风格稳定，Agent 的润色质量即使偶尔波动，也不会破坏整体结构。

### 4. 人工复核与自动推送

生成草稿后，系统不会直接发送，而是推送到企业微信的机器人私信，附带“一键发布/编辑/重生成”三个快捷按钮。按钮背后只是一个简单的规则引擎：如果 10 分钟内未处理，则自动以草稿状态归档，不发正式群。这个**静默超时机制**救了我们多次——有次一个数据源挂掉，草稿明显残缺，在自动发布前被拦了下来。

## 踩坑记录

**时区地雷**：日志源有的返回 UTC，有的返回本地时间，MCP 服务器未统一转换，导致“当日部署”被归入前一天。最终在 MCP 侧增加统一时区标准化层，工具返回的时间字段统一带上时区偏移量，Agent 只消费符合 RFC3339 的时间。

**Token 窗口过载**：一开始让 Agent 同时处理三个源的原始 JSON，1.2 万 token 的上下文导致漏掉后面数据。改造为逐个拉取-写出中间文件后，每步上下文控制在 2000 token 内，稳定性和速度明显提升。

**Agent 自创内容**：某次日志中根本没有数据库故障，Agent 却生成了“数据库连接池轻微抖动，已自动恢复”。原因是它把历史记忆中的模版句带入了当天报告。解决办法是明确指令：“当数据中不存在异常时，不得编造任何事件，直接填写‘无’。”并在生成后增加一个校验 Agent，对比事实清单与报告中的事件数量，差异过大时打回重试。

## 可复用建议

- **MCP 是好的抽象边界**：把数据源封装成 MCP 工具，成本不高，但能显著降低 Agent 直接面对脏数据的概率。
- **模板与生成分离**：日报结构用模板定死，Agent 只负责摘要文字，修改模板不需要重新调试提示词。
- **显式兜底机制**：凡是自动发布链路，必须保留人工确认或超时静默取消的出口，否则一定会出发布事故。
- **设计负面约束**：告诉模型“不要做什么”常常比告诉它“要做什么”更有效，尤其是避免编造。
- **中间文件可见**：所有中间 JSON 都存盘，方便事后排查“为什么报告里出现了这条”的问题。

## 总结

这条流水线跑了三个月，日报生成从每天 40 分钟人力降到 2 分钟复核。但它并不是一个“写完就丢”的工具——每月还是会因为上游系统格式微调而需要调整解析规则。自动化的真正价值，是把维护成本集中到少数明确的点上（MCP 服务器），而不是散落在脚本和提示词的各处。对于 OpenClaw 社区的用户，如果你手头有类似的重复汇总工作，不妨先抽象成“数据获取-清洗-结构化-输出”四段，然后用 MCP 工具承担前两段，用模板锁定后两段，体验会稳定得多。
