## 背景

多人协作的代码仓库中，“按规范开分支、写合格的 commit message” 是最基础也最容易失控的环节。规范文档写得再清楚，依然会出现 `fix bug`、`update` 这类无意义提交，或者分支名变成 `feature/test`、`dev1`，让 changelog 生成、回溯、code review 都变得困难。

OpenClaw 的 Agent 能力和 MCP 协议为我们提供了一个新思路：把 Git 仓库的部分操作暴露成工具，让 AI 助手在理解上下文后，根据团队规范自动执行分支创建、生成提交信息，甚至发起 Pull Request。这不仅能降低开发者的心智负担，还能从源头保障仓库历史的质量。

## 问题拆解

自动化 Git 要解决的几个核心问题：

1. **如何让 AI 安全地操作仓库？** 直接给 Agent shell 执行 `git` 命令风险太高，权限不可控。
2. **如何让 AI 读懂代码变更？** diff 内容可能非常大，超出上下文窗口。
3. **如何保证生成的结果符合规范？** 团队的分支命名、commit 格式各有约定，AI 必须知晓并遵守。
4. **如何处理异常和冲突？** 分支已存在、推送被拒绝等情况需要稳妥处理。

典型的工程化解法是：通过 MCP Git Server 暴露一组限定的、幂等性友好的工具，再在 OpenClaw 中配置一个专用 Agent，将团队规范写入 system prompt 和工具描述，形成「规则驱动 + 人工复核」的半自动化流程。

## 做法与步骤

### 1. 搭建 MCP Git 服务

选用社区实现（例如 `goplus/mcp-git`），或者用 Python 自建一个最小化 MCP Server，只暴露以下工具：

- `git_create_branch(base_ref, branch_name)`：基于指定引用创建新分支。
- `git_stage_and_commit(message, files?)`：暂存修改并提交，message 由 Agent 生成。
- `git_push(remote, branch)`：推送到远端。
- `git_get_diff(summary_limit=500)`：获取当前工作区与最近一次提交的差异摘要，而非完整 diff，避免 token 爆炸。

所有工具均限定在「非 force push、不删除分支」的权限范围内。启动时绑定特定仓库路径，避免跨仓操作。

### 2. 在 OpenClaw 中配置 Agent

创建一个专用 Agent，绑定上面的 MCP 服务，并编写详细的系统指令。例如：

```
你是一个 Git 自动化助手。以下规则你必须严格遵守：

分支命名规则：
- 新功能：feature/<描述>-<issue_id>
- 修复：fix/<描述>-<issue_id>
- 描述部分使用小写字母和连字符，如 feature/user-login-timeout-42

提交信息格式（Conventional Commits）：
<type>(<scope>): <subject>
- type: feat, fix, docs, refactor, test, chore
- scope: 模块名，如 auth, ui, api
- subject: 英文，不超过 72 字符，使用祈使语气

工作流程：
1. 用户告知任务“修复用户登录超时，关联 #42”。
2. 你生成分支名 fix/login-timeout-42，调用 create_branch 创建。
3. 用户完成开发后告知“可以提交了”，你调用 get_diff 获取变更摘要。
4. 根据摘要和用户任务描述，生成合规的提交信息，调用 stage_and_commit。
5. 用户确认后调用 push。

生成提交信息前，将候选 message 展示给用户确认，不要直接提交。
```

这种半自动方式既保留了 AI 的建议能力，又让人守住最后一道防线。

### 3. 渐进式引入

不建议一步到位让 Agent 直接 push。可以从「生成 commit message 建议」开始，例如开发者手动 `git add` 后，Agent 根据 `git diff --staged` 摘要输出一条 Conventional Commits 格式的 message，开发者复制使用。运行一两周，确认生成质量稳定后，再逐步开启自动提交。

对于分支创建，也可以先让 Agent 输出建议命令，开发者手动运行。只有在多次验证无误后，才允许 Agent 通过 MCP 工具直接创建分支。

### 4. 与现有工作流集成

OpenClaw Agent 可通过 CLI 或 HTTP 接口触发，很容易集成到 VSCode 插件、GitHub Actions 或聊天面板中。例如：

- 开发者在 Chat UI 中输入 `/branch fix login timeout #42`，Agent 生成分支名并创建。
- 在 pre-commit hook 中调用 Agent 分析 staged diff，返回推荐的 commit message，供开发者选择或修改。

## 踩坑与反思

在实际落地中，有几个容易忽视的问题：

- **diff 过大导致 token 超限**：一个功能分支可能修改十几个文件，直接喂给 AI 会超出上下文。必须做摘要或只提取变更文件列表、函数签名。我最终用了 `git diff --stat` 加关键文件的前 20 行变更，效果不错。
- **生成信息与真实意图偏离**：AI 看到的只是文本 diff，可能误判改动性质。例如，一个“重构”被识别为“修复”，因为修改了异常处理代码。所以必须要求用户用一句话描述任务，结合描述和 diff 共同生成 message。
- **冲突处理不能自动化**：当远程分支有新提交导致 push 被拒时，Agent 不应自行决定 merge 或 rebase。工具返回错误信息后，必须交给开发者处理。我们在 MCP 工具的错误描述中明确写了“请手动解决冲突后重新推送”。
- **分支名冲突**：如果分支已存在，create_branch 工具应当返回明确错误，并建议更名。Agent 接到错误后可以生成新名字再试，但最多重试一次，避免死循环。
- **安全性**：千万不要给 Agent `delete branch`、`force push`、`reset --hard` 等破坏性工具。最小权限原则是 MCP 工具设计的底线。

## 可复用建议

经过几个项目的试验，我觉得以下配置可快速在其他团队复制：

1. **将团队规范编码成字符串常量**，放入 Agent 的 system prompt 和 MCP 工具描述中，而不是散落在文档里。
2. **搭建 MCP Git Server 时使用 Docker 容器隔离**，每个 Agent 实例绑定一个临时工作区，操作完销毁，避免污染宿主机。
3. **生成提交信息时，强制列出变更文件列表**，让用户一眼判断 AI 是否遗漏或误判范围。
4. **日志记录所有 Agent 调用的工具参数和返回**，方便出现问题时回溯。
5. **优先在 feature 分支的个人仓库中试验**，成熟后再推广到共享仓库。

## 总结

Git 自动化不是要用 AI 取代开发者的版本控制意识，而是把重复、机械的部分（起分支名、拼 commit message、推代码）交给 Agent，让人聚焦在“改了什么、为什么改”的决策上。MCP 的标准化工具接口 + OpenClaw 的可控 Agent 行为，让这件事的工程成本变得足够低。下一步可以探索自动生成 Pull Request 描述、根据 issue 标签决定分支策略等更复杂的编排，但无论如何，**保留人工最终确认**这条底线在早期阶段绝不能丢掉。
