## 背景：AI 助手永远在“初次见面”

用 Agent 处理日常任务久了，你大概率经历过这些：每次都要重复“我是后端开发，偏好 Go 语言”“公司代码仓库在私有 GitLab，不要建议公开方案”“我的时区是 Asia/Shanghai”。明明已经解释过很多次，换一个会话、清一次上下文，一切又归零。这不是模型能力的问题，而是 Agent 缺乏一套工程化的记忆系统。

所谓记忆，不是把整段聊天历史塞进 prompt，而是在正确的时间，以最小的 tokens 成本，让 Agent 拿到真正相关的背景信息。这篇文章就基于我在 OpenClaw 插件体系和 MCP server 上的实践，聊聊怎么设计一套可落地的 Agent 记忆系统。

## 问题拆解：记忆到底要解决什么

我们把问题收敛成三点：

1. **跨会话遗忘**：上下文窗口是一种“工作记忆”，会话结束便消失。这导致频繁的手动重复说明。
2. **偏好污染 prompt**：为了让 model 了解你，一次性在 system prompt 里塞入大量描述，反而挤占推理空间，降低指令遵循度。
3. **动态演化缺失**：用户的偏好会变（“最近在学 Rust”），而静态设定无法反映这种变化。

目标很明确：让记忆成为 Agent 的基础设施，像文件系统一样，按需存取，不影响主流程。

## 三层记忆架构设计与实现

我在 OpenClaw 中落地了一套“会话记忆 – 用户档案 – 长期语义记忆”的三层结构，各司其职。

### 1. 会话记忆（短期）
这一层最简单，就是当前会话的完整对话历史。OpenClaw 的 `ConversationHandler` 本身就维护了一个消息队列，Agent 每次推理时会看到最近 N 轮对话。不做特殊处理，仅作为“上下文缓存”。

### 2. 用户档案（中期）
这是记忆系统的核心。每当会话结束，触发一个钩子（利用 OpenClaw 的 `SessionClosed` 事件），调 LLM 从对话中提取结构化的用户偏好摘要。提取 prompt 类似：

```
从以下对话中提取用户长期偏好，以 JSON 输出：
- 角色、技能栈、常用工具
- 明确要求（格式、风格、约束）
- 短期正在学习或关注的话题
仅输出新增或变更的信息，不要重复已有内容。
```

提取结果会合并到本地一个 `user_profile.json` 中，每条记录带有时间戳和来源会话 ID，便于回溯。下次新会话启动时，通过 `SessionStart` 钩子，把 profile 中最近活跃的条目（按时间衰减排序）注入到 system prompt 的动态区，而不是全量塞入。我一般控制注入条目在 5 条以内，每条不超过 60 tokens。

### 3. 长期语义记忆（长期）
当用户和 Agent 的交互积累到上千次后，依赖静态 profile 就不够了。我需要 Agent 能在具体问题出现时，主动去“回想”：“关于这个话题，以前说过什么？”

我把所有历史消息做了 embedding（用 bge-small-en），存入本地 Chroma 向量库。然后通过 MCP server 暴露两个工具：
- `memory_search(query: str, top_k: int)`：语义检索相关历史片段。
- `memory_add(doc: str, metadata: dict)`：手动添加重要记忆。

在 OpenClaw 的插件函数描述里注册这两个工具，Agent 就会在“需要回忆上下文”时自行调用。例如，用户问：“帮我配一下那个新服务器的 SSH alias”，Agent 会先调用 `memory_search("SSH alias 服务器配置")`，拿到之前讨论的服务器 IP 和命名规则，再给出建议。

## 避坑：四个容易翻车的地方

1. **偏好提取的噪声**  
   直接用通用 prompt 让 LLM 提取，容易出现“用户今天说了一句喜欢喝咖啡”也被写进技能栈。解决方式：明确领域限定（仅提取工作相关的技术偏好、工具链、项目约束），并加入 few-shot 示例，过滤掉日常闲聊。

2. **记忆更新冲突**  
   “我最近在学 Python”出现三次，profile 里不应该有三条。需要做去重与合并。我用的策略是：对新增条目计算相似度（可以用简单的 Jaccard + TF-IDF），相似度 > 0.75 时，只更新时间戳，不重复插入。

3. **检索相关性崩塌**  
   纯向量检索会把“GitLab CI 配置”和“GitHub Actions 使用”当成相似，但可能用户只关注 GitLab。所以必须在 metadata 里标记来源项目，检索时先用关键词过滤（metadata.project == "platform"）再语义排序，也就是混合检索。

4. **prompt 膨胀**  
   system prompt 越长，模型对指令的抓取越弱。记忆注入必须“吝啬”。每次按优先级和时效性准入，超过 token 预算就截断，确保核心 system prompt 不受污染。

## 可复用建议

- **从最简单的一层开始**：先做会话结束时的 profile 摘要提取和下次加载，立刻能感受到连贯性提升。长期语义记忆在对话量超过几百条后再引入。
- **结构化记忆格式**：统一用 `{ category, content, timestamp, priority, source }` 的 schema，便于后续扩展和过滤。
- **存储选型**：profile 用本地 JSON 就够了，语义记忆用 Chroma 或 LanceDB 本地部署，避免网络依赖和隐私风险。所有数据只留在本机。
- **与 MCP 结合**：把记忆操作封装成标准化工具，Agent 就能自主决定何时回忆、何时记录，而不是被动的写入读。

## 总结

好的记忆系统不是让 Agent 变成你肚里的蛔虫，而是让它礼貌地“记得上次说过的事”，并且在不打扰对话的情况下提供背景。分层设计、结构化存储和按需检索三个原则，能够在不显著增加复杂度的情况下，把 Agent 从每次“失忆”的循环里拉出来。在 OpenClaw 的插件和 MCP 体系下，这套方案可以插拔式地集成，不会侵入原有 workflow。

如果你正在折腾让助手更懂你，建议从一份简单的 profile JSON 开始，亲身感受记忆带来的体验跃迁。
