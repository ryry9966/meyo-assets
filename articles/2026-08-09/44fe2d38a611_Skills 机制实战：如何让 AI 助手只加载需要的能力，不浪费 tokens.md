# Skills 机制实战：如何让 AI 助手只加载需要的能力，不浪费 tokens

## 背景：能力膨胀带来的隐形成本

在基于 LLM 的 Agent 开发中，几乎所有生产环境都会遇到一个共同问题：随着系统功能越来越丰富，可用的工具（tools）、插件、知识源也越来越多。一开始可能只是查天气、发短信，后来加上了 CRM 查询、工单创建、数据分析、多语言翻译、合规审核……如果每次都把所有工具定义一股脑塞进 system prompt 或 function calling 的列表中，会直接导致：

- **上下文窗口被大量元数据挤占**，留给实际对话的空间减少
- **模型推理时注意力被分散**，工具选择准确率下降，甚至出现幻觉调用
- **tokens 成本线性增长**，每一次对话都在为永远用不到的能力付费

而且，并不是所有工具都适合用一句话描述就能安全触发。例如“删除用户”这种高危操作，必须只在极其明确的意图下才能被加载和调用，否则就是一颗定时炸弹。

OpenClaw 的 Skills 机制就是为解决这个矛盾设计的：它允许你定义一组“技能”，每个技能包含自己的提示词、工具集、约束条件，由框架根据当前任务上下文**按需激活**。它既不是简单的 prompt 拼接，也不是把路由逻辑全部交给开发者硬编码，而是一种声明式的、可组合的能力编排方案。

## 问题：什么时候你需要 Skills 而不是一股脑全带上

以下几种实际场景会让你明显感到“全量加载”的极限：

1. **多角色 Agent 系统**：同一个 Agent 可能要同时承担客服、运维、数据分析角色，每个角色的工具和语气要求完全不同，混在一起会导致模型行为错乱。
2. **动态工具集**：某些工具只在特定阶段存在（例如“提交审批”只在订单草稿阶段有效），全量暴露会让模型在不该调用的时候尝试调用。
3. **安全与最小权限原则**：敏感操作只应在当前任务确实需要时才出现在候选列表里，而不是一直挂着等模型误触。
4. **Token 预算极度紧张**：在手机上运行的轻量 Agent，或者高频调用的 API 服务，每一个 token 都要精打细算。

如果你手动在 prompt 里用 if-else 拼装工具，很快就会陷入管理地狱。Skills 机制把这些逻辑提升到框架层，用清晰的配置和生命周期来管控。

## 做法与步骤：定义一个按需激活的 Skill

在 OpenClaw 中，一个 Skill 通常由三个核心文件或块组成（以 YAML 声明为例）：

```yaml
# skills/order_cancel.skill.yaml
name: order_cancel
description: 处理订单取消请求，包括确认资格、执行取消、发放退款
trigger:
  keywords: ["取消订单", "退款", "不想要了"]
  intents: ["cancel_order", "request_refund"]
  required_context:
    - order_id
tools:
  - name: check_order_status
    source: ./tools/order_api.js
  - name: cancel_order
    source: ./tools/order_api.js
    dangerous: true
system_prompt: |
  你是一个订单取消助手。只有在用户确认要取消后，才调用 cancel_order。
  调用前必须先用 check_order_status 查询订单是否可取消。
  如果用户提供 order_id，优先使用；否则向用户索要。
```

加载到 Agent 时，框架并不会直接把所有 skill 的 system_prompt 和 tools 拼接进主 prompt。而是先由 **Skill Router** 根据用户输入和对话历史进行匹配，只把当前激活的 skill（以及通用基础配置）注入当次推理的上下文。

基本集成流程：

1. 在项目根目录或配置文件中指定 skills 目录，框架启动时扫描所有 `.skill.yaml`。
2. 根据 `trigger` 规则建立轻量级索引（关键词、正则、意图分类均可）。
3. 每次接收到用户消息，路由层计算匹配度，选定一个或多个 Skill（通常只有一个被激活，除非配置了协同模式）。
4. 将选中 Skill 的 `system_prompt` 拼接到通用 system prompt 之后，并将其 `tools` 列表加入当前可用的 function calling 定义。
5. 如果对话上下文发生重大转变（例如用户从询问订单转为投诉物流），路由层可以动态切换 Skill，并清理前一个 Skill 的专属状态。

## 踩坑点与真实调试经验

### 1. 触发规则过于宽泛
我曾为了方便测试，把关键词设成“订单”，结果所有关于订单的查询都命中，包括“我想下订单”。于是高频场景下，取消订单专用的危险工具一直被暴露。解决之道是**增加意图分类**（用一个小模型或规则引擎做二次确认），或在 trigger 中加入排除条件。

### 2. Skill 间的上下文污染
当两个技能共享相同的工具名称但实现不同时（例如都有 `get_user`），切换 Skill 后调用可能指向错误的函数。必须为每个 Skill 的工具增加唯一前缀（如 `order_cancel_get_user`），或者在 OpenClaw 的 tool registry 中启用命名空间隔离。目前推荐的做法是：工具定义跟随 Skill，不要使用全局共享工具，除非是明确的通用能力（如日志记录）。

### 3. 提示词片段拼合后的矛盾
基础 system prompt 说“你是友好的助手”，而 Skill 的 prompt 说“你只做订单取消，不闲聊”。模型可能会在这两个指令间摇摆。解决办法是在基础 prompt 中预留替换槽位，或让 Skill 的 prompt 以“**覆盖规则**”的口吻描述，并调高 Skill prompt 的权重（通过提示词层级实现）。

### 4. 频繁切换 Skill 导致 token 浪费
用户快速切换话题时，每次都要重新注入大量工具定义，反而比全量加载消耗更多 tokens（因为框架需要反复重写上下文）。这种情况需要设置**切换冷却时间**，或让路由逻辑更倾向于保留当前 Skill，除非意图发生剧烈变化。

## 可复用建议

- **粒度适中**：一个 Skill 对应一个明确的业务任务（如“取消订单”），不要过大成一个“电商客服”，也不要过小到一个 API 调用。
- **默认 Skill 永远存在**：处理闲聊、帮助、能力列表等，防止无 Skill 命中时 Agent 失语。
- **把危险工具放在独立 Skill 中**，并要求二次意图确认，这是最简单有效的安全防线。
- **编写 Skill 时同步写测试用例**：模拟典型对话，验证路由是否按预期激活和退出。
- **系统监控 Skill 切换频率**：频繁切换是设计不良的早期信号，可以设置告警。

## 总结

Skills 机制并不是一个花哨的概念，而是工程实践中逐渐收敛出来的必然模式。它把“按需加载能力”从硬编码的 if-else 解放出来，变成声明式配置与自动化路由的组合。对于已经感受到 token 成本和工具管理压力的 OpenClaw 或 Agent 项目，尽早引入 Skill 抽象，可以明显提升系统的可维护性和安全性，也让模型更专注于真正需要处理的任务，而不是在几十个工具中大海捞针。

最后一点经验：Skills 的设计是迭代出来的，不要试图一步到位。先从 2-3 个差异较大的业务场景开始切分，跑通切换和工具隔离流程，再逐步细化。
