# OpenClaw 的多模型路由：什么时候用 GPT，什么时候用本地模型

## 背景：单一模型的困境

在 OpenClaw 的生产环境里，如果你只接一个模型——不管它是 GPT-4-turbo 还是本地跑通的 Qwen2.5-72B——很快都会碰上边界。全部走云端 API，单日 token 账单比上班的咖啡钱还滚得快；全部走本地部署，遇到复杂长链 Agent 任务时 agent loop 能卡在半路，甚至返回“您的请求已成功处理，结果如下：null”。

OpenClaw 本身的设计并没有替你决定“该用哪个模型”，但它的 MCP 协议和插件体系为你留出了一块非常灵活的路由层。你完全可以在同一个 Agent 会话里，把“理解用户意图”交给 GPT，把“从工具返回的网页里提取结构化字段”交给本地模型，还不需要改一行业务逻辑。本文记录的就是我们在这个路由层上的工程选择，什么时候切 GRC（GPT Remote Cloud），什么时候切 LLC（Local Low Cost），以及怎么踩坑后还能跑稳。

## 问题：决策不在于“哪个模型强”，而在于任务剖面

不是所有的 prompt 都值得花 0.03 美金。真正需要路由判断的是任务的三维剖面：

- **认知复杂度**：是否需要深度推理、多步规划，还是简单分类/抽取/摘要。
- **上下文长度与连续性**：是否需要跨多轮维护相同 token 空间，否则路由切换会破坏思维链。
- **与工具的耦合程度**：本地模型对 MCP 工具定义 schema 的遵从度未必一致，出错后回退成本很高。

如果把这些维度都扔给 Agent 自己判断，结果就是“模型自举路由”，用昂贵的模型去决定是否使用廉价模型，路由开销比执行开销还大。工程上更务实的做法是把路由下沉到 OpenClaw 的中间件，利用静态规则 + 轻量信号完成首次分派。

## 做法：在 OpenClaw 里落地三层路由

我们的环境是这样搭的：

1. **模型接入**  
   通过 OpenClaw 的 MCP 服务端注册两个后端：  
   - `gpt-4-turbo`（Azure API，带监控）  
   - `llama3.1-70b`（Ollama 本地实例，4-bit 量化，单卡 3090）

2. **路由中间件**（`before_hook`）  
   在 OpenClaw 的任务管线里，我们在 `before_hook` 实现了一个无状态 Router 插件。它不调用任何 LLM，仅根据结构化信号做决策：

   - **路由键提取**：从上游 task payload 中拿到 `task_type`、输入长度、工具数量、历史失败次数、是否涉及 PII 字段等。
   - **规则引擎**：一个 YAML 规则集，核心规则类似：
     ```
     - if task_type in ["classification","extraction","format_conversion"] and context_len < 4000 → llama
     - if task_type in ["long_form_generation","complex_reasoning","code_synthesis"] → gpt
     - if has_tool_schema and model_compliance_score < 0.9 → gpt  # 本地模型对某些工具 schema 服从度低
     ```
   - **强制路由标记**：Task 可以自带 `force_model`，调试时绕过。

   路由结果会注入到 task context 的 `selected_model`，后续的模型调用节点无条件使用该模型。

3. **回退回路（fallback）**  
   本地模型的结果不是最终态。我们在 `after_hook` 里加了一个质量门槛：  
   - 如果本地模型输出包含空结果、违反 JSON Schema 或触发业务校验失败，自动将同一个 task 扔进重试队列，改用 `gpt`，并记录事件。  
   - 对于多轮对话，当路由需要切换模型时，我们会把已生成的摘要（而非原始上下文）作为系统 prompt 灌给新模型，缓解 token 空间断裂。虽然 lossy，但够用。

## 踩坑点：这几点没人会提前告诉你

- **规则维护地狱**：一开始规则只有 5 条，两周后变成 30 条，因为每个 agent 的 prompt 都有特例。最终我们引入了“规则打分 + 阈值”，而不是堆叠 if-else，可维护性才回升。
- **本地模型的“假性服从”**：它能把工具调用格式写对，但参数会塞进无关字段。靠 `model_compliance_score`（基于历史工具调用成功率统计）动态调权才压住。
- **路由延迟**：`before_hook` 里的规则计算极轻量，但一旦加入实时成本/延迟预测 API（比如拉取当前 GPU 队列深度），整个 agent 的 TTFB 会陡增。我们把“动态负载”挪到后台，由定时器更新一个 Redis 标志位，路由只读标志位，不再同步探测。
- **多轮对话中的模型切换导致上下文丢失**：就算有摘要，复杂任务的状态机也容易被打乱。我们的妥协是，标记某些 session 为“高认知连续会话”，默认使用 GPT，仅允许在分支子任务里调用本地模型。

## 可复用建议

1. **从“黑白名单”开始，不要一步到位动态路由**：先找出 20% 安全、高频的低复杂度任务（比如日志美化、固定 schema 提取），强制走本地模型，其余保持 GPT，跑一周看成本曲线。
2. **把模型服从度量化**：给每个 `(model, tool_schema)` 对维护一个成功率计数器，低于阈值自动禁用本地路由。
3. **埋点优先于算法**：至少记录每次路由决策的 `task_id, model_selected, cost, latency, success, fallback_used`。这些数据会在几周后成为你优化规则的唯一依据。
4. **缓存是隐形的第四层**：本地模型适合作为缓存后端。对语义相似度很高的输入，先用向量检索判断是否可复用上一次的输出，能进一步压缩云模型调用。
5. **回退不要让用户感知**：重试时带上 `x-fallback-reason` 头部，但不要改变响应结构，下游只看到结果，不关心哪个模型生成的。

## 总结

在 OpenClaw 框架里实现多模型路由，并不是为了造一个 fancy 的分发系统，而是要解决一个实实在在的成本与可靠性平衡问题。静态规则 + 轻量信号已经能覆盖 70% 的路由需求，剩下 30% 依赖数据闭环慢慢调优。不必追求“零人工干预的智能路由”，那通常意味着你会把一棵决策树的复杂度换成一个同样脆弱的神经网络，而后者更难调试。

别让路由本身变成你 Agent 里最贵的组件。
