## 背景：你的 AI 助手为什么总在同一个坑里跌倒？

过去半年，各类 AI coding agent 的普及速度远超预期。不少人已经习惯了让助手写代码、修 bug、跑测试，甚至直接帮忙重构模块。但很快就碰到一个尴尬的问题：AI 对项目约定几乎一无所知。它能写出语法正确的代码，却不清楚你的接口命名习惯、目录结构约定、中间件使用规范，也不知道本地开发环境有哪些特殊的启动参数。结果就是，每次让它干活，你都得先把上下文重新交代一遍；稍微复杂点的任务，它就开始自由发挥，留下一堆风格割裂、不符合内部契约的实现。

给 AI 配一份“工作空间使用手册”成了刚需。OpenClaw 为此提供了一个非常朴素的约定：只要在项目根目录（或工作目录）下放置一个 `AGENTS.md` 文件，agent 就会在每次会话启动时自动读取并将其作为长期上下文的一部分。这不是什么黑科技，而是一种用工程化手段降低 AI 理解成本的实践。

## 问题拆解：一份 AGENTS.md 到底要解决什么？

表面看，是告诉 AI “我们项目怎么玩”。但拆开看，它至少要覆盖三个维度：

1. **消除隐式知识**：架构师脑子里那套“这里必须用 Repository 模式，不要直连数据库”的规矩，对 AI 而言是完全不可见的。
2. **轻量环境对齐**：本地开发用的端口、假数据开关、必须手动启动的依赖服务，这些容易忽略但又天天用到的信息。
3. **输出边界约束**：AI 倾向于一次性生成大量代码。但项目可能要求“只改指定文件，不要动其他模块”“只输出 diff 不要全文”，这些约束需要在手册里显式声明。

如果 AGENTS.md 只是把 README 复制一遍，那等于白写。它的核心价值在于**给 AI 看的操作指令集**，而不是给人类看的介绍页。

## 实践：从零搭建一份能用的 AGENTS.md

### 1. 文件放置与加载时机

在 OpenClaw 中，agent 默认会查找工作目录下的 `AGENTS.md`（也支持通过配置指定其他路径）。建议直接放在项目根目录，与 `package.json` 同级。Agent 会在新会话启动时读取一次，中途不会热加载，所以改完文档需要重开会话才能生效。

一个容易忽略的配置：如果你的项目是多 package 单体仓库，可以在每个子 package 目录下各放一个 `AGENTS.md`，OpenClaw 会合并读取。这比写一份巨型文件更易于维护。

### 2. 内容结构模板

经过几个项目的迭代，我目前稳定使用的结构如下：

```markdown
# Project: [项目名]

## Stack & Runtime
- Node 20, pnpm 9.x, TypeScript 5.4
- Runtime: Express + Prisma + Redis

## Directory Conventions
- `src/domain/` - 业务模型，禁止引入 HTTP 相关依赖
- `src/adapters/` - 外部服务适配器
- `src/middleware/` - 只放 Express 中间件
- 测试文件与源文件同目录，后缀 `.test.ts`

## Naming & Patterns
- REST 接口使用 `POST /api/resource/:id/action` 形式
- 数据库查询一律通过 Repository，禁止在 Controller 中直接使用 Prisma Client
- 错误处理统一使用 `AppError` 类，携带 `code` 和 `httpStatus`

## Commands You Can Use
- `pnpm dev` - 启动开发服务器 (端口 4000)
- `pnpm db:migrate` - 执行数据库迁移
- `pnpm test -- --testPathPattern=<file>` - 运行单个测试文件
- `pnpm lint:fix` - 自动修复 ESLint 问题

## Environment & Secrets
- 本地需要 Redis 运行在 `127.0.0.1:6379`，无密码
- `.env.local` 中需要配置 `DATABASE_URL` 和 `JWT_SECRET`
- 集成测试依赖 Docker，运行前先执行 `docker compose up -d`

## Constraints & Rules (Very Important)
- 除非明确要求，否则不要修改任何 `.github/` 下的 CI 配置文件。
- 同一任务中只修改与需求直接相关的文件，不要随意“顺手优化”其他模块。
- 输出代码时优先使用 unified diff 格式，避免输出整个文件。
- 遇到不确定的约定，优先询问，而不是擅自决定。
```

这看起来像是给新同事写的上手文档，但差别在于**指令密度极高**、**去除了所有叙事性描述**。AI 不需要知道团队历史，它只需要知道“能做什么、不能做什么、怎么做”。

### 3. 让 AI 遵守手册的小技巧

光有文档不够，还得在 prompt 里强化优先级。每次会话开始，可以补一句：

> “在开始所有操作前，请先仔细阅读 AGENTS.md 并严格遵守其中的约束。”

如果你用 OpenClaw 的自定义指令功能，甚至可以把这句话内嵌到全局指令里，省去每次手动提醒。

另一个技巧：对于特别容易出错的约束（比如“禁止直连 Prisma”），可以在 AGENTS.md 中用 **加粗** 或 `⚠️` 符号标记。Agent 对标记词有注意力偏向，实测能显著降低违规率。

## 踩坑记录

**坑一：文件太长导致上下文污染**  
曾把 AGENTS.md 写到 600 多行，包含大量示例代码和边角说明。结果 agent 经常因为上下文窗口被撑满而截断关键约束。后来把示例部分挪到单独的 `docs/patterns.md` 里，只在 AGENTS.md 中写“参考 `docs/patterns.md` 中的 Repository 示例”。Agent 会自行按需查阅，效果反而更好。

**坑二：过时信息比没有信息更糟糕**  
有次改了本地开发端口，忘记更新 AGENTS.md。Agent 照着旧文档连接，排错了半天。后来我在项目 CI 里加了一个轻量检查脚本：用 `curl -s` 探测 AGENTS.md 里声明的端口是否真的在监听，未通过则发出提醒。虽然土，但有效。

**坑三：格式兼容性**  
早期用了大量 YAML front matter 来结构化数据，以为能提高解析精度。实际测试发现，纯 Markdown 的兼容性最好，Agent 对层级标题、无序列表和反引号内的命令识别率最高。现在完全用纯 Markdown，不搞骚操作。

## 可复用建议

- **小项目从 50 行起步**，只写目录约束和常用命令。跑一周后根据 agent 的违规记录补全规则。
- **为新手态 AI 写手册**。想象你的 agent 是一个刚入职、有技术背景但完全不了解项目的同事——这才是它的真实状态。
- **和代码一起 review**。当团队约定发生变化时，在 PR 里同步更新 AGENTS.md，reviewer 可以顺手检查一致性。
- **分层使用**：项目级放通用约定，个人目录放个人的工具快捷键习惯（如果需要），减少冲突。

## 总结

AGENTS.md 本质上是一份“写给机器的内部契约”。它不需要漂亮的叙述，不需要面向人类读者的渐进式引导，只追求精确、简短和可执行。当你要同时管理多个项目、和多个 AI agent 协同工作时，这种工程化的约束文件会比临时口头交代可靠得多。

在这个 AI 辅助编程还处于“可用但不可靠”的阶段，我们能做的最务实的事情，就是把手动传授经验的成本压缩到最低。AGENTS.md 就是这么一个小而硬的杠杆——投入一次，复用千百次。
