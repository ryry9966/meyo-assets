## 背景

仓库数量上来之后，Git 日常操作逐渐变成体力活：写 commit message、按规范命名分支、清理合并后的残留分支、拼 changelog。OpenClaw 的 agent 本身具备执行 shell 命令和调用 MCP 工具的能力，让它接管这部分流程化操作是顺理成章的事。关键不在于“能不能做”，而在于怎么做得可控。

## 问题

直接把 git 交给 agent 会遇到三个典型问题：

1. **不受控行为**：agent 可能自作主张执行 `reset --hard`、`push --force` 这类破坏性命令；
2. **描述失真**：生成的 commit message 和实际 diff 对不上，事后翻 log 全是误导；
3. **上下文溢出**：大仓库一次 diff 几千行，直接塞给模型效果差、成本高。

## 做法

我的方案分四步，核心思路是“白名单 + 规则文件 + 人工确认点”。

**第一步：收敛 Git 能力。** 不给 agent 裸 shell，而是包一层白名单脚本（或使用 MCP git server），只暴露 `status`、`diff`、`add`、`commit`、`branch`、`checkout`、`log` 这些只读或低危命令。`push`、`rebase`、`reset` 一律不进白名单，需要时人工执行。

**第二步：写一份 Git 规则文件。** 内容包括：commit message 采用 Conventional Commits 格式；分支命名 `feature/xxx`、`fix/xxx`；任何 commit 前必须先输出当前分支名和 `git status`；禁止直接向 main 提交。这份文件放进 agent 的系统规则，比在对话里反复叮嘱可靠得多。

**第三步：定义标准工作流。** 提交流程固定为：`git status` → `git diff` 分析改动 → 起草 message（要求引用 diff 中的关键改动点）→ 输出给用户确认 → 确认后执行 `add + commit`。分支流程：先 `checkout -b` 再动代码；合并后由 agent 定期跑 `git branch --merged` 找出可清理分支，列清单待确认后删除。

**第四步：扩展批量任务。** 基于同一套能力做周报用的 changelog 汇总（`git log` 按标签区间过滤）、多仓库分支巡检。这类任务只读、风险低、收益明显。

## 踩坑点

- **message 幻觉**：早期让 agent“看着办”，出现过把三个无关改动写成一个 feat 的情况。后来强制要求 message 逐条对应 diff 中的文件级改动，问题基本消失。
- **大 diff 溢出**：几千行 diff 直接分析会丢细节。改用先看 `diff --stat`，再对关键文件分块看 diff，成本和准确率都可控。
- **错误分支提交**：agent 曾在 main 上顺手 commit。此后规则文件加了硬性检查：commit 前必须回报分支名，不是 feature 分支就中止。
- **凭证暴露**：agent 的运行环境里不要放可 push 的凭证，本地演示用只读 remote 即可，push 永远留给人。

## 可复用建议

- 白名单脚本 + 规则文件是通用模式，换任何 agent 框架都适用；
- commitlint 之类 CI 校验照常保留，agent 的产出也要过同一道闸；
- 确认点不要省。自动化省下的是写 message 和记规范的心智成本，确认一次只需几秒，但能挡住大部分事故。

## 总结

让 AI 助手管理 Git，本质是把“规范”从人的记忆搬进规则文件，把“执行”从手指搬进白名单工具，人只保留确认权。这套做法跑了一个多月，commit 规范率和分支整洁度确实上来了，也没出过破坏性事故。克制地放权，是这类自动化的前提。
