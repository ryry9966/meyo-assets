## 背景

做自动化和 Agent 实践的人大多有个共同痛点：信息源太多。GitHub Releases、技术博客、论文、社区公告……RSS 仍然是最干净的聚合协议，但它只解决「汇聚」，不解决「读得完」。这篇帖子记录我用 OpenClaw 的定时任务 + 插件体系搭的一条 RSS → AI 摘要管线，思路可以直接迁移到任何支持 cron 调度和 HTTP 调用的环境。

## 问题

最初的做法很粗暴：定时拉 RSS，全文丢给 LLM，摘要推送到 Telegram。跑一周就暴露三个问题：

1. **成本失控**——每天几百条，全文 token 量很大；
2. **噪音没降**——同一事件五六个源都在报，摘要高度重复；
3. **不可信**——原文被截断时，LLM 会「脑补」结论。

## 做法

现在管线拆成四段，每段独立、幂等：

1. **抓取层**：每个源单独配置抓取间隔（高频源 30min，低频源 6h），拉取后立即落盘 SQLite，记录 guid/hash 和抓取时间，天然防重。
2. **预处理层**：先规则过滤——URL 去重、标题 embedding 相似度 > 0.85 的合并、黑名单关键词剔除；再用 readability 抽正文，截断到 2000 字符。这一步通常砍掉 60% 的条目，只有剩下的才进 LLM。
3. **摘要层**：模板化 prompt，要求输出结构化 JSON（一句话结论 / 关键点数组 / 原文是否完整）。规则明确：摘要只能基于给定文本，原文截断就标 `incomplete`，禁止推测。
4. **分发层**：按重要性打分（来源权重 + 关键词），高分实时推 Telegram，低分攒进每日 digest 邮件。所有摘要归档到静态页面，可回溯。

调度上用 OpenClaw 定时任务把四段串起来，模型调用走 MCP 工具封装，换模型、记账、限流都在一处收口。

## 踩坑点

- **summary 字段不可信**：很多源的 summary 是 SEO 文案，不能直接喂模型，必须自己抽正文。
- **防幻觉靠 prompt 不够**：真正有效的是强制模型标注「原文是否完整」，`incomplete` 的条目在展示层降权。
- **时区漂移**：部分源时间戳不带时区，导致漏抓或重抓。统一按本地时区解析，同时保留原始值备查。
- **源失效是常态**：加一个健康检查任务，连续 N 次空结果就告警，别等用户来报障。
- **模型分层**：分类和打分用小模型，确认值得精读的才用大模型摘要，成本直接降一个量级。

## 可复用建议

- 每一步落库、幂等，任何一段挂掉重跑都不产生副作用；
- prompt 当代码管理，改模板前先跑几条固定样本做回归；
- 摘要永远附带原文链接，AI 只是压缩，不是替代；
- 上线前先跑两周纯日志模式（只记录不推送），人工抽查摘要质量再开分发。

## 总结

这条管线没用什么新技术，价值全在工程细节：去重先行、成本分层、输出可信度标注。RSS + AI 摘要的合理定位是**降低扫描成本**，而不是替你阅读。真正值得精读的东西，还是得点开原文。
