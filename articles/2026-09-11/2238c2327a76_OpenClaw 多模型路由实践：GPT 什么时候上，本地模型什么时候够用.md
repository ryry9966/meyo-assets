## 背景

跑过几个稍微像样的 OpenClaw agent 之后，你会发现一个事实：一次任务里 LLM 被调用的次数远比想象的多。意图分类、工具选择、参数抽取、失败重试后的重规划、最后的总结，轻则七八次，重则二十次以上。如果所有节点都走 GPT-4 级别的云端模型，单任务成本和尾延迟都会翻倍；反过来全压给本地 7B，复杂规划环节又会大面积翻车。

## 问题

所以真正的问题不是“GPT 和本地模型哪个好”，而是：**流水线里哪个环节需要哪个档位的模型**。模型选择应该从一份全局配置，变成按节点路由的策略。

## 做法

1. **先给节点分档**：
   - A 类：需要跨工具规划、长上下文推理、复杂 tool call 的节点（planner、代码生成、多工具编排）→ 云端强模型；
   - B 类：输入输出结构稳定的小任务（意图分类、实体抽取、模板化改写、单文档摘要）→ 本地模型；
   - C 类：能规则化或命中缓存的 → 不调模型。
2. 在 OpenClaw 的**节点级 model 字段**里分别绑定模型 profile，不要让全局 default 兜底所有请求。
3. 给本地模型配 **fallback**：超时或解析失败时升级到云端，而不是把错误直接抛给上层。
4. 打开按节点的用量日志（模型、token、耗时），跑一两周再按数据调整分档。

```yaml
nodes:
  planner:
    model: gpt-4o              # A 类
  classifier:
    model: qwen2.5-7b-local    # B 类
    fallback: gpt-4o-mini
```

## 踩坑点

1. **tool call 兼容性**。多数开源模型对 function calling 的 schema 遵循不稳，路由到本地后 agent 解析失败率明显上升。经验：本地只承接输出为纯文本或单层 JSON 的节点，涉及多工具调用的留在云端。
2. **上下文长度**。按长上下文习惯写的 prompt 丢给本地 4k/8k 窗口会被静默截断，RAG 场景表现为“答案驴唇不对马嘴”——先查截断，再怪模型。
3. **fallback 风暴**。本地超时设太短，流量会全量涌向云端，成本反而更高。超时阈值按实测 p95 设，不要拍脑袋。
4. **量化损失**。同一模型不同量化等级在分类任务上可能差出好几个点。切路由之前，先拿 100 条左右的标注样本跑一个小评测。
5. **回归评测缺失**。调路由的影响是分布式的，改完务必跑一遍固定的回归任务集，“感觉变好了”不算证据。

## 可复用建议

- 分档**先粗后细**：先按 A/B 两档跑两周，靠日志定位值得单独调的节点，不要一上来设计七八条路由规则。
- 成本护栏放在**路由层**（单任务 token 上限、每日预算），而不是月底看账单。
- 把“哪些节点可以降级、哪些不能”写成团队文档，避免新人接手后一刀切全换强模型。

## 总结

多模型路由的价值不来自模型信仰，而来自节点级的用量数据。OpenClaw 把 model 选择下放到节点之后，你手里有的是旋钮，不是赌注：先用日志说话，再动手调路由，收益会自然体现在账单和 p95 延迟上。
