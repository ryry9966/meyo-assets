## 背景

Agent 接上 MCP 和插件之后，能力上限往往不取决于模型，而取决于我们愿意给它多大权限。实践里常见两种极端：一种是什么都问——"要我读这个文件吗？""要继续吗？"，自动化退化成逐帧确认；另一种是什么都干——直接删分支、发消息、调付费 API，出一次事故就足以让团队把权限全收回来。两种都不可持续。这篇帖记录我们在 OpenClaw 环境里划权限边界的一套做法，核心思路是**分层**，而不是一个总开关。

## 问题：判断标准是什么

"要不要问人"不能靠感觉，我们归纳成四个可判定的维度：

- **可逆性**：能不能撤销？`git revert` 可以，发出去的邮件、已调用的付费接口不行。
- **影响范围**：只在 workspace 里，还是触达生产环境、第三方、真实用户？
- **歧义度**：指令是否完整，Agent 是否掌握全部所需信息？
- **失控成本**：单次花费，以及循环重试的累积代价。

## 做法：三级分层

按上面四个维度，把所有工具和动作分成三档：

1. **自动执行**：只读、沙箱内、可逆。读文件、grep、跑测试、lint。零确认，直接跑。
2. **带护栏执行**：workspace 内的写操作。先 dry-run，产出 diff 或命令清单，执行后全部落日志，确保可回滚。Agent 自己干，但必须留痕。
3. **必须问人**：不可逆操作、对外副作用（发邮件、发消息、部署、支付）、指令有歧义、同一工具连续失败 3 次以上触发熔断。

落地步骤：

- 给每个 MCP 工具打风险标注，拆进配置里的 allowlist 和 approval_required 两份清单；
- 凭证默认最小权限：只读 token、按插件单独 scope，禁止一把 root key 走天下；
- 审批门要求 Agent 提交**自包含问题**：完整 diff 或精确命令 + 一句话影响说明，人只需要回答是/否；
- 超时策略：人没响应就默认 no-op，绝不自动放行。

## 踩坑点

- **确认疲劳**：把低风险操作也塞进审批，用户会养成无脑点确认的习惯，这道门就形同虚设——比没有门更危险。
- **批量审批**：Agent 打包 20 个动作问一次，人不可能逐条看。原则是一次一问、一次一事。
- **工具粒度错配**：MCP 工具是按"工具"授权而不是按"动词"，一个名叫 read_report 的工具顺手就能写文件。接插件前先读它的 schema 和权限声明。
- **假 dry-run**："测试邮件"真的发出去了。护栏动作本身要先被验证，否则护栏就是谎言。
- **问完丢上下文**：Agent 暂停等人时被压缩或重启，回来就忘了刚才问什么。所以问题必须自包含，答案能直接接上执行。

## 可复用建议

一句话版本：**读操作自动，写操作分环境，对外副作用必问，不可逆必问。**

另外三条：

1. 让"拒绝"很便宜——拒绝不应该引发重试、争论或降级绕路；
2. 让"撤销"成为可能——先有回滚方案，再谈放权；
3. 每月复盘一次动作日志，根据事故记录调整工具档位。权限边界是运营出来的，不是配置一次就完的。

## 总结

权限边界不是一个 yes/no 开关，而是把动作按可逆性、影响面、歧义度、成本分档之后的持续运营。目标是把人的介入压缩到真正需要担责的那几个动作上，其余全部交给 Agent 自己跑。当你的审批队列里只剩下"发出去就收不回"的操作时，这套边界就算划对了。
