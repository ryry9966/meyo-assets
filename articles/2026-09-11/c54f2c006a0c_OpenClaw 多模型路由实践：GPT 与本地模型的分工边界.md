## 背景

OpenClaw 里跑的 Agent 任务差别很大：有的是一次意图分类、字段抽取，有的是多步工具调用规划，还有长上下文的代码推理。全部丢给 GPT，账单和数据隐私都不好看；全部换成本地模型，复杂任务的质量又明显下滑。所以真正要解决的不是“选哪个模型”，而是建立一条清晰的路由规则。

## 问题

实践中常见的三个错位：

1. 简单任务用了重模型，成本高、延迟抖动大；
2. 敏感数据（日志、密钥、客户信息）被默认发往云端；
3. 本地小模型被塞进多步 Agent 循环，工具调用格式频繁出错，失败重试反而比直接用 GPT 更贵。

## 做法

我的路由分三层：

1. **按任务类型静态路由**。在 OpenClaw 的插件/skill 配置里直接指定模型：意图分类、格式化输出、简单摘要走本地 7B–14B 量化模型；工具规划、代码生成、长上下文推理走 GPT。
2. **动态升级（escalation）**。默认本地模型先行，输出后做一次轻量校验（JSON schema、工具调用参数合法性）。校验失败或置信度低，携带原始上下文升级到 GPT 重试一次。
3. **前置分类器**。对混合流量，用一个本地小模型先做“任务分级”再分发。分类本身就是本地任务，边际成本几乎为零。

同时把敏感数据源做成白名单，命中即强制本地，且不参与升级。

## 踩坑点

- **工具调用格式不统一**：本地模型生成的 function call 参数经常不合 schema。路由层必须先校验再执行，否则错误会穿透到 MCP 工具层，排查非常痛苦。
- **上下文窗口差异**：本地 8K 和 GPT 128K 差距巨大，升级重试前要先裁剪上下文，否则直接报错。
- **升级风暴**：本地失败→GPT 失败→再回本地。重试链条要设上限（我设 2 次），并打上标记防止级联。
- **输出风格漂移**：同一个面向用户的 skill 混用模型，语气和格式会变。面向用户的最终输出固定一个模型，只允许中间步骤路由。
- **本地冷启动**：Ollama 首次加载模型要十几秒，定时任务场景需要预热或保持常驻。

## 可复用建议

- 路由依据是“任务类别 + 数据敏感级”，不是个人对某个模型的偏好。
- 每次路由决策写日志：任务类型、命中规则、最终模型、token 数、是否升级。跑两周再调规则，比拍脑袋准得多。
- 模型版本钉死，升级单独走灰度，避免规则隐性失效。
- 升级判断尽量用确定性手段（schema 校验、正则、长度阈值），不要用一个模型去判断另一个模型。

## 总结

多模型路由的本质，是把“质量敏感、数据敏感、成本敏感”三个维度拆开，分别落成规则。我的现状：本地模型承接约七成调用量，成本降了一个量级，GPT 只在它真正值钱的地方出场。先把路由日志建起来，规则自然会越调越准。
