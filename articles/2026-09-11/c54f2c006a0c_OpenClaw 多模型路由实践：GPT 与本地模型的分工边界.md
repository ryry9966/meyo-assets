# OpenClaw 多模型路由：GPT 与本地模型的分工边界

## 背景

OpenClaw 的 agent 跑起来之后，最大的开销往往不是机器，是 token。规划、反思、摘要、格式化全走 GPT 一类云端模型，账单很容易超出预期；全换本地模型（Ollama / llama.cpp 跑 Qwen、Llama 系列），成本下来了，但复杂任务的成功率也跟着掉。多模型路由解决的就是这个矛盾：**不同任务喂给不同档位的模型**。

## 问题

实际部署中我们遇到三个具体问题：

1. **账单不可控**：agent 循环里大量 token 花在重复摘要、日志压缩这类低难度任务上；
2. **隐私边界**：含客户数据的任务不想出内网，但又不想整条流水线都本地化；
3. **延迟波动**：本地小模型快但偶尔抽风，云端稳但网络抖动时会卡住整条链。

## 做法

我们在 OpenClaw 里的落地分四步：

**1. 给任务分档。** 把 agent 内部的调用分成三档：S 档（规划、复杂工具编排、代码生成）走 GPT；M 档（摘要、改写、分类）走本地 14B 左右的模型；X 档（格式转换这类正则能解决的事）不进模型。

**2. 注册多 provider，写显式路由规则。** OpenClaw 支持在同一份配置里挂多个模型。路由优先用规则，而不是再调一次 LLM 来"智能分流"——按任务类型标签、预估 token 数、是否含敏感字段三个维度匹配，命中即路由，未命中落默认模型。

**3. 配 fallback 链。** 每档配主备：S 档 GPT 主、本地大参数量化版备；M 档本地主、GPT 备。本地模型连续两次工具调用格式错误就临时降级，避免死循环重试。

**4. 记录路由决策。** 每次调用记下：命中的规则、实际使用的模型、延迟、token 数。跑一周后回看，会发现很多"以为必须用 GPT、其实本地完全够"的调用。

## 踩坑点

- 本地模型的 function calling 格式很不稳定，量化之后尤甚。我们在 M 档任务里禁用了复杂工具调用，只允许纯文本输出。
- **上下文长度不一致**：本地模型 8K 上下文，长对话切过去直接截断，agent 表现为"失忆"。切模型前先检查上下文预算。
- 不要让 LLM 自己决定路由——判断本身也是一次调用，成本延迟双输，规则匹配毫秒级搞定。
- fallback 注意幂等：降级重试前先确认上一步工具没执行成功过，否则会出现重复下单这类事故。
- 量化版本要实测再用：Q4 做摘要还行，做结构化抽取错误率明显上升。

## 可复用建议

- 先全量跑一周**只记录不路由**，拿到真实任务分布再定分档标准，别拍脑袋；
- 规则路由为主，模型自路由为辅；
- 敏感数据默认本地，宁可慢一点；
- 每次升级本地模型或改路由规则，跑一遍固定评测集回归，别只看单条案例。

## 总结

多模型路由不是省钱银弹，而是把"哪些任务值得花大模型的钱"变成一个可观测、可回归的工程问题。我们的经验是：**规则先行、日志兜底、评测集护航**——GPT 用在刀刃上，本地模型吃掉长尾，整条 agent 流水线的成本和稳定性都会明显改善。欢迎在社区里贴出自己的分档标准和路由日志分析，一起迭代这套实践。
