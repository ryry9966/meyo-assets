## 背景

多数人用 Agent 的方式仍是对话式：你提问，它回答，会话结束即停止。但真正省时间的往往是"值守型"任务——每天早上汇总一次 GitHub 通知、磁盘超过 80% 时告警、周五下午整理本周未完成事项。这类事不需要模型多聪明，只需要它按时醒来、看一眼清单、按需执行。

## 问题

传统方案是 cron + 固定脚本，或在 crontab 里写死一段 prompt。痛点很明显：行为变更要改配置，prompt 与执行逻辑割裂，模型也没法自己判断"今天这件事要不要做"。OpenClaw 把这件事收敛成一个文件：心跳调度器按固定间隔唤醒 Agent，Agent 读工作区里的 HEARTBEAT.md 决定做什么。你维护的是一份 Markdown，而不是一段 cron。

## 做法

1. **找到文件**：HEARTBEAT.md 通常在工作区根目录，没有就新建。
2. **设置间隔**：默认 30 分钟唤醒一次，可在配置里调成 `10m` / `15m`，按任务容忍延迟定。
3. **写任务**：每条任务包含四要素——触发时机、执行条件、动作、输出方式。示例：

```markdown
- 每天 09:00：拉取 GitHub 通知，按 repo 分组，汇总发到聊天
- 每次心跳：检查磁盘用量，>80% 才通知，否则静默
- 每周五 18:00：把本周 MEMORY.md 未完成项整理成周报，只存文件不推送
```

4. **用好控制词**：`静默`（不主动发消息）、`仅异常时通知`；长内容放外部文件引用，不要全内联。
5. **验证**：先手动触发一次心跳确认能读到任务，再看日志跑一天观察行为。

## 踩坑点

- **token 成本**：即使无事可做，每次心跳也是一次模型调用。文件保持精简，空任务列表时让它走轻量路径。
- **任务模糊**：不写阈值和时间，Agent 要么每轮都执行，要么凭想象编状态。触发、条件、输出渠道都要写实。
- **通知轰炸**：不加"仅异常时通知"，你会每 30 分钟收到一条废话。
- **时间漂移**：心跳不是 cron，"每天 9 点"依赖模型对当前时间的判断，可能偏移一个间隔。高精度任务回退给系统 cron 触发。
- **失败循环**：某个任务一直报错会每轮重试。写明失败时行为（跳过/汇报/冷却），并定期翻心跳日志。
- **权限**：心跳等于授予 Agent 自主执行权，shell 和 MCP 的写操作范围要先收紧再放开。

## 可复用建议

- 把 HEARTBEAT.md 当声明式任务清单：一任务一行，触发 + 条件 + 动作 + 输出。
- 任务数控制在 3–7 个，复杂逻辑下沉到脚本或 MCP 工具，心跳只负责调用。
- 状态外置：让任务读写独立的 log/state 文件保证幂等，避免重复执行。
- 用 git 管工作区，Agent 改了什么，diff 一目了然。
- 从一个只读任务（如每日摘要）起步，观察一周 token 消耗和噪音，再逐步扩展。

## 总结

HEARTBEAT.md 的价值不在"AI 会主动做事"这个说法本身，而在把主动行为的定义权交给一份你能随时编辑的 Markdown——文件即接口。写得越具体，Agent 越可靠；写得越含糊，token 烧得越快。先小后大、先只读后写入，是落地这套机制最稳妥的路径。
