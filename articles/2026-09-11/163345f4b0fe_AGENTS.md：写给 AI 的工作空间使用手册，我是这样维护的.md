## 背景

用 OpenClaw 做日常开发一段时间后，我的体感是：agent 的表现上限往往不取决于模型，而取决于它对工作空间的"认知质量"。每次新会话，它都像第一天入职的同事——不知道构建命令、不知道哪些目录能动、不知道团队约定。在聊天里反复粘贴 prompt 不是办法，那些上下文是一次性的。AGENTS.md 的思路很简单：README 写给人看，AGENTS.md 写给 agent 看，放在工作空间根部，随仓库一起版本化。

## 问题

没写它之前，我反复遇到三类翻车：

1. **冷启动成本高**：每个会话都要重新交代构建、测试、目录约定，说漏一句就跑偏。
2. **行为不可预期**：agent 自作主张重命名文件、跳过 lint、把临时脚本写进不该写的目录。
3. **团队知识不沉淀**：每个人的私有 prompt 各不相同，同一个项目里 agent 的表现因人而异。

## 做法

第一步，在仓库根部建 `AGENTS.md`，我按五块组织：

```markdown
# 项目概览（3 行以内）
# 常用命令（构建 / 测试 / lint，可直接复制执行）
# 目录地图（每个目录一句话：是什么、能不能动）
# 约定（命名、错误处理、提交规范）
# 边界（禁止操作 / 需先确认的操作）
```

第二步，单仓库多子项目时用嵌套文件：根文件写全局规则，子目录的 AGENTS.md 写局部覆盖。

第三步，接了 MCP 或插件的，在文件里写清每个工具的用途、副作用和调用时机。比如"数据库工具默认只读，写操作必须先向用户确认"，这类一句话规则收益极高。

第四步，把它当代码维护：每次改完跑一次冷启动测试——开新会话，让 agent 独立完成一个常规任务（跑测试、加个小功能），观察偏差，回填到文件里。

## 踩坑点

- **写成散文**。agent 对操作型指令的遵从远好于长段落叙述，命令和规则优先，解释性文字压到最少。
- **太长**。超过一两个屏幕后，中间内容容易被"跳读"。我的经验是控制在 100 行内，细节拆到子目录文件里。
- **多处声明冲突**。规则和 README 或系统提示词不一致时，agent 行为会摇摆。约定只在一处声明，其他地方引用。
- **写死环境**。绝对路径、本机端口、个人 alias 都会让文件在别人机器上失效，命令一律用项目内相对形式。
- **过期**。目录重构后没更新，agent 会按旧地图走路。把它挂进 PR 检查：动结构必须动手册。
- **放敏感信息**。它会被整体读进上下文，密钥、内网地址都不该出现在这里。

## 可复用建议

- 按"入职文档"的心态写：假设读者是能干活的工程师，但对这个项目一无所知。
- 每条规则尽量可执行、可验证："提交前跑 lint 并修复所有报错"好于"注意代码风格"。
- 边界规则写具体动作，不写情绪化措辞。
- 冷启动测试是检验文件质量的唯一标准，建议每月跑一次。
- 团队共享同一份；个人偏好放自己的 prompt 层，不进仓库。

## 总结

AGENTS.md 的价值不在文件本身，而在于把"调教 agent"从一次性对话，变成可版本化、可 review、可复用的工程资产。写它的过程也会倒逼你把项目约定想清楚——很多时候第一个受益的其实是团队里的人类新成员。建议从今天起给活跃仓库补一份，先从"常用命令 + 边界"两块写起，跑两周再迭代。
