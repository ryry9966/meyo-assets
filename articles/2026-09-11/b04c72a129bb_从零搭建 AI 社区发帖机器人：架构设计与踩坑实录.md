## 背景

社区运营里有一类重复劳动：每周整理仓库动态、汇总 issue、发预告帖。纯手写耗时，纯模板又死板。我的目标是做一个**半自动**发帖机器人：定时或事件触发，由 Agent 拉取仓库/社区数据生成草稿，经审核后发布。注意是"半自动"——这个定位后来被证明是整个项目里最正确的决定。

## 最初的问题

第一版贪快，直接"cron + LLM + 发帖 API"三件套上线，48 小时内出了三个事故：

- 同一篇帖子发了两次（超时重试无幂等）；
- 正文里引用了两个不存在的 issue 链接（模型编造）；
- 凌晨连发五帖，触发社区风控限流。

问题不在模型，在架构。发帖的本质是**一次外部副作用**，所有设计都该围绕"如何保证这个副作用只发生一次、且内容可信"展开。

## 实际架构

重写后分四层：

1. **触发层**：cron 定时 + webhook 事件（新 release、issue 打标签）双通道，避免纯定时的僵硬。
2. **Agent 层**：LLM 只负责"给定输入，产出结构化草稿"。数据获取全部走 MCP 工具（查仓库活跃度、搜 issue、读上周帖子），模型不允许自由生成 URL，只能引用工具返回值里的原文链接。
3. **状态层**：SQLite 三张表——`posts`（幂等键 = 内容指纹 hash）、`attempts`（发布状态机：pending / published / failed）、`dedup`（近 30 天已发主题的 embedding，做语义去重）。
4. **发布层**：统一走一个带限流和指数退避的 publish 函数，先写库再调 API，成功后回写状态。审核门：草稿先进人工队列，前两周 100% 人工审，现在降到抽检 20%。

## 踩坑实录

- **重试导致重复发帖**：API 超时时无法确认服务端是否已成功。解法：发布前先落幂等键，重试携带同一 key 由服务端去重；没有服务端支持时，退化为"重试前先查后发"。
- **模型编造链接**：prompt 明确"只允许引用工具返回值中的 URL，否则留空"，校验层再用正则抽取全部链接逐个发 HEAD 请求，404 直接打回草稿池。
- **语义重复**：字面去重挡不住"换个说法再发一遍"。用 embedding 余弦相似度 > 0.85 即拒绝，阈值靠两周人工标注调出来。
- **上下文膨胀**：一开始把整份 issue 列表塞给模型，token 爆且输出质量差。改为工具层先做 top-N 截断和预摘要，模型只看结论。
- **cron 时区**：容器是 UTC，预期是北京时间，整体推迟 8 小时。这类低级错误值得在部署 checklist 里单列一项。

## 可复用建议

1. 先跑 dry-run：草稿只写日志不发帖，观察一周再接发布 API。
2. 把"发布"做成状态机而不是一个函数调用，每次状态转换落日志，出问题能回放。
3. 模型输出永远过结构化校验（JSON Schema + 链接存活验证），不要因为它"看起来对"就放行。
4. 人工门禁逐步放宽，信任是靠数据建立的，不是靠乐观假设。
5. 留一个 kill switch：环境变量一改就全局停发，凌晨出事时你会感谢它。

## 总结

这个项目的技术含量不在 prompt 调优，而在工程兜底：幂等、去重、校验、回滚。AI 发帖机器人的可靠性上限，由你为它设计的防呆机制决定，而不是由模型能力决定。半自动起步、数据说话、逐步放权——是我能给出的最朴素也最有效的路线。
