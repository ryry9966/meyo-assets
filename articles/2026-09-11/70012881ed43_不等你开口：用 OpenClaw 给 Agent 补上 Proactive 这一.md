## 背景

大多数人用 AI 助手的方式仍是"你问它答"。这个模式跑通后，下一个瓶颈很自然地出现了：**调度权始终在人手里**。每日巡检、邮件摘要、CI 失败跟进——这些事本身不难，难的是每次都得有人记得发起。

所谓 proactive，就是把"感知触发条件"也交给 agent：满足条件时它自己醒来，自己判断要不要行动。OpenClaw 生态里原料其实都齐了——MCP server 当传感器、插件系统接通知渠道、agent 主循环做决策，缺的只是中间那层"触发-门控"逻辑。

## 问题

把 reactive 流程跑顺之后，我在自己的工作流里遇到三个实际痛点：

1. **固定节奏的工作**每次都要人工拉起，坚持不了两周；
2. **事件驱动的事**（重要邮件、工单升级）依赖人刷新才能发现，经常滞后半天；
3. 人肉当调度器，是整条链路里最贵、最不稳定的一环。

## 做法

我按四层搭了一套链路：

1. **触发层**：cron 定时、webhook、文件/消息监听，通过 OpenClaw 插件注册 trigger；
2. **传感层**：MCP server 拉原始数据（邮箱、日历、仓库、监控）；
3. **门控层**：一个轻量判断——这事值不值得打断用户或执行动作。用规则加便宜模型先过滤一遍；
4. **执行层**：agent 主循环，带工具白名单和确认队列。

落地步骤：

- 每类 proactive 任务做成**单一职责的小 agent**，别用一个全能 agent 全包；
- system prompt 里写死决策标准：什么必须立刻报、什么可以攒到日报、什么直接忽略；
- 强制结构化输出 `{should_act, reason, action, confidence}`，门控不过直接丢弃，不进主循环；
- **先 dry-run 两周**：只记日志不发通知，人工审计"如果发了会怎样"；
- 上线后每个触发源设速率上限和去重键。

## 踩坑点

- **自触发环路**：agent 发出的通知被自己的监听器再次捕获，无限循环。解决：出站消息统一打标记，监听侧过滤。
- **通知疲劳**：第一周发了 40 多条，用户直接静音。后来收紧为低优先级攒日报，只有高置信度事件即时推送。
- **无上下文的幻觉**：proactive 运行时没有对话历史，agent 容易瞎猜。解决：状态持久化到本地 store，每次运行先读后判。
- **幂等问题**：同一条告警 5 分钟内触发三次，动作也执行了三次。解决：去重键 + 执行前查"近期是否已处理"。
- **权限边界**：无人值守执行写操作很危险。我的原则是只读工具直连，写操作一律进确认队列，人点一下才放行。

## 可复用建议

- **sense / decide / act 三段分离**，门控层必须便宜、可审计；
- 所有 proactive 输出先落日志，通知只是日志的一个消费者，方便回溯和调参；
- 宁可漏报，不可误报刷屏——信任一旦被静音，几乎回不来；
- 每个触发源独立开关、独立限流，出问题能单独掐断；
- 给用户留一个"太吵了/太少了"的反馈入口，用真实反馈调阈值，别靠自己拍脑袋。

## 总结

Proactive 不是把 agent 变得更聪明，而是把一部分调度权从人手里拿走。工程上的核心其实是两件事：**一个便宜可靠的门控层**，和**一份克制的通知策略**。先 dry-run、先只读、先攒日志，等审计数据证明它靠谱了，再逐步放开执行权限——这条路径在任何 agent 框架里都通用。
