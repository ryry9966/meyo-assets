## 背景

跑 Agent 的人很快会发现：成本大头不在“写一个聪明的 prompt”，而在调用次数。一条带 MCP 工具的自动化流程，动辄几十次 LLM 调用——规划一次，每轮工具调用前后各一次，最后汇总再来一次。全走 GPT 级别的云端模型，账单和敏感数据出境都是问题；全走本地模型，复杂规划又经常翻车。OpenClaw 的多模型路由就是把这个矛盾拆开处理：不同阶段，用不同模型。

## 问题

实际项目里最常见的两种极端：

- **全量走云端**：九成调用其实是分类、抽取、格式化这类“小活”，性价比很差；
- **全量走本地**：Qwen/Llama 这个量级的模型做自由度高的多步工具编排时，参数幻觉、JSON 不合规、忘记调工具的情况明显变多，排障成本反而更高。

## 做法

1. **先给任务分型**。把流程拆成四类：规划/编排（难）、结构化抽取（中）、摘要/改写（易）、涉敏数据处理（必须本地）。
2. **配置两条模型通道**。云端走 OpenAI 兼容接口挂 GPT-4o/4.1 级别；本地用 Ollama 起一个 qwen2.5:14b 之类，同样暴露兼容端点。在 OpenClaw 里给两条通道各起一个 alias。
3. **按阶段静态路由**。planner 绑云端，worker/extractor 绑本地。先静态跑通，别一上来就上动态路由。
4. **加一条受预算约束的升级链路**。本地输出做 schema 校验，连续失败 N 次升级到云端重试，且每次 run 设升级上限（比如 2 次），防止成本失控。
5. **记录数据再调优**。按阶段统计 token、延迟、失败率，跑一周真实流量后再改路由表。

配置示意（简化）：

```yaml
models:
  strong: { provider: openai, model: gpt-4.1 }
  local:  { provider: ollama, model: qwen2.5:14b, endpoint: http://127.0.0.1:11434/v1 }
routing:
  planner: strong
  extractor: local
  escalation_budget: 2
```

## 踩坑点

- **本地模型的 tool calling 是重灾区**：函数名记错、参数类型乱填都常见。给本地模型的工具集收敛到 3–5 个，并配 JSON schema 严格校验。
- **上下文长度**：MCP 工具返回的大段 JSON 很容易撑爆本地模型窗口，先在插件层做字段裁剪再喂模型。
- **升级链路退化成“全量升级”**：本地模型静默失败、重试全打到云端，等于双倍付费。升级预算和告警必须第一天就有。
- **本地模型切换延迟**：Ollama 在多个模型间换载会触发显存交换，容易超时。常驻一个模型，别在一条流程里频繁切。
- **版本漂移**：换本地模型版本等于换行为，路由表现可能悄悄变化。版本要 pin 住，升级前跑一遍回归集。

## 可复用建议

- 路由按“任务阶段”定，不按“感觉”定；路由表进配置文件、进版本管理。
- 涉敏数据默认本地，确需云端先做脱敏。
- 用自己积累的真实 trace 做基准，别只看公开榜单——你的工具集和提示词才决定本地模型的真实水位。
- 成本按 per-run 算而不是 per-call，单次便宜不等于整条链路便宜。

## 总结

多模型路由的本质是三个变量的权衡：质量、成本、数据边界。我的建议路径是：先静态按阶段路由跑通，用一周真实数据校准，再决定要不要上升级链路和动态路由。多数自动化场景，静态路由加一条受预算约束的升级通道，就已经够用了。
