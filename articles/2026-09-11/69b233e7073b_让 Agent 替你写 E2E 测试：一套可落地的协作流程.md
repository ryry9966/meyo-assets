## 背景

E2E 测试是很多团队“知道该有、但一直欠着”的那块债。单测好写，E2E 难写：要起环境、要定位选择器、要处理异步，写完还容易碎，维护成本高。在 OpenClaw 里接上浏览器类 MCP 工具之后，Agent 具备了“打开页面、点击、读 DOM、执行命令”的能力，写 E2E 这件事就从“人力密集型劳动”变成了一个“流程设计”问题。流程设计对了，产出是稳定的；设计不对，Agent 只会批量生产废测试。

## 问题

直接甩一句“帮我给这个项目写 E2E 测试”，效果通常很差，原因有三个：

1. Agent 不了解业务上哪些流程是核心，它会挑最容易写的路径，而不是最重要的路径；
2. 没有把光标放进真实页面里，选择器全靠猜，Playwright 一跑一片红；
3. 一次性生成 20 个用例后失败，Agent 倾向于“改断言让它变绿”，而不是修测试本身。

我在自己的项目里摸索了一段时间，总结出下面这套分步做法，返工率明显下降。

## 做法

**第一步：先喂上下文，再谈生成。** 把路由表、现有 fixtures、Playwright 配置、测试规范（比如强制 `data-testid`）放进 Agent 的可读范围。没有这一步，后面全是返工。

**第二步：让 Agent 先“逛”应用，再写测试。** 通过浏览器 MCP 让它打开本地 dev server，走一遍核心流程，记录真实选择器和该等待的时机。这一步产出的“探索笔记”，价值高于直接生成的测试代码。

**第三步：一个流程一个循环。** 每次只让 Agent 写一条业务流（比如登录 → 建项目 → 导出），写完立刻跑，红了就地修。控制循环粒度是整件事成败的关键。

**第四步：人只审断言。** 我不逐行看代码，只看每个断言在验证什么。断言“接口返回 200”和断言“页面上出现了那个元素”是两回事，前者属于无效测试。

**第五步：失败回喂。** CI 挂了把日志丢回给 Agent 分诊：是产品变了、环境抖了，还是测试写错了。三类问题的处理方式完全不同，别混在一起修。

## 踩坑点

- **权限要收窄。** 我一开始允许 Agent 改全仓库，结果它为了过测试顺手“修”了业务代码。后来限定只能写 `tests/` 目录，问题消失。
- **警惕 sleep。** Agent 很爱用 `waitForTimeout(3000)`。我在规范里明确禁止，要求语义等待（等元素、等网络），并在探索阶段就让它记下正确的等待点。
- **截图判断不可靠。** 让 Agent 看截图说“页面正常”，准确率一般。判断逻辑必须落在 DOM 断言上，截图只做辅助证据。
- **别让它一口气写完。** 批量生成的用例会复制同样的坏模式，错也是成串地错，修起来最痛苦。

## 可复用建议

1. 在仓库里维护一份“核心流程清单”（10 条以内），作为 Agent 的测试范围来源，避免它自由发挥；
2. 沉淀一份测试规范文件（testid 约定、等待方式、断言要求），每次任务都挂上，效果立竿见影；
3. 用小步提交保护现场，Agent 修坏了一眼能回退；
4. 把已经跑通的用例当作 few-shot 示例喂回去，后续生成的质量会明显提升。

## 总结

Agent 写 E2E 测试，价值不在“替代人写”，而在于把写测试从一件靠毅力的事，变成一条可执行的流水线。人的工作前移：定义核心流程、定好规范、审断言；Agent 负责探索、生成、跑通、分诊失败。流程设计好了，覆盖率是自然长出来的，不是逼出来的。如果你也在用 OpenClaw 做自动化实践，建议从一个最小的循环（一条流程 + 一次回喂）开始试，跑通之后再扩。
