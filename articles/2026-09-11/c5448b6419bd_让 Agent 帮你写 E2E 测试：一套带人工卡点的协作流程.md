## 背景

E2E 测试是大多数团队"知道该写但一直欠债"的部分：搭环境、造数据、写选择器、处理异步，一条核心链路的用例半天就过去了，UI 一改又崩。我们团队让 Agent（Claude + Playwright MCP）参与写测试，但不是"一句话生成"，而是一套有约束的协作流程。跑了一个多月，核心链路用例从 3 条涨到 17 条，维护成本可控，这里记录具体做法和踩过的坑。

## 问题的本质

直接把需求扔给模型"帮我写 E2E 测试"，通常得到三类东西：

1. **凭空捏造的选择器**——模型没见过你的页面，`data-testid` 全靠猜；
2. **只覆盖 happy path**——真实用户会填一半提交、断网、连点按钮；
3. **把当前行为当正确行为**——页面本身有 bug 时，生成的断言会把 bug 固化成"测试通过"。

根因是模型缺两个输入：真实的页面结构，以及"什么才算对"的业务判断。前者可以用工具解决，后者必须人来补。

## 做法：五步协作流程

1. **给 Agent 真实浏览器。** 通过 Playwright MCP 让它能实际打开页面、截图、读 DOM 快照，绝不凭描述写代码。
2. **喂测试规范而非需求。** 维护一份 `TESTING.md`：选择器优先级（`data-testid` > role > 文本）、page object 目录结构、fixture 写法、超时策略。Agent 生成前先读，产出风格统一，review 成本大降。
3. **一次只做一条用户流。** 比如"未登录用户提交订单并看到确认页"。让 Agent 先浏览真实页面，输出用例 spec（步骤 + 期望断言），人先审断言——这是流程核心：**Agent 提议，人裁定什么是对的**。确认后再落成 Playwright 代码，跑不通就带着报错让它自己修。
4. **显式要求失败路径。** prompt 里明确：每条 happy path 至少配一条异常用例（接口 500、必填为空、重复提交）。不要求它就不写。
5. **进 CI 并打标。** 生成的用例统一加 `@ai-generated` 标签，红了先怀疑环境或数据，再怀疑功能回归。

## 踩坑点

- **不接真实浏览器，选择器全靠编。** 第一版生成的用例八成跑不过，全是 `getByText('提交')` 这类脆弱写法；接上浏览器工具后一次通过率明显提升。
- **断言抄现网行为。** Agent 看到"价格显示 ¥0"就断言 ¥0，而那其实是折扣计算的 bug。审断言这步不能省。
- **硬编码测试账号。** Agent 爱"用 user_test_001 登录"，换环境就挂。规范里强制走 fixture 工厂，禁止写死账号。
- **上下文爆炸。** 整页 DOM 快照很大，几轮对话 token 就失控。限定 Agent 每次只截当前交互区域的快照，而不是整页。
- **无条件等待。** Agent 很爱写 `waitForTimeout(3000)`，规范里直接禁掉，统一用 `expect(...).toBeVisible()` 这类自动等待断言。

## 可复用建议

- 先写规范文件再上 Agent，半天投入，全程受益；
- "写 spec"和"写代码"拆成两个阶段，人工卡点只审断言，不必逐行看代码；
- 用例按用户流组织而非按页面组织，和业务对齐，Agent 也更好理解；
- 失败用例的报错直接回喂给 Agent 修，比人自己 debug 快，但修完必须人审一遍 diff。

## 总结

Agent 写 E2E 的价值不在"自动生成代码"，而在把最耗时的部分——浏览页面、搭用例骨架、填等待逻辑——自动化掉，把"判断什么是对的"留给人。工具上 Playwright MCP 加一份测试规范就够起步，关键是流程里必须保住两个卡点：真实浏览器访问、人工断言审核。缺了前者，生成的是幻觉；缺了后者，是把 bug 固化的假绿灯。
