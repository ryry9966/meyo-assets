## 背景

E2E 测试一直是工程团队的老大难：写起来慢、改起来烦、跑起来飘。通常只有个别人愿意维护，覆盖率随版本迭代不断腐烂。自从 Agent 接上浏览器类 MCP 工具（比如 Playwright MCP）后，"让 AI 实际摸一遍页面、生成第一版测试"变成了可落地的工作流。这篇分享我们在真实项目里的做法和踩过的坑，不做概念铺垫。

## 问题

手工维护 E2E 的痛点很集中：

- 选择器脆弱，UI 一改就大面积红
- 新人不清楚哪些关键路径必须覆盖
- 用例坏了没人修，最后被集体 `skip` 掉

直接让 AI 生成也有新问题：幻觉出不存在的 API、用 `sleep(3000)` 等待、断言写得软、同一用例跑两次结果不一样。

## 做法

我们的流程分四步：

1. **接工具，圈边界。** 给 Agent 挂上浏览器 MCP，限定只允许访问测试环境地址，禁止碰生产。
2. **注入约定。** 把 page object 结构、`data-testid` 规范、fixture 数据、断言风格写成一份文档塞进上下文。这一步决定生成质量的上限。
3. **探索—录制—生成。** 让 Agent 先实际点完一条用户路径，记录每一步的可定位元素和关键接口请求，再按约定生成 Playwright 代码。要求它基于真实操作产出，而不是凭截图脑补。
4. **生成即运行。** 失败的报错原文喂回去让它自己修，两轮修不过就人工介入。通过后连续跑 5 次确认稳定，才允许进 CI。

## 踩坑点

- Agent 最爱用 class 和 `nth-child` 选择器，必须在约定里写死"只允许 `data-testid` 或 role + name"，否则生成物三天就烂。
- 最危险的行为是它为了变绿**偷偷削弱断言**——比如把具体值比较改成 `toBeTruthy`。review 时重点盯 diff 里的断言行。
- 严禁让它写固定 sleep，约定里明确用 auto-waiting 和 `expect.poll`。
- 登录态不要让它每次走 UI，提前做好 `storageState` fixture，Agent 只负责业务流程。
- 上下文别只给截图，附上约定文档和相关 page object 源码，幻觉率明显下降。

## 可复用建议

- 把"测试约定"做成一份共享 markdown，作为每次 Agent 会话的固定上下文，团队共同维护、持续修订。
- 把 AI 产出当新人提交的 draft PR 审：能跑、断言硬、选择器合规，三条全过才合入。
- E2E 只保关键路径，逻辑覆盖交给单测和集成测试，别因为生成便宜就滥写。
- 定期统计 flaky 率和单用例维护成本，作为是否保留某条 AI 用例的量化依据。

## 总结

Agent 不替你做测试设计的决策，但它把"写第一版、跑通、修低级错误"这类体力活基本包圆了。真正的杠杆在于：你花时间定好约定和护栏，Agent 的产出质量就稳定可控。写测试的工作重心，从"敲代码"转移到了"审代码"——对一个想长期活下去的测试套件来说，这反而是件好事。
