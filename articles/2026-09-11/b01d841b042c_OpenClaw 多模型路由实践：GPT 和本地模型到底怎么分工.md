## 背景

OpenClaw 的 agent 跑起来后，一个 session 里往往混杂着各种任务：解析日志、写 SQL、总结文档、编排 MCP 工具。全走 GPT-4 级模型，token 成本和尾延迟都难看；全压到本地模型，多步规划和长上下文又明显掉链子。多模型路由不是炫技，就是在这个矛盾里做工程取舍。

## 问题

路由设计要回答三件事：

1. **按什么维度分**——敏感度、任务复杂度、延迟要求、成本预算，权重怎么排；
2. **规则放哪一层**——网关层、agent 层还是插件层，谁说了算；
3. **路由错了怎么办**——云端限流、本地 OOM、模型不支持工具调用时的回退路径。

## 做法

**第一步：按敏感度先切一刀。** 涉及内网数据、客户信息、未脱敏日志的任务强制走本地模型。这条规则放在网关的 pre-route 钩子里，优先级最高，agent 自己不能覆盖。

**第二步：按复杂度分档。**

- 简单任务（格式转换、字段抽取、短文本总结、固定模板回复）→ 本地 7B/14B；
- 中等任务（单次工具调用、代码补全、常规问答）→ 中档云模型；
- 复杂任务（多步规划、跨 MCP 工具编排、长上下文分析）→ GPT-4 级。

**第三步：实现静态路由 + 轻量分类。** 在 OpenClaw 的路由配置里用 `task_type` 加上下文长度做静态规则；规则覆盖不了的场景，用本地小模型做一次打分分类再转发。注意别让大模型判断自己该不该上，那笔账算不平。

**第四步：配 fallback 链。** 云端超时或限流 → 本地模型兜底并标记降级；本地显存不足 → 排队或降级到更小的模型，宁可慢一点也不能断。

## 踩坑点

- **本地模型 function calling 兼容性参差。** 有些模型对 tool schema 支持不完整，agent 会静默失败而不是报错。工具调用类任务路由前，先跑通一遍真实的 schema 验证。
- **Tokenizer 不一致。** 云端和本地的上下文预算不能按同一个 token 数复用，长上下文任务的阈值要单独标定。
- **路由决策不落日志等于没做。** 每次命中哪条规则、用了哪个模型、耗时多少，都要进日志，否则规则退化几周后才发现。
- **分类模型本身也要控制成本和延迟。** 一个本地小分类器足够，别在这里叠复杂度。

## 可复用建议

- 建一张**路由矩阵表**（任务类型 × 敏感度 × 档位），进仓库、随代码评审演进，别散落在个人配置里。
- 给每个 MCP 插件声明 `recommended_model`，插件自带路由建议，agent 只做最终裁决，边界更清晰。
- 维护一个 20–50 条真实任务的**固定评测集**，每次调路由规则跑一遍回归，看成功率和成本的变化，用数据说话。
- 本地模型节点做**独立的资源隔离和排队**，避免和 embedding 服务抢显存，这是本地路线最常见的翻车点。

## 总结

多模型路由的核心不是"哪个强用哪个"，而是把敏感度、复杂度、成本变成显式规则，配上日志和回退机制。落地顺序建议：先切敏感度红线，再分复杂度档位，最后靠评测集持续校准。在 OpenClaw 里这套配置半天能搭起来，收益大概在第二周的账单和延迟曲线上就能看到。
