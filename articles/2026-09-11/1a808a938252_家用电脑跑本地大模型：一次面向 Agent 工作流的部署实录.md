## 背景

做 Agent / MCP 自动化的同学大多依赖云端 API，但有两类场景促使我开始折腾本地模型：一是任务涉及本地文件和隐私数据，不想把内容发出去；二是高频小任务（分类、摘要、格式转换）按 token 计费，攒起来并不便宜。目标从一开始就明确：不是让本地模型替代旗舰模型，而是让它承担"脏活"，并在断网时保底。

## 问题

我的机器是一张 12GB 显存的消费级显卡 + 32GB 内存。要解决三件事：选哪个推理后端和量化档位；怎么用 OpenAI 兼容接口暴露给 Agent 框架；本地模型做 MCP 工具调用时，可靠性能不能过关。

## 做法

**第一步：按显存定预算。** 经验公式：GGUF Q4_K_M 量化下每 1B 参数约 0.6GB，再留 2–4GB 给 KV cache。12GB 显存实际能跑 14B 级别；靠内存兜底可以跑更大模型，但速度会掉一个量级。

**第二步：选后端。** 日常用 Ollama，设置 `OLLAMA_HOST` 后默认暴露 OpenAI 兼容接口，Agent 框架把 base_url 指过去即可。需要精细控制（自定义模板、flash attention、KV cache 量化）时换 llama.cpp；Linux + NVIDIA 环境追求吞吐可上 vLLM。

**第三步：选模型。** Qwen 系列、GLM、DeepSeek 蒸馏版对中文和工具调用都比较友好。量化从 Q4_K_M 起步，别低于 Q4。接进 Agent 前，先用脚本压测：连续 50 次要求输出结构化 JSON，统计解析失败率，低于 5% 才继续。

**第四步：验证工具调用。** 挂上 MCP server，跑一条固定的多步任务链（查文件 → 调工具 → 写结果），观察参数填写是否稳定。温度压到 0.2 以下，工具调用场景越低越稳。

## 踩坑点

- **上下文长度是隐形杀手。** Ollama 默认 num_ctx 很小，Agent 多轮对话后静默截断，表现为"模型失忆"。务必显式设到 8K 以上，同时注意 KV cache 显存随上下文线性上涨。
- **不是所有模型都支持正经的 function calling。** 有些靠 prompt 拼接模拟，模板不对就输出自由文本。选型时直接看模型卡是否声明 tool use。
- **量化过狠，参数就开始编。** Q3 以下经常把 JSON 字段名写错，排查半天发现是模型问题而非代码问题。
- **显存不足会自动 offload 到内存，速度从 40 token/s 掉到 5。** 启动后看日志确认实际加载到 GPU 的层数。
- **本地推理基本是单并发。** Agent 并行跑多个子任务时会排队，吞吐按串行预估。

## 可复用建议

1. 用"路由"思路做两级 fallback：简单任务和涉隐私任务走本地，规划和长文生成走云端。
2. 压测脚本固化下来，每次换模型或量化版本重跑一遍，用数据说话。
3. KV cache 量化（q8_0）能省约 30% 显存，长上下文场景值得开。
4. 模型目录固定版本号，别追新追到把已验证的工作流搞坏。

## 总结

本地模型的价值在于可控、便宜、断网可用，而不是打赢旗舰模型。把预期放在"可靠地干简单活"上，配好上下文长度并完成工具调用验证，一台 12GB 显存的家用机完全可以成为 Agent 工作流里稳定的一环。
