## 背景

大多数 AI 助手的默认形态是"被动应答"：你发消息，它回复，会话结束。但真正长期跑在 OpenClaw 上的助手，价值大头往往在它"不请自来"的部分——每天早上汇总监控告警、发现 CI 连续失败主动提醒、日历冲突提前一天预警。这类能力统称 proactive。它不是模型能力问题，而是触发与治理的工程问题。

## 问题

LLM 本身不会自己跑起来。要让它主动，必须回答三件事：

1. 谁来唤醒它——时间还是事件；
2. 唤醒后它依据什么判断"值不值得打扰你"——状态与阈值；
3. 它能自作主张到什么程度——权限边界。

任何一件事没设计好，结果要么是助手永远沉默，要么是半夜推送轰炸。

## 做法

我在自己的 OpenClaw 实例上分三层搭的：

**1. 触发层：两条通路**
- 时间触发：用 cron / heartbeat 定时唤醒，系统提示写清"值班巡查"职责，比如每天 9 点检查一次监控面板和未读 issue。
- 事件触发：监控、CI、邮件等外部系统通过 webhook 或 MCP server 把结构化事件推给 agent。事件带 payload，别让模型自己解析原始日志。

**2. 状态层：外置 + diff**

agent 每次唤醒把关键状态（上次构建号、告警快照）写到本地文件，唤醒时先读上次状态做对比，只汇报增量。这一步是抑制噪声的核心。

**3. 行动层：分级输出**
- L0 静默：只更新状态文件，不说话；
- L1 通知：推一条消息，附证据链接；
- L2 执行：涉及写操作（重启服务、回滚）必须走确认门控，用户点头才放行。

## 踩坑点

- **token 成本失控**：早期我把 heartbeat 设成 5 分钟一次，每次唤醒都带完整会话上下文，一天烧掉平时一周的量。后来单独建一个轻量巡查会话，上下文只放系统提示和状态 diff。
- **误报**：模型不调工具、凭想象判断"服务可能挂了"。解决：系统提示硬性要求"没有工具返回的证据，不许报告异常"。
- **通知风暴**：同一告警没去重，一小时提醒六次。加了冷却时间 + 指纹去重，同一 fingerprint 在 N 分钟内不重复推送。
- **权限越界**：proactive 场景下 agent 特别容易"顺手"执行写操作。所有 L2 动作走白名单 + 二次确认，别指望提示词能约束住。

## 可复用建议

1. 感知、判断、行动三层解耦，每层单独可测、可关。
2. 唤醒 prompt 里显式写"无事可报就保持沉默"，并把这句话当成硬约束来测。
3. 状态永远外置，agent 只做 diff，不做记忆。
4. 预算先行：给 proactive 任务设每日唤醒次数和 token 上限。
5. 灰度上线：先跑两周纯只读的 L0/L1，确认误报率可接受，再放开写操作。

## 总结

Proactive 的本质不是让模型更聪明，而是把"什么时候跑、凭什么说话、能做什么"变成三个明确的工程开关。触发器负责唤醒，状态负责判断，分级负责兜底。这套东西做完，助手才真正从"问答工具"变成"值班同事"。
