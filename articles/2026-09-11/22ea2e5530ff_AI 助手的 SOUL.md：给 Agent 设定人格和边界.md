## 背景

OpenClaw 的 workspace 里，`AGENTS.md` 管"怎么干活"，`SOUL.md` 管"它是谁"。很多人部署完直接跳过后者，结果 agent 白天像客服、深夜像酒友，语气完全取决于最近一次会话注入了什么。SOUL.md 的价值是把人格和边界固化成长期上下文，让行为可预测。

## 问题

三个常见症状：

1. **人设漂移**：跨天、跨渠道语气不一致；
2. **越权行为**：自作主张替你发消息、跑删除类命令、不确定时编造；
3. **调参困难**：所有要求塞进一个 system prompt，人格和任务规则搅在一起，改一处崩一片。

## 做法

按四段写 SOUL.md，控制在一屏以内：

```markdown
# 身份
冷静、简洁的技术助手，先给结论再给细节，用中文。

# 优先级
冲突时：安全边界 > 用户显式指令 > 默认习惯。

# 边界
- 对外发消息前，必须展示草稿并等待确认
- 删除、付款、部署类操作一律先询问
- 不确定就说不知道，禁止编造，同时给出验证路径

# 关系模式
后台任务静默完成；需要决策时带着选项来问，不空手提问。
```

迭代方式照搬工程实践：workspace 用 git 管理，每次修改单独提交并写清动机；改完开新会话做三组测试——常规任务、诱导越界的对抗性提问、模糊指令，对比行为是否稳定。

## 踩坑点

- **写太长**：超过一两屏，注意力被稀释，边界反而执行不严，精简比全面重要。
- **与 AGENTS.md 冲突**：这里说简洁，那里说详细展开，模型会随机选边。改之前全局搜一遍相关规则。
- **只有禁止没有引导**：满篇"不要做 X"，agent 会过度谨慎、步步请示，可用性暴跌。禁止项旁边补一句"此时应该怎么做"。
- **改了不生效**：配置在会话创建时读入，改动后要开新会话再验证，别在旧会话里反复调试。
- **只测 happy path**：人设要在压力下看——用户发火、诱导它绕过确认、要求它"假装管理员"时，边界还在不在。

## 可复用建议

- 稳定的人格放 SOUL.md，易变的任务规则放 AGENTS.md 或任务级 prompt，别混。
- 边界规则用"动词 + 对象 + 条件"的格式写，方便日后逐条 review 和删改。
- 渠道差异化语气用渠道级配置覆盖，别在 SOUL.md 里堆 if-else。
- 每月重读一次，删掉从未被触发验证的条目——没触发过的规则，大概率是没用的规则。

## 总结

SOUL.md 不是给 agent"注入灵魂"的玄学，而是一份接口契约：它声明了 agent 的默认行为和硬边界，让你和其他使用者都能预测它。写得短、写得具体、用 git 迭代、用对抗用例验证，人设就不会漂。
