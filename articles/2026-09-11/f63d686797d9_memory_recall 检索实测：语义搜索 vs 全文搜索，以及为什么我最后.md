## 背景

OpenClaw 的 agent 跑久了，`memory_recall` 是决定"助手像不像记得你"的关键。我的场景：日常开发助手，积累了几千条 memory（决策记录、配置、踩坑笔记），每次对话前 agent 调 memory_recall 拉相关条目进上下文。

最初用纯向量检索（embedding + 余弦相似度），后来发现一些很基本的查询根本召回不到，于是把 SQLite FTS5 全文检索加进来做了对比，最后落地成混合方案。这篇记录测试过程和结论。

## 问题：两者各有一块明显短板

从自己两周的真实会话日志里抽了 60 条查询，分三类测：

- **精确指代**（"xx 项目的部署端口"、"那个 postgres 的密码提醒"）：全文检索命中率 80%+，语义检索不到 50%。专有名词、代号、代码标识符在 embedding 空间里区分度很差，`deploy_port_8443` 和别的端口字符串在向量上几乎没差别。
- **换说法查询**（"上次说服务器老挂的那个事"）：语义检索明显占优，全文检索因为字面不匹配直接空手而归。
- **时间类查询**（"上周定的规范"、"三个月前那个问题"）：两者都烂。memory 正文里往往没有"上周"这种词，纯靠内容检索无解。

## 做法：混合检索 + 元数据过滤

落地结构不复杂：

1. **存储层**：SQLite 单库，memory 表 + FTS5 虚表 + sqlite-vec 向量列，写入时同步生成正文 embedding。
2. **中文分词**：FTS5 默认 tokenizer 对中文不友好，我用 trigram tokenizer，短词召回一般，但专有名词能兜住；要求更高可以写入前先 jieba 分词再入库。
3. **检索层**：两路各取 top 8，用 RRF（reciprocal rank fusion）合并取 top 5。RRF 的好处是不用调两路分数的量纲，实现就几行。
4. **元数据过滤**：每条 memory 带 `created_at`、`project`、`tags`。时间类查询先让 LLM 抽出时间范围转成 SQL 过滤，再走检索，命中质量立刻上来了。

## 踩坑点

- **别迷信语义检索的 demo 表现**。demo 里查询和 memory 措辞接近时效果都好；真实日志里专有名词查询占大头，这正是向量的弱区。
- **条目太短 embedding 质量很差**。一句话的 memory 缺上下文，写入时让模型补一句"这条是关于什么的"，比换 embedding 模型管用。
- **top_k 别贪大**。top 5 之后的内容大多在稀释上下文，agent 反而会被带偏。
- **去重比检索更影响体感**。同一件事写三遍，检索回来三遍占 token。写入前做一次相似度查重。

## 可复用建议

- 任何检索改造前，先从真实日志抽 50-100 条查询做基准集，不然全凭感觉调参。
- 全文检索便宜、可解释、零依赖，永远值得作为 baseline 和兜底。
- 混合方案里 RRF 是最低成本的选择；延迟敏感的话，向量路的结果可以做缓存。
- 时间和项目维度靠元数据过滤，别指望检索本身解决。

## 总结

语义搜索和全文搜索不是二选一，而是覆盖两类不同的真实查询：全文兜住精确指代，语义兜住换说法，元数据过滤兜住时间范围。三件事加起来不到两百行代码，memory_recall 的命中率却从"经常想不起来"变成了基本可靠。对跑长线的 agent 来说，这笔投入值得。
