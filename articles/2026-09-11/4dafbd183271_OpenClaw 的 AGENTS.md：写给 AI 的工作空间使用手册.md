## 背景

OpenClaw 的 agent 并不是每次都从零开始。每次会话启动，它会随 workspace 一起加载一组固定文件：`SOUL.md` 管人设，`USER.md` 管用户画像，而 `AGENTS.md` 管的是"在这个工作空间里怎么干活"。你可以把它理解为写给模型看的 README——README 写给人，AGENTS.md 写给 AI。

## 问题

很多人装完 OpenClaw 第一件事是调人设，却放着默认的 AGENTS.md 不动。后果很典型：路径靠猜、构建命令选错、该备份的文件直接覆盖；你在会话里临时纠正它的那句"删东西前先问我"，下一个 session 就忘了。这些重复纠正，本质上是规则没有沉淀。

## 做法

我的路径是从空白开始，逐步生长，而不是抄一份大而全的模板：

1. **先记录，后成文。** 前一两周不急着写，每次想纠正 agent 的地方记下来，这就是规则的原材料。
2. **按"触发条件 + 期望行为"写。** 例如：

```markdown
## 安全
- 删除或覆盖文件前必须先向我确认
- 修改 *.config.js 前先复制到 backup/

## 工具
- Python 一律用 uv，不要用 pip
- 优先使用 MCP 的 filesystem 工具，不要用 shell 拼命令
```

3. **分层。** 子目录的 AGENTS.md 可以覆盖根目录规则。根目录放全局约定（语言、安全边界、工具偏好），子项目目录放局部约定（构建命令、测试方式）。
4. **长知识外移。** API 说明、架构备忘放独立文件，AGENTS.md 里一句话指路即可，别把手册写成百科。
5. **进 git。** 它是行为配置，改坏了比代码 bug 更隐蔽，值得走 review。

## 踩坑点

- **写成文档而非指令。**"本项目使用 pnpm"是描述，模型不一定照做；"安装依赖时用 pnpm，禁止 npm"才是指令。
- **越写越长。** 上下文预算有限，200 行的手册会稀释关键规则。我的准入标准是：同一个错误重复纠正过两次以上，才值得写进去。
- **写死易变信息。** 路径、版本、端口一进手册，环境一变就成了误导源。
- **放机密。** AGENTS.md 每个会话都注入上下文，token 和 key 绝对不能出现。
- **与 MCP 工具描述冲突。** tool description 说一套、AGENTS.md 说另一套，行为会抖动，以一边为准。

## 可复用建议

- 规则分四节：安全、流程、风格、指路，方便定位和维护。
- 用 git diff 审规则变更，像审代码一样。
- 每月花十分钟通读一遍，删掉三个月没触发过的条目——手册的生命力在于精简。

## 总结

AGENTS.md 不是一次性配置文件，而是你和 agent 之间逐步沉淀出来的协作协议。写得克制、具体、可验证，agent 的表现就会从"每次现场发挥"变成"稳定可预期"。如果你还在每次会话里重复解释自己的项目，今天就该打开这份手册补两条规则。
