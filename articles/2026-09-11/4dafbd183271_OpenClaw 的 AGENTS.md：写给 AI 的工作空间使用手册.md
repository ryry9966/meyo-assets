## 背景

用 OpenClaw 一段时间后，大多数人都会遇到同一个场景：agent 的能力没问题，但行为不稳定。今天回复简洁，明天长篇大论；今天删除文件前先确认，明天直接执行。原因往往不在模型，而在于你没告诉它这台机器上的规矩。

OpenClaw 的工作空间（默认 `~/.openclaw/workspace`）里有一组约定文件，其中 `AGENTS.md` 会在每次会话启动时注入模型上下文。它不是给人看的文档，而是写给 agent 的操作规程——类比仓库里的 README，但读者是模型。工作空间里人设归 `SOUL.md`，工具说明归 `TOOLS.md`，而"这个 agent 在这里该怎么干活"这件事，由 AGENTS.md 承担。

## 问题

不写或乱写 AGENTS.md，通常表现为三类问题：

1. **行为漂移**：同样一个请求，执行方式每次不一样，全靠会话内临时纠正。
2. **边界缺失**：agent 同时握着 shell 和消息通道权限，该问的不问，不该发的发了。
3. **上下文浪费**：把人读的项目介绍、历史背景塞进去，token 花掉了，行为没有任何变化。

每次出错都靠打字口头纠正，等于把同一套规则重复输入。规则应该落在文件里，一次写清。

## 做法

一个实用的三段式结构：

```markdown
# AGENTS.md

## 运行环境
- 宿主机：Ubuntu 22.04，时区 Asia/Shanghai
- 长期记忆写入 memory/ 目录，按日期分文件

## 行为规则
- 默认中文回复，控制在 200 字内，除非我要求展开
- 删除文件、重启服务、对外发送消息前，必须先列出操作等我确认
- 不确定时直接问，不要猜

## 工作流
- 定时任务失败：记录到日志，重试不超过 2 次
- 需要检索时优先调用本地 MCP 文件工具，网页抓取前先查缓存
```

三条写法要点：

- **祈使句 + 可判定条件**。"尽量简洁"是无效指令，"默认 200 字内"才是。
- **只写会改变行为的条目**。人看的介绍、历史、致谢，放 README 去。
- **每条规则可验证**。改完开一个新会话，实际触发一次场景确认生效。注意修改后对新会话才生效，别改完在旧会话里测。

## 踩坑点

1. **写成小作文**。这个文件每轮对话都占上下文，超过一两百行后，关键规则反而被稀释。做减法比加法难，但更重要。
2. **规则互相冲突**。"永远先确认"和"定时任务自动执行"放在一起，agent 会自己挑一个理解。冲突条目要么写明优先级，要么按场景拆开。
3. **塞敏感信息**。文件内容会被完整送进模型上下文，不要写密钥、内网地址、私人清单。
4. **职责混淆**。语气和人设归 SOUL.md，操作规程归 AGENTS.md。混着写，后期没法单独调整。
5. **只加不减**。agent 犯一次错补一条，半年后全是过时补丁。定期清理和代码 review 同等重要。

## 可复用建议

- **错题本机制**：每次 agent 行为不符合预期，先问自己"这能不能变成一条 AGENTS.md 规则"。能落文件的，就不要口头发脾气。
- **事实在前，规则在后**：环境类条目改动频率低，放文件开头；行为规则改动频繁，集中放在后面便于维护。
- **具体步骤下沉**：AGENTS.md 只写"什么情况调用哪个技能"，详细操作步骤放到对应的 skill 文件里，保持手册本身轻量。
- **用 git 管理工作空间**：规则变更有 diff 可查、可回滚，也方便在多台机器间同步。

## 总结

AGENTS.md 的本质，是把反复的"调教"固化为配置。它的价值不在于写得多全，而在于每一条都可执行、可验证、可删除。把每次纠偏沉淀成一条规则，agent 的行为才会随使用时间收敛，而不是每天重新磨合。手册写得越好，你越感觉不到它的存在——这正是它该有的状态。
