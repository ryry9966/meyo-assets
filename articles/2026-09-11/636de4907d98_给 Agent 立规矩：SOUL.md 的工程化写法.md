## 背景

在 OpenClaw 里，决定 Agent 行为的不只是模型，还有工作区里的几个 markdown 文件：AGENTS.md 管工作流，USER.md 和 memory 管上下文，而 SOUL.md 管的是"这个助手是谁"——性格、口吻、价值观和边界。很多人的 SOUL.md 要么空着，要么写成自我介绍式口号，跑一段时间后发现 Agent 时而热情过头、时而越界办事，换个模型更是判若两人。

## 问题

具体表现为四类：

1. **人格漂移**：长会话或升级模型后，语气、立场明显变化；
2. **边界模糊**：Agent 擅自对外发消息、花钱、改工作区外的文件；
3. **指令冲突**：插件和 MCP 工具注入的 prompt 与 SOUL.md 打架；
4. **token 浪费**：SOUL.md 每轮都会进上下文，写太长既费钱又稀释注意力。

## 做法

我的 SOUL.md 模板分五段，控制在 100 行以内：

1. **身份**：一两句话，说清角色定位和口吻基线。
2. **原则**：3~5 条价值观，写"遇到 X 优先 Y"，不堆形容词。
3. **风格**：回复长度、语气、是否用 emoji，各给一个正反例。
4. **边界**：核心部分。每条写成可触发的规则——"凡涉及对外发消息、支付、删除文件，先列出计划并等待确认"。
5. **升级规则**：什么时候停下转人工，比如连续两次失败、涉及法律医疗建议。

边界语句有个公式：**触发条件 + 动作（确认/拒绝/转交）**。"注意安全"这种写法等于没写。

另外坚持两点：SOUL.md 进 git 版本管理，改动像代码一样走 review；动态信息（用户偏好、当前项目）放 USER.md 和 memory，SOUL.md 保持接近静态，一个模型周期才改一次。

## 踩坑点

1. **写成营销文案**。"你是最强大最贴心的助手"对行为没有约束力，模型不会因此更可靠。
2. **只写负向规则**。模型对"遇到 X 时改为做 Y"的遵循度明显更好，每条"不要做"最好补一个正向出口。
3. **和插件冲突**。部分 MCP 工具会注入自己的系统级指令，优先级处理不好会盖过 SOUL.md 的边界。接新插件时，先用几个越界探测 prompt 验一遍。
4. **拿 prompt 当安全边界**。SOUL.md 是软约束，注入攻击、模型抽风都可能绕过它。真正的强边界要在工具层做：MCP 工具白名单、沙箱隔离、支付类操作二次确认。prompt 只负责第一道。

## 可复用建议

- 建一份 10~20 条的探测 prompt 清单（越界请求、诱导套话、角色扮演攻击），每次改 SOUL.md 或换模型后跑一遍，当回归测试用。
- 五段式模板可以裁剪，但"边界"和"升级规则"两段别删。
- 模型大版本升级后人格漂移几乎必然发生，把重跑探测清单纳入升级 SOP。
- 多 Agent 场景下，共享同一段"原则"文本，各自身份段独立，避免语气分裂。

## 总结

SOUL.md 的维护成本很低，但决定了 Agent 在几百次对话后还是不是"同一个它"。把它当代码对待：分层、可测试、版本化。同时认清定位——prompt 层管人格和第一道边界，工具层管硬约束，两层配合才稳。
