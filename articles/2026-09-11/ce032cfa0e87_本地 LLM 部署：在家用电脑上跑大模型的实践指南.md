## 背景

最近把 Agent 自动化里的部分调用从云端 API 迁到了本地模型。动机很朴素：高频的工具编排任务（分类、抽取、格式化）对模型上限要求不高，但调用量大，API 费用和首字延迟都难受；另外有些本地数据不想出网。折腾两周，把过程和坑记录一下，给有同样需求的同学省点时间。

## 问题

家用电脑跑大模型，核心矛盾是**显存**。一张 8GB 卡跑 7B 模型还行，上下文一拉长就吃紧；14B 起步就得权衡量化精度；纯 CPU 推理能用，但慢到影响 Agent 体验。另一个隐性问题是生态：本地模型对 function calling 的支持参差不齐，接进 OpenClaw 这类 Agent 框架后，工具调用稳定性直接决定能不能用。

## 做法

1. **选运行时**。Ollama 上手最快，llama.cpp 可调参数最细，LM Studio 适合纯图形界面用户。我最终用 llama.cpp 的 server 模式：暴露的 OpenAI 兼容接口字段更全，接 Agent 时少踩兼容性问题。
2. **选模型和量化**。Qwen 系列 7B/14B 的 Q4_K_M 是性价比基线，工具调用训练相对扎实。先跑 Q4 建立基线，确认任务能过再考虑 Q6/Q8。
3. **估算显存**。粗略公式：权重 ≈ 参数量 × 每权重字节数（Q4 约半个字节），再留 20%–30% 给 KV cache 和激活。7B Q4 大约 4GB 权重 + 1–2GB 运行开销，8GB 卡刚好。
4. **接入 Agent**。server 起在 `127.0.0.1:8080`，在 OpenClaw 里配一个 OpenAI 兼容 provider 指过去。先用最小工具集（两三个 MCP 工具）验证调用链，再逐步放开。
5. **压测记录 tokens/s**。同一任务跑 20 次，记录生成速度和工具调用成功率，作为后续换模型、调量化的对比依据。

## 踩坑点

- **显存临界时的断崖式降速**：llama.cpp 会把放不下的层 offload 到 CPU，速度不是“略慢”而是暴跌。用 `-ngl` 逐层调，找到全 GPU 放得下的最大层数。
- **上下文别拍脑袋拉满**：ctx 设 32K 但 KV cache 放不下时，要么 OOM 要么悄悄换页。按任务实际长度设置。
- **小模型 function calling 不稳**：参数漏填、格式跑偏是常态。工具描述里写死参数 schema，系统提示里给一个调用示例，成功率明显改善。
- **并发是硬伤**：本地 server 基本单请求串行，Agent 并行发三个工具调用会排队，注意超时和重试设置。
- **Windows 环境**：WSL2 里跑 server 时，宿主机访问要走 localhost 转发，防火墙规则也要检查。

## 可复用建议

- **分层路由**：本地模型承接高频低成本任务（分类、摘要、草稿），关键决策留给云端大模型，整体成本能降一个量级。
- **固化压测脚本**：任务样本 + tokens/s + 调用成功率三件套，换模型或换量化后跑一遍即可横向对比，避免凭感觉。
- **显存留余量**：给系统和其他进程留 1GB 以上，避免推理跑起来整机卡死。

## 总结

本地 LLM 不是替代云端，而是给 Agent 体系加一层可控、可离线、边际成本为零的执行单元。务实的路径是：先把 7B Q4 的基线跑通、把工具调用链验证稳定，再按任务复杂度逐级上探。从能用到好用，中间隔的不是 bigger model，而是压测数据和路由策略。
