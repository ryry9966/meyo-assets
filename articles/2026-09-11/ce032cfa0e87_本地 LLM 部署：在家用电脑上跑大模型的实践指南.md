## 背景

做 Agent 和自动化的人，迟早会想把模型搬回本地：一是 API 按调用计费，Agent 循环动辄几十次工具调用，账单经不起跑；二是私有数据不想出网；三是希望整个链路离线可用。我自己在 OpenClaw 里挂了一组 MCP 工具做日志分析，全走云端时一天成本不低，于是花了一个周末把主模型切到本地，这里记录完整过程。

## 问题

家用电脑跑大模型，核心矛盾只有一个：**显存/内存预算 vs 模型质量**。7B 模型几乎任何机器都能跑，但工具调用格式遵循能力弱，Agent 场景经常输出坏 JSON；70B 质量够，但量化后也要 40GB 以上显存。中间的 14B~32B 量化模型是甜点区，但坑都藏在这段。

## 做法

**第一步：盘点硬件。** 我的主力机是 RTX 3060 12GB + 32GB 内存。经验法则：模型量化后体积 ≈ 参数量 × 0.6GB（Q4 级别），再留 20%~30% 给 KV cache。12GB 显存实际能全量放 7B~14B，32B 只能部分 GPU offload。

**第二步：选运行时。** 想省事用 Ollama，一条命令拉模型；想精细控制用 llama.cpp 直接编；要并发吞吐上 vLLM（但显存要求高）。家用场景推荐 Ollama，它默认暴露 OpenAI 兼容接口，OpenClaw 里把 base_url 指到 `http://localhost:11434/v1` 即可接入。

**第三步：选模型。** 中文 + 工具调用场景，我最终落在 Qwen2.5-14B-Instruct 的 Q4_K_M 量化上，约 9GB，12GB 显存刚好放下，推理速度 25~30 token/s，Agent 单步响应在可接受范围。32B 的 Qwen 也测过，offload 后掉到 6 token/s，多轮工具调用体感太慢，放弃。

**第四步：接进 Agent 链路。** 关键是验证工具调用质量：准备 10 个典型任务（查库、写文件、调 MCP 工具），让模型连续跑 20 轮，统计格式错误率和工具参数错误率。14B Q4 在我的测试里格式错误率约 3%，配合 OpenClaw 侧的重试逻辑可以兜住。

## 踩坑点

1. **上下文长度吃显存比模型本身还狠。** 32K context 的 KV cache 能额外吃掉 3~4GB，模型放得下不代表跑得动。Agent 场景历史膨胀快，建议先限到 16K 观察。
2. **量化级别别贪 Q2/Q3。** 工具调用对指令遵循极其敏感，Q4_K_M 是底线，再压会出现参数幻觉——模型"发明"不存在的工具字段。
3. **GPU offload 层数凭感觉调会翻车。** 显存利用率 95% 时极易 OOM，留 10% 余量反而总吞吐更高。
4. **长任务发热降频。** 连续跑一小时 Agent 后 token/s 掉了 15%，笔记本用户尤其注意散热。

## 可复用建议

- 先用现有硬件的最大显存反推模型上限，不要先选模型再凑机器；
- Agent 用途把"工具调用错误率"作为第一指标，perplexity 和榜单分数参考价值有限；
- 本地模型 + 云端模型混合调度：规划类步骤走本地大模型，需要长上下文精读的子任务回落到 API，OpenClaw 的模型路由配置就能做到；
- 所有配置写进脚本固化，换机重建成本极低。

## 总结

本地部署不是替代云端，而是给 Agent 链路多一层可控的选择。硬件够 12GB 显存，14B Q4 量化模型就能承担日常自动化任务的主力；再往上性价比急剧下降。先小规模验证工具调用质量，再决定本地化的边界，是最不容易返工的路径。
