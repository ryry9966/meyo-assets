## 背景

做 Agent 和自动化的人迟早会碰到两个问题：一是隐私——对话记录、家庭数据、自动化日志都要过一遍第三方 API；二是成本——一个 7×24 挂着的助手，API 账单比电费贵。本地部署大模型不是为了追平云端旗舰，而是把"够用的智能"留在自己手里。

## 问题

家用硬件跑大模型，硬约束只有一条：**显存**。其次是 Agent 场景特有的问题——模型必须可靠地输出工具调用，而很多小模型一量化，function calling 就开始飘。

## 做法与步骤

1. **盘硬件**。8GB 显存跑 7-8B Q4；16GB 跑 14B Q4；24GB 是分水岭，可勉强上 32B Q4。没有 N 卡的话，Mac 统一内存是另一条路，32GB 内存的 Mac 跑 14B 很舒服。
2. **选推理栈**。图省事用 Ollama（自带 OpenAI 兼容端点），要控制粒度直接上 llama.cpp，显存富裕且追求吞吐用 vLLM。Agent 场景优先选提供 `/v1` 兼容接口的方案。
3. **选模型**。看工具调用能力，不看榜单分数。14B 以下档位，Qwen 系列的 function calling 稳定性口碑较好，务必选官方支持 tool use 的版本。
4. **定量化等级**。Q4_K_M 是默认甜点；显存有富余升 Q5/Q6；Q2 以下不要碰，工具参数会乱编。
5. **接入 Agent**。把 OpenClaw 的模型配置指到 `http://127.0.0.1:11434/v1` 这类本地端点，并发数设为 1——家用显卡同时只能算一条请求。
6. **实测工具调用**。用你真实在用的 MCP 工具跑十几个场景，检查参数 JSON 是否合法、是否漏调用、是否幻觉出不存在的工具。

## 踩坑点

- **KV cache 比权重更吃显存**。标称 32K 上下文的模型，开满后显存占用接近翻倍。Agent 多轮循环涨上下文特别快，建议配置摘要压缩或截断策略。
- **并发是假的**。Agent 并行发三个工具调用，本地推理实际是排队串行，很容易触发上游超时。把 Agent 并行度调低，超时放宽到 120s 以上。
- **量化伤工具调用**。同一个模型 Q8 下正常，Q4 下偶尔参数字段缺失。上线前必须用真实工具链做回归。
- **笔记本 GPU 长跑会降频**。跑半小时 token 速率掉一半是常态，认真用就上台式机。
- **别信跑分**。跑分高 2 分，不如工具调用成功率高 10%。

## 可复用建议

- **分层路由**：简单任务（摘要、分类、改写）走本地，复杂推理和长上下文走云端 API。多数 Agent 框架支持 fallback，这是本地模型最务实的用法。
- **建自己的回归集**：存 10-20 条真实任务 prompt 加期望的工具调用结果，每次换模型或量化跑一遍，五分钟内得出能不能用的结论。
- **记录 token 统计**：tokens/sec 掉速大概率是散热问题；上下文占用超 70% 就触发压缩。
- **锁版本**：量化文件和推理栈都会更新，可复现的前提是 pin 住版本。

## 总结

本地部署的定位很清楚：不是替代云端，而是给 Agent 体系加一层"私有、便宜、离线可用"的基础档。从 Ollama + 一个 14B Q4 开始，接进 OpenClaw，用真实 MCP 工具验证调用质量，跑稳了再考虑更大的模型。硬件上，一张 16GB 显存的卡加 32GB 内存，是目前性价比最好的起点。
