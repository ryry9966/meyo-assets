## 背景

社区里聊 OpenClaw 工作流时，常见两种极端：一种是所有请求都打 GPT，改格式、抽字段、补工具参数这类活也用旗舰模型，月底 token 账单很难看；另一种是全走本地模型省钱，结果多步规划和长上下文任务翻车率明显上升。多模型路由要解决的核心问题就一句话：**哪类请求配哪种算力**。

## 问题

难点在于没有现成的“复杂度探测器”——任务难度往往跑起来才知道。而且 OpenClaw 里大量流量来自插件和 MCP 工具调用，对输出格式敏感，本地小模型一不稳定，整条 agent 链路就断。路由策略必须在“省钱”和“不断链”之间找到可量化的平衡点。

## 做法

1. **任务分桶**：把流量按类型分成两桶。结构化抽取、短文本改写、工具参数填充归简单桶；多步规划、长上下文、代码生成、歧义指令归复杂桶。
2. **静态规则起步**：在 `openclaw.yaml` 的 `routes` 段按任务类型映射模型。简单桶走本地（vLLM 或 Ollama 起一个 14B 级别的 Qwen 就够），复杂桶走 GPT。
3. **失败升级（escalation）**：本地侧设硬超时（比如 8 秒）和输出 schema 校验，失败或校验不过就带上原始上下文升级到 GPT，并给请求打上升级标记，方便事后统计。
4. **度量回看**：每条路由记录 token 消耗、首 token 延迟、失败率、人工修正率。跑两周数据再回头调桶边界，不要拍脑袋。

## 踩坑点

- **上下文静默截断**：本地模型窗口小，长会话被悄悄截掉，agent 表现为“失忆”而非报错，非常隐蔽。路由层要加 prompt 长度预检，超限直接走云端。
- **工具调用格式差异**：小模型 function calling 偶尔输出不合规 JSON，MCP 插件解析直接挂。schema 校验加一次重试能挡掉大部分，但别裸奔。
- **升级风暴**：本地失败再走 GPT，延迟叠加，P95 可能翻倍。超时和重试上限必须硬编码，别信框架默认值。
- **自评置信度不可靠**：让小模型自己判断“我行不行”基本没用。路由决策优先依赖任务类型规则，别指望模型自评。
- **流式行为不一致**：本地和云端的流式输出节奏差很多，前端要做兜底 UI，否则看起来像假死。

## 可复用建议

- 顺序很重要：规则先行、数据驱动，最后才考虑上分类器。分类器本身可以用本地小模型做单标签分类，但它要单独评测，别和业务模型混在一起调。
- 所有工具 schema 在路由层归一化，别让插件直接面对两种模型的原生调用格式。
- 简单桶的高频重复请求加缓存，命中率往往出乎意料，这块省得最干脆。

## 总结

多模型路由不是省钱技巧，而是把贵的智能用在刀刃上的工程问题。实践顺序记四步：**分桶 → 静态规则 → 失败升级 → 数据回看**。先让它在生产里跑起来，攒两周真实流量，再谈让它变聪明。有同学已经跑了类似分层路由的，欢迎在评论里贴一下你们的桶边界和失败率数据。
