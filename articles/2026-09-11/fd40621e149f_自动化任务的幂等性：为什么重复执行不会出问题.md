## 背景

在 OpenClaw 里跑过定时任务、webhook 触发或 MCP 工具调用的人，多半见过这种场景：网络抖动导致超时，框架自动重试；或者自己不确定任务是否跑过，手动又执行了一遍。结果数据库里多了三条重复记录，同一个渠道发了两次通知。

自动化系统的可靠性，从来不是建立在"永不失败"上，而是建立在"失败了可以安全重跑"上。幂等性（Idempotency）就是让重跑变得安全的那个性质：**同一个操作执行一次和执行多次，最终结果一致。**

## 问题

典型的非幂等操作：`insert into orders`、`send_message`、`counter++`。它们执行两次就产生两次副作用。而在 Agent 场景里，重复执行几乎不可避免：

- **传输层重试**：HTTP 超时后客户端重发请求；
- **Agent 层重规划**：LLM 判断上一步失败，再调一次工具；
- **人工重触发**：不确定跑没跑过，干脆再跑一次。

更关键的一点：不能指望模型"记得"自己做过什么。上下文可能被压缩，会话可能重启，凭记忆去重天然不可靠。**幂等必须做在工具和数据层，而不是对话层。**

## 做法

按投入产出比排序，几个可落地的步骤：

1. **给每个逻辑任务一个稳定 ID**。注意是"逻辑任务"，不是"本次执行"。重试必须复用同一个 ID，每次重试都重新生成 UUID 是最常见的错误。
2. **用 upsert 代替 insert**。靠数据库唯一约束兜底，`insert ... on conflict do nothing` 比应用层先查后写可靠得多。
3. **副作用落盘前先查标记**。维护一张已处理任务表（或状态文件），工具入口先检查该 ID 是否处理过，处理过就返回上次的结果。
4. **把动作改成状态描述**。能写"把状态置为 done"，就不要写"执行一次部署"。声明式接口天然幂等。
5. **拆小步骤**。长链条任务让每一步独立幂等，从头重跑的代价才可接受。

## 踩坑点

- **重试发生在多个层级**。你以为只有 Agent 会重试，实际上 HTTP 库、MCP 客户端、上游调度器都可能重发。幂等键必须贯穿全链路。
- **先查后写的竞态**。两个并发请求同时查到"不存在"，然后都写入。解法是数据库唯一约束，不是应用层检查。
- **时间窗口去重**。"五分钟内相同请求忽略"在任务间隔不确定时必然漏。ID 去重比时间去重可靠。
- **部分成功**。五步任务在第三步挂掉，重跑会重复前两步的副作用。要么每步幂等，要么记录断点、从断点续跑。

## 可复用建议

给每个新工具或插件收尾时，问自己一句：**同样的输入调用两次，会怎样？** 答案如果不是"无事发生"，这个工具就还没写完。这一条检查比任何框架特性都便宜，也最常被跳过。

## 总结

幂等性是重试的前提，重试是自动化的前提。在 OpenClaw 这类自动化体系里，与其祈祷网络稳定、模型不犯糊涂，不如把每个工具都设计成"可以随便重跑"的样子。多做这一步设计，换来的是半夜告警响起时，你敢直接按下"重新执行"的底气。
