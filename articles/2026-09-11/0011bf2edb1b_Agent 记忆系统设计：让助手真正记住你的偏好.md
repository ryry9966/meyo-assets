## 背景

LLM 本身无状态。今天你告诉助手“回复尽量简短、代码示例用 Python"，明天开新会话它全忘了。对 OpenClaw 这类常驻 Agent 来说，记忆不是加分项，而是基本能力：没有它，每次会话都在重新培养一个实习生。

## 问题

常见的错误做法有两种。一种是把用户偏好全塞进 system prompt——几轮之后就超预算，而且改一条要手动改配置。另一种是把所有历史对话存下来靠检索——噪音极大，模型分不清“用户随口提过”和“用户明确偏好”。真正的难点在写入侧：什么时候记、记什么、冲突了听谁的。

## 做法

**1. 分层存。** 我把记忆拆成三层：会话内工作记忆（受上下文窗口约束）、情节记忆（会话结束后的摘要，用于回顾“上次聊到哪”）、偏好记忆（结构化事实，如“部署默认走 Docker"）。长期只存第三层，其余靠摘要压缩。

**2. 写入走独立管线，不挤占主对话。** 会话结束后跑一个提取 pass（用便宜的小模型即可）：从对话中抽出候选事实，输出结构化 JSON——字段包括 key、value、confidence、来源时间戳。然后三步处理：与已有记忆做相似度去重；发现矛盾时“新值覆盖旧值，但保留版本”；低置信度丢弃或标记待确认。

**3. 读取决定体验。** 新会话启动时不注入全部记忆，而是按当前任务检索，取 top 3~5 条，设注入预算上限（我这边 500 token）。用户偏好里八成是高频通用项，剩下两成才需要按场景检索。

**4. MCP 工具化。** 把记忆做成一个 memory server，暴露三个工具：`memory_write`（用户明确说“记住这个"时由 Agent 调用）、`memory_search`、`memory_delete`。写权限收紧、删权限放开，用户随时可用 `/memory` 查看和清理。

## 踩坑点

- **记忆污染最难撤。** 早期我允许 Agent 对话中途随手写入，结果把用户的临时假设当偏好存了下来，污染后续所有会话。现在只保留两个写入入口：用户显式要求、会话结束后的提取 pass。
- **偏好会过时。** “喜欢详细解释”半年后可能变成“只要结论”。必须有版本和时间戳，覆盖而不是报错。
- **注入预算失控。** 有一阵检索命中太多，system prompt 膨胀，反而稀释了任务指令。硬性预算上限是必须的。
- **别上来就上向量库和知识图谱。** 我第一版就是 SQLite 一张表 + LIKE 查询，跑了两个月才换 embedding。偏好记忆通常几百条量级，全文检索够用。

## 可复用建议

1. 记忆当数据管，不当 prompt 管：有 schema、有版本、可导出。
2. 写入从严、读取从宽：宁少记，靠检索补。
3. 给用户可见性和控制权：能看、能删、能改，才敢长期用。
4. 提取用小模型省成本，主对话模型不承担记忆职责。
5. 先调好读取路径，再优化写入——体验主要在读取。

## 总结

Agent 记忆本质是数据工程问题，不是提示词问题。核心就四件事：结构化存储、独立写入管线、带预算的检索注入、用户可控。从一张 SQLite 表开始，跑通再演进，比一上来搭复杂架构靠谱得多。欢迎在评论区交流你的记忆层实践。
