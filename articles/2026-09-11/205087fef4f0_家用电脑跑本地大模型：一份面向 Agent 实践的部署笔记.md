## 背景

过去一年我把一台 16GB 显存的台式机改造成了本地推理节点，给日常的 Agent 自动化流程供模型。动机很朴素：批量任务跑云端 API 月账单不低，且部分涉及私有数据的流程不方便出网。这篇帖记录从选型到接入工作流的全过程，以及那些文档里不会写的坑。

## 问题

本地跑大模型，门槛早就不在“能不能跑”，而在两点：

1. **能不能稳定服务 Agent**。自动化流程要求模型可靠输出结构化结果、正确触发工具调用，这比聊天场景难得多。
2. **资源约束下的取舍**。显存、上下文长度、速度三者互相挤压，选错组合会得到一个“能跑但没法用”的服务。

## 做法与步骤

**第一步：盘硬件，定模型上限。** Q4 量化后的模型体积约等于显存需求（还需预留 KV cache 开销）：7B~8B 约 5GB，14B 约 9~10GB，32B 起 20GB。显存不够可把部分层放 CPU，但速度明显下降；纯 CPU 机器建议不超过 8B。

**第二步：选运行时。** 我用 Ollama，理由是默认暴露 OpenAI 兼容接口（`/v1/chat/completions`），Agent 侧只需把 base_url 指到 `http://localhost:11434/v1`，代码几乎零改动。追求极限性能可以直接跑 llama.cpp，但接入成本高一些。

**第三步：量化从 Q4_K_M 起步。** 这是质量和体积的平衡点。Q2 以下在工具调用场景崩得很快，不建议。

**第四步：接进 Agent / MCP 工作流。** 本地端点当普通 OpenAI 兼容后端用即可。MCP server 与模型之间通过 Agent 框架解耦，不需要本地模型“认识”MCP。

**第五步：用真实任务压测。** 拿 20~50 条生产样本（含工具调用、长输入、JSON 输出）跑批，看成功率和延迟，别只看 benchmark。

## 踩坑点

- **小模型的 function calling 是重灾区。** 同一模型的基础版和 tool-use 微调版差距巨大，务必选对变体；即便如此，代码层仍要做 JSON schema 校验加重试。
- **上下文开太大直接 OOM。** KV cache 随上下文线性增长，8GB 显存跑 8B 模型时把 context 拉到 32k 必炸，默认值够用就别动。
- **GPU offload 层数别拍脑袋。** 逐层加，观察 token 速度拐点，而不是抄别人的配置。
- **长任务会撞温度墙。** 我跑过两小时的批量任务，40 分钟后速度掉了三成，风扇策略和机箱风道值得提前检查。
- **模型文件校验。** 损坏的 GGUF 会输出乱码，首次使用前核对 sha256。

## 可复用建议

1. **分层路由**：格式化、分类、摘要类任务走本地小模型，长链路规划和复杂推理回落云端。我的流程里本地承担了约七成调用量。
2. **固定评测集**：换模型只跑同一套真实任务样本，避免被榜单带偏。
3. **把本地模型当“工人”而非“顾问”**：它擅长稳定重复的窄任务，别指望它做精细的多步决策。

## 总结

本地部署的价值不是替代云端，而是给自动化流程增加一层可控、低成本、可离线的兜底。硬件门槛比想象中低：一张 12GB 以上的显卡加 Q4 量化的 8B 级模型，足以撑起日常 Agent 任务的大头。真正的工作量在接入之后的校验、重试和路由策略上——那才是工程该花时间的地方。
