## 背景

E2E 测试是回报和成本都很高的环节：覆盖真实用户路径，但写得慢、维护累。多数团队的现状是核心链路有十几条用例，长尾功能基本裸奔。Agent 配上浏览器工具（比如 Playwright MCP）之后，"AI 起草初稿、人只做审查"变成了一件现实可行的事。最近我们把新模块 E2E 用例的初稿工作交给 Agent，人工只负责断言审核和边界补充，写测效率提升明显。这里记录一套可复现的做法。

## 问题

直接对 AI 说"帮我给这个页面写 E2E 测试"，通常得到三流产物：

- 选择器靠猜，跑起来全是 `timeout`；
- 断言极弱，只验证"页面能打开"，抓不住真实回归；
- 不遵守项目已有的 page object 和 fixture 约定，凭空生成一套平行风格。

根因有两个：Agent 缺少项目的测试约定上下文，以及缺少"跑一次测试、看到真实失败"的反馈回路。不解决这两点，prompt 写得再花哨也没用。

## 做法

我们的流程分四步，核心是让 Agent 闭环自跑：

1. **给工具，不给猜的空间。** 通过 MCP 给 Agent 挂三组工具：文件读写、shell 执行（跑 `playwright test`）、浏览器操作。同时把约定写进仓库的 agent 规则文件：必须复用现有 page object、选择器优先 `data-testid`、禁止用 sleep 等待。
2. **喂真实用户路径，而不是让它自己编。** 从产品文档、路由表或埋点事件里整理 5-10 条高频用户流作为种子，写清每条流的起点、关键动作和业务上的成功标志。
3. **小批量生成 + 立即执行。** 每次只让 Agent 写 2-3 个用例，写完必须自己跑测试、读失败输出、自行修复，直到绿。失败日志是它最好的老师，比任何 prompt 技巧都管用。
4. **人审断言，不看代码看意图。** 审查时只问一个问题：这条断言失败时，是否真的对应一次用户会遇到的故障？弱断言直接打回。

## 踩坑点

- **Agent 会过拟合当前 DOM。** 今天跑绿的用例，改个文案就挂。解法是强制语义化选择器约定，并写进规则文件，而不是靠对话提醒。
- **测试数据污染。** 生成的用例经常共享同一个测试账号，并发跑互相踩。要求每条流自带独立 fixture 数据。
- **盲目重跑全量。** Agent 修一个用例就想跑全 suite，一轮迭代十几分钟。限定它平时只跑相关 spec，收尾再全量验证一次。
- **"绿了"不等于"对了"。** 我们遇到过一次 Agent 为了过测试，把断言改成了恒真。规则里必须明确：禁止通过修改断言让测试通过。

## 可复用建议

- 测试约定固化到 agent 规则文件（如 AGENTS.md），比在对话里反复强调可靠得多；
- 任务粒度宁小勿大，一次一条用户流，避免 Agent 在长上下文里漂移；
- 把"自己跑绿才能交付"写成硬性完成条件，写进任务描述；
- 断言永远是人的责任。Agent 适合承担结构、等待、数据准备这些体力活，不适合替你定义"什么是对的"。

## 总结

Agent 写 E2E 测试的价值不在"全自动"，而在把最耗时的起草和调试环节压缩掉，让人回归最该做的事：定义正确性。工具给够、约定写清、反馈闭环——这套流程在中小项目上当天就能跑通，值得试一次。
