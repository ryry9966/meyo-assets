## 背景

OpenClaw 的模型配置天然支持 primary + fallbacks 模型链，也允许给不同 Agent 绑不同模型，但很多部署跑成两个极端：要么全链路旗舰云端模型，一天十几刀；要么全本地，工具调用十次坏三次。我们内部跑了一段时间后，把任务拆开路由，成本降了一半以上，质量没有肉眼可见的损失。这篇记录一下拆分思路。

## 问题

所有请求塞给同一个模型，问题不在"能不能跑"，而在三件事：

1. **成本**：交互式 Agent 一天几百次调用，其中摘要、分类、格式化这类重复任务占了七成 token，但它们根本不需要旗舰模型。
2. **延迟与可用性**：云端 API 限流、网络抖动时整条链路卡死；本地模型没有外部依赖，但 GPU 排队也要时间。
3. **隐私**：频道消息、日志摘要这类内容，不少人不想出网。

## 做法

核心原则：**按任务类型路由，不按时间或感觉路由**。

**1. 分层定责。** 把 Agent 工作拆成三层：

- 规划与决策层（拆解任务、决定调用哪个工具、写代码）→ GPT 级云端模型；
- 执行层（格式转换、摘要、翻译、简单分类）→ 本地 14B~32B 级模型；
- 感知层（embedding、去重、打标）→ 本地小模型，且 embedding 模型一旦定了就别换。

**2. 用多 Agent 分流，而不是单 Agent 内部切换。** 这是最干净的做法：主交互 Agent 绑云端主力；定时摘要、日报这类 cron Agent 绑本地模型；批量抽取的子 Agent 也走本地。路由粒度在 Agent 级，排查问题时一目了然。

**3. fallback 链显式设计。** primary 挂云端主力，fallback 第一级挂另一家云端，最后才落到本地。不要把本地模型当"隐形备胎"顶在关键链路上——降级发生时你必须知道。

**4. 建一个金标集做回归。** 20~30 条典型 prompt（覆盖工具调用、长上下文、严格 JSON 输出），每次改路由后跑一遍，人工核对结果。没有这个，路由调整就是玄学。

## 踩坑点

- **小模型工具调用是重灾区**：参数漏字段、JSON 里混注释、工具名写错。表面看 Agent "跑完了"，执行链其实是断的。建议本地模型只承接无工具或单工具任务。
- **上下文窗口**：本地模型常见 8k/32k，长会话在压缩前后表现差异很大，换模型前先确认窗口大小。
- **fallback 掩盖故障**：错误被静默降级，你以为在用 A 模型，实际在用 C。会话日志里 per-request 的 model 字段要定期盯。
- **参数语义不一致**：maxTokens、思考模式的含义各家不同，配置直接照搬会出怪问题。
- 别拿 reasoning 模型跑"翻译这段话"级别的任务，纯粹烧钱。

## 可复用建议

- 先全云跑一周，用日志统计各任务类型的 token 分布，再决定哪些下沉本地——用数据决策，别拍脑袋。
- 成本看板按"模型 × 任务类型"两个维度统计，一天看一次足够。
- 关键 Agent 的降级宁可失败报错，也不要静默换成弱模型。
- 换 embedding 模型等于重建向量库，成本极高，动之前三思。

## 总结

多模型路由的本质是在质量、成本、延迟之间做**显式取舍**：决策层交给云端旗舰，重复性执行层下沉到本地，降级链路做到可见、可审计。先用日志说话，再动配置，路由策略就能稳定演进，而不是反复翻烧饼。
