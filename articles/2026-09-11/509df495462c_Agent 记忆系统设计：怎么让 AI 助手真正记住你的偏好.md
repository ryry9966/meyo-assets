## 背景

Agent 默认是无状态的。每次会话开始，system prompt 一样，上下文从零积累。你上周说过"回复用中文、代码示例用 TypeScript、时区按 UTC+8"，这周它照样写英文注释。上下文窗口再大也不等于记忆——窗口是工作内存，记忆是跨会话的持久状态，这是两件事。

## 问题

多数人的第一版做法是把"用户偏好"直接堆进 system prompt，几周后通常出现三类问题：

1. **膨胀**：条目越积越多，token 开销上升，注意力被稀释，反而记不住重点；
2. **过时**：早期记录和新习惯冲突，agent 拿旧偏好当圣旨；
3. **不可审计**：用户不知道它为什么突然换语气，也删不掉某条记忆。

## 做法

我落地了一套分层设计，核心是读写分离。

**存储分三层：**

- **热层（硬偏好）**：十几条以内的 key-value，如语言、时区、代码风格。每次会话无条件注入 system prompt；
- **温层（事实记忆）**：带时间戳的事件记录（"正在重构支付模块""部署在自建 K8s"），用 embedding 检索，按相关度取 top 3–5；
- **冷层（会话摘要）**：滚动摘要，用于长项目续接，只在会话开头注入一段。

**写入路径**：两个来源。显式指令（用户说"记住…"）高置信直接写入；隐式信号（重复出现的模式）先进候选池，累计命中 3 次以上再固化，避免一次性任务被当成永久偏好。

**更新与衰减**：每条记忆带 `source / confidence / updated_at / scope` 四个字段。新旧冲突时不静默覆盖，向用户确认一次；90 天未命中的记忆降权，由定时整理任务合并去重。

**读取路径**：热层全量注入 + 温层向量检索，每条注入的记忆带来源标签，agent 引用时能说清"因为我记住了你 X"，而不是凭空行为。

工程上不需要复杂基建：SQLite 起步足够，把 `memory_search` / `memory_write` 封装成 MCP tool，任何支持 MCP 的 agent 客户端都能复用同一份记忆；`/memory` 的查看与删除命令用 OpenClaw 插件暴露即可。

## 踩坑点

- **隐式捕获太激进**。用户临时说一句"这周赶进度，回复短点"，被固化成永久偏好，一个月后还在生效。候选池 + 命中次数阈值能挡掉大部分误伤。
- **检索 top-k 贪多**。超过 5 条注入后，模型开始混淆哪些与当前任务相关。宁缺毋滥。
- **只写不删**。记忆系统最大的成本不是存储，是过时记忆的干扰。整理任务必须定时自动跑，不能想起来才跑。
- **没有 `/memory` 命令**。用户看不到、删不掉的记忆，迟早变成信任问题。

## 可复用建议

- **先分层再上强度**：KV + 向量检索覆盖 90% 场景，知识图谱等记忆稳定后再考虑；
- **硬软偏好分开**：硬偏好（语言、时区）无条件注入，软偏好（语气、详细度）按场景检索；
- **记忆是数据生命周期问题**：写入门槛、冲突策略、衰减规则、用户可控出口，四者缺一不可；
- **度量命中率**：抽样 20 个会话看偏好是否用对，比换 embedding 模型收益大。

## 总结

让 agent 记住偏好，本质是设计一套小型数据系统，而不是往 prompt 里塞文字。分层存储、受控写入、可衰减、可审计——先跑通最小闭环再迭代。记忆系统的上限不在模型，而在你对数据生命周期的认真程度。
