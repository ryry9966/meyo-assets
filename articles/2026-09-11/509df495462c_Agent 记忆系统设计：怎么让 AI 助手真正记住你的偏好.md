## 背景

LLM 本身是无状态的。会话一结束，上下文清零——你上周明明说过"回答用中文、示例代码用 TypeScript、别加表情符号"，今天它照样一个都不记得。在 OpenClaw 这类长期运行的 Agent 场景里，记忆不是锦上添花，而是决定助手"是否可用"的底线能力。配合 MCP 把记忆做成独立服务，是目前比较务实的路径。

## 问题：三种常见的失败做法

1. **全量塞 system prompt**：记忆越多 token 越贵，且无关记忆会稀释指令，模型行为越来越飘。
2. **只靠对话历史回放**：上下文窗口有限，几天前的偏好早被截断在窗口外。
3. **一上来就上向量检索**：语义相近不等于相关。查部署问题时，召回的可能是一堆"喜欢深色主题"的旧偏好。

核心矛盾：记忆要持久、可检索、可更新，但不能无限膨胀。

## 做法：一个最小可用的分层设计

**1. 分层存储**

- 会话内记忆：当前对话，不持久化
- 偏好记忆（重点）：语言、代码风格、回复长度等稳定偏好
- 事实记忆：项目结构、常用命令、环境信息

每条记忆是结构化记录，不是自由文本：

```json
{
  "key": "code_style",
  "value": "TypeScript, 避免 any",
  "scope": "global",
  "confidence": 0.8,
  "updated_at": "2025-01-10",
  "source": "session#42"
}
```

**2. 提取：单独一轮 LLM 调用**

会话结束后（或定时），用专门的提取 prompt 扫描对话，只输出符合 schema 的候选记录。提取和主对话分开，不污染主流程，也方便单独换模型。

**3. 存储与检索**

- 存储：SQLite 或 JSONL 起步足够。偏好类数据量小，关键词 + 标签检索就能覆盖，向量库可以后置
- 检索：会话开始时按 scope + key 注入 top-N；会话中通过 MCP tool（如 `memory_search`）按需召回
- 建议把读写封装成独立的 MCP server，Agent 只见工具、不见实现

**4. 更新与衰减**

- 同 key 新值覆盖旧值（latest wins），保留 `updated_at`
- confidence 随时间衰减，低置信记忆不主动注入
- 用户显式纠正的记录，confidence 直接拉满并打标

## 踩坑点

- **过度提取**：一次性指令被存成永久偏好。提取 prompt 必须限定"只提取重复出现或用户明示的偏好"，并给分类设白名单。
- **过期偏好**：用户换技术栈了，旧记忆还在干扰。除了时间戳，冲突时可以把新旧值都摆给模型现场判断。
- **记忆投毒**：记忆内容会进 prompt，等于持久化的注入面。写入前校验来源，至少别把网页抓取内容直接入库。
- **不可见性**：用户不知道助手"记得什么"，就不会信任它。把记忆导出成可编辑的 JSONL/markdown，提供 list / delete 命令。

## 可复用建议

- 先跑"结构化文件 + 提取轮 + 按需注入"，用两周再决定要不要向量检索——多数场景用不上
- 记忆条目控制在几十条量级，宁可少而准
- 每条留 `source` 字段，出问题时能回溯是哪次对话写进去的
- 提供 `/memory` 查看命令：透明比聪明重要

## 总结

Agent 记忆本质是数据工程问题：schema 设计、更新策略、失效机制，比 prompt 技巧重要得多。从最小结构化方案起步，让记忆可检查、可纠正、可删除，助手才会从"每次都重新认识你"变成"真的了解你"。欢迎在社区贴出你们的记忆 schema，互相抄作业比闭门造车快得多。
