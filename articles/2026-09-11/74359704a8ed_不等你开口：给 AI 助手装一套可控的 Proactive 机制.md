## 背景

大多数 AI 助手的默认形态是"被动应答"：你提问，它回答，会话结束就归零。但真正省时间的场景往往相反——磁盘快满了、日历上有冲突、某个指标连续三天爬坡，等你发现时已经晚了。社区里不少基于 OpenClaw + MCP 搭的自动化流程，最后都在往同一个方向演进：让助手具备主动发现、主动汇报、甚至在受控范围内主动执行的能力。

## 问题：主动不等于乱动

proactive 做砸的样子大家都见过：每小时推一条没用的"摘要"、半夜发消息、重复执行已办过的事，甚至触发事件循环把自己绕死。核心矛盾在于：**判断"该不该说、该不该做"的应该是显式策略，而不是模型即兴发挥**。没有策略的 proactive 就是垃圾通知生成器。

## 做法：拆成观察 → 决策 → 行动 → 汇报 四段循环

**1. 观察层：定时与事件双通道。** 用 cron 做低频巡检（如每 30 分钟），用 webhook / 文件监听做事件触发。巡检先用脚本或 MCP 工具做廉价检查，命中条件才升级到 LLM 判断，控制 token 成本。

**2. 决策层：把"允许主动做什么"写成策略文件**，而不是塞在 system prompt 里靠模型自觉。按风险分四级：

- L0 只记日志，不打扰
- L1 汇报但不执行
- L2 生成草稿，等确认
- L3 低风险可逆操作直接执行（如整理目录、重命名），全程留审计记录

**3. 行动层：所有写操作必须幂等**，带去重键。执行前先检查目标状态是否已满足，避免重试造成重复副作用。

**4. 汇报层：批量合并、设免打扰时段、同类事件冷却**（如同类告警 2 小时内只推一次）。

再加一个反馈回路：每次主动推送记录用户是采纳、忽略还是拒绝，周度统计采纳率，低于阈值的触发器直接下线。

## 踩坑点

- **自触发死循环**：助手自己的消息进了事件流，又触发自己处理。解法是给所有自产事件打标记，观察层直接跳过。
- **心跳成本失控**：高频巡检全走 LLM，一天烧掉的 token 比对话本身还多。原则是"脚本能判断的不进模型"。
- **权限第一天给太大**：上来就能发消息、写文件，出一次事故就再也不敢开。建议从纯只读的 L1 起步，跑两周再升 L3。
- **时间与边界**：免打扰时段要按用户时区算，别用服务器时区；"低风险"的定义要写死在策略里，不要让模型自己现场判断。

## 可复用建议

- **策略即配置**：分级、冷却、免打扰全部放配置文件，改行为不改编排代码。
- **先有 undo，再有 auto**：每个主动动作都要能撤销，没有回滚路径的操作永远留在 L2。
- **用采纳率而非执行次数衡量质量**：数字难看的触发器宁可关掉。

## 总结

proactive 的价值不在"做得多"，而在"说得准、做得稳"。把观察、决策、行动、汇报拆开，用显式策略约束主动性，用反馈回路修剪噪音，助手才能从"随叫随到"进化成"靠谱的同事"。建议先从一个只读巡检触发器开始跑通全链路，比一次堆十个功能有效得多。
