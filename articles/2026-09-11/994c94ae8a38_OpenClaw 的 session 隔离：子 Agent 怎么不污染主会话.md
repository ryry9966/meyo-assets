## 背景

用 OpenClaw 跑自动化任务一段时间后，几乎一定会进入多代理场景：主会话负责拆解需求、汇总结果，子代理负责检索、批处理、调用 MCP 工具。如果子代理的上下文和主会话共用一套 transcript，或共享同一个工作区，跑得越久问题越明显——主会话越来越"健忘"，早期指令莫名失效，工具状态开始串台。

## 问题

实际踩到的污染主要有三类：

1. **上下文污染**：子代理把中间过程（原始日志、网页全文）回灌主会话，几轮下来窗口被塞满，有效指令被稀释，模型开始忽略早期约束。
2. **工具与连接状态污染**：多个子代理共用同一个 MCP server 实例时，有状态工具（浏览器会话、登录态、分页游标）互相干扰，A 的操作把 B 的状态改了。
3. **工作区污染**：子代理在主仓库目录里改文件、拉分支甚至 commit，主会话后续读到的状态已经不对。

## 做法

我目前的隔离方案分三层：

**第一层：session 隔离。** 每个子代理派生时分配独立 session id 和独立 transcript。主会话只保留子代理的"返回契约"——一个结构化 JSON 摘要（状态、结论、产物路径、错误码），原始过程留在子会话里，需要时按 id 回查。

**第二层：workspace 隔离。** 子代理在独立子目录或临时容器内工作，产物写在自己的输出区，主会话对子目录默认只读。涉及 git 的任务，要求子代理在 detached 状态下操作，禁止直接 commit 到主分支。

**第三层：工具作用域隔离。** 有状态的 MCP server 按子代理实例化，无状态的可以共享。子代理的工具白名单只给完成任务所需的最小集合，环境变量和凭证按 session 作用域注入，不落全局。

## 踩坑点

- **摘要失败比超长更危险**：返回契约生成失败时，不要把原始输出兜底回主会话，宁可标记失败让主会话重试，否则隔离形同虚设。
- **重试别复用旧 session id**：否则上一次的脏上下文会"复活"。我吃过一次亏，排查很久才发现是重试逻辑带着旧 transcript 在跑。
- **有状态工具的"看似无状态"**：浏览器类 MCP 工具即使声明无状态，cookie 和 storage 也可能残留，涉及登录态的任务必须独立实例。
- **观测要按 session 拆**：token 计量和工具调用审计如果合并统计，既定位不了泄漏源，还容易把子代理的消耗误算到主会话头上。

## 可复用建议

1. 先定义返回契约模板再写子代理逻辑，字段固定：`status / result / artifacts / errors`，禁止自由文本摘要。
2. 把 session 隔离、workspace 隔离、工具作用域当成上线前的三道检查项，缺一不发。
3. 每个 session 留独立审计日志，出问题时能按 id 完整回放子代理做了什么。
4. 隔离粒度按"是否有状态"决定，不必一刀切全部容器化，成本扛不住也没必要。

## 总结

子代理污染主会话，本质是三样东西没分开：上下文、工作区、工具状态。OpenClaw 的 session 机制提供了隔离能力，但默认配置不会替你做完所有决策——返回契约要自己定，有状态的 server 要自己拆，重试的 session 生命周期要自己管。把这三层隔离固化成模板，多代理任务的可控性会有明显提升。
