## 背景

团队里 AI 生成的技术内容越来越多，但写完只是第一步。真实流程是：模型产出 Markdown → 校对 → 发博客、发公众号、发掘金、进文档站。每个平台的渲染器都不一样，同一篇 Markdown 在四处能显示出四种效果。我们用 OpenClaw 搭了一条 Markdown 管线，把格式适配从人工搬运变成确定性步骤，这里记录设计与踩坑。

## 问题

三个具体痛点：

1. **AI 输出不受控**。同一次生成里可能混着内联 HTML、脚注、mermaid、任务列表，人工审查只能兜住明显错误。
2. **平台差异是硬约束**。公众号编辑器只认白名单标签和内联样式，表格支持很差；知乎会吞部分 HTML；掘金的代码高亮规则自成一派。
3. **字符串级替换不可维护**。最早的脚本是一堆 regex，遇到嵌套代码块里的 `#` 和转义符直接崩。

## 做法

管线分四层，核心原则：**一切转换以 AST 为中心，原始 Markdown 是唯一事实源。**

**1. 约束生成端。** 在模型的 system prompt 里明确“发布安全子集”：只允许标题、段落、列表（嵌套不超过两层）、代码块、引用、图片；禁止内联 HTML、脚注、数学公式。内容写不进约束就分节生成。

**2. 规范化层。** 用 remark/mdast 解析后跑一组自定义 lint 规则：图片必须有 alt、链接必须是绝对地址、连续空行收敛、`---` 分隔线一律删除（避免被下游工具误判成 frontmatter）。lint 不通过整篇打回重生成，不做静默修复。

**3. 适配器层。** 每个平台一个 transformer，输入统一 AST：

- 公众号：mdast → HTML，样式全部转内联，代码高亮 token 展开为 span + style；
- 掘金/知乎：微调 MD 方言，主要处理表格和图片说明的兼容写法；
- 文档站：注入 frontmatter，图片路径改写为站点资源路径。

**4. 资产层。** 图片统一转存自有图床、替换 URL 后再进适配器，避免各平台二次上传后 alt 和顺序错乱。

lint 和 transform 都封装成 MCP tool 暴露给 agent：agent 负责内容审校和调度，管线负责确定性转换，分工干净。

## 踩坑点

- 公众号的样式白名单比文档写的更窄，`class` 全丢、部分伪元素不支持，必须真机预览验证，不能只看产出的 HTML。
- markdown-it 和 remark 对 `\_`、`*` 的转义处理不一致，中途换解析器会让已转义字符“复活”。管线里固定一个解析器，别混用。
- 图片转存后平台会重命名文件，依赖图片顺序的引用逻辑全部失效，引用关系要在转存前落成 slug。
- 管线必须幂等：重跑输出不能有 diff，否则 CI 里的发布步骤会互相覆盖。我们用产物快照测试兜底。
- AI 偶尔无视约束输出三层嵌套列表，宁可打回重生成，也别写“聪明”的自动修复逻辑——修复代码比内容本身更容易引入新问题。

## 可复用建议

- 先写“安全子集”清单再接模型，约束前置比后置转换便宜一个数量级。
- 适配器做成插件，统一接口 `transform(ast, config)`，新平台半天能接上。
- 产物放独立 dist 目录，源文件只读；每次发布留存渲染快照，回归一眼可见。

## 总结

这条管线的价值不在省下几分钟排版，而在于把**内容生成**和**多平台分发**解耦：模型只负责产出合规的 Markdown，平台差异被压缩到一层薄适配器里。之后接新平台，改的只是插件，管线其余部分不动——这才是自动化该有的样子。
