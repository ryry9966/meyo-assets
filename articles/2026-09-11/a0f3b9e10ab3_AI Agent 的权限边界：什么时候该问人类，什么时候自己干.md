## 背景

Agent 接上 MCP 工具之后，能力就从"聊天"变成了"动手"：读文件、写数据库、发消息、调付费 API。自动化的价值恰恰来自少打扰人，但每一次自主执行都是一次风险敞口。边界划不好，两个极端都会出现。

## 问题

- **事事确认**：用户变成橡皮图章，看到弹窗就点允许，自动化名存实亡；
- **事事自作主张**：一条误删语句、一次全量推送，翻车成本不可逆。

核心矛盾是**确认成本 vs 事故成本**，而这两者对不同操作完全不同。所以不该有全局开关，应该按操作分级。

## 做法：按"可逆性 × 影响范围"分四级

先把 Agent 能调用的所有工具动作盘点出来，逐个归类：

| 级别 | 特征 | 例子 | 策略 |
|---|---|---|---|
| L0 只读 | 无副作用、无数据外发 | 本地查询、检索 | 自动执行，记日志 |
| L1 可逆写 | 可回滚、范围小 | 写草稿文件、建分支 | 自动执行，保留 diff |
| L2 大范围可逆 | 批量操作、影响他人 | 批量改文件、发频道消息 | 阈值内自动，超出需确认 |
| L3 不可逆/外部副作用 | 删除、支付、对外发布 | 删数据、转账、群发 | 强制人工确认 |

落地步骤：

1. **工具清单化**：把每个 MCP server 暴露的 tool 列全，别凭感觉，很多事故来自"忘了它还能干这个"。
2. **逐个标级**：写进权限配置，默认按 L2 处理，拿不准就往高定。
3. **实现确认门**：L3 强制 human-in-the-loop，且确认时必须展示"将做什么、影响谁、如何回滚"，不允许只弹一个"是否继续"。
4. **会话级授权**：一次确认只覆盖当前任务，不签发永久通行证。
5. **审计与回调**：L1 以上操作全部落日志，定期抽查，出过问题的动作降级或加门。

## 踩坑点

- **确认疲劳**：L2/L3 太多，用户会无脑点允许，等于没有门。宁可收紧工具粒度，也别让人养成盲点习惯。
- **只读不等于无害**：某些"查询"会把数据发出去（搜索、webhook 式读取），L0 也要过一遍数据出口。
- **GET 里有写**：有的 API 用 GET 触发副作用（触发构建、消耗额度）。按行为分级，别按 HTTP 方法分级。
- **上下文注入改主意**：Agent 读到的网页或文档可能诱导它调用高权限工具。提示词约束挡不住注入，L3 的门必须做在执行层。
- **批量授权放大事故**："以后这类都别问我"是常见口癖。授权应随会话过期，而不是随好感累积。

## 可复用建议

- 新工具默认 L2，观察一周再考虑降级；
- 确认卡片三要素：做什么、影响范围、回滚方式；
- 给 Agent 一个"申报"出口：判断不清时主动停下问人，比猜错便宜得多；
- 阈值参数化（如"影响超过 10 个文件需确认"），让策略可评审、可调整。

## 总结

权限边界不是信任问题，是工程问题。分级、默认保守、确认时给足上下文、日志兜底——这套组合拳不复杂，但能让 Agent 在"能干活"和"不出事"之间站到一个可持续的位置。别追求一步到位的策略，先从给现有工具标级开始。
