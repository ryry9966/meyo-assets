## 背景

Agent 一旦接上 MCP 工具，就不再是聊天玩具：它能跑 shell、写数据库、调付费接口、对外发消息。能力上来之后，第一个真实的问题往往不是"它聪不聪明"，而是"哪些事它可以直接做，哪些事必须停下来问我"。这条线划不好，系统要么慢得没法用，要么迟早出事故。

## 问题

实践中常见两个失败方向：

- **过度请示**：每一步都弹确认，Agent 退化成需要人肉点头的脚本，效率还不如自己干。
- **过度放权**：Agent 默默执行了 `rm -rf`、给生产库发了一条 UPDATE、往客户群里发了消息，事后你才知道。

两个方向都会消耗人对系统的信任。核心难点在于：权限边界不能靠感觉，需要有可执行的判据，而且必须落在工具调用层，不能只写在提示词里。

## 做法：按"可逆性 × 影响范围"分四档

动手配置前，先把 Agent 能调用的所有工具列个清单，逐个问两个问题：

1. 这个操作能撤销吗？（可逆性）
2. 出错时波及的是我自己，还是别人 / 生产 / 钱？（影响范围）

据此分档：

- **T0 只读、沙箱内**：自动执行。搜索、读文件、查接口。
- **T1 可逆的本地写入**：自动执行 + 全量日志。改工作目录内文件、本地 git commit。
- **T2 触达共享状态或外部世界**：必须确认。push、发 PR、发消息、调第三方付费接口、生产环境任何写操作。
- **T3 不可逆或高危**：始终人工，最好双人。删数据、转账、改权限、对外承诺。

落地步骤（以 OpenClaw + MCP 为例）：

1. 工具默认关闭，按档位逐个放开，T0/T1 进自动白名单。
2. T2 工具外面包一层确认门：执行前把"将执行什么、在哪个环境、影响哪些资源"渲染成 diff / 预览，人确认后才放行。
3. 确认要有作用域：一次批准只对"本会话内、这个路径、这类命令"生效，会话结束或超时失效。
4. 每次决策（自动放行和人工确认）都写审计日志，记录原因。没有日志，边界调优无从谈起。

## 踩坑点

- **确认疲劳**：T2 切得太细，人很快会变成无脑点"允许"，机制形同虚设。同会话内同模式的操作可合并成一次批量确认。
- **把提示词当安全边界**：在 system prompt 里写"未经允许不得删库"只是软约束，模型可能被间接注入绕过。真正的闸门必须在 approval hook 里强制执行。
- **确认上下文不足**：只弹一句"是否允许删除？"，人根本无法判断。确认框必须带预览：文件列表、SQL 语句、消息全文。
- **后台任务的超时策略**：异步跑批时确认卡住，超时默认"继续"是事故来源。超时应默认挂起或失败，而不是放行。
- **阈值含糊**："小额付款可自动"——多小算小？写成数字，例如单笔 < 10 元且日累计 < 100 元。

## 可复用建议

- 默认拒绝、白名单放行，而不是反过来。
- 分级只看两个维度：可逆性、影响范围，其余都是次要参数。
- 确认必须带预览，授权必须有作用域和有效期。
- 像测代码一样测闸门：写一个用例，断言未批准时高危调用必然失败。
- 定期翻审计日志：频繁被批准的操作降档，被拒绝的升档。

## 总结

权限边界不是一次性配置，而是随 Agent 能力和信任度持续调整的策略。原则可以压缩成一句话：**可逆且只影响自己的，让它自己干；不可逆、花钱、对外、碰共享状态的，停下来问人。** 把这条线写进工具层而不是提示词里，Agent 才敢放心交给它干活。
