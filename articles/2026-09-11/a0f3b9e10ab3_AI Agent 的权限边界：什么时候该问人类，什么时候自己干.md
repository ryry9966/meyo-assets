## 背景

Agent 接上 MCP 和插件之后，能力上限取决于你给了它多少工具，风险上限同样如此。一个能读写文件、发 HTTP 请求、对外发消息的 agent，本质上是一个持有部分系统权限的协作者。权限边界不是哲学问题，是工程配置问题。

## 问题：两个失败方向

实践中最常见的两种翻车：

- **事事都问**：每一步都弹确认，三天后用户开始无脑点"同意"，审批闸门形同虚设，还白白消耗交互轮次。
- **事事都干**：agent 觉得"顺手"就删了目录、给通讯录全员发了消息、动了生产配置。一次不可逆操作，足以让用户永久关掉整套自动化。

核心矛盾在于：确认很贵（人的注意力有限），出错更贵（不可逆）。所以要做的不是调节"问的频率"，而是给每个操作分档。

## 做法：二维打标 + 四级策略

给每个工具/操作打两个标签：

- **可逆性**：undo 是否可能，是否只影响沙箱；
- **影响面**：只在 workspace 内，还是触达外部世界、生产环境。

据此分四档：

1. **自动执行**：只读操作、沙箱内可逆写，打日志即可；
2. **执行但留痕**：白名单内的写操作，先 dry-run 输出预览，落审计日志；
3. **必须确认**：不可逆操作、对外动作（发消息、邮件、支付、发布）、任何涉及凭据的调用，确认时必须附上下文；
4. **直接拒绝**：修改自身权限配置、白名单外的凭据访问，写死在宿主层，不交给模型自行判断。

落地步骤：

1. 盘点 agent 可用的全部工具，列成清单；
2. 按二维矩阵逐个分档，写进权限配置；
3. 高危确认必须带 diff、目标、后果三项信息，保证人能在十秒内做出有效判断；
4. 跑一到两周，回看审计日志再调整分档。

## 踩坑点

- **确认问题太模糊**："我可以继续吗？"这种问法没人认真看，等于没问。要问就贴出 diff 和收件人列表。
- **一次授权被当成永久授权**：批处理任务中途出现新文件、新收件人时，应重新触发确认，而不是沿用旧授权。
- **prompt injection 从工具侧进来**：外部网页、文档的内容不应有权触发"自动放行"。放行逻辑只能存在于宿主层，不能由模型推理得出。
- **权限震荡**：出事 → 全部升档 → 更疲劳 → 降档 → 再出事。调档要靠审计数据，别靠情绪。
- **测试和生产共用配置**：至少按环境区分白名单。

## 可复用建议

- 默认拒绝、白名单放行，别反过来；
- 每条确认必带 diff/预览，否则不发弹窗；
- 不可逆操作加二次门槛，比如要求复述目标文件名；
- 会话级与持久级权限分开，会话结束即回收；
- 每月回顾审计日志：反复同意的操作降档，差点出事的升档。

## 总结

权限边界不是削弱 agent，而是让自动化能长期安全地跑下去。目标从来不是"少问"或"多问"，而是问得少而准，每一次弹窗都值得认真看，每一次放行都经过了真实的判断。做到这一点，自动化才真正敢交给它。
