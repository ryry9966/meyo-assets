## 背景

日常开发里 Git 占用的时间比想象中多：写规范的 commit message、按约定开分支、清理合并后的残留分支。这些事机械、重复，但容易出错。OpenClaw 这类带 shell 执行能力和 MCP 工具的 Agent，天然适合接手这部分工作——前提是你得把权限收好。

## 问题

直接让 Agent"帮我提交代码"会遇到三类麻烦：

1. **历史污染**：Agent 对改动粒度没有业务判断，容易把调试代码、临时文件打包成一个巨大的 commit；
2. **危险操作**：`push --force`、`reset --hard`、`clean -fd` 一旦进入工具箱，误触发代价很高；
3. **上下文爆炸**：大改动时 `git diff` 输出几千行，直接塞进对话既浪费 token 又影响判断质量。

## 做法

我的工作流分四步落地：

**第一步，收敛工具面。** 不给 Agent 裸 shell，包一层 wrapper 脚本（或用 MCP git server 的白名单配置），只暴露 `status`、`diff`、`add`、`commit`、`log`、`branch`、`checkout -b`、`branch -d`。`push` 单独留一个需确认的入口；`push --force`、`reset`、`clean` 完全不暴露。

**第二步，提交流程模板化。** 在仓库里放一份约定文件（AGENTS.md 或类似），规定动作序列：先 `status` 看工作区，再 `diff --stat` 估规模；小改动直接读 diff，大改动按文件分块。然后按 Conventional Commits 生成 message，类型从内容推断（改测试大概率是 `test:`，改 CI 配置是 `ci:`）。最后把"待提交文件清单 + message"打印出来等确认，确认后才执行 `add` + `commit`。

**第三步，分支生命周期管理。** 约定命名 `feat/<ticket>-<slug>`、`fix/<ticket>-<slug>`。Agent 可根据 issue 标题自动建分支；合并后的清理逻辑是：先 `git branch --merged main` 列出可删分支，本地直接删，远端只打印候选清单由我手动确认。

**第四步，定时巡检。** 用 OpenClaw 的定时任务每天跑一次只读检查：两周以上未动的分支、长期未提交的仓库，输出报告。只报告，不动手。

## 踩坑点

- **diff 截断**：必须先 `--stat`，超阈值文件让 Agent 总结而非全文阅读，否则一轮对话就吃满上下文；
- **密钥泄露**：自动 `add -A` 可能带上 `.env`。我在 wrapper 里加了路径过滤，命中敏感模式就拒绝并提示加入 `.gitignore`；
- **钩子被绕过**：pre-commit 失败时 Agent 有时会自作主张加 `--no-verify`。规则里明确禁用该 flag，钩子错误原样带回；
- **工作目录漂移**：多仓库下可能跑错目录，wrapper 固定校验当前路径在授权列表内；
- **清理误删**：`--merged` 对 cherry-pick 过的提交会漏判，远端分支永远只出清单不自动删。

## 可复用建议

核心原则一句话：**读操作放开，写操作加确认门，破坏性操作从工具层物理移除**。让 Agent 想越权也没工具可用，比在提示词里写"请不要 force push"可靠得多。

另外三条：

1. 约定写进仓库内的说明文件，随代码走、可版本化，不散落在聊天记录里；
2. 所有 Agent 的 Git 动作落一份本地审计日志（时间、命令、结果），出问题能回溯；
3. 新仓库先跑一周"只读模式"，确认 Agent 判断符合习惯，再逐步解锁 commit 和 push。

## 总结

Git 自动化的价值不在"全自动"，而在把判断密集的部分（message 质量、改动拆分）交给 Agent 草拟，把风险决策（推不推、删不删）留给人。工具面收敛 + 确认门 + 审计日志这套组合搭好后，每天省下的十分钟是真实的，而且不会在某个凌晨三点还你一个被 force push 过的分支。
