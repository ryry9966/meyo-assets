## 背景

OpenClaw 的 memory_recall 是 agent 记忆系统的入口：用户问“上次那个部署脚本在哪”，agent 调 recall 从记忆库捞相关条目塞回上下文，检索质量直接决定回答质量。

社区里常见两种声音：一种说“必须上 embedding，语义检索才是未来”；另一种说“关键词够了，向量库是过度设计”。我最近在自己的 assistant 上把两条路都跑了一遍，记录如下。

## 问题

我的记忆库约 4000 条，单条 50–200 字，内容是部署笔记、个人偏好、项目上下文。核心疑问：**这类数据上，到底哪种检索更准？**

先给结论：单路都不完美，混合最好。但过程比结论有用。

## 做法

我搭了个 30 条 query 的评测集，每条人工标注 1–3 个正确条目，统一算 recall@5。

- **方案 A：SQLite FTS5 全文检索**，BM25 排序，零额外依赖，召回延迟 <5ms
- **方案 B：bge-m3 embedding + sqlite-vec**，余弦相似度，阈值 0.35 起步
- **方案 C：混合**，两路各取 top10，用 RRF（倒数排名融合）合并取 top5

结果（recall@5）：A 62%，B 71%，C 84%。

两个典型 case：用户存的是“上游 API 限流，改用令牌桶”，提问却是“请求太频繁怎么办”——FTS 直接挂，语义和混合都能命中；反过来问“v2ray 具体配置”这类精确名词，FTS 稳，语义反而被相似度不高的泛化条目挤占。两路的失败模式几乎互补。

## 踩坑点

1. **FTS5 默认分词器不切中文。** unicode61 按空格切词，中文整段变成一个 token，等于只能整段匹配。要么换 trigram，要么入库前用 jieba 预分词。很多人因此断定“FTS 中文不可用”，其实是配置问题。
2. **换 embedding 模型必须全量重嵌。** 中途换模型后维度或语义空间就变了，旧向量和新查询不在同一空间，检索会安静地劣化，且没有任何报错——这是最阴险的坑。
3. **相似度阈值别拍脑袋。** 我试过 0.35 噪声偏多，0.5 开始漏召。跑一遍评测集看相似度分布，找山谷取值。
4. **语义检索有延迟成本。** 查询要先过一次 embedding，本地模型 30–80ms，走 API 还要加网络往返，高频 recall 场景要算这笔账。

## 可复用建议

- 记忆量 <1000 条、以用户自己写的笔记为主：FTS 先行，够用，别上向量。
- 查询和存储措辞差异大（口头提问 vs 笔记体）、或多语言混用：直接上混合检索。
- RRF 不需要调融合权重，二十来行代码能实现，是混合检索成本最低的形态。
- 无论选哪条路，先花一小时建 30 条的评测集。没有它，一切选型都是玄学。

## 总结

语义搜索不是银弹，全文搜索也没过时。中文场景下 FTS 的坑集中在分词，语义检索的坑集中在阈值和模型迁移。混合 + RRF 是当前性价比最高的答案，代价是维护两套索引。评测集是唯一能终结争论的东西——先用数字说话，再定架构。
