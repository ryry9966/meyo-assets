## 背景

订阅制推荐流越用越被动之后，很多人又绕回了 RSS：源头自己选，算法插不了手。但 RSS 只解决"信息从哪来"，不解决"来了之后怎么办"。我最近用 Agent 框架搭了一条 RSS + LLM 摘要的管线，每天产出一份摘要日报，跑了一个多月，这里记录下思路和踩过的坑。

## 问题

裸 RSS 有三个痛点：

1. **量大**：十几个源一天能出上百条，标题都不想全看；
2. **噪声高**：真正值得读的可能不到 10%；
3. **全文缺失**：很多 feed 只给摘要，点进去才发现不值得点。

直接"每条都扔给 LLM 总结"当然能跑，但 token 账单和推送轰炸会教做人。

## 做法

整条管线拆成五步，每步独立可重跑，挂在 cron 上：

**1. 数据源收敛。** 只保留 15~20 个高质量 feed，宁缺毋滥。没有 RSS 的站点用 RSSHub 之类工具生成，但要做好它随时挂的心理准备。

**2. 抓取与去重。** 拉取后先做 URL 规范化（去掉 utm 参数、统一协议和 host），对 guid 和规范化 URL 各存一份 hash 进 SQLite。去重必须在这一步做完，后续所有环节默认输入是新的。

**3. 两级过滤。** 第一级纯规则：关键词黑白名单、正文长度下限，成本为零，能砍掉一半。第二级用便宜模型打相关性分（0-10），只放行 6 分以上的，prompt 里给一句自己的兴趣描述就够。

**4. 结构化摘要。** 过筛条目批量送主模型，要求 JSON 输出：一句话摘要、2-3 个要点、建议阅读时长。temperature 设 0，并明确约束"只允许使用原文信息"。

**5. 汇聚输出。** 不做实时推送，攒成早/晚两份摘要推到 Telegram bot。按相关性分降序排，摘要在前，原文链接永远带上。

## 踩坑点

- **去重漏网**：同一篇文章会以不同链接出现在多个源，只 hash guid 不够，规范化 URL + 正文前 200 字符 hash 一起比对才稳。
- **全文抓取被封**：一开始想给"只有摘要的 feed"补抓全文，结果被反爬教育。后来接受降级：抓不到就用 feed 自带摘要，宁缺毋滥。
- **JSON 输出偶尔夹带解释文字**：解析前先提取校验，失败重试一次，再失败跳过并记日志，别让一条脏数据卡住整个批次。
- **成本失控**：头两天没设上限，一个高产源直接烧完当日 token。后来加了每日预算闸门，超了就只处理得分最高的。
- **幻觉**：即便约束了"只用原文"，偶尔还是会脑补。日报我固定通读一遍，发现幻觉就回炉改 prompt——这条管线本质上是在养 prompt。

## 可复用建议

- 抓取、去重、过滤、摘要、推送五步解耦，任何一步失败单独重跑，不做全量重放；
- 把"取 feed""存 seen 记录""调 LLM"各包成独立工具 / MCP tool，Agent 侧只管编排，可测试性会好很多；
- 先规则后模型，便宜的砍在前面；
- 记录每次调用的 token 消耗，一周后你就知道该砍哪个源了。

## 总结

这条管线技术上没有任何新东西，价值在于它是一套完整的工程闭环：幂等去重、成本闸门、失败降级、结构化输出——都是大项目里同样要面对的问题，只是规模小、反馈快。如果你想给 Agent 找一个低风险的第一条自动化任务，RSS 摘要是个不错的起点。
