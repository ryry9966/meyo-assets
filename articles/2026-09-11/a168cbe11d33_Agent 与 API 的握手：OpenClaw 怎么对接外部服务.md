## 背景

OpenClaw 这类 agent 框架的真正价值，不在“会聊天”，而在“能动手”。让它查数据、发工单、操作内部系统的前提，是 agent 能稳定地调用外部 API。MCP 生态成熟之后，接入方式标准化了不少，但真跑在日常工作流里，仍然有一堆工程细节要处理。

## 问题：能调通 ≠ 能用

很多人第一次对接的做法是：把 API 文档塞进系统提示词，让模型自己生成调用。演示能跑，一旦进入真实流程就暴露三类问题：

1. **不可靠**：没有超时和重试策略，网络一抖，整轮会话卡死。
2. **上下文失控**：外部 API 返回几万 token 的原始 JSON，直接灌进对话，又贵又容易让模型跑偏。
3. **密钥裸奔**：API key 硬编码在配置甚至提示词里，日志里也到处都是。

## 做法：给每个 API 包一层薄工具

我们目前沉淀下来的固定流程是六步：

1. **先查 MCP**。常见服务（代码托管、IM、数据库）优先用现成的 MCP server，不要重复造轮子；内部或冷门服务再自己写 skill。
2. **接口做窄**。不要把整个 REST 服务暴露成一个万能工具。一个工具只做一件事，参数用 JSON Schema 严格约束，描述里写清楚“什么场景该调用我”。
3. **认证走环境变量**。key 从 env 或 secret 管理读入，代码、配置文件、提示词三处都不出现明文。
4. **加工程护栏**。超时设 5–10 秒；读操作做指数退避重试，最多 2 次；错误返回结构化的、面向 agent 的描述（例如“配额已满，请稍后重试”），不要吐原始堆栈。
5. **裁剪响应**。在工具层完成字段过滤和分页截断，只把决策所需的最小信息送进上下文。
6. **分层验证**。先用脚本确认 API 本身可用，再用 mock 数据过一遍对话流程，最后才接真实凭证。

## 踩坑点

- **重试风暴**：POST 类写操作不幂等，盲目重试会重复下单、重复发消息。写操作要么带幂等键，要么干脆不自动重试，把失败交还 agent 决策。
- **工具描述含糊**：agent 会瞎猜参数格式。描述里给一个最小示例，效果立竿见影。
- **schema 漂移**：外部 API 偷偷改字段名，工具静默失败。给响应加一层校验，异常时显式报“响应结构不符合预期”。
- **debug 日志打全量请求头**：密钥顺手就进了日志文件。

## 可复用建议

- 每个外部服务一个独立适配模块，业务逻辑不感知 HTTP 细节，方便替换和 mock。
- 读、写拆成两个工具，写操作默认要求 agent 先复述关键参数再执行，多一道人工可审计的关卡。
- 外部 SDK 版本钉死，升级前先跑一遍工具层回归。

## 总结

Agent 对接外部服务，本质是把传统后端调 API 的工程纪律平移到工具层：**说清楚**（schema 和描述）、**守规矩**（超时、重试、限流）、**留后路**（结构化错误与降级）。握手谈成了，agent 才算真正接入现实世界。欢迎在社区里分享你们对接时的护栏配置。
