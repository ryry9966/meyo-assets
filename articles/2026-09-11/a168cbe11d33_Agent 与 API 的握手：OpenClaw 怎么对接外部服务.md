## 背景

用 OpenClaw 做自动化跑了一段时间后会发现，Agent 的真正价值不在对话本身，而在于它能不能"够得着"外部世界：查工单、发通知、读写数据库、触发 CI。这些都绕不开一件事——对接外部服务的 API。

传统 API 对接是开发者写给开发者看的：看文档、拼请求、处理响应。而 Agent 对接是让模型自己决定"什么时候调、怎么调、调完怎么解释结果"。这个差异决定了不少老经验不能照搬。

## 问题

实践中最常见的三个矛盾：

1. **Schema 粒度**。工具描述写得太粗，Agent 只能猜参数；写得太细，模型选择困难，还吃上下文。
2. **响应体量**。接口返回几 MB 的 JSON 原样回灌给模型，一轮就撑爆上下文，还烧钱。
3. **失败语义**。429、500、超时、部分成功，这些异常如果不翻译成模型能理解的结构化信息，Agent 只会盲目重试，或者干脆编造结果。

## 做法：一条务实的对接路径

**第一步，选对接形态。** 简单只读接口直接注册成 HTTP 工具；需要会话状态、本地凭证或复杂编排的服务，包成 MCP server；有生命周期和交互的走插件体系。原则是：能用窄接口就不用宽接口。

**第二步，Schema 面向模型设计。** 每个工具的 description 回答三个问题：什么时候该用它、参数是什么含义、返回什么。宁可拆成 `list_orders` 和 `get_order_detail` 两个工具，也不要做一个带十几个可选参数的大而全接口。

**第三步，凭证走环境变量。** API key 一律从环境变量或配置文件读取，不写死在工具定义里，更不能进对话历史。

**第四步，裁剪响应。** 在工具层做三件事：只挑模型需要的字段；分页数据默认返回首页加总数；超长文本截断并标注 `truncated: true`。让模型拿到"摘要 + 句柄"，需要细节再二次调用。

**第五步，翻译错误。** 把 429 翻译成"速率受限，建议 30 秒后重试"，把 404 翻译成"资源不存在，不要重试"。错误信息本身就是给模型的提示词。

## 踩坑点

- **重试不幂等**。写操作没加幂等键，Agent 一次超时重试，订单创建了两条。写接口务必带上客户端生成的幂等键。
- **工具描述互相打架**。"查询数据"和"搜索数据"描述高度相似，模型随机二选一。描述要写出差异化的适用场景。
- **吞掉原始错误**。工具层 catch 完只返回 `failed`，模型无从判断。宁可返回带错误码的结构体。
- **缺 Dry-run**。高危写操作上线前，先加一个 `dry_run` 参数在测试环境把链路验证一遍。

## 可复用建议

- 新对接先只读、后写入，权限灰度放开。
- 单个 Agent 挂载的工具控制在 10 个以内，超了就按场景拆 Agent。
- 每个外部工具记一层调用日志（参数摘要 + 耗时 + 结果状态），排障时是救命稻草。
- Schema 变更走版本号，别让线上 Agent 在升级瞬间拿到不兼容的工具定义。

## 总结

Agent 对接外部服务，本质上是在"给模型的能力"和"给系统的安全"之间找平衡：Schema 是给模型的说明书，错误翻译是给模型的提示词，裁剪和鉴权是给系统的护栏。这三层做扎实了，握手才算真正握上。
