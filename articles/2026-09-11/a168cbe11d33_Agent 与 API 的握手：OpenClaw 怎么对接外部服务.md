## 背景

跑过一段时间 Agent 之后，你会发现真正决定它"能不能用"的往往不是模型，而是工具层。模型负责推理，外部服务负责事实和数据——工单、内部数据库、第三方 SaaS。在 OpenClaw 里这条链路主要有两条路：写 MCP Server 把服务包成工具，或者直接写插件暴露函数。本文以一次把内部工单系统接进 OpenClaw 的实践为例，聊聊这个"握手"怎么做才稳。

## 问题

直接让 Agent 裸调 HTTP 会遇到一堆工程问题：鉴权放哪里、超时算成功还是失败、返回体太大撑爆上下文、写操作重试后重复建单。更隐蔽的是工具描述写得含糊，模型传参会"自由发挥"。这些问题不解决，演示能跑，生产必挂。

## 做法

**1. 先盘点，别全包。** 只挑 Agent 真正需要的 2-3 个端点：查询工单、创建工单、追加备注。一个工具暴露三十个端点是反模式，模型会在选择上犯错。

**2. 工具定义写给模型看。** 名称用"动词+名词"（如 `search_ticket` / `create_ticket`），description 写清楚"什么时候该用我、参数什么格式、什么情况会失败"，配一两个例子约束输出。

**3. 鉴权下沉到封装层。** API key 放环境变量或配置中心，由 MCP Server/插件持有，绝不进系统提示词。token 刷新逻辑写在封装层，对模型透明。

**4. 超时、重试、限流显式声明。** 统一封装一层 HTTP client：10 秒超时，429/5xx 指数退避重试（最多 2 次），连续失败熔断。重试只用于幂等操作。

**5. 返回值瘦身。** 外部 API 动辄返回几 KB 的 JSON，全部塞给模型是浪费。裁剪成结构化摘要，列表截断到 top N，错误信息改成"可行动"的一句话，比如"工单号格式应为 TKT-xxxx"。

**6. 写操作加确认。** create/update 类工具先让 Agent 输出待执行参数，用户确认后再落地；参数里带幂等键，网络重试不会重复建单。

## 踩坑点

- description 写"查询工单信息"这种废话，模型分不清它和 `search_order` 的边界，乱调用；
- 没设超时，上游服务挂了 Agent 一直转圈，体验崩塌；
- 大响应直接透传，几轮对话后上下文被塞满，推理质量肉眼可见地下降；
- 分页参数没封死，模型自作主张拉了 500 页；
- 时区：创建时间传 UTC，展示层按本地时区解析，对账对不上。

## 可复用建议

- 端点不超过 3 个时手写封装，超过再考虑从 OpenAPI 自动生成工具定义，生成后仍要人工精简 description；
- 建 mock server 跑离线测试，工具层单测不依赖真实服务；
- 日志记录每次工具调用的参数摘要、耗时、状态码，这是排查 Agent 行为的第一现场；
- 提供 dry-run 开关，接新服务时先只读不写，跑稳一周再放开写操作。

## 总结

Agent 对接外部服务，本质是给模型一个"边界清晰、失败可控"的接口面。OpenClaw 侧做好工具定义和封装层，把鉴权、超时、重试、裁剪这些脏活挡在模型之外，握手才算握牢。先跑通一个只读工具，再逐步放开写操作，是最省心的路径。
