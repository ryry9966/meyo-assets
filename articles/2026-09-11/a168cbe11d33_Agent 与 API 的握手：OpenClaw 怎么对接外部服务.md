## 背景

Agent 本身只会"说"，能力来自它能调到的工具。OpenClaw 的实际价值，很大程度上取决于接了多少外部服务：查工单、发通知、操作数据库、跑内部脚本。接得好，它是顺手的自动化助手；接不好，就是每天报错的玩具。这篇记录社区里比较稳的一套对接思路，以 MCP 为主，插件和脚本为辅。

## 问题

直接把一个 HTTP API 丢给 Agent，通常有三类麻烦：

1. **模型不理解接口语义**：参数名、鉴权方式、错误码全靠猜，调用成功率低；
2. **响应不可控**：一个全量列表接口返回几十 KB 的 JSON，几轮对话就把上下文吃满；
3. **安全边界模糊**：token 放哪、日志打什么、谁能触发写操作，没人说得清。

## 做法

核心经验一句话：**不要透传 API，要为 Agent 重新封装一层"动词化"的工具。**

1. **选接入路径**。只读、低频场景用 MCP server 包一层；需要长驻连接或复杂状态的写插件；一次性需求直接写成 skill 脚本，别过度工程化。
2. **按意图拆工具**。一个工具只做一件事：`create_issue`、`query_order_by_id`、`send_notification`。不要做 `call_api(path, body)` 这种万能口——模型面对万能口时的选错率明显更高。
3. **收敛参数和描述**。工具描述是写给模型看的：必填项、取值范围、典型用例写进 description，参数能枚举就枚举。
4. **处理鉴权**。凭证放环境变量或密钥管理，禁止进仓库；封装层统一注入，日志侧做脱敏。
5. **裁剪响应**。在封装层做字段筛选、分页上限、错误归一化，返回给模型的是结构化摘要，不是原始 JSON 瀑布。
6. **写操作加闸门**。危险操作默认 dry-run 或走确认；保证幂等，超时重试不会重复下单。

## 踩坑点

- **大 schema 吃上下文**：接了个网关，30 个工具的 schema 一次全载入，对话几轮后质量明显下降。后来按场景拆开、按需启用才恢复。
- **重试不幂等**：网络超时后 Agent 自动重试，创建了两个重复工单。写操作必须带幂等键。
- **错误信息太"人类"**：把 HTML 错误页直接返回给模型，它原样念给了用户。错误也要结构化，模型才能据此调整下一步。
- **限流没有兜底**：手工测试没事，挂上定时任务就触发 429，Agent 陷入无意义重试循环。封装层要做指数退避。

## 可复用建议

- 工具命名用动宾结构，跨服务保持一致风格，降低模型选择成本；
- 每个工具维护 3-5 条固定测试 prompt，改动封装层后跑一遍回归；
- 封装层日志记录：工具名、参数摘要、耗时、结果状态，排障全靠它；
- 先只读、后写入，灰度放量，别一上来就开放删除类操作。

## 总结

对接外部服务的本质，不是"把 API 接进来"，而是把 API 翻译成 Agent 能稳定使用的语言。封装层做得越克制——工具越少、语义越准、响应越小——Agent 表现越稳。先跑通一个最小工具，再谈生态。
