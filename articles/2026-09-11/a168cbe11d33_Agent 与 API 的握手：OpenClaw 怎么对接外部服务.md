## 背景

跑过一段 OpenClaw 之后，大多数人会遇到同一个坎：Agent 本身会推理、会规划，但它对世界的感知和操作，最终都要落到外部服务上——查个天气、发条消息、建一张工单、调一次内部系统接口。在 OpenClaw 的设计里，这些能力不是内置的，而是通过工具层（MCP server 或插件）接进来的。这篇帖子记录我把几个外部 API 接进 OpenClaw 的过程，以及反复踩到的坑。

## 问题

对接外部服务，难的从来不是“发一个 HTTP 请求”，而是三件事：

1. **凭证管理**：API key 放哪、怎么轮换、Agent 有没有权限看到它；
2. **调用边界**：模型怎么知道该调哪个工具、传什么参数、什么时候不该调；
3. **失败路径**：超时、限流、鉴权过期这些非 happy path，Agent 该怎么表现。

很多对接失败表面上是“工具调不通”，根子都出在这三点上。

## 做法

我的路径是：**优先复用 MCP，私有接口走自定义 tool**。

**第一步，选接入方式。** 目标服务已有现成 MCP server 的，直接配置启动，成本最低；内部私有 API 则在 OpenClaw 插件里写自定义 tool 暴露成函数，不强行包一层 MCP。

**第二步，凭证走环境变量。** API key 一律放 `.env` 或系统环境变量，插件里只读引用，绝不写进配置文件或 prompt。这既是安全底线，也让多环境切换变成换变量的事。

**第三步，把工具定义当成写给模型的接口文档。** description 和参数说明的读者是模型，不是人。我的经验是：在描述里写清“什么时候该用、什么时候不该用”，比罗列一堆参数含义更能减少误调用。

**第四步，收敛返回值。** 外部 API 动辄返回几十 KB 的 JSON，原样塞回上下文又贵又容易把模型带偏。我在工具层做过滤：只取任务需要的字段，必要时先做一次摘要再返回。

**第五步，把失败翻译成模型能理解的语言。** 超时返回“服务暂时不可用，可稍后重试”，401 返回“凭证失效，需人工更新 key”，而不是把原始堆栈丢给模型。模型拿到结构化的错误语义，才能判断该重试、换路径还是上报。

## 踩坑点

- **一个工具塞十几个参数**：模型选参混乱，幻觉率明显上升。拆成单一职责的小工具后稳定很多。
- **写操作没有幂等保护**：一次重试导致工单建了两条。现在所有写操作都带客户端生成的请求 ID。
- **没设调用超时**：外部服务挂起时整个 Agent 循环被卡住。工具层统一加了超时和熔断。
- **限流没在工具层处理**：模型连续重试把额度打穿，触发更长封禁窗口。429 必须在工具层做退避，不能交给模型自己决定。

## 可复用建议

1. 工具粒度宁小勿大，一个工具只做一件事；
2. 返回值面向任务裁剪，不搬运原始 payload；
3. 错误信息结构化，区分“可重试”与“需人工”；
4. 凭证永远环境注入，写操作永远幂等；
5. 上线前准备一组固定调用样例做回归，换模型版本或改 prompt 后跑一遍，防止工具调用行为漂移。

## 总结

Agent 对接外部服务，本质是一次工程化的握手：模型负责决策，工具层负责把现实世界的接口约束——鉴权、限流、超时、幂等——挡在自己这一侧。脏活累活留在工具层，模型侧的接口越干净、语义越明确，Agent 就越稳定。OpenClaw 的 MCP 与插件机制给了足够的自由度，但自由度不等于可靠性；可靠性来自你在边界上做的每一层收敛。
