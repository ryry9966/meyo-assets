## 背景

跑过内容类 Agent 的人多半有过类似经历：模型写出一篇像样的 Markdown 技术稿，往公众号、掘金、静态博客三处一贴，三份结果各自出问题——表格垮了、脚注丢了、代码高亮失效。问题不在模型写得好不好，而在下游平台的 Markdown 方言不统一。自动化的最后一公里，往往卡在格式适配。

## 问题

实际噪声主要来自三处：

1. **生成端不稳定**：模型偶尔在 Markdown 里夹 HTML、列表缩进两空格四空格混用、代码围栏语言标成 `text` 或干脆不标；
2. **平台能力参差**：公众号不支持 GFM 表格和脚注，任务列表、数学公式在各平台渲染行为各异；
3. **资源链接失效**：本地图片路径、相对链接发布后直接 404。

## 做法

管线思路是三段式：**生成端收敛、中间层规范化、出口端适配**，核心是所有内容先落成一份"规范 Markdown"，再按平台分发。

**第一步：约束生成端。** 在 Agent 的 system prompt 里限定输出为安全子集：禁内联 HTML、禁脚注、表格只用基础 GFM、代码围栏必须标语言。能用结构化约束（JSON schema 包一层再转 Markdown）就别指望自由文本自觉。

**第二步：解析与规范化。** 用 `remark` 把文本解析成 mdast AST，在 AST 层做修复：统一列表缩进、归一代码围栏语言（`shell`/`bash` 合并）、校验 frontmatter。在 AST 上操作比正则替换可靠得多。

**第三步：能力矩阵 + 降级规则。** 用一份 YAML 维护各平台支持情况，例如公众号：表格→有序列表、脚注→行内括号、任务列表→普通列表。降级规则集中管理，不要散落在业务代码里。

**第四步：平台适配器。** 每个平台一个插件式 adapter，输入规范 mdast，输出平台可接受的内容——公众号走 rehype 生成内联样式的 HTML，博客直接序列化回 Markdown，迁移成本最低。

**第五步：图片与校验。** 发布前统一执行图片本地化→上传 OSS→回写链接；出口处用 markdownlint + 干跑渲染做校验，并维护一组 golden 样本做快照测试。

## 踩坑点

- **正则修 Markdown 是反模式**：嵌套代码块里的 ` ``` ` 会吞掉匹配，务必在 AST 层处理；
- **流式输出别边收边转**：模型可能在一个代码围栏中间被 chunk 切断，先收完整篇再进管线；
- **管道符转义**：表格单元格里的 `|` 不转义，整张表直接错位；
- **公众号编辑器会剥 class**：rehype 产出的 HTML 必须内联样式，且别假设所有 `style` 属性都能存活；
- **AI 夹带的 HTML 标签**要在规范化阶段显式剥离或告警，而不是静默通过。

## 可复用建议

1. 能力矩阵、降级规则、golden 样本三件套沉淀为仓库级配置，新平台接入只写一个 adapter；
2. 给规范 Markdown 定版本号，格式变更走变更记录，避免历史文章重渲时崩掉；
3. 降级转换必须留日志——改写了什么、丢了什么，发布前人工一眼可核对。

## 总结

多平台发布难的不是"转格式"，而是把"AI 输出的随机性"与"平台方言的差异性"隔离在一套显式规则后面：生成端收敛子集、中间层 AST 规范化、出口端插件式适配，三段各司其职，管线才稳定可维护。对做 Agent 自动化的人来说，这本身就是一类典型的工具/插件拆分实践——生成归 Agent，适配归管线，校验归测试。
