## 背景

LLM 本身无状态，每次调用都"失忆"重来，但用户天然期待连续性：说过一次"我用 Python、别用 tab 缩进"，就希望之后所有会话都生效。在 OpenClaw 这类框架里，常见做法是把记忆塞进 system prompt，或通过 MCP 接一个外部存储，但多数实现停留在"能存"，离"记得准、检索对、可维护"还有距离。

## 问题

三个典型的失败模式：

1. **全量堆积**：把历史对话原样塞进上下文，token 成本线性上涨，关键偏好被噪声淹没。
2. **提取失控**：让模型"自己记住重要的东西"，结果记住的全是琐事（"用户今天打了个招呼"），真正的偏好反而漏了。
3. **冲突无解**：用户上周喜欢 tabs，这周改成 spaces，两条记忆同时被检索回来，模型输出自相矛盾。

本质是四个工程问题：记什么、何时写、怎么读、何时删。

## 做法

我们的方案是三层结构 + 一个 MCP 记忆服务：

**分层**

- 工作记忆：当前会话上下文，不持久化。
- 情景记忆：会话结束后由小模型生成摘要，按 session 归档，用于"上次做到哪了"。
- 偏好记忆（核心）：结构化条目，每条含 `type / content / source_session / confidence / updated_at / hit_count`。

**写入路径**：会话结束后跑一次提取 pass，用便宜模型按严格 schema 抽取候选偏好，类别白名单限定（编码习惯、部署环境、沟通风格等），低于置信度阈值的直接丢弃。写入前与现有条目做相似度比对，命中则走幂等 upsert——显式的新声明覆盖旧值，旧值保留在 history 字段。

**读取路径**：每次请求注入两段——固定的 top-K 核心偏好（按 hit_count 和 recency 排序，token 硬上限 500），加上按当前任务向量检索的相关记忆（阈值调到宁缺毋滥）。

**暴露给 Agent 的 MCP 工具只有三个**：`memory_search`、`memory_write`（仅限用户显式"记住××"触发）、`memory_list`。删除和编辑走人机界面，不给模型自主删的权限。

## 踩坑点

- **提取别贪。** 第一版没做类别白名单，一周后记忆库 40% 是废话。先用规则兜住高频类别，再逐步放开。
- **冲突必须显式处理。** 相似度超过 0.9 且语义相反的两条，标记 conflict，检索只返回 updated_at 新的那条，旧条降权但不删。
- **检索阈值靠评测定，不靠感觉。** 攒 20 条"该想起 / 不该想起"的用例，每次调参跑一遍，比拍脑袋可靠。
- **让用户看得见。** 有用户反馈"你怎么知道我用 ARM 机器"——体验上是惊吓不是惊喜。后来加了记忆面板，每条注入都能溯源到原始对话。
- **时效性事实要重新确认。** "我住在上海"这类事实加 90 天 stale 标记，过期后在对话里自然求证一次，别默默继续用。

## 可复用建议

- 先做显式记忆（用户说"记住"才写），跑稳了再上自动提取。
- schema 从小做起，字段宁少勿多，每条必须带出处。
- 写入用幂等 upsert，避免并发会话产生重复条目。
- 提取用便宜模型足够，别为省一次调用把主模型上下文撑爆。

## 总结

Agent 记忆与其说是 prompt 技巧，不如说是一个小型数据工程问题：结构化存储、带出处的条目、可控的检索、可见的管理界面。把"记什么"的判断权交给 schema 和阈值，把"忘什么"的判断权交给用户，连续性体验才能真正稳定。这套三层结构在我们的插件里跑了两个月，偏好召回命中率从 60% 出头提到 90% 左右，代码不到四百行，值得从零实现一遍。
