## 背景

OpenClaw 这类常驻 Agent 跑久了，MEMORY 和碎片笔记会越积越多，memory_recall 的检索质量直接决定“这个助手到底记不记得住事”。社区里常见的两种方案：全文检索（ripgrep / SQLite FTS5 / BM25）和语义检索（embedding + 向量库）。争论很多，实测很少。我把自己三个月的迁移过程整理成这篇。

## 问题

纯语义检索出现过两类翻车：

- 问“上次那个报错 code 429 是怎么处理的”，召回一堆“限流最佳实践”，唯独没召回当时记的那条原始笔记；
- 中文口语提问时 query 向量偏移，top-k 里塞满主题相近但无用的条目。

纯全文检索则是换个说法就搜不到：“服务器又挂了”搜不到当时记的“宕机排查”。

结论先说：两者不是替代关系，是互补。真正的问题是怎么混、混多少。

## 做法

最终结构是双层混合召回，步骤如下：

1. **语料整理**。把大块 MEMORY 拆成单条事实，每条带元数据（tags、日期、来源）。单条不超过 200 字，embedding 对长文本会“稀释”。
2. **全文索引打底**。SQLite FTS5，成本零、零延迟、可解释。注意中文分词：默认 unicode61 tokenizer 会把整句中文当成一个 token，要么分词后入库，要么改用 trigram。
3. **叠加语义通道**。本地跑 bge-m3（多语言效果好，中文优先），或接 API embedding。SQLite + sqlite-vec 就够用，不必上独立向量库。
4. **融合排序**。两路各取 top-20，用 RRF（倒数排名融合）合并，叠加时间衰减和 pinned 权重，最终取 top-5 进上下文。
5. **建评测集**。从真实对话里捞 60 条 query，人工标注该召回哪几条笔记，跑 recall@5 做回归。每次调权重先过评测，不靠感觉。

实测：纯全文 recall@5 ≈ 0.52，纯语义 ≈ 0.61，混合后 ≈ 0.78。数字因人而异，但“混合明显占优”这个结论是稳的。

## 踩坑点

- **精确 token 必须走全文**。错误码、版本号、人名、路径，语义检索几乎必丢，全文这一路不是可选项。
- **FTS5 中文分词是最大的暗坑**，不处理等于没建索引，上线前拿真实 query 验证。
- **k 不要贪多**。top-10 塞进上下文，噪音会稀释模型注意力，top-5 反而效果更好。
- **旧记忆要降权**。按天做时间衰减即可，否则几个月前的临时结论会一直霸榜。
- **embedding 模型别中途换**。换了就得全量重建向量，评测集里留几条老 query 做回归兜底。

## 可复用建议

- 默认架构：FTS5 打底 + 本地 embedding 叠加 + RRF 融合，两路都不重，一个 SQLite 文件能跑。
- 先建评测集再调参，recall@5 是最诚实的指标。
- 记忆条目化 + 结构化元数据，收益比换检索算法更大。
- pinned 置顶机制解决“重要但低频”的记忆召回问题。

## 总结

语义 vs 全文不是选边题。全文搜索保住精确性下限，语义搜索抬高中文口语查询的上限，RRF 把两者拼起来，再用一个小评测集守住回归。整套方案半天可以落地，建议从“先建评测集”这一步开始动手。
