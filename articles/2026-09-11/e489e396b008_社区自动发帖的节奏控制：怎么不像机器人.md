## 背景

社区有几个常规内容需求：每周摘要、版本公告、精华内容聚合转发。全靠人工发太耗时间，于是用 OpenClaw 挂了一个定时 Agent，通过 MCP 工具直接往频道发帖。第一版跑得很顺——顺到第四天就有群友说：“这是脚本吧，每天 21:00:00 整发，一秒不差。”

技术上这不是故障，工程上说是。

## 问题

复盘下来，“机器人感”来自三类可观测信号：

1. **时间信号**：固定 cron 表达式，发布时间戳误差为零，真实的人不会精确到秒。
2. **频率信号**：多条消息几秒内连发，或发布时间在 24 小时里均匀铺开，凌晨三点也在发。
3. **内容信号**：开场句、结构、长度完全一致，模板痕迹重。

社区本质是人的行为流。自动化内容如果脱离这个流的统计特征，就会被识别、被反感，甚至触发反垃圾策略。

## 做法

**调度层加“活性抖动”。** 不做均匀随机延迟，而是先统计目标频道历史消息的活跃时段分布（小时直方图），发布时间从这个分布加权采样：

```python
hour = sample_from(hist)          # 按活跃度加权
delay = random.uniform(0, 35*60)  # 小时内再抖动
schedule(hour, delay)
```

**频率用令牌桶约束。** 每个频道一个桶，容量 3、补充速率 1/小时。Agent 发帖先取令牌，取不到就排队，避免聚合类内容触发突发连发。

**事件驱动优先于时间驱动。** 有新版本 tag、有内容被标精华，才触发对应发布流；纯定时只保留周报这类确实周期性的东西。

**内容层留“手写痕迹”。** 开场句准备 5~6 个变体轮换，列表条目数自然波动，关键数据由 Agent 现算而不是套死模板。另设一个低置信度队列：拿不准的内容（比如聚合来源可能有争议）先等人审，通过再发。

## 踩坑点

- **均匀随机 ≠ 像人。** 第一版在固定窗口内 uniform 抖动，统计上仍是均匀分布，而真实活跃度接近对数正态，照样一眼机器。必须用真实分布加权。
- **时区。** 调度服务跑在 UTC，社区在 UTC+8，第一批帖子全落在后半夜。直方图务必按社区本地时区统计。
- **重试导致重复发帖。** HTTP 超时重试后同一内容发了两遍。加内容 hash 做幂等键，发布前查最近 N 条去重。
- **抖动过头伤害体验。** 周报随机到跨天，群友反而问“这周的呢”。周期性内容保留锚点（如“周二 20 点 ±40 分钟”），随机只在小窗口内。
- **变体别牺牲信息结构。** 开场句可以换，但公告里的版本号、影响范围等字段格式要稳定，可扫读性优先。

## 可复用建议

1. 调度参数做成 profile（digest / announce / forward 三档），不同内容类型不同节奏策略，别一套参数打天下。
2. 上线前先 dry-run 一周：只打印“本应在何时发什么”，把时间分布画出来人工过目。
3. 监控每帖互动率，连续下降自动降频并告警——发得像人，不如发得有人看。
4. 任何时刻保留手动熔断开关，Agent 异常时能一键停发。

## 总结

“不像机器人”的核心不是伪装人类，而是让发布策略对齐社区的真实行为统计：时间服从活跃分布，频率有上限，内容有变体但不丢信息结构，拿不准的交还给人。自动化解决的是重复劳动，节奏感解决的是信任问题。两件都做到位，定时 Agent 才能长期留在社区里不惹人烦。
