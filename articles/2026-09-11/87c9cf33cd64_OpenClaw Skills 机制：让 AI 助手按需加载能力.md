## 背景

用 OpenClaw 做了一段时间自动化后，我的 agent 配置长成了"越养越胖"的样子：工作流说明、代码规范、部署步骤、日常模板……全堆在 system prompt 和常驻 memory 里。结果上下文成本越来越高，模型还经常在无关任务里引用不相干的规则。

Skills 机制就是针对这个问题的解法：把能力拆成独立的技能目录，平时只在上下文里留一行元数据，任务匹配时才加载正文。

## 问题

把所有能力塞进常驻 prompt 有三个代价：

1. **Token 成本**。不管今天跑什么任务，都要为全部说明付费。
2. **注意力稀释**。指令越多越容易互相干扰，长尾指令基本失效。
3. **维护困难**。改一条规则要在巨型 prompt 里翻找，改完还不敢删旧版本。

## 做法

一个 Skill 就是一个目录，核心是 `SKILL.md`：

```text
~/.openclaw/skills/release-notes/
├── SKILL.md          # frontmatter + 使用说明
├── references/       # 按需读取的详细文档
└── scripts/          # 可执行脚本
```

写法上分三步：

1. **写 frontmatter**。`name` 用小写连字符，`description` 是路由键——模型无时无刻看到的只有它。要写成使用条件，例如"当用户要求生成周报、汇总 issue 变更时使用"，而不是"这是一个周报工具"。
2. **写正文**。只放操作步骤、约束和边界条件，控制在两百行以内。细节（完整模板、历史案例）下沉到 `references/`，可执行逻辑写成 `scripts/` 里的脚本。
3. **验证与测试**。跑 `openclaw skills check` 确认格式合法，重载会话，抛一个预期任务，观察它是否触发、实际加载了哪些文件。

加载是三级的：元数据常驻 → 正文触发时读入 → 附加资源真正需要时再读。这让"会一百种事"和"当前只想一件事"在上下文里可以共存。

## 踩坑点

- **description 写成功能简介**。路由失败最常见的原因：模型只凭这行字决定要不要加载，写文案不如写触发场景。
- **正文塞太满**。触发一次吃掉大半个上下文，等于把 prompt 换了个地方堆。
- **多个 skill 描述重叠**。"生成周报"和"汇总 issue"边界不清时，路由会摇摆，要么都触发要么都不触发。
- **脚本环境依赖没声明**。相对路径、Python 版本、缺依赖，换台机器就挂。脚本要做防御式检查并给出可读的报错。
- **把密钥写进 skill 文件**。技能目录会进版本库，凭证一律走环境变量。

## 可复用建议

- description 统一用"当遇到 X 时使用"句式，多个技能之间保持语义互斥。
- 想清楚 Skill 和 MCP 的分工：MCP 提供"能调用的工具"，Skill 提供"怎么用好这些工具的流程"，不要用 Skill 重新实现一个已有的工具。
- 技能目录进 git，团队共用一个 skills 仓库，新人开箱即用。
- 定期清理：两个月没被触发过的 skill，要么合并要么删掉。

## 总结

Skills 的价值不在"给助手装更多能力"，而在把有限的上下文花在当下这件事上。它本质上是把 prompt 工程变成文档工程：一个写得好的 description 决定能不能被找到，一份克制的正文决定被找到之后能不能把事办成。建议从你最常口头重复解释的那件事开始，抽成第一个技能。
