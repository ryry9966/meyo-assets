## 背景

Agent 化之后，自动化链路里的外部依赖越来越多：LLM 网关、搜索、天气、数据库、各类 MCP 工具。任何一个环节 429 或超时，整条任务链就可能停摆。传统后端早有一套重试、熔断、降级的成熟方案，但 Agent 场景多了一层复杂度——模型本身也是"消费者"，它会对你喂给它的错误信息做出反应。错误处理做得糙，轻则浪费 token，重则模型编造一个"看起来合理"的结果继续往下跑。

## 问题

实践中最常见的三类翻车：

1. **工具层和规划层双重重试**。工具函数内部写了三次重试，模型看到失败后又在对话层自己再试三次，流量放大一个量级，把原本只是限流的 API 彻底打挂。
2. **原始报错直接丢给模型**。一段 stack trace 喂进去，模型要么无限道歉循环，要么自信地"推断"出调用成功了。
3. **非幂等操作被重试**。下单、发通知这类 POST 被盲目重试，用户收到三条一样的消息，事后排查极痛苦。

## 做法

核心思路是把弹性能力全部下沉到工具层，Agent 层只做决策。分四步：

**1. 错误分类先行。** 把外部错误分成可重试（429、503、超时）和不可重试（401、400、配额耗尽）。写一个统一的 resilient client，重试用指数退避 + 随机抖动，上限 3~5 次。

**2. 加熔断，快速失败。** 连续失败达到阈值就打开熔断器，一段时间内直接拒绝调用，避免雪崩。必须有半开状态，定期放探测请求试探恢复。

**3. 结构化错误返回给模型。** 不要给原始报错，给这样的结构：

```json
{
  "ok": false,
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "hint": "上游服务超时，可稍后重试或改用备用数据源"
}
```

模型拿到 `retryable` 和 `hint` 才能做出像样的决策，而不是瞎猜。

**4. 检查点 + 幂等键。** Agent 每完成一步就持久化状态（run_id、已完成步骤、中间结果），崩溃后从检查点恢复而不是从头跑。所有写操作带幂等键，重试不产生副作用。

## 踩坑点

- **超时设置**：太短会反复打断半成功的请求，太长会把 Agent 卡死。我们一般取上游 P99 的 1.5 倍，再靠重试兜底。
- **把失败缓存成"成功"**：缓存层要区分空结果和错误，否则熔断恢复后 Agent 还在用旧的坏数据。
- **熔断器没有半开恢复**：一旦熔断永不恢复，等于把工具永久下线，模型会开始幻觉填补空缺。
- **日志缺 run_id 贯穿**：事后无法把 Agent 的一次执行和具体 API 请求对上，日志再多也是垃圾。

## 可复用建议

- 所有外部调用走同一个 client，重试/熔断/超时/指标集中管理。插件各自为政是事故之源。
- 给每个 MCP 工具定义标准错误 schema，`retryable` 字段必须有。
- 上线前做故障注入：写一个 mock 工具，随机返回 429/500/超时，观察 Agent 行为是否符合预期。
- 关键任务保留人工升级路径，熔断打开时通知人，而不是硬扛。

## 总结

错误恢复是系统工程问题，不是 prompt 问题。原则三条：弹性下沉到工具层、状态可恢复、错误信息结构化。模型只负责在拿到干净信号时做合理决策，别让它直面混乱的原始报错。把这些做扎实，Agent 才敢放进生产环境跑长任务。
