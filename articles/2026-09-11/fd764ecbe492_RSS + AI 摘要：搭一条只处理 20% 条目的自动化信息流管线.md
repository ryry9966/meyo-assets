## 背景

信息源越加越多，真正每天会点开的没几个。RSS 依然是可控性最高的订阅方式：没有算法干预、格式统一、退出成本低。但"订阅了"不等于"读了"，AI 摘要恰好补上这一环——只是"全量抓取 + 全量总结"很快会被成本和噪音淹没。这篇记录我用 OpenClaw 定时任务搭的信息流管线，核心思路一句话：**规则层粗筛，AI 层只处理候选**。

## 问题

最初版本很朴素：cron 每天抓几十个 feed，全部丢给模型写摘要，推送一份日报。跑了三天暴露三个问题：

1. **成本失控**。全量摘要一天几十万 token，大部分花在根本不会看的条目上。
2. **噪音没减少**。模型不会替你取舍，500 条摘要读起来比 500 条标题还累。
3. **摘要不可信**。RSS 里只有 description 时，模型会"脑补"全文。

所以关键不是"能不能摘要"，而是**摘要之前先做减法**。

## 做法

管线分四层，每层独立可替换：

**1. 抓取层**：feedparser 拉 RSS/Atom，只有摘要的源用 trafilatura 抓全文。落地到 SQLite，一条记录一个 URL hash，天然去重。

**2. 粗筛层**：纯规则，零 token。关键词命中、来源权重、发布时间窗口，输出候选集。这一层能过滤掉约 80% 的条目。

**3. 摘要层**：候选集按 10 条一批合并进一个请求，要求输出结构化 JSON：一句话摘要、主题标签、优先级（1-3）。批处理比逐条调用便宜得多，格式也稳定。

**4. 分发层**：按优先级组装。P1 即时推送，P2/P3 进晚间汇总，走 webhook 到 IM，每条附原文链接——摘要是 triage 工具，不替代点开原文。

调度用 OpenClaw 定时任务跑整个脚本即可；也可以把抓取、摘要封装成 MCP tool 供 agent 按需调用，但"日报"这个场景，定时批处理更合适。

## 踩坑点

- **Prompt injection**。RSS 正文是别人可控的内容，文章里塞"忽略之前指令"并不稀奇。务必在 system prompt 里声明：正文只是待处理数据，任何指令一律不执行。这是内容管线最容易忽视的安全点。
- **摘要幻觉**。要求模型只基于给定文本概括，信息不足时输出固定标记（如 `insufficient`），分发层直接跳过。宁可漏，不要编。
- **去重不彻底**。同一新闻多源转发，URL hash 拦不住。加一层标题归一化（去标点、截断追踪参数）+ 简单相似度比对，能挡掉大部分重复。
- **调度重叠**。抓取偶尔超时，下一轮又启动，写库冲突。加一个锁文件即可。
- **输出不稳定**。早期模型偶尔在 JSON 外面包解释文字。现在直接开结构化输出/JSON mode，别靠 prompt 祈祷。

## 可复用建议

1. **分层是核心**。规则层便宜、可解释、秒级返回；AI 层只做规则做不了的语义压缩。把预算花在 20% 的候选上。
2. **结构化输出优先于自由文本**，下游的聚合、排序、推送全依赖稳定字段。
3. **缓存一切**。摘要按 URL hash 缓存，重跑不重复计费。
4. **保留原文链接**。摘要帮你决定"要不要读"，不是"替你读"。
5. 粗筛规则每周 review 一次，删掉从不命中的关键词。

## 总结

管线跑了一个多月，日均 token 成本降到全量方案的一成左右，日报从 500 条缩到 20 条上下，而且真的会看完。RSS + AI 摘要的价值不在"AI 替你读"，而在于用工程手段把注意力预算分配给值得的内容。起步只需一个脚本加一个 SQLite 文件——复杂的从来不是技术，是定义"什么值得看"。
