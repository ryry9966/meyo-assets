## 背景

现在让模型生成初稿已经很常见，OpenClaw 的 Agent 工作流里也经常是"生成 → 审核 → 发布"这条链。但实践下来大家会发现：AI 吐出来的 Markdown 只是半成品。真正花时间的不是写，而是把同一篇内容适配到公众号、知乎、掘金、静态站这几套格式规则完全不同的平台上。

## 问题

适配的麻烦集中在三层：

1. **生成侧不干净**。模型输出常带对话腔（"以下是正文："）、孤立的两级标题、缺失语言标注的代码块，直接进管线会污染下游。
2. **平台方言**。公众号只吃内联样式的 HTML，剥掉 `<style>` 和 class；知乎限制标签子集；静态站要 frontmatter 和相对路径图片；掘金对代码围栏的处理又不一样。
3. **资产处理**。外链图床有防盗链，公众号对图片体积和来源域名都有限制，不重传基本必挂。

逐个平台手工改，每次平台改版都要重来。正确的思路是把它当编译问题处理：Markdown 是源码，各平台是目标架构。

## 做法

我们的管线分五步，核心操作用 remark（mdast）而不是正则：

**1. 清洗与规范化**。入口先跑 clean 步骤：去掉对话残留、统一代码块语言标注、中英文之间补空格、全角标点归一。然后 markdownlint + prettier 统一格式，保证后续 diff 干净。

**2. 元数据层**。frontmatter 定义 schema（title、tags、cover、canonical_url），用 zod 校验，缺字段直接 fail，不靠人眼兜底。

**3. AST 转换**。所有格式操作都在 mdast 上做：剥 frontmatter、脚注降级、mermaid 转占位图。接口统一为 `transform(ast, meta) -> ast`。

**4. 平台适配器**。每个平台一个插件：公众号目标做服务端代码高亮 + juice 内联样式 + 图片转存；知乎目标裁掉不支持的标签；静态站目标生成 frontmatter 和相对路径。渲染结果落盘为构建产物，单独目录管理。

**5. 校验与自动化**。dry-run 输出 diff 预览，检查死链和图片体积。CLI 和 CI 各跑一份；同时把"清洗 → 发布 → 回写平台文章 ID"暴露成 MCP tool，Agent 一句话就能完成全量更新。

## 踩坑点

- **正则替换在嵌套代码块上必翻车**。`.*?` 会跨块匹配，代码块里的示例文本被当正文改掉。第一版吃过亏，全面切 AST 后才稳定。
- **公众号的样式剥离是静默的**。本地预览好好的，发上去样式全丢。必须用内联样式渲染，且提前用小号验证一遍。
- **防盗链**。图床 referer 校验导致公众号编辑器里图片裂开，图片必须先转存到目标平台或自有对象存储。
- **幂等性**。重复执行发布任务会产出重复文章。发布后要把平台返回的文章 ID 写回 frontmatter，存在 ID 就走更新接口而不是新建。
- **人工改产物**。有人图省事直接改生成后的 HTML，下次构建全被覆盖。纪律是：源文件是唯一事实源，产物不可手改。

## 可复用建议

- 把"清洗"做成独立、可单独调用的步骤，AI 生成的任何草稿都先过一遍再进管线。
- 适配器接口保持统一，新增平台只写一个插件，不动主流程。
- dry-run 默认开启，diff 确认后才真正发布。
- MCP 化时把每个阶段拆成独立工具（clean / render / publish），便于 Agent 分步确认，不要塞成一个黑盒大工具。

## 总结

多平台发布的本质是格式编译：一份 canonical Markdown，多条编译目标，产物是派生物。把清洗、转换、适配、校验做成管线而不是脚本堆，AI 生成的内容才能真正低成本地走完"生成到发布"的最后一公里。
