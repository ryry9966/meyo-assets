## 背景

团队里大部分系统的运行痕迹都以日志形式散落各处：服务日志、CI 任务记录、Agent 定时任务的执行输出、告警事件。日报本应是对这些信息的浓缩，但实践中往往靠人肉拼凑——翻几个面板、复制几段日志、凭记忆补两句结论。结果是格式不统一、关键事件遗漏、写的人烦、看的人不信。

## 问题

把这件事自动化的难点不在"生成文档"，而在中间那段：原始日志量大且噪声高，直接丢给 LLM 既贵又容易编造；纯统计报表又干瘪，缺少解释。我们要的是一条流水线：机器负责把海量日志压成可信的结构化事实，Agent 只负责最后的叙述。

## 做法

整条流水线分四步，每一步落盘缓存，方便单独重跑和排查：

1. **采集与归一化**：定时脚本拉取前一日各来源日志，统一转成 JSONL，字段收敛为 `timestamp / source / level / event_type / payload`。不同来源的时区、时间格式在这一步全部对齐。
2. **切片与聚合**：按自然日切片，统计错误/告警计数、Top-N 高频事件、与过去 7 天基线的偏差项。输出是纯数据的 JSON 摘要，通常只有几 KB。
3. **Agent 叙述**：把聚合摘要通过 MCP 工具喂给 Agent，要求按固定 JSON schema 返回各章节内容——只允许引用摘要里的数字，不允许新增事实。LLM 在这一步做的只是组织语言和标注异常优先级。
4. **渲染与分发**：Markdown 模板渲染，机器人推送到群频道，同时归档到对象存储。生成过程幂等，同一天重跑不会产生两份报告。

调度用 cron 驱动，失败重试一次后告警。

## 踩坑点

- **不要把原始日志直接喂给 Agent**。第一版我们这么做过，上下文爆掉，结论里还出现了日志中根本不存在的原因分析。改为"先聚合、后叙述"才稳定。
- **时区与迟到数据**。跨时区服务和延迟上报让日切边界含糊，重跑窗口要预留回溯缓冲（比如多拉 1 小时，按事件时间归窗）。
- **LLM 输出不稳定**。让 Agent 自由发挥 Markdown 经常破坏格式，改成 schema 约束输出、模板负责最终渲染后，问题消失。
- **全绿报告更可疑**。流水线自身挂掉、静默产出空报告，比不产出更糟。务必对聚合结果做行数/来源数校验，数量为 0 时走告警而不是照常发日报。

## 可复用建议

- **分阶段落盘**：raw → normalized JSONL → aggregate JSON → report，任何一段出问题都能离线复现，不必等第二天再跑一遍。
- **报告 schema 独立成文件并带版本号**，字段变更向后兼容，避免下游消费方静默解析失败。
- **先跑纯统计版日报两周**，确认口径和基线可信，再引入 LLM 叙述层。LLM 是最后一层，不是第一层。
- **把报告校验也做成独立的 Agent 任务**，对照聚合 JSON 抽查报告数字，作为低成本的质量门禁。

## 总结

这套流水线的核心是责任分层：确定性的部分（采集、归一、聚合、渲染）全部交给脚本，不确定的部分（叙述、优先级判断）交给 Agent，并用 schema 和校验兜住边界。上线后日报从"人写一小时"变成"机器跑三分钟"，更重要的是口径稳定、可追溯、可回放。如果你在 OpenClaw 里已经在跑定时 Agent 任务，加一层采集归一脚本和一份聚合 schema，就能直接复用这条路径。
