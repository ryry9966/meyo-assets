## 背景

我们团队维护着十几个服务和多条流水线，每天早会前需要一份日报：昨天发了哪些版本、出了哪些告警、关键指标有没有异常。以前靠值班同学手写，格式因人而异，平均要花 20-30 分钟，还经常漏掉凌晨的部署记录。

## 问题

原始日志有三个特点：噪音大（构建输出里九成是无关行）、来源分散（git、CI、监控各有一套格式）、归纳主观（同一堆日志，两个人能写出完全不同的结论）。我们要的不是"看起来像报告的东西"，而是一份数字准确、格式固定、可以回溯的底稿。

## 做法

设计原则只有一条：**能用确定性代码算出来的，绝不交给模型**。整条流水线分四层：

1. **采集层**：用 OpenClaw 的定时任务在每天固定时间触发，通过几个小的 MCP 工具分别拉取 git log、CI 记录和告警历史，每个数据源一个适配器，统一吐 JSON。
2. **加工层**：纯脚本完成过滤、去重、聚合，所有数字（部署次数、失败率、Top 告警）在这一层预算好，同时把原始数据快照存档备查。
3. **生成层**：Agent 只干两件事——把数字填进固定模板，用两三句话写"今日要点"。输出强制走 JSON Schema 校验，不通过就带着错误信息重试一次。
4. **投递层**：插件通过 webhook 推到群里，失败进重试队列。

## 踩坑点

- **别让模型算数**。早期直接把原始日志丢给模型"顺便统计一下"，数字偶尔凭空出现。改成预计算后，模型只负责措辞，这类幻觉彻底消失。
- **时区坑**。数据源是 UTC，日报按本地时间切"昨天"，第一天晚上八点后的提交全丢了。切分窗口统一用业务时区，写进配置而不是散落在代码里。
- **别把日志直接塞上下文**。日志一多，token 爆炸，摘要质量反而下降。先聚合成几十条结构化条目再进模型。
- **流水线自己也会挂**。加了一条自监控：生成连续失败就发一条"日报生成失败"的裸告警。宁可收到空报告，也不要静默失败。

## 可复用建议

- 确定性计算与生成措辞严格分层，模型不碰任何数字。
- 把日报格式固化成一份 Schema，人读的模板和机器校验用同一个定义。
- 保留原始快照，报告有疑问时能回溯核对。
- 从一个数据源跑通闭环，再接下一个，别一上来就搭"平台"。

## 总结

这套流水线的采集适配器每个只有几十行代码，成本不高，换来的是每天省下半小时人工，以及一份格式稳定、数字可信、可追溯的日报。自动化日报的价值从来不在于"写得漂亮"，而在于"每天都有一份可信的底稿"——有了底稿，人才有余力去讨论真正重要的事。欢迎在社区里贴出你们自己的采集适配器和模板 Schema，互相抄作业。
