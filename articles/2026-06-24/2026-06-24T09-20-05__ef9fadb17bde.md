最近一条说法在技术圈吵得挺热：大模型一年内就会“吞噬” Harness 这类工具，创业公司要活下去，必须深耕垂直领域。话听起来很猛，但拆开看，它讨论的不是某一家公司的输赢，而是一个更底层的问题：当大模型能写代码、读日志、调 API、生成工作流时，通用软件工具的护城河还剩多少？

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-06-24/a279cd8b234907d3.png)

## 先说 Harness 到底代表什么

Harness 不是一个单点小工具，它代表的是一类 **DevOps / software delivery platform**：

1. **CI/CD 流水线**
   - 代码提交后自动构建、测试、部署。
   - 常见对象包括 YAML pipeline、runner、artifact、environment。

2. **发布治理**
   - 灰度发布、回滚、feature flag、审批流。
   - 目标不是“跑起来”，而是“稳定、可追踪地跑起来”。

3. **可观测与成本控制**
   - 部署后看日志、指标、告警。
   - 云资源花了多少钱，哪里浪费，也要纳入流程。

所以，所谓“大模型吞噬 Harness”，更准确地说，是：  
**AI agent 可能把一部分通用 DevOps 操作变成自然语言指令，不再需要用户逐页点击工具界面。**

比如过去你要写：

- Jenkinsfile
- GitHub Actions YAML
- Kubernetes manifest
- Terraform 配置
- 发布审批规则

未来可能变成一句话：  
“给这个服务加一条生产环境灰度发布流水线，先 5%，观察 30 分钟，错误率超过阈值自动回滚。”

工程师听完会心一笑：这不就是“把需求写清楚”又换了个入口？只是这次，机器真的能帮你干不少脏活累活。

## 为什么大模型确实会压缩通用工具空间

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-06-24/1128920022850c71.png)

这轮 AI 对 SaaS 的影响，不是简单“加个聊天框”。它真正厉害的地方在于三层能力叠加：

1. **语言理解变成操作入口**
   - 过去软件靠菜单、按钮、表单组织功能。
   - 现在用户可以用自然语言描述目标，模型再拆成步骤。
   - 对工具来说，UI 的差异化会被削弱。

2. **代码和配置生成能力变强**
   - DevOps 里大量工作本质是“模板 + 参数 + 约束”。
   - 大模型擅长补全 YAML、生成脚本、解释报错。
   - 这会直接冲击以“流程配置效率”为卖点的工具。

3. **Agent 能调用外部工具**
   - 通过 API、CLI、MCP 等方式，模型不只会回答，还能执行。
   - 读仓库、查日志、跑测试、开工单、调云服务，都能串起来。
   - 软件从“人操作系统”变成“模型操作系统”。

这也是为什么横向工具最先感到压力。只要你的产品主要价值是：

- 帮用户填表；
- 帮用户拼流程；
- 帮用户查文档；
- 帮用户生成标准配置；

那大模型很可能把它变成一个功能，而不是一个独立产品。就像计算器功能还在，但很少有人专门买一个网页计算器 SaaS。

## “吞噬”不等于“马上消失”

但把话说死也不务实。企业软件最硬的部分，往往不是界面，而是 **控制权、可靠性和责任链**。

DevOps 场景尤其如此，因为它连接的是生产环境。出错不是页面不好看，而是服务不可用、订单失败、数据错乱。这里有几件事，大模型短期很难单独扛住：

1. **权限与审计**
   - 谁批准了发布？
   - 哪个模型生成了配置？
   - 哪个人确认了变更？
   - 出问题后如何追责和复盘？

2. **稳定性与确定性**
   - 发布系统不能“今天灵感不错，明天换个写法”。
   - Pipeline 要可重复、可回放、可验证。
   - AI 可以建议，但生产系统需要硬约束。

3. **复杂企业集成**
   - 大公司内部可能有十几套权限系统、工单系统、制品库、监控平台。
   - 真正难的是把它们接稳，而不是写一个漂亮 demo。
   - demo 是赛车游戏，企业交付是开叉车进仓库，慢但得准。

4. **安全边界**
   - 密钥、镜像、生产集群、客户数据都不能随便暴露。
   - AI agent 如果能部署，也必须被 policy-as-code、审批流、沙箱和日志系统约束。

所以，更可能发生的是：  
**通用 DevOps 平台不会立刻被清零，但会被迫从“操作界面”升级为“可信控制平面”。**

谁能把 AI 变成安全、可控、可审计的交付能力，谁还有机会。谁只剩一层漂亮壳子，就比较危险。

## 为什么垂直领域更像创业公司的防波堤

“深耕垂直领域”不是一句鸡汤，而是对大模型时代竞争结构的判断。

大模型会快速吃掉通用能力，因为通用能力最容易被训练、复用和封装。但垂直领域通常有几类壁垒：

1. **专有流程**
   - 例如工业设备巡检、游戏版本发布、跨境物流报关、医疗编码辅助。
   - 每个行业都有自己的术语、节点、异常情况。
   - 外行看像表格，内行知道每一格都有坑。

2. **高质量场景数据**
   - 通用模型知道“应该怎么做”。
   - 垂直产品知道“在这个客户、这个系统、这个限制下怎么做”。
   - 后者才是能收费的部分。

3. **合规与责任**
   - 金融、医疗、能源、制造等行业，不是模型回答对就行。
   - 还要有记录、审批、留痕、解释和边界。
   - 这些都需要产品化，而不是单纯 prompt。

4. **分发渠道**
   - 垂直 SaaS 往往靠行业关系、实施经验、服务网络进入客户。
   - 大模型再强，也不会自动拥有行业销售和交付能力。

历史上类似的事发生过很多次：云计算没有让数据库消失，而是重塑了数据库；低代码没有让程序员消失，而是让简单系统更便宜；搜索引擎没有让知识服务消失，而是逼知识服务往更深处走。

这次也一样。AI 会压低“通用软件动作”的价格，但会抬高“行业问题解决能力”的价值。

## 对 DevOps 产品的未来判断

如果把未来的 DevOps 工具画成一张架构图，大概会变成三层：

1. **上层：意图输入**
   - 人用自然语言描述目标。
   - 例如“把支付服务发布到新集群，保留自动回滚策略”。

2. **中层：AI 编排**
   - 模型生成 pipeline、检查依赖、补齐配置。
   - 结合历史发布记录，判断风险等级。
   - 遇到异常时给出修复建议。

3. **底层：可信执行**
   - 权限控制、审计日志、策略校验、测试门禁。
   - 真正部署仍由确定性系统执行。
   - 关键节点需要 human-in-the-loop。

DORA 长期用四个指标衡量软件交付能力：部署频率、变更前置时间、变更失败率、恢复时间。AI 如果只是让 YAML 写得更快，价值有限；如果能同时降低失败率和恢复时间，那才是真正进入核心区。

一句话：  
**AI-native DevOps 的关键不是“自动部署”，而是“带刹车的自动部署”。**

## 给创业团队的三条冷思考

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-06-24/4a4e99711e7b86f0.png)

1. **别只做通用 Copilot，要抓住具体岗位**
   - “帮开发者提效”太宽了。
   - “帮游戏后端团队做多区服灰度发布”就清楚得多。
   - 客户愿意为具体痛点付费，不会为宏大愿景报销。

2. **把数据闭环做成护城河**
   - 记录输入、建议、执行、结果、回滚、复盘。
   - 让系统越用越懂客户，而不是每次都从零开始猜。
   - 没有闭环的数据，只是日志；能改进决策的数据，才是资产。

3. **把可控性放在第一天设计**
   - AI agent 能力越强，越要有权限边界。
   - 审批、沙箱、回放、审计、策略引擎都不是后期补丁。
   - 工程世界的浪漫很简单：能跑，也能停。

这条热议真正提醒我们的，不是某个工具会不会被替代，而是软件的价值正在迁移：从“提供按钮”迁移到“理解场景”，从“包装流程”迁移到“保证结果”。大模型像一只巨大的自动化钳子，能夹走很多浅层功能；但真正扎进业务泥沙里的产品，仍然有活路，而且可能活得更硬。
