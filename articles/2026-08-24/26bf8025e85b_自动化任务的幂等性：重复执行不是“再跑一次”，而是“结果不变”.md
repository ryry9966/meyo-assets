## 背景

在 OpenClaw 这类自动化环境里，任务很少只被执行一次。定时任务可能因为调度重叠而并发触发；Agent 调用 MCP 工具可能因为模型超时、上游重试而重复提交；webhook 插件也可能收到同一个事件的多次投递。若任务本身没有幂等设计，重复执行会带来重复消息、重复文件、重复 issue、重复计费等副作用。

## 问题

幂等性指同一操作执行一次或多次，对系统状态和外部副作用的影响一致。很多自动化任务表面上看“再跑一次也没事”，但实际会把非只读操作重复叠加。典型反例：

- 抓取 RSS 后调用 MCP 发送通知，同一篇文章被推送多次；
- 处理 GitHub webhook 时，同一个 push 事件重复建 CI 任务；
- Agent 超时重试导致同一个 ticket 被创建两次；
- 写日志文件时重复追加，导致内容错乱。

关键点在于：自动化链路天然具备“至少一次投递”的语义。你可以减少重复触发，但无法完全避免，因此任务本身必须能安全重放。

## 做法/步骤

### 1. 先定义 dedupe_key

为每个任务确定“一次业务执行”的唯一标识。常见来源：

- 事件 ID：webhook 中的 event id、消息队列中的 message id；
- 业务键：源 URL hash、请求体 hash、日期 + 任务类型；
- 组合键：task_type + external_id + 日期粒度。

不要用全局 `task_id` 去重，否则第二次合理的业务执行会被误判为重复。

### 2. 入口先落库，靠唯一索引兜底

不要只做“先查再插”。正确做法是直接插入一条 `running` 记录，并依赖唯一索引：

```python
def run(task_id, dedupe_key):
    try:
        insert task_runs(task_id, dedupe_key, status='running')  # 唯一索引
    except DuplicateKey:
        return get_existing_result(task_id, dedupe_key)

    try:
        result = execute()
        mark_done(task_id, dedupe_key)
        return result
    except Exception as e:
        mark_failed(task_id, dedupe_key)
        raise
```

这样即使多实例并发，只有一个 worker 能成功插入 `running` 记录。

### 3. 用状态机控制生命周期

任务状态流转应原子化：

`pending -> running -> done/failed`

建议用条件更新抢占任务，例如：

```sql
UPDATE tasks
SET status = 'running'
WHERE id = ? AND status = 'pending';
```

只有影响行数为 1 时才继续执行。避免两个 worker 同时抢到同一个任务。

### 4. 外部副作用使用 outbox 或幂等键

调用第三方 API 时，优先传平台支持的 `Idempotency-Key`。如果平台不支持，就在本地维护 outbox 表：

```text
dedupe_key | external_ref | status
```

执行前检查是否已有 `external_ref`，有则直接返回；执行成功后更新状态。发消息、创建 issue、写文件都适用这个思路。

### 5. 文件写作用临时文件 + 原子 rename

避免重复执行时截断或追加错乱：

```bash
write tmp_file
mv tmp_file target_file
```

## 踩坑点

- **只依赖内存 Set 去重**：进程重启、多实例部署后失效。
- **先查再写不是并发安全**：两个请求都查到不存在，然后重复执行。
- **唯一索引字段选错**：用了全局 `task_id`，导致第二次正常执行被跳过。
- **忽略外部副作用**：数据库事务回滚了，但短信/推送已经发出。外部调用需要放在事务外，或者使用 outbox 记录。
- **失败处理混乱**：不可恢复错误标记 `failed` 后，应该返回相同失败，而不是再次产生副作用；可恢复错误才允许重试。
- **时间窗口去重误伤**：仅按“5 分钟内相同内容”去重，会丢失合理重复任务。稳定 dedupe_key 比时间窗口可靠。
- **返回缓存结果与当前状态不一致**：执行成功后收到重复请求，直接返回旧结果可能掩盖外部资源后续变化。

## 可复用建议

- 所有非只读自动化任务默认要求 `dedupe_key`，并在入口做幂等检查。
- 能用数据库唯一约束/原子状态更新，就不要自建应用层锁。
- 对 MCP 工具封装：如果工具本身无幂等，在 OpenClaw 侧加 outbox 记录外部调用结果。
- 测试幂等性：连续调用同一任务 3 次，断言外部副作用只发生 1 次；再用两个 worker 并发触发，确认不会重复执行。
- 把不可逆副作用集中在任务末尾，或拆成“准备阶段”和“提交阶段”。

## 总结

幂等性不是让任务不报错，而是让重复触发和重试不会产生额外的业务副作用。在 OpenClaw/Agent/MCP 这类自动化链路中，任务随时可能被重放。把幂等设计作为默认能力，而不是事后补丁，才能让定时任务、webhook 和 Agent 重试真正可控。
