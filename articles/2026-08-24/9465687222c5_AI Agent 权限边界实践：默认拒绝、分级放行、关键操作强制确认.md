## 背景

接入 MCP、插件和自动化工具后，OpenClaw 这类 Agent 不再只是对话模型。它能读写文件、调用 GitHub API、发送 HTTP 请求、执行 shell 命令，甚至操作浏览器。能力扩大后，真正的风险不是“模型不够聪明”，而是“它一次误判，成本远超一次聊天”。

如果每次操作都问人类，自动化就变成摆设；如果全部自动执行，一条错误指令可能删文件、关 issue、刷爆外部 API。权限边界需要提前设计，而不是等事故发生后补丁式收紧。

## 问题

我们需要回答一个工程问题：**什么样的操作允许 Agent 自己干，什么样必须停下来问，什么样应该直接拒绝？**

这个边界不能只写进系统提示词。Prompt 只能降低调用概率，不能构成安全边界。真正的边界必须落在工具调用层、MCP scope 和插件权限配置里。

## 做法/步骤

### 1. 给工具做副作用分级

先列出 Agent 实际会接触的工具，按副作用和可逆性分类：

- **L0 只读**：读文件、查 API、搜索。允许自动执行。
- **L1 可逆写**：写工作目录内的临时文件、创建分支。可以自动执行，但必须记录。
- **L2 不可逆/外部副作用**：删除文件、关闭 issue、发送消息、扣费 API。默认 ask。
- **L3 高风险**：删除仓库、修改权限、执行任意 shell。默认 deny，或走二次确认。

这个分级不追求复杂，但要覆盖所有会“改变世界”的动作。

### 2. 把分级落到 allow / ask / deny 策略

以 OpenClaw 的配置习惯举例，可以组织成类似结构（伪配置，非完整语法）：

```yaml
tools:
  read_file: allow
  write_file:
    policy: ask_if_outside_workspace
  delete_file: ask
  shell:
    policy: deny
    allowlist: ["git status", "ls"]
  github_close_issue: ask
  http_request:
    policy: ask_if_external_domain
```

关键不是语法，而是**默认 deny，按需 allow**。不要让 Agent 继承用户的全部权限。

### 3. 对 MCP server 做 scope 最小化

MCP 授权很容易过粗。比如为了读一个 GitHub issue，给了整个 repo 的 write 权限。一旦 Agent 误判，就可能在仓库里乱改。

正确做法是只开放必要 scope：

```yaml
mcp_servers:
  github:
    allowed_scopes: ["repo:read"]
```

如果某个任务只需要读，就不要给它写。如果只碰某个目录，就把它限制在沙箱路径内。

### 4. 让 ask 信息包含具体参数

确认框不要只写“是否执行该操作？”这种无效提示。应包含工具名、目标对象和关键参数摘要。

例如：

> 即将关闭 GitHub issue #1234，对应仓库：openclaw/agent。是否继续？

这样人类判断才有依据，而不是惯性点击“允许”。

### 5. 保留审计日志

每次工具调用记录：工具名、参数摘要、执行结果、是否经过人工确认。日志不能只记工具名，否则出问题后无法定位到底改了什么。

## 踩坑点

- **只用 prompt 约束**：Agent 可能绕过或误判。执行层必须硬性限制。
- **MCP scope 过大**：只为了读数据，却给了写权限。这是最常见的事故源头。
- **确认太频繁**：所有操作都 ask，用户会疲劳，最终无脑点允许，保护失效。只在 L2/L3 级打断。
- **日志缺参数**：只知道调用了 `delete_file`，不知道删了哪个文件，回滚无从下手。
- **测试环境宽松，生产未收紧**：测试时图方便全 allow，上线时忘记改回，变成默认全放行。

## 可复用建议

可以用一个简单的四象限决策矩阵：

| 影响范围 \ 可逆性 | 可逆 | 不可逆 |
|---|---|---|
| 本地/沙箱 | allow + 记录 | ask |
| 外部/生产 | ask | deny 或双人确认 |

落地原则：

- 默认拒绝，按需放行。
- 只对高风险操作打断人类，不滥用 ask。
- MCP 权限按任务最小化，不图省事全开。
- 权限策略和代码一起版本化、评审、定期 review。
- 每季度关闭不再使用的工具权限和 MCP scope。

## 总结

权限边界不是限制 Agent，而是让它能够被信任地自动运行。目标不是“问人类越少越好”，而是把确认放在真正需要判断的地方。工具层限制、MCP scope、审计日志，三者配合，才能让 Agent 既能干活，又不会自动闯祸。
