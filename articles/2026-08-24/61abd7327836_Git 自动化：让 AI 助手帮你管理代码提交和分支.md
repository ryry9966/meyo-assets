## 背景

在 OpenClaw 类 Agent 工作流里，很多任务会停在“代码已改完，但提交还得人来”的阶段。Agent 生成了 patch、改了文件，却缺少一个受控的 Git 操作入口；直接给它 shell 权限，风险又太高。于是我们尝试把 Git 抽象成工具，让 AI 只负责生成规范提交和管理分支，命令执行留在受控层。

## 问题分析

AI 直接操作 Git 最容易出三类问题：

- **误提交**：`git add .` 会把临时文件、本地配置、未完成实验一起提交。
- **提交信息不稳定**：不同任务生成的 message 格式混乱，后续很难检索和生成 changelog。
- **分支操作越界**：让 Agent 自己删除、强推或 rebase，一旦理解错误，恢复成本很高。

所以关键不是“让 AI 更会写 Git 命令”，而是把 Git 能力收窄成一组白名单工具。

## 做法/步骤

### 1. 封装白名单工具

不建议给 Agent 通用 shell。通过 MCP server 或 OpenClaw plugin 暴露有限命令：

`git_status`、`git_diff`、`git_log`、`git_branch_list`、`git_branch_create`、`git_add`、`git_commit`、`git_push`。

把 `branch_delete`、`reset_hard`、`force_push` 单独拆开，默认关闭或要求人工确认。

### 2. 约束提交信息

不要让模型自由写整段 commit message。把 `git_commit` 设计成结构化参数：

```json
{
  "type": "feat",
  "scope": "agent",
  "summary": "add git automation tool wrapper",
  "body": "expose whitelisted git commands via MCP"
}
```

服务端按 Conventional Commits 拼接为 `feat(agent): add git automation tool wrapper`，同时限制 summary 不超过 72 个字符。这样格式稳定，后续也能自动生成 changelog。

### 3. 提交前强制看状态

在 prompt 或工具编排里要求：每次提交前必须先调用 `git_status` 和 `git_diff --stat`，把变更列表、统计和当前分支放进上下文。没有这两步，不允许调用 `git_commit`。

这套约束看起来简单，但能显著降低误提交。

### 4. 分支模板化

分支创建用固定规则，例如：

- `feature/ai-{task_id}`
- `fix/ai-{issue_id}`

不允许 AI 即兴创造长分支名，也不允许 AI 自动删除分支。删除或合并到主分支前，必须输出计划并等待人类确认。

### 5. 审计日志与恢复

工具服务端记录每次调用：会话 ID、时间、参数、返回结果、耗时。配合 `git reflog`，出错后可以定位到具体命令并恢复。关键分支操作额外记录前后 commit SHA。

## 踩坑点

- **`git add .` / `git commit -am`**：会把未跟踪文件和不相关改动一起提交。应根据 `git status --short` 列出的路径逐项 add。
- **脏工作目录**：提交前未检查，容易把半成品提交进去。遇到非预期变更时，先停下或 `stash`，不要继续。
- **认证问题**：在本地/容器中提前配置好 SSH key 或 token，避免让 AI 接触密码、sudo 或交互式输入。
- **提示注入**：diff 中可能出现类似指令的文本，模型不应把 diff 内容当作命令执行。工具层只操作 Git 对象，不执行任意字符串。
- **并发冲突**：同一仓库不要同时跑多个 Agent；如需并发，给 repo 加锁或租约。
- **破坏性操作**：`reset --hard`、`push --force`、删除分支必须设置二次确认，最好提供 UI 按钮或显式 `confirm` 参数。

## 可复用建议

- 把上述能力做成 MCP Git server 或 OpenClaw plugin，通过环境变量控制是否允许 push、force_push 等。
- 默认 dry-run：Agent 先输出将要执行的命令和影响文件，人类确认后再真正执行。
- 统一提交模板和分支命名，减少模型发挥空间。
- 在 CI/pre-commit 增加格式校验，和 Agent 提交策略对齐。
- 保留至少 30 天审计日志，结合 reflog 做恢复预案。

## 总结

AI 管理 Git 的收益不在完全接管，而在把低风险、重复性操作自动化。状态查看、规范提交、按模板建分支、生成变更摘要，这些交给 Agent 很合适；删除分支、强推、回滚，仍然应该由人确认。工程化的边界控制，往往比让模型更聪明更可靠。
