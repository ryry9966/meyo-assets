# OpenClaw Skills 机制：让 AI 助手按需加载能力

## 背景：Agent 功能越多，上下文越不够用

在 OpenClaw 里接 MCP、插件、自动化脚本一段时间后，很容易陷入一个困境：为了让助手“什么都能干”，把所有工具、技能、system prompt 全量挂载。结果就是：

- 上下文窗口被大量工具描述占用，真正留给任务的空间变少；
- 每次对话都要遍历几十个工具，响应变慢；
- 权限面过大，一个简单问答也可能触发不必要的外部调用；
- 工具之间命名冲突、版本冲突，排错成本高。

这类问题在插件化 Agent 架构里很常见。OpenClaw 的 Skills 机制要解决的核心就是：**默认不加载，按需加载，用完即走**。

## 问题：按需加载到底难在哪

“按需加载”听起来简单，但工程上要处理三件事：

1. 如何判断当前任务需要哪个技能？
2. 技能以什么形态加载？是 prompt、工具、脚本，还是组合体？
3. 加载后如何回收、缓存、隔离，避免污染后续对话？

OpenClaw 的答案是：把每个技能做成一个**自描述目录**，由声明文件驱动匹配和加载。

## 做法：一个 Skill 的基本结构

一个最小可用的 skill 目录长这样：

```
skills/
└── time_report/
    ├── skill.yaml
    ├── prompt.md
    ├── entry.py
    └── requirements.txt
```

其中 `skill.yaml` 是核心：

```yaml
name: time_report
description: >
  生成周报、日报或时间区间工作总结。适用于用户要求“总结本周工作”、
  “写日报”、“整理这段时间做了什么”等场景。
triggers:
  - 周报
  - 日报
  - 工作总结
entrypoint: entry.py
permissions:
  - read:./logs
  - run:git
cache: session
```

加载流程大致如下：

1. 用户输入后，OpenClaw 先把任务意图与所有 skill 的 `description` 和 `triggers` 做轻量匹配；
2. 命中后，读取该 skill 的 `entrypoint` 和 `prompt.md`，注入当前会话上下文；
3. 执行 entrypoint 暴露的能力，按 `permissions` 限制外部调用；
4. 任务结束或切换话题后，根据 `cache` 策略决定是保留、降级还是卸载。

这里的匹配不是重型语义检索，而是用“声明 + 触发词 + 简短描述”做过滤。好处是快、省 token，坏处是描述写得差就匹配不上，这是后面要说的踩坑点。

## 踩坑点

### 1. description 写得太泛或太窄

最常见的翻车现场：技能描述写“帮助用户处理事情”，结果任何任务都可能误命中；或者写“处理周一上午的销售数据”，换个时间就匹配不上。

**建议**：description 用“功能 + 适用场景 + 不适用场景”三段式。明确边界比堆关键词更有用。

### 2. entrypoint 路径和运行环境不一致

技能在本地能跑，加载到 OpenClaw 后报 `ModuleNotFoundError` 或路径错误。原因通常是入口文件依赖了技能目录外的全局包，或者用了相对导入。

**建议**：每个 skill 目录自带 `requirements.txt` 或锁定依赖版本；入口文件用绝对路径或基于 `__file__` 定位资源。加载器最好在隔离环境或容器里执行。

### 3. 缓存策略导致上下文污染

`cache: session` 能让技能在会话内保持状态，但如果用户切换任务，旧技能的工具描述还留在上下文里，新任务可能被误导。

**建议**：默认 `cache: none`，只在确需连续状态的技能上开启 session 级缓存；并且提供显式卸载指令，比如 `/skill unload time_report`。

### 4. 权限声明过宽，等于没隔离

有些技能为了“方便”，直接写 `permissions: [*]`，能读文件、执行 shell、访问网络。这跟全量加载没有本质区别，一旦误触发风险很大。

**建议**：权限最小化声明，只给当前技能必需的能力。例如只读日志、只跑 `git log`，不要给整个文件系统或任意命令执行权。

## 可复用建议

1. **原子化技能**：一个 skill 只做一件事，比如“生成周报”和“发送邮件”拆开。组合能力交给编排层，而不是塞进一个大而全的技能。
2. **声明文件当契约**：`skill.yaml` 里包含版本、依赖、权限、入口、缓存策略。任何技能先看声明，再决定是否加载。
3. **测试匹配准确率**：准备一组真实用户问句，定期检查每个 skill 的命中率和误命中率。描述改了之后要回归测试。
4. **版本锁定与回滚**：技能目录用 git 管理，发布时打 tag。线上出现行为异常时，能快速回退到上一个可用版本。
5. **可观测性**：记录每次技能加载、执行、卸载的耗时和权限调用。出问题先看“是不是技能被误加载了”，而不是直接怀疑模型推理能力。

## 总结

OpenClaw Skills 机制的价值不在于“多了一种插件格式”，而在于提供了一套**控制加载边界**的工程实践。它让 AI 助手保持轻量，同时保留扩展能力：默认只加载基础上下文，遇到明确任务再拉取对应技能，执行完回收。

如果你的 OpenClaw 实例开始出现上下文吃紧、工具冲突、响应变慢，不妨把现有能力拆成原子 skill，用声明文件管起来。你会发现，很多时候不是模型不够强，而是加载策略太粗暴。
