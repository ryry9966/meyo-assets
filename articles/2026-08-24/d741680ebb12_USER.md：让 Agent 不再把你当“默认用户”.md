很多 OpenClaw 用户会给项目写 AGENTS.md，告诉 Agent 仓库怎么构建、怎么测试、哪些目录不要碰。但换个项目、换个机器，同样的问题还会再来一遍：“我用什么包管理器？”“你希望回复中文还是英文？”“哪些目录不能动？”这些问题不是项目上下文能解决的，因为它们描述的是你，而不是仓库。

USER.md 就是把这个“你”沉淀成用户级上下文文件。

## 问题：Agent 默认把你当“默认用户”

Agent 在没有用户信息时，会用训练数据里的平均用户画像：英文回复、常见 Linux 路径、npm/pip 通用流程、对 sudo/rm 等操作缺乏边界感。结果是要么反复追问，要么给出不符合你环境的命令。

例如：

- 你用 pnpm，但 Agent 一直给 npm 命令；
- 你在 WSL2 里跑 OpenClaw，但 Agent 建议 macOS 路径；
- 你只是问一个 Docker 问题，Agent 顺手给了带 `--privileged` 的参数；
- 每次新会话都要重新声明“我是用 uv 管理 Python”。

项目规则管不到这些，因为项目规则通常只覆盖仓库内部。

## USER.md 应该写什么

建议只写四类：

1. 身份/环境：时区、OS、shell、编辑器、语言。
2. 工具偏好：包管理器、Python 环境、Node 版本管理、Git 提交格式。
3. 约束/负面清单：不要自动 push、不要删除指定目录、不要联网搜索、不要安装系统级依赖。
4. 沟通偏好：回复语言、详略、给命令时是否解释。

一个最小示例：

```markdown
# USER.md

- 时区：Asia/Shanghai
- OS：macOS / zsh
- 包管理：Homebrew；Node 用 pnpm；Python 用 uv
- 回复：中文；默认给可执行命令，再给解释
- 项目根目录：~/dev
- 不要自动 git push；不要触碰 ~/Documents 和 ~/Photos
- 不要写入真实密钥；密钥在 1Password 中
```

这个长度足够解决大部分重复澄清。不要追求一次写全，更新成本会很高。

## 加载与验证

把文件放在 `~/.config/openclaw/user.md`，然后确认 OpenClaw 是否支持全局 instructions。支持的话，在全局指令里增加一行引用或直接 include；不支持的话，可以在启动脚本里把该文件内容作为第一条用户消息注入，或写进项目模板的 AGENTS.md 首部。

验证方法很简单，开一个新会话问两个问题：

- “请根据你的上下文，描述我的工作环境。”
- “如果我要初始化一个 Python 项目，你会用什么工具链？”

如果答案与你的环境基本一致，说明 USER.md 已生效；如果不一致，检查加载顺序和文件路径。

## 踩坑点

1. **写太长**：超过 100 行后，模型容易忽略后面的约束，也会占用大量上下文。USER.md 是“快速索引”，不是文档库。
2. **写入密钥**：全局文件会被日志、调试信息、工具调用上下文带走。不要在 USER.md 里写 API key、token 或密码。写“密钥在 1Password 的 xxx 条目”即可。
3. **和项目规则冲突**：项目 AGENTS.md 说用 npm，USER.md 写 pnpm，Agent 可能会产生矛盾行为。需要明确优先级，例如“项目规则优先，USER.md 在没有项目约束时生效”。
4. **信息过期**：换机器、升级工具、改默认 shell 后，旧的 USER.md 会让 Agent 坚持错误环境。建议加一行“更新时间”，并让 Agent 在发现 env 输出与你描述不一致时先报告。
5. **角色设定污染**：不要把 USER.md 写成“你是我的高级技术顾问”之类的 system prompt。用户文件应描述事实和边界，角色设定放在具体会话或项目指令里。

## 可复用建议

- 用脚本生成基础信息：检测 OS、shell、包管理器、时区，生成一个 USER.md 骨架，人工补偏好。
- 把 USER.md 纳入 dotfiles 仓库；敏感内容拆成单独文件并 gitignore。
- 每遇到一次重复澄清，就往 USER.md 里加一条。这样它是“长出来”的，而不是拍脑袋写的。
- 定期核对：换设备、重装系统或升级 OpenClaw 后，跑一次环境核对。

## 总结

USER.md 解决的不是“Agent 不够聪明”，而是“Agent 不知道你”。它是低成本的个性化层：文件小、规则少、可版本化，就能明显减少跨会话的重复沟通。对 OpenClaw、MCP、插件和自动化流程用户来说，值得在补项目规则之前，先把自己的 USER.md 建起来。
