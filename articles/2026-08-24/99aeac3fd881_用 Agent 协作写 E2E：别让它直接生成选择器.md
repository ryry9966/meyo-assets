## 背景

E2E 测试长期处于“能跑就行，维护随缘”的状态。很多团队不是不知道要写，而是写完之后每隔两周就要跟着 UI 改选择器、改等待、改测试数据，最后放弃。Agent + MCP 的出现让这件事有了新的可能性：让 AI 直接操作浏览器、读取页面结构、执行并修改测试脚本。

但在实际落地中，直接对 Agent 说“帮我写个登录测试”，产出的脚本通常脆弱、断言空洞、失败后反复修改却无法收敛。问题不在 Agent 能力，而在于我们没有把测试设计中的关键约束交给它。

## 问题：为什么直接生成会失控

常见的失败模式有几种：

- AI 默认选中可见文本、绝对 XPath 或 CSS 层级，UI 一改就挂。
- 生成脚本只验证“页面没报错”“跳到了某个 URL”，缺少真实业务断言。
- 失败后 Agent 为了“让测试通过”，会把断言改弱，甚至删除关键验证。
- 并行执行时共用同一个账号，导致互相踢下线或数据污染。
- 把完整 innerHTML 丢给 Agent，上下文爆炸，生成质量下降。

这些问题的根源是：我们把“测试意图”和“具体实现”混在一起，让 Agent 一次性完成了太多不稳定决策。

## 做法：把 Agent 当成执行者，而不是决策者

### 1. 先建立稳定的选择器策略

在让 Agent 写任何脚本之前，先约束它使用 `data-testid`。如果页面还没有，就先用半天时间补关键路径的 testid。不要依赖文字、placeholder、class。可以在指令中写清楚：

> 优先使用 `data-testid`，禁止使用绝对 XPath；遇到没有 testid 的元素，先报告，不要自己猜 CSS 层级。

### 2. 用 MCP 暴露受控浏览器能力

在 OpenClaw 的 Agent 编排里，可以把 Playwright 封装成 MCP server，让 Agent 通过工具调用完成导航、点击、输入、读取 ARIA snapshot、截图。关键是不要给 Agent 完整的 DOM。让工具返回可访问性树或简化的语义结构，减少噪声。

例如只返回角色、名称、状态、关联的 testid，不返回 `div`、`span` 嵌套。这会让 Agent 更接近“用户视角”，而不是“DOM 视角”。

### 3. 分两步生成：先意图，后脚本

不要一步到位。先让 Agent 根据用户流程生成“测试意图清单”：

- 前置条件：需要什么角色、什么数据状态
- 操作步骤：用户做了什么
- 预期结果：哪些元素状态变化、哪些接口被调用、哪些数据被写入

人工确认意图后，再让生成具体测试代码。这个阶段 Agent 也可以读取现有测试目录，模仿 fixtures、命名、命令风格，而不是从零发明。

### 4. 失败后只诊断，不急着改

测试跑挂后，不要让 Agent 自动修改。先让它读取错误信息、失败步骤的 ARIA snapshot，然后提出“根因假设”和“拟修改方案”。人工确认后，再授权修改。同时设置最大重试次数，比如每轮最多改 2 次，超过就停下让人处理。

这样可以避免 Agent 在上下文里反复尝试、把测试越改越弱。

### 5. 把重复操作沉淀成工具

登录、创建订单、切换租户这类高频操作，可以封装成自定义 MCP 工具或测试 fixture。Agent 只需要调用 `login_as(role)`，而不是每次重新生成一套登录流程。这样测试代码更短，生成结果也更稳定。

## 踩坑点

- **别给完整 HTML**：上下文会和依赖一样快速膨胀，且模型会关注错误层级。用 ARIA snapshot 或简化后的可访问树。
- **断言空洞**：AI 倾向于写“页面包含成功”这类弱断言。需要明确要求验证接口请求、数据库状态或关键元素状态。
- **测试数据污染**：多人并行或多次执行时，共用账号会导致不确定性。要么为每个测试生成随机数据，要么按角色/租户隔离环境。
- **Agent 会把断言改弱**：修改前后 diff 必须 review。可以加一条硬规则：“修改后断言数量不得少于原测试，且核心业务断言必须保留。”
- **长任务超时**：OpenClaw 跑复杂 E2E 生成链容易超时。把中间产物（意图、脚本、执行报告）保存成文件，分阶段续跑，不要一次跑完。

## 可复用建议

- 建立仓库级约束：`testid` 规范、fixtures 模板、断言风格说明，放在 Agent 可读取的文档里。
- 让 Agent 生成的是“测试计划”和“测试骨架”，关键业务断言由人补充。
- 限制 MCP server 的能力范围：只允许访问测试域名，禁止外部请求，降低风险。
- 每轮生成后跑 lint、tsc、现有 CI，不通过就停止，不进入下一轮。
- 把 Agent 的每次修改记录到 git，方便回溯和对比。

## 总结

Agent 在 E2E 测试中的价值，不是替代测试设计，而是降低“从页面理解到脚本实现”的转换成本。只要把选择器策略、测试意图、环境隔离、修改边界这些工程约束先做好，Agent 就能稳定地产出可维护的测试骨架，而不是快速制造一堆坏测试。

真正可复用的做法是：**人定义意图和约束，Agent 负责执行和生成，最终审核权留在人手里。**
