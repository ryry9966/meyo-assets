## 背景

在 OpenClaw / Agent 工作流里，AI 生成内容默认是 Markdown，这本身很高效。但一旦要把内容发到公众号、知乎、飞书、GitHub 等平台，差异就暴露出来了：公众号不认代码块语法，表格经常错位；飞书 API 要求块级 JSON；知乎对标题层级和表格有隐形规则。很多时候 Agent 输出的 Markdown 看起来“很标准”，复制到目标编辑器里却面目全非。我们需要一条可控的管线，而不是每次手动修格式。

## 问题拆解

直接暴露的差异点集中在：

- **标题层级**：AI 常输出一级 `#`，但多数内容平台只接受二级以下。
- **表格**：复杂表格、列宽、换行、特殊字符在公众号/知乎容易翻车。
- **代码块**：没有语言标注，平台无法高亮；公众号会直接去掉格式。
- **图片**：相对路径或本地文件无法直接发布，必须转成绝对 URL。
- **扩展语法**：LaTeX 公式、HTML 内嵌、脚注等非 CommonMark 扩展，支持度参差。
- **API 格式**：飞书要块列表，知乎更接近 HTML，GitHub 要标准 Markdown。

这些不是“平台限制”能概括的，而是需要工程化适配才能稳定跨平台发布。

## 做法与步骤

我实践中的管线分为五步：

1. **输出约束**  
   在 Agent 的 system prompt 里写死 Markdown 规范：从 `##` 开始；表格必须有表头且不超过 4 列；代码块必须带语言标识；所有图片必须是 `https://` 绝对 URL；禁用 HTML 标签、脚注和 LaTeX；列表嵌套不超过 3 层。同时给出正面和负面示例。

2. **规范化校验**  
   生成后立即用 markdownlint 或自定义规则做校验。常用规则包括：MD001（标题层级递增）、MD033（禁用 HTML）、MD040（代码块语言必填）。这一步能挡住 80% 的低级错误。校验失败时触发 Agent 二次修复，而不是直接发布。

3. **转换层**  
   用 mdast（Markdown AST）作为中间表示，写各平台 adapter。例如：
   - **公众号 adapter**：表格转文本对齐表格或生成图片；代码块通过 Carbon 类服务转高亮图片；删除不支持的 HTML 标签。
   - **飞书 adapter**：递归遍历 mdast，生成飞书 OpenAPI 的块 JSON，列表、引用、代码块需要单独映射。
   - **知乎 adapter**：一级标题降级；表格转 Markdown 原生表格，注意竖线转义；`<`、`&` 在输出阶段处理。
   - **GitHub / Notion adapter**：基本保留，但统一换行、清理多余空行。

4. **发布与回滚**  
   把 adapter 封装成 MCP 工具或 OpenClaw 插件。发布前先 dry-run 输出预览；平台 API 失败时保留原始 Markdown 和 adapter 输出，可重试或回滚。

5. **回读校验**  
   发布后抓取渲染结果，与源 Markdown 做 diff，标记格式漂移（如代码块变纯文本、表格错位）。连续两次漂移就升级为规则，加入 lint。

## 踩坑点

- **不要只依赖 prompt**：AI 会随机突破约束，必须把校验放在管道里，而不是靠提示词。
- **表格是重灾区**：规范里就限制复杂度，超过阈值直接转图或文本，别硬扛。
- **公众号代码块**：直接粘贴会变成无高亮纯文本。要么用编辑器插件，要么提前转图。转图注意行号、字号和暗色主题。
- **飞书块 JSON 很繁琐**：列表和引用的嵌套容易出现“块类型不匹配”。先写最小可用解析器，别想一次覆盖全部语法。
- **字符转义**：`<`、`&` 在 HTML 渲染平台需要转义，但在 Markdown 源里转义会破坏语法。统一在 adapter 输出阶段处理。
- **图片防盗链**：图床 URL 可能在知乎/公众号被拦截。优先使用支持白名单的图床，或提前下载图片走平台上传接口。
- **发布顺序**：先发对 Markdown 支持最好的平台（GitHub），再发适配层较薄的（公众号），最后发需要结构化 JSON 的（飞书），便于逐步验证。

## 可复用建议

- **一份源，多端发布**：源 Markdown 只使用 CommonMark + GFM 表格 + 代码块语言 + 绝对 URL 图片。这是最小公共子集，也是管线的契约。
- **用 markdownlint 配置文件作为团队标准**，提交到项目仓库，和 Agent 的 system prompt 保持一致。
- **把 adapter 做成插件或 MCP server**，而不是写死在脚本里，社区可以复用不同平台的转换逻辑。
- **每次发布保留两个文件**：`source.md` 和 `rendered-preview.html`，方便回滚和排障。
- **维护平台能力矩阵**：记录各平台支持的 Markdown 特性、上限和降级策略，每两个月更新一次。

## 总结

Markdown 管线不是银弹，它的核心是把“AI 生成的不可控格式”通过约束、校验、转换、回读几道工序，变成可复现、可回滚的发布流程。很多问题不是 AI 的错，而是平台差异没有被显式处理。把适配逻辑固化成工具，让 Agent 只负责生成和调度，管线负责把格式修到各平台能吃，自动化发布才算真正落地。
