## 背景

在 OpenClaw/Agent/MCP/插件自动化里，重复触发基本无法避免：定时任务和手动触发可能叠加，Agent 对同一个 MCP 工具可能因为模型重试而重复调用，消息队列可能重复投递，用户也可能连点按钮。真正危险的不是“多跑一次”，而是任务本身不幂等，导致重复建单、重复扣费、重复发消息、重复写入外部系统。

所以，幂等性不是“防止重复执行”，而是**重复执行不会产生额外副作用**。

## 问题

不少自动化任务一开始只写了 `create_xxx`，没有去重入口。更常见的是只做“先查不存在再插入”的 check-then-act，或者把时间戳、随机数放进请求里。单线程下看起来没问题，一旦遇到 Agent 重试、并发 worker、插件热加载后重复回调，就会出重复资源、脏状态或任务卡死。

## 做法/步骤

### 1. 给每次业务动作生成稳定幂等键

优先使用上游传入的 `idempotency_key`，或者业务唯一号，如订单号、来源 ID、工单编号。如果没有，可以计算：

```text
hash(namespace + action + business_key)
```

注意：幂等键里不要包含时间戳、随机数、模型输出等非确定内容，否则同一次业务动作每次都会生成不同 key。

### 2. 入口先查后建，并用唯一约束兜底

只靠 SELECT 查重是防不住并发的。数据库层要建唯一索引，例如：

```sql
CREATE UNIQUE INDEX uk_task_runs_idem
ON task_runs(namespace, idempotency_key);
```

写入时：

```sql
INSERT INTO task_runs(idempotency_key, result, created_at)
VALUES ($1, $2, now())
ON CONFLICT (idempotency_key) DO NOTHING;
```

如果冲突，说明已经执行过，直接返回已有结果，而不是报错重试。

### 3. 任务状态用状态机，认领必须原子化

定时任务或 MCP 工具处理任务时，用原子更新认领：

```sql
UPDATE tasks
SET status = 'processing', worker_id = $worker
WHERE id = $id AND status = 'pending';
```

影响行数为 0，说明别的 worker 已经处理，当前调用直接返回。处理完成后改成 `done`。失败时回到 `pending` 或 `failed`，不要让它卡在 `processing`。

### 4. 第三方 API 尽量透传幂等键

外部服务如果支持 `Idempotency-Key` 请求头，就一路透传；如果不支持，就用业务唯一标识先查再建。外部副作用一旦产生就无法回滚，所以需要额外加对账任务。

### 5. MCP/插件层封装安全语义

不要只暴露裸的 `create`。可以封装成：

- `ensure_task_created`
- `upsert_by_external_id`
- `get_or_create_by_key`

让 Agent 重复调用同一个工具时，行为可预期。

## 踩坑点

- **check-then-act 竞态**：并发下两条请求都能查到“不存在”，然后都插入，唯一约束才是最后防线。
- **幂等键包含纳秒时间戳或随机种子**：看起来更精确，实际让幂等失效。
- **只处理主资源，忽略通知、日志、统计等副作用**：主记录没重复，但用户收到两条通知，仍然算事故。
- **失败后状态未回滚**：任务一直停在 `processing`，后续重试被自己的状态机挡住。
- **冲突后不返回已有结果**：上层以为失败，继续重试，反而放大压力。

## 可复用建议

- 新插件或 MCP 工具先写幂等测试：同一参数并发调用 10 次，断言只产生一条核心记录。
- 内部统一维护 `task_runs` 或 `idempotency_records` 表，保存 `key -> result`，方便对账。
- 设计文档里标注副作用类型：可重复消费、需幂等、不可逆。
- 对“至少执行一次”的流程，接受 at-least-once，但必须配合幂等消费，而不是追求 exactly-once。
- 长任务加心跳和超时回收，让 `processing` 状态可恢复。

## 总结

自动化系统很难做到“绝不重复触发”，但可以做到“重复触发也安全”。稳定的幂等键、数据库唯一约束、任务状态机原子迁移，以及外部接口去重，这四件事组成一个现实的工程边界。对 Agent/MCP/插件来说，幂等性不是附加功能，而是重试、并发和故障恢复的基础。
