# Git 自动化：给 AI 助手装好刹车，再让它管提交和分支

## 背景

在 OpenClaw-CN 的很多实践里，代码生成、文档整理、信息查询已经交给 Agent 处理。但 Git 操作仍然是高频重复劳动：改完一个 bug 要写 `fix: ...`，每个 issue 要手动切分支，合并后本地堆着一堆没人清理的分支。这些操作规则明确、格式固定，其实很适合交给 AI 助手。

问题在于，Git 是强状态、可写远端、可破坏历史的工具。如果直接给 Agent 一个 shell 权限，很容易出现错误提交、把密钥或临时文件一起提交、误用 force push、批量删除未合并分支等情况。所以真正的挑战不是“让 AI 能执行 git 命令”，而是“把 Git 能力放进一个可控的笼子里”。

## 做法

### 1. 接入受限的 Git 工具

在 OpenClaw 中接入 Git MCP Server 时，不要暴露通用 shell，只暴露必要的 Git 工具，并明确禁止危险操作。例如：

```yaml
tools:
  - git_status
  - git_diff
  - git_log
  - git_branch_list
  - git_create_branch
  - git_stage
  - git_commit
  - git_push_current_branch
forbidden:
  - git_reset_hard
  - git_force_push
  - git_delete_remote_branch
```

这样模型即使“想做更多”，也没有入口。工具层先做一次权限收敛，比 prompt 里的“不要乱来”可靠得多。

### 2. 拆成“分析”和“执行”两阶段

读操作可以自动跑，写操作必须经过确认。例如让 AI 先输出一份计划：

```text
计划：
1. 创建分支 feat/ISSUE-123-fix-login-timeout
2. 暂存 src/auth/login.ts
3. 提交信息：fix(auth): handle login timeout gracefully
```

人工确认后，再调用写工具执行。OpenClaw 中可以接一个 approval 步骤，或者让 Agent 输出 JSON 计划，由外部脚本解析后执行。

### 3. 提交信息生成

最轻量的切入点是提交信息。只让 AI 读 `git diff --staged --stat` 和具体文件的 diff，并限定输出格式：

```text
根据以下 staged diff 生成提交信息。
要求：
- 使用 Conventional Commits
- 标题不超过 72 字符
- 不要包含文件路径
- 只输出一行 commit message
```

这样比让模型自由发挥稳定得多。配合 commitlint 做二次校验，基本可以替代手写大部分常规提交。

### 4. 分支管理

分支创建可以从 issue 标题生成 slug，例如 `feat/ISSUE-123-fix-login-timeout`。清理分支时，先让 AI 列出 `git branch --merged` 的候选分支，标记建议删除项，再由人工确认。删除命令只允许本地分支，且必须带上 merged 状态检查，避免误删。

### 5. 固化规则到配置

把 prompt、分支命名规则、允许的 commit 类型、diff 长度限制等写进 `.openclaw/git-agent.yml`，随仓库版本化。这样任何成员或 CI 环境都能复用同一套规则，不会因为口头约定而漂移。

## 踩坑点

- **长 diff 截断导致提交信息失真**：一次提交改动几十个文件时，模型只看到部分 diff，生成的信息往往不准确。可以先传 `diff --stat` 建立全局，再按文件分块摘要，单次输入控制在 8k tokens 以内。
- **模型幻觉执行 shell**：不要给通用 shell 工具。即使模型说“我会只运行 git status”，也要在工具层限制它只能跑白名单命令。
- **密钥泄漏**：提交前加一道 `gitleaks` 或类似扫描，发现敏感信息直接阻断提交，不要等推送后再补救。
- **批量删除误删分支**：删除操作必须 dry-run 先展示会删哪些分支，并显示每个分支是否已合并。人工确认后再真正执行。
- **pre-commit hook 卡住提交**：在 hook 里调用 AI 生成 commit message 时，要设置 5 秒左右超时，失败则回退到模板，不能阻塞开发流程。
- **权限过度**：push 只允许推当前分支，禁止 `--force`，远端分支删除默认关闭。

## 可复用建议

1. **能只读就不写，能本地就不远端**。先从本地提交信息、PR 描述草稿开始，分支清理和推送留到稳定后再放开。
2. **任何写操作先 dry-run**，展示预期结果，确认后再执行。
3. **用 commitlint、gitleaks 做机器校验**，不要只依赖模型自觉。
4. **保留操作日志和 reflog**，即使误操作也能恢复。
5. **从小场景落地**：一个只生成 commit message 的 pre-commit hook，比一个全自动 Git Agent 更容易被团队接受，也更可控。

## 总结

AI 管理 Git 的合理定位是：执行重复规则、草拟规范内容，最终确认权仍然留在人手里。通过工具白名单、dry-run、人工确认和规范校验，Git 自动化可以从“危险玩具”变成真正省时间的工程助手。先在本地 feature 分支上跑通，再逐步扩展，是更务实的路径。
