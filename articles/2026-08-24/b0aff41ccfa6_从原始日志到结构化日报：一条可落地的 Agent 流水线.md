## 背景

很多团队的日报素材其实已经存在于原始日志里：Git 提交、CI 构建记录、监控告警、日历会议、IM 讨论。问题不是没有数据，而是数据太散、格式不统一，每天靠人工翻一遍再拼贴，重复且容易漏。

在 OpenClaw/Agent/MCP 的实践里，日报自动化很适合作为一个“信息整理型”流水线来落地。但要做得稳定，就不能只写一句“帮我根据今天日志生成日报”。真正可维护的做法，是把原始日志经过采集、清洗、抽取、渲染，最后输出结构化报告。

## 问题

直接让模型读原始日志，往往会遇到几类问题：

- 来源分散：Git、CI、监控、日历格式完全不同。
- 时区混乱：服务端 UTC、本地时间混在一起。
- 重复记录：一次工作既出现在 commit，也出现在 PR 合并。
- 语义混淆：把监控告警当成“今天完成的工作”。
- 幻觉：模型可能补出你没做过的任务，或编造完成度。
- 输出不稳定：日报格式每次不一样，难以沉淀和复用。

所以需要一条流水线，而不是一段一次性 prompt。

## 做法/步骤

### 1. 先定义最小事件结构

不要一上来就生成报告，先把所有来源抽象成统一的中间事件。例如：

```json
{
  "source": "git",
  "id": "repo:commit_sha",
  "ts": "2025-01-01T09:30:00Z",
  "type": "done|doing|blocked|incident|meeting|other",
  "actor": "alice",
  "summary": "修复登录超时",
  "ref": "https://example.com/commit/abc",
  "raw": "原始日志片段"
}
```

关键是保留 `source`、`id`、`ref`、`raw`。这些字段是后续去重、回溯、防幻觉的基础。

### 2. 用 MCP 或插件做采集层

把 Git、CI、日历、监控等能力封装成只读 MCP server 或 OpenClaw 插件，输出上面定义的中间事件。不要直接在 prompt 里粘贴一整段原始日志，而是让工具先返回标准化片段。

采集时尽量只拿当天或指定时间窗口的数据，避免上下文爆炸。

### 3. 清洗与过滤

清洗比生成更重要。常见处理：

- 统一转换为 UTC 存储，渲染时再转本地时区。
- 用 `source + id` 去重。
- 过滤自动提交、机器人消息、CI 重试记录。
- 把同一 PR 的 commit 和 merge 事件合并成一个工作项。

### 4. 低温度抽取与归类

把清洗后的事件交给模型时，目标不是“写日报”，而是“抽取和归类”。使用低温度、JSON mode，要求每条 `summary` 只能基于 `raw` 内容生成，不能凭空补全。没有把握的事件标记为 `other`，而不是硬塞进“今日完成”。

规则能做的先交给规则。例如确定性的 CI 状态、Git 作者、时间窗口，用脚本处理；模型只做语义归纳和复杂归类。

### 5. 模板渲染与人工审查

结构化事件进入模板后，再生成日报草稿。每条工作项尽量带 `ref` 链接，方便回溯。发布前保留人工确认环节，不要一开始就全自动发送。

## 踩坑点

- **幻觉**：模型很容易把“今天处理了告警”写成“完成了优化”。所有的 `summary` 都要能对应到 `raw` 和 `ref`，无法溯源的直接丢弃。
- **时区**：统一 UTC 存储，显示层再转换，否则跨时区成员日报会错位。
- **重复归一**：Git commit、PR merge、需求状态变更可能描述同一件事。需要设计合并键，如 `repo + PR number`。
- **告警不等于工作**：给事件打 `type`，不要把 `incident` 和 `done` 混在“今日工作”里。
- **输出格式漂移**：用 JSON schema 校验，字段缺失时重试，仍失败则降级为规则输出。
- **安全**：MCP 工具只读权限，token 和凭据不要放进 prompt 或日志。

## 可复用建议

1. **先建中间事件流**，不要直接生成最终报告。中间结构稳定了，上层报告格式可以随时换。
2. **规则优先，模型兜底**。确定性处理不要用模型，节省 token，也减少随机性。
3. **保留 raw 和 ref**。日报里的每一条都应能回到原始证据。
4. **小步扩展数据源**。先接 Git 和 CI，跑通后再加监控、日历、IM。
5. **保留审计日志**。把自动生成结果和人工修改后的版本做对比，持续发现规则缺陷。

## 总结

从原始日志到结构化日报，关键不是把模型能力拉满，而是把流程拆成采集、清洗、抽取、渲染、审查几个环节，让模型只在受约束的抽取环节发挥作用。这样得到的不是“看起来像日报”的随机文本，而是一条可以维护、可以回溯、可以渐近扩展的自动化流水线。
