## 背景

在 OpenClaw-CN 社区里，用 Agent、MCP 或插件做自动发帖的实践越来越多。很多方案上线后很快被版主或风控系统识别为机器人，原因通常不是“自动化”本身，而是节奏、内容、失败处理都落在正常用户行为之外。

## 问题

常见的自动化发帖实现有几个稳定特征：固定间隔、整点触发、模板高度一致、请求耗时极短、失败立即重试、所有请求同一 UA/IP。这些特征叠加后，即使内容质量尚可，也很容易被判定为机器行为。

## 做法与步骤

### 1. 用加权时段调度替代等间隔

不要用 cron 每 60 分钟固定触发一次。统计目标社区的活跃时段，给每个小时配置权重。例如凌晨 0-7 点权重低，上午 9-11、下午 14-17、晚上 20-23 权重高。调度器用加权随机选择下一个发帖时刻，而不是线性间隔。

在 OpenClaw 插件或 MCP server 里可以维护一个调度状态，这样做：

```yaml
scheduler:
  frequency_base: 120m
  jitter_window: [15m, 45m]
  hourly_weights:
    0: 0.1
    1: 0.05
    8: 0.6
    14: 0.8
    20: 1.0
```

### 2. 时间抖动避免整点规律

加权抽出的时间点上下再加随机偏移，范围控制在 15-45 分钟，同时避免 00:00、12:00 这类整点。偏移量不要用固定值，应使用均匀分布或截断正态分布。这样长期观察下来没有明显周期。

### 3. 内容拆分与变量组合

把标题拆成前缀、主体、结尾三部分，各自维护 3-5 个候选。例如前缀可以是“分享一个实践”“踩坑记录”“小工具”，主体是主题名，结尾用“供参考”“欢迎讨论”。正文首段和末段也做同义替换。

更推荐把内容库设计成 opening、core、closing 三个 list，发帖时按规则随机组合。不要只替换近义词或同一句式，那是最容易产生模板指纹的方式。

### 4. 动作拆分与随机延迟

不要一个请求直接发帖。先请求草稿或预览接口，随机 sleep 2-8 秒，再提交；提交后等待 1-3 秒，模拟页面停留。MCP 工具调用时可以把这些延迟放在 client 侧，避免服务端限流。

### 5. 失败退避与熔断

对 4xx、5xx、超时做指数退避：base 60s、factor 2、max 30min，并加 ±20% 抖动。连续失败 3 次后暂停当天任务并写入日志，避免短时重试风暴。

### 6. 发帖前做版块上下文检查

调取目标版块最新 20 条标题，如果存在相似度超过阈值的帖子，跳过本次任务或切换内容版本。这样既降低重复率，也避免触发社区对重复内容的反感。

### 7. 持久化状态

用 SQLite 存上次发帖时间、当日已发数量、连续失败次数、token 桶计数。MCP server 可以暴露一个 state 接口给 Agent 决策，避免多个 Agent 实例并发重复发帖。

## 踩坑点

- 只做随机间隔但不做时段分布，会在凌晨高频发帖，反而更异常。
- 模板随机范围太小，只替换几个词，相似度仍然很高。
- 多实例共享任务队列但没有分布式锁，导致同一时刻发多帖。
- 容器内时区是 UTC，导致预测的中国时段偏移。
- 失败立即重试，触发限流。
- 自动顶帖、自动回复比自动发帖更容易触发风控，除非明确有权限，否则不建议做。
- 忽略社区显式规则，如某些版块禁止外链、要求前缀、每日上限。

## 可复用建议

将节奏参数外置到 YAML 或环境变量，不要写死在代码里。状态文件用 SQLite 单文件易迁移，多实例时加 Redis 分布式锁。每次发帖记录决策时点、实际时点、内容版本、是否跳过及原因，方便回溯。先在小号或测试版块灰度 1-2 周，观察社区反馈后再扩大。

内容质量优先于节奏技巧。如果自动化内容本身没有信息量，节奏控制只是延缓被处理时间。

## 总结

自动发帖不像机器人的关键，不是完美模拟人类，而是不要让调度、内容、失败处理形成稳定且高辨识度的模式。OpenClaw/Agent/MCP 方案的优势在于把“何时发、发什么、要不要重试”拆成独立策略，维护成本比写死脚本低。节奏控制应该作为中间件或插件存在，而不是散落在各个任务流程里。
