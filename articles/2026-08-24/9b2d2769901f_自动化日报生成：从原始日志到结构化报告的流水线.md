## 背景

很多团队每天要整理日报：今天提交了什么、CI 构建是否通过、有没有告警、上线了什么、还有哪些遗留风险。这些信息散落在 Git、CI、监控告警、服务器日志、工单系统里，人工汇总很费时间，内容还容易因人而异。

我们在 OpenClaw 里用 Agent + MCP 做了一条自动化流水线，把原始日志逐步处理成结构化日报。整体思路不算复杂：采集、归一化、聚合、生成、校验、推送。真正关键的不是“让模型写日报”，而是前面的日志治理和后面的输出约束。

## 问题

原始数据源通常有三个特点：

1. **格式异构**：Git log、CI stdout、K8s events、告警接口字段完全不一致。
2. **噪声很大**：一次构建可能输出几千行日志，但真正有价值的只有失败栈和关键阶段。
3. **不可追溯**：如果日报里写“修复了登录问题”，但没有 commit、没有告警链接，读者不敢信。

直接把原始日志塞给 Agent，不仅上下文容易爆，模型注意力还会漂移，漏掉真正重要的异常。另一个常见问题是幻觉：模型会生成看起来很合理的 commit 标题或指标，但原始来源里根本不存在。

## 做法/步骤

### 1. 先定义日报 Schema

先不要把日志直接丢给模型。我们第一步是定义结构化输出，例如：

```json
{
  "date": "2025-01-01",
  "summary": "一句话总结",
  "changes": [
    {"source": "git:repo@abc123", "title": "修复登录超时", "impact": "auth 模块"}
  ],
  "incidents": [
    {"source": "alert:12345", "level": "high", "status": "resolved"}
  ],
  "metrics": {"deploy_count": 3, "failed_jobs": 1},
  "risks": ["支付回调延迟未排查"]
}
```

Schema 先行，后续所有环节都为这个结构服务。

### 2. 采集层：用 MCP 连接数据源

在 OpenClaw 里配置 Git MCP、CI MCP、日志文件 MCP 等连接器。采集层只做时间窗口过滤和基础裁剪，不要把完整大文件直接交给 Agent。

例如 Git MCP 只拉当天 00:00 到当前时间的 commits；CI MCP 只拉当天失败 job 的关键日志段。

### 3. 归一化：统一事件结构

每个数据源输出统一事件：

```json
{
  "ts": "2025-01-01T00:12:00Z",
  "source": "github",
  "level": "info",
  "ref": "repo@abc123",
  "summary": "feat: add login timeout retry"
}
```

时间统一转成 UTC ISO8601，原始引用保留在 `ref` 字段。这一步建议用脚本或插件完成，不要交给模型。

### 4. 聚合与压缩

重复错误合并，同一任务的多阶段日志压缩成一条摘要。错误栈只保留前 N 行。聚合后的数据量通常能缩小一到两个数量级，再进入生成阶段。

### 5. 生成日报

Prompt 固定模板，重点约束：

- 只能依据给定 events 编写；
- 每条结论必须带 `ref`，没有来源不写入；
- 指标必须由可统计字段计算，不得估算；
- 严格输出 JSON，不额外解释。

### 6. 校验与推送

用 JSON Schema 校验生成结果。校验失败时，把错误信息回传给 Agent 重试。通过后输出两份：Markdown 推送到 IM 或邮件，JSON 存档供后续统计。

## 踩坑点

- **直接喂原始日志**：上下文爆炸，模型漏掉关键异常。改成先规则聚合，再让 LLM 写报告，效果提升明显。
- **时区不统一**：CI 是 UTC，业务日志可能是 UTC+8。窗口错位会导致漏报“昨晚”的事件。统一在采集层转 UTC，按业务日期归日。
- **幻觉来源**：模型偶尔会生成好看的 commit 标题，但 `ref` 并不存在。我们在校验阶段加 ref 格式检查，并强制“无 ref 不写入”。
- **敏感信息泄露**：日志里可能带 token、手机号、内网地址。进入外部模型前先做正则脱敏，必要时用本地模型做摘要。
- **MCP server 不稳定**：某个源拉不到时，报告里要明确标注 `missing`，而不是空着或编造。需要超时、重试和降级策略。

## 可复用建议

1. **Schema 先行**：用 JSON Schema 约束输出，不要让模型自由发挥格式。
2. **分层架构**：Collector → Normalizer → Aggregator → Reporter。各层可独立调试，不要把逻辑堆在一条 prompt 里。
3. **保留 raw_ref**：每条结论都能跳回原始日志，否则日报没有可信度。
4. **缓存归一化事件**：当天事件缓存下来，后续修改 prompt 后可以重跑，不需要重新采集。
5. **双输出**：Markdown 给人看，JSON 给程序消费。
6. **先覆盖三类源**：Git、CI、告警。跑稳后再扩展工单、监控指标等。

## 总结

自动化日报流水线的核心不是模型有多聪明，而是日志治理和输出约束。先把原始日志处理成带来源、带时间、结构统一的原子事件，再让 Agent 在固定 Schema 下生成报告，能显著减少幻觉和遗漏。稳定比聪明更重要。
