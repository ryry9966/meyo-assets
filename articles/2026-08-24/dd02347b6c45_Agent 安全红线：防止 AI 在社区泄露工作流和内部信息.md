## 背景

OpenClaw 社区里，分享自动化工作流、插件配置、MCP 工具调用链是常态。但最近几次事件让人警惕：有人贴出包含真实 API 密钥的配置文件；有 Agent 在群里回答问题时把内部服务器路径、数据库表结构带了出来；还有人把公司内部系统的调试日志当示例发出来。这些泄露轻则导致服务被滥用，重则直接暴露内部资产。

## 问题

泄露通常来自两个通道：一是人主动分享时未做脱敏；二是 Agent 运行过程中自主输出。后者更隐蔽：如果 Agent 接入了企业知识库、工单系统或内部 MCP 工具，它可能在回答社区问题时引用真实数据。比如有人问“怎么配置定时任务”，Agent 返回的示例里带着生产环境的 cron 表达式和主机名。这种情况下，人工审核往往来不及拦截。

## 做法/步骤

1. **敏感信息分级与标记**  
   把配置、日志、代码片段中的敏感项分成三类——凭证（密钥/token/密码）、资产（IP/域名/路径/表名）、业务数据（客户名/工单内容）。分享前对这三类做替换，而不是只靠感觉“应该没问题”。

2. **使用环境变量隔离**  
   所有密钥、端点、数据库连接串通过环境变量注入，不在代码、配置、提示词中硬编码。社区示例统一用 `process.env.XXX` 占位。这样即使有人复制了你的配置，也不会直接拿到真实值。

3. **给 Agent 增加输出边界**  
   在系统提示词里明确禁止输出真实凭证、内部路径、客户数据。例如：“你是一个面向社区的技术助手，回答示例时一律使用 `example.com`、`your-api-key`、`/path/to/project` 等占位符。”不要只写“注意安全”，要给出具体替换规则。

4. **工具输出过滤**  
   如果使用 MCP 或自定义工具，对工具返回内容做白名单或黑名单过滤。例如数据库查询工具只返回行数或脱敏后的字段，不返回完整 schema；文件读取工具默认隐藏 `.env`、`config.yaml` 等敏感文件。

5. **分享前检查清单**  
   在社区发帖或发消息前，执行以下检查：
   - 搜索 `sk-`、`token`、`password`、`secret` 等关键词
   - 检查是否出现内网 IP 段（10.x、172.16-31.x、192.168.x）
   - 确认示例域名都是 `example.com` 或 `your-domain.com`
   - 删除所有真实公司名、项目名、客户名

## 踩坑点

- **直接把 .env 或 config.yaml 粘贴出来**：很多人觉得“只给一段”没关系，但配置文件里的注释可能包含真实路径或负责人邮箱。
- **调试日志未脱敏**：Agent 在排查问题时输出的堆栈、HTTP 请求头、数据库连接字符串，随便一张截图就可能泄露。
- **MCP 工具结果透传**：接入 MCP 后，Agent 调用工具的结果可能未经处理直接返回给用户。比如“帮我查一下最近的工单”，工具返回了完整客户手机号和地址。
- **忽略 Agent 的长期记忆**：如果 Agent 有持久化记忆或上下文缓存，它可能把之前会话中见过的内部信息带到新对话中。
- **社区“内部梗”暴露资产**：比如“我们那台 10.0.0.5 上的服务又崩了”，这种看似随意的话也能被拼出拓扑。

## 可复用建议

- **建立脱敏模板**：在团队内部维护一个 `safe-example` 仓库，包含替换好的配置样例、日志样例，分享时直接从模板复制。
- **配置 pre-commit 或 CI 检查**：对要发布到社区的文档、代码片段做自动扫描，检测密钥格式和内部域名。
- **使用一次性密钥或专用测试环境**：如果必须展示真实运行效果，使用临时 token 和隔离的测试环境，用完即焚。
- **给 Agent 增加“安全护栏”工具**：在 Agent 工具链中加入一个输出过滤器，对最终回复做敏感词拦截或替换。
- **定期审计 Agent 对话记录**：查看 Agent 在社区或内部群里的历史回复，发现泄露立即撤回并修复。

## 总结

安全红线不是为了阻止分享，而是让分享不反噬自己。在 OpenClaw 这样以自动化和插件为核心的社区里，Agent 的自主性让泄露风险从“人失误”扩展到“系统行为”。把敏感信息隔离在环境变量里、把输出边界写进提示词、把检查动作固化成流程，这三件事成本不高，却能避免一次大事故。记住：任何发到公共频道的字节，都可能被永久保存。
