## 背景

接入 MCP / 插件 / 本地工具后，Agent 不再只是聊天，而是能查库、发请求、改文件、执行命令。权限边界开始变成工程问题。常见两种失败：

- 所有操作都问：只读查询也弹确认，自动化流程总被卡住。
- 所有操作都自己干：模型一次判断失误，写操作或发信操作直接生效，没有回滚机会。

## 问题

权限边界不能只靠“系统提示词里写清楚不要乱操作”。提示词只能约束模型意图，不能约束工具实际执行。真正可靠的做法是把权限判断下沉到工具层：每个工具调用先经过风险分级和策略匹配，再决定是自动执行、记录后执行、确认后执行，还是直接阻止。

## 做法/步骤

### 1. 先给工具分级

把 MCP server、插件或本地工具按风险级别分类：

- `read`：只读查询，如 select、查天气、读文件内容
- `create`：新建资源，如创建工单、新建分支
- `update`：修改现有资源，如更新配置、修改文档
- `delete`：删除或不可逆写操作，如删除表、清空对象
- `execute/send`：执行命令、发送消息、触发外部系统

### 2. 定义默认策略矩阵

一个可落地的默认策略：

- `read` -> `auto`：自动执行，但写审计日志
- `create` -> `auto` 或 `log`：通常自动，涉及外部用户时升级为 `confirm`
- `update` -> `confirm`：默认确认，除非目标在 allowlist
- `delete` -> `confirm` + 二次确认：高风险不可逆
- `execute/send` -> `confirm`，且必须展示完整命令/目标/参数

### 3. 把策略放到工具元数据或执行外套

不要在每次 Agent 提示词里重复写策略，而是在工具定义里带上 `risk` 和 `requires_confirmation` 字段。OpenClaw / MCP 客户端可以做一层 tool wrapper：调用工具前读取元数据，命中 `confirm` 就插入审批流；命中 `auto` 就直接执行并记录。

示例元数据：

```json
{
  "name": "db_query",
  "risk": "read",
  "policy": "auto"
}
```

```json
{
  "name": "delete_user",
  "risk": "delete",
  "policy": "confirm",
  "confirm_ttl_sec": 120
}
```

### 4. 设置上下文升级

同一任务里连续触发多个敏感操作，或者 Agent 请求扩大权限范围时，自动提高确认级别。比如前三次只读可以自动，第四次突然要执行 shell，即使命令本身风险中，也应当强制确认。

### 5. 结构化审计

自动执行和人工确认都要落日志：时间、工具、参数摘要、策略命中、结果、会话 ID。便于回放和复盘。不要只记“执行成功”，要记“执行了什么”。

## 踩坑点

- **按 MCP server 整体授权**  
  一个 server 里可能同时有只读接口和写接口。整体 allow 会让危险能力失控，整体 deny 会让只读能力不可用。需要细化到工具级。

- **确认信息不含参数**  
  只提示“是否允许执行命令？”而不展示命令内容和目标，人无法判断。确认应包含：工具名、关键参数、目标对象、影响范围、能否回滚。

- **把 dry-run 当成绝对安全**  
  dry-run 只能验证命令是否可解析，不代表真实执行时不会出问题。涉及权限、网络、外部系统时，dry-run 通过后仍需要确认。

- **同步确认阻塞 Agent**  
  在生产流程里，如果审批人不在，同步等待会超时。应支持异步 approval：Agent 挂起后持久化请求，审批通过后再继续，超时可配置自动拒绝或重新请求。

- **对“可回滚”过度乐观**  
  删除到回收站算可回滚，清空生产数据库表通常不算。需要在工具定义时明确回滚方式，而不是统一叫“可逆”。

## 可复用建议

- 默认最小权限：MCP server 尽量暴露只读或范围受限的工具，不要给通用 shell。
- 强制 policy 元数据：工具注册时没有 `risk/policy` 字段，默认按 `confirm` 处理，不能默认 `auto`。
- allowlist 优先：对高频、低风险、可回滚的写入操作，用 allowlist 规则减少确认；对敏感目标用 denylist 直接阻止。
- 审核周期：定期看审计日志，把误拦截和漏拦转换成规则，而不是只加更多提示词。
- 把“问人类”设计成便宜、快速的过程：确认请求要简短、清晰、可一键批准或拒绝，否则用户会养成盲点通过的习惯。

## 总结

AI Agent 的权限边界不是一次性写死的，而是一条可配置、可审计、会随上下文升级的控制链路。适合问人类的操作，通常是高影响、不可逆、或目标不明确的；适合自己干的，是低风险、可回滚、且有日志兜底的。真正工程化的做法，是把这些判断从提示词里拿出来，放进工具层和审批流里。
