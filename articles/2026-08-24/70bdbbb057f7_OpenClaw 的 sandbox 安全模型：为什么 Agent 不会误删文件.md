## 背景：Agent 的文件操作不再是“建议”

在 OpenClaw 的自动化场景里，Agent 通过 File、Command 或 MCP 工具直接操作本地目录越来越常见。一个典型任务是“清理 workspace 下超过 7 天的日志”。如果 Agent 对路径判断错误，`rm -rf` 可能落到真实项目目录。过去在聊天工具里这只是一句建议，在 OpenClaw 里它是可执行动作，因此必须把 Agent 当作一个受控系统来对待。

## 问题：不能不用文件工具，但也不能直接信任

多数误删不是模型“有恶意”，而是路径拼接、相对路径、符号链接或隐藏文件导致。直接禁用删除工具会让很多自动化任务无法完成；完全不限制，等于把宿主目录交给一个会犯错的程序。OpenClaw 的 sandbox 模型解决的是中间问题：允许 Agent 操作文件，但不让它直接接触真实文件系统里的关键区域。

## 做法：默认拒绝 + 白名单可写 + 写时复制

OpenClaw 的 sandbox 通常不是单一“删不掉”，而是四层约束。

1. **默认只读**：Agent 启动时，整个文件系统对它是只读的。读取配置、查看日志可以，但不能写入。
2. **可写白名单**：只有显式声明的目录可写，例如 `workspace/`、`tmp/`。需要清理的目录必须出现在白名单里。
3. **路径规范化与边界检查**：所有文件工具在执行前，把 `..`、符号链接、`~`、环境变量展开成绝对路径，然后判断是否仍在允许目录内。任何试图跳出白名单的路径直接拒绝。
4. **写时复制 / 事务层**：写入先落到临时层或 overlay 里，任务结束确认后才合并到真实目录。删除操作在未提交前只是标记，不真正删除物理文件。

一个简化配置示意：

```yaml
sandbox:
  mode: strict
  filesystem:
    read_only: true
    writable_paths:
      - ./workspace
      - /tmp/openclaw-agent
    deny_paths:
      - ~/.ssh
      - ~/.aws
      - ~/Documents
  commands:
    allow_delete: false
    delete_strategy: trash
```

在这个配置下，Agent 执行 `rm -rf ./workspace/old_logs` 只会影响 `workspace` 下的内容，且默认进入回收站。若它尝试删除 `~/Documents`，沙箱会在路径检查阶段拒绝，而不是依赖模型自觉。

## 一个可复现的排障路径

如果你担心 Agent 误删，可以按这个顺序验证：

1. 在配置中把 `read_only` 设为 `true`，只给一个测试目录可写。
2. 在测试目录外放一个“金丝雀文件”，例如 `~/canary.txt`。
3. 让 Agent 执行删除指令，观察是否被拒绝。
4. 再在测试目录内放一个文件，让 Agent 删除，观察是否进入回收站或 overlay 层。
5. 检查任务日志中的路径解析结果，确认没有出现 `..` 或符号链接逃逸。

## 踩坑点

- **符号链接**：白名单目录里如果有软链指向外部，单纯字符串前缀检查会被绕过。必须解析真实路径后再判断。
- **相对路径拼接**：Agent 生成 `../../etc/xxx` 时，如果工具直接拼到基础目录，可能越界。要先 normalize 再检查。
- **写时复制没有落盘**：有用户以为删除已生效，实际只在临时层，任务失败回滚后文件又出现了。需要明确“提交”时机。
- **白名单过宽**：把 `~` 或 `/` 设为可写等于没有沙箱。建议最小化到具体子目录。
- **隐藏文件与大小写路径**：macOS/Windows 的大小写不敏感路径容易被忽略，跨平台时要统一处理。

## 可复用建议

- 永远为 Agent 分配独立工作目录，不要直接指向真实项目根目录。
- 对文件工具做统一封装：所有读写都经过一个 `FileAccess` 入口做 normalize 和权限判断，不要散落各插件。
- 删除操作默认走回收站或改名 `.trash/`，保留 7 天。
- 对破坏性命令使用二次确认或白名单参数，例如只允许 `rm` 作用于明确路径参数。
- 保留 sandbox 决策日志，尤其在自动化任务中，定期审计“被拒绝的路径”列表，能提前发现坏路径模式。

## 总结

OpenClaw 的 sandbox 安全模型不是让 Agent 变得不会犯错，而是让它的错误没有机会作用到真实文件上。默认拒绝、白名单可写、路径规范化和写时复制，这四件事组合起来，才是“不会误删”的真正原因。对工程实践来说，比“模型更聪明”可靠得多的是把权限边界放在代码层，而不是放在提示词里。
