## 背景

在 OpenClaw / Agent / MCP 的自动化场景里，单个 Agent 经常被要求完成一条长链路：查数据、读配置、调 MCP、写文件、再汇总。串行执行不仅慢，而且上下文越长，后半段质量越容易下降。于是自然想到：能不能把任务拆给多个 subagent 并行处理？

能，但前提是把调度和控制做好。否则并行带来的排障成本，会远高于提速收益。

## 问题

Subagent 编排不是简单的“多开几个 AI”。真正需要解决的是四件事：

1. 哪些任务可以并行，哪些必须串行；
2. 每个 subagent 的上下文如何隔离，避免互相污染；
3. 结果如何校验和聚合；
4. 失败、超时、资源冲突如何定位。

这些问题不解决，并行只会把原来的慢变成更乱的慢。

## 做法 / 步骤

### 1. 只拆无依赖的叶子任务

不是所有步骤都适合并行。比如“拉取 A 数据”“读取 B 配置”“检查 C 日志”是独立的，可以并行；而“先构建再测试”有强依赖，不能拆。拆之前先问一句：如果这个步骤失败，其他步骤是否还能继续？能继续，才适合并行。

### 2. 给每个 subagent 定义契约

每个 subagent 的 system prompt 要短，但必须固定四件事：

- 输入变量：只传必要字段，不要塞整个主 Agent 历史；
- 输出格式：固定 JSON schema，例如 `{"status":"ok","summary":"...","risk":"low|medium|high"}`；
- 允许工具：默认只读，写操作由主 Agent 或专用工具统一执行；
- 超时与失败返回：规定无法完成时必须返回结构化错误，不要自由发挥。

### 3. 主 Agent 只做调度与校验

主 Agent 不替 subagent 干细活，只负责：拆包、派发、收集结果、校验 schema、必要时重试一次。这样主 Agent 的上下文不会膨胀，职责也清晰。

### 4. 控制并发

不要一上来开 10 个并发。默认 2-4 个 worker 足够。每个任务带超时，超时返回结构化错误，而不是让主 Agent 一直等。MCP server 如果本身不支持并发，还要用队列串行化请求。

### 5. 结果落盘与聚合

每个 subagent 写入自己的输出目录，例如 `artifacts/{agent_id}/`，最后由主 Agent 统一合并。避免多个 subagent 同时写同一文件。聚合时先检查每个返回的 `status` 和 schema，失败任务按策略降级：跳过、重试或转人工。

## 踩坑点

**上下文复制过多**  
不要把所有主 Agent 历史塞给 subagent。只传当前任务需要的字段。常见错误是把整段对话作为 subagent 输入，导致 token 暴涨、输出漂移。

**工具权限过大**  
Subagent 误删/改文件是最常见事故。默认只读工具或白名单，写操作集中到主 Agent 或专用工具。

**资源写冲突**  
多个 subagent 同时写同一路径或数据库，轻则覆盖，重则损坏状态。拆分时就要保证输出路径隔离。

**模型输出不稳定**  
JSON 格式不对、字段缺失。解决方式：schema 校验 + 一次 retry，并在 prompt 中明确失败返回格式。

**伪并行**  
有些任务底层共享同一 MCP 连接或配额，并行反而限流。需要确认 MCP server 的并发能力。

**成本失控**  
并行任务各自携带 system prompt 和工具描述，固定成本叠加。建议先评估单个任务 token，再决定是否值得并行。

## 可复用建议

- 先串行跑通 3 个案例，再改成并行；不要直接上编排。
- Subagent 的 prompt 保持在 300-500 字，超过说明职责不纯。
- 所有 subagent 返回统一信封：`status / data / error / meta`，主 Agent 只依赖这个信封。
- 为每次运行记录 manifest：`run_id`、`agent_id`、起止时间、模型、token、状态、输出路径。没有这个，排障基本靠猜。
- 设置全局预算和熔断：单次总 token 超限或失败率超过 30%，停止新任务，返回部分结果。
- 关键写操作前设置人审点，比如发布、发消息、合并文件，避免多 Agent 同时做不可逆操作。

## 总结

Subagent 并行不是让多个 AI 随便跑，而是把主 Agent 变成一个小型调度器：定义清晰任务、隔离上下文、限制权限、校验结果。做好契约、并发控制和日志，并行才能稳定复用；否则不如老老实实串行。
