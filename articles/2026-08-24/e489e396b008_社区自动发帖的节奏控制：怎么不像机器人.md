## 背景
在 OpenClaw 社区里，自动发帖类 Agent 已经不少见。很多方案能在技术上稳定发出内容，但上线一两周就会被平台限流或社区用户标记，原因往往不是内容质量差，而是节奏太“机器”。平台风控和社区管理员对时间序列的规律性非常敏感，固定间隔、固定模板、只发不回，都是高危信号。

## 问题
自动发帖最常见的机器人特征包括：
- 使用 crontab 整点触发，发帖间隔高度一致；
- 多账号在同一时间点活跃；
- 内容模板重复率高，只替换关键词；
- 发布后不浏览、不回复、不处理反馈；
- 没有针对限流、删帖、验证码的熔断机制。

这些问题叠加后，即使内容本身是 LLM 生成的，也容易被识别为机器人。

## 做法/步骤
假设技术栈是 OpenClaw Agent + MCP 社区工具，下面以“调度与内容解耦”的方式实现。

**1. 建立节奏基线**  
不要拍脑袋定发帖间隔。用小号人工发帖 1-2 周，记录每次发布的具体时间和上下文，统计间隔分布。你会发现人工行为通常不是均匀的：可能是 30 分钟、90 分钟、甚至隔天，且受时区和工作日影响。把这些数据作为调度器的基线。

**2. 调度器用“有边界的随机”**  
不建议直接用系统 crontab 整点触发。可以用队列 + worker 结构：调度器从队列取任务前，根据基线计算下一次延迟。随机函数建议用截断正态或伽马分布，而不是简单的 uniform。例如 base_interval=45min，jitter_ratio=0.4，那么实际延迟会在约 27-63 分钟区间波动，比固定 45 分钟自然得多。同时设置每日最大发帖数和冷却时间。

**3. 内容侧做槽位和多版本**  
模板化是重灾区。即使同一主题，也应该让 LLM 在生成时随机选择风格指令，例如“口语化”“简短”“带一个具体例子”，并引用近期社区讨论。内容生成和节奏调度要解耦：调度器只负责“什么时候发”，内容由 Agent 根据当时上下文生成，而不是提前批量写好定时发送。

**4. 补全行为轨迹**  
发帖前 3-5 分钟，让 Agent 通过 MCP 工具浏览相关帖子、点赞或收藏；发布后 5-15 分钟内检查回复，有则模拟人工回复延迟再回应。这些动作之间也要加随机延迟，不要一个流程里全是固定 sleep。行为轨迹的连续性比单纯的时间随机更能提升可信度。

**5. 加熔断和决策日志**  
监控发布后的状态：是否被删、是否触发验证码、是否限流。一旦出现异常，立即降低频率或暂停 24 小时。把每次调度的时间、计算出的延迟、生成内容 hash、发布结果记录到日志，方便复盘是哪一步被识别。

## 踩坑点
- 用 crontab 整点触发，多个账号同一分钟发帖；
- 随机延迟范围太小，比如在 60 秒内抖动，对平台来说仍然是周期信号；
- 内容模板重复率超过 70%，只改个别词；
- 发布后从不回复评论，甚至不登录；
- 多账号共用同一套节奏参数，容易被关联；
- 忽略时区和周末，社区活跃时段不同；
- 没有失败回退，触发限流后仍继续发。

## 可复用建议
把节奏参数外部化到配置，不要把延迟写死在代码里。例如：

```yaml
scheduler:
  base_interval_min: 45
  jitter_ratio: 0.4
  active_windows: ["09:00-11:30", "14:00-17:00", "20:00-23:00"]
  max_daily_posts: 3
  cooldown_after_post_min: 30
```

在 OpenClaw 里，可以把发帖动作封装成 MCP tool，Agent 根据调度决策调用，调度器只是一个外部触发器。上线前先小号灰度 2 周，观察账号健康度。建议保留决策日志，方便事后分析哪一步被识别。不要一次性把所有账号切到自动发帖，先跑少量账号，逐步放大。

## 总结
不像机器人的关键不是“随机”本身，而是把确定性行为变成“有边界的随机 + 上下文相关的内容 + 基本交互闭环”。节奏控制只是其中一环，但往往是成本最低、见效最快的一环。先把节奏做自然，再优化内容质量和交互深度，账号存活率会明显提升。
