最近，Rabbit 提出并上线了一个被称为“所有 Agents 的 Agent”的新方向。很多人第一反应是“又一个套壳产品”，但实际体验后，我发现它真正解决的并不是模型能力不够，而是 Agent 之间长期缺少一个调度层。它没有把每个 Agent 做得更强，而是让一堆普通 Agent 第一次像团队一样工作。这件事如果继续演进，可能会改变我们对 Agent 产品形态的预期。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-24/d00619d40e8a9c9d.png)

## 一、现有 Agent 为什么像“孤岛型实习生”
![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-24/d9c7f9ea2e378a14.png)

过去两年，AI Agent 数量增长很快，但大多数产品都停留在一个尴尬阶段：

- 单个任务还行：写文案、查资料、生成图片、整理表格，这些已经很常见。
- 跨任务协作很弱：一个 Agent 的输出，往往只是聊天框里的一段自然语言，另一个 Agent 没法直接消费。
- 上下文经常断裂：用户需要在不同工具之间复制、粘贴、重写 prompt，甚至重新说明背景。
- 状态不共享：写报告 Agent 不知道搜索 Agent 已经查过哪些来源，也不知道图表 Agent 需要什么字段。

举一个典型例子：让 Agent 做一份竞品分析，你可能要开三个窗口。先用搜索 Agent 查信息，再把结果喂给 PDF 解析器读报告，最后把要点复制到生成图表的 Agent。你在中间扮演的不是管理者，而是“人肉 API”。Agent 越多，手工活反而越多。

从工程角度看，原因并不是模型不够聪明，而是缺少三样东西：统一的任务描述、结构化的结果回传、可靠的状态管理。自然语言适合表达意图，但不太适合作为系统之间的交接格式。这也解释了为什么很多“多 Agent 框架”听起来强大，一落地就翻车：它们可以生成很多节点，但节点之间的数据流仍然靠文本硬凑。

## 二、Rabbit 这次做的“总调度”到底是什么
![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-24/38a4a5368001c4ef.png)

Rabbit 这次的方向，不是重新训练一个更大的模型，而是在多个 Agent 之上增加一个“元 Agent”或“调度层”。你可以把它理解为 Agent 世界的操作系统：用户不需要直接指挥每个工具，只需要把目标交给调度层。

它主要做三件事：

1. 拆解：把一个复杂目标转成可执行的任务图。比如“搜集三家云厂商最近三个月的 AI 动态，整理成表格，并邮件摘要发给我”，会被拆成搜索、解析、制表、写作、发送等步骤。
2. 路由：根据每个子任务的特点，调用最合适的底层 Agent。搜索类调用联网 Agent，文档类调用解析 Agent，结构化输出调用代码执行或表格 Agent。
3. 回收：把每个节点的输出统一成结构化结果，再注入下一个节点，而不是让自然语言在流程中裸奔。

这个概念并不新。AutoGPT、LangGraph、OpenAI Swarm 等都在做编排，Anthropic 的 Model Context Protocol 也在解决工具接入标准化。Rabbit 的差别在于，它把早期 Large Action Model（LAM）积累的“操作能力”和“用户入口”放进了一个更完整的产品闭环里：以前 LAM 强调代替人操作界面，现在它把“操作”扩展成了“调用其他 Agent”。

换句话说，Rabbit 想做的不是某个更强的 Agent，而是所有 Agent 的调度入口。这也是“Agent-of-Agents”这个名字最直白的含义。

## 三、体验中最让我觉得“早该这样”的几个细节
![img3](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-24/5daf7d4481ab1054.png)

体验之后，我最大的感受不是模型输出质量突然飞跃，而是很多过去被忽略的工程细节被补上了。

- 跨 Agent 上下文自动接力。调度层维护一个共享上下文，上一个节点的结构化输出会直接变成下一个节点的输入。用户不用再复制一堆中间结果。
- 失败会重路由，而不是直接报错。一次搜索超时后，调度器自动换了数据源，并把任务拆成更小的查询重新执行。这种容错在传统工作流引擎里很常见，但在 Agent 产品里反而少见。
- 用户不再需要知道有哪些 Agent。以前用 Agent 产品很像自己选插件、配参数；现在更像给一个项目经理派活。目标只要说清楚，调度层负责找工具、排顺序。
- 执行过程可回溯。每一步调用哪个 Agent、输入输出摘要、耗时多少，都按时间线展示。出现问题时，至少能知道是哪一环出了问题，而不是面对一个黑盒。

举一个实际任务：让它整理五家云厂商最近三个月 AI 产品公开动向，做对比表，并生成邮件摘要。过去我至少要在搜索、文档解析、表格生成和写作四个产品之间切换；现在一个入口，三分钟左右完成，中间能看见四个 Agent 被依次调度。效率提升未必夸张，但心智负担明显下降。

## 四、技术关键与边界：调度不是魔法，但也不该被神化
![img4](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-24/c28de2c09e3c042d.png)

总调度能跑起来，靠的不是单一模型突然变强，而是一组软件工程能力被重新组织。

- Planner：负责生成任务计划和依赖关系，通常由大模型充当，但不负责具体执行。
- Registry：底层 Agent 需要在注册表里声明能力、输入输出 schema、成本和超时。没有这层，调度器就无法可靠路由。
- 通信协议：结构化输出是关键。很多 Agent 协作失败，不是模型笨，而是自然语言交接太不可靠。JSON Schema、工具调用协议、甚至 MCP 这类标准化接口，都在补齐这一层。
- Memory 与状态：短期任务状态和长期用户偏好要分开存，才能避免上下文无限膨胀。
- Executor：支持串行、并行、条件分支、重试、熔断。这些能力来自工作流引擎，却被很多 Agent 产品忽视。

但也要保持冷思考。能调度不等于能理解，流程化不等于自动化质量高。如果底层 Agent 本身能力很弱，调度层只是把错误编排得更快。安全边界、权限控制、敏感操作二次确认，仍然是这类产品最容易出问题的地方。

基于目前体验，留三条实用建议：

1. 把总调度用在“目标清晰、步骤可拆”的任务上，比如信息收集、报告生成、流程化写作；不要一上来就押注开放性创意任务。
2. 优先选择能暴露执行链路的调度产品。如果看不到中间节点、不能回滚、不能检查每一步输入输出，出错成本会很高。
3. 对涉及付费、发送、删除、发布等不可逆操作，务必设置人工确认。Agent 越自动，权限边界越要提前设计。
