## 背景

OpenClaw 里越来越多任务不是“聊天”，而是 Agent 规划、MCP 工具调用、插件自动化和长流程任务。这种情况下，模型选择不再只是效果好不好的问题，而是成本、延迟、稳定性、隐私和结构化输出能力之间的权衡。云端模型如 GPT 系列在复杂推理、工具调用和长上下文上更强，但每条请求都有成本，且不适合直接处理敏感数据；本地模型便宜、低延迟、数据不出域，但在多步工具调用和严格 JSON 输出上容易翻车。因此需要一套可维护的多模型路由策略，而不是全局一刀切。

## 问题

真正要解决的问题不是“哪个模型更好”，而是“这类任务应该优先走哪条路径”。常见失败有两种：一种是所有请求都走云端，结果 MCP 日志压缩、意图分类、简单摘要等高频低难度任务堆高了延迟和成本；另一种是盲目把 Agent 规划也塞给本地模型，工具调用格式错误、漏调用、输出截断，最后人工排查成本更高。路由的核心是把不确定性高、结构要求强、上下文长的任务交给云端，把高频、机械、低延迟或敏感任务留在本地。

## 做法/步骤

先把 OpenClaw 里的模型调用抽象成一个 router 层，不要让业务逻辑直接绑定某个 provider。可以按下面几类规则逐步落地。

1. **建立任务分类**：把现有请求分成四类：  
   - A 类：分类、摘要、抽取、日志压缩、简单改写；  
   - B 类：需要工具调用的 Agent 任务；  
   - C 类：多步规划、跨文档比较、复杂代码生成；  
   - D 类：敏感数据清洗、本地结构化预处理。

2. **默认白名单路由**：A 类和 D 类优先走本地模型；B 类和 C 类默认走云端。不要一上来写复杂打分模型，先让规则可解释。

3. **设置阈值**：例如输入 token 小于 2000、无工具调用、温度低、只要求 JSON 抽取时可以走本地。可以用类似配置：

```yaml
router:
  rules:
    - name: local_first
      conditions:
        task_type: [classification, summarization, extraction]
        max_input_tokens: 2000
        tools: 0
      provider: local
    - name: cloud_reasoning
      conditions:
        tools: ">0"
        or:
          - requires_json: true
          - expected_steps: ">3"
      provider: cloud
```

4. **双向 fallback**：本地解析失败、超时或格式错误时自动升级云端重试；云端限流、超时或输出截断时降级本地，但要在响应里标记降级，避免误判能力。

5. **固定本地模型参数**：temperature 设低，启用 guided decoding 或 JSON grammar；MCP 工具返回长 JSON 时，先让本地模型做一次压缩再交给云端规划，能明显降低成本。

## 踩坑点

- **工具调用不能只看模型大小**：一些中小模型在特定任务上够用，但通用 function calling 不稳定。只要任务里出现 MCP 工具选择或参数填充，建议默认云端，除非你已经有完整回归用例。
- **路由规则本身会成为故障点**：条件太复杂时，排障会非常痛苦。建议先做白名单，再逐步加规则，并给每条规则加命中日志。
- **本地模型对 prompt 风格很敏感**：同样的 JSON 指令，在云端能稳定返回，在本地可能因为多一个换行或少一个示例就失败。需要单独维护本地 prompt 模板。
- **不要忽视日志脱敏**：即使用本地模型处理敏感数据，OpenClaw 日志里可能仍会记录 prompt 或工具返回。要检查日志级别和脱敏策略。
- **同对话上下文频繁切换模型**：会导致前后风格和状态不一致，尽量在一个会话或任务阶段内保持模型稳定。

## 可复用建议

- 给每一次路由决策记录 `provider`、`reason`、`latency_ms`、`fallback` 和 `error_type`，便于回查。
- 建一个 20 条左右的小型 eval 集，覆盖分类、摘要、工具调用、复杂规划四类，每次换模型或调路由都跑一遍。
- 云端优先级可配置，不要写死某一家；OpenClaw 里用 provider 抽象来切换。
- 对高频任务做缓存：相同或相似输入的摘要、分类结果可以缓存，减少不必要的模型调用。
- 最终答案前加一道轻量检查：如果本地模型输出格式错误、漏字段或置信度低，再升级云端，不要直接返回坏结果。

## 总结

OpenClaw 的多模型路由不是“本地不够用才上云”，而是把不同任务特征匹配到合适的执行路径：云端负责复杂推理、工具调用和长上下文，本地负责高频、敏感、低延迟和机械性工作。先做任务清单和小型评估，再上白名单路由，配合双向 fallback 和可观测日志，比一开始就搞复杂调度更实际。工程上最稳的路线通常是：简单任务本地优先，复杂任务云端兜底，所有失败都有记录并可回放。
