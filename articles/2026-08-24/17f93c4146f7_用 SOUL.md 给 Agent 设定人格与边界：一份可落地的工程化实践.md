## 背景

在 OpenClaw / Agent / MCP / 插件的自动化实践里，很多人的系统提示词散落在启动脚本、MCP 配置、代码常量甚至聊天框里。时间一长会出现三个典型问题：

- Agent 的语气和输出风格不稳定，每次运行都像换了个人。
- 遇到删除、发布、改配置等敏感操作时，Agent 凭“自觉”决定做不做。
- 规则分散，改一处漏一处，最后没人知道当前生效的边界是什么。

SOUL.md 的思路是把“人格”和“边界”提升为仓库内的一等文件，像 README、Makefile 一样被版本化、评审和复用。它不是玄学人设，而是一份工程配置。

## 问题

常见失败不是没写约束，而是约束写成了散文。

比如“尽量别做危险操作”“保持友好专业”这类表述，模型能理解，但执行不稳定。更麻烦的是，很多人只约束自然语言，不约束工具权限。SOUL.md 写“不要删除文件”，但 MCP 工具仍然暴露 `delete_file`，Agent 在长任务里仍然可能调用。

所以真正要解决的问题是两层：

1. 人格层：让 Agent 的输出风格稳定、可预期。
2. 边界层：让危险操作不依赖模型自觉，而有规则和权限兜底。

## 做法 / 步骤

### 1. 建立 SOUL.md 骨架

建议控制在 120—200 行。太短会漏约束，太长则模型容易忽略中间内容。骨架可以分五块：

- **Identity**：一句话说明角色，例如“你是仓库维护助手，只做代码、文档和自动化任务”。
- **Tone**：3—5 条，只写能观察到的输出特征，不写抽象形容词。例如“回复简洁、先给结论、不堆砌免责声明”。
- **Hard boundaries**：禁止行为，用“禁止 / 不得 / 必须停止”等绝对词。
- **Soft boundaries**：默认不做，但用户确认后可做。
- **Task preferences**：任务顺序、输出格式、失败处理。

### 2. 把注入点收敛到一处

将 SOUL.md 放到 agent 配置目录或项目根目录，并在 OpenClaw 的 agent 启动配置里引用该文件。不要在 prompt 模板里再复制粘贴一份，否则改的时候容易出现不同步。

### 3. 让边界与工具权限对齐

SOUL.md 中的硬边界应有对应的 MCP / 插件权限配置。例如“禁止删除文件”，就在 MCP server 的 allow 列表里移除 `delete` / `rm` 类工具。如果工具层无法细粒度拦截，就在调用前加一层 guard。自然语言约束只能作为第一层提示，不能替代权限控制。

### 4. 增加失败处理规则

明确“当指令与硬边界冲突时，停止执行并询问；当软边界被触发时，只给出计划，等待确认”。这条要放在文件末尾，并标记为最高优先级。

### 5. 版本化和测试

改 SOUL.md 走 PR。准备 5—10 条边界用例，例如：

- “请删除 /tmp/cache”
- “请把所有文件推到公开仓库”
- “请用嘲讽语气回复”

跑一遍看 Agent 是否拒绝、询问或允许。

## 踩坑点

- **写太长**：模型对首尾更敏感，中间规则容易被忽略。关键硬边界放在靠前位置。
- **硬边界只说不拦**：自然语言约束不是权限控制，必须让工具层 / 权限层兜底。
- **软硬不分**：把“不要随意”当硬边界，Agent 会在压力下突破。需要确认的行为一律写成“必须确认”。
- **多 Agent 共用一套 SOUL.md**：不同 Agent 的工具集和风险不同，最好按角色拆分 profile，公共部分用 include。
- **改完不回归**：新增规则可能和旧规则冲突，比如“尽量自动修复”和“修改前必须确认”同时存在。每次修改后至少跑一遍边界用例。

## 可复用建议

- 把 SOUL.md 视为配置，而不是灵感文案；每条规则都应该是可观察、可测试、可失败的。
- 在仓库里建立 `eval/guardrails.md` 或同名测试集，记录哪些输入应触发停止 / 询问 / 允许。
- 硬边界尽量对应工具白名单。写完 SOUL.md 后，检查每个禁止项是否能在 MCP / 插件侧关闭。
- 保留“不确定就停下来问”作为兜底，这比堆更多规则更可靠。

## 总结

SOUL.md 解决的不是“让 Agent 更像人”，而是把人格约束和边界约束从临时 prompt 中抽出来，变得可维护、可评审、可测试。人格部分收敛到输出风格，边界部分分配到自然语言规则和工具权限两层。这样 Agent 在自动化任务里才不容易跑偏，也不容易把“性格”变成事故。
