# OpenClaw 多模型路由：什么时候用 GPT，什么时候用本地模型

## 背景
在 OpenClaw 里跑 Agent / MCP / 插件自动化时，模型选择很容易走两个极端：要么所有任务都走 GPT 系列云模型，月底成本难看；要么强行上本地模型，遇到复杂推理或工具调用频繁翻车。多模型路由不是新概念，但在 OpenClaw 这种强调工具调用和自动化编排的场景里，它更像“工程分诊”：先判断任务属性，再分派到合适模型。

## 问题
真正需要回答的不是“GPT 和本地模型谁更好”，而是：

- 哪些任务必须用 GPT：长上下文、复杂推理、多步规划、自然语言生成质量要求高。
- 哪些任务可以交给本地模型：高频结构化抽取、分类、简单问答、隐私敏感、离线/低延迟要求。
- 哪些任务可以先用本地模型做预处理，再由 GPT 做最终生成。

如果不做路由，典型后果是：简单意图识别也走 GPT-4 级别模型，单条成本高但价值极低；或者让 7B 本地模型去选 MCP 工具、填复杂 schema，错误率升高，重试次数增加，实际成本并不低。

## 做法 / 步骤
实践上我会把 OpenClaw 的模型路由拆成四层。

**1. 任务分层**

先按复杂度分成 L1/L2/L3：

- L1：关键词分类、实体抽取、格式转换、简单问答、情绪判断。适合本地小模型，如 Qwen2.5-7B-Instruct、Llama-3.1-8B。
- L2：摘要、语义搜索、工具选择、参数抽取、简单代码生成。适合本地中型模型或 GPT-4o-mini。
- L3：长文档分析、复杂排错、多步 Agent 规划、复杂 MCP 工具链调用。优先 GPT 系列。

**2. 配置多 provider**

不要默认模型写死。在模型网关配置里同时挂云端和本地 provider，例如：

- cloud：gpt-4.1、gpt-4o-mini
- local：qwen2.5-7b-instruct、qwen2.5-32b-instruct，通过 Ollama/vLLM 暴露 OpenAI 兼容接口

**3. 路由层**

Agent 入口前加一层轻量 Router。先跑一个本地小模型做意图分类，输出 `task_type`、`is_sensitive`、`expected_steps`，再查路由表。隐私敏感的 L1 任务强制走本地；公开的 L3 任务直接走 GPT。分类 prompt 控制在 200 token 左右，否则路由开销会吃掉本地模型优势。

**4. 降级与缓存**

本地模型超时、输出 JSON 不合法、工具调用连续失败时，自动降级到 GPT-4o-mini 兜底。对高频、确定性强的任务，例如日志解析、状态码归类，先查本地缓存，命中后不再走模型。

## 踩坑点

- **本地模型工具调用不稳定**。不是所有本地模型都对 function calling 兼容得好，最好用明确支持工具调用的版本，并在 prompt 里给出严格 JSON 输出示例。
- **别拿小模型做多步规划**。7B/8B 模型做单步工具选择尚可，但涉及多工具依赖、条件分支时容易漏步骤或幻觉工具名。失败重试的成本可能比直接上 GPT 还高。
- **超时设置不区分**。本地模型高并发下吞吐会明显下降，路由层要设置更短的 P95 超时，超时立即降级，避免阻塞整个 Agent 流程。
- **隐私不是“不能上云”这一条**。长文档且隐私敏感，本地模型上下文不够时，可以本地先分块脱敏，只将必要摘要或实体上云，而不是把全文直接丢给 GPT。
- **JSON 解析失败要兜底**。本地模型输出 JSON 容易多逗号、少引号，必须做 schema 校验；校验失败限时重试一次，再失败走云端。

## 可复用建议

1. 路由表显式化：每类任务对应 `provider/model/timeout/retry/fallback`，不要散落在插件代码里。
2. 先用规则挡一层：能用关键词、正则、MCP 工具请求名判断的任务，不必每次都让模型分类。
3. 看真实指标：记录每条路由的 P50/P95 延迟、token 成本、工具调用错误率、重试率，定期调整阈值。
4. 本地优先并非永远正确。短输入、低频、需要强推理的任务，GPT-4o-mini 的综合成本可能低于维护本地模型的显存占用和失败重试。
5. 工具调用优先用“本地中型模型试一次 + GPT 兜底”，而不是默认全走云端。

## 总结
OpenClaw 的多模型路由本质是把模型当资源，而不是把模型当默认答案。GPT 系列适合复杂推理、长上下文、高难度工具调用和最终生成；本地模型适合高频结构化、隐私敏感、低延迟和离线任务。真正稳定的是路由层和降级策略，而不是某个单一模型。做得不好，路由本身反而会成为新的故障点。
