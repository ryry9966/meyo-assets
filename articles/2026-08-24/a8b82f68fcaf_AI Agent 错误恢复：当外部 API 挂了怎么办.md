## 背景

在 OpenClaw 里，Agent 很少直接靠模型记忆回答问题，更多是通过工具、插件或 MCP server 访问外部系统：查订单、发消息、读文档、调模型。外部 API 一旦抖动或挂掉，Agent 很容易出现两类问题：一是把失败当事实，把异常文本写进最终回复；二是反复重试同一个工具，烧掉大量 token 和时间。外部依赖故障不是“代码 bug”，而是日常运维的一部分，需要提前设计恢复路径。

## 问题定义

外部 API 挂掉通常表现为超时、5xx、限流、连接拒绝、返回体异常、MCP server 进程退出或工具列表变化。对 Agent 来说，最危险的不是失败本身，而是失败信息没有结构化。原始 traceback 进入上下文后，模型可能误判为参数错误、任务不可完成，或者继续尝试奇怪的重试。另一个问题是缺少熔断，一个慢接口可以把整个任务拖到超时。

## 做法 / 步骤

1. **错误分级，只对可恢复错误重试。** 把外部调用结果分成四类：参数错误（4xx，不可重试）、限流（429，可退避重试）、服务端错误（5xx/超时，可重试）、依赖不可用（连接拒绝/MCP 掉线，需降级或快速失败）。不要一刀切。

2. **给外部调用加统一包装。** 在 OpenClaw 的工具执行层或插件 adapter 里加超时、重试、熔断。建议超时 5–10 秒；重试使用指数退避加抖动，例如 1s、2s、4s，最多 3 次；熔断器连续失败 5 次打开，冷却 30 秒后放一个探测请求。

3. **让工具返回结构化错误。** 工具返回给 Agent 的应该是 `{ok: false, error_code: "rate_limited", retryable: true, fallback_hint: "稍后重试或使用缓存"}`，而不是把异常堆栈原样塞给模型。模型拿到结构化信息后，可以选择等待、换参数、走降级路径。

4. **读降级、写排队。** 读接口可以回退到最近成功缓存，并标注 `stale=true`；写接口不能简单丢弃，应写入本地队列或待处理表，等依赖恢复后再补做。否则用户会看到“已发送”但实际没有发出去。

5. **MCP 专项处理。** MCP server 可能进程崩溃、版本不兼容、工具列表发生变化。客户端要做健康检查、自动重启、工具调用失败后重新列出工具；如果某个 MCP 工具连续失败，暂时摘除或标记不可用，避免 Agent 反复调用。

6. **可观测与告警。** 每次外部调用记录延迟、状态码、重试次数、熔断状态、是否走了缓存。给熔断打开、MCP 掉线、队列积压设告警。没有观测的错误恢复等于盲飞。

## 踩坑点

- **不要无限重试。** Agent 会把重试当作任务步骤，不仅烧 token，还可能触发上游限流。必须限制总重试次数和任务级时间预算。
- **写操作要有幂等键。** 外部 API 可能在超时前已执行成功，只是响应丢失。重试前用幂等键去重，否则会重复下单或重复发消息。
- **降级不能静默。** 返回缓存/默认值时，必须告诉 Agent 数据已经过期。否则模型会把旧数据当成实时事实继续推理。
- **熔断恢复别太快。** 依赖刚恢复时可能仍不稳定，熔断器要半开探测，逐步放量，避免刚恢复又被打挂。
- **MCP 工具列表可能缓存。** 如果 MCP server 重启后工具签名变了，而客户端仍用旧列表，会持续失败。工具调用失败时先重新协商能力，而不是继续重试同一工具。

## 可复用建议

- 在 OpenClaw 插件/工具层封装一个 `externalCall` 代理，统一处理超时、重试、熔断、降级和日志。
- 为所有外部工具定义错误契约：`{ok, error_code, retryable, data, fallback_hint}`。
- 给 Agent 设置工具调用预算和总超时，避免一个依赖拖垮整个任务。
- 任务开始前做健康预检：检查关键 API/MCP 是否在线，快速失败优于长时间悬挂。
- 定期做故障注入：手动把某个 API 超时或返回 503，验证降级和恢复路径是否成立。

## 总结

外部 API 挂了不是异常情况，而是系统常态。Agent 工程的关键不是避免失败，而是让失败有边界：错误可分类、重试有上限、降级有标注、写操作可恢复、MCP 连接可自愈。把这些做成工具层默认能力，比在 prompt 里“让模型自己看着办”可靠得多。
