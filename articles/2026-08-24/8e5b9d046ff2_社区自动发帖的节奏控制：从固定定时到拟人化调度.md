## 背景

在 OpenClaw 社区的自动化实践里，很多团队用 Agent、MCP server 或插件接入 Discourse/论坛 API，定时发布更新摘要、知识卡片、巡检报告等内容。初衷是保持信息稳定输出，但上线一段时间后，往往出现两种结果：要么被社区成员一眼识别为机器人，要么触发平台的限流或风控。

常见现象包括：每天固定在 10:00:00 整点发帖，误差不超过一秒；帖子标题永远是“【每日一帖】xxx”；正文结构完全一致，只替换日期；发布后从不回复讨论；多个任务并发时甚至同一秒发出多条主题。

这些问题的本质不是“自动发帖”本身，而是节奏和行为模式太像定时任务，缺少人类贡献者的随机性、节律感和交互意识。

## 问题

自动发帖的机器人感主要来自四个特征：

1. **时间固定**：整点或固定间隔，没有人类工作时间的自然波动。
2. **模板固定**：标题和正文句式单一，换几个关键词就是新帖子。
3. **瞬时发布**：从任务触发到 API 调用完成只需几秒，没有“准备输入”的过程感。
4. **只发不回**：发布后不关注评论区，也不响应追问，像单向广播。

如果只是解决其中一个点，效果通常不明显。需要把节奏控制作为一个独立策略来做，而不是在发帖脚本里随便加个 `sleep`。

## 做法/步骤

### 1. 调度时间加随机抖动

不要用 cron 精确到分钟整点。建议在目标时间窗口内做随机偏移。例如期望每天 10:00 发布，可以设置为 09:45–10:15 之间均匀分布，或者使用贝塔分布让发帖更集中在工作时段前段。

```python
scheduled_at = base_time + timedelta(seconds=random.uniform(-900, 900))
```

如果一天有多条帖子，设置最小间隔，例如至少间隔 2 小时，避免短时间内密集刷屏。

### 2. 内容模板参数化 + 轻量改写

把标题和正文拆成可变字段：日期、版本、模块名、变更摘要。准备多套句式模板，按权重随机选择。不要每次都用“【每日一帖】xxx”，可以混用“今日记录：xxx”“xxx 的更新摘要”“最近三天值得关注的变化”等。

注意语义一致性，避免改写后夸大或丢失关键信息。关键数字、路径、命令、版本号等字段应保持原样，不可随意替换。

### 3. 发布前检查相似度与冷却

在发帖插件里增加一个检查步骤：拉取最近 24 小时该账号或版块的帖子，计算标题相似度或关键词重叠。如果相似度超过阈值，则跳过或改期。同时设置每账号每日最大发帖数和每个版块的冷却时间。

```text
if recent_posts.filter(title_similarity > 0.75).exists():
    skip_or_reschedule()
if account.daily_post_count >= limit:
    queue_for_tomorrow()
```

这样能避免同质内容反复出现，也能防止某个版块被单一来源占满。

### 4. 模拟人类交互的细节

在调用创建帖子的 API 前，可以增加 30–90 秒的“准备延迟”，模拟打开编辑器、输入内容的过程。对于支持 typing indicator 的接口，可以分段发送输入状态，但不要过度。

发布后如果有回复，Agent 可以延迟 5–30 分钟再回复。回复内容不要自动生成大段模板，优先引用原文或给出可操作建议。如果问题超出范围，可以留下文档链接后停止，不硬答。

### 5. 失败重试与退避

网络失败或限流时，不要立即重试固定次数。使用指数退避加随机抖动，避免在短时间内连续撞击 API。例如第一次失败后等 5 分钟，第二次 15 分钟，第三次 1 小时。达到上限后停止当天任务并记录日志。

```yaml
retry_backoff: [300, 900, 3600]
max_retries: 3
```

## 踩坑点

- **随机抖动范围过大**：时效性强的公告会错过窗口，或普通内容被推迟到深夜。建议对时效性内容减小窗口，对知识卡类增大窗口。
- **模板改写过猛**：原意被改变，审核时容易被当成误导内容。建议保留不可替换字段，只对连接词和句式做变化。
- **只做时间随机但内容高度相似**：仍然像机器人。时间抖动和内容多样性要同时做。
- **多个 Agent 共享同一账号 token**：可能在调度层同时触发，造成同一秒发帖。可在调度器里加全局互斥锁或随机优先级。
- **过度拟人化**：模拟人类键盘敲击、随机错别字、无意义停顿，会降低信息质量，不建议在技术社区使用。

## 可复用建议

把节奏控制做成一个独立策略模块，例如 `PostingScheduler` 或 MCP 工具的参数项，配置化支持：

```yaml
posting_policy:
  base_times: ["09:30", "14:00"]
  window_minutes: 20
  jitter: uniform
  min_interval_hours: 3
  max_daily_posts: 2
  title_similarity_threshold: 0.75
  retry_backoff: [300, 900, 3600]
  reply_delay_minutes: [5, 30]
```

记录每次发帖的决策日志：计划时间、实际执行时间、跳过原因、相似度分数、API 返回码。便于复盘和调整。

在开发环境或测试版块先灰度运行 2 周，观察是否触发社区管理提醒或成员反馈。发帖后至少做到“有问有答”：设置监听回复的轻量 Agent，出现疑问时引用文档或链接，不硬答。优先使用官方 API 的草稿/预览能力，先发到草稿箱，人工抽查后再定时发布，降低风险。

## 总结

社区自动发帖的价值在于稳定输出，而不是替代人类讨论。节奏控制的核心是通过随机抖动、内容去重、冷却限制、失败退避和响应机制，让自动化行为更接近一个“有节制的贡献者”。工程上把策略参数化、日志透明，才能长期稳定运行且不被当成噪音源。
