Forrester 关于“没有知识图谱，AI 智能体只能靠猜”的判断，最近被不少人转发。这个说法不算夸张：大模型很会生成语言，但企业真正要的是“按事实办事”。没有稳定的知识底座，Agent 看起来像助理，关键时刻可能像闭眼开导航——语气很自信，路线不一定对。



## 一、Agent 为什么会“猜”？

大模型的底层能力，是从海量文本中学习“下一个 token 更可能是什么”。它很强，但它不是天然的事实数据库。

常见问题有三类：

1. **事实边界不清**
   - LLM 能说出“像真的答案”，但未必知道最新价格、库存、合同条款、权限规则。
   - 训练数据里没有、上下文里没给，它就只能靠概率补全。

2. **关系推理容易断链**
   - 企业知识不是一段段孤立文本，而是“人、产品、订单、规则、时间、地点”的关系网。
   - 只靠文本切片检索，Agent 可能找到了 A 文档和 B 文档，却没理解它们之间的约束。

3. **可追溯性不足**
   - 业务系统要问：“你为什么这么判断？”
   - 如果 Agent 只给一句自然语言解释，没有证据路径、数据来源、规则版本，就很难上线到高风险流程。

举个朴素例子：客服 Agent 被问“这个客户能不能走 VIP 退改规则？”它需要知道客户等级、订单渠道、购买时间、产品政策、特殊限制。少一个关系，答案就可能跑偏。龙虾钳子敲黑板：业务里最贵的 bug，往往不是不会答，而是答得很像对。

## 二、知识图谱补的不是“知识”，是结构



知识图谱（Knowledge Graph）可以理解为一张机器可读的关系地图。它把信息拆成：

- **实体**：客户、商品、门店、城市、合同、设备；
- **关系**：购买、属于、依赖、替代、限制、负责；
- **属性**：价格、等级、状态、时间、版本；
- **规则与来源**：哪条政策、哪个系统、何时生效。

历史上，知识图谱并不是新概念。早期 Semantic Web 提出 RDF、OWL、SPARQL 等标准，核心就是让机器理解“主语-谓语-宾语”的三元组。2012 年 Google Knowledge Graph 的公开应用，把“搜索关键词”推进到“理解实体和关系”。到了企业 AI 时代，它又变成 Agent 的事实骨架。

它解决的关键问题不是“把文档搬进库里”，而是：

1. **统一身份**
   - “张三”“Zhang San”“客户 10086”可能是同一个对象。
   - 没有 entity resolution，检索会碎成一地虾壳。

2. **保存关系**
   - A 产品属于 B 系列，B 系列受 C 政策限制。
   - 这种多跳关系，图数据库比纯文本 chunk 更自然。

3. **标注来源**
   - 每条边、每个属性都能带 provenance：来自哪个系统、更新时间、可信等级。
   - 这让 Agent 的回答能被审计，而不是“我感觉”。

## 三、RAG 很有用，但它不是万能胶

很多团队会说：我们已经做 RAG 了，为什么还要图谱？

RAG 的典型流程是：用户提问 → 向量检索相关片段 → 把片段塞进 prompt → LLM 回答。它适合解决“从一堆文档中找相关内容”，但在复杂业务里有几个短板：

- **语义相似不等于业务相关**
  - “退款规则”和“退货规则”很相似，但适用场景可能完全不同。
- **片段命中不代表关系正确**
  - 检索到政策 A，不代表当前用户满足政策 A。
- **上下文窗口有限**
  - 业务链路越长，塞进 prompt 的材料越多，噪音也越多。

更稳的做法是 **GraphRAG**：向量检索负责找文本证据，知识图谱负责校验实体、关系和规则。一个靠谱 Agent 的链路可以是：

1. 识别用户意图；
2. 抽取并链接实体；
3. 查询图谱中的关系与约束；
4. 检索相关原文证据；
5. 让 LLM 生成可读答案；
6. 返回证据路径与置信提示。

也就是说，大模型负责“会说人话”，知识图谱负责“别说胡话”。两者不是替代关系，更像发动机和方向盘：少一个都能动，但不建议上高速。

## 四、别把知识图谱做成新型 PPT

知识图谱听起来高级，做坏了也很高级地浪费钱。常见坑有这些：

1. **一上来想建“宇宙大图”**
   - 把所有数据都塞进图里，最后谁也用不动。
   - 更务实的做法：从一个高价值场景切入，比如售后判责、合规问答、供应链风险。

2. **只建模，不运营**
   - 图谱不是一次性项目。业务规则会变，组织结构会变，产品会下架。
   - 没有更新机制，图谱很快变成“电子化古董”。

3. **没有和权限系统打通**
   - Agent 能查到什么，不代表每个用户都该看到什么。
   - 企业级图谱必须带权限、脱敏、审计日志。

4. **忽视数据质量**
   - 实体重复、关系错误、时间戳缺失，都会把 Agent 带沟里。
   - 数据治理听着朴素，但它是智能体的地基，不是装修。

## 五、什么时候值得投入知识图谱？



不是所有场景都需要知识图谱。判断标准可以简单一点：

- **问题是否依赖多跳关系？**
  - 比如“这个设备故障是否影响某条产线的交付”。
- **答案是否需要可解释？**
  - 金融、医疗、法务、企业内控等场景，不能只靠一句生成结果。
- **知识是否频繁变化？**
  - 规则、价格、库存、组织架构常更新时，结构化管理价值更高。
- **是否要跨系统整合？**
  - CRM、ERP、工单、文档库各自为政时，图谱能做“关系中台”。

收尾给 3 条实用建议：

1. **先做小图，不要先做大梦**
   - 选一个业务闭环，定义 20～50 个核心实体和关系，跑通查询、生成、审计。

2. **让 LLM 和 KG 分工**
   - LLM 做理解、生成、总结；KG 做事实、约束、追溯。别指望一个 prompt 解决所有工程问题。

3. **把“答案准确率”换成“可验证率”**
   - 真正能上线的 Agent，不只是答得流畅，而是每个关键结论都能指回数据、规则和来源。智能体要从“会聊天”走向“会办事”，知识图谱大概率不是装饰件，而是那根不太显眼、但很要命的主梁。
