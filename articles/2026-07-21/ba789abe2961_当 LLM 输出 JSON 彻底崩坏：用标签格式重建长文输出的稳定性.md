## 背景：JSON 作为 Agent 管道的“通用语言”正在反噬稳定性

在 OpenClaw、Agent 工作流、MCP 插件以及各类自动化实践中，我们通常依赖 JSON 来串联不同模块。无论是工具调用参数、LLM 的中间推理、结构化摘要，还是多步任务的中间状态，JSON 几乎成了默认的数据交换格式。这种做法在短输出、固定 Schema 的场景下足够可靠，可一旦要求模型生成长文、复杂嵌套结构，或者输出本身需要保留自然语言段落的排版，JSON 就会频繁崩塌。

最常见的崩塌形式包括：

- 字符串未正确转义，导致整个 JSON 解析失败
- 嵌套层级过深，模型遗漏闭合括号
- 换行符、引号、反斜杠未处理，输出变成“坏 JSON”
- 长 Token 序列使模型“遗忘”最外层结构，直接截断

尤其在需要模型一次性输出完整章节摘要、多段对话分析、或包含代码块与自然语言混合的内容时，仅靠 System Prompt 要求“必须输出合法 JSON”已经不够。总是需要外层修复、重试、甚至降级处理，极大增加了工程复杂度。

## 问题：为什么 JSON 在长文输出中如此脆弱

这不是模型能力的问题，而是**自回归生成与 JSON 语法严格性之间的根本冲突**。

JSON 是一个括号平衡、逗号精确、转义规则严格的格式。但大语言模型是逐 Token 生成的，当输出序列长达数千 Token 时：

1. **局部注意力衰减**：模型在生成第 3000 个 Token 时，已经很难准确“记住”起始的花括号、数组层级。
2. **无回溯修正**：一旦多写或少写一个 `}` 或 `]`，后面无法逆转。
3. **内容干扰格式**：如果输出中包含大段文字，这些文字内部的引号、换行极容易破坏 JSON 结构，哪怕要求模型转义，越长的内容越容易遗漏。

于是，重试成为常规操作。更糟的是，部分 Agent 框架在 JSON 解析失败后会回退到更宽松的修复逻辑，有时会默默吞掉错误，导致下游拿到非预期的数据，排查起来非常痛苦。

## 做法：用“标签格式”替代 JSON 承载长文本输出

面对这种困境，一种更务实的思路是：**放弃在长文本内容上使用 JSON 包裹，改用自定义标签标记法**。

标签格式的思想很简单——用清晰的 XML 式标签（或 Markdown 式分隔符）明确划出不同的信息块，而让内容本身保持自由文本形态，不再要求严格的转义。

### 一个实际案例

假设我们需要从一篇长文章中提取标题、摘要、关键词和全文要点分段。传统做法可能要求模型输出：

```json
{
  "title": "...",
  "summary": "这里是可能包含换行、引号、代码块的超长文本...",
  "keywords": ["...", "..."],
  "sections": [{"heading": "...", "content": "..."}]
}
```

当 `summary` 和 `content` 很长时，上面提到的各种问题就会暴露。

改为标签格式后，我们的输出 Schema 变成：

```xml
[LLM_OUTPUT]
<title>文章标题</title>
<summary>
这里是摘要内容，可以直接包含换行、引号、"双引号"、甚至代码块：
```
print("hello")
```
完全自然，无需转义。
</summary>
<keywords>
- 关键词1
- 关键词2
</keywords>
<SECTION>
<heading>要点一</heading>
<content>
大段自由文本……
