# 从坏 JSON 到标签格式：让 LLM 长文输出更稳定

## 背景：长文结构化输出成了 Agent 的隐形瓶颈

在 OpenClaw 生态里，Agent 经常需要让 LLM 输出一篇包含多段落、多角色、多步骤的“长报告”。比如一次本地文件系统巡检 Agent，需要模型同时返回“文件摘要”、“风险项”、“修复建议”三个区块，每个区块内可能再有嵌套列表和代码片段。我们最初的设计很自然——要求模型输出 JSON：

```json
{
  "summary": "...",
  "risks": [
    {
      "title": "权限过于宽松",
      "detail": "`chmod 777 /etc/shadow`...",
      "fix": "run `chmod 600 /etc/shadow`"
    }
  ]
}
```

这套结构在短文本上工作得不错，但一旦输出超过 500 词，尤其在涉及反引号、换行、缩进、Markdown 片段时，JSON 的可靠性就会剧烈下降。于是我们开始碰见各式各样的“坏 JSON”：缺少闭合括号、字符串内忘记转义双引号、数组末尾多出一个逗号——这些错误让下游自动化流程直接中断，而重试成本极高。

## 坏 JSON 的根源并不全在模型

很多人会把锅甩给“模型不够聪明”，但实际场景中，问题更多出在**协议本身对长文本不友好**。JSON 的严格语法要求 LLM 在生成一个字段时就必须时刻记得已开启的引号、括号层级，且不能出现任何未转义的控制字符。当模型需要输出嵌有 Markdown 的字段时（如上例中的 `detail` 和 `fix`），它对引号、反引号的处理几乎不可能做到 100% 正确。大型语言模型是概率生成系统，不是状态机，越长的结构化文本，累积错误概率越大。

工程角度看，更好的做法是让输出协议的容错性更贴合 LLM 的行为特征，而不是强迫模型去满足严格语法。

## 实操：用自定义标签替代 JSON

我们逐步将长输出协议迁移到了**自定义标签格式**。核心思路是：用成对的、独特的 XML 风格标签来界定每个语义块，解析时依靠标签名称提取内容，而不再要求整个输出是一个合法 JSON 对象。

举个例子，上面的巡检输出可以改为：

```xml
<file_summary>
/etc/shadow 权限为 777，任何用户可读写
</file_summary>

<risk_item>
<risk_title>权限过于宽松</risk_title>
<risk_detail>
当前权限为 `chmod 777 /etc/shadow`，建议修改为 600。
</risk_detail>
<risk_fix>
sudo chmod 600 /etc/shadow
</risk_fix>
</risk_item>
```

这种格式对模型的要求降到最低：它只需要记住“此刻在哪个标签内部”，而不用关心引号、转义或层级。即便模型在中途生成了孤立的 `<` 或 `>`，只要不碰触我们定义的标签边界，解析器仍然可以准确抽取内容。

### 步骤拆解

**1. 设计标签协议**  
标签名必须独特，避免与普通文本内容冲突。建议加上项目前缀，例如 `ocl-`。如 `<ocl-section>...</ocl-section>`。同时明确约定是否允许嵌套。如果场景简单，禁止嵌套能极大降低解析复杂度；若有嵌套需求，则采用可以按层级匹配的解析器。

**2. 改造提示词**  
在 system prompt 或对应任务指令中加入明确的标签格式要求，并提供 few-shot 示例。比如：

> 你的输出必须严格使用以下格式，不要添加多余的解释：
> ```xml
> <ocl-section>内容</ocl-section>
> ```
> 任何内容，包括代码、多行文本，直接放在标签之间，不需要额外转义。

**3. 编写解析器**  
对于禁止嵌套的场景，一个简单的正则提取就足够了：

```python
import re
def extract_tag(text: str, tag: str) -> str:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    m = re.search(pattern, text, re.DOTALL)
    return m.group(1).strip() if m else None
```

如果允许多个同级标签或需要嵌套，可以用小型栈解析器，或者借助 `html.parser`（需处理未闭合标签的容错）。关键是不再将整个文本当作一个对象去 `json.loads`，而是按需抽取片段。

**4. 错误处理与降级**  
当标签缺失或未闭合时，不能像 JSON 那样直接抛异常。可以设计的降级策略：如果某个标签缺失，使用默认值或空字符串；如果结束标签缺失，则取到文本末尾。这种“部分成功”的能力对自动化流程非常实用。

## 踩坑记录

**标签重名**  
即便加了前缀，仍有可能遇到用户输入或模型生成内容里包含同样的标签名。我们的解决办法是：在前缀中加入短随机串，比如 `ocl-a7b3-`，并在提示词中动态传入。这样冲突概率几乎为零。缺点是标签稍显冗长。

**内容包含结束标签**  
这是最经典的问题。模型输出了某个修复命令为 `echo "</ocl-section>"`，导致解析器提前截断。解决方法有三：要求模型使用 CDATA（`<![CDATA[...]]>`），但模型容易忘记；或把内容做 base64 编码，但牺牲可读性；我们最终选择在解析时处理明显的“误关闭”，例如只有当 `</ocl-section>` 单独成行或位于段落结尾时才视为真正结束，这种启发式规则在实践中可用率很高。

**嵌套解析性能**  
当大规模并发处理时，正则或栈解析的 CPU 开销需关注。我们在 Python 环境下用 `re` 和简单栈足够支撑每秒数百条解析，尚未产生瓶颈。如果需要更高性能，可以考虑用 `lxml` 的容错模式，但要注意它是一个严格的 XML 解析器，部分非法字符会触发错误。

## 可复用的工程建议

- **优先考虑“是否真的需要嵌套”**。很多场景一次扁平化就够，提高解析可靠性的同时减少歧义。
- **在提示词里给出一个完整、准确的示例**。示例远比语言描述更有效，且示例中要包含可能出现的特殊字符（引号、反引号、尖括号）。
- **将解析器与模型输出解耦**，单独测试。收集真实长输出的日志，构建一个解析器的回归用例集，每次修改协议后跑一遍，可以有效避免线上意外。
- **对 Agent 来说，结构化的标签输出天然适合分块流式处理**。你可以让每个标签块出来后就推送一个事件，而不必等待整个输出结束。这一点对用户体验提升明显。

## 总结

从坏 JSON 切换到自定义标签格式，本质上是一次“为模型而设计”的接口妥协。它牺牲了 JSON 的标准化和工具链便利，换回了在长文本、多格式内容场景下极高的生成鲁棒性。在我们多个内部 Agent 上，结构化输出的首次成功率从 70% 左右跃升到 99% 以上，重试大幅减少，流程更流畅。

如果你正在用 OpenClaw 搭建需要输出长报告、多段落分析的 Agent，或是在 MCP 服务间传递大段自然语言指令，不妨试试用标签取代 JSON。这不是放弃结构，而是用更弹性的协议换取工程上的稳定。
