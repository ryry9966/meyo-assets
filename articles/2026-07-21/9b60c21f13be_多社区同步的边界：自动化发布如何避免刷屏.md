# 多社区同步的边界：自动化发布如何避免刷屏

## 背景：一次推送，多个社区，一种尴尬
维护开源项目或技术产品时，我们常常需要把一次更新同步到 Twitter、Discord、Telegram、GitHub Discussions，甚至多个语言的社群。手动发送太慢，于是很自然会想到用 Agent + MCP 搭建一条自动化发布流水线。我在最近一次把发布流程接入 OpenClaw 的实践中就踩了一次坑：一个版本发布的自动通知，由于重试逻辑不严谨，在 10 分钟内触发了 5 条内容相似但格式略有差异的推文和频道消息，直接被用户点名“刷屏”。这才意识到，多社区同步的核心不是“发出去”，而是“有节制地发对”。

## 问题出在哪里
自动化同步导致刷屏，通常不是脚本完全失控，而是几个边界处理不当：

- **无分级策略**：无论是重大安全公告还是每日 tip，都按同一频率、同一通道无差别推送。
- **重试风暴**：发送失败后会立即重试，且未去重，短时间内多条相同或略微调整的消息涌入同一个社区。
- **格式不适应**：为了“一套内容通发”，结果在 Twitter 超长被截断，在 Discord 丢失格式，在 Telegram 变成纯文本垃圾，强行刷存在感。
- **缺少全局静默**：在欧洲深夜推送产品更新，对用户就是噪音。

这些问题的本质，是我们用发布者的便利替代了信息接收者的体验。自动化不应该把人工操作的“斟酌”也优化掉。

## 做法：构建一条有节制的发布流水线
我用 OpenClaw 作为编排核心，通过 MCP 封装 Twitter、Discord、Telegram 等社区接口，设计了一套可落地的防刷屏机制。

### 1. 定义通知分级
给每一条待发布内容打上优先级，对应不同的通道和频率：

| 等级 | 示例 | 通道策略 |
|------|------|----------|
| P0 | 安全漏洞、破坏性变更 | 所有公告频道，允许加急，但必须经过人工确认 |
| P1 | 正式版本发布 | 主要公告频道，进入审批队列，延迟发送避免高峰重叠 |
| P2 | 博客、案例、集成更新 | 仅发布到相关主题社群，且合并进周报摘要 |
| P3 | 日常技巧、小提示 | 只发到低频频道（如论坛），每天最多 1 条 |

Agent 根据 GitHub release 标签、commit message 关键词等因素自动判定优先级，P0/P1 默认进入人工复核节点，通过 Slack 交互式消息允许或驳回。

### 2. 速率限制与去重
为每个社区设置独立的冷却时间，例如同一 Discord 频道 30 分钟内最多 1 条公告，Twitter 每小时最多 3 条。使用 Redis 记录最近发送的消息指纹（title + body hash），如果新任务与历史指纹重复且间隔小于冷却时间，则自动静默丢弃并记录日志。重试时，采用指数退避（5s, 25s, 125s…），避免瞬间风暴。

### 3. 通道适配模板
不再“一段话通发”，而是为不同社区编写 Jinja2 模板。Agent 根据原始 Markdown 结构化数据填充：

- Twitter: 截取核心摘要 + hashtag + 链接，字符数自动控制在 280 以内。
- Discord: 使用 Embed 对象，标题、描述、字段结构化，加上颜色标识级别。
- Telegram: HTML 格式，保留加粗、链接，去除不必要的装饰。
- GitHub Discussions: 完整 Markdown，添加 Metadata 标签。

模板保存在单独仓库中，修改不触发流水线逻辑变更。

### 4. 全局静默窗口
在配置中心维护一个全局发布日历，标注每个渠道用户活跃时段。例如亚洲社群为 UTC+8 的 09:00-22:00，欧洲则对应不同窗口。非紧急消息自动排队到下一个可用窗口发送。紧急消息可绕过，但需要单独审批并记录操作原因。

### 5. 监控与回退
所有发送事件写入结构化日志，并设置异常告警：15 分钟内同一通道发送超过 N 条、失败率超过 30% 时，自动暂停该通道的自动化任务，切换到手动模式并通知管理员。同时保留最近 48 小时的消息回放记录，必要时可以快速撤回或澄清。

## 踩坑点
- **指纹去重设计太简单**：最初只比较 body 的完全一致性，结果正文加了个空格就认为是新消息。后来改成标准化 Markdown ast 后取语义哈希，配合编辑距离阈值，误判率大幅降低。
- **静默窗口的边界条件**：跨天队列如果没处理好时区，会导致消息困在队列中永远发不出去。需要设置最大排队时间（如 6 小时），超时降级或通知人工处理。
- **人工审批流程过重**：开始所有 P1 都审批，导致夜间发布延迟。后来引入信任策略——同一作者 24 小时内已审批通过的消息，后续 P1 可自动放行，但 P0 永远不跳审批。

## 可复用建议
1. **优先级即策略**：把发布行为的差异性建立在分级基础上，而不是统一脚本参数。
2. **把社区当作客户**：每次推送前问自己“如果我正在刷这个频道，看到这条消息会不会觉得烦？”，这种直觉比任何 Metrics 都管用。
3. **重试不等于重发**：区分“发送失败需要重试”和“发送成功但觉得不够好再发一次”，后者的危害远大于前者。
4. **用 OpenClaw + MCP 统一接入**：不必为每个社区写独立轮询，MCP server 将 API 抽象为工具后，Agent 可以用自然条件判断和组合，更容易加入防刷屏逻辑。
5. **记录并复盘**：自动化不是“跑起来就不管”，每周看一次发送日志，找出被用户静音、折叠的模式，持续调整。

## 总结
多社区同步的自动化，技术实现的难点并不在“通发”，而在“能不发就不发，要发就发对”。一条无节制的通知可能只浪费你几分钟写脚本，但会消耗几百上千个用户的注意力。把边界划清楚，让 Agent 理解时机、频率和语境，远比追求全自动的酷炫更有工程价值。

一个安静的社区，本身就是最好的社区体验。
