## 背景

在构建基于 Agent 的自动发帖流水线时，我们通常关注生成输出与平台发布两个环节，容易忽略中间的持久化。当帖子量累积到几百篇后，复盘生成质量、修正错误或重新编排内容时才发现：原始输出早已被发布流程消费掉，平台 API 不提供原始内容回捞，本地只剩凌乱的临时文件。对于多模态内容（文字 + 配图），这个问题更突出——文章与图片关系丢失，生成参数无法追溯，导致重复调试成本很高。

于是我们为流水线增加了一个独立的本地归档层：在每篇帖子成功生成但尚未发布前，将其文章、图片及元数据按统一结构落盘，形成可检索的资产库。这篇文章记录这个实践过程中的设计、实现与踩坑点，面向正在用 OpenClaw、MCP 或自定义 Agent 搭建自动化内容管线的同学。

## 问题拆解

一个可靠的归档方案至少需要解决三件事：
1. **文章文本的版本化存储** —— 保留最终用于发布的 Markdown 原文，而不是经过 API 转义后的内容。
2. **图片的本地副本** —— 生成服务返回的图片 URL 有有效期或可能被删除，必须下载并关联到对应帖子。
3. **元数据与关联关系的记录** —— 需要清晰地知道哪张图片属于哪篇文章、图片在文章中的引用方式、生成所用 prompt、生成时间、发布状态等。仅仅平铺文件无法满足后续检索和重放的需求。

如果直接把这些信息往磁盘上一扔，很快就变成难以维护的文件堆。我们需要一个轻量、无额外依赖、容易被脚本和 Agent 读取的结构。

## 做法

### 1. 目录与文件命名约定

以单篇帖子为一个归档单元，目录结构固定：

```
posts/
  2025-07-11-how-to-build-agent/
    post.md
    images/
      img_01.png
      img_02.png
    assets.json
```

目录名采用日期 + slug 的形式，既保证时间排序，又便于人眼识别。图片统一存放在 `images/` 子目录，文件名与 assets 里的引用保持一致。

### 2. assets.json 结构设计

不追求大而全，只记录必要字段，保持体积小，方便用命令行工具或简单脚本读取。一个典型的 assets.json：

```json
{
  "slug": "how-to-build-agent",
  "title": "How to Build a General-Purpose Agent",
  "created_at": "2025-07-11T09:22:00Z",
  "generator": "content-pipeline-v2",
  "status": "draft",
  "post_file": "post.md",
  "images": [
    {
      "local_path": "images/img_01.png",
      "original_url": "https://api.dalle.example/v1/images/xxx.png",
      "prompt": "architecture diagram of an agent system, clean tech illustration",
      "alt_text": "Agent architecture",
      "position": "cover"
    }
  ],
  "prompts": {
    "article": "Write a technical blog post about ...",
    "system_prompt": "You are a ..."
  }
}
```

`prompts` 字段记录了生成文章时使用的提示词，这对后续微调或 debug 非常重要。 `images` 数组保存每张图的原始 URL（以备重新下载）、生图 prompt、位置标记等，这样未来即便 API token 发生变化，也能从 prompt 重新生成。

### 3. 归档流程嵌入流水线

在 Agent 的输出处理阶段（OpenClaw 的 action 或者自定义 MCP server 的工具）增加一个 `local_archive` 步骤：

1. 接收 Agent 产出的文本、图片列表及元数据。
2. 创建以日期 + slug 命名的目录（若已存在则追加后缀或报错）。
3. 将 Markdown 文本写入 `post.md`（UTF-8，LF 换行）。
4. 依次下载每张图片到 `images/`，失败则重试 2 次，仍失败则标记 `download_failed: true` 并继续。
5. 组装 `assets.json` 并写入，使用 `json.dumps` 时开启 `indent=2`，方便版本控制 diff。
6. 返回归档路径，供后续发布步骤引用。

如果用 OpenClaw 的插件机制，可以把归档操作抽象成一个 Tool，供其他 Agent 直接调用；如果是在 Python/Node 脚本中，直接写成函数即可。MCP 用户也可以将这个功能封装为 FileSystem + 自定义 resolver。

### 4. 索引与检索

仅有目录结构还不够，为了快速查找某篇帖子，可额外维护一个 `index.json`，由脚本扫描所有 `assets.json` 生成：

```json
[
  {
    "slug": "how-to-build-agent",
    "title": "How to Build a General-Purpose Agent",
    "created_at": "...",
    "status": "published",
    "path": "posts/2025-07-11-how-to-build-agent"
  }
]
```

在 Agent 的 planning 环节可以直接读取该索引，避免重复生成相似内容。

## 踩坑点

- **路径分隔符问题**：本地开发用 macOS，Agent 或 CI 运行在 Linux，最安全的是统一使用 `/`，并在代码中不做平台转换。Windows 非目标环境，此处可忽略。
- **图片下载并发**：如果一次生成多张图，并发下载会触发反爬或超时。用信号量限制并发数为 2，并加入指数退避重试，稳定性显著提升。
- **assets.json 写入原子性**：直接写入文件可能因程序崩溃导致数据不完整。采用“先写临时文件，再 rename”的方式，文件系统层面保证原子操作。
- **JSON 序列化时的不可序列化对象**：当元数据里包含 datetime、Path 对象时，一定要显式转换为字符串或数值，否则序列化会静默降级或直接报错。
- **文章内图片引用路径**：post.md 内部应使用相对于归档根目录的路径还是 images/ 的相对路径？建议采用 `./images/img_01.png` 这种相对路径，这样整个归档目录可以随意移动，文章渲染不受影响。
- **assets.json 膨胀**：虽然每个文件很小，但一年积累上千条记录后，全量索引生成可能变慢。定期将旧索引归档即可，不必过早优化。

## 可复用建议

- **通用归档器抽象**：将归档逻辑封装为独立模块，提供 `archive_post(metadata, markdown, images)` 接口，内部处理目录创建、文件写入、索引更新。与具体生成器或平台解耦。
- **schema 验证**：为 assets.json 定义一个 JSON Schema，每次写入前进行校验，避免字段错乱。在 Agent 流程中增加 `validate_archive` 工具，发布前检查落盘是否完整。
- **与发布步骤的解耦**：归档失败不应阻塞发布（除非你的发布依赖本地文件），但应记录错误日志，并增加告警。可以用一个简单的“归档状态”字段区分。
- **利用本地归档做 prompt 优化**：一段时间后，可以拉取归档中的 prompts 和对应内容，用人类反馈做 RLHF 或作为 few-shot 示例，形成内容质量的良性循环。
- **版本控制**：将归档目录纳入 Git（排除 images 大文件或用 Git LFS），可以追踪每次生成的差异历史，便于回溯，尤其是在频繁调整 prompt 或模板的时期。

## 总结

本地归档是自动发帖流水线中投入低、收益高的基础设施。它为生成内容增加了一道持久化防线，让 Agent 的输出不再是仅供发布的“一次性用品”，而成为可检索、可复盘、可复用的内容资产。设计上保持轻量，不引入额外存储引擎；通过 assets.json 记录元数据和关联关系，能有效降低日后二次开发的认知负担。如果你的自动发帖 Agent 已经稳定运行，不妨现在就把本地归档加上，未来一定会感谢这个决定。
