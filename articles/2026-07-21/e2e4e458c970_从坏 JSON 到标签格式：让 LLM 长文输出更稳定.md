在构建 OpenClaw 或 Agent 自动化流程时，我们经常让大模型输出结构化数据。短小的信息抽取用 JSON 问题不大，但一到长文生成——比如输出带章节的报告、多步操作计划、完整的 Markdown 文档，JSON 就频繁翻车。这篇文章从工程实践出发，聊聊为什么 JSON 在长文场景不够可靠，以及如何用简单的标签（tag）格式来换取更高的解析稳定性。

## 背景：JSON 遇到的长文困境

典型场景：你让 Agent 生成一份项目上线方案，要求包含“项目背景”“步骤拆解”“风险与预案”等章节，并让模型用 JSON 返回。Prompt 里写清 `{"sections": [{"title": ..., "content": ...}]}`，但真正运行时，经常收到这些坏 JSON：

- 内容中的换行、引号没转义，导致整个 JSON 字符串断裂。
- 数组最后一个元素多了逗号。
- 嵌套对象的花括号不配对，尤其在 `content` 里有类似 JSON 的代码块时，模型会提前闭合。
- 长文本中偶尔冒出的反斜杠、Unicode 控制字符，让标准解析器直接抛错。

很多人上来就想用“容错 JSON 解析器”（比如 `json5`、`json_repair`）来解决，但这些库对结构性破坏（如括号层级错乱、引号内嵌大量自然语言）仍然很无力。修复成本高，重试又会消耗 token 和时间。

更要命的是，Agent 的后续步骤强依赖解析结果，一旦提取失败，流程就会打断、需要人工介入——这与自动化的初衷背道而驰。

## 换思路：用自定义标签约定结构

既然长文内容本身含有大量自由文本，为什么不放弃 JSON，而用更宽松的标签来标记结构？XML/HTML 风格的标记天生适合包裹长文本，解析也更容易容错。

例如，将前面的上线方案改成这样：

```
<project_plan>
<background>
... 任意长度的项目背景描述 ...
</background>
<steps>
<step title="第一步：环境准备">
... 包含换行、引号、代码块的步骤内容 ...
</step>
<step title="第二步：部署上线">
... 内容 ...
</step>
</steps>
<risks>
... 风险评估 ...
</risks>
</project_plan>
```

这种格式的优点：标签是成对出现的，自然语言中的标点几乎不影响解析；不小心出现的裸 `<` 或 `>` 可以通过简单转义或直接忽略处理；即使模型输出时多了一层嵌套或少了一层闭合，我们也能用局部匹配提取出内容，而不是整个 JSON 直接报废。

## 做法与解析器设计

### 1. 明确标签规范，写入 prompt

不要给模型太多自由。在 system 提示或输出示例中明确指出标签的使用规则：

- 标签名使用小写字母和下划线，避免特殊字符。
- 每个结构块必须用对应的开闭标签包裹。
- 标签内部可以包含任意文本，但不要出现与当前标签同名的闭合标签（除非有严格嵌套需要）。
- 如果内容可能包含 `<` 或 `>`，请用 `&lt;`、`&gt;` 转义（这部分模型通常能遵循）。

示例 prompt 片段：

> 请严格按如下标签格式输出计划：
> `<plan>`
>  `<title>策划案标题</title>`
>  `<steps>`
>    `<step name="步骤名">步骤内容</step>`
>  `</steps>`
> `</plan>`
> 内容中如遇尖括号请转义。

### 2. 编写稳健的标签提取器

不要使用标准的 XML 解析库——模型输出可能不是 well-formed，库会直接报错。自己写一个轻量提取函数，按需匹配即可。

实用思路：**基于正则的非贪婪匹配置信区间**。对于 `<tag>`...`</tag>` 结构，我们用 `re.findall(r'<tagname>(.*?)</tagname>', text, re.DOTALL)` 提取内容。如果标签可能会嵌套（例如 `<step>` 内允许出现其他标签），就改为先找到起始标签，然后手动计数层级，或者约定只使用树状但标签名唯一的结构（即同级标签不同名），这样可以避免嵌套匹配歧义。

以 `<step>` 为例，假设一条 step 内不会出现另一个 `<step>`，但可能包含 `<code>` 等内联标签，我们仍可用非贪婪匹配 `<step.*?>(.*?)</step>`。只要内联标签不同名，就不会被错误截断。

如果需要支持属性（如 `<step name="部署">`），正则的开放标签部分改为 `<step\b[^>]*>`。

### 3. 处理流式输出

在 OpenClaw 等支持流式解析的场景，标签可能在 chunk 边界被切断。一种工程化方案是：将收到的所有 chunk 拼接到缓冲区，定时尝试解析已完整闭合的标签块，解析成功的移出缓冲区，未闭合的保留继续拼接。这就避免了在字符中间切分标签名或 `</` 导致的解析失败。

## 踩坑点与真实教训

在实践中我们踩过几个坑：

- **标签名冲突**：模型在自由文本中意外输出了与标签同名的普通词语。如 `<title>关于<title>标签的使用</title>`，导致最早的非贪婪匹配只拿到“关于”。解决办法：选择相对“冷门”的标签名，例如 `_title_` 或 `opt_title`，并在 prompt 中强调避免使用这些字符串作为正文。
- **属性值中的引号**：如果属性值包含引号，正则捕获会出错。现在更推荐**不要依赖属性**，而是把信息放在子标签里，例如：

  <step>
  <name>部署</name>
  <content>具体内容
