# 微博超话同步实践：图片上传、限流和状态归档

## 背景

我们有一个基于 MCP (Model Context Protocol) 的社交内容代理，需要将生成的内容自动同步到微博超话。同步不只是发文字，还包括配图上传、话题标签拼装，以及一整套“发完就忘”的归档流程。微博开放接口对超话的支持度有限，很多操作依赖移动端 API 的逆向，这就把同步任务从简单的 HTTP 请求，升级成了需要处理登录态、图片上传链路、频率控制和任务持久化的工程问题。

这篇文章记录我们在 OpenClaw 体系下，用 Agent + MCP 工具链搭建超话同步能力的整个过程，重点讲图片上传、限流策略和同步状态的归档设计。

## 问题拆解

一张微博配图帖在超话里的发布路径，比想象中复杂：

1. **登录态维护**：需要从已有的 cookie/会话中提取可用凭证，并处理过期刷新。
2. **图片上传**：微博的图片上传接口是独立于发微博接口的，需要拿到 `pic_id` 之后才能组装发帖请求。
3. **超话标识**：发帖时必须携带超话的 `topic_id` 或特定参数，否则帖子不会出现在超话 feed 中。
4. **限流陷阱**：图片上传和发帖接口都有频率限制，超话相关操作的风控权重更高。
5. **状态追踪**：同步任务不能“请求结束就当成功”，需要存档每条帖子是否成功、失败原因、是否已被删除或仅自己可见。

## 做法与步骤

### 1. MCP 工具封装

我们在 OpenClaw 环境中把微博同步拆成三个 MCP 工具：

- `weibo_image_upload`：接收本地图片路径，返回 `pic_id` 和上传后的 CDN 地址。
- `weibo_post_create`：接收文本内容、图片 `pic_id` 列表、超话 ID，返回 `post_id` 和可见性状态。
- `weibo_status_check`：传入 `post_id`，查询帖子当前状态（存在/已删除/审核中/仅自己可见等），供归档任务使用。

每个工具都内建了凭证管理器，从环境变量或专用密钥存储中拉取 cookie，自动在 403/登录过期时触发告警而不是静默失败。

### 2. 图片上传的具体实现

微博图片上传走的是 `multipart/form-data`，接口地址类似 `https://picupload.weibo.com/interface/pic_upload.php`。需要注意的点：

- 必须携带有效的登录 cookie 和 `Referer`。
- 部分账号要求 `crossdomain` 参数与上传回调域一致，否则会得到空响应。
- 服务端返回的 `pic_id` 是一串数字，后续发帖需要用 JSON 数组包装，如 `[{"pic_id":"xxx"}]`。
- 上传成功后，强烈建议用返回的图片 CDN URL 做一次 HEAD 请求验证可访问性，因为我们遇到过 `pic_id` 正常但图片被拦截为私有的情况。

在 MCP 工具内，我们用 `curl` 或 Python `requests` 保持了完整的上传链路日志，每次上传记录耗时、返回状态码和 `pic_id`，方便排查。

### 3. 超话发帖与参数拼装

发帖接口是 `https://weibo.com/ajax/statuses/update`（或移动端变体）。要使帖子进入超话，需要在文本内容中嵌入超话标识，或通过 `topic_id` 参数显式指定。我们的实践是：

- 文本末尾追加 `#某某超话#`，但仅靠话题标签不一定能被归入超话，尤其当超话名有特殊符号时。
- 更稳妥的做法：通过预请求超话信息接口，获取 `topic_id`，然后在发帖请求的 `extparam` 或 `visible` 相关字段中指定。这部分字段在不同版本的客户端接口中有所不同，需要抓包确认。

我们最终维护了一个超话 ID 映射表，由 Agent 在发帖前通过 MCP 工具查询最新有效 ID，避免硬编码带来的失效问题。

### 4. 限流与重试策略

微博的限流体现在多个层面：

- **图片上传频率**：短时间内连续上传超过 5 张会触发“操作太频繁”，返回 302 或空响应。
- **发帖频率**：同一账号连续发帖会进入验证码或强制退登。
- **超话特殊限制**：部分超话有等级限制或发帖审核，接口返回成功但帖子实际不可见。

我们的应对方案：
- 在 MCP 工具侧引入“滑动窗口计数器”，用 Redis 记录每个账号每分钟/每小时的上传次数和发帖次数。
- 遇到频率限制错误码（如 `100005` 或特定 `msg`），立即返回给 Agent 一个明确的 `rate_limited` 状态，并附带 `retry_after` 建议值。Agent 根据这个值将任务重新放回队列，而不是疯狂重试。
- 对于超话审核导致的“假成功”，下线后通过 `weibo_status_check` 工具定时扫描最近发帖，发现 `visible=only_self` 或 `deleted` 的状态，归档标记为“被过滤”。

### 5. 状态归档设计

每条同步任务在数据库中存有一条记录，核心字段如下：

- `task_id`：唯一 ID
- `content_hash`：内容 SHA256，用于去重
- `pic_ids`：上传成功的图片 ID 列表
- `post_id`：微博返回的帖子 ID
- `sync_status`：`pending` / `uploading` / `posted` / `failed` / `filtered` / `deleted`
- `rate_limit_info`：JSON 字段，记录触发限流时的返回体和时间
- `last_check_time`：最后一次状态检查时间

一个 cron 任务每小时拉取 `sync_status=posted` 且 `last_check_time` 超过 24 小时的任务，调用 `weibo_status_check` 刷新状态。如果帖子消失或变成仅自己可见，标记并通知运维频道。这样就形成了一个“发帖-验证-归档”闭环。

## 踩坑记录

1. **图片上传接口的 `pic_id` 格式变更**：不同账号类型（普通/企业/会员）返回的 `data` 结构不一致，有时 `pic_id` 在 `data.pics[0].pid`，有时直接在 `data.pic_id`。必须做好兼容解析，不要只取第一个字段。
2. **cookie 时效**：抓取的 cookie 有时效，从几小时到几天不等。Web 端和移动端的接口域不同，cookie 不能混用。我们在 MCP 工具中把 cookie 分成“上传专用”和“发帖专用”两套，分别验证。
3. **超话 ID 失效**：超话改名或合并后，原来的 `topic_id` 会失效，但接口不报错，帖子直接发到个人主页。因此要定期更新映射表。
4. **内容过滤**：带链接的帖子在超话中极易被转为仅自己可见。我们在 Agent 提示中明确避免带外链，除非是微博自有域名。

## 可复用建议

- **MCP 工具粒度**：把上传、发帖、状态检查拆成独立工具，方便 Agent 组合调用，也方便限流逻辑单独精细控制。
- **状态机驱动**：用明确的状态流转代替“成功/失败”二元判断，尤其是 `filtered` 这种半成功状态，对后续数据质量至关重要。
- **凭证分离**：不同操作使用不同 cookie/profile，降低单点故障。
- **记录限流元数据**：每次 429/频率限制都详情存档，可以后续分析出安全速率，避免再次触发。
- **不要信任“成功”响应**：微博的“发帖成功”不保证可见性，异步检查是必须的。

## 总结

微博超话同步看似简单，实际工程化后才发现，难点不在发帖接口本身，而在图片上传链路的稳定、限流的智能规避，以及帖子真实状态的追踪。通过 MCP 工具封装，我们将这些复杂性限制在可控范围内，让上层的 Agent 能专注于内容生成和调度逻辑。这套设计也同样适用于其他需要“发布 + 验证”的平台同步场景，只需替换底层 API 适配和状态检查逻辑。

如果你也在 OpenClaw 体系下做类似的多平台分发，希望这篇实践能让你少走一些图片上传和状态归档的弯路。
