## 背景

在内容分发自动化的场景里，把图文内容同步到微博超话是一个常见需求。无论是给博客摘要做扩散，还是将 AI 生成的早报发到垂直话题下，背后都需要一条可靠的发布链路。这条链路不能只是“发一条带话题的微博”那么简单，它必须处理好三件事：图片如何稳定上传、接口限流如何应对、以及每一次发布的状态如何留痕与回溯。

过去一段时间，我在基于 OpenClaw 构建自己的内容编排流程时，把微博超话同步做成了一个可复用的 MCP 工具。下文整理了这个过程中的关键设计、实施步骤和踩坑记录，希望能给同样在折腾微博自动化的朋友一些参考。

## 问题拆解

一条“把图文发到微博超话”的流水线，拆开来看包含三个核心子问题：

1. **图片上传**：微博开放平台要求先调用 `statuses/upload` 上传图片，拿到 `pid`，再在发微博时传入。上传接口的限流和错误码需要单独处理。
2. **限流策略**：上传和发微博共用账号级别的频率配额。短时间密集调用会触发错误码 10024（发布过于频繁），严重时可能导致功能降级。需要一个温和的限流器，而不是简单粗暴的 sleep。
3. **状态归档**：重复同步会骚扰粉丝，丢失发布记录则无法排查问题。每次发布的源内容标识、微博 ID、发布时间、话题名称都需要持久化，并在下次同步前查询去重。

此外，微博开放平台的 `access_token` 有过期时间，超话发布接口并不向普通开发者开放，实际只能通过“正文中包含 #超话名称#”的方式近似实现。这些限制都需要在工程上提前考虑。

## 实施步骤

### 1. 准备工作

- 在 [微博开放平台](https://open.weibo.com) 创建网页应用，获取 `App Key` 和 `App Secret`。
- 通过 OAuth2.0 授权码流程获取 `access_token`。若需长期运行，建议使用票据刷新接口并持久化 token，避免人工干预。
- 在 OpenClaw 中为后续操作封装一个 `weibo_client` 工具实例，统一管理 token 读取与过期检测。

### 2. 图片上传

上传接口为 `https://upload.api.weibo.com/2/statuses/upload.json`，采用 `multipart/form-data` 方式提交。关键点：

- 表单字段名必须为 `pic`，不能写成 `file`。
- 文件元组格式：`('pic', (filename, file_bytes, content_type))`。
- 上传成功后返回 JSON 中的 `pid` 字段（字符串），这就是发微博需要的 `pic_id`。

```python
files = {'pic': (image_name, image_bytes, 'image/jpeg')}
resp = requests.post(upload_url, data={'access_token': token}, files=files)
pid = resp.json()['pid']
```

### 3. 发布微博（带超话）

调用 `statuses/update`，在 `status` 字段内包含 `#超话名称#`，并将前面获得的 `pid` 通过 `pic_id` 参数传入。由于普通开放平台接口不支持真正的超话发帖，这种话题文本的方式是最务实的替代方案。

### 4. 限流处理

微博对同一个 `access_token` 下的发帖和上传有共享配额。实际测试中，间隔低于 30 秒就很容易触发 10024 错误。我的做法是在工具层引入一个 **令牌桶 + 指数退避** 的轻量限流器：

- 初始速率设为 3.0，每分钟最多 2 次调用（考虑上传+发布两条请求）。
- 遇到 10024 或 HTTP 429 时，退避时间从 60 秒开始，上限 10 分钟。
- 发布前显式等待令牌，避免盲目重试。

### 5. 状态归档

创建一个 SQLite 数据库，记录每次发布的状态：

| 字段        | 说明                     |
| ----------- | ------------------------ |
| source_id   | 源内容唯一标识           |
| weibo_id    | 发布后返回的微博 ID       |
| topic       | 超话名称                 |
| created_at  | 发布时间                 |
| status      | success / failed / skipped |

每次同步前，先根据 `source_id + topic` 判断是否已成功发布，跳过重复项。失败记录保留，供后续人工核查或自动重试。

## 踩坑记录

- **图片 `pid` 不是图片 URL**：拿到 `pid` 后无法直接访问，只有微博正文里的图片才可通过 `pic_infos` 找出 `thumbnail_pic` 等字段。
- **图片大小限制**：官方要求不超过 5MB，但实际测试接近 5MB 时上传成功率下降，建议压缩到 2MB 以内，同时控制长边在 1280px 左右。
- **`status` 长度限制**：普通应用为 140 字，超出会被截断。如需长文，需要使用 `statuses/share` 或将正文作为图片文案的一部分另做处理。
- **超话显示差异**：带话题的微博会进入话题页，但并不直接等于超话内的“发帖”。个别超话可能因为设置无法同步，需要在选定话题前测试确认。
- **Token 过期静默失败**：错误码 21332 或 21317 表示 token 过期，必须自动检测并刷新，否则所有请求直接返回错误，容易被忽略。

## 可复用建议

在 OpenClaw 体系中，我最终把这个工具封装成一个 MCP Server 提供的 `post_to_weibo_topic` 动作，暴露如下参数：

- `content`：纯文本，140 字以内
- `images`：本地文件路径或 bytes 列表
- `topic`：超话名称，如“AI绘画作品展”
- `source_id`：外部系统的唯一 ID

工具内部自动完成上传、限流、发布和归档。调用方只需关心“发什么”和“发了没有”，不用再重复处理底层的 token、重试和状态记录。

如果团队有多个自动化流程需要发布微博，建议将限流器做成集中服务，多个 Worker 共用同一个配额更安全。

## 总结

微博超话同步在工程落地层面并不复杂，但细节缠脚。图片上传的参数、限流器的退避策略、以及状态归档的完整性，是决定这套自动化能否长期稳定运行的关键。把“发一条微博”这件事抽象成一个可监控、可去重、可限速的工具，远比写一个一次性脚本更有价值。

整个方案在 OpenClaw 体系内作为 MCP 工具运行后，日常同步的失败率从接近 20% 降到了 1% 以下，所有的异常也都有了可追溯的日志。如果你也在构建类似的内容分发链路，希望这些记录能帮你少走一些弯路。
