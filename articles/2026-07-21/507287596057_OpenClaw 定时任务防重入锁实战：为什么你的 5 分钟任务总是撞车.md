## 背景

在 OpenClaw 的自动化板块里，“每 5 分钟跑一次”是高频需求：同步外部数据、清理过期会话、触发下游 Agent 工作流……人们习惯用 `cron: "*/5 * * * *"` 一配了之。  
但当任务执行时间悄悄超过 5 分钟时，上一次还没跑完，下一次又启动了。于是一个本应串行的逻辑变成了并发执行，典型症状包括：

- 数据库重复插入或更新覆盖  
- 下游服务被短时间高频调用触发限流  
- 日志里出现两个 PID 同时操作同一资源  
- 回调错乱、状态机推进异常

这就是“5 分钟任务撞车”的根因：**调度间隔 < 任务执行耗时**，加上没有任何互斥保护。

OpenClaw 本身不替你做重入控制，它只负责按表达式触发。因此防重入锁需要由任务自身或插件来实现。本文以常见的本地部署场景为例，给出一套轻量但工程化的做法。

## 问题建模

一个典型的定时任务伪代码：

```python
@schedule("*/5 * * * *")
def sync_orders():
    orders = fetch_from_api()      # 可能耗时 2-3 分钟
    transform_and_save(orders)     # 可能耗时 3-4 分钟
```

在正常负载下，总耗时 6~7 分钟，已超过 5 分钟周期。如果没有锁，第 6 分钟第 2 次执行会与第 1 次重叠。  
更隐蔽的坏情况：某次网络抖动让 `fetch_from_api` 卡了 8 分钟，后面可能堆积 2~3 个实例。

## 做法：文件锁 + 超时兜底

以 OpenClaw 插件或自定义 Agent 为例（Python 实现，Linux 环境），步骤拆解如下：

### 1. 定义锁文件与超时
```python
LOCKFILE = "/tmp/openclaw_sync_orders.lock"
LOCK_TIMEOUT = 10 * 60  # 任务最大容忍执行时间 10 分钟
```

### 2. 尝试获取锁（非阻塞）
```python
import os, time

def acquire_lock():
    if os.path.exists(LOCKFILE):
        # 检查锁是否过期（防止死锁）
        mtime = os.path.getmtime(LOCKFILE)
        if time.time() - mtime > LOCK_TIMEOUT:
            os.remove(LOCKFILE)  # 强制释放过期锁
        else:
            return False
    # 创建锁文件，写入当前时间戳
    with open(LOCKFILE, 'w') as f:
        f.write(str(time.time()))
    return True
```

### 3. 任务执行与释放
```python
def sync_orders():
    if not acquire_lock():
        print("Previous job still running, skip.")
        return
    try:
        # 实际业务逻辑
        orders = fetch_from_api()
        transform_and_save(orders)
    finally:
        if os.path.exists(LOCKFILE):
            os.remove(LOCKFILE)
```

### 4. 在 OpenClaw 中挂载
如果你用 YAML 定义 Agent，可以在 `steps` 的首位插入一个 Python 脚本步骤，或直接写成带锁的 callable。  
若使用 MCP 工具，可将锁逻辑封装成 `acquire_lock` / `release_lock` 工具，让任务在开始和结束时调用。

## 踩坑实录

**坑 1：锁未释放导致死锁**  
进程崩溃、`kill -9` 都会跳过 `finally`，锁文件残留。  
解决：采用 **过期强制释放** 策略，并设置合理的超时时间（比任务正常耗时长 50% 以上）。必要时可结合 `flock` 系统调用获得内核态自动释放能力。

**坑 2：超时时间一刀切**  
超时太短，会把一个仍在正常运行的慢任务误杀；太长，故障时丧失保护。  
建议在锁文件中记录 PID，过期清理前检查进程是否存在，若存在则（可选）发送报警，但不强制删除。

**坑 3：跨节点部署时文件锁失效**  
若同一个任务可能被 OpenClaw 调度到不同机器，本地文件锁形同虚设。  
此时必须升级为 **分布式锁**，推荐用 Redis (`SET NX PX`)、etcd 或数据库的 `INSERT ... ON CONFLICT` 实现。

**坑 4：锁粒度混用**  
不同任务如果用同一个锁名，会互相阻塞。务必为每个任务生成唯一锁标识，例如 `task_name + hash(参数)`。

**坑 5：幂等性缺失**  
即使加了锁，任务重试或手动补跑时仍需保证幂等。  
应在数据层使用 `upsert`、唯一约束、业务去重键等手段配合。

## 可复用建议

1. **抽象为 OpenClaw 插件**：把锁逻辑封装成一个 PreRun Hook，所有定时任务共享同一机制。
2. **利用 MCP 工具统一管理**：例如暴露一个 `dist_lock` 工具，内部自动根据 `caller_name` 选型（文件 / Redis）。
3. **集成健康检查**：暴露 `/health` 时报告当前锁持有状况与堆积任务数，方便监控。
4. **与重试策略解耦**：锁只负责互斥，重试交给调度器（如 `on_error: retry`），避免在锁内睡眠等待。
5. **记录诊断日志**：获取锁失败时打印原因（锁存在、过期等），并可选写入 OpenClaw 的执行审计。

## 总结

“5 分钟任务撞车”的本质是异步调度与同步资源的冲突，防重入锁是工程上最直接的解法。实现并不复杂，但需要处理好死锁、过期、分布式这三座大山。  
在 OpenClaw 生态中，你可以从最简单的文件锁开始，随着部署规模演进到分布式锁。核心原则只有两条：

- **永远假设任务可能超时**  
- **永远让锁具备自动恢复能力**

遵循这两点，你的定时任务才会从“差不多能用”变成“可以自信地跑在生产环境”。
