## 背景

做技术输出的朋友大多会面临一个现实问题：同样的内容需要在不同社区发布，比如 Twitter 发一条摘要、Discord 频道同步一条带格式的更新、GitHub Discussions 归档完整版、知乎再发一篇带上下文的长文。手工操作既浪费时间又容易遗漏，于是自动化同步几乎成了标配。

过去半年，我在维护几个技术项目的对外内容时，尝试用 OpenClaw 的 Agent 能力加上 MCP 协议搭建了一套多社区分发管道。初期的确省力，但很快踩到了“刷屏”的坑：同一个夜间窗口，所有平台一起推，关注者跨平台看到一模一样的东西，反馈像极了“你是不是被盗号了”。

这篇文章记录我从“能发就行”到“控制边界”的工程化调整过程，主要分享如何用 Agent + MCP 插件实现**有抑制、可审计、不失真**的多社区发布，避免沦为内容污染源。

## 问题拆解

粗暴的自动化同步通常会导致三个具体问题：

1. **重复刷屏**：同一内容在多个平台几乎同时出现，关注者会产生疲劳甚至反感。
2. **格式错乱**：各社区 Markdown 方言不同、链接解析规则不同、最大长度不同，直接复制粘贴常出现断裂内容。
3. **误发敏感信息**：某些草稿或内部讨论无意间被管道发到公网，难以撤回。

解决这些问题不能只靠“先发一个平台，再手动转发”。我们需要一种可编程的节律控制，同时保持 Agent 的灵活性。

## 实现方案

整体架构： **OpenClaw Agent → MCP 客户端 → 多个 MCP 服务（封装各个社区 API）**。Agent 负责决策“什么时候发、发什么、发到哪里”，MCP 服务则提供标准化的工具接口（比如 `create_post`、`get_channel_info` 等）。

核心模块如下：

### 1. 内容指纹与去重
为每一条待发内容生成一个内容指纹（比如，取 Markdown 正文的前 256 字节 + 标题 + 模板版本号做 SHA256）。在分发之前，Agent 查询存储（我用的是 SQLite，方便部署）检查该指纹是否已经发布过。如果发现指纹重复，直接跳过，并将事件记录到日志。

```
fingerprint = sha256(f"{title}#{body[:256]}#{version}")
if db.exists(fingerprint):
    agent.log("skip duplicate")
    return
```

### 2. 发布冷却队列
每个目标社区设定一个最小发布间隔（例如 Twitter 至少 30 分钟，Discord 至少 2 小时）。Agent 维护一个优先级队列，按社区分类，距离上次发布时间不足冷却时间的社区不会被立即投递。内容会暂存到队列里，由单独的定时器评估是否可以触发发送。

为了避免队列堆积导致的“延时爆发”，每次触发前会重新计算当前时间减去上次发布时间，只对有资格的平台进行投递。

### 3. 多平台格式化适配
在 MCP 工具层面，每个社区的服务实现独立处理文本转换。例如，Discord 需要将 Markdown 图片转换成语义清晰的 Discord 嵌入格式；GitHub Discussions 需要追加固定分隔线和源链接；Twitter 需要智能截断并附上卡片。Agent 调用工具时只需传递结构化内容（标题、正文、链接、标签等），格式化交给对应的 MCP 服务，保证内容和展示不互相污染。

### 4. 预发布草稿与确认
对于重要公告，增加一条“dry-run”路径：Agent 先生成一个预发布摘要，发送到内部审核频道或通过日志 webhook 通知我，只有在我明确回复 `confirm` 后才会真正执行发布。这是防止错发的最后一道闸门。

## 踩坑点

实践下来，最容易卡住的地方有几个：

- **API 速率限制的雪崩**：一开始我想当然地用全局固定间隔，结果某天多个社区同时解除冷却，瞬间触发一堆请求，直接撞上 Twitter 的速率墙。修复方式是引入“吉特抖动”（jitter），在每个冷却间隔上加上 0～30% 的随机延迟，错开密集触发点。
- **指纹误判**：仅用标题做指纹会导致“更新日志”这种周期性内容被误判为重复。后来改成标题+正文前 256 字节，并且区分模板版本号，有效区分类似但实际不同的内容。
- **格式的一次性适配陷阱**：Discord 的 embed 长度限制会无声截断内容，一开始没做截断检测，导致内容丢失。现在在每个 MCP 服务里都加了内容长度校验，超长则自动拆分成多条或提示人工处理。
- **Agent 的“过度自信”**：Agent 有时会错误地认为某个内容已经发布过（因为指纹碰撞），导致真正需要更新的通告被跳过。给 Agent 增加了人工确认路径，让重要的发布决策始终有机会被人类检查。

## 可复用建议

如果你也想搭建类似的发布管道，建议从这些角度切入：

1. **最小可行管道**：先只对一个社区做指纹 + 冷却控制，跑通流程，再扩展到多社区。
2. **用 MCP 解耦社区逻辑**：不要把每个平台的 API 调用写死在 Agent 里。通过 MCP 暴露统一工具，后续切换或新增社区只需增加 MCP 服务，Agent 逻辑零改动。
3. **所有动作留下审计日志**：指纹检查结果、发送成功/失败、冷却评估、人工确认记录都入库。出了问题可以回溯到具体决策点，而不是猜。
4. **人工辅助断点**：关键公告或新模板的第一次发布，永远保留一个“需要人工确认”的开关。
5. **考虑社区文化**：自动化不是泯灭人情味。像 Discord 这类重视即时交互的社区，同步内容可以搭配一条非模板化的简短介绍，让关注者觉得是“人”在说话。

## 总结

多社区同步的核心不是“发得更快更多”，而是**用最少的打扰、最一致的格式，把内容递送到需要它的人面前**。通过 Agent 做智能决策，结合 MCP 将执行抽象化，再辅以内容指纹、冷却队列和人工断点，可以构建一条既足够自动化，又不失尊重的发布管道。

这套方法不仅适用于内容发布，还可以泛化到任何需要“多通道输出”的自动化场景，比如多环境通知、多语言文档同步等。我自己现在每周大约节省 3-4 小时重复发布工作，且不再收到“刷屏”投诉——这个结果刚好印证了一句老话：好自动化是让你感觉不到它存在的自动化。
