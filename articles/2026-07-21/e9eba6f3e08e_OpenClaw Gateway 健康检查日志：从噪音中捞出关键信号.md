## 背景

在 OpenClaw 的部署形态里，Gateway 往往是所有 Agent 请求、MCP 工具调用与外部插件流量的统一入口。Kubernetes 的 liveness/readiness 探针、负载均衡器的健康检查、甚至部分监控系统的拨测都会反复访问 Gateway 的健康检查端点。这些请求会在日志里留下大量痕迹，但很少有人专门梳理这些日志在说什么、怎么高效看、以及踩过哪些坑。

本文假设你已经使用 OpenClaw Gateway 构建过 Agent 服务，至少见过 `access.log` 或类似输出，主要面向需要分析健康检查异常、或在生产环境中被健康检查日志淹没的实践者。

## 问题

健康检查日志最常见的三类困扰：

1. **日志量洪水**：每 5 秒一次探针，一天 17280 条，和正常业务日志混在一起，干扰排查。
2. **“成功但异常”**：健康检查返回 200，但后端 Agent 其实已经超时无响应，日志里看不出更深层的问题。
3. **“失败但无痕”**：健康检查失败时，除了负载均衡器告警，Gateway 日志里可能只有一条简单的 `GET /healthz` 加上状态码，缺少上下文。

要解决这些问题，需要先理解 OpenClaw Gateway 健康检查日志的结构，再决定在哪一层做过滤、增强和告警。

## 做法 / 步骤

### 1. 定位健康检查路径

OpenClaw Gateway 默认提供 `/healthz`（存活）和 `/readyz`（就绪）端点，常见部署可能还自定义了 `/health` 或 `/api/health`。首先在反向代理或网关配置文件中确认路径，然后到日志里分离这些请求。

如果你使用文件日志，可以用 `grep` 快速提取：

```bash
grep -E "/healthz|/readyz" /var/log/openclaw-gateway/access.log
```

如果使用标准输出并接入了 Loki/ELK，可以用类似的过滤条件查询：

```logql
{app="openclaw-gateway"} |~ "/healthz|/readyz"
```

### 2. 读取关键字段

一条典型的 OpenClaw Gateway 访问日志可能长这样：

```
[2025-01-20T10:03:15.432Z] "GET /healthz HTTP/1.1" 200 4 "-" "kube-probe/1.28" - 2ms upstream=127.0.0.1:9090
```

重点关注：

- **状态码**：200 代表探针本身返回成功；非 200（如 503）要马上看上游。
- **响应时间**：`2ms` 通常表示本地处理极快；如果突然升高到秒级，可能是路由逻辑或认证模块卡住。
- **upstream 字段**：如果健康检查转发到了后端，该字段会显示后端地址和状态。如果出现 `upstream status=502` 但网关本身返回 200，说明探针未正确判断后端健康（常见配置错误）。
- **User-Agent**：`kube-probe/1.28` 是典型 Kubernetes 探针；负载均衡器的探针往往使用自定义 UA，可以借此区分来源。

### 3. 为健康检查日志单独分流

在生产环境强烈建议将健康检查日志写入独立文件或打上特殊标签。以 OpenClaw Gateway 配置文件为例（通常 YAML/JSON），在 access log 配置段增加按路径过滤：

```yaml
logging:
  access:
    filters:
      - paths: ["/healthz", "/readyz"]
        output: /var/log/healthcheck-access.log
      - paths: ["*"]
        output: /var/log/access.log
```

此举可将 95% 的无意义心跳日志从主业务日志中剥离，同时不影响排障时需要全量信息的场景。

### 4. 启用调试日志看探针内部过程（谨慎使用）

当怀疑健康检查端点的行为不符合预期时，可临时将对应路径的日志级别调整为 `debug`。在 Gateway 的插件链中，健康检查可能经过鉴权、限流、路由模块。调试日志会打印每个模块的处理耗时会话，甚至显示是否因为某个插件导致了拒绝。注意调整后立即监控 CPU 和日志增量，排障后恢复为 `info` 级别。

### 5. 设置趋势告警而非单点告警

不建议直接对单次健康检查失败做钉钉/飞书告警。更工程化的做法是：连续 N 次失败、或 1 分钟内失败率超过 50% 才触发告警。同时关联后端 Agent 的自身健康指标，防止 Gateway 探针正常但后端已经半死不活的情况。

## 踩坑点

- **探针频率过高导致日志风暴**：Kubernetes 默认 `periodSeconds: 10` 已经足够，有些团队设为 1 秒，日志量激增同时也会略微增加延迟波动，需要平衡。
- **忘记区分存活和就绪探针**：两者日志路径可能相同，只有状态码可能不同。务必为两个端点设置不同的日志标记，否则无法快速判断是服务启动慢还是已挂死。
- **健康检查成功不代表网关健康**：Gateway 本身 `/healthz` 只检查进程是否存活，如果想探测下游 Agent 是否可用，应该让就绪探针 `/readyz` 调用一个轻量级后端检查并返回合成状态，否则会出现“网关活着，Agent 全死”而 K8s 不重启 Pod 的尴尬。
- **把健康检查日志混入了业务监控指标**：如果使用 Access Log 计算 QPS、错误率，一定要排除健康检查请求，否则数据失真，尤其是短期窗口内可能显示毛刺下降。

## 可复用建议

1. **日志分层**：健康检查日志 → 独立文件/独立标签；业务日志 → 单独保留。
2. **规范探针路径与 UA**：在团队内部约定 `/healthz`、`/readyz`，并要求负载均衡器使用特定 `User-Agent`，方便区分来源。
3. **监控联动**：将健康检查日志的延迟和状态码指标化（例如 Prometheus 的 `healthcheck_duration_seconds`），与 Pod 状态、后端 Agent 健康指标放在同一看板。
4. **日常巡检**：每周拉取健康检查错误趋势，哪怕未触发告警，也可能发现某些探针偶发超时而未被 Kuberentes 判定失败（例如刚好不超过 `failureThreshold`）。

## 总结

OpenClaw Gateway 的健康检查日志看似简单，但能否从中看明白系统的真正健康度，往往决定了问题排查的速度。不要满足于“探针返回 200”，要把日志当作信号，通过分流、字段读取、关联后端和趋势告警，才能让健康检查日志从噪音变成有效的运维信息。下一次翻看日志时，可以先问两个问题：这条健康检查日志是来自 K8s 还是 LB？它的上游状态和你想象的一样吗？
