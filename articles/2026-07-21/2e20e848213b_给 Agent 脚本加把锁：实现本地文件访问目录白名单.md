## 为什么需要文件访问护栏

在 OpenClaw 这类 Agent 框架里，我们经常通过 MCP 工具或自定义插件让自动化脚本访问本地文件系统：读取配置、写入日志、导出报告。一旦工具定义稍显粗放，`read_file` 或 `write_file` 就可能暴露整个文件系统，Agent 的 prompt 注入或意外行为会导致任意路径读写。这不是假设出来的威胁——当 Agent 被赋予“帮我把输出保存到本地”的能力时，它完全可以接受一个类似 `/etc/crontab` 或 `~/.ssh/id_rsa` 的路径。

容器化可以部分缓解这个问题，但不是在每种部署形态下都可行，也不该成为唯一防线。更务实的做法是：在工具实现层加一层薄薄的护栏——**本地目录白名单**，只允许 Agent 读写指定的项目目录或沙箱目录。

## 目标设计

需求很明确：

1. 定义白名单目录列表，例如 `["./workspace", "/tmp/agent-sandbox"]`。
2. 所有文件系统操作工具（读、写、删除、列表）在进行实际 I/O 前，校验目标路径是否落在白名单内。
3. 校验逻辑必须防止 **目录穿越**（`../`）和 **符号链接绕过**。
4. 实现要足够轻，能嵌入现有 MCP server 或脚本运行器，不影响正常性能。

下面以 TypeScript（Node.js）为例给出核心思路，同样的逻辑在 Python 或其他语言里也完全适用。

## 实现步骤

### 1. 白名单配置与路径规范化

白名单应当使用绝对路径，并在启动时完成规范化并存储：

```typescript
import path from "path";
import fs from "fs";

const RAW_WHITELIST = ["./workspace", "/tmp/agent-sandbox"];

// 启动时解析为绝对路径，并保留一份 realpath 版本用于符号链接校验
const WHITELIST_RESOLVED = RAW_WHITELIST.map(p => path.resolve(p));
const WHITELIST_REAL = WHITELIST_RESOLVED.map(p => fs.realpathSync(p));
```

这里同时保存 `resolve` 结果和 `realpath` 结果，后面处理符号链接时会用到。

### 2. 安全校验函数

核心是一个 `isPathSafe` 函数，接受用户传入的文件路径，返回布尔值或抛出具体拒绝原因。

```typescript
function isPathSafe(userInput: string): boolean {
  // 1. 基础规范化：绝对路径 + 解析 '.' 与 '..'
  const resolved = path.resolve(userInput);

  // 2. 直接检查：resolved 是否以任何一个白名单目录开头
  const directMatch = WHITELIST_RESOLVED.some(
    base => resolved.startsWith(base + path.sep) || resolved === base
  );
  if (directMatch) return true;

  // 3. 符号链接解析：用户可能通过软链接跳出白名单
  let real: string;
  try {
    real = fs.realpathSync(resolved);
  } catch {
    // 文件不存在时, realpathSync 可能抛错
    // 对于写操作，还需要检查父目录的 realpath。这里简化为先检查父目录。
    return isPathSafeForNonExistent(resolved);
  }

  return WHITELIST_REAL.some(
    base => real.startsWith(base + path.sep) || real === base
  );
}
```

对于尚不存在的文件路径（例如要创建的新文件），`realpathSync` 会失败。此时需要逐级向上查找最近存在的父目录，对其调用 `realpathSync`，并检查该真实路径是否在白名单内，同时保证剩余子路径部分不含 `..` 等手段。这部分代码稍长，但原理一致，可用 `path.dirname` 递归处理。

### 3. 集成到 MCP 工具

在 MCP server 的 `read_file`、`write_file` 等工具实现里，**第一行**就插入安全检查：

```typescript
server.setRequestHandler("tools/call", async (request) => {
  const { name, arguments: args } = request.params;
  
  if (name === "write_file") {
    const filePath = args.filePath;
    if (!isPathSafe(filePath)) {
      throw new Error(`Access denied: ${filePath} is not within allowed directories.`);
    }
    // ... 执行实际写操作
  }
  // 同理处理 read_file、list_directory 等
});
```

这样无论 Agent 如何构造参数，只要路径不在白名单内，操作就会在进入 I/O 前被阻断。

## 踩坑记录

在实际落地中，有几处容易忽略：

- **符号链接的真实身份**：白名单目录本身可能包含指向外部的符号链接，或者用户传入的路径中途经过符号链接。因此必须用 `realpathSync`（或 `fs.realpath`）得到物理路径再比对。
- **Windows 下的盘符与分隔符**：`C:` 与 `c:`、`\` 与 `/`。Node.js 的 `path.resolve` 会规范化分隔符，但盘符大小写仍可能不一致，建议在校验前统一转为小写。
- **容器挂载点差异**：如果脚本运行在容器内，白名单路径 `/app/workspace` 可能对应宿主机的 `/data/project`。这通常不影响安全性，但排查问题时要意识到报错路径与宿主机路径不一致。
- **文件夹遍历的遗漏**：除了单文件操作，`list_directory` 这类工具也需要受控，否则 Agent 可以遍历白名单内的目录结构，获取所有文件名后再逐个读取。如果业务上不希望暴露子目录结构，需要进一步限制列举能力或采用模糊化策略。
- **竞态条件**：检查通过到实际 I/O 之间存在时间窗口，恶意进程可能替换路径为符号链接（TOCTOU）。对大多数 Agent 内部脚本场景，这个风险可接受；高敏感环境可以考虑在操作前再次校验，或使用 `openat` 等避免中途切换的手段。

## 可复用的工程建议

- **抽离为安全文件系统层**：不要在每个工具里手写校验，封装一个 `SafeFileSystem` 类，暴露 `readFile`、`writeFile`、`readdir` 等方法，内部统一调用安全检查。这样新增文件操作不容易遗漏。
- **配置化白名单**：通过环境变量或配置文件注入白名单，避免硬编码。例如 `AGENT_FS_WHITELIST=/app/data,/tmp/sandbox`，便于在容器编排中调整。
- **与权限体系分层**：目录白名单是应用层的防御，底层仍建议配合操作系统用户权限（例如以非 root 运行）和容器挂载只读，构成纵深防御。
- **测试用例**：务必构造以下异常路径进行测试：`../../../etc/passwd`、指向外部的软链接、包含特殊字符的路径、不存在的文件路径、以及跨操作系统的边界情况。

## 总结

给自动化脚本加上本地目录白名单，本质上是为 Agent 的工具能力划定一条清晰的边界。实现不复杂，但需要严肃对待路径解析和符号链接。这套护栏可以和现有的 prompt-level 限制（如“只允许操作 workspace 下的文件”）相互补充，把安全约束真正落到执行层，而不是只靠自然语言保证。对于所有允许 Agent 触碰本地文件的实践者，这一步值得在第一个可用原型后就补上。
