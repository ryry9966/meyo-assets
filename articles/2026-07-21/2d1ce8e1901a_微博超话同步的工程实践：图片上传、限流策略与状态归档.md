## 背景

在做内容多平台分发时，经常需要将原创文章或动态同步到微博超话。相比普通微博，超话帖能获得更精准的曝光，但自动化同步会面临一系列工程问题：图片不能直接使用外链、接口频率限制严格、同步状态容易失控。基于 OpenClaw 的 Agent 与 MCP 工具，可以把这套同步流程封装成可复用的自动化逻辑。本文记录一次完整的落地过程，核心聚焦图片上传、限流处理和状态归档三个环节。

## 问题拆解

微博超话发布并非简单的文本提交，主要难点在于：

1. **图片必须上传至微博图床**：不能使用第三方图片链接，需要先通过 upload 接口换取 `pid`。
2. **限流非常敏感**：同一账号在短时间内的发帖、上传操作都会触发频率限制，返回错误码 `100000` 或 `100001`。
3. **状态管理缺失**：如果没有归档，重跑任务会导致重复发布，故障恢复后也无法判断哪些已成功。
4. **会话维持**：Cookie 有效期短，需要定期刷新，否则所有请求都会失效。

## 实现步骤

我们基于 Node.js 实现了一个 MCP 工具，对外暴露 `sync_to_chaohua` 方法，Agent 通过工具调用来触发同步。整体流程如下：

### 1. 认证维持

微博移动端 API 稳定性更高，采用扫码登录获取 `SUB` Cookie，并存储在本地文件。每次调用前检查 Cookie 是否过期（尝试访问用户信息接口），若失效则触发重登流程，通知用户扫码。

```ts
async ensureAuth() {
  const resp = await this.request('https://m.weibo.cn/api/config', { cookie: this.cookie });
  if (resp.data?.uid) return;
  // 触发扫码更新 cookie
  await this.qrLogin();
}
```

### 2. 图片上传

图片上传是耗时最长、也最容易出错的步骤。关键点：

- 使用 `multipart/form-data` 上传，字段名固定为 `st`。
- 请求头中必须携带 `Referer: https://m.weibo.cn/`，否则可能被拦截。
- 每个图片上传后返回 `pid` 和 `width/height`，保存下来用于发帖请求。

```ts
const form = new FormData();
form.append('st', imageBuffer, { filename: 'image.jpg', contentType: 'image/jpeg' });
const uploadResp = await fetch('https://m.weibo.cn/api/statuses/uploadPic', {
  method: 'POST',
  headers: { Referer: 'https://m.weibo.cn/', Cookie: this.cookie },
  body: form
});
const { pid } = uploadResp.data;
```

**踩坑点**：图片大小超过 5MB 或尺寸异常会导致上传失败，但接口不会明确提示，仅仅返回空 `pid`。因此在调用前需对图片做压缩和尺寸校验，限制在 1200px 以内，JPG 质量 85%。

### 3. 限流处理

微博接口限流表现为返回 `ok: 1` 但附带 `code: '100000'`（频率过快）或直接超时。我们使用**指数退避重试**策略：

- 首次重试延迟 2 秒，后续 4、8、16 秒，最多重试 3 次。
- 当错误码为 `100000` 时，额外等待 60 秒再重试，避免账号被短期 block。
- 所有 API 调用均通过统一请求函数，内置重试逻辑。

```ts
async requestWithRetry(url, options, retries = 3) {
  for (let i = 0; i < retries; i++) {
    const resp = await fetch(url, options);
    if (resp.status !== 200 || resp.data?.code !== '100000') return resp;
    const delay = Math.pow(2, i) * 1000 + (resp.data?.code === '100000' ? 60000 : 0);
    await sleep(delay);
  }
  throw new Error('Request failed after retries');
}
```

### 4. 发布超话帖

发布请求需要附带超话 ID 和 `pic_ids`（多个 pid 拼接）。文本中必须包含 `#超话名#`，否则会被视为普通微博，丢失超话入口。

```ts
const text = `${title} #${chaohuaName}# ${summary} ${link}`;
const body = new URLSearchParams({
  content: text,
  pic_ids: pids.join(','),
  visible: 0,
  containerid: `230283${chaohuaId}`
});
await this.request('https://m.weibo.cn/api/statuses/update', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: body.toString()
});
```

### 5. 状态归档

为避免重复发帖，我们使用 SQLite 记录每一条内容的同步状态。以内容唯一标识（如原文 URL 的 md5）为主键，字段包括：

- `resource_id`：内容标识
- `weibo_id`：发布成功后返回的微博 ID
- `status`：pending / success / failed
- `retry_count`：已重试次数
- `created_at` / `updated_at`

每次任务启动先查询归档表，跳过已成功条目；发布成功后更新 weibo_id 和状态。这样即使任务中断，恢复后也能准确续传。

## 踩坑实录

- **Cookie 复用**：从浏览器复制的 Cookie 可能在几分钟内失效，因为移动端 API 依赖 `SUB` 和 `SUBP`，而网页端的 `_s_tentry` 等字段不适合 API。建议完整保存扫码登录返回的所有 Set-Cookie。
- **图片 pic_ids 顺序**：多图时 `pic_ids` 的顺序必须与上传顺序一致，否则微博会显示错乱。
- **超话 containerid**：不是所有超话的 containerid 都符合 `230283xxxx` 规律，部分需要先通过搜索接口获取。懒得动态查询的话可以直接抓包拿到固定值。
- **#超话名# 空格**：如果文本中 `#超话名#` 前后没有空格，可能无法识别，建议前后加空格或换行。

## 可复用建议

在 OpenClaw 环境下，这套逻辑可以进一步封装为 **MCP Server**，提供 `sync_weibo_chaohua` 工具。Agent 只需传入文章标题、正文摘要、图片列表（buffer 或 URL）、超话名称，即可完成同步。此外：

- 增加**回调钩子**，在成功或失败后发送通知（如飞书、Discord）。
- 使用**队列**控制并发发帖，避免短时间大量请求触发硬限流。
- 将 Cookie 刷新逻辑作为 MCP 的独立工具，允许用户手动触发重新登录。

## 总结

围绕微博超话同步，我们通过图片上传预处理、指数退避限流策略和状态归档三个环节，构建了一条稳定可靠的自动化管线。结合 OpenClaw 的 Agent 生态，这条管线可以无缝接入内容分发工作流，把机械性的重复劳动转化为一个安静运行的工具。实践中遇到的坑大多集中在 Cookie 维护和请求参数的细节上，而这些正是自动化工程中最容易被忽视却决定成败的地方。
