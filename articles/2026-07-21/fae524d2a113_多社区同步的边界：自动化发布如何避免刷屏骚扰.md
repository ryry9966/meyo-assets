## 背景

在维护 OpenClaw 这类 Agent 项目的过程中，我同时运营着 Discord、Telegram、Twitter、微信公众号和知乎。为了提升效率，我搭建了一套基于 Agent + MCP 的自动化发布管线：一次编辑，就能把更新日志、使用技巧或公告推送到所有社区。

最初的版本很“直给”——Agent 拿到内容后立刻并行调用所有平台的发布接口。结果是什么呢？关注者如果在多个渠道关注了我，会在 5 秒内收到 4 条完全一样的推送。Discord 里有人直接留言“bot spam”，公众号掉粉，Twitter 上的互动率反而下降。那一刻我意识到：**自动化同步的边界，不是技术能不能发，而是社群体感能不能接受。**

这篇文章分享我在 OpenClaw 生态下，用 Agent 做多社区内容分发时，如何设计发布节奏、避免刷屏，同时保持工程上的可控与可观测。

## 问题拆解

刷屏的本质不是“发得多”，而是“同一内容在短时间内跨平台密集出现”。带来的后果：

- 用户被打扰，取关或静音
- 平台风控：公众号限流，Discord 触发 anti-spam，Twitter shadow ban
- 内容传播效果互相稀释

从工程角度看，需要解决三个核心问题：

1. **时序控制**：不同平台的发布时间错开，而不是并发推送。
2. **内容去重与变体**：并非每个平台都适合发完全一样的文案。
3. **异常熔断**：某一平台发布失败或限频时，不能拖垮整体流程，且要有清晰的恢复路径。

## 做法与步骤

我的发布管线基于 OpenClaw 的 Agent 框架，通过 MCP 工具封装了各平台的发布能力。整体架构分为三层：

### 1. 内容层：用指纹去重与变体生成

内容在进入队列前，会计算一个 `content_fingerprint`（取正文前 200 字符的 MD5 + 标题哈希）。Agent 会检查指纹在 `published_log` 中是否存在，防止人工重复提交或因 hook 导致的重复触发。

同时，为了让同一篇内容在不同平台有更好的适配，我让 Agent 根据平台生成微调版本（通过不同 system prompt 实现）：
- Twitter：提炼亮点，控制在 240 字符内，带图片
- Discord：保留 Markdown，强调社区互动语气，末尾加讨论链接
- 公众号：完整长文，排版优化
- Telegram：简洁带 URL 预览，无格式干扰

所有变体都挂载在同一 `content_group_id` 下，方便后续追踪。

### 2. 调度层：时间窗口与分组发布

这是避免刷屏的关键。我不使用“统一排期”，而是定义了一个**分组错峰策略**：

```
platform_groups = [
  { "group": "alpha", "platforms": ["twitter"], "delay_min": 0 },
  { "group": "beta",  "platforms": ["discord"], "delay_min": 15 },
  { "group": "gamma", "platforms": ["telegram"], "delay_min": 30 },
  { "group": "delta", "platforms": ["wechat_mp", "zhihu"], "delay_min": 60 }
]
```

Agent 将同一 `content_group_id` 下的内容入队时，会按 `group` 的顺序执行。每组发布完成后，等待指定间隔，再触发下一组。这样，**用户在短时间内最多只会在某一个渠道看到信息**，跨渠道的最密出现间隔也被拉长到 15 分钟以上。

实现上使用 Redis 的 `ZSET` 做延迟队列，Agent 轮询到期任务并调用 MCP 发布。这样即使 Agent 重启，任务也不会丢失。

### 3. 保障层：风控避让与可观测

每调用一次平台的 MCP 工具，我都会等待并检查返回中的速率限制信息（`X-RateLimit-Remaining` 等）。如果剩余量低于阈值，Agent 会自动推后该平台的发布队列 10–30 分钟。

熔断策略：同一平台连续失败 3 次，Agent 会将该平台标记为 `degraded`，后续任务挂起，并通过内部告警通知我人工介入。同时，已经发布成功的其他平台不受影响。

所有发布事件都落入结构化日志（平台、时间戳、内容指纹、状态），并用一个简单的 SQLite dashboard 做可视化，方便复盘发布节奏是否合理。

## 踩坑点

- **不同平台对 Markdown 的支持天差地别**：Telegram 的 MarkdownV2 需要转义特殊字符，Discord 可以接受多数 GFM，微信公众号的编辑器连 `##` 都要额外处理。MCP 封装时必须做 platform-specific 的渲染，否则内容变形。
- **公众号发布不是实时生效**：群发后实际推送可能有 1-3 分钟延迟，导致我一开始误判为发布失败。必须在 MCP 工具里做好状态轮询。
- **测试环境与生产环境隔离不足时，容易“真发”**：早期用同一个 bot token 测试调度逻辑，结果 Discord 测试频道收到了 20 条重复消息。后来严格区分 `ENV`，生产 MCP server 只在灰度通过后开启。
- **内容指纹过于严格会导致正常更新阻塞**：比如只是改一个错别字，重新发布时被去重逻辑拦截。解决方案是加入 `force` 参数，并在指纹计算时忽略空白和 URL trailing slash 差异。

## 可复用建议

- **分组延迟，而不是统一排期**：统一排期无法适应各平台不同的用户活跃时段。按相对间隔分组，更简单，也更容易移植到新项目。
- **把“发布”当作异步任务队列来对待**：不要用一次性脚本。用延迟队列 + 幂等消费，可以天然获得重试、可观测性和恢复能力。
- **给每个内容一个 `content_group_id`**：所有平台变体都挂在同一个组下，方便追踪整体发布状态，也便于将来做 A/B 标题测试。
- **保留手动 override 入口**：自动化到一定程度后，总会有“这期必须所有平台一起发”的特殊需求。设计一条快捷指令让 Agent 忽略分组延迟，走紧急发布通道，但要留下审计记录。

## 总结

多社区同步的自动化发布，真正要约束的不是内容本身，而是**时间维度上的打扰密度**。用 Agent 配合 MCP 做平台抽象后，加上简单的分组延迟队列，就能在“高效分发”和“尊重用户注意力”之间找到平衡。这套方案在 OpenClaw 的维护中已经平稳运行了三个多月，没有再收到过一次 spam 投诉。

如果你也在用 OpenClaw 做类似的跨社区运营，不妨从内容指纹和分组错峰这两步开始，成本很低，但体验改善非常明显。
