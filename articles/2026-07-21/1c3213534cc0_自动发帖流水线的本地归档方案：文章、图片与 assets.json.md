# 自动发帖流水线的本地归档方案：文章、图片与 assets.json

## 背景
在基于 Agent/MCP 的自动化内容发布实践中，一条常见的流水线是：AI 模型生成文章正文和配图，随后通过 API 或浏览器自动化发布到目标平台。很多同学初期只关心“能不能发出去”，忽略了产物本身的持久化——文章随手丢弃，图片链接失效，生成参数（prompt、模型、时间戳）消失在日志的海洋里。等需要复盘、迭代 prompt、或把老内容改成视频脚本时，才发现什么都没有留下。

于是就有了本地的归档需求：每一次批量生成，每篇文章及所附图片，连同生成时的元数据，都应该被持久化到文件系统，形成一个可回溯、可检索、可二次利用的资产库。

## 问题
别看“存一下”听起来简单，实际会面临几个工程问题：

1. **关联性**：一篇文章可能有多张图片，归档后必须能通过文件路径或清单明确对应关系。
2. **无覆盖**：多次生成可能使用相同的临时文件名，直接放进同一个 `images/` 目录容易互相覆盖。
3. **自描述**：不希望靠额外的数据库才能读懂归档；最好打开一个 JSON 文件就能知道这次生成了什么、用了什么参数、文章在哪。
4. **增量友好**：不同 batch 的归档应互不干扰，方便后续按日期或主题检索。
5. **与生成流解耦**：归档逻辑应作为流水线的最后一步，不侵入生成过程，方便任何 Agent/MCP 工具接入。

## 做法 / 步骤
### 1. 约定目录结构
以本次生成运行的时间戳作为 batch 名，建立如下结构：

```
archive/
└── run_2025-03-21_140522/
    ├── assets.json
    ├── posts/
    │   ├── post_001.md
    │   └── post_002.md
    └── images/
        ├── post_001_img1.png
        ├── post_001_img2.png
        └── post_002_img1.png
```

- `posts/` 存放 Markdown 文章，内部可以使用相对路径引用图片，例如 `![cover](./images/post_001_img1.png)`。
- `images/` 集中存放图片，文件名必须带上 `post_id` 前缀，避免不同文章间的文件名冲突。
- `assets.json` 是一个 JSON 数组，记录该 batch 下所有文章和图片的元数据。

### 2. assets.json 结构设计
```json
[
  {
    "post_id": "post_001",
    "title": "Your Post Title",
    "markdown_file": "posts/post_001.md",
    "images": [
      {
        "file": "images/post_001_img1.png",
        "prompt": "A minimalist illustration of...",
        "alt": "cover image"
      }
    ],
    "generated_at": "2025-03-21T14:05:22Z",
    "model": "gpt-4o",
    "tags": ["automation", "archive"],
    "status": "draft"
  }
]
```
`images` 字段直接保留了生成每张图片时使用的 prompt，方便日后分析 prompt 效果。`status` 可用于标记是否已发布、发布到了哪个平台。

### 3. 归档动作的实现
将归档封装为一个独立函数或 MCP 工具，在流水线的末尾调用。伪代码思路：

```python
def archive_batch(posts_metadata, base_dir="archive"):
    batch_dir = create_batch_dir(base_dir)
    assets = []
    for post in posts_metadata:
        post_id = generate_unique_id()        # 如 post_001
        md_path = save_markdown(post.content, batch_dir, post_id)
        img_records = save_images(post.images, batch_dir, post_id)
        assets.append({
            "post_id": post_id,
            "title": post.title,
            "markdown_file": str(md_path.relative_to(batch_dir)),
            "images": img_records,
            "generated_at": datetime.utcnow().isoformat(),
            "model": post.model,
            "tags": post.tags,
            "status": "draft"
        })
    write_json(batch_dir / "assets.json", assets)
```

### 4. 在 OpenClaw / Agent 中集成
- 若使用 OpenClaw 的 Action 机制，可将上述函数暴露为一个 HTTP 或本地调用的 Action，在文章+图片生成完毕后触发。
- 若已接入 MCP 工具，可将归档脚本封装成 `archive_posts` 工具，接收文章列表和图片路径列表即可。
- 不论哪种方式，建议归档步骤只负责「写入文件」，不负责生成逻辑。

## 踩坑点
1. **图片覆盖**：不加 `post_id` 前缀直接将 `img1.png` 丢进 `images/` 是常见翻车现场。解决：文件名形如 `{post_id}_img{index}.png`。
2. **Markdown 相对路径失效**：部分编辑器或静态站点生成器在移动 `posts/` 文件后，图片相对路径会断掉。方案：在 `assets.json` 额外记录图片相对于 batch 根目录的路径，程序读取时用 `assets.json` 中的路径来定位图片，而不是让 Markdown 自己生扛所有移动。
3. **`assets.json` 写入原子性**：同时写入可能产生损坏。通常归档是单线程顺序执行，问题不大。若有多 Agent 并发同一个 batch，可在写入前使用文件锁或直接限制为单 worker 操作。
4. **批次命名兼容性**：Windows 不允许文件名含冒号，时间戳使用 `2025-03-21_140522` 格式而非 `14:05:22`。
5. **图片体积膨胀**：如果不对图片做 resize 或压缩，几轮 batch 下来磁盘占用会很可观。可在归档前统一将图片转为 WebP 或限制长边分辨率。

## 可复用建议
- 将归档逻辑做成一个标准 Python 脚本或 Docker 镜像，通过环境变量或参数接收目标目录，避免与具体项目强绑定。
- 在 `assets.json` 中预留 `published_to` 字段，发布成功后回写发布平台和发布时间，实现本地状态同步。
- 可以基于 archive 目录快速开发一个本地查询工具：如 `python archive_cli.py --tag automation --status draft`，列出所有待发布的草稿。
- 若要升级为可搜索的知识库，可以定期将 `assets.json` 的内容同步到 SQLite 或全文检索引擎，但文件层面的归档始终是基础。

## 总结
这套方案通过“**时间戳批次目录 + 带前缀文件名 + assets.json 清单**”三个约定，低成本地解决了自动发帖流水线中文章、图片和生成元数据的本地归档问题。它不依赖数据库，不绑定特定工具，适合个人开发者和小团队在 Agent/MCP/OpenClaw 的自动化实践中快速落地。把每一条生成记录都留住，你会在复盘 prompt 调优、内容二次创作时感谢现在的自己。
