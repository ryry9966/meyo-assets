## 背景

我们在维护一个内容分发 Agent，核心职责是把指定平台的内容同步到多个社交媒体。其中微博超话是高频目标渠道——它拥有垂直受众、话题聚合和长尾曝光优势。但超话的发布并非开放 API 直接支持，且图片上传、限流逻辑与普通微博有差异。手动转发效率低、容易遗漏，因此需要一套可靠的自动化同步链路。

在这个场景中，Agent 基于 OpenClaw 的插件机制与自定义 MCP 工具实现：定时拉取源内容，经过格式适配后推送到微博超话，并记录每一次发布状态用于事后核对与补发。

本文记录实际落地过程中遇到的三个典型问题及其解决路径：图片上传失败、被限流、以及缺乏可追溯的状态归档机制。

## 问题拆解

初次运行时，Agent 能完成基本文本发布，但在图片环节频繁折戟，且几次触发微博反爬/限流导致账号被短暂限制。更大的隐患在于：没有系统记录每次任务的结果，出问题后只能人工排查，完全违背自动化初衷。

整理下来，核心是三个工程问题：

1. **图片上传不稳定**：微博对超话图片的格式、尺寸、体积和上传接口有隐性约束，稍有不符就返回模糊错误，甚至无报错但图片缺省。
2. **限流难以捉摸**：无论是 Web 端操作频率还是单日发布总量，实际阈值都比公开文档更严格，且限流后无明确提示，仅表现为发布“转圈”或超时。
3. **状态不可见**：任务执行完即消失，成功、失败、限流等待等状态无法追溯，导致难以评估同步质量和及时补发。

## 实践步骤

### 1. 构建可观测的发布管线

为每个同步任务生成唯一 `task_id`，并设计状态机：`pending -> processing -> success/failed/rate_limited`。所有状态变更写入本地 SQLite，同时输出结构化日志（JSON Lines），方便对接现有监控告警。

Agent 发布前创建任务记录，发布后根据结果更新状态和错误原因。对于 `rate_limited` 状态，额外记录下次可重试的时间窗口。

### 2. 图片预处理器：解决上传兼容性

微博超话图片上传接口对格式要求比想象中严格，我们踩到的坑包括：

- 非 JPEG/PNG 格式（例如 WebP）会被静默丢弃。
- 尺寸超过 4096px 可能导致超时，但不会返回明确错误。
- 体积过大（>10MB）直接上传失败，且错误码不精准。

解法是在 Agent 上传前强制走一遍预处理 pipeline：

- 统一转换为 JPEG，质量为 85（保证清晰度与体积平衡）。
- 长边缩放至 2048px，使用 Lanczos 算法。
- 若处理后仍超过 8MB，降质量至 75 或切换到 PNG8。
- 计算 MD5 作为图片指纹，避免重复上传浪费资源。

这步实现为一个 MCP 工具 `image_preprocess`，OpenClaw 插件直接调用。

### 3. 限流规避：令牌桶 + 主动休眠

微博超话的限流模型可近似为：单账号每分钟最多 3 次发帖操作，单日上限约 30~50 条超话帖（浮动）。硬撞会触发不可见封锁，表现为请求返回空数据或长期挂起。

工程上我们采用两级控制：

- **本地令牌桶**：每分钟补充 3 个令牌，发布消耗 1 个，无令牌则等待。使用 Redis `INCR` + TTL 实现，方便多进程共享，但单机直接用 `token-bucket` 库即可。
- **发布后随机退避**：每次成功发布后 `sleep(2~5)` 秒，降低时序特征。
- **分段发布**：单次运行最高处理 5 个任务，超出留到下个调度周期，防止连续命中限流。

当遇到疑似限流（例如请求超时或返回特定错误码），Agent 不再重试，而是把任务标记为 `rate_limited`，并设定 15 分钟冷却时间。避免无意义重试加剧封禁。

### 4. 超话选择与校验

微博超话 ID 并非固定不变，且不同超话的发帖权限、格式要求有差异。我们维护一个配置文件，存储可用的超话名称、ID、发帖权限标记，并在任务执行前做校验。如果超话不存在或无权，直接标记为 `failed`，记录原因。

## 踩坑记录

- **图片 EXIF 方向**：有些来源图片 EXIF Orientation 非 1，处理后上传仍可能旋转错乱。必须在预处理阶段读取并旋转到位，再转换 JPEG。
- **图文混排时文字被截断**：微博正文长度限制对超话帖子更严格（约 1000 字），且若包含话题词，话题不计入字数但会占用“视觉长度”。我们采用 `text_truncate` 工具按字节计算，留出 50 字余量。
- **限流的假象**：有时发布成功但微博未立即展示，是因为超话审核队列延迟，并非失败。我们设置 10 分钟后回调检查任务状态，通过搜索含 `task_id` 的帖子确认是否真正上线。
- **Cookie 持久化**：使用 Web 自动化时，微博 Cookie 过期时间不稳定。采用 Playwright 持久化浏览器上下文，并在每次任务开始前验证登录态，过期则触发人工介入或自动刷新。

## 可复用建议

- **状态机 + 归档是自动化基石**：哪怕只有两种状态，也要落地，否则无法排障。
- **图片预处理做成独立工具**：不要耦合在发布逻辑里，方便复用和单独测试。
- **令牌桶优于固定延迟**：能适应不同调度频率，最大化利用配额。
- **保留原始错误快照**：在任务记录中存储完整错误响应和上下文，方便事后分析阈值变化。
- **监控要关注“无状态”的失败**：如转圈、超时，这类失败不会返回错误码，需要上层的超时探测器。

## 总结

微博超话同步看似是一个简单的自动化发布任务，实际上包含图片兼容性、反爬限流、状态管理等工程化细节。通过构建清晰的状态模型、图片预处理 pipeline 和令牌桶限流控制，我们将同步成功率从最初的 67% 提升到 98% 以上，且问题可追溯、可回溯。

对于 OpenClaw 社区的用户，这一实践证明了：即使是非开放 API 的渠道，通过 MCP 工具化的方式将共性操作封装成服务，再配合 Agent 调度，也能实现稳定、可控的自动化。
