## 背景

多平台内容分发是很多创作者的刚需，超话作为微博的垂直社区，同步博客、视频更新能够保持账号活跃。手工搬运效率低、易遗漏，我们基于 OpenClaw 的自动化能力搭建了一套超话同步流程，把“取源 → 上传图片 → 发帖 → 归档”串成可靠管线。运行大半年后，沉淀了一些绕不开的工程细节，集中在图片上传规程、接口限流和状态归档三个方面。本文以实际踩坑视角还原这些问题的解决过程，供同样在 OpenClaw/Agent/MCP 框架下做内容分发的同学参考。

## 问题拆解

超话同步看似只是发一条带图微博，但拆开后至少要解决四个子问题：

1. **图片必须先上传到微博图床**，得到 `pid` 才能引用。直接使用外链图片无法被超话认领，且会被降权。
2. **发帖接口强制要求登录态**，且超话需作为参数嵌入，同时文本必须包含 `#超话名称#` 前缀。
3. **严苛的限流和风控**。不仅接口有频率上限，短时间内大量发文或图片内容异常会触发图形验证码甚至临时冻结。
4. **可靠的状态归档**。任务可能被中断、重试，必须保证同一篇源内容不被重复同步，并能回溯每次同步的成败。

如果只写一次性脚本，遇到验证码或 403 就中断，后续手工补发，完全没有工程价值。我们希望它在 OpenClaw 中作为常驻 Agent 运行，容忍波动，可观测、可恢复。

## 做法与步骤

### 1. 图片上传：稳定获取 `pid`

微博图片上传接口需要 `multipart/form-data` 提交二进制流，并且依赖有效的 cookie。我们实践中的稳定路径是：

- **压缩前置**：在 Agent 节点内先对图片进行重编码，统一转为 JPEG，长边不超过 1920px，体积控制在 3MB 以内。大量案例表明超过 5MB 的图片上传后会被静默压缩成低质量版本，颜色偏移严重，影响阅读。
- **接口选择**：使用 `picupload.service.weibo.com` 的旧版上传，因为它对 cookie 和 UA 的校验相对宽松，只需携带合法登录态即可稳定返回 `pid`。
- **容错重试**：上传如果返回 `{"code":"-200"}`（临时错误），等待 5s 后重试，最多 3 次。如果连续失败，则将图片转为 Base64 存入归档，等待人工介入。

上传成功后得到一个类似 `007uGZyXly1hx...` 的 `pid`，后续发帖时带上即可。

### 2. 发帖与超话嵌入

发帖接口构造时必须在文本最前面拼接 `#超话名#`，并且传入 `topic_id` 参数。如果仅靠文本中的 `#` 标签，超话页未必能正常收录。

同时，携带 `pic_id` 参数引用刚才上传的 `pid`。注意一次最多传 9 张图，超出需拆为多条微博。OpenClaw 的任务节点会对源内容进行分片，自动生成多条发帖任务。

### 3. 限流策略：退避 + 身份切换

最烦人的是限流。我们观察到两类限制：

- **接口级限流**：同一账号短时间连续调用发帖接口，约 5 次/小时后开始返回 `{"code":"10024"}` 或 `“发布过于频繁”`。我们的应对策略是在发帖节点前后强制加入随机延迟（8~15 秒），并且在遇到 10024 错误时暂停队列 30 分钟，同时通过通知通道提醒。
- **账号级风控**：图片内容被算法判定为营销图、二维码过多时，直接跳验证码。验证码无法自动过，只能触发人工打断。为了降低触发概率，我们会随机变换图片的 MD5（添加隐写噪声），并在上传前剔除过大的纯色区域，让图片看起来更“原生态”。

另外，为了容量我们维护了多个账号的 cookie 池。OpenClaw 的流程会根据账号的历史配额分配任务，并在主账号触发风控后自动切换备号，避免整体停滞。

### 4. 状态归档与幂等

我们使用 SQLite 维护一张 `sync_log` 表，核心字段：

- `source_id`：源内容唯一标识（如博客文章 ID 或短视频哈希）。
- `weibo_mid`：发帖成功后微博返回的 `mid`。
- `status`：`pending` / `success` / `failed`。
- `retries`：已重试次数。
- `extra`：JSON 字段存放错误码、pid、异常截图 URL 等。

每条发帖任务启动前，先查询 `source_id` 是否已有 `success` 记录，保证幂等。如果任务异常退出，重试时只会处理 `pending` 或 `failed` 次数未超阈值（比如 5 次）的记录。这样归档数据库既是状态机也是审计日志，出现漏发时能迅速定位。

## 踩坑与应对

- **图片上传耗时不稳定**：网络波动导致上传时间可能超过 20 秒，OpenClaw 默认 HTTP 客户端超时需调大至 60 秒，并开启 gzip。
- **超时重试导致重复上传**：上传节点在未收到响应时重试，可能产生多个 `pid`。解决方案是为每次上传先生成唯一 `upload_id`，写入任务上下文，服务端通过日志去重；同时发帖节点只使用最新一个 `pid`，旧的会自动被回收。
- **状态归档与真实微博状态不一致**：有时发帖接口返回成功，但微博实际被秒删（anti-spam）。我们在发帖成功后新增一个延迟检查节点（30 分钟后查询微博是否可访问），若不可访问则把 `status` 改为 `failed` 并告警。这个异步校验大大提高了数据可信度。
- **验证码无法自动处理**：坦率说，这是目前最大的瓶颈。当账号触发图形验证码时，Agent 会将该账号标记为 `locked`，并通知人去解封，24 小时内不再分配任务。

## 可复用建议

如果你也在 OpenClaw 上构建内容分发 Agent，下面几点或许能借鉴：

- **将上传和发帖解耦**：作为独立的 OpenClaw 节点或 MCP 服务，方便单独调试和替换。图片上传节点可以输出标准化 `pid` 列表，供下游任何发布任务使用。
- **限流组件化**：封装一个 `RateLimiter` 插件，支持令牌桶或延迟队列，输入错误码自动级联退避。和 OpenClaw 的 Task 模型结合，轻松实现“任务暂停/恢复”。
- **必做幂等与可观测**：每个同步环节都写入状态归档，接入可视化面板（哪怕只是 SQL 查询），解放记忆力。
- **日常维护不能自动化**：定期清理 cookie、更新 UA、更换 IP 出口仍是必须的手动作业。不要妄图全自动对抗平台反作弊，工程上的妥协才是长期稳定运行的前提。

## 总结

微博超话同步不是“调通一个 API”的一锤子买卖，而是一个持续对抗限制、保证数据一致性的小系统工程。用 OpenClaw 可以较好地结构化这个过程：图片上传定制节点、退避队列、状态机归档、多账号调度都可以作为独立可复用的能力组件沉淀下来。希望这些真实踩坑记录和应对方案，能为你的自动化内容分发带来一些落地参考。
