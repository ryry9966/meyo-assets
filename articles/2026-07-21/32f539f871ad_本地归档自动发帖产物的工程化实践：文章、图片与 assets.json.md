## 背景

在以 OpenClaw、MCP Server 或自定义 Agent 驱动的自动发帖流水线中，每一条内容通常由多个资产组成：Markdown 原文、本地引用的图片（可能由 DALL·E、Stable Diffusion 等生成）、以及发布后的平台链接、时间戳、状态等信息。如果流水线直接推送到远程平台后不做本地归档，几天后想回查「当初生成的那张图到底长什么样」「发布时的 prompt 是什么」就会变得非常困难。

尤其当流水线集成了多种 MCP 工具（如图片生成、网页抓取、SEO 检查）时，一次发帖可能联动多个外部服务，任何远端数据丢失或 API 变更都可能导致历史记录无法追溯。因此，建立一套可复现、可审计的本地归档机制，是工程化发帖流水线的重要一环。

## 问题拆解

本地归档需要解决以下核心问题：

1. **资产离散**：文章文本、多张图片、生成参数分散在不同工具的返回结果中，没有统一的收集点。
2. **元数据孤岛**：发布状态、平台 ID、发布时间等元数据仅存在于发布工具的日志或远端，无法和本地文件一一对应。
3. **文件重名与版本覆盖**：同一标题的帖子可能多次重写或重新生成图片，若直接按标题保存文件，后一次会覆盖前一次。
4. **归档索引**：当帖子积累到上百条后，单纯依赖文件系统翻阅会很痛苦，需要结构化索引文件。
5. **跨环境可移植**：流水线可能在本地开发、容器、CI/CD 中运行，归档路径必须可配置、不依赖绝对路径。

## 做法与步骤

我们设计了一套轻量的本地归档方案，核心是一份 `assets.json` 索引文件，配合以时间戳命名的目录存放文章与图片。

### 1. 目录结构约定

```
archives/
  ├── 2025-04-01_090101_hello-world/
  │   ├── post.md
  │   ├── images/
  │   │   ├── cover.png
  │   │   └── chart.png
  │   └── assets.json
  └── 2025-04-01_090101_hello-world_rerun/
      ├── post.md
      ├── images/
      │   └── cover_v2.png
      └── assets.json
```

目录名采用 `{YYYY-MM-DD}_{HHMMSS}_{slug}`，slug 从标题或主题中生成，避免重名时追加后缀。每一次生成（或一次完整的发布会话）对应一个独立目录，即使内容标题相同，也不会互相覆盖。

### 2. 收集资产与写入 assets.json

在发帖流水线的最后一环（或通过 MCP 工具封装一个「归档器」），将以下内容写入该会话的 `assets.json`：

```json
{
  "session_id": "2025-04-01_090101_hello-world",
  "created_at": "2025-04-01T09:01:01Z",
  "post": {
    "title": "自动发帖流水线如何做本地归档",
    "content_file": "post.md",
    "prompt": "...",        // 原始生成 prompt，可选
    "tags": ["automation", "archive"]
  },
  "images": [
    {
      "file": "images/cover.png",
      "prompt": "a tech knowledge card, ...",
      "generator": "dalle3"
    }
  ],
  "publish": {
    "platform": "openclaw-cn",
    "status": "published",
    "url": "https://...",
    "published_at": "2025-04-01T09:05:00Z"
  }
}
```

关键字段说明：
- `session_id` 与目录名保持一致，方便反查。
- `content_file` 指向同目录下的 Markdown 原文，不作嵌入，保持文件独立。
- 图片列表记录文件名、生成 prompt 及模型，便于后续审计图片来源。
- `publish` 部分在发布成功后由发布插件回填，如果发布失败则该对象记录失败原因。

### 3. 流水线集成

以 MCP 工具链为例，假设我们用 `mcp-server-markdown` 生成文章，`mcp-server-image-gen` 生成配图，最后使用一个自定义 MCP 工具 `mcp-archiver` 完成归档：

1. 生成文章后，将 Markdown 内容和标题暂存。
2. 提取文章中引用的本地图片相对路径，调用图片生成工具，将图片保存到当前会话的 `images/` 目录。
3. 调用 `mcp-archiver`，传入标题、内容文件路径、图片列表、生成参数，该工具负责创建会话目录、复制/移动文件、写入 `assets.json` 并返回归档路径。
4. 发布成功后，再调用 archiver 工具的更新接口，回填发布状态和 URL（或直接在流水线脚本中修改 `assets.json`）。

如果手头没有现成的 MCP 工具，用一段 Node.js/Python 脚本封装同样简单可靠。关键是**归档动作必须作为流水线的一个固定步骤**，不允许跳过。

## 踩坑点

### 1. 文件命名与字符编码
图片文件名如果来自用户 prompt 截断，可能包含空格、Unicode 或特殊字符。建议对文件名做 slugify 处理，统一使用小写字母、数字、连字符，避免跨平台问题。Markdown 文件统一用 UTF-8 无 BOM。

### 2. 大文件与并发写入
当图片生成较多（如10张以上）且每张几 MB 时，不要在归档步骤中做 Base64 内联到 JSON 内，否则 `assets.json` 会迅速膨胀到无法阅读。始终保持文件外置，索引只记录路径。

并发发布多条帖子时必须保证每个会话目录独立创建，用原子操作（如 `mkdir -p` 或 `fs.mkdirSync` 配合异常捕获）避免冲突。

### 3. 路径规范化
归档路径中如果使用了绝对路径，切换到容器或 CI 环境后会失效。因此 `assets.json` 中的所有文件路径必须以 `session_id` 为基准的相对路径，整个归档目录可整体移动。

### 4. 重复生成导致覆盖
如前面所述，重名目录会覆盖。实践中的一个隐蔽坑点是：流水线失败后快速重试，时间戳精确到秒仍然可能相同，slug 又一样。解决方案是：`slug` 使用高精度的毫秒或随机短码，或者检测目录已存在时自动追加 `_1`、`_2`。

## 可复用建议

- **内容哈希去重**：为每篇 Markdown 正文计算 SHA256，写入 `assets.json`。后期可以用脚本检测不同 `session_id` 下哈希相同的帖子，快速排查重复生成。
- **分级索引**：当归档目录数量超过 200 个时，在 `archives/` 根目录维护一个汇总 `index.json`，由 cron 任务或归档步骤自动更新，方便全局搜索。
- **配合 Git 做版本管理**：将归档目录纳入 Git 仓库（注意`.gitignore` 忽略大图片的二进制，可改用 Git LFS），实现天然的改版历史与异地备份。
- **最小化元数据**：`assets.json` 不要试图记录所有中间步骤，保持精简。额外调试信息可另存 `debug.log`，避免索引文件过于混乱。
- **回滚与重新发布**：归档允许你以文件形式恢复过往的任意版本。可以写一个脚本，读取某个 `session_id` 下的 `post.md` 和 `images/`，直接重新调用发布工具，实现一键回滚或跨平台转载。

## 总结

自动发帖流水线如果只考虑「生成」和「发布」，就忽略了工程化里最可靠的资产溯源环节。通过约定式目录结构、一份结构化的 `assets.json` 索引，以及将归档动作固化为流水线的必执行步骤，我们可以把每一篇帖子变成一组独立、可复现、可迁移的文件集合。这种做法不复杂，没有额外服务依赖，只是用最普通的文件系统承担了审计和灾备的职责。

后续还可以基于归档数据构建简单的本地看板，统计生成量、平台发布成功率，或作为 OpenClaw 社区内共享数据集的基础——这些扩展都建立在扎实的本地归档之上了。
