## 背景：内容资产的“黑盒”问题

在基于 OpenClaw/Agent/MCP 构建的自动发帖流水线中，一次典型的运行路径是：提示词触发 → 大模型生成 Markdown 正文 → 图片生成或匹配 → 通过 MCP 服务器发布到目标平台。这条链路上产出的文章和视觉素材，一旦发布完成，很容易就散落在平台缓存、临时目录或远程 CDN 里。运营一段时间后，想回溯某篇稿件的原始版本、配图原图、生成参数，往往只能翻日志或者去平台后台捞——既低效又不可靠。

更深层的问题在于：自动化发布意味着内容被“推送出去”之后，本地很可能 **没有留存全部资产**。图片可能只以 URL 形式存在于最终正文中，而源文件并未落盘；文章生成所用的 prompt、模型、时间戳等元信息也随着上下文切换而丢失。这导致两个典型痛点：

1. **不可复现**：想重发、微调或审计某篇稿子时，找不到确切原始内容。
2. **素材难复用**：配图散落各处，难以迁移到其他平台或二次加工。

因此，在流水线中嵌入一个 **本地归档** 环节，将所有产出物原子化保存，是一项低投入、高回报的工程优化。本文将分享我们围绕 OpenClaw 插件和 MCP 工具打磨出的一套归档方案，聚焦于文章、图片与 `assets.json` 的协同管理。

## 问题拆解：归档需要解决什么

如果只是把生成结果存一个文件，那算不上方案。真正可用的本地归档需要回答这几个问题：

- 文章本身用什么格式存储？如何保证在本地查看时图片仍可渲染？
- 图片源可能来自生成器返回的 base64、临时下载链接或者图床 CDN，如何统一本地化？
- 一次发布可能涉及多篇帖子、多张图，如何组织目录和命名，避免冲突？
- 如何记录元数据（prompt、模型、生成时间、发布状态、原始 URL 等），方便检索和审计？
- 归档操作的触发时机是什么？如何与现有流水线低耦合集成？

下面给出我们经过验证的实践做法。

## 做法与步骤：三层归档结构

### 1. 目录与文件规范

以一篇自动生成的文章为单位，归档目录结构如下：

```
archives/
└── 2025/
    └── 03/
        └── my-first-auto-post/
            ├── index.md
            ├── images/
            │   ├── cover.png
            │   └── diagram-01.png
            └── assets.json
```

- **按年月 / slug 分层**：避免单个目录下文件爆炸，便于按时间范围批量操作。
- **`index.md`**：存放文章正文，内部图片引用改为 **相对路径**，例如 `./images/cover.png`。
- **`images/`**：存放所有配图原始文件，保持原始格式（png/jpg/webp），不二次压缩。
- **`assets.json`**：一份结构化元数据清单，细节见下节。

### 2. assets.json 设计

`assets.json` 是归档的索引核心，我们建议至少包含以下字段：

```json
{
  "slug": "my-first-auto-post",
  "title": "自动发帖流水线的本地归档方案",
  "created_at": "2025-03-30T10:15:00Z",
  "generation": {
    "model": "gpt-4o",
    "prompt": "写一篇关于本地归档的技术帖……",
    "params": { "temperature": 0.7 }
  },
  "publish": {
    "platform": "wordpress",
    "url": "https://example.com/post-123",
    "status": "published",
    "published_at": "2025-03-30T10:20:00Z"
  },
  "assets": {
    "images": [
      {
        "local_path": "images/cover.png",
        "remote_url": "https://cdn.example.com/abc123.png",
        "original_name": "generated_cover_0.png",
        "size": 245760,
        "sha256": "e3b0c44..."
      }
    ]
  }
}
```

这个文件的几点设计思想：

- **生成溯源**：记录 prompt 与模型参数，方便复盘生成质量。
- **平台发布信息**：保存发布后的 URL 和时间，便于与平台侧数据对账。
- **素材映射**：`assets.images` 数组记录了每张图片的本地路径、原始远程 URL 以及哈希值，既可检查文件完整性，也能在需要时重新上传到其他图床。
- 后期可扩展视频、音频等资产类型，结构不变。

### 3. 归档操作的工程实现

我们将其封装为一个 MCP 工具（也可用普通脚本），在流水线发布成功后调用。伪代码逻辑如下：

1. 接收文章内容（Markdown 字符串）、图片映射表（URL → 本地临时文件路径或 base64）以及元信息。
2. 创建归档目录 `archives/{year}/{month}/{slug}/`。
3. 遍历图片映射：
   - 如果是远程 URL 且尚未下载，使用 `curl` 或 `fetch` 下载至 `images/`，带重试和超时控制。
   - 如果已经是本地二进制文件，直接复制，并计算 SHA256。
   - 如果来源是 base64 字符串，解码后写入文件。
4. 替换文章正文中的图片链接为相对路径 `./images/xxx`。
5. 将处理后的 Markdown 写入 `index.md`。
6. 组装 `assets.json` 并写入目录。
7. 可选：将整个归档目录纳入 Git 仓库，执行 `git add` 与 `commit`。

对于 OpenClaw 插件用户，可以在 Agent 的 Tool 定义中增加 `archive_post` 工具，由 LLM 根据发布结果自行决定调用时机，实现完全自动化。

## 踩坑点与对策

在实际落地中，我们踩过几个坑，总结如下：

- **图片下载的时效性与稳定性**  
  如果图片 URL 是临时签名地址（例如某些生成图 API 返回的预签名 URL），可能在几分钟内失效。所以归档必须 **紧跟在生成之后**，不能延迟。脚本需加入重试机制（最多 3 次，指数退避），并在失败时记录告警，避免部分图片缺失。

- **重复图片导致存储膨胀**  
  多篇文章可能复用同一张品牌图或通用插图。直接每篇都拷贝一份会浪费磁盘。可引入 **内容寻址去重**：在归档前计算文件 SHA256，与全局存储库（如 `shared-images/`）比对，若已存在则仅创建硬链接或软链接，并在 `assets.json` 中保留引用计数。如果不想引入复杂度，可以先承受少许冗余，等规模上来再优化。

- **特殊字符导致的文件名与路径问题**  
  slug 生成应严格过滤，只保留小写字母、数字和连字符；图片文件名统一重命名为 `{role}-{index}.{ext}`，避免空格、中文、特殊符号。

- **相对路径与 Markdown 渲染器差异**  
  某些本地 Markdown 预览工具对 `./images/x.png` 和 `images/x.png` 的支持不一致，统一采用 `./images/` 前缀，兼容性最好。如果后续要从本地直接发布到支持相对路径的平台，直接用这个文件即可。

- **Git 与二进制文件**  
  如果使用 Git 归档，图片频繁变更会使仓库急速膨胀。建议对大仓库启用 Git LFS，或只将 `index.md` 和 `assets.json` 纳入版本控制，而将 `images/` 目录通过对象存储或本地文件系统备份管理。

## 可复用建议

这套归档思路可以快速移植到不同技术栈：

1. **独立脚本版本**：提供一个 Node.js 或 Python 脚本，接受命令行参数（`--content-file`, `--images-dir`, `--output-dir`），方便非 OpenClaw 环境也能使用。
2. **MCP Server 封装**：将归档功能实现为一个 MCP 工具，暴露 `archive` action，任何支持 MCP 的 Agent 都可以直接调用，进一步降低集成门槛。
3. **模板化 assets.json**：提供 JSON Schema 和生成模板，社区可以按需扩展字段，比如增加 SEO 关键词、标签、多语言版本等。
4. **与现有管道组合**：比如结合 `puppeteer` 生成文章截图，一并归档；或者通过 `rclone` 将归档目录同步到云端备份。

建议将归档步骤作为发帖流水线的 **“最后一步”**，并且设计为 **幂等操作**——如果目标目录已存在同 slug 归档，则跳过或根据策略覆盖，便于重复调试。

## 总结

本地归档看起来是一件“小事”，但它让自动发帖流水线从一个内容喷射器变成了一个可审计、可复盘、可迁移的内容资产管理器。通过 `index.md` 保存正文、`images/` 本地化所有配图、`assets.json` 记录结构化元数据，我们获得了：

- **完整的资产视图**：不用在各种平台之间跳转，一个本地目录就能看到某篇文章的全部细节。
- **工程可演进性**：后续如果要迁移发布平台、重新生成 SEO 元数据或者训练模型，都可以直接从归档中批量读取。
- **审计与合规**：所有自动生成的内容都有据可查，方便对外解释或内部复盘。

对于 OpenClaw 社区用户，我们鼓励大家在自己的 Agent 工作流中加入这样一个小环节，投入成本极低，而长期收益显著。代码与示例配置可以在社区仓库中找到，也欢迎贡献更通用的归档 MCP 工具。
