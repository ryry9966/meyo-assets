## 背景

在 OpenClaw、各种 Agent 框架以及 MCP 工具链里，“让脚本自动操作文件”几乎是标配需求。无论是处理上传的附件、生成报告，还是执行本地数据清洗，自动化脚本总是需要触碰文件系统。但直接给脚本整个文件系统的读写权限，无异于把房子钥匙交给一个随时可能会被注入提示词的实习生。数据泄露、关键配置被误删、攻击者通过脚本横向移动——这些不是假设，是我们在内部测试中反复碰到的问题。

容器和虚拟化确实能治本，但很多时候我们要的就是“轻量”：一个几十行的 Python 脚本，通过 MCP 服务器调用，不希望为了它去拖一个 Docker 运行时。于是我们开始尝试一种更务实的方案：在脚本进程内部，构建一个**本地目录白名单**，只允许代码在预设的路径下进行文件 I/O。

## 问题的切面

真正动手时你会发现，文件访问控制比直觉复杂得多：

- 内置的 `open()`、`os.open()`、`pathlib.Path` 都能读写文件；
- 很多第三方库内部会读自己的配置文件、写缓存，一不小心白名单就误杀了依赖；
- 符号链接、相对路径、当前工作目录变化，都会让简单的路径前缀匹配失效；
- 还要考虑性能：对每次 I/O 都做全路径解析和比对，会不会拖慢数据密集型任务？

我们的目标是在不改动原始脚本业务逻辑的前提下，以近乎零侵入的方式插入护栏逻辑，并且要对开发者透明——出问题时能快速定位是护栏拦截，还是业务本身错误。

## 实现步骤与设计

我们选择在 Python 环境中实现，因为 OpenClaw 生态里 Python 脚本占比极高。方案思路很直接：**在脚本运行前，通过 sitecustomize 或显式 import，把内置的文件操作函数替换成带检查逻辑的版本**。

### 1. 白名单定义

用一个 YAML 配置文件，例如 `fileguard.yml`：

```yaml
allowed_paths:
  - /data/workspace/uploads
  - /tmp/agent-cache
exempt_modules:        # 这些模块的文件操作不拦截
  - tmpfile
  - PIL.Image
log_level: debug
```

路径统一使用绝对路径，并且在加载时立即调用 `os.path.realpath()` 规范化，确保后续比较用的是真实路径。

### 2. 核心钩子模块

写一个 `fileguard.py`，要点如下：

- 维护一个全局 `_ALLOWED_REAL_PREFIXES` 列表。
- 实现一个 `_check_path(path, mode)` 函数：
  1. 将传入路径用 `os.path.abspath()` + `os.path.realpath()` 解析为真实路径；  
     - 这里必须捕获 `OSError`（比如路径不存在），对于不存在的路径，用 `os.path.realpath()` 可能失败，需要降级处理，防止因解析失败而把合法写入新文件的请求都拦死。
  2. 检查是否以白名单中的任一前缀开头。
  3. 如果是写模式（`w`/`a`/`x` 等），额外检查父目录是否在白名单内，否则拒绝。
- 替换内置 `open`：保存原 `builtins.open` 引用，新 `open` 调用 `_check_path`，通过后调用原函数。
- 替换 `os.open` 同理。
- 对 `pathlib.Path.open()` 也需要拦截——可以修改 `Path` 类的 `open` 方法，但更安全的做法是在导入时做一次 Monkey Patch。
- 模块初始化时解析配置，如果发现当前脚本在 `exempt_modules` 白名单中（通过检查调用栈），则直接放行，避免误拦标准库内部的临时文件操作。

### 3. 集成到 OpenClaw 脚本执行流程

在 Agent 的脚本执行入口前面，加上一行显式 import：

```python
import fileguard  # 必须在其他文件操作 import 之前执行
```

或者在 OpenClaw 的 Python 子进程启动参数里指定 `-S` 配合 `sitecustomize.py`，让护栏在解释器启动的最早阶段生效。我们选择前者，因为对部署透明，而且能够按需加载。

### 4. 日志与试运行模式

拦截时除了抛出 `PermissionError`，还要记录日志（写到一个固定的允许路径），包含时间、脚本调用栈、被拦截的路径、请求模式。开发阶段可以设置 `mode: dry-run`，只警告不阻止，用来发现未纳入白名单的必要路径。

## 踩坑记录

实际落地过程踩了不少坑，挑几个典型的：

- **符号链接解析失败导致所有写入被拒**  
  当脚本试图在 `/data/workspace/uploads` 下创建尚不存在的文件 `/data/workspace/uploads/result.csv` 时，`realpath()` 会失败，因为它会尝试解析整个路径，而文件还不存在。修复方式：先对最深层存在的父目录做 `realpath()`，再拼接剩余部分，再对拼接结果做简单规范化。这样即使最终文件不存在，只要父目录在白名单内，就允许写入。

- **多线程下 `os.getcwd()` 竞态**  
  有些库内部使用相对路径，我们必须在拦截器里拿到当前工作目录来拼绝对路径。但是 `os.getcwd()` 在另一个线程执行 `os.chdir()` 时可能变化。最终我们在脚本入口处缓存一份初始 cwd，全部基于那一个绝对基准来解析相对路径。同时对 `os.chdir()` 本身也可以拦截，但复杂度较高，我们先保持简单假设：Agent 脚本不随意变更 cwd。

- **第三方库如 `PIL.Image.save()` 使用文件描述符**  
  拦截 `open()` 还不够，某些库可能直接使用 `os.open()` 得到 fd 再传给 C 扩展。如果白名单漏掉这类调用，会导致运行时 PermissionError。我们的做法是提供豁免模块机制，将整个 `PIL` 加入豁免列表，风险可控，因为这些库的操作通常只在其自身缓存目录下。

- **配置热更新需求**  
  Agent 在运行时可能需要动态添加许可路径，比如处理用户上传的新临时目录。我们为 `fileguard` 增加了一个线程安全的函数 `add_allowed_path(real_path)`，供业务在需要时调用。

## 可复用建议

这套方案可以沉淀为一个轻量级 Python 包，供任何 Agent 脚本环境直接引用。建议的工程实践是：

1. **护栏配置与环境绑定**——不同 Agent 实例使用不同的 `allowed_paths`，通过环境变量 `FILEGUARD_CONFIG` 指定配置文件路径。
2. **全局开关**——提供一个 `FILEGUARD_DISABLE=1` 环境变量，在紧急排障时绕过所有限制，但记录告警。
3. **与 MCP 工具集成**——如果你的 Agent 通过 MCP 提供文件操作工具，最好在工具实现层就做白名单检查，双重保险。
4. **测试清单**——每次修改白名单后，必须验证：新建文件、追加文件、通过符号链接访问、读取白名单外已知安全文件（如系统时区文件），确保拦截逻辑正确且不会引发额外异常。

## 总结

进程内文件白名单护栏不是银弹，它无法防御恶意代码直接调用系统调用或修改解释器内存。但对于绝大多数基于 Python 的自动化脚本场景，它提供了一种成本极低、可审计的约束方式，让“放权给 Agent”这件事不再那么令人心惊胆战。在 OpenClaw 社区里，我们看到的很多安全事件，往往源于“脚本本来只想写日志，却扫描了整个主目录”——这个护栏恰是为此而生。

动手之前，建议先用 dry-run 模式在自己的脚本环境跑上几天，让拦截日志告诉你：你的自动化究竟在哪些角落里悄悄摸着文件。
