## 1. 背景

在 OpenClaw 这类自动化框架里，微博超话的自动同步是个高频需求：内容创作出来后，需要推送到指定超话，并尽可能减少人工干预。社区里已经有一些登录、扫码的实践，但真正踩坑最多的是**图片上传可靠性、发帖限流及任务状态追踪**。如果这些没处理好，轻则丢图，重则账号被风控。

这次分享一套工程化方案，基于 Agent + 直接 HTTP 接口的方式实现超话发帖，重点覆盖三个难点：图片上传的细节、限流重试与频率控制、发帖任务的状态归档。方案不依赖任何特定插件，可以轻松封装成 MCP 工具或 Agent 动作。

## 2. 核心问题拆解

- **图片上传**：微博要求先上传图片获取 `pid`，再携带 `pid` 发帖。上传接口参数多、返回格式不统一，大图或非标准格式容易失败。
- **发帖限流**：超话发帖接口有严格的频率限制（典型如每 5 分钟不超过 5 条），且不同时间段、不同账号等级可能有差异。直接硬怼会被返回“操作太频繁”，甚至暂时封禁发帖功能。
- **状态归档**：自动化任务一旦变多，需要知道哪些内容已成功、哪些失败、失败原因，以及如何避免重复发布同一内容。

## 3. 工程实现步骤

### 3.1 图片上传

使用 `requests` 模拟浏览器行为，向 PicUpload 接口发送 multipart/form-data：

```
POST https://picupload.weibo.com/interface/pic_upload.php
  ?m=upload&data=1&urltype=1&markpos=1&logo=&nick=@OpenClaw&marks=1&app=miniblog&s=json&pri_spec=1&pri_simple=1
```

Headers 需要携带登录后的 Cookie 和合理的 Referer。Body 中包含字段 `pic`（图片二进制）以及表单其余固定参数。

**踩坑点**：

- 图片大小超过 **5MB** 或格式非 `jpg/png/gif` 会被拒绝，返回 `code: -100`，msg 为“图片类型不支持”或“上传失败”。
- Cookie 中 `SUB` 是核心凭据，过期后上传接口会返回 `retcode: 0` 但实际无图片数据。需检查返回值中 `data.pics.pic_1.pid` 是否存在。
- 部分旧版上传接口（如 `picupload.php`）需要携带 `trimming` 参数指定裁剪信息，当前推荐接口固定 `pri_spec=1` 即可避免裁剪弹窗。

成功后拿到 `pid`，这个值在发帖时作为 `pic_id` 参数使用。

### 3.2 超话发帖与限流

发帖采用微博移动端常用的 composer 接口：

```
POST https://weibo.com/aj/mblog/add?ajwvr=6&__rnd={timestamp}
Content-Type: application/x-www-form-urlencoded
```

参数：
- `text` : 微博正文，需包含超话话题，如 `#OpenClaw自动化#`
- `pic_id` : 上一步获取的 pid
- `topic_id` : 超话的 topic_id（可在超话页面 URL 中获取）
- `location` : 可选，固定为 `v6_content_home` 或 `page_100808_{topic_id}`
- `_t` : 0（通常固定）

返回 JSON 中 `code == "100000"` 表示成功。

**限流症状**：当频率过高时，接口返回 `code: "100001"`，msg 类似“发送频率过高，请稍后再试”。需要实现自动退避。

**工程化处理**：

1. **本地速率限制**：维护一个带时间窗口的计数器（如每分钟最多 2 次发帖），通过 `time.sleep` 或异步队列控制实际调用频率，比硬抗微博限流更稳定。
2. **指数退避重试**：遇到 `100001` 时，从 10 秒开始退避，最大 5 分钟，每次重试前检查账号是否仍有效（以免浪费重试）。若 3 次仍失败，标记任务失败并通知。
3. **登录态预热**：长时间不活动后，Cookie 可能部分失效，发帖会返回 `login error`。可在发帖前用 `statuses/friends_timeline` 之类的接口探测一下，无效则触发重新登录动作。

### 3.3 状态归档

为了可观测性和幂等性，每个待发布的内容都会生成一个唯一键（例如文本和图片 URL 的 SHA256 哈希）。每条任务记录包含：

- `content_key` : 唯一定位
- `status` : pending / pic_uploading / posting / success / failed
- `retry_count` : 当前重试次数
- `last_error` : 最后一次错误信息
- `published_id` : 微博返回的 `mid`（如果有）

使用 SQLite 文件存储，轻量且无需额外服务。Agent 每次取任务时，会跳过已 success 或重试耗尽的任务。遇到异常时，最终的状态会更新到归档，方便人工介入。

## 4. 可复用建议

- **封装为 MCP 工具**：将上传图片、超话发帖分别定义为 `upload_weibo_image` 和 `post_to_topic` 两个工具，内部封装限流和状态记录。Agent 只需传入文本、图片路径和目标超话，工具会自己处理异常和退避。
- **状态外置**：不要只用日志，要用可查询的归档表。这样方便后续构建 dashboard，监控发帖成功率、平均延迟、限流次数等。
- **多账号支持**：如果有多账号需求，需要在状态数据和生产/消费者之间分离 credential 池。建议用 `account_id` 维度隔离限流窗口。
- **与现有自动化集成**：如果你的 Agent 已经在管理内容生成（例如通过 OpenAI 生成摘要和配图），只需在发帖动作前后增加图片上传步骤，复用上述逻辑即可。

## 5. 总结

微博超话同步的坑集中在图片上传协议的隐蔽规则和发帖限流的不可预测性上。通过明确上传接口的格式/大小要求，使用 local ratelimit + 指数退避来处理限流，并用状态归档实现任务幂等与可观测性，可以构建出一套可靠的自动化发帖管道。整个过程不用引入重框架，只用基础 HTTP 库就能跑起来，很适合嵌入到 OpenClaw 的 Agent 工具集或 MCP 插件里，把“发布”变成一个安静执行的后台步骤。
