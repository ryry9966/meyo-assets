## 背景：当 LLM 输出成为自动化流程的瓶颈

在构建 Agent、MCP 工具链或 OpenClaw 这类编排系统时，我们经常让 LLM 输出结构化数据——配置文件、多步骤计划、代码片段，甚至是一整篇带格式的文档。为了让下游模块消费，开发者普遍选择 JSON 作为交换格式，甚至约定复杂的 Schema。

看起来很美，直到你遇到：

- LLM 在长 JSON 中途莫名添加注释（`// 这里有个坑`）或尾随逗号；
- 嵌套过深时模型错误闭合括号，返回 “残缺 JSON”；
- 为了合规，模型突然在 JSON 里插入一段道歉文本，解析器直接崩溃；
- 生成篇幅一长，后半段键名开始出现幻觉（`“step3_detail”: …` 变成 `“step3_detial”: …`）。

这些情况在 GPT-4、Claude 3.5 Sonnet 等前沿模型上依然高频出现，尤其是在超过 2000 token 的结构化生成中。问题本质不是模型不够强，而是 JSON 作为一种严格语法，与自回归模型“边走边编”的生成方式天然冲突。只要一步错，整个输出就不可解析，错误恢复成本极高。

更麻烦的是，在自动化流水线里，我们往往没有人工兜底——坏 JSON 意味着流程卡死，重试浪费 token，还可能引发级联异常。

## 问题：为什么 JSON 是长文输出的“脆弱管道”

JSON 的脆弱性在长文本场景会被放大：

1. **无容错能力**：一个字符错误（多一个逗号、少一个引号）就让整个 payload 报废。标准解析器没有“部分恢复”机制。
2. **上下文压力**：长 JSON 要求模型在生成几千 token 后仍记得外层结构、未闭合的括号栈。这对注意力窗口是极大的考验。
3. **逃逸噩梦**：当 JSON 值内部包含自然语言、代码或多语言文本时，引号、反斜杠、换行符的转义极易出错。模型容易“忘记”转义，制造非法字符串。
4. **格式污染**：某些模型会输出 ` ```json … ``` ` 包裹的代码块，或前导白名单文本（“这是你的 JSON：”），导致解析器无法直接读取。

修复这些问题常见做法是加 retry、用 JsonFormer 等约束采样、写一堆正则预处理。但 retry 成本高，约束采样可能牺牲生成质量，正则永远写不完边缘情况。

## 做法：用自定义标签格式替代 JSON 长文输出

我的解决思路是彻底放弃 JSON，改用一种**自定义标签格式**（Tag-based Format）。原理简单：既然 LLM 擅长遵循自然语言中的标记（XML/HTML 标签、Markdown 分隔符），那就用标签来划定结构边界，让解析变成友好的正则匹配，而非严格语法分析。

### 步骤 1：设计标签结构

以生成多章节技术报告为例。原本你期望这样的 JSON：

```json
{
  "title": "...",
  "sections": [
    { "heading": "背景", "content": "..." },
    { "heading": "方案", "content": "..." }
  ],
  "conclusion": "..."
}
```

改为标签格式后，提示词要求模型输出：

```
<title>报告标题</title>
<section>
<heading>背景</heading>
<content>
背景内容段落……
甚至可以跨行，无需转义。
