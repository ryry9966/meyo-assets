## 背景：JSON 输出的幻觉与脆弱性

在 OpenClaw、Agent 或 MCP 插件这类自动化链条里，我们经常让 LLM 输出结构化数据，再用下游工具解析执行。JSON 几乎是默认选择——直到你要求模型一次性输出长文摘要、多段落分析，或者混合自然语言与结构化字段时，问题就开始出现。

典型的场景：
- 让 LLM 总结一篇会议纪要，除了摘要还要求提取 action items、决策点、时间线。
- 在 Agent 的 `final_answer` 中要求同时返回“正文”和“元数据”（引用来源、置信度、下一步建议）。
- MCP 工具希望一次调用获得带格式的报告内容，便于下游渲染。

在这些场景里，开发者通常会提供一个 JSON schema，然后用 `response_format: json_object` 或 prompt 里强调“严格返回 JSON”。结果却是：
- 字符串内未转义的双引号、换行符导致整段 JSON 解析失败。
- 模型在长文本中“丢失”闭合括号，或者多出一个逗号。
- 字段值里包含 ```json 代码块标记，导致解析器误判。
- 输出被截断在中间，只剩半个 JSON。

这些问题统称为“坏 JSON”。它们的共同特征是：**当我们把自然语言的自由度塞进 JSON 的刚性结构中，模型在长输出下的稳定性急剧下降。** 尤其在需要长文本嵌套的场景，一个微小的 token 级错误就能让整个 Agent 流程中断，重试成本高且未必成功。

这并不是模型不够强大，而是 JSON 作为序列化格式在生成式模型下存在固有脆弱性：自回归生成逐 token 输出，无法像编程语言编译器那样全局校验，一旦前期选择了一个未转义的引号，后面就没有回头路。

## 从结构化到半结构化：标签格式的思路

与其强迫模型在一个极易出错的字符串转义迷宫里行走，不如换一种思路：使用**基于自定义标签的半结构化格式**。这种格式的理念很简单：

- 用自然语言作为主要载体，只在需要机器解析的地方插入特殊标签。
- 标签成对出现，边界清晰，不会被模型误认为自然语言的一部分。
- 解析时只需要简单的正则或字符串匹配，容错性强。

一个典型标签格式可能是：

```
<thought>
这里是可以自由表达的思考过程，无需转义。
</thought>
<summary>
会议讨论了 Q3 产品路线图，重点包括……
</summary>
<action_items>
- 调研竞品 X 的新功能
- 周一前输出原型设计
</action_items>
<next_step>
调用工具 search_competitor("X product") 获取更多信息。
</next_step>
```

解析器只需提取 `<action_items>...</action_items>` 之间的内容，分割成列表即可。即使模型在 `<summary>` 里写了引号、换行、甚至不小心写了个 `<` 符号，也不会破坏整体结构，因为标签本身就是明确的边界。

## 做法：如何在 OpenClaw/Agent 中落地标签格式

1. **定义标签集合与语义**

   根据你的下游任务，确定一组有限的标签。例如在 OpenClaw 的 `final_answer` 中，我常用：`<thought>`、`<reply>`、`<suggestions>`、`<source_citations>`。每个标签的值可以是纯文本、Markdown 甚至嵌套标签（以简单缩进区分）。

2. **修改 System Prompt 和 Few-shot 示例**

   去掉“你必须返回 JSON”的指令，改为：
   > 你的输出必须使用以下标签格式。在 `<reply>` 标签内你可以使用 Markdown 自由组织回答正文；在 `<suggestions>` 标签内给出用户可能感兴趣的下一个问题；在 `<source_citations>` 标签内列出你引用的文档编号，用逗号分隔。

   并提供 2-3 个真实场景的 few-shot 示例，示例中的 `<reply>` 要包含长段落、列表、代码块等，让模型理解标签内部的自由度。

3. **解析器实现：容错优先**

   解析不用 XML 解析器，因为模型输出不是合法的 XML（可能缺少声明、标签未闭合等）。更好的做法是顺序扫描：

   - 用正则 `r'<tag>(.*?)</tag>'` (DOTALL) 提取内容。如果标签可能嵌套同名结构，用简单的栈计数处理。
   - 对未闭合标签做保护：若缺 `</tag>`，则截取到字符串末尾或下一个已知标签开始处。
   - 提取后对内容做 strip，必要时清理首尾的 Markdown 代码块标记。

   在 Python 中可以封装成 `parse_tagged_output(text)` 函数返回字典，失败时抛自定义异常，让调用方决定是否重试。

4. **结合 function calling 控制输出**

   如果你使用支持 tool call 的模型，可以把标签格式整合到工具返回值中。例如定义一个 `return_final_answer` 函数，参数就是各个标签字段的字符串。这样既能利用模型的 tool call 训练偏好，又避免了 JSON 嵌套字符串的痛苦——因为每个字段本身在函数参数中就是普通字符串，由 API 层面完成转义，大幅减少坏 JSON 概率。

## 踩坑点与排障经验

- **标签冲突**：模型偶尔会在正文中解释标签本身，比如写出“请在 `<reply>` 标签内回复”。对策是 prompt 中强调“标签仅作为结构标记，不要在正文中提及它们，如需讨论请用【】代替”。或在解析前先过滤掉包含标签说明的段落。
- **流式输出处理**：OpenClaw 使用流式传输时，标签可能跨 chunk。解析器需要缓冲并检测完整闭合标签才触发抽取，或等到流结束后整体解析。简单场景建议在流完全结束后解析，避免实时解析的复杂性。
- **模型遗忘标签结构**：长上下文中模型可能忘记输出某个非必需标签。解析器要设定合理默认值，不因缺失标签而整体失败。比如 `<suggestions>` 缺失则视为空列表。
- **与现有 JSON 工具的兼容**：如果整个 pipeline 已经依赖 JSON 传递，可在最终层加一个适配器，将解析后的字典 dump 成 JSON 传递给下游。这样渐进替换，不改动过多已有代码。

## 可复用建议

- **从低风险场景开始**：先在内部知识库问答或总结类 Agent 中替换掉 JSON，验证稳定性改善后逐步推广到更多 MCP 工具调用。
- **统一标签词汇表**：团队内约定一套标签命名规范（动词名词组合），避免不同 Agent 用不同标签造成维护混乱。
- **监控与 fallback**：记录解析失败率、重试次数。当标签格式解析失败时，fallback 到“将整个输出作为纯文本”，并触发告警，便于持续优化 prompt。
- **不要过度标签化**：只在机器必须解析的字段上使用标签，其他内容保留自然语言。标签格式的目的是减少出错面，不是创造新的语法。

## 总结

“坏 JSON”不是 LLM 的 bug，而是 JSON 强结构化约束与自回归生成特性之间不可调和的矛盾。标签格式通过放宽对转义和语法的要求，在自然语言和结构化之间找到一个更稳健的平衡点。对于 OpenClaw 社区中大量需要长文输出、混合分析与元数据的自动化流程，这种半结构化方案能显著降低流程中断率，让 prompt 工程更专注于任务本身，而不是和解析器搏斗。

它并不是万能银弹，但在工程实践中，一个容错性更好的输出格式，往往比一个理论上完美的 schema 更有价值。
