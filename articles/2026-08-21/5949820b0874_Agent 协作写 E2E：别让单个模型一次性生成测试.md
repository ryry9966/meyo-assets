## 背景

E2E 测试在真实项目里很容易变成“写一次、维护到放弃”。选择器动不动失效，等待条件靠猜，登录态处理复杂，最后测试反而拖慢发布。现在不少团队尝试让 LLM 直接生成 Playwright 测试，但单个模型一次性写出来的用例往往“看着像那么回事，跑起来各种崩”。原因很简单：模型没有真实页面反馈，选择器基本靠脑补。

## 问题拆解

一个可靠的 E2E 生成流程，需要同时解决三件事：

1. 理解页面结构：哪些元素存在、怎么定位、交互后发生什么。
2. 生成可维护的定位策略：优先 `data-testid`、语义角色，而不是脆弱 XPath。
3. 执行并反馈修正：跑挂了要么修选择器，要么修等待条件，但不能改业务断言。

这更像多角色协作，而不是一次静态补全。

## 做法/步骤

### 1. 先把浏览器能力通过 MCP 暴露给 Agent

在 OpenClaw 中注册 Playwright MCP，至少提供这些工具：

- `navigate` / `click` / `type`
- `snapshot`：返回可访问性树摘要，而不是完整 HTML
- `expect_visible` / `waitForResponse`
- `save_storage_state` / `load_storage_state`
- `start_trace` / `stop_trace`

### 2. 拆四个 Agent 角色

- **Explorer**：打开目标页面，根据验收标准走关键路径。每操作一步就获取可访问性树快照，输出“页面事实”，例如：登录按钮可通过 `getByRole('button', { name: '登录' })` 定位，提交后跳转 `/dashboard`。
- **Writer**：基于 Explorer 的事实和用户验收标准生成测试草稿。约束必须写清：优先 `data-testid`，其次 `getByRole/getByLabel/getByPlaceholder`，禁止深层 CSS 和绝对 XPath。
- **Runner**：在隔离环境执行测试，保存 trace、截图和报错信息。
- **Fixer**：只读失败测试和 DOM 快照，做有限次修复。只允许改定位策略、等待条件、步骤顺序，不允许改断言意图。

### 3. 执行闭环

```
Explorer 出事实 -> Writer 出用例 -> Runner 跑测试
                    ↑                  |
                    |                  v
                  Fixer <-------- 失败进入修复
```

循环最多 3 次。仍失败就输出带 trace 的报告，交人工处理。

### 4. 一个真实流程示例

用户输入验收标准：“验证创建订单后出现在订单列表”。

Explorer 走完流程后会发现：提交按钮没有 `data-testid`，但角色名很稳定。Writer 生成测试时就会写：

```ts
await page.getByRole('button', { name: '提交订单' }).click();
await page.getByRole('listitem').filter({ hasText: 'ORD-2025-001' }).waitFor();
```

Runner 跑通后，Fixer 不介入。后续如果前端动了按钮文案，Runner 失败，Fixer 会根据新的 DOM 快照把定位改成的新语义角色，而不是像传统录制脚本那样直接崩掉。

## 踩坑点

### 1. 选择器漂移

动态 class 在构建后随时会变。不要允许 Writer 使用 `div.card-primary` 这类定位。MCP 返回快照时，应把“稳定语义 id”和“不稳定 class”分开标记。没有 `data-testid` 时，让 Explorer 中断并提醒人工补充。

### 2. 固定等待问题

Agent 很容易写出 `waitForTimeout(3000)`，这种代码在 CI 里必炸。约束 Writer 使用断言等待：

```ts
await expect(locator).toBeVisible();
```

MCP 里也要提供 `waitForResponse`，而不是暴露纯 sleep。

### 3. 登录态处理

不要每个用例都从 UI 登录。把登录成功后的 `storageState` 保存下来，Runner 启动时直接加载。除非测的就是登录本身，否则 UI 登录只会增加 flaky。

### 4. 上下文膨胀

Explorer 如果保留整页快照，token 很快会爆。只保留可访问性树摘要，字段只留 `role / name / testid / visible`，丢弃无关 DOM 结构。

### 5. 危险操作

Explorer 可能会点到“删除”“支付”这种按钮。MCP 工具必须把写操作设为需要审批，支付/删除类按钮要二次确认。最好只在 staging 环境跑，生产环境不要自动测。

### 6. 修复循环发散

Fixer 如果反复改，可能把断言越改越弱。例如“订单出现”被改成“页面加载完成”。必须固定修复次数，并且禁止修改业务断言，只允许换定位和等待策略。

## 可复用建议

- MCP 工具按 `read` 和 `write` 分类，write 默认需要人工审批。
- 给 Agent 维护一份 `testid-convention.md`，所有生成过程强制引用。
- 测试代码入库前至少跑两次，确认不是偶发 flaky。
- 把整条链路封装成 OpenClaw 技能，用 `/e2e flow <验收标准>` 触发，输出测试文件和 trace 链接。
- Explorer 的产出可以复用：同一条关键路径不用每次重新探索，可以缓存页面事实摘要。

## 总结

Agent 协作写 E2E 的价值，不是“自动写出完美测试”，而是把探索、验证、修复这三件高反馈成本的事放进运行时闭环。单个模型一次性生成测试很容易翻车，但当一个 Agent 能真实操作页面、另一个 Agent 能根据失败信息修正定位时，产出质量会稳定得多。关键是工具约束和反馈闭环，而不是换更大的模型。
