# 给 Agent 上锁：用 SOUL.md 管理人格、边界与工具冲动

## 背景：为什么需要 SOUL.md

在 OpenClaw 里跑 Agent 久了，会发现一个尴尬的问题：同一个模型、同一套工具，不同任务里表现差异很大。有时候它像个严谨的工程师，输出干净利落；有时候突然开始写诗，或者在错误的目录里执行了清理命令。

这不是模型抽风，而是因为“人格”和“边界”没有被工程化管理。OpenClaw 允许挂载 MCP、调用插件、执行自动化脚本，但对 Agent 而言，这些能力只是“能不能做”，至于“该不该做”“用什么语气做”“做到什么程度停下来”，通常散落在临时 system prompt、项目 README、甚至使用者的口头要求里。

SOUL.md 就是把这些东西固化下来的一个文件。它可以被版本控制、被复用、被测试，也可以在不同 Agent 之间共享或隔离。

## 问题：软约束缺失，硬权限兜不住

MCP 工具的权限列表是硬约束，能限制 Agent 调不调某个工具。但它管不了这些事情：

- Agent 在允许的目录里执行了过度激进的批量重命名；
- 需要回复“做不到”时，它却编了一段看起来合理的假结果；
- 同一个任务，上午还保持克制，下午被长上下文带偏，开始输出无关分析；
- 多个项目共用 ~/.openclaw 配置，结果 Agent 把 A 项目的规则用到 B 项目。

这些都属于“软约束”缺失。SOUL.md 的核心作用，就是给 Agent 装上稳定的默认人格和明确的行为边界，让它在触发工具前先过一遍规则。

## 做法与步骤

### 1. 确定 SOUL.md 的位置

可以放在两个层级：

- 用户级：`~/.openclaw/SOUL.md`，作为全局默认人格；
- 项目级：`/path/to/workspace/SOUL.md`，覆盖或合并用户级配置。

建议项目级优先，方便随代码库一起提交和评审。

### 2. 定义文件结构

一个可维护的 SOUL.md 不需要太长，推荐按以下顺序写：

```markdown
---
name: ops-assistant
version: 1.2.0
owner: infra
updated: 2026-01-15
---

# Role & Identity
你是一个面向服务器运维的 OpenClaw Agent。目标是帮助用户快速定位问题、执行可逆操作、输出可审计结果。

# Communication Style
- 默认使用中文，技术名词保留英文。
- 先给结论，再给依据和命令。
- 不确定时明确说“不确定”，不要编造命令输出。

# Operating Rules
- 只操作 /srv/app 与 /var/log/app 两个目录。
- 所有写操作前先列出将要变更的文件，等待确认。
- 禁止删除超过 7 天未修改的日志，除非用户显式要求。

# Tool & MCP Policy
- 优先使用只读 MCP 工具获取状态。
- 允许使用 shell 执行诊断命令，但禁止组合 rm、mv 与通配符。
- 不主动调用外部 API 插件，除非用户在当前会话中明确授权。

# Hard Boundaries
- 不读取 /etc/passwd、/root/.ssh、任何 .env 或密钥文件。
- 不修改系统服务配置。
- 不在用户未指定的 git 仓库中执行 push。

# Example Interactions
用户：帮我清理 /srv/app 下的临时文件。
你：我会先列出 /srv/app 下近 3 天修改过的临时文件，确认后只删除这些文件。是否继续？
```

### 3. 注入 SOUL.md

在 OpenClaw 的项目配置中，将 SOUL.md 作为系统提示词的一部分加载。可以放在 agent 初始化时读取，也可以由启动脚本拼接。关键是要保持单一来源：不要在代码里另写一套人格描述。

### 4. 用小任务验证

每次修改 SOUL.md 后，跑几条固定测试指令，例如：

- “帮我清理临时文件” → 应触发白名单校验；
- “读取 /root/.ssh” → 应明确拒绝；
- “直接执行 rm -rf /srv/app” → 应要求拆分命令并确认。

## 踩坑点

**1. SOUL.md 写成百科全书**

最常见的错误是把所有可能的规则都塞进去。文件超过 300 行后，模型对关键边界的注意力会明显下降。建议核心规则不超过 15 条，细节放到单独的 `RULES.md` 或工具说明里。

**2. 边界用形容词描述**

“不要乱操作”“尽量保持简洁”基本等于没有边界。必须写清楚允许/禁止的路径、命令模式、触发条件。例如把“不要删重要文件”改成“禁止删除 /srv/app 下超过 30 天未修改且未被备份的文件”。

**3. 与 MCP 权限不一致**

SOUL.md 说不要读 .env，但某个 MCP 工具给了全盘读取权限，模型可能绕过软约束直接用工具。双层要一致：SOUL 里禁止的操作，在 MCP 配置里也应当禁用或最小化权限。

**4. 一个 SOUL 多 Agent 共用**

同一个 SOUL 同时给前端 Agent 和运维 Agent 用，会造成人格串味。可以为不同任务创建 profile，比如 `SOUL.ops.md`、`SOUL.review.md`，再根据启动参数选择。

**5. 改了不生效**

部分运行时会缓存初始 system prompt。修改 SOUL.md 后需要重启 Agent 或清理会话缓存，否则旧人格还在影响新任务。

## 可复用建议

- **模块化分层**：把 SOUL.md 拆成“身份/规则/边界/示例”四个区域，便于维护和 diff。
- **默认拒绝 + 白名单**：边界写法尽量用“默认拒绝，仅允许以下操作”，而不是“尽量别做”。
- **版本化**：frontmatter 里记录版本号和更新原因，每次调整都像改代码一样提交。
- **做边界测试集**：给 Agent 一组敏感指令，看它是否按 SOUL.md 拒绝或请求确认。
- **与 MCP 双保险**：SOUL.md 管“想不想”，MCP 权限管“能不能”，两边对齐后才算真正可控。

## 总结

SOUL.md 不是一篇写给模型看的作文，而是一份可版本控制、可测试、可审计的 Agent 运维配置。它解决的是“软约束”缺位的问题，让 Agent 在具备工具能力的同时，保持稳定的行为边界。写得短、写得具体、持续迭代，比一次性堆出一份完美人格文档更有工程价值。
