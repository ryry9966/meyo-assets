# OpenClaw 的多模型路由：什么时候用 GPT，什么时候用本地模型

## 背景

OpenClaw 的 Agent、MCP 和插件体系里，模型调用是高频动作。很多实践者一开始会把所有请求都丢给 GPT 这类云端模型，跑通之后再回头看，会发现三个问题：

1. **成本**：大量简单任务，比如实体抽取、意图分类、格式转换、日志摘要，消耗的 token 并不少。
2. **延迟**：云端 API 的排队和网络往返，在自动化流水线里会积累成明显的端到端延迟。
3. **数据敏感**：有些文本不适合出内网，比如内部代码片段、用户隐私数据、密钥周边日志。

本地模型（通过 Ollama、llama.cpp 等接入 OpenClaw）在这些简单、结构化、可枚举的任务上，已经能达到可用水平。但复杂推理、多步骤规划、长上下文代码生成，仍然需要 GPT 或同级云端模型。

这就带来一个工程问题：**怎么把请求自动分到合适的模型，而不是靠人肉判断。**

## 问题

多模型路由的难点不在“接入两个模型”，而在：

- 什么任务可以安全地降级到本地模型？
- 本地模型输出不稳定时怎么兜底？
- 如何避免路由策略变成代码里的散落 if-else？
- 怎么评估路由决策是否划算？

如果只是简单地把某个固定请求改成调用本地模型，后续业务变化时很容易失控。

## 做法 / 步骤

我在 OpenClaw 里用了一套比较克制的规则路由，流程如下。

**第一步：给任务分三级**

- **L1 低复杂度**：实体抽取、关键词提取、简单分类、JSON 格式转换、固定模板回复。这类任务本地模型基本能胜任。
- **L2 中等复杂度**：摘要、信息重组、多步工具调用的参数填充、短文档问答。可以尝试本地模型，但必须加输出校验和回退。
- **L3 高复杂度**：复杂代码生成、长文档推理、多 Agent 规划、异常处理。默认走 GPT，不主动降级。

**第二步：在 OpenClaw 中配置模型 provider**

本地模型通过 Ollama 暴露 OpenAI 兼容接口，GPT 走官方 API。OpenClaw 里配置两个 provider，例如：

- `gpt-4o-mini` 作为默认云端模型
- `local-qwen2.5-32b` 作为本地模型

不要把本地模型设成默认，避免误伤复杂任务。

**第三步：用规则策略做路由**

在任务定义或插件配置里，给不同 action 指定允许的模型级别。例如：

- `extract_entities` → 优先 `local-qwen2.5-32b`
- `summarize_meeting` → 优先 `local-qwen2.5-32b`，但设置 fallback
- `generate_code` → 固定 `gpt-4o-mini` 或 `gpt-4o`
- `plan_next_steps` → 固定 GPT

如果 OpenClaw 支持模型策略配置，可以把这些规则集中放在一个文件里，而不是散在业务代码中。关键是：**规则要可读、可版本管理、可批量修改。**

**第四步：设置 fallback 和超时**

本地模型最常见的失败是输出格式不对、生成超时、上下文不够。对每个走本地模型的任务，我都会设置：

- 超时时间，通常 10–20 秒
- 最大输出 token，避免长生成卡住
- 输出格式校验，比如 JSON schema 校验、字段完整性检查
- 失败时自动回退到 `gpt-4o-mini`

这样即使本地模型抽风，流水线也不会断。

**第五步：日志记录 + 离线评估**

所有请求记录模型名、输入长度、输出长度、延迟、是否回退、格式错误信息。每周跑一次离线脚本，统计：

- 本地模型成功率
- 回退率
- 格式错误率
- 平均 token 成本和延迟

用真实数据决定是否扩大或缩小本地模型的适用范围。

## 踩坑点

1. **本地模型 JSON 输出不稳定**  
   很多开源模型在“不相关文本”上也会强行输出 JSON，或者字段缺失。不要指望 prompt 里写一句“请输出 JSON”就能解决。最好在 OpenClaw 里接一个后处理校验，失败就回退 GPT。

2. **上下文窗口不够**  
   本地模型常见的 8k/32k 窗口，在长文档摘要或长对话里容易截断。不要直接把长文本塞进去，先做 chunk 级抽取，或者只让本地模型处理短输入。

3. **提示词不通用**  
   把 GPT 的复杂 system prompt 直接给本地模型，效果经常很差。需要给本地模型写更简单、更具体的指令，少用“你是一个专家”这类虚词。

4. **工具调用支持不完善**  
   很多本地模型对原生 function calling 支持不稳。我的做法是：在 prompt 里约定输出特定格式的“工具名 + 参数”，然后在 OpenClaw 侧解析，而不是依赖模型的 tool calling 能力。

5. **硬件瓶颈反而更慢**  
   如果本地模型跑在 CPU 或显存不足的 GPU 上，生成速度可能比 GPT 还慢。上线前先 benchmark 一下，记录 tokens/s 和 p95 延迟，必要时只保留 L1 任务给本地。

6. **不要频繁切换模型**  
   同一个会话或任务链里，来回切换模型会导致上下文风格不一致，尤其是本地模型和 GPT 对同一段对话的理解可能偏差很大。我一般按“任务节点”粒度切换，而不是按单条消息切换。

## 可复用建议

- **先日志后路由**：不要拍脑袋决定哪些任务走本地。先记录现有 GPT 请求的分布，跑一个月日志，再决定降级范围。
- **从只读任务开始**：分类、抽取、摘要这类任务不会产生破坏性动作，适合作为第一批本地模型验证。
- **保持模型可替换**：模型名写在配置里，不要在代码里硬编码。哪怕换一个本地模型，也只需要改配置。
- **监控四个指标**：本地成功率、回退率、格式错误率、p95 延迟。这四个指标能告诉你路由策略有没有跑偏。
- **每两周校准一次规则**：业务分布会变化，比如最近日志里长文档比例上升，可能就需要把摘要任务从本地模型撤回到 GPT。
- **不要追求全自动动态路由**：目前 OpenClaw 的工程实践里，基于规则的静态路由比“让模型自己判断”更可控。动态路由可以作为后续实验，但不建议作为生产默认。

## 总结

多模型路由不是“省钱”的银弹，它的本质是：**让合适复杂度的任务去合适的模型**。本地模型适合 L1 甚至部分 L2 任务，能显著降低成本和延迟；GPT 适合 L3 复杂推理和需要稳定输出的场景。

在 OpenClaw 里落地时，我建议从简单的规则路由开始，配合日志和回退机制，逐步扩大本地模型的适用范围。重点不是模型本身，而是**可观测、可回退、可替换**。

如果只能记住一件事：**先让日志告诉你哪些请求可以降级，再动手改路由。**
