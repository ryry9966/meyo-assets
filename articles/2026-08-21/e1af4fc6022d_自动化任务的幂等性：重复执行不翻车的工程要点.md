## 背景

在 OpenClaw、Agent、MCP 和插件自动化的场景里，任务很少只跑一次。定时器可能重扫，Webhook 可能重推，Agent 不确定工具是否成功时会重试，队列在超时后可能再次投递。现实的语义是 **at-least-once**，而不是理想化的 exactly-once。

如果你的处理函数默认“每次事件只发生一次”，重复执行就会带来真实副作用：重复扣款、重复创建工单、重复发送消息、状态被错误回退、统计翻倍。幂等性不是锦上添花，而是自动化任务的基本约束。

## 问题：为什么重复执行会出问题

典型根因有三个：

1. **无唯一性约束的写入**：比如每次事件都 `INSERT` 一条记录，没有业务唯一键，重复事件就产生重复数据。
2. **无条件状态更新**：`UPDATE tasks SET status='done' WHERE id=?`，即使任务已经被置为失败或已归档，也会被覆盖。
3. **外部调用的不确定性**：支付、创建资源、发通知等 API 如果本身不支持幂等，网络超时后重试可能产生重复请求。

另外，Agent/MCP 工具层的重试会让问题被放大。一个 MCP 工具可能被 Agent 连续调用多次；如果工具内部不做幂等，副作用会随调用次数线性累积。

## 做法 / 步骤

### 1. 定义业务自然唯一键

每个写操作都应该有可以唯一标识“同一次业务意图”的字段。例如：

- 订单号、工单号
- `user_id + task_type + business_date`
- Webhook 的 `event_id`
- 定时任务批次的 `batch_id + item_id`

如果不能从业务里找到自然键，就在事件入口生成并且透传 `idempotency_key`。

### 2. 入口记录幂等键与结果

在插件或工具入口处，先把请求结果按幂等键存下来。如果同一个键已经成功处理过，直接返回第一次的结果，不再执行业务逻辑。

```python
def handle_event(event):
    idem_key = event.get("idempotency_key") or sha256(event["payload"])
    with db.transaction():
        existing = idempotency_store.get(idem_key)
        if existing:
            return existing.result
        result = do_business(event)
        idempotency_store.save(idem_key, result, status="done")
        return result
```

这里要持久化 `status` 和 `result`，不只是“是否见过”。否则第二次请求可能返回空，或者触发部分流程重复执行。

### 3. 数据库唯一约束兜底

只靠应用层查重不够。并发下两个相同事件可能同时通过检查，因此必须让数据库兜底。

```sql
UNIQUE KEY uniq_task (task_type, business_id)
```

写入时使用：

```sql
INSERT INTO tasks (task_type, business_id, status, payload)
VALUES (?, ?, 'pending', ?)
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id);
```

或捕获 duplicate key，再走查询路径，返回已有结果。

### 4. 状态更新改成条件更新

把“无条件覆盖”改成“只有从合法前置状态才允许迁移”。

```sql
UPDATE tasks
SET status = 'running'
WHERE id = ? AND status = 'pending';
```

检查影响行数。如果是 0，说明任务已经被其他请求处理，应当退出或查询现有状态。这样能避免重复执行导致状态回退。

### 5. 外部调用使用 Provider 幂等能力

支付、云资源、消息推送等外部 API，通常支持 `Idempotency-Key` 或类似字段。把业务内部幂等键传给 Provider，而不是每次生成新 UUID。如果 Provider 不支持，就在本地记录 `request_id -> response`，重试前先查是否有已完成记录。

### 6. 重试策略分离

只有网络超时、429、5xx 这类可重试错误才自动重试；4xx 业务错误不应无脑重试。重试使用 exponential backoff + jitter，避免瞬时拥堵。此外，重试时应复用同一个幂等键，不能每轮生成新的。

## 踩坑点

- **前端 loading 不等于幂等**：按钮防重复点击不能保护后端，API 重放或并发调用依然会穿透。
- **时间戳或随机 UUID 当幂等键**：第一次和重试时值不同，幂等键失效。
- **check-then-act 竞态**：先查存在再插入，并发下两个都通过；必须依赖唯一约束或行锁。
- **MCP 链路丢失幂等键**：工具内部调用另一个服务时没有透传 `idempotency_key`，导致子操作重复。
- **部分成功后盲目重试整个流程**：比如创建订单成功、扣款超时，整单重试会重复创建订单。需要按步骤拆分幂等键，或做回查补偿。
- **只记录幂等键，不记录响应**：第二次请求返回“成功但内容为空”，调用方可能会错误重试。

## 可复用建议

在 OpenClaw 插件或 MCP 工具层，建议统一做一层幂等包装：

- 工具声明里把 `idempotency_key` 作为可选参数，并建议 Agent 传入 `run_id` 或 `message_id`。
- 入口装饰器自动解析 `idempotency_key`，没有则从 payload 生成稳定哈希。
- 结构化日志里记录 `source`、`attempt`、`idempotency_key`、`status`，方便追踪。
- 做幂等性测试：同一 payload 并发触发 10 次，预期只有一次副作用；对历史事件重放，数据应保持一致。
- 区分幂等范围：整个任务、单步工具调用、外部 API 调用，分别设计，不要混在同一个键里。

## 总结

幂等性不是“等出了问题再补”，而是自动化任务设计时的默认约束。关键是三层防线：**应用层幂等键 + 数据库唯一约束 + 条件状态更新**。对 OpenClaw、Agent、MCP 插件而言，很多重复执行来自重试、重放和交互式决策，因此把幂等做成工具入口的默认行为，能显著降低线上排障成本，也让重试真正变成安全的恢复手段。
