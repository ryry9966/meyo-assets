# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景

在 OpenClaw-CN 社区维护内容时，经常需要把外部优质文章、项目动态转成社区帖子。手动操作重复且耗时：抓链接、读内容、写摘要、排版、发布。于是想做一个半自动发帖机器人：机器人负责采集、筛选和生成草稿，人工做最后审核。目标不是全自动灌水，而是让内容运营从“体力活”变成“审核活”。

## 问题定义

动手前先明确边界：

- 社区对帖子质量有要求，纯 LLM 生成内容容易被判水。
- 需要长时间稳定运行，出错可追踪、可回放。
- 不能触发社区频率限制或打扰正常用户。
- 架构要可扩展，未来能接入更多数据源和发布渠道。

## 总体架构

整体拆成五层：调度层、采集层、加工层、审核层、发布层。

```
Scheduler -> Collector -> Summarizer -> Reviewer -> Poster
```

- **调度层**：用 OpenClaw 的定时任务，每 6 小时跑一次。
- **采集层**：通过 MCP 工具抓取 RSS 和 GitHub Trending，清洗 HTML，做 URL 去重。
- **加工层**：调用 LLM 生成中文标题、摘要、标签和讨论点。
- **审核层**：草稿推送到内部 Webhook，人工点通过/拒绝。
- **发布层**：审核通过后调用社区 API 发帖，记录帖子 ID。

## 技术选型

- **OpenClaw**：负责任务编排和工具调用，定时触发、串行执行。
- **MCP server**：封装 RSS 解析、GitHub API、社区发帖接口。统一成 MCP 工具后，OpenClaw 侧调用更干净。
- **SQLite**：存储状态和草稿。表结构大致如下：

```sql
CREATE TABLE posts (
  id INTEGER PRIMARY KEY,
  url_hash TEXT UNIQUE,
  url TEXT,
  status TEXT,  -- fetched/summarized/pending_review/approved/published/rejected/failed
  draft TEXT,
  post_id TEXT,
  created_at TEXT,
  published_at TEXT
);
```

- **LLM**：只做内容总结和格式转换，使用 function calling 约束输出字段。

## 关键步骤

1. **定义状态机**  
   status 字段枚举：`fetched -> summarized -> pending_review -> approved -> published`，另有 `rejected` 和 `failed` 分支。状态不清是后面排障的噩梦。

2. **实现 Collector**  
   从多个 RSS 源拉取，用 BeautifulSoup 提取正文，保留代码块和链接。对每个 URL 做规范化，去掉无关 query 参数，生成 url_hash 去重。

3. **实现 Summarizer**  
   Prompt 要求输出 JSON：
   ```json
   {
     "title": "...",
     "summary": "...",
     "tags": ["...", "..."],
     "discussion_points": ["..."]
   }
   ```
   强制走 function calling，避免 LLM 在 JSON 外多解释文字。

4. **实现 Reviewer**  
   草稿不直接发布。推送到飞书/Telegram 内部群，带“通过/拒绝”按钮。通过后才进入 Poster 队列。这步保留人工，是防止封号的关键。

5. **实现 Poster**  
   调用 MCP 工具发帖，记录返回的帖子 ID。发布成功后把 status 更新为 `published`，失败则标记 `failed` 并保留草稿供重试。

## 踩坑点

### 1. MCP server 连接不稳定
OpenClaw 调用 MCP 工具时偶发超时，尤其是 RSS 源响应慢的时候。  
**解决**：增加指数退避重试，工具调用设置 15s 超时。MCP server 进程交给 supervisor 管理，挂了自动拉起。

### 2. LLM 输出格式漂移
有时 JSON 外包裹了 Markdown 代码块，有时字段缺失。  
**解决**：强制使用 function calling，并在代码里做 post-validate。字段不合法就重试一次，再不行就丢弃并记录原始输出，方便后续排查 prompt 问题。

### 3. HTML 清洗不彻底
RSS 内容常夹带 `<style>`、`<script>` 残留，直接喂给 LLM 浪费 token 还影响生成质量。  
**解决**：BeautifulSoup 提取正文，删除 `script/style` 标签，保留 `pre/code`。内容超过 3000 字符截断，避免 token 爆炸。

### 4. 发布频率限制
社区 API 对短时间发帖有风控，连续发帖容易触发。  
**解决**：设置最小发布间隔 6 小时，队列串行处理。发布前查询最近一条 `published` 记录，间隔不足就跳过本轮。

### 5. 去重失效
同一篇文章在不同 RSS 源出现，或 URL 带不同追踪参数导致重复。  
**解决**：规范化 URL，去掉 `utm_*` 等参数，只对主 URL 做 hash。若标题高度相似也可做二级去重。

### 6. 内容太“干”
纯摘要没人看。  
**解决**：Prompt 中要求 LLM 额外生成“为什么值得关注”和“可讨论的问题”。人工审核时顺手润色，质量明显提升。

## 可复用建议

- **状态机要明确**：状态字段用枚举，不要用自由文本。排障时能快速知道卡在哪一步。
- **所有动作写日志**：每次采集、生成、审核、发布都记录关键信息。出问题可以按 url_hash 回放。
- **人工审核必须保留**：在社区全自动发帖容易被封，半自动也是内容质量的保障。
- **灰度发布**：先发到测试版块或小范围观察反馈，稳定后再放开。
- **敏感配置走环境变量**：token、webhook 地址不要硬编码在代码里。

## 总结

这个机器人上线两周，每天稳定产出 1-2 篇候选草稿，人工审核后发布，节省了大量重复劳动。核心不是 LLM 多强，而是**状态管理、人机协作和错误处理**。做自动化最怕“跑起来就没人管”，所以每一步都要可观测、可恢复。OpenClaw + MCP + SQLite 这套组合轻量够用，适合个人或小团队维护。
