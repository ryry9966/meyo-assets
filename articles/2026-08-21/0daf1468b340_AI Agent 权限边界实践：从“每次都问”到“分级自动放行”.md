# AI Agent 权限边界实践：从“每次都问”到“分级自动放行”

## 背景

在 OpenClaw / Agent / MCP / 插件自动化场景里，Agent 早已不只是聊天。它可以读文件、跑命令、改配置、发通知、调用外部 API，甚至可以操作浏览器和服务器。

能力越大，权限越容易失控。很多事故不是 Agent 不够聪明，而是它“太勤快”——把不该自己干的事也干了。于是我们面临一个经典问题：**什么时候该问人类，什么时候可以自己干？**

如果每步都问，自动化基本报废；如果全自动，删库跑路只是时间问题。工程上要做的，不是追求“全自动”，而是设计一套可解释、可回滚、可审计的权限边界。

## 问题

一个典型的失败模式是这样的：

- Agent 说“我会修复配置”，用户点了同意。
- 结果它改了 30 个文件，其中 5 个是生产配置。
- 用户想撤回，发现没有回滚记录。
- 最后只能手动抢救。

另一个极端：Agent 每执行一个只读命令都要确认一次，用户被问麻了，开始无脑点“允许”。审批流形同虚设。

核心矛盾只有一句话：**把确认当成稀缺资源，只花在不可逆、高风险、影响面大的动作上。**

## 做法/步骤

### 1. 先给动作分级，而不是按工具分

不要笼统地定义“shell 危险，文件读写安全”。真正有效的是按动作的风险等级分类：

- **L0 只读/低风险**：读文件、查状态、搜索、获取日志。默认自动。
- **L1 可逆中风险**：创建草稿、生成代码到临时目录、更新非关键配置、新建分支。自动执行，但必须留痕、支持回滚。
- **L2 不可逆高风险**：删除、覆盖生产文件、执行 shell、发送消息/邮件、发布、支付、修改权限、批量操作。默认必须人类确认。

在 OpenClaw 这类框架里，可以实现一个权限中间件或策略引擎，让每个工具在注册时声明 `riskLevel`、`impactScope`、`reversible`、`requiresApproval`。所有工具调用统一走这个入口，而不是散落在各插件里各自判断。

### 2. 用“影响摘要”代替“是否继续”

审批文案不要写：

> 是否允许执行 shell 命令？

要写成：

> 计划：删除 `./dist` 目录下 12 个文件，释放 340MB。
> 影响范围：当前工作区，不涉及生产。
> 回滚方式：可从回收站恢复 / 已有构建缓存。
> 操作：`rm -rf ./dist/*`

这种文案让人在 5 秒内做出正确判断。比单纯的 y/n 强得多。

### 3. 先 dry-run，再执行

对高风险动作，强制先输出执行计划。可以用 MCP 工具包装一层 `dryRun`，只生成计划不实际执行。人类确认后，Agent 再进入执行阶段。

注意：执行阶段必须校验实际动作与 dry-run 计划一致。否则会出现“计划改 3 个文件，实际改 30 个”的越权问题。

### 4. 设置确认有效期和授权范围

支持三种授权粒度：

- **单次授权**：只允许当前这一条操作。
- **会话授权**：当前任务内同类操作自动放行。
- **模式授权**：例如“允许在当前工作区覆盖 `.log` 文件”。

同时设置超时默认拒绝。比如审批请求等待 5 分钟，超时自动取消，避免挂起后被人误点。

### 5. 记录审计日志

每次自动执行、人工确认、拒绝、回滚，都记录：时间、动作、风险级别、影响范围、执行结果、回滚状态。日志不一定要给人天天看，但出事后能复盘。

## 踩坑点

1. **审批疲劳**：每个动作都问，用户机械点“是”。解决方式是把 L0/L1 默认自动，只对 L2 做确认。
2. **计划与实际不符**：Agent 嘴上说改 3 个文件，实际改 30 个。必须做契约校验，执行前比对目标清单。
3. **权限描述太模糊**：工具名只有 `run_command`，用户根本不知道它要跑什么。给工具加描述和影响范围元数据，审批时展示具体命令。
4. **忽略回滚**：高风险动作没有回滚手段，一旦批准就无法恢复。至少要求提供“可回滚证明”，或者先备份。
5. **测试与生产不分**：在测试环境跑通的自动化，直接切到生产。环境边界要隔离，生产环境默认升一级风险。
6. **全局 shell 授权**：一旦给了 shell，后面所有命令都能绕过策略。尽量用细粒度工具替代裸 shell，比如 `write_file`、`delete_path`、`restart_service`。

## 可复用建议

- **建立权限分级表**：在团队里维护一份工具/动作风险清单，新接入插件先对齐风险等级。
- **审批文案模板化**：固定格式为“计划 + 影响范围 + 回滚方式 + 实际命令”，降低沟通成本。
- **允许干跑影子模式**：先让 Agent 在影子模式下跑一周，只记录“如果自动执行会做什么”，再逐步放权。
- **把人工确认当资源**：只在不可逆、影响面大、首次操作时使用。其余用日志和回滚兜底。
- **用 allowlist/denylist 兜底**：对关键路径、敏感目录、生产环境做显式白名单，宁可不执行，不可越界。

## 总结

权限边界不是为了让 Agent 变得“乖”，而是为了让它在不打扰人类的前提下，安全地完成更多自动化。

好的边界设计有三个特征：低风险动作自动放行，高风险动作不厌其烦地给足信息，所有决策可回溯、可回滚。这样既能避免“每次问”的疲劳，也能防住“自己干”的事故。

在 OpenClaw 体系里，权限策略应该作为基础设施来做，而不是每个插件各写一套。越早统一，越不容易在后期被某个插件的一个 `delete` 搞到半夜回滚。
