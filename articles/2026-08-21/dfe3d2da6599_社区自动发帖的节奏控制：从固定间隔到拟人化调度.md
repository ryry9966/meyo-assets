## 背景

在 OpenClaw 社区做自动化内容发布，常见链路是：定时任务唤醒 Agent，Agent 通过 MCP 工具调用社区接口发帖。跑通不难，但跑一段时间后容易遇到限流、折叠、账号权重下降，或者被社区用户说“怎么像机器人”。

这里有个常见误区：大家总去改文案，让它更像人写的。但实际工程中，文案只占一部分，发布节奏的机械感更容易暴露自动化特征。本文不讨论内容生成，只聊节奏控制。

## 问题：太规律比 AI 味更明显

实际观察下来，容易被识别为机器人的行为包括：

- 固定间隔发布，比如每 60 分钟一条，间隔方差接近零。
- 整点或半点发布，时间分布过于规整。
- 短时间批量发多条，或者连续多天无休。
- 发完从不回复、从不删改、失败仍硬重试。
- 对社区时区无感知，在目标用户睡觉时规律活跃。

这些行为比“文案带 AI 味”更容易触发风控。社区风控和用户直觉都会捕捉“太规律”和“太完整”。

## 做法：把节奏控制做成显式策略

不要只用 cron 直接触发发帖。建议把发布过程建模为状态机：

`draft -> wait -> check_window -> post -> observe -> cooldown`

状态最好可持久化，Agent 重启后不丢任务。具体控制点如下。

### 1. 时间抖动

基础间隔加上随机偏移。例如基础间隔是 4 小时，实际间隔用：

`interval = base * uniform(0.75, 1.5)`

同时设定每天最大发布数，比如 2~3 条。偶尔跳过一天也可以，不要长期无休。

### 2. 本地时间窗口

根据目标社区主要活跃时区设置可发布窗口。例如北京时间：

- 10:00–12:00
- 15:00–17:00
- 20:30–23:00

窗口内再随机选择分钟，避开整点和凌晨。

### 3. 内容指纹与重复控制

发布前计算文本相似度，与历史发布内容、草稿队列比对。可以用 SimHash、MinHash 或简单 TF-IDF。相似度阈值建议设在 0.82 左右，超过就拦截或改写，不要直接发。

标题可以加变量，但不要每篇都改得很刻意，否则又像参数填充。

### 4. 发布后行为

不要发完就结束。让 Agent 在发布后 20~60 分钟巡检一次，看是否被折叠、是否需要回复、是否要删改。回复动作也做随机延迟，避免秒回。

### 5. 失败退避

遇到 429、验证码、审帖、限流，不要立即重试。使用指数退避加随机抖动：

`5min -> 25min -> 2h`

连续失败达到阈值后，暂停当天任务，把失败任务转入人工队列，不要自动硬重试。

### 6. 审计日志

每步记录关键事件：`task_id`、`planned_at`、`actual_post_at`、`interval_jitter`、`fingerprint_sim`、`http_status`、`retry_count`。这样后续可以复盘节奏，而不是黑盒。

## 踩坑点

- **随机不是越大越好**。抖动太大导致发布时间不可控，可能错过活跃窗口；太小又没效果。建议先固定 baseline，再引入 ±30%~50% 抖动。
- **不要过度拟人**。加错别字、无意义停顿、假装“手滑”，容易被识破，还损害信息质量。
- **不要把重试当成发布**。失败后继续自动重试，可能触发更重风控。失败队列和待发布队列要分开。
- **时区错误很常见**。服务器 UTC 时间直接当本地时间，会导致发布时间偏移。显式配置时区并打印验证。
- **MCP 工具层不够用**。如果 MCP 工具只提供发帖接口，没有延迟、重试、审计能力，需要在 Agent 上层加一层调度策略，不要直接裸调接口。
- **频繁编辑会暴露**。如果社区公开编辑记录，发布后反复修改反而更像机器人。尽量一次到位。

## 可复用建议

- 把节奏控制抽成独立模块或 MCP server：输入内容，输出“建议发布时间”和“是否放行”。内容生成和发布策略解耦。
- 新账号先灰度：每天 1 条，观察 7 天，再提升到 2~3 条。
- 保留 kill switch：一条命令暂停所有自动发布，避免批量翻车。
- 监控三个指标：间隔分布方差、失败率、折叠/举报率。如果间隔方差趋零或折叠率上升，立即降频。

## 总结

自动发帖不像机器人的核心，不是把文案写得像人，而是让行为节奏失去机械规律。通过状态机、时间抖动、本地窗口、内容指纹、失败退避和审计，可以在保持工程可控的同时，降低风控和社区反感。

不要追求完美拟人，追求“可解释、可停止、可复盘”的自动化。
