## 背景

在 OpenClaw 这类 Agent/MCP 工作流里，自动发帖常被用在几个场景：同步技术笔记、发布 release changelog、定时推送社区更新、自动回复常见问题。功能一旦跑通，很多人会立刻上一套 cron 或 `setInterval`，然后发现账号很快被识别成机器人。

问题通常不是内容质量，而是节奏失拟。

## 问题在哪里

典型的“机器人特征”不是发了什么，而是发布行为的时间分布：

- 固定间隔精确到秒，比如每 30 分钟一条；
- 堆积任务一次性爆发，长时间沉默后突然连发；
- 对评论、引用的响应速度恒定，几乎毫秒级；
- 失败后无退避，几秒内重试十几次；
- 多个账号或多个 MCP 工具行为高度同步。

这些特征在日志里看起来很正常，在平台侧和人工观察下非常明显。

## 做法与步骤

### 1. 把“发布节奏”做成独立配置层

不要让每个 Agent 自己决定什么时候发。拆出一个 posting profile，按平台或账号配置：

```yaml
posting_profile:
  base_interval_sec: 2400
  jitter_ratio: 0.25
  active_hours:
    - "09:00-11:30"
    - "14:30-17:30"
    - "20:00-22:30"
  daily_max_posts: 3
  cooldown_after_fail_sec: 1800
  backoff_sec: [60, 300, 900, 3600]
```

这一步的价值在于：节奏控制与内容生成解耦。内容 Agent 只负责产出草稿，发不发、什么时候发由调度层决定。

### 2. 间隔加抖动，但不要只加均匀抖动

固定间隔加一个 `random.uniform` 是最容易做的，但太均匀的随机也不像真实用户。真实用户的发布间隔往往有长尾：大部分时间较短，偶尔很长。

更工程化的做法是使用对数正态或指数分布生成间隔：

```python
import random
import math

def next_delay(base_sec: int, jitter_ratio: float = 0.25) -> int:
    # 对数正态，避免完全均匀的抖动
    sigma = 0.35
    delay = random.lognormvariate(math.log(base_sec), sigma)
    return int(max(base_sec * (1 - jitter_ratio), min(delay, base_sec * (1 + jitter_ratio))))
```

如果你的系统不需要这种复杂度，至少做到两点：间隔不取整、同账号不同发布之间加入状态记忆。

### 3. 内容队列分层

不要每条内容都走同一个频率。把内容分成：

- `cold`：低时效聚合、周报，可以低频；
- `warm`：常规技术笔记、项目更新；
- `hot`：需要尽快发布的 release、紧急说明。

不同层级允许不同的 `base_interval` 和 `daily_max`。同时避免每次发布都使用完全相同的模板结构。哪怕只改动词序、摘要长度、链接位置，也能减少模板化特征。

### 4. 发布前增加随机停顿

Agent 生成完一条帖子后，不要立即执行发布。可以在流程里插入一个 15-90 秒的随机等待，或者拆成多步：

`生成草稿 -> 停顿 -> 编辑/校验 -> 停顿 -> 发布`

这种停顿不需要很复杂，但它能消除“生成即发布”的瞬时相关性。

### 5. 互动响应要有节流

自动回复、自动点赞、自动追踪评论这类互动行为，比发帖更容易暴露。建议对每个账号设置滑动窗口：

- 每 10 分钟最多响应 1 次；
- 每天最多自动响应 5 次；
- 超过阈值后只入队列，等待人工处理或下一个活跃窗口。

如果平台返回风控信号，如 429、验证码、登录失效，应停止当前任务，而不是换 IP 硬刚。

### 6. 失败退避与可观测

指数退避是底线，但要注意加上随机抖动。失败后的重试间隔建议同时记录平台返回码和剩余重试次数，并在日志中打出节奏事件：

```text
[posting] channel=discord status=429 delay=1800s attempts=3 last_ok=2025-01-01T12:00:00Z
```

这样后续调参才有依据。

## 踩坑点

- **全局 jitter 不够**：多个任务叠加后仍可能集中发布，必须按账号或 channel 维护会话级状态。
- **完全均匀随机反而可疑**：真实间隔通常有明显长尾，均匀抖动只是把机械感从“固定”变成“均匀随机”。
- **忽略活跃窗口**：凌晨三点高频发技术帖，内容再好也像机器人。
- **失败后立刻重试**：平台暂时限流，几分钟内连续撞十几下，风险最高。
- **发布后马上用小号点赞/评论**：协同行为的时间耦合极容易被识别。
- **模板结构高度统一**：标题、摘要、链接三段式一用到底，内容和节奏都机械。

## 可复用建议

1. 节奏控制做成独立中间层或 MCP 工具，不要侵入内容生成逻辑。
2. 每个平台维护独立的 profile，参数可配置、可回放。
3. 低置信度内容只生成草稿，不自动发布。
4. 发布计划可以每天根据随机种子预生成，便于审计和复现。
5. 新账号从低频少次开始，不要一上来就跑满配额。

## 总结

社区自动发帖像不像机器人，核心不是“要不要自动化”，而是节奏是否具备多样性、失败处理是否克制、行为是否可观测。固定间隔和瞬时响应是最容易修掉的问题；真正需要长期维护的是按账号解耦的状态、随机模型的选择，以及风控触发后的退避策略。

控制好节奏，自动化才能长期稳定地跑下去，而不是跑三天就被封号。
