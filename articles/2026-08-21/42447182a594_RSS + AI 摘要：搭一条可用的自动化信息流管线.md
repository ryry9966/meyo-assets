# RSS + AI 摘要：搭一条可用的自动化信息流管线

## 背景

在 OpenClaw、Agent 和 MCP 的自动化实践里，很多人的需求不是“让模型多跑一步”，而是把外部信息整理成可消费的格式。RSS 仍然是最容易获取、最容易控制的公开信息源之一。问题在于：订阅多了之后，每天几十上百条 entry，人工筛不过来；如果直接把每条全文丢给 LLM，成本高、延迟大，而且输出格式容易乱。

这篇文章不讨论“RSS 复兴”之类的泛话题，只给一条能落地的管线：**抓取 → 解析 → 去重 → 摘要 → 推送**。适合已经会一些 Python/Node、用 OpenClaw 或 MCP 做自动化的用户。

## 问题拆解

原生 RSS/Atom feed 通常只给标题、链接、时间，部分带摘要。要做 AI 摘要管线，主要卡在四个点：

1. **重复推送**：同一条内容因 URL 跟踪参数、多源转载、GUID 缺失而反复出现。
2. **状态管理**：重启后不能重新摘要已经处理过的内容。
3. **模型输出不稳定**：LLM 可能返回纯文本、错误 JSON，或者摘要过长。
4. **feed 质量参差**：缺时间、时区混乱、正文编码问题、内容过长。

这些问题都能用很普通的工程手段解决，不需要复杂框架。

## 管线设计

最小实现可以拆成这些步骤：

```text
RSS sources
    │
    ▼
fetch feeds (timeout, UA, retry)
    │
    ▼
parse & normalize entries (title, link, guid, published_utc, content)
    │
    ▼
dedupe against SQLite
    │
    ▼
filter / truncate (optional rules)
    │
    ▼
LLM summarization (structured JSON)
    │
    ▼
push (Telegram / ntfy / email / webhook)
```

状态外置到 SQLite，表结构建议：

```sql
CREATE TABLE seen_items (
    id INTEGER PRIMARY KEY,
    link_hash TEXT NOT NULL,
    title_hash TEXT NOT NULL,
    source TEXT NOT NULL,
    first_seen_utc TEXT NOT NULL,
    last_seen_utc TEXT NOT NULL,
    status TEXT DEFAULT 'new',
    summary TEXT,
    UNIQUE(link_hash, title_hash)
);
```

`link_hash` 用规范化后的 URL 计算，`title_hash` 用清理后的标题计算。两者联合唯一，能覆盖大部分缺 GUID、URL 带参数的情况。

## 实现步骤

### 1. 抓取与解析

Python 用 `feedparser`，Node 用 `rss-parser`。设置 10 秒超时、自定义 User-Agent，失败后指数退避重试一次。不要每 10 分钟全量抓一遍所有源，按源更新频率分组调度。

### 2. 规范化与去重

对每个 entry：

- 取 `link`，移除 `utm_source`、`utm_medium`、`utm_campaign` 等跟踪参数。
- 如果没有 `guid`，用 `link` 和 `title` 共同生成 hash。
- 时间统一转 UTC，缺时间则用抓取时间兜底。
- 正文或摘要截断到 2000 字符左右，避免 token 爆炸。

先查 SQLite，如果 `link_hash` 和 `title_hash` 已存在，就跳过摘要，只更新 `last_seen_utc`。

### 3. LLM 摘要

Prompt 固定模板，要求输出 JSON：

```json
{
  "title": "标准化后的标题",
  "summary": "不超过80字摘要",
  "tags": ["分类标签"],
  "importance": "high|medium|low",
  "action_items": ["可能需要跟进的信息"]
}
```

调用时设置 `response_format` 为 JSON，解析失败就重试一次。第二次仍失败，则降级为截取原摘要后直接推送，不要阻塞管线。

### 4. 推送

优先采用聚合推送：每个源或每轮任务产出一条 digest，而不是每条 entry 单独推。Telegram 和 ntfy 都很适合，保留原文链接，限制消息长度在 2000 字符内。

### 5. 与 OpenClaw / MCP 集成

建议把三个能力封装成 MCP tools：

- `fetch_feeds(sources, limit)`
- `summarize_entry(content, template)`
- `mark_seen(link_hash, title_hash, status)`

然后让 OpenClaw 插件或外部 cron 调用。不要在 Agent 推理循环里频繁抓取 RSS，会让上下文变脏，也容易打满限流。

## 踩坑点

- **feed 不是标准时间**：很多站点的 `pubDate` 是本地时间但没带时区信息。统一按 UTC 解析，解析失败用时区推断或抓取时间兜底。
- **URL 跟踪参数导致重复**：除了 utm，还有 `spm`、`from`、`share_token` 等，最好维护一个参数黑名单。
- **LLM 输出字段漂移**：不要依赖自然语言描述字段，直接要求 JSON，并在代码里做 schema 校验。重要度这种字段最好限定枚举。
- **成本失控**：长正文先截断，或先用关键词规则过滤，只对入选条目调用 LLM。高噪声源要降低抓取频率。
- **失败静默**：如果 fetch 连续失败，要记录日志并告警，否则管线会“看起来在跑，实际已停”。

## 可复用建议

1. **状态外置**：SQLite 或 JSON 文件都可以，但要有唯一键，重启可恢复。
2. **摘要 prompt 保持极简**：字段少、输出短、可校验。先跑通闭环，再优化摘要质量。
3. **分源灰度**：先接 2–3 个质量较高的源，跑一周，确认去重和推送稳定后再扩大。
4. **日志记关键指标**：每个源抓取成功/失败、新增条目数、被过滤数、LLM 调用次数。没有这些数据，后面排查会很痛苦。
5. **推送要可关闭**：把重要度阈值和推送开关做成配置，避免低质量摘要刷屏。

## 总结

RSS + AI 摘要这条管线不复杂，但真正稳定跑起来，关键在于去重、状态外置、输出约束和调度控制。别把重心放在“模型多聪明”上，先把 feed 规范化、去重和推送闭环做好。对 OpenClaw/Agent/MCP 用户来说，这是很适合练手的自动化项目：体积小、可复现、长期有用，而且能自然地把外部信息接入你的 agent 工作流。
