## 背景

在 OpenClaw / Agent / MCP 的日常实践里，外部 API 已经从“偶尔调用”变成“任务主链路的一部分”。搜索、天气、网页抓取、智能家居控制、通知推送，甚至 MCP Server 本身，都可能因为限流、认证过期、网络抖动或上游 5xx 直接失败。

但很多 Agent 对外部 API 失败的处理仍然很原始：要么把异常直接抛给用户，要么反复重试直到上下文爆掉，要么更危险——把错误信息当成真实结果继续推理。

这篇文章不讨论“如何让 API 永远不挂”，而是讨论：当它挂了，Agent 如何失败得体面一点，并且能自动恢复。

## 问题

一个典型故障链路是这样的：

1. Agent 调用天气 API，上游返回 500。
2. 工具函数抛出 `requests.exceptions.HTTPError`。
3. Agent 把这段异常塞回 prompt，继续尝试“分析”错误。
4. 任务没有中断，但最终输出里混入了半成品数据或错误结论。

更糟的是，如果这个 API 被多个 Agent 或定时任务同时依赖，一次上游抖动可能变成大量任务连续失败，甚至触发更多重试，形成雪崩。

核心问题不是“API 挂了”，而是**Agent 缺少错误分类、降级路径和恢复边界**。

## 做法与步骤

### 1. 先分类，再决定是否重试

不要对任何异常都重试。在工具调用层先做一次错误分类：

- **可重试**：429、502、503、504、网络超时。
- **不可重试**：400 参数错误、401/403 认证权限问题、404 资源不存在。
- **写操作**：POST/PUT/DELETE 默认不自动重试，除非上游明确支持幂等键。

可以用一个简单的 `classify_api_error(e)` 函数返回 `retryable` 和 `error_type`，不要让 Agent 自己去猜。

### 2. 重试要有退避和抖动

固定间隔重试很容易造成“惊群”。建议使用指数退避加随机抖动：

```python
delay = min(base * (2 ** attempt), max_delay)
jitter = random.uniform(0, delay * 0.3)
time.sleep(delay + jitter)
```

对读接口，重试 2–3 次通常足够；对写接口，只在有幂等键时重试 1 次。超时时间不要设置过长，否则一个慢 API 会把整个任务卡死。

### 3. 给 Agent 一条降级路径

重试失败后，不要直接返回异常。准备以下降级手段之一：

- **Fallback provider**：主天气 API 挂了，切到备用的 Open-Meteo 或缓存数据。
- **Last-good-response 缓存**：保存最近一次成功响应，降级时返回并标记 `stale=true`。
- **结构化错误返回**：告诉 Agent：“这个工具当前不可用，错误类型为 `rate_limited`，建议跳过或使用本地数据。”

关键是：**降级结果必须明确标记**。不要让用户误以为缓存数据是实时数据。

### 4. 加一层简单的熔断

连续失败达到阈值后，快速失败比反复超时更好。可以在工具调用层维护一个熔断状态：

- 连续失败 3–5 次，打开熔断。
- 熔断期间直接返回结构化降级结果，不再请求真实 API。
- 30–60 秒后进入半开状态，用一次探测请求验证恢复情况。

这个逻辑并不复杂，但对多 Agent 同时依赖同一 API 的场景非常有效。

### 5. 校验响应，别让坏数据进入最终结果

即使 HTTP 200，响应体也可能缺失字段或格式错误。工具函数返回给 Agent 前，至少做一次必要字段校验。校验失败按 `invalid_response` 处理，而不是把原始 JSON 丢回上下文。

## 踩坑点

- **无限重试**：没有最大重试次数，任务卡在单个工具上，LLM 上下文越等越长。
- **写操作重复提交**：没有幂等键就重试，可能创建重复订单、重复消息。
- **降级不标记**：缓存/兜底数据被当成实时数据，用户做出错误决策。
- **错误信息全量塞入 prompt**：一段 300 行的 traceback 会污染上下文，让 Agent 偏离任务。
- **熔断不恢复**：熔断打开后没有探测机制，API 恢复后仍长期走降级。
- **超时设置极端**：超时过长导致任务卡死，过短导致正常慢请求被误判为失败。

## 可复用建议

1. **统一封装工具调用层**：错误分类、重试、熔断、降级都在这一层完成，不要让每个工具各自实现。
2. **工具返回结构化错误**：统一返回 `{ok, error_type, retryable, fallback_used, data}`，让 Agent 能做清晰决策。
3. **维护 last-good-response 缓存**：关键读接口保存最近一次成功响应，作为最后兜底。
4. **把恢复策略配置化**：重试次数、退避参数、熔断阈值放到配置里，不要在 prompt 里硬编码。
5. **主动演练故障**：手动让 API 返回 429、500、超时，观察 Agent 是否能正确降级、停止或跳过。

## 总结

外部 API 挂了不是意外，而是迟早会发生的事。对于 AI Agent，真正的健壮性不在于“永不失败”，而在于失败时能否分类、降级、恢复，并且不让错误数据污染最终结果。

在 OpenClaw 或 MCP 工具链中，把恢复逻辑沉淀到工具调用层，用结构化错误代替异常堆栈，用缓存和熔断代替无限重试，通常比继续优化 prompt 更有效。
