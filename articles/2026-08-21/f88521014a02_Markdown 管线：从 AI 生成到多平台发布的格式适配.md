# Markdown 管线：从 AI 生成到多平台发布的格式适配

在 OpenClaw/Agent 工作流里，Markdown 经常被当作默认输出格式。Agent 把结果写入 `.md` 文件，插件或 MCP 工具再拿去发布到公众号、知乎、Notion、GitHub 等平台。很多自动化流程到这一步就开始出问题：Markdown 看起来是“通用格式”，但不同平台对它的理解差别很大。真正工程化的做法不是让 Agent 直接输出“适合某个平台”的文本，而是建立一条从 AI 生成到多平台发布的 Markdown 管线。

## 背景

AI 生成内容时，通常只会输出标准 Markdown 或某种方言。比如有些 Agent 会输出 Obsidian 风格的双链、YAML front matter、脚注、任务列表、数学公式，甚至把本地图片路径直接写进文档。发布到 GitHub 没问题，但发布到微信公众号、知乎或小红书时，这些元素可能原样显示、丢失、格式错乱，甚至导致整段内容不可读。

如果每个平台都写一套独立的转换逻辑，Agent 每次调整输出格式，所有适配器都要跟着改，维护成本很高。因此需要把“生成”和“发布”解耦，中间增加一层可复用的转换管线。

## 问题

主要问题集中在四类：

1. **渲染差异**：表格、脚注、任务列表、代码块、数学公式在不同平台支持程度不同。微信基本不渲染标准 Markdown，需要先转 HTML 再粘贴；Notion 对表格宽度处理不稳定；知乎会拦截部分外链。
2. **图片与链接**：本地相对路径、base64 图片、Obsidian 双链在发布后全部失效。图片必须先上传到图床或 CDN，并替换为远程 URL。
3. **元数据与样式**：YAML front matter 在部分平台会显示为正文；代码块语言标签丢失导致高亮失效；行间距、引用块样式也会变形。
4. **自动化断点**：没有统一中间格式时，Agent 输出一变，所有平台适配器都要联调。

## 做法/步骤

**1. 定义单一源格式**

在仓库或工作区固定一个“可移植 Markdown”子集。例如只允许 ATX 标题、围栏代码块带语言、标准表格、普通图片语法、绝对 URL；禁用脚注、YAML front matter、内嵌 HTML、硬换行。元数据放到单独的 JSON/sidecar 文件里，不要混在正文。

这一步的价值是：Agent 输出可以提前约束。把规则写进 system prompt 或输出 schema，AI 生成的内容直接符合子集，后续清洗成本大幅下降。

**2. 建立中间转换层**

不要直接改原始文本，而是用解析器把 Markdown 转成 AST 或结构化数据，再按平台 profile 输出。Python 可以用 `markdown-it-py`，Node 可以用 `remark`，也可以直接用 Pandoc 做批量转换。关键是转换层只依赖源格式，不依赖某个 Agent 的具体写法。

**3. 图片先上传**

转换前扫描所有 `![](...)` 图片路径，统一上传到图床并替换为远程 URL。如果是本地相对路径，必须在这一步处理完，否则发布后图片裂掉。图片上传可以做成独立插件或 MCP tool，输入是本地路径，输出是远程地址映射。

**4. 维护平台 profile**

每个平台一个 profile 文件，例如 `wechat.json`、`zhihu.json`、`notion.json`。里面描述：支持哪些元素、代码块如何处理、表格是否允许、emoji 是否保留、换行规则、外链是否会被拦截等。转换器读取 profile 后决定保留、降级还是替换。

**5. 校验与回归样本**

准备一组固定 Markdown 样本，覆盖标题、列表、代码、表格、图片、引用、任务列表等。每次转换后用脚本检查关键元素是否保留，必要时截图对比渲染结果。新平台接入时先跑回归样本，避免手工发布后才发现问题。

## 踩坑点

- **微信公众号**：必须转 HTML，且直接转换容易丢样式。代码块要转成带背景的 `pre`，表格需要显式 `border`，长代码要处理换行。行内样式最好服务端内联，避免粘贴后丢失。
- **代码块语言丢失**：粘贴到微信或部分编辑器时，围栏代码块会变成无语言文本。可以在转换层提前用 highlight.js 做服务端渲染，把高亮后的 HTML 作为最终输出。
- **外链拦截**：知乎、微信可能拦截或屏蔽外链。需要在 profile 里标记“外链风险”，对关键链接做平台内跳转或文字提示。
- **表格列数**：复杂表格在部分平台会被截断或挤压。源格式建议限制表格不超过 4 列，避免合并单元格。
- **数学公式**：多数平台不支持 LaTeX。应在 profile 中标记“不支持公式”，自动转成图片或纯文本，而不是保留 `$...$`。

## 可复用建议

- 把“可移植 Markdown”规则内置到 Agent 输出约束中，让生成内容天然符合管线要求。
- 转换层单独做成 MCP tool，例如 `markdown.transform`，输入源 Markdown、目标平台、图片映射，返回适配后的文本或 HTML。新增平台只加 profile，不改主流程。
- 保留每个平台的转换快照，发布前人工抽查一次，尤其是代码块和表格。
- 不要假设 Pandoc 默认参数适合所有平台，必要时针对微信、知乎自定义模板。

## 总结

Markdown 管线本质上是一个“编译”过程：从 AI 生成的粗粒度 Markdown，经过规范化、资源处理、平台适配，最终得到可发布内容。工程化的关键是固定源格式、分离转换与发布、用 profile 管理平台差异，并用回归样本验证。这样 Agent/MCP/插件可以稳定输出，而不是每次发布前手动修补格式。
