## 背景

在 OpenClaw 里接上 Agent、MCP、插件之后，很容易出现一种情况：所有任务都无脑走同一个模型。要么全部发给云端 GPT，成本越来越高，敏感数据也不合适；要么全部压给本地 7B/8B 模型，复杂推理和工具调用经常翻车。

多模型路由不是“省到极致”，而是把适合本地干的活稳定留在本地，把真正需要强推理的活交给 GPT。这篇文章记录我在 OpenClaw 环境里做多模型路由的一套做法，偏工程落地。

## 问题

路由最难的不是“写几个 if”，而是这三点：

1. 任务类型判断不准，简单抽取被送到 GPT，复杂推理反而被本地模型接住。
2. 本地模型输出不稳定，尤其是 JSON、工具参数，一次解析失败就会中断整条 Agent 流程。
3. 隐私和 fallback 冲突：本地模型失败了，要不要自动切 GPT？切了会不会把内部文档发到云端？

所以路由策略不能只按模型能力，还要同时考虑数据敏感性、延迟、成本和可回退性。

## 做法/步骤

### 1. 先建立模型能力清单

在 OpenClaw 的模型配置里，给每个模型标注能力字段，不要只写一个名字。例如：

- `cloud-gpt`：reasoning、tool_call、json_mode、长上下文、成本高、延迟中
- `cloud-gpt-mini`：轻量推理、分类、抽取、成本低、延迟低
- `local-qwen`：分类、抽取、脱敏、格式转换、离线、成本极低、延迟低
- `local-llama`：备用本地模型，长文本能力略强，但显存占用更高

这一步看起来啰嗦，但后续路由规则都以这些能力标签为准。

### 2. 用规则先切大类，不要一上来就做智能路由

在 OpenClaw 里可以写一个 `model_router.yaml` 或插件节点，按下面顺序判断：

```yaml
rules:
  - name: offline_or_sensitive
    when: "offline_required or contains_pii(text)"
    model: local-qwen

  - name: light_task
    when: "task_type in ['extract', 'classify', 'summarize', 'format', 'rewrite']"
    model: local-qwen

  - name: complex_task
    when: "task_type in ['reasoning', 'code', 'planning', 'tool_use']"
    model: cloud-gpt

  - name: default
    model: cloud-gpt-mini
```

这个顺序很关键：**隐私和离线判断必须放在最前面**，不能被后面的复杂任务规则覆盖。

### 3. 对本地模型做结构化约束

本地模型最常翻车的地方是 JSON 输出。比如 MCP 工具需要 `{"action": "search", "query": "xxx"}`，本地模型可能输出：

```text
{"action": "search", "query": "xxx"
```

或者前后多出解释文字。

我的做法是：

- 用 grammar 约束输出，比如 llama.cpp / Ollama 的 `format=json`，但不完全可靠。
- 在 prompt 里给 2 个 few-shot 示例，明确要求“只输出 JSON，不要解释”。
- 代码层做容错解析：截取第一个 `{` 到最后一个 `}`，再做一次 `json.loads`，失败才触发 fallback。
- 对于严格的结构化场景，不要依赖本地模型直接生成 tool_call，而是本地模型输出简单字段，由 OpenClaw 插件组装成 MCP 工具参数。

### 4. 设置 fallback 策略

本地模型超时、输出非法、工具参数解析失败时，可以自动切到 GPT。但要注意：

```text
本地失败 -> 判断任务是否包含敏感数据
  - 无敏感：切到 cloud-gpt-mini，并记录失败原因
  - 有敏感/离线要求：直接返回错误，不自动切云端
```

最多允许一次 fallback，避免在 local 和 cloud 之间来回切换形成死循环。

## 踩坑点

- **本地模型 JSON 不闭合**：不要只靠提示词，必须加代码层解析兜底。
- **上下文截断**：本地模型 context 经常只有 4K/8K，长文档直接送进去会被截断，输出质量很差。路由前先检查 token 数，超过阈值直接上云端。
- **敏感信息判断不要交给本地模型**：本地小模型漏判率不低。敏感信息优先用规则、正则、NER 白名单判断，模型只做辅助。
- **冷启动和显存**：本地模型按需加载会有明显延迟。建议常驻一个 7B 级别模型，大模型不要频繁加载卸载。
- **工具调用参数生成不稳定**：本地模型直接生成 MCP tool_call 参数很容易出错。建议工具调用统一走 GPT，本地模型只做参数预处理或结果格式化。

## 可复用建议

1. 路由粒度从“节点/工具”开始，不要一开始就做 prompt 级路由。
2. 把成本、延迟、解析成功率都打进日志字段，每周看一次哪些任务在 cloud 上花费最多。
3. 优先把“可验证”的任务切给本地模型：分类、抽取、格式转换、简单摘要。
4. 本地模型先跑“影子模式”：同时调用本地模型，但结果不直接使用，先和 GPT 输出对比，连续稳定后再切换。
5. 在 OpenClaw 里把路由策略做成配置文件，而不是硬编码在插件代码里，方便后续调整。

## 总结

多模型路由的核心不是省钱，而是让模型各司其职。我的实际体验是：GPT 负责复杂推理、代码生成、多步工具调用；本地模型负责分类抽取、敏感数据处理、离线批处理和低延迟响应。先把隐私和离线判断放在路由最前面，然后按任务类型切大类，最后用结构化约束和 fallback 兜底。这样一套下来，成本会明显下降，同时复杂任务的成功率不会受到太大影响。
