# AI 助手 heartbeat 设计：轮询 vs 推送的取舍与混合兜底实践

## 背景

在 OpenClaw、Agent、MCP 以及插件自动化的实践里，heartbeat 很容易被简化成一句“定时发个包证明还活着”。但 AI 助手的任务链路通常比普通微服务更长：一次 Agent 运行可能要连续调用多个工具、经过多轮推理，期间没有任何输出，前端或调用方只能靠心跳判断“是不是卡死了”。

heartbeat 不只是保活信号，还承担着任务状态同步、进度上报、断线检测和恢复触发。设计不当会导致两类典型问题：轮询过密拖垮服务端，推送断线后任务状态丢失。下面结合 OpenClaw 插件和 MCP 场景，梳理一套可落地的取舍方法。

## 问题拆解

先明确 heartbeat 的目的，再谈传输方式。通常有四种诉求：

1. **保活**：确认对方进程还在，连接没被 NAT/代理静默断开。
2. **状态同步**：让调用方知道任务当前处于 `running`、`waiting_for_tool`、`done` 还是 `failed`。
3. **进度上报**：长任务需要知道完成百分比或当前步骤。
4. **断线检测与恢复**：连接异常后，能重新对齐状态，而不是从零开始。

轮询的优势是实现简单、无状态、天然兼容 HTTP 和防火墙；缺点是延迟取决于间隔，且空闲时也会产生请求。推送（SSE/WebSocket/Webhook）延迟低、服务端主动，但需要处理连接管理、重连、背压和事件丢失。

在 AI 助手场景中，任务状态变化通常不是高频的，但调用方对“卡住”的感知要尽量及时。因此，纯粹的轮询或纯推送都不理想，混合模式成本最低。

## 做法：定义轻量心跳契约 + 推送优先、轮询兜底

### 1. 统一 heartbeat 结构

不要只发 `ping`/`pong`，把心跳和任务状态合并。一个够用的结构如下：

```json
{
  "seq": 123,
  "task_id": "task_01H...",
  "status": "running",
  "progress": 0.42,
  "ts": 1716900000000
}
```

字段尽量少，避免把大段日志或工具输出塞进心跳。`seq` 用服务端单调递增序列号，不要依赖客户端时间戳，防止时钟漂移误判。

### 2. 推送通道：SSE 优先，WebSocket 按需

OpenClaw 这类宿主通常已有事件总线，插件内部可以直接订阅任务状态变更事件。对外暴露时，如果只需要服务端到客户端单向通知，SSE 比 WebSocket 更简单：自动重连、基于 HTTP、无需额外握手。在 SSE 流里，每隔 15–30 秒发一次 `: keepalive` 注释，防止代理断开空闲连接。

如果插件需要双向通信，比如客户端主动取消任务，再上 WebSocket。但不要用 WebSocket 重写一遍 HTTP 已有的查询能力，取消操作直接 POST `/tasks/{id}/cancel` 更清晰。

### 3. 轮询兜底：定时全量拉取

无论推送通道多稳定，都必须保留一个 `GET /api/tasks/{id}/heartbeat` 或等价的查询接口。客户端维护 `last_seen_at`，超过 `3 × heartbeat_interval` 没收到推送时，自动降级为轮询，并做一次全量状态拉取。

重连时不要只重新订阅，要先拉取一次当前状态，因为断线期间可能漏掉了中间事件。SSE 可以用 `Last-Event-ID` 或服务端游标补发，但实现成本较高时，一次全量拉取足够覆盖大多数场景。

### 4. MCP/插件内的心跳

MCP 的 JSON-RPC 通知没有响应，不适合单独作为存活判断。建议在 MCP server 里实现一个 `ping` 方法，客户端周期性发 request，等待 response，超时触发重连或重启 server。OpenClaw 插件的宿主通信也一样，不要只依赖单向事件通知，保留一个同步的 `health` 命令。

## 踩坑点

- **推送连接在 ≠ 任务健康**：代理可能只保持 TCP 连接但应用层已经收不到数据，必须加应用层心跳，不能只看 socket 状态。
- **轮询间隔一刀切**：多任务并发时，统一 1 秒轮询会把服务端打爆。可以在任务活跃时高频（2–5 秒），空闲超过 1 分钟后降到 15–30 秒，用指数退避。
- **时间戳误判**：客户端和服务端时钟不一致时，仅靠时间戳判断超时会误报。用服务端 `seq` 或单调时钟。
- **推送丢失中间状态**：网络闪断后重连，如果只恢复订阅，可能永远不知道任务已经失败。必须支持全量拉取兜底。
- **心跳包过大**：把日志、堆栈、工具输出都放进心跳，会阻塞推送通道，甚至拖垮前端。心跳只带状态和进度，详细内容走单独查询。
- **通知型心跳无确认**：MCP 通知或 UDP 式心跳无法确认对端存活，一定要有一个 request/response 类型的健康检查。

## 可复用建议

1. **默认混合模式**：SSE/WebSocket 推送优先，超时或断开后自动降级为轮询，恢复后再切回推送。
2. **心跳间隔参考**：保活 15–30 秒，任务进度 2–5 秒；超时阈值设为 3 次心跳间隔，避免误判。
3. **心跳只做轻量同步**：状态变更用事件，进度用节流（例如 200ms 内最多推一次），大字段走独立接口。
4. **在 OpenClaw 里复用宿主事件总线**：不要自己起一套定时器和连接管理，优先把任务状态写入宿主已有的 pub/sub，再按需暴露 HTTP/SSE。
5. **记录心跳只记状态变更**：避免每次心跳写日志，否则日志量会非常大，排查问题反而困难。
6. **测试要覆盖**：半开连接、乱序 `seq`、重复心跳、推送断线后降级轮询、MCP ping 超时重启等场景。

## 总结

轮询和推送不是二选一，而是相同心跳语义下的不同传输策略。AI 助手的任务状态变化不频繁，但对“卡住”的感知要求较高，因此“推送优先、轮询兜底”是最务实的组合。核心在于三点：轻量统一的心跳契约、可降级的兜底查询、以及断线后的全量状态重对齐。先保证可恢复性，再追求实时性，能避免大部分 heartbeat 相关的线上问题。
