## 背景

在 OpenClaw-CN 给 Agent 接 memory_recall 时，最常遇到的问题不是“记忆存不进去”，而是“存进去后召不回对的东西”。我做过一个实验：同一个 memory 库，分别用 SQLite FTS5 全文搜索和本地 embedding 做语义搜索。结论是二者互补，但单独上任何一个都会有明显失败样本。这里把过程记录下来。

## 问题

全文搜索依赖词面匹配，对改写、同义表达不鲁棒；语义搜索对语义相近但事实无关的内容容易误召回，对 ID、路径、版本号、报错原文不敏感。Agent 执行任务时往往既需要“上次那个连接池报错是什么”，也需要“之前用户说过不喜欢自动升级”。这是两种不同的召回场景。

## 做法/步骤

1. **先建评估集**。从真实运行日志里抽 50 条 memory 查询，标注应该命中的 memory id。没有评估集，后面所有对比都是凭感觉。
2. **全文搜索基线**。建 FTS5 表，BM25 排序。中文如果没有分词器，先用 jieba 分词后写进 FTS 文本字段。
3. **语义搜索基线**。把 memory 按 300–500 字分块，title 单独保留为 metadata，用本地 embedding 模型生成向量，查询时取 top20。
4. **混合检索**。两边各召回 top20，用 RRF 合并排序；或先按 metadata 过滤，再让语义搜索在候选集内排序。
5. **统计失败样本**，按“精确型查询”和“模糊型查询”分类。

## 结果

在我的测试集上，全文搜索在命令、路径、报错原文、专有名词的 recall@5 明显更高；语义搜索在用户改写后的查询上更好，比如“上次那个内存问题”能召回具体的 OOM 记录。

语义搜索最大的坑是数值范围：查询“内存超过 500MB”可能召回“内存低于 300MB”，因为语义上它们都是内存相关。全文搜索最大问题是分词和大小写：中英文混合 ID 容易漏召回。

## 踩坑点

- 不要固定相似度阈值。0.7 在一个 embedding 模型上可能很宽松，换模型或换领域就需要重新标定。
- 语义搜索的 top_k 不要太小，20 比较稳；先召回再过滤，不要用低 top_k 把候选截断。
- metadata 过滤比调权重重要。时间、来源、类型过滤往往比向量相似度更能救召回。
- 增量写入后，FTS 索引和向量索引都要维护，否则旧 memory 被召回但内容已更新，Agent 会拿到过期信息。
- 混合检索的权重不要拍脑袋。用验证集扫几组，RRF 的 k 值也可以从 60 开始调。

## 可复用建议

- 第一版先用全文搜索，理由是可解释、好调试、对事实型 memory 友好；等出现“换说法就召不回”再引入语义搜索。
- memory 表里保留 source、type、created_at、updated_at、tags，查询时先做 metadata 过滤，再做向量或文本排序。
- 给 memory_recall 返回结果附带 match_type 和 score，让 Agent 能判断这条记忆是词面命中还是语义关联，避免把弱相关当事实。
- 维护一个 50 条左右的回归评估集，每次换 embedding 模型、分词器或权重跑一次，记录 recall@5 和 MRR。

## 总结

语义搜索和全文搜索不是替代关系，更多是两类失败模式。全文搜索负责“精确事实”，语义搜索负责“模糊回忆”。在 OpenClaw/Agent 的 memory_recall 场景里，比较务实的路径是：先全文搜索保住精确查询，再按失败样本加语义搜索，最后混合检索并配合 metadata 过滤。没有评估集的混合检索，很容易变成“看起来高级但召回更差”的负优化。
