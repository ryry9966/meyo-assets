## 背景

在 OpenClaw 里跑长任务或多步自动化时，最明显的消耗不是模型能力，而是上下文里反复交代“项目在哪、命令是什么、哪些目录不能动”。尤其接入 MCP 和插件后，agent 可用的工具变多，行为空间变大。如果每次会话都靠临时指令，很容易出现误用工具、扫错目录、跑出不可逆命令的问题。

AGENTS.md 就是放在工作空间根目录的一份规则手册。OpenClaw 在启动 agent 时可以读取它，把项目约束作为默认上下文注入。它不是给人类看的 README，而是给 AI 的操作边界说明。

## 问题

没有 AGENTS.md，或者写得太随意，典型表现有：

- 每次新会话都要重新描述构建命令、目录结构和启动方式；
- agent 对 MCP/插件只会“随机选一个”，不知道哪个场景用哪个；
- 无法区分可读目录和不可写路径，误改配置或数据；
- 命令副作用不明确，执行删除、发布、迁移前不会暂停确认；
- 团队成员各自教 agent，规则不一致，会话经验无法沉淀。

## 做法 / 步骤

1. 在 OpenClaw 工作空间根目录新建 `AGENTS.md`，确保 agent 每次启动都能读取。
2. 先写“项目是什么”：一段话说明项目用途、技术栈、入口文件。不要写历史背景和人员信息。
3. 定义常用命令：安装、启动、测试、构建、lint、单测。只写 AI 执行任务时会用到的命令，不要堆版本号。
4. 目录结构只列 agent 会碰的层级，并标注权限。例如：

   - `src/` 主代码，可读可改
   - `scripts/` 自动化脚本，只读
   - `data/` 运行数据，禁止修改
   - `config/` 配置文件，修改前需要确认

5. 写清 MCP/插件使用边界。逐一列出已接入的 MCP server 和插件，写明触发场景。例如：“浏览器 MCP 仅用于抓取公开页面，禁止登录态操作；文件插件不得跨出工作空间根目录。”
6. 约束和危险操作单独成节，用“禁止”“需要确认”“只读”三类标记，比长段描述更有效。
7. 补充常见工作流。例如新功能开发的默认路径：拉分支 → 改代码 → lint → test → 提交 PR。给 agent 一个稳定路径，减少自由发挥。

## 踩坑点

- **把 AGENTS.md 写成 README 缩小版**。堆砌背景、架构演进、团队分工，AI 检索关键信息成本很高。控制在 300 行以内比较合适。
- **只写命令不写副作用**。例如写了 `rm -rf` 但没说明目标范围，agent 可能在错误目录执行。危险命令必须标注影响面。
- **和环境漂移**。新增 MCP、改端口、迁移目录后不更新 AGENTS.md，agent 会照着旧规则做。
- **使用模糊表达**。“适当测试”“合理使用工具”这类话 agent 无法判断。要用“必须”“禁止”“仅当……才……”这样的确定性语言。
- **规则过严把 agent 锁死**。如果要求每一步都确认，多步自动化任务会退化成人类手动驱动。

## 可复用建议

- 用固定标题分节：项目概览、命令、目录、MCP/插件、边界、工作流。
- “禁做清单”比大段解释更有效。先写清楚不能做什么，再说推荐路径。
- AGENTS.md 纳入版本管理，和代码同步评审。任何工具链变更、MCP 接入、目录调整，都要在 PR 里同步更新。
- 单个章节超过 50 行就拆到独立文件，在 AGENTS.md 里只保留摘要或链接，避免文件膨胀。
- 定期跑一次“空会话”验证：新会话只读 AGENTS.md，让 agent 复述关键规则，看它理解是否一致。

## 总结

AGENTS.md 的目标不是完整描述项目，而是让 agent 在不猜测的情况下选对目录、用对工具、避开危险操作。在 OpenClaw 的多 MCP/插件环境里，这份文件能把重复引导成本降下来，也能把不可逆错误概率降下来。

写得越像规则手册，越有用；写得越像项目介绍，越会被忽略。
