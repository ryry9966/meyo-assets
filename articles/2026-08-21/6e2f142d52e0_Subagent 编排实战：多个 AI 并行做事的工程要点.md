## 背景

单个 Agent 同时处理多个数据源时，上下文很容易膨胀：抓取、清洗、检索、写文件全混在一个会话里，后几步经常被前几步的中间产物干扰。串行执行也慢，尤其调用外部插件或 MCP 服务时，等待时间会叠加。

Subagent 编排的思路是把复杂任务拆给多个子代理，主控只做分发、校验和汇总。这样每个子代理上下文更小、工具范围更窄，多个任务可以并行推进。

## 问题

不是所有任务都适合并行。适合 subagent 的场景通常满足三个条件：数据源或步骤相对独立、结果可以结构化、失败可以重试。

不适合的情况包括：强依赖执行顺序、需要共享大量中间状态、结果之间强耦合。并行前先问一句：子任务的输入能否压缩成一小段？输出能否用一个 JSON schema 描述？如果不能，不要强行上 subagent。

## 做法/步骤

1. **主控只做编排。**  
   主控 prompt 里明确：不亲自执行，只拆解、分配、校验。拆解结果写成任务清单，每项包含 id、目标、输入和期望输出 schema。

2. **子代理单一职责。**  
   每个子代理只绑定完成该任务所需的最小工具集和 MCP 连接。例如一个只读 Notion，一个只调搜索插件，另一个只写本地文件。在 OpenClaw 的子代理配置中，我会显式声明 MCP tools，而不是继承主代理全部工具。

3. **约定结构化输出。**  
   子代理输出必须包含 `result` 和 `error` 两个字段，`result` 内部按预设 schema 组织，不要返回自由文本。主控收到后先解析，失败则携带原始错误重试一次。

4. **控制上下文。**  
   不要给子代理全量主对话历史。只传该任务需要的上下文切片、相关文件和约束。上下文越少，子代理越不容易跑偏。

5. **并行与超时。**  
   每个子代理独立设置超时，主控用并发调度，不因一个挂起而阻塞其他任务。全部返回后再统一合并。

6. **汇总校验。**  
   主控检查字段缺失、冲突、重复。必要时再启动一个 repair 子代理，专门处理合并和格式修复。

## 踩坑点

- **上下文越传越多。**  
  主控把前几轮完整结果抛给后续子代理，导致后期又慢又贵。解决方法是只传最终结果和必要引用，不传过程稿。

- **工具或插件冲突。**  
  多个子代理同时写同一文件，或同时调同一个 MCP 写接口，容易出现覆盖和限流。写操作最好集中到一个子代理，或者加锁、排队。

- **JSON schema 漂移。**  
  模型有时返回 markdown 包裹的 JSON、缺失字段或类型错误。解决：prompt 里给完整示例；主控做 defensive parse；失败重试时把原始报错一并带回。

- **伪并行。**  
  底层模型网关或 MCP server 有并发上限，并行度上不去，所谓并行退化成串行。上线前先低峰压测，设置合理并发数和限流。

- **排障困难。**  
  子代理失败后如果只报 timeout，没有中间信息，很难定位。让每个子代理输出 `trace_id` 和关键步骤，日志单独记录。

## 可复用建议

准备一套 subagent 模板，固定包含 Role、Input Schema、Output Schema、Rules、Example。主控不要替子代理思考，只给约束和验收标准。

先跑 2 个子代理并行，稳定后再扩展。记录每个子代理的 token 消耗、耗时、重试次数，方便找瓶颈。MCP 连接命名带上资源类型和读写权限，避免误接。

## 总结

Subagent 编排的价值不在“多个 AI 同时聊天”，而在把任务边界、上下文、工具权限和失败重试工程化。先定契约，再并行；先做小规模灰度，再扩大。这样多 AI 并行做事才会稳定可维护。
