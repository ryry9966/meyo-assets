最近在 OpenClaw 里让 agent 参与代码生成后，最耗精力的往往不是模型写得好不好，而是每轮变更后要手动 `git add`、切分支、写 commit message。于是我把 Git 操作包装成受限工具，交给 agent 调用。这里记录一套可复用的做法，适合已经在用 MCP、插件或自定义工具链的工程化用户。

## 背景与问题

Agent 生成代码后，通常会出现三类问题：

1. **提交噪音大**：模型一次改多个模块，提交信息写成 “update” 或 “fix”，历史不可追溯。
2. **分支混乱**：agent 在主分支直接改文件，或者创建一堆无意义分支。
3. **操作不可控**：如果直接给 agent 一个 shell，它可能执行 `push --force`、`reset --hard`，风险很高。

所以目标不是“让 AI 替你敲 git 命令”，而是把确定性的 Git 操作工具化，把判断留在人和规则里。

## 做法与步骤

### 1. 将 Git 能力封装为白名单工具

通过 MCP Git server 或 OpenClaw 的工具封装，只暴露少数安全命令：

- `git status --porcelain=v1`
- `git diff -- <pathspec>`
- `git diff --cached`
- `git add <file>`
- `git commit -m <message>`
- `git branch --show-current`
- `git switch -c <branch>`

禁止：`push --force`、`rebase`、`reset --hard`、`clean -fd`、`checkout -- .` 等破坏性操作。工具返回结构化文本，而不是让模型读原始终端输出。

### 2. 让 agent 先读 diff，再生成提交信息

每次提交前，要求 agent 先读取 `git status --porcelain` 和 `git diff`，再输出提交计划。可以用类似提示词：

```text
请基于以下 git diff 生成提交信息：
- 格式：type(scope): subject
- type 仅限 feat/fix/docs/test/chore/refactor
- subject 不超过 72 字符
- 不要包含文件路径
- 如果变更跨多个模块，请拆分为多个 commit
```

这样能有效减少“一次性提交全部文件”的情况。agent 可以先给出 plan，人工确认后再执行。

### 3. 自动分支管理

在任务开始时创建 `agent/<task-id>-<slug>` 分支，完成后提交并通过 PR 合并。合并前由人 review，主分支不直接允许 agent push。

示例流程：

```text
agent 收到任务 -> 创建分支 agent/task-231-fix-upload -> 修改文件 -> 
读取 diff -> 生成提交信息 -> 执行 commit -> 推送分支 -> 人审 PR
```

### 4. 用 hooks 守住底线

在仓库里配置：

- `pre-commit`：跑 lint/format，拒绝明显格式问题。
- `commit-msg`：校验 Conventional Commits，正则不通过则提交失败。
- `pre-push`：禁止直接 push 到 `main` 或 `master`。

这些 hooks 对 agent 和人都生效，避免自动化绕过质量检查。

## 踩坑点

1. **自动提交产生大量噪音**：agent 可能在一次任务里生成十几个 “fix lint” commit。建议在推送前执行 `git rebase -i` 或 squash，把未推送的提交合并成一个有意义的提交。

2. **误提交敏感文件**：即使给定了 pathspec，模型仍可能把 `.env` 或密钥文件加入暂存区。建议在 `pre-commit` 中接入 `gitleaks` 或 `detect-secrets`，直接拒绝包含敏感信息的提交。

3. **并发操作冲突**：两个 agent 同时在同一仓库执行 git 命令会导致 index 锁冲突。可以限制同一时刻只允许一个 git agent 操作，或为每个任务创建独立 worktree。

4. **模型重试死循环**：当 git 操作失败时，agent 可能不断重试。建议设置最大重试次数，失败后将完整上下文交给人处理，而不是继续自动执行。

5. **提交信息夸大**：模型生成的 commit message 可能声称“修复了 X”，但实际只改了一个拼写。PR review 时要重点检查提交信息与 diff 是否一致，必要时在 squash 时重写。

## 可复用建议

- **先 plan 后执行**：让 agent 输出「将要提交的文件、分支、message」，人工确认后再调用工具。
- **提交带追溯标记**：在 commit body 中添加 `Origin: openclaw-agent` 或 `Task: #123`，方便后续过滤和统计。
- **工具输出作为上下文**：每次执行前先读 status/diff，不要让模型凭记忆操作。
- **不要跳过 hooks**：即使是 agent 提交，也必须走完整 hooks 流程，否则会污染仓库。
- **保留人工回滚权**：自动化只负责常规提交，遇到冲突、模糊变更或大范围删除时，应停止并交给人。

## 总结

Git 自动化在 OpenClaw 工作流里的价值，不是让模型替你做所有决定，而是把重复、确定性的操作固化为工具调用。模型负责理解 diff 和生成规范提交，工具负责执行命令，人负责审核合并和回滚。限制越清楚，自动化越可靠。与其追求“一键全自动”，不如先把边界、hooks 和可追溯性做好。
