## 背景

在基于 OpenClaw 搭建自动化内容管线时，我曾把多个段落的长摘要、元数据一股脑塞进一份 JSON 要求模型返回。结果模型很努力，但总在关键位置给惊喜：段落中的双引号没转义，换行直接躺在字符串里，或者末尾少一个闭括号。每次 `JSONDecodeError` 抛出来，整个 Agent 流程就卡死，不得不加解析重试甚至人肉修。

这不是个别现象。当要求 LLM 输出带有大段自由文本的 JSON 时，因为模型本质是按 token 序列生成，它对括号配对、转义协议的遵守远不如专用编码器。可是在许多自动化任务——比如分章节摘要、多步规划加备注、插件返回含描述的元数据——我们确实需要长文本和结构标记一起出现。

## 问题再往下挖一层

典型失败模式包括：

- **短距离的灾难**：长字符串内未转义的双引号，JSON 解析直接崩。
- **多余的逗号**：数组最后一个元素后面多一个逗号，标准解析器不依。
- **截断之痛**：输出超过 `max_tokens`，最后一个对象只剩一半，整体 JSON 不可用。
- **将所有文本塞进一个值**：逼迫模型把一篇文章压成单个字符串，只要含有换行、反斜杠就会出现转义问题。

这些问题的根源不是模型“笨”，而是 **JSON 对载有大段自然语言文本的内容过于严苛**。我们需要一种对文本更亲和、又保有基本结构标记能力的替代方案。
