## 背景

在构建面向多个内容平台的自动发帖流水线时，我遇到了一个被大多教程忽略的问题：**中间产物的持久化与可溯源性**。通常我们会用 Agent + MCP 工具链生成文章、配图，然后直接推送到目标平台。一旦发布失败、需要回溯某篇内容，或要基于历史素材做二次创作，就会陷入“原文找不到了”“图片链接已失效”的窘境。

为此，我在自己的 OpenClaw 工作流中引入了一套**本地归档规范**：每次运行发帖流水线，不仅输出最终发布物，还在本地文件系统中落盘一份结构化资产，用 `assets.json` 将所有资源关系显式记录下来。这篇文章将分享具体做法、踩过的坑，以及可复用的工程化建议。

## 问题定义

自动化内容生产链路的典型流程是：

1. Agent 根据话题生成 Markdown 正文
2. 调用图像生成工具（如 DALL·E、Stable Diffusion 插件或本地模型）产出配图，得到临时 URL
3. 将图文组装后通过发布工具（如 WordPress REST API、Mastodon API、WeChat MP 等）发送

如果此时流程中断，比如发布失败，或者三天后想找回当时的封面图，你会发现：

- Markdown 内容可能只存在于 Agent 的对话历史中，尚未持久化
- 图片 URL 很可能是云存储的临时签名链接，几天后自动过期
- 没有任何文件记录哪张图片对应哪篇文章、什么尺寸、生成参数是什么

这就导致原本自动化、去人工的流水线，在异常处理和素材复用上又回到了手工翻找的状态。

## 目标

打造一个**本地优先的归档节点**，位于“内容生成完成”与“对外发布”之间，达成：

- 每轮发帖任务在本地生成唯一的日期时间目录
- Markdown 原文以 UTF-8 纯文本落盘
- 配图全部下载到同目录下，用可读文件名管理
- 生成一份 `assets.json`，记录文章元数据、图片文件清单、关联关系及生成参数
- 归档完成后，发布步骤可直接使用本地文件，无需再依赖外部 URL

## 实践步骤（以 OpenClaw + MCP 为例）

### 1. 选定归档根目录

在项目中约定一个环境变量 `ARCHIVE_ROOT`，如 `/data/archives`。所有归档按日期分层：

```
/data/archives/
  2025/
    03/
      2025-03-15_14-30-00_demo-post/
        article.md
        cover.png
        img_inline_01.png
        assets.json
```

### 2. 生成 Markdown 文章并落盘

在 Agent 生成文章后，用一个简单的函数将内容写入 `article.md`。这里可以直接使用文件系统 MCP 服务器的 `write_file` 工具，或者在自建 Agent 中调用 Node.js/Python 完成。

关键点：保存时必须保证原始 Markdown 中包含的图片引用是**相对本地的临时占位符**，方便后续替换。例如，生成阶段图片可以用 `![alt](TMP_IMG_1)`，待图片下载完成后再批量替换为 `./cover.png`。

### 3. 下载图片到本地

图像生成接口返回的通常是一个临时 URL。我们需要用 HTTP 客户端将图片流式下载到归档目录下。实践中我写了一个小工具 `download_and_localize_images`，逻辑如下：

- 从 Markdown 中提取所有形如 `TMP_IMG_*` 的占位符及其实际 URL
- 根据图片用途（封面/内联）和顺序生成文件名：`cover.png`, `img_inline_01.png` 等
- 逐一下载，校验 HTTP 状态码、Content-Type，确保是有效图片
- 下载后立即计算文件 SHA256，存入后续 JSON

注意：下载过程要有重试机制（3次，指数退避），防止临时 URL 短暂不可达导致的归档失败。

### 4. 构建 assets.json

这是整个归档的核心。`assets.json` 设计为一个 JSON 对象，包含：

```json
{
  "archive_id": "2025-03-15_14-30-00_demo-post",
  "created_at": "2025-03-15T14:30:00Z",
  "title": "自动发帖流水线如何做本地归档",
  "source_prompt": "...", // 可选，生成文章用的 prompt 摘要
  "article": {
    "file": "article.md",
    "sha256": "abc123..."
  },
  "images": [
    {
      "id": "cover",
      "file": "cover.png",
      "sha256": "def456...",
      "width": 1200,
      "height": 630,
      "generation_params": {
        "model": "dall-e-3",
        "prompt": "A tech archive pipeline diagram...",
        "size": "1792x1024"
      },
      "original_url": "https://cdn.openai.com/...",
      "downloaded_at": "2025-03-15T14:30:03Z"
    }
  ],
  "publish_targets": ["wordpress", "wechat_mp"],
  "status": "archived"
}
```

这种结构化数据的收益在于：以后任何工具或脚本只要找到这个 JSON，就能完整复现当时的资源集合，而无需解析 Markdown 或依赖文件名约定。

### 5. 将归档接入后续发布步骤

发布工具读取 `assets.json`，获取 `article.file` 路径，用本地 Markdown 文件作为正文；图片则直接使用本地路径或上传到目标平台的对象存储并替换链接。这样即使外部图片源已失效，发布流程丝毫不受影响。

## 踩坑记录

### 坑1：图片下载时文件名冲突
多次生成同一类图片（如多个“内联图”）时，若并行下载并使用相同的递增序号，可能出现覆盖。解决：在下载函数内使用互斥锁，或者预先生成所有文件名并原子化写入。

### 坑2：临时 URL 的时效窗口极短
某些国内模型厂商返回的图片 URL 仅 60 秒有效。所以图片下载必须在文章生成的 **await 链中立即执行**，不能延后。为此我将图片生成与下载绑定为一个原子操作：Agent 拿到 url 的同时，异步触发下载，并限制超时 30 秒。

### 坑3：Markdown 内图片引用替换不彻底
如果文章中有同一张图被多次引用（比如封面也出现在文末），只替换一次会导致残留的临时占位符。需要全局搜索替换所有出现的位置，并验证替换后文中不含任何 `TMP_IMG_` 字符串。

### 坑4：归档目录膨胀
高频运行流水线会快速堆积大量目录。我增加了一个清理策略：默认保留最近 30 天的归档；超出部分压缩为 tar.gz 并移动到冷存储目录，同时在 `assets.json` 里记录归档包路径以备解压。

## 可复用建议

1. **将归档逻辑封装为独立 MCP 工具或 Skill**
   例如实现一个 `archive_content` 工具，输入为 Markdown 文本 + 图片 URL 列表，输出为归档路径和 `assets.json` 内容。这样任何 OpenClaw Agent 只需调用一个 Tool 即可完成本地持久化。

2. **利用 assets.json 做内容审计与回溯**
   可以与 Git 结合，将 `assets.json` 纳入版本控制，跟踪每次自动发帖的素材来源和生成参数，便于后续分析什么类型的 prompt 产出质量高。

3. **标准目录结构便于外部消费**
   第三方预览工具或静态站点生成器可以直接遍历日期目录，根据 `assets.json` 中的 `title` 生成索引页，实现自动化博客存档展示。

4. **注意隐私与存储安全**
   归档中包含生成 prompt 和历史链接，可能含有敏感信息。建议归档根目录权限设为 `0700`，避免被 web 服务意外暴露。

## 总结

本地归档并不是自动发帖流水线中最炫的部分，但它决定了这条流水线是“一次性脚本”还是“可维护的工程资产”。通过落盘文章、下载图片、构建 `assets.json`，我们让每一次 Agent 运行都留下了可追踪的足迹，在异常恢复、素材复用和合规审计方面都有了坚实的基建。

这套做法在 OpenClaw 生态中可以直接用文件系统 MCP 服务器 + 少量自定义逻辑实现，无需引入额外后端服务。如果你也在折腾内容自动发布，不妨试试在“发送”按钮前加一个“归档”步骤，它会是你未来不后悔的决定。
