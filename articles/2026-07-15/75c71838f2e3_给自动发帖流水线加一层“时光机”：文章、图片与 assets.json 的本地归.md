## 背景
基于 OpenClaw Agent + MCP 自动生成内容并发布到多个平台，已经成为不少技术写作者和运营团队的常规操作。这些流水线通常专注于“生成 → 推送”，链路短且直接。但一段时间后你会发现：平台上的编辑历史不可靠，被删改后无法追溯原文；图片链接可能过期或被压缩；换平台重发时，原始素材早已散落各处。本地归档不是“备份”，而是让自动化发帖具备可审计、可复用、可恢复的基础能力。本文将拆解一个轻量方案：如何用目录、Markdown 文件和 `assets.json`，把文章与配图统一归档到本地。

## 问题拆解
发帖流水线中，需要归档的内容通常包含三类：
- 正文（Markdown 或 HTML）
- 配图（可能是本地生成或下载的）
- 元数据（标题、平台、发布时间、标签、图片引用关系、生成参数等）

常见痛点：
1. 文件与元数据割裂，只保存了正文，丢掉了图片来源和版本信息。
2. 目录结构随意，几个月后连自己都找不到。
3. 同一篇文章发布到多个平台后，缺乏统一的家乡记录（source of truth）。
4. 图片引用路径在平台发布时往往需要转换成绝对 URL，本地归档用相对路径，两种路径容易混淆。

## 实战方案：三层归档结构
我们采用“日期平台 + 文章目录 + 元数据”的递进式结构，既能快速查找，也方便工具解析。

### 1. 目录与文件约定
```
archives/
└── 2025-04-22_x/
    └── my-article-slug/
        ├── article.md
        ├── images/
        │   ├── cover.png
        │   └── diagram.png
        └── assets.json
```
- **父目录**：`{日期}_{平台}` 前缀，如 `2025-04-22_twitter`，若多平台可共用同一个 slug 但不同平台目录。
- **文章目录**：用文章 slug 命名，使用小写连字符，禁止空格和特殊符号。
- **article.md**：最终发布版本的正文副本，内部图片引用使用相对路径 `images/cover.png`。
- **images/**：存放所有原始配图，不压缩、不裁剪，保留生成时的原始文件。若图片来自外链，可选择下载并放置于此。
- **assets.json**：结构化元数据，记录完整上下文。

### 2. assets.json 的设计
一个最小但“够用”的 schema：

```json
{
  "title": "How to Build a Local Archive for Auto Posting",
  "slug": "local-archive-auto-post",
  "platform": "x",
  "publish_date": "2025-04-22T10:30:00Z",
  "tags": ["automation", "openclaw", "archive"],
  "description": "A guide to local archiving...",
  "images": [
    {
      "file": "images/cover.png",
      "alt": "cover image for archive post",
      "source": "dalle",
      "prompt": "A simple diagram showing three layers...",
      "seed": 12345
    },
    {
      "file": "images/diagram.png",
      "source": "screenshot",
      "origin_url": "https://..."
    }
  ],
  "draft": false,
  "word_count": 950,
  "generation_model": "gpt-4o",
  "prompt_summary": "prompt used to generate article..."
}
```

**扩展注意**：若同一内容发布到多个平台，建议为每个平台保留一份 `assets.json`（放在不同平台父目录下），避免一股脑塞进一个文件导致难以维护。也可以用 `platforms` 数组记录，但单文件多平台容易在后续更新时产生字段冲突。

### 3. 嵌入发帖流水线的做法
归档步骤应设计成**副操作（sidecar）**，不影响主发布链路。典型流程：

1. Agent 生成正文与图片，产出 Markdown 文本和图片文件（或图片链接）。
2. 调用归档工具（可以是 MCP Server 的 `local-archive` 工具，或直接在代码中调用函数）。
3. 归档工具负责：根据平台与 slug 创建目录、写入 `article.md`、将图片保存到 `images/`、生成/更新 `assets.json`。
4. 归档完成后，主流程继续执行发布（API 推送）。
5. 发布时，若平台需要图片链接，可从 `assets.json` 中读取线上地址字段（如果已上传到图床），或临时上传后补写回 `assets.json`。这样本地归档保存的是“原件”，线上地址只是衍生品。

如果流水线使用 MCP 工具，可以把归档逻辑封装成一个 `write-archive` 工具，输入参数为 `{ platform, slug, content, images[], metadata }`，Agent 在生成完内容后调用该工具，再调用发布工具。这种模式让归档成为一个可替换的“微服务”，不影响 Agent 核心逻辑。

### 4. 踩坑记录
- **路径与平台命名的摩擦**：平台标识容易写成 `x` 或 `twitter` 前后不一致，建议用一个 `platform.yml` 配置表强制映射，例如 `{"twitter": "x", "x": "x"}`，避免同一平台出现两个目录。
- **Markdown 图片相对路径**：归档用的 `article.md` 必须使用 `./images/...` 或 `images/...` 的相对路径。但发布到平台时，通常需要转换为绝对 URL。可以用正则或 AST 处理，将 `![alt](images/x.png)` 替换成 `![alt](cdn-url)`，发布完成后还原成本地路径再写回归档。不要直接在归档文件中写入线上地址，否则迁移时就是一笔乱账。
- **并发写入问题**：如果多篇文章同时归档，公用同一平台父目录不存在冲突（因为 slug 子目录不同），但创建父目录时可能产生竞争。直接用 `mkdir -p` 或 `fs.mkdirSync({ recursive: true })` 已经足够健壮，极少失败。
- **大文件与 git**：若将归档目录纳入 git 仓库，图片可能快速撑大仓库。建议对大图（>1MB）设置忽略规则，或使用外部存储（如 MinIO）归档，`assets.json` 中只记录本地缩略图的路径和原始图片的哈希/URI。
- **assets.json 的 schema 变更**：随着需求增加，字段肯定会变。可以加一个 `version` 字段（如 `1`、`2`），在读取时做迁移，或者参考 JSON-LD 的思路用 `@context` 声明语义，但实践中一个简单的 version + 文档说明已经足够。

## 可复用建议
- 将归档逻辑封装成**独立 MCP Server**，暴露几个方法：`create_archive`、`update_archive`、`query_archive`。Agent 通过调用这些 MCP 工具即可接入，不关心底层文件操作。
- 配置化归档路径：通过 Agent 的初始化配置或环境变量指定归档根目录，方便团队切换存储位置。
- 命令行辅助工具：在 Agent 之外，可以提供一个简单的 CLI（`archive-tool --platform x --range last-week`）方便人工查询。
- 与现有内容运营工具集成：如果你已经用 Notion、Obsidian 管理内容，可以直接把归档目录映射为仓库，让这些工具直接索引。

## 总结
本地归档看似是“多此一举”，但在自动化内容工作流跑起来之后，它会是你最不后悔的一次投入。三层结构（目录、Markdown、assets.json）成本极低，却解决了溯源、复用、灾难恢复的刚需。更重要的是，它把发帖流水线从一个“一次性消费”的管道变成可积累的内容资产库，后续无论是迁移平台、训练模型、还是二次改写，都有据可依。下手时谨记：归档做副操作，不要阻塞主流程；路径规范化是长期省心的关键；元数据宁可少字段但结构清晰，也不要一个大 JSON 包罗万象。希望这套模式能帮你的自动化实践多一层可靠的底座。
