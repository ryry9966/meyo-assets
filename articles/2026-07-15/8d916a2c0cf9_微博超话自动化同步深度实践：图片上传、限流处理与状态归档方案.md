## 背景

在维护多个社交平台内容矩阵时，微博超话作为高互动场景，很难用官方开放 API 直接完成自动化发帖——超话发帖接口并不在微博公开的 statuses/update 权限范围内，且强制要求图片不能仅以链接形式存在，必须通过内部图片上传流程。我的需求很明确：将已发布在博客或其他平台的文章摘要与配图，以可控、可追溯的方式同步到指定超话，同时规避因调用频率过高引发的封禁。

工具选型上，选择了 OpenClaw 的 Agent 模式，它允许我们自定义执行逻辑并通过插件扩展浏览器、HTTP 请求等能力，适合这类非标接口的集成。目标是实现一个**端到端的同步管道**：读取 Markdown 源 -> 提取正文首段与图片 -> 模拟登录态上传图片 -> 组装超话发帖参数 -> 发送并归档结果 -> 遇限流自动退避重试。

## 问题拆解

整个链路的核心难点有三处：

1. **图片上传接口**：微博 PC 端图片上传使用的是 `https://picupload.weibo.com/interface/pic_upload.php` 这类内部端点，需要有效的 cookie、`crossdomain` 策略以及 multipart/form-data 正确编码，缺一不可。而且返回的 `pid` 才是发帖时直接引用的图片标识，常规图床链接无效。
2. **发帖接口与超话绑定**：发帖并不是标准的 `statuses/update`，而是需要向 `https://weibo.com/aj/mblog/add`（或类似 `aj` 端点）POST 一组特定表单，其中包括 `title`、`content`、`pic_id`、`topic_id`（对应超话）等字段。
3. **限流与状态归档**：非官方接口的请求频率稍高就会触发“操作频繁”或强制验证码，必须有退避机制；同时同步任务需要持久记录成功/失败状态，以便补发和监控。

## 具体实现

### 1. 登录态保温

提供一个心跳函数定期检查 cookie 有效性，失效时通过 OpenClaw 浏览器插件打开微博登录页，用已保存的账号密码自动填充并提交（必须处理可能的短信验证码环节，采用人工介入或第三方接码）。获取到登录后完整 cookie 对象（尤其是 `SUB` 和 `SUBP`），持久化到本地文件，每次请求前加载并检查过期时间。

### 2. 图片上传模块

使用 OpenClaw 内置的 `http` 工具发送 multipart 请求。关键点：

- `Referer` 必须设为 `https://weibo.com/`。
- 表单字段：`file`（文件流）、`type`（固定值 `json`）、`source`（固定值如 `1022`）。
- 文件流需要指定文件名和 `Content-Type`（如 `image/png`）。
- 解析返回 JSON，取 `data.pics.pic_1.pid` 作为后续发帖的 `pic_id`。
- 多图上传需逐个调用并收集所有 `pid`，发帖时以逗号拼接。

遇到的坑：部分图片因尺寸过大或格式限制被拒绝，需要预处理缩放到合理宽度（如 1920px）并保证 `sRGB` 色彩空间，否则返回 `error_code` 不为 0。

### 3. 超话发帖请求

构造 POST 到 `https://weibo.com/aj/mblog/add`，参数包括：

- `_t=0`（保留）
- `title`：可选，空字符串
- `content`：微博正文，可含超话词条前缀 `#超话名称#`
- `pic_id`：前面获取的 pid 字符串
- `topic_id`：超话对应的数字 ID（可从超话页面 URL 抓取）
- `page_id`：与 `topic_id` 一致
- `rank`：0
- `isReEdit`：false
- 其他固定字段如 `location`, `module` 等需从浏览器真实发帖抓包获得。

请求头携带完整 cookie，`X-Requested-With: XMLHttpRequest` 和正确的 `Referer`。返回 JSON 中 `code` 为 `100000` 即成功。反之，错误码如 `100001`（参数错误）、`100005`（限流）等需分别处理。

### 4. 限流处理与退避

实际运行中，微博对同一账号的连续发帖频率极其敏感。策略如下：

- 维护一个全局请求计数器与滑动窗口。若 15 分钟内发帖请求超过 3 次，强制等待到窗口结束。
- 当返回 `msg` 包含“操作频繁”或 `code` 为特定错误时，按指数退避（1min, 5min, 15min）重试，最多 3 次。若仍然失败，标记为“需要人工复查”。
- 遇到验证码要求时，暂停所有自动化任务并输出报警，等待人工处理。

### 5. 状态归档

每次同步任务结束后，将以下信息写入 SQLite：

- 任务 ID、源文件路径
- 图片上传 pid 列表
- 发帖结果：成功/失败/重试中
- 微博返回的 `mid`（帖子 ID）与跳转链接
- 时间戳与重试次数

这样就能构建一个简单的 Dashboard，看到最近哪些内容同步成功，哪些被限流拦截，便于补发和清理。

## 踩坑点整理

- **cookie 作用域**：必须确保 `SUB` cookie 的 Domain 为 `.weibo.com`，否则部分请求鉴权失败。
- **图片 pid 有效期**：上传得到的 pid 不会长期有效，需在上传后短时间内发帖，不然可能“图片不存在”。
- **超话 ID 获取**：不要硬编码，每次发帖前从 `https://weibo.com/p/{超话 containerid}` 页面抓取 `topic_id`，防止超话改名或迁移失效。
- **emoji 和特殊字符**：content 中若包含特殊 emoji，需要转成 unicode 或采用微博支持的格式，否则会被截断或导致接口报错。
- **代理与 IP**：最好使用固定白名单 IP，避免因频繁切换触发风控。

## 可复用建议

将以上流程封装为一个 OpenClaw 插件，提供三个 Action：`upload_image`、`post_to_topic`、`check_status`，由上层调度器按顺序调用。调度器使用内置消息队列（如 Redis Stream），实现“上传-组装-发送-归档”的解耦与重试。可扩展为多账号并行同步，只需为每个账号独立维护 cookie 和限流窗口即可。

限流逻辑和归档模块建议做成公共中间件，其他类似的非标同步任务（如抖音、小红书客户端模拟）也能复用。

## 总结

这种非官方 API 的同步方案属于典型的“工程化 Hack”，它不是一次性的脚本，而是一个需要持续监控、随时准备适配前端改动的小型系统。通过 OpenClaw 的插件和 Agent 能力，可以把登录、请求封装、退避归档这些重复劳动固化下来，达到“一次配置、长期无人值守”的效果。核心价值不是技术炫技，而是真正减少手工搬运内容的消耗，同时把同步过程变得透明、可审计。如果你有类似多平台分发的需求，不妨从“图片上传+限流归档”这个最小闭环开始验证。
