## 背景

在 OpenClaw 生态中，我搭建了一条“AI 生成 → 自动发布到微博超话”的管线，用于将摘要、资讯卡片等内容同步至指定超话。微博开放平台未提供超话发帖的标准 API，因此依赖移动端接口逆向。实践中遇到了几个核心难题：图片上传的特殊编码要求、发帖频率的精细限流，以及多任务并行时的状态追踪。本文记录如何在 OpenClaw Agent 中以插件形式封装这一功能，重点放在图片上传、限流策略和状态归档三部分。

## 问题拆解

- **图片上传**：微博移动端上传使用 `https://picupload.weibo.com/interface/pic_upload.php`，需要有效 Cookie 以及特殊参数、文件字段。上传成功后返回 pic_id（pid），发帖时需引用该 pid。若直接使用 multipart 文件上传，易因参数缺失或 `appid`、`cb` 不匹配而失败。
- **限流**：超话发帖受频率控制，短时间内重复请求会返回 10024 或“操作频繁”等错误，甚至触发账号风控。同时，内容重复度检测会拦截完全相同标题或正文的帖子。
- **状态归档**：同步任务往往批量执行，需要记录每一条内容的上传、发帖状态及失败原因，便于排查和重试。轻量但结构化的持久化方案是必须的。

## 工程实现

### 1. 图片上传模块

基于 `aiohttp` 构造请求。抓包后发现微博移动端上传使用 `pic1` 文件名（不是 `file`），同时需附带固定参数：

```
url: "https://picupload.weibo.com/interface/pic_upload.php"
data: {
    "cb": "http://weibo.com/aj/static/upimgback.html?_wv=5&callback=STK_ijx_xxx",
    "mime": "image/jpeg",
    "data": "base64",  // 实际仍为文件流
    "appid": "...",
    ...
}
files: {"pic1": ("filename.jpg", image_bytes, "image/jpeg")}
```

要点：  
- `cb` 参数需与实际回调一致，可从首页 `tid` 动态获取或写死一个通用值。  
- 必须携带登录 Cookie，否则返回 403。  
- 上传成功后，返回体中通过 `pid` 字段提取图片 ID。

上传失败时处理：解析 JSON 中的 `code`，若非 0 则抛出异常，并在错误日志里记录 `code` 和 `msg`。

### 2. 限流器设计

采用基于时间的令牌桶，每分钟限制 1 次发帖操作（可配置）。实现时在插件内维护一个异步锁和一个 `next_allowed_at` 时间戳：

```python
class RateLimiter:
    def __init__(self, interval: float):
        self.interval = interval
        self._next = 0.0
        self._lock = asyncio.Lock()

    async def acquire(self):
        async with self._lock:
            now = time.monotonic()
            if now < self._next:
                wait = self._next - now
                await asyncio.sleep(wait)
            self._next = time.monotonic() + self.interval
```

发帖前调用 `await limiter.acquire()`，若执行过程中收到平台限流错误码（如 10024），则主动退避 5 分钟并记录到归档表中。针对内容去重，可在正文尾部添加不显示的零宽空格或随机注释（如 `<!-- rand:xxx -->`），避开完全匹配检测。

### 3. 状态归档

使用 SQLite 存储每次同步任务的状态，表结构精简：

```sql
CREATE TABLE sync_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL,
    content_hash TEXT,
    stage TEXT NOT NULL,      -- 'upload_image', 'post', 'done'
    status TEXT NOT NULL,     -- 'pending', 'success', 'failed'
    error_msg TEXT,
    created_at TEXT DEFAULT (datetime('now'))
);
```

流程中每一步（下载源图、上传微博图床、构造发帖、调用发帖接口）都向 `sync_log` 写入一条记录。通过 `task_id` 关联，可以追踪一条完整链路的每一步。失败任务支持按 `content_hash` 去重重试，避免重复上传图片。

## 踩坑记录

1. **上传接口的参数“复制粘贴”陷阱**  
   抓包获得的 `cb` 参数包含回调函数名，每次请求可能变化。早期写死一个有过期风险，后改为从微博首页 `tid` 拼接，提高了稳定性。

2. **多图上传的顺序问题**  
   超话发帖如需多张图，`pic_ids` 参数是逗号分隔的 pid 列表，顺序必须与上传顺序一致。并发上传时容易导致图片顺序错乱，改为顺序上传并收集 pid。

3. **Cookie 的生命周期**  
   扫码登录获取的 Cookie 有效期约 2-3 天，非活跃使用可能被提前踢出。工程上我用一个独立任务每天凌晨访问一次微博首页，探测状态，若失效则通过 Push 通知手动刷新。

4. **发帖接口的 content 自动转义**  
   文本中包含 `#超话名称#` 是必须的，但直接拼接后易出现 Unicode 转义问题。务必保证最终 Post body 为 `application/x-www-form-urlencoded`，并对内容进行 `quote` 编码。

## 可复用建议

- **封装为 OpenClaw 插件**：将上传、发帖、限流、归档封装为一个 `Tool` 或 `Action`，通过配置文件提供 Cookie、超话 ID、限流间隔。Agent 只需调用 `weibo_super_topic_post(text, image_urls)`。
- **使用 MCP 暴露状态接口**：可以起一个 MCP 服务器，对外暴露 `query_sync_status` 等资源，方便 Agent 查询任务结果。
- **错误码集中处理**：建立错误码到重试策略的映射（如 `10024` 等待 5 min，`10017` 内容重复直接丢弃），并在全局拦截器中统一处理。
- **与现有工作流集成**：可利用 OpenClaw 的调度器周期性检查 `sync_log` 中失败任务，进行重试。

## 总结

通过工程化手段逐一解构图片上传、限流保护和状态归档，我实现了一套可以在 OpenClaw 中稳定运行的微博超话同步插件。关键收益是：异常可追溯、速率可控、上传成功率 98% 以上。这一模式同样适用于小红书、B站等方式接口，当开放平台受限时，逆向移动端 API 配合合理的工程约束，不失为一种务实解法。
