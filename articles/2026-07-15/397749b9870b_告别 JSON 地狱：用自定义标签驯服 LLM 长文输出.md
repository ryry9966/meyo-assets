## 背景：OpenClaw 管道中的结构化输出困局

在 OpenClaw、Agent 工作流以及各类 MCP 插件实践中，我们经常需要让大模型输出便于下游程序解析的结构化内容。无论是生成长篇摘要、多步骤推理，还是用于后续工具调用的参数，解析的稳定性直接决定了整个自动化链条的可用率。

很长一段时间里，JSON 是唯一的选择。提示词里加上“请输出 JSON 格式”，代码里 `json.loads`，简单直接。然而当输出长度超过几十行，尤其包含嵌套对象、代码块、多段落文本时，JSON 就会露出糟糕的一面：花括号不配对、字符串内忘记转义引号、尾随逗号、莫名出现的注释……这些在常规 API 返回中还能靠重试弥补，但在批量处理或连续对话中，任何一次解析失败都会打断流程，修复成本很高。

我们在 OpenClaw 社区中维护了几个批处理插件，最早都强依赖 JSON 输出。经历过几十次“症状完全随机”的解析错误后，我们开始寻找更健壮的结构化方案，最终稳定在一种朴素但工程上非常可靠的策略——**自定义标签格式**。

## 问题解剖：JSON 在长文本输出中的硬伤

JSON 的设计初衷是数据交换，不是为自然语言生成准备的。三个最常见但难以根治的问题：

1. **转义灾难**：LLM 输出里只要出现双引号、反斜杠等字符，就必须正确转义。长文本里一旦漏掉一个，整个 JSON 就毁了。
2. **结构复杂度**：层级一多，大模型容易把括号、逗号搞错，而且错误往往是全局性的——一个字符的位置不对，整个文件无法解析。
3. **对空白和尾随字符敏感**：一些模型会在 JSON 后面追加一句“希望对你有帮助”，直接让解析器报错。这不是模型能力问题，而是生成过程缺乏严格的语法边界。

重发、加验证提示词、JSON 修复库都尝试过，有的能缓解，但没有一个能在**0.99 的可用率**上持续稳定。我们需要的是容错性高、局部失败不影响整体的方案。

## 方案：用自定义标签划分语义块

核心思路很简单：**把解析粒度从“整个 JSON 文档”拆分到“一个独立的语义块”，每个块用不会出现在正文中的标签包裹。** 例如，让 LLM 输出：

```
<summary>
这里是一段摘要文本，可以包含任意标点、"引号"和换行。
</summary>
<steps>
- 第一步
- 第二步
</steps>
<code type="python">
def hello():
    print("world")
</code>
```

后处理只需按标签名提取内容，而不是解析整个文档。由于标签只是一个普通字符串标记，解析几乎不受内容中的特殊字符影响。即便某个块的标签丢失，最多丢失这一个块，其他块依然可用。这对长时间运行的自动化流水线来说，是一个巨大的可靠性提升。

### 实际操作步骤（以 OpenClaw 自动化脚本为例）

**1. 设计标签体系，编码为系统提示词**

选择不易与生成内容冲突的标签名，比如 `<|summary|>` 和 `<|end|>`，或使用 XML 风格但采用全大写 `<OUTPUT_SECTION>`。避免使用 `code`、`step` 这类 LLM 本身就可能产生的词。在系统提示词里明确约束：

```
你必须严格按以下格式输出各个部分：
<|analysis|>
（你的分析内容）
<|end|>
<|final_answer|>
（最终答案）
<|end|>
```

关键是给每个块一个明确的结束标记，简化解析。

**2. 提取函数：用正则而非 XML 解析器**

不要引入 XML 解析库。LLM 输出的标签经常缺少闭合、嵌套混用，XML 解析器会直接抛异常。最简单的正则可以胜任：

```python
import re

def extract_tag(content, tag_name):
    pattern = rf"<\|{tag_name}\|>(.*?)<\|end\|>"
    matches = re.findall(pattern, content, re.DOTALL)
    return matches  # 返回列表，可能有多个同名块
```

这种方法天然允许标签缺失、顺序变化，甚至允许内容中包含 `<|end|>` 以外的类似标记。只有一点需要注意：如果文本里会出现 `<|end|>` 字面量，就需要更换结束标记为更独特的字符串（如 UUID）。

**3. 处理边缘情况**

- **未闭合标签**：正则的非贪婪匹配 `.*?` 会在遇到 `<\|end\|>` 或文末自动停止，不会导致程序崩溃。
- **内容中意外出现标签头**：如果非要保护，可以在提示词里要求把这类字符实体化，比如用 `&lt;`；但实践中很少发生，概率远低于 JSON 解析错误。
- **多块输出**：比如希望模型同时输出多个候选摘要，只需约定 `<|summary_1|>...<|end|>`、`<|summary_2|>...`，提取时用列表即可。

### 跨平台适配：MCP 工具与 Agent

如果你在开发 OpenClaw 的 MCP 工具插件，可以在工具的 description 中明确输出格式要求，并在调用方统一使用上述正则提取。Agent 循环中，可以将前一步的标签输出直接喂给下一步作为部分上下文，无需二次序列化。比起 JSON，它更贴合链式 Prompt 的阅读习惯。

## 踩坑与经验

1. **标签名选择要极端**  
   初始我们用了 `<summary>`，结果有模型在输出中写了 “The summary is: <summary> 内容” —— 这种意外定义被解析器当成新的块。后来改成 `<|syS_summary|>` 这类带前缀和怪异大小写的组合，彻底解决。

2. **不要指望模型一次学会**  
   用 `few-shot` 示例演示标签闭合很重要。一个巧妙的方法：在用户消息末尾附上 “你的输出必须从 `<|start|>` 开始，到 `<|end|>` 结束”，并给出完整示例。即便这样，仍有约 2% 的请求会忘记闭合，但此时正则不会报错，程序只需检查拿到的是否为空即可优雅降级。

3. **保留原始输出用于排障**  
   将所有原始输出以日志或数据库字段存下来。标签方案即使在早期也有助于观察模型“失准”的模式：比如某个特定场景下模型会在标签内插入另一组标签。这类问题很快能通过调整提示词修正。

## 可复用建议

- **从 JSON 迁移时，逐步替换**：不需要一次改造所有模块。先对最易断裂的长文本部分使用标签，其他短字段（如温度、分数）仍保留 JSON，两者可以共存。
- **Schema 验证简化为键值存在检查**：不必写复杂的 JSON Schema，只需确认必须出现的标签名都存在，以及内容非空。
- **保留可读性**：标签格式对人类阅读也友好，这在调试和人工复核时是额外优势。
- **嵌套需求用编号展开**：如果真的需要层级结构，用 `<|section_1_2|>` 这种编号约定比嵌套标签好解析得多。

## 总结

在 OpenClaw 的自动化实践中，放弃全局 JSON，转向基于自定义标签的块级解析，是我们做过回报率最高的架构调整之一。它不仅将长文输出的解析成功率提升到近乎 100%，还让下游处理面对模型的不稳定输出时拥有更高的韧性。这项技术没有复杂的依赖，纯粹依靠正则和严谨的提示词设计，很适合在 Agent、MCP 服务以及各类流水线插件中复用。

如果你正在被 JSON 解析错误折磨，尝试用标签来“去结构化”，也许会发现，给模型松绑的同时，你的系统反而更牢固了。
