## 背景

维护开源项目或技术产品时，一条更新往往需要同步到 GitHub Discussions、Discord、Twitter、Telegram、掘金、知乎等多个社区。初期手动复制粘贴还能应付，但随着版本迭代加快，很容易陷入“发布 5 分钟，同步 2 小时”的体力劳动。

于是自然想到用 OpenClaw + MCP 搭建一个自动化同步 Agent：从 Release Notes 或博客 RSS 中提取内容，按模板生成各平台消息，再通过 MCP 连接器分发出去。听起来很美，但第一次跑通后，团队同事立刻反馈：“你今天在几个群里刷屏了，而且 Twitter 上短文案像是机器人，Discord 格式还崩了。”

这就是多社区同步的真实边界：**自动化的收益会被“骚扰感”瞬间清空**。本文记录一个工程化可复用的同步方案，重点不在“怎么发”，而在“如何不发过头”。

## 问题拆解

直连全推的自动化至少会引入四类问题：

1. **频率拥塞**：多个平台的发布时间窗口重叠，短时间内信息轰炸同一个受众。
2. **内容错配**：GitHub 的 Markdown 长文直接推到微博会溢出，长文塞进 Discord 会被截断。
3. **规则隐形**：各平台对 API 频率、内容长度、外链、@用户的限制各不相同，一次 429 可能让后续全部失败。
4. **缺乏熔断**：没有人工兜底的自动发布一旦踩雷（敏感词、错误信息），撤回成本极高。

因此，不是要否定自动化，而是要在 Agent 里内置**边界控制**。

## 做法与步骤

我们用 OpenClaw 实现了一个带策略层的同步 Agent，整体架构：内容源 → 策略引擎 → 平台适配器 → 审核站 → 发布器。

### 1. 内容转换与裁剪

不再把同一个长文推送到所有平台。Agent 会先生成三个层级的有效载荷：

- `long_form`：完整 Markdown，用于 GitHub Discussions、博客评论。
- `social_card`：≤280 字符的摘要，用于 Twitter/微博。
- `chat_card`：带截断和跳转链接的简短消息，用于 Discord/Telegram。

借助 OpenClaw 的 `text_processor` 工具，配合简单的模板（Jinja2），可以在一次生成中产出三套文案，保证信息一致，形态适配。

### 2. 发布窗口与频率控制

定义全局与单平台两级频率限制：

- **全局冷却**：同一个内容源触发的发布事件，至少间隔 5 分钟再推下一个平台。
- **每平台每日上限**：Discord 不超过 3 条/天，Twitter 不超过 5 条/天，避免被平台降权或被用户静音。
- **时间窗口**：通过 Agent 读取配置文件，避开凌晨时段，只在 9:00-23:00 发布。

用 OpenClaw 的状态管理记录每个平台的最后一次发布时间和当日计数，调度器在 push 前先检查，条件不满足则进入等待队列，超时后降级为“次日发布”。

### 3. 人工确认环

全自动最大的风险是内容失当。我们引入了一个“审核站”机制：在正式发布前，Agent 将各平台最终渲染后的消息发送到内部 Discord 审核频道，并附上三个反应按钮：✅ 发布 / ❌ 丢弃 / ⏸️ 暂停一小时。

审核站本身是一个 MCP 工具，返回到 Agent 的控制流。只有当 `decision == "publish"` 时，才继续执行对应平台的 push。这个环节的成本很低，但能拦截 90% 的翻车场景。

### 4. 失败处理与重试策略

发布器执行时的异常分为两类：

- **临时性错误**（网络超时、平台限流 429）：指数退避重试 3 次。
- **内容性错误**（长度超限、含有被禁链接）：直接标记失败，写入日志，并通知审核频道人工处理后重试。

特别重要的一点：**禁止全局重试**。如果一条消息在 Twitter 发送失败，不能导致整个同步流程回滚重新推送 Discord，否则就是二次刷屏。各平台发布器状态完全隔离。

## 踩坑点

- **Markdown 到纯文本的转义**：Discord 对 Markdown 支持不完整，`#` 标题会被渲染成大号字体，不小心就变成了“大喊大叫”。需要在 `chat_card` 生成时明确去格式化。
- **同一内容跨平台时间重叠**：最初的调度逻辑是并发推送，结果用户同时在三个平台收到相同信息。改为顺序间隔 5 分钟后体感好很多。
- **审核疲劳**：如果每次发布都需人工确认，高频发布期会变成另一种负担。增加“信任模板”白名单：仅公告类、发布类消息触发审核，日常的文档更新链接同步自动放行。
- **社交平台外链降权**：部分平台对带有链接的消息降低曝光。Agent 可以选择在某些平台仅发文本，将链接放到第一条评论，这需要平台适配器单独处理。

## 可复用建议

如果要在自己的 OpenClaw 项目里落地这套方案，推荐抽象出三个可复用模块：

- **Policy Engine**：负责频率、窗口、内容长度等策略判断，暴露统一接口 `should_publish(platform, content) -> bool`，方便为不同社区更换规则。
- **Platform Driver**：每个平台封装为独立 driver，实现 `render()`、`publish()`、`validate()` 方法，新平台接入只需新增 driver，不影响调度逻辑。
- **Audit Tool**：一个标准的 MCP 审核工具，输入待发布内容和平台标识，返回人工决策。可以在本地 Discord/Slack 复用。

这些模块都可以用 OpenClaw 的 Tool/Agent 组合实现，与现有的 MCP 生态无缝衔接。

## 总结

自动化多社区同步的核心不是“全自动”，而是**给自动化设定边界**：什么时候发、发多少、谁来拍板、失败了怎么办。尊重每个社区的读者体验，比技术上的零延迟更有价值。Agent 的智能不体现在能发多少条消息，而体现在它知道什么时候该闭嘴。

如果你正在用 OpenClaw 写自己的同步工作流，希望这篇实践能帮你避开刷屏的坑，让自动化真正服务于社区，而不是消耗社区。
