## 背景

在内容自动化场景里，将 Markdown 长文或 Agent 生成的日报同步到微博超话，是一个典型的「多模态 + 限流对抗 + 长时任务」问题。OpenClaw 这类 Agent 框架虽然内置了任务编排能力，但面对微博非标准 API 的图片上传流程、客户端频繁的 403/429 拦截，以及长期运行中出现的状态丢失，仍需做大量工程化适配。

本文复盘一次基于 OpenClaw + 微博超话发布插件的同步实践，重点解决：图片格式兼容、Cookie 保活、调用频率控制、任务状态归档四个核心痛点，最终实现日均 30+ 帖子的无值守同步。

## 问题分析

### 1. 图片上传的隐性约束
微博图片接口对 `Content-Type` 与表单字段名极其敏感。直接使用 `multipart/form-data` 并填充 `pic` 字段并不总能成功，还需要携带 `mid` 与 `is_single` 等参数。同时，图片大小超过 5MB 或尺寸超过 4096px 会静默失败，服务端返回 200，但实际未生成 `pid`。这意味着上传成功后必须立即用 `pic_id` 做二次校验，否则后续发帖会因缺少图片而空转。

### 2. 限流矩阵
非白名单 IP 的图片上传接口存在双重限流：单次操作间隔不能小于 3 秒，同一 Cookie 每小时上限约 120 次。发帖接口更严格，短时间内连续发布超话帖会被视为营销行为，触发 403 并附带 `action="deny"` 的 JSON 体，有时会污染 Cookie 导致所有接口降级。

### 3. 任务状态漂移
长任务链中，任何一步失败（如图片上传后进程 OOM）都会产生孤儿图片，或已发布帖子在归档表中缺失。如果只记录最终结果，无法反查中间态，给调试与重试带来困扰。

## 方案设计

整体架构如下：
- **Agent 层**：OpenClaw 调度器，负责读取任务队列，按照 "预处理 → 图片上传 → 发帖 → 归档" 的流水线执行。
- **工具层**：通过 MCP（Model Context Protocol）封装微博 HTTP 工具，暴露 `upload_image`、`post_weibo`、`check_limit_remain` 等原子接口。
- **持久层**：SQLite 归档表 + Redis 限流计数器。

### 核心步骤

**图片上传：**  
Agent 在拿到图片路径后，先调用 `PIL` 进行预处理：缩略至 2048px 宽边、转为 RGB、压缩至 3.5MB 以内的 JPEG。随后调用 MCP 工具 `upload_image`，该工具自动注入从配置中心拉取的 Cookie，并以固定间隔（可动态调整）发送请求。如果连续 3 次未获得有效 `pid`，则进入异常归档并标记 `image_failed`。

**限流控制：**  
不使用简单的 `time.sleep`，而是采用令牌桶 + 响应码反馈。`upload_image` 与 `post_weibo` 各自维护一个令牌桶，桶容量等于对应接口的硬上限（图片 80 次/小时，发帖 20 次/小时）。每次调用前尝试获取令牌，若桶空则抛出 `RateLimitError`，由 Agent 调度器在未来重试。同时，当接口返回 429 或 `{"ok":0,"msg":"频率太快"}` 时，立即将桶清空并设置冷却时间 10 分钟，并向调度器报告冷却窗口。

**状态归档：**  
设计了一张 `task_journal` 表：
```
task_id | status | stage | image_pid | post_id | retries | created_at | updated_at
```
每个任务从 `pending` 开始，每进入一个阶段（image_upload/post/archived）即更新 `stage` 与 `status`。遇到异常时，记录具体错误码。Agent 在启动时还会扫描长时间处于中间态的任务（如超过 30 分钟仍为 `image_upload`），强制标记为 `zombie` 并人工修复。这种「最小状态机」避免了孤儿数据，且归档表可直接作为监控看板的数据源。

## 踩坑记录

1. **图片重名导致微博反垃圾：**  
曾经因为用固定文件名（如 `image.jpg`）连续上传，触发反垃圾逻辑，Cookie 被封 24 小时。修复方式是为每张图片生成 UUID 文件名，且每次上传间隔至少 5 秒。

2. **Cookie 解析丢失字段：**  
从环境变量取 Cookie 字符串时，容易被换行符截断，导致 `SUB` 或 `SUBP` 字段丢失。MCP 工具在初始化时会做完整性校验，若缺失关键字段直接拒绝启动，并输出缺失字段名。该机制至少挡掉了 3 次凌晨的无效运行。

3. **状态表写入失败被吞掉：**  
因为用 `try-except` 单独包裹了数据库写入，出现主键冲突时异常被吞，导致归档字段为空。最终改为“写入失败则任务直接标记为失败并重试”，利用 task_id 的唯一性保证幂等。

4. **限流桶与多实例竞态：**  
当用多个 OpenClaw 实例消费同一任务队列时，基于内存的令牌桶失效。解决办法是改用 Redis `SETEX` 做计数，每个 Consumer 对同一接口递增计数，超限后返回 `RateLimitError`，由全局调度器统一等待。

## 可复用建议

- **接口都要做回验：** 上传图片后，用返回的 `pid` 调用一个图片信息查询接口，确认图片可访问且尺寸正常。不信任 200 状态码。
- **状态机是最低成本的可观测性：** 不必引入复杂工作流引擎，一张 journal 表就能让排障时间从 2 小时降到 5 分钟。
- **限流用显式 Token 模式：** 不要依赖 `sleep`，要让 Agent 知晓限流状态，以便它在全局层面规划任务顺序，而不是本地死等。
- **Cookie 要用探活机制：** 每小时用一次无需敏感操作的接口（例如获取用户信息）验证 Cookie 可用性，失败立即暂停调度并告警。
- **把“异常归档”作为一等公民：** 所有不成功的调用都写入专门的错误归档，保存请求参数与响应体，便于后期分析反垃圾策略的变化。

## 总结

微博超话同步看似只是调几个 API，但把它做成可靠的无值守服务，至少要在图片处理、限流对抗、状态追溯三个维度下足功夫。OpenClaw 的编排能力让这种工程化变得更容易，但真正的稳定性来自于对每个原子工具的精雕细刻，以及对异常路径的完整覆盖。这套实践同样适用于小红书、头条等其他内容平台的自动化同步，只需替换 MCP 工具集，顶层调度逻辑完全可以复用。
