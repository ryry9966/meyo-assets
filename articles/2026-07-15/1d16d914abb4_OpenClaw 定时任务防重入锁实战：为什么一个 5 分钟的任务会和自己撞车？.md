# OpenClaw 定时任务防重入锁实战：为什么一个 5 分钟的任务会和自己撞车？

## 背景：一个“刚刚好”的定时任务

在 OpenClaw 里搭了一条数据同步流水线：通过 Agent 调用外部 API 拉取订单，清洗后写入内部库，再触发下游通知。平均跑一轮大概 4 分 30 秒，于是顺手配了个每 5 分钟执行一次的定时触发器。逻辑上看着天衣无缝——前一次刚结束，下一次刚好启动。上线头两天一切平静，第三天却收到了重复通知投诉。查日志发现两条流水线在时间上重叠了整整一分钟：一条还在写库，另一条已经开始拉单，导致同一条订单被处理了两次。这就是典型的“定时任务撞车”。

## 问题：为什么 5 分钟任务会撞车？

定时触发器（无论是 cron 还是 OpenClaw 内置调度）只关心时间点，不关心上一次是否跑完。当任务执行时间偶尔超过间隔（网络抖动、数据量突增、下游慢响应），新旧实例就会并发。更隐蔽的是，即便平均耗时低于间隔，长尾分布下仍然会撞。没有防护机制，你的 Agent 就会像没有信号灯的十字路口，早晚会出事。

在单次执行中，OpenClaw 的任务实例彼此独立，没有内置的互斥语义。所以我们需要自己加一把防重入锁。

## 做法：给任务加上互斥锁

实现原理很简单：任务启动时尝试获取一把命名锁，拿到了才执行业务逻辑；拿不到就说明已有实例在跑，直接退出或延迟重试。任务结束（无论成功或异常）必须释放锁，否则会造成死锁。

针对 OpenClaw 的实践，推荐以下步骤：

### 1. 选择锁的存储与工具

- **单实例部署**：内存锁（如 Python 的 `threading.Lock` 或 `asyncio.Lock`）最快，但仅限同一进程。
- **多实例或分布式执行器**：必须使用外部存储，比如 Redis（`SETNX` + TTL）、数据库唯一索引或 OpenClaw 自带的全局资源锁（如果版本支持）。我习惯用 Redis，因为 OpenClaw 环境通常已经连着一个 Redis 做缓存或状态存储。

### 2. 设计锁的 key 和超时

锁名必须全局唯一，建议带上任务名称：`lock:sync_orders_task`。**超时时间一定要大于任务的最大可能执行时间**。实测那个数据同步任务，我给锁设置了 10 分钟的过期时间（正常 5 分钟 + 充裕 buffer）。如果设置太短，任务还没跑完锁自动释放，新实例依然会闯进来。

### 3. 编写任务装饰器或上下文管理器

在 OpenClaw 的 Agent 脚本里，我封装了一个 `@prevent_reentry` 装饰器（代码见下），它内部通过 Redis 实现加锁与释放。核心逻辑：

```python
import redis
import os
from functools import wraps

def prevent_reentry(lock_key, expire_seconds=600):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            r = redis.Redis.from_url(os.getenv("REDIS_URL"))
            # 尝试获取锁：仅在 key 不存在时设置，并带过期时间
            acquired = r.set(lock_key, "1", nx=True, ex=expire_seconds)
            if not acquired:
                print(f"任务 {lock_key} 已有实例在运行，跳过本次执行")
                return
            try:
                return func(*args, **kwargs)
            finally:
                # 正常或异常退出都释放锁
                r.delete(lock_key)
        return wrapper
    return decorator

@prevent_reentry("lock:sync_orders_task", expire_seconds=600)
def run_sync_orders_agent():
    # OpenClaw agent 逻辑...
```

如果你的 OpenClaw 流程是图形化编排，没有写代码的入口，可以尝试用内置的“互斥锁”或“资源锁”插件（命名可能不同，本质是同一个概念）。在触发节点后、业务节点前插入一个“获取锁”的动作，配置锁名称和超时，再在流程末尾（包括错误处理分支）加上“释放锁”的节点。

### 4. 监控锁跳过事件

当发现锁已被占用而跳过一次执行时，绝不能静默。务必在日志里记录，最好接入告警通道（如钉钉、飞书机器人）。这样你可以及时知道：**任务开始变慢，定时间隔已不够用，需要扩充资源或调整频率**。

## 踩坑点：那些让你抓狂的细节

- **锁超时 < 最大执行时间**：如上文所说，会造成“锁提前释放”，等于没有防重入。一定要取 P99 执行时间 + 安全 margin。
- **异常未释放锁**：如果业务代码抛异常，且释放锁在 `finally` 之外，就死锁了。用 `try...finally` 或 OpenClaw 的错误分支确保释放。
- **多实例用了内存锁**：表面上加了锁，实则每个实例各锁各的，防不住多实例并发。只要不是单进程单线程执行，就上分布式锁。
- **锁被误删**：别用 `KEYS` + `DEL` 模式去清理锁。确保同一把锁只有持有者能释放。可以用 Lua 脚本原子比较 value 再删除（value 为唯一实例 ID）。简单场景下，超时自动过期也能容忍低概率误伤。
- **重试风暴**：不建议在加锁失败时 sleep 后重试，如果上游触发频率高，会堆积大量等待任务，最终拖垮资源。更稳妥的策略是“跳过并在日志告警”。

## 可复用建议

把防重入锁做成团队内部标准组件，无论是写 Agent 还是用插件，都用同一套命名规范和超时策略。对于 OpenClaw 任务，可以形成如下 checklist：

- 锁名：`lock:project:task_name` 前缀，一目了然。
- 超时：不拍脑袋，取历史执行时间的 2~3 倍（至少 10 分钟）。
- 释放：永远在最终块里释放，并处理释放失败时的日志。
- 环境：区分本地测试（内存锁）和生产（Redis/DB 锁），避免互相影响。
- 监控：为“锁跳过”配置告警，便于发现性能退化。

## 总结

5 分钟定时任务和自己撞车，本质是异步调度中执行时长超过调度间隔的经典并发问题。在 OpenClaw 体系中，只要有一把可靠的分布式锁，配合合理的超时和释放机制，就能从根上消除重入。实现成本很低，但能避免数据重复、资源冲突等一连串生产事故。与其等撞车发生后再排查，不如一开始就把“防重入”作为定时任务的默认配置。
