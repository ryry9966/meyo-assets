## 背景：为什么我们要做多社区同步

如果你同时在维护 GitHub Discussions、Discord 频道、Twitter、Telegram 公告板，或是通过 Agent 把内容推送到微信、飞书等内部群，你就会明白一件事：手动复制粘贴会消耗大量注意力，也会带来版本不一致的问题。

OpenClaw/MCP 生态里的很多插件项目，天然适合用自动化 pipeline 处理发布。比如你写了一个 MCP Server 的更新日志，希望自动同步到 Twitter 宣布、Discord 发公告、GitHub Discussions 归档，同时不被用户当成 spam。这时你需要面对的就不再是“能不能发”，而是“发多少算打扰”。

这里讨论的“自动化发布”，不是营销号那种短时间铺量的逻辑，而是工程团队在做产品通知时的一种可控分发：你仍然要给每条内容保留上下文，只是让机器替你完成格式适配和投递。

## 问题：刷屏感从哪来

多数人一开始会以为“刷屏”是指消息条数多。但实际观察下来，真正让人退群、取关、静音的不是频率，而是三个更细的因素：

1. **信息密度过低**  
   多条消息本质上说的是同一件事，却没有增量信息。比如一个 release，先发一条“马上发版”，再发一条“发了”，再跟一条“修正一个错别字重新发”，这就是典型的低密度通知。

2. **格式割裂**  
   同步到不同平台时，直接把 Markdown 贴进 Discord，代码块没换行、链接展开成裸 URL，用户需要“解码”才能读懂。这种体验会让自动化看起来粗糙且不在意读者。

3. **缺乏退路机制**  
   全自动发布一旦出错，没有停止按钮，用户只能被动接受。比如 Webhook 重试导致重复推送，或者测试消息意外发到了正式群。

这些问题的根源不是自动化本身，而是缺乏边界设计。接下来讨论一套我们实际在 OpenClaw 插件同步中用到的做法。

## 做法：一个可控的同步 pipeline

目标：同一份发布说明，通过 MCP + 简单脚本，适配多个社区格式，且每条消息有明确的“是否发布”的判断点。

### 1. 内容源单一定义

所有发布内容从 CHANGELOG.md 或一个 JSON 公告文件读取。样例如下：

```json
{
  "version": "0.4.2",
  "title": "MCP Server 0.4.2: 新增资源限流",
  "summary": "增加了 per-session 的资源限流，避免单个客户端占用过多内存。",
  "detail_url": "https://github.com/xxx/releases/tag/v0.4.2",
  "type": "release",
  "audience": ["discord-announce", "twitter", "github-discussions"]
}
```

在入口处做一次内容校验：如果没有 summary 字段，直接中断，避免空消息流出。这个校验用简单的脚本就能完成，不需要大模型参与。

### 2. 按渠道做格式适配，而非改写

通过 MCP tool 对不同渠道渲染格式。以 Discord 为例：

- Discord 公告：支持 embed，优先使用 embed 规范渲染，不会裸发 Markdown。
- Twitter：生成 1-2 条 thread，第一条是主要信息，第二条补充链接和图片。
- GitHub Discussions：直接使用 Markdown 原文，增加 frontmatter 便于搜索。

关键点：不做“用 GPT 润色成小红书风格”这种不可控操作。每一条输出都可以通过模板对照回原文，减少幻觉和不一致。

### 3. 增加“预发布视图”和人工卡点

所有消息在真正发送前，先渲染到一个本地 HTML 或 Markdown 预览文件里。我们习惯的做法是：

```
make preview-release
```

这步会拉取内容源，渲染各渠道格式，生成一个 `preview/` 目录，你可以在浏览器里直接看每条消息最终长什么样。没有确认之前，不进入真实发送。

真实发送时，通过环境变量 `LIVE=true` 控制，测试阶段不加该变量，所有操作都是 dry-run。这个习惯可以在个人项目里显著降低事故率。

### 4. 幂等与去重

每次发布前，记录一个 `sent_v0.4.2_discord` 这样的标记文件，避免重复发送。MCP 工具在执行发送时检查标记，如果已存在就直接退出。

此外，对 Webhook 返回的 HTTP 状态码做判断。若对方返回 429，退避重试最多两次，且每次间隔不低于 30 秒，避免瞬间重试导致重复消息。

## 踩坑点：三个真实教训

### 坑 1：时间窗口内的多次触发

问题出现在 GitHub Actions 被 push 和 tag 事件同时触发，导致同一版本发布了两次。  
解决：在 workflow 里通过 `if: github.event_name == 'release'` 限制触发条件，并增加一个 `concurrency` 组，防止同一 workflow 并行执行。

### 坑 2：长文本被平台截断后丢失链接

Discord embed 的 description 有字符限制，某次更新日志较长，直接截断了末尾的 GitHub URL。  
解决：适配时优先保证链接完整，description 超出长度时用 `fields` 拆分，或者把链接放在 `url` 字段（embed 可点击标题）。

### 坑 3：测试消息发到正式群

本地测试时，Discord webhook URL 写死在代码里，忘记改成测试频道的 hook。  
解决：永远用环境变量注入 webhook，测试环境和正式环境用不同的 `.env` 文件，CI 中不提交真实 hook。

## 可复用建议

- **把发布看作一次“事件”，而不是一个“动作”**。每次发布都有唯一 id（版本号），方便去重、回查和撤回。
- **渠道适配只做格式映射，不做内容再创作**。保持信息一致，减少用户混淆。
- **永远保留一条纯文本 fallback**。如果 embed 或富文本渲染失败，至少有一条可读的 plain text 到达用户。
- **给社区留一个“静音版本”选择**。例如 Discord 里除了 announcement 频道，建立一个只有文字摘要的 `#releases-minimal`，供不想看到 embed 的用户订阅。
- **在自动化前言里写下 opt-out 路径**。如果用户觉得被打扰，知道如何关掉通知，反而会提高容忍度。

## 总结

自动化发布不会天然导致刷屏，不加以边界控制的自动化才会。通过内容源单一定义、渠道格式适配、预发布视图和幂等去重，工程师完全可以在不牺牲触达效率的前提下，让社区消息保持清晰、一致、可预期。

对于 OpenClaw 社区来说，这种实践还有一个额外价值：当你把发布流程做成 MCP tool 后，可以继续抽象成一个“社区通知 Agent”，把同步逻辑和发布决策解耦。到那时，你就可以放心地让 Agent 负责“怎么发”，而把“发什么”牢牢握在人的手里。
