## 背景

跨平台内容分发是很多个人博主或自动化工具的常见需求。过去半年，我在 OpenClaw 体系内维护了一个用于将每日生成的内容同步到微博超话的 Agent。目标很简单：给定文本与图片，安全、稳定地发布到指定超话，并在本地归档每次同步状态，方便失败重试与审计。

这不是一个花哨的功能，但它暴露了微博开放体系在自动化接入时的各种非标行为：图片上传接口独立、登录态脆弱、对非移动端 UA 的限流近乎严苛。这里记录的就是在长期运行中沉淀下来的工程化做法与踩过的坑。

## 问题拆解

一次完整的超话同步涉及三个核心链路：

1. **图片上传**：图片必须先通过 `picupload` 类接口转换为微博内部 `pid`，不能用外链。
2. **超话发帖**：将文本与 `pid` 组装后，调用超话专属的发帖接口。
3. **状态归档**：记录每条任务的最终状态（成功/限流/失败），支撑后续补发与监控。

看上去清晰，但实际执行中会被三个因素打乱：**认证与 UA 校验**、**频率控制**、**图片格式限制**。下面按照工程实现的顺序来拆解。

## 实现步骤

### 1. 凭证与 UA 管理

微博 web 端和移动端接口对 `User-Agent` 和 `Cookie` 的校验规则差异很大。多次测试后我选择模拟移动端 Weibo 官方客户端的 UA，并用真实的登录 Cookie（包含 `SUB`、`SUBP` 等关键字段）。

登录态维护是个独立话题。这里我采用了一个独立的心跳脚本，每 6 小时检测一次 Cookie 有效性，失效时通过二维码扫描自动续期。OpenClaw 内可以将这个检测逻辑封装成一个 `HealthCheck` 工具，让 Agent 在每次任务前调用。

### 2. 图片预处理与上传

微博的图片上传接口对尺寸、体积和格式有隐含限制。经验总结：

- **格式**：优先使用 JPEG，PNG 在某些场景下会被拒绝或转换后丢失透明通道。
- **尺寸**：长宽均不超过 4096px，但建议提前缩放至 1920px 宽以内，否则上传后会被强制压缩，发出来模糊。
- **体积**：控制在 5MB 以内。

我使用 Pillow 做预处理，将图片转为 RGB 模式的 JPEG，品质设为 85。处理完再调用上传接口。

上传接口形如：

```
POST https://picupload.weibo.com/interface/pic_upload.php
```

这里关键参数包括 `cb`（JSONP 回调）、`mime` 必须为 `image/jpeg`，图片数据以 `pic1` 字段上传。返回体中可提取 `data.pics.pic_1.pid`，这就是发帖时引用的图片 ID。

一个容易忽略的细节：上传接口对 `Referer` 也做了校验，缺失时会直接返回错误或降速。需要至少带上 `https://weibo.com/` 的 Referer。

### 3. 发帖接口与超话绑定

有了 `pid` 后，发帖时还需指定超话 ID。超话帖子实际是通过普通发微博接口，在文本中追加 `#超话名称#` 并传入 `topic_id` 参数实现。

实际测试下来，带图超话帖更稳妥的做法是使用：

```
POST https://m.weibo.cn/api/statuses/update
```

参数中 `content` 包含话题词，`pic_id` 传入图片 PID（支持多个，逗号分隔），同时带上 `topic_id` 字段（从超话页面抓取）。这种方式比在 Web 端拼凑老接口稳定得多。

### 4. 限流感知与自适应退避

限流是贯穿全流程的核心痛点。微博对同一 IP 或同一账号在单位时间内发帖、上传图片均有严格频控。

我观察到的典型限流信号：

- 发帖接口返回 200，但 body 中 `ok` 为 0，`msg` 包含“发布频率过高”或“操作太频繁”。
- 图片上传返回空响应或超时，但没有显式错误码。

单纯的固定间隔 `sleep` 不够可靠。我在 Agent 中引入了一个简单的令牌桶+指数退避策略：

- 发帖请求用令牌桶控制，默认 1 令牌/分钟，最多积攒 3 个。
- 图片上传独立限频，每分钟不超过 5 张。
- 一旦命中限流响应，立即将令牌重置为 0，并启动 2x 指数退避（初始 120 秒），最大重试 3 次。

为了不让限流阻塞整个队列，所有发帖任务被放入一个优先级队列，由独立的 Worker 消费。这样即便某个帖子被暂缓，也不会影响后续需要更低频操作的任务。

### 5. 状态归档与可观测性

每次同步无论成功与否，都会写一条记录到本地 SQLite：

```
task_id | status | retries | last_error | created_at | updated_at
```

失败任务会标记为 `rate_limited` 或 `failed`，并由一个定时任务每天凌晨拉取 `rate_limited` 条目进行低峰期补发。这个表同时对接了一个简单的 Grafana 面板，方便观察成功率趋势和限流频率变化。

## 踩坑总结

- **图片上传对 Cookie 域敏感**：不要混用 `.weibo.com` 和 `.weibo.cn` 的 Cookie，否则上传接口可能返回 302 登录页。
- **`content` 字段需要 URL encode**：许多 SDK 会默认编码，但手动请求时容易遗漏，导致部分符号丢失或接口 400。
- **超话 ID 非固定**：一些超话会因运营原因更换 ID，需要定期校验，否则发帖会变成普通微博。
- **移动端接口返回格式不一致**：成功和失败有时都用 `ok: 1`，实际需要通过 `data` 中是否有 `id` 来判断。

## 可复用建议

如果你在 OpenClaw 体系内复刻类似能力，建议：

1. **将上传、发帖、归档拆成三个独立 Skill**，通过状态机串联，便于单独调试和替换。
2. **把限流参数做成可配置**，不同账号或代理出口需要的节奏差异很大。
3. **保留最近 7 天的请求日志**，至少记录状态码和耗时，方便事后回溯非显式错误。
4. **为图片上传增加校验环节**：上传后拉取一次图片信息比对 MD5，避免微博侧压缩导致图片无法使用。

## 总结

微博超话同步的自动化远谈不上“一键发布”。它的难点不在于接口本身的复杂度，而在于如何在非标鉴权、模糊限流与格式要求之间找到一套可以稳定运行数周的工程方案。上面的做法经过近三个月的实际流量验证，日同步成功率稳定在 97% 以上，限流导致的延迟基本在重试窗口内消化。

如果你也在维护类似的自动化发布链路，希望这些笔录能帮你少踩几个坑。
