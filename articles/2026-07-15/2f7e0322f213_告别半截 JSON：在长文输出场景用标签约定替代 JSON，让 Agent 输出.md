## 背景

在 OpenClaw 这类工具链里，让大语言模型（LLM）输出结构化内容是日常操作。无论是生成最终报告、任务拆解清单，还是多轮对话的中间状态，我们通常都希望拿到一份机器可解析的结果。最常见的做法是让模型输出 JSON。模型也确实很擅长“写 JSON”——前提是输出短，且结构不复杂。

但一旦需要生成 **长文输出**（几百到几千 token，包含多段落、多节点、嵌套信息），JSON 就开始出问题：缺闭合括号、字段值里出现未转义的双引号、数组元素多了少了逗号，甚至模型在长生成中途“忘记”自己正在输出一个 JSON 对象，转而去自由发挥。

在 Agent 自动化流程里，这意味着解析失败、触发重试、浪费 token 和时间，严重时直接导致整个 Pipeline 中断。有没有更稳定的结构化约定方式？实测下来，**自定义标签格式（类似 XML 但更宽松）** 是一个高性价比的替代方案。

## 问题：为什么长 JSON 容易崩？

JSON 的严格语法对模型的长序列生成很不友好：

- **括号配对压力**：一个长 JSON 对象需要在生成结束时才知道最后该有几个 `}` 或 `]`。在中途如果某个嵌套层级没处理好，输出就直接报废。
- **字符串转义地狱**：长文本中难免有双引号、换行符，模型很容易在中间的字符串值里写出未转义的双引号，导致解析器提前截断。
- **无法逐步校验**：在没有完整拿到整个 JSON 前，几乎无法校验结构是否正确，也不适合流式处理。

这些特性让 JSON 在“生成大量自然语言文本又需要结构标记”的场景里很脆弱。我们需要的是一种对模型更友好、边界清晰、对不完整输出也有一定容错能力的格式。

## 做法：用自定义标签约定代替 JSON

核心思路是：**用明确的开始/结束标签包裹各个区块，解析时按标签切割，不强求全局括号配对，部分缺失仍可抢救。**

### 1. 定义标签语法

可以采用类似 XML 的标签结构，但不需要声明命名空间、属性可以简单用 `key="value"`。例如，我们要让模型输出一份包含摘要、详细分析、行动建议的报告，可以约定如下：

```
<OUTPUT>
<SUMMARY>
这里是摘要内容...
</SUMMARY>
<ANALYSIS topic="问题一">
这里是针对问题一的详细分析...
</ANALYSIS>
<ANALYSIS topic="问题二">
这里是针对问题二的详细分析...
</ANALYSIS>
<RECOMMENDATIONS>
- 建议1
- 建议2
</RECOMMENDATIONS>
</OUTPUT>
```

标签名称自定义，只要在 prompt 里和模型约定好即可。

### 2. 提示词设计要点

在系统消息或用户消息中，需要明确告诉模型：

- 使用指定标签包裹整个输出（如 `OUTPUT`）。
- 各个子块使用特定标签，可给出示例。
- 标签内部的自然语言内容保持原样，不要额外转义（这消除了 JSON 字符串转义问题）。
- 强调“务必闭合所有标签，但如果在极端情况下输出被截断，解析器会尽量提取已闭合的部分”。

一个简化的指令示例（用于系统 prompt）：

```
请用以下标签格式输出：
<OUTPUT>
<SUMMARY>摘要内容</SUMMARY>
<DETAILS>详细分析内容</DETAILS>
</OUTPUT>
必须完整闭合所有标签。如果内容包含特殊字符，请保留原样，不要使用任何转义。
```

### 3. 解析实现（Python 示例）

解析器不必强依赖 XML 库（因为模型输出的标签可能不规范，比如属性值没加引号），可以用正则 + 栈。

一个简单的提取函数：

```python
import re

def parse_tagged_output(text: str) -> dict:
    result = {}
    # 提取整体输出块
    output_match = re.search(r'<OUTPUT>(.*?)</OUTPUT>', text, re.DOTALL)
    if not output_match:
        return result
    inner = output_match.group(1)

    # 提取各个子块
    for tag in ['SUMMARY', 'DETAILS', 'RECOMMENDATIONS']:
        pattern = rf'<{tag}>(.*?)</{tag}>'
        match = re.search(pattern, inner, re.DOTALL)
        if match:
            result[tag.lower()] = match.group(1).strip()
    return result
```

对于可能有多个同名字段的情况，用 `re.finditer` 遍历并把属性当作键。这样，即使模型只输出到一半（比如 `</OUTPUT>` 缺失），也能拿到已经闭合的那些区块。

### 4. 流式场景的适应性

流式接收 token 时，可以仿照 SAX 解析器的思路：维护一个当前标签栈，每收到完整标签就触发事件。比如用生成器实现：

```python
def tag_stream_parser():
    # 状态机实现，最简可用正则逐块匹配
    # 当检测到开始标签 <TAG> 时，push；遇到结束标签 </TAG> 时，yield 一个完整块
    pass
```

相比流式 JSON 解析（如 ijson），标签格式解析更宽容，也更适合“边生成边消费”的 Agent 场景。

## 踩坑点

1. **标签名称冲突**：如果输出内容里恰好包含类似 `<SUMMARY>` 的文字，会被误解析。解决办法：使用足够独特的标签名，如 `<OC_OUTPUT>`，并在指令里明确“在输出中如果你要讨论标签本身，请用反引号包裹，而不是直接写尖括号”。

2. **模型有时会漏写闭合标签**：虽然比 JSON 好一些，但仍偶有漏闭合。可以在解析后检查期望的标签数量，对缺失的标签记录 warning，不影响其他区块的使用。重试策略可以设为“仅当核心区块缺失时才重试”。

3. **嵌套处理**：如果确实需要多层嵌套，标签格式也可以做到，但需要更严谨的栈解析。此时可以考虑用支持容错的 HTML 解析器（如 BeautifulSoup 的 lxml 模式），并做好实体转义设定。

4. **与 Markdown 混用**：如果输出同时还希望保留 Markdown 格式，让模型把 Markdown 内容放在标签内部即可，无冲突。因为标签是外层容器。

## 可复用建议

- **先设计 Schema，再写 Prompt**：梳理清楚需要哪些字段，每个字段的标签名、是否可重复、是否必选。然后才编写指令。
- **少量示例（Few-shot）**：在系统 prompt 中给出 1-2 个完整示例，能大幅提高格式遵从度。
- **构建通用解析工具**：在项目里抽象一个 `TagParser` 类，通过配置字段定义（标签名、必选、多值等）来解析，方便在不同任务中复用。
- **结合重试逻辑**：如果核心标签缺失，则重试并附带错误信息（如“请确保在输出中包含完整的 <OUTPUT> 和 </OUTPUT>”）。
- **日志记录部分解析**：记录每次解析成功与失败的标签数，便于长期观察模型行为变化。

## 总结

在长文输出场景里，JSON 的严格语法反而成为模型生成的枷锁。自定义标签格式通过“明确的开始结束标记”大幅降低了 LLM 维持结构完整的难度，同时让解析器对不完整输出有一定容忍能力。这在需要 Agent 自动编排多步骤报告、长文档生成、流式处理等场景下，是一个非常务实的工程选择。它不够“标准”，但够“稳定”，且实现成本极低。
