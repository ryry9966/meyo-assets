## 背景

在信息监控与多平台分发的自动化场景中，将内容定时同步到微博超话是一个常见需求。例如，跟踪某个开源项目动态、行业资讯聚合、或者多账号品牌内容分发，都会涉及向指定超话发布带图微博。如果只靠人工维护，不仅效率低，还容易出错。而一旦交给自动化脚本，又会立刻撞上图片上传鉴权、超话发帖频率控制、任务状态追踪等一系列工程问题。

本次实践围绕一个典型的 Agent 工作流展开：通过 MCP（Model Context Protocol）工具封装微博操作，由 OpenClaw 调度执行，实现带图微博的自动发布、异常重试和任务归档。整个过程不依赖第三方商业平台，完全基于本地可复现的工程组件。

## 问题拆解

核心难点可以归纳为三点：

1. **图片上传链路不透明**  
   微博开放平台虽然提供上传接口，但实际使用时，必须区分“开放平台应用”和“网页端登录态”。超话发帖行为更接近普通用户行为，因此必须使用 `weibo.com` 的登录 Cookie，并调用网页端的上传 API。图片需要先上传获得 `pid`，再通过发帖接口携带 `pid`。直接使用 `requests` 模拟会遇到 `st` 参数加密、`crossdomain` 等反爬机制。

2. **超话发帖限流复杂**  
   超话有独立的频率限制，且规则并不完全公开。实践中观察到，同一超话连续发帖间隔小于 3 分钟可能触发“发帖太快”警告，单日总量也有软性上限。账号本身还受登录 IP、设备指纹等因素影响。粗暴重试会直接导致账号被临时限制发帖。

3. **状态归档缺失**  
   一批待发布内容中，可能部分图片上传成功但发帖失败，部分因为网络抖动被跳过。如果没有状态记录，根本不知道哪些已经处理、哪些需要补发，会变成“薛定谔的同步”。

## 实现方案

### 1. 图片上传：通过 MCP 工具封装网页端接口

使用 MCP 的 `@modelcontextprotocol/server-fetch` 模拟浏览器请求，封装一个 `upload_weibo_image` 工具。步骤如下：

- 预先通过抓包获取微博 `login` 流程，保留有效的 `SUB` Cookie 和 `_s_tentry`、`crossidcc` 等字段，存入本地 `.env`。
- 工具接收本地图片路径，自动处理图片：压缩至宽高不超过 1280px、质量 85%，转换为 JPEG，单张大小控制在 3MB 以内，避免触发审核延时。
- 调用 `https://picupload.weibo.com/interface/pic_upload.php` 进行上传，`multipart/form-data` 包含 `pic1` 文件流，带上从网页端获取的 `st` 参数（可从首页预取）。
- 返回解析出的 `pid`，供后续发帖使用。

在实际 Agent 流程中，OpenClaw 先读取本地待发内容队列，对每条内容的图片逐一调用该工具，将获得的 `pid` 列表缓存入内存或临时文件。

### 2. 发帖与限流控制

发帖工具 `post_to_topic` 包装了超话的 `aj/weibo/add` 接口，需要提供：
- 超话名（对应的 `page_id` 抓取获得）
- 文本内容（注意超话会自动添加超话后缀，所以内容中不要再手动加 `#` 标签）
- `pic_id` 字符串（多个用逗号分隔）

限流控制采用本地令牌桶 + 指数退避：
- 配置每个超话的最小发帖间隔（如 `min_interval: 180s`）和最大重试次数（`max_retries: 3`）。
- 发帖前检查上次该超话发帖时间，不足间隔则 `sleep` 到满足条件。
- 若收到“发帖太快”错误（code 100005 或 msg 包含频率限制），将当前任务放回队列尾部，等待时间翻倍（最大不超过 15 分钟）。
- 若遇到登录失效错误，触发告警并暂停整个任务流，等待人工介入。

### 3. 状态归档

使用本地 SQLite 数据库维护一张 `sync_tasks` 表，字段如下：
- `task_id` (UUID)
- `content_hash`（内容摘要，用于去重）
- `image_path`（原始图片路径）
- `uploaded_pid`
- `post_status`（`PENDING / UPLOADED / POSTED / FAILED`）
- `retry_count`
- `error_message`
- `created_at` / `updated_at`

每完成一步（图片上传完成、发帖完成），都会更新对应状态。Agent 在每次启动时，会先查询 `post_status != 'POSTED'` 且 `retry_count < max_retries` 的任务，恢复执行。这相当于一个简单的持久化工作队列，避免了内存流失导致的状态丢失。

## 踩坑记录

- **Cookie 时效与异地登录**：微博网页 Cookie 如果更换 IP 或 UA，很容易触发二次验证。我的做法是固定部署机器的出口 IP 和 User‑Agent，并定期（每 12 小时）通过一个静默访问首页的请求刷新 `st` 参数，保持会话活跃。
- **图片审核延迟**：有时图片上传返回成功，但发帖时提示“图片未审核通过”。这是因为图片触发了内容审核，而且审核是异步的。解决方案是对上传后的 `pid` 先执行一次轮询检查（通过评论接口间接判断），超时未通过则丢弃该图片，仅发布文字。
- **超话 page_id 不稳定**：直接写死 `page_id` 可能因为超话改名或合并而失效。需要在 Agent 中增加一个 `resolve_topic_id` 工具，通过搜索接口动态获取当前 page_id，每次发帖前刷新。
- **文本长度计算**：微博 140 字限制计算的是“显示长度”，表情、URL 等占据不同字符位。实践中直接使用 `len(text.encode('utf-16-le')) // 2` 估算更准确，确保截断后再添加超话后缀。

## 可复用建议

整个发布流程可以抽象为三个独立的 MCP 工具：
- `upload_weibo_image`
- `post_to_topic`
- `query_topic_info`

然后将上述限流和归档逻辑写成 OpenClaw 的 Skill 或 Workflow 定义文件，例如 `weibo_sync.agent.yaml`。这样其他人只需要配置自己的 Cookie、超话列表和待发布内容目录，即可复用整套流程。

状态归档不要省略。哪怕只是最简单的 JSON 文件记录，也能让你在出问题时快速定位“到底发了没有”，而不是盲目重发导致限流更严重。

同时强烈建议加入监控通知（比如通过 Webhook 发到钉钉/飞书），当重试次数用尽或 Cookie 失效时，第一时间人工介入，避免静默失效。

## 总结

微博超话同步看似简单，背后却是典型的“对抗性自动化”：鉴权、限流、异步审核、状态恢复，每一环都可能让一个脆弱的脚本彻底卡死。通过 MCP 工具化、令牌桶限流、本地状态持久化，可以把这套流程变成稳定可维护的 Agent 能力。更重要的是，这种“上传→发布→归档→异常恢复”的模式，同样适用于其他 UGC 平台（知乎、贴吧、小红书等），具有一定的通用性。

如果你的 OpenClaw 工作台里正好缺一个可靠的超话分发组件，希望这篇记录能帮你少踩一些坑。
