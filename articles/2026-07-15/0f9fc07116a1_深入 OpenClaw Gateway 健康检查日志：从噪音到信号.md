## 背景：被健康检查日志淹没的日常
OpenClaw Gateway 是连接 Agent 与 MCP 工具、插件服务的核心中介，负责路由、负载均衡和健康探测。一旦上线，网关会以固定间隔对其管理的所有上游服务发起健康检查请求，`GET /health` 这类请求会不断出现在访问日志和内建日志中。在微服务数量较多或检查间隔较短的情况下，日志文件很容易被“心跳”刷屏，真正需要关注的错误、超时或上游状态变化反而被淹没。

但有经验的运维实践者都知道：这些日志绝非无用噪音。每一条健康检查记录都携带上游服务是否存活、响应耗时、状态码变化等信号。如何看懂它们、如何配置让日志“少而精”，是工程化交付必不可少的一环。

## 问题定位：哪些信号值得关注
通常健康检查日志包含以下关键信息，理解了它们就等于拿到一份实时的依赖健康报告：

- `upstream` / `upstream_addr`：目标的物理地址或服务名。
- `status`：健康检查请求自身的 HTTP 状态码（通常期望 200）。
- `upstream_status`：某些实现中，健康检查端点返回的上游内部状态码（例如 503 表示依赖数据库异常）。
- `response_time` / `latency`：响应耗时，持续升高往往预示着上游性能退化。
- `health_check_type`：active（主动探测）还是 passive（根据真实请求结果判断）。
- `healthy` / `threshold`：当前健康状态及是否越过阈值。

常见的需求是：**不看每一次成功，但必须在第一次失败时立刻感知**。这就要求对日志进行分级、过滤和采样。

## 实践步骤：从原始日志到结构化可操作信息
### 1. 开启结构化日志
在 OpenClaw Gateway 配置中启用 JSON 格式输出。例如（示意）：
```
logging:
  format: json
  level: info
```
这样 `jq`、`grep` 等工具可以精准筛选字段，避免正则匹配不稳定。

### 2. 按条件过滤健康检查记录
假设所有健康检查日志都包含 `"check":"health"` 标签，快速找出异常：
```bash
cat /var/log/openclaw/gateway.log | jq 'select(.check=="health" and .status!=200)'
```
若仍需保留一定量的成功日志以便统计趋势，可以只采集响应时间超过阈值的事件：
```bash
jq 'select(.check=="health" and .response_time>0.5)'
```

### 3. 调整健康检查参数以减少日志量
在配置中微调：
- `interval`：生产环境建议 15~30 秒，避免过于密集。
- `unhealthy_threshold` / `healthy_threshold`：例如连续 3 次失败才标记不可用，避免网络抖动引发误报警。
- `log_success_every`：某些网关支持每 N 次成功才输出一条日志，或成功时将级别设为 `debug`，失败时 `warn`。若无此能力，可通过日志采集器（如 fluentd）丢弃高频定期成功事件。

### 4. 区分主动与被动健康检查
主动检查由网关定时发起，被动检查利用真实请求的返回码（如 5xx 视为不健康）。被动检查日志往往携带真实的业务路径和错误信息，价值更高。可以专门提取被动检查失败事件：
```bash
jq 'select(.health_check_type=="passive" and .status>=500)'
```

## 踩坑记录
- **间隔陷阱**：将 `interval` 设为 5 秒甚至更短，一旦上游数量超过 20，日志写入瞬间变成海量，不仅占满磁盘，I/O 压力还会拖慢网关自身响应。
- **阈值过灵敏**：`unhealthy_threshold: 1` 配合短暂网络波动会导致大量上游被摘除，引发主动超时风暴。建议至少设为 2~3。
- **忽略 passive 检查的副作用**：只依赖主动检查，可能绕过真实流量暴露的局部故障（如某个接口 500，但 `/health` 仍然 200）。一定要同时观察 passive 结果。
- **日志级别统一为 info**：成功健康检查的信息密度极低，应降级为 `debug` 或 `trace`，仅错误保留 `warn`/`error`。如果没有内置分级能力，通过日志后处理将其丢弃。

## 可复用建议
1. **分离健康检查日志流**：给健康检查事件打上独立标签（如 `source=health_check`），输出到独立文件或主题，避免污染主访问日志。
2. **建立面板而非盯日志**：将健康检查的状态变化、响应时间导出为 Prometheus 指标，在 Grafana 中用 `up{job="openclaw-upstream"}` 之类的查询绘制面板。日志只用于下钻单次问题。
3. **采样与动态调整**：在开发/测试环境保持全量日志方便调试；生产环境启用采样（例如成功时每 10 次打印一次），并配合动态配置能力在需要排查时临时降低采样率。
4. **组合告警**：当日志中出现连续失败 + 被动检查失败时，触发告警通知，而不是仅凭单一健康检查失败。

## 总结
OpenClaw Gateway 的健康检查日志不是用来逐行阅读的“流水账”，而是一张跳动的心电图。工程化的处理方法是通过结构化、过滤、采样和指标化，将其从刷屏噪音转化为可观测性信号。调整参数时要平衡实时性与系统开销，始终保留对“第一次失败”的敏锐感知。当你不再被海量 200 日志打扰，却能第一时间捕捉到上游 503 时，这套日志才算真正为你工作。
