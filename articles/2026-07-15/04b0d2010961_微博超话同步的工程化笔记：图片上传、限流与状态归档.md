## 背景

在维护一个多平台内容分发管线时，微博超话成了绕不开的一环。我们已有的自动化流程基于 OpenClaw 做任务编排，通过 MCP 工具调用各类开放平台 API，期望能将图文定时同步到指定超话。但在接入微博时，很快发现图片上传的兼容性、接口的隐性限流，以及缺少持久化状态都会让一个看似简单的同步任务频繁卡死，且难以追责。

本文记录我们如何在一个工程化管线中处理这三大问题，而不依赖任何中间层的“高级封装”，只基于微博标准 API 和 OpenClaw 的任务与重试机制。所有踩坑点、代码思路和归档设计都经过真实验证，可复制到类似自动化场景。

## 问题拆解

- **图片上传不是一次调用就能成功**：微博开放平台对图片格式、上传方式、Content-Type 都有严格但未充分文档化的约束，一旦不满足只会返回模糊的「无效图片」。
- **限流像暗礁**：除了文档上写的应用级频率限制，还存在用户级、IP 级的软限流，拒绝请求时返回的错误码必须处理，否则整个管线会被拖垮。
- **缺少状态归档**：同步任务没有持久化记录，导致失败重做时可能重复发博，也无法统计健康度，排查历史问题只能翻日志。

## 做法：构建一个可靠同步 Pipeline

我们将整个同步抽象为“获取凭证、准备内容、上传图片、发布微博、归档状态”五个环节，并由 OpenClaw 的 Agent 循环调度。关键环节如下：

1. **凭证管理**  
   使用微博开放平台的 OAuth2 授权，提前获取 `access_token`，并存放在安全存储中。每次任务从配置拉取，若过期则触发刷新，避免在执行中因 token 失效中断。

2. **内容与超话标签**  
   超话通过博文中的两个 `#全角井号` 包裹的话题名识别。必须把 `#超话名称#` 放在博文最末尾或最前，中间不能有换行或多余空格。例如：
   ```
   status = "今日份同步内容 #OpenClaw#"
   ```
   我们会在代码里强制校验话题名是否与目标超话一致，防止打错标签导致落入无人区。

3. **图片上传**  
   调用 `statuses/upload_pic.json`，使用 `multipart/form-data`，字段名必须为 `pic`。关键：必须在 `Content-Disposition` 里带上 `filename`，且后缀严格是 `.jpg`、`.png` 或 `.gif`。微博 API 会检测文件的魔术头，如果上传了一个后缀为 `.png` 的 WebP 图片，会直接拒绝。我们的做法是上传前调用 `python-magic` 校验真实 MIME，并将其转为 RGB 模式的 JPEG（避免 CMYK 导致的解码失败）。  
   上传成功后得到 `pic_id`，立刻归档到临时存储，防止丢失。

4. **发布微博**  
   调用 `statuses/update`，传 `status` 与 `pic_id`。注意：微博不支持在一次请求里同时发多张图，如果需要多图，得调用 `statuses/upload_url_text` 等其他接口，但超话同步我们仅使用单图模式。发布成功后解析返回的 `id`（微博 ID），它是最终归档的关键。

5. **限流处理**  
   我们维护了一个简单的令牌桶，以应用级限制（测试账号为 1000次/小时）为上限。但更棘手的是隐性限流，错误码 `10022`（IP 请求频次过高）和 `10023`（用户请求频次过高）。当捕获到这些错误码时，我们会对该任务施以指数退避重试（首次 15s，下次 30s，最多 5 次）。如果 5 次后依然失败，记录为 `failed` 并发送告警，人工排查。同时还启用了一个轮换代理池，当单 IP 连续收到 `10022` 时就切换到备用出口。

6. **状态归档**  
   每一步的状态都写入轻量级 SQLite 表（后期可迁移到 Postgres）。表结构大致为：
   ```
   task_id | content_hash | status | pic_id | weibo_id | error_msg | retry_count | created_at | updated_at
   ```
   用 `content_hash` 作为幂等键，发布前先查询是否有成功的 `weibo_id`，避免重复发博。归档还允许我们构建一个简单的 Dashboard 观察最近成功率、失败原因分布。

## 踩坑点实录

- **图片分片上传的错觉**：有文档提到可以视频分片上传，但图片接口完全不需要分片，一次上传即可。尝试分片只会得到 `upload error`。
- **超话名称的大小写与特殊符号**：微博超话对大小写敏感，`#OpenClaw#` 和 `#openclaw#` 是不同的，且一些颜文字话题可能需要 Unicode 转义后才能被识别。务必从超话页面复制精确名称。
- **限流时返回的 HTTP 状态码是 200**：微博所有业务错误都放在 JSON 的 `error_code` 字段里，HTTP 层不会返回 429。因此不能依赖通用 HTTP 重试库，需专门解析错误码。我们的 MCP 工具封装了解析逻辑，收到 `10022/10023` 时抛出可重试异常，由 OpenClaw 调度器统一处理退避。
- **归档竟态**：早期并发调度时，同一个内容哈希可能同时查询无成功记录，导致发了两次。我们用数据库的 `INSERT ... ON CONFLICT DO NOTHING` 和唯一索引 `content_hash` 解决，但后来发现微博对完全相同的文本会返回同一条微博 ID，所以额外用 `weibo_id` 也做了去重校验。

## 可复用建议

如果要在 OpenClaw 生态中复用这套方案，建议：

- 将微博能力封装为一个 MCP 服务器，提供 `upload_image`、`publish_super_topic` 等可调用工具，内置退避、令牌桶和参数校验。
- 使用 OpenClaw 的任务系统管理重试与超时，不要在 MCP 工具内部无限轮询。
- 状态归档统一使用 SQLite，单文件零依赖，便于迁移和调试；在并发要求高时可加上文件锁或改用 PGlite。
- 图片准备步骤用 Lambda/函数计算执行，避免在主流程中安装 heavy 图片库。
- 监控上，归档数据可导出到 Prometheus，为成功率、限流次数设报警。

## 总结

微博超话同步的难点不在于发布一个帖子，而是如何让这条管线在不确定的图片素材、隐晦的接口约束和沉默的限流中依然可观测、可恢复。通过梳理上传细节、显式处理限流错误码、并为每一步构建幂等的状态表，我们把一个脆弱的脚本变成了工程化同步组件。对于任何需要对接国内开放平台的自动化管线，这套思路都有参照价值。
