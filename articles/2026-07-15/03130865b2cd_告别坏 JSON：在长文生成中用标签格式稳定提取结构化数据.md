## 背景：JSON 的长文软肋

在构建 OpenClaw 插件或基于 MCP 的自动化 Agent 时，我们频繁需要让大模型输出结构化信息——文章摘要、多段落翻译、分步骤规划。JSON 是自然首选，多数模型也都有针对 JSON 模式的微调。但当生成内容超过 2000 token，尤其包含换行、引号、代码片段时，JSON 的脆弱性就会集中爆发。

典型场景：一个翻译插件要求模型输出如下结构：
```json
{
  "title": "xxx",
  "paragraphs": ["段落1...", "段落2..."]
}
```
结果在流式推理中，输出可能是：
```
{"title": "xxx", "paragraphs": ["段落1...", "段落2...
```

尾部引号与括号缺失，直接导致 `JSON.parse` 失败。更糟的是，简单截断修复（如用正则补全 `"]}`）很容易误伤真实内容，或者产生语义错位。一旦某个 Agent 节点因为解析失败抛异常，整个自动化流水线都会中断，而这类错误在长文本、批量任务中复发率极高。

## 问题本质：生成式模型不是序列化器

模型输出 JSON 的本质是**模拟一种固定语法**，但自回归解码天然有累积误差。即使强制 JSON 语法约束（如 grammar-based sampling），在长序列中浮动依然明显。此外，流式解析 JSON 需要缓冲区维护 SAX 状态，对边缘情况（如字符串内未转义引号、换行、Unicode 特殊字符）的容错远不如标签格式直观。

## 方案：用自定义标签替代 JSON

我们尝试用 XML 风格的标签承载结构化字段。例如将上述翻译结构转换为：
```
<title>标题文本</title>
<paragraphs>
<item>段落1内容...</item>
<item>段落2内容...</item>
</paragraphs>
```
有几个关键设计：
- **顶层标签唯一**，避免与内容中的自然语言混淆（如 `<title>` 就比 `<t>` 安全，但仍可能跟 HTML 冲突，加前缀 `<reply_title>` 更保险）。
- **数组用重复子标签**，不用 JSON 的 `[]` 方括号，彻底避免闭合括号丢失。
- **禁止属性**，值只放在标签内文本，降低解析复杂度。
- **无自闭合标签**，一律 `<tag>...</tag>`，保持解析状态机最小化。

在 system prompt 中约束模型：“严格按照以下格式输出，所有字段必须闭合，禁止在标签外输出其他内容，标签名大小写敏感。”并提供 1-shot 示例。实测 GPT-4o、Claude 3.5 Sonnet、Qwen 72B 都能在 3～4 个示例内稳定遵守，输出 3000+ token 也未出现闭合错误。

## 解析器实现：极简流式状态机

重点在于支持流式 chunk 解析，边收 token 边提取已完成字段，避免缓冲全文。核心逻辑：
1. 维护当前解析状态：`outside_tag` / `inside_open_tag` / `inside_value` / `inside_close_tag`。
2. 遇到 `<` 且非转义时，切换状态开始记录标签名。
3. 遇到 `>` 时，判断是开标签还是闭标签（`/` 前缀）。
4. 文本累计在 `inside_value` 状态中，直到出现对应闭标签才提交字段值。
5. 错误恢复：若出现未闭合开标签就遇到新开标签，可丢弃之前未闭合的字段（或记录异常日志），不阻塞后续解析。

示例伪代码（Node.js 流式处理）：
```ts
class TagParser {
  private state = 'text';
  private buffer = '';
  onField(field: string, value: string) { /* 处理字段 */ }
  feed(chunk: string) {
    for (const char of chunk) {
      if (char === '<' && this.state !== 'tag') {
        this.commitText(); this.state = 'tag'; this.buffer = '';
      } else if (char === '>' && this.state === 'tag') {
        const tag = this.buffer.trim();
        if (tag.startsWith('/')) this.closeTag(tag.slice(1));
        else this.openTag(tag);
        this.buffer = ''; this.state = 'text';
      } else {
        this.buffer += char;
      }
    }
  }
}
```
整个解析器不到 100 行，可嵌入 OpenClaw 插件中。特别地，当模型在流式输出时产生意外换行，标签格式天然将其包含在值内，不会破坏外部结构。

## 踩坑与对策

**1. 标签名冲突**  
内容中可能出现与标签同名的文本，例如文章标题本身就是 “title”。模型可能输出 `<title>title</title>`，导致解析提前闭合。解决办法：使用带前缀的唯一标签如 `response_title`，并对值内容做最小转义（将 `<` 替换为 `&lt;`）。在 prompt 中明确要求模型：“如果值中包含 `<` 字符，必须转义为 `&lt;`”。

**2. 模型不闭合标签**  
当生成到预设 max_tokens 限制时，最后一个标签可能未闭合。解析器应设计为可丢弃最后未闭合字段，或留待下一次拼接后继续解析。在批处理中，可以设置稍大的 max_tokens 并让解析器校验所有必填字段，缺失时触发重试。

**3. 嵌套结构误判**  
避免使用同名子标签嵌套（如 `<list><item><item>...`），推荐扁平化或使用序号后缀（`<step_1>`, `<step_2>`）更简单。

**4. 多 Agent 协作中的 schema 契约**  
若前后节点由不同模型负责，标签格式同样便于人类调试。在 MCP 工具返回中，直接粘贴标签片段即可快速定位问题，远比残缺 JSON 容易肉眼排查。

## 可复用建议

- **标签设计规范**：全部小写+下划线，用前缀区分来源（如 `agent1_result`, `agent2_plan`）。为每个字段提供明确描述，写入 prompt 的格式节。
- **与 OpenClaw 集成**：将标签解析器封装为 `responseParser` 钩子，在 `afterModel` 阶段自动提取字段，注入到上下文字段中，后续节点可直接引用，无需手动解析。
- **兜底策略**：如果标签解析失败，退回原始文本，启动一次轻量修复 prompt（告知模型补全缺失标签），避免流程中断。
- **测试用例**：针对包含特殊字符、长文本、嵌套代码块的样例进行回归，确保流式与非流式均能正确提取。

## 总结

在自动化 Agent 的长文输出场景中，强制 JSON 模式往往成为瓶颈，而标签格式凭借其流式友好、容错性高、解析简单等特性，显著降低了结构化提取的工程复杂度。尤其在 OpenClaw 这类需要节点间可靠传递结构化数据的框架里，这套轻量级规范可以大幅减少“坏 JSON”引发的重试成本和流程脆弱性。标签格式不是银弹，但在内容为主、结构为辅的生成任务中，它比 JSON 更贴合模型的生成本质。
