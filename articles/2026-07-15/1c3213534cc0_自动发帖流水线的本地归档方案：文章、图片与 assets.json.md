## 背景

用 Agent 或脚本自动生成内容并分发到多平台，常见于个人知识库同步、技术博客自动推送等场景。早期流水线只关心“发出去了”，很少考虑本地留档。一旦要回溯某篇文章的完整上下文、排查平台渲染差异，或是准备迁移发布策略，就会发现原始内容散落在各平台的草稿箱、审核队列甚至已删除记录里，可追溯性极差。

更实际的问题是：生成的文章通常依赖图片，图片可能临时托管在 CDN、图床，或直接由 Agent 生成后上传，一旦外部链接失效，本地没有任何留存。此外，发布流程中往往缺少对 `title`、`slug`、`tags`、`published_at` 等元数据的结构化保存。这就要求在发帖流水线里加入一个**本地归档环节**，以可检索的文件结构保存文章全文、图片及一个 `assets.json`。

## 要解决的问题

1. **文章正文无留存**：只有推送后的平台链接，原始 Markdown 已丢失或被平台渲染后不可逆。
2. **图片依赖外部存储**：图片链接指向临时 OSS，流水线重跑或清理后无法恢复。
3. **元数据丢失**：发帖时间、目标平台、发布 ID、标签等没有统一记录，无法做跨平台关联查询。
4. **多版本混乱**：同一篇文章可能经过多次修改后重新发布，归档如果不做版本隔离，内容会对不上。

## 做法与步骤

### 1. 归档目录结构标准化
采用 `posts/{post_id}/` 为单元的目录规范，示例：

```
archive/
  posts/
    20250314-a-post-about-mcp/
      article.md
      images/
        diagram.png
        screenshot.webp
      assets.json
```

`post_id` 使用 `YYYYMMDD-slug` 或 UUID，保证唯一且可读。目录内所有文件都围绕同一个发布单元。

### 2. 在发布流水线中插入归档步骤
以典型 Agent 发帖流程为例（伪代码）：
```python
def publish_workflow(content_md, images: dict, meta):
    post_id = make_post_id(meta)
    archive_path = os.path.join(ARCHIVE_ROOT, post_id)
    # 归档文章
    write_file(os.path.join(archive_path, "article.md"), content_md)
    # 归档图片（从临时目录或内存路径拷贝）
    for name, img_path in images.items():
        copy2(img_path, os.path.join(archive_path, "images", name))
    # 构造并写入 assets.json
    assets = build_assets(post_id, meta, images, timestamp=now())
    write_json(os.path.join(archive_path, "assets.json"), assets)

    # 后续才是推送各平台
    for platform in meta.targets:
        publish_to_platform(platform, content_md, images)
```

**actions.json 的结构字段建议**：
- `post_id`
- `title`
- `slug`
- `created_at`
- `tags`
- `platforms`: 数组，每项包含 `name`（如 `openclaw-cn`）、`status`（`draft/published`）、`post_url`、`platform_post_id`、`published_at`。
- `images`: 记录图片相对于文章中的引用名、本地路径、原始URL。

这种设计能直接回答“这篇文章在某某平台上的链接是什么”“那条帖子的原文是什么”这类问题。

### 3. 处理图片的可靠归档
如果在 Agent 内部通过 MCP 工具生成了图片（比如调用绘图服务返回临时 URL），需要先下载到本地临时目录，再按命名规范拷贝到归档图片目录。  
建议：
- 下载时校验 Content-Type，防止把错误响应保存为图片。
- 统一转换为可长期保存的格式（如 PNG/WebP），避免依赖特定编解码器。
- 图片文件名使用固定映射，例如 `header.png`、`diagram-01.png`，与 `article.md` 中的相对路径对应。

### 4. 增量与版本控制
如果同一条 post_id 可能会被多次发布（修正错误后重发），可以用 `drafts/v2/` 子目录或通过 `assets.json` 中的 `revisions` 数组记录历次发布历史。每次重新发布时，只更新 `platforms` 字段和新增修订记录，不覆盖旧 `article.md`，而是写入 `article_v2.md`。

### 5. 对已有的多平台帖子的回填
如果已经有大量已发布内容，可以通过各平台的 API 拉取自己的帖子，反写为本地归档。此时 `post_id` 可以先用平台上的 ID 或 slug 推导，然后在 `assets.json` 中关联。这一步可以写一个一次性的 MCP 工具脚本，避免手工整理。

## 踩坑点

- **图片路径不一致**：本地归档的图片路径与生成文章时的临时路径不同，归档后 `article.md` 里的图片引用仍是旧路径，导致后续离线渲染失败。解决方式：在归档时，统一用正则替换 Markdown 中的图片链接为相对路径 `./images/xxx.png`。
- **并发归档**：如果多个 Agent 执行流水线，可能同时向同一 `post_id` 写入，产生竞态。用文件锁或基于 post_id 的文件系统信号量可以规避。
- **大文件图片**：一些绘图服务返回高分辨率位图，直接归档会撑大仓库。需在归档前进行尺寸检查与压缩，保留原始信息在 `assets.json` 中注明原始尺寸和来源。
- **windows/linux 路径分隔符**：归档的 JSON 中如果硬编码了 `\` 路径，跨平台读取会出错。统一使用正斜杠，避免踩坑。

## 可复用建议

1. **用 MCP 工具封装归档能力**：对外暴露一个 `write_archive` 工具，接受文章、图片、平台结果，内部完成规范化落地，降低每个流水线实现者的心智负担。
2. **将归档目录纳入版本控制**：推荐用 Git 管理 `archive/posts/`，每次流水线结束自动提交并推送，避免单机硬盘故障导致内容永久丢失。
3. **引入校验流程**：归档完成后，立即用本地渲染器（如 `mammoth` 或 `marked`）解析 `article.md` 与图片，若引用缺失直接告警，阻断发帖，防止发布后才暴露资源缺失。
4. **定义 assets schema**：与团队约定 `assets.json` 的 JSON Schema，并做运行时校验，保证数据的结构化程度，方便后续做跨帖子查询（如“找出所有 tag 包含 mcp 且已发布到 openclaw-cn 的文章”）。

## 总结

本地归档看起来是一个不起眼的附属步骤，却是自动化发帖系统长期健康运行的基础。通过标准化的 `posts/{id}/` 目录结构、`article.md` + 图片 + `assets.json` 的三件套组合，可以低成本实现完整的内容可追溯性。遇到交叉平台问题、历史内容恢复、重复发布管控时，一份可靠的本地归档就是最可靠的真相来源。

对 Agent/MCP 开发者而言，值得把这个归档能力作为发帖流水线的第一个步，而不是最后“顺便执行”的一步——因为只有先保存了原始数据，后续的发布、修改、回溯才有稳固的根基。
