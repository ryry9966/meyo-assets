## 背景

在基于 OpenClaw 搭构建微博内容同步 Agent 时，超话场景是一个高频但容易翻车的需求。Agent 需要将生成内容周期性发布到指定超话，包含图文。简单几次手动调用还能应付，一旦放大到每日数十条、跨多个超话，图片上传稳定性、限流处理和失败重试立刻成为工程瓶颈。本文记录在实现微博超话同步自动化过程中，围绕图片上传接口、限流退避和状态归档所做的功课，力求给其他自动化实践者一个可复用的参考。

## 问题拆解

微博超话发帖并不是标准开放 API，只能走网页端/ App 端的私有接口。一条完整的超话图文发布实际分为三步：获取超话可用权限与 fid → 上传图片得到 pid → 将文本与 pid 组合调用发帖接口。每一步都可能因 cookie 失效、频率限制、文件格式不符等造成中断。如果缺少状态记录，脚本重跑就会造成重复发布或遗漏。

因此我们明确三个重点：图片上传的可靠性、限流的工程化处理、发布状态的可追溯与可恢复。

## 接口分析与实现要点

### 1. 图片上传

通过抓包超话发帖流程，图片先上传至 `https://picupload.weibo.com/interface/pic_upload.php`。该接口采用 `multipart/form-data`，核心字段：

- `pic1`：图片文件二进制流
- `app`：固定值 `miniblog`
- `sina_upload`：`1`
- `mime`：`image/jpeg`（按实际指定）
- `data`：`1`，返回 JSON 格式

服务端返回 JSON 中包含 `pid`，如 `{ "data": { "pics": { "pic_1": { "pid": "0085D9Nvgw1..." } } }`。只有拿到有效 `pid` 才能拼接 `pic_id` 参数进行发帖。踩坑点在于：

- 图片格式：只接受 JPEG/PNG/GIF，WebP 会返回无意义错误。需要前置转换。
- 大小限制：大于 5MB 直接失败，但响应码仍为 200，需要解析 body 判断。
- Cookie 依赖：必须在请求头携带当前登录态的完整 Cookie，尤其是 `SUB=` 字段，有效期通常几天；一旦失效，上传返回 `-101` 需要实现自动重新登录获取。

### 2. 超话发帖

发帖接口为 `https://weibo.com/aj/mblog/add`，POST 表单参数：

- `text`：正文内容，注意超话标识会自动从 `topic_id` 生成
- `pic_id`：上述获取的 `pid`
- `topic_id`：超话 fid，形如 `1022:xxxxxx`
- `location`：`page_100808_super_index`
- `style_type`：`1`
- `pdetail`：`1022`

超话 fid 需要从用户关注列表或搜索接口提前获取并缓存，不建议每次调用都查询，浪费请求配额。

### 3. 限流机制

微博对发帖频次和图片上传频次均有严格限制。最常见错误码为 `100001`（操作太频繁），消息体为“您操作太频繁啦，请稍后再试”。经验表明：

- 同一账号两次发帖间隔最低需 ≥ 120 秒
- 短时间内连续上传多张图片也容易触发限流
- 触限后立刻重试只会延长封禁，需要冷却 5–10 分钟

工程上采用指数退避 + 状态机处理：一旦捕获限流错误，将任务状态置为 `rate_limited`，记录 `next_retry_at = now + backoff`，由调度器定期扫描过期任务重新执行，最大重试次数设定为 3，超次则置为 `failed` 并告警。

## 状态归档设计

没有状态记录的自动化如同定时炸弹。我们使用 SQLite 作为轻量状态库，表结构如下：

```sql
CREATE TABLE sync_task (
    id TEXT PRIMARY KEY,
    topic_id TEXT,
    content TEXT,
    image_path TEXT,
    pid TEXT,
    status TEXT,  -- pending, image_uploaded, posted, rate_limited, failed
    retries INTEGER DEFAULT 0,
    next_retry_at DATETIME,
    created_at DATETIME,
    updated_at DATETIME
);
```

发布流程每一步更新 `status` 与 `pid`，即使进程退出，重启后也能从断点继续，避免已上传图片浪费或内容重复发布。归档中还记录了每条任务的创建与更新时间，方便回溯。

## 可复用建议

1. **封装为 MCP 工具**：将上述流程打包成 MCP server，暴露 `sync_to_super_topic(image_path, content, topic_name)` 接口，供 OpenClaw 的 Agent 直接调用，内部处理图片转换、上传、发帖、限流等待，并返回最终状态。Agent 层只需关心内容生成与调度。
2. **幂等保障**：基于 content + topic 生成唯一 `task_id`（如 hash），写入前先查重，防止重复入队。
3. **Cookie 轮换**：若多账号同步，可以为每个账号维护独立 session，结合状态归档中的 `account_id` 做到负载与限流隔离。
4. **监控与告警**：对 `failed` 任务计数，超出阈值时推送通知（可复用 OpenClaw 内置的通知通道），避免长时间静默失败。

## 总结

微博超话同步看似简单，但图片上传的私有限制、触限后的混乱以及无状态导致的重复发布，才是自动化工程需要真正解决的痛点。通过细致还原接口逻辑、引入退避与状态归档，我们把一个脆弱的手动流程变成 Agent 可长期依赖的可靠组件。这些实践对任何涉及私有接口、频率限制的社交平台自动化都可复用，核心思想是：**让每一个步骤可观测、可中断、可恢复**。
