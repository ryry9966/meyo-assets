## 背景：一个帖子，五个平台

对于保持多社区活跃的技术创作者或小型团队，常见的工作流是：写完一篇内容，手工分发到 Twitter、Discord、GitHub Discussions、知乎、即刻等。随着自动化工具的成熟，不少人尝试用 Agent 串联 MCP 工具，实现“一次编写、多处发布”。

但当自动化真正跑起来，第一个令人头疼的问题不是技术联通，而是**发布行为失控**——同样的内容在五分钟内铺满五个平台，读者在多个渠道被同一信息轰炸，最终取关或静音。自动化发布如果没有边界设计，效率越高，体验越差。

## 问题拆解：为什么自动化发布容易变成刷屏

从工程角度，自动化的“刷屏感”主要来自三个层面：

1. **时间窗口过短**：脚本顺序执行，所有平台几乎同时发布，给关注你多个账号的人形成瞬时垃圾信息。
2. **内容完全同质**：直接复制粘贴 Markdown，缺乏对不同平台语境的适配，观感上像机器群发。
3. **缺少发布状态记忆**：每次触发都是“全新发布”，不检查最近已发内容，也没有频率控制，容易叠加重复或相似帖子。

对于 OpenClaw 生态里使用 Agent + MCP 做发布的人来说，这意味着需要一套可程序化表达的发布边界规则，而不只是脚本的“一键群发”。

## 做法：用 Agent 构建带时序与内容感知的发布管线

我们可以在 Agent 内部设计一个三阶段的发布决策流水线，通过 MCP 工具获取平台状态，再决定“发不发、何时发、发什么”。

### 1. 发布前检查（Pre-flight）

在内容生成后，Agent 调用一个 `memory://` 协议的自建 MCP Server，该 Server 持久化记录各平台最近 N 次的发布时间、内容指纹（语义哈希）、互动数据。检查项包括：

- **跨平台最小间隔**：同一作品在不同平台发布时间差 ≥ 2 小时（可配置）。
- **平台日内上限**：单平台每天不超过 2 条自动发布（人工发布不计）。
- **相似内容冷却**：取待发内容的 embedding，与 72 小时内已发内容做余弦相似度，超过阈值（如 0.85）则进入待定队列，提示人工复核。

这一步代码量不大，核心是一个 SQLite 数据库，MCP Server 暴露 `check_publish_policy` 工具，返回 `allowed` 布尔值与 `suggested_delay`。

```json
// MCP 工具返回示例
{
  "platform": "twitter",
  "allowed": true,
  "suggested_delay_minutes": 45,
  "reason": "上次发推 15 分钟前，未达到跨平台最小间隔"
}
```

### 2. 内容微调与格式适配

如果检查通过，Agent 使用内置的 LLM 根据平台特性对原始帖子进行简炼改写，而不是粗暴截断。例如：

- Twitter：提取核心观点 + 一句引导链接，控制在 240 字符内。
- Discord：保留完整技术细节，使用 `--` 分隔信息块。
- GitHub Discussions：保持完整长文，附加社区提问引导。

改写指令通过 Agent 的系统提示固化为模板，并用 few-shot 示例保证风格一致。这种**差异化微调**让同一内容在不同渠道呈现不同信息量，不造成重复阅读感。

### 3. 延时队列与最终发送

Agent 不直接调用平台发布 MCP，而是先推入一个基于 Redis 的延迟队列（可用 BullMQ 实现），发布时间为当前时间加 `suggested_delay`。这样即使多次触发发布，也自然形成错峰。

平台发布动作封装在不同 MCP Server 中（如 `twitter-mcp`、`discord-mcp`），每个 Server 负责 OAuth、速率限制、格式化。Agent 只在队列到期时调用相应 Server 的 `publish` 工具，并把发布结果回写记忆。

## 踩坑实录

- **时间同步与分布式执行**：如果 Agent 和队列运行在不同容器，时钟偏移会导致延迟计算不准。统一使用 UTC，并在检查间隔时基于绝对时间戳判断，避免“本地 now()”陷阱。
- **平台 API 的隐性频率控制**：Twitter API v2 对发推有 3 小时 300 条的硬限，但更隐蔽的是“重复内容降权”。我们遇到过几乎一致的帖子因短时间重复被 shadow ban，最终在相似度检查中加上了平台级的自适应冷却。
- **语义哈希计算开销**：用在线 embedding 服务对短文本做相似度，每次 check 会增加约 200ms 延迟。改用本地 MiniLM 模型 + 缓存池，延迟降到 30ms，适合高频检查。
- **人工打断的处理**：自动发布被用户手动编辑或删除后，记忆库中的指纹要同步失效，否则会错误地阻止新发布。实现上通过 Webhook 监听平台事件更新状态矩阵。

## 可复用建议

如果将这套逻辑提炼为可配置组件，可以在多个 Agent 项目里复用：

- **发布策略 DSL**：使用 YAML 定义规则集，包括最小间隔、平台优先级、改写模板、冷却时长等，Agent 启动时加载。
- **独立的 PubPolicy MCP Server**：提供 `check`、`record`、`reset` 三个核心工具，所有发布 Agent 统一调用，避免策略分散在多处。
- **监控与降级**：当记忆库不可用时，应降级为“只允许发布到单一平台”的安全模式，而不是直接放行所有请求。
- **在社区宣导**：告诉你的读者或团队成员，自动化发布有固定节奏（比如每日早 9 点、晚 7 点），帮助他们建立预期，减少“刷屏”的主观感知。

## 总结

自动化发布的价值不是“更快地填满所有渠道”，而是**用可控的节奏把合适的内容推到合适的地方**。通过 Agent + MCP 架构，我们可以把发布时间、内容形态、频率控制固化为可执行、可监控的策略层，而不是寄望于每次手动克制。

设定同步的边界，本质是用工程手段为读者保留信息呼吸感。这不仅保护了用户的注意力，也保护了内容品牌本身。

**边界做好了，自动化才能真正被信任。**
