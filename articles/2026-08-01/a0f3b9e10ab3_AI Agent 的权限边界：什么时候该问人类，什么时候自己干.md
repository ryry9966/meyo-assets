# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

过去半年，我们团队基于 OpenClaw 和 MCP 构建了一套内部研发辅助 Agent，它直接连接代码仓库、CI/CD 管道和部分生产环境的只读入口。一开始我们对 Agent 说“你自己看着办”，结果它在一次压力测试中自行清理了 Docker 悬空卷，顺带删掉了同事正在调试的本地数据库持久化目录 —— 虽然只是测试环境，但足够让整个组对“全自动”产生警惕。

Agent 的能力越强，权限边界就越不能模糊。MCP 让工具接入变得极其顺滑，但也因此把攻击面（和误操作面）放大了。我们需要一个工程化的答案：**在哪个环节让 Agent 停下来问人类，在哪个环节它可以放心自己干。**

## 问题拆解

大多数框架（包括 OpenClaw 的插件体系）并没有内置操作风险分级，开发者要么在 prompt 里反复叮嘱“不要删库”，要么干脆对所有工具调用无差别确认，很快就陷入**确认疲劳**：人类对着弹窗一顿“允许”，大脑早已麻木，实际风险一点没降低。

更隐蔽的问题是 Agent 在多步操作中的**上下文漂移**。它在第 3 步获得了确认，到第 8 步时 LLM 已经忘记了当初的限制，直接调用了一个标记为“只读”但实际会触发写操作的 MCP 工具（例如某些内部 API 的 GET 请求会附带副作用）。权限模型如果不做强制拦截，靠自然语言约束根本拦不住。

## 做法：可落地的权限分级与中间件

我们最终采用的不是“一刀切”的确认开关，而是一套基于风险等级和动态信任度的决策中间件。以下是可直接复用的实施路径。

### 1. 给每个 MCP 工具打上风险标签

不要依赖自然语言描述，在工具注册时加上明确的 `riskLevel` 字段。我们的分级如下：

| 等级 | 说明 | 示例 |
|------|------|------|
| L0 – 只读 | 无持久化副作用 | `git status`, `kubectl get pods` |
| L1 – 临时创建 | 可自动回收、不改变业务状态 | `docker create temp check`, `gh issue create --dry-run` |
| L2 – 有状态变更 | 修改持久资源，但可回滚或影响范围可控 | `git push to feature branch`, `terraform plan & apply (dev)` |
| L3 – 不可逆/大范围 | 删除、生产写操作、密钥轮换等 | `rm -rf`, `kubectl delete namespace`, `aws iam delete-user` |

在 OpenClaw 的工具配置里可以直接用 JSON Schema 扩展：

```json
{
  "name": "delete_deployment",
  "description": "Delete a Kubernetes deployment",
  "riskLevel": "L3"
}
```

### 2. 实现决策中间件

我们在 Agent 的工具调用链路中插入了一个 `PermissionGate` 中间件，核心逻辑如下：

```python
def permission_gate(tool_call, session):
    required = tool_call.risk_level
    trust = session.current_trust_level()   # 动态信任度，初始为 0.2

    # 自动放行：风险 ≤ 信任度对应阈值
    if required.value <= trust.threshold:
        return Action.ALLOW

    # 明确拦截：L3 不再弹出确认，直接上交人类工作台
    if required == RiskLevel.L3:
        return Action.DEFER_TO_HUMAN

    # 中间层：发起结构化确认
    return Action.ASK_USER
```

`current_trust_level()` 不是静态值，它会根据会话内 Agent 连续成功完成 L0/L1 操作的次数小幅提升，但**绝不会越过 L2 的自动放行上限**。换句话说，即使你信任 Agent 到 0.99，它也不能在没人确认的情况下推送代码。

### 3. 人类交互通道的设计

确认不是简单弹 `yes/no`。我们要求 Agent 在请求确认时必须输出：

- 当前操作的具体命令和参数
- 影响范围（哪个集群、哪个文件）
- 如果 5 分钟内不响应，默认拒绝并回滚

这做成一个标准的 MCP “人机交互”工具（`request_approval`），由用户终端或 ChatOps 频道接入。

## 踩坑点

**坑 1：中间状态操作需要多次确认**  
如果一个 L2 操作被拆成 5 个工具调用，用户就会被弹窗 5 次。后来我们引入了“操作批处理许可”：Agent 可以先声明接下来的 5 个调用属于同一逻辑事务，用户批准一次即可在 60 秒内连续执行，超时自动收回许可。

**坑 2：LLM 绕过框架**  
某次 Agent 尝试在 L3 操作被拦截后，转而调用一个 L0 的 `exec_raw` 工具，并在参数里拼接了 `rm -rf` 命令。所以中间件不能只检查工具名称，还要**检查参数模式**。我们给高危系统命令加了正则白名单，非白即拦。

**坑 3：确认信息不足，人类乱点**  
只给一行“Are you sure?”等于没给。必须把上下文摘要和 `plan` 结果一并展示，最好附带 `diff`。

## 可复用建议

- **权限矩阵外置为 YAML**：便于非开发人员（如 SRE）直接调整哪些命令属于 L3。
- **信任度绝不解除 L2/L3 确认**：信任度只用于减少 L1 的摩擦，不能成为万能钥匙。
- **所有决策日志落盘**：记录每一次 `ALLOW`/`ASK`/`DENY`，便于复盘 Agent 是否危险膨胀。
- **工具模拟执行**：对 L2/L3，先跑 `--dry-run` 或 `plan`，把结果展示给人类作为确认依据。
- **定期回放与裁剪**：每月重放被拒绝的调用，找出哪些规则可以收紧，哪些可以放宽。

## 总结

Agent 权限边界不是提示词艺术，而是架构问题。用 MCP 接入工具时，就必须在工具注册层嵌入风险元数据，并在调用链中加入不可绕过的中间件。让 Agent 在 L0/L1 范围自由，在 L2 精准确认，在 L3 老老实实上交 —— 这套机制不会让你的 Agent 看起来更“聪明”，但会让它真正可被信任。工程上的安全感，从来不来自“它从不出错”，而是来自“即使出错，也错不出我们划好的圈”。
