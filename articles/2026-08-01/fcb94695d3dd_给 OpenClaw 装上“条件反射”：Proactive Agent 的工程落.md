## 背景：你的 Agent 还在等人开口？

大多数 AI 助手的使用方式是对话驱动——你问一句，它答一句。即使接入了 MCP、插件和自动化工具，多数也只在用户显式触发时执行动作。OpenClaw、LangChain Agent、Coze 这类框架，很多教程都教你如何“响应请求”，但很少有人谈：**怎么让 Agent 自己决定什么时候该干活。**

这就是 proactive（主动式）能力。不等你打开聊天框敲指令，Agent 根据时间、事件或外部信号直接触发思考和行动。典型场景：

- 每天 9:00 自动汇总 GitHub 仓库的 Issue 并推送到 Slack
- 线上监控到错误日志后，Agent 自主调取上下文、跑诊断命令、开 Jira 工单
- 检测到数据库慢查询时，Agent 自动分析执行计划并把建议发给 DBA

要把这类行为落进 OpenClaw 体系里，需要解决一连串工程问题：触发器放哪、上下文怎么给、权限怎么控、出错怎么回滚。下面是一次实操记录，不卖概念，只讲做法和坑。

## 问题拆解

让 Agent 从“被动应答”变成“条件触发执行者”，核心要解决三件事：

1. **可靠的事件源与触发器**——谁通知 Agent“该干活了”
2. **可恢复的上下文**——Agent 醒来时，它对该任务的记忆是什么
3. **受限的行动空间**——主动行为不能失控，必须做沙箱、审批、回滚

我选择用 OpenClaw 作为 Agent 调度核心，搭配一个轻量的 sidecar cron 进程 + MCP Server 来扩展工具，实现一个每天早上自动分析代码仓库活跃度并发送简报的 proactive 工作流。

## 做法：从 cron 到 Agent 行动的完整链条

### 1. OpenClaw 实例与 MCP 工具箱

先让 OpenClaw 具备必要的行动能力。通过配置文件挂载两个 MCP Server：

- `github-mcp`：封装 GitHub API（读取 issues、PR、commits）
- `notify-mcp`：封装企业微信 / Slack 消息发送

确保 tools 在 OpenClaw 中可用，并且做好参数校验。这个部分和常规 MCP 接入一样，此处不赘述。

### 2. 植入外部的“神经脉冲”：定时触发器

OpenClaw 本身没有内置 cron，所以我在同一台机器上跑了一个简单的 Python 脚本，用 `schedule` 库实现每天 9:00 触发。触发动作是向 OpenClaw 的一次性对话注入：

```python
# 伪代码：触发主动任务
openclaw_client.create_conversation(
    system_prompt="你是一个仓库监控助手...",
    initial_message="请现在执行每日仓库活跃度检查，自主使用工具完成。"
)
```

这里的关键是 **initial_message 不是用户发的，而是系统定时注入的**。这意味着 Agent 的“用户”变成了定时器，而不是人。

为了让 Agent 能够做出正确判断，我在 system prompt 中明确描述了：

- 它的身份：早晨简报助手
- 可用的工具及使用顺序
- 输出格式要求
- 异常处理原则（如某仓库无权限，跳过并报告）

### 3. 多步编排与决策

Agent 被触发后，自主完成以下链路：

1. 调用 `github-mcp` 获取指定 repos 过去 24 小时的 events
2. 本地（通过 OpenClaw 内置的 skill）做数据清洗：统计提交次数、新增 issue 数、未关闭 PR 数
3. 用模板生成 Markdown 简报
4. 调用 `notify-mcp` 发送到团队频道

这里最需要注意的其实是 **工具调用的顺序容错**。如果第一步 GitHub API 返回 403 限流，Agent 必须停止后续步骤并发送“简报生成失败”的错误通知，而不是继续空数据渲染。我在 system prompt 中加入了状态机式的指令：

> 若任一步骤失败，立即用通知工具汇报失败详情，并停止任务。

### 4. 上下文记忆与连续性

定时任务每次都是新对话，没有记忆。为了让 Agent 可以“记得昨天的情况”，我让它在输出简报的同时，把关键数据（如未关闭问题数量）写入一个本地 JSON 文件，通过另一个 MCP 工具 `file-mcp` 实现。下一次运行时，Agent 先读取这个 memory 文件做趋势对比，这样就模拟出了跨会话的轻量记忆。

## 踩坑点

- **权限过大是风险源头**  
  早期我把 `github-mcp` 的权限开到可写（close issue、merge PR），结果有一次因为 API 误报，Agent 自动关了 3 个真实 issue。教训：proactive 类工具一律只给只读权限，需写操作的动作单独拆出，走人工确认 MCP（`human-in-the-loop`）。

- **上下文膨胀与 Token 泥潭**  
  定时触发时，如果 system prompt 写太长、工具描述过细，会导致每次对话从 1k token 起步，复杂任务还没开始已经吃掉一半窗口。解决方案是：将静态指令外置到 OpenClaw 的 skill 文件中按需加载，system prompt 只放任务流程，工具描述保持简短。

- **重复触发与幂等性**  
  调度器偶尔发重，导致同一简报发了两遍。在 notifier 工具中加入了去重键（基于日期+仓库名 hash），二次调用检测到已发送过，直接忽略。

- **Agent “沉默失败”**  
  某次 GitHub token 过期，Agent 调用工具后得到错误返回，但没主动汇报，而是产出一份“一切正常”的简报。原因是 prompt 里对工具返回码的判断疏忽了。后来强制要求：任何非 200 返回都要当作异常处理，不得推断数据。

## 可复用的工程建议

1. **分离触发器与 Agent 引擎**  
   不要把 cron 逻辑塞进 Agent 内部，用外部 sidecar 触发对话，保持 Agent 的无状态弹性。

2. **工具权限最小化 + 人工确认节点**  
   proactive 行为天然危险，只读工具可以自动执行，写操作工具建议封装成 MCP 内等审批的机制，例如发送确认请求到 IM，超时则回滚。

3. **用 MCP 实现记忆外存**  
   跨会话状态别用上下文窗口硬背，落地到文件、KV 或数据库，通过工具读写，Agent 自己决定何时取用。

4. **主动行为日志全记录**  
   每次定时触发的对话 ID、工具调用序列、最终结果都落地到集中日志。不是给人看的，是给另一个监控 Agent 看的，它负责检测“简报连续两天内容完全一样”这种异常。

5. **从简单节奏开始**  
   别一上来就搞复杂的事件驱动（webhook + 消息队列），先用 cron 跑单任务验证完整链路，搞定权限和容错，再扩展到 Kafka/MQ 这类流式触发。

## 总结

Proactive 不是给 Agent 装一个无限循环的 `while True`，而是给它一套可靠的触发-决策-行动-记忆循环。用 OpenClaw + MCP + 外部调度器这个组合，可以在不大幅改动现有对话式 Agent 的前提下，让它具备“自己找事做”的能力。

这次实践中花时间最多的不是写 prompt，而是搞清工具的异常契约、做权限隔离和处理重复触发。这些工程细节才是 proactive 能力能否在生产环境跑起来的关键。
