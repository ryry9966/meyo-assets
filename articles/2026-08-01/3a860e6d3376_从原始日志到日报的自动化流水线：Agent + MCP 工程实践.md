## 背景

团队日会之前，必须从 ELK、Loki、云监控、数据库慢查询日志甚至业务埋点里捞数据，人工拼成一份“昨日核心指标 + 异常事件”的日报。这份工作机械、重复，稍有遗漏就会被追问。

在 OpenClaw 生态里，Agent 能编排多步推理，MCP 能将外部能力标准化为工具。我们尝试用这套组合搭建一条日志到日报的管道，让 Agent 执行数据拉取、聚合、分析、渲染和推送，人只做最后的核对。以下是实践过程与经验。

## 问题拆解

一条可靠的日报管道需解决五个子问题：

1. **日志源异构**：格式不统一，来源分散（HTTP 日志、业务事件、告警接口）。
2. **提取与聚合**：需要从原始日志中计算出指标（QPS、P95 延迟、错误率），并定位异常片段。
3. **语义总结**：单纯扔数字太干巴，需要 Agent 用自然语言解释“为什么慢”“哪个服务有问题”。
4. **定时触发**：每天 8:30 之前必须发出。
5. **可靠推送**：输出到飞书、Slack 或邮件，且需处理限流、格式异常。

传统做法是写一堆 Python 脚本 + crontab，但业务变化时修改成本高。引入 Agent 不是为了“炫技”，而是让非开发人员也能通过自然语言调整统计口径和模板。

## 流水线设计

### 1. 统一日志接入层 —— MCP Server

我们没有让 Agent 直接连接各种数据源，而是用 MCP 暴露一个 `log-query` 工具，负责：

- 接受时间范围、日志类型、过滤条件，返回结构化 JSON 数组。
- 内置重试、超时和缓存（当天日志只查一次）。
- 对常见日志格式（JSON、nginx combined、自定义）做解析，统一输出 `timestamp, service, level, message, fields` 结构。

在 OpenClaw 中注册该 MCP Server：

```json
// openclaw_mcp_config.json 示例
{
  "mcpServers": {
    "log-bridge": {
      "command": "node",
      "args": ["dist/index.js"],
      "env": {
        "ES_ENDPOINT": "http://es:9200",
        "LOKI_ENDPOINT": "http://loki:3100"
      }
    }
  }
}
```

这样一来，Agent 只需调用 `log_query` 工具，不必关心后端是 Elasticsearch 还是 Loki。

### 2. Agent 编排 —— 分步推理

我们用 OpenClaw 构建了一个多步 Agent（基于 ReAct 模式），任务描述如下：

> 你是一个 SRE 日报助手。请查询昨日所有生产服务的日志，计算请求量、错误率和 P95 延迟；找出 Top 3 报错服务并解释原因；输出 Markdown 格式日报，包含指标卡片和异常摘要。

Agent 的第一步是调用 `log_query` 获取汇总数据（聚合由 MCP Server 内部完成，不消耗 token）；若检测到错误突增，会进一步调用 `log_query` 抓取具体错误栈。关键提示词约束了**分段处理**：统计先完成再总结，避免上下文窗口被原始日志撑爆。

实际运行中，我们观察到 Agent 倾向于一次性输出完整日报。为增加可控性，拆成两个 step：  
- Step 1：数据收集与统计（仅输出结构化原语）  
- Step 2：自然语言润色与排版（基于前一步输出）

### 3. 日报模板与推送 —— 插件化输出

日报最终需要美观地呈现在 IM 中。我们封装了 `report_render` 和 `send_message` 两个 MCP 工具。前者接收 agent 生成的结构化数据，填充 Jinja2 模板生成 Markdown 或飞书卡片 JSON；后者对接 Webhook。模板和渠道通过环境变量配置，修改无需动 Agent 逻辑。

## 踩坑记录

**坑1：日志格式变化导致解析静默失败**  
自以为正则稳如磐石，结果某天运营配置改动了 User-Agent 字段位置，导致上报数据缺失。最终强制要求所有服务输出 JSON 日志，用 schema 校验；非 JSON 日志在 MCP 层做降级解析，并附带 `_parse_warning` 字段，Agent 看到警告会主动汇报“部分日志未识别”。

**坑2：LLM 幻觉制造假指标**  
Agent 有时会把“错误率 5.2%”说成“5.0%”让数字变好看，或者凭空捏造一个不存在的时间点。解决：要求 Agent 在报告中引用 `log_query` 返回的 summary 对象，并在最终发送前做一轮关键数字校验（用简单的正则比对工具）。

**坑3：大时间窗口导致查询超时**  
7 天数据全量拉取让 Elasticsearch 和 Agent 都扛不住。我们强制日报仅允许查 TTL ≤ 48h 的窗口，且 MCP Server 会增加“预聚合模式”参数。Agent 通过参数选择分钟级或小时级聚合，大幅减少传输量。

**坑4：Agent 上下文污染**  
多天日报生成共用同一个 Agent 实例时，旧消息残留导致幻觉。解决：每次运行启动独立 session，并将系统提示词中显式声明“只根据最新工具输出回答”。

## 可复用建议

- **让 MCP 承担脏活**：日志清洗、聚合、格式转换都不应是 Agent 的推理任务，这些确定性逻辑放在 MCP server 里，既稳定又省 token。
- **配置驱动模板**：把日报统计指标、阈值定义成 YAML 配置文件，如 `daily_report.yaml`，Agent 运行时动态读入，这样 PM 可自行调整“核心接口 P95 ≥ 800ms 需告警”的规则。
- **防御性输出校验**：在 Agent 完成草稿后增加一个“Reflection”步骤，调用 `validate_report` 工具检查必需章节、数据范围、明显矛盾（如错误率总和超过 100%），不符合则重试。
- **灰度接入新数据源**：避免一次性把全部日志喂给管道，先选一个业务域的 Error 日志跑通，再逐步加 INFO、访问日志和 DB 慢查。
- **记录每次生成的审计日志**：存储原始查询参数、中间聚合结果和最终报告，失败时无需反复查数据源就可以复盘。

## 总结

从原始日志到结构化日报的自动化，本质是“确定性数据处理 + 不确定性语义总结”的结合。我们的流水线把前者交给 MCP 工具链，后者交给 Agent，并通过严格的校验层兜底。当前这套方案已在内部稳定运行两个月，每日 8:25 自动推送，人工核对通常在 2 分钟内完成。最大的改变不是省了多少时间，而是日报格式与关注指标可以随时用自然语言调整，响应业务变化的能力大幅提升。

如果读者已有 OpenClaw 环境和日志中心，建议从“一个 MCP server + 单步 Agent”的最小闭环开始验证，再逐步叠加分段推理和防御校验。
