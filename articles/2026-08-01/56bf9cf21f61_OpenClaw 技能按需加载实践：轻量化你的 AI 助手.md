# OpenClaw 技能按需加载实践：轻量化你的 AI 助手

## 背景：当“万能助手”变得臃肿

在给 OpenClaw 接入各种自动化能力后，Agent 的描述越来越长：文件操作、数据库查询、HTTP 请求、代码执行、画图、天气……大部分对话其实只需要其中一两个能力，但为了让模型知道有哪些工具可用，我们不得不把所有工具定义原封不动地塞进 system prompt 或 MCP 工具列表里。这带来几个实在的麻烦：

- **上下文窗口被工具描述大量占用**，实际留给对话和推理的空间严重缩水。
- **Agent 启动变慢**，所有工具模块在启动时被无条件加载，哪怕根本用不到。
- **依赖冲突频现**，不同技能依赖的库版本不一致，混在一起容易炸环境。
- **维护心智负担重**，加一个能力要小心翼翼评估对现有全局状态的影响。

OpenClaw 社区逐渐演化出一套 **Skills 按需加载机制**，本质上就是把“能力”拆成独立技能包，根据对话意图动态加载，用完释放。这并非新概念，但工程落地上有不少细节值得写一写。

## 问题拆解

要实现按需加载的技能系统，需要回答四个核心问题：

1. **怎么描述一个技能**，才能让匹配器理解“什么情况下该用它”？
2. **如何在不实际加载代码的情况下发现技能**？
3. **怎么实现动态加载，且不会搞垮主进程的环境**？
4. **用完后如何干净地回收**？

下面结合 OpenClaw 的实际做法，给出可复用的设计与步骤。

## 做法与步骤

### 1. 技能包标准化

每个技能是一个目录，包含两个必要文件：`skill.yaml` 和 `entrypoint.py`（或 Dockerfile）。

`skill.yaml` 最小结构如下：

```yaml
name: weather-query
description: Get current weather and forecast for a given city
triggers:
  - keywords: [weather, temperature, forecast, rain, celsius, fahrenheit]
  - embedding_ref: "weather_check"
version: 1.0.0
dependencies:
  python: requests>=2.28
isolation: process  # 或 container / thread
timeout: 30s
entrypoint: main.py:run
```

**关键词**是快速匹配的第一道过滤，`embedding_ref` 可以指向一个典型查询语句的向量化结果，用于精确匹配。  
`isolation` 字段指明运行方式，`process` 表示单独进程，避免库冲突；`container` 则完全隔离。

### 2. 技能注册（只读元数据）

OpenClaw 启动时扫描 `skills/` 目录，读取所有 `skill.yaml`，生成一个轻量索引（名字、描述、触发器、隔离模式、超时），**但绝不导入任何 Python 模块**。这个过程极快，且不需要在启动时安装依赖。

我们可以用 `pyyaml` 快速构建索引，存入一个 dict：

```python
index = {}
for skill_dir in Path("skills").iterdir():
    if (skill_dir / "skill.yaml").exists():
        with open(skill_dir / "skill.yaml") as f:
            skill_meta = yaml.safe_load(f)
        index[skill_meta["name"]] = skill_meta
```

内存开销极小，几百个技能也不成问题。

### 3. 意图路由与技能匹配

用户消息进来后，引入一个轻量的 **Router**，它由两部分组成：
- **快速规则层**：用关键词集合进行多模式匹配，命中的技能进入候选池。
- **语义匹配层**（可选）：如果关键词匹配不准，将用户 query 与各技能的 `embedding_ref` 做相似度计算，取超过阈值的技能。可以用本地小模型或调用 openai embeddings。

Router 最终输出一个 **技能名**，并把该技能元数据提交给加载器。这里要设置一个 fallback——如果什么都没命中，就什么都不加载，避免无意义开销。

### 4. 动态加载与隔离执行

根据 `isolation` 类型，动态加载策略不同：

- **process**：用 `subprocess.Popen` 启动一个 Python 子进程，传入序列化后的参数，通过 stdout 或临时文件回传结果。子进程中可以自由安装技能 dependencies，不影响主环境。
- **container**：预先构建好技能镜像，动态 `docker run`，通过 volume 或网络通信。
- **thread**（仅限信任且无依赖冲突的技能）：在受限的线程池里执行，谨慎使用。

加载完成后，Agent 的工具列表里会增加该技能对应的函数签名。注意：加载是异步的，Router 可以先返回一个“正在准备工具”的提示，避免让用户干等。

### 5. 卸载与资源回收

会话结束或超过 N 轮不再调用该技能时，执行卸载：
- 若为子进程，发送终止信号，等待退出，清理临时文件。
- 若为容器，`docker stop` 并移除容器。
- 从当前 Agent 的工具列表中移除对应函数，释放上下文字节。

为防止内存泄漏，卸载逻辑用 `atexit` 或 `contextlib` 做兜底注册，确保即使异常退出也能回收。

## 踩坑点

### 坑1：技能匹配时好时坏
关键词匹配容易漏掉口语化表达，比如用户说“今儿会下雨吗”可能不在 weather 的英文关键词中。  
**解法**：让 Router 支持多语言关键词列表，并始终配合 embedding 相似度做第二道保证。可以先将用户输入自动转英文或直接用多语言向量模型。

### 坑2：子进程依赖安装引发“启动风暴”
如果技能用 process 隔离，每次动态启动时执行 `pip install`，首冷启动延迟可能达到数秒甚至十几秒。  
**解法**：为常用技能预构建虚拟环境，放在技能目录的 `.venv` 里，启动时直接指定解释器路径。或使用 `pex` / `shiv` 打包成自包含可执行文件。

### 坑3：有状态的技能未清理
比如数据库技能可能打开连接池，卸载时连接没关，导致资源泄露。  
**解法**：在技能入口函数里实现 `cleanup()` 方法，卸载器在杀掉进程前先尝试调用该方法（可通过 SIGTERM 信号 + 合理 timeout）。

### 坑4：冷启动带来的体感卡顿
即使做了预热，用户第一次请求某个技能时还是要等几秒。  
**解法**：Router 可在空闲时根据历史对话习惯预热几个高频技能；或者在收到用户消息后先快速返回一个“正在准备相关工具...”的文本，同时异步加载。

## 可复用建议

- **技能清单是接口契约**：不要在 skill.yaml 之外定义额外的加载逻辑，所有运行时行为必须能从元数据推导出来。
- **使用无状态函数为佳**：技能函数最好设计成接收参数、返回结果，不保留内部状态；状态统一交给外部存储（如 Redis，或回写到 OpenClaw 的记忆模块）。
- **为技能写测试**：单独执行技能入口函数，输入 mock 参数，检查输出格式。测试应独立于 OpenClaw 主框架运行。
- **监控加载耗时与成功率**：埋点记录每个技能的加载次数、冷启动时间、超时次数、卸载是否完整，方便持续优化。
- **版本化技能**：技能元数据中标明 version，升级时保留旧版本目录，Router 可以根据模型能力选择合适的版本（类似 API versioning）。

## 总结

按需加载不是魔法，而是把“静态全局注册”改成“基于意图的动态按需装配”。合理设计技能描述、隔离模式与 Router，可以让 OpenClaw Agent 大幅瘦身：启动更快，上下文被高效利用，依赖冲突几乎消失，扩展新能力的成本也低得多。

下一步可以探索的，是将这套机制与 MCP 的动态工具发现结合——让 Agent 不仅能按需加载本地技能，还能在对话过程中发现并挂载远程 MCP server，真正做到能力即插即用。这会在生产环境中显著提升可伸缩性，也让我们告别把一切能力都塞进 system prompt 的粗放模式。
