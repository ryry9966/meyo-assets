## 为什么需要 AGENTS.md

在 OpenClaw 社区中，越来越多的团队开始利用 Agent 与 MCP 工具链完成日常编码、部署、测试等自动化任务。一个常见的痛点很快暴露出来：**AI 代理对你项目的上下文一无所知**。它不知道你的 monorepo 是怎么组织的，不清楚应该用 pnpm 还是 npm，也不理解为什么 `infra/terraform/` 下的文件不能随便动。结果就是：

- 代理生成了正确的代码，但运行了错误的脚本；
- 测试跑在错误的 Node 版本上，CI 一路飘红；
- 一个“简单的文件修改”意外覆盖了关键配置。

这些问题不是 Agent 能力不够，而是它缺少一份**工作空间的使用手册**。AGENTS.md 正是为此而生——它是放在项目根目录下的纯文本文件，专门写给 AI 代理看，告诉它这个仓库的规矩、工具、边界。

OpenClaw 生态里，AGENTS.md 配合 `claw.yaml` 可以自动注入为系统提示的一部分，或者通过 MCP 的文件系统工具让 Agent 主动读取。下面我就以一个真实项目为例，拆解这份手册该写什么、怎么写，以及那些让人头大的坑。

## 怎么写出有效的 AGENTS.md

### 1. 确定基本结构

一份合格的 AGENTS.md 不需要长篇大论。我提炼了五个必填段落：

**项目概览**：一句话说明项目是什么，运行的产物是什么。比如：“一个 Next.js 14 的博客平台，输出静态站点到 `out/`。”

**目录速查**：只列对代理有意义的路径。避免把整个 `tree` 输出塞进去，那样只会浪费 token。例如：
```
/app        - 页面路由（App Router）
/content    - Markdown 文章
/lib        - 通用工具函数，禁止在此处添加组件
/infra      - Terraform 定义，除非明确要求，否则不要修改
```

**运行环境与命令**：明确工具链和常用命令。代理需要知道用什么跑，怎么跑。
```
Node.js 18+，使用 pnpm
开发: pnpm dev
构建: pnpm build
测试: pnpm test -- --coverage
Lint: pnpm lint
```
附带 `package.json` 的 scripts 固然可行，但手动写一遍能强制人工审核哪些命令允许代理执行，哪些需要隔离。

**硬约束与禁区**：这是最重要的一部分，必须用明确、不可商量的语气。例如：
- **永远不要** 直接修改 `infra/` 下的任何 `.tf` 文件。
- 新增依赖前，必须先在 `package.json` 的 `dependencies` 对象中确认是否已存在。
- 所有生成的数据库迁移文件必须放在 `migrations/` 目录，并遵循 `V<序号>__描述.sql` 命名。

**可使用的外部工具（MCP Server）**：如果你的 OpenClaw 代理连接了多个 MCP 服务器，可以在这里列出，并说明哪些任务应触发哪个工具。例如“查询订单数据 -> `order-db` MCP，只读操作”。这能减少代理调用错误接口的概率。

### 2. 让 OpenClaw 自动加载

在 OpenClaw 的工作空间配置 `claw.yaml` 中，可以显式声明上下文文件：

```yaml
context:
  files:
    - AGENTS.md
    - .cursorrules
  inject: system_message # 注入到系统消息的最前面
```

这样一来，每次启动 Agent 会话时，AGENTS.md 的内容会自动拼接到提示词的首部。我个人习惯把 `inject` 设为 `system_message`，因为这会让模型在处理后续所有任务时都受到手册的约束。如果项目特别大，AGENTS.md 内容较长，可以改用 `tool: read_file` 模式，让 Agent 按需主动读取，避免首轮 token 超支。

### 3. 验证是否生效

写完手册后，别直接把它当成隐形铠甲。做一个简单测试：向 Agent 发出一个“越界”的指令，例如“帮我重构一下基础设施代码”，如果 AGENTS.md 生效，代理应该回复类似“根据项目约定，我无法修改 `infra/` 下的文件，除非你明确允许”。如果它一声不吭就动手，说明注入失败或约束描述不够强。

## 真实踩坑实录

**坑一：手册写成了回忆录**  
最开始时，我把项目历史、架构决策、PR 规范全塞进 AGENTS.md，生成了一篇 3000 多字的文档。结果 Agent 在解决一个小 Bug 时，系统提示的上下文窗口被挤满，模型完全忽略了关于测试命令的说明，导致提交了没跑过 lint 的代码。后来我将内容压缩到 800 字以内，核心信息结构化，问题消失。

**坑二：软约束被忽视**  
“尽量避免修改 `legacy/` 目录”这种软约束对模型约束力很差。必须改成“**禁止** 修改 `legacy/` 目录下的任何文件，除非任务描述中显式要求”。在 AGENTS.md 里，语气比想象中更重要。

**坑三：外部链接的幻觉**  
我尝试在 AGENTS.md 中写“详细的代码风格参考 `https://internal.wiki/style`”，但这个链接 Agent 无法访问（MCP 没有获取内网页面的工具），反而让模型开始编造规范。最终我把核心风格要点直接内联到手册里解决了这个问题。

**坑四：多人协作时的滞后**  
AGENTS.md 会被作为约束文件，但团队成员更新 `package.json` 命令后往往忘记同步手册。后来我们在 pre-commit hook 里加了一个检查：如果 `scripts` 字段变动，会提醒开发者同步更新 AGENTS.md 中的命令列表。一个简单的脚本就避免了很多麻烦。

## 可复用的工程化建议

1. **模板化维护**：为同类项目维护一个 AGENTS.md 模板，只替换目录树和命令。模板示例：
```markdown
# {项目名} 工作空间手册
- 运行环境: ...
- 包管理器: ...
- 构建命令: ...
- 测试命令: ...
- 禁止修改: ...
- MCP 工具: ...
```
这样新项目接入 OpenClaw 时，十分钟就能完成手册配置。

2. **使用分隔注释**：在手册中插入 `<!-- AGENT: 以下内容为高优先级约束 -->` 这样的注释，虽然对人类无用，但可以作为后续自动化解析的分割标记，未来如果 OpenClaw 支持按分段注入，这种标记会很有用。

3. **与 MCP 工具描述对齐**：如果你用的 MCP 服务器已经提供了详细的工具描述，AGENTS.md 里就不要再重复写一遍，而是写明“当需要操作数据库时，使用 `db-mcp` 工具，参见其工具描述”。保持单一事实来源，降低维护成本。

4. **定期审计**：每隔一两个迭代，开一个临时 Agent 会话，让它“复述你认为项目最重要的三条约束”，检查它是否能准确提取 AGENTS.md 中的核心规则。如果不能，说明手册需要调整。

## 总结

AGENTS.md 不是什么银弹，只是为 AI 代理准备好的一份“入职文档”。但它投入的成本极低，收益却很明显：减少误操作、统一命令规范、让 Agent 在正确的边界内发挥最大效能。对 OpenClaw 这类深度整合 MCP 与插件的代理框架而言，一份精确的工作空间手册往往比盲目增加工具更有效。如果你的项目还没有 AGENTS.md，今天花 20 分钟写一份，明天早上让 Agent 跑一次全量测试，大概率会对它的“懂事程度”感到意外。
