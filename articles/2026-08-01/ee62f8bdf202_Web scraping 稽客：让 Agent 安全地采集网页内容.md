## 背景

在基于 OpenClaw 的自动化流水线里，Agent 经常需要访问外部网页来获取实时数据、验证信息或补充上下文。原生的做法是通过 function calling 或插件直接执行 HTTP 请求，甚至启动无头浏览器。这种做法灵活，但缺少约束，一旦 Agent 发送了错误请求，轻则触发目标站点的风控，重则泄露内网信息。我们需要的是一种“稽客”机制——在 Agent 和网页之间插入一层用于稽核、脱敏、限速和审计的代理，使得每次采集行为都是安全、可解释、可回放的。

## 具体问题

1. **无节制的请求**：Agent 可能短时间内发出大量请求，部分调用还可能命中内网地址或不受信任的外部站点。
2. **危险内容携带**：采集结果可能包含恶意脚本、Iframe、跟踪像素，直接喂给后续步骤会扩大攻击面。
3. **审计缺失**：生产环境需要知道 Agent 什么时候、因为什么 Prompt 访问了哪个 URL、返回内容的大致形态，以便排障和合规。
4. ** token 浪费**：HTML 噪声信息过多，会迅速耗尽 LLM 上下文窗口，增加成本。

## 方案与步骤

我们在 OpenClaw 的 MCP 生态里实现一个“稽客”（Guike）服务，作为 MCP 工具暴露给 Agent。整体思路是：Agent 只拥有向稽客服务申请网页的权限，而稽客服务负责执行真实请求、进行内容清洗、写入审计日志，并将安全的纯文本或 Markdown 返回给 Agent。

### 1. 定义采集策略
在稽客服务的配置中明确：
- **域名白名单**：允许采集的域列表，支持通配符，例如 `*.example.com`。
- **速率限制**：每个 Agent 会话的全局 QPS，以及对同一域名的连续请求间隔。
- **内容最大尺寸**：超过阈值则截断并标记，避免 token 爆炸。
- **可接受的内容类型**：只允许 `text/html` 和 JSON 资源，拒绝二进制文件。

### 2. 实现稽客 MCP 服务器
以 Python 为例，使用 `playwright` 或 `httpx` + `BeautifulSoup` 做抓取核心，借助 `bleach` 或 `nh3` 库做 HTML 清洗，并通过 MCP 库暴露工具：

- `fetch_page(url: str) -> dict`：接收 URL，校验域名 → 检查频率→ 发起请求 → 提取文本 → 清洗脚本/样式/注释 → 转 Markdown → 记录审计日志 → 返回 `{"title":..., "markdown":..., "fetched_at":...}`。
- `check_url(url: str) -> dict`：只做安全校验并返回建议，允许 Agent 先试探。

启动时通过环境变量注入白名单、Redis 连接等参数，便于运维调整。

### 3. 集成到 OpenClaw
在 OpenClaw 配置中增加 MCP 服务器声明（示例）：

```json
{
  "mcp_servers": {
    "guike": {
      "command": "python",
      "args": ["-m", "guike_mcp", "--config", "/etc/guike/config.yaml"]
    }
  }
}
```

这样，Agent 的可用工具列表中自然出现 `guike_fetch_page` 和 `guike_check_url`。在系统级 prompt 中增加指引：“当需要获取网页信息时，必须使用稽客工具，不要自行构造任何 HTTP 请求。”

### 4. 审计与监控
稽客服务每次调用都生成一条结构化日志，包含：
- 调用时间、Agent 实例 ID、会话 ID
- 原始 URL（敏感参数做哈希脱敏）
- 检查结果：是否命中白名单、是否被限流
- 响应大小、清洗后大小、耗时
- 成功/失败状态及异常信息

日志输出到 stdout 供采集，同时对接 Prometheus 指标暴露 `/metrics` 端点，可以配置 Grafana 面板观察采集健康度。

## 踩过的坑

1. **无头浏览器资源开销大**：如果直接用 Playwright 启动完整浏览器，并发几个请求就有可能打满 CPU。改为优先使用轻量 HTTP 客户端 + HTML 解析，仅当页面需要 JS 渲染时才降级到 headful 方案，并用浏览器池控制并发数。
2. **清洗不彻底**：部分目标站点将脚本藏在 SVG 或自定义元素里，`bleach` 白名单可能遗漏。推荐使用 `nh3`（Rust 实现的 HTML 净化器）并配置严格的标签白名单，然后通过 Markdown 转换剥离其余结构。
3. **速率限制被多实例绕过**：多个 OpenClaw agent 进程可能共享同一个稽客服务，但每个进程自行计数会导致超量。必须使用集中式计数器（如 Redis `INCR` + TTL）来实现精确限流。
4. **验证码与反爬**：即使是内部系统，有时也会突然弹出验证码。稽客可以返回特定错误码 `captcha_required`，要求 Agent 暂停并向用户请求人工介入，避免无意义重试。
5. **审计日志过于啰嗦**：不要直接把页面全文写入日志，只记录摘要和尺寸；日志级别可配置，生产环境不在日志中输出 URL 查询参数。

## 可复用建议

- 将稽客服务容器化，通过 Docker Compose 或 K8s 部署，配合 OpenClaw 的 MCP 连接串，实现开箱即用。
- 内容统一转为 Markdown 后返回，既能减少 token 消耗，也能降低后续解析难度。
- 提供健康检查端点（如 `GET /healthz`），方便 OpenClaw 在工具调用前进行可用性探测。
- 对于频繁用到的域名，可以增加本地缓存（带 TTL），减少重复抓取。
- 白名单和限流配置存放在配置中心（如 etcd 或 AWS Parameter Store），实现热更新，无需重启服务。
- 与内部 DNS/网络策略联动：稽客服务部署在隔离网络区域，确保即使 Agent 变坏了，也只能访问白名单域名。

## 总结

“稽客”不是单个工具的名字，而是一种在 OpenClaw Agent 和外部 Web 之间引入安全控制的模式。通过 MCP 工具化、内容清洗、速率限制、审计日志的组合，我们可以安全地将网页采集能力赋予 Agent，同时保持可观测性和控制力。这种模式已经在实际项目中平稳运行数月，日均处理数万次网页请求，未发生过因 Agent 行为导致的安全事件。如果你的 OpenClaw 流程准备放开网页采集，从第一天起就把稽客加进去，远比事后补救要轻松。
