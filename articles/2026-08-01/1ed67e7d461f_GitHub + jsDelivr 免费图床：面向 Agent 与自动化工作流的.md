## 背景：Agent 流水线中的静态资源归处

在搭建 OpenClaw、MCP 插件或自动化工作流时，经常需要托管少量静态资源——插件 logo、执行截图、知识卡片配图、API 返回的图表快照。这类资源有两个共性：体积小、调用不频繁，但对可用性和外网可达性有要求。

常见的做法是买 OSS+COS 或者套 Cloudflare R2，但对于个人开发阶段或社区工具，引入计费账号、权限管理、跨域配置的复杂度远超图片本身的价值。也有人直接把图片塞进 GitHub 仓库用 `raw.githubusercontent.com` 访问，但 Raw 节点没有边缘缓存，国内部分运营商下速度堪忧，甚至会间歇 443 超时。

有没有一种零成本、零鉴权、天生支持 CDN 而且能与 GitHub 仓库天然绑定的方案？jsDelivr 提供了一个不错的折中。

## 问题：免费图床的工程约束

在选择免费图床时，我们给自己定了几条工程约束：

1. **不依赖额外账号体系**：最好复用 GitHub 仓库，不要为图片再注册一套服务。
2. **支持 CDN 分发**：至少保证国内主要城市能在 2s 内获取几十 KB 的图片。
3. **稳定规则 URL**：避免动态签名链接，方便在 Prompt、配置文件中直接拼接。
4. **能融入脚本/Agent 自动上传**：这是关键，一切手动拖拽的图床都不值得用于自动化流水线。

第三方图床服务要么需要登录、要么链接七天后失效、要么随时关闭。GitHub Raw 和 GitHub Pages 在性能上又不够理想。jsDelivr 的免费套餐对 GitHub 公开仓库提供全球 750+ 节点加速，并且完全兼容语义版本，刚好踩中我们的需求。

## 做法：最小化搭建流程

整个搭建过程不需要任何服务器，只依赖一个 GitHub 公开仓库。

**第一步：创建专用图床仓库**

新建一个公开仓库，例如 `assets-bed`。初始化 README 后，在根目录下建立按用途分类的目录结构：

```
assets-bed/
  screenshots/
  logos/
  cards/
```

**第二步：上传图片并获取 jsDelivr 链接**

把图片文件直接推送到仓库。假设仓库名为 `your-username/assets-bed`，main 分支上有 `screenshots/demo.png`，那么 jsDelivr 的访问地址是：

```
https://cdn.jsdelivr.net/gh/your-username/assets-bed@main/screenshots/demo.png
```

如果仓库打了 tag 如 `v0.1`，就可以用 `@v0.1` 替代 `@main`，实现版本化资源管理。这一点对需要稳定引用固定版本资源的工作流很有用——避免主分支更新后、历史聊天记录里的图片内容发生意外变化。

不需要任何额外配置，直接浏览器打开链接就能看到图片，响应头自动包含强缓存和跨域允许。

**第三步：集成到自动化环节**

对于 OpenClaw 或 Agent 工作流，可以通过 Git 命令或者 GitHub API 自动上传。一个常见模式是：Agent 生成图片后，调用 `gh` CLI 或者 Node.js 的 `@octokit/rest` 将图片推送到指定路径，然后拼接 jsDelivr 链接返回给用户。比如在 MCP 工具实现中，我们用这样一段伪代码构造链接：

```
const baseURL = 'https://cdn.jsdelivr.net/gh/owner/repo@main';
const filePath = 'screenshots/result.png';
const finalURL = `${baseURL}/${filePath}`;
```

整个过程零鉴权配置（公开仓库），不需要 token，只要保证仓库路径正确即可。

## 踩坑清单

实践过程中踩了几个对自动化不友好的坑，记录如下：

**1. 缓存刷新不及时**

jsDelivr 对每个文件有较长的边缘缓存，默认情况下覆盖上传同一个路径的图片，CDN 节点不会立即更新。对自动化流水线而言，生成截图后如果立即拼接链接返回，用户看到的可能是旧图。解决方法是上传时使用带时间戳或 UUID 的唯一文件名，或者在 URL 末尾追加任意 query 参数 `?v=timestamp`。我们更推荐唯一文件名方案，可以避免同一 URL 内容语义变化造成的缓存脏读。

**2. 文件大小 20MB 软限制**

GitHub 单个文件建议不超过 50MB，但 jsDelivr 对超过 20MB 的文件可能不缓存或拒绝加速。对于截图类应用一般不超过 2MB，不会触发限制。如果工作流里有视频预览或模型文件托管需求，不适合此方案。

**3. 私有仓库无效**

jsDelivr 只能加速公开仓库。如果你希望图床内容不对外直接暴露，就不能用这个方案。一个变通办法是托管加密后的图片，或者让 Agent 在上传前对敏感图片进行打码处理。

**4. 链接格式必须大小写完全匹配**

GitHub 仓库路径区分大小写，而 jsDelivr 不会自动纠正。自动化脚本拼接 URL 时，一定要保证路径字符串完全一致。建议在脚本中统一转换为小写 slug，或严格遵循约定的命名规范。

**5. 并发和 QPS 限制**

免费套餐有每分钟 100 次请求的软限制，超过会返回 403。对个人工作流完全够用，但如果你的 MCP 工具将在短时间内大量请求同一资源的场景下部署，需要考虑本地缓存或换用其他 CDN。

## 可复用建议

- **建立路径约定**：用 `/<project>/<type>/<timestamp>_<contenthash>.png` 的路径结构，避免重名和缓存混淆。
- **脚本化上传**：写一个简单的 shell 函数或 Node 脚本 `upload-asset`，接收本地路径和目标目录，自动计算 jsDelivr URL 并复制到剪贴板，减少人工拼接。
- **版本标签流程**：对稳定发布的配图打 tag，通过 `@tag` 引用，确保生产环境的历史链接内容一致。
- **灾备兜底**：尽管 jsDelivr 很稳定，但 GitHub 服务偶尔故障。重要图片可以在另一个分支保留一份 raw 链接作为回退，Agent 在生成链接时可同时输出主链接和回退链接。
- **监控成本可控**：用一个简单的 Uptime Monitor 监控仓库内一张测试图片的 CDN 可达性，如果发现大面积不可用可以告警通知。

## 总结

GitHub + jsDelivr 并不是一个能承载高并发生产流量的图床方案，但恰好填补了个人自动化项目和 Agent 插件开发中“我需要一个稳定、免费、可编程引用的图片托管点”这个需求缺口。它零门槛、零成本、完全基于 Git 版本控制，让图片和代码、Prompt 一起被管理，工作流的可追溯性显著提升。

对于 OpenClaw/MCP 社区的开发者来说，这个组合足够轻量，又能被脚本轻松集成，值得作为插件配图、调试截图、知识卡片等轻量资源的默认方案。如果你正在为下一个 MCP 工具选图床，不妨从一行 `cdn.jsdelivr.net/gh/...` 开始。
