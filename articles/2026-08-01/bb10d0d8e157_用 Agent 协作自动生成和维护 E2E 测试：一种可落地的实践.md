# 用 Agent 协作自动生成和维护 E2E 测试：一种可落地的实践

端到端测试（E2E）的编写和维护成本，是每个认真做自动化的团队都会遇到的隐痛。UI 频繁变动，定位器失效，测试脚本逐步腐化，最终沦为 CI 里的摆设。最近几个月，我在内部尝试将 AI Agent 引入 E2E 测试的生成与修复流程，结合 OpenClaw 社区熟悉的 Agent 编排思想和 MCP 浏览器工具，跑通了一条“能用”的路径。本文记录这套实践的背景、具体步骤、踩过的坑以及可复用的设计建议。

## 背景：为什么 E2E 测试特别适合 Agent 介入

AI 写单元测试已经有比较成熟的工具，但 E2E 测试的自动化生成其实更难——它需要理解页面的真实渲染结构、交互时序和业务含义。而 Agent 恰好擅长：观察环境、执行动作、根据反馈调整计划。社区里已经出现了一批通过 MCP（Model Context Protocol）暴露浏览器能力的工具（例如 Playwright MCP Server），让 Agent 可以直接打开网页、点击、输入、截图、读取 DOM，甚至执行 JavaScript。这让“让 AI 替你写测试”从一个 demo 变成可以工程化的命题。

## 要解决的核心问题

不是“一次性生成一堆测试脚本”，而是解决两个更痛苦的问题：
1. **路径盲写**：你手动描述页面流程，AI 凭空写出定位器和操作序列，大规模运行瞬间脆断。
2. **变更感知与自动修复**：前端改了按钮结构，测试挂了，是不是只能手工修补？

因此目标不是生成后就撒手，而是建立一个**感知-生成-验证-修复**的闭环。

## 实践步骤：设计一个双 Agent 协作流水线

我使用了 Playwright + OpenClaw 风格的 Agent 编排，配合 MCP 浏览器服务。整体流程拆成两个 Agent 角色：

### 1. Explorer Agent（探索者）
**职责**：在真实浏览器中遍历页面关键路径，产出结构化的操作记录。

具体做法：
- 通过 MCP 工具打开目标页面，读取可访问性快照（`accessibility snapshot`），拿到元素角色、名称、层级。
- 按照预设的探索策略（比如“先点击所有导航项，再在每个页面中点击主要按钮”）依次执行操作，同时对每次交互截图并记录 DOM 片段。
- **关键**：生成的记录不包含具体 CSS 选择器或 XPath，而是保留“语义描述 + 可访问信息 + 视觉上下文”。例如：`点击导航栏中文字为“订单管理”的链接，页面出现标题“我的订单”`。这一步避免早期绑定脆弱的定位器。

### 2. Scripter & Healer Agent（脚本生成与修复者）
**职责**：
- 读入 Explorer 的操作记录，生成 Playwright 测试脚本。
- 执行脚本，根据结果决定是否触发自我修复。
- 修复失败用例时，重新查看当前页面截图、DOM 差异以及错误日志，尝试更新定位策略。

生成脚本时，Agent 被要求优先使用 `data-testid`，其次是 `role` + `name`，再到文本内容，最后才退化到 CSS 选择器。每一步都加上合理等待与断言。脚本结构强制使用 Page Object 模式，便于未来替换选择器。

对于修复，Agent 会对比失败时的截图与之前成功时的基线截图，尝试通过视觉差异推断哪个元素变了，然后搜索当前 DOM 中语义最接近的元素，更新选择器。这个做法仍然有失败概率，但平均修复率在内部可以接受——大约 70% 的中等复杂度变更能在无人工干涉下自动修复。

## 具体命令与工程配置

假设你已经拥有一个 MCP 浏览器服务（例如 `playwright-mcp-server`）并在 Agent 框架中配置好工具，可以这样发起一次自动测试生成：

```
Agent: 使用浏览器工具打开 https://example.com，探索所有顶部导航链接及其对应页面的 CRUD 操作路径，
将操作记录以 YAML 格式保存到 e2e/records/order-flow.yaml。
完成后，通知 Scripter Agent 基于该记录生成 Playwright 测试文件。
```

生成的测试文件会带上注释，标记出哪些定位器属于“动态推断”，方便 Code Review。CI 中每天跑一次自动修复巡检：收集所有失败的 E2E 用例，连同错误上下文发给 Healer Agent，修复后自动提交 PR。

## 踩过的坑与真实教训

### 1. 定位器退化策略不足
单纯让 AI 自己决定用 text 还是 selector，容易产生“一次性脚本”。必须通过 System Prompt 显式规定优先级，并在生成后做静态规则检查——例如禁止直接使用 `.css-xxxx` 这种编译后哈希类名。我们花了大量时间做 Prompt 对抗。

### 2. 等待策略过于乐观
Agent 生成的 `page.waitForSelector` 往往只等待元素出现，而不考虑元素是否可交互。我们追加了一条规则：对任何点击操作，目标元素必须先通过 `toBeVisible()` 和 `toBeEnabled()` 双重检查，添加了通用重试装饰器。

### 3. 探索策略的盲区
Explorer Agent 没法自动发现需要特定数据才能触发的状态，例如“表单提交后的错误提示”。解决方式是允许人工在探索配置中注入“预设操作上下文”（比如先填入无效邮箱），相当于给 Agent 一个“教学大纲”。

### 4. 截图对比修复的误判
视觉差异算法在遇到页面整体布局微调（如 padding 变化）时会产生大量假阳性。后来我们强制 Agent 只关注失败断言附近的元素区域，并降低差异阈值。

## 可复用的工程建议

- **分层设计测试基类**：让 Agent 生成的脚本依赖稳定的 fixture，例如统一的登录流程和 mock 数据，避免每生成一个文件都要重新处理鉴权。
- **人工审核 gate**：AI 生成的代码必须经过 PR review。我们在文件中加了 `// AUTOGEN_RISK: MEDIUM` 这类标签，提醒 reviewer 关注选择器部分。
- **记录修复模式**：每次 Healer 成功修复后，将“旧选择器→新选择器”的映射写入一个知识库，可以用于未来预测其他用例的同类型变更。
- **不要追求 100% 自动化生成**：当前阶段，Agent 更适合增量生成和针对性修复，而不是从零构建整个测试套件。把人力花在定义探索策略和关键断言上，产出反而更可靠。

## 总结

用 Agent 协作写 E2E 测试，本质上是在建立一个“观察-操作-验证-修复”的闭环，而不是简单地靠提示词生成脚本。这种模式的收益在于降低了因 UI 变动带来的维护负担，同时把测试工程师从重复的选择器修补里解放出来。对 OpenClaw 社区的用户来说，现有 MCP 浏览器工具的组合已经能支撑起可见的工程价值。要做的，是沉住气设计好 Agent 的决策边界，并在失败时提供足够的上下文，而不是幻想一次性生成无懈可击的测试。

接下来我计划把 Explorer 的探索策略从规则驱动迁移到“目标驱动”——例如只告诉 Agent“请验证用户下单全流程”，由它自主决定需要访问哪些页面、做哪些交互。如果你也在做类似尝试，欢迎带着失败的日志和截图来交流，那个比成功演示更有意思。
