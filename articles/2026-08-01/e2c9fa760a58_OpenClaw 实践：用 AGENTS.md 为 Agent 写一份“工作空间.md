## 背景：当 Agent 拥有了“自家后院”，混乱就开始了

OpenClaw 让本地 Agent 能够驱动编辑器、脚本、MCP 服务器和各类插件，在项目目录里自由执行操作。这种能力带来的问题不是“能做什么”，而是“被告知了什么”。一个典型的场景：你让 Agent 跑一下测试，它却误用全局 Jest 而非项目锁定的版本，因为工作区里没有明确说明；或者它写了一段 Python，却忽略了你精心维护的虚拟环境，结果在系统 Python 里装了一堆依赖。

Agent 不是人，看不懂团队约定俗成的 README。它需要一份写给机器的、结构化的上下文声明。这正是 OpenClaw 引入 `AGENTS.md` 的动机：把“工作空间该怎么用”这件事，用 Agent 能稳定理解的方式，告诉它。

## 问题：为什么 `.cursorrules` 或 `CLAUDE.md` 不够用

社区里已经有类似文件（如 Cursor 的 `.cursorrules`、Anthropic 的 `CLAUDE.md`），但它们在 OpenClaw 场景下有两个致命短板：

1. **作用域过窄**：那些文件通常只为单个模型或编辑器定制，不涉及 MCP 工具声明、脚本入口、本地开发服务器的启停方式。OpenClaw 开启多个工具链时，需要更广的上下文。
2. **未能约束工具调用形态**：OpenClaw Agent 可能通过 shell、HTTP、MCP 等多种渠道操作，如果 `AGENTS.md` 不说明哪些命令是安全的、哪些目录不可写，Agent 很容易踩雷。

一个真实踩坑案例：我在项目根目录放了 `AGENTS.md`，只写了 Node 版本和启动命令，没有声明 MCP 工具 `memory` 应该只读。Agent 在执行“归档当前进度”时，直接调用了 `memory.clear()`，把短期上下文全删了。这不是模型的问题，是我没给它画好边界。

## 做法：编写一份“可被 AI 解析”的工作空间使用手册

OpenClaw 的 `AGENTS.md` 放置在项目根目录，Agent 每次进入工作空间都会优先读取。以下是经过三次迭代后沉淀下来的结构骨架，既适合人类维护，也能被模型稳定利用。

### 1. 项目目的与顶层约束
用最精简的语言告诉 Agent：“你是谁”、“这里在做什么”、“绝对不能做什么”。示例：

```markdown
# AGENTS.md

## 项目目的
- 这是一个数据分析工具集，用于处理本地 CSV 并提供可视化。
- 不要修改 `data/raw/` 下的任何文件，它们是只读源数据。
```

### 2. 环境与工具链
明确所有可用的运行时、包管理器、虚拟环境、MCP 服务器，以及它们对应的入口命令。避免 Agent 猜测。

```markdown
## 环境
- Node.js 20（通过 `nvm use` 激活）
- Python 3.11（`.venv` 位于项目根，使用 `source .venv/bin/activate`）
- 包管理器：`pnpm`（锁定版本 8.15）
- MCP 服务器：`/mcp/filesystem`（根路径 `./workspace`，只读）、`/mcp/shell`（限制工作目录为项目根）
```

### 3. 常用任务与正确命令
把高频操作写成“意图-命令”对，告诉 Agent 应该怎样做，而不是让它自由发挥。

```markdown
## 常用任务
- 运行所有测试：`pnpm test`
- 格式化代码：`pnpm lint:fix && pnpm format`
- 启动开发服务器：`pnpm dev`（端口 3000）
- 构建生产文件：`pnpm build`（输出在 `dist/`）
```

### 4. 目录结构与职责
Agent 需要知道往哪里写文件、从哪里读状态。简单画一个逻辑地图：

```markdown
## 目录结构
- `src/`：源码，按功能分模块
- `scripts/`：一次性或批处理脚本，Agent 可以自由写入
- `output/`：Agent 生成产出物（报告、日志）的默认位置
- `data/raw/`：只读源数据
- `.openclaw/`：OpenClaw 内部状态，Agent 不得手动修改
```

### 5. 约束与边界
这是最具工程价值的部分。必须写明禁止操作、资源限制和超时预期。

```markdown
## 约束
- 不得执行 `rm -rf` 或任何递归删除命令
- 写入文件前必须确认目录存在
- 启动服务时等待最多 10 秒，超时视为失败并报错
- MCP 工具 `database.query` 仅限 SELECT，禁止写操作
```

### 6. 同步与更新提示
最后提醒维护者（也提示 Agent）在什么情况下应该更新本文件。

```markdown
## 维护
- 每次添加新的 MCP 工具后，必须更新本文件
- 当 Node/Python 版本升级时，同步修改环境章节
```

## 踩坑点：那些表面遵循、实则无效的声明

1. **路径写错作用域**  
   在 `AGENTS.md` 写 `cd backend && npm test`，但 Agent 当前工作目录可能是项目根，它会把 `cd` 和 `npm test` 分成两条命令执行，导致第二条在错误目录运行。正确做法是给出完整命令：`npm test --prefix backend`。

2. **忘记声明工具超能力**  
   当 MCP 服务器提供 `web_search` 工具时，Agent 会在任何困惑时反复搜索，拖慢速度，还容易搜到过时文档。必须在约束中说明“仅当用户明确要求时才使用 web_search”。

3. **过时的 `AGENTS.md` 比没有更危险**  
   项目结构变更后，如果忘记更新 `AGENTS.md`，Agent 会按照旧路径写文件，结果写到了废弃目录。建议用 CI 检测关键路径是否存在，并在 PR 检查中提醒更新。

## 可复用建议：将“规矩”沉淀为团队资产

- **把 `AGENTS.md` 纳入版本控制，像对待 Makefile 一样严格**。代码评审时，如果新增了脚本或工具，必须同步更新 `AGENTS.md`。
- **使用注释帮助模型理解优先级**。Markdown 的标题层级本身就有结构，但我们会在约束前加上 `⚠️` 或 `IMPORTANT:` 等视觉标记，实测能略微提升 Agent 的遵守率。
- **多仓库场景用“总-分”结构**。在 monorepo 根目录放一个总纲 `AGENTS.md`，各个子包内放入 `.agentcontext` 补充局部规则，OpenClaw 会自动合并读取（需配置 `contextMergeMode`）。
- **定期“演练”**。每半个月让 Agent 从头执行一遍核心命令，观察它是否误触边界。如果触发了不该用的工具，立即修订手册。

## 总结

在 OpenClaw 的体系里，`AGENTS.md` 不是一份文档，而是一条总控规则链的起点。它把“人对项目的理解”翻译成“Agent 可遵守的指令集”。写得好的手册，能让 Agent 像一个安静、准确的初级成员，而不是一个到处乱撞的“实习生”。

工程领域没有银弹。如果你正在为 Agent 的无序行为头疼，不用急着调 prompt，先检查你的工作空间使用手册是不是说清楚了边界。多数时候，Agent 只是在忠实地执行我们未曾言明的混乱罢了。
