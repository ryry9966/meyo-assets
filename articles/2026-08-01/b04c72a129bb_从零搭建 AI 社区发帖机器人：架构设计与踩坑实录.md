# 从零搭建 AI 社区发帖机器人：架构设计与踩坑实录

## 背景
在技术社区中保持活跃的内容输出，对很多开源项目和开发者组织来说既是刚需也是负担。我们团队维护着一个面向 AI 工程师的讨论社区（类似 OpenClaw 生态的使用者圈子），每周需要产出 3-5 篇高质量帖子：更新日志解读、插件推荐、Agent 案例复盘等。这件事纯粹靠人肉维护，很快会沦为没人愿意接的脏活。

于是我们尝试把流程自动化——做一个**可控、可审核、不智障的社区发帖机器人**。它的输入是代码仓库 changelog、社区热点、产品更新公告等信号源，输出是已经排版好、带标签、符合社区调性的帖子，必要时能自动配图并定时发布。

整个方案基于 OpenClaw 的 Agent 编排能力和 MCP 工具链，下面把架构设计、实现步骤和真实踩坑点完整拆开。

## 要解决的问题
1. **内容质量不可控**：直接用 LLM 自由发挥会产出“看起来通顺、实际上全是错”的幻觉帖子。
2. **格式规范难统一**：社区帖有固定的标题层级、代码块风格、标签体系，纯文本生成再人工修改成本很高。
3. **多源信息聚合**：帖子素材分布在 GitHub Release、Discord 讨论、RSS 订阅等多个渠道，需要自动汇总并提取关键信息。
4. **发布调度与安全**：机器人不能把草稿直接发出去，必须有人工确认环节；同时要支持定时发布、失败重试、平台限流处理。

## 架构设计
整体架构分三层：**感知层 → 生成与审核层 → 执行层**，全部通过 OpenClaw 的 Agent 协调 MCP 工具完成。

![Architecture](cover)

- **感知层**  
  使用 MCP 协议接入多个数据源：  
  - `github-mcp`：抓取仓库 Release 和指定 Issue。  
  - `rss-mcp`：订阅技术博客和公告频道。  
  - `discord-mcp`（自研）：读取指定频道的消息摘要。  
  每个 source 被封装成一个 MCP resource，统一由感知 Agent 定时轮询，将原始信息写入本地缓存（SQLite），避免重复处理。

- **生成与审核层**  
  核心是一个具备结构化输出能力的 Agent，调用 LLM 完成三个任务：  
  1. **素材摘要**：把 changelog、聊天记录等长文本压缩成要点列表，并标注来源。  
  2. **帖子起草**：基于社区风格指南（一份 Markdown 模板 + few-shot 示例）生成帖子草稿，强制要求使用特定 front matter 格式（标题、标签、作者、摘要）。  
  3. **事实性校验**：用另一个校验 Prompt 逐条对比草稿中的技术声明和原始素材，标注冲突点。  
  草稿生成后写入一个“待审核队列”，由人类管理员通过内部 Bot 命令 `/publish <id>` 或 `/reject <id>` 进行审批。

- **执行层**  
  审核通过的帖子交给发布 Agent，通过社区平台的 API（基于 `community-api-mcp`）发送。发布前会做最终格式检查（代码块是否闭合、图片链接是否可访问），成功后将帖子 URL 回写至内部数据库，并通知 Discord 审核频道。

整个流程用 OpenClaw 的任务编排能力串联，状态转换用 Redis 做轻量级状态机，防止重复发布。

## 核心踩坑点
### 1. LLM 幻觉导致的“事实性踩雷”
最早版本我们让一个 Prompt 同时完成“摘要 + 生成”，结果 AI 会把推测当成事实写进帖子。例如 changelog 写“提升了性能”，它就编出“延迟降低 40%”的具体数据。  
**解决办法**：强制分离摘要和生成两个步骤。摘要 Agent 要求“只提取原文中明确出现的信息”；生成 Agent 的 Prompt 里显式要求引用来源编号；校验 Agent 用对比模式标红冲突。这相当于给整个 pipeline 加了一道事实性网关，虽然多消耗 token，但错误率从 15% 降到了接近 0。

### 2. 社区平台 API 的反爬与格式适配
发布 API 看起来只是 `POST` 一个 Markdown 正文，实际坑很多：  
- **特殊字符转义**：平台对 `#`、`>`、`-` 的解析远比标准 Markdown 严格，标题如果以 `## ` 开头且后面紧跟中文标点，偶尔解析失败。  
- **图片缓存策略**：外部图片链接可能被平台 CDN 缓存为缩略图，导致代码截图模糊。必须用平台自带图床接口先上传，再引用返回的 `asset_id`。  
- **频率限制**：发布接口限流 10 次/分钟，连续发帖会触发静默丢弃，没有明确错误码。  
**解法**：在 MCP 工具里加了 200ms 的发射间隔和重试逻辑，并对返回的 HTTP body 做特征匹配（如果缺失预期的 `post_id`，则视为失败重试）。

### 3. 定时调度的时间漂移
最早用系统 cron 触发感知 Agent，但多个源抓取时间有重叠，加上审核延迟，经常出现“今晚的帖子明天才发”的错位。  
**改进**：改为 OpenClaw 的 scheduled trigger 配合任务优先级，将“素材抓取”和“生成草稿”定在每日固定时段（如每日 09:00 和 13:00），并设置最晚审核时间窗口（如 17:00 前未审核则自动暂缓），避免过期内容自动发布。

### 4. 长帖被截断与 token 窗口管理
部分 Release Notes 极长（如 Kubernetes 小版本更新），直接塞进 Prompt 会超出上下文。  
**处理**：感知层对文本做分段（按二级标题拆），每段独立生成摘要，再合并；同时 Prompt 中增加截断提示，要求生成 Agent 优先照顾“用户可见的重要变化”。

## 可复用建议
- **把人工审核设计为系统的一部分，而不是补丁**。初期就想好草稿队列、审核指令、修改反写流程，否则机器人一定会变成没人敢用的“自动扰民器”。
- **MCP 工具要返回结构化错误**。不要只返回自然语言错误描述，应包含 `error_code` 和 `retryable` 字段，方便上游 Agent 决策（重试/跳过/告警）。
- **为社区风格建立单独的 Prompt 库**。风格指南不是一两句“语气友好”就够，需要包含大量正反例，最好把已审核通过的帖子作为动态 few-shot 加入 Prompt。
- **监控发布链路每个环节的耗时与失败率**。我们在 Redis 里为每个帖子记录状态变更事件，配合简单的 Web 看板，快速定位是抓取慢、生成超时还是发布被限流。

## 总结
这个机器人在内部跑了两个月，从“玩具”变成每天稳定产出 2~3 篇帖子的半个“编辑”。核心收获不是自动化本身，而是**把人类编辑的审校直觉转换成 Agent 流水线里的可验证步骤**，这正是 Agent 应用能否工程化的分水岭。如果你也在基于 OpenClaw 做内容类自动化，希望这些踩坑记录能让你少走弯路。
