## 背景

在基于 OpenClaw 搭建 Agent、MCP 工具链与自动化工作流时，模型的选择直接决定了系统的响应质量、时延和运行成本。随着本地大模型的成熟，很多团队希望在保持智能程度的同时，把部分计算搬到本地，用 Ollama 等运行时承载 7B~14B 模型处理确定性较高的指令。但在实际工程中，很少有人会完全依赖单一模型——云端 GPT 依旧是最可靠的“兜底推理器”。

因此，“多模型路由”成为刚需：根据任务类型、上下文复杂度、工具调用需求和时延要求，在 GPT 和本地模型之间动态切换。本文总结我们在 OpenClaw 环境下落地这套路由机制的背景、做法、踩坑和可复用经验。

## 问题拆解

核心问题可以拆成三个子问题：

1. **什么时候该用本地模型？**  
   简单问答、格式规整的文本生成、无复杂工具调用的意图识别、预置领域知识的短回答。典型场景：用语料库给用户解释术语、生成固定模板的邮件、判断用户指令属于哪类操作。

2. **什么时候必须用 GPT？**  
   多步推理、需要实时联网搜索的 MCP 调用、复杂 JSON 结构化输出、遵循严格指令格式的 tool-calling，或任务描述本身较模糊、需要模型自主澄清意图的场景。此外，当本地模型出现幻觉、输出格式错误无法修复时，也需要 GPT 作为 fallback。

3. **如何让路由决策不拖慢整体响应？**  
   如果为了选模型又发起一次模型推理，就本末倒置了。最佳实践是用轻量级规则或极低成本的特征分类器在进入主推理前完成分流，但规则必须可观察、可调整。

## 做法与步骤

### 1. 定义模型池和基本指征

在 OpenClaw 的 `config.yaml` 中，配置两个 provider，并标记“属性”以供路由中间件使用：

```yaml
models:
  - id: local_qwen
    provider: ollama
    model: qwen2.5:7b
    tags: [fast, private, structured_light]
    max_tokens: 2048
  - id: gpt4o
    provider: openai
    model: gpt-4o
    tags: [powerful, tool_calling, fallback]
    max_tokens: 4096
```

这里的 `tags` 不是 OpenClaw 原生字段，但可以在自定义 router 中读取，用来做决策。

### 2. 设计路由决策器

OpenClaw 支持在 agent 管线中加入 **router** 插件。我们实现了一个基于规则与轻量文本特征的决策器，逻辑如下：

- **从输入中提取快特征**：字数、是否包含工具调用描述（如“请用工具”、“调用 MCP”等关键词）、是否要求 JSON 输出、历史对话轮次。
- **分级判断**：
  - 字数 < 150 且无工具调用关键词、历史轮次 < 2 → 路由到本地模型。
  - 包含 `"complex_cot"` 标签的任务配置（通常指多步推理）→ 路由到 GPT。
  - 其余情况默认本地模型，但开启 output validator 监控。
- **output validator**：本地模型返回后，校验是否满足预期格式（如必为 JSON 或包含特定字段）。一次校验失败则自动将原上下文重新发送至 GPT，并标记本次路由决策失败。

此处的校验器完全基于规则，不额外调用模型，延迟增加 < 10ms。

### 3. MCP 工具调用的特殊处理

当 agent 绑定 MCP 工具时，本地模型经常无法正确输出 function call 所需要的 schema 结构。我们的做法是：

- 用 prompt 预注入工具描述，并给出 2~3 个 one-shot 示例。
- 在 router 层面，如果检测到当前对话正在持续使用工具（即最近一条 assistant 消息中包含 tool_call），则后续此轮对话锁定使用 GPT，直到工具调用链结束。
- 对于本地模型发出的工具调用，在发包至 MCP server 前增加一次格式修正（正则匹配补齐缺失字段）。效果有限，但能挡住 30% 的低级格式错误。

### 4. 灰度与监控

不能一上来就把所有流量切给本地模型。先在 OpenClaw 的 observability 中间件中记录每次推理的模型 ID、延迟、是否 fallback。上线初期，用权重分配（如 20% 流量走本地模型）观察一段时间，同时对比两类模型的任务成功率。逐步上调本地比例，直到成功率轻微下降为止。

## 踩坑点

- **本地模型输出格式不稳定**：即便给了 JSON 约束（如通过 Ollama 的 `format: json`），本地模型仍可能在最后一个 `}` 后追加自然语言解释，导致解析失败。必须在 validator 中 strip 尾部无效字符。
- **多轮对话上下文割裂**：如果前几轮对话由本地模型回答，突然切换到 GPT，GPT 可能因为对话风格差异而不能利用之前的隐含信息。统一用 ChatML 格式和对齐 system prompt 可以减少此问题。
- **成本计算陷阱**：只看到 GPT 的 token 费用，却忽略本地 GPU 长期占用的电费和折旧。如果请求量不饱和，本地推理的闲置算力也是成本。建议设定本地模型最大并发数，超出则排队或直接使用 GPT（相当于弹性的混合池）。
- **时延变化导致交互体验不一致**：本地模型 50ms 首 token，GPT 可能需要 400ms。用户能感知到“时快时慢”。可以在本地模型回答太快时人为加入少许均衡延迟，但一般没必要，只要不频繁交替就可以。

## 可复用建议

- 从高频低风险任务开始，逐步拓展本地模型承担范围。优先替换那些输出格式固定、逻辑确定的 prompt 节点。
- 构建“共享守护层”：把校验、格式修正、fallback 封装成独立中间件，每个 agent 构建时都可复用，不重复实现。
- 强依赖 MCP 工具调用的场景，尽量让 GPT 主导；仅当工具无复杂参数、返回固定结构时，才尝试用本地模型。
- 每次本地模型升级（如从 7B 换到 14B），要重新遍历路由规则评估成功率和延迟，避免经验性阈值失效。

## 总结

在 OpenClaw 环境下，多模型路由并没有想象中那么“黑盒”。本质上是一个基于规则、可观测、带 fallback 的轻量调度层。把本地模型当作“经济的吞吐层”，GPT 当作“可靠的保障层”，并允许系统在两者之间无缝切换，能让你的 Agent 在成本和智能之间找到实际可行的平衡点。最后，保持监控和迭代习惯，远比一次性设计一个完美路由器更重要。
