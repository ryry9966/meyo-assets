## 背景

团队站会、周报、日报是许多工程师每天要面对的“元工作”。我们自己的场景里，日报需要汇总：

- 昨天的 Git 提交摘要
- 任务看板（Linear/Jira）的状态变更
- 部分系统日志里的关键事件
- 自己记录的工作片段

手动拼凑这些碎片，每天至少 15–20 分钟。更麻烦的是，不同来源的数据结构各异，一周下来经常遗漏上下文。

我们调研了市面上一些“自动周报”工具，要么只能对接单一数据源，要么生成的内容像流水账，缺乏提炼。既然团队已经在用 OpenClaw 做部分自动化，为什么不直接搭一条从原始日志到结构化报告的流水线？

## 问题拆解

核心挑战不是“能不能生成”，而是“生成的能不能用”。具体来说有三个难点：

1. **多源异构数据采集**：Git、任务系统、本地 Markdown 草稿，API 和格式完全不同。
2. **上下文聚合与去噪**：原始数据中存在大量无意义的 commit（如 fix typo）、重复状态变更，直接拼接会让日报变成噪声。
3. **稳定结构化输出**：日报不只是摘要，需要固定的章节（进度、阻塞项、下一步），且格式必须一致，否则阅读成本上升。

## 做法：三条流水线级联

我们没有从一开始就追求全自动。经过几次迭代，最终形成三条可以独立运行的 MCP 工具链，再通过一个调度 Agent 串联。

### 1. 数据采集层（MCP 连接器）

使用 MCP server 分别对接：

- **Git**: 通过 `git log --since="yesterday" --pretty=format:"%h %s %an"` 获取提交记录，过滤掉 merge commit 和带有 `skip-report` tag 的提交。
- **Linear**: 用 Linear 的 GraphQL API 查询 assigned issues 状态变更和评论。封装成 MCP tool `list_linear_updates`。
- **本地草稿**: 读取指定目录下的 `YYYY-MM-DD.md` 文件，作为“人工补充”入口。

> **踩坑点**: Linear API 的分页逻辑在 MCP tool 里容易把 `after` cursor 搞丢，导致重复拉取第一页。后来将 cursor 存入 Agent 的临时状态对象，避免依赖 LLM 记忆。

### 2. 清洗与摘要层（Agent 节点）

采集到的原始数据送入一个专门的“清洗 Agent”，这个 Agent 只做三件事：

- 去重：按消息相似度（Jaccard 距离）合并重复的状态变更。
- 分类：根据规则将 commit 分为 `feature/fix/refactor/chore`，丢弃 `chore` 中无意义的条目。
- 初步摘要：对每个分类生成一句话总结，要求不丢失关键名词（人名、任务号、模块名）。

这里踩过最大的坑是 **LLM 幻觉导致的任务号篡改**。例如 `TASK-123` 被总结成 `TASK-1234`。解决方案：在 prompt 中强制要求引用原 ID 时使用反引号，并在后处理用正则校验所有 ID 是否存在于输入中，不匹配的直接回退为原始文本。

### 3. 报告生成层（模板化输出）

清洗后的摘要喂给“报告 Agent”，使用固定的 Markdown 模板：

```
# 昨日进展 (YYYY-MM-DD)

## 1. 完成任务
{feature_summary}

## 2. 进行中/阻塞项
{in_progress_summary}

## 3. 今日计划
{today_plan}

## 4. 风险与备注
{risks}
```

模板不是用 f-string 硬拼，而是要求模型严格按章节输出 JSON，再由脚本渲染成 Markdown。这样做的好处是，如果某个章节缺失，至少能得到空数组而不是奇怪的占位符。

### 4. 调度与人工回路

整个流水线由一个小型调度器（Python 脚本）触发，每天早上 9:00 跑一次：

1. 调用 MCP 采集数据
2. 调用清洗 Agent
3. 调用报告 Agent
4. 将生成的草稿发送到 Slack 指定 channel，同时 @本人，要求确认或编辑。
5. 确认后自动归档到团队 Notion 数据库。

人工确认这一步目前仍然保留，因为完全自动化在“阻塞项描述”这种需要主观判断的地方还不可靠。

## 踩坑总结

- **Token 成本失控**：原始日志直接塞进 prompt 会爆上下文。初期一天消耗 $2–3。后来强制采集时就做截断（单条消息不超过 200 字符），并让清洗 Agent 只处理摘要，成本降到 $0.3/天。
- **时区问题**：MCP server 运行环境 UTC，Linear API 返回的时间也是 UTC，但日报需要本地时间。最开始漏掉了转换，导致昨天下午的任务被归到今天。统一在采集层转换时区。
- **Slack 格式适配**：Markdown 到 Slack mrkdwn 的转换不是 1:1，特别是表格和代码块。我们用 `slack_sdk` 的 `TextObject` 构建，避免转义问题。

## 可复用建议

1. **MCP 工具设计要“窄”**：每个 tool 只做一件事，参数简单。例如 `get_git_log` 只接受 `since` 和 `until`，不要试图在 tool 内部做过滤，把逻辑留给 Agent 编排。
2. **输出校验优先于 prompt 调优**：对于 ID、日期等结构化字段，用后处理正则验证，比反复调整 prompt 更稳定。
3. **保留“干系人确认”节点**：自动化报告的最后一步应该是通知而非直接发布，避免错误信息扩散。

## 总结

这套流水线在我们团队稳定运行了两个月，每天生成日报的时间从 15 分钟降到 1 分钟（检查确认）。技术栈的核心是 MCP 连接数据源 + Agent 做语义清洗 + 模板化输出，没有引入黑盒大模型产品。如果你已经在用 OpenClaw 搭自动化流程，增加一条日报流水线的成本其实不高，难的是对噪声和数据一致性的持续治理。
