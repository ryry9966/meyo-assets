## 背景

OpenClaw 作为面向插件的自动化 Agent 框架，核心默认依赖 LLM 完成推理与工具调用。不少团队在初期直接用 GPT-4 或 Claude 覆盖所有任务，却很快撞上两个现实问题：一是 API 成本随调用量线性上涨，在批量数据处理、日志分析等场景中显得过于昂贵；二是某些数据不能离开内部环境，合规要求迫使部分推理必须本地完成。同时，本地部署的 7B/13B 模型在代码生成、复杂多步规划等任务上仍与云端大模型有明显差距。

因此，“模型路由”不再只是一个架构话题，而是工程上必须解决的成本-能力分配问题。我们需要一个可控的决策器，在合适的时候把任务交给合适的模型。

## 问题定义

假设你维护一个 OpenClaw Agent，它同时具备：
- 对话式答疑（对用户意图要求高）
- 内部文档摘要（数据敏感，量大）
- 基于 MCP 工具返回的数据做分类与告警（高频，响应要快）

如果所有推理走 GPT-4，单月 token 消费很容易超过预算；但把文档摘要直接交给一个未调优的本地模型，可能出现胡编乱造或格式错乱，下游自动化流程直接崩溃。更棘手的是，有些任务的难度无法提前静态判断——同一个“分析日志”请求，可能只是统计行数，也可能需要关联多个错误栈进行根因推断。

于是，路由的核心变成：**如何在 Agent 内部根据任务特征和执行阶段，动态选择后端模型，并保证 prompt 兼容与回退能力。**

## 做法与步骤

在 OpenClaw 中，Agent 的模型选择可通过自定义 Skill 或中间件层的 “model_profile” 实现。我们的做法不依赖特定版本，通用步骤如下：

**1. 定义模型池**
把所有可用后端抽象为 profile，例：
- `gpt-4o` ：云端复杂推理，长上下文，函数调用强
- `claude-haiku` ：云端快速轻量任务
- `local-llama3-8b` ：本地隐私摘要、分类
- `local-codellama-7b` ：本地代码补全

每个 profile 除了模型名，还要携带标签：`cost_per_1k`、`max_context`、`supports_tools`、`internal_only`。

**2. 注入路由决策器**
在 OpenClaw 的插件钩子 `before_llm_call` 中插入路由逻辑（伪代码）：
```python
def route_model(task: Task) -> str:
    if task.tags.get("sensitive_data"):
        return "local-llama3-8b"
    if task.complexity_score < 0.3 and not task.requires_tools:
        return "claude-haiku"
    # 默认走强模型
    return "gpt-4o"
```
复杂度分数可通过一个轻量级分类器（如基于 BERT 的意图复杂度模型，或规则的句子长度+关键词密度）得到。分类器本身也可以跑在本地 CPU 上，几乎不增加延迟。

**3. 统一消息协议与重试**
本地模型对 system / user 角色分割的遵守不如商业模型。我们在调用本地模型前，通过 `prompt_adapter` 将 system prompt 塞进 user 消息首段，并限制输出格式（要求纯 JSON 或 Markdown 代码块）。同时为本地模型增加输出解析重试：若 JSON 解析失败，自动追加“请仅输出有效 JSON”提示并重试一次。

**4. 利用 MCP 工具返回决定后续路由**
有时路由不是在任务开始前决定，而是在中间步骤。例如 MCP 调用数据库后返回了 2000 行记录，需要进一步摘要。此时可在 Agent 的工具返回处理逻辑里动态切换为本地模型处理摘要，并将结果传回云端模型做最终回答。OpenClaw 的 pipeline 支持在同一个 turn 内切换 `model_profile`，只需在 yield 新的 LLM 调用前修改上下文配置。

## 踩坑点

**本地模型输出格式不稳定**
即使加上了“请输出 JSON”的咒语，部分本地模型仍会在 JSON 外包裹解释文字。解法是：在解析前用正则提取首个 `{` 到最后一个 `}` 的区间，而不是依赖 `json.loads` 直接解析。这减少约 90% 的解析失败。

**上下文窗口被低成本模型截断**
路由到 `claude-haiku` 或本地 4k 模型时，容易忘记裁切上下文。我们踩过很隐蔽的坑：长文档摘要时，系统自动把前一轮的全量日志塞进 prompt，导致本地模型静默截断中间部分，摘要却仍然通顺（只概括了开头和结尾），结果遗漏了中间关键故障。对策是在路由到低上下文模型前，对消息列表做 token 预算检查，超出则触发分段摘要或用云端模型兜底。

**工具调用与本地模型不兼容**
OpenClaw 的 tool calling 往往依赖 function calling API。本地模型虽然也可以通过 prompt 引擎模拟，但可靠性差异巨大。我们的策略很明确：凡是需要工具选择或结构化 action 的请求，绝不分流到本地模型。路由判断中 `requires_tools` 标记会直接锁定云端模型，避免 Agent 执行断层。

**并发请求下的显存争抢**
当多个 Agent 实例同时调用本地模型（比如 10 个文档并行摘要），GPU 显存不够时 ollama 会排队，导致部分请求超时。我们改为单实例消费一个本地模型队列，并且为这类任务设置了更宽松的超时时间（30 秒）。如果超时，再回退到云端轻量模型。

## 可复用建议

- **先统计再路由**：花一周记录生产任务的实际复杂度分布和成功/失败模式，再确定分流阈值，避免拍脑袋。
- **复杂度评分可以用规则起步**：文本长度、是否包含特定关键词（如“总结”“分析原因”“写代码”）、对话轮次，简单加权就能覆盖大部分场景，不必一上来就训模型。
- **本地模型专门准备一张 “回退提示词”**：当检测到本地模型连续两次解析失败或输出空内容，自动切换到后备云端模型，并把前两轮失败上下文清空，防止污染新会话。
- **把成本可视化**：在 OpenClaw 的日志中对每次 LLM 调用打上 `model_used` 和 `token_cost`，通过插件上报到内部看板，帮团队直观感受路由带来的成本变化。
- **内部敏感数据强制本地路由**：可在任务创建时打标签，由中间件保证绝不离开安全域，这在金融和医疗场景中是刚需。

## 总结

多模型路由并不是为了让架构看起来“先进”，而是让推理成本与业务风险对齐的一项工程手段。在 OpenClaw 这类自动化框架里，路由的收益尤其明显：你不必再为一万条日志摘要付 GPT-4 的账单，也不必担心本地小模型搞砸用户面对面的对话。关键是找到一个可解释、可调试的决策边界，并设计好失败时的回退路径。一旦这套管线跑顺，你会发现 Agent 既可以聪明，也可以节俭。
