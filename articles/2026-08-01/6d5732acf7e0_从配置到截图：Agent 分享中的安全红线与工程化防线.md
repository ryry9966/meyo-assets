## 背景：链式自动化放大了信息暴露面

OpenClaw 社区里，越来越多的开发者通过 MCP 插件、Agent 工作流、自动化脚本串联起外部 API 与内部服务。一个典型场景是：调试 MCP server 连接失败，直接把 `mcp.json` 贴到 Discord；或者分享了 n8n 工作流截图，不小心露出了内网地址。Agent 架构天然是多跳、多组件的，数据从环境变量流经工具调用、再输出到频道，任何一环的“分享惯性”都可能让敏感信息越界。

这不是理论风险。过去几个月中，社区频道里至少出现过十余次 API Key 明文、两次内部数据库连接串、以及数次因 Agent 输出未脱敏知识库内容被截图转发的案例。每次事后删除、轮换密钥，都消耗了大量工程信任。与其事后补救，不如把安全红线前置到开发与分享的工作流里。

## 问题拆解：泄露不只是“贴密钥”

Agent 相关的敏感信息泄露有四种高频形态：

1. **配置泄露**：MCP server 配置中的 `env` 字段直接写了生产 Token，或 `.env` 文件被整体复制。  
2. **日志泄露**：调试时将 `console.log` 的完整 HTTP 响应贴出，Authorization 头完整可见。  
3. **Agent 动态输出泄露**：Agent 在回答用户问题时，将内部 Wiki、代码库中未过滤的接口地址原样返回，然后该回复被截图分享到社区。  
4. **截图二次泄露**：以为用画笔涂掉了敏感字段，但 PNG 保留了图层或可通过 OCR 复原。  
5. **工作流元数据泄露**：分享的工作流 JSON 带了内部服务主机名、数据库 Schema 片段等业务上下文。

这些形态的共同特征：泄露者往往具有一定安全意识，但低估了 Agent 链路的复杂度，也没在“分享”这个动作前建立强制性检查点。

## 工程化防护：从编码到分享的四层栅栏

### 第一层：开发期——让秘密不可被粘贴

- **环境变量强制外部化**：MCP server 的 `args` 或 `env` 中只放变量名，真实值通过系统环境变量或 secrets manager 注入。在 OpenClaw 中，可以借助 `$$SECRET` 引用语法避免明文出现在配置文件里。
- **Pre-commit 扫描**：使用 `detect-secrets` 或 `gitleaks` 作为 Git hooks，禁止包含疑似密钥、Token、私网 IP 段的代码进入仓库历史。
- **示例文件隔离**：保留 `.env.example` 或 `mcp.example.json`，所有分享都以此模板为准，真实文件加入 `.gitignore` 并在 IDE 中标记为“谨慎分享”。

### 第二层：调试期——让日志和输出自动闭嘴

- **日志脱敏中间件**：在 Agent 运行时的日志输出层统一拦截。可以写一个简单的中间件替换 `Authorization: Bearer .*` 为 `Bearer <REDACTED>`，同时遮蔽手机号、邮箱等模式。OpenClaw 的插件体系支持在 tool 调用前后挂载此类函数。
- **Agent 输出约束**：系统提示词中明确禁止输出内部主机名、Token、数据库连接串等关键词。如果 Agent 需要引用内部文档，必须经过摘要脱敏层。常见做法是在 RAG 检索后加一道输出过滤器，检测到敏感正则即要求重写。
- **调试开关与分级日志**：开发环境开启详细日志，但推向社区前必须切换到 “sanitized” 模式，甚至提供一条命令一键过滤历史日志文件。

### 第三层：分享前——建立强制检查清单

把分享视为一次“数据出口”，在粘贴或上传前运行检查程序：

- **配置文件清洗**：写一个脚本，遍历项目中的 `*.json`, `*.yaml`, `*.env` 并自动替换已知 value 为 `CHANGE_ME`。社区可共建一份 OpenClaw 项目常用的占位符映射表。
- **截图合规验证**：截图前关闭终端历史、隐藏 Dock 和应用名。使用纯色块遮挡而非马赛克，避免 OCR 还原。完成后可用本地 OCR 工具（如 Tesseract）反向扫描截图，确认无敏感字符串。
- **工作流 JSON 脱敏**：如果导出自动化流程，用 `jq` 或自定义工具删除 `credentials`、`server` 等字段，替换内部 URL 为 `http://internal.service`。
- **“分享专用”分支**：在 Git 里切一个 `share` 分支，运行脱敏脚本后提交，确保原始仓库不受影响。

### 第四层：应急与文化建设

即使再小心，也可能意外泄露。团队应预先约定：

- **轮换流程**：发现泄露的 5 分钟内通知相关服务 owner，立刻轮换密钥，再追溯影响面。
- **社区快速响应**：联系频道管理员删除消息，同时评估是否有被爬取存档，必要时发布安全通告。
- **将事故写入 Postmortem**：不惩罚个人，而是检视工具链和检查点的缺陷，反哺到第一、二层的自动化规则里。

## 踩坑点：容易被忽略的细节

- **MCP 配置中的隐式泄露**：有些 MCP server 的 `description` 字段会被 Agent 当作工具说明读取，如果说明中包含了实例地址，Agent 可能在回答时复述出来。
- **终端回显陷阱**：执行 `curl` 测试时，URL 中的 query 参数携带 token，全选复制时一并被抓取。建议用 `--header` 方式传递认证信息，且利用终端插件自动遮蔽敏感命令。
- **环境变量默认值**：`process.env.API_KEY || 'sk-xxx'` 这种写法，一旦在分享代码时被看到默认值，等同于暴露。禁止在代码中设置真实默认值。
- **多跳 Agent 的上下文溢出**：Agent A 调用 Agent B 时，可能将完整的上下文（包含用户请求和中间结果）传给 B，而 B 的日志若未经脱敏便记录了该上下文，则发生二次泄露。
- **截图文件名和 EXIF**：截屏工具可能包含时间戳、设备名、部分窗口标题，分享前应删除 EXIF 信息，或使用“复制到剪贴板”而非文件的形式传输。

## 可复用建议：让安全成为默认

- **在脚手架里内置安全检查**：OpenClaw 插件生成器可以默认添加 `pre-commit` 配置和脱敏脚本模板，新人初始化项目即具备基础防线。
- **社区共建共享检查工具**：一个轻量的 CLI 工具，比如 `openclaw-sanitize share`，自动扫描工作区，生成脱敏后的共享包并给出合规报告。
- **将红线写进贡献指南**：在社区文档中明确“切勿分享未脱敏的配置/日志/截图”并给出操作范例，让安全规范不再是沉默的期望，而是显性的行为准则。

## 总结

Agent 的安全边界不再止于服务器，而是延伸到每一次截屏、每一段粘贴的配置、每一个被导出的工作流。工程化的做法不是让所有人成为安全专家，而是通过工具和检查点，让“不泄露”变得比“不小心泄露”更容易。当我们把脱敏集成到编码和分享的工作流中，社区互助的效率和安全才能真正兼得。
