# 从日志碎片到团队日报：用 OpenClaw + MCP 搭建一条可复用的数据流水线

**背景**

每天下班前手工整理项目日报是件内耗严重的事。Git 提交散落在多个仓库，Slack 里的讨论穿插着决策与反馈，再加上 Jira 任务的状态变更——信息并不缺，缺的是一条能自动归拢、清洗、提炼成结构化报告的流水线。我们团队一直在用 OpenClaw 搭建内部 Agent，配合 MCP 协议把各种数据源接入同一个上下文，于是尝试把日报生成这件事彻底自动化。

这篇文章会记录一条从原始日志到可发送日报的工程化 pipeline，覆盖数据采集、清洗、结构化输出与定时投递，重点在于可复现的步骤和踩过的坑。

**问题拆解**

自动化日报的难点不是“调用一次大模型”，而是多源异构数据的采集与规整。需要解决的问题包括：

1. 如何统一拉取 Git、Slack、Jira 等不同来源的“原始日志”；
2. 如何按日期窗口裁剪数据，避免信息过载；
3. 如何让 Agent 产出的报告既有结构，又不丢失关键上下文；
4. 如何定时执行并可靠投递。

工具选型上，数据接入用 MCP 服务（github、slack、jira 这类社区 server 即可），调度与编排用 OpenClaw 的 Agent 能力，报告模板用自然语言约束即可，无需额外引入低代码平台。

**做法与步骤**

**1. 配置 MCP 服务，打通数据源**

我们分别为 GitHub、Slack、Jira 启动了 MCP server，并在 OpenClaw 的 Agent 配置里声明了这些能力。这里一定要使用个人令牌或机器人账号，权限控制到最小可用范围，避免泄露敏感数据。

实际操作时，先用 `claw` 命令行测试连接，确保每个 MCP tool 都能正常返回数据，比如：

```
claw mcp github list_commits --repo="my-team/project" --since="2025-01-12T00:00:00Z"
```

这一步踩坑不少：部分 MCP server 的默认参数名与 OpenClaw 预期不一致，需要手动调整映射；Slack 的分页需要处理 `cursor`，如果一次拉取大量消息，容易触发 rate limit，解决办法是在 Agent 侧增加指数退避重试。

**2. 设计数据采集脚本，按日期窗口裁剪**

我们没有让 Agent 直接消费整天的原始数据，而是先在 MCP 调用层做了一次预过滤：只拉取前一个自然日的提交、消息和任务变更。日期范围用 UTC 时间对齐，避免时区混乱导致的遗漏或重复。

采集后的原始数据统一存为 NDJSON 格式，每条记录带来源标签和时间戳。这样做有两个好处：一是后续清洗不依赖实时连接，二是可以保留日志快照便于排障。

**3. Agent 清洗与结构化提炼**

采集到的原始 JSON 体积可能很大，一次性塞给 LLM 会超出上下文窗口。我们对数据做了两级处理：

- 第一级：用 Agent 的 `filter` 能力，按预定义规则丢弃无关事件（如 CI 成功通知、自动构建日志），只保留人工提交、评论、状态更新。规则不必完美，但要稳定。
- 第二级：将筛选后的数据分成若干语义块，分块送入 LLM 做摘要，再在最后一步合成一份完整的日报。

重要的一点：**日报结构必须在 prompt 中显式约束**。我们要求输出包含三个部分：

1. 昨日进度（按项目/模块聚合的关键进展）
2. 风险与阻塞（从讨论和任务中提取的异常信号）
3. 今日计划（基于未完成任务和上下文推断）

这样，日报就不再是“流水账”，而是有信息增益的总结。

**4. 定时调度与投递**

OpenClaw 支持通过内置 cron 触发器定时运行 Agent。我们设定每天早上 8:30 执行，生成的报告通过邮件 MCP 或 Slack webhook 投递到团队频道。

这里遇到过一个隐蔽的问题：如果前一天没有任何事件（如全员休假），Agent 会产生一份空报告或胡乱填充内容。解决方法是在生成阶段增加一个前置检查：若有效事件数为零，则输出预设的“昨日无活动”简短消息，不进入 LLM 提炼流程，既省 token 又避免幻觉。

**踩坑点汇总**

- **时区对齐**：我们坚持一切内部时间戳存 UTC，只在展示层转换。否则查询窗口会有边界偏移，导致数据丢失或重复。
- **Slack 消息上下文**：单条消息往往脱离上下文难以理解。我们在采集时把同一 thread 的消息合并成一个复合事件，显著提高了摘要质量。
- **Token 消耗失控**：早期我们让 Agent 一次性处理所有原始数据，成本高且总结质量不稳定。改成分块摘要+二次合成后，token 用量下降了约 60%，日报反而更准确。
- **Jira 自定义字段**：MCP server 返回的 Jira 数据中包含大量自定义字段，需要提前做好 schema 映射，否则 Agent 无法识别重要信息（例如优先级、关联版本）。

**可复用建议**

1. **先搭数据管线，再做智能总结**：不要一开始就沉浸在 prompt 调优中。数据采集的稳定性和干净程度决定了日报质量的底线。
2. **对 MCP server 做一次轻量封装**：统一处理鉴权、分页、重试，让上层 Agent 只关心业务逻辑。我们抽象了一个 `fetchYesterdayEvents` 的统一接口，隐藏了不同数据源的差异。
3. **日报结构模板化**：定义一份 Markdown 模板，让 Agent 填充具体内容，而不是完全自由生成。这样报告格式一致，也方便下游做自动化分析。
4. **记录运行日志与快照**：每次运行都保留一份原始事件快照和中途摘要，出问题时能回溯是采集错了还是总结错了，而不是盲猜。

**总结**

从原始日志到结构化日报的流水线，核心并不在大模型本身，而在于工程上的拆解：把采集、清洗、分块总结、定时投递做成可组合的步骤。MCP 让多源数据接入变得标准化，OpenClaw 的 Agent 能力则负责串联和调度。整个方案一次搭建后几乎没有维护成本，团队日报从“晚上加班凑字数”变成了“早上自动出现在频道里”。

如果你的团队也有类似的“手工日报”痛点，不妨从最小可用的数据源开始，先跑通一条流水线，再逐步扩展。毕竟，能自动化的重复劳动，就不要再消耗工程创造力了。
