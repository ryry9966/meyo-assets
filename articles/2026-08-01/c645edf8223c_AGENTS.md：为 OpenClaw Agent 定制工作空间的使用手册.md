## 背景：Agent 需要一个“项目说明书”

在 OpenClaw 的日常工作流里，我们通过自然语言给 Agent 下指令，让它调用 MCP 工具、操作文件、执行命令。但每次会话都要重复解释项目结构、环境变量、编码规范、测试流程，不仅低效，还容易因为上下文遗漏导致不可预期的输出。

借鉴 Anthropic 为 Claude Code 设计的 `CLAUDE.md`，OpenClaw 生态也在推动一种类似约定——`AGENTS.md`。它是一份放在仓库根目录的 Markdown 文件，专门写给 AI 看的工作空间使用手册。Agent 启动时会自动读取（或按需注入），从而理解这个项目的“潜规则”和“操作手册”。

简单来说，`AGENTS.md` 就是你和 Agent 之间的静态上下文协议。

## 要解决的工程问题

- **命令幻觉**：Agent 不知道项目的构建工具是 `pnpm` 还是 `yarn`，可能会反复尝试错误命令。
- **环境错配**：没有说明 Node 版本、Python 虚拟环境路径，导致调用失败。
- **MCP 工具滥用**：虽然已经挂载了 MCP 服务器，但 Agent 不了解各个 tool 的使用边界与前置条件。
- **规范不统一**：代码风格、提交信息格式、测试覆盖要求等全靠口头描述，不同会话行为割裂。
- **重复解释成本**：每次新开工作空间或切换任务，都要先“教育”一遍 Agent。

一个结构良好的 `AGENTS.md` 能把这些元信息固化为可维护的指令集，让 Agent 的行为更加确定、可预期。

## 落地步骤：从 0 构建 AGENTS.md

### 1. 确认加载机制
通过官方文档或源码确认 OpenClaw 默认会读取项目根目录的 `AGENTS.md`。如果支持子目录或自定义路径，建议保持简洁，统一使用根目录下的 `AGENTS.md`，并配合 `.openclaw/` 目录存放更多细节（如 MCP 配置、插件清单）。

### 2. 编写最小可用骨架
一个实用的 `AGENTS.md` 不需要长篇大论，聚焦 Agent 真正需要知道的执行上下文。推荐结构：

```markdown
# 项目概览
简述项目做什么，技术栈关键词（如 React + Next.js + Tailwind）。

## 环境
- 使用 Node.js 20 LTS，通过 `nvm use` 切换
- 包管理器：pnpm@9
- 必须安装全局工具：`vercel CLI`
- 启动命令：`pnpm dev`

## 常用命令
- 构建：`pnpm build`
- 测试：`pnpm test`（单元） `pnpm test:e2e`（端到端）
- 格式化：`pnpm format`（Prettier + ESLint）

## 代码规范
- 使用 TypeScript 严格模式，禁止 `any`
- React 组件使用函数式写法，避免 class 组件
- 提交信息遵循 conventional commits

## MCP 工具使用约定
- `fetch` 工具仅用于外网 API 测试，不得调用内网地址
- `shell` 命令执行前先检查是否在 venv/pnpm context 内
```

### 3. 与 MCP 配置联动
如果你的项目使用了自定义 MCP 服务器，在 `AGENTS.md` 中简略说明每个 tool 的用途和参数限制，但不要在本文档里粘贴冗长的 JSON schema。例如：

```markdown
## MCP 工具速查
- `search_docs`: 搜索内部知识库，必须使用英文关键词。
- `trigger_deploy`: 触发部署流水线，环境参数仅允许 `staging` 或 `production`。
```

这样 Agent 在调用前会先行比对约束，降低误操作。

### 4. 渐进式迭代
不要把 `AGENTS.md` 当成一次性文档。每当你发现 Agent 出现规律性错误、或需要反复纠正某个行为时，就把它用简短指令写入该文件。相当于把“调教成本”固化为可共享的团队资产。

## 踩坑记录与排障

### 坑1：过长内容被截断，Agent 视而不见
某些 Agent 实现对系统提示词长度有限制，或者会根据优先级裁剪。如果你的 `AGENTS.md` 写了三千字，后半部分可能根本不会被读取。  
**解决**：控制总篇幅在 500-800 词以内，多用短句、列表，避免大段散文。

### 坑2：指令模糊，Agent 过度解读
例如写“使用合适的工具处理文件”，Agent 可能调用 MCP 的文件编辑工具，也可能直接用 shell 的 `sed`，导致不可复现。  
**解决**：提供具体示例，如“优先使用 `write_file` MCP 工具编辑文件，并在修改前用 `read_file` 读取原内容”。

### 坑3：环境状态信息写死在文档里
你在 `AGENTS.md` 中写了 “当前激活的 Python 虚拟环境是 `./venv/bin/activate`”，但两天后切换到 conda，文档没有同步更新，Agent 依然按照旧指令执行。  
**解决**：动态环境信息不要硬编码，应该由包装脚本或环境变量在会话初期注入；`AGENTS.md` 只负责描述“如何激活环境”的固定模式，而不是当前状态。

### 坑4：忽略版本兼容
OpenClaw 的不同版本对 `AGENTS.md` 的解析方式可能有差异（例如是否支持 Frontmatter、是否允许嵌入变量）。  
**解决**：锁定项目使用的 OpenClaw 版本，并在团队文档中注明兼容性信息。如果升级，必须重新验证 Agent 行为。

## 可复用的工程化建议

1. **模板化**：为新项目提供统一的 `AGENTS.md` 骨架，包含技术栈、命令、规范三个基础模块，团队成员只需填空。
2. **与 .cursorrules / CLAUDE.md 共处**：如果同时使用多种 AI 编程工具，可以通过软链接或脚本从单一源（如 `docs/ai-instructions.md`）生成各自的配置文件，避免信息不同步。
3. **纳入代码评审**：将 `AGENTS.md` 的变更纳入 PR 检查，确保任何工具链、环境、规范的调整都会同步更新 Agent 的“认知”。
4. **分层提供上下文**：除了静态 `AGENTS.md`，建议实现一个“动态上下文”挂载点（如 `openclaw context add` 命令），在会话中临时注入当前分支、构建状态等实时信息，静态手册只负责稳定的知识。
5. **持续观察日志**：定期审计 Agent 会话中出现的“规则违反”和“重复询问”，这些是 `AGENTS.md` 改进的直接反馈。

## 总结

`AGENTS.md` 不只是给 OpenClaw 看的文本，它本质上是 Agent 与工程环境之间的**稳定接口**。当你的队友从人类变成 AI 助手时，用一份结构清晰、持续维护的说明书来对齐彼此预期，远比在每次 Prompt 里多写几行“记住用 pnpm 别用 yarn”要可靠得多。

投入半小时写好第一版，然后像维护代码一样维护它——这是低成本提升 Agent 工程可靠性的务实实践。
