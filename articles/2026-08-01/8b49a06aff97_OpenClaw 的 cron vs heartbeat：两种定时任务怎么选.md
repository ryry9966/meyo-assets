定时任务是对抗状态遗忘最朴素的手段。OpenClaw 同时提供了 `cron` 和 `heartbeat` 两种触发器，但在实际工程里，很多人会混用，或者根本分不清它们的行为差异。这篇文章把它们的适用边界、踩坑点和组合方式说清楚，希望能帮你少写一些事后补救的补丁。

## 背景：为什么需要两种定时

在插件 / Agent / MCP 的实践里，定时任务通常承担三类职责：

- 周期性数据采集：比如每 5 分钟抓一次 Prometheus 指标、每小时同步一次 Git 仓库。
- 周期性自检与修复：比如检查某条长连接是否活着，不活着就重新建立。
- 带状态的轮询：比如每隔 30 秒触发一次推理步骤，执行完后才进入下一个周期。

`cron` 是基于绝对时间的触发，`heartbeat` 是基于相对间隔的触发。它们的差异会直接反映在时区处理、冷启动行为、任务耗时影响、以及跑批与实时系统的协同上。

## 核心差异拆解

### 1. cron：我们在墙上时钟的哪个位置

`cron` 的写法与 Unix cron 基本一致：

```yaml
triggers:
  - type: cron
    schedule: "*/5 * * * *"
    task: sync_metrics
```

它的判断逻辑是：“当前时间是否匹配这个表达式”。这就意味着：

- 任务触发时间固定对齐到分钟级，无论上次执行是否完成。
- 如果 OpenClaw 进程重启，`cron` 会立刻评估一次当前时间是否命中。命中则立即执行，**不管你刚才是不是已经跑过**。这在一些幂等任务上没问题，但在非幂等任务上可能导致重复扣款、重复发消息等事故。
- 服务穿越夏令时或时区配置变更时，`cron` 可能会“提前”或“延后”一小时触发，这取决于你是否在容器 / 运行环境中固定了 TZ。

一个不那么显而易见的纠正手段：给 `cron` 任务加上执行锁（例如文件锁或数据库主键去重），或者与 `startup_delay` 配合，避免重启风暴。OpenClaw 虽然没有原生锁机制，但可以在任务执行的 handler 里自行实现。

### 2. heartbeat：距离上次执行过了多久

`heartbeat` 的定义更简单：

```yaml
triggers:
  - type: heartbeat
    interval: 30s
    task: health_check
```

它的逻辑是：从上次执行**结束**开始计时，等待 `interval` 时间后再次触发。带来的行为特征包括：

- 如果一次执行耗时过长，下一次就会被“推迟”，不会叠罗汉。这对于下游保护是好习惯。
- 冷启动后**不会立刻执行**，而是先等待一个完整的 `interval`，除非你显式配置了 `immediate: true`。这是很多人反馈“为什么重启后要等半分钟才开始干活”的根源。
- 不受墙上时钟影响，部署到不同时区的节点行为一致，这对跨地域集群非常友好。

但 `heartbeat` 自身无法表达“必须在每天凌晨 3 点”这类人类可读的时间语义。如果你需要日切批处理，还得靠 `cron`。

## 怎么选？一个工程决策框架

我通常用三个问题来决定：

1. **任务是否依赖墙上时间？** 是 → `cron`；否 → `heartbeat` 优先。
2. **任务耗时与间隔是否可能冲突？** 如果间隔很短（比如 5 秒），而且任务可能跑 3 秒以上，`cron` 会导致并发堆积，`heartbeat` 是更安全的选择。
3. **重启后需要补跑吗？** 需要立刻补一次 → `cron`；不需要，宁可等待一个完整周期避免雪崩 → `heartbeat`。

实际部署里，多数高频巡检（比如检查 Agent 心跳、MCP 服务存活性）都会落在 `heartbeat` 上；而数据同步、报表生成、缓存定期重建这些有自然时间边界的任务，仍然回归 `cron`。

## 常见踩坑点

**坑 1：cron 表达式的时区陷阱**
OpenClaw 默认使用 UTC。如果你在 `schedule: "0 3 * * *"` 注释里写“每天凌晨 3 点执行”，在中国区会变成上午 11 点。必须在容器环境变量里显式设置 `TZ=Asia/Shanghai`，或者在运行时注入。

**坑 2：heartbeat 不加 `immediate` 导致冷启动空窗**
对于需要“进程一起来就开始干活”的探活类任务，忘记设置 `immediate: true` 会导致服务虽然起来了，但第一个检查周期内处于盲区。尤其是配合 readiness probe 时，很可能 pod 已经是 ready，但动作 30 秒后才执行。

**坑 3：cron 的并发重叠**
如果任务平均耗时 70 秒，而 cron 表达式是 `* * * * *`（每分钟），那么第二分钟到来时第一个任务还没结束，会导致同一任务并发执行。除非你明确需要这种并行，否则应该在 handler 入口处加互斥。`heartbeat` 天然避免了这个问题。

**坑 4：混合触发引起二义性**
有人会给同一个任务同时加 `cron` 和 `heartbeat`，企图“又定时又保底”。结果在某个时刻两种触发器同时命中，造成双倍执行。如果确实需要双重保障，应该由 handler 内部做幂等去重，而不是依赖触发层。

## 一个可复用的组合模式

在我的实践里，对于需要周期采集且不容忍数据空洞的场景，会使用“cron 为主、heartbeat 为兜底”的模式：

```yaml
tasks:
  collect_metrics:
    triggers:
      - type: cron
        schedule: "*/10 * * * *"
      - type: heartbeat
        interval: 15s
        immediate: false
```

处理逻辑里维护一个简单的状态：检查上次采集的时间戳，如果距离当前时间小于一个阈值（比如 5 秒），就跳过本次执行。这样保证了即使某些周期因进程重启或短暂故障而错过，也能在短时间内被 heartbeat 补齐，且不会重复。

## 总结

`cron` 回答的是“什么时候”，`heartbeat` 回答的是“过了多久”。这句话听起来简单，但背后隐含了对时区、重启、任务耗时、并发策略的不同假设。避免事故的办法不是记口诀，而是在每次定义触发器时，手写出你期望的时序图，然后对比文档验证是哪种语义。OpenClaw 把两种触发器都暴露出来，正是为了适配不同工程场景，而不是让你随便选一个差不多的就行。

在你的场景里，选错一次，往往比一开始没选正确更难排错。
