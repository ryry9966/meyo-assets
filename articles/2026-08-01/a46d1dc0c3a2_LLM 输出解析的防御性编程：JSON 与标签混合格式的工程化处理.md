## 背景

在基于 LLM 的自动化工作流中，我们常常要求模型输出结构化数据——最常见的就是 JSON。但实际运行中，模型的输出往往不会那么“干净”：

- 输出被包裹在 Markdown 代码块中，如 ` ```json { ... } ``` `；
- 要求输出 JSON，却返回了 `<output>{ ... }</output>` 这类自定义标签；
- 更极端的情况：输出的 JSON 前后既有代码块标记，又有自定义标签，甚至内嵌注释、多余空格或截断。

OpenClaw 这类面向 Agent 与 MCP 插件的框架里，解析 LLM 输出是连接智能与工程的“最后一公里”。如果解析环节脆弱，再精巧的提示词也会在边界条件下让自动化链路崩溃。本文整理了一套防御性编程策略，帮助你在工程实践中可靠地提取有效 JSON，同时兼容标签与混合格式。

## 问题分析

典型的“脏”输出可以归纳为以下几种模式：

1. **纯 JSON，但有格式噪音**  
   前后有换行、空格、BOM 头，或者 JSON 中包含 `undefined`、`NaN` 等非标准值。

2. **Markdown 代码块包裹**  
   ```text
   ```json
   {"result": "ok"}
   ```
   ```

3. **自定义 XML/标签包裹**  
   ```text
   <response>{"data": [1,2,3]}</response>
   ```

4. **混合嵌套**  
   ```text
   ```xml
   <output>
   {"key": "value"}
   </output>
   ```
   ```

5. **截断或拼接异常**  
   输出在生成过程中被截断，JSON 不完整；或者多段输出意外拼接在一起。

若用单一的正则或 `json.loads()` 直接解析，这些情况会直接抛出异常，需要人工介入。防御性编程的目标是：尽可能多地自动恢复有效数据，同时在不可恢复时给出明确的错误信息，方便上层重试或降级。

## 做法与步骤

### 1. 构建解析策略链

不要试图用一个大正则解决所有问题。推荐采用**责任链**模式，按优先级依次尝试不同的解析器：

```python
parsers = [
    parse_pure_json,
    parse_markdown_fenced_json,
    parse_tag_wrapped_json,
    parse_fallback_regex,
]
```

每个解析器接受原始字符串，返回 `(success, data_or_error)`。一旦某个解析器返回成功，就终止链条。

### 2. 实现各层解析器

**纯净 JSON + 格式清理**  
标准库 `json.loads` 对格式十分敏感。先做一次预处理：

- 去除零宽字符、BOM；
- 替换可能出现的 `NaN`、`Infinity`、`undefined` 为 `null`（需谨慎，可能丢失业务语义，建议日志告警）；
- 尝试用 `ast.literal_eval` 兜底（仅适用于非标准 Python dict 字面量）。

```python
def parse_pure_json(text: str):
    text = text.strip()
    for bom in ['\ufeff', '\ufffe']:
        text = text.lstrip(bom)
    text = re.sub(r'\bNaN\b|undefined\b', 'null', text)
    try:
        return True, json.loads(text)
    except (json.JSONDecodeError, ValueError):
        return False, None
```

**Markdown 代码块剥离**  
模型习惯输出带语言标识的代码块。可以用正则提取代码块内容：

```python
FENCE_PATTERN = re.compile(
    r'```(?:json|javascript)?\s*\n(.*?)\n```', re.DOTALL
)
```

注意 `re.DOTALL` 是为了跨行匹配。如果文本中存在多个代码块，可以只取最后一个或最长的，具体取决于业务场景。提取后再交给 `parse_pure_json` 处理。

**标签包裹处理**  
常见标签如 `<output>`、`<response>`、`<json>` 等。可以按以下步骤处理：

1. 用正则提取最外层标签内的内容：  
   `re.search(r'<\w+>\s*(.*?)\s*</\w+>', text, re.DOTALL)`
2. 将提取到的内容递归送入解析链，因为标签内部可能还有代码块或纯 JSON。
3. 如果标签嵌套多层（比如 `<outer><inner>JSON</inner></outer>`），可以用栈结构或多次剥离，直到没有标签为止。

**截断 JSON 的修复（尽力而为）**  
当所有正常解析都失败，可以尝试“最大公共子串”思路：找到最后一个 `}` 或 `]` 的位置，截断到此处再解析。但要小心，这种修复可能产生错误数据，所以解析成功后最好做 schema 校验，校验不通过仍视为失败。

### 3. 加入 schema 校验层

不管数据是从哪个解析器出来的，都必须经过业务定义的 schema 校验（例如用 `pydantic` 或 `JSON Schema`）。这一步可以过滤掉“看起来合法但结构错误”的结果，比如字段缺失、类型不符等。校验失败时，可以触发重试流程，或将原始输出与错误信息一并记录，供后续分析。

### 4. 与 OpenClaw 工作流集成

建议将上述解析器封装成一个独立工具函数，注册为 OpenClaw 的插件或工具。在 Agent 的 `response_parser` 钩子中调用。配置文件里支持选择策略模式（严格/宽松）、fallback 最大尝试次数。

## 踩坑点

1. **标签同名导致贪婪匹配**  
   `<output>...<output>inner</output>...</output>` 这种非正规嵌套（实际上标签名相同）会使简单的正则 `<\w+>` 匹配到错误的闭合标签。解决方案：使用栈式手动解析，或限制场景不允许重名标签。

2. **JSON 内部包含 `</tag>` 字符串**  
   例如输出内容是一段 HTML 代码的字符串。此时正则提取标签内容会提前截断。需要通过分析引号上下文来避免，但实现成本高。工程中我们加了一个限制：如果输出被要求为 JSON，内容中不应包含裸 XML 标签；若可能存在，则需要先转义。

3. **性能与可维护性**  
   责任链中的每个解析器都有开销。但 LLM 场景下单次解析耗时远小于模型调用，性能不是瓶颈。重点在于解析器要写单测，把收集到的真实异常输出作为 regression 用例。

## 可复用建议

- **优先设计清晰的输出格式**：提示词中明确要求“仅返回有效 JSON，不要使用代码块或标签”，能避免 80% 的脏数据。防御性编程是兜底，不是替代提示词优化。
- **封装成库**：将解析链、预处理、schema 校验打包成一个 `LLMJSONParser` 类，支持自定义扩展解析器。
- **日志与可观测性**：记录解析失败的原始输出、所处环节、失败原因，便于持续打磨解析规则。
- **与重试机制联动**：当解析失败且错误类型为“格式错误”（非业务数据错误），可以触发 LLM 重试，并带上更严格的格式指令。

## 总结

LLM 输出解析的鲁棒性，本质上是在处理“非结构化文本中提取结构化信息”这一经典问题。没有银弹，但通过责任链模式、多层后处理与严格校验，我们可以在工程上达到可接受的可靠度。在 OpenClaw 这类自动化 Agent 系统中，这套方法能显著降低流程中断率，让 Agent 更稳定地运行长链路任务。

防御性编程不是过度工程，而是对“模型不确定性”的必要保护。希望本文的思路和代码片段能帮你在实际项目中少踩一点坑。
