## 背景

维护一个活跃的开发者社区往往意味着每天都要有新鲜内容。人工找选题、写摘要、排版发布，既耗费精力又难保持频率。更理想的方式是利用 AI 把“筛选内容 → 撰写摘要 → 安全审核 → 发帖”这条链路自动化。但早期用定时脚本加 LLM 直接输出的方案问题很多：大模型容易产生“AI 味”文案、容易踩社区红线，而且当内容来源变多（RSS、API、网页）时，脚本越来越像意大利面条。

后来我们把整个流程迁移到 [OpenClaw](https://github.com/openclaw/openclaw) 这个 Agent 框架上，重新设计成一套可观测、可干预、可扩展的工程管线。目前机器人已在内部社区稳定运行超过 40 天，日更帖子基本不需要人工介入。以下是架构设计和过程中真正踩过的坑。

## 问题拆解

发帖机器人表面看就是“取内容 → 写帖子 → 发布”，工程里却要解决四个具体问题：

1. **多内容源统一**：热点来自 RSS、Hacker News、特定博客 API，还可能手动补充链接；
2. **内容质量与合规**：大模型撰写的摘要可能夸大其词、夹带外链，或是无意中违反社区规则；
3. **发布稳定性**：部分社区没有开放 API，只能模拟 Web 操作，登录态和限流是老大难；
4. **可回滚与可观测**：AI 发帖必须保留每一步日志，以便快速下线问题内容并溯源。

## 架构设计

基于 OpenClaw 的 Agent + MCP 工具模式，将整条链路拆成 6 个步骤，每个步骤都是独立工具，既可被 Agent 自动编排，也能在沙箱中手工触发。

```
[定时触发] → get_feeds → filter_and_select → generate_post → safety_check → publish_post
```

**工具说明**：

- `get_feeds`：通过 MCP 服务器拉取多个内容源，返回标准化文章列表。比如 `rss-reader-mcp` 拉 RSS，`hackernews-mcp` 爬热门，`web-fetch-mcp` 抓指定 URL。
- `filter_and_select`：让 Agent 根据预设的社区偏好（技术深度、话题热度、是否已有相似内容）选出 1-2 篇候选，并给出理由。这一步实际依赖大模型对文章摘要的语义理解，效果比基于关键词的过滤好得多。
- `generate_post`：根据选中文章生成帖子正文和标题。Prompt 里注入社区历史高分帖作为 few-shot 示例，并要求输出观点而不只是总结。
- `safety_check`：独立安全工具，不依赖 Agent 判断。内部组合了规则引擎（禁止外链黑名单、敏感词）和 LLM 辅助审核（检测引流、夸大、引战倾向），返回 `pass/review/reject`。
- `publish_post`：针对不同社区封装发帖逻辑。有 API 的平台直接用 HTTP 请求，无 API 的平台则通过 `playwright-mcp` 模拟浏览器操作。

所有工具的输出均被 OpenClaw 记录到会话中，方便回放和复盘。Agent 配置了最大重试和人工中断条件，例如 `safety_check` 返回 `review` 时，会自动暂停并通知人工审核。

## 踩坑实录

### 1. “AI 味”太重，被社区群嘲
最初直接让大模型生成摘要和标题，结果行文充满“值得一读”“不容错过”这类营销感，用户一眼看出是机器。后来从社区历史帖子中提取了 10 篇高赞内容作为 few-shot，明确要求输出带个人观点、口语化、可以使用 emoji 但不过度。生成质量立竿见影。

### 2. MCP Server 稳定性不足
自建的网页抓取 MCP 在目标网站改版时频繁失败。我们为每个内容源配置了至少一个备选渠道（如 RSS 源降级），并在 `get_feeds` 工具中加入超时和错误捕获，单个源失败不影响整体。所有失败条目会被写入日志 Topic，由另一个定时任务分析是否需要修复。

### 3. Web 发帖的登录态和限流
对无 API 的社区，Playwright 模拟发帖时最常见问题是会话过期。我们的方案是使用 Playwright 的持久化上下文，并每 3 小时执行一次“健康检查”访问首页以维持 Cookie。另外，社区一般有发帖频率限制，我们实现了退避算法，并在遇到验证码时立即暂停流程，通知人工处理。

### 4. 安全审核不够智能
最初只靠规则引擎拦截敏感词，结果机器人发了一篇内容正常但标题刻意引战的帖子。后来把 `safety_check` 改成“规则引擎 + LLM 二道防线”，LLM 会从“煽动性、合规性、价值观”三个维度打分，阈值可调。高风险内容自动转人工队列，不再直接发布。

## 可复用建议

- **工具即契约**：把所有外部依赖（内容源、社区平台、审核接口）封装成标准 MCP 工具，Agent 只负责决策，不要让它直接处理网络细节。
- **审核层必须独立**：不要用同一个 Agent 既生成内容又判断安全，审核工具要粗暴、要可调控，最好支持人工介入。
- **可观测性是底线**：每步工具的输入输出、Agent 决策理由最好全量记录，否则出了问题你无从查起。
- **灰度与回滚**：先在影子社区或小号上跑全流程，设成功率阈值，低于阈值自动切断计划任务；每次发帖成功后也保留草稿，以便快速编辑或下架。

## 总结

用 Agent 框架搭建社区发帖机器人的本质，是用工程化手段管住大模型的不确定性。OpenClaw 提供的工具编排和 MCP 原生支持，让我们把注意力集中在“内容质量”和“稳定运行”上，而不是反复和脚本、Cookie 作斗争。

目前这套机器人每日稳定输出 1-2 篇原创性较强的社区帖子，人工干预率低于 5%。感兴趣的可以关注 OpenClaw 的 MCP 生态，把发帖能力扩展到你自己的社区平台。
