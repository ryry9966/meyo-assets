## 背景：为什么需要“稽客”

在 OpenClaw 这类 Agent 编排系统中，实时信息获取几乎离不开网页采集。无论你是让 Agent 分析竞品价格、抓取文档更新，还是为 RAG 管道补给最新数据，一条稳定的 Web Scraping 管线都是基础设施。但绝大多数 Agent 默认不具备“边界感”——它们不知道什么能抓、什么时候该停、以什么身份出现。没有稽核的采集行为，轻则 IP 被封、重则踩中法律红线，甚至把脏数据喂进后续推理链路，造成决策错误。

“稽客”（Audit Scraper）本质上就是一个轻量级的安全代理层，专门负责审核、记录并控制 Agent 发起的每一个网页请求。它不改变原有抓取逻辑，而是在上游插入一层可观测、可干预的治理点。

## 问题：失控的采集会带来什么

实际工程中，不经管控的 Web Scraping 常常暴露以下几类典型故障：

- **协议违规**：直接忽略 `robots.txt`，或高频请求导致服务降级，触发反爬。
- **身份泄露**：Agent 带着默认 User‑Agent、固定 IP 去爬，被目标站点瞬间识别并封禁。
- **范围越界**：Agent 顺着链接爬到不该碰的页面（用户数据、后台接口、内部文档）。
- **缺乏审计**：出了问题无法回溯是哪个 Agent 调用了哪个 URL，只能靠猜。
- **数据污染**：被反爬机制返回的虚假内容直接进入知识库，污染后续输出。

这些问题用“事后加规则”是补不完的，必须在出站流量必经路径上建立强制稽核。

## 做法：以 MCP 工具为锚点构建稽核层

在 OpenClaw 生态中，Agent 通常通过 MCP 工具访问外部能力。我们在实现一个网页抓取工具时，可以把稽核直接做成该工具的一个无状态中间件。

**1. 定义策略配置（policy.yaml）**
将可允许的域名、抓取频率、禁用路径、需要走无头浏览器的动态站点等用声明式配置管理。示例：

```yaml
policies:
  - domain: "docs.example.com"
    respect_robots: true
    max_rps: 2
    allowed_paths: ["/api/v2/docs"]
  - domain: "*"
    respect_robots: true
    max_rps: 0.5
    default: true
```

**2. 构建稽核中间件**
所有 Agent 发起的 `fetch_url` 调用都会经过一个 `AuditMiddleware`，依次完成：

- **域名白名单校验**：匹配 policy，若无匹配则按默认策略或直接拒绝。
- **robots.txt 缓存检查**：用 TTL 缓存目标站点的 robots 规则，对不允许的路径返回拒绝，附带原因。
- **限速令牌桶**：以域名粒度控制每秒并发请求数，超过限制则排队或返回 429 到 Agent。
- **请求头消毒**：统一注入轮换的 User‑Agent 和 Accept‑Language，移除 Agent 可能携带的原始标识。

**3. 集成到 MCP 工具**
将上述中间件封装成一个 MCP Server，提供 `scrape_with_policy` 工具。Agent 调用该工具时，必须传入目标 URL 和预期用途标签（如 `"doc_indexing"`），工具内部完成稽核、实际下载、内容清洗，并返回带元数据的结果（成功/失败原因、HTTP 状态码、耗时、缓存命中情况等）。

**4. 审计日志与告警**
每一次抓取请求都输出结构化日志，包含 `agent_id`、`trace_id`、`url`、`action`（allowed/blocked/throttled）、`status_code`、`duration_ms`。当拒绝率或超时率在滑动窗口内异常升高时，通过 Webhook 通知运维或自动降低对应 Agent 的并发度。

## 踩坑点：这些细节会决定成败

- **robots.txt 的解析与缓存**：不要每次请求都实时抓取 robots.txt，可设置 10 分钟缓存。但要注意某些 CDN 或 WAF 会对非标 Headers 返回错误 robots 内容，解析失败时必须退避到保守策略（只允许 GET 根路径）。
- **动态渲染的隐形成本**：一旦配置中打开了 headless 浏览器，CPU/内存消耗会数倍增长。为这类请求设置独立的资源池，并强制超时时间（如 15 秒），防止一个慢页面拖垮整个 Agent 推理。
- **法律边界不止 robots.txt**：即使 robots.txt 允许，部分网站 ToS 明确禁止自动化采集。稽核层无法自动识别法律风险，建议将敏感用途（如竞争对手分析）标注为人工审核后启用。
- **不要奢求绕过所有反爬**：稽核的目标是让采集行为正当化，而不是提供傻瓜式反爬破解。当你发现目标站点启用了严格的验证码，正确的做法是标记该任务降级，而不是在稽核层强行接码。

## 可复用建议

- **无状态中间件设计**：稽核层最好只依赖配置和本地缓存，不要求数据库，这样可轻松横向扩展或嵌入不同 Agent 进程。
- **开放策略插件接口**：除了域名白名单和限速，你可能还需要关键词过滤、内容尺寸限制、PII 脱敏等。预留一个 `AuditPlugin` 接口，让后续按需挂载。
- **与 OpenClaw 的 trace 打通**：在 audit log 中带上 OpenClaw 的 `conversation_id` 或 `workflow_run_id`，让抓取结果可在整个对话链路中被回溯。
- **灰度上线**：先在测试环境用低风险站点验证稽核逻辑，然后逐步引入内部知识库抓取任务，最后再开放给面向外网的 Agent。

## 总结

给 Agent 加上 Web Scraping 稽核，不是在限制它的能力，而是在为它建立可信的安全边界。配置驱动、中间件化的轻量稽核层可以让每一次网页访问都变得可审计、可控制、可优化，同时也大幅降低了运维反爬熔断的被动压力。当你把“能不能抓”从 Agent 的决策链中移出，交给专门的稽客来处理时，剩下的事情反而变得简单了。
