# 构建上下文感知的 Agent 权限边界：何时自主，何时停下询问

## 背景

在基于 OpenClaw、MCP 与自定义插件搭建的自动化 Agent 中，我们不断给 Agent 接入更多能力：文件系统读写、数据库操作、远程 API 调用，甚至通过 Shell 工具执行系统命令。Agent 从“只能回消息”的对话机器人，逐渐变成能真正干活的数字助手。

但能力扩展的同时，一个老问题会反复出现：**哪些操作 Agent 可以自己决定执行，哪些必须经过人类确认？**

如果权限放得太宽，一句提示词的偏差就可能触发不可逆的副作用；如果每步都要求确认，Agent 的自动化价值会被频繁打断所稀释，用户也会陷入“批准疲劳”。我们需要一个工程上可落地、可演进的权限边界设计，而非硬编码的 if-else。

## 问题本质

这不是一个“要不要权限控制”的二元选择，而是一个**细粒度的自主权分配问题**。我们需要在工具调用层面，根据操作的风险等级、当前任务上下文、用户的即时与历史决策，动态决定允许、询问或拒绝。

在 MCP 体系中，工具本身仅描述能做什么，不携带风险语义；Plugins 通常也只是暴露能力，没有内建权限策略。所以边界必须由 Agent 的运行时框架或中间件来定义和实施。

## 工程实践：三层分级 + 上下文感知

### 1. 操作风险分级

不要试图对每个工具一刀切。先对所有工具调用做静态风险分级，例如：

- **低风险（可自动执行）**：读取当前工作目录下的文件列表、查询只读数据库、非敏感信息的 API GET 请求等。这类操作不会改变状态，或影响范围严格受限。
- **中风险（需上下文判断或一次性确认）**：写入临时文件、创建日志、在隔离沙箱内执行命令、发送消息到频道等。这类操作可能产生副作用，但易于回滚或影响面小。
- **高风险（必须人类明确批准）**：删除文件或记录、修改线上配置、执行不受限的系统命令、调用付费 API、操作敏感数据等。这类操作一旦执行，很难或无法撤销。

分级规则应明确记录在配置中，且支持被项目覆盖。例如，你可以维护一个 `tool_risk.yaml`，定义每个 MCP 工具名和参数的默认风险等级。

### 2. 上下文感知的动态决策

静态分级还不够。同一个操作，在不同上下文中风险感知完全不同。比如，Agent 在用户刚刚说“帮我把临时文件都删掉”的对话上下文中，执行 `delete_tmp_files` 应该比突然自行删除要更可被接受。

引入几个关键上下文信号：

- **用户意图匹配度**：当前操作是否在最近几轮对话中被用户明确要求或隐含授权？
- **操作参数的敏感性**：是否涉及系统目录、特定表名、外部域名？
- **历史决策**：用户是否在最近针对类似操作选择了“始终允许”？
- **环境标识**：当前运行环境是开发、预发还是生产？生产环境应默认收紧。

可以将这些信号组合成一个简单的决策函数，输出“自动执行 / 询问确认 / 拒绝并解释”。决策逻辑需要可解释——当 Agent 选择询问时，能够在 UI 中清晰说明哪项风险因素触发了中断，这能显著减少盲目批准。

### 3. 人类介入界面的设计

权限边界的生效需要人机交互界面的配合。审批提示不应只是“是否继续？[是/否]”，而应包含：

- 将要执行的具体动作和参数；
- 风险等级及原因；
- 影响范围说明（哪个文件、哪个数据库、哪个环境）；
- 选项：“仅本次允许”、“本次会话内类似操作自动允许”、“拒绝”。

此外，提供“撤销信任”的入口，让用户可以随时检查和管理已授权的自动执行规则，避免权限滥用。

## 踩坑实录

1. **把“询问”变成了“骚扰”**  
   如果每写一个临时文件都弹窗确认，用户会在第三次后直接点“始终允许”，权限控制形同虚设。一定要把真正的低风险操作自动放行，把“询问”留给那些有副作用的操作，而不是所有写操作。

2. **忽视参数的动态风险**  
   很多团队只按工具类型设权限，例如“允许执行命令”就是允许一切。实际上 `run("ls")` 和 `run("rm -rf /")` 风险天差地别。需要对参数内容做匹配，至少用简单的模式检查（如命令白名单、目录限制）。

3. **持久化信任缺乏过期与审计**  
   用户授权“此类型操作一直允许”后，该规则可能永久生效。一旦环境变化（如从开发切到生产），或用户早已忘记授权，就可能产生安全隐患。建议给信任规则加上时效性和环境作用域，并记录完整的审批日志以供回溯。

## 可复用建议

- **实现一个统一的权限中间件**：拦截所有工具调用，统一经历“风险标注 → 上下文评估 → 决策执行”流水线，而不是在每个 Agent 逻辑里散布 if-else。
- **将风险矩阵与工具定义解耦**：权限配置独立于代码部署，方便随时调整。一旦发现某工具误分类，不需要重新发布 Agent。
- **提供“推理摘要”而非原始技术信息**：当 Agent 请求人类批准时，用自然语言解释它为什么要执行这个操作，而不是丢出一串 JSON 参数，让用户真正理解后再做决定。
- **从保守起步，逐步开放**：先按最严格策略运行，收集用户批准与拒绝数据，再基于数据调整低风险分类。不要试图一开始就做到完美自动化。

## 总结

Agent 的权限边界不是一个静态配置项，而是一个需要持续演化的工程体系。通过**风险分级、上下文感知、可撤销信任**的组合，我们可以在保持自动化效率的同时，给人类留下真实、有效的控制点。这不仅是安全需求，更是让 Agent 能够被长期信任的基础。

最终，让 Agent 知道何时该停手，比让它什么都能做更重要。
