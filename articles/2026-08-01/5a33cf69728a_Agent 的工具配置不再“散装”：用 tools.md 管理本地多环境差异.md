## 背景
在 OpenClaw、MCP 插件的工程实践中，Agent 需要接入的外部工具越来越多：搜索引擎、文件读写器、第三方 API、本地脚本……几乎每个工具都有自己的一套配置项——API Key、Base URL、文件根路径、超时时间。起初开发者可能把这些值散落在代码里、`os.getenv()` 里，或者一股脑塞进 `.env` 文件，等到需要切换环境（本地开发 → CI → 生产部署）时，才开始面对一连串“在我机器上是好的”问题。工具配置的管理，如果没有一个明确的约定，很快就会变成环境差异引发的排障重灾区。

## 当前常见的问题
- **配置零散，缺乏声明**：新人接手时不知道要设置哪些环境变量，只能从报错或源码里猜。
- **环境差异隐蔽**：开发环境与生产环境使用了不同的工具版本、不同的服务端点，但这些差异没有任何文档或机制来显式化。
- **变量命名冲突**：多个工具都用了 `API_KEY` 这种通用名，互无感知，改一处可能伤及另一处。
- **.env 文件臃肿且不安全**：所有变量混在一起，容易误提交真实密钥，且无法区分哪些变量是必填、哪些有默认值。

## 做法：把工具配置声明到 tools.md
一个工程化的方案是：在 Agent 项目根目录维护一个 `tools.md` 文件，它不是死的文档，而是**工具需求的声明式配置**。既给人看，也给机器解析。

### 1. 定义声明格式
用 Markdown 表格来描述每个工具需要的环境变量、类型、默认值和是否必填。一个简短的示例如下：

```markdown
# tools.md

## web_search
| 环境变量            | 类型   | 必填 | 默认值                  | 说明                |
|---------------------|--------|------|-------------------------|---------------------|
| `SEARCH_API_KEY`    | string | 是   | -                       | 搜索引擎的 API Key   |
| `SEARCH_ENGINE_ID`  | string | 否   | `google`                | 搜索引擎 ID          |
| `SEARCH_ENDPOINT`   | url    | 否   | `https://api.s.com/v1`  | 自定义搜索端点       |

## file_reader
| 环境变量            | 类型   | 必填 | 默认值      | 说明                  |
|---------------------|--------|------|-------------|-----------------------|
| `FILE_READER_ROOT`  | path   | 否   | `./data`    | 文件读取根目录        |
| `FILE_MAX_SIZE_MB`  | int    | 否   | `10`        | 最大读取文件大小(MB)  |
```

这种格式可读性高，同时也便于脚本解析（用正则或 Markdown 解析器取出表格内容）。

### 2. Agent 启动时加载 tools.md
在 Agent 的配置加载模块实现一个解析函数，它读取 `tools.md`，提取所有声明的环境变量，构建出一个配置清单。然后用该清单从实际环境变量（`process.env` 或 dotenv 加载后的对象）中获取值，进行类型转换与校验：

- 对必填但缺失的变量直接抛出明确的错误，附带工具名称，避免启动后再莫名崩溃。
- 对布尔型、数字型按声明转换（如 `"true"` → `true`），避免 `if (config.maxSize)` 这种隐式判断出错。
- 路径类型自动展开 `~`（使用 `os.homedir()` 或对应方法），保证在 Linux/macOS 下的本地路径可以正确解析。

这样，工具的初始化代码就不再需要零散地读取环境变量，它们只需要从统一的配置对象中取值。

### 3. 环境差异只靠 .env 与控制层
不同的环境（dev/staging/prod）通过各自的 `.env` 文件来提供变量值，`tools.md` 保持不变。同时，可以从 `tools.md` 自动生成 `.env.example`，让新成员一目了然，只需复制并填入真实密钥。也建议提供一个轻量 CLI 命令：
```
agent tools validate
```
该命令解析 `tools.md`，检查当前环境下所有必填变量是否已设置，并可列出可选变量及其当前有效值，便于调试。

## 踩过的坑
- **类型转换陷阱**：环境变量都是字符串，若声明为 `int` 却拿到 `"10"`，要在加载阶段强制 `parseInt`，否则 `config.maxSize` 用在比较中可能变成字符串拼接。  
- **路径中特殊字符**：Windows 路径反斜杠、Linux 下的 `~`，解析时务必用 `path.resolve` 或 `untildify` 库做归一化，否则工具会报“找不到路径”。  
- **多工具变量同名**：如果两个工具都声明了 `API_KEY`，上述表格会自动加上工具前缀防止冲突（实际加载时会给每个工具一个独立命名空间，如 `web_search.API_KEY`），未做命名空间隔离时会互相覆盖。  
- **版本控制污染**：`tools.md` 本身应提交到仓库，但任何默认值如果包含敏感信息（例如测试 key），应及时替换为占位符。同步确保 `.env` 被 `.gitignore`，并用自动化脚本检查提交中是否包含真实密钥。  

## 可复用建议
- **单一声明源**：让 `tools.md` 成为工具配置的唯一真相源，CI 脚本、本地开发指南、Docker 入口脚本都基于它生成所需配置。
- **Profile 分隔**：如果环境差异非常大，可在 `tools.md` 中使用多级标题区分 `## dev`、`## prod`，加载时按 `NODE_ENV` 选择对应段落的声明。
- **结合容器化**：在 Docker 镜像中，通过 `COPY tools.md .` 并配合启动脚本，在生产环境自动校验所有必需变量，避免启动后才发现缺少密钥。
- **工具链校验**：把 `agent tools validate` 放到 CI 的 lint 阶段，任何新加工具而未更新 `.env.example` 或缺少文档的行为都会提前暴露。

## 总结
`tools.md` 的实践本质是把“环境配了没”这种隐性知识，转变成一份显式、可验证、可自动化的声明文件。它即是一份文档，也是一个配置合约。对 Agent 这种外部依赖繁多的工程来说，尽早建立这个约定，可以减少大量由环境差异引起的低效排障，让团队在本地、CI、生产之间无缝切换。如果你正在为工具配置的散乱而头疼，不妨从一张 Markdown 表格开始整理，它能带来的工程收益远超出预期。
