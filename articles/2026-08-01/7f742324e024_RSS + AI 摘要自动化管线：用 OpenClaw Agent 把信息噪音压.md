## 背景：囤积的 RSS 与永远读不完的文章

我做技术文档和方案设计，日常依赖 RSS 订阅了大约 60 个信息源（官方技术博客、独立开发者周报、安全公告等）。过去两年我反复尝试“每日精读”，但成果总是归零——不是没时间，而是被大量重复内容、接近零信息密度的更新以及标题党消耗掉了意志力。

最近把这条管线重构了一遍，用 **OpenClaw Agent + MCP 工具** 搭建了一条全自动的信息摘要流水线：定时拉取 RSS，由本地 LLM 生成结构化的中文摘要，最后归档到本地知识库并推送通知。这篇文章记录管线设计、踩过的坑以及可以复用的工程片段。

## 问题拆解：一条好的管线长什么样

第一条原则：**不把未经处理的 Feed 直接喂到眼前**。RSS 管线要解决的其实是三个问题：

1. **可靠抓取**：网络抖动、源站改版、超时重试。
2. **去重 & 增量**：同一条目在不同源重复出现，或者源自身重复推送。
3. **有意义摘要**：不是把文章前 200 字截断，而是按照我的需求提取出“做了什么/为什么重要/可复现点”。

OpenClaw 的 `workflow` 类型 Agent 天然适合这种**有顺序、可重试、可观测**的管道任务。配合 MCP（Model Context Protocol）工具，我可以直接把 `rss-fetch`、`md5` 和 `llm-summarize` 串成一个可调试的序列，而不是写一堆胶水脚本。

## 实现步骤：Agent 如何跑完一条流水线

### 1. 用 MCP 工具接入 RSS 抓取能力

我把 RSS 解析封装成一个 MCP 工具 `fetch-rss`，底层用 `rss-parser` 库。MCP 工具运行在 `@anthropic/mcp` 提供的标准接口上，OpenClaw 的 Agent 通过标准 JSON-RPC 调用它，不需要额外适配。

工具接收两个参数：Feed URL 和上次抓取的时间戳（可选）。返回标准化的条目列表，包括 `title`、`link`、`pubDate`、`contentSnippet`，以及唯一标识 `guid` 或 `link` 的 md5。

### 2. 用 OpenClaw Workflow 定义处理步骤

在 OpenClaw 中创建一个 `workflow` Agent，配置如下几个步骤：

```yaml
agent:
  name: rss-summary-pipeline
  type: workflow
  triggers:
    - cron: "0 7,12,18 * * *"   # 早中晚各一次
  steps:
    - id: fetch_all
      tool: fetch-rss
      params:
        urls: ["`url1`", "`url2`", ...]
        since: "{{ last_run }}"
    - id: dedup
      tool: hash-dedup
      params:
        field: link_hash
    - id: summarize
      tool: llm-summarize
      params:
        model: openclaw-local
        template: tech_deep
    - id: save_and_notify
      tool: archive-roam  # 写入本地知识库
      tool: push-notify   # 推送摘要到手机
```

这里的每一步都是幂等的。`fetch-rss` 如果某源超时，只会返回该源错误并继续其他源；`dedup` 用 link 的 md5 过滤，并且会记录 24 小时内已见过的条目；`summarize` 配置了最大重试 2 次。

### 3. AI 摘要的模板工程

摘要质量的关键不是提示词开脑洞，而是**明确约束输出形状**。我用的模板长这样：

```
你是技术摘要助手。生成中文摘要，长度不超过 150 字，必须包含以下字段：
- 一句话核心内容
- 技术关键词（≤3）
- 可复现结论或动作
请用下划线标出以上三项。原文：
{{ content }}
```

配合本地 7B 模型（量化后 4GB 显存），单条摘要平均 1.9 秒，质量稳定。幻觉控制主要靠强制字段和字数约束，一旦输出缺失字段，工作流就会标记该摘要为 `low_quality` 并降级成原文前 200 字截图。

### 4. 通知与归档：避免“看完就忘”

摘要最终写入本地 Markdown 库，按日期和源分类。推送方面，我用了 OpenClaw 内置的 `push-notify` 工具（实际上它只是一个 MCP 适配器，底层可以是 Bark 或者 ntfy）。每天中午 12 点和晚上 6 点的推送只发送**过去 6 小时内新增且打分 ≥ 3（我自己给的可复现性 1-5 分）** 的条目，大约每天 3-5 条，阅读负担极低。

## 踩坑实录与调优

**坑 1：某些 RSS 源链接不是永久链接**  
比如某些网站的 Feed 给的是 `https://example.com/123?utm_source=rss`，第二天因为 UTM 参数变化导致 md5 变化。处理办法是解析出真实 path 后再 hash，并在工具中增加 `normalizeUrl` 步骤。

**坑 2：LLM 总结夹带私货**  
小模型容易把原文没有的观点编进去，例如“这篇文章认为……”后面就开始自由发挥。我的解决方案是要求摘要引用原文关键词，并禁止输出“本文认为”之类的主观前缀。实测“使用下划线标出三个字段”这个硬格式比 prompt 约束更有效。

**坑 3：并发抓取导致 IP 被限**  
同时请求 50+ 源会触发某些站点的速率限制。在工作流中加入了 `fetch-rss` 的并发限制参数（用信号量控制同时发出的请求 ≤ 5），并且单源超时设为 8 秒。

## 可复用建议

- **把管道当成“可观测流水线”而不是脚本**，每一步都输出结构化的成功/失败/副作用日志，OpenClaw 的 workflow 原生支持步骤级日志，这比自己写异常捕获舒服得多。
- **摘要模板版本化**。我将模板放在一个单独的文档中，每次修改都会在摘要记录中标记模板版本，便于回溯质量。
- **手搓 MCP 工具不要过度封装**。我的 `fetch-rss` 不到 40 行，`hash-dedup` 基于 Redis Set 也就 20 行，足够可靠。
- **允许降级而不是中断**。某一步失败不应该影响其他条目，每一条目的处理状态独立，这样可以避免一个脏数据阻塞整条管线。

## 总结

这条 RSS + AI 摘要的管线跑了一个月，把每天需要手动 40 分钟的扫读压缩到了 印象中 5 分钟的通知扫视。关键点在于：

- 借助 OpenClaw 的 Agent 与 MCP 工具，把“异构源拉取 → 去重 → 摘要 → 归档推送”串联成一条声明式工作流；
- 用硬格式模板和字段约束控制小模型的摘要质量；
- 每一步都做幂等、超时、降级处理，让管线本身几乎不需要人工维护。

如果你想复现，最轻量的方式是从两个 MCP 工具开始：一个 RSS 拉取工具 + 一个 LLM 摘要工具，接上本地 OpenClaw 的 workflow。随后再逐步扩展去重和归档层。工程上，先跑通一条源，再批量，是对抗“信息焦虑”的最高性价比路径。
