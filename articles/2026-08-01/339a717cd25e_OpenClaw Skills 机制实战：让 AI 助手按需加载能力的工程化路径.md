## 背景

如果你正在用 OpenClaw 构建 AI Agent，迟早会撞上一个问题：**能力越多，助手反而越蠢**。

在实验阶段，我们习惯把所有工具、知识、指令一股脑塞进系统提示词。一开始工作得很好——Agent 能查天气、能读文件、能调用 MCP 服务。但当工具数从 3 个变成 30 个，上下文窗口开始膨胀，推理速度变慢，生成质量下降，甚至模型开始“遗忘”某些工具的用法。

这就是典型的**能力膨胀（capability bloat）**：一次加载全部能力，却只有不到 10% 会被实际用到。更糟糕的是，不同任务之间的提示词互相干扰，模型更易产生幻觉。

OpenClaw 的 Skills 机制就是为此设计的：**将能力拆成独立的技能包，只在对话中按需注入**。它不是简单的“开关”，而是一套基于触发规则的动态加载系统，能在不牺牲响应质量的前提下，让 Agent 持有成百上千个技能。

## 问题拆解

按需加载的核心挑战有三个：

1. **触发精度**：什么时候加载哪个技能？错误加载会让 Agent 混乱。
2. **上下文管理**：技能注入后如何不超出 token 限制？如何保证 prompt 拼接后模型的注意力仍集中在用户问题？
3. **多技能协同**：一次对话可能需要多个技能，如何避免冲突、让它们有序协作？

OpenClaw 采用“描述词 + 触发条件 + 优先级”的三层模型来应对。每个 Skill 是一个独立的描述文件（YAML），定义自己的名称、用途描述、触发关键词/意图模式、以及实际注入的指令或工具列表。运行时引擎会在每轮对话前扫描匹配的 Skill，按优先级排序后注入。

## 实践路线：从零构建一个按需技能

我们以一个“工时记录”技能为例，展示完整过程。

### 1. 定义 Skill 文件

在 OpenClaw 默认的 `skills/` 目录下创建 `time_tracking.yaml`：

```yaml
name: time_tracking
description: |
  记录用户在项目上的工时。
  当用户提到开始工作、结束工作、记录时间、
  查看工时统计时触发。
triggers:
  - pattern: "(开始|结束|停止)(工作|计时|记录)"
  - pattern: "(今天|本周|这个月)(工作了|干了)多久"
  - intent: "time_tracking"
priority: 10
inject:
  system_prompt: |
    你现在可以协助用户管理工时。
    记录开始时间、结束时间、项目名称，
    并维护一个简单的内存日志。
    每次操作后，用[工时]前缀回复。
  tools:
    - name: record_time
      description: 记录工时条目
      module: tools.time_tracker
```

这里的关键要素：
- **triggers** 支持正则模式与语义意图两种方式。意图匹配需要额外配置意图识别模型（默认使用轻量级 NLU 服务），但绕过精确关键词。
- **priority** 决定了当多个技能同时被触发时的执行顺序。数字越小越优先。
- **inject** 精确控制要注入的内容，最小化上下文污染。

### 2. 启用技能注册

在 Agent 配置文件（如 `agent.yaml`）中指定技能路径并启用按需加载：

```yaml
skills:
  dir: ./skills
  mode: on_demand    # 可选 always / on_demand / fallback
  max_tokens_per_skill: 2000
  default_priority: 50
```

这里的 `mode` 值得展开：
- `always`：技能始终注入，适合基础能力（如安全策略）。
- `on_demand`：仅在触发匹配时注入，我们的主要战场。
- `fallback`：当 Agent 无法识别用户意图时作为兜底技能加载，可用于异常处理或引导。

### 3. 测试与调试

启动 Agent 后，首先用明确的触发句测试：

```
用户：帮我开始记录工作，项目是 OpenClaw 优化。
```

观察日志中是否出现 `Skill inject: time_tracking` 以及模型回复前缀 `[工时]`。

第一次失败很常见——通常是触发模式写得太严格。比如 `(开始|结束|停止)(工作|计时|记录)` 不会匹配“开始记录工作”，因为顺序反了。调整为：

```yaml
- pattern: "(开始|结束|停止)(工作|计时|记录)|(记录|计时|工作)(开始|结束)"
```

正则编写是精细活，建议遵守“宁松勿紧、先上线后收紧”的原则。

调试时启用 `--log-level debug`，你会看到类似这样的流程：

```
[INFO] Checking triggers for message: '帮我开始记录工作...'
[DEBUG] Skill 'time_tracking' pattern matched: (...)
[DEBUG] Injecting skill prompt (token_count: 342)
[INFO] Candidate skills: ['time_tracking']
[INFO] Assembled system prompt with 1 active skill(s).
```

这个日志是理解加载行为的命门——一旦出现预期外的技能未加载，第一时间检查这里的匹配情况。

## 踩坑实录

### 坑1：多人对话时技能残留

在会话模式下，一个技能被加载后会持续生效，直到显式移除。如果 A 用户的请求触发了“工时记录”，B 用户的后续问题也会看到注入的技能指令。

**解法**：在 `inject` 中设置 `lifespan: single_turn`，让技能仅在下一轮回复中有效，或者每次请求结束时主动重置。

### 坑2：触发冲突与噪音

当多个技能的正则都匹配了同一条消息，所有符合的技能都会被加载。如果你有 20 个技能都用了非常宽泛的模式（如 `(帮忙|协助)`），一次简单的招呼就可能注入大量无关指令，导致模型不知所措。

**解法**：利用 `priority` 字段让高优技能先执行，并在注入前做去重。更根本的是，将触发器收敛到领域性强且互斥的模式，避免使用万能词。

### 坑3：上下文溢出

即使按需加载，如果一次匹配 5 个技能，每个注入 2000 token 的系统提示，总长度可能瞬间超过模型限制。

**解法**：设置 `max_skill_tokens` 全局上限，或采用动态裁剪策略——当注入超限时，优先保留高优技能，裁剪低优技能的指令长度。在我们的场景中，将每个技能的系统提示控制在 1000 token 以内，并尽可能用工具定义代替长指令，长期有效。

## 可复用的工程化建议

1. **技能原子化**：每个技能只做一件事。不要造一个“办公全能”技能，而是拆成邮件、日历、笔记等独立包。原子化让触发更精准，也方便组合。
2. **编写可测试的触发器**：为每个技能的 pattern 写单元测试（用 Python 的 `re` 或专用脚本），覆盖正例与负例，保证改动不破坏已有触发逻辑。
3. **维护技能版本**：在 YAML 中添加 `version` 字段，配合 Git 管理。当某个技能出现行为退化时，能快速回退。
4. **与 MCP 工具协同**：技能注入的工具可以直接是 MCP 工具的包装器，这样你可以在技能中引用已有的 MCP 服务，避免重复实现。
5. **监控技能命中率**：统计每个技能每周的触发次数，对长期未被触发或误触率高的技能进行下线或重构，保持技能池的精简与高效。

## 总结

OpenClaw Skills 的按需加载机制，本质上是在**扩展能力与保持模型专注**之间做博弈。它不是一个“自动魔法”，需要你精心设计触发规则、控制注入量、管理生命周期。但一旦调顺，你将得到一个既能充当万能工具箱、又不会被工具压垮的 AI 助手。

最好的 AI Agent 不是最全能的，而是知道在什么时刻该激活什么能力。Skills 机制让这一点工程化地落地。
