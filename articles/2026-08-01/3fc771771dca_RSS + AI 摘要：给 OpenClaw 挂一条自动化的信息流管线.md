## 背景

信息源越来越多，RSS 反而成了最干净的获取方式。但“订阅→未读积压→放弃”的路径太常见了。AI 摘要能解决“看不完”的问题，但把 RSS 接上 AI 再输出到日常简报，中间的胶水代码总要反复写。

在 OpenClaw 的生态里，这件事可以做得更工程化：用 MCP 服务器暴露 RSS 能力，用 Agent 编排采集、去重、摘要与分发，配合定时触发器，一条管线就能跑起来。这篇文章记录一个实际可用的搭建方案，以及过程中踩过的坑。

## 问题定义

目标管线很简单：
1. 定时拉取指定 RSS 源的新条目。
2. 对未处理过的条目调用 AI 生成 100–150 字中文摘要。
3. 汇总后推送到通知渠道（如邮件、Webhook 或 OpenClaw 内部消息）并持久化存底。

需要解决的问题：
- 如何让 Agent 可靠地拿到 RSS 数据，且不需要针对每个源写定制解析。
- 如何避免重复摘要，控制 AI 调用成本。
- 管线异常时如何降级，而不是彻底断流。

## 做法与步骤

### 1. 搭建 RSS MCP 服务

社区已有能抓取 RSS/Atom 的 MCP server，如 `rss-reader-mcp`，将其挂载到 OpenClaw 的 MCP 配置中：

```json
{
  "mcpServers": {
    "rss": {
      "command": "npx",
      "args": ["-y", "rss-reader-mcp"],
      "env": {
        "RSS_CACHE_TTL": "300"
      }
    }
  }
}
```

该 server 暴露 `fetch_rss` 工具，接收 URL 返回标准化条目（title, link, description, pubDate, guid）。标准化输出是对抗 RSS 源差异的关键。

### 2. 在 OpenClaw 中设计 Agent 工作流

定义三个工具组合：

- `fetch_rss`（来自 MCP）：拉取条目数组。
- `kv_get / kv_set`：用一个简单的 KV 存储载体（可以是 OpenClaw 内置持久化或外部 Redis）保存以 `guid` 为键的处理状态，值存处理时间。
- `ai_summarize`：调用模型生成摘要，prompt 固定为：“用 100–150 字中文摘要以下文章，保留关键事实和观点，不要评价。”

Agent 流程（可在 OpenClaw 中封装成一个技能）：
1. 对每个 RSS 源调用 `fetch_rss`。
2. 遍历条目，对每个 `guid` 查询 KV 是否存在。若存在则跳过。
3. 对未处理的条目调用 `ai_summarize`，传入 `title + description` 拼接文本。
4. 摘要结果立即写入 KV 标记已处理，同时追加到当日摘要缓存（内存或临时文件）。
5. 所有源处理完毕，组装一份 Markdown 简报，通过 `notify` 动作发送。
6. 设置 OpenClaw 的定时任务，每小时触发一次该技能，避免高频抓取被源站封禁。

### 3. 防重复与成本控制

仅用 `guid` 去重不够安全——某些源更换域名或重建后 guid 会变。增加一层内容指纹兜底：对 `title+link` 做 md5 作为次键。写入 KV 时同时存两份，查询时满足其一即跳过。

AI 调用成本方面：
- 限制单次任务最大摘要条目数（如 20 条），超出部分顺延到下次触发。
- 对 description 截断至 300 字再送入 AI，避免 token 浪费。
- 使用小型模型（如 7B–13B 参数量）足够胜任摘要任务，性价比高。

### 4. 日志与降级

每次任务结束记录拉取条数、新条目数、摘要调用次数、耗时。若连续 3 次调用失败，通过 OpenClaw 的内置通知发送告警。RSS 抓取失败不阻断其他源，捕获异常后记录错误源并继续。

## 踩坑点

**RSS 源不规范**
不少国内网站输出的 RSS 缺少 `pubDate` 或 `guid`，或 content-type 错误导致 MCP 解析失败。降级方案：对缺失 `guid` 的条目用 `link` 作为唯一标识；如果 `pubDate` 缺失，去重逻辑完全依赖标题指纹，但会略降准确性。可在 MCP server 侧预置几个容错规则。

**MCP 传输超时**
某些 RSS 源响应极慢（超过 10 秒），导致 Agent 工具调用超时中断。解决：在 MCP 配置中设置 `timeout`，并在 Agent 侧用 try/catch 包裹每个 `fetch_rss`，避免慢源拖死整个任务。

**KV 持久化选型**
早期用内存字典，重启 OpenClaw 后状态丢失导致重复摘要。改用文件存储或 Redis，并开启定期备份。KV 结构不要只存“是否处理”，最好存摘要本身，以备将来想重建索引或搜索。

**AI 摘要质量波动**
提示词里加一句“如果文章无法提取实质内容，请输出‘内容不明，跳过’”，模型会更诚实地反馈，而不是强行编造。

## 可复用建议

- **模板化 prompt**：将摘要指令与输出格式分离，便于切换生成长度、语言或风格。
- **保留原始条目**：即使推送摘要，也建议存一份完整条目到 Markdown 或 SQLite，为后续全文搜索留口子。
- **源分类**：给每个 RSS 源打标签（技术、社科、新闻），摘要生成时可带上标签，方便分类汇总。
- **最小化配置分享**：一个可运行的技能包可以仅包含一个 Agent 定义文件、一个 MCP 配置片段、一份 KV 实现示例，哪怕脱离 OpenClaw 也能在同生态里复用。

## 总结

用 OpenClaw 结合 MCP 与 Agent 搭建 RSS+AI 摘要管线，本质上是用编排取代了定制化脚本。结构清晰后，折腾的核心就剩两件事：对抗不规范的 RSS 数据，以及控制好用模型的钱包。这套管线还可以长出很多分支：关键词监控、论文每日速览、竞品动态聚合，都只是换个源、改个 prompt 的问题。

在信息输入流上多做一点自动化，省下的是持续注意力的开销。工程化不是为了酷，是为了让它稳定到可以被遗忘、却每天准时出现。
