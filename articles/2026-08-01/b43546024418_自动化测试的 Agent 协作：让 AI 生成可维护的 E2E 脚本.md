## 背景：E2E 维护成本居高不下

端到端（E2E）测试是保障核心业务流程的最后一道防线，但维护成本人尽皆知。UI 的一次微调就可能导致数十条用例挂掉，定位策略从 ID 退化到 XPath，又因为框架升级需要全部重写。录制回放工具的脚本更脆弱，几乎不可维护。

过去一年，LLM 驱动的 Agent 从概念走向落地，自动化测试领域也开始受到冲击。在用 OpenClaw 搭建内部工具链的过程中，我们尝试让 Agent 承担 E2E 脚本的生成与自愈工作，效果远超预期。这篇文章还原整个实践过程，聚焦真实问题与可复用的做法。

## 问题拆解：Agent 需要跨越的鸿沟

最终目标是：给定一段自然语言的测试场景，Agent 操控浏览器完成操作，输出一条可脱离 Agent 独立运行的测试脚本，并在失败时自我修正。

这中间存在几个核心挑战：

1. **定位策略的鲁棒性**：Agent 常生成 `div > div:nth-child(3) > ...` 这类脆弱选择器，页面结构一改就失效。
2. **断言的质量**：生成的断言要么过于简单（只判断页面标题），要么过于严格（精确匹配某个时间戳文本）。
3. **异常处理缺失**：脚本不包含等待或容错逻辑，网络延迟就直接超时。
4. **自愈时的循环陷阱**：Agent 在修正失败后会尝试更换选择器，但可能一直失败，无限重试。

## 实践方案：基于 OpenClaw + Playwright MCP

我们选择了 Playwright MCP 作为浏览器操作接口，配合 OpenClaw Agent 框架实现以下工作流：

1. **场景录入**：以自然语言描述用例，如“登录后，搜索‘机械键盘’，加入购物车，进入结算页，填写地址并选择微信支付，确认下单”。
2. **环境感知**：Agent 调用 `browser_navigate` 进入系统，通过 `browser_snapshot` 获取基于可访问性树的页面结构（类似 `page.accessibility.snapshot()`），同时可选截图做视觉参考。
3. **逐步生成与执行**：Agent 根据感知信息规划操作步骤，生成 Playwright 代码片段，使用 `browser_run_code` 执行，观察结果后继续下一步。
4. **断言注入**：每个关键步骤后，Agent 必须插入一条可验证业务状态的断言，例如下单成功后检查订单号是否生成、金额是否匹配。
5. **自愈循环**：如果某一步执行报错，Agent 会将错误信息、当前页面快照和之前的代码作为上下文，重新生成修正后的代码，最多重试 3 次。

最终输出产物是一份完整、可独立运行的 Playwright 脚本（`.spec.ts`），而不是依赖 Agent 的一次性会话。

## 具体步骤（可复现）

**Step 1 – 配置 MCP Server**

在 OpenClaw 的 MCP 配置中加入 Playwright server 的 SSE 端点，确保工具可用。我们用 chromium 有头模式运行，并开启 trace 用于事后分析：

```json
{
  "mcpServers": {
    "playwright": {
      "url": "http://localhost:8931/sse"
    }
  }
}
```

**Step 2 – 设计 Agent 的 system prompt**

Prompt 的质量直接决定生成脚本的工程水平。我们给出的核心约束：

- 优先使用 `getByTestId`（需业务配合在 DOM 上埋 `data-testid`），其次 `getByRole`/`getByText`，严禁使用 `:nth-child` 或绝对路径 XPath。
- 所有操作前必须通过 `waitForSelector` 或 `expect(...).toBeVisible()` 确保元素可达。
- 断言必须验证业务结果，不能仅检查 URL 或标题；推荐使用 JSON 格式的 API 响应校验（如果页面有对应的网络请求）。
- 脚本需包含 `test.describe` 封装，并合理使用 `test.beforeEach` 复用登录态。
- 只输出可运行的 TypeScript/Playwright 代码，移除多余的解释性文字。

**Step 3 – 小步运行，积累上下文**

不让 Agent 一次生成全部脚本再执行，而是要求它规划步骤后，生成一步、执行一步、观察结果。这让 Agent 能够基于真实的页面反馈调整后续操作，也更容易定位错误。

例如“加入购物车”这一步骤，Agent 会先定位商品列表，截取第一个商品的文本，再通过文本找到“加入购物车”按钮，执行后检查购物车图标上的数字是否更新。每一步成功后才会进入下一步。

**Step 4 – 保留执行历史以辅助自愈**

我们将每次执行的代码、错误信息、页面快照都保存为临时文件，供 Agent 自愈时使用。若重试 3 次仍失败，则生成一个包含详细注释的半成品脚本，方便人工介入。

## 踩坑记录

1. **视觉定位的不可靠**：即便提供了截图，Agent 也常常错误识别按钮位置，尤其在 H5 动画和高分辨率屏幕上。最终我们强制 Agent 以可访问性树为准，截图仅作为“视觉确认”的可选项。
2. **动态列表的断言容易飘**：搜索结果的商品列表每次会变，Agent 生成的断言写明“第一个商品名称为‘XX’”，第二天就跑不过了。改为要求断言列表长度大于 0 且每个条目都包含价格等通用特征，稳定性大幅提高。
3. **登录态复用问题**：Agent 生成的 beforeEach 经常硬编码账号密码，安全性差。我们改为引导它使用全局认证状态文件（`storageState`），与 CI 环境集成。
4. **MCP 工具调用延迟**：每次 `browser_snapshot` 耗时约 1-2 秒，复杂页面快照体积大，Agent 处理变慢。通过限制快照层级深度（只取 role 为 main 的区域）优化了速度。

## 可复用的建议

- **将业务页面封装为 Page Object 的骨架**：虽然脚本由 Agent 生成，但让 Agent 输出符合你项目 Page Object 模式的代码，后续人工维护成本会大减。可以在 prompt 中给出 Page 类的范例。
- **为 Agent 准备一份“语义标注指南”**：告诉它你的系统中哪些 DOM 属性表示唯一标识，比如 `data-testid="add-to-cart-btn"`，Agent 就会倾向使用这些属性。
- **拆分长场景**：超过 10 个步骤的场景，失败后重试时间太长。拆分成多个独立用例，通过 API 创建前置数据，而非全走 UI，可提升效率和稳定性。
- **保留人工审查关卡**：Agent 生成的脚本必须经过代码审查再合入主干。我们的经验是，大约 20% 的脚本需要微小调整（主要是等待条件），真正完全无误的比例还不够高，但已节省了 60% 以上的编写时间。

## 总结

用 Agent 协作编写 E2E 测试不是取代测试工程师，而是把机械化的 UI 操作翻译工作转交给 AI，让人更专注于场景设计和异常分析。OpenClaw 与 Playwright MCP 的组合提供了一个灵活的基座，你可以在此基础上叠加自己的规范、prompt 与审查流程。目前的产出已经能够直接进入 CI 并保持一定的抗变性，这让我们对“测试脚本自愈”有了更实际的期待。

如果你也在做类似的尝试，建议从一条核心业务流程开始，跑通生成-执行-自愈的闭环，再逐步扩大覆盖范围。工程化的细节，才是决定这套方案能否长期运转的关键。
