## 背景：为什么认真讨论 memory_recall

在 OpenClaw / Agent 这类项目中，为助手加上长期记忆已经成为标配需求。记忆模块通常包含两个动作：写入（memory_store）和召回（memory_recall）。写入相对单纯，真正的工程瓶颈往往在召回侧：如何从几百条到几万条历史片段中，精准找出与当前对话最相关的记忆。

最直接的两种实现路线：

- 全文搜索：基于关键词匹配，常用 BM25、SQLite FTS、Elasticsearch 等。
- 语义搜索：将记忆文本向量化，用余弦相似度检索，常用 embedding 模型 + 向量数据库。

一开始很多人会认为语义搜索明显更智能，但实际落地时两种方案各有利弊，而且混合使用才是大多数靠谱实现的选择。

---

## 问题：两类搜索在 memory 场景下的真实表现

我曾在基于 OpenClaw 的助手插件里先后落地过纯全文、纯语义和混合检索三版 memory_recall，踩过不少坑。

**全文搜索的优势**  
- 对专有名词、ID、邮箱、命令等精确词汇，召回非常可靠。  
- 不需要额外算力，本地 SQLite FTS5 也能跑得飞快。  
- 逻辑简单易调试，行为可解释性强。

**全文搜索的硬伤**  
- 严重依赖分词器质量。中文场景下，jieba / IK 分词对口语化表达、混用中英文和符号时很吃力。  
- 无法理解语义相近但用词不同的句子，例如“上周报的预算”和“财务提交的数字”可能完全匹配不上。

**语义搜索的优势**  
- 模型天然理解同义词、句式变化，能捞到“意思接近”的记忆片段。  
- 直接支持跨语言召回（如果用多语言 embedding 模型），不需要翻译步骤。

**语义搜索的痛**  
- 面对短文本、数字、代码片段时，向量区分度极低。一条只包含 `“32.5”` 的记忆，可能跟大量无关数字撞车。  
- 推理成本高，本地 CPU 跑 embedding 时延高，云端 API 又会引入延迟和额度消耗。  
- 黑盒难调试，相似度分数波动大，很难设定统一阈值。

## 做法与步骤：在 OpenClaw 插件中接入可切换的 recall 方案

下面是我在 memory 插件中采用的结构，支持配置在全文 / 语义 / 混合之间切换。

**1. 记忆存储入口（统一写入）**  
每次对话结束后，将用户发言、助手回复和关键元信息拼接为一条记忆文本，写入 SQLite 主表，同时异步更新对应的检索索引（全文索引或向量索引）。统一写入保证两种搜索共享同一份源数据，避免不一致。

**2. 全文检索通道**  
使用 SQLite FTS5，搭配自定义分词器（用 simple 分词 + 手动预处理，避免 jieba 在短句上过度切分）。查询时先用原始 query 匹配，对无结果的情况用自动生成的 bi-gram 兜底。

**3. 语义检索通道**  
选用本地部署的 BGE-small-zh-v1.5 模型，通过 ONNX Runtime 做 CPU 推理，将单条记忆转为 512 维向量存入 qdrant-client 的本地文件模式（无需服务进程）。召回时取 top_k=20，相似度阈值默认 0.6，但为了降低漏召回，实际使用中通常设置得比较低（0.45），之后再靠重排序兜底。

**4. 混合检索：先全文，后语义**  
这是目前效果最稳的一条路。流程为：
- 用户 query → 全文检索（快速过滤，取 top 100 候选）；
- 候选文本 → 语义重排序（使用 SentenceTransformer 计算 query 与每个候选的相似度）；
- 二次排序后返回 top 5～10，不再依赖单一的相似度阈值。

这样做的好处是：全文保证了专有名词不会被遗漏，语义重排又补偿了同义表达的召回。

## 踩坑点实录

**坑1：短记忆的向量失效**  
用户一条记忆只有“192.168.1.1”，语义搜索几乎无法区分。解决方式：写入时自动为短记忆拼接上下文标签，例如“用户提供的服务器 IP 地址：192.168.1.1”。这样就算纯语义也能获得可用的召回。

**坑2：分块与时间衰减**  
如果记忆不按时间加权，老记忆会不断积累并干扰新对话。我用了一个简单策略：每次相似度分数乘以时间衰减因子 `0.999^(days_ago)`，让新的相近记忆优先出现。这个衰减系数需要根据业务场景调整。

**坑3：重排序模型的资源消耗**  
一开始在 CPU 上直接用 BGE 做重排，20 条候选 + query 需要近 1 秒。后来改用轻量的 paraphrase-multilingual-MiniLM-L12-v2，并加了一个小缓存（相同 query 短时间内复用），延迟降到 200ms 内。

**坑4：全文索引的更新延迟**  
写入后立刻调用 memory_recall，可能因为异步索引还没建好而漏掉。排查了半天，最后在写入后显式提交 SQLite 事务并 `fts_rebuild`，确保同步可见。

## 可复用建议

- **开局先做全文，别着急上语义**。全文成本低、可解释，能快速验证记忆本身的格式和分块策略是否合理。
- **语义搜索必须搭配固定的 embedding 模型版本**，否则换模型后整个向量库需要重建，迁移很痛。
- **混合检索是目前性价比最高的入口设计**：用轻量全文过滤，用小模型做重排，谨慎分配算力。
- **给记忆打上“时效”“类型”“用户意图”等标签**，比单纯依赖文本相似度更可控。比如标签为“偏好”的记忆，可以提升权重。
- **为召回的失败案例建立评测集**。把 query 和漏召回的黄金记忆记录下来，定期跑一轮准确率，再调整阈值或模型。

---

## 总结

在 AI 助手的 memory_recall 实践中，“语义搜索 vs 全文搜索” 不是二选一，而是按场景组合的工具箱。全文负责兜底精确查询，语义负责理解模糊意图，重排序负责最终把关。

短期内，如果你的记忆规模在 1 万条以下，SQLite FTS5 + 轻量 BGE 重排器就可以做出相当好用的召回系统——不需要什么分布式向量数据库，也不依赖云端 API。把重心放在记忆的写入质量和评测机制上，远比纠结用哪个向量库重要。
