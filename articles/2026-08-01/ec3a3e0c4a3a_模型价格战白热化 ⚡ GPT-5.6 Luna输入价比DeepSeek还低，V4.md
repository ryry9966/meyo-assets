就在刚刚过去的这个周末，硅谷和杭州几乎同时炸开锅：OpenAI 毫无先兆地放出了代号为 Luna 的 GPT-5.6 系列 API，并公布了一份「击穿行业底价」的费率表；而仅仅几个小时后，DeepSeek 官方便宣布 V4 正式版即刻可用，且同步调低了入门档的调用成本。两件事放在一起看，绝不是巧合。一场围绕大模型推理定价的极限竞赛，已经进入读秒阶段。



## 一、价格极限在哪里？GPT-5.6 的「成本魔法」拆解
让行业震动的核心数字，是 GPT-5.6 Luna 的输入定价：每百万 token 低至 0.018 美元，而 DeepSeek V3 此前标称的最低价为 0.14 美元/百万 token。这不是打五折，而是直接抹掉了一个数量级。如此极端的降幅背后，绝不只是一次简单的促销，而是整套技术栈系统性优化的结果。

- **MoE 架构的极致瘦身**  
  Luna 沿用了 Mixture-of-Experts 路线，但将激活参数压降至 4.2B，同时总专家数翻倍至 256 个。推理时只需唤醒 1~2 个专家，浮点运算量相比 GPT-4 降低 83%，单 token 的能耗成本被压缩到接近嵌入式设备的水平。
- **分层 KV Cache 与 4-bit 量化**  
  新模型采用了 FlashAttention-3 思想的分层键值缓存策略，将长文本场景下显存占用缩小 60%；配合硬件原生支持的 FP4/Int4 混合精度，即便在 H200 上跑 128K 上下文，单卡也能维持 300+ token/s 的吞吐。
- **推理硬件换代与调度优化**  
  OpenAI 首次大规模部署 B200 推理集群，并用定制版 CUDA kernel 将 prefill 与 decode 阶段流水线化，GPU 空泡时间减少 40%。边际成本的断崖式下降，最终传导为用户看到的价格。



## 二、横向比价：一毫一厘的降维打击
如果只看单价数字，可能还感受不到冲击力。我们把几款主流模型的 API 定价拉成一张表，就能看出 GPT-5.6 Luna 的定价策略有多激进。

| 模型                | 输入 $/M token | 输出 $/M token | 自由度备注                     |
|---------------------|----------------|----------------|-------------------------------|
| GPT-4 Turbo         | 0.01（注：实际无此低价） | 0.03           | 旧参考，已被替代              |
| GPT-4.1 Nano        | 0.10           | 0.40           | 曾是对标 DeepSeek 的防守款    |
| DeepSeek V3 (api)   | 0.14           | 0.28           | 缓存命中有折扣                |
| GPT-5.6 Luna        | **0.018**      | 0.045          | 输入价仅为 DeepSeek V3 的 1/8 |
| DeepSeek V4 (正式版) | 0.12           | 0.24           | 首发价，仍较 Luna 高出数倍    |

> 注：以上为公开标准标价，具体折扣、批量合约价不在讨论范围。为便于比较已统一折算为美元。

关键差距出现在两个维度：

- **读多写少的场景**——比如客服总结、知识库检索、RAG 流——Luna 近乎仅为对手 1/10 的输入成本，会立刻改变开发者选型的计算器。
- **商业模式倒逼**——Midjourney、Notion AI 这类重度消耗方，原本每月大模型开销可达六位数美元，现在有可能直接砍半甚至砍掉一个零。

可以说，OpenAI 不是要打价格战，而是直接退出一张牌，把友商逼进「跟不起」的死角。



## 三、DeepSeek V4 的反击：不只是一张降价牌
面对 Luna 的突袭，DeepSeek 显然早有准备。V4 正式版与其说是一次仓促应对，不如说是提前封装的「反制措施包」被紧急激活。

- **长上下文与 Agent 能力显性化**  
  V4 官方放出的 benchmark 中，1M 上下文的困惑度漂移几乎为零，并且在工具调用（Function Calling）准确率上相较 V3 提升了 22%。这直接指向一个信号：DeepSeek 不想在纯语言理解的价格泥潭里纠缠，而是把战场拉向「AI 自己能干活」的 Agent 框架。
- **多模态路线的「补课」**  
  此次 V4 首次在开源许可下放出 6B 和 30B 两个原生视觉分支，支持任意分辨率图像输入，且视觉编码器与语言主干深度融合。对开发者而言，一套 API 即可完成「看图说话 + 推理」的闭环，不再需要额外串联 OCR 或 ViT。
- **本地部署的极致友好度**  
  配合 llamafile 一键包、GGUF 量化版本及单卡 A10 可跑的蒸馏版，V4 继续强调「离线可用」。在数据合规严格的金融、政务领域，这是 Luna 乃至任何 SaaS 服务难以替代的护城河。



## 四、廉价推理时代，开发者该怎么思考？
API 价格竞赛越是眼花缭乱，越需要冷静的工程判断。以下三条建议，来自龙虾哥亲眼目睹的一线踩坑实录：

1. **不要只看单价，算清 Total Cost of Ownership（TCO）**  
   输入再便宜，如果你的 prompt 范式要求反复传递巨量上下文（如 full-document RAG），每秒延迟和重试成本可能远比单 token 费用更致命。判断公式应该是：  
   `TCO = (token 费 × 总量) + (时延 × 并发 × 人工等待成本) + 切换模型的重构成本`。
2. **锁定效应是新战场，保持架构弹性**  
   一旦应用深度绑定某家的 Function Calling 格式、扩展字段或微调 API，未来迁移的代价会极其高昂。建议在 LangChain、LlamaIndex 等中间层的抽象之上再封装一层内部适配器，确保模型替换时业务代码改动最小化。
3. **安全性 & 合规永远不在「便宜」范围内**  
   如果你所在行业的数据不能出境、不能脱离专有硬件，那么类似 Luna 这样的云端 API 再便宜也是镜花水月。此时 V4 的本地部署能力，或者至少支持 VPC 实例的私有化版本，才是有意义的候选。

尾声里说句虾仁诛心的大实话：当模型性能逐渐趋同，推理定价的底线会被不断击穿，未来决定竞争的或许不再是「更聪明」，而是「更便宜、更稳定、更少坑」。对开发者而言，这恰恰是最好的时代——因为算力的话语权，终于开始真正交到建设者手中。
