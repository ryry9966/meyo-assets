## 背景：Agent 越强，越需要“懂你”

随着 OpenClaw、MCP 插件、多工具链编排的成熟，助手不再只是单轮对话的聊天窗口。它可以读取你的本地文件、操作代码仓库、查阅知识库、调用数十个工具来完成一项任务。但问题也随之而来：助手对你的工作习惯、项目结构、偏好和约束几乎一无所知，每一轮对话都要重新交代上下文，效率极低，输出也常偏离预期。

在现实生活中，我们通过“README.md”让协作者快速了解项目；在人与助手的协作中，同样需要一份“用户手册”来让 Agent 了解你的背景、行为方式与边界。于是 **USER.md** 这个概念开始出现：它是一份由你维护、由助手在会话中自动加载的上下文文件，相当于给你的 AI 助手一个“用户画像”。

## 问题：没有 USER.md 时，Agent 踩过的坑

在没有 USER.md 的情况下，我曾遇到几类高频故障：

1. **代码风格反复横跳**：助手有时用 TypeScript 严格模式，有时又换成宽松的 any 类型，只因它不记得我的默认配置。
2. **路径假设错误**：助手猜测项目路径为 `/src`，实际我的 monorepo 里真正的工作区是 `/packages/agent`。
3. **工具选择失当**：我偏好在本地用 Docker Compose 启动服务，它却总是建议用 systemd 或直接裸跑进程。
4. **越权操作风险**：助手热情地建议我 `sudo rm -rf` 清理缓存，却不知道我操作系统上有隔离环境限制。

这些问题本质上不是模型能力不足，而是**缺乏持续可用的用户侧上下文**。让模型每次都从零推理你的背景，既浪费 token，也增加出错概率。

## 做法：从零搭建一份可被 Agent 消费的 USER.md

我采用的做法是：使用 OpenClaw 的 Custom Instructions 或项目级 `AGENTS.md`/`USER.md` 机制，将用户画像注入每次对话。以下是实践步骤：

### 1. 确定存放位置和加载方式
- 如果助手支持项目级上下文（如 OpenClaw 的 `AGENTS.md`、项目根目录下的 `.claw/user.md`），直接放入对应路径。
- 如果不支持自动加载，可以利用 MCP 工具或自定义插件在会话开始时通过 prompt 拼接注入。也可用系统 prompt 模板在客户端手动添加。

### 2. USER.md 的内容结构

一份可维护的 USER.md 应包含以下模块（可根据实际情况裁剪）：

```markdown
# USER.md — 个人/项目助手上下文

## 关于我
- 角色：全栈开发者，负责 Agent 和基础设施
- 常用语言：TypeScript（优先）、Python、Shell
- 操作系统：macOS + Ubuntu 22.04 开发机
- 编辑器和终端：VSCode、zsh

## 项目工作区
- 当前项目路径：~/workspace/openclaw-core
- Monorepo 结构：packages/agent, packages/tools, packages/ui
- 构建工具：pnpm + turbo

## 偏好和默认规则
- 代码风格：严格模式 TypeScript，无 any，eslint-config-strict
- 测试框架：vitest
- 服务启动方式：docker compose up -d
- 版本控制：遵循 conventional commits

## 约束与禁止行为
- 禁止删除 ~/Documents 外的任何文件
- 禁止未经确认执行 sudo 命令
- 敏感信息勿写入日志或公开文件

## 常驻工具和插件
- MCP 工具：filesystem, github, postgres
- 自定义脚本：~/scripts/health-check.sh
```

### 3. 验证 Agent 是否“读懂了”

写完后，可以向助手提问以验证：

- “请根据我的 USER.md 告诉我，我的主开发语言是什么？”
- “如果我要启动后端服务，你应该如何操作？”
- “如果我说‘清理缓存’，你会执行什么命令？”

助手若无法正确回答，排查方向通常为：文件路径未被正确加载；文件中存在特殊字符导致截断；或指令优先级被其他 prompt 覆盖。

## 踩坑点

1. **文件过长导致注入失败**  
   USER.md 超过 2000 行时，有些实现会截断或干脆跳过。建议控制在 300 行以内，可以用链接引用详细文档。

2. **敏感信息泄露**  
   不要将 API KEY、密码等写入 USER.md。如果必须包含，使用环境变量占位符（`$SECRET`），由运行时注入。

3. **未区分个人和项目上下文**  
   个人习惯与项目规则应在不同文件中管理。我在家目录放 `~/.claw/user.md` 存放通用偏好，在项目根目录放 `AGENTS.md` 存放项目特定规则，避免混在一起难以维护。

4. **Agent 无视指令**  
   当系统 prompt 中已有较强约束时，USER.md 中的请求可能被压制。需要调整优先级，例如在插件中将 USER.md 放在指令最前面或最后面，取决于模型的注意力机制，并通过实验确定。

## 可复用建议

- **分层上下文**：将 USER.md 拆分为 `user-profile.md`（通用）、`project-rules.md`（项目规则）、`session-preferences.md`（临时覆盖）。由 Agent 插件按优先级拼接。
- **模板化生成**：写一个小脚本用 `whoami`、`git config`、项目结构自动生成 USER.md 骨架，减少手动维护成本。
- **定期清洗**：每季度检查一次 USER.md，删除已过时的规则，避免给助手传递矛盾信号。
- **团队场景**：如果是团队共用某个 Agent，建议将 USER.md 替换为 `TEAM.md`，个人差异再通过 `USER.md` 叠加。这样不至于让每个协作者都被迫适应同一个上下文。

## 总结

给 AI 助手一份精心维护的 USER.md，相当于在每一次协作开始前花 30 秒对齐期望，却能省下无数个“我不是这个意思”的修正对话。它不是一个技术奇迹，而是一个工程习惯：把你自己当成一个需要文档化的系统，把“你如何工作”准确地告诉另一个系统。

目前 OpenClaw 生态对 USER.md 的支持正在变得更原生。未来，Agent 甚至可以根据你的 USER.md 自动调整 tool 调用策略、输出风格和安全边界。而在这之前，先把你的第一份 USER.md 写好并放到正确的位置，就是务实的开始。
