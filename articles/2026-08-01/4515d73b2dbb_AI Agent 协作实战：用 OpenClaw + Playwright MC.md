## 背景

端到端（E2E）测试是保障应用链路完整的最后一道防线，但它的编写与维护成本一直是团队的痛点。UI 每改动一点，定位器就可能失效；新增一个业务分支，测试脚本就得手工补齐等待、断言、数据清理——这些重复性工作既耗人力，又容易引入疏漏。

随着 LLM 推理能力提升，以及 Agent 框架（如 OpenClaw）与 MCP 协议的成熟，“让 AI 写测试”不再是空洞的口号。通过多 Agent 协作，我们可以让规划、编码、验证三个环节各司其职，结合 Playwright MCP 的真实浏览器操控能力，构建一套可工作、可演进、可内省的自动化测试生成流程。这篇文章记录我们的一次工程化尝试，包含完整步骤、踩坑点和可复用建议。

## 问题拆解

简单的“给 Prompt 让 AI 吐代码”在生产环境中并不可靠。典型问题包括：

- 选择器脆弱：AI 偏好 `text=登录` 或深层嵌套 XPath，页面微调即告崩溃。
- 等待机制缺失：动态渲染、接口延迟常被忽略，导致时序型失败。
- 断言空泛：只检查“页面包含 xx 文本”，遗漏状态码、接口返回、数据一致性等关键验证。
- 无自我修复能力：失败后仍需人工定位根因、手动改写代码。

我们需要一套闭环流程，让 Agent 能主动探索页面、生成高可维护性代码，并在失败时获取 DOM 信息进行修复，最终输出经人类审核的可靠用例。

## 方案与步骤

### 1. 环境准备：OpenClaw + Playwright MCP

- 安装 OpenClaw 框架，并启用多 Agent 协作模块。
- 部署 Playwright MCP Server，暴露浏览器操作工具（导航、点击、键入、截图、获取 DOM 等）。
- 在 OpenClaw 中注册三个 Agent：
  - **Planner**：负责分析需求、探索页面、生成测试步骤。
  - **Coder**：将步骤转化为 Playwright 脚本，遵守编码规范。
  - **Validator**：执行脚本，分析失败原因，驱动修复循环。

每个 Agent 连接同一个 Playwright MCP Server，可实现浏览器会话的复用与上下文传递。

### 2. 工作流设计

以“登录功能”为例，完整流程如下：

1. **需求输入**  
   用户提供被测页面 URL，以及自然语言测试目标：
   ```
   测试登录功能，包括：正确账号密码登录成功、错误密码提示、空提交校验。
   ```

2. **Planner 探索与规划**  
   - 使用 MCP 工具打开登录页，提取表单元素、按钮属性。
   - 生成步骤列表，例如：
     ```
     1. 打开 /login
     2. 输入正确邮箱和密码，点击登录，验证跳转到 /dashboard 且页面包含用户名
     3. 输入错误密码，验证出现错误提示“密码错误”
     ```
   - 特别指令：检查元素是否已有 `data-testid`，若缺失则建议开发者补充，暂用稳定 ID 回退。

3. **Coder 生成脚本**  
   - 接收 Planner 给出的步骤，生成 Playwright 代码，约束规则包括：
     - 定位器优先 `data-testid` → `id` → `aria-label`。
     - 执行动作前强制 `waitForSelector` 或 `waitForLoadState`。
     - 断言需包含 URL、关键 UI 元素、API 响应状态（通过 `page.waitForResponse`）。
   - 每生成一个用例，立即通过 MCP 执行初步语法检查。

4. **Validator 执行与修复循环**  
   - 运行生成的测试脚本，若全部通过则标记为待审核；若失败则捕获堆栈、截图、DOM 快照。
   - 解析失败类型（定位器未找到、超时、断言不匹配），通过 MCP 查询当前页面实际的 DOM 结构，生成修正建议（如替换选择器、增加等待）。
   - 将修正建议发回 Coder 重生代码，重新验证，直到通过或达到最大重试次数（通常设为 3 次）。

5. **人工审核**  
   所有自动生成的用例最终进入代码仓库 PR，团队成员重点检查：
   - 业务断言是否正确（AI 偶尔会产生“幻觉断言”）。
   - 是否引入了不合理的外部服务依赖。
   - 关键操作是否具备幂等性（如数据清理）。

## 实际踩坑点

- **MCP 连接安全性**  
  Playwright MCP 在 CI 容器中运行时，需开启 `--no-sandbox` 并限制 Agent 可访问的域名白名单，避免误触外部链接导致策略违规。

- **Agent 对复杂 DOM 的过拟合**  
  对于动态加载的表格或列表，Agent 极易生成基于 `nth-child` 的定位器。解决方法是在规划阶段由 Planner 识别数据结构，生成“获取所有行，遍历匹配特定条件”的语义步骤，而非直接锁定索引。

- **修复循环失控**  
  当页面频繁变更（如 A/B 测试）时，Validator 可能不断生成补丁却始终过不了。需设置严格的重试上限，并记录每次修复的 diff，便于人工快速归因。

- **上下文窗口溢出**  
  大型页面 DOM 直接塞进 Prompt 会超出 token 限制。我们限制 Planner 仅获取 `<main>` 区域的结构摘要，并用结构化 JSON 表示可交互元素，降低噪声。

## 可复用建议

1. **沉淀测试知识库**  
   将团队的测试规范（命名、目录结构、登录态复用方式）写成 Markdown 文件，作为系统提示注入给 Coder Agent，保证输出风格一致。

2. **封装高频操作为 MCP 工具**  
   如果“登录”“清理购物车”等流程在多个测试中出现，应编写专用 MCP 工具函数，让 Agent 直接调用而非每次重新生成，减少出错概率。

3. **渐进式落地**  
   先选择一个 API 较少变动、页面相对静态的模块试点（如注册/登录页），跑通修复循环并积累经验后，再推广到复杂业务页面。

4. **保留人类检查门禁**  
   至少对断言部分和新增的定位器进行人工抽查，防止 AI 生成虽“通过”但毫无价值的假验证（如 `expect(true).toBe(true)`）。

## 总结

用 OpenClaw 的多 Agent 协作 + Playwright MCP 实现 E2E 测试的半自动化生成，已在我们的内部项目中产生了可度量的收益：登录、注册等标准流程的测试编写时间从小时级缩短到分钟级。但它远非银弹——面对复杂交互和频繁变更的页面，仍需人工介入优化。建议团队将这一流程定位为“增强而非替代”，把机械性工作交给 Agent，保留人对业务正确性的最终判断。
