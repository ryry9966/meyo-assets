# AI 助手的 heartbeat 设计：轮询 vs 推送的工程化取舍

## 为什么心跳会成为一个问题

当你开始用 MCP 把多个 Agent 或插件串成一条自动化流水线时，很快就会遇到一个实际问题：**如何判断某个对端是否还活着？**

在单机脚本里，我们习惯了直接调函数。一旦进程分开、网络介入，就需要一种探活机制——也就是心跳。这玩意儿看起来就是定时发个包或查一下状态，但在 Agent 协作场景里，不同方案带来的延迟、资源消耗、误判风险差异巨大，选错之后排查问题就像在抓鬼。

本文基于我们在 OpenClaw 插件体系中的实践，梳理轮询与推送两种思路的真实取舍，并给出一种在生产中跑过一段时间的折中方案。

## 轮询：看起来直白，规模上去就头疼

最朴素的做法是，中心调度器每隔 N 秒，向每个已注册的 Agent 或插件发一次 HTTP 健康检查请求（比如 `/health`），返回 200 就算活着。

**优点**：
- 实现成本极低，一个定时器加 HTTP 客户端就能搞定。
- 无需 Agent 主动配合，对无状态微服务很友好。

**工程中吃过的亏**：
1. **检查风暴**：当 Agent 实例数从个位数涨到上百个，中心调度器每秒需要发出的 HTTP 请求数会急剧上升。即便用协程并发，也会明显拉高调度器自身的 CPU 和端口占用。
2. **假活陷阱**：Agent 进程的主循环可能已经卡死，但 HTTP 服务框架仍在正常工作，健康端点照样返回 200。这种“半死不活”靠简单轮询根本发现不了。
3. **延迟与负载的跷跷板**：想把故障发现延迟压到 3 秒以内，就得把轮询间隔设到 1-2 秒，这会让负载问题雪上加霜。放宽到 10 秒，问题发现又太慢。

因此，纯轮询在 Agent 数量少、对延迟不敏感的 MVP 阶段能用，但扩大规模后必须调整。

## 推送：实时，但要管好连接

推送模式通常借助 WebSocket、gRPC 长连接或 MQTT 实现：Agent 定期向中心发送心跳包，中心根据最后一次心跳到达时间判断存活。

**优点**：
- 故障发现延迟低，可做到秒级甚至亚秒级。
- 不需要中心主动扫描所有节点，负载更均衡。

**实际踩坑点**：
- **断线重连的轰炸**：网络闪断时，大量 Agent 同时重连，如果没做好指数退避和 jitter，瞬间就会把中心打崩。
- **超时阈值不好定**：心跳间隔 5 秒，超时设 15 秒？在某次网络抖动中可能连续丢三个包，导致大面积误判死亡，引发无谓的故障转移。
- **双向耦合**：中心必须保持与每个 Agent 的长连接，服务端资源（文件描述符、内存）随 Agent 数线性增长。如果中心本身要做高可用，连接迁移又是另一坨复杂度。

## 我们的折中：基于 Redis 的“主动上报 + 惰性检查”

在多次被长连接重连搞得半夜起来修生产之后，我们转向了一种解耦更彻底的模式：**Agent 主动写心跳，中心端只在需要时查**。具体做法依赖 Redis 的 `SETEX`（或 `SET ... EX`） 创建一个带 TTL 的键。

### 步骤

1. **Agent 侧**：每隔固定间隔（如 5 秒）执行一次：
   ```
   SETEX agent:heartbeat:<instance_id> 10 1
   ```
   键的 TTL 设为心跳间隔的 2 倍（10 秒）。写操作可以由一个独立 goroutine/线程执行，与主业务逻辑隔离。

2. **中心侧（或被调用方）**：当需要判断某个 Agent 是否存活时，直接 `GET agent:heartbeat:<instance_id>`。如果键存在，说明该实例在最近 10 秒内上报过；不存在则视为死亡（或进入可疑状态）。

3. **即时故障感知**：如果不想等待中心主动查询，可以订阅 Redis 的 `__keyevent@0__:expired` 频道，在键过期时立即触发回收或告警逻辑。注意启用键空间通知会额外消耗一些 Redis 性能，按需开启。

### 为什么这比纯轮询和纯推送更合适？

- **无连接耦合**：Agent 和中心不直接相连，任何一方重启、扩缩容都不影响心跳通道。
- **查询成本恒定**：中心不需要遍历所有实例，只需在有调度任务时才判断目标 Agent 是否存活，避免无意义的扫描开销。
- **天然防止假死**：因为 Redis 键的 TTL 由 Agent 主动续期，一旦 Agent 的监控协程卡死，键就会过期，中心会立刻感知。

## 那些让方案更“抗造”的细节

1. **实例唯一标识**：必须使用 `instance_id` 区分同一 Agent 的不同部署，否则两个同配置实例互相覆盖心跳键，会造成“永远活着”的假象。我们直接使用 pod name 或 hostname + PID 组合。

2. **业务假死检测**：心跳协程可以在写 Redis 之前，检查一个由主业务循环定期刷新的原子变量（如最近一次任务执行的时间戳）。若超过预定阈值，则**主动不续期**，让心跳键自然过期，从而暴露业务卡死。

3. **Redis 降级**：Redis 本身不可用时，可以降级为 Agent 自带的 HTTP `/health` 端点轮询（前提是中心实例数不多），或临时写入本地文件，人工介入。我们在 SLA 中明确定义了 Redis 依赖，接受这一风险。

4. **TTL 的抖动**：为了避免多个 Agent 同时写 Redis 造成的毛刺，我们在心跳间隔上加了 ±500ms 的随机抖动，平摊压力。

## 可复用的建议

- **延迟优先级**：如果业务要求 3 秒内必须发现故障，直接上 WebSocket 推送，但同时做好重连退避和连接数监控。
- **规模与资源**：Agent 实例数超过 50 以上，强烈建议用 Redis / etcd 这类外置存储解耦，中心不再做主动轮询。
- **与现有基础设施对齐**：如果团队已经维护着 Consul 或 etcd，可以复用其健康检查与 TTL 机制，避免引入新的依赖。
- **永远不要只依赖单一信号**：将心跳与任务执行的超时信号结合使用，才能更全面地判决一个 Agent 是否“可用”。

## 总结

轮询和推送不是非黑即白的选择。在 Agent 自动化的工程实践中，真正好用的 heartbeat 设计往往是一种“混合制品”：Agent 主动上报存活信息，中心按需惰性检查，中间靠类似 Redis TTL 的机制自动过期。这种方案既规避了检查风暴，又躲开了长连接维护的坑，在大量实际场景中比两头极端的方案更经得起折腾。

下次你在写 Agent 健康监控的时候，不妨先从“写一个会过期的键”开始，而不是上来就拉 WebSocket 连接。
