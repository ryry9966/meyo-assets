# 当 AI 有了可进化的身份文件：OpenClaw 的 IDENTITY.md 实践与避坑

## 背景

在搭建基于 OpenClaw 的 Agent 或自动化机器人时，很多人习惯把“角色设定”硬编码在代码里，或者写几行 system prompt 丢进配置。项目稍微长大一点，就会暴露三个典型问题：

- **调整一个角色指令，你必须改源码或翻十几层配置文件**，牵一发动全身；
- **切换不同的 Agent 身份时，很难做到环境隔离**，上一轮的残留记忆经常串场；
- **AI 的行为变更没有历史记录**，一旦 Prompt 退化，根本不知道是谁在什么时候改了什么。

在工程化要求更高的场景（多租户 Agent、长周期项目、协同维护的聊天机器人），我们需要把 AI 的“身份”当成一项可独立维护、可溯源、可进化的 artifact——就像基础设施即代码一样。

OpenClaw 生态里有一项容易被忽略，却很适合做这件事的模式：`IDENTITY.md`。它是用 Markdown 文件定义 Agent 身份、指令、记忆与边界的约定，配合 Git 做了版本化，再把 MCP 或 OpenClaw 的内存插件接进来，最终形成“AI 的进化档案”。

## 问题再聚焦

如果不做结构化身份管理，你会反复踩这些坑：

1. **Prompt 漂移**：每次微调身份描述都直接改字符串，没有 diff 记录，退化后难以回滚。
2. **记忆膨胀**：为了“让 AI 记住上一次对话”，无节制地拼接上下文，迟早爆掉 token 窗口，表现突然变呆。
3. **共享与复用难**：一套身份定义想要给另一个 OpenClaw 实例用，得靠复制粘贴，很容易遗漏关键暗约束。
4. **敏感信息硬编码**：身份文件里直接写了 API key 或内部系统提示，历史提交中永远留下痕迹。

`IDENTITY.md` 不是银弹，但它提供了一条**显式的工程路径**——把身份从隐性上下文中剥离，变成可审查、可测试、可复用的文件。

## 做法与步骤

### 1. 约定文件结构
在 OpenClaw 项目的根目录（或专用 `profiles/` 文件夹）创建 `IDENTITY.md`，使用 YAML front matter 叠加 Markdown：

```markdown
---
name: ops-assistant
version: 1.2.0
created: 2025-02-06
core_instruction: "你是一个站点可靠性工程师，使用 SRE 方法论回答问题"
tools: [GitHub, PagerDuty, Runbook]
---

# 身份画像
…

## 行为准则
…

## 记忆
（该区域由 Agent 在对话结束后自动更新，保留最近关键信息）
```

这样做的好处：**元数据可直接被 OpenClaw 的插件解析**，不需要额外映射；记忆区用明确的 `## 记忆` 标题，方便脚本抓取和截断。

### 2. 通过 MCP 或自定义插件动态加载/持久化
在 OpenClaw 启动时，可以用一个 MCP 服务（Memory Context Protocol）读取 `IDENTITY.md`，追加到 system prompt；在会话结束时，从 Agent 的总结结果中写入 `## 记忆` 区域，并执行一次 Git 提交。实现原则：

- 只让 Agent 更新 **受控的记忆区**，而不是整篇文档；
- 写入时做 token 核算，超过阈值自动触发摘要再写入；
- 所有变更通过 Git 记录，commit message 带上时间戳与摘要长度。

### 3. Git 驱动的版本进化
`IDENTITY.md` 纳入版本控制，每次记忆写入或人工调整时生成一次 commit。这样你可以：

- 通过 `git log -- IDENTITY.md` 回溯每一次身份变化；
- 给重大行为变更打 tag（例如 `v1.2.0`），与行为测试对应；
- 在 CI 中快速检出旧版本身份，用 promptfoo 等工具对比两个版本的行为差异。

### 4. 敏感信息与变量分离
绝不要将 API 密钥、内部 IP 等直接放进 `IDENTITY.md`。使用 OpenClaw 的环境变量替换机制，例如 `${GITHUB_TOKEN}`，或通过插件在加载时注入 secrets。这样文件本身保持纯配置，可以安全地分发和公开审计。

## 踩坑点

### 记忆膨胀导致的上下文溢出
最常见的问题：Agent 持续往 `## 记忆` 写入小作文，几个月后整个 identity 文件突破 8000 token，system prompt 就把窗口吃光。解决办法：

- 维护一个 **最大 token 预算**（比如记忆区不超过 1200 token）；
- 用轻量摘要脚本定期（或每次写入前）将旧记忆压缩为 3～5 条要点；
- 抽象出“长期记忆”（关键偏好、长期知识）和“短期记忆”（最近几次会话细节），二者分开管理。

### Git 自动提交产生噪音
记忆更新非常频繁时，Git log 会迅速膨胀，干扰真实的人工修改追踪。我们建议：

- 将所有自动写入记忆的 commit 打上 `[bot]` 前缀或使用单独分支；
- 只在**达到具体条件**（如记忆区变化超过 5%）时才合并到主分支；
- 使用 pre-commit 钩子保证文件格式正确，避免 Agent 写出损坏的 YAML。

### 多实例并发写入的竞争
如果一个 OpenClaw 集群共享同一个 `IDENTITY.md` 文件（例如通过 Git 仓库同步），可能出现两个实例同时写入记忆导致冲突。工程上的解法：

- 将记忆后移至外部数据库（PG/SQLite），`IDENTITY.md` 仅存放冷启动的基线；
- 或使用文件锁，强制同一时刻只有一个 Writer，并构建自动 merge 策略。

## 可复用建议

- **建立模板库**：把经过验证的身份结构抽象为 `template/base.md`，新项目直接 Fork 并修改；
- **加入行为回归测试**：对于核心 Agent，在 CI 中跑一组固定对话用例，检查回答是否依然符合约束，一旦身份退化立刻报警；
- **记忆维护脚本**：编写一个简单的 Python/Node 脚本，定时分析 `## 记忆` 区的 token 数，超过上限自动触发压缩，可作为 cron 或 pre-commit 钩子；
- **语义化版本**：当身份定义发生会改变外部行为的修改（如增加严苛限制、改变语气风格）时，升级主版本号，其他人引入时可以清楚感知风险。

## 总结

`IDENTITY.md` 的出现，把 AI 身份从粘在代码和 prompt 里的一次性贴纸，变成了一个**可进化的独立制品**。它让你可以用代码化的方式管理 Agent 的“人设”，用 Git 追踪演进历史，通过 MCP 实现运行时读写，再加上自动化测试和记忆截断，整个组合为严肃的 AI 协作项目提供了一套低摩擦的工程基线。

如果你已经在用 OpenClaw 跑自动化或 Agent，给每个机器人配上这样一个可进化的身份文件，是成本极低但收益极高的工程选择。
