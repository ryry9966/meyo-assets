# Web Scraping 稽客：让 OpenClaw Agent 安全地采集网页内容

## 背景：Automation Agent 的采集困境

在 OpenClaw 体系里，Agent 常常需要实时采集网页作为决策依据——汇总新闻、抓取 API 文档、监控竞品页面。但“能爬”和“安全地爬”是完全两件事。很多 Agent 在原型阶段直接用 requests + BeautifulSoup 怼目标，上线后立刻遇到三类问题：

1. **合规风险**：忽略 robots.txt、忽略服务条款，甚至误爬内部系统。
2. **反爬对抗**：缺少频率控制、固定 User-Agent 导致 IP 被封。
3. **数据污染**：未校验内容直接把广告、跟踪脚本、用户隐私字段喂给 LLM。

这些问题在 Agent 被赋予“自动决定爬取什么”的能力后会被放大：MCP 工具调用可以实现任意 URL 的采集，但如果没有一套边界规则，Agent 就像没有刹车的高速赛车。“稽客”的理念正是为此而生——**在 Agent 与目标站点之间建立一条可审计、可约束、可自愈的采集管道**。

## 核心问题：Agent 天生不理会网页采集的边界

通常开发者会写一个 `fetch_url` 的 MCP 工具，Agent 传入 URL 和选择器，返回页面文本。这看似灵活，但 Agent 的推理性会让它自作主张：

- 根据页面上的链接递归爬取，可能触及管理后台。
- 在短时间内大量请求，触达站点的速率阈值。
- 使用默认 Python 请求头，被 WAF 直接丢弃。

根本原因是缺少一个**面向 Agent 的采集策略执行器**，这个执行器不是简单地发送 HTTP 请求，而是为每一次采集行为评估风险、遵守约定、保留证据。

## 实践：为 Agent 构建安全的网页采集管线

我们以 OpenClaw 环境下的一个 MCP 工具模块为例，给出可落地的四步设计。技术栈使用 `httpx`、`robotparser`、`selectolax`，配合自定义的审计日志。

### 1. 采集策略声明

在 Agent 连接工具时，先注入一段强制策略 Prompt，示例：

> 你可以使用 `safe_fetch` 工具获取网页内容。仅限爬取公开页面，遵循 robots.txt。单个域名每分钟不超过 10 次请求，同一页面 5 分钟内不重复请求。禁止爬取用户评论区、登录页面及任何包含 `admin` 路径的 URL。

同时，在工具侧将策略参数化，例如：

```python
POLICY = {
    "max_rpm": 10,
    "cache_ttl": 300,
    "blocked_paths": ["/admin", "/wp-login", "/user"],
    "allowed_domains": None,  # None 表示任意公开域名
    "respect_robots": True
}
```

这样策略可审计、可调整，也便于团队在合规审查时提供证据。

### 2. 请求前的合规过滤器（稽客核心）

对于 Agent 传入的目标 URL，工具必须执行前置检查：

- **域名解析与黑名单**：对 IP 地址类 URL 直接拒绝，避免访问内网地址。
- **robots.txt 校验**：使用标准库 `urllib.robotparser` 下载并缓存解析结果，检查 `User-Agent` 为自定义名称（例如 `OpenClawAgent/1.0`）时的路径权限。注意部分站点 robots.txt 可能较大或不存在，需设置 2 秒超时和 7 天缓存。
- **路径模式匹配**：检查 URL 路径中是否包含 `blocked_paths` 中的片段，以及判断是否为登录、注销、购物车等功能性页面。采用简单的关键字匹配 + URL 参数解析，避免正则误伤。
- **频率控制**：为每个域名维护一个时间窗口令牌桶，使用 Redis 或内存字典实现。若当前窗口内已达 `max_rpm`，工具应返回特定错误信息（如“rate_limited”），并建议 Agent 稍后重试，而不是直接丢弃请求。这能让 Agent 自行调整任务顺序。

### 3. 请求时的身份管理与内容清洗

请求发送阶段：

- **User-Agent 与请求头**：设置真实的产品化 UA，同时允许 Agent 模拟不同设备？不推荐。保持一致的 UA 更易遵守 robots.txt，也便于网站运营方识别与联系。可增加 `From` 头部，填入运维邮箱。
- **追踪用途 Header**：附加 `X-Request-Purpose: automated-research` 之类的自定义头，虽然不是标准，但不少 CDN 会记录，有助于被误拦时沟通。
- **内容清洗**：拿到 HTML 后，先去除 `<script>`、`<style>`、`<noscript>`、`<iframe>` 等元素，然后使用 selectolax 的 CSS 选择器或按语义标签提取正文。**关键步骤**：检查提取内容中是否意外包含 email、手机号等 PII（可维护一个正则清单），若检测到则截断并记录日志，不返回给 LLM。

### 4. 响应缓存与审计日志

对成功提取的页面内容进行哈希，存入本地 SQLite 缓存，TTL 300 秒。相同 URL 再次请求时，直接返回缓存内容，减轻目标站点压力。同时，每次采集记录审计日志，包含：时间戳、请求 URL、是否命中缓存、响应状态码、采集字节数、是否受限、使用的策略版本。这些日志在排查 Agent 异常行为时价值巨大。

## 踩坑记录

- **robots.txt 解析不严谨**：`urllib.robotparser` 默认不处理 `Crawl-delay` 指令，如需严格限制频率，需自行解析该字段并与令牌桶联动。另外，某些站点返回 403 时，标准库会直接抛出异常，需捕获并视为全站禁止。
- **动态页面强行静态采集**：Agent 传入的 URL 可能是 React 渲染的页面，仅返回空壳。此时不能盲目引入 headless 浏览器，因为会大幅增加资源消耗和反爬风险。建议工具明确指出仅支持静态 HTML，让 Agent 调用者自行处理，或者针对特定白名单站点开启 Playwright 渲染，但作为单独权限授予。
- **令牌桶实现的时间精度**：使用秒级时间戳在高并发下可能放行超出配额，改用毫秒级窗口或漏桶算法更可靠。
- **URL 规范化**：带 tracking 参数的同一页面会被视为不同 URL，导致缓存失效和重复请求。务必实现去除 utm_、fbclid 等无用查询参数的规范化函数。
- **内部工具误伤**：如果企业内部 Wiki 需要采集，`allowed_domains` 需要灵活配置，但不能让 Agent 动态修改策略。通过环境变量注入白名单是更安全的做法。

## 可复用建议

- **将采集策略外部化为配置文件或 MCP 服务**，不要让策略散落于 Agent Prompt 中。策略变更时可立即生效，且能统一为多个 Agent 提供一致约束。
- **为 OpenClaw 社区提供可插拔的稽客引擎**，开发者只需要实现一个符合 MCP 规范的 `safe_web_fetch` 工具，就能让所有兼容 Agent 享受到安全爬取能力。
- **定期审计爬取日志**，建立异常告警规则，例如单 IP 突然遭遇大量 403/429，或缓存命中率骤降，这些往往是站点更改反爬策略或工具缺陷的信号。
- **公开告知用途**：在 User-Agent 和 `From` 中提供联系方式，不但降低被封概率，也为可能的误爬提供了沟通窗口。真实工程中，这比任何技术对抗都有效。

## 总结

Web scraping 稽客不是限制 Agent 的能力，而是为 Agent 的自动化行为定义一个合法的、可预期的边界。在 OpenClaw 生态中，Agent 越自主，采集管的约束就要越显性。通过策略前置、合规过滤、身份管理与审计日志的四层防线，我们能让 Agent 安全地利用整个开放的 Web，同时把法律风险、目标站点负担和系统维护成本控制在可接受范围内。这套小框架已经在内部几个监控类、汇总类 Agent 中稳定运行了数月，日均处理数千页面，仅触发过一次 429 警报——那次因为运维忘记更新 robots.txt 缓存。希望这个经验对同样在踩坑的社区同学有帮助。
