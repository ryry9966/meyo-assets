# AI Agent 权限边界：何时自主执行，何时必须确认

## 背景

在 OpenClaw + MCP 的自动化实践中，Agent 正从“对话体”进化为“执行体”。它可以读取文件、操控浏览器、发送网络请求、操作数据库，甚至修改系统配置。每一次工具调用背后，都是一个需要被评估风险的决策：**是全自动执行，还是先问过人类？**

过去我们写脚本，权限边界体现在代码逻辑里；现在 Agent 根据自然语言指令动态组合工具，边界变得模糊。如果在电话拨打、仓库删除、生产环境部署等操作上没有明确的“人类确认点”，一次误判就会变成事故。

这篇文章不讨论理论上的 AI 安全，而是从工程实操出发，梳理一套可落地的权限分级与审批策略，帮助你在 OpenClaw 和 MCP 工具链里构建可控的自动化。

## 问题：完全自主与反复确认之间的困境

常见的两种极端：

1. **无限制自主**：Agent 能直接执行任何工具，老板一句“帮我清理硬盘”可能触发删除关键文件。
2. **过度确认**：每一步操作都要弹窗确认，用户点得手麻，自动化形同虚设。

真正需要的是**风险感知的权限模型**：Agent 能看到一个动作可能造成的后果，再决定是自己干，还是拉人审核。

在 MCP 工具定义里，很多 Server 只是暴露了功能，并没有风险标定。例如 `filesystem` 工具中 `read_file` 和 `delete_file` 混在一起，Agent 没有能力自行区分。此时，我们需要在 Agent 与工具之间，增加一层**权限执行网关**。

## 做法：三层权限与决策引擎

### 1. 定义风险等级

为每一个 MCP 工具调用（或工具 + 参数组合）划分风险等级：

| 风险等级 | 典型操作 | 策略 |
|-----------|----------|------|
| **低风险** | 只读查询：读文件、搜索、查看日志、获取 API 数据 | 自动执行，记录日志 |
| **中风险** | 可逆写操作：创建文件、发送消息、新增评论、编辑草稿 | 自动执行 + 异步通知，保留回滚能力 |
| **高风险** | 不可逆或影响面大的操作：删除、格式化、付款、部署、修改权限、向客户发送邮件 | 必须同步确认，人类批准后执行 |

对 MCP 工具，可以在工具 name 或 description 中增加风险标记，或者在 OpenClaw 的工具调用层封装一层“风险修饰器”。

### 2. 实现审批网关

在 OpenClow 的插件体系中，可以利用 `before_tool_call` 钩子拦截工具调用，做如下判断：

- 若风险等级为 `low`，直接放行；
- 若 `medium`，放行同时向人类发一条提示消息（如 Slack 通知），并提供撤销入口；
- 若 `high`，**阻塞执行**，向人类发出审批请求，附带完整的参数、上下文和影响评估。

审批请求不应只是“是否允许？”，而应让人类快速理解 Agent 想做什么。可以附带：触发对话摘要、目标工具及参数、风险原因、预估影响范围（如将删除的文件数量）。

### 3. 借助 AskUser 工具实现“回流”

OpenClaw 生态中常见的 `AskUser` 工具正是权限闸门的直观实现。当一个高风险任务被拆解时，Agent 识别到需要人类定夺，主动调用 `AskUser` 提出问题，例如：

> 我将要删除 /data/cache 下的 120 个文件，总计约 3.2 GB。是否继续？

只有收到明确的“确认”后，Agent 才进入下一个工具调用阶段。这比硬性的权限规则更灵活，也让人类保持在决策回路中。

### 4. 把决策权交给人类，把执行留给 Agent

对于常见的高风险场景（如发布上线），可以把 Agent 的角色定义为“执行准备 + 待确认”，而非“全权执行”。流程如下：

1. Agent 完成所有准备工作（构建、测试、生成变更清单）
2. 汇总成检查清单并输出
3. 人类确认：“执行清单里的 4 个步骤”
4. Agent 按清单逐项执行，每一步后报告状态

这种模式既保证了自动化效率，又将关键判断点交还给人类。

## 踩坑点

- **隐性高风险操作**：`mv` 命令看起来只改路径，但如果跨文件系统，等同于复制后删除，可能造成数据丢失。工具封装时需要揭示这类影响。
- **上下文过度自信**：Agent 可能会根据聊天的语气误判，例如用户随口一句“先删了吧”被当作许可。应强制执行审批流程，即使对话中已出现“确认”类词语，也要二次确认。
- **日志不全导致无法回溯**：自动执行的中风险操作必须记录完整的请求参数、时间戳和结果，以便回滚或排查。只记“调用成功”是没有意义的。
- **确认疲劳**：把过多的操作标为高风险，导致用户习惯性“点允许”，最终边界失效。应根据实际使用数据，定期下调那些从未出过问题且影响面可控的操作等级。

## 可复用建议

1. **构建工具风险码表**，作为 MCP Server 开发的一部分，强制标注。
2. **审批请求结构化**：统一包含 `action`, `intent`, `params`, `impact`, `rollback` 字段。
3. **使用渐进放权**：对新 Agent，初始全部高风险操作走审批；稳定运行 N 小时后，可将特定场景降级为中风险。
4. **监控与审计**：所有高风险请求、审批结果、执行结果进审计表，定期出报告，发现异常自动告警。
5. **保留手动接管通道**：即使 Agent 自主执行，也应允许人类打断并收回控制权。

## 总结

AI Agent 的权限边界不是一个技术开关，而是一套设计——需要把风险分级、审批机制、人类决策回路有机结合。在 OpenClaw 与 MCP 的实战中，**低风险自动跑通，中风险边做边看，高风险必须堵在门口**，是经得起折腾的原则。让 Agent 大胆准备、谨慎执行，人类则守住那几个不可逆的关键节点，自动化才能真正走得稳。
