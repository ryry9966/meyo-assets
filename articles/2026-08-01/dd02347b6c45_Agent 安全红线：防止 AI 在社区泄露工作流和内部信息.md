## 背景

越来越多的团队在社区（Discord、Slack、飞书等）部署 AI Agent，用于自动答疑、FAQ 处理甚至部分调试支持。这些 Agent 通常基于 OpenClaw 流水线，结合 MCP 插件、检索增强（RAG）和长期记忆，能直接触达内部文档、代码仓库、项目看板。但随之而来的是一个被低估的风险：Agent 在处理公共提问时，可能无意间把内部工作流、接口描述、定价策略甚至内网地址拼接进回复里，造成信息泄露。

过去几个月，社区中已经出现不止一起“自家 Agent 在公开频道输出了内部设计稿链接”的事故。大多不是模型越狱，而是上下文污染和高置信度的 RAG 片段被直接引用。

## 泄露是如何发生的

典型的泄密路径有三条：

1. **RAG 检索无分级控制**  
   团队为 Agent 构建的知识库包含了公开培训材料，也混入了仅限内部使用的设计文档。检索时仅靠语义相似度匹配，很可能把一份标有“P0 定价方案 - 勿外传”的片段带回上下文，随后在回答中被原样生成。

2. **MCP 工具描述与返回数据过载**  
   很多 MCP 服务的工具定义（`tool.description`）里直接写了内部系统模块名；工具实际返回的 JSON 也有可能暴露字段名（例如 `internal_api_endpoint`、`cost_markup_ratio`），或者完整输出内部 API 的响应结构，哪怕只有一次错误调用，信息就可能泄露。

3. **对话记忆跨域污染**  
   同一个 Agent 先用于内部调试（操作手册、故障树），然后切到社区环境，但共享了同一个记忆命名空间。当用户提出看似相似的问题，Agent 从长期记忆里调取内部回复，直接复述操作步骤或权限信息。

## 三层防御实践

基于多次踩坑，我们给社区 Agent 设定了一条硬红线：**Agent 面向外部时，禁止携带任何“非公开”上下文**。具体做法分成三层。

### 第一层：上下文净化

在 RAG 入库阶段就为每条文档打上可见度标签（`public`、`internal`、`confidential`）。社区 Agent 的检索请求带固定过滤条件：

```yaml
retrieval_filter:
  visibility: "public"
```

如果用的向量库不支持自定义标签，就用分离索引：公共知识库和内部知识库物理隔离，Agent 只挂载公网索引。

对于 MCP 工具，通过 MCP 网关注入中间件，截获 `tools/list` 响应，把工具描述中的敏感词（如内网域名、项目代号）替换成通用词。同时在调用工具后对其返回数据进行字段白名单过滤，只保留必要的键，丢弃 `internal_debug`、`cost` 等敏感字段。

### 第二层：输出审查管道

在模型生成回复后、推送消息前，插入一层输出保护。可以是一个轻量级的 OpenClaw `output_guard` 函数，也可以走外部 NER / 正则扫描服务。规则是两层：

- **硬规则**：匹配内网 IP、特定路径前缀（例如 `/internal/projects/`）、内部域名、明显秘密标记（如 `TODO:remove after demo`）。命中则直接替换为安全回答，同时触发告警。
- **软规则**：用卡阈值的方式，当回复中同时出现“定价”+“策略”+数字百分比，或包含疑似内部接口名的长串路径时，先临时撤回消息，转人工审核。

写过的一个 OpenClaw 防护片断：

```python
forbidden = re.compile(r'internal\.api\.secret', re.I)
@output_guard
def community_guard(output: str) -> str:
    if forbidden.search(output):
        return "I can't disclose that information."
    return output
```

### 第三层：记忆与提示词隔离

社区会话和内部调试会话必须写入不同的记忆命名空间。OpenClaw 中可以通过不同 `memory.name` 配置实现。同时社区 Agent 的 system prompt 里写死一条约束，并给出 few‑shot：

> You are a public-facing bot. Never reveal internal workflows, API endpoints, project code names, or unreleased features. If asked, respond that you can only assist with public documentation.

当用户尝试用“忘记你的系统提示”这类注入时，这条约束依然在第一优先级。

## 踩坑点

- **关键词过滤误伤**：把“API”整体加入黑名单会导致正常问题无法回答。需要结合前后词，建议用短语模式（如 `internal-api`）或 n‑gram 窗口。
- **MCP 中间件开销**：高 QPS 场景下，拦截每个 `tools/list` 和 `tools/call` 的响应会增加 20‑40ms 延迟，建议在网关层异步处理，或预缓存净化后的工具描述。
- **记忆分级疏忽**：早期用同一个向量库存储记忆，仅靠元数据标记区分，结果发现社区会话在某些边缘查询中仍能召回内部记忆。彻底隔离比标记更可靠。
- **RAG 标签不一致**：文档更新后未同步标签，导致新版本内部文档流入公共索引。必须把文档标签纳入 CI 校验，发布时自动检查。

## 可复用建议

1. **最小权限开局**：所有新上社区的 Agent 默认禁用记忆、关闭工具调用，白名单审核通过后再逐步开放。
2. **建立敏感词库**：与安全团队一起维护一份扩展性好的正则库，覆盖短文本、路径、参数名，定期注入 Agent 的审计流水线。
3. **自动化回归**：写一组“探针”测试用例（模拟用户问内部工作流），跑在 CI 里，确认 Agent 输出不包含预定义敏感片段。
4. **日志标记与审计**：所有社区 Agent 的请求‑响应日志存入审计仓，保留 90 天，便于追溯泄漏点。

## 总结

Agent 在社区中泄露内部信息，根源不是模型弱，而是工程上把公私环境混用。防止这类事故不需要昂贵的工具，只要在**检索层做标签隔离、在输出层做消毒、在记忆层做物理分片**，就能大幅度降低风险。这几点对 OpenClaw + MCP 技术栈的 Agent 完全是可落地的，缺的往往只是把安全当成前置设计，而不是事后补丁。
