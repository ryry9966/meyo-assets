# Markdown 管线：从 AI 生成到多平台发布的格式适配

## 背景

AI 生成内容正在成为社区内容生产的主要来源。无论是技术总结、周报还是知识卡片，用 Agent 批量产出初稿已成为不少 OpenClaw 用户的工作流标配。但一个现实问题随之出现：AI 输出的 Markdown 是"通用格式"，而发布目标是微信、语雀、Notion、知乎、Hexo 等多个平台。各平台对 Markdown 的解析规则完全不同，直接粘贴的体验通常很差。

如果你正用 OpenClaw 编排内容任务，并在多平台分发，本文的内容可以作为一个可复用的管线参考。

## 问题

AI 生成的 Markdown 存在三个层面的格式失控：

1. **结构失控**：标题层级跳跃（h2 直接跳到 h4）、列表嵌套混乱、多级引用块滥用。
2. **语义缺失**：代码块不带语言标注、图片使用本地相对路径、表格缺少表头分隔。
3. **平台不兼容**：同一个 Markdown 在不同平台渲染结果差异极大——微信不支持 GFM 表格、知乎自带的编辑器对代码块支持粗糙、语雀对嵌套列表渲染有自己的一套逻辑。

如果不做适配，无非是每次手工修正，或者接受"能发就行"的质量妥协。这违背了自动化管线减少人工干预的初衷。

## 做法：一条三层管线

我目前在 OpenClaw 的 Agent 工作流中，用一条三段式管线处理 AI 输出到多平台发布的过程：

**第一层：规范化（Normalize）**

AI 生成后不直接进入发布流程，而是先过一次 Markdown 校验——检查标题层级是否连续、列表前缀是否统一、代码块是否标注语言，将不规范的写法修正为"语法干净"的 Markdown。这一步可以用一个独立的 MCP 工具（比如 markdownlint 的 Agent 封装）完成，也可以在 Agent 提示词里约定输出规范，但我更建议走工具校验，提示词约束不可靠。

**第二层：平台适配（Adapt）**

这一层按目标平台做条件变换。目标平台在 Prompt 阶段就作为参数传入，Agent 根据平台差异执行不同规则：

- 微信生态：表格转成图片、代码块尽量精简、标题层级压到两层以内（微信编辑器对深层嵌套支持差）。
- 语雀 / Notion：保留完整 Markdown 结构，但需要把图片转为图床 URL，避免本地相对路径失效。
- 知乎 / 掘金：保持 GFM 风格，但表格转成 HTML 有时兼容性更好（取决于你的编辑器插件）。

**第三层：发布分发（Publish）**

适配后的内容通过目标平台的 API 或 Webhook 推送。强调一点：不要在这一层做"内容修改"，格式转换在前面完成，发布层只负责传输和状态确认。

## 踩坑点

管线跑起来后，最典型的坑有四个：

**1. 标题层级**——AI 偶尔会生成"h2 之后直接接 h4"的结构，多数渲染器不会报错，但目录生成时会显得很乱。规范化时强制按层级加 1 修正，而不是删除标题，以保留原意。

**2. 代码块语言标注**——不写语言，GitHub 渲染没问题，但微信编辑器会直接吞掉代码块样式。建议在规范化时对未标注的代码块做启发式补全（按内容关键字判断语言），而不是统一设为 `text`。

**3. 图片路径**——AI 生成的图片本质是占位符。需要约定：所有图片必须走图床完整 URL，管线里做一个检测钩子，发现相对路径或本地路径就 fail 掉整篇任务，不进入发布环节。

**4. 表格**——微信是最大痛点。常规做法是用 `html2canvas` 类工具渲染成图片，但图片在微信内不可复制的缺点依旧存在。更务实的做法是按内容量做规则：短表格保留为纯文本列表，长表格才转图。

## 可复用建议

这套管线的关键在于"分层"——不要试图让 AI 一次生成多平台兼容的内容，而是先产出一个干净的 Markdown 中间态，再由平台层做变换。具体建议：

- 用 OpenClaw 的一个 Agent 实例专门负责规范化，另设一个负责转换，不要在同一个 Agent 里耦合两个职责。
- 平台差异的规则维护成 JSON 配置文件，每次新增发布平台时只改配置，不动代码逻辑。
- 发布后留一个回读机制：抓取已发布页面的 Markdown 渲染结果，用于后续迭代规则，而不依赖人工反馈。

## 总结

AI 撰写 + 自动发布的技术链路已经成熟，真正的工程难点不在"生成能力"，而在"格式适配"这种看似琐碎的细节上。把 Markdown 管线做扎实，一套内容才能真正在多个平台复用，自动化才算是闭环。

格式适配本质上是一种设备驱动类的任务：给每个目标平台写一份"驱动"，让内容像 USB 设备一样即插即用。这比追求大而全的转换器更务实，也更符合 OpenClaw 社区"小工具、拼流程"的风格。
