## 背景

运维和研发每天都在产出大量日志——CI 构建输出、服务错误、告警事件、定时任务结果。日报的本意是让团队知道"昨天发生了什么"，但大多数日报是下班前手工拼的：翻终端、复制粘贴、凭记忆补几条。结果要么漏掉关键异常，要么把噪音也写进去。

我最近把这件事做成了一条流水线：原始日志进，结构化 Markdown 日报出。全程由 OpenClaw 驱动的 agent 定时执行，MCP 负责对接日志源和归档系统。运行几周后，日报稳定输出，人工介入降到几乎为零。

## 问题

最初的痛点很具体：

1. **日志源分散**。CI、监控、服务器文件、工单系统各一份，格式不统一，手工聚合成本高。
2. **摘要不稳定**。不同人写日报风格差异大，领导要的是"异常 + 变更 + 待办"，实际拿到的是流水账。
3. **时效性差**。日报应该在第二天早上 9 点前出现，手工写经常拖到中午。

## 做法

流水线分四段，全部由 OpenClaw agent 编排：

**第一步：采集与归一化。** 用一组采集脚本把各日志源拉下来，统一转成带时间戳的 JSON 行。这一步不做任何智能处理，只保证"能对上时间轴"。我用 MCP 的 filesystem 和 http 工具对接不同源，agent 根据配置文件决定拉取哪些。

**第二步：噪音过滤。** 原始日志里大量是心跳、轮询成功、无关 debug。我维护一个 stopword 正则清单，agent 先按清单粗滤，再对剩余条目做雷同检测，只保留"首次出现或状态变化"的事件。

**第三步：分段摘要。** 直接让 agent 一次性读全部日志，会撞 token 上限，而且长上下文下摘要质量明显下降。所以我把当天日志按小时切片，每片单独交给 agent 生成要点，再汇总成时间段摘要。

**第四步：结构化输出。** 我定义了一份 JSON Schema：`date`、`incidents`、`changes`、`metrics`、`followups` 五个字段。agent 必须输出符合 schema 的 JSON，再用模板渲染成 Markdown 日报。Schema 校验放在本地脚本里做，不满足就自动重试一次。

最后，渲染好的日报推到团队群和归档目录，归档文件名带日期，方便回溯。

## 踩坑点

- **时间跨日**。很多日志的时间戳是 ISO 格式但时区混乱，导致"昨天 23:59"的事件被归到错误的日期。解决办法是在归一化阶段强制统一为 UTC+8 本地时间，并显式处理跨日边界。
- **指令漂移**。agent 跑久了输出格式会悄悄走样，比如字段名大小写不一致、incidents 里混入 changes。靠一遍遍改 prompt 没用，最后靠 JSON Schema 硬校验 + 失败重试兜住。这是最值得加的一层。
- **日志重复触发的告警风暴**。一条错误在 5 分钟内重复 30 次，agent 会老老实实写 30 条。需要做合并：同源同消息的告警只保留时间窗口和出现次数。
- **MCP server 不稳定**。某个日志源的 HTTP 接口偶尔超时，导致整条流水线失败。后来给每个源加了独立重试和超时上限，单源失败只跳过该源，并在日报里标注"数据缺失"。

## 可复用建议

1. **先定 schema，再写 prompt**。输出结构是需求，不是建议。
2. **分段摘要 + 合并**，不要试图一次喂全文。
3. **把滤波规则外置成配置文件**，别写死在 prompt 里，否则每次调规则都要改 agent 逻辑。
4. **失败要可见**。流水线跑挂了不要静默，至少在日报头部打上缺失标记。
5. **模板与数据分离**。JSON 是中间产物，Markdown 只是渲染层，以后要换 HTML 或 PDF 不用动 agent。

## 总结

这条流水线的本质，是把"人读日志并复述"这件事拆成可控的机械步骤：归一化、过滤、分段摘要、结构化输出。每步都很朴素，没有用到任何花哨的模型技巧，但组合起来的效果远比"让 agent 自由发挥写日报"稳定。

如果你也在做类似的自动化，建议从最痛的一类日志源开始，先把 schema 钉死，再谈智能化。工具链跑得通，比跑得漂亮重要得多。
