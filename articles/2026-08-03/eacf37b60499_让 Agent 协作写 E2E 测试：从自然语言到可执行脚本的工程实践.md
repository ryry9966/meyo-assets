## 背景

端到端（E2E）测试是保障关键用户路径的最后一道防线，但编写和维护测试脚本的成本居高不下。页面改版、元素变更、流程调整都会让手工维护的脚本脆断。过去一年，AI 辅助生成测试代码的尝试很多，但结果往往停在 demo 层面——生成的选择器脆弱、缺少上下文理解、难以融入现有测试体系。

本文的目标不是泛泛地“用 AI 写测试”，而是借助 OpenClaw 的 Agent 协作能力和 Playwright MCP 工具链，搭建一套能从自然语言描述生成可靠测试脚本的工作流。我们会讨论工程化的细节、真实踩坑和可复用的设计模式。

## 问题拆解

直接让一个 LLM 从一句话生成完整测试脚本，面临三个核心问题：

1. **选择器脆弱性**：AI 习惯用 CSS 类名或 XPath，这些在框架升级时极易失效。
2. **状态与上下文缺失**：测试需要处理登录态、数据准备、跨页面跳转，单次生成无法感知这些运行时信息。
3. **验证闭环断裂**：生成即结束，没有自动执行和修正的回路，导致产出无法直接用。

单纯提升 prompt 质量无法根治，需要引入**多 Agent 协作 + 实时页面感知 + 自动修正循环**。

## 做法与步骤

我们基于 OpenClaw 的 Agent 框架，组合 Playwright MCP server，设计了一个四阶段协作流水线：

### 1. 需求解析 Agent
输入用户描述（如："登录后，在订单列表筛选最近7天的已完成订单，验证金额求和正确"）。该 Agent 将自然语言拆解为结构化测试步骤列表，包含 action（如 navigate、click、type、assert）、目标描述、预期结果，并标记需要动态数据的部分。

```json
[
  {"step":1, "action":"navigate", "target":"/login"},
  {"step":2, "action":"type", "target":"用户名输入框", "value":"test_user"},
  {"step":3, "action":"click", "target":"登录按钮"},
  ...
]
```

### 2. 页面感知 Agent
OpenClaw 通过 Playwright MCP 打开目标环境页面，获取可访问性树快照和渲染后的 HTML。Agent 不依赖静态 DOM 选择器，而是基于**角色（role）、可访问名称（accessible name）、测试 ID（data-testid）和文本内容**为每个 step 匹配最稳健的元素定位方式。对于没有合适属性的元素，Agent 会记录备选方案，并向用户建议添加 `data-testid`。

### 3. 脚本生成 Agent
将结构化步骤与选择器元数据合并，生成 Playwright 脚本。该 Agent 遵循团队的代码风格配置（如使用 fixture、page object 模式），并自动处理等待、键盘导航、下拉选择等常见交互的健壮写法。生成的脚本不会硬编码选择器，而是尽量依赖 `getByRole()`, `getByLabel()`, `getByTestId()` 这类语义化 API。

### 4. 验证与修正 Agent
生成完的脚本在沙箱容器中立即执行。Playwright MCP 将执行结果（trace、截图、错误信息）回传给验证 Agent。若测试失败，Agent 解析错误原因（如超时、元素未找到），将失败步骤的上下文剪枝后，传回给脚本生成 Agent 进行定向修正，上限 3 轮迭代，避免无限循环。

最终输出的测试文件自动归入项目测试目录，并附带一份生成报告，标注哪些步骤使用了 AI 推断选择器，哪些经过了人工确认。

## 踩坑点

- **MCP 超时与页面状态同步**：内网站点加载慢，MCP 调用 `navigate` 后未等网络空闲就抓取快照，导致元素树不完整。需要显式调用 `waitForLoadState('networkidle')` 并设置合理超时。
- **选择器回退策略**：当语义化定位缺失时，Agent 容易退化为 XPath，这反而降低了可维护性。我们在 Agent 指令中加入了“宁缺毋滥”规则：如果语义定位不可用，直接标记为待人工标注，并中止生成。
- **登录与状态共享**：测试往往依赖已有的认证态。我们将登录抽象为可复用的 MCP tool，通过注入保存的 storageState 避免每个脚本重复编写登录流程；同时，生成脚本时自动引入 `test.use({ storageState })`。
- **动态数据断言不稳定**：金额验证等依赖数据库状态的断言，AI 容易硬编码预期值。解决方式是在需求解析阶段识别这类动态断言，生成为从 API 获取期望值的辅助函数，而非写死数字。
- **迭代修正可能引入新错误**：我们限制单次修正仅允许改变当前步骤的选择器或等待条件，禁止重写整个测试流，并通过 diff 对比防止修改已通过的步骤。

## 可复用建议

1. **建立团队测试语料库**：收集典型场景的自然语言描述与对应的人工编写测试，微调需求解析 Agent 使其理解业务术语，而非每次都从零上下文开始。
2. **推行 data-testid 规范**：AI 定位成功率的瓶颈在于可访问性标注，推动前端在可交互元素上加 `data-testid` 是投入产出比最高的改进。
3. **将常用操作封装为自定义 MCP tool**：登录、造数据、清理环境等操作不应让 AI 每次都重新发明，抽象为 tool 并注册到 OpenClaw 中，生成时 Agent 会直接调用。
4. **人工审核卡点嵌入流程**：在验证 Agent 之后，增加一个“人工确认”节点，对于新生成的测试或经过修正的脚本，推送到 Git 的草稿分支，由测试工程师快速复核一遍选择器和断言逻辑。
5. **渐进集成**：不要试图一次性替换所有 E2E 测试。优先在回归频繁、变动小的后台管理流程中跑通全流程，积累信心后再推广到核心交易路径。

## 总结

Agent 协作写 E2E 测试，本质是将人工从重复的定位和编码中解放出来，转向更高价值的策略设计和异常分析。工程化落地的关键不是模型有多强，而是**如何用工具链将 AI 的不确定性约束在可控范围内**。多 Agent 的职责切分、页面实时感知、自动验证回路，这些组合起来，才是一个可用的系统，而不是一个炫酷的 demo。

在实际使用中，我们还需要保持克制：不追求 100% 自动生成率，接受 AI 在遇到模糊定位时主动求助，这样反而能让测试资产在长期维护中存活下来。
