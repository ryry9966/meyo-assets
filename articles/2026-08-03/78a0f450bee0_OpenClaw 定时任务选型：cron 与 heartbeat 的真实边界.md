## 背景：一个调度，两种语义

在 OpenClaw 的自动化体系里，定时触发几乎是所有 Agent 工作流的脊梁。平台很早就暴露了两套看似都能“定期执行”的机制：**cron** 和 **heartbeat**。刚上手的时候，大多数人都会把 heartbeat 当成“更灵活的小 cron”，或者反过来，用 cron 去做心跳检测。结果要么任务被跳过，要么 Agent 反复重启，要么监控面板上出现诡异的执行尖刺。

这篇文章不打算把文档翻译一遍，而是结合我们在实际项目中踩过的坑，理清二者在设计意图、执行约束、故障表现上的真实差异，并给出一个可落地的选型思路。

## 问题：不是所有“每隔 30 秒”都能用 cron 表达

典型需求示例：

- 每隔 30 秒检查一次消息队列是否有待处理的任务，有则拉起 Agent 执行；
- 每天早上 9 点汇总前一天所有对话，生成日报并推送；
- 每 5 分钟执行一次数据库连接保活，同时更新工作节点的存活时间戳；
- 在特定业务窗口期（例如 9:00–21:00）内，每 3 分钟轮询一次外部 API。

粗看之下，全都可以归为“定时执行”。但当你真正在 OpenClaw 里配置时，第一个分水岭就会出现：**cron 的最小调度粒度为 1 分钟**，且表达式是标准 5 位 cron（分 时 日 月 周）。任何需要亚分钟间隔的场景，cron 直接出局。

有人会选择强行把 cron 间隔设到 1 分钟，然后让任务自身内部做快速循环——但这会让 OpenClaw 的调度控制失效，并发、超时、任务重叠的坑全都得自己填。这正是 heartbeat 语义要解决的问题。

## 做法：配置与选型推演

### 1. cron 的正确打开方式

cron 擅长的是**日历驱动**的固定时间点任务，最典型的就是日报、周报、凌晨数据清理这类需要“在某个具体时间发生一次”的场景。

在 OpenClaw 任务配置中，cron 字段一般长这样：

```yaml
trigger:
  type: cron
  cron: "0 9 * * *"   # 每天早上9点整
```

**注意事项：**
- OpenClaw 解析的是 **5 位 cron**，不支持秒级字段。如果你把“秒”写进去，要么报错，要么被当成分级解析，结果是执行时间漂移。
- cron 的执行时间是**基于节点本地时间**，不是 UTC 固定偏移。这意味着在跨国分布式部署时，如果多个节点上的 Agent 都配了同一个 cron，各节点都会在各自 9 点执行一次——导致重复触发。解决办法是配合分布式锁或者将 cron 任务限定到指定 worker。
- 任务耗时如果超过间隔，cron 不会阻止下一次触发。默认行为是**允许重叠**。我们踩过的坑：一个原本 10 分钟就结束的报表任务，在某次数据库慢查询下跑了 50 分钟，结果下一小时的任务再次启动，两个任务共同争抢连接，最后 OOM。所以任何运行时间不可控的 cron 任务，必须显式打开 `concurrencyPolicy: Forbid` 或使用外部锁。

### 2. heartbeat 不只是“高频 cron”

heartbeat 的设计初衷是**存活与连续性检查**，它的调度是“在固定的间隔之后，重新触发一次”，但携带了更多运行态上下文。

典型配置：

```yaml
trigger:
  type: heartbeat
  interval: 30s
  timeout: 25s
```

从工程角度看，heartbeat 有几个面向连续场景的关键特性：

- **间隔粒度** 可以低到几秒，甚至毫秒级（受限于框架调度器精度）。
- 内建 **超时边界**：`timeout` 会杀死超过预定时长的执行实例，防止雪崩。
- 带有“积压跳过”语义：如果上一次执行未能在下一个间隔前结束，**默认策略是跳过**，而不是像 cron 那样堆积。这天然适合轮询队列、连接保洁等“错失一次不可怕，堆积才致命”的场景。

**我们实践下来的规则是：** 凡是带有“如果上次没结束，这次就别做了”语义的连续检查，都该用 heartbeat；你可以在任务内部靠返回状态控制是否真的要做，但调度侧的保护必须由 heartbeat 的 skip 策略兜底。

## 踩坑点：时间漂移与并发幻觉

除了上面提到的 cron 重复触发和重叠问题，heartbeat 也有自己的坑：

- **假想的 1 秒精度**：设定 `interval: 1s`，实际看到的执行间隔可能是 1.2 秒、0.9 秒。OpenClaw 使用的事件循环模型会受线程池饱和、GC 停顿影响。不要用 heartbeat 做绝对的时钟同步，也不要依赖“一秒一次”来作计数器，应该用日志的时间戳做补偿计算。
- **heartbeat 的中断重连**：当 OpenClaw 进程重启时，heartbeat 不会追赶历史遗漏，它会从当前时间点开始新一轮。如果你的业务需要精确的次数统计（比如一天总计执行多少次），必须在业务记录里打点，而不是靠 heartbeat 的次数。
- **混合使用导致模糊**：曾经看到有配置在一个任务里同时写了 cron 和 heartbeat 字段，这是 API 允许的合并覆盖行为，但极难排错。最好严格只选其一。

## 可复用建议

经过几个项目的踩坑，我们总结了一个简单的决策路径，适合直接复制到团队规范里：

1. **问自己三个问题：**
   - 需要精确到“某时某分某秒”吗？ → **是** → cron
   - 需要间隔小于 60 秒吗？ → **是** → heartbeat
   - 任务重叠是危险且必须禁止的吗？ → **是** → heartbeat（并配置 timeout+skip）

2. **cron 使用者必须做两件事：**
   - 配置 `concurrencyPolicy` 为 `Forbid` 或 `Replace`（根据业务决定）。
   - 在任务顶部主动获取分布式锁（如 Redis 锁），防止多节点重复执行。

3. **heartbeat 使用者必须做：**
   - 显式设置一个比 `interval` 略小的 `timeout`，防止任务堆积导致调度饿死。
   - 业务代码内部将“该不该干活”的判断和“干活”解耦，快速退出远比干完重要。

4. **避免任何形式的“动态调度” hack：** 不要在一个 heartbeat 任务里根据外部变量去修改自己的 interval，这会使调度器的预测失效，产生不可复现的漏洞。需要动态调整频率，就把决策上提到上层流程控制，让调度触发保持不变。

## 总结

cron 和 heartbeat 在 OpenClaw 里不是谁比谁高级，而是两种完全不同的运行假设：cron 面向离散的、日历锚定的时间点；heartbeat 面向连续的、存活相关的时间线。选错的代价往往不是报错，而是那种“偶尔丢任务，偶尔重复跑”的偶发灵异问题，排查成本极高。

把上面的决策逻辑固化进 CI 检查里（比如限制 cron 不允许 interval < 60s 的写法，强制 heartbeat 必须有 timeout），能帮团队少走很多弯路。
