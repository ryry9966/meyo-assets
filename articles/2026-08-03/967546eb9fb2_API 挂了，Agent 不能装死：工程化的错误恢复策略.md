# API 挂了，Agent 不能装死：工程化的错误恢复策略

## 背景

在 OpenClaw 这类 Agent 工作流里，外部 API 几乎无处不在。查询天气、调用翻译、读取数据库、请求大模型接口——任何一个链路出问题，整个任务都可能中断。实际生产环境中，网络闪断、限流（429）、服务端 5xx、超时、非预期响应格式都是家常便饭。如果 Agent 没有针对这些异常的恢复机制，最直接的结果就是任务失败、上下文丢失，严重时还会触发无限制重试耗尽资源，产生“雪崩”。

因此，在工具链和插件里植入韧性能力，不是“锦上添花”，而是 Agent 能长期稳定运行的底线。

## 问题在哪

一个典型的 OpenClaw 流程可能看起来像这样：用户输入 → Agent 分析意图 → 调用某个 MCP 工具（比如 `get_stock_price`）→ 工具内部要访问第三方财经接口。若财经接口抛出一个 `HTTP 503` 或者 `ConnectionError`，工具直接把异常往上抛，最终 Agent 只能返回“出现了一个错误”甚至凭空消失。

常见痛点：
- 无重试或无限重试导致资源耗尽；
- 没有熔断保护，服务恢复后仍因黏连错误一直失败；
- 降级逻辑缺失，明明有缓存或备用接口却未启用；
- 错误信息直接暴露给用户，既不友好又存在安全风险。

这些问题不解决，Agent 就是个“晴天型选手”——环境稍微起风就瘫痪。

## 工程化做法

我们可以在三个层面构建错误恢复：**工具/插件层**、**MCP 服务层**、**编排层**。建议优先在靠近故障源的工具层处理，让上层无感知。

### 1. 给工具加“保险丝”：超时、重试、退避

不要信任任何外部调用能“快速成功”。以 Python 为例，用 `httpx` 给所有网络请求设置统一超时：

```python
async with httpx.AsyncClient(timeout=5.0) as client:
    resp = await client.get(url)
```

再封装一层重试逻辑。这里推荐稳定库 `tenacity`，它能处理指数退避和特定异常重试：

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=10))
async def fetch_external_data(url: str):
    ...
```

**注意对 429 特殊处理**：遇到限流响应，最好读取 `Retry-After` 头来决定等待时间，而不是机械退避。

### 2. 增加熔断器，避免雪崩

重试过多会加剧服务端压力。当连续失败达到阈值，应启用熔断器暂停调用一段时间。`pybreaker` 是很轻量的选择：

```python
import pybreaker

breaker = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=60)

@breaker
async def call_external_api(data):
    ...
```

一旦熔断打开，后续调用会立即失败，不消耗资源。半开状态自动探测恢复，适合生产环境。

### 3. 设计降级与回退

最怕的不是 API 挂了，而是挂了之后 Agent 无话可说。降级策略可以是：
- **读缓存**：比如之前成功获取的天气数据，允许返回 5 分钟前的旧结果，并标注`（数据略有延迟）`。
- **兜底值**：对非关键功能，提供静态占位数据或语义化的解释。
- **备用接口**：同一功能接入多个提供商，主备切换。

在工具定义里为每个方法添加 `fallback` 逻辑：

```python
result = await primary_api()
if is_error(result):
    result = await secondary_api() or cached_value
```

在 MCP 服务内部完成这一套操作，Agent 端只需看到最终结果，甚至不需要知道发生了故障。

### 4. 编排层的错误路径

某些情况下，工具层无法自动恢复，需要 Agent 决策。可以在流程中使用条件分支：如果调用返回特定错误标记，Agent 进入“澄清路径”，告知用户并引导下一步，比如：“当前查询服务暂时不可用，我可以帮您记录提醒，等恢复后通知您。”

## 踩坑实记

- **忘记设置最大重试次数**：因为下游返回的都是同一个瞬间异常，无限重试瞬间跑崩服务器，这是入门级但是致命错误。
- **熔断器没有半开放探测**：要么永远不打开，要么一开就再也回不来，导致恢复延迟。
- **降级时不做标识**：给用户显示了旧数据但未说明，万一价格变动，会引发投诉。透明一点，标注“缓存数据，刷新时间…”。
- **错误信息直接透传**：显示底层 `500 Internal Server Error` 或堆栈信息既不专业，还可能泄露架构细节。始终做好异常包装，给用户友好提示，给日志留详细上下文。
- **MCP 工具单点依赖**：如果一个工具调用需要同时调用多个外部服务，其中任何一个失败都导致工具失败，应尽量拆分或引入局部降级。

## 可复用的几个建议

1. **抽取出“韧性调用器”**：用工厂模式生成不同策略的调用函数，在插件体系里统一使用，比如 `create_resilient_caller(retries=2, timeout=4, fallback=...)`。
2. **MCP 服务复用**：把熔断、降级逻辑沉淀在 MCP 服务端，多个 Agent 可以共用同一套稳定性基础。
3. **监控与告警不可少**：熔断打开、降级触发这些事件必须记日志，并通过钉钉/企微等渠道通知维护者，防止“悄悄失败”。
4. **压力测试错误注入**：定期在测试环境关闭依赖服务，检验 Agent 是否按预期降级，而不是等到生产首次暴露。

## 总结

外部 API 不稳定是常态，不是意外。Agent 的错误恢复能力应当内建在工具和基础设施里，而不是事后打补丁。通过“超时-重试-熔断-降级”的层层递进策略，结合缓存和备用通道，我们完全可以让 Agent 在恶劣环境下依然保持基本的可用性和优雅的用户体验。逻辑并不复杂，关键在于每个有可能失败的地方都去设想失败场景，并执行对应的恢复路径。做好这些，你的 Agent 才能真正值得托付生产任务。
