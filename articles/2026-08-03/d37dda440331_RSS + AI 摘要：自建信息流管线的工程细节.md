## 背景：RSS 没死，只是需要重新定位

信息输入这件事，过去几年被推荐算法彻底重构了。但做技术的人大多有同感：推荐流里优质信息占比越来越低，时间线越来越吵。RSS 的价值不在于“回到过去”，而在于它是目前唯一一种**你完全掌控订阅源、格式、更新频率**的内容获取协议。

OpenClaw 这类 Agent 框架普及之后，RSS 的价值又上了一个台阶——它不再是给人看的列表，而是**可以被 AI 消费的稳定结构化数据源**。我搭建了一条 RRS + AI 摘要的管线，核心逻辑很简单：抓取原文 → 用模型抽取要点 → 输出结构化摘要。下面记录实际操作和踩过的坑。

## 问题：原始 RSS 对 Agent 不友好

直接订阅原始 RSS 源，你会发现几个问题：

1. **噪音密度高**：很多技术博客的 RSS 输出的是全文，一篇文章 2000 字，Agent 处理成本高，token 消耗大。
2. **格式混乱**：有的源是 summary，有的是 content，有的只有 title + link，解析逻辑很难统一。
3. **上下文不连续**：对于跟踪某个话题（比如 MCP 生态变化），单篇摘要无法形成趋势感知。

所以目标很明确：做一个**中间层**，把任意 RSS 源转成“低噪音、结构化、带摘要”的标准化 feed，既能给 Agent 当输入，也能自己快速扫读。

## 做法：一个 Python 管道

我用 Python 写了约 150 行代码，没有引入重型框架，结构如下：

```
fetch_rss → parse_items → dedup → AI_summary → generate_output_feed
```

核心依赖只有 `feedparser`（解析）、`openai`（调用模型）、`jinja2`（生成模板），调度用系统 crontab。

关键设计：

1. **元数据与摘要分离**：摘要存在本地 SQLite 里，原始链接和发布时间保留在 feed item 里，避免重复调用接口。
2. **增量抓取**：用 `published_parsed` 时间戳做增量，只处理新条目，避免每次全量刷新。
3. **摘要模板固定**：输出格式定为 `标题 | 要点1 | 要点2 | 相关标签`，结构化程度高，Agent 后续处理成本低。

核心代码片段：

```python
def summarize_item(item):
    text = item.get("summary", "")[:1500]
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{
            "role": "system",
            "content": "你是技术编辑。将以下文章压缩为 3 个要点，用中文输出，每个要点不超过 20 字。"
        }, {
            "role": "user",
            "content": text
        }]
    )
    return resp.choices[0].message.content
```

模型用 `gpt-4o-mini` 这类小模型就够，摘要任务对推理能力要求不高，主要靠 prompt 约束格式。成本大约每 1000 条摘要 0.5 美元，完全可以接受。

生成的新 feed 部署在本地 Nginx 上，路径 `/feed/ai.xml`，OpenClaw 里注册为一个自定义工具，Agent 每次只需要读取这个列表就能感知最新动态。

## 踩坑点

**1. 摘要指令要逐字符明确**

第一次 prompt 要求“提取三个要点”，结果模型在部分条目上返回了一段描述，导致下游解析报错。修复方式：在 prompt 里明确“用分号分隔，不要出现句号”，并在代码侧加一道格式校验，不合法就重试一次。

**2. 有些 RSS 源更新不规范**

个别源不会更新 `published` 字段，导致增量抓取永远拿不到新条目。解决：除了时间戳，额外维护一个 URL 指纹库（hash 前 64 字符），两者都作为去重条件。

**3. 别抓全文摘要**

最初我把 `content:encoded` 全文塞给模型，后来发现：其一，token 成本翻了几倍；其二，全文太长导致模型把细节题的内容当重点，反而丢失了文章主线。限制前 1500 字符效果最好。

**4. HTTPS 证书会过期**

这条管线跑了三周后突然断了，排查半天是 Nginx 证书过期。建议在 crontab 里加一个证书到期检查，至少提前一周提醒。

## 可复用建议

- **订阅源分优先级**：行业动态（更新频繁）和深度长文（更新慢）分开处理，深度源可以做更长的摘要，动态源只输出标题列表 + 一句话结论。
- **把摘要当数据而不是文本**：摘要结果落库而不是直接丢弃，可以按月回溯做趋势分析。我现在每周跑一个聚合脚本，统计哪些关键词出现频率在上升，效果像是一个私人技术雷达。
- **本地模型兜底**：OpenAI 接口偶尔会限流，加了 `ollama` 本地模型作为 fallback。响应质量有差距，但至少保证管线不断。

## 总结

RSS + AI 摘要的管线本质上解决的是一个很朴素的问题：**把信息获取从靠运气变成靠流程**。整个系统搭下来不到两小时，但收益是每天的阅读时间从无底洞变成 15 分钟内的固定动作。对于 OpenClaw 用户来说，这个 feed 可以作为 Agent 感知外部信息的重要入口，后续接任务调度、定时播报都很方便。

工具从来都是次要的，管线的可维护性和透明度才决定了它能跑多久。
