## 背景

当前大多数 Agent 实践仍停留在“问—答—执行”的交互闭环：你发一句指令，Agent 运行一次，结果返回，对话结束。这种模式适合单次任务，但很难覆盖另一类高频需求——**周期性、无人干预的主动执行**。比如早晨 8:00 自动抓取行业资讯并生成摘要、每 30 分钟检查一次服务可用性并告警、或在项目文件变更后自动同步文档。

在 OpenClaw 或类似 Agent 框架下，想让 Agent 从“等人问”变成“主动做”，常见的思路是外挂 cron 任务直接调用 Agent API。但这样耦合重、状态管理麻烦，且丢失了 Agent 本身的上下文连续性。我们需要一种更轻量、工程上更容易复用的模式。

## 问题

我们希望 Agent 能像心跳一样，定期“醒来”，自主完成一组预定义动作，而不用每次都等着人类发起对话。具体要实现：

1. **定时触发**：按自然时间或事件驱动（如文件变更）启动执行。
2. **上下文连续**：Agent 知道上次做了什么，本次不应该重复或遗漏。
3. **可观测**：我们能知道任务是否成功、何时运行、输出了什么。
4. **可干预**：在必要时能暂停、修改或注入一次性指令。
5. **低侵入**：不改变 Agent 主体逻辑，不依赖特定平台调度器。

## 做法：用 HEARTBEAT.md 构建文件驱动型主动循环

核心思路：**把任务触发和状态存储都压入文件系统**。Agent 文件系统既是感知端，也是记忆体。具体设计如下：

### 1. 目录结构

```
agent-workspace/
├── HEARTBEAT.md      # 心跳触发文件，每次更新即触发一轮任务
├── STATUS.md         # 当前状态：运行中/成功/失败，以及最后完成时间
├── TASKS.md          # 主动任务的清单（YAML / Markdown 表格）
└── OUTPUT/           # 每次执行的产出（日报、摘要、截图等）
```

### 2. HEARTBEAT.md 的协议

HEARTBEAT.md 不存放复杂配置，只记录两样东西：

- **心跳序号**：递增的整数，每次触发时写入新序号。
- **可选的元指令**：例如 `#override: priority-urgent` 表示本轮需要执行高优先级任务。

示例内容：

```
# HEARTBEAT
id: 47
timestamp: 2025-03-21T08:00:00Z
```

### 3. 触发机制

可以用最简单的文件 watch 或定时写入来实现：

- **方案 A（定时写入）**：外部 cron（或者系统内置定时模块）每 N 分钟向 `HEARTBEAT.md` 写入新序号和时间戳。
- **方案 B（文件监听）**：Agent 通过 `watchdog` 或文件系统事件监控 `HEARTBEAT.md` 的修改。一旦检测到内容变更，立即启动一轮主动任务。

对于 OpenClaw 环境，方案 B 更贴合 Agent 自闭环：Agent 启动后进入监听状态，收到心跳信号后读取 `TASKS.md` 和 `STATUS.md`，决定本轮应该执行的任务批次。

### 4. 主动任务的执行逻辑

Agent 每一轮心跳执行步骤：

1. 读取 `HEARTBEAT.md`，记录心跳 ID。
2. 读 `STATUS.md`，确认上一轮任务是否已完成。如果上次状态为“运行中”，先处理异常（重试或置为失败并报警）。
3. 读 `TASKS.md`，根据任务定义的时间策略决定哪些任务需要在此轮执行。例如：

   ```yaml
   - id: morning-brief
     schedule: "0 8 * * *"   # cron 表达式
     action: generate_daily_brief
   - id: health-check
     schedule: "*/30 * * * *"
     action: run_health_check
   ```

4. 按序执行任务，将执行日志和输出写入 `OUTPUT/`。
5. 更新 `STATUS.md`，写入本轮心跳 ID 和各项任务的执行结果。
6. 等待下一个心跳。

### 5. 人类如何介入

人类想临时加塞任务或修改行为，只需编辑文件：

- 在 `TASKS.md` 中增删或暂停任务。
- 在 `HEARTBEAT.md` 中加入 `#override: once task=emergency-restart`，Agent 见到后执行一次并自动移除 override 指令。
- 修改 `STATUS.md` 的状态为 `paused`，Agent 会挂起所有自动执行，直到状态恢复。

这种方式保持了操作接口的一致性：**所有控制即文件，所有状态即文件**，不需要额外管理面板或 CLI。

## 踩坑点

实际落地过程中有几个容易翻车的地方：

1. **文件锁与写入冲突**  
   心跳写入和 Agent 读取可能同时发生，会导致读取不完整。建议写入时使用原子化方式：先写临时文件再 `mv` 重命名，或者 Agent 读取前验证文件最后修改时间距当前时间大于 2 秒，避免读到正在写入的半截数据。

2. **心跳丢失后的死锁**  
   如果 Agent 进程异常退出，`STATUS.md` 仍为“运行中”，下一次心跳无法推进。需要一个超时机制：如果 `STATUS.md` 中的心跳 ID 距离当前时间超过预期周期 3 倍，且状态未更新，则强制重置为 `idle` 并报警。

3. **Agent 自身陷入循环**  
   主动任务中如果包含写回 `HEARTBEAT.md` 的逻辑，极易引发无限递归。设计上必须保证：Agent 只读心跳文件，不修改它。心跳的推进完全由外部调度器或文件写入者负责。

4. **日志爆炸**  
   长期运行后 `OUTPUT/` 会堆积大量文件。需要内建保留策略（比如只保留最近 30 天），并在每次心跳时做清理。

5. **时区和 cron 模拟**  
   对于跨时区环境，所有时间统一用 UTC。最好让 Agent 内置一个轻量 cron 解析器，而非依赖外部调度，以便在文件监听模式下自行判断任务就绪。

## 可复用建议

- **把 HEARTBEAT.md 模板化**  
  提供一份初始化脚本，一键生成以上目录结构和基本文件，降低每次新项目的手工搭建成本。OpenClaw 用户可以把它做成一个插件或 skill。

- **状态机尽量简洁**  
  `STATUS.md` 只保留 idle / running / paused / error 四种状态，所有细节放在各个任务的 OUTPUT 里，避免信息过载。

- **与现有通知通道整合**  
  在错误或关键任务完成时，Agent 可以将 OUTPUT 路径或摘要推送到钉钉/Slack/邮件。这可以作为任务配置中的一个可选输出。

- **逐步演进，不要一次做全自动**  
  先从一个手动写入心跳文件触发 Agent 的半自动模式开始，验证任务逻辑稳定后，再接入定时写入。这样排查问题边界清晰，不容易在早期被复杂异步困住。

## 总结

Agent 的“主动”不应该是一个复杂的 AI 觉醒概念，而是一个工程上的调度问题。通过一个简单的 `HEARTBEAT.md` 文件，配合 `TASKS.md` 和 `STATUS.md`，我们可以把文件系统变成轻量的任务总线，让 Agent 在不改变对话式主体能力的前提下，获得周期性自主执行的能力。这个模式足够原始，因此也足够可靠。在 OpenClaw 这类强调本地化、可控性的工具链中，文件驱动的主动心跳是一种值得沉淀的基础范式。
