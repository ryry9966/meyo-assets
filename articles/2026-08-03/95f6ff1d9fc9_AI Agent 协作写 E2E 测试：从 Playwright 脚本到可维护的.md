## 背景：端到端测试的维护困境

E2E 测试的价值毋庸置疑，但它长期处在一个尴尬的位置：写完很快乐，维护很痛苦。页面结构稍有变化，选择器失效；业务逻辑调整后，测试用例和真实操作脱节；异步加载、弹窗时序、网络波动等看似琐碎的细节，轻易就能让一条原本稳定的测试变成“红色闪烁”。

团队常见的应对方式无非是抽象 Page Object、引入视觉回归、甚至减少 E2E 测试覆盖。但这些策略本质上是把维护成本推迟到未来，并没有改变**测试脚本是被动记录、缺乏对页面语义理解**的根本问题。

近半年，随着 Agent 架构和工具调用能力的成熟，我开始尝试把 E2E 测试的编写和维护工作，部分移交给一个能理解自然语言意图、能操作浏览器的 AI 协作体。不是让 AI 完全替代测试工程师，而是让它可以作为测试套件中的一个可执行步骤，参与到用例生成、执行和自愈的闭环里。这篇文章就是这个实践过程的记录和拆解。

## 问题拆解：我们在让 AI 做什么？

目标不是“我用中文描述一个功能，AI 给我变出 100 条测试用例”。这种一次性生成并不难，但对真实项目的帮助有限。实际需要的是三个递进层次的能力：

1. **步骤理解与转换**：把人写的验收条件（比如“用户登录后，在订单列表页点击第一个订单的详情按钮，应能看到含商品图片的详情弹窗”）稳定地翻译成可执行的 Playwright 步骤。
2. **执行与观察**：AI 能真实驱动浏览器，观察 DOM 变化、网络请求，并在步骤失败时给出上下文信息，而非只抛出一个超时错误。
3. **自适应修复（初步）**：当选择器失效或页面结构变化时，AI 能基于对页面语义的理解，尝试定位替代元素，并建议新的选择器。

这三层能力，单靠传统脚本引擎无法做到，但结合 LLM 的规划能力和浏览器自动化工具（Playwright、Puppeteer），是可以在可控范围内实现的。

## 做法：用 Agent + MCP Server 构建测试协作流

我选择的工具组合是：

- **Playwright**：浏览器自动化执行器
- **Agent 框架**：OpenClaw 的 Agent 定义，负责接收自然语言指令、规划步骤、调用工具
- **MCP Server（Browser/Action）**：封装 Playwright 的操作为标准化工具（如 navigate、click、type、screenshot、get_dom_snapshot），供 Agent 调用
- **自定义工具**：为测试场景补充了 extract_element_info 和 propose_selectors，让 Agent 能分析页面元素并提供定位建议

具体工作流大致这样：

### 1. 定义测试意图，而不是脚本

不再直接写 `page.click('#order-123 .detail-btn')`，而用自然语言声明意图文件：

```yaml
test_case: 订单详情查看
steps:
  - action: 输入用户名 "test@example.com"
  - action: 输入密码 "secret"
  - action: 点击登录按钮
  - action: 等待订单列表加载完成
  - action: 点击第一个订单的详情按钮
  - assert: 页面上应出现包含商品图片的弹窗
```

这些意图会被喂给 Agent 的执行计划模块。

### 2. Agent 使用 MCP 工具逐步执行

Agent 拿到意图后，会通过 MCP 工具逐步操作浏览器。每执行一步，它都会：

- 获取当前 DOM 快照（可访问性树，而非全量 HTML）
- 基于步骤意图在快照中定位元素
- 调用 click / type 等工具
- 出错时自动截图、记录网络请求，并尝试分析失败原因

这里一个关键的工程决策是：不要直接把完整 HTML 发给 LLM，可访问性树足够定位绝大部分元素，且 token 消耗下降一个数量级。

### 3. 失败时的自愈尝试

当某一步失败（比如找不到“详情按钮”），Agent 不会立即判定测试失败，而是调用 `propose_selectors` 这个定制工具。该工具会：

- 提取当前页面上所有疑似按钮元素
- 将元素列表（文本、角色、层次关系）返回给 LLM
- LLM 根据语义匹配最可能的替代元素，返回新的选择器
- Agent 使用新选择器重试，并将变更记录到测试日志中

注意，自愈只发生在可控范围内（例如按钮文案从“详情”变为“查看详情”），如果页面结构剧烈变化，Agent 会停止自愈并标记需要人工介入。这样避免因过度“聪明”而掩盖真实回归问题。

### 4. 输出可维护的测试产物

每次执行后，Agent 会生成两份产物：

- **执行报告**：包含每一步的状态、截图、耗时、网络瀑布流
- **建议脚本**：将本次成功步骤转译回 Playwright 脚本，方便测试人员审阅和提交到仓库。这个脚本不再是手工编写，而是经 AI 验证过的，可复现的操作序列。

## 踩坑点

1. **DOM 快照的时效性**  
   SPA 页面中，Agent 拿到的快照可能不包含动态渲染后的元素。必须在操作后等待至少两次 DOM 稳定，并添加自定义轮询工具，确保快照反映最新状态。否则 Agent 会在空快照上决策，频繁失败。

2. **工具调用链过长**  
   一个简单的登录步骤，Agent 可能产生 5-6 次工具调用（导航→等待→获取快照→定位输入框→键入→获取快照验证）。如果每个调用都经过 LLM 推理，执行延迟明显。我们的解决方法是把连续的、无分支的操作（如导航后等待稳定状态）合并为复合工具，减少来回通信。

3. **断言与验证的界定**  
   自然语言中的“应该看到”很容易让 Agent 误以为只要元素存在就通过，但可能元素被遮挡或在视口外。必须强制 Agent 在断言前执行 `scroll into view` 并检查可见性，否则会出现假阳性。

4. **自愈的边界**  
   让 Agent 自动替换选择器要承担把“测试应失败”修复成“表面通过”的风险。实践中我们要求自愈步骤必须被记录并推送到 PR 评审，不允许静默通过。

## 可复用建议

- **从意图到脚本的半自动化更现实**：全自动端到端测试维护在复杂业务中仍不成熟，现阶段不妨把 Agent 定位成“测试脚本生成器”，人工审核后再纳入 CI，渐进建立信任。
- **可访问性树优先**：用 `page.accessibility.snapshot()` 代替全量 HTML，能大幅降低 token 成本，也强迫 Agent 学习更鲁棒的元素定位方式（按角色和文本，而非 CSS 类名）。
- **封装测试专用 MCP 工具集**：不要只依赖通用浏览器操作工具，加一个专门服务测试上下文的自定义工具（例如提取表单验证错误信息、检查 console 错误），能让 Agent 的诊断能力跨越式提升。
- **记录比脚本更重要**：AI 生成的脚本是快照，执行过程的上下文日志（DOM 快照、网络请求、决策理由）才是真正的长期资产，对调试和持续改进意义更大。

## 总结

把 AI Agent 引入 E2E 测试，本质上是用推理能力去弥补脚本对页面的“不理解”。这不会消灭测试工程师的工作，而是把测试活动的重心从维护脆弱的定位符，转向设计意图和验收标准的准确性。

经过几个月的实践，我最深的感受是：好的测试 Agent 协作，不应该是“你说一句话，它跑完所有步骤”，而应该是**它的每一步决策都透明、可审计、可干预**。只有保持这种工程化的克制，AI 在测试中的角色才可能从玩具变成工具。

对于已经在 OpenClaw 生态里探索 Agent 自动化的团队，这条路径值得一试。从一条关键业务流程的 E2E 用例开始，让 Agent 作为测试的“探险队员”，会比你预期更快地看到回报。
