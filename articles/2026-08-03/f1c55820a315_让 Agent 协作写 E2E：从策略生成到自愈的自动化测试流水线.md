## 背景：E2E 测试的维护陷阱

端到端（E2E）测试素来是质量保障里“投入产出比最低”的一环。它能验证真实用户路径，却需要持续投入大量精力去维护：前端改个 class，定位器就失效；一个弹窗延迟没处理好，整条链路就飘红。即便团队投入人力编写 Playwright 或 Selenium 脚本，几轮迭代后，用例腐化速度往往超过更新速度，最终只能被注释掉或直接移除。

过去一年，Agent、MCP（Model Context Protocol）、插件化工具链的成熟，让“用 AI 写测试”开始从 Demo 走向工程实践。思路不再是让单个模型一次性生成完整脚本，而是让多个专业 Agent 协作：一个负责理解页面结构，一个负责设计场景，一个负责生成代码，还有一个负责自我修复。围绕这一流水线，我们团队在内部项目中做了一次试水，踩了不少坑，也提炼出一些可复用的工程化经验。

## 问题拆解：为什么单体模型不够用

直接用 GPT-4 或 Claude 根据截图或 DOM 生成 Playwright 脚本，看起来一步到位，实际产出的用例往往难以持久。原因在于：

1. **缺乏上下文**：模型不了解业务关键路径，只能根据眼前页面生成零散操作。
2. **定位器选择草率**：为追求一次性成功，经常生成复杂的 XPath 或层级选择器，脆弱且不可读。
3. **无法应对变更**：测试失败后无法自行修正，只能人工介入重写。

因此，我们需要把任务拆分成多个专业环节，每个环节交给擅长该任务的 Agent 处理，并且让它们通过标准化协议（MCP）协作，形成一个闭环流水线。

## 做法：多 Agent 协作测试生成流水线

我们使用 OpenClaw 作为 Agent 编排框架（它也支持 LangChain、AutoGen 等，思路相通），通过 MCP 连接 Playwright MCP Server 以控制浏览器、获取可访问性树和执行操作。流水线包含四个 Agent：

### 1. 页面感知 Agent
职责：打开目标页面，提取结构化的“可访问性树”和关键交互元素（而非完整 DOM）。  
通过 Playwright MCP 的 `browser_snapshot` 返回精简的 ARIA 角色、名称和层级关系，避免直接分析复杂 HTML。这一步的输出是一个结构化的页面地图，供下游 Agent 消费。

### 2. 场景生成 Agent
职责：基于产品需求（自然语言描述）和页面地图，生成 Gherkin 格式的测试场景。  
例如，输入“用户登录并创建新订单”，Agent 会分解出 Given/When/Then 步骤，明确前条件和断点。这个 Agent 关注业务逻辑，不关心具体实现。

### 3. 代码生成 Agent
职责：将 Gherkin 场景转换为可执行的 Playwright 脚本。  
它会参考页面感知 Agent 提供的元素标识（如基于 `data-testid` 或可访问性名称），优先生成语义化定位器。脚本会加入合理的等待策略和失败重试逻辑。生成后直接通过 MCP 执行并返回结果。

### 4. 自愈 Agent
职责：当测试执行失败时，分析失败步骤的页面快照与原始页面地图的差异，尝试更新定位器或调整操作序列。  
例如，如果“提交”按钮的 role 未变但文本从“保存”变为“确认”，自愈 Agent 会尝试用新的文本进行匹配。修改后的脚本会进入人工审批队列，避免静默引入错误。

### 工具链示意

- **Agent 框架**：OpenClaw（负责 Agent 编排与记忆管理）
- **浏览器控制**：Playwright MCP Server（提供 `snapshot`、`click`、`type` 等工具）
- **语言模型**：使用内部部署的 Claude Sonnet 或 GPT-4o
- **存储**：生成的脚本和页面地图存入 Git，自愈修改以 PR 形式提交
- **CI 集成**：通过 OpenClaw 的 API 触发流水线，定时或事件驱动运行

## 踩坑记录

1. **可访问性树过于理想化**：不少现代前端框架渲染出的 ARIA 信息不完整，导致元素角色缺失或名称同质化。“listitem” 遍地都是，Agent 难以准确定位。此时需要退回 DOM 分析，但复杂度陡增。解决办法是与前端约定关键交互必须添加 `data-testid`，这是投入产出比最高的工程约束。

2. **自愈的“副作用”**：自愈 Agent 仅根据当前失败页面修改定位器，可能让脚本通过但不再验证原始业务意图。我们强制要求自愈后的脚本必须重新执行完整的回归集，并附带 diff 说明，由 QA 负责人审核。

3. **执行环境差异**：本地环境与 CI 环境的网络、分辨率、字体渲染不同，导致视觉截图匹配型断言不稳定。我们最终尽量避免纯截图对比，优先使用文本可见性、属性值等确定性断言。

4. **Agent 的成本与延迟**：一次完整的“感知-生成-执行-修复”循环可能需要多次 LLM 调用，耗时 3-5 分钟，尤其自愈阶段可能触发多次重试。目前仅适用于非阻塞的日常回归，不适合 pre-commit 钩子。

## 可复用建议

- **从关键用户路径起步**：选择 3-5 条最重要的端到端链路（如注册、下单、支付），让流水线先生成并维护这些用例，跑通闭环后再扩展。
- **以 `data-testid` 为锚点**：与前端团队约定规范，让 Agent 优先使用该属性，大幅降低定位器脆弱性。
- **建立人工审查节点**：自愈修改和新增测试必须走 Pull Request，让 QA 人员确认步骤语义无误后才合并。
- **版本化一切**：生成的 Gherkin 场景、Playwright 脚本、页面快照均纳入 Git，便于回溯和对比。
- **组合断言策略**：以文本、属性断言为主，截图对比为辅，仅在需要前端样式验证时才引入，并设置合理的像素容忍度。

## 总结

让 Agent 协作编写 E2E 测试，本质上是用“多个受限的 AI 步骤”替代“一个不可靠的大模型调用”。这种流水线模式让测试生成变得更可控，自愈机制也让维护负担显著降低——在我们的内部试点中，关键路径的 E2E 用例存活率从原来的 2 周延长到超过 2 个月。

但这套方案距离“无人值守”还有很长距离。Agent 更像是一个高速运转的初级 QA，能快速产出粗稿、处理简单失败，但最终决策权仍需交还给熟悉业务的人类。如果你正在维护一套日渐腐化的 E2E 测试套件，不妨尝试从一两条核心链路开始，搭建属于你自己的多 Agent 测试流水线。
