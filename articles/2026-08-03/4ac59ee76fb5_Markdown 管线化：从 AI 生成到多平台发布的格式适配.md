## 背景

借助 OpenClaw 这类 Agent 框架，让 LLM 批量产出 Markdown 内容已经不是问题。但在多平台分发时，真正的成本往往不是“写”，而是“改”——微信公众号、掘金、知乎、GitHub 等平台对 Markdown 的支持各有残缺，加上图片转存、代码高亮方言、元数据对齐，每次都手工调格式，完全没有自动化作业该有的体面。

我们需要的不是更快地 Ctrl+C/V，而是一条可复现、可扩展的 **Markdown 管线**：一端对接 AI 生成的统一源文档，另一端输出贴合各平台格式要求的终稿。

## 问题拆解

抽象来看，多平台发布的矛盾集中在三个层面：

1. **语法子集差异**  
   微信公众平台不认原生 Markdown，只能接收富文本或特定 HTML；掘金、知乎虽支持 Markdown，但对脚注、任务列表、内联 HTML 的容忍度不一；GitHub 对 CommonMark 的兼容最好，但图片必须可公开访问。

2. **资源处理割裂**  
   AI 生成的文档常混用外链图片，这些链接在各平台可能不可达，且每个平台推荐（甚至强制）使用自己的图床。图片的生命周期管理——下载、上传、替换 URL——如果依赖人工，就很容易出错。

3. **元数据与排版细节**  
   标题、摘要、标签、封面图在各个发布后台需要单独填写；代码高亮主题在移动端经常暴雷；表格在微信视口下溢出；LaTeX 公式只有少数平台原生支持。

这一套问题如果靠记忆和手动修修补补，迟早会拖垮发布的频次和一致性。

## 做法与步骤

我们落地了一条可集成进 OpenClaw 工具链的 Markdown 管线，基本架构如下：

**Step 1：规范源格式**  
与 Agent 约定输出带 YAML front matter 的 Markdown，统一管理 `title`、`tags`、`summary`、`cover` 等字段。通过提示词约束 AI 生成时避开平台通用痛点（如禁用脚注、图片用标准 `![]()` 语法、代码块强制标注语言）。

**Step 2：解析为中间表示**  
基于 `unified`/`remark` 生态，将 Markdown 解析成 AST。这一步负责标准化内部结构：统一图片链接格式、提取代码块语言标识、标记出需特殊处理的内容块（公式、特殊表格）。

**Step 3：平台适配器输出**  
每个目标平台封装一个适配器：
- **微信公众号**：通过 `remark-gfm` 转 HTML 后，注入轻量响应式样式，代码块使用已测试的移动端友好主题，生成可直接粘贴到公众号编辑器的 HTML。
- **知乎 / 掘金**：输出增强 Markdown，同步调用各平台图床 API 上传图片并替换链接，自动映射代码语言别名（如 `ts` → `typescript`）。
- **GitHub/GitLab**：仅做图片可达性检查，如果图片不可公开访问则先做中转上传，其余保持原始 Markdown。

**Step 4：通过 MCP 插件暴露能力**  
将整套转换逻辑封装成 MCP 工具（如 `md-publish`），接收原始 Markdown 和目标平台参数，直接返回终稿文本。这样一来，OpenClaw 的 Agent 在对话中就能即时调用该工具，完成“生成-转换-发布草案”闭环。对于支持 API 的平台，还可以直接推送到草稿箱，实现准自动化。

## 踩坑记录

- **公众号样式暗坑**  
  不同 Android 系统 WebView 对 CSS 的解析有差异，导致代码块换行异常或字体回退丑陋。最终我们锁定两套经过真机验证的代码主题，对所有输出做强制覆盖，哪怕牺牲一点美观度也要保证可读性。

- **图片转存的时效与失效**  
  外链图片可能临时失效或触发防盗链。管线的做法是：先本地缓存图片，再异步上传至目标图床，失败时自动用占位图替换并告警。对于掘金等需要审核的图床，必须增加重试与状态轮询。

- **代码块语言识别混乱**  
  LLM 生成时可能出现 `json` 标成 `json5`，或 `shell` 标成 `bash` 的边界情况。适配器要内置一个别名映射表，并给出“未识别语言降级为 `text`”的安全兜底。

- **长文档截断问题**  
  MCP 调用有输出长度约束，部分平台发布 API 也有字数限制。需在适配器中对超长内容做智能切分或提示，防止发布失败。

## 可复用建议

1. **建立内部 Markdown 方言**  
   为你的 Agent 定义一份最小化写作公约（禁用哪些语法、图片如何处理），比事后做兼容要划算得多。这份公约随 Agent 指令一起版本管理。

2. **用中间表示解耦**  
   不要把转换逻辑写死在某个脚本里。定义统一的 `Post` 数据结构，AST 阶段只做标准化，各平台适配器实现同一个接口。新增平台时只需添加一个新的适配器，改动面极小。

3. **将转换封装为 MCP 工具**  
   不止 OpenClaw，任何支持 MCP 的 Agent 都能复用这个工具，真正让格式适配变成“自动化常识”而非每次都要重复的体力活。

4. **CI/CD 驱动发布**  
   将源 Markdown 存放在 Git 仓库，用 GitHub Actions 触发转换与发布。对无 API 的平台，生成终稿并上传为 artifact，人工只需做最后的复制粘贴，其他环节全由管线完成。

## 总结

Markdown 管线不是银弹，但它用工程手段把最不可控的格式适配问题拆解成了可维护的模块。OpenClaw 用户完全可以借助已有的 unified 生态和 MCP 扩展开源组件，快速搭建自己的多平台发布加速器。沉没成本只在前期的适配规则积累，但一旦跑通，从 AI 生成到多平台可见的耗时，将从小时级压缩到分钟级。
