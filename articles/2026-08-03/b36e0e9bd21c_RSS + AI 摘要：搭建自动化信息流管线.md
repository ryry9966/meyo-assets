## 背景：信息流里的“未读焦虑”

我们订阅的 RSS 源越来越多，技术博客、产品更新、安全公告、个人周报……每天上百条未读条目堆积在阅读器里。略读标题只能过滤掉一半，剩下的文章点开还是需要时间判断是否值得精读。于是很自然地想到：**能不能让 AI 先帮我们把每篇文章读一遍，给出三句话总结，再决定要不要点开？**

这个需求在 Tweet、Telegram 频道、邮件摘要等领域已经有不少现成产品，但在 RSS 场景下，我们更希望有一条**完全自己掌控的管线**——可以自定义摘要风格、选择通知渠道，并且跟现有的 OpenClaw / MCP / Agent 生态无缝组合。

## 问题拆解

一条可用的信息流管线至少要解决四个问题：

1. 如何可靠地获取 RSS 条目，并拿到全文（不少 RSS 只有摘要）。
2. 如何避免对同一篇文章重复摘要（跨源转载、重新抓取）。
3. 如何低成本调用 AI 做中文摘要，同时控制质量和 Token 消耗。
4. 如何将摘要推送到我们真正天天看的地方（机器人、Notion、浏览器通知等）。

下面是一个经过实际工程验证的轻量方案，适合在 VPS 或本地持续运行。

## 做法与步骤

### 1. 选择 RSS 后端

推荐使用 **Miniflux** 或 **FreshRSS**，两者都提供 REST API。

Miniflux 的 API 尤其简洁，`/v1/entries?status=unread` 直接拿到未读条目，并且内置了全文抓取规则（`crawler=true` 参数）。对于一般技术博客，成功率超过 90%。少数抓取失败的站点，补充一个简单的 `readability` 解析容器（例如 `mercury-parser-api`）即可兜底。

### 2. 摘要管线设计

核心逻辑是一个定时执行的轻量服务，伪代码如下：

```
for entry in get_unread_entries():
    if is_duplicate(entry.url):
        mark_read(entry)
        continue
    full_text = get_full_text(entry)
    summary = ai_summarize(full_text)
    send_notification(entry.title, summary, entry.url)
    mark_read(entry)
```

将这个逻辑封装为一个 MCP tool 非常自然：`get_unread_entries`、`mark_read`、`fetch_full_text`、`ai_summarize` 各自是一个能力原子，由 OpenClaw 的 Agent 组合调用。

### 3. AI 摘要的 prompt 工程

直接用 OpenAI 兼容接口（或本地部署的模型），关键在系统提示词的设计。一个适合中文 RSS 的模板：

```
你是一个信息筛选助手。请用中文对以下文章进行关键信息提取，输出格式：
- 核心结论（1 句，不超过 40 字）
- 三个要点（每条不超过 60 字，用 bullet 列出）
- 标签（3～5 个，用逗号分隔，只保留技术关键词）

如果文章内容无实质信息，直接回复“无关键信息”。
```

这个提示词同时完成了摘要和是否值得推送给人的过滤。在模型选择上，对于大多数技术文章，`gpt-4o-mini` 的性价比最佳，约 0.15 USD/1000 篇文章。本地跑 qwen2.5:7b 也足够应对，延时略高但零边际成本。

### 4. 通知渠道选择

推荐**企业微信/Slack/飞书 Webhook**。这些渠道的消息卡片可以灵活排版标题、摘要和原文链接，且消息提醒不会淹没在阅读器中。

如果更习惯在笔记工具里二次消化，也可以写入 Notion 数据库或 Logseq 每日日志，附带标签便于未来检索。

### 5. 定时调度

最简单的方案：systemd-timer + Python 脚本，每 30 分钟跑一次。如果已经在用 OpenClaw 的 Agent，可以创建一个 cron-triggered 的 Agent，自动完成整条管线。

## 踩坑记录

**中文摘要偶尔输出英文**。即使 prompt 里强调“用中文”，某些模型在文章英文占比高时仍会切到英文。解决办法是在系统提示词最后加一句强制性约束：“所有输出必须使用简体中文，包括技术术语。禁止使用英文回复。”并给出一个错误示例让模型理解边界。

**去重不能只用 URL**。很多技术文章会同时被多个源转载，或同一作者在个人博客和掘金都发一遍。最终我们用了“URL + 标题规范化后取 hash”作为去重依据，基本避免重复摘要。代价是需要一个很小的 SQLite 表来记录已处理条目。

**API 速率缺口**。当一次性未读数量过多（例如周末积累了几百篇），瞬时调用 AI 接口可能触发 rate limit。处理方式是分批 + 指数退避。更稳妥的做法是在 MCP tool 里内置队列和限速器，Agent 只管调用而不关心底层流控。

## 可复用建议

- 将所有配置抽出为 YAML/JSON 文件：订阅源列表、渠道 Webhook、AI 模型参数、摘要 prompt 模板、去重 hash 开关等。这样无论是切换通知渠道还是调优摘要风格，都不必改代码。
- 把核心能力封装为 MCP server：`rss-fetcher`、`text-summarizer`、`notification-pusher`。之后在任何 Agent 或插件里都能复用这些积木块，比如搭建一个“每周重要技术动态总结”的 Agent。
- 监控开销：在 `ai_summarize` 工具内部记录每次调用的 token 数，并通过推送渠道附带一个小尾巴“本次摘要消耗 1.3k tokens”。这能帮你直观感受到优化 prompt 是否能省钱。

## 总结

用不到 200 行 Python，外加一个 OpenClaw 可调度的 MCP 模块，就能把“未读焦虑”转化为精准的信息摘要流。整套管线稳定运行后，每天真正需要点开精读的文章会骤降到十来篇，其余只需要扫一眼摘要即可归档。更重要的是，这套流水线完全开源、可控，可以根据自己的阅读偏好不断打磨模型提示词和过滤规则——这是任何现成阅读器都无法提供的自由度。
