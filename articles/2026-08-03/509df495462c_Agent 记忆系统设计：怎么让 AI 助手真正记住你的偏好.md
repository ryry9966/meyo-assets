## 背景：Agent 总是在“重新认识你”

如果你用过 OpenClaw 跑自动化任务，或者基于 MCP 做了一些 Agent 编排，大概率遇到过这种场景：每次对话重启，你都得把之前交代过的偏好重新说一遍——“记住，我最常用的部署方式是 docker compose”、“我的时区是 +8”、“上次我们决定用那套模板”。Agent 的会话上下文一旦清空，它就失忆了。

传统的做法是把信息写进 System Prompt 或者塞到一个长期 Vector Store 里。System Prompt 越写越长，很快会撑满上下文窗口，而单纯的向量检索往往把不相干的历史片段拉回来，干扰推理。

这就引出一个工程上绕不开的问题：怎样设计一个 Agent 记忆系统，让它在不显著增加 token 消耗的前提下，真正记住用户的长期偏好，并且能随时用得上？

## 核心问题：记忆分层与检索冲突

如果不加分层，所有用户偏好、对话摘要、历史操作日志都混在一起，会导致三个痛点：

1. **记忆污染**：旧指令和新要求冲突，Agent 不知道该听谁的。  
2. **检索噪音**：用向量相似度去查“我喜欢什么部署方式”，可能拉回一堆同主题但不同场景的聊天记录，反而打乱推理链。  
3. **Token 膨胀**：把所有记忆一股脑塞进 prompt，不仅浪费还容易超过上下文限制。

所以设计记忆系统时，首先得接受一个前提：**记忆不是存得越多越好，而是要按“使用场景”分层存取**。

## 工程做法：基于场景的记忆分层存储

我们可以在 OpenClaw 的 Plugin 架构或者 MCP Server 里实现一个三层记忆结构：

- **用户属性层（Profile）**：存放确定性偏好，比如常用命令、默认时区、项目路径等。这类信息基本不变，适合用键值对存储（JSON 文件、Railway 环境变量或 SQLite 都行）。  
- **任务记忆层（Task Memory）**：记录最近几次任务的关键决策、异常信息、用户修改点。用结构化的摘要存储，加上时间衰减权重。  
- **知识快照层（Knowledge Snapshot）**：当用户长期用同一个知识库或文档集时，把他们的阅读位置、收藏和标注抽出来，作为附加上下文，而不是每次都全文检索。

举个例子，用 MCP Server 实现一个 `memory_server`，对外暴露两个工具：`remember` 和 `recall`。`remember` 接收用户明确说出的偏好（“记住我在 /home/user/project 下的工作”），按类型写入 Profile 存储；`recall` 在每次对话轮次开始前，根据当前查询意图决定从哪一层拉记忆。对于“帮我部署最新的镜像”这类请求，优先匹配 Profile 里的 deploy 偏好；如果没有命中，再降级到近期任务记忆。

在 OpenClaw 的 Agent 配置里，可以把 `memory_server` 作为 pre-processing 工具链的一部分，每次生成之前先跑一次 `recall`，将返回的结构化上下文注入到消息列表的前端（而不是把所有记忆全贴上去）。这样既保证记忆被用到，又避免 token 暴增。

## 踩坑记录：这些地方最容易翻车

1. **记忆更新没有冲突策略**  
   用户说“我现在喜欢用 npm 了”，但旧的 profile 里写着 `package_manager: yarn`。如果直接覆盖，万一上下文是指“这个子项目用 npm”而不是全局改变，就会出错。解决办法是把偏好按 scope 分级存储，比如 global / project / session 三层，merge 时按优先级覆盖，同时保留历史版本便于回溯。

2. **把所有对话摘要都存成向量**  
   短对话摘要做 embedding 很容易误召回。推荐的做法是：只有经过“关键决策点”的摘要才存入向量库，其他流水账对话只保存最近 N 轮纯文本，作为短期记忆直接在会话开头注入，超出窗口就丢弃。

3. **忘记记忆时效性**  
   三个月前用户说“暂时用 Redis”，现在项目早迁移到 Kafka 了。记忆系统没有过期机制会严重误导 Agent。可以给每条记忆增加 `last_accessed` 和 `expiry` 字段，配合定时清理或惰性检查。在检索时根据最后使用时间降权。

4. **记忆注入位置随意**  
   如果一股脑把历史记忆放在 System Prompt 末尾，可能被新的用户指令覆盖优先级。正确做法是把高优先级偏好放在 System Message 开头，并加标记 `[IMPORTANT USER PREFERENCES - DO NOT OVERRIDE]`，让模型在推理时更倾向于遵循。

## 可复用的设计建议

如果你打算在 OpenClaw 里长期维护自己的 Agent 记忆方案，可以考虑以下几点：

- **抽象 MemStore 接口**：定义 `get(key, scope)`、`set(key, value, scope, ttl)`、`query(intent, top_k)` 三个方法，底层可以换成文件、SQLite、Redis 或 Postgres，业务逻辑不用变。  
- **记忆衰减策略**：对于任务记忆，引入类似缓存淘汰的 LRU + 时间衰减机制，保证高频且近期使用的偏好优先被召回。  
- **显式确认 vs 隐式学习**：关键偏好可以让 Agent 通过一个“需要我记住这个偏好吗？”来确认，避免把闲聊当作用户真实意图。隐式学习（比如自动记录反复使用的命令）也要有阈值，减少噪声。  
- **与 MCP 工具链整合**：把记忆服务做成 MCP Server，不仅 OpenClaw 能用，你本地的其他 Agent 框架也能复用同一套记忆存储。

一个轻量级实现，大概几十行 Python：用 `tinydb` 存 profile 的 JSON，用 `chromadb` 只存经过筛选的关键决策摘要，再用一个简单的 `remember.py` 脚本作为 MCP 工具。这样启动成本低，后期迁移也方便。

## 总结

让 Agent 真正记住你的偏好，并不是买一个超长上下文模型就能解决的。核心在于把记忆分层，让系统知道什么该存、存多久、什么时候取、取多少。在 OpenClaw 这类工具生态里，通过 MCP Plugins 我们可以相对低成本地搭建一个符合自己使用习惯的记忆层，并且随着使用逐渐优化。

设计思路概括起来就是一句话：**把用户偏好当数据管，别把记忆当聊天记录堆**。做好分层存储、时效清理、检索消噪这三点，你的 Agent 就不会再像个每次都要从头介绍自己的新同事了。
