## 背景

团队维护了多个微服务和数据处理任务，分散在云主机、数据库、Git 仓库和自建监控中。每天晨会前，需要汇总这些来源的关键信息——应用错误日志、资源使用峰值、重要业务指标变化以及代码提交摘要。人工登录不同系统、复制粘贴、手动排版，不仅耗时，还容易遗漏异常信号。当环境中的组件增多，维护一份可靠的“昨日快报”就成了一项隐性负债。

OpenClaw 作为可编排的智能体平台，配合 MCP（Model Context Protocol）不断丰富的工具生态，为这类信息聚合与格式化任务提供了一套标准化解答。本文复盘的是我们如何用 OpenClaw + 现有 MCP 工具，搭建一条无人值守的“原始日志 → 结构化日报”流水线。

## 问题拆解

本质上，这个任务是一道 ETL（提取-转换-加载）题，但它的触发器是人，而不是调度器。主要痛点有三个：

1. **多源异构**：Git 日志是结构化的 JSON，应用日志是分行文本，数据库查询结果是表格，监控 API 返回的是时序数据。统一解析成本高。
2. **手工排版易出错**：每天手动将数据填入固定模板，一旦某个源缺失就要追溯很长时间。
3. **维护负担**：如果只写一次性脚本，数据源格式稍变就需要改代码；用智能体承担编排，可以降低后续修改的心智成本。

## 做法

我们将整条流水线拆成五个阶段，全部在 OpenClaw 的 Agent 内串行完成，并借助 MCP 工具连接外部系统。整体架构： **MCP 数据源 → Agent 编排与清洗 → Markdown 报告 → 分发通道**。

### 1. 确定数据源与 MCP 连接器

选择已经稳定可用的 MCP 实现，尽量不走“自研连接器”的弯路：

- **Git 提交记录**：通过 `github-mcp` 拉取指定仓库过去 24 小时的 commit 列表，返回 author、message、timestamp。
- **应用错误日志**：通过 `ssh-executor-mcp` 远程执行 `journalctl` 或 `grep` 命令，只返回错误级别的行；对于海量日志，加 `tail` 和过滤条件，避免把原始文本全部拉进上下文。
- **业务数据库指标**：用 `postgres-mcp` 执行预定义的聚合查询（如昨日新增用户数、异常订单比例），返回标量或简单表。
- **服务器资源使用**：同样用 SSH MCP 读取 `/proc/loadavg`、`free -m` 摘要，或者拉取 Prometheus API 的瞬时值（通过 `fetch-mcp`）。

在每个源调用前，Agent 会注入固定的“时间窗口”参数，基于 UTC 计算 `since` 和 `until`，解决时区漂移问题。

### 2. 编写 Agent 提示与工具调用序列

OpenClaw Agent 的系统提示明确约束行为：它只做数据采集、清洗和排版，不进行额外推理；所有工具调用失败需记录原因并继续下一源。实际操作中，我们使用了“强制工作流”的方式：在提示中列出必须按顺序执行的步骤，而非完全依靠模型自主规划，这样做可以极大降低步骤遗漏的概率。

步骤示例（伪指令）：

```
1. 调用 git_mcp 拉取最新 24 小时 commits，提取 author、message 首行。
2. 调用 ssh_mcp 在所有应用节点执行错误日志提取命令，收集后统计 Top 5 错误类型。
3. 调用 postgres_mcp 执行指标查询。
4. 本地解析各源结果，按模板生成 Markdown 表格。
5. 调用 slack_mcp / feishu_mcp 发送报告。
```

在 Agent 内嵌入了简单的 Python 代码片段（由 OpenClaw 的代码解释器执行），用于日志统计和排版，避免模型本身在数学或表格对齐上出错。

### 3. 异常隔离与弱依赖设计

每个数据源的调用包裹在独立的 try-catch 块中（通过提示逻辑实现）。如果一个源因权限过期或网络抖动而失败，不会阻断整个流水线，报告会在对应板块标注“数据获取失败：{原因}”。这样晨会时团队成员至少知道某类信息缺失，而不是整个日报消失。

### 4. 定时执行与人工触发

OpenClaw 支持定时触发和消息指令触发。我们设置每日早 7:30 自动运行，并通过企业微信机器人回调触发手动“补发”，方便临时需要。

## 踩过的坑

1. **MCP 工具返回格式不统一**  
   Git MCP 返回对象数组，SSH 命令返回纯文本，Fetch MCP 的 JSON 结构差异大。最初想让 Agent 自行适配，结果解析经常出错。最终解决方案是：在 Agent 解析阶段，统一要求每个源调用后输出标准 JSON 中间格式（`{source, status, summary, raw}`），再由排版模块消费。

2. **上下文长度溢出**  
   最初直接把 `journalctl --since yesterday` 的完整输出拉入上下文，导致超出 token 限制。后来规定所有日志源必须先在远端通过 `| head -200` 或 `| awk` 聚合，只将摘要送回。一条硬规则：禁止 Agent 获取超过 200 行的原始日志。

3. **Agent 规划不稳定**  
   如果允许 Agent 自行决定工具调用顺序，偶尔会跳过数据库查询步骤。改为“任务清单”模式，将其视为必须完成的 checklist，即使某个工具失败也要在清单中打标记，稳定性显著提升。

4. **密钥与权限腐化**  
   MCP 工具的 API Token 或 SSH Key 过期后，日报静默残缺。我们为此增加了一个健康检查 Agent，每天凌晨测试所有 MCP 连接的连通性，失败则通过备用通道告警。

## 可复用的工程建议

- **模板化配置**：把“日报内容结构”抽成一个 JSON 配置文件，定义每个板块的数据源、提取规则、显示格式。Agent 解析配置来生成报告，切换项目只需修改配置，不改提示。
- **预处理脚本封装**：如果某个源的清洗逻辑复杂，可以写成远程脚本（放在服务器上），通过 SSH MCP 触发，让 Agent 只接收清洗后的结果。这样做既省 token，也更容易调试。
- **强约束提示模板**：为日报类 Agent 编写的提示可以复用。声明明确的成功/失败合约、输出格式要求、Token 预算意识，会大幅减少“幻觉排版”。
- **依赖 MCP 市场**：尽量使用社区维护的 MCP 工具，避免为一次性任务造轮子。只在没有现成实现时才考虑用通用 fetch/ssh 兜底。

## 总结

这套“原始日志 → 结构化报告”流水线运行两个月后，日报准时率从 70% 提升到将近 100%，人工介入只出现在新数据源接入或异常处理时。OpenClaw + MCP 的组合降低了信息聚合门槛，但工程化的细节——异常隔离、Token 控制、统一数据契约——才是稳定运行的关键。如果你的团队也在被碎片日志困扰，不妨从一条最小原型开始：先接入一两个 MCP 源，跑通流程，再逐步扩展覆盖范围。
