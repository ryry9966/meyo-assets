## 背景

在一个典型的 OpenClaw + MCP 工具链里，模型并不只有 GPT-4 一种选择。很多工程师会把 `llama3.1`、`qwen2.5` 这类本地模型通过 Ollama 或 vLLM 挂进 OpenClaw，再配合远端 OpenAI 模型一起使用。但多数人还停留在“所有请求都走 GPT”或者“全部换成本地模型”的状态，缺少根据任务特征自动分流的逻辑。

其实 OpenClaw 本身内置了灵活的模型路由能力，允许你根据提示词长度、复杂度、是否使用工具、预算上限等维度，把不同请求分发到不同模型端点。把这件事做好，可以在保持响应质量的同时，显著降低 API 开销，并缓解速率限制的问题。

这篇文章会从**为什么需要多模型路由**讲起，给出一个可落地的路由配置步骤，分享我在踩坑过程中碰到的三个典型问题，最后给出一套可复用的路由策略模板。

## 为什么需要路由：云端模型与本地模型的真实差异

先厘清一个容易被忽略的点：**本地模型不等于“免费但更差”**。对于一些高频、低门槛的任务，本地模型的体验甚至更好。

- **延迟敏感型任务**：像代码补全、对话式问答、简单的 MCP 工具选择（例如“帮我取一下今天的天气”），本地 7B/13B 模型在 RTX 4060 上可以做到 50ms/token，远低于 GPT-4 的 300~800ms 首 token 延迟。
- **隐私约束任务**：涉及本地文件内容、密钥片段、个人笔记的请求，不应该离开本机。本地模型是唯一选择。
- **成本型任务**：日常调试中可能产生大量“无效”对话（比如测试提示词效果），如果全走 GPT-4，每月账单会非常难看。

反过来，GPT-4 在**复杂推理、长上下文理解、多步工具编排**上仍然难以被本地模型替代。例如需要将用户模糊指令分解为 5 步 MCP 调用，且中间涉及条件判断时，7B 模型很容易丢失意图或编造参数。因此关键任务必须路由到云端强模型。

## OpenClaw 多模型路由的实现方式

OpenClaw 的模型路由配置主要通过 `profiles` 和 `routing_rules` 两部分完成。下面是一个生产环境中可用的最小可行配置（基于 OpenClaw 0.8+）。

**第一步：注册多个模型端点**

在 `openclaw.yaml` 中定义远端 GPT 和本地 Ollama 模型：

```yaml
models:
  - id: gpt-4o
    provider: openai
    model: gpt-4o
    api_key: ${OPENAI_API_KEY}
  - id: local-llama3
    provider: ollama
    model: llama3.1:8b
    base_url: http://localhost:11434
  - id: local-qwen2.5-coder
    provider: ollama
    model: qwen2.5-coder:7b
    base_url: http://localhost:11434
```

**第二步：编写路由规则**

引入 `routing` 块，按优先级从上到下匹配：

```yaml
routing:
  rules:
    - name: complex_tool_use
      when:
        estimated_tokens: { gt: 4000 }   # 上下文超过 4000 token
        tools_required: true              # 需要调用 MCP 工具
      route_to: gpt-4o
    - name: coding_tasks
      when:
        intent: "code_generation"        # 意图识别为代码生成
      route_to: local-qwen2.5-coder
    - name: simple_qa
      when:
        intent: "question_answering"
        estimated_tokens: { lt: 2000 }
        tools_required: false
      route_to: local-llama3
    - name: fallback
      route_to: gpt-4o                    # 默认兜底
```

**第三步：确认意图识别源**

路由依赖的 `intent` 字段可以由 OpenClaw 内置的轻量分类器填充，也可以来自上游 Agent 在请求时附加的 metadata。如果你的流程已经通过 LangChain 或自定义状态机明确了任务类型，建议在上层传递 `x-openclaw-intent` 头，避免额外分类开销。

## 实际踩过的三个坑

### 1. 本地模型上下文窗口不足导致静默截断

`llama3.1:8b` 默认上下文只有 8k。当对话累积超过 6k token 时，很多 Ollama 部署会直接截断前半部分，而不是拒绝请求。结果就是：模型突然“忘记”前面的指令，MCP 工具调用参数乱填，且没有任何警告。

**解决办法**：在路由规则里加一条“如果估算 token 超过本地模型限制，直接升到 GPT”的规则。同时监控 Ollama 日志中的 `truncation` 关键字，设置告警。

### 2. 本地模型对工具 schema 的遵循度极不稳定

同一个模型版本，昨天还能准确输出正确的 `function_call` JSON，今天就可能把参数名写成中文或直接返回一段自然语言描述。这种不稳定在 MCP 自动化管道里是致命的。

**经验**：所有涉及**关键执行动作**（如文件写、数据库操作、发送消息）的工具调用，不要信任本地模型。可以在路由规则里把 `tools_required` 和 `risk_level: high` 强制路由到 GPT。

### 3. 成本节省不及预期

初次配置路由后，我发现 API 开销只降了 15%，远低于预估的 40%。排查发现，很多简单对话因为系统提示词过长（包含了大量 MCP 工具描述），导致 `estimated_tokens` 总是超过 2000，全部掉进了 GPT 路由。

**优化**：为本地模型创建精简版 system prompt，仅在路由匹配后动态注入，而不是公用同一份长提示词。OpenClaw 支持 `prompt_overrides`，可以按 route 替换。

## 可复用的路由策略建议

经过多次迭代，我提炼出下面这个决策矩阵，你可以直接映射为 OpenClaw 路由规则：

| 任务特征                        | 推荐模型            | 理由                         |
|---------------------------------|---------------------|------------------------------|
| 简单问答、闲聊、摘要 < 2k token | 本地 7B/8B 通用模型 | 低延迟、零成本               |
| 代码生成、代码解释              | 本地专用 coder 模型 | 代码质量可接受，响应快       |
| 多步工具使用、参数提取          | GPT-4o              | 工具调用遵循度高             |
| 长上下文（>6k）或复杂推理       | GPT-4o              | 本地模型推理能力骤降         |
| 涉及敏感数据                    | 本地模型（强制）    | 数据不出机                   |
| 紧急兜底                        | GPT-4o              | 保证可用性                   |

实际落地时，建议先**只路由明显的简单任务**（比如 80% 的闲聊和代码生成），稳定运行一周后再逐渐扩大本地模型的覆盖范围。同时务必监控路由命中率、异常工具调用率和成本变化。

## 总结

OpenClaw 的多模型路由不是“把便宜模型当备胎”，而是一套基于任务理解的动态调度系统。用好它的关键是：

1. **精细估算 token** 而不是只看消息条数；
2. **对执行类工具调用保持敬畏**，不强求本地模型；
3. **根据本地模型上下文窗口反推路由阈值**，防止静默降智；
4. **为不同路由准备不同的 system prompt**，避免长提示词拖累轻量任务。

稳定运行后你会发现，GPT 的使用量下降 50% 以上，但核心自动化管道的可靠性几乎没有打折。这在工程上是相当划算的。
