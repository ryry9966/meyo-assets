## 背景：你多久没用过 `git commit` 的命令行了？

在 OpenClaw、MCP、各种 Agent 和自动化插件越来越多地进入日常开发流程之后，我们开始重新考虑一个问题：**Git 操作到底该由人来一个个敲，还是该交给具备上下文感知能力的 AI 来完成？**

如果你在维护多个微服务仓库，每天在 feature、hotfix、release 分支之间跳来跳去，还在费力回忆“这次改动到底是修了一个空指针还是加了缓存的过期策略”，那么你很可能已经踩到了 Git 操作中重复劳动占比最高的区域：**写 commit message、合并分支、保持分支整洁**。

这些操作不需要创造力，却需要细心、规范，并且很容易在疲劳时出错。它们恰恰是“自动化”最适合切入的环节。

本文不会教你如何写更好的 commit 习惯——习惯能解决的问题我们就不写工程文了。我要分享的是：**如何做一个基于 Agent 的 Git 自动化助手，让它帮你处理提交信息生成、自动创建符合规范的分支，并在拉取和合并前做一些基础的风险检查**，同时告诉你哪些地方容易翻车，以及怎么避开。

## 问题：人做重复决策的精度与效率天花板

我们来看几个典型场景：

1. **提交信息不规范**  
   你提交了一个 `fix bug`，回头在 CHANGELOG 里找不到到底修了什么。强推 commitlint 可以挡住格式错误，但无法保证信息本身“有意义”。

2. **分支命名混乱**  
   `feature/xxx`、`f_xxx`、`xxx-new`、直接从 `main` 开的新分支而没有带上 JIRA 编号，导致自动 deploy 流程失败，或者 code review 时无法追溯需求。

3. **合并时缺少上下文校验**  
   从 `dev` 往 `main` 合代码时，只是习惯性 `git merge`，没有检查是否有未解决的冲突标记、是否有不应该一起合入的 WIP commit。

在这些场景里，人类其实是 “执行引擎”，不是决策者。真正需要的只是一个能理解上下文、能遵守团队规范并给出建议的自动化层。

## 做法：一个最小可用的 AI 自动化层的设计

我搭建的结构是这样的（以 OpenClaw + MCP Git 插件为基础，当然你也可以用自定义 Agent + 脚本实现）：

```
用户意图 (对话/CLI 指令)
          │
  ┌───────▼────────┐
  │  Agent 调度层  │
  └───────┬────────┘
          │ 调用
  ┌───────▼────────┐
  │ 上下文收集器   │ ─── 收集 diff、当前分支信息、历史提交
  └───────┬────────┘
          │ 送给 LLM
  ┌───────▼────────┐
  │  决策 & 生成  │ ─── 生成 commit message / 分支名 / 检查结果
  └───────┬────────┘
          │ 执行
  ┌───────▼────────┐
  │ MCP Git 工具层│ ─── git add/commit/branch/merge 等
  └────────────────┘
```

**具体步骤：**

1. **将 Git 操作暴露为 MCP 工具**  
   使用现成的 MCP Git server（如 `@anthropic/mcp-server-git` 或自己用 `simple-git` 封装的），在 OpenClaw 或你自己的 Agent 中注册。这样 AI 就能通过 `git_status`、`git_diff_unstaged`、`git_log` 等工具读懂仓库状态。

2. **编写上下文收集器**  
   一个轻量函数，把以下信息拼成一个 prompt 前缀：
   - 当前分支名
   - 未暂存/已暂存的 diff 摘要（如果 diff 太长，只取文件列表和前 200 行变更）
   - 最近 5 条 commit 记录（用于理解工作节奏）
   - 团队的 commit 规范示例（如 Conventional Commits）

3. **定义 Agent 的三个核心能力**

   **3.1 智能提交**  
   - 用户说：“提交代码”  
   - Agent 读取 diff → 生成符合规范的 commit message，并展示给用户确认。  
   - 确认后执行 `git add` 和 `git commit`。  
   - 如果检测到 `WIP` 字样或临时调试代码，会提醒用户拆分提交或清理。

   **3.2 创建合规分支**  
   - 用户说：“新功能：支付通知”  
   - Agent 根据团队规范生成分支名，比如 `feature/PAY-1024-payment-notify`，然后 `git checkout -b` 并推送。  
   - 命名规则可以放在配置里，让 Agent 去拼。

   **3.3 预合并检查**  
   - 用户说：“合到 dev”  
   - Agent 先 fetch 远端，比较分叉点，检查是否有冲突标记（`<<<<<<<`）；  
   - 再检查目标分支的保护规则（比如不能直接推到 `main`，应该走 PR）；  
   - 最后输出一个检查报告，询问是否执行合并。

## 踩坑点：不是所有 Git 操作都能放心交给 AI

**1. 自动生成 commit message 的质量飘忽**  
   如果只给 LLM 看 `diff`，它经常写出太泛或太具体的信息。例如把多个逻辑改动合成一段话，或者对空行修改也反复描述。  
   **解法**：  
   - 在 prompt 中强制要求“每个逻辑变动点最多一句话，用列表形式，不要复述 diff 内容”。  
   - 提供 bad/good 示例 pair，让模型参考。  
   - 如果 diff 超过 200 行，必须提示用户手动拆分提交——这是硬性规则，不可破。

**2. 在错误的分支上执行操作**  
   Agent 理解自然语言时，可能会在受保护分支上直接提交，或者合到错误的目标。  
   **解法**：  
   - 在工具层做硬限制：禁止直接在 `main`/`master`/`release/*` 上 `git commit`，必须要求用户手动绕过（例如用一个 `--force` 标记）。  
   - 合并操作必须输出拟执行的命令，要求用户确认。

**3. Token 消耗与 API 费用**  
   如果每次提交都送全量 diff，成本会很高。  
   **解法**：  
   - diff 截断策略：优先取文件级摘要，只有文件数少于 5 时才送部分内容。  
   - 对简单的重构（仅移动/重命名），可以跳过 LLM 调用，直接用模板生成信息。

**4. 与大团队 CI 流程的冲突**  
   有些仓库的 CI 会通过 git hooks 做签名检查或要求交互式 rebase，Agent 执行时容易 hang 或失败。  
   **解法**：  
   - 先在工作流里加 `--no-verify` 白名单，只允许在非关键仓库使用。  
   - 针对签名钩子，可以让 Agent 先检查 hook 是否存在，若存在则自动降级为“仅生成指令，不执行”。

## 可复用建议

经过几次迭代后，我们沉淀了几条可以复用的工程原则：

- **把 Git 操作分为“只读”和“写入”，Agent 默认只有只读能力，写入必须带确认流程。**  
  这是安全感的基础。你不想在某一天看到一个 commit message 写着“已根据您的指令删除所有未提交的变更”。

- **团队规范写成配置，不要硬编码在 prompt 里。**  
  分支命名规则、commit 类型、JIRA 编号格式，都放在一个 `git-automation.yml` 中，上下文收集器读取并注入。

- **除了生成文本，Agent 还应输出“建议动作”和“风险项”。**  
  比如：“建议先 rebase 到最新 dev，当前分叉点落后 12 个 commit，其中包含一次数据库迁移。”

- **把预合并检查做成一个独立工具，可以被任何 CI 或本地命令复用。**  
  你可以在合并前调用 `agent check-merge-target dev`，它返回结构化的风险报告，判断是否安全。这样就不仅仅是个“提交生成器”了。

## 总结

Git 自动化不是让你放弃对版本控制的掌控，而是把一些机械、易错、且需要核对大量规范的步骤移交给 AI，帮你**保持仓库健康度**，同时**降低认知负荷**。自动生成的 commit message 可能仍然需要你调整，分支名不一定每次都完美，但相比每天十几次手动敲 `git commit -m "update"`，这已经是巨大的升级。

从工程角度说，这套做法的真正价值不在于 AI 多聪明，而在于把**团队规范转成了可执行的自动化检查**，让 Git 操作从“个人习惯”变成“系统能力”。如果你已经在 OpenClaw 或类似的 Agent 平台上有了基础框架，接入 Git MCP 工具并构建这三项核心能力通常只需要半天时间，但收益会持续很久。

在你的下一个迭代里，试试让 AI 帮你管一天 Git，看看它会在第几条 commit 让你惊喜，或者在第几个坑里让你庆幸提前加了确认步骤。
