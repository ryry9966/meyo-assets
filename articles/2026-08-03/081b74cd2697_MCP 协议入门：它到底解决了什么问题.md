### 背景：工具集成正在变成一场噩梦

如果你在过去一年里做过 Agent 开发，大概率遇到过这种场景：为了让模型调用某个 API，你需要写一个 adapter、处理鉴权、设计 prompt 来描述这个工具该怎么用。每接一个工具，这套流程就要重新来一遍。OpenClaw 用户应该更有体会——插件生态越丰富，依赖和冲突也越明显。

这本质上是一个集成碎片化问题：工具方要针对每个 Agent 框架定制 SDK，Agent 方要为每个工具写胶水代码。整个生态的 85% 精力都耗在"对接口"上，而不是"用能力"上。

### 问题：N 个工具 × M 个框架 = 死循环

具体来说，传统方式有四个很明显的痛点：

1. **协议私有化**：每个 Agent 框架都有自己的 tool call 格式，OpenAI 的 function calling、Anthropic 的 tool use、本地框架的 JSON schema 各不相同。工具方不知道该适配哪家，Agent 方也不敢深度绑定某家。
2. **鉴权混乱**：API key 放哪里？scope 怎么定？权限怎么审计？各搞各的，没有统一标准。
3. **资源类型单一**：多数方案只能"调用函数"，但实际的业务场景还需要读取数据、订阅事件、操作文件。这些资源类型没有被建模。
4. **上下文割裂**：工具返回的结果和对话历史是割裂的，Agent 需要自己决定怎么把工具结果塞回记忆里，容易丢上下文。

### 做法：MCP 的核心思路

MCP（Model Context Protocol）的思路其实很简单——把工具/数据/上下文统一建模成一个标准协议，让 Agent 和工具方各自只实现一次协议。

协议里有三个核心概念：

- **Server**：工具提供方，暴露自己的 capabilities（如 `tools/list`、`resources/list`）
- **Client**：Agent 或宿主运行时，连接 Server 并操作其资源
- **Tool / Resource / Prompt**：三种原语，分别对应"可执行的函数"、"可读取的数据"、"可复用的对话模板"

回到 OpenClaw 场景，接入 MCP server 的流程大致是：

```bash
# 1. 启动一个本地 MCP server（示例用 Python SDK）
pip install mcp
python my_server.py

# 2. 在 OpenClaw 配置文件中注册该 server 的 endpoint
# 配置项一般形如：
# mcp.servers.my_server:
#   transport: stdio | sse | http
#   command: python
#   args: ["my_server.py"]
```

配置完重启 OpenClaw，Agent 在对话中就能自动发现并调用 server 里声明的工具，不需要写胶水代码。

### 踩坑点（都是实际操作中遇到的）

1. **SSE 传输的 POST 限制**：MCP 规范里 `prompts/get` 和 `tools/call` 都是 POST 请求，但部分 HTTP 中间件会默认拦截。排查时先确认你的网关是否放行了这两个 path。
2. **初始化握手有超时**：Server 在 `initialize` 阶段如果响应超过 60 秒，Client 就会断开连接。建议把懒加载的资源放到 `initialize` 完成后再加载。
3. **Tool 名称冲突**：多个 server 如果同时暴露了 `get_weather`，OpenClaw 的工具路由表需要你手动指定 server 前缀。规划阶段就给 tool 名加一个 `servername_` 前缀会省很多事。
4. **本地文件资源路径校验**：MCP 规定资源 URI 必须是绝对的 `file://` 或 `resource://` 格式，相对路径会直接报 invalid。这个在官方的 Python SDK 中查得比较严。

### 可复用建议

- **先跑 `inspector` 再写业务**：MCP 官方提供了 `@modelcontextprotocol/inspector`，图形化调试工具，能看到每个请求的时序和 payload，强烈建议接入前先用它验证你的 server。
- **传输方式的选择逻辑**：本机单用户用 `stdio` 最简单；跨机器部署用 `sse`，注意保活；如果走公网，直接用 `streamable-http` 会更稳，减少连接数。
- **权限粒度按用户分**：Server 的 `capabilities` 可以细粒度控制谁可以访问哪个工具。多租户场景下不要把所有权限放在一个 token 上。
- **对齐 resource 缓存策略**：静态资源做一次性缓存就够，动态资源要设计 `watching`，除非你的 Agent 不在乎新鲜度。

### 总结

MCP 不是银弹，它目前还在快速演进阶段。但它的价值在于把"生态碎片化"这个根问题摆到台面上，用一个统一协议收敛了集成成本。对于 OpenClaw 用户来说，理解 MCP 的收益是立竿见影的：用一套配置接入所有兼容 server，后续工具迭代不需要改 Agent 侧代码。

如果你正在维护自己的工具，今天开始把它包一层 MCP 原型是值得的——等协议稳定后，迁移成本远小于现在观望的代价。
