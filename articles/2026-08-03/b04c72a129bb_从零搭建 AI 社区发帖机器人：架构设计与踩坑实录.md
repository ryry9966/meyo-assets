## 背景与动机

在 OpenClaw 生态中，Agent 与 MCP 工具链的实践场景一直不缺讨论，但落到“内容发布”这类高风险长链路任务上，工程细节远比 demo 复杂。我们的目标是：用 OpenClaw 搭建一个面向中文技术社区的发帖机器人，能根据主题自动生成结构化内容并安全发布，整体架构可复用、可审计、不灌水。这个机器人不仅要处理模型生成的不确定性，还要面对传统论坛 API 的限频、反爬与格式约束，是一次典型的 Agent 生产化尝试。

## 问题拆解

发帖机器人表面是“生成-发布”两步，但实际需要解决四个核心问题：

1. **任务编排**：如何让 Agent 准确把握生成、审核、发布的节奏与异常恢复？
2. **工具链打通**：论坛无标准接口，需要通过 MCP 封装一套稳定的发布工具。
3. **内容质量控制**：AI 内容容易跑题、越线或重复，需要规则与审核层介入。
4. **运维可控**：多 Agent 并发、限频、会话污染等长尾问题必须提前设计。

## 架构设计

整体采用 **Agent + MCP Tool Server + 内容流水线** 结构：

- **OpenClaw Agent**：负责计划循环 (plan-act-observe)，通过系统提示词约束角色与输出格式，维护每次发布任务的独立短会话。
- **MCP Server**：使用 `mcp` 包快速搭建一个本地/远程服务，暴露 `create_post`、`get_forum_info`、`upload_media` 三个工具。内部封装了论坛 HTTP 客户端的登录态管理、CSRF 令牌获取、重试策略等逻辑。
- **内容流水线**：在 Agent 决策生成全文后，串联**模板引擎**（填充板块、标签、标题前缀）、**审核模块**（敏感词过滤 + 质量评分）和**发布执行器**。
- **触发器**：支持 cron 定时主题池轮询，或通过 Webhook 接收外部任务。

这样拆分的最大好处是：工具与 Agent 解耦，发布行为变成标准 Tool Call，日后替换论坛平台只需重写 MCP Server 内部适配，Agent 侧不变。

## 踩坑实录

### 1. MCP 工具参数序列化陷阱

MCP 工具定义要求输入输出为 JSON Schema。论坛发帖接口常包含复杂对象，如 `content` 字段需要传递带 HTML 标签的长文本。在 Agent 调用时，模型偶尔会错误转义引号或插入不支持的 Unicode 控制符，导致 MCP Server 解析失败。**对策**：在工具描述中明确强类型约束，对 `content` 做 Base64 编码传入，Server 端解码后使用，彻底规避转义问题。同时，在 Agent 提示词中要求“调用工具时保持 content 字段为原始 Markdown 的 Base64 字符串”。

### 2. 上下文长度与 Token 爆炸

Agent 生成一篇 1000 字以上的技术帖时，容易在一次会话中携带大量历史上下文。当任务链路过长，上下文窗口被无用的工具返回结果撑满，导致 Agent 在发布后突然开始胡言乱语，甚至重复发帖。**对策**：每个发帖任务强制使用“一次性会话”，即 Agent 完成任务后立即结束进程并清理存储。使用 OpenClaw 的 `ephemeral` 会话模式，可避免状态泄露。

### 3. API 限频与反爬

论坛服务端对短时间内同一用户的发布频率敏感，且会检查 User-Agent 和请求头完整性。初始测试时，连续发帖会触发 429，并且 IP 被临时拉黑。**对策**：在 MCP Server 内实现令牌桶限流器，每两次发布间隔不少于 120 秒；引入指数退避重试 (1s, 2s, 4s… 最多三次)；并设置 User-Agent 白名单与 Referer 可信源。配置支持代理池作为可选项，但不强依赖。

### 4. 内容质量盲区

让 LLM 直接输出整篇帖子，偶尔会夹带“作为 AI 模型”之类的自反性表述，或在技术深度上浮于表面。虽然加入了规则过滤，但仍出现过一篇关于“闭包与内存泄漏”的帖子，示例代码明显错误。**对策**：引入两层审核——第一层是关键词黑名单和长度/格式校验；第二层是调用一个评判 Agent（另一个小容量模型）对帖子质量打分，低于阈值则回退为人工草稿箱。这套机制虽然增加了延迟，但大幅降低了线上事故。

## 可复用建议

- **工具抽象**：将社区发帖抽象为 `/posts` 资源，MCP 工具命名与 RESTful 概念对齐，方便未来替换后端。
- **配置外移**：所有板块 ID、标签模板、发布频率、审核阈值均写入 YAML 配置文件，避免硬编码。
- **灰度发布**：新增社区或调整模板时，先以“仅自己可见”或放入草稿区，观察无异常再开放。
- **可观测性**：每次 Tool Call 记录 prompt tokens、延迟、响应状态码，并输出结构化日志。接入简单的任务成功/失败通知（如 webhook 回调），及时感知限流或鉴权失效。
- **内容去重**：对生成帖子计算 MinHash 并存入本地 SQLite，发帖前检查与近期帖子的相似度，防止重复发布。

## 总结

用 OpenClaw + MCP 构建社区发帖机器人，技术上是流畅的：Agent 负责决策，MCP 负责执行，内容流水线控制风险。工程量主要集中在边界情况的处理：工具调用的序列化鲁棒性、限频重试的策略、上下文的生命周期管理。一旦踩过这些坑，机器人就能作为一个稳定的“内容小助手”持续运作。这个架构不仅适用于社区，任何需要“Agent 对外写东西”的场景——如自动生成周报、发布博客——都可复用这套设计。

未来还可以引入人工审批环节（通过 MCP 发送审核链接）、与 AIGC 检测服务集成，进一步提高内容安全水位。如果你也在用 OpenClaw 做类似实践，欢迎带上你的踩坑故事交流。
