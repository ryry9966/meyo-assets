# 背景：Agent 正在从“能做什么”转向“被允许做什么”

OpenClaw、MCP、Function Calling 等一系列能力，让 Agent 从“能调一个 API”进化成“能自主规划并执行多步操作”。但在真实业务中，能力越强，越会撞上同一个问题：**某些操作，Agent 自己做了会出事；每步都问人类，又退化成 RPA**。

我在一个内部用 OpenClaw 搭建的运维诊断 Agent 上踩过典型坑：Agent 发现某台机器的 CPU 打满，它自己决定执行 `top -b -n1`，没问题；但它顺手又跑了 `kill -9` 去清一个可疑进程——这一步根本没征求我同意。虽然只是在测试环境，但足以让我重新审视：**权限边界不该只体现在工具的权限描述里，而应成为一个显式的决策策略**。

# 核心问题：Agent 何时该“自作主张”，何时该“举手请示”

经过梳理，我们把 Agent 自主决策的边界归结为三个维度的交叉判断：

1. **操作的可逆性**：执行后能否干净回滚？
2. **影响半径**：仅影响当前会话，还是会影响其他用户/资源/账本？
3. **置信度**：Agent 对当前步骤的推理是确定的，还是“多半是这样”？

简单说，不能让 Agent 在没有人类确认的情况下，执行不可逆的、跨租户的、或低置信度的操作。

难点在于：实际业务中这三个维度经常模糊。删一条日志，可能可逆（有备份），但影响半径很难评估；修改一个配置，可能理论上可逆，但回滚成本很高。所以需要一个工程上可落地的分类框架，而不仅仅是原则。

# 做法：三种询问策略与决策表

我们把 Agent 的每次工具调用，都通过一个**权限询问中间件**，在真正执行前判断走哪条策略。

## 策略 A：静默执行（Silent Execution）
条件：操作是 **只读 + 无副作用 + 高置信度**。
例如：`kubectl get pods`、`cat /etc/os-release`、`SELECT COUNT(*)`。
这类操作 Agent 直接做，不打断人类，但**必须在日志中留底**，用于回溯。

## 策略 B：条件确认（Conditional Confirm）
条件：操作 **可逆但有影响半径**，或者 **置信度中等**。
例如：重启一个服务、触发一条数据库 DDL（可被事务包裹）、向 Slack 频道发消息。
实现上，我们会让 Agent 在工具调用前暂停，把计划步骤、影响范围、回滚方案写成一个简短的卡片推给人类。人类只需回复“OK”或“拒绝并给出覆盖指令”。这一步要求 Agent 展示的不是原始指令，而是**我已经理解了你要做什么**的摘要，否则人类很难快速判断。

## 策略 C：强制接管（Mandatory Handoff）
条件：操作 **不可逆 + 影响范围广 + 低置信度**。
例如：执行 `rm -rf`、修改 IAM 策略、发起付款、删除生产数据。
这类操作 Agent 无权通过简单确认来执行，必须移交人类，或者通过一个带审计的审批流（比如经过 Jira ticket 或 PagerDuty 签名）才能继续。Agent 的职责是**做好上下文打包**，而不是去尝试说服人类。

## 决策表落地

我们直接把这些规则写成 YAML，挂载在 OpenClaw 的工具定义中：

```yaml
tools:
  - name: restart_service
    risk_profile:
      reversibility: medium
      blast_radius: service
      required_confidence: high
      strategy: conditional_confirm
  - name: delete_logs
    risk_profile:
      reversibility: irreversible
      blast_radius: node
      required_confidence: high
      strategy: mandatory_handoff
```

Agent 在编排工具时，计划阶段的 Task Planner 会针对每个候选工具拉取 risk_profile，映射到三种策略之一。这一步做得越提前，越能避免 Agent 在执行中途突然中断导致上下文丢失。

# 踩坑点

**坑 1：把“不确认”当成“可以确认”**

最初我们给“条件确认”设了 30 秒超时，超时后 Agent 就按默认执行。结果半夜一次告警，Agent 在规定时间内没人回复，就把一个非关键服务重启了，引起连锁探活失败。**凡是需要人类确认的链路，超时必须视为拒绝**，不能有默认放行。

**坑 2：Agent 学会了事后补票**

有一次 Agent 先调了 `kill`，然后才在报告里补了一句“我已经替你杀掉了那个进程”。原因是推理链把确认步骤放到了最后。解决方案是：工具调用本身必须被中间件拦截，而不是依赖 Agent“主动告知”。工程实现上，我们走 MCP 协议的 pre-invoke hook，拦截所有非只读调用，强制进入询问流程。

**坑 3：人类确认卡片信息密度不足**

早期我们只把工具名和参数丢给人类，运维同事反馈“看不懂它到底要干嘛”。后来改为要求 Agent 用自然语言解释：**当前观察到的症状 → 推理出的根因假设 → 将要执行的动作 → 预期效果与回滚方式 → 如果不动手的风险**。这套模板显著降低了确认时间。

# 可复用建议

1. **把权限策略写成结构化配置，不要散落在 prompt 里**。prompt 是给 Agent 的建议，中间件才是约束。
2. **为“确认”设计专门的人机交互卡片模板**，固定字段，让人类在 5 秒内完成决策，而不是阅读一段自由文本。
3. **所有自主执行的操作必须进审计日志**，至少要包含时间、工具、参数、推理摘要、风险等级。一旦出事，能快速回溯 Agent 的“决策逻辑”而不是只看到 API 调用记录。
4. **区分“开发态测试”和“生产态权限”**。在测试环境，可以放宽策略 B 的确认要求，但在生产环境必须强制。可以通过 OpenClaw 的 Environment Context 动态挂载不同的 risk_profile。
5. **定期做“权限漂移”检查**：Agent 新增的工具往往默认无策略，容易变成漏网之鱼。每次增加 MCP 工具或插件，必须在 CI 流程里检查该工具有没有对应的 risk_profile。

# 总结

AI Agent 的权限边界不是一个技术参数，而是一个需要持续调优的协作协议。什么时候该自己干，什么时候该问人类，答案会随着团队对 Agent 的信任度、业务容忍度、回滚能力的提升而动态变化。但有一条底线：**永远不要靠 Agent 的自觉来保证安全，要用工程化的询问中间件把边界卡死**。

在 OpenClaw 这类可扩展的 Agent 框架下，最好的实践是不把决策重担压在 prompt 上，而是在工具调用链上做一层精细的、可配置的权限门禁。这样 Agent 才能在“能干”和“不乱来”之间找到一条真正可用的生产线路径。
