## 背景
在 OpenClaw 生态里，越来越多团队用 Agent 直接产出长文——技术博客、产品周报、使用手册。默认输出几乎都是 Markdown。但一涉及“把同一篇文章发到公众号、知乎、掘金、内部知识库”时，格式问题就集中爆发：有些编辑器不支持脚注，有些把代码块吞掉，有些把表格渲染成一行字。

纯靠人工逐平台校对，既低效又不可持续。更麻烦的是，每次大模型更新或 prompt 微调后，输出格式可能轻微漂移，之前的适配脚本直接失效。我们需要的是一条工程化、可复现的 Markdown 管线：上游接任意 AI 生成的原始 md，下游输出各平台就绪的格式。

## 核心问题拆解
1. **AI 生成 Markdown 的一致性差**  
   不同模型、同一模型不同对话轮次，对缩进（2 空格还是 4 空格）、列表符号（`-` 或 `*`）、空行数量、代码块语言标注的处理都不一样。直接输出到严格渲染器时容易变形。

2. **多平台渲染规则零散**  
   - 微信公众号：本质是富文本，不支持 Markdown，需转成带内联样式的 HTML，且外部链接有屏蔽风险，图片需提前上传返回自有 URL。  
   - 知乎：支持部分 Markdown，但表格、公式、脚注支持差，代码高亮依赖特定标签。  
   - 掘金：有 front matter 约定，封面图必须从正文提取，且禁止某些 HTML 标签。  
   - 自建博客（VitePress / Hexo）：一般标准 Markdown 兼容良好，但需要统一资源路径。

3. **公式、图表等复杂内容的退化**  
   LaTeX 公式在多数内容平台无法直接渲染，需提前转成 SVG 或 PNG 并嵌入。AI 生成的 ASCII 图表也可能需要合成图片。

4. **发布接口各异**  
   公众号需要走官方 API + 草稿箱；知乎和掘金有各自的开放 API；自建站可能用 Git push 触发 CI。管线必须对接不同发布协议。

## 做法与步骤
我们设计的管线分三层：解析标准化 → 规则转换 → 目标输出与发布。依托 OpenClaw 的 Agent 调度能力和 MCP 插件生态，各环节可以解耦。

**1. 标准化处理（基于 AST）**  
不直接操作字符串。使用 remark 解析成 mdast 语法树，再统一注入规范化插件：
- `remark-preset-lint-markdown-style-guide` 统一列表符号、强调语法、标题层级。
- 自定义插件修正空行：标题前保证一个空行，代码块前后保留空行。
- 将 AI 可能输出的非标准 HTML（如 `<br/>`）转为标准 md 换行。

标准化后的 AST 序列化为一份“干净 Markdown”，作为后续所有平台的唯一中间源。

**2. 平台适配转换**  
对每个目标平台维护一个独立的转换配方：
- **公众号**：用 `remark-rehype` 转 HTML，再遍历 hast 树，把代码块包装成带高亮类的 `<pre><code>`，并注入通过 CSS 内联处理的样式。外链统一替换为跳转提示或短链接。图片节点触发 MCP 图片上传工具，返回的 `media_id` 替换 src。最终 HTML 片段可直接通过公众号草稿 API 提交。
- **知乎 / 掘金**：保留 Markdown，但通过插件移除不支持的语法（脚注转成括号说明，复杂表格转成无边框图片），并根据平台约定添加或修改 front matter。知乎的公式使用 `rehype-mathjax` 预渲染成 SVG 并注入 img 节点。
- **知识库（如 Notion、飞书）**：通过 MCP 插件调用对应 Block API，将 md 文档分段映射为 block 结构。

**3. 输出与发布编排**  
用 OpenClaw 的 Agent 工作流串联：读取 AI 生成的原始 md → 标准化 Agent → 多个平台适配 Agent 并行执行 → 结果存入草稿目录 → 人工复核后触发发布 Agent。发布 Agent 可以是执行 API 调用的 MCP Server，也可以输出可直接粘贴的富文本。

## 踩坑记录
- **代码块高亮的幻觉**：AI 有时标注语言为 `javascript` 全小写，但平台高亮库（如 Prism）依赖别名映射，如果映射缺失就无高亮。我们统一在标准化阶段将语言字段映射到标准 alias 集合。
- **嵌套列表缩进**：公众号转换时需要将列表转成带 `margin-left` 的段落，但 2 空格和 4 空格混用会导致层级错乱。强制规范化列表缩进为 4 空格并基于此生成 HTML 层级。
- **图片链接的时效性**：AI 生成常带外部图片 URL，但多个内容平台不允许外部图片（知乎允许但可能屏蔽）。必须将图片下载后重新上传到各平台 CDN，管线中需增加重试与缓存，防止同一图片反复下载上传。
- **公式在移动端**：渲染的 SVG 公式在手机端可能不缩放，需要添加 `width="100%"` 和 `preserveAspectRatio` 设置，通过 rehype 插件插入属性。
- **API 限制**：公众号草稿接口每日调用次数有限，且内容包含敏感词时会静默失败。必须增加校验与重试，并在发布前扫描敏感词。

## 可复用建议
1. **使用统一的中间 Markdown 标准**  
   推荐以 CommonMark + GFM 表格/任务列表为中间格式，不使用脚注、定义列表等非标准扩展。扩展风格转换由适配层负责。

2. **将转换逻辑封装为 MCP Server**  
   每个适配器（公众号、知乎等）作为独立的 MCP 工具，输入为标准化 md，输出为目标格式文本或 API 响应。Agent 可以通过 MCP 发现和调用，避免硬编码。

3. **配置文件驱动规则**  
   用 YAML 描述每个平台的转换规则和发布参数，如：
   ```yaml
   platforms:
     wechat:
       transform: wechat-adapter
       publish: wechat-draft-api
       options:
         remove_external_links: true
         code_theme: "github"
   ```
   这样新增平台成本低，且便于版本管理。

4. **引入格式校验门禁**  
   在标准化后输出前，使用 markdownlint 检查，若有严重格式问题直接中断流水线并通知，防止脏数据进入后续转换。

5. **保留草稿与人工审核节点**  
   自动化不等于无人值守。发布前生成预览链接或本地预览，人工确认后再推送到正式接口。可在 Agent 流程中插入挂起等待人工审批的 MCP 工具。

## 总结
构建从 AI 生成到多平台发布的 Markdown 管线，并不是想做一锤子买卖的“万能转码器”，而是建立一套可持续维护的标准化与适配机制。在 OpenClaw 技术栈中，结合 remark/rehype 生态做 AST 级转换，再用 MCP 封装各平台适配器，能显著降低格式适配的工程成本，让内容产出真正跑起来。随着 Agent 生成内容越来越长、越来越复杂，这条管线会从“锦上添花”变成必备的基础设施。
