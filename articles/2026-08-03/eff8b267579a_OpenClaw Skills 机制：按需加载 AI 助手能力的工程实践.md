## 背景

在使用 OpenClaw 这类面向复杂任务的 AI 助手上，我们常会集成文件操作、网页抓取、Shell 执行、数据库查询等能力。早期做法是把所有工具一次性注册到系统提示和工具列表中，让模型知道自己“什么都能做”。这种做法在简单场景下尚可，但任务一多就会暴露三个明显问题：

- **Token 消耗失控**：数百行的工具描述挤占上下文窗口，每一个请求都要带着完整能力清单。
- **模型混淆**：工具过多会让模型误判意图，把不需要的能力塞进 Plan，甚至调用错误的工具。
- **扩展不便**：每次新增能力都要修改核心配置文件，不同项目之间难于复用。

为了解决这些问题，OpenClaw 引入了 **Skills 机制**，核心思想是把能力拆成独立模块，运行时根据用户意图或显式指令**按需加载**。这类似于操作系统里的动态链接库，也呼应了 Agent 工程中“组合优于继承”的原则。

## 问题场景

假设你维护着一个辅助开发者日常的 OpenClaw 助手，它要同时处理代码重构、日志分析、部署脚本生成。如果一次性挂载所有 skill，哪怕用户只是问“帮我分析这个日志”，模型也会看到“Kubernetes 部署”“AWS 凭证管理”等无关工具——不仅浪费 token，还增加了幻觉风险。更麻烦的是，不同 skill 可能定义同名的函数（如 `read_file`），加载冲突后会直接报错。

而按需加载则要求助手能够判断当前对话需要哪些能力，然后才注入对应的工具和指令。这背后需要一套触发匹配与动态加载机制。

## Skills 工作机制（以 OpenClaw 现行设计为例）

OpenClaw 的 Skills 机制基于**声明式定义 + 自动触发**模式。每个 Skill 是一个独立目录，包含 `skill.yaml` 配置文件，大致结构如下：

```yaml
name: log-analyzer
description: 分析应用日志、识别异常模式、生成摘要。
triggers:
  - 关键词: ["日志分析", "log analysis", "异常检测"]
  - intent: log_inspection
tools:
  - name: grep_logs
    description: 在日志目录中按模式检索...
    schema: { ... }
instructions: |
  你需要先确认日志来源，再用 grep_logs 过滤...
```

核心要素：
- **triggers**：定义触发条件。可以是对话中出现的关键词、意图分类结果，或是用户显式输入的命令（如 `/use log-analyzer`）。
- **tools**：该 Skill 专属的工具列表，仅在 Skill 激活时添加到会话。
- **instructions**：专属的系统指令，会追加到当前上下文中，指导模型如何组织工作流。

运行时，OpenClaw 的调度器会在每轮对话中检查用户输入，与各个 Skill 的 trigger 做匹配。一旦命中，就将 tools 和 instructions 注入当前上下文，模型即刻获得这项能力。任务结束后（或显式卸载），加载的 Skill 可以被回收，避免污染后续对话。

这样设计的好处是，助手的基线系统提示始终保持轻量，能力按需膨胀。

## 操作步骤

1. **创建 Skill 目录**  
   在 OpenClaw 配置指定的 `skills/` 路径下新建子目录，如 `skills/log-analyzer/`。

2. **编写 skill.yaml**  
   按上述结构填写 name、description、triggers、tools、instructions。**description 字段极其关键**，因为在某些模式下，调度器会依据 description 做语义匹配，而不仅仅依赖固定的 trigger 关键词。

3. **定义工具实现**  
   如果 Skill 需要执行本地脚本，可以将脚本放在同目录下，并在 tools 的 `handler` 字段中指定调用方式（如 `python my_script.py`）。

4. **配置加载策略**  
   在 OpenClaw 主配置中启用 `skill_auto_load: true`，或者指定仅允许手动加载。手动加载模式下，用户可通过对话指令触发，避免自动匹配的误触。

5. **测试与观察日志**  
   用典型用例测试触发情况，通过 OpenClaw 的运行时日志查看 `[SkillLoader]` 相关信息，确认 Skill 是否被正确激活以及 tools 是否注入成功。

## 踩坑点

**触发条件过于宽泛导致误加载**  
如果 `triggers` 只写了一个常见词如“文件”，会导致助理每次提到文件就加载整个文件管理 skill，反而干扰其他任务。建议结合多关键词组合，或使用更明确的 intent 标签。

**工具 Schema 冲突**  
多个 Skill 内如果定义了同名函数，加载时会直接冲突。OpenClaw 目前没有命名空间自动隔离，解决办法是统一加前缀（如 `log_grep` 而非 `grep`），或者在 `skill.yaml` 中声明 `tool_prefix`。

**上下文膨胀**  
虽然按需加载了，但部分 Skill 的 instructions 过长，注入后仍然会挤占上下文。推荐将 instructions 写成精简版，详细知识放在工具 description 中，或使用外部知识库按需检索。

**版本不匹配**  
人手维护的 Skill 多了以后，很容易出现配置文件格式更新而旧 Skill 未同步的情况。建议在目录中加一个 `version` 字段，加载前做兼容性检查，或直接在 CI 中跑格式校验。

## 可复用建议

- **单一职责**：一个 Skill 只做一类事。比如把“Git 操作”和“Issue 追踪”拆成两个 Skill，触发精度和可维护性都更高。
- **强化 description**：即使有 triggers，也建议把 description 写得像给模型看的“使用说明书”，因为有时调度器会基于语义选 Skill。
- **利用 MCP 封装远程工具**：如果某些能力是通过 MCP 服务提供的，可以在 Skill 的 tools 里直接声明 MCP 资源，OpenClaw 会按需连接，避免长连接占用。
- **建立 Skill 模板仓库**：团队内可以维护一套标准化模板，包含 example trigger、错误处理兜底指令，减少重复踩坑。
- **监控加载频率**：统计各个 Skill 的加载次数、平均存活轮次，帮助发现哪些 Skill 被过度触发或从未使用，有针对性地优化 trigger 或合并低频 Skill。

## 总结

OpenClaw 的 Skills 机制本质上是一种**动态能力注入**策略，让 AI 助手在面对多样化任务时保持提示词精简、工具集干净，同时不失灵活性。它符合 Agent 工程中的模块化思想：内核保持稳定，外围能力像插件一样按需挂载。实际落地时，仍然需要在触发精度、命名规范、上下文管理上做工程化打磨。当你的助手需要从“能聊天”走向“能做事”，按需加载就是一个值得认真配置的环节。
