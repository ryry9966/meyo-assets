## 背景

大多数 OpenClaw 用户的日常是：给 Agent 发指令，它执行，你等结果。这套 ReAct 模式跑通之后，大家自然会想下一个问题——能不能让它在我开口之前就把事办了？

这不是异想天开。对于规则明确、状态可感知、执行后果可逆的事情，Agent 完全可以在人类介入之前自主完成。但现实是，很多人尝试做 proactive 时都会卡在一个点上：**不是模型不行，而是触发链路没有设计清楚**。

这篇文章基于我在 OpenClaw 上跑通的 proactive 实践，讲清楚一个最小可复用的架构，以及那些文档里不会告诉你的坑。

## 问题

Proactive 的本质是事件驱动。拆开来看，它由三个问题组成：

- **什么时候触发？** 靠什么感知到"该干活了"。
- **该不该动？** 意图判断和授权边界。
- **做完了通知谁？** 结果如何触达用户。

很多人做失败，是因为试图让 Agent "随时思考该干什么"——这是伪需求。真正的 proactive 不是创造一个全知全能的常驻大脑，而是把**高频、规则明确、状态可迁移**的事情，交给事件流去驱动。

## 做法

下面是一个我验证过的最小链路，用到的都是 OpenClaw 原生能力和 MCP 生态：

### 第一步：定义触发源

Proactive 的触发源通常分两类：

1. **定时触发**：适合有明确周期的任务。比如每天早上 9 点检查服务器磁盘占用，超过 80% 自动清理旧的构建产物。
2. **事件触发**：适合状态变化驱动的任务。比如收到新的 GitHub Issue 时，自动打标签并分配给维护者。

在 OpenClaw 里，我用一个简单的 scheduler loop 挂载 Agent 作为 event handler。核心思路是：**Agent 是执行者，不是轮询器**。轮询和事件订阅由外层容器负责，Agent 只负责收到事件后的判断与执行。

### 第二步：设计意图过滤

收到事件不等于要执行。一个常见的错误设计是"收到任何事件都让 Agent 决定要不要动"——这会让你的 API 账单爆炸，而且 Agent 会在大量无关事件上做无意义推理。

我的做法是加一层**规则前筛**：

- 事件先经过结构化 filter（比如只看 label 为 `bug` 的 issue）
- 通过前筛的事件才进入 Agent 的上下文

这层前筛可以用简单的脚本实现，不需要大模型参与。成本低，速度快，还顺带给 Agent 省 token。

### 第三步：授权边界与人工确认

Proactive 不等同于全自动。对于后果不可逆的操作（删数据、发消息、花钱），我设置了一个 `confirm` 机制：

在 Agent 的 system prompt 里明确写：对于 `[destructive]` 类工具，必须返回一个 `pending_confirmation` 状态，通过 IM 通道（我用的 Telegram MCP）推送给用户，等待确认后才继续执行。

对于可逆操作（创建草稿、打标签、写日志），则可以直接执行，事后在通知里汇总。

### 第四步：结果触达

执行完不算完。用户需要知道"你已经帮我办了"。我习惯把所有 proactive 动作的执行摘要写入一个统一的 `proactive_log`，每次执行后通过通知通道推送。这样用户不会觉得 Agent 在背后乱动——透明性是信任的前提。

## 踩坑点

几个实际遇到的问题，供参考：

1. **通知疲劳**：一开始我设了"每次清理完都通知"，结果两天后用户把通知静音了。后来改成只通知"异常情况"和"本周摘要"，保留了 Agent 的知情权，砍掉了打扰频率。
2. **重复触发**：没有做去重/幂等设计，导致同一个事件被处理了两次。我加了 `event_id` 的 dedupe cache，所有事件入口都先查重。
3. **Agent 幻觉式 proactive**：模型有时会在没有触发条件的情况下"自作主张"执行操作。解决办法是把触发源的判断逻辑完全剥离出模型决策，模型只负责"收到指令后怎么执行"，不负责"要不要执行"。

## 可复用建议

给想尝试的 OpenClaw 用户几点建议：

- **从一个场景切入**，不要一开始就做全场景 proactive。磁盘清理、工单分配这类"低风险、高确定性"的活儿是最好起步的。
- **给 Agent 一个过滤 prompt 模板**，我目前在用的：

```
你是一个事件处理助手。收到事件后，按以下步骤执行：
1. 判断事件类型是否在你的职责范围内
2. 若不在范围内，回复 SKIP 并说明原因（不超过 10 个字）
3. 若在范围内，执行对应工具，并返回结构化摘要
```

- **proactive_log 建议用 JSON Lines 格式**，方便后续统计和分析哪些 proactive 动作真正被用户认可（没有被打断/撤销）。
- **设计"打扰预算"**：每周能主动打扰用户多少次，用完了就只能等用户主动发起。这个机制能强迫你认真筛选什么值得 proactive。

## 总结

Proactive 能力不是让 Agent 变得"像人一样主动"，而是把**事件驱动 + 规则过滤 + 授权边界 + 透明通知**这四件事串成一条流水线。核心原则是：让模型做判断和生成，让规则做裁决，让用户始终保有最终确认权。

在 OpenClaw 的体系里，这套链路用 cron/scheduler + MCP 工具 + IM 通知就能实现，不需要复杂的编排框架。门槛不高，但设计细节决定体验。

下次当你发现自己在重复做同一件查状态、整理、通知的活儿时，不妨把它交给 Agent——它不需要变聪明，只要你在合适的地方放了触发器。
