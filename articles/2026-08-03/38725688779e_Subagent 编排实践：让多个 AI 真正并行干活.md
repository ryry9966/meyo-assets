## 背景

单 Agent 跑一个复杂任务时，最常见的形态是"顺序执行"：检索 → 思考 → 调用工具 → 再检索。逻辑上没问题，但一旦任务包含多个独立子任务，顺序执行就会把时间浪费在等待上。

我们的场景是处理一批代码仓库的合规审查：每个仓库需要读取配置文件、扫描依赖版本、检查日志规范，最后输出一份审查报告。一开始用单个 Agent 逐个处理，三个仓库跑完花了 40 多分钟，而且中途一旦某一步出错，整个任务就挂住。

## 问题

单 Agent 的瓶颈不是模型能力，而是串行。

- 子任务之间没有数据依赖，却被迫排队执行；
- 长任务的上下文越滚越长，token 消耗呈指数增长，末尾的表现明显退化；
- 一个子任务的失败会阻塞全部后续流程。

用 subagent 编排的本质，就是把一个大任务拆成互相独立的子任务，交给多个 Agent 并行执行，最后统一汇总。这跟并发编程里的 fork-join 是一个道理。

## 做法

我们最终在 OpenClaw 里落地了这样一个模式：一个 orchestrator 负责拆解、一个 worker pool 负责执行、一个 collector 负责合并。三者都是 Agent/子 Agent 的角色，通过 MCP 工具调用和结构化消息协作。

**第一步：任务拆解（planner）**

Orchestrator 先读取总任务，输出一个 JSON 形式的子任务清单。每个子任务必须包含明确的输入路径、期望输出格式和依赖列表。关键约束：子任务之间不允许有隐式依赖，如果发现 A 的结果会被 B 使用，就把它们合并成一个任务。

**第二步：并行分发（dispatcher）**

每个子任务作为一个独立的 subagent 实例启动，用 OpenClaw 的 task 调度并发执行。我们按"一组最多 4 个并行 subagent"来控制资源占用，避免一次性起太多导致 API 限流或上下文堆积。每个 subagent 只拿到自己的子任务 brief，不知道自己之外还有别的 Agent 在跑——这很重要，能让它们专注于局部问题。

**第三步：合并与校验（collector）**

所有 subagent 返回结果后，collector 做两件事：

1. **格式校验**：检查结果是否符合约定的 schema（字段齐全、路径正确）。
2. **冲突处理**：如果两个 subagent 的结果有重复或矛盾，collector 不是直接改，而是把冲突项单独拎出来重新跑一次定向子任务。

最后，collector 把干净的结果整理成最终报告。

## 踩坑点

这部分是真实成本。

**坑 1：共享状态污染**

最早的版本让所有 subagent 共享同一个工作目录，结果两个 Agent 同时往同一路径写临时文件，互相覆盖。解决办法是每个 subagent 一个独立工作目录，最终产物统一放到约定的输出区。

**坑 2：上下文丢失**

子 Agent 在执行过程中如果需要查一些全局信息（比如总数、批次号），我们最初让它们自己拼 prompt，结果不同 Agent 拼出来的口径不一致，最后的报告数字对不上。解决方式是 orchestrator 在分发前就把所有必要信息塞进 brief，子 Agent 不允许自行补充全局上下文。

**坑 3：成本失控**

并行意味着 token 消耗暴增。第一轮实验跑一个 5 子任务的任务，直接烧掉了单任务串行 3 倍的 token。我们加了硬限制：每个子任务最多轮询 3 次工具调用，超过就终止并标记为"不完整"，由 collector 决定是否重试。

**坑 4：失败重试语义不明确**

如果某个子 Agent 超时或崩了，直接整个任务重跑会浪费前面的成果。我们的做法是子任务级别重试：只重发失败的那一个，其他结果保留等待。

## 可复用建议

1. **任务接口要窄**：subagent 的输入输出是结构化的，尽量只用 JSON，不要用长文散文描述。这就跟函数签名一样，接口越窄越不容易出错。
2. **默认 4 并发，不贪多**：并行度不是越高越好，要考虑 API 限流、上下文显存占用的现实约束。实测 4 并发是稳定性和速度的平衡点。
3. **给每个子任务一个"不干活的选项"**：允许子 Agent 声明"信息不足，无法完成"，比让它硬编一个答案强得多。
4. **合并前先校验，校验不通过就重跑**：不要靠 collector 去"修复"格式错误，让上游重来。
5. **全程留日志**：每个子任务的开始时间、耗时、token 数、结果摘要都记录到一个统一清单里。出问题时这个清单比聊天记录有用一百倍。

## 总结

Subagent 编排不是一个炫技功能，它解决的是真实存在的工程问题：任务可并行时，为什么要串行等？但并行也带来了状态管理、成本控制和一致性这些新复杂度。我们现在的结论是：**能用单 Agent 快速完成的，不要硬拆；拆开的子任务，接口和边界必须定义清楚；并行的红利靠调优拿到，不是靠堆数量**。

以后如果再做大任务拆分，我会优先按"数据是否独立"来划分子任务边界，而不是按"职责是否不同"——前者真正利于并行，后者只是让代码更好看。
