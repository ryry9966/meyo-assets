单 Agent 处理复杂任务时，输出质量随上下文变长而下降，且主链路每一步都是串行的。把多个模型实例挂上去各干各的，听起来是"并行"，但真正的问题是：怎么分活、怎么收口、怎么容忍失败。

## 问题

把任务拆给 subagent 后，最常见的问题不是"不干活"，而是：

- 每个 subagent 返回格式不一致，合并时要清洗
- 一个 subagent 崩了，整条任务跟着失败
- 并行写入同一份文件、或调用同一个 MCP 工具时出现竞争
- 上下文污染：子任务的思考链被带进主流程，主决策被干扰

## 做法/步骤

以一个"多源调研 + 汇总"任务为例（OpenClaw + MCP 场景）：

**1. 任务拆分**
在主 Agent 中定义固定的拆分函数，按数据源切分：Web 搜索、Slack 历史、本地文档各为一个子任务。每个子任务只带最小上下文（源路径、查询条件、输出 schema），不要带主对话历史。调用 subagent 时显式指定 `inherit_context: false`，避免把主流程的闲聊内容喂给子任务。

**2. 并行执行**
给每个 subagent 独立超时（如 60s），用 `allSettled` 风格收集结果——成功与失败分开记录，而不是一票否决。子任务之间互不阻塞，超时的直接标记失败。

**3. 结构化解构**
要求每个 subagent 输出严格 JSON：`{"status": "ok" | "error", "data": {...}, "refs": [...]}`。OpenClaw 的 tool call 天然走 JSON 路径，拿到后用 schema 校验，不合法直接判失败。

**4. 收口合并**
主 Agent 只拿到 3 个结构化结果 + 错误列表。合并策略：2/3 成功则继续，失败项在最终报告中单独列出；过半失败则终止，并给出重试建议。

## 踩坑点

- **格式漂移**：让模型"尽力输出 JSON"不可靠，必须 schema 校验 + 重试一次（附上校验错误信息）。
- **上下文污染**：subagent 返回的结果里带思考链，合并层容易被带偏。只允许返回结论字段，过程日志单独走文件。
- **并发限流**：并行开 5 个以上 agent，提供商 API 容易 429。实测 3 路并发较稳，必要时错开 200ms 启动。
- **MCP 工具竞争**：多个 subagent 同时写同一个 note 文件会互相覆盖。给每个任务分配独立 namespace 或加文件锁。

## 可复用建议

- 拆分遵循"数据源隔离"原则，而非"主题隔离"——同一数据源内的查询串成链，避免重复读。
- 输出一律走 JSON schema，外层带 `schema_version`，方便日后换模型。
- 做失败注入测试：故意让一个子任务超时，验证主流程的降级输出符合预期。
- 日志里给每个 subagent 打 `trace_id`，便于回溯谁拖慢了链路。

## 总结

Subagent 编排不是把活丢给多个模型就完事，而是一个工程问题：划定边界、收敛输出、容忍失败、可观测。先跑通 3 路并行，再逐步加路数，比一开始就追求高并发靠谱得多。
