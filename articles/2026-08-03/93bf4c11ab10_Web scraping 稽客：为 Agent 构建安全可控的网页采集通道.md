在 Agent 驱动的自动化流程里，网页内容采集几乎是刚需。无论是信息聚合、竞品监控还是知识库构建，让 Agent 自己“看网页”并提取结构化信息，可以省去大量人工搬运。但直接让 Agent 裸调 `requests` 或 `curl` 去抓页面，很快就会被目标站点封禁，甚至引发合规风险。工程化的做法，是在 Agent 和 Web 之间竖起一道“稽客”层——一种安全、可审计、尊重目标站点规则的采集策略。

## 问题拆解：为什么 Agent 挂网页经常翻车

典型的 Agent + 网页采集故障模式包括：

- **无 User-Agent 伪装**：默认 UA 可能直接暴露脚本身份，触发 WAF 直接拦截。
- **无速率控制**：Agent 在多轮对话、多次工具调用中短时间内高频访问同一域名，直接被 IP 封禁。
- **无视 robots.txt**：搜索引擎和合规爬虫需要遵守的约定，在 Agent 工具链里常被忽略，容易踩到法律红线。
- **内容无序解析**：抓回整页 HTML（含脚本、样式、广告），既不安全，也浪费 token，还容易污染 Agent 的判断。
- **缺乏失败重试与熔断**：一次被 ban 后，持续的失败请求会在 Agent 推理回路里反复触发，浪费资源且暴露身份。

这些问题不是简单的“换个 IP”就能全部解决，需要一套体系化的稽客机制。

## 稽客的设计：让 Agent 请求变成“合理访客”

稽客的核心目标不是隐藏采集行为，而是让采集行为对目标站点“无害且可解释”，同时保证 Agent 拿到的内容干净可用。可以按照以下层次来落地：

### 1. 请求身份的标准化
至少设置合规的 `User-Agent`（例如模仿普通浏览器，或使用标明 bot 身份的字符串并附带项目 URL）。对于更严格的站点，可以追加 `Accept-Language`、`Referer` 等常规头，降低指纹异常度。注意不要伪造搜索引擎爬虫 UA，那反而容易触发反欺诈机制。

### 2. robots.txt 解析与遵守
每次对域名发起请求前，应先拉取并解析该域的 `robots.txt`，判断目标路径是否允许访问，以及推荐的 `Crawl-Delay`。这一步可以缓存，避免频繁拉取。当 `Disallow` 命中时，稽客层应直接返回明确的拒绝理由给 Agent，而不是强行请求。这样既保护目标站点，也让 Agent 的决策可解释。

### 3. 请求速率队列
对每个域名维护独立的请求间隔，遵守 robots.txt 中的延迟，若无明确声明，默认延迟 2 秒，并加入±20% 的随机抖动。可以使用滑动窗口计数器或令牌桶实现，极端高频的 Agent 调用会被动排队。

### 4. 内容安全净化
返回给 Agent 的应只是主要文本内容，过滤掉 `<script>`、`<style>`、评论、广告侧栏等。优先使用可读性提取器（例如基于 `readability` 算法的库），输出纯文本或简化 Markdown。这样做不仅降低上下文长度，更重要的是阻断恶意内容注入，避免 Agent 执行抓取到的脚本指令，提升安全性。

### 5. 可观测性与熔断
记录每一次采集的域名、路径、状态码、耗时、是否被限流或拦截，方便排障。当某域名连续返回 403/429/5xx 超过阈值时，自动熔断一段时间，并向 Agent 返回友好提示：“目标站点暂时不可用，请稍后重试”，而不是把一堆报错交给 Agent 自行处理。

## 在 OpenClaw 中的落地步骤

如果你的 Agent 环境基于 OpenClaw 或类似的 MCP 架构，推荐使用已有的 MCP 服务来实现稽客，快速得到工程化收益。例如启用 `firecrawl-mcp` 或自建一个安全的 scraping MCP server。

**配置示例**（`openclaw.yaml` 或 MCP 配置段）：

```yaml
mcp_servers:
  safe-fetch:
    command: npx
    args:
      - "@anthropic/firecrawl-mcp"
    env:
      FIRECRAWL_API_KEY: "${FIRECRAWL_API_KEY}"
      MAX_RETRIES: 3
      RESPECT_ROBOTS_TXT: true
      RATE_LIMIT_PER_DOMAIN: 2000   # 毫秒
```

在 Agent prompt 中明确定义调用规则：

```
当需要获取网页内容时，务必使用 safe-fetch 工具，禁止绕过它直接调用 curl、http_request 等。
如果 safe-fetch 返回“被拒绝”或“熔断”，请记录该域名状态并等待 5 分钟后再试，不要立即重试。
```

这样，Agent 的行为就被限制在一个受控走廊里。

## 踩坑与排障

在实际使用中会遇到一些边界问题：

- **robots.txt 不标准**：部分小站用 404 或 500 代替“无限制”，应在解析失败时默认允许但降低速率，并记录告警。
- **JavaScript 渲染的页面**：稽客层如果仅做纯 HTTP 请求，SPA 站点只能拿到空壳。需评估是否引入无头浏览器，但成本较高。建议优先寻找站点是否提供 API 或 SSR 版本，或使用 `?format=json` 这类参数。
- **内容提取器误杀正文**：某些页面结构诡异（如论坛翻页），可读性算法可能截断关键信息。需要留一个“降级模式”，在捕获不到足够文本时返回原始 body 的摘要，同时通知 Agent 内容可能不完整。
- **Agent 的重试风暴**：即使有限流，Agent 可能因为一次失败而疯狂尝试不同路径，造成“无心 DDoS”。必须在稽客层做域名级别的请求计数，超阈值直接返回统一拒绝，不给 Agent 变道机会。
- **本地开发与生产环境的 User-Agent 差异**：本地测试可能用真实浏览器，生产跑在容器里就变成了默认 `Go-http-client/1.1`。务必在部署时检查稽客层的默认 UA，避免上线即被拦。

## 可复用建议

- **先评估，再动手**：明确你的 Agent 真的需要实时抓取，还是可以用预爬取的本地缓存或第三方数据集。
- **优先使用标准化 MCP 服务**：除非有特殊定制需求，不要从零造轮子。firecrawl、Jina.ai 等已经内置了合规、清洗、缓存等能力。
- **为稽客层建立单独的日志和监控**：采集成功率、延迟分布、封禁数，这些指标是判断 Agent 工作质量的重要依据。
- **在 Agent 指令中内嵌伦理规则**：即使技术层限制了，也要让 Agent 知道“为什么被拒绝”，避免它学着规避。例如：“遵守 robots.txt 是必须的，不允许绕过”。

## 总结

稽客不只是反反爬的技术对策，更是让 Agent 在开放网络上可持续运行的基础设施。它把 Web 采集从“想方设法拿到数据”提升为“以最不打扰的方式取得必要信息”，既降低了自身被屏蔽的风险，也减少了对目标网站的伤害。对于任何一个要在生产环境长期运行的 Agent 系统，稽客层应该是标配，而不是补救措施。
