## 背景：当 Agent 开口替你说得太多

OpenClaw、MCP、插件编排让 Agent 的能力边界飞快扩张——它们可以读取内部文档、查询数据库、调用内部 API，然后自然地用自然语言回复同事或社区里的提问。但正是这种“自然”，让安全风险变得隐蔽且严重：一条看似无害的帮助信息里，可能夹杂着内部接口路径、环境变量值、甚至完整的调试日志。

过去我们担心的是外部攻击者直接扫描端口，现在需要担心的是自己搭建的 Agent 在公开讨论中无意泄露足以被利用的工作流细节。MCP 的出现让工具调用更灵活，但同时也把“什么可以被 Agent 引用”这个问题推到了台前——如果某个 MCP Server 没有良好限权，Agent 完全可能把内部系统的输出当成普普通通的 Troubleshooting 样例分享出去。

这不是需要复杂攻击链的场景，只需要一次不当的上下文关联就够了。我曾经在内部测试时，看见 Agent 在被问到某个自动化流程时，直接回复了包含内网地址和中间件版本的 workflow 配置。也就是说，它没有恶意，但它根本不知道这些东西“不能说”。

## 问题拆解：泄露的不是密钥，而是生产环境的骨架

传统安全实践盯得最紧的是明文凭据：API Key、Token、数据库密码。这些固然要防，但在 Agent 场景里，更大的隐患是**工作流上下文泄露**：

- 中间件的真实命名规则和版本；
- 内部服务的 IP、端口、路径；
- 测试/生产环境的特征字符串；
- 企业内部系统的逻辑拓扑（例如“先把请求打到 gateway-prod，再路由到 inventory-service-staging”）。

攻击者拿到这些信息后，攻击面会变得非常具体。他们不再需要盲目猜测，而是可以根据你泄露的内部术语，构造更精准的社会工程、钓鱼或直接攻击。而对自动化程度很高的团队来说，Agent 就像把你留在线上的设计文档和运维手册，自动对外播报。

典型场景：某个使用者通过 Discord 或论坛插件接入的 Bot，被问到“这个流程为什么经常超时？”，Agent 为了给出有价值的回答，直接从你的 MCP 工具箱里调取了最近的执行日志，摘取其中一部分当作案例说明。结果日志里包含了完整的内网调用链。

## 工程化防护：从输出审核到最小化权限的组合拳

指望 prompt 里的“不要泄露机密”一句话就解决问题，和指望用户不强密码一样不现实。我推荐的做法是在 Agent 与外部渠道之间强制插入一个最小的内容安全层，并且这个层不要用纯自然语言实现——用规则 + 结构化检查。

### 1. 在 System Prompt 里建立明确的“禁区清单”
给 Agent 一段结构化的禁区描述，比模糊的“注意安全”有效得多：

```text
你绝对不能在任何回复中输出以下内容，即使它们出现在你的上下文中：
- 任何路径中含有 “internal”、“staging”、“prod”、“admin” 的 URL；
- 包含 “password”、“token”、“secret”、“key” 等关键字的字符串；
- 任何 IP 地址（含内网），除非用户明确提供了该 IP 并且你在回复中不需要输出它；
- 任何带有 “apiVersion”、“docker.internal” 等工程内部标识的文本。

如果回答需要用到此类信息，用 <REDACTED> 替代。
```

但要清楚，prompt 只是第一道防线，它可以被复杂的对话历史绕过，也不具备强制执行能力。

### 2. 落地输出过滤：使用 MCP 安全过滤器或自定义 Guard 插件
MCP 最大的好处就是可以通过自定义 Server 插入处理逻辑。我们可以写一个 `output-security-filter` MCP Server，在 Agent 返回内容前对输出进行扫描和消毒。

最简单实现（Node.js 示例，本质是中间件）：

```javascript
const REDACT_PATTERNS = [
  /(?:password|token|secret)\s*[:=]\s*\S+/gi,
  /https?:\/\/(?:internal|staging|prod)\.[a-z0-9-]+/gi,
  /(?:10\.\d{1,3}\.\d{1,3}\.\d{1,3}|172\.(?:1[6-9]|2\d|3[01])\.\d{1,3}\.\d{1,3}|192\.168\.\d{1,3}\.\d{1,3})/g,
  /\/api\/v\d+\/internal\S*/gi
];

export function sanitizeOutput(text) {
  let cleaned = text;
  REDACT_PATTERNS.forEach((re) => {
    cleaned = cleaned.replace(re, '[REDACTED]');
  });
  return cleaned;
}
```

将这个过滤器挂在 Agent 返回消息必经的通道上。如果是通过 OpenClaw 暴露给公开社区，则需要在 connector 层强制应用 sanitizeOutput，而不是指望 Agent 自己遵守。

### 3. 权限最小化：MCP Server 只暴露必要能力
很多泄露的根本原因是 Agent 拥有过大的上下文读取权限。为每一个接入外部渠道的 MCP Server 单独定义 capability scope：

- 用于社区支持场景的 Agent，只应连接“FAQ 库”和公开文档，禁止连接包含实时日志、工单详情的 Server；
- 若确实需要调取执行记录，MCP Server 应只返回脱敏后的摘要，而不是原始日志对象；
- 对关键的内部 API，使用只读且过滤后的视图提供。

核心原则：**不把面向内部的 default toolkit 直接暴露给外部接口**。

## 踩坑点：自然语言的不可控与绕过手法

最典型的坑是过于信任“自然语言理解”能自动识别泄密。实际上：

- 敏感信息常以非标准方式呈现，比如 `db_host = “10-0-1-5”` 使用连字符而不是点分十进制，正则抓不到；
- Base64 编码的配置段会被 Agent 原样搬出，单纯检查明文无意义；
- 攻击者刻意引导对话，使 Agent 通过正常问答逐步拼凑出完整拓扑——单条回复不违规，组合起来就能绘制攻击地图。

因此必须把安全控点放在**非自然语言层**：正则、关键词匹配、熵检测（如检测高熵字符串）作为基础，再辅以人工抽检日志。不要寄希望于一句 prompt 防所有。

另一个坑是过度脱敏带来的可用性崩塌。如果把所有技术词汇都替换成占位符，Agent 的回答会变得毫无帮助。需要根据渠道分级：内部 IM 允许更多细节，但需要标记；公开社区必须强过滤，哪怕损失部分信息量。

## 可复用建议：从第一天就嵌入安全流水线

如果你的 OpenClaw Agent 会接触任何非私密渠道，请现在就做下面几件事：

1. **在 MCP 中接入一个输出审查工具**，即使只是一组正则规则，作为默认 Pipeline 的一部分。这比事后加护栏效果好得多。
2. **建立输出日志抽样机制**：每周抽取 100 条外部回复，人工 Review 是否包含任何内部信息。这能帮你发现那些规则无法覆盖的泄露模式。
3. **为工作流配置“内外分离”**：将 workflow 定义本身拆分，面向外部的入口 Agent 永远只引用脱敏后的模板，而不是内部真实配置。
4. **教育团队**：写技术分享时，不要直接把 Agent 的对话记录截图外传——你可能自己也在泄露。

市面上有一些成熟的 Guardrails 实现思路可以参考，但重要的是把安全控制集成到你的 Agent 编排流中，而不是事后打补丁。MCP 的可组合性让这件事的成本变得很低——一个独立的 filter Server，就可以让所有连接器共享。

## 总结：安全不是在 Agent “读懂规则”之后，而是在它开口之前

Agent 安全的核心矛盾在于：知识越丰富，回答越有用，泄露风险也越大。限制它的上下文并不可怕，可怕的是你让它拥有全部记忆却只依赖一个自然语言指令来管住嘴。

将安全防线落在代码层级——输出正则替换、权限限定、渠道差异化脱敏，才是工程上可验证、可审计的做法。不要等第一次事故再行动，因为届时泄露的已经不是你个人的密钥，而是你们整个内部工作流的结构。

永远假设 Agent 会说出它看到的任何东西，然后据此来设计它能看到什么。
