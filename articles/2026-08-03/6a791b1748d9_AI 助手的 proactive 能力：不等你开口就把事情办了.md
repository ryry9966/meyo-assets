先说明一个前提：这篇文章里的"proactive"，不是指 AI 突然跳出来跟你聊天，而是指**在明确的规则和上下文条件下，Agent 在用户开口之前执行预定的动作**。我不会聊"AI 是否该主动关怀用户"这种话题，只聊 OpenClaw 里怎么把这类能力工程化。

## 背景：为什么需要 proactive

大多数 Agent 的默认模式是 reactive：用户输入，模型推理，工具执行，返回结果。这个模式的问题在于——**如果用户忘了说，事情就不会发生**。

比如你约定周一上午给团队发周报，Agent 不会记得；某个 API 的 token 周三到期，Agent 不会知道；仓库里有个 issue 48 小时没人处理，Agent 也不会察觉。

解决方案不是让 Agent"变聪明"，而是给它装上一套**触发器的轮子**：让它在特定条件下主动拉取数据、执行判断、产出动作，而不是等人来问。

## 问题拆解

实现 proactive 能力，要解决三个实际问题：

1. **感知条件**：Agent 怎么知道"该做事了"？靠定时任务、MQTT 消息，还是外部 Webhook？
2. **判断时机**：条件触发了，但上下文里可能没有足够的信息决定该不该行动。
3. **收敛动作**：proactive 不等于把所有事情都做掉，而是做"该做的"，且**动作可回溯、可撤销**。

## 做法：用 OpenClaw 实现一个"主动巡检" Agent

下面是一个我在 OpenClaw 里实际验证过的方案。核心思路是：**用系统定时触发一段 prompt，让 Agent 基于当前上下文自行决定是否执行某项操作**。

这个方案分三步：

### 1. 设置一个定时的系统级触发

在 OpenClaw 的配置里加入一个 cron 规则，让 Agent 每 30 分钟被唤醒一次。关键点是：**这个唤醒不是让 Agent 输出内容，而是让它自己决定要不要做事**。参考配置如下：

```yaml
# ~/.openclaw/agents.daily-check/config.yaml
triggers:
  - name: "inbox_scan"
    cron: "*/30 * * * *"
    prompt: |
      你现在是主动巡检助手的触发器。检查当前会话中以下条件是否满足：
      1. 未完成的任务是否超过 2 个
      2. 是否有超过 24 小时无人响应的讨论
      3. 当前时间是否为 09:30 和 17:30
      如果满足任一条件，调用 record_message 记录事件，
      并生成一个 1 句摘要写入 todo 列表。
      如果都不满足，返回空字符串，不要回复任何内容。
```

### 2. 用 MCP 工具把动作收敛到"可执行的最小集合"

proactive 动作不能是"AI 的自由发挥"，一定要收敛到具体的工具调用。上面配置里 `record_message` 是一个 MCP 工具，你可以自己实现。另一个实用工具是写一个 `auto_issue_reminder` 的 MCP 插件：它可以查询未关闭的 issue，但**只发送提醒到指定频道，不做任何标记或修改**。

我在实际操作中，把动作收敛到了这三类：

- `record_message`：记录事件，不修改任何状态
- `todo.add`：往待办列表插入一条，必须带截止时间
- `notify.send`：发送通知，但只发到指定 channel

### 3. 验证触发过程

在日志里加上 `--verbose`，观察每半小时 Agent 被唤醒时的推理内容。如果某次触发后 Agent 没有做任何动作，但日志显示它认为"当前无任务条件满足"，说明你没配错，是场景条件确实不满足。

## 踩坑点

这几个坑我花了些时间才排干净，值得说出来。

**第一个坑：空返回也会引发一轮模型推理调用。** 这不只是浪费 token 的问题——如果 Agent 每次都空跑一轮而没有任何动作，日志会很难看，排查故障时容易忽略真正的报警。我的做法是：在 cron 触发的 prompt 里显式要求"返回空字符串"，并且为这类调用配一个独立的 model instance，用更便宜的模型如 `instruct` 系，而不是每次都用最强的推理模型。

**第二个坑：反复触发同一动作。** 比如某天网络抖动，API 超时，Agent 在 30 分钟内被唤醒两次，把同一个未完成事项记了两次。解决方案：在 `record_message` 工具里加一个 deduplicate 逻辑——按 `(来源会话ID, 任务摘要的前32个字符)` 做 hash，重复的条目直接忽略。

**第三个坑：时区。** 这是 cron 和本地时间最容易翻车的地方。OpenClaw 的定时器默认走 UTC，但 Agent 在 `09:30` 和 `17:30` 做事需要的是本地时区。如果你容器里没做 TZ 映射，你的巡检行为会按 UTC 跑，凌晨触发，结果没人看。一定要在容器或系统层面固定 `TZ=Asia/Shanghai`，同时用 `date` 工具验证 Agent 感知到的当前时间是否符合预期。

## 可复用建议

1. **触发规则放配置，不放 prompt。** 不要在 prompt 里写"如果用户很久没说话就如何"，这种判断会因为上下文窗口滚动而丢失。cron 规则加上外部事件钩子（如 MQTT/Webhook）是稳定的触发源。
2. **proactive 的边界是"提醒和记录"，不是"代做决定"。** 除非是极其确定且幂等的操作，否则优先设计成"告知 + 提出建议"，而不是"直接执行"。这一点决定了用户敢不敢长期开着这个功能。
3. **每次主动动作都留痕。** 在 MCP 工具里带上 `triggered_by: cron/event_name` 字段，便于事后审计。
4. **渐进式信任。** 前两周只跑"记录 + 提醒"，第三周才让 Agent 自动关掉 long-lived issue，第四周再考虑让它直接改代码并提交。

## 总结

proactive 能力的工程本质，**不是让 AI 更聪明，而是给它装一套"规则调度器"**。用 OpenClaw 的 cron 触发 + 收敛的 MCP 工具集，能让 Agent 在用户开口之前完成记录、提醒、汇总这类低风险动作。关键不在于能做什么，而在于**不该做什么、以及做了之后怎么留痕**。

如果你的场景里也有"定期检查 + 汇总 + 提醒"类的需求，这套方案可以直接复用。把边界定清楚，剩下的就是观察日志，慢慢调。
