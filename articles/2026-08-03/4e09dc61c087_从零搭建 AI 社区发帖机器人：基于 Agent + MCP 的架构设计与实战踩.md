## 背景

社区运营中，常规的周期性内容——如周报整理、常见问题回复、知识库摘要更新——占据了大量人力。我们希望引入一个 AI 驱动的助手，能理解社区语境，自主调用接口完成“读取→理解→发布”的闭环，而不是简单的定时 POST 一段固定模板。

考虑到团队已经在使用 OpenClaw 的 Agent 编排能力，并且有意将社区基础能力沉淀为可复用的 MCP 工具，这个场景非常适合用“Agent + MCP”来实现。最终目标是：机器人能模拟一个初级运营人员的行为，阅读未回复的帖子、判断是否需要介入、生成接近人工质量的回复并发布。

## 问题抽象

传统自动化脚本的核心痛点是 **语义理解的缺位**：它只能匹配关键词或正则，无法判断帖子的真实意图。而引入 LLM 之后，新的工程问题又出现了：

- 如何安全地把社区数据交给 LLM 处理？
- 如何防止模型生成违规或重复内容？
- 工具调用失败、超时、并发冲突怎么处理？
- 机器人行为如何可观测、可回撤？

这不是一个简单的“调用 ChatGPT API”的任务，而是一个需要完整架构设计的 Agent 工程。

## 架构设计

我们采用了“1 个 Agent + 2 层工具 + 1 条流水线”的模式：

- **社区工具层（MCP Server）**：封装论坛 REST API，提供 `list_unanswered_threads`、`get_thread_detail`、`create_reply`、`update_post` 等工具。使用 HTTP with token 鉴权，内部做限流重试和结果裁剪。
- **知识工具层（可选）**：对接内部知识库或 RAG 服务，提供 `search_knowledge_base` 工具，供 Agent 检索历史解决方案。
- **Agent 核心**：基于 OpenClaw 的 Agent 框架，配置系统提示词、few-shot 示例、工具调用策略。Agent 被设计成单步决策：一次 run 只处理一个帖子，避免 token 膨胀。
- **调度流水线（Pipeline）**：用 crontab 或 scheduler 触发，每 15 分钟执行一次，取回未回复列表，逐条交 Agent 决策，决策通过后执行 `create_reply`，并记录日志。

## 实施步骤要点

1. **MCP Server 实现**  
   我们选择 TypeScript 编写 MCP Server，部署在社区所在的云环境内部，减少网络延迟。关键细节：
   - `list_unanswered_threads` 返回最近 2 小时内的未回复帖，并限制一次最多 10 条，避免 Agent 处理过载。
   - 每个工具返回前做摘要裁剪：正文截断至 1500 字符，去除 HTML 标签，但保留代码块边界，防止破坏技术内容。
   - 内置重试逻辑：遇到 429 限流，指数退避最多 3 次；遇到 5xx，立即标记为失败并记录日志。

2. **Agent 提示词与 few-shot 设计**  
   系统提示词明确限制 Agent 的行为：
   - 仅回答技术问题，遇到非技术帖直接跳过（输出 `SKIP` 状态）。
   - 若已有类似回复则不再重复（先读取现有回复）。
   - 回复需包含具体步骤或文档引用，禁止“欢迎来到社区”等泛化内容。
   我们提供了 3 个真实的少样本示例，将社区历史高质量回复嵌入提示词，显著提高了回答的专业度。

3. **Pipeline 的编排与安全措施**  
   - 每条帖子的处理是一个独立的 Agent run，上下文不跨帖子共享，防止 token 累加。
   - 在执行 `create_reply` 前，Pipeline 对生成内容做一次规则校验：检查是否包含禁用词、是否超过 2000 字符、是否与近期其他回复高度重复（用 Jaccard 相似度）。
   - 校验通过才实际发布，并写入可回撤日志。如果校验失败，将回复草稿发送到审核频道，人工介入。

4. **监测与回滚**  
   我们为每次操作生成了 `operation_id`，关联帖子和生成的回复。日志系统中可查询任意一次回复的历史，支持一键删除并通知管理员。

## 踩坑实录

### 坑 1：MCP Server 的长连接超时
Agent 调用工具时，默认的超时设置是 60 秒，但社区论坛在高峰期响应有时超过 10 秒。更隐蔽的是，MCP 传输层（stdio/SSE）在某些网络环境下心跳被中间设备丢弃，导致连接静默中断。  
**解决**：将 MCP Server 切换为 HTTP+SSE 模式，并增加应用层心跳（每 30 秒一次）。Agent 侧工具调用超时放宽到 15 秒，并加上失败自动重试一次。

### 坑 2：LLM 生成的回复被反垃圾系统拦截
早期机器人发布的一段回复因包含“加群获取资料”字样，被社区自动标记为垃圾并封禁账号。  
**解决**：在内容校验环节加入常见广告/违规模式的正则，同时在系统提示词中禁止任何引导至外部联系方式的行为。我们还将账号“洗白”——降低发布频率、先手动发布一些正常回复积累信誉。

### 坑 3：工具调用结果中的编码错乱
社区接口返回的某些老帖子中含有 GBK 编码残留，MCP Server 在 `get_thread_detail` 中直接返回原始 utf-8 字符串，导致 Agent 看到乱码后给出了错误回答。  
**解决**：在 MCP Server 侧加入编码检测与转码逻辑，确保输出给 LLM 的文本始终是干净 utf-8。

### 坑 4：并发冲突
同一时间段运行了两个 Pipeline 实例（因为 cron 触发重叠），导致对同一帖子生成并发布了几乎相同的回复。  
**解决**：通过分布式锁（Redis）确保同一时间只有一个实例在处理，同时给每个帖子处理前检查“是否有过去 1 分钟内的回复”，防止重复。

## 可复用建议

1. **社区能力 MCP 化**  
   将论坛操作抽象为 MCP Server，不只是一个项目使用，也可以复用到运维问答、工单处理等场景。接口设计时提前考虑批量操作、分页、错误码标准化。

2. **Agent 策略模块化**  
   不要把所有策略塞进一个超长提示词。可以将“判断是否需要回复”“检索知识”“生成草稿”“校验发布”拆为 Pipeline 的不同 stage，每个阶段可以独立调试和替换。

3. **可观测性前置**  
   从一开始就记录每次工具调用的输入、输出、耗时和最终发布内容，建立回撤能力。日志最好结构化（JSON），方便对接现有监控系统。

4. **人机协同是刚需**  
   全自动机器人容易失控，初期必须保留人工审核通道。建议设计一个“信心度”评分，当 Agent 对回复质量不确定时自动转入人工审核，降低风险。

## 总结

用 Agent + MCP 搭建社区发帖机器人，不是简单地把 ChatGPT 接上一个发送按钮，而是一次对社区交互链路的工程化重构。核心收益在于：社区操作能力被解耦为可复用的工具集，而 Agent 则成为灵活的编排者。过程中踩过的坑大多集中在“可靠性”和“内容安全”上，解决方法也多是将工程实践（重试、锁、校验、日志）引入到 AI 流程里。

如果你的团队也在尝试类似的自动化运营，希望上述经验能让你少走些弯路。最终的架构，其实远比“发帖机器人”这个称呼更加通用：它就是一个具备领域工具操控能力的自主 Agent，随时可以被移植到其他需要“理解语境并执行操作”的任务中。
