## 背景

在 OpenClaw 这类支持长记忆的智能体中，`memory_recall` 是一个高频入口：当助手需要引用过往对话、用户偏好或历史上下文时，它决定了哪些片段能被“想起来”。随着社区里 MCP memory server 和各类 memory 插件的普及，大家开始面临同一个工程问题：**到底是上向量库做语义搜索，还是老老实实用全文索引？**

我们团队在去年把内部助手从“无记忆”升级到“带记忆”时，恰好在这个分岔口反复踩坑。下面把两种方案的对比实验、踩坑记录和落地方案写出来，供 OpenClaw 的深度用户参考。

## 问题抽象

典型场景：用户前几次对话说过“我主要用 Svelte 写前端，讨厌复杂的配置”，间隔若干轮后问“帮我搭个项目骨架”。助手如果能 recall 到“Svelte，讨厌复杂配置”，就能直接给出 `npm create vite@latest` 这种回答，而不是泛泛推荐 React/Vue 全家桶。

检索系统需要从几百到几千条历史记忆中，根据当前查询召回最相关的 top-k 片段。我们有两条路：

- **全文搜索**：基于关键词倒排索引，严格匹配词项。  
- **语义搜索**：将记忆和查询向量化，按余弦相似度召回。

此外，工程上还会考虑延迟、存储、分词语言支持、更新频率等。

## 实验做法

为了量化对比，我们搭建了一个小规模测试床：

1. **数据准备**  
   - 从内部测试群中抓取约 800 条真实对话片段，经脱敏后作为记忆库。  
   - 每条记忆含 `role`, `content`, `metadata`（时间戳、标签等）。  
   - 人工标注了 50 个测试查询及其理想的 top-3 记忆，作为评估集。

2. **全文检索方案**  
   - 存储：SQLite FTS5 表，对 `content` 字段建索引。  
   - 中文分词：`jieba` 分词后写入索引（FTS5 需要外部分词）。  
   - 查询：接收用户输入，同 tokenize 后 `MATCH` 查询，取 BM25 得分 top-5。

3. **语义检索方案**  
   - 嵌入模型：OpenAI `text-embedding-3-small`，维度 1536。  
   - 向量存储：ChromaDB 本地模式，HNSW 索引。  
   - 查询时：将当前用户消息向量化，召回余弦相似度 top-5。

4. **评估指标**  
   - Recall@5：在前五结果中命中至少一条“理想记忆”的比例。  
   - MRR（Mean Reciprocal Rank）：理想记忆出现位置倒数平均。  
   - 人工可用性打分：将召回的记忆喂给 LLM 后，看回答是否更精准（1-3 分）。

快速 3 轮测试后得到初步结果（非学术严谨，但趋势明确）：

| 指标 | 全文搜索 | 语义搜索 |
|------|----------|----------|
| Recall@5 | 64% | 82% |
| MRR | 0.44 | 0.67 |
| 可用性评分均分 | 2.1 | 2.6 |

语义搜索明显更“抗措辞变化”——比如查询“前端样式方案”能命中含“Tailwind CSS”的记忆；而全文搜索要求准确命中词项，漏掉很多同义表达。

不过语义搜索也暴露出**过度泛化**的毛病：曾把“我讨厌开会”的向量和“最喜欢的会议形式”混淆，因为句子结构相近。这在工程师眼里是个典型的噪声引入点。

## 踩坑实录

### 1) 中文分词对全文搜索是硬门槛
FTS5 默认按空格分词，中文直接全段索引，查询只能匹配连续子串，效果极差。引入 jieba 后效果提升明显，但分词词典维护、新词发现又成了配套任务。对于多语言更麻烦，后来我们切到 `tantivy` + `lindera` 分词才算跑通。

### 2) 语义搜索暗藏“语义但无关”陷阱
用户说“我昨天重构了一下 state 管理”，查询“状态库”时会高分命中。但如果意图是“推荐一个 Vue 状态库”，这段记忆其实无帮助。单纯提高 top-k 会带进噪音，反而挤占 LLM 有限的上下文窗口。

### 3) 更新频率与资源
向量索引重建成本高。记忆每天都在增长，若要求实时 recall，就必须支持流式写入和增量索引。ChromaDB 的持久化在小数据量下没问题，但超过 5 万条之后内存和磁盘 I/O 快速增长，需要转向 Milvus 或使用轻量级 scaNN 近似索引。

### 4) 混合搜索的融合难度
直觉会想到“先全文过滤，再语义重排”，可工程上多了一跳查询，增加 30-50ms 延迟。实现 Reciprocal Rank Fusion (RRF) 时还要调试权重，不然两边分数尺度不一致反而劣化。

## 可复用的落地建议

1. **数据量 < 2000 条且查询模式固定**  
   直接用 SQLite FTS5 + jieba，足够清晰，无外部依赖。

2. **需要理解改写、多语言、同义表达**  
   上语义搜索，但**务必加上相似度阈值**（如 0.7），过滤掉弱相关结果，减少噪声。

3. **生产环境首选混合管道**  
   我们最终方案：  
   `Query → 全文检索（取 top-20 候选） → 语义重排序（交叉编码器 cross-encoder） → 阈值过滤 → top-3 记忆`  
   这样兼顾召回和精度，交叉编码器模型用 `BAAI/bge-reranker-base` 本地部署，延迟控制在 120ms 以内。

4. **在 OpenClaw 中的集成姿势**  
   - 把记忆服务抽象成 MCP 资源或 tool，暴露 `search_memory(query, top_k, method)` 接口。  
   - 通过在 `server.json` 中切换后端实现（`chroma`, `sqlite`, `hybrid`）。  
   - 设置记忆的 `scope`（user/session/global）避免跨租户污染。

5. **监控与评估闭环**  
   记录实际调用中“召回记忆被 LLM 用到”的频率，持续验证可用性评分。每周抽查 20 条 recall 结果，像做 CI 一样跑评估集，防止索引腐化。

## 总结

AI 助手的记忆召回没有银弹。文本量小时全文搜索简单可靠；需要语义鲁棒性时使用向量检索，但必须谨慎处理噪声；最终宜落脚在混合架构，并根据业务场景调整召回-重排流水线。在 OpenClaw 生态里，一个好的 memory 插件应让两种方式可配置、可观测，而不是强迫用户二选一。

**把宝贵的上下文窗口塞满高价值记忆，比用哪种技术更重要。**
