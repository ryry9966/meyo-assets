# LLM 输出解析的防御性编程：JSON 与标签格式的混合处理

## 背景

在基于 OpenClaw 或自建 Agent 的自动化流程中，大模型输出的结构化内容几乎每天都在“变脸”。同一个模型，可能会在三次调用里返回三种格式：

- 纯 JSON：`{"tool": "search", "query": "OpenClaw release"}`
- 代码块包裹的 JSON：` ```json\n{ ... }\n``` `
- XML 风格标签包裹的 JSON：`<tool_call>{"tool": "search", "query": "..."}</tool_call>`
- 混合自然语言的 JSON：“好的，我将执行以下操作：{ ... }”

若解析逻辑只覆盖其中一种，线上就会频繁出现 `JSONDecodeError`，令整个 Agent 管道宕掉。防御性编程的目标不是“让模型更听话”，而是**在输出不可靠的前提下，让解析器的容错半径足够大**。

## 问题本质

解析失败往往不是模型“坏掉了”，而是 prompt 与模型输出分布之间存在不可控偏差。即使你用 function calling 约束，也会有部分模型（尤其是在 tool-use 微调较少的小模型上）自行发挥。一个典型的混合输出可能长这样：

```
I’ll now call the search tool.
<tool_call>
{
  "name": "search_web",
  "arguments": {
    "query": "best MCP server for filesystem",
    "max_results": 5,
  }
}
</tool_call>
Let me analyze the results.
```

这里有四个陷阱：
1. 外层自然语言干扰；
2. XML 标签内外都有噪声；
3. JSON 内部有尾随逗号；
4. 字段命名可能不一致（`name` vs `tool_name`）。

简单的 `json.loads(content)` 注定一碰就碎。

## 做法：构建分层回退解析链

工程上的解法是实现一条“解析器链”，按成功率从高到低依次尝试，直到拿到可用的结构化对象。一个经过实战验证的链式顺序如下：

### 第一步：正则提取标签块
先用正则定位可能的标签对，比如 `<tool_call>...</tool_call>`、`<action>...</action>`、甚至简单的 `{{ ... }}`（部分模型偏爱）。如果命中标签，对内部文本进行归一化后送入 JSON 解析；如果解析失败，不是直接放弃，而是降级到下一步。

```python
import re

def extract_tagged_json(text: str, tag: str = "tool_call"):
    pattern = rf"<{tag}>(.*?)</{tag}>"
    matches = re.findall(pattern, text, re.DOTALL)
    candidates = []
    for m in matches:
        try:
            candidates.append(json.loads(m.strip()))
        except Exception:
            # 如果标签内不是合法 JSON，可能被自然语言污染，交给下游
            candidates.append(m.strip())
    return candidates
```

### 第二步：剥离 Markdown 代码块
许多模型习惯用 ````json` 代码块。通过正则删除```及其语言标记，保留内容部分。然后尝试用宽松的 JSON 解析器（如 `json5`）加载。`json5` 能容忍单引号、注释、尾随逗号——这些恰是模型的常见“语法错误”。

```python
import json5

def extract_code_block_json(text: str):
    # 卸载 ```json ... ``` 或 ```...
    pattern = r"```(?:json)?\s*\n?(.*?)\n?```"
    matches = re.findall(pattern, text, re.DOTALL)
    for m in matches:
        try:
            return json5.loads(m.strip())
        except Exception:
            continue
    return None
```

### 第三步：整段文本直接解析
当没有标签或代码块时，尝试将整个响应作为 JSON（或 json5）解析。这在模型输出恰好是纯 JSON 时最快。

### 第四步：首次出现 JSON 的贪婪提取
如果前面全部失败，使用正则定位第一个完整的 JSON 对象或数组。具体做法是查找第一个 `{` 并向前寻找与之匹配的 `}`，注意处理括号嵌套和字符串内的花括号。一个简化但有效的实现：用 `json5` 的 `json5.loads` 在每一个 `{` 位置尝试解析子串，直到成功或超限。这种做法的计算成本略高，但可以救回大量“自然语言 + JSON”的情况。

### 第五步：字段容错与补全
解析成功后，还要防御字段名不匹配。例如模型返回的是 `{"tool_name":"search"}` 而程序期望 `name`。在解析器输出处增加一层映射表或者 `try-except` 字段回退逻辑。比如：

```python
tool = parsed.get("name") or parsed.get("tool_name") or parsed.get("function")
```

对于缺失的必填参数，可以填入默认值或抛出结构化异常，让上游进行重试或降级处理。

## 踩坑点

- **json5 并不是万能药**：它允许尾随逗号，但模型如果输出类似 `{"a": ,}` 这种空值，json5 也会炸。此时需要在上游增加预清洗正则（移除形如 `,\s*[,}]\( 的片段）。
- **多工具调用混在同一个块**：有时 `<tool_calls>` 内包含一个 JSON 数组，有时同一标签重复出现多次。解析器需要根据约定的 schema 决定是返回列表还是只取第一个。最好在配置中声明 `multi: true/false` 来统一行为。
- **标签不闭合**：模型因 token 截断等原因可能输出不完整的 `<tool_call>{"a":1`。这时正则的 `re.DOTALL` 匹配会失败或捕获垃圾。可以在最后一步加入片段修复试探，例如尝试补全闭合符再解析，但风险较高。更稳健的做法是直接标记为失败，触发重试机制。
- **语言标签混淆**：少数模型使用 `'''xml` 或 `'''tool` 作为代码块标记，正则要稍微放宽。

## 可复用建议

如果你正在构建 OpenClaw 插件或基于 MCP 的 Agent 中线，建议将上述逻辑封装成一个独立模块：

```python
class RobustParser:
    def __init__(self, fallback_tags=["tool_call", "action"], default_fields={}):
        ...
    def parse(self, raw_text: str) -> dict | list[dict]:
        ...
```

对外暴露单一方法 `parse`，内部顺序执行提取策略，记录每一步成功/失败到日志，方便回溯模型输出质量。

另外，每次解析失败时，**把原始文本和失败原因写入结构化日志**，积累数百条后可以很直观地发现模型的一些“方言”，进而提前在 prompt 或微调中修正，形成良性闭环。

## 总结

在 Agent 工程里，信任模型输出格式是最大的幻觉。防御性解析不是“过度设计”，而是保证系统在不可控生成侧依然能体面运行的唯一手段。用分层回退、宽松解析器、字段映射和失败日志，能让一个单点脆弱的字符串处理模块变得足够强韧。实践下来，这套链式处理可以将解析成功率从 85% 左右拉升到 99% 以上，而代码量不过百行——这绝对是投入产出比最高的稳健性投资之一。
