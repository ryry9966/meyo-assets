## 背景

如果你的 AI 助手接入了记忆模块，大概率绕不开 `memory_recall` 这个东西。社区里已经有不少项目在实现类似功能：用向量库存 embedding，用关键词建倒排索引，或者两个都上，然后跑一次 RAG 式召回。

但选型矛盾一直存在：**语义搜索**（向量相似度）和**全文搜索**（关键词匹配）到底哪个更靠谱？网上大多数对比结论是“语义完胜”，但我们在自己的一轮实测中，发现事情没那么简单，而且很多人会在这上面踩坑。

## 问题

我们的使用场景是：OpenClaw 长期记忆，每次对话前从历史记忆库中召回相关片段，拼进 system prompt 或作为上下文注入。记忆内容包含两种类型：一是用户闲聊时的偏好记录（“不喜欢吃香菜”），二是操作日志（命令、报错、配置片段）。

先说结论性差异：

- **语义搜索** 擅长处理**语义相似、字面无关**的问题——“用户讨厌的食物”能命中“用户对香菜的态度”。
- **全文搜索** 擅长处理**字面精确、专有名词**的问题——“docker compose up 报错”如果被语义模型转成向量，很容易和别的容器编排错误搅在一起，但关键词硬匹配一找一个准。

我们跑了一轮 200 条实测记忆、50 个查询的评测流程，结果如下（基于我们自己的数据集）：

| 查询类型 | 语义搜索 | 全文搜索 |
|---------|---------|---------|
| 口语化偏好记忆 | 命中率 82% | 命中率 54% |
| 代码/报错/专有名词 | 命中率 51% | 命中率 88% |
| 混合型历史操作记录 | 命中率 63% | 命中率 71% |

## 做法与步骤

我们用了最朴素的落地方式：语义用 `sentence-transformers` 做切段和 embedding，存进 `chromadb`；全文用 SQLite 的 FTS5 或 `meilisearch` 拉倒排索引。

评测流程如下：

1. **清洗数据**：把历史记忆按 200-400 token 切段，去掉时间戳和系统噪声。
2. **构造查询集**：50 条查询命中了三种类型（偏好、技术故障、混合日志）。
3. **跑双通道召回**：两个通道各取 top-5，合并后由大模型做重排（一个简单的 rerank prompt 或一个分数加权）。
4. **人工标注命中率**：判断召回结果是否对解决当前问题有实际帮助。

这是我们的关键代码片段（核心逻辑）:

```python
def recall_hybrid(query: str, k: int = 5):
    sem_results = semantic_search(query, k=k)  # chromadb query
    full_results = fulltext_search(query, k=k) # FTS5 match
    merged = merge_by_weight(sem_results, full_results, alpha=query_has_technical_term(query) ? 0.3 : 0.7)
    return rerank_with_llm(merged)
```

`query_has_technical_term` 判断是否有代码、命令、报错模式。返回最终结果后注入 prompt。

## 踩坑点

**1. 不要用语义搜索查代码**

一个 `docker run -p 8080:80` 的错误日志，语义搜索会召回“容器端口冲突”的相关片段，但如果你要的是“那条具体的命令长什么样”，必须靠全文通道。

**2. 切段长度影响巨大**

向量搜索对 400 token 以上的片段几乎失效——embedding 被平均掉所有细节。500 字以上一定切短。全文搜索则相反，太短的关键词会出现大量噪声匹配。

**3. 多用户隔离是隐藏坑**

如果 memory_recall 没有按 user_id 过滤就直接检索，语义搜索会把另一个人的偏好混进来，而且因为“语义相关”，你很难看出问题。全文搜索倒还好，关键词硬匹配不太会串（但也会）。

**4. simple rerank 比你想的有效**

我们起初直接用分数相加，后来改成让模型判断“哪条记忆对当前问题有帮助”，准确率提高了 14 个百分点，而且 prompt 只需要 5 行。

## 可复用建议

- **语义 + 全文双路召回，永远不要只上一个**。语义负责覆盖“换一种说法”，全文负责覆盖“精确匹配”，两者是互补关系，不存在谁替代谁。
- **按记忆类型分流**：偏好、人物关系、长期目标走语义通道；命令、报错、依赖配置走全文通道。
- **每个会话注入 3-5 条记忆即可**。社区里见过 10 条以上的配置，实际跑下来效果反而下降——上下文被稀释，模型不知道该用哪条。
- **每周跑一次离线评测**。用 20 条真实历史查询过一遍，人工看命中率，花不了 15 分钟。
- **先过滤后召回**：按 user_id、时间范围过滤后再做向量检索。

## 总结

在 memory_recall 这个场景里，语义搜索和全文搜索不是替代关系，而是分工关系。**偏好记忆交给语义，技术记忆交给全文，有条件再上 LLM rerank**。如果你的助手记忆库中操作日志占比高，全文搜索的价值会被严重低估；如果你的助手主要记录用户偏好，语义搜索更重要。

真正的答案取决于你的记忆内容结构——先花一天做评测集，再调权重，别一上来就押注某一套方案。
