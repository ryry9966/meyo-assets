## 背景

在 OpenClaw 系列的 Agent 自动化编排中，定时执行是最基础的模式之一。无论是定期拉取数据、周期性触发 MCP 工具，还是驱动插件任务轮转，都会用到定时器。

OpenClaw 内置了两种调度原语：**cron** 和 **heartbeat**。它们在配置文件中通过 `triggers` 字段定义，从表面看都能实现“每隔一段时间做某事”，但底层行为差异很大。如果选择不当，轻则导致任务错位，重则引发惊群效应或时钟漂移。

写这篇的起因，是我在维护一个每30秒同步一次 Notion 日历的 Agent 时，先用了 cron，却在高峰期观测到大量“吞事件”现象；切到 heartbeat 后稳定了，但发现心跳断连后再启动会有补充触发的问题。排查过程中翻了一遍调度器源码，把两种模式的行为边界搞清楚了。以下是我的工程化总结。

## 问题拆解：cron 与 heartbeat 的核心差异

| 维度 | cron | heartbeat |
|------|------|-----------|
| 触发基准 | 基于系统时钟的绝对时间（例如“每小时的第5分钟”） | 基于从上一次执行结束后的**相对间隔**（例如“上次执行完30秒后再次触发”） |
| 精度 | 分钟级，不支持秒级（最小单位是分钟） | 毫秒级，支持短间隔（min 1s） |
| 补调策略 | 如果节点在触发时间点宕机，错过即错过（无补偿） | 恢复后若检测到心跳过期，会立即触发一次“补偿执行”（可配置关闭） |
| 重叠保护 | 无：如果上次任务未结束而新触发到来，可能会并发执行 | 默认等待上次完成才启动下一次（可配置并发） |
| 状态依赖 | 无状态，仅看时间 | 有状态，依赖上次执行结束时间 |

在多节点或容器重启环境中，cron 的“无补偿”特性可能导致任务被悄悄跳过；heartbeat 的“补偿执行”则可能让一个长时间阻塞的任务在恢复后瞬间完成多次重放，冲击下游系统。

## 做法/步骤

### 1. 使用 cron 触发任务

在 `agent.yaml` 中如下定义：

```yaml
triggers:
  - type: cron
    spec: "*/5 * * * *"      # 每5分钟触发一次
    task: sync_jira
```

OpenClaw 的 cron 实现基于 `robfig/cron` 库，标准 5 字段，不支持秒。要注意：如果你写 `* * * * *`，它每分钟整点触发，而不是每秒。曾经有人写了 `*/30 * * * * *`（6字段），解析直接报错。

**适用场景**：需要与地球时间对齐的任务，比如每小时结算、每天0点数据快照。

### 2. 使用 heartbeat 触发任务

```yaml
triggers:
  - type: heartbeat
    interval: 30s          # 支持 ms / s / m / h
    task: poll_notion
    compensate: false      # 关闭补偿执行
    concurrent: false      # 串行模式（默认）
```

heartbeat 的实现内部维护了一个 `lastRunEnd` 时间戳。调度循环每 500ms 检查一次：如果 `now - lastRunEnd >= interval`，且满足并发控制条件，就触发任务。因此它有最低一次的执行间隔，但能精确到秒级。

**适用场景**：持续轮询、长连接保活、需要严格控制请求间隔的 API 调用。

### 3. 混合编排

如果你的 Agent 同时包含对齐钟表的批处理任务和依赖间隔的流式任务，可以把它们放在同一个 `triggers` 数组中。调度器会为每个触发器分配独立的 goroutine，互不阻塞。

## 踩坑点

1. **cron 表达式时区问题**  
   调度器默认使用系统本地时区。如果你在 Docker 中运行，容器时区可能是 UTC，而你的 cron 心里想的是 Asia/Shanghai。可以在 spec 前加 `TZ=Asia/Shanghai ` 前缀（OpenClaw 支持 robfig/cron 的时区扩展），但容易遗漏。建议部署时统一用 `-v /etc/localtime:/etc/localtime:ro` 并明确指定 TZ。

2. **heartbeat 的“补偿陷阱”**  
   默认 `compensate: true`。如果 heartbeat 任务 pause 了 10 分钟，恢复后调度器发现距离上次结束已远超 interval，便会立即触发任务。如果下游系统在这 10 分钟内已经积压了数据，补偿执行可能造成“雪崩”。**生产环境若不需要补偿，务必显式设置 `compensate: false`。**

3. **心跳的时钟源**  
   heartbeat 依赖 goroutine 内部的 time.Sleep，不受系统时间回调影响（墙钟调整不影响单调时钟），但如果节点 CPU 密集导致调度延迟，实际间隔会偏大。我在 4 核 low 负载下观测 1s heartbeat 的实际间隔分布为 1.0s ± 15ms，尚可接受；但如果任务本身耗时接近 interval，建议开启 `concurrent: true` 并在任务内做幂等控制。

4. **并发叠加导致惊群**  
   多 pod 场景下，如果多个实例同时跑同一定时任务（比如没有做 leader election），cron 会在同一时刻海量触发，heartbeat 也会在启动瞬间几乎同时触发。OpenClaw 自身不解决分布式互斥，需接入 Redis 锁或利用数据库的 `SELECT ... FOR UPDATE` 保证单实例执行。

## 可复用建议

- **面向时间的批处理选 cron**：当“什么时间点执行”比“距上次多长时间”更重要时，cron 是天然选择。注意只支持分钟级，且错过不补。
- **面向间隔的持续轮询选 heartbeat**：例如限速调用外部 API、拖动进度检测、心跳上报等，务必确认 `compensate` 策略与幂等设计。
- **生产环境默认关闭 compensate**：除非你的业务能容忍重复执行，否则将其设为 false。如果需要补偿，用业务标识做幂等（如基于上一次游标处理）。
- **设置最低 interval**：heartbeat 下 100ms 的 interval 在高负载时几乎不可能准确，建议不小于 1s，否则将暴露 goroutine 调度抖动。
- **监控缺失触发**：为关键任务增加指标—— cron 记录每次触发的 wall clock 时间，heartbeat 记录实际间隔，当偏差超过 2 × interval 时报警。

## 总结

OpenClaw 的 cron 与 heartbeat 本质上是**绝对时间调度**与**相对间隔调度**两种原语，分别对应“何时做”和“多久做一次”。不分优劣，全看场景。真正踩坑的地方往往不在调度器本身，而在时区、补偿、并发和分布式互斥这些工程细节上。在实际项目中，我倾向于用一个 cron 来起床，用一个谨慎配置的 heartbeat 来跑腿。

希望这份对比能帮你少走几圈排查循环。
