## 背景：Agent 的能力越强，权限焦虑越重

随着 MCP（Model Context Protocol）工具生态和 OpenClaw 这类可编程 Agent 框架的成熟，单个 Agent 能做的事已经远超“问答”。它可以读取文件、发邮件、操作数据库、调用云资源、触发 CI/CD 流水线，甚至修改配置并重启服务。

能力扩大的同时，一个新的工程问题浮出水面：**“什么时候 Agent 该自己干，什么时候必须停下来问人类？”** 这不是一个抽象的安全哲学问题，而是直接影响系统稳定性、用户体验和合规风险的具体实现问题。

如果所有操作都自动执行，一个 prompt 里的歧义就可能酿成大祸；如果事事都弹窗确认，那自动化等同于虚设，用户很快会对 Agent“免疫”，习惯性点“确认”。

在 OpenClaw 的开发实践中，我踩过一条清晰的路：**给 Agent 的每个动作加一层可配置的权限边界，让“问人类”这件事变成一条可工程化的决策规则，而不是一句模糊的口号。**

## 问题定义：自动化决策里缺失的那一环

一个典型的 OpenClaw 任务可能是：

> 用户：“帮我把昨天生产的报表数据归档到冷存储，然后清空临时目录。”

Agent 需要执行的动作可能包括：
- 读取某目录下的文件列表（低风险）
- 移动文件到归档桶（中风险）
- 删除临时目录下的文件（高风险）
- 调用对象存储生命周期策略（高风险）

现在的问题是：**你不能把这些动作的权限决定权完全扔给 LLM。** LLM 可能产生幻觉，可能误判风险，可能在多步任务中连续犯错。你需要一套独立于模型推理之外的机制来兜底。

## 工程方案：三级权限决策模型

我落地的是一个 **“动作评分 + 上下文阈值”** 的决策模型，把它做成了 OpenClaw 的一个中间件，对所有通过 MCP 客户端发出的工具调用做拦截和裁决。

### 1. 动作风险分级
首先为每个 MCP 工具（或工具组）定义基础风险等级：

- **L0 – 纯读取，无副作用**：例如 `list_files`、`read_object`、`query_db_readonly`
- **L1 – 受限写入，影响范围明确**：例如 `write_file(path, content)` 写入单一文件、`send_slack_message`
- **L2 – 批量修改或资源变更**：例如 `delete_files_by_pattern`、`restart_container`
- **L3 – 权限提升或不可逆操作**：例如 `drop_table`、`update_dns_record`、`run_shell_script`

每个工具在注册时就带有一个 `risk_level` 字段，这不是由 LLM 判断的，而是由开发者在一开始就明确标注的。

### 2. 上下文安全因子
仅有风险等级不够，静态风险不能反映真实场景。同一个“删除文件”操作，在临时目录上执行的风险远低于在生产数据目录执行。因此引入**上下文安全因子**，它是一个 0~1 的浮点数，由几个可配置的评估器加权计算：

- **目标资源标签匹配**：文件路径是否匹配只读/安全目录白名单（`/tmp`, `/workspace/scratch` 等）
- **操作参数规模估算**：是否涉及超过 N 个对象（批量删除阈值）
- **租户/环境属性**：当前会话绑定的是 dev 环境还是 prod 环境
- **历史审计信号**：该用户/Agent 是否在过去 N 分钟内频繁触发高风险操作

安全因子的计算公式可以是简单的加权求和或最劣条件下限策略。我倾向于“最差路径优先”，即只要任一评估器标定该操作为高风险上下文，安全因子就取较低值。

### 3. 决策矩阵
将风险等级和上下文安全因子交叉，得到最终的行为决策：

| 风险等级 \ 安全因子 | 高（>0.8） | 中（0.4–0.8） | 低（<0.4） |
|-------------------|------------|--------------|-----------|
| L0                | 自动执行   | 自动执行     | 自动执行  |
| L1                | 自动执行   | 日志记录+降级通知 | 请求确认+回滚预览 |
| L2                | 日志记录+降级通知 | 请求确认+回滚预览 | 阻止，要求人类接管 |
| L3                | 请求确认+回滚预览 | 阻止，要求人类接管 | 阻止，要求人工审核 |

其中：
- **自动执行**：直接执行，仅记录审计日志。
- **日志记录+降级通知**：执行，但向用户/频道推送一条非阻塞通知，例如“🟡 Agent 正在移动 15 个文件至 /archive”。
- **请求确认+回滚预览**：暂挂执行，生成一个可理解的操作摘要和反向操作说明（如“将删除以下 3 个表，可回滚方式为恢复最近快照 snapshot-xxx”），等待用户明确回复“确认”或“取消”。
- **阻止**：直接拒绝执行，输出原因和建议的人工处理路径。

这套决策矩阵完全不依赖 LLM 判断，全部是确定性规则。你可以把它放在 OpenClaw 的 Tool Use 流程之前，作为一个 middleware 拦截所有 tool call。

## 踩坑记录：理想模型到工程落地之间的距离

**坑1：确认疲劳导致的“无脑确认”**
最初我们的 L1 操作在一定条件下也会弹确认，结果用户几乎看都不看就点确认，失去了保护意义。改进方式：将 L1 下的非危险上下文改为“降级通知”，保持自动化流畅性，只在真正的边界上打断用户流程。用户对通知的注意力反而比弹窗更高。

**坑2：LLM 绕过权限中间件**
如果 OpenClaw 允许 Agent 生成并执行任意的 shell 命令而不经过工具封装，权限模型就形同虚设。我们的解法是：禁用通用 `run_command` 工具，所有破坏性操作必须走经过封装的 MCP 工具，这样每个动作都有明确的风险标签。这是很多人容易忽略的关键点——**权限边界必须和工具粒度绑定，不能存在任意代码执行的自由通道。**

**坑3：回滚预览的可信度问题**
“可回滚”这个承诺本身是有风险的。比如删除 S3 对象后，如果桶没有开启版本控制，根本回滚不了。所以回滚预览信息必须由工具端提供真实的元数据支持，而不是靠 LLM 编造。我们让每个 L2/L3 工具在返回结果时附加一个 `rollback_info` 字段，若无法提供可信回滚手段，则权限模型直接将其升级为“阻止”操作。

## 可复用的工程建议

1. **工具注册时就定义风险，而非执行时猜测**：在 MCP server 的 `tool/list` 或注册代码里添加 `risk_level` 元信息，让权限决策可以离线审计和测试。
2. **将决策逻辑抽离为独立中间件，不耦合 Agent 逻辑**：这样无论是用在 OpenClaw 还未来的其他运行时，规则是一致的、可替换的。可以做成一个简单的 Go/TypeScript 库，接收 `{tool_name, parameters, session_context}` 并返回决策动作。
3. **区分“通知”和“确认”，设计成渐进的干涉等级**：不要只有“自动”和“确认”两态，中间加一个“异步通知”状态，大幅改善体验。
4. **对所有不可逆操作要求工具侧提供回滚能力或明确标记“不可逆”**：没有回滚方案的操作默认只能由人工执行，这个策略要写在硬规则里。
5. **将安全因子做成可配置的策略文件**：不同团队对风险容忍度不同，用 YAML 或 JSON 策略文件管理阈值、白名单和评估器权重，而不是硬编码。这样就可以在 dev 环境放宽策略提高自动化率，在 prod 环境收紧。

## 总结

AI Agent 的权限边界问题，本质上是一个控制系统里的 **“人在回路”（human-in-the-loop）工程化问题**。关键不在于问多少次“你确定吗”，而在于把“问人类”这件事的频率降到足够低，把每一次打断用在真正需要人的时刻，并且给人足够的信息去快速决定。

用风险等级、上下文安全因子和明确决策矩阵构建出来的权限边界，不会拖慢自动化，也不会让系统变成脱缰野马。这是目前我在 OpenClaw 上实践下来最稳定、最可复用的解法。
