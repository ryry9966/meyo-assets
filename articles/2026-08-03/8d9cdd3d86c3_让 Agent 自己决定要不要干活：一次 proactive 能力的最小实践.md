## 背景

大多数 OpenClaw 用户的日常是：在对话窗口输入指令，Agent 被动执行。这没问题，但距离"助手"还差一步。

真正的助手应该在你意识到需要之前，把事情办好。比如周一早上自动汇总上周的 issue 状态，而不是等你去问"帮我看看上周的 issue"。

我花了两周时间在 OpenClaw 上做了一个最小可用的 proactive 方案，想把其中关键的设计和踩坑记录下来。

## 问题

Proactive 的难点不在"执行"，而在"触发"。核心问题有三个：

1. **定时触发没有上下文**：定时器只会告诉你"该干活了"，但 Agent 不知道现在该关注什么。
2. **事件驱动需要守候**：如果要监控邮件、IM、日历，Agent 需要持续运行，资源开销大。
3. **主动性容易变成噪音**：如果 Agent 频繁主动打扰，用户很快就会关掉这个功能，比被动还差。

## 做法：基于 OpenClaw 的最小实现

我的思路是：**用 cron 表达式作为节拍器，用 MCP 工具作为上下文源，让 Agent 自己判断"现在该不该做"**。

具体步骤如下：

### 1. 配置定时唤醒

在 OpenClaw 的 agent 配置中，绑定一个 cron 表达式。我没有让它频繁触发，只选了两个时间点：早上 9 点和下午 3 点。前者做晨间汇总，后者做下午检查。

```yaml
proactive_schedule: "0 9,15 * * 1-5"
```

关键点：**不要在 system prompt 里写"每天早上 9 点执行"这种自然语言描述**。LLM 解析时间描述不可靠，用 cron 表达式让调度器精确触发。

### 2. 定义"待办抽屉"

我给 Agent 定义了三个 MCP 工具：

- `gitlab_open_issues`：读取当前项目的 open issues
- `calendar_events_today`：读取今日日历
- `pinned_note_list`：读取我在笔记里手动 pin 的重点

这三个工具合起来，构成 Agent 的"待办抽屉"。每次 cron 唤醒时，Agent 并行调用这三个工具拿数据。

### 3. 给 Agent 一个决策提示词

核心提示词模板如下：

```
现在是 {time}，以下是当前状态：
- 未关闭 issues：{n} 个
- 今日日历事件：{m} 个
- 置顶笔记：{k} 条

请判断：
1. 是否有需要我立即关注的事项？
2. 如果有，用不超过 50 字说明，并给出一个建议动作。
3. 如果没有，直接回复 PASS（不打扰用户）。
```

注意最后一条：**允许 Agent 选择"什么都不做"**。这是整个设计里最重要的部分。

### 4. 处理结果

OpenClaw 的 cron 触发的消息会作为新会话进入，我在上层做了一个轻量过滤器：如果回复以 `PASS` 开头，直接丢弃不推送；否则推送到我预设的 Slack channel。

## 踩坑点

**坑 1：早上 8 点的触发全部失败**

原因是 Agent 首次唤醒时模型尚未加载，cron 任务在冷启动时超时。解决方式是加了一个 warm-up 机制：第一次触发后让 Agent 保持常驻 10 分钟，而不是执行完就退出。

**坑 2：Agent "过度积极"**

第一版提示词没有"PASS"选项，结果 Agent 每天早上都会给我发"今日有 3 个 issue 待处理，建议尽快处理"。这就是噪音。加了 PASS 选项之后，干扰减少约 70%。

**坑 3：时间信息不可靠**

Agent 自己报的时间有时候是错的，因为模型训练数据的截止时间并不等于当前时间。必须显式注入 `{time}` 变量，不能依赖模型自己判断"现在几点"。

**坑 4：token 消耗比预期高**

每次 cron 唤醒都会调用多个 MCP 工具，虽然只推一句话，但后台 token 消耗接近一个完整对话。目前的做法是限制工具返回长度，比如只取 issue 的 title 和状态，不取 description。

## 可复用建议

1. **先定"不做什么"**：proactive 的边界比能力更重要。建议先想清楚哪些情况必须保持沉默。
2. **所有上下文必须来自工具，不能来自模型记忆**：模型记忆不可靠，工具输出是唯一的信任源。
3. **噪音阈值要保守**：如果你对一条推送的预期是"还行，能看"，那它大概率不该发。要推到"这确实帮到我了"才发。
4. **主动推送的量控制在每天 1-3 条**：超过这个量，用户会开始忽略所有推送，包括重要的。
5. **可回溯**：推送出去之后，对话记录要能被检索到。用户可能会想追溯 Agent 为什么推送了这条。

## 总结

Proactive 能力不是让 Agent 变得更聪明，而是**给它一个节拍器和一个仪表盘**。定时唤醒解决"什么时候看"，MCP 工具解决"看什么"，PASS 机制解决"什么不说"。

这套方案不一定适合所有人，但框架是可迁移的：cron 定时 + 状态工具 + 决策提示词 + 噪音过滤，四个组件缺一不可。

下一步我打算尝试用 Webhook 替代部分 cron 触发，让事件驱动（比如新 issue 创建）直接唤起 Agent 判断是否值得打扰。但从目前的体验看，cron 的稳定性比事件驱动的实时性更重要——毕竟，助手的第一要务是不打扰。
