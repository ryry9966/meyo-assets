## 背景：被日报困住的五分钟

团队内部一直有个不成文的规矩：下班前在飞书群里发当天工作摘要。听起来简单，但实际执行时经常会变成“回忆半小时，写不出三行字”。特别是跨仓库、跨平台协作的场景，一天的变更散落在 Git 提交、Jira 工单、文档评论和内部聊天记录里，手动汇总时漏掉关键变更几乎是常态。

另一面，OpenClaw 这类以 MCP（Model Context Protocol）为连接骨干的 agent 框架，已经能把 LLM 变成可以调用外部工具的执行者。我们就在想：能不能把“回忆-搜索-整理”这个过程，交给一个可控的流水线，每天自动生成一份结构化的日报草稿，人只需要最后做确认和补充？

刚好 OpenClaw 的插件体系和 MCP 工具接入比较自然，我们就试了一把，把做了一半的手工日报替换成了半自动 pipeline。这篇文章记录整个流程、工程细节和踩过的坑。

## 问题拆解：不只是调用一次 LLM

从原始日志到结构化日报，中间有几个工程问题需要拆清楚：

1. **数据来源碎片化**：Git commit 在 GitLab，任务在 Jira，技术文档在飞书文档，临时通知在群聊，没有一个单一数据源能覆盖全部工作。
2. **时间窗口和去重**：日报一般按天划分，需要精确截取当天的变更。如果有多条日志描述同一件事（比如 Jira 状态变更和对应的 commit），需要合并而不是重复列出。
3. **输出结构可控**：团队对日报格式有隐含期待，不能是泛泛的自由文本，至少需要“今日完成 / 进行中 / 计划明日 / 风险与阻塞”这四个区块。
4. **容错和可观测性**：流水线如果因为某个数据源不可用就直接报错中断，反而增加了焦虑，需要优雅降级。

这些问题单靠一条 prompt 塞给大模型很难稳定解决，必须把流程拆成可编排、可替换的步骤。

## 实现方案：基于 MCP 工具链的日报 Agent

整体架构是：**定时触发器 → OpenClaw Agent → 多个 MCP server → 汇总渲染 → 飞书消息投递**。下面分步骤说明。

### 1. 接入数据源，每个源包装成一个 MCP server

我们用三个已有的 MCP server，分别对接 GitLab、Jira 和飞书文档。如果开源社区的 server 不完全符合需求，可以自己小改一下，关键是暴露三类工具：

- `gitlab.list_commits(since, until, project)` 按时间区间拉取 commit 记录，返回 message、author、branch 和 diff 摘要。
- `jira.search_issues(jql)` 直接传 JQL 查询当天被分配或更新的卡片，拿到 key、summary、status。
- `feishu.list_doc_updates(date)` 获取指定日期有更新的文档列表和最后修改段落。

没有把群聊接进去，因为群聊信号太杂，事后发现人工补充更合适。

在 OpenClaw 的 `mcp_servers` 配置里，把这几个 server 注册为不同的工具源，Agent 启动后就能直接看到这些 tool。

### 2. Agent 编排：结构化计划取代一次性生成

最容易踩坑的地方是直接把“帮我写一份日报”丢给 Agent，期望它自己探索工具然后写出结果。实际效果很差，要么漏掉重要变更，要么把很多无关 commit 都塞进报告。

我们的做法是：**在 system prompt 里定义日报生成的标准作业程序（SOP）**，强制 Agent 按照“三步走”执行：

1. **数据采集**：依次调用三个 MCP server，拉取当天原始数据。每个调用都要指定精确的时间范围（`since` 和 `until` 用当天 00:00 到当前时间，避免时区偏差）。
2. **线索合并与去重**：把 Git commit 和 Jira issue 按照关键词（工单号、主题词）做粗粒度关联，把同一件事的多条记录合并成一条工作项。飞书文档更新作为背景补充，自动归入“进行中”或“其他”。
3. **结构化输出**：严格按照四段式模板生成日报，每一段用简洁的列表形式呈现，不添加主观评价和问候语。

system prompt 还加了一条约束：“若某个数据源不可用或返回空数据，跳过并在日报末尾注明数据源状态，不得凭空编造内容。”这是幻觉防御的底线。

### 3. 定时执行与结果投递

使用 OpenClaw 的任务调度能力，每个工作日下午 5:50 触发一次生成。生成后的 Markdown 文本，通过飞书 webhook 丢到团队日报群。我们保留了一个“confirm”参数，默认值为 false，所以消息会带上一行提示：“以上为自动生成草稿，请手动确认并补充必要内容”。

## 踩坑记录

1. **时区与时间范围**  
   不同的 MCP server 对时间的处理不一致。GitLab API 用 UTC，Jira 用用户时区。最终我们统一在 Agent 计划里要求所有查询先用 UTC 时间构造，再让 server 端做转换，避免出现“下午生成的日报漏掉整个上午工作”的情况。

2. **上下文窗口被 commit diff 撑爆**  
   最初实现时会让 Agent 直接把 commit 的 full diff 读进上下文，结果遇到大型重构提交时直接触发 token 超限。后来改成在 MCP server 层对 diff 做截断，只保留前 300 字符，并在返回时标注“... [truncated]”，让 Agent 能判断是否需要进一步拉取完整 diff。这个优化让上下文使用量降低了 60% 以上，同时没有明显影响日报质量。

3. **合并逻辑的假阳性**  
   按关键词合并 commit 和 Jira 时，有时会误将两条不相关的工作项合并。比如包含“优化”关键词的多个 commit 被归到同一个优化类 issue 里。我们在 prompt 里增加了验证步骤：合并前必须显式列出被合并的条目和合并理由，让 Agent 自己判断是否合理。虽然偶尔还会出错，但频次已经降到一周一次以内。

4. **工具调用失败静默跳过导致信息缺失**  
   最初我们让 Agent 在某个工具调用失败时直接跳过，但发现它有时不会在报告中注明数据缺失，导致用户以为当天真没变更。加上“缺失源必须在日报开头用声明提示”的规则后，可观测性好了一大截。

## 可复用建议

- **日报模板要“古板”**：不要追求生成漂亮的充满过渡句的报告。给出固定区块和列表格式，降低 LLM 自由发挥空间，反而更稳定。
- **数据源接入粒度要粗**：总想第一时间把所有 IM 消息、代码 review 指摘都接进去，结果噪音占比过高。从信息密度最高的源头（commit + issue）开始，跑通后再逐步加源。
- **保留人工确认环节**：自动化日报的价值是“减少回忆成本”，而不是“替代沟通”。生成草稿、人工补充的流程比全自动推送更可持续，也减少了团队对“AI 帮我说了错话”的焦虑。
- **把 MCP tool 当成 API 的包装**：不要直接用 LLM 的非结构化理解去处理日志，所有日志数据都必须通过 MCP tool 的结构化字段返回，确保 agent 看到的是干净、可比较的 schema，而不是一坨文本。

## 总结

这个流水线跑了三个月，日报草稿的“可直接使用率”从最初的 40% 逐步提升到 80% 左右，人工修改主要集中在对优先级的调整和补充临时发生的紧急事务。技术上没有引入新范式，只是把 OpenClaw 的 agent 能力、MCP 的标准化工具接口和硬性流程约束结合在了一起。

如果你也在用 OpenClaw 或类似框架做自动化汇报，建议从最烦的那个手工汇总步骤开始切，而不是试图一次做成全自动。日报只是一张“名片”，背后真正有用的是那条让你不再靠回忆填表的流水线。
