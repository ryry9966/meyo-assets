## 背景：从“等你说”到“主动干”

绝大多数 AI 助手都是被动响应的：你发一条消息，它回一条结果。Request-Response 模式简单、可控，但也决定了它永远只是你身后的工具，而不是会帮你留心杂事的前哨。

Proactive 能力指的是：在用户没有明确发出指令的情况下，助手根据预设条件、外部事件或内部状态变化，自行启动一项任务并交付结果。比如凌晨自动拉取竞品更新并生成简报、GitHub 仓库有异常流量时主动告警并尝试分析、交易日收盘后整合持仓数据推送。

在 OpenClaw 及更广泛的 Agent 生态中，有了 MCP (Model Context Protocol) 逐渐统一的工具调用与资源暴露方式，加上成熟的调度机制，构建一个可靠的 Proactive Agent 已经不再是“画饼”。本文记录一次完整的工程实践：如何让一个 Agent 在不等你开口时，就把事情办得明明白白。

## 问题拆解：Proactive 不是简单加个定时任务

直接给 Agent 套一个 cron 然后调用 `send_message`，会立刻踩坑。Proactive 的本质是一个“感知-决策-执行”循环，比被动模式多了一整套基础设施问题：

- **感知源多样性**：时间驱动、事件驱动（Webhook / MCP Resource 变化）、阈值驱动（数据监控）。
- **决策安全性**：何时该行动？如果上次任务还没结束，要不要再触发？错误重试多少次后放弃？
- **状态一致性**：如何避免重复执行、如何回传结果给正确的上下文。
- **用户可见与可控性**：主动行为必须可追溯、可停止、可调参。

因此，做法不能只靠“cron + LLM call”，需要把 Proactive 当作一个子系统来设计。

## 做法：基于 OpenClaw 的 Proactive 工作流

我们以一个真实需求为例：**监控一组服务健康检查端点，当连续失败次数超出阈值时，Agent 主动分析日志、创建 issue，并通知值班人员。** 下方是整个实现的核心骨架。

### 1. 感知层：统一触发器

使用 OpenClaw 的 `Task` 模型承载每个监控项，并借助 MCP 暴露的 `cron` 工具来驱动定时检查。

```
# 伪代码：注册一个定时健康检查任务
task = openclaw.create_task(
    name="health-check-proactive",
    trigger={
        "type": "cron",
        "expression": "*/5 * * * *"
    },
    action="run_health_check_agent"
)
```

除了定时，我们也可以利用 MCP 的 Resource Watcher 来监听数据库变更、文件落地等事件。MCP Server 将资源变化推送给宿主，宿主判断是否需要触发决策。对于 Webhook 源，用一个轻量网关（如 OpenClaw 内置的 HTTP 扩展）接收后写入内部事件队列，让后续统一处理。

### 2. 决策层：小模型 + 规则混合

高频检查如果每次都走大模型，成本高、延迟大。实际做法是：先通过规则引擎做第一层过滤。

```python
def should_activate(context):
    fail_count = context["fail_streak"]
    if fail_count >= 3:  # 阈值
        return True
    return False
```

当规则判定需要干预时，才将上下文打包成 prompt 交给 Agent，让它决定下一步操作：是尝试自动修复，还是直接通知人工。这样既保证了灵敏性，又不过度消耗推理资源。

### 3. 执行层：工具链与容错

Agent 拿到决策结果后，通过 MCP 工具组件执行具体操作，例如调取日志、重启服务、创建工单。必须为每个执行步骤包裹幂等逻辑与超时控制。

```
tools:
  - name: create_issue
    description: 在告警平台创建问题工单
  - name: fetch_recent_logs
    description: 拉取指定服务的最近错误日志
  - name: notify_ops
    description: 发送实时通知
```

关键点：所有执行流程都记录在 OpenClaw 的 memory 中，以便断点续跑和事后审计。

### 4. 反馈闭环

Proactive 动作执行完毕后，不能只存在日志里。我们将结果摘要推送到与用户的共享频道（如 Slack / 钉钉），并附上快速操作按钮（确认、回滚、调整阈值）。这样用户既能享受“先你一步”的便利，又始终保持对系统的掌控。

## 踩坑实录

1. **重复触发**：cron 触发时，如果上次任务因网络抖动执行了 90 秒，而间隔只有 60 秒，就会并发执行。解决方案是引入分布式锁或任务状态标记，每次触发前检查是否有未完成的同类型任务。
2. **上下文撕裂**：主动任务没有用户消息作为锚点，直接调用 LLM 时很容易缺少背景信息。必须在决策 prompt 中显式注入状态快照、历史动作和当前环境数据。
3. **死循环**：自动修复失败 → 再次触发修复 → 再次失败。必须设置每个周期内的最大重试次数以及全局冷却时间，冷却期间只记录不动作。
4. **MCP 资源泄漏**：长期运行的 Resource Watcher 若未及时关闭，会消耗客户端连接。使用连接池并设置合理的心跳和超时非常重要。
5. **权限传导**：主动任务默认以 Agent 所属身份运行，但有时操作目标需要更高权限。建议通过 MCP 的 `request_permission` 机制，在执行高危操作前获得用户的一次性授权。

## 可复用建议

- **采用事件总线而不是点对点调用**：让所有感知事件（时间、数据、外部）汇入总线，Agent 作为订阅者消费，解耦的同时便于扩展新事件源。
- **状态机管理任务生命周期**：定义 `IDLE -> CHECKING -> DECIDING -> ACTING -> COOLDOWN` 这样清晰的状态，避免混乱的 if-else。
- **幂等性设计是底线**：每一次操作都携带唯一 `idempotency_key`，下游工具基于该 key 保证执行一次且仅一次。
- **主动动作必须可观测**：将每一次主动决策的原因、过程、结果以结构化事件流暴露出来，方便调试和复盘。
- **提供“安静模式”**：允许用户一键暂停所有主动行为，确保在需要专注时不被助手干扰。

## 总结

让 AI 助手不等你开口就把事情办了，不再是智能音箱式的“今天天气怎么样”，而是工程化的自主任务系统。基于 OpenClaw 的任务调度、MCP 的标准化工具链，加上合理的事件感知与状态管理，已经可以落地到监控、数据处理、日常运维等场景。核心难点不在 AI 本身，而在如何设计一个安全、可观测、非侵入的 Proactive 外壳。希望这篇实践记录能给同样在尝试“让 Agent 先行一步”的你，提供一些真实的参考。
