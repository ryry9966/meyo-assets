## 背景：串行 Agent 的“慢”与“乱”

OpenClaw 社区的很多自动化流程都长这样：一个 Agent 接任务，按顺序调 MCP 工具——先查 A 接口，拿到结果后再喂给 B，最后汇总。当查询源只有两三个时问题不大，可一旦要做多维度的信息采集，比如同时检索 GitHub 仓库、Confluence 文档、内部 API 和用户反馈系统，串行模式立刻暴露出三个致命伤：

- **总耗时线性叠加**：每个工具调用都是阻塞的，5 个源依次跑，即便单个只花 10 秒，整体也要 50 秒。
- **上下文肿胀**：所有中间结果都堆在同一个 context window 里，Agent 很快开始“遗忘”早期信息或陷入幻觉。
- **错误传染**：一个源超时或返回异常格式，很容易导致后续步骤解析失败，整个 Task 崩溃。

于是团队开始寻找办法让多个 AI 可以**同时干活**，并且结果能被干净地合并。这就是“subagent 编排”进入实践的场景。

## 问题定义：不是多 Agent 聊天，而是并行执行单元

先厘清概念。我们说的 subagent 不是让两个 Agent 对话，而是一种 **Agent-工具化** 的模式：把一个带独立上下文、独立 tool 集的 Agent 封装成一个普通工具（Tool），主 Agent 可以像调用函数一样调用它，并可同时发起多个调用。在 OpenClaw 体系中，这完全可以通过 MCP 服务器或框架内置的 Task 机制实现，比如在 node.js 环境里将子 Agent 的逻辑包装为 `callSubAgent` 方法，注册到主 Agent 的工具列表。调用时给每个子 Agent 分配明确的小任务，比如“从源 X 提取关键变更”，并发执行，最后主 Agent 做合成。

## 实现步骤

以我们最近做的一个“发布巡检 Agent”为例，它需要在发版前同时从三个渠道收集变更证据：Git 提交 diff、CI 产物报告、安全扫描结果。我们这样拆解：

### 1. 定义子 Agent 的原子任务
为每个数据源写一个独立的 prompt 模板，让子 Agent 只做一件事。比如 Git diff 子 Agent 的 instruction 严格限定：

> 仅分析提供的 git diff 内容，输出结构化的变更摘要：{“files_changed”:...,”repos”:...,”risk_level”:...}。不调用任何额外工具，不扩展分析。

这类限制能避免子 Agent “自由发挥”产生冗余输出。

### 2. 将子 Agent 封装为工具
在 OpenClaw 中，我们基于 `createAgent` 为每个子任务生成 Agent 实例，再用 `tool()` 将其包装成可调用函数。关键配置是 `limitContext` 与 `maxSteps`——给子 Agent 极小的 token 配额和步数，强制其快速完成并退出。示例伪代码：

```ts
const gitSubAgent = createAgent({...});
const gitTool = tool(gitSubAgent, { maxConcurrency: 3 });
```

### 3. 主 Agent 并行派发
主 Agent 在接到用户指令时，系统 prompt 明确要求：“对数据采集步骤使用并行工具调用”。OpenClaw 的 Agent 执行器会自动在同一个 turn 内发出多个 `tool_call`，这些调用会被同时执行，无需额外线程管理。

我们只需保证每个工具调用之间没有数据依赖。这一步其实是在 prompt 里声明：“先同时调用 `git_diff_tool`、`ci_report_tool`、`security_scan_tool`，得到全部结果后再进入分析。”

### 4. 结果聚合与容错
当三个结果返回后，主 Agent 在下一轮推理中将它们填入一个合成 prompt，生成最终摘要。为了保证稳定性，每个子工具的输出都强制套了一层 JSON schema 校验（通过 MCP 服务器的结构化输出参数），即使某个源挂了，也能返回标准错误对象 `{"error": "timeout"}`，主 Agent 看到这个对象后能自行降级：“git 信息缺失，仅基于 CI 和安全报告给出结论。”

## 踩坑点

真正上线后碰到的坑远比设计时多，挑几个有代表性的：

- **并发不是越高越好**  
  最初把 `maxConcurrency` 设为 10，结果多个子 Agent 同时抢 LLM API 的速率限制，引发大面积 429。最终调整为 3~5，配合 backoff 重试才稳定。如果数据源本身有速率限制（如某些内部系统），还要在工具层加限流器。

- **子 Agent 的上下文隔离不彻底**  
  如果用同一个 Agent 实例复用 context window，上一个子任务留下的对话残留会污染下一次执行。必须确保每个工具调用都重新初始化子 Agent 的上下文。OpenClaw 的 `tool()` 封装默认每次调用传入的是独立的 message 列表，但切忌在子 Agent 内部使用 session 级别的记忆。

- **合并时的事实冲突**  
  两个源对同一次变更给出了矛盾信息，比如 Git 显示有代码改动，CI 报告却显示构建未触发。早期的主 Agent 会直接崩溃或瞎编一个解释。后来我们给合成 prompt 加了冲突解决步骤：“如发现事实冲突，标记为 `conflict: true` 并分别陈列矛盾点，不做猜测。”这样反而让输出更有工程价值。

- **Token 消耗暴增**  
  并行子 Agent 把多个独立上下文同时压入 LLM，虽然速度快了，但总 token 量约等于各子任务之和加上主合成。需要权衡：如果数据源体积不大，串行其实更省 token。推荐在数据量大的场景（如 diff 超过 5000 行）才用并行，小任务直接内联。

## 可复用建议

在多个项目中复用这套模式后，总结出几条工程原则：

1. **子 Agent 输出强 schema**：用 strict JSON 模式，定义必选字段和错误字段，让主 Agent 不用猜格式。
2. **设置硬超时**：工具调用层面设置 deadline（如 30 秒），避免某个源长 hang 拖垮整个编排。
3. **部分失败优于全失败**：允许部分子任务失败，主流程依然出得啦结果（标记缺失字段）。这比固执地重试直到成功体验更好。
4. **监控并发与速率**：为每个子工具记录执行时长和状态码，便于后续调优并发度。
5. **边界清晰是前提**：子 Agent 的职责必须极度单一，绝不能让子 Agent 再去调另一个子 Agent，嵌套会导致调试噩梦。

## 总结

Subagent 编排不是让系统变“酷”的炫技，而是真实解决耗时痛点的架构选择。在 OpenClaw 中，利用 MCP 工具封装和并发 tool_call，我们得以把原来 50 秒的串行巡检压缩到 15 秒，且上下文更干净、失败更可控。当然，代价是更复杂的错误处理和 token 账单。建议先在重度 I/O 场景落地，逐步沉淀出团队自己的“并行工具箱”，再推广到其他 Agent。
