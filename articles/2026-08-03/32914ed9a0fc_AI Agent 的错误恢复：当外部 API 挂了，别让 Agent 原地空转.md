## 背景

OpenClaw 这类 Agent 框架的价值在于把多个外部工具串成自动化流水线：MCP 拉起插件、查询数据库、调用大模型、操作第三方服务。但串得越多，依赖的外部 API 就越多。下游任何一个服务抖动，都会顺着调用链传导到 Agent 主流程。

最常见的现象是：Agent 报了一个异常，然后开始疯狂重试同一个请求，或者直接中断退出，留下一段没有执行完的任务日志。这在定时任务和无人值守场景下尤其致命——深夜里某个天气 API 升级导致整个早报流程挂掉，第二天你才发现。

## 问题本质

外部 API 故障分两种：**瞬时故障**（网络抖动、超时、限流）和**永久故障**（密钥失效、请求体非法、接口已下线）。Agent 和普通程序最大的区别是——普通程序遇到错误会抛出异常让人来处理，Agent 往往会"自作主张"地重试、换参数或者继续往下执行。

问题就出在这里：Agent 不知道哪些错误值得重试，哪些错误重试一万次也没用。如果不对这一步做显式控制，Agent 的行为就不可预测，也谈不上可靠。

## 做法与步骤

下面是我在 OpenClaw 的 MCP 工具调用和自动化脚本里逐步验证过的一套方案，核心思路是把错误处理从 Agent 的"自由发挥"变成工程化的**显式策略**。

### 第一步：错误分类，而不是统一 retry

在 MCP 插件或工具函数的出口做一个统一的错误拦截层，把异常归一化成两类：

- **可重试错误**：网络超时、5xx、429 限流、EOF/连接重置
- **不可重试错误**：401 鉴权失败、400 请求体非法、404 资源不存在

代码层面可以用一个极简的装饰器实现：

```python
RETRYABLE_STATUS = {408, 429, 500, 502, 503, 504}

def classify_error(exc):
    if isinstance(exc, TimeoutError):
        return True
    if hasattr(exc, "status_code") and exc.status_code in RETRYABLE_STATUS:
        return True
    return False
```

Agent 拿到分类结果后，只对第一类错误做重试，第二类直接返回错误给上层或记录日志，不再浪费 token。

### 第二步：指数退避 + 抖动，而不是死循环重试

对可重试错误，设计固定的重试参数，不要依赖 Agent 的"直觉"：

- 最多重试 **3 次**
- 延迟序列：1s → 4s → 9s（指数增长）
- 每次加 ±20% 随机抖动，防止多个 Agent 实例同时重试打爆下游

在 OpenClaw 的自动化流程里，可以把它封装成一个 Task 的中间步骤，而不是把重试逻辑写在 prompt 里让 LLM 自己去判断——LLM 对时间的感知不可靠。

### 第三步：熔断，给下游和 Agent 都留条活路

连续失败超过阈值（比如 5 次），就直接打开熔断开关，后续请求不再发起，直接走 fallback 路径。熔断状态可以放在 Redis 或本地文件里，按服务名维度存储。半开状态（熔断 30 秒后放一个试探请求）有助于快速恢复而不用一直卡死。

### 第四步：降级，要有可用的 Plan B

这是很多人忽略的。Agent 调用外部 API，目的通常是为了拿到某种数据。在数据源挂掉时，有没有备选路径？

- **缓存兜底**：把上次成功获取的结果存到本地（带时间戳），API 挂了就返回缓存并标注 `stale_data: true`
- **静态降级**：一些天气、汇率类 API 有公开的静态页面，可以用爬虫或数据文件顶一下
- **结果拼接**：如果 A 服务挂了但 B 服务有相似能力，可以临时切换工具

### 第五步：持久化 + 队列，别丢任务

无人值守场景下，所有失败任务应该落盘或者进队列，不能就地丢弃。OpenClaw 的定时任务可以在失败后把任务上下文 dump 到 `.jsonl` 文件，恢复后重放队列。这一步保证了不可用期间的请求不会丢失，等 API 恢复后补跑。

## 踩坑点

1. **429 不等于 5xx**。限流是瞬时错误，但它的重试窗口是 `Retry-After` 头部指定的值，不按这个来，怎么重试都会失败。要主动读取该头部并按它校准退避时间。

2. **幂等是重试的前提**。如果下游 API 不是幂等的（比如创建订单的 POST 请求），盲目重试可能产生重复数据。要么保证请求带幂等键，要么严格限定只对 GET 类请求做自动重试。

3. **Agent 会对错误过度解释**。OpenClaw 的 LLM 收到异常后，有时会自己编造一个修复方案，比如偷偷改参数重试、绕到另一个工具。要让 Agent"少做判断"，通过工具层的强约束把错误处理流程固定下来。

4. **Mock 测试蒙蔽了真实网络**。在本地测试时一切正常，因为 mocking 库对错误类型的模拟不完整。上线前务必用真实网络断开、kill 进程、改错 URL 等方式做故障注入测试。

5. **错误日志要有足够上下文**。只记一个 `API Error` 对排查毫无帮助。要记录请求 URL、入参 hash 值、重试次数、熔断状态、耗时，方便事后复盘。

## 可复用建议

- 每个外部 API 的调用都应该有一个统一的**错误处理模板**，不要顺手写到处散落的 try-except
- 重试策略、熔断阈值、降级路径都要写进配置，方便不换代码调整
- 所有 Agent 的自动化 Task 都值得加一个 **5 秒超时 + 3 次重试** 的默认配置，成本极低收益明显
- 定期做一次"混沌测试"：手动停掉某个外部服务的 key，看 Agent 会不会优雅降级
- 把错误处理做成三层：**代码层拦截**（确保异常结构一致）→ **策略层控制**（重试/熔断/降级决策）→ **Agent 层输出**（LLM 只用最后的结果语义）

## 总结

外部 API 挂掉是常态，不是例外。AI Agent 的价值不应该只体现在"能调用工具"，更体现在**当工具不可用时依然能给出理智的行为**。错误恢复不是靠给 prompt 里写一句"如果出错请重试"就完事，而是要靠代码层把不确定性约束住。

把错误分类、退避重试、熔断、缓存降级、持久化队列这五件事做扎实，你的 OpenClaw 自动化流程才真正谈得上"无人值守"。别让你的 Agent 在深夜里对着一个 503 空转。
