## 背景：E2E 测试自动化的痒点

端到端测试的价值人尽皆知，但维护成本一直是团队的隐痛。页面一改，选择器就失效；场景一多，脚本就臃肿。近两年 AI 辅助生成测试代码（尤其是 Playwright / Cypress 脚本）让人看到希望，可现实往往是：第一次生成“看起来像那么回事”，真正跑起来要么定位不到元素，要么断言形同虚设，稍微复杂的业务流程就直接翻车。

本质问题不是 AI 不够聪明，而是我们把测试生成当成了一次性的“问答”——给一段需求描述，期望直接产出可用的测试文件。这种单步生成在缺乏上下文反馈的情况下，成功率很难突破工程化落地的那条线。

如果你所在的环境已经在使用 OpenClaw 这类多 Agent 协作框架，并且通过 MCP 连接了浏览器、日志等工具，那么正好可以把“写测试”这件事变成一个可迭代的协作闭环。

## 问题拆解：一次性生成的软肋

以一个常见的电商结算流程为例，一次性生成经常会踩中这些坑：

- **选择器脆弱**：AI 默认倾向于 `text=`、`css=` 这种表层定位，一旦页面文案或 DOM 结构微调，脚本立刻崩掉。
- **断言敷衍**：只检查“页面不报错”或“按钮可点击”，缺失对业务状态（如订单金额、库存扣减）的校验。
- **无法应对动态页面**：生成时没见过真实的异步加载、骨架屏、鉴权跳转，代码看似正确，实则一跑就超时。
- **修复靠猜**：跑失败之后，只能手工改脚本，没有形成“执行→观测→修正”的回路。

把流程拆开，让不同的 Agent 分工负责理解、建模、编码和反馈，就能逐个击破这些问题。

## 做法：多 Agent 协作工作流

下面是一套基于 OpenClaw 编排的实现步骤，核心思路是用 MCP 协议把 Playwright 的浏览器能力暴露给 Agent，形成一个闭环。

### 1. 准备环境与 MCP 工具

启动一个 Playwright MCP Server，提供 `browser_navigate`、`browser_snapshot`、`browser_click`、`browser_evaluate` 等原子能力，并注册到 OpenClaw 的 Agent 可用工具集中。同时为后续的反馈环节保留截图和 Console 日志获取接口。

### 2. 定义四个 Agent

- **需求理解 Agent**：接收测试目标（可用自然语言描述，或解析已有的 PRD 摘要），输出结构化的测试场景步骤，类似简洁的 Gherkin 语言。
- **场景建模 Agent**：把测试步骤映射为页面交互序列，补充前置条件、数据准备、期望的 API 回应和页面状态。它可以调用 `browser_snapshot` 获取当前页面的可访问性树，以此推断合理的定位策略。
- **代码生成 Agent**：将建模结果转为 Playwright 脚本，强制要求优先使用 `data-testid` 或团队维护的元素映射表，其次才是可访问性定位；断言必须覆盖关键业务状态。
- **执行与反馈 Agent**：真正运行测试，收集失败信息、截图和 DOM 快照，解析错误（如 `TimeoutError`、`strict mode violation`），将修正建议打包后回传给代码生成 Agent。

在 OpenClaw 中，这些 Agent 通过工作流定义串联起来，可以设置最大迭代次数，防止无限修正。

### 3. 执行与反馈循环

一次完整的任务大致是这样：

1. 需求理解 Agent 输出场景：`用户登录 -> 搜索商品 -> 加入购物车 -> 结算 -> 确认订单金额`。
2. 场景建模 Agent 在沙箱环境内打开页面，抓取登录按钮的 `data-testid` 和输入框属性，补齐每个步骤的 UI 元素信息。
3. 代码生成 Agent 产出测试文件，并标明需要注入的测试数据。
4. 执行 Agent 运行脚本，假设“结算”按钮因为二次确认弹窗导致定位失败，它会截取弹窗截图和最近的 DOM 快照，附上错误堆栈，反馈给代码生成 Agent：“在点击结算后出现 Dialog，需先处理 `dialog_confirm` 按钮。”
5. 代码生成 Agent 据此修正选择器和步骤顺序，重新生成，直到测试通过或达到迭代上限。

这个闭环让 Agent 能基于真实浏览器反馈自我校准，而不是凭空猜测。

## 踩坑记录

实际落地中，有几个反复出现的坑值得注意：

- **元素定位的最后一公里**  
就算用了可访问性树，AI 还是可能把“看起来唯一”的 `role=button` 当成稳定选择器，结果页面里 3 个同样角色的按钮直接让 `click()` 报 strict mode 错误。最终方案是强制要求页面开发者提供一份关键元素的 `data-testid` 映射表，并通过 MCP 的工具注入到 Agent 的上下文里，才把误判率降下来。

- **断言空洞问题**  
Agent 天然倾向于生成“不报错就算通过”的断言。需要在场景建模 Agent 的提示中硬约束：每条场景必须包含至少一个显式业务状态校验，比如“订单金额等于商品单价×数量”。同时，允许执行 Agent 在失败时调用 `browser_evaluate` 抓取关键 DOM 的文本内容，供反馈阶段参考。

- **MCP 工具调用超时与资源清理**  
多次迭代跑测试，浏览器实例容易残留。我们在执行 Agent 的清理逻辑里加上了强制关闭 context 的步骤，并设置了单次迭代的最长执行时间，避免工作流卡死。

## 可复用的工程化建议

如果要在团队里推行这套方法，有几点经验可以复用：

1. **维护一份页面元素映射表**：用 JSON 或 YAML 记录每个页面的 `data-testid` 及其对应的业务含义，作为 Agent 的固定知识库。更新页面时同步更新映射，比让 AI 猜要可靠得多。
2. **测试意图与实现分离**：让 Agent 先生成一份人类可读的测试意图文件（场景步骤），再自动转为代码。这份意图文件既方便人工审核，也能在页面结构变化时快速定位需要修改的步骤。
3. **设置人工审查门禁**：Agent 产出的测试脚本不要直接进 CI，先由开发或 QA 快速扫一遍，标记为“可信”后再合入。这样几轮下来，Agent 的生成模式会更贴合团队习惯。
4. **利用多模态辅助定位**：如果页面没有稳定的 `data-testid`，可以让 Agent 在失败时截取页面图片，通过支持视觉的模型做一次区域标注，再自动计算坐标位置。虽然速度会慢一点，但对遗留系统很管用。

## 总结

Agent 协作并没有让写 E2E 测试这件事变得“完全不用动脑”，但它的确把一个高门槛、高失败率的单步生成任务，拆成了可观测、可修正的工程化流程。通过多 Agent 分工和 MCP 提供的工具接口，我们得以在真实浏览器反馈的基础上反复迭代，生成的测试脚本从“偶尔能跑”变成“大多数情况下可用”。对于已经在使用 OpenClaw 做自动化编排的团队来说，这是一条可以立刻着手实践的路径。
