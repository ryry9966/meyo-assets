## 背景：Agent 的记忆总被“想不起来”拖后腿

在构建带长期记忆的 AI 助手时，大家几乎都会第一时间上向量数据库：把所有对话切片打入 embeddings，recall 时用语义相似度拉回 Top-K。但当系统真正跑起来，很多人会发现，“我昨天说的重要事”召回了三条不相关的闲聊，而“帮我记住 Wi-Fi 密码是 abc123”这种精确信息，反而比 SQLite 全文搜索更不可靠。

另一方面，纯全文检索（如 SQLite FTS5、Elasticsearch）在中文分词、同义词和指代消解上又是个盲人，遇到“上次提到的那个客户”大概率直接哑火。

在 OpenClaw 生态里，memory 通常通过 MCP 工具（`memory_store` / `memory_recall`）或插件体系落地。无论你是直接用社区的 memory 插件，还是自己包了一个 MCP server 做记忆服务，都会面临一个选择：**recall 到底用语义搜索、全文搜索，还是混合？** 本文从工程实践角度做一个可复现的对比，并给出选择建议。

## 问题：不是谁更“先进”，而是谁在场景里更准

我们设定一个贴近真实 Agent 的场景：助手需要记住用户偏好、待办事项、特定事实，并能在后续对话中准确 recall 并注入上下文。评测指标不是理论上的 Recall@K，而是“喂给 LLM 后能否正确回答问题”的端到端准确率。

我们选择两种典型实现：

- **语义搜索**：OpenAI `text-embedding-3-small` + Chroma，chunk_size=512，overlap=50
- **全文搜索**：SQLite FTS5 + jieba 分词，以每条 fact 作为一个文档（相当于结构化存储）

测试集从真实团队使用日志中抽取出约 200 条记忆项，包含精确事实（“我的 GitHub 用户名是 xxx”）、模糊提及（“下周那个评审会议”）、偏好（“我不喜欢太正式的邮件风格”）等，并构造了 50 个查询。

## 做法与步骤：搭建一个可量化的对比流水线

1. **数据准备**  
   从多轮对话日志中提取“记忆事件”。可以人工标注，也可以让 LLM 做一次主动提取（`请从对话中提取需要长期记住的事实`）。每条事件保留原始表述，作为 ground truth 的“本体”。

2. **双写存储**  
   - 语义路：用 embedding 模型向量化每条事件，存入 Chroma collection，metadata 中带原始文本和事件 ID。  
   - 全文路：在 SQLite 中建 FTS5 虚拟表，对每条事件的文本做 jieba 分词后插入索引入口。

3. **构建查询集**  
   针对事件分别写两种风格的查询：  
   - 精确匹配型：“我的 GitHub 用户名是什么？”  
   - 语义模糊型：“之前聊到的那个代码仓库地址是哪？”  

4. **Recall & 评测**  
   每个查询分别走两条检索路径，取 Top-3 片段拼成上下文，调用同一 LLM（如 gpt-4o-mini）作答。人工判断回复是否命中原事实。统计分别的准确率与 bad case 类型。

实际跑下来，这个小规模实验出的趋势是：  
- 精确事实类查询，全文搜索准确率高出约 15-20%；  
- 模糊指代、上下文依赖类查询，语义搜索领先 10-15%；  
- 两类都存在“召回相关但不够精确”导致 LLM 幻觉的情况，但全文搜索对中文指代的漏召问题更突出。

## 踩坑点：实现细节才是魔鬼

### 1. 向量模型的中文理解力与成本
直接用 OpenAI 的 embedding 模型虽然省事，但遇到领域缩写、拼音别名等容易产生漂移。如果想压成本上本地模型（如 bge-large-zh-v1.5），需额外关注部署资源和 qps 瓶颈。

### 2. 分块与分词策略强耦合
语义搜索的 chunk 太大，召回的片段含噪过多，LLM 容易分心；chunk 太小则丢失上下文。全文搜索的分词器对中文分词误差敏感，例如“马上手”被拆成“马上/手”，而实际是“马上手”指 immediate handoff。需要维护自定义词典。

### 3. 混合检索并非“加个权重”那么简单
最简单的 `score = α * vector_similarity + (1-α) * bm25_score` 看似公平，但两种分数的分布和尺度完全不同，需要做归一化。实践中，先用全文搜索做粗筛（Candidate Pool），再对粗筛结果做高精度语义重排序，效果更稳定。

### 4. 记忆的新鲜度衰减
不管是哪种检索，都容易忽略“旧信息应该权重更低”。我们后来在 recall 的排序侧统一加入了时间衰减因子，这比单纯纠结向量还是全文影响更大。

## 可复用建议

- **从简单开始，渐进升级**  
  对于可结构化存储的偏好/事实，直接用 SQLite + FTS5 完全够用。在 OpenClaw 里可以写一个最小化的 `memory_recall` MCP tool，只做全文匹配，上线后根据 bad case 决定是否引入语义路。

- **用显式记忆类型分流检索策略**  
  如果你的系统支持“主动记忆”与“对话上下文”的区分，可以对主动性事实走全文，对被动隐式信息走语义。比如 `memory_store("key", "value")` 直接存键值对，recall 时精确匹配 key。

- **建立回归测试集**  
  抽 50-100 条真实查询，每次改动 embedding 模型、chunk 大小或排序权重后跑一遍，看准确率变化。这是防止记忆系统悄悄退化的最低成本防线。

- **考虑 context window 的边际效用**  
  如果你总是把 Top-3 塞进 prompt，但 LLM 上下文窗口足够大，不如适当扩大召回数量到 Top-5 甚至 Top-10，再用 LLM 自己做相关性筛选（比如让 LLM 在思考前先输出“相关记忆项 id”）。这可以弥补单一路径的漏召。

## 总结

语义搜索和全文搜索在 memory_recall 里不是替代关系，而是互补手段。工程上更务实的路径是：
1. 先上一套可观测的全文检索基线；
2. 通过线上真实对话积累 bad case；
3. 再针对模糊指代和语境依赖型查询引入语义搜索；
4. 最终走向粗筛+精排的混合检索。

记忆系统的核心竞争力从来不在于“用了多贵的向量库”，而在于你能否持续迭代那个贴近真实对话的数据集和评测流程。
