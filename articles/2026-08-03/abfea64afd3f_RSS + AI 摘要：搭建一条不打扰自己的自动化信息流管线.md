## 背景

订阅 RSS 的人往往有一种执念：想掌控信息入口，而不是被算法投喂。但 RSS 的一个副作用是，它会把你拖回“信息松鼠病”的深渊——订阅源越来越多，未读数常年 999+。

当你订阅了 50 个技术博客、3 个资讯站和若干 GitHub Releases 之后，每天面对几百条标题，筛选成本已经超过了阅读收益。这时候需要解决的，不是“如何订阅更多”，而是“如何让管线先替我读一遍”。

这篇文章记录了我基于 OpenClaw 搭建 RSS + AI 摘要管线的一次实践。它不是一个多复杂的系统，但足够实用，能让你每天花 5 分钟读完原本需要 1 小时才能消化完的信息量。

## 问题

人工处理 RSS 的痛点很明确：

1. **标题无法反映内容价值**。技术文章的标题往往具有欺骗性，要么过于标题党，要么过于平淡。
2. **信息密度低**。很多文章前面 80% 是铺垫，真正有价值的可能只有几句话。
3. **跨源去重困难**。同一个技术热点，多个博客会在同一天推送相关文章。
4. **时效性压力**。你总觉得今天不看，明天就过期了。

这些问题的本质是：**筛选和摘要工作需要前置，而不是人工后置**。

## 做法

整体架构是一个“拉取 → 清洗 → 摘要 → 推送”的管道，全部跑在 OpenClaw 的自动化任务里。

### 第一步：订阅源管理

用 OPML 文件统一管理。我的原则是“宁缺毋滥”，只保留以下三类来源：

- 原创技术博客（个人站点，非聚合站）
- GitHub Release 或 Changelog（用于追踪工具更新）
- 行业通讯（如 Hacker News 精选，而非全量）

OPML 文件的维护建议放在单独的 Markdown 文档里，写明每个源的添加理由和移除日期，避免订阅源无限膨胀。

### 第二步：拉取与过滤

OpenClaw 的 RSS 插件负责定时拉取。关键配置是：拉取间隔 30 分钟、单次最大条目 50 条、超时 10 秒。这个配置能避免被反爬，也不会因为某个源响应慢而阻塞整个管道。

拉取后保留原始 XML 结构，不要急着转 Markdown。因为后面清洗需要知道每个字段的原始语义（如 `dc:creator` 和 `content:encoded` 是不同的字段，混在一起会丢失信息）。

### 第三步：AI 摘要（核心步骤）

摘要服务用 OpenClaw 工具调用 LLM 接口完成。构造 Prompt 时要注意：**摘要其实是“压缩 + 提炼”两件事**。

我用的 Prompt 模板大致如下：

```
你是信息筛选助手。下面是一篇技术文章的标题和正文（可能被截断）。
请输出：
1. 一句话结论（如果文章没有结论，则写“无明确结论”）
2. 三个要点（每条不超过 30 字）
3. 可采取的行动（如有，例如“升级到 v2.1 修复了 CVE-2024-XXXX”）
4. 建议保留或丢弃（理由一句话）
如果文章内容与标题无关，或明显是 SEO 垃圾，请在“建议”中标注“弃”。
```

这里有个细节：正文不要全部塞进上下文，而是**截取前 1500 字符 + 标题 + 所有小标题**。绝大多数技术文章的结论都出现在开头或标题里，全量塞入既费 token，又会稀释注意力。

AI 输出的结构化结果以 JSON 返回，方便后续处理。

### 第四步：汇总推送

摘要完成后，管道不直接推送到终端，而是写入一个当日汇总文件 `digest-YYYY-MM-DD.md`，按来源分组。每晚 21 点，OpenClaw 将该文件推送到我的 IM 工具（或邮箱）。

推送格式统一为：

```
📌 值得细读（2篇）
- [标题1] 一句话结论 + 链接
- [标题2] 一句话结论 + 链接

🗑 建议跳过（8篇）
- [标题3] 理由
```

这样做的优势是：**你不必在信息到达的瞬间就响应它**。信息在后台被消化，你只在固定时间点做一次阅读决策。

## 踩坑点

**1. 频率控制是必须的。** 一开始我把拉取间隔设成 10 分钟，结果几个获取频率较高的源触发了服务端的 429 限制，被临时封禁 IP。后来把间隔改为 30 分钟，并加入了“连续三次拉取失败则暂停一天”的熔断逻辑。

**2. 既有内容要跳过。** RSS 拉取插件默认会重复推送相同条目。如果你的任务调度是“每 30 分钟跑一次”，必须使用基于 `item_guid` 的去重逻辑，否则你会在第二天收到 20 条一模一样的摘要。

**3. AI 摘要会“说瞎话”。** 当文章内容被截断后，LLM 有时会脑补结论。如果你遇到“摘要内容似乎真实，但原文搜索不到”的情况，一定要在 Prompt 里显式加一句：“如果信息不足，请不要猜测，直接输出‘信息不足’”。

**4. 不要忽略输出端限流。** 如果你把摘要推送到企业微信或 Telegram Bot，发消息频率超过限制会被静默丢弃。最好在推送前做二次合并，减少消息条数。

## 可复用建议

如果你也想搭一套，我建议按这个顺序推进：

1. **先跑通 R0 版本**：只订阅 3 个源，拉取后直接把原文丢给 LLM 输出“一句话摘要 + 是否值得读”，推到终端。不要一开始就搞整套“打分 + 分类 + 知识库”。
2. **建立自己的“跳过词库”**：当 AI 连续三天标记某类文章为“弃”时，把这类的关键词（如“速来”“震惊”“必看”）记下来，加入预处理过滤。
3. **保存每周统计**：记录每天“值得读”的比例。如果这个比例低于 5%，说明你的订阅源质量下降了，需要清理。
4. **人机确认回路**：每周末花 10 分钟检查本周“建议跳过”的文章。这个反馈很重要，它能持续校准你的 Prompt 和过滤规则。

## 总结

RSS + AI 摘要并不会让你“知道得更多”，它的核心价值是**帮你省下筛选的注意力**，把精力留给真正值得读的少数内容。

这套管线的工程亮点不在单个环节，而在于组合之后的整体稳定性和可维护性。对于 OpenClaw 用户来说，最大的意义在于：**你不再追求“感知一切”，而是搭建了一个有思考能力的过滤器**。

信息爆炸时代，真正稀缺的从来不是信息，而是判断力。把判断力留给最重要的那几篇文章，剩下的交给自动化。

### 相关配置片段（仅供参考）

```yaml
# OpenClaw 任务调度示例
rss_digest:
  cron: "*/30 * * * *"
  rss_sources: "sources.yml"
  dedup_key: "item_guid"
  llm_config:
    model: "gpt-4o-mini"
    max_input_chars: 1500
    response_format: "json"
  output:
    type: "markdown_file"
    path: "./digest-{{date}}.md"
  push:
    time: "21:00"
    channel: "im"
  circuit_breaker:
    max_failures: 3
    cooldown_days: 1
```
