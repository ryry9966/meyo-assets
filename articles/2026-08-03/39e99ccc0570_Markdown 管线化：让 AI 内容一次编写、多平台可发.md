最近在把 OpenClaw 生成的几篇文章同步到公众号、知乎和个人博客时踩了不少坑。同一个 `.md` 文件，在本地预览正常，粘贴到公众号就丢失代码块高亮；发到知乎标题层级全乱；博客倒是没问题但图片引用路径又对不上。来回手工修格式的时间甚至超过了写正文本身。

如果你也依赖 Agent 批量产出内容，这篇文章值得一看：我们要讨论的不是“如何用 AI 写文章”，而是“如何把 AI 生成的 Markdown 变成一条可重复的发布管线”。

## 问题本质：Markdown 有方言，平台有编辑器

Markdown 号称统一标记语言，但每个平台都实现了自己的方言：

- 公众号富文本编辑器不支持标准 Markdown 语法，代码块渲染尤其脆弱
- 知乎支持标准 Markdown，但标题层级、数学公式有严格限制
- 掘金对 ```js``` 等围栏代码块友好，却不支持某些 GFM 表格
- 个人博客（如 VitePress/Hugo）需要本地完整渲染链路

如果 Agent 只输出一份“标准 Markdown”，最终人工适配成本极高。**你需要的是格式适配层，而不是再生成一份内容**。

## 做法：用 OpenClaw 把转换过程脚本化

我在 OpenClaw 里定义了一条简单的转换管线，核心思路是：**单一源文件 + 平台感知 prompt + 后置 lint**。

### 第一步：定义源文件标准

每个 AI 生成的文章使用统一的 YAML front matter：

```yaml
---
title: "用 OpenClaw 管理发布管线"
platforms: ["wechat", "zhihu", "juejin"]
created: 2025-03-20
---
```

正文只写最基础的 Markdown 子集：`#` 标题、段落、`-` 列表、围栏代码块、`![alt](相对路径)`。不写表格（平台差异大）、不写注脚（被忽略）、不用 HTML 标签（容易注入问题）。

### 第二步：创建平台转换 prompt

针对每个平台写一份转换规则，存为 OpenClaw 的 skill。以公众号为例，核心 prompt 是：

```
将输入的 Markdown 转换为公众号富文本可粘贴的格式。
- 代码块保留为 ``` 围栏，但仅用简洁语言包裹
- 标题层级压缩为三级以内
- 表格改为无序列表表述
- 图片引用重写为 base64 或服务端 URL
```

这里的关键是：**不要让 LLM 自由发挥**。prompt 里明确“不做内容增删，不改变标题含义，只调整语法表现层”。

### 第三步：后置 lint 校验

用轻量脚本扫描转换结果，检查：

```bash
# 检测不合规语法
grep -nE '^#{4,}' dist/wechat.md  # 不允许多级标题
grep -nE '!\[.*\]\(http' dist/wechat.md  # 不允许网络图片引用
```

我直接在 OpenClaw 里挂了一个 `format-lint` 插件，每次转换后自动跑一遍。失败则重新调用转换 skill。

## 踩坑点

1. **LLM 会“自作聪明”补介绍语**。初次跑管线时，模型经常在开头加“大家好，今天我们来聊聊……”。这类内容在博客和公众号会出现两次。解法：prompt 中写明“禁止添加任何原文不存在的导语或总结”。

2. **标题层级漂移**。源文件是 H1，转换后变成 H2，平台默认样式差异会直接影响阅读节奏。我在 prompt 中加入特殊标记：`标题层级映射表：wechat(H2->H3)`，模型按表执行。

3. **图片路径是零散文件名**。AI 生成图片时经常产出 `img_20250320_abc.png` 这类字符串，插入正文后一旦重命名就断链。正确的做法是：转换前先跑一个 `asset_cleanup` 插件，将图片改名为 `<slug>-01.png` 并移动到 `assets/` 目录，正文引用相对路径。

4. **表格是所有平台的灾难**。哪怕你在系统 prompt 里写好语法，不同 markdown 渲染器的管道符转义还是会让表格崩坏。最省心的方案是：**在源文件阶段就禁止表格**，如果有数据矩阵内容，用 JSON 代码块 + 简洁说明代替。

## 可复用建议

如果你准备在 OpenClaw 里实现这条管线，建议注意：

- **配置驱动而非代码驱动**：每个平台对应一个 `.yaml` 配置（包含目标语法白名单、禁止语法、标题映射），LLM 只负责读配置做转换。
- **输出目录分离**：`source/` 放 AI 生成原文，`dist/<platform>/` 放转换后结果，`assets/` 放图片。这样回滚和回溯都容易。
- **加入手工审查节点**：不要完全自动化。转换后先丢进本地 markdown 预览器检查一遍，确认格式没问题再发布。控制在 1 分钟内。
- **复用 lint 脚本**：大部分 lint 规则在博客场景也适用。先让 Agent 输出一份“最严格格式”（如知乎），再向宽松平台降级，会减少重跑次数。

## 总结

Markdown 管线化的目标不是“全自动发布”，而是**把格式适配从重复劳动中剥离出来**，变成一个可复用的工程组件。AI 生成内容的质量、平台规范的变化，都是持续迭代的事。但只要你把转换规则沉淀成插件和配置，将来发布到新平台只是增加一份 YAML 的事。

管线跑通之后，我每篇文章从 AI 生成到多平台发布的时间压缩到了 20 分钟以内，其中大部分时间是人工审查内容。希望这条思路对你也有参考价值。
