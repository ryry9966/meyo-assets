## 背景

OpenClaw 的价值在于把工具调用、记忆管理和模型推理组合成可编程的 Agent 工作流。但它在模型层是单纯的 client 抽象，本身不做路由。

这和 OpenAI SDK 没有本质区别——你在配置里写什么 endpoint，请求就发去哪。路由是自己加的一层逻辑，不是框架自带能力。

我接触 OpenClaw 时踩过两个极端：一是所有请求都喂 GPT，二是想用本地模型覆盖全部场景。前者账单好看不了，后者延迟和效果都不尽人意。需要的是按任务类型做请求级路由。

## 问题

OpenClaw 里模型调用发生在几个不同位置：

- 主对话循环（推理）：决定 Agent 下一步动作
- 工具调用参数生成：结构化输出
- 子任务 / 插件内部请求：比如摘要、分类、向量化

很多配置项是全局的。如果你只设一个 `model`，那所有环节都走同一个模型。插件内部可能有自己的模型参数，但那是插件各自负责，你需要逐一检查。

核心问题不是“GPT 好不好、本地模型行不行”，而是：**哪些环节的失败容忍度高、哪些环节的延迟敏感度低，以及哪些数据必须留在本地。**

## 做法

我的路由方案分两层，都很轻量。

第一层是环境变量切换。OpenClaw 配置里，模型端点用环境变量管理。在 `~/.openclaw/.env` 里定义：

```
OPENAI_BASE_URL="https://api.openai.com/v1"
OPENAI_API_KEY="sk-..."
LOCAL_BASE_URL="http://localhost:11434/v1"
LOCAL_MAIN_MODEL="gpt-4o"
LOCAL_FAST_MODEL="qwen2.5:14b"
```

主配置里指向这些变量。这样切换全局默认模型只需改 `.env`，不用动 YAML。

第二层是任务级拦截。OpenClaw 支持写请求拦截器（interceptor），在请求发出去前做判断。判断逻辑按任务特征：

- **工具调用与结构化输出**：走 GPT。这类响应必须 JSON 严格合法，本地小模型很容易漏字段、错格式。
- **对话主循环（推理）**：如果 Agent 的下一步动作大概率是“读文件→调工具→总结”，且链路过长，我会先用本地模型试一轮。本地模型给的工具调用若解析失败，拦截器直接捕获异常，重试时降级到 GPT。用重试机制兜底，比提前预判更可靠。
- **纯文本摘要 / 信息提取**：走本地模型。这类任务对格式错误容忍度高，错过几个要点影响有限。
- **含隐私数据的任何请求**：强制本地，甚至可以选择完全跳过云端。

拦截器的大致逻辑：

```python
def route_request(req):
    task_type = classify_task(req)
    if task_type == "tool_call" or task_type == "structured":
        req.model = "gpt-4o"
    elif task_type == "summary" and not req.contains_pii:
        req.model = "qwen2.5:14b"
    elif req.contains_pii:
        req.model = "qwen2.5:14b"
    return req
```

`contains_pii` 可以简单做关键词和正则匹配，不需要上模型。

## 踩坑点

几个实际遇到的问题：

**1. 工具调用的格式差异比想象中大。** 本地模型（Ollama 跑的）在 OpenAI 兼容模式下，工具调用的 JSON 结构与 GPT 有细微差别。OpenClaw 对工具调用有内部校验，不通过就直接报错。这不是简单改提示词能解决的，需要实测你的本地模型对复杂 tool schema 的遵循程度。我的经验是 7B 以下模型基本不可用，14B 的 Qwen 在简单工具上可以，复杂嵌套参数直接放弃。

**2. 重试逻辑不能只做一次。** 本地模型有概率性失败，特别是上下文很长时，attention 漂移导致格式错误率上升。重试一次不够，我在拦截器里做了最多 3 次重试，前两次本地，第三次切 GPT。

**3. 延迟不等于计算时间。** 本地模型看起来无网络延迟，但 Ollama 的 prompt processing 在小显存机器上很慢。长上下文的场景下，本地模型反而比 API 慢。需要实测你的硬件，别想当然认为本地更快。

**4. 异步任务里的路由容易被忽视。** OpenClaw 里有些后台任务（比如自动摘要、记忆压缩）不走主模型的配置，走的是默认配置。如果你没给它们单独设模型，它们会偷偷用 GPT，账单就是这么上去的。检查所有异步任务入口。

## 可复用建议

- **先分场景，再定模型。** 列出你的 Agent 所有可能的调用场景，标出：格式严格性要求、延迟敏感度、数据敏感度。然后划出分界线。
- **配置放 `.env`，逻辑放入口。** 模型名不放 YAML 硬编码，统一变量管理。
- **兜底用降级，不用双模型同时请求。** 同时请求两个模型（speculative routing）延迟高且浪费钱，串行降级就够用。
- **本地模型的选择，以工具调用的 JSON 准确性为第一标准，而不是看 benchmark 分数。** 跑一遍 OpenClaw 自带的 tool-calling 测试集，看通过率。
- **记录路由决策日志。** 每次请求打日志标明走了哪个模型、task type 是什么、是否重试。一个月后看统计数据，能发现哪些场景该调整分界线。如果本地模型的成功率低于 85%，直接切回 GPT 更省心。

## 总结

多模型路由不是“省钱方案”，是“成本-性能-隐私”三方权衡的工程决策。OpenClaw 没给你做这个权衡，你得自己来。

我的阈值是：**凡是需要严格结构化的，交给 GPT；凡是可以接受模糊输出的，交给本地模型；凡是不能出错的，交给 GPT。** 这个边界按你实际数据的失败率来调，不靠感觉。

路由逻辑本身不难，难的是认清你的 Agent 工作流里哪些是“不能错”的部分。这个判断只有你自己能做。
