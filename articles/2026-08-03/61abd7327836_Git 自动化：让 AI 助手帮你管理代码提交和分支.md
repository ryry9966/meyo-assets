# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

日常开发中，大量时间消耗在重复的 Git 操作上：切分支、暂存文件、写合规的 commit message、推送到远程、清理已完成的分支。这些动作本身没什么智力含量，但频率极高，一旦被打断就容易出错——提交信息不规范、分支名拼写错误、忘记 rebase、甚至把临时改动推到错误的远程分支。

最近半年，随着 agent 框架和 Model Context Protocol (MCP) 的工程化落地，“把工具交给 LLM” 不再是演示玩具。我们可以让 AI 助手真正理解仓库状态、执行 Git 命令，并在安全的边界内完成分支管理、变更提交和清理工作。本文记录我在 OpenClaw 环境下搭建 Git 自动化 agent 的过程，包括具体步骤、踩过的坑以及可复用的工程建议。

## 问题定义

目标是让一个 AI agent 能处理以下常见任务：

1. **从当前分支创建功能分支**，命名遵循团队规范（如 `feat/issue-123-description`）。
2. **自动生成规范的 commit message**，基于 `git diff` 和暂存区内容。
3. **安全地推送分支**，并在合并后删除远程/本地特性分支。
4. **始终避免在 main/master 上直接提交**，不执行 force push 等危险操作。

这些任务需要 agent 能够读取仓库状态（当前分支、文件变更、远程信息），调用系统 git 命令，并遵守预定义的安全策略。

## 做法：基于 MCP 的 Git 工具暴露

我们使用 MCP server 将 Git 操作封装为 LLM 可调用的 tools。社区已有 [git MCP server](https://github.com/modelcontextprotocol/servers/tree/main/src/git) 实现，它暴露诸如 `git_status`, `git_diff_unstaged`, `git_add`, `git_commit`, `git_create_branch`, `git_push` 等工具。结合 OpenClaw 的 agent runtime，可以直接注册这些工具并交给 LLM 使用。

### 步骤 1：搭建 MCP Git 服务

在 OpenClaw 配置中，将 git MCP server 作为一个子进程启动：

```json
{
  "mcpServers": {
    "git": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/path/to/your/repo"]
    }
  }
}
```

其中 `--repository` 指向你要自动化的仓库路径。注意这个服务只在允许操作的仓库范围内生效，避免 agent 碰触其他目录。

### 步骤 2：定义 Agent 的系统提示

系统提示需要明确 agent 的角色和硬性约束：

```
你是一个 Git 操作助手。你可以使用提供的 Git 工具管理仓库。
规则：
- 永远不要在 main/master 分支上直接提交或推送。
- 仅当用户明确请求时才执行 rebase 或 force push。
- 创建分支前检查工作区是否干净，若有未提交变更应先 stash 或提交。
- commit message 遵循 conventional commits 规范：type(scope): description。
- 推送前确保当前分支不是保护分支。
```

有了这些约束，LLM 在每个操作前会自我检查，降低误操作风险。

### 步骤 3：自然语言触发自动化工作流

用户通过聊天界面发出指令，例如：

> “帮我把最近的改动提交一下，主题是实现用户认证的登录接口，关联 issue #42，然后推到远程，创建 MR 链接发给我。”

Agent 内部执行流程：

1. 调用 `git_status` 获取工作区状态，确认有未暂存变更。
2. 调用 `git_diff_unstaged` 获取详细 diff。
3. 基于 diff 内容生成符合 conventional commits 的 message：“feat(auth): add login endpoint with JWT token generation”。
4. 检查当前分支：若在 main 则报错拒绝；若在 `feat/issue-42-login` 则继续。
5. 调用 `git_add` 暂存所有变更。
6. 调用 `git_commit` 提交。
7. 调用 `git_push` 推送当前分支到远程。
8. 读取输出中的远程 URL，构造创建 MR 的链接并返回给用户。

以上所有执行都有对应的工具调用和返回日志，一旦某步失败（如推送被拒绝因未拉取最新代码），agent 会反馈错误并给出修正建议，而不是盲目重试。

## 踩坑记录

### 1. 工作区不干净导致分支切换失败

用户可能忘记暂存或提交就要求创建新分支。直接 checkout 会丢失未保存的改动。我们的处理方式是让 agent 在创建分支前检查 `git status --porcelain`。如果有未跟踪或修改，先提示用户并暂停，或询问是否自动 stash。自动 stash 会增加复杂度，因此目前采用“仅提醒，不自动处理”策略，让用户显式确认。

### 2. commit message 生成质量波动

让 LLM 阅读 `git diff` 输出生成 commit message 时，若 diff 过大或包含二进制文件，生成的 message 可能偏离重点。解决方案是对 diff 做截断（限制 token 数），并明确告诉 LLM 只关注语义变更，忽略锁文件、构建产物等。我们还加入了 fallback：如果 diff 超过阈值，直接使用用户手动输入的 message 而非自动生成。

### 3. 权限与钩子冲突

有些仓库配置了 pre-commit hooks（如 lint-staged），但 agent 运行环境中可能缺少相关依赖，导致 commit 失败。提前让 agent 检测是否有 hook 执行失败，并提示用户解决环境问题，或通过 `--no-verify` 跳过（需在提示中明确允许该行为，且有审计日志）。

### 4. 并发操作与状态脏读

多个 agent 或用户同时操作同一仓库会导致竞态。我们的实践是给每个仓库加一个文件锁（如 `.mcp_git.lock`），工具在执行写操作前获取锁，操作完后释放。对于本地开发场景，这基本够用。

## 可复用建议

- **限定操作范围**：MCP server 启动时只能访问指定仓库，防止 agent 误操作其他项目。
- **所有操作记录审计日志**：每次工具调用都记录参数、返回码和用户 ID，方便回溯。
- **分层错误处理**：工具调用失败时，不要直接抛出原始错误给用户。通过 LLM 把错误翻译成自然语言建议，降低认知负担。
- **人工确认高风险动作**：rebase、merge、force push 需要用户二次确认。可以将这些工具标注为 `dangerous`，在 agent 逻辑中增加确认弹窗。
- **与 CI/CD 联动**：推送成功后，agent 可直接调用 GitLab/GitHub API 创建 MR，并设置为自动合并（如果通过 CI），形成“自然语言 → 分支+提交 → MR → 合并”的完整流水线。

## 总结

Git 自动化不是银弹，但对于频繁的多分支协作和规范化提交需求，AI 助手能显著降低机械操作成本，并强制推行团队的 commit 规范。通过 MCP 暴露 Git 工具，LLM 从“聊天机器人”进化为“仓库协作者”，既保持了灵活性，又守住了工程化的安全底线。

目前我们已将这套 agent 集成到 OpenClaw 工作空间，每日处理近百次分支创建和提交，人工介入率低于 5%。后续计划将代码审查（diff 总结、潜在问题分析）也纳入同一 agent，进一步释放开发者的时间。

如果你也在尝试类似的自动化，欢迎在社区分享你的安全策略和踩坑经验——毕竟 Git 是分布式系统，容不得半点马虎。
