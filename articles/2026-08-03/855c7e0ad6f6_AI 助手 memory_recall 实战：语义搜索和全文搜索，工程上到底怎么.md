## 背景：memory_recall 不是魔法，是工程选择

在 OpenClaw 这类可组合 Agent 架构里，长期记忆通常通过 MCP（Model Context Protocol）或插件形式外挂。你启动一个会话，Agent 背后调了一个 `/memory/recall` 接口，把和当前对话最相关的历史片段拉回来，塞进提示词里。这个过程的逻辑就叫 `memory_recall`。

但它有两个主流实现方向：**语义搜索** 和 **全文搜索**。前者靠 embedding 向量，后者靠关键词索引（比如 BM25 或 FTS5）。社区里常见的问题是：大家都说语义搜索高级，是不是直接上向量库就完事了？在实际跑了一段时间的 Agent 项目后，我发现没这么简单。

这篇文章不聊概念，只谈在 OpenClaw + MCP 体系下，自己做 memory service 时，语义搜索和全文搜索的实测差异、踩坑点，以及怎么组合使用才真正工程化。

## 问题：两个方案的真实边界

我们做的是一个面向开发者的本地知识库 Agent，需要从几千条历史对话和文档片段里召回相关内容。最初我们直接上了 OpenAI 的 `text-embedding-3-small`，用 Chroma 存向量，召回效果很好，但跑了三天就发现两个致命问题：

1. **延迟不可控**：单次 recall 从 embedding 计算到向量检索，API 往返 + 遍历索引，P99 延迟超过 800ms，Agent 端经常要等 2-3 秒才能拼出完整提示词。
2. **成本非线性增长**：每段新增记忆都要调一次 embedding API，高频使用时每天几万 tokens 的用量，账单涨得比用户增速还快。

然后我们回退到全文搜索，用 SQLite FTS5 建了一个本地索引，延迟直接压到 5ms 以内，零新增成本。但问题也明显：对口语化表达、同义词、跨语言查询的召回率掉得很厉害。比如用户问“上次那个接口报 500 是怎么处理的”，全文搜“500 错误”可能匹配不到，而语义搜索能捕获到“服务器内部错误”的相关片段。

所以真实对比是这样的：

| 维度 | 语义搜索 (embedding) | 全文搜索 (FTS) |
|------|---------------------|----------------|
| 语义理解 | 强，能跨表达匹配 | 弱，依赖精确或相近词汇 |
| 召回速度 | 慢，API/模型推理 + 向量检索 | 快，毫秒级 |
| 成本 | 持续产生 API 费用或本地 GPU 资源 | 几乎零成本 |
| 可维护性 | 向量维度、模型切换复杂 | 索引文件简单，易调试 |
| 冷启动 | 需要预热或加载模型 | 立即可用 |

## 做法：在 OpenClaw 下搭建双路召回服务

我们最终在 OpenClaw 的 memory MCP server 里实现了一个两阶段召回：**全文粗筛 → 语义精排**。具体步骤：

1. **统一记忆存储格式**  
   所有记忆条目用 SQLite 存两份结构：  
   - `memory_raw` 表：`id, content, metadata, created_at`  
   - `memory_fts` 虚拟表：用 FTS5 对 `content` 建立全文索引（分词器使用 `unicode61`，去掉默认的 porter 词干，保留原词）。  
   向量可以按需异步生成存到另一个表 `memory_emb`，不阻塞写入。

2. **MCP 工具接口设计**  
   在实现 `recall_memory` 工具时，接收参数 `query: str`，内部执行：
   - 第一步：用 FTS5 的 `MATCH` 结合 `bm25()` 排序，取 Top-50 候选（按相关性分数），耗时 <5ms。
   - 第二步：对这 50 条候选，调用本地的轻量 embedding 模型（比如 `all-MiniLM-L6-v2`，通过 ONNX 加速），计算与 query 的余弦相似度，选 Top-5 返回。
   
   如果系统检测到 query 是明确的关键词式提问（比如含文件名、错误码），甚至可以跳过第二步，直接返回全文结果。

3. **接入 OpenClaw Agent**  
   在 OpenClaw 配置文件里声明这个 MCP server，Agent 调用时无需关心内部是语义还是全文，只看到标准的 tool schema。我们使用了 session 级别的缓存，同一 query 在短时间内不重复计算 embedding。

## 踩坑点

- **分词器地狱**  
  SQLite FTS5 默认的 `porter` 词干对中文完全无效，对英文也会过度匹配（`running` -> `run`）。必须重建 tokenizer 或者用 ICU 扩展。对于中文，简单的单字分词（`unicode61` 下直接索引字符 n-gram）反而比用结巴分词更适合短文本召回，因为不会产生歧义切词。

- **本地 embedding 模型的资源陷阱**  
  用 `all-MiniLM-L6-v2` 时，CPU 推理一次 50 条文本需要约 200-300ms，虽然比 API 快，但并发上去了内存占用会飙升。我们踩过的坑是：首次加载模型需要 400MB 内存，而且在 Docker 限制 512MB 的容器里直接 OOM。最终改用 `BGE-small-en` 做 ONNX 量化，内存控制在 200MB 以内，延迟降到 50ms/50条。

- **记忆长度截断导致语义丢失**  
  全文索引可以索引很长的文本，但 embedding 模型通常有 max_seq_length（比如 512 token）。如果记忆片段超长，直接截断会丢失后半段语义。我们的做法是在写入时就把长记忆按语义边界（双换行）切块，每块独立建索引，召回时把同源块的分数做 max-pooling。

## 可复用建议

1. **先上 FTS，再补语义**  
   全文搜索是兜底，零成本、低延迟，能解决 60% 的场景。等确认 Agent 的 QA 质量和成本瓶颈后，再加精排。

2. **把语义搜索当成 reranker，而不是 retriever**  
   在工程上，向量库的全量检索在万级数据量以上就开始吃力，而 FTS 做粗筛可以轻松扩展到百万级。两阶段架构让语义模型只处理小量候选，延迟和成本都可控。

3. **为记忆加时间衰减权重**  
   无论是全文还是语义的分数，最后都乘以一个时间衰减因子（比如 `1/(1+log(days))`），让近期更相关。我们在 FTS 的 bm25 分数基础上直接加权，效果更贴合对话场景。

4. **监控 recall 的命中率和空响应率**  
   在 MCP server 里埋点，记录每次 recall 返回的条目数和用户最终是否引用了这些记忆。如果空响率 >20%，大概率是索引策略有问题。

## 总结

memory_recall 没有“最好”，只有最合适的组合。语义搜索擅长理解，全文搜索擅长精确和效率。在 OpenClaw 的 Agent 实践中，用“全文粗筛 + 语义精排”的两阶段模式，能在成本、延迟、准确性之间找到工程上的平衡点。关键是不要一上来就追求纯向量的“高级感”，而是根据实际数据量和用户行为逐步演进。你的 memory 模块是给 Agent 用的，不是给自己炫技的。
