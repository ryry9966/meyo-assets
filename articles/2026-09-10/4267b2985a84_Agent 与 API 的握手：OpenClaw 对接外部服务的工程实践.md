## 背景

OpenClaw 这类 Agent 的价值不在于对话本身，而在于能代替人操作真实系统：查工单、发通知、调内部接口。Agent 要"动手"，就必须和外部 API 握手。这条链路上，模型只负责决策，真正的脏活——认证、超时、重试、幂等——全部落在工具层。

## 问题

早期我们对接外部服务的方式很随意：每个服务写一段胶水代码，认证散落各处，有的没设超时，有的报错直接抛异常。结果模型经常"用错工具"——不是它笨，而是工具描述不清、错误信息不可读。接了三个服务后，问题集中爆发：

- 模型传参类型错误，下游接口一律 400；
- 超时重试导致重复下单；
- 返回结果太大，直接把上下文撑爆。

## 做法

后来我们收敛成一条标准链路，分五步：

1. **能力盘点**：先区分读写。读操作天然幂等，可放心重试；写操作必须设计幂等键，或明确标注"不可重试"。
2. **用 MCP server 封装**：每个外部服务包一层 MCP server（或等价的插件工具），统一暴露 JSON Schema。模型只看得到 schema 和描述，看不到实现。
3. **描述即接口**：工具描述是写给模型看的，不是写给人看的。参数含义、单位、必填可选、典型取值，都要写进 description。这一步花的时间最值。
4. **认证与配置隔离**：密钥只从环境变量或配置文件注入，绝不进入对话和日志；给 Agent 用最小权限的 scoped token。
5. **超时、重试与错误回传**：每次调用显式设超时；429/5xx 指数退避重试；失败时返回结构化错误（错误码 + 人话原因 + 下一步建议），让模型能自我修正而不是瞎猜。

## 踩坑点

- **Schema 太松**：参数全用 string，模型什么都往里塞。类型收紧后错误率立刻下降。
- **大结果直接回传**：列表接口一次返回几百条记录。工具层必须做截断/分页/摘要，只回传模型需要的字段。
- **忽略幂等**：Agent 超时后自动重试，结果创建了两个一样的资源。写操作加幂等键是底线。
- **同步跑长任务**：一个部署任务跑十分钟，Agent 干等。改成异步任务 + 轮询工具：先拿 job id，再查状态。
- **工具一多就乱**：超过十几个工具后，模型选择明显变差。按场景分组、按需挂载，比全量注册有效得多。

## 可复用建议

给每个工具封装定一条硬性 checklist：

- 显式超时（读写可以不同）
- 429/5xx 退避重试，写操作带幂等键
- 结构化错误：code + message + hint
- 输出截断，只回传必要字段
- 密钥仅来自环境/配置，日志脱敏
- 每次调用留审计记录（谁、何时、调了什么、结果如何）

按这个模板接一个新服务，半天内可以跑通，且行为可预期。

## 总结

Agent 与 API 的握手，本质是把"不可靠的自然语言决策"接到"可靠的网络调用"上。模型侧的功夫花在描述和错误设计上，工程侧的功夫花在超时、幂等和观测上。两者对齐之后，对接外部服务不再是碰运气，而是一条可复制的流水线。OpenClaw 的插件与 MCP 机制提供了统一的挂载点，剩下的纪律，靠 checklist 守住。
