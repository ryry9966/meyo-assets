## 背景

我们团队的信息源很散：Git 提交、CI 流水线结果、服务错误日志、告警推送。每天的"日报"以前靠人肉拼凑——写的人痛苦，看的人更痛苦：格式不统一、重点靠猜、经常漏掉真正的故障。

这个帖记录我们用 OpenClaw 搭的一条日报流水线：定时触发 → 采集 → 清洗 → LLM 结构化 → 渲染 → 推送。跑了一个多月，基本稳定。

## 问题

最直觉的做法是"把日志直接丢给 Agent 让它写日报"，实际试过，有三个硬伤：

1. 原始日志量太大，token 成本高，且关键低频事件会被海量 INFO 级噪音淹没；
2. LLM 输出格式不稳定，下游解析经常挂；
3. 流水线本身会静默失败，某天没收到日报没人发现，等察觉已经隔了两天。

## 做法

核心原则：**确定性的活交给代码，LLM 只做分类和摘要**。

1. **采集层**：cron 触发一个 skill 脚本，按"昨日 09:00–今日 09:00"窗口拉取 git log、CI API、错误日志。所有时间先归一到 UTC+8 再比较。
2. **清洗层**（纯代码）：过滤 health check 和 DEBUG 级别；同类错误按"错误指纹"聚合计数；单条截断到 500 字符。清洗后数据量通常降到原始的 3–5%。
3. **结构化层**（LLM）：清洗后的事件按固定 JSON Schema 交给模型，字段包括：类型（故障/发布/变更/指标）、影响模块、严重级别、一句话描述、原始日志行引用。schema 校验失败重试一次，再失败就标记 `degraded`，而不是让模型瞎填。
4. **渲染层**（纯代码）：JSON → Markdown 模板，段落固定：昨日概览、故障与处理、发布与变更、需关注事项。结构化数据先落 JSON 存档，日报只是它的渲染结果。
5. **推送层**：webhook 发群，同时按日期 key 写入仓库，天然幂等——同一天重跑是覆盖，不是堆两份。

## 踩坑点

- **时区**：服务器是 UTC，日志时间戳里混着本地时间，第一版日报窗口直接错位。必须在采集入口统一归一化，别指望后面补救。
- **LLM 幻觉**：早期模型会"补全"根本没有的处理措施。加了两条约束：每个事件必须携带原始日志引用；描述只能改写原文，不能新增事实。人工抽查几天才敢放开。
- **静默失败**：某次 API token 过期，日报停发两天没人察觉。现在流水线无论成败都发一条心跳，失败消息里带阶段名，五分钟内就能定位。
- **输出漂移**：模型偶尔多给字段或改键名，渲染就挂。schema 校验加 `additionalProperties: false` 基本解决。

## 可复用建议

- 先做 `--dry-run` 模式手动触发跑一周，人肉对比效果，再开定时任务。
- JSON 存档与渲染分离，之后加周报、月报只是换模板的事。
- 日报段落结构保持稳定，读者才会形成"先看故障段"的阅读习惯。
- 把流水线自身的运行日志也落盘，排障时省一半时间。

## 总结

这条流水线没有黑科技，价值在于把"写日报"从一个依赖自觉的开放任务，变成一条可观测、可重跑、失败会喊话的确定流程。LLM 用在刀刃上（分类与摘要），其余全部交给代码——这套分工方式，我们后来接其他自动化任务时也在反复复用。
