# 自动化日报生成：从原始日志到结构化报告的流水线

## 背景

团队每天要写日报，大部分人时间花在翻日志、拼数字上，而不是判断上。我们用 OpenClaw 搭了一条流水线，把服务日志、部署记录、告警摘要自动聚合成结构化日报，人只负责最后的审核和补充。这篇记录一下设计取舍和踩过的坑。

## 问题

原始数据有三个特点：**分散**（git 提交、服务日志、工单系统、监控告警各在一处）、**噪声大**（重复心跳、DEBUG 输出）、**口径不一**（时间戳格式和时区各不相同）。直接把原始日志丢给模型总结会遇到两个致命问题：超出上下文长度，以及模型编造数字。

## 做法

流水线分五段，每段职责单一：

1. **先定 Schema，再写代码**。日报的每个字段（变更清单、事故摘要、关键指标、阻塞项）先用 JSON Schema 固化，这是整条流水线的合同。
2. **采集层**：三个定时任务分别拉取昨日 git log、日志切片、告警列表，各自输出中间 JSON 落盘。对接工单系统走 MCP 工具，采集器只取数、不做理解。
3. **预处理层**：纯脚本完成去重、过滤 DEBUG 行、统一时区到 UTC+8、按服务聚合错误计数。关键指标（错误率、请求量、P99）由脚本计算，不经模型之手。
4. **生成层**：OpenClaw Agent 拿到预处理后的紧凑摘要（通常 2-3k token），只做两件事：合并同类告警的归因、为指标变化写一句叙述。输出强制走结构化模式，temperature 压到 0.2。
5. **校验与投递**：Schema 校验失败则重跑一次生成，仍失败就降级投递"原始摘要版"并在报告头部标注降级原因。产物同时推群 webhook 和归档目录。

## 踩坑点

- **不要让模型算数**。第一版让 Agent 直接读日志总结错误次数，数字经常对不上。改成脚本算数、模型只做叙述后，可信度问题基本消失。
- **静默失败最伤信任**。流水线挂了没人发现，第二天大家看到的是前一天的旧报告。加了失败告警和产物时间戳检查才稳住。
- **时区坑**。各数据源时区不一致导致"昨日"边界漂移，有天漏掉了傍晚的发布记录。边界统一收敛到采集层处理。
- **敏感信息**。日志里有 token 和内网地址，脱敏必须写在采集器里，不能指望人记得。
- **Schema 演进**。加字段容易，删字段要留过渡期，下游（包括人）都按合同读。

## 可复用建议

- 把"日报"抽象成 **Schema + 数据源列表 + 生成提示词** 三件套，周报、值班报告只是换配置。
- 预留一组 golden case 做回归：固定输入，校验输出字段和关键数字，改提示词后跑一遍再上线。
- 每个环节产物落盘，出问题能从中间节点重放，不必全链路重跑。

## 总结

这条流水线的核心不是"让 AI 写日报"，而是把确定性的事（取数、算数、校验）交给脚本，把归纳性的事（归因、合并叙述）交给模型，中间用 Schema 钉住。上线两个月，日报从人均 30 分钟降到 5 分钟审核，更重要的是数字不再需要人工核对。建议从单数据源、最小 Schema 起步，跑稳了再扩。
