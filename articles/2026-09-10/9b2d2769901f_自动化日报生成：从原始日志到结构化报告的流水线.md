## 背景

团队每天要在群里发一封服务日报：核心接口的请求量、错误率、慢查询、异常摘要。过去由值班同学手动翻日志、复制数据、写结论，坚持两周后问题就暴露了：漏发、数字抄错、格式漂移。于是我们用 OpenClaw 搭了一条自动流水线，跑了两个多月，日报再没断过。

## 问题

把原始日志直接丢给大模型总结行不通，有三个硬伤：

1. **量太大**：一天几百万行日志，远超上下文窗口，硬塞必然丢信息；
2. **不可靠**：LLM 算数不精确，让它从日志里数请求量，结果每天都"差一点"；
3. **不可控**：输出格式漂移，今天表格、明天散文，下游没法消费。

因此核心设计原则是：**确定性的部分交给脚本，叙述性的部分才交给模型**。

## 做法

流水线分四步，由 OpenClaw 的定时任务驱动（cron 触发，固定配置的 Agent 会话）：

**第一步：采集与过滤（脚本）。** Python 脚本按时间窗口拉取前一天日志，先按关键字和状态码过滤，只保留错误、慢查询、告警三类，其余丢弃，输出中间 JSON。

**第二步：指标计算（脚本）。** 请求量、P95 延迟、错误率、Top 5 异常类型及次数全部由脚本算定，模型无权修改任何数字。

**第三步：摘要生成（Agent + MCP 工具）。** 把过滤后的异常明细和算好的指标交给 Agent，通过 MCP 工具读取同环比数据做对比。Prompt 明确要求：只解释数字、归纳原因、指出需人工关注的点，禁止编造数值。输出强制走 JSON Schema 校验，不合规重试一次。

**第四步：渲染与投递（脚本）。** 校验通过后用固定模板渲染成 Markdown 和群消息卡片发送，并归档到对象存储。

## 踩坑点

- **时区错位**：日志源是 UTC，人看的是北京时间，第一批日报时间窗口偏了 8 小时，指标"全线偏低"。现在统一在采集层转换时区。
- **LLM 幻觉数字**：最初直接让模型总结原始日志，它"算"出的错误率与脚本差 2 个百分点。彻底砍掉这条路径后问题消失。
- **Schema 校验静默失败**：一次模板改动导致渲染脚本拿到 null 字段没报错，发出去的日报缺了错误率。之后加了投递前的完整性断言，缺字段直接告警不发。
- **采集超时卡死**：日志服务偶发变慢，脚本没设超时导致整条流水线挂起。现在每步独立超时加重试，重试仍失败则降级发"数据不完整"的占位日报。

## 可复用建议

1. **中间产物落盘**：每步输出存成带日期的文件，方便回溯重跑，也方便定位是哪一步坏了；
2. **Schema 先行**：先定日报的 JSON Schema，各环节围绕它开发，格式漂移基本绝迹；
3. **干跑模式**：流水线支持 `--dry-run`，只生成不投递，改 Prompt 或模板时先干跑对比；
4. **数字只能来自脚本**：这条红线值得写进任何 Agent 流水线的设计文档。

## 总结

这条流水线的本质不是"用 AI 写日报"，而是把日报拆成确定性与非确定性两部分：脚本负责事实，Agent 负责解读。OpenClaw 在其中承担编排与摘要环节，而不是替你算数。上线以来最大的收益不是省下 20 分钟人工，而是日报从此有了稳定格式和完整数据，下游的周报与复盘可以直接复用中间产物。
