## 背景

单 agent 跑长任务的痛点大家都遇到过：上下文越滚越大，工具调用串行排队，中间某一步卡住，整条链路跟着停。我们的典型场景是批量任务——比如一次性给 30 个模块补测试、对 5 个候选方案做独立调研、并行修一批互不相关的 lint 报错。这类任务天然可拆，但单 agent 只能一个一个啃。

OpenClaw 的 agent 运行时支持在任务中 spawn subagent，每个 subagent 有独立上下文和工具集，主 agent 负责拆解、分发、汇总。跑了一段时间，记录一些实践。

## 问题

把任务丢给 subagent，并不等于并行化成功。常见的失败模式：

- subagent 拿到的任务描述不完整，产出主 agent 没法用；
- 并发一开，API 限流和 token 消耗同时爆炸；
- 多个 subagent 写同一批文件，互相覆盖；
- 某个 subagent 失败或死循环，主 agent 一直干等。

## 做法

我们沉淀出一套比较稳的流程：

1. **主 agent 只做拆解与汇总**，明确约束它不亲自执行具体操作，只产出任务清单。
2. **任务书自包含**。每个 subagent 的 prompt 是一份"单页任务书"：目标、输入路径、可用工具、输出格式、边界（不许改哪些文件）。不依赖父对话的任何上下文。
3. **固定输出契约**。要求 subagent 按统一结构返回（改动文件列表、结论、遗留问题），主 agent 才能可靠聚合。
4. **并发度控制在 3–5**。再高就撞限流，出错后排查成本也陡增。做成配置项，不写死。
5. **失败降级**。单个 subagent 超时或报错，标记该子任务为 failed 并继续推进，最后统一汇报，不允许一个失败阻塞全局。
6. **禁止递归 spawn**。subagent 内不允许再开 subagent，从机制上杜绝任务树失控。

## 踩坑点

- **上下文不共享是特性不是 bug**。早期我们默认 subagent"应该知道"背景，结果它把已废弃的模块也重构了。背景必须写进任务书，别靠猜。
- **文件级加锁**。按路径划分领地，或在调度层做互斥，否则并发写冲突极难排查。
- **成本要预估**。一次 5 并发 × 10 分钟的编排，消耗可能抵平时一天。正式跑之前先 2 并发试运行。
- **聚合时别过度摘要**。主 agent 汇总时把 subagent 的关键细节压没了，下游拿着结论没法验证。聚合输出里保留对原始结论的引用。

## 可复用建议

- 判断标准很简单：子任务互相独立就并行，有依赖就串行。别为了并行而并行。
- 把"任务书模板"沉淀成项目内的固定文件，新人改参数就能用。
- 全程留 trace：每个 subagent 的输入、输出、耗时、token 数落盘，出问题能回放。
- 先串行跑通整个流程，再打开并行。串行都跑不通的编排，并行只会错得更快。

## 总结

subagent 编排不是魔法，本质是分布式任务调度的工程问题：任务拆得干净、边界写得清楚、失败路径想得周全，并行才有收益。我们现在的原则是——能用串行解决的不用并行，能 3 并发解决的不开 10 并发，控制爆炸半径永远优先于追求速度。欢迎在社区里交换各自的编排配置和失败案例。
