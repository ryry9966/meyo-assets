## 背景

OpenClaw 里跑一个像样的 agent，一次任务远不止一次 LLM 调用：意图识别、MCP 工具参数生成、长上下文摘要、多步规划、最终答复撰写。全走 GPT，账单和 P95 延迟都难看，私有数据还要出域；全走本地 7B/14B，复杂规划和严格结构化输出又明显掉链子。多模型路由要解决的不是"选哪个模型"，而是"流水线里每一步该花多少钱、买什么能力"。

## 问题

两种常见的一刀切：

1. **全云端**：成本不可控，延迟叠加，敏感中间结果随调随出。
2. **全本地**：function call 格式漂移、长文截断、规划能力不足，agent 表现为"莫名变笨"，而且失败往往是静默的。

根因是：同一条流水线里，不同步骤对能力、延迟、隐私的要求差异极大，但很多人在配置层面只用一个全局 model 字段。

## 做法

**1. 先给任务分型。** 把 agent 内的调用拆成五类，分别标注对上下文长度、schema 严格性、延迟、隐私的要求：意图分类、结构化工具调用、长文摘要、代码/规划、答复撰写。

**2. 按角色绑定模型，建路由表。** 在 OpenClaw 的节点级配置里下放模型选择：

- 意图分类、简单改写：本地小模型（Ollama/vLLM 起一个就够）
- 工具参数生成：本地微调过调用格式的模型，失败升级云端
- 多步规划、代码生成：GPT 类云端模型
- 摘要：上下文超 8k 才走云端，否则本地

**3. 用校验器驱动升级，不要让模型自评。** 本地输出先过 JSON Schema / 正则硬校验，失败后升级云端重试一次，并记录升级原因。模型自己说"我有信心"不可信。

**4. 加观测。** 每条路由记录 token 消耗、首 token 延迟、升级率、失败率。没有这四个数，路由策略永远在拍脑袋。

## 踩坑点

- **格式漂移是静默失败大户**：本地模型的 function call 输出和 OpenAI 格式不完全兼容，枚举值错一个照样"成功返回"，必须做 schema 硬校验。
- **级联要封顶**：本地失败→云端→再失败→重试，不设最大尝试次数会打出意外账单。
- **上下文错配不报错**：8k 窗口的本地模型接 20k 摘要任务，截断后质量崩了但日志一片绿。
- **"本地=快"不成立**：弱 GPU 上首 token 延迟可能比云 API 还高，先压测再路由。
- **隐私不是二元的**：简单分类走云端同样送出中间结果，敏感字段应在路由前脱敏。

## 可复用建议

- 维护一张三列路由表：**任务类型 → 默认模型 → 升级条件**，进版本库，改路由等于改代码、走 review。
- 升级触发条件用"结构校验失败 + 关键字段缺失"，别用自报置信度。
- 每周看一次升级率：某条路由持续高于 30%，说明是本地模型选型错了，换模型而不是死调 prompt。
- 同一份 prompt 不要无脑跨模型复用，本地和云端各维护一份模板差异。

## 总结

多模型路由不是省钱技巧，而是把"每一步需要什么能力"显式化的工程手段。原则就三条：按任务分型、按校验结果升级、按数据迭代。在 OpenClaw 里把模型选择从全局配置下沉到节点级，这一步做完，成本和稳定性通常是同时改善的。
