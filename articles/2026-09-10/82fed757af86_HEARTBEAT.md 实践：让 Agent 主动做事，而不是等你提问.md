## 背景

多数人对 Agent 的使用是「问答式」：你提问，它回答，会话结束就静止。OpenClaw 内置了一个方向相反的机制——心跳（heartbeat）：守护进程每隔一段时间（默认约 30 分钟）自动唤醒一次 agent，让它读取工作区里的 `HEARTBEAT.md`，自行判断这一轮有没有值得做的事。这个文件，本质上是你给 agent 的常驻任务清单。

## 问题

纯被动模式有几个真实痛点：

- 周期性事项全靠人记：每日摘要、检查某个仓库有没有新 issue、盯一下磁盘余量——你不想起，它就不动。
- 系统 cron 只能定时执行固定命令，没有上下文判断；而 agent 恰好擅长「看情况决定做不做」。
- 结果是：agent 明明有工具、有记忆、有权限，却只在你想起来时才干活。

## 做法

1. 在 agent 工作区根目录新建 `HEARTBEAT.md`，用清单式写法，分三类维护：
   - **Checks**：每轮心跳都做的轻量检查，比如读一次日志尾部、看某个状态文件是否更新；
   - **Tasks**：满足条件才执行的动作，写清判断标准和具体命令；
   - **Reminders**：低频提醒，如「每周五下午汇总本周仓库改动」。
2. 通过 `HEARTBEAT_INTERVAL_MS` 或配置项调整心跳周期，默认 30 分钟对多数场景够用。
3. 约定空转回复：无事可做时让 agent 只回 `HEARTBEAT_OK`，不往聊天里灌水。
4. 条目写成可执行的一句话，带路径和命令，例如：「若 `~/logs/error.log` 当日新增超过 200 行，摘要前 10 条发我」。

## 踩坑点

- **写成散文**。心跳文件一旦是大段描述，agent 要么无从下手，要么自由发挥。逐条列、动词开头、给出判定条件。
- **条目太多**。`HEARTBEAT.md` 每轮都会进上下文，十几个条目就是持续的 token 开销。细节放别的文件，主清单只留指针。
- **没约定空转回复**。不处理的话，它会每半小时礼貌汇报一次「暂无事项」，很快你就会忍不住关掉整个心跳。
- **一上来就加副作用**。发消息、改文件这类写操作先别写，跑几天只读检查，确认它的判断质量可靠后再逐步放开。
- **拿心跳跑重活**。心跳轮次应该快进快出；确定性的定时重任务交给 cron 或系统定时器，心跳只负责「需要判断」的部分。

## 可复用建议

- 把 `HEARTBEAT.md` 当轻量版 runbook 维护：进版本库、改动写清 commit message、定期清理失效条目。
- 心跳与 cron 是互补关系：确定性时间点用 cron，模糊触发（「有变化就告诉我」）用心跳。
- 让 agent 把每轮心跳的实际动作追加写入一个日志文件，事后审计它「自作主张」了什么，也方便调参。

## 总结

HEARTBEAT.md 是把 agent 从「问答工具」升级为「值班助手」的最低成本方案：一个 Markdown 文件加一个时间间隔。它的价值其实不在自动化本身，而在于你被迫把「希望它主动做什么」写成清晰的规则——这个整理过程往往比机制本身更值钱。建议从两三条只读检查起步，跑稳了再扩展。
