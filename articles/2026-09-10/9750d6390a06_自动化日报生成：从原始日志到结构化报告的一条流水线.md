## 背景

团队里"日报"这件事通常有两种下场：要么靠人肉复制粘贴，坚持三周后退化成周报；要么直接上重型 BI 系统，成本远超收益。我的场景介于两者之间：服务端散落着应用日志、CI 记录和告警事件，需要每天早上九点前产出一份包含"做了什么、坏了什么、明天注意什么"的简报。OpenClaw 自带 cron 触发、Agent 编排和 MCP 工具接入，正好可以把这条链路串起来。

## 问题

直接让 Agent"读日志写日报"基本会失败，原因有三：

1. 原始日志量大且非结构化，上下文撑不住，关键信息被截断；
2. 模型对缺失数据会脑补，日报里出现没发生过的"事故"；
3. 没有中间产物，失败后无法定位是采集、解析还是生成哪个环节的锅。

所以核心设计原则是：**先结构化，再总结**。LLM 只做最后一步，且只允许基于结构化输入输出。

## 做法

流水线分四步，每步落盘中间产物：

1. **采集**：cron 任务每天 08:30 拉取过去 24 小时的日志（应用日志 + CI 接口 + 告警 webhook 存档），统一写入 `logs/raw/YYYY-MM-DD/`。
2. **结构化**：写一个独立脚本（不经过 LLM）做正则/JSON 解析，输出 `daily_events.json`，schema 固定：`{deploy_count, error_summary[], slow_requests[], notable_commits[]}`。字段缺失就写 `null`，绝不留空字符串。
3. **生成**：OpenClaw cron 触发 Agent，通过 MCP 的文件系统工具读取 `daily_events.json`，按固定模板填充，生成三段式日报（概况 / 异常 / 待办）。prompt 中明确约束：所有数字必须来自输入 JSON，禁止推测。
4. **投递**：写入 Markdown 文件并推送通知。投递失败走重试，三次失败后落一条告警，不静默吞掉。

关键点：第 2 步是纯代码，可单测；第 3 步是 LLM，只做语言组织，不做事实生产。职责切开后，出问题先看中间 JSON，一分钟内能定位在哪一层。

## 踩坑点

- **时区**：容器内是 UTC，"昨天"的边界差了 8 小时，第一周日报全是错的。日期必须在采集脚本里用本地时区显式计算。
- **LLM 编数字**：早期把原始日志直接塞给模型，它会把 error 计数"估算"成整数。改成模板填空后彻底消失——结构化数据用占位符注入，不要让模型复述统计结果。
- **静默失败**：采集脚本一次权限报错，日报照常发出，内容是"今日无异常"。之后加了断言：输入文件不存在或字段缺失超阈值时直接不发报告，改为发故障通知。
- **编码混杂**：日志同时存在 GBK 和 UTF-8，解析脚本统一先探测编码再读，别假设 utf-8。

## 可复用建议

- schema 先行：先定 JSON schema，再写解析器和 prompt，Agent 输出永远跟着 schema 走。
- 中间产物落盘：每个阶段一个目录，失败可重放，也方便 diff 两天的数据。
- 确定性部分用代码，模糊部分才用模型；能模板填空的不要让 LLM 生成。
- 给流水线加"不健康即不发"的熔断——宁可不日报，不要发错日报。

## 总结

这套流水线上线一个月，日报从未缺勤，也没再出现虚构内容。工程量不大：一个采集脚本、一个解析脚本、一份 Agent prompt、一条 cron。真正的收益不是省了写日报的十分钟，而是把"发生了什么"从主观记忆变成了可审计的数据链路。对已在用 OpenClaw 做自动化的同学，建议从最痛的一类日志入手先跑通单条链路，再横向扩展数据源。
