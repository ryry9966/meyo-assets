## 背景

OpenClaw 的 Agent 工作流里，模型调用往往不止一种。一条典型链路是：意图识别 → 工具编排（MCP 调用）→ 内容生成 → 结构化落库。每一步对模型能力的要求差异很大，但很多项目默认全程走 GPT，或者图省钱全程走本地 7B/14B，结果要么成本和延迟失控，要么复杂步骤频繁翻车。

我们团队在一条「数据清洗 + 报告生成」的自动化流水线里做了约两个月的路由改造，云端调用占比从 100% 降到 35%，端到端 P95 延迟下降约 40%。这篇帖子整理一下判断标准和落地方法。

## 问题：三种常见的错误姿势

1. **全走云端**：简单的格式转换、字段抽取也调 GPT，单次便宜，量大后账单可观，且高峰期限流会卡住整条流水线。
2. **全走本地**：本地模型做结构化抽取没问题，但长上下文工具编排、多步推理的质量差距明显，失败重试反而更贵。
3. **写死映射**：在业务代码里硬编码「步骤 A 用模型 X」，换模型要改一堆地方，也没有降级路径。

## 做法：按任务特征分流 + 失败升级链

**第一步，给任务分类**，按三个维度打标：是否涉及敏感数据（必须走本地）、上下文长度与推理复杂度、输出是否强结构化（纯 JSON 抽取对能力要求低）。

**第二步，配置模型池**：云端走 GPT-4o 级别模型，本地用 vLLM 部署 Qwen2.5-14B-Instruct，通过 OpenClaw 的 provider 配置统一暴露。

**第三步，写路由规则**，规则优先、小模型兜底：

- 敏感/内网数据 → 仅本地
- 强结构化抽取、格式转换、简单摘要 → 本地
- 工具编排超过 3 步、长上下文对齐、代码生成 → 云端
- 规则判不了的，用一次便宜的分流调用兜底

**第四步，加升级链**：本地先行，输出过不了校验（JSON schema、关键词命中率）就升级到 GPT 重试一次，并记录升级原因。

**第五步，埋点观测**：每次调用记录 route、模型、token 数、延迟、是否升级。跑两周看数据再调阈值，不要凭感觉。

## 踩坑点

- **路由模型自己会错**。小模型分流时会把复杂任务判成简单任务，本地模型输出「错误但不报错」的结果——静默失败最难受。校验规则一定要硬，不能只靠模型自评。
- **本地模型输出格式漂移**。同一个 prompt，Qwen 偶尔在 JSON 里多塞解释文字，下游解析直接挂。解法：system prompt 锁格式 + 输出前 strip/修复，必要时上 guided decoding。
- **上下文长度不一致**。本地（32K）升级到云端没问题，反向降级时超长上下文被截断，工具调用历史丢失导致行为异常。降级前先做摘要压缩。
- **本地推理冷启动**。vLLM 空闲回收显存后首次请求要十几秒，流水线表现为周期性毛刺。保持常驻或定时预热。

## 可复用建议

- 路由逻辑做成独立的 MCP 工具或插件，业务 prompt 里不要出现模型名，换模型只动配置。
- 准备 50~100 条带标注的真实任务样本，改路由策略前先跑一遍对照，别在生产线直接实验。
- 升级链优于并行双跑：省钱且可解释，并行只在评估期用。
- 每周看一次「升级率」：某类任务持续高于 30%，说明它该直接路由到云端，别硬省。

## 总结

多模型路由的本质是承认「不是所有步骤都值得用最强的模型」。OpenClaw 这类框架的价值在于把 provider、路由、降级都变成可配置的层；工程上的关键是规则先行、校验兜底、数据说话。建议从一个混合链路的最小改造起步，跑两周数据再扩，比一次性设计复杂路由策略靠谱得多。
