## 背景

OpenClaw 的 cron 任务，本质是定时唤醒一个 agent 会话：到点后框架把 instruction 作为输入丢进一个全新会话，agent 跑完，输出走消息通道或落盘，全程没有人在场。

这决定了它和聊天 prompt 是两种文体。聊天 prompt 背后有个会追问、会纠错的人；cron instruction 背后没有人，写不清楚，错误只会静默累积。

## 问题

实践中写得不好的 cron 任务，通常表现为三种症状：

1. **空转噪音**：“每天看看 RSS 有没有有趣的东西”。agent 每次都能“找到”有趣的东西，于是每天准时推一堆内容，两周后你关掉这个任务。
2. **重复执行**：没有记录处理进度，每次运行都从头处理，重复推送、重复写文件。
3. **静默失败**：数据源挂了、MCP 工具没配好，agent 不知道该报给谁，任务跑了但什么都没发生，你还以为一切正常。

共同根因：instruction 只定义了“做什么”，没定义“不做什么”和“失败了怎么办”。

## 做法

我现在的写法，是把 cron instruction 当成一份交接文档，固定分六段：

1. **任务与输入**：一句话说清任务是什么，数据从哪来，具体到文件路径、URL 或 MCP 工具名。
2. **步骤**：线性、可枚举，避免“探索式”措辞，每步用到的工具写死。
3. **成功输出契约**：格式、长度、发到哪。例如“每条一行，含标题、一句话说明、链接，总数不超过 10 行”。
4. **空转分支**：写死一句固定短语（如“今日无更新”），方便肉眼识别，也方便下游过滤。
5. **失败分支**：源不可用或工具报错时输出什么，而不是沉默。
6. **状态与幂等**：每次运行前读一个 cursor 文件（记录上次处理到的时间戳或 ID），处理完更新它。这是消灭重复执行最有效的一招。

骨架示例：

```
任务：每日 09:00 汇总 <数据源> 新增条目
步骤：
1. 读取 /path/cursor 记录的上次位置
2. 用 <MCP 工具> 拉取晚于该位置的条目
3. 摘要：每条一行，含标题、一句话说明、链接
出口：
- 有新条目：发送摘要，并更新 cursor
- 无新条目：仅回复「今日无更新」
- 来源异常：回复「数据源异常：<错误摘要>」，不改 cursor
禁区：不做任何额外写操作，不扩展任务范围
```

## 踩坑点

- **依赖上下文的措辞**。“继续之前的工作”在 cron 会话里一律失效——会话是全新的，instruction 就是全部输入。
- **相对时间歧义**。“最近一天”不如“先取系统当前时间，再取前 24 小时”。
- **把人设塞进 instruction**。长篇 persona 会稀释任务重点，人设放系统提示词，cron instruction 只谈任务。
- **没有禁区**。定时任务默认只读；需要写文件、发消息的，在 instruction 里显式列出白名单。
- **空转分支缺失**。哪怕只写“无事可做时回复 no-op”，也远好于让 agent 自己决定——它通常会选择找点事做。

## 可复用建议

- 一个任务一句话说清目标；超过三步就拆成多个 cron。
- 成功、空转、失败三个出口都写死输出，宁可啰嗦。
- 用 cursor 管增量，用固定短语标空转，方便后续做统计和告警。
- 上线前手动触发跑两三天，对照契约检查输出，再放手无人值守。

## 总结

cron instruction 是写给一位无人值守同事的交接文档，不是聊天消息。判断写得好不好，看三点：**可预测**（同样输入产出同样格式的输出）、**可静默**（没有新东西时安静）、**可恢复**（失败后下次能接上）。把这三点写进 instruction，定时任务才能长期跑下去。
