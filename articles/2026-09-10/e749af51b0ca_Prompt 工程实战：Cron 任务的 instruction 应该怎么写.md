## 背景

OpenClaw 的 cron 任务本质是"无人值守的定时对话"：到点唤醒 agent，执行一段 instruction，然后把结果投递到指定渠道。很多人的第一版定时任务都写在聊天习惯里——交互场景下模型可以追问、可以借助上下文补全，定时场景里这些全都没有。我维护了几个每天跑的定时任务（仓库巡检、日报汇总、数据核对），踩过一轮坑之后，总结出一套比较稳的写法。

## 问题：交互 prompt 的假设在 cron 里全部失效

典型失败形态有这么几种：

- 写"帮我总结一下昨天的动态"，agent 不知道"昨天"的边界、不知道从哪取数，于是自由发挥；
- instruction 留了追问空间，但定时触发时没人回答，agent 要么空转，要么自己编个答案；
- 没写投递目标，结果躺在会话里，谁都没看到；
- 数据源挂了，agent 不报错，而是编一份"看起来正常"的内容。

一句话概括差异：**交互 prompt 是对话，cron instruction 是程序规格说明。**

## 做法

我的 instruction 固定分六段，可以直接当模板：

1. **目标**：一句话说清做什么、给谁看；
2. **输入来源**：明确用哪个工具/MCP/命令取数，写清路径与参数，不让 agent 猜；
3. **步骤**：3–5 条有序动作，每步只做一件事；
4. **输出契约**：格式、条数、长度、语言、是否带链接；
5. **投递方式**：明确发到哪个渠道/会话，否则结果无人接收；
6. **异常处理**：取不到数据时"跳过本次并记录原因"，明令禁止编造兜底。

一个日报任务的骨架示例：

```
目标：每天 08:30 汇总 XX 仓库昨日提交，投递到 #dev-daily。
输入：用 git log 取昨天 00:00–23:59（本地时区）的提交。
步骤：1) 拉取提交列表；2) 按 feature/fix 分组；3) 每组提炼要点。
输出：3–6 条要点，每条一行；无提交时输出"昨日无提交"。
投递：发送到 #dev-daily，不 @ 任何人。
异常：git 失败时只报告失败原因，不得推测提交内容。
```

## 踩坑点

- **留追问空间**：instruction 里出现"如果你想……也可以……"，在定时场景等于邀请幻觉，全部改成确定性指令。
- **时间边界模糊**："最近的消息"不如"过去 24 小时"，时区一定要写明。
- **没做幂等/去重**：任务重叠或重跑会重复投递。让 agent 把上次运行时间写进工作区文件，下次先读再跑。
- **让 agent 干脚本的活**：取数、格式转换这类确定性工作交给脚本，agent 只负责需要理解力的部分（归纳、判断、异常解释）。
- **任务堆叠**：一个 cron 塞五件事，失败一半还查不出哪一步。拆成多个单一职责任务，各自独立排障。

## 可复用建议

- 把 instruction 当代码管理：进 git、改动走 review、出问题可回滚；
- 上线前手动触发跑 3–5 次，观察输出方差，方差大说明写 得不够确定；
- 留运行日志，每次执行记一条结果摘要，一周后回看能快速发现退化；
- 频率宁低勿高，先每天一次跑稳，再考虑加密。

## 总结

写 cron instruction 的心法：假设执行者是一个能力很强、但完全不了解上下文、且永远不会向你提问的新同事。目标、来源、步骤、格式、投递、异常——六项写全，定时任务才能从"每次执行都是抽卡"变成"可依赖的基础设施"。
