## 背景

OpenClaw 的每一轮对话，都会把工作空间根目录下的 AGENTS.md 注入系统提示。它是唯一一份"必然在场"的上下文。职责划分大致是：SOUL.md 管人格和语气，TOOLS.md 管工具说明，而 AGENTS.md 是操作手册——Agent 该怎么干活、遇到什么情况停下来问、哪些事不许碰。

## 问题

默认状态的 Agent 什么都会一点，但对你的环境一无所知：不知道你用 pnpm 还是 npm，不知道长任务该不该先汇报，不知道哪些目录只读。实践中常见两个极端：要么什么都不写，行为全靠模型默认值；要么把所有规则堆进去，几周后没人记得哪句话还有效，token 成本也水涨船高。

## 做法

**1. 分区明确，每条写成祈使句。** 推荐骨架：环境与机器边界 / 沟通约定 / 工具与命令偏好 / 任务执行流程 / 记忆纪律 / 安全红线。分区不超过六七个。

```markdown
# 环境
- 本机 macOS，shell 为 zsh，包管理统一 pnpm
- ~/projects 只读，写操作仅限 workspace 内

# 沟通
- 中文回复；长任务先回执行计划再动手
- 重试不超过 2 次，仍失败则停下询问

# 记忆
- 结论写 memory/当日.md；AGENTS.md 不记流水
```

**2. 写可执行动作，不写形容词。** "长任务先回一条计划再执行"优于"做事要稳妥"；命令要精确到可直接粘贴。

**3. 一条规则只出现在一个地方。** 稳定规则进 AGENTS.md，人格进 SOUL.md，流水信息进 memory 日记。职责重叠是行为漂移的根源。

**4. 子目录可以嵌套 AGENTS.md。** 离文件越近优先级越高，适合给特定项目覆盖全局规则。

**5. 纳入 git 管理。** 改规则走 commit，能 diff 能回滚，团队共享也方便评审。

## 踩坑点

- **手册写成百科。** 超过 200 行后，模型对中后段指令的遵循度明显下降，建议控制在 100~150 行。
- **多文件互相矛盾。** 表现为今天用 bash、明天非要换 PowerShell，排查半天发现是 SOUL.md 和 AGENTS.md 各写了一版约定。
- **重复引用导致过期。** 写了"详见 TOOLS.md"又把工具用法复述一遍，工具升级后手册先行腐化。
- **塞入敏感信息。** 路径、密钥、内网地址会进入每一轮上下文，手册等于把敏感数据常驻提示词。
- **改完不验证。** 固定准备两三个测试问题，每次改动后跑一遍对比行为，否则你永远不知道这条规则是否真的生效。

## 可复用建议

把 AGENTS.md 当 runbook 维护，而不是文档：每季度裁剪一次，删掉规则时问自己"是约束错了还是写法不对"。新规则先在一次会话内小成本试验，观察生效后再固化。团队共享规则和机器本地规则分开存放，前者进仓库，后者放在手册尾部单独分区，避免同步冲突。

## 总结

AGENTS.md 的价值不在于写了多少，而在于每一轮都被稳定遵守。把它当成给新同事的入职手册：短、可执行、单一事实来源。做到这三点，Agent 的行为就会从"随机发挥"变成"可预期交付"。
