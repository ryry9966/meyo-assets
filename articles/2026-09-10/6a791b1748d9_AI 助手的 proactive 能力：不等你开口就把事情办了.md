## 背景

现阶段大多数 Agent 是被动应答式的：用户发消息，模型响应，会话结束。但在 OpenClaw + MCP 的自动化实践里，真正的价值往往在那些"你还没意识到、它已经处理掉"的事——比如每天早上扫描 CI 失败并汇总根因、监听目录变化自动归档产物、在关键依赖发新版时先跑一轮兼容性验证。这类事不需要对话，只需要在正确的时机被触发。

## 问题

把 reactive Agent 改造成 proactive，工程上有三个难点：

1. **触发从哪来**：没有对话轮次，谁来唤醒 Agent？
2. **时机怎么判**：什么时候该说话，什么时候闭嘴？
3. **动作怎么控**：无人值守运行时，权限边界划在哪？

## 做法

以一个"CI 失败主动汇报"场景为例，我把它拆成四层：

**1. 触发层。** 用 cron / webhook / 文件监听做感知源。比如 Actions 的失败 webhook 打到本地一个轻量 HTTP 服务，收到事件后进入下一步。

**2. 上下文组装层。** 把日志片段、最近 commit、历史同类失败拼成结构化输入。这一步用纯代码完成、不经过 LLM，省 token 且输出稳定。

**3. 决策层。** 先过确定性规则：同一 job 一小时内是否已报过？是不是 flaky test 重试后通过了？再让 Agent 分析根因、生成汇报草稿。**规则在前、模型在后**，是控制成本和噪音的关键。

**4. 执行层。** 按严重度分流：阻断主干的失败立即推送；其余进"每日摘要"，固定时间一次性发。所有动作写本地日志，事后可审计。MCP 工具按 playbook 配最小权限——汇报类任务只给只读工具加消息发送，不开放任何写操作。

## 踩坑点

- **过度触发**。早期每个失败都推，第三天用户就开始无视推送。改成"首报 + 摘要"后，噪音降了大约八成。
- **无人值守的宽权限**。有次给 proactive 任务挂了全量工具，它"好心"尝试自动回滚，幸好跑的是 dry-run。教训：无人值守的工具白名单要比交互式会话更紧。
- **重复动作**。webhook 重试导致同一事件被处理两次。现在每次执行带幂等键（事件 ID + 动作类型），命中即跳过。
- **上下文陈旧**。定时任务没有会话记忆，需要把必要状态（比如"昨天已报过什么"）持久化到本地 store，触发时显式注入。

## 可复用建议

1. 先做"观察 + 通知"，再做"观察 + 行动"。让用户先信任它的判断，再逐步放开执行权。
2. 不可逆操作永远留人工确认位，proactive Agent 只负责"把草稿准备好"。
3. 每类触发源单独限流；日志区分 triggered / skipped / executed 三种状态，方便复盘调阈值。
4. 模型只做它擅长的事：读日志、写摘要、提建议；调度、去重、分流全部交给确定性代码。

## 总结

Proactive 不是让模型"更聪明"，而是把调度、过滤、权限这些工程活做扎实，让模型只在正确的时机被调用。判断一个 proactive 助手是否合格，标准其实很朴素：**它主动找你的次数，是否每次都值得你停下来看一眼。** 达不到，就先回头收紧触发条件，而不是加更多功能。
