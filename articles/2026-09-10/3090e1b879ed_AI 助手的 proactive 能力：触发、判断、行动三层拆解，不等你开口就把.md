## 背景

大多数助手默认是"被动应答"：你问一句，它答一句，不问不动。真正的效率差距在主动执行——任务到期、状态异常、流程卡住时，Agent 自己把事情推进到"只差你点头"的程度。

对 OpenClaw 这类常驻 Agent 来说，做 proactive 的原料其实齐了：常驻进程、cron/定时器、webhook 钩子、MCP 工具调用、插件体系。缺的不是能力，是一套工程化的约束框架。

## 问题

最常见的失败路径：把 LLM 直接挂上定时器，得到一个"定时废话机"——每 5 分钟总结一次日志、推送一堆没人看的消息，token 账单还翻倍。

Proactive 的难点不在"能主动"，而在三个问题：**什么时候触发**、**要不要出手**、**出手到什么程度**。这三层没拆开，做出来的东西要么太吵，要么太险。

## 做法：三层结构

**1. 触发层：事件优先于轮询**

cron 只做兜底，首选 webhook、文件变更监听、MCP 工具返回的状态 diff。每个触发源带降噪字段：去抖窗口、合并窗口、source 标记。

**2. 判断层：两段式过滤**

先用规则（阈值、白名单、状态变化检测）干掉 80% 的噪音，剩下的再交给一个便宜模型做三分类：忽略 / 出草稿 / 直接执行。不要一上来就用大模型做全量判断。

**3. 行动层：分级执行**

默认 propose-only——Agent 只产出草稿和证据（链接、diff、判断原因），等你确认后才落地。只有低风险、幂等、可回滚的动作（打标签、写日志、缓存预热）才开 auto 模式。

最后给 Agent 一个**主动预算**：每天 N 次主动打扰、每天 M token，超了就静默降级为只记录、不推送。

## 踩坑点

- **自触发循环**：Agent 写的文件又触发了自己的 watcher。事件里必须打 source 标记，来自自身的直接吞掉。
- **上下文过期**：定时任务拿着昨天的快照做判断，全错。触发后先拉一次实时状态，再进判断层。
- **通知疲劳**：前三天觉得新鲜，第四天开始全部忽略。宁可漏报，不可滥报，阈值从紧起步。
- **成本失控**：判断层直接调大模型，一次日志风暴能打穿当天预算。规则先行，模型只兜底。
- **权限越界**：proactive 模式下 Agent 在"没人盯着"时行动，工具权限要单独收敛一份最小集，和交互模式的权限区分开。

## 可复用建议

1. 先跑两周 propose-only，统计"建议采纳率"，超过某个值（比如 60%）再逐步放开 auto 动作。
2. 判断逻辑配置化（YAML/JSON），和代码解耦，按场景调阈值不用发版。
3. 每条主动动作留证据链：触发事件、过滤结果、模型理由、最终动作，方便复盘误报。
4. 幂等键必须做：同一事件去重，重试不重复执行。

## 总结

Proactive 不是把 LLM 挂上 cron 就完事，而是触发降噪、分级判断、行动约束三层配合的工程问题。先用便宜的规则和 propose-only 建立信任，再把高风险动作逐步下放——让 Agent 从"你问它答"进化到"它先把事备好，你点头才落地"，这条路比一步到位的全自动靠谱得多。
