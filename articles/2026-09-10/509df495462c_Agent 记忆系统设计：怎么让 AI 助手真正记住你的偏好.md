## 背景

LLM 本身无状态。会话一结束，上下文就清零。用户反复交代"回复要简短""我主用 TypeScript"，下次对话 Agent 还是忘。记忆系统要解决的，就是把跨会话的用户偏好变成可检索、可更新、可删除的持久状态。

## 问题

常见三种做法，各有坑：

- **全量塞 system prompt**：token 成本线性上涨，超窗口直接失效；
- **只靠 RAG 检索历史对话**：噪音大，偏好被日常闲聊淹没；
- **完全不存**：体验最差，但很多人实际就是这个状态。

核心矛盾：记太少没用，记太多检索不准，还会记错、记旧。

## 做法：三层记忆 + 读写策略

**1. 分层存储**

- 工作记忆：当前会话上下文，不持久化；
- 偏好记忆：结构化画像（JSON），例如 `{"reply_length": "short", "code_style": "functional"}`；
- 事件记忆：带时间的事实（"3 月部署了 k8s 集群"），进向量库用于召回。

**2. 写入策略**

不是所有话都值得记。提取时区分"一次性事实"和"长期偏好"，只有偏好进画像。可以在主对话里让模型顺带输出 `memory_update` 字段，也可以用小模型异步提取，避免阻塞主流程。

**3. 读取策略**

每次会话开始固定注入偏好画像（几百 token，便宜且稳定）；事件记忆走检索，top-k 控制在 3–5 条，加时间衰减权重。

**4. MCP 化**

把 `memory.read` / `memory.write` / `memory.update` 做成 MCP 工具暴露给 Agent，让它自己决定何时调用。比硬编码在 pipeline 里灵活，也更符合工具化的架构方向。

## 踩坑点

- **记忆冲突**：用户先说用 Vue，三个月后换 React。不做冲突处理，旧偏好会反复覆盖新指令。解法：写入走 append-only log，每条带时间戳，读取取最新；
- **过度提取**："今天天气不错"也被存进画像。提取 prompt 必须给反例，并设置信度阈值；
- **检索污染**：召回很多相似但不相关的内容。加元数据过滤（用户 ID、话题标签）比换 embedding 模型更有效；
- **隐私与删除**：记忆至少做用户级隔离，"忘掉 X"要真能删掉，不是只改个标记。

## 可复用建议

1. 偏好用结构化 schema，别存自由文本——检索准、更新易；
2. 每条记忆记 source（来自哪次对话），排查"它为什么这么想"时可回溯；
3. 记忆写入异步化，失败重试，不阻塞主对话；
4. 准备一组"记忆回归用例"：改了提取逻辑就跑一遍，确认偏好仍被正确读写。

## 总结

记忆系统的本质不是"存得多"，而是"取得准、更新得对"。分层存储、严格写入策略、带冲突处理的更新机制，三者都做对，Agent 才会显得"真的记得你"。建议从最简单的结构化偏好画像起步，跑两周看真实对话里缺哪些字段，再决定要不要上事件记忆——先跑通，再变复杂。
