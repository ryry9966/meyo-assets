## 背景

模型本身无状态，每次会话都是"失忆"重启。写过 OpenClaw 插件或接过 MCP 工具链的人都清楚：助手能不能记住"我喜欢简洁回复、代码用 TypeScript、部署走 Docker"，直接决定它是玩具还是生产力工具。很多方案停留在"把历史对话塞进 system prompt"，短期可用，长期必崩。

## 问题

实践里最常见的三类失败：

1. **全量记忆**：什么都存，检索时噪声淹没信号，token 成本失控；
2. **记忆冲突**：三个月前的旧偏好和昨天的新指令打架，助手机械执行过时结论；
3. **黑箱不可控**：用户不知道助手记了什么、为什么会那样做，信任崩塌。

## 做法

核心经验：把写入路径和读取路径拆开设计。

**1. 定义结构化 schema，拒绝自由文本存储**

```json
{
  "category": "coding_style",
  "key": "language",
  "value": "typescript",
  "source": "explicit",
  "confidence": 0.95,
  "updated_at": "..."
}
```

区分 `explicit`（用户明说）和 `implicit`（模型推断），后者初始置信度要压低。

**2. 写入要保守**。每轮或每会话结束跑一次蒸馏：只沉淀"可复用、跨场景稳定"的偏好；一次性事实（"今天服务器挂了"）进 episodic 日志，不进偏好库。高影响偏好（支付方式、默认收件人之类）必须显式向用户确认后才落库。

**3. 读取分两层**。核心画像（十条以内的关键偏好）每次会话固定注入；长尾记忆走混合检索——关键词精确匹配 + 向量相似度，只取 top-N 并附带来源标注。

**4. 冲突与遗忘**。新记忆按时间戳覆盖旧条目；隐式记忆加衰减机制：长期未被检索命中且低置信度的条目自动降权或清理。

**5. 可视可编辑**。做一个 `/memory` 类命令（MCP 工具或插件均可实现），列出、删除、修正任意一条记忆。这步看似可有可无，实际是用户敢不敢长期用的分水岭。

## 踩坑点

- **只上向量库**：语义相似会把"喜欢简洁"和"喜欢详细解释"召回在一起，exact match 必须保留；
- **隐式推断不设门槛**：用户问过一次正式语气，助手就永久切换——需要置信度阈值 + 二次确认；
- **schema 不留版本号**：后续迁移字段时痛不欲生；
- **检索结果直接拼 prompt**：记忆库若含外部输入，等同于开了注入后门，至少做来源隔离和转义；
- **忘了做导出/清空**：隐私合规和用户心理都需要一个"一键失忆"。

## 可复用建议

- 结构化优先于自由文本；
- 写入严格、读取宽松；
- 混合检索，别赌单一召回；
- 准备一组回归用例（"它还记得我要求过 XX 吗"），每次改动记忆逻辑后跑一遍；
- 存储本地优先，敏感字段单独加密。

## 总结

记忆不是 prompt 技巧，而是读写分离、带置信度和生命周期的数据工程。先让每条记忆可查、可删、可解释，再谈"越用越懂你"。从一个几十行的 SQLite schema 开始，往往比直接上向量数据库更接近能落地的答案。欢迎在社区贴出你们的记忆 schema 和蒸馏策略，这块大家的坑值得互相抄作业。
