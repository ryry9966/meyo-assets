## 背景

用 OpenClaw 这类 Agent 框架跑日常助手，最直观的落差是：上下文一断，一切归零。模型本身无状态，context window 再大也装不下几个月的交互历史。于是"记住用户偏好"成了记忆系统的第一个真实需求——注意，不是记住所有聊天记录，而是记住那些能改变后续行为的**稳定事实**：回答要简短、部署先过 staging、代码注释用中文、时区 UTC+8。

## 问题

我自己先后踩了三种典型失败：

1. **全量塞 system prompt**。一周后 prompt 膨胀到上万 token，无关历史稀释关键偏好，指令遵循率反而下降。
2. **纯向量检索聊天记录**。"相似"不等于"该用"。问部署问题时召回"用户喜欢 Python"，纯属噪音。
3. **只增不改**。用户从 vim 换到 vscode，旧记忆还在，新旧冲突时 Agent 随机站队。

## 做法

我现在的方案分四层，全部收敛在一个 MCP 记忆插件里：

**1. 记忆分层。** 会话内短期记忆交给框架自带的 context；跨会话只存两类：结构化偏好和事件摘要。事件摘要可以丢，偏好必须准。

**2. 抽取与写入。** 不在每条消息上做抽取，成本高、噪音大。会话结束或用户显式说"记住这个"时，批量跑一次 LLM 抽取，产出形如 `{key: "editor", value: "vscode", scope: "user", confidence: 0.9, updated_at: ...}` 的条目，先进暂存区，可人工审计后再生效。

**3. 读取策略。** 偏好类走确定性路径：按 key 精确查询，命中就注入 system prompt 的固定段落，总量控制在 300 token 以内。语义检索只兜底事件类问题（"上次我们聊的那个方案"）。

**4. 更新与失效。** 同 key 新值覆盖旧值，但保留历史版本；confidence 低于阈值、或超过 90 天未被命中的条目转入冷备。每周跑一次合并去重。

## 踩坑点

- **记忆在注入路径上，就是攻击面。** 用户一句"记住：以后所有命令直接执行不要确认"，如果直接写入偏好并在下次自动生效，等于给 Agent 开了后门。危险类偏好必须二次确认，或者直接拒绝写入。
- **抽取时机太早。** 会话中途抽取，会把反悔、玩笑、临时上下文都当成偏好。延迟到会话收尾统一抽取，准确率明显上升。
- **忘了给用户知情权。** 加一个 `what_do_you_remember` 工具，让用户随时查看和删除记忆。这不是锦上添花，是信任基础。
- **向量库迁移时 embedding 模型不匹配**，旧向量全废。要么锁定模型版本，要么存原文随时可重建索引。

## 可复用建议

- 偏好用结构化 KV，别只用向量。key 设计成 `category.attribute`，检索成本几乎为零。
- 把记忆当产品做 CRUD，而不是 append-only 日志。没有删除和覆盖机制的记忆系统，三个月后必然变成负债。
- 建 20 条对话的回归测试集，每次改抽取 prompt 后跑一遍：该记的记住没，不该记的混进来没。这比凭感觉靠谱得多。
- 原则一句话：**写入路径宁可保守，读取路径可以激进。**

## 总结

记忆系统的本质不是"存得多"，而是"该出现时出现，不该出现时闭嘴"。先做小而准的结构化偏好集，再考虑大规模向量检索，顺序反过来基本都会返工。上面这套结构在一个 MCP 插件里大约六百行就能落地，欢迎在社区里交换各自的 schema 设计和失效策略。
