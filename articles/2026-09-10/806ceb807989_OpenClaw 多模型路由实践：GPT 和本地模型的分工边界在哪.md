# 背景

我们的 OpenClaw agent 日常跑三类负载：多步任务规划、批量数据抽取、内部文档问答。早期全走 GPT，token 账单和 P95 延迟都很难看；后来全切本地模型（vLLM 部署 Qwen 系列），工具调用成功率又明显下滑。最后落到多模型路由方案：按「阶段」而不是按「任务」分流。

# 问题

路由最容易踩的坑是粒度定错。按任务类型分流看起来合理，但同一个「文档问答」里，改写、抽取、分类并不需要强推理，真正吃模型能力的是规划和工具编排。另一个问题是降级策略缺失：本地模型一旦输出不合法的 JSON，整条 pipeline 直接挂，省钱变成救火。

# 做法

我们的路由分四步：

1. **拆阶段**。把执行链拆成 planner（任务分解、工具选择）、worker（抽取、格式化、分类）、summarizer（汇总）三段。planner 固定走 GPT，worker 和 summarizer 优先走本地。
2. **显式配置路由**。在 OpenClaw 的 model profile 里声明映射，不搞 prompt 里「请自行选择模型」的隐式做法。路由判断用规则：任务 tag、上下文长度阈值、隐私标记。不要用大模型来做路由——那是给账单加杠杆。
3. **校验 + 升级**。本地模型输出先过 JSON Schema 校验和工具参数检查；失败重试一次本地，再失败升级到 GPT 并打标。这个 validate-then-escalate 是整套方案里收益最大的设计。
4. **硬路由**。涉及客户数据、内部代码的任务不看质量分，直接走本地。隐私线优先于成本线。

# 踩坑点

- **上下文窗口**：本地模型窗口小，长文档被截断后，工具调用参数恰好缺一块。路由规则里必须加上下文长度阈值，超限强制走云端。
- **function calling 兼容性**：不少本地模型的工具调用要么不支持原生协议、要么靠 prompt 模拟，格式漂移常见。建议锁死推理后端和模型版本，升级前先跑回归。
- **冷启动**：vLLM 首次加载要几十秒，serverless 场景下本地「便宜」是假象。常驻服务加模型预热之后才真正省钱。
- **输出风格漂移**：下游 prompt 往往是按 GPT 的输出习惯调的，换本地模型后分隔符、枚举值经常不对。少依赖格式暗示，多依赖 Schema 强约束。

# 可复用建议

- 按阶段路由，不按任务路由，粒度对了问题就消失一半。
- 「本地优先 + 校验失败升级」比「云端优先图省钱」稳健得多。
- 在仓库里维护一张路由决策表：阶段 × 模型 × 升级条件 × 隐私等级，改路由先改表、再改配置。
- 每周复盘分路由的 token 消耗、失败率、P95 延迟。路由规则是活的配置，不是一次性决策。

# 总结

多模型路由的核心不是「哪个模型更好」，而是承认 agent 链路里不同阶段对能力的要求不同：GPT 买的是规划质量和工具调用稳定性，本地模型买的是成本、延迟和隐私。用校验做闸门、用配置做边界，这套方案在我们环境里月成本降了约六成，工具调用成功率反而回升。建议从最简单的路由规则起步，跑一周真实数据再迭代，别一上来就堆智能调度。
