## 背景

Agent 的工作负载是不均匀的。OpenClaw 一次典型任务流里，规划、多步推理、长上下文代码生成只占请求的一小部分，却消耗大部分 token；而工具参数格式化、结果摘要、简单抽取这类“体力活”请求量大、单次价值低。全走 GPT，账单和延迟都难看；全走本地小模型，复杂任务质量立刻崩。多模型路由的本质，是让每类子任务落在合适档位的模型上。

## 问题

我的一条自动化流水线，单任务平均触发 15~20 次模型调用，真正需要强推理的不超过 3 次。全量走 GPT-4o 时成本和 P95 延迟都偏高；切成全本地 Qwen 后成本降了九成，但工具调用参数出错率从不到 1% 涨到 8% 以上，下游插件解析频繁失败。这就是路由缺位的典型症状。

## 做法

1. **先分类子任务**，分成三档：强推理（规划、多步决策）、格式化输出（工具调用参数、结构化 JSON）、高频低价值（摘要、去重、翻译）。
2. **挂两套 endpoint**：云端 GPT 走 API；本地用 vLLM 起 Qwen2.5-14B，暴露成 OpenAI 兼容接口，在 OpenClaw 的模型注册表里统一管理。
3. **按阶段路由，而不是按请求路由**：planner 阶段绑定 GPT，tool-caller 和 summarizer 绑定本地。阶段在编排层是确定的，路由就不需要额外判断。
4. **配 fallback 链**：本地调用失败或结构化校验不过，自动升级到 GPT 重试一次，并打标记录。
5. **观测一周再调**：按路由类别统计成本、P95 延迟、解析失败率，用数据决定边界往哪边挪。

```yaml
profiles:
  strong: gpt-4o
  fast: local/qwen2.5-14b-instruct
routes:
  planner: strong
  tool_caller: fast
  summarizer: fast
fallback:
  from: fast
  to: strong
  max_retries: 1
```

## 踩坑点

- **别让小模型自己决定“这次路由给谁”**。自路由的判断本身就会错，错误会级联放大；显式按阶段绑定远比动态路由稳。
- **本地模型的结构化输出必须过 schema 校验器**，别迷信 json mode。vLLM 开 guided decoding 后，格式错误率下降非常明显。
- **fallback 要有次数上限**。本地模型持续半失败时，无限制的云端重试会把延迟放大三倍，账单也跟着爆。
- **注意上下文长度**。本地 14B 模型 32k context，planner 塞进来的长文档转给它会被静默截断，工具参数直接缺字段，报错还很隐蔽。
- **隐私一致性**。标记为“本地处理”的数据一旦 fallback 到云端，必须在 trace 里显式标注，否则做数据审计时会翻车。

## 可复用建议

- 从“全强模型”起步，先拿到质量基线，再逐阶段往本地降，每降一档跑一遍回归用例。
- 路由决策写进 trace，和调用结果放一起。排障时你才知道某次失败是模型弱，还是路由选错了。
- “格式化输出”类任务设计成可校验的（schema + 有限重试），这是本地模型最值得先接管的一类，收益立竿见影。
- 把模型档位抽象成 profile（fast / strong），业务代码只引用 profile，换模型、换部署方式都不改代码。

## 总结

多模型路由不是单纯的省钱技巧，而是把“模型能力”当资源做分配的工程手段。按阶段绑定、结构化校验兜底、fallback 设上限、全程留 trace——这四件事做到位，云端 + 本地混合的 Agent 流水线，质量不会比全 GPT 差多少，成本和延迟却能砍掉一大截。路由规则一定是演化的：先跑起来，让数据告诉你边界在哪，比一开始设计“完美策略”实际得多。
