## 背景

OpenClaw 这类自动化系统的触发源很多：cron 定时任务、webhook 通道、Agent 的自主重试、人工补跑。它们的共同点是：你无法保证"恰好执行一次"。响应超时后框架重发、部署重启窗口 cron 重叠触发、Agent 判断工具调用失败后重新规划再调一次——在真实环境里，重试不是异常，而是常态。

## 问题

幂等性回答的是：同一任务被执行多次，副作用是否仍然正确。几个典型翻车场景：

- MCP 工具"创建工单"被调用两次：第一次其实成功了，只是响应超时，结果留下两张重复工单；
- 定时推送在容器重启窗口被执行两遍，用户收到两条一模一样的消息；
- 多步任务在第三步失败，整体重跑时前两步的副作用被重复执行。

根因是把"执行一次"当成了隐含约定，而底层投递语义实际是"至少一次"。

## 做法

1. **优先语义改造**：把"动作叠加"改成"状态断言"。"把配置设为 X"天然幂等，"追加一条 X"不是；upsert 优于 insert。
2. **定义幂等键**：`task_id + 步骤名 + 业务日期` 是常见组合。键必须稳定，不要掺时间戳或随机数，否则每次重试键都不同，等于没做。
3. **加执行台账**：一张 SQLite 表就够——幂等键、状态（进行中/成功/失败）、结果摘要、时间。执行流程收成一句话：查台账 → 已完成直接返回缓存结果 → 未命中则靠唯一约束抢占键位 → 执行 → 更新状态。
4. **防并发穿透**：两个 worker 同时通过应用层检查会双写，唯一约束是底线，不能只靠"先查一次"。
5. **能借力就借力**：不少外部 API（支付、消息类）原生支持 Idempotency-Key 机制，比自己造轮子可靠。

## 踩坑点

- **先执行后记账**：执行成功、进程崩溃、没来得及记录，重试就是重复副作用。更稳的顺序是先写"进行中"状态（带 TTL 防卡死），再执行。
- **键的粒度错了**：按整个任务生成键，第三步失败重跑时，前两步会被误判"已完成"而直接返回旧结果——应按步骤粒度；反之掺了随机参数就失去去重能力。
- **只记成功**：失败的执行也占住了键，导致永远无法重试。状态要区分，失败应允许重新执行。
- **只管自己幂等**：你这边去重了，下游 API 没有，重试照样发两条消息。链路每一跳都要确认。

## 可复用建议

- 把"至少一次"当默认假设：所有 cron 任务、webhook 处理器、Agent 工具调用，默认要求幂等。
- 在 MCP 工具的 description 里写明幂等保证（如"同一 resource_id 重复调用不会重复创建"），Agent 做重试决策时有据可依。
- 执行台账顺手就是审计日志，排障时"这任务到底跑了几次"一目了然。
- 给关键任务加一条"连跑两遍"断言：第二次执行不产生新副作用。这条测试比任何文档都有效。

## 总结

重试无法消除，只能消化。幂等性的本质，是把脆弱的"最多执行一次"升级为健壮的"执行多次、生效一次"。在 OpenClaw 生态里做自动化，与其追求完美的调度保证，不如让每个副作用天然可重放——这通常是更便宜、也更耐故障的那条路。
