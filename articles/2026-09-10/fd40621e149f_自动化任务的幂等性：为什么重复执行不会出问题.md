## 背景

跑 OpenClaw 自动化的人迟早会遇到这类场景：定时任务被调度器重复触发、Agent 重规划后把同一个 MCP 工具调了两次、网络超时触发重试、webhook 被投递了不止一份。这些不是偶发 bug，而是自动化系统的常态——大多数调度器和消息机制只能保证「至少执行一次」，从来不会承诺「恰好一次」。

幂等性（Idempotency）就是应对这个现实的工程手段：同一个操作执行一次和执行 N 次，系统的最终状态完全相同。有了它，重试、补跑、并发触发都不再是风险。

## 问题出在哪

先看几个典型的非幂等操作：

- **追加写入**：任务「同步新增订单」用 `INSERT`，重跑一次就多一批重复行；
- **发送类动作**：Agent 通知任务重试，用户收到两条一模一样的消息；
- **增量修改**：`counter += 1` 这类操作，执行两次结果就错了。

共同特征是：操作效果会**累加**，而不是收敛到一个确定终态。幂等性改造的核心，就是把这些操作变成收敛型的。

## 怎么做

**第一步：盘点，分类。** 列出所有自动化任务里的副作用操作，分成两类——增量式（insert、send、increment）和终态式（upsert、set status）。前者是改造对象。

**第二步：优先改写为天然幂等的形式。** 能 upsert 就不要 insert（用业务键定位）；能「把状态设为 shipped」就不要「追加一条 shipped 记录」；能整份覆盖（PUT 语义）就不要做增量合并。

**第三步：引入幂等键。** 无法改写终态式的操作（比如发通知），用业务内容派生一个稳定 key（如 `task_id + 触发批次号`），执行前先查执行记录表，存在则跳过。注意 key 必须跨重试稳定。

**第四步：把去重下沉到存储层。** 给幂等键建唯一索引，靠约束冲突兜底，而不是只靠应用层的 if 判断。数据库约束是最后一道、也是最可靠的一道防线。

**第五步：多步任务用「先认领、再执行」。** 执行前原子地把任务状态从 pending 改为 running（`UPDATE ... WHERE status='pending'`），改不到说明别人在跑或已跑完，直接退出。

**第六步：MCP 工具层面。** 自己封装的 MCP 工具，handler 内部应接受外部传入的 `external_id` 或先检查目标状态再变更，让上层 Agent 循环重试时天然安全。

## 踩坑点

1. **check-then-act 竞态**：先 SELECT 再 INSERT 之间有空窗，两个并发实例可能同时通过检查。解法是唯一约束或原子认领，别信应用层检查。
2. **每次重试重新生成 key**：在任务体内部生成新 UUID，等于每次都是新任务，去重完全失效。key 要从触发源派生，不是从执行现场派生。
3. **部分成功后的重试**：三步任务第 1 步成功、第 2 步失败，整体重跑会把第 1 步再做一遍。要么每一步各自幂等，要么持久化检查点。
4. **时间窗口逻辑**：「拉取最近 5 分钟的数据」在重试时可能重叠或漏掉。改用随执行记录持久化的 cursor/水位线。
5. **高估底层保证**：队列、调度器、Agent 重规划循环都可能是 at-least-once，别把「应该只触发一次」当设计前提。

## 可复用建议

- **一条原则：假设任何自动化任务都会被执行至少两次。** 从这条出发设计，几乎不会错。
- 优先声明式（终态）操作，少写增量式操作。
- 去重靠存储层约束兜底，应用层检查只是第一道门。
- 把 run_id / 幂等键写进日志，排查重复执行时有据可查。
- 给自研 MCP 工具写说明时，明确标注哪些调用可安全重试。

## 总结

幂等性不是额外的工程负担，而是让重试、调度、Agent 循环变得安全的前提。它换来的是：你可以放心加大重试次数、放心并行跑任务、放心让 Agent 自主重规划。对一个以自动化为核心的工作流来说，这是性价比最高的一笔前期投入。
