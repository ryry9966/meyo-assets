## 背景

写自动化任务时，我们默认脚本是"跑一次就完"。但实际运行中，重试无处不在：网络超时后 MCP 客户端重发请求、定时任务在上一轮没跑完时又被触发、人看到报错后手动点了一次"重新执行"。Agent 驱动的流程里还有一层：模型可能对同一个意图生成两次几乎相同的工具调用。

所以一个务实的标准是：**任何任务都应该允许被重复执行，且结果和执行一次相同。**这就是幂等性。它不是锦上添花，而是自动化系统能"放心失败"的前提。

## 问题

不幂等的操作在重试时会产生真实损失。典型的几类：

- **重复创建**：同一个触发事件创建了两个工单、发了两条通知、插了两条数据库记录。
- **重复副作用**：库存扣两次、余额减两次、文件追加写了两遍。
- **状态错乱**：先检查"是否存在"再创建，但两个并发实例同时通过了检查，各自创建了一份。

这些 bug 在测试时几乎不会出现——测试环境没人重试。它们只在生产环境的凌晨三点、网络抖动的那一刻浮出水面。

## 做法

把任务里的每个操作按性质分类，分别处理：

**1. 读操作：天然幂等，不用管。** 查询、列表、读取状态，重复执行无害。

**2. 创建操作：引入幂等键（idempotency key）。** 不要让服务端自己生成 ID，而是由任务侧根据业务上下文构造一个稳定的键，比如 `hash(事件ID + 目标对象)`，随请求一起带上。服务端按这个键去重，第二次请求直接返回第一次的结果。如果服务端不支持，就在数据库层面给业务字段加唯一索引，让重复插入自然失败。

**3. 更新操作：用条件更新代替盲写。** 把"把状态改成 done"写成 `UPDATE ... WHERE status = 'processing'`，或者带上版本号做乐观锁。重复执行时条件不满足，更新零行，无害返回。

**4. 删除操作：天然幂等。** 删除不存在的对象按成功处理即可，别把 404 当失败去重试。

**5. 记一份执行台账。** 一张简单的表：任务 ID、幂等键、状态、时间戳。每次执行前先查台账，已成功的直接跳过。这一步同时解决了"Agent 重启后不知道之前做过什么"的问题——状态不要只存在对话上下文里。

## 踩坑点

- **幂等键里掺了时间戳**。用 `hash(输入 + now())` 当键，重试时键变了，去重完全失效。键必须只由业务语义决定，时间窗口要取自事件本身。
- **check-then-act 的竞态**。"先查有没有，没有就创建"在并发下必挂。要么靠数据库唯一约束兜底，要么用分布式锁，别依赖应用层的检查。
- **把 HTTP 200 当成功**。有些接口返回 200 但 body 里是失败，这种情况不记录台账会导致反复重发。判定成功要看业务语义。
- **重试没有退避**。失败立刻重试形成重试风暴，把幂等保护也冲垮了。至少加指数退避和上限。

## 可复用建议

- 新任务上线前问一句：**这个任务连跑三遍，数据会不会坏？**不会才准上线。
- 创建类 API 一律设计成接受客户端生成的请求 ID，这是成本最低的幂等方案。
- 台账表 + 幂等键 + 条件更新，三件套覆盖绝大多数场景，不需要引入重型框架。
- Agent 的工具定义里，把"此操作可安全重试"写进描述，让模型在重试决策时有依据。

## 总结

幂等性的本质不是防止重复，而是**允许重复**。自动化系统的可靠性不来自"保证只跑一次"——这在分布式环境里几乎做不到——而来自"跑多次也没关系"。把重试当作常态来设计，任务才敢无人值守地跑。下次写自动化任务时，先想清楚它的幂等键是什么，这个习惯能省掉大部分凌晨的救火。
