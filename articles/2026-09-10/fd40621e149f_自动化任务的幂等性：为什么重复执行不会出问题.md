## 背景

在 OpenClaw 这类 Agent 自动化场景里，"一个任务只跑一次"其实是奢望：

- 模型可能对同一个工具调用重新发起请求；
- Webhook / 消息队列普遍是 at-least-once 语义，重投递是设计内行为；
- 定时任务可能重叠：上一轮还没跑完，下一轮已经触发；
- 超时最麻烦：请求发出去了，不知道对面到底执没执行，重试是唯一理性选择。

也就是说，重复执行不是异常路径，而是自动化的常态。幂等性就是为此准备的：同一个操作执行一次和执行 N 次，最终效果一致。

## 问题

不幂等的自动化，故障模式很固定：

- 汇报类任务重试后，群里出现两条一模一样的日报；
- 初始化脚本重复执行，往配置文件里追加了三段重复内容；
- 创建类 API 重试，实际只成功一次，系统里却多了两条记录；
- 更隐蔽的：清理类任务重跑，把刚生成的合法数据当垃圾删了。

这些问题在手动时代很少见——人不会一天点二十次按钮。自动化把执行频次放大了几个数量级，非幂等操作的副作用会同步暴露。

## 做法

按下面的顺序改造，多数场景够用：

**1. 先给任务定身份。** 每个自动化任务有稳定的 task_id，用 `hash(task_id + 业务日期 + 关键参数)` 生成幂等键。这是后面一切的地基。

**2. 写操作优先"声明式"而不是"动作式"。** 把"追加一行配置"改成"确保这行配置存在"；把"插入一条记录"改成"按唯一键 upsert"。目标状态不变，执行几次都无所谓。

**3. 创建类操作挂幂等键。** 调外部 API 时，能带幂等键的一定带（不少支付、消息类 API 原生支持）；不支持的，在本地落一张已处理表，执行前先查。

**4. 唯一约束兜底。** 数据库层加唯一索引，重复插入直接报错而不是生成脏数据。应用层去重是第一道防线，约束是最后防线。

**5. 副作用单独设卡。** 发消息、发邮件这类不可回滚的效果，触发前用幂等键核对一次"是否已经发过"。

## 踩坑点

- **check-then-act 的竞态**：先查"不存在"再创建，两个并发实例同时通过检查，照样重复。查和写必须原子，或者交给唯一约束。
- **幂等键的作用域**：键里只含日期，当天第二个合法任务会被误杀；键里含时间戳，重试就变成新任务。作用域应覆盖"会被重复执行的那次逻辑执行"，而不是自然时间。
- **超时后的盲重试**：第一次请求可能已经成功。没有幂等键保护的 API，重试前先设法核对状态，或者明确接受风险并记录。
- **"只读"工具的隐藏副作用**：有些 MCP 工具名义上读，实际会改状态（标已读、推进游标）。接进自动化前逐个确认。
- **只测成功路径**：幂等性要专门验——预发环境把同一个任务连跑两遍，diff 前后状态。

## 可复用建议

- 心态上默认"任何任务都会至少跑两次"，这是自动化的默认契约，不是悲观。
- 设计工具/插件时，优先暴露"设定状态"型接口，慎暴露"执行动作"型接口；动作型的一律要求幂等键。
- 日志里带上幂等键，排查重复问题时能一眼串起来。
- 新自动化上线前，"连跑两遍"应成为标准验收动作。

## 总结

幂等性不是锦上添花的优化，而是自动化系统的承重墙。Agent 环境里重试是结构性的——模型会重发调用，队列会重投递，定时器会重叠。与其祈祷不重复，不如让重复变得无关紧要：定好幂等键，写操作声明式化，唯一约束兜底。做到这三点，"再跑一次"就从一次事故风险，变成了一个无需关心的普通事件。
