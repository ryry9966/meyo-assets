## 背景：自动化里"只执行一次"是幻觉

任务只要跑得够久，一定会遇到重复执行：cron 到点触发但上一轮还没跑完；webhook 因为对端没返回 200 而重投；Agent 调工具超时后自动重试；插件崩溃重启后从头再来。消息队列更是明确告诉你：投递语义是 at-least-once。

所以"这段代码只会执行一次"是个不可依赖的假设。可靠的假设是：它会被执行至少一次，甚至并发多次。幂等性就是让这个假设变得无害的手段——同一任务执行 N 次，最终状态与执行 1 次完全一致。

## 问题：不幂等的任务，出事都在第二次

几个在社区里反复出现的形态：

- 通知插件用"追加发送"，重试后用户收到两条一模一样的告警；
- 定时任务往结果文件里 append，跑几次叠几层脏数据；
- MCP 工具封装的是 POST 创建接口，Agent 超时重试，系统里出现重复工单；
- 多步任务在第 3 步挂了，重试从第 1 步重做，前两步的副作用被重复施加。

共同点：单次执行看不出毛病，测试很难覆盖，全在"第二次"爆。

## 做法：把任务改造成"跑 N 次等于跑 1 次"

**1. 先给操作分类。** 读操作、按键覆盖写、按键删除，天然幂等；创建类 POST、增量写（append、计数 +1）、发消息，天然不幂等。改造精力只花在第二类。

**2. 给不幂等操作配幂等键。** 从业务上下文生成跨重试稳定的键，比如 `task_id + 步骤名 + 业务日期`，调用前查去重表：存在就跳过，不存在先落键再执行。关键是键必须稳定——每次重试现场生成新 UUID 等于没做。

**3. 让存储层兜底。** 应用层"先查后插"在并发下会双双通过检查，必须靠唯一约束做最后防线，写入用 upsert。检查逻辑走快速路径，约束保证正确性。

**4. 面向目标状态写，而不是面向增量写。** 把工具设计成"把 X 置为状态 S"，而不是"给 X 加 1"。前者跑多少次都收敛到 S，后者每次都叠加。写 MCP 工具和插件时优先暴露收敛式接口。

**5. 多步任务加检查点。** 每步完成后记录 journal（含幂等键和结果），重试时先读 journal，跳过已完成步骤。注意 LLM 本身不确定，重试可能换路径——要么固化计划再执行，要么把 journal 作为唯一的进度真相。

**6. 处理"超时但可能成功"。** 超时 ≠ 失败，请求可能已生效。第三方接口不支持幂等键的，用本地去重账本包一层：调用前登记，重试时先查账本再决定是否真发起。

## 踩坑点

- **幂等键不稳定**：每次重试重新生成键，去重形同虚设。
- **键的作用域错**：只用日期做键，同一天合法的第二次执行会被误杀；键要绑定"业务这一次动作"，不是时间窗口。
- **只做应用层判重**：并发下照样重复插入，唯一约束才是底线。
- **把"删除"当不幂等处理**：目标已不存在时返回 404 应视为成功，否则响应丢失会引发无意义重试风暴。
- **重试时复用上次的缓存状态**：每次运行应重新加载状态，否则基于过期数据的"幂等"会写坏结果。
- **工具幂等但 Agent 不幂等**：重试时 Agent 重新规划、换工具，副作用照样翻倍。固化计划 + 检查点缺一不可。

## 可复用建议

- 定一条默认假设：凡是定时或 webhook 触发的任务，一律按"至少跑两次"设计。
- 写一个通用去重模块（键生成 + 带 TTL 的存储），所有插件复用，别各写一套。
- 每个任务的日志都带幂等键，排查重复问题时一行就能对上。
- 加一个收敛性测试：同一任务连跑两次，断言第二次不产生任何新副作用。这条测试比十页文档都管用。

## 总结

幂等性不是锦上添花的优化，而是自动化可信的前提。重试、超时补偿、任务重叠、Agent 重放——这些机制全部建立在"重复执行无害"之上。把每个自动化任务改造成"跑 N 次等于跑 1 次"，你才真正获得"放心重跑"的自由，重试才会从风险变成安全网。
