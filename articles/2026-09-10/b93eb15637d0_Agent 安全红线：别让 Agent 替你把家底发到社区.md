## 背景

OpenClaw 社区的交流密度很高：晒配置、贴日志、传插件、共享 MCP server 是日常。这类共享对生态确实有价值，但有个常被低估的前提——**Agent 能读到的东西，远比你想分享的多**。它默认能访问工作目录、读配置、调工具、积累记忆。分享习惯不严谨，内部工作流就顺着社区渠道出去了。

## 问题在哪

实际观察到的三类泄露路径：

1. **配置即泄露。** 求助时直接贴 agent 主配置，里面除了模型参数，还有内网地址、真实目录结构、插件清单——有经验的人能从中还原你的内部自动化流程。
2. **截图即泄露。** 终端截图带 token、带客户名、带完整路径，是最高频的翻车方式。
3. **工具即出口。** 第三方 MCP server 和插件本质是可执行代码加网络出口。装上之后，Agent 读到的内容可能被发往作者的服务器，而你完全看不到。

## 做法：四步划红线

1. **先圈地，再放权。** 把 Agent 的工作范围限定在专用 workspace，敏感目录（客户数据、内部文档）明确不进 allowlist。文件系统的可见范围就是第一道边界。
2. **密钥出配置。** API key、token 走环境变量或本地 secret 文件，主配置里只留引用。这样贴配置求助时天然不带敏感内容。
3. **工具当出口审计。** 每装一个 MCP server 问三个问题：本地还是远程？要什么权限？源码能不能读？读不了源码的远程 server，不给写权限和文件权限。
4. **分享前过清单。** 截图裁掉路径和参数；日志先 grep 一遍 key 和内网域名；memory、session 文件永远不整包外发。

## 踩坑点

- 在 system prompt 里写"不要泄露内部信息"有用，但只是**软约束**。真正的边界是权限和工具清单，不是措辞。
- "我把 key 删了"不等于安全——日志里的请求参数、内部 URL 同样能还原架构。
- 有人把整个配置目录（含 memory 文件）打包发群里求排查，历史上下文里积攒的内部信息全在里面，这是最大的单点泄露源。
- 插件"看着无害"不等于无害。一个只是"读剪贴板做格式化"的辅助插件，就足够搬运敏感内容。

## 可复用建议

- 建一个**分享专用的最小配置模板**，求助时用它重建问题，而不是发生产配置。
- 给 Agent 单独跑一个低权限用户或容器，至少和日常工作权限隔离。
- 每月花十分钟 review 一次已安装的 MCP server 和插件清单，卸掉不用的。
- 把"分享前四查"（路径、密钥、内部名、memory）写进群公告，成本最低、收益最高。

## 总结

Agent 的能力边界，就是你的泄露边界。社区分享是 OpenClaw 生态变好的方式，但分享的应该是**解决思路**，不是**生产现场**。圈地、密钥外置、工具审计、分享清单——四件事都不难，难的是每次贴出配置前记得做一遍。
