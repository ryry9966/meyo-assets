## 背景

AGENTS.md 是放在工作空间根目录（或任意子目录）下的 Markdown 文件，也是目前多家 Agent 工具共同采纳的开放约定。OpenClaw 在会话初始化时会自动读取它并注入上下文，作为该工作空间内长期生效的行为规则。一句话概括：README 写给人看，AGENTS.md 写给 AI 看。

## 问题：上下文靠嘴喂，撑不过三天

没有这份文件时，我们遇到的典型状况：

- 每个新会话都要重复交代"测试用 `pnpm test`，别用 npm"、"提交信息走 Conventional Commits"；
- 定时任务、插件触发的自动化流程没有人在场，Agent 按默认习惯乱跑；
- 团队成员口头约定不一致，Agent 的行为随提问者漂移；
- MCP 工具一多，Agent 分不清哪些工具在这个仓库里该用、不该用。

这些不是模型能力问题，是上下文工程问题——缺一份机器可读、随代码演进的工作空间说明。

## 做法

建议按五段结构来写，整体控制在 100～150 行：

1. **项目概览**：这个仓库是什么、技术栈、目录结构，两三句话讲清；
2. **常用命令**：构建、测试、lint 的准确命令，别让 Agent 猜；
3. **代码与提交约定**：命名风格、分支策略、commit 格式；
4. **工具使用规则**：声明哪些 MCP 工具、插件在此工作空间可用，调用前是否需要人工确认；
5. **边界与禁止项**：不要动的目录、不要执行的命令、敏感文件的处理方式。

配套两个实践：

- **分层放置**：根目录放全局约定，`plugins/`、`docs/` 等子目录各放一份局部约定，就近生效，避免堆出一个巨型文件；
- **当代码维护**：进 Git、走 PR 评审。Agent 行为突然变了又找不到原因时，先查 AGENTS.md 的 diff。

## 踩坑点

- **写太长**。超过两三屏，关键约束会被稀释，token 成本也上去了。原则：每一条都必须影响 Agent 决策，否则删掉；
- **写成人类文档**。"本项目致力于……"这类介绍性文字对 Agent 没有约束力，要写祈使句："始终……"、"禁止……"、"调用 X 前先……"；
- **指令互相冲突**。根目录写"不要自动 commit"，子目录写"完成后直接 commit"，行为就不可预测。改约定时全局搜一遍；
- **硬编码路径和密钥**。这份文件会进版本库，绝对路径、token 一律不写，用环境变量引用；
- **过期不维护**。过期指令比没有指令更糟——Agent 会非常自信地做错事。重构目录、换构建工具时，把更新 AGENTS.md 列为验收项。

## 可复用建议

- 拿不准写什么，就记录你一周内对 Agent 重复说过的每句话，那就是初稿；
- 写完做个验证：新开会话问 Agent"你了解这个工作空间哪些约定"，看回答是否覆盖关键项；
- 细节规范不要塞进来，放进 `docs/` 再让 AGENTS.md 引用路径，保持主文件轻薄；
- 跑自动化任务（定时任务、webhook 触发）的场景尤其依赖它——没有人当场纠偏，这里的每一条都是唯一防线。

## 总结

AGENTS.md 本质上是"行为配置即代码"：用一个 Markdown 文件的成本，把散落在聊天记录和口头约定里的上下文固化下来，随仓库版本化、随团队演进。它不会让模型变强，但能让同一个模型在你的工作空间里稳定地做对事。对在 OpenClaw 上跑自动化流程的用户来说，这份文件值得当成基础设施来维护。
