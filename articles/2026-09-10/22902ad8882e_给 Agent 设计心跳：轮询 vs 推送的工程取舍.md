## 背景

OpenClaw 的 Agent 默认靠 heartbeat 醒来：gateway 按固定间隔注入一次 heartbeat prompt，Agent 读取 HEARTBEAT.md，判断有没有该做的事，没有就回 `HEARTBEAT_OK` 继续沉默。这套机制本质是**轮询**。而很多自动化场景还有另一条路：外部系统在事件发生时通过 webhook 或消息通道**主动推**给 Agent。两种唤醒方式怎么选，是做 Agent 自动化绕不开的第一道架构题。

## 问题

轮询的两个极端都不好受。间隔设太短（比如 30s），绝大部分 beat 是空转，token 按次数烧掉，上下文里堆满无意义的 OK 记录；设太长（比如 6h），事件响应延迟的下限就是间隔本身，监控类任务形同虚设。推送看着省心，但要求上游支持事件、端点要暴露、要处理鉴权/去重/重试，而且有一个隐蔽缺陷：上游“静默挂掉”时，Agent 永远不会知道——“没有消息”本身也是异常，但没有任何机制会把它报出来。

## 做法

我的实践是分层混合：

1. **先给任务分类。** 周期巡检类（整理待办、检查订阅源、日报）走轮询；即时事件类（CI 失败、告警、用户消息）走推送。
2. **轮询侧按实际时效配间隔。** 日常任务 30min 起步，巡检类 1–6h 都够。HEARTBEAT.md 只放“到点要做的事”，保持极短，不要当知识库用。
3. **推送侧加一层落盘。** 用 webhook 插件或消息通道把事件注入会话，中间垫一个轻量队列（哪怕就是一张 SQLite 表），Agent 忙或离线时事件先落库，醒来再消费。
4. **保留 watchdog。** 无论推送多完善，留一个低频 heartbeat 做存活检查和事件对账，发现积压或上游异常时主动汇报。

## 踩坑点

- **heartbeat 太频繁 + 指令模糊**：Agent 会在每个 beat 上“找点事做”，开始乱动。心跳指令必须可判定——要么明确动作，要么明确沉默。
- **webhook 重试没做幂等**：一次告警触发三次重复处理。事件里带唯一 ID，消费前查重。
- **推送端点裸奔公网**：被扫到就是垃圾注入入口，至少加签名校验或 token。
- **只信推送**：上游半夜挂了，第二天才发现“它没来报错”。这正是 watchdog 存在的意义。

## 可复用建议

- **度量两个指标**：空转率（`HEARTBEAT_OK` 占比）和事件到动作的 P95 延迟。空转率超过 90%，就该调大间隔或迁去推送。
- **算一笔 token 账**：单次 beat 成本 × 频率 × 24h。很多“30s 一跳”的配置，一天烧掉的量够跑几百次真实任务。
- **推送负责触发，轮询负责补偿**：事件驱动保证快，周期对账保证不丢。二者不是二选一，而是互补。

## 总结

轮询简单、可预测、不依赖上游，代价是延迟和空转；推送实时、省 token，代价是基础设施和故障面。单选任何一个都有明显短板，我最终落在“推送触发 + 低频心跳兜底”的混合结构上。heartbeat 的本质不是定时器，而是给 Agent 一个确定性的自查节拍——把节拍设计好，自动化才敢放手跑。
