## 背景

日常开发里有大量机械性的 Git 操作：写提交信息、按规范建分支、清理已合并的旧分支。这些事不难，但琐碎、易忘、风格难统一。OpenClaw 这类常驻 Agent 配上 MCP 的 shell 和文件工具后，正好可以把其中一部分流程接管掉。

## 问题

直接丢一句"帮我提交"给 Agent，常见的三类事故：

1. 提交信息与实际改动无关——模型没看全 diff，或者干脆编了一个；
2. 用 `git add -A` 一把梭，把临时文件、本地配置甚至密钥带进提交；
3. 分支清理时误删未合并分支，或对共享分支做了 rebase / force push。

所以核心问题不是"能不能自动化"，而是"在什么边界内自动化"。

## 做法

我们采用三步递进，每步跑稳了再进下一步：

**第一步：只读优先。** 只开放 `git status` / `diff` / `log` 等只读命令，让 Agent 输出提交信息草稿和分支命名建议，人确认后再手动执行。跑一两周，先验证生成质量，也校准团队规范。

**第二步：把约定固化下来。** 将团队的 commit 规范（Conventional Commits、scope 取值、message 中禁止出现的内容）写进仓库内的 Agent 约定文件（如 AGENTS.md），任何会话自动携带。提示思路：读取 staged diff → 判断 type/scope → 输出一行 subject 加可选 body → 列出将执行的命令，等待确认。

**第三步：受控执行。** 用命令白名单限制 Agent 可用的 git 子命令：允许 `add`（必须指定文件，禁止 `-A`）、`commit`、`switch`、`branch`；明确禁止 `push --force`、`reset --hard`、`clean`。所有 Agent 执行的 git 命令落一份操作日志，方便事后审计。

分支管理上让 Agent 固定做三件事：从任务标题生成分支名；每天列出已合并分支供人确认删除；每次提交前断言当前分支不是 main。

## 踩坑点

- **squash merge 陷阱**：被 squash 合并的分支在 `git branch --merged` 里不会出现，按这个清单清理会漏删，也可能误判；用 `git cherry` 比对补丁等价性，或在合入时记录分支元数据。
- **大 diff 截断**：diff 超过上下文窗口后，Agent 生成的 message 可能只覆盖前半段改动。限制单次提交规模，比反复调提示词有效得多。
- **message 泄密**：提交信息本身可能带内网地址、客户名等敏感内容，要在规范里明确禁止，并让 Agent 做一次自查。
- **detached HEAD**：Agent 在游离 HEAD 状态下容易把 commit 丢在临时位置，执行写操作前先断言 HEAD 状态正常。

## 可复用建议

- 先半自动再全自动，人工确认环节保留得越久越好；
- 规范写进仓库内的约定文件，而不是散落在每次聊天的提示里；
- 白名单加日志是底线，不要依赖模型自觉；
- 每条自动化规则都要想清楚对应的回滚方式。

## 总结

AI 管 Git 的价值不在"全自动提交"，而在于把 diff 理解、命名规范、分支卫生这类低判断量、高重复度的工作接过去。边界清晰、留有人工确认点的半自动模式，是目前最稳的落地形态。先把提交信息这一件事做扎实，再谈更大的自动化。
