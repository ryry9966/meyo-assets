## 背景

大多数 AI 助手默认是被动式的：用户发消息，助手回复，会话结束。但一个真正"贴身"的助手，价值往往产生在用户没开口的时候，日报定时推送、异常主动告警、任务到期前提醒。OpenClaw 这类常驻 agent 网关天然具备做 proactive 的条件：进程常驻、可接 MCP 工具、可挂 cron。所以问题从来不是"能不能主动"，而是"什么时候该主动"。

## 问题

直接在系统提示里加一句"你可以主动联系我"，实际跑起来通常是两种灾难：

1. **沉默型**：心跳按时醒来，agent 觉得没什么可说，一天消耗几十次心跳的 token，产出为零；
2. **烦人型**：每次心跳都憋出一条"我检查了一下，一切正常"的废话，第三天你就把它静音了。

本质是缺一个决策层：触发机制只解决"醒来"，不解决"醒来后说不说话、说什么、说完能不能动手"。

## 做法

我把 proactive 拆成三层来落地：

**1. 触发层（什么时候醒）**
- 确定性时间任务走 cron：每日 9 点汇总 GitHub 通知、周三提醒周报。时间已知的事不需要智能。
- 开放式监控走 heartbeat：比如每 45 分钟醒一次，扫一眼监控页 / 收件箱 / 服务器状态，判断有没有值得说的。
- 事件驱动走 webhook / 文件监听：CI 失败、特定邮件到达才触发，最省 token。

**2. 决策层（醒来说不说）**
这是关键。我在 heartbeat 的系统提示里写死了三条规则：
- 默认沉默，主动开口是例外；
- 开口标准：新信息 + 与用户目标相关 + 已造成实际影响（或用户很快会自己注意到）；
- 只读类信息（汇总、告警）可直接推；有副作用的动作（替用户发消息、写文件、调付费 API）必须先征求确认。

**3. 执行层（说了之后干什么）**
- 主动消息走单独的通道 / 标签，与正常对话区分，方便事后审计；
- 已推送的内容写入 workspace 的记忆文件，避免下次心跳重复汇报同一件事；
- 静音时段：23:00–8:00 只入队不推送，早上合并成一条 digest。

## 踩坑点

- **心跳 prompt 太空泛**：早期我写"看看有没有有趣的事"，agent 会为了显得有价值而硬找事汇报。改成清单式检查项后，误报率明显下降。
- **重复汇报**：agent 不记得自己已经报过"磁盘 80%"，每 45 分钟报一次。加了"已上报事项"清单才治好。
- **token 成本**：心跳 15 分钟一次时，空转消耗很可观。降到 45–60 分钟、心跳 prompt 压到两三百 token、用便宜模型做初筛，成本降了一个量级。
- **静音时段没做**：凌晨三点收到"你有一封新邮件"，这条消息比 bug 本身更让人想把它卸载。

## 可复用建议

- 先跑一个最小场景（比如每天一条日报），观察一周再扩展，别一上来挂五个监控；
- 把权限做成"观察 / 通知 / 执行"三级，逐步放开；
- 每次 proactive 行为落日志，包括"为什么决定开口"，方便回溯调规则；
- 用 cron 解决"知道时间的事"，heartbeat 只留给"不知道什么时候发生的事"。

## 总结

Proactive 不是给 agent 加一句"你要主动点"，而是触发机制 + 决策策略 + 权限边界三件事的组合。默认沉默、例外开口、副作用必确认——这三条原则能让助手从"话痨"变成真正省心的值班员。建议从一个具体的监控需求开始，把决策规则当代码一样持续迭代。
