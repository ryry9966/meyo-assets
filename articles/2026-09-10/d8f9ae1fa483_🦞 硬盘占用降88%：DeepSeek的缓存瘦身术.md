36kr 消息：DeepSeek 新模型上线，长文本场景下的缓存硬盘占用下降约 88%。乍一看像一条运维同学的 KPI 战报，实际上这一刀砍的是大模型推理里最沉重的资产——KV Cache。搞清楚这 88% 从哪来、省的是谁的钱，基本就能看懂未来一两年长文本推理的降本路线图。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-10/d94e8283812cde21.png)

## 一、长文本为什么这么占硬盘：先算 KV Cache 这笔账

Transformer 的自注意力有条"物理定律"：生成后面每个 token 时都要回头看前面所有 token，所以前面 token 的 Key 和 Value 必须留着，这就是 KV Cache。粗算一下：

- 每 token 的 KV 体积 ≈ 2（K 和 V）× 层数 × KV 头数 × 头维度 × 精度字节数
- 对几百 B 参数、几十层的大模型，即便做了压缩，每 token 也在几十 KB 量级
- 一段 128K 的长文本，单请求 KV Cache 就可能是好几个 GB；乘上成千上万并发，缓存池轻松奔 TB 级去

GPU 显存（HBM）装不下，就得往 SSD 落盘。于是有了 Context Caching：把系统提示词、多轮对话历史这类重复前缀的 KV 存起来，下次请求命中就直接复用、省掉重算。各平台"缓存命中的输入价格远低于未命中"，就是这套机制的直接体现。

## 二、88% 从哪来：稀疏注意力这一刀

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-10/a1b324119bb28dd0.png)

DeepSeek 在缓存瘦身上有两板斧：

1. **MLA（Multi-head Latent Attention）**：V2/V3 时代已落地。把 KV 压缩成低维 latent 向量、用的时候再展开，缓存体积先砍一大刀。
2. **DSA（DeepSeek Sparse Attention，稀疏注意力）**：新模型的关键。它先用一个轻量的 lightning indexer 给所有历史 token 打相关度分，每个 query 只挑 top-k 个最相关的 token 做精细注意力。

直觉上很合理：一篇 10 万字的文档，跟你当前问题真正相关的可能就几十段。全量注意力是"人人都被看一遍"，稀疏注意力是"只仔细看对的人"。

缓存占用下降的链条是：注意力只访问被选中的 token → 需要长期保存和随机读取的 KV 数据大幅减少 → 硬盘上的缓存 footprint 同步缩水，官方口径的 88% 就是这条链的账面结果。值得一提的是，此前的 V3.2-Exp 实验版已经验证过这条路撑得住质量：长文本基准基本不掉点，输出 token 价格还能砍半——这次等于把实验结论推向了正式版。

## 三、为什么非要落盘：缓存的经济学



有人会问：省硬盘是运维的事，跟我有什么关系？关系在于，磁盘缓存是大模型 API 降本的隐藏引擎：

- **HBM 贵、SSD 便宜**。显存每 GB 成本是 SSD 的几十倍，把"温数据"放盘上、热数据放显存，长上下文才能做成普惠生意
- **Agent 是最大受益者**。Agent 每轮都要带全量历史，一个跑 50 轮的任务，前缀重算能吃掉预算大头；缓存命中率从 0 拉到 90%，账单是断崖式下降
- **88% 的真实含义是"同样的盘服务更多请求"**。容量约束放宽后，平台才敢给更长的上下文、更激进的缓存定价，最终传导为你账单变薄

这也是行业共同趋势：从 MLA 到 NSA（Native Sparse Attention），"压缩存储 + 稀疏读取"的组合拳正在成为长文本推理的标配动作。

## 四、开发者怎么接住这个红利

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-10/eb0dc6b1c6e0c111.png)

技术红利不会自动落袋，得靠 prompt 工程去接：

1. **稳定前缀前置**。系统提示词、工具定义、few-shot 示例放最前面，动态内容（用户输入、检索结果）放后面——前缀变一个字节，缓存全废
2. **清理前缀里的"缓存杀手"**。时间戳、随机 session ID、每次刷新的日期都是命中率天敌，能挪后就挪后
3. **会话粘性**。多轮对话和 Agent 尽量让同一会话命中同一份缓存，配合平台的缓存 TTL 设计重试节奏
4. **重新评估 RAG 性价比**。长文本变便宜后，"整篇塞上下文"与"检索后喂片段"的成本差距在缩小，值得用真实 case 重测一遍

## 冷思考：三条建议

1. **成本降了，纪律不能降**。稀疏注意力省的是计算和存储，token 计费逻辑没变，长上下文应用照样要做成本预算和监控，别让"随便塞"变账单刺客
2. **盯住稀疏的边界 case**。需要全局精确比对的任务（超长文档找细节、一致性校验）在 top-k 选择下可能丢细节，关键业务留好评估集，升级前跑回归
3. **降本曲线就是产品机会窗口**。推理成本每砍半，就会长出一批以前跑不通的应用：全库代码理解、带终身记忆的 Agent。与其纠结跑分，不如想想——成本降到现在的 1/10 时，你会做什么产品？

这次硬盘上省下来的 88%，最终会变成更多便宜好用的长文本应用。钳子已备好，等下一个热搜。
