## 背景

OpenClaw 的 agent 每次会话启动时，除了系统提示，还会把 workspace 下的几个记忆文件注入上下文——`USER.md`、`MEMORY.md`、`SOUL.md` 等。其中 `USER.md` 的定位很明确：一份关于"你是谁"的长期档案，随每次会话常驻。

问题在于，很多人的 `USER.md` 要么是空的，要么写成了自我介绍散文。Agent 依然在每轮对话里猜你的偏好，猜错就返工。

## 我遇到的具体问题

- 让 agent 写运维脚本，它默认给 macOS 路径，而我日常在 Ubuntu 上跑
- 回复风格忽长忽短，经常贴一大段我不需要的解释
- 它不知道我在维护哪几个项目，每次都要口头交代一遍
- 定时任务算错时区

这些都能靠"每次都说一遍"解决，但重复成本高，换个会话照样忘。正确做法是把这类**全局事实**落盘到 `USER.md`（通常在 `~/.openclaw/workspace/` 下）。

## 我的 USER.md 结构

```markdown
# 用户档案
## 基本信息
- 语言：中文为主，技术名词保留英文
- 时区：Asia/Shanghai
- 环境：Ubuntu 22.04，shell 是 zsh

## 技术栈
- 后端：Python (FastAPI)、Go
- 部署：Docker Compose，无 K8s
- 不用：Java、PHP

## 当前项目（2025-06 更新）
- home-lab：家庭服务器自动化，路径 ~/projects/home-lab

## 协作偏好
- 先给结论和代码，再说理由
- 改配置前先列出 diff
- 未经确认不执行安装类命令
```

几条写法经验：

1. **只写全局事实，不写任务细节**。任务上下文走 `MEMORY.md` 或当场说。
2. **用可度量的陈述句**。"喜欢简洁"没用，"回答不超过三段，代码优先于解释"才有用。
3. **时效性信息带日期**。项目列表两周审一次，过期条目直接删。
4. **控制篇幅**。这份文件每次会话都注入，是常驻 token 成本，建议几百行以内。

## 踩坑点

- **和人设文件混写**。早期我往里塞"你是一位资深工程师"这类内容，后来意识到那是 `SOUL.md` 的职责。两者混写会导致指令互相打架。
- **敏感信息入库**。`USER.md` 会完整进入上下文，也会随 workspace 备份/同步。凭据、内网地址、家人信息一律不写。
- **过期信息比没有信息更糟**。残留的旧版本号会让 agent 按旧版本写代码。带日期、定期清理，比堆内容重要。
- **自相矛盾**。同时写"回答要极简"又附三段详细示例，模型只能随机选一个。可以定期让 agent 通读全文并指出冲突，比自己 review 快。

## 可复用建议

- **冷启动别硬写**：直接让 agent 面试你——"问我十个问题，然后生成 USER.md 初稿"，人工删改后收工。五分钟能得到八十分的版本。
- **workspace 进 git**：每次改动有 diff 可查，多台机器也好同步。
- **每月做一次档案审计**：让 agent 找出与近期对话矛盾的条目，列出修改建议，确认后合并。
- **区分两个文件**：`USER.md` 管"我是什么样的人/环境"，`MEMORY.md` 管"最近发生了什么"，边界清晰才不会互相污染。

## 总结

`USER.md` 本质上是一份**人工审核、机器常读**的配置文件。它的价值不在写得漂亮，而在准确、新鲜、无冲突。把它当配置管理来做——有结构、有日期、有 review 周期——Agent 的"懂你"就从玄学变成了一个可维护的工程项。
