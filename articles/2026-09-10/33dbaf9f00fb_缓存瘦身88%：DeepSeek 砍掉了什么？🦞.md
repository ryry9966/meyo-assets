热搜这行字值得拆开读：**长文本缓存**、**硬盘占用**、**88%**。三个词连起来，其实是推理产业一次教科书级的"存储经济学"操作。对普通用户，体感可能是 API 更便宜、长对话响应更快；对开发者，这直接关系到你的 agent 账单。这篇文章讲清楚三件事：推理系统往硬盘里塞的到底是什么、88% 是怎么省出来的、以及你该怎么吃到这波红利。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-10/aac3313a6ffc52bb.png)

## 先补课：推理时，硬盘里到底存了什么？

大模型生成一段话，内部其实分两个阶段：

- **Prefill（预填充）**：把你的 prompt 一次性算完。Transformer 的每一层都要为每个 token 记录 Key 和 Value 两个向量，供后续注意力查询使用。
- **Decode（解码）**：逐个 token 往外蹦。每生成一个新 token，都要回头"看"历史所有 token 的 Key/Value，所以这堆向量必须一直留着——留下的这份，就是 **KV Cache**。

问题是 KV Cache 大得离谱。以 DeepSeek V3 系列的 MLA（Multi-head Latent Attention）架构估算：每层每个 token 缓存约 576 维潜向量，61 层合计，bf16 精度下约 **70KB/token**；而主流 GQA 架构普遍在 200~300KB/token。即便已经被 MLA 压缩过，一条 128K 的长对话仍然是 128000 × 70KB ≈ **9GB**，约等于一部高清电影。这就是"长文本 = 存储怪兽"的由来。

## 为什么要放到硬盘上？缓存是一门生意

既然 KV Cache 这么大，显存肯定装不下所有会话，于是厂商把算好的缓存放进分布式 SSD 池，这就是**上下文缓存（Context Caching）**：

- 大量请求共享相同前缀——system prompt、RAG 参考文档、agent 的历史轨迹。第二次请求命中缓存，就可以跳过 prefill 直接解码：省算力，也省首 token 延迟。
- 厂商把这件事显性化成了定价：命中缓存的 token 按折扣价计费。DeepSeek 早在 2024 年就把缓存命中价格打到未命中价格的约十分之一，等于明说"我帮你存了，省下的算力分你一份"。
- 全行业都在走这条路：Moonshot 的 Mooncake 用 SSD 池做 KV 分离式推理；SGLang、vLLM 内置前缀缓存；Anthropic、OpenAI 的 prompt caching 是同思路的内存版本（带 TTL）。

代价是缓存池容量爆炸：10 万条 128K 会话就是约 900TB 的企业级 NVMe。而且命中率存在长尾——大量会话只被访问一两次，却一直占着盘。存储，从配角变成了成本表上显眼的一行。

## 88% 从哪来：稀疏注意力这一刀砍在哪

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-10/e19a01b5b7881571.png)

新模型的关键变化是引入**稀疏注意力（DeepSeek Sparse Attention，DSA）**，原理可以粗略概括为"先索引，再精读"：

1. 一个轻量的 indexer 先给每个 query 打分，从长上下文里挑出最相关的少量 token（top-k 量级）；
2. 注意力计算只在被选中的子集上进行，而不是对全序列逐个对账。

这一刀顺着三层传导到了缓存上：

- **存得少**：既然大部分 token 的 KV 在推理时根本不会被读到，缓存就没必要为每个 token 保存完整 KV——只需保存很小的索引打分，加上真正会被选中的那一小部分 KV，单会话缓存体积断崖式下降。
- **算得省**：注意力计算量从"全序列"降到"top-k"，prefill 和 decode 双双变便宜。
- **存得久**：同样一块盘能塞下更多会话、保留更久，命中率上升，又反过来摊薄单位成本。

对个账：按 88% 折算，一条 128K 会话的缓存从约 9GB 降到约 1.1GB；同一批 SSD 从存 10 万条变成能存 80 多万条。顺带一提，NVMe 读盘带宽通常在 GB/s 量级——缓存命中后要把数据从盘里捞回来，9GB 要读约 3 秒，1.1GB 只要 0.4 秒左右，这也是长对话变快的直接原因。

需要说明：官方没有公开全部工程细节，以上是基于公开信息的机制性解释，但方向是明确的——把"全量精读"改造成"索引 + 按需抽查"。回头看 DeepSeek 的路线图：MLA 压缓存体积、硬盘缓存换价格、稀疏注意力砍存储，这是一条连续的存储优化主线，不是突发奇想。

## 这事为什么重要：成本战从算力打到了存储

- 模型能力趋同之后，单位 token 成本就是硬竞争力。训练看 GPU 豪横，推理看账单精细，而存储是账单里长期被低估的一项。
- Agent 时代，长上下文成了默认形态：一个 coding agent 的一次请求可能携带几十万 token 的历史与工具输出，缓存命中率直接决定这条业务线的盈亏。
- 效率红利传导到了价格端：伴随模型更新，官方口径的 API 价格进一步下探，"每百万 token 单价"的行业锚点又被压低了一截。价格战的底层，其实是架构效率战。
- 对应用侧，长文档问答、代码库级理解、多轮 agent 这些"以前嫌贵"的场景，盈亏平衡点被进一步拉低，很多产品从"做不了"变成"可以试试"。

## 冷思考与实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-10/7b386ba7887ac68c.png)

1. **把"可缓存性"当架构目标**：稳定的 system prompt、工具 schema、参考文档放在 prompt 最前面，动态内容放最后；前缀里改一个字，整段缓存就可能失效。持续监控 cache hit rate——它对你账单的影响，往往大于模型单价本身。
2. **用"每任务成本"做评估**：别只盯着每百万 token 的标价，用端到端任务（比如完整跑一轮 agent 流程）的总花费做 A/B 对比。命中率、重试、上下文膨胀都会改写结论，而且模型迭代很快，选型测试应该做成常规动作。
3. **别把当前价格当成永久假设**：推理成本曲线的方向是确定的——向下，而且经常是跳崖式向下。产品定价和毛利模型里，应该留出"成本再降 80%"的余量；真正的壁垒在数据、工作流和交付质量，而不是占住一时的 API 差价。

硬盘第一次在推理成本表里拿到了主角戏份，转头就被新技术砍掉了八成戏份。对用户来说这是好事——这样的"裁员"，多多益善。
