## 背景

用 OpenClaw 这类 Agent 框架做自动化，cron 是最常用的入口：每天拉数据、定时巡检、周期汇总。我目前维护着十几个定时任务（数据日报、日志巡检、内容聚合），早期踩坑极多，任务时好时坏。核心原因最后都指向同一处：instruction 写得像一句聊天消息，而不是一份可独立执行的任务书。

## 问题：定时执行和对话是两回事

Cron 触发的任务有三个本质区别：

1. **冷启动**：每次触发都是全新会话，没有上下文，Agent 只带你这一个 instruction；
2. **无人纠偏**：跑歪了没人当场拦，错误往往几天后才被发现；
3. **结果必须有去处**：输出只留在会话里，等于没做。

所以评判标准不是“写得像人话”，而是：**一个陌生人拿着这张纸条，能否在无人协助下独立完成并留下可检查的痕迹。**

## 做法：按交接文档的六段结构写

1. **目标一句话**：做什么，完成与否怎么判定；
2. **输入**：数据从哪来（MCP 工具名 / 文件路径 / 接口），时间窗怎么算——明确时区，以触发时刻为基准推算；
3. **步骤**：3–5 步，每步一个动作，不写形容词；
4. **输出**：写到哪（文件/频道/webhook），给格式模板甚至填充示例；
5. **异常**：重试几次、失败时输出什么，明确“禁止编造数据”；
6. **边界**：明确不做的事（不回复用户消息、不调用清单外工具）。

对比示例。“每天总结昨天的群消息”这种写法在 cron 里几乎必挂，改写后：

```text
调用消息工具，读取 #dev 频道 {触发时刻-24h} 至 {触发时刻}
（Asia/Shanghai）的消息；过滤 bot 消息后按主题归类去重；
输出到 /data/digest/{当日日期}.md，格式按模板；
消息为空则写入"今日无内容"；工具调用失败重试 1 次，
仍失败则记录错误原因，不得推测内容；不回复任何消息。
```

## 踩坑记录

- **相对时间歧义**：“昨天”以谁为准？统一约定一切以触发时刻为基准，写清换算规则，不让 Agent 猜。
- **时区不一致**：调度器时区和 instruction 内时间语义可能对不上，两处都写死。
- **不幂等**：任务重跑导致重复推送。加“若当日目标文件已存在则跳过”，或明确覆盖策略。
- **状态膨胀**：有人把上次结果贴回 instruction 传状态，几周后 prompt 越滚越大。状态放文件，instruction 只声明读写哪个文件。
- **职责错位**：通用能力（工具用法、输出规范）放 system prompt 或插件，cron instruction 只留任务级编排，控制在半屏以内。
- **静默失败**：在输出里强制带一行状态（成功/部分/失败+原因），巡检时只扫这一行。

## 可复用建议

- 上线前用相同 instruction 手动触发一次，当测试用例跑；数据源一变就重测；
- instruction 进版本管理，改动留 commit；
- 每个任务配最小权限工具清单，写进边界段；
- 每月 review 一次 instruction 和数据源是否仍匹配。

## 总结

Cron instruction 的功力不在措辞花哨，而在于把“人不在场”这个前提翻译成结构化约定：目标、输入、输出、异常、边界，一段不缺。写完自问一句：凌晨三点无人值守，Agent 拿这张纸条能不能独立跑完并留下可核查的输出？能，就够了。
