## 背景

大多数 Agent 的默认形态是 request-response：用户开口，它才动。但真正像"助手"的体验，往往发生在你没开口的时刻——磁盘快满了它先告警，每天早上汇总昨晚的 CI 失败，监控到某个文件变动后自动触发一次检查。在 OpenClaw 生态里，MCP 工具、插件、定时任务这些原料都已经齐了，缺的是把它们串成一条**主动触发流水线**的工程方法。

## 问题

最直接的做法是给 agent 挂个 cron，让它"自己看着办"。实际跑起来通常是两个极端：要么安静得像没装（事件根本没进来），要么疯狂输出通知把人淹没（什么事件都全量跑一遍 LLM）。根因是把**触发**和**决策**混在了一层里。Proactive 能力的核心不是让模型更聪明，而是让确定性代码先把 90% 的噪音挡掉。

## 做法：四层结构

**1. 触发层：统一事件源。** cron、webhook、文件 watcher、消息监听，全部归一化成同一种事件结构（`source` / `type` / `payload` / `timestamp`），推进一个事件队列。不要让每个插件直接调 agent，否则后面没法统一治理。

**2. 过滤层：判断值不值得做。** 这一层纯代码、不用 LLM：同 `source+type` 在 N 分钟内只保留最新一条；静默时段直接丢弃；剩余事件按规则打优先级分，低于阈值要么丢，要么攒成一批日报。行为完全可预测，且不烧 token。

**3. 决策/执行层。** 只有通过过滤的事件才组装 prompt 交给 agent，并在 prompt 里明确说明"这是一次主动触发，上下文如下"。工具走白名单：主动场景默认只读，写操作要么在白名单里，要么降级为待确认项。

**4. 反馈层。** 每次主动行为落一条结构化日志，用户端提供"有用/没用"标记，按周回顾调阈值。

## 踩坑点

- **自触发循环**：agent 执行动作（比如写了份报告文件）又触发了 watcher，事件再进队列。给 agent 自己产生的事件打标记，过滤层直接丢弃。
- **去重键设计太粗**：用原始 payload hash 做去重，payload 差一个字节就全通过，照样通知轰炸。去重要用语义键，比如"同一目录 + 同类告警"。
- **时区**：cron 按服务器时区跑，"每天早上 8 点汇总"变成晚上 8 点。统一存 UTC，触发时按用户时区换算。
- **成本失控**：低价值事件也全量跑 LLM。过滤层必须放在模型调用之前。
- **权限惯性**：调试时开了写权限，上线忘了收。主动模式和交互模式的权限分开配置，物理隔离。

## 可复用建议

- 先以 **report-only 模式**跑两周：只输出建议、不动手，用真实反馈校准阈值，再逐步放开写权限。
- 所有主动写操作做**幂等**：带幂等键，重复触发不产生重复副作用。
- 触发检测与执行**拆成两个进程**：执行端挂了不影响事件收集，重启后补跑。
- 给用户**总开关 + 分类开关**，而不是一刀切；一个关不掉的主动助手会被当成垃圾邮件源。
- 把主动行为日志当一等公民，排障基本全靠它。

## 总结

Proactive 不是"给 agent 加个定时器"，本质是一条事件流水线：统一触发 → 代码层过滤 → agent 决策 → 全量审计。LLM 只出现在决策环节，前面的脏活累活交给确定性代码。先克制、后放开，主动能力才能真正被留下来用。
