## 背景

Agent 场景对模型调用的特点和聊天不一样：一次任务往往是几十次短调用——规划、工具选择、结果摘要。这类调用对首 token 延迟敏感、对单次智力要求不高，恰好是本地小模型吃得下的活。加上 MCP 工具经常要碰私有文件和内网服务，数据不出本地的诉求是真实的。把一部分模型搬回家用电脑上跑，动机成立。

## 问题

真正落地时会遇到三件事：

1. 显存/内存怎么算，选多大的模型才不会 OOM；
2. 本地推理服务怎么接进现有的 Agent/MCP 链路；
3. 小模型的工具调用（function calling）质量参差，怎么判断"够用"。

## 做法

**第一步：算账。** 粗略公式：显存占用 ≈ 参数量 × 量化字节数 + KV cache。Q4_K_M 约每参数 0.6 字节，7B 模型权重约 4GB，8K 上下文的 KV cache 再加 1~2GB，留 20% 余量。经验值：8GB 显存跑 7~8B Q4，16GB 跑 14B，24GB 可上 32B。纯 CPU + 大内存也能跑，但 tokens/s 掉到个位数，只适合批处理，不适合交互式 Agent。

**第二步：选推理服务。** 三条路线：

- **Ollama**：最省事，自带 OpenAI 兼容接口，适合快速验证；
- **llama.cpp / llama-server**：可控性强，能调 context、量化 KV cache；
- **vLLM**：显存充足且要并发时再上，家用场景通常用不满。

**第三步：选模型。** 中文能力 + 工具调用是两个硬指标。实测 Qwen 系列 7B/14B 量化版的 tool call JSON 输出稳定性最好，建议从这里起步。

**第四步：接入 Agent 链路。** 把 base_url 指到本地端口的 OpenAI 兼容端点，model 名对上即可。关键动作是先写一个最小 MCP 工具（比如列目录、读文件）做冒烟测试，确认模型能稳定吐出合规的工具调用格式，再接全量工具。

**第五步：压测并记录。** 记三个数：tokens/s、首 token 延迟、10 轮工具调用成功率。这三个数决定该模型能否进你的自动化链路。

## 踩坑点

- **默认 context 太小**：部分推理服务默认上下文只有 2K，Agent 的长 system prompt 会被静默截断，症状是"模型忘了工具列表"。务必显式调大，同时注意 KV cache 显存会跟着涨。
- **量化档位与 JSON 质量**：Q4 聊天没问题，但工具调用的 JSON 会偶发格式错误。关键链路升到 Q5/Q6，或开结构化输出约束。
- **offload 断崖**：GPU offload 层数卡在临界点时，个别层溢出到 CPU 会导致 tokens/s 断崖式下跌。宁可换小一档模型，不要"刚好塞满"。
- **别忘了 embedding**：做本地 RAG 时 embedding 模型也要本地化，CPU 跑 embedding 完全够用。
- **固定版本**：模型文件加校验，别让自动更新悄悄换掉线上行为。

## 可复用建议

- 建一个 `local-models.md`，记录每个模型在自己机器上的三个压测数，选型不再靠感觉。
- 混合路由：本地模型接"高频低难"节点（分类、摘要、格式化），难任务留给云端大模型。Agent 框架里按节点配模型即可，成本和延迟都能打下来。
- 工具调用成功率是本地模型的第一淘汰指标，比 perplexity 有用得多。

## 总结

本地部署的价值不在于"替代云端"，而在于把 Agent 循环里那些大量、琐碎、涉及隐私的调用收回来。硬件按显存公式选型，服务用 OpenAI 兼容接口无缝接入现有链路，用冒烟测试加三个压测数字决定去留——这套流程一个晚上能跑通。欢迎在评论区贴出你的机型和压测数据，攒一份社区实测表。
