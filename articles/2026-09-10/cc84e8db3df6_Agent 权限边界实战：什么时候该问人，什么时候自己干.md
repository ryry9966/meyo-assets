## 背景

Agent 接上 MCP 和插件后，能力边界从"聊天"扩展到了真实世界：读写文件、跑 shell、调内部 API、发消息，甚至碰生产数据。问题随之而来——每一步都问人，自动化就失去了意义；每一步都自己干，一次误操作就可能造成不可逆的损失。在 OpenClaw 这类可自由接入工具的框架里，权限边界不是别人替你做好的默认值，而是自己搭 agent 时绕不开的设计题。

## 问题：边界模糊在三个地方

1. **工具本身不携带风险信息**。`read_file` 和 `send_email` 在协议层看起来都是"一次函数调用"，风险差异全靠调用方自己判断。
2. **单步安全，组合危险**。读配置文件（只读）+ 调外部 API（可写）连起来，就是一次数据外发。
3. **人的审批能力有限**。确认弹窗一多，就会退化成无脑点"允许"，确认机制名存实亡。

## 做法：三档分级 + 运行时强制

我的做法是把所有接入的工具先做一次静态分级，再在运行时按档位执行不同策略：

- **绿色（自动执行）**：只读、影响仅限本地、天然可逆。比如读文件、查数据、搜索。
- **黄色（先出计划，等人确认）**：写操作、批量操作、花钱、调外部服务。确认时必须带上 diff 或操作摘要，让人 10 秒内能判断。
- **红色（默认拒绝）**：不可逆删除、对外发送、支付、改权限/密钥。除非显式加白名单，否则不暴露给 agent。

落地要点：

1. **分级不要只写在 system prompt 里**。prompt 是"建议"，可以被注入绕过；真正的强制应该放在 MCP 网关 / 插件加载层做 allowlist。
2. 黄色档的确认请求做成**计划卡片**：要调什么工具、参数是什么、影响哪些资源。不要把完整上下文原文甩给人看，看不完的。
3. 长任务跑到黄色操作时，把"已完成步骤摘要 + 待执行计划"一起给出来，而不是只问"可以继续吗"。
4. 所有放行和拒绝都记审计日志，攒两周数据后回看：自动档有没有越界？确认档有没有人从不细看？

## 踩坑点

- **只盯写操作**。读 `.env`、读聊天记录同样是高危，泄密往往发生在"只读"上。我在绿色档里单独排除了含密钥和凭证的路径。
- **把确认做成橡皮图章**。早期我让每个写操作都要确认，三天后自己就开始盲点。宁可缩小黄色档的范围，也要保证每次确认都被真正看过。
- **回收站不等于可逆**。有的删除有 30 天恢复期，可以降级到黄色；有的没有，必须红色。可逆性要看实现，不能看 API 名字。
- **中间态最难审**。agent 跑了 20 步之后才来问"要不要删这个目录"，人根本没有足够上下文判断。这种情况宁可让它先停，导出状态重新确认。

## 可复用建议

- 新接入的工具一律先进红色档，观察一段时间再降级。反过来"先放开再收紧"的代价高得多。
- 用三个维度给工具打分：**是否可逆、是否出边界（本地→外部）、是否批量**。三个都低才给绿色。
- 高危写操作先 dry-run：让 agent 输出"将要做什么"，确认后再真执行。
- 每月花十分钟翻一遍审计日志，权限配置应该跟着实际使用数据走，而不是拍脑袋。

## 总结

权限边界不是一次性的 prompt 工程，而是一套随数据迭代的机制：静态分级定基调，运行时强制做底线，计划卡片降低人的审批成本，审计日志反过来修正分级。目标不是让 agent 少干活，而是把"问人"花在真正值得问的地方。
