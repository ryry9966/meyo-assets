## 背景

LLM 本身无状态，每个会话都是白纸。用户最常见的抱怨不是模型不够聪明，而是"我上周明明说过用 pnpm、别写多余注释、部署走 staging，它今天又来一遍"。在 OpenClaw 这类 agent 框架里，MCP 给了记忆系统一个自然的位置：把记忆做成一组工具，而不是往 system prompt 里硬拼字符串。

## 问题

把记忆做坏的方式惊人地一致：

1. **流水账式记录**：每轮对话都 append，两周后检索出来全是噪音；
2. **偏好冲突不处理**：早期的"用 tabs"和上周的"改用 2 空格缩进"同时命中，模型随机选一个；
3. **注入不设预算**：几百条记忆全塞 prompt，token 爆炸且行为过拟合；
4. **隐式推断太自信**：用户随口说了句"这个项目用 Python 3.10"，就被固化成永久全局偏好。

本质是：记忆不是存储问题，而是**写入过滤 + 读取预算 + 冲突消解**的工程问题。

## 做法

**1. 分层，但只分三层。** 全局偏好（结构化、条数少）、项目/会话级上下文（可检索）、当轮工作记忆（就在上下文里）。不要造更多层。

**2. 写入靠提取，不靠记录。** 会话结束后跑一次提取，输出候选记忆条目，每条带字段：type（preference/fact/procedure）、scope（global/project）、confidence、source、时间戳、命中次数。低于置信度阈值的直接丢弃，或标记待确认。

**3. 读取分两条路。** 全局偏好按 confidence + recency 排序取 top N 注入 prompt，硬性预算 300–500 token；情景记忆不预注入，封装成 MCP 工具（`memory_search` / `memory_list`），让 agent 按需调用。

**4. 冲突消解三原则。** scope 窄的覆盖宽的；时间新的覆盖旧的；覆盖不删除，保留 superseded 标记以便回滚。用户显式说"以后别这样"时，写入一条高置信度反偏好，不要指望模型自己权衡。

**5. 留评测集。** 攒 20–30 个"助手应该想起某偏好"的对话用例，每次改写入或排序逻辑后跑一遍命中率。没有这个，调记忆系统全靠玄学。

## 踩坑点

- **检索噪音比缺记忆更伤。** 一条无关记忆命中就会把回答带偏。宁可召回少，也要卡相似度阈值。
- **"忘记"要做硬删除。** 只从索引摘除、embedding 还留着，检索偶尔还是会捞出来，用户会觉得 agent 阳奉阴违。
- **推断型记忆默认低置信度。** 从单次交互推断的偏好，最好在合适时机向用户确认一句，尤其是影响产出的（代码风格、依赖选择这类）。
- **scope 泄漏。** 工作项目的偏好跑到个人项目里，比没有记忆更让人恼火。scope 校验要在读取侧再做一次，别只信写入侧。
- **区分记忆和 RAG。** 记忆是关于"这个用户和这个 agent 的关系"，保留策略、衰减逻辑都和知识库检索不同，别共用一套。

## 可复用建议

- 别一上来就上向量库。一个手工维护的 preferences.json + prompt 注入，能拿到 80% 的收益，先跑通再演进。
- MCP server 保持"笨"：只做存取和过滤，提取和排序逻辑放 agent 侧，方便快速迭代。
- 每条记忆带 provenance（来源会话 id），排查"它为什么记住了这个"时能救命。
- 写入放在会话结束而非每轮，噪音至少降一半。

## 总结

让 agent 记住你，靠的不是更大的数据库，而是三层克制：写入时过滤、读取时设预算、冲突时有明确规则。先用最土的方案跑起来，攒好评测集，再逐步替换组件——记忆系统的迭代周期很长，一开始别过度设计。
