# HEARTBEAT.md：让 Agent 主动做事，而不是等你提问

## 背景

多数 Agent 的默认形态是"应答机"：你提问，它回答，会话结束就沉寂。OpenClaw 给了另一种可能——心跳机制。Agent 每隔一段时间自动醒来，读取工作区根目录下的 `HEARTBEAT.md`，按里面的常备指令自行判断"要不要做点什么"。这个文件的定位很朴素：它不是任务队列，而是你留给 Agent 的**常备指令单**（standing orders）。

## 问题

有了心跳不等于有了主动性。实践里最常见的三种失败形态：

- **心跳空转**：Agent 醒来发现没事做，回一句无意义的问候，白烧 token 还刷屏
- **汇报噪音**：每次心跳都汇报一遍同样的状态，聊天记录变成日志流
- **重复执行**：循环场景下同一件事做两遍，比如把同一条提醒发两次

根源是同一个：`HEARTBEAT.md` 没写好。

## 做法

**第一步**：在工作区根目录（通常是 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，保持精简：

```markdown
# 常备指令（每次心跳逐条检查）

- 检查 PROJECT/TODO.md，有到期任务就提醒我，做完打勾
- watch 的仓库有标注 bug 的新 issue，简述后汇报
- 磁盘占用超过 85% 时提醒
- 无任何需要汇报的内容时，仅回复 NO_REPLY，不要寒暄
```

最后一条是关键。心跳流程中，Agent 判断"无事可做"时回复 `NO_REPLY`，系统就不会把这条消息打进会话——这是防止刷屏的官方阀门，务必显式写进文件。

**第二步**：配置间隔与会话目标。默认 30 分钟对多数场景够用：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": {
        "every": "30m",
        "target": "main"
      }
    }
  }
}
```

（旧版本用 `HEARTBEAT_INTERVAL_MS` 环境变量，字段以你部署版本的文档为准。）

**第三步**：给需要状态的检查加"水位记录"。比如让 Agent 在 `NOTES/heartbeat-state.md` 里记下"已处理到 issue #123"，下次心跳先读这个文件再决定动作，天然幂等，不会重复汇报。

## 踩坑点

1. **文件写太长**。`HEARTBEAT.md` 每次心跳都会进上下文，20 行和 200 行的日常 token 开销差一个量级。常备指令控制在 20 行内，一次性任务放进它引用的 TODO 文件。
2. **间隔贪短**。把 `every` 设到 1–5 分钟，成本陡增且容易动作重叠。精确到分钟的调度交给 cron 类技能，心跳只留"需要判断力"的巡检。
3. **重活压进心跳**。心跳是轻量唤醒，跑长任务会拖垮节奏，重活拆成 cron 任务或手动触发。
4. **"每天早上汇报"不靠谱**。Agent 对当前时间没有天然感知，让它先执行 `date` 确认时区再判断，否则日报会在奇怪的时间出现。
5. **忘了 `NO_REPLY`**。不写这条，多数模型每次心跳都会"礼貌性"汇报——第一天你就会把心跳关掉。

## 可复用建议

- **分工要清楚**：心跳管判断，cron 管精确调度，手动消息管临时指令，三者不越界，Agent 才稳
- 所有跨心跳的状态**落盘成文件**，不依赖会话记忆
- `HEARTBEAT.md` **进 git**，改指令像改代码一样有记录、可回滚
- 上线后先观察一周心跳行为日志，再回头调间隔和指令粒度

## 总结

HEARTBEAT.md 的价值不在"自动化"本身，而在于把你的偏好固化成一份常备指令：Agent 每次醒来都知道该看什么、什么值得打扰你、什么该沉默。写好这二十行，它才从应答机变成一个真正在值守的助手。
