## 背景

OpenClaw 这类常驻 agent 和普通聊天机器人的核心区别在于**主动性**：它不需要用户每次手动触发，而是会周期性“醒来”检查有没有该做的事。典型实现是 heartbeat 机制——agent 每隔 N 分钟收到一条系统级心跳消息，按照 `HEARTBEAT.md` 里的清单逐项判断，有活就干，没活就静默返回。

但只要做主动性，就绕不开一个架构问题：**事件怎么到达 agent？** 是定时轮询，还是事件源主动推送？

## 问题

两种方式的代价结构完全不同：

- **轮询**：实现简单，agent 只需要一个定时器。但每次唤醒都要消耗 token 和上下文窗口，绝大多数心跳其实是空转——磁盘没满、日历没变、邮件没来。间隔短了成本高，间隔长了时效差。
- **推送**：实时性好、无空转。但前提是事件源支持 webhook（或 IMAP IDLE 这类长连接），且 agent 的 gateway 得能被回调到——本地部署时往往涉及内网穿透，还要自己处理认证、重放和去重。

实际项目里纯粹选一种通常都不划算，问题变成**怎么分层组合**。

## 做法

我的实践路径，供参考：

1. **先盘点事件源**。能推送的（GitHub webhook、监控告警、邮件）走推送；只能轮询的（本地文件、无 webhook 的第三方 API、电池/磁盘这类状态检查）走心跳。
2. **心跳间隔分层**。默认 30 分钟兜底，高关注任务单独配 5 分钟，并设置 active hours，避免深夜空转烧 token。
3. **HEARTBEAT.md 写成精简 checklist**，明确约定“所有条件不满足就静默返回”，不产生任何用户可见回复。
4. **关键事件走推送通道**：webhook → 本地 gateway → 以高优先级消息注入当前会话，绕过轮询延迟。
5. **加冷却与去重**。同一事件源设最短触发间隔，防止告警风暴把会话刷爆。

## 踩坑点

- 心跳从 10 分钟调到 2 分钟试过一次，当月 token 用量翻了几倍，而真正触发的动作不到心跳总数的 5%。
- 早期没写静默约定，agent 每次心跳都回一句“暂时没什么事”，体验极差。
- webhook 打到内网机器上根本不可达，最后要么开 tunnel，要么退化成 30 秒长轮询——提前确认网络拓扑能省一晚上。
- 心跳任务和用户会话并发写同一个文件，出现过内容互相覆盖，后来把心跳触发的写操作收敛到独立工作区。
- 笔记本合盖休眠期间心跳全部丢失，唤醒后积压任务一次性涌入，需要做唤醒后的合并处理。

## 可复用建议

- 选型判断：**延迟敏感且事件源支持 webhook → 推送；状态型检查 → 轮询；两者都可行 → 低频轮询兜底 + 变更时推送**。
- 心跳回复默认静默，只有 checklist 条件命中才“开口”。
- 把心跳本身也纳入观测：记录每次心跳的耗时和触发率，空转率持续偏高就说明间隔该调大了。

## 总结

heartbeat 设计的本质是**用 token 换时效**。不必追求全推送的架构复杂度，也别忍受高频轮询的资源浪费：分层间隔、静默默认、关键事件走推送，是目前实践下来最稳、最省心的组合形态。先把 checklist 收敛好，再谈频率，顺序不要反。
