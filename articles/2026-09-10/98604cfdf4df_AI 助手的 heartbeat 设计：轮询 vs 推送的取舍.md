## 背景

OpenClaw 的 heartbeat 是个容易被低估的机制：网关按固定间隔唤醒 agent，模型看一眼当前状态，没事就返回 `HEARTBEAT_OK`，有事才真正干活。很多人第一次搭自动化时会陷入两难：所有事都靠 heartbeat 轮询，延迟和 token 成本吃不消；全部改成推送（webhook / 事件回调），又要在本地环境里折腾入口和重试。这篇聊聊我们实际用下来怎么取舍。

## 问题

先拆开看两种模式的真实代价：

- **轮询**：延迟期望值约为间隔的一半；每次唤醒都要付出固定的上下文开销，哪怕 99% 的唤醒无事发生。
- **推送**：时效好、空闲零成本，但要求事件源能打到你的网关——公网可达、证书、重试、幂等、削峰，全要自己管；NAT 后的家用机直接不可达。

## 做法

1. **按触发源给任务分类**。外部系统产生的事件（消息、CI 结束、监控告警）倾向推；自己手里的低频巡检（每日摘要、日历检查、目录变化）倾向轮询。
2. **高时效链路走推送**：webhook 进网关，入口处做去抖（比如 5–10 秒窗口合并）和幂等键，先落队再交给 agent，避免事件洪峰直接打爆会话。
3. **巡检类走 heartbeat**：间隔宁长勿短，30 分钟起步；心跳 prompt 写死「无事则只返回 OK」，把每次唤醒的固定成本压到最低。
4. **保留一条长间隔心跳做对账**：推送可能丢，任务可能静默失败，让心跳兜底做自检和补漏。
5. **加观测**：记录每次唤醒的来源（heartbeat 还是事件）、耗时、token 消耗，跑一周再调参，不要拍脑袋。

## 踩坑点

- 心跳间隔设到 1–2 分钟：token 消耗翻几倍，且心跳 run 和用户对话抢同一个 session 锁，聊天开始排队。
- webhook 重试没做幂等，同一条告警触发两次，agent 重复执行了有副作用的操作。
- 在心跳回调里跑重活（批量抓取、大文件处理），阻塞主循环，正常消息全被拖住。重活应该丢队列异步做。
- 本地部署以为「配了 webhook 就有推送」，实际 NAT 后根本收不到，任务看起来「没触发」，其实从未到达。
- 笔记本休眠唤醒后定时器堆积，一次性补触发 N 次心跳，需要合并或跳过错过的周期。

## 可复用建议

- 一句话决策：**事件源在你控制不到的地方，就让它推；状态在你自己机器上、频率低，就轮询。**
- 拿不准就先长间隔轮询起步，等出现「延迟不可接受」的真实痛点再上推送，不要为想象中的时效性提前付复杂度。
- 所有推送入口必备三件套：幂等键、去抖窗口、失败落盘。
- 心跳 prompt 保持极简，是省钱最有效的一招。

## 总结

轮询和推送不是二选一，而是分层：**推送保时效，心跳保底账**。一个务实的默认配置是——事件走 webhook + 幂等去抖，巡检走 30–60 分钟心跳，另留每小时一次的对账心跳。跑一周看观测数据再收敛参数，比一开始追求「完美架构」划算得多。
