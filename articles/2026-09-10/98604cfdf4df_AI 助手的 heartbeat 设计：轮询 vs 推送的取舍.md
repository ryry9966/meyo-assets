# 心跳 vs 推送：常驻 Agent 的唤醒机制怎么选

## 背景

OpenClaw 这类常驻 Agent 有一个核心问题：它得自己知道"什么时候该干活"。目前主流的 heartbeat 方案是轮询式的——网关按固定间隔唤醒 agent，agent 读一份 checklist（比如 `HEARTBEAT.md`），有事就处理，没事就静默跳过。另一条路线是推送：事件源通过 webhook、消息队列或文件监听，主动把事件喂给 agent。

两条路线我们都在生产里跑过，这篇记录一下取舍逻辑。

## 问题

- **轮询**：响应延迟 ≈ 心跳间隔；成本 = 每次唤醒的 token 消耗。间隔调短烧钱，调长了 agent 变"钝"。
- **推送**：延迟低，但链路长（事件源 → 网关 → agent），任何一环挂了事件就丢。更麻烦的是，从 agent 视角看，"没有事件"和"事件丢了"无法区分。
- 纯推送的 agent 宕机期间错过的事件不会自动补；纯轮询的 agent 对即时消息响应太慢。单选一条路都有明显短板。

## 做法：推送做触发，心跳做兜底

1. **事件分类**。需要"人可感知及时性"的事件（用户消息、告警、定时提醒）走推送；自维护类动作（整理记忆、检查任务列表、对账）走心跳。
2. **心跳承担对账**。每次心跳对比"上次成功处理的时间戳"，把推送空窗期丢失的事件补齐。这是心跳存在的核心理由——它保证正确性下限。
3. **心跳瘦身**。checklist 放文件里按需读取，不塞进常驻上下文；无事项时直接 skip，不触发模型调用，或用极小上下文调用。
4. **推送加幂等**。事件带唯一 id，agent 侧去重，防止 webhook 重试导致重复执行。
5. **间隔自适应**。空闲时段拉长（如 30 分钟），有活跃任务时缩短（如 5 分钟），写成配置项而不是硬编码。

## 踩坑点

- **心跳污染上下文**：早期我们把每拍心跳都写进会话，几小时后上下文全是心跳日志，模型开始认真"回应"心跳。改法：心跳走独立通道，结果为空不进会话。
- **静默跳过不彻底**：prompt 里没写死"无事项则不输出"，agent 把"没事"也当任务汇报，一晚上产出几百条废话。
- **webhook 无重试**：事件源一次请求失败就丢，最后靠心跳对账才发现积压了一整天的通知。
- **定时漂移**：用固定间隔的实现，机器休眠恢复后心跳连拍多次，瞬间打爆配额。要用"下次执行时间"而非 `setInterval` 语义。
- **对账没测断线场景**：进程重启后时间戳丢失，触发全量重放，重复执行了一批任务。时间戳要持久化，不能只放内存。

## 可复用建议

- 选择标准一句话：**延迟敏感走推送，正确性敏感走心跳对账**。两者是分工，不是二选一。
- 心跳成本要可预算：间隔 × 单次 token 上限，写进配置，避免某次 checklist 膨胀后费用悄悄翻倍。
- 任何推送通道上线前先回答一个问题："宕机期间的事件去哪了？"答不上来，就等于没有可靠性，必须有心跳兜底。

## 总结

轮询和推送不是优劣关系，而是兜底与触发的分工。对 OpenClaw 这类常驻 agent，比较稳的形态是：**推送负责快，心跳负责全**——推送丢了心跳能补，心跳贵了推送能省。把这两个机制当成互补层来设计，比纠结"哪个更先进"务实得多。
