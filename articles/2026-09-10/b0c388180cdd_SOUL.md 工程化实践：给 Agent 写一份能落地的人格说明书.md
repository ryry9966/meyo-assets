## 背景

OpenClaw 的 agent 每次会话启动时会加载 workspace 下的几个 Markdown 文件：`AGENTS.md` 管行为规则，`SOUL.md` 管人格。很多人的做法是装完框架直接跳过 SOUL.md，或者原样留着默认模板——结果就是 agent 时而过度热情、时而突然谨慎，长会话里人格还会漂移。

## 问题

实际用下来有三个典型痛点：

1. **默认人格太"通用助手"**：和具体使用场景（运维、写作、个人助理）不匹配，回复风格总是那套客服腔；
2. **边界不清**：agent 会自作主张执行危险操作，或者在该停下来确认时直接往下冲；
3. **人格漂移**：会话拉长后，语气和谨慎程度逐渐偏离初始设定，口头纠正只能管一轮。

## 做法

我的 SOUL.md 现在固定在 50–60 行，分四段写：

1. **身份核心（5–8 行）**：一句话定义角色和服务对象。例："你是我的个人技术助理，主要服务对象是我一个人，不是泛化用户。"
2. **语气与表达**：不写"友好、专业"这类空词，写具体规则。比如"回复默认简短，先给结论再给细节；不确定时直说不确定，禁止编造。"
3. **硬边界（最重要）**：列出禁止项和必须确认项。例："删除文件、对外发消息、涉及花钱的操作，必须先列出计划等我确认；不主动重构我没有要求的代码。"
4. **升级规则**：给一个判断标准而不是罗列场景。"可逆且影响面只在我自己 → 直接做；不可逆或涉及他人 → 先确认。"

写完后用一组固定的 10 个测试 prompt 跑一遍（包含故意诱导的"帮我直接删掉所有日志"），确认边界生效，再提交 git。

## 踩坑点

- **写太长**：早期我写了 200 行，注意力被稀释，边界反而更容易被绕过。控制在模型能"整段记住"的量级。
- **形容词不约束行为**："要有分寸"没有信息量，"未经确认不执行删除类操作"才有。
- **和 AGENTS.md 打架**：两个文件对同一行为给出矛盾指令时，行为不稳定。定期检查重叠部分，同一规则只放一处。
- **子 agent 不一定继承**：派生的 subagent 主要读 AGENTS.md，SOUL.md 里的语气设定可能丢失。安全相关的硬约束要写进 AGENTS.md 或系统提示，别只写在 SOUL.md 里。

## 可复用建议

- **当持久化补丁用**：每次人格不符合预期，别口头纠正了事，回写进 SOUL.md，这样修一次管所有后续会话。
- **用 diff 思维维护**：一次只改一处，改完跑同一组测试 prompt，避免"调一处崩三处"。
- **边界放前部**：优先级最高的内容放文件开头，别埋在抒情段落后面。
- **每季度重读**：使用场景变了，人格也要跟着改，过期设定比没有设定更危险。

## 总结

SOUL.md 本质上是一份用自然语言写的 policy 文件。它不神秘，也不万能——真正的可靠性来自四个字：**短、具体、可测试、进版本库**。把人格当配置管理，而不是当玄学，agent 的行为才会稳定下来。
