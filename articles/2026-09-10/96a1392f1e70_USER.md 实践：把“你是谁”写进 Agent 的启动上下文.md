## 背景

大模型 Agent 的会话是无状态的。项目侧我们有 AGENTS.md / CLAUDE.md 这类约定文件解决“这个仓库怎么干活”，但“我是谁”这一层长期缺位：我用什么系统、什么运行时、偏好哪种命名风格、哪些目录不许碰——这些信息要么每次开场手动复述，要么散落在历史对话里，Agent 每次都靠猜。

我在 OpenClaw 的日常使用中，把这层信息固化成一个 USER.md，随会话启动注入。跑了几个月，维护成本极低，收益稳定，值得写下来。

## 问题：Agent 对你的默认假设几乎都是错的

不提供用户侧上下文时，Agent 的行为由训练分布决定：

- 你是 macOS 本机 + 远程 Linux 混合开发，它默认给单平台命令；
- 你用 pnpm，它给 npm；你跑在 NAS 上而非云主机，它给 systemd 而不是你实际的 Docker Compose；
- 你希望先结论后细节，它每次铺垫三段。

单次纠正不贵，贵的是每周纠正二十次。

## 做法

**1. 定位置、定边界。** 我放在 `~/.openclaw/USER.md`，随会话引导注入。明确分工：USER.md 描述“人”，项目根目录的 AGENTS.md 描述“仓库”，两者不重复。

**2. 控篇幅、用声明式短句。** 全文压在 60 行以内，bullet 列表，现在时态，不写叙事。模型检索的是事实点，不是文章。

**3. 按稳定度分层。** 不变的事实放上面（技术栈、目录约定、沟通偏好），易变的加日期标注，过期就删。

模板（可直接抄）：

```markdown
# USER
## 环境
- 主力机: macOS 15 (arm64)；远程: Ubuntu 22.04 NAS (Docker Compose)
- Python 3.12 / Node 22，包管理用 pnpm，不要建议 npm
## 编码偏好
- 正式项目：类型标注、模块化、先写测试；临时脚本可从简
- 不修改 ~/scripts/ 以外的路径，除非明确要求
## 沟通
- 先结论后细节，中文回复，代码注释用英文
- 不确定时问一句，不要自行假设部署目标
## 已验证事实
- 2025-06: NAS 上 80/443 已占用，新服务统一走 8xxx 端口
```

**4. 定义优先级。** 项目文件与 USER.md 冲突时项目优先。把这条规则写在文件开头，实测能明显减少 Agent 在别人仓库里套用你个人偏好的情况。

**5. 当代码维护。** 放进 dotfiles 仓库走 git，改动有提交记录；每季度清理一次。

## 踩坑点

- **写太长。** 早期我写到 200 行，关键偏好被稀释，Agent 反而漏掉。压缩到 60 行后命中率明显回升——上下文注入是零和的，每一行都在和你的任务抢注意力。
- **塞敏感信息。** 密钥、内网真实 IP、客户名不要进 USER.md，尤其这个文件会同步、会进 git。写“密钥从环境变量读取”这类规则，而不是值本身。
- **偏好被当成硬约束。** “回复要简短”曾让它在排查复杂问题时也只给一行结论。改成带作用域的表述：“日常问答简短；排障场景给完整推理。”
- **过期事实比没有更糟。** 它会自信地引用你三个月前的版本号。易变信息务必带日期，定期修剪。

## 可复用建议

- 判断标准很简单：**同一条纠正说过三次以上，就进 USER.md。**
- 建设顺序：先把 AGENTS.md（项目层）做扎实，再补 USER.md（个人层），最后才是会话记忆。层次反了会互相污染。
- 写完做一次验证：新开会话问 Agent“你对我的环境了解多少”，能复述出 80% 即合格。

## 总结

USER.md 不是记忆，是声明——把散落在对话里的用户上下文，收敛成一份可版本化、可审计的静态文件。它的杠杆在于：一次维护，所有会话受益。先从 30 行写起，比完美方案更重要的是，现在就有一个。
