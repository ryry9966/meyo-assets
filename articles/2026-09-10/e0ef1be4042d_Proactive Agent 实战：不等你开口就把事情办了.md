## 背景

绝大多数 AI 助手的工作模式是“你问我答”，它不会主动发现你该看的东西。但在 OpenClaw 这类常驻型 agent 框架里，助手本来就有长期运行、通过 MCP 接工具、走渠道推消息的前提——这意味着它完全可以具备 proactive 能力：定时巡检、监听事件、条件满足时先干一步，再把结果推给你。

## 问题

主动性是双刃剑。做少了，它还是个高级聊天框；做多了，它每十分钟发一条“我检查了一下，没事”，三天后你就把它静音了。此外，无人值守执行有真实的权限风险：一个凌晨三点跑的 cron 任务拿着写权限，出错时没人盯着。所以核心问题不是“能不能主动”，而是：**什么时候该主动、主动到什么程度、出了事谁兜底。**

## 做法：sense → judge → act → report

我在自己环境里落地了一条四段流水线：

1. **触发层**：cron 任务 + webhook 两个入口。cron 负责周期巡检（每天早上汇总 RSS、日历、仓库动态）；webhook 负责事件驱动（CI 失败、issue 被打标签）。OpenClaw 的 scheduled job 直接挂 cron 表达式即可。
2. **判断层**：这是关键。触发不等于打扰。我给 agent 一条明确的门禁规则：先评估“值不值得打断用户”，用廉价模型初筛，只有命中阈值（错误率突增、deadline 邻近）才升级。日常内容攒进 digest，固定时间合并推送一次。
3. **执行层**：默认只读。巡检任务只能读 RSS、读日志、读 repo；写操作（建 issue、给第三方发消息）一律二次确认或走白名单。权限按任务粒度授予，不共用一个大 token。
4. **回报层**：所有主动行为——包括“判断为不值得打扰”的那些——都写进一条审计频道。既能回溯误判，也为调阈值积累数据。

## 踩坑点

- **噪音失控**：初期没有 digest 机制，每次巡检都推送，两天就被静音。合流 + 固定推送窗口是第一优先级。
- **静默失败**：无人值守任务挂了没人知道。给每个定时任务加心跳，超时未上报就在审计频道报警。
- **重复触发**：webhook 重试导致同一事件执行两次，写操作必须带幂等键。
- **陈旧上下文**：agent 基于三天前的状态文件做判断。主动任务每次运行都要先刷新状态，缓存不要跨任务复用。
- **成本**：初筛用便宜模型，写摘要和决策才上大模型，月账单差一个量级。

## 可复用建议

- **触发与策略分离**：cron 只管到点醒来，值不值得行动由判断层决定，调频率不改代码。
- **先 dry-run**：新增主动任务先跑一两周“只记录不执行”，人工 review 后再放开。
- **留一个降频口子**：让用户能用一句话说“这种事以后别单独推我”，agent 要能理解并持久化这条偏好。
- **量化主动性**：核心指标是“被打断次数 / 有价值的打断数”，定期看这个比值，高于 0.5 就该收紧阈值。

## 总结

Proactive 不是把自动化堆得更满，而是让 agent 学会克制地打断你。工程量的大头不在触发器，而在判断规则、权限边界和反馈回路。先用只读巡检建立信任，再逐步放开写能力——这条路走得慢，但不翻车。
