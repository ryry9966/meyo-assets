## 背景

Agent 接上 MCP 工具、插件和 shell 之后，真正难的不再是"能不能做"，而是"该不该自己做"。跑一次只读检索可以放手，发一条对外消息要不要等人点头，删一批文件之前要不要拦截——每个团队都在回答这些问题，但多数是凭感觉答的。

## 问题

实践里两种失败模式都很常见：

- **问得太多**：每一步都弹审批，人很快就退化成无脑点"允许"的橡皮图章。审批疲劳比没有审批更危险，因为它在训练人忽略提示。
- **问得太少**：agent 在一次自动执行里删了数据表、给客户群发了消息、或者烧掉一笔预算。事后复盘会发现，出事的动作几乎都不是"agent 不会做"，而是"没人定义过这件事需要问"。

根因是：边界靠直觉画，而不是靠标准画。

## 做法：用两个维度切三层

建议用**可逆性**和**爆炸半径**两个维度做判断：

- 可逆性：出问题能不能撤回？有 git、有 dry-run、有备份的算可逆。
- 爆炸半径：影响范围是工作区内部，还是会触达外部系统、其他人、真实资金？

据此分三层：

1. **T0 自动执行**：只读、工作区内、完全可逆。读文件、搜索、lint、本地计算，不需要人。
2. **T1 带护栏自动执行**：工作区内的写操作。可以自动跑，但强制走 git 提交 + diff 留痕，跑在沙箱里，工具按 allowlist 配置。人 review 结果，而不是逐步审批。
3. **T2 必须问**：一切跨边界的动作——对外发送（邮件、评论、发布）、支付、超规模的删除、权限变更、schema 变更。这类 MCP 工具显式标记为需要确认，审批回调里展示真实参数和影响范围，而不是一句"我要调用工具 X"。

落地方式：把这套策略写成配置进版本库，像 review 代码一样 review 权限策略；所有自动执行的动作留审计日志（工具名 + 参数 + 结果摘要）。

## 踩坑点

- **审批疲劳**：一天弹 40 次确认，人会全部通过。宁可把低风险动作全部放行，把弹窗留给真正值得停 3 秒的事。
- **"只读"不等于安全链路**：注入可以藏在只读工具的返回内容里，诱导 agent 去调写工具。不能因为"第一步是读"就放开后续写——T2 工具无论如何留在审批后面。
- **批量操作别逐条问**：agent 要改 50 个文件，弹 50 次窗是灾难。支持"先 dry-run 汇总 diff，一次审批整体执行"的模式。
- **"本会话总是允许"会蠕变**：会话级授权很方便，但要设过期时间，且范围限定到具体工具，不要一放放一片。
- **没测过拒绝路径**：多数团队只测了批准后的表现。在测试里主动拒绝一次审批，确认 agent 能优雅降级（报告并停止），而不是绕路找别的工具硬干。

## 可复用建议

- 对有外部副作用的工具默认拒绝，逐个显式开启。
- 工具设计得小而类型化；一个"万能执行"工具会逼你只能在整体放行和整体锁死之间二选一。
- 每条自动执行路径，事后都要能回答三个问题：做了什么、依据什么、能不能撤。
- 审批弹窗本身是 UI 产物，认真设计：展示 diff、参数、影响范围，别只给一个"允许/拒绝"。

## 总结

权限边界 = 可逆性 × 爆炸半径：两个都低就自动干，任何一项高就停下来问。目标不是"多问"或"少问"，而是**问得少、但问在刀刃上**。策略进版本库、动作留日志、拒绝路径也要测——这三件事做到，agent 的自主性才敢往上加。
