## 背景

Agent 的能力上限，往往不取决于模型本身，而取决于它能调用哪些工具。模型再强，拿不到工单系统、数据库、消息通知的接口，就只能纸上谈兵。OpenClaw 作为偏工程化的 agent 运行框架，与外部服务的对接方式直接决定自动化任务的落地质量。这篇帖整理我们团队近期对接内部若干 REST 服务时的做法，供参考。

## 问题

直接把 API 丢给 agent，通常会撞上四类问题：

1. **模型不知道怎么调**：参数 schema 含糊、工具描述模糊，调用命中率低；
2. **返回值失控**：一个接口返回 8KB 的 JSON，几轮对话就把上下文撑爆；
3. **鉴权与泄露**：key 写在配置里，随调用被带进 prompt 或日志；
4. **副作用不可控**：写操作被模型重试，产生重复工单、重复下单。

## 做法

我们的标准路径是：**用一层薄的 MCP server 包住外部 API**，而不是让 agent 直接发 HTTP。

1. **盘点接口，划定边界**。只暴露 agent 真正需要的操作，一个服务通常 5–10 个工具足够，不是 API 有什么就给什么。
2. **设计工具签名**。命名用"动词_宾语"（如 `create_ticket`、`query_order`），参数用严格 JSON Schema，枚举值尽量用 enum 而非自由字符串。
3. **裁剪返回值**。在 MCP server 里做字段过滤和扁平化，只返回模型决策所需的字段，大列表强制分页。
4. **鉴权集中在 server 侧**。密钥放环境变量或密钥管理服务，工具的输入输出中永远不出现凭据。
5. **错误要"可推理"**。不要只返回 `failed`，返回结构化错误：错误码、可读原因、建议动作（如"date 格式应为 YYYY-MM-DD"），模型才能自我修正。
6. **超时与重试在 server 侧兜底**。设 10–30 秒超时；读操作可自动重试，写操作不自动重试，交给 agent 决策。

## 踩坑点

- **写操作必须考虑幂等**。`create_ticket` 早期没做幂等，模型在网络超时后重试，一天造了十几张重复工单。后来加了幂等键参数和执行前确认机制才解决。
- **工具数量爆炸**。一度注册了 40+ 工具，模型选择正确率明显下降。按业务域拆成多个 MCP server、按任务动态加载后恢复正常。
- **描述要写给模型看**。"查询订单"不如"按订单号或时间范围查询订单状态，返回金额与物流信息"。描述里写清参数示例和边界条件，命中率提升明显。
- **日志脱敏**。工具调用参数会进日志，手机号、token 之类必须在 server 层做替换，否则排查问题时自己先中招。

## 可复用建议

- 一个服务一个 MCP server，wrapper 保持薄，不放业务逻辑；
- 每个工具配 3–5 条测试 prompt，改动后跑一遍回归；
- 写操作提供 `dry_run` 参数，先预览再执行；
- 工具签名变更视为接口变更，加版本号管理。

## 总结

对接外部服务的本质，是把"给人用的 API"翻译成"给模型用的工具"。在 OpenClaw 侧做好 MCP 封装、凭据隔离、输出裁剪和副作用控制，agent 的稳定性会有数量级的改善。工具设计值得投入时间——它比换模型便宜，见效也更快。
