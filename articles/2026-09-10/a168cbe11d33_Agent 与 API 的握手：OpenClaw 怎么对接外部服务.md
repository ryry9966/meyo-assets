## 背景

Agent 的价值不在“会说”，而在“能做”。LLM 本身只是推理引擎，真正让它落到业务上的，是把外部 API 包装成模型可理解、可调用的工具。OpenClaw 里这条链路通常有两种做法：在插件里直接注册 tool，或者跑一个 MCP server 把能力以标准协议挂进来。无论哪种，本质相同：把一个 HTTP 接口翻译成一段模型能读懂的 schema，并保证调用结果模型能正确消化。

## 问题

实际对接中，最常见的失败不是“调不通”，而是调通了但结果不可用：

- schema 描述与真实 API 行为不一致，模型传参靠猜；
- 接口报错返回裸 JSON 或整页 HTML，模型把错误当数据继续推理；
- 大响应原样灌进上下文，几轮对话后 token 爆掉；
- 慢接口阻塞 agent 主循环，用户侧表现为“卡死”。

## 做法

以给 OpenClaw 挂一个内部订单查询 API 为例，我沉淀下来的稳定流程是五步：

1. **先定契约再写代码。** 工具名用动词+名词（如 `query_order`），description 写清“什么时候该用、什么时候不该用”。这段描述本质是 prompt，值得花时间打磨。
2. **参数收敛。** JSON Schema 里给每个参数标注类型和枚举，日期统一格式。能收敛成单值的，就不要让模型自由发挥字符串。
3. **认证隔离。** API key 走环境变量或配置中心，工具代码只读引用，绝不把凭证拼进任何返回给模型的字符串。
4. **响应整形。** 这是收益最大的一步。上游返回不要原样透传，裁剪成结构化短对象：

```json
{
  "status": "ok",
  "order_id": "A1024",
  "state": "shipped",
  "updated_at": "2025-06-01"
}
```

错误也一样，显式区分 `retryable: true/false`，模型才知道该重试还是该换路。

5. **超时与重试放在工具层。** timeout、退避重试、限流都在工具实现里兜底，不要指望模型自己“等一等”。超过 3 秒的接口，考虑改成提交任务 + 轮询的异步模式。

## 踩坑点

- **description 写得太泛。** “查询订单信息”不如“按订单号查询物流状态；不知道订单号时先调用 `list_orders`”。模型选工具主要靠这段话。
- **裸透传上游响应。** 一次 404 页面的 HTML 进上下文，比十次正常调用还费 token。
- **错误只有一句 "failed"。** 模型无从判断，轻则瞎编结果，重则陷入重试循环。错误对象里要给原因和建议动作。
- **schema 与线上接口漂移。** 上游加了必填字段，工具没更新，模型每次调用都失败。schema 的契约测试要进 CI。
- **日志打全量请求。** 密钥和用户数据容易从这里漏出去，工具层日志必须脱敏。

## 可复用建议

- 一个工具只做一件事，拒绝“万能工具”——参数越多，模型传错概率越高；
- 返回值永远带 `status` 字段，给模型明确的成功/失败信号；
- 工具层加 trace id 并记录每次调用，排障时你会感谢自己；
- 上游接口再脏，也在适配层消化掉，保持 agent 侧 schema 干净稳定。

## 总结

对接外部服务的核心不是“调通 HTTP”，而是设计一份模型与 API 之间的翻译契约：schema 说清边界，响应整形控制成本，错误显式传达意图，超时重试在工具层兜底。把这四件事沉淀成模板之后，OpenClaw 里每接一个新服务，都只是填空题。
