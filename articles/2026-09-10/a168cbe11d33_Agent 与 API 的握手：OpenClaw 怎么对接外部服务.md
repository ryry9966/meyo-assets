## 背景

Agent 的价值在于"能动手"。OpenClaw 的推理和编排能力再强，如果不接外部服务——查库存、发工单、调内部 RPC——就只能停在聊天层面。OpenClaw 对接外部服务常见三条路径：MCP Server、原生插件（plugin）、直接注册的 function tool。三者本质是同一件事：**把一个 HTTP/RPC 接口包装成模型可理解、可稳定调用的工具**。

## 问题

实际对接中最常见的失败不是"连不上"，而是"连上了但不可靠"：

- 模型幻觉出不存在的参数或端点；
- 鉴权凭证写死在配置里，甚至被带进上下文；
- 超时、限流没有统一处理，一次失败拖垮整轮任务；
- 工具描述含糊，该调 A 工具时模型调了 B。

## 做法：五步握手

**1. 先选路径。** 标准协议、第三方服务优先 MCP，社区现成 server 多；内部系统或需要定制逻辑的，写 OpenClaw 插件自己控粒度；一次性脚本需求直接注册 tool 函数，别过度设计。

**2. 定义工具 schema，宁窄勿宽。** 参数尽量用 enum 收紧，description 写清"什么时候用、什么时候不该用"。描述是给模型看的文档，写得越像接口文档，调用越稳。

**3. 鉴权走环境变量或密钥管理。** 插件层注入请求头，凭证绝不进 prompt、不进日志。

**4. 统一封装失败语义。** 超时设 10 秒左右，重试用指数退避、最多 2 次；错误信息翻译成人话返回给模型——它知道失败原因才能自我修正，看到裸堆栈只会乱猜。

**5. 日志落盘。** 每次调用记录工具名、参数摘要、耗时、状态码。排障时这是唯一可靠的证据，别依赖模型复述"我刚才做了什么"。

## 踩坑点

- **工具越多越乱**：实测超过 15 个工具，选错率明显上升。按场景分组，用插件的启用/禁用控制可见性。
- **返回值塞爆上下文**：一个接口吐 5000 条 JSON 会直接打爆窗口。封装层做分页或截断，返回摘要 + 游标，让模型按需翻页。
- **把幂等想当然**：写操作必须考虑重试导致的重复下单、重复发消息，关键操作加幂等键。
- **接口本身没调通就写工具层**：接口的问题别留给 agent 调试，先用 curl 跑通再封装。

## 可复用建议

- 每个外部服务独立一个封装模块，HTTP 细节不散落在工具函数里；
- 给高风险操作（写库、发消息、删数据）加 `dry_run` 参数，默认只读，确认后再放开；
- 上线前跑一轮对抗测试：故意传错参数、断网、mock 限流，观察 agent 是崩溃、死循环还是优雅降级；
- 工具版本化管理，改 schema 时旧调用链可回溯。

## 总结

对接外部服务的核心不是"接上"，而是"接稳"。把鉴权、超时、重试、错误语义这些工程问题解决在封装层，模型只需要面对一组语义清晰的工具，握手才算真正完成。OpenClaw 的 MCP 与插件机制已经把管道铺好了，剩下的功夫都在接口之外。
