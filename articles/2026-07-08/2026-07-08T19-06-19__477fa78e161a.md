最近 36kr 的一条热搜在工程圈和创业圈炸开了锅——"AI Native 组织转型：岗位，不再以人为单位"。听起来像又一句 HR 黑话，但仔细拆解，背后是组织架构、岗位定义、绩效考核、协作链路的一整套重构。RY 哥今天就把这话题掰开揉碎，看看"以岗位为单位"到底意味着什么、能省多少成本、又会踩哪些坑。



## 一、"岗位不再以人为单位"到底在说什么

传统组织里，一个岗位 = 一个具体的人 + 一份 JD + 一组汇报关系。人离职，岗位就跟着缺位，知识沉淀靠交接文档（往往还没写完）。

AI Native 组织的思路是：**岗位 = 一组任务流 + 人 + AI Agent 的组合**。人不一定是任务的唯一执行者，AI Agent 可以承担其中 30%~70% 的标准化环节，人负责决策、判断、例外处理、跨域整合。

举例来看：

- **内容运营岗**：选题由人定，但资料检索、初稿、配图、SEO 优化由 Agent 完成，人做编辑和发布决策
- **客服岗**：一线问答由 Agent 处理，人处理投诉升级、情感安抚、合规判断
- **数据分析岗**：取数、清洗、可视化由 Agent 完成，人负责定义问题、解读结果、推动业务落地
- **研发岗**：单元测试、文档生成、CR 初筛交给 Agent，人负责架构决策、复杂调试、跨团队协议设计

岗位里的"人"和"AI"比例不是固定值，而是按任务复杂度、风险等级、数据可得性动态分配。RY 哥把它叫做"任务粒度的混编"——比"岗位粒度的人"灵活得多。



## 二、AI Native 组织与传统组织的差异

把两个模型摆到一张表里对比，差异比想象中更结构化：

| 维度 | 传统组织 | AI Native 组织 |
| --- | --- | --- |
| 岗位定义 | 围绕人写 JD | 围绕"任务流"定义能力组合 |
| 协作单元 | 部门 / 小组 | 人 + Agent 的临时 task force |
| 绩效考核 | KPI / OKR 到人 | 任务完成质量到"人 + AI 组合" |
| 知识沉淀 | 文档 / Wiki（人写） | Agent memory + 可复用 prompt |
| 招聘逻辑 | 招"全栈岗位" | 招"稀缺判断力 + AI 协同力" |
| 决策链路 | 层层汇报 | 数据 + Agent 推理 + 人拍板 |
| 成本结构 | 人力成本为主 | 算力 + token + 人力混合 |

核心差异只有一个：**组织的最小单位从"一个人"变成了"一段任务 + 人 + AI"**。这意味着组织可以以任务为粒度做编排，而不是以人头做编排。从工程视角看，这是从"单体应用"走向"微服务 + 编排层"的组织版本。

一个直接后果：原本一个 senior 岗位的产能，可能由"一个 senior + 三个 Agent"的组合完成 3~5 倍的工作量。但前提是任务流被正确拆解、Agent 被正确治理——否则就是"用 AI 把错误放大十倍"。



## 三、岗位解构后，人怎么定位

把岗位拆成任务流以后，人会重新分层。RY 哥按"AI 替不掉的浓度"从高到低分了四层：

1. **判断层**：负责定义"问题对不对""方向选哪个""结果能不能上"——这是 AI 替不掉的部分，也是组织最稀缺的能力。本质上是从信息和推理的海洋里捞出一句话：现在该做什么。
2. **编排层**：负责把任务拆解、分派给合适的 Agent 和人，做流程编排和质量把控。本质上是从"执行者"变成"AI 的产品经理"——需求拆解、prompt 设计、效果评估、迭代闭环。
3. **执行层**：标准化、可复用、低风险的部分，逐步交给 Agent；人只在 Agent 不够稳的场景兜底。比如合同模板填充、报表生成、日志分析、回归测试。
4. **治理层**：合规、安全、数据治理、Prompt 审计、Agent 行为可解释性——这是 AI Native 组织必新增的岗位，传统组织里几乎不存在。

举个例子，以前一个"高级运营"可能既写文案又看数据又做投放。拆解后：写文案交给 Agent，看数据交给 Agent，人聚焦在"这个 campaign 该不该做、预算怎么分、效果不达标要不要砍"。看起来人变"闲"了，其实是把人的注意力从低杠杆动作里解放出来，压到高杠杆决策上。

这也是为什么 AI Native 组织里，"高级"这个词的含义会重写：高级 = 判断密度高，而不是工龄长。



## 四、转型路径与坑

转型不是"买几个 Agent 工具"就完事，RY 哥见过太多团队踩的坑，归纳成四类：

**坑 1：只换工具，不换流程**
买了 Copilot、接了 GPT，工作流还是按老样子走。Agent 产出没人 review，错就直接发出。**正确做法**：先画任务流，识别哪一段适合 Agent，再设计人审节点。流程先行，工具跟进。

**坑 2：Agent 黑箱化，没有可观测性**
Agent 输出错的时候没人能复盘，prompt 改了也没版本记录。**正确做法**：建 Agent 日志、prompt 版本管理、输出可回放，像对待一个 microservice 一样治理 Agent。没有 trace 的 Agent 系统等于黑盒炸弹。

**坑 3：绩效考核还按人头算**
一个人带 3 个 Agent 干了 5 个人的活，绩效却因为"产出看着不多"被打低分；另一个人不用 AI 但加班多，反而拿高分。**正确做法**：把"人 + AI 组合"作为绩效单元，看任务覆盖度、质量、成本三件事。考核的对象变了，考核方法必须跟着变。

**坑 4：忽视治理层**
合规、隐私、幻觉风险没人管。等出事再补就晚了——一次数据泄露或一次严重幻觉输出，够一个团队喝一壶。**正确做法**：从 day 1 就配一个 AI 治理负责人，哪怕兼职，也要有明确的责任主体。



## 五、冷思考与 3 条实用建议

hype 周期里，RY 哥想泼盆冷水：AI Native 不等于"裁掉一半人"，它等于"重新定义人"。短期看是效率提升，长期看是组织能力的重新分层。盲目跟风转型的，先看清自己业务里哪些任务真的可被 Agent 稳定承担，再动手。不是所有岗位都适合解构——高接触、高情感、高例外密度的岗位，强行套 AI Native 反而损失体验。

3 条建议：

1. **先做任务流审计，再做组织调整**。把每个岗位拆成 5~10 个任务，标注每个任务的"AI 可承担度"（0~100%），这是转型的基础数据。没有这张表就谈 AI Native，都是空中楼阁。审计结果往往让人意外：你以为很 AI 化的岗位，可能只有 20% 可承担；你以为很人工的岗位，可能有 60% 可承担。
2. **保留"人审"节点，至少 6 个月**。Agent 在边界场景的稳定性远低于预期，关键决策必须有人兜底。这不是保守，这是工程常识。6 个月后根据 Agent 的实际表现，逐步撤掉低风险节点的人审，保留高风险节点的双签。
3. **投资 Agent 可观测性基础设施**。日志、trace、prompt 版本、输出回放、效果指标——五件套缺一不可。没有可观测性的 Agent 系统等于裸奔，出问题时连 root cause 都定位不到。这部分投入在转型预算里占比建议不低于 20%。

最后一句：AI Native 组织的竞争壁垒，不是模型多强，而是"人 + AI 编排能力"多强。模型是公共品，编排能力是组织资产——这才是这场转型真正的胜负手。
