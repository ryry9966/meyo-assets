36kr 最近一篇文章把"AI助手"推上了热搜——标题挺狠，大意是说 AI 助手是个伪命题。社区里炸开了锅，有人拍大腿说"终于有人讲真话了"，也有人反驳"我用 Cursor 写代码不香吗？你管这叫伪命题？"

RY哥花了一晚上把原文和相关讨论扒了一遍，结论是：这篇文章有干货，但"伪命题"这三个字本身也是个伪命题——它把好几个不同层次的问题打包成了一个口号。今天我们就一层一层拆开看。



## "AI助手"到底在承诺什么

要判断一个东西是不是伪命题，得先搞清楚它在承诺什么。AI 助手这个概念在过去两年被反复包装，核心承诺大致有三层：

1. **全场景通用助手** — 你不用学工具，工具来适应你。无论是订机票、管日程还是写报告，一个入口搞定所有事。
2. **主动决策能力** — 不只是回答问题，而是帮你做决定并执行。你说"安排一下下周的差旅"，它自己查日历、订机票、发邮件通知相关人。
3. **持续记忆与个性化** — 越用越懂你，最终成为你的"数字分身"，知道你的偏好、习惯、甚至决策风格。

这三层承诺的兑现程度差异极大。第一层，部分做到了；第二层，差得远；第三层，基本是画饼。

| 承诺维度 | 现状 | 实际差距 |
|---------|------|---------|
| 全场景通用 | 能聊天、能写文档、能写代码 | 跨工具协作几乎为零，每个 App 各自为战 |
| 主动决策 | 能给建议、能生成方案 | 执行链路断裂，到"动手做"这一步就卡住 |
| 持续记忆 | 上下文窗口从 4K 涨到 128K+ | 真正的长期记忆和人格演化几乎不存在 |

问题不是"AI 助手有没有用"，而是"它承诺的那个终极形态，在当前技术路径下能不能兑现"。把这两件事混为一谈，就会得出极端结论。

## 为什么"助手"叙事出了问题



"助手"这个词本身就有误导性。人类助手是什么？是你交代一件事，他/她能自己拆解任务、协调资源、处理例外情况、最后把结果交付给你。这背后需要四种核心能力：自主规划 + 工具调用 + 异常处理 + 意图深层理解。

现在逐项对照来看：

1. **自主规划** — 单步规划没问题，多步规划容易跑偏。比如"帮我订下周去上海的机票，预算 2000 以内，尽量上午到"，它能理解需求。一旦加上"如果上午没票就改高铁，高铁也没有就改时间"这种条件分支，执行链就开始碎裂。
2. **工具调用** — Function calling 是个好框架，但每个 API 都要预先定义。真实世界的工具组合是无限的，你不可能把所有可能性都枚举出来。而且多工具串联时的错误传播问题非常棘手——第 3 个工具报错了，它不知道是该重试、换工具、还是放弃整个流程。
3. **异常处理** — 遇到报错就傻眼。要么反复重试同样的方法（就像你让一个人修水管，他只会反复拧同一个阀门），要么直接放弃跟你道歉说"抱歉，我无法完成这个任务"。
4. **意图理解** — 表面意图理解不错，深层意图几乎为零。你说"帮我订个会议室"，它不知道你是要开什么性质的会、需要多大场地、有没有远程参会的人。一个真正的人类助手会追问这些，AI 不会。

这就导致了一个尴尬局面：**AI 单点能力在涨，但"助手"的体验感没有同步涨**。因为单点能力涨的是回答质量（更长的回答、更准确的代码、更好的摘要），而助手体验依赖的是系统能力（规划、协调、容错、闭环）。

这就好比你招了个员工，单项技能点拉满了——写 PPT 世界第一。但他不会主动问你需求，不会在素材不够时自己去找，不会在 deadline 快到了时提醒你。你说他是不是个好助手？技术上绝对是，体验上不是。

## 哪些场景是真需求，哪些是伪需求

讨论"伪命题"最怕一刀切。我们把当前 AI 的典型使用场景拆开看。

**真需求（AI 确实在解决问题）：**

- **代码生成与补全**（Cursor、Copilot）— 开发者自己就能验证代码对错，反馈闭环极短，AI 写错了你立刻知道。这是目前 AI 落地最成功的场景，没有之一。
- **文档摘要与信息提取** — 把长文本压缩成要点，不需要多步执行链，单次生成就够了。RAG（检索增强生成）让这个场景越来越靠谱。
- **知识检索与问答** — 替代搜索引擎的初筛功能。以前你要翻 5 页搜索结果，现在 AI 直接给你合成答案。当然幻觉问题还在，但比传统搜索的体验好太多。
- **内容创作辅助** — 起草、润色、翻译。人类在闭环里做质量把控，AI 负责把初稿从 0 变到 80 分，人类从 80 分推到 95 分。分工清晰。

这些场景的共同特点：**反馈闭环短、人类在 loop 里、不需要跨工具协调、出错代价可控**。

**伪需求（听起来美好但用起来别扭）：**

- **"AI 帮你自动管理日程"** — 连你的日历权限、会议室预定系统、同事的日程都搞不定，怎么自动？现在所谓的"AI 日程助手"本质还是个自然语言界面，底下还是传统日历 API。
- **"AI 帮你自动回复邮件"** — 商务邮件的上下文依赖极强。AI 不知道哪些邮件该秒回、哪些该晾着、哪些根本不该回。监督它回复的成本，可能比自己写还高。
- **"AI 帮你做投资决策"** — 先不说准确性问题。你敢让一个不理解你风险偏好、不知道你当下财务状况的系统替你下单吗？出错代价太高。
- **"全能个人助理"** — 什么都想做，什么都做不深。这恰恰是当前 AI 产品最大的陷阱：为了讲一个"助手"的故事，把单点能力之间的断层用 UI 包装起来，用户一用就露馅。

简单判断标准：如果一个场景里，人类花在"监督和修正 AI"上的时间，超过了自己直接做的时间——那这个场景在当前阶段就是伪需求。

## 技术瓶颈：不是模型不够大，是范式不够对

很多人把 AI 助手的问题归结为"模型还不够强"。这只是一半的真相。

另一半是：**当前 LLM 的技术范式在架构层面就不适合做"助手"**。

LLM 本质上是一个 next-token predictor。它的核心能力是"给定上文，预测下一个 token"。这个范式在生成文本时极其强大，但做助手需要的不是"生成"，而是"规划→执行→观察→调整"的闭环。

学术界管这个闭环叫 **agentic loop**，说白了就是：

```
感知 → 规划 → 行动 → 观察 → 调整 → 再行动 ... → 完成
```

现在 LLM 在这个 loop 每一环的表现：

- **感知**：还行，能理解用户输入。多模态后图像、音频也能处理。
- **规划**：单步可以，多步容易丢上下文。规划超过 5 步就开始"忘记"自己最初要干嘛。
- **行动**：能调工具，但工具一多就乱。5 个以上的工具选择，准确率明显下降。
- **观察**：能读结果，但不会判断"这个结果对不对，要不要重来"。缺乏 meta-cognition。
- **调整**：几乎没有。不知道自己不知道什么，所以也不会主动说"我可能搞错了，让我换个思路"。

这不是把模型从 70B 训到 700B 能解决的。需要的是架构层面的变化——真正的 working memory 机制、层次化规划框架、self-reflection 的训练范式。

好消息是，业界已经在往这个方向走了。ReAct、Reflexion、Tree of Thoughts 这些方法都在尝试给 LLM 加上"闭环思考"能力。Anthropic 的 Computer Use、OpenAI 的 Operator 也在试探 agentic 的边界。坏消息是，这些都还处于早期阶段，距离产品级稳定体验还有明显差距。

所以"AI 助手是伪命题"这个说法，更准确的表述应该是：**在当前 LLM 范式下，以"通用个人助手"为目标的 AI 产品，在体验上无法兑现承诺。这不代表方向错了，而是说现在的技术路径还走不到那里。方向是对的，但中间还差几个关键架构突破。**

## 三条冷思考



最后给三条实际可操作的建议，帮你在这个喧嚣的阶段做出务实判断：

**1. 把 AI 当"工具"用，别急着当"助手"用**

工具和助手的区别：工具是你能力的延伸，你决定做什么、怎么做，工具帮你做得更快；助手是你把决策权交出去，让它替你做。当前阶段，AI 在"工具"角色上表现远好于"助手"角色。别急着放权，先用好单点能力——写代码、写文档、做摘要、翻译、信息检索。这些场景里你在 loop 里，质量你自己把控。等 agentic 架构真正成熟了，再逐步放权也不迟。

**2. 用三维框架评估 AI 使用场景**

选 AI 使用场景时，用这个框架快速判断：

- **反馈闭环长度** — 几秒内知道对错？适合用。几天后才知道结果？谨慎。
- **出错代价** — 错了改改就行？适合用。错了造成不可逆损失？别碰。
- **人类监督成本** — 不用时刻盯着？适合用。要全程盯着还不如自己做？当前阶段放弃。

三条都满足，现在就是好场景。三条都不满足，至少等 2-3 年再看。满足一到两条，可以试但别赌。

**3. 盯 Agent 架构进展，而不是模型参数**

判断 AI 助手什么时候能真正落地，看模型参数增长没意义。要关注三个信号：

- 有没有新架构解决 working memory 问题（不是简单加大 context window，而是真正的长期记忆机制）
- 有没有标准化的 tool-use 协议出现（像 HTTP 之于 Web 那样的统一层）
- 有没有产品在 agentic loop 上做出可复制、可规模化的体验（不是 demo，是真实用户日常使用）

这三个信号同时出现的时候，"AI 助手"就从伪命题开始变成真命题了。在那之前，保持期待但别 all in。
