最近，「Claude Fable 5 续命5天，省钱攻略来了」这个话题在技术圈刷了一波屏。核心说的是：在 Claude 的使用配额或免费额度即将耗尽时，通过一系列策略组合——切账号、压 context、降模型档位、 Prompt 缓存——硬是把可用时间拉长了5天。这事儿听起来像「薅羊毛」，但背后其实是一套完整的 LLM API 成本优化方法论。今天RY哥就从工程视角，把这层窗户纸捅透。



## 一、先搞清楚：Claude 的计费模型到底怎么算

Anthropic 的 Claude 系列目前主要按 token 量计费，核心逻辑和 OpenAI 的 GPT 系列类似，但有几个关键差异值得注意：

- **输入与输出分别计价**：以 Claude 3.5 Sonnet 为例，输入约 $3/百万 token，输出约 $15/百万 token。注意输出是输入的5倍价格，所以长回复比长提问贵得多。
- **Context window 影响单次成本**：Claude 3.5 Sonnet 支持 200K token 的上下文窗口。但更大的 context 不只是「能塞更多内容」，它还会让每次调用的输入 token 数飙升——你每次请求都在把全部历史重新发一遍。
- **Prompt Caching 带来阶梯式降价**：Anthropic 在 2024 年推出了 Prompt Caching 功能，对重复使用的 system prompt、长文档等前缀部分进行缓存，缓存命中时输入 token 价格降至原来的 **1/10**（约 $0.30/百万 token）。这是省钱的核心杠杆之一。
- **模型档位差异巨大**：Haiku（轻量）输入 $0.25/百万、输出 $1.25/百万；Sonnet（中档）输入 $3、输出 $15；Opus（旗舰）输入 $15、输出 $75。Haiku 和 Opus 之间差了 **60倍**。

所以「续命5天」的本质，不是什么魔法技巧，而是在这些参数空间里找到最优组合：用最便宜的模型处理最简单的任务，用最短的 context 传递最精准的信息，用缓存兜住重复部分的开销。



## 二、「续命」策略拆解：四板斧把成本压到地板

从社区讨论和实际工程经验来看，所谓省钱攻略大致可以归纳为四个维度：

### 1. 模型分级路由（Model Routing）

不要所有任务都上 Sonnet 甚至 Opus。做一个简单的路由层：

- **简单分类/抽取/格式转换** → Haiku，成本仅为 Sonnet 的 1/12
- **常规对话/代码生成/RAG 检索后问答** → Sonnet，性价比最优
- **复杂推理/长文档深度分析/多步规划** → Opus，只在必要时触发

实际项目中，80% 的请求可以用 Haiku 处理，只有 15% 需要 Sonnet，5% 才需要 Opus。这样混合路由后，整体 API 成本能降低 **60%~80%**。

### 2. Context 压缩与摘要链

这是「续命」最有效的一招。长对话场景下，context 会像滚雪球一样膨胀：

- 第1轮：输入 500 token
- 第5轮：输入 3000 token（含历史）
- 第20轮：输入 15000+ token

策略是对历史对话做**滚动摘要**：每5轮用 Haiku 把前面的对话压缩成一段 200 token 的摘要，替换原始历史。这样 context 增长从线性变成对数级，单次请求的输入 token 始终控制在合理范围。

举个例子：一个客服 bot 原本跑到第 20 轮时单次输入 15K token，做摘要后稳在 2K 以内，**单次成本降低约 87%**。

### 3. Prompt Caching 用满

如果你的 system prompt 固定且较长（比如包含角色设定、工具说明、few-shot 示例），一定要开 Caching：

- **缓存写入**：第一次请求时多收 25% 费用（写入 overhead）
- **缓存命中**：后续请求中匹配到的前缀部分按 1/10 价格计费
- **缓存有效期**：5 分钟，每次命中自动续期

典型场景：一个 3000 token 的 system prompt，被 1000 次请求复用。不开缓存时输入成本 = 3000 × 1000 × $3/M = $9。开缓存后 ≈ $0.93（首次写入 $3.75 × 1.25 + 后续命中 999 × 3000 × $0.30/M ≈ $0.90）。**省了约 90%**。

### 4. 批处理与异步调度

Anthropic 的 Batch API 提供 **50% 折扣**，但要求请求在 24 小时内完成即可。对于非实时场景（批量标注、数据清洗、离线分析），这是最直接的省钱方式。把 1000 条独立请求打包成 batch，成本直接砍半。



## 三、账号维度的「续命」操作：合规边界在哪里

社区讨论中提到的「续命5天」，有一部分操作涉及多账号轮换——即在一个账号的免费额度或速率限制耗尽后切换到另一个。这里需要厘清合规边界：

- **API 层面**：Anthropic 的 API 按 organization 计费，多 organization 账号在技术上可行，但需要每个账号都通过合规注册。如果是为了**正式 production 的负载均衡和容灾**，多账号是合理的工程实践。
- **免费额度/试用额度**：平台提供的试用 credit 通常有使用期限和用途限制。在试用期内最大化利用是合理的，但通过非常规手段绕过限额（如伪造身份信息批量注册）违反 ToS，可能导致封号。
- **Pro 订阅（$20/月）**：Claude.ai 的 Pro 订阅有使用上限（通常按消息数计），而非按 token 计。如果你主要做交互式对话而非 API 集成，Pro 订阅的性价比在轻度使用场景下比 API 更高。

核心原则：**省钱的手段应当是工程优化，而非规避平台的计费规则。** 前者可持续，后者随时可能被风控系统识别并清零。



## 四、成本优化的数学建模：别凭感觉，算出来

真正想控制 LLM 成本，不能靠「感觉贵了就省省」，得建立一个简单的成本模型：

```
日成本 = Σ(每类请求的调用量 × (输入token × 输入单价 + 输出token × 输出单价))
```

举个例子，假设你的应用每天有：

| 请求类型 | 调用量 | 平均输入token | 平均输出token | 模型 | 单次成本 |
|---------|--------|-------------|-------------|------|---------|
| 简单分类 | 5000 | 200 | 50 | Haiku | $0.000175 |
| RAG问答 | 800 | 2000 | 500 | Sonnet | $0.0135 |
| 深度分析 | 50 | 10000 | 2000 | Opus | $0.225 |

日总成本 ≈ $0.875 + $10.8 + $11.25 = **$22.9/天**

如果对简单分类开 batch（省50%）+ 对 RAG 开 caching（省90%输入）+ 深度分析改用 Sonnet（降档）：

- 分类：$0.44
- RAG：$1.35（输入部分大幅下降）
- 分析：$1.35（Sonnet 替代 Opus）

日总成本 ≈ **$3.14/天**，降幅约 **86%**。这就是「续命5天」的数学本质——不是凭空多出来的额度，是把每一分钱花在了刀刃上。



## 五、三条冷思考

**1. 省钱的终极手段是「不调用」**。在架构设计阶段，先问自己：这个功能真的需要 LLM 吗？关键词匹配、规则引擎、传统 ML 模型在很多场景下够用且成本为零。把 LLM 用在它不可替代的地方——开放域理解、复杂推理、自然语言生成——其余链路用确定性方案兜底。

**2. 模型迭代速度远快于你的优化速度**。今天精心调优的路由策略，下个月新模型发布可能就被颠覆了（比如某款新模型可能在同等效果下价格直接降一个数量级）。保持架构灵活，模型可热替换，比死磕某一个省钱技巧更重要。

**3. 监控比优化更重要**。上线一套 token 级别的实时监控（按 endpoint、按用户、按模型分别统计），在成本异常波动时能第一时间定位。很多团队不是被单价贵死的，是被某个 bug 导致的死循环调用烧光的。先观测，再优化，最后才谈省钱。
