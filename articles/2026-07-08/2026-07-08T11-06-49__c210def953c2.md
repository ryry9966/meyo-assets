最近，Fable 5 团队声称仅靠 Claude 就撑过了五天连续高强度开发，把 context window 的利用率压榨到了极致。这件事之所以刷屏，不是因为"AI 写代码"有多新鲜，而是它精准踩中了所有 LLM 使用者的痛点：**context 用完了怎么办？** 这篇就来拆解这套"续命"方法论背后的技术逻辑。



## Context Window：Claude 的天花板在哪？

先说清楚物理约束。Claude 的 context window 目前是 200K tokens（约 15 万英文单词，中文更少因为 token 效率低）。听起来很多，但实际开发场景下：

- 一个中型项目代码库轻松超过 100K tokens
- API 文档、设计文档再吃掉 20-30K
- 多轮对话的历史消息不断累积
- Claude 自身的回复也占用 context

结果就是：一个复杂项目跑两三个小时，context 就满了。Claude 开始"遗忘"早期信息，输出质量断崖式下降——这就是所谓的 session 死亡。

**关键原理**：LLM 的注意力机制并非均匀分配。斯坦福 2023 年的研究指出，模型对 context 中间部分存在 "lost in the middle" 效应——首尾信息被较好利用，中间内容容易被忽略。所以光把信息塞进去远远不够，排布策略同样重要。

另外，实测中当 context 接近 150K tokens 时，Claude 的指令遵从能力开始明显衰减。这不是 bug，而是注意力机制在超长序列上的固有退化。这也解释了为什么"手动续命"比"无脑堆 context"更有效。

## 五天续命的核心策略拆解



Fable 5 团队分享的做法被社区概括为"极限续命"，核心思路可以归纳为三个字：**分层、压缩、外挂**。

### 1. 分层 Context 管理

把信息按重要性分层，而不是一股脑全塞进去：

- **L0 常驻层**：项目核心约束、技术栈选型、编码规范——始终保留，通过 system prompt 固化
- **L1 工作层**：当前任务的相关代码和文档——随任务切换动态替换，用完即清
- **L2 参考层**：完整 API 文档、历史决策记录——按需检索，只注入相关片段

这本质上就是操作系统内存管理的思路：L0 是内核常驻内存，L1 是工作集（working set），L2 是磁盘上的交换区。只不过这里的"内存"是 context window，"磁盘"是你外部的文件系统或 RAG 检索。

### 2. 定期压缩对话历史

每完成一个子任务，主动让 Claude 做一次"状态快照"：

```
请总结当前进度：
1. 已完成的任务清单及关键变更
2. 当前文件结构和核心函数签名
3. 待解决问题和下一步计划
4. 所有重要决策及理由
```

拿到这份快照后，开新 session，把快照作为起点注入。这样原来几万 tokens 的对话历史被压缩成几百 tokens 的结构化摘要——相当于给进程做了一次 checkpoint，把内存快照写到磁盘再重新加载。

### 3. 外部记忆系统

Claude 自己记不住的东西，让它写到外部文件里：

- 设计决策记录到 `DECISIONS.md`
- API 接口约定写到 `API_CONTRACT.md`
- TODO 清单实时更新到 `TODO.md`

下次需要时，只检索相关文件的**相关部分**注入 context，而不是整个文件丢进去。这就把 Claude 从"无状态聊天机器人"变成了一个"有持久化外部记忆的工作系统"——和人类开发者用 Notion 记笔记是同一个道理。

## Token 经济学：每句话都是真金白银

续命的本质是 token 经济学——在有限预算下做资源分配。几个容易被忽略的 token 黑洞：

- **重复粘贴大段代码**：每次把同一份 500 行的文件贴进 context 就是浪费。应该只贴变更部分，用 diff 格式描述修改
- **冗长的解释性文字**：Claude 有时过度解释前因后果。在 system prompt 里设定"回复简洁，代码优先"能省大量 token
- **格式化开销**：Markdown 表格比列表更贵；JSON 比 YAML 更费 token
- **中英混用的 token 效率**：中文在 Claude 的 tokenizer 中效率偏低（一个汉字可能 2-3 个 token），纯英文 prompt 大约省 30-40%。但考虑理解精度，"关键技术概念用英文、叙述用中文"是合理折中

**实用技巧——prefill 控制**：与其让 Claude 自由发挥生成一堆废话，不如在 prompt 末尾预填 `{` 或 ` ```python`，直接强制它输出 JSON 或纯代码，省去前后解释性文字。这是 Anthropic 官方文档里提到但很多人忽略的特性。

## Claude 特有特性：用好是加速器，用差是绊脚石



Claude 有一些区别于 GPT 系列的特性，理解了才能榨干价值。

### System Prompt 的绝对优先级

Claude 对 system prompt 的遵从度在主流 LLM 中属于第一梯队。把项目规范、技术约束、输出格式要求全部写进 system prompt，效果远好于在对话中反复提醒。一个结构化的 system prompt 应包含：

- **角色定义**：你是某技术栈的资深工程师
- **硬性约束**：禁止使用某库的某版本，必须包含类型注解
- **输出规范**：代码块标注语言，函数需有 docstring
- **上下文锚点**：当前项目处于什么阶段，下一步目标是什么

### Artifact 功能的正确用法

Artifact 适合生成独立的组件、文档和可视化内容，但不适合管理复杂项目结构。把整个项目代码塞进 Artifact 会导致 Claude 试图一次性输出所有文件，token 暴涨且容易截断。正确做法是逐文件迭代，每次只聚焦一个模块。

### 避坑：不要等 context 满了才压缩

这是最常见的误区。等 context 用到 90% 再做快照，Claude 此时已经在"遗忘"早期关键信息，快照质量必然受损。正确的做法是在 60-70% 用量时就主动 checkpoint，这比极限续命更可持续。

## 冷思考：五天续命背后被忽略的问题

Fable 5 的五天续命确实精彩，但几个问题值得冷静看待：

**第一，人力成本被低估了。** "极限续命"意味着开发者要持续维护 prompt、管理 context、做状态快照。这套流程的隐性成本不低——你本质上变成了 Claude 的"context 管理员"，真正写业务代码的时间反而被挤压。

**第二，五天 ≠ 高质量。** 能跑五天和五天产出的代码质量是两回事。长时间 session 容易积累"技术债"——早期的不完美决策被快照固化，后续很难回头修正。Fable 5 团队自己也承认，后期花了不少时间回头修前面埋的坑。

**第三，工具链在快速进化。** Claude Code、Cursor、Cline 等工具已经在做自动化的 context 管理和压缩。手动续命的技巧可能很快被工具内置化——就像手动内存管理最终被垃圾回收取代一样。现在学这套手艺有价值，但别把它当终极方案。

### 三条实用建议

1. **建立 context 健康线机制**：不要等满了才压缩。在用量到 60% 时主动做状态快照，开新 session。设定一个心理阈值并严格执行，比极限续命更可持续，产出质量也更稳定。
2. **固化项目级 prompt 模板**：把 system prompt、状态快照模板、文件检索格式都做成模板文件。每次开新 session 只需加载模板即可恢复上下文，把重复劳动降到最低。这就像 CI/CD pipeline 的思路——把流程自动化。
3. **区分探索模式与执行模式**：探索阶段允许 context 混乱，广撒网多尝试；执行阶段必须严格控制 context，只保留必要信息。两种模式之间显式切换，比一直极限续命更高效。因为不同任务对 context 纯度的要求完全不同，混在一起做只会两头不讨好。
