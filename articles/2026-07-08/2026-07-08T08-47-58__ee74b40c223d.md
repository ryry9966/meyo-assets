最近，36kr 的一篇报道在技术圈引发了广泛讨论：Anthropic 的命令行编码工具 Claude Code，其身世远比外界想象的曲折——它并非一个"专门为写代码而训练"的产品，而是在安全对齐（safety alignment）研究的过程中"长出来的"。更值得玩味的是，Anthropic 团队的 Boris 坦言，这条路"才走完了 1%"。

这个消息之所以引发热议，是因为它直接挑战了一个直觉判断：安全对齐是给模型"上镣铐"的，怎么反而催生了更强的编码能力？要理解这个反直觉的故事，我们需要从技术链条一层层拆开看。



## Claude Code 是什么？先对齐一下认知

在讨论身世之前，先把基础事实理清楚。Claude Code 是 Anthropic 在 2025 年初推出的命令行（CLI）AI 编码代理。与 GitHub Copilot、Cursor 等 IDE 插件式工具不同，它的核心特征是：

- **终端原生**：直接运行在 terminal 中，不依赖特定 IDE，理论上能在任何开发环境里工作
- **Agentic 工作模式**：不只是"补全代码"，而是能自主规划任务、读写文件、执行 shell 命令、搜索代码库、运行测试，形成一个完整的"感知→推理→行动→验证"闭环
- **动态上下文工程**：通过自动探索项目结构、读取相关文件、追踪依赖关系来构建上下文，而非简单粘贴代码片段

换句话说，Claude Code 的定位不是"更聪明的补全工具"，而是"一个能干活的初级工程师"。这也解释了为什么它的诞生路径如此特殊——Agentic coding 对模型的指令遵循、多步推理、自我纠错能力要求极高，而这些能力恰恰是安全对齐训练过程中的核心产物。

## 安全对齐的"副产品"：约束为什么催生了能力

这是整个故事最反直觉的部分。传统认知里，安全对齐 = 给模型加限制 = 牺牲能力。但 Claude Code 的案例揭示了一条更复杂的因果链。

### 对齐训练到底在训练什么

Anthropic 的安全对齐核心技术之一是 Constitutional AI（CAI），其核心机制可以概括为三步：

1. **Self-critique（自我批判）**：模型先生成一个回答，然后根据一组原则（"宪法"）评估自己的回答是否存在问题
2. **Self-revision（自我修正）**：基于评估结果，模型修改自己的回答
3. **RLAIF（AI Feedback 强化学习）**：用 AI 自身生成的偏好数据训练 Reward Model，再用 RL 优化策略

这套流程训练出来的核心能力包括：

- **精确理解复杂指令**：模型必须同时理解并满足"宪法"中的多条原则
- **多步推理与因果关系分析**：评估一个回答是否安全，需要推理其潜在后果与间接影响
- **自我纠错的迭代能力**：生成→评估→修正→再评估，这本身就是一个完整的 agentic loop
- **长程上下文管理**：在整个对话中保持一致性，不"忘掉"前面的约束条件

### 这些能力与编码能力的重叠

把上述能力和 Agentic coding 所需的能力放在一起对比，重叠程度惊人：

| 对齐训练培养的能力 | 编码场景中的对应需求 |
|---|---|
| 精确理解复杂多条件指令 | 理解"重构这个模块并保持 API 兼容"这类复合约束任务 |
| 多步推理与后果分析 | 预测代码改动对其他模块、测试、性能的连锁影响 |
| 自我纠错的迭代能力 | 写代码→运行测试→根据报错修正→再测试的经典开发循环 |
| 长程上下文管理 | 在大型代码库中保持对整体架构和模块间依赖的理解 |



这就解释了为什么 Claude Code "脱胎于安全对齐"——不是因为 Anthropic 原本想做编码工具然后顺便做了安全，而是对齐训练过程本身锻造了 agentic coding 所需的核心能力。安全不是"镣铐"，更像是"健身房"。

## 从 Constitutional AI 到 Agentic Coding 的技术链条

理解了能力重叠之后，可以更具体地看从对齐研究到编码产品的转化路径。

### 第一步：对齐研究沉淀的 Agentic 基础设施

安全对齐研究不只是"训练模型别说坏话"，它实际上催生了一整套 agentic 基础设施：

- **Tool use 框架**：为了让模型安全地在受限环境下执行任务，Anthropic 开发了完善的 tool use（函数调用）机制。这直接成为 Claude Code 执行 shell 命令、读写文件、调用搜索工具的技术底座
- **长上下文窗口**：对齐评估需要模型处理长文本（评估长对话的安全性），这推动了 200K token 上下文窗口的研发，而长上下文正是代码库级理解的前提条件
- **Trajectory 评估方法**：对齐研究需要评估模型在多轮交互中的表现（而非单轮质量），这套多轮评估方法论直接迁移到了编码任务的 benchmark 设计上（如 SWE-bench）

### 第二步：从"能做"到"做得好"的能力跃迁

Anthropic 模型在 agentic 能力上的提升轨迹也印证了这条路径：

- **Claude 2**：初步具备多轮对话能力，但复杂指令遵循不稳定
- **Claude 3**：指令遵循和多步推理显著提升，开始展现较强的代码生成能力
- **Claude 3.5 Sonnet**：在 SWE-bench 等编码基准上表现突出，agentic 编码成为标志性特征
- **Claude Code**：将 agentic 编码能力封装为终端工具，直接进入开发者工作流

每一步的能力提升，都可以追溯到对齐训练中对"精确指令遵循"和"自我纠错迭代"的持续优化。这不是巧合，而是能力 transferred 的必然结果。

### 第三步：产品化中的安全哲学烙印

从技术能力到产品，Claude Code 的设计选择也带着对齐研究的烙印：

- **CLI 而非 IDE 插件**：终端是最通用的接口，不绑定编辑器生态，也更符合 agentic 工具"与开发者协作"而非"嵌入开发者环境"的哲学
- **Human-in-the-loop 设计**：执行敏感操作（删除文件、运行有副作用的命令）前请求确认，直接继承了对齐研究中的审慎原则
- **沙箱化执行**：在设计上限制行动范围，避免"自由发挥"带来的安全风险

这些选择说明，Claude Code 的 DNA 里确实刻着安全对齐的哲学——不是作为约束，而是作为设计语言。

## "才完成 1%"：这句话的含金量

Boris 说"才完成 1%"，这不是商业话术里的谦虚，而是在描述一个技术现实：当前的 AI 编码代理，距离真正的"自主软件工程"还有数量级的差距。

### 当前能做的（≈1%）

- 在明确指令下完成局部代码编写和修改
- 搜索代码库、理解项目结构、定位已知类型的 bug
- 运行测试、根据报错信息修复问题
- 在人类监督下完成中等复杂度的多文件重构

### 还做不到的（≈99%）

- **自主架构设计**：从模糊的产品需求出发，设计合理的系统架构、做出技术选型
- **跨系统调试**：在微服务、数据库、前端、基础设施组成的复杂系统中定位根因
- **超长程上下文管理**：在数百万行代码的大型项目中保持全局视角，理解所有模块间的隐式依赖
- **自主工程权衡**：在性能、可维护性、安全性、成本之间做出合理的 trade-off 决策
- **协作与沟通**：与产品经理对齐需求模糊点、与团队成员协调接口契约、编写有说服力的技术方案文档

从 1% 到更高完成度，需要突破的不只是模型参数规模，还包括几个深层难题：

1. **上下文工程的质变**：当前的长上下文窗口能"装下"大量代码，但"能装下"≠"能理解"。Attention 机制在超长序列上的信息衰减问题尚未根本解决，模型在百万 token 级别上的有效信息利用率仍然偏低
2. **Reward signal 的精细化**：编码任务的 reward 远比"安全/不安全"二元判断复杂。代码的正确性、效率、可读性、可维护性如何量化为可训练的信号，目前还是没有标准答案的开放问题
3. **从 Follower 到 Planner 的范式跨越**：当前模型擅长"被告诉做什么"（instruction follower），不擅长"自己决定做什么"（autonomous planner）。这一跨越可能需要新的训练范式，而非简单 scale up

## 三条冷思考

1. **安全投入不是沉没成本，而是能力杠杆。** 很多团队把安全合规当作"不得不做的负担"，但 Claude Code 的故事提供了一个反直觉的视角：对齐训练中锻造的指令遵循、多步推理、自我纠错能力，恰恰是 agentic AI 最核心的基础设施。如果你在做 AI 产品，不要把安全和对齐当作"扣分项"来对待——它可能是你最重要的能力护城河。那些在安全上"偷工减料"的模型，短期看可能跑得快，但在 agentic 场景下会率先撞到天花板。

2. **"1%"意味着现在开始学 agentic coding 的人，仍然在起跑线附近。** 不要因为"才 1%"就观望等待，也不要因为"已经有了"就焦虑。现阶段最值得投入的事情是：理解 agentic 工具的工作原理（上下文如何构建、工具如何调用、推理链如何展开），培养与 AI 协作的工作习惯——包括如何拆解任务、如何描述约束、如何审查 AI 的产出。工具会快速迭代，但"与 agentic AI 高效协作"的 skill 是不会过期的长期资产。

3. **编码工具的终局不是"替你写代码"，而是"扩展你的工程能力边界"。** 如果 Claude Code 的起点是安全对齐，终点大概率不是"一个更快的打字员"，而是"一个能理解系统、做出权衡、与你讨论方案的数字协作者"。这意味着开发者的核心竞争力会持续向两端移动——"定义问题"和"评估方案"的价值在上升，"实现细节"的比重在下降。提前调整能力结构的投入比例，比纠结"AI 会不会取代我"有用得多。
