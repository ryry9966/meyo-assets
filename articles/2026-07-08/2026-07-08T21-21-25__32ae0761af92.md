最近技术圈炸了个不大不小的瓜：有团队用 AI 凭感觉写代码，项目上线后直接崩盘。为了收拾烂摊子，又花了整整 1 周时间和 1 万美元，请外面包工头继续用 AI 来修代码。这种“用 AI 写，用 AI 修，越修越崩”的荒诞闭环，把目前圈内大火的 Vibe Coding（凭感觉编程）推上了风口浪尖。今天咱们就扒一扒这套闭环背后的技术逻辑，看看这 1 万美元究竟花在了哪里，又买到了什么教训。



## 什么是 Vibe Coding？为何让人上头？

Vibe Coding 这个概念最近在开发者圈子里火得一塌糊涂。简单来说，就是不再逐行审查 AI 生成的代码，而是完全跟着感觉走：给个 Prompt，跑一下，能跑通就继续往下推，跑不通就把报错丢给 AI 让它自己改。开发者从“码农”变成了“代码审稿人”，甚至变成了“甩手掌柜”。

这种模式之所以让人上头，有几个硬核原因：

1. **多巴胺的即时反馈**：传统写代码需要脑内维护变量状态、调用栈、上下文逻辑，极其耗能。而 Vibe Coding 把这种心智负担全部外包给了 LLM。你敲下一句话，几秒钟后代码就生成了，点一下 Run，居然能跑。这种即时反馈极其容易让人产生“我是全栈大神”的错觉。
2. **原型构建极快**：在项目初期，用 Cursor 或 GitHub Copilot 这种工具，配合强大的模型（如 Claude 3.5 Sonnet 或 GPT-4o），几十分钟就能搭出一个带前后端交互的 Demo。这种效率提升是实打实的。
3. **门槛降到地平线**：哪怕是不懂 TypeScript 语法的产品经理，只要能把逻辑用自然语言描述清楚，就能让 AI 吐出能跑的脚本。

但问题在于，“能跑”和“跑得对”之间，隔着马里亚纳海沟。Vibe Coding 的快感，往往在项目复杂度超过单次上下文窗口能理解的阈值时，戛然而止。

## 崩坏的必然性：AI 修 AI 代码为何是死循环？

当 AI 写出的代码出现 Bug 时，最本能的反应是把报错信息扔给 AI，让它修。但这恰恰是荒诞闭环的开端。AI 修 AI 代码往往会陷入死循环，根本原因在于以下几个技术机制：



1. **上下文污染与状态丢失**：当前的 LLM 本质上是无状态的前馈神经网络。它之所以看起来有记忆，是因为每次把历史对话塞进 Context Window。当 AI 修改代码时，它并不知道这段代码当初的设计意图，只能根据当前的报错信息进行“头痛医头脚痛医脚”的局部适配。这种局部修改极容易破坏全局的不变量。
2. **补丁套补丁的“屎山”成型**：每次 AI 修 Bug，往往是在原有逻辑外面再包一层 `try-catch` 或者加一个 `if-else` 分支。修复几次后，代码的圈复杂度呈指数级飙升。原本优雅的抽象被彻底破坏，AST（抽象语法树）变成了一团乱麻。这时候再让 AI 理解这段代码，连上下文窗口都塞不下它的依赖关系。
3. **幻觉叠加效应**：AI 在修复代码时，如果涉及外部库的 API 调用，非常容易产生幻觉。它可能会编造一个不存在的参数，或者在错误的命名空间里找方法。用带有幻觉的代码去修复原本就有缺陷的代码，就像是饮鸩止渴，引入的新 Bug 比修掉的还多。

所以，当系统复杂度达到临界点，AI 修复代码的成功率会断崖式下跌。你以为是 AI 在修 Bug，实际上是 AI 在玩“打地鼠”游戏。

## 1 万美元的账单构成与隐性成本

那这 1 万美元的账单，到底是怎么算出来的？表面上看是外包费用，实际上这是一系列隐性成本的大爆发：

1. **Token 燃烧**：在死循环里挣扎时，每次对话都要带上大量的历史代码和报错日志。几十轮对话下来，Token 消耗量极其惊人。如果用的是企业级 API，这部分的 API 费用本身就是一笔大开销。
2. **代码考古学**：接手这个烂摊子的人，需要花大量时间去搞清楚“AI 当初为什么这么写”。人类开发者去逆向工程 AI 生成的屎山代码，难度远大于阅读另一个人类写的烂代码。因为人类的烂代码至少还有某种蹩脚的逻辑可循，而 AI 的代码可能在不同层级间存在随机跳跃。
3. **架构重构的沉没成本**：最终这 1 万美元里，很大一部分必然花在了“推倒重来”上。因为有些代码的结构已经被 AI 改得无法挽回，只能靠人类工程师手动重构核心模块。也就是说，你花了钱，请人用 AI 去试错，试错失败后，还得请人用人类智慧去兜底。

这就好比用廉价的豆腐渣建了一座楼，塌了之后请了个高级工程师用更高级的豆腐渣去补，最后发现还是不行，只能花钱请结构专家重新打地基。这 1 万美元，买的就是这个试错教训。

## 拆解 Vibe Coding 的适用边界

技术没有银弹，Vibe Coding 翻车不代表我们要回到纯手写时代，关键是要搞清楚它的适用边界。务实的工程师应该建立一套判断框架：

**适合使用 Vibe Coding 的场景：**
- **原型验证与 Demo 搭建**：只要求展示交互逻辑，不考虑性能、安全性和可维护性的一次性代码。
- **正则表达式与复杂字符串处理**：这类符合“描述需求即可，不需要关心过程”的特征，AI 写正则的效率远超人类。
- **单元测试编写**：在已经有明确业务逻辑接口的前提下，让 AI 根据代码生成覆盖各种边缘条件的单测，非常高效。
- **样板代码生成**：如数据库 Model 定义、CRUD 接口骨架，这类高度模式化的代码，AI 生成几乎不会出错。

**绝对不能 Vibe Coding 的场景：**
- **核心支付与金融交易链路**：一分钱的误差都不能有，状态机极其复杂，绝不能让 AI 凭感觉处理。
- **高并发临界区代码**：涉及锁、并发控制、内存屏障的代码，连人类专家都要反复 review，AI 在这种细粒度上极易产生死锁。
- **安全与权限校验模块**：涉及加解密、鉴权的代码，一旦出现漏洞后果不堪设想。
- **复杂状态机维护**：状态流转涉及多个外部系统交互时，AI 极易丢失中间态的异常处理。



## 冷思考：如何不被 AI 带进沟里？

面对 Vibe Coding 的荒诞闭环，给出三条避坑冷思考：

1. **坚持“人类在环”的严肃 Code Review**：AI 写的每一行代码，都必须经过人类工程师的审查才能合并。不要被“能跑就行”的错觉蒙蔽，你要对最终的架构负责，而不是对单次 Prompt 的输出负责。如果一段代码你看不懂，那就不要让它进主分支。
2. **用 TDD（测试驱动开发）给 AI 套上缰绳**：先写好明确的单元测试用例，再让 AI 去实现代码让测试通过。这样 AI 的输出有了客观的验收标准，而不是靠肉眼盯着控制台看有没有报错。测试用例就是防止 AI 搭积木塌方的脚手架。
3. **架构设计权必须留在人类手里**：你可以把“实现某个函数”的权限交给 AI，但“模块如何划分、数据流向如何设计、采用什么设计模式”这种架构级决策，绝不能下放。如果架构是乱的，AI 只会以最快的速度往上面堆砌垃圾代码。

工具再好，也只是杠杆，放大的是使用者的能力，也放大使用者的愚蠢。保持清醒，才能在这波 AI 浪潮里做稳执锤人，而不是被锤子砸了脚。
