## 背景

在 OpenClaw 这类 Agent 框架中，心跳（heartbeat）是维持助手「存活感」和可靠性的基础机制。无论是让前端展示“在线”状态，还是后端判断某个 Agent 实例是否失活，都需要一种轻量的探活协议。工程上最常见的两派实现是：**客户端轮询** 和 **服务端推送**。

轮询实现简单，每 N 秒发一个 `GET /health`，立即返回 `{"status":"ok"}`。推送则通常用 WebSocket 或 SSE 保持长连接，由服务端定期下发心跳包。

看起来只是实现手段的区别，但在插件系统复杂、多协议并存、需要切分长任务与短连接的 OpenClaw 场景下，选型会直接影响系统资源开销、架构延展性，甚至造成长时间任务被误判为掉线。

## 问题拆解：不是选一个，而是明确谁来主导心跳

很多时候我们问“轮询还是推送”，默认只有服务端到客户端这一个方向。但一个 Agent 系统至少要处理三种心跳：

1. **前端 ↔ 网关**：用户界面判断 Agent 是否存活  
2. **Agent 进程 ↔ MCP Server / 工具端**：长时间运行的任务需要定期报告进度，避免触发超时 kill  
3. **插件实例 ↔ OpenClaw 核心**：挂载在 Agent 上的插件需要维持自身健康上报

如果所有方向都用同一套策略，要么前端被无效长连接拖垮，要么服务端被海量轮询压垮。更实际的做法是**根据信道的天然属性去打散设计**。

## 做法：在 OpenClaw 中落地混合心跳

我们以一次基于 OpenClaw 的自动化流水线 Agent 为例，拆解三步实施。

**第一步：前端借网关的 SSE 承载心跳，不做独立长连接**  
在 OpenClaw 的 API 网关上开启 Server-Sent Events（SSE）通道，专门用于推送 Agent 的状态变更。前端不主动建立 WebSocket，而是通过 `EventSource` 连接到 `/api/agent/{id}/events`，服务端每 10 秒下发 `: heartbeat\n\n`。这样做的好处是连接由 HTTP 协议承载，经过反向代理时不需要额外配置 Upgrade，也天然支持断线重连。前端收到数据后重置本地计时器，超时 30 秒则标记 Agent 离线。

**第二步：Agent 内部用轮询保活长任务，防止 MCP 超时**  
OpenClaw Agent 执行一个长任务（比如运行多步数据分析）时，可能会调用外部 MCP Server，而很多 MCP Server 设定了 60 秒无消息自动关闭会话的机制。此时若 Agent 主循环同步阻塞，极易被当成僵尸会话清理。  
做法是在任务循环中嵌入一个独立协程 / 线程，每 45 秒向调用链上的所有 MCP 连接发送 `ping` 请求。不采用 WebSocket 自带的 ping/pong 是因为要与各 MCP 实现保持兼容——某些基于 stdio 或 HTTP 的 transport 不支持应用层自动心跳。

**第三步：插件注册定时上报，推送至监控总线**  
OpenClaw 的插件管理器允许插件声明一个 `healthCheck` 周期。核心并不直接轮询插件，而是插件自行把自身健康状态以 gRPC 推送的方式写入内部状态总线。核心订阅这些事件，实时聚合后在管理面板展示。这种模式下，插件是状态的生产者，而不是被动的被探测对象，天然避免“我不知道我挂了”的观察者失效问题。

## 踩坑点

1. **SSE 在 Nginx 下的默认缓冲**  
   Nginx 默认会缓冲响应数据，导致 SSE 的心跳不能立即到达前端。需要在 location 块显式设置 `proxy_buffering off`，并增加 `proxy_read_timeout 600s` 防止自动断连。

2. **移动端 WebSocket 省电策略干扰**  
   如果提供给移动端 Native 面板的心跳走 WebSocket，Android/iOS 会在退到后台不久后切断长连接。这时即使用推送，也需要结合前台检测，退后台时切到后端发送静默推送（push notification）触发重新连接，或临时降级为低频轮询。

3. **长任务内部的心跳轮询造成 GC 抖动**  
   大量 Agent 同时使用轮询保活 MCP 时，如果心跳请求对象没有复用，会频繁创建临时对象拖慢执行。需要统一为每个长任务复用一个单连接上的 ping 请求对象，控制 QPS。

4. **时钟偏移误判离线**  
   用时间戳比较的方式判断心跳超时，必须考虑分布式节点间的 NTP 同步。建议统一以服务端单调时钟计算间隔，不要依赖客户端携带的时间戳。

## 可复用建议

- **按信道选协议**：用户可见的 UI 状态推送优先用 SSE；服务间长连接可以保留 WebSocket 或 gRPC 流；无法改造的老旧接口继续用轮询，并在调用侧加 jitter 防止惊群。
- **设置多层超时阈值**：短期超时（如 10 秒无心跳）触发重试；中期超时（30 秒）标记疑似失活并通知；长期超时（120 秒）才清理内核资源。避免颠簸。
- **统一心跳上下文**：在 OpenClaw 内所有心跳包附带 agent_id + session_id，方便集中追踪，不会与其他业务请求混淆。
- **不把心跳当成任务健康度的唯一信号**：长任务要额外上报“业务进度”信标，心跳只表示进程存活。否则工作流卡死但心跳照发，照样没人发现。

## 总结

轮询与推送之争，在 AI 助手工程化落地中并不是非此即彼。核心逻辑是让心跳的发起方靠近资源消耗的受益方：前端希望省电省用户流量，就走到服务端推送；后端需要兼容各种老旧工具和 MCP 通道，就继续用可控频率的轮询。

在 OpenClaw 这样的 Agent-First 框架下，更值得建立的是一个**混合、可观测、分层超时**的心跳基础设施，而不是强行统一到某一种“完美”协议上。
