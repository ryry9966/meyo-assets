## 背景

团队每天要写的日报，大多是把几个系统的运行日志、API 调用记录、错误告警手工翻一遍，数出“今日处理多少请求”“失败多少条”“P99 耗时是否异常”，再按固定模板填成文字。这个过程重复、容易遗漏，而且不同人对同一份日志解读出来的数字经常对不上。

我们一直在用 OpenClaw 做日常自动化编排，于是尝试把“日志解析→指标提取→结构化日报”这条链路固化成一个可复用的流水线，让 Agent 去完成数据采集、聚合和排版，人只在最终确认时介入。

## 问题拆解

从原始日志到一份可发送的日报，实际要解决三个核心问题：

1. **日志来源不统一**：业务日志在本地文件、云服务日志在对象存储或 API、数据库审计日志在独立库，拉取方式各不相同。
2. **指标定义不稳定**：业务关注的指标会随着版本发布和告警规则调整而变化，硬编码的聚合逻辑很快过时。
3. **报告格式要求结构化**：日报需要表格、同比/环比、异常摘要，且要能直接插入 Markdown 或企微/飞书消息，不能只是一堆裸数字。

对应地，流水线需要做到：数据接入可插拔、指标计算可配置、输出格式松耦合。

## 做法：用 OpenClaw 组装流水线

我们选择基于 **OpenClaw** 作为编排引擎，通过 **MCP (Model Context Protocol)** 把日志查询、指标聚合、模板渲染等能力封装成可调用的工具，再用一个轻量级 Agent 控制执行流程。整体结构如下：

1. **日志查询 MCP server**：暴露两个工具 `query_file_logs` 和 `query_api_logs`，内部适配不同的日志后端（本地文件用 grep + awk，远程用对象存储 SDK 和简单的 HTTP 客户端）。返回统一结构的 JSON 行。
2. **指标聚合 MCP server**：提供 `compute_daily_metrics`，接收查询结果和一份 YAML 格式的指标定义，输出结构化的指标字典，例如请求量、错误率、P50/P90/P99 延迟、环比变化。
3. **报告渲染与发送**：一个 Python 脚本通过 `report_template` 资源获取 Markdown 模板，将指标填入后生成最终日报，再调企微机器人 webhook 或保存为文件。

OpenClaw 里的 Agent 配置很简单：定义一个 `daily-report` skill，顺序调用这三个 MCP 工具，对异常指标自动添加说明（例如“P99 耗时环比上升 32%，对应 /api/order 接口晚间有批量重试”）。整个流程通过 cron 定时触发，或者早间手动输入一句 “跑一下昨天的日报” 启动。

### 关键步骤

#### 1. 日志清洗与归一化

接入日志的第一件事不是查，而是定义清洗管道。我们在 `query_file_logs` 内部做了三级处理：

- **行过滤**：按时间范围、日志级别、关键字过滤，减少后续解析压力。
- **字段提取**：用正则 + 简单状态机把 Apache 格式日志拆成 `timestamp, method, path, status, latency, trace_id` 等字段，非结构化日志只保留时间戳和 body。
- **时区校准**：所有时间统一转为 UTC，避免跨服务器时区不一致导致日报时间窗口错位。

这一步的坑最多：业务日志里经常出现堆栈信息跨行，简单的逐行解析会把一条错误拆散；同一台机器上不同应用的日志时间格式居然有四种。最后我们放弃了实时流处理，改为每次查询时对原始文本做一次轻量清洗，避免维护状态。

#### 2. 指标定义外部化

指标计算逻辑不能写在代码里。我们用 YAML 定义指标：

```yaml
metrics:
  total_requests:
    type: count
    filter: "status != '-'"
  error_rate:
    type: ratio
    numerator: "status >= 500"
    denominator: "status != '-'"
  p99_latency:
    type: percentile
    field: latency
    percentile: 99
```

`compute_daily_metrics` 工具读取这份配置，对传入的 JSON 行做聚合。新增指标只需改 YAML 并重启 MCP server，不用动流水线代码。与环比计算相关的，工具会自动保留昨天数据做 diff。

#### 3. 报告生成与异常标注

模板是一个标准 Markdown 文件，包含日期、业务线、指标表格、异常小结等占位。Agent 拿到指标后，先判断每个指标是否超出预设阈值（也在 YAML 里配置），若超出则调用 LLM 生成一句简短的解释与建议，再整体填充到模板。这样日报在数据之外多了一层“工程判断”，而且只有异常时才会触发额外生成，成本控制得很好。

最终报告可以直接发送到群聊，也可以归档到 Git 仓库作为周报素材。

## 踩坑记录

1. **日志缺字段导致聚合失败**：早期版本对缺失字段直接抛异常，导致整个日报中断。后来改成对缺失字段的行单独统计，在日报末尾附上“解析失败行数”，方便排查日志质量问题。
2. **环比数据的窗口对齐**：直接用前一天同一时间段的日志，遇到跨周末或节假日业务量骤变，环比值没有参考意义。我们增加了一个“对比过去 7 天同一时段均值”的选项，在节假日自动启用。
3. **大日志文件的查询性能**：早期用全量读取再过滤，一天几 GB 的日志会让 MCP 调用超时。改为先用 `grep` 按日期和关键字粗筛，再传给 Python 做细粒度解析，调用时间从分钟级降到秒级。
4. **模板中的硬编码**：日报模板一开始写死了“今日请求量: xxx”，实际上不同业务线关注点不同。改成按 project 维度选择模板片段后，才真正适配了多团队。

## 可复用建议

- **从最小可用流水线开始**：先做一个只统计请求总数和错误数的最简版本，用上一周后自然会发现要补充哪些指标，再逐步扩。
- **把索引和查询分开**：如果日志量大，可以提前把日志发到一个轻量搜索引擎（如 zincsearch），MCP 工具只负责查，避免每次 grep。
- **Agent 的角色是“胶水”**：不要试图让 LLM 做精确数值计算，它的作用是把已有数据拼成通顺的文字，以及判断异常是否需要说明。
- **监控日报本身**：日报没生成出来就是一种故障。设置一个简单的死信告警：如果超过预定时间 30 分钟还没有日报产出，通知到运维群。

## 总结

用 OpenClaw + MCP 构建日报自动化流水线，本质上是在 **日志系统和团队沟通之间架一条稳定的管道**。投入前期主要花在日志清洗和指标定义的磨合上，一旦跑通，日常维护成本非常低。目前这套流水线已在团队内稳定运行数月，除了偶尔调整指标阈值和模板措辞，几乎不再需要人工干预，真正把“写日报”这件事从待办清单上划掉了。
