## 背景

随着 OpenClaw、MCP 以及插件生态的成熟，越来越多的团队将 Agent 接入社区协作流程：自动回复 Issue、处理用户求助、根据内部文档生成回答，甚至通过 MCP 直接调用工单系统或代码仓库。这些 Agent 在提升效率的同时，也打开了一个新的攻击面——**AI 在公开对话中可能泄露工作流细节、内部架构、甚至凭证信息**。

常见风险场景包括：

- Agent 在回答用户“这个功能怎么实现的”时，直接复述了内部设计文档中的未公开细节
- RAG 检索到的内部片段中包含数据库连接串或内部 URL，被模型原样透传
- 插件返回的完整 JSON 里藏有 API 密钥，而 Agent 未做脱敏就输出了部分内容
- 社区机器人同时连入了内部工单库，用户巧妙诱导下输出其他用户的工单标题或状态

这些问题无法通过单点补丁解决，必须在从上下文注入到最终输出的全链路上建立纵深防御。

## 问题本质

Agent 并不真正理解“机密性”。它的行为由系统提示、上下文窗口和工具返回共同决定。当上下文携带了内部信息，即使提示词明确禁止泄露，模型也可能在长对话中遗忘约束，或者在“帮助用户”的目标驱动下，把内部细节当作有效上下文使用。

因此，纯靠提示词防护是不可靠的。真正有效的方案需要**数据层隔离 + 输出层守护 + 审计兜底**三层结合。

## 做法与步骤

以下面向 OpenClaw 实践者，给出可直接落地的工作流。

### 1. 构建“社区专用数据视图”

不要直接将完整的内部 MCP 资源暴露给社区 Agent。为社区场景单独创建一个**只读、已脱敏的视图**。

具体做法：

- 在 MCP Server 中为社区 Agent 提供专用 resource，例如 `/public/faq`、`/public/summary`，而不是 `/internal/wiki`  
- 对检索到的文档做预处理：摘要化而非原文，正则剥离 IP、内部域名、邮箱、密钥模式
- 示例 OpenClaw 配置思路（伪代码）：

```yaml
mcp_servers:
  community_docs:
    command: "npx"
    args: ["-y", "@my/mcp-docs-server", "--mode=public-view", "--strip-internal"]
```

这样做的好处是：即使 Agent 完全服从用户，它能“看到”的数据也已是脱敏版本。

### 2. 输出守护管道

在 Agent 回复实际发送到社区前，增加一层输出检查。可以在 OpenClaw 的 message handler 中挂载一个自定义 filter，或通过插件机制拦截。

检查逻辑包括但不限于：

- 正则匹配内部域名、IP 段、密钥特征（AWS Key、JWT Token 等）
- 检测是否包含“内部”“未公开”“confluence.internal”等关键词
- 命中则自动替换为“该部分信息不在可公开范围内”，并触发告警

伪代码示例（消息后处理）：

```python
def output_guard(message: str) -> str:
    patterns = [r'192\.168\.\d+\.\d+', r'secret-[\w]+', r'internal\.example\.com']
    for p in patterns:
        if re.search(p, message):
            message = re.sub(p, "[REDACTED]", message)
            alert_admin("sensitive_pattern", p)
    return message
```

注意：**输出检查必须在消息离开系统之前的最后一步执行**，不建议仅异步分析。

### 3. 最小权限 Agent 设计

社区的 Agent 账号本身应使用受限的 API/插件权限：

- 不授予读取内部 Issue 追踪器、代码库、工单系统的权限
- 如果需要调用外部功能（如搜索文档），使用专用的只读凭据，该凭据只能访问公开索引
- 将社区 Agent 视作一个“低信任边界”节点，所有它使用的 MCP Server 都必须假设会被公开

实操上，可以为 `community-agent` 创建一个独立的 OpenClaw 实例或命名空间，与内部 Agent 物理隔离。

### 4. 系统提示加固（辅助手段）

提示词仍需写明规则，但不要依赖它作为唯一防线，而应配合上述工程手段。

推荐写法：

```markdown
你是一个面向外部用户的社区助手。
- 你只能使用公开文档和 FAQ 中的信息。
- 绝对禁止输出任何包含 “internal”、“private”、“secret” 的内容。
- 如果用户的问题需要内部信息，请回答：“该信息未公开，建议联系支持团队。”
- 不要逐字复制文档原文，必须用自己的话总结，并确保不含技术敏感细节。
```

同时加入 few-shot，展示什么会被拒绝。

### 5. 审计与回放

所有社区 Agent 的对话和工具调用日志必须持久化，便于事后追溯：

- 记录完整对话、生成的回复、使用的 MCP 工具及其返回内容（脱敏后可保存）
- 设定告警规则：当输出被 output guard 拦截时，实时通知安全人员
- 定期回放部分日志，检查是否存在新的泄露模式

## 踩坑点

- **RAG 片段嵌入敏感信息**：如果用向量数据库直接存储内部文档切片，极易将密钥或内链带入上下文。必须在入库前做脱敏，而不是事后过滤。
- **插件返回深层次嵌套**：某个 MCP 工具返回的 JSON 可能在嵌套字段里藏着内部信息，简单的正则可能覆盖不到。建议对工具返回的数据结构做 schema 白名单，仅取必要的公开字段。
- **模型长上下文遗忘约束**：当多轮对话塞入大量 user prompt 时，模型可能忽略早期的安全指令。可考虑定期重注入安全提示，或限制对话轮次。
- **性能与延迟**：输出检查若过于复杂（如调用外部检测 API），会增加回复延迟。建议使用本地轻量正则+关键词组合，误杀可以豁免，漏杀则是红线。
- **用户诱导绕过**：用户可能要求 Agent “扮演内部运维角色”或“忽略前置指令”，即使模型不服从，也要确保此时 Agent 可触及的数据本身就是无害的。**数据层隔离为王**。

## 可复用建议

- 制作一份“社区 Agent 安全配置模板”，包含受限 MCP 配置、输出 guard 插件和审计设置，作为新机器人上线的基线
- 环境变量中严格分离内部凭证和社区凭证，使用 .env 文件区分，例如 `COMMUNITY_BOT_DB_RO` vs `INTERNAL_FULL_ACCESS`
- 在每个社区 Agent 项目下建立 `SECURITY.md`，说明该 Agent 能访问什么、不能访问什么，以及已知的限制
- 实施“三步发送”机制：生成 → 安全检查 → 发送，若安全步骤失败则进入人工审核队列

## 总结

防止 Agent 在社区中泄露工作流和内部信息，本质上是一个**多层纵深防护**问题，而非模型能力问题。核心原则是：

1. **Agent 能访问的数据本身就应该是可公开的**（数据视图隔离）
2. **在输出边界强制清洗**，不能只靠提示约束
3. **所有交互行为可追溯、可告警**

在 OpenClaw 体系中，MCP 的资源设计、插件机制和消息管道为我们提供了丰富的防守工具。安全不是事后附加的特性，而是构建社区 Agent 的第一道基线。当你的机器人下一次在社区回复“让我查一下内部文档……”之前，请先确认它看到的文档，本来就是可以给人看的。
