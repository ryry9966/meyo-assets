## 背景：Agent 与插件为什么需要心跳

在基于 OpenClaw 的 Agent、MCP 服务器或自动化插件中，组件往往分布在多个进程中：MCP 工具作为一个独立进程运行，浏览器自动化插件在另一个沙箱里，模型推理服务可能跑在远端 GPU 上。为了让 Orchestrator 知道这些依赖项是否“活着”、任务是否还在执行，就必须设计一种心跳（heartbeat）机制。

心跳不止是存活性检测。它经常承载更多职责：任务执行进度回传、长时间操作的取消信号、分布式锁的续租。如果心跳设计不当，要么引入不必要的延迟和成本，要么因为假死判定造成误恢复，要么直接拖垮资源。

本文不空谈“选哪个好”，而是从实际踩坑中抽象出一套可复用的权衡方法，适用于 OpenClaw 场景下的 MCP 连接管理、插件生命周期监控和异步任务推进。

## 问题定义：两类心跳需求

在实际工程中，我们遇到的需求可以归为两种模式：

1. **存活性 Probe**：只需知道目标是否可达、进程是否存活，不关心瞬时负载。典型如 MCP 服务器的进程守护、浏览器插件是否崩溃。
2. **进度/状态同步**：需要及时感知任务状态变化，比如长时工具调用是否完成、流式输出是否中断。对实时性要求更高。

前者用轮询通常够用；后者更青睐推送。但真正的矛盾出现在中间地带：你需要一定的实时性，又不想维护 WebSocket；或者推送链路不稳定，需要降级策略。

## 核心取舍：轮询 vs 推送的工程化对比

以下对比基于我们在 OpenClaw 插件环境中实际测量的结果（单机/容器环境，CPU 和内存约束明显）。

| 维度         | 轮询 (Polling)                                 | 推送 (Push: SSE/WebSocket)                         |
| ------------ | ---------------------------------------------- | -------------------------------------------------- |
| 实时性       | 受轮询间隔限制，通常 1-5 秒                    | 近实时，延迟通常在 100ms 内                          |
| 资源消耗     | 客户端定期新建/复用 HTTP 请求，有规律的 CPU 波峰 | 需维护长连接，常驻内存和文件描述符，可能阻塞事件循环 |
| 实现复杂度   | 极为简单，几乎无状态                           | 需要处理重连、心跳保活、背压、连接管理               |
| 可靠性       | 短连接，单次失败容易隔离                       | 连接断开后状态丢失，必须设计至少一次送达或回放       |
| 可观测性     | 通过日志和指标直接观察请求失败率               | 需要额外监控连接数、重连次数、推送积压               |
| MCP/插件兼容 | 主动发起 HTTP，适配任意标准 HTTP 服务器        | 需服务器支持 SSE/WS，某些 MCP 实现不原生支持长连接    |

**重要坑点：切勿把业务心跳和传输层心跳混为一体。** 很多实现图省事，把 WebSocket ping/pong 直接当作存活性信号。一旦出现半开连接（客户端认为连接正常，服务端早已断开），对方收不到 pong 时早已错过恢复窗口。正确的做法是应用层更粗粒度的心跳（如 30s 一次），搭配传输层的 keep-alive，且必须设计独立的超时重连逻辑。

## 可复用的设计模式

我们提炼出三种常用模式，按场景选用。

### 1. 单纯轮询 + 指数退避（适合存活性检测）

```
每隔 5s 对 MCP 服务器发起 GET /health
连续 3 次失败 → 判定失活，触发重启
定时器进入冷却期，改为 10s→20s 渐进退避，直到返回成功
```

踩坑：轮询间隔小于 1s 时，在高并发插件数量下可能触发 HTTP 连接池耗尽，甚至被对端当作 DDos 限流。组件内务必使用全局统一的心跳调度器，复用连接池。

### 2. 推送为主，轮询兜底（适合异步任务状态同步）

- 主路径：建立 SSE 连接，服务器推送任务状态变更事件。
- 故障切换：SSE 连接在 3s 内未建立或意外中断 2 次，自动降级到 2s 间隔的轮询（带条件请求 ETag），直至 SSE 恢复。
- 优势：既获得正常情况的低延迟，又在网络抖动时保持信息同步，避免 UI 假死。

实现要点：降级轮询必须使用相同的状态模型，避免推送事件与轮询结果出现竞态（例如，推送“任务完成”时，轮询仍返回“进行中”，导致前端倒回旧状态）。可以在每个状态上附加严格递增的版本号/时间戳，客户端只接受较新的状态。

### 3. 反向心跳 / Lease 续租（适合分布式锁、长时间任务）

- 客户端启动任务时拿到一个租约（lease），有效期 10s。
- 客户端必须每 5s 续一次租，否则任务被系统认为失联并自动转移到错误处理队列。
- 这是一种“被动检测+主动续约”的心跳，过期即清理，避免僵尸任务占坑。

实施时要注意：续租请求本身可能失败，需在租约到期前留出 2-3 次重试时间，并设置最大续租次数，防止无限续命。

## 踩坑实录

- **连接泄漏**：在 Node.js 环境下使用 SSE 时，如果忘记在关闭时调用 `response.destroy()`，文件描述符会慢慢耗尽，导致整个 Agent 进程无响应。
- **心跳风暴**：多个插件同时向同一个 MCP 服务发轮询心跳，瞬间并发过高。解决办法：由中心化 Agent 进程统一心跳，结果广播给插件，或使用随机抖动（jitter）错开请求时刻。
- **假死误报**：GC 停顿或短暂 CPU 飙升导致心跳超时，触发不必要的重启。对心跳超时阈值应设置足够的缓冲（如平均响应时间的 3 倍+），并结合二次确认（连续失败次数）避免毛刺误杀。
- **推送积压**：SSE 通道如果产生事件快于消费，会在服务端缓冲区积压，最终撑爆内存。必须施加背压或限流，并监控缓冲区大小。

## 可复用建议与自动化封装

如果要在 OpenClaw 生态中复用，建议将心跳策略封装为一个轻量级库或插件内置模块，提供以下原语：

```ts
createHeartbeat({
  mode: 'polling' | 'push' | 'lease',
  interval: '2s',
  onAlive: () => {},
  onDead: (reason) => {},
  fallbackToPolling: true,
  jitter: true
})
```

内部自动处理重连、退避、降级和指标暴露（Prometheus 格式的健康状态与延迟）。这样插件作者只需声明策略，不必每次重复造轮子。

## 总结

AI 助手的 heartbeat 设计没有“完美”方案，只有“适合场景”的权衡。记住三条原则：

1. **职责分离**：传输层心跳仅保活，业务层判断存活与状态同步。
2. **默认简单，按需升级**：优先选择轮询，直到性能瓶颈真正出现再切换到推送，而不预优化。
3. **设计链路容错**：推送永远要有轮询兜底，连接断开要有状态回放，误检测要有二次确认。

最终，一个稳定运行数天的 Agent 集群，往往不是因为选择了推送或轮询，而是因为它的心跳机制在异常时做到了可观测、可降级、可自愈。
