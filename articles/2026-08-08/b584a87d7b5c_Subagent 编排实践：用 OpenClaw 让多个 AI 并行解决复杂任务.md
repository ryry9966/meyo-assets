## 背景

单个 Agent 处理复杂任务时经常会遇到两个瓶颈：一是上下文窗口有限，长链条推理容易丢失中间信息；二是串行执行导致整体延迟很高。比如需要同时完成数据查询、图表生成、文案撰写和格式排版的任务，如果让一个 Agent 从头做到尾，每一步都必须等待上一步完成，用户感知的等待时间就会被严重放大。

OpenClaw 框架提供了内置的 subagent 调用能力，配合 MCP 工具可以很自然地实现“主 Agent 拆解任务、多个 subagent 并行执行、最后汇总结果”的编排模式。这个模式本质上是一种 **多 Agent 协作的工程化落地方式**，不是概念验证，而是能稳定运行在自动化工作流里的实践。

我在一个日报自动生成流水线里应用了这套方案，效果比较明显：整体执行时间从串行模式的 40 秒左右降到 12 秒以内，且各部分输出质量可控。下面把完整的做法、踩过的坑和可复用的建议梳理出来。

## 问题

实际需求是这样的：每天固定时间，系统需要采集多个数据源（数据库指标、竞品变动、用户反馈摘要），并生成一份结构化日报，包含：
- 数据变化说明（基于 SQL 查询结果）
- 趋势图表（用代码生成，而非幻觉图）
- 要点摘要与行动建议

如果让一个 Agent 串行处理，它会依次调用数据查询工具、写图表代码、生成摘要，最后拼装。每一个步骤的提示词都很长，累积到后面容易丢失前面信息的细节，而且总耗时等于各步骤耗时之和。

如果能把三个独立子任务（数据分析、图表生成、文案撰写）分派给三个 subagent 并行执行，就能同时利用多个推理通道，减少等待。问题在于：**如何设计一种稳定的编排方式，让 subagent 之间不互相污染上下文，又能可靠地返回结构化结果？**

## 做法 / 步骤

### 1. 定义 Subagent 角色和输出 Schema

先用 OpenClaw 的 subagent 配置定义三个子代理，分别负责 `data-analysis`、`chart-generation`、`copywriting`。每个子代理的 system prompt 里除了角色描述，还强制要求返回一个固定 JSON 结构：

```json
{
  "status": "ok",
  "result": "...",          // 核心产出
  "metadata": {             // 元信息，方便主 Agent 校验
    "token_usage": 1234,
    "key_findings": ["..."]
  }
}
```

这样做的好处是主 Agent 不必从自然语言里猜测内容，可以直接通过字段取值判断成功与否，降低解析失败的概率。

### 2. 主 Agent 拆解与分发

主 Agent 的 system prompt 里明确了它只做三件事：
- 理解用户请求，生成子任务描述
- 调用 `dispatch_subagents` 工具（以 MCP server 形式封装）同时发送三个子任务
- 等待所有结果返回，对 JSON 结果做校验，然后拼装最终日报

`dispatch_subagents` 是这次实践里比较关键的工具，它内部通过 OpenClaw 的 subagent API 同时发起三次调用，并设置 `parallel=true`。调用成功后返回一个聚合响应，包含每个子代理的执行状态、耗时和输出 JSON。

工具调用示例（由主 Agent 生成）：

```
dispatch_subagents(tasks=[
  { "agent": "data-analysis", "input": "查询昨日XX指标，给出变化说明" },
  { "agent": "chart-generation", "input": "根据数据 {data} 生成 Matplotlib 折线图代码" },
  { "agent": "copywriting", "input": "基于数据变化和图表，写150字摘要和两条建议" }
], timeout=15)
```

### 3. 结果校验与降级

并行执行会带来一个新问题：某个 subagent 可能超时或返回不合法 JSON。主 Agent 需要有一套固定的降级逻辑：
- 如果 `status != "ok"`，直接丢弃该子任务产出，使用一个预设的默认占位内容；
- 如果返回的 JSON 缺少必要字段，同样视作失败；
- 所有超时任务记录到日志，但主流程不阻塞。

实际运行中，`chart-generation` 偶尔会因为模型幻觉生成不存在的 API，导致运行时报错。我们在工具层做了异常捕获，保证即使图表失败，日报也依然可以输出其余部分，不会整个任务挂掉。

## 踩坑点

**坑1：上下文残留导致子代理回答风格不一致。** 第一次尝试时，我把子代理的 system prompt 写得太泛，结果 `copywriting` 子代理有时会在文案里评价图表好不好看，出现了不属于它职责范围的内容。后来在 system prompt 里加入了严格的边界约束：“只处理文案部分，不要评价数据或图表质量”，问题解决。

**坑2：并行调用与 token 额度冲突。** 如果三个 subagent 同时占用大量 token，可能会导致瞬时配额耗尽。我们的做法是为每个子代理配置不同的 API key 或使用不同的模型权重分组，通过 OpenClaw 的 provider routing 能力实现资源隔离。

**坑3：子代理输出格式不稳定。** 即使有 JSON schema 要求，某些轻量模型还是会漏掉字段。最后的加固方案是在工具层加了一层后处理：如果 JSON 不合法，用一次极轻量的修复调用（few-shot prompt）尝试补全；如果依然失败，直接丢弃。这比让主 Agent 再重试更省 token。

## 可复用建议

1. **永远让 subagent 输出结构化对象**。不要依赖自然语言总结，这会增加主 Agent 的汇总难度，也让降级逻辑很难写。
2. **子代理的 system prompt 要比主 Agent 更“窄”**，只给它们完成单一任务所需的最小上下文，多余信息会诱导废话。
3. **用工具封装并行调度**，而不是在主 Agent 的 prompt 里“期待”模型自己知道怎么并行。工程上可靠度更高。
4. **设置超时和降级兜底**，尤其是需要调用外部服务（数据库、绘图库）的子任务。一个慢查询不应该拖垮整个日报流程。
5. **增加少量可观测性**。每个子代理返回的 metadata 里放置 token 耗用和关键发现，日积月累可以帮助评估不同子代理的效率和产出质量。

## 总结

Subagent 编排本质上是一种 **把复杂推理任务拆成可并行、可计量、可降级的工程模块** 的设计思路。OpenClaw 的原生 subagent 机制加上 MCP 工具封装，让这套模式可以在生产流水线里稳定运行，而不只是 demo。实践中最大的收益不是“快”，而是结构更清晰：每个子代理只做一件事，主 Agent 只做协调，整体健壮性明显提升。

如果你的工作流里有明显的多步骤可并行环节（报告生成、多源数据整合、多维度审查），不妨试一下这种编排方式，会比单纯的“长 prompt 神教”更能落地。
