## 背景

在构建 Agent（无论是纯脚本、OpenClaw 插件还是 MCP 工具链）的过程中，我们几乎都会遇到同一个问题：**“本地跑得好好的，一推到服务器就崩。”**  

原因很少是逻辑错误，更多是**配置与环境差异**：本地用的是本地端口、开发数据库、调试开关；生产环境需要真实凭证、链路追踪、严格的超时设置。这些差异散落在 `.env`、启动参数、硬编码常量甚至注释里，时间一长，排查成本远高于开发成本。

一个常见的反模式是，Agent 的“工具声明”文件（比如 `tools.md`）原本只用来描述工具签名，却被塞进了各种临时参数和路径。于是，**tools.md 不知不觉承载了配置中心的角色**——与其抗拒，不如把它设计成一套可控的配置管理入口。

## 为什么是 tools.md？

在 OpenClaw/Agent 生态里，`tools.md`（或类似约定的清单文件）具有几个天然优势：

1. **与 Agent 逻辑同源**：工具声明本身就需要描述调用方式、参数、依赖服务，这些信息天然与环境相关。  
2. **可读性强**：Markdown 结构让它既适合机器解析，也适合开发者肉眼检查。  
3. **易于版本控制**：相比分散的 `.env` 文件、环境变量模板，一个结构化的 `tools.md` 差异一目了然。

因此，我们可以让 `tools.md` 不仅仅停留于“声明有哪些工具”，而是**承担起声明工具在不同环境下行为差异的职责**。

## 做法 / 步骤

### 1. 定义分层配置结构
在 `tools.md` 中为每个工具增加一个 `<!-- config: ... -->` 块（或用 YAML Front Matter，视解析器而定）。例如：

```markdown
## tool: db_query
<!-- config:
  default:
    host: "localhost"
    port: 5432
    pool: 2
  production:
    host: "prod-db.internal"
    port: 5432
    pool: 10
    ssl: true
-->
- 参数: query, params
- 描述: 执行只读 SQL 查询
```

**约定**：配置块包含 `default`（本地/基准值）和若干环境名（如 `production`、`staging`），Agent 启动时根据环境变量 `AGENT_ENV` 选择合并。

### 2. 加载与合并逻辑
在 Agent 初始化时，解析 `tools.md`，提取配置片段。合并顺序：`default` → 指定环境覆盖。

```
最终配置 = deepMerge(default, selectedEnvConfig)
```

这种方法让本地开发只需要维护一份 `default`，生产或预发布只在特定环境下覆盖差异项。新增一个环境时，只需追加一个命名环境块，不用复制全部配置。

### 3. 敏感信息的处理
**绝对不要把 credentials 明文写在 tools.md 里。**  
配置块中的密码、API Key 一律使用占位符（如 `${DB_PASSWORD}`），真实值从环境变量或密钥管理服务注入。`tools.md` 只负责声明“这里需要一个密码”，而值由运行环境提供。

### 4. 工具行为的运行时差异
除了连接参数，有些工具的行为差异也需要配置化，例如：

- 开发环境输出详细错误堆栈，生产环境只返回 ID 和状态码。
- 本地可以执行写操作，生产环境只放行只读。
- 某些工具在 CI 环境下用 mock 实现。

这些开关都适合放在该工具的环境配置块中，比如 `allow_write: true/false`，由 Agent 加载后决定实际执行策略。

## 踩坑点

1. **格式不一导致解析失败**  
   如果团队多人维护，极易出现缩进不一致、Markdown 块嵌套错误。建议使用脚本校验 `tools.md` 的配置语法，在 CI 中加入 `lint` 步骤，防止错误合并进入主分支。

2. **`default` 过于“丰富”**  
   `default` 中放入了生产环境的参数（比如生产数据库 IP），本地启动时忘记覆盖，结果直接把本地流量打到生产库。**原则：default 里只放真实可用的本地/开发值，生产值必须显式覆盖。**

3. **环境变量与文件配置冲突**  
   有时为了调试临时修改了环境变量，但忘记了 `tools.md` 中也有同名变量，产生叠加错误。明确优先级：环境变量 > 文件配置。启动日志里打印最终合并后的配置（敏感信息脱敏），方便核查。

4. **忽略工具依赖的本地路径**  
   比如一个工具需要读取本地 CSV 文件，`path` 在 Mac 和 Linux 差异巨大。解决方案：使用相对路径配合 `$PROJECT_ROOT`，并在 `default` 中注明预期操作系统，必要时用 `runtime.os` 条件分支。

## 可复用建议

- **提供配置模板**：除 `tools.md` 外，提供 `tools.example.md`，只含 `default` 块，敏感值全部占位。新成员只需复制并填写本地值。
- **漂移检测**：写一个简单的 CLI 工具或 Make target，对比当前环境的实际配置与 `tools.md` 声明，报告差异（如本地缺少某个环境变量）。
- **CI 中验证环境完整性**：当 MR 修改了 `tools.md` 时，自动在 CI 中用 `staging` 环境加载一次配置，确保解析无误且关键变量存在。
- **合并日志**：启动时打印类似 “Loaded config for 'db_query' from production, overriding host: prod-db.internal”，让运维排障更轻松。

## 总结

`tools.md` 不应只是工具声明的静态清单，它可以成为 Agent 配置和环境差异管理的“单一事实来源”。通过明确定义分层配置、统一加载机制、保护敏感信息并在不同环境间清晰划分默认与覆盖，可以大幅减少“环境不同所以崩”的低级问题。

在工程实践中，保持结构简洁、自动化校验、并与运行时环境变量协作，是这套方案长期可靠的基础。把它视为代码的一部分，而不是随手编写的 Markdown 笔记，是团队走向稳定的关键一步。
