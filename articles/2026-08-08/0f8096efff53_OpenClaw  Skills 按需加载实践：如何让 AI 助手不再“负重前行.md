## 背景：工具膨胀的代价

在构建基于 OpenClaw 的 AI 助手时，一个常见的做法是把所有可能用到的能力都预先注册：翻译、数据分析、网页抓取、代码解释器、知识库查询……看似“全能”，实则带来了严重的上下文膨胀。每次对话的系统提示词里都被塞进几十个工具声明和对应的 schema，即使当前对话只是一个简单的问候。这会导致三个直接问题：Token 消耗剧增，特别是使用按量付费的模型时；推理质量下降，冗余信息干扰了模型对意图的判断；对于有上下文窗口上限的场景，甚至直接报错。按需加载，几乎是从 demo 走向生产的第一道门槛。

## OpenClaw 的 Skills 机制

OpenClaw 提供了一套技能（Skills）配置框架，允许你把不同能力拆分成独立定义的文件，并在运行时根据用户意图动态挂载。每个技能包含触发条件、专属的系统提示词、工具列表（可来自内置函数或 MCP 服务器），以及依赖声明。主引擎只负责轻量级的路由和会话管理，实际的工具和提示词在识别到对应意图后才注入当前上下文。

这种设计天然与 MCP 协议契合：每个技能可以关联一个或多个 MCP 服务器，连接只在技能被激活时建立，用完后根据策略决定保持或释放，避免了长连接资源占用。

## 实践步骤

### 1. 定义技能文件
在 `skills/`  目录下为每个技能创建一个 YAML 文件，例如 `web_summarize.yaml`：

```yaml
name: web_summarize
description: Summarize content from a given URL
triggers:
  keywords: ["summarize url", "read webpage", "网页总结"]
  intent: "web_summary"
prompt: |
  You are a web content summarizer. When given a URL, fetch its content and provide a concise summary in the user's language.
tools:
  - name: fetch_url
    from: builtin
  - name: summarize_text
    from: builtin
mcp_servers:
  - name: fetch
    command: python -m mcp_server_fetch
keep_alive: false
```

触发条件可以基于关键词，也可以配置为交给一个轻量级路由模型（比如用一个 7B 模型做意图分类），关键词仅作为初筛以降低路由成本。

### 2. 主配置启用懒加载
在 OpenClaw 的主配置中指定技能目录，并开启懒加载模式：

```yaml
skills:
  dir: ./skills
  lazy_load: true
  router:
    type: keyword_then_llm  # 先关键词过滤，不命中再由 LLM 路由
    model: local_router
  preload: ["greeting"]  # 始终加载的基础技能
```

### 3. 触发与卸载
当用户输入进入会话时，router 分析意图并匹配技能。一旦命中，系统将技能的 prompt 和工具列表拼接到当前会话的上下文，同时按需启动 MCP 服务器。技能完成其任务后，如果 `keep_alive` 为 `false`，工具的上下文会在下一个对话轮次中移除，MCP 连接关闭，释放资源。对于频繁使用的技能，可以设置 `keep_alive: true` 并配合会话级缓存，避免反复加载的延迟。

## 踩坑记录

**加载延迟与首次响应**  
首次触发某个技能时，可能需要启动 MCP 服务（例如 Python 进程），如果该服务依赖较大的库，冷启动会带来 2-5 秒的延迟。解决方法是为高频技能配置 `preload` 列表，在助手启动时即预热常驻技能；或者为 MCP 服务实现连接池，使断开后不立即销毁进程。

**工具命名空间冲突**  
不同技能中如果有同名工具，会产生覆盖，导致调用错误。早期我们吃过这个亏，后来在技能定义里强制使用 `alias` 字段，实际调用时工具名变成 `skill_name__tool_name`，完全避免了冲突。

**意图路由的准确性**  
纯关键词匹配极易误判，而每次都让大型 LLM 做路由又过于昂贵。最终采用两级路由：先用关键词白名单快速放行明显命中的请求；未命中集合交给一个微调过的轻量级分类模型（甚至可以使用 xgboost 对输入文本做分类），成本很低但准确率可以从 70% 提升到 95% 以上。

**回退与错误处理**  
必须为技能加载失败设计降级路径。我们在框架里加了一段逻辑：如果技能文件损坏或 MCP 服务启动失败，自动回退到通用助手提示，并给出一条委婉的回复，比如“我现在暂时无法处理这个请求，但我可以帮你做其他事情”。同时记录结构化日志，方便后续排查。

## 可复用建议

- **粒度控制**：一个技能只做一件事。把“数据分析”拆成“CSV 分析”和“数据库查询”，而不是做一个巨型技能。
- **写好 description**：这个字段不仅给人类看，也会被路由模型作为输入。用自然语言描述清楚技能能做什么、不能做什么。
- **监控加载统计**：记录每个技能的触发次数、加载时长、失败率。你会惊讶地发现某些技能从未被触发，可以安全下掉；某些技能用时过长，需要优化。
- **预加载与缓存策略**：对于用户会话中可能重复使用的技能（比如一个长期分析任务），在会话期间保持 `keep_alive` 可以有效减少响应时间。
- **测试工具链**：OpenClaw 提供了模拟工具，可以在 CI 中验证技能配置的有效性，确保 MCP 命令能够正确启动并返回预期结构，这条建议能省掉大量上线后的惊喜。

## 总结

按需加载并不是什么新概念，但在 AI Agent 的上下文中，它就是成本与体验的平衡器。OpenClaw 的 Skills 机制通过与 MCP 的结合，让这种架构落地得非常干净。如果你还在把所有工具一股脑塞进 prompt，不妨花一个小时，把能力拆一拆，试试动态加载，大概率你会在第一次测试时看到 Token 消耗断崖式下降。
