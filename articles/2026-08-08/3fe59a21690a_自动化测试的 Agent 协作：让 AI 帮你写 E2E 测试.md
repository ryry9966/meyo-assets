## 背景

写端到端（E2E）测试是保障业务链路的关键，但很少有人享受这一过程。选择器频繁失效、DOM 结构随前端重构抛锚、断言逻辑靠人工反复调试——这些痛点直接拉高了测试的维护成本。随着 LLM 能力提升，社区开始探索用 AI 自动生成测试脚本，但“一句话让模型吐出完整的 Playwright/Cypress 代码”远没有到开箱即用的程度。我们更需要一套工程化的 Agent 协作流程，让 AI 在可控的循环里帮你写测试，而不是扔出一段跑不通的“幻觉代码”。

如果你已经在使用 OpenClaw 编排 Agent，或者接入过 Playwright MCP Server，这套思路可以直接落地。

## 问题拆解

直接把网页 URL 丢给模型让它生成测试，会遇到三类典型问题：

1. **选择器不可靠**：模型习惯用 `.class` 或 `#id`，这些在生产环境中极易变动，跑两次就“红屏”。
2. **缺乏运行时上下文**：模型不知道当前页面的异步加载状态、登录态、弹窗干扰等，生成的 `await` 时机往往不准确。
3. **断言模糊**：只检查“页面包含某文案”远不够，复杂交互后的状态验证需要理解业务含义。

这就需要 Agent 具备“观察→执行→反馈”的闭环，而不是一次性生成。

## 实践步骤：Agent + Playwright MCP 的协作流程

我们以 Playwright 为例，配合 Playwright MCP Server 让 Agent 拥有真实浏览器操控能力。

### 1. 搭建基础环境

在 OpenClaw 中配置好 Playwright MCP Server，确保 Agent 可以调用 `browse`, `snapshot`, `click`, `type` 等工具。启动一个带认证状态的浏览器上下文（比如复用已登录的 storageState），避免每次让 Agent 从登录流程开始浪费 token。

### 2. 让 Agent 获取页面可访问性树

不要直接把整段 HTML 喂给模型。更稳定的做法是使用 Playwright 的 `page.accessibility.snapshot()` 或 MCP 的 snapshot 工具，提取语义化的元素结构——角色、名称、层级关系。Agent 看到的不是一堆 div，而是 `button "提交订单"`、`textbox "搜索商品"` 这样的可访问性描述。这一步是后续生成稳定选择器的基础。

### 3. 生成自然语言测试步骤

先不让 Agent 写代码，而是让它根据页面结构输出易读的测试步骤：

```
1. 在“搜索商品”输入框中输入“蓝牙耳机”
2. 点击“搜索”按钮
3. 等待列表中出现至少一个商品卡片
4. 点击第一个商品卡片的“加入购物车”按钮
5. 确认购物车图标上的数量变为 1
```

这一步可以人工快速校验逻辑是否覆盖了核心路径，也能避免 Agent 在代码层面过早陷入细节。

### 4. 用稳定选择器生成 Playwright 代码

将自然语言步骤转化为代码时，在提示词中严格约束选择器策略：

- 优先使用 `getByRole`、`getByLabel`、`getByPlaceholder`、`getByText`
- 如果页面有 `data-testid`，优先使用 `getByTestId`
- 禁止使用复杂 CSS 层级或动态 ID

生成的代码片段示例：

```typescript
await page.getByPlaceholder('搜索商品').fill('蓝牙耳机');
await page.getByRole('button', { name: '搜索' }).click();
await expect(page.getByRole('listitem').first()).toBeVisible({ timeout: 5000 });
await page.getByRole('button', { name: '加入购物车' }).first().click();
await expect(page.getByTestId('cart-count')).toHaveText('1');
```

### 5. 执行与反馈修复

让 Agent 调用 MCP 工具执行这段测试脚本，捕获异常（超时、元素不可见、断言失败）后，将错误信息重新喂给 Agent，并要求它只修正失败的部分而不是重写全部。经过 2-3 轮这样的对话，绝大多数因等待时机和选择器定位引起的问题都能解决。

## 踩坑实录

- **选择器退化为脆弱版本**：即使提示词强调语义化，Agent 偶尔仍会偷偷用 `.btn-primary` 这种类选择器。解法是在生成后加一步自动检查：使用 Playwright 的 `locator` 解析结果，发现非标准选择器直接回退要求重写。
- **复杂表单的上下文丢失**：多步表单（如分步注册）中，Agent 容易忘记之前已填写字段的当前状态。对策：每步操作后都 snapshot 一次，并把前一步的状态简要描述保留在对话上下文中。
- **登录态失效静默跳转**：执行中如果 token 过期，页面可能跳转到登录页，但 Agent 仍试图在原始页面操作并抛出无意义错误。需要预设一个“页面守卫”——在执行关键操作前校验 URL 或特定元素的持久性，否则触发重新认证。

## 可复用建议

1. **建立页面对象模型（POM）的 Agent 模板**：与其让 Agent 从头生成选择器，不如维护一套项目级别的 POM。Agent 的职责变成“基于已有 POM 组装测试用例”，这大幅提升了稳定性。你可以在提示词中注入 POM 的 API 文档。
2. **分层 Agent 协作**：探索 Agent 负责抓取页面快照和交互路径，编码 Agent 负责生成与调试代码，审查 Agent（或简单规则）负责检查选择器健壮性。OpenClaw 的 Agent 嵌套天然支持这种流水线。
3. **维护一个“测试失败知识库”**：将典型失败模式（如“元素未找到是因为页面尚未完全加载”）沉淀为 few-shot 示例，在后续生成时自动注入，减少 Agent 重复犯错。
4. **CI 集成时保持人机协作**：自动生成的测试必须经过人工评审再进入主干，可以借助 PR 评论自动展示 Agent 生成过程的可视化截图与步骤说明，降低审核成本。

## 总结

当前阶段，AI Agent 还做不到“一键生成完美 E2E 测试”，但通过精细化的协作流程——语义化抓取、自然语言解耦、严格选择器约束、闭环反馈——我们已经能将编写和维护测试的效率提升至少 30%~50%。对于页面结构频繁迭代的业务，这套方案尤其适用。关键是在 Agent 的自主性和代码可靠性之间找到平衡，让 AI 成为测试工程中的协作者，而不是一个不可控的黑盒。
