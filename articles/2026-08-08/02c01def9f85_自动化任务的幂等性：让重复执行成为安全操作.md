# 自动化任务的幂等性：让重复执行成为安全操作

## 背景：重试与重放无处不在

在 OpenClaw、Agent 编排、MCP 工具链或插件自动化场景中，任务的“重复执行”几乎是无法避免的。消息中间件的 at-least-once 语义、网络超时触发客户端重试、人为误操作的重新触发，甚至是调试阶段反复运行同一条 Pipline，都会让同一个业务逻辑被执行多次。

如果没有幂等性兜底，这些重复执行会直接变成生产事故：用户收到两笔扣款通知、数据库被插入重复记录、下游外部服务被反复调用导致限流或脏数据。

## 问题的本质：非幂等操作的状态污染

“幂等”在工程上的定义很明确：同一个操作执行一次与执行多次，产生的副作用完全相同。典型的非幂等案例包括：

- **无唯一约束的 `INSERT`**：重试产生重复行。
- **递增更新 `UPDATE counter + 1`**：每次重试都让计数器不可逆上升。
- **无状态检查的外部推送**：重复发送邮件、短信、Webhook。
- **MCP 工具调用**：比如一个 `create_issue` 工具在无保护的情况下被 Agent 重放，Jira 里多出几条一模一样的 Issue。

这些问题本质上都是因为程序没有建立起“执行边界”的概念——每次收到请求都当作全新的，而不会判断“这次请求我是不是已经做过了”。

## 工程化做法：四步构建幂等防线

以下步骤可直接落地到 OpenClaw 的任务节点或自定义 MCP Server 中。

### 1. 为关键操作预设幂等键（Idempotency Key）
在任务入口处生成或接收一个业务唯一标识，例如 `order_id + $action`、`task_id + stage` 或独立的 `idempotency_key`。这个键必须由调用方稳定生成，重试时保持不变。

### 2. 引入“处理状态表”或唯一约束
在数据库或缓存中建立一张去重表：

```
CREATE TABLE idempotency_records (
    key VARCHAR(255) PRIMARY KEY,
    result TEXT,
    created_at TIMESTAMP
);
```

处理前先尝试插入该键，利用主键冲突判断重复。若插入成功，继续执行主逻辑并写入结果；若冲突，直接返回已有结果。

对于 Insert 型操作，业务表本身可借助 `UNIQUE` 约束完成去重，例如在记录写入时使用 `INSERT ... ON DUPLICATE KEY UPDATE` 将副作用降至纯读取。

### 3. 对状态更新使用 Compare-and-Swap（CAS）
不写 `SET status = 'done'`，而是携带预期前置状态：

```sql
UPDATE tasks SET status = 'done', version = version + 1
WHERE task_id = ? AND version = ? AND status = 'pending'
```

如果受影响行数为 0，说明状态已被其他请求变更，可以选择幂等返回或拒绝。这种方法天然防止覆盖丢失与重复状态跃迁。

### 4. 外部调用包围 “查询-决策” 逻辑
每次调用邮件、支付、短信等外部接口前，先查询业务侧是否已有成功记录（如 `send_log` 表）。如果记录存在且成功，跳过实际调用。对于接口本身提供幂等键的（如 Stripe 的 `idempotency_key`），直接透传更可靠。

## 踩坑点：排查比实现更难

### 不是有唯一键就万事大吉
唯一键只能避免重复写入，但如果业务逻辑还包含非事务性的外部调用（比如插完数据库发 MQ），仍可能造成“插了但发了两遍”的情况。务必将外部调用与状态标记放在同一本地事务中，或使用 Outbox 模式解耦。

### 幂等键的有效期与膨胀
把所有幂等键永久留存会导致存储膨胀。可以按业务窗口清理，例如 7 天前的记录可以归档。但清理逻辑必须确保不会让一个新来的“旧请求”再次生效——通常通过请求中携带的时间戳与过期策略共同判断。

### 并发下的竞态窗口
即使有 unique key，如果处理逻辑是先 select 再 insert，高并发下仍可能多个请求同时通过检查。**唯一键必须建在数据库约束层面，而非应用层的 if 判断。** 必要时可以加分布式锁（如 Redis `SETNX`），但锁的粒度与超时需要仔细权衡。

### 与重放攻击的区分
对外暴露的 API 如果使用客户端提交的幂等键，需要结合认证信息进行隔离。否则一个用户可能猜测另一个用户的幂等键，触发重放。建议将幂等键与租户 ID 或 session 绑定。

## 可复用建议：内置到 Agent 与 MCP 中

在 OpenClaw 的 Agent 管道中，可以为每个异步 Task 自动生成 `task_run_id`，任务调度器在执行前先查库判断是否已完成，从而让重试天然安全。封装一个 `@idempotent` 装饰器，用函数参数散列值 + 方法名作为幂等键存储于 Redis，可快速为快慢任务提供保障。

对于 MCP 工具开发者，在 `tools` 描述中明确说明工具的幂等特性，同时在 Server 实现中利用传入的会话或请求 ID 作为幂等键的一部分，能极大降低使用方的心理负担。

## 总结

自动化任务的幂等性不只是一个 0 和 1 的开关，它是一层在混沌重试前挡住的防护网。通过**稳定幂等键 + 数据库约束 + CAS 更新 + 外部查询决策**的组合，可以把“重复执行会出事”变成“重复执行也无副作用”。在 Agent 与 MCP 生态里，这层设计会让你的自动化流程从容面对网络抖动、人工误操作和不可避免的调试重跑。
