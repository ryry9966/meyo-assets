## 背景：我们为什么让 Agent 写 E2E

团队维护的前端项目长期依赖手工编写 Playwright 测试，一个 CRUD 页面写三五条用例就要花掉小半天，还经常因为选择器脆弱导致回归时批量挂掉。测试运维成本甚至超过了用例本身的价值。

尝试过让通用 LLM 直接输出测试脚本，但脱离实际页面结构的一次性生成几乎不可用——要么找不到元素，要么断言写成 `expect(true).toBe(true)` 一样的无效检查。真正缺的不是代码生成，而是一个能**感知页面状态、按步骤执行、在失败后自行修正**的协作循环。

所以我们用 OpenClaw 的 Agent 能力，结合 MCP（Model Context Protocol）提供的浏览器工具，搭了一套“AI 测试助理”：把页面交给他，描述验收条件，让他在真实浏览器里一边探索一边写测试，遇到失败自动调整选择器和等待逻辑，直到用例稳定通过。

## 问题拆解：一个可用的 AI 测试助理需要什么

简单让模型吐一段 Playwright 代码只能覆盖理想情况，工程化要求至少解决三个问题：

1. **缺乏页面上下文**：不知道 DOM 结构、状态变化时机、动态列表长度。
2. **脆弱的元素定位**：默认使用 `text=提交` 或 `.btn-primary` 这类选择器，一换文案或样式就坏。
3. **无反馈循环**：写出来的代码不会自己跑一遍，即使跑失败也不会自愈。

因此我们要求 Agent 能做到：打开页面 → 理解结构与交互 → 用稳定的定位策略生成代码 → 逐步执行 → 观察到失败后分析原因并重写，直到全部通过。

## 具体做法：基于 OpenClaw + MCP 的测试生成循环

### 1. 准备工具链

- **OpenClaw**：作为 Agent 运行时，负责规划、调用工具、反思修正。
- **MCP 浏览器服务器**：提供 `navigate`、`click`、`snapshot`（获取可访问性树/简化 DOM）、`evaluate` 等原子操作。我们用的是社区实现，集成在 Agent 的工具列表中。
- **Playwright 测试运行器**：Agent 最终将稳定后的代码保存为 `.spec.ts` 文件，交由本地 Playwright 执行。

### 2. 定义测试意图

不直接写测试步骤，而是给出业务验收条件，例如：

> “用户登录后进入订单列表，点击‘新建订单’，选择商品并填写数量，提交后应在列表中看到新订单，且库存数量减 1。”

Agent 拿到这段话后，第一步是规划探索路径：先登录、进入订单页、记录当前列表项数、执行新建流程、最后校验列表变化及库存数值。

### 3. 逐步探索与代码生成

Agent 不是一次生成全量代码，而是按照以下循环工作：

1. **探索页面**：调用 `navigate` 打开目标页面，用 `snapshot` 获取可访问性结构（比完整 DOM 干净得多，去除了样式干扰）。
2. **定位关键元素**：根据 snapshot 中的角色、名称、层级，选择稳定的定位策略，优先顺序为 `getByRole` → `getByLabel` → `getByTestId` → 数据分析后认为稳定的文本。
3. **生成单步操作代码**：例如点击“新建订单”按钮，Agent 生成类似 `await page.getByRole('button', { name: '新建订单' }).click();`。
4. **立即执行验证**：通过 `evaluate` 或让工具执行该 Playwright 代码片段，观察是否成功触发预期变化。若失败，回到步骤 2 重新选择定位方式或加入 `waitFor` 等待。
5. **累积可工作的步骤**，直至完成整条用例，最终输出完整的测试文件。

这种边探索、边生成、边验证的方式，让脆弱的选择器在本地循环里就被替换掉，而不是等到 CI 挂了才由人修。

### 4. 稳定性加固

Agent 在重试过程中会自动学习页面规律，比如某些按钮点击后需要等待列表刷新。我们显式要求它在最终代码里加入以下模式：

- 每次改变状态后用 `waitForResponse` 或 `waitForSelector` 确认关键网络/渲染完成。
- 断言不再只比文本存在，而是用 `expect(listItems).toHaveCount(N+1)` 等更严格的逻辑。
- 把定位策略沉淀为 `testid` 映射表，后续回归时可以自动补上 `data-testid`。

## 踩坑点

**snapshot 信息不完整**：某些动态加载的组件（如 lazy 加载的 Modal）在初始 snapshot 中不可见，导致 Agent 认为元素不存在而放弃。解决办法是让它先尝试触发操作（如滚动、点击父级），等待 2 秒后重新 snapshot，给足渲染时间。

**Agent 趋向于“通过就行”**：一次跑通后热情地把 `expect(true).toBe(true)` 塞进去。我们必须通过 system prompt 强制要求每个测试至少包含一个对业务数据的断言，否则算作无效，触发重写。

**选择器蜜汁自信**：模型偶尔会执着于用 `text=确定` 而忽略页面有三个“确定”按钮。处理方式是在工具描述里强调，遇到重复文本时必须结合父容器 role 或邻近 label 缩小范围，否则直接返回失败信息让 Agent 反思。

## 可复用建议

- **建立项目级的可访问性规范**。Agent 依赖 role/label 信息来定位，如果前端组件缺乏合理的 ARIA 属性，定位质量会直线下降。花点时间补齐组件的 role 和 aria-label，受益的不只是测试。
- **维护一份选择器白名单/黑名单**。把团队已知不稳定的类名（例如 CSS Module 生成的 hash 类）加入黑名单，要求 Agent 避开。同时沉淀常用的 `data-testid` 命名规范，使 Agent 优先使用。
- **让 Agent 把失败修复过程写成注释**。最终测试文件里保留“原选择器 `text=提交` 因匹配到多个实例而替换为 `getByRole('button', { name: /^提交$/ })`”这样的注释，方便人审核时理解为什么代码长这样，加速团队成员对 AI 生成测试的信任建立。
- **分层执行**：本地开发时使用 Agent 交互式生成并调试；CI 中只运行已经稳定通过的生成用例，并定期（如每周）让 Agent 重新扫描页面定位是否需要更新，自动提交修复 PR。

## 总结

Agent 写 E2E 测试的价值不在于省掉敲键盘的时间，而是把“写→跑→挂→调”的疲劳循环内化到 AI 的自动化迭代里。通过 Browser MCP 工具让 Agent 获得了接近人类的探页能力，结合 OpenClaw 的任务规划与反思，最后产出的是经过实际运行验证、定位策略趋于稳健的测试代码。

目前这套方案让我们新页面的测试产出速度提升了约两倍，更重要的是回归失败的排查成本明显下降——因为大部分脆弱性问题在生成阶段就被修掉了。后续计划继续把 Agent 连接到视觉模型，用截图对比辅助断言，进一步降低复杂 UI 的测试维护成本。
