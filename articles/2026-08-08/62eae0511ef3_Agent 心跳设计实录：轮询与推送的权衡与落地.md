## 背景：Agent 为什么需要心跳

在 OpenClaw 的插件与自动化实践中，Agent 经常需要与外部进程、远程工具或 MCP server 保持长会话。例如：Agent 通过 MCP 调用了一个需要 5 分钟才能完成的推理任务，或者启动了一个后台子进程处理文件转换。在这些异步场景里，Agent 需要回答两个问题：

1. 对方还活着吗？（存活检测）
2. 结果是否就绪？（状态同步）

这就是 **heartbeat（心跳）** 要解决的事情。但如果心跳设计不当，要么把服务端打爆，要么让用户等得发慌，要么在网络抖动时崩溃。

## 问题：轮询 vs 推送的经典取舍

### 轮询（Polling）

Agent 每隔固定时间（如 2 秒）主动请求一次状态。

- **优点**：实现简单，无状态，对中间网络设备（代理、防火墙）友好，天生适应 HTTP 生态。
- **缺点**：延迟与资源消耗正相关。2 秒一次的轮询，平均延迟 1 秒，却可能产生每秒数十次无效请求；如果同时监控多个任务，请求量成倍增长。

很多初次实现会掉进“快一点就好”的陷阱，把间隔设成 200ms，结果直接把 MCP server 打满 CPU。

### 推送（Push / SSE / WebSocket）

任务端在状态变化时主动通知 Agent。

- **优点**：实时性好，资源占用低，无无效请求。
- **缺点**：需要维持长连接，处理断线重连、心跳保活、代理超时等问题；某些环境（如部分 serverless 平台、企业内部代理）甚至会阻断长连接。

理想情况当然是用推送，但工程上往往无法只选一种。

## 工程落地：一套可降级的心跳管理器

在 OpenClaw 插件的实际开发中，我为 Agent 侧实现了一个 `ChannelMonitor` 抽象，核心思想是 **“推送优先，轮询兜底”**，并且将控制面（心跳检测存活）与数据面（获取结果）解耦。

### 设计流程

```
  ┌─────────┐     握手阶段协商       ┌──────────┐
  │  Agent  │ ◄─────────────────► │ MCP Tool │
  └────┬────┘   transport: ws/ss http    └──────────┘
       │
       ▼
  ┌──────────────────────────┐
  │  ChannelMonitor          │
  │  - preferred: push       │
  │  - fallback: poll        │
  │  - retry with backoff    │
  └──────────────────────────┘
```

**步骤：**

1. **能力协商**  
   在 Agent 发起异步调用时，MCP 或插件返回一个 `MonitorConfig`，指明支持的传输方式：`"push: ws://...", "poll: GET /status"`。Agent 优先尝试建立 WebSocket/SSE 连接。

2. **推送通道建立与心跳**  
   WebSocket 连接成功后，双方约定应用层心跳：每 15 秒一次 Ping/Pong，连续 3 次无响应判定连接死亡。注意这里必须用**应用层心跳**而非仅依赖 TCP keepalive，因为很多代理会沉默地断开空闲连接，TCP 无法感知。

3. **降级到自适应轮询**  
   如果推送通道建立失败（如 WebSocket 被代理拒绝），`ChannelMonitor` 自动降级为轮询模式。关键优化是**根据任务剩余时间动态调整间隔**：刚提交任务时，大概率还在处理中，用较长间隔（如 5 秒）；进入预期完成窗口后，把间隔缩短到 1~2 秒。这能在不明显增加负载的前提下接近推送的响应速度。

4. **结果获取与状态同步**  
   无论哪种方式检测到“已完成”，Agent 使用专门的 **数据面请求** 去获取结果（例如 `GET /result`），而不是依赖心跳消息承载业务数据。这个分离能避免一条消息过大阻塞心跳、也能让重试逻辑更清晰。

### 踩坑记录

- **重连风暴**  
  当 MCP server 重启时，数十个 Agent 实例几乎同时检测到断线，又几乎同时重连，瞬时流量直接打挂服务。解决方案是**在重连间隔中加入随机抖动（jitter）**，并在客户端侧使用指数退避（1s→2s→4s→…，上限 30s）。

- **轮询导致连接泄漏**  
  在 Node.js 或 Python 环境里，如果每次轮询都 `fetch()` 而不复用连接，系统端口会迅速耗尽。务必启用 HTTP Keep-Alive 连接池，并设置合理的 `agent` 参数。

- **状态机不严谨**  
  出现过“已完成消息到达前又发起一次轮询，导致任务被重复消费”。必须为每个异步任务维护严格的状态机：`IDLE → RUNNING → DONE`，在任何路径上只要状态转为 DONE，后续心跳结果都应忽略或幂等处理。

- **推送通道的代理超时**  
  企业环境里的反向代理可能会在 60 秒后断开无数据 WebSocket。所以心跳间隔必须小于代理超时阈值，常见做法是 30 秒一次，足够安全。

## 可复用的设计建议

1. **推送优先，但永远提供轮询降级**  
   如果目标环境可控（例如自建 MCP server），用 WebSocket/SSE；否则至少提供基于 HTTP 的状态查询端点。

2. **控制面与数据面分离**  
   心跳只管“是否存活”和“状态变化”，不要夹带结果数据。这能降低耦合，让各自的重试和错误处理独立演进。

3. **客户端侧设置以下参数并暴露配置**  
   - `heartbeatInterval`：应用层心跳间隔（15-30 秒）
   - `missedHeartbeats`：失联多少次判死（3 次）
   - `pollInterval`：轮询基础间隔（2-5 秒）
   - `backoffLimit`：重连最大间隔（30 秒）
   - `jitter`：是否启用随机抖动

4. **运用自适应策略**  
   轮询间隔不应写死，可以根据任务预估耗时动态调整，在接近完成窗口时加速，既能降低负载，也能提升体验。

## 总结

心跳设计看似简单，但在 Agent 复杂的运行环境里，任何一刀切的方案都会在未来背刺你。**推送优先、轮询兜底**，配合动态间隔和谨慎的重连策略，是在插件、MCP 工具乃至 OpenClaw 自动化流程中比较经得起考验的组合。这次落地过程中最大的收获不是技术选型本身，而是认识到**心跳不仅是一个网络问题，更是一个状态同步的工程问题**——把控制和数据分离、严格管理状态机，远比你选择 WebSocket 还是 HTTP 更重要。
