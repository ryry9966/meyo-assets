## 背景：Agent 的“记忆”为什么需要两种召回？

在给 OpenClaw 搭建长期记忆模块时，几乎绕不开 `memory_recall` 这个接口。无论是用内置的 MemoryPlugin，还是通过 MCP 桥接外部知识库，存储动作记录、用户偏好、文档片段后，都需要一种方式把它们从记忆库里“拽”出来。目前主流实现都提供两种召回路径：语义搜索（向量检索）和全文搜索（关键词/BM25）。问题是——在生产环境里，单押一种往往会翻车。

我之前在一个 OpenClaw 自动化脚本中，需要根据聊天历史中的报错信息，召回过去类似问题的解决步骤。记忆库里存着几百条运维笔记，包括“数据库连接池耗尽导致重启”、“因环境变量 DATABASE_URL 配置错误构建失败”等。用默认的语义搜索召回时，查询“数据库连接问题”的 top-3 结果里，两条不相关却相似度很高——“Redis 连接超时”和“消息队列积压告警”。而全文搜索只匹配到“DATABASE_URL”那条，却漏了真正相关的“连接池耗尽”。

这不是个例。语义搜索擅长理解“意图相近”，但召回边界模糊，容易淹在噪声里；全文搜索精确命中字面，却对同义表达毫无反应。

## 问题定义

假设你在 OpenClaw 中通过类似下面的方式配置了 memory 后端：

```python
from openclaw import MemoryPlugin, MemoryBackend

memory = MemoryPlugin(
    backend=MemoryBackend(
        vector_store="qdrant",
        fulltext_store="sqlite_fts5",
        embedding_model="text-embedding-3-small"
    )
)
```

每次 `memory.add(content, metadata)` 后，系统会同时生成稠密向量和倒排索引。但 `memory.recall(query)` 到底该走哪个通道？两种模式各自的失效场景是什么？能不能做一个工程上可维护的选择？

## 做法与实验

我在一个离线脚本里构建了 120 条 mock 运维记忆，覆盖三类场景：配置错误、资源瓶颈、CI/CD 异常。每条记忆长度 40-200 汉字，确保信息密度接近真实日志。

使用 OpenClaw 的 `recall` 接口分别测试 **semantic** 和 **fulltext** 模式：

```python
# 语义召回
results_sem = memory.recall(query, mode="semantic", top_k=5, min_score=0.7)

# 全文召回
results_fts = memory.recall(query, mode="fulltext", top_k=5)
```

针对 15 个典型查询（如“上次的数据库连接报错”、“k8s pod 突然重启”、“pipeline 缺依赖失败”），手工标注理想召回结果，计算 Precision@5 和 Recall@5。

关键发现：
- 语义搜索对口语化、意图模糊的查询效果更好。例如问“为什么构建炸了”，能召回“CI build 因 libssl 缺失失败”。全文搜索几乎零命中。
- 全文搜索在**专有名词、错误码、配置项键名**等查询上优势明显。查询“DATABASE_URL”时，语义搜索会混入“MySQL 连接超时”，而全文搜索能精准返回那条具体的记忆。
- 中文分词对全文搜索的影响巨大。SQLite FTS5 自带分词器对中文毫无作用，必须编译时开启 `icu` 或使用 jieba 分词插件，否则“环境变量”无法匹配“环境”+“变量”的组合。

## 踩坑点

1. **语义相似度阈值是个暗坑**  
   我最初把 `min_score` 设成 0.75，本以为能过滤噪声，结果大量相关但表述差异大的记忆被丢弃。不同 embedding 模型的分数分布差异很大，需要用验证集校准阈值，而不是照搬教程的 0.7。

2. **全文索引的“冷连接”问题**  
   当使用 Qdrant+SQLite 双后端时，如果只启用了语义模式，SQLite FTS5 的索引从不更新，导致突然切换全文搜索时召回为空。必须在写入流程中同时维护两个索引，或开启自动同步。

3. **混合召回不是简单拼结果**  
   直接取 `results_sem + results_fts` 并去重，会导致排名混乱。实践中至少需要加一层基于 recency 或 BM25 分数的重排序，否则用户看到的第一条可能是不相关的语义噪声。

4. **Embedding 模型的上下文长度限制**  
   长记忆被截断后再向量化，会丢失关键信息。当单条记忆超过 8k token，必须切片存储并赋予相同 meta_id，召回时再做聚合。

## 可复用建议

**优先语义，并用全文兜底及精排**。具体实现：

- 在 OpenClaw 的 memory recall 前加入一个轻量级判断：若查询中包含特殊标记（如 `env:`, `config:` 前缀、错误码、明显的关键词），则激活全文搜索并提升其权重。
- 默认流程：先语义召回 top_k=10（阈值 0.65），然后对这 10 条结果使用全文查询匹配关键实体，若命中则优先展示。未命中则按原始向量分数排序。
- 引入 `Cross-Encoder` 小模型做最后精排（如 `ms-marco-MiniLM-L-6-v2`），在 CPU 上也能毫秒级完成，能榨出显著精度提升。
- 中文场景务必引入外部分词。开放替代方案：将全文存储切成 Elasticsearch 并配置 IK 分词器，或直接在 SQLite 中使用 `jieba` 自定义 tokenizer。

决策树可以这样记：长尾口语意图 → 语义；精确代码/配置项查找 → 全文；两者混合 → rerank。

## 总结

语义搜索 vs 全文搜索不是选择题，而是如何组装的问题。在 Agent 的长记忆模块里，语义召回负责“理解你大概在问什么”，全文召回负责“找到你需要的那个确切的字符串”，再配上简单的重排序机制，就能用很小的工程代价换取明显的召回质量提升。别在选型上纠结太久，真正要花时间的是设计更新链路、阈值校准和分词适配——这些才是决定“记忆好用与否”的幕后功臣。
