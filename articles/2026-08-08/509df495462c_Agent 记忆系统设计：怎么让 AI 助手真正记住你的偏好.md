# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景：一个“失忆”的助手能走多远

你花半小时告诉 AI 助手的项目背景、沟通风格、代码规范偏好，第二天打开对话窗口，它又像第一次见面一样问你：“请问你想用什么技术栈？”这不是虚构，而是绝大多数基于 OpenAI/Claude 等模型的 Agent 和聊天体验的现状——上下文窗口内是聪明的，窗口之外一片空白。

在 OpenClaw 这类 Agent 平台上，我们把流程编排、工具调用、多步推理做得越来越成熟，但缺少一层稳定的**持久记忆**，很多个性化场景就难以落地：AI 没法记住你偏爱 Python 3.10 的类型提示风格，不记得上次排障时已经排除过哪些原因，也无法从历史对话里提炼出“你讨厌被打断”这种工作习惯。

要让 Agent 从“一次性工具”变成真正跟随你的助手，记忆系统是绕不开的工程题。

## 问题拆解：记忆不是简单的日志

直接保存全部对话历史会遇到三个核心问题：

1. **检索效率低**：全量对话太长，Agent 每次都要在几万 token 里翻找相关片段，延迟高、成本高，还容易超过上下文限制。
2. **信息噪声多**：大量“好的，已收到”“正在处理中”这类交互对个性化没有价值，反而淹没了关键偏好。
3. **更新与冲突**：偏好是会变的，两个月前你说“尽量用 requests 库”，现在你统一换成 httpx，旧的记录必须被覆盖或降权，而不是永远停留在过去。

工程上，我们要的是一个能**提取、存储、检索、更新**的记忆系统，它要轻量、可控，并且能和 Agent 的工具链自然集成。

## 实践方案：基于 MCP 的轻量记忆服务

我采用的方案是自建一个 Memory MCP Server，通过标准协议对 OpenClaw 的 Agent 暴露记忆读写工具，这样任何遵循 MCP 的 Agent 都能直接调用，不用改框架内部代码。

### 一、记忆分层设计

将记忆分成三种粒度，分别用不同策略处理：

- **事实性偏好（Profile）**：键值对或简单 JSON，例如 `{"prefer_language": "Python 3.11", "code_style": "type hints mandatory"}`。用 SQLite 存储，直接全量注入 system prompt，体量小、不需要检索。
- **对话摘要（Episodes）**：每次有意义的交互结束后，让 LLM 生成 2~3 句话的摘要，并打上标签（如 `bug-fix`, `deployment`, `meeting-notes`）。摘要文本做 embedding，存入本地 ChromaDB，按语义相似度检索最近 5~10 条。
- **实体与关系（Facts）**：从对话中提取“项目名：OpenClaw-CN 后端”，“负责人：张三”这样的三元组，存在 SQLite 的 facts 表里，支持精确查询和覆盖更新。

这个分层带来的好处是：需要快速偏好时只读 Profile，需要上下文时只检索相关摘要，不会把整本“回忆录”塞给模型。

### 二、MCP 工具接口

提供给 Agent 的工具分为两类：

- **写入类**：
  - `add_user_preference(key, value)` – 直接覆盖写入偏好。
  - `record_episode(summary, tags)` – 存入摘要并生成 embedding。
  - `update_fact(subject, predicate, object)` – 以 subject+predicate 作为联合主键 upsert。

- **查询类**：
  - `get_user_profile()` – 返回完整 Profile JSON。
  - `search_memory(query, n=5)` – 用 query embedding 检索相关摘要，返回摘要列表。
  - `get_facts(subject)` – 按主题查询事实。

Agent 根据当前任务自行决定何时读写记忆，而不是被动等待系统注入。例如在一次部署排障中，Agent 发现用户之前已经排查过端口占用问题，可以通过 `search_memory("端口占用排查")` 找到上次的摘要，直接给出“上次已确认非端口问题，建议检查防火墙规则”的答复，极大减少无效重复。

### 三、记忆的生命周期管理

光存不清理很快就会膨胀。我在记忆服务里加了两条规则：
- **重要性评分**：每次存储摘要时让 LLM 输出一个 1~10 的重要性分，低于 3 分的内容只保留 7 天。
- **基于时间的衰减**：Profile 和 Facts 中的项，如果超过 30 天未被提及，会在查询时自动附加 `(可能已过时)` 标记，让模型自行判断是否沿用，而不是突然删除导致信息丢失。

## 踩过的坑

1. **LLM 抽取记忆不准**  
   让一个模型从对话里提取结构化摘要和三元组，本身又引入一次推理错误。最开始我用同一个模型同时干对话和记忆，结果经常把“不要用 asyncio”总结成“偏好 asyncio”。后来改成**固定 schema + few-shot 示例**，准确率提升明显。一定要对提取后的内容做格式校验，发现不符合 schema 的直接丢弃，并在工具返回时给 Agent 报错，让它可以重试或跳过。

2. **向量检索的语义漂移**  
   用“用户喜欢什么样的日志输出”去检索，结果返回的全是关于“日志轮转策略”的摘要。原因在于 embedding 对短查询的上下文不够敏感。解决办法是在 embedding 前把用户查询扩充为完整句子，例如“请帮我找关于日志输出格式偏好的历史记录”，同时检索时加 `tag` 过滤，先缩小范围。

3. **并发写入冲突**  
   同一个用户可能在两个会话里同时更新偏好，SQLite 的写入锁让其中一次失败。改成 WAL 模式 + 带重试的写入逻辑可以缓解，但根本上要用单用户级别的内存锁，或者在应用层排队。

4. **隐私与可控**  
   记忆系统必然要存用户数据。需要提供 `/memory/app` 这样的 HTTP 端点让用户查看、单条删除或清空记忆。Agent 在首次写入记忆前，必须申明“我会记住你以下偏好，是否允许？”——这不仅是合规要求，也是赢得信任的必要姿态。

## 可复用建议

- **从 Profile 开始，逐步加复杂度**：不要一上来就做全功能记忆。先用 SQLite 存键值偏好，再引入摘要检索，最后做事实抽取。每一步都能独立交付价值。
- **用 MCP 解耦记忆与 Agent**：哪怕你只是在 OpenClaw 里跑一个实验性 Agent，把记忆做成 MCP 工具，以后换框架或换模型，记忆层完全不用动。这也方便单独调试记忆服务。
- **始终保留“遗忘”机制**：记忆系统最大的敌人不是“记不住”，而是“记住了不该记住的东西”。无论是过期自动标记还是手动删除，都必须在设计早期就考虑好。
- **把记忆当作辅助，而非权威**：永远让模型保留“可能过时”的判断权。把记忆作为上下文的一部分，而不是硬约束。当存疑时，允许 Agent 向用户确认。

## 总结

Agent 记忆系统不只是一个技术组件，它定义了助手与用户之间“关系”的连续性。上面这套基于分层存储 + MCP + 带权重的生命周期管理的方案，已经在 OpenClaw 的自用助手和几个自动化工作流里跑了一段时间，准确率和延迟都控制在可接受范围。

如果你也在让 Agent 干更长期的工作，不妨从一个最朴素的 `add_user_preference` 开始，它会比你预想中更快成为不可或缺的一块拼图。
