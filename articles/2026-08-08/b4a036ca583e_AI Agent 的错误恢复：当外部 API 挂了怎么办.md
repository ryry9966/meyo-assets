# 背景：你的 Agent 有多依赖外部世界？

在 OpenClaw、MCP 插件或自动化工作流的实际运行中，Agent 往往不是活在真空里。它需要调用外部 API —— 天气服务、搜索引擎、数据库、内部微服务、对象存储…… 任何一个链路抖动，都可能导致一次任务执行失败。

典型的错误场景：

- 第三方 API 突然返回 500，且持续几分钟；
- 速率限制（429）来得比预期更早；
- 下游服务部署导致短暂不可用；
- 网络超时，但业务操作其实已部分执行（非幂等噩梦）。

如果不做任何处理，这些错误会把 Agent 拖入不可恢复的状态：LLM 拿到一串异常堆栈后胡乱解释，工具重复调用耗尽 token，或者整个工作流中断，需要人工重跑。

本文旨在给出一种工程上可落地的错误恢复方案，面向已经或正在把 Agent 接上真实工具的开发者。

# 问题定义：错误不是异常，是常态

设计外部 API 调用时，首先要接受一个前提：**没有任何外部服务是 100% 可用的**。因此，错误恢复不是“出了问题再修”，而是作为调用逻辑的一部分提前设计。

我们需要处理的不只是“API 挂了”，还包括：

- 临时性错误（可重试）
- 持续性错误（需熔断）
- 业务错误（如参数非法，不应重试）
- 半成功操作（需补偿或查询实际状态）

Agent 的特殊之处在于，错误信息最终会喂给 LLM。如果工具返回的内容模棱两可，LLM 可能会发明一个“解决方案”继续执行，造成更大偏差。所以错误恢复的另一个目标是 **生成可被 LLM 正确理解的错误摘要**。

# 做法 / 步骤：从单次调用到韧性工具

## 1. 为每一次外部调用设置三层防护

直接将 `requests.post` 或 `fetch` 暴露给 Agent 是危险的。需要抽象出一个公共的 API 调用层，包含：

- **重试策略**：仅针对可重试错误（网络超时、429、5xx，且方法幂等 GET/PUT）。使用指数退避 + 随机抖动，避免惊群效应。例如初始等待 1s，每次加倍，最大 5 次，总窗口控制在 30s 内。
- **熔断器**：基于滑动窗口统计失败率。连续失败超过阈值（如 10 次中 5 次失败），直接短路，立即返回降级结果，不再尝试真实调用。冷却一段时间（如 30s）后进入半开状态试探。
- **超时控制**：永远不要依赖默认超时。根据 API 的 P99 延迟设置 connect timeout 与 read timeout，并在 Agent 侧设置更宽松的总执行时限。

如果使用 MCP 工具封装外部调用，这些逻辑可以天然放在 server 端，Agent 只看到工具返回的结构化结果。

## 2. 定义工具返回的统一错误结构

错误信息需要包含三个部分，方便 LLM 做出决策：

- **错误级别**：`transient`（可重试）、`permanent`（不可重试）、`degraded`（已降级但有部分数据）
- **人类可读描述**：简明告知发生了什么，如“搜索引擎 API 暂时不可用，已使用本地索引作为替代”
- **建议动作**：可选，比如“请简化查询条件再试”、“建议用户稍后重试”、“该操作已自动降级，继续执行不会丢失主要信息”

例子（JSON 风格）：
```json
{
  "error_level": "transient",
  "message": "GitHub API 返回 503，已重试 3 次仍失败",
  "suggestion": "可暂时使用本地缓存的数据，请向用户说明数据可能是 5 分钟前的版本"
}
```
不要直接把异常堆栈扔给 LLM，那会污染上下文。

## 3. 降级与兜底：让 Agent 优雅失败

并非所有失败都需要终止任务。按场景准备降级策略：

- **读操作**：返回缓存数据，并标注过期时间。对于实时性要求不高的场景（如文档检索），旧数据远好过无数据。
- **写操作**：将请求写入持久化队列，异步重放。需告知 Agent “操作已受理，预计稍后完成”。
- **多供给切换**：主 API 不可用时切换到备选 API（如从 Google Maps 切换到 OpenStreetMap），但需注意数据模型差异，在工具层做好映射。
- **默认值填充**：当某个非关键数据点获取失败，使用默认值并继续。比如天气 API 故障时用“晴朗”代替，并在输出中注明假设。

Agent 的工作流设计应允许工具返回降级标记，LLM 看到 `degraded` 后可以调整后续步骤，或在最终回复中诚实说明不确定性。

## 4. 让 Agent 参与恢复决策

错误恢复的最后一步是把控制权交还给 LLM。工具返回的结构化错误会被投喂到下一次推理中。此时，Agent 可以：

- 判断降级结果是否可接受，继续执行；
- 请求用户提供更少/更多的信息后重试；
- 对非关键失败直接忽略，聚焦主要目标；
- 当多次重试后仍为 `transient`，主动终止并向用户报告。

为了提高决策质量，可以在 system prompt 中给出错误处理指南，例如：“当工具返回 transient 错误且已附带降级数据时，优先使用降级数据继续，但必须在最终回复中明确指出数据可能不完整”。

# 踩坑点

1. **所有错误都重试**：写操作、非幂等 POST 盲目重试可能造成重复下单或重复扣款。务必区分请求方法是幂等还是非幂等，非幂等操作应转入查询补偿逻辑（如查询是否已创建）。
2. **无界重试耗尽资源**：Agent 运行时间有限（尤其有 token 上限或超时），无限重试会吃掉所有预算。必须设置最大重试次数和总耗时限制，到达后强制降级或失败。
3. **熔断阈值凭感觉设置**：阈值太灵敏，正常抖动就熔断，导致降级被频繁触发；阈值太迟钝，等到发现时系统已经过载。建议基于历史流量统计，设置窗口大小（如 60s）和最小请求量（避免冷启动误判）。
4. **忽略部分成功**：一个 API 批量调用中部分成功、部分失败，如果简单返回整体失败，会丢失已成功的操作。这种情况应返回详细的成功/失败列表，让 Agent 处理差异。
5. **熔断后状态不透明**：Agent 不知道工具已处于熔断状态，会反复尝试并得到相同错误，浪费推理。工具应在返回的错误中明确说明“当前处于熔断状态，冷却剩余 20 秒”，让 Agent 做合理等待或绕行。

# 可复用建议

- **封装一个内部的 API 调用工具工厂**：将重试、超时、熔断、日志监控统一封装，所有外部调用都经过该工厂产生，避免每个工具开发者重复造轮子。
- **使用 MCP 中间件**（如果你已经在用 MCP）：在 MCP server 端实现一个 `mcp-tool-wrapper`，负责错误分类和统一返回格式，Agent 端无需感知底层细节。
- **记录错误上下文**：每一次外部调用失败都应记录完整的 request、response、重试次数、最终动作（重试成功/降级/失败），便于后续优化阈值和发现上游问题。
- **为关键路径编写降级演习**：定期手动关闭某个依赖服务，观察 Agent 行为是否符合预期，而不是等到线上故障才第一次验证。
- **让 LLM 可观测错误恢复过程**：在 OpenClaw 或自建编排中，将工具返回的错误信息作为可观测事件输出，便于调试和审计。

# 总结

AI Agent 的错误恢复不是附加功能，而是系统韧性的基线。当外部 API 挂了，真正可靠的 Agent 应该能检测错误类别、有策略地重试、果断降级，并清晰地与用户沟通当前状态。在这个过程中，把每次外部调用都当作可能失败的远程资源来看待，将错误信息设计为 LLM 友好格式，并结合熔断、缓存、异步队列等常见后端模式，才能让自动化工作流在真实世界的不可靠之上平稳运行。

不要等到 API 真的挂了才去救火。今天就可以检查一下你的工具代码：有没有重试？重试安全吗？失败时 Agent 看到了什么？
