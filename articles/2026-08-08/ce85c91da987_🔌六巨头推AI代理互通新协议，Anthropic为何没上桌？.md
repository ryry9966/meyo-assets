最近科技圈被一条消息刷了屏：Google、Microsoft、OpenAI、Meta、Amazon、Nvidia 六家巨头联合发布了一项全新的开放协议——Agent2Agent Protocol（A2A），目标直指让不同公司、不同框架的AI代理实现自由对话与任务协作。协议一出，很多人立刻联想到 Anthropic 去年力推的 MCP（Model Context Protocol），二者无论是命名风格还是技术愿景都有几分神似。有趣的是，这次联合发布的长名单里，唯独没有 Anthropic 的身影。自家的协议刚被行业讨论，转眼巨头们就另起炉灶，这背后到底是技术路线之争，还是生态卡位的阳谋？今天这篇就掰开来聊聊。



## 为什么AI代理需要“对话”？

过去两年，大模型厂商都在卷单体的智商和能力，但从2024年开始，风向变了——AI Agent（智能代理）成为焦点。单个模型再强，也只能在限定环境里做任务，真正的企业级应用需要多个Agent协作：一个负责查询数据库，一个负责写代码，一个操作CRM，还有一个统筹调度。

这就碰到了一个老问题：不同的Agent通常由不同团队用不同框架开发，就像让一群操着不同语言的人合作修一栋楼，没有翻译就没法干活。如果想让 Google 的 Agent 调起 Microsoft 365 里的日程、再交给 OpenAI 的代码助手处理脚本，靠现在的私有接口得对接 n×m 次，成本高得离谱。

所以，一个通用的“代理间通信语言”就成了刚需。A2A 协议正是为了解决这个：它定义了一套标准的发现、协商、任务传递和结果反馈机制，让 Agent 可以像调用 API 一样互相收发“任务卡片”（Task），而不需要知道对方底层是 GPT-5 还是 Gemini。

## A2A协议：六个关键设计，一看就懂

官方放出的协议草案里，A2A 的骨架并不复杂。我挑出六个最能体现其设计哲学的点：

- **基于HTTP/JSON的RESTful风格**：沿用了 Web 开发者最熟悉的技术栈，Agent 之间通过 HTTP POST 交换 JSON 格式的消息，门槛很低。
- **任务卡片（Task）模型**：不是简单的“一问一答”，而是把一次协作抽象为一个可追踪、可暂停、可恢复的 Task，包含状态、输出结果、附件等字段，更贴近真实工作流。
- **能力发现（Agent Card）**：每个 Agent 对外暴露一张标准化的能力卡片，描述自己能做什么、安全策略、输入输出格式，其他 Agent 无需提前配置就能动态发现和调用。
- **异步推送与SSE**：长耗时任务不能一直等，A2A 引入了 Server-Sent Events 机制，让被调 Agent 可以实时把进度推回发起方，用户体验提升一大截。
- **安全与信任边界**：协议本身不绑定认证方式，但预留了 OAuth2、mTLS 等扩展点，企业可以叠加自己的零信任策略。
- **多模态扩展预留**：虽然初版主要处理文本和结构化数据，但 Task 的 output 里已经设计了 artifacts 字段，可以承载图片、文件等，明显在为多模态 Agent 做准备。

从工程角度看，A2A 很像一个“去中心化的 Agent 总线”，背后是六家巨头对自身生态互通的强烈需求。毕竟，Google 不希望自己的 Agent 只能在 Google Workspace 里打转，OpenAI 也不愿意 ChatGPT 沦为信息孤岛。



## MCP vs A2A：这不是“重复造轮子”

很多人看到 A2A 第一个念头就是：“这不就是 Anthropic 的 MCP 吗？” 二者确实撞脸，但定位有本质区别。做个对比会更清楚：

- **MCP（Model Context Protocol）**：解决的是模型与外部工具/数据源之间的连接问题，是一种 **客户端-服务器模式**。Host（比如 Claude Desktop）通过 MCP 客户端访问本地或远程的 MCP 服务器，服务器暴露具体的工具和资源。本质上是一套让模型“伸手拿东西”的协议。
- **A2A（Agent2Agent）**：解决的是代理与代理之间的协作问题，更偏向 **对等网络模式**。重点是让两个已经具备工具调用能力的 Agent 互相委派任务，而不是让 Agent 去拿一个工具。

用一个比喻：MCP 像是给厨师一套标准接口的炉灶和冰箱，厨师（模型）可以用它完成烹饪；A2A 则像是让两个厨师用同一套点菜单互相传活——一个负责切菜，一个负责炒菜，配合出菜。

技术路线上，MCP 更底层、更偏向 sessionful 的长连接，用 JSON-RPC 交互；A2A 基于 RESTful，更轻量、更容易穿透企业防火墙。二者并不直接冲突，甚至可以互补：一个 Agent 既可以通过 MCP 获取本地工具，又通过 A2A 向其他 Agent 派活。但问题在于，标准一旦被六巨头联手推成事实，MCP 的生存空间就会受到挤压——毕竟开发者更愿意押注有 Google、OpenAI、Microsoft 背书的协议。

## Anthropic为何缺席？三种可能推演

Anthropic 没坐上这张桌子，官方的沉默让猜测四起。从技术和商业逻辑看，大致有三种可能：

1. **路线分歧，不愿妥协**  
   Anthropic 一贯重视安全与对齐，MCP 的设计里有大量关于安全边界、用户许可的精细控制。如果 A2A 为了兼容更多厂商，在安全层面做了简化，Anthropic 可能认为这不符合自己的原则。另外，MCP 已经在年底被集成到 Claude 生态、Zed 编辑器、Sourcegraph 等产品中，有了小范围落地，此时放弃自己的标准去追随别人，脸上挂不住。

2. **被故意排除在外**  
   六巨头中有三家是云平台（Google、Microsoft、Amazon），而 Anthropic 与 Amazon 关系极其紧密（AWS 是其主要投资方和基础设施），但这次 Amazon 在列，Anthropic 不在，显得微妙。一个猜测是：巨头们想握住 Agent 层标准的主导权，而 Anthropic 的 MCP 已经抢跑，如果拉它入伙，谈判过程必然涉及大量 MCP 既有设计的争议，反而拖慢协议速度。干脆先“六家锁仓”，把生米煮成熟饭。

3. **战略观望，后发优势**  
   也不排除 Anthropic 主动选择不上车。A2A 目前还只是 0.1 版草案，实际落地需要时间。如果协议在某些场景下暴露出安全缺陷，Anthropic 届时再带着更成熟的 MCP 2.0 入局，反而可能后发制人。况且 MCP 已经开源，社区贡献者仍可打通 MCP 与 A2A 的桥接，不至于把自己彻底关在生态外。



## 开发者该怎么办？三条务实决议

热闹归热闹，手里有活要干的工程师最关心的是：我今天写的 Agent 该接哪个协议？三条建议：

- **不要立刻选边站，先用适配器模式隔离**  
  在协议尚未固化的阶段，最好的策略是把你 Agent 的通信层抽象出来，内部定义一套中立的消息接口，然后分别写 A2A adapter 和 MCP adapter。这样无论最终谁赢，切换成本都极低。已经有开源项目开始做这类双协议桥接，值得关注。

- **关注任务卡片模型，它可能成为事实标准**  
  无论协议信封怎么变，A2A 提出的 Task 抽象（状态、里程碑、artifact）非常贴合实际工作流，即使未来协议细节调整，这种设计范式大概率会留下来。现在就在你自己的 Agent 里用类似的结构管理任务，将来对接任何协议都会顺滑。

- **安全上下文必须自主可控**  
  A2A 把认证授权丢给了实现层，千万别图省事直接用简单的 API Key 硬编码。任何跨组织 Agent 通信，至少拉起来一个 OAuth2 的 token exchange，并对传入的任务做严格的能力范围检查。别让你的 Agent 被别人的任务卡片当枪使。

## 冷思考：开放协议背后的生态棋

最后泼一盆冷水：开放协议从来不只是技术问题，更是生态控制权的争夺。当年 Kubernetes 能一统容器编排，靠的也不是纯粹的技术优雅，而是 Google 让利、红帽站台、AWS 被迫跟随的合纵连横。今天 A2A 的六家，每家都有自己的 Agent 平台和云服务，协议之下，谁家的 Agent 发现机制更优先、谁的云上跑得最顺滑，都会悄悄倾斜天平。

对普通开发者来说，最健康的姿势是：**用开放的东西，但要保持自己迁移的能力。** 管它是 MCP 还是 A2A，你的 Agent 的核心推理与决策逻辑才是真正的资产，通信协议终究只配做一层可插拔的外壳。别把房子建在别人的地基上——这句话在今天仍然成立。
