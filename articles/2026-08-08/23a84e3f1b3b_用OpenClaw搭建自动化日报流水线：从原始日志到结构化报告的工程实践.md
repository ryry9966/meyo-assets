## 背景

团队每天需要汇总多个系统的运行日志、版本发布记录、告警事件和关键业务指标，整理成结构化日报同步给干系人。手工从Grafana、Elasticsearch、飞书群消息、GitLab commit log等不同来源拉数据、核对、排版，耗时1小时以上，且容易遗漏关键变更。在引入OpenClaw作为自动化Agent底座后，我们尝试构建一条“原始日志→结构化报告”的端到端流水线，将日报生成时间压缩到5分钟内，并保证输出格式稳定、信息不缺失。

这篇文章记录整个落地过程的关键设计、踩坑点和可复用的工程化建议，适合已经在使用OpenClaw/MCP/Agent或计划用这类工具做自动化报告生成的技术同学。

## 问题拆解

看似简单的“生成日报”，拆开后有四个硬骨头：

1. 数据源分散：ES慢查询日志、K8s事件、Prometheus告警、GitLab MR记录、内部运维平台API，每种数据格式和鉴权方式不同。
2. 上下文窗口有限：一天内的原始日志量可能远超LLM的上下文窗口，直接灌入会导致token溢出或成本爆炸。
3. 结构化输出不稳定：即使要求输出Markdown表格，模型也经常漏字段、多加字段、或改变层级。
4. 多步工具调用容易中断：一条日报可能涉及10+次MCP工具调用，中间任意一次网络超时或权限错误都会导致整个流程失败，很难重放。

## 做法与步骤

### 整体架构

```
定时触发 (cron) → OpenClaw Agent → MCP tools (数据采集)
                        ↓
                  预处理脚本 (本地) → 注入Agent会话
                        ↓
                  分层摘要 → 结构化日报 → 飞书 Webhook 推送
```

- **定时触发**：Jenkins cron job，工作日8:30执行。
- **OpenClaw Agent**：使用GPT-4o，通过`openclaw run`以headless模式执行一个预定义的workflow文件。
- **MCP tools**：封装了ES查询、K8s API、GitLab API、运维平台接口，统一走MCP协议，在OpenClaw里直接作为function calling工具使用。
- **预处理脚本**：在Agent调用前，先用Python脚本从各个工具拉取原始数据到本地NDJSON文件，粗略过滤掉debug/trace级别日志，并统计各时间段的事件计数。这一步作为“粗加工”喂给Agent，而不是让Agent直接面对海量原始日志，大幅减少token消耗和幻觉概率。

### 第1步：数据采集与粗过滤

我们在MCP server侧暴露了一个`fetch_daily_raw`工具，背后实际是调用预置的多个数据源聚合脚本。该工具返回一个结构体：

```json
{
  "alerts": [...],
  "deployments": [...],
  "es_slow_queries_count": 45,
  "k8s_restarts": [...],
  "business_metrics": {...}
}
```

每类数据都已做过去重、按时间排序，且单条记录压缩到最多300字描述。这一步注意点：MCP tool返回的字符串总长度必须控制在模型上下文窗口的30%以内，留给后续推理和格式化足够空间。

### 第2步：分层摘要提示词

我们将日报生成拆成两个Agent步骤，避免“一步出全文”带来的格式漂移。

**第一层：事实摘要**

提示词要求模型对`fetch_daily_raw`返回的每一类事件，生成不超过5条的要点列表，格式为：

```
- [类别] 时间 简要描述 (涉及系统/负责人)
```

例如：
```
- [告警] 02:15 ES集群yellow，持续12分钟，已自动恢复 (搜索团队)
- [发布] 10:30 订单服务v2.3.1上线，包含慢SQL优化 (支付组)
```

这一步的输出本质上是脱敏、降噪后的摘要数组。

**第二层：日报组装**

将第一层输出作为上下文，加上一个固定的Markdown模板，要求模型严格按模板填充。模板中每个章节的标题固定，模型只需将对应类别的要点插入到正确位置。我们甚至在system prompt里写了一个“你必须严格复制以下Markdown结构，不要新增章节”的强制指令，并在提示词末尾追加一个校验提示：“输出前检查：是否包含‘告警摘要’、‘发布记录’、‘系统事件’、‘关键指标’四个一级标题？”——实测这种末尾检查提示能显著降低结构变异。

### 第3步：发送与归档

生成的日报再通过一个MCP工具`send_feishu_message`推送到指定群聊。为了保证归档，Agent同时将Markdown正文上传到内部文档库（通过API），以便日后搜索。

## 踩坑实录

**1. Token超限导致摘要不完整**

初期我们让Agent直接从ES查询当日全部慢日志，结果返回字符串超过3万token，Agent在生成摘要时频繁截断，丢失后半天的数据。解决方案正是上文提到的预处理粗加工：只给Agent“统计后的代表样本”而非全量日志，每条样本限制100 tokens。对于必须展示的明细，改为提供“点击查看详情”的链接，而不是把内容塞进日报。

**2. MCP工具超时未重试导致整条流水线崩溃**

OpenClaw调用MCP tool时，默认超时时间较短（约30秒）。某天ES查询因集群负载高而耗时45秒，直接抛错，整个workflow中断。我们的修复：在MCP server侧增加指数退避重试（最多3次），同时在Agent workflow中对`fetch_daily_raw`的结果做非空校验，如果某个类别为空，会触发一次降级重跑，只拉取最近2小时数据兜底。

**3. 结构化输出中的“幽灵字段”**

模型有时会自作主张加一段“风险评估”或“建议”，破坏模板结构，导致飞书消息解析异常。最终我们用了一个简单的后处理脚本，在推送前用正则匹配“## ”标题数量，检查是否为4个，若不是则拒绝发送，并自动触发一次“修复日报结构”的低成本gpt-4o-mini修补调用，成功率95%以上。

**4. 时区与日期偏移**

Agent默认使用UTC时间，而业务系统的日期是北京时间。我们在`fetch_daily_raw`返回的每条记录中都显式注入了`+08:00`的日期标签，并在提示词中固定了“所有时间均为北京时间”的声明，避免模型自行推断产生8小时偏差。

## 可复用建议

- **预处理是降本提质的核心**：不要让Agent直接面对原始日志海，先做聚合、去噪和截断。可以把预处理做成一个独立微服务，通过MCP暴露，方便复用。
- **模板化 + 末尾检查提示，保证结构可靠**：用固定Markdown骨架并限制模型仅做内容填充，显著降低格式变体。
- **关键步骤设置兜底和重试**：MCP tool调用必须考虑超时、空返回、部分失败的情况；Agent workflow中应加入判断分支，避免整条流水线雪崩。
- **日报归档与可检索同样重要**：自动化日报不但要发出，还要存下来，方便后续故障回溯或AI复盘。建议推送到工具库的同时落一份Markdown到Git仓库。
- **用指标监控流水线健康度**：给流水线加上简单的成功率、耗时、重试次数指标，当成功率低于95%时告警，避免日报静默丢失。

## 总结

我们通过OpenClaw Agent + MCP工具 + 轻量预处理的组合，将原本需要人工1小时的日报生成压缩为全自动5分钟流水线，输出格式稳定，信息覆盖完整。核心经验是：工程化的自动化不是“让AI做所有事”，而是通过合理的任务分层、容错机制与模板约束，让AI和传统脚本各司其职。希望这些踩坑和方案能为同样在搭自动化报告管线的同学提供一些可直接落地的参考。
