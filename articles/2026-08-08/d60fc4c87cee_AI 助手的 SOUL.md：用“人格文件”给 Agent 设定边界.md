## 背景：从一个散落在代码里的 system prompt 说起

在 DIY Agent 或者搭建自动化助手时，几乎每个人都会经历同一个阶段：把 system prompt 硬编码在脚本开头，每次改一句调调就重新部署，很快 prompt 就变成一坨不可维护的文本。更糟的是，多人协作时大家各写各的，助手时而冷漠、时而过份热情，甚至在某次更新后突然说出不该说的话。

为了把“助手人格”和“能力边界”真正管起来，我们开始在项目里引入一个标记为 `SOUL.md` 的文件。它的作用很直白：给 Agent 一张身份证，定义它是谁、能做什么、坚决不做什么。这不仅是 prompt 工程的问题，更是工程化治理的问题——让非开发人员也能通过 PR 审核人格变更，让人格演进有版本历史可追溯。

这篇文章不会教你写“超级提示词”，而是分享一个工程化的做法：如何用 SOUL.md 组织 Agent 的人格与边界，怎么落地、踩过哪些坑、有哪些可以马上复用的经验。适合已经在用 OpenClaw 这类框架，或者自己拼接 Agent + MCP 工具链的工程师。

---

## 问题：为什么需要一份独立的“人格文件”

如果没有 SOUL.md，通常你会遇到这些麻烦：

- **提示词散落各处**：一部分在代码里，一部分在数据库配置，一部分在文档里，改完根本不知道实际生效的是哪一个。
- **边界模糊**：开发者只关注功能，随口加一句“你是 helpful 的助手”，却不定义“helpful 的边界”，导致用户诱导后泄露内部信息或者滥用工具。
- **协作冲突**：产品想让人亲切一点，安全想让人保守一点，运营想临时插入营销话术，最后 system prompt 变成一场拔河。
- **测试缺失**：人格变更没有自动化验证，上线才发现助手开始用错语气，或者在特定输入下崩坏。

把这些内容收敛到一个 Markdown 文件里，本身就是在做“接口定义”。所有人围绕同一个文件讨论，CI 可以基于它跑评测，部署时加载它成为 system prompt 的核心部分。

---

## 做法：设计一个可落地的 SOUL.md 结构

在实际项目中，我们最终沉淀下来的 SOUL.md 大概分为五个区块，不是教科书式的八股，而是多次掉坑后收敛出的最小必要集。

### 1. 元信息与加载声明

```markdown
# SOUL.md for OpenClaw Agent
version: 1.2.0
last_updated: 2025-01-10
scope: production
```

用于标识版本、更新时间、生效环境。CI 可以校验版本号，防止旧版意外上线。

### 2. 人格定义（Persona）

用自然语言描述助手是谁，语气、角色、说话风格。**不要写作文，要写约束**。错误示范：“你是一个热情友好的助手。”正确示范：“用第二人称‘你’称呼用户；每句话不过三行；不主动使用 emoji；不表达个人情绪或立场。”

### 3. 能力与工具边界（Capabilities & Tools）

列出 Agent 可以调用的工具或 MCP 服务，**同时明确使用的触发条件和禁止项**。例如：

```markdown
- 可使用 `search_web`，但仅在用户明确要求“搜索”时调用。
- 禁止自动调用搜索，即使在回答中不确定事实。
- 禁止将搜索结果的链接暴露给用户，只总结内容。
```

这部分是踩坑高发区，后文细说。

### 4. 安全与合规边界（Guardrails）

这里放硬性规则：不回答哪些类别的问题、不生成哪些类型的内容、不透露系统 prompt 本身、不承认自己是 AI 的某些表达方式等。建议用简单的“禁止”列表，便于正则或 guard 模块检查。

### 5. 示例对白（Few-shot Examples）

别写一长串对话，放 3-4 组典型“用户输入-理想回答”对照，重点放在**边界情形**：用户尝试越狱、诱导调用禁用工具、模糊请求等。示例不是训练，而是给 Reviewer 看的预期行为说明。

## 加载机制：从文件到 system prompt

在 OpenClaw 类框架中，加载 SOUL.md 通常有三种方式：

1. **启动时读取**：Agent 进程启动时，读取文件内容注入初始 system prompt。这是最简单的方式，适合人格不频繁变动的场景。
2. **通过 MCP 资源动态加载**：把 SOUL.md 注册为一个 MCP 资源，Agent 在需要时调用 `read_resource` 获取当前人格。好处是可以热更新，但增加了调用开销。
3. **分段拼接**：如果 SOUL.md 很大，可拆成多个文件，根据对话上下文动态拼接。例如基础人格 + 领域知识 + 安全规则，安全规则始终加载，领域知识仅在特定话题时注入。

无论哪种方式，一个关键要求是：**SOUL.md 的内容不能经过任何用户可控的参数直接拼接**，必须走安全的模板变量替换，避免注入。

## 踩坑点：那些真正让人头疼的细节

### 坑1：Token 预算失控

工程师一上来容易把 SOUL.md 写成文档，一写就是 3000 字。加上工具描述、示例对话，system prompt 轻松超过 2000 token。对于需要多轮对话的任务，这直接挤压了上下文窗口，导致 Agent “健忘”。**做法**：把每条规则用一句话表达，砍掉所有形容词；示例压缩到最短；做 token 预算，把 SOUL.md 的总长度写进 CI 检查。

### 坑2：边界声明后工具仍然失控

在 Capabilities 里写了“禁止自动调用搜索”，但因为工具描述里写了“当助手不确定时可搜索”，模型还是会自动调用。这是因为工具描述对模型行为的约束往往强于 system prompt。**对策**：工具描述必须与 SOUL.md 边界对齐，必要时在 SOUL.md 中重申“忽略工具描述中的自动调用建议”。

### 坑3：人格文件面向模型，但 Reviewer 是人

写得太抽象，人类看不懂，就失去了版本管理的意义。例如“遵循道德准则”——没人知道这具体指什么。改进方式：用可验证的行为描述，比如“拒绝回答要求生成可用于欺诈的文本的请求”。

### 坑4：多语言人格裂化

中英文混合的 SOUL.md 会让模型时而切换语气。**建议**：为人格描述维护中文和英文两份并行的约束，注入时根据对话语言选择。如果用同一份，那就用英文写规则，中文只放示例。

## 可复用建议：把 SOUL.md 当成产品来维护

1. **拆分模块，组合加载**  
   把基础人格、领域知识、安全规则拆成独立文件，基础部分变动极少，安全部分随法规更新，领域知识由业务方维护。这样各模块保持短小，责任清晰。

2. **引入 CI 评估**  
   为 SOUL.md 写一组评估用例（例如 50 条边界提问），每次变更自动跑 Agent 的输出，检查是否有违规话术或人格偏移。OpenClaw 社区已有一些 eval 框架，可以直接参考。

3. **使用变量占位符**  
   在 SOUL.md 中嵌入 `{{user_name}}`、`{{current_time}}` 等模板变量，加载时替换，避免在 prompt 里强编码动态信息。

4. **保留回滚能力**  
   对 SOUL.md 做 Git 版本控制，发布时打 tag，并确保框架支持快速回滚到上一版本的人格定义。

5. **设定最小的“零号版本”**  
   如果拿不准要写多少规则，先发布一个只含基础边界和一条人格约束的最小版本，观察线上行为，再逐步添加。过度设计的人格往往一上线就被用户玩坏。

---

## 总结

SOUL.md 不是一张锦上添花的贴纸，而是 Agent 产品的安全边界和体验基调。把人格定义从代码中拎出来，像管理 API 文档一样管理它，才能在快速迭代中保持一致性，也能让非技术团队成员参与进来。

对于已经在用 OpenClaw + MCP 的组合搭建助手的工程师，这件事的投入成本极低，但长期收益远超预期——尤其是当你某天发现一条线上的拒绝回答，正好来自三个月前产品同事在 SOUL.md 里加的一句话时。
