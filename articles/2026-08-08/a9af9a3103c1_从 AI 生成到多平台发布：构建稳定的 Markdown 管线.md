## 背景：为什么需要一条 Markdown 管线
在基于 OpenClaw 的自动化内容工作流中，AI 生成 Markdown 已是基础操作。无论是用 Agent 自动写周报、生成产品文档，还是通过 MCP 请求大模型输出教程草稿，绝大多数产出都是 Markdown 文本。这些内容往往需要分发到微信公众号、Notion、飞书文档、GitHub README 等多个渠道。表面看，直接把 Markdown 复制粘贴到对应平台就行，但实际上，这套流程极其脆弱：平台对 Markdown 的兼容性参差不齐，AI 生成的 Markdown 又会引入非标准语法、冗余转义、错误嵌套等问题。如果把“AI 生成→多平台发布”当作一个固定管线来维护，而不是每次手工调整，就能在自动化场景下获得可靠且一致的输出。

## 问题拆解：从哪里开始失控
经过多次实践，我把失控点归纳为三类：

1. **AI 产出的非标准 Markdown**  
   大模型训练数据里混入了各种方言（如 GFM、CommonMark、Obsidian 语法扩展），生成内容中经常出现全角半角混排的列表符号、数学公式的 `$$` 与 `$` 随意混用、代码块缺少语言标识、引用中嵌套表格等。这些在 Hugo 或 VSCode 预览中尚可，但导入飞书会丢失样式，粘贴到微信编辑器直接炸排版。

2. **目标平台的富文本转换黑盒**  
   很多平台的编辑器并非真正解析 Markdown，而是“看起来像 Markdown”的富文本渲染。比如微信公众号，它不原生支持 Markdown，需要借助第三方工具（如 markdown-nice）将 Markdown 转成带样式的 HTML，这个过程对不同语法的处理差异巨大：有些工具遇到 `#` 开头的标题会包裹多重 `<div>`，导致后来编辑又粘连。

3. **管线化缺失**  
   如果没有统一中间处理层，每次发布都变成“AI 生成→人眼检查→手动修复→逐个粘贴→调整排版”。这在单次任务里可以忍，一旦接入自动化 Agent，比如用 OpenClaw 设置每日按时生成快讯并自动推送，就必须建成稳定的格式处理流水线。

## 做法：从粗放到可控的三步管线
在实践中，我搭建了一条“预处理→标准化转换→平台适配输出”的管线，核心依赖 OpenClaw 的 Agent 调度能力和 MCP 工具链。

### 第一步：预处理，清洗 AI 输出
在 Agent 调用大模型返回 Markdown 后，立即进入一个预处理节点。这个节点用 Python 脚本实现，主要做三件事：
- **统一行尾与空行**：把所有非 LF 行尾转成 `\n`，并规范化列表前后的空行，确保不同平台粘贴时不会出现粘在一起的无序列表。
- **消除不兼容的转义**：大模型有时会在 Markdown 里加入 `\` 转义普通字符（如 `\*`、`\_`），这在部分渲染器中被视为原义，需要移除不必要的转义。
- **强行给代码块添加语言标识**：如果遇到没有标注语言的 fenced code block，按内容侧写补充 `text` 或 `json` 标识，避免在飞书等平台显示为无样式纯文本。

这个预处理节点封装为 MCP 工具 `md-sanitize`，供 Agent 在工作流中直接调用。

### 第二步：标准化转换，输出中间格式
清洗完的文本还不适合直接分发，需要转成一种“中间表示（IR）”。我选择的 IR 是符合 CommonMark 规范的 AST（抽象语法树），借助 `markdown-it` 或者 Unified 生态的 `remark-parse` 生成。在 AST 阶段可以做很多精确操作：
- 将 Obsidian 风格的 `[[内部链接]]` 格式转为标准引用或直接移除，避免在平台上显示为失效链接。
- 把表格重新对齐，统一列分隔线的 `---` 与 `:---`，防止在某些解析器中出现宽度塌陷。
- 将所有 HTML 标签按白名单过滤，去掉 `<style>`、`<script>` 和不安全的 `<div>` 嵌套。

这一步做成另一个 MCP 工具 `md-ast-clean`，输出统一的 AST，而不是立刻渲染为 Markdown，因为最终渲染需要根据不同平台选择不同模板。

### 第三步：平台适配渲染与发布
对于目标平台，使用各自的渲染器生成所需的格式：
- **微信公众号**：用 AST 直接驱动 markdown-nice 的样式模板，生成可粘贴的 HTML，并自动处理微信禁止的样式标签（如 margin、外部图片防盗链）。通过 OpenClaw 的插件触发浏览器自动化或调用微信官方素材接口，完成上传。
- **飞书 / Notion**：这两个平台都有官方接口可以接收块结构数据，最好不传 HTML，而是将 AST 转换为符合其 Block API 的 JSON。我曾用 `remark` 自定义插件将 Markdown AST 映射为 Notion 的 `paragraph`、`heading_1`、`bulleted_list_item` 等块类型，效果稳定，基本不会出现格式丢失。对于飞书，同样类似。
- **GitHub / Gitee**：直接还原为 GFM 规范的 Markdown，并保留 front matter 内容用于 SEO。

最后一步用 OpenClaw 的多播（multicast）机制，将一条原始 Markdown 内容同时发布到上述平台，每种输出路径都绑定好对应的 MCP 工具。

## 踩坑记录
1. **微信图片外链白名单**  
   Markdown 中的图片链接如果是外站地址，微信编辑器会直接过滤掉 `src` 属性。必须在管线里加入“图床自动转存”工作流，将外链图片上传到微信允许的 CDN（如公众号素材库），并替换为返回的 `https://mmbiz.qpic.cn` 链接。这一测让我明白，光格式适配不够，还要理解目标平台的安全限制。

2. **飞书 Block API 的表格限制**  
   飞书开放接口的表格块不支持合并单元格，而有些 AI 生成的 Markdown 表格含跨列表头，强行转成 Block 会丢失结构。我的处理是检测到复杂的表格时自动降级为截图模式（headless 渲染表格区域为图片），替换成富文本图片块，代价是失去可编辑性，但保证了阅读体验。

3. **MCP 工具超时**  
   当 AST 处理大文本（超过 1MB 的 Markdown）时，`md-ast-clean` 解析耗时很长，可能超过 MCP 调用默认超时。改进方式是引入流式处理，分段解析并合并 AST，同时在 Agent 端设置合理的 `request_timeout` 为 30 秒，并返回进度信息，避免 Agent 认为调用失败而重试。

## 可复用建议
- **构建中间 AST 层**：不要在不同平台间直接映射字符串式的 Markdown，基于 AST 做转换，复用性远高于正则修复。
- **为每个平台写配置文件**：定义允许的块类型、支持的样式特性、图片处理策略，使用 YAML 描述，让 Agent 根据配置动态选择渲染器。
- **把图片处理独立出来**：图片转存、压缩、格式转换是高频痛点，独立成 `media-uploader` 工具，让管线可组合。
- **添加校验门禁**：在正式发布前，用 MCP 调用渲染为 HTML 或 JSON，并在本地预览检查关键元素（如所有标题层级、链接有效性），失败自动中止发布并通知。

## 总结
这条管线的本质，不是“完美适配所有平台一次做完”，而是在 OpenClaw 的自动化骨架中，把最容易出问题的格式处理拆解成可调试、可替换的微小工具链。AI 生成的内容越来越容易获得，但让这些内容稳定地走到不同读者的屏幕上，仍然需要工程化的耐心。把格式适配写成 MCP 工具，让 Agent 像调用函数一样调用它们，你会发现，原本堆在人工面前的杂活，开始被有序地搬进了自动化流里。
