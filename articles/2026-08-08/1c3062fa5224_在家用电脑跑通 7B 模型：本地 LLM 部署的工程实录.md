## 为什么在本地跑大模型

对于经常折腾 OpenClaw、Agent 或者 MCP 工作流的同学来说，云端 API 虽然省事，但总有绕不过去的痛点：高频调用时延迟不可控，处理内部文档时数据不准出境，还有半夜调试突然弹出的 Rate Limit。把 LLM 搬到本地，牺牲一点绝对能力，换来的是可预测的延迟、零网络依赖和完全的数据控制。

这篇记录一次在普通家用台式机（i7-13700K + 64G DDR5 + RTX 4070 Ti 12G）上部署并 API 化一个可用 7B 模型的完整过程。目标不是跑分，而是让 Agent 能稳定调用，且出图 / 工具调用不崩。

## 硬件边界与模型选型

家用显卡最大的短处是显存。12G 显存去掉 CUDA 上下文和系统保留，实际可用约 10.5G。这意味着：

- 13B 模型在 FP16 下需要约 26G，直接放弃；
- 7B 模型 FP16 需要约 14G，仍超限；
- 必须使用 4-bit 或 8-bit 量化，显存才能压进 10G 以下。

实际操作中选用了 Mistral-7B-Instruct-v0.2 和 Qwen2-7B-Instruct 两个模型，均采用 Q4_K_M 量化（Ollama 默认）。单模型加载后显存占用约 7.8–8.5G，留出 2G 左右给 KV cache 和少量并发，刚好不触发 OOM。

## 部署与 API 化步骤

部署工具选 Ollama，理由很简单：它在 Ubuntu/WSL 下一行命令就能起服务，而且内置模型量化与 Modelfile 机制，省去手动折腾 Transformers 和 bitsandbytes 的体力活。

**1. 环境准备**
- 系统：Windows 11 + WSL2 (Ubuntu 22.04)
- Nvidia 驱动：535.129.03，CUDA 12.2
- WSL 内安装 Ollama 官方脚本：`curl -fsSL https://ollama.com/install.sh | sh`
- 确认 GPU 可用：`ollama run mistral` 后 `nvidia-smi` 看到显存占用，说明 CUDA 正常工作。

**2. 拉取并配置模型**
直接用 `ollama pull mistral:7b-instruct-v0.2-q4_K_M`。为了适配 Agent 的工具调用模式，再写一个 Modelfile 强制输出结构化 JSON：

```dockerfile
FROM mistral:7b-instruct-v0.2-q4_K_M
PARAMETER temperature 0.3
PARAMETER num_ctx 8192
SYSTEM """
You are a helpful assistant. When asked to call a tool, output JSON only with 'tool' and 'params'.
"""
```

`ollama create agent-mistral -f Modelfile` 生成专用模型。

**3. 开启一致 API 网关**

Ollama 默认只监听 127.0.0.1:11434，且 API 格式与 OpenAI 不完全一致。为了让 OpenClaw 或 LangChain Agent 无缝接入，用 LiteLLM 做一层代理：

```bash
pip install 'litellm[proxy]'
litellm --model ollama/agent-mistral --port 4000 --api_base http://localhost:11434
```

LiteLLM 向外暴露 `/v1/chat/completions`，与 OpenAI 格式完全兼容，同时可以加负载监控、fallback 和限速。配置环境变量 `OPENAI_API_BASE=http://localhost:4000/v1`，上层应用就不用改了。

**4. 健康检查与并发控制**

Ollama 默认并发为 1，多 Agent 同时调用会排队超时。通过设置环境变量 `OLLAMA_NUM_PARALLEL=3` 允许多请求并行，但需注意显存峰值：实测 3 并发时显存会冲到 10.2G，再高就触发系统缓存回收导致延迟抖动。另外，用 `ollama serve` 时加 `--keep-alive 10m` 让模型常驻，避免每次请求重加载。

## 踩坑记录

- **Ollama 抢占全部内存**：即使只加载一个 7B 模型，Ollama 也会把系统空闲内存全部占满作为缓存，导致其他服务被 OOM killer 干掉。解决办法是在 WSL 配置里限制内存上限：`%UserProfile%\.wslconfig` 中设 `memory=32GB`，或物理内存充足时直接不管。
- **模型并发 1 的坑**：如果一个 Agent 正在进行长推理，另一个调用会立刻返回 "model is busy"。必须手动设 `OLLAMA_NUM_PARALLEL`，并合理调整 `num_predict` 上限避免单请求吃尽上下文。
- **量化回退**：Q4_K_M 虽省显存，但在多步工具调用时会因为误差累积产生错误 function call 参数。遇到时升级到 Q5_K_M（显存多占 1G）或换用 8-bit 的 GGUF，代价是可能要减短上下文长度。
- **WSL2 网络问题**：宿主机访问 WSL 内的 Ollama 需要端口转发，直接用 `localhost` 可能不通。用 WSL IP 或在 Windows 侧起一个 netsh 转发解决，更稳妥的是全扔进 Docker 用 host 网络。

## 可复用的建议

1. **再封装一层 API 网关**：不论用 LiteLLM 还是自建 FastAPI，保持对上层暴露标准 OpenAI 格式，随时可以切换到云端模型而不改代码。
2. **显存紧张时先砍上下文长度**：`num_ctx` 从 8192 降到 4096 能释放约 1–2G，比折腾量化更直接。
3. **工具调用任务选择 7B+ 模型**：3B 模型在复杂 function call 的准确率急剧下降，曾经试过 Phi-3-mini，结构一复杂就输出非法 JSON。
4. **监控是关键**：用 `nvitop` 或 `nvtop` 抓显卡负载，结合 LiteLLM 自带的 `/metrics` 端点做 Prometheus 采集，长时间运行才能知道是否需要加主动重启策略。
5. **不要把本地 LLM 当生产环境主力**：家里电费和散热都是隐性成本，当稳定的 staging 环境或离线环境更合适。

## 总结

本地部署一台能硬抗 Agent 调用的 LLM，工程化重心不在“把模型跑起来”，而在“让它稳定地变成 API”。Ollama 大幅降低了门槛，但并发、量化和内存管理仍是必须跨过的坎。这套方案已经连续运行两周，为 OpenClaw 的工具调用节点提供了约 90% 的本地后端请求，平均响应时间 1.2s（含 TTFT），足够日常折腾。

如果你也被云 API 的波动折磨，不妨用周末半天照着这套流程搭一次，说不定就会发现：本地 LLM 没有想象中慢，而且再也不用担心调试到一半被断流。
