# OpenClaw 定时任务选择指南：Cron 还是 Heartbeat？

在 OpenClaw 的自动化流程中，定时触发是最常见的启动方式之一。插件通过 `manifest.yml` 或代码定义触发器时，通常面临两种选择：**cron** 和 **heartbeat**。这两种机制看似都能让任务“定期执行”，但其背后的语义、行为边界和适用场景差异明显。本文从工程实际出发，梳理它们的特性、配置、典型陷阱，并给出可复用的选型建议。

## 1. 两种定时器的本质差异

- **Cron**：基于**墙上时钟**的调度，精确到分钟（或秒），例如“每天 09:00”。它依赖于系统时间和 cron 表达式，适合需要与自然时间对齐的任务。
- **Heartbeat**：基于**固定间隔**的调度，例如“每 300 秒执行一次”。它不关心当前是几点，只关心上次触发后是否过了指定时间，适合持续轮询或周期性维护。

简单来说，你的任务是“在某个时间点做某事”还是“每隔一段时间做某事”？这个问题是选型的核心依据。

## 2. 配置与验证步骤

### 2.1 Cron 配置示例
```yaml
triggers:
  - type: cron
    spec: "0 9 * * *"          # 每天 09:00（UTC）
    timezone: "Asia/Shanghai"  # 明确时区，避免默认 UTC 导致的偏差
    # 可选：missedExecutionPolicy 等，视 OpenClaw 版本支持
```

### 2.2 Heartbeat 配置示例
```yaml
triggers:
  - type: heartbeat
    interval: 300000           # 毫秒，即 5 分钟
    initialDelay: 10000        # 启动后延迟 10 秒首次执行，避免冷启动拥塞
```

部署后，通过 OpenClaw 日志或 Debug 端点确认触发时机是否与预期一致。可以在任务中打印时间戳，快速比对。

## 3. 踩坑实录

### 3.1 Cron 的时区陷阱
若未显式指定 `timezone`，OpenClaw 很可能默认使用 UTC。一个配置为 `0 9 * * *` 的任务，在 UTC 时区运行时，北京时间实际触发在 **17:00**。一旦出现业务时间与预期不符，应先检查时区设置，而非怀疑 cron 表达式。

### 3.2 Heartbeat 的任务重叠
当任务执行时间 **大于** heartbeat 间隔时，默认行为可能是再次触发新实例，导致任务堆积甚至资源耗尽。例如，一个需要 2 分钟完成的任务，间隔却设为 60 秒，很快就会形成多个并发执行。应对措施：
- 将间隔设为 **至少 2 倍于任务平均耗时**。
- 在任务内部实现幂等性（如基于唯一键的去重锁）。
- 如果 OpenClaw 提供并发策略配置（如 `concurrencyPolicy: Forbid`），应优先启用。

### 3.3 服务重启的边界行为
- **Heartbeat**：重启后会立即开始下一个间隔（除非设置了 `initialDelay`）。这可能导致大量任务在同一个重启窗口扎堆触发。
- **Cron**：某些调度引擎在重启后会检查“错过的执行时间”，并尝试立马补跑一次。如果你不希望补跑，需要确认 OpenClaw 的 `missedExecutionPolicy` 是否可设为 `skip` 或类似值。

### 3.4 高频 Heartbeat 的资源开销
将 interval 设为 1000 毫秒（1 秒）虽然技术上可行，但会显著增加 CPU 和 I/O 开销。高频轮询通常意味着设计欠佳——考虑是否能用事件驱动（Webhook）代替。

### 3.5 任务失败被“静默”
无论 cron 还是 heartbeat，任务执行失败（如网络超时、API 返回错误）都不会自动告警。必须主动接入监控：
- 在任务代码中捕获异常并记录结构化日志。
- 利用 OpenClaw 的 notification 插件，将关键错误推送到 Slack、邮件等通道。
- 为定时任务设置独立的成功率监控，而非仅依赖系统级心跳。

## 4. 可复用的选型建议

| 场景                              | 推荐机制   | 典型配置                             |
|-----------------------------------|------------|--------------------------------------|
| 每日业务报表、定时推送            | Cron       | `0 9 * * *` + 指定 Asia/Shanghai     |
| 周期性清理过期缓存、临时文件      | Cron       | 在凌晨业务低峰执行                    |
| 轮询外部 API 状态（如训练任务）   | Heartbeat  | interval: 60000（1分钟），避免过频    |
| 健康检查、本地状态同步            | Heartbeat  | interval: 30000，配合 initialDelay   |
| 低频（每小时/每天）数据拉取      | Cron       | 清晰表达“在几点拉”                   |

通用原则：
- **幂等性**：无论选择哪种触发器，都假设任务可能被重复执行，确保多次执行结果一致。
- **间隔约束**：Heartbeat 的 interval > 2 * 任务执行时间，防止重叠。
- **时区显式化**：Cron 必须明确 `timezone`，避免跨团队协作时的隐性时区问题。
- **文档化**：在 `manifest.yml` 注释或团队文档中记录选用理由，降低后期维护成本。

## 5. 总结

Cron 与 Heartbeat 并非优劣之分，而是语义不同。Cron 锚定自然时间，适合“定点”需求；Heartbeat 锚定相对间隔，适合“周期”需求。选型时，先问自己：任务触发是由钟表决定，还是由时间差决定？然后基于本文的踩坑清单做好防护——时区、重叠、幂等、监控。做到这些，你的 OpenClaw 定时任务就能从“能跑”进阶为“可靠运行”。
