# 本地配置不再失控：使用 tools.md 统一管理 Agent 的环境差异

## 背景：为什么 Agent 总要和环境配置纠缠

在构建自己的 Agent 工作流（无论是通过 OpenClaw 的 Tool calling，还是 MCP 插件、自动化脚本）时，很快就遇到一个绕不开的问题：**同一套 Agent 逻辑，在自己笔记本上跑得好好的，换一台机器就错漏百出**。原因通常不是代码 bug，而是底层环境差异 —— API 密钥路径不同、数据库连接串因地而异、模型推理用的缓存目录不一样，甚至只是 `/tmp` 和 `C:\Temp` 的区别。

常见的应对方式是把这些“环境专属信息”塞进系统 prompt 里，或者直接硬编码在 Python 脚本的参数中。短期能跑通，但随着工具数量增加、团队成员变多、部署目标从一台 Mac 扩展到一台 Windows 虚拟机再加一台 Linux 服务器，配置就会迅速腐烂：你的 prompt 里写死了 `/home/me/data`，同事那边却需要 `D:\projects\data`，最后只能各自维护一份 prompt 变体，合并起来极其痛苦。

我们需要一种方式，让 Agent 在调用工具前能够**感知当前环境的结构化配置**，而不是依赖模糊的自然语言提示或散落在各处代码里的变量。

## 问题：配置差异如何破坏 Agent 的可用性

整理一下，这里有三个层次的问题：

1. **工具参数的环境敏感性强**：比如一个“读取本地日志”的工具，路径在 Linux 上是 `/var/log/app/`，在 macOS 上是 `~/Library/Logs/app/`，如果不抽象出来，Agent 就无法跨平台复用。
2. **敏感信息无处安放**：API_KEY、数据库密码等不适合放进 prompt（容易泄露），也不能硬编码在代码里（不安全且不灵活）。
3. **环境切换缺乏自动化**：你在家目录的 `.env` 里改了一个值，Agent 未必会重新加载；如果同时维护开发机和服务器两套配置，忘记切换就会导致线上误调用本地服务。

这时就需要一份**声明式的、机器可读的**配置文件，来集中描述 Agent 可用的工具及其在不同环境下的参数差异。

## 做法：用 tools.md 构建可感知环境的工具配置层

我们在 OpenClaw 的实践中逐渐收敛到一种模式：**tools.md**。这并非某个框架强制的文件名，而是一个约定 —— 一份 Markdown 格式的文档，既方便人阅读维护，又能被 Agent 的上下文解析逻辑进行结构化提取。

### 第一步：设计 tools.md 的结构

一份典型的 tools.md 会按工具划分为多个区块，每个区块包含工具的名称、描述、可用参数以及**环境变量占位符**。例如：

```markdown
## tool: read_app_logs
- description: 读取应用日志最近 50 行
- command: tail -n 50 ${LOG_DIR:-./logs}/app.log
- env: LOG_DIR
- default_env:
  - linux: /var/log/myapp
  - macos: ~/Library/Logs/myapp
  - windows: %APPDATA%\myapp\logs
```

这里 `${LOG_DIR:-./logs}` 表示优先使用环境变量 `LOG_DIR`，未设置时回退到 `./logs`。紧接着用 `default_env` 给出了针对不同操作系统的合理默认值，Agent 运行时可以根据 `platform` 信息自动适配，而无需人类在 prompt 里反复交代。

### 第二步：结合环境变量与本地覆盖

tools.md 本身**不存储任何机密**，它只定义结构。真正的敏感值（如 `DATABASE_URL`、`OPENAI_API_KEY`）依然通过 `.env` 文件或系统环境变量注入。Agent 启动时，会加载环境变量并将其注入到工具解析的上下文中。

为了兼顾本地开发时的便利，我们在 `.gitignore` 中忽略 `.env.local`，并在工具描述里允许本地覆盖：  
例如 `command` 里可以使用 `${MY_TOOL_PATH:-$(which mytool)}` 的写法，本地只需设置 `MY_TOOL_PATH` 即可绕过系统查找。

### 第三步：让 Agent 理解 tools.md

在 OpenClaw 的体系里，可以把 tools.md 的内容作为系统 prompt 的一部分动态注入，但更工程化的做法是**在 Agent 的 tool calling 中间层解析它**。具体来说：

1. Agent 接收到用户指令时，首先调用一个内置的 `list_tools` 函数，该函数读取 tools.md 并返回当前环境下可用工具的列表及其参数说明（已替换好环境变量）。
2. Agent 根据返回的结构化信息决定调用哪个工具，并生成正确的参数。
3. 实际执行时，由宿主进程（如 Python 运行时的工具执行器）再次根据当前环境进行最终的命令组装。

这样就将“环境感知”的责任从 Agent 的推理转移到了确定性的解析层，大大减少了幻觉和误用。

### 第四步：多环境切换的真实案例

假设你有一个需要访问本地数据库的工具 `query_db`，在开发机上它连接 `localhost:5432`，在测试服务器上连接 `10.0.1.50:5432`。tools.md 里可以这样写：

```markdown
## tool: query_db
- command: psql -h ${PG_HOST:-localhost} -p ${PG_PORT:-5432} -d mydb -c "..."
- env: PG_HOST, PG_PORT
```

部署到服务器时，只需在 `.env.production` 里设置 `PG_HOST=10.0.1.50`，启动脚本指定 `ENV=production` 即可。Agent 无需知道环境类型，它看到的工具描述里已经是正确的连接地址。

## 踩坑点

在多个项目中推广这套方案时，有几个非常实在的坑：

- **Windows 路径反斜杠与转义**  
  tools.md 里的路径如果写成 `C:\Users\foo`，Markdown 解析和 shell 执行可能会吞掉反斜杠。统一规则是用正斜杠或使用 `%APPDATA%` 等环境变量来表示路径。
- **Markdown 解析的歧义**  
  工具块的结构要足够简单：避免在描述中使用可能会被误当成代码块的 ```，解析逻辑如果只是简单的正则，很可能被坑。我们最终用 YAML front matter 或代码块内嵌 JSON 来明确结构，而不是纯 Markdown 自由文本。
- **变量展开时机**  
  如果在系统 prompt 阶段就展开变量，可能导致 prompt 中包含敏感信息。应当把变量展开推迟到工具执行的那一刻，并且只在 Agent 侧向执行器传递工具名称和参数骨架。
- **Git 版本控制与本地覆盖的冲突**  
  tools.md 本身需要版本控制，以便团队分享工具定义，但不同开发者的本地环境变量差异不能写入 tools.md。解决之道是坚持让 tools.md 只定义工具签名和默认值范式，把差异化全部移入 `.env.local`。

## 可复用建议

- **保持 tools.md 单一职责**：只描述“有哪些工具、需要怎样的环境”，不要在里面写业务流程。
- **模板化生成**：如果你的工具数量激增，可以从代码注释或 OpenAPI spec 自动生成 tools.md 的基础骨架，降低人工维护成本。
- **加入自动化校验**：写一个启动检查脚本，扫描 tools.md 中声明的环境变量是否都已设置（区分必需和可选），避免 Agent 跑到一半才报错。
- **与 MCP 集成**：如果你的 Agent 已经接入 MCP 服务，可以将 tools.md 作为 MCP 资源暴露，让 Agent 通过标准的 `resources/read` 获取工具列表，实现真正的动态工具发现。

## 总结

把 Agent 的本地配置和环境差异管理好，不是靠更聪明的 prompt，而是靠可读、可解析、可版本化的声明式配置文件。tools.md 作为一种轻量级的中心化约定，既不增加过多的工程依赖，又能显著提升跨环境协作的稳定性。最终的效果是：Agent 不再“水土不服”，你也不用再为换一台机器就改一堆 prompt 而头疼。
