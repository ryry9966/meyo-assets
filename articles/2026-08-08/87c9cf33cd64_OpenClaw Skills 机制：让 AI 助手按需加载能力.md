# OpenClaw Skills 机制：让 AI 助手按需加载能力

## 背景：AI 助手的“能力过载”陷阱

在构建基于 OpenClaw 的智能体时，我们通常会为它配置多种能力：查天气、发邮件、操作数据库、调用内部 API…… 初始方案往往是把所有工具和提示词一次性注入系统消息。这在原型阶段没问题，可一旦能力数量超过 20 个，问题开始集中暴露：

- **上下文膨胀**：每一个工具定义（schema、描述）都会占用 token 预算，压缩留给真正推理的空间。
- **指令混淆**：工具太多时，模型在闲聊场景也会“胡思乱想”地猜测该调用哪个函数，造成无意义的延迟和幻觉。
- **维护困难**：新增或修改一种能力，需要动全局配置，多人协作容易冲突。

为了解决这些问题，OpenClaw 引入了 Skills 机制——将能力拆分为独立的“技能模块”，在运行时由助手**按需加载**，而不是预先全部塞进提示词。

## 问题定义

我们的目标是：

1. 每个技能独立定义，包含触发描述、所需工具、知识片段和专属系统指令。
2. 助手接收到用户意图后，先判断应该激活哪个（或哪几个）技能，然后将对应配置动态注入当前会话。
3. 技能之间互不干扰，且加载/卸载过程对用户无感。

OpenClaw 的 Skills 并非简单的“工具集合”，它更像是给助手配备了一套可插拔的专家子系统。

## 做法：从定义到动态加载

### 1. 技能定义

每个 Skill 是一个标准目录，结构如下：

```
skills/
  weather/
    manifest.yaml
    tools.py
    context.md
```

`manifest.yaml` 包含技能的元数据和激活条件：

```yaml
name: weather
description: "提供全球城市天气查询与预报"
triggers:
  - "天气"
  - "气温"
  - "会下雨吗"
  - "需要带伞"
tools: [get_weather, get_forecast]
priority: 10
```

`context.md` 存放该技能专属的指令和知识，如 API 调用规范、回复格式要求等，会在技能激活时作为系统消息注入。`tools.py` 则是实现具体功能的 Python 模块，函数签名需使用 OpenClaw 的 `@tool` 装饰器。

### 2. 技能注册与加载器

在助手启动时，`SkillLoader` 会扫描指定目录，解析所有的 `manifest.yaml`，构建一个技能注册表。加载器的核心逻辑仅保留每个技能的元数据（名称、描述、触发词、优先级），并不把完整上下文和工具列表直接纳入全局提示词。

```python
loader = SkillLoader("./skills")
registry = loader.scan()  # 只提取轻量元数据
```

### 3. 意图匹配与技能激活

每次用户输入到达时，OpenClaw 的中间件会执行一个轻量级意图分类步骤。可以基于规则（关键词匹配）或微调的小模型进行快速判断。示例基于规则的策略：

```python
def match_skill(user_input, registry):
    for skill in sorted(registry, key=lambda s: s.priority, reverse=True):
        if any(kw in user_input for kw in skill.triggers):
            return skill
    return None
```

一旦匹配到技能，系统就会动态构建本轮会话的完整提示词：
- 基础系统指令（助手人格、安全边界等）
- 激活技能的 `context.md`
- 对应工具列表的定义
- 历史对话消息

对于未匹配到任何技能的场景，只保留基础指令和一组最通用的工具（如计算器），保证轻量运行。

### 4. 卸载与状态隔离

当用户连续提问且话题明显切换时，技能需要被替换。OpenClaw 默认在每轮对话开始时重新进行一次意图匹配，如果匹配结果与当前激活的技能不同，则卸载旧技能上下文，注入新技能的配置。为了避免“闪退”状态丢失，技能可以通过 `session.state` 将关键数据（如已查询的城市）暂存，新技能如需使用，需要显式声明依赖关系。

## 踩坑点

- **触发词覆盖冲突**：多个技能的触发词可能存在交集（如“查一下”同时匹配天气和汇率），导致加载了错误的技能。解决方案是增加负向触发词（negative_triggers）字段，或引入更精确的语义相似度匹配，并设置优先级。
- **上下文注入的 token 爆炸**：乍看按需加载省 token，但如果一个技能的 `context.md` 过于冗长，仍然会拖慢响应。需要严格控制知识片段的长度，推荐控制在 500 字符以内，必要时通过动态检索缩减。
- **工具函数全局命名污染**：当多个技能拥有同名工具时，注入后的函数列表会出现冲突。必须为每个技能的工具加上命名空间前缀，例如 `weather_get_forecast`，并且修改模型推理时的工具调用名称映射。
- **会话连续性的心理预期**：用户切话题后，助手“忘记”了上一轮讨论的内容，容易让使用者感到不稳定。可以适当在基础提示词中加入“若话题切换，请告知用户你将转换模式”的指引，增强可控感。

## 可复用建议

1. **技能粒度宜小不宜大**：单个技能只解决一个明确定义的领域问题，避免“万能查询助手”这种大杂烩。
2. **描述即文档**：好好写 `manifest.yaml` 中的 `description` 和 triggers，它们直接影响下游意图识别的准确率。可考虑用真实日志中的用户语录作为触发词来源。
3. **日志记录每次技能切换**：在生产环境中记录 `session_id`、触发词、加载的技能、耗时，方便复盘错配和性能瓶颈。
4. **提供 fallback 机制**：当意图识别犹豫不决时（匹配分数均低于阈值），不强行加载技能，而是让基础助手直接回复并追问需求，降低误激活风险。
5. **测试多轮切换**：不仅测试单句触发，更要测试连续对话中“进入技能→在技能内多轮交互→切出技能→再进入”的完整流程，确保上下文卸载干净，不会残留上一次的工具定义。

## 总结

OpenClaw 的 Skills 机制本质上是一种 **动态提示词组装策略**，它用轻量级的意图路由代替了“全量注入”的蛮力做法。在工程实践中，它显著降低了平均 token 消耗，减少了工具调用的混淆率，也让能力的扩展更模块化。当然，它的实现也引入了匹配不准、状态隔离等新问题，需要我们在触发词设计、上下文管理和监控上下功夫。

如果你正在维护一个越来越臃肿的 OpenClaw 助手，不妨尝试将能力拆分为 Skills 并按需加载，你会发现不仅助手更“清醒”，团队里不同能力的维护也彼此解耦，可以并行迭代。
