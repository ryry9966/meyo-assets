## 背景：信息洪流与 RSS 的尴尬回归

对于需要持续追踪技术动态、行业情报，又不想被算法投喂的人而言，RSS 是保持信噪比的最后防线。但问题也很直接：订阅源动辄上百，每天涌进来的条目根本看不完。纯靠人工筛选，最后就是“已读不回”；靠关键词过滤，又容易误杀长尾有价值的内容。

自动化的解法很自然——让 Agent 替你先读，然后给你摘要。结合 MCP (Model Context Protocol) 和日常使用的 OpenClaw/Agent 框架，可以搭出一条安静、可控的“信息流管线”：从 RSS 抓取到结构化清洗，再到大模型摘要，最后推送到你面前。

## 问题定义

目标不是又造一个 RSS 阅读器，而是构建一条 **无人值守的摘要管线**，它必须满足：
- 解耦：抓取、解析、摘要、分发每个环节可独立替换。
- 对 Agent 友好：以工具 (Tool) 形式暴露给 LLM，方便在工作流里拼装。
- 低成本、高容错：大量源、大量文章，不能一次失败就全挂。

下面以 MCP Server 为核心，记录一套可以 30 分钟内跑通的实现思路。

## 做法与步骤

### 1. 选一个靠谱的 RSS 解析方案
直接用 `feedparser` 处理大部分标准 RSS/Atom 输出，同时准备一个清理函数处理常见脏数据。关键词：
- HTML 标签剥离 (`BeautifulSoup`)
- HTML 实体解码
- 无正文时回退到 `summary` 字段
- 时间归一化（`dateutil.parser` + 兜底用收到时间）

```python
def clean_html(raw_html):
    soup = BeautifulSoup(raw_html, "html.parser")
    return soup.get_text(separator=" ", strip=True)
```

### 2. 封装为 MCP Server 工具
创建一个 Python MCP Server，暴露一个工具 `fetch_latest_articles`，参数：
- `feed_url`：RSS 源地址
- `since_minutes`：抓取最近多少分钟内的条目，默认 60 分钟（配合 Cron 周期）
- `max_items`：一次返回上限，防止超大 feed 爆 token

工具返回整洁的 JSON 数组，每个条目只保留 `title`, `link`, `cleaned_text`（截断至 1800 字符）和 `published`。这样 Agent 拿到的是可以直接喂给 LLM 的结构。

### 3. 在 OpenClaw 里组装 Agent 工作流
配置一个周期性技能（例如每 30 分钟触发），内部流程：
1. 调用 MCP 工具批量拉取所有监控源的更新。
2. 将条目列表传给 LLM，要求按“关键信息 / 技术要点 / 可行动作”模板生成每个条目的中文摘要（每条不超过 120 字）。
3. 合并为一条 Markdown 日报，通过 Webhook 推送到 Slack / 飞书 / Telegram。

提示词中需要明确约束：禁止扩写、禁止评价、只提取原文事实。示例如下：
> 对下面每条资讯生成摘要，只包含：1) 核心事件/结论；2) 若涉及技术则标明技术栈；3) 若无实质内容标记为 [无要点]。绝对不要添加建议或引申。

### 4. 定时与去重
在 Agent 侧维护一个简单的已处理链接缓存（可以是本地 JSON 文件或 SQLite），根据 `link` 去重，避免重复摘要。缓存设置 72 小时过期，平衡存储和准确性。

## 踩坑记录

**乱码与编码声明**：部分中文源不遵守 Content-Type 声明，需要手动探测编码（`chardet`）。建议对 `cleaned_text` 做一次 `encode/decode` 检查，失败则丢弃该条目而不是让整个批次挂掉。

**时间戳漂移**：不少源的时间是未来时间或 1970，统一用 `now` 作为上界，超过当前时间 12 小时的条目置为当前时间。

**LLM 摘要“过度创作”**：最初摘要总带上“建议关注”“值得思考”等水词，后来在 system prompt 中加入了反面示例和严格评分规则（例如出现建议类词汇就扣分），才真正收敛成硬核简报。

**全文抓取的代价**：部分源仅为摘要，正文需要抓取原网页。过早引入 headless 浏览器让管线复杂度翻倍，后改为仅对白名单内高价值源做全文回捞，其余直接基于 RSS 摘要进行处理，性能够用。

**成本控制**：每日 300 条源、每 30 分钟一次轮询，使用 DeepSeek-V3 等低成本模型，月均消耗不到 2 美元。关键点在“截断长度”和“非必要不重跑”。

## 可复用建议

- **MCP 工具独立部署**：把 RSS 抓取工具做成长期运行的 MCP Server，不要每次调用都新建进程，利用连接池复用 HTTP 连接。
- **参数外置**：源列表、摘要模板、推送渠道都通过 Agent skill 的配置注入，方便换团队复用，不用改一行代码。
- **渐进式接入**：先接入 5 个高质量源跑一周，观察 token 消耗和漏报情况，再批量添加。
- **错误优雅降级**：单个源超时或解析失败不影响其他源，最终日报里注明失败源数量即可，避免整条管线静默挂掉。

## 总结

信息焦虑只能靠自动化治理，不能靠意志力硬扛。RSS + AI 摘要这条管线，核心价值不在于省了几分钟阅读时间，而在于把“持续关注”这个动作交给 Agent，让你可以在需要时快速切入原文。用 MCP 把一切能力工具化之后，组装和维护成本都很低，适合作为 OpenClaw 日常自动化实践的常驻模块。

下一步可以扩展的方向：为每个源维护“关注度权重”，让高频命中关键字的源自动提升检索频率；或者基于摘要生成跨源的趋势简报，真正从信息流里浮现线索。
