## 一、背景：日报为什么总在占用你的思考余量

在一个同时维护多个 Agent、多个自动化任务、多项数据抓取的环境里，日志散落在不同系统里：OpenClaw 的运行日志、MCP Server 的调用记录、自建插件的 stdout、定时任务的 cron 输出。每到要写日报时，都要手动翻看这些碎片，拼凑出“今天做了什么”，还要按项目归类、补充状态说明、去掉重复信息——这个过程每天至少耗费 20–40 分钟，且很容易遗漏某些后台静默执行的重要事件。

更麻烦的是，当你需要跨项目把进度对齐给协作方时，松散的口述或备忘录并不能构成一份可追溯的工程记录。理想状态是：**完成工作的同时，日报也自动生成好了**，你只需要做最后的确认和微调，而不是从零开始组织语言。

## 二、问题定义：从原始日志到结构化日报需要解决什么

以 OpenClaw 生态为例，典型问题包括：

1. **源异构**：OpenClaw 采用 YAML/JSON 结构化日志，MCP Server 大多输出 JSON Lines，部分老脚本只有无结构文本或时间戳+消息体。
2. **时效与去重**：某些 Agent 会短时间内反复触发同一错误，日志可能重复数十条，直接全部放入日报没有意义。
3. **归并上下文**：单条日志只说“调用了某个工具”，缺少“该工具属于哪个任务链、任务目前成功与否”的语义。
4. **输出格式**：最终产出需要是一份 Markdown 或文本，可以粘贴到飞书、Notion，或通过 Webhook 发送到群里。

## 三、做法与步骤：一条最小化但能落地的流水线

这里不引入重量级调度系统，只基于脚本 + MCP + 简单的 Python 聚合器，让 OpenClaw 用户可以快速搭建。

### 步骤 1：统一日志收集格式

让所有产生日志的组件至少遵循一种可解析格式。推荐的最小约定是：

```json
{
  "ts": "2025-03-15T09:32:01Z",
  "source": "openclaw-agent/weather",
  "level": "INFO",
  "task_id": "daily-weather-0325",
  "message": "Fetched weather data for 3 cities",
  "extra": { "cities": 3, "duration_ms": 1203 }
}
```

- `source` 用来区分是 OpenClaw Agent，还是 MCP Server（例如 `mcp/github`）。
- `task_id` 用于将多条日志串联成一个任务，这是后续聚合的关键。

改造方法：
- 对已有 Python/Node 脚本，用标准库 json 输出一行一条 JSON，追加到统一日志目录。
- OpenClaw 本身支持 JSON 格式日志，只需在配置里指定。
- 对于只能用文本输出的老脚本，写一个轻量 wrapper 解析 stdout，添加时间戳和 source 后转换成上述格式。

### 步骤 2：按任务聚合，生成日报骨架

写一个聚合脚本（Python 约 150 行），流程如下：

1. 读取昨天（或今天截至某一时刻）的所有日志行。
2. 根据 `task_id` 分组，每组是一个任务。
3. 每个任务提取：
   - 起始时间、结束时间
   - 所有 `ERROR` 及以上等级的日志（摘要）
   - 任务结束时的最终消息（如 "finished successfully" 或 "aborted after 3 retries"）
   - `extra` 中关心的指标，如处理条数、耗时等。
4. 对无 `task_id` 的零散日志（如系统启动、健康检查），归入“系统事件”分组，并根据 source 和 message 内容做轻度去重（相同 source+message 在 30 分钟内只保留 1 条）。

聚合结果就是一个中间态日报对象，可以直接渲染成 Markdown。

### 步骤 3：生成结构化日报

由聚合脚本直接输出 Markdown：

```markdown
# 日报 - 2025-03-16 自动生成

## 任务执行摘要（7项）

- **daily-weather-0325**：成功，3城市数据更新，耗时1.2s
- **backup-db-nightly**：成功，备份大小 142MB，耗时 4min
- **crawl-prices**：部分失败，4/5 源成功，1 源超时待重试
- **agent-stock-alert**：已触发 2 次告警，均已通知
- **cleanup-temp-files**：成功，清理 12GB
- **mcp-github-sync**：成功，已同步 3 个 repo
- **system-events**：2 次健康检查通过，1 次计划重启

## 需要关注的事件

- [错误] `crawl-prices` 数据源 B 超时，今天第3次出现，建议检查对方接口。
- [警告] `agent-stock-alert` 内存使用超过阈值 85% 持续 5 分钟，可考虑调整并发数。

## 明日计划（建议项，需手动确认）
- 重试 `crawl-prices` 超时源并在监控中加入超时率指标。
- 评估 `agent-stock-alert` 是否需要资源限制策略。
```

这个模板确保了信息密度高，且可直接复制使用。

### 步骤 4：自动化调度与输出

触发时机：每天早上 9 点或在你开始工作前 10 分钟运行聚合脚本。

实施方式：
- 使用 cron 或 OpenClaw 自身的定时任务能力，调用脚本 `python3 gen_report.py --date today`。
- 输出结果可以通过：
  - 写入本地 Markdown 文件，再用 OpenClaw 的一个 Agent 发送到飞书/钉钉 (通过 Webhook 插件)。
  - 直接输出到剪贴板（仅限桌面环境），粘贴即用。
- 如果希望人工确认，可先生成“草稿”存为文件，在 IDE 中快速过一遍再发送。

## 四、踩坑点与经验

1. **task_id 设计不当导致聚合过稀或过密**  
   太粗（如 date-agent_name）会把不同日期的任务混在一起；太细（每次 HTTP 调用一个 task_id）则日报会膨胀成数百条琐碎记录。合理的粒度是**一个业务意义的任务**，比如“每天一次的数据抓取”“一次手动触发的事件处理”。可利用 OpenClaw 的 context，在启动任务时生成 UUID 并传递给后续步骤。

2. **日志时序乱序**  
   多进程/多线程输出日志可能先写入结束消息，再刷出中间步骤。聚合时需要根据 `ts` 排序，不要依赖追加顺序。同样，跨服务器若时钟不同步，可能出现“未来”时间戳，需要加入容错逻辑。

3. **隐私与敏感信息**  
   日志中的 query 参数、密码、token 可能会被打入日报。解析时最好配置过滤词/正则，将敏感字段替换为 `<REDACTED>`。

4. **错误摘要的表述要克制**  
   不要直接把调用栈堆进日报。应提取错误类型和关键消息，并限制每个任务内的错误摘要不超过 3 条，否则就只写“出现多次类似错误，详情见日志”。

## 五、可复用的建议

- **从现在开始统一日志格式**，即使只有两个组件，这个投入也会在两周内看到回报。
- **把日志和指标分开**：日报聚合的是日志事件，不适合承载精确的量化指标，后者应走单独的监控面板。
- **利用 MCP 的标准化接口**，如果你的 MCP Server 实现了 `logging` capability，可考虑让 OpenClaw 统一收集 MCP 的日志流到同一个日志文件，省去额外解析。
- **保留日报生成的历史 Markdown**，可以变成团队的每周回顾资料，或用来训练 AI 摘要模型，后续自动生成“本周关键进展”。

## 六、总结

从松散日志到结构化日报，核心不是花哨的 NLP，而是**约定、聚合、过滤、模板**四个工程动作。当你把日报生成纳入自动化流水线后，原本需要回忆和拼凑的认知负担就被转移到离线脚本里，你只需要在发送前花 2 分钟校对和微调。更进一步，这份日报可以成为你搭建 OpenClaw 内部工作台的一部分，为后续的 AI 辅助总结、任务回顾提供干净、一致的结构化数据。先写一个 200 行的聚合器试试，跑一周再迭代，效果远比想象中实用。
