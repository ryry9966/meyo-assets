## 背景

做自动化和 Agent 相关开发久了，总有一个绕不开的刚性需求：**日报**。无论是给自己复盘，还是向团队同步进度，从调试日志、API 调用记录、告警信息和脚本输出里提炼出一份清晰的日报，是一件高频却极其消耗心力的事。

在 OpenClaw 生态里使用 MCP 插件或自定义 Agent 时，各类工具会产生大量半结构化甚至非结构化的日志。一条典型的工作流可能是：Agent 调用浏览器插件抓取数据 → 本地脚本做清洗 → 写入 SQLite，中间夹杂各种异常重试。面对一天积攒的上千行日志，手工整理日报不仅低效，还容易漏掉关键异常。

于是我开始尝试构建一条**从原始日志到结构化日报的自动化流水线**，不求大而全，只求能在自己的一台开发机上稳定跑起来，每天早晨生成一份干净、可读的报告。

## 问题定义

表面上看，这是一个“把日志变成总结”的任务。但真正落地时，问题很快分解为四层：

1. **日志采集分散** – 不同工具、不同进程的日志格式不一致，有的带时间戳前缀，有的是 JSON Lines，有的只是 print 输出。
2. **关键信息提取** – 需要从日志流中区分正常步骤、警告和错误，识别重复模式，并关联上下文（比如某个 API 调用到底成功没有）。
3. **结构化与聚合** – 日报告需要按项目/模块、按时间窗口汇总，形成“完成事项”“进行中”“待解决风险”等版块。
4. **可靠交付** – 流水线本身不能静默失败，日报缺失时需要有兜底通知。

这也正好是一个典型的 Agent 编排场景：用 MCP 工具读取日志，用 LLM 做摘要，用脚本做格式转换与发送。但完全依赖 LLM 成本高且不稳定，核心思路应该是**规则先行、LLM 做补充**。

## 做法与步骤

整条流水线分为四个阶段：**收集 → 清洗与标记 → 聚合与生成 → 交付**。

### 1. 统一日志收集

我强制所有自研脚本和 Agent 工具统一输出到 `~/.openclaw-agent/logs/` 下，按 `YYYY-MM-DD/模块名.log` 存储。对于无法控制输出路径的 MCP 服务器或第三方插件，使用 `tee` 或 `systemd` 日志重定向，并在 crontab 里设置每小时同步脚本，把分散的日志文件复制到统一目录并追加日期。

关键操作：

```bash
#!/bin/bash
# sync_logs.sh
SRC_DIRS=( "/var/log/openclaw/plugins" "/home/user/project/logs" )
DST="/home/user/.openclaw-agent/logs/$(date +%F)"
mkdir -p "$DST"
for d in "${SRC_DIRS[@]}"; do
  find "$d" -type f -name "*.log" -mmin -60 -exec cp {} "$DST/" \;
done
```

这一步的坑在于文件命名冲突，所以我在复制时加入源目录的 hash 后缀。另外，按天分区让后续日报生成时只需读取当天目录。

### 2. 清洗与标记

清洗脚本使用 Python，遍历当天所有日志行，输出带标签的 JSON Lines：

- `ts` – 标准化时间戳
- `level` – 自动识别 ERROR/WARN/INFO，通过正则匹配
- `module` – 来源模块
- `message` – 原始消息
- `tags` – 预定义关键词匹配，如 `api_call`, `retry`, `timeout`, `done`

关键技术点：

- 对 JSON Lines 日志直接解析 `level` 和 `message` 字段；对纯文本日志用正则提取时间戳和级别，如 `^(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}) \[(ERROR|WARN|INFO)\] (.*)`
- 使用 Aho-Corasick 自动机做关键词匹配，在日志行中高效扫出 `tag`，避免逐行上百次正则。
- 对于跨行上下文（如 traceback），设置一个滑动窗口，当检测到 ERROR 后的缩进行，将其合并到同一条记录。

踩坑：时间戳格式五花八门，甚至有些日志只有时间没有日期。解决方案是读取时用文件修改日期补全缺失的日期部分。

### 3. 聚合与日报生成

清洗后的 JSON Lines 被加载到 SQLite 内存表中，方便做聚合查询。日报结构固定为三部分：

- **概览**：总日志行数、ERROR/WARN 数量、涉及模块
- **模块摘要**：每个模块的 INFO 关键事件（如“数据抓取完成: 200 条”）、ERROR 事件及最后发生时间
- **异常跟踪**：所有未恢复的 ERROR（即当日最后未见到对应恢复日志的异常）

生成逻辑用纯 SQL + 少量 Python 格式化：

```sql
-- 按模块聚合异常
SELECT module, 
       COUNT(*) FILTER (WHERE level='ERROR') AS errors,
       GROUP_CONCAT(DISTINCT message) AS error_msgs
FROM logs
WHERE date(ts) = date('now', 'localtime')
GROUP BY module
HAVING errors > 0;
```

然后用 Jinja2 模板渲染 Markdown。为什么不用 LLM？因为规则生成的结构已经足够清晰，只有在“异常跟踪”部分，如果同样错误反复出现，会调用一次 LLM（通过本地 API）对相同错误消息做一次压缩总结，避免报告中出现 100 行重复的“Connection timeout”。

LLM 调用加了双重保护：超时重试 1 次，返回内容若为空或超过模板预留长度，直接退回原文。

### 4. 交付与兜底

生成的 Markdown 日报写入 `~/daily_reports/日报-YYYY-MM-DD.md`，然后通过企业微信机器人 Webhook 推送。整个流水线由一个 systemd timer 在每天 8:00 触发。

**静默失败是这类流水线的大敌**。一旦某天日报没生成，很容易陷入“无人知晓”的状态。因此我增加了一个看门狗脚本，在 8:15 检查当天日报文件是否存在，否则通过 ntfy.sh 推送告警到手机。

## 踩坑复盘

1. **日志编码问题**：第三方插件有时输出 GBK 编码，导致 Python 读取报错。统一在读取时尝试 `utf-8` 失败后 fallback 到 `gbk`，并记录该文件路径以便后续修正。
2. **日界问题**：跨天运行的 Job 用 `date +%F` 取日期时，因凌晨执行可能拿到前一天日期，导致日志目录错位。改为在脚本内部统一使用 `TZ='Asia/Shanghai' date +%F`，并保证所有写入读取都使用同一时间源。
3. **SQLite 并发**：systemd timer 和手动测试同时触发会导致 database locked。解决方案是使用 WAL 模式，并加文件锁 (`flock`) 保证只有一个实例运行。
4. **LLM 幻觉**：让 LLM 总结错误时，有时会无中生有一条新的错误描述。后来限制 prompt 为“仅压缩重复消息，不得新增内容”，并在 render 阶段做 diff 检查。

## 可复用建议

- 如果你的 Agent 系统使用 MCP 插件，**务必约束日志输出规范**，最简单的就是要求每条日志必带时间戳和级别，这会大幅降低清洗成本。
- 不要一开始就上 LLM 管道，先用规则和模板生成 80% 的日报内容，只在真正需要语义概括的地方用 LLM 做补充。
- 交付环节加入 **watchdog**，日报生成类任务最容易“静默死掉”，缺少通知会导致信任崩塌。
- 整条流水线保持“无状态”，每次运行从原始日志目录重新计算，避免中间状态丢失导致不一致。

## 总结

从原始日志到结构化日报的自动化，本质上是一次**数据工程实践**和**可靠调度设计**的结合。在 OpenClaw/Agent 工具链中，我们已经有能力让程序完成复杂操作，但把这些操作的痕迹转化为人类可读的报告，依然需要精心设计规则和容错机制。这个流水线在我本地稳定运行了两个月，节省了大量早晨整理信息的时间，也让我更早发现了几次脚本静默异常的问题。

自动化不是一蹴而就，而是一步步把确定性的部分交给代码，把不确定性圈在可控范围里。
