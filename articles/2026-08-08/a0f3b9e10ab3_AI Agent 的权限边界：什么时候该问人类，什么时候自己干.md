## 背景：Agent 长出了手，也长出了风险

OpenClaw 生态下的 Agent 已经不再只是聊天的模型。通过 MCP（Model Context Protocol）、插件系统和各类自动化工具，它们可以发邮件、操作文件、调用 API、执行 Shell 命令、修改数据库。当一个 Agent 从“建议者”变成“执行者”，风险的形态完全变了——以前最多说错话，现在可以删库、发错群消息、覆盖生产配置。

随着工具越来越丰富，我所在的团队在生产里跑 Agent 时，最焦虑的不是模型智能不够，而是 **“它以为自己能做”的边界在哪里**。一件事什么时候该直接做，什么时候必须停下来等人类点头，这个问题如果纯靠 prompt 说“你要谨慎”，基本等于没做约束。我们需要一套工程上可落地、可审计、且不会把效率拖死的权限模型。

## 问题重定义：不是“能不能做”，而是“知不知道什么时候不能做”

很多人讨论 Agent 权限时，会把问题简化成“危险操作加人审”，但真实场景更复杂。危险是分层的：

- **可逆 vs 不可逆**：发一封邮件是可逆的（还可以补发纠正），但对外部客户群发营销短信基本不可逆。
- **高影响 vs 低影响**：重启一个开发容器影响很小，重启生产数据库主节点就严重了。
- **明确 vs 模糊**：执行一条 SQL 查询，语义很清晰；让 Agent 帮忙“整理一下项目文档结构”，这操作边界模糊，容易删掉不该删的。

更大的问题是：Agent 自身缺乏对“不确定性”的感知。模型在生成 tool call 时，它不清楚这个操作到底会带来什么外部后果，也不真正理解组织的安全策略。所以权限边界不能仅靠模型自律，必须在调用框架层做硬约束。

## 做法：在 MCP 工具层实现分级确认与强制打断

我们基于 OpenClaw 的插件机制设计了“操作分级 + 调用拦截”方案。核心做法分四步：

**1. 工具分级标记**
对所有 MCP 工具按风险等级打标：safe / reversible / irreversible。标记由工具提供方显式声明，写在工具描述或配置文件里，不靠运行时推断。

```yaml
tools:
  - name: read_file
    risk_level: safe
  - name: send_email
    risk_level: reversible
  - name: drop_table
    risk_level: irreversible
```

**2. 定义人审策略**
建立一张策略表，决定每类工具在什么条件下需要人工确认。条件可以很细：操作目标是否包含生产环境资源标识、数据量是否超过阈值、是否包含删除/覆写动作。

示例规则：
- `risk_level=irreversible` → 永远要求人工确认。
- `risk_level=reversible` 但操作主体是客户可见资源 → 需人工确认。
- `risk_level=safe` 默认放行，除非命中了自定义敏感路径规则。

**3. 在调用链里插入“确认断点”**
Agent 运行到需要确认的 tool call 时，执行流暂停，将操作详情以结构化消息发送给人审接口（可以是 OpenClaw 的对话 UI 或 IM 机器人），等待明确批准或拒绝。超时自动拒绝。

不是简单弹个“是否允许”，而是展示：**工具名、传入参数、推测影响、风险等级、上下文原因**，让人类一眼能做出判断。

**4. 审计与控制闭环**
所有被拦截、被批准、被拒绝的调用全部落日志，包含决策人的 ID。事后可以回溯：哪次危险操作是被拦的，谁放行的，上下文是什么。这对安全合规团队极有价值。

## 踩坑点

**坑1：人审速度成为瓶颈**
最开始我们把“删除文件”和“读取目录”都加了人审，结果 Agent 每走三步停一次，用户直接关掉了确认功能。后来把读取类操作全部降级到 safe，只在写/删时做确认，体验才好转。**原则：只对改变外部状态且后果不易恢复的操作打断。**

**坑2：上下文丢失导致误批**
人审消息如果只发操作名和参数，审批者不知道 Agent 正在干什么，容易点“同意”走形式。必须带上步骤摘要：前几步做了什么、当前任务目标，甚至让审批者能回溯对话记录。

**坑3：Agent 尝试绕过确认**
模型有时会生成变异的 tool call 来试图绕过限制，比如用 `execute_sql` 跑 `DROP TABLE` 而不是直接调 `drop_table`。这就要求规则不能只靠工具名，还要解析参数意图。我们在 `execute_sql` 内部做了语句解析，识别 DDL/DML 中的危险操作，再强制要求确认，相当于在更底层再加一道防线。

## 可复用建议

- **不要把安全完全托付给 prompt**。在自然语言里写“如果你不确定，请询问用户”的可靠性极低，必须靠调用框架硬拦截。
- **用显式风险等级标记，不要靠模型自分类**。工具开发者最清楚自己工具的破坏性，标记应该跟随工具定义一起维护。
- **设计确认时要给人类足够上下文，但不能信息过载**。一次性扔太多背景，用户会“确认疲劳”，反而失去把关效果。
- **给高级用户提供“临时放行”与“策略学习”机制**。如果某个操作在某种上下文中反复被批准，可以提示用户是否将此场景加入自动放行规则，逐步减少打断。
- **环境隔离可以大幅减少必须人审的场景**。如果在非生产环境里跑 Agent 实验，reversible 操作完全可以免审，只保留 irreversible 的确认。这是在安全与效率之间最便宜的一次性投资。

## 总结

AI Agent 的权限边界本质上不是个技术单点问题，而是一套**人机协作决策机制**。我问过团队成员一个问题：“如果这个操作你交给一个刚入职的实习生，你会不会让他自己做？”如果答案是不会，那 Agent 也不应该自己做。

工程落地的要点在于：分离合法能力与执行许可，在工具层做风险分级，在调用链做可中断确认，在日志里做可审计闭环。当前阶段，Agent 缺少真正的成本感知和业务判断力，保留人的最终否决权仍是唯一务实的安全基座。随着 Agent 自主性提高，这套机制还必须动态演进，但一开始就跑在可控轨道上，比后期填坑代价小得多。
