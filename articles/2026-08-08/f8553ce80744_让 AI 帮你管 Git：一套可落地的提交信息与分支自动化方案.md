## 背景：为什么 Git 自动化值得认真搞

在多人协作的代码仓库里，commit message 永远是老大难：“update”、“fix bug”、“WIP” 满天飞，导致 changelog 没法看、blame 时一头雾水。分支命名也是，随手建个 `test`、`dev2`，两个月后根本想不起来是干什么的。

过去我们搞 git hooks + 模板规范，但强制约束往往被绕过。后来在 OpenClaw 社区里看到不少同学把 Agent 用在代码审查、文档生成上，我突然想到：能不能让 AI 助手接管一部分 Git 的琐碎决策？比如自动生成结构化的提交说明，或者根据 Issue 标题自动建议分支名。

我花了一个周末在本地搭了一套轻量方案，既能保持 commit 历史干净，又不需要人肉遵守规范。这篇文章就是一次工程化的复盘，包含代码、踩坑和可复用建议。

## 问题拆解

我们的输入是**代码变更**（git diff）和**上下文**（如任务标题），输出是**规范的 commit message** 和**合理的分支名**。挑战有三点：

1. **信息截断**：模型上下文有限，diff 太长会被截断，导致生成的 message 丢失关键修改说明。
2. **格式稳定性**：git 对 commit message 的格式有隐形要求（首行不得超过 50 字符，之后要有空行等），AI 很可能返回不符合格式的内容，导致提交中断。
3. **延迟与成本**：如果每次提交都调一次云端 API，网络抖动和费用都是问题。

我选择**本地模型 + git hook** 的方案，通过 `prepare-commit-msg` 钩子在用户编写 message 之前自动预填建议信息，再由人工确认或微调。

## 实践步骤

### 1. 准备本地 AI 服务
我用 Ollama 部署了 `qwen2.5:7b`，它体积小、响应快，对中文友好。启动服务：

```bash
ollama pull qwen2.5:7b
ollama serve
```

如果你所在网络能直连 OpenAI 兼容 API，也可以用任何支持 `/v1/chat/completions` 的服务，替换即可。

### 2. 创建一个 Python 脚本用于生成 commit message
在仓库根目录下创建 `scripts/gen_commit_msg.py`：

```python
import sys
import subprocess
import requests
import os

OLLAMA_URL = "http://localhost:11434/v1/chat/completions"
MODEL = "qwen2.5:7b"

def get_diff():
    try:
        diff = subprocess.check_output(['git', 'diff', '--cached', '--stat'], text=True)
        if diff.strip():
            return diff[:3000]  # 截断过长内容
        diff = subprocess.check_output(['git', 'diff', '--stat'], text=True)
        return diff[:3000]
    except:
        return ""

def generate_message(diff_text, branch_name):
    if not diff_text:
        return ""
    prompt = f"""你是一个严谨的代码助手。根据以下 git diff 摘要和当前分支名，用中文（或英文）生成一条简洁的 commit message，格式如下：
<类型>: <简短描述>
空行
<详细说明>

类型可选：feat, fix, refactor, docs, test, chore 等。首行不超过 50 个字符。

分支名: {branch_name}
Diff 摘要:
{diff_text}
"""
    data = {
        "model": MODEL,
        "messages": [{"role": "user", "content": prompt}],
        "temperature": 0.2,
        "max_tokens": 300
    }
    try:
        r = requests.post(OLLAMA_URL, json=data, timeout=10)
        r.raise_for_status()
        content = r.json()["choices"][0]["message"]["content"]
        # 清洗多余的空行和符号
        lines = content.strip().splitlines()
        if lines and lines[0].startswith("```"):
            lines = lines[1:]
        if lines and lines[-1].startswith("```"):
            lines = lines[:-1]
        return "\n".join(lines)
    except Exception as e:
        print(f"AI 生成失败: {e}")
        return ""

if __name__ == "__main__":
    branch = subprocess.check_output(['git', 'rev-parse', '--abbrev-ref', 'HEAD'], text=True).strip()
    diff = get_diff()
    msg = generate_message(diff, branch)
    if msg:
        print(msg)
```

### 3. 挂载 Git Hook
在 `.git/hooks/prepare-commit-msg` 中写入（注意需可执行权限 `chmod +x`）：

```bash
#!/bin/bash
# 仅在非 merge、非 squash、非 template 时执行
if [ "$2" = "merge" ] || [ "$2" = "squash" ]; then
    exit 0
fi

MSG_FILE="$1"
# 如果 message 文件已有内容（例如 -m 指定了），不覆盖
if [ -s "$MSG_FILE" ]; then
    exit 0
fi

AI_MSG=$(python3 "$(git rev-parse --show-toplevel)/scripts/gen_commit_msg.py")
if [ -n "$AI_MSG" ]; then
    echo "$AI_MSG" > "$MSG_FILE"
fi
```

这样每次执行 `git commit`（不带 -m）时，编辑器会预填 AI 生成好的 message，你可以直接 `:wq` 提交或修改。

### 4. 分支自动命名（扩展）
如果你从某个任务平台（如 Jira、线性系统）获取 Issue 标题，可以写一个脚本 `suggest_branch.py`，调用类似 prompt 让 AI 把标题转成 `feature/XXX-123-add-login` 格式，再用 `git checkout -b` 自动创建。这通常结合 Git 别名使用，而非 hook，因为 hook 触发时机不合适。

## 踩坑实录

**坑1：扩散中的 diff 造成 token 溢出**  
当你首次添加大量文件时，`git diff --cached --stat` 可能也超过模型长度。必须截断，比如只取前 3000 字符。更好的策略是只传递改动的文件列表和前几个文件的 diff 摘要。

**坑2：AI 返回的 message 包含非法字符**  
Ollama 有时会返回 markdown 代码块包裹，或者首行超长。脚本里做了简单清洗，但仍然建议在 prompt 中强调“不要用 markdown 包裹，直接输出文本”。如果首行过长，git 会拒绝提交，测试时要留意。

**坑3：钩子影响交互式提交效率**  
调用本地模型响应约 2-5 秒，如果网络或服务未启动，会造成等待超时。建议加上超时 (我设了 10 秒) 和静默失败，不让钩子阻塞提交流程。

**坑4：敏感信息泄露**  
不要把包含密码/密钥的文件变更无意中发给模型，尤其是使用云端 API 时。可以在脚本里过滤文件名关键词，或只提交统计信息。

## 可复用建议

- **模板约束**：prompt 的格式必须严格，因为生成的结果要直接写入 git。用 few-shot 示例能显著提高合格率。
- **分层回退**：如果 AI 服务不可用，脚本返回空字符串，让开发者自己写，不要阻塞提交。
- **日志记录**：将 AI 生成过程中的错误记录到 `.git/ai_hook.log`，方便排查。
- **团队推广**：不要强制所有人安装 hook，用 `make setup-hooks` 提供一键安装脚本，尊重个体差异。
- **结合 pre-commit 框架**：如果团队已用 `pre-commit`，可以把 Python 脚本封装成 pre-commit hook，统一管理依赖。

## 总结

与其天天拷问队友“这个 commit 到底改了什么”，不如让 AI 先丢出一个 80 分的草稿，人再微调。这套方案我用了一个多月，提交信息质量肉眼可见地提高，分支切换也不再痛苦。代码整体才 70 行 Python，运行在本机，几乎零成本。如果你的团队正在实践 Agent 辅助研发，可以把 Git 自动化当作首个入门实验，投入产出比很高。

希望这篇文章能帮你把 Git 流程打磨得更丝滑。
