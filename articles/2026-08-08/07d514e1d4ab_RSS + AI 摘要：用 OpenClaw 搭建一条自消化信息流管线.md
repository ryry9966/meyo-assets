## 背景：为什么需要一条信息流管线

信息获取的瓶颈早已不是“找不到”，而是“看不完”。当 RSS 订阅源超过 20 个，每天涌进来的数百条标题就会迅速变成未读红点，最终被标记已读、一键清空——阅读效率趋近于零。

与此同时，大型语言模型的摘要能力已经足够工程化落地：它能把一篇 3000 字的评论压成 80 字，同时保留核心观点。真正缺的是一条稳定、低维护、无需人工介入的管线，把“抓取-清洗-摘要-投递”串起来。

这篇文章要做的，就是用 OpenClaw 的 Agent、MCP 协议和内置插件体系，把 RSS 变成每天一杯浓缩信息。

## 问题拆解：管线的四个核心环节

一条可靠的信息流管线至少需要解决四个问题：

1. **订阅与抓取**：准时拿到源数据，处理更新频率、304 缓存、Feed 格式差异。
2. **内容提取**：从 RSS 摘要、截断正文、原始网页中拿到完整可读文本，去广告、导航、相关推荐。
3. **AI 摘要**：调用模型生成可控长度、语言一致的摘要，处理好 token 消耗与并行请求。
4. **推送与存档**：摘要送达到日常阅读工具，同时保留原文链接，方便回溯。

只有每个环节都做到“静默运行、失败自愈”，这条管线才不会从自动化变成新负担。

## 做法：在 OpenClaw 中串联成工作流

这里不给出单次脚本，而是展示一个可以长期运行的 Agent 工作流设计。所有步骤都可以在 OpenClaw 内编排，通过 MCP 扩展对接外部能力。

### 1. 配置 RSS 源并定时触发
在 OpenClaw 中使用 `cron` 触发器，每 6 小时（或每条新文章）触发一次抓取流程。RSS 源列表维护在一个配置文件中，每条包含：
- feed_url
- 自定义名称
- 最大抓取条目数
- 是否启用全文提取
- 目标推送渠道

使用 OpenClaw 的 **RSS MCP server**（社区已有实现）完成标准化抓取，返回统一的 `{title, link, contentSnippet, pubDate}` 结构。这里要注意：很多 RSS 源在 `contentSnippet` 中截断，必须做好紧接着的全文提取。

### 2. 全文提取与清洗
对于需要完整正文的源，通过 **网页爬取 MCP（fetch + readability）** 获取并清洗文章。在流程中嵌入重试逻辑：一次读取超时，间隔 2 秒后重试两次，仍失败则降级使用 RSS 摘要内容。

清洗后的文本统一存入临时上下文，不做持久化，只在这个工作流生命周期内流转。此时每条文章变成一个对象：
```
{
  title, link, pubDate, cleanText, length
}
```

### 3. AI 摘要生成
调用 **LLM MCP server**（可配置 OpenAI 兼容接口或本地模型），逐个文章生成摘要。这里踩坑最多，后面单独讲。

摘要要求通过 prompt 模板固定下来，比如：
```
你是一个技术信息筛选助手。请用 3 句话总结以下文章的核心观点，包含“做了什么”、“为什么重要”、“是否可操作”。只输出中文。
```

输出格式固定为纯文本，方便后续分发。同时记录 token 消耗，用于监控成本。

### 4. 多渠道推送与归档
摘要产出后，根据配置推送到不同渠道。OpenClaw 内置了对 Telegram、邮件、Obsidian（通过 MCP 写本地 Markdown）等渠道的支持。我目前的实践是：
- **Telegram 频道**：即时推送，每条消息包含标题、摘要、原文链接、发布时间。
- **Obsidian 日记目录**：生成 `YYYY-MM-DD - AI Digest.md`，把所有当次摘要追加进去，方便检索。

推送完成后，RSS 条目标记为已处理，避免重复。整个流程日志写入 OpenClaw 的 run history，异常会触发通知。

## 踩坑点：工程上的真实代价

**1. 摘要长度失控**  
用“3 句话”约束不总是有效，某些模型喜欢输出 5-6 句。需要在 prompt 末尾加一句“严格 3 句，超过则不输出”，并且在后处理中按句号切分截断。更稳定的做法是追加 max_tokens 限制，但要保证不会切断句子，可以再套一层简单的规则检测。

**2. 全文提取失败率高**  
中英文媒体的正文提取不可靠，尤其是付费墙、动态加载页面。Readability 算法会吞掉大段引文或代码块。可接受的折中是：正文提取失败时使用 RSS 自带的 contentSnippet，并在摘要里注明“基于来源摘要生成，非全文”。

**3. API 速率与并发**  
一轮抓取可能产生 30 篇文章，直接并发调用 LLM 会立刻触发 rate limit。需要用信号量控制并发数（例如一次 3 条），并在返回 429 时自动退避。OpenClaw 的 task 编排天然支持这种并发控制，只需在 node 配置里指定 `maxConcurrency: 3`。

**4. Feed 不可靠**  
部分 RSS 源会间歇性 500、SSL 过期、feed URL 重定向。要设置超时 15 秒，失败后跳过该源并记录日志，而不是拖垮整个流程。

## 可复用建议

- **模块化节点**：将“抓取”、“清洗”、“摘要”、“推送”设计为四个独立的可复用 Agent 节点，便于单独调试或替换实现（比如清洗从 readability 换成 mozilla/readability）。
- **摘要模板外部化**：不要硬编码 prompt，放在配置里，可以针对不同源用不同模板。技术博客摘要侧重“核心结论”，新闻摘要侧重“发生了什么”。
- **监控与降级**：在管线中间增加一个 check 节点，如果摘要为空或全部失败，则发送简要通知，避免静默断流。

整个工作流的 OpenClaw YAML 配置可直接在项目仓库里版本控制，团队其他人 clone 后批量导入即可跑起来。

## 总结

RSS + AI 摘要管线不是新概念，但用 OpenClaw 和 MCP 搭建的意义在于：它把过去零散的 Python 脚本、docker cron、消息通知黏合成一个可观测、可扩展的工作流。一旦跑通，信息处理就从“每天花一小时扫标题”变成“早晚各看两条 Telegram 消息”，而源头依然是你自己筛选过的信源，没有被算法稀释。

这条管线的维护成本很低，唯一持续投入的是偶尔修复失效的 feed 和调整摘要长度偏好——相比于信息焦虑的缓解，这笔时间账非常划算。
