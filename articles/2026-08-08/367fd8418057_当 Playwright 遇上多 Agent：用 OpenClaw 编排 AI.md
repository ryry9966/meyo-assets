## 背景：E2E 测试的“最后一公里”依然麻烦

端到端（E2E）测试能模拟真实用户路径，验证关键业务流程，但编写和维护成本居高不下。选择器稍纵即逝，页面结构一改，几十条用例就变成维护债务。AI 辅助生成测试脚本不是新鲜事，但单次 prompt 生成的代码往往充满幻觉：`page.click('.btn-submit')` 看起来正确，实际按钮可能是 Shadow DOM 里的组件，或者动态挂载，测试跑起来就崩。

真正拖慢进度的不是“不会写”，而是“写出来跑不通 → 盯着报错和截图修脚本 → 修完又发现新问题”这个循环。一次成功的 E2E 测试生成，需要的不只是代码补全，而是一个能理解需求、执行、观察反馈并自我修正的闭环。

## 问题拆解：单 Agent 的边界

上一次我们尝试让一个 LLM Agent 直接生成 Playwright 脚本，结果很不稳定。分析下来，是因为一个 Agent 要同时承担三件事：

1. 将自然语言用例翻译为可操作步骤（需求解释）
2. 生成合法且稳健的 Playwright 代码（工程实现）
3. 处理运行时异常并修复（调试观察）

这三件事所需的上下文和推理模式差别很大。强行塞给一个 Agent，prompt 变臃肿，幻觉率飙升。更合理的方式是借鉴软件工程的分工，用多个 Agent 协作完成。

正好 OpenClaw 对多 Agent 协作有原生支持，我们决定搭一条“E2E 测试自动修复流水线”，让一组 Agent 各司其职，用结果文件兜底，跑在一个可控的沙箱里。

## 做法：四阶段流水线与 MCP 执行

整个流程如图（见配图），核心是四个 Agent 角色：

- **需求解析 Agent**：接收非结构化的测试场景描述（例如“用户登录后修改昵称，并验证新昵称出现在主页”），输出结构化步骤列表，包含前置状态、操作及预期断言。
- **代码生成 Agent**：根据结构化步骤生成 TypeScript + Playwright 代码，强制使用 `page.getByTestId()` 或 `page.getByRole()` 等较稳定选择器，并补全必要的等待策略（如 `waitForResponse`）。
- **执行 Agent**：通过 Playwright MCP Server 在真实浏览器中运行生成的脚本，捕获报错、console 日志以及关键截图。
- **修复 Agent**：接收执行结果（截图 + 错误堆栈 + DOM 快照），分析失败原因，返回修正后的代码或选择器建议，再交回执行 Agent 验证。

这里用到了 OpenClaw 的 **MCP 集成**。我们把 Playwright 封装成一个 MCP Tool，暴露 `navigate`、`click`、`type`、`screenshot` 等原子操作。执行 Agent 并不直接读脚本源码，而是通过 MCP 驱动浏览器，这样能精确获得每一步的运行时信息。代码生成 Agent 输出的脚本，实质上是给执行 Agent 的“计划”，再由执行 Agent 翻译为 MCP 调用去执行——这个间接层避免了直接运行脚本时难以捕获中间状态的问题。

配置上，在 OpenClaw 里定义一个顺序流水线（Sequential Pipeline），并在执行 Agent 与修复 Agent 之间设一个简单的循环控制器：最多重试 3 次，每次重试前将上次的失败上下文注入修复 Agent 的 prompt。所有生成的代码和修正记录会写回工作目录，方便人工审查和纳入 Git。

## 踩坑实录

### 选择器“看起来稳健”，实际依旧脆弱

即使提示词里明确要求优先 `data-testid`，生成 Agent 仍会偶尔偷懒用 `text=登录` 或 CSS 类名。我们的补救措施是在代码生成后增加一个静态检查 Agent（简单的规则扫描），用 AST 快速发现不推荐的选择器并强制替换。如果前端团队没有铺 `data-testid`，我们要么接受一定比例的维护成本，要么退而求其次让 Agent 使用 `getByRole` 并辅以正则匹配，但需要人工确认可访问性标记是否齐全。

### 执行环境隔离不够

直接在开发者本地跑 MCP 浏览器会污染用户数据，而且可能受本地插件影响。我们最后用 Docker 启动一个独立的 chromium 实例，通过 CDP 连接，MCP Server 指向该容器。这带来一个问题：页面中的第三方服务（如 SSO）可能依赖内网地址，容器需要正确配置网络和 hosts，这部分在首次搭建时踩了不少坑。

### 修复 Agent 容易陷入“补丁循环”

两三次重试后，修复 Agent 有时会给出一个“碰巧能跑通”但不泛化的选择器（比如 `nth-child(3) > div > span`）。虽然测试当下绿灯，下一轮 CI 必然挂。我们不得不在修复 prompt 中明确禁止使用结构选择器，并始终要求给出可解释的定位策略。若 3 次仍失败，则把完整上下文推送到人工审核队列，不强行通过。

## 可复用建议

1. **从契约测试的角度定义需求**：让需求解析 Agent 输出的不只是步骤，还应包括触发动作与预期的 API 响应 / UI 变化，这样可以同时做数据校验。
2. **沙箱化执行**：浏览器执行环境必须与开发环境隔离，推荐用容器化的 Playwright server 或 browserless 服务，保证每次运行状态一致。
3. **限定重试次数与修复策略**：别让 Agent 无限修下去，浪费 token 和时间。3 次后转人工，并把失败用例、截图、DOM 打包留痕。
4. **代码一定要入库审查**：AI 生成的测试代码和人工写的一样需要 review。我们会在修复完成后生成一个 PR 摘要，由开发者合并前确认。
5. **利用 MCP 抽象浏览器操作**：比直接运行脚本更易观测和调试，而且可以为后续把执行 Agent 换成视觉模型等更高级方案留接口。

## 总结

用多 Agent 协作处理 E2E 测试生成，核心收益不是零人工，而是把“写 → 跑 → 修”的最枯燥循环自动化，让人只需要做最后的确认和策略调整。OpenClaw 的流水线编排和 MCP 插件让各 agent 的边界很清晰，出问题时也能快速定位是需求理解错了、代码生成有毛病还是执行环境的问题。现阶段最扎实的使用方式，是把它作为测试团队的“自动补刀”工具：快速生产草稿，自动修正到可运行状态，再由人工拍板合入。

当你的项目中有大量重复性、流程化的 E2E 场景时，这套模式值得尝试。
