定时任务是 Agent 和自动化流程里最容易被轻视的一环。选错机制，轻则浪费资源，重则漏触发、误重试，甚至把下游打挂。OpenClaw 提供了两种原生定时触发能力：**cron** 与 **heartbeat**，经常被问到“到底用哪个”。这篇文章从工程实践角度，把二者的边界、适用场景和常见踩坑点一次理清。

---

## 一、背景：为什么要有两种？

简单说：cron 解决“**在某个时间点触发**”，heartbeat 解决“**以固定间隔持续运行，且需要感知活性**”。

但在实际 Agent/MCP 工作流里，事情没这么简单。比如：

- 你需要每 30 秒拉取一次消息队列，但拉取后任务可能耗时 2 分钟。
- 你需要每小时生成一份报表，但要求恰好是整点触发，不能因为上次任务没跑完就错过。
- 某个 MCP 工具调用需要后台心跳维持长连接，调用侧必须能感知“工具是否还活着”。

这些问题背后，考验的不只是定时精度，还有**任务重叠处理、失败降级、活性检测与资源占用**。

---

## 二、cron 与 heartbeat 的本质区别

**cron** 基于时间表达式（如 `0 */2 * * *`），规则是“到点就发一次触发信号”。  
**heartbeat** 基于固定间隔（如 `interval: 30s`），规则是“每次执行完成后，再等 interval，开始下一次”。

关键差异：

| 维度 | cron | heartbeat |
|------|------|-----------|
| 触发基准 | 挂钟时间 | 执行结束时间 |
| 并发策略 | 可能上一次未结束，新触发又来 | 默认串行，不会重叠 |
| 断连感知 | 不感知任务是否存活 | 可通过超时与错误计数感知 |
| 适合场景 | 日历驱动、对齐绝对时间 | 恒频轮询、心跳保活、消费型循环 |

举个例子：  
- 用 cron 做“每 10 分钟从 API 拉一次数据”，如果某次拉取因为网络慢跑了 12 分钟，就会和下一次触发撞车。  
- 用 heartbeat 做同样的事，虽然不会有并发重叠，但真实的拉取间隔会漂移成“完成时间 + 10 分钟”，可能逐渐偏离原始时间。

## 三、配置与使用步骤（关键做法）

### 1. 声明式配置示例

在 OpenClaw 的 `tasks` 定义中，两种方式都非常简洁：

```yaml
tasks:
  - name: hourly_report
    type: cron
    cron: "0 * * * *"
    timeout: 600s
    task_ref: generate_report

  - name: queue_listener
    type: heartbeat
    interval: 15s
    timeout: 30s
    max_consecutive_failures: 3
    task_ref: poll_queue
```

### 2. 选择逻辑（可复用判断树）

我在多个工作流中总结出一个简单决策顺序：

- 需求是否**必须对齐挂钟时间**（如整点、每天 8:00）？  
  → 是：用 cron，并做好锁或幂等防重叠。
- 是否需要**恒定的触发频率**（不管每次跑多久）？  
  → 是：用 cron，但必须设置 `timeout` 与并发控制。
- 是否是一个**持续消费循环**，根本不关心绝对时间？  
  → 是：用 heartbeat，天然防止堆积。
- 是否需要**监测对端活性**（如 MCP 连接）？  
  → 是：heartbeat 配合超时和失败计数是最简方案。

### 3. MCP/Agent 场景的特殊注意

当你通过 OpenClaw 调度 MCP 工具调用时，heartbeat 还有一个隐藏优势：它能作为**心跳探针**维持工具层的长连接。  
例如某些 MCP 服务器要求客户端每隔 30 秒发一次 `ping`，否则断开。用一个 `interval: 25s` 的 heartbeat 任务包装 `mcp_ping`，并在失败后触发预警，比额外写独立健康检查进程省事且对等。

## 四、踩坑记录与排障复盘

### 坑 1：cron 任务隐形堆积

**现象**：某天中午 12 点后的数据报表有少量重复、时间戳异常。  
**排查**：那一小时外部 API 超时，任务跑了 7 分钟，刚好下一分钟的新触发又起来，两个实例同时操作同一个临时表，导致幂等失效。  
**修复**：cron 任务增加 `concurrency_policy: forbid` 或加 Redis 分布式锁，且对关键写操作做幂等。  
**教训**：**永远不要假设 cron 任务一定能在下一个周期开始前结束**。

### 坑 2：heartbeat 的“死亡沉默”

**现象**：心跳任务因一次 OOM 被杀死后，进程不在了，但 OpenClaw 的调度器没有立即感知，导致长达 20 分钟无告警。  
**原因**：我们只配置了 `interval`，没配 `max_consecutive_failures` 和明确的 `timeout`。进程消失后，外部看就像“执行中没返回”，直到长时间超时才报错。  
**修复**：heartbeat 任务务必同时设定 **严格的 timeout（应与 interval 配合，留出缓冲）** 和 **连续失败阈值**。  
**公式参考**：`timeout < interval - 预估最大执行时间`，并设置 `max_consecutive_failures ≤ 3`。

### 坑 3：时区与 cron 表达式的微妙坑

如果宿主机的时区与 OpenClaw 容器不一致，cron 会以容器内时区为准。曾在一次跨国部署中，容器时区为 UTC，而业务期望北京时间 8:00 触发，写成了 `0 8 * * *`，结果在 UTC 8:00 触发。  
**解法**：显式在配置中声明 `timezone: "Asia/Shanghai"`，或使用带时区的 cron 库语法（如 TZ 前缀），不要依赖系统默认。

## 五、可复用的工程化建议

1. **默认倾向 heartbeat，除非明确需要日历语义**。  
   在大多数轮询、消费场景下，heartbeat 行为更可预期，风险可控。

2. **cron 任务标配“三件套”**：  
   - `timeout`：强制超时终止，比任务自身保证更可靠  
   - `concurrency_policy`：forbid / replace，防止堆积  
   - 外部锁或幂等标记：不要靠调度器保证唯一执行

3. **heartbeat 的“安全三参数”**：  
   - `interval`：基础心跳间隔  
   - `timeout`：单次最大执行时间  
   - `max_consecutive_failures`：异常检测灵敏度

4. **可观测性组合**：  
   无论哪种，都输出结构化日志（至少包含 `task_name, trigger_type, start_time, outcome`），并设置执行耗时指标。heartbeat 要额外监控“连续失败次数”和“最近一次成功时间”，用于探测寂静故障。

---

## 六、总结

cron 与 heartbeat 的选择，本质是你在权衡**时间语义、资源重叠风险与故障模型**。没有银弹，但可以通过少量前置约定把坑堵住：cron 严防重叠，heartbeat 严防静默。工程上多花 5 分钟加上超时和并发策略，远好过半夜收到下游告警再追日志。

在 OpenClaw 的自动化拼图里，定时任务是最基础的一块砖，放稳了，上面的 Agent 与 MCP 集成才不会摇摇晃晃。
