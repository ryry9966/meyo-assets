## 背景：当 Agent 的腿被 “打断” 时

在基于 OpenClaw 或类似框架构建的 AI Agent 中，外部 API 是最常见的 “手脚”—— 查天气、调搜索、访问数据库、发邮件，几乎所有有价值的能力都依赖外部服务。但任何有过生产经验的人都知道：API 会挂，延迟会漂，限流会突如其来。

问题不在于 “会不会挂”，而在于挂了之后 Agent 怎么处理。传统的做法是在代码层硬编码重试、熔断、降级，但 LLM 驱动的 Agent 本身就具备推理能力，如果能将错误信息正确地喂给模型，就可以把故障恢复从机械的 `try/catch` 升级为上下文感知的智能决策。

这篇文章总结我在 OpenClaw 插件和 MCP 服务器开发中，让 Agent 优雅处理外部 API 故障的一套模式，不依赖某个特定平台，工程可落地。

## 问题：重试循环、幻觉回复与沉默失败

当一个工具调用失败时，如果不加干预，Agent 最常见的行为有三种：

1. **无限重试**：LLM 看到 “调用失败”，可能反复尝试同一个工具，尤其在思维链中它会假设 “刚刚只是运气不好”，直至耗尽 token 或超时提示。
2. **幻觉回复**：工具没拿到数据，模型编造一个看似合理的答案糊弄用户。
3. **沉默失败**：给了模棱两可的 “出了点问题”，流程卡死，而用户不知道发生了什么。

这三种行为都源于同一个根因：**模型没有获得足够的结构化信息来做恢复决策**。一个 `500 Internal Server Error` 和一个 `429 Too Many Requests` 对于模型来说只是一串字符串，除非我们告诉它区别。

## 做法：让 Agent 学会 “读懂” 错误并决策

核心思路是把错误变成一种可被推理的输入，同时用工程手段兜底，防止 worst-case 行为。下面是实践过的四步做法，按优先级排。

### 1. 设计结构化的错误响应

不要在工具层面直接抛出异常让 Agent 进程崩溃，也不要只返回 `"error":"something went wrong"`。应当把每个工具的错误响应包装成标准的 JSON，字段至少包含：

- `error_code`：机器可读的错误码，如 `RATE_LIMITED`、`AUTH_FAILURE`、`UPSTREAM_TIMEOUT`
- `severity`：`retryable` / `non_retryable` / `degraded`
- `user_message`：适合展示给用户的一句话
- `retry_after`：（可选）建议等待秒数
- `suggestion`：给模型看的操作建议，例如 `"You can retry in 10s, or try the cached version, or ask the user to try later."` 

在 OpenClaw 的 MCP 工具定义中，可以在输出 schema 里显式声明这些字段，让模型明确知道会收到什么。

### 2. 用系统提示教会 Agent 如何决策

工具响应只是数据，决策仍然需要指令。在 Agent 的 system prompt 中加入这类规则（简化版）：

> 当工具返回 `severity: retryable` 时，你可以最多重试 2 次，每次重试前等待建议的时间。当 `severity: non_retryable` 时，不要再次调用同一工具，而应考虑降级方案，例如使用本地缓存数据、类似工具，或向用户解释当前限制。

这里有一个关键技巧：**给重试次数设上限**，并且在 prompt 中明确写出 “如果重试 N 次仍失败，必须停止并告知用户”。这会大幅降低死循环概率。

### 3. 工程兜底：退避、熔断与超时

模型按指令行事，但代码层必须防止模型 “不听话” 的情况。即使 prompt 里写了最多重试 2 次，仍可能出现意外循环，因此需要在工具封装层强制约束：

- **指数退避 with jitter**：针对可重试错误，工具实现内部自动重试 1-2 次，而不是完全依赖 Agent 来重试。建议用 `min(600ms * 2^attempt, 10s)` 加随机抖动，避免惊群效应。
- **熔断器**：对同一个外部 API 设置熔断，若在滑动窗口内失败率超过阈值（如 5 次连续失败），直接短路返回 `severity: non_retryable`，让 Agent 走降级路径。熔断状态需要持久化（文件/Redis），这样进程重启后还能记住 “这个 API 刚才就挂了”。
- **严格的单工具超时**：每个工具调用设定绝对超时（如 30s），超时返回 `UPSTREAM_TIMEOUT`，防止 Agent 卡住。

在 OpenClaw 插件中，可以把这一整套逻辑封装成 `ResilientTool` 类，对外暴露与普通工具一致的接口，内部集成重试、熔断、错误格式化。

### 4. 为关键路径准备降级方案

Agent 的韧性最终取决于 “没有这个 API 我还能干什么”。为高频工具配备降级数据源：

- 搜索 API 不可用时，退回本地文档检索或缓存结果。
- 天气 API 故障，用最近一次缓存数据并明确标注时间。
- 需要写操作时，若上游写服务不可用，将操作写入内部队列暂存，待恢复后重放。

同时，在工具描述里告诉 Agent 降级能力的存在，这样模型在碰到 `non_retryable` 时会主动尝试。

## 踩坑点实录

- **把 429 和 500 混为一谈**：429 必须等，500 可能立刻重试也能成功。错误码不分清，模型就不知道该等还是该重试。
- **熔断状态忘记持久化**：开发时进程常驻看不出问题，线上容器重启后熔断器清零，刚启动的 Agent 又去猛锤那个已瘫痪的 API，加剧雪崩。
- **超时设置过长**：Agent 单个步骤卡住 60 秒，用户体验极差，而且 LLM 会误以为 “工具还在跑” 而重复调用。工具超时最好短于 Agent 级别的 step timeout。
- **降级数据过于陈旧误导模型**：告诉模型这是 “昨天的缓存” 没问题，如果伪造当前时间戳，后续推理会一错到底。
- **模型无视错误建议**：有时提示里写了 “不要重试”，但模型仍硬来。必须在工具侧做最终拦截（熔断短路）而非完全信任 prompt。

## 可复用建议

如果你正在开发自己的 Agent 工具或 MCP 服务器，可以考虑这个精简版的检查清单：

1. 每个工具返回统一的结构化错误模型（`error_code`、`severity`、`suggestion` 至少三个字段）。
2. 在工具的 system prompt 片段中加入错误处理决策指南，并硬限制最大重试次数。
3. 对下游 API 封装轻量级 resilience 层：指数退避、熔断、超时。
4. 关键工具提供降级数据源，并在工具描述中暴露降级能力。
5. 全链路日志记录每次工具调用的原始错误，便于事后分析 Agent 的决策是否合理。

与传统的微服务错误处理不同，AI Agent 给了我们一个额外杠杆：可以用自然语言告诉模型 “发生了什么，你可以怎么做”。但这根杠杆只有建立在坚实的工程基座上才安全 —— 提示词定方向，代码托底。

## 总结

外部 API 故障不是异常，是常态。AI Agent 的优势在于它能把故障视作一个需要推理的 “情况”，而不是简单的 pass/fail。把错误信息结构化地暴露给模型，加上经典的后端韧性手段，就能做出不慌张、不胡说、不卡死的自动化流程。最终目标：让用户感知到的是 “这个助手很稳”，而不是 “它又挂了”。
