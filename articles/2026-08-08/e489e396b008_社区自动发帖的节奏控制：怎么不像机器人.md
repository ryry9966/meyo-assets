## 背景

在 OpenClaw 开源社区里，不少维护者会通过自动化脚本把项目周报、更新日志或精选讨论同步到多个平台（GitHub Discussions、Discord、飞书话题群等）。最近几周我在搭建一套基于 OpenClaw Agent 调度器 + MCP browser-use 工具的同步管线时，踩了一个很经典的坑：发帖速度和行为模式过于机械化，触发平台的风控策略，导致账号被临时限制甚至帖子被折叠。

经历过几次短暂封禁后，我重新设计了发帖的节奏控制模块，让它运行起来更接近一个真实社区维护者的操作习惯。这篇文章把做法、踩坑点和可复用的工程化建议整理出来，供同样在用 Agent/MCP/自动化管线的朋友参考。

## 问题拆解

所谓“不像机器人”，本质上要消除以下几个可被检测的特征：

1. **请求间隔固定**：相邻操作之间的间隔完全一致或呈等差数列。
2. **内容模式僵化**：每次生成的帖子正文结构、用词、标点几乎不变。
3. **操作序列机械**：例如总是“打开页面 -> 点击输入框 -> 粘贴全文 -> 瞬间点击发送”，缺少随机性的停顿和额外的浏览动作。
4. **忽略环境反馈**：对验证码、限流提示、页面加载变慢等情况没有应对逻辑，直接报错或持续重试。

这些问题在技术层面都对应着调度策略和动作生成的改进点。

## 做法与步骤

### 1. 分析人工发帖的时序特征

先用 OpenClaw 自带的回放录像和日志，记录下自己手动完成一次发帖的所有时间戳：浏览器打开到页面渲染完成、聚焦输入框、真正开始输入、修改文字、滚动检查、点击发布等。统计这些间隔的分布，发现它大致符合对数正态分布或带抖动的泊松过程，而非均匀分布。

### 2. 实现带抖动的随机延迟生成器

把固定 `sleep(3)` 替换为可控的随机延迟函数。我选择了一个分段策略：

- 页面加载后到首次输入：`gamma(alpha=2, beta=1.5)` 生成 1~6 秒的延迟，模拟阅读内容。
- 输入过程中的停顿：在长文本输入时，每 10~20 个字符后插入 0.2~0.8 秒的暂停，模拟打字节奏。
- 点击发送前：统一加入 0.5~2 秒的延迟，并随机决定是否先滚动到底部再点击。

实现上，将这些随机生成器封装成一个 `HumanRhythm` 模块，供 Agent 调用。例如：

```python
def human_delay(base: float, jitter: float) -> None:
    time.sleep(max(0, base + random.uniform(-jitter, jitter)))
```

更进一步，可以用指数分布生成间隔，避免均匀分布带来的检测指纹。

### 3. 内容自然化：用 Agent 做同义改写 + 结构微调

OpenClaw 的 Agent 本身支持调用本地 LLM 对草稿做轻微改写（例如替换连接词、调整列表符号、随机增减少量填充词）。我并没有追求语义大变，而是做“格式抖动”：

- 把固定的 `- ` 列表随机变为 `* ` 或 `1. `。
- 在标题后随机添加一个 emoji 或不添加。
- 对于长贴，偶尔在首段后插入一行 `---` 作为分隔。
- 不同平台适配时，保留核心信息，但改变段落长度和语气。

关键是要有随机种子，且种子随 session 变化，避免每次运行产生完全相同的内容。

### 4. 调度策略：编排“人类”的行为序列

不再一成不变地执行“登录→发帖→退出”。而是在两次发帖之间混入一些无副作用的浏览动作，例如：

- 随机访问首页或热门列表，并停留 3~10 秒。
- 偶尔模拟点击“个人中心”再返回。
- 如果检测到平台有弹窗（如公告），先关闭再继续。

这套行为通过 OpenClaw 的 MCP 工具链很容易编排。我把每一步抽象为一个有成功/失败反馈的 Task，并用有限状态机串联，当某个步骤失败时，不会机械重试，而是回退到安全状态（比如关闭标签页并重新登录）。

### 5. 异常熔断与自适应调节

引入一个简单的“压力感知”逻辑：如果短时间内连续遇到 HTTP 429 或验证码，就自动降低后续操作的频率，并将异常情况记录到监控，暂停计划任务。工程上，我做了一个 `RateLimitSensor`，在每次请求后更新滑动窗口内的请求计数，超过阈值就主动插入更长的冷却期。

## 踩坑点

1. **随机延迟的种子可预测**：初始时使用了固定随机种子以便调试，结果部署上去后每个 session 的延迟序列一模一样，很快被平台识别。务必改用 system time + instance id 作为种子。
2. **过度追求“人化”反而降低效率**：有一次在打字模拟中加入了太多停顿，导致单个帖子耗时超过 30 秒，用户体验不好。后来限制总延迟不超过实际打字时间的 1.5 倍。
3. **忽略 session 保持**：每次发帖都重新登录，大量使用新 token，被判定为异常设备切换。改成在 MCP browser session 内保持 cookie 和 local storage，并定期续期。
4. **验证码处理误区**：试图自动识别验证码，但引入了 2captcha 服务的调用延迟和费用，其实大部分社区平台在节奏正常时根本不会弹出验证码。目前策略是遇验证码立即中断本次发帖，标记人工处理，避免陷入打码循环。

## 可复用建议

- **模块化节奏引擎**：将延迟生成、内容变换、行为序列配置化分开，比如用 YAML 定义不同平台的 `rhythm_profile`，方便调参。
- **把“不像机器人”作为可观测指标**：记录每次发帖的成功率、被折叠比例、账号风险分。如果异常，回看 session 录像对比人工操作的时间分布，调整分布参数。
- **利用 OpenClaw 的插件能力**：将 `HumanRhythm` 包装成 Agent 可依赖的 Tool，通过 MCP 接口暴露给自动化 Pipeline，让计划任务调度器和内容生成 Agent 都能复用。
- **灰度测试**：先在低频的小号上运行新节奏配置至少 24 小时，确认账号状态正常后再扩展到主账号。

## 总结

社区自动发帖的目标从来不是替代人，而是把重复劳动自动化，同时保持账号健康和社区信任。节奏控制的核心在于对随机性和反馈的尊重——让机器学会“犹豫”和“放弃”。在 OpenClaw 的 Agent + MCP 体系下，这些策略可以被提炼成可配置、可观测的工程组件，既避免被误识为机器人，也保留了后期持续优化的空间。

最后，真正的社区连接还是需要真实的人在关键时刻介入互动，自动化只应是辅助。
