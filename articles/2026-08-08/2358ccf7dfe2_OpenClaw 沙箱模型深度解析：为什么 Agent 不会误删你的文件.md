## 引言：自动化中的文件安全焦虑

对于经常用 Agent 做文件整理的开发者，最不安的瞬间莫过于看到终端闪过 `rm -rf` 之类的命令。哪怕你只是说“帮我把临时文件清理掉”，一个上下文理解偏差或模型幻觉，就可能让宿主机上的重要目录瞬间消失。在 OpenClaw 的实践中，这种焦虑被一套分层的沙箱安全模型大幅降低。本文将拆解这套模型如何从文件系统层面阻断“误删”，以及在实际工程中如何配置、避坑和复用思路。

## 问题：Agent 删文件的风险从何而来？

Agent 并非故意作恶，风险主要来自两类情况：

1. **指令歧义**：用户说“清空过期的日志”，Agent 可能把系统日志目录也纳入清理范围，而用户并未显式授权。
2. **工具链透明度过高**：许多 MCP 文件工具直接映射宿主文件系统路径，Agent 获得与用户同等的读写权限，一旦错误决策，就没有二次拦截机会。

传统的解决方案是“用户确认弹窗”，但这会打断自动化流程，难以在无人值守场景中落地。因此需要一套更底层、可编程的隔离机制。

## OpenClaw 的沙箱设计：Overlay 层 + 代理文件操作

OpenClaw 对 Agent 的文件访问构建了一个三层模型：

- **只读基础层**：宿主文件系统以只读方式挂载到沙箱的 `/host`，Agent 可读取，无法写入或删除。
- **可写工作层**：基于 OverlayFS 在内存或临时目录中创建的私人文件系统。Agent 的所有写入、修改、删除都发生在这里，对基础层不可见。
- **安全导出层**：如果 Agent 确实需要改变宿主文件，必须通过 `publish` 或 `export` 这类受限工具，经白名单路径检查后，显式地将工作层中的文件复制到宿主目标位置。

MCP 文件操作插件在沙箱内也被替换为代理版本。例如 `deleteFile` 工具的内部实现是检查目标路径是否位于 `/workspace`（工作层），如果指向 `/host` 下的路径，直接抛出“不允许删除受保护文件”的错误。这从代码层面杜绝了误删宿主的可能。

```yaml
# 沙箱配置示例
sandbox:
  type: overlay
  baseDir: /var/sandbox/base          # 只读基础层
  workDir: /tmp/sandbox/work          # 可写 diff 层
  allowedExports:
    - path: /home/user/projects       # 允许导出的白名单
```

Agent 在运行时看到的文件结构类似于：

```
/
├── host/               # 只读挂载的宿主根
├── workspace/          # 可写工作区
└── exports/            # 导出映射点（需白名单）
```

当 Agent 试图“删除 `/host/home/user/important.txt`”时，沙箱只允许删除 `/workspace` 内的文件，宿主文件毫发无损。

## 实践步骤

如果在 OpenClaw 中启用沙箱，通常只需三步：

1. **声明工作区范围**：在 Agent 配置中指定 `workspace` 路径，Agent 的所有文件操作默认作用于此。
2. **配置白名单导出**：仅当结果文件需要写回宿主时，才添加允许导出的目录，且默认不加系统关键路径。
3. **测试回滚**：在沙箱环境中执行一次“危险指令”，观察日志确认拦截成功。

日志中会看到类似“Sandbox blocked delete on /host/etc/config – operation allowed only within /workspace”的记录，帮助快速定位未经授权的操作。

## 踩坑点：持久化、符号链接与性能

实际使用中常见三个坑：

- **持久化数据的误区**：很多人习惯让 Agent 直接写 `~/Documents`，但在沙箱中若未配置导出，这些文件只在工作层存活，Agent 结束后即丢失。正确做法是：要么将目录加入白名单导出，要么使用 Agent 的 `session://` 持久化存储接口，它独立于宿主文件结构，由平台管理生命周期。
- **符号链接逃逸**：沙箱必须启用 `nosymfollow` 或对 `readlink` 结果进行路径规范化，防止 Agent 通过软链接跳转到宿主的未授权路径。早期版本曾出现通过 `ln -s /etc/passwd workspace/link` 然后删除 `link`，实际却操作了 `/etc/passwd` 的情况，OpenClaw 在后续更新中加入了内核级符号链接锁定解决此问题。
- **OverlayFS 的性能开销**：大量小文件的频繁修改可能导致 diff 目录膨胀，建议定期清理工作层或设置大小上限，并在容器化场景中使用 `tmpfs` 提升 IO 速度。

## 可复用建议：如何在自己的 Agent 中构建类似安全层

即使不使用 OpenClaw，以下几个原则可以直接应用到你自己的 Agent 项目中：

- **永远不给 Agent 宿主真实路径的写权限**：利用 Docker 的 `--read-only` 加上 `tmpfs` 挂载工作区，或用 `bwrap` 创建无特权沙箱。
- **对 MCP 工具进行权限封装**：如果开发自定义 MCP 服务，文件写入工具应先解析符号链接，再检查路径前缀是否属于允许的目录白名单，拒绝则返回结构化错误而非实际执行。
- **日志与回放审计**：记录所有文件的创建、修改、删除操作及其运行时的环境，便于事后验证和复盘。OpenClaw 提供的操作日志可直接用于回放，快速排查意图是否被正确执行。
- **半自动化控制关键操作**：对 `delete`、`overwrite` 等操作开启“提案-批准”模式，Agent 生成操作清单，由用户一次性确认，而非每次中断。

## 总结

OpenClaw 的沙箱模型并非黑魔法，而是将早已成熟的 Linux 容器技术与 Agent 工具链深度结合。它让 Agent 在“能读不能乱写”的环境中工作，即使出现幻觉级别的误判，也不会突破文件系统隔离。对于追求自动化的团队，这层保护可以让无人值守任务更可靠，也降低了代码审查的心理成本。

安全没有绝对，但通过分层隔离、代理拦截和导出白名单，你至少可以把“误删文件”这种噩梦从日常运维清单中划掉。
