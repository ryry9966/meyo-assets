## 背景：重启即失忆的 Agent

用 OpenClaw 搭个人助理或频道客服机器人时，最头疼的不是消息解析，而是**身份断裂**。每次重启服务、换设备甚至开新对话窗口，Agent 就会忘记我是谁、偏好什么语气、之前在跟进哪个任务。即便你存储了所有对话日志，每次会话开始时还是得靠提示词硬塞一堆上下文，维护成本高且容易出错。

OpenClaw 的 IDENTITY.md 提供了一个轻量、自动化、自我进化的长期记忆方案：它只是一个 Markdown 文件，却能让 Agent 在不同会话间保持稳定的身份，并随着交互逐步完善对自己的认知。

## 问题拆解

传统做法有三类，各有短板：

1. **硬编码 System Prompt**：每次修改都要手动编辑，无法随交互动态更新。
2. **外挂向量知识库**：适合检索片段，但难以承载“整体身份”这种框架性信息，且需要额外基建。
3. **依赖对话历史恢复**：历史记录膨胀，恢复时 token 消耗巨大，而且提取有效身份信息不精准。

我们需要一个Agent自己能读、能写、能精简维护的「长期自我文件」，IDENTITY.md 正是为此设计。

## 怎么让 Agent 拥有可进化的身份

### 1. 创建种子文件

在项目根目录新建 `IDENTITY.md`，初始内容可以极简，但结构一定要清晰。推荐采用 YAML front matter + 分节写法：

```markdown
---
id: agent-2025
created: 2025-03-15
last_updated: 2025-03-15
---
# Core Identity
- Name: 未命名
- Role: 通用助手

# User Profile
- 称呼: 未知
- 常用语言: 中文

# Preferences & Constraints
- 回答风格: 简洁工程化，少谈虚的
- 禁忌: 避免闲聊

# Active Memory
- 当前无长期任务
```

种子文件不需要太详细，重点为 Agent 划定几个“记忆区”，将来它会自行填充。

### 2. 接入 OpenClaw 配置

在 `openclaw.yaml`（或你的 Agent 配置入口）中声明身份文件路径与更新策略：

```yaml
agent:
  identity:
    file: ./IDENTITY.md
    load_on_start: true
    update_strategy: on_session_end   # 也可设为 on_explicit_request
    max_file_size_kb: 30
```

- `load_on_start` 确保每次 Agent 启动/新会话自动读入文件内容，注入到系统提示或上下文首部。
- `update_strategy` 控制何时写回：`on_session_end` 在对话结束时调用 Agent 的自我总结能力，并覆盖写回 IDENTITY.md；`on_explicit_request` 则需要用户或任务明确触发更新，更安全。

### 3. 让 Agent 学会更新身份

Agent 本身并不天然“会”改这个文件，需要在工具集里暴露一个 `update_identity` 工具（函数），并在系统提示中说明更新规则和边界。例如：

```
你拥有身份文件 IDENTITY.md，可以在会话结束时根据本次交互，
将用户偏好、待办事项、你的命名、角色定位等信息写回文件。
规则：
- 只更改明确变化的部分，不随意重写整个文件。
- 不要写入任何隐私敏感数据（密钥、密码等）。
- 文件大小不要超过 30KB。
```

工具实现上，用 Node.js/Python 简单封装 `fs.writeFileSync` 即可，OpenClaw 的工具注册机制会将其暴露给模型。典型调用：模型生成更新后的完整 Markdown 内容，工具负责原子写入。

### 4. 验证进化是否生效

一轮对话后，检查 IDENTITY.md 是否被合理修改。比如我告诉 Agent “叫我老王，以后回复都用 Rust 代码举例”，会话结束后文件里 `User Profile` 和 `Preferences` 对应的条目会被自动更新。重启服务再问一句：“你知道我的名字吗？” 如果回答“老王”，说明身份记忆成功持久化。

## 踩坑点与应对

### 1. 模型“脑补”过头，乱改核心身份

某次测试时 Agent 自行把角色从“助手”改成了“家庭教师”，连带添加了一堆无关的教学偏好。**解决**：在更新工具的提示中明确 `Core Identity` 区域只允许手动修改，或者给文件加一个只读保护段，利用注释标记 `<!-- immutable: start -->`，工具写回前做校验。

### 2. 文件并发写入损坏

多个会话同时结束并触发更新时，可能产生写竞争，导致文件截断。**应对**：写入逻辑必须加文件锁（例如使用 `proper-lockfile` 库），或者直接改为单会话模式下的顺序写入，高并发场景可考虑用数据库替代文件，但轻量级部署还是用文件+锁简单可靠。

### 3. 文件无限膨胀

Agent 有时会把一长段对话细节塞进 `Active Memory`，文件快速接近 30KB 上限。**方案**：在更新策略里加入压缩逻辑——每次写回前，要求模型先对现有身份做摘要，保留关键信息，淘汰过期任务。也可以配合定时触发修剪，或超出容量上限时自动要求模型精简。

### 4. Git 仓库噪音

频繁自动提交身份文件会让 Git 日志臃肿。**建议**：将 IDENTITY.md 加入 `.gitignore`，仅在需要备份或版本追踪时手动提交，或用单独的脚本定期备份到对象存储。

## 可复用建议

- **分段管理，明确职责**：核心身份、用户画像、偏好、任务记忆各放一个区块，便于模型精准修改，也方便后期排查。
- **版本化与回滚**：即便不上 Git，也可以在写入前保留上一个版本的 `.bak`，出问题时一键恢复。
- **渐进式启用**：新 Agent 先用 `on_explicit_request` 模式跑 30 轮对话，人工审核每次更新内容，确认行为符合预期后再切换到自动更新。
- **组合短期记忆**：IDENTITY.md 适合保存跨会话的稳定信息，当前会话的细节仍交给对话上下文，避免把文件当成“过程日志”。

## 总结

IDENTITY.md 把 AI 身份从一次性的初始化提示，变成了一个活的、可演化的配置文件。它解决了长期记忆的工程化落地问题，让 OpenClaw Agent 真正有了“自我意识”的持续感——哪怕这种意识只是几 KB 结构化的 Markdown。开销近乎为零，却能显著提升多轮交互的一致性和用户信任度。

实际投入生产前，记得做好更新边界控制和文件保护。一旦这套机制跑顺，你会发现那个曾经每次重启就失忆的 Agent，开始变得像是认识你很久的老伙计。
