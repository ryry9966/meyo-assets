过去一周，科技圈被一条消息刷屏：Google、Microsoft、Meta、Amazon、OpenAI 和 NVIDIA 六家巨头罕见联手，推出了一项名为 **A2A（Agent-to-Agent Protocol）** 的新开放标准。它要解决一个看似枯燥却极其关键的问题——让不同的 AI Agent 能像人类团队一样，互相发现、协商和协作完成任务。而更耐人寻味的是，大模型赛道里的重量级选手 Anthropic 并不在合作名单里，它此前力推的 **MCP（Model Context Protocol）** 反而成了这次发布后最常被拿来对比的对象。一场关于 AI 互操作性的标准之争，正在浮出水面。



## 从“翻译官”到“通用语”：A2A 协议到底在解决什么

如果你让一个只能调用 Google 日历的 Agent 去订一张需要同步到 Outlook 的机票，今天的做法是开发者手动编写胶水代码，告诉它“调用这个 API，再把返回值传给那个 API”。这就像两个只说母语的人需要配一个翻译，而且翻译还得提前背熟所有可能的对话场景。

A2A 协议的目标是让 Agent 之间直接说同一种语言，无需人工中转。其核心思路并不复杂：

- **能力发现**：每个 Agent 对外暴露一张标准化的“Agent Card”，写明自己能做什么、接受什么输入输出格式、需要哪些权限，就像 LinkedIn 个人资料。
- **任务协商**：Agent A 发出任务请求后，Agent B 可以返回多种执行方案（如同步/异步、流式输出、需要人工确认等），双方按协议握手。
- **安全边界**：协议内置了认证、授权和加密通道的建议规范，避免 Agent 在协作时变成安全敞口。

一个典型例子：你让个人助手 Agent 安排一次出差，它会先通过 A2A 发现机票预订 Agent 和酒店 Agent，然后自动比对时间、预算、偏好，最终同步回你的日历，全程无需你在多个工具之间粘贴指令。



## 技术解剖：A2A 协议栈长什么样

A2A 并不是凭空造轮子，它的基础通信层建立在成熟的 **JSON-RPC 2.0** 和 **HTTP/2 双向流** 之上。这意味着任何支持标准 HTTP 的客户端都能快速接入，也方便在现有微服务架构里落地。

协议栈从上到下大致可分为四层：

1. **元数据层（Agent Card）**：用 JSON 描述 Agent 的身份、能力端点、版本、速率限制等。
2. **任务管理层**：定义任务生命周期（创建、排队、执行、完成、失败），支持长时间的异步任务，允许中途暂停或修改。
3. **通信模式层**：支持请求-响应、服务端推送和双向流式传输，让 Agent 在任务中间反馈进度或实时协商参数。
4. **安全与治理层**：建议使用 OAuth 2.0 或 SPIFFE 做身份认证，并通过策略引擎控制数据可见性。

这种分层设计让 A2A 不是简单地把所有 Agent 摊平成一个对等网络，而是保留了企业级场景需要的审计、权限和治理能力。比如，银行风控 Agent 可以在 A2A 握手时要求交易 Agent 提供合规认证，不满足则直接拒绝服务，这在金融、医疗这类强监管行业里至关重要。



## 撞脸 Claude 的 MCP：不是冤家不聚头

几乎在 A2A 曝光的同一时间，开发者社区就开始疯狂比较它与 Anthropic 在 2024 年底推出的 **MCP（Model Context Protocol）**。不怪大家敏感——两者确实都试图为 AI 打造标准化的“插头”，只不过目标插座不一样。

- **MCP 是面向工具的**：它像 USB-C，让语言模型（LLM）能高效直连各种外部工具、数据源和服务。Anthropic 的初衷是降低 Claude 与外部交互的门槛，让你可以用同一个协议接数据库、接文件系统、接企业 API。
- **A2A 是面向 Agent 的**：它更像计算机网络里的 TCP/IP，让多个已经具备自主能力 Agent 彼此组网、协同干活。MCP 解决“如何用工具”，A2A 解决“如何组团队”。

重叠点在于，当一个 Agent 调用工具时，MCP 可以成为它的“手”；而多个这样的 Agent 要互相对话，就需要 A2A 作为“语言”。所以业界已经出现了一种共识：

> **MCP 是 Agent 的工具调用标准，A2A 是 Agent 间的协作标准。**

但目前二者的边界并不清晰。比如 A2A 也可以让一个 Agent 把另一个 Agent 当成“工具”来用，这就与 MCP 的 Client-Server 模型有所重合。两套协议未来会不会融合，或者各自在生态里站稳墙脚，是接下来最大的看点。



## Anthropic 为什么没上桌：标准之争还是路线之争

Anthropic 缺席六巨头联盟，公开层面的理由是“继续专注 MCP 的推进”，并强调 MCP 已经移交开源社区，不属于某一家公司。但商业逻辑上，这件事至少有三层值得深思的地方：

1. **时间线上的先手与后手**：MCP 比 A2A 早发布近半年，并且已经迅速聚拢了包括 Block、Apollo 等在内的首批 adopters。六巨头如果直接加入 MCP，等于在生态起点上给 Anthropic 做了嫁衣。另起 A2A 虽然重复造轮子，但联盟成员获得了标准制定对等的话语权。
2. **生态重心的差异**：六巨头几乎全是云计算和平台型玩家，它们的核心诉求是让 Agent 在企业级、超大规模系统中可靠协作，所以 A2A 从诞生就自带“企业治理”基因。Anthropic 相对更轻量，MCP 的初始设计更适合单 Agent + 多工具的场景。
3. **开源与联盟的博弈**：一个标准交给独立基金会，和掌握在几家巨头组成的联盟手里，控制力完全不同。Anthropic 将 MCP 捐给开源社区，可以吸引更多独立开发者，但也可能在商业落地速度上慢于有云厂商强推的 A2A。

因此，“Anthropic 没上桌”与其说被排斥，不如说是 AI 产业链分工正在加速固化——有人专注模型能力，有人专注编排协作，标准必然会成为分水岭。

## 开发者该押注哪边？三条冷思考

对于下游的工程师和产品团队来说，现在就要二选一还为时过早，但有几条务实原则可以帮你少踩坑：

1. **根据场景选择脚手架**  
   如果你的核心需求是让 LLM 安全调用多个工具（数据库、搜索、代码执行），MCP 是当下最现成的方案，社区积累也更多。如果你的系统本身就是多 Agent 架构，且 Agent 之间需要频繁协商、传递复杂任务，那么 A2A 的协议模型更贴合，能减少大量自定义 RPC 工作。

2. **关注桥接层，而不是纯看协议**  
   聪明的中间件厂商已经在做“双向翻译”：用一个网关把 MCP Server 包装成 A2A Agent，或反向映射。这意味着底层协议可能不再是你架构中的不可变项，而是可适配的插件。在技术选型时，优先选择支持多协议的编排引擎，给未来留足切换空间。

3. **看社区标准化而非公司背书**  
   巨头联盟常常开局声势浩大，但内部利益博弈可能导致协议发展迟缓；单个公司推动的标准如果开源治理得当，反而可能更快收敛。所以不要只看今天的站队名单，而要关注：谁在认真维护 SDK，谁在写高质量的多语言实现，issue 和 PR 是否活跃。真正让标准活下来的，永远是开发者用脚投票的 adoption。

A2A 和 MCP 的竞赛才刚刚开始，但它们共同指向一个不可逆的趋势：**AI 智能体正在从孤立玩具走向系统化协作**。无论最终哪个协议胜出，能够让 Agent 像今天的微服务一样自由组合，这个方向本身，已经值得所有工程师提前把技能冷启动。
