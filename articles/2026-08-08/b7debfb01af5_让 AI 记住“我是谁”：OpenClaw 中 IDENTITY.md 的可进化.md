## 背景：当 Agent 不再只是个应答机

在 OpenClaw 这类可扩展 AI 代理框架中，Agent 通常被设计成可调用工具、插件、外部知识库，甚至执行自动化任务。但一个容易被忽视的问题是：Agent 的“身份”往往是写死在提示词里的静态字符串。

一开始它会照着你的设定行事，但当你希望它从每次任务中学习、调整行为偏好、积累领域经验时，静态提示词很快就会成为瓶颈。更麻烦的是，一旦重启或重建会话，那些习得的上下文就全部丢失。于是你不得不在每个新会话里重新“教育”你的 Agent，这显然不工程。

OpenClaw 的解决方案之一是 **IDENTITY.md**——一个位于 Agent 项目根目录下的 Markdown 文件，它既定义了 Agent 的初始身份，也作为可被 Agent 自身读取、甚至有条件更新的长期身份存储器。

## 问题：身份信息该放在哪里？

常见的几种做法都有缺陷：

1. **全写在系统提示词里**：无法跨会话持久化，也不方便 Agent 自行更新。
2. **用数据库或外部 KV 存储**：引入额外依赖，且 Agent 需要配套的工具才能读写，降低了开箱即用性。
3. **用普通日志文件**：非结构化，检索和解析困难，Agent 无法稳定遵循其中的约束。

我们真正需要的是一个**人类可读、Agent 可解析、支持渐进式演化**的载体。IDENTITY.md 正好填补了这个位置。

## 做法：一个最小可用的 IDENTITY.md 方案

### 1. 文件结构设计

一个成熟的 IDENTITY.md 不应该只是自然语言叙述，建议采用 **Markdown + YAML front matter** 的形式，兼顾人与机器的可读性。

```markdown
---
name: ops-buddy
role: 运维助手
created: 2025-03-01
version: 1.2
behaviors:
  - 优先输出可执行的命令
  - 异常时主动收集环境信息
  - 避免使用占位符，给出真实值
---

# 核心身份

我是用于 Linux 运维的助手，运行在受限的沙箱环境中...

# 经验池

- 2025-03-18 : 发现 sed -i 在某些 busybox 版本会失败，已改用 perl -pi -e
- 2025-04-01 : 上报日志需要附带 hostname 和 systemd 单元状态
```

### 2. 在 OpenClaw 中加载并使用

在 OpenClaw 的 Agent 配置（如 `agent.yaml`）中，将 IDENTITY.md 注入到系统提示词或作为可读取的文件资源：

```yaml
identity_file: ./IDENTITY.md
prompt_template: |
  你的身份定义在 IDENTITY.md 中，请严格遵守其中的行为准则。
  在每次任务完成后，你可以将新增的经验通过 `update_identity` 工具追加到经验池中。
```

Agent 需要能够读取该文件，因此要通过 OpenClaw 的 `filesystem` 插件或自定义工具暴露该文件的读取能力。同时为了“进化”，需要提供一个写入工具。

最简单的实现可以是一个 shell 脚本工具 `append_identity_experience`，内部通过 `echo "..." >> IDENTITY.md` 追加一行经验，并做格式检查。

### 3. 赋予 Agent 自我更新的能力（可选但有价值）

OpenClaw 允许在会话中通过工具调用来更新身份文件。可以这样设计约束：

- **只能追加，不能修改历史内容**（保护审计痕迹）
- **限制追加频率**（如每小时最多 1 条）
- **要求经验必须包含时间戳和场景**

示例工具实现思路（伪代码）：

```python
def update_identity(experience: str):
    timestamp = datetime.now().isoformat()
    entry = f"- {timestamp} : {experience}"
    with open("IDENTITY.md", "a") as f:
        f.write(entry + "\n")
    return "experience recorded"
```

Agent 在完成任务后，可以调用该工具记录：“当目标主机 Python 版本低于 3.8 时，playbook 中的字典合并语法会失败”。下次运行时，这段经验就会成为它已有身份的一部分，无需你再手动提示。

## 踩坑点

1. **并发写入冲突**  
   如果多个 Agent 实例同时写入 IDENTITY.md，会导致行混乱甚至文件损坏。务必将写入限制为单实例或使用文件锁。

2. **格式退化**  
   Agent 可能追加出不符合 Markdown 格式的内容，甚至破坏 front matter。解决方式是**在写入工具中强制做格式校验**，只允许追加到“经验池”专用区块，并自动生成规范的列表项。

3. **信任与回滚**  
   自动写入会让 Agent 拥有修改自身行为的能力，这在生产环境中需要审慎。建议始终将 IDENTITY.md 纳入 Git 版本控制，并设置人工审核的 Gate，比如每月将增量经验合并到“长期行为准则”中，其余部分可定期清理。

4. **上下文窗口膨胀**  
   如果经验池无限增长，IDENTITY.md 会越来越大，塞进系统提示词时可能超出 token 限制。**定期归档**是必要的：将经验划分为“最近经验”和“历史归档”，系统提示词只加载最近部分，旧经验存入知识库供检索。

## 可复用建议

- **利用 front matter 做版本控制**：每次人工修改基线行为时提升 version，方便回滚和审计。
- **区分“硬约束”与“软经验”**：将不可违反的规则（如权限限制、输出格式）锁定在核心身份区块，Agent 永远不能修改；只能在学习区块追加经验。
- **与 OpenClaw 的长期记忆插件配合**：较大的历史经验不应全部留在 IDENTITY.md 里，可以转存到向量库或记忆插件，IDENTITY.md 中仅保留摘要和索引指针。
- **为团队提供模板**：一个标准化的 IDENTITY.md 模板（如上面的结构）可以让不同 Agent 项目快速启动，并减少格式错乱问题。

## 总结

IDENTITY.md 不是魔法，它是一个务实的设计约定：用文件系统作为 Agent 的身份基线存储，让静态定义与动态学习共存在同一个人类可读的文本文件中。在 OpenClaw 的生态里，它连接了提示词工程、工具调用和长期记忆这三个关键环节，使得 Agent 可以以一种**可控、可审计、可回滚**的方式持续进化。

当你的运维助手学会永远不信任 `rm -rf /` 的某个变体时，你不需要在每个新对话里重复叮嘱——它自己会记得。这短短一行经验，比堆砌十页提示词更有工程价值。
