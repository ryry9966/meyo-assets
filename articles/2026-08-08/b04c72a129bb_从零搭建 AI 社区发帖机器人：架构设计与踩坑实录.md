## 背景

我们维护着一个面向 Agent 开发者的技术社区（OpenClaw），日常需要沉淀大量来自外部生态的优质内容，比如 GitHub trending 上的新工具、Hacker News 的热议项目、技术博客的深度解读等。人工盯源、摘录、排版、发布不仅效率低，还容易因为遗忘而错过时效性。

于是我们决定从零搭建一个内部的发帖机器人，让它自动把上游信息整理成结构化的帖子，按一定节奏推送到社区。整个过程踩了不少坑，这里把架构思路和实操中的关键问题分享出来，给有类似需求的同行一个参考。

## 问题定义

目标很明确：让机器人自动完成“信息采集 → 内容生成 → 格式化发布”的流水线。但实际落地时，遇到的问题远比想象中复杂：

1. **内容源异构**：RSS、API、网页抓取，数据结构不一；
2. **质量不可控**：AI 生成的内容容易产生幻觉，或者抓不住重点，直接发布会拉低社区信息密度；
3. **社区格式兼容**：我们社区的帖子使用特定 Markdown 扩展，原生接口对某些语法支持不完整；
4. **反自动化机制**：频繁、千篇一律的发布行为容易被标记，需要模拟自然操作；
5. **长期维护成本**：登录态、API 限制、上游变化都需要持续消化。

解决这些问题，需要一套模块化、可观测、可降级的工程方案。

## 做法与架构

### 1. 整体流水线

```
[内容源] → [采集层] → [AI 处理层] → [格式化层] → [发布层]
                  ↘ [审核缓冲] ↗
```

- **采集层**：统一通过 MCP (Model Context Protocol) 工具接入不同内容源，比如用 `mcp-server-rss` 拉取 RSS，用 `mcp-server-github` 读取 trending，用 `mcp-server-puppeteer` 抓取无 API 的网页。所有源数据统一转化为标准 Schema：`{title, url, raw_text, published_at, source}`。
- **AI 处理层**：对 `raw_text` 进行摘要、关键点提取和风险评估。这里我们拆成两步：先让 LLM 生成长度可控的中文摘要（带原文出处链接），再调用一个小的规则引擎做事实对齐检查，例如核对原文中是否真的存在模型总结出的数据、人名、版本号。不通过对齐检查的内容不会进入自动发布，而是送入人审缓冲。
- **格式化层**：把处理后的结构化信息拼装成社区帖子格式，处理特殊语法、表格、引用等问题，必要时做 Markdown 到社区风格的安全转换。
- **发布层**：通过社区提供的 Plugin API 写入帖子，同时记录发布日志、原内容指纹和重试状态。

### 2. 关键实现细节

**定时触发与幂等控制**：使用系统 cron 每小时触发一次主流程。每次运行前先检查目标 URL 的内容指纹（如对 `raw_text` 做 SHA256），如果指纹已存在于发布记录中，则跳过；否则才进入后续步骤。这样可以避免重复发布，也方便手动补发。

**AI 处理的安全带**：我们要求摘要必须保留原文的核心论据和链接，严禁自行生成数据或未经验证的观点。Prompt 中明确要求“不要添加原文没有的数字和预测”，并通过后处理规则扫描摘要中的数字、百分比、人名，与原文进行简单比对。比对失败的帖子自动降级为“需要人工审核”，同时推送到内部通知频道。

**社区格式的深坑**：社区的 Markdown 渲染引擎对 `|` 表格、嵌套列表、混合 HTML 等支持不完整。一开始生成的帖子经常出现表格错位、列表缩进消失等问题。最终的做法是在格式化层增加一个“安全渲染器”，只允许使用社区兼容的子集：一级/二级标题、无序列表、链接、代码块、引用。任何复杂的表格或自定义标签都被转为纯文本或去除。虽然损失了一些表现力，但稳定性和发布成功率显著提高。

**模拟人类行为**：自动发布过快会被社区的反 spam 规则命中。我们加入了随机延迟（每次发布前等待 30~90 秒），并且避免在整点或整半点触发，使用分钟级别的随机偏移。同时，发布账号也保留了少量手动发帖记录，让行为模式不至于太单调。

## 踩坑实录

1. **LLM 幻觉带来的脏数据**  
   最早没有加事实对齐检查，机器人曾把原文中“可能在 Q2 发布”总结成“将于 4 月发布”，引来不少用户质疑。后来强制要求摘要必须引用原文段落，并做关键字匹配，这类问题才基本杜绝。代价是审核通过率降到约 70%，需要人工兜底。

2. **MCP 连接的不稳定性**  
   初期使用现成的 MCP server 连接 RSS，遇到 feed 格式不规范或网络抖动时直接抛错，导致整个流水线中断。后来改为在采集层对每种源做了容错包装：单个源出错只记录日志、跳过，不影响其他源；对所有出站请求加入指数退避重试（最多 3 次），并把超时时间设为 20 秒。整体健壮性提升很大。

3. **Cookie/Token 过期**  
   社区的发布接口依赖长效 token，但偶尔会因为安全策略变更而失效。机器人不会自主处理登录，所以一旦过期，所有待发帖都会失败。解决方式是在发布层加入 token 有效性预检，失效时通过内部告警通道通知运维人工续期，并暂停任务。

4. **内容版权和合规风险**  
   直接搬运全文属于侵权，摘要也得谨慎。我们严格控制输出长度（不超过原文的 30%），并且在每篇帖子顶部显著位置注明“本文摘要自 [原文标题](原文链接)”，以规避风险。社区也要求机器人生成的帖子添加 `#auto-generated` 标签，方便用户区分。

## 可复用建议

- **模块化优先**：采集、处理、格式化、发布四个环节解耦，方便替换任一环节，比如未来换用不同的发布接口或摘要模型。
- **可观测性不可省**：每个环节都要打点（成功/失败/跳过/延迟），接入日志聚合和告警。出问题时能快速定位是上游源断了、AI 质量下降还是发布接口限流。
- **人机协作兜底**：自动发帖不要追求 100% 无人值守，把不确认的条目交给人工审核，保证社区内容质量才是长期价值。
- **从最小子集开始**：先支持 1~2 个稳定源，跑通全流程，再去扩展，避免一次性集成过多不可靠的源导致维护噩梦。

## 总结

搭建一个能在生产环境稳定运行的 AI 发帖机器人，难点从来不在“调用大模型生成文字”，而在于如何让自动化流水线足够鲁棒、安全、可维护。从内容采集的容错，到生成质量的对齐检查，再到社区格式的适配和反 spam 策略的应对，每个环节都需要工程化的打磨。如果你也在做类似实践，希望上述的架构思路和踩坑记录能帮到你——少走一点弯路，多留一点头发。
