## 1. 背景：Agent 的“想不起来”问题

在基于 OpenClaw 的 Agent 编排中，我们逐渐把短期记忆做成了 MCP 服务，让 Agent 自己调工具存下对话摘要、代码片段、配置变更记录。这么做之后，确实延长了任务的记忆窗口，但紧接着遇到一个新问题——recall 效果不稳定。

记忆工具的核心只有两步：store 写入，recall 召回。我们最初的实现直接挂了一个向量库，单纯用 embedding 做语义搜索。名字听着很合理，实际一跑，Agent 却经常搜不出上次改过的那段异常栈，或者把毫不相关的日志捞了出来。于是我们回过头，把全文搜索也补了进去，做了一轮工程对比。

这篇文章记录当时的设计、测试方式和踩到的坑，给同样在折腾 memory 的 OpenClaw 社区提供一些可复现的思路。

## 2. 问题定义：什么时候该用哪种搜索

我们抽象出两类典型的记忆查询：

- **精确检索**：比如“上周三凌晨的 OutOfMemoryError 堆栈”“config.py 中 timeout 参数的值”。这些查询关键词明确，甚至包含唯一标识符。
- **模糊回忆**：比如“之前讨论过的那次支付超时问题”“和数据库连接池相关的配置调整”。表达比较口语化，关键词不一定精准。

两种情况的预期索引方式完全不同。进一步，我们的记忆单元大多是 200–800 字的短文本，包含中文、英文、片段代码。直接在工程线上盲目坚持一种策略，召回率和延迟都要吃亏。

## 3. 实现做法与测试对比

### 3.1 记忆 MCP 服务设计

我们基于 Python 写了一个 MCP 服务器，暴露两个工具：`memory_store` 和 `memory_recall`。`memory_recall` 接受一个 `query` 和一个 `mode` 参数（`semantic` / `fulltext` / `hybrid`）。后端同时维护：

- **Chroma** 向量存储，使用 `text-embedding-3-small` 生成 1536 维向量，索引全部记忆。
- **SQLite FTS5** 全文索引，搭配 jieba 分词和自定义 tokenizer，处理中英混合内容。

OpenClaw 通过 MCP 客户端接入这个服务，Agent 在需要回溯信息时按策略调用相应模式。初期我们手工写了 80 多条测试记忆，涵盖异常日志、对话总结、配置片段。然后构造 30 个查询，逐个评估 Top-5 命中率和 MRR。

### 3.2 核心发现

- **精确查询**：FTS5 明显胜出，尤其对错误码、IP、文件名这类 token。语义搜索经常把“ConnectionTimeout: 5000ms”匹配到“连接超时说明文档”，召回内容过于发散。
- **概括性查询**：语义搜索占优。例如“支付环节的超时处理”，向量检索能把相关的日志、总结都找出来，而全文搜索如果记忆中用的是“订单超时”就丢了不少。
- **中英混合代码片段**：两者都不理想。全文分词切碎代码；语义搜索受限于模型对代码的嵌入质量，非英文代码表现尤其差。

最后我们采用带权重的线性融合 hybrid 模式，初步对精确查询给 FTS5 更高权重，模糊查询则语义优先。简单调整后，MRR 从纯语义的 0.42 提升到 0.61，基本达到可用线。

## 4. 踩坑记录

### 4.1 语义搜索的暗坑

- **短查询漂移**：查询只有两三个词时，cosine 相似度分布平坦，噪声记忆容易挤进 Top-N。需要设最小相似度阈值，但阈值依赖数据分布，得靠可视化调。
- **长文本截断**：模型输入 token 限制常被忽略。我们把记忆文档统一裁剪到 512 token，但嵌入模型最大长度是 8191，裁剪方式（头/尾/中间）对召回影响很大。踩过坑：日志前半部分是时间戳和无用信息，后半核心异常被截掉，语义搜索直接失效。
- **成本**：embedding 费用和向量数据库的扩容成本在记忆量超过 10 万时陡增，需要做冷热分层，把历史记忆做粗索引。

### 4.2 全文搜索的适配

- **中文分词**：jieba 默认词典不适合技术文本，例如“空指针异常”被切开成“空/指针/异常”，影响精确匹配。需要添加技术词典，尤其是错误信息的固定短语。
- **大小写与标点**：SQLite FTS5 默认不处理大小写，但代码片段大小写敏感。我们选择保留大小写并额外建立一个全小写索引列，查询时分别检索后合并。
- **同义词/缩写**：Agent 会用“OOM”但记忆存的是“OutOfMemoryError”。单纯全文无法解决，靠 embedding 补足。

### 4.3 Agent 自主选择模式的风险

一开始我们尝试让 Agent 自己判断用哪个模式，结果经常出现：用户问“上次那个报错”时，Agent 选了全文搜索，返回空结果后自行编造。因此改为先走 hybrid，仍无结果时向用户请求更明确的关键词，而不是默默失败。

## 5. 可复用建议

1. **两层索引优于单一策略**：向量索引负责语义兜底，FTS 保证精确命中，用 RRF（倒数排名融合）比权重调参更稳定，尤其避免了向量距离和 BM25 分数的量纲差异。
2. **记忆分段策略**：长日志存储前先用固定 prompt 让轻量 LLM 提取摘要，将摘要与原始内容分开索引。摘要走语义搜索，原始内容关键词走全文搜索。
3. **参数化工具接口**：在 MCP 工具中保留 `top_k`、`similarity_threshold`、`hybrid_alpha` 等参数，方便根据不同 Agent 场景调优，而不是写死在服务里。
4. **监控召回空洞**：定期抽取线上查询日志，人工标注相关记忆，计算召回率。这是唯一能发现模型老化、分词失效的方法。

## 6. 总结

语义搜索和全文搜索在 AI 助手的 memory recall 里不是替代关系，而是互补。工程上最扎实的做法是同时维护两类索引，通过融合排序输出。具体到 OpenClaw 体系，把 memory 搜索封装成可切换模式的 MCP 工具，让上游 Agent 可以按需调用，同时内置兜底和反馈闭环，才能让记忆召回真正可靠。

如果你的记忆库还不到千条，先做全文搜索就能解决大部分问题；一旦场景扩展到多轮对话、多模态日志，就值得尽早把混合检索的基础设施搭起来。
