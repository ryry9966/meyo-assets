## 背景：社区分享习惯正在制造信息泄露盲区

OpenClaw 这类 Agent 平台的一大优势是“可复用的工作流市场”。开发者把打磨好的流程、提示词、MCP 插件配置分享到社区，其他人一键复制即可投产。这个闭环效率极高，但安全的坑也随之而来：**多数“开箱即用”的模板分享，并不具备信息隔离的意识**。

我近期复盘了多个在社区公开的 Agent 工作流配置，发现三类高频泄露点：

1. **硬编码的密钥与内部域名**：你调试时的 dev 环境地址、内网 API 端点、测试用的 API Key，留在提示词或 MCP 配置里，导出时直接带了出去。
2. **工作流步骤暴露组织内部流程**：某个看起来人畜无害的“审批提醒 Bot”，节点名称就是内部项目代号、审批角色真实姓名，甚至透出了某一级部门的组织架构。
3. **Agent 在社区自动应答时“引经据典”**：开启了社区自动回复的 Bot，调用内部知识库后，把只该对内输出的 SOP 片段、客户名字、订单尾号原样贴到了公共帖子回复中。

这不是理论推演，而是反复出现的工程事故。OpenClaw 的插件化架构与 MCP 协议让信息流动变得更灵活，但**灵活性的背面，是更难追踪的数据流向**。下面给出可落地的防护做法、踩过的坑，以及一套可复用的发布 checklist。

## 问题拆解：泄露的真正路径

表面看是“开发者不小心”，但根因往往在架构层面缺少两样东西：

- **发布态与调试态的边界**：工作流配置里哪些字段属于“开发期变量”，哪些属于“可公开模板变量”，从未被明确定义。
- **Agent 输出缺少上下文感知过滤**：你的 Agent 在内部频道可以自由输出关键数据，但进入社区频道时没有切换输出策略。

具体到 OpenClaw 技术栈，泄露路径常见于：
- 提示词模板中的 example 值（带着真实数据）
- MCP 工具的 `description` 字段透露了内部系统名称
- 工作流日志 / debug 输出被无意复制到社区帖子里
- 社区 Bot 调用内部工具后，工具返回数据直接被 LLM 用于生成回复

## 做法：四层防护，从配置到输出

### 1. 提示词与配置的变量化隔离

不要把任何具体的内部信息写在提示词的静态文本里。最小化原则：**所有运行时特定值，都通过变量注入**。

在 OpenClaw 中，你可以利用：
- 环境变量引用：`{{env.INTERNAL_API_BASE}}` 而不是 `http://192.168.1.100:8080`
- 用户变量（仅内部可见）：在工作流设置中将 `customer_name`、`order_id` 等标记为“不导出”
- 模板变量的 `default` 值使用 `PLACEHOLDER` 或空字符串，而不是你调试时填的测试数据

**额外一步**：创建导出用的“展示提示词”，与生产提示词分支维护。展示版去掉所有上下文示例，仅保留骨架和类型说明。

### 2. 输出门禁：在 Agent 发言前加一层 Post‑processor

对于会进入社区频道的 Agent，在 LLM 生成回复后、真正发出前，插入一个轻量级“输出清洗”步骤。这可以是一个简单的 JS/Python 代码节点，也可以是另一个小模型调用。

清洗规则要覆盖：
- 正则匹配：API Key 格式、内部 IP 段、内部域名后缀（如 `.internal`, `.corp`）
- 结构化数据特征：如 JSON 中包含 `"secret"`, `"token"`, `"password"` 字段
- 项目/客户名称黑名单：用哈希或前缀匹配，避免明文存储黑名单本身

注意：**这一层不应依赖 LLM 判断**，要基于规则和模式匹配。LLM 可能被 prompt injection 绕过敏感词检查。

### 3. MCP 工具权限分级与输出脱敏

MCP 插件最容易忽略安全问题。工具暴露给 Agent 后，Agent 会在推理中自主决定调用哪个工具，并对返回结果直接加工后输出。

安全实践：
- 为社区用的 Agent 单独配置一套 MCP 工具清单，只暴露“安全视图”接口。比如内部 HR 系统 API 有 `/employee/{id}/full` 和 `/employee/{id}/public`，只开放 public 端点。
- 工具 `description` 不要写真实系统名，使用泛化描述：“查询员工公开联系方式”代替“调用 HR‑PROD 系统的 getPublicInfo”。
- 在工具实现层截断敏感字段，而不是依赖 Agent 的自觉。返回 JSON 中甚至不应包含可推断出敏感信息的字段名。

### 4. 共享模板的导出消毒流程

OpenClaw 的模板分享功能，建议走一个固定的“消毒流水线”：

1. 用“导出安全模式”（部分平台已支持）剔除所有标记为 `internal` 的变量值。
2. 手动检查所有节点配置中的默认值、示例数据、错误提示语，去掉任何可能关联到具体业务实体的信息。
3. 检查截图：不要直接截生产环境的日志或调试面板，使用抽象化的示意截图或打码。
4. 让另一个人（而非原始作者）跑一遍导入流程，在隔离的工作区中测试，确认没有残留信息。

**踩坑点**：很多人以为只要把 API Key 删掉就安全了。但我们遇到过，模板里的一个“Webhook 回调示例 URL”暴露了内网 Jenkins 地址，攻击者通过这个信息拼接出了未授权接口。**示例数据同样致命**。

## 可复用建议与 checklist

基于这些经验，一个最小安全发布 checklist 如下：

- [ ] 所有密钥、token、密码字段已替换为 `{{env.XXX}}` 或空占位符
- [ ] 所有 URL/域名不包含内部资产信息
- [ ] 提示词示例数据已替换为虚构数据（如 `John Doe`, `Example Corp`）
- [ ] MCP 工具描述和返回字段名不含内部系统/组织名
- [ ] 导出模板经第二人在隔离环境测试通过
- [ ] 社区 Agent 的输出已配置规则型脱敏节点
- [ ] 分享的截图/日志片段已脱敏或使用示意素材
- [ ] 工作流名称、节点名称、描述不含内部代号或人名

**组织层面**：可以考虑设置一个内部“社区发布负责人”，所有分享模板需经其批准，形成习惯闭环。同时定期扫描已发布的历史模板，因为新的漏洞发现后，旧模板可能成为攻击面。

## 总结

Agent 安全的红线不在“能不能分享”，而在“分享时是否存在自动化手段保证信息隔离”。把脱敏检查完全交给人的自觉性，等于没有安全策略。利用好 OpenClaw 的变量作用域、MCP 工具分层、后处理节点，完全可以在不牺牲分享效率的前提下，避免把内部工作流暴露给整个社区。安全是工程问题，不是喊口号的宣传问题。
