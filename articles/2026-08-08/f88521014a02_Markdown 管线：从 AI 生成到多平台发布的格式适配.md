## 背景：AI 生成内容越多，格式适配越痛

如果你在用 Agent 或 MCP 组合生成长文、技术文档、周报甚至公众号推文，大概率会遇到同一个问题：AI 出来的 Markdown 在本地预览很正常，但一推到不同平台就变得七扭八歪——代码块没有高亮、标题层级错乱、图片断裂、外链被吞。更麻烦的是，很多 AI 模型输出的 Markdown 其实是一种“方言”，带上渲染器特定的扩展语法，或者干脆就在基础语法上不够严谨。

当你的发布目标是 GitHub、知乎、微信公众号、Notion、飞书文档等多个渠道时，这件事就不再是手动改改格式能应付的，必须有一条可复用的 Markdown 处理管线。下面分享一条在 OpenClaw 生态里实际跑通的工程化思路，尽量避开泛泛而谈的“使用 xx 工具”，聚焦于规则选型、管线设计及踩坑经验。

## 问题拆解：多平台差异到底差在哪

实际踩下来，差异主要在四个层面：

1. **基础语法容忍度**  
   - 常见坑：标题 `#` 后面是否必须有空格？列表缩进是 2 空格还是 4 空格？空行是否必须？知乎编辑器对紧挨着的代码块有时会合并；微信公众号编辑器甚至完全不吃 Markdown，需要转成富文本。

2. **扩展语法支持**  
   - 表格：少数平台不支持管道表格，或者对齐语法被忽略。  
   - 脚注：GitHub 支持，知乎、公众号不支持。  
   - 任务列表：部分平台直接渲染成普通无序列表。  
   - LaTeX 公式：GitHub 不原生支持，知乎和某些博客平台支持但分隔符有差异（`$` vs `$$` vs `\(`）。

3. **代码块与高亮**  
   - 语言标识大小写敏感：` ```python` vs ` ```Python` 在少数渲染器中不被识别。  
   - 某些平台会过滤 `<pre>` 或 `<code>` 的属性，导致高亮失效，只能退回无高亮纯文本。

4. **链接与图片**  
   - 微信公众号会替换外链，只允许白名单域名；部分平台要求绝对路径图片，且不允许相对引用。  
   - 图床稳定性与防盗链策略也影响最终成像。

## 管线设计：三层处理，一次输出多份目标格式

我目前用在 OpenClaw 代理工作流里的管线结构如下：

```
AI 原始输出 (Markdown 方言)
    │
    ▼
[规范化层]  基于 CommonMark + 部分 GFM 扩展
    │
    ▼
[通用中间格式]  严格的、无平台特异性的 Markdown
    │
    ▼
[发布适配层]  根据目标平台生成对应版本
    ├─ GitHub (GFM)
    ├─ 公众号 (HTML 富文本)
    ├─ 知乎 (Markdown 受限子集)
    └─ 博客静态站 (Hugo/Hexo 专用)
```

### 第一层：规范化

这一步的目标是把 AI 产物拉回一个可控、确定的标准。CommonMark 是一个很好的强基线，GitHub Flavored Markdown (GFM) 作为增强。规范化规则包括：

- 统一标题 `#` 后加空格。
- 代码块统一为带语言标识的小写名称，并使用围栏式。
- 修复错误的列表缩进（统一用 2 空格缩进，保证与 GFM 兼容）。
- 移除部分模型爱用的 HTML 标签（如 `<center>`、`<font>`），或标准化为可替换的标记。
- 将 LaTeX 公式用统一分隔符包裹，并标注为“公式块”，留到适配层再决定是否渲染。

实现上，我用了一个本地 MCP 工具（基于 markdown-it 和自定义规则），将其包装为 MCP server，OpenClaw 的 Agent 可以直接调用，处理完再走下一步。也可以不用 MCP，直接用 Node 脚本 + unified/remark 系列做 AST 级别的处理，效果更可控。

### 第二层：通用中间格式

处理好后的 Markdown 不再包含任何平台特异性，作为“发布源”。所有后续转换都从这个中间格式派生。这样做的好处是：增加一个新平台，只需增加一个适配脚本，不影响上游。

### 第三层：发布适配

这一层根据目标平台规则生成最终文本：

- **GitHub**：基本可直接使用中间格式，仅需处理相对路径图片 → 绝对路径（利用 GitHub raw URL）。
- **公众号**：需要将 Markdown 转为 HTML 富文本，并遵守微信的外链与图片限制。做法是先用 pandoc 或 markdown-it 转成 HTML，再通过一个后处理脚本处理：外链加 `nofollow`、图片替换为已上传的素材 URL、代码块转为带内联样式的 `<pre>`（因为公众号会删掉 class）。这个环节最脆弱，后面讲踩坑。
- **知乎**：知乎的 Markdown 编辑器对扩展语法容错较低。这里做减法，移除脚注、任务列表转为普通列表、公式转成知乎支持的 `$$` 格式。同时避免使用 HTML 标签，全部用纯 Markdown 表达。
- **静态博客（Hugo）**：需要添加 Front Matter，并将内部链接转为 Hugo shortcode，保持图片路径为站点相对路径。

## 踩坑点总结

1. **公众号代码块样式丢失**  
   微信会过滤 `<code>` 的 class，所以不能依赖 highlight.js 在前端高亮。解决方案是在服务端将代码块转为带内联样式的 `<span>` 实现语法高亮，或者退一步将代码块全部设为黑色背景、浅色文字，牺牲准确性换取可读性。

2. **公式适配的边界情况**  
   中间格式里若混合行内公式和块级公式，转公众号时一般只能全部转成图片（推荐用 MathJax 服务端渲染或 svg）。如果用知乎，需要把 `\(`、`\)` 替换为 `$`，并注意 `$` 符号前后的空格，否则知乎可能不做渲染。

3. **列表嵌套深度**  
   公众号富文本对嵌套列表支持极差，超过 2 层缩进就可能样式崩塌。因此适配层需要检测列表深度，强制将超过 2 层的嵌套展开为段落或使用符号缩进提示。

4. **链接替换逻辑**  
   公众号外链需要替换为“阅读原文”或干脆转成脚注式链接文字，并保留超链接的视觉提示。这个转换一旦自动做，体验很生硬，建议 AI 在生成时就不要依赖外链，而是用括号引用，再由管线决定是否转化为脚注。

## 可复用建议

- **统一使用 CommonMark + 明确扩展子集**。不要试图支持所有 Markdown 语法，先定义“你的管线支持的语法边界”，超出边界的部分在规范化层就发出警告或直接剔除。
- **用 AST 而不是正则处理 Markdown**。remark/unified 生态或 Python 的 mistletoe 都比正则可靠得多。
- **将适配逻辑拆成独立插件**，通过配置文件切换目标平台。如果已经用到 Agent 编排，可把每个适配器封装为 MCP tool，构成一条 tool chain。
- **为 AI 输出加上格式约束 prompt**，比如：严格使用 GFM 语法、禁止 HTML 标签、代码块必须标注语言且用小写、图片使用绝对 URL。这会大幅降低规范化层的工作量。
- **持续集成很重要**。把整个管线跑在 GitHub Actions 里，每次推送内容变更时自动生成各平台版本，再通过 API 或手动复制发布，避免本地手工转换。

## 总结

从 AI 生成到多平台发布，Markdown 格式适配并不是一个技术难点，而是一个工程细节密集的琐碎问题。构建一条规范化 -> 中间格式 -> 多平台适配的管线，本质上是在做“格式契约”的收敛与分发。用 Agent 和 MCP 工具把这条管线串起来之后，发布流程可以从 20 分钟的人工调整降到 1 分钟不到的一键执行，并且格式一致性远高于人工操作。

如果你也在 OpenClaw 生态里做内容自动化，不妨从定义自己的“安全 Markdown 子集”开始，逐步建立适配层。管线的价值不在于炫技，而在于把格式适配这件事从“每次都会踩坑”变成“踩过一次就再也不用管”。
