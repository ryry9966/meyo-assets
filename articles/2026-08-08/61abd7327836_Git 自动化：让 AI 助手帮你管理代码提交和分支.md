## 为什么需要 AI 来管 Git

在本地开发中，开发者的精力消耗不只是写代码。频繁切换分支、撰写有意义的提交信息、遵循团队的分支命名规范，这些重复但是“轻决策”的动作会持续打断心流。尤其在多需求并行的场景下，手动维护分支结构往往会拖慢节奏，有时还会产生错误的合并或混乱的历史记录。

现有的 Git 图形工具和 CLI 别名已经解决了一部分操作效率问题，但在决策层面——例如，这个改动应该切什么分支、提交信息怎么写才符合 Conventional Commits 规范——仍然依赖人的判断。让一个 LLM（大语言模型）代理这些轻量决策，同时通过工具调用真实地去执行 Git 命令，可以把“我决定做什么”和“机器帮我做完”更自然地连接起来。

这篇文章会给出一个可以直接落地的方案：利用具有工具调用能力的 Agent（例如 OpenClaw 或任何支持 MCP 的宿主）连接到一个 Git 操作服务，实现自然语言驱动的工作流，并分享在实际搭建中遇到的坑和可复用的设计思路。

---

## 问题拆解

要把 Git 管理交给 AI 助手，本质上要解决三件事：

1. **安全的命令执行环境**  
   不能让一个幻觉产生的 `git push --force` 进入生产仓库。需要有一层中间的 validation 与权限控制。

2. **上下文感知**  
   助理需要知道当前仓库的分支状态、暂存区内容、最近的提交历史，才能做出合理的分支创建或提交建议。

3. **结构化输出到动作的映射**  
   自然语言指令要能转化为具体的 Git 操作序列，比如“基于 main 切一个 feat/xxx 分支并做一次 WIP 提交”。

工程上，我们选择了 **MCP (Model Context Protocol)** 来桥接 Agent 与 Git。Agent 通过 MCP 客户端调用一个暴露 Git 操作的服务端（例如一个本地运行的 MCP server），服务端提供 tools 列表，包括：`git_status`, `git_branch`, `git_add`, `git_commit`, `git_checkout` 等。所有危险命令被有意排除，由人的最终审批或者 CI 承担。

## 实现步骤

### 1. 搭建 Git MCP server

最简单的方式是使用现有的开源实现，比如 `mcp-server-git`（Python），但需要做一层包装以限制命令范围和添加安全检查。我们内部封装了一个轻量的 server，核心逻辑如下：

- 使用 `subprocess` 调用 Git，但只允许白名单子命令（`status`, `branch`, `add`, `commit`, `checkout -b`, `log`, `diff` 等）。
- 每次 `checkout -b` 前强制检查是否基于受保护分支（如 `main`、`master`），并禁止直接操作远程。
- 对于 `commit`，规定传入的 message 必须符合约定的格式，否则在服务端就拒绝。

Server 通过 MCP 暴露这些 tools，每个 tool 有清晰的 JSON schema 输入描述，方便 LLM 理解。

### 2. 在 Agent 中注册 MCP 工具

以 OpenClaw 配置为例，你可以在 `openclaw.yaml` 中增加一个 MCP 服务连接：

```yaml
mcp_servers:
  git-assistant:
    transport: stdio
    command: python
    args: ["-m", "git_mcp_server", "--workspace", "/path/to/repo"]
```

启动 Agent 后，LLM 就能在需要时自动调用这些 Git 工具。可以预先在 system prompt 中注入项目的分支命名规则和提交规范，比如：

> 所有分支使用 `feat/`, `fix/`, `chore/` 前缀，提交信息符合 Conventional Commits 格式，禁止使用 `--force` 选项。

### 3. 定义自动化工作流触发器

真正提升效率的不是“每次手动让 AI 去做 Git”，而是在特定上下文自动触发。举几个实际例子：

- **提交前检查**：在 pre-commit hook 中调用 Agent 检测暂存区 diff，如果发现变更涉及多个不相关的功能，建议拆分为多次提交。
- **工作区恢复**：当你从一个打断中回来，告诉助理：“我刚在修登录 bug，帮我切回对应分支并显示未提交的改动。” Agent 会通过 `git branch` 和 `git log` 找到最近带有 `fix/login` 的分支并切换，然后用 `git diff` 展示现状。
- **PR 前面的整理**：完成开发后，让 AI 分析本分支的提交历史，建议哪些 commit 可以 squash 到一起，并给出合并后的提交信息草稿。

这些场景的共同特点是：人工负责起点和最终确认，AI 负责中间的上下文查找和操作执行。

## 踩坑记录

在实际接入过程中，有几个必须留意的点：

- **路径隔离问题**  
  MCP server 执行命令时的当前工作目录必须固定为仓库根目录。如果 Agent 开启了多个对话 session 且每个可能涉及不同仓库，需要为每个 repo 启动独立的 server 实例，避免串台。我们采用在 OpenClaw 配置中为不同工作区指定不同 MCP 服务名来解决。

- **状态一致性的幻觉**  
  LLM 有时会“以为”自己已经切换了分支，但没有真正调用 tool。必须在 prompt 中强调：必须通过工具获取最新状态，不能根据之前轮次的记忆猜测。另一个有效方法是在 server 端给 `git_status` 返回值增加时间戳，Agent 看到“2 分钟前的状态”会明白需要刷新。

- **部分失败的处理**  
  当 `git add` 失败（例如有未解决的合并冲突），Agent 倾向于一遍遍重试同一个失败调用。我们在 MCP server 中为工具返回添加上下文提示，比如：“add 失败，原因：存在未解决的合并冲突，请先调用 `git_status --porcelain` 检查。” 这样 LLM 会根据提示转向正确的修复步骤。

- **提交信息生成质量波动**  
  虽然 Conventional Commits 格式可以用正则约束，但内容质量仍依赖模型。小型模型容易生成无意义摘要。我们通过在 system prompt 中给出 3–5 个该仓库历史上的高质量提交示例，大幅提升了生成的信息相关性。

## 可复用建议

这个方案可以脱离特定 Agent 框架单独使用，只要具备 MCP 支持或自定义工具调用能力即可。一些实践经验：

- **从“读”开始，再慢慢开放“写”**  
  先接入只读工具（status, diff, log），让团队成员习惯通过对话查询仓库状态。确认稳定性后，再逐步加入 checkout、commit 等写操作。
- **保留人工审批最后一公里**  
  不要把 `git push` 的控制权交给 AI。可以将生成好的提交和分支以 MR/PR 的方式推送到平台，由同事 review 后再合并。这样即使 AI 做了错误的判断，影响也局限在本地或 feature 分支内。
- **把规范用代码固定下来，而不是只写在 prompt 里**  
  MCP server 层做 schema 校验和规则拦截，比试图通过 prompt 约束 LLM 更可靠。比如 branch 前缀校验、commit 格式校验都应该在工具执行前由代码硬性检查。
- **定期清理 AI 创建的分支**  
  自动化容易产生大量临时分支。可以增加一个定时清理任务，删除所有带有 `ai/` 标记且超过 7 天没有活动的分支，避免仓库过乱。

## 总结

用 AI 管理 Git 并不是取代开发者的版本控制思维，而是把那些“查找、回忆、格式化”的低决策成本动作自动化。通过在 Agent 和 Git 之间引入 MCP server 作为安全层，我们获得了可控的命令执行、规范校验和上下文管理能力。

在整个落地过程中，最大的收益不是速度的提升，而是减少了上下文切换带来的认知负担。你可以把这个方案看作一个始终在线的、理解你项目约定的 Git 配对助手——它做得越快越安静，你越能保持在主要逻辑上的专注。

如果你已经在使用 OpenClaw 或类似支持 MCP 的 Agent 平台，不妨从一个只读 Git 工具开始，体验一下让助手帮你“搞清楚现在仓库到底在什么状态”的流畅感。
