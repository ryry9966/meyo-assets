最近，36kr 的一篇报道把 Claude Code 推上了舆论的风口浪尖。有开发者在逆向分析中发现，这个 Anthropic 推出的命令行 AI 编程助手在运行过程中可能存在未被充分披露的数据收集行为和安全风险，被网友戏称为"藏木马"事件。抛开情绪化的讨论，这件事真正值得关注的不是某一家公司的对错，而是它揭示的一个事实：当 AI 编程工具深入开发者的本地环境，安全边界已经从"模型输出对不对"变成了"整个供应链安不安全"。中美 AI 竞争的焦点，也正在从模型跑分转向生态可控。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-06/d0b8a8af37750df7.png)

## 事件还原：Claude Code 到底"藏"了什么

Claude Code 是 Anthropic 在 2025 年初推出的 CLI 工具，定位是"终端里的 AI 程序员"。它不像 ChatGPT 那样在浏览器里聊天，而是直接跑在你的终端里，能读文件、改代码、执行 shell 命令、操作 git——权限极大，能力极强。

争议的核心集中在三个点：

- **数据回传机制不够透明**：有开发者在抓包分析中发现，Claude Code 在执行任务时，会向 Anthropic 的服务器发送超出用户预期的上下文数据，包括部分本地文件内容和终端环境信息。虽然这在技术上可能属于"正常运行所需"，但问题在于披露不够充分，用户无法精确控制哪些数据可以被发送。
- **系统 Prompt 中的隐藏策略**：逆向分析者发现 Claude Code 的 system prompt 中包含一些关于代码修改策略的指令，这些指令在实际运行中可能导致模型在用户不知情的情况下修改配置文件或添加依赖项。
- **更新机制的盲区**：作为一个通过 npm 分发的工具，Claude Code 的每次更新都可能引入新的行为变化，而绝大多数开发者不会逐行审查版本 diff——你 `npm update` 一下，行为就可能变了。

这里有一个关键的区分：**"木马"和"设计缺陷"之间的边界其实很模糊**。很多时候，一个功能是出于产品目的设计的（比如遥测数据用于改进模型），但在用户看来就是"未经授权的数据收集"。这个边界问题在 AI 工具领域会越来越突出，因为 AI 工具的行为本质上不是确定性的——你很难证明某次代码修改是"bug"还是"故意为之"。

## AI 编程工具的攻击面：从 Prompt 到 Supply Chain

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-06/437ca016fe20a7a1.png)

要理解这个事件的严重性，需要把 AI 编程工具放在整个软件供应链的语境下来看。

传统的开发工具（编译器、Linter、Formatter）是**确定性系统**——同样的输入永远产生同样的输出，你可以通过 diff 审查来发现异常。但 AI 编程工具是**概率性系统**——同样的输入可能产生不同的输出，而且输出内容受到模型权重、系统 prompt、上下文窗口、温度参数等多重因素影响。这就带来了全新的攻击面：

1. **Prompt Injection 攻击**：攻击者可以在开源项目的代码注释、README 甚至依赖包的描述字段中植入恶意 prompt。当 AI 编程工具读取这些文件时，可能被"劫持"执行非预期操作。2024 年已有研究者证明，在 npm 包的 description 中植入 prompt injection 文本，可以让 GitHub Copilot 在生成代码时引入恶意依赖。这种攻击的可怕之处在于：攻击者不需要入侵你的系统，只需要在你的代码上游埋下"文字陷阱"。

2. **隐蔽数据外泄通道**：AI 工具天然需要把本地代码发送到远程服务器进行推理。这意味着你的源代码、配置文件、环境变量、甚至 SSH 密钥路径都可能经过网络传输。如果工具的数据收集策略不够透明——哪些被发送了、哪些被存了、哪些被用来训练了——就存在严重的信息泄露风险。对于企业级用户来说，这直接触及知识产权和合规红线。

3. **供应链传递性放大**：如果你用 AI 工具生成的代码引入了一个有问题的依赖包，这个依赖又会被下游项目引用——典型的供应链传染。AI 工具在这里充当了"放大器"：一个错误的包推荐可以在几小时内扩散到数百个仓库。npm 生态的依赖深度平均达到 6-7 层，追踪起来非常困难。

4. **权限过度授予**：像 Claude Code 这样的 CLI 工具需要文件系统读写权限、shell 执行权限、网络访问权限——几乎是开发环境的" root 级"权限。一旦这些权限被滥用（无论是被攻击者利用还是被厂商主动收集数据），影响范围远超传统工具。传统工具的权限边界是固定的、可审计的；AI 工具的权限边界是动态的、难以预测的。

用一个不太精确但很直觉的类比：传统工具像是你请了一个装修工人来干活，他带什么工具来你大概知道；AI 编程工具像是你请了一个"能自动学习"的工人，他每次来可能带不同的工具，而且你不太确定他会不会顺手把你家的户型图拍照发回去"用于改进服务"。

## 供应链安全：这不是第一次，也不会是最后一次

把时间线拉长来看，软件供应链安全事件其实一直在发生，而且手法越来越隐蔽：

- **2024 年 xz-utils 后门事件**：一个名为 Jia Tan 的贡献者用了近三年时间，逐步在开源压缩库 xz 中植入后门。手法之隐蔽、周期之长、耐心之可怕，让整个开源社区不寒而栗。如果不是微软工程师偶然在性能调试中发现异常，这个后门可能已经进入数百万台 Linux 服务器。这是"长期渗透型"攻击的教科书案例。
- **2020 年 SolarWinds 事件**：黑客通过入侵软件构建流程，在 Orion 的更新包中植入了后门，影响了 18,000 多个客户，包括多个美国政府机构。攻击者没有直接攻击目标，而是攻击了"目标信任的工具"。
- **2018 年 event-stream 事件**：一个被广泛使用的 npm 包被原作者转交给了陌生人维护，新维护者悄悄加入了恶意代码，专门窃取比特币钱包。下游有数千个项目依赖这个包。

这些事件的共同特征是：**攻击者不再直接攻击目标，而是通过渗透开发工具链来间接影响成千上万的下游用户**。AI 编程工具的出现，让这条攻击链又多了一个环节——而且是一个权限极高、行为不可预测、审计困难的环节。

## 竞争新阶段：从模型跑分到生态博弈

回到 36kr 报道的核心论点：中美 AI 竞争进入了更残酷的新阶段。这个"新阶段"到底新在哪里？可以做两阶段划分：

**第一阶段（2023–2024）：模型能力竞赛**
- 核心指标：参数规模、benchmark 分数、上下文窗口长度、推理速度
- 竞争主体：OpenAI、Anthropic、Google vs 百度、阿里、月之暗面、智谱等
- 特征：谁的模型更聪明、跑分更高，谁就占据优势。竞争主要集中在模型层。

**第二阶段（2025–）：生态与安全竞赛**
- 核心指标：工具链安全性、数据合规性、供应链可控性、开发者信任度
- 竞争主体：扩展到整个开发者生态——IDE、CLI 工具、CI/CD 集成、Agent 框架、模型市场
- 特征：光模型聪明已经不够了，还得让开发者用得放心。安全与信任成为新的护城河。

Claude Code 事件恰好发生在阶段切换的节点上。它的意义不在于"Anthropic 到底有没有做坏事"（这一点仍有争议），而在于它让大家意识到：**当你把一个外国公司的 AI 工具放进你的开发环境里，你面对的不只是一个产品，而是一整套数据流转、模型推理、远程更新、行为漂移的技术栈**。

在这个新阶段，竞争的关键词变成了：

- **数据主权**：代码数据流向哪里、存储在哪里、是否被用于训练、能否被彻底删除。对于中国开发者来说，这涉及《数据安全法》和《个人信息保护法》的合规边界。
- **供应链审计能力**：AI 工具的行为是否可审计、可追溯、可回滚。一个不可审计的工具，本质上就是一个黑盒。
- **本地化与私有化部署**：是否可以在本地或私有云运行 AI 工具，减少数据外流。Ollama、vLLM 等本地推理框架的兴起，部分动力就来自这种需求。
- **开源 vs 闭源的重新审视**：开源模型和工具在透明度上有天然优势——你可以读 system prompt、审查数据流、甚至 fork 后自用。在安全语境下，开源不再只是"便宜"的代名词，而是"可控"的保障。

## 冷思考：开发者该怎么活下去

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-06/084ecd3245f60ecc.png)

最后给三条务实建议，不灌鸡汤，不说"保护隐私"这种正确的废话：

**1. 分层隔离你的 AI 工具使用**

把"辅助编写函数"和"直接操作项目仓库"分成两个信任级别。敏感项目（涉及核心 IP、用户数据、商业逻辑）用本地模型——Ollama + CodeLlama / DeepSeek Coder 等开源模型在本地跑，数据不出机器。非敏感项目可以用云端工具，但也要定期检查授权范围。核心原则：**不要让任何一个工具有全部权限**。给 Claude Code 一个独立的 sandbox 环境，至少用 Docker 隔离文件系统访问。

**2. 养成审查 AI 生成代码的习惯，像 review 人类 PR 一样**

具体来说，每次 AI 生成代码后，检查三个点：
- **新增的依赖包是否可信**：查 npm registry 的下载量、维护者活跃度、GitHub issue 数量。一个上周才注册、下载量个位数的包，再方便也别用。
- **是否有不明的网络请求**：`grep` 一遍 `fetch`、`axios`、`http.get`、`XMLHttpRequest`，确认每个请求的目标地址都是你预期的。
- **是否有对配置文件或环境变量的读取操作**：AI 生成的代码如果突然开始读 `.env` 文件，你需要问一个为什么。

**3. 关注供应链安全的工具化进展，至少用起来基础工具**

供应链安全框架（.sigstore、SLSA、in-toto）正在快速演进，虽然目前主要面向企业级安全团队。但对独立开发者来说，至少应该用起来这些基础工具：
- `npm audit`：检查已知漏洞依赖（虽然它检测不了 AI 引入的未知风险，但能挡住已知的）
- Socket.dev：分析 npm 包的行为特征，能检测出"这个包突然开始执行网络请求"之类的异常行为
- Git hooks + pre-commit：在 AI 生成的代码提交前自动跑一遍安全扫描

AI 编程工具不会因为安全担忧就停止普及——就像云计算也不会因为数据泄露事件就退回本地机房。但每一个开发者都应该成为自己供应链的"守门人"，而不是把信任廉价地外包给任何一家公司。

不管它叫 OpenAI、Anthropic，还是别的什么名字。
