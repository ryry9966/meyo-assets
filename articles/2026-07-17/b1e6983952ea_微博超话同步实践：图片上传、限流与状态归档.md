## 背景

如果你用 OpenClaw 或类似 Agent 框架做内容分发，微博超话往往是最头疼的一个平台。不同于普通微博，超话发帖需要带着社区归属，还要处理图片上传、频控和状态管理。如果只是手动发帖，这些问题不明显；一旦要接入自动化流水线，就必须把每一步都做成可观测、可恢复的工程化流程。

这次同步任务的目标是：根据上游内容源（例如本地 Markdown 仓库、RSS 或 CMS）自动向指定超话发布图文帖，要求带上封面图、话题标签，并能容忍超话的提交限制与登录态波动。

## 核心问题拆解

微博开放接口对超话支持非常有限，公开发帖流程里几个典型的坑：

1. **图片上传**：微博图片服务有独立的 `picupload` 接口，需要先上传图片获得 `pid`，再在发帖请求里引用。如果直接使用 session 级别的 cookie，容易被反爬策略拒绝。
2. **超话归属**：发帖时必须携带 `pub_source` 或 `topic_id` 类参数，而且不同超话可能有不同的发帖门槛（等级、签到要求等），自动化流程需要能捕获这些业务错误。
3. **限流与风控**：短时间连续发帖或上传图片会触发 `100005` 类风控拦截，直接拒绝请求，甚至短暂封禁账号一段时间。
4. **状态归档**：微博发帖不是幂等的，重复请求可能导致重复发帖。需要一套唯一任务 ID 与结果映射，以便回溯和去重。

## 做法与步骤

下面给出基于 OpenClaw + 自定义 MCP 工具的实现思路。为了方便说明，我们将流程拆成四个阶段。

### 1. 登录态维护

放弃用 `requests` 手动管理 cookie 的方式，改用 `playwright` 或有头浏览器模拟登录后导出 cookie 字符串，然后注入到后续 HTTP 客户端。每次调用前检查 cookie 是否临近过期（例如通过请求一个需登录的接口看返回码），如果失效，自动触发一轮无头登录刷新。

```python
# 伪代码：cookie 刷新包装
async def ensure_cookie():
    if not cookie_jar or cookie_jar.is_expired():
        cookie_jar = await headless_login(account)
    return cookie_jar
```

登录过程要处理验证码，准备一个手动验证的 fallback：弹出二维码或登录链接，由人扫码后继续。这个步骤可以封装为 MCP 资源，当 Agent 收到“需验证”信号时，暂停流水线并通知人工。

### 2. 图片上传与 pid 获取

上传接口地址类似于：`https://picupload.weibo.com/interface/pic_upload.php`，表单中包含 `type=json`、`pic1` 文件字段，以及从页面提取的 `data` 字段（含有跨站请求参数）。

关键点：

- 图片必须过防火墙格式校验，只支持 jpeg/png，且文件大小建议在 5MB 以内。
- 上传时使用 `multipart/form-data`，且 `Referer` 必须为 `https://weibo.com/`，否则可能被拒。
- 返回 JSON 中提取 `data.pics.pic_1.pid`，即为此图的唯一标识。

将这一步封装为 MCP 工具 `upload_weibo_image`，输入为本地图片路径，输出为 pid。失败时记录错误码，例如 `100005` 或 `20003`，供上层决策。

### 3. 超话发帖请求

发帖接口为 `https://weibo.com/aj/mblog/add`，核心参数：

- `text`: 微博正文（已编码）
- `pic_id`: 上传得到的 pid（多图用逗号分隔）
- `pub_source`: 标识来源，超话发帖需要填入 `page_2` 之类根据具体超话页面抓到的值
- `topic_id`: 超话对应的 id，一般从超话页面 `window.$render_data` 中提取
- `_t`: 时间戳，通常设为 0
- `location`, `appkey` 等非必需字段可以省略，但某些超话要求补充 `extra_param`

请求头必须模拟真实浏览器，尤其是 `X-Requested-With: XMLHttpRequest` 和正确的 `Referer`。

特别注意：微博接口返回的 `code` 可能为 `100000`（成功）或 `100001`（参数错误），而风控相关错误码可能是 `100005`。一旦遇到风控，要区分是暂时限流还是账号级别限制。暂时限流可以等待后重试，而账号风控则需要中止流程并告警。

### 4. 任务状态归档与去重

为每个发帖任务分配一个唯一的 `task_id`（可以基于内容摘要 + 时间戳的哈希）。发帖前检查本地归档库（SQLite 或 JSON 文件），如果 `task_id` 已存在且状态为 success，则跳过；如果状态为 failed/pending，则按策略重试或跳过。

状态归档设计：

| 字段 | 说明 |
|------|------|
| task_id | 唯一任务标识 |
| content_hash | 博文内容摘要哈希 |
| pid_list | 上传图片 pid 列表 |
| post_result | 微博返回结果原始 JSON |
| status | pending / success / failed_retryable / failed_final |
| retry_count | 重试次数 |
| created_at | 任务创建时间 |

这样的设计让 Agent 可以放心地重复执行同步命令，而不会导致重复发帖。此外，失败任务可以被一个清理流程周期性重试，或者人工介入修复后标记为 pending 重新发布。

## 踩坑记录

1. **上传图片后 pid 并非永久有效**  
   上传得到的 pid 有有效期（约24小时），必须及时使用。如果流程中断，第二天再补发，需要重新上传图片。

2. **超话发帖参数随 Web 端升级变化**  
   之前有效的 `pub_source` 字段可能因微博前端改动而失效。建议每隔一段时间用真实浏览器抓包确认参数，或从超话页面 `render_data` 动态提取最新配置。

3. **限流粒度比预想更细**  
   不仅是一个账号维度，相同 IP 下不同账号也可能被关联限流。多账号分发时建议使用不同代理出口，且发帖间隔不小于 60 秒。

4. **混合内容问题**  
   如果正文里包含外部链接，极大概率被标记为广告而发不出去。超话发帖尤其严格，建议纯图文、不带链接。

5. **人工验证不可避免**  
   无论自动化做得多完善，阶段性的滑块验证、短信验证总会跳出来。接受这一点，在流程里设计人工 fallback 比追求全自动要务实得多。

## 可复用建议

- **抽象出 MCP 工具集**：把登录、上传、发帖、状态查询分别做成 MCP tool，这样任何一个 Agent 或插件都可以直接调用，而不必关心底层 cookie 管理。
- **增加回执通知**：发帖成功后，构造一条消息（包含微博链接、发布时间、归档 ID）推送到 IM（如飞书、微信），方便人工交叉检查。
- **失败分级处理**：`100005` 类错误属于风控，应触发冷却期；参数错误 `100001` 则需要程序修正参数；网络超时单纯重试即可。
- **用文件锁防止并发写**：如果多个 Agent 进程可能操作同一归档文件，记得加锁，避免归档状态错乱。
- **留档原始响应**：`post_result` 中保存完整返回 JSON，未来排查问题时不必再复现请求。

## 总结

微博超话的自动化发帖本质上是在和不透明的反爬系统博弈。尽量降低调用频率、模拟真实浏览器行为、保留人工干预入口，才是长期可维护的方案。用 OpenClaw 框架把图片上传、发帖、归档封装成标准的 MCP 工具后，上游 Agent 只需关注内容准备和策略调度，不需要重复踩坑。整个流程最终形成一条可控、可回滚的内容分发管线，让超话这个渠道真正融入到自动化发布流水线里。
