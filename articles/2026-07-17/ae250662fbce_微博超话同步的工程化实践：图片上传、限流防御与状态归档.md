## 背景

在 OpenClaw 生态里，内容的多平台分发是一个常见需求。让 Agent 自动将生成好的图文推送到微博超话，能有效保持账号活跃度，但实际操作远非调用一个接口那么简单。非官方渠道没有稳定 API，上传图片要模拟浏览器行为，中间还会遇到颗粒度很细的限流与风控。如果只是临时跑一次脚本，这些问题勉强能忍；一旦想做成长期运行、可观测、可恢复的自动化流水线，图片处理、限流兜底和同步状态记录就必须被认真对待。

本文记录一次微博超话同步工具的工程化摸索，重点放在三个最耗心力的模块：图片上传的实现与规避陷阱、面对接口限流的健壮处理、以及用状态归档保证任务幂等。全部基于 Python + requests / Playwright，无外部商业平台依赖，可集成进 OpenClaw 的 Agent 或 MCP 工具链。

## 问题拆解

微博超话发帖并不是一条简单的 RESTful 请求。实际需要解决这几个问题：

- **图片上传**：图片必须预先上传到微博 CDN，拿到 pid 后再嵌入发帖参数。上传接口使用 `multipart/form-data`，且对请求头、Cookie 来源、图片尺寸有隐形校验。
- **限流**：超话发帖频率稍高就会触发 `100000` 系列错误码，有时是“操作过于频繁”，有时直接打回验证码。没有合理的退避和重试策略，很容易陷入硬性封禁。
- **状态归档**：一个内容源可能对应多条微博。为了避免重复发送或部分失败后无法溯源，需要一套状态机记录每个待发贴的当前状态，并在重启后依然可读。

另外，微博 Web 端和移动端 API 行为不完全一致，选型不同会导致不同的限流阈值和上传限制。这里以 Web 端接口为例，更贴近浏览器自动化场景。

## 做法与步骤

### 1. 图片上传：模拟完整的表单请求

直接抓包得到的上传地址类似 `https://picupload.weibo.com/interface/pic_upload.php`，参数中需要带 `mime`、`data`、`cb` 等。关键是不光要传图片二进制，还要在请求头里带上正确的 `Referer` 和从登录 Cookie 域继承的 cookie。

简化后的上传函数核心逻辑：

```python
import requests
from io import BytesIO
from PIL import Image

def upload_image(image_path: str, cookies: dict, headers: dict) -> str | None:
    img = Image.open(image_path)
    # 微博对图片尺寸有隐式限定，过宽过高的图会直接返回失败而无明确错误
    img.thumbnail((1200, 1200))
    buf = BytesIO()
    img.convert("RGB").save(buf, format="JPEG", quality=85)
    buf.seek(0)

    url = "https://picupload.weibo.com/interface/pic_upload.php"
    data = {
        "mime": "image/jpeg",
        "data": "base64",
        # 实际base64编码需要先做，有些接口需要去掉data:前缀
    }
    # 构造multipart，某些接口要求文件字段名为 filedata
    files = {"filedata": ("image.jpg", buf, "image/jpeg")}
    resp = requests.post(url, cookies=cookies, headers=headers, files=files)
    # 解析返回的pid，形如 "001ABC..."
    pid = extract_pid(resp.text)
    return pid
```

踩坑中最隐蔽的一点是：请求头里的 `Content-Type` 不能手动指定 `multipart/form-data` 的 boundary，否则微博 CDN 会当成异常请求拦掉。完全交给 `requests` 自动生成反而是安全的。

### 2. 限流防御：退避、错误码分类与代理切换

微博的限流不是简单的 HTTP 429，而是隐藏在响应 JSON 里的业务错误码。常见如：

- `100000`：操作太频繁
- `100001`：需要验证码
- `100002`：内容重复（这也算一种软限流）

工程做法是捕获这些错误码，执行 **分级退避**：

- `100000`：随机等待 60–180 秒后重试，最多 3 次。
- `100001`：暂停当前任务，发送通知给维护者，并标记该条微博状态为 `rate_limited`，等待人工处理验证码后恢复。
- 连续触发限流 3 次以上，自动切换到备用的代理 IP 或修改 `User-Agent` / cookie 域，降低单账号压力。

示例重试装饰器：

```python
import time, random

def retry_with_backoff(tries=3, base_delay=60):
    def decorator(func):
        def wrapper(*args, **kwargs):
            for attempt in range(tries):
                result = func(*args, **kwargs)
                if not result.get("error"):
                    return result
                code = result["error_code"]
                if code == "100000":
                    delay = base_delay + random.uniform(0, 60)
                    print(f"限流，等待 {delay:.0f}s...")
                    time.sleep(delay)
                elif code == "100001":
                    raise NeedCaptcha("触发验证码，需人工")
                else:
                    raise WeiboError(code)
            raise MaxRetryExceeded
        return wrapper
    return decorator
```

为了不在限流等待时丢失进度，这部分逻辑最好放在一个独立的任务执行器里，与状态归档协同。

### 3. 状态归档：轻量级任务日志

用 SQLite 保存每条待发微博的状态，表结构参考：

```sql
CREATE TABLE sync_tasks (
    id INTEGER PRIMARY KEY,
    source_id TEXT UNIQUE,   -- 源内容唯一标识（如RSS guid）
    content TEXT,
    image_pid TEXT,
    status TEXT DEFAULT 'pending',
    retries INTEGER DEFAULT 0,
    created_at TIMESTAMP,
    last_attempt TIMESTAMP
);
```

每次发布前检查该 `source_id` 是否已存在且状态为 `success`，避免重复发送。失败状态如上文，`rate_limited` 会被定期扫描重新进入队列。通过这种方式，即使进程被杀，下次启动也能接着未完成的任务继续。

另外，图片的 `pid` 上传成功后也存入该记录，防止重复上传。微博的 `pid` 在短时间（约 24 小时）内可复用，所以还可以增加针对图片 MD5 的去重，减少上传频率。

## 踩坑点汇总

- **Cookie 保持**：Web 接口的 cookie 过期时间不稳定，尤其是 `SUB` 和 `SUBP` 字段。最好每 2 小时用 Playwright 模拟登录刷新一次 cookie，存到共享的 `cookies.json` 中给所有 worker 读取。
- **图片长度限制**：超话对图片文件大小有限制（约 3MB），但更狠的是图片边长不能超过 4096px。用 Pillow 做尺寸检查时，如果直接传入高清截图很容易被静默拒绝。
- **超话 ID 获取**：超话的 `topic_id` 并非页面直观可见，需要通过 `https://weibo.com/p/{uid}/super_index` 解析，且不同版本有不同的获取路径，最好封装一个查找函数，一旦失败能自动回退。
- **内容去重**：即使 `source_id` 不同，也可能产出语义几乎相同的文本。对于超话这种社区，短时间内发相似内容会直接触发 `100002`。一种缓解策略是，为每条微博生成一个短随机后缀（如 #自动打卡 等标签），改动足够比特度。

## 可复用建议

如果希望将这套能力暴露给 OpenClaw 的 Agent 或 MCP 服务，建议封装成两个 MCP tool：

1. `weibo_image_upload(file_path, cookies_store_path) -> pid`
2. `weibo_super_topic_post(pid, content, topic_id, cookies_store_path) -> result`

这样 Agent 在规划流程时可以直接调用这两个工具，而不用关心底层退避和归档。状态数据库则作为共享资源，保持所有 MCP 实例状态一致。

## 总结

微博超话同步并不是一个高难度技术点，但它密集集成了反爬、状态管理和容错设计等工程化挑战。没有万能的绕过方案，只能通过细致的错误分类、合理的退避窗口以及完善的任务归档来保证系统韧性。最后提醒一句：一切自动化操作都应以遵守平台规则为前提，合理控制频率，避免影响正常社区生态。
