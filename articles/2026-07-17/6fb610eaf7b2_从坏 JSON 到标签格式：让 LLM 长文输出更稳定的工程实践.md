## 背景：JSON 的“理想”与“现实”

在 OpenClaw 社区的自动化实践里，大量场景需要让 LLM 输出结构化内容：插件返回的多步骤计划、Agent 的工具调用指令、MCP 服务的长文本摘要…… 最常见的做法是“请输出 JSON 格式”，比如：

```json
{
  "steps": [
    {"action": "click", "element": "#submit"},
    {"action": "wait", "ms": 500}
  ]
}
```

理想很丰满，但在实际运行中，哪怕 temperature 设为 0，长文本输出中的 JSON 依然问题频出：缺少引号、括号不匹配、内容中包含未转义的双引号或换行符、模型凭空添加注释…… 最终解析器抛异常，整个自动化流程中断。修复方式往往是加一堆 post-processing 或反复调整 prompt，维护成本极高。

更麻烦的是，一旦输出变长，JSON 的嵌套结构会急剧放大这些脆弱性。很多时候我们并不需要完整的对象图，只需要把模型生成的大段内容按逻辑块分开。

## 核心转变：用自定义标签替代 JSON

思路其实不难：既然 JSON 的严格语法是障碍，那就换一套对 LLM 更自然、对解析器更宽容的标记方式——**自定义标签（custom tags）**，类似轻量级 XML，但规则由你掌控。

比如上面的多步指令，可以改写为：

```
<step n="1">
<action>click</action>
<element>#submit</element>
</step>
<step n="2">
<action>wait</action>
<ms>500</ms>
</step>
```

这种写法有几个关键优势：

1. **语法容错性强**：标签不要求全局唯一键值、不强制逗号，文本块可以包含任意字符（只要不包含标签分隔符）。
2. **解析极其简单**：用正则 `re.findall(r'<step(.*?)>(.*?)</step>', text, re.DOTALL)` 就能提取所有 step 块，再对每个块内部做小粒度抽取。
3. **LLM 更容易遵循**：多数基座模型在预训练数据中见过大量 HTML/XML 结构，闭合标签的输出概率远高于正确的 JSON 尾括号层级。

我在 OpenClaw 的插件开发和 Agent 流程中落地这一模式后，解析成功率的提升非常明显：原本用 JSON 时 15%~20% 的输出需要二次修正，换成标签后失败率降到 3% 以下，且重试逻辑也更轻量。

## 具体做法与步骤

### 1. 设计最小化标签集
只定义必要标签，层级尽量不超过 2 层。例如一个“报告生成”任务：

```
<report>
<title>周报</title>
<summary>本周完成核心功能迭代...</summary>
<detail>
本周进行了以下工作：
- 重构登录模块
- 接口联调完成
</detail>
</report>
```

标签名使用英文单词，避免特殊字符。对于可能包含标签分隔符的文本，可以在 prompt 中要求 LLM 转义，但更简单的做法是选择内容中几乎不会出现的分隔符，比如用 `<|section|>` 作为稀有标记。

### 2. 编写 Prompt 模板
切忌只说“输出 XML”，要给明确示例和格式约束：

```
你要输出一段结构化内容，**必须严格**使用以下标签格式（不要用 JSON）。

输出格式：
<report>
<title>...</title>
<summary>...</summary>
<detail>...</detail>
</report>

要求：
- 不得在标签外泄露任何内容
- 标签必须正确闭合
- 如果内容中包含字符 "<" 或 ">"，请用 &lt; 和 &gt; 代替

现在开始：
```

如果你的流程控制允许，还可以加入“先输出一个确认标记”的方式，让模型把长文本放在 `[START]` 和 `[END]` 之间，再包裹标签，进一步降低截断风险。

### 3. 解析与容错代码
用 Python 实现一个轻量解析器：

```python
import re

def extract_tag(tag: str, text: str) -> str:
    pattern = rf'<{tag}>(.*?)</{tag}>'
    m = re.search(pattern, text, re.DOTALL)
    return m.group(1).strip() if m else None

def parse_report(text: str):
    # 提取根块
    block_match = re.search(r'<report>(.*?)</report>', text, re.DOTALL)
    if not block_match:
        raise ValueError("Missing <report> block")
    inner = block_match.group(1)
    return {
        "title": extract_tag("title", inner),
        "summary": extract_tag("summary", inner),
        "detail": extract_tag("detail", inner)
    }
```

这里不依赖整个文档是唯一的 `<report>`，就算模型在输出前后加了闲聊文本（比如“好的，这是报告：”），我们的正则依然能匹配到目标块。

### 4. 重试与验证
即使切换成标签，还是有闭合不匹配的可能。加入快速验证：统计每个标签的开闭次数，最简单的可用 `assert text.count('<report>') == text.count('</report>')`。验证失败时，把错误信息（如“您的输出中缺少 </report>”）喂回模型，再请求一次补全。因为标签结构简单，模型改正的概率极高。

## 踩坑点与关键细节

- **内容部分误含标签分隔符**  
  如果 detail 里出现了 `</detail>` 字样，解析器会提前截断。解决方式：让 LLM 转义或用极低频定界符（如 `<|end_detail|>`）。但更工程化的做法是：在 prompt 中约定“标签只用于结构，不要出现标签文字”，并设置正则的非贪婪匹配，这能覆盖大多数情况。

- **深层嵌套不可靠**  
  虽然 XML 支持多层，但 LLM 写三层以上嵌套时出错率明显上升。实践证明，一层列表（根+多个子块）是最佳平衡点。如果需要复杂结构，可以把深层数据放在一个 `<detail>` 内，内部保留为 Markdown 列表或纯文本，由下游二次解析。

- **不同模型对转义的支持差异**  
  有些模型会自动把 `&lt;` 写成 `<`，反过来又破坏结构。此时不再要求模型做实体转义，而是在 prompt 中强调“内容中不要包含 `<` 或 `>`”，并在解析侧对内容做一次安全检查。

- **与 JSON 混用的场景**  
  某些字段确实适合 JSON（例如数值列表），可以在标签内嵌套一个 `<json_data>` 块，但请务必明确标注：`<json_data>{"key": "value"}</json_data>`。这样即使 JSON 部分出错，也只影响局部字段，不会导致整个输出不可用。

## 可复用的建议

- **优先选标签，而不是修补 JSON**：只要你的结构化目标是把长文本切分成语义块，标签就是更稳的选择。
- **控制标签数量**：一个好用的原则是“不超过 5 种标签，不超过 2 层嵌套”。
- **把格式示例固化到系统 prompt 里**：并在示例中故意写几个闭合标签，让模型有样学样。
- **解析器保持宽容**：能用正则非贪婪匹配就别写完整词法分析器，非核心字段缺失时降级处理而不是直接崩溃。
- **加入低成本校验与重试**：简单统计开闭标签数量，失败时把错误描述注入下一次请求，比人工调试更高效。
- **与 MCP/插件结合时，将标签规范写入 service 的 description 或 output schema 旁边**，让下游自动理解。

## 总结

从 JSON 到自定义标签的转变，表面是格式选择，内核是**保持结构化输出的同时，降低对 LLM 语法精确性的依赖**。在 OpenClaw 的自动化流程中，稳定性远比技术美感重要。用 30 行正则代替繁杂的 JSON 修补逻辑，能让你的 Agent 跑得更踏实，维护负担也会大幅下降。

希望这个实践能帮助你在做插件、MCP 服务或长文本自动化时，把更多的精力花在业务逻辑上，而不是和花括号较劲。
