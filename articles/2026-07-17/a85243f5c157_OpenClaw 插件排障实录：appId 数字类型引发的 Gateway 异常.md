## 背景

在 OpenClaw 的插件生态里，Gateway 是所有外接能力进出的统一入口。无论是调用模型、访问外部 API，还是触发自动化流程，插件最终都要把请求结构化成 Gateway 定义的格式，通过 HTTP 或 gRPC 发出去。

最近在移植一个内部用的 Agent 插件到 OpenClaw 社区版时，遇到了一个典型的类型反序列化异常：插件工作得好好的，一旦切到社区 Gateway 端点，就直接爆出 `cannot unmarshal number into Go struct field xxx.appId of type string`。这个报错本身并不陌生，但背后暴露出来的设计细节和插件兼容性问题，远比一行 error 更值得复盘。

## 问题表现

现象很干脆：插件向 Gateway 发送某个资源查询请求时，Gateway 直接返回 400，body 中是反序列化失败的错误信息。关键字段是 `appId`，在 Gateway 的 OpenAPI 定义里，它被声明为 `string` 类型，但我们的插件在构造请求体时，因为历史原因把它当成了 `int64` 处理，最终 JSON 序列化出来是数字，而不是字符串。

```
// 异常请求体片段
{
  "appId": 500123456789,
  "action": "query_config"
}
```

Gateway 的 Go 结构体接收时，`appId` 严格要求 `string`，`json.Unmarshal` 自然失败。这个报错在链路里清晰可见，但真正麻烦的是，同样的请求在旧版测试网关（也是 Go 实现）上却不会报错，因为旧网关的验证逻辑宽松，内部做了兼容转换。到了社区严格模式，立刻现了原形。

## 排查过程

整个排查并不复杂，但值得把流程写下来，因为这类问题全靠「细心对比」和「静态类型检查」就能快速定位，没必要围着日志一顿瞎猜。

**第一步：先确认报错到底从哪一层抛出。**  
Gateway 返回的错误信息直接给出了完整的堆栈，明确定位在 `json.Unmarshal` 阶段，排除了网络抖动、鉴权等问题。

**第二步：对比正常请求与异常请求的 JSON 差异。**  
把插件发出的请求体用抓包工具（mitmproxy 即可）dump 下来，和 OpenAPI 文档里的示例一对照，`appId` 类型的差异立刻浮现。

**第三步：逆向追踪插件内部的类型定义。**  
插件里定义了 `AppConfigRequest` 结构体，其中 `AppId` 字段类型是 `int64`，json tag 也没有加 `,string`。这说明问题根因在插件的结构体定义与外部 Gateway 约定不一致。

**第四步：检查是否还有类似字段。**  
很容易顺手把 `userId`、`projectId` 等字段也检查一遍，发现确实还有一个 `projectId` 也存在相同隐患，提前一并修正。

一个值得注意的细节：之所以插件里会定义成 `int64`，是因为最初接入的内部系统 ID 一直是数字，且没有文档强制要求用 string 传输。久而久之，这个假设就「固化」到了插件结构体中。直到跨环境对接时，类型约束才被 Gatewey 严格校验出来。

## 解决方案

修复逻辑本身很简单，但为了保证长期兼容，我们采取了两种手段并用：

1. **修改插件结构体定义**  
   把 `AppId` 从 `int64` 改为 `string`，并在序列化时强制以字符串输出。如果上游系统返回的 ID 本身就是数字，在入库或缓存之前就做一次 `strconv.FormatInt` 转换，保证插件内部始终持有字符串。

2. **增加请求构建层的类型适配**  
   为避免类似问题在其他字段上重现，我们在插件与 Gateway 交互的 adapter 层加了一个轻量的 JSON Schema 校验。每次构造请求时，自动根据 Gateway 的 OpenAPI schema 检查字段类型，不符合就提前打 log + 转换。这样即使今后有新的数字字段漏网，也能在出口处拦下来。

最终修改量很小，改动集中在 3 个文件：请求结构体定义、ID 转换工具函数、adapter 的序列化预处理。修改后重新打包插件，在本地和 OpenClaw 社区环境均通过回归测试。

## 踩坑点与反思

- **动态语言与静态语言混用的隐性冲突**  
  插件本身使用 Python/TypeScript 等弱类型语言编写时，`appId` 是 `12345` 还是 `"12345"` 往往被 `json.dumps` 自动判断，容易忽略 Gateway 端强类型反序列化的约束。这次就是插件侧 TS 中把 `appId` 当 `number` 传，最终在 Go 侧崩掉。

- **数字精度问题**  
  如果 `appId` 是一个超出 JavaScript 安全整数范围的数字（如雪花算法生成的 int64），即使 Gateway 允许 number，前端也可能因为精度丢失拿到错误的值。统一用 string 传输，是避免这类问题的工程共识。这一点在插件输出给前端展示时同样适用。

- **测试环境与生产环境的差异放大**  
  旧网关的宽松策略让类型错误被静默吞掉，脱离严格校验后，插件实际上一直在「幸运运行」。在 OpenClaw 这种强调标准化的社区环境下，任何假设都会被严格验证，所以移植插件时，务必对准最新的 OpenAPI 定义做一次彻底的 schema 对齐。

## 可复用建议

总结几条可以马上落地的实践：

1. **ID 类字段一律用 string 定义和传输**  
   无论是插件内部、Gateway 交互，还是输出给前端，不要依赖 number，避免精度和类型问题。可以在团队 lint 规则中强制要求。

2. **插件必须做出口 schema 校验**  
   不要信任「看起来长得一样」的 JSON，用 Gateway 官方发布的 OpenAPI/JSON Schema 文件，在请求发出前做一次类型和必填字段的校验。可以用小工具或中间件自动完成。

3. **引入端到端的接口契约测试**  
   针对每个插件，至少写一条请求-响应的契约测试，直接打在真实或 mock 的 Gateway 上。让类型不一致的问题在 CI 阶段暴露，而不是等到上线后。

4. **保持与社区 Gateway 版本同步**  
   OpenClaw Gateway 在迭代中可能会收紧校验规则，建议在插件仓库里加上一个依赖版本检查，定期读取最新的 OpenAPI 描述，确保没有新增的 breaking change。

## 总结

appId 数字类型引发的 Gateway 异常看起来很小，但它恰好反映了插件开发中一个常见的工程短板：当我们习惯了一种「宽容」的内部环境后，容易在做跨平台、跨语言对接时忽略最基础的类型约束。在 OpenClaw 这样的标准化社区中，严格校验不是缺陷，而是一种保护。与其事后排查反序列化错误，不如在设计和工具链阶段就把类型一致性刻进工作流里。

希望这次排障记录能给同样在移植或开发 OpenClaw 插件的朋友一些前置提醒，少走几步弯路。
