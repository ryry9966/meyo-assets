## 背景：一条定时任务引发的“血案”

在 OpenClaw 中，我们通过内置的调度器为 Agent 配置了每 5 分钟执行一次的自动化流程：调用外部 API 拉取数据，经大模型处理，再通过 MCP 工具写回数据库。一切运行平稳，直到某天监控显示数据库出现了 **大量重复记录**，LLM token 消耗在两天内翻了 3 倍。排查后发现，元凶是“定时任务重入”。

**根源很简单**：任务的实际执行时间常因上游 API 响应变慢或模型推理卡顿而延长至 7–12 分钟，远超过 cron 的 5 分钟间隔。每次调度器触发时，前一次运行并未结束，两个 Agent 实例同时操作同一批数据，发生“撞车”。OpenClaw 的调度器默认 **不检查上一次任务是否完成**，由此引出了一项基础但极易被忽视的工程需求——**防重入锁**。

## 问题：并发重入带来的连锁反应

当同一个 Agent 任务并发执行时，带来的不仅是数据重复：

1. **幂等性被破坏**：即使代码设计了幂等逻辑，在“读-改-写”间隙仍可能被另一实例覆盖。
2. **外部资源争抢**：API 限流、数据库连接池耗尽、临时文件冲突。
3. **上下文污染**：部分 Agent 会维护内存中的状态（如累计计数、会话历史），并行运行导致状态错乱。
4. **排障困难**：日志交织，难以区分异常来自哪个实例。

对于 OpenClaw 这种集成 Agent、MCP 服务器、插件脚本的编排环境，**并发安全几乎全靠开发者自行兜底**。问题一旦出现，往往已是生产故障。

## 做法：在 OpenClaw 中实现可靠的防重入锁

我们无法修改调度器代码，但可以通过 **前置检查步骤** 在 Agent 运行前插入锁逻辑。下面给出两种可落地的方案，均已在生产环境验证。

### 方案一：本地文件锁（适合单实例部署）

若你的 OpenClaw 运行在单台机器且无需考虑跨节点锁，文件锁是最轻量的选择。利用 Python 标准库 `fcntl` 或三方库 `portalocker`，实现如下：

在 Agent 配置的 `pre_hook` 或通过一个 `script` 插件执行锁定脚本：

```python
import portalocker
import os
import sys

LOCK_FILE = "/tmp/openclaw_task.lock"

def acquire_lock():
    try:
        f = open(LOCK_FILE, "w")
        portalocker.lock(f, portalocker.LOCK_EX | portalocker.LOCK_NB)
        return f
    except (portalocker.LockException, IOError):
        print("Previous task still running, exiting.")
        sys.exit(0)

def release_lock(f):
    portalocker.unlock(f)
    f.close()
```

在 Agent 主逻辑开始前调用 `acquire_lock()`，结束时在 `finally` 块中调用 `release_lock()`。如果锁已被持有，另一个实例立即退出，不会进入实际处理。

**关键细节**：锁文件路径应使用绝对路径并确保目录可写；进程被强制杀死时，操作系统会回收文件描述符并释放锁，但为防万一，配合一个 **守护进程检测** 更稳健。

### 方案二：Redis 分布式锁（适用于多实例 / 水平扩展）

OpenClaw 默认可通过 MCP 连接 Redis，我们可以将锁外化到 Redis。以 `SETNX` 配合过期时间实现一个带超时的锁：

```
if redis.call("SET", KEYS[1], ARGV[1], "NX", "EX", ARGV[2]) then
    return 1
else
    return 0
end
```

在 Agent 中调用该脚本获取锁，`unique_value` 使用 UUID，超时时间设定为 **任务最大可能执行时长的 1.2 倍**（如最长 10 分钟，则设 720 秒）。解锁时使用 Lua 脚本保证原子性，避免误删其它实例的锁。

封装成 OpenClaw 可复用的 **技能（Skill）**，在 YAML 中引入：

```yaml
skills:
  - name: redis-task-lock
    type: mcp
    server: redis-server
    parameters:
      lock_key: "openclaw:locks:my_task"
      timeout: 720
```

Agent 在第一次工具调用前检查锁，若获取失败直接返回终止信息。

## 踩坑点：那些让你加班的不起眼细节

1. **锁超时设置不当**：必须基于历史耗时 P99 设置，动态调整。若超时过短，锁会提前释放让新任务闯入；超时过长则会导致任务异常退出后锁长时间不释放，造成“假死”。建议先用监控数据跑一周再固定。
2. **锁未释放的死锁**：即使使用 `try-finally`，进程收到 SIGKILL 时 `finally` 不会执行。文件锁随进程退出而释放相对安全；Redis 锁则完全依赖过期时间，务必设置 `EX` 并做好监控。
3. **多环节竞争**：有的 Agent 内部还会调用 MCP 工具，这些工具本身可能也需要锁。注意锁的粒度——用同一个锁键避免嵌套等待，或采用可重入锁设计。
4. **日志淹没**：频次较高的任务会在锁冲突时疯狂打印日志。获取失败时可采用 **指数退避记录** 或仅每 10 次记录一次，避免磁盘 I/O 拖垮 Agent。
5. **环境隔离**：锁键务必包含工作区、环境标识（如 `dev/prod`），防止不同环境互相干扰。

## 可复用建议

- **封装成通用装饰器 / Skill**：将上锁逻辑抽象为 OpenClaw 的一个 `pre_action` 插件，任何 Agent 只需在配置中声明 `lock: redis_task` 即可启用。
- **搭配心跳续期**：对于执行时间波动极大的长任务，可以在任务内定期延长锁过期时间，避免意外超时。
- **报警至上**：在获取锁失败的退出点埋入指标，当拒绝次数连续超过阈值时触发告警。不要等到数据错乱才发现任务已经撞了一整天。
- **从设计上减少重入概率**：如果任务执行时长接近或超过间隔，优先评估能否增大定时间隔，或改为事件驱动触发，而非单纯依赖锁。

## 总结

定时任务的“撞车”是分布式调度的经典问题，在 OpenClaw 这类灵活的 Agent 编排环境里更容易被忽视。实现防重入锁的成本极低——几行代码、一个键值对或一个文件，却能避免深夜告警和脏数据回溯的噩梦。无论你选择文件锁还是 Redis，核心逻辑始终只有三条：**执行前获取、失败即放弃、执行后释放**。配上合适的超时和监控，你的 5 分钟任务就能告别随机撞车，平稳运行在生产线上。
