## 背景

自动发帖流水线已经能稳定产出格式规范的 Markdown 文章和配套图片，不少实践者会把这一串流程接到发布步骤就收工。但一个容易被忽略的问题是：**生成物只在临时目录或内存中流转，缺少结构化的本地存档**。一段时间之后，想要回溯某篇文章的完整素材、核对图片是否被篡改、或者在另一个环境复现发布，就会变得非常痛苦。

对 OpenClaw / Agent / MCP / 插件这类自动化体系的用户来说，归档不是一个“锦上添花”的特性，而是流水线工程化的必要组成。它让每次生成的结果可追溯、可复现，也为后续的再发布、本地预览、个人知识库建设提供基础。

## 问题

- **素材散落**：文章是独立的 `.md`，图片可能放在系统 `/tmp`、远程 CDN，或者某个临时 oss bucket，清理后资源丢失。
- **关联不清**：一篇帖子到底用了哪几张图、每张图对应的 alt 文本是什么，全靠跑一遍原文才能提取，无法快速索引。
- **元数据缺失**：标题、slug、生成时间、图片哈希等信息没有统一记录，只能靠文件名或文件夹名猜测。
- **重发或迁移成本高**：迁移到新平台、重新生成不同尺寸缩略图时，本地没有可靠的源文件，只能从线上爬图或重跑整个生成流程，效率低且容易出错。

## 做法：建立以文章 slug 为维度的本地归档

### 1. 约定目录结构

每篇文章的归档使用一个独立文件夹，以 `slug` 命名。推荐结构：

```
posts/
  why-auto-archive/
    index.md          # 文章正文，内部图片引用使用相对路径
    assets/           # 文章专属图片资源
      hero.png
      diagram.png
    assets.json       # 元数据 & 资源清单
```

`index.md` 是原始文章，图片引用全部使用 `./assets/xxx.png` 的相对路径。这样整个文件夹可以独立被任何 Markdown 渲染器打开，不依赖外部路径。

### 2. 归档流程拆解

在自动发帖流水线中，把归档模块做成一个独立步骤，可放在“生成完成之后、发布之前”或“发布之后”，具体看你是否需要将发布结果也一并存档。核心逻辑如下：

1. **确定 slug**：从文章标题或生成时指定的标识符生成。
2. **创建归档目录** `posts/<slug>/`，若存在则考虑是否覆盖或报错。
3. **处理图片**：
   - 读取 Markdown 中的图片链接（正则 `!\[.*\]\((.*)\)`）。
   - 若图片在本地临时目录，复制（或移动）到 `assets/` 中；若图片来自远程，先下载并校验哈希后再保存。
   - 将正文中的图片链接统一重写为相对路径 `./assets/filename`。
4. **写入 `index.md`**：保存重写图片路径后的文章。
5. **生成/更新 `assets.json`**：记录文章元数据，以及每张图片的文件名、alt 文本、sha256 等信息。
6. （可选）将整个文件夹纳入 Git 版本控制，提交时用 `slug` + 日期作为 commit message。

### 3. `assets.json` 的 schema 建议

不搞过度设计，一个够用的最小结构：

```json
{
  "title": "Why Auto-Archiving Matters",
  "slug": "why-auto-archive",
  "created": "2025-03-15T10:00:00Z",
  "updated": "2025-03-15T10:05:00Z",
  "images": [
    {
      "file": "hero.png",
      "alt": "OpenClaw agent writing into a folder",
      "sha256": "b2e8f...",
      "width": 1200,
      "height": 630
    }
  ],
  "tags": ["automation", "openclaw"]
}
```

这样做带来的好处是：不需要打开 Markdown 文件就能拿到完整的资源清单，方便做预览列表、批量校验完整性，或者作为未来知识库的索引入口。

## 踩坑点

### 图片路径跨平台问题

Windows 和 macOS/Linux 的路径分隔符不同，直接拼接很容易出乱子。统一使用正斜杠，并且在归档时显式调用 `path.posix` 风格的处理逻辑。另外，Markdown 里的图片链接可能有各种写法：绝对路径、带 query 参数的 URL、甚至 base64。正则解析需要覆盖主要场景，对于 base64 图片建议直接 decode 存成文件，否则 `assets.json` 会异常臃肿。

### 重复归档与覆盖策略

如果同 slug 的文章重新生成，你是选择完全覆盖旧文件夹，还是追加版本号？简单场景下，覆盖并更新 `assets.json` 最省事；但如果需要保留历史版本，可以在 slug 后加时间戳或在 `assets.json` 中加入 `generation` 字段。要避免的是：仅部分覆盖导致新旧文件混在一起，图片引用可能指向已经被删除的旧文件。

### 并发写入 `assets.json`

在批量归档或 Agent 并发调用时，多个进程可能同时写入同一个 `assets.json`。最简单的方案是使用原子写（先写临时文件再 rename），并使用写锁或者单线程队列。如果是 Node.js 实现，可以用 `write-file-atomic` 或类似库。

### 大图片和存储膨胀

如果文章引用了大量高清图片，本地归档的体积会迅速增长。建议在归档时生成一份压缩版本（如长边不超过 2400px），将原图命名为 `*-original`，主引用保留对压缩图的重写。这样可以兼顾本地预览性能和存储成本，原图在需要时仍然可以找回。

## 可复用建议

- **将归档实现为独立命令或 MCP tool**：接收 `{markdown, images[], metadata}` 入参，执行上述步骤，返回 `{slug, archivePath, assetList}`。这样任何 Agent 或流水线都能直接调用，不必每个项目重复造轮子。
- **与发布流程解耦**：归档逻辑不应混在发布逻辑里。写一个专门的 `archive` 步骤，无论是 CLI、GitHub Actions、还是容器化环境，都可以独立执行。
- **借助 Git 做历史追溯**：把 `posts/` 目录作为独立仓库或在主项目里作为一个子模块，提交时只包含归档内容，commit 信息带 slug，等于拥有了一份完整的发布历史。
- **用 CI 做完整性校验**：跑一个简单的 lint 脚本，检查所有 `assets.json` 中的文件是否真实存在，sha256 是否匹配。这能避免磁盘损坏或误删带来的静默错误。

## 总结

自动发帖流水线做到“能发”只是及格线，让生成结果有落地的本地归档才是走向工程化的关键一步。通过约定目录结构、重写图片路径、生成标准化 `assets.json`，并处理好路径、并发和存储等坑，可以低成本地构建出稳健、可迁移的离线存档体系。这对个人知识管理、团队协作、以及流水线的长期维护，都有实打实的价值。
