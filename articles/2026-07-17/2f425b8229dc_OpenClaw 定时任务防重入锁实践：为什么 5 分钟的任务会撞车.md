## 背景：定时任务“以为自己空窗，实际在追尾”

在 OpenClaw 或类似 Agent 自动化框架中，定时触发的任务是家常便饭：每 5 分钟拉取一次消息队列、每 10 分钟做一次数据清洗、每小时调用一次 MCP 工具刷新外部缓存。当任务的平均执行时间远小于间隔，一切风平浪静。

问题出现在任务执行时间**偶然或经常性超过调度间隔**时。一个每 5 分钟运行一次的流水线任务，单次执行可能因为下游 API 限速、锁竞争或模型推理排队而拉长到 7 分钟。此时经典场景诞生：

- 第 0 分钟，Task-A 开始执行，预计 5 分钟完成，实际跑了 7 分钟。
- 第 5 分钟，调度器准时拉起 Task-B，发现 Task-A 还在跑，两者并行运行。
- 两个实例同时处理相同资源，引发重复消息推送、数据覆盖、外部服务超限熔断等一系列“撞车”后果。

这种**重入（reentrancy）**在单进程调度下可能仅仅消耗额外内存，但在多 worker、Kubernetes CronJob 或分布式 Agent 部署中，往往演变成数据竞争和资损。下面以一次实际排查为例，拆解 OpenClaw 定时任务如何引入防重入锁，以及为什么锁没加好反成新的事故源。

## 问题拆解：两层重叠与隐性假设

首先明确撞车的两层重叠：

1. **时间重叠**：前一个实例尚未退出，后一个实例已被触发，二者执行窗口有交集。
2. **资源重叠**：两个实例操作同一外部资源（数据库同一行、同一个 MCP 工具实例、同一批文件）。

很多团队第一反应是“任务耗时很短，不会重叠”，但这个假设在负载波动、网络抖动和远程工具调用增加时脆弱不堪。另一个常见误区是把调度周期改成“固定延迟”（上一个完成再启动下一个），这在单 worker 场景有效，但在分布式调度或多 pod 环境中，不同 worker 间没有统一的内存状态，仍可能并发执行。

因此需要一个**分布式防重入锁**，让同一任务在任何时刻只有一个实例在跑。

## 做法：为任务套上分布式锁

在 OpenClaw 的 agent 任务中，我们接入了 Redis 实现简单可重入的排他锁。基本思路：

1. 任务启动时尝试获取锁，使用 `SET lock_key unique_value NX PX lock_timeout`。
2. 如果获取成功，写入自己的唯一标识（如 `uuid`），并设置合理的锁超时时间。
3. 如果获取失败，说明已有实例在执行，当前任务直接退出并记录日志。
4. 任务正常结束时，用 Lua 脚本比对 `value` 后删除锁；若异常退出，锁会在超时后自动释放，防止死锁。

**代码示例（Python + redis-py）**：

```python
import uuid
import redis

LOCK_KEY = "cron:task:daily_sync"
LOCK_TIMEOUT = 600  # 10 分钟，略大于预计最长执行时间

def acquire_lock(r: redis.Redis) -> str | None:
    identifier = str(uuid.uuid4())
    acquired = r.set(LOCK_KEY, identifier, nx=True, px=LOCK_TIMEOUT * 1000)
    return identifier if acquired else None

def release_lock(r: redis.Redis, identifier: str):
    # Lua 保证原子性
    script = """
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
    else
        return 0
    end
    """
    r.eval(script, 1, LOCK_KEY, identifier)
```

在实际工程中，我们将这个锁封装为一个装饰器或任务中间件，对已有的 `@schedule` 任务无侵入接入。

## 踩坑点：锁超时、异常处理和长任务抑制

然而真正应用时，以下几个坑会让“防重入锁”自己变成故障源。

### 1. 锁超时时间难以拍定
`LOCK_TIMEOUT` 必须比任何可能的最大执行时间都长，否则前一个任务还在正常跑，锁却过期，第二个任务就会闯入。设定过长又会导致任务异常崩溃后迟迟不释放锁，后续调度全部失败。实践中的折衷是：

- 基于历史监控取 P99 执行时间为基准，乘以 2～3 倍作为超时。
- 搭配**续期机制**：如果任务执行接近超时仍未结束，由后台线程对锁进行 `pexpire` 延长，但需保证只有持有锁的实例可以续期。过度复杂的续期逻辑不如直接加大超时时间，但必须配合监控。

### 2. 异常未释放锁导致“一死全挂”
如果任务内部抛出未捕获异常，锁释放代码可能被跳过。需要确保 `release_lock` 始终在 `finally` 块中执行，或利用上下文管理器。

但更隐蔽的是进程被 `kill -9` 或 OOM 杀死，锁不会被主动删除。此时只能等待锁超时自动释放。因此超时时间必须覆盖异常场景下的恢复窗口，并且监控锁持有时间，及时告警。

### 3. 锁粒度与任务分组
一个锁对应一个逻辑任务。如果多个不同任务操作同一资源，应将锁键设在资源层（如对某 MCP 设备的互斥访问），而不是单纯按任务名区分。我们曾遇到“两个看似不同的定时任务，实则在同一个外部工具上做了写操作”，最后为工具实例维度加锁。

### 4. 锁获取失败后的行为
简单丢弃任务不一定正确。有些任务需要保证“至少一次执行”，可降级为延迟重试或放入死信队列。但要防止无限重试引发的雪崩。我们在锁获取失败时记录事件，如果连续 N 次失败则触发告警，而不是静默跳过。

## 可复用建议

- **不要只依赖调度间隔**：只要任务执行时间可能 > 调度间隔，就需要防重入设计。
- **Redis 锁是成本最低的起点**：如果你的 Agent 已经依赖 Redis 做缓存或消息，可以自然引入分布式锁。
- **锁时间窗口要监控**：对 `lock timeout` 设置黄金指标，若锁实际持有时间接近或超过设定值，需要告警和调整。
- **单进程内也要小心**：即使只用 threading 或 asyncio，也可以通过文件锁或内存标志避免协程级重入，但跨进程必须用外部锁。
- **测试异常路径**：用 chaos engineering 的思路，手动 kill 任务进程，查看锁是否在预期时间内恢复，验证自愈能力。

## 总结

“5 分钟任务撞车”的本质不是调度器不可靠，而是**执行时间不确定**碰上**固定频率调度**产生的并发窗口。为 OpenClaw 定时任务加上分布式防重入锁，可以低成本解决大部分重叠执行问题。但锁本身引入了新的分布式状态，需要谨慎设计超时、异常释放和监控。锁用好了是防止撞车的安全带，用不好就成了勒死调度的绳索。在 Agent 自动化越来越长的任务链中，最后一道防线永远是：**用监控说话，别靠估算**。
