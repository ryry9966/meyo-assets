## 背景

在日常运营或个人自动化需求中，将内容同步到微博超话是一个常见但繁琐的操作。尤其当需要附带图片、避免触发频率限制，并维护一个可追溯的发布记录时，纯手工几乎无法稳定执行。我们基于 OpenClaw 生态中的 Agent 与 MCP 插件，构建了一套无头浏览器内运行的自动化发布管线，实现了图片上传、超话发帖、限流退避与状态归档的闭环。

本文不涉及具体的产品名或第三方平台账号，只描述技术实践过程，面向有类似需求的自动化和插件开发者。

## 问题拆解

微博超话的发帖流程包含几个关键步骤：

1. **登录态维护**：需要保持有效的 Cookie，否则所有接口均会返回 403。
2. **图片上传**：发帖前必须先将图片上传到微博图床，获取 pid（图片标识），才能在发帖 json 接口中引用。
3. **超话发帖接口**：POST 到 `https://weibo.com/ajax/statuses/update`，携带文本、图片 pid、超话 id 等参数。
4. **频率限制**：对同一超话短时间高频发帖会触发“操作太频繁”错误，需要退避策略。
5. **状态归档**：每次发布成功或失败都需要记录，便于事后统计和重试。

手工处理这些问题很容易遗漏 Cookie 过期、图片上传失败、429 限流等异常。我们的目标是构建一个 Agent 工作流，通过编排 MCP 工具和脚本，实现端到端的自动化。

## 做法与步骤

### 1. 环境准备与 Cookie 注入

我们使用 Playwright 驱动一个 Chrome 实例。启动后先导航到微博首页，通过 `page.evaluate` 注入预先从浏览器导出的 Cookie 字符串。注意 Cookie 必须包含 `SUB`、`SUBP`、`login_sid_t` 等关键字段，且域设置为 `.weibo.com`。注入后刷新页面，验证登录状态。

### 2. 图片上传流程

图片上传接口为 `https://picupload.weibo.com/interface/pic_upload.php`，需要以 `multipart/form-data` 形式提交。关键参数：

- `mime`：`image/jpeg` 或 `image/png`
- `data`：base64 编码的图片数据
- `cb`：jsonp 回调函数名，可固定为 `httpupload`

请求必须携带完整的 Cookie 和 Referer（通常为 `https://weibo.com/`）。接口返回的 json 中需提取 `data.pics.pic_1.pid`，这就是图片 pid。我们封装了一个 MCP 工具 `upload_image_to_weibo`，输入本地图片路径，返回 pid 或错误信息。

> 踩坑点：直接上传非 Base64 编码的二进制文件时，部分图片会被微博压缩服务拒绝，提示“图片类型不支持”。最终统一采用 Base64 后再上传，成功率大幅提升。

### 3. 超话发帖

发帖接口采用 Ajax 格式，请求体为 `application/x-www-form-urlencoded`。核心参数：

- `content`：文本内容，需进行 URL 编码
- `pic_id`：上一步获得的 pid，多个用逗号分隔
- `visible`：0（公开）
- `topic_id`：超话 id，从超话页面 URL 可获取，例如 `100808xxxxxxxxx`

请求头中需携带 `X-Requested-With: XMLHttpRequest` 和 `Referer`。接口返回 `ok: 1` 表示成功，否则解析错误信息。

### 4. 限流应对

发帖成功后，Agent 会监控返回的 HTTP 状态码和 body 中的 `msg`。如果出现“操作太频繁，请稍后再试”，则进行退避：

- 第一次收到限流，等待 30 秒后重试
- 第二次等待 90 秒
- 第三次等待 180 秒
- 超过三次则记录失败，归档并通知人工介入

通过在 Agent 的状态机中维护一个 `rate_limit_counter`，可以实现平滑的自动退避，而不会打断整个发布队列。

### 5. 状态归档

每次发帖无论成功或失败，都会在本地 JSON Lines 文件中追加一条记录：

```json
{
  "timestamp": "2025-01-12T14:23:01Z",
  "topic_id": "100808xxx",
  "content_hash": "sha256...",
  "image_pids": ["pid1", "pid2"],
  "status": "success",
  "response": {"ok": 1, "id": "46254xxxx"}
}
```

失败记录会额外包含 `retries` 和 `last_error`。这个归档文件既可以用于重复发布的去重，也能作为后续审计或数据分析的输入。

### 6. 集成到 Agent 工作流

整体编排使用 OpenClaw 的 tool-use 循环：LLM 根据用户指令（如“将这篇草稿发布到指定超话”）生成调用计划，依次调用 `upload_image_to_weibo`、`post_to_topic`，并根据返回决定是否重试或归档。状态管理全部由 agent 状态树承载，配合 MCP 服务器的资源读写实现了全自动闭环。

## 踩坑点总结

- **Cookie 过短**：注入的 Cookie 如果没有 `login_sid_t` 字段，图片上传会失败，但页面浏览可能是登录态，容易误判。建议注入后立即访问一次 `https://weibo.com/aj/account/watermark` 验证。
- **图片大小限制**：单张图片超过 5MB 或分辨率过高可能被转码，导致 pid 临时失效。实际测试控制在 3MB、1920px 以内比较稳定。
- **Referer 缺失**：发帖和上传都必须带有正确的 Referer，否则易触发 302 重定向或反爬。
- **超话 id 并非固定数字**：某些超话的 topic_id 是十六进制字符串，不能简化为数字，否则接口返回“话题不存在”。

## 可复用建议

对于有类似需求的开发者，可以将上述能力抽象为可复用的 MCP 工具集：

- `weibo_login`: 维持登录态，自动续期。
- `weibo_upload_image`: 本地图片 -> pid 。
- `weibo_post_to_topic`: 文本 + pid + topic_id -> 发帖结果。
- `weibo_rate_limiter`: 内置退避逻辑，便于组合调用。

这些工具可被任何 agent 或脚本调用，无需重新实现 Cookie 管理和限流逻辑。

## 总结

微博超话的自动化同步完全可以通过无头浏览器+API 模拟的方式工程化实现，关键在于正确维护 Cookie、处理图片上传的格式细节以及构建可靠的限流退避机制。配合状态归档，整个系统能够长期无监督运行。我们将这套流程嵌入 OpenClaw 的 Agent 工作流后，日常的同步任务耗时从 15 分钟/次降低到无人值守，且出错时可精确恢复。

这套思路也可迁移到其他社交平台的自动化发布中，区别仅在于接口认证方式和请求参数的差异。希望本文能为正在构建内容分发自动化的朋友提供一些踏实的参考。
