## 背景

用OpenClaw或Agent搭建自动发帖流水线的同学，通常会关注生成质量、多平台适配、发布频率，但很少有人认真做**内容资产本地归档**。常见的情况是：文章发完就留在平台上，图片靠外链，元数据散落在日志里。等哪天需要回溯某篇文章用了哪些图、排查被平台删改的内容、或者想迁移到新发布渠道时，才发现手边只有一堆不可靠的URL，复现成本极高。

本地归档的价值不只是备份，更在于**让生产流水线可审计、可复现、可复用**。这篇文章分享一套轻量但工程化的做法，把文章正文、图片以及结构化元数据（assets.json）统一落地到本地文件系统。

## 要解决的具体问题

- 文章Markdown中引用的图片往往是外链（AI生成图的临时URL、公共图床等），链接随时可能失效。
- 图片没有尺寸、用途等元数据，二次加工时需要人工检查。
- 代理生成的同一篇文章可能被多次修改，缺乏版本锚点。
- 需要一种简单、脚本友好、不依赖数据库的归档格式，方便与Git或rsync配合。

## 做法与步骤

### 1. 约定归档目录结构

每次发布任务生成一个独立目录，以日期+主题slug命名：

```
archives/
└── 2025-03-21_auto-post-pipeline/
    ├── post.md
    ├── assets.json
    └── images/
        ├── cover.png
        ├── diagram-01.png
        └── ...
```

- `post.md`：最终要发布的Markdown正文，其中的图片路径已经替换为相对路径 `./images/xxx`。
- `images/`：所有引用到的图片本地副本。
- `assets.json`：记录每张图片的元信息及归档任务的整体信息。

### 2. 在流水线中插入归档环节

归档动作应该发生在**文章生成完成、准备发布之前**（或发布成功后立即执行）。你可以在CodeAct Agent的工具链中增加一个“本地归档”函数，或者通过MCP Server暴露一个 `archive_content` 工具。

核心逻辑如下：

1. 解析Agent生成的Markdown内容，提取所有图片链接 `![](url)`。
2. 对每个图片URL执行下载，保存到 `images/` 目录下。文件名建议用内容哈希（sha256前12位）或 `uuid`，避免重名覆盖。
3. 在下载的同时记录原始URL、本地文件名、图片尺寸（可用PIL或sharp）、alt文本（从Markdown解析）、用途（如果文件名或上下文能推断，如cover/banner/body）。
4. 将Markdown中的图片URL替换为 `./images/xxx.png`。
5. 构建 `assets.json`，写入结构化信息，并连同 `post.md` 一起落盘。

`assets.json` 的结构可以参考：

```json
{
  "generated_at": "2025-03-21T10:30:00Z",
  "title": "自动发帖流水线实践",
  "source_model": "gpt-4.1",
  "images": [
    {
      "filename": "cover.png",
      "original_url": "https://...",
      "width": 1200,
      "height": 630,
      "alt": "封面图",
      "purpose": "cover"
    }
  ]
}
```

### 3. 集成到OpenClaw工作流

如果你在OpenClaw的Agent逻辑中组装内容，可以把它组织成以下流水线节点：

- **ContentGenerator** → 输出 `{ title, markdown }`
- **ImageDownloader** → 拉取外部图片，返回 `{ local_paths, metadata }`
- **ArchiveBuilder** → 替换路径、生成 `assets.json`、写入归档目录

建议将 `ArchiveBuilder` 封装为一个独立MCP工具，由Agent在完成内容生成后显式调用，参数就是已经组装好的结构化对象。这样做的好处是归档行为独立、可测试、可替换。

## 踩坑记录

- **图片下载超时或403**：有些图床有防盗链，需要设置 `User-Agent`，或使用 `referer`。如果不行，则记录失败并保留原始URL，在 `assets.json` 中标为 `download_failed: true`，方便后续人工处理。
- **Markdown中的图片链接形式多样**：有的用HTML `<img>` 标签，有的带查询参数，正则提取要覆盖这些情况。实践中建议用markdown解析库先提取AST节点，再取URL。
- **命名冲突**：同一文章里可能出现来自不同URL但文件名相同的图片（如都叫 `image.png`），所以必须生成唯一文件名，不要直接沿用原始文件名。
- **大图片存储膨胀**：对于信息密度不高的截图，可以在下载后转码为WebP或者做无损压缩，但必须保留 `original_url` 以备查验。
- **并发归档**：若多条流水线并行，写入同一目录时需要加锁或确保目录名包含唯一标识（如UUID），避免交叉覆盖。

## 可复用的工程建议

1. **归档工具做成无状态函数或MCP Tool**，输入标准化的 `ArchivePayload`，输出 `ArchiveResult`，方便单元测试与复用。
2. **用Markdown front matter 记录归档ID**，例如在 `post.md` 头部添加 `archive_id: 2025-03-21_auto-post-pipeline`，这样即使文章被拷贝到别处，也能反向定位原始归档。
3. 与Git工作流结合：每次归档后自动执行 `git add` 和 `commit`，message格式 `archive: 2025-03-21_auto-post-pipeline`，形成自然版本历史。
4. 定期将老旧归档目录移动到低成本存储（如对象存储冷层），本地只保留最近30天，平衡空间和可追溯性。

## 总结

给自动发帖流水线加上本地归档，投入不多（几十行脚本或一个MCP工具），但解决了“内容资产飘在云端”带来的长期风险。文章、图片、元数据统一沉淀在文件系统里，不仅方便审计和重发，也为后续基于历史内容的二次加工（比如重新裁剪封面图、提取关键素材）提供了结构化基础。

对于已经在使用OpenClaw或类似Agent框架的团队，这套归档模式几乎是“即插即用”的：用现有Tool/MCP机制封装一个归档逻辑，配置归档根目录，然后剩下的就交给流水线自动完成。别再等到某个关键图片链接404才想起来补救了。
