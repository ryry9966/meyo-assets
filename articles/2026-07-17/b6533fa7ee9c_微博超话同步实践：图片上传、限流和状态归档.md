## 背景

用 OpenClaw 搭建内容分发管线时，有一个很常见的需求：博客文章、产品动态发布后，自动同步到对应的微博超话。相比在官方客户端手动操作，管线能省下大量重复劳动，也能保证发布格式统一。

然而微博并没有给普通开发者提供超话发帖的开放 API，整个流程都需要模拟 Web 端行为：走图片上传 → 获取 pid → 带上超话 ID 和文本请求发帖接口。同时还会遇上两个工程难题——**限流**和**状态管理**。图片一多就可能被暂时封禁，没有状态记录则容易重复发帖甚至死循环。

经过三个月的实际运行，管线已经把“从 RSS 抓取到超话发布”的整套链路稳定下来。这篇文章记录其中的关键环节：图片上传的实现、限流策略以及状态归档的设计，面向已有 OpenClaw 或 MCP 使用经验、想做类似自动化的同学。

---

## 问题拆解

超话同步至少要解决四个问题：

1. **图片上传**：必须拿到 `pid` 才能嵌入帖子，而微博图片服务对 Cookie、请求格式、文件大小都有要求。
2. **超话发帖**：需要定位到正确的超话 ID，并构造一个包含文本、图片 `pid`、来源标识的请求。
3. **限流应对**：短时间多次请求会触发图形验证码或账号临时限制，必须有退避和延时。
4. **同步状态归档**：防止同一篇内容被反复发布，一旦管线重试或重启，能从上次断点继续。

下面按实践顺序展开。

## 做法 / 步骤

### 1. 捕获并分析请求

没有文档可参考，先用浏览器开发者工具手动在超话发一条带图片的帖子，沿 Network 面板记录下两个关键请求：

- **图片上传**：`POST https://picupload.weibo.com/interface/pic_upload.php`
- **发帖**：`POST https://weibo.com/aj/mblog/add?ajwvr=6`

将请求头、Form Data 全部导出。重点关注 `Cookie`、`Referer` 以及图片上传返回的 `pid` 字符串。

### 2. 用 OpenClaw 的 HTTP 节点模拟图片上传

在 OpenClaw 里使用 **HTTP Request 节点** 模拟上传操作。关键配置：

- **Method**：`POST`
- **URL**：`https://picupload.weibo.com/interface/pic_upload.php`
- **Headers**：
  - `Cookie`：从环境变量 `WEIBO_COOKIE` 读取
  - `Referer`：`https://weibo.com/`
  - `Content-Type`：`multipart/form-data`
- **Body (form-data)**：
  - `pic1`：文件内容（使用上一步下载好的图片 url 转换成的二进制），文件名保留原后缀
  - `mime`：`image/jpeg` 或 `image/png`
  - 其他固定参数，如 `data`、`url` 等直接从抓包复制

上传成功后，响应体会包含 `<pid>...</pid>`，用 **JSON/XML 解析节点** 提取出 `pid`。

> 注意：微博 `pic_upload.php` 要求 `pic1` 作为字段名，不可写成 `pic`，否则会无响应。

### 3. 构造超话发帖请求

发帖节点同样使用 HTTP Request：

- **URL**：`https://weibo.com/aj/mblog/add?ajwvr=6`
- **Headers**：`Content-Type: application/x-www-form-urlencoded; charset=UTF-8`，带上同一个 Cookie
- **Body (x-www-form-urlencoded)**：
  - `text`：帖子正文，末尾附加超话标识 `#超话名称#`
  - `pic_id`：上一步取到的 `pid`
  - `topic_id`：超话 ID，需要提前从超话页面 URL 或 DOM 里获取
  - `rank`：0
  - 其他固定字段与 `_t` 时间戳

这一步请求成功会返回 JSON，包含帖子 ID。

### 4. 加入限流控制

经验表明，**单账号每分钟发帖不宜超过 2 条**，图片上传频率也不能太高。我在 OpenClaw 工作流中加入了两个控制点：

- **延时节点**：每处理一条同步任务后，固定延时 45–60 秒，避开风控窗口。
- **错误重试与退避**：如果返回状态码 302（要求登录）或返回包含 “验证码” 的响应体，暂停该超话发布 30 分钟，并将任务标记为 `rate_limited`。

用 OpenClaw 的条件分支很容易实现：若检测到限流标志，则转到延时 30 分钟的 Wait 节点，结束后再重新尝试。

### 5. 状态归档：用 SQLite 做幂等控制器

在 OpenClaw 中引入一个 **SQLite 节点**（或自建 API），设计一张表：

```sql
CREATE TABLE sync_log (
    source_url TEXT PRIMARY KEY,
    weibo_post_id TEXT,
    status TEXT,  -- pending, success, rate_limited, failed
    created_at INTEGER,
    updated_at INTEGER
);
```

每次准备同步前，先去 `sync_log` 里以 `source_url` 为键查询：

- 如果已有 `success` 记录，跳过。
- 如果 `rate_limited` 且 `updated_at` 距今小于 30 分钟，跳过。
- 否则进入发布流程，发布成功后将 `status` 更新为 `success`，并写入 `weibo_post_id`。

这样做实现了**幂等**：管线重启、重试都不会重复发帖。

## 踩坑点

1. **Cookie 定期失效**：微博 Web 端 Cookie 有效时间短，尤其是 `SUB` 这条。最初硬编码，一周就失效。改为接入扫码登录流程，通过 MCP 工具每 12 小时自动刷新并写入环境变量，大幅降低人工维护成本。
2. **图片大小和格式**：超过 5MB 或非 JPEG/PNG 的图片，上传接口会直接返回空 `pid`，但没有明确错误提示。因此在上传前增加图片压缩和格式校验节点，避免浪费时间。
3. **超话 `topic_id` 不是固定的数字**：部分超话 ID 需要通过页面源码解析，而非 URL 中的数字串，遇到异常可参考页面 `<script>` 里的 `topic_id` 变量。
4. **频繁请求导致账号风控**：一旦触发图形验证码，短期内所有自动化都会中断。限流不要依赖固定间隔，结合失败反馈动态延长冷静期更可靠。

## 可复用建议

- **抽象为 MCP 工具**：把图片上传、发帖和状态查询封装成一个 `weibo-supertopic` MCP 服务，OpenClaw 只需调用工具即可，不必每次都拼请求。
- **配置驱动**：超话列表、Cookie、频率限制等全部配置化，方便迁移到新项目或新账号。
- **队列削峰**：如果内容源一次性产生大量待同步文章，不要直接全量推送，使用消息队列（如 Redis List）并以固定速率消费。
- **监控告警**：为 `rate_limited` 和 `failed` 状态设置钉钉或 Slack 通知，避免“静默断更”很久后才发现。

---

## 总结

微博超话同步的难点不在于发帖本身，而在于如何在非开放接口和反爬策略下保持长期稳定。通过模拟上传、动态限流和状态归档，OpenClaw 管线已经连续运行 90 多天未出现大规模断更。这套设计不限于微博，对于任何需要保持会话、管理状态的自动化发布场景都有参考价值。如果你也在用 Agent 或工作流做类似的事，不妨先从这三块（上传、限流、归档）入手，把基座打牢再扩展其他功能。
