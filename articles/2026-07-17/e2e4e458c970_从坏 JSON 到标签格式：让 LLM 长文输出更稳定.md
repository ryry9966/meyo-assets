# 从坏 JSON 到标签格式：让 LLM 长文输出更稳定

## 背景：长文结构化输出的“日常翻车”

在构建基于 OpenClaw 的自动化内容流水线时，我们经常需要让大模型一次性输出**较长的结构化内容**，比如：

- 多段落摘要 + 关键词列表
- 带层级的多步操作报告
- 用于 MCP 工具返回的复杂结果体

最初很自然地选择了 JSON——毕竟下游解析方便、生态成熟。Prompt 里写清楚 schema，让模型返回纯 JSON，结果却发现：**内容一超过 500 字，JSON 就开始变得不可靠。**

典型的问题包括：

- 字符串内部未转义引号，直接打断解析
- 嵌套对象或数组末尾多一个逗号
- 生成到一半截断，缺少闭合的 `}` 或 `]`
- 模型在长文本中“忘记”自己在输出 JSON，突然插入注释或自然语言

这些问题在大批量自动化任务里极其致命：解析失败会导致整个 pipeline 中断，重试又消耗 token 和时间，且重试后仍可能再次失败。于是我们开始寻找一种更**长文友好的结构化方式**，最终落到了**标签格式**上。

## 问题：JSON 为什么在长文里容易崩？

从生成机制看，LLM 是按 token 流式输出的，它对括号匹配和转义规则并不像解析器那样严格校验。当输出较短时，模型还能够“照葫芦画瓢”维持 JSON 形态；一旦文本变长，字符级别的约束（如字符串内的 `"` 需要转义）变得极易被忽略。另外，JSON 的结尾必须有全局闭合符号，流式输出时若中途截断，整个 JSON 作废。

相比之下，**类 XML 的标签格式**有几个关键优势：

- 标签是**文本的一部分**，不需要像 JSON 那样处理引号转义
- 可以按段闭合，**天然支持流式解析**（读到 `</section>` 就能确定一段结束）
- 对模型的生成习惯更友好：交替输出标签和文本，与写 Markdown 类似
- 容错性强：即便缺少某些结束标签，也可以降级提取已闭合部分

## 做法：用标签协议替代 JSON Schema

我们设计了一套轻量标签协议，类似：

```
<summary>
<para>第一段要点...</para>
<para>第二段要点...</para>
</summary>
<keywords>
<item>关键词1</item>
<item>关键词2</item>
</keywords>
```

然后在 system prompt 中明确要求模型**只使用这些标签输出结构化内容**，并提供一个完整的示例。关键步骤：

1. **定义标签协议**  
   保持标签名语义清晰，避免使用可能出现在正文中的常用词。结构尽量扁平，嵌套不超过两层。

2. **重写 Prompt**  
   不仅要说明输出格式，还要强调：“你的输出将被 XML 解析器读取，请严格使用指定标签，不要添加额外解释。”

3. **示例驱动**  
   在 user prompt 中给出一条完整示例，输入一段样例文本，输出符合标签格式的结果。这对模型行为约束非常有效。

4. **流式解析器实现**  
   我们使用简单的正则状态机：遇到 `<section>` 开始收集，遇到 `</section>` 触发回调。解析器只需处理基本闭合，跳过未识别标签，处理不完整标签时缓存并等待后续 chunk。

5. **降级策略**  
   如果最终内容缺失某些结束标签，解析器会按现有闭合标签提取已生成部分，记录警告并尝试补全缺失字段，避免整个任务失败。

## 踩坑点

实践中踩过几个坑，值得注意：

- **正文中出现尖括号**  
  用户输入或生成内容中可能包含 `<`、`>`，会干扰解析。我们采用前缀标签名（如 `::section`）并在 prompt 中要求模型对正文中的尖括号进行转义，或改用特殊标记包裹正文。

- **标签被模型“挪用”**  
  如果提示不充分，模型可能擅自发明新标签或错用标签顺序。解决方案是固定标签集合，并在 system prompt 中加入：“只使用上述标签，不要创建新标签。”

- **要求输出大量重复元素时标签混乱**  
  例如生成数十个 `<item>`，末尾模型可能忘记闭合。此时可要求模型先生成数量少的示例，再在后续用代码补齐，或人工限制最大条目数。

- **迁移成本**  
  原有 JSON schema 的下游消费需要调整成标签解析，但一次编写后即可复用，且解析器远比容错 JSON 好写。

## 可复用建议

根据我们的经验，给出几条可直接落地的建议：

- **协议优先**  
  在项目初期就约定标签结构，沉淀为内部标准，跨 Agent 和工具调用时保持一致。

- **Prompt 中固定示例不可省略**  
  即使标签很简单，也必须给模型一个明确的输出样本，长度可以是 5~6 行。

- **解析器设计成宽松模式**  
  只提取已知标签内容，忽略未知标签和文本节点，强健性远高于严格 XML 解析。

- **日志记录“坏输出”**  
  将解析失败或降级处理的原始输出落盘，定期检查，迭代优化标签协议和 prompt。

- **混合使用**  
  对于简单、长度短的字段，仍可沿用 JSON 作为标签内的一段块（如 `<meta>{"id": "123"}</meta>`），平衡可读性与兼容性。

## 总结

从 JSON 切到标签格式，不是要否定 JSON 的价值，而是在**长文输出**这个特定场景下做出的工程权衡。标签格式牺牲了一定的通用性，换来了**流式解析友好、容错性高、对模型生成更自然**三个关键好处，明显降低了自动化 pipeline 的失败率。

在 OpenClaw 及类似的 Agent 工程中，输出稳定性往往比格式严谨性更重要。如果你也常为 LLM 的长文 JSON 输出抓狂，不妨花一个小时设计一套标签协议，收益可能超出预期。
