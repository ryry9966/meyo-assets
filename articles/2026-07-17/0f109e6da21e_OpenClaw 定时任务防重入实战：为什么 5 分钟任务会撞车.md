## 一、背景：一次看似偶然的“撞车”

在 OpenClaw 的自动化工作流里，我们经常用 Cron 触发器去执行 Agent 任务：每 5 分钟拉取一次外部数据、每 10 分钟做一次状态检查、每小时同步一次配置。这些任务通常被设计得“刚好”在间隔时间内完成。

但某天你会发现，日志里出现了奇怪的并发操作——同一个资源被两个任务实例同时修改，数据出现了错乱，甚至触发了下游的重复通知。检查时间线才发现：上一个任务因为网络抖动或计算量突增，执行了 6 分钟，而下一个任务在第 5 分钟准时启动，两个实例就这样“撞车”了。

OpenClaw 的默认调度并不会检查前一个任务是否还在跑，每次 Cron 触发都会直接启动新的执行体。对于 Agent 或 MCP 工具调用这类有状态操作，这种设计默认就隐藏着并发冲突的风险。

## 二、问题根因：缺少防重入机制

所谓的“防重入锁”（也叫互斥锁、任务去重），本质上就是确保同一个任务在同一时刻只允许一个实例运行。缺失这一层保护，会导致三类典型问题：

- **数据竞争**：两个实例读写同一资源（数据库、文件、外部 API 资源），产生脏写、覆盖或重复创建。
- **资源浪费**：同样的计算重复执行，不仅消耗服务器算力，还可能达到外部服务的限流阈值。
- **状态错乱**：插件或 Agent 内部维护的状态机被并发修改，出现无法预期的逻辑路径。

在 OpenClaw 的架构下，Agent 的执行可能跨越多个插件、多个 MCP 服务，并发执行时状态传播更难排查。因此，在关键定时任务入口加一道锁，是成本最低的保序手段。

## 三、实现方案：两步为任务上锁

下面给出一个适用于 OpenClaw 工程的轻量级方案，使用 Redis 分布式锁（单实例可用内存锁或文件锁，这里以多实例通用的 Redis 为例）。

### 1. 定义锁的统一约定

- **锁键命名**：`lock:task:{task_name}`，让同一个任务名称共享一把锁。
- **锁超时时间**：需大于任务的最大可能执行时间，建议取 `2 * 预期执行时间`，例如原本 5 分钟完成的任务，锁超时设为 10 分钟。
- **锁持有者标识**：用 UUID 或进程 ID 组合，保证释放时只删自己的锁。

### 2. 在任务入口加锁逻辑

在自定义的 Agent 入口函数（或插件处理函数）里，用 `redis.set(key, owner, nx=True, ex=timeout)` 获取锁。如果获取成功，执行任务并在 finally 块中释放；获取失败则记录一条 info 日志后直接返回。

简单示例（Python 版本）：

```python
import redis, uuid, time
r = redis.Redis()

def run_with_lock(task_name, ttl_seconds, func):
    lock_key = f"lock:task:{task_name}"
    owner = str(uuid.uuid4())
    if r.set(lock_key, owner, nx=True, ex=ttl_seconds):
        try:
            func()
        finally:
            # 防止误删他人的锁
            if r.get(lock_key) == owner:
                r.delete(lock_key)
    else:
        logging.info(f"Task {task_name} is already running, skip.")
```

如果使用 OpenClaw 的插件系统，可以把这段逻辑封装成一个装饰器，应用到所有需要防重入的 handler 上。对于 MCP 调用，同样可以在 Tool 定义的最外层包裹这一逻辑。

## 四、踩坑实录：三个容易忽略的细节

### 1. 锁超时时间不合理

设定的 TTL 太短，任务还没跑完锁就过期了，后续任务仍会闯入。但 TTL 太长，任务异常挂死时会长时间阻止新调度。需要在“安全时长”和“故障恢复时间”之间权衡。建议监控任务历史执行时间的 P99，据此调整。

### 2. 未妥善释放锁导致死锁

如果在 `func()` 内部抛出异常，且 finally 块中的释放逻辑没有做“持有者校验”，就可能把别人持有的锁误删。上面的示例中通过比对 owner 解决了这一问题。更保险的做法是使用 Redis 的 Lua 脚本原子化判断与删除。

### 3. 集群环境下不要用本地锁

如果 OpenClaw 部署了多个实例，本地内存锁（例如 `threading.Lock`）只能限制同一进程内并发，无法跨实例互斥。文件锁在共享存储下才有效，更简单的还是切换到 Redis 或数据库锁（如 MySQL 的 `INSERT ... ON DUPLICATE KEY` 模拟）。

## 五、可复用建议

- **统一装饰器/中间件**：在插件框架内封装一个 `@synchronized` 装饰器，配置任务名称与锁超时即可接入，避免到处散落锁逻辑。
- **动态超时策略**：将锁超时与任务执行时间挂钩，例如取近 5 次执行时长均值的 2 倍，比固定值更可靠。
- **可观测性**：在获得锁、释放锁、跳过执行时输出结构化日志，并上报指标（如锁冲突次数、锁等待时间），方便排障。
- **快速失败与排队**：默认策略是“获取不到直接跳过”，适合大多数监控类任务。对于必须执行的划，可改为排队等待模式（如 Redis 的 BLPOP），但需增加超时控制以防堆积。

## 六、总结

定时任务防重入锁是分布式自动化中极容易被忽视的基础设置。一个 5 分钟的定时任务，如果执行时间波动 20%，就可能在一个月里发生上百次并发冲突。在 OpenClaw 的 Agent 和插件开发过程中，给关键 Job 加上一层轻量锁，既能避免数据事故，也能减轻排查负担。

这条规则不仅适用于 Cron 触发，也适用于消息队列、Webhook 回调等任何可能并发执行同一任务的场景。把防重入作为任务定义的一部分，就像给电源加个保险丝——平时不起眼，故障时才有价值。
