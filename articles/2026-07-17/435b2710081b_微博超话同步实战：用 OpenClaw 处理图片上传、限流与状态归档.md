## 背景

在一些内容自动化场景里，我们需要把本地或 AI 生成的图文，定时推送到微博超话。手动操作效率太低，而且容易漏发、重复发。团队之前用 OpenClaw 跑过几个网页自动化流程，于是决定基于它的 Web Agent 能力，搭建一条从“图文就绪”到“超话成功发布”的稳定管道。

真正落地时，问题集中在三块：
- 图片上传：文件尺寸、格式不合规会导致发布失败或图片被压成糊图。
- 限流与风控：微博对超话发帖有明显频率限制，触发后轻则丢弃请求，重则短暂禁言。
- 状态归档缺失：没有记录哪条已发、哪条失败，同步中断后恢复困难，容易出现重复或漏发。

下面记录我们围绕这三个问题的完整实践，重点落在可工程化、可复用的思路上，不依赖特定黑盒。

## 问题拆解

微博超话的发帖流程，本质上是“选超话 → 填文案 → 传图片 → 点发布”。通过 OpenClaw 的浏览器 Agent 可以模拟这一过程，但面临的坑主要来自：

1. **图片限制**：一般超话允许的图片大小在 5MB 以内，但实际上超过 1.2MB 就容易上传失败或转换后再压缩失真。格式方面，虽然宣称支持 PNG/JPG/GIF，但部分场景下非 sRGB 的 PNG 会触发转码丢失透明度。
2. **频率限制**：同一账号在超话中发帖间隔过短，会直接返回“操作过于频繁，请稍后再试”，且连续触发后限制时间指数级增加。这在批量同步时尤其致命。
3. **发布状态不可见**：如果不记录每次发布的结果，出问题后只能靠人工翻微博确认，重试策略无从谈起。

## 实践步骤

### 1. 图片预处理管道

在进入 OpenClaw 之前，先对所有待发图片做统一预处理，确保格式和大小可控。

- 统一转换为 JPEG，色彩空间 sRGB，质量设为 85。
- 长边限制在 2048px 以内，用 LANCZOS 做缩放，避免微博二次压缩引入过强噪点。
- 最终文件大小硬限制在 1MB 以下；若仍然过大，逐步降质量到 70，仍不行则降分辨率到 1600px。
- 预处理后的图片存入 `staging` 目录，供 Agent 直接使用。

这一步完全独立于 OpenClaw，可以复用给任何社交平台。

### 2. OpenClaw Web Agent 实现上传与发布

用 OpenClaw 提供的 Browser Agent，操作超话页面路径：

1. 先进入目标超话首页 `https://weibo.com/p/100808{超话ID}`，等待“发帖”按钮出现。
2. 点击按钮，弹出发帖浮层（或跳转到新页面）。
3. 在浮层内输入文案，通过 `textarea` 选择器定位并填入。
4. 点击“图片”图标，等待文件 `input[type=file]` 出现，直接通过 Agent 的 `upload_file` 动作将本地 staging 图片路径写入，而不是用系统文件选择器。
5. 主动轮询图片缩略图是否渲染完成（检测 `.imgWraper` 内 `img` 加载），超时 30 秒则标记失败。
6. 点击“发布”按钮，监听网络响应或页面提示。

关键踩坑：浮层 DOM 每次可能不同，我们采用多重回退选择器，并给每个动作加上显式等待，避免因网络延迟导致的元素未出现。

另一个坑是 Cookie。长时间运行的 Agent 会遇到 Cookie 过期，需要定时刷新。我们通过 OpenClaw 的会话管理插件，每 6 小时自动走一次手机验证码登录流程，写入新 Cookie，保持会话活跃。

### 3. 限流处理与重试机制

微博的限流信息往往出现在发帖后的 toast 提示或页面文字中。Agent 在点击发布后，会抓取页面新增的文本内容，匹配关键词：

- “操作过于频繁” → 遇到频率墙。
- “发布失败” / “网络错误” → 可能是临时拒绝。
- 成功则会出现“已发送”或直接跳转到微博详情页。

一旦触发频率限制，Agent 不立即重试，而是将当前任务放回队列末尾，并进入冷却。冷却时间初始为 10 分钟，如果 10 分钟后重试仍失败，则加倍到 20 分钟，上限 60 分钟。同时设定一个最小全局间隔（我们设为 30 分钟），即使没有触发限流，也保证相邻两次成功发布间隔不小于该值。这能大幅降低被系统标记的概率。

### 4. 状态归档设计

我们用一个极简的 SQLite 数据库记录每条同步任务：

```
tasks (
  id         TEXT PRIMARY KEY,
  content    TEXT,
  image_path TEXT,
  status     TEXT,   -- queued/uploading/posted/failed
  retries    INTEGER DEFAULT 0,
  post_url   TEXT,
  error_msg  TEXT,
  created_at TEXT,
  updated_at TEXT
)
```

每次发布前将状态更新为 `uploading`，成功后更新 `posted` 并写入帖子链接；失败则记录 `failed` 与错误信息，并根据重试次数决定是否继续。这样在任何时候中断了 Agent，只需重新扫描 `queued` 或 `failed` 且未超最大重试次数的记录即可续传，不会重复发布。

## 可复用建议

- 图片预处理器做成独立 CLI 工具，接收目录和参数，输出标准化图片。这样即便换其他平台（小红书、Twitter）也能复用。
- 发布 Agent 与状态归档解耦：Agent 只负责网页操作，归档读写通过 HTTP API 或本地 SQLite 完成，方便切换成 Redis/PostgreSQL。
- 限流检测模块抽取成策略函数，允许针对不同平台配置不同关键词与冷却策略。
- 所有配置（间隔、质量、超时）都通过环境变量注入，方便在不同账号间调整。

## 总结

整个方案运行三个月，平均每天同步 20 条图文到多个超话，失败率从最初的 35%（手动上传加无冷却）降到 2% 以下。主要支出是 Cookie 维护和偶尔的人机验证，但通过 OpenClaw 的插件体系都做成了自动闭环。

对于类似需求，建议一开始就把图片规范、发布间隔、状态持久化这三个基础打牢，否则后面的自动化会持续被边缘 case 拖垮。微博的规则随时可能微调，保持日志详细和重试策略可配置，是长期维护的关键。
