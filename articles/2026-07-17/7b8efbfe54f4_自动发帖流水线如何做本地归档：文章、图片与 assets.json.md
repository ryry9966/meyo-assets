# 自动发帖流水线如何做本地归档：文章、图片与 assets.json

## 背景

在使用 OpenClaw 或类似 Agent 构建自动发帖流水线时，内容的生产往往以 Markdown 文本和配图的形式产出。发布动作完成后，这些资产要么散落在临时目录，要么仅存在于平台 CDN 上，本地不留痕迹。随着流水线日积月累地运行，很快会遇到几个现实问题：

- 已发布内容难以检索和复用，尤其是同主题的系列文章；
- 排查发布异常时，找不到当时的原始输入；
- 平台策略变更导致图片外链失效，而本地没有备份；
- 想将发过的内容迁移到其他平台，需重新收集素材。

因此，为自动发帖流水线增加一个**本地归档环节**，变得和发布本身一样重要。这不仅仅是存个文件，而是要形成结构清晰、可查询、可复用的内容资产库。

## 问题定义

一条典型的自动发帖流水线，最终产出的通常是：

- 一个 Markdown 文件（文章正文，可能含相对路径的图片引用）；
- 若干图片文件（本地生成的 PNG/JPEG，或第三方生成的 URL）；
- 零散的元信息（标题、标签、发布时间），散落在脚本变量或日志里。

归档的挑战在于：

1. **如何可靠地获取最终状态的内容**？如果在生成过程中就归档，可能与实际发布的内容不一致。
2. **图片资源如何本地化**？远程 URL 可能过期，本地文件也有被后续流程清理的风险。
3. **如何建立文章与资源的映射**？方便后续批量处理。
4. **如何避免文件名冲突和版本覆盖**？

## 方案设计

我们设计一个轻量归档模块，以发布成功作为触发点，完成以下动作：

### 1. 确定归档根目录与命名规则

在项目根目录或指定挂载卷下建立 `archived_posts/`，内部按 `YYYY-MM-DD-slug/` 划分目录。`slug` 从标题自动生成（小写、空格转连字符、去特殊符号）。这样既能避免重名，也便于按时间浏览。

```
archived_posts/
└── 2025-03-15-auto-post-pipeline/
    ├── post.md
    ├── assets/
    │   ├── cover.png
    │   └── diagram.png
    └── assets.json
```

### 2. 收集并标准化内容

在发布成功回调里，将 Markdown 正文重新保存为 `post.md`。这一步的关键是**不处理图片引用**，直接保存原始文本，因为后续归档图片时我们会保持引用路径的一致性。

对于图片，区分两种情况：

- **本地文件**：直接复制到 `assets/` 目录，并确保在 `post.md` 中的引用为相对路径 `./assets/...`（如果不一致，脚本自动修正）。
- **远程 URL**：通过 `fetch` 下载并保存到 `assets/`，文件名从 URL 路径中提取或根据内容哈希命名。

### 3. 生成 assets.json

为每一篇归档生成一个机器可读的元数据文件，核心字段示例如下：

```json
{
  "title": "自动发帖流水线本地归档实战",
  "slug": "auto-post-pipeline",
  "created_at": "2025-03-15T10:30:00Z",
  "post_file": "post.md",
  "assets": [
    {
      "file": "assets/cover.png",
      "original_url": "https://cdn.example.com/cover.png",
      "type": "image/png"
    }
  ],
  "tags": ["automation", "openclaw", "archiving"]
}
```

这份 JSON 不仅记录了所有资源的位置，还保存了原始 URL，方便日后追溯或重新上传。

### 4. 集成到流水线

如果使用 OpenClaw 的流水线配置，可以将归档步骤包装成一个自定义 Action 或 MCP 工具。以 Node.js 脚本为例：

```javascript
// archive-post.js 核心逻辑
const postDir = path.join(ARCHIVE_ROOT, `${dateStr}-${slug}`);
fs.mkdirSync(path.join(postDir, 'assets'), { recursive: true });

fs.copyFileSync(sourceMdPath, path.join(postDir, 'post.md'));
// 图片复制/下载并修正引用
// ...
const manifest = buildManifest(title, slug, date, assetList, tags);
fs.writeFileSync(path.join(postDir, 'assets.json'), JSON.stringify(manifest, null, 2));
```

只要在发帖成功后的 `finally` 或管道出口调用这个脚本即可。对于 Agent 驱动型流水线，也可以通过让 Agent 调用一个 `archive_post` 工具（MCP Server 提供）来完成。

## 踩坑与排障

实际落地时，几个细节容易出错：

- **文件名冲突**：如果一天内多次生成同一 slug 文章（比如重发修正），简单的日期前缀无法区分。解决办法是追加时分或短哈希，如 `2025-03-15-14-23-slug`。
- **图片下载超时/失败**：远程图片可能因为防盗链、CDN 下线等原因无法下载。脚本需做异常捕获，记录失败 URL 到 `assets.json` 的 `fetch_error` 字段，并给出告警，而不是让整个归档流程中断。
- **Markdown 图片引用语法不统一**：有的生成器用 `![](url)`，有的是 `<img>` 标签。正则替换时需覆盖两种情况，避免留下错误的绝对路径。
- **跨平台路径**：在 Windows 运行的流水线，路径分隔符需统一处理为 `/`，否则在 Unix 下读取 `assets.json` 时会出错。
- **大文件问题**：如果文章包含高清大图，归档可能变得臃肿。可以设置图片尺寸上限或转换格式，但这并非归档层该做的事；更好的做法是在生成阶段控制，归档只原样保存。

## 可复用建议

1. **封装成 MCP Server**：实现一个 `archive-content` 工具，接受文章内容、图片列表和元数据，内部完成以上全部操作。这样任何 Agent 或流水线都可以通过标准接口调用。
2. **使用 Git 托管归档**：将归档目录挂进一个 Git 仓库，每次归档后自动 commit。既得到了历史版本，又便于在多台机器间同步内容资产。
3. **加入完整性校验**：归档完成后，自动读取 `post.md` 和 `assets.json` 再回读一遍，确保文件存在、引用有效，并在 CI 中生成简报告警。
4. **与索引系统对接**：归档不应该是终局。可以在归档目录上挂一个简单的静态站点生成器，将 `assets.json` 转换为带预览的索引页，方便日常查找。

## 总结

自动发帖流水线如果只管发布不管留存，就像一个没有仓库的工厂。本地归档看起来简单，却是将自动化内容生产从“一次性运行”转变为“长期资产积累”的关键一步。通过约定的目录结构、一份 `assets.json` 和少量脚本，就能将散落的文章和图片变成可检索、可迁移、可回溯的本地知识库。在多 Agent 协作和频繁迭代的场景下，这种工程化的归档习惯，往往比炫酷的新功能更有用。
