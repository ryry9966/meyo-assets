## 为什么 Agent 需要文件访问护栏

在 OpenClaw 或其他 Agent 框架中，我们经常让自动化脚本直接操作本地文件：生成报表、写日志、读取配置文件、运行代码生成器。这些脚本通常以较高权限运行——否则很多任务没法完成。问题在于，如果不对文件操作加以限制，一个有意或无意的路径遍历就能让 Agent 读到 `~/.ssh` 下的密钥、删掉系统配置，甚至通过 `/proc/self/environ` 泄露敏感环境变量。

“我只跑受信任的脚本”在工程环境中往往不成立。脚本可能由 LLM 动态生成、从 MCP 工具返回的代码片段拼接而成，或者由团队成员临时上传。与其依赖代码审计，不如在文件访问层加一层护栏：**本地目录白名单**。这个思路实现成本低，又能在绝大多数场景下兜住风险。

## 核心问题与目标

目标很明确：只允许 Agent 在指定目录（如 `/data/agent_workspace`）及其子目录内读写文件。任何试图访问白名单外路径的操作都应被拦截并记录日志。

看似简单的“检查路径前缀”在现实文件系统中会遇到几个经典坑：

1. **符号链接绕过** — 用户在允许目录内建一个指向 `/etc/passwd` 的软链接。
2. **相对路径与 `.` `..`** — 脚本传入 `../../etc`，如果不规范化路径，前缀检查形同虚设。
3. **大小写与路径分隔符差异** — Windows/macOS 默认不区分大小写，而 Linux 区分。
4. **白名单根目录自身是符号链接** — 真实路径可能不在预期的位置。
5. **部分操作隐藏的路径问题** — 比如归档解压、文件复制时目标路径未做检查。

## 实现步骤（以 Python/pathlib 为例）

### 1. 定义白名单根目录，并解析为真实路径

```python
from pathlib import Path

WORKSPACE_ROOT = Path("/data/agent_workspace").resolve(strict=False)
```

采用 `resolve()` 会将所有符号链接消解，得到一个绝对且规整的真实路径。如果根目录本身是符号链接，此时得到的已经是目标真实路径，后续比较不会再被绕开。

> `strict=False` 避免根目录不存在时直接抛出异常，你可以按需改为 `strict=True` 强制目录必须存在。

### 2. 构造一个通用的路径验证函数

```python
def is_within_workspace(target_path: str | Path) -> bool:
    """
    将目标路径解析为真实路径，判断是否在 WORKSPACE_ROOT 下。

    注意：如果目标路径不存在（比如写操作即将创建的文件），resolve()
    会将其视为不存在的文件，但仍会基于当前工作目录解析符号链接和 ..。
    """
    target = Path(target_path).resolve()
    try:
        target.relative_to(WORKSPACE_ROOT)
        return True
    except ValueError:
        return False
```

`Path.relative_to()` 在路径不属于给定父目录时会抛出 `ValueError`，这一点比字符串前缀比较更可靠，能避免 `/data/agent_workspace_evil` 这种前缀包含问题。

对于写操作，路径可能尚不存在。此时 `resolve()` 的行为是：对于不存在的最后一级路径，它不会消解其符号链接（因为无链接可跟），但会解析前面所有的中间路径。也就是说，如果用户试图通过中间目录的符号链接跳出白名单，依然会被捕获。不过有一个极端情况：用户先创建了一个符号链接指向白名单外，然后用写操作指向该链接文件。这种情况下 `resolve()` 会跟随链接，从而正确拒绝——所以需要用到 `resolve()` 而不是 `absolute()`。

### 3. 封装安全的文件操作

在实际 Agent 中，你不应该期望所有开发者都手动调用验证函数。更好的做法是提供一套经过包装的文件操作接口。例如：

```python
def safe_read_text(path: str) -> str:
    if not is_within_workspace(path):
        raise PermissionError(f"Access denied: {path}")
    return Path(path).read_text()
```

一次写好，所有脚本统一引入。对于使用 MCP 工具的场景，可以在 MCP server 侧的文件系统工具中内嵌同样的检查逻辑。

### 4. 集成到 Agent 运行时

对于 OpenClaw 插件或 MCP server，通常代理以下操作：

- 文件读写（`read_file`, `write_file`）
- 执行系统命令（`subprocess.run` 内可能包含 `rm -rf`、`mv` 等）
- 解压/打包文件

建议在执行命令时额外限制工作目录，例如：

```python
subprocess.run(cmd, cwd=str(WORKSPACE_ROOT), shell=False)
```

并优先使用绝对路径。如果命令允许参数传递文件路径，同样需要先通过白名单校验后再拼接。

## 踩过的坑

**符号链接无处不在**  
Python 的虚拟环境（venv）内部就有大量符号链接，某些测试框架也有。验证逻辑没用到 `resolve()` 时，脚本可以通过 `venv/bin/python` -> `/usr/bin/python3` 来跳出白名单读取系统文件。换成真实路径比较后，问题解决。

**`os.path.realpath` vs `Path.resolve()`**  
两者都解析符号链接，但 `resolve()` 在路径不存在时仍能解析中间部分。实践中，我们统一使用 `pathlib` 以获得更一致的行为。

**Windows 上的路径分隔符**  
路径比较如果不用 `pathlib`，手写 `commonpath` 在 Windows 上可能因 `\\` vs `/` 而失败。`pathlib.relative_to()` 是平台无关的。

**临时文件与白名单范围**  
有时 Agent 会调用 `tempfile` 模块在系统临时目录创建文件，这显然在白名单之外。需要根据业务判断是否允许只读临时目录，或者强制将临时目录挂载到工作空间内（通过环境变量 `TMPDIR`）。我建议限制临时目录也在工作空间下，避免意外泄露。

## 可复用建议

1. **将白名单检查抽成独立模块**，支持多个目录白名单，而不仅是单一根目录。
2. **为 MCP 文件系统工具增加权限校验层**，在 `read_file`/`write_file`/`list_directory` 的入口统一调用。
3. **记录拒绝日志**，包含时间、请求路径、解析后的真实路径、用户标识（如有），便于发现误拦或恶意操作。
4. **结合操作系统能力做纵深防御**：比如容器挂载 `read-only` 根目录，仅把工作空间挂载为 `rw`；或者使用 Linux 的 `unshare --mount` 给 Agent 进程私有挂载空间。
5. **对解压、复制等复合操作特别小心**，必须验证源路径和目标路径。
6. **在自动化测试中添加绕过检查的用例**：包括符号链接、`..`、绝对路径、特殊情况（如 `/proc/self/cwd`），确保门禁有效。

## 总结

给 Agent 的本地文件访问加目录白名单，本质上是为“脚本可以做任何事”画一个圈。实现起来并不复杂，核心就是 **真实路径解析 + 可靠的父目录判断**。这套机制足以拦住绝大多数目录遍历和符号链接绕过，而代价极小。对于在 OpenClaw 或 MCP 生态里跑自动化任务的团队来说，这是一个低成本、高收益的工程习惯。

在 AI 生成代码逐渐落地的今天，这类护栏不会让 Agent 变得更聪明，但能让它出错时毁不掉你的 `/etc`。
