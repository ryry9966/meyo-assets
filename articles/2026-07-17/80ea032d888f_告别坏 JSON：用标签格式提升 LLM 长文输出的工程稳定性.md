## 背景

在构建基于 LLM 的自动化流程（无论是 OpenClaw 任务引擎、MCP 工具调用，还是 Agent 的多步推理链路）时，最常见的痛点是 **“LLM 输出看似结构化，但解析就跪”**。出于工程直觉，大家的第一选择往往是 JSON——因为它通用、有标准解析器。然而，在**长文输出场景**（例如让模型生成多段摘要、分点分析、结构化报告），JSON 的脆弱性会被急剧放大：多一个回车、少一个引号、某段文本中包含未转义的特殊字符，都可能导致整段输出成为“半废数据”。

更麻烦的是，这类问题在 Agent 式流水线里会形成级联故障：一个环节的 JSON 解析失败，后续工具调用参数错误，重试又消耗 token 与时间，最终整套自动化停摆。这篇帖子就聊一个务实的解法：**舍弃纯 JSON，改用自定义标签格式做长文结构化输出**，以及实施中真正落地的经验。

## 坏 JSON 到底坏在哪

表面上看，JSON 解析是一个简单任务，但其实在 LLM 输出中，以下情况反复出现：

1. **大段文本嵌套**：模型需要在某个字段里写几百字，其中自然包含双引号、换行符、甚至用户输入里的特殊字符。JSON 要求精确转义，LLM 极容易出错。
2. **尾随逗号与括号不匹配**：生成到一半 token 耗尽或被截断，JSON 结构残缺。
3. **语言模型“创作力”**：偶尔会在 JSON 对象外加一段说明文字，例如“这是你要的 JSON: {…} 希望对你有帮助”，让标准解析器直接报错。
4. **修复成本高**：写正则补括号、用 `jsonrepair` 等库是常见操作，但长文本中它们也会误判，补出一个合法但内容错误的 JSON，导致后续静默失败。

这些问题在长度超过 2000 字符的输出中尤其突出，而重试又浪费资源。我们需要一种**对文本内容更宽容、解析更鲁棒、且能保留结构化信息**的格式。

## 标签格式方案：设计思路与实践

核心思路很简单：用类似 HTML/XML 的成对标签来划分输出段落或字段，例如：

```
<summary>
这里是模型生成的长篇摘要，可以包含任意字符，甚至包括 XML 标签原样（如果选择用 CDATA 或约定标签名称不会冲突）。
</summary>
<key_points>
- 第一条
- 第二条，文本中自然包含 "引号" 和换行都不影响解析。
</key_points>
```

解析侧不依赖严格的 JSON 文法，而是用**基于标签名的提取**，天然容忍文本中的多余字符和未严格转义。我在几个 Agent 工作流中进行了改造，步骤：

1. **定义标签集**  
   确定输出需要哪些结构化部分。标签命名用全大写或带前缀，如 `<OUTPUT_SECTION>`，避免与文本中自然出现的单词冲突。不要使用属性（如 `<tag attr="value">`），保持纯标签匹配，简化解析。

2. **改写提示词，强调标签用法**  
   在 system 或 prompt 中明确约定格式，给出一个简短示例。例如：
   ```
   你必须用以下格式回答：
   <ANALYSIS>
   ...你的详细分析...
   </ANALYSIS>
   <RECOMMENDATIONS>
   - 建议1
   - 建议2
   </RECOMMENDATIONS>
   不要在其他任何地方使用类似标签的尖括号。
   ```

3. **实现容错解析器**  
   不依赖第三方 XML 解析（Security 风险和严格性），用简单的正则或栈实现：
   - 用 `re.findall(r'<TAG>(.*?)</TAG>', text, re.DOTALL)` 提取单层内容。
   - 如果有嵌套，用栈计数（遇到 `<TAG>` 入栈，`</TAG>` 出栈，只有栈顶为零时才认为标签闭合）。
   - **容错处理**：如果发现未闭合标签（文末 `<TAG>` 没有对应闭合），就取从起始到文末的内容，或根据特殊标记（如双换行）截断。

4. **回退机制**  
   如果关键标签完全缺失，可以尝试降级为纯文本处理，或通过分块策略重新请求。对于 Agent 而言，比整体 JSON 失败后全部重试划算得多。

## 真实踩坑点

- **标签名污染**：如果输出内容中自然包含 `<summary>` 这样的标签，解析会错乱。可以在 prompt 中要求模型将原文中的尖括号替换为 `&lt;` 和 `&gt;`，但会增加 token 消耗。更实用的做法是选用怪异标签名（如 `__SUMMARY_BLOCK__`）降低冲突概率。
- **嵌套结构需求**：标签格式不擅长表现深层嵌套（比如 JSON 里的三层对象）。此时可以将复杂结构拆成多个并行标签段，或用层级命名的后缀区分：`<SECTION_1>`, `<SECTION_2>`。不要强求一套标签承载所有层级。
- **输出中包含 XML 标签代码**：比如代码片段、配置内容。可以在 prompt 中指定将代码块放入专门标签，内部不做解析，如 `<CODE_SNIPPET>...</CODE_SNIPPET>`，后端解析时将其整体取出后不做二级提取。
- **和流式输出的配合**：如果用流式（streaming），标签格式天然友好——你可以在收到闭合标签时立即触发对应处理块的后续流程，而不必等待全 JSON 生成完毕，对长文处理尤其明显。

## 可复用工程建议

1. **封装一个通用的标签解析工具**  
   支持多标签提取、嵌套检测、缺失标签回退策略，输出字典或列表，可直接替换你现在从 JSON 拿到的数据结构。这样在项目里可以无缝切换。

2. **在 Prompt 中提供“格式说明书”而非“示例”**  
   仅给一串示例模型仍可能画蛇添足，加上简短的规则描述（如 “每个区块必须以 <BLOCK> 开头且以 </BLOCK> 结尾”）效果更好。

3. **结合输出长度限制**  
   对特别长的生成，可在 prompt 中指定分段标签，例如 `<CHUNK_1>`、`<CHUNK_2>`，让模型主动分段，前端解析逐个消费，避免单个大块失控。

4. **兼容 JSON 的轻量封装**  
   如果外部接口必须是 JSON，可以先用标签格式让模型生成稳定输出，然后由确定性代码将其注入 JSON 对象的对应字段——这样把不可靠的 JSON 生成转移到了可靠的后处理，一举两得。

5. **测试不同模型的标签遵从度**  
   小模型（7B–13B 等级）可能漏掉闭合标签，此时可适当提高 temperature，或在 prompt 末尾强调 “必须严格闭合所有标签”，并在解析器里做最大努力的模糊匹配。

## 总结

从 JSON 迁移到标签格式，本质上是在做一种**鲁棒性换结构性精度**的权衡。在长文输出、多段式报告、Agent 多步结果收集等场景，标签格式带来的解析宽容度和分段处理能力，远比“原生态 JSON”方便。工程上，它降低了重试频率、减少了对修复黑魔法的依赖，当你的 MCP 工具或 OpenClaw 任务流因为 JSON 解析频繁卡住时，不妨试一下这套思路。

或许未来的 LLM 本身的格式遵守能力会改善，但在那一天到来前，简单的标签格式是我们可以立刻落地、立刻见效的工程手段。
