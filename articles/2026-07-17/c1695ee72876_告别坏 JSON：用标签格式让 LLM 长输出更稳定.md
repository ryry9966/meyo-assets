## 背景：为什么长 JSON 总是出问题

在 OpenClaw 的 Agent 工作流、MCP 工具调用和自动化脚本中，我们经常需要让大语言模型输出结构化内容——一篇带标题的长文、一份包含多个章节的报告、一组由模型自行分组的数据。直觉上，JSON 是首选格式：几乎所有编程语言都能解析，结构清晰，嵌套方便。

然而，当输出长度超过几百个 token 后，JSON 的可靠性急剧下降。即使是最新的模型，也难免会出现缺少引号、花括号不配对、数组末尾多一个逗号、嵌套层级断裂等问题。这些问题在短输出中偶有发生，面对 2000 token 以上的长文本时几乎成了常态。错误 JSON 导致整个流水线中断，重试又会消耗大量 token 和时间，更危险的是，部分解析在静默中丢失内容，污染下游数据。

我们当然可以通过后处理来“修” JSON：用正则补引号、用 jq 风格语法检测括号、甚至二次调用 LLM 修复。但这类方案投入产出不成正比，修了一个边界 case 又来一个，工程复杂度被不断推高。

## 核心思路：用自定义标签替代 JSON

换个角度思考：大多数时候，我们并不需要 JSON 的全部语义。标题、段落、列表、代码块，需要的只是从一片长文本中**提取出几块明确命名的内容**。这时候，自定义标签（类 XML 风格）比 JSON 更适合这种场景。

例如，让模型生成一篇带标题的文章，我们希望稳定拿到 `title` 和 `body`。与其要求如下 JSON：

```json
{
  "title": "...",
  "body": "..."
}
```

不如在提示词中约定：

```
请按以下格式输出：
<title>文章标题</title>
<body>
文章正文内容，可以包含多行...
</body>
```

之后，我们不再使用 `JSON.parse()`，而是用简单的正则提取标签内容：

```python
import re

def extract_tag(content: str, tag: str) -> str | None:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    m = re.search(pattern, content, re.DOTALL)
    return m.group(1).strip() if m else None
```

这种方式有几点关键好处：

1. **容错性极强**：模型偶尔多输出一个空白、换行、甚至遗漏闭合标签中的斜杠，我们可以通过模糊匹配（如 `<title>(.*?)</title>` 允许缺失斜杠）来兼容，而不至于整段解析崩溃。
2. **解析简单**：不需要引入第三方解析器，正则或简单的状态机就能工作。
3. **友好可读**：模型训练数据中大量存在 XML/HTML 类标签，理解成本低，比 JSON 更不容易出现格式错误。
4. **支持部分提取**：即使只有 `body` 成功提取而 `title` 失败，我们仍然可以使用已有的内容，JSON 解析失败则全丢了。

## 工程实践：在 OpenClaw 管道中落地

以 OpenClaw 中的一个典型场景为例——调用 LLM 生成日报摘要，并自动拆分为标题、核心内容、待办事项三个部分。原方案要求模型返回如下 JSON：

```json
{"title": "...", "content": "...", "todos": ["...","..."]}
```

改为标签格式后，提示词变成：

```
请严格按照以下格式输出，每个标签必须成对出现，标签内可以是多行文本：
<title>日报标题</title>
<content>
今日核心工作内容...
