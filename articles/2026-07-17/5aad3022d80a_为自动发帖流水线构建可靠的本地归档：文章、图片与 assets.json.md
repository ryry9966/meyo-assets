## 背景

在基于 OpenClaw 搭建的内容生产流水线中，我们通常更关注“生成 - 格式化 - 发布”这条主链路，而本地归档往往被当作一个无足轻重的附庸。但如果你的流水线已经开始定期产出，比如每天一篇技术短文、产品更新通告或 AI 生成的领域摘要，缺少一个结构化的归档策略很快就会让历史内容变成一笔糊涂账——某天想回溯三个月前那条帖子的原始 Markdown 时，却发现图片链接早已失效，内容也被发布平台的富文本引擎改得面目全非。

本地归档并非为了取代平台上的在线内容，而是为了建立一个可审计、可重构、可移植的“源素材”仓库。这篇文章会聚焦一个具体的工程目标：让每一次文章生成任务自动、可靠地把文章、图片以及一份轻量级元数据文件 `assets.json` 落盘到统一的归档目录中。它会面向正在使用 Agent、MCP、自动化脚本串联内容的开发者，尽量不依赖额外的 SaaS 服务。

## 问题拆解

一条自动化生成的帖子在发布前，本质上由三样东西构成：

1. **正文（Markdown/HTML/纯文本）**：可能来自大模型输出，或经过模板渲染。
2. **图片**：由模型间接引用的远程资源，也可能是流水线中调用配图服务生成的。
3. **上下文元数据**：生成时间、使用的 prompt、模型标识、目标发布渠道、修订记录等。

当我们不做归档时，遇到的问题很典型：

- 图片托管在临时存储或图床，过了保留期自动清理，历史帖子的图片全部变成裂图。
- 不同发布平台使用的 Markdown 方言不同（比如草稿中的 `![alt](url)` 上线后可能变成 `<img>` 标签），归档时根本找不到原始引用的可靠版本。
- 批量回溯、重新发布、质量审计成本极高，通常需要人肉去翻日志或数据库。
- 多个 Agent 并发归档同一个任务时，可能发生目录冲突或写入覆盖。

所以，我们要的是一个“内容快照”机制，在一次生成任务结束后，立刻保存一份自完备的副本，并且让这份副本可以脱离外部依赖独立阅读。

## 方案设计

### 目录结构

简单的日期分层是最容易理解和实现的方案。我使用的结构如下：

```
archive/
  2025-05-01-09h30m-python-decorators/
    article.md
    images/
      pic-1a2b3c.png
      diagram-0e4f5a.webp
    assets.json
  2025-05-02-16h10m-agent-memory-patterns/
    ...
```

每个归档条目以 `日期-时间-slug` 命名，slug 可以从文章标题自动生成。这保证了时间线清晰、无命名冲突，即使有多条流水线同时运行（不同分钟级别的时隙），也不会碰撞。

`article.md` 存放经过处理的最终正文，其中所有远程图片引用都已被替换成 `./images/xxx` 的相对路径。`images/` 目录存放从原始 URL 下载下来的二进制文件，文件名统一使用 `{原始文件名的 slugified version}-{URL 内容的 SHA-256 前八位}` 以避免同一文件名意外覆盖。

### assets.json 的结构

`assets.json` 是让归档变得可机器处理的关键。它不是一个“顺便记录一下”的松散文件，而是有明确 schema 的元数据中枢。我定义的字段大致如下：

```json
{
  "id": "2025-05-01-09h30m-python-decorators",
  "title": "Python 装饰器的三层理解",
  "generated_at": "2025-05-01T09:30:00Z",
  "source_prompt": "生成一篇面向中级开发者的 Python 装饰器讲解帖...",
  "model": "claude-3.5-sonnet",
  "publish_target": "xiaohongshu",
  "article_file": "article.md",
  "images": [
    {
      "local": "images/pic-1a2b3c.png",
      "remote_url": "https://example.com/genimg/abc.png",
      "sha256": "1a2b3c4d...",
      "downloaded_at": "2025-05-01T09:31:02Z",
      "width": 1200,
      "height": 800
    }
  ],
  "revision": 1,
  "custom_tags": ["python", "decorators"]
}
```

你可以根据实际需要加入投稿状态、审核标记等字段，但尽量保持 schema 稳定，通过新增可选字段迭代。

### 归档执行流程

整个归档动作最好被封装为一个独立的函数或 MCP 工具，由生成流水线在得到完整内容后调用。流程如下：

1. **接收输入**：文章 Markdown 文本（或从模型响应中提取）、图片 URL 列表、生成元数据。
2. **预处理目录**：根据当前时间戳和 slug 创建目标目录，若目录已存在（极少情况），使用毫秒级戳或递增后缀处理。
3. **处理图片**：遍历每个图片 URL，使用 `download_image(url, target_dir)` 下载，下载时需处理重定向（常见于图床 CDN）、超时重试，并计算 SHA-256 校验值；若下载失败，在 `assets.json` 中记录错误状态，并保留原始远程 URL，但不阻断流程。
4. **替换正文图片路径**：将 Markdown 中的远程 URL 替换为相对路径。
5. **写入文件**：将处理后的文章写入 `article.md`，组装 `assets.json` 并写入，确保在写 `assets.json` 之前 images 已全部下载完成，避免元数据与实际文件状态不一致。
6. **可选索引**：在顶层 `archive/index.json` 追加一条记录，方便扫描所有归档。

在 OpenClaw 中，这个过程可以做成一个 MCP server 工具，比如 `local_archive_article`，运行该工具的 Agent 只需将模型输出和配图列表传入即可。这种做法比散落在各处的手写脚本要可靠，也更容易随 agent 编排复用。

## 踩坑与规避

**图片 URL 重定向和认证**
很多图床或临时图片服务返回 302，有的甚至在首次访问时需要带有特定 Referer。我使用带 Cookie jar 的 HTTP 客户端去模拟常规触发，但仍有一部分 CDN 图片会在短时间内失效，此时只能保留远程 URL 并标记 `downloaded: false`。归档不是实时发布的最后一步，无法解决所有外部依赖，但把范围逐步控制在本地方案内才是目标。

**并发归档时目录冲突**
虽然概率不高，但同一分钟内生成两条 slug 接近的文章（比如摘要类任务）仍有可能。解决方式是归档工具内部使用静态文件锁或直接用时间戳的更高精度（如微秒）构造目录后缀，而不是依赖外部锁服务。我的实践是 `YYYY-MM-DD-HHmmssSSS-slug`，几乎不会碰撞。

**大图片导致归档时间过长**
如果配图是 4K 级别的，下载和校验可能超过 5 秒。我在工具中加入了可配置的超时和最大尺寸限制（比如超过 5MB 的图片自动转存为无损或轻量压缩的 WebP），在保真度和存储效率之间折中。这可以通过 Sharp 或 Pillow 执行。

**Markdown 引用替换不完整**
有些模型输出的图片 Link 不是标准 `![](url)` 格式，可能是 HTML `<img>` 或引用式链接。有必要在归档前先将内容统一成标准 Markdown 图片语法，再执行路径替换。我写了一个简单的正则预处理步骤，可覆盖 90% 的情况，剩下的边缘 case 手工修正。

## 可复用建议

1. **做成可复用模块**：不用每次都写下载图片、建目录的代码。在 OpenClaw 生态里我将其封装为 MCP 工具，支持通过 JSON 参数调用；你也可以做一个独立的 CLI 或库，供工作流脚本调用。
2. **配置化归档根目录**：使用环境变量 `ARCHIVE_ROOT` 决定归档位置，便于在不同环境（本地开发、CI、容器内）复用。
3. **定期进行完整性检查**：附加一个简单的校验脚本，遍历 `archive/` 下所有 `assets.json`，检查记录的 `local` 图片路径是否存在，校验和是否匹配，提早发现文件损坏。
4. **在生成流水线里嵌入自检钩子**：Agent 在完成发帖后，可调用一个 `verify_archive` 工具，检查刚刚的归档是否完整，若失败则向工程师发送通知，而不是静默丢失内容。
5. **考虑归档打包**：当单日归档条目过多时，可以定期将按月的归档目录打包成 tar.gz 并冷存储到对象存储中，本地只保留近期热数据。

## 总结

自动化内容生产并不会因为“没人看”而降低归档的重要性，恰恰相反，当一切由 agent 决定、由脚本完成时，人类工程师最晚发现问题。一个结构清晰、图片可访问、元数据齐备的本地归档，始终是回溯问题、改进 prompt、重新发布或数据审计的唯一锚点。围绕 `article.md` + `images/` + `assets.json` 这个小三角，你可以用很少的代码在现有流水线里建立起牢固的本地历史存档，而无需依赖任何外部服务。对于正在推动内容生成工程化的团队来说，这比再多一个花哨的发布功能都更具长尾价值。
