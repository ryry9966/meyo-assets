## 背景

E2E 测试长期处在一个尴尬位置：业务越依赖它，维护成本越高。选择器漂移、等待条件不稳定、登录态处理复杂、环境差异，都会让用例频繁变红。很多团队尝试用 AI 直接生成测试脚本，但结果往往是“看起来对，一跑就挂”。

问题不在模型能力，而在于生成过程缺乏可执行反馈。通用 Agent 如果只能看到静态 HTML，就一定会猜选择器、猜等待时间、猜业务意图，生成物自然不可用。

## 问题

直接让通用 Agent “帮我写 E2E 测试”通常会踩四个坑：

1. 只看源码，看不到运行态，无法确认元素是否可见、可点。
2. 生成脆弱选择器，比如 `/html/body/div[3]/div[1]/span` 或基于布局 class 的 CSS。
3. 等待策略靠固定 `sleep`，环境一慢就失败。
4. 不遵守现有测试工程约定，引入新依赖、新目录、新写法，导致 review 成本很高。

这些问题的共同点是：Agent 在静态生成代码，而不是在真实环境中闭环执行。

## 做法：把浏览器 MCP 接进 Agent

在 OpenClaw 里，我通过 MCP 接入 Playwright 浏览器工具，让 Agent 获得 `browser_navigate`、`browser_snapshot`、`browser_click`、`browser_expect` 等能力。然后按四步走：

### 1. 先取可访问性快照，不读原始 HTML

让 Agent 打开目标页面后，先调用 `browser_snapshot` 获取页面的可访问性树，包含 role、name、label 等信息。基于这些信息生成定位器，通常更接近真实用户行为，稳定性更好。

### 2. 人工走关键路径，标记断言点

不要让 Agent 自由发挥。先由人操作一遍核心流程，Agent 记录步骤和可观察结果。明确告诉它哪些是关键结果，比如“提交后出现成功提示”或“列表新增一行”。这样生成出的用例有业务意图，而不是机械模拟点击。

### 3. 注入工程约束

在 system prompt 或 MCP 工具描述中，写清楚项目约定。例如：

```text
- 使用 getByRole / getByLabel / getByTestId，禁止布局类选择器
- 禁止 waitForTimeout 和 cy.wait 固定时间
- 登录态通过 storageState 注入，不要处理登录 UI
- 每个用例至少包含一个用户可见结果断言
- 生成后必须本地运行通过两次以上
```

约束越具体，Agent 生成的 diff 越容易 review。

### 4. 执行失败后回填，只修不重写

生成第一版测试后，让 Agent 自己运行。拿到失败堆栈、截图、DOM 快照后，只修改定位器或等待条件，不重写整个用例。通常经过两到三轮“运行-失败-修复”，用例就能从不可用收敛到可提交。

## 踩坑点

- **不要只丢给 Agent 一个 URL**。没有运行态，它一定靠猜。先让 MCP 打开页面取快照，再进入生成流程。
- **不要让 Agent 读完整 HTML 字符串**。信息过载且丢失可访问性语义，容易生成脆弱 XPath。
- **凭证不要写进 prompt**。优先复用浏览器 profile、storageState 或环境变量注入 session，避免泄露。
- **收窄 MCP 工具权限**。如果 Agent 能在页面上乱点，可能触发不可逆操作。尽量限制在测试环境，禁用支付、删除类按钮，或使用录制回放模式。
- **固定 sleep 是重灾区**。看到 `waitForTimeout` 或 `cy.wait(3000)` 要直接打回，要求改为等待文本、角色或网络响应。
- **防止 Agent 引入新依赖**。它可能会自作主张使用新版本特性或额外库。限制它只使用项目已有依赖和 runner。

## 可复用建议

- 把“页面可访问性快照”封装成标准输入，每次生成前先取快照，而不是每次都手写提示词。
- 团队内统一测试选择器规范：优先 role/label，其次 data-testid，禁止布局类 class。
- 将流程拆成“探索-草稿-运行-修复”四个阶段，每个阶段输出中间产物，方便 review。
- 把 Agent 生成测试的 diff 作为普通 PR 提交，CI 跑通后才合并，不直接推送到主分支。
- 如果已有失败用例，优先让 Agent 做“修复”而不是“重写”。保留业务意图，减少回归风险。

## 总结

Agent 参与 E2E 测试的价值，不是替代人工写用例，而是把定位器、等待、断言模板这些重复劳动自动化。关键是让它在真实浏览器里闭环，而不是静态生成代码。

工程上花时间把 MCP 工具、上下文约束、失败回填做好，比换更强模型更有效。测试工程师的角色会从“写每一条用例”变成“定义约束、审核 diff、维护可执行环境”。这可能是更长期、更务实的方向。
