## 背景

单 agent 串行处理复杂自动化任务时，问题会越来越明显。比如一个“内容采集→清洗→写报告→发送通知”的任务，如果让一个 agent 从头做到尾，它会在同一个上下文里反复横跳：一会儿读网页，一会儿写文件，一会儿调用通知插件。结果是要么上下文被大量中间数据撑爆，要么工具调用开始不稳定。

后来我把任务拆成 subagent，每个只做一件事，由主 agent 编排。实践下来，并行不一定需要复杂框架，关键是把边界和契约做好。

## 问题

直接用多个 AI 同时干活，最常见的失败不是模型不够聪明，而是工程控制没跟上：

- 共享上下文互相污染；
- 多个 subagent 同时写同一文件或数据库；
- 某个 subagent 权限过大，误操作影响全局；
- 任务卡住没有超时，整体被拖死；
- 返回结果是非结构化文本，主 agent 很难合并。

这些问题不解决，并行只会让错误更快发生。

## 做法

### 1. 主 agent 只做编排

在 OpenClaw 的 agent 配置里，我会把主 agent 的 system prompt 限制为“拆任务、分发、校验、汇总”，不直接执行具体业务。主 agent 产出任务列表，每个任务包含：

- `task_id`
- 目标描述
- 输入数据或引用
- 期望输出 schema
- 依赖任务
- 是否需要重试

无依赖的任务直接并行分发。

### 2. subagent 单一职责

每个 subagent 有自己的 system prompt、工具权限、超时时间和模型配置。例如：

- `fetch_subagent`：只允许读取 URL 和解析 HTML；
- `clean_subagent`：只做文本清洗；
- `report_subagent`：只写指定目录下的报告文件；
- `notify_subagent`：只发送通知。

在 OpenClaw 中可以把这些拆成独立 agent 文件或配置项，避免所有 subagent 共享同一套工具。

### 3. 通过 MCP 收口工具

我不建议给 subagent 直接开放文件系统或数据库连接。更适合的做法是通过 MCP server 暴露受控工具。比如写文件工具只接受 `path` 和 `content`，内部限制写入目录；数据库工具只暴露 `insert` 和 `select`，不暴露 `drop`。

这样做的好处是，即使某个 subagent 执行出错，也不会把整个环境搞坏。

### 4. 并行执行与汇聚

主 agent 按依赖关系调度：

1. 无依赖任务并行执行；
2. 有依赖任务等到前项完成后执行；
3. 每个 subagent 返回结构化 JSON；
4. 主 agent 做 schema 校验；
5. 失败任务进入重试或降级。

我在实践中通常会限制并行度为 2-3。除非任务非常轻量，否则不会一次开 10 个 subagent。

## 踩坑点

### 上下文不是天然隔离的

如果 subagent 共用同一个会话上下文，它们可能会读到彼此的中间结果。即使系统提示要求“只关注自己的任务”，模型也可能被无关内容带偏。我的做法是为每个 subagent 单独组织输入，只传入必要字段。

### 并发写文件极易出问题

两个 subagent 同时写同一路径，后写覆盖先写，或者写到一半被读走。解决方案是让每个 subagent 写独立文件，如 `parts/report_01.md`、`parts/report_02.md`，最后由主 agent 合并。数据库写入则使用唯一幂等键。

### 权限过宽会放大错误

例如一个负责清洗数据的 subagent，如果同时有发送通知和删除文件的权限，一旦误判就可能删数据。最小权限不是“尽量少”，而是“只给完成当前任务必须的工具”。

### 超时和重试必须先行设计

并行任务中，一个 subagent 卡住会让整批等待。每个 subagent 设 30-60 秒超时，失败只对幂等操作重试。非幂等操作如“发送通知”失败后直接标记为需人工确认。

### 不要默认返回自然语言

要求 subagent 返回 JSON 或 YAML，字段提前定义。主 agent 只做字段检查，不做二次“理解”。如果返回自然语言，汇总阶段很容易引入新的错误。

## 可复用建议

1. **先串行跑通再并行**：用最小任务验证输入输出契约，不要一上来就并行。
2. **给每个任务分配 `trace_id`**：日志里记录 subagent 的开始、结束、工具调用和错误，便于定位。
3. **限制并行度**：从 2-3 开始，观察 token 消耗和失败率。
4. **写文件用独立路径，数据库用幂等键**：避免竞态和重复写入。
5. **失败隔离**：单个 subagent 失败不应让整个任务崩溃。主 agent 可以跳过、降级或转人工。
6. **保持结构化输出**：每个 subagent 的输出 schema 要固定，并做校验。

## 总结

Subagent 编排的本质不是“让多个 AI 聊天”，而是把 agent 当作有限权限、单一职责的执行单元。并行能减少串行等待和上下文污染，但前提是主 agent 的调度、工具收口、超时重试、结果合并都经过设计。控制好边界和契约，这套模式在 OpenClaw 的自动化任务里会比单 agent 稳定得多。
