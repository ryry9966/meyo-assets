## 背景

我维护的一套自动化流程每天产生几万条原始日志，分散在多个服务、任务执行机和本地文件里。看日志本身不难，难的是每天要花十几分钟汇总“昨天发生了什么、哪些失败、哪些需要跟进”。于是把这件事交给 OpenClaw 上的 Agent + MCP 工具链处理：定时采集日志，清洗成结构化中间层，再让模型生成固定格式的日报。

这篇文章不追求“一键智能”，只记录一条能落地的流水线和几个真实踩坑点。

## 问题拆解

原始日志有三个特点：量大、噪音多、格式不一致。直接丢给 LLM 会撞 token 上限，还会因为上下文里混入无关堆栈导致摘要漂移。所以日报生成不能是“把日志塞进 prompt”，而是分三步：

1. 先过滤与聚合，只保留关键事件；
2. 生成结构化的中间表示（JSON）；
3. 基于中间表示写日报，而不是基于原始日志。

## 做法/步骤

### 1. 采集与清洗

在 OpenClaw 里注册一个定时插件，每小时拉取增量日志。日志源通过 MCP 暴露：文件系统用 `fs` MCP，任务系统走内部 HTTP 接口。清洗阶段做三件事：

- 按服务名、时间戳、日志级别标准化；
- 去掉重复行和已知噪声，比如健康检查和心跳；
- 对错误堆栈只保留首行和最后一个用户态帧。

经过清洗，单日日志从几万行降到几百条关键事件。

### 2. 生成结构化中间层

这一步用规则，不用模型。将清洗后的事件转成 JSON 数组，字段固定为：

```json
{
  "ts": "2025-01-15T08:32:00+08:00",
  "service": "worker",
  "level": "error",
  "msg": "task 1234 failed after 3 retries",
  "trace_id": "abc"
}
```

同时按服务聚合失败次数、首次出现时间、最后出现时间。这个中间层既给 Agent 用，也可直接存库备查。不要省略这层，否则后面每次改 prompt 都要重新解析原始日志。

### 3. Agent 生成日报

日报 prompt 只接收上一步的 JSON 摘要。用 OpenClaw 的 Agent 节点调用 LLM，要求输出固定 Markdown 模板：

- 昨日整体状态
- 失败事件 Top 3
- 需要人工跟进事项
- 趋势提醒（与前一天对比）

为了减少幻觉，prompt 里明确：只允许引用 JSON 中出现的 `trace_id` 和服务名；不得推断原因；无法判断时写“原因待查”。输出后再用 JSON Schema 校验一个隐藏结构，确认关键数字对齐。

### 4. 发布与归档

生成结果由插件写入本地 `daily-report/YYYY-MM-DD.md`，同时推送到群机器人。归档目录按日期命名，保留原始清洗后 JSON，方便回溯。

## 踩坑点

- **上下文窗口不够**：第一次直接把 2 万行日志塞给模型，输出里出现大量不存在的时间戳。后来改为“先规则聚合，再给模型”，单次输入从 60K token 降到 3K 左右。
- **时区错乱**：日志源有 UTC、CST 混用。生成日报时把“昨天”定义成 `+08:00` 自然日，统一在清洗层转换，不要依赖模型理解时区。
- **JSON 输出偶尔断裂**：长报告用流式输出时，模型可能中途截断。改成先生成 JSON 摘要，再让第二个节点把 JSON 渲染成 Markdown，稳定性好很多。
- **敏感信息泄漏**：日志里可能带 token、手机号。清洗层必须做脱敏，不能只靠 prompt 提醒。
- **MCP 工具偶发超时**：文件系统 MCP 在夜间备份时响应慢。定时任务加重试和指数退避，不要默认一次成功。

## 可复用建议

1. **永远保留一层结构化中间表示**。它比原始日志更适合做审计、对比和重放。
2. **用模板约束日报结构**，让模型只负责“措辞”，不负责“事实提取”。
3. **增量处理优于全量重跑**。每天只处理增量，失败时补跑前一天，比每次全量稳。
4. **把校验和生成解耦**。生成后跑一个规则校验器，检查 trace_id 数量、服务名是否与源数据一致。
5. **先跑一周“影子模式”**：让日报生成但不自动推送，人工对比原始日志，确认无误再上岗。

## 总结

这套流水线的核心不是模型多强，而是把“日志 -> 日报”拆成“清洗 -> 聚合 -> 生成 -> 校验”。OpenClaw 的插件调度和 MCP 工具负责搬运，模型只做最后一公里的表达。上线后每天能省下十几分钟人工汇总时间，关键是日报内容可追溯、可校验，不会出现“看起来合理但和原始日志对不上”的情况。对自动化实践来说，这种朴素工程化路线反而更值得复用。
