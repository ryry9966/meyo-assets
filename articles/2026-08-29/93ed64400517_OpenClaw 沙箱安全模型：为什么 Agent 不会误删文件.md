## 背景

OpenClaw 的 Agent 会执行本地命令、读写文件、调用 MCP 工具。真正危险的不是模型“不知道命令危险”，而是文件操作直接落在宿主机真实目录上。`rm -rf`、覆盖写入、移动目录，只要一次误判直接命中真实路径，恢复成本很高。因此安全边界不能只依赖提示词约束，必须放在执行层。

## 问题

对 Agent 来说，删除文件只是一次工具调用。如果删除直接作用于真实文件系统，任何误判都会变成生产事故。需要回答的核心问题是：为什么 Agent 在 OpenClaw 里执行了删除操作，真实文件仍然还在？

这个保证来自沙箱的文件系统隔离，而不是模型“更听话”。

## OpenClaw 的沙箱做法

OpenClaw 的 sandbox 会把 Agent 的文件操作放进一个隔离视图。真实工作目录通常以只读方式挂载，Agent 看到的是一层叠加文件系统。写入、删除、重命名都发生在临时差异层里；只有策略允许并显式提交后，变更才会进入真实目录。

可以简单理解为三层：

- **只读基础层**：真实目录，Agent 不能直接修改。
- **临时差异层**：Agent 的所有修改、删除、新建都记录在这里。
- **提交策略层**：决定哪些差异可以落盘，哪些只能丢弃。

当 Agent 删除某个文件时，它在沙箱视图里看到文件“消失”，但实际上只是在差异层里写入了一个删除标记。真实文件仍然存在于只读基础层。只要会话不提交，或提交策略不允许，这次删除就不会作用到真实磁盘。

### 验证步骤

1. 在项目目录放一个哨兵文件，例如 `sentinel.txt`。
2. 确认 sandbox 开启，真实根目录只读，临时目录可写。
3. 启动一个 OpenClaw 任务，让 Agent 删除 `sentinel.txt`。
4. 在沙箱视图内确认文件已消失；回到真实目录确认文件仍然存在。
5. 查看会话差异层或审计日志，能看到删除标记或拦截记录。
6. 只有手动执行提交/审批后，真实文件才会被删除。

简化配置思路示意，不以具体字段为准：

```yaml
sandbox:
  enabled: true
  root: read-only
  writable_paths:
    - ./workspace/tmp
    - ./workspace/artifacts
  delete_policy: allowlist
  commit_mode: manual
```

这个示例只表达隔离思路，不同版本字段命名和默认值可能有差异。

## 踩坑点

**白名单过宽**：如果为图省事把整个项目根目录或 home 目录设为可写，删除标记一旦提交，仍然会误删真实文件。

**符号链接和路径穿越**：Agent 可能创建指向真实目录的符号链接，再通过链接删除目标文件。沙箱如果没有做路径归一化或禁止危险 symlink，保护会被绕过。

**MCP 文件工具绕过**：如果 MCP 服务器提供独立的文件操作工具，并且直接使用宿主机路径，它可能不受 OpenClaw sandbox 约束。第三方 MCP 尤其需要做隔离测试。

**未提交写入丢失**：会话内产生的新文件，如果没有提交，沙箱退出后会消失。这在日常使用中可能造成另一种数据丢失，需要明确哪些目录需要持久化。

**忽略提交前 diff**：提交策略如果没有 diff/变更预览，等于把风险留到最后一步。手动审批前必须看清楚将要删除或覆盖的内容。

## 可复用建议

- 把 Agent 工作目录和重要数据目录分离，不要给它整个项目根目录的写权限。
- 只允许写入 `tmp/`、`artifacts/` 等明确目录，删除策略默认走 allowlist。
- 限制符号链接创建，开启路径归一化检查。
- MCP 的文件能力统一接入 OpenClaw 的受控文件接口；不能确认安全的第三方 MCP 先隔离运行。
- 提交前强制查看变更清单或 diff。
- 开启文件操作审计日志，出错时能定位是哪次任务、哪个工具调用产生的差异。
- 对持久化数据单独备份，不要把只读基础层当作唯一副本。

## 总结

OpenClaw 的 sandbox 不能让 Agent 永远不犯错，但它把错误限制在一个可丢弃的差异层里。误删之所以不会直接发生，是因为 Agent 的文件操作没有立即作用到真实磁盘，而是先进入叠加层，再经过提交策略。

理解这一点，比单纯加一句“不要删文件”更可靠，也更容易在真实工程环境里落地。
