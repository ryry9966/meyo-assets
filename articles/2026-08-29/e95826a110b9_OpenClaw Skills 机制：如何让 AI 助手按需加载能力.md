# OpenClaw Skills 机制：如何让 AI 助手按需加载能力

## 背景：能力越多，助手越“重”

接入 MCP、插件、脚本的 OpenClaw 实例，常见做法是把所有工具描述、提示词、schema 一次性放进上下文。刚开始还好，能力增多后问题开始暴露：首轮响应变慢、模型容易忽略关键信息、低权限任务也能看到高权限工具、维护一处改动影响全局。

很多团队的第一反应是继续加能力、改提示词。但真正的问题往往不在“能力不够”，而在“加载方式不对”。

## 问题：全量加载的三个代价

全量加载会带来三个工程问题：

1. **上下文消耗**：大量工具描述占满上下文，复杂任务反而容易被挤掉关键信息。
2. **安全边界模糊**：一个只读查询任务如果加载了写操作工具，风险面被无谓放大。
3. **技能冲突**：不同插件可能定义同名工具、共享全局状态或依赖不同版本的库。

Skills 机制的核心思路，是把能力定义为可发现、可触发、可装载、可卸载的独立单元，运行时按需挂载，而不是常驻。

## 做法：用“清单 + 加载器 + 生命周期”管理技能

### 1. 先拆技能，不写大而全的助手

把能力按“领域/动作”拆成独立目录，例如：

```
skills/
  stock-query/
    skill.yaml
    run.py
    resources/
  pdf-extract/
    skill.yaml
    run.sh
```

每个技能只负责一个明确动作，有单一入口和清晰边界。

### 2. 用声明式清单描述触发条件与权限

`skill.yaml` 建议包含以下字段：

- `name` / `version`：版本化管理
- `triggers`：触发词或意图描述，用于做轻量路由
- `permissions`：网络域、文件读写范围、环境变量
- `entrypoint`：执行入口
- `timeout`：执行上限

这样系统可以先加载清单索引，而不加载完整实现。

### 3. 按需加载：先索引，后注入

简单实现流程：启动时扫描 `skills/` 目录，只把每个技能的 `name`、`triggers`、摘要注入路由层或系统提示。当用户意图命中某个技能的触发条件，再从磁盘读取详细指令、挂载工具、授予权限。

关键点是“注入时机”：不要一次性把所有技能详情注入上下文。越晚加载，上下文越干净。

### 4. 给技能加生命周期

每个技能至少应经历：

- `validate`：检查清单格式、入口存在、权限白名单
- `load`：装载工具、注入指令
- `execute`：执行用户任务
- `cleanup`：卸载工具、清理临时文件、回收权限

很多实现只做 `load` 和 `execute`，忽略 `cleanup`，这是后续踩坑的主要来源。

### 5. 监控命中率与加载耗时

记录每次技能加载的触发命中、耗时、超时、报错。积累一段时间后，就能判断哪些触发词需要收紧，哪些技能应该合并或拆分。

## 踩坑点

**1. 触发条件太宽**  
用“文件”“查询”这类词做触发，几乎每次对话都会误加载。建议用组合条件：意图 + 实体 + 上下文，而不是单关键词。

**2. 卸载不干净**  
技能修改了全局环境变量、挂载了工具后没有在 `cleanup` 恢复，导致后续任务被污染。保持每个技能的副作用可回滚，是稳定运行的前提。

**3. 路径安全**  
技能资源路径如果未做校验，可能被元数据中的 `../../` 读取任意文件。加载前要解析并限制在技能目录内。

**4. 依赖冲突**  
多个技能依赖不同版本库时，建议进程级隔离或容器执行，而不是全部装进同一个 Python/Node 环境。

**5. 上下文注入格式错误**  
直接把 YAML 原始内容作为 system prompt 插入，可能破坏格式或超长。建议使用结构化模板，只注入必要字段。

## 可复用建议

- **最小权限**：默认不授予写权限，按技能显式声明。
- **版本化技能**：每个技能带版本号，变更走 changelog，便于回滚。
- **dry-run 模式**：支持“只展示将加载什么，不实际执行”，方便调试。
- **样本回归**：准备 10–20 条用户指令，测试是否命中正确技能、是否误触发。
- **加载指标**：记录技能命中率、平均加载耗时、失败率，用于持续优化。

## 总结

OpenClaw Skills 机制的价值不在于增加更多能力，而在于让已有能力以更小粒度、更安全、更可维护的方式被调用。先拆技能、再声明清单、按需注入、管好生命周期，是落地时最值得投入的四个环节。与其继续给助手加全量工具，不如把“按需加载”本身做成一项基础工程。
