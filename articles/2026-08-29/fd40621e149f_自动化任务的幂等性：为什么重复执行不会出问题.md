## 背景：重复执行不是异常，而是常态

在 OpenClaw、Agent 编排和 MCP 工具调用的场景里，一条自动化任务通常不会只经过一个进程：定时器触发、消息回调、MCP 工具调用、外部 API 重试、Agent 内部补救循环。任何一个环节都可能把同一个逻辑动作执行两遍。比如 webhook 因超时重发、用户重复点击、调度器在前一次未结束时再次启动，或者 Agent 判断工具调用失败后自动重试。

如果任务不是幂等的，重复执行会带来重复消息、重复工单、重复写入、重复扣减库存等副作用。更麻烦的是，这些问题常常不是必现，而是在偶发重试或并发下才暴露。

幂等性简单说就是：同一个请求或同一个逻辑动作，执行一次和执行多次，业务结果一致，副作用不叠加。

## 问题：非幂等任务长什么样

典型反例：

- 收到事件后直接调用“创建记录”接口，没有业务唯一键。
- 在 MCP 工具里用相对值更新，例如 `count = count + 1`，重试一次就多加一次。
- 任务状态只靠内存或日志判断，没有持久化检查点。
- Agent 重试时生成新的 `request_id`，导致下游无法去重。

这类任务在测试环境跑一次没问题，但一旦进入真实重试、并发或补偿流程，就会出现“看起来成功，但数据被复制了一份”。

## 做法：把任务改成可重复执行

### 1. 给每个任务定义一个幂等键

幂等键应该来自业务输入，而不是随机生成。可以组合：

- 事件 ID + 任务类型
- 用户 ID + 动作类型 + 目标对象
- 对关键输入做 SHA-256

例如处理一条消息，可以用 `message_id + pipeline_name`，而不是当前时间戳。时间戳会让同一条重试消息每次看起来都像新任务。

### 2. 执行前先检查，执行后落状态

在任务入口维护一张幂等表或状态表，结构类似：

- `idempotency_key`
- `status`：`pending / processing / done / error`
- `result`
- `updated_at`

执行前用原子方式插入 `pending`。如果已存在且状态为 `done`，直接返回上次结果；如果状态是 `processing`，可以等待或跳过，取决于业务语义。

### 3. 下游写入使用确定性标识

凡是创建资源，先按外部标识查询，存在则返回已有资源，不重复创建。比如创建文档、创建标签、创建任务，都要有 `external_id` 或 `source_key`。

对更新操作，尽量使用绝对值而不是相对值。比如 `status = "closed"` 是幂等的，`close_count = close_count + 1` 不是。

### 4. MCP 工具要显式声明幂等语义

在 OpenClaw 的 Agent 调用 MCP 工具时，Agent 可能会在超时或异常后重试。因此工具描述里应写明：

- 哪些参数是幂等键
- 重复调用会返回相同结果还是会被安全忽略
- 是否支持 `create_or_update` 语义

不要让工具内部自行做隐式重试，尤其不要在工具内再包一层“失败就再调一次”的逻辑，那样会和 Agent 的外层重试叠加。

### 5. 完成标记要严格

只有在下游操作全部成功后才把状态更新为 `done`。如果中途失败，保留 `error` 或 `processing`，让后续重试可以从检查点继续，而不是重新创建一套资源。

## 踩坑点

1. **唯一索引没建，检查形同虚设。** “先查再插”在并发下会有竞态，必须给 `idempotency_key` 建立唯一索引，依赖数据库原子约束。

2. **锁 TTL 太短。** 一个任务正常执行 3 分钟，但锁 1 分钟过期，另一个 worker 看到 `processing` 直接抢锁重复执行。需要心跳续期，或者把超时设得足够保守，并在任务内处理“前任是否还活着”。

3. **误把“接口成功返回”当成“业务成功”。** 下游可能返回 200 但实际写入不完整，或者异步任务尚未落地。幂等表应记录明确的业务结果，而不是 HTTP 状态码。

4. **消息队列至少一次投递。** 即使用户只触发一次，MQ 重平衡、ACK 超时也可能造成重复投递。自动化入口必须假设会收到重复消息。

5. **Agent 重试生成新 ID。** 如果每次重试都换 `request_id`，下游幂等键就被打散。最好在 Agent 任务上下文中保持同一个 `job_id`。

## 可复用建议

- 新建自动化任务时，先写一句“该任务的幂等键是什么”，再开始写流程。
- 用一个统一封装处理幂等状态，而不是每个任务各写一套。
- 自测时连续触发两次相同输入，检查下游记录数、返回值是否一致。
- 对关键 MCP 工具增加一个“安全重试”测试：第一次执行到一半杀掉进程，再重新执行。
- 在日志中记录 `idempotency_key`，排障时能快速关联重复事件。

## 总结

自动化任务不可能完全避免重复执行，但可以把重复执行变得无害。幂等性不是额外的复杂设计，而是让 Agent、MCP 工具和调度器能够安全协作的基础。对 OpenClaw 场景来说，与其相信“上游不会重发”，不如让每个任务显式回答：如果我再跑一次，会发生什么？如果答案不是“结果一致、副作用不再叠加”，就还没到可上线状态。
