---
title: 自动化任务的幂等性：为什么重复执行不会出问题
feedId: 35262
source: 综合讨论
publishedAt: 2026-08-29
---

自动化任务跑挂，往往不是因为没执行，而是因为执行了太多次。OpenClaw 里的定时巡检、Webhook 回调、Agent 工具重试、MCP 写操作，都是重放高发区。一个创建工单的工具被重试三次，就收获三张重复工单；一个发消息插件因为网络超时重试，就打扰用户三次。要解决的不是“让任务不重复”，而是让重复执行不产生额外副作用，这就是幂等性。

问题不在于框架。OpenClaw 的调度、Agent 的重试、Webhook 的至少一次投递，都在提高可靠性，但可靠性机制天然会把同一意图投递多次。真正的防重必须下沉到工具和存储层。否则调用方再小心，也会被一次补偿任务打穿。

### 做法/步骤

1. 给每次业务意图生成唯一幂等键。不是每个工具调用随机生成，而要稳定可复用：Webhook 事件 ID、外部工单 ID、任务 ID + 目标对象，或关键字段哈希。例如：`event_id + action`。

2. 在 OpenClaw Agent 或 MCP 调用中显式传递 `idempotency_key`。工具实现第一步按 key 查执行历史，命中则直接返回首次结果，不执行写操作。

3. 数据库层用唯一约束兜底。建一张 `tool_executions` 表，`unique(action, idempotency_key)`。即使前置查询漏判，插入重复行时捕获唯一键冲突，再回查已有结果。

4. 多步流程用状态机保护。把子任务状态设为 `pending/running/done`，执行前做 compare-and-set：只有把 `pending` 改成 `running` 成功的那一个调用能继续，中断恢复时不会重跑已完成步骤。

5. 对不可控的第三方 API，使用防重窗口 + 执行指纹。本地先写 `intent_hash`，记录调用时间和结果。重试时先检查窗口内是否已生效，避免重复扣款、重复发送。

### 踩坑点

- 把任务实例 ID 或消息 ID 当幂等键。调度器重新跑任务会生成新实例 ID，重试会换消息 ID，防重失效。应该用业务 ID。

- 只做前置查询不加唯一约束。并发两个请求都查不到记录，然后都执行写操作。唯一约束或分布式锁必须二选一加底。

- 重试时参数不一致。第一次 `amount=100`，第二次 `amount=120`，如果直接覆盖，会造成数据漂移。命中已有记录应返回首次结果，不覆盖。

- MCP 工具不返回稳定结果 ID。Agent 重试时无法关联。建议所有写操作返回 `resource_id` 和 `idempotency_key`。

- 对读操作过度设计。读操作重复执行无害，不必加幂等，聚焦写和副作用。

### 可复用建议

- 在 OpenClaw 的任务模板里，把带 `idempotency_key` 作为写操作插件的默认约定；插件统一封装 check-and-set。

- 为 MCP 工具做一个幂等包装器：校验 key、记录执行、冲突时返回缓存结果。

- 日志统一输出 `action + key + outcome`，重复触发时能快速定位来源。

- 对发消息、扣款、删除等不可逆操作，保留硬防重窗口或人工确认。

- 测试时故意重放同一 Webhook 十次，看副作用数量是否只有一次；用本地数据库唯一键验证兜底能力。

### 总结

自动化任务里的幂等性不是额外优化，而是底线。OpenClaw/Agent/MCP 项目里，可靠的重试机制必须配合业务层的防重设计。核心原则只有一句话：一个业务意图一个 key，先查再写，唯一约束兜底，返回首次结果。做到这四点，重复执行就不会出问题。
