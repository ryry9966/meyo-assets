# OpenClaw 的 IDENTITY.md：给 AI 一个可进化的身份

## 背景

在 OpenClaw 里跑 Agent，时间一长都会遇到同类问题：每次新会话都要重新交代项目背景、工具边界、代码风格；换了插件或 MCP 配置后，Agent 的行为开始漂移；更麻烦的是，团队里每个人对“这个 Agent 该做什么、不该做什么”的理解不一致，导致同一个任务有时跑得很顺，有时完全跑偏。

最初大家习惯把大段提示词塞进系统提示、任务描述或者某个插件的配置里。这在小项目里够用，但项目变大以后，身份信息散落在多个文件、脚本和对话里，无法复用，也难以审计。Agent 的身份需要被当成一项工程资产来管理，而不是每次临时口述。

## 问题

OpenClaw 本身提供了丰富的工具、插件和 MCP 接入能力，但缺少一个稳定的“身份层”。常见症状包括：

- Agent 在长任务中逐渐忘记最初的角色设定。
- 不同 MCP 工具之间的调用策略没有统一约束。
- 团队协作时，A 写的 Agent 提示词 B 接不上。
- 想调整 Agent 行为时，不知道改哪一处。
- 身份信息与代码混在一起，版本控制困难。

简而言之，身份定义如果不落成文件、不进入版本库、没有更新机制，Agent 就只是一个一次性的执行器，而不是可维护的工程组件。

## 做法与步骤

在 OpenClaw 项目中，我们用 `IDENTITY.md` 作为 Agent 的身份文件，放在项目根目录或 `.openclaw/` 下。文件内容保持精简，只写真正影响行为的部分。

### 1. 定义最小字段

建议从六个字段开始：

```markdown
# IDENTITY

## Role
你是一个负责 OpenClaw 项目自动化运维的 Agent。

## Goals
- 减少重复人工操作
- 保持任务可追踪、可回滚
- 优先使用已有 MCP 工具

## Constraints
- 不主动修改生产配置
- 不读取与当前任务无关的密钥文件
- 遇到权限不足时停止并报告

## Tool Policy
- 文件写入前先做 dry-run
- 调用 MCP 工具时优先选择只读接口
- 每次变更后记录到变更日志

## Failure Handling
- 一次失败立即重试，两次失败必须换策略
- 无法判断影响范围时，不执行破坏性操作

## Evolution Log
- 2025-01-11: 初始版本
```

### 2. 在 OpenClaw 中加载

如果 OpenClaw 支持项目级配置，可以在配置文件里引用该文件。例如在 `openclaw.json` 中增加：

```json
{
  "identity": {
    "file": ".openclaw/IDENTITY.md",
    "reload_on_change": true
  }
}
```

如果当前版本不支持自动加载，也可以在会话启动时通过一个轻量插件读取 `IDENTITY.md`，把它作为上下文注入到系统提示中。关键是做到“每次会话自动加载”，而不是靠人手动粘贴。

### 3. 让身份可进化

在 `Evolution Log` 中记录重大行为调整。每次复盘后，把发现的问题和对应规则追加到文件里。例如：

```markdown
## Evolution Log
- 2025-01-11: 初始版本
- 2025-01-15: 发现 Agent 在批量写文件时缺少确认，增加 Tool Policy 第 2 条
- 2025-01-20: 增加 Failure Handling，避免连续失败后持续消耗 token
```

这样 `IDENTITY.md` 不只是一个静态提示词，而是随着项目一起迭代的行为契约。

### 4. 配合 MCP 与插件

可以把 `IDENTITY.md` 的读取、写入做成一个轻量 MCP 工具或插件。思路如下：

- `identity:read`：读取当前身份文件。
- `identity:update`：在 Evolution Log 追加一条记录。
- `identity:check`：启动时校验必填字段是否完整。

这样做的好处是，Agent 可以在运行中请求当前身份信息，也可以把复盘结果写回文件。但写操作必须受控，不能随意修改核心规则。

## 踩坑点

**身份文件过长**

一开始容易把所有项目说明都塞进 `IDENTITY.md`，导致上下文被大量无关信息占用。身份文件应该只写角色、边界、策略和变更历史，具体项目细节放到 `CONTEXT.md` 或任务输入中。

**允许 Agent 自由修改身份**

如果开放了 `identity:update` 的写权限，Agent 可能会把一次偶然失败写入规则，导致后续行为更加保守或激进。建议把 Evolution Log 的写入限定为人工确认或复盘阶段，日常运行中只读。

**敏感信息泄漏**

不要在 `IDENTITY.md` 中写 API key、数据库密码或内部地址。身份文件会进入版本库，也可能被不同会话频繁读取，不适合放敏感信息。敏感信息走环境变量或独立密钥管理。

**中英文混杂导致理解偏差**

规则用英文写通常更稳定，因为模型对英文指令的执行一致性更好。但团队协作时，中文说明更容易理解。建议核心规则用英文，注释和 Evolve Log 用中文，避免在同一句规则中混用。

**版本冲突**

多人同时提交身份文件时容易出现冲突。可以把 `IDENTITY.md` 视为代码的一部分，遵循分支、评审和合并流程。Evolution Log 的条目尽量单独成行，减少合并难度。

## 可复用建议

- 把 `IDENTITY.md` 当作代码管理，不直接在生产环境手工改。
- 区分静态身份和动态状态：身份规则放 `IDENTITY.md`，任务进度放 `STATE.md` 或数据库。
- 限制写权限：日常运行只读，复盘或人工审批后才允许修改。
- 定期审计：每隔一段时间检查规则是否仍然适用，删除过时约束。
- 模板化：给新项目一个最小模板，减少团队成员重新设计的时间。

## 总结

OpenClaw 的 Agent 不应该只是一段临时提示词，而应该有一个可持续演化的身份文件。`IDENTITY.md` 的成本不高，但能显著改善 Agent 在长任务、多工具、多人协作场景下的稳定性。它解决的不是“怎么让 AI 更聪明”，而是“怎么让 AI 在项目里更可靠”。

真正好用的身份文件，不是写得多完整，而是团队愿意持续维护、Agent 每次都能稳定遵循的那一份。
