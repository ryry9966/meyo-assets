## 背景

RSS 仍然是少数可以自主控制信源的信息入口，但问题很直接：订阅多了读不过来，订阅少了又怕漏掉重要内容。全量阅读不现实，逐条丢给大模型做摘要又显得浪费，而且摘要质量不稳定、推送重复、上下文容易被噪音淹没。

这条管线想解决的不是“能不能摘要”，而是怎么把 RSS 抓取、去重、批量摘要、推送这几个环节做得可维护、可降级、不依赖人工每天盯。

## 问题

常见做法是每个 feed 单独写脚本，抓到就调一次模型，然后把结果直接推到 IM。这样会出现几个工程化问题：

- 没有稳定去重，重复抓取产生重复推送。
- 逐条摘要成本高，且缺少同一 feed 的上下文，摘要容易泛泛而谈。
- LLM 输出结构不稳定，直接拼文本容易污染后续处理。
- 推送频率不可控，容易从“信息流”变成“打断流”。

所以目标很明确：统一入口、持久化状态、批量处理、推送前可干跑。

## 做法 / 步骤

### 1. 抓取与归一化

用 `feedparser` 或 RSSHub 拉取源，把所有 item 统一成 JSON Lines：

```json
{"feed_id":"hn","item_id":"abc","title":"...","link":"...","summary":"...","published":"2025-01-01T00:00:00Z"}
```

字段不要直接信任上游，`published`、`id`、`summary` 都可能缺失或格式不一致。建议在抓取阶段补齐默认值，并记录 `fetched_at`。

配置用 `feeds.yaml` 驱动，避免每加一个源就改代码：

```yaml
- name: hn
  url: https://hnrss.org/frontpage
  priority: high
  tags: [tech]
```

### 2. 去重与状态持久化

用 SQLite 存已经处理过的 item。不要依赖 RSS 源给的 `id`，很多源会变。建议用 `sha1(link + title)` 作为去重键，必要时对 URL 做规范化，去掉 utm 参数、fragment。

只有新 item 才进入下一步。这样即使定时任务重复跑，也不会重复推送。

### 3. 批量摘要

不要逐条调模型。按 feed 分组，每组取 5–10 条新文章，放进同一个上下文里生成结构化摘要。提示词可以类似：

```
你是一个信息过滤助手。下面是同一 feed 的新文章。
请只输出 JSON 数组，每项包含 id、abstract、worth_reading、tags。
abstract 不超过 60 字；不要推测原文没有的信息。
```

代码里用 `json.loads` 解析，失败时重试一次。温度设 0 或接近 0，能显著降低输出漂移。

批量处理的好处是模型能看到同一 feed 的多条内容，更容易判断哪些是重复报道、哪些是真正增量信息。

### 4. 接入 OpenClaw / MCP

如果你在用 OpenClaw，建议把这条管线封装成一个 MCP 工具，例如 `fetch_new_items_digest`，返回结构化摘要、优先级和原文链接。

更好的边界是：管线负责“搬运、去重、摘要、状态”，Agent 只负责“决定看什么、是否进一步展开”。不要把每条摘要都丢给 Agent 重新润色，那会增加不必要的上下文占用和延迟。

定时触发可以直接用 OpenClaw 的 scheduled task，也可以用系统 cron。核心逻辑保持普通 CLI 可运行，方便脱离 Agent 环境排障。

## 踩坑点

- **item id 不稳定**：很多源的 `id` 会变，去重键不要只依赖它。
- **正文缺失**：RSS 只有摘要时，可以用 Readability 类库抓正文，但要加缓存和限速，否则容易被源站封。
- **LLM JSON 解析失败**：不要一失败就放弃，先记录原始输出，再用更保守的 prompt 重试一次。
- **推送过频**：建议做 digest 窗口，例如每 6 小时聚合一次，而不是每抓到新 item 就推。
- **发布时间不可信**：有些源会漏掉 `published`，有些会给未来时间。做时间过滤时最好以 `fetched_at` 为主。

## 可复用建议

- 先跑 `dry-run`，只输出摘要，不实际推送，稳定后再开推送。
- 保持原文链接，AI 摘要只做过滤，不做替代。
- 给管线加简单监控：抓取成功率、去重命中数、LLM 失败次数。比复杂告警更有用。
- 能跑单文件就别上队列。RSS + 摘要的规模通常很小，SQLite + CLI 足够稳定。
- 把提示词和模型参数放进配置，方便按 feed 调整摘要长度或过滤标准。

## 总结

RSS + AI 摘要的核心不是“摘要”本身，而是把不稳定环节工程化：抓取、去重、批量处理、结构化输出、推送降级。管线越简单，越容易长期运行。真正留给 Agent 和 OpenClaw 的价值，是最后的过滤与决策，而不是让它陷在每次抓取的脏活里。
