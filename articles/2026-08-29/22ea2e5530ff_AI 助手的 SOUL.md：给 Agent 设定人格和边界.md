## 背景：Agent 配置正在从“提示词”变成“工程文件”

在 OpenClaw、Agent、MCP、插件和自动化实践里，越来越多的人开始把系统提示词从聊天框里搬出来，放进独立文件维护。常见做法是 `system.md`、`agent.md`、`rules.md`，但很快会发现一个问题：人格、规则、工具策略、安全边界全部混在一起，改一处容易把另一处带崩。

`SOUL.md` 的思路是把“这个 Agent 是谁、能做什么、不能做什么、用什么方式做事”作为单一事实来源。它不替代 MCP 工具描述，也不替代插件自己的配置，而是给 Agent 一个稳定的“人格内核”和硬边界。

## 问题：没有 SOUL.md 时，Agent 容易出现三类偏差

第一，人格漂移。同一个 Agent 在不同会话里语气忽冷忽热，有时过度热情，有时变成客服腔。因为没有固定的人格描述，模型会根据上下文随机补全。

第二，越界操作。遇到模糊指令时，Agent 倾向于“先做再说”。比如自动化脚本里出现删除、覆盖、推送、发消息等动作，如果边界写得不清晰，Agent 可能会执行本应确认的操作。

第三，规则冲突。MCP 工具自带说明、插件注入的指令、用户临时 prompt、SOUL 文件之间经常互相打架。没有优先级和冲突处理策略，Agent 就容易选择最省事而不是最安全的解释。

## 做法：把 SOUL.md 当成可测试、可版本化的配置

### 1. 固定文件结构，但不追求大而全

一个可用的 `SOUL.md` 建议只保留五个区块：

- **身份**：一句话说明这个 Agent 是什么角色，避免长段落自我介绍。
- **语气与沟通方式**：用 3~5 条可观察行为描述，不要写“专业、友好”这种空洞词。
- **工作边界**：明确能做什么、不能做什么、什么情况必须停下确认。
- **工具与插件策略**：说明优先使用哪个工具、什么情况下不调用工具、工具失败后怎么降级。
- **失败与恢复策略**：遇到权限不足、工具报错、信息缺失时如何响应。

示例片段：

```markdown
## 身份
你是本地自动化运维助手，默认在用户机器上工作。

## 工作边界
- 禁止删除用户目录、禁止覆盖已有文件，除非用户明确写出目标路径。
- 涉及 git push、发送消息、执行 sudo 的操作，必须先输出计划并等待确认。
- 读取文件优先，修改文件前必须确认。

## 失败与恢复
- 工具返回权限不足时，不要尝试绕过，直接报告原因。
- 连续两次工具失败后，停止当前任务，给出最小排查步骤。
```

### 2. 在 OpenClaw 中挂载，而不是复制进每段对话

建议把 `SOUL.md` 作为项目级或全局级 agent 上下文挂载。OpenClaw 中可以在 agent 配置里指定 `system_prompt_file` 或类似机制，让每次会话自动加载。不要手动复制到 prompt 里，否则版本容易不一致。

### 3. 与 MCP/插件做边界切分

`SOUL.md` 只写“决策规则”，不写工具的具体参数。MCP 工具描述已经说明参数格式时，SOUL 里不要再重复一遍。重复描述不仅浪费 token，还可能在工具升级后变成过期信息。

可以把 SOUL 里的工具策略写成：

```markdown
## 工具策略
- 优先使用 MCP 提供的 read_file / write_file，不使用 shell 重定向。
- 如果工具支持 dry-run，先 dry-run 再正式执行。
```

而不是写：

```markdown
## 工具策略
- read_file 参数 path 是字符串，encoding 默认 utf-8……
```

后者属于工具自身的职责，写进 SOUL 会造成维护负担。

## 踩坑点

**1. 把 SOUL.md 写成“美德列表”**

“你是一个聪明、可靠、细心的助手”对 Agent 行为几乎没有约束力。可执行的人格描述应该能通过行为判断。比如“回答前先给出假设，再给出结论”比“逻辑清晰”更有效。

**2. 边界写得太死，导致任务完全无法推进**

如果写“永远不修改文件”，那么所有自动化任务都会卡住。更好的写法是“默认不修改文件；当用户明确要求修改时，先输出 diff 或计划，确认后执行”。

**3. 没有给“失败”留出口**

很多 SOUL 只写正常流程，不写失败流程。Agent 在工具报错后容易反复重试同一个错误，或者擅自换一种未授权的方式。明确失败策略能减少这类情况。

**4. 与插件自带指令冲突**

某些插件会注入自己的提示词，比如要求 Agent 每次调用后都输出特定格式。SOUL 里要写明优先级：“当插件指令与本文件冲突时，以本文件为准，除非用户当前消息明确覆盖。”否则 Agent 容易在不同指令间犹豫。

**5. 忽视版本管理**

`SOUL.md` 改坏后会直接影响后续所有会话。建议放进 git，每次修改写清楚变更原因。也可以给关键版本打 tag，方便回滚。

## 可复用建议

- **用“可观察行为”定义人格**：不说“友好”，说“不用反问句，先给结论再给解释”。
- **边界分三级**：禁止、默认不做但可确认、主动执行。这样 Agent 不会把每件事都问一遍。
- **为工具策略写默认值**：优先工具、失败降级、禁止工具各自列清楚。
- **把 SOUL 文件纳入测试**：写几个固定任务，检查 Agent 是否遵守边界。比如“尝试删除文件”应触发确认，而不是直接执行。
- **控制长度**：`SOUL.md` 不是越长越好。800~1500 字通常够用，太长会增加模型忽略关键规则的概率。

## 总结

`SOUL.md` 不是给 Agent 写一篇自我介绍，而是给自动化系统加一个稳定、可回归、可回归失败的人格和边界层。它解决的不是“让 Agent 更聪明”，而是“让 Agent 更可控”。

在 OpenClaw + MCP + 插件的组合里，工具生态已经足够丰富，真正缺的往往是一个清晰的决策内核。把 SOUL.md 当成工程文件维护，比每次在 prompt 里临时补规则可靠得多。
