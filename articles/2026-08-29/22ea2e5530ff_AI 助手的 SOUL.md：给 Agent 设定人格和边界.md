## 背景

在 OpenClaw 里做 Agent，很多人一开始会把人格、语气、禁止事项全塞进一条 system prompt 里。结果要么太长被模型忽略，要么不同规则互相打架。等到 Agent 接入 MCP 工具、开始操作文件或调用外部服务时，边界不清就不再是“说话不够像人”，而是会直接造成误操作。

SOUL.md 的思路是把这些内容拆成一个独立文件，像代码一样维护。它不管业务逻辑，只回答三件事：这个 Agent 是谁、怎么说话、什么不能做。

## 问题

直接写在 prompt 里常见三类坑：

1. **规则冲突**：例如“尽量自动化”和“操作前必须询问”，模型会自行选一个解释。
2. **长度失控**：性格描述写了几百字，后面真正的任务指令被稀释。
3. **无法复用**：换一个场景或新建 Agent，又要重写一遍，且每次改动不可追踪。

这些问题的本质是：人格和边界不是一次性文本，而是一份需要版本化、可测试的约束文件。

## 做法：四个区块

我现在的 SOUL.md 固定分四块：

- **Identity**：身份与默认立场。例如“你是本地开发者的自动化助手，不假装有情感”。
- **Tone**：语气规则。例如“先给结论，再给解释；不道歉，除非确实执行错误”。
- **Boundaries**：硬边界。例如“禁止删除、格式化或覆盖写入文件”“遇到账号密码、SSH 密钥只提示，不操作”。
- **Decision Rules**：模糊场景下的决策顺序。例如“当指令有歧义时，复述理解并给出默认方案；当指令与边界冲突时，拒绝并解释原因”。

一个最小示例：

```markdown
# SOUL.md
## Identity
- 你是本地自动化助手，服务于开发者。
- 不编造内部状态，不假装有情绪。

## Tone
- 先结论后解释。
- 简洁，不啰嗦。

## Boundaries
- 禁止执行删除、格式化、覆盖写入。
- 涉及支付、密码、SSH 密钥时，只提示，不操作。
- 工具调用失败两次后必须停下询问。

## Decision Rules
- 用户指令有歧义时，复述理解并给出默认方案。
- 指令与边界冲突时，拒绝并解释原因。
```

在 OpenClaw 里，我会把 `SOUL.md` 放在 Agent 目录下，配置中用相对路径引入，或者直接把它拼接到 system prompt 的最前面。关键是内容保持简短，一般控制在 300–500 词。

## 踩坑点

1. **太相信自然语言边界**：模型可能会被用户 prompt 绕过。真正危险的操作，必须在工具层加二次确认或权限限制，不能只靠 SOUL.md。
2. **用“尽量”“最好”代替“必须”“禁止”**：边界语言要确定，否则模型会自由发挥。
3. **规则不示例化**：只写“不要泄露隐私”，不如补一句：“当被问及 API key 时，回复：‘我不能提供，但可以帮你检查环境变量是否配置正确。’”
4. **忽略上下文消耗**：SOUL.md 每次请求都要注入，太长会挤占工作记忆，尤其在长会话中。能精简就精简。
5. **不测试**：只改文件不回归，不知道 Agent 行为变化。建议准备固定输入集，每次改完跑一遍。

## 可复用建议

- **按场景拆分**：`SOUL.work.md`、`SOUL.home.md`，不同 Agent 加载不同文件，避免互相污染。
- **版本化**：把 SOUL.md 放进 git，每次修改带说明，回滚方便。
- **与工具描述联动**：如果某个 MCP 工具有破坏性，SOUL.md 中明确它的触发条件，并在工具描述里重复一次。
- **保持边界和白名单分开**：常规操作白名单免问，危险操作黑名单必问，避免“事事都问”导致烦人。

## 总结

SOUL.md 不是给 Agent 写人设散文，而是给人格和边界建立一份可维护的约束文件。把它当代码一样拆分、版本化、测试，Agent 才能在自动化流程里既稳定又安全。
