## 背景：Agent 很能干活，但它不认识你

用 OpenClaw 或类似 Agent 工具时，一个常见场景是：你给它一个任务，它开始生成命令、写脚本、改配置，但总是差那么一点。不是能力不够，而是它不知道你常用的目录结构、本机环境、代码风格、甚至哪些目录不能碰。

每次会话都是空白开局，你不得不反复解释：

- “我的项目在 `~/work/project-a`，不是 `~/project`。”
- “用 pnpm，不要用 npm。”
- “测试跑 vitest，不要生成 jest 配置。”
- “不要自动执行 git push，先给我过目。”

这些信息不是任务本身，但决定了任务能否一次做对。把重复出现的个人信息和约束固化下来，就是 USER.md 的价值。

## 问题：上下文稀缺，用户信息却总是“口述”

Agent 的上下文窗口有限，如果每次都临时粘贴一段个人说明，会挤占真正的任务上下文。更麻烦的是，不同会话里的描述可能不一致：今天说“注释用中文”，明天忘了说，Agent 就默认英文注释。

USER.md 解决的是“稳定用户模型”的问题。它让 Agent 在启动时或任务开始前读取一个结构化文件，快速建立对你和当前环境的认知，减少反复澄清，也降低前后不一致带来的返工。

## 做法：维护一份可被 Agent 读取的 USER.md

在 OpenClaw 中，通常可以在用户目录或项目根目录放置 `USER.md`，并在启动配置或任务入口中引用它。具体路径以你使用的工具文档为准，关键是让 Agent 在开始推理前能够加载到这些信息。

### 1. 内容建议模块

一份可用的 USER.md 不需要长篇大论，建议包含以下几个模块：

```markdown
# 用户环境

## 身份
- 后端开发，主要写 TypeScript 和 Go
- 当前在维护一个内部平台

## 环境
- OS: macOS 14 / Ubuntu 22.04
- Shell: zsh
- Editor: VS Code
- 包管理: pnpm

## 技术栈
- 前端: React + Vite
- 后端: Node.js + Fastify
- 数据库: PostgreSQL
- 部署: Docker Compose

## 偏好
- 使用 TypeScript 严格模式
- 测试用 vitest，不用 jest
- 注释用中文
- 错误处理偏好显式返回，不抛异常

## 约束
- 不要修改 /etc 下任何文件
- 不要自动执行 git push 或 git commit --amend
- 生产环境相关操作必须先给出手动执行步骤
- 只读分析时不要创建临时文件到项目外

## 常用命令
- 安装依赖: pnpm install
- 启动开发: pnpm dev
- 跑测试: pnpm test
```

### 2. 让 Agent 读到它

如果 OpenClaw 支持自动加载 `~/.openclaw/USER.md`，直接放进去即可。如果不支持，可以在任务 prompt 的开头加上类似：

```text
请先阅读 ~/.openclaw/USER.md，并严格遵循其中的偏好和约束。
```

对于项目级信息，可以在项目根目录放一份 `PROJECT.md`，并在任务里让 Agent 同时加载全局 USER.md 和项目文件。这样既保持全局一致，又能覆盖项目差异。

## 踩坑点：看似简单，实际容易翻车

1. **把敏感信息写进去**  
   API key、SSH 私钥、密码、内网地址都不应该出现在 USER.md 里。它可能被日志记录、同步到仓库或分享出去。敏感信息一律通过环境变量注入，USER.md 只写“使用 `$DATABASE_URL`”这样的引用。

2. **文件过大，淹没重点**  
   写了几百行个人喜好，Agent 读完已经消耗大量 token，反而忽略关键约束。建议控制在一两百行以内，重要的约束放在最前面。

3. **信息过时**  
   换了技术栈或目录结构，USER.md 没更新，Agent 就会按照错误信息执行。需要像维护代码文档一样定期更新。

4. **全局与项目冲突**  
   全局 USER.md 说“用 pnpm”，但某个老项目只能用 npm。如果 Agent 只读全局文件，就会出错。建议明确优先级：项目级文件覆盖全局文件，并在任务中说明。

5. **权限边界模糊**  
   只写了“不要执行危险操作”没用，要具体到命令和目录。例如“不要删除 `node_modules`”“不要递归 chmod”。

6. **格式混乱**  
   Markdown 结构不清晰，Agent 可能解析错字段。保持简单、层级分明，避免嵌套过深。

## 可复用建议

- **模块化拆分**：全局 USER.md 放通用信息，项目级文件放具体信息，避免一份文件堆满所有内容。
- **提供最小模板**：团队内可以维护一份模板，新成员复制后快速修改。
- **定期审计**：每周或每次环境变更后检查 USER.md，删除过时项。
- **版本管理**：把 USER.md 放进 dotfiles 仓库，可回溯变更。
- **敏感信息只引用不落盘**：用环境变量或密钥管理工具。
- **给 Agent 明确读取顺序**：全局 -> 项目 -> 任务临时说明，后者优先级更高。

## 总结

USER.md 是上下文工程里投入很小、收益很直接的一环。它不能解决所有问题，但可以把“你需要知道我是谁”这件事从每次会话的口述，变成一份稳定的、可维护的、可版本化的文件。

对于 OpenClaw/Agent/MCP/插件/自动化实践者来说，它不是一个花哨技巧，而是一种基础纪律：把重复的信息写下来，让 Agent 真正按你的方式工作。写一份精简、准确、边界清晰的 USER.md，可能比多调几次 prompt 更管用。
