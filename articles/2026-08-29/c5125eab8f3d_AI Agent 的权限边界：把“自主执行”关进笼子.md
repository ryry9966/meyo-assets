过去一年，Agent 已经从“帮你查资料”进化到“帮你改文件、发消息、跑命令、调 API”。在 OpenClaw/MCP 这类工具链里，一个插件往往就能把 shell、文件系统、浏览器、支付接口暴露给模型。能力越强，越要回答一个工程问题：哪些操作该让 Agent 自己干，哪些必须停下来等人确认。

## 问题

如果所有操作都问人类，Agent 会变成“聊天机器人”，自动化价值归零；如果完全自主，一次误删、一次错误 push、一次重复扣费就可能造成真实损失。不能靠“我觉得模型已经很聪明了”来兜底，需要一套可落地的权限边界。

## 做法：四档权限分级

我目前在实践中用四档分级，在 OpenClaw 的工具/插件层强制，而不是只写进 system prompt。

1. **只读与查询：自己干**  
   不改变状态、不触发副作用、不泄露敏感字段。例如读取单个文件、查询公开 API、查看构建状态。注意：只读不等于安全，后面会讲。

2. **低风险可逆：自己干，但留痕**  
   操作可逆、有回滚点、影响面小。例如创建临时目录、在隔离环境安装依赖、运行测试、生成报告。这类操作要自动记录命令和结果，方便回溯。

3. **中风险不可逆或影响他人：先问**  
   例如 git push、删除用户目录文件、发送消息/邮件、修改配置、调用付费 API。Agent 必须给出“将要执行的动作 + 影响范围 + 可逆性”，等待人类批准。审批信息要具体，不能只给一句“是否执行 rm？”。

4. **高风险/破坏性/敏感：默认禁止或双人确认**  
   例如 rm -rf、sudo、数据库结构变更、读取 .env/.ssh、外发内部数据。这类操作在工具层直接拦截，需要额外令牌或明确的维护模式才能放开。

实现上，可以在 OpenClaw 的工具封装层给每个工具打风险等级；低风险工具放行，高风险工具触发审批回调或进入确认模式。同时设置 dry-run 模式：中高风险操作先打印计划，不实际执行。

## 踩坑点

- **把“只读”当安全**。有些 MCP 工具的“查询”接口会返回密钥、用户手机号、内部路径；有些 GET 接口可能触发任务。要在输出前做字段脱敏，不要信任工具描述里的“readonly”。
- **提示词注入可绕过权限**。网页、邮件、文档里的一句话可能诱导 Agent 执行危险操作。权限边界必须在工具层强制，不能依赖 prompt 约束。
- **工具粒度太粗**。如果一个“shell”工具允许任意命令，权限分级就形同虚设。应封装成具体命令：run_test.sh、git_push、list_files，并限制参数。
- **自动重试放大危险操作**。失败重试可能重复扣费、重复发送。对中高风险操作，关闭自动重试，或要求每次重试都重新确认。
- **审批信息不完整**。只显示“执行 rm -rf /tmp/xxx”但不知道影响多少文件、是否可恢复。审批界面应展示命令、路径、影响列表、回滚方案。

## 可复用建议

- 最小权限：默认只读，按需提权。
- 禁止裸 shell：用白名单命令或封装脚本。
- 保护敏感路径：$HOME/.ssh、.env、密钥目录、生产配置。
- 环境隔离：测试/沙箱可自主，生产需审批。
- 可打断：让用户能随时暂停或取消 Agent 的批处理任务。
- 记录决策：每次自主执行和审批通过都留日志，便于排障和审计。

## 总结

权限边界不是“信不信任 AI”的问题，而是把操作风险纳入工程控制。低风险区让 Agent 高效自主，高风险区让它老实停下来问。对于 OpenClaw/MCP 实践者来说，最好的体验不是“Agent 什么都能干”，而是“该干的干得爽，该问的问得准”。
