“让 Agent 自动提交代码”听起来很美，但直接把 shell 交给模型，通常会在第一次运行时就踩坑。OpenClaw-CN 这边不少项目已经在用 MCP/插件做 Git 自动化，本文不讨论“能不能”，只讲怎么把权限、审计和回滚边界做得足够小。

## 背景与问题

手工整理提交、创建分支、清理已合并分支，确实耗时。Agent 擅长读取 diff、归纳变更、按规范生成 commit message。但 Git 是高风险工具：一条 `push --force`、`reset --hard` 或 `clean -fd` 可能造成不可逆损失。模型也可能把临时文件、本地配置一并加入提交，或者在冲突时自作主张继续 rebase。

所以目标不是让 AI 拥有完整 Git 权限，而是把它包装成一组受控工具。

## 做法：先封一层，再谈自动化

### 1. 不暴露系统 Git 给 Agent

使用 MCP Git server 或自建 wrapper。OpenClaw 里可以把 MCP 命令指向脚本 `git-safe`，只提供：

- 只读：`status`、`diff`、`log`、`branch -l`、`show`
- 写：`checkout -b`、`commit`（仅限 staged）、`branch -d`（仅已合并）
- 高危命令默认不提供：`push --force`、`reset --hard`、`clean`、`rebase --continue` 等

### 2. 写操作必须确认

commit 前让 Agent 给出：

- 变更文件列表
- 完整或摘要 diff
- 拟提交的 commit message

确认后才执行。创建分支只允许从 main 拉出，不允许从任意脏工作区创建。

### 3. 固定提交信息格式

在系统提示中写明：

```
type(scope): subject

body: 说明为什么改、影响范围、测试方式
```

禁止 “update code”、emoji、无信息量描述。让 Agent 先读 `git diff --stat` 和关键 diff，再生成 message。

### 4. 分支自动化流程

- 从 issue 或任务 ID 生成 `feat/<id>-<slug>` 或 `fix/<id>-<slug>`
- 创建前检查工作区是否干净，分支是否已存在
- 同步主干只做本地 merge/rebase，不自动 push
- 清理已在远端合并的分支时，先列出清单，确认后执行 `branch -d`，不用 `-D`

### 5. CI/钩子兜底

保护 main 禁止直接推送；pre-push 或 CI 检查分支名、commit message 是否符合规范。即使 Agent 误操作，也会被远端拦住。

## 踩坑点

- **模型喜欢 `git add -A`**：一次把所有文件加入暂存，包括 `.env`、临时文件、本地配置。应让 Agent 只提交相关路径，或先展示 `status --short` 人工勾选。
- **diff 被截断**：部分 MCP Git server 对 diff 输出长度有限制，模型只看前半段就生成错误的提交信息。需要限制单次提交文件数，或使用 `diff -- <path>` 分片读取。
- **冲突时继续自动处理**：`pull --rebase` 或 merge 冲突后，模型可能尝试自行解决，结果丢代码。规则应设为：冲突即停止，转人工。
- **远端 push 过于主动**：没有远端分支保护时，模型可能把本地分支推上去。务必区分“本地自动化”和“远端变更”：远端操作单独确认。

## 可复用建议

- 把 Git 能力收口成一个 `git-safe` MCP/wrapper，命令白名单化，所有写操作日志记录。
- 默认 dry-run：先展示将执行什么、影响哪些文件。
- 高频任务先跑在克隆仓库或测试分支，验证模型行为后再接入主项目。
- 将提交信息规范、分支命名、停止条件写进 OpenClaw 的系统提示，不要每次重复。
- 至少保留最近 50 条 Git 操作审计记录，便于回溯。

## 总结

AI 助手管理 Git，本质上不是“把终端交给模型”，而是把 Git 变成受控工具链。权限收口、写操作确认、diff 完整性、CI 兜底这四件事做到位后，Agent 可以在生成提交信息、创建规范分支、清理已合并分支等低频场景稳定工作。先在可回滚、低风险的环节落地，比一次性全面自动化更实际。
