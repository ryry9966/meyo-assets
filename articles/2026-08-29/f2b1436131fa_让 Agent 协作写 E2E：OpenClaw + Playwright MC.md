## 背景

E2E 测试的价值不用多讲：它能覆盖真实用户路径，抓住单测和集成测试看不到的问题。但维护成本也很高——选择器脆弱、异步等待不稳定、登录态处理麻烦、测试数据容易互相污染。很多团队不是不想写 E2E，而是写了之后跟不上前端变更，最后变成“红一片就跳过”。

我最近在 OpenClaw 环境里做了一轮尝试：不再把“写 E2E 测试”当成单个 AI 生成任务，而是拆成多个 Agent 协作，让探索、生成、执行、修复、审查各司其职。整体效果比单次生成稳定很多，但也踩了不少坑。

## 问题

直接让一个 Agent 生成 Playwright 测试，常见失败模式是：

- 使用脆弱的 CSS 选择器，比如 `div:nth-child(3) > span`；
- 断言空泛，只检查某个文本存在，不检查交互后的状态；
- 登录态处理不完整，生成的测试一跑就跳回登录页；
- 异步等待靠 `waitForTimeout`，慢且不稳定；
- 生成完不验证，坏代码直接混入仓库。

本质上，单 Agent 缺乏稳定上下文：它不知道页面的可访问性结构、项目里已有的测试约定、data-testid 规范，也没有能力运行测试并回灌失败信息。

## 做法：拆成多个 Agent 协作

我在 OpenClaw 里把流程拆成 5 个 Agent，每个只负责一段可验证的闭环。

### 1. 工具边界

- **explorer**：挂 Playwright MCP，拥有导航、点击、输入、读取可访问性快照等浏览器工具；
- **runner**：挂本地命令工具，只负责运行 Playwright 测试并收集失败信息；
- **generator / fixer / reviewer**：只给文件读写权限，不直接操作浏览器。

这样避免一个 Agent 既要浏览页面、又要写代码、又要跑测试，上下文过载。

### 2. 探索阶段

让 explorer Agent 按真实用户路径走一遍关键流程，输出“页面状态记录”，包括：

- URL 和路由变化；
- 关键可访问性节点的 role、name、层级；
- 必需的登录态、权限、前置数据；
- 等待条件，例如哪个接口返回后才渲染表格。

要求它只记录，不写代码。这一步的目标是拿到稳定、脱敏后的页面结构，而不是让模型看图猜。

### 3. 生成阶段

generator Agent 接收三份输入：

- explorer 的页面状态记录；
- 项目已有测试样例；
- 测试约定文档。

它必须先输出测试计划，包括文件路径、用例列表、动作序列和断言目标。计划通过后再生成代码。Prompt 里强制要求：

- 优先 `getByRole` / `getByTestId`；
- 禁止裸 CSS 结构选择器；
- 等待策略使用 `expect(locator).toBeVisible()` 或 `waitForResponse`，而不是固定 `waitForTimeout`；
- 登录态通过 fixture 或 `storageState` 注入，不在用例里写账号密码。

### 4. 执行阶段

runner Agent 在 headless 环境运行测试，收集结构化失败信息：文件、用例、错误行号、期望值/实际值、页面快照、网络失败请求。

这些信息会原样回灌给 fixer Agent，避免把整段日志直接丢给模型。

### 5. 修复阶段

fixer Agent 只允许改测试代码，不允许改业务代码。如果失败来自业务 bug，必须标记为 `product issue`，而不是继续修测试。修复后重新执行，最多三轮。超过三轮就停下来，交给 reviewer 判断，防止陷入“修了一个又坏两个”的死循环。

reviewer Agent 负责检查选择器质量、断言是否被放松、是否有 `it.skip` 或删除断言的补丁。

## 踩坑点

### 1. 浏览器上下文不一致

Playwright MCP 探索时用的是可见浏览器，执行时是 headless 新上下文。登录态、本地存储可能丢失。解决方案是把登录步骤抽成 fixture，或使用 `storageState`，不要在测试里硬编码账号密码。

### 2. Agent 爱用 `waitForTimeout`

这是最明显的坏味道。必须在生成和修复 prompt 里明确禁止，并给出替代写法。否则测试越来越慢，偶发失败越来越多。

### 3. 选择器过度依赖 DOM 结构

即使给了 data-testid 规范，模型有时还是会抄一个很长的 CSS path。reviewer 需要设置硬规则：超过两层结构选择器直接驳回，要求改成 `getByRole` 或 `getByTestId`。

### 4. 动态数据被写死

探索记录里可能包含时间戳、随机 ID、订单号。生成代码如果直接照抄，跑一次就挂。需要让 explorer 做脱敏，把动态内容标记为变量或正则。

### 5. 修复阶段容易“假通过”

模型很可能通过删除断言、跳过用例来让测试变绿。修复 prompt 里必须明确：禁止 `it.skip`、禁止删除断言、禁止放宽期望。失败用例要么修复，要么标记为业务问题，不允许默默消失。

### 6. 无限制探索消耗大量 token

给 explorer 设置最大步数和最大读取节点数，并要求它优先读取可访问性快照，不要对整页截图做视觉判断。截图识别不稳定，成本也高。

## 可复用建议

- **用可访问性快照，不用截图识别**：快照更稳定、更便宜、可 diff，也更接近 Playwright 的定位方式。
- **维护一份测试约定文档**：包含 data-testid 命名、登录 fixture、等待策略、禁止事项。把它作为 Agent 的固定上下文。
- **先计划，后代码**：计划可评审，能大幅减少生成返工。
- **失败日志结构化回灌**：只给文件、错误、期望/实际、页面状态，不要把整段日志塞给模型。
- **CI 里先跑草稿，通过后再合并**：不要让 Agent 直接推主分支。
- **定期重跑探索，触发更新**：页面变化后可以自动发现差异，但更新必须走 PR，人工审批。
- **限制修复轮次和 diff 范围**：防止 Agent 把失败测试改成永远通过的“假测试”。

## 总结

Agent 协作写 E2E 的核心不是“模型替人写测试”，而是把探索、生成、执行、修复串成一个可回滚、可审计、可回灌失败的流水线。工具边界清晰、上下文稳定、失败反馈结构化，这三点比换更强模型更关键。

目前更务实的定位是：让 Agent 当“测试草稿生成器 + 维护助手”，人工审核仍然不可少。这样才可能真正降低 E2E 的维护成本，而不是引入一层新的脆弱抽象。
