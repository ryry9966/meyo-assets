# 用 Agent 协作生成 E2E 测试：从“能跑”到“可维护”

## 背景

E2E 测试的价值不用多说：它能覆盖真实用户路径，防止回归。但做过的人都知道，E2E 用例的维护成本非常高。页面一改版，选择器就失效；异步逻辑一调整，等待策略就要重写；最难受的是，手写测试经常是在项目后期补，补出来的用例往往只覆盖了主流程，边界场景和异常路径长期空白。

在 OpenClaw 的 Agent 实践里，我们开始尝试把“写 E2E 测试”这件事拆成多个 Agent 协作完成。目标不是让 AI 替代测试工程师，而是让它承担最重复的部分：根据页面结构生成初版用例、根据失败日志做第一轮修复、在代码变更后更新失效选择器。

## 问题：直接让 LLM 生成的测试为什么不可靠

如果只是把 PRD 或需求描述丢给模型，让它输出测试代码，通常会有几个典型问题：

- **选择器脆弱**：模型会倾向于用 CSS path、XPath 或很深的 DOM 层级，页面稍微改动就挂。
- **脱离项目上下文**：不知道你现有的测试框架、fixtures、命名约定、已有命令。
- **无法验证**：生成的用例没有运行过，可能连 import 路径都是错的。
- **断言不合理**：要么断言太多实现细节，要么只检查“页面没报错”，实际是假绿。
- **上下文不足**：模型不了解真实 DOM 结构、异步渲染时机和路由跳转。

所以，单纯“生成测试代码”不是难点，难点是**生成后能跑、跑了能维护**。

## 做法：多 Agent 协作 + MCP 运行反馈

我们目前的流程是四个角色接力，核心是通过 MCP 浏览器工具把“真实页面信息”和“真实运行结果”喂给 Agent。

### 1. Explorer Agent：读取真实页面

通过 MCP server 暴露浏览器能力，比如 `browser_snapshot`、`browser_click`、`browser_navigate`。Explorer Agent 打开目标页面，拿到可访问性树、关键 DOM 节点、路由状态和已有的 `data-testid` 约定。它的输出不是整页 HTML，而是一份“页面对象候选清单”：每个可交互元素对应的稳定选择器、角色、可访问名称、触发后的路由变化。

### 2. Writer Agent：按项目风格生成用例

Writer Agent 拿到 Explorer 的输出，加上测试意图和现有测试样例，生成第一版测试代码。这里的关键是**不要让它自由发挥**，而是要求它复用项目已有的 page object、commands、fixtures。如果项目里有 `loginAs` 命令，就必须用 `cy.loginAs` 或 Playwright 的 `page.login()`，不允许自己再写一遍 UI 登录流程。

### 3. Runner / Repair Agent：跑测试、读失败、再修复

生成的测试直接丢给 Runner Agent，通过 MCP 调用 Playwright 或 Cypress 运行。运行失败后，把失败堆栈、截图、DOM 快照回传给 Repair Agent，让它做定向修复。这里要限制迭代次数，一般是 2-3 轮。超过三轮还修不好，就标记为需要人工介入，而不是继续让 Agent 瞎改。

### 4. 人工 Review：只重点看选择器和断言

最终 diff 进入分支，人工 review 时重点关注两点：选择器是否基于 `data-testid` / role / accessible name；断言是否验证了业务结果，而不是验证了实现细节。其余代码风格、import 顺序等可以放宽。

## 踩坑点

这套流程跑下来，踩过的坑比较集中：

- **别让 Agent 用 CSS path**。一定要在 prompt 里明确禁止 XPath 和深层 CSS selector，只允许 `data-testid`、ARIA role、accessible name。否则第一版跑得通，第二周页面改个 class 就挂。
- **假绿比失败更危险**。Repair Agent 为了通过测试，可能会把断言改弱，或者直接 `test.skip`。所以要限制它的修改范围，并对断言变化做 diff 审核。
- **异步等待不要用 `waitForTimeout`**。模型生成固定等待很常见，但这是不稳定来源。应要求显式等待某个元素可见、网络空闲或路由跳转完成。
- **全量 DOM 会撑爆上下文**。不要直接把 `document.body.innerHTML` 塞给 Agent。只传可访问性树和关键节点，必要时截取局部 DOM。
- **测试意图漂移**。如果没有写清验收标准，Agent 可能把“验证登录成功”写成“验证登录按钮颜色变化”。给每个用例写一句明确的业务断言。

## 可复用建议

- **先做 smoke 用例**。选 3-5 条核心路径作为种子，跑通流程后再扩展到更多场景。
- **把稳定操作封装成 MCP 工具或 commands**。例如 `mcp__browser__click_by_testid`、`mcp__browser__wait_for_route`。Agent 调用这些原语，比直接操作裸 DOM 更稳定。
- **保留失败日志作为上下文**。每次修复时把上一轮失败信息、截图和 DOM 快照一起传给 Agent，修复成功率会明显提高。
- **用 Git diff 跟踪 Agent 改动**。不要让它直接 push 到主分支，先开 feature 分支，人工确认后再合并。
- **限制 Agent 的自治范围**。它只负责生成、运行、修复这三步，不负责决定“测什么”。测试策略和优先级由人定。

## 总结

Agent 协作在 E2E 测试里最适合干的活是：**生成测试脚手架、根据真实页面补全选择器、根据失败日志做第一轮维护**。它不能替代测试工程师，但能显著减少重复劳动。把 Agent 当成一个可以跑测试、读报错、改代码的结对实习生：你负责给清楚上下文和验收标准，它负责把脏活累活先干一遍。上下文越具体，反馈闭环越完整，产出越可维护。
