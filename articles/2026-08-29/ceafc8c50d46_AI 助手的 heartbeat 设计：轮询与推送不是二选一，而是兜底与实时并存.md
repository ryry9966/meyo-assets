## 背景

在 OpenClaw、Agent 以及 MCP 工具/插件实践里，heartbeat 不只是“进程还活着吗”，更多时候是长任务状态同步、子 Agent 探活、外部工具结果回传的基础机制。

常见两条路线：
- 轮询：宿主或客户端定期请求 `/status`、`/tasks/{id}` 或轻量 `/healthz`。
- 推送：通过 SSE、WebSocket、webhook 等方式，状态变化时主动上报。

聊天里常会把二者对立起来，实际上工程里很少只用一种。它们解决的是不同层次的问题。

## 问题

轮询的麻烦在于：
- 固定间隔太短，无状态变化时会产生大量无效请求；
- 间隔太长，任务失败或卡死后发现太迟；
- 多任务并发时 N 个任务各自轮询，负载容易扩散；
- 如果每次轮询都拉完整状态，payload 会被放大。

推送的麻烦在于：
- 需要维护长连接或回调通道，断线、重连、鉴权、幂等都要处理；
- 客户端重启或网络抖动后会漏事件；
- 推送过快时消费方可能处理不过来，出现堆积或乱序；
- 回调地址不可达时，服务端需要有重试和补发策略。

因此，heartbeat 设计的第一件事不是选轮询还是推送，而是把“存活”和“状态同步”拆开。

## 做法/步骤

1. **定义心跳语义**
   建议至少拆成两层：
   - Liveness：`/healthz` 或任务租约，只回答“是否存活/最近活跃时间”。
   - Status/Progress：任务状态、阶段、错误信息，走事件推送或按需查询。

   不要把大 JSON 状态塞进每个 liveness 心跳里。

2. **轮询端做动态间隔和批量**
   空闲时拉长间隔，有活跃任务时缩短；用 `If-Modified-Since`、ETag 或版本号减少无效传输。多任务场景提供批量状态接口，例如 `/tasks/status?ids=...`，避免 N+1 查询。

3. **推送端优先考虑 SSE/WebSocket，webhook 只用于外部系统**
   内部 Agent 与插件之间，SSE 或 WebSocket 比公网 webhook 更可控。事件需要带单调递增的 `event_id` 或 `seq`，消费端做去重和乱序判断。

4. **混合兜底**
   正常路径以推送为主；客户端若超过 `heartbeat_timeout` 没有收到任何事件，就降级到低频轮询 `/status`。一旦推送恢复，停止轮询。这样断线不会漏掉任务完成这类关键事件。

5. **用租约避免误判**
   长任务主动续期，服务端记录 `last_seen_at` 和租约过期时间。只有连续丢失多次心跳或租约过期，才标记疑似失联，避免网络抖动造成误报。

## 踩坑点

- **一刀切轮询间隔**：空闲任务仍高频拉取，浪费资源。按任务活跃度动态调整。
- **把 heartbeat 做成大而全的状态接口**：心跳包越来越大，liveness 探测反而变重。
- **推送断线没有查询兜底**：漏掉“任务完成”事件后，客户端一直傻等。状态查询接口必须保留。
- **重连后全量补发不幂等**：事件重复或乱序覆盖了较新状态。用 `event_id` 去重，状态带版本号。
- **依赖连接本身保活长任务**：HTTP 短轮询经过网关可能被超时或缓冲，长任务应在任务侧更新时间戳，而不是靠连接不断开。
- **忽略背压**：推送过快导致消费队列堆积，最终内存上涨。客户端要有队列上限，服务端可批量发送。

## 可复用建议

在 OpenClaw/Agent 项目里，可以把 heartbeat 收敛成独立组件，而不是每个插件各自实现。统一一个轻量协议：

- 字段尽量少：`last_seen_at`、`status`、`version`、`seq`；
- 默认混合：SSE/WebSocket 推送 + `GET /tasks/{id}/status` 兜底；
- 轮询加缓存和条件请求，批量接口减少连接数；
- 推送事件带 `seq`，消费端按版本号判断新旧；
- 记录探测延迟、丢失率、误报率，用来调整超时阈值；
- MCP 工具如果是长任务，不要让 MCP 请求本身一直阻塞，应返回 `task_id`，通过 heartbeat 通道查询进度。

## 总结

轮询和推送不是对错选择题。轮询胜在简单、可控、易兜底；推送胜在实时、低延迟、体验好。工程上更实用的组合是：

> liveness 用轻量轮询兜底，状态变更用推送加速，断线用查询补漏，任务续期用租约避免误判。

先把心跳语义和协议定清楚，再决定通道类型，比一开始纠结“到底用轮询还是推送”更重要。
