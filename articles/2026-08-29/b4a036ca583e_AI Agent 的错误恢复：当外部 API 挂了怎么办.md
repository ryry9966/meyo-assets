## 背景

在 OpenClaw 这类 Agent 工程里，真正让任务失败的不一定是模型能力，而是工具链上的外部依赖。天气、搜索、CRM、支付、MCP server 等任何 HTTP API 都可能超时、限流、返回 5xx，甚至状态码 200 但内容是一张登录页。API 挂掉不是小概率事件，而是长期运行必须处理的常态。

## 问题

典型链路是：Agent 发起 tool call → 插件/MCP server 请求外部 API → 超时或异常 → 工具把原始错误抛给模型。此时代理容易进入两类坏分支：一是模型看到堆栈后开始“推测”API 可能返回了什么；二是 Agent 反复重新调用工具，导致上下文膨胀、token 消耗、甚至重复副作用。没有恢复策略的 Agent，通常只能用于演示。

## 做法/步骤

1. **在工具层做错误分类，不要只返回异常字符串。**  
把错误分成：可重试（429/502/503/504/网络瞬断）、不可重试（400/401/403/404/422）、假成功（200 但响应体是登录页/限流页/空数据）。给 Agent 返回结构化错误：`{"ok":false,"error_type":"upstream_timeout","retryable":false,"fallback_used":true,"message":"..."}`。

2. **设置短超时与重试预算。**  
连接超时 2s、总超时 8s；重试最多 2～3 次，只针对可重试类型。指数退避加抖动：例如 base 200ms，每次翻倍，再加 0～100ms 随机抖动，避免多个请求同时重试造成雪崩。

3. **引入熔断。**  
连续失败 5 次或错误率超过阈值后，熔断器打开，后续请求快速失败 30～60 秒；半开状态只放一个探测请求，成功则关闭，失败继续熔断。

4. **降级与缓存。**  
对读接口缓存最近一次成功结果，失败时返回 stale data 并标记 `stale=true`。如果外部 API 只是辅助信息，可告知 Agent：“该数据源当前不可用，请基于已有上下文继续，不要虚构数据。”不要让模型假装取到了实时值。

5. **控制副作用。**  
对写操作加幂等键或请求指纹，重试前检查是否已经成功，避免重复创建订单、重复发送消息。外部 API 挂掉的时间点往往不确定，靠“重试一次”很容易产生重复副作用。

6. **做可观测。**  
记录 request_id、HTTP 状态、延迟、重试次数、是否降级、熔断状态。把外部调用日志与 Agent trace 关联，出问题时能快速判断是模型判断错了，还是上游真的不可用。

## 踩坑点

- 无限重试：工具内部重试 + Agent 再次调用，会让上下文爆炸。
- 把 4xx 当可重试：401/403/422 重试没有意义。
- 没有超时：HTTP 客户端默认可能长时间挂起，卡死整个 Agent。
- 把 200 当成功：登录页、限流页、网关错误都可能返回 200，要校验内容特征。
- 降级不告知模型：模型会误以为拿到了实时数据。
- 缓存没有 TTL 和版本：脏数据比失败更危险。
- 原始堆栈直接丢给模型：模型容易脑补，或给出不稳定的恢复动作。

## 可复用建议

最好做一个统一的外部调用包装器，把 timeout、retry、circuit breaker、fallback、metrics 收敛在一起，所有插件/MCP server 都走同一套策略。工具描述里可以声明“该工具可能返回降级数据”，让 Agent 在规划时就有预期。运行时可动态注入资源健康状态，例如系统提示中标注“当前外部 API 状态：weather 不可用，search 正常”，模型会自然绕开故障资源。最后，建议定期做故障演练：手动断开某个 API，观察 Agent 是否能返回可接受的降级结果，而不是崩溃或胡编。

## 总结

外部 API 挂掉不是异常，而是输入。好的错误恢复不是让 Agent 更“聪明”，而是让工具层更可预期：短超时、有限重试、熔断、降级、结构化错误、灰度演练。把这层做好，Agent 才能从演示走向生产。
