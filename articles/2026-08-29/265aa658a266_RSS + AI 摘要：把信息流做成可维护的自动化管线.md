## 背景
RSS 仍然是最省心的信源接口，但订阅一多后，真正的问题是“没空看”。把全文丢给大模型，成本高、输出飘、还容易重复推送。适合的做法是搭一条小而稳的管线：抓取、清洗、去重、摘要、推送、归档，再把关键环节暴露给 OpenClaw/Agent/MCP 调用。

## 问题
不是写个脚本调 API。实际会遇到：

- 源格式混乱：GUID 缺失、相对链接、CDATA、时区异常。
- 重复推送：同一篇内容因为发布时间或标题微小变化被处理两次。
- 摘要质量不稳定：输出废话多，或格式不可解析。
- 调度重叠：定时任务还没跑完又启动，造成并发写和重复发送。
- 成本失控：每条都取全文再摘要，很快消耗 token。

## 做法
1. **采集与归一化**  
用 feedparser 拉取，只保留 title、link、published、summary、id。link 缺失用 urljoin 补全；id 缺失用 link 做 fallback。

2. **去重和状态**  
建 SQLite 表 items，对 link+title+published 做 sha1 作为 item_key，先查是否存在，处理成功后再 upsert。失败不标记 seen，下次重试。

3. **可选正文提取**  
AI 摘要不一定要全文。优先用源的 summary；若源只有标题，再用 trafilatura 抓正文，但限制超时和最大字符数。

4. **AI 摘要**  
使用 OpenAI-compatible 接口，要求 JSON 输出，字段固定：
`summary / key_points / importance / action_items / confidence`  
Prompt 里明确“只基于给定内容，不补充外部知识，无法判断就写不确定”。max_tokens 控制在 300-500。

5. **推送与失败隔离**  
用 ntfy / Telegram / 飞书 webhook 推送。单条失败记录到 error_log，不阻塞后续。推送内容带原文链接和 AI 摘要，不替代原文。

6. **调度**  
cron 或 systemd timer 每 30 分钟跑一次。用文件锁或 SQLite 事务防止重叠。若已经在 OpenClaw 环境里，可以把 fetch_rss、summarize、mark_seen、push 封装成 MCP tools，由 Agent 按需编排或追问。

伪代码：
```python
key = sha1((entry.get("id") or entry.link).encode()).hexdigest()
if exists(key): continue
summary = summarize(text, source=feed_title)
push(summary, link)
mark_seen(key)
```

## 踩坑点
- 不要仅用 title 做 hash，很多站标题会改，link+title+published 更稳；但同一文章有多个短链时要先 canonize。
- JSON 输出即使开了 response_format 也可能失败，做一次容错解析，失败降级为“截断前 N 字”。
- 时区问题：published 可能是未来时间，不要依赖排序判断新旧，用 seen 去重。
- 限流：给每个源设间隔，避免短时间抓太猛被封。
- 成本控制：先基于标题/摘要做粗过滤，再决定是否调用模型；低相关源用便宜模型。

## 可复用建议
- 先维护 5-10 个高质量源，跑通两周再加量。
- 摘要模板按源微调：新闻源要事实和影响，技术博客要方案和可操作点。
- 保留原始数据（raw/JSONL），便于重放和调试。
- 失败通道与正常推送分开，例如失败发到独立日志，避免污染主信息流。
- 如果接 OpenClaw Agent，建议给 Agent 一个“查询已处理条目”的工具，而不是只让它看推送结果，这样它能回答“今天有哪些值得看”。

## 总结
RSS + AI 摘要的核心不在模型调用，而在去重、清洗、状态管理和失败隔离。把这些基础做扎实后，它才能从一个一次性脚本，变成可扩展、可追问的个人情报管线。
