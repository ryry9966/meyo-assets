# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

在 OpenClaw-CN 社区里，很多同学已经用 Agent 做代码审查、issue 分诊、脚本生成和日志分析。真正落到日常开发流程时，Git 操作仍然偏手工：提交信息写得随意、分支命名不统一、PR 描述复制粘贴、发布前反复检查变更范围。更尴尬的是，Agent 明明已经读完了 diff，却还要人把结论手动敲进 commit message。

本文记录一套在 OpenClaw 上可落地的 Git 自动化方案：用 MCP Git 工具代替裸 shell，用摘要 diff 控制上下文长度，用 hook 和 dry-run 做兜底。适合已经接触过 MCP、插件或自动化脚本的实践用户。

## 问题

一开始最容易踩的坑是直接让 Agent 执行 `git add . && git commit -m "..."`。这看起来能跑通，实际上有几个风险：

1. **权限过大**：Agent 可能执行 `git push --force`、`git reset --hard` 或误删本地分支。
2. **上下文爆炸**：大仓库的完整 diff 很容易超出 token 限制，模型开始截断或编造内容。
3. **误提交敏感信息**：调试日志、本地配置、临时文件可能被一起提交。
4. **非交互环境卡死**：commitizen、交互式 rebase、hook 中的用户输入会让 Agent 一直等待。
5. **提交信息不稳定**：不同模型对 Conventional Commits 的理解有差异，生成的类型、scope、正文格式容易漂移。

因此，Git 自动化不能只靠一句 system prompt，需要从工具边界、输入裁剪、输出结构和人工确认四个层面一起设计。

## 做法：分四步落地

### 1. 用 MCP Git 工具代替裸 shell

在 OpenClaw 的 MCP 配置中挂载一个 Git 服务，并明确区分只读和写操作。只读工具默认开放：`status`、`diff`、`log`、`branch`、`show`。写操作只保留白名单：`commit`、`create branch`、`push` 的封装命令，而不是直接暴露原始 shell。

配置示例思路：

```yaml
mcpServers:
  git:
    command: npx
    args: ["-y", "your-git-mcp-server"]
    env:
      GIT_ALLOW_WRITE: "commit,branch,push"
      GIT_DENY_FORCE: "true"
      GIT_EDITOR: "true"
```

如果暂时没有现成 MCP 服务，可以先用 OpenClaw 的 skill 封装本地 `git` CLI，但入口仍然限制为固定子命令，避免 Agent 自由拼接参数。

### 2. 先摘要，再按需读 diff

不要让 Agent 一上来就读全量 `git diff`。先让它执行：

```bash
git status --short
git diff --stat
git diff --name-only
```

根据变更文件数量和语言类型，再分文件读取关键 diff。一个可复用的 skill 可以命名为 `git-diff-summary`，输出变更文件、增删行数、是否包含二进制文件，并限制最多读取前 20 个文件。这样既省 token，也减少无关上下文干扰。

### 3. 生成提交计划，人工确认后再执行

让 Agent 输出一个 JSON 格式的提交计划，而不是直接执行：

```json
{
  "files": ["src/parser.ts", "tests/parser.test.ts"],
  "type": "feat",
  "scope": "parser",
  "summary": "support nested block parsing",
  "body": "Add recursive descent for nested blocks and update tests."
}
```

OpenClaw 可以把这个 JSON 渲染成确认卡片，用户点确认后才调用写操作。空提交问题可以通过先执行 `git diff --quiet` 判断，无实际变更时直接返回。

### 4. 分支和 PR 描述自动化

从 issue 标题生成分支名时，要统一 slug 规则：小写、连字符分隔、去掉特殊字符。例如 issue 标题“Support nested block parsing”映射为 `feat/parser-nested-block`。创建分支后推送，再用 PR 模板生成描述。这里建议让 Agent 只生成描述草稿，PR 标题和 reviewer 仍由人确认。

## 踩坑点

- **交互式 hook 卡住**：设置 `GIT_EDITOR=true`，并在非交互环境变量中运行，例如 `CI=true`。如果 hook 需要输入，Agent 会一直等待，表现为任务超时。
- **推送前丢上下文**：Agent 提交后可能忘记推送，或者推送到错误远端。封装 push 命令时默认只推送当前分支，并打印 remote 和 branch。
- **误提交 lock 文件或本地配置**：在 `.gitignore` 之外，可以加一份 AI 提交白名单，只允许提交指定目录或文件类型。
- **模型输出漂移**：同一套提示词在强模型上稳定，在弱模型上会漏掉 scope 或生成错误类型。可以把规则写成多条短句，并在 system prompt 里给一个正确示例和一个错误示例。
- **仓库太大**：即使有摘要，巨型 monorepo 仍可能超出限制。可以按 module 或 package 拆分仓库上下文，让 Agent 只关注当前工作目录。

## 可复用建议

1. **默认只读，写入白名单**：永远不要让 Agent 直接拿 shell 权限。
2. **提交计划先审后执行**：用 JSON 结构输出，OpenClaw 渲染成确认步骤。
3. **封装成 skill**：把常用流程做成 `/git-summary`、`/git-commit-plan`、`/git-branch-from-issue`，减少每次重复配置。
4. **保留 dry-run 选项**：所有写操作先展示将执行的命令，确认后再去掉 dry-run。
5. **记录每次自动提交的 diff 来源**：在 commit body 中附加 `--stat` 摘要，方便事后审计。

## 总结

Git 自动化适合编码 Agent 的重复性环节，但前提是把权限边界和人工确认放在前面。用 MCP Git 工具替代裸 shell，用摘要 diff 控制上下文，用 JSON 提交计划保证输出稳定，再用 hook 和 dry-run 兜底安全。这样一套下来，AI 助手才能真正帮你管理代码提交和分支，而不是制造新的代码事故。
