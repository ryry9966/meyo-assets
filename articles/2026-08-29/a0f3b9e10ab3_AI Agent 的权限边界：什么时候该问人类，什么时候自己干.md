## 背景

在 OpenClaw 里，Agent 早就不只是聊天。它通过工具、MCP、插件和脚本连接真实系统，能查日志、改配置、跑命令、发消息、操作资源。权限边界因此从“能不能用某个工具”变成了“什么动作可以自动做，什么动作必须停下来问人”。

如果所有操作都自动，一次误删、误发或误发布就足够严重；如果所有操作都确认，自动化流程会变得又慢又烦。真正可落地的做法，不是给 Agent 一个总开关，而是把动作风险分级，再在工具层和流程层设置硬约束。

## 问题

最容易犯的错误，是把安全边界放在提示词里，比如写“请只执行只读操作”。模型可能会被上下文带偏，也容易被工具描述误导。真正的边界应该在工具策略、参数白名单和确认机制上。

另一个问题是确认疲劳。什么都问，人最终会麻木地一路点允许。权限边界的重点不是“问得更多”，而是“问在关键节点”。

## 做法

### 1. 给动作分级，而不是给 Agent 分级

建议按“影响域 + 可逆性 + 数据敏感度”把动作分成四层：

| 级别 | 典型动作 | 策略 |
| --- | --- | --- |
| L0 只读/可逆 | 查询状态、看日志、生成摘要、dry-run | 自动执行 |
| L1 低影响可逆 | 创建临时文件、发内部测试通知 | 自动执行，结构化审计 |
| L2 中等影响/部分可逆 | 改配置、批量改名、合并分支 | 确认后执行 |
| L3 高影响/不可逆 | 删除资源、发布生产、变更 IAM、调用支付 | 人工确认或双人审批 |

不要只按工具名判断。比如 `rm` 不一定是 L3，删除临时文件可能只是 L1；但要限制路径、文件类型和影响范围。

### 2. 在工具层做默认 deny

OpenClaw 里不要全局开启自动批准。更稳妥的做法是：

- 给 shell 工具设置只读命令 allowlist，例如 `kubectl get`、`git diff`、`ls`、`cat` 等；
- 写命令、删除命令、批量命令默认进入确认流程；
- MCP 如果同时暴露查询和写入能力，尽量拆成两个 server，或者给查询 server 只读凭证；
- L2 操作先跑 dry-run，把结果放回上下文，人工确认后再执行真实动作。

### 3. 确认信息要具体

不要只问“是否继续”。一个有效的确认应包含：

- 目标环境；
- 影响对象和范围；
- 是否可逆；
- 预计耗时；
- 回滚方式。

让人类在明确信息下拍板，而不是让模型转述模糊风险。

### 4. 自动执行也要加硬约束

对 L0/L1 动作，自动执行不是无限制。建议加上：

- 超时时间；
- 最大批量数；
- 目标环境标签校验；
- 参数格式白名单；
- 错误率或重试次数上限。

## 踩坑点

1. **用提示词当安全边界**  
   工具层没有 deny，模型就可能被诱导执行越权动作。提示词可以辅助，但不能替代权限策略。

2. **MCP 工具面太宽**  
   一个 server 同时有 query 和 delete，Agent 选错工具的概率不低。拆分工具或限制凭证比事后补救更有效。

3. **确认疲劳**  
   所有操作都问，人会麻木。L0/L1 自动，只拦 L2/L3，阈值要实际调，而不是一味求稳。

4. **只限制命令，不限制参数**  
   例如允许执行 `kubectl delete` 但不校验命名空间和资源标签，仍然可能误删生产对象。

5. **审计日志太乱**  
   自动执行产生大量日志，没人看，出事后翻不到关键决策。审计要结构化，至少包含动作、参数、结果、是否命中白名单、耗时。

## 可复用建议

- 默认 deny，用“工具名 + 参数 + 目标资源”三层 allowlist；
- 高风险动作使用短时 token，不让 Agent 持有长期 key；
- 自动执行动作都写结构化审计；
- 每两周复盘一次“被误拒”和“不该自动但自动了”的 case，调整分级阈值；
- 把“不确定就停下来问”作为系统级规则，同时在工具层拦截兜底。

## 总结

AI Agent 的权限边界不是让模型更自律，而是把风险分级、工具层限制、确认机制和审计做成默认流程。能自动的清爽地自动，该问的必须停下。对于 OpenClaw 实践者来说，真正可靠的 Agent 不是跑得最快的那一个，而是每次越界前都能被拦下来的那一个。
