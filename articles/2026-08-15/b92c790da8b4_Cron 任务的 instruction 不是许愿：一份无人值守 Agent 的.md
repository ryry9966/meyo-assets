## 背景

在 OpenClaw 里配 cron 定时任务时，经常能看到类似这样的 instruction：

> 每天早上 9 点总结一下昨天的日志，发到群里。

这种写法在交互式场景下可能没问题，但放到 cron 里，往往会出现三种结果：某天没发成功、某天连发三条、或者发了一堆中间推理过程到频道里。

问题通常不在模型能力，而在于：**cron 任务是一次无人值守执行，不是聊天。**

## 问题：Cron 任务和交互式任务的本质区别

交互式任务里，人类可以随时打断、纠正、补充上下文。但 cron 没有第二次确认机会。它到点直接执行，出问题时你可能几个小时后才发现。

模糊 instruction 会让模型在至少三个地方自行猜测：

1. 时区是什么？
2. 成功标准是什么？
3. 失败后要不要重试、要不要说话？

只要有两处猜错，任务行为就不稳定。所以 cron instruction 需要按“运维脚本的工作说明书”来写，而不是按聊天指令来写。

## 做法：给 Cron Instruction 固定六个字段

我会把每条 cron instruction 拆成以下六块。

### 1. 任务目标与完成判据

一句话说明要产出什么，以及怎样算完成。

示例：

> 统计昨天 00:00–23:59 的 ERROR 日志，汇总到 #daily-report。完成 = 消息已发送且包含错误数量。

不要写“看看有没有异常”，因为模型会自行定义“异常”。

### 2. 运行上下文

明确时区、时间范围、数据来源。

示例：

> 时区 Asia/Shanghai；统计范围是前 24 小时；只读 /data/logs，不修改任何配置。

时区一定要写进 instruction，不要只依赖系统配置。很多 agent 默认按 UTC 推算，跨日统计容易偏移。

### 3. 约束与禁止项

写明不要做什么，尤其是写操作和编造数据。

示例：

> 查不到就写 0，不得编造；不要重发 30 分钟内已成功的同一任务；不要为了补日志而创建文件。

### 4. 工具与权限

明确允许调用哪些工具，是否允许发消息、写文件、创建工单。

默认原则是：**能只读就不开放写权限。** 工具范围越窄，无人值守执行越稳。

### 5. 输出协议

要求最后只输出结构化摘要，不要输出完整思考过程。

示例：

```json
{
  "status": "ok|failed|skipped",
  "date": "YYYY-MM-DD",
  "error_count": 0,
  "top_3_errors": [],
  "sent": true
}
```

结构化输出有两个好处：方便后续程序解析，也避免频道里刷屏。

### 6. 异常与静默策略

失败时做什么、重试几次、什么时候保持安静。

示例：

> 如果数据源不可用，连续失败 2 次后发送一条简短告警到 #ops-alert，然后停止。不要无限重试。

## 一个可直接改写的示例

```text
Role: 每日日志巡检 cron
Trigger: 0 9 * * *
Timezone: Asia/Shanghai

Goal:
统计昨天 00:00–23:59（Asia/Shanghai）的 ERROR 日志，发送到 #daily-report。

Rules:
- 只读 /data/logs，不修改或删除任何文件。
- 如果日志为空，报告 0 条，不得编造。
- 同一时间窗口只执行一次；若发现 30 分钟内已有成功记录，直接退出并返回 skipped。

Tools:
grep_logs, send_channel

Output JSON:
{"status":"ok|failed|skipped","date":"YYYY-MM-DD","error_count":n,"top_3_errors":[],"sent":true}

Failure:
如果 grep_logs 连续失败 2 次，发送告警到 #ops-alert，然后停止。
```

## 踩坑点

- **没写成功判据**：模型每次对“完成”理解不同，可能漏发或重复发。
- **没做幂等约束**：网络重试、调度抖动可能造成同一任务执行两次。
- **时区只写在系统里**：agent 内部仍可能按 UTC 计算，导致统计日期错位。
- **输出完整思考过程**：定时频道变成日志频道，真正有用的信息被淹没。
- **失败处理过于口语化**：“有问题就处理一下”会让模型反复尝试，甚至陷入错误循环。
- **工具权限过大**：无人值守时，一次写操作幻觉的代价比交互式高得多。

## 可复用建议

1. 把 cron instruction 当作**只读优先的无人值守脚本**，写操作必须显式列出。
2. 每个任务都带一个 JSON 输出 schema，方便后续解析和监控。
3. 加一个“安静模式”字段：正常成功只输出单条摘要，失败才详细告警。
4. 加幂等键：基于时间窗口或任务名，执行前先检查是否已完成。
5. 先手动触发或 dry-run 一次，确认输出符合 schema，再正式上 cron。
6. instruction 版本化。修改后保留变更记录，避免“改了但没生效”的排查困难。

## 总结

Cron 任务 Prompt 的本质，是把人不在场时的判断依据提前写死。

好的 instruction 不靠更会表达，而是把五件事写清楚：**时区、幂等、工具权限、输出协议、失败策略**。做到这些，定时 agent 才会从“偶尔出问题”变成“可预测执行”。
