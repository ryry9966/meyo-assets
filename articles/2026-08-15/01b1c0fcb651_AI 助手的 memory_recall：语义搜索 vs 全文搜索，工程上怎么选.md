## 背景：memory_recall 为什么总会纠结检索方式

在 OpenClaw / Agent / MCP / 自动化实践里，memory_recall 是一个很常见的自定义工具：把历史偏好、工具结果、命令片段、对话摘要写进记忆库，下次任务时再按 query 拉回来。实际做的时候，很多人会卡在一个点上：到底用语义搜索还是全文搜索？

语义搜索听起来更“智能”：能理解同义改写、模糊表述。全文搜索看起来更“原始”：精确匹配、速度快、可解释。但在工程落地时，不是先进一定更好。尤其当记忆只有几百到几千条规模、query 又经常包含命令、路径、报错码、插件名时，语义搜索可能会给你一堆“看起来相关但不可用”的结果。

## 问题：没有一种检索方式能通吃

全文搜索强在：
- 对 ID、命令、报错、路径、插件名等精确 token 友好；
- 快、索引小、部署简单；
- 可解释，知道为什么召回。

弱在：
- 中文分词容易出错；
- 对同义改写、口语化 query 召回差。

语义搜索强在：
- 能理解“把上次下载视频的设置找回来”和“youtube-dl 参数”这种关联；
- 对自然语言 query 更友好。

弱在：
- 精确 token 容易被向量空间淹没；
- 引入 embedding 成本、维度管理、相似度阈值问题；
- 小数据量时效果不稳定，容易过度自信。

所以在 memory_recall 里，正确做法不是“选一个”，而是按 query 和记忆类型做分流或混合。

## 做法/步骤：用混合召回搭一个可用的 memory_recall

**1. 明确记忆类型**

先给写入的记忆打上类型：`preference`、`fact`、`command`、`tool_result`、`summary`。这步很关键，后面检索策略会按类型分流。别一上来就无脑 embedding。

**2. 建立全文索引**

用 SQLite FTS5 存原文和预处理后的文本。中文不要直接依赖默认 tokenizer，建议用 trigram tokenizer 或写入前用 jieba/简单规则分词。命令、路径、报错码这类内容可以保留原始 token，不要过度清洗。

**3. 可选建向量索引**

只有记忆规模较大、或 query 确实以自然语言为主时，再接入 embedding。固定模型和维度，向量做归一化，避免后期更换模型导致索引失效。本地开发可以用 sqlite-vec 或单独向量库，不要盲目上重型向量数据库。

**4. 查询分流**

在 memory_recall 工具里做轻量 query 判断：
- query 含明显 token（命令、路径、插件名、短 ID、报错码）→ 走全文搜索；
- query 是完整句子且无精确 token → 走语义搜索；
- 混合模式：全文粗筛 top 50，再用向量重排。

不要一上来就 RRF 融合，先跑通单路，再考虑融合。

**5. 返回结果带上来源和分数**

每条召回结果至少返回：`text`、`memory_id`、`source`、`score`、`ts`。阈值没调好之前，分数先显示出来，别拍脑袋截断。

**6. 本地评测**

准备 30~50 条真实 query，标注相关记忆。对比 recall@5、MRR、平均延迟。这个评测集不用很复杂，但它能帮你判断阈值和分流规则是否合理。

## 踩坑点

- **FTS5 中文分词不当**：默认 tokenizer 对中文很弱，容易出现“更新插件”召回不到“插件更新”。trigram 或预分词能改善，但会增大索引，需要实测延迟。
- **语义搜索小数据量容易飘**：几百条记忆时，向量相似度可能都在 0.7 以上，阈值设 0.8 会漏光，设 0.5 会召回一堆噪声。要根据实际分数分布调，不要抄通用阈值。
- **精确 token 被语义淹没**：用户 query 里带一个具体报错码，语义搜索可能返回“看起来相关”的错误排查记忆，但漏掉完全匹配的那条。含短 token、特殊字符的 query，应强制走全文。
- **混合融合不要简单加权**：语义分和全文分分布差距很大，直接加权容易被一边带偏。先做粗筛再重排，或用 RRF 更稳。
- **向量索引与更新不同步**：记忆已经更新或删除，但向量库没同步。排查时先看写入链路是否触发了 embedding 和 upsert。

## 可复用建议

如果你的 memory_recall 还停留在几百条规模，不要急着上语义搜索。先用 SQLite FTS5 + 规则分流解决 80% 的需求。等确认 query 确实大量是同义改写、自然语言表达，再引入语义检索作为补充。

写 memory_recall 的 MCP 工具时，保留一个 `mode` 参数：`fts` / `semantic` / `hybrid`，方便后续切换和 A/B。记录未命中 query，定期翻一下，能发现很多分词和阈值问题。

## 总结

语义搜索和全文搜索不是谁替代谁。在 AI 助手的 memory_recall 场景里，全文搜索负责精确、快速、可解释的兜底；语义搜索负责理解泛化、处理自然语言。工程上的合理路径是：小规模全文优先，按 query 分流，语义作为扩展，混合策略逐步引入。先把召回和阈值打磨好，再谈“智能记忆”。
