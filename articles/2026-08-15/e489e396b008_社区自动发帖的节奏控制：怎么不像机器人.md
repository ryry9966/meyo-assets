## 背景

在 OpenClaw 生态里，越来越多同学用 Agent、MCP 或插件做内容同步、社区维护和自动发帖。一个常见落地路径是：LLM 生成文案，直接调用发布 API，然后定时触发。

上线头几天往往正常，但很快会遇到问题：账号被限流、帖子进入审核、社区用户觉得账号像机器人，甚至被版主标记。多数人第一反应是优化内容质量，但真实原因常常不是文案不好，而是**节奏不像人**。

## 问题

固定每 30 分钟发一条，连续 8 小时，这种模式即使内容再自然，也很容易被平台风控识别。

平台风控通常不看单条内容，而看行为序列：

- 发帖间隔是否过于稳定
- 每日发帖数量是否异常
- 活跃时段是否符合正常作息
- 是否只有发布行为，没有正常互动
- 编辑、删除、重发频率是否过高

所以，节奏控制要解决的不是“发慢一点”，而是让行为序列落在一个合理、可解释、可调控的区间里。

## 做法 / 步骤

### 1. 把节奏从脚本里独立出来

不要在发布脚本里写死 `sleep(randint(1800, 3600))`。先定义一份策略配置：

```json
{
  "min_interval_sec": 1800,
  "max_interval_sec": 7200,
  "daily_limit": 3,
  "active_hours": [9, 11, 14, 17, 20],
  "jitter_ratio": 0.2,
  "weekly_off_days": [0],
  "cooldown_after_reply": 900,
  "backoff_on_captcha": 86400
}
```

这套配置应该能独立修改、版本管理，而不是散落在代码里。

### 2. 发帖前先问策略

在 OpenClaw 里可以封装成一个 MCP tool 或独立 policy service。发布工具在真正调用 API 前，先请求 `can_post()`：

- 返回 `ShouldPost`
- 返回 `WaitSeconds`
- 返回 `Reason`

只有 `ShouldPost=true` 时才允许发布。不要让发帖工具自己决定节奏。

### 3. 持久化状态

至少记录：

- `last_post_at`
- `today_count`
- `daily_off_count`
- `consecutive_active_days`

多账号、多实例部署时，必须用 Redis 或数据库做原子计数。否则多个任务同时检查，很可能出现“同一分钟发两条”的情况。

### 4. 加入人类波动

真实用户不会每天发满固定条数。比较实用的做法是：

- 每天先决定发帖数量：例如 1 条 20%，2 条 50%，3 条 30%
- 发帖间隔在 `min_interval_sec` 到 `max_interval_sec` 之间随机，再叠加轻微抖动
- 每周允许 1 个休息日，不完全停，但降低频次

注意：随机要有边界，过度随机本身也可能是特征。

### 5. 互动与发帖联动

发帖后如果收到回复，冷却时间应单独计算。同一话题、同一子版块连续发帖，需要比跨板块更大的间隔。原创内容和转载内容也可以使用不同节奏。

### 6. 可观测与自动回滚

每次决策都记录原因：

```
today_count=3, daily_limit=3, wait=5h, reason=daily_limit_reached
```

遇到验证码、限流、帖子被删除时，自动进入冷却或暂停状态。不要继续“坚强”地发。

## 踩坑点

- **只加随机 sleep 不够**：均匀随机仍然可能产生连续发帖或集中在某一天。
- **Jitter 范围过大**：容易错过活跃时段；太小则时间间隔仍然过于规律。
- **多进程没做原子计数**：分钟级撞车非常常见。
- **时区错误**：`active_hours` 要明确是 UTC 还是本地时区，否则会在半夜发帖。
- **编辑、删除也计入频率**：不要只统计发布，编辑、删除、置顶同样消耗平台配额。
- **验证码后只睡 10 分钟**：此时账号可能已被标记，应该进入长冷却或直接暂停。
- **不要追求 100% 拟人**：过度随机、太像人的“剧本”本身也是异常特征。

## 可复用建议

- 把节奏策略做成独立模块或 MCP tool，发布插件只调用，不内嵌规则。
- 先开 shadow mode 跑 3–7 天，不真正发布，只记录决策日志，和人工发帖行为做对比。
- 给每个帖子加 `trace_id`，把内容生成、策略决策、发帖结果串起来。
- 新账号先每天 1 条，连续跑一周再逐步放量。
- 策略参数放配置文件，修改不必改代码，变更也要走 review。

## 总结

社区自动发帖不像机器人，关键不在某一条文案多像人，而在于行为序列是否可控、可解释、可回滚。

把节奏从脚本 `sleep` 提升为独立策略层，配合持久化状态和可观测日志，既能降低风控风险，也能让自动化更稳定。最稳的自动化往往不是“发得多而逼真”，而是**少发、可停、能追溯**。
