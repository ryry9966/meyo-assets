# OpenClaw 的 cron vs heartbeat：定时任务别只看“能不能跑”

在 OpenClaw 里给 Agent、插件或自动化流程配定时任务时，通常会遇到两种调度方式：`cron` 和 `heartbeat`。它们看起来都能“定时执行”，但工程上代表的是两种完全不同的调度模型。选错不会立刻报错，但会在某个凌晨多跑一次，或在业务高峰把队列扫重复。

## 背景：两种调度，不是两个参数

`cron` 是日历触发，表达的是“每周一 9:00”“每月 1 号 00:30”这类与自然时间对齐的语义。

`heartbeat` 是固定间隔触发，表达的是“每 30 秒检查一次”“每 5 分钟拉一次队列”这类相对节奏。

很多实践里会把它们混用：用 `heartbeat` 做日报，上线后发现第一次执行不是早上 9 点，而是部署后 1 小时；或者用 `cron` 做高频队列扫描，最后因为任务执行时间超过间隔，出现并发与重复通知。

## 问题：什么时候必须选 cron，什么时候选 heartbeat

一个比较实用的判断方式是看触发基准：

- 业务关心“具体时刻”：选 `cron`。
- 业务关心“固定频率”：选 `heartbeat`。

例如：每天早上 9 点生成前一日报表，这是日历语义，适合 `cron`。每 30 秒检查 MCP 工具是否有新结果，这是节奏语义，适合 `heartbeat`。

如果用错，`cron` 在高频场景下表达力差、配置不直观，还容易受时区影响；`heartbeat` 在日历场景下会随部署时间、重启漂移，永远对不齐业务日界。

## 做法：在 OpenClaw 中配置两种任务

### 1. cron：显式指定时区

以 OpenClaw 任务声明为例：

```yaml
schedule:
  type: cron
  expr: "0 0 9 * * *"
  timezone: "Asia/Shanghai"
```

这里的 `expr` 要确认 OpenClaw 是否支持 6 段秒级表达式。很多平台默认是 5 段，少一位就会从分钟开始匹配。

时区不要依赖运行环境默认值。容器里常见 `TZ=UTC`，本地验证正常，上线后晚 8 小时。建议统一使用 `UTC` 触发，任务内部再做本地日界转换；如果业务必须本地时区，就显式写在调度配置里。

### 2. heartbeat：控制单次耗时与重叠策略

```yaml
schedule:
  type: heartbeat
  interval: 30s
  timeout: 25s
  on_overlap: skip
```

`interval` 是触发间隔，`timeout` 是单次执行超时，`on_overlap` 决定上一次未完成时下一次是否允许启动。对 Agent 任务来说，`on_overlap: skip` 通常比默认并发更安全，否则外部 API 调用会被重复触发。

### 3. 任务内部加幂等

不管选哪种，任务本身都应有幂等键。例如按业务日期、数据时间窗口或任务批次号生成锁 key，避免重复执行。

```python
lock_key = f"sync:{business_date}:{window_start}"
```

心跳任务尤其容易在边界重复扫描同一批数据，幂等键比“感觉不会有重复”可靠得多。

## 踩坑点

- **cron 时区错位**：容器默认 UTC 导致日报晚 8 小时。上线前检查 `timezone` 是否生效。
- **heartbeat 默认允许重叠**：任务执行 40 秒，间隔 30 秒，第二批会并发启动。必须配置 `on_overlap` 或任务开头抢锁。
- **cron 表达式段数不一致**：同一段配置在本地 5 段能跑，换到 OpenClaw 的 6 段实现可能直接报错或永远不触发。
- **heartbeat 随重启漂移**：不要用 `heartbeat: 24h` 期望它每天 0 点执行。重启会重置起始点，日历对齐必须用 `cron`。
- **间隔太短导致延迟堆积**：`interval` 小于实际耗时时，即使不重叠，调度器也可能持续滞后。建议 `interval >= 3 * avg_duration`，或把耗时操作丢到异步队列。
- **只查“任务有没有跑”，不查“跑得对不对”**：记录 `scheduled_at`、`started_at`、`finished_at` 和 `delay_ms`，对 cron 的 miss、heartbeat 的 drift 做监控。

## 可复用建议

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 每日 9 点生成报表 | cron | 需要日历对齐 |
| 每 30 秒扫描队列 | heartbeat | 需要固定频率 |
| 每小时健康检查 | heartbeat | 相对间隔足够 |
| 每周一发送总结 | cron | 需要自然周语义 |
| 高频数据同步且耗时不可控 | heartbeat + skip | 防止重叠和堆积 |

实际项目中可以混用：日历驱动用 `cron`，内部健康检查、队列轮询、MCP 结果拉取用 `heartbeat`。不要试图用一套机制覆盖所有定时需求。

## 总结

`cron` 和 `heartbeat` 在 OpenClaw 里不是可替换的两个参数，而是两种调度模型。选型时先问：任务是“在某时刻发生”，还是“每隔一段时间发生”。确定后，再补齐时区、重叠策略、幂等和监控。

工程上更稳妥的做法是：cron 只负责到点触发，heartbeat 只负责节奏巡检，任务逻辑保持幂等，调度与业务解耦。这样即使将来从 heartbeat 切换成 cron，也不会因为执行逻辑耦合而重写。
