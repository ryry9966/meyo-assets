## 背景

在 OpenClaw、MCP、插件和自动化实践里，Agent 的能力越来越像“工具集合”：文件读写、Shell 执行、浏览器操作、数据库变更、消息发送。权限配置如果只停留在“允许/禁止”这个粒度，很快会出问题。

我们经常看到的两种极端：

- 全部放权：Agent 确实自动化了，但一次误判就能删文件、发错消息、执行危险命令。
- 全部询问：每步都弹确认，用户审批疲劳后开始机械点“允许”，最终等于没有边界。

真正要解决的不是“模型够不够聪明”，而是工程上有没有一套可复用的权限分级与拦截机制。

## 问题

在 OpenClaw/Agent 实践中，权限失控通常来自以下四点：

1. 工具只按名称放行，不按动作和对象评估风险。
2. 依赖模型在提示词里“自觉询问”，缺少工具层强制。
3. MCP server 暴露的工具元数据不一致，外层没有统一策略。
4. 审批交互设计太粗糙，用户要么被打断到烦，要么一键放行危险操作。

这些问题的本质是：权限边界没有落到工具调用管道里，而只是停留在 prompt 意愿上。

## 做法/步骤

### 1. 先做风险分级，不急着写代码

把 Agent 会接触到的工具按风险分成四级：

| 级别 | 类型 | 默认策略 |
|------|------|----------|
| L0 | 只读、幂等操作，如 `read_file`、`list_dir` | 自动执行 |
| L1 | 可逆写入、低风险变更，如 `append_note`、`create_draft` | 需要确认或会话内允许 |
| L2 | 不可逆操作、敏感数据读取，如 `delete_file`、`shell_exec` | 默认确认，必要时拒绝 |
| L3 | 外发、支付、凭据访问、批量删除 | 默认 veto，只允许白名单 |

这个分级不追求完美，但必须让每个工具在注册时就带上风险等级。

### 2. 在工具注册层加权限元数据

不要只写 `tools: [file_read, file_delete]`。建议在配置里显式声明：

```yaml
tools:
  file_read:
    risk: read
    approval: auto
  file_delete:
    risk: destructive
    approval: confirm
  shell_exec:
    risk: exec
    approval: confirm
    allowlist:
      - "git status"
      - "ls -la"
```

这样后续所有判断都基于元数据，而不是靠模型临场发挥。

### 3. 用 middleware 或 hooks 强制拦截

OpenClaw 的工具调用管道里，可以在 `before_tool_call` 阶段做策略检查：

- `approval: auto`：直接放行。
- `approval: confirm`：暂停执行，向用户展示完整参数和影响范围，等待批准。
- `approval: veto`：直接拒绝，并记录审计日志。

关键是：模型可以生成调用计划，但真正执行前必须经过这一层。不要相信模型会自己“先问一下”。

### 4. 加入 dry-run 预览

对于写操作和 Shell 命令，先执行只读检查或生成命令预览，再把计划推给用户。例如删除文件前先列出匹配到的文件路径；执行 Shell 前先展示完整命令，而不是只显示 `shell_exec` 这个函数名。

### 5. 按会话上下文动态调整

交互式会话里，用户在场，可以多确认；后台 cron、批处理任务里，用户不在场，权限应默认更严格，只允许 L0 和其他已明确批准的模式。

### 6. 记录已批准模式，减少重复打断

如果用户批准了某个低风险模式，例如“允许向 `notes/` 目录追加内容”，后续同类操作可以自动执行。但批准模式必须限定路径、动作和时间范围，不能变成永久放行。

## 踩坑点

- **把“是否询问”写进 system prompt 就完事**：模型在长任务里会跳过甚至忘记，必须在工具层强制。
- **信任 MCP server 自报的风险等级**：不同 server 描述不一致，最好在外层统一包一层 policy，不要让 server 决定你的安全边界。
- **审批按钮只有“允许/拒绝”**：用户会习惯性点允许。建议提供“允许一次 / 本会话允许 / 拒绝并解释”，降低机械放行概率。
- **确认时只显示工具名**：用户不知道 `delete_file(path)` 具体删的是什么。必须展示完整参数、目标路径和影响范围。
- **用全量权限账号跑 Agent**：即使有确认机制，一旦误确认也可能造成不可逆后果。对敏感环境使用最小权限账号、只读凭据或沙箱。

## 可复用建议

1. 建立统一的 `agent_policy.yaml`，所有 Agent 实例继承同一套风险分级和审批策略。
2. 工具接入时做 capability 声明：能读什么、能写什么、能否执行命令、是否访问网络。
3. 把“计划-批准-执行”设为默认工作流，特别是对于 L1 及以上操作。
4. 审计日志不要只记“调用了什么”，还要记“谁批准的、批准范围是什么”。
5. 定期回看审批记录，把真正高频且低风险的模式下沉为自动执行，把误批过的模式上提为默认拒绝。

## 总结

AI Agent 的权限边界不是“要不要给权限”的问题，而是“权限在哪个层级被检查”的问题。合理做法是：

- 低风险幂等操作自己干；
- 可逆但影响可见的操作先预览再执行；
- 不可逆操作默认确认，甚至默认拒绝；
- 所有边界都通过工具层策略强制，而不是依赖模型自觉。

在 OpenClaw/Agent/MCP 这类工具密集的生态里，权限策略越早做，后面自动化越敢放开；越晚做，越容易在一次误操作后把整个 Agent 关进笼子。
