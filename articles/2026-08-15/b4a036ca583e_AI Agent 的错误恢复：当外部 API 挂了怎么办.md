## 背景

在 OpenClaw / Agent / MCP / 插件类自动化实践里，外部 API 是最常见的单点故障。一个任务链可能同时依赖搜索接口、天气接口、对象存储、通知服务，任何一个挂掉都会让 Agent 中断、乱猜，甚至重复执行有副作用的操作。

实际工程中，外部 API 的故障不是“会不会发生”，而是“什么时候发生”。DNS 抖动、限流、网关超时、上游 5xx、供应商维护、网络分区，这些都会以不同形式出现在 Agent 的工具调用链路里。

## 问题

很多 Agent 的错误处理停留在“把异常文本丢给模型”。这样会导致三个典型问题：

1. **模型自由发挥**：看到超时或 JSON 解析错误后，模型可能自己编造结果，或者反复用不同参数调用同一个工具。
2. **无差别重试**：4xx、5xx、超时混在一起重试，既无效又可能触发风控。
3. **没有降级与熔断**：下游已经过载，Agent 还在不断发起请求，最终把故障放大。

更重要的是，MCP 工具或插件如果直接把堆栈抛给模型，模型很难做出稳定决策。错误恢复应该放在工具层、插件层，而不是 prompt 层。

## 做法/步骤

### 1. 先做错误分类

把外部调用错误分成三类：

- **不可重试**：400、401、403、404，以及业务参数错误。重试没有意义。
- **可重试**：429、5xx、连接超时、DNS 失败、连接被拒绝。
- **协议/内容错误**：响应不是合法 JSON、字段缺失、schema 不符。

不可重试错误应立即返回结构化失败，不要让 Agent 继续尝试。

### 2. 设置明确超时

外部调用不要只依赖默认超时。建议拆成三层：

- 连接超时：2–5 秒
- 首字节超时：5–10 秒
- 整体超时：10–20 秒

Agent 场景下，超时不宜过长。一个任务如果卡在某个工具上 30 秒，用户体感会很差。宁可快速失败，再走降级或人工接手。

### 3. 有限重试 + 指数退避 + 抖动

对可重试错误，最多重试 2–3 次。使用指数退避，并加上随机抖动，避免多个并发任务同时重试形成共振。

例如：

- 第 1 次重试：500ms–1s
- 第 2 次重试：2s–4s
- 第 3 次重试：8s–12s

不要用固定间隔，也不要在 MCP 工具里做无限循环重试。

### 4. 读接口走缓存兜底，写接口明确失败

只读接口可以提前缓存成功响应。当外部 API 失败时，返回缓存数据，并在返回结构里标记：

```json
{
  "data": { "weather": "..." },
  "fallback": true,
  "stale_at": "2025-04-10T10:00:00Z",
  "source": "cache"
}
```

这样 Agent 知道这是旧数据，可以继续执行，但要降低置信度。

写接口不要自动降级为“假装成功”。扣款、发消息、创建工单这类操作一旦失败，必须返回明确错误和 `cause`，否则会产生严重副作用。

### 5. 加熔断与隔离

每个外部依赖单独设置熔断器。例如，滚动窗口内连续失败 5 次，或错误率超过 50%，就打开熔断，后续请求直接快速失败。熔断打开后，隔 30–60 秒进入 half-open 状态，用少量探测请求验证下游是否恢复。

熔断的目的是保护下游，也保护 Agent 任务不被长时间挂起。

### 6. 保存任务状态，保证幂等

在调用外部 API 前，先保存任务 checkpoint。写操作必须携带幂等键，例如 `idempotency_key = task_id + step_id`。这样即使重试，也不会重复创建订单、重复发送通知。

任务失败后，能从 checkpoint 恢复，而不是从头执行整个流程。

### 7. 给 Agent 返回结构化错误

工具失败时，不要只返回一句话。建议返回结构化字段：

```json
{
  "ok": false,
  "error_type": "upstream_timeout",
  "retryable": true,
  "retry_count": 2,
  "fallback_used": false,
  "next_action": "pause_or_retry_later",
  "message": "search_api timed out after 10s"
}
```

模型看到这种结构，更容易做出正确决策：等待、降级、还是请求人工介入。

## 踩坑点

- **把 4xx 当 5xx 重试**：账号可能被锁定。例如 401 或 403，重试 3 次只会让风控更早触发。
- **降级返回空列表**：如果 Agent 把空列表当成真实结果，可能会得出“没有数据”的错误结论。降级数据必须带 `fallback` 标记。
- **熔断阈值太敏感**：一次抖动就切全熔断，会让服务长期不可用。应基于窗口和错误率，而不是单次异常。
- **重试放大流量**：并发任务同时重试，会把下游打得更死。必须限制重试并发，并加抖动。
- **MCP 工具异常被包装**：很多框架会把工具异常包成通用错误，丢掉 `status_code`、`retry_after` 等关键字段。需要在工具内部解析并保留结构化信息。
- **依赖模型判断“再试一次”**：模型容易过度重试，也容易在失败后直接放弃。重试策略应该由代码决定，不要让模型控制重试次数。

## 可复用建议

- 错误处理放在工具/插件层，形成统一封装，不要散落在各个 prompt 里。
- 给 Agent 的失败信息至少包含：`what failed`、`error_type`、`retryable`、`retry_count`、`fallback_used`、`next_action`。
- 默认配置可作为起点：整体超时 15 秒，重试 2 次，退避 1s/3s/8s，熔断阈值 5 次/60 秒，缓存 TTL 5–30 分钟。
- 定期做故障注入测试：主动返回 429、500、超时、非法 JSON，观察 Agent 是否按预期降级、停止或转人工。
- 监控四类指标：上游错误率、重试率、降级命中率、熔断打开次数。只看任务成功率会掩盖很多问题。

## 总结

外部 API 挂掉不是异常，而是常态。错误恢复的目标不是“保证每次都成功”，而是让失败可预测、可降级、可恢复。

在 Agent 工程里，稳定可靠的错误处理往往比优化 prompt 更有效。把重试、退避、熔断、缓存、幂等和结构化错误反馈做扎实，Agent 才能在外部依赖不稳定时保持可控，而不是把故障放大成一次混乱的自主行为。
