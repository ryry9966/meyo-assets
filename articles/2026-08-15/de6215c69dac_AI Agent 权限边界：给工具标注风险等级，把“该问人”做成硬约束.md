## 背景

不少 OpenClaw 实践者都经历过两个极端：Agent 太保守，每执行一步都问“可以吗”，自动化形同虚设；Agent 太激进，一个误判就把生产数据删了。权限边界不清晰，往往源于我们只把“什么时候该问人类”写进 system prompt，而没有把它变成工程约束。

模型不会稳定地自觉遵守“不要做危险操作”。尤其当任务链变长、工具变多、MCP server 引入外部能力后，靠自然语言约束的可控性会迅速下降。我们需要一套轻量但明确的分级授权机制，让 Agent 在不同风险等级下自动判断：自己干，还是中断等待人类审批。

## 问题

权限边界模糊通常表现为：

- 低风险操作反复询问，打断自动化流程；
- 高风险操作不询问，直接执行；
- 权限描述散落在 prompt 里，模型理解不一致；
- MCP 工具按 server 授权，粒度太粗；
- 只有同步审批，没有 suspend/resume，异步任务被卡死。

这些问题无法靠“再强调一下 prompt”解决。需要把权限判断下沉到工具调用层，用结构化元数据描述风险，用审批回调拦截高风险操作。

## 做法：给工具打风险分，而不是只靠 prompt

### 1. 定义风险等级

建议按“可逆性 + 影响面 + 外部副作用”划分四个等级：

- **L0 只读**：查询、列表、读取配置。默认自动执行。
- **L1 可逆写**：创建临时文件、写入测试库、可回滚的本地变更。自动执行，但需记录日志。
- **L2 不可逆/外部副作用**：删除生产数据、发送邮件/消息、调用外部 API、发布内容。默认需审批。
- **L3 敏感/资金/权限变更**：转账、修改 IAM、删除备份、批量操作。默认禁止自动执行，至少需要人工确认，必要时双人审批。

这个分级不需要完美，但需要团队内统一。核心是：**风险等级是工具的属性，不是模型临场判断的结果。**

### 2. 用结构化描述声明风险

不要只在工具 description 里写“请谨慎使用”。建议用 YAML/JSON 元数据或统一的前缀格式：

```yaml
tools:
  - name: delete_file
    description: "Permanently delete a file from the workspace"
    risk_level: L2
    approval_required: true
    impact_scope: ["filesystem"]
```

如果使用 MCP，可以在工具描述的固定位置加入 `risk_level: L2`，由 Agent 框架解析。关键点：**风险等级要让框架能读到，而不是让模型“理解”。**

### 3. 实现 human-in-the-loop 审批回调

在 Agent 框架的工具调用链中插入一个拦截器：

1. Agent 发起 tool call；
2. 框架读取该工具的 `risk_level`；
3. 若低于当前环境阈值，直接执行并记录；
4. 若达到或超过阈值，暂停当前任务，发送审批请求到 IM / CLI / Webhook；
5. 人类回复 allow / deny / 修改参数；
6. 根据决策继续执行或跳过，并将整个决策写入审计日志。

审批回调需要支持超时和重试。如果任务运行在异步队列里，建议设计 suspend/resume 而不是简单阻塞：保存任务状态，等待人工决策后再恢复执行。

### 4. 设置环境阈值

同一工具在不同环境下风险不同。例如 `drop_table` 在测试库可以设为 L1 自动执行，在生产库必须设为 L3 审批。建议在 Agent 配置中维护 `environment: dev/staging/prod`，并分别设置允许自动执行的最高风险等级。

Dev 环境可以放宽到 L2，生产环境只允许 L0/L1 自动执行，L2 及以上必须审批。

### 5. 记录与回放

所有自动执行和审批决策都要落到日志，包含：工具名、参数摘要、风险等级、最终决策（auto/approved/denied）、时间戳、会话 ID。这样既能回溯问题，也能帮助发现模型是否在权限判断上出现偏差。

## 踩坑点

- **只靠 prompt 约束**：模型可能误判风险，或者在长上下文中忘记约束。必须在工具层拦截。
- **风险等级太粗**：所有写操作都设为 L2，会导致审批疲劳，人类开始机械点“允许”，审批失去意义。
- **风险等级太细**：每个参数都单独分级，维护成本高，模型也难以正确匹配。
- **MCP server 整体授权**：一个 MCP server 暴露多个工具时，不要按 server 授权，必须按工具粒度声明 risk_level。
- **同步审批阻塞异步任务**：长时间运行的 Agent 任务在中间步骤需要审批时，如果直接同步阻塞，会占用 worker 资源。需要 suspend/resume 或任务状态机。
- **自动执行的部分副作用**：L1 操作如果失败，可能留下半成品状态。建议为可逆写操作增加简单的回滚或清理逻辑，或者至少记录足够信息便于人工恢复。

## 可复用建议

1. **用结构化元数据声明风险**，不要写在 prompt 里。框架可解析、可拦截、可审计。
2. **按环境配置自动执行阈值**，开发环境宽松，生产环境收紧。
3. **审批流做成异步 suspend/resume**，避免长时间占用执行资源。
4. **高风险操作增加“干跑”模式**：先打印将要执行的动作和影响范围，人工确认后再真正执行。
5. **定期 review 自动执行日志**，特别关注模型多次试图调用高风险工具的情况，及时调整工具描述或风险等级。
6. **保留“只读模式”开关**：复杂任务可以先在只读模式下跑一遍，观察工具调用链是否符合预期，再放开写权限。

## 总结

AI Agent 的权限边界不应该是一个道德劝告，而是一套工程机制。把风险等级定义在工具层，用框架拦截和审批回调来保证高风险操作必须经过人类，才能真正做到“该问的时候必须问，该自己干的时候不啰嗦”。这比不断优化 prompt 更可靠，也更可持续。

在 OpenClaw 这类实践中，越早把权限分级做进工具描述和调用链，后面接入更多 MCP 工具和自动化场景时，越不容易失控。
