## 背景

在 OpenClaw 里接 Agent、MCP 工具或写自动化插件时，定时触发几乎是最常见的需求。社区里经常看到两种配置方式同时出现：一种是 `cron` 表达式，另一种是 `heartbeat` 间隔触发。很多人一开始只是能跑起来，但任务多了以后会发现，有些任务偶尔不执行、有些任务重复堆积、有些又白白消耗资源。问题通常不在 OpenClaw 本身，而在于这两种机制的适用场景被混用了。

这篇不讨论“哪个更好”，只从工程实践角度整理两者的边界和选型方法。

## 问题

`cron` 和 `heartbeat` 虽然都叫定时任务，但语义不同：

- `cron` 表达的是**绝对时间点**：每天 9:00、每周一 10:30、每月 1 号 0 点。
- `heartbeat` 表达的是**相对时间间隔**：每 30 秒、每 5 分钟、每 1 小时执行一次。

如果拿 `heartbeat` 去实现“每天 9 点发日报”，你会发现它在 9:00 附近触发，但可能因为进程启动时间偏移变成 9:03、9:07。如果拿 `cron` 去做“每 30 秒巡检队列”，表达式会非常别扭，而且 cron 本身不擅长高频短间隔场景。

## 做法

### 1. 先判断任务语义

拿到一个定时需求时，先问一句：**这个任务是“到点做一次”，还是“每隔一段时间检查一次”？**

- 到点做一次：日报、周报、数据快照、定时推送、定时拉取外部数据。
- 每隔一段时间检查：队列消费、状态探活、缓存刷新、失败重试扫描。

前者用 `cron`，后者用 `heartbeat`。

### 2. OpenClaw 中的典型配置

假设有一个 OpenClaw 插件需要两个任务：每天 10:00 汇总网页监控结果，以及每 5 分钟检查一次抓取队列。配置可以这样区分：

```yaml
tasks:
  - name: daily-digest
    type: cron
    schedule: "0 10 * * *"
    action: run_digest
    timezone: Asia/Shanghai

  - name: queue-scan
    type: heartbeat
    interval: 5m
    action: check_queue
    max_parallel: 1
    timeout: 4m
```

这里 `daily-digest` 是典型的时间点任务，`queue-scan` 是间隔巡检。`max_parallel: 1` 用来防止上一次还没跑完，下一次又启动导致堆积。

### 3. 给 heartbeat 加执行条件

heartbeat 触发频率固定，但没必要每次都做完整逻辑。比如每 1 分钟醒来一次，先查一下队列长度，大于 0 才继续处理。这样可以避免空转而占用 MCP 调用额度或数据库连接。

## 踩坑点

1. **cron 不会自动补跑**  
   如果 OpenClaw 实例在触发时间点宕机或重启，那个时间点的任务不会被补执行。需要补跑策略，比如启动时检查上次成功时间，决定是否手动触发一次。不要默认 cron 会像系统 crond 那样有补跑机制。

2. **heartbeat 间隔太短导致任务重叠**  
   如果任务执行时间是 3 分钟，heartbeat 间隔设成 1 分钟，且没有 `max_parallel` 或分布式锁，后续触发会大量堆积，最终拖垮 Agent 或 MCP 服务。务必设置并发上限，或使用 lease/lock 机制。

3. **时区不一致**  
   容器默认 UTC，而业务通常用本地时间。cron 表达式里写的 9 点，可能实际在凌晨触发。配置中显式声明 `timezone`，并在日志里记录触发时间，方便排障。

4. **把 heartbeat 当 crontab 用**  
   有些同学会写 `interval: 24h`，再在任务内部判断当前时间是否接近 9 点。这样既不可靠也不直观。OpenClaw 已经有 cron 支持，没必要绕。

5. **监控只看触发次数**  
   cron 触发成功不代表任务执行成功。应该记录每次执行的“最后成功时间”，如果超过一个 cron 周期还没更新，就告警。这一点对 Agent 类任务尤其重要，因为 Agent 可能卡在工具调用或长时间推理中。

## 可复用建议

- **业务时间约束用 cron，状态轮询用 heartbeat。** 不要混用。
- **所有定时任务都做成幂等。** 无论触发一次还是多次，结果都不应产生副作用。
- **长任务必须加超时和并发控制。** `timeout`、`max_parallel`、分布式锁至少有一个。
- **heartbeat 任务保持轻量。** 醒来先做条件判断，再决定是否执行重逻辑。
- **记录 last_success_time。** 这是比触发次数更有意义的健康指标。
- **在 OpenClaw 插件中，把 cron 表达式和 heartbeat 间隔做成配置项**，方便部署环境调整，不要写死在代码里。

## 总结

`cron` 和 `heartbeat` 并不是竞争关系，它们解决的是不同类型的定时问题。OpenClaw 或 Agent 自动化任务越复杂，越需要把“到点执行”和“间隔巡检”分开。用错机制，短期只是偶发不准确，长期会让任务系统变得难以维护和排障。

一句话选型：**如果你能说清“每天/每周几点做”，用 cron；如果你只能说“每隔多久看一次”，用 heartbeat。**
