## 背景

接入 MCP、插件和自动化脚本之后，Agent 的能力变强了，但行为漂移也更常见：有时过度解释，有时擅自调用危险工具，有时同一类问题两种回答风格。团队里每个人都在 system prompt 里加规则，最后规则互相打架，排查时没人知道哪一条真正生效。

问题不是模型不够聪明，而是人格和边界没有被当作配置来管理。我们后来在 OpenClaw 里开始用 SOUL.md 作为 Agent 的声明式人格文件，把“是谁、怎么说话、不能做什么、失败时怎么办”固定下来。

## 做法

SOUL.md 不负责具体业务流程，只回答几个关键问题：这个 Agent 是谁、用什么语气、绝对不能做什么、工具失败时怎么表现。

在 OpenClaw 中，可以把 SOUL.md 放在项目根目录或 `~/.openclaw/` 下，启动时作为前置上下文注入。一个最小可用的骨架如下：

```markdown
# SOUL.md

## Identity
你是 OpenClaw 项目的运维助手，只处理部署、日志和告警。

## Tone
- 默认简洁，先给结论再给依据。
- 不道歉，不进行过度寒暄。
- 遇到不确定时明确说“我不确定”，不要编造。

## Hard limits
- 禁止执行 rm -rf、DROP、TRUNCATE 等不可逆操作。
- 禁止读取 .env、私钥或凭证文件。
- 禁止把用户输入直接拼进 shell 命令。

## Tool policy
- 只使用已授权的 MCP server。
- 写操作前必须复述影响范围，等待确认。
- 同一失败重试不超过 2 次。

## Failure mode
- 工具报错时，先给错误码，再给排查路径。
- 如果连续失败，停止并建议人工介入。

## Example
User: 帮我把缓存清一下
Agent: 会执行 redis-cli FLUSHDB，影响当前 db 0，确认吗？
```

这个模板不到 500 词。重点不是写出完美人设，而是让硬边界可读、可查、可回滚。

实际操作步骤：

1. 收集最近两周 Agent 的越界或风格漂移 case，把重复出现的规则提炼出来。
2. 写最小 SOUL.md，只保留身份、语气、硬边界、失败模式。
3. 在 OpenClaw 中加载验证，跑固定任务集，观察行为是否稳定。
4. 后续每次新增规则都要求附上触发场景，否则不接受变更。

## 踩坑点

- **SOUL.md 过长**：超过约 800–1000 词后，模型对硬边界的遵守率明显下降。后来我们把工具策略拆到工具配置层，SOUL 只保留意图和语气。
- **硬边界只写在 SOUL.md 没有用**：MCP server 层如果没有 allowlist，模型一句话就可能绕过。必须双层落地：SOUL 管“想不想”，权限层管“能不能”。
- **规则互相冲突**：例如 Tone 里写“极简”，Example 又给了一段很长的解释，模型会偏向示例。写完要做小样本回归。
- **热更新不生效**：OpenClaw 可能缓存了启动上下文，改完 SOUL.md 要重启 Agent 或显式 reload，否则还在用旧人格。
- **把敏感信息写进 SOUL.md**：凭证应走环境变量或 secret 管理，不要提交进仓库。

## 可复用建议

- 用“必须 / 禁止 / 优先 / 最多”等词，减少形容词。
- 硬边界尽量转成可执行策略，例如“禁止删除”不如“删除类命令需要二次确认且白名单控制”。
- 给失败模式留 2–3 个示例，比长篇解释更有效。
- 把 SOUL.md 纳入版本管理和 code review，避免个人本地改完不生效。
- 不同环境用不同 profile，如 `SOUL.dev.md`、`SOUL.ops.md`，避免开发调试和生产边界混用。

## 总结

SOUL.md 不是给 Agent 写人设作文，而是把最容易漂移的部分变成一个可维护的配置。边界要双层落地：SOUL 表达意图，权限层执行限制。保持简短、可测、有版本，比追求人格丰富更重要。
