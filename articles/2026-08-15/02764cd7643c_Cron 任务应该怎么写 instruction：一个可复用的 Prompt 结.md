## 背景

Cron 在 OpenClaw / Agent 自动化里只解决“何时触发”，不解决“触发后做什么”。真正执行任务的是模型，所以 cron 里的 instruction 应该按运行手册来写，而不是按对话来写。很多定时任务不稳定，不是 cron 表达式有问题，而是 prompt 本身没把执行边界说清楚。

## 问题

常见的 cron instruction 写法有四个坑：

- 目标过宽：例如“每天看看服务器有没有问题”，没有交付物，模型容易自由发挥。
- 没有前置检查：任务在错误前提下继续执行，例如重复跑同一天的报告。
- 没有输出约束：成功也通知、失败也通知，时间一长没人再关注。
- 没有异常路径：工具超时、权限不足时，模型会自己编一个结果。

这些问题在普通对话里不明显，但一旦变成定时任务，就会被稳定地放大。

## 做法：把 instruction 写成五段式

一个可复用的 cron instruction 结构如下：

1. 角色与目标：一句话说清任务交付物。
2. 前置检查：执行前必须确认的状态。
3. 执行步骤：给确定性动作，不要写“分析一下”。
4. 工具与边界：允许使用哪些 MCP/插件，禁止哪些操作。
5. 输出与异常：结果写到哪里、通知谁、失败怎么处理。

对比一个差例和一个好例。

差例：

```text
每天检查服务状态，有问题通知我。
```

好例：

```text
你是运维值班 agent。每天北京时间 09:00 执行一次检查。

前置检查：
- 读取 last_check.json，如果 run_at 为今天且 status=success，则直接退出，避免重复执行。
- 忽略历史消息，只按本次任务上下文执行。

执行步骤：
1. 使用 server-status MCP 查询 prod-api 的 CPU、内存、磁盘。
2. 只读取，不执行任何变更操作。
3. 如果 CPU > 80% 或磁盘 > 85%，触发 notify 插件发送一条消息到 #ops。
4. 否则不发送通知。

输出：
- 将结果以 JSON 追加到 logs/cron-check.jsonl，字段：task_id, run_at, status, cpu, mem, disk, alert。
- 成功且无告警时静默；有告警时只发一条通知。
```

这个好例的核心不是长，而是每一段都限制了模型的自由空间。

## 踩坑点

**时区问题**  
cron 表达式通常按 UTC 触发，但 instruction 里如果写“今天”，模型可能按 UTC 理解。建议在任务里明确“北京时间”或“本地时区”，并让模型读取日期时带时区信息。

**上下文污染**  
如果任务会话保留历史记录，上一轮的输出会进入下一轮上下文。模型可能把旧结果当成当前状态。建议在 instruction 开头加一句“忽略历史消息，只按本次任务上下文执行”。

**幂等性**  
重复触发会导致重复报告、重复通知。用状态文件或 marker 做去重，例如写入 `run_at` 和 `status`，下次执行前先检查。

**外部工具超时**  
MCP 或插件卡住会让 cron 任务悬挂。给工具调用设超时，失败时写 `failed` 日志并退出，不要让模型无限等待。

**通知策略**  
成功静默、异常通知。否则连续几天收到“一切正常”，真正告警时反而被忽略。

## 可复用建议

- 维护一个 cron instruction 模板，只改目标、步骤和输出，不重写结构。
- 上线前先 dry-run 一次，观察工具调用链是否符合预期。
- 状态外置：把进度写入文件或数据库，不依赖模型记忆。
- 结构化日志：每次运行带 `task_id`、`run_at`、`status`，方便排障。
- 给 cron 加随机延迟，避免多个任务准点集中触发。

## 总结

Cron instruction 的目标不是让模型“聪明”，而是让它在限定边界内可预期地执行。把 prompt 写成 runbook，模型就像值班员；写成聊天，它就会在凌晨三点自由发挥。
