RISC-V 很长时间被当成 MCU 和 IoT 的“低成本替代品”，但最近产业讨论的方向明显变了。36氪这篇话题把下一站指向服务器、AI 和机器人，不是因为这三个场景容易，而是因为它们都出现了同一个信号：芯片不再只拼参数，而拼软件栈、生态和能不能在真实负载里活下来。

过去一年能观察到几个变化：64 核 RISC-V 服务器芯片开始出现在云厂商测试机柜里；AI 推理工具链开始把 RISC-V Vector 当一等公民；机器人控制器厂商开始认真评估 RISC-V 的多核异构方案。变化是真的，但坑也是真的。下面拆开看。



## 一、为什么是这三个场景？

- **共同点：算力分散、定制需求高、授权成本敏感**  
  服务器、AI 推理、机器人都不再是“一颗大芯片通吃”。服务器边缘节点、推理盒子、关节控制器需要不同算力，RISC-V 的模块化和可扩展性刚好能切入。

- **服务器：从“能开机”到“能跑业务”**  
  单看参数，64 核 RISC-V 已经能跑 Linux、KVM、Docker，部分云厂商在测数据库和 Web 负载。但在生产环境，固件、内核、JVM、K8s 的细节问题会成倍放大。

- **AI：推理比训练更现实**  
  训练仍然被 GPU 和高端加速器统治，但推理负载分散在边缘、中小集群和终端。RISC-V 通过 Vector Extension 和部分 Matrix Extension 可以在 CPU 侧吃掉一批低精度算子。

- **机器人：天然的多核异构试验场**  
  机器人控制器通常需要实时核、通用核、DSP/向量核协同。RISC-V 可以按需裁剪和扩展，比固定架构更灵活。

这三个场景不是互相独立，而是一条链条：服务器验证生态高度，AI 验证扩展指令，机器人验证低功耗和实时性。中国有整机、云和机器人产业链，给 RISC-V 提供了内需试验场，但试验场不等于商业闭环。

## 二、服务器：真正的坎在软件和平台化



- **硬件可用性已经前进一步**  
  多核、PCIe、DDR 等基础能力不再是问题，RISC-V 服务器开发板到服务器形态都有。跑个 Linux 发行版已经不是新闻。

- **软件栈是真正分水岭**  
  服务器不能只看 CPU 核数，还要看 U-Boot/EDK2、ACPI、Linux 内核、GCC/LLVM、OpenJDK、数据库、K8s 的配合。RISC-V 在这些组件上仍然存在性能回退和功能缺失，比如 JIT 编译优化、加密库向量化、数据库内存屏障等。

- **平台规范在收敛，但还不够**  
  RVA20、RVA22、RVA23 这些 profile 让基础软件有了共同目标，RISE 社区也在推动固件和 OS 一致性。但相比 Arm 的 ServerReady 体系，RISC-V 服务器平台规范还处于早期。采购方很难像买 Arm 服务器一样拿到一张明确的兼容性清单。

- **一个残酷事实**  
  服务器市场对宕机和性能回退几乎零容忍。RISC-V 服务器最容易陷入“开发板繁荣、商业订单稀少”的尴尬。真正愿意为它掏钱的，不是看开发板的工程师，而是用云资源池成本算账的采购负责人。

## 三、AI 算力：扩展指令是机会也是风险

- **机会：RVV 1.0 已经冻结**  
  RISC-V Vector Extension 1.0 冻结后，TVM、MLIR、ONNX Runtime 开始有目标后端。这意味着 AI 框架可以把 RISC-V CPU 当一个可编程向量处理器来用，不需要每颗芯片都单独写算子。

- **风险：Matrix 扩展还没完全统一**  
  低精度矩阵乘是 AI 推理的关键，但 RISC-V 的 Matrix 扩展目前尚未完全冻结。于是有厂商做私有扩展，导致一颗芯片一个 SDK，AI 团队适配成本直线上升。

- **现实定位：先做算子卸载，别碰训练**  
  训练集群的带宽、缓存一致性、互联要求太高，RISC-V 短期内不适合硬碰硬。推理侧的图像分类、检测、NLP 轻量模型，以及视频结构化、音频识别等边缘任务，是可以先落地的场景。

- **判断标准**  
  如果一款 RISC-V AI 芯片不提供公开的编译器后端、量化工具和标准 RVV 支持，只给闭源 SDK，基本可以判定会锁死在单厂商生态里。

## 四、机器人：比服务器更接近现金流

- **需求更具体**  
  机器人对芯片的要求不是“极致算力”，而是实时性、低功耗、多路外设和可靠通信。EtherCAT、CAN、PWM、编码器接口这些在机器人控制器里是刚需。

- **RISC-V 的定制能力匹配度高**  
  一个关节控制器可以用小尺寸 RISC-V MCU，一个视觉模组可以用带 RVV 的 SoC，一个底盘控制器可以用多核异构。芯片厂商可以按机器人厂商的接口和算法去裁剪，这是 x86 给不了、Arm 未必愿意做的灵活度。

- **软件生态比服务器轻，但有硬门槛**  
  ROS 2 对 RISC-V 的支持、实时 Linux、外设驱动、安全认证，这些是机器人厂商最关心的。它们不会因为“开源指令集”买单，只会因为便宜、好买、好开发而切换。

- **落地路径**  
  从视觉加速卡、边缘网关、关节控制器等小节点上量，比一上来做整机主控更现实。先在真实产线上跑几千小时，再谈平台化。

## 五、别只谈替代，先谈软件和商业闭环

- **碎片化是最大的敌人**  
  RISC-V 的自由是一把双刃剑。过度自定义会让编译器、内核、发行版分裂，最终变成“各家玩各家的”，软件成本反而高于省下的授权费。

- **工具链投入被低估**  
  很多公司愿意流片，却不愿意长期养编译器、调试器、性能分析团队。RISC-V 社区的核心基础软件仍由少数公司维护，一旦这些公司转向，生态会明显震动。

- **人才结构是瓶颈**  
  懂微架构、编译器、操作系统、性能调优的复合工程师非常稀缺。这不是培训班能速成出来的，需要项目里喂出来。

- **商业闭环要算清楚**  
  芯片公司如果只做开发板生意，财报很难看。真正的锚定场景应该是机器人大批量控制器、边缘推理盒子、存储/网络加速卡这类愿意持续采购的品类。

## 收尾：三条实用判断



1. **先锁定软件栈，再看 PPT 参数**  
   评估任何 RISC-V 方案，先明确要跑哪版 Linux 内核、哪套编译器、哪些框架和中间件。让厂商给出的是“能跑哪些软件”的清单，而不是核数和跑分。

2. **优先选遵守公开 profile 的芯片**  
   尤其在服务器和 AI 场景，RVA22/RVA23、标准 RVV 1.0 是迁移成本的关键。远离未冻结的私有扩展，除非你愿意和单一芯片厂商签长期绑定协议。

3. **从小算力节点切入验证**  
   机器人网关、边缘推理盒子、存储控制器，这些场景容错度高、迭代快，能拿到真实负载数据和功耗数据。跑通之后再谈服务器或平台级产品，节奏更稳。

RISC-V 的下一站，看起来是服务器、AI 和机器人，实际上是在考验软件工程、生态治理和商业耐心。谁能把这三件事做扎实，谁才能从“能点亮”走到“能上生产”。
