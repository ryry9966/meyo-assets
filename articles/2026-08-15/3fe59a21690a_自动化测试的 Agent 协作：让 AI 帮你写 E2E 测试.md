## 背景

E2E 测试最贵的不是“写”，而是“维护”：页面改版后选择器失效、异步加载导致偶发失败、断言写得太宽或太死。把生成初稿交给 Agent，把人放在审校和规则制定上，是一条比较务实的路径。

在 OpenClaw 的 Agent 配置里，给测试 agent 挂上 Playwright MCP 和文件系统 MCP，它就能完成“生成用例 → 执行 → 读失败日志 → 修一版”的闭环。下面记录一个可复现的做法。

## 问题

直接让 Agent 写 Playwright 测试，通常会遇到三类问题：

1. 只生成不执行，选择器是猜的，跑起来就挂。
2. 喜欢写超长流程，一个用例串起登录、搜索、下单、登出，失败后很难定位。
3. 为了“修到通过”，自动加 `waitForTimeout(3000)` 或跳过断言，测试通过但失去价值。

所以重点不是“要不要用 Agent”，而是“给它什么样的约束和反馈”。

## 做法 / 步骤

### 1. 先给 Agent 定规则

在仓库里放一份 `E2E_AGENT_PROMPT.md`，每次生成用例时作为 system prompt 注入。内容可以很短，但必须明确：

```text
你是 E2E 测试生成 agent。

规则：
- 优先使用 data-testid，没有则用 role + accessible name。
- 禁止使用 waitForTimeout。需要等待时用 expect(locator).toBeVisible()。
- 每个 test 只验证一个用户目标，不写长流程串联。
- 断言业务可见结果，不断言内部 API 或实现细节。
- 完成后必须运行测试并读取失败输出。
- 最多自动修复两轮，仍失败则停止并输出 diff 总结。
```

### 2. 提供可执行工具链

测试 agent 需要能调用命令。OpenClaw 的 MCP 可以挂 Playwright，也可以简单粗暴地让 agent 在指定目录执行：

```bash
npx playwright test tests/e2e/checkout.spec.ts --reporter=line
```

关键是让 agent 能看到 stdout/stderr，而不是只生成代码。

### 3. 分阶段生成

不要一次让 agent 写完整个模块的 E2E。按流程拆分：

- 第 1 轮：只生成 happy path，检查元素定位是否稳定。
- 第 2 轮：补一个边界场景，例如空购物车提交、未登录访问。
- 第 3 轮：执行失败后，只允许修复定位器或等待策略，不允许改业务语义。

### 4. 人工复核

Agent 产出后，人工只需要看四件事：

- 有没有删掉断言？
- 有没有用 `test.skip` 掩盖失败？
- 有没有把业务数据写死导致下次跑挂？
- 有没有顺手改了生产代码来迎合测试？

这四步通过，基本可以纳入 CI。

## 踩坑点

**第一，Agent 喜欢写“上帝流程”。**  
一个 test 里从登录到支付全串完，失败信息指向中间某一行，根本没法维护。解决办法是在 prompt 里写死：一个 test 只验证一个用户动作的结果。

**第二，等待策略会被自动改成 sleep。**  
修复失败时，Agent 第一反应往往是 `await page.waitForTimeout(3000)`。因为这最“有效”。要明确禁止，并给出替代写法：

```ts
await expect(page.getByRole('button', { name: '提交订单' })).toBeVisible();
```

**第三，选择器越写越脆。**  
Agent 会从 DOM 里复制长 CSS 路径，例如 `.main > div:nth-child(2) > span`。必须强制优先 `data-testid`。项目里如果还没有 testid，先补一批，再让 agent 写用例，否则后续维护成本会反噬。

**第四，自动修复轮数要限制。**  
超过两轮还失败，说明不是定位器问题，可能是环境、权限或数据问题。继续让 agent 修，容易“改到通过为止”，把断言改宽或者把用例跳过。限制两轮，第三轮转人工。

## 可复用建议

- 把规则写成 `E2E_AGENT_PROMPT.md`，而不是每次口头描述。
- 准备一个测试数据工厂或 API 登录态注入，避免每次 UI 登录消耗时间。
- 让 agent 生成的用例输出到指定目录，方便 `git diff` 审查。
- 稳定后用 `npm run e2e:gen -- --flow checkout` 一类命令固化下来，不要每次手动聊天触发。

## 总结

Agent 很适合做 E2E 的“初稿生成”和“失败修复”，但不适合直接决定断言质量。工程化落地的关键不是模型多强，而是：给它清晰的规则、强制它执行并读反馈、限制它的自动修复次数、保留人的最终审查。这样得到的不再是“能跑就行”的 demo 测试，而是可以进 CI、可以长期维护的测试资产。
