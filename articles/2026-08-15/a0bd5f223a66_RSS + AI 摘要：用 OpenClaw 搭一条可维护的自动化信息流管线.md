## 背景

信息源一多，RSS 阅读器里的未读数就成了负担。不是每条都值得精读，但完全不看又怕漏掉关键信息。常见的 AI 摘要工具往往封闭，难以接入自己的自动化栈，也没法按需求定制“哪些源做全文摘要、哪些只做标题过滤、输出到哪里”。

在 OpenClaw 这类 Agent 框架里，这个问题可以拆成一条清晰的管线：**抓取 RSS → 清洗正文 → 增量去重 → LLM 摘要 → 分发到指定位置**。本文记录我实际搭这套管线的过程，重点放在工程细节和踩坑点，不堆概念。

## 问题拆解

要做的不只是“调 API 总结一篇文章”，而是让管线能无人值守地跑下去。主要难点有三个：

1. **源质量不稳定**：有些 RSS 只给摘要，有些正文里混着大量 HTML 标签、广告和脚本。
2. **重复与增量判断**：RSS 源的 guid 不一定可靠，重复处理浪费 token，漏处理又失去时效。
3. **摘要质量不可控**：直接让模型“总结一下”，容易得到长篇大论或格式混乱的输出，影响后续分发和阅读。

## 做法/步骤

### 1. 统一 RSS 入口

我用 RSSHub 或 FreshRSS 把不同源聚合到本地，统一输出格式。每个条目只保留必要字段：`title`、`link`、`pubDate`、`content` 或 `summary`、`guid`。OpenClaw 的任务全部基于这个统一结构处理，避免后续为不同源的字段差异写兼容逻辑。

### 2. 在 OpenClaw 中定义定时任务

用 OpenClaw 的 task/agent 机制建一个定时任务，周期建议 30 分钟到 1 小时。任务流程如下：

```
fetch_rss → clean_content → dedupe → summarize → dispatch
```

每个步骤独立成函数或 sub-agent，失败时只影响当前步骤，便于重试和定位。

### 3. 清洗正文

RSS 返回的 `content` 经常带完整 HTML。直接喂给 LLM 会浪费大量 token，还容易被脚本标签干扰。我使用 `BeautifulSoup` 提取纯文本，再截断到 1500～2500 字符。如果源只给摘要，不强求抓全文——除非该源对你极其重要，否则投入产出比不高。

### 4. 增量去重

去重不要只依赖 `guid`。某些源会更换 guid 或使用不稳定的参数。更可靠的方式是：对 `link` 做 SHA-256，再加 `pubDate` 做辅助判断。我用 SQLite 存已处理条目的 hash、处理时间和是否成功，状态表放在仓库外，避免污染版本控制。

### 5. LLM 摘要

摘要 prompt 要限制输出结构。我要求模型返回 JSON：

```json
{
  "one_line": "一句话总结",
  "key_points": ["要点1", "要点2", "要点3"],
  "action_items": ["与我相关的行动项"]
}
```

同时设置 `max_tokens` 和 `temperature=0.2`。对于特别短的内容，直接跳过摘要，保留标题即可。每天设置摘要总量上限，避免某个源突然爆发导致成本失控。

### 6. 分发

摘要完成后，通过 MCP 工具写回 Markdown 日报、发送到 ntfy/Telegram，或追加到个人知识库。每条摘要必须保留原文链接，方便回溯。AI 摘要只能做过滤器，不能替代原文。

## 踩坑点

**RSS 源只给摘要**：一开始总想抓全文，结果碰到反爬、登录墙、页面结构变化。后来改成：默认用 RSS 提供的摘要，重要源再单独处理。稳定性优先。

**guid 不稳定**：某源每次抓取都会生成新的 guid，导致同一篇文章反复处理。改成基于 link hash 后去重才稳定。

**HTML 清洗不干净**：直接正则去标签会留下大量 CSS 和脚本残留。用 BeautifulSoup 提取正文文本，再做空白规范化，能显著降低无效 token。

**LLM 输出格式漂移**：让模型输出自由文本，分发时很难解析。改成 JSON 输出并在代码里校验字段，失败就重试一次，仍失败则保留原文标题和链接，不做摘要。

**任务并发冲突**：定时任务偶尔会撞上上一轮还没跑完。加一个文件锁或状态检查，避免重复抓取和写入。

**MCP 工具返回体过大**：RSS 读取工具若一次返回所有条目，可能超出上下文限制。确认它支持 limit/offset 参数，或者在本地做分页。

## 可复用建议

1. **拆成可测试的步骤**：fetch / clean / dedupe / summarize / dispatch 各自独立，单独调试比整条跑容易得多。
2. **状态持久化**：用 SQLite 或 JSONL 记录已处理条目、错误统计和每次运行日志。出了问题能回溯。
3. **dry-run 模式**：在管线里加一个 `--dry-run` 参数，只抓取和清洗，不调用摘要和分发，便于验证上游。
4. **摘要分级**：长文做摘要，短文只过滤标题，极长文再考虑分段。别所有内容都用同一种处理方式。
5. **保留原文链接**：这是底线。AI 摘要可能遗漏重要细节，甚至误读。

## 总结

RSS + AI 摘要这条管线本身不复杂，但要做到稳定运行，关键在于去重、清洗、输出结构化和状态管理。OpenClaw 的 Agent 和 MCP 机制适合做这类自动化编排，因为它能把外部工具、定时任务和 LLM 调用放在同一个可维护的工程结构里。真正花时间的不是写 prompt，而是处理那些“脏数据”和边界情况。把这些细节做好，它就会成为一个安静、可靠的信息过滤器，而不是又一个需要每天照看的玩具。
