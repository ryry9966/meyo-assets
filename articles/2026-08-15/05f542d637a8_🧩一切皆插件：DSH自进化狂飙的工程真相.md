36kr 那条《一切皆插件，DSH在“自进化”之路上狂飙》把两个词炒热了：插件化、自进化。很多人关注的是“狂飙”的速度，但真正值得拆解的是——为什么插件会成为 AI 系统的一等公民？所谓自进化，到底发生在模型权重里，还是发生在工具层？如果不把这两个问题说清楚，很容易把架构选择当成营销概念。下面从工程实现和产品逻辑两个角度展开。



## 一、“一切皆插件”不是新词，但含义变了

- 插件化在软件行业并不新鲜。Chrome 用 extension 把浏览器变成平台，VSCode 用插件把编辑器变成 IDE，Figma 用 plugin 把设计工具变成生态。它们的共同点是：核心内核保持稳定，长尾能力交给外部开发者。
- 传统插件通常是被用户“点开”的功能，例如一个网页截图扩展、一个代码格式化插件。宿主机制固定，插件单向补充。
- AI 语境下，含义发生关键变化：LLM 本身没有实时数据，也不直接操作外部系统，但模型能理解自然语言、生成调用计划。于是插件成为模型主动调用的“手和脚”。典型技术路径包括 function calling、tool use，以及后来被广泛讨论的 MCP（Model Context Protocol）。
- 这个变化意味着：插件不再只是功能补充，而是决定模型能力边界本身。一个没有浏览器插件的模型，和挂载了实时检索、代码执行、订单查询插件的模型，完成复杂任务的能力天差地别。

## 二、DSH 的激进之处：插件变成“一级公民”

- 很多 AI 系统仍以模型为中心，插件只是可选外挂。DSH 类架构则把插件地位抬到一级公民：模型调用器、memory、retrieval、evaluator、planner 都可以作为 plugin 挂载。
- 统一 manifest 或声明式 schema，让每个插件描述自己的能力、输入输出 schema、权限要求。模型只需要读取描述，就能判断该调用谁。
- 热插拔是核心特征：新增一个 plugin，不需要重新训练模型，也不需要重启整个系统。能力扩展从“重新训练”变成“加载一个描述文件”。
- 组合能力来自 workflow：多个插件可以串成一条链，比如检索插件拿到文档、提取插件抽取字段、写入插件回写数据库。模型在中间只做调度和异常处理。
- 这种设计和 Unix 哲学很像：small pieces, loosely joined。也像微服务，但粒度更小、生命周期更短、调度更动态。区别在于，AI 系统把“判断该用哪个小模块”这件事也自动化了。

## 三、“自进化”不是玄学，是三个闭环在转



- 第一个闭环是 tool-use loop。模型感知任务后，先规划步骤，再调用插件，观察返回结果，根据结果决定下一步。这个 pattern 在 ReAct 论文里被总结为 reasoning 和 acting 交替；function calling 让它变成结构化调用，MCP 则把插件接入协议标准化。
- 第二个闭环是 feedback loop。任务完成后，evaluator 插件对结果打分，失败原因、错误 trace、用户反馈写回 memory。没有反馈，系统只是重复犯错；有了反馈，错误才可能被纠正。
- 第三个闭环是 skill distillation loop。高频成功路径被抽象、封装成新的 plugin，进入 registry。下次遇到相似任务，模型可以直接调用这个新插件，而不是重新试错。
- 关键点在于：这波“自进化”主要发生在符号层/工具层，而不是模型权重层。参数不变，行为变。这让更新成本更低，也比直接 fine-tune 更容易回滚、审计。
- 但筛选标准必须严格。如果 evaluator 只奖励表面完成率，系统就可能沉淀出“看起来对、实际错”的快捷插件，进化反而会放大偏差。

## 四、为什么它会“狂飙”：生态飞轮与热插拔经济学

- 插件市场存在双边网络效应：开发者提供 plugin，使用方消费 plugin。使用方越多，开发者越有动力补长尾能力；插件越丰富，系统越强，吸引更多使用方。
- 能力解耦大幅降低训练成本。模型不需要为每个细分场景重新训练，只要学会稳定调度即可。长尾能力交给插件解决。
- 热插拔经济学很直接：换一个插件、新增一个数据源，成本远低于微调一个模型。业务迭代从“周/月”变成“小时/天”。
- 当模型能力趋于同质化，竞争焦点会从参数规模转向工具生态。谁能更快接入高质量插件、谁的回写机制更稳、谁的评估更可信，谁就更可能留住复杂任务用户。
- 这也是为什么“一切皆插件”会被视为一种平台策略：plugin 不只是工具，还是数据入口、分发位和商业闭环。

## 五、冷思考：插件化 + 自进化 ≠ 自动变好

- 安全与权限是第一道坎。插件可能执行代码、读取数据、写入系统。如果模型被 prompt injection 诱导，调用恶意插件或错误写入，后果比聊天说错话严重得多。
- 依赖与兼容问题会随插件数量指数上升。两个插件可能争抢同一个资源，版本升级可能破坏既有 workflow。插件越多，越需要依赖锁、版本管理和兼容测试。
- 目标漂移值得警惕。自进化系统如果只追求评估指标，可能学会走捷径，而不是真正解决用户问题。比如为通过“回复快”的指标，直接返回模板，牺牲准确性。
- 可观测性会变差。链路从单模型推理变成多个插件协作，排错需要 trace、日志和回放。没有这些，系统一旦变“聪明”，反而更难理解它做了什么。
- 数据质量决定进化质量。如果反馈主要来自模型自己生成，可能出现自我表扬循环；如果来自用户，又需要处理噪声和偏见。

## 六、实用建议：跟进之前，先做三件事



1. 先定边界。把插件分成“只读工具 / 写入操作 / 数据访问”三类，按最小权限授予。涉及资金、删除、外发数据的操作必须加二次确认。
2. 再建评估。自进化必须配一套离线 eval set，任何 skill 沉淀、插件替换、prompt 调整都要跑回归。不要只凭聊天观感判断好坏。
3. 后加熔断。给插件调用设超时、重试、降级和 kill switch。系统越能“自进化”，越要有“一键回滚到上次稳定版”的能力。

插件化和自进化都不是银弹。它们把复杂度从模型内部转移到了系统层，真正值钱的不是“跑得快”，而是能不能把边界、反馈和回滚做扎实。
