## 背景

在 OpenClaw / Agent / MCP 这类自动化环境里，Cron 任务和交互式对话有本质区别：交互式对话可以随时澄清，而 Cron 是无人值守执行。一个 instruction 写错，不会有人追问“你确定要删这个目录吗”，而是会在凌晨三点静默执行，然后第二天你发现数据已经被改坏，或者任务“成功”了但什么都没干。

过去一段时间我在 OpenClaw-CN 社区里看到不少 Cron 翻车案例，问题很少出在模型能力上，更多出在 instruction 写得太像“自然语言目标”，而不是像一份可执行的规格说明。

## 问题

常见的失败模式有三类：

1. **目标含糊**：写“检查一下服务器状态”“看看有没有异常”，模型只能输出“一切正常”，没有判断依据。
2. **权限过大**：写“清理旧文件”，但没说清理哪个目录、什么条件，结果误删了不该删的东西。
3. **输出不可验证**：任务跑了，但输出只有一段自然语言，没有结构化结果，后续无法监控、检索或告警。

Cron 任务没有交互确认的机会，所以 instruction 必须更接近“运行手册”，而不是“聊天指令”。

## 做法 / 步骤

我会把 Cron 任务的 instruction 拆成几个固定部分来写：

### 1. 先定义任务契约

不要在 instruction 里只写目标。明确输入、输出、成功标准。

例如，不要写“每日检查证书过期”，而是写成：

- 输入：`list_domains` 返回的域名列表
- 输出：JSON 数组，包含域名、过期天数、是否告警
- 成功标准：所有能查询的域名都被检查到，失败项进入 `errors` 字段

### 2. 固定执行边界

只允许调用什么工具、MCP、脚本；禁止什么操作。Cron 任务默认应该最小权限。

例如：

```text
只允许调用：list_domains, get_cert_expiry, send_alert
禁止：修改 DNS、重启服务、写数据库
```

### 3. 拆分单一职责

一个 Cron 只做一件事。如果既要巡检又要清理又要发报告，拆成多个任务，或者至少拆成多个明确的步骤阶段。不要用“顺便”“同时”这类词。

### 4. 写步骤和分支，而不是写目标

“确保系统健康”是无法执行的。改成：

```text
1. 调用 list_domains 获取 domains。
2. 对每个 domain 调用 get_cert_expiry。
3. 如果 expiry_days <= 7，生成 alert 记录。
4. 如果 get_cert_expiry 失败，记录到 errors，不要重试超过 1 次。
```

### 5. 定义输出 schema

要求模型输出固定 JSON，包含 `run_id`、时间戳、结果摘要、错误类型。如果后续要落盘、发告警、做监控，结构化输出是前提。

示例：

```json
{
  "run_id": "20250101-0300",
  "checked": 12,
  "alerts": [{"domain": "example.com", "days": 3}],
  "errors": []
}
```

### 6. 写失败策略

重试几次、退避多久、失败后通知谁、是否允许修改状态。Cron 任务最怕的是失败后静默重试，或者一直重试造成堆积。

## 踩坑点

- **时区没写清楚**：Cron 表达式是 UTC 还是本地时间？instruction 里要写“以下时间均为 Asia/Shanghai”，否则日报日期会偏移。
- **“必要时”“酌情处理”**：这类词在无人值守场景下等于随机行为。改成明确阈值：`expiry_days <= 7` 就告警。
- **默认开放写操作**：清理任务一定要写绝对路径和匹配规则，例如“只允许删除 `/tmp/xxx/` 下匹配 `*.tmp` 且 mtime 超过 7 天的文件”。
- **上下文漂移**：如果任务带历史记忆，又没有重置机制，错误会累积。每次运行使用独立上下文，或明确写“不要参考上次执行结果”。
- **外部依赖变化**：网页结构、API 字段一旦变化，模型可能会猜测。指令中加一句：“如果结构变化，输出 PARSE_ERROR，不要猜测。”
- **并发重叠**：上次没跑完，下一次又启动。加锁，或指令中写：“如果检测到已有同任务运行，直接退出并记录 skipped。”

## 可复用建议

- 使用结构化模板，把 instruction 当代码一样管理：目标、触发时间/时区、输入、允许工具、禁止操作、步骤、输出 schema、失败策略、验证方式。
- 超过 15 行的 instruction，拆成多个任务。
- 在 prompt 开头加一句：“你是一个无人值守任务，不会有用户确认。”
- 测试阶段先只读，跑 3-5 次历史数据，确认输出一致，再开放写权限。
- 监控输出 schema 的字段错误率和空结果率，而不是只看任务“成功/失败”。

## 总结

Cron instruction 的核心不是“写得像人话”，而是“写得像可执行的 spec”。好的定时任务指令让 Agent 在凌晨三点也能按同一套规则行动：边界清晰、输出可验证、失败可追踪。交互式 prompt 可以模糊一点，Cron prompt 不行。
