## 背景

在 OpenClaw / Agent / MCP / 插件的实践里，AI 助手经常需要感知外部组件是否存活、任务是否完成、配置是否变化。heartbeat 不是新概念，但很容易被做成“一个定时器反复拉取”。实际工程中会面对不同部署形态：本机插件、远程 MCP server、长任务 Agent、WebSocket/SSE 通道。不同形态下，轮询和推送的成本差异非常大。

## 问题

先要明确 heartbeat 到底解决什么。如果只是判断“进程还在不在”，轮询足够；如果要同步任务进度、状态变更，问题会复杂很多。主要矛盾在于：

- 轮询简单可靠，但延迟和资源成本随频率线性上升；
- 推送及时，但连接维护、重连、代理超时、鉴权都很麻烦；
- MCP 本身以请求-响应模型为主，原生推送能力有限；HTTP SSE 和 WebSocket 可用，但要处理断线、缓冲和网关限制。

所以这不是“轮询好还是推送好”的二元选择，而是不同场景下怎样组合更划算。

## 做法 / 步骤

### 1. 区分 liveness 和 state sync

liveness heartbeat 应该非常轻量，比如 `/health` 或 MCP 里的 `ping`，只返回：

```json
{ "ok": true, "ts": 1710000000, "version": 1, "seq": 42 }
```

任务进度、状态同步不应该塞进心跳，而应走专门的事件流或查询接口。把心跳当业务查询接口用，是常见的性能坑。

### 2. 默认采用：低频轮询 + 事件推送

比较稳的工程做法是混合模式：

- 轮询作为兜底，周期 15–30 秒，用来发现进程存活、触发重连；
- 事件推送用来即时通知任务状态变化，例如 OpenClaw 插件里暴露一个 SSE 端点 `/events`，客户端连接后收到 `task.started`、`task.progress` 之类的结构；
- 低频轮询继续存在，即使推送断了，也不会完全失明。

### 3. 推送通道必须自带心跳

不要以为建立 SSE 或 WebSocket 连接后就万事大吉。Nginx、负载均衡、云函数网关通常会在几十秒空闲后静默断开。建议：

- SSE 每 15 秒发注释帧，或显式发送 `event: heartbeat`；
- WebSocket 发 ping/pong；
- 客户端设置读取超时，发现心跳丢失时主动重连。

### 4. 重连策略：指数退避 + 抖动

断线后固定频率疯狂重连，很容易造成重连风暴。推荐退避基数 1 秒，上限 30 秒，公式大致为：

```text
delay = min(cap, base * 2^attempt) + random(0, 500ms)
```

这条同样适用于 MCP server 的轮询失败，避免瞬时打满服务端。

## 踩坑点

- **轮询过频**：把 MCP 工具状态轮询设成 3 秒一次，每次调用都走完整 JSON-RPC 往返，任务量上来后触发限流，日志也被刷爆。健康检查不是业务查询。
- **同一个心跳接口做重活**：在 `/heartbeat` 里顺带查数据库、聚合任务队列、写日志，导致响应延迟抖动，客户端误判超时。心跳响应应恒定小，本地场景建议控制在 50ms 以内。
- **推送通道没有心跳**：SSE 没有注释帧，Nginx 默认 60 秒断开，客户端不断重连，日志里满是 499/504。
- **时间不同步**：客户端和 server 时钟不同步时，用 `ts` 判断“过期”会误报。优先使用服务器返回的 `seq` 或 `last_event_id` 这类单调递增标识。
- **状态竞态**：轮询和推送同时到达，旧状态覆盖新状态。可以在状态消息里带单调递增的 `version`，客户端只接受更新的版本。

## 可复用建议

- 心跳包保持轻量，只返回 `{ ok, ts, version, seq }`，不要携带大对象。
- 分离 liveness 与 readiness：进程活着不代表能接任务，liveness 管重启，readiness 管流量。
- 对 MCP 场景，尽量复用协议内的 ping / 资源变更能力；没有原生支持时，用 HTTP SSE 作为旁路事件，不要用高频轮询模拟实时。
- 监控心跳质量：记录实际间隔、丢包、重连次数、推送延迟，比单纯看“是否在线”更有用。
- 本机插件或进程可以用文件锁、Unix socket 做轻量心跳，避免网络栈开销。

## 总结

heartbeat 设计没有银弹，关键是先界定目的，再用“低频轮询兜底 + 事件推送更新”的混合模式。推送通道一定要自维护心跳，重连必须加退避和抖动。不要为了求实时去疯狂轮询，也不要为了省事只靠推送。工程上，可控的延迟和可观测性，往往比极致的低延迟更重要。
