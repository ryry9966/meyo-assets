## 背景

在 OpenClaw、Agent、MCP 插件这类自动化环境里，Cron 任务早已不是单纯的 shell 定时脚本，而是让 Agent 在固定时间按照自然语言 instruction 执行一段工作流。比如“每天早上 9 点抓取告警并总结”“每小时检查一次队列积压”。

问题在于，很多人把 Cron 的 instruction 写成了“意图”，而不是“可执行步骤”。“每天总结重要新闻”这种写法，Agent 可能去搜索一堆来源、格式混乱、失败也不报错。定时任务一旦静默漂移，比不跑更危险。

## 问题

在实践中，Cron 任务的 instruction 常见几类问题：

- 目标模糊：不知道“总结”的范围、长度、数据来源。
- 没有执行边界：Agent 可能调用无关 MCP 工具，耗时且不稳定。
- 输出不可控：结果淹没在日志里，或者刷屏。
- 异常处理缺失：接口挂了、权限不足，任务静默失败。
- 时区与幂等：不同环境时区不一致，重复执行产生重复数据。

这些问题的根源是：我们把 Agent 当成了“理解意图的助手”，但 Cron 场景下，它更像一个需要明确约束的运维执行器。

## 做法：把 instruction 写成四段式 SOP

我目前可复用的模板是四段式：

1. **目标**：一句话说明任务成功的定义。
2. **前置检查**：运行前需要确认的状态、数据、依赖。
3. **执行步骤**：只允许调用的工具、顺序、参数。
4. **输出与失败**：输出格式、目标渠道、失败策略。

一个实例：

```text
[Cron 任务] 工作日 09:00 Asia/Shanghai

目标：抓取指定 API 的最新告警，过滤 P0/P1，输出不超过 200 字摘要到 #ops 频道。

前置检查：
1. 确认当前时间为工作日，否则直接结束并输出 SKIP。
2. 检查环境变量 OPS_API_TOKEN 是否存在，缺失则发送“cron 失败：缺少 token”到 #ops，不执行后续。

执行步骤：
1. 仅使用 fetch 工具 GET https://api.internal/incidents?since=24h
2. 只读取返回中的 id、severity、title、status 字段。
3. 过滤 severity in [P0, P1] 且 status != resolved 的记录。
4. 按 severity 降序排列，最多取 5 条。

输出与失败：
- 有结果：输出 Markdown 列表，每条格式为 `[P0] 标题 - 状态`。
- 无结果：输出“过去 24h 无 P0/P1 活跃告警”。
- 任何异常：输出“cron 失败：{error}”到 #ops，不要自行重试超过 1 次。
- 禁止调用除 fetch 以外的工具，不要搜索、不要总结历史告警。
```

这样写的好处很明显：边界清楚，Agent 不容易漂移；失败可追踪；输出约束避免刷屏。

## 踩坑点

1. **自然语言时间表达**  
   写“早上”“上午”会被 Agent 按自己默认时区解释。必须写 `Asia/Shanghai` 或直接给 Cron 表达式，并确保执行环境时区一致。

2. **“适当总结”必须量化**  
   “适当”“简要”这类词每次执行结果都不同。改成“不超过 200 字”“最多 5 条”“只输出标题和状态”，可验证性会强很多。

3. **没有限定工具**  
   很多 Agent 为了“更完整”，会调用额外 MCP 工具甚至联网搜索。明确写“仅使用 fetch 工具”“禁止调用搜索”，能显著降低不确定性。

4. **没有失败出口**  
   太多定时任务失败后没有留下记录，过了三天才发现。要求失败时也发一条简短消息，并限制重试次数。

5. **不幂等**  
   重复执行可能重复写文件、重复发消息。instruction 里要写“若目标文件已存在且内容一致，则跳过”，或者用日期字段做去重。

6. **没有 dry-run**  
   不要直接挂 Cron。先在对话里手动跑一遍同一 instruction，确认输出符合预期，再交给定时器。

## 可复用建议

- 建立 instruction 模板，放在插件或项目 README 里，新任务从模板改，不要每次从零写。
- 用“完成定义”代替“目标”：可验证的字段、数量、目标位置。
- 所有外部依赖都要显式声明：环境变量、文件路径、API 地址、权限。
- 输出格式固定，方便后续 diff 或通知。
- 失败策略至少包含：报错摘要、是否重试、通知谁。
- 定期检查 Cron 日志，不要“设后即忘”。

## 总结

Cron 任务的 instruction 本质是给 Agent 的一份运维 runbook。写得越像“可执行约束”，执行越稳定。把模糊意图改成“目标 + 前置检查 + 执行步骤 + 输出与失败”，再配合 dry-run、失败通知和幂等约束，定时自动化才能从玩具变成可靠的基础设施。
