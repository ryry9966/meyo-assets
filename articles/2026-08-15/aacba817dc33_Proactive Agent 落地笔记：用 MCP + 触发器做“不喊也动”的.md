## 背景

大多数 AI 助手仍然是“被动应答式”：你问一句，它答一句；你调用一次工具，它执行一次。时间一长，很多自动化场景会卡在一个尴尬位置——助手明明有能力处理，但如果你不主动开口，它就不会动。

在 OpenClaw 这类 Agent 框架里，我们已经有 MCP、插件、工具调用和上下文记忆。理论上，把“触发”从“用户输入”扩展到“事件/时间/状态变化”，就能让助手从被动变成主动。但实际落地时，proactive 不是简单加个定时器，它更像一个需要控制权限、频率和可回滚性的小型调度系统。

这篇文章记录我在 OpenClaw 环境中实现“不等你开口就把事情办了”的一次实践，重点不是炫技，而是可复现的工程做法和踩坑点。

## 问题

我想解决一个具体场景：监控某个数据目录，当新增文件超过阈值或文件内容匹配规则时，让 Agent 自动整理摘要、通知我，并在允许的情况下执行清理/归档。

第一版很快失败：我直接写了一个循环任务，让 Agent 每 5 分钟扫描目录，发现问题就处理。结果出现三类问题：

1. **重复执行**：同一个文件被处理多次。
2. **误触发**：临时文件、写入中的文件被当成新文件。
3. **动作不可控**：Agent 自动删除文件时，没有留下足够上下文，事后很难追溯。

这些问题的本质不是“AI 能力不够”，而是缺少一个稳定的触发层和执行边界。

## 做法 / 步骤

我把实现拆成四层：感知、决策、执行、回执。每一层都可以在 OpenClaw 中独立替换或关闭。

### 1. 感知层：让 MCP Server 暴露事件，而不是让 Agent 硬扫

不在 Agent 的主循环里写文件扫描逻辑。单独起一个轻量 MCP server，只做两件事：

- 轮询目标目录；
- 将“新文件稳定写入完成”作为事件输出。

判断“稳定写入”可以用文件大小和 mtime 两次采样间隔不变，避免读到写了一半的文件。

MCP server 暴露类似工具：

```json
{
  "name": "poll_data_events",
  "description": "Return new stable files since last cursor",
  "inputSchema": {
    "cursor": "string",
    "limit": "number"
  }
}
```

OpenClaw 侧只负责持有 cursor 和调用结果，不关心底层扫描逻辑。这样做的好处是：触发逻辑可以单测，不会污染 Agent 的上下文。

### 2. 决策层：把 proactive 动作拆成 proposal，而不是直接执行

Agent 拿到事件后，第一步不执行高风险动作，而是生成一个 proposal。比如：

```text
发现 3 个新文件，总大小 2.1GB。
- 建议归档 2 个超过 7 天的 .log 文件
- 建议保留 1 个 .csv 等待人工确认
```

这一步可以用 OpenClaw 的正常对话/工具调用完成。关键是强制 Agent 输出结构化建议，而不是自然语言段落。结构化之后，后续执行和审计都容易。

一个简单的输出约束：

```json
{
  "action": "archive",
  "targets": ["a.log", "b.log"],
  "reason": "older_than_7d",
  "dry_run": true
}
```

### 3. 执行层：白名单 + dry-run 先行

只有 `action` 落在白名单里的动作才允许自动执行。白名单我目前只放了三类：

- `archive`：移动到归档目录；
- `notify`：发送通知；
- `append_summary`：写摘要文件。

删除、覆盖、上传外部服务等高危动作一律不进白名单，必须转人工确认。

同时所有自动动作先跑 `dry_run`，返回预期结果。比如归档会返回源路径和目标路径，但实际不移动。确认无误后，再切到真实执行。

### 4. 回执层：每次 proactive 行动都要留下审计记录

每次自动执行写一条 JSONL 日志，至少包含：

```json
{
  "ts": "2026-01-01T10:00:00Z",
  "trigger": "new_file_event",
  "proposal_id": "uuid",
  "action": "archive",
  "targets": ["a.log"],
  "dry_run": false,
  "result": "ok",
  "hash": "sha256:..."
}
```

这个日志不是为了好看，而是为了回滚。比如 Agent 误归档了文件，可以从日志里找到目标和 hash，恢复现场。

## 踩坑点

**1. 触发器太敏感，导致 Agent 被频繁唤醒**

早期我按“有新文件就触发”，结果一次批量导入会唤醒 Agent 几十次。后来加了两个限制：最小触发间隔 60 秒；单次批量事件合并上报。这样 Agent 上下文不会被刷爆，token 消耗也稳定很多。

**2. Agent 把“通知”当成“任务完成”**

有一次 Agent 只发了通知，没有执行后续处理，但日志显示任务成功。原因是我把 `notify` 和 `archive` 放在同一个 proposal 里，Agent 倾向于选择成本最低的动作。后来改成：通知是默认附带项，核心动作必须单独声明。这样它不能再只通知了事。

**3. 上下文膨胀**

如果每次触发都把完整目录列表、历史事件全塞进上下文，Agent 很快会变得迟钝。解决办法是感知层只返回增量事件，决策层只接收最近 20 条事件摘要。完整数据不进上下文，只留在外部存储，需要时再通过工具查询。

**4. 忘记处理 cursor 失败**

MCP server 返回 cursor 后，如果 Agent 执行失败，cursor 没有回滚，下次会漏掉事件。后来把 cursor 更新和审计日志放在同一个事务里：只有确认 proposal 处理完成，cursor 才推进。

## 可复用建议

如果你的场景也想做 proactive，建议先满足以下条件再动手：

- **动作白名单**：先只开放只读或可逆动作；
- **dry-run 默认开启**：所有写操作先模拟，输出预期结果；
- **事件去重与合并**：避免重复唤醒；
- **结构化 proposal**：不让 Agent 输出自由文本就去执行；
- **审计日志与 cursor 绑定**：确保失败可重放；
- **人工确认逃生门**：当 proposal 置信度低或动作不在白名单时，转人工。

一个可以用在所有 proactive 场景的极简流程：

```text
事件源 → MCP 增量 poll → Agent 生成 proposal → 白名单校验 → dry-run → 审计日志 → 真实执行/转人工
```

## 总结

Proactive 能力不等于“让 AI 自动做更多事”，而是让 AI 在明确的边界内、以可审计的方式主动推进。OpenClaw + MCP 提供了很好的工程底座，但真正的难点在于：如何区分“新事件”和“有效事件”，如何让 Agent 先提出建议而不是直接动手，如何确保每一条自动动作都能被追踪和回滚。

先跑通一个小而稳的触发闭环，比一次性接入十几个 proactive 场景重要得多。把白名单、dry-run 和审计做好，你的 Agent 才能真正做到“不等你开口，但不会替你闯祸”。
