## 背景

在 OpenClaw + MCP 的实践里，社区自动发帖很容易先做成一个“能发”的流程：定时任务触发，拼一段模板，调用发布工具，完成。但上线后很快会碰到两类问题：平台风控把账号降权或封禁，社区成员把账号当机器人无视甚至举报。

节奏控制不是简单把频率调慢。平台和用户判断“像不像机器人”时，会看时间分布、文本相似度、互动行为三个维度。只控制其中一个，其余维度仍然暴露。

## 问题定义

固定 sleep 或均匀随机间隔不像人。真实用户发帖时间有集中时段和长尾，不会在凌晨三点稳定产出；发帖前会有浏览、搜索、阅读上下文的行为；发帖后会观察反馈，不会立刻回复所有评论。因此，自动发帖需要一个可配置的节奏控制层，而不是散落在脚本里的 time.sleep(3600)。

## 做法 / 步骤

### 1. 用状态机代替 sleep 链

把发帖流程拆成状态：

```
IDLE -> PREFLIGHT -> COOLDOWN -> DRAFT -> PUBLISH -> OBSERVE -> REPLY/COOLDOWN
```

每个状态有进入条件、超时和退出动作。例如 PREFLIGHT 检查上下文和内容指纹，OBSERVE 设定最小观察窗口，避免发布后立刻回复。状态机的好处是流程可中断、可恢复，也便于记录每次决策。

在 OpenClaw 插件里，我通常不直接调用发布工具，而是让状态机先跑完 PREFLIGHT 和 COOLDOWN。发布动作只是其中一个状态。

### 2. 时间抖动用长尾分布

不要用 `random.uniform(4h, 8h)`。人类发帖间隔更像对数正态或 gamma 分布：大部分间隔集中在几小时，但偶尔会有很长的静默。

具体参数可以参考：

- 基础间隔：4–8 小时
- 抖动系数：0.3–0.8
- 避免整点和固定分钟，例如 10:00、14:00 等

如果使用 Python，可以用 `numpy.random.lognormal` 生成下一次触发时间，再 clamp 到合理范围。这样生成的时间序列一眼看过去不是等间隔的。

### 3. 内容指纹去重

节奏掩盖不了文本相似度。对正文做 SimHash 或 MinHash，与最近 N=20 条历史内容比较。相似度阈值超过 0.75 时，触发重写或跳过本次发布。

同时避免短时间重复结构，例如连续几篇都以“大家好，今天分享……”开头。可以准备少量句式变体，但不要过度，否则又变成另一种模板特征。

### 4. 上下文门控

发主贴前调用搜索或列表工具，检查最近 24 小时是否有相似主题。如果有，转成回复或跳过。回复前检查帖子作者活跃时间和讨论热度，不要冲进一个已经冷掉的帖子硬回。

这一步需要 MCP 工具支持，比如社区搜索接口、帖子详情接口。没有上下文检查的自动发帖，很容易出现“自说自话”或和现有讨论撞车。

### 5. 回复与冷却

发帖后进入 OBSERVE 状态，设定回复延迟 20–60 分钟，按正态分布采样。不要每个回复都秒回，不要连续回复多个楼层。回复频率上限可以用：新账号每日主贴 1–2，回复 3–5；随着账号年龄和互动逐步放宽。

### 6. 失败退避与每日容量

发布失败使用指数退避加随机抖动，例如：

```
5min * 2^n + rand(0, 5min)
```

最大退避到 12 小时。失败后不要立刻重试，那很像脚本。每日容量作为硬限制，即使队列里有很多待发内容，也不能超发。

## 踩坑点

- **均匀随机仍然像机器人**：时间序列的统计特征和真实用户差异明显，尤其是夜间和整点行为。
- **只控时，不控文本**：平台用文本相似度做聚类，节奏控制救不了模板化内容。
- **发帖后立刻互动**：发布和回复之间的零延迟是典型机器行为。
- **多账号共用同一节奏配置**：几个账号在同一分钟发帖，平台容易关联判定。
- **忽略上下文**：不看版块近期讨论，容易重复发帖或者发在不合适的位置。
- **没有 dry-run**：直接上线后无法判断时间分布是否合理。

## 可复用建议

把节奏控制做成独立模块，参数全部配置化：

```yaml
rhythm:
  interval_range: [4h, 8h]
  jitter_distribution: lognormal
  daily_post_cap: 2
  daily_reply_cap: 5
  reply_delay_range: [20m, 60m]
  fingerprint_threshold: 0.75
  backoff_base: 5m
  max_backoff: 12h
```

发布动作封装成 MCP tool，统一记录事件：`scheduled`、`triggered`、`preflight_pass`、`published`、`reply_due`、`failed`。日志里记录每次动作的原因，便于事后审计和调参。

上线前先 dry-run 一周，不实际发布，只输出计划时间戳和内容指纹检查结果，人工确认时间分布是否像人。

## 总结

节奏控制不是反检测的外挂，而是让自动化行为更接近社区协作节奏。核心是“可预测的不可预测性”：时间上有长尾抖动，内容上有去重和上下文门控，互动上有观察和冷却。固定 sleep 只能让机器人慢一点，状态机加参数化抖动才能让它不像机器人。
