# OpenClaw memory_recall 实战：语义搜索与全文搜索不是二选一

## 背景
在 OpenClaw 里，memory_recall 是把历史片段从本地记忆库里捞回来的关键环节。很多同学一上来就接 embedding，默认“语义搜索一定比全文搜索好”。但在 agent 的 memory 里，除了自然语言笔记，还有大量 API 报错、UUID、文件路径、配置项、错误码这类字符型信息。纯向量召回在这些场景下经常翻车。

## 问题
我拿 200 条真实 agent 运行日志和笔记做了个小实验，分别用纯向量检索和纯全文检索召回，测试查询包括“为什么 webhook 返回 403”“/tmp/xxx 文件残留”“session 超时怎么处理”等。结果很典型：

- **语义搜索**在“session 超时怎么处理”这类自然语言问题上召回自然，但对“403”“/tmp/xxx”这种精确词，向量相似度经常被语义相近但无关的内容干扰。
- **全文搜索**对精确字符串命中率极高，但遇到“webhook 挂了”“回调失败”这种同义表达就完全漏掉。

结论很简单：memory 的语料是混合型，没有一种搜索方式能通吃。

## 做法/步骤
我在 OpenClaw 里把 memory_recall 改成了一条可配置的混合召回链路，步骤不复杂，但需要把几个组件拆清楚。

**1. 先做 memory 分块和 metadata 过滤**
不要整段存，按“时间/任务/来源”切小块，每条 memory 保留原始文本和 metadata（type、tags、ts、agent_instance_id）。召回前先按 agent 实例、时间窗口、source_type 过滤，这一步能砍掉大量噪声，比调模型更有效。

**2. 开两条召回通道**
在 OpenClaw 的 memory 插件或 MCP 里同时保留两种检索方式：
- **语义通道**：embedding 余弦相似度，top_k 取 20。
- **全文通道**：SQLite FTS5 或 BM25（我本地用 FTS5 就够），top_k 也取 20。

**3. 混合排序用 RRF，不要直接加权**
embedding 相似度和 BM25 分数的量纲差异很大，直接相加会让某一方主导。我采用 RRF（Reciprocal Rank Fusion），只关心排名，稳定且对量纲不敏感：
```python
score = sum(1 / (60 + rank_i) for rank_i in ranks)
```
k=60 比较稳，太小放大排名差异，太大趋于平均。

**4. 记录召回来源，方便排查**
每次召回结果里带上来源标记：`source: semantic | fulltext | hybrid`。这很重要，后面排障全靠它。

**5. 用小评测集跑回归**
准备 30–50 个真实查询，标注相关 memory ID，每次修改阈值、模型或分块策略后跑一遍，别凭感觉调。

## 一个典型翻车记录
之前只开向量召回时，agent 被问“把昨天那段 403 的排查记录找出来”，它返回了一段关于“HTTP 403 错误”的通用教程。语义上确实很像，但实际需要的是我 session 里带 webhook 关键词的日志。改成 hybrid 后，全文通道命中日志里的“403”和“webhook”，排名直接升到第一，问题解决。

## 踩坑点
- **中文分词**：FTS5 默认分词器对中文不友好，容易按单字切，召回不准。可以换支持中文的 tokenizer，或对中文内容做 bigram 索引。
- **embedding 模型选择**：专有名词、代码片段、数字 ID 在向量空间里往往不独特。别用太老的模型，选支持中文和代码的开源模型，并做归一化。
- **阈值不可跨项目复用**：笔记场景和日志场景的相似度分布差异大，建议按 source_type 分开设置阈值。
- **RRF 不是玄学**：k 值可以简单调，但别频繁改。先固定 k=60，把评测集跑通再说。
- **别忽略 metadata 过滤**：很多人直接全库召回，既慢又脏。先按 agent_instance_id、时间窗过滤，效果立竿见影。

## 可复用建议
- 先判断 memory 是“关键词型”还是“语义型”。日志、代码、ID、错误码优先全文；会议纪要、想法、读书笔记优先语义。
- 默认走混合召回，但保留纯语义/纯全文的开关，方便对比和降级。
- 把 memory_recall 当成可观测组件：打印 query、top-k、分数、命中来源。
- 评测集不要一次性做完，新增 case 就加入回归测试，让 memory_recall 越来越稳。

## 总结
语义搜索和全文搜索不是谁替代谁，而是互补。OpenClaw 里的 memory_recall 工程上默认走混合，保留手动切纯检索的开关，能让你在 agent 行为异常时快速定位是召回问题还是生成问题。memory 召回不是玄学，用日志和小评测集把它变成可复现的工程组件，比盲目换模型更有价值。
