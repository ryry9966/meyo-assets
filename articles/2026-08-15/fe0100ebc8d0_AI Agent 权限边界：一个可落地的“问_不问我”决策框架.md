## 背景

在 OpenClaw、MCP 和插件自动化场景里，Agent 的能力已经从“回答问题”扩展到“调用工具、读写文件、执行 shell、访问外部服务”。能力越强，误操作的代价越大。

权限控制如果做成二元开关——要么全部自动执行，要么每次都问——都会出问题。全自动容易把工作区搞脏、删错东西、触发外部副作用；全人工确认又会打断流程，Agent 失去自动化意义。

真正工程化的做法，是把每个工具调用放进一个**可解释的决策框架**：什么时候该问人类，什么时候可以自己干，什么时候必须直接拒绝。

## 问题

一个 Agent 执行任务时，可能经过多轮工具调用。不同操作的风险完全不同：

- 读取工作区里的普通文件，风险低，可以自动做。
- 写入 `/etc` 或 `~/.ssh`，风险高，不应该静默执行。
- 执行 `rm`、`curl | bash`、调用支付/发信接口，属于不可逆或外部副作用操作，必须确认。
- 通过 MCP 引入的第三方工具，风险未知，默认不能信任。

所以在 Agent 的工具调用链上，需要有一个 **权限闸门（confirmation gate）**，根据工具、参数、目标资源、运行环境动态决定：`allow`、`ask`、`deny`。

## 做法/步骤

### 1. 先给工具做风险分级

不建议只按“读/写”粗略分类。可以用三个维度判断：

- **可逆性**：只读、新增、修改、删除、外部副作用。
- **影响范围**：单文件、目录、整个仓库、系统级、外部服务。
- **环境**：开发沙箱、生产环境、共享资源。

组合起来形成风险等级。例如：

| 等级 | 示例 | 默认策略 |
|---|---|---|
| 低风险 | 读取工作区普通文件、查询状态 | allow |
| 中风险 | 修改工作区文件、创建分支 | ask 或会话授权 |
| 高风险 | 删除、写系统配置、执行未知 shell | ask |
| 禁止 | 越权访问、明显与目标无关的操作 | deny |

### 2. 在工具调用层加确认闸门

在 OpenClaw 的工具调用包装层或策略引擎里，统一处理所有工具，包括内置工具和 MCP 插件工具。不要只在 Agent 的 prompt 里写“遇到危险操作要问用户”，这不可靠。

一个策略配置示例，思路如下：

```yaml
policy:
  default: ask
  rules:
    - tool: fs.read
      scope: workspace
      action: allow

    - tool: fs.write
      scope: workspace
      action: allow

    - tool: fs.write
      path_pattern: "~/.ssh/**"
      action: deny

    - tool: shell
      action: ask
      allowlist: ["git status", "pwd", "ls -la"]

    - tool: shell
      command_pattern: "rm -rf /*"
      action: deny

    - tool: mcp.*
      action: ask
```

这个示例不绑定具体版本，重点是：**默认安全，白名单放行，高风险拒绝，中间态询问**。

### 3. 确认信息必须带上下文

当 Agent 需要问人类时，不能只抛一句“要执行 shell 吗？”。确认信息至少应包含：

- 具体命令或工具调用原文；
- 影响范围，例如“将删除 12 个文件，约 43MB”；
- 是否可回滚；
- 确认选项：`批准一次`、`批准同类操作`、`拒绝并说明原因`。

人类只有看到足够信息，确认才有意义。

### 4. 用审计日志逐步放宽权限

每次 `ask` 的决策都记录下来。如果某类操作长期被批准、从未出问题，可以在策略里把它降级为 `allow`。如果某类操作频繁被拒绝，就调整 Agent 的行为提示，或者直接加入 `deny`。

权限边界不是一成不变的，而是通过审计逐步收敛。

## 踩坑点

**1. 把“只读”当成绝对安全**

读 `.env`、读 `~/.aws/credentials`、读取大量数据，都可能造成泄露或性能问题。只读操作也要按数据敏感度和大范围读取做限制。

**2. 确认结果被缓存成宽泛授权**

用户批准了 `rm ./tmp/cache`，不代表批准了后续所有 `rm`。确认粒度最好是“工具 + 参数 + 影响范围”的指纹，而不是工具名。

**3. MCP 插件工具被忽略**

第三方 MCP server 可能引入几十个新工具。权限策略只配内置工具是不够的。对 `mcp.*` 应默认 `ask`，再单独放行经过验证的工具。

**4. 频繁确认导致“机械点确认”**

如果每 10 秒问一次，用户很快会习惯性点“批准”，保护失效。可以引入会话授权：用户对某类低中风险操作授权 30 分钟，或者支持批量确认“这 3 个文件写入都允许”。

**5. dry-run 成功不等于可执行**

有些命令干跑时不会暴露真实副作用。不要因为 `--dry-run` 没报错，就自动把实际操作降级为 `allow`。

## 可复用建议

- **默认 ask，逐步 allow**：未知工具、未知参数、生产环境，优先问。
- **用风险矩阵替代二元开关**：低风险自动，中风险会话授权，高风险必须确认，明显越权直接拒绝。
- **确认文案要具体**：命令、影响范围、回滚方案，缺一不可。
- **把权限策略当代码管理**：纳入版本控制，变更要评审，能回滚。
- **保留决策日志**：审计是放宽权限的依据，也是排障时还原现场的依据。

## 总结

给 Agent 设置权限边界，不是限制它，而是让它能在安全范围内自主运行。真正值得问人类的，是那些不可逆、影响面大、风险未知的关键节点；而重复、可逆、范围明确的操作，应该放行。

在 OpenClaw 这类工具调用频繁的系统里，权限策略最好落在工具调用层，而不是依赖 prompt 自我约束。默认安全、动态分级、带上下文确认、审计后放宽——这套思路可以避免 Agent 变成“需要盯着干活的半自动脚本”。
