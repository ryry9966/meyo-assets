## 背景

社区日常有不少重复性发帖需求：更新日志、教程同步、活动公告。之前靠人工复制粘贴，不仅耗时，还容易在格式、标签、发布时间上出错。我们想做一个“半自动”发帖机器人：内容由 AI 生成，人工审核后由系统稳定发布。

这个项目不是追求全无人值守，而是把最容易出错的执行环节工程化。技术栈基于 OpenClaw 的 agent 调度能力，配合 MCP 工具封装浏览器自动化和社区操作。

## 问题

目标社区没有开放写 API，只能通过 Web 操作完成发帖。直接让 Agent 拿着 Playwright 脚本“一步到位”风险很大：登录态失效、DOM 变动、限流风控、重复发帖，任何一个问题都可能导致误发或内容丢失。

因此核心问题不是“能不能发”，而是“如何可靠地发，并且出问题时能停下来、可回溯”。

## 架构设计

整体拆成四层：

1. **调度层**：OpenClaw agent 负责触发任务、决策是否继续。
2. **工具层**：MCP server 封装社区操作，不暴露万能点击工具。
3. **内容层**：Git 仓库保存草稿与已发布内容，所有改动可追溯。
4. **状态层**：SQLite/Postgres 记录每条帖子的状态、重试次数、错误日志。

关键设计是“审核闸门”。内容生成后进入 `_drafts` 目录，人工确认后移动到 `_approved`，agent 只发布 `_approved` 里的内容。这样即使调度出错，也不会把未审核内容直接发出去。

## MCP 工具设计

MCP server 只提供几个窄接口：

- `community_login_check`：检查当前登录态
- `community_preview_post`：渲染预览，不实际提交
- `community_create_post`：真正发布，使用内容 hash + 日期作为幂等键
- `community_get_status`：查询发布结果

工具内部封装 Playwright 操作，但在 agent 侧只看到明确的语义化接口。这样避免了 Agent 直接操作 DOM 带来的随机性。

发布流程状态机为：

```
draft -> approved -> publishing -> published | failed
```

`failed` 状态允许重试，但重试前必须先检查是否已经实际发布成功，避免重复。

## 踩坑实录

**1. 登录态失效**

Cookie 过期后，发布请求可能返回成功，但实际跳到了登录页。解决方式是每次发布前先访问个人中心，断言页面 URL 或关键元素；MCP 工具内置登录态探测。另外使用独立浏览器 profile，不与日常浏览器混用。

**2. DOM 选择脆弱**

社区模板改版导致选择器失效，脚本直接崩。后来尽量用文本、role 定位，少用复杂 CSS 层级。封装成 MCP 工具后，即使前端改版，也只需改一个 server，不影响 agent 逻辑。

**3. 限流与风控**

发布过快会触发验证码甚至临时封禁。调度层加入随机间隔，失败后按指数退避。遇到验证码不重试，直接标记 `needs_human` 并通知人工处理。

**4. 重试造成重复发帖**

网络超时但实际已发布成功，重试会导致重复内容。解决方法是生成内容 hash，发布后查询用户主页/列表比对；如果状态不确定，停止自动重试，转人工确认。

**5. Prompt 漂移**

同一提示词在不同模型版本下输出格式可能变化。生成层强制使用 JSON schema 约束，解析失败时回退到模板，并保留原始输出快照，方便排查。

**6. 定时任务误执行**

没有锁的情况下，cron 可能并发跑多个实例。任务启动时写 lock 文件或数据库行锁，单实例部署或明确选主。

## 可复用建议

- 把“发布”视为不可逆副作用，默认不自动执行，必须有审核闸门。
- 工具层做薄封装，Agent 只做决策，不直接操作 DOM。
- 内容与动作分离，所有发布记录保留 trace_id、截图、HTTP 状态、返回文本。
- 先跑 dry-run 模式：所有 `publish` 工具只返回将要执行的内容，不实际提交。
- 失败后优先停止并通知，而不是无限重试。

## 总结

这个机器人最终跑起来后，主要收益不是“全自动”，而是把发帖流程变成了可审计、可回滚、可人工介入的工程系统。OpenClaw 负责调度，MCP 负责封装副作用，Git 负责内容版本，状态表负责可观测。踩过的坑大多集中在“真实世界不可靠”这一点上：登录、DOM、限流、重试。把这些边界处理好，自动化才能从演示走向稳定运行。
