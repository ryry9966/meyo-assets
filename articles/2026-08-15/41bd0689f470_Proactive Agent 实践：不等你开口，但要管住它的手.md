## 背景

大部分 Agent 目前还是“你问我才动”的问答机。但在运维、数据监控、依赖安全这些场景里，真正有价值的不是回答，而是主动发现：SSL 证书快过期了、队列堆积超过阈值、某个 API 错误率突然升高。等用户想起来再问，往往已经造成影响。于是我开始尝试给 Agent 加 proactive 能力，让它在这些事件发生时自己启动任务。

## 问题

直接让 Agent“在后台自己决定什么时候干活”非常危险。没有边界的话，它很容易变成两台机器：一台是全自动误报机，另一台是 token 焚烧炉。在 OpenClaw 这类 Agent 编排环境里，我倾向于把 proactive 拆成三个明确的层：触发器、判断器、执行器。每一层都做隔离，避免模型参与不该参与的决策。

## 做法/步骤

### 1. 触发器外置，不写在 prompt 里

定时逻辑用系统 cron、systemd timer、GitHub Actions schedule，或者文件 watcher、MQTT 订阅、webhook 来承接。不要在 prompt 里写“每 10 分钟检查一次”，那样不可控也不可观测。触发器只负责唤醒一个轻量脚本，脚本先做条件过滤，再决定要不要拉起 LLM。

例如一个队列堆积检查：

```yaml
# .github/workflows/proactive.yml
on:
  schedule:
    - cron: "*/10 * * * *"
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/check_queue.sh
      - if: failure()
        run: ./scripts/invoke_agent.sh "队列堆积超过阈值，请分析并生成告警建议"
```

`check_queue.sh` 只做数值比较，不调用模型。只有条件成立时才唤醒 Agent，日常开销几乎为零。

### 2. 上下文最小化

给 Agent 的输入只保留必要数据：日志最后 200 行、metric 快照、diff 内容，而不是把整个数据库或日志文件 dump 进去。proactive 场景里上下文越长，模型越容易跑偏，成本也越高。

### 3. 工具化执行，通过 MCP 封装副作用

把“查日志”“发告警”“建工单”“重启服务”都封装成 MCP 工具。Agent 只生成调用参数，不直接拼接 shell 命令。这样即使模型判断失误，破坏面也被限制在工具定义的范围内。

### 4. 决策与执行分层

高风险动作默认 dry-run 或需要人工确认；低风险动作（如打标签、发每日摘要）可以自动执行。不要给 proactive Agent 开放 `rm`、`drop table`、`reboot` 这类不可逆工具。如果一定要，加白名单和二次确认。

### 5. 闭环与去重

每个 proactive 任务生成一个 `trigger_id`，记录到本地 SQLite 或 KV。执行前检查是否在冷却窗口，比如同一类告警 10 分钟内只处理一次。同时把 `trigger_id` 写入最终动作的元数据，方便回溯。

## 踩坑点

- **自触发循环**：Agent 发了一条消息到 IM，IM 的 webhook 又把消息当成事件喂回来。解决：消息来源加 bot 标识，过滤自身消息。
- **Token 成本失控**：每 5 分钟全量跑一次 Agent，一个月账单惊人。解决：先用规则/阈值过滤，只有异常才唤醒 LLM；日常用便宜模型或纯脚本。
- **误报疲劳**：阈值太敏感，主动消息变成噪声。解决：静默窗口 + 聚合，例如 10 分钟内同类事件合并成一条摘要。
- **权限过大**：主动执行危险操作，一旦判断错误不可逆。解决：最小权限 + 白名单 + 人工确认。
- **并发冲突**：多个触发器同时操作同一文件或数据库。解决：任务加锁，例如 SQLite 事务或 Redis lock。

## 可复用建议

- 从“定时摘要”这种低风险场景开始，比如每天早上 9 点让 Agent 汇总昨日数据变化并推送到飞书/钉钉。
- 触发条件用代码写，prompt 只负责理解和表达，不负责判断“该不该做”。
- 给 proactive Agent 单独的身份标识和 API key，方便审计和吊销。
- 每个动作记录 `trace_id`、触发源、模型输入输出摘要，便于回溯。
- 先做影子模式：Agent 只生成建议不执行，人工确认几轮后再放开自动执行。

## 总结

proactive 的价值在于把 Agent 放进真实工作流的事件闭环里，而不是让它变“主动聊天”。好的 proactive 设计是少打扰、可解释、能回滚。工程师要做的不是给模型更多自由，而是给它一个受控的触发器、最小上下文和可审计的执行边界。
