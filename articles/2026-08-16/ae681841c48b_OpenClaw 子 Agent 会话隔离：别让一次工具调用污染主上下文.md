## 背景

在 OpenClaw 里，子 Agent 一旦跑起来，很容易变成“上下文黑洞”。主 Agent 让子 Agent 去查一份数据、跑一个 MCP 工具、处理一段长文档，结果子 Agent 把完整的中间推理、工具日志、重试记录全带回来。主会话很快被撑满，后续指令被无关信息干扰，甚至出现记忆串线。

这类问题在自动化流程里更隐蔽：主 Agent 批量调用子 Agent 处理任务，某一个子任务的失败状态、MCP 连接残留、插件全局变量，会悄悄影响下一个任务。主会话的上下文污染不是一次性事故，而是慢慢累积出来的。

## 问题表现

典型的污染路径有四种：

1. **上下文合并污染**：子 Agent 返回时，把子会话的完整消息历史直接 append 到主会话，而不是只回传结果。主 Agent 看到的是大量过程细节，而不是可用的产出。
2. **session_id 复用污染**：多个子任务共用一个子 session id，导致上一个任务的历史消息、工具状态、甚至错误上下文残留在下一次调用里。
3. **MCP/插件共享污染**：子 Agent 调用 MCP server 时，如果复用主会话的连接和工具注册表，子 Agent 注册的临时工具、环境变量、认证状态可能回写主进程。
4. **状态单例污染**：插件或自定义工具把状态放在全局变量、模块级缓存里，子 Agent 执行时写入的状态没有清理，影响后续所有调用。

这些问题的共同点：**执行边界不清晰，只看输入输出，不看会话生命周期。**

## 做法/步骤

### 1. 给每个子 Agent 独立 session_id

不要为了省事复用主会话的 session_id，也不要用固定 id。按任务维度生成独立 session：

```yaml
child_session_id: "child:{task_id}:{run_id}"
main_session_id: "main:{conversation_id}"
```

task_id 和 run_id 建议使用短随机字符 + 时间戳，避免可预测 id 导致串线。OpenClaw 的 runner 配置里，如果支持 `session_id` 参数，显式传入即可；不支持的话，在封装层用 `run_id` 隔离上下文。

### 2. 只回传结构化结果，不回传原始历史

子 Agent 执行完成后，定义统一返回协议：

```python
child_result = {
    "ok": True,
    "output": "...",           # 可读结果
    "artifacts": [...],        # 文件、图片、结构化数据
    "errors": [],
    "metrics": {
        "tokens_used": 1234,
        "tool_calls": 3
    }
}
```

主会话只 append 这个结果，而不是子会话的完整 `messages`。如果必须保留部分中间信息，用 `summary` 字段压缩，长度控制在主会话可接受范围内。OpenClaw 的 artifact 机制适合做这类传递：子 Agent 产出文件或 JSON，主 Agent 只拿引用，不拿全文。

### 3. 隔离 MCP 连接和插件状态

子 Agent 需要调用 MCP 工具时，优先创建独立连接。不要图省事把主会话的 MCP client 直接传给子 Agent。如果 OpenClaw 插件支持按 session 隔离变量，开启对应选项；不支持的话，在子 Agent 包装器里手动清理：

- 执行前备份相关全局状态
- 执行后恢复，或直接丢弃子进程环境
- 避免在插件里用模块级可变变量

对于长驻进程的插件，最好把子 Agent 放到独立 worker 进程或至少独立 namespace 里执行。进程级隔离最彻底，但成本较高；namespace 隔离成本低，但需要插件配合。

### 4. 设置生命周期和超时回收

每个子 Agent 执行完，要么主动关闭 session，要么设置 TTL。批量任务里，如果有子 Agent 卡死或异常退出，残留 session 会继续占内存、占连接。建议在 runner 封装里加上：

```python
with child_session(timeout=300, cleanup=True) as child:
    result = child.run(task)
```

超时强制返回错误，避免主会话无限等待。cleanup 负责关闭 MCP 连接、清理临时文件、释放 session id。

## 踩坑点

### 1. 日志混入主会话

很多自动化流程会把子 Agent 的日志直接打到主会话的 output 里。调试时看起来方便，生产环境就是灾难。日志应该写文件或独立日志流，主会话只接收最终状态。

### 2. 嵌套子 Agent 没有隔离

子 Agent 内部再调用子 Agent 时，容易复用最外层 session。每层嵌套都要传递自己的隔离上下文，否则内层污染会在外层放大。最好限制嵌套深度，并在每层强制生成新 session id。

### 3. 错误结果被当成正常输出返回

子 Agent 失败时，如果直接把错误堆栈拼到结果里，主 Agent 可能误判为成功。一定要用 `ok` 字段区分，错误走独立的 `errors` 数组，主 Agent 根据 `ok` 决定后续动作。

### 4. 全局缓存看起来“没事”

插件用模块级 dict 缓存 MCP 结果，开发时单个子 Agent 调用没问题，批量跑就出现数据串。这类问题很难复现，建议代码评审时重点检查 `global`、`class attribute`、模块级可变对象。

## 可复用建议

- **统一封装 runner**：不要在每个调用点写隔离逻辑。封装一个 `ChildAgentRunner`，负责 session 创建、结果归一化、清理回收。
- **结果最小化**：主会话只拿 `summary + artifact 引用`，需要详情时再拉取。
- **强制超时**：所有子 Agent 调用都带超时，默认 300 秒，批量任务可以更短。
- **错误分区**：子 Agent 的调试信息写日志文件，主会话只接收结构化错误码。
- **可观测性分离**：给子 Agent 打上独立 trace id，但 trace 数据进监控系统，不进主会话上下文。

## 总结

子 Agent 会话隔离的核心不是“加个开关”，而是**把子 Agent 当成不可信的外部进程对待**：它可能留下状态、可能超时、可能返回大量垃圾上下文。主会话只接收经过归一化的结果，不接收过程。这个边界守住了，子 Agent 才能真正变成自动化流程里的稳定单元，而不是污染源。

在 OpenClaw 的实际使用中，建议从结果协议和 session_id 隔离开始，这两项成本最低、收益最大。遇到复杂插件状态问题，再引入进程级隔离。
