## 背景

在 OpenClaw 这类 Agent 框架里，扩展 AI 助手能力通常有两条路：接 MCP 工具，或者挂本地插件/脚本。但当能力数量上来以后，一个常见问题开始出现：所有技能常驻注入，导致上下文膨胀、首响延迟变高、权限边界模糊。

我们团队在接短信、日程、消息推送、文件处理等能力时，最早的做法是全部预加载。结果每次会话开头就吃掉大量 token，而且 AI 容易在不需要时误调用权限较大的工具。后来改成基于 Skills 的按需加载，问题才收敛下来。

OpenClaw 的 Skills 机制更像“操作手册 + 工具组合”，而不是单个远端工具。它解决的核心问题是：**不是装得多，而是给得准**。

## 问题

如果 Skills 设计不清，按需加载会演变成两种极端：

1. **全量加载**：所有 skill 的说明、工具列表、示例被塞进 system prompt，上下文被无意义占用。
2. **找不到**：触发条件写得太模糊，用户已经明确表达意图，但 skill 没有被匹配。

另外还有几个隐性成本：依赖初始化失败但无反馈、权限声明缺失导致运行中报错、修改后不生效导致旧逻辑继续执行。

## 做法/步骤

### 1. 让每个 Skill 自描述

在 OpenClaw 中，一个 skill 通常是一个目录，包含 `SKILL.md` 清单和实现文件。建议目录结构：

```
skills/
  sms-sender/
    SKILL.md
    handler.py
    README.md
```

`SKILL.md` 的 frontmatter 至少要写清楚：名称、适用场景、不适用场景、工具、权限、依赖。

```markdown
---
name: sms-sender
description: 发送短信验证码或通知，仅在用户明确要求发短信时使用。
when_to_use:
  - 用户要求发送验证码
  - 用户要求发送通知短信
when_not_to_use:
  - 邮件、微信推送、站内信
tools:
  - sms_api
permissions:
  - sms:send
dependencies:
  - requests>=2.31
---
```

### 2. 配置按需路由

OpenClaw 里可以设置 skill 的加载模式。核心思路是启动时只扫描和建索引，不注入完整 skill 内容；当用户意图命中时，再把必要指令注入上下文并挂载工具。

```yaml
skills:
  mode: on-demand
  index: skills/
  preload: []
  routing:
    - skill: sms-sender
      match: [sms, 验证码, 发短信]
```

这里 `match` 只是路由提示，不要依赖单一关键词。真正可靠的还是 `description` 和 `when_to_use` 的组合，让 Agent 做语义判断。

### 3. 做一个最小加载测试

写完 skill 后，不要直接丢进生产。用一个固定用例集测试：

- 明确命中用例：用户说“帮我发一条验证码短信”，是否加载。
- 负向用例：用户说“帮我发一封邮件”，是否不加载。
- 边界用例：用户说“通知一下张三”，是否产生多个 skill 竞争。

重点看日志里的加载耗时、注入 token 数、工具是否可用。

## 踩坑点

**触发词冲突**  
两个 skill 都响应“查天气”，或者“发消息”同时命中短信、邮件、推送。解决办法是给每个 skill 增加 `when_not_to_use`，必要时在路由层加优先级。

**权限声明缺失**  
skill 运行时请求了 `contacts:read` 或 `file:write`，但 manifest 里没声明。OpenClaw 的安全层可能直接拒绝，或者弹出确认但日志里没有明确指向哪个 skill。建议权限声明和实际调用保持同步。

**路径与执行环境**  
脚本依赖外部命令或环境变量，但 skill 加载后运行在隔离的工作目录，导致 `PATH` 不对或找不到配置文件。可以在 manifest 中显式声明 `env` 和 `workdir`，不要依赖全局环境。

**长文档被全量注入**  
有人把详细操作手册写在 `SKILL.md` 里，结果命中后几千字全进上下文。正确做法是 `SKILL.md` 只保留必要指令，详细文档放 `README.md` 或 `docs/`，运行时按需读取。

**修改不生效**  
OpenClaw 对 skill 有索引缓存，改完 `SKILL.md` 后没有重载，触发条件还是旧的。每次修改后建议执行重载命令或重启对应 worker，并在日志中确认新版本号。

## 可复用建议

1. **最小清单模板**：每次新写 skill 都从模板开始，强制写清 `when_not_to_use` 和权限。
2. **依赖显式化**：`dependencies` 写清版本，能在加载时发现缺失，而不是运行到一半才报错。
3. **可观测日志**：记录每个 skill 的加载时间、注入 token 数、路由命中原因、失败详情。没有日志的按需加载就是黑盒。
4. **灰度与回滚**：新 skill 先对部分会话开放，确认没有权限扩窗或误触发后再全量。
5. **安全边界**：敏感操作默认不静默执行，保留二次确认。Skills 机制能减少误调用概率，但不能替代权限设计。

## 总结

OpenClaw 的 Skills 机制不是简单地“减少能力”，而是把能力的激活成本降下来。按需加载的价值体现在三处：上下文更干净、工具调用更精准、权限暴露更可控。

务实的做法是：先规范 skill 自描述，再配置按需路由，然后通过日志和测试持续收敛触发边界。工程上最忌讳的是一上来就堆 skill，却不关心它们何时被加载、被谁加载、失败后怎么反馈。

把按需加载当成一种纪律，而不是一个配置项。
