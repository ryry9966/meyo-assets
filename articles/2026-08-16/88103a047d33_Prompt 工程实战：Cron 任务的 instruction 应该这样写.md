# Prompt 工程实战：Cron 任务的 instruction 应该这样写

## 背景

在 OpenClaw 这类 Agent 自动化环境里，Cron 定时任务不再只是跑一段 shell，而是“定时唤醒一个可能没有上下文的 Agent”。很多定时任务失败，不是工具没权限，也不是插件不稳定，而是 instruction 写得太像口头备忘，例如：

> 每小时检查一次服务状态，有问题就发通知。

这句话对 Agent 来说信息量太低。它不知道检查哪个服务、用什么命令、异常阈值是什么、通知发到哪里、重复告警怎么处理。于是同一任务每次执行结果可能不同，甚至反复调用工具。

## 问题

Cron 触发有两个天然约束：

1. **没有交互澄清机会**：凌晨三点跑出问题，没人帮 Agent 补一句“我其实是指 API 服务”。
2. **运行环境可能无状态**：冷启动后没有历史上下文，所有关键信息必须显式写在 instruction 或文件里。

所以，Cron 任务的 instruction 需要比普通对话 prompt 更接近“操作手册 + 验收标准 + 故障处理”。

## 做法：用 7 个字段写定时任务 instruction

我常用的模板如下：

1. **任务目标**：一句话说明本次运行要产出什么结果。
2. **运行环境与前置条件**：可用的 MCP 工具、插件、脚本、工作目录、环境变量。
3. **输入来源**：文件、API、数据库或环境变量，写清路径和读取方式。
4. **执行步骤**：编号列表，明确顺序、条件分支和判定标准。
5. **完成定义 / 输出格式**：必须产出的结构化结果，写到哪、字段是什么。
6. **幂等与去重**：明确“同一事件处理过就跳过，不重复通知”。
7. **失败与边界**：重试次数、超时、禁止操作、失败兜底。

下面是一个精简示例：

```text
你是定时巡检 Agent。任务目标：每小时检查一次 API 服务健康状态。

环境：使用 shell 工具，工作目录 /opt/openclaw，可读取 .env。

输入：
- curl -sf http://127.0.0.1:8080/healthz
- 通知脚本 scripts/notify.sh

步骤：
1. 执行 curl，超时 10 秒。
2. 如果返回码为 0 且响应体 ok=true，记录 status=healthy，结束。
3. 如果返回码非 0 或 ok!=true，检查 /var/lib/openclaw/last_alert_api。
4. 若 30 分钟内已有相同告警，写日志 duplicate 后结束。
5. 否则调用 notify.sh 发送告警，并将当前时间写入 last_alert_api。

完成定义：生成 /var/log/openclaw/healthcheck.json，字段包含 status、checked_at、action。

失败处理：curl 失败重试 2 次，间隔 5 秒；仍失败则写 status=unknown 并通知值班。

禁止：不要重启服务；不要修改 iptables；不要连续发送相同告警。
```

## 踩坑点

- **把 Cron 当“定时聊一次天”**：没有确定性输出，Agent 每次都可能换一种做法。
- **不写幂等**：任务每 5 分钟跑一次，告警容易刷屏。
- **时区语义不清**：Cron 表达式到底按 UTC 还是本地时区，必须写清 TZ。
- **依赖对话记忆**：Cron Session 通常没有历史上下文，信息要放进 instruction 或外部文件。
- **没有 dry-run 开关**：建议支持 `DRY_RUN=1`，只输出将执行的动作，不真正操作。
- **工具权限开太大**：定时任务不需要全部 MCP 工具，最好在运行配置里限制工具集，不要只靠提示词约束。

## 可复用建议

- 把这 7 个字段沉淀成仓库模板，所有 Cron instruction 共用。
- 把“完成定义”写进输出格式，让 Agent 能自我核对。
- 写“禁止做什么”往往比多写“要做什么”更能防止跑偏，尤其是生产环境。
- 每次运行留痕：固定日志路径、输出文件、通知格式，便于回溯。
- 首次运行先在 `DRY_RUN=1` 和缩小时间窗口下测试。
- 把命令固化到脚本或 MCP 工具，而不是让 Agent 每次手写 shell，降低误操作概率。

## 总结

Cron 任务的 instruction，本质是给无状态执行者的一份可重复作业指导书。它不需要很长，但必须覆盖目标、输入、步骤、完成定义、幂等和失败边界。写好这份 instruction，Agent 才能在凌晨三点没有人类在场时，做出确定、可审计、可恢复的决策。
