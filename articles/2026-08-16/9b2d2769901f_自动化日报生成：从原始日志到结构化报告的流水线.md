## 背景

日报不是没有数据，而是数据太散。Git 提交、CI 结果、告警、工单、线上错误日志，分散在不同系统。每天人工打开四五个页面，复制粘贴再整理成 Markdown，耗时半小时到一小时。我们尝试用 Agent/MCP 把这套流程固化成一条流水线，目标不是“自动写日报”炫技，而是把稳定重复的部分自动化，人只做最后的确认和补充。

## 问题

直接让 Agent 读取原始日志并生成日报，会遇到三类问题：

1. **上下文爆炸**：一天原始日志可能几 MB，全塞进上下文成本高且容易丢重点。
2. **结构不稳定**：模型偶尔输出非 JSON，或字段缺失，导致下游渲染失败。
3. **信息噪声**：大量 DEBUG、依赖更新、重复提交，直接进入报告后变成流水账。

因此需要一条“采集—抽取—聚合—渲染”的流水线，而不是一步到位。

## 做法/步骤

### 1. 采集层：统一原始日志

在 OpenClaw 里配置一组 MCP 工具，只读访问 GitLab、CI、监控和工单系统。定时任务按天拉取原始事件，统一写成 JSONL，每条带 `source`、`ts`、`raw`、`repo/project`。例如：

```json
{"source":"gitlab","ts":"2025-01-14T09:12:00+08:00","project":"billing","raw":"fix: correct invoice rounding"}
```

采集层不做理解，只做原始留档。落盘到 `daily/2025-01-14/raw/`。

### 2. 抽取层：分桶后结构化

把一天的原始日志按项目或时间段切成小桶，每个桶控制在 200-400 行左右。对每个桶调用 Agent，要求输出固定 schema：

```json
{
  "date": "2025-01-14",
  "project": "billing",
  "type": "fix|feature|infra|incident",
  "summary": "一句话",
  "impact": "对业务/系统的影响",
  "next": "后续动作或风险"
}
```

这里的关键是给 Agent 明确的 system prompt 和 3-5 个 few-shot 示例。开启 JSON mode 或使用结构化输出能力，减少格式漂移。抽取结果写入 `daily/2025-01-14/structured/`。

### 3. 聚合层：去重与合并

抽取结果会有重复：同一次提交可能出现在多个 CI 步骤中。按 `project + summary` 做归一化，例如计算规范化后的 key，合并相同 key 的事件，保留第一条原始引用。将 incident 类型单独提级，避免被日常提交淹没。

### 4. 渲染层：模板生成日报

用 Markdown 模板渲染：

```markdown
## 昨日概览
- 项目：billing
  - 修复：correct invoice rounding
  - 影响：修复账单舍入误差
  - 后续：待 QA 回归
```

渲染后先输出到 dry-run 文件，不直接发送。人工检查一遍，再通过 IM/邮件插件推送。

## 踩坑点

- **上下文超限**：早期尝试把全天日志一次塞给模型，结果 token 爆掉，且模型只关注前 1/3 内容。必须分桶，且每个桶大小要和模型上下文匹配。
- **JSON 不稳定**：即使要求 JSON，模型偶尔输出 Markdown 代码块包裹，或字段缺失。解决：使用 JSON mode，并在代码里做 schema 校验，失败自动重试一次；仍失败则将该桶标记为人工处理，不强推。
- **时区混乱**：Git 提交时间是 UTC，CI 时间是本地时区，直接混在一起导致日报日期错位。统一在采集层转成项目约定的时区，并保留原始时区字段。
- **敏感信息**：日志里可能出现 token、密码或内部 IP。需要在采集层加脱敏规则，例如正则替换 `token=xxx`、`password=xxx`，而不是等到报告阶段才处理。
- **日报变流水账**：如果对所有提交都生成一条，摘要没有重点。聚合层要设置最小影响阈值，日常 chore、依赖更新可以归入“其他”，不单独展开。

## 可复用建议

1. **采集与推理解耦**：原始日志先落盘，Agent 只读结构化中间层。这样出问题可以回放，不会反复拉取生产系统。
2. **用 MCP 封装只读工具**：不要让 Agent 直接拿数据库连接串或 API 写操作。MCP 工具返回分页、时间范围过滤后的数据，权限最小化。
3. **Schema 先行**：先定义好日报需要哪些字段，再设计 prompt。不要希望模型自由发挥出“好的日报”。
4. **保留原始引用**：结构化结果里带 `raw_id` 或 `source_url`，方便人工回溯，避免总结后的信息失真。
5. **模板版本化**：日报模板和 prompt 放 git，变更可追溯。跑批前支持 dry-run，先看输出再发送。

## 总结

从原始日志到结构化报告的自动化，难点不在“调模型”，而在流水线边界和容错。采集层保证可回放，抽取层保证结构化，聚合层保证重点，渲染层保证可读性。这条流水线稳定后，人工只需要花几分钟确认，而不是每天从零开始翻日志。
