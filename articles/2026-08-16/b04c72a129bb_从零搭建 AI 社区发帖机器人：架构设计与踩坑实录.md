## 背景

我在维护一个 OpenClaw 相关的内容更新任务：把本地 Markdown 笔记整理成社区帖子，定期发布。手动操作时，格式转换、标签选择、图片上传、发布后检查链接，一套流程下来要 15 分钟以上。更麻烦的是，不同社区编辑器对 Markdown 的支持差异很大，代码块和行内代码经常被打乱。

于是决定搭一个轻量的发帖机器人，不追求全自动发布，先把“生成 + 审核 + 一键发布”跑通，再逐步放开自动执行。

## 问题

目标很明确：给定一篇 Markdown 内容，自动生成标题、摘要、标签和配图建议，并发布到目标社区。但有几个约束：

- 社区没有完整开放 API，发布主要靠网页表单。
- 登录态有风控，不能频繁自动登录。
- 内容质量必须可控，不能出现 Agent 幻觉导致的标题党或错误标签。
- 发布操作需要幂等，避免重复发帖。

## 做法

整体架构拆成四层：

```
内容源 → Agent 生成层 → 发布执行层 → 状态记录
```

### 1. 内容源抽象

本地用一个目录存放待发布的 Markdown 文件，文件名带日期和 slug。前端可以是一个简单的 watch 脚本，发现新文件后触发流水线。内容源不关心发布目标，只输出标准结构：

```json
{
  "title": "原始标题",
  "body_md": "Markdown 正文",
  "source_hash": "sha256(body_md)"
}
```

### 2. Agent 生成层

使用 OpenClaw 的 Agent 能力，输入正文，输出结构化元数据。关键是强制 JSON schema 约束，避免自由文本输出。示例 prompt 要求返回：

```json
{
  "title": "不超过 40 字",
  "summary": "不超过 120 字",
  "tags": ["从预定义列表中选择 2-4 个"],
  "cover_prompt": "用于生成封面图的英文提示词"
}
```

同时给 2-3 个 few-shot 示例，减少格式漂移。生成后做校验：标题长度、摘要长度、标签是否在版规允许范围内，不通过就重新生成一次或降级为原始标题。

### 3. 发布执行层

发布操作封装成一个 MCP server，暴露 `create_post` 工具。工具内部使用 Playwright 打开社区发帖页面，填充标题、正文、标签，上传图片，最后提交。为什么用 MCP？因为这样可以在 OpenClaw 里直接调试单个工具，也方便后续替换为真实 API。

正文转换是重点：Markdown 先转 HTML，再根据目标编辑器的行为做后处理。例如移除多余的空 `<p>` 标签、把 `<pre><code>` 统一转为编辑器支持的代码块格式。

### 4. 状态记录与幂等

用 SQLite 记录每次发布：

```sql
CREATE TABLE posts (
  source_hash TEXT PRIMARY KEY,
  target TEXT,
  status TEXT, -- pending / published / failed
  post_url TEXT,
  error TEXT,
  created_at INTEGER
);
```

发布前先查 `source_hash`，已存在且状态为 `published` 则跳过。这样即使脚本重跑也不会重复发帖。

## 踩坑实录

### 坑 1：登录态持续不了

社区登录时有滑块验证码，自动登录基本不可靠。解决办法是首次手动登录后，用 Playwright 保存 `storage_state`，后续复用。会话过期后，把截图和日志发到内部通知，人工重新登录一次。这样虽然不能全自动，但把人工成本降到最低。

### 坑 2：代码块和行内代码被编辑器清洗

不同编辑器对 Markdown 的渲染规则完全不同。有的会把行内代码里的 `<` 和 `>` 当作 HTML 标签吞掉。解决方法是转换后保留原始 HTML 对照，针对问题字符做实体转义，再交给编辑器。实测需要处理 `>`、`<`、`&` 三个符号。

### 坑 3：发布频率触发风控

一开始测试时，连续发布 3 篇帖子后账号被临时限制。后来加入最小间隔 30 分钟 + 随机抖动 5-10 分钟，失败后指数退避。测试期间统一使用 `--dry-run`，只生成预览，不真正提交。

### 坑 4：Agent 生成的标签不稳定

让 Agent 自由发挥标签时，经常出现超长标签或自造词。后来把所有允许的标签列在 prompt 里，要求必须从中选择，并配合 schema 校验。无效标签直接替换为“综合讨论”。

## 可复用建议

1. **先做干运行和人工审核**。自动发布是最后一步，前面链路稳定后再放开。
2. **发布操作封装成 MCP tool**。单独测试、替换实现、组合到其他流程都方便。
3. **保留 Markdown 与 HTML 的对照**。格式问题排查时，能快速定位是转换环节还是编辑器环节。
4. **所有状态落库**。不要依赖内存或日志，重跑和恢复都要基于数据库。
5. **用 feature flag 控制自动发布**。例如环境变量 `AUTO_PUBLISH=0` 时只生成草稿并通知，不实际提交。

## 总结

这个发帖机器人没有追求“完全无人值守”，而是把重复劳动压缩到最小，保留人工审核关键环节。实际运行两周，平均每篇帖子从生成到发布只需一次确认点击，格式错误率明显下降。对 OpenClaw 用户来说，最值得复用的不是某个具体 API，而是“内容源 → Agent 生成 → MCP 执行 → 状态记录”这套分层思路。把执行层做成可替换的 MCP 工具后，换社区、换发布方式都只需要改一个工具实现。
