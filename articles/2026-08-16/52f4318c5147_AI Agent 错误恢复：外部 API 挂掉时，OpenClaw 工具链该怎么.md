## 背景

在 OpenClaw 里接外部 API 是很常见的场景：天气接口、翻译服务、支付回调、向量库查询、甚至 MCP Server 背后的远端模型。很多 Agent 跑不好，不是模型能力不够，而是外部依赖一抖，整个链路就断。

实际生产环境里，外部 API 不可用并不是“异常”，而是常态。5xx、429 限流、超时、DNS 解析失败、TLS 握手失败、上游维护、余额耗尽……任何一环都能让 Agent 卡死或给出错误结论。更麻烦的是，Agent 往往会在失败后反复调用同一个工具，造成重试风暴，把本就脆弱的第三方服务打得更不可用。

## 问题

Agent 的错误恢复和普通后端服务不一样，有几个容易忽略的点：

1. **盲目重试**：遇到超时或 5xx 就无限重试，结果雪上加霜。
2. **错误信息直接进上下文**：把原始堆栈、HTML 错误页、网关返回的一坨东西塞给模型，污染决策。
3. **降级不明确**：接口挂了就返回 `null` 或空对象，Agent 误以为数据真的不存在。
4. **没有熔断**：依赖已经不可用，仍然每个子任务都去请求一次。
5. **工具不可观测**：失败了几次、熔断了没有，完全不知道，只能靠日志猜。

## 做法 / 步骤

下面是一套我在 OpenClaw 插件和 MCP 工具里比较稳定的处理方式。

### 1. 先定义错误分类

不要把所有错误都当成同一种。建议分成四类：

- **不可重试**：401、403、400、404 等，重试没有意义。
- **可重试**：429、500、502、503、504、超时、`ECONNRESET`、`ETIMEDOUT`。
- **上游维护 / 配额耗尽**：这类可以降级，但不应该继续消耗请求。
- **网络不可达**：DNS 失败、连接拒绝，重试收益很低，应快速失败。

### 2. 包一层带超时和退避的调用

给每个外部 API 调用加一个统一 wrapper，而不是在工具里各写各的。核心逻辑可以很简单：

```ts
async function withUpstreamGuard(fn, opts) {
  const breaker = getBreaker(opts.name)

  if (breaker.isOpen()) {
    return {
      ok: false,
      retryable: false,
      reason: 'CIRCUIT_OPEN',
      message: '外部服务熔断中，请暂停调用并告知用户稍后再试',
      degrade: opts.degrade ?? false,
    }
  }

  try {
    const result = await withRetry(fn, {
      retries: opts.retries ?? 2,
      timeout: opts.timeout ?? 8000,
      backoff: 'exponential+jitter',
    })
    breaker.recordSuccess()
    return { ok: true, data: result }
  } catch (err) {
    return handleUpstreamError(err, opts, breaker)
  }
}
```

重试策略上，2～3 次足够，指数退避加随机抖动，避免所有任务同时重试。

### 3. 加熔断与半开状态

熔断是防止依赖被拖死的最后一道防线。简单实现可以用固定阈值：

- 连续失败 5 次，熔断 30 秒；
- 熔断期间所有请求直接短路返回；
- 30 秒后进入半开状态，只放行一个探测请求；
- 探测成功则关闭熔断，失败则继续熔断。

OpenClaw 里如果有多个任务共享同一工具，熔断状态必须是全局的，不能每个子任务各算各的。

### 4. 降级要明确，不能假装成功

如果这个 API 有缓存，可以返回最后成功数据，但必须标注：

```json
{
  "ok": true,
  "degraded": true,
  "source": "cache",
  "staleAt": "2026-04-01T10:00:00Z",
  "message": "实时数据不可用，当前为缓存数据，可能不是最新"
}
```

如果没缓存，可以返回明确的不可用信息，让 Agent 换一条路径，比如告知用户稍后重试、使用备用通道、或者跳过这一步。

### 5. 给模型返回结构化错误

这是 Agent 场景里最容易做错的地方。不要返回：

```
Error: connect ECONNREFUSED 172.18.0.3:5432
    at TCPConnectWrap.afterConnect ...
```

而应该返回模型能理解、能继续规划的结构化信息：

```json
{
  "ok": false,
  "retryable": false,
  "reason": "UPSTREAM_5XX",
  "message": "支付接口暂时不可用。建议：告知用户稍后重试，或检查是否有备用支付通道。",
  "nextAction": "DO_NOT_RETRY_IMMEDIATELY"
}
```

模型收到这种信息后，会倾向于停止重复调用，而不是继续硬试。

### 6. 加一层可观测

每次外部调用至少要记录：

- 依赖名称
- 耗时
- 是否重试 / 重试次数
- 错误类型
- 是否降级
- 熔断状态

这些信息不仅方便排障，也能帮助判断一个依赖是不是已经不适合继续挂在关键链路里。

## 踩坑点

**重试放大，造成重复副作用。**  
如果支付接口已经扣款但响应超时，盲目重试可能造成重复扣款。对非幂等接口，重试要非常克制，或者要求上游支持幂等键。

**熔断后模型仍然反复调用同一个工具。**  
熔断快速失败是好，但如果不把熔断状态反馈给模型，Agent 可能在同一轮里调用十几次，每次都是秒回 `CIRCUIT_OPEN`。这依然浪费上下文。

**缓存兜底带来脏数据。**  
库存、价格、余额这类数据，如果返回旧的缓存，下游可能做出错误决策。降级必须带 `degraded: true` 和时间戳，让 Agent 知道数据新鲜度下降。

**超时设太长，任务卡死。**  
外部 API 如果 hang 住，8 秒超时和 30 秒超时差别很大。Agent 任务有时间预算，单个工具等待过久会让整个规划失败。

**MCP Server 进程崩溃但客户端无感知。**  
如果 MCP Server 本身挂了，OpenClaw 侧要检测进程退出并自动拉起，而不是一直等待响应。可以在 MCP 客户端外层加健康检查和重启逻辑。

## 可复用建议

- 为每个外部依赖准备一个 `withUpstreamGuard`，统一超时、重试、熔断、降级参数。
- 配置集中管理：`retries`、`timeout`、`breakerThreshold`、`cooldown` 不要散落在工具代码里。
- 给模型一个“依赖状态摘要”工具或变量，让 Agent 在做规划前可以查看哪些外部服务当前不可用。
- 定期做故障演练：手动 kill 一个 API 或 MCP Server，观察 Agent 是否能在不崩溃的情况下结束任务。
- 对关键外部依赖设置告警，但避免每个 5xx 都发消息，按“熔断打开”作为告警触发条件更合理。

## 总结

Agent 错误恢复的核心不是“把所有失败都救回来”，而是：

**快速失败、有限重试、降级明确、反馈结构化。**

外部 API 挂了不可怕，可怕的是 Agent 不知道它挂了，或者知道但不知道下一步怎么办。把错误处理做成 Agent 可感知、可决策的一部分，比多写几层 try/catch 更有效。
