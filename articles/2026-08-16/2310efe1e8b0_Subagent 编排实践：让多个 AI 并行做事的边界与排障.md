## 背景

单个 Agent 在复杂自动化里很容易变成串行瓶颈。比如一个任务既要抓多个数据源、又要写文件、还要调用插件做格式转换，如果让一个 Agent 顺序处理，上下文会迅速膨胀，前面步骤的中间结果会污染后面判断，工具调用之间互相等待。

后来我把主控和 worker 拆开，用 subagent 并行处理。稳定性提升不是来自“更多 AI 同时干活”，而是来自上下文隔离和结构化回收。

## 问题

不是所有任务都适合并行。真正适合的是可拆分、低依赖、可独立验证的批量任务：批量代码审查、多源信息采集、多插件独立执行、多个文件生成。强依赖链路的任务并行，反而会增加回滚和协调成本。

真正要解决的是三件事：

1. **上下文隔离**：每个 subagent 不共享主控上下文，避免中间结果互相污染。
2. **结果回收**：主控只拿需要的信息，不把全文拉进主控上下文。
3. **失败隔离**：一个 worker 失败不应拖垮整个任务。

## 做法/步骤

### 1. 定义主控与 worker 边界

主控只做三件事：拆解任务、派发、合并结果。它不直接做具体执行，避免主控上下文被细节占满。worker 只做单一任务，返回结构化结果。

### 2. 给每个 subagent 写清 task_spec

我通常用固定模板：目标、输入、关键约束、输出格式、超时、失败策略。例如：

```json
{
  "goal": "抓取指定 URL 的正文并提取核心观点",
  "input": {"url": "https://example.com/report"},
  "constraints": ["不要点击站外链接", "只使用文本内容"],
  "output": {
    "status": "ok|failed",
    "summary": "核心观点摘要",
    "artifacts": ["output/report.txt"]
  },
  "timeout": 60
}
```

### 3. 在 OpenClaw 中派发

在 OpenClaw 里，我习惯把每个 subagent 配置为独立 agent/session，主控通过 MCP 工具或队列文件派发 task_spec。如果插件接口不直接支持并发，我会用后台任务队列：主控写入 task 文件，多个 worker agent 轮询领取。这种方式对插件和 MCP 更友好，也方便观察每个 worker 的状态。

### 4. 合并结果

主控等待结果后，只读摘要和产物路径，不把全文拉进主控上下文。关键结果需要复核时，再按路径打开原始文件。

## 踩坑点

- **颗粒度过细**：每个 subagent 只做一分钟小事，但主控要花大量 token 读返回、协调。一般 2-5 个子任务比较合适，超过 8 个先考虑批量脚本而不是 subagent。
- **全局约束丢失**：worker 上下文隔离后，它不知道主控已经做过的判断。关键约束必须写进 task_spec，不要假设它“应该知道”。
- **资源冲突**：多个 subagent 并行写同一文件、同一数据库行、同一浏览器 profile，会互相覆盖。给每个 worker 分配独立输出目录或命名空间。
- **超时僵尸**：subagent 可能卡在网络或插件调用上。必须设置 timeout，主控要有取消/忽略策略，否则并行反而拖垮整体。
- **token 消耗放大**：并行 subagent 的上下文消耗是加法，不是魔法。如果任务很简单，单 agent 串行更便宜。并行前先估算收益。

## 可复用建议

- 模板化 task_spec，避免每次临时拼提示词。
- 主控只读摘要，关键验证再看原文。
- 为每个任务生成 task_id，落状态文件，便于排障和重试。
- 失败节点独立重试，不影响其他 worker。
- 逐步扩大并行度：先 2 个 worker，跑通结果合并和失败处理，再上量。

## 总结

subagent 编排的核心不是“让更多 AI 同时干活”，而是把主控从执行细节里解放出来，用隔离上下文和结构化回收降低复杂度。并行可以提升吞吐，但会放大调度、超时、冲突问题。它适合批量、低依赖、可验证的任务，不适合强依赖链路。工程上先把 task_spec、超时、状态文件和结果合并做扎实，再谈扩展 worker 数。
