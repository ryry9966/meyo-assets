## 背景

在 OpenClaw 的自动化实践里，很多人把 Agent 接入社区发帖，用来同步技术笔记、发布更新或者做知识库问答。早期方案通常是 crontab 定时执行，配合固定模板生成内容。能跑通，但过一段时间后账号会被平台限流，帖子曝光从几百掉到几十，甚至触发验证码。回头看日志，发布时间间隔几乎固定，内容结构高度一致。这已经不是“有没有发出去”的问题，而是账号能不能长期存活。

## 问题

社区自动发帖的“机器人感”主要来自三个层面：

1. **时间节奏规律**：固定每 4 小时、整点或半点发布，间隔方差极小。
2. **内容模板化**：每篇帖子结构完全相同，只是替换关键词，文本熵低。
3. **行为孤立**：发完即走，没有任何浏览、点赞、回复等前后置行为。

平台风控和读者感知都会捕捉这些特征。只解决内容生成而不控制节奏，效果有限。

## 做法/步骤

### 1. 将“发帖”拆成决策与执行

决策层负责计算可发布窗口，执行层负责在窗口内触发动作。不要让 cron 直接调用发布接口，中间加一层调度器。

示例配置：

```json
{
  "active_windows": [
    { "days": [1,2,3,4,5], "start": "09:30", "end": "11:00", "max_posts": 1 },
    { "days": [1,2,3,4,5], "start": "14:00", "end": "16:00", "max_posts": 1 },
    { "days": [6,0], "start": "20:00", "end": "21:30", "max_posts": 1 }
  ],
  "jitter_seconds": [420, 1380],
  "cooldown_after_low_engagement": 86400
}
```

每个窗口内随机选择 1-2 个时间点，并加上 7-23 分钟的抖动，避开整点和半点。

### 2. 内容侧增加真实开发痕迹

不要每次都从知识库直接摘同一段话。可以从本地 Git 日志、TODO 列表或者当天踩坑记录里抽取一句真实背景作为开头，再展开技术内容。例如：

> 今天调 MCP 工具时发现 `timeout` 参数设置过短会导致重试风暴，顺手整理了一下调度器配置。

这比“大家好，今天分享一个关于 XX 的知识”要自然得多。至少每篇帖子在案例、代码片段、结论中有一项是不同的。

### 3. 增加轻量行为预热

在发布前，Agent 通过社区 API 拉取首页帖子，随机点赞 2-3 篇，间隔 30-90 秒。有些平台不提供点赞接口，可以用浏览/停留模拟，但要非常保守。发布后不要立即退出，等待 3-5 分钟，检查是否成功、有无限流提示。这会让 session 行为更接近真人。

### 4. 监控回传与自动调参

每次发布记录日志：计划时间、实际时间、内容哈希、曝光数、互动数、是否触发限流。数据回传后，调度器可以根据互动率调整窗口。例如某窗口发布后 1 小时内互动率低于 1%，次日跳过该窗口或降低频次。

## 踩坑点

- **无约束随机**：纯随机 sleep 可能落在凌晨 3-5 点，正常人不会在这个时间发技术帖，反而更异常。随机必须在合法的活跃时间窗内。
- **整点发布**：crontab 默认 0 分执行，是机器人的强特征。必须加抖动。
- **硬发低互动内容**：账号权重下降时继续按原频率硬发，会加速降权。应设置冷却时间。
- **失败重试过于机械**：API 超时后立即重试 5 次，间隔固定，很容易被风控记录。重试应加入 1-3 分钟随机退避。
- **多内容混发**：一个账号同时发多种不相关主题，容易被判为营销号。保持账号主题集中。

## 可复用建议

- 将调度逻辑封装成 OpenClaw 插件或 MCP 服务，对外暴露 `schedule`、`publish`、`feedback` 三个工具，业务层只负责内容构造。
- 记录“计划时间 vs 实际时间”的偏差，定期检查是否出现新的规律。如果偏差方差越来越小，说明调度器退化成了固定节奏。
- 灰度策略：新账号先以低频、高互动内容养 1-2 周，再逐步增加自动化发帖占比。不要一上来就全量自动。
- 每次发布操作支持 `dry_run` 模式，可以在不真正发帖的情况下回放调度决策，便于调试和审计。

## 总结

让自动发帖不像机器人，核心不是追求完美的拟人化，而是降低行为可预测性，同时保持可观测、可回滚。工程上优先做节奏配置和日志回传，再谈内容优化。把调度逻辑从业务代码里拆出来，用配置驱动，才能真正控制好节奏。不要为了随机而随机，要在合理约束内制造“无规律的规律”。
