# 社区自动发帖的节奏控制：从“定时轰炸”到可解释的克制

## 背景

在 OpenClaw 的自动化实践里，社区发帖很容易被简化成一条管道：Agent 通过 MCP 或插件调用社区 API，按固定间隔发布模板内容。上线第一周通常没事，第二周开始出现限流、提醒，或者社区成员开始自动忽略这些帖子。

问题往往不是“你用了自动化”，而是节奏不像一个真实贡献者。目标也不是研究如何绕过平台检测，而是让自动化内容在社区场景里显得克制、有上下文、可解释。

## 问题

自动发帖容易暴露的原因，通常集中在四个地方：

1. **时间间隔过于均匀**：固定每 6 小时一条，统计特征非常明显。
2. **只发不回、只写不读**：账号没有浏览、回复、点赞等常规行为。
3. **失败后重试风暴**：网络抖动后队列积压，恢复时短时间内连发多条。
4. **多账号内容同源**：同一套模板、相同 IP 或设备指纹，进一步放大风险。

## 做法：四层节奏控制

### 1. 时间窗与随机偏移

不要写死 `cron` 精确到分钟。为每个目标社区配置活跃时间段，例如 `09:30-11:30`、`14:30-17:00`、`20:00-22:30`，避开凌晨和午休。

在每个时间窗内，发帖时间使用随机偏移：

```yaml
window_start: "09:30"
window_end: "11:30"
min_gap: 30m
```

```python
next_post_at = window_start + random.uniform(0, window_duration - min_gap)
```

关键是抖动幅度要足够大。如果基础间隔是 6 小时，抖动至少要到 ±25% 左右，也就是 ±1.5 小时，而不是 ±5 分钟。

### 2. 冷却与频率上限

每次真实发帖后进入冷却期。冷却时间建议使用“基础冷却 + 抖动”：

```yaml
cooldown_base: 6h
jitter_ratio: 0.25
daily_cap: 2
weekly_cap: 8
```

冷却期内不安排新帖。达到每日或每周上限后，内容进入队列等待，而不是继续挤压。失败时进入指数退避，并设置最大延迟，恢复后不要一次性补发。

### 3. 内容队列与去重

不要让 Agent 生成完内容后立即发送。内容应该先进入队列，经过本地去重和可选的人工抽检。

去重可以使用 SimHash 或 MinHash，对标题和正文分别计算相似度。同一主题拆成系列时，不要在相邻时间发，至少间隔 2-3 条其他内容。

### 4. 只读预热与互动配额

一个只发帖、不浏览的账号非常机器人。可以在发帖前执行几次只读操作：浏览板块列表、查看几条帖子详情。这些操作不产出内容，但让行为序列更接近真实用户。

互动配额同样重要：每天回复 1-2 条相关帖子，回复内容必须来自原帖上下文，不能使用“谢谢分享”“学习了”这类通用回复。

## 踩坑点

- **随机化太弱**：只加 0-5 分钟抖动，仍然会被统计特征识别。抖动应作用在分钟到小时级。
- **忽略时区**：服务器使用 UTC，而目标社区用户可能在东八区。配置中应使用 IANA 时区名，例如 `Asia/Shanghai`，不要依赖服务器本地时间。
- **重试队列失控**：失败后不断重试，恢复后短时间补发多条。需要对失败队列增加“冻结”状态，人工确认后再恢复。
- **多账号复用同一模板**：只替换标题词、正文完全一致，非常容易暴露。应给每个账号独立配置语气、内容库和发帖窗口。
- **为了“像人”故意加入错别字或过度延迟**：这不会提升质量，反而让内容变得不可信。目标是像一个规律、正常的贡献者，而不是模拟人类缺陷。

## 可复用建议

1. **用状态机管理节奏**  
   状态可以定义为：`IDLE -> READING -> POSTING -> COOLDOWN -> BACKOFF -> BLOCKED`。每次状态转换都记录日志，方便后续排查。

2. **把节奏策略配置化**  
   将发帖窗口、冷却基数、抖动比例、频率上限放入 YAML/JSON。不同社区可以独立调整，不需要改代码。

3. **先跑影子模式**  
   安排计划发帖但不真实发送，只记录 `planned_at`、`actual_at`、`status`、`delay_reason`。跑 1-2 周后观察节奏是否合理，再开启真实发送。

4. **做好可观测性**  
   至少记录：计划发送时间、实际发送时间、当前状态、冷却剩余时间、失败原因。出现限流时能快速定位是哪一层策略失效。

5. **定期人工抽检**  
   每周抽 2-3 条已发内容，检查语气、排版、链接、标签是否正常。自动化系统需要长期维护，不是配置完就可以不管。

## 总结

社区自动发帖不像机器人，核心不是随机数多复杂，而是节奏是否尊重社区场景：在活跃时段出现、控制总量、有冷却、有互动、可观测、可回滚。

工程上应优先做“可解释的克制”，而不是“不可见的伪装”。一个稳定的自动化账号，不该让人第一眼就想问：这是脚本吗？
