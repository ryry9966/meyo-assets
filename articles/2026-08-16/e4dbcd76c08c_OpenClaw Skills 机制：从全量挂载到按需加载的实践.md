# OpenClaw Skills 机制：如何让 AI 助手按需加载能力

## 背景：为什么需要“按需加载”

在 OpenClaw 这类 Agent 框架里，AI 助手能调用的工具、脚本、外部 API、领域知识越来越多。最早的做法是把所有能力全部挂载进系统提示词或工具列表。这在只有三五个插件时没问题，但一旦 skill 数量超过十几个，问题就变得明显。

全量加载的代价主要有三方面：

1. **上下文预算被挤占**：每个 skill 的说明、参数、示例都会消耗 token，实际任务还没开始，上下文已经所剩不多。
2. **工具选择退化**：当模型同时看到太多相近能力时，容易选错工具，或者在多个候选项之间反复横跳。
3. **启动与响应变慢**：初始化阶段要注入大量定义，后续每次推理都要带着这些内容。

OpenClaw 的 Skills 机制要解决的核心问题是：**不要把整个世界都塞给模型，而是在它需要某类能力时，再把对应能力加载进来。**

## 问题：按需加载的难点

“按需”说起来简单，工程上却容易翻车：

- 模型如何知道现在需要哪个 skill？
- 加载晚了，任务已经失败；加载早了，又变成变相全量。
- 加载进来的 skill 如果权限不清晰，执行到一半会被安全策略打断。
- 多个 skill 之间可能存在命名冲突或依赖缺失。

所以按需加载不是一个简单的 feature，而是一套“描述—检索—注入—执行—回收”的流程。

## 做法与步骤

### 1. 用 manifest 描述 skill，而不是只写提示词

每个 skill 建议独立成目录，例如：

```text
skills/
  weather/
    SKILL.md
    scripts/
      query_weather.py
```

在 `SKILL.md` 的 frontmatter 里写清楚触发条件、参数和权限：

```yaml
---
name: weather
description: 用户询问当前天气、未来天气、穿衣建议、出行预报时使用
entrypoint: scripts/query_weather.py
parameters:
  - city
  - date
permissions:
  - network:api.weather.com
timeout: 15s
---
```

这里的 `description` 不是给最终用户看的介绍，而是给检索阶段和模型选择阶段看的“触发信号”。

### 2. 先检索候选，再注入完整内容

不要让模型直接从一个巨大的 skill 列表里挑。推荐流程是：

- 主代理收到用户输入后，先根据 `description`、`when_to_use` 等字段做轻量召回，取 top-k 候选。
- 只把这些候选的**名称 + 一句话描述**放进系统提示词，让模型做最终选择。
- 模型选定后，再加载完整的 `SKILL.md` 内容、脚本说明和必要上下文。
- 执行完成后，将 skill 标记为 inactive，必要时缓存结果，但不要把完整内容常驻在后续对话里。

这样做的好处是：在决策阶段，模型只看到很小的候选集；在真正执行时，才拿到完整的能力定义。

### 3. 权限声明放在加载阶段，而不是执行阶段

如果一个 skill 需要网络、文件写入、shell 权限，最好在 manifest 里写明。OpenClaw 在加载 skill 时可以提前校验权限，而不是等脚本执行到一半才报“缺少权限”。对于自动化场景，可以给低风险 skill 配置预授权；高风险 skill 仍然保留人工确认。

### 4. 为高频 skill 设置常驻，低频 skill 走冷加载

不是所有 skill 都适合按需加载。比如「时间查询」「当前用户信息」这种高频、低占用的能力，可以直接常驻。而「生成 PDF 报告」「数据库迁移」这类低频、高占用的能力，适合按需加载。

## 踩坑点

### 1. description 写得太宽或太窄

太宽的 description 会导致大量无关 skill 被召回，触发混乱；太窄则可能导致该加载时没加载。建议写法是“用户会怎么问”，例如：

- 好的：`当用户询问某个城市今天或未来几天的天气、气温、降雨概率时使用`
- 差的：`天气能力`

### 2. 加载了 skill，但依赖没声明

有时 skill 脚本依赖某个 Python 包、环境变量或外部服务。如果在 manifest 里没有声明，加载后执行会失败。建议在 manifest 里增加 `dependencies` 字段，并在加载阶段做快速校验。

### 3. 动态注入的指令反而污染上下文

如果每次加载 skill 都把很长的示例、边缘情况、版本历史全塞进去，上下文会迅速膨胀。按需加载的内容应该保持精简：只放当前任务需要的接口说明、参数约束和最少示例。

### 4. 权限审批打断自动化流程

在无人值守的自动化任务里，突然弹出一个权限确认框，任务就会卡住。建议根据 skill 的风险等级做分级策略：低风险静默授权，中风险记录日志，高风险才中断请求。

## 可复用建议

- **一个 skill 只做一件事**：职责单一的 skill 更容易描述、测试和回收。
- **先做触发测试，再做功能测试**：准备一组用户输入样例，检查是否召回正确 skill，以及是否误触发无关 skill。
- **给 skill 加版本和超时**：manifest 里声明 `version` 和 `timeout`，避免行为变化不可追踪。
- **记录加载日志**：至少记录每次 skill 的加载时间、是否命中、执行结果。没有日志，按需加载的效果很难评估。
- **限制单次加载数量**：一次对话最多同时加载 2-3 个 skill，避免多个 skill 指令互相干扰。

## 总结

OpenClaw Skills 机制的核心价值不是“有更多技能”，而是**在正确的时间只暴露必要的能力**。按需加载如果做得好，可以显著降低上下文占用、减少工具选择错误，并让自动化流程更稳定。

对于工程实践者来说，最值得投入精力的地方不是写更多 skill，而是把每个 skill 的触发描述、权限边界和生命周期管理清楚。毕竟，能力不是越多越好，能按需出现的能力才是真正可用的能力。
