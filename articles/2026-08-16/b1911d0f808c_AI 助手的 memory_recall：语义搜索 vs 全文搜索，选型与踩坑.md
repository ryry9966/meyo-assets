# AI 助手的 memory_recall：语义搜索 vs 全文搜索，选型与踩坑

## 背景

最近在优化 OpenClaw 的 memory_recall 模块。原实现只有全文搜索（基于 SQLite FTS5），不少用户反馈记忆召回不准，尤其是自然语言提问，比如“上次说的那个不用联网的方案是什么”。这类问题靠关键词匹配基本抓瞎。

于是我们把语义搜索（embedding + 向量检索）加了进去。结果准确率确实有提升，但成本上来了，精确匹配反而变差——查“端口号 8080”会把所有含“端口”的记忆都捞出来。折腾几轮后，才搞清楚两者不是替代关系，而是分层互补。

这篇文章记录我们最终的选型思路、实验过程和踩过的坑，适合正在给 Agent 做记忆召回的同学参考。

## 问题定性

memory_recall 本质是从历史记忆中找最相关条目，喂给模型作为上下文。关键指标是：召回的相关记忆是否足够，以及无关记忆是否被过滤掉。

- **全文搜索**：擅长精确匹配，比如人名、参数、日期、特定短语。对口语化、同义词、改写句基本无效。
- **语义搜索**：擅长模糊语义，比如“不用联网的方案”能召回“离线模式”。但对数字、专有名词、日期不敏感，容易混。

所以问题不是“哪个好”，而是“什么场景用哪个，怎么合起来”。

## 做法与步骤

### 1. 记忆数据分类

我们把记忆分成三类：

- **结构化事实**：用户偏好、设置、姓名、端口号、版本号。这类信息适合全文搜索，最好直接存成字段，用 SQL 过滤。
- **对话片段**：讨论过的方案、用户说过的想法。适合语义搜索。
- **任务日志**：执行过的命令、结果状态、时间戳。全文 + 时间过滤为主。

### 2. 索引方案

- **全文索引**：继续用 SQLite FTS5，但对中文做了 trigram 支持（`tokenize=trigram`），英文保留默认分词器。如果数据量大，可换 Meilisearch 或 Elasticsearch。
- **语义索引**：用 Qdrant 存向量，嵌入模型选 `bge-small-zh-v1.5`（本地，512 维，中文效果好）。对话片段按 200~500 token 切块，太长会稀释语义。

### 3. 混合检索

先分别召回 top_k（比如各 20 条），然后做 **RRF 融合**：

```
score = sum(1/(k + rank_i))
```

`k` 取 60。最后按 score 排序，再过一个阈值。

### 4. 阈值与空召回

语义相似度低于 0.7 或全文得分过低时，直接返回空。避免把无关记忆硬塞给模型，反而污染上下文。

## 踩坑点

1. **语义搜索对数字/日期不敏感**：查“2024-03 的会议”会召回“2025-03 的会议”。解决办法：把日期、数字抽成结构化字段，用过滤条件，不参与语义匹配。

2. **中文语义搜索用英文模型会翻车**：一开始用 `text-embedding-3-small`，中文效果明显不如本地 `bge-small-zh`。如果是纯中文场景，建议优先本地中文嵌入模型。

3. **SQLite FTS5 默认分词对中文不友好**：必须用 trigram 或外部分词器（如 simple 分词 + 词表）。否则“不用联网”查不到“离线方案”。

4. **RRF 的 k 值玄学**：k 越小，排名靠前的结果权重越大，容易偏向单一来源；k 越大越平均，但噪声增加。我们测试下来，60 是个稳妥起点。

5. **向量库选型**：Chroma 在小规模（<1 万条）够用，但增量更新需要重建索引或者接受陈旧。Qdrant 支持实时更新，但运维复杂。如果你只有几百条记忆，直接全量塞给模型也可以，不需要搜索。

6. **长记忆要切块**：一条 2000 token 的对话片段做 embedding，语义会被稀释。切块后按块召回，再还原上下文。

## 可复用建议

- **先用全文搜索覆盖明确查询，再上语义搜索处理模糊口语**。不要一上来就全量语义。
- **建立评估集**：从真实用户查询中采样 50~100 条，标注相关记忆作为 golden set。每次调参、换模型都跑一遍，看 Hit Rate@k 和 MRR，不要只看单例。
- **记忆写入侧加时间衰减或重要性评分**，召回时作为排序特征，降低旧记忆干扰。
- **如果不想维护两套索引**，可以先用 SQLite FTS5 + trigram + 同义词扩展，在小规模下能凑合。但当用户开始用自然语言追问历史时，语义搜索就是刚需。

## 总结

语义搜索不是银弹，全文搜索也不是过时货。memory_recall 的正确姿势是：**结构化事实走全文 + 字段过滤，对话片段走语义，最后 RRF 融合 + 阈值过滤**。工程重点在数据切分、评估集和阈值控制。

先跑通简单方案，再逐步替换，比一开始就上复杂向量栈更务实。
