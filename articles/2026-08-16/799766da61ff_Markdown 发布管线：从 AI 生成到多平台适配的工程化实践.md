## 背景

用 OpenClaw 的 Agent 生成内容已经很顺，但生成完只是第一步。真正麻烦的是把同一份 Markdown 发布到公众号、知乎、掘金、Notion、WordPress 等多个平台时，格式总会出现各种偏差：代码块丢失语言标注、表格不渲染、外链被转成纯文本、本地图片无法显示、frontmatter 被当成正文输出。

原因很简单：Markdown 只是“接近”纯文本的书写格式，但每个平台对 Markdown 的解析能力、HTML 白名单、图片资源策略都不一样。AI 生成的 Markdown 往往还带有自己的习惯，比如行内 HTML、emoji、特殊引号、不规范的代码围栏，这些都会放大兼容性问题。

如果只是偶尔手动发布，手动修一下还能忍。但一旦接入 Agent 自动化流程，格式问题就会变成持续返工。我们需要一条可复用的 Markdown 管线，把“AI 生成”到“多平台发布”之间的格式适配做成确定性的工程步骤，而不是每次靠人肉排查。

## 问题拆解

从工程视角看，Markdown 多平台发布主要面临四类问题：

1. **结构解析不稳定**：正则处理嵌套列表、引用块内嵌代码、表格内嵌格式时容易出错。
2. **平台能力差异**：微信公众号不渲染 Markdown，知乎对表格和脚注支持有限，Notion 有自己的 block 结构，WordPress 需要 HTML。
3. **资源引用失效**：本地图片、相对链接、临时图床链接在发布后无法访问。
4. **元数据处理不一致**：frontmatter、标签、摘要、封面图没有统一约定，平台之间字段映射混乱。

## 做法与步骤

在实践中，我倾向于把管线拆成五步：标准化 → AST 转换 → 平台适配 → 资源处理 → 校验发布。

**第一步：标准化输入**

在 Agent 输出后，先不要直接发布。统一做一次 Markdown 规范处理：

- 将 frontmatter 和正文分离，frontmatter 只保留 title、summary、tags、cover、date 等约定字段。
- 使用 `markdownlint` 做基础规则检查，如 MD040 代码块语言缺失、MD031 围栏前后空行等。
- 统一换行符为 `\n`，清理 Word 风格弯引号、连续空行、行尾空格。

这一步可以用 OpenClaw 插件调用现成的 lint 工具，或者直接让 Agent 按固定模板输出，减少后续清洗成本。

**第二步：基于 AST 转换，而不是正则**

正则处理 Markdown 只适合简单替换，遇到嵌套结构就容易漏。更稳妥的做法是用 `unified` + `remark-parse` 把 Markdown 解析成 AST，再针对目标平台做 AST 转换。

例如，针对微信公众号，需要把代码块从 Markdown 围栏转成带内联样式的 `<pre><code>`，并保留语言标注作为第一行注释；针对知乎，需要把脚注转成文末引用列表；针对 Notion，则需要把 Markdown 标题、列表、代码块映射成 Notion API 的 block 结构。

AST 转换的好处是：每种平台写一个 transformer 插件，互不影响，后续新增平台也只是加一个转换规则文件。在 OpenClaw 里，这部分可以封装成 MCP 工具，Agent 把标准化后的 Markdown 传入，工具返回目标平台格式。

**第三步：平台 Profile 化**

不要让 Agent 在 prompt 里记住所有平台规则，那样既占 token 又容易漏。更工程化的做法是维护一个 `platforms/` 目录，每个平台一个 JSON profile，描述该平台的能力边界和转换偏好：

```json
{
  "name": "wechat",
  "markdown": false,
  "html_whitelist": ["section", "pre", "code", "p", "strong", "em", "ul", "ol", "li", "blockquote", "h2", "h3"],
  "code_block_style": "inline_css",
  "image_required": "cdn_url",
  "table_support": false,
  "line_break": "two_spaces"
}
```

转换器根据 profile 决定是否需要降级、是否把表格转成列表、是否把外链转成脚注。这样新增平台时，不需要改动核心转换逻辑。

**第四步：资源处理前置**

AI 生成的 Markdown 经常包含本地图片路径或临时链接。发布前需要统一做资源上传：

- 本地图片上传到图床或对象存储，替换为 CDN URL。
- 为图片生成定宽 URL 参数或 `width` 属性，避免移动端溢出。
- 外链统一检查可达性，失效链接降级为纯文本或加备注。
- 封面图单独提取，按平台尺寸要求裁切。

这部分可以做成独立脚本或 MCP 工具，在转换前执行。

**第五步：校验后再发布**

发布前至少做三轮校验：

- 结构校验：用 `remark` 重新 parse 一次，确认无未闭合围栏、无非法嵌套。
- 平台校验：模拟目标平台渲染逻辑，检查是否有被过滤的 HTML、是否超出长度限制、是否有屏蔽敏感词。
- 链接与图片校验：批量请求所有外链和图片 URL，记录 404 或防盗链。

校验通过后再通过平台 API 或 MCP 工具发布。原始 Markdown 作为 source of truth 存入仓库，发布后的平台版本只做存档，不反向修改原始文件。

## 踩坑点

实际跑起来有几个容易忽略的坑：

**第一，公众号代码块不是简单加 `<pre>`。** 微信会过滤部分内联样式，直接贴 HTML 代码块经常出现换行丢失、字体错位。稳妥做法是把代码块转成普通文本块，用等宽字体和灰底样式，语言标注以注释形式放在首行。

**第二，表格经常是最容易翻车的地方。** 公众号、知乎对 Markdown 表格支持都不好，Notion 的表格 API 又比较繁琐。建议默认策略：表格在发布前转成列表或分点描述，只有确认目标平台支持时才保留表格。

**第三，frontmatter 不要直接进正文。** 很多平台会把 YAML 头当普通文本渲染出来，尤其是一些 CMS 系统。必须在标准化阶段就剥离，不要依赖平台解析。

**第四，链接和图片的防盗链。** 即使图片上传成功，有些平台会重写图片链接或添加防盗链，导致发布后图片仍然不可见。建议使用支持白名单的图床，并在发布后做一次成品截图抽查。

**第五，换行符不一致。** 有些平台把单个 `\n` 当空格，有些当换行。统一使用两个空格加换行来明确软换行，段落之间保持空行，不要依赖平台默认行为。

## 可复用建议

如果要长期跑这条管线，建议做三件事：

**一是保留原始 Markdown 与转换后的中间产物。** 原始文件是唯一事实来源，平台版本只是输出物。这样以后调整转换规则，可以重新生成，不用手动修复已发布内容。

**二是建立一个固定测试样本集。** 包含代码块、表格、嵌套列表、引用、图片、脚注、外链、emoji、frontmatter 等典型元素。每次改转换器或新增平台，先用样本集跑一遍，对比渲染结果。

**三是把管线做成可观测。** 每次发布记录平台、转换耗时、资源上传结果、校验失败项。Agent 可以根据失败反馈调整输出策略，比如“知乎表格不支持，下次生成时用列表代替”。

## 总结

Markdown 多平台发布的格式适配，本质不是“找一个全兼容格式”，而是建立一条确定性的转换管线：统一输入、AST 处理、平台 profile、资源前置、校验发布。OpenClaw 的 Agent 负责生成和调度，MCP 工具负责转换和校验，人只做规则维护和异常兜底。这样，AI 生成的内容才真正进入可自动分发的工作流，而不是每次发布都重新调试格式。
