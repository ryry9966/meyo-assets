# AI 助手的 memory_recall：语义搜索与全文搜索，不是二选一

在 OpenClaw 这类 Agent 里，`memory_recall` 的定位很明确：把长期记忆里最相关的那几条捞出来，塞进当前上下文，让模型不要凭空回答。捞得准，助手就像记得你；捞得偏，它就开始编。

很多人的第一反应是“上 embedding 做语义搜索”。但实际跑一段时间会发现，语义搜索在处理命令、错误码、路径、日期、版本号、人名这类精确信息时，经常翻车。全文搜索虽然“笨”，却能稳定命中这些硬 token。本文不讨论谁取代谁，只讲我在 OpenClaw/Agent 记忆检索里用下来的混合做法。

## 问题：两类查询根本不是一个物种

`memory_recall` 面对的查询大致分两类：

- **概念型**：例如“上次那个数据库连接问题怎么解决的？”  
  - 期望召回：“数据库连不上，后来把连接池调大了。”  
  - 这类靠语义相似度有效，因为措辞可能完全不同。

- **精确型**：例如“redis 连接报 `ECONNREFUSED 127.0.0.1:6379` 那次怎么处理？”  
  - 关键词就是错误码、IP、端口、命令。  
  - 纯向量搜索很容易漏召回，尤其是长尾错误码、短词、带特殊符号的字符串。

更麻烦的是否定语义：记忆里写的是“不要重启容器，先看日志”，语义搜索可能把“不要重启”和“重启”当成相似表达，召回出来给模型一看，反而容易让它执行反操作。对 Agent 来说，这是很实际的危险。

## 做法：先全文，后语义，再融合

我的工程路线很朴素：**FTS 基线 → 语义补充 → 混合融合 → 必要时重排**。

### 1. 用 SQLite FTS5 打底

OpenClaw 很多部署是单机 SQLite，建一张 `memory_fts` 表，把记忆内容和结构化字段一起写入。FTS5 支持 BM25 排序，速度够快，几千到几万条完全没压力。

中文环境有一个大坑：默认 tokenizer 不分中文词。也就是说 “数据库连接池” 会被切成单字或者奇怪的 token，查询效果很差。两个解法：

- 使用 `tokenize='trigram'`，适合中文子串匹配。缺点是短查询如“Redis”可能不如英文 tokenizer 精准。
- 写入前用 jieba 等分词后，以空格拼接再交给 FTS5。这样“数据库连接池”真正成为可检索 token。

我常用后者，配合一条前缀 `LIKE` 查询兜底，避免输入 “redis” 时漏掉 “Redis 集群”。

### 2. 语义搜索只做补充

FTS 跑通后，再加 embedding 检索。本地模型选轻量的 `bge-small-zh` 或 `gte-small` 就够，不需要一上来就接大模型 API。写入记忆时同步生成向量，存 SQLite 或轻量向量库均可。几千条记忆用 SQLite 存 JSON 数组，配合 `sqlite-vec` 也能做余弦检索。

注意不要只拿向量相似度做阈值判断。不同 embedding 模型的 0.7 不是同一个 0.7，必须在自己真实查询集上评估。

### 3. 合并用 RRF

两路各自取 top20，然后用 Reciprocal Rank Fusion 合并成 top10。RRF 的好处是不依赖两个分数的绝对大小，只需要各自排序：

```text
score = sum(1 / (k + rank_i))
```

通常 `k = 60`。语义路能捕捉“上次连接问题”这种 paraphrase，全文路能锁定错误码和专有名词。合并后，Agent 得到的上下文既有相似记忆，又有精确 token。

如果硬件允许，再挂一个 cross-encoder 做精排。不过在小规模记忆里，直接 RRF 就够，先不要加复杂组件。

## 踩坑点

1. **中文全文搜索不配置分词等于没做**。FTS5 默认对中文不友好，trigram 或 jieba 预分词至少选一个。

2. **语义搜索对数字、版本、否定词不可靠**。记忆里 “Python 3.11 升级到 3.12 后 asyncio 报错” 和 “Python 3.12 降级回 3.11” 在向量空间里可能非常近。这类内容要保留原文，优先让全文路召回。

3. **召回数量不是越多越好**。一次塞 20 条记忆给模型，往往上下文噪声过大。控制在 5-10 条、总量不超过模型可用上下文的 1/3，效果更稳定。

4. **每次全量重建 embedding 会拖垮写入**。记忆模块应当是增量更新，而不是每次 recall 都把所有记忆重新向量化。

5. **别只看单个查询效果**。至少要准备 30-50 条真实历史查询，算一下 `recall@10` 或 `MRR`，才知道混合到底有没有提升。只看一两个 case 很容易自我感动。

## 可复用建议

- **抽象成 provider**：`memory_recall` 支持 `fts`、`vector`、`hybrid` 三种模式，同一接口切换，方便对比和回滚。
- **中文优先做 FTS 分词方案**，向量路只处理 paraphrase，不背精确 token 的锅。
- **记录 recall 日志**：每次召回了哪几条、最终模型用了哪几条，最好能在 debug 时看到。没有日志，memory 调优就是玄学。
- **先 FTS，后混合**：不要因为 “向量搜索高级” 就直接上 Chroma/向量库。几千条记忆用 SQLite FTS5 + 轻量 embedding 足够。

## 总结

语义搜索和全文搜索不是替代关系。AI 助手的记忆里，既有“感觉像”的泛化描述，也有“必须一样”的硬标识。合理的工程方案是：**全文负责精确，语义负责泛化，RRF 做低成本融合，日志和评估做裁判**。这样 `memory_recall` 才不会成为 Agent 产生幻觉的入口。
