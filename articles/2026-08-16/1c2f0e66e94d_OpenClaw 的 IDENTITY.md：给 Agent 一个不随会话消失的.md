## 背景：Agent 有工具，但没有“身份”

在 OpenClaw 里接 MCP、挂插件、写自动化的人，很容易陷入一种状态：工具越来越全，但 Agent 的行为越来越漂。

同一个 Agent，今天在群聊里回复得像客服，明天在自动化任务里又变得像运维脚本。每次开新会话，都要重新纠正一遍它的语气、边界和工具使用习惯。问题通常不在模型能力，而在我们把“身份”散落在 system prompt、插件说明、项目 README 甚至某次聊天记录里。

IDENTITY.md 的思路就是把这些东西收敛成一个可版本、可复用、可进化的身份文件。它不只是 prompt 美化，而是给 Agent 一个跨会话、跨入口的稳定身份层。

## 问题：为什么 prompt 里写人设不够用

直接的 system prompt 至少有三个问题：

1. **不可复用**：换一个入口或新设备，人设就要重新粘贴。
2. **不可版本化**：改了几次之后，很难知道当前生效的到底是什么版本。
3. **无法分层**：核心身份、项目约定、临时上下文混在一起，模型容易抓错重点。

在 OpenClaw 这类 Agent 框架里，还有一个更现实的问题：接上 MCP 之后，工具使用策略往往写在 MCP server 的说明里。身份文件如果不统一，Agent 很可能在工具失败时自行“合理化”，返回一个看似正常但实际伪造的结果。身份层要管的正是这些边界。

## 做法：把 IDENTITY.md 接进 OpenClaw

### 1. 建一个最小身份文件

在工作区根目录创建 `IDENTITY.md`，不要一上来写成长篇大论。建议只保留几个块：

```md
# IDENTITY

## Who I am
- 面向 OpenClaw 的工程助手，偏务实、克制。
- 默认中文回复，除非用户要求其他语言。

## What I optimize for
- 先复现问题，再给方案。
- 优先使用现有工具，不臆造 MCP 返回结果。

## How I work
- 涉及文件改动前，先说明影响范围。
- MCP 工具失败时，明确报告失败，不回退到猜测。

## Hard constraints
- 不读取 .env 内容。
- 不在群聊中输出完整内部路径。

## Evolution Log
- 2025-02-01：首次建立身份基线。
```

### 2. 在 OpenClaw 配置中挂载

不要复制粘贴到每个入口的 prompt。在 OpenClaw 的全局或项目配置里，把 `IDENTITY.md` 作为预加载内容引入。这样群聊、自动化任务、插件触发三种入口读到的是同一份身份。

### 3. 让身份可进化

每次出现明显的行为偏差，不要只修 prompt，而是问自己：这个偏差是不是长期有效的规则？

如果是，就追加到 `Evolution Log`，写上日期和理由。如果不是，就不要写进去。身份文件应该像 git 仓库的主干，稳定且可回滚，而不是聊天记录的流水账。

### 4. 验证一致性

开一个新会话，让 Agent 复述三个内容：我是谁、我的硬约束、我在工具失败时怎么处理。如果复述不完整，说明文件太长或重点被稀释，需要精简。

## 踩坑点

### 1. 身份文件越长越没用

IDENTITY.md 超过两屏后，模型注意力会明显稀释。不要把项目细节都塞进去。细节放 `docs/` 或项目 README，身份文件只保留“何时该去查什么”。

### 2. 只写规则，不写触发条件

“遇到问题要谨慎”没用。要写“当 MCP 返回超时，先重试一次；连续失败则回报用户，不要自动更换工具”。没有触发条件的规则，模型不知道什么时候激活。

### 3. 与 system prompt 冲突

如果 OpenClaw 入口里还残留一份手写人设，模型会在两份指令之间摇摆。统一入口后，把其他地方的重复人设删掉，只保留真正与入口相关的任务指令。

### 4. 把敏感信息写进去

不要在 IDENTITY.md 里放 token、内网地址、测试账号。身份文件经常会被引用、展示、甚至分享。敏感信息走环境变量或 secret 注入。

### 5. 进化变成流水账

每次犯错都往 Evolution Log 里加一条，很快文件就不可维护。只沉淀“可复用决策”，并且定期合并相近条目。一个简单的判断标准：如果这条规则只对今天这个任务有效，就不要进入身份文件。

## 可复用建议

- **分层管理**：身份层（IDENTITY.md）只放稳定身份和硬约束；项目上下文层放当前项目的约定；会话临时层放这次任务的具体目标。三层不要互相渗透。
- **用祈使句写规则**：短句、可验证。例如“工具失败时报告失败，不猜测结果”，比一段解释更有效。
- **定期瘦身**：每 5-10 次修改后，删掉过时条目，合并相近规则。身份文件需要维护，不是只增不减。
- **和 MCP manifest 对照**：把身份文件里的工具使用边界，与 MCP server 实际暴露的权限做一次对照，避免权限漂移。
- **纳入版本管理**：IDENTITY.md 随项目 git 管理。改坏可以回滚，也能看到身份演进历史。

## 总结

IDENTITY.md 的价值不在于写得漂亮，而在于它给 Agent 提供了一个稳定、可版本、可进化的身份锚点。对 OpenClaw 用户来说，它能把“这个 Agent 该怎么做事”从口头约定变成工程文件，让群聊、自动化、插件调用保持同一套行为边界。

务实一点的做法是：先建一个最小身份文件，跑几天，只把真正反复出现的偏差写进 Evolution Log。身份不是一次设计出来的，而是用出来的。
