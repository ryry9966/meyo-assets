# OpenClaw Skills 机制：让 AI 助手按需加载能力的工程实践

## 背景

在 OpenClaw 里接入 MCP 工具、本地脚本和外部 API 之后，很快会遇到一个现实问题：system prompt 越来越长。全量预加载所有能力，不仅推高 token 成本，还会稀释模型对关键指令的注意力。工具描述越多，模型越容易在任务开始时选错工具，或者忽略约束。

OpenClaw 的 Skills 机制提供了一种拆分方式：把能力做成独立技能包，模型先只读索引，再按需加载技能正文。这样上下文里不会一直堆着几十个工具的说明，只有当前任务需要的技能会被注入。

## 问题

按需加载不是简单把“所有技能”改成“晚点加载”。实际落地时，常见问题集中在三类：

1. 索引不清，导致选错技能或漏选技能。
2. 加载后没有释放，上下文继续膨胀。
3. 技能加载成功，但依赖的脚本、权限或前置技能缺失，执行失败。

这些问题会让按需加载看起来比全量加载更不稳定。关键不在于“要不要加载”，而在于索引质量和生命周期管理。

## 做法/步骤

### 1. 定义技能目录

在 OpenClaw 配置中指定 `skills_dir`，每个技能一个目录，核心是 `SKILL.md`。例如：

```text
skills/
  pdf/
    SKILL.md
    scripts/extract.py
  sql/
    SKILL.md
  browser/
    SKILL.md
```

`SKILL.md` 使用 frontmatter 声明元信息：

```yaml
---
name: pdf-extract
description: Extract text and tables from PDF files.
when_to_use: User asks to read a PDF or extract data from PDF.
when_not_to_use: Scanned PDFs that need OCR unless ocr skill is loaded.
dependencies: [ocr]
permissions: [read_files]
version: 1.2.0
---
```

正文部分写具体执行步骤、脚本调用方式和输出格式。不要把大量细节都堆在正文里，复杂内容放到外部文件按需读取。

### 2. 只把索引挂进主配置

OpenClaw 启动时扫描技能目录，生成索引。主配置只加载索引，不加载技能全文。索引里保存每个技能的 `name`、`description`、`when_to_use`、`when_not_to_use`、依赖关系和预估 token 成本。

```yaml
skills:
  dir: ./skills
  index: auto
  max_loaded: 3
  unload_after_turn: true
```

这样基础上下文里只有一屏左右的技能摘要，不会因为技能数量增加而线性膨胀。

### 3. 运行时两阶段调用

任务进来后，模型先看索引，输出一个加载指令，例如 `load_skill("pdf-extract")`。OpenClaw 读取对应的 `SKILL.md`，注入当前会话，并把脚本路径注册为可用工具。

如果是无状态技能，执行完直接卸载；如果技能需要保存会话状态，则保留到显式卸载或空闲超时。

### 4. 记录加载日志

每次加载记录技能名、触发原因、加载耗时、执行结果、是否失败回退。日志是后续调索引和排查加载错误的主要依据。

## 踩坑点

- **描述太宽泛**：只写“处理文件”会让技能被反复误加载。`when_to_use` 和 `when_not_to_use` 都要写，否定条件比肯定条件还重要。
- **技能正文过长**：单个 `SKILL.md` 超过 1200 token 后，加载一次就可能挤掉核心系统约束。建议控制在 500–1200 token，复杂逻辑拆到外部文档或脚本。
- **相对路径失效**：技能内脚本如果用相对路径，OpenClaw 工作目录不同会导致找不到文件。建议使用基于技能目录的绝对路径，或在加载时注入技能目录变量。
- **依赖顺序错误**：例如 PDF 技能依赖 OCR 技能，索引里声明了依赖，但加载器没有递归加载，执行时就会失败。加载器需要支持依赖解析。
- **状态残留**：技能设置了环境变量或修改了共享文件，卸载时没有清理，会影响后续任务。无状态技能优先，有状态技能要显式定义清理步骤。
- **版本漂移**：直接引用外部脚本的 main 分支，更新后行为变化，排查困难。建议锁定版本，或把技能目录整体纳入版本控制。
- **权限过大**：技能加载后拥有了读文件、执行脚本等权限，但 `SKILL.md` 没有声明边界。建议在 frontmatter 中写明所需权限，高风险操作执行前增加确认。

## 可复用建议

- 把技能当发布包管理：有版本、有测试、有变更日志。
- 索引不要手写，用脚本扫描技能目录并校验 frontmatter，避免漏字段。
- 为每个技能写一个最小 smoke test，验证脚本可运行、输出格式符合预期。
- 先 dry-run：不实际加载，只输出“将加载哪些技能”，用来调索引。
- 设置 token 预算：加载技能后总上下文不超过模型窗口的 70%，防止挤爆窗口。
- 定期看加载日志，统计误加载率。某个技能命中率低时，优先改描述，而不是急着加更多技能。
- 高风险技能默认不自动加载，必须由模型显式调用并二次确认。

## 总结

OpenClaw Skills 机制的价值不在于“多了一种加载方式”，而在于把“可用能力”和“当前任务所需能力”分开。索引质量决定模型能否选对技能，生命周期管理决定加载是否稳定，失败回退决定系统可不可用。

不要一上来把所有能力都做成 skill。先把高频、独立、可清晰描述的任务拆出来，跑通索引、加载、执行、卸载的完整链路，再逐步扩展。按需加载如果做不好，不如先保留少量常驻能力；如果做好了，它可以显著降低上下文成本，同时让助手在面对复杂任务时更专注。
