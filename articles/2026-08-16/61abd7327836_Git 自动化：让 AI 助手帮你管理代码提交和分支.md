# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

在 OpenClaw / Agent / MCP 的实践里，有几个 Git 场景几乎每个项目都会遇到：根据 diff 生成规范提交信息、创建 feature 分支、清理已合并的陈旧分支、生成 PR 描述。这些操作重复、规则明确，但又不能完全放任模型自己敲 shell。

直接给 Agent 一个 `shell_exec` 权限，让它执行任意 `git` 命令，风险很高：误删分支、提交敏感文件、把测试残留或本地配置一起提交、在错误的分支上 rebase。更现实的问题是，模型会在没有 diff 的情况下也生成“Update code”这种无效提交。

这篇文章整理一套我目前在用的、可复现的 Git 自动化思路：不追求全自动，而是把 Git 操作封装成受控工具，让 Agent 在边界内干活。

## 问题

AI 管理 Git 的难点不在“能不能执行命令”，而在：

- 模型容易幻觉，生成的提交信息与实际 diff 脱节
- 危险命令不可逆，例如分支删除、force push、reset
- 工作区状态不可控，可能提交未跟踪文件或敏感文件
- pre-commit hook 修改文件后，提交结果不符合预期
- monorepo 下 diff 过大，上下文直接爆掉

所以核心目标不是“让 AI 替你操作 Git”，而是“把重复的、可审计的 Git 操作变成小工具”。

## 做法 / 步骤

### 1. 抽象一个受控工具层

不要在系统提示里让模型自由调用 `git`。通过 MCP 或插件注册一组白名单工具，例如：

```json
{
  "tools": [
    "git_status",
    "git_diff",
    "git_log",
    "git_commit",
    "git_branch_create",
    "git_branch_cleanup"
  ],
  "protected_branches": ["main", "master", "release/*", "hotfix/*"],
  "commit_style": "conventional"
}
```

每个工具内部做参数校验。比如 `git_commit` 只接受 `message` 和可选的 `body`，不接受 `--amend`、`--no-verify` 等危险参数；`git_branch_cleanup` 只允许删除已合并分支，并且必须经过确认。

### 2. 先给上下文，再让模型决策

提交信息生成前，工具先返回：

```bash
git status --short
git diff --stat
git diff --cached --stat
```

不要一次性丢完整 diff。大仓先用 `--stat` 筛选，再按文件逐个读取。必要时只保留 hunks 摘要，避免上下文超限。

模型输出提交信息后，工具侧校验 conventional commits 格式，例如：

```text
feat: add branch cleanup tool
fix: handle empty diff in commit tool
refactor: split diff reader from executor
```

### 3. 写操作先 dry-run，再执行

分支清理是一个典型场景。工具先返回计划：

```text
[plan] delete merged branches:
  - feature/old-login
  - feature/update-docs
[skip] protected: main, release/1.4
```

用户或 Agent 确认后才执行 `git branch -d`，而不是 `-D`。这样即使模型判断错误，也不会造成不可逆损失。

### 4. 记录日志，保留回滚点

每次工具调用记录命令、参数、输出和退出码。关键写操作前自动保存 `git status --porcelain` 和当前 commit hash。如果事后发现工作区变脏或提交错误，至少可以快速定位。

## 踩坑点

### 空 diff 仍生成提交

模型在 diff 为空、或只有空白变更时，也经常生成“Update code”。工具层需要拒绝空提交，并返回 `nothing to commit, working tree clean`。

### pre-commit hook 修改文件

很多项目有 prettier、eslint、gofmt 等 hook。它们会在 `git commit` 过程中修改文件，导致提交后工作区仍然 dirty。执行完提交后，工具应重新运行 `git status --short`，如果有变更，提示用户而不是继续盲目提交。

### GPG / SSH 卡住非交互环境

在 Agent 运行环境里，GPG 签名或 SSH key 的 passphrase 提示会让进程挂起。工具层设置：

```bash
export GIT_TERMINAL_PROMPT=0
```

并捕获失败信息，避免 Agent 超时后重试造成重复提交。

### 敏感文件被提交

模型可能把 `.env`、`config/local.yml`、密钥文件加入提交。不要把安全寄托在模型自觉上。工具层增加风险文件检测，或至少让 `git_status` 高亮未跟踪文件，并要求提交前显式确认文件列表。

### monorepo diff 过长

一个大仓的完整 diff 可能几万行。Agent 读到一半就开始生成提交信息，质量很差。正确做法是分文件读取，按目录聚合，或者只提供文件级摘要，让模型决定深入查看哪个文件。

## 可复用建议

- **白名单 + 参数化**：不要让 Agent 拼接 shell 字符串，所有 Git 操作走固定工具。
- **写操作必须有 dry-run 和人工确认**：尤其是删除、reset、push 这类不可逆操作。
- **统一提交规范**：工具侧校验 conventional commits，不依赖模型自觉。
- **保护分支用正则**：`main`、`release/*`、`hotfix/*` 默认不可删除、不可 force push。
- **提供仓库规范文件**：在 `AGENTS.md` 里写明提交规范、保护分支、测试命令、敏感文件路径。Agent 执行前先读这个文件。
- **区分规划与执行**：让模型先输出计划，确认后再调用执行工具。不要让它边想边做。

## 总结

Git 自动化不是让 AI 替你做所有决定，而是把重复、规则明确的操作封装成可审计、可回滚的小工具。受控工具层 + dry-run + 人工确认，比一个“万能 shell 权限”可靠得多。这个思路也适用于其他命令类自动化：边界越清晰，Agent 越稳定。

现在的结论是：能自动化的部分有限，但把这有限的部分做稳，就已经能省下大量日常 Git 杂活。
