## 背景

在 OpenClaw 的日常使用里，单 Agent 串行执行很容易遇到瓶颈。比如需要同时抓取多个数据源、批量跑文件转换、或对多个模块做独立审查时，一个主 Agent 从头跑到尾，时间线性叠加，而且上下文越长越容易漂移。

后来我把任务拆给几个 subagent 并行跑，再由主 Agent 汇总，整体耗时从 8 分钟降到 2 分钟以内。这里记录一次完整实践，包含做法、坑点和可复用建议。

## 问题

最初我用一个 Agent 做“多渠道信息采集”：先搜网页、再调 API、再写文件，串行下来有三个明显问题：

1. **等待时间长**：网页抓取、API 请求、文件读写互相阻塞；
2. **上下文污染**：前面步骤的中间结果堆进上下文，后面推理质量下降；
3. **错误难定位**：一个步骤失败，整个任务中断，重跑成本高。

本质上，这一步不是推理难，而是任务天然可并行，却被硬塞进单线程。

## 做法/步骤

我用的环境是 OpenClaw 加上两个 MCP 工具：`web_search` 和 `http_client`，再配合本地文件系统工具。核心思路是：主 Agent 只做拆分和汇总，subagent 只做单一职能。

### 1. 定义 subagent 配置

先在 OpenClaw 里定义两个 subagent，一个负责网页检索，一个负责 API 调用：

```yaml
subagents:
  collector_web:
    prompt: "你是网页信息收集器。只从给定 URL 或搜索词抓取结构化数据，返回 JSON。不要分析，不要总结。"
    tools: ["web_search", "browser"]
    timeout: 120
    max_output_tokens: 2000

  collector_api:
    prompt: "你是 API 数据收集器。只调用指定接口，解析响应为 JSON 返回。不要添加任何解释文字。"
    tools: ["http_client"]
    timeout: 60
    max_output_tokens: 1500
```

关键点：subagent 的 prompt 必须窄而明确，“只做一件事”，避免它自由发挥。

### 2. 主 Agent 拆分任务并并行调度

在主 Agent 的指令里，让模型先输出一个任务清单，再调用平台提供的并行执行能力。示例逻辑：

```python
# 主 Agent 生成的拆分结果
tasks = [
    {"agent": "collector_web", "input": "抓取产品A在3个评测页面的评价摘要"},
    {"agent": "collector_web", "input": "搜索产品A的竞品B的负面评价"},
    {"agent": "collector_api", "input": "调用库存API获取产品A近30天的销量"},
]

# 并行执行，限制并发数为 3
results = run_parallel(tasks, max_workers=3)
```

实际运行时，三个 subagent 同时启动，完成后主 Agent 收到三份结构化结果。

### 3. 汇总与校验

主 Agent 拿到结果后做两件事：

- 检查返回格式是否符合预期（不然就要求重跑单个 subagent）；
- 汇总成最终报告，但不再重新推理原始数据。

## 踩坑点

实际跑下来，有几个坑值得记录：

**上下文隔离**  
Subagent 与主 Agent 之间不是共享上下文。主 Agent 的变量、前一步结果，subagent 默认看不到。所以输入必须完整写在任务里，不能以为“它知道前面的内容”。

**共享工具并发限流**  
`web_search` 和 `http_client` 在并发时容易触发上游限流或超时。我最多同时跑 3 个 subagent，超过 4 个失败率明显上升。

**返回格式漂移**  
即使用 prompt 强调“只返回 JSON”，仍有 subagent 会加解释文字、或返回不完整 JSON。应对方式是主 Agent 做一次轻量格式校验，不合规就带错误信息重跑该 subagent。

**合并成本被低估**  
拆分过细会导致汇总很痛苦。比如把 10 个 URL 拆成 10 个 subagent，结果合并时上下文又膨胀了。合理粒度是按“数据源类型”或“功能模块”拆，而不是按单条数据拆。

## 可复用建议

1. **先串行验证，再并行**  
每个 subagent 单独跑通 2-3 个示例，确认输出稳定后再放入并行流程。否则并行放大了错误，排障更累。

2. **强制结构化输出**  
在 subagent 的 prompt 里给出明确 JSON schema，并设置 `max_output_tokens` 限制，避免输出过长。

3. **设置超时和重试**  
每个 subagent 必须有 timeout。主 Agent 对失败任务做一次重试，仍失败就返回占位错误，不让整个流程挂掉。

4. **控制并发数**  
实践下来 3 个并发是较为稳妥的默认值。如果 MCP 工具是自建服务，可以适当调高；如果是外部 API，保守一点。

5. **用文件传大结果**  
如果 subagent 返回的数据量很大（比如几百 KB 的 JSON），不要塞进主 Agent 上下文。让 subagent 写文件，主 Agent 只拿文件路径和摘要。

6. **记录 token 消耗**  
并行不一定省钱。主 Agent 汇总时仍要消耗上下文，建议每次运行后看一眼 token 分布，避免“省了时间、多了成本”。

## 总结

Subagent 编排解决的是“任务可并行但被串行执行”的问题，适合数据采集、批量转换、独立审查等场景。它的价值不在“多 Agent 协作”这个说法上，而在于把主 Agent 从琐碎等待中解放出来，只做拆分、校验和汇总。

真正落地时，工程化细节比编排概念重要：返回格式、超时、重试、并发控制，这些才是决定能不能稳定跑起来的东西。建议从两个 subagent、三个并发的小任务开始，跑通后再逐步扩展。

不要为了并行而并行。如果任务之间依赖强，或者单任务本身很快，串行可能更简单可靠。先把串行路径走顺，再让它并行，这是成本最低的路径。
