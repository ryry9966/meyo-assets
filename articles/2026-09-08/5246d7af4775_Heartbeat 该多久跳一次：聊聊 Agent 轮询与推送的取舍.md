## 背景

OpenClaw 的 agent 大部分时间是静默的，触发来源基本就两类：用户消息，和 heartbeat——agent 按固定间隔自我唤醒，读一份 HEARTBEAT.md 清单，决定要不要干活。这个机制本质上就是轮询。

但实践中很多需求不是"到点了"，而是"有事发生"：CI 挂了、监控告警了、邮件到了。这类事更适合推送（webhook / 事件注入会话）。两条路线各有代价，选错的话要么烧 token，要么漏事件。

## 问题

我最初的配置：heartbeat 间隔 10 分钟，清单里塞了七八项检查。跑了一个月，问题很直观：

- 心跳 token 消耗占了大头，其中九成唤醒的结果是 nothing to do；
- 真正的事件（构建失败）平均延迟五分钟才被处理；
- 后来补的 webhook 通道因为没有兜底，一次网络抖动丢了一条告警，没人发现。

轮询贵但稳，推送便宜但脆。单选哪个都不对。

## 做法

后来改成混合模式，步骤如下：

1. **降频 heartbeat**：间隔放到 30–60 分钟，HEARTBEAT.md 只留"没有事件源也能查"的项（磁盘空间、日历、待办回顾）。心跳醒来无事可做就直接返回，不带工具调用。
2. **外部事件走推送**：webhook server 收事件，经 gateway 注入 agent 会话。CI、监控、邮件这些有明确事件源的，全部迁过来。
3. **推送加兜底**：事件先落盘（一个 JSONL 队列即可），注入成功才标记完成；心跳清单里加一项"检查未派发的事件"，作为推送失败后的补偿路径。
4. **参数细节**：间隔加随机抖动，避免整点扎堆；夜间静默时段降频到 2 小时；高优告警按 severity 绕过静默。

## 踩坑点

- **webhook 必须鉴权**。第一版裸奔公网，被扫到后灌了一堆垃圾事件，agent 疯狂空转。至少 token 校验 + 来源白名单。
- **事件去重**。监控重试会导致同一告警推两次，注入前按 event id 去重，否则 agent 会重复处理甚至重复回复用户。
- **别让心跳干重活**。心跳和用户交互共用会话，一次心跳跑十分钟的工具调用，用户的即时消息就得排队。心跳只做"检查 + 轻决策"，重活派给后台。
- **推送失败要可观测**。注入失败不能只写 log，得有计数和告警——兜底机制本身坏了你也不知道。

## 可复用建议

一个简单的判断标准：

- 有明确事件源、要求分钟级以内响应 → 推送；
- 没有事件源、或"定期回顾"性质 → 轮询（heartbeat）；
- 拿不准 → 推送为主，heartbeat 做兜底检查。

再加三条通用经验：心跳间隔宁长勿短，先统计"空醒率"再调；心跳清单保持短小，长清单拆成独立任务；所有推送通道默认会失败，落盘重试是底线不是可选项。

## 总结

轮询和推送不是二选一。OpenClaw 的 heartbeat 适合作为低频兜底节律，真正的实时性交给事件推送。省下来的 token 是真金白银，补上的那条队列，可能就是下次没漏掉的那条告警。
