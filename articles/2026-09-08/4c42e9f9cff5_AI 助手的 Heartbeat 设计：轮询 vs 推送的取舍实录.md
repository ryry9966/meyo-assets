## 背景

OpenClaw 这类常驻助手有个根本约束：LLM 不是带事件循环的常驻进程，没人触发它就不动。Heartbeat 是最朴素的解法——定时唤醒 agent，检查 `HEARTBEAT.md` 里的待办，有活干活，没活闭嘴。它解决的是"没人叫你时也要自转"的问题，但定时唤醒只是兜底，不是银弹。

## 问题

真正要回答的是：哪些事必须秒级响应，哪些事半小时知道就行？全靠轮询，低价值事件也在烧 token；全靠推送，各事件源协议不一，还要求网关可达、鉴权可靠。核心矛盾在于：一次唤醒是一轮完整的 agent turn，成本远高于一次普通 API 调用，"多醒一次"不是免费的。

## 做法

1. **给事件分层**：列出所有事件源（git push、监控告警、邮件、日历、日志巡检），按响应时限分三档：<1 分钟 / <10 分钟 / 小时级。
2. **小时级交给 heartbeat**：间隔从 30 分钟起步，`HEARTBEAT.md` 只放巡检类任务；无任务时强制返回固定短句或静默，避免每次唤醒都产出长文。
3. **分/秒级走推送**：告警、CI 失败直接 webhook 打到助手网关；走 IM 通道的消息本身就是 push，天然可用。
4. **MCP 摊薄轮询成本**：把多个事件源封装成一个 MCP server 的工具，一次唤醒批量查询，而不是一个源一个 cron。
5. **心跳兼作 watchdog**：heartbeat 每次必做的一件事是自检——确认推送通道近期有事件流入，形成 dead man's switch。
6. **记账**：每次唤醒记日志（触发原因、消耗、是否产生动作），每周算 wake-to-action 比例，据此调间隔。

## 踩坑点

- **心跳太密**：15 分钟一次跑一周，token 账单很难看，且绝大多数唤醒无事可做。
- **唤醒即长输出**：heartbeat 每轮都"汇报工作"，上下文被无效内容污染，后来改成无任务时一句话结束。
- **推送无幂等**：webhook 重试导致同一条告警触发三次任务，加幂等键才止住。
- **本地部署收 webhook 要暴露公网**：用内网隧道 + 签名校验，别裸奔。
- **最危险的是心跳静默死亡**：cron 还在跑但 agent 已经挂了，没人发现，靠 watchdog 对账才兜住。

## 可复用建议

- 推送管时效，心跳管底线：事件驱动保响应，轮询保活，二者是分层关系不是二选一。
- 心跳当哨兵不当工人：唤醒只做廉价检查，必要时再升级为完整任务。
- 一切推送事件带幂等键和时间戳，重试不重复执行。
- 心跳加 jitter 和静音时段，避免整点齐刷刷醒来。

## 总结

轮询 vs 推送的真实答案是一个分层结构：低价值、时限容忍的事件走心跳兜底；高价值、紧急事件走推送直达；心跳同时承担活性监控。先记账、再调参，比任何"最佳间隔"的玄学都可靠。
