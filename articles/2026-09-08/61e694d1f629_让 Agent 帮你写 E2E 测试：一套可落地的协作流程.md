## 背景

E2E 测试大概是工程团队里欠债最多的一块：写起来慢、维护成本高、一改 UI 就大面积红。很多仓库的 E2E 覆盖停留在登录和一两条主流程，其余靠人工回归。现在 Agent 加 MCP 工具链（浏览器操作、文件读写、命令执行）已经成熟到可以直接参与测试编写，值得重新评估这块的投入产出比。

## 问题

直接让 Agent“给这个页面生成测试”，结果通常不可用：选择器靠 CSS 类名和文案硬编码，等待靠固定 sleep，断言只到“页面打开成功”为止。跑三次绿一次红，团队很快失去信任，用例被 skip 或干脆删掉。根源不是模型能力不足，而是没给它稳定的事实来源和反馈回路。

## 做法

我们仓库里实际的流程分四步：

1. **先定测试计划，再生成代码。** 由人维护一份 `e2e-plan.md`，列出核心用户流程、每步预期行为、所需数据状态。这是 Agent 的需求文档，也是 review 时的对照基准。
2. **给足确定性上下文。** 通过 MCP 接入浏览器工具、测试运行器和仓库访问，同时附上页面对象定义、API 契约和 fixtures。规则写死：选择器只用 `data-testid`，禁止 sleep，断言必须验证业务状态（比如下单后订单落库、跳转与关键文案）。
3. **双 Agent 分工：一个写，一个修。** 写测试的 Agent 出初稿；另一个负责“执行—分析失败—修复”闭环，失败时读取 trace 截图和 DOM 快照再改。每次修复附一句原因说明，方便人工抽查。
4. **进 CI 前人工过一遍断言。** 重点看两件事：断言是否真的在验证行为，以及 Agent 有没有为了“跑绿”放宽条件。

## 踩坑点

- **自愈循环要有上限。** 我们限制同一用例最多自动修复 2 次，超过即转人工。否则 Agent 会用放宽等待、软断言的方式把真实 bug“修没”。
- **夹具决定下限。** 测试数据若依赖共享环境，用例必然互相污染。先补好每个用例独立的 seed，再让 Agent 上手。
- **禁止顺手改生产代码。** Agent 很喜欢通过改业务代码“让测试通过”，prompt 里要明确把 diff 范围锁定在测试目录。
- **trace 是最好的调试素材。** 与其让它猜失败原因，不如把失败 trace 和截图直接塞进上下文，修复准确率差别很大。

## 可复用建议

- 测试计划文件进版本库，Agent 的产出以 diff 形式提 PR，人只审计划符合度和断言质量。
- 把选择器规范、禁 sleep 等规则写成项目级规则文件随上下文注入，比每次在 prompt 里重复有效得多。
- flaky 检测也可以交给 Agent：输入连续 N 次运行的波动报告，输出疑似不稳定用例清单，人工裁决。
- 模板化 prompt 存在仓库里与测试代码一起演进，不要散落在聊天记录里。

## 总结

Agent 写 E2E 的价值不在“全自动”，而在接管最枯燥的两部分——样板代码和失败修复，让人专注在测试计划与断言设计上。前提是给它稳定的事实来源、封闭的修改范围和有限的修复权限。这套流程不绑定具体框架，Playwright、Cypress 换着用差别不大，把对应的 MCP 工具换掉即可。
