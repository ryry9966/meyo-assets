## 背景

用 OpenClaw 一段时间后会发现一个模式：Agent 能力不弱，但它是"叫才动"的。你不发消息，它就安静待机。而值守型场景——巡检磁盘、盯 git 仓库、汇总每日变更——都需要有人先开口。heartbeat 机制就是为这个设计的：网关按固定间隔向主会话注入一次心跳提示，Agent 被要求去读 workspace 根目录的 `HEARTBEAT.md`，按文件里的清单决定"现在该做什么，还是没事可做"。

## 问题：它不是 cron

很多人第一反应是"这不就是定时任务？"实际用下来差别很大：

- cron 执行的是写死的命令；心跳执行的是模型根据清单做的判断，有弹性，也有不确定性；
- cron 静默是默认；心跳的产出默认是要推给你的消息，需要约定"无事可做"的信号（`HEARTBEAT_OK`）才会安静；
- 每次心跳都消耗 token，且占用主会话上下文。

所以 HEARTBEAT.md 写得好不好，直接决定这个机制是"省心的值班员"还是"烧钱的轰炸机"。

## 做法

1. 在 workspace 根目录建 `HEARTBEAT.md`，用 checklist 语法，一行一个任务。
2. 每个任务写清三件事：**做什么、什么条件算到期、什么情况算没事**。"看看有没有新东西"这种描述必踩坑，要写成可判定条件，比如"磁盘使用率超过 85% 才推送，否则静默"。
3. 控制节奏：心跳间隔在配置里调整（默认约 30 分钟，可改成 `15m`）。巡检类 30–60 分钟合适，提醒类没必要这么密。
4. 收敛输出：让 Agent 把详细结果落盘到 workspace 里的文件，只有值得打扰你的结论才推送一句话；无事可做时明确要求只回 `HEARTBEAT_OK`。
5. 观察几天网关日志，看哪些任务每次都触发、哪些从没触发，回头修判定条件。

一个能跑的起步模板：

```markdown
# Heartbeat
- [ ] 每次心跳：检查 ~/projects/api 的 git status，
      有未提交变更且超过 2 天才推送，否则静默
- [ ] 磁盘使用率 > 85%：推送告警，否则 HEARTBEAT_OK
- [ ] 每天 8 点后第一次心跳：汇总昨日提交写入 inbox/daily.md，
      只推送一句话摘要
```

## 踩坑点

- **清单当 cron 堆满**：十几个任务全标"每次必做"，每个心跳就是一串工具调用，token 费用肉眼可见地涨。起步放 2–3 个任务就够。
- **静默约定失效**：部分小参数模型不太稳定地遵守 `HEARTBEAT_OK`，隔三差五推一句"今天没什么事"。要么换模型，要么在文件顶部重申"无事必须只回 HEARTBEAT_OK"。
- **时间条件太模糊**："每天早上"依赖模型对当前时间的感知，跨时区部署容易跑偏，写具体时刻更稳。
- **上下文污染**：心跳和日常对话共享主会话上下文，长输出的巡检结果会把上下文撑大。把"结果落盘、只推结论"直接写进任务描述。
- **权限先行**：心跳意味着 Agent 会无人值守地调工具，先收紧工具白名单和 workspace 权限，再让它"主动"。

## 可复用建议

- 把 `HEARTBEAT.md` 纳入 git 管理，每次调整有据可查，也能回滚。
- 任务分三层维护：固定巡检、条件触发、低频汇总，别混着写。
- 每个任务补一行"什么事不值得推送"，负向条件比正向条件更能压住误报。
- 先跑一周再加任务——心跳的节奏感是调出来的，不是设计出来的。

## 总结

heartbeat 把 Agent 从被动应答器变成有例行值守的协作者，但它的可靠性完全取决于你怎么写 `HEARTBEAT.md`：可判定的到期条件、克制的推送策略、明确的静默信号。这三件事写清楚，Agent 就能在你提问之前，先把该做的做完。
