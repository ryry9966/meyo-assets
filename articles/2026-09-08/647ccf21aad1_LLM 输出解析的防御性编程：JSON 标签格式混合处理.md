## 背景

做 Agent 和自动化流水线时，我们经常要求 LLM「只输出 JSON」。但只要采样温度不为 0、上游模型会换版本，输出格式就不可能完全可控。实践中最常见的不是纯 JSON，而是各种混合格式：代码围栏包裹、自定义标签包裹、前后带解释性文字、全角引号、尾逗号，甚至因 max_tokens 被截断的半截 JSON。

## 问题

很多项目的解析层是这样写的：先 `json.loads`，失败就用正则 `\{.*\}` 抠一次。这套写法 demo 里能用，上量后两类故障很典型：

1. 贪婪匹配在嵌套对象或字符串值含 `{` 时抠错边界；
2. 让模型「先解释再给 JSON」时，正文里的字符串值本身可能包含 ``` 围栏，朴素剥围栏逻辑剥错层，把正文当成了数据。

这类故障的特征是偶发且难复现——同一个 prompt 十次里坏一次，日志里只留一行 `JSONDecodeError`，原始输出没存，排障无从下手。

## 做法：分层解析 + 失败分类

核心思路是把解析做成一条流水线，每层只处理一类脏格式，全部失败再报错；同时永远保留 raw_output。

```python
def parse_llm_json(raw: str):
    text = raw.strip().lstrip('\ufeff')
    # 1. 直接解析
    # 2. 剥代码围栏：只剥首尾围栏，语言标记为 json 或空
    # 3. 剥自定义标签：<json>...</json> 等
    # 4. 括号平衡提取：扫描 { } [ ]，跳过字符串与转义，取最深平衡块
    # 5. 轻量修复：去尾逗号、全角引号转半角
    # 每层成功即返回 (data, meta)，meta 记录命中层与失败分类
```

几个实现要点：

- **括号平衡扫描比正则可靠**：维护深度计数器，遇引号进入字符串态，处理 `\"` 转义，只在字符串外计数。这能正确处理嵌套和值内花括号。
- **修复层要保守**。尾逗号、全角标点这类确定性修复可以做；单引号转双引号要小心字符串内容本身含单引号。截断修复（自动补右括号）风险最高——补出来的可能是语法合法但语义残缺的数据，建议默认不修，改为触发重试。
- **解析后必须过 schema 校验**（pydantic / zod 均可）。JSON 合法不等于字段类型对，`"count": "3"` 这种字符串数字只有校验能兜住。
- **失败要分类落日志**：`DIRECT / FENCE / TAG / BALANCED / REPAIRED / TRUNCATED / FAIL`，配合 raw_output 存档，故障从「猜」变成「查」。

## 踩坑点

- 只在 prompt 里写「请只输出 JSON」是不够的，提示端和解析端要双保险；模型支持 JSON mode / 结构化输出时优先用，但仍要保留兜底解析。
- 多围栏场景下别取第一个围栏，取能通过平衡扫描的那个。
- 温度大于 0 时，昨天没出现的问题今天可能出现。解析层要按「必然出错」设计，而不是按「偶尔容错」。

## 可复用建议

1. 解析逻辑收敛到一个工具模块，全项目共用，不要各插件各写各的。
2. 函数签名返回 `(data, meta)` 而不只是 data，meta 带失败分类，方便上游决定重试还是降级。
3. 攒一份「脏输出语料」，把线上真实故障样本做成单元测试用例，回归时全量跑一遍。
4. 按 prompt 模板统计解析失败率，失败率突增往往意味着模型版本或提示词被改动，是最便宜的回归报警。

## 总结

LLM 输出解析的本质是：假设输入永远是脏的，用分层流水线对脏格式分类处理，用 schema 校验兜底语义，用失败分类和原始输出存档保证可观测。解析层不追求聪明，追求稳定和可查。把这层做扎实，上层 Agent 逻辑才谈得上可靠性。
