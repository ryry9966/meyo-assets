## 背景

OpenClaw 侧的 agent 常配一个 `memory_recall` 工具：把用户偏好、项目约定、历史决策写进本地库，对话时检索出相关条目注入上下文。检索实现基本两条路——向量语义搜索，或传统的全文检索（BM25 / FTS5）。群里经常争论哪个“更好”，我们拿真实数据跑了一轮，结论比想象中简单。

## 问题

我们最初全量用向量检索，两类翻车很明显：

1. **标识符类查询失准**。查「ERROR 5023 处理办法」这类带错误码的记忆，语义检索召回一堆“错误处理最佳实践”式的泛化条目，真正那条精确记忆排不进 top-3。
2. **中文短查询不稳定**。「部署脚本超时」这种口语化短句，相似度分数抖动大。

反过来，纯全文搜索又扛不住同义改写：用户说「发布流程」，记忆里存的是「上线步骤」，直接搜空。

## 做法

1. **先建评测集**：从历史会话抽 50 条真实查询，人工标注应命中的记忆条目，算 top-3 命中率。没有这一步，后面全是感觉之争。
2. **跑单路基线**：SQLite FTS5 + 中文分词。结果显示含专有名词、错误码、文件名的查询，全文命中率又高又稳定。
3. **补语义路**：对模糊、改写型查询换向量检索（bge 系列 embedding + 本地向量库），命中明显改善。两类查询特征基本互补。
4. **简单融合**：两路各取 top-8，用 RRF（倒数排名融合）合并出 top-5；查询里带引号、错误码、路径特征时，把全文路的权重调高。
5. **注入时带元信息**：每条记忆附时间戳和来源标签，prompt 里声明「以下为历史记忆，可能过时」。

## 踩坑点

- **FTS5 默认 unicode61 分词器不切中文**，整句变一个 token，等于不可用，必须外挂分词或用 trigram。
- **embedding 模型要选中文友好的**，纯英文模型对中文查询的相似度分数会整体漂移，排序基本失真。
- **切块别按固定长度硬切**。按“一条记忆一个原子事实”来存，检索粒度对齐存储粒度，比任何调参都管用。
- **向量索引有更新延迟**，删改记忆后要重建或打墓碑标记，否则会召回已作废条目。
- **top-k 别贪大**，超过 8 条会稀释上下文，模型反而抓不住重点。

## 可复用建议

- 别一步到位上向量库。先用 FTS5 + 好的分词跑两周，拿评测集确认哪类查询漏召，再针对性补语义路。
- 写入时顺手打结构化标签（类型：决策/偏好/事实；关键词单独存字段），收益大于事后检索调优。
- 融合排序不必复杂，RRF 十行代码够用；关键是保留两路各自的分数，便于事后回放排查。

## 总结

这不是二选一：标识符类查询全文赢，改写类查询语义赢。混合检索 + 简单融合后，我们评测集的 top-3 命中率从全文单路的约 74% 提到约 89%。正确的工程顺序是：**可评测 → 单路基线 → 按短板补路 → 记忆原子化**。先能度量，再谈选型。
