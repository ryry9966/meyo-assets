## 背景

大多数 agent 的用法是被动式：你发消息，它回复。OpenClaw 里其实早就有做 proactive 的材料——gateway 的事件通道、MCP 工具、cron 心跳和 webhook。缺的从来不是能力，而是**触发纪律**。

## 问题

直接让 LLM“主动干活”，有三种典型翻车：

1. 用 LLM 轮询判断“要不要提醒用户”，token 烧得快，判断还不稳定；
2. 没有去重，同一事件反复推送，用户两天后就把它静音；
3. 触发时上下文过期——事件发生时环境已变，agent 拿着旧状态执行出错误动作。

Proactive 的工程本质不是“更聪明”，而是“**更少但更准地醒来**”。

## 做法

我们在一个内部助手上落了三层结构。

**第一层：确定性触发器（脚本，不花 token）**

- cron 心跳：每 5 分钟跑一次轻量检查（CI 状态、磁盘水位、日历临近事件、PR 停滞天数）；
- webhook：外部系统事件直接 POST 到 gateway；
- watcher：仓库关键路径变更。

触发器只回答“要不要唤醒 agent”，输出结构化事件：`type`、`source`、`payload`、`ts`、`dedup_key`、`priority`。

**第二层：节流与状态**

一个 KV 状态库（SQLite 够用）：`dedup_key` + TTL 做去重；每类事件设 cooldown；全局每日主动推送预算（比如 10 条），超了只写日志不推送；quiet hours 按用户时区算。

**第三层：分级动作**

agent 拿到事件后按风险分级执行：

- **L0 静默**：写日志，攒进每日摘要；
- **L1 草稿**：备好建议等确认，比如“PR #42 已停滞 3 天，要我起草一条 ping 评论吗？”；
- **L2 自动执行**：仅限低风险、可逆、幂等的动作（打标签、建草稿文档），且回执第一行必须写清“为什么现在提醒你”。

## 踩坑点

- **去重 key 粒度**：用 `repo+pr` 会漏（同一 PR 的不同事件被吞），用 `repo+pr+event` 又刷屏。最终用 `repo+pr+事件+语义桶`——状态真正变更才算新事件。
- **幂等**：MCP 工具重试会建出两个 ticket。所有写操作前先查一次“是否已存在”，或带外部幂等键。
- **过期上下文**：事件 payload 带 `ts`，执行前对关键前提跑一次 pre-check，失败就降级到 L1。
- **时区**：quiet hours 一开始用了服务器时区，凌晨三点被自己人骂。
- **推送格式**：主动消息必须一句话讲清触发原因 + 建议动作 + 一个明确的“不再提醒”选项，否则信任度掉得很快。

## 可复用建议

- **预算先行**：先定“每天最多主动打扰几次”，再写触发器；
- **LLM 管决策不管检测**：检测用脚本，判断用模型；
- **灰度升级**：新事件类型先跑 L1 观察一周，误报率低于 5% 再升 L2；
- **埋点复盘**：每条主动推送记录触发源、动作、用户是否确认，每周看数据调阈值。

## 总结

Proactive 不是把 agent 变成主动轰炸机，而是给它一套“何时值得开口”的纪律：便宜可靠的触发、有预算的节流、分级的动作、一句话可解释的理由。OpenClaw 这套不需要新组件，cron + webhook + 一个 KV 库 + 现有 MCP 工具就能跑起来。先做窄（一两个事件类型），跑稳了再扩。
