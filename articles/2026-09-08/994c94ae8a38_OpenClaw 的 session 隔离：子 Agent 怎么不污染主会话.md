## 背景

OpenClaw 的主会话本质上是一条持续增长的上下文：你的指令、模型的回复、每次工具调用的返回值，全都堆在同一条 transcript 里。跑得越久，上下文质量越直接决定 agent 的表现。子 Agent 机制要解决的就是这个问题——批量检索、长文档分析、多轮试错的代码探索这类"脏活"，应该在独立 session 里完成，主会话只收结论。

## 问题

如果子任务和主任务共享同一个 session，会出两类麻烦：

1. **上下文膨胀**。子任务产生的几十次工具调用和长输出会把主会话的上下文窗口撑爆，早期那些关键约束（比如"不要动某个文件"）被挤出窗口。
2. **语义污染**。更隐蔽的是，主 agent 会把子任务遗留的中间状态当成"已知事实"，在后续推理里引用早已过期的中间结论。这类 bug 很难排查，因为它不报错，只是悄悄变蠢。

## 做法

OpenClaw 的隔离是两层配合的：

1. **session 层隔离**。在配置里为子 agent 单独声明 agent 后，它拥有独立的 session 空间，transcript 落在自己的 sessions 目录下，和主会话物理分开。
2. **调用层收敛**。主会话通过子代理工具下发一段自包含的任务 prompt，子 agent 在全新上下文里执行；结束后只回传一份最终结果（结论、摘要、产物路径），主会话把它当作一条普通工具结果插入。

实操上记住三步：

- 任务 prompt 写成自包含的：目标、边界、期望的输出格式，不依赖任何"我们之前聊过"的上下文；
- 明确要求子 agent 只返回摘要和产物位置，不要全量 dump；
- 排查问题时去看子 agent 自己的 transcript，别翻主会话——过程本来就不在那里。

## 踩坑点

- **session 隔离 ≠ workspace 隔离**。文件系统默认是共享的，子 agent 写下的文件、改掉的状态都会留下。主会话之后读到这些文件，等于被动接收了污染。这是最常见的翻车点。
- **在任务描述里写"参考之前的对话"**。子 agent 看不到主会话，它不会报错，只会编一个看起来合理的答案。
- **回传结果不设上限**。子 agent 把完整检索结果原样塞回来，等于换了个位置继续污染主会话。
- **共享 memory 的双刃剑**。如果子 agent 和主 agent 共用同一份 memory 文件，"经验"会跨 session 渗透。有时是加分项，有时子任务里的临时结论会污染主 agent 的长期判断。要不要共享，建议按场景显式决定，而不是用默认值。
- **并发子 agent 写同一个文件**。两个子 agent 同时做写入，后写的覆盖先写的，且主会话对过程无感知。

## 可复用建议

- 把子 agent 当**函数**设计：入参是自包含的任务 prompt，出参是结构化摘要加产物路径。接口清晰，隔离才有意义。
- **明确共享面**：只在文件系统和显式传参这两个地方共享数据，永远不要依赖上下文共享。
- 给子 agent 配**独立的工具白名单**，缩小爆炸半径——子任务不需要的能力就不给它。
- 养成习惯：出问题时先看子 agent 的 transcript 复现它的决策链，再决定要不要 reset 主会话，顺序别反。

## 总结

session 隔离的本质，是把"过程"和"结论"分开：过程留在子 agent 的独立 transcript 里供审计，结论以受控的、紧凑的形式回到主会话。OpenClaw 在机制上已经帮你划好了边界，真正容易出问题的从来是边界两侧的约定——任务 prompt 是否自包含、回传是否收敛、workspace 是否被当成隐式共享通道。把这三件事当纪律执行，子 agent 就是杠杆；执行不到位，它就是另一个污染源。
