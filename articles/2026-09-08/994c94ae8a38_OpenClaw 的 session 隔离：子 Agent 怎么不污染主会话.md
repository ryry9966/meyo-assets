## 背景

OpenClaw 的主会话是和用户对话的连续上下文：历史消息、工具调用、中间推理都在里面滚动。单 Agent 跑长任务时，最大的隐患不是出错，而是上下文被中间过程塞满——读取的大文件、重试日志、一次性搜索结果，全都留在主会话里，导致后面每轮对话都背着这些包袱。

子 Agent 机制就是为这个准备的：把一段"过程重、结论轻"的工作扔进独立 session 跑，主会话只收最终结果。

## 问题：污染长什么样

典型症状有三个：

- 主会话 token 消耗随任务数线性上涨，几轮之后明显变慢、变贵；
- 模型注意力被早期无关的工具输出稀释，回答质量下降；
- 主会话消息流被子任务过程刷屏，人工回看成本变高。

## 做法

我们的实践可以压成四步：

1. **筛选任务**。只把"fire-and-forget"型任务交给子 Agent：批量检索、多文件整理、大范围代码扫描。判断标准很简单——预计产生超过十条工具调用、且主会话不需要中间过程的，都值得隔离。
2. **写自包含的任务提示词**。子 Agent 在 spawn 那一刻拿到的是快照，看不到主会话后续消息。所以任务描述必须自带：目标、边界、工具约束、返回格式。
3. **强制结构化返回**。在提示词里明确要求返回不超过 N 字的 JSON 或要点摘要。这一步最关键——不约束返回值，污染会换一条通道回来。
4. **主会话只消费摘要**。把返回的摘要当作唯一产物，顺手记下子会话的 session key，需要复盘时再单独查子会话的完整记录。

验证隔离也简单：用 session 列表确认子会话独立存在，再回看主会话记录，确认里面没有子任务的工具调用痕迹。

## 踩坑点

- **以为子 Agent 能看到主会话的后续消息**。它看到的是 spawn 时的快照，之后主会话聊了什么它完全不知道。需要的信息要在 spawn 时一次性给全。
- **返回值污染**。子 Agent 老老实实跑完，却返回了一整段原始工具输出，主会话照样被撑爆。返回格式必须写进任务提示词，不要靠"它应该懂"。
- **共享 workspace 的写冲突**。子 Agent 和主会话如果写同一批文件，顺序不可控。给子 Agent 单独的工作目录，或者约定只读。
- **子会话堆积**。每次 spawn 都会留一个 session，跑批任务一天能堆几十个。建议定期清理，或按 key 前缀批量归档。
- **权限继承**。子 Agent 默认继承主 Agent 的工具面，涉及敏感操作前最好显式收窄。

## 可复用建议

- 把 spawn 提示词做成团队模板：目标 / 边界 / 返回 schema 三段式，统一口径。
- 给子会话 key 定命名约定，方便脚本批量管理和事后审计。
- 沉淀一个判断口诀："过程重、结论轻，就隔离"。
- 反向提醒：如果任务需要主会话的实时状态，说明它不适合子 Agent——要么在主会话跑，要么拆成两次 spawn 分阶段传状态。

## 总结

session 隔离不是高级技巧，本质是"上下文卫生"：主会话留给需要连续性的对话，过程性工作进独立 session，只让结论回流。管住输入快照和输出格式这两个口，OpenClaw 的子 Agent 就能在不污染主会话的前提下，稳定承担真正的重活。
