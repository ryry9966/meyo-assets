## 背景

跑 Agent 一段时间后，大多数人都会遇到同一个账单问题：一条链路里，规划、工具调用、总结、格式化，全走同一个旗舰模型，成本和延迟都压不下来；反过来全换成本地小模型，复杂任务的成功率又明显下滑。OpenClaw 的多模型路由，本质上就是把「用哪个模型」从一次全局选择，变成按环节决策。

## 问题

难点不在「能不能配」，而在判据。我们早期踩过两种极端：一是按成本一刀切，全走本地，结果反复重试，综合成本反而更高；二是按直觉分配，链路一长就说不清哪个环节该升级、哪个该降级。路由需要可量化的规则，而不是偏好。

## 做法

我们目前的分层经验：

1. **按任务分层**。规划、多步推理、代码生成、有歧义的判断 → 云端旗舰（GPT 系）；摘要、格式转换、结构化抽取、工具参数填充、简单分类 → 本地模型（Qwen/Llama 系，8B–32B 区间够用）。
2. **按数据分层**。涉及内网文档、客户数据的环节强制本地，写进路由规则，不靠自觉。
3. **配置上用 profile + 规则路由**。给每个环节声明意图和模型档位，示意：

```yaml
models:
  frontier: { provider: openai, model: gpt-4.1 }
  local:    { provider: ollama, model: qwen2.5:32b }

routing:
  - match: { task: [plan, code, judge] }
    use: frontier
  - match: { data: private }
    use: local
    override: true            # 隐私数据不允许落到云端
  - default: local
  fallback: local -> frontier # 本地连续失败 N 次再升级
```

4. **观测先行**。每个环节记录：用了哪个模型、耗时、重试次数、token 成本。先跑一周拿数据，再调路由，不要拍脑袋。

## 踩坑点

- **路由器本身别太重**。用大模型做意图分类再路由，省下的钱可能不够付分类的账。规则能覆盖 80% 的场景就先用规则。
- **本地模型的 tool calling 不稳**。参数格式跑偏、漏字段很常见，解析层要做宽松校验 + 明确的失败信号，否则 fallback 根本不会触发。
- **静默降级最危险**。本地模型「看起来能用」地输出了低质量结果，链路照常走完，问题几天后才暴露。降级必须留痕、可告警。
- **换 embedding 模型要重建索引**。检索环节动了本地 embedding，旧向量库整体漂移，这是最容易忘的一步。
- **别用重试掩盖质量差距**。同一任务本地模型重试三次才通过，账面省钱，延迟和失败率已经不可接受了。

## 可复用建议

1. 先全量用 GPT 跑通，拿到质量和延迟基线，再逐环节下沉到本地——没有基线的优化是盲调。
2. 给每个 Agent 环节标注意图（plan / extract / format / judge），路由规则跟着意图走而不是跟着具体模型走，换模型只改 profile。
3. 把预算和 P95 延迟写进路由条件，超了就降档或提前终止，别让长尾任务烧穿成本。
4. 每周看一次分环节的模型用量报表，路由规则的漂移比想象中快。

## 总结

多模型路由不是省钱技巧，而是工程决策：把「贵而准」和「快而糙」的模型放进各自合适的环节，用规则加观测守住质量底线。在 OpenClaw 里落地并不复杂，复杂的是持续维护判据——先量化，再路由，别反过来。
