## 背景

Agent 要干活，光靠模型本身不够：查数据库、读本地文件、调内部 API，这些能力都得接进来。在 MCP 出现之前，每家的接法都不一样——function calling 的 schema 各自定义，工具发现、鉴权、传输方式全靠各写各的胶水代码。你有 3 个 Agent、要接 5 个工具，理论上就是 15 份适配逻辑，改一处动全身。

MCP（Model Context Protocol）是 Anthropic 在 2024 年底开源的协议，一句话概括：给「模型应用 ↔ 外部工具/数据」这条链路定一个标准接口。工具方按协议写一次 MCP Server，任何兼容的 Host（Agent 运行时、IDE、桌面客户端）都能直接挂载。

## 它到底解决了什么

1. **M×N 变 M+N**。工具方只维护 Server，应用方只实现 Client，两边在协议层对齐，不再互相定制。
2. **统一的上下文原语**。协议把能力拆成三类：Tools（模型可调用的动作）、Resources（可读取的上下文数据）、Prompts（可复用的提示词模板）。边界清晰，Host 知道什么交给模型选、什么直接塞进上下文。
3. **传输与消息标准化**。消息层是 JSON-RPC 2.0，本地走 stdio（子进程），远程走 Streamable HTTP，能力协商和生命周期都有约定。

## 最小上手路径

以给 Agent 加一个「查内部文档」能力为例：

1. 选官方 SDK（Python / TypeScript 都有），起一个最简 Server，先只暴露一个 tool，比如 `search_docs(query)`。
2. 认真写工具的 name、description、参数 schema——这是写给模型看的，不是写给人看的。
3. 在 Host 配置里注册：本地用 stdio 填启动命令，远程填 HTTP 端点。
4. 重启会话，确认工具列表被正确发现，再跑一次真实调用。
5. 观察返回内容是否失控，再决定要不要加分页、截断、鉴权。

半天内能跑通闭环，别一上来就规划十个工具。

## 踩坑点

- **描述含糊，模型就乱选**。description 写「查询数据」这种，模型会在相似工具间瞎猜。要写清楚什么时候该用、什么时候不该用。
- **返回值太大，撑爆上下文**。默认返回全量数据是常见事故源，主动分页或截断，并在描述里说明返回规模。
- **工具一多，选择准确率明显下降**。单 Server 十几个 tool 尚可，几十个就要考虑按场景拆分或合并语义。
- **stdio 模式在 Windows 上注意编码**，子进程输出建议强制 UTF-8，否则中文返回容易乱码。
- **安全别裸奔**。第三方 Server 等于把外部内容注入模型上下文，工具结果里可能藏 prompt injection；文件、数据库类能力务必最小权限，关键操作加一层人工确认。

## 可复用建议

- 工具设计成小而正交的操作，命名精确；错误信息返回模型能读懂、能自我纠正的文本，而不是裸堆栈。
- Server 尽量无状态，状态留在被包装的服务里，方便横向扩展和独立重启。
- 每次调用记录入参和结果摘要，排查时这就是唯一可靠的线索。
- 先用社区现成 Server（文件系统、浏览器、Git 等都有成熟实现）验证场景，确认不够用再自己写。

## 总结

MCP 没有让模型变聪明，它解决的是工程问题：把一次一议的私有集成，变成有契约、可复用、可替换的插件生态。对 Agent 开发者来说，真正的收益是接入成本从「适配」降到「配置」。建议从一个最小 Server 跑通全链路，再决定在自己的体系里铺多深。
