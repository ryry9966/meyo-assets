## 背景

社区运营里最耗时的不是写帖，而是"持续稳定地产出"。我们想把每周的版本更新、精选 issue、社区动态整理成固定栏目，由一个 Agent 自动完成"取材—成稿—发布"的全流程。本文记录基于 OpenClaw + MCP 的完整搭建过程，以及实际跑起来之后遇到的坑。

## 整体架构

系统拆成四层：

1. **触发层**：cron 定时任务，每周触发一次，不做常驻进程。
2. **Agent 层**：OpenClaw Agent，只负责编排和写作，不直接调用任何外部 API。
3. **工具层（MCP Server）**：三个职责单一的工具——`fetch_sources`（拉取 RSS / GitHub Release / issue 列表）、`publish`（调用社区 API 发帖）、`query_state`（查询已发布历史）。
4. **状态层**：SQLite 存发布记录、内容 hash 和失败日志。

核心原则：Agent 只做编排和文案，所有"事实"（版本号、链接、日期）必须来自工具返回值，模型不允许凭记忆补全。

## 实施步骤

1. **先写 MCP 工具，再写 prompt**。工具先行保证输入输出可单独测试。
2. `publish` 接口强制要求 `idempotency_key` 参数（由内容 hash 生成），服务端幂等去重。
3. **先跑两周 dry-run**：完整走一遍流程，产出写入草稿箱而非直接发布。
4. 人工审核 20 篇草稿后，把质量稳定的栏目切自动发布，其余保留审核环节。

## 踩坑实录

**坑 1：重试导致重复发帖。** 社区 API 偶发超时，脚本重试后同一篇帖子发了两次，根因是重试请求没带幂等键。修复：所有写操作强制携带幂等键，服务端按 key 去重，客户端只做有限次指数退避。

**坑 2：模型"编造"版本号。** 早期让 Agent 自己回忆上周更新，结果 Release 里没有的 feature 也写了进去。修复：`fetch_sources` 返回结构化 JSON，prompt 中明确"只允许引用工具返回的事实，缺失字段留空并标注待人工补充"。

**坑 3：单个源挂掉拖垮全流程。** 某个 RSS 源返回 500，异常直接向上抛，整期帖子没有产出。修复：每个源独立 try/catch，失败记录日志并降级跳过，只要有一个源成功就继续出稿。

**坑 4：时区问题。** cron 按 UTC 配置，预期周一早 9 点的发布实际落在下午。国内社区高峰在早 9 点和晚 8 点，定时配置必须显式指定时区，并在日志里打印实际触发时间。

**坑 5：语气漂移。** 跑了一个月后，文案越来越像营销号，"重磅"高频出现。修复：system prompt 里加入负面词清单和 3 篇人工撰写范文，并保持每周一次人工抽检。

## 可复用建议

- 工具要小、要确定性；编排交给 Agent，别把业务逻辑塞进 prompt。
- 一切写操作都要幂等，重试是必然发生的。
- dry-run 阶段不能省，机器产出必须先经人眼。
- 失败要隔离、要降级——自动化系统的可用性取决于最不稳定的那个依赖。
- 结构化日志（触发时间、使用了哪些源、token 消耗）是排障时的救命稻草。

## 总结

这套架构本身不复杂，工作量几乎全在工程细节上：幂等、降级、审核兜底。经验是让 Agent 负责的部分越窄（只写文案、只编排），系统越稳定。目前该栏目已自动运行一个多月，人工介入只剩每周一次的抽检，整体符合预期。欢迎在社区里交流你们的自动化实践。
