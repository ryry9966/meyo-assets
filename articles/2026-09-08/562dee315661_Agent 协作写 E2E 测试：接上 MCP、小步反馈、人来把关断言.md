## 背景

E2E 测试一直是"该做但没人爱做"的活：写一条用例要理解业务流程、定位选择器、处理异步等待，而且 UI 一改就得跟着修，维护成本长期压在人身上。随着 MCP 浏览器类工具普及，Agent 可以直接操作真实页面、读取实际 DOM，"让 AI 起草 E2E"从口号变成了可落地的流程。最近我们把核心链路的用例改为 Agent 起草、人工评审，效率提升明显，但踩的坑也不少，记录如下。

## 问题

直接甩一句"帮我写登录加下单的 E2E 测试"，效果通常很差，常见三种翻车：

1. **凭空想象 DOM**：Agent 没见过真实页面，选择器全是猜的，跑起来一片红。
2. **断言过弱**：只断言页面标题或元素存在，测试永远绿，测不出任何回归。
3. **硬编码等待**：到处塞 sleep，本地能过，CI 里随机挂。

根因是 Agent 缺两样东西：真实页面上下文，和执行后的反馈闭环。

## 做法

1. **接上浏览器 MCP**。给 Agent 挂一个 Playwright 类的 MCP 工具，让它能打开页面、点击、读取实际 DOM。没有这一步，后面全是空转。
2. **准备流程说明，而不是一句话需求**。每条核心链路写一份 10 行以内的步骤文件：前置数据、操作序列、预期结果，放进仓库随代码版本化。
3. **先走一遍，再写用例**。明确要求 Agent 先用浏览器工具手动执行流程、记录真实选择器，再基于观察结果生成 Playwright 脚本，而不是直接从需求文本开始编。
4. **小步执行反馈**。每生成一到两条用例立刻运行，把失败日志原样喂回去修正。千万别攒二十条一起跑——后写的会越漂越远。
5. **人工评审三个点**：断言改错后测试是否会红（验证它真的能失败）、等待是否依赖 auto-wait 而非 sleep、用例之间是否重复。

## 踩坑点

- **Agent 特别爱写"永远绿"的断言**。评审时逐条看每个 expect 是否对应真实业务结果，这是最容易漏的质量洞。
- **文本选择器必碎**。多语言或文案一改就挂。把"优先 data-testid"写成规范文件，随系统提示一起喂给 Agent，作为硬约束。
- **单轮生成数量要克制**。一次超过三条，上下文开始漂移，质量明显下滑。我们后来固定为单轮最多三条。
- **测试数据隔离**。让 Agent 用固定前缀造数、用例末尾清理，否则第二遍重跑就互相污染，看起来像"测试不稳定"，其实是数据没扫干净。

## 可复用建议

- 把「流程说明模板 + 选择器规范 + 断言要求」打包成一份接入文档，新链路只需填空，Agent 侧不用重新调教。
- 跑稳之后可以加一层：CI 失败时把日志交给 Agent 做初步分诊——判断是产品 bug 还是测试腐化，人只处理它拿不准的部分。
- 目标是**少数高价值链路的确定性覆盖**，不是用例数量。Agent 一次给我们生成了四十多条，评审后只留下十二条核心链路，其余全砍了。

## 总结

Agent 写 E2E 的正确姿势不是"全自动生成"，而是**Agent 起草 + 真实环境反馈 + 人工把关断言**：MCP 解决上下文问题，小步执行解决质量问题，剩下的交给约定和评审。这套流程跑了三周，新链路的 E2E 编写时间从大约半天降到一小时，更重要的是，至今没有出现一条"永远绿"的假测试。工具解决的是速度，可信度仍然来自人对断言的把关。
