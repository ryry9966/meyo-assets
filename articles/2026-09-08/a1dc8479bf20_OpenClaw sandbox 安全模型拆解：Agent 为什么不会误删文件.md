## 背景

OpenClaw 里 Agent 最常用的能力就是文件和 shell：读写代码、跑脚本、清理构建产物。权限给得越大效率越高，但 LLM 的输出本质是概率性的——路径解析错、把"清理"理解成"递归删除"，这类事故迟早会碰到。OpenClaw 的回答不是"祈祷模型别犯错"，而是 sandbox 安全模型：让破坏性操作在结构上就很难生效。

## 问题

一个典型危险场景：让 Agent"清理构建目录里多余的文件"。失败方式至少有三种：

1. 相对路径解析出错，从 workspace 根跑到了上级目录；
2. shell 命令拼接出错，`rm -rf "$DIR"` 里的变量为空，展开成 `rm -rf`；
3. Agent 在 workspace 里建了一个指向宿主机的 symlink，再顺着它删东西。

如果只靠提示词约束（"请小心删除"），这三条都防不住。

## 做法：四层防线

**1. 路径规范化 + 根约束。** 所有文件工具的路径先做 realpath（解析符号链接），再校验是否落在 workspace 根内；`..` 和越界 symlink 直接拒绝。这是最关键的一层，防住第 1、3 两种事故。

**2. 能力声明 + 最小授权。** 每个会话声明 `fs:read` / `fs:write` / `fs:delete` / `exec` 等能力，默认全关、按需打开。没有 `fs:delete` 时，删除类调用在 MCP 工具层就被拒，模型连试的机会都没有。

**3. 破坏性命令拦截。** exec 命令执行前过模式匹配：作用于根目录或空变量的 `rm -rf`、`sudo`、`mkfs`、`dd` 写块设备等直接阻断并记入审计日志。这层是兜底，不追求完美，只挡最常见的坑。

**4. 宿主级隔离。** 容器内运行，非 root 用户，workspace 用 rw 挂载、参考资料用 ro 挂载，禁 sudo，配 seccomp。就算前三层全漏，破坏也只发生在容器里。

另外，OpenClaw 默认把"删除"实现为移入 trash 目录而非真删，会话结束前都可恢复。

## 验证步骤

- 在 workspace 放一个 canary 文件，并在系统提示中标注"此文件不可删除"；
- 跑一轮日常任务，检查审计日志中每次写入/删除的路径与 diff；
- 故意用模糊指令做对抗测试："把不要的东西都清理掉"，观察防线是否触发。

## 踩坑点

- **symlink 逃逸**：只在入口做路径检查不够，必须在 realpath 之后判断，否则 Agent 可以"先造链接、再穿透"。
- **rw 挂载真实数据**：容器不是护身符，把真实目录 rw 挂进去等于第 4 层失效，参考目录一律 ro。
- **容器内有免密 sudo**：非 root + 可 sudo 等于没隔离，务必移除。
- **用 shell 拼路径**：文件名带空格、引号时注入风险陡增。文件操作优先走结构化的 fs 工具，shell 只留给真正需要的场景。
- **把提示词当防线**："请不要删重要文件"第 1 次有效，第 50 次会失效。约束必须落在工具和系统层。

## 可复用建议

- **默认拒绝，按需开放**：能力清单从空开始，缺什么加什么；
- **快照先行**：会话开始前给 workspace 打 git commit 或 overlayfs 快照，回滚成本趋近于零；
- **审计日志是刚需**：每条写/删操作记录命令、参数、结果，出事才有得查；
- **trash 语义替代 delete**：把不可逆操作变成可逆操作，比任何拦截都便宜。

## 总结

OpenClaw 不会误删文件，不是因为模型更聪明，而是因为误删在架构上难以发生：路径出不了根、能力拿不到授权、命令过不了拦截，就算全漏也只是在容器里删了一个可回滚快照的目录。给 Agent 权限时，与其信任模型，不如抬高破坏性操作的成本。**防线分层、默认拒绝、可回滚**——这三条放到任何 Agent 项目里都成立。
