## 背景

LLM 本身无状态，会话一关记忆清零。上下文窗口再大，也装不下三个月积累的使用习惯。对 OpenClaw 这类常驻个人助手来说，记忆层几乎是绕不开的：用户希望“我说过一次不吃香菜，它就永远记得”。最近给内部 agent 加偏好记忆，踩了两轮坑，把方案和教训整理出来。

## 问题：为什么“塞进上下文”不是方案

- 全量历史拼进 prompt：token 成本线性涨，且注意力被稀释，关键偏好反而被淹没。
- 只用向量库存对话：检索回来的是“相关的话”，不是“确定的偏好”，模型还要自己脑补。
- 没有更新机制：用户三个月前说不吃辣，现在吃了，旧记忆仍在生效。

本质上，偏好和对话历史是两类东西：前者是结构化、需要增删改的“事实”，后者是可丢弃的“过程”。混在一起存，是大多数记忆系统翻车的起点。

## 做法：读写分离的两条路径

**写路径（记忆沉淀）：**

1. 会话结束（或每 N 轮）用一次廉价模型调用做抽取，输出候选条目：`{type, content, confidence, source_msg_id}`。
2. 去重：新条目与旧条目语义相似度超过阈值时，走“更新”而不是“新增”。
3. 冲突处理：同 type 的偏好按时间戳覆盖，可选保留版本链。
4. 存储：偏好类用结构化存储（KV/JSON，按 user_id 隔离），只有事件类记忆才进向量库。

**读路径（记忆注入）：**

1. 构建会话时读取该用户 top-k 偏好，按 `importance + last_used` 排序，硬性控制在几百 token 内。
2. 向量检索只用于“回忆某次对话”，不参与偏好注入。
3. 记忆被实际引用后更新 `last_used`，长期未用的自动降权或过期。

## 踩坑点

- **抽取太激进**：“我最近在减肥”被存成了永久偏好。给记忆定 TTL，临时状态不进长期库。
- **只做向量库**：碎片化检索让模型自由发挥，容易张冠李戴。偏好必须结构化、可枚举。
- **注入无预算**：50 条偏好全塞进去，模型开始混淆。top-k + 排序必须是硬约束，不是建议。
- **隐私缺位**：记忆库必须按用户隔离，支持单条删除和导出，这是信任问题而不只是合规问题。
- **用户不可见**：加一个 `/memory` 命令让用户查看、手动删改，比任何算法自动修正都有效。

## 可复用建议

- **先显式后隐式**：先支持“记住：xxx”的显式指令加用户确认，跑通全链路，再上自动抽取。一步到位的隐式方案几乎都会先死于噪音。
- **schema 固定五字段**：`id / type / content / confidence / updated_at`，别为了“灵活”存自由文本。
- **建回忆测试集**：20~30 条（“我上次说过什么”），每次改动跑一遍。记忆回归比想象中容易坏，且坏得很安静。
- **用 MCP 就拆成独立 memory server**：agent 侧只依赖接口，后面换存储或加评分策略不动主链路。

## 总结

记忆系统的难点不在“存”，而在沉淀什么、何时失效、如何呈现。结构化的偏好 + 有预算的注入 + 用户可见可删的控制，这三件事做到位，助手才算真的认识你。先简后繁、逐步加自动抽取，是目前验证过性价比最高的路线。
