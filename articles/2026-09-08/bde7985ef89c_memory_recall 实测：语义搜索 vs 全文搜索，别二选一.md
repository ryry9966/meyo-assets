## 背景

给 agent 挂上 memory 插件后，每次对话它都会调 `memory_recall` 去翻历史记忆。最初图省事用了纯语义检索（embedding + 余弦相似度），直到某天问它“HY-204 这个错误码上次怎么处理的”，返回的 top5 全是聊过“报错排查”但和这个码毫无关系的条目。于是花了个周末做了对比实验。

## 问题

两条路线各有明显短板：

- **语义检索**擅长“意思相近”：改写、换说法都能命中；但对错误码、变量名、专有缩写这类精确 token，embedding 会把它们“糊”进语义空间，近义但不相关的条目反而排前面。
- **全文检索**（BM25/FTS）精确匹配稳，可一遇到同义改写、中英混查就哑火。
- 实测下来，记忆条目本身的写入质量对召回的影响，比换检索算法大得多。

## 做法

1. **条目结构化**：写入时不存原始对话，让 agent 先总结成“一句话事实”，每条 ≤200 字，带时间戳、来源和项目 tag。
2. **双索引**：SQLite FTS5 建全文索引（中文需接 jieba 分词），sqlite-vec 建 embedding 索引，模型选 bge-m3（中文友好、跨语言）。个人助手几千条的量级，一个库文件够用。
3. **检索管线**：agent 先把当前需求改写成一条独立查询，不直接拿聊天原文；两路并行各取 top10，RRF 融合排序，叠加时间衰减权重，再按 tag 过滤后取 top5 进上下文。
4. **评测**：手写 30 个召回用例，分三类——同义改写、精确 ID、时间相关。结果：纯语义在改写类约 80% 命中，精确 ID 类掉到 40%；纯全文正好反过来；混合 RRF 三类都稳定在 85% 以上。

## 踩坑点

- **中文分词**：FTS5 默认按空格切 token，中文基本等于不可用，必须换 tokenizer。
- **embedding 语言错配**：早期用英文模型索引中文记忆，跨语言查询召回率直接腰斩。
- **查询词污染**：拿对话原文当 query，语气词和上下文噪音会把排序搅乱，改写这一步不能省。
- **近重复堆积**：同一条记忆的三四个变体把 top5 占满，写入侧要做去重合并。
- **过度设计**：这个量级上独立向量数据库属于杀鸡用牛刀，运维成本远大于收益。

## 可复用建议

- 默认上混合检索 + RRF，别在“哪个更好”上纠结，答案是互补。
- 写入质量 > 检索算法：短、自包含、带 tag 和时间，比调任何超参都有效。
- 维护一个小评测集，任何索引或模型改动先跑一遍再上线。
- 把召回失败的 query 记下来定期人工看，比盲调参数有用。

## 总结

语义搜索解决“换个说法还能找到”，全文搜索解决“精确 token 不丢”。`memory_recall` 的正确姿势是两路并行、融合排序，再配上干净的写入流程——检索层只决定下限，记忆质量才决定上限。
