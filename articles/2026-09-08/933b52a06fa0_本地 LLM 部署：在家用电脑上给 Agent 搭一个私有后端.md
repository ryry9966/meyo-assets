## 背景

用 OpenClaw 做自动化和 Agent 的用户迟早会遇到两个问题：云端 API 在长任务循环里按量计费烧得很快；隐私敏感的日志和文件也不方便外发。在一台家用电脑上部署中等规模的本地模型作为 Agent 后端，是成本和可控性都不错的折中。这篇帖子记录我在 12GB 显存的消费级显卡上部署并接入 Agent 工作流的完整过程。

## 问题

本地模型不是“能跑起来”就算完成。实际要解决三件事：

1. **显存预算**：模型权重 + KV cache + 运行时开销，都要塞进显存；
2. **工具调用质量**：Agent 依赖 function calling，小模型在这块差距很大；
3. **吞吐量**：Agent 一轮任务动辄几十次调用、数万 token，单次回复快没用，tokens/s 才是关键。

## 做法

**1. 盘点硬件，定模型上限。** 12GB 显存跑 14B 级别的 Q4 量化模型是上限；24GB 可以摸到 32B Q4。只有 8GB 的话，优先考虑 MoE 结构的小激活参数模型（如 30B-A3B 一类），权重可部分放内存，激活量小、速度快。

**2. 选推理引擎。** 图省事用 Ollama，一行命令起服务；要精细控制用 llama.cpp 的 llama-server；显存充足且跑批量任务再考虑 vLLM。三者都暴露 OpenAI 兼容接口，接入 OpenClaw 只需在 provider 配置里指向 `http://127.0.0.1:11434/v1` 这类本地地址。

**3. 量化从 Q4_K_M 起步。** Q8 体积翻倍但感知差异很小，Q3 以下工具调用开始不稳定，除非显存极限，别低于 Q4。

**4. 显式设置上下文长度**（最大的坑，见下文）。

**5. 用真实 Agent 负载压测。** 跑一个多轮工具调用任务，记录 tokens/s、工具调用格式错误率、长上下文后的指令遵循能力。单轮问答测不出问题。

## 踩坑点

- **Ollama 默认上下文只有 2K/4K**，Agent 场景必爆。要显式设 `num_ctx`，但注意 KV cache 随上下文线性增长，32K 上下文可能多吃好几个 GB 显存，不够就开 KV cache 量化。
- **部分层卸载到 GPU ≈ 不可用。** “能跑”和“能用”是两回事，权重放内存的部分会把速度拖到 3–5 tokens/s，Agent 循环根本没法用。宁可换小模型全放显存。
- **工具调用格式因引擎而异。** 同一模型在 Ollama 和 llama-server 上的 function calling 行为可能不同，换引擎后必须重测工具调用，别只看对话质量。
- **小模型要调采样参数。** 默认参数下容易复读，建议 temperature 0.6–0.7、top_p 0.9 起步，按实测微调。
- **Embedding 别复用同一个模型。** 记忆检索/RAG 用专门的 embedding 模型（0.5B 级别就够），占用很小。

## 可复用建议

- 显存粗算公式：`参数量 × 每权重字节数（Q4≈0.5）+ KV cache`，再留 1–2GB 给运行时。
- 把压测脚本固化下来：每次换模型/引擎/量化版本，跑同一套 Agent 任务对比，用数据说话。
- 双模型策略：本地处理高频、私密的常规任务，复杂推理仍走云端 API，在 OpenClaw 里按任务路由。
- 记录每次配置变更。本地部署调参频繁，没记录等于反复踩坑。

## 总结

家用电脑跑本地模型做 Agent 后端，现在已经是可行方案，但成败不在“跑起来”，而在显存预算、上下文配置和工具调用质量这三件事。建议先用小模型全显存跑通全流程，再逐步加大规模。欢迎在评论区交流硬件配置和实测数据。
