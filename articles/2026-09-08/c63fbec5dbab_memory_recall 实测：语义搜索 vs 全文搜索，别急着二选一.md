## 背景

OpenClaw 助手跑久了，memory 目录会积累几百条笔记：运维操作记录、项目决策、踩过的坑。`memory_recall` 是把这些旧上下文拉回来的唯一入口，检索策略直接决定“它到底记不记得”。最近把家里的检索层从纯语义换成了混合方案，记录一下数据和踩坑。

## 问题

两个极端各有硬伤：

- **纯语义检索**（embedding + 向量库）：遇到精确 token 就抓瞎。错误码 `ECONNRESET`、配置项 `retry_budget`、路径 `/etc/openclaw/`，被压成向量后几乎没有区分度。
- **纯全文检索**（BM25/grep）：笔记里写“连接被重置”，用户问“网络断了咋回事”，一个词都对不上，零召回。中文分词还会雪上加霜。

我的场景：约 500 条笔记，平均 200 字，查询一半是口语化描述，一半是带精确标识符的排障问题。两头都要接得住。

## 做法

上了混合检索，三步：

1. **双路索引**：BM25 全文索引（jieba 分词 + 自定义技术词典）+ 向量索引（bge-small-zh 量级的中文 embedding，本地跑）。单条笔记一个 chunk，超过 500 字再切。
2. **融合**：两路各取 top-10，用 RRF（Reciprocal Rank Fusion）融合排序，取前 5 进上下文。
3. **写入端配合**：memory 笔记首行放日期 + 关键词标签（如 `2025-01-12 #nginx #证书`），正文写完整叙述。标签行喂全文索引，正文喂向量索引，等于一次双写。

实测：手工标了 50 条“应该被想起”的查询。纯语义召回率约 71%，纯全文约 64%，混合做到 89%。代价是每次 recall 多约 30ms 的索引查询，可忽略。

## 踩坑点

- embedding 对代码标识符几乎无区分度，`retry_budget` 和 `retry_limit` 的向量距离比两句无关的闲聊还近。这类 token 只能靠全文路捞。
- jieba 会把不认识的技术词切碎，要么维护自定义词典，要么对连续 ASCII 串整段保留不切。
- 不切 chunk、整篇进索引的话，top-5 能塞 3000+ token，一次 recall 吃掉小半上下文窗口。单 chunk 控制在 300–500 字。
- 没加时间衰减时，三个月前“用方案 A”的旧决策反复压过上周“已切换方案 B”的新决策。按笔记日期加了个简单的指数衰减加权才压住。
- 改了笔记忘了增量重建索引，表现为“它明明记得却想不起来”，排查一晚才发现是索引陈旧。重建挂到 memory 写入钩子上，别靠手动。

## 可复用建议

- **默认混合，不要二选一。** 语义管“换了个说法”，全文管“精确 token”，是分工不是竞争。
- **写入时就为检索做准备**：关键词行 + 叙述正文双写，比事后调检索参数有效得多。
- **建一个 30–50 条的评估集**，改参数前后各跑一遍。凭感觉调召回，必翻车。
- **top-k 宁小勿大**：recall 是为了省 token，不是烧 token。漏一条还能追问，塞爆窗口是确定性损失。

## 总结

语义 vs 全文在 memory_recall 这个场景里不是选型题，是分工题。助手的记忆查询里精确标识符出现频率远比想象中高，全文路不可省；用户表述又千变万化，语义路也不可省。混合检索 + 结构化写入 + 小评估集，三件事做完，“记不住”基本能压到可接受范围。代码和索引配置都在我的插件仓库里，有需要可以来群里讨论。
