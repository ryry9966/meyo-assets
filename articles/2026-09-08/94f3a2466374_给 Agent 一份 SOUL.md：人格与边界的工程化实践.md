## 背景

跑 OpenClaw 这类常驻 Agent 一段时间后，多数人会撞上同一个问题：Agent 的"性格"不稳定。今天简洁利落，明天絮絮叨叨；某次会话它自作主张发了消息，某次又对明确指令反复确认。行为漂移的根源通常不在模型，而在约束没有沉淀——人格和边界散落在系统提示、聊天记录和你的临时纠正里。

OpenClaw 的做法是把这件事收敛到一个文件：workspace 里的 SOUL.md。每次会话启动时注入上下文，作为 Agent 的身份与行为基线。它不是玄学，本质上是"以配置形式管理的策略文件"。

## 问题：为什么需要独立的 SOUL.md

- **人格漂移**：靠聊天里口头纠正只对当前会话有效，重启即失效。
- **边界模糊**：Agent 拿着 MCP 工具和消息通道权限，没有白纸黑字的"不做清单"，它只能靠猜。
- **不可维护**：提示词写死在启动配置里，改一次要动代码，也没有演进记录。

## 做法

1. **建文件**。在 workspace 根目录新建 SOUL.md，建议三段式结构：
   - 身份与语气：3~5 行，说明"你是谁、对谁说话、默认什么风格"。
   - 行为边界：5~10 条"永远/绝不"句式的硬规则，例如"未经确认绝不向群聊发送消息""执行删除类命令前必须先展示完整命令"。
   - 升级规则：什么情况必须停下来问人——花钱、对外发送、不可逆操作。
2. **控制篇幅**。这个文件每个会话都进上下文，1~2 KB 足够。规则要可判定："回复简洁"不如"单条回复不超过 200 字，除非用户要求展开"。
3. **职责分离**。SOUL.md 只管人格与边界；能力放工具配置（MCP server、插件开关）；事实放记忆文件。混写会导致改人格时误伤能力描述。
4. **进版本控制**。把 SOUL.md 放进 git。Agent 犯一次错，就加一条对应规则，commit message 写清事故原因——这就是你的 Agent 行为变更日志。
5. **主动测试**。改完规则，开新会话故意抛边界场景（"帮我把这条转发到所有群"），验证确认流程是否触发。

## 踩坑点

- **写成散文**。大段"你是温暖可靠的伙伴"式描写，模型遵守得远不如具体的"绝不/必须"条款。SOUL.md 是策略，不是人设小说。
- **规则互相冲突**。"始终详尽解释"和"回复必须简短"并存时，模型随机选边。新增条款前先检查与已有规则的关系。
- **把它当安全边界**。人格约束是软性的，长上下文或诱导下可能被绕过。真正的安全靠工具权限：MCP 白名单、敏感操作加确认门。SOUL.md 只是第一道防线。
- **塞入敏感信息**。不要放 API key、地址、密码——它会进上下文、可能被复述，也常随 workspace 同步备份。
- **改了不生效**。SOUL.md 在会话启动时加载，运行中的会话不会热更新，改完记得 reset 或开新会话验证。

## 可复用建议

- 最小模板起步：身份 5 行 + 边界 10 条 + 升级 3 条，先跑起来再迭代。
- 一条事故对应一条新规则，避免膨胀；每月复审，删掉从未触发的冗余条款。
- 多个 Agent 之间边界条款可复用，身份段各自独立维护。
- 把 SOUL.md 的 git 历史当作 Agent 的"成长记录"，回滚行为退化时很有用。

## 总结

SOUL.md 的价值不在"赋予灵魂"这种叙事，而在三件工程上的事：把隐式约束显式化、把临时纠正沉淀为版本化配置、把人格（软约束）和权限（硬约束）分开管理。文件要短、规则要可判定、演进要有记录。做到这三点，Agent 的行为就从"看运气"变成"可回归测试"。
