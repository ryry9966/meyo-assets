## 背景

OpenClaw 的 cron 任务，本质是**定时把一段自然语言 instruction 喂给 agent 执行**。它和聊天场景有三个关键差异：没有会话上下文、无人值守、产出需要投递（发消息 / 写文件）。这意味着 instruction 不能写成一句"每天帮我看看日报"——它更像留给值班同事的 runbook：写得越像脚本，跑得越稳。

## 问题：我踩过的几类典型失败

1. **指令太泛**："总结我的 GitHub 通知"——agent 不知道筛几条、按什么标准、结果发哪，每次输出格式都不同。
2. **重复播报**：没有去重条件，任务每小时把同样的提醒重发一遍。
3. **依赖"上次"**："只报告上次之后的新增"——但每次触发是独立会话，agent 根本不知道上次是啥，只能全量重报或瞎编。
4. **静默缺失**：没写"无事不发"，于是每天准时收到"今日无异常"。
5. **时区**：宿主机是 UTC，instruction 里写"早上 9 点"，实际下午才触发。

## 做法：一个可以直接抄的七段模板

```text
- 目标：一句话说清做什么、为谁做
- 数据来源：用哪个工具/MCP/文件，路径写全
- 判定标准：什么算"值得报告"，条件必须可执行
  （如：仅含过去 24h 内创建、label 为 bug 的 issue）
- 输出格式：固定模板，如"3 行以内，每行：标题 + 链接"
- 投递目标：发到哪个渠道/会话，不确定就写明
- 静默条件：无满足判定标准的条目时，不发任何消息
- 失败处理：工具报错重试一次，仍失败则发一条带
  错误摘要的消息，禁止自行猜测
```

最关键的一条：**需要跨次运行的状态，不要指望 agent 记得**。让任务自己读写一个状态文件（如 `~/.openclaw/cron-state/xxx.json`），存"上次处理到的时间戳"，每次运行先读再比对，去重问题就解决了。

## 步骤

1. 先手动触发跑一遍，看原始输出是否符合格式，**别直接挂 cron**；
2. 把输出锁死成模板，禁止自由发挥；
3. 补上静默条件和时间戳去重；
4. 挂上 cron，前 2–3 个周期盯着投递渠道观察；
5. 稳定后再拉长周期，或基于模板复制派生新任务。

## 踩坑点

- **频率别贪高**。15 分钟一次的轮询，出错时就是一天 96 条垃圾消息。
- **一个任务一件事**。"平日发日报、周一发周报"请拆成两个任务——instruction 里写 if-else，agent 经常走错分支。
- **条件要可判定**。"重要的消息"没法执行；"包含 @我 或关键词 X 的消息"可以。
- **别要求 agent 记住任何东西**，它每次都是失忆状态。

## 可复用建议

把 cron instruction 当**幂等脚本**来写：同样的外部状态，跑两次结果一致。跨次状态一律落盘，判定标准一律可机读，输出一律有模板。另外建议在任务备注里留一行元信息（用途、创建时间、依赖工具），半年后维护时不至于看不懂自己写过什么。

## 总结

Cron 的 instruction 写作，本质是把"人肉值班经验"翻译成 agent 可执行、可验证的指令。挂上去之前问自己三个问题：**它知道去哪拿数据吗？它知道什么该说、什么该沉默吗？它第二次运行和第一次行为一致吗？** 三个都能答"是"，这个任务就可以放心跑了。
