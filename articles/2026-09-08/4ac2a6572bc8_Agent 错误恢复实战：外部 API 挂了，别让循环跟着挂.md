## 背景

跑过稍复杂的 Agent 自动化的人大概都遇到过：流程里某个外部 API——LLM 供应商、搜索、自家业务接口——突然 503，整个 agent loop 要么原地空转烧 token，要么把报错原文塞进上下文后开始一本正经地胡编。传统后端里这是一类成熟问题（重试、熔断、降级），但 Agent 场景多了个变量：**错误信息本身会成为模型的输入**，处理不好会被模型"消化"成幻觉。

## 问题出在哪

三个典型症状：

1. **原始报错进上下文**。工具把整段 stack trace 抛给模型，它要么试图"修复"一个自己改不了的服务端问题，要么下一轮直接编造一个看似合理的结果。
2. **无上限重试**。模型看到失败就再调一次，没有退避、没有封顶，一个挂掉的下游能把账单和限流一起打爆。
3. **单点阻塞**。一个非关键工具挂了，整条工作流卡死，用户什么都拿不到。

## 做法：分四层处理

**第一层：错误分类 + 消息瘦身。** 在工具封装层（MCP server 或插件里）拦截所有异常，不让原始错误进上下文，转成一句结构化的短消息：

```json
{
  "status": "upstream_unavailable",
  "retryable": true,
  "detail": "search API 503, 3 retries exhausted",
  "suggestion": "use fallback_search or report partial result"
}
```

`retryable` 字段很关键，它替模型做了第一个决策。

**第二层：退避重试，且有预算。** 只对瞬时错误重试：超时、429、5xx。指数退避加抖动，次数封顶（2~3 次），尊重 `Retry-After`。401/403/参数错误是永久失败，重试没有意义，直接走失败分支。

**第三层：熔断。** 连续 N 次失败后把该工具标记为不可用，冷却 60~120 秒，期间 agent 收到"工具暂停"而不是真去调 API。注意熔断状态要放**进程级共享**，而不是每个会话各一份——否则每个新会话都会去撞一次已死的下游。

**第四层：降级与部分成功。** 给 agent 留出路：备选工具（换数据源）、带时间戳的缓存值、或明确输出"这步没做成，其余已完成"。允许部分成功，比强迫 agent 硬凑一个完整结果好得多。

## 踩坑点

- **HTTP 客户端没设超时**。默认配置下一次挂起的调用能把整个 loop 卡死，connect/read 超时和工具级总 deadline 都要有。
- **非幂等操作盲目重试**。对"创建订单"这类 POST 重试会造出重复数据，写操作带幂等键，或干脆不自动重试。
- **模型自作主张改参数"绕过"报错**。它可能把查询词改成空串、数量改成 0。提示词里要明确：失败时不要修改语义，按错误类型处理。
- **重试没加抖动**。多个并行 agent 同时退避、同时再打，等于人造流量尖峰。
- **熔断恢复后直接放全量流量**。半开探测（先放一两个请求）更稳。

## 可复用建议

- 所有外部调用走统一封装的客户端：超时、分类、重试、熔断、计数，一处配置。
- 给模型的错误消息控制在两三行内，只留决策需要的信息。
- 上线前做故障演练：写个固定返回 503 的 mock 工具，看 agent 是优雅降级还是当场表演。
- 盯三个指标：重试次数、熔断触发、降级命中率，比翻日志高效。

## 总结

Agent 的错误恢复本质是系统工程问题，不是提示词问题。核心三句话：瞬时和永久分开处理、一切重试有上限、永远给 agent 留一条"体面失败"的路。API 一定会挂，挂的时候你的 agent 是空转烧钱还是稳稳输出部分结果，取决于有没有提前把这四层做完。
