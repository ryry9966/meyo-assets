## 背景

在社区里很常见的一类自动化流程是：Agent 生成一篇 Markdown，然后发到公众号、知乎、掘金、GitHub Pages 等多个平台。听起来只是“换个地方粘贴”，实际做下来你会发现，生成内容只占 20% 的工作量，剩下 80% 都花在格式适配和发布交付上。

## 问题

LLM 默认输出的是 GitHub 风格 Markdown：表格、任务列表、脚注、行内 HTML 都可能随机出现。而各平台渲染器各自为政：

- 公众号不认 Markdown，只吃带内联样式的 HTML；
- 知乎对 HTML 标签有严格白名单，脚注和复杂表格直接失效；
- 掘金代码高亮规则、表格宽度处理又是另一套。

同一段文本直接投递，结果就是排版崩坏、图片挂掉、代码块变纯文本。更麻烦的是模型输出本身不稳定：fence 不闭合、标题层级混乱、代码块缺语言标注，都是常态。

## 做法

我们的管线分四层，核心原则是**分层解耦**：

1. **规范化层（canonical）**：Agent 输出先过一遍清洗——H1 只保留一个、补齐代码块语言标注、用最长匹配修复嵌套 fence、行内 HTML 剥离或降级为纯文本。不要信任模型输出的格式，这一层是第一道闸门。
2. **AST 转换层**：用 unified/remark 生态把 Markdown 解析成 mdast，所有适配规则写在树操作上。比如“表格超过 6 列转为列表”、“脚注转文末编号”，在 AST 上做既可靠又可测试，比正则替换稳一个数量级。
3. **Renderer 层**：每个平台一个 renderer，负责 canonical MD → 平台格式。公众号输出内联样式 HTML，知乎输出受限 HTML，GitHub 直接透传 MD。
4. **Publisher 层**：负责图片转存、API 调用、重试。外链图片在发布前统一下载、压缩、传到目标图床并替换 URL——热链是事故重灾区，必须单独走资产管线。

进阶做法是把第 2、3 步封装成 MCP 工具：输入 canonical markdown，输出适配结果。这样任何 Agent 都能组合调用，不用在每个 workflow 里重写一遍转换逻辑。

## 踩坑点

- **嵌套 fence 吞内容**：模型偶尔在代码块里再写 ```，规范化时必须用最大长度匹配 fence，否则后半篇全被当成代码。
- **中英混排间距**：转 HTML 后全角半角混排很难看，建议在规范化层统一加盘古之白。
- **宽表格**：移动端必崩。规则要定死：超过 N 列一律降级为列表，不给 renderer 自由发挥的空间。
- **数学公式**：各平台方言互不兼容，要么提前渲染成 SVG，要么明确放弃该平台，别留半成品。
- **发布是异步的**：平台限流和图文审核不可控，publisher 要做成可重试任务队列，不要同步阻塞 Agent 主流程。

## 可复用建议

- **Golden file 快照测试**：准备几篇覆盖全要素的样例（表格、代码、脚注、图片、任务列表），每次改 renderer 跑 diff，防止“修 A 坏 B”。
- **规则配置化**：用“平台 × 元素 × 策略（保留/降级/删除）”的配置表登记所有适配规则，新平台接入只加配置不写死代码。
- **canonical 层保持纯净**：平台特判全部下沉到 renderer，一旦规范层出现 if 公众号，管线就开始腐烂。

## 总结

这条管线的核心不是“转换”这个动作，而是分层：生成层只管内容，canonical 层保证一致，renderer 消化平台差异，publisher 处理交付。每层独立可测、MCP 工具化之后，新增一个平台就是新增一个 renderer + publisher，成本可控，Agent 侧完全无感。
