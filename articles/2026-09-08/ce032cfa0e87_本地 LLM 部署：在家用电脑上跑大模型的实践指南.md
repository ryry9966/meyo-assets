## 背景

Agent 自动化跑起来之后，最先膨胀的是 token 账单。社区里不少工作流——定时摘要、工单分类、MCP 工具路由——单次请求不长，但一天几百上千次调用，全走云端 API 既贵，又把业务数据送了出去。把一部分流量切到本地模型，是很多人的第一反应，但真正落地时踩的坑比想象多。

## 问题

家用电脑跑大模型，核心矛盾是三件事：

1. 硬件预算有限，显存/内存决定能跑哪个量级的模型；
2. Agent 场景强依赖工具调用（function calling），而很多本地模型在这块表现不稳定；
3. 上下文长度、量化精度、推理速度三者互相牵制，没有免费的午餐。

## 做法

我的环境：Ryzen 7 + 32GB 内存 + RTX 4060Ti 16G，供参考。

**第一步：选推理框架。** Ollama 上手最快，llama.cpp 控制粒度更细，LM Studio 适合先摸底。三者都提供 OpenAI 兼容接口，接入 OpenClaw 只需把 base_url 指到 `http://localhost:11434/v1` 这类本地端点，插件侧几乎不用改。

**第二步：选模型和量化。** 优先选社区验证过 tool calling 的模型，如 Qwen2.5 系列、DeepSeek-R1-Distill。量化从 Q4_K_M 起步，别低于 Q4，否则结构化输出容易崩。经验估算：Q4 的 7B 模型约占 5GB 显存，14B 约 9GB，再留 20% 余量给 KV cache。

**第三步：调上下文窗口。** 默认 num_ctx 往往只有 2048/4096，Agent 场景塞 system prompt 加工具描述很快就爆。Ollama 里显式设 `num_ctx=8192` 或更高，同时注意 KV cache 会额外吃显存。

**第四步：分层路由。** 别把所有请求压给本地模型。我用 7B 做意图识别和简单摘要，14B 处理复杂推理，敏感度低但本地跑不动的请求 fallback 回云端 API。路由逻辑放在 OpenClaw 插件层做成配置项，整体成本降了约七成。

## 踩坑点

- **工具调用模板不匹配**：同一模型，chat template 不对时 function call 直接失效或输出残缺 JSON。升级模型版本后务必重测整条工具调用链路。
- **显存不够触发 CPU offload**：速度从 40 token/s 掉到 3 token/s，比 API 还慢。用 `nvidia-smi` 盯住占用，宁可换小一档的模型。
- **量化过狠毁掉结构化输出**：Q3 以下模型生成 JSON 经常断在半截，Agent 解析工具参数就报错。要跑 Agent，Q4 是底线。
- **超时和重试没配**：本地推理高峰期会排队，客户端默认超时太短会把慢误判成失败。

## 可复用建议

- 先用云端 API 跑通全流程作 baseline，再逐模块切本地，方便归因。
- 建一个 20 条左右的典型请求基准集，每次换模型或量化版本跑一遍，记录延迟和工具调用成功率。
- 显存预算宁可保守：模型文件大小约等于显存占用，另留 2–4GB 给上下文。
- 路由规则做成可配置项而非硬编码，后续换模型不用动业务逻辑。

## 总结

本地 LLM 不是要替代云端，而是在 Agent 高频调用场景里做一个成本和隐私都可控的第二梯队。正确的顺序是：先把工具调用链路跑稳，再谈量化档位和吞吐优化。欢迎在社区贴出你们的硬件配置和实测数据，攒一份真实的选型参考。
