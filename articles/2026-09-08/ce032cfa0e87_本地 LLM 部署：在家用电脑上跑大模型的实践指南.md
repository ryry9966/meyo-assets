## 背景

做 Agent 和自动化这条线的人，迟早会遇到两个问题：一是调试 prompt 和工具调用链路时，API 费用肉眼可见地涨；二是任务上下文里经常带私有数据，过云端总有点不踏实。本地跑一个模型不是要替代旗舰模型，而是给开发过程提供一个免费、私密、可以反复折腾的实验场。这篇文章记录我在一台 16GB 显存的台式机上的完整部署过程，面向想把本地模型接进 OpenClaw / MCP 工作流的用户。

## 问题

真实的门槛不是"能不能跑"，而是四个具体问题：家用硬件能承载多大的模型；选什么运行时；量化到什么程度不伤 agent 的工具调用；上下文和并发怎么配才不会半路翻车。

## 做法

**1. 摸清硬件。** 显存是硬约束。经验值：Q4_K_M 量化的 7B 模型权重约 4.5GB，加上 KV cache 和运行时开销，8GB 显存舒服跑 7B，16GB 跑 14B，24GB 以上再考虑 32B。纯 CPU 也能跑，吞吐低，只适合异步批处理，交互式 agent 会很煎熬。

**2. 选运行时。** Ollama 上手最快，LM Studio 有图形界面，vLLM 适合并发和长上下文。三者都提供 OpenAI 兼容接口，agent 侧只需改 base_url，迁移成本几乎为零。

**3. 选模型。** 结合中文能力和工具调用，Qwen 系列是本地方案的稳妥选择，7B/14B 档位性价比最高。量化优先 Q4_K_M——Q8 在小模型上收益有限，显存却几乎翻倍。

**4. 接入 agent。** 把 base_url 指向本地服务的 `/v1` 端点，模型名填运行时里的 tag。关键一步是确认模型支持 structured output，否则 MCP 工具的 JSON schema 参数经常被编造。

**5. 用真实任务压测。** 准备 3~5 个你 agent 的典型任务（必须含工具调用），跑通并记录 token 速度和成功率，这比任何跑分榜都可信。

## 踩坑点

- **默认上下文太小。** Ollama 默认 `num_ctx` 只有 2048/4096，agent 场景几乎必爆，务必显式设置；且上下文越大，KV cache 吃显存越快，预算要重算。
- **小模型 function calling 不稳。** 7B 在工具多、参数复杂时会漏字段或幻觉参数。工具收敛到 5 个以内、用 JSON schema 强约束输出，成功率提升明显。
- **量化伤工具调用。** Q4 以下不要碰；同一任务在 Q4_K_M 和 FP16 上可能差出一截，换量化后必须重跑评测。
- **并发默认排队。** agent 并行发起多个工具调用时会互相阻塞，注意 `OLLAMA_NUM_PARALLEL` 这类参数。
- **显存预算别只算权重。** 把 KV cache、系统占用、浏览器都算进去，留 1~2GB 余量，否则跑到长上下文必 OOM。

## 可复用建议

- **建立自己的评测集**：5 个固定的 agent 任务，每次换模型、换量化、改参数都跑一遍，结果可对比、可回滚。
- **分层用模型**：路由、摘要、格式化交给 7B，规划和复杂推理交给 14B/32B，通过不同端点挂在 agent 的不同节点上，本地也能做混合调度。
- **吞吐红线**：低于 15 token/s 的组合不建议用于交互式 agent，单次工具调用的等待会把体验拖垮。
- **配置版本化**：模型 tag + 量化等级 + num_ctx + 温度一起记录，出问题时能快速定位是模型变了还是配置变了。

## 总结

本地部署的价值不在于替代云端旗舰，而在于给 agent 开发一个零成本、数据不出门的沙盒。**7B~14B + Q4_K_M + OpenAI 兼容接口**，是家用电脑上投入产出比最高的起点。先跑通你的真实任务，再谈优化。
