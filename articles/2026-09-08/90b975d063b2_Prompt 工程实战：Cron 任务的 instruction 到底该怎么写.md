## 背景

OpenClaw 的 cron 能力让 Agent 具备了"定时值班"的可能：每天早八点跑一次晨报，每小时巡检一次日志，每周整理一次待办。我们实际落地最多的是三类：定时汇总、定时巡检、定时提醒。

但用起来会发现一个现象：同一个 Agent，对话时表现很好，一旦挂上 cron，产出就开始飘——有时跑题，有时没有产出，有时自作主张做了多余的事。

## 问题出在哪

聊天 prompt 和 cron instruction 本质上是两种东西：

1. **聊天是交互式的**，Agent 不清楚可以反问；cron 是发射后不管，跑的时候没人值班，反问等于任务失败。
2. **聊天有上下文**；cron 大多起在全新 session 里，它不记得昨天跑过什么。
3. **聊天的结果给人看就行**；cron 的结果要被投递到频道或写入文件，格式不稳定，下游就没法消费。

所以 cron instruction 的定位是：写给一个"零上下文、无人值守、输出要交接"的执行者的一次性任务书。

## 做法：五段式模板

我们内部收敛出一个骨架，新任务基本照抄：

1. **时间基准**：明确"今天"怎么算、时区是什么。Agent 对日期的默认感知不可靠，晨报类任务尤其要写死规则。
2. **输入来源**：数据从哪来（哪个文件、哪个订阅列表），禁止自行扩展搜索范围。
3. **任务边界**：只做哪些事，并明确"不要做的事"（不要修改文件、不要发送计划外消息）。
4. **输出格式**：固定结构，比如"三行摘要 + 数据来源 + 异常项列表"，方便人和下游脚本消费。
5. **交付与异常**：结果写到哪、失败怎么办——要求显式报告失败原因，而不是回一句"任务完成"。

对比一下：

反例：

> 帮我看看今天的新闻，整理一下发给我。

正例（节选）：

> 以系统当前时间为准，生成今日（北京时间）晨报。仅使用 workspace 中 feeds.md 列出的订阅源。输出固定三部分：1) 三条最重要条目，各一句话摘要；2) 与 AI Infra 相关条目列表；3) 数据源异常说明。不要访问列表之外的站点。若任一源拉取失败，在第三部分列出失败项与原因。

前者每次跑出来的范围、颗粒度都不一样；后者连续两周产出基本稳定。

## 踩坑点

- **隐式状态假设**：instruction 里出现"接着上次的""和昨天一样"，大概率翻车，每次运行都是独立任务。
- **边界缺失**：不写"不要做什么"，Agent 会热心过头，巡检任务顺手改配置。能只读就只读。
- **输出格式自由发挥**：今天列表明天散文，下游解析直接挂。格式必须写成硬约束。
- **硬编码易变值**：日期、路径不要写死在 instruction 里，放到 workspace 的数据文件中让任务去读。
- **instruction 与投递配置脱节**：cron job 的 delivery 设置和 instruction 里的交付描述要对齐，两边各说各话最容易出"跑完了但没人收到"。
- **没做 dry-run**：加完排程就去睡觉，第一次失败三天后才发现。先手动单次触发验证，再启用。
- **长任务重叠**：上一轮没跑完下一轮又触发。切小任务或拉长间隔，instruction 里也可要求控制产出规模。

## 可复用建议

- 把模板沉淀为 workspace 里的一个文件，新任务照抄骨架只填变量。
- instruction 也进版本管理，改了排程没改 prompt（或反之）都是排查成本。
- 每个任务写一条最小验收标准附在 instruction 末尾，让 Agent 自检后再交付。
- 交付目标收敛到固定渠道，方便回溯历史产出。

## 总结

Cron instruction 的核心不是"写得更详细"，而是换一种写作对象：它不是给对话伙伴的提示，而是给无人值守执行器的任务书。时间基准、输入边界、输出契约、异常路径，四样写清楚，定时任务的稳定性就从"看运气"变成"看配置"。
