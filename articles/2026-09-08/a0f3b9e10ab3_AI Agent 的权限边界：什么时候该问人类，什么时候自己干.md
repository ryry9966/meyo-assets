## 背景

Agent 能挂的工具越来越多：本地 shell、文件读写、MCP 接进来的各种服务、消息通道、定时任务。权限问题早就不是"要不要让它执行命令"，而是变成了一个更细的问题：**哪些事它可以直接干，哪些事必须停下来问人**。

实践中大多数人会走两个极端：要么全放开——省事，直到某天它把该留在本地的内容发了出去；要么步步确认——安全，但坚持不了三天，你就开始无脑按 y，确认框形同虚设。

## 问题

真正的难题不是"问不问"，而是三个具体的失效模式：

- **问得太频繁** → 审批疲劳，用户沦为橡皮图章，比不问更危险；
- **问得太少** → 不可逆操作（删数据、对外发消息、花钱）无人把关；
- **问的方式不对** → 弹一句"是否允许？"，用户没有任何判断依据。

还有一个容易忽略的点：权限边界是**工程问题，不该交给模型自己判断风险**。模型自评不稳定，规则必须是确定性的、写在配置里的。

## 做法：按爆炸半径分级

给每个工具/操作标两个维度：影响范围（本机 / 项目内 / 对外）和可逆性。然后分四档：

- **L0 只读**：读文件、查状态 → 直接干，不用问；
- **L1 可逆写**：工作区内写文件、跑测试 → 直接干，记日志；
- **L2 对外副作用**：发消息、调第三方 API、部署到 staging → 先执行但必须通知，或 dry-run 后执行；
- **L3 不可逆/高危**：删除、支付、对外发布、批量操作、碰凭证 → 必须确认。

落地步骤：

1. 盘点所有工具调用面，逐一归类到 L0–L3。接 MCP server / 插件时，把分级写进工具描述里，别留在脑子里。
2. 写一份声明式的权限策略文件，进版本库，像代码一样 review。
3. L3 的确认内容必须包含：具体命令或目标、diff / 影响说明、回滚方式。"允许吗"三个字没有意义。
4. 全量记录工具调用与审批结果，事后能回答"它当时为什么这么干"。
5. 定期复盘日志：审批通过率接近 100% 说明问得太多，接近 0% 说明该重新收权了。

## 踩坑点

- **审批疲劳是最常见的死法。** 确认框多到用户无脑点同意时，这层防线已经失效。宁可 L3 少而准。
- **授权粒度太粗。** 给整个 MCP server 授权等于给它的所有工具授权，应该按单个工具控制。
- **组合调用绕过边界。** 两个 L0 操作串起来可能变成 L3：先读本地文件，再发到外部。边界检查要在调用链层面再做一次，尤其是涉外的最后一步。
- **确认没有过期时间。** 半小时前的批准未必适用于现在的上下文，超时应重新询问。
- **权限只增不减。** 每次出问题就加白名单、从不回收，一年后等于全放开。

## 可复用建议

- 默认拒绝危险动词（delete / send / pay / deploy 类），白名单显式放开；
- 把"问"和"告知"分开：L2 可以先斩后奏但要留痕，L3 必须先批后动；
- 沙箱隔离 + 用量/预算上限兜底，作为策略规则之外的最后一道防线；
- 策略文件和审批日志都是资产，定期 review 比一次性设计更重要。

## 总结

权限边界不是配一次就完事的开关，而是需要持续迭代的产品决策。目标不是让 Agent 零提问，也不是让它事事请示，而是让它**只在真正不可逆、影响超出沙箱的时刻打扰你，且每次提问都带着足以判断的信息**。做到这一点，"自己干"和"问人"就不再是玄学的信任问题，而是一条可以被评审、被回滚、被改进的策略问题。
