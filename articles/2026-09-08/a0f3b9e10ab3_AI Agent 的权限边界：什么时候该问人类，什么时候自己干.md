## 背景

Agent 接上 MCP 和插件之后，真正的分水岭不是"能不能完成任务"，而是"每一步工具调用要不要经过人"。社区里反复出现两种极端：一种 Agent 每写一个文件都要确认，用户全程陪跑，自动化形同虚设；另一种直接连上生产库和邮件通道，一次误操作就是事故。权限边界本质上不是能力问题，而是风险管理问题。

## 问题：边界画在哪里

判断"问不问"，建议只看两个维度：

- **可逆性**：这个操作能不能被撤销？
- **影响半径**：出错时波及的是草稿目录，还是真实用户？

组合起来就是一张四象限决策表：

| | 低影响半径 | 高影响半径 |
|---|---|---|
| 可逆 | 自动执行 | 自动执行 + 预算限制/分批 |
| 不可逆 | 自动执行 + 审计日志 | 必须人工确认 |

读文件、查库、拉 issue 列表，让 Agent 自己干。批量改配置、群发消息、删数据、付款，问人。

## 做法：把规则落进工程

1. **给每个工具标注副作用元数据**。在 MCP 工具的 description 里写清楚：readonly 还是 write、是否可逆、影响范围。模型选对行为的前提是它知道自己在调什么。
2. **实现统一的确认网关**。把"需要确认"做成策略层，而不是散落在各处 prompt 里：命中规则就暂停执行，把变更 diff、影响范围、回滚方式渲染给用户，等明确批准后才放行。
3. **高风险操作先 dry-run**。写操作支持 plan/apply 两段式，Agent 先产出变更计划，人批准后再 apply。
4. **加预算和批处理**。即使是可自动执行的高影响操作，也限制单次影响行数、调用频率、费用上限，超出即降级为人工确认。
5. **全量审计日志**。每次工具调用记录参数、结果、是否经过确认。出事之后，你唯一能依赖的就是这份日志。

## 踩坑点

- **确认疲劳**：确认弹得太频繁，人就会无脑点"允许"，确认机制退化成橡皮图章。宁可收紧默认规则，也别让确认变成噪音。
- **确认上下文不足**：只弹一句"是否继续？"等于没问。必须带上将要执行的具体变更和回滚手段，让人能在 10 秒内做出判断。
- **会话级放行被滥用**："本次会话总是允许"要限定到具体工具和参数范围，不能一把梭到所有写操作。
- **重试导致重复副作用**：网络超时后 Agent 重发请求，同一封邮件发了两遍。外部写操作必须带幂等键。
- **工具描述含糊**：一个叫 `update_record` 的工具到底是更新、upsert 还是整条覆盖？描述不清，边界规则设计得再好也没用。

## 可复用建议

- **上线初期默认从严**：全部写操作要求确认，跑两三周攒审计数据，再把低事故率的操作逐步降级为自动执行。
- **权限矩阵做成配置文件**，不硬编码，按项目、按环境（dev/staging/prod）分层管理。
- **不可逆操作强制配套撤销工具**：没有 rollback 手段的操作，不允许进入自动执行白名单。
- **定期回顾审计日志**：如果发现 95% 以上的人工批准都是无脑通过，说明规则该放宽了；反之出现犹豫和撤销，说明降级太快。

## 总结

权限边界不是一次性画好的线，而是一个随信任数据演进的策略系统。原则很简单：可逆且影响小，就让 Agent 自己干，用日志兜底；不可逆或影响大，就把决策权留给人，并把决策所需的上下文准备到位。Agent 自主性的提升，应该来自审计数据支撑下的策略放宽，而不是来自一次胆大的默认配置。
