# AI Agent 的权限边界：什么时候该问人类，什么时候自己干

## 背景

在 OpenClaw 上做插件和自动化实践，给 Agent 接上 MCP 工具之后，最头疼的往往不是它“不会干”，而是不知道它“该不该自己干”。读个文件、跑个测试，每步都问人纯属浪费双方时间；但静默地删库、给客户发消息、在生产环境执行迁移，出一次事就够喝一壶。这本质上不是模型能力问题，而是权限设计问题。

## 问题：两个方向都会翻车

实践中常见的两种失败：

- **过度放权**：Agent 拿着一个大而全的 `execute` 工具，读和删不分家，出了事无法追溯是哪一步放开的口子。
- **过度请示**：每一步都弹确认。人被问了二十次之后就会无脑点“同意”——这就是**确认疲劳**。确认疲劳等于没有边界，只是把责任转嫁给了点鼠标最快的那个人。

所以目标不是“多问”或“少问”，而是把稀缺的确认次数花在真正危险的操作上。

## 做法：一个可落地的分级框架

### 1. 给每个工具标两个属性

- **可逆性**：操作错了能不能撤销？git 能兜底的文件修改可逆；发出去的消息、扣掉的款不可逆。
- **影响范围**：只在本地 workspace，还是会触达外部系统、生产环境、真实用户？

### 2. 按三档划分权限

| 档位 | 判定 | 策略 |
|---|---|---|
| T0 自动执行 | 只读、沙箱内操作 | 直接干，不问 |
| T1 自动但留痕 | workspace 内可逆写操作 | 直接干，全量审计日志 |
| T2 必须问人 | 不可逆、外部副作用、涉及凭据、生产环境 | 挂起等确认 |

### 3. 在工具层落实，而不是在 prompt 里

“请不要删除文件”这种约束写在 system prompt 里是不可靠的，模型偶尔会忘。边界必须由插件/MCP 层强制：

- **读写分离**：只读工具和写操作拆成不同工具（甚至不同 MCP server），不提供通用执行入口。
- **危险工具默认 dry-run**：`apply=false` 时只返回 diff 预览，Agent 和人都能先看再批。
- **确认闸门做成工具**：T2 操作不直接执行，而是返回“待审批”状态，由外部进程注入批准后才真正运行。
- **量化预算**：金额上限、批量文件数、请求频率写进配置文件，随代码一起评审，不要写进提示词。

### 4. 让“问”变得高效

问人的时候必须带上五要素：要做什么、作用于哪个目标、关键参数、影响范围、如何回滚。一句“可以继续吗？”得到的只会是无脑的“可以”。

## 踩坑点

- **确认疲劳**：统计一下 Agent 的提问频率，一旦人类开始橡皮图章化，先收窄 T2，再用 T1 的日志抽查兜底。
- **会话级授权永久化**：“本次会话允许”经常演变成“永远允许”。给授权加过期时间和作用域（单次 / 单目标）。
- **子 Agent 静默继承权限**：主 Agent 管得很好，它派生的子任务却拿着完整工具箱。派发时要显式收窄。
- **审计日志没人看**：T1 留痕的价值取决于抽查。固定节奏（比如每周）过一遍日志，发现“居然自己干了这事”就升档，发现“这事也来问”就降档。

## 可复用建议

1. 默认允许可逆的读，默认拒绝不可逆的写。
2. 每次提问必含五要素：动作、目标、参数、影响范围、回滚方案。
3. 权限分级是配置和代码，进版本管理、走评审，不进 prompt。
4. 预算类约束用数值写死在配置里，别指望模型“自觉控制在 100 元以内”。
5. 边界是活的：用审计数据持续调档，而不是一次定终身。

## 总结

权限边界的本质不是“信不信任模型”，而是**让错误的代价变得便宜**。可逆、局部、留痕的操作放手让 Agent 干；不可逆、外部、花钱的操作停下来问人，且每次都问得让人能负责任地回答。确认是一个稀缺资源，省着用，用在刀刃上。
