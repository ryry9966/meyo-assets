## 背景

Agent 接上 MCP 和插件之后，能力就从"聊天"变成了"动手"：读文件、发 HTTP 请求、改数据库、调内部 API。我们把 OpenClaw 接进日常工作流的第一周就撞上了这个问题——哪些事它自己干，哪些必须停下来问人？

早期做法很粗糙：要么全放开（出过一次误删共享目录的事故），要么全加确认（人变成点"确认"的机器，第三天就没人细看了）。这篇帖记录后来收敛出来的一套划分方法，不算完美，但可复现。

## 问题

权限边界不是"信不信任模型"的问题，而是两个具体的失败模式：

1. **问得太多**：每步都确认，人进入橡皮图章模式，审批形同虚设，效率归零。
2. **问得太少**：不可逆操作（删数据、对外发消息、花钱）一旦自动执行，重试和幻觉会被放大成事故。

核心矛盾在于：审批的边际价值随频率递减，而风险随操作的不可逆程度递增。所以边界必须按**操作属性**划，而不是按心情或一刀切。

## 做法：三个维度 + 四个层级

我们给每个 MCP 工具打三个标签：

- **可逆性**：能否撤销？改本地草稿可逆；删远端数据、发外部消息基本不可逆。
- **爆炸半径**：只影响会话临时目录，还是共享仓库、生产环境、外部第三方？
- **输入确定性**：Agent 是在执行明确指令，还是在自行解释模糊需求？

据此分四层：

| 层级 | 定义 | 策略 |
|---|---|---|
| L0 | 只读 | 自动执行，仅记录 |
| L1 | 可逆写、半径小 | 自动执行 + 全量审计日志 |
| L2 | 可逆但半径大 / 参数有歧义 | 先产出 plan/diff，人批一次，批的是计划不是单步 |
| L3 | 不可逆、涉外部、涉钱 | 硬闸门：Agent 只准备材料，人执行或二次显式确认 |

落地到配置层面：工具白名单**按层级配，而不是整台 MCP server 一把放行**；L2 的确认请求必须携带具体 diff 和影响范围，禁止"我可以继续吗"这种无法审查的问法；每次工具调用记录层级、参数、结果，方便回溯。

## 踩坑点

- **确认疲劳**：L2 判得太宽，一天弹几十次确认，很快有人无脑点同意。改成按计划批量审批后，单日确认降到个位数，审批质量反而上来了。
- **模糊提问**：Agent 曾问"可以清理这些文件吗"，人批了，但它对"清理"的理解和人不一致。确认请求必须含具体命令。
- **重试放大副作用**：L1 写操作遇错自动重试，重复创建了三份资源。写类工具尽量幂等，或加去重键。
- **审批状态跨会话丢失**：长任务上下文被压缩后，Agent 忘了自己被拒过，换个说法又来一遍。拒绝理由要写入持久状态，不能只留在对话历史里。
- **环境漂移**：测试环境全放开、生产忘了收紧。靠配置模板加启动时校验兜底。

## 可复用建议

1. 默认拒绝、显式白名单；新工具先按 L2 观察一段时间再决定降级。
2. 批"计划"不批"单步"，一次审查一个完整执行方案。
3. 所有自动执行必须可审计：哪个会话、调了什么、参数、结果。
4. 每周抽查一次 L0/L1 自动执行日志，发现误判就调整分层，而不是临时加确认。
5. 分层标准写成团队文档，Agent 系统提示里只引用结论，避免每轮重复解释。

## 总结

权限边界的本质，是把"信任"翻译成工程参数：**可逆性决定能不能自动，爆炸半径决定要不要确认，确定性决定确认的形式**。边界不是一次定死的，靠审计日志和定期抽查持续校准。Agent 自主性的提升，应该来自层级判定的精确化，而不是来自悄悄放宽闸门。
