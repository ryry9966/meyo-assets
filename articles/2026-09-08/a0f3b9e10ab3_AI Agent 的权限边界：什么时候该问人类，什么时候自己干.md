## 背景

用 OpenClaw 这类 agent 框架的日常状态是：给模型挂一排 MCP 工具——读写文件、跑 shell、调 HTTP、发消息——然后让它自主完成任务。工具一多，绕不开的问题就是权限边界：哪些动作 agent 可以直接干，哪些必须停下来问人。

边界划太紧，agent 每步都来确认，自动化就失去了意义，人也会陷入"无脑点确认"的疲劳；划太松，一次误操作可能就是删库、发错频道、超额消费。这两种失败我都踩过。

## 问题：两个失效方向

- **过度请示**：对 `ls`、`cat` 这类只读操作也请求确认，十步的任务被打断七八次。
- **过度自主**：模型在长上下文里"忘了"提示里的约束，直接执行了删除命令，或把草稿发到了生产频道。

一个关键认知：靠系统提示写"删除前请先问我"是不可靠的。约束必须落在工具层，提示词只是补充。

## 做法：按两个维度分级

我现在的做法是把每个工具（必要时到参数级）按两个维度打标签：

1. **可逆性**：能不能撤销？本地文件编辑可以回滚，发出去的消息、付出去的钱不能。
2. **影响半径**：只影响 agent 自己的工作区，还是会触达别人或生产环境？

由此分四档：

| 档位 | 例子 | 策略 |
|---|---|---|
| 只读 | ls、搜索、查询 | 自动执行，记日志 |
| 可逆写 | 编辑工作区文件、写草稿 | 自动执行，留审计 |
| 高危写 | 删除、批量修改、git push | 阻断，请求确认 |
| 不可逆外发 | 发消息、调付费 API、部署 | 确认 + 展示完整上下文 |

落地要点：

- **在 MCP 服务端配置权限，而不是在提示里求模型**。对危险工具设置 require_approval，让模型根本拿不到"直接执行"的路径。
- **高危工具必须带 dry-run**。删除类操作先列出将影响的文件，确认后才真删。
- **确认请求要有信息量**。不是"是否继续？"，而是 diff、目标地址、回滚方式一次给全，让人 10 秒内能做判断。
- **所有调用全量记日志**，包括自动放行的，出事后才能回放。

## 踩坑点

- **只读工具会组合成写**。agent 读了本地的凭证文件，再调一个"只读"的外部搜索 API，参数里带上了密钥——组合起来就是数据外泄。所以外部调用一律按不可逆外发处理，敏感路径进 denylist。
- **确认疲劳**。早期我把"写文件"也设成需确认，一周后我开始机械地点"是"，确认形同虚设。宁可放宽可逆操作，也要保证高危确认时人是清醒的。
- **子任务绕过权限**。主 agent 把危险操作委托给插件或子 agent 执行，权限检查没有传递。工具层限制必须覆盖所有执行路径，不能只拦主对话。
- **确认框塞太满**。放整个会话摘要进去，人根本不会看。确认框只放关键事实。

## 可复用建议

- 默认规则一句话：**本地可逆的自动干，触达外部或不可逆的必须问。**
- 新接入一个 MCP 工具，先按四档归类再启用，不要默认全开。
- 给每个写类工具设计 dry-run，这是投入产出比最高的一件事。
- 每次出事故后回头收紧一档，而不是试图一次性设计"完美权限"。

## 总结

权限边界不是提示词工程，是工具层的工程问题。核心动作就三个：按可逆性和影响半径分级、把分级固化进工具配置、让每次确认都携带足够的判断信息。自动化价值来自 agent 能自己干的部分，信任价值来自它明确知道哪里必须停下。
