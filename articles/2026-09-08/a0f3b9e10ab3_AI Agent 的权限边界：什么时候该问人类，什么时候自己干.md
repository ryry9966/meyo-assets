## 背景

Agent 接上 MCP 和插件之后，能力从"聊天"变成了"动手"：读写文件、跑 shell、调外部 API、往群里发消息。这时候一个绕不开的问题出现了——哪些动作它可以直接做，哪些必须先问人。

实践中两个极端都很常见：权限收得太紧，每一步都弹确认，人沦为点击机器，Agent 的效率优势被抵消；权限放得太开，一次误操作就可能删掉目录、把消息发到错误的频道、或者烧掉一笔付费 API 账单。

## 问题

很多人用"这个操作危不危险"来描述边界，但这太模糊了。更麻烦的是，让模型自己判断"要不要问人"并不可靠：上下文一长判断会漂移，任务一紧它就倾向于先斩后奏。**提示词约束不等于系统约束**，这是所有权限设计的出发点。

## 做法

我们用两个可量化的维度给工具操作归级：**可逆性**（能否撤销）和**影响范围**（波及谁）。

| 级别 | 特征 | 例子 | 策略 |
|---|---|---|---|
| L0 | 只读 | 读文件、查询状态 | 自动执行 |
| L1 | 可逆写 | 改有 git 覆盖的文件、写草稿 | 自动执行 + 记录 |
| L2 | 难逆低危 | 发消息、建 PR、写外部文档 | 预授权清单 + 事后通知 |
| L3 | 难逆高危 | 删除、外发、付款、生产变更 | 必须人工确认 |

落地四步：

1. **接入新工具先归级**。每个 MCP 工具上线前，按上表定级，写进工具注册配置，而不是靠提示词嘱咐。
2. **确认时给足上下文**。L3 的确认请求要带上 diff、目标地址、影响范围，让人 10 秒内能判断，而不是一句"我要执行某命令，可以吗"。
3. **L2/L3 先 dry-run**。先输出执行计划预览，通过后再真跑。
4. **硬护栏放系统层**。路径白名单、金额上限、时间窗，在工具层做参数校验，提示词只负责解释。

## 踩坑点

- **确认疲劳**：问得太频繁，人会无脑点"允许"，权限系统形同虚设。宁可分级细一点，减少低价值确认。
- **确认无信息量**：不展示具体命令和改动范围的确认，等于让人闭眼签字。
- **护栏写进提示词**：提示词会被注入、被摘要压缩，涉及钱和删除的规则必须落在代码层。
- **一次性授权过宽**："本会话全部允许"基本等于没有边界，授权应按操作而非按会话。
- **忽略间接影响**：发消息本身可逆，但发错对象造成的影响不可逆。影响面要按接收方视角评估，不只看操作本身。

## 可复用建议

- 一句话原则：**可逆的自己干，难逆的问一句，高危的当面确认**。
- 分级表贴进团队 wiki，作为新插件/MCP 接入的 checklist。
- 每个 L2 操作配一条事后通知（写了哪里、改了什么），成本极低，排查价值极高。
- 定期翻审计日志：频繁被确认且从无拦截的操作，降级到 L1；确认后被否决比例高的，说明分级或任务描述有问题。

## 总结

权限边界不是一次性的配置，而是随工具增多、信任度变化而持续演进的分层系统。先用可逆性和影响面归级，再把硬护栏放进工具层，最后靠审计日志不断校正——让 Agent 在低风险区跑得快，在高风险区慢下来。
