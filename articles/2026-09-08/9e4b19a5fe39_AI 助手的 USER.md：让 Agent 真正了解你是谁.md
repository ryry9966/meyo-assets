## 背景

搞 Agent 的人都熟悉 AGENTS.md 这类"项目说明书"：告诉模型仓库怎么跑、有什么约定。但很少有人给"用户自己"写一份。结果就是：你的环境、偏好、工作习惯，散落在几百条聊天记录和不可控的自动记忆里，Agent 每次都在靠猜。

我在自己的 OpenClaw 工作区里放了 USER.md，用了一个多月。它解决的不是"记不住"，而是"每次都要重新对齐"的问题。

## 问题

没有 USER.md 时，三个痛点反复出现：

1. **重复自我介绍**。换会话、换子 Agent、换工具链，都得再说一遍"我用 macOS、注释用中文、先给结论"。
2. **默认假设经常错**。模型默认 Ubuntu + bash，我在 macOS；默认要详细解释，我只想看 diff。错的不是模型，是没人告诉它。
3. **记忆不可审阅**。Agent 的自动记忆是黑盒：不知道它记了什么、记错了什么，没法 diff，也没法回滚。

## 做法

核心动作很简单：在 Agent 工作区根目录建 USER.md，并确保它被注入上下文。

**第一步：定结构。** 我目前用四段：

```markdown
# USER.md

## 环境
- macOS 15 + zsh；服务器 Ubuntu 22.04
- 时区 Asia/Shanghai，23:00 后勿触发通知类任务

## 技术偏好
- Python 3.12 + uv；Node 用 pnpm
- 提交信息用英文，正文解释 why

## 沟通风格
- 先给结论和 diff，过程解释放最后，可省略
- 不确定就问，不要编造路径和 API

## 红线
- 不自动 push、不动生产配置
- 密钥只走环境变量，不写入任何文件
```

**第二步：接上下文。** OpenClaw 会读取工作区内的 markdown 作为长期上下文；如果你的框架不自动读，有两条路：system prompt 拼接，或用 MCP resource 把它暴露成可读取资源。关键是让"每次会话开始必然可见"，而不是指望模型主动想起来去查。

**第三步：维护。** 放进 git。每当 Agent 行为不符预期、且根因是"它不知道"，就改一行。每月花五分钟通读，删过期项。

## 踩坑点

- **写太长**。超过一屏，注意力被稀释，关键规则反而失效。我控制在 50 行内。
- **写形容词不写规则**。"专业一点""简洁一些"是无效信息；"注释只写为什么，不复述做什么"才是可执行规则。判断标准：这条能否被机器验证？
- **放敏感信息**。USER.md 会进模型上下文，可能经过第三方 API 或插件。真名、住址、密钥都不要写，用指代即可。
- **和项目级配置打架**。分层解决：USER.md 是全局默认，项目内的 AGENTS.md 覆盖它，冲突时以更近作用域为准——这条规则本身也写进去。
- **过期信息比没有更糟**。换了技术栈记得删旧条目，否则 Agent 会拿着三个月前的栈给你写迁移脚本。

## 可复用建议

- 把 USER.md 当配置文件而非日记：短、可验证、进版本控制。
- 让 Agent 参与维护：每周让它从对话里提炼新偏好，输出 diff 提案，人工确认后合并。这比纯手写可持续。
- 多 Agent 场景下，USER.md 是唯一事实来源，各子 Agent 引用同一份，避免各记各的、互相矛盾。

## 总结

USER.md 的价值不在于"让 AI 更懂你"这类玄学表述，而在于把散落的隐性上下文，收敛成一份可审计、可版本化、可跨 Agent 复用的显式配置。它很土——一个 markdown 文件而已——但在 Agent 还不能可靠自主记忆的当下，这是成本最低、收益最稳的做法。先写十行，用一周，再决定加什么。
