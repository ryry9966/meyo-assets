## 背景

E2E 测试是最容易被"欠账"的一层。单元测试写起来快，E2E 要搭环境、造数据、写选择器、处理异步，一条关键路径的用例动辄半天。很多团队的现状是：核心链路靠人肉回归，覆盖率全凭自觉。

AI 代码助手出现后，"让 AI 写测试"听起来很美，但直接一句话让模型生成 Playwright 用例，结果往往是：能跑、断言形同虚设、选择器绑死在自动生成的 class 上，跑两周就全线飘红。问题不在模型能力，而在把测试生成当成了单轮文本任务。

## 做法

我在项目里跑通的方案，核心是"闭环 + 约束"，用 OpenClaw 的 agent 挂上 Playwright MCP 和文件工具：

1. **先探路再写**。让 agent 先用浏览器工具以只读方式走一遍关键路径（登录 → 核心操作 → 结果确认），输出一份流程摘要。这步不能省：没看过真实 DOM 结构，生成的选择器全是猜的。
2. **注入测试规范**。准备一份 conventions 文档放进 agent 的技能/上下文：优先 `data-testid`、禁止 `sleep`/固定等待、断言必须验证业务结果而非元素存在、命名统一。没有这份约束，agent 会本能地写 `nth-child` 加 `waitForTimeout`。
3. **小批量生成**。每次只让它写 3–5 条流程的草稿，放进独立目录（如 `e2e/agent/`），与人工用例物理隔离，方便观察质量。
4. **强制真跑**。生成后立刻在本地 runner 执行，把真实输出（含报错栈）回喂给 agent 迭代。这是整个方案的分水岭——不允许它"自称通过"。
5. **人工 PR 把关**。agent 提 PR，人只审两件事：断言是否真的在测业务、失败时错误信息是否可读。选择器和样板代码不用细看。
6. **夜间巡检（可选）**。用 cron 触发 agent 跑全量，失败时先自行分类：是产品变更导致用例过期，还是疑似 bug？输出带复现信息的 issue，而不是直接改测试。

## 踩坑点

- **幻觉式通过**：早期版本会写出"绿色但没断言"的用例。解法是把"至少一个业务断言"写成硬规则，回喂时检查断言数量。
- **用 sleep 修 flaky**：一旦它发现重试能变绿，就会滥用等待。规范里直接禁用，报错就报错。
- **选择器腐化**：让 agent 在 PR 里附带一份"建议补充的 data-testid 清单"，前端同学照着加，比事后修用例便宜得多。
- **测试数据互相污染**：并行跑会串。要求 agent 只写幂等用例，数据要么每次新建，要么走 seed fixture。
- **凭截图推理**：视觉截图对布局问题有用，但写选择器时容易误读。生成阶段一律基于 accessibility tree / DOM 快照。

## 可复用建议

- 把"关键用户流程"维护成一份 YAML 清单，agent 按清单领取任务，生成范围可审计、可增删。
- 记一个简单指标：agent 用例的 flaky 率。超过人工用例基线就暂停"晋升"（从 `agent/` 移入正式目录）。
- 用例失败先分类再重写。直接让 agent 重新生成，会把产品 bug 洗成"测试修好了"。

## 总结

Agent 写 E2E 的价值不在"一键生成"，而在接走最枯燥的 80%（脚手架、选择器、等待逻辑、跑通），让人专注于真正需要判断的部分：测什么、断言什么、什么算坏。闭环执行 + 明确约束 + 人工把守断言质量，这套组合拳在任何支持 MCP 工具调用的 agent 框架里都能落地。OpenClaw 的技能、MCP 接入和定时任务机制，只是让它跑起来更省心。
