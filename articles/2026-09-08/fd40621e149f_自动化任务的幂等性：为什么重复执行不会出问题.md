## 背景

写自动化久了（定时任务、Agent 工作流、MCP 工具、webhook）都会默认一件事：**任何任务都可能被执行不止一次**。调度器超时重试、Agent 重规划后重新调用工具、人工手动补跑、消息队列 at-least-once 投递——重试不是异常路径，而是常态。

## 问题

幂等性回答的是一个很朴素的问题：同一操作执行一次和执行 N 次，最终结果是否一致。

常见的不幂等操作：

- 向表格 / 数据库追加一行 → 重复数据
- 调用「创建工单 / 建目录 / 发通知」类接口 → 重复资源
- 基于「未处理」状态筛选再推进的流水 → 状态被覆盖、顺序错乱

典型场景：Agent 因为工具调用超时重试了一次 MCP 写入，表格里出现两条一模一样的记录，下游统计和去重逻辑全部被污染。这类问题在第一次重试发生之前往往完全不暴露。

## 做法

1. **先分类**：把任务里的操作分成「读」和「写」，只需要对写操作做幂等设计。
2. **定义幂等键**：用稳定的业务键（文件路径 + 日期、内容哈希、外部资源 ID）。不要用时间戳或随机 UUID——每次重试都生成新键，等于没做幂等。
3. **写入前先查**：已存在就跳过或更新。小规模场景「先查后写」够用，但要意识到并发下有竞态（见踩坑点）。
4. **优先 upsert / 覆盖式语义**：「把状态设为 X」天然幂等，「再追加一次 X」不是。能用 update 就不用 insert，能覆盖写就不追加写。
5. **外部系统不配合时，本地记账**：用 sqlite 或本地文件记录已完成的幂等键，执行前先查账。
6. **多步骤任务把键做到步骤级**：失败后从断点继续，而不是从头重跑所有副作用。

## 踩坑点

- **幂等键里含时间戳**：每次重试键都不同，形同虚设。这是最常见的错误。
- **并发竞态**：两个进程同时通过「不存在」检查，然后都写入。至少按键串行化，或依赖数据库唯一约束兜底。
- **只盯着写接口**：有些「读」操作也有副作用（标记已读、触发计费的模型调用），同样需要幂等处理。
- **部分成功**：第 3 步成功、第 4 步失败，整体重跑导致前 3 步的副作用重复发生。
- **传输层盲目重试**：HTTP 客户端对非 GET 请求自动重试，会把不幂等问题放大到你看不到的地方。

## 可复用建议

- 设计任何自动化时，默认假设：**它一定会被执行至少两次**。
- 如果你自己封装 MCP 工具或插件，直接在接口上暴露 `idempotency_key` 参数，由服务端负责去重——把幂等变成契约，而不是口头约定。
- 日志里带上幂等键，出问题时可以对账。
- 写一个简单验证：同一任务连续跑两遍，diff 结果，应当完全一致。这条检查可以放进 CI。

## 总结

幂等性不是为了避免重试，而是**让重试变得安全**。Agent 系统里 LLM 的不确定性又叠加了一层「重复触发」的可能，工具层的幂等设计是唯一能稳住的部分。把「重复执行不产生额外副作用」当作自动化任务的验收标准之一，很多半夜被告警叫醒的场面，其实可以提前避免。
