## 背景

Agent 的可靠性往往不取决于模型多聪明，而取决于它依赖的外部世界多稳定。OpenClaw 里 agent 频繁通过 MCP 工具、插件和 HTTP 调用外部服务：搜索、数据库、消息推送、第三方平台。这些服务迟早会出问题——超时、限流、5xx、凭证过期。

没有恢复机制的 agent，遇到故障通常有三种表现：直接崩掉、陷入死循环重试烧 token，或者更糟——模型对着一段原始报错"脑补"出一个看似合理的回答。

## 做法：分层恢复策略

**1. 先分类，再处理。** 错误分两类：可重试（网络超时、429、5xx）和不可重试（400、403、参数错误）。401 特殊处理——先尝试刷新凭证，再重试一次。

**2. 指数退避 + 抖动。** 基础间隔 1 秒、倍率 2、最多 3 次，每次加随机抖动。同时设置总预算（比如 30 秒），避免一次工具调用阻塞整个 agent loop。

**3. 熔断。** 连续 N 次失败就打开熔断器，一段时间内直接 fail fast，期间走降级路径；冷却结束后用半开状态探测服务是否恢复。

**4. 降级链。** 主 API → 备用 API → 本地缓存 → 明确告知失败。降级结果必须打标记（stale / degraded），不能让模型把三天前的缓存当实时数据用。

**5. 结构化错误回传给模型。** 不要把 stack trace 直接喂给 LLM，翻译成 `{code, retryable, hint}` 这样的结构，模型才能正确决策：换工具、告知用户、还是稍后再试。

配置层面大致长这样：

```json
{
  "retry": { "max_attempts": 3, "backoff_base_s": 1, "backoff_factor": 2, "jitter": true, "total_budget_s": 30 },
  "circuit_breaker": { "failure_threshold": 5, "cooldown_s": 60, "half_open_probes": 1 },
  "fallbacks": ["backup_api", "local_cache", "report_failure"]
}
```

## 踩坑点

- **对非幂等操作盲目重试**：下单、发消息重试一次就是双倍。所有写操作必须带幂等键，重试前先确认幂等性。
- **原始报错直接给模型**：模型会编造失败原因，用户看到一本正经的错误解释。错误必须经过翻译层。
- **无抖动的同步重试**：所有实例在同一时刻重发，刚恢复的服务被二次打死。
- **缓存了错误响应**：错误也进了缓存层，之后降级路径返回的全是垃圾数据。
- **把 4xx 一律当致命**：token 过期本可以自动刷新恢复，直接判死太浪费。
- **降级不透明**：模型拿着过期数据输出给用户，且没有任何提示，这是最隐蔽的事故源。

## 可复用建议

- 所有 MCP 工具调用走**同一个错误处理包装层**，策略集中配置，别让每个插件自己造一套。
- 错误对象统一 schema，日志里记录每次重试与降级决策，事后能完整复盘。
- 上线前做**故障注入测试**：手动掐掉依赖、加延迟、返回 500，观察 agent 行为是否符合预期。没经历过 故障演练 的恢复逻辑，基本等于没写过。

## 总结

错误恢复不是让 agent 永不失败，而是让失败**可控、可解释、可恢复**。分类、退避、熔断、降级、结构化回传——这五层做完，外部 API 挂掉时，agent 的表现会从"随机崩溃"变成"有礼有节地告诉你哪里坏了、正在用什么替代方案"。在 agent 实际投产的过程中，这部分工程工作的收益，通常比多调几轮 prompt 大得多。
