## 背景

跑过一段时间 Agent 自动化的人基本都遇到过：任务流程本身没问题，但依赖的外部 API 突然抽风——搜索接口 429、天气服务超时、某个 MCP 工具背后的上游直接 5xx。Agent 和普通脚本的区别在于，它处在“半自主”状态：失败之后会**自己决定下一步**。这正是危险所在。

## 问题：三种典型的坏结局

1. **无限重试烧 token**。prompt 里写了一句“遇到错误请重试”，Agent 就真的每次都重试。两小时后你发现账单翻倍，而 API 从头到尾都是挂的。
2. **静默编造结果**。工具返回错误，但 Agent 不愿“空手而归”，直接在回复里编了一个看起来合理的答案。这是最恶性的失败，因为它不报错。
3. **状态不一致**。任务执行到一半挂掉，前面已写入的数据留在库里，没有 checkpoint，重跑会重复操作（比如重复下单）。

## 做法：把错误恢复做在工具层，而不是 prompt 里

核心原则：**重试、超时、熔断是工程问题，不要指望靠一句 system prompt 解决。**

**1. 给每个工具调用包一层统一执行器**，做四件事：强制超时（不只是 HTTP 超时，是整次调用的 wall-clock 上限）、错误分类、重试策略、结构化返回。

**2. 错误分类决定后续动作**。建议一个最小 schema：

```json
{ "ok": false, "error_code": "UPSTREAM_TIMEOUT", "retryable": true, "message": "上游超时，已重试2次" }
```

- 429 / 超时 / 5xx → `retryable=true`，指数退避 + 抖动，最多重试 2~3 次
- 401 / 403 / 配额耗尽 → 不重试，直接熔断该类调用，转入降级路径
- 参数错误 → 把结构化错误原样还给 LLM，让它自己修参数再试（这类往往能自愈）

**3. 熔断器**。连续 N 次失败就短路，冷却期（比如 5 分钟）内快速失败，避免每个循环都去撞同一堵墙。

**4. 诚实地把错误交给 LLM**。返回给模型的信息要“够用但不脏”：给错误码和一句人话描述，不要塞整个堆栈。同时明确它可选项：换备用工具、询问用户、或终止任务。禁止它自行编造默认值兜底。

**5. 有降级预案的工具才算上线**。关键依赖要有 plan B：备用 API、本地缓存快照（必须标注数据时间），或干脆明确输出“该步骤无法完成”。宁可失败得清楚，也不要成功得可疑。

## 踩坑点

- **非幂等操作不要自动重试**。POST 下单失败后盲目重试可能下两单。要么服务端支持幂等键，要么重试前先查状态。
- **原始报错直接进上下文**。几千 token 的堆栈又贵又容易带偏模型，先收敛成 schema 再给。
- **降级缓存不标时间**。Agent 拿着三小时前的数据当实时数据用，比直接失败更糟。
- **熔断粒度太粗**。整个插件熔断会把健康接口一起陪葬，尽量按“插件 + 端点”维度熔断。
- **没做过故障演练**。上线前用 mock 注入 429 和超时，看 Agent 到底会怎么反应——很多“理论上没问题”的策略第一次跑就露馅。

## 可复用建议

- 所有工具走统一执行层，重试/熔断策略集中配置，不要散落在各插件的 prompt 里
- 每次降级打结构化日志（哪个工具、错误码、走了哪条降级路径），事后能复盘
- 主循环做 checkpoint：已完成步骤落盘，恢复时跳过而非重做

## 总结

外部 API 挂了不是异常路径，而是 Agent 生产环境的日常。把重试、熔断、降级做成工具层的基础设施，把错误诚实地交给模型去决策，Agent 才能从“演示能跑”走到“无人值守敢开”。失败要响亮，成功才可信。
