## 背景

跑自动化的人都有体感：Agent 链路越长，外部依赖越多。一次任务里可能要调 LLM API、搜索接口、数据库，外加几个 MCP 工具。本地代码不会随机挂，但外部 API 一定会挂——限流、超时、证书过期、返回结构悄悄变了。演示时一切正常，放进定时任务跑一晚，第二天早上收到的往往是半截结果。

所以错误恢复不是加分项，而是 Agent 能否长期运行的基本前提。

## 问题：三种性质不同的失败

实践中外部 API 的失败大致分三类，处理方式完全不同：

1. **瞬时故障**：429 限流、502/503、读超时。等一下重试大概率就好。
2. **持续故障**：key 失效、配额用完、接口下线。重试没有意义，只会烧 token。
3. **语义故障**：最隐蔽。HTTP 200，返回内容却是空数组、错误页 HTML、或字段改名后的"合法垃圾"。Agent 拿到后照常往下推理，产出一本正经的错误结论。

Agent 场景还有两个特有问题：模型看到报错后在推理循环里疯狂原样重试，token 火烧；插件吞掉异常返回空字符串，Agent 把"没数据"当成"数据是空的"。

## 做法：五层防线

思路是给每个外部调用套统一外壳：

```json
{
  "ok": false,
  "error": {
    "code": "upstream_timeout",
    "retryable": true
  }
}
```

具体分层：

1. **先分类再重试**。只有 `retryable` 的错误进重试通道；401/403/400 直接失败并告警。
2. **指数退避 + 抖动**，最多 2~3 次。加抖动是为了避免多个定时任务同时撞上限流墙。
3. **超时显式设置**：连接超时、读超时、单次工具调用总预算，三层都要有。
4. **降级路径显式声明**。备用数据源、缓存旧值都可以，但传给模型时必须带 `degraded: true` 标记，并在提示词里约定：降级数据只能标注来源，不能当事实输出。
5. **熔断**。连续 N 次失败后打开熔断器，冷却期内直接走降级路径，避免每次调用都白等 30 秒超时。

写操作（下单、发消息）必须带幂等键，重试才是安全的。

## 踩坑点

- **对所有错误一律重试**：最常见的问题。拿 400 重试三次，除了证明它确实是 400 没有任何产出。
- **在模型推理层重试**：模型看到工具报错，下一步立刻原样再调，循环三四轮。限流应该在工具层用代码做，模型只负责决定跳过、换路还是上报。
- **降级数据不标注**：Agent 把昨天的缓存汇率当今天的报给用户，比直接失败更糟。
- **同步调用里塞长退避**：单次调用退避 60 秒，上层看起来就像 Agent 卡死。重试应该上移到调度层。
- **不区分"API 挂了"和"key 过期了"**：两者的告警通道和响应人完全不同。

## 可复用建议

- 所有外部工具统一错误外壳，schema 校验放在喂给模型之前。
- 重试次数、退避、超时、熔断阈值全部配置化，按工具独立设置——搜索 API 和内部数据库的容忍度不该一样。
- 关键工具配轻量健康检查，定时探测，提前发现问题。
- 提示词里明确写入失败处理约定："工具不可用时如实说明，禁止猜测数据。"

## 总结

Agent 的错误恢复本质是边界设计问题，不是提示词问题。核心就五件事：分类、退避重试、熔断、显式降级、让失败可见。做到这些，一次 API 故障对整条链路的影响就能从"任务报废"降到"个别步骤降级"。
