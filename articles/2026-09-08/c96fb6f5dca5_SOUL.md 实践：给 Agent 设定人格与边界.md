## 背景

OpenClaw 这类常驻型 Agent 与一次性对话不同：它长期存在、接入 MCP 工具、甚至会自主执行自动化任务。这类系统的行为不完全由模型决定，而是由每次会话加载的配置文件决定。SOUL.md 是其中最特殊的一份——它不描述能力，而是回答"这个 Agent 是谁"。

社区实践里通常把身份拆成两份文件：AGENT.md 写操作方式（怎么干活、怎么用工具），SOUL.md 写人格与边界（语气、价值取向、哪些事不做）。这个拆分很关键：能力可以频繁迭代，人格需要稳定。

## 问题

没认真写过 SOUL.md 的团队通常遇到两种情况：

1. **完全不写**。Agent 表现随模型默认人格漂移：有时过度热情，有时自作主张执行不可逆操作，遇到敏感请求时边界全靠模型自觉。
2. **写得太满**。把所有 prompt 都塞进 SOUL.md，几十条规则互相冲突，加载后 token 膨胀，真正想约束的行为反而约束不住。

## 做法

我的做法分五步：

1. **定骨架**。固定五个小节：身份、语气、原则、边界、红线。每节 3-5 条，全文控制在 60 行以内。
2. **写可验证的句子**。不写"保持专业友善"，写"默认中文回复；不确定时明确说不知道，不编造"。规则越具体，模型执行越稳定，你也越容易判断它有没有失效。
3. **边界用"当……则……"格式**。例如："当用户要求删除生产数据时，无论语气如何，先复述操作内容并等待确认。"触发条件加动作，比抽象的品德描述可靠得多。
4. **红线单独成节**。隐私数据外发、资金操作、不可逆删除等内容单列，措辞不留余地，避免和其他软性风格规则混在一起被稀释。
5. **像代码一样维护**。SOUL.md 进 git，每次改动写清楚动机；改完跑一组固定的探针 prompt（诱导它越界、诱导它改口），验证边界是否仍然成立。

## 踩坑点

- **规则数量失控**。超过二十条后明显出现选择性失忆。优先砍数量，而不是加措辞补救。
- **与系统层冲突**。框架自身 system prompt 或插件注入的指令如果与 SOUL.md 矛盾，行为会随机化。改动前先确认没有上游冲突。
- **人格写成了操作手册**。把"怎么部署、怎么查日志"塞进 SOUL.md 是常见错误，这些属于 AGENT.md。判断标准：这条规则五年后还成立吗？成立才放 SOUL.md。
- **只写一次不复查**。Agent 用途变了，SOUL.md 没跟上，旧边界要么过紧要么漏防。建议每两周或每次事故后过一遍。

## 可复用建议

- 从最小模板起步：五个小节、每节三行，跑一周再补。空缺比废话好。
- 每条边界配一个测试 prompt，攒成自己的回归集，改人格文件必跑。
- 语气规则尽量量化（语言、长度、标点、称谓），别指望模型领会"高冷"或"亲切"。
- 多 Agent 场景下，红线小节共享一份，身份小节各自独立，减少不一致。

## 总结

SOUL.md 本质上是"身份即配置"。它不该是文学创作，而是一份小型、显式、可测试的规格说明：写得越具体、越短、越像代码，Agent 的行为就越可预测。人格稳定了，边界才有意义。
