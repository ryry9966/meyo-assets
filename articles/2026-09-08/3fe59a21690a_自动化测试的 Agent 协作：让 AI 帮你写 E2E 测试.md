# 自动化测试的 Agent 协作：让 AI 帮你写 E2E 测试

## 背景

E2E 测试是那种"人人知道重要、没人愿意写"的活。Playwright 框架搭好不难，难的是每加一个功能就要补一批测试：找选择器、造数据、处理异步等待，写完跑一次还可能因为环境抖动挂掉。不少团队的 E2E 覆盖率长期卡在核心链路，长尾功能基本裸奔。

Agent 的能力刚好对口这类重复劳动：读代码、操作浏览器、跑命令、看报错、改代码。但问题是，直接甩一句"给这个页面生成 E2E 测试"，产出质量普遍不行——断言空洞、选择器脆弱，甚至是幻觉出来的交互路径。

## 问题：为什么"一句话生成测试"不好使

我们踩过三个典型失败模式：

1. **自证式断言**。Agent 先造了测试数据，再断言这个数据存在。测试永远绿，但什么都没验证。
2. **凭想象写交互**。没有真实跑过页面，写出来的点击路径和实际 DOM 对不上，`await page.click()` 直接超时。
3. **一次性产物**。生成的测试能跑，但没人维护得了，重构后成片变红，最后被整个 skip。

根因是 Agent 缺少两个输入：**真实的运行时反馈**，和**团队自己的测试规范**。

## 做法：五步协作流程

我们在 CI 之外搭了一条 Agent 协作链路，以 Playwright MCP 为例：

**第一步，给上下文。** 把 `playwright.config.ts`、fixtures 目录、两三个"标杆测试"喂给 Agent，明确约定：必须用 `data-testid`、必须用 `expect.poll` 替代 `sleep`、测试数据带随机前缀。

**第二步，让 Agent 先逛页面。** 通过 Playwright MCP 让 Agent 真实打开页面、执行目标流程、截图并 dump 关键 DOM。这一步很关键：它写的所有选择器必须来自它亲眼看到的 DOM，而不是代码推断。

**第三步，生成草稿并立即执行。** 写完马上本地跑，禁止"生成完就交付"。跑不过自己修，最多 3 轮，超限就停下来汇报。

**第四步，人审断言意图。** Agent 负责让测试跑通，人负责确认"这个测试到底在验证什么业务规则"。断言空洞的（比如只断言元素可见）一律打回。

**第五步，接入 CI 并留痕。** 生成的测试打上来源标记（fixture 注释里记录 Agent 版本和会话摘要）；跑挂时把 trace.zip 喂回给 Agent 做首轮修复建议，人再确认。

效果上，新增一个中等复杂度流程的 E2E 从半天缩到一小时以内，主要时间花在第四步。

## 踩坑点

- **并行与数据隔离**。Agent 生成的测试最初共享一套测试账号，并行跑必挂。后来强制每条测试自建数据才稳。
- **严格等待**。Agent 很爱写 `waitForTimeout(3000)`，必须在规范里明确禁止，用断言轮询替代。
- **别让它顺带重构**。任务边界要窄，只加测试不改业务代码，否则它会很热情地"优化"你的组件。
- **Token 成本**。让它逛完整站一次比写一条测试贵得多。按用户路径拆任务，每次只覆盖一条流程。

## 可复用建议

- 把第一步和第二步固化成 prompt 模板或 Agent skill，团队共用。
- 建立 `data-testid` 契约并写进 lint 规则，Agent 和人都受益。
- 收集历史上跑挂的 trace，作为 Agent 修复测试的 few-shot 素材。
- 覆盖率决策留给人：Agent 擅长"把测试写出来"，不擅长"判断该测什么"。

## 总结

Agent 写 E2E 的正确姿势不是"生成"，而是"闭环"：真实操作页面 → 生成 → 执行 → 失败反馈 → 修复，人只在断言意图和覆盖范围两个节点介入。把它当成一个不知疲倦、但需要严格规范的初级测试工程师来带，产出质量反而最可控。
