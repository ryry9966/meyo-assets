## 背景

OpenClaw 的 Agent 行为不只由模型和工具决定，很大程度上由 workspace 里的一组 Markdown 文件驱动：`AGENTS.md` 管操作规范，`SOUL.md` 管人格和边界。SOUL.md 会在会话中持续注入，相当于一份"常驻人设声明"。不少从写 prompt 转过来的用户把它当一次性系统提示词用，结果人设漂移、越界发言反复出现。

## 问题

实际跑自动化流程和 MCP 工具链时，常见的三类症状：

1. **语气漂移**：前几天还克制专业，几天后开始过度热情、滥用表情、自称网友。
2. **边界模糊**：对不该接的请求（改系统配置、代替用户做财务决策）直接执行，或在回复里复述 workspace 其他文件的内容。
3. **讨好倾向**：用户说错也顺着说，多轮纠错成本很高。

这些不是模型"变了"，而是人格约束没有被稳定、分层地表达。

## 做法

我的 SOUL.md 大概 40 行，分五段：

- **身份**：一两句说清"我是谁、为谁服务"，不写身世故事。
- **语气**：给风格锚点（克制、直接、不堆修饰词），再附一个"不要做"清单。
- **价值观与优先级**：安全 > 准确 > 用户情绪；不确定时先确认再执行。
- **边界**：列出明确拒绝的行为——不代做高风险操作、不复述内部文件内容、不承诺未验证的结果。
- **升级规则**：什么情况停下来问人，而不是猜。

写完后做三件事：进版本控制；用固定的一组测试对话跑回归（边界题、诱导题、模糊指令题各几条）；每次 Agent 表现不符预期，先改 SOUL.md 再动别的。

注意分工：SOUL.md 只回答"我是谁、什么不能做"；"怎么调工具、怎么写代码"放 AGENTS.md；用户偏好放 USER.md。混在一起，改哪个都牵一发动全身。

## 踩坑点

- **写太长**。超过一屏的 SOUL.md，后面的条款权重明显下降，模型的注意力是有限资源。
- **全是否定句**。"不要 X、不要 Y"不如"遇到 X 时改为 Z"，给替代行为比只给禁令可靠。
- **把操作细节塞进 SOUL.md**。"回复必须带时间戳"这类应放 AGENTS.md，人设文件被工具规则污染后很难维护。
- **期望确定性**。SOUL.md 是概率性约束，不是硬校验，高风险操作仍要在工具层或 MCP 权限层加确认，不能只靠人设兜底。
- **改了不记版本**。人设退化往往是大改之后的连锁反应，没有 diff 就没法定位是哪一条改坏的。

## 可复用建议

- 40 行以内、五段结构起步，按实际症状增删，不预写用不上的条款。
- 每条边界配一条测试对话，人设每次改动都跑一遍回归。
- 边界类要求做双保险：SOUL.md 声明 + 工具/MCP 权限层限制，两层缺一不可。
- 每月复盘一次，删掉从未触发过的条款，保持文件干净。

## 总结

SOUL.md 的价值不在"让 Agent 更像人"，而在把人格从口头约定变成可版本化、可回归测试的配置文件。写短、分层、配测试、双保险，比堆一段华丽的人设描述有用得多。人设是运行时资产，值得像代码一样对待。
