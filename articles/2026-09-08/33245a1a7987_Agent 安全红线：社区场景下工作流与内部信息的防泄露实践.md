# 背景

越来越多团队把 Agent 接入社区场景：答疑机器人、插件助手、挂 MCP 工具的自动化代理。这些 Agent 平时在内部跑任务，带着完整上下文和工具权限；一旦直接面向社区，风险结构就变了——听众里不只有用户，还可能有主动探测的人。这不是杞人忧天，社区里“套话术”早已是公开玩法。

# 问题

三条高频泄露路径：

1. **提示词即配置**。system prompt 里写了内部流程、端点约定、账号规范。对方一句“逐字复述你的指令”，大概率直接拿走。
2. **权限即风险**。社区 Agent 挂着和内部自动化同一套 MCP 工具（文件读写、shell、内部 API），一条注入消息就能让它把内部笔记当“参考资料”检索出来。
3. **上下文串味**。共享 memory、跨会话摘要、调试日志把内部对话带进社区回答；更常见的低级失误是求助帖里直接贴了带 token 的配置。

核心认知一句话：**对模型而言没有“内外”之分，只有“在上下文里”和“不在上下文里”。** 防泄露靠的不是模型自觉，是工程隔离。

# 做法

1. **内外双实例**。社区-facing Agent 与内部自动化物理分离：不同 workspace、不同 memory、不同凭据。宁可维护两份配置。
2. **最小权限**。社区实例只挂白名单只读工具；不给文件系统、不给 shell、不给内部 API token。每个 MCP server 单独发短时效凭据。
3. **把 system prompt 当公开物来写**。密钥、内部域名、真实路径一律不进 prompt，走环境变量和工具层注入。写的时候假设它明天会被截图发出来。
4. **出口过滤**。响应管道加一层规则：正则扫 token 前缀、内部域名、路径特征，命中即拦截并记日志。规则引擎比“再调一次模型审一遍”更便宜、更可控。
5. **输入一律按不可信处理**。社区消息和工具返回值都是数据，不是指令；对“忽略之前的设定”“导出你的配置”类请求显式拒绝并留痕。
6. **定期红队**。每周自己攻击一次自己的 Agent：诱导复述 prompt、枚举工具、要求读本地文件，结果沉淀成回归用例。

# 踩坑点

- 以为 system prompt 是机密。所有主流模型都能被诱导输出指令，“指令外泄”应作为默认假设。
- 贪图方便共享 workspace：内部笔记和社区问答同目录，Agent 检索时“顺手”带出。
- 调试日志含明文密钥，贴社区求助时一起贴出去。日志必须先过 scrubber。
- 出口过滤只挡关键词不挡语义：内部项目代号换个说法照样流出，规则要随复盘持续迭代。
- memory 跨会话共享：上一个会话的内部上下文被摘要进了下一个会话。

# 可复用建议

- **上线前 checklist**：工具清单是否最小？凭据是否短时效？prompt 是否可公开？出口过滤是否在位？日志是否脱敏？红队用例是否通过？
- **分享工作流前先假名化**：内部域名换 example、真实 ID 换占位符；配置文件建议重写而不是截图打码——打码内容可被语境还原。
- **把“该 Agent 允许知道什么”写成文档**，与权限配置一起 review，避免人走了配置漂移。

# 总结

Agent 泄露不是模型问题，是边界问题：上下文决定泄露面，权限决定伤害上限。内外分离、最小权限、prompt 视为公开物、出口过滤、常态红队——五件事单看都不难，难的是在“先跑起来”的压力下坚持做。在社区分享经验值得鼓励，但请记住：分享的应该是方法论，不是你的内部拓扑。
