# 背景

OpenClaw 的 `memory_recall` 是 Agent 回忆历史信息的入口：用户偏好、过往决策、踩过的坑，全靠它从记忆库里捞回来。默认链路是本地 embedding + 向量相似度，也就是语义搜索。用了一段时间后我发现一个问题：明明记过的事，Agent 就是想不起来。

# 问题

把失败 case 拉出来看，基本分两类：

- **问法改写了就召回不到**。存的是“部署脚本放在 ~/ops/deploy.sh”，问“上次部署用的哪个文件”，语义分数排不进 top-5，embedding 对中文改写本来就不稳。
- **精确词直接失灵**。模块名、命令、报错关键字、ID 这类 token，语义模型几乎不敏感，全文搜索一查一个准。

反过来，全文搜索遇到同义改写又是另一个极端。结论很直觉：语义管“意思相近”，全文管“字面一致”，单用哪个都有明显盲区。

# 做法

我没动 OpenClaw 核心，只替换了 recall 的调用入口：

1. **先建评估集**。从最近对话里整理 40 条真实 recall query，人工标注期望命中的记忆条目。这步不能省，后面所有改动都靠它验证。
2. **跑语义基线**。默认链路下 hit@5 七成出头，失分集中在精确词和改写两类。
3. **加全文通道**。记忆本来就落在 SQLite，加一张 FTS5 虚表即可。中文要注意：默认分词器会把整段中文当一个 token，我用 trigram tokenizer 解决，代价是索引变大。
4. **双路召回 + RRF 融合**。语义、全文各取 top-20，用 Reciprocal Rank Fusion 合并：`score = Σ 1/(60 + rank)`。不用调权重，实现五行代码。
5. **收口**。融合后取 top-5，单条截断 300 字，避免撑爆上下文预算。

改完同一评估集 hit@5 到九成上下，其中约三分之一的提升来自全文通道兜住精确词。

# 踩坑点

- **中文分词是第一个坑**。FTS5 默认 unicode61 对中文基本不可用，要么 trigram，要么入库前用 jieba 预分词，选一个就好。
- **chunk 别贪大**。一开始按整段对话存，语义被稀释，相似度全挤在 0.7x 区间拉不开差距，切到 200–400 字后区分度明显变好。
- **评估集别拍脑袋**。自己造的同义改写 query 会高估效果，一定用真实对话里 Agent 实际问出的问题。
- **返回条数要克制**。recall 结果直接进上下文，10 条长记忆比检索不准更伤，上下文灌满后 Agent 反而抓不住重点。

# 可复用建议

- 记忆量在几千条以内，别上独立向量库。SQLite FTS5 + 本地 embedding 文件 + 一个融合脚本，一个下午能落地。
- 混合检索应该是默认选项，不是优化项。两条通路的失败模式几乎不重叠，RRF 是性价比最高的组合方式。
- 每次调 chunk、调 top-k、换 embedding 模型，都重跑一遍固定评估集。没有数字支撑的调参都是玄学。
- 时间衰减只对“偏好类”记忆开；事实类记忆（路径、配置、决策）别衰减，老答案可能仍是唯一正确答案。

# 总结

语义搜索 vs 全文搜索不是二选一：前者解决“换个说法还记得”，后者解决“逐字精确命中”，混合 + RRF 用极小的工程成本覆盖两边盲区。对跑 OpenClaw 的个人 Agent 来说，与其纠结换哪个更强的 embedding 模型，不如先把第二条召回通道搭起来——这一步的收益，比换模型大得多。
