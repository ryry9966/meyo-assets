36kr 有一篇讨论最近在技术圈刷屏：当一个人同时带着 16 个 AI Agent 干活时，最先撑不住的不是算力、不是 token 账单，而是人本身。这听起来像段子，其实是个严肃的工程命题，并行化的浪潮终于涌到了“人”这个环节。今天把这件事拆开看：瓶颈为什么偏偏落在人身上，以及工程界正在怎么解。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-08/8b5b40ad3bfaa93d.png)

## 一、工作范式变了：从“我干活”到“我派活”

过去十年，工具的进化逻辑是“放大器”：IDE 让你写代码快一点，搜索引擎让你查得快一点，但单位时间里干活的主体始终是一个人。多 Agent 时代把这个逻辑倒过来了：

- 人退到编排者（orchestrator）的位置，负责拆任务、派任务、验收结果
- Agent 是并行执行单元：一个查资料、一个写代码、一个跑测试、一个写文档、一个盯监控……16 个 Agent 同时开跑在技术上完全可行
- 类比系统设计：这相当于从单机单进程，升级成了分布式集群。而集群里最难搞的从来不是 worker，是那个单点的调度器

问题恰恰出在这里——调度器没有被并行化。

## 二、为什么瓶颈是人：三个硬约束

**1. 注意力带宽是串行的。** 认知科学的基本盘：人的工作记忆容量极其有限（经典的 Miller's law 是 7±2，近年的修正值大约 4 个组块），且注意力本质上是单线程资源。16 个 Agent 并行吐结果，你只有一个“处理器核心”去消化。龙虾有十条腿可以同时动，但大脑只有一个，人类面对多 Agent 的处境类似，只是腿还是借来的。

**2. 验证成本不对称。** 生成便宜，验证贵。Agent 十分钟能产出 300 行代码，但你认真读一遍、确认边界条件、判断架构合理性，可能要一小时。软件工程里 Code Review 本来就是公认的瓶颈环节，现在 review 对象的数量翻了十几倍。

**3. 上下文切换有隐性税。** UC Irvine 的 Gloria Mark 做过经典研究：人在任务间切换后，平均需要 20 分钟以上才能重新进入深度状态。当 16 个 Agent 各自需要 human-in-the-loop 的确认时，你一天可能被切成上百个碎片。

## 三、本质：一个“漏斗”结构，阿姆达尔定律在人类身上应验

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-08/a1b67802c2efddd1.png)

把整个人机协作系统画出来，会发现它是一个漏斗：

- 宽口：16 个 Agent 组成的生成端，吞吐量指数级上升
- 窄口：一个人的审核、决策、合并端，依然是那条单线程

这几乎是 Amdahl's law 的现实版：并行部分再快，系统整体速度被串行部分锁死。Agent 把 95% 的执行工作并行化了，剩下 5% 串行的部分——判断、拍板、担责——恰好全压在人身上，于是这 5% 成了 100% 的瓶颈。

还有一个更隐蔽的问题：**信息聚合**。16 个 Agent 各自产出，结果之间可能冲突、重复、口径不一，谁来做一致性合并？还是人。这是分布式系统里的老问题，现在有了人类的血肉版本。

## 四、工程界正在给出的解法

好消息是，这些都不是新问题，分布式系统三十年攒下的工具箱正在被搬过来：

1. **分层编排**：让 Agent 管 Agent。Orchestrator-Worker 模式下，一个主 Agent 负责拆解与汇总，下面挂多个子 Agent 干活，人只对接主 Agent。Claude Code 的 subagent、微软的多 Agent 框架 AutoGen 都是这个思路。
2. **用机器验证替代人工审查**：测试、lint、CI 流水线当客观裁判，Agent 之间互相 review。凡能被自动化验证的部分，就不消耗人的判断力。
3. **异步化 + checkpoint**：放弃全程盯梢，只在关键节点（设计定型、合并前、上线前）介入，其余时间让 Agent 自己跑，跑完再汇报。
4. **结构化汇报**：规定 Agent 用统一格式的 diff 与摘要回报，把人的理解成本压到最低。
5. **从逐条审批到抽样审计**：像风控一样管理产出——关键路径全审，长尾抽样，出错再回溯。

## 五、三条实用建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-08/664c77baf9d4b138.png)

如果你已经在跑多 Agent 工作流，这三条今天就能用：

1. **给自己设“并行预算”**：同时跑的 Agent 数量，上限应该是你能保持深度 review 的数量，而不是你能开多少窗口。经验值：关键任务 2~4 个，其余降级为后台批处理，跑完一次性回收结果。
2. **把标准前置到开工之前**：写清规格、验收条件、边界情况，让 Agent 自查、互查，人只做终审。Spec 写得越清楚，漏斗窄口的压力越小。这本质上是把人的判断“编译”进系统，一次编写、多次执行。
3. **每天留一段“串行时刻”**：一个不被打断的 60~90 分钟时间块，只处理最需要人判断的事——架构决策、取舍、担责的那 5%。这是你作为调度器唯一的深度工作窗口，别让 16 个 Agent 把它切碎。

最后一点冷思考：瓶颈不会消失，只会转移。工业革命把瓶颈从体力转移到机器效率，信息革命把它转移到信息处理，Agent 时代它转移到了人的判断力。从这个角度看，“人成为瓶颈”并不是坏消息——它只是重新回答了一个老问题：人最值钱的部分到底是什么。答案越来越清晰：不是执行，而是定义问题，以及为每一个判断承担后果。
