## 背景

我们团队每天要发一份工作日报，内容涵盖昨日构建结果、部署记录、线上告警、工单变动。之前靠人手工拼：先翻 CI 记录，再翻告警群，再回忆昨天做了什么。一次 20–30 分钟，而且经常漏项。后来用 OpenClaw 的定时任务加 MCP 工具接口，把整条链路自动化了，这里记录一下完整做法和教训。

## 问题

手工日报有三个硬伤：

1. 数字靠回忆和复制粘贴，容易抄错；
2. 格式随人而变，跨天没法对比和统计；
3. 关键事件可能整条漏掉，事后才被发现。

本质问题是：原始数据散在多个系统里，而"读日志 → 归纳 → 成文"这中间的脏活没人愿意每天做一遍。

## 做法

核心思路一句话：**确定性的事交给代码，语言组织交给 Agent**。流水线分五步：

**1. 采集层。** 一个 cron 定时任务在固定时间拉取原始数据：git log、CI 结果、告警记录、工单变更。每类数据一个独立脚本，各自落缓存，互不阻塞。

**2. 归一化。** 这是整条流水线最重要的中间层。所有数据统一转成固定的 JSON 结构：时间戳、来源、类型、严重级别、一句话摘要。不管上游是 CI 还是告警系统，到这一层长一个样。

**3. 聚合去重。** 同一事件常在多个来源出现（一次故障既在告警里也在工单里）。按时间窗口和关键词合并，按严重级别排序，裁掉超出日报时间窗的条目。

**4. LLM 摘要。** 把归一化后的 JSON（注意，不是原始日志）交给 Agent，按固定模板生成各段落。prompt 里明确约束：只允许使用输入 JSON 中出现的数字，禁止推断。

**5. 投递与归档。** 生成 Markdown 推到群 webhook，同时把当天的中间 JSON 和最终日报都存档，保证事后可追溯。

## 踩坑点

- **别让 LLM 直接读原始日志。** 早期我们把几千行 CI 日志直接丢给模型，结果数字是编的，还频繁撑爆上下文。加了归一化层之后才稳定。
- **时区问题。** 日志全是 UTC，日报按本地时间切天，第一次跑出来"昨日"混进了前天晚上的记录。切天逻辑必须收敛到一个地方统一做。
- **流水线自己会静默挂掉。** 日报系统挂了没人发日报，也没人发现。后来加了心跳：流水线自身的失败告警走独立通道——日报生成器不能是全系统里唯一一个失败无人知晓的组件。
- **输出格式漂移。** 模型偶尔会改写模板里的小节标题。现在对 LLM 输出做 schema 校验，不合格就带报错信息重试一次，仍失败则发告警并用原始 JSON 兜底投递。

## 可复用建议

- 中间 JSON schema 单独版本化，变更走显式版本号，别让下游悄悄坏掉；
- 每一步做成幂等，失败可单独重跑，不必从头来；
- 加一个 dry-run 模式，只打印中间产物、不投递，调试时少很多尴尬；
- 先接一个数据源跑通全链路，再横向扩展。一口气接四个源，出问题时很难定位是哪层坏了。

## 总结

流水线跑了一个多月，日报从"手工 20 分钟 + 经常漏项"变成"零人工 + 偶尔人工修正"。回头看，真正起作用的不是 LLM，而是那个不起眼的归一化中间层：它把不可控的自然语言问题收敛成了可控的数据问题，Agent 只负责最后一步把数据说成人话。凡是想用 Agent 做"从原始数据到报告"这类事的场景，这个分层思路都值得先搭起来。
