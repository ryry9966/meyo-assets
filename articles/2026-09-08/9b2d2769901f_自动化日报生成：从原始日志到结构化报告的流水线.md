## 背景

每天写日报，数据散落在服务器日志、git 提交、任务看板三处，手工汇总既费时又容易漏。既然 OpenClaw 常驻在跑定时任务，顺理成章想把这事交给 Agent。第一版的思路很直接：定时触发，把当天原始日志整个丢给 Agent，让它自己总结成日报。跑了一周就放弃了——这篇记录后来怎么改的。

## 问题

直接喂原始日志，暴露出三个硬伤：

1. **模型不可靠**：日志噪声大，长上下文里模型会遗漏关键错误，甚至编造不存在的条目；
2. **数字对不上**：错误计数、部署次数这类统计交给 LLM，和 grep 的结果偏差超过 20%；
3. **无兜底**：一次采集超时，当天日报就静默缺失，没人发现。

结论是：不能把 Agent 当流水线本身，它只能当流水线的一环。

## 做法

改成五段式流水线，每段一个独立脚本，中间产物落盘为 JSONL，方便逐段调试：

1. **采集**：OpenClaw 定时任务触发，通过 shell 和 MCP 工具拉三类数据——应用日志（按级别过滤）、当日 git log、任务系统 API 导出；
2. **归一化**：每条记录统一为 `{source, ts, type, payload}`，时间戳显式转本地时区，按唯一键去重；
3. **统计**：纯代码完成。提交数、错误数 Top5、异常耗时分布，输出一份紧凑的统计摘要；
4. **总结**：只把统计摘要加少量关键事件原文喂给 Agent，prompt 里固定输出 JSON schema（headline / risks / tomorrow），用校验器验证字段，不合格自动重试一次；
5. **渲染推送**：模板渲染成 Markdown，推送到群 webhook，同时归档留档。

## 踩坑点

- **别让 LLM 做算术**。这是最大的坑。所有计数、求和、排序都在代码里做完，模型只负责归纳措辞，数字偏差问题随之归零；
- **时区**。容器默认 UTC，按"当天"过滤会漏掉早上 8 点前的数据，采集端必须显式指定时区；
- **日志格式漂移**。上游改了一行日志格式，解析脚本静默返回空列表。现在解析结果为空即告警，绝不当"无事发生"处理；
- **日志里的提示注入**。日志文本可能包含看似指令的内容。总结阶段给 Agent 关闭全部工具，日志放进明确的分隔块里，只当数据处理；
- **重复推送**。失败重试必须配幂等键（日期 + 任务 ID），否则一次重试群里连收两份日报。

## 可复用建议

- 先定报告 schema，再写 prompt，最后才接模型，顺序反了会反复返工；
- 阶段间用落盘的中间产物解耦，排障时逐段回放，不用重跑全链路；
- 保留 dry-run 模式，改模板时不真推送，本地看渲染结果即可；
- prompt 模板进版本管理，总结风格调整可以 diff 回溯；
- 给流水线本身加心跳检测：连续两天没产出，比产出有错误更危险。

## 总结

核心经验一句话：**LLM 只做归纳表述，不做收集和计算**。采集、清洗、统计交给确定性脚本，Agent 负责最后的整合与措辞，schema 校验兜底。整条流水线上线一个多月，日报准时率和数字准确率都稳定，人只需要每周扫一眼异常项。改造本身约两天工作量，对已在用 OpenClaw 跑定时任务的同学，属于性价比很高的一类自动化。
