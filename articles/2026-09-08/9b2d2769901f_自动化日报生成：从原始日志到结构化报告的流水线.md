## 背景

我们团队每天要发一份日报，内容覆盖：昨天的代码提交、CI 失败情况、线上告警、关键服务指标波动。以前靠人肉：打开几个后台各看一眼，凭记忆写几行发到群里。结果就是日报质量完全取决于当天谁有空，漏报、口径不一、时间戳混乱是常态。

后来我们用 OpenClaw 的 Agent + MCP 工具链把这件事做成了流水线，跑了两个多月，日报稳定在每天早上九点自动送达，人工介入只剩"看一眼再转发"。

## 问题

直接让 Agent"读日志写日报"听起来美好，实际会撞上三类问题：

1. **原始日志噪声太大**。一天的日志几十万行，直接塞给模型既超 token 又容易被无关信息带偏。
2. **事实性错误不可接受**。日报里的数字（失败次数、告警条数）如果靠模型"数"出来，迟早出错。LLM 只适合组织语言，不适合做统计。
3. **输出格式不稳定**。今天多一个章节、明天少一个字段，下游归档和检索都没法做。

结论是：不能把日报当成一次性的 Agent 对话，得当成一条**确定性为主、LLM 为辅**的数据流水线。

## 做法

整体分四层：

**采集层**：脚本从各数据源拉取时间窗口内的原始数据——git log、CI API、告警平台存档、指标查询结果。每个源一个独立脚本，输出统一 JSON。

**结构化层**：这一层完全不用 LLM。做清洗、去重、按窗口切分，聚合成"事实条目"，例如"服务 A 昨日 CI 失败 3 次，其中 2 次为同一用例"。数字全部由代码算好，连同证据（commit hash、告警 ID）放进结构化快照。

**摘要层**：Agent 只拿结构化快照，prompt 里明确约束"仅允许使用输入中的事实，不得推断，不确定就标注待确认"。输出走固定模板 + JSON Schema 校验，校验不过自动重试一次，再失败则降级为纯结构化版本——没有润色，但数字一定对。

**投递层**：渲染成 Markdown，按模板归档到仓库，同时推送到 IM webhook。调度用 cron，整条链路做了幂等：同一天重跑是覆盖而不是追加。

## 踩坑点

- **时间窗口边界**：最初按自然日 00:00 切分，跨夜的发布和事故被腰斩，前后两天日报各一半。改成"业务日"（早 9 点到次日早 9 点）才符合阅读习惯。所有源统一转 UTC 存储、展示时再转本地时区，否则时区问题会让你怀疑人生。
- **单源失败拖垮全链路**：告警平台 API 偶发超时，早期整份日报直接难产。现在每个源独立超时、独立重试，失败源在报告里占位标"数据缺失"，其余照常。
- **Agent 格式漂移**：模型偶尔在 JSON 里加注释或改字段名。靠 Schema 校验 + 重试 + 降级路径兜底，而不是调 prompt 调到天荒地老。
- **中间快照没留存**：有次日报数字被质疑，原始日志已过期查不到。现在每天的结构化快照落盘保留 30 天，可审计。

## 可复用建议

1. 记住一条原则：**先结构化，再摘要**。LLM 负责叙事，代码负责事实。
2. 把日报抽象成"数据源 → 快照 → 模板"，以后加周报月报只是换聚合窗口和模板。
3. 给流水线加 `--dry-run` 模式，改模板和 prompt 时先本地跑一遍不投递。
4. 保留降级输出。一份朴素但准确的日报，好过一份漂亮但不可信的。
5. 模板进版本管理，字段变更留 git 记录，下游消费者不会突然找不到字段。

## 总结

这个项目的代码量不大，脚本加起来几百行，Agent 部分反而最薄。真正的工程量在时间窗口、失败隔离和幂等这些"无聊"的地方——但这恰恰是它跑了两个多月没出过事实性错误的原因。如果你也在用 Agent 做周期性报告，建议从"哪些数字必须由代码算"这个问题开始设计，而不是从 prompt 开始。
