## 背景

OpenClaw 的 agent 默认通过"心跳"获得主动性：每隔一段时间被唤醒一次，检查任务清单（HEARTBEAT.md 或等价的任务队列），再决定是否行动。这个机制本质上就是轮询。写到插件和自动化这一层，几乎每个人都会撞上同一个问题：要不要改成推送（webhook / 事件订阅）？

## 问题

两者的代价结构完全不同：

- **轮询**：延迟有上限——事件发生后最长要等一个周期；同时有空转成本——如果每次唤醒都直接进模型，token 消耗和实际任务量无关，纯白烧。
- **推送**：实时性好、空闲时零成本，但工程复杂度全在你这边——常驻入口、鉴权、去重、断线重连、失败重试，一样都不能少。

这不是二选一，关键是分层。

## 做法

1. **按任务性质分流。** 低频巡检类（定时汇总、日志清理、健康检查、每日简报）留在心跳轮询里；实时类（IM 新消息、CI 失败、监控告警、用户显式触发）走推送。
2. **轮询侧做"无模型短路"。** 唤醒后先由轻量逻辑判断任务队列是否为空，为空直接休眠，不进模型。这一步做到位，心跳间隔可以压到分钟级而成本依然可控。
3. **间隔动态化并加抖动。** 工作时段密、夜间疏；多实例部署时给间隔加随机 jitter，避免所有实例同一秒醒来形成惊群。
4. **推送只传信号，不传状态。** webhook 收到事件后写入与轮询共用的同一个任务队列，agent 被叫醒后仍然从队列取任务。事件丢了，还有下一轮心跳兜底。
5. **幂等与去重。** 每个事件带唯一 ID 和时间戳，队列侧按 ID 去重，重试不会导致重复执行。

## 踩坑点

- **心跳每次都进模型**：最常见的 token 黑洞。先短路，再唤醒。
- **推送通道静默失效**：长连接断开、webhook 持续返回 4xx/5xx 却没人发现，表现为"agent 好像变聋了"。给推送通道本身加探活。
- **事件只发一次、无重试**：网络抖一下就永久丢。至少做三次退避重试，再靠轮询兜底。
- **心跳任务与用户会话并发写同一上下文**，互相覆盖。给后台任务单独会话，或者加锁。
- **固定整点间隔**容易撞上游 API 的限流窗口，错峰即可。

## 可复用建议

- 默认架构就按"**轮询做兜底、推送做提速**"来搭。
- 心跳间隔、静默时段、任务队列路径全部配置化，别写死在代码里。
- 每次心跳留一行结构化日志（唤醒原因、队列长度、是否进模型），排障时极其有用。

## 总结

heartbeat 设计的目标不是"更聪明地醒来"，而是"尽量不醒"。轮询提供了简单可靠的下限，推送补上了实时性的上限；把状态收敛到一个队列、让事件只做叫醒信号，是让两者共存的最小改动路径。先把短路和幂等做扎实，再谈提升实时性，顺序不要反。
