## 背景：单 Agent 循环的天花板

最近在 OpenClaw 上跑自动化任务，遇到一个典型场景：让 agent 调研三个候选方案、各写一段验证代码、最后汇总对比报告。单个 agent 串行做下来，主上下文被中间的工具输出塞满，等开始写报告时，前面调研的细节已经在压缩中丢失，还经常出现"拿着 A 方案的结论去评价 B 方案"的张冠李戴。

这基本是单 agent 循环的两个天花板：**上下文污染**和**串行等待**。Subagent 编排是社区里验证过比较有效的解法：每个子任务跑在独立上下文里，主 agent 只接收摘要结果。

## 做法：五步搭一个 fan-out 编排

**1. 切分任务。** 找"低耦合、可独立交付"的子任务。三个方案的调研天然适合并行；"先定接口再写实现"这种有依赖链的，老实用流水线，别硬拆。

**2. 写自包含的子 prompt。** 这是最容易被省略的一步。Subagent 看不到主会话，prompt 里必须带齐：任务背景、输入文件路径、约束条件、期望的返回格式。

**3. 控制并发。** 3~5 个并发起步。给每个子任务设超时（比如 5 分钟）和重试上限（2 次），超时任务直接标记失败，不要无限等。

**4. 约定结构化返回。** 固定三字段：`status`（success / partial / failed）、`summary`（200 字内的结论）、`artifact`（产物文件路径）。让 subagent 把完整产物写到磁盘，主 agent 只读摘要和路径，需要细节时再按路径取。

**5. 隔离写操作。** 涉及写文件的子任务，各分一个独立工作目录（或独立分支），主 agent 最后统一合并。读操作可以随便并行。

## 踩坑点

- **"子 agent 应该知道吧"**：不会。它对主会话一无所知，prompt 里没写的等于不存在。这是新手翻车第一名。
- **并行写同一文件**：两个 subagent 同时改一个配置文件，后写的覆盖先写的，而且不报错。写操作必须隔离。
- **摘要压缩过度**：subagent 只回一句"已完成"，主 agent 无法校验，出错后也没法定位。summary 要包含关键结论和数据点。
- **单点失败阻塞全局**：一个子任务失败不该废掉整轮编排。收集部分结果，失败项单独重试。
- **并发拉满**：撞 rate limit、成本翻倍，收益却没涨——很多任务表面独立，实际共享同一份上下文依赖，硬并行只是浪费。

## 可复用建议

- 判断标准一句话：**只读或写隔离的任务才并行，共享可变状态的串行。**
- 三字段结构化返回值得固化成模板，所有编排任务复用。
- 先用便宜模型把编排链路跑通，验证切分和回收逻辑，再换主力模型跑正式任务。
- 把每个 subagent 的 prompt 和返回落盘存档，排障时能省一半时间。

## 总结

Subagent 编排的第一价值是**上下文隔离**，第二才是并行提速。别一上来追求十个并发，从两三个子任务的 fan-out 开始，把自包含 prompt 和结构化返回这两件事做扎实，再扩展到更复杂的编排模式，是水到渠成的事。欢迎在社区里贴你们的编排配置和失败案例，踩坑记录比成功案例更有价值。
