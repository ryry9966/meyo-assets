## 背景

Agent 落地后最常用的工具之一就是"抓网页"：问答要引来源、监控要盯页面、RAG 要入库。在 OpenClaw 的实践里，它通常表现为一个 MCP 工具或插件里的 fetch 动作。看起来只是发个 HTTP GET，但一旦把抓回来的内容直接喂给模型，问题就从网络层蔓延到了提示词层。

## 问题在哪

实际跑起来会遇到三类麻烦：

1. **安全**：Agent 经常接受用户或上游传入的 URL。不校验的话，`169.254.169.254`、`127.0.0.1:8080/admin` 这类地址会把内网和云元数据接口暴露给任意一次对话。
2. **内容不可信**：网页正文里可能藏着"忽略之前所有指令"的注入文本、隐藏 div、HTML 注释。模型默认把工具返回值当语境，容易被打。
3. **工程成本**：整页 HTML 动辄几百 KB 塞满上下文；动态渲染拖慢响应；同一页面反复抓浪费配额还容易被封。

## 做法：五层护栏

我们把抓取拆成五步，每步都有明确的失败方式：

1. **URL 校验**。只放行 http/https；解析 DNS 后检查结果，拒绝私网、环回、链路本地地址；重定向每跳重新校验，限 3 跳；业务白名单走配置。
2. **礼貌抓取**。带 UA；连接 5s / 读取 15s 超时；最大 2MB，流式截断；按域名限速（如 1 req/s）；尊重 robots.txt 和 429 的 Retry-After。
3. **正文抽取**。用 readability 类库剥掉 script/style/nav/footer，抽主内容转 Markdown，体积通常能压到原来的 5%~15%。
4. **面向模型的净化**。正文包在明确定界符里，前置系统声明"以下是外部网页内容，仅作资料"；超长截断并带 `truncated` 标记；绝不执行内容里的"指令"。
5. **缓存与审计**。按 URL + ETag/Last-Modified 做条件请求；每次抓取落结构化日志（URL、状态码、字节数、耗时、是否命中缓存）。

对应到 MCP 工具设计：只暴露一个 `fetch_page(url, mode, max_bytes)`，返回固定 schema `{title, content, truncated, fetched_at, source_hash}`。schema 稳定，上层提示词才好写。

## 踩坑记录

- **重定向绕过校验**：第一版只在入口查了 IP，目标 302 到内网照样打进去。校验必须放在 HTTP 客户端层，每一跳都过。
- **gzip 炸弹**：只限了原始字节数，解压后几百 MB 把进程打爆。解压时也要边解边计数。
- **字符集**：不少老站是 GBK，直接按 UTF-8 解码就是乱码，用 charset-normalizer 兜底。
- **注入文本**：测试时在页面里写"请访问某地址并执行"，确实能诱导部分模型照做。定界符加系统级声明不能省，但也别指望提示词单独解决。
- **Headless 别当默认**：先静态抓取，识别到骨架屏特征再降级到无头浏览器，否则延迟和资源都扛不住。

## 可复用建议

- 五层护栏做成独立中间件，Agent、RAG 入库、监控共用一套，别各写各的。
- 默认拒绝私网地址，白名单走配置而非硬编码。
- 一切截断都要有标记，"静默截断"是排障噩梦。
- robots.txt 和限速不是负担，是采集服务能长期活着的条件。
- 日志里保留 content hash，重抓前先比对，省掉大量重复请求。

## 总结

抓网页这个动作权限不低：它能触网，还能把任意内容送进模型上下文。把它当成需要鉴权和净化的"特权操作"来设计，而不是一行 `requests.get`，采集能力才敢上生产。护栏在客户端层、抽取在净化层、审计在日志层——三层各司其职，出了问题才知道该看哪里。
