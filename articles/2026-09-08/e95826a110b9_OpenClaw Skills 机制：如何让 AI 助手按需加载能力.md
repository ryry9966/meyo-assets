# OpenClaw Skills 机制：如何让 AI 助手按需加载能力

## 背景：能力多了，prompt 先扛不住

用 OpenClaw 做日常自动化（抓数据、管日程、写周报、跑部署脚本）一段时间后，最直观的感受不是功能不够，而是上下文不够。早期我把每个工具的用法、每条 SOP 的细节全塞进 system prompt，结果一个 agent 的常驻 prompt 轻松破万 token，模型反而开始犯低级错误：该调 A 工具时去调 B，长指令读到一半就"忘了"。

## 问题：全量注入的代价

把所有能力说明全量塞进上下文，有三个明确代价：

1. **Token 成本线性上涨**，且每一轮对话都在重复支付；
2. **指令互相干扰**。无关指令越多，模型对关键指令的遵从度越低，这个现象很容易自己复现；
3. **维护困难**。改一处措辞要在巨大 prompt 里找位置，改完还得全量回归。

## Skills 的解法：两级加载

OpenClaw 的 Skills 机制本质是把"能力说明书"拆成两级：

- **一级（常驻）**：每个 skill 的 `name` + `description`，体积很小，始终在上下文里，充当"路由表"；
- **二级（按需）**：SKILL.md 正文，只有当请求命中 description 时，agent 才去读全文。

目录结构很简单：

```
~/.openclaw/workspace/skills/
└── weekly-report/
    └── SKILL.md
```

一个最小可用的 SKILL.md：

```markdown
---
name: weekly-report
description: 当用户要写周报、汇总本周工作、生成本周总结时使用。负责收集条目、按项目分组、套用固定模板输出。
---

# 周报生成

1. 先向用户确认时间范围（默认本周一到今天）
2. 收集来源：仓库提交记录、会议纪要、用户口述补充
3. 按「本周进展 / 风险 / 下周计划」三段输出，不确定的条目标注"待确认"
```

关键在 description 里的"当……时使用"，它决定了模型什么时候想起这个技能。

## 踩坑点

1. **description 写成"是什么"而不是"什么时候用"**。"这是一个周报工具"不如"当用户要写周报时使用"。前者是名词解释，后者才是路由信号。
2. **正文越写越长，退化成第二个大 prompt**。一个 skill 正文建议控制在几百字，写清步骤和边界即可，细节让模型现场追问。
3. **写死环境假设**。正文里写死绝对路径、固定端口，换台机器就废。把路径作为第一步向用户确认，或者写成"先探测再执行"。
4. **技能职责重叠**。两个 description 都含"总结"二字，触发就靠猜。一个 skill 只做一件事，重叠关键词越少越好。
5. **把 skill 当用户文档写**。读者是模型不是人，少写背景故事，多写可执行的判断和步骤。

## 可复用建议

- **重复三次的 SOP 就该沉淀成 skill**：格式固定、来源固定、输出固定的任务收益最大。
- **用 git 管理工作区 skills**：改坏一条指令能立刻回滚，多机同步也省事。
- **写完做触发测试**：准备三句"应该触发"和三句"不应该触发"的话各测一遍，比肉眼审 description 靠谱。
- **模板放正文，事实放对话**：固定结构写进 SKILL.md，易变内容（时间范围、目标仓库）每次运行时确认。

## 总结

Skills 机制没有黑魔法，它只是把"能力描述"和"能力细节"分开：常驻的 description 负责被想起，按需加载的正文负责被执行。对个人 agent 来说，这是控制上下文成本最便宜的杠杆，不需要改代码，写好一个 markdown 文件，助手就多一项召之即来的能力。
