最近 36kr 一篇文章在技术圈刷了屏：一位开发者同时驱动 16 个 AI Agent 干活，最后发现最累的不是 Agent，而是他自己——任务要他派、产出要他验、异常要他拍板。过去我们争论"AI 会不会取代人"，而在这种工作流里，一个更朴素的问题先冒了出来：人的注意力和判断力，成了整条流水线上最窄的管道。这篇就来拆一拆：瓶颈到底卡在哪，以及怎么给自己"扩容"。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-08/b02e4f65529b1373.png)

## 一、从"手动挡"到"带舰队"：16 个 Agent 是什么工作法

先对齐概念。这里的 Agent 不是聊天机器人，而是：

- **能自主多步执行的 LLM 系统**：给定目标后，自己拆解任务、调用工具（读写文件、跑命令、检索资料）、根据反馈迭代，直到交付结果；
- **典型玩法**：以编程为例——Agent A 重构前端、Agent B 补测试、Agent C 修 bug、Agent D 更新文档，16 个会话并行推进，人只负责派活与验收；
- **角色变化**：你从"写代码的人"，变成"带着 16 个永不离职实习生的 Tech Lead"。

这条工作流能跑通，靠的是 2023 年 AutoGPT 那波尝试踩过的坑被逐一填平：更长的上下文窗口、稳定的工具调用、以及 coding 场景里天然可验证的产出（代码能跑、测试能过）。可靠性上来后，"一人带多 Agent"才从炫技变成日常。Sam Altman 反复预测的"一人独角兽公司"有了现实雏形——只是走在最前面的那批人，先撞上了自己这堵墙。

## 二、瓶颈的真实形态：生成提速了，验收在排队

把一天的作业拆开看，时间都漏在三个地方：

1. **任务下发比执行慢**。把一个需求描述到"Agent 可执行"的精度——背景、边界、验收标准——人可能要写 20 分钟，Agent 5 分钟干完。输入端是肉身打字，吞吐量天然受限；
2. **产出验收堆积**。16 个 Agent 平均十几分钟交一次活，认真 review 一份变更却要 30 分钟。经典的 producer-consumer 问题复现：Agent 是生产者，人是消费者，消费速率跟不上，队列只增不减；
3. **上下文切换吃掉深度思考**。UC Irvine 的 Gloria Mark 团队研究发现：人被打断后，平均要约 23 分钟才能重回之前的专注状态。在 16 个会话之间横跳，看似多线程，实际大量时间花在"重新想起自己刚在干嘛"。

工程师看到这里会心一笑：这就是教科书级的单消费者瓶颈——只不过这次的瓶颈不是 CPU，是你。

## 三、两条老定律，解释这个新困境

这不是全新问题，经典系统理论早把剧本写好了：

- **Amdahl 定律**：系统整体加速比受限于串行部分。"定义任务、验收、拍板"恰恰是只能由人串行完成的那部分。假设它占总时长 20%，那么无论并行多少个 Agent，整条流水线的加速上限就是 5 倍——开第 17 个 Agent 不会更快，只会让队列更长；
- **排队论（M/M/1 模型）**：把人建模成单窗口服务台，服务速率 μ 固定，Agent 交付速率是到达率 λ。当利用率 ρ = λ/μ 逼近 1，平均等待时间不是线性上涨，而是非线性爆炸。16 个 Agent 干的事，本质就是把 λ 拉高 16 倍；
- **布鲁克斯法则的变奏**：《人月神话》说加人会让沟通成本按 n(n-1)/2 膨胀。Agent 之间不需要沟通，但"人对 Agent 的管理上下文"不会消失——16 条任务线各自进行到哪、依赖什么、卡在哪，全装在你脑子里。而认知心理学的经典结论是，人的工作记忆只有 4±1 个组块，16 条线早就超载了。

一句话总结：**Agent 解决的是执行带宽，解决不了判断带宽；流水线的总吞吐，由最窄那段决定。**



## 四、解法：加中间层，给注意力装闸门

瓶颈在人，但人不必亲自站在瓶颈位上。目前实践里跑得通的几招：

1. **分层编排（Orchestrator 模式）**：加一个 Lead Agent，人只跟它对话。它负责拆解任务、派活给 Worker、汇总结果，只把例外上报。管理拓扑从星型变树型，人的 fan-in 直接降一个数量级；
2. **让机器验收机器**：把验收标准前置写进任务（spec-driven），配好测试、CI 和 eval，Agent 自检通过才交付。生成成本趋近于零的时代，验证资产（测试覆盖率、评估集）比代码本身更值钱；
3. **风险分级 review**：低风险变更（文档、样式、注释）自动合并；涉及数据、安全、资金的高风险操作必须人工过目。注意力是稀缺资源，只花在不可逆的事上；
4. **批处理 + 时间盒**：不开 16 个窗口实时盯盘，而是每天设几个固定"验收窗口"集中处理，保护整块的深度工作时间；
5. **主动降并行**：并行数等于你的消化能力，不是荣誉勋章。4 个被认真验收的任务，价值高于 16 个堆在队列里的半成品。

## 五、冷思考：人没有退出，只是换了岗位

- **角色是迁移，不是淘汰**：从执行者变成 spec 作者、首席验收官、风险守门员。"把问题定义清楚"和"快速判断产出好坏"，正在成为新的稀缺技能；
- **委派悖论依然成立**：想指挥 16 个 Agent，前提是你能判断这活干得对不对。外行带 16 个"内行"，结局通常是被流畅的错误输出带进沟里——Agent 把提问成本降到零，也把识别错误的成本转嫁给了你；
- **Trust, but verify**：Agent 不会主动汇报坏消息，也不会质疑不合理的需求。这些看似"低效"的人类特质，恰恰是人还站在回路里的理由。

三条可落地的建议收尾：

1. **先量验收带宽，再定并行数**：统计你一天能认真 review 多少产出，用这个数（大概率是个位数）反推该开几个 Agent；
2. **把写清楚任务当成核心工作**：花 30 分钟写好 spec 与验收标准，比事后返工 3 小时便宜得多；
3. **每开一个新 Agent 前问一句**：新增的产出谁来验、什么时候验？没有答案，就先别开。

工具在变快，人不必跟着变快，但必须想得更清楚。瓶颈不可怕，可怕的是不知道瓶颈在哪。
