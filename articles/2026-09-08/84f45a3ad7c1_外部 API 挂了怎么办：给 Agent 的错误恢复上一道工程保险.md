## 背景

OpenClaw 里的 Agent 自动化，本质上是一长串对外部依赖的编排：MCP 工具、第三方 API、自建服务。单次对话里接口挂一下，重试就过去了；但放进定时任务和长流程后，任何一次 503、超时、限流都可能让整条流水线停在半路——更糟的是停在"看起来跑完了"的假象里。

## 问题

实际踩过的三类典型故障：

1. **无限重试**：Agent 收到超时后反复调用同一个工具，烧完 token 预算，任务队列被堵死。
2. **幻觉式补全**：模型拿不到真实结果，返回"根据上下文推测……"的内容，下游拿着假数据继续跑。
3. **状态不一致**：非幂等操作（发消息、写库）成功了一半，重试后产生重复数据。

共同根源是：错误处理散落在各个工具里，没有统一契约，Agent 只能靠猜。

## 做法

把错误恢复做成基础设施，而不是让模型临场发挥：

**第一步：错误分类。** 在工具封装层把错误分成三类——瞬时错误（超时、429、5xx）、永久错误（400、404、鉴权失败）、未知错误。只有瞬时错误值得重试。

**第二步：有界重试 + 退避。** 指数退避加随机抖动，比如 1s → 2s → 4s，上限 3 次。抖动很重要，避免限流恢复瞬间所有任务一起打回去。

**第三步：熔断。** 封装层统计连续失败次数，超过阈值就在一段时间内快速失败，不再真的发请求。给 Agent 的返回里明确标注"该工具当前不可用"，让它走降级分支而不是继续撞墙。

**第四步：降级与兜底。** 每个关键工具准备降级策略：备用数据源、过期缓存（标注数据时间戳）、或直接跳过该步骤并把任务标记为"部分完成"。

**第五步：断点续跑。** 长流程每完成一个工具调用就落盘状态，恢复时从上一个成功节点继续。这比任何重试策略都省钱。

**关键一点：把结构化错误还给模型。** 返回 `{error_type, retried, suggestion}` 这样的 JSON，而不是抛异常后让模型看一堆堆栈。模型拿到结构化错误，通常会做出合理的绕行决策。

## 踩坑点

- 重试非幂等操作前先想清楚：发消息前查一下是否已发过，最好给每次操作生成幂等键。
- 超时别设太长。单个工具 120s 超时，十个工具串起来就是 20 分钟假死。
- 不要吞错误返回空结果。模型会把空列表当成"查过了，没有数据"，这是最常见的幻觉来源。
- 熔断阈值别太敏感，偶发一次失败就熔断，流程会频繁降级。

## 可复用建议

1. 所有工具走同一个封装层，错误分类、重试、熔断只写一次。
2. 把重试预算纳入 Agent 的整体预算管理，重试同样耗 token 和时间。
3. 每次失败记录完整上下文（入参、错误、重试次数），方便离线回放定位。
4. 定期做故障注入测试：手动关掉某个 API，看 Agent 走的是降级路径还是直接烂掉。

## 总结

外部 API 挂掉不是异常，是常态。好的 Agent 系统不追求永不失败，而是保证三件事：**失败快速、失败可见、失败可恢复**。把错误恢复从模型的临场发挥变成工程上的确定性保障，自动化流程才真正敢放到生产上跑。
