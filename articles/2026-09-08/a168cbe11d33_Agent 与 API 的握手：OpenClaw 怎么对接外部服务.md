## 背景

Agent 跑通对话只是第一步，真正产生价值要靠它调用外部服务：查库存、建工单、读数据库。在 OpenClaw 里，这条链路主要有三种接法：MCP 工具、插件（plugin）、以及流程节点里直接挂 HTTP 调用。本文以 MCP 为主线，复盘一次真实对接内部工单系统的完整过程。

## 问题

需求很朴素：让 Agent 能“创建工单、查询工单状态”。但把 API 文档直接丢给模型显然不行——它会编参数。拆下来实际是四个问题：

1. 工具怎么暴露，粒度怎么切；
2. 鉴权信息放哪，怎么保证不漏进上下文和日志；
3. 超时与重试怎么设计，尤其是“创建”这种非幂等操作；
4. 接口返回的大 JSON 怎么喂回模型而不撑爆上下文。

## 做法

**第一步：切工具粒度。** 不要一个 `ticket_api` 打天下。我们拆成 `create_ticket`、`get_ticket`、`list_tickets` 三个工具。粒度太粗模型会乱传参，太细它又选不过来。

**第二步：包一层 MCP server。** 用 OpenClaw 的 MCP 接入方式写了个薄封装：入参用 JSON Schema 严格约束（枚举、必填、格式），出参只挑模型需要的字段。工单系统返回 40 个字段，裁到 6 个再回给模型。

**第三步：鉴权走环境变量。** token 只在 MCP server 进程内读取，不进对话上下文，也不写进工具描述。日志对 Authorization 头统一脱敏。

**第四步：幂等与超时。** `create_ticket` 携带客户端生成的 request_id，服务端据此去重；超时设 10 秒；重试只对查询类工具开启，创建类失败就直接返回错误，让 Agent 去问用户，而不是自己硬重试。

**第五步：留观测。** 每次工具调用记一条结构化日志：工具名、入参摘要、耗时、状态码。出问题先查这条链。

## 踩坑点

- description 只写“创建工单”不够，用户只是“问问流程”时模型也会真建单。补上“仅当用户明确要求提交时调用”才稳定。
- 某接口偶发 5 秒以上慢查询，同步等待会卡住 Agent 循环，改成“提交任务 + 轮询结果”的工具对。
- 大 JSON 原样返回导致多轮之后 token 消耗明显上涨，裁字段后降了约 70%。
- 一次调试把完整请求头打进了日志，token 差点泄漏，之后所有日志强制过脱敏函数。

## 可复用建议

- 一个 MCP server 只管一类服务，别做全家桶；
- 每个工具描述写清三件事：适用条件、不适用条件、失败时怎么办；
- 错误返回统一结构 `{ok, error_code, message}`，模型才知道如何向用户解释；
- 写操作默认带 dry-run 开关，联调期先只跑参数校验。

## 总结

对接外部服务的核心不是“把 API 接上”，而是把接口翻译成模型能稳定理解、安全调用的契约。工具粒度、鉴权隔离、幂等设计、字段裁剪——这四件事做扎实，Agent 与 API 的握手才算真正握上。代码量不大，功夫都在约定里。
