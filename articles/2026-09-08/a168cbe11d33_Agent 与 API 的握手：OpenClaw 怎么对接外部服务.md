# Agent 与 API 的握手：OpenClaw 怎么对接外部服务

## 背景

Agent 真正干活，靠的不是会聊天，而是能调用外部服务。OpenClaw 的工具层把模型能力和真实世界连起来：查工单、发消息、跑脚本，本质上都是 Agent 和某个 HTTP API 之间的“握手”。握手协议没定好，后面全是事故。

## 问题

直接把 API 裸丢给模型，常见三种翻车：

1. 模型按描述猜参数，字段填错，甚至幻觉出不存在的接口；
2. 网络一抖就重试，非幂等的 POST 造成重复下单、重复建单；
3. 出错时只返回一句 "failed"，模型不知道怎么自救，任务原地卡死。

这些问题不在模型，在集成层没做好。

## 做法

以把一个工单系统接进 OpenClaw 为例，分四步：

**1. 定义工具 Schema。** 给每个工具写清名称、用途、参数类型和约束。描述是写给模型看的，不是写给人看的：参数说明里给例子，也给负向约束（"status 只接受 open/closed，不要自造值"）。工具名带动作语义，用 `ticket_search` 而不是 `api_call`。

**2. 写一层薄适配器。** 不要让插件直接发 HTTP。中间加一层：注入鉴权（密钥放环境变量）、设超时（建议 10–30 秒）、只对幂等请求做指数退避重试、把上游错误归一化成结构化信息。模型永远不接触密钥。

**3. 注册到插件层或 MCP。** 只在 OpenClaw 里用，写成插件即可；想让多个客户端复用，就包一个 MCP server，一个上游服务对应一个 server，工具名带版本前缀，升级不破坏旧调用。

**4. 控权限、留日志。** 读操作和写操作分开，删除、支付类动作加人工确认；每次工具调用记录请求摘要、耗时和结果状态，出问题能回放。

## 踩坑点

- **重试炸出重复数据**：只对 GET 等幂等操作开自动重试；POST 必须带幂等键，否则宁可失败让人介入。
- **原始 JSON 整包塞回模型**：上游返回 50KB 响应，token 烧完模型还看不懂。在适配器里做字段投影，只返回必要字段加一条简短摘要。
- **错误信息没有行动价值**：`{"error": "timeout"}` 模型没法处理；改成“请求超时，可重试或用 limit=10 缩小范围”，模型才能自我修正。
- **超时设太长**：一个工具挂 120 秒，整个 Agent 循环都被堵住。宁可快速失败，让模型走降级路径。
- **密钥进了上下文**：调试时图省事把 token 拼进参数，日志和对话记录全泄露。鉴权只存在于适配器内存里。

## 可复用建议

接任何一个新服务，过一遍这张清单：

1. Schema 描述含示例和负向约束；
2. 适配器具备鉴权、超时、重试、错误归一化四件套；
3. 返回体做了裁剪，错误信息能指导下一步动作；
4. 写操作有确认机制；
5. 有 dry-run 模式，上线前先空跑；
6. 工具描述进 code review，当代码对待。

## 总结

Agent 和 API 的握手，Schema 是打招呼，适配器是谈条件，错误信息决定这段对话能不能继续。集成层做得越“无聊”——超时、重试、裁剪、日志都规规矩矩——Agent 在上层就跑得越稳。先把这套基础件固化成模板，之后每接一个新服务，都是复制粘贴级别的体力活。
