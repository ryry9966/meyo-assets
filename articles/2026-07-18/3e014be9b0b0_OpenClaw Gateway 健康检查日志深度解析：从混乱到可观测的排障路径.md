## 背景

OpenClaw Gateway 作为 Agent 与插件、MCP 服务之间的流量入口，它的健康检查端点（通常是 `/healthz` 或 `/ready`）几乎是所有自动化部署、负载均衡和容器编排系统的第一道探活关口。一旦健康检查返回不健康，上游立刻摘流，Agent 调用链随即中断。然而，实践中很多团队只在“不通”的时候才去看日志，而且往往只看到一行 `GET /health 503`，却忽略了 Gateway 内部更完整的健康评估逻辑。要根治问题，必须把健康检查日志当作一种时序诊断信号，而不是简单的成功/失败标记。

## 常见痛点

Gateway 的健康检查日志通常混合了多类信息：自身进程探活、上游依赖（数据库、Redis、MCP Server）的连通性，以及各项子检查的耗时。默认 `INFO` 级别下，日志可能只输出整体结果，缺少细节；开启 `DEBUG` 后又容易淹没在海量的请求追踪里。另外，由于健康检查频率高（例如 kubelet 每 10 秒探测一次），日志量迅速膨胀，关键故障信号往往被淹没。很多人甚至误将健康检查超时（probe timeout）与业务超时混为一谈，造成排障方向错误。

## 步骤：三层递进式日志解读

以下基于 OpenClaw Gateway 0.8+ 版本中的结构化日志实践，假设使用 JSON 格式输出。

**1. 开启健康检查专用日志通道**

不要全局调高日志级别，而是通过配置将 `/health` 相关请求单独输出到一个文件或 stdout 标记：

```yaml
logging:
  rules:
    - path: "/health"
      level: DEBUG
      output: health.log
```

这样可以把“心跳噪音”与业务日志隔离，避免干扰。

**2. 关键字段拆解**

一个典型的 DEBUG 级别健康检查日志包含以下字段：

- `ts`：时间戳，用于关联探活周期。
- `status`：HTTP 状态码，但**不等于总体健康**。需结合 `checks` 数组。
- `checks[].name`：如 `db`, `redis`, `mcp-weather`, `self`。
- `checks[].status`：`pass`, `fail`, `warn`。
- `checks[].duration_ms`：单次探测耗时。若接近探活超时上限（例如 1s），即使 pass 也要警惕。
- `error`：仅在 `fail` 时出现，包含原始错误信息，如 `dial tcp 10.0.1.5:6379: i/o timeout`。
- `level`：日志等级，注意 Gateway 在健康检查失败时可能用 `WARN` 而非 `ERROR`，这取决于配置，容易漏看。

**3. 构建观察命令**

```bash
# 只看失败的探测
jq 'select(.path=="/health" and .status >= 500)' health.log

# 统计各依赖失败次数
jq -r '.checks[]? | select(.status=="fail") | .name' health.log | sort | uniq -c

# 查看最近一次失败前的时序（关联 MCP 服务抖动）
grep -B 10 "mcp-weather.*fail" health.log | jq .
```

通过将失败事件与上下游日志（如 MCP Server 自身的重启记录）对齐，可以快速判断是网关自身问题还是依赖方故障。

## 踩坑点

- **健康检查成功但容器重启**：典型原因是探测器超时设置小于检查实际耗时，导致容器编排层判定失败。必须对比 `duration_ms` 和 kubelet 的 `timeoutSeconds`，日志里看起来“成功”毫无意义。
- **`warn` 被忽略**：某些插件返回降级状态但不至于 `fail`，Gateway 仅标记 `warn`，整体健康仍为 200。很多人不关注 `warn`，直到累积多个降级后服务雪崩。建议对 `warn` 设置独立告警。
- **日志时间漂移**：若在容器中未正确同步时间，`ts` 与宿主机偏差会导致排查时无法对齐事件。注意确认 NTP 同步和日志采集器的时间字段。
- **结构化日志不完整**：旧版 Gateway 在 panic 或 OOM 前可能只打出半行 JSON，日志采集器会丢弃整条记录，导致“明明失败却找不到日志”的假象。升级 Gateway 并开启缓冲区写盘可缓解。

## 可复用建议

1. **统一健康检查日志 schema**：要求所有自定义插件和 MCP 适配器的健康检查也要输出统一字段，不要私自打印纯文本。
2. **基于持续时间的动态阈值告警**：不要仅对 `fail` 告警，可对 `duration_ms` 设置 P95 阈值，例如当 Redis 检查 P95 超过 200ms 时触发通知，提前发现网络劣化。
3. **将健康检查日志作为发布回滚指标**：发布后对比新旧版本在同一窗口内的 `fail` 次数和平均耗时，能比业务指标更早暴露依赖连接池泄漏等问题。
4. **按环境配置日志保留策略**：开发环境保留详细 DEBUG 日志，生产环境可采样 1% 的健康检查日志并聚合到监控系统，兼顾存储成本与可观测性。

## 总结

OpenClaw Gateway 的健康检查日志不是简单的“是否 200”，而是一个由多个时序探针组成的信号矩阵。通过分层解读、专用日志通道和结构化分析，你可以把零散的心跳记录变成一张清晰的依赖健康度热图。下次遇到偶发摘流，不要只盯着最后一条日志，试着把检查项的时序拉长，你会看到完全不同的故事。
