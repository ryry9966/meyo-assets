## 为什么 JSON 在长文场景频繁翻车

在基于 OpenClaw 搭建自动化 Agent 或 MCP 插件时，有一个绕不开的需求：让大模型一次性输出完整的长篇结构化内容，比如一份包含多步骤的操作指南、多个段落的分析报告，或者一个需要后续工具解析的复杂指令块。常规做法是要求模型严格输出 JSON，但实际体验是：一旦要求输出的 JSON 长度超过 500 个 token，非法 JSON 的概率就会急剧上升。

常见的坏 JSON 现象包括：
- 字符串内部未转义的双引号：`"content": "他说，"你好""`
- 对象或数组末尾多出一个逗号：`"...}",]`
- 嵌套层级过深时丢失闭合括号
- 模型中途“走神”，用自然语言解释而非 JSON
- 输出被截断，导致整个 JSON 无法解析

在自动化流程里，JSON 解析失败意味整个工作流中断，需要增加大量的重试、修复逻辑和二次调用，严重拉高延迟和 token 成本。更麻烦的是，许多廉价模型或小参数量模型的 JSON 合规性更差，只能在选择模型时被迫抬高门槛。

## 真实场景：一次多步操作指令生成任务

我在开发一个面向运维场景的 OpenClaw 自定义 Action 时，需要让模型分析用户需求，输出一个包含动态步骤、参数、预期结果的结构化操作序列。每次生成的内容约 800–1500 个 token。一开始我使用了下面的 Prompt 模板：

```
请输出如下的 JSON：
{
  "steps": [
    {"name": "...", "command": "...", "expected": "..."}
  ]
}
```

前几轮测试还算正常，但一旦用户问题变得复杂或需要处理的上下文变长，`json.loads()` 失败的比率一度超过 30%。尝试过 “请确保输出合法的 JSON”、“不要输出多余内容” 等描述性补丁，效果仍然有限。更令人头疼的是，有些错误只有部署到生产环境后才会暴露。

## 切换为自定义标签格式

问题的根源在于：JSON 是一种极严苛的格式化语言，对符号和结构的要求很高，而大模型本质上是基于概率生成文本，无法完美保证符号的精确匹配。相比之下，模型对于成对的 XML 风格标签的闭合性掌握得更好，即使内容中出现换行、引号等特殊字符，只要标签本身不冲突，就不会破坏整体结构。

我设计了如下输出规范，使用自定义标签包裹各段落：

```
<operation_steps>
<step>
<name>重启服务</name>
<command>sudo systemctl restart nginx</command>
<expected>服务成功重启，无错误输出</expected>
</step>
<step>
...
</step>
</operation_steps>
```

对应的 Prompt 改为：

```
请严格按照以下格式输出，不要包含任何额外的解释：
使用 <operation_steps> 包裹全部步骤，每个步骤用 <step> 包裹，内部用 <name>、<command>、<expected> 分别表示步骤名称、命令和预期结果。
务必确保所有标签正确闭合。
```

解析端不再依赖 `json.loads()`，而是先用正则提取 `<operation_steps>` 内容，再通过简单的 SAX 风格解析或 `xml.etree.ElementTree`（必要时需要包裹一个根元素）取出每个 `<step>` 块的文本。由于标签名称是我自己定义的，和输出内容的自然语言几乎不会冲突。

实际收益非常明显：在我测试的 200 次长文任务中，非法格式的比率从 30% 降到了不到 3%，这 3% 主要是因为模型未完整闭合标签（通常是被 max_tokens 截断）。

## 实施过程中的坑点

**1. 标签名与内容冲突**  
如果 content 可能包含类似于 `<step>` 的子串，就会破坏解析。解决办法是给标签名加上不具有二义性的前缀，或直接使用不常见的名称，如 `<ops_step>`。此外，在 Prompt 中告知模型：“如果内容中需要出现标签，请用实体编码或避免使用。”

**2. 模型忘闭标签或被截断**  
长文本接近 max_tokens 时，模型会优先输出内容而非闭合标签。可以在 Prompt 中强调“先闭合最内层标签再继续”，并在调用 API 时设置 `stop` 为 `</operation_steps>`，当生成到结束标签时主动停止，避免多输出废话。在解析端，如果找不到闭合标签，可以回退到用栈结构补齐未闭合标签。

**3. 嵌套标签解析的鲁棒性**  
XML 解析器对于未转义的 `&`、`<` 也很敏感。如果内容内存在这些字符，会导致 ElementTree 解析报错。一个工程化的做法是不依赖标准 XML 解析器，而是用基于正则的“段落抽取”：先根据 `<step>...</step>` 匹配每个步骤，再用简单字符串提取子标签内容，降低对整体合法性的依赖。  
例如：`re.findall(r'<step>(.*?)</step>', text, re.DOTALL)`，再对每个块提取 `<name>(.*?)</name>` 等。这比完美 XML 解析更耐受瑕疵。

**4. 与 Markdown 代码块的干扰**  
Agent 工作流里有时会将输出包裹在 Markdown 代码块中（如 ` ```xml `）。解析前需先剥离可能的围栏。处理方法：用正则去除首尾的 ` ``` ` 及其语言标识。

## 可复用的工程建议

- **优先使用唯一标签名**：避免与通用词汇或 Markdown 语法冲突，可在标签中加入项目前缀，如 `<ocl_step>`。
- **设置 API 的 stop 参数**：利用结束标签停止生成，既节省 token，又防止截断。例如 `stop=["</operation_steps>"]`。
- **解析允许多级容错**：第一级用正则提取，第二级尝试 XML 解析，如果失败则降级为纯文本切片，只拿能匹配到的字段。
- **定义输出规范时给一个完整示例**：把期望标签格式的完整示例放在 system prompt 中，比只用语言描述更有效。
- **配合返回格式验证**：在 OpenClaw Action 中实现一个校验函数，若解析不到必要字段，则触发自动重试（最多一次），重试时追加“上次输出格式不合规，请严格按照标签格式输出”。

## 总结

在 Agent 和自动化流水线里追求 100% JSON 合规是一种脆弱的强约束。换用自定义标签格式，实际上是利用了 LLM 更擅长的“成对标记闭合”能力，以低成本的解析宽容度换取系统整体稳定性。这并不意味着 JSON 应该被抛弃，在短小、高度嵌套且需要数字与布尔类型明确区分的场景，JSON 仍是最佳选择。但在以长文本段落、自然语言混合指令为主的输出里，标签格式会是一条务实可靠的路径。

对于 OpenClaw 的插件/MCP 开发者而言，减少解析失败就是减少重试次数和延迟，从而让自动化流程更顺畅地落地。希望这个经验能为你的下一个 Action 设计提供一些参考。
