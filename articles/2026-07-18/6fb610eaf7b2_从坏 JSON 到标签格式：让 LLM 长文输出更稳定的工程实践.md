## 背景

在 OpenClaw 上搭建自动化 Agent 或多步 MCP 工具链时，经常需要让大模型输出一段结构化的长文——比如一份带有章节的分析报告、符合模板的文档或一系列 FAQ。早期我们会很自然地让模型返回 JSON，例如：

```json
{
  "sections": [
    {"title": "摘要", "content": "……"},
    {"title": "方案", "content": "……"}
  ]
}
```

看起来清晰明了，后续工具直接 `json.loads()` 就能消费。但当输出超过几百 token，这种约定的脆弱性就暴露出来了。

## 问题：JSON 对付长文天然不可靠

LLM 是自回归生成的，当它输出一段长长的 JSON 字符串时，需要在注意力滑窗中同时维护所有尚未闭合的括号、保留引号配对和逗号位置。内容越长，模型就越容易在前面的自然语言段落中丢失格式上下文。常见的坏 JSON 包括：

- 最后一个数组元素后面多了一个逗号  
- 字符串内部的引号没有转义  
- 结尾少了一个 `}` 或 `]`  
- 多出一个 `}` 导致解析错误  

在 Agent 流水线里，一次 JSON 解析失败就意味着整个节点任务中断，只能等待重试，浪费 token 和时间。有些场景还必须拿到结果才能继续调用下一个工具，容错成本很高。

## 做法：切换到自定义标签格式

我们选择用类似 XML 但更宽松的标签格式替代 JSON 来承载长文结构。比如，输出约定成下面这样：

```
<report>
  <section title="概述">
    这是概述的内容……
  </section>
  <section title="细节">
    这里是细节部分……
  </section>
</report>
```

解析时不再需要严格的 JSON 语法，而是基于简单正则或状态机按标签切分。即便模型忘记闭合某个标签，我们也可以用“遇到下一个开标签即关闭上一个”的容错策略继续提取内容，不至于全盘丢弃。整体改造步骤如下：

### 1. 设计标签体系
只用最简单的英文单词（`<report>`、`<section>`、`<item>`），尽量减少嵌套，最多两层。属性只保留必要的 `title`，且要求属性值用双引号包裹。

### 2. 重写 Prompt 和 Few-shot
在 system prompt 中明确输出格式，并提供至少一个完整示例。强调：
- 必须从 `<report>` 开始，以 `</report>` 结束。  
- 只输出标签包裹的结构，不要附加任何解释或闲聊。  
- 内容中不得出现 `<` 或 `>`，若必须使用则写成 `&lt;` 与 `&gt;`。

### 3. 实现宽松解析器
解析器核心逻辑：

1. 用正则找到第一个 `<report` 和最后一个 `</report>`，截掉模型可能额外输出的前缀后缀。
2. 找到所有 `<section title="...">` 并取出 `title` 属性，将后续文本作为内容，直到碰到下一个 `<section` 或 `</report>`。
3. 对于未闭合的最后一个 section，直接取到字符串末尾作为内容，同时打一条 warning。
4. 最后构造一个字典列表，供后续工具使用。

### 4. 后处理与防御
- 如果 title 属性因为引号问题没匹配到，退化为 `title="未命名"`。  
- 对内容 trim 多余空行。  
- 如果整个提取到的 section 数量为 0，才启动重试机制。

## 踩坑记录

**内容中出现尖括号**  
即使 prompt 中强调不要使用 `<`，模型偶尔还是会输出形如“如果 `i<10`”的技术内容。我们的正则匹配 `<section` 时会误判。解法：在定位 section 标签前，先扫描内容中将 `<` 开头的非标签文本替换成占位符，解析完再还原；或者更简单地，让模型把所有 `<` 写成 `&lt;`，解析器自动反转义。

**模型自行“加戏”**  
经常在开头写“好的，这是报告：<report>...”或结尾加一句“希望对你有帮助”。用截取首尾标签的方法处理，效果很好。

**属性值中夹带引号**  
比如 `<section title="关于 "智能" 的部分">`，造成 title 提前截断。在 prompt 中严格禁止标题内出现双引号，并将 title 规范为实体名或简单描述。

**流式输出导致截断**  
部分流式 API 可能在标签中间就断开连接，返回不完整文本。为避免这种情况，在需要结构输出时改回非流式调用，确保拿到完整响应后再解析。

## 可复用的工程建议

- **让数据格式适应模型，而非相反**。不要在 prompt 里塞复杂的 JSON Schema，模型很难严格遵循。用松散的标签格式，配合“最佳努力”解析，能显著提升整体稳定性。
- **提供清晰、单一的示例**。示例不要多，但要和真实输出场景一致，包括标题长度、内容风格。
- **用解析器代码覆盖边界情况**：空内容、纯英文、包含 emoji、标题缺失等，单独写单元测试。
- **记录解析失败的样本**，用它们去迭代 prompt 模板和后处理规则，形成正向循环。
- **考虑演进到函数调用**。如果模型支持原生 function calling 或 structured output，它们对短 JSON 可靠，但做长文多段输出时，标签格式仍然有优势，可以把两者结合：用 function calling 定义外层结构，内层长内容用标签标注，解析更灵活。

## 总结

从 JSON 切换到自定义标签格式，表面上是“减少语法严格性”，本质上是对 LLM 生成过程的认知修正。长文输出中，模型出错是常态，工程设计的重点应当放在如何从半成品中尽可能多地提取有价值信息，而不是幻想一次就得到完美结果。这种思维转变会直接影响整个 Agent 流水线的健壮性。希望这一实践能给 OpenClaw 社区里正在处理类似场景的同学一个低成本的替代方案。
