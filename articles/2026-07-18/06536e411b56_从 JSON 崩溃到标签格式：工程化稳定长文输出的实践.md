## 背景：LLM 长文输出为何需要结构化

在 Agent 自动化流程中，经常需要 LLM 一次性生成包含摘要、要点、代码段、步骤列表的长篇回答。为了让下游工具（MCP 服务、本地插件、OpenClaw 工作节点）自动切割和路由这些内容，我们最先想到的是 JSON。但实际工程里，**长文输出场景下 JSON 几乎必然失败**——模型容易少写一个花括号、在字符串里忘了转义、输出到一半被截断，导致整段响应解析崩溃，无法回退。

这个问题在 Agent 做调研报告、文档生成、日志摘要时尤其突出。我们需要的是**部分可用的结构化数据**，而不是要么全有、要么全无的 JSON。

## 问题：JSON 在长文输出中的三个硬伤

1. **截断即报废**  
   当 max_tokens 或流式中途中断时，缺失结尾的 `}` 或 `]` 让整个 JSON 不可解析，前面已生成的有效内容也被丢弃。

2. **转义地狱**  
   代码块、对话记录、带有双引号和换行的文本，塞进 JSON 字符串里极易引发转义错误，模型经常忘记 `\`，或生成非法的 Unicode 转义。

3. **容错成本高**  
   即使你用 `json.loads` 捕获异常，也很难定位到错误位置去做局部修复。而手工加 fallback 逻辑（如补全花括号、按行重新拼接）往往脆弱且因模型变换而频繁失效。

## 做法：用自定义标签替代 JSON 承载结构化信息

核心思路：**让模型输出一组约定好的 XML 风格标签，每个标签包裹一段独立内容**。解析时按标签边界提取，即使某个标签缺失或截断，也能保留前面完整的部分。

### 1. 设计标签协议

根据实际业务定义少数几个标签，避免嵌套。例如生成技术解读文章时可以约定：

```
<summary> ... </summary>
<key_points> ... </key_points>
<code_block> ... </code_block>
<step_list> ... </step_list>
```

给模型的 system prompt 明确说明：

- 必须使用上述四种标签包裹内容。
- 标签可以按顺序重复出现（如多个 `<code_block>`）。
- 不要使用 HTML 注释或额外属性。
- 如果内容本身包含类似标签的文本，请用 `<![CDATA[` ... `]]>` 包裹（可选，大多数模型会自行避开）。

### 2. 编写容错解析器

使用正则按 **开始-结束** 对提取。关键是不要求整个文本合法，只按标签名提取内容区间。

```python
import re

def extract_tag(text: str, tag: str) -> list[str]:
    pattern = rf"<{tag}>(.*?)</{tag}>"
    return re.findall(pattern, text, re.DOTALL)
```

对于可能缺失闭合标签的情况，可以增加“开放标签开始至结尾”的 fallback：

```python
def extract_tag_fallback(text: str, tag: str) -> list[str]:
    results = []
    for m in re.finditer(rf"<{tag}>(.*?)(?:</{tag}>|$)", text, re.DOTALL):
        results.append(m.group(1))
    return results
```

这样即使响应在 `<summary>` 内部被截断，也能取到截至截断点的内容，而不是完全丢弃。

### 3. 在 Agent 流程中的集成方式

在 OpenClaw 或自定义 Agent 里，LLM 调用节点返回原始文本后，先走标签提取器，产出结构化字典：

```python
raw = llm_response.text
result = {
    "summary": extract_tag_fallback(raw, "summary"),
    "key_points": extract_tag_fallback(raw, "key_points"),
    "code_blocks": extract_tag_fallback(raw, "code_block"),
    "steps": extract_tag_fallback(raw, "step_list"),
}
```

下游节点根据存在性判断，比如如果有 `summary` 则送入摘要卡片生成器，不做全有全无校验。对于代码块，还可以额外做语言标注，靠约定 `<code_block lang="python">` 这种格式，但非必须。

### 4. Prompt Engineering 要点

- 在 system prompt 里给一个完整示例，展示标签用法。
- 明确指出“如果内容不适合某个标签，可以省略，不要强行生成空标签”。
- 对于长文任务，建议分阶段调用：先让模型生成带标签的草稿，再由第二个轻量级调用补齐缺失标签，避免单次生成过长。

## 踩坑点

- **标签重名或嵌套**  
  如果模型自行嵌套了 `<summary>` 内部又写了 `<summary>`，简单正则只会匹配到第一个闭合，导致内容错误。可以在 prompt 里明确禁止嵌套，并在解析时优先匹配最外层标签（用更严格的 start/end 组合）。

- **标签名与自然语言混淆**  
  一些模型会在正文中讨论“请使用 `<summary>` 标签”，这时需要用更独特的标签名，如 `⟨report_summary⟩` 或 `【summary】`，但全角或特殊符号在部分模型上表现不一致，建议用英文全大写+下划线：`<REPORT_SUMMARY>`。

- **模型“学习”了 XML 但忘记闭合**  
  高频出现的情况：输出 `<summary>内容<summary>` 漏了斜杠。解析时可按开始标签到下一个开始标签或结尾截断，然后清理残留的标签名。可接受少量噪声。

- **CDATA 误用**  
  部分模型会把所有尖括号内容放进 CDATA，反而让提取复杂化。除非你的内容大量含标签，否则不推荐使用 CDATA 语法。

## 可复用建议

1. **协议即文档**：标签名和结构写进项目 README，让所有下游插件引用同一份约定，避免沟通偏差。
2. **解析器放进 MCP 工具**：封装为一个 `parse_tagged_output` 工具，供 Agent 在多步推理中随时调用，减少代码重复。
3. **结合少量校验**：提取后可以校验每个标签内容长度，若为空可以触发补全请求，而不是整体失败。
4. **日志保留原始响应**：始终保存 LLM 原始输出，便于出现异常时人工回检和改进解析规则。
5. **测试时的控制变量**：调高 temperature、缩短 max_tokens 模拟截断，测试 tag 提取的鲁棒性。

## 总结

从 JSON 转向自定义标签格式，本质上是**把输出协议从严格结构化降级为半结构化**，牺牲一点点解析精度，换来极高的工程稳定性。在长文生成、分段内容提取、流式多组件输出等场景下，这是一个低成本、高回报的实践。对 OpenClaw 社区来说，这种思路可以无缝嵌入现有的 Agent 工作链，搭配 MCP 工具做轻量后处理，让“不可靠的模型输出”变得可控。

不要再让一个花括号毁掉整段报告。让标签成为你解析链上的缓冲带，在截断和格式错误面前依然能够提取出有价值的内容。
