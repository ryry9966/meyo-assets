## 背景

最近用 OpenClaw 搭了一条内容同步管线，把某个垂直领域的信息流自动推到微博超话。流程本身不复杂：Agent 定时抓取远程数据，裁切文案，配上图片，调用微博发布接口完成发帖。真正让人头疼的，是图片上传的稳定性、接口限流和任务状态的持久化。这三块处理不好，一条管线要么丢帖子，要么被风控，要么事后根本查不出哪条没发成功。本文记录工程化过程中遇到的几个关键问题、解决思路和可复用的组件设计。

## 问题拆解

在 OpenClaw 环境下，整个动作用一个 Agent 执行，但它调用的工具链要分别处理以下三个痛点：

1. **图片上传**：微博发布需要提前将图片传到微博图床获取 pid，但移动端与 PC 端接口不同，上传成功率受 Cookie 有效性、图片尺寸、格式和时间窗口影响。
2. **接口限流**：超话发帖和图片上传有频率阈值，短时间内高频操作会触发“操作太频繁”或图形验证码，必须实现客户端侧的自适应等待。
3. **状态归档**：帖子可能是“待发”、“已发”、“失败（可重试）”、“放弃”，这些状态如果没有持久化，重启 Agent 或程序异常退出后无法继续推进。

## 做法与步骤

### 1. 图片上传组件化

使用微博移动端接口 `https://picupload.weibo.com/interface/pic_upload.php`，模拟 multipart/form-data 提交。OpenClaw 里我把它封装成一个 MCP 工具 `upload_image_to_weibo`，输入参数为本地图片路径和从环境变量读取的 Cookie（已登录）。

复现步骤：

- 从浏览器 DevTools 抓一次成功上传的请求，提取必带字段，包括 `app_id`、`min_pic_b`、`pic_b` 等。
- 注意到移动端接口会返回 `pid`，需配合 `size=2048` 参数限制最大宽高，否则大尺寸图会直接失败。
- Agent 调用该工具获得 pid 列表后，组装微博发帖 payload，通过 `statuses/update` 下发。

踩坑点：

- 微博图床对图片 EXIF 信息敏感，部分从 Unsplash 下载的图会因 metadata 过大被拒。处理方式是在上传前统一用 Pillow 压缩并剥离 EXIF，转 PNG/JPG，固定宽高不超过 2048。
- Cookie 过期检测：上传失败时返回 code 100005 或 redirect 到登录页，工具内部通过预先校验一次 /profile 接口来确保会话有效，若无效则向 Agent 返回错误并终止此次发布。

### 2. 限流控制与退避

微博超话相关接口（包括获取超话列表、发帖、上传图片）共享一个频率窗口。经验数据：同账号每 30 秒最多 3 次写操作，连续触发则被限 5-10 分钟。

工程化做法：

- 在 Agent 调度层实现令牌桶（Token Bucket），桶容量设为 3，令牌生成速率 1 个/10 秒。
- 每次发帖前尝试获取令牌，获取不到则等待。若接口仍然返回 5020 “发送太频繁” 等错误码，切换至指数退避（2s→4s→8s）重试，最多 3 次。
- 将限流信息反馈给 OpenClaw 的任务调度：当出现连续限流，Agent 直接将该任务挂起 600 秒并写入归档，避免浪费资源。

踩坑点：

- 首次测试时只用 sleep 固定间隔，结果遇到跨时段的限流窗口滑动，接连被封 2 小时。加上随机抖动（jitter）后问题明显减少。
- 超话自身的标签也有写入阈值，同样要纳入桶计数，所以最好将“检查超话是否可发”也算作一次请求。

### 3. 状态归档设计

使用本地的 SQLite 建一张 `posting_jobs` 表，每条记录包含：`id, content, pic_paths, pid_list, status, retry_count, error_msg, created_at, updated_at`。MCP 工具每次操作后同步更新状态。

状态机设计：

pending → uploading_img → img_uploaded → posting → posted / failed  
failed 中 retry_count < 3 可回到 uploading_img 重试；≥3 标记为 abandoned。

Agent 启动时先查询所有 status 为 pending 或 failed（且 retry_count < 3）的任务，重新投递。这样可以保证进程重启不丢任务。

踩坑点：

- 图片上传成功但发帖失败时，如果没记录 pid，重试时会重新上传，浪费图片存储配额。因此务必在 `img_uploaded` 阶段持久化 pid 列表。
- 归档表里要记录错误信息，方便事后排查。比如 cookie 过期错误要单独分类，提醒人工更新。

## 可复用建议

1. **工具化拆分**：将微博操作封装成 MCP server，例如 `weibo-mcp`，对外提供 `upload_image`, `post_weibo`, `check_limit_status` 等工具，让不同 Agent 直接复用。
2. **限流中间件**：实现一个通用的 RateLimiter，可以是令牌桶+退避的组合，与业务逻辑解耦。OpenClaw 的工具可以声明自己的限流需求，由 Agent 运行时统一管理。
3. **状态表模板**：准备一份 SQLite 迁移脚本，包含任务表、限流日志表，作为自动化发帖类管线的基础设施，直接粘进新项目。
4. **监控与告警**：在归档表上挂一个简单的轮询，当 abandoned 比例超过阈值时，通过 Webhook 推送到 IM，避免无声积累失败任务。

## 总结

微博超话同步看似是一个简单的发帖动作，实际落到自动化管线里，图片上传、限流和状态归档这三块必须当作一等公民来设计。图片上传要处理尺寸、EXIF 和会话有效性；限流不是等多久的问题，而是要用令牌桶+退避+抖动来适应不确定的风控窗口；归档是整条管线的韧性基础，没有它，Agent 就只是用一次抛一次的脚本。这几部分一旦模块化，可以轻松移植到其他社交媒体自动化的场景中，比如小红书笔记发布、贴吧发帖等，本质上都是对同一组工程问题的变体。
