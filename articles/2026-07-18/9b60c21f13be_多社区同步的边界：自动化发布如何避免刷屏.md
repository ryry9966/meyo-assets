## 背景

在 OpenClaw 生态里，用 Agent + MCP 把技术文章一键推到多个社区已经不是新鲜事。典型的链路是：写 Markdown → Agent 调用各平台 MCP（掘金、知乎、SegmentFault、Dev.to、Twitter/X 等）→ 格式化内容 → 发布。这类工具链在“一次撰写、多处触达”上效率极高，但也非常容易踩进一个工程陷阱——**同步即刷屏**。

我所在的小团队基于 OpenClaw 自己搭建了一套内容分发流水线，前期的发布全是“全自动、零延时”模式。上线不到一周，就收到了两个明确的负反馈：其一，Twitter/X 上短时间内连发三条相似内容，关注者手动取关；其二，某中文社区后台警告“单日发文量异常”。回头看，这是我们完全忽视了**跨平台发布的时间窗口与频次边界**。

## 问题拆解

自动发布造成刷屏，表象是时间线污染，根因却来自几个维度的设计缺失：

1. **无延时编排**：所有目标平台在同一个 Agent 工作流中顺序或并发执行发布，各平台几乎同时命中。
2. **缺乏平台频率感知**：不同社区对发帖频率的容忍度差异很大。比如 Dev.to 容忍每小时 3 条以下，知乎专栏日更 2 篇已是上限，而 X 平台短时间频繁 API 调用本身就容易触发限流。
3. **内容特征重复**：相同摘要、相同链接在短时间内出现在不同平台，信息流智能算法会将其识别为垃圾内容，进而降权或限制分发。

如果不加以控制，自动化不但不能放大影响力，反而会消耗账号信用。

## 做法：用调度 Agent 构建时间边界

我们没有推翻已有的 MCP 发布工具链，而是在其上增加了一层**发布调度 Agent**。核心思路是把“发布”变成一个可延迟、可限流、可分时的任务队列，而非即时执行动作。

### 1. 发布任务入队，而非直接执行

每篇待发布内容生成后，不直接调用各平台 MCP，而是写入一个发布任务队列（我们用本地 SQLite + JSON 实现，无外部依赖）。每条任务包含：目标平台、内容 Payload、计划发布时间窗口、优先级等字段。调度 Agent 作为常驻 Worker，按规则消费队列。

### 2. 基于平台特性设定频次规则

在配置文件中为每个平台定义频率边界，以 YAML 为例：

```yaml
platforms:
  zhihu:
    min_interval_min: 360        # 最小间隔 6 小时
    daily_limit: 2
    allowed_hours: [9, 22]      # 允许发布的时间区间
  devto:
    min_interval_min: 120
    daily_limit: 4
  x:
    min_interval_min: 45
    daily_limit: 10
    jitter_sec: 300             # 随机抖动 ±5 分钟
```

调度 Agent 每次从队列取任务前，会通过对应 MCP 查询该平台今日已发布次数（可从平台自身接口读取，或自建计数器）。只有同时满足间隔、日内上限、时间窗口的任务才会真正执行；否则任务保持阻塞，等待下一轮检查。

### 3. 引入随机抖动与分时发布

各平台即使都满足条件，也并非立即并发。我们在 Worker 中增加了全局的 **任务间最小步长**（默认 90 秒），并对每个平台的执行时间加一个随机抖动（±jitter_sec）。这样即使三四个平台都处于可发布状态，也会在时间轴上自然错开。对于同一篇文章需要在不同平台发布的情况，我们特意在配置中设置了 `cross_platform_delay_min: 30`，保证跨平台之间有至少 30 分钟的时间差，避免阅读者“一眼看到同一内容”。

### 4. 预检与降级

在真正调用发布 MCP 之前，调度 Agent 会进行预检：检查内容中是否包含正确的规范链接、Markdown 渲染兼容性（例如知乎不支持某些 HTML 标签）、图片是否可正常外链等。预检失败则任务进入“待修复”状态，通过 OpenClaw 的内部通知 Agent 推送到维护者，不强行发布。这减少了因格式问题导致的发布失败和重复试发。

## 踩坑点

- **API 限流远比想象中隐蔽**：一些平台不会立刻拒绝请求，而是将频繁发文悄悄降权，导致发布成功但无人可见。我们在 X 平台吃过亏，最后只能通过拉取近 24 小时的 Impression 数据来反向判断是否被限制。
- **时间窗口的时区问题**：所有允许发布的时间窗口必须以目标平台时区为准，而不是 UTC。知乎的“流量高峰”在 UTC+8 的晚 8 点前后，错配时区会导致发布在凌晨，错失互动。
- **动态内容去重**：有时需要在多平台发布高度相似但略有调整的版本（如开头引语），简单的哈希去重会失效。我们最终基于文本相似度（MiniHash）做了一个轻量检查，当两篇内容相似度超过 0.9 且目标平台不同时，强制延长跨平台延迟。
- **状态计数不一致**：某平台发布成功后，它的“今日发文数”可能要等几分钟才更新。我们采用本地持久化计数器 + 查询平台接口双重校验，避免计数器滞后造成的频次误判。

## 可复用建议

1. **发布规则一定要外部化配置**，不要硬编码在 Agent prompt 或脚本里。随着账号成长，平台策略、发布的间隔都需要快速调整。
2. **给 Agent 设计“发布日志”和“操作回放”能力**，每条发布任务的调度决策和最终结果都记录在案。出了问题不用猜，直接回看调度过程。
3. **保留人工介入的入口**。我们在 OpenClaw 工作流里为调度 Agent 设置了一个“待审核”状态，紧急内容或高价值内容可以手动解除所有间隔限制，但要记入审计日志。
4. **不要过度设计**。如果只有两三个平台，分时队列已经足够，无需引入复杂分布式调度框架。先用最小可行调度验证频次假设，再逐步优化。

## 总结

自动化内容分发的本质不是“快”，而是**在多个社区之间建立可持续的发布节奏**。不加边界的一键同步，往往在技术上是成功的，在运营上却是失败的。通过一个轻量的发布调度 Agent，结合平台 MCP 的实时状态检查，我们能够将全自动发布拉回到一个安全区间，既保留自动化效率，又不透支社区信任。

如果你也在用 OpenClaw 体系搭建自己的内容分发工具，建议优先把精力投入在“边界设计”而非“速度优化”上。一条能被时间线接受的帖子，远胜过五条被系统折叠的刷屏。
