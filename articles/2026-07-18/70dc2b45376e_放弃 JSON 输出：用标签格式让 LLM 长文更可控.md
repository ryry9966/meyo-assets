## 背景

在使用 OpenClaw 搭建自动化工作流时，经常会遇到需要 LLM 输出结构化长文的场景：生成多段摘要、按章节输出报告，或者一次性返回多个候选回答。很长一段时间里，我的第一反应是让模型返回 JSON，例如：

```json
{
  "sections": [
    {"title": "...", "body": "..."},
    {"title": "...", "body": "..."}
  ]
}
```

但一旦正文内容变长，JSON 的稳定性就迅速崩塌——少一个引号、多一个换行、body 里出现未转义的特殊字符，整个 `JSON.parse` 就直接抛错。这对于跑在 Agent 流水线里的自动化任务来说不可接受，因为容错逻辑一写就复杂，而且耗费 token。

后来我把输出格式从 JSON 改成了类似 XML 的 **标签格式（tag-based format）**，解析变得异常稳定，即使正文里出现奇怪的字符，也基本不会破坏结构。这篇文章就聊这个切换过程，以及在实际工程中怎么设计标签格式。

## 坏 JSON 的根源

长文场景下 JSON 容易坏，核心原因有三个：

1. **LLM 是 token 序列生成器，不是语法检查器**  
   在生成长文本时，模型需要同时维护内容连贯性和 JSON 语法正确性。一旦内容里出现双引号、反斜杠或换行，模型忘记转义的概率很高。

2. **长上下文中括号匹配压力大**  
   多层嵌套的 `{}` 和 `[]` 在长输出时容易漏掉闭合。哪怕漏一个括号，整个结构就毁了。

3. **修复 JSON 的成本高**  
   很多开发者会加一个“重试”步骤，让 LLM 修复自己的坏 JSON。但这是补丁，不是方案：一是浪费 token 和延迟，二是修复可能引入新错误，甚至内容失真。

## 转向标签格式

标签格式的思路很简单：用成对的、不易自然出现的标记（和内容类型无关），包裹每段结构化内容。类似前端模板里的 `{% block %}` 或 XML 的 `<section>`。

比如要求模型输出如下格式：

```
<section>
<title>趋势分析</title>
<body>
这段时间的流量变化……
</body>
</section>

<section>
<title>建议措施</title>
<body>
建议从以下几点入手……
</body>
</section>
```

**优点很直接：**

- 不依赖转义，正文里直接放引号、换行、代码块都不影响结构。
- 标签名唯一性强，正文偶然出现 `<section>` 的概率极低；即使出现，也可以通过“输出开始/结束哨兵”做范围隔离。
- 解析简单，一段正则 `/<section>(.*?)<\/section>/gs` 就能把所有区块抓出来，然后分别提取 title 和 body。

对比 JSON，这种方式把“结构维护”交给了显式且简单的分隔符，大幅降低了 LLM 的认知负担。

## 做法与步骤（以 OpenClaw 插件为例）

1. **设计标签名称**  
   选取和业务无关、不易出现在正文中的标签，比如 `<reply-block>`、`<entity>`。长度适中，不要过分精简导致误匹配。

2. **在 prompt 中硬约束格式**  
   给出示例，并明确说明“只输出以下格式，不要添加额外解释”。示例一定要包含空行和可能的特殊字符，示范正确处理方式。

   示例 prompt 片段：
   ```
   你需要按以下格式输出，每个章节以 <section> 开始，以 </section> 结束，
   章节内包含 <title> 和 <body> 标签。
   示例：
   <section>
   <title>摘要</title>
   <body>
   这是第一段内容，可以包含 "引号"、换行等。
   </body>
   </section>
   ```

3. **解析端实现**  
   从模型完整响应中提取有效内容。因为模型有时会在前后附加短句，可以使用一个整体输出哨兵，比如要求以 `<output>` 开始、`</output>` 结束，作为提取边界。

   一个可靠的解析流程：
   - 用 `/<output>(.*?)<\/output>/s` 提取内容块。
   - 再按 `<section>` 切分成多个片段。
   - 每个片段内提取 `<title>` 和 `<body>` 的 inner text。
   - 容错处理：若某段缺失闭合标签，则丢弃该段或合并到上一段，不影响其他部分。

   相较于 JSON 解析，这种局部容错特性非常关键——一个区块坏掉不影响其他区块的提取。

## 踩坑与注意点

- **嵌套内容处理**  
  如果 body 里可能包含 `<title>` 这样的字串，就会出现标签混乱。实践中我会对标签名加前缀或使用少见的分隔字符，比如 `|~title~|`，并在 prompt 中强调“不要输出与标签完全相同的字符串”。

- **模型偶尔在标签内加空格**  
  输出可能出现 `< section>` 或 `</section >`，需要解析时做正则的兼容处理，比如 `<\s*\/?\s*section\s*>`，消除空格影响。

- **标签闭合不完整**  
  正则的 `.*?` 非贪婪匹配可以解决大多数情况，但必须在匹配时加上 `DOTALL` 标记（让 `.` 匹配换行）。如果某个 section 没有闭合，可以设置超时或最大长度限制，防止贪婪吞并后续内容。

- **在 Agent 链条中保持格式一致性**  
  多个 Agent 之间传递结构化信息时，最好统一一个标签格式规范，否则每次都需要写格式转换器，增加维护成本。

## 可复用建议

- 对于需要分段提取的多段结构，**优先用自定义分隔标签**，而不是 JSON。尤其是正文可能包含自然语言、markdown 代码块时，标签方式的鲁棒性远高于 JSON。
- 在 prompt 里提供一个包含特殊字符的示例，比纯文字说明更有效，可以直接降低转义错误。
- 如果输出格式比较固定，可以使用类似 `yaml` 的 `---` 文档分隔符，但注意内容中可能包含 `---`；标签的显式开关语义更清晰。
- 封装一个通用的标签解析工具函数，放入项目公共模块，后续所有需要结构化长输出的场景都直接复用。

## 总结

放弃 JSON 并不是否定结构化输出的价值，而是在长文本生成这个特定条件下，选择一种对抗 LLM 生成缺陷的更可靠格式。标签格式胜在容错性强、解析简单、边界清晰，尤其适合自动化流水线里那种“没人盯着看、出错就要重跑”的任务。

如果当前你的 OpenClaw 自动化流程还在因为一个格式错误反复重试，不妨试试把 JSON 换成标签格式，多测试几轮长边界，大概率会平稳很多。
