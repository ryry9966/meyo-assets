## 背景：内容自动化的“黑盒”难题

在基于 OpenClaw 或自定义 Agent 搭建的内容发布流水线中，最常见的工作模式是“生成 → 推送”。Agent 根据关键词与配置生成文章正文，调用图片生成服务产出配图，最后通过 MCP 或 API 写入 WordPress、Notion、飞书文档等目标平台。整个过程流畅、高效，解决了批量内容生产的问题。

然而一旦流水线跑顺，一个工程痛点会逐渐浮现：**没有本地归档，所有产出物只存在于远端**。当需要回溯某篇文章的生成参数、重做封面图、审计模型行为，或是迁移发布渠道时，我们只能从远端反查，甚至无处可查。生成过程中的提示词、模型版本、种子值、时间戳等关键信息，散落在日志里或直接被丢弃。缺乏结构化归档，意味着内容资产的“可维护性”与“可复现性”极低。

本文不做复杂系统设计，而是给出一个轻量、工程化的本地归档方案：围绕文章 Markdown、图片文件以及一个描述性文件 `assets.json`，把每次生成的内容和元数据一起落地到本地文件系统，供后续检索、重处理或版本管理。

## 问题拆解

归档需要回答三个问题：

1. 文件如何组织才便于人工查看与程序读取？
2. 图片引用路径如何在 Markdown 中保持一致？
3. 哪些元数据值得保存，以及如何确保写入不被意外中断或覆盖？

## 做法与步骤

### 1. 确立归档目录结构

采用按年月分桶，内部以时间戳+slug命名子目录：

```
/archives
  /2025
    /01
      /20250112-1130-auto-posting-pipeline/
        - article.md
        - assets.json
        - cover.png
        - img_01.png
        - img_02.png
```

目录名包含时间 (UTC) 与文章 slug，人类可读，也方便排序。所有与该文章相关的图片均放置在同一目录下，避免相对路径引用跨层级。

### 2. 生成环节植入归档逻辑

在 Agent 完成文章生成后、发布前，插入一个归档步骤。以 Node.js 脚本为例（与 OpenClaw 插件体系容易集成），核心逻辑如下：

```ts
import { writeFile, mkdir } from 'fs/promises';
import path from 'path';

async function archiveArticle(params: {
  markdown: string;
  images: { filename: string; buffer: Buffer }[];
  meta: Record<string, any>;
}) {
  const date = new Date();
  const dirName = `${formatDate(date)}-${slugify(params.meta.title)}`;
  const baseDir = path.join(ARCHIVE_ROOT, getYearMonth(date), dirName);
  await mkdir(baseDir, { recursive: true });

  // 1. 写入图片文件
  for (const img of params.images) {
    await writeFile(path.join(baseDir, img.filename), img.buffer);
  }

  // 2. 处理 Markdown 内部图片引用，统一为本地相对路径
  let finalMd = params.markdown;
  params.images.forEach((img, idx) => {
    finalMd = finalMd.replace(
      new RegExp(`!\\[.*?\\]\\(.*?${img.filename}\\)`, 'g'),
      `![img${idx + 1}](${img.filename})`
    );
  });

  // 3. 写入文章 Markdown
  await writeFile(path.join(baseDir, 'article.md'), finalMd, 'utf-8');

  // 4. 生成 assets.json
  const assetInfo = {
    generated_at: date.toISOString(),
    model: params.meta.model,
    prompt_hash: hashPrompt(params.meta.prompt),
    images: params.images.map((img) => ({
      file: img.filename,
      prompt: img.prompt,
      seed: img.seed,
      model: img.model,
    })),
    tags: params.meta.tags || [],
  };
  await writeFile(
    path.join(baseDir, 'assets.json'),
    JSON.stringify(assetInfo, null, 2),
    'utf-8'
  );
}
```

归档最好在发布成功**之后**执行，避免发布失败却留下“孤儿文件”。但如果生成图片耗时较长，也可在图片产出后立即落盘，最后统一整理。

### 3. 与 OpenClaw 工作流的结合方式

无论是通过 OpenClaw 的 Plugin 机制，还是在 Agent 的 Tool 调用链里直接加入一个 `archive_content` 工具，实现都很直接。例如在 OpenClaw 的运行配置中定义一个新的 action：

```yaml
actions:
  - name: archive_post
    on: post_generated
    handler: ./handlers/archive.js
```

然后在 `archive.js` 中获得上游传递的文章内容、图片 Buffer 数组和元数据，执行上述逻辑。这样做的好处是归档与发布解耦，归档失败不会阻塞发布，但会输出告警。

## 踩坑与经验

**1. 图片引用不一致**

许多文本生成模型产出的 Markdown 里，图片链接是外部 URL（如 `https://image.example.com/abc.png`），归档时如果只保存图片文件而不修正 Markdown 引用，就会导致本地打开文章时图片无法展示。建议在归档环节统一重写为本地文件名引用，同时保留原始 URL 记录在 `assets.json` 的 `original_url` 字段中，以备溯查。

**2. 同名文件覆盖**

若同一 slug 在一个月内多次生成，简单的时间戳-秒级可能仍冲突。工程里我会在目录名追加 6 位短哈希（如 `20250112-1130-auto-posting-pipeline-a3f2e1`），成本几乎为零，换来了绝对的唯一性。

**3. assets.json 的原子写入**

使用 `writeFile` 时如果进程崩溃，可能导致 JSON 不完整。最好采用“写入临时文件 → 重命名”的方式实现原子替换。Node.js 中可以使用 `rename` 的跨分区兼容性需要注意，保守起见可在同一目录下创建 `.tmp` 文件后重命名。

**4. 图片文件名里的特殊字符**

图片提示词中可能包含冒号、引号等，直接截取作文件名会引发文件系统错误。我的做法是对提示词取稳定哈希（如 SHA256）前 8 位作为文件名，同时保留原提示词在 `assets.json` 中，无歧义且安全。

## 可复用建议

上述方案轻量到可以直接内嵌到任何 Node.js 或 Python 内容流水线中。面向 OpenClaw 用户，更推荐的复用方式是将归档逻辑封装为一个独立的 MCP Server 工具，以标准 Tool 接口暴露 `save_article_archive` 能力。这样无论是哪种 Agent 框架，只要支持 MCP，就能通过调用该工具完成归档，不必在每一个 Pipeline 里重复实现。

字段设计上，`assets.json` 里除了上文提到的基础信息外，还可以加入 `agent_version`、`pipeline_run_id`、`source_prompt`，未来在审计生成质量、对比模型表现时，这些数据会变得极有价值。甚至可以配合一个简单的本地静态页面生成器，将归档目录渲染成可浏览的归档站点。

## 总结

本地归档不是为了满足某种“数据洁癖”，而是把自动生成的内容从一次性消耗品转变成可追溯、可重处理的数字资产。这个习惯一旦建立，后续无论是迁移发布平台、调试生成质量，还是重新生成不同尺寸的配图，都会节省大量时间。而整个方案的核心只是三个文件类型的落地：Markdown、图片、一份结构化的 `assets.json`。没有外部依赖，不绑定任何特定平台，适合作为任何自动化内容系统的“最后一步”。
