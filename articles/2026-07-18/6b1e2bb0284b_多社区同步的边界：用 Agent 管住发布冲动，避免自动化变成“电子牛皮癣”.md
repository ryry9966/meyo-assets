## 背景：从一键发布到一键社死

技术作者普遍面临一个矛盾：内容需要在多个社区（Twitter/X、Discord、Reddit、微博、知乎、开发者社区等）分发以获取反馈，但逐个平台手动发布耗时且容易遗忘。于是自动化同步脚本/Agent 成了“救命稻草”——写完一篇总结，触发一次工作流，所有平台瞬间更新。看起来很高效，但实际上，这种无差别、零延迟的广播式发布极容易触发平台风控，更会让关注者感觉被刷屏，最终取关、静音，甚至举报。

更微妙的是，所谓“刷屏”并不只是频率问题。同样的长文同时出现在多个平台，会给人一种“批量灌水”的廉价感；但如果你为了适应不同社区去改标题、改结构，又增加了手工成本，自动化就失去了意义。

**我们要的不是彻底拒绝自动化，而是在 Agent 的编排下，让每一条发布都像是人写的、有边界感的投递。**

## 问题拆解：自动化发布踩到红线的 4 种方式

在实际工程中，自动化发布导致负面体验通常来自以下细节：

1. **时间撞车**：短文类似 Twitter、Mastodon 在 3 分钟内连发 5 条，哪怕内容不同，也被判定为机器人。
2. **内容一模一样**：同一段 Markdown 直接倒进微博、知乎和 Discord，连表情符号都不改，社区用户一眼识破。
3. **忽略社区规范**：Reddit 的板块禁止自荐，Discord 频道要求`#showcase`标签，微博需要头条文章格式，不遵守就直接被隐藏或删帖。
4. **缺少回撤机制**：一条错误的链接发布到 5 个平台，发现后必须逐个手动编辑，手忙脚乱。

真正的痛点不在于“能不能发出去”，而在于**是否能在多个社区的规则、节奏与人类观感的夹缝里，找到一条可编程的路径**。

## 做法：用 OpenClaw Agent + MCP 构建“带刹车”的同步管线

我当前的方案是基于 OpenClaw 的任务编排能力，配合多个平台 MCP 服务器，实现一个“分级异步、内容变形、频率受限”的发布代理。整体架构如下：

- **触发层**：本地 Git 仓库推送新帖 → 触发 Webhook 进入 OpenClaw Agent。
- **决策层（Agent 核心）**：Agent 读取文章元数据（标题、摘要、标签、目标社区列表），生成**发布计划**。这一步不是直接执行，而是输出 JSON 计划表：
  ```json
  {
    "tasks": [
      {"platform": "twitter", "content": "...改写摘要", "delay_seconds": 0},
      {"platform": "discord", "content": "...技术频道格式", "delay_seconds": 600},
      {"platform": "reddit", "content": "...提问式标题", "delay_seconds": 1800}
    ]
  }
  ```
- **执行层**：Agent 按计划顺序调度 MCP 客户端，调用对应平台 API。每个平台执行前检查两个条件：
  - **全局冷却**：过去 30 分钟内是否已有 2 次以上跨平台发布？如果是，暂停所有剩余任务，转为手动确认。
  - **平台速率**：读取该平台的本地限流记录（存储在 SQLite），确保不会突破 Twitter/Reddit 的短时间窗口限制。
- **内容变形中间件**：在执行前，Agent 会对原始正文应用平台适配指令。例如给 Twitter 生成 280 字符内的 thread 首条，给 Discord 加上代码块和 `##` 标题，给知乎重新生成开头提问句式。这是通过调用 OpenClaw 内部的模板引擎 + LLM 改写节点完成，但改写成本很低，仅在缓存未命中时触发。
- **回撤守护**：任务队列持久化在 SQLite。如果发布后 5 分钟内收到来自任意平台的“负面信号”（比如 Twitter 上被作者自己删除、Reddit 被移除），Agent 自动将同批其他平台任务标记为“待撤回”，并尝试通过 API 删除或编辑为“内容已修订”。这一步依赖平台 API 的撤回能力，但至少提供了止损入口。

## 踩坑实录：不是所有边界都能代码化

1. **MCP 服务器质量参差不齐**  
   Tweetnacl、Reddit API wrapper 还能用，但部分社区 MCP 实现只处理了 OAuth，没处理 429 重试、分页发布。结果 Agent 以为发送成功，实际平台返回 `rate limited` 5分钟后才报错。解决方案是为每个平台 MCP 客户端包裹一个重试/退避中间件，并将最终状态写回任务记录，而不是单靠返回值。

2. **“内容变形”容易出现失真**  
   如果让 LLM 自由改写技术帖，偶尔会加入幻觉解释，甚至把代码块替换成伪代码。必须约束：仅允许调整格式和开头引导句，禁止修改代码块、链接和数字。我的做法是提取出“不可变区块”（代码、链接、关键术语），将它们作为保护字段传入提示词，并要求模型输出 diff 而非全文。

3. **社区规则无法穷举**  
   即使提前给 Agent 喂了 Reddit 板块规则，仍然会遇到“管理员临时禁止某种格式”的情况。所以计划表中每个任务都预留 `requires_approval: true` 的选项，当 Agent 对规则不自信（比如板块规则变更检测到 404）时，自动转入人工确认队列，通过一个简单的 Web UI 或 Telegram Bot 推送审批。

4. **多平台发布≠多账号管理**  
   每个平台最好有独立的开发者应用和 Token，避免一处封禁牵连全局。但这增加了 OAuth 刷新的复杂度。我使用 OpenClaw 的 secrets 管理器轮换 token，并设置过期预警，算是勉强可用。

## 可复用建议：给自己画一条“人工感”红线

结合近半年的折腾，可以提炼几条直接能落地的原则：

- **把发布频率锁死在“人肉速度”**：即使技术上限允许 10 秒内发 5 个平台，也强制加入随机延迟（60~300 秒），并设置全局并发上限为 2。这样时间线上的关注者看到的是自然分布，而不是同步轰炸。
- **内容指纹 + 差异审计**：在发布前计算内容哈希，与过去 24 小时已发布内容的哈希比对，如果相似度 > 85%，阻止发布并询问。这能防止“改了两个字又发一遍”的意外。
- **永远保留一个手动终止开关**：所有自动化管道必须有一个“一键熔断”机制，不管是物理按钮还是 `/halt` 命令。一旦发现连锁反应，先停管道，再排障。
- **以“单平台首发，多平台延发”代替同步**：优先在一个核心社区发布并观察反馈，2 小时后 Agent 再将优化后的版本推送到其余渠道。这不光是边界，更是内容质量的迭代机会。

## 总结：自动化的终点，是让人感觉不到自动化

多社区同步的边界不是技术天花板，而是你愿意保留多少“人的痕迹”。当自动化发布系统开始精细地模仿人类的节奏、语气和社区礼仪，它就不再是刷屏工具，而是一个有分寸感的助理。

对于 OpenClaw 用户来说，这套方案完全可以建立在现有 Agent + MCP 的基础设施上，不需要引入第三方黑盒服务。你掌控的不仅是发布键，更是你在每个社区的数字体面。

记住一句话：**如果你的自动化让人一眼看出是自动化，那它已经越界了。**
