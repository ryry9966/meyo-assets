## 背景：JSON 的结构化幻觉

在 OpenClaw 的自动化流水线、MCP 工具链和 Agent 编排中，LLM 被很多开发者当作“解析器前的最后一公里”——让模型从非结构文本中提取字段，输出结构化 JSON，再交给下游脚本消费。看起来很美好，但一旦输出变长（例如一次提取多个文档、生成复杂配置），JSON 的稳定性就会急剧下降。

典型问题包括：

- 多出的反引号或 markdown 代码块标记导致 `json.loads()` 直接报错
- 嵌套对象里缺失引号、尾随逗号，或键值分隔符变成全角符号
- 模型中途提前闭合 `}`，后续内容变成无效尾巴
- 重复输出相同 key，甚至生成自相矛盾的字段

这些“坏 JSON”并非模型能力不足，而是长文生成时概率分布导致的格式衰退。尤其在非英语语境、微调较少的模型上更为频繁。重试（retry）和 function calling 能缓解但不能根除，引入 JSON schema 约束也会增加 token 开销，并且在小参数模型上效果有限。

曾用正则修复、用 `jsonrepair` 库兜底，但仍然遇到无法自动恢复的情况，导致整个 Agent 流程中断。这逼迫我重新审视一个问题：**我们真的必须输出严格 JSON 吗？**

## 问题拆解：为什么非 JSON 不可？

很多时候，我们只是需要一种能容纳多层字段、可被机器稳定解析的结构化文本，并不要求它 100% 符合 JSON 规范。下游代码可以自行处理，何必强求 LLM 输出完美 JSON？意识到这一点后，我开始尝试一种更宽容的方案：**自定义标签格式（tag-based format）**。

它的灵感来自 XML，但比 XML 更简单，只用少量固定标记来界定段落和字段，模型只需要学会“用开始/结束标签包裹内容”，规则极短，不容易出错。

例如，需要输出人员信息时，不使用：
```json
{"name": "张三", "role": "开发", "skills": ["Python", "Agent"]}
```
而使用：
```
<person>
<name>张三</name>
<role>开发</role>
<skills>Python, Agent</skills>
</person>
```
这种格式对 LLM 极友好：标签结构线性、不需要转义引号或处理逗号，模型可以逐行生成，不容易出现格式折断。

## 做法与集成步骤

### 1. 设计标签规范

为每个结构化“对象”定义一个包裹标签（如 `<record>`），内部字段使用语义标签（如 `<name>`、`<desc>`）。多值字段可以直接用分隔符（逗号、换行）放在同一个标签内，避免嵌套复杂度。

原则：
- 标签名使用小写英文下划线或驼峰，避免与自然语言冲突
- 开启一个新文档时，让模型将整个输出放入一个根标签（如 `<document>`）
- 明确要求“每条记录必须以 `<record>` 开始、以 `</record>` 结束”
- 内容中的 `<` 和 `>` 如果不作标签，可要求使用占位符 `&lt;` `&gt;`（简单场景下可忽略）

### 2. 编写 Prompt 示例

在提示词里用 few-shot 示例展示期望的标签格式，并把格式要求说得极其简短：

```
请严格按照下面的标签格式输出，且只输出标签文本，不要添加额外解释。

<document>
<record>
<name>张三</name>
<role>开发</role>
<skills>Python, Agent</skills>
</record>
</document>
```

对于 OpenClaw 的 prompt 模板，可以直接通过 `template` 或 `mcp_prompt` 注入。

### 3. 实现解析器

用 Python 写一个简单的逐行状态机解析器，而不是用正则一次性匹配整个文档。因为长文输出很可能不完整、末尾标签缺失，逐行处理能更精细地容错。

示例解析逻辑：
- 逐行读取 LLM 返回的 `content`
- 当遇到 `<record>` 开始一个新记录字典，后续行寻找 `<field>...</field>` 对
- 如果某个字段标签未闭合，就用当前行的剩余文本作为值，直到遇到下一个开始标签或结束标签
- 遇到 `</record>` 则把当前记录加入列表
- 最终返回记录列表，即便缺少尾标签也尽力收集

### 4. 集成到 OpenClaw 工作流

在 `post_process` 钩子或自定义插件中调用解析器。可以将解析结果转换为标准 dict/list，再传回流水线。若解析失败，记录 raw 文本并告警，而不是直接中断。

```python
def parse_tagged_output(raw_text):
    records = []
    current_record = None
    current_field = None
    current_value = []

    return records
```

## 踩坑点

1. **标签与内容的冲突**  
   当模型输出“`<name>`”这种字符串作为字段值时会破坏解析。解决方式：在 prompt 中明确“标签仅在结构层出现，内容中不要包含尖括号”，对于无法避免的场景，提供转义说明（`&lt;`）但不可靠。折中方案是使用罕见分隔符（如 `{{name}}`）替代尖括号标签，但因为 LLM 对少见标记记忆不深，需要更多 few-shot 示例。

2. **模型忘记闭合标签**  
   特别是整篇文档末尾，模型常常漏掉 `</document>`。在做解析时，必须在遇到 EOF 时自动闭合所有已打开但未关闭的标签，并把当前缓冲的值写入记录。

3. **多记录输出时的标签嵌套混乱**  
   如果让模型同时输出 `<records>` 作为外层，偶尔会出现 `<record>` 未结束就开始下一个。解析器需要强健：如果遇到新 `<record>` 但上一个尚未闭合，则先强制保存当前记录，再开启新记录。

4. **歧义空格与换行**  
   标签内部的值可能包含换行，这需要解析器按标签边界拆分，而不是简单按行拆分。推荐方法是先用正则 `<[^>]*>` 分割 token 再处理。

## 可复用建议

- **建立企业内部统一的标签规则库**：例如 `<entity>`、`<sent>`、`<rel>` 等，供不同 Agent 复用，降低 prompt 设计成本。
- **结合 Markdown 代码块**：提示模型输出在 ` ```tag ` 代码块内，这样能防止外围的评论干扰解析，又保留了标签格式。
- **工具化解析器**：把上述状态机封装成 OpenClaw 的一个 MCP 工具或插件，接收原始文本，返回结构化 JSON，这样其他流程无需改动即可兼容。
- **监控与自修复**：在流水线中加入标签闭合检查，若发现闭合不完整，自动调用一次 LLM “修复”请求（只给模型提供有问题的片段，让它补全标签），大部分情况下能自动恢复。

## 总结

从强迫 LLM 输出完美 JSON，到采用标签格式主动适应生成的不确定性，这一步转变让长文结构化输出的稳定性提升了不止一个量级。标签格式并不完全替代 JSON——它牺牲了 schema 校验与类型严格性，但换来鲁棒性、更低的 token 开销、更高的可解析率。在 OpenClaw 这类需要高自动化、低人工干预的工程化环境中，这种务实的妥协非常值得。

如果你的流程还在和坏 JSON 做斗争，不妨花半小时设计一套简单标签，用状态机解析。你可能会发现，Agent 的“幻觉”大幅减少，流水线因为格式错误而中断的次数曲直线下降。
