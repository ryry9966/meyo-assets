## 背景

在构建基于 LLM 的自动化管道时，我们经常要求模型输出结构化数据，然后由下游 Agent 或插件消费。对于短文本或简单任务，直接要求输出 JSON 是可行的。然而，一旦需要生成长篇报告、多段分析或嵌套列表时，JSON 的可靠性急剧下降。

典型场景包括：用 OpenClaw 生成日报摘要并提取关键指标，由 MCP 工具解析后写入数据库；或让 Agent 从会议记录中抽取行动项并格式化交给任务系统。这种长文输出中，最常见的问题就是 JSON 结构被破坏。

## 问题：JSON 脆弱性在长文本中的表现

LLM 生成 JSON 时，常见失败模式包括：

- **括号/引号未闭合**：生成到一半被截断，最后缺少 `}` 或 `]`。
- **非法转义**：文本中包含未转义的双引号或反斜杠，例如：“他说：“你好””。
- **尾部逗号**：最后一个元素后多余逗号，很多解析器会报错。
- **嵌套对象中的幻觉键**：模型在长文本中突然添加一个未要求的字段，破坏 schema。
- **截断内容不完整**：超过输出 token 限制时，JSON 几乎肯定损坏。

修复这些问题的常规手段是重试、后处理正则修复，或使用结构化输出（如 OpenAI function calling 的 `strict` 模式）。但重试浪费 token，正则修复不可靠，而严格的结构化输出对长文本的 schema 定义和平台支持仍有局限。更根本的是：**JSON 不太适合人类或模型书写长内容**——它要求每个细节都符合机器解析规范，而模型本质上是在生成自然语言。

## 做法：切换到标签格式，把解析责任从模型转移给解析器

我们的核心思路是：让模型使用 **自定义标签** 包裹不同语义块，而不是嵌套 JSON。模型的任务是遵守简单的打开/关闭标签约定，解析工作由确定性的后处理器完成。

### 步骤 1：设计标签 Schema

以生成一份“日报摘要 + 关键指标 + 待办事项”为例，标签格式可以这样设计：

```
<report>
<summary>这里是多段自然语言摘要，可以包含换行和标点，只要不包含 </summary> 字面量。</summary>
<metrics>
<metric><name>营收</name><value>123.45</value><unit>万元</unit></metric>
<metric>...</metric>
</metrics>
<action_items>
<item><desc>整理周报数据</desc><owner>张三</owner><deadline>2025-03-20</deadline></item>
</action_items>
</report>
```

提示词中明确说明：只允许标签及其内容，不要添加额外解释。并给出一个完整示例。

### 步骤 2：实现确定性标签解析器

编写解析函数，基于简单的状态机扫描文本。以 Python 为例，核心逻辑：

- 定义允许的顶层标签集合。
- 逐字符遍历，当遇到 `<tag>` 时入栈，记录开始位置；遇到 `</tag>` 时出栈，提取内容。
- 不依赖正则或 XML 库，避免处理转义实体的复杂性。
- 如果发现未闭合标签，可以返回部分解析结果并标记 `partial=True`，供上游决策。

这种解析器极其便宜，没有递归深度问题，并且不会因为内容中的特殊字符（如 `<`、`>`）而崩溃，只要我们在提示中要求模型避免输出裸的尖括号或使用实体转义 `<` `>`。即使模型违规，我们也可以通过简单启发式修复（例如将未匹配的开标签视为普通文本）。

### 步骤 3：在 OpenClaw 流程中集成

在 OpenClaw 中，通常通过 prompt 模板调用 LLM。我们将标签指令作为系统消息的一部分，并配置输出解析器为自定义标签解析器。如果解析失败，触发重试逻辑，但根据我们的经验，标签格式的重试率远低于 JSON。

**重试策略建议：**

- 若检测到未闭合标签，向模型发送简短纠正提示：“请补全 </summary> 标签后继续。”
- 如果多次失败，降级为纯文本处理（使用正则提取关键信息），保证管道不中断。

## 踩坑点

1. **模型仍可能输出多余的解说前缀**。例如以“好的，以下是报告：”开头。解决方法：在 prompt 中要求“只输出指定标签包裹的内容，不要任何前置或后置文本”，并在解析前调用 `strip()` 去除首尾空白，若仍以非 `<` 开头则裁剪到第一个 `<`。对于严重违规，触发重试或自动裁剪。

2. **标签嵌套时的内容泄露**。比如 summary 中出现了 `</metrics>` 这样的字面量，导致解析器提前闭合。我们要求在 prompt 中告知模型避免输出标签关闭字符串，并在解析时进行嵌套检查：如果当前内容中出现了不应出现的闭合标签，可认为解析异常提高重试。

3. **多段相同标签的歧义**。`<metric>` 可能有多个，需正确处理重复同级标签。解析器应维护列表，遇到同名标签就累积。

4. **token 过长被截断**仍然是任何格式都存在的问题。处理方式与 JSON 相同：设置足够大的 `max_tokens`，并在解析失败时判断是否因 `finish_reason=length`，如果是，则要求模型从截断点续写，或忽略该不完整块。

5. **模型版本差异**。有些模型对标签格式的遵循度更好（如 GPT-4o、Claude 3.5），而弱一些的模型仍需更严格的示例引导。建议在提示中使用少样本示例。

## 可复用建议

- **保留 schema 的简单性**：尽量避免深层嵌套，两层通常足够（如 `<items><item>...</item></items>`）。复杂结构拆为多次调用，每次返回更简单的部分。
- **定义 MCP 工具约定**：如果你的 OpenClaw MCP 服务需要消费标签格式，将解析器封装成可导入模块，并提供 schema 验证函数，让其他 Agent 也能复用。
- **使用流式聚合**：如果必须流式输出，在收到完整标签前不解析，可以使用缓冲区策略：当检测到顶层闭合标签后触发一次解析。
- **记录解析失败**，并统计不同模型使用标签格式的失败率，用于后续调优。

## 总结

放弃 JSON 直接用标签格式，本质上是承认 LLM 在生成结构化长文本时的不完美，把确定性工作交给代码，把灵活性留给模型。这种设计在工程实践中提高了稳定性，减少了重试次数和意外中断，也降低了对模型版本的依赖。

对于在 OpenClaw、Agent 和自动化管道中大量使用 LLM 生成结构化内容的团队，标签格式是一种简单、可靠、易调试的选择。它的代价仅仅是编写几十行的解析器，收益却是管道更加健壮。
