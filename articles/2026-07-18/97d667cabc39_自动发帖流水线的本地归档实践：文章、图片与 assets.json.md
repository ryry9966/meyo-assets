## 背景

在基于 OpenClaw 搭建的自动发帖流水线中，Agent 会串联大模型生成文章、调用绘图模型生成配图，最后通过社区 API 将内容发布出去。这些内容通常只存在于线上平台，本地仅保留构建脚本和少量中间日志。一旦需要回溯修改、分析生成质量，或想用历史产出做训练语料，就会面临内容缺失、结构混乱、图片链接失效等问题。

因此，为流水线引入系统性的本地归档机制，将文章、图片及其关联关系落盘保存，就成了一件投入不大但长期收益明显的事。

## 问题

最初的流水线只在发布成功后记录一条日志，内容本身既不落盘，也不保存结构。随着发布数量增加，陆续暴露出几个具体痛点：

1. **文章与图片关系断裂**  
   Markdown 中引用的是绘图模型返回的临时 URL，这些链接在若干小时后就会失效，事后根本无法还原帖子的视觉效果。

2. **内容版本失控**  
   同一篇帖子可能被 Agent 反复修改、重新生成，但没有保留历史版本，难以对比不同 prompt 的效果。

3. **缺少结构化元数据**  
   比如某张图片用了哪个模型、什么参数、生成时间等，全部散落在日志里，事后再查如同考古。

4. **无法用于下游任务**  
   想用历史产出微调模型或构建检索库时，原始素材往往已经不完整，需要大量人工整理。

## 做法

核心思路是：在发布环节之前插入一个“归档步骤”，将文本、图片和元数据结构化存储到一个本地目录中。目录结构如下：

```
posts/
├── 2025-03-01-troubleshooting-llm-concurrency/
│   ├── post.md          # 替换为本地引用后的正文
│   ├── images/
│   │   ├── a1b2c3.png   # 以内容哈希命名的图片
│   │   └── ...
│   └── assets.json      # 图片与元数据的映射文件
└── ...
```

### 1. 确定归档时机

在 Agent 完整生成帖子内容（Markdown 文本 + 图片 URL 列表）并确认润色无误后，发布之前执行归档。这样即使后续发布失败，本地仍有一份一致的记录。

### 2. 处理文本与图片引用

拿到原始 Markdown 文本后，遍历其中的图片链接。为避免后续打开本地 Markdown 时出现破图，将远程 URL 替换为相对路径 `images/<hash>.png`。原始链接可以以 HTML 注释形式保留，方便溯源。示例：

```markdown
<!-- original: https://cdn.example.com/temp/xxx.png -->
![架构图](images/a1b2c3.png)
```

### 3. 下载图片并避免冲突

用图片 URL 的 SHA256 前六位作为文件名，既避免重名又能快速判断重复。下载时设置超时和重试（如 3 次，间隔 2 秒），防止网络波动导致归档不完整。如果已经在 images 目录下存在相同哈希的文件，则直接复用，防止重复下载浪费资源。

### 4. 构建 assets.json

为每个帖子生成一份 `assets.json`，记录该帖所有图片的元数据。一个最小可行的 Schema 如下：

```json
{
  "post_title": "排查 LLM 并发限制的三种方法",
  "generated_at": "2025-03-01T10:30:00Z",
  "images": [
    {
      "local_path": "images/a1b2c3.png",
      "original_url": "https://cdn.example.com/temp/xxx.png",
      "prompt": "A flowchart showing rate limiting strategies",
      "model": "flux-pro-1.1",
      "size": "1024x768",
      "generated_at": "2025-03-01T10:28:00Z"
    }
  ]
}
```

字段不必一次完备，先从最核心的 `local_path`、`original_url`、`prompt` 开始，后续按需扩展。保持结构的可读性和可解析性即可。

### 5. 实现层面的简化

将上述逻辑封装成一个独立函数或脚本，接收 Markdown 文本和图片列表，返回归档后的本地路径。在 OpenClaw 的 pipeline 中，可以在发帖 Action 之前插入这个归档 Action，完全无侵入。

实际代码可以用 Python 实现，不到 100 行。核心依赖只有 `requests`、`hashlib`、`json` 和标准库的路径处理，适合嵌入到任何 Agent 工具链中。

## 踩坑点

1. **带鉴权的图片 URL**  
   某些绘图平台返回的临时 URL 不需要鉴权即可直接下载，但私有化部署的模型可能要求 Bearer Token。如果 Agent 调用的是内部绘图服务，下载时记得带上相同的认证头。

2. **并发归档的目录冲突**  
   如果流水线并行发布多篇帖子，同时创建同一日期目录时可能引发竞态。使用 `os.makedirs(path, exist_ok=True)` 并捕获异常，可以避免大部分问题，但更稳妥的做法是用时间戳到毫秒级命名目录，或引入文件锁。

3. **assets.json 的原子写入**  
   直接 `json.dump` 到文件，如果归档过程被中断，可能留下不完整的 JSON。建议先写入临时文件，然后 `os.replace` 到目标位置，保证写入是原子的。

4. **URL 引号与特殊字符**  
   Markdown 中的图片语法可能会有各种变体，例如带 title、跨行、URL 包含括号等。正则替换容易遗漏边界情况，推荐用 Markdown 解析器（如 `mistune`）提取图片节点，再回写相对路径，可靠性更高。

5. **视频或其他媒体**  
   如果帖子包含视频，assets.json 可以扩展 `type` 字段，不做强行限制。但视频体积大，归档策略需要单独考虑（例如只存元数据，不下载原始文件）。

## 可复用建议

如果想在多个项目中复用这套逻辑，两点建议：

- **抽成 MCP 工具**  
  归档功能本身很适合封装成一个 MCP server 工具，例如 `archive_post`，接收文本和图片 URL 列表，返回本地归档路径和 assets 信息。这样 OpenClaw 中的任何 Agent 都可以直接调用，无需重复实现。

- **去重与增量归档**  
  在 assets.json 中维护一个全局的图片哈希索引，跨帖子共享，可以大幅减少重复下载。如果后续接入 Git 版本控制，每次归档自动 commit，就形成了一个自带历史的内容仓库。

## 总结

本地归档看似是一件“顺便做”的小事，但它为自动化内容工程提供了一个可靠的事实基础。所有 AI 生成的内容最终都变成可查、可管、可训练的结构化资产，后续无论是做质量分析、修订，还是把历史帖子作为 ICL 示例注入新的任务，都变得顺理成章。

对于已经使用 OpenClaw 搭建自动化流水线的同学，这个轻量级归档方案不需要改动核心逻辑，却能明显提升整个系统的工程成熟度。
