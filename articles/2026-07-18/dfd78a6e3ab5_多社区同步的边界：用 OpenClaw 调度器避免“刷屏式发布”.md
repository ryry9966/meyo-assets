## 背景：从一键发布到被限流，只差一个调度器

随着 MCP 生态和 OpenClaw Agent 的成熟，越来越多的开发者搭建了自己的内容发布管道。只需一条指令，Agent 就能将文章推送到掘金、SegmentFault、知乎、CSDN、个人博客等多个平台。这看起来很高效，但实际使用中却常常遭遇账号风控、内容降权甚至封禁——原因只有一个：**粗暴的全量同步像极了刷屏脚本**。

各社区都有反滥用机制。短时间内同一账号、同一 IP 连续发送高度重复的内容，会被自动判定为垃圾信息。即使你写的是原创技术文章，这种“广播式”发布依然会触发红线。我们需要的不只是“能发”，而是“发得聪明”，让自动化发布遵守每个平台的社交契约。

## 问题拆解：一次性全发的代价

- **风控触发**：知乎对高频率操作敏感，连续发布多篇文章可能直接锁账号；掘金会检测文章的相似度，完全相同的 Markdown 正文可能被标记为“低质”。
- **读者反感**：同一天内在多个平台看到一模一样的标题和内容，读者会认为你是在机械分发，损害个人品牌。
- **资源浪费**：如果某个平台的 Cookie 已过期，批量发布时整批失败，你没有机会补救，只能全量重试，进一步加剧风控。

我们需要一个发布调度层，它介于 Agent 的内容创作与目标平台 API 之间，负责**流量整形**和**内容微调**。

## 实现方案：用 OpenClaw 构建带边界的发布 Agent

整个方案基于 OpenClaw 的任务编排能力和 MCP 服务器封装，核心是在“内容源”和“目标平台”之间加入一个可控的调度器。

### 1. 定义统一的发布任务模型

```typescript
interface PublishTask {
  id: string;
  contentHash: string;
  title: string;
  body: string;
  summary: string;
  tags: string[];
  targetPlatforms: string[];
  tweaks: Record<string, any>; // 按平台微调
  status: "pending" | "scheduled" | "success" | "failed";
  retries: number;
  scheduledAt: number;
}
```

内容在生成后先进入任务队列，不与平台直接耦合。

### 2. 平台适配层：MCP 工具

为每个社区实现一个 MCP 工具，例如 `post_to_juejin`、`post_to_zhihu`。这些工具封装鉴权（Cookie/OAuth）和发布接口，可以单独测试和调度。Agent 通过工具选择器调用它们，而不是一次性全调。

### 3. 调度策略：分批 + 随机延迟

将目标平台列表拆分为多个批次，每批最多 2 个平台，批次间引入随机间隔（10~30 分钟），同一批次内各平台也间隔至少 3~5 分钟。这模拟了人类在不同的时间窗口手动登录、复制粘贴的节奏。

一个简单的 YAML 配置：

```yaml
publish_schedule:
  - batch: 1
    platforms: [juejin, segmentfault]
    base_delay_min: 10
    jitter_min: 5
  - batch: 2
    platforms: [zhihu]
    base_delay_min: 25
    jitter_min: 10
  - batch: 3
    platforms: [csdn, dev_to]
    base_delay_min: 15
    jitter_min: 5
```

OpenClaw 的 Agent 可以通过定时器 MCP 工具或内置的 `setTimeout` 语义实现延迟触发，而不是死板的 `sleep`，以便在等待期间还能响应其他任务。

### 4. 内容差异化：小幅改写防去重

大多数平台使用 SimHash 或 MinHash 检测重复内容。完全一致的正文会被降权。我们可以在 Agent 里内置一个微调模块（例如基于提示词的轻量改写），针对不同平台的口味做局部调整：

- 知乎：标题可能加上“？”句式，开头增加一段个人观点。
- 掘金：标题保留技术关键词，加上“实战”或“原理解析”。
- Dev.to/Medium：英文翻译或双语摘要（如果目标包含海外平台）。

改写程度控制：只调整 5%~10% 的正文，不改变技术事实，不虚假润色。改写后的版本仍由 `contentHash` 关联，避免重复发布。

### 5. 状态持久化与幂等发布

用 SQLite 或本地 JSON 文件记录每个平台的文章发布状态。每次触发时，先查询该平台是否已存在同一 `contentHash` 的成功记录，存在则跳过。失败记录则根据重试次数和冷却时间决定是否尝试。

重试时加入指数退避，且重试前先检测当前平台是否处于可发送状态（如检查 Cookie 有效期），避免盲目重试加剧风控。

## 踩坑记录

- **无官方 API 的平台**：用模拟登录和 Cookie 处理的 MCP 工具极易因平台升级而失效。建议将 Cookie 刷新逻辑做成可手动触发的子工具，定期检查健康度。
- **IP 信誉联动**：如果你同时在开发机器、服务器和本地调试，IP 变化可能触发异地登录保护。要么固定出口 IP，要么为每个平台维护独立 HTTP 会话（Agent 可以做到，但需要额外管理）。
- **平台的特殊限制**：掘金草稿箱有上限，知乎专栏发布需要人工审核首篇文章。自动化不可越俎代庖，需要在这些环节设置“卡点”，等待人工确认。
- **高并发任务的顺序性**：如果任务队列中同时有 5 篇文章等待发布，必须保证同一平台的文章串行发表，而不是并发。否则，平台看到的是一秒内多篇同时冒出来，刷屏警告立即生效。

## 可复用的工程建议

- **永远不要同时推超过 2 个平台**，除非你有多年养号经验。
- **将“生成”和“分发”彻底解耦**：生成后的内容存放至公共缓冲区，分发 Agent 按计划消费，互不阻塞。
- **搭建预生产环境**：用一个低粉丝量的小号先行跑通全流程，确认调度策略和改写模板不会触发风控，再切换到正式号。
- **幂等设计是底线**：同一文章绝不重复发布，状态记录要能扛住进程重启。
- **做好失败预警**：当任一平台连续失败 2 次，Agent 应通过通知 MCP（如 Bark、企业微信）提醒人类介入，而不是静默停止。

## 总结

自动化发布不是机械广播，而是一场与平台社交规则的精细共舞。用 OpenClaw 的能力，我们完全可以在保持多社区覆盖的同时，做到克制和分散，就像一位真正的创作者的发布节奏。边界控制——分批延迟、内容微调、幂等、监控——这些看似多余的环节，恰恰是长时间稳定运营的基石。下次你的 Agent 再帮你发文章时，让它等一等、改一点，账号才能活得更久。
