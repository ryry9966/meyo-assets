## 背景

不少开发者维护着三到五个技术社区账号——个人博客、Dev.to、掘金、Medium、SegmentFault，外加 X/Twitter 这样的社交渠道。一篇有质量的长文，自然希望在不同平台获得曝光。过去靠手工逐个发布，很容易忘记某个步骤；现在有了 Agent、MCP 服务器和 GitHub Actions，一键全发变得非常容易。

问题也由此产生：**当同一篇文章在几分钟内出现在所有关注者的时间线上，就变成了刷屏**。尤其在技术圈关注者重叠度高的社区（比如同一个人既关注你的掘金，又关注你的 Twitter），这种重复曝光会消耗信任。平台方（如 Dev.to、Medium）也会对短时大量相似内容产生警惕，甚至限流。

这篇文章复现一个基于 OpenClaw Agent + MCP 工具编排的**多阶段安全发布管线**，重点讨论如何用工程化手段控制节奏、减少冗余，而不是抑制发布。

## 问题拆解

刷屏的根源不是“多发”，而是 **“多条内容在短时间内被同一个社交图谱捕获，且信息增量几乎为零”**。

具体表现为：
- 在 10 分钟内，同标题、同段落内容出现在 4 个平台；
- 社交平台直接搬运全文，没有做网址规范化（canonical），导致关注者点进去发现是同一篇文章；
- 没有利用平台的摘要、导语做差异化，阅读体验重复。

因此，自动化发布的核心矛盾不是速度，而是**时间间隔、内容裁剪与平台特性匹配**。

## 做法：设计三阶段发布模型

我基于 OpenClaw 的 Agent 调度器，配合多个社区的 MCP 服务器（Dev.to MCP、自定义的 Medium API 封装、Twitter API v2 工具），搭建了下面的发布管线。

### 阶段一：首发平台（博客 / 主社区）
- 将 Markdown 原文推送到自建博客（例如 Hugo + GitHub Pages）或你指定的“规范源”。
- 同时，在 Dev.to 设定 `canonical_url` 指向博客，避免搜索引擎把转载当原创。
- **立即发布**，不延迟。这一步的目的是建立内容权威源，并为后续渠道提供引用基础。

### 阶段二：长文社区延迟分发
- 在 GitHub Actions workflow 中，通过 Agent 调度 MCP 工具，对掘金、SegmentFault、Medium 等平台执行**延迟发布**。
- 延迟时间至少为 **4–6 小时**，视时区而定。例如，假设博客首发在北京时间 8:00，那么掘金安排在 14:00，Medium 安排在次日凌晨（覆盖欧美阅读高峰）。
- 每个平台发布前，用 Agent 自动做两件事：
  - 提取文章第一段，改写为平台风格的“导读”或“摘要”（而不是直接复制开头）；
  - 检查该平台是否已有相同内容指纹（标题 hash + 前 200 字 hash），防止重复发布。

### 阶段三：社交平台摘要推送
- 对 X/Twitter 等短内容渠道，只发布**2-3 句摘要 + 链接**，并且进一步延迟 12–24 小时。
- 可配置为发布到博客的链接（或阶段二中表现最好的长文社区链接），并附上不同角度的评论（例如一次强调解决的问题，一次强调适用场景），避免两条推文看起来雷同。

### 调度实现细节
在 `.github/workflows/distribute.yml` 中设置多个 job，利用 `sleep` 或 `schedule` 事件实现时间差。OpenClaw Agent 以 MCP client 的身份连接各平台 MCP server，统一管理认证和重试策略。

为了避免手工维护时间偏移，可以使用一个 YAML 配置文件：
```yaml
platforms:
  - name: juejin
    delay_hours: 6
  - name: medium
    delay_hours: 22
  - name: twitter_summary
    delay_hours: 28
    variant: problem_solving
```
Agent 读取该配置，按序执行，日志统一回写。

## 踩坑记录

1. **API 限频与重试风暴**  
   Dev.to 每分钟允许的发布次数极少，如果多个 job 同时触发，会触发 429。解决方法是在 MCP 工具层实现指数退避 + 队列化，确保同一平台同一时间只有一个有效请求。

2. **认证过期静默失败**  
   Medium 的 token 有时会突然失效，HTTP 返回 401，但部分 SDK 仅返回空字符串。需要通过 Agent 监控两个信号：HTTP 状态码和返回内容中是否包含文章 ID。失败则通过持久化通知（如 Slack Webhook）告警，而不是静默跳过。

3. **平台格式转换导致 “空文”**  
   Markdown 转掘金/Medium 时，代码块、自定义 HTML 可能被吞掉。务必先经过一个“可发布格式校验” step：将 Markdown 转为该平台富文本后，检查字数是否大于 300，否则中断并报告异常。

4. **时区陷阱**  
   GitHub Actions 的 cron 使用 UTC，而业务延迟基于北京时间容易计算错误。建议所有延迟配置统一用 UTC 偏移量，由 Agent 在运行时根据目标社区的主要读者时区动态调整，避免手动换算。

## 可复用建议

- **建立发布指纹库**：在 CI 中生成 `sha256(title + first_200_words)`，存入 JSON 文件作为发布记录。每次发布前校验，防止因为人工干预而重复推送。
- **区分 “通知” 与 “内容” 渠道**：博客、掘金、Medium 是内容主体；Twitter、Telegram 频道、Discord 只是通知。后者永远只推摘要 + 链接，且间隔拉开。
- **增加人工确认节点**：完全自动化容易变成“一错全错”。在 stage 2 执行前，Agent 可以通过 issue comment 或 Approve 按钮请求发布许可，这样既能自动化，又保留了人控的保险。
- **使用 OpenClaw 统一观测**：将所有 MCP 工具调用日志收敛到 Agent 的 trace 中，当出现发布失败时，可以回放步骤，快速定位是哪个平台的认证或限频问题。

## 总结

多社区同步不是“一键分发”的能力问题，而是 **信息节奏的控制问题**。用 Agent 编排延迟、指纹去重、内容摘要差异化，才能让自动化真正服务于个人品牌，而不是消耗它。

本次实践的管线已开源在 [GitHub](#)（示例仓库），你可以直接 fork，替换自己的 MCP 配置和平台凭证。减少刷屏，不是少说话，而是说得有节奏。
