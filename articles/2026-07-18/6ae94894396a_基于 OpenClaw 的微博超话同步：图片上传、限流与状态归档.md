## 背景

在内容多平台分发的自动化场景中，微博超话是一个容易被低估的渠道。相比普通微博，超话帖子的曝光更聚焦，适合面向特定兴趣圈层做持续运营。考虑到人力维护成本，用 Agent 自动推送内容到指定超话就成了自然的选择。

我在 OpenClaw 上搭建了一个轻量分发 Agent，对接内部内容源，定时将筛选后的图文同步到微博超话。整个过程在工程上本质是一次“带外序状态管理”的 API 编排：把本地的图文资源，通过微博开放接口安全送达，并在多重限制下保持可控。

这篇记录聚焦其中最棘手的三个环节：图片上传、接口限流、以及发布状态的可靠归档。希望给同样在 OpenClaw/Agent 生态里做社交平台自动化的同学一些可以复用的参考。

## 问题拆解

微博超话发帖的底层接口仍然是 `statuses/share`（或 `statuses/update`），只是多出一个 `topic` 参数指向超话名称。实际压力来自两点：

1. **图片必须先上传获得 `pic_id`，再随文本一起提交**，且上传接口对格式、大小、频率都有独立限制。
2. **全局限流 + 用户级限流**：测试应用每天调用总量限制，单用户写操作限制更严格，超频后直接封禁一段时间，重则降权。

除此之外，自动化发布要能追溯“这条内容到底发没发成、需不需要重试、是不是已经发过”，这就要求有一个哪怕简陋的状态归档机制，否则 Agent 的自动重试会把限流问题放大，甚至造成重复发布。

## 做法与步骤

### 1. 获取 access_token 并缓存

使用微博开放平台的 OAuth2 授权，拿到具有一定时效的 `access_token`。Agent 启动时检查本地缓存，若过期则自动用 refresh_token 续期，避免每次调用都走授权流程。这一步直接关系到后续稳定性，因为在图片上传高峰期如果触发续期接口的并发，很可能被判定异常。

### 2. 图片上传：构造合法的 multipart/form-data

微博图片上传接口 `https://api.weibo.com/2/statuses/upload_pic.json` 要求以 `multipart/form-data` 提交，且图片字段名必须是 `pic`，同时附带 `access_token` 作为表单字段。关键约束：

- 图片格式仅支持 JPEG、GIF、PNG，且文件大小不能超过 5MB（注意 GIF 动图实际有额外隐藏限制）。
- 文件名需保留扩展名，否则服务端可能拒绝。
- 每次上传成功后返回的 `pic_id` 仅在很短的时间窗口内有效（观察下来大约 5 分钟），之后发布微博时若继续使用该 ID，可能触发“图片无效”的错误。

Agent 侧实现时，我封装了一个 `upload_image` 工具，入参为本地图片路径，内部完成类型校验、压缩（按需）、构造请求、解析返回的 `pic_id`，并立即传递给下一步的发布流程，防止过期。

### 3. 发布微博到超话

使用 `statuses/share` 接口，参数 `status` 拼接超话标签，形如 `#超话名称#` 再加正文，并带上 `pic_id` 参数。注意官方文档中有时用 `pic_id` 有时用 `pic_ids`，这里使用 `pic_id` 传单个字符串即可。测试中使用多张图需要上传多次获取多个 ID 并以逗号分隔传入 `pic_id`。

发布成功会返回微博 `id` 和 `mid`，这两个数值是后续归档和监控的关键标识。

### 4. 限流处理

微博开放平台对不同等级的应用和接口设有限流规则，开发者后台可查。我的 Agent 运行在测试应用等级下，每天总调用次数有限，且写接口（发微博、上传图片）的维度更细。实际遇到的限流形态：

- HTTP 状态码 403，错误码 `10006` 或 `10022`，提示频率受限。
- 有时不是 403，而是返回空或超时，需要做好超时重试但不放大请求。

应对策略上并没有去“破解”限制，而是采用经典令牌桶 + 本地队列：

- 为图片上传和发微博分别设置最小间隔（如 6 秒 / 条），令牌桶控制瞬时并发为 1。
- 触发限流错误后立即退避（指数退避 + 抖动的上限设为 120 秒），并将此次任务重新排入队列尾部。
- 运行时缓存当天已消耗调用次数，接近阈值时暂停非关键任务，留给重要内容。

### 5. 状态归档

单纯的自动化发布不够，必须可追溯。我设计了一个轻量的 SQLite 归档表，字段包含：

- `local_content_id`：内部内容 ID
- `task_type`：图片上传 / 发帖
- `api_response_code`、`weibo_id`、`created_at`
- `status`：pending / success / failed / throttled

在每次 API 调用完成后立即写入一条记录，发布成功时更新最终微博 ID。这样：

- 重试逻辑可以检查是否已有成功的发布记录，避免重复发。
- 发生异常时，可通过 `throttled` 记录统计限流频次，调整间隔。
- 便于后期做对账和监控看板，不必回查微博平台。

## 踩坑点

1. **图片文件名的坑**：某次图片处理后临时文件没有扩展名，上传接口返回“图片格式不支持”，但错误信息模糊，查了半天才发现是服务端依靠扩展名判断类型，而非文件魔术字。
2. **`pic_id` 过期**：批量图文场景下，图片上传和发帖之间如果因为限流排队等了超过 5 分钟，会导致发布失败。解决办法是将 `pic_id` 的获取和发布操作绑定成一个原子任务，不提前批量上传。
3. **Content-Type 头填充**：构造 multipart 请求时，不要手动设置 `Content-Type` 头，让 HTTP 客户端自动生成带 boundary 的头部，否则服务端解析失败。
4. **超话名称中的特殊字符**：超话名带点号或特殊符号时，需在 `status` 中使用完整正确的话题格式，比如 `#超话·名称#`，并确保编码为 UTF-8。
5. **access_token 过期后 403**：错误码和限流 403 容易混淆，Agent 需要区分 token 过期（错误码 21332 等），触发自动续期并重试。

## 可复用建议

- **封装为 OpenClaw MCP 工具**：将图片上传、发帖、状态查询包装成标准的 MCP 资源或工具，这样任何 Agent 可以直接调用，而不必重复处理 multipart、限流等细节。
- **本地队列 + 退避做成独立限流器插件**：因为微博的限制参数可能在动态调整，把令牌桶、退避策略、日调用计数做成可配置的插件，可以在类似 API 接入场景复用（比如微信公众号、B站动态等）。
- **归档数据模型**：设计足够通用的状态表，字段不用绑死微博，扩展为 platform、post_id 等，可支撑多平台分发状态聚合。

## 总结

微博超话同步的自动化并不复杂，但工程细节容易被低估。图片上传的时序强关联、限流的隐形限制、状态的散落，是实际生产中最常出问题的地方。通过把上传与发布原子化、内置限流排队、做好本地归档，我们能够在 OpenClaw 的调度下，获得一个相对稳定的分发流水线。

对于想做类似接入的同学，重点不是去克服微博的反爬或各种检测，而是用最朴素的后端工程方法，把状态管好、把调用节奏控稳，Agent 的可靠性自然就上来了。
