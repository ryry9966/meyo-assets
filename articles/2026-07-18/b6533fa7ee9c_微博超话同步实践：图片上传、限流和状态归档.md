## 背景

几个月前，我需要把一批经过筛选的图片和文案，按固定频率推送到某个微博超话。源内容来自内部素材库，信息已经过编辑，剩下的事情是自动化发布。原以为无非是调用微博开放 API，结果卡在了图片上传、接口限流和重复发布的处理上。

正好团队在用 OpenClaw 串联这类长尾自动化流程，我便把整个同步链路拆成了 OpenClaw 工作流，结合自建的 MCP 工具和本地状态存储，跑了一段时间后，基本稳了下来。下面把当时的做法和踩坑点还原一遍，给有类似需求的同学参考。

## 问题拆解

微博超话发帖接口是 `statuses/update`，支持携带图片，但图片必须先通过 `statuses/upload` 上传获取 `pic_id`。所以一条图文帖的发布需要至少两次 HTTP 调用。

真正让我难受的是三个问题：

1. **图片上传不稳定**：偶尔返回 `-1` 或超时，但不是接口挂了，重试又常常能成功。
2. **接口限流难以预判**：开放平台的文档里写了“测试权限 150 次/小时”，但在实际调用中，有时不到 100 次就开始返回错误码 `10022` 或 `10023`，而且没有明确的 `Retry-After` 头。
3. **重复发布**：触发器周期性扫源目录，源文件可能还在，如果不记录“哪些内容已经发过”，同一条内容会在每个周期再发一次。

这三个问题如果不解决好，要么丢帖，要么被限流卡死，要么超话变垃圾桶。

## 做法 / 步骤

### 1. 工作流编排

我把整个过程拆为 5 个步骤，用 OpenClaw 的节点串联：

- **素材拉取**：从标记目录读取待发布文件，解析文案和图片路径，生成一个 JSON 列表。
- **状态检查**：逐条对比本地 SQLite 数据库内的 `source_id`，过滤掉已处理项。
- **上传图片**：调用 MCP 工具 `upload_weibo_image`，传入本地图片路径，返回 `pic_id`。
- **发布帖子**：调用 MCP 工具 `post_weibo_status`，带上文案和 `pic_id`。
- **状态归档**：发布成功后，将 `source_id`、微博返回的 `id`、时间戳写入 SQLite。

触发器使用定时节点，每 30 分钟跑一次。这样不会持续占用 OpenClaw 线程，也方便错开峰值。

### 2. MCP 工具封装

为了实现可靠的重试和限流处理，我并没有在 OpenClaw 流程里写一堆 `retry` 节点，而是把微博相关的 API 封装成两个 MCP 工具，部署在本地 MCP Server 里。工具内部统一做了：

- **图片上传重试**：最多 3 次，间隔 2 秒，遇到网络错误或返回码 `-1` 时触发，最后一次失败才向上抛出异常。
- **发帖限流处理**：捕获 `10022`（IP 请求超限）或 `10023`（用户请求超限）错误码，自动退避 60 秒后重试，最多 2 次；如果还是失败，则将请求写入延迟队列文件，由另一个 10 分钟的慢轮询流程补发。
- **日志透传**：每次调用将请求参数和返回写入本地日志，方便排查。

这样一来，OpenClaw 主体流程保持简洁，只关心成功或最终失败，失败时则由错误处理分支发通知。

### 3. 状态归档的细节

为了避免重复发布，我建了一张简单的表：

```sql
CREATE TABLE IF NOT EXISTS post_history (
    source_id TEXT PRIMARY KEY,
    weibo_id  TEXT,
    created_at TEXT
);
```

每次发布成功后立即 `INSERT`。这里有个小坑：并行发布时如果同一个 `source_id` 被多个 worker 抢到，可能出现竞态。由于我现在是单实例串行消费，暂时安全。后续如果扩展到多进程，会考虑用 `INSERT OR IGNORE` 加唯一约束来兜底，或者引入 Redis 分布式锁。

## 踩坑点复盘

1. **图片上传接口不返回 `Retry-After`**  
   微博的限流错误码只告诉你“超限了”，不告诉你要等多久。我最初用固定 5 分钟退避，结果仍可能撞墙。后来改为“先退 60 秒，再退 120 秒”，同时监控连续失败次数，达到阈值后暂停整个流程 30 分钟，避免无效重试堆满日志。

2. **防盗链导致图片 403**  
   发布成功后，微博前端有时会返回缩略图不显示，排查发现是因为上传的图片链接被第三方服务引用时触发了防盗链。这个与 API 无关，但如果业务上需要用外部链接引用图片，需要预先将图片传到微博图床或使用允许的域名。我的场景里只在客户端展示，影响不大。

3. **超话发帖需要 cookie 吗？——不需要，但权限要够**  
   测试环境和正式应用在超话发帖上行为一致，只要应用通过审核并拥有“微博高级写入”权限，`statuses/update` 带上 `visible` 参数设置超话即可。不要尝试模拟 cookie 或网页端接口，那样反而容易被风控。

4. **状态归档的文件锁**  
   我用的是单文件 SQLite，定时任务并行执行时会短暂锁定，但 SQLite 的 WAL 模式基本够用。如果并发量更大，建议切换到 PostgreSQL 或者使用 OpenClaw 内置的全局 KV 存储（如果有），减少耦合。

## 可复用建议

- **抽象成可配置的 MCP 工具**：上传图片和发帖这类原子操作，直接做成 MCP 工具，后续无论哪个工作流要发微博，都可以复用同一套重试和限流逻辑。
- **用延时队列处理限流后任务**：别在流程里死等，把被限流的请求序列化到文件或 Redis，再由低频任务轮询重放，可明显降低踩踏风险。
- **设计状态存储的幂等主键**：使用内容哈希或源系统 ID 作为主键，业务层保证 `INSERT` 一次，就不会重复发布。不要依赖自增 ID 或时间戳。
- **监控失败率，而不是单条失败**：微博 API 偶发性失败很正常，单条失败可重试或丢弃，但整体失败率陡增时一定要告警，可能是 token 过期、IP 被封或接口变更。

## 总结

把微博超话同步做得“能用”和“不惹麻烦”，关键在于把重试、限流和去重这些脏活沉到工具层，让上层流程只关心业务逻辑。OpenClaw 的编排能力配合 MCP 的工具抽象，正好匹配这种分层思路。状态归档虽然简单，但一旦疏忽，带来的内容重复会让超话体验急剧下降。

目前这套工作流已经稳定运行了几个月，每天大概处理 20~30 条帖子，偶尔遇到限流也能自动恢复，几乎不需要人工干预。如果后续要扩展到其他社交平台，这套“上传-发布-归档”的模式大概率也能复用，只是细节需要适配各自的 API 特性。

如果你也在做类似的多平台同步，欢迎在社区交流更轻量的状态管理方案。
