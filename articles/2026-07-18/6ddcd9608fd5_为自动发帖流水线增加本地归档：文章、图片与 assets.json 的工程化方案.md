## 背景

使用 OpenClaw 搭配 Agent、MCP 工具链自动生成内容并发布，已经是很多效率场景的常见玩法。一条流水线可能包括：拼装 prompt → 调用模型生成 Markdown → 生成配图 → 调用发布接口 (如小红书、公众号、Notion)。但多数方案只关注“发出去”，对生成过程的原始产物（最终 markdown、图片、元数据）缺少系统化的本地留存。

缺少归档的代价会慢慢显现：想对历史内容做二次改写或再分发，找不到原始材料；平台故障或封号导致历史文章丢失；图片引用全部是临时链接，离线后无法查看；想分析自己生成过什么、哪些效果好，却没有可供查询的结构化记录。

本文介绍一种轻量、可集成到现有自动化流程中的本地归档方案，围绕三种核心资源：文章 (Markdown)、图片文件和描述资源清单的 `assets.json`。

## 核心问题

自动发帖流水线产生的资产通常散落在临时目录或内存中：

- 文章正文可能是在 Agent 返回后直接被消费，没有落盘。
- 图片可能由图片模型生成后，上传到图床仅保留在线 URL，本地不留底。
- 发布状态、时间、标签等元数据分散在平台后台或 workflow 的运行日志里，缺乏统一视图。

想在本地重建一份“内容资产副本”，必须解决三个具体问题：

1. 如何设计目录结构，让归档可读、可扩展。
2. 资源清单 (`assets.json`) 应包含哪些字段，才能兼顾查询和可追溯性。
3. 如何将归档步骤嵌入现有自动化流水线，且不干扰主流程。

## 做法与步骤

### 1. 目录结构设计

以每次生成任务为一个归档单元，目录按 `YYYYMMDD-{slug}` 命名，包含：

```
archive/
  20250410-how-to-backup-automation/
    article.md
    images/
      cover.png
      diagram.png
    assets.json
```

`slug` 取自标题的英文或拼音缩写，确保可识别。如果同一天可能生成多篇同主题内容，可追加自增序号或短 UUID。

### 2. assets.json 字段约定

为让以后的工具可以轻松扫描所有归档，约定一个最小但实用的 JSON 结构：

```json
{
  "id": "20250410-how-to-backup-automation",
  "title": "为自动发帖流水线增加本地归档",
  "created_at": "2025-04-10T14:30:00Z",
  "tags": ["automation", "archiving", "openclaw"],
  "source": {
    "prompt": "你是一个技术作者...",
    "model": "gpt-4o",
    "image_model": "dall-e-3"
  },
  "files": {
    "article": "article.md",
    "images": [
      "images/cover.png",
      "images/diagram.png"
    ]
  },
  "publish": {
    "platform": "xiaohongshu",
    "status": "draft",
    "published_at": null
  }
}
```

字段可按需扩展，关键是保证 `id` 与目录名一致、`files` 中的路径相对于归档根目录有效，这样任何程序都能通过解析 `assets.json` 找到对应文件。

### 3. 集成到流水线

典型的流水线步骤：Agent 输出 markdown 正文与图片 URL/ base64 → 下载或保存图片到临时目录 → 发布 → 归档。

归档逻辑放在发布步骤之后（或并行）执行。用一个独立脚本或 MCP tool 完成以下操作：

- 接收参数：文章文本、图片路径列表、元数据 (标题、标签、prompt 等)。
- 根据标题生成目录名，做安全处理（去除特殊字符、截断长度）。
- 创建归档目录及 `images/` 子目录。
- 将 markdown 正文写入 `article.md`。
- 将图片文件复制/移动到 `images/`，同时修正 markdown 中的图片引用为相对路径 `./images/xxx`。
- 组装 `assets.json` 并写入。
- 输出归档目录路径，供后续版本管理 (git commit) 或同步使用。

如果你已经在用 OpenClaw 的 MCP 插件，可以把上述逻辑封装成一个 MCP tool，接受文本和文件路径，返回归档结果。在 Agent 的执行计划里，在发布工具之后调用该 tool 即可。

## 踩坑点

- **图片引用修正**  
  Markdown 中往往包含临时图床链接或绝对路径。归档时必须将图片引用替换为 `./images/xxx.png`，否则离线查看文章时图片会失效。建议先下载图片到 `images/`，再对 markdown 做正则替换。

- **并发任务与命名冲突**  
  如果流水线是异步处理多条内容，必须保证目录名唯一。单纯用日期 + slug 不可靠，推荐在生成目录名时附加一个短随机后缀，或在 `assets.json` 内部使用 UUID 作为唯一 ID。

- **assets.json 的更新策略**  
  初次生成只有 `draft` 状态，后续发布成功或修改后如何处理？简单做法是“覆盖写”：每次流水线最终状态重新生成整个归档目录，老版本由 git 保留历史。更精细的做法是只更新 `assets.json` 中的 `publish` 字段，但会增加逻辑复杂度，初期不建议。

- **文件名安全处理**  
  标题可能包含空格、斜杠、emoji，直接用于目录名会在不同操作系统上出问题。必须转换为只含字母、数字、短横线和下划线的字符串，中文标题可转拼音或直接用英文 slug。

- **大图片与存储膨胀**  
  如果图片模型输出 raw 大图，直接归档会快速占满磁盘。可在保存前用图像库做一次无损压缩或调整尺寸上限，保持归档可用性的同时控制体积。

## 可复用建议

- **封装为标准 Tool**  
  将归档操作写成独立脚本 (Python/Node)，或封装成 MCP tool，与具体发布平台解耦。这样无论发布到小红书、微信公众号还是自建站点，都可以复用。

- **搭配版本控制**  
  归档目录本身纳入 git 仓，每次生成自动 commit。这样不仅有多版本记录，还能通过 git log 看到生成时间线。

- **结构化查询能力**  
  定期扫描所有 `assets.json`，导入简单的本地 SQLite 索引，可快速回答“上周生成了多少篇带‘教程’标签的文章”这类问题。

- **与自动化平台的分层**  
  不要把归档逻辑塞在发布 workflow 的主路径中。建议发布成功后再触发归档，避免归档失败阻塞发布。可用 n8n 的“on success”分支或 webhook 触发独立归档流程。

## 总结

本地归档是自动化内容生产中被严重低估的一项基础能力。它不复杂，却可以在平台变动、数据丢失、二次创作等场景下省去大量回溯成本。通过统一的目录结构、结构化的 `assets.json` 和可复用的归档工具，你可以让每一条自动生成的内容都在本地留下完整“足迹”。这件事越早做，收益越大，建议在现有流水线里花一小时做好第一版归档脚本。
