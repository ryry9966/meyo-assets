在基于 Agent 的自动发帖流水线里，我们经常让 LLM 生成一篇 Markdown 文章，有时候还会调用图像生成接口为文章配上插图。文章和图片最终被发布到不同平台，但流水线本身往往缺少一个规范的本地归档环节。一段时间后，想回溯某篇文章的原始内容、配图版本，或者做内容再加工，就会发现原始资产散落在日志、临时目录甚至只存在于别人的 CDN 上。

这篇文章介绍一种轻量的本地归档做法：把文章（Markdown）和图片统一保存到本地，用 `assets.json` 文件作为资产索引，方便自动化流水线查询和维护。

## 背景与问题

典型的内容自动化流水线长这样：Agent 生成 Markdown 正文，同时可能返回几张图片的远程 URL（比如来自图床或对象存储）。发布模块负责将 Markdown 渲染并推送到平台。如果发布成功，很多团队就直接把中间产物丢弃了。

这会带来几个问题：
- **链接失效风险**：远程图片可能过期或被删除，文章“失图”后无法恢复。
- **回溯困难**：没有原始 Markdown 的版本记录，后续优化 prompt 或分析内容质量时缺少对照。
- **资产复用成本高**：想用同一批图片生成不同格式的内容（如图文笔记、视频脚本），需要重新搜索下载。

这些问题的根源并不是架构缺陷，而是缺少一个统一的本地资产存储和索引机制。

## 方案设计：目录结构与 assets.json

我们选择在流水线的最后增加一个“归档步骤”，将每篇帖子打包到一个目录中，并在项目根目录维护一个 `assets.json` 文件作为全局索引。这样既保留了原始内容，又方便程序化访问。

### 目录结构

```
/posts
  /{slug}
    content.md       # 原始 Markdown 文章
    /images
      cover.png
      diagram.png
    metadata.json    # 可选，单篇元数据
assets.json          # 全局索引
```

`slug` 可以由标题或日期自动生成，确保唯一性。

### assets.json 的结构

```json
{
  "posts": [
    {
      "slug": "archiving-pipeline",
      "title": "自动发帖流水线的本地归档方案",
      "created_at": "2025-03-15T10:00:00Z",
      "tags": ["automation", "archiving"],
      "content_file": "posts/archiving-pipeline/content.md",
      "images": [
        {
          "local_path": "posts/archiving-pipeline/images/cover.png",
          "original_url": "https://cdn.example.com/abc.png",
          "alt_text": "归档流水线架构图"
        }
      ]
    }
  ],
  "last_updated": "2025-03-15T10:05:00Z"
}
```

这个索引文件承担了三个角色：快速查找某篇文章的所有资产、记录原始图片来源（方便回溯）、为自动化工具提供可解析的资产清单。

## 流水线中的实施步骤

以下是一个典型的归档步骤实现（以 Python 脚本为例，可以集成到 OpenClaw 的自定义插件或 MCP 工具中）：

1. **接收上游输出**  
   从 Agent 或生成函数拿到 `{ markdown, images: [{url, alt_text}] }` 结构。

2. **生成 slug 并创建目录**  
   根据文章标题或时间戳生成 `slug`，创建 `posts/{slug}/images` 目录。

3. **处理 Markdown 中的图片引用**  
   - 如果原始 Markdown 里已经通过 `![alt](url)` 引用了远程图片，解析出所有图片 URL。
   - 将这些 URL 与 `images` 列表合并去重。

4. **下载图片到本地**  
   每个图片使用 `requests` 下载，写入 `images/` 目录。文件名建议用 **内容哈希**（如 SHA256 的前 8 位）+ 原始扩展名，避免同名覆盖。同时记录映射关系：`original_url -> local_path`。

5. **更新 Markdown 引用**  
   将正文中的远程图片 URL 替换为 **相对路径**  `./images/filename.png`，这样文章文件与图片可以作为一个整体打包、迁移、重发布，不依赖任何外部链接。

6. **更新 assets.json**  
   读取现有 `assets.json`（如有），追加或更新当前帖子的条目。注意需要处理并发写入的问题（见踩坑点）。

7. **版本控制（可选）**  
   将 `posts/{slug}` 目录加入 Git，与项目代码一同管理，形成内容版本历史。

## 踩坑点

- **图片下载稳定性**  
  某些图床可能会限流或返回 403。需要为下载函数加上重试（例如 3 次，指数退避）以及超时判断。对于最终下载失败的图片，可以在 `assets.json` 中标记 `status: "failed"`，并保留原始 URL，便于后续手动补救。

- **文件名冲突**  
  不能直接使用原始文件名，因为多个文章可能引用同名的 `image.png`。使用内容哈希可以有效避免冲突，同时还能检测出完全相同的图片（节省存储空间）。

- **assets.json 的并发写入**  
  如果流水线中可能有多篇文章同时归档，需要对 `assets.json` 的读写加锁（使用 `fcntl` 或 `portalocker`），或者改用每个帖子独立的 `metadata.json`，再通过脚本定期聚合为 `assets.json`。后者在运维上更简单、冲突更少。

- **Markdown 路径替换的边界情况**  
  图片语法可能带有标题、参考式链接，或者图片 URL 也出现在代码块中。解析时需要限制在 `![](...)` 语法内，避免误替换。建议使用 Markdown 解析器（如 `mistune`、`markdown-it-py`）进行 AST 级别的修改，而不是正则全局替换。

- **大文件与存储成本**  
  图片总体积可能增长很快，可以设定尺寸阈值（如超过 5 MB 的图片做缩放后再存储），并定期清理时效性已过的旧帖归档（归档到冷存储或打包压缩）。

## 可复用建议

- **标准化函数封装**：将归档逻辑抽象成一个独立脚本或 OpenClaw MCP 工具，接受标准输入（Markdown + 图片列表），输出本地目录和 `assets.json`。这样无论底层 Agent 怎么换，归档步骤都不变。
- **与发布解耦**：归档应当作为发布的后置步骤，而不是发布前的必要条件，避免因为本地写入缓慢影响发布速度。
- **使用 frontmatter 携带元数据**：可以在 Markdown 文件头部加入 YAML frontmatter，记录标题、标签、创建时间，这样单篇 Markdown 就能独立成文件，不依赖外部 JSON。
- **结合 OpenClaw 插件体系**：如果有现成的文件系统插件或 MCP 资源管理工具，可以将其包装成资源写入操作，让 Agent 自己“记住”已生成的资产，增强自主性。

## 总结

自动发帖流水线加上本地归档看似是一次性工作，但实际上为内容资产的长期管理打下了基础。`assets.json` 索引 + 相对路径 Markdown 这个组合，实现了人与工具都可读的资产组织方式。它不增加运行时的外部依赖，也不改变发布流程，只是安静地留下了每篇文章的“底片”。在后续做内容重制、质量复盘或训练数据集构建时，你会发现这些沉淀下来的原始文档和图片才是最有价值的部分。
