## 为什么你需要关心 Agent 的文件访问边界

在 OpenClaw、MCP 插件以及各类自动化脚本里，文件读写几乎是标配能力——Agent 需要写日志、读配置、产出报告、甚至操作本地知识库。但问题也很突出：一旦把文件系统的钥匙完全交给一个由 LLM 驱动的流程，错误的推断或未预期的行为就可能去改写系统文件、删除用户数据、或者将敏感文件内容通过对话通道泄露出去。

传统的做法是“靠人审”，但在全自动链路里并不现实。更工程化的思路是：**给所有文件操作加一层目录白名单**——只允许脚本在指定的安全目录下读写，任何试图跨出白名单的访问直接拦截并报错。

这篇文章会给你一个可直接嵌入 OpenClaw/MCP 工程中的目录白名单方案，包含实现步骤、几个容易踩穿的坑，以及一份可复用的检查组件。

---

## 问题抽丝：文件操作为什么容易失控

典型的失控场景包括：

- 用户把整个文件系统挂进了工具的 `read_file`/`write_file` 能力，Agent 可以遍历任何路径。
- 相对路径 `../../` 绕过预期目录，或在符号链接的掩护下跳出限制。
- 配置疏忽：工具声明了自己的工作空间，但实际上没有做任何校验。
- 第三方依赖（例如某个 Shell 调用）完全不受应用层白名单约束。

本质上，我们需要在任何文件 I/O 发生前，回答一个问题：**目标路径是否在允许的目录集合内？** 而这远比一眼看上去要复杂。

---

## 做法：从零落地一个路径白名单校验器

下面所有示例基于 Python，设计原则同样适用于 Node.js 或其他语言。我会把核心逻辑抽成一个独立的检查器，然后分别用在普通 Python 脚本和 MCP 工具中。

### 1. 定义白名单目录，并解析为绝对路径

```python
from pathlib import Path
from typing import List, Union

ALLOWED_DIRS: List[Path] = [
    Path("/home/user/agent_workspace").resolve(),
    Path("/mnt/shared_data").resolve()
]
```

要点是 `resolve()`，它会把目录解析为不含符号链接的绝对路径。**记住：每次比较时都要对目标路径也做同样解析**，否则闭环会被类似 `/var/data/../etc/passwd` 或符号链接打破。

### 2. 核心校验函数

```python
def is_allowed_path(target: Union[str, Path], allowed: List[Path] = ALLOWED_DIRS) -> bool:
    try:
        target_real = Path(target).expanduser().resolve()
    except (OSError, RuntimeError):
        # 如果路径不存在或不可解析，直接拒绝
        return False

    for base in allowed:
        # 检查 target_real 是否是 base 的子路径（含自身）
        try:
            target_real.relative_to(base)
            return True
        except ValueError:
            continue
    return False
```

这里使用了 `relative_to` 来做路径包含判断：如果目标路径不属于任一基础目录，会抛出 `ValueError`，直接返回 False。

### 3. 将它嵌入文件操作：装饰器版

```python
import functools

def safe_file_op(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        # 简单策略：提取所有 str/Path 参数中可能是路径的值
        for arg in args:
            if isinstance(arg, (str, Path)) and '/' in str(arg) or '\\' in str(arg):
                if not is_allowed_path(arg):
                    raise PermissionError(f"Access outside allowed dirs: {arg}")
        return func(*args, **kwargs)
    return wrapper
```

装饰器适合统一对已有函数加保护，比如往 `open()` 或 `shutil.copy` 的调用上套一层。缺点是有时难以区分路径和普通字符串，生产环境建议明确定义哪些参数是路径。

### 4. 应用到 MCP 工具函数

在 MCP 服务器中，文件访问工具往往是显式的，比如 `read_local_file` 和 `write_local_file`。我们可以直接在工具入口处校验：

```python
@server.tool()
async def read_local_file(file_path: str) -> str:
    if not is_allowed_path(file_path):
        raise ValueError(f"File path {file_path} is not within allowed directories.")
    # 正常读取逻辑...
```

这样做的好处是失败时返回明确的错误消息给模型，LLM 还可以基于此自行调整行为，而不是静默地操作到不该碰的文件。

## 踩坑点：四个最容易击穿白名单的地方

在实际工程中，下面几个点是真实翻车高发区：

### 1. 符号链接绕过

`/allowed_dir/link -> /etc` 这样的符号链接，如果不用 `resolve()` 解析真实路径，白名单等于没有。因此，**始终对传入路径调用 `Path.resolve()`**，放弃“业务目录内就一定安全”的幻觉。

### 2. 相对路径的上下文陷阱

Agent 可能在执行过程中改变了当前工作目录（`os.chdir` 或被依赖库影响）。`Path("config.json").resolve()` 会根据进程的 cwd 变化。建议一律在接收到路径参数时就尽早 `resolve()`，或者统一转化为基于某个固定 base 的绝对路径。

### 3. 路径分隔符不归一化

Windows 下同时存在 `\` 和 `/`，`relative_to` 会视为不同。统一使用 `pathlib` 的 `PurePath` 操作，并确保白名单目录和目标路径都经过 `resolve()`，可以规避大部分问题。

### 4. 目录遍历攻击的边缘形态

类似 `/allowed_dir/../secret` 或大小写差异（Windows）也会钻空子。好消息是 `resolve()` 会自动处理 `..` 和 `.`，而大小写问题在 Windows 上可通过 `os.path.normcase` 辅助判断，但跨平台建议最好限制允许目录为全小写，并将目标路径也归一化。

## 可复用建议：收敛成工程组件

把这个检查逻辑收敛成一个独立的 `file_guard` 模块，对外暴露：

- `set_allowed_dirs(*paths)`
- `is_allowed_path(path) -> bool`
- `guarded_open(path, mode)` （带校验的 open 替代）
- 上下文管理器：`guarded_dir_context(paths)` （临时调整白名单）

可以在 OpenClaw 的插件初始化阶段配置好白名单，并把 `guarded_open` 注入到 Agent 的工具空间里。如果你的脚本还会调用 Shell 命令，**要额外注意**：白名单无法限制系统调用，最好将 Shell 类工具彻底关掉，或者严格限制传入的命令参数。

---

## 总结

给自动化脚本加目录白名单，并不是为了“防黑客”级别的安全，而是**在工程层面把 Agent 的行为锁定在一个可控的伤害半径内**。你不需要实现一个内核级的沙箱，只需要在应用层做一次干净、一致的路径校验，就能避免绝大多数因误操作导致的文件损坏和泄露。

构建这种护栏的要点就四个字：**尽早拒绝**。在任何实际 I/O 之前完成解析和校验，失败时给出明确错误，保留操作日志——让失控的自动化慢下来、停下来，而不是任由它带着 root 的权限一路狂奔。

把目录锁加上去，你才会放心地把 Agent 交给下一个后半夜的全自动流水线。
