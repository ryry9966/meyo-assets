## 谁在忍受坏 JSON 的折磨？

在 OpenClaw、Agent 管线以及各类 MCP 插件里，我们经常要求大模型生成结构化长文——一份完整报告、一串步骤分解、一个多组块的分析结果。最“自然”的工程选择是让模型输出 JSON，规定好 keys，紧接着交给 `json.loads()`。可偏偏现实是，模型输出的 JSON 总有瑕疵：

- 最后几个字段丢掉了闭合的 `}`
- 字符串里嵌入了未转义的双引号
- 多层级嵌套时中途变得不一致
- 长文本内插入了多余的换行或注释

这些不是偶然，而是 LLM 自回归解码的本质使然。JSON 是脆性语法，一处断则全盘皆错。尤其在长文输出场景，长度每增加一个 token，概率误差累积，在 2000+ token 之后崩坏概率急剧攀升。一旦解析失败，整个自动化流中断，需要重试、回退甚至人工介入。

我曾经在一个自动生成技术文档的插件里，为了让模型输出分析 + 代码 + 对比的 JSON 结构，反复调整 prompt、增加 JSON 校验示例、甚至写了三步修复函数，坏 JSON 率依然徘徊在 10% 左右。直到我把思路转向“标签协议”，成功率才从 90% 提到接近 99.8%。

## 标签协议的思路

与其指望 LLM 恰好生成可解析的 JSON，不如设计一套只需“部分匹配”即可恢复的标记语言。核心是**用明确的、独特的文本边界将内容分块**，后处理用正则按块提取，单个块格式出错不影响其他。这比 JSON 容错性好得多，因为它不需要全局闭合，不需要严格句法。

最简单有效的方式是 `<SECTION>内容</SECTION>` 这类标签，但需要预防内容里出现相同标签。更好的是使用带 ID 的唯一分隔符，例如：

```
[BLOCK_INTRO]
...内容...
[BLOCK_INTRO_END]

[BLOCK_METHOD]
...内容...
[BLOCK_METHOD_END]
```

或者 `<block id="summary">...</block>`，但要正则匹配。我自己实践中收敛到形如 `<<<BLOCK_START:key>>>` 与 `<<<BLOCK_END:key>>>` 的模式，因为极低概率与普通文本冲突。

## 做法：三步切换标签输出

### 1. 定义标签协议与 Prompt 模板

根据任务定义一套标签。比如生成一个多部分技术分析，有背景、原因、操作、注意事项四部分。协议设计为：

```
<<<BLOCK_START:background>>>
（内容）
<<<BLOCK_END:background>>>

<<<BLOCK_START:reasons>>>
（内容）
<<<BLOCK_END:reasons>>>

...
```

然后在系统/用户 prompt 中明确要求：“请严格按照以下格式输出，不要输出任何额外的 JSON 或 Markdown 代码块。每个区块使用指定的起始和结束标记，区块内可以包含任意文本。”

示范示例有助于模型遵守。比如给出一个结构正确的例子，并强调“务必保持标记与示例一致，注意闭合”。对于长输出，可加一句：“即使内容截断，也请确保所有已开启的标记闭合。”

### 2. 后处理：按标记切分

用正则非贪婪匹配提取各块内容：

```python
import re

def extract_blocks(text: str, key: str) -> str | None:
    start_tag = f"<<<BLOCK_START:{key}>>>"
    end_tag = f"<<<BLOCK_END:{key}>>>"
    pattern = re.escape(start_tag) + r"(.*?)" + re.escape(end_tag)
    m = re.search(pattern, text, re.DOTALL)
    return m.group(1).strip() if m else None
```

若某个块缺失，返回 `None`，上层可以触发重试或填充默认值，不必让整个流水线崩溃。对于允许复用的工具，可以降级处理；或者检查必填块，缺失的只针对该块做补全请求，极大节省 token。

### 3. 容错与恢复

实践中会遇到三种典型异常：

- **模型忘记闭合标签**：可以在 prompt 中提醒，另外在解析时检测块起始后若无结束，则取到文本末尾或下一个 BLOCK_START 为止。比如通过 `.*?` 匹配不到时，用 `.+` 到文件尾作为 fallback。
- **标签嵌套或内容包含类似标签**：由于使用唯一字符串 `<<<BLOCK_START:`，几乎不可能出现，但万一内容有类似的，可以改用带随机盐的动态分隔符，每次生成前生成一个唯一标识，如 `[[BX7k3_`，嵌入到 prompt 里。这样污染可能性降为零。
- **编码与换行问题**：模型可能在标签周围插入多余空格或换行。正则匹配时使用 `re.DOTALL`，并在提取后 `strip()` 即可。

## 踩过的坑：标签冲突与性能

在初期，我企图用简单的 `[BLOCK_开头的]` 和 `[/BLOCK]` 闭合，结果因为内容本身包含方括号描述，造成了误匹配。后来改成长唯一前缀解决了。

另一个错误是试图用同一个 `re.compile` 来匹配所有块，然后按出现顺序分配。这样代码看似优雅，但碰到输出顺序改变或模型漏掉某一个时恢复异常复杂。还是老老实实逐块 `re.search` 清晰又可维护。

此外，标签协议增加了输出 token 数量（约 5-10%），但在稳定性提升面前完全可以接受。

## 可复用建议

- **最小化标签语法**：能区分边界即可，不必模拟 XML。
- **加入唯一随机成分**：如果输出内容极度不可控，可在每次调用时生成一段随机盐作为闭合标记，如 `[SALT_a3dE_END]`，提示词和解析同时使用。
- **提供清晰示例**：Show, don't tell. 在 prompt 里给一个完整的标注样例，比自然语言说明更有效。
- **降级策略**：用 missing block fallback 或者在块缺失时做最小限度的单独补全，避免因一个小块错失整个长回复。
- **与 JSON 共存**：如果团队仍需要 JSON 用于后续节点，也可以让每个块内部是合法 JSON 字符串，外层用标签包覆。比如：

```
<<<BLOCK_START:data>>>
{"name": "...", "value": "..."}
<<<BLOCK_END:data>>>
```

这样整体仍是可恢复的结构，内部交给严格 JSON 解析。

## 总结

在 Agent 自动化流程中，追求完美的端到端 JSON 输出往往是用“确定性”去硬套“概率性”系统。退一步，采用基于标签分隔的半结构化输出，把解析的鲁棒性掌握在自己手里，让 LLM 做它擅长的——生成自然内容，而不是生成语法绝对正确的数据结构。实践表明，切换之后长文输出的稳定性和可维护性都跃升一个台阶，重试次数显著下降，管线掉线率趋近于零。

如果你也受够了 `json.decoder.JSONDecodeError` 带来的中断，不妨试试给 LLM 换一套更宽容的“输出协议”。
