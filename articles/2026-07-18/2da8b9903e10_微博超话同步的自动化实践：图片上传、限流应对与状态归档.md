# 微博超话同步的自动化实践：图片上传、限流应对与状态归档

## 背景

在内容分发和多平台同步场景中，将产出内容自动发布到微博超话是一个常见需求。对于已经搭建 OpenClaw 自动化管线的用户来说，这通常意味着要在已有的 Agent、插件或 MCP 工作流里，串联起“内容生产 → 图片处理 → 微博发布 → 状态记录”的全流程，替代人工每天手动搬运的枯燥操作。

这篇文章记录一次基于 OpenClaw 生态的微博超话同步实践，重点解决三个核心问题：**图片上传的稳定处理**、**超话发帖的限流策略**，以及**发布状态的持久化归档**。整体方案以 Python + 微博开放接口实现，封装为可被自动化流程调度的能力模块，所有踩过的坑都在这里如实交代。

## 遇到的问题

1. **图片上传门槛**  
   微博要求先通过 `/statuses/upload` 上传图片，拿到 `pid` 后才能附带在发博请求里。官方限制单张不超过 10MB，一次最多 9 张，而真实运营中还会碰到格式兼容、接口偶发超时、图片返回为 0 等问题。

2. **限流与风控**  
   超话发帖接口 `/statuses/update` 本身没有严格的限速文档，但实际测试中，一个普通授权用户如果短时间内连续发帖超过 5 条，极易触发验证码弹窗、账号被临时限制，甚至被微博系统标记为垃圾营销。尤其在带上图片的情况下，发帖间隔如果过于机械，很容易被反作弊策略命中。

3. **状态追溯与补偿**  
   自动化流程不能指望每次都 100% 成功，必须有清晰的状态——哪些帖子已成功发布，哪些由于限流或报错需要重试，哪些因为内容审核被“形式成功实际屏蔽”需要人工核查。否则几轮下来，发布记录就成了一笔糊涂账。

## 实践步骤

### 1. 环境与鉴权准备

- 在微博开放平台创建网站接入应用，获取 `App Key` 和 `App Secret`。
- 通过 OAuth2 获取 `access_token`，这里强调必须使用 **获得微博写权限**（`scope` 包含 `statuses_update` 等）的授权，且 token 长期有效需要通过用户授权页获取，而非仅用开发者测试 token。
- 将 token 安全存储（如环境变量或加密配置），并在自动化脚本中添加 token 过期检测与自动重刷逻辑。

### 2. 获取超话 ID

超话在微博里的标识是 `topic_id`，它与超话名之间的映射可以用 `/search/topics` 接口：

```python
import requests

def get_topic_id(name):
    r = requests.get('https://api.weibo.com/2/search/topics.json',
                     params={'q': name, 'access_token': TOKEN})
    topics = r.json().get('topics', [])
    return topics[0]['id'] if topics else None
```

**注意**：超话名如果有特殊符号、表情等，需要用 UTF-8 编码后做 URL Encode，否则搜不到。

### 3. 图片上传

微博的图片上传是典型的 multipart/form-data 请求。核心步骤：

```python
def upload_image(image_path):
    url = 'https://api.weibo.com/2/statuses/upload.json'
    with open(image_path, 'rb') as f:
        files = {'pic': f}
        data = {'access_token': TOKEN}
        resp = requests.post(url, data=data, files=files, timeout=30)
    return resp.json().get('pic_id', '')
```

**工程化要点**：
- 预设重试机制：网络超时或返回 `error` 时，最多重试 3 次，间隔指数退避；
- 图片尺寸与大小预检：对于超过 10MB 的图片进行自动压缩（Pillow 调整品质）；
- 多图场景下按顺序上传，记录每个 `pid`，失败时整组放弃或仅丢弃问题图片。

### 4. 发布到超话并施加限流策略

带图和 `topic_id` 发布：

```python
def post_to_chaohua(content, pic_ids, topic_id):
    url = 'https://api.weibo.com/2/statuses/update.json'
    payload = {
        'access_token': TOKEN,
        'status': content,
        'pic_id': ','.join(pic_ids),
        'topic_id': topic_id
    }
    resp = requests.post(url, data=payload)
    return resp.json()
```

限流控制没有固定参数，实践中采用 **“最小间隔 + 随机抖动 + 硬上限”** 的组合：
- 两次发帖最短间隔设为 **6 分钟**；
- 在 6 分钟基础上增加 1~3 分钟的随机浮动，避免形成规律时间序列；
- 每个自然小时内累计发帖不超过 8 条，达到后强制休眠至下一小时窗口。

流程里通过一个状态文件（`schedule.json`）记录最近一次发帖时间和当日已发次数，每次发帖前读取并判断。这套逻辑可以直接嵌入 OpenClaw 的定时任务或事件驱动的异步插件中。

### 5. 状态归档

每次发帖后，无论成功失败，都记录一条结构化日志，存储为 JSON Lines 文件或 SQLite 表。关键字段：

- `task_id`（内部唯一标识）
- `content_hash`（内容摘要）
- `pic_ids`
- `weibo_id`（成功时微博返回的 ID）
- `status`（success / failed / pending_retry / shadow_ban）
- `error_code` 与 `error_msg`
- `timestamp`

还需定期对 `status=success` 的微博做一次 `/statuses/show` 查询，检查是否被系统删除或不可见，更新为 `shadow_ban` 状态。这样可以让后续自动化流程生成一份可交付的归档报告，也为人工复查提供入口。

## 踩过的坑

- **Token 陷阱**  
  测试时用的 `access_token` 往往来自开发者账号的“授权测试”，有效期只 1 天，且无 refresh 机制。生产环境必须引导真实用户授权，获得较长时间有效的 token，并实现刷新逻辑。

- **`topic_id` 直觉错误**  
  刚开始想当然以为超话 ID 就是超话主页 URL 里那串数字，实际接口要求的是 `search/topics` 返回的 `id` 字段，两个值可能完全不一样。

- **“成功”背后的假象**  
  发布接口返回 `created_at` 且无 error，并不意味着帖子真的存活。审核系统可能在几秒到几分钟内遮罩内容（仅自己可见但不在超话列表出现）。务必异步进行二次校验，并显式标记状态。

- **重试引发的风控升级**  
  曾经在发帖失败后立即重试，连续 3 次 403 错误后，账号直接被限制发博 24 小时。后来改为失败后进入 `pending_retry` 状态，等待 30 分钟后才允许重试，且每天总重试次数有限。

## 可复用建议

把上述流程从一次性脚本提炼成可配置模块，在 OpenClaw 生态中更容易复用：

- **抽象为服务**：图片上传、发布、状态归档各自独立函数，方便在 Agent 里按需调用。
- **持久化任务队列**：用小型的 SQLite 或 Redis 任务表管理待发布内容，配合调度器消费，状态机清晰。
- **集成进自动化插件**：发布模块封装为 OpenClaw 的定时插件或 MCP 工具，允许外部触发和目标动态配置。
- **可观测性**：接入结构化日志和简单的健康检查，让问题不再“发了没发都不知道”。

## 总结

自动同步微博超话不是“调一个 API 就完事”的轻量操作，图片上传的健壮性、限流策略的经验性调整，以及状态归档的完整性，决定了整个流程是可靠的还是灾难性的。从一开始就把重试、间隔控制和状态审计纳入设计，远比事后收拾烂摊子省心。在 OpenClaw 体系下，这样一套模块化的同步能力可以快速嵌入更多自动化工作流，把机械劳动交给人造物，让人专注内容本身。
