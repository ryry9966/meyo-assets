## 背景：当 Agent 需要碰本地文件

在 OpenClaw、MCP 插件、或个人自动化脚本里，Agent 经常要以“本地用户”的身份做文件操作：写入临时文件、读取配置、生成报告、清理日志……这类场景下，脚本权限通常等于当前进程用户。风险也在这里：一句误写的 `os.remove("/")` 或一个路径拼接错误，就可能酿成严重事故。

很多 Agent 框架对文件操作并不设限——它们假定你有沙箱环境或者干脆把责任扔给开发者。可真实工程里，很多自动化就运行在开发机上。我们需要一个“轻量护栏”：不引入容器，不影响调试，但能有效阻止跳出自名单路径的文件访问。

## 问题：不是防恶意代码，而是防“脚本写劈叉”

护栏的目标不是防黑客——那是沙箱的活儿。我们要防的是工程失误：路径拼错、循环删除跑飞、第三方库内部使用 `os.remove` 时传入了不该传的路径。这类问题在自动化脚本里非常高频，且往往在晚上无人值守时爆发。

因此护栏的核心设计应该是：
- 定义一个**目录白名单**（例如 `./workspace`, `/tmp/agent-sandbox`）
- 在所有文件操作前，将目标路径**归一化**并与白名单做前缀匹配
- 对 `open()`, `os.remove()`, `shutil.rmtree()` 等危险调用进行拦截

## 做法：给文件操作函数打“安全补丁”

一个经得起工程使用的方案是：不修改业务代码，而是在 Agent 启动脚本里“猴子补丁”掉危险的系统调用。下面是一个可落地的实现，用 Python 示例。

### 步骤 1：定义白名单与路径验证

```python
import os
import functools

WHITELIST_DIRS = [
    os.path.abspath("./safe_workspace"),
    os.path.abspath("/tmp/agent_sandbox"),
]

def _is_path_allowed(path: str) -> bool:
    # 解析真实路径，处理符号链接与相对路径
    real_path = os.path.realpath(path)
    for allowed in WHITELIST_DIRS:
        if real_path.startswith(allowed + os.sep) or real_path == allowed:
            return True
    return False
```

注意这里用了 `os.path.realpath()`。它能解开符号链接、处理 `..` 和波浪号展开（需自行处理 `~`），是避免绕过的关键。

### 步骤 2：包装危险函数

我们只包装最常见的几个“破坏性”操作，对 `open` 可区分读写模式：

```python
import builtins

original_open = builtins.open

def safe_open(file, mode='r', *args, **kwargs):
    # 对只读模式放行，或者也可以统一检查；这里选择仅拦截写/追加/创建
    if any(m in mode for m in ('w', 'a', 'x', '+')):
        if not _is_path_allowed(file):
            raise PermissionError(f"Write access denied: {file}")
    return original_open(file, mode, *args, **kwargs)

builtins.open = safe_open
```

对于 `os.remove`、`shutil.rmtree`、`os.rename` 等，可直接包装：

```python
import os, shutil

_original_remove = os.remove
def safe_remove(path, *args, **kwargs):
    if not _is_path_allowed(path):
        raise PermissionError(f"Remove denied: {path}")
    return _original_remove(path, *args, **kwargs)
os.remove = safe_remove
# 类似包装 shutil.rmtree, os.rename, os.unlink ...
```

### 步骤 3：集成到 Agent 启动流程

在 OpenClaw 或 MCP 插件中，可以把这个补丁脚本作为“预执行钩子”注入。例如，如果是基于 Python 的 Agent，在入口文件最上方导入安全模块即可：

```python
from agent_safety import apply_patches
apply_patches()
```

如果 Agent 是调用外部 Python 脚本，可以在子进程启动参数中加入 `-c "import agent_safety; agent_safety.apply_patches()"` 后再执行目标脚本；或用 `PYTHONSTARTUP` 环境变量（注意这会作用于所有交互式解释器，需要谨慎）。

## 踩坑点：这些地方最容易穿帮

1. **路径归一化不彻底**  
   - `os.path.realpath` 需要路径实际存在才能解析符号链接。要防范尚未创建的文件路径绕过，可先对父目录进行 `realpath`，再拼接文件名后再次 `realpath`（需容错）。
   - 用户可能用 `~` 或环境变量（如 `$HOME`），需要提前做 `os.path.expanduser` 和 `os.path.expandvars`。

2. **白名单路径本身被删除或移动**  
   如果白名单目录在运行时被重命名或删除，`realpath` 可能返回不同结果。建议在启动时锁定白名单的 `realpath` 并缓存，后续不再重新解析。

3. **跨平台的盘符和分隔符**  
   在 Windows 上，`c:\dir` 与 `C:\dir` 是否等同？需要使用 `os.path.normcase` 做大小写规范化，并处理盘符。前缀匹配时要连带处理路径分隔符，避免 `/tmp/agent` 白名单匹配到 `/tmp/agent_attack`（通过加分隔符比对）。

4. **第三方库的“直调”系统 API**  
   如果你的补丁只覆盖 `os.remove`，但某个 C 扩展库用 `os.unlink` 或直接 `syscall`，护栏就失效了。这需要审慎选择拦截面，或限制 Agent 可用的第三方库。对于绝大多数纯 Python 自动化，上述补丁已足够。

5. **日志和错误处理**  
   拦截时抛 `PermissionError` 可能会打断业务流程，设计上应配合统一的错误捕获和告警。如果是后台任务，触发违规则应立刻中止，并推送通知给开发者。

## 可复用建议

- **做成独立 pip 包**：将安全补丁抽取成 `agent-sandbox` 包，提供 `install_patches(whitelist)` 函数，可配置日志等级和违规回调。
- **白名单来源可配置**：从环境变量 `AGENT_SAFE_DIRS` 或者配置文件加载，避免硬编码。
- **保留逃生通道**：在开发/调试模式下（通过环境变量控制），可以不启用补丁，方便诊断。
- **与 Agent 上下文结合**：如果 Agent 有“任务工作目录”概念，可自动将任务目录加入白名单，并在任务结束时清理。

## 总结

这个护栏的实现非常薄——不到 100 行代码，但它能在根子上阻止绝大多数因脚本 bug 导致的文件破坏。它不依赖 Linux 命名空间或 Docker，也不会拖慢执行效率，非常适合在本地开发环境、CI 流水线和轻量级自动化 Agent 中使用。

核心工程心法：**文件操作的防护不是在异常里加 try，而是把危险调用本身关进笼子。** 给 Agent 一把真正的“只读偏锋”的刀，比在它身后放灭火器更靠谱。
