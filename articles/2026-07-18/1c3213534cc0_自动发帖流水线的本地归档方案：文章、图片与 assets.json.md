## 背景

在基于 Agent / MCP / 插件搭建的自动发帖流水线中，单次运行往往只关注“生成并发布”这一条路径。最初的实现通常是：LLM 写好正文、调用生图工具出图、再通过平台 API 发布，整条链路跑通就算完成任务。

问题会随着批量运行慢慢暴露。生成的内容会丢失上下文，想回溯某篇文章的原始 Markdown 或当时使用的图，只能去平台后台翻找，而且平台压缩过的图片往往不是原图。如果后续要接入 RAG、做内容分析、或者换平台重新发布，缺少本地的结构化归档会变成明显的效率瓶颈。

这篇文章面向已经拥有自动化发帖能力的读者，讨论如何以工程化的方式在流水线末端加上一步 **本地归档**，以及围绕 `assets.json` 保存文章与图片的关联关系。

## 问题分析

一个典型的自动发帖 Agent 产出的结果通常包含：

- 一份 Markdown 正文（可能已经嵌入了图片引用）
- 若干张配图（可能是 URL，也可能是本地临时文件）
- 元数据：标题、标签、发布时间、目标平台等

直接把这些散落的信息交给发布函数，发布完后丢弃，后续会遇到几个典型痛点：

1. **图片链接失效**：临时图床或即生即用的 URL 有有效期，几天后 Markdown 里的图片就裂了。
2. **正文被平台二次处理**：平台可能会自动转义、删除某些格式，回捞不到原始 Markdown。
3. **多平台发布时关联混乱**：同一个帖子发到 Twitter、Blog 和 Discord，本地没有任何索引，很难知道它们指向同一内容。
4. **后续检索困难**：没有结构化的元数据文件，做全文检索或喂给向量数据库时需要额外清洗。

因此，我们需要在发布前或发布后立即将“文章 + 图片 + 元数据”作为一个整体归档到本地文件系统，并生成一份 `assets.json` 作为该帖子的入口描述文件。

## 做法与步骤

### 1. 确定归档目录结构

建议采用 **`posts/{slug}/`** 的扁平化结构，slug 可以由日期和标题哈希组成，保证唯一性：

```
posts/
└── 20250321-how-to-build-crawler/
    ├── article.md
    ├── assets.json
    └── images/
        ├── architecture.png
        └── flow-diagram.png
```

这样做的好处是，每篇帖子是一个独立目录，可以直接用 Obsidian 打开 `posts/` 作为 Vault，也可以用 Git 进行版本管理。

### 2. 保存 Markdown 原文

在调用发布 API 之前，拿到未处理的 Markdown 正文。如果正文中的图片已经是 URL，先不要替换，保持原始引用，稍后在下载图片时统一处理。将原始正文直接写入 `article.md`。这是最纯净的版本，不会受任何平台转义影响。

### 3. 下载并本地化图片

遍历 Markdown 中的图片语法 `![alt](url)`，提取所有图片 URL。对每个 URL 执行下载：

- 根据 `Content-Disposition` 头尝试获取原始文件名，若无则取 URL 路径的 `basename`，再不行则用 URL 的 SHA256 前 8 位加合适的扩展名（通过响应的 `Content-Type` 判断）。
- 将图片保存到 `images/` 目录下，并记录“原始 URL -> 本地相对路径”的映射关系。
- 下载全部完成后，再对 `article.md` 中的图片 URL 做批量替换，改为 `./images/xxx.png`。

这样做可以保证 `article.md` 在本地查看时图片能正确渲染，同时原始 URL 依然被记录在 `assets.json` 中，方便溯源。

**并发控制**：一般 3-5 张图可以并发下载，但需要注意不要打爆本地文件句柄或触发远端限流，建议使用带并发限制的队列（例如 Node.js 中用 `p-limit`，Python 中用 `asyncio.Semaphore`）。

### 4. 生成 assets.json

`assets.json` 是这组归档的核心索引文件，建议包含以下字段：

```json
{
  "slug": "20250321-how-to-build-crawler",
  "title": "How to build a polite crawler in 2025",
  "created_at": "2025-03-21T10:00:00Z",
  "tags": ["crawler", "python"],
  "platforms": [
    {
      "name": "twitter",
      "post_id": "1903123456789",
      "url": "https://x.com/.../status/...",
      "published_at": "2025-03-21T10:05:00Z"
    }
  ],
  "images": [
    {
      "original_url": "https://cdn.example.com/gen-img/abc.png",
      "local_path": "images/architecture.png"
    }
  ],
  "word_count": 1200,
  "source_prompt_hash": "sha256:xxx"
}
```

`platforms` 字段允许同一份内容发布到多个平台，每次发布成功后追加一条记录。如果发布是异步的，也可以在后续更新该字段。

`source_prompt_hash` 是可选的，如果你希望回溯是哪个 Prompt 生成的这篇内容，可以记录 Prompt 的哈希值。

### 5. 集成到流水线

无论你的流水线是 TypeScript 写的 Agent 工具，还是 Python 脚本配 MCP Server，都可以将上述逻辑封装为一个函数或一个 MCP tool：

```
tool: archive_post({
  slug: string,
  markdown: string,
  image_urls: string[],
  metadata: {...}
})
```

调用时机建议放在发布成功之后，尽量避免因为归档写盘失败而阻塞发布。可以捕获写盘异常打日志，并在内存中保留失败队列，下次运行补齐。

## 踩坑点

- **图片链接格式多变**：有些生图工具返回的 URL 带 query 参数和临时签名，直接取 `basename` 会得到无意义字符串。优先处理 `Content-Disposition`，其次解析 URL 路径中的有效文件名段，再用 fallback 策略。
- **Markdown 图片语法误匹配**：当文章正文中包含示例代码或转义字符时，正则可能匹配到非图片内容。建议使用 Markdown AST 解析器（如 `remark`）精确提取，避免手写正则的边界问题。
- **路径分隔符问题**：在 Windows 环境使用 Node.js 或 Python 时，写入文件系统的路径需要统一转换为当前系统的正确格式。`images/xxx.png` 在 Windows 下需要处理成 `images\xxx.png`，不过 Markdown 中的引用统一使用正斜杠即可，因为多数本地 Markdown 渲染器都支持。
- **重复下载**：如果同一张图片被多篇文章引用，是否要复用？简单方案是不复用，每篇文章独立存放，避免一个目录文件被删除影响其他帖子。但如果存储敏感，也可以做硬链接或内容寻址存储，并在 `assets.json` 里记录内容哈希。

## 可复用建议

- 将归档逻辑打包成一个 **CLI 工具**或 **MCP Tool**，输入为 Markdown 字符串和图片列表，输出为写入本地目录的完成信号。后续各种 Agent 项目可以直接调用，减少重复开发。
- 用 **Git** 管理 `posts/` 目录，每次归档后自动提交，形成内容版本历史。搭配 Obsidian 或 Logseq 可以直接将其作为知识库使用。
- `assets.json` 的结构可以被下游 RAG 管道直接消费，例如用 `jq` 或脚本批量导入向量数据库时，提取正文、标签和图片描述。
- 如果已有内容排期系统，归档步骤可以顺便更新排期状态，实现闭环。

## 总结

给自动发帖流水线加上本地归档，看起来是“多一事不如少一事”的工作，但在内容量起来之后，这项工作会从可选项变为必需项。通过一个约定好的目录结构、一篇干净的 Markdown、一组本地化的图片，再加上一份结构清晰的 `assets.json`，我们能够把 Agent 生成的每一条内容都沉淀为可检索、可复用、可分析的本地资产。整个方案的实现成本很低，但能显著提升长期维护的工程体验。
