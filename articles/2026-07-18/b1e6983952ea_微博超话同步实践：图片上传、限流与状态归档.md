## 背景

在维护垂直领域微博超话的过程中，我们经常需要将内部内容源（如每日精选、系统通知）自动同步为图文帖子。这类工作如果依靠人工重复操作，不仅效率低下，而且容易出错。借助 OpenClaw 的流程编排能力和 MCP（Model Context Protocol）工具生态，我们可以把“取内容→处理图片→发布→归档”整条链路自动化，让 Agent 代替人工执行重复劳动。

本次实践的目标是：从指定内容源抓取图文，调用微博 API 将图片上传并发布到超话，同时处理好频率限制和发布状态管理，做到无人值守。

## 问题拆解

看似只是一条发帖动作，但在微博的接口约束下，工程上要解决几个典型难题：

1. **图片上传前置**：微博发布图文帖时，不能直接附带图片二进制，必须先调用 `upload` 接口将图片上传至微博图床，拿到返回的 `pid`，再在发帖请求中引用这些 `pid`。任何一步失败都需要整体重试。
2. **严格的限流与风控**：微博开放接口对调用频率相当敏感，短时间内连续请求极易触发 `10022` 等错误码或 HTTP 429 响应。频次上限没有公开确切数字，需要自行摸索并设计退避策略。
3. **图片格式与尺寸限制**：图片必须为 `jpg`/`png` 格式，大小一般不超过 5 MB，长边建议控制在 2048 px 以内。来源内容提供的图片可能是 `webp`、超大尺寸或带有透明通道的 `png`，不做预处理会直接上传失败。
4. **状态归档与去重**：如果没有发布记录，一旦重试逻辑不当或任务被多次触发，就会造成重复发帖；而如果只在内存中记录状态，进程重启就丢失历史，同样危险。
5. **Token 过期**：微博 access token 并非永久有效，发布失败可能是 token 失效导致，需要支持无感刷新。

上述问题中，任何一个处理不当都会导致自动化流水线频繁中断。

## 做法与实践步骤

### 1. 基于 MCP 的微博工具层

我们使用一个自己维护的 `weibo-mcp-server`，通过 MCP 协议向 OpenClaw 暴露三个关键工具：

- `upload_image(image_path: str) -> dict`：处理图片上传，内部包含格式检查、自动转换与重试，返回 `pid` 等信息。
- `create_post(text: str, pids: list, topic: str) -> dict`：发布帖子，支持指定超话名称。
- `check_token() -> bool`：验证当前 access token 是否有效，并触发刷新。

工具内部封装了 OAuth2 流程和错误处理，让 OpenClaw 业务流不需要关心底层 HTTP 细节。

### 2. OpenClaw 同步流水线

在 OpenClaw 中定义一个同步 Skill，大致步骤为：

1. **获取待发布内容**：从内部 API 或队列中拉取一条图文记录，包含标题、正文、图片 URL 列表、内容指纹（hash）。
2. **查询归档状态**：连接本地 SQLite 数据库，根据内容指纹检查是否已发布。若存在则跳过，避免重复。
3. **媒体预处理**：将图片下载到临时目录，使用 Pillow 检查分辨率与格式。若图片为 `webp`，转换为 `jpg`（白底）；若长边超过 2048 px，等比缩放；若文件体积仍超过 5 MB，降低 JPEG 质量至 80%，确保符合微博约束。
4. **上传图片**：调用 `upload_image` 工具，该工具内部实现了重试逻辑：捕捉到频率限制错误（`10022` 或 429）后，采用指数退避（初始 5 秒，最大 120 秒）等待后重试，最多尝试 5 次。每次重试前随机抖动 1~3 秒，降低冲突。
5. **发布帖子**：调用 `create_post`，传入文本（@超话名称 + 正文）和上一步获取的 `pid` 列表。如果返回 token 失效错误，自动调用 `check_token` 刷新后再重试一次。
6. **归档状态**：帖子发布成功后，立即在 SQLite 中写入记录（内容指纹、微博帖 ID、时间戳、状态），并标注成功。若多次重试后仍失败，记录失败状态并告警。

### 3. 限流与容错细节

除工具层自带重试外，我们在 MCP server 实例上挂载了一个基于令牌桶的本地限流器，每秒最多允许 1 次请求，突发峰值不超过 3 次。这样可以避免短时间内密集调用触发微博封控。实际运行下来，配合退避重试，很少再被主动拦截。

另外，所有工具调用信息（请求参数、返回码、耗时）都会输出到结构化日志，便于后期分析调用模式和限流阈值。

## 踩坑记录

- **GIF 动图陷阱**：首次测试时，源内容包含一个 2.1 MB 的 GIF，虽然不到 5 MB，但微博对动图的帧数/分辨率有额外限制，直接上传失败且返回错误码模糊。最终策略是强制将动图转换为静态首帧 JPG，满足超话场景以静态图为主的需求。
- **状态归档竞争**：在并发度较高的测试中，出现过短暂重复发帖的情况。排查发现是因为查询归档与写入之间有微小的时间窗口。后来通过 SQLite 的 `INSERT OR IGNORE` 加内容指纹唯一索引，彻底消除了重复。
- **Token 刷新时机**：最早只在发帖失败时才刷新 token，但遇到 token 过期时第一次发帖必然失败，产生无效告警。改为在流水线启动时主动调用 `check_token`，如果剩余有效期不足 30 分钟则提前刷新，大幅减少了被动失败。
- **手机端长文本截断**：微博手机端对长文显示有折叠，部分超话粉丝习惯用移动端阅读。我们增加了文本截断逻辑，超过 140 字则自动在文末加上“... [展开全文]”并附加原文链接，保持阅读体验一致。

## 可复用建议

- **封装通用发布器**：将微博发布能力连同图片预处理、限流、归档打包为一个独立的 MCP wrapper，对外只暴露 `publish_to_topic(content, images)`，让 OpenClaw Skill 的逻辑更纯粹。
- **状态库独立化**：使用 SQLite 文件存储已发布指纹，便于跨不同 Skill 复用、备份和迁移，比依赖 OpenClaw 自身的 memory 更可靠。
- **死信队列兜底**：对于重试耗尽仍未成功的内容，写入一组死信队列，再由独立的人工检查流程处理，避免丢失重要信息。
- **可观测性**：确保每一环节都有结构化日志，限流触发次数、图片转换耗时、发布成功率都能在仪表盘中体现，方便调整容量和退避参数。

## 总结

借助 OpenClaw 的流程编排与 MCP 协议的工具化能力，微博超话同步可以构建为一条稳定、可维护的自动化流水线。核心挑战并非在“能不能发出帖子”，而在于如何优雅处理图片限制、频率风控以及发布状态的可靠记录。文中给出的预处理策略、退避重试机制和归档方案，已在持续运行中证明了其有效性。同样的工程思路也适用于其他社交平台的自动发布，只需替换对应的 MCP 工具即可。
