## 背景

在构建一个面向社交平台的内容同步 Agent 时，微博超话是绕不开的目标渠道。与普通微博不同，超话有独立的发布接口、限流规则和格式要求。如果只是简单调用“发微博”的 API，往往会遇到无声失败或账号风控。

这次实践基于 OpenClaw 的插件体系，把超话同步拆成一组合规的 MCP 工具，由 Agent 调度执行。核心目标有三个：稳定上传图片并关联到帖子，妥善处理限流，以及对每一次任务做好状态归档，避免重复或丢失。

下面我会绕过通用 SDK，直接用 HTTP 层的踩坑经验来说明思路。

## 问题拆解

把一条超话帖子拆成三个技术动作：

1. **图片上传**：微博的图片上传接口有独立的域名、需要 cookie，且 multipart 表单格式比预想的脆弱。
2. **发送超话帖**：文本必须显式包含 `#超话名称#`，且 `topic_id` 需要和超话名称匹配；接口对频率、图片尺寸都有隐性限制。
3. **限流与恢复**：错误码 10022（发帖太快）和 10024（需要验证码）最常见，必须设计重试等待和退避策略。
4. **状态归档**：Agent 是异步运行的，任务状态必须在本地持久化，才能支持断点续传、对账和重试。

## 做法/步骤

### 1. 登录态维护

所有操作都依赖微博 `cookie`。我用一个简单的 MCP 工具 `read_cookie_from_env` 从本地配置文件读取 `SUB` 和 `SUBP` 等关键字段，注入到所有请求头。不再做模拟登录，避免触发风控。

### 2. 图片上传

微博图片上传接口为：
```
POST https://picupload.weibo.com/interface/pic_upload.php
```
主要参数：`mime=image/jpeg`、`data=1`、`url=0`（返回 pid 而不是 url）。表单字段 `pic1` 是文件二进制流。

**关键踩坑点**：
- 必须先调一次 `preupload` 获取 `st` 参数吗？实测在带完整 cookie 且 `mime` 正确时，直接上传可以成功，但部分老账号需要先访问 `https://picupload.weibo.com/interface/pic_upload.php?ori=1&data=1&mime=image/jpeg&url=0&markpos=1&logo=&nick=0&marks=1&app=miniblog` 获取 `st`。为兼容性，我在上传前自动发一个 GET 取回 cookie 里的上传 token。
- **文件名必须带扩展名**，否则返回 `code=-1`，只提示“图片类型错误”。建议固定为 `upload.jpg`。
- **图片大小**：超过 5MB 会上传成功但发布后不显示，或被静默压缩。我的做法是上传前用 `sharp` 重采样到最长边 1280px，质量 85%，文件控制在 2MB 内。
- **multipart 表单构造**：用标准的 `form-data`，注意不要加 `Content-Type` 头（交给 http 库自动生成），否则 boundary 会出错。

上传成功后响应里会有一个 `pid`，格式类似 `007c1f2bgy1hx...`，这是后续发帖必需的 `pic_id`。

### 3. 发送超话帖

接口：
```
POST https://weibo.com/ajax/statuses/update
```
参数（表单格式）：
- `content`：文本，**必须以 `#超话名称#` 开头或包含该话题**，否则不会归入超话。
- `topic_id`：超话的 id，可从前端页面 URL 获取。
- `pic_id`：上传图片返回的 pid。
- `visible`：`0` 公开。

响应体 JSON，`code` 字段判断成功。成功返回 `ok: 1` 和帖子 id；失败返回错误码。

### 4. 限流处理

我将限流逻辑封装成一个独立的 `rate_limit_guard` 函数，在每次发帖前检查：

- 如果上次发帖时间距离现在 < 60 秒，sleep 到间隔满足。
- 如果响应返回 `10022`（操作太快），指数退避：等待 `(2^retry_count) * 10` 秒，最多重试 3 次。
- 遇到 `10024`（需要验证码），直接中断当前批次，标记任务为 `captcha_required`，并发通知。

为了更安全，我还限制了单账号一天的超话发帖上限（30 条），通过状态归档里的计数器控制。

### 5. 状态归档

使用本地 SQLite 数据库，表结构：
```
task_id | status | content | topic_id | images | cookie_version | created_at | attempt | last_error
```
状态枚举：`pending`, `image_uploading`, `posting`, `success`, `rate_limited`, `captcha_required`, `failed`。

Agent 启动时查询 `pending` 或 `rate_limited` 且冷却时间已过的任务，重新入队。成功和终态失败的任务会被移入归档表，每周清理一次。

## 真实踩坑记录

- **坑1：图片上传成功但帖子无图**  
  现象：发帖接口返回 `ok: 1`，但实际微博只有文字。排查发现 `pic_id` 格式正确，但图片尺寸超过 5000px 宽，被后台丢弃，没有任何提示。解决：强制压缩至 2048px 宽以内。

- **坑2：超话名称大小写敏感**  
  `#超话名#` 必须与超话创建时完全一致，包括简体/繁体。一次因为 `#生活#` 写成 `#生活 #` 多一个空格，导致帖子变成普通微博。增加预处理步骤，从官方 `topic_id` 反查正确的 `topic_name`。

- **坑3：Cookie 过期无明确报错**  
  上传图片或发帖时，过期 cookie 可能导致返回莫名其妙的重定向 HTML。添加请求前检查，响应头有 `location: https://passport.weibo.com/...` 时直接标记 cookie 失效。

## 可复用建议

如果你在 OpenClaw 生态下实现类似同步，建议：

1. **抽象成一组 MCP 工具**：`upload_weibo_image`、`post_to_topic`、`check_rate_limit`，由 Agent 按工作流调用，而不是在一个长脚本里揉合。
2. **图片预处理工具化**：提供压缩、格式转换功能，集成进上传工具中。
3. **状态外置**：不要把状态只存在 Agent 内存里，轻量 SQLite 非常适合这种任务级别的归档。
4. **可观测性**：每次任务都生成 task_id，记录每步耗时和返回码，方便回溯和排障。
5. **测试帖隔离**：开发时用一个仅自己可见的超话，或者发帖时 `visible=1`（仅自己可见），确认无误再改公开。

## 总结

用 Agent 做微博超话同步，难点不在“能不能发出去”，而在于错误处理和可恢复性。图片上传的脆弱参数、限流的隐式规则、cookie 的生命周期管理，每一环都可能导致静默失败。把过程拆成可观测的工具调用，配合状态归档和重试策略，才能真正跑成一个无人值守的同步链路。

这次实践也验证了 OpenClaw 插件模式在社交平台自动化中的可维护性：不用每次从头写脚本，而是积累可复用的工具集。
