# OpenClaw 定时任务防重入锁实战：为什么 5 分钟任务会撞车

你在 OpenClaw 里配置了一个每 5 分钟执行一次的 Agent，让它去拉取外部数据、调用 MCP 服务、写入内部表。过程预计耗时 6-8 分钟。为了“防止重复执行”，你在任务入口挂了一个 Redis 分布式锁：`SET lock:sync_data 1 NX EX 300`，执行完再 `DEL` 掉。上线后你发现——它还是撞车了，同时两个实例在跑。日志里数据被写了两遍，下游偶尔告警。

这正是防重入锁中最经典的坑：**“我已经加锁了，为什么还重入？”**。本文以 OpenClaw 定时任务为背景，复盘一次真实的锁失效案例，拆解根因，并给出可靠的工程化方案。

---

## 一、问题场景与初步复现

在 OpenClaw 工作流中，这种模式非常常见：一个 Cron 触发器每分钟（或每 N 分钟）调用一次任务节点，任务内部可能串联多个 Skill 或 MCP 工具。当任务执行时间 **大于调度间隔** 时，两个调度窗口都会拉起的任务实例就可能并发运行。

为防并发，很多团队会立即想到“分布式锁”。简单实现：

```python
# 伪代码
if redis.set("lock:job", "some_value", nx=True, ex=300):
    try:
        run_job()
    finally:
        redis.delete("lock:job")
else:
    log("前一个任务还在执行，跳过")
```

在理想情况下，这把锁可以阻止后一个实例启动。但实际观察发现，仍然会出现两个实例同时执行的情况，有时甚至看到锁被提前释放或误删。

根本原因集中在两点：

1. **锁超时时间 ≤ 任务实际执行时间**  
2. **非原子释放导致了“错删”别人的锁**

我们设置的 `ex=300`（5 分钟），但任务有时跑 6 分钟、7 分钟。当旧实例还在跑，锁在 5 分钟时过期，Redis 自动删除。此时新调度恰好触发，`SET NX` 成功，新实例获得锁并开始执行。于是新旧两个实例并发运行。雪上加霜的是，5 分钟后旧实例跑完，执行 `DELETE lock:job`，却把新实例持有的锁删掉了。如果此时再叠一次调度，第三个实例也能进来——连锁撞车。

---

## 二、根因拆解：锁的“归属”和原子释放

分布式锁的可靠性要求两条铁律：

- **持有锁的实体（线程 / 进程 / 实例）必须有唯一标识**，释放时只释放自己的锁。
- **锁的续期机制** 必须保证锁的生存期 ≥ 任务最大执行时间，否则即使有标识也会因锁过期而产生竞争。

`SET key value NX EX` 只是提供了互斥的获取语义，并没有解决“谁来释放”的问题。而简单的 `DEL` 是无差别操作，必然会在超时场景下误伤后继锁。

## 三、工程化做法：在 OpenClaw 中实现正确的防重入锁

以下步骤基于 OpenClaw 插件体系与 MCP 工具的能力，假设环境中已接入 Redis 服务（通过内置插件或 MCP Redis Server）。

### 1. 生成唯一实例标识
每次任务执行开始时，生成一个 UUID（例如 `uuid.uuid4()`），作为当前任务实例的“令牌”。

```
instance_token = uuid.uuid4().hex
```

### 2. 加锁时写入所属令牌
使用 `SET lock_key {instance_token} NX EX timeout`，将令牌存入锁值。  
锁超时 `timeout` 需设置为 **预期最大执行时间 × 1.2 ∼ 1.5 倍**。如果任务最长 8 分钟，可设为 600 秒。

```
acquired = redis.set("lock:sync_data", instance_token, nx=True, ex=600)
if not acquired:
    skip()
```

### 3. 释放锁使用 Lua 脚本原子化执行
一定不要用 `DEL`，而是提交一段 Lua 脚本，**仅当锁的当前值等于本实例 token 时才删除**：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

在 OpenClaw 中，你可以通过 MCP 工具直接执行 `EVAL` 命令，或在封装好的 Redis 插件中调用该方法。

### 4. 补充“看门狗”续期（可选但推荐）
如果任务运行时长波动较大，可在子进程内启动一个轻量线程，每隔 `timeout/3` 秒用 `EXPIRE` 延长锁的生存时间。续期时也需要校验令牌，确保锁仍归自己所有。若续期失败（锁已被抢占），应主动终止任务，避免数据冲突。

### 5. 在 OpenClaw 工作流中集成
将加锁、执行、释放包装成一个「防重入 Task 模板」或自定义 Skill 节点。入口仅暴露业务回调函数，其余锁逻辑复用，减少重复代码。

## 四、踩坑记录

1. **混用无标识的锁**：即使最初就知道要 Lua 原子释放，但在快速验证时，团队成员可能随手写了 `DEL`。Code review 必须强制使用带 token 的释放方式。

2. **锁超时拍脑袋设置**：以为“任务平均 5 分钟，锁设 5 分钟够了”，但忽略 GC、网络抖动、下游反压带来的延迟尖刺。永远按 P95 或最大允许时长来设定。

3. **Redis 主从切换**：如果 Redis 使用主从架构，锁刚在主节点写入，还未来得及同步至从节点就发生故障切换，新的主节点可能没有这把锁，导致另一个实例获取锁成功。对于严格防重入的场景，可考虑 Redlock 或使用 etcd 等硬件时钟要求的实现。非金融级场景可权衡接受极低概率的冲撞。

4. **任务异常退出**：如果任务被 `kill -9` 或 OOM，并不会执行 Lua 释放脚本。依赖锁过期把坑填上，因此过期时间必须设置；反之也不能设置过短。

5. **锁竞争频率**：如果任务实际执行时长经常超过调度间隔，防重入只能保证不并发，但会导致每次调度都失败（跳过），看起来像任务“掉了”。这时需要重新设计调度策略，比如改为“上一个完成后再触发下一次”，或增大调度间隔。

## 五、可复用的工程建议

- **封装通用 LockService**：在 OpenClaw 插件中提供一个 `acquire(key, ttl)` 和 `release(key, token)` 接口，内置 Lua 释放逻辑，以及可选的 `RenewalTask`。通过 MCP 或内置 API 暴露给工作流使用。
- **状态表双重保险**：对关键业务，在数据库增加一个 `task_run` 状态表（如 `status = 'running'` 配合唯一约束），作为应用层的二次防重。锁和状态同时使用，可避免锁误删后的并发。
- **可观测性**：为锁获取、释放、续期事件打点，输出到 OpenClaw 的日志/指标面板。当长期出现“锁获取失败”说明调度周期或执行时长需要调整。
- **压测验证**：部署后模拟长时间运行、异常中断、Redis 短暂不可用等情况，确认防重入行为符合预期。

---

## 六、总结

“5 分钟任务为什么会撞车”的答案不在锁的有无，而在锁的**实现细节**。没有归属标识的分布式锁，在超时场景下一定会发生误删，进而导致并发执行。工程上，用唯一令牌 + Lua 原子释放 + 合理超时 + 看门狗续期，可以构建出在 OpenClaw 自动化流程中足够可靠的防重入机制。这个思路不仅适用于 OpenClaw，对所有依赖 Redis 锁的定时任务系统同样适用。

编码时多花十几行代码，上线后就能少出一次事故，把脑子腾出来写更有价值的 Agent 逻辑。
