## 背景

在 OpenClaw 这类 Agent 框架中，我们经常通过 MCP 工具或自定义 Shell 脚本让 Agent 操作本地文件系统——读取配置、生成报告、执行代码审查。这种能力很强大，但默认情况下，Agent 进程通常拥有当前用户的所有文件访问权限。随便一个 prompt 里写 `“读取 ../../.env”` 就可能把敏感信息泄露到对话上下文，或者误删重要的系统文件。

常见的应对是在系统级用容器或沙箱把整个进程圈起来，但日常开发、内部工具场景往往需要一种更轻量、方便集成到脚本里的方案：对文件读写操作做路径白名单，只允许在指定目录内操作。

这篇文章聊的就是如何在 MCP 工具或自动化脚本里给文件访问加一道「目录白名单」护栏，实现最小权限，同时保持工程上的可维护性。

## 问题建模

设想一个典型的 MCP 文件工具：接收 `action` (read/write/list) 和 `path` 参数，然后直接用 `open()` 或 `os.listdir()` 执行操作。安全风险主要来自两方面：

1. **路径穿越**：传入 `../../etc/passwd` 类相对路径跳出工作区。
2. **符号链接绕过**：白名单目录下的一个软链接指向外部目录，通过该链接读写等于以白名单用户身份访问了外部文件。

我们的目标很明确：在工具入口对 `path` 做一次校验，保证解析后的绝对路径一定位于预设的白名单目录树下。

## 实现步骤

### 1. 定义白名单目录集合

通常在工具配置里写成数组，比如：

```python
whitelist_dirs = [
    "/home/user/projects/myapp",
    "/tmp/safe_workspace"
]
```

建议使用绝对路径，配置时解析好。

### 2. 路径解析与规范化

用 `pathlib.Path.resolve()` 完成规范化，同时处理符号链接和相对路径。核心校验逻辑如下：

```python
from pathlib import Path

def is_within_whitelist(target_path: str, whitelist: list[str]) -> bool:
    try:
        abs_target = Path(target_path).resolve(strict=False)
    except (OSError, RuntimeError):
        return False
    
    for allowed in whitelist:
        allowed_path = Path(allowed).resolve(strict=True)
        # 确保目标路径以白名单目录为前缀，且不允许直接比较目录本身(可选)
        try:
            abs_target.relative_to(allowed_path)
            return True
        except ValueError:
            continue
    return False
```

`resolve(strict=False)` 处理路径存在与否的情况，即使文件还不存在（比如写操作），也能解析路径是否落入白名单。`relative_to` 如果目标不在该目录树内会抛出 `ValueError`，我们捕获后继续检查下一个白名单目录。

### 3. 集成到 MCP 工具

以简单的 Python MCP 服务器为例，在工具函数入口加装饰器或手动调用校验：

```python
@server.tool()
def file_read(path: str) -> str:
    if not is_within_whitelist(path, WHITELIST):
        raise PermissionError(f"Access to {path} denied.")
    real_path = Path(path).resolve()
    return real_path.read_text()
```

对于写操作同理。对于 `list` 目录操作，同样要对传入的目录路径做校验。

### 4. 处理边缘情况

- **工作目录**：MCP 服务器如果设置了不同的 CWD，`resolve()` 依然能给出正确的绝对路径，因为 `Path(path)` 会基于当前进程的 CWD 解释相对路径。确保启动时 CWD 是你信任的即可，或者显式用 `Path.cwd()` 不便，`resolve()` 自动处理。
- **Windows**：`resolve()` 在 Windows 上也会处理盘符、UNC 路径等。需注意大小写不敏感问题：`resolve()` 返回的路径是真实路径，大小写会被文件系统规范化。如果白名单目录定义的大小写与真实路径不一致，需要提前把白名单目录也 `resolve()` 一下，保证比较基于真实大小写。
- **符号链接**：`resolve()` 会跟踪所有符号链接。这意味着即使白名单目录内有一个符号链接指向 `/etc`，经过 `resolve()` 后路径会变为 `/etc/...`，自然不匹配白名单，会被拒绝。这正是我们需要的。如果你需要允许通过符号链接访问外部目录，那需要额外设计，但本文场景是禁止。

## 实际踩坑记录

在一次给文件管理 MCP 集成白名单时，遇到了几个坑：

1. **相对路径含 `..` 且目标不存在**  
   `Path("projects/../etc/passwd").resolve(strict=False)` 会尝试解析，但如果中间的 `projects` 目录存在，`..` 会正常跳转。如果 `projects` 不存在，路径解析可能会提前失败，但通常文件系统还是能正确规范化，只要不设置 `strict=True`。测试时注意构造不存在的深层路径。

2. **多线程/多进程 CWD 污染**  
   如果 MCP 服务器内部某些库或业务逻辑修改了 `os.chdir()`，会影响 `Path` 的相对路径解析基础。建议在工具入口统一转为绝对路径，减少对全局状态的依赖。更好的做法：要求工具只接受绝对路径（由 Agent 前端或提示词约束），不过仍有风险，加上白名单校验更彻底。

3. **`resolve()` 在挂载点上的行为**  
   如果白名单目录是挂载点（如容器环境），`resolve()` 会返回设备上的真实路径，可能与预期路径不一致，需要测试确认。保守做法是用 `os.path.realpath()` 行为类似，但 `pathlib` 更干净。

4. **性能**  
   每次文件操作都做一次 `resolve()` 基本无感，但如果你有一个频繁调用的工具，并且白名单目录很多，可以把白名单提前 `resolve()` 缓存，每次都直接比较前缀，不必重复解析。

## 可复用设计建议

不要把校验逻辑散落在每个工具里，应该封装成一个可配置的中间层：

- **路径安全层函数**：`secure_path(path, whitelist)` 返回解析后的绝对路径，若违规则抛异常。
- **装饰器**：`@require_whitelist(whitelist)` 自动校验被装饰函数的某个参数（通过参数名约定，如 `path`）。
- **配置化白名单**：从环境变量或配置文件读取，支持多个项目目录，方便开发/测试/生产环境切换。
- **日志记录**：拒绝时记录请求路径、真实路径、白名单目录，便于排错。

例如简单装饰器实现：

```python
def require_file_access_whitelist(arg_name="path"):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            path = kwargs.get(arg_name) or (args[0] if args else None)
            if path:
                safe_path = secure_path(path, WHITELIST)
                kwargs[arg_name] = str(safe_path)
            return func(*args, **kwargs)
        return wrapper
    return decorator
```

## 总结

给 Agent 的本地文件操作加上目录白名单，是工程化安全实践的第一步。它不依赖重量级容器，代码量很小，却能有效防止大部分路径穿越和符号链接绕过攻击。配合 MCP 工具的规范设计，可以让自动化脚本在灵活性和安全性之间取得平衡。

在 OpenClaw 的生态中，类似机制可以沉淀为社区通用的 MCP 工具安全模块，让做插件的开发者直接复用，避免每个人都从零踩坑。安全护栏不是一时的工作，而是持续迭代的基线。

**最后记住**：没有万无一失的方案，白名单只是纵深防御的一层。如果你的 Agent 能执行任意命令，还需要考虑命令注入、进程隔离等问题。但把文件访问圈在一个目录树内，永远是值得做的第一步。
