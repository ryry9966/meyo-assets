## 为什么你的自动化脚本需要目录白名单

当 Agent 被赋予“读写本地文件”能力的时候，事情就开始变得危险。一个 MCP 插件、一个自定义工具调用，甚至一段 AI 生成的 Shell 命令，都可能无意中扫到 `~/.ssh`、覆盖 `config.yaml`，或者把日志写到系统关键路径里。

传统的权限控制依赖操作系统用户隔离，但 Agent 进程通常以当前用户身份运行，和你的个人文件处于同一信任域。更糟糕的是，很多自动化实践者为了让功能跑通，直接把项目根目录作为工作区，给了脚本访问整个 home 目录的机会。

这不是安全问题突然变多了，而是**自动化能力的半径在变大，但访问约束没有同步收紧**。如果不加限制，任何一个文件写入工具都可能变成删库的入口。所以，在 Agent 访问文件系统之前，必须加一层**本地目录白名单**——只允许它读写你明确指定的目录，其余路径一概拒绝。

## 问题拆解：白名单的边界在哪里

最简单的想法是：在调用 `open()`、`os.remove()` 之类函数前，检查目标路径是否以白名单目录开头。这能挡住 80% 的直白攻击，但还有一些边缘情况需要专门处理：

- **符号链接逃逸**：`/allowed/dir/link` 可能指向 `/etc/passwd`，直接检查前缀会误判。
- **相对路径混淆**：`../../sensitive/file` 在拼接工作目录后，可能绕出白名单范围。
- **路径规范化差异**：`/allowed/dir/../sensitive` 在解析后等价于 `/allowed/sensitive`？还是 `/sensitive`？不同语言和系统表现不一致。
- **Windows 兼容**：盘符、反斜杠、长路径前缀 `\\?\`，都容易让字符串匹配失效。

所以，一个可用的白名单检查不能只做前缀匹配，而是必须**解析路径的真实绝对路径**，再判断其是否落在白名单子树内。

## 一个可复用的实现路径（以 Python 为例）

在 OpenClaw 体系中，大量工具和插件通过 Python 实现。我们可以为文件操作函数加一个统一的路径校验装饰器或上下文管理器。核心逻辑如下：

```python
import os
from pathlib import Path
from typing import List

class FileAccessGuard:
    def __init__(self, allowed_dirs: List[str]):
        # 预先将所有白名单目录转为解析后的绝对路径
        self.allowed = [Path(d).resolve() for d in allowed_dirs]

    def is_allowed(self, target_path: str) -> bool:
        # 1. 转为绝对路径，并跟随符号链接
        resolved = Path(target_path).resolve()
        # 2. 检查任一台名单目录是否为 resolved 的前缀
        for allowed in self.allowed:
            try:
                resolved.relative_to(allowed)
                return True
            except ValueError:
                continue
        return False

    def guard_open(self, path, mode, *args, **kwargs):
        # 读操作可以酌情放宽，但写、删必须拦截
        if 'w' in mode or 'a' in mode or 'x' in mode:
            if not self.is_allowed(path):
                raise PermissionError(f"写入路径 {path} 不在白名单内")
        return open(path, mode, *args, **kwargs)
```

使用时，在插件中注入 `guard` 实例，所有文件写入路径通过 `guard.guard_open()` 走查。这样，即使 Agent 生成了恶意路径，也会在真正触碰文件系统之前被拒绝。

## 实践中踩过的坑

1. **`resolve()` 在路径不存在时会抛异常吗？**  
   Python 的 `Path.resolve()` 要求路径存在，否则会抛出 `FileNotFoundError`。这很讨厌，因为很多写入操作本身就是创建新文件。解决方案是**先解析父目录**，再拼接文件名后判断。或者使用 `os.path.realpath` 的类似逻辑自己实现一个“尽力解析”函数——对存在的部分逐级 `resolve`，不存在的部分保留原样，最后再检查前缀。工程上，这个“部分解析”反而是最花时间的点。

2. **临时文件绕行**  
   如果 Agent 可以调用系统临时目录（如 `/tmp`），白名单通常会放行。但攻击者可能先在 `/tmp` 下创建恶意脚本，再通过其他工具执行。如果临时目录必须可用，建议隔离一个专用临时子目录，例如 `/tmp/agent-sandbox/`，并在脚本结束后清空。

3. **相对路径与工作目录绑定**  
   有些开发者习惯在代码中 `chdir` 到项目目录，然后使用相对路径操作文件。白名单检查时，如果忘记用 `os.getcwd()` 拼接当前工作目录，会导致校验绕过。更好的做法是**完全禁止直接使用相对路径**，在 guard 中强制要求传入绝对路径或者自动拼接为绝对路径。

4. **Windows 符号链接和 Junction**  
   Windows 上除了 `.lnk`，还有 Junction 和符号链接，`pathlib` 的 `resolve()` 在 Python 3.8+ 已能较好处理，但需注意权限问题，可能静默失败。建议在单元测试中覆盖跨盘符、Junction 场景。

## 可复用的建议

- **最小白名单原则**：不要直接把 `$HOME` 放进去。按项目需求，精确到单个数据目录、输出目录。
- **读写分离**：只读目录和可写目录分开配置。对配置文件、模型权重等，只给读权限，避免脚本误写。
- **日志和临时文件隔离**：将日志输出重定向到白名单内的专用目录，避免 Agent 访问 `/var/log` 或系统级路径。
- **在 MCP 服务端做校验**：如果 Agent 通过 MCP 协议调用文件工具，校验逻辑放在工具服务端，而不是依赖 Agent 的提示词约束。提示词是软约束，代码才是硬边界。
- **测试要覆盖恶意样本**：准备几个典型的攻击路径（如 `../../etc/passwd`、symlink 指向高权限文件），写成自动化测试，每次修改 guard 逻辑后跑一遍。

## 总结

本地目录白名单不是什么新概念，但在 Agent 自动化的新场景下，它的重要性被重新放大。文件系统访问权限的约束，应该像 HTTP 请求的 CORS 策略一样，成为每个具备文件能力的插件的标配。上面这套基于路径解析的 guard 方案，虽然简单，但足够对抗绝大多数非提权类的误操作和恶意注入。配合容器或沙箱使用，效果更好。对于 OpenClaw 生态的实践者来说，**从一开始就把“允许访问哪些目录”作为一个必须回答的部署问题**，会少踩很多坑。
