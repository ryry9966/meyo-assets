# 给 Agent 加一把锁：用本地目录白名单防止自动化脚本误删文件

## 背景：当 Agent 开始操作本地文件

近半年，越来越多的开发者把 Agent 直接接入本地环境——通过 MCP 文件系统工具、OpenClaw 插件或者自建自动化流水线，让 LLM 可以读取、创建、编辑甚至删除文件。这种“把终端交给 Agent”的模式确实能压缩手工操作，但随之而来的风险也很直接：一条未经校验的指令，就可能清掉一个配置目录，或者把输出写进不该碰的路径里。

工程里有个基本共识：**信任模型输出，不意味着要给它 root 权限**。给文件访问加护栏，不是不信任 Agent，而是承认现实——LLM 会犯错，提示词有边界，环境变量会串，甚至执行链里可能混入意外的路径拼接。

## 问题：一个没有边界的工作区是危险的

常见风险场景包括：

1. **误删/误改系统文件**：Agent 在拼接路径时出现幻觉，或者 prompt 里示例路径被当真，结果删除了 `/etc/nginx/` 下的配置。
2. **信息泄露**：Agent 读到了本不该访问的凭证文件或密钥，并可能通过日志或输出意外泄漏。
3. **命令注入**：文件名或目录名里夹带特殊字符，在拼接命令时形成注入，最终访问了限定范围之外的文件。
4. **自动化流程越权**：一个本应只处理 `./data/` 目录的脚本，因为软链接或相对路径，跑到了上级目录。

我在一次使用 MCP filesystem 工具的自动化流程中就踩过坑：因为配置了 `writable: true`，Agent 在整理日志时把 `/tmp` 下的一些临时文件移动到了项目目录，顺带把 `/tmp` 里某些其他进程的临时文件也给改了——虽然没造成实质损失，但“越界”这件事本身就是工程债务。

## 做法：为本地文件访问加上目录白名单

最务实的方法不是完全禁用文件操作，而是**把 Agent 的文件访问能力关进一个显式声明的目录笼子里**。下面给出三种从轻到重的实施方式，可根据自己的运行环境选择。

### 方式一：使用 MCP 服务器的内置白名单

如果用的是官方 `@modelcontextprotocol/server-filesystem`，其实现已经支持在启动参数中指定允许的目录。在 MCP 客户端配置（比如 OpenClaw 的 `mcp_config`）里，把 `args` 写成：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "--allow",
        "/home/user/projects/my-agent-workspace"
      ]
    }
  }
}
```

`--allow` 可以重复多次，允许多个目录。注意这里的路径必须是绝对路径。启动后，Agent 调用 `list_directory`、`read_file`、`write_file` 等方法时，只要目标路径不在白名单目录下，就会直接返回权限错误，连读的机会都没有。

**优点**：零侵入，只需配置，MCP 服务器自身保证安全边界。  
**局限**：只适用于标准 filesystem 工具；需要重启 Agent 重新加载配置；不支持动态修改白名单。

### 方式二：自建文件代理层，拦截并校验路径

当需要更大的灵活性（如动态白名单、日志审计、操作类型限制）时，可以自己写一个轻量级的 MCP 包装服务。以 Python 为例，在文件操作前统一调用一个 `guard` 函数：

```python
import os
from pathlib import Path

ALLOWED_ROOTS = [
    Path("/home/user/projects/agents/sandbox"),
    Path("/tmp/agent-scratch"),
]

def is_allowed(target: Path) -> bool:
    # 解析真实路径以防止符号链接绕过
    real_path = target.resolve()
    return any(real_path.is_relative_to(root) for root in ALLOWED_ROOTS)

def guarded_read(path: str) -> str:
    target = Path(path)
    if not is_allowed(target):
        raise PermissionError(f"Access to {path} is not allowed")
    return target.read_text()
```

这里最关键的一行是 `target.resolve()`，因为直接比较字符串前缀是危险的。例如白名单是 `/home/safe`，攻击者或意外输入可能用 `/home/safe/../secret` 绕过简单的 `startswith` 检查。`resolve()` 会解析所有 `..` 和符号链接，得到真实路径后再与白名单比较。

这种代理层可以进一步注入日志、操作频率限制，以及只允许读写、禁止删除等细粒度控制。

### 方式三：操作系统级隔离（容器 + 挂载）

如果 Agent 运行在 Docker 中，采用只读挂载加少量可写 volumes 是最彻底的办法。Dockerfile 示例片段：

```dockerfile
FROM python:3.11-slim
RUN useradd --create-home agent
USER agent
WORKDIR /workspace
# 运行时挂载: -v /safe/data:/workspace/data:rw
```

配合 `--read-only` 标志和 `tmpfs` 挂载 `/tmp`，即使 Agent 尝试写入系统目录也会因为只读文件系统被内核拒绝。这种方式不仅解决了文件访问边界，还限制了进程本身对环境的影响。

## 踩坑记录

1. **软链接与挂载点穿越**：  
   `resolve()` 只能消除脚本层面的符号链接，如果底层存在 bind mount 或自动挂载，仍需保证白名单目录自身不包含越界的挂载点。验证方法：`findmnt` 或 `mount` 检查目标路径下是否有其他文件系统的挂载。

2. **相对路径隐式拼接**：  
   某些 MCP 服务端实现允许客户端传入相对路径，并以服务端工作目录为基准。如果启动目录在白名单之外，需要显式在服务端设置 `cwd` 或拒绝相对路径请求。

3. **部分 MCP 实现忽略白名单**：  
   个别第三方 filesystem 工具可能根本就没实现路径校验，只是在 README 里提了一句“建议运行在沙箱”。使用前最好直接看源码里的 `validate_path` 逻辑。

4. **白名单目录内权限过于宽泛**：  
   即使限制了目录，如果可执行权限、SUID 文件或 `.env` 文件也在白名单内，仍可能产生风险。建议白名单目录内不要保留不必要的敏感文件。

5. **配置热更新不可达**：  
   修改 MCP 配置后，Agent 进程不重启就不会生效。如果依赖这种护栏作为主要安全手段，需要同步到运维流程里——比如每次修改后自动发送 SIGHUP 或触发重连。

## 可复用建议

- **最小权限声明**：Agent 需要的目录精确到一个叶子目录，而不是 `/home/user` 这种大范围。
- **读写分离**：若 Agent 只需读，就不要给写权限；在 MCP 端可以通过只运行 `read_file`、关闭 `write_file` 实现。
- **操作日志全量记录**：在自定义代理层记录每次文件访问的 (时间, 请求ID, 目标路径, 操作类型, 结果)，方便事后追溯。
- **周期性审计**：定期检查白名单目录内是否出现了不应存在的文件，以及是否存在新的符号链接。
- **结合 prompt 约束**：在 system prompt 中加入文件操作路径限制说明，这样做虽然不能代替程序级护栏，但可以减少 Agent 主动越界的意图。
- **测试越界用例**：把越界访问作为自动化测试的一部分，例如用 `..`、符号链接、绝对路径等形式尝试逃逸，确保护栏有效。

## 总结

Agent 文件访问护栏不是“防黑客”级的重型安全方案，而是工程化里的一道有效防呆机制。它的价值在于：**用极小的实现成本，避免绝大多数由失误、幻觉和路径拼接错误导致的文件事故**。对于每天都在和本地文件打交道的 OpenClaw 或 MCP 用户来说，在配置里加上白名单、解析真实路径、挂载只读数据卷这三板斧，已经能兜住 90% 以上的坑。

别等到 `rm -rf` 真的被执行了再去改配置——花十分钟加上白名单，相当于给自动化脚本装了一个看得见的“文件权限门禁”。
