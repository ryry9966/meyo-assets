## 背景

OpenClaw 的 Agent 是长期运行的：接着消息渠道、跑定时任务、调 MCP 工具，甚至替你回复群里的朋友。它不是一次性会话，而是持续存在于你的社交关系里。这种场景下，模型出厂的默认性格是不够的。SOUL.md 就是留给你的那个口子——一个纯 Markdown 文件，定义这个 Agent 是谁、怎么说话、哪些事不碰。

## 问题

实际跑下来常见三类毛病：

1. **人设漂移**：上下文被压缩或会话重置后，Agent 语气变了，熟人会觉得“换了个人”。
2. **越界行为**：没有明确边界时，Agent 可能替你做承诺、透露不该说的信息，或对陌生请求照单全收。
3. **调教无效**：很多人把 SOUL.md 写成超长 prompt，堆满形容词，结果每次表现不一致，以为是模型不行，其实是文件没写对。

## 做法

我的 SOUL.md 控制在 40 行左右，分五段：

1. **身份**：一两句话，名字、定位、和主人的关系。不写背景故事。
2. **语气**：用具体规则替代形容词。不写“友好一点”，写“中文回复，短句，不用 emoji，除非对方先发”。
3. **价值观**：3~5 条真正影响取舍的，比如“不确定的事说不确定，不编”。
4. **边界（最重要）**：写成可判定的规则，例如——
   - 不替我承诺任何时间、价格、结果；
   - 涉及转账、验证码、隐私信息，一律转给我本人处理；
   - 不确定是不是我本人发的消息时，先不行动。
5. **兜底**：规则没覆盖的情况，默认保守，先问人。

写完保存，重启网关生效。然后做回归测试：开三个全新会话，问同一组诱导性问题（让它转钱、让它冒充你、让它点评你老板），逐条验证边界是否真的生效。

## 踩坑点

- **写太长**。SOUL.md 每次会话都会进上下文，500 行的“人格说明书”会稀释关键规则，还挤占任务 token。一屏以内，细节下沉到 AGENTS.md 或 USER.md。
- **形容词堆砌**。“聪明、幽默、有温度”模型执行不了，每条都要能翻译成一个可观察的行为。
- **规则冲突**。前面写“简洁”，后面写“详细解释”，模型会随机选边。写完通读一遍，冲突就合并。
- **只改不测**。行为往往在长对话末端、上下文被压缩之后才暴露，不跑测试等于没改。
- **当日记写**。SOUL.md 是宪法不是流水账，改动走 git，别靠印象。

## 可复用建议

- 给 SOUL.md 建独立 git 仓库，每次行为异常就补一条规则，提交信息写清触发场景，攒一个月就是一份真实的行为档案。
- 维护一个 5~10 条的“边界测试集”，每次改完全量跑一遍。
- 分层：稳定人格放 SOUL.md，操作规程放 AGENTS.md，关于你的信息放 USER.md，别三层混写。
- 多写正面指令，少堆否定句——“保持简短”的遵循率高于“不要太啰嗦”。

## 总结

SOUL.md 的价值不在“让 Agent 更像人”，而在把行为约束从玄学变成配置。它和 MCP 工具清单、自动化脚本一样，是需要版本管理和回归测试的工程产物。花一个下午写 40 行、跑一轮边界测试，远比事后向朋友解释“那不是我说的”划算。
