## 背景

OpenClaw 这类本地 Agent 的能力边界，基本等于它能触达的外部服务集合。模型再强，不接 API 就只能聊天。实际落地时，对接外部服务常见三条路：把 API 文档塞进 prompt、写 skill 插件封装、挂一个 MCP server。下面以我们对接内部服务的一次实践为例，梳理一条比较稳的路线。

## 问题：为什么"把文档丢给模型"不够

最初的做法很朴素：把 REST 文档贴进 system prompt，让模型自己拼请求。能跑，但问题很快暴露：

- 每轮对话都重复携带完整文档，token 开销大；
- 密钥不得不写进上下文，日志一落盘就是事故；
- API 返回 500 时，模型倾向于"编一个成功结果"，排查无从下手；
- 同一接口被不同会话以不同姿势调用，行为不可预测。

结论：模型适合决策，不适合当 HTTP 客户端。鉴权、重试、超时、限流这些工程细节，必须沉到代码层。

## 做法：三层结构

**1. 工具层（skill 插件）**。每个外部服务封装成独立 skill，按插件规范声明工具签名。两个关键设计：

- 工具按用户意图划分，不按 REST endpoint 划分。比如不暴露 `GET /user`、`GET /order` 两个接口，而是暴露一个 `query_user_orders`，内部做编排；
- 参数用 JSON Schema 严格约束，枚举值写全，模型填错的概率会显著下降。

**2. 传输层**。统一走一个 HTTP client 封装：环境变量读密钥、默认 10 秒超时、幂等 GET 自动重试两次、非幂等 POST 绝不重试。请求与响应（脱敏后）落结构化日志。

**3. 注册层**。skill 装载时向 Agent 注册工具清单，一次只挂当前任务相关的 3-5 个工具。工具描述是写给模型看的，不是写给人的：动词开头、说清返回结构、明确"什么情况该调、什么情况不该调"。

## 踩坑点

- **错误必须作为数据返回**。工具直接抛异常会让 Agent 中断；改成返回 `{"ok": false, "error": "...", "hint": "..."}`，模型能自己决定重试还是换路。
- **长任务别阻塞主循环**。有次对接导出接口，同步等了 90 秒，Agent 整个卡死。改成提交任务返回 job_id + 提供轮询工具，体验立刻正常。
- **工具描述的措辞**。写"查询订单"，模型会乱调；改成"根据用户 ID 查询近 30 天已支付订单，仅当用户明确询问购买记录时使用"，调用准确率明显提升。
- **密钥隔离**。skill 只允许从环境变量读配置。我们踩过一次 token 被打进错误日志的坑，之后所有日志出口统一做脱敏。

## 可复用建议

1. 一个服务一个 skill，禁止跨服务混用配置；
2. 上线前先跑 dry-run：工具只返回"将要发出的请求"，不真调，用来校验 Agent 的调用意图；
3. 写操作一律加确认门槛，Agent 给出参数摘要，人点头再执行；
4. 工具数量做减法比做加法难，但每多一个工具，模型选错的概率都在涨。

## 总结

Agent 对接外部服务，本质是一次"握手协议"的设计：模型负责理解意图和编排，skill 负责把意图翻译成可靠的 HTTP 语义，中间靠严格的工具契约对齐。把工程细节从上下文挪到代码里，Agent 的稳定性会有数量级的改善。这套三层结构已在内部复用到五个服务的对接，新服务接入大约半天。
