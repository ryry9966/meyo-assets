# 为什么现在都要谈这件事

Agent 接上 MCP 和各类插件之后，能力边界从"回答问题"扩展到改文件、调 API、发消息、动数据库。工具一多，核心问题就从"能不能干"变成了"该不该自己干"。这个问题不解决，要么 agent 出格，要么人被审批消息淹没。

## 两类典型翻车

**过度自主**：让 agent"清理一下临时数据"，它理解成删了生产环境的一张表；让它"跟进一下客户"，它直接发了封对外邮件。事后看每一步调用都"合理"，串起来就是事故。

**过度请示**：每一步都问"可以继续吗"。一天二十条审批，人开始机械点确认——这比不问更糟，因为它制造了"有人把关"的假象，实际没人真的在看。

本质上是中断成本和出错成本的权衡：问得太勤，人变成瓶颈和摆设；问得太少，错误不可逆。

## 一个可落地的判断框架

用两个维度给操作分类：

- **可逆性**：出错后能否低成本撤销。git 里的改动可逆，发出去的邮件不可逆。
- **影响半径**：只碰 agent 自己的沙箱，还是波及生产环境、共享资源或外部他人。

交叉出四类：

| | 半径小 | 半径大 |
|---|---|---|
| 可逆 | 直接执行，留日志 | dry-run 出 diff，确认后批量执行 |
| 不可逆 | 可执行，留日志 | 必须人工确认 |

对应到落地步骤：

1. **盘点工具，打风险标签**。把每个 MCP 工具/插件标为 read / write-reversible / write-irreversible / external 四类，一张表就够。
2. **规则落在执行层，不是 system prompt**。只读工具直接放行；写类操作走审批 gate；外部副作用类默认禁用，按需开启。
3. **审批内容自包含**。必须带三样：要执行什么（具体命令和参数）、影响哪些资源、怎么回滚。只问"可以继续吗"等于没问，人没法做判断。
4. **审计与复盘**。每次自主写操作留日志，每周抽十条看看它自己都干了什么。

## 踩坑点

- **审批疲劳**。同类请求一天超过几条，说明规则该调了：要么把高频低危操作放进白名单自动执行，要么这个任务本来就不该交给 agent。
- **prompt 约束不是权限边界**。在 system prompt 里写"不要删库"没有强制力，agent 犯迷糊时照样会调。约束要落在工具层——没有那个工具，或者工具本身要求二次确认。
- **无人值守没预设计**。定时任务半夜卡在"等待确认"，要么挂死要么超时乱来。无人值守任务必须预授权一份明确白名单，白名单外一律挂起等人。
- **凭证粒度太粗**。为省事给 agent 一个管理员 token，边界就只剩 prompt 了。按工具拆最小权限凭证。
- **会话中途放宽权限没留痕**。临时开通的权限结束后应回收，放宽决策本身也要进日志。

## 可复用建议

- 新接工具先问两个问题：这个操作能撤销吗？影响谁？
- 默认拒绝不可逆操作，白名单放行高频低危。
- 写操作先出 plan/diff，再执行。
- 审批消息必须包含"做什么 / 影响 / 回滚"三要素。
- 规则集中在一个文件里维护，别散落在各处 prompt。

## 总结

权限边界不是一次性配置，而是随 agent 能力和任务变化的活规则。判断标准可以压缩成一句话：错误能低成本撤销、影响不出自己的边界，就自己干并留痕；否则停下来，把即将发生的事讲清楚再问人。宁可少一点自动化，也不要让"有人审批"沦为摆设。
