## 背景

多数人对 AI 助手的使用仍然停留在"一问一答"：你发消息，它响应。这个模式的隐含成本是，发起权永远在人这边——盯服务器磁盘、记着每周汇总、跟进 CI 状态，都是你记得去找助手，而不是助手记得来找你。OpenClaw 常驻运行，天然带 cron、事件钩子和 heartbeat 这些机制，做 proactive 的地基其实早就有了，只是很多人只把它当聊天入口用。

## 问题

但直接把"主动性"打开，常见的失败模式有三种：

1. **噪音爆炸**：每半小时汇报一次"一切正常"，三天后你把它静音，主动性直接归零；
2. **无状态重复**：同一个事件反复触发、反复通知；
3. **无人监督的写操作**：定时任务拿着完整权限在后台改东西，出错没人兜底。

核心矛盾在于：触发可以自动化，但"值不值得打断人"这个判断必须被工程化约束。

## 做法：三层触发链路

**第一层：定时任务（cron）。** 适合周期确定的事，比如每天 9 点汇总昨日日志、每周一生成周报草稿。表达式写进配置，进版本管理。

**第二层：事件驱动。** webhook、文件监听、git push 触发，适合"条件明确、时机不定"的事，比如 CI 挂了立刻推送。要点是事件源只传"发生了什么"，判断交给 agent。

**第三层：heartbeat 状态巡检。** 给 agent 一份 checklist（磁盘水位、待办、日历、监控阈值），每个心跳周期自检一遍，强制输出结构化结论：

```json
{ "action": "notify | act | ignore", "reason": "..." }
```

只有 `notify` / `act` 才真正执行，`ignore` 静默落日志。这一条是整个 proactive 体验的总开关。

三层的分工一句话讲清：cron 管"什么时候必须做"，事件管"发生了就要做"，heartbeat 管"要不要现在告诉你"。

## 踩坑点

- **时区**：cron 默认 UTC，国内环境比预期晚 8 小时触发，第一份日报直接变成"明天的日报"。
- **通知去重**：把已通知的事件 ID 写进本地状态文件，heartbeat 每次先读再判，否则同一条告警每 30 分钟轰炸一次。
- **心跳成本**：每个 beat 都是一次完整调用，频率太高账单难看。建议 5–15 分钟起步，确认输出有价值再加密。
- **幻觉汇报**：不给结构化约束时，模型倾向于"编点东西显得有用"。schema 必须强制，且"无事必须返回 ignore"要写进 system prompt。
- **静默失败**：主动任务失败时没人收到消息，因为报错通道就是通知通道本身。单独留一条失败路径：写本地文件 + 低频兜底 cron 扫描。

## 可复用建议

1. **默认沉默**：所有触发器先配成只写日志，观察一周输出质量，再放开通知权限。
2. **权限最小化**：proactive 链路里的技能先挂只读凭证，写操作只生成草稿等你确认，跑稳一个月再考虑放权。
3. **触发配置即代码**：cron 表达式、事件路由、heartbeat checklist 全部进 git。以后每次想问"它为什么主动给我发这个"，diff 一下就有答案。
4. **全量审计**：每次主动行为记录触发源、输入、输出、耗时，出问题有迹可循。

## 总结

Proactive 不是把 agent 调得更"聪明"，而是把触发、判断、执行三个环节拆开，各自加上护栏：触发靠 cron / 事件 / 心跳三层，判断靠结构化阈值，执行靠最小权限和审计。先把"沉默地正确"跑通，再逐步放开"主动地打扰"——信任不是一次惊艳攒出来的，是一次一次没白打扰攒出来的。
