## 背景

OpenClaw 的 cron 任务，本质是定时触发的一次性 agent 会话：到点自动执行你写好的 instruction，把结果发到指定渠道。听起来简单，但很多人（包括我最初）会顺手写成聊天的口吻，比如"帮我看看昨天的日志有没有问题"。结果就是：有时跑得很好，有时输出一大堆无关内容，有时干脆卡住不动。

原因不复杂：cron 触发的运行和对话场景有本质区别——**没有上下文、不能追问、无人值守**。它更像给一个能力很强、但不了解你项目的新同事留一张夜班交接单，而不是发一条消息。

## 做法：按"岗位说明书"结构写

我现在的模板固定六段，直接上例子：

```text
任务：每个工作日 08:30 汇总前一日网关错误日志。

步骤：
1. 读取 ~/logs/gateway-<昨日日期>.log，统计 ERROR 条目。
2. 按 module 分组，取次数前 3。
3. 结果发到「运维提醒」会话。

输出格式（不超过 10 行）：
- 日期 / ERROR 总数 / 与前日对比
- Top 3 模块及次数

异常处理：
- 日志缺失：只发一句「昨日日志缺失」，不推测原因。
- 拿不准的数据标注「数据缺失」，禁止估算。
- 本次任务只读，不修改、不删除任何文件。
```

1. **目标与产出**：一句话说清做什么、产出物是什么。
2. **输入**：明确数据源（哪个 MCP 工具、哪个路径），不让 agent 自己猜。
3. **步骤**：编号拆解，每步可验证，控制在 5 步以内。
4. **输出格式**：规定渠道、结构和行数上限，防止刷屏。
5. **异常分支**：工具失败、数据缺失时怎么办，明确"宁可报缺失，不许编"。
6. **边界**：无人值守任务默认只读，禁止写操作和反问。

写完先手动触发两三次验证，稳定了再挂调度。

## 踩坑点

- **写成对话体**。"最近的""刚才那个"在 cron 里全是悬空引用——每次运行都是全新会话，没有任何记忆。
- **没写异常分支**。MCP 工具一挂，agent 要么编数据，要么停下来反问，而没人能回答它，任务就死了。
- **时间语义两处管**。cron 表达式定了 08:30，instruction 里又写"早上八点"，时区一错就是两个时间。时间只交给 cron，instruction 里用"以系统当天日期为准"。
- **输出不设上限**。不约束格式，几次运行后消息会越来越长，渠道很快没人看了。
- **给无人值守任务写权限**。定时任务带写操作，等于半夜无人监督地改文件，出问题连第一现场都没有。
- **长任务重叠**。耗时接近触发间隔会叠跑，加一句"如发现上次运行的残留痕迹，直接退出"。

## 可复用建议

- 把"目标 → 输入 → 步骤 → 输出 → 异常 → 边界"骨架存成 snippet，新任务只填内容。
- instruction 当代码维护：改动后手动触发回归，别直接上调度。
- 一个任务只做一件事，要日报又要周报就拆成两个 cron。
- 异常处理和输出格式两段跨任务高度可复用，值得单独沉淀成片段库。

## 总结

Cron instruction 的核心不是"写得更详细"，而是换一个写作模型：它是一份给单独值夜班的实习生的岗位说明书——目标明确、步骤有限、输出有格式、异常有兜底、权限最小化。按这个结构写，任务稳定性会有立竿见影的提升。
