## 背景

AGENTS.md 是一个正在固化的社区约定：在仓库或工作区根目录放一个同名 Markdown 文件，AI agent 进入工作区时会优先读取它，作为本次任务的行为上下文。OpenClaw 的 agent 运行时遵循这一约定——根目录的 AGENTS.md 会被注入会话上下文，子目录的同名文件则按当前工作路径就近生效。

它和 README.md 的分工很清楚：README 写给人看，回答"这项目怎么跑起来"；AGENTS.md 写给 AI 看，回答"在这个工作区里干活要守什么规矩"。

## 问题

没有这份手册时，团队只能靠 prompt 反复交代，问题随之而来：

- 每次会话都要重申"测试用哪个命令、哪些目录别碰"，口口相传，成本高且容易漏；
- agent 靠猜：项目用 pnpm 它用 npm，把 `generated/` 里的生成代码当手写代码改掉，顺手 `git commit` 打乱历史；
- 换机器、换人、换模型后行为不一致，同一个任务三个人调出三种结果。

本质上，"怎么和这个代码库打交道"的经验没有沉淀成资产。

## 做法

从十几行开始，别贪多。建议按五段组织：

1. **概览**：一句话说清项目是什么、技术栈、入口在哪；
2. **命令**：构建、测试、lint 的准确命令，写成可直接复制执行的完整形态，并附期望结果（如 `pnpm test`，全绿）；
3. **约束**：明确禁区——`generated/`、`vendor/` 不要改；不要自动 commit；提交信息格式是什么；
4. **风格**：命名、错误处理、注释语言等硬约定；
5. **已知坑**：agent 实际翻过车的地方，一条一行。

写完做三件事：纳入版本控制，像代码一样 review；改构建方式时同步更新；子目录有特殊规矩，就在该子目录再放一份，只写增量。

## 踩坑点

- **写太长**。塞满项目历史和愿景，agent 抓不住重点，token 也浪费。只写"每次任务都会用到"的信息。
- **命令过期**。错命令比没有更糟，agent 会照着反复失败还以为是自己方法不对。动构建脚本时，把更新 AGENTS.md 当成同一笔变更的一部分。
- **当成 prompt 堆场**。把一次性的任务描述写进去，会污染之后所有会话。
- **嵌套文件互相矛盾**。根目录说 pnpm、子目录说 npm，agent 行为不可预测。定一个权威来源，其余位置只写差异。
- **写入敏感信息**。密钥、内网地址会被注入上下文，随任务外泄。手册里只写"去哪里取配置"，不写配置本身。

## 可复用建议

- 每条指令用"祈使句 + 可验证结果"的句式："跑 `pnpm lint`，必须零告警"，远比"注意代码质量"有效。
- 定期做冷启动测试：新开会话、清掉本地记忆，只丢一个常见任务给 agent，观察它是否按手册行事。哪里跑偏，哪里就是文档缺口。
- 把踩坑日志当反哺来源：agent 犯的每个错，修完后折算成一行写进 AGENTS.md。几个月后，手册会越来越贴近项目的真实形态。
- 团队内把 AGENTS.md 的 diff 和代码 diff 放进同一条 review 流程，避免"文档说一套、代码做一套"。

## 总结

AGENTS.md 的价值不在文件本身，而在把协作经验从聊天记录变成可版本化、可 review、可随代码一起演进的工程资产。前期投入可能只有二十分钟，换来的是 agent 更少翻车、prompt 更短、团队行为更一致。建议今天就在工作区根目录建一个，从"三条命令 + 两条禁区"起步，让下一次翻车直接变成一行新文档。
