## 背景

OpenClaw 的典型玩法是给 agent 一个工作区，加上文件读写、shell、MCP、插件等一组工具，让它在会话里自主完成构建、修改和验证。但 agent 每次冷启动时对项目一无所知：不知道这个仓库用 pnpm 还是 npm，不知道迁移脚本是生成的不能手改，不知道测试该跑哪个子集。README.md 是写给人看的入职材料，agent 并不会自动把它转成可执行的操作规则。

## 问题

没有 AGENTS.md 时，上下文只能靠两种方式补：要么每次在对话里口头交代，要么让 agent 自己探索。前者成本高且不可复现，后者容易踩雷——我见过它把 `pnpm install` 跑成 `npm ci`，把手写的 migration 覆盖掉，也在代码风格上和团队约定打架。同一个任务，不同会话产出不一致，事后排查比提前写文档贵得多。

## 做法

1. 在工作区根目录放一个 `AGENTS.md`，OpenClaw 会话启动时自动加载；子目录可以再放一份，对管辖范围内的文件生效，并覆盖根级规则。
2. 内容控制在几十行以内——它会整体进入上下文。建议结构：三到五行项目概述；命令区（构建/测试/lint 的确切命令，可复制直接执行）；目录说明（只写不明显的部分）；约定（命名、错误处理、提交粒度）；边界（明确"不许动"的清单）；以及验证标准（改动完成的判定方式）。一个最小骨架：

```markdown
# Project
内部网关服务，Go 1.22 + Postgres。

# Commands
- 测试: `go test ./internal/... -race`
- 本地构建: `make build`

# Rules
- `internal/gen/` 下全部是生成代码，禁止手改
- 涉及 SQL 的改动先跑 `make migrate-check`
- 需求不明确时先提问，不要自行假设
```

3. 持续迭代：agent 犯错后，不要只在对话里纠正，把结论沉淀成一行规则写进去，随代码一起进 git，团队里其他人的 agent 也自动受益。

## 踩坑点

- **写太长**。几百行的 AGENTS.md 会稀释关键规则，效果反而下降。它不是第二份 README。
- **规则不可执行**。"写高质量代码"等于没写，要落到可验证的命令和条件上。
- **过期信息比没有更糟**。构建方式变更时同步更新，最好作为同一个 PR 的一部分提交。
- **把密钥写进去**。文件内容会进模型上下文，敏感信息走环境变量，AGENTS.md 只指向机制。
- **和 README 抢话语权**。两份"真相"必然漂移，AGENTS.md 只保留操作性内容，其余用链接引用。

## 可复用建议

- 一条经验阈值：同一条指令在对话里重复第二次，就该进 AGENTS.md 了。
- 把每次 agent 事故当作文档 bug 处理：归因、补一行、提交。
- 软硬结合：AGENTS.md 负责表达意图，硬约束交给 CI、lint 和 hook 强制。只靠文档守不住底线，只靠闸门又缺乏弹性。
- 根级文件保持全局通用，模块差异下沉到子目录文件，注意别让两层规则互相矛盾。

## 总结

AGENTS.md 的本质，是把"老成员脑子里的隐性知识"变成 agent 可加载的显性上下文。起步投入大概十分钟，回报是跨会话、跨成员的可复现行为。它不解决所有问题，但它是工作区自动化的第一块地基——先写好手册，再谈放权。
