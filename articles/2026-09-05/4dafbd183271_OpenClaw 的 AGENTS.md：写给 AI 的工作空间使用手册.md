## 背景

AGENTS.md 是一个正在被各家 agent 工具采用的开放约定：在工作区根目录放一份 Markdown 文件，agent 启动时会优先读取它，作为对这个工作区的“入职说明”。OpenClaw 的 agent 同样遵循这一约定。可以把它理解为写给 AI 的 README——人看 README，agent 看 AGENTS.md。

## 问题

没有这份文件时，我们反复遇到三类麻烦：

- **每次会话都要重新交代**：怎么跑测试、用 npm 还是 pnpm、哪些目录是生成物不能手改，全靠在对话里重复输入；
- **行为不确定**：agent 这次跑了 lint，下次直接提交；动 lock 文件、改 build 产物，方向对但细节越界；
- **约定散落各处**：真正的规范躺在聊天记录、issue 评论和某次口头沟通里，agent 根本看不到。

本质上，这是把只存在于“人脑”里的工作区知识，换成 agent 也能稳定获取的形态。

## 做法

我们的 AGENTS.md 大约 40 行，分五段：

1. **项目概况**：两三句说清这是什么、技术栈是什么；
2. **常用命令**：构建、测试、lint，全部写成可直接执行的一行命令，注明预期耗时；
3. **目录说明与禁区**：哪些目录是生成物、哪些文件不允许 agent 修改；
4. **代码约定**：命名、错误处理、测试要求，一条一行；
5. **边界行为**：什么情况必须停下来问人，例如删除超过 20 行代码、引入新依赖。

维护方式借鉴 CI 配置：agent 犯一次错，就补一条对应规则；每次改动走 PR review，让全团队对“AI 该怎么干活”达成一致。

## 踩坑点

- **写成散文**。最早的版本有两千字的项目介绍，agent 读得慢、抓不住重点。改成短句和命令列表后效果明显更好——具体优于抽象。
- **规则冲突**。“不要动 lock 文件”和“可以升级依赖”同时存在，agent 会随机选一边，规则之间要互相校对。
- **命令过期**。一次重构后忘了更新测试命令，agent 照着跑了十分钟报错。改工作区时要同步更新这份文件。
- **写入敏感信息**。内网地址、密钥占位符都别放，它会被 agent 完整读进上下文。
- **monorepo 只放根目录**。子项目有独立约定时，在子目录再放一份，agent 通常会就近读取。

## 可复用建议

- 用“事实 + 命令 + 边界”三段式起步，先保证 20 行以内跑通，再逐步加；
- 规则尽量写成“如果遇到 X，做 Y”的条件式，agent 执行更稳定；
- 把每次踩坑的结论固化进去，它会慢慢变成团队级的 AI 协作记忆；
- 每个季度清理一次过期规则，长度失控约等于没有。

## 总结

AGENTS.md 的价值不在技巧，而在于把工程规范从口口相传变成随仓库分发。成本是一小时内写完并持续维护的小文件，收益是 agent 行为的确定性和多人协作时的一致性。如果你在用 OpenClaw 跑日常任务，建议今天就给工作区补一份最小版本——第二次会话开始，你会明显感到交代成本在下降。
