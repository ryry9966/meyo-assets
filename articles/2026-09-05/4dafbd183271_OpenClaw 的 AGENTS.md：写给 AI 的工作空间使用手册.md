## 背景

AGENTS.md 是一个约定胜于配置的机制：在 OpenClaw 工作空间根目录放一个同名 Markdown 文件，agent 每次启动会话时自动读取。它不参与解析和执行，只是纯文本上下文——相当于新人入职时拿到的“内部须知”，只不过读者是 AI。

## 问题

没有这份文件时，agent 每次都从零推断：跑测试的命令靠猜，哪些文件能碰靠试，代码风格靠从已有文件反推。于是常见一类体验：上个会话纠正过的错误，这个会话原样再犯。聊天里的口头约定救不了它——上下文截断或换会话之后就丢了。

AGENTS.md 解决的正是“人知道但 AI 不知道”这部分项目常识的固化。

## 做法

一份够用的 AGENTS.md，我们按五段组织：

1. **项目概述**：3~5 行说清仓库是干什么的、核心入口在哪；
2. **常用命令**：测试、lint、构建、本地启动的确切命令，要求可直接复制执行；
3. **约定**：命名、错误处理、日志风格；
4. **禁改区域**：生成代码、密钥目录、vendored 的第三方代码；
5. **排障指引**：测试失败先看哪份日志、哪些操作不要自作主张。

三条写法原则：

- **写操作，不写目标**。“保证代码质量”没有信息量，“提交前必须通过 pytest tests/ -x”才有。
- **保持短**。整份控制在百行以内，细节下沉到子目录的 AGENTS.md——OpenClaw 就近加载，子目录规则覆盖根目录。
- **命令必须亲手验证**。agent 会严格照做，包括照做错误的命令。

## 踩坑点

- **写太长**：几百行的规范塞进去，关键指令被稀释，不如 40 行清单管用。
- **与插件/MCP 工具描述冲突**：工具 schema 说参数这样传，AGENTS.md 说按另一种来，agent 大概率信工具——冲突根源通常是文档过期。
- **写入会变的状态**：TODO、迭代计划放进去，两周后就成了误导源。
- **混入敏感信息**：AGENTS.md 会进上下文，key、内网地址不要出现。
- **写完就不管**：它要进版本控制、走 review，否则必然腐烂。

## 可复用建议

- 用最小模板起步：概述、目录地图、命令、禁改、排障五段，20 行即可运行。
- 每次在对话里纠正 agent 后问一句：这条规则值得沉淀吗？同一个坑踩第二次，就该写进去了。
- 分清归属：跨项目的个人偏好放系统提示词，项目事实放 AGENTS.md，别互相侵占。
- 定期让 agent 自检：让它通读 AGENTS.md，标出与代码库现状不符的条目，人工确认后修订。

## 总结

AGENTS.md 的本质，是把团队经验编译成 agent 可读的形式。投入很小——一个下午加上持续的小修——换来的是 agent 行为的可预期。把它当代码维护，而不是文档，这个约定才真正立得住。
