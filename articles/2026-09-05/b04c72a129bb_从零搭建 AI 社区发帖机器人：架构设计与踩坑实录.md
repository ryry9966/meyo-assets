## 背景

社区日常运营里有一类重复劳动：整理值得讨论的 issue、搬运有价值的技术话题、在固定栏目发摘要帖。我基于 OpenClaw Agent 做了一版发帖机器人，跑了两个多星期，把架构决策和踩过的坑整理出来，供有类似需求的朋友参考。

## 问题定义

目标不是“全自动灌水”，而是：每天定时从指定信息源（GitHub issues、RSS、本地笔记）拉取素材，由 Agent 生成一篇符合社区语气的技术帖，先落草稿区，人工确认后再发布。硬约束：每天最多 2 帖、失败可重试、绝不重复发帖。

## 架构与做法

整体分四层，彼此解耦：

1. **调度层**：系统 cron 触发，每天两个时间窗，附加 0–10 分钟随机抖动。
2. **Agent 层**：OpenClaw Agent 持有系统提示词（含社区风格指南），负责素材筛选和正文生成，temperature 固定 0.3。
3. **工具层**：两个 MCP server。一个只读，负责解析 issues/RSS 并输出结构化 JSON；一个只写，对接社区 API（存草稿/发布）。
4. **状态层**：SQLite 单文件，维护状态机 `pending → generated → reviewed → published / failed`。

最关键的设计是把**生成和发布拆成两次独立调用**：生成完先落库，人审通过再触发发布。这样 LLM 挂了或 API 挂了互不拖累，也天然留出了审核窗口。

## 踩坑实录

- **重试导致重复发帖**。首次上线时发布接口超时，脚本自动重试，同一帖发了三遍。修复：发布前先生成全局唯一 `post_key` 写库，接口返回后回填状态，任何重试前先查库。
- **幻觉链接**。Agent 编造了不存在的 issue 链接。修复：要求工具层素材必须携带原始 URL，发布前校验正文中的链接是否全部在素材集合内，校验不过打回重写。
- **语气漂移**。跑一周后帖子风格开始像营销号。修复：把风格指南从描述性改成约束性——明列禁止用语（感叹号堆叠、过度承诺），并在 few-shot 里放三篇社区老帖。
- **cron 时区**。服务器是 UTC，定时全部偏移 8 小时。改为显式时区配置，不再依赖系统默认。
- **速率限制**。集中连发两条被社区反垃圾机制标记。修复：加入发布间隔下限和每日硬配额，配额写库而非写在配置文件里，防止随手改掉。

## 可复用建议

- 任何“Agent + 发布”类系统，先跑草稿模式，稳定两周再放开自动发布。
- 幂等键落库的优先级高于一切重试逻辑。
- 对 LLM 输出做结构化校验（链接、长度、禁用词），不过就重试生成，而不是靠人工兜底。
- 留一个 kill switch：一个配置项能瞬间停掉调度，比改代码重启快得多。

## 总结

这个项目核心代码约 300 行，难点不在模型，全在工程细节：幂等、校验、限速。Agent 负责“写得像人”，真正决定能不能上线的是这些无聊但关键的部分。另外，MCP 把工具层隔离得很干净——后来换发帖渠道时只改了一个 server，Agent 和状态层零改动，这是本次架构里最划算的一笔投资。
