## 背景

用 OpenClaw 一段时间后，大多数人会经历同一个阶段：接了 MCP server、加了定时任务、写了各种自定义指令，能力越来越多，直到某天发现 system prompt 已经膨胀到几万 token——模型响应变慢、注意力被稀释，改一条全局规则要在十几个地方同步。

Skills 机制就是针对这个问题设计的：把"能力"从常驻上下文里拆出来，变成按需加载的独立单元。

## 问题：常驻指令的三个代价

1. **Token 成本**：所有工具说明、操作流程全部常驻，不管本次对话是否用到；
2. **注意力稀释**：上下文越长，模型对关键指令的遵从度越差，这是实践中反复验证过的现象；
3. **维护困难**：能力之间没有隔离，一处改动容易牵连其他行为。

## Skills 的工作方式

一个 Skill 就是一个目录，核心是 `SKILL.md` 文件，分三层：

- **元数据层**：frontmatter 里的 `name` 和 `description`，会话启动时常驻注入；
- **内容层**：正文的具体操作指令，只在模型判断当前任务相关时才加载；
- **资源层**：正文引用的同目录脚本、参考文件，用到才读。

本质是三级渐进式披露——常驻的只有"索引"，正文按需进入上下文。

## 实操步骤

1. 在 `~/.openclaw/skills/<skill-name>/` 下新建 `SKILL.md`；
2. frontmatter 写 `name`（小写连字符）和 `description`；
3. `description` 按"什么场景 + 做什么"来写，包含用户可能说的触发词，例如："当需要把 B 站视频转成文字笔记时使用，覆盖下载、转录、摘要流程"；
4. 正文写操作步骤、边界条件和失败时的处理方式；
5. 重启会话或重载，用一个典型问题验证是否命中。

## 踩坑点

- **description 太泛**："处理日常事务"这类描述要么永远命中要么永远不命中，它本质是检索索引，要具体到场景和关键词；
- **多个 Skill 描述重叠**：会互相竞争，触发行为不稳定，职责必须切干净；
- **正文塞太长**：违背按需加载初衷，大段参考资料应拆到附属文件，正文只写"什么情况读哪个文件"；
- **误以为正文常驻**：Skills 加载后也未必永远留在上下文里，全局性的行为约束不要写在这里；
- **脚本路径**：相对路径以 Skill 目录为基准，写死绝对路径换机器就挂；
- **改完不生效**：已开启的旧会话不会自动刷新元数据，要新开会话验证。

## 可复用建议

- 一个 Skill 只做一件事，宁拆勿合；
- 把 `description` 当搜索引擎的摘要来打磨，这决定了命中率；
- 用 git 管理 skills 目录，行为退化时可以回溯是哪次改动引入的；
- 排查触发问题时先看加载日志，确认"没命中"还是"命中了但执行错了"，这是两类完全不同的问题。

## 总结

Skills 的价值不只是省 token，更重要的是把 prompt 工程从"一个大字符串"拆成"索引 + 按需正文"的结构。当你的 agent 能力超过一屏放不下的程度，就值得把常驻指令逐步迁移成 Skills——从最高频的能力开始，小步验证命中率，再逐步铺开。
