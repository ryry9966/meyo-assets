## 背景

跑过自动化 Agent 的人多半遇到过：任务执行到一半，MCP 工具背后的第三方 API 返回 503，或者干脆连接超时。传统服务挂了会报错、告警、人工介入；但 Agent 的麻烦在于，失败会顺着推理链继续传导——模型可能拿着错误信息继续"编"，或者陷入无意义的循环重试，token 烧了活却没干完。

这篇整理一套我们在 OpenClaw 插件里实际验证过的错误恢复做法，核心思路一句话：**不要指望 API 不挂，而是让挂掉这件事可预期、可恢复。**

## 问题：Agent 的失败模式与传统服务不同

- **失败不是终态。** 传统调用失败直接抛异常结束；Agent 却会把错误文本塞回上下文，继续推理。
- **重试会被放大。** 一个步骤重试 3 次，上层规划器可能换个措辞再触发 3 次，实际打了 9 次请求。
- **上下文会被污染。** 原始堆栈、HTML 错误页塞进窗口，既浪费 token，还会带偏后续判断。

## 做法：四层防线

**第一层：重试，但只重"该重的"。**
先分类：429、5xx、网络超时可以重试；400、401、403、404 重试无意义，直接失败。重试用指数退避加抖动（base 1s，factor 2，jitter ±30%），上限 3 次。写操作必须带幂等键，否则重试等于重复下单、重复发消息。

**第二层：超时与熔断。**
每个外部调用都要有显式超时，别用库默认值。同一个 API 连续失败达到阈值就熔断，直接走降级路径，而不是让每个 Agent 实例都去撞一遍。熔断后要有半开探测，避免服务恢复了系统还在降级。

**第三层：降级与替代路径。**
按业务定优先级：有缓存读缓存；有多供应商做 failover；实在不行，把"此工具暂不可用"作为结构化信息返回给模型，让它换工具或向人求助。Agent 的优势恰恰是能换路，前提是你明确告诉它路断了。

**第四层：断点续跑。**
长任务的中间状态落盘（数据库或文件均可），恢复时从上一个 checkpoint 继续，而不是从头再来。这决定了一次 API 故障是损失 30 秒还是损失 40 分钟。

## 踩坑点

1. **无差别重试**：见过对 401 重试 5 次直到密钥被锁的案例。先分类，再重试。
2. **把原始错误喂给模型**：截断成一两句结构化摘要（错误码、是否可重试、建议动作），堆栈留在日志里。
3. **并发重试风暴**：多个 Agent 共享同一下游时，退避必须加抖动，最好在插件层做全局并发限制。
4. **只有熔断没有恢复**：缺半开探测，故障恢复后系统长时间"假死"，比不熔断还难排查。
5. **降级路径没演练过**：failover 代码写完从没触发过，真出事才发现备用供应商早换了鉴权方式。

## 可复用建议

- 在插件层封装统一的错误分类器和重试包装器，别让每个工具各写一套。
- 幂等键用业务语义生成（任务 ID + 步骤序号），确保重试落到同一操作上。
- 给 Agent 的错误反馈定义固定 schema：`{code, retryable, hint}` 三个字段够用。
- 监控上区分"调用失败率"和"任务失败率"：前者高但后者低，说明恢复机制在真正起作用。

## 总结

API 故障不是异常，是常态。好的 Agent 错误恢复不追求"永不失败"，而是保证三件事：失败的调用快速失败，可恢复的任务有 checkpoint，不可恢复的任务能清楚告诉模型和人发生了什么。把四层防线做成插件的默认行为，而不是每次事故后的事后补救，Agent 的稳定性会有质的提升。欢迎在社区里交流你们踩过的坑。
