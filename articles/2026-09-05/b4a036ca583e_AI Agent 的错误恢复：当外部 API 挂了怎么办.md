## 背景

Agent 应用越做越“重”：一次任务里往往串着 LLM 调用、MCP 工具、第三方 API（搜索、天气、数据库、消息推送……）。链路一长，单点故障的概率就上来了。跑批任务凌晨三点因为一个搜索 API 超时导致全链路报废，这种事几乎每个做过自动化的同学都遇到过。

## 问题

很多人的第一反应是把异常堆栈原样塞回上下文，让模型“自己想办法”。实践里这通常走向两个坏结局：

1. 模型编造一个看起来合理的返回值继续往下走（最危险）；
2. 无限重试或直接放弃整个任务，烧掉 token 和配额。

核心矛盾在于：Agent 需要的是**结构化的失败信号**，而不是原始报错。

## 做法

我们在 OpenClaw 插件层统一做了四件事：

**1. 错误分类。** 把异常归为三类：瞬时错误（超时、429、5xx）、永久错误（401/403、参数错、接口下线）、业务错误（调用成功但结果为空）。只有第一类值得重试。

**2. 有界重试 + 退避。** 指数退避加随机抖动，最多 3 次，并设总超时上限，避免重试本身变成新的故障源。

**3. 工具层熔断。** 单个工具连续失败 N 次后直接短路，返回“不可用”，不再让每个任务都去撞一遍已知的坑。

**4. 结构化降级返回。** 失败时不抛异常，而是给模型返回约定好的 JSON：

```json
{
  "status": "unavailable",
  "error_type": "transient",
  "retryable": false,
  "fallback": "cache_5min_ago",
  "hint": "可使用缓存数据，或改用备选工具 web_search"
}
```

模型拿到这个信号，会自主选择：切备用 API、用旧缓存、跳过该步骤，或者明确告诉用户“这一步没做成”——而不是瞎编。

## 踩坑点

- **非幂等操作别自动重试。** 下单、发消息这类 POST，重试可能造成重复提交，必须带幂等键或人工确认。
- **退避不加抖动。** 批量任务同时重试，会把刚恢复的上游再次打挂。
- **降级信息写得太模糊。** 只返回 `error` 模型照样猜，`retryable` 和 `hint` 字段才是让模型正确决策的关键。
- **熔断粒度太粗。** 按“工具 + endpoint”维度熔断，别按整个插件，否则一个次要接口拖死全部能力。

## 可复用建议

- 在插件层统一封装一个 `safe_call` 包装器，让错误契约对所有工具生效，上层 Agent 逻辑零改动。
- 对读多写少的数据源，常备一份带时间戳的陈旧缓存。“旧数据 + 明确标注”远好于“无数据”。
- 把错误分类落日志，跑一段时间后你会知道哪个上游最不稳定、最值得加备用源。
- 任务中间状态落盘，恢复时从断点续跑，而不是从头再来。

## 总结

外部 API 挂掉不是异常路径，而是 Agent 生产环境的常态。好的错误恢复不是让模型“更聪明”，而是在工程层把失败变成模型能理解、能决策的结构化输入。分类、有界重试、熔断、结构化降级——四件事单看都不复杂，组合起来，任务成功率会有肉眼可见的提升。建议从给现有插件加一层 `safe_call` 开始，成本最低，收益最直接。
