## 背景

Agent 的能力边界，基本等于它能调到的外部服务。LLM API、搜索、数据库、MCP 工具、第三方 SaaS——链条上任何一环抖动，整个任务就可能停在半路。和确定性代码不同，Agent 循环里出错更麻烦：模型拿到一个异常后，可能陷入无意义的重试循环、直接编造结果，或者把失败当成功继续往下走。

## 问题

实际跑过长任务 Agent 的人大多遇到过这几类故障：

- API 限流（429）或临时不可用（503），短时间大量重试把配额打光；
- 没设超时，一次挂起的工具调用卡死整个循环；
- 工具报错被吞掉，模型误以为操作成功，继续执行后续步骤；
- 对非幂等接口（下单、支付、发消息）盲目重试，造成重复执行。

本质上，错误恢复是系统工程问题，不是改两句 system prompt 能解决的。

## 做法

给每个工具调用包一层标准执行器，核心四件事：

**1. 错误分类。** 把异常分成三类：可重试（429、503、超时）、不可重试（401、400、参数错误）、结果未知（请求发出但没收到响应）。第三类最危险，必须当作“状态未知”处理，而不是直接判失败。

**2. 有界重试。** 指数退避加抖动（jitter），上限 3~5 次。重试策略放在执行器里，不要交给模型自己决定——LLM 对“该重试几次”没有可靠判断，只会循环烧 token。

**3. 熔断。** 同一工具连续失败 N 次后标记为不可用，冷却期内直接走降级路径，不再打真实请求。熔断粒度按“工具”算，不按单次调用算。

**4. 显式降级。** 提前准备二级方案：备用 API、缓存数据，或者明确告诉模型“该能力当前不可用，请向用户说明并暂停该子任务”。宁可让 Agent 停下来报告，也不能让它拿空结果编故事。

另外两个必要项：所有调用设置连接和读取超时；非幂等操作带上幂等键（idempotency key）。

## 踩坑点

- **退避不加抖动**：多实例同时重试，服务恢复的瞬间被再次打挂。
- **把异常直接抛进对话**：原始堆栈既浪费上下文，也可能误导模型。应转成结构化 JSON，例如 `{"error": "rate_limited", "retry_after": 30}`。
- **降级 API 的 schema 不一致**：备用源字段含义不同，Agent 拿到的是“格式正确但语义错误”的数据，比直接失败更难排查。
- **熔断没有告警**：静默降级跑了一周没人发现，直到用户来投诉。

## 可复用建议

- 建统一错误码表（limited / unavailable / timeout / unknown / bad_request），所有工具遵守；
- 在 system prompt 里写明降级行为约定：“工具不可用时明确告知用户，禁止编造结果”；
- 每次尝试都落日志：工具名、耗时、错误类别，按失败率配告警；
- 长任务做检查点，恢复时从断点继续，而不是从头重跑。

## 总结

外部 API 挂掉不可避免，差别在于挂掉之后 Agent 的表现。核心原则三条：一切有界（重试、超时、循环都要有上限）、错误结构化、降级要显式。把这些放在执行器层而不是 prompt 层，Agent 才能从“demo 能跑”走向“生产能用”。
