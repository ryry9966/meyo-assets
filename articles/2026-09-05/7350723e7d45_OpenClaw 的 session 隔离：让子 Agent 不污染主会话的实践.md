## 背景

OpenClaw 的主会话（如 `agent:main:*` 对应的上下文）是和用户对话的唯一载体：系统提示、注入的记忆、历史消息全在这里。但很多任务天然"重上下文"——批量读文件、抓一轮网页、跑长链路自动化。这些活如果在主会话里干，工具输出会持续挤占 context window，最终触发 compaction，把真正重要的对话历史挤掉。

## 问题

我实际踩到的症状：

- 主会话自己跑一批文件处理，几轮工具调用后开始答非所问——早前的关键约束被压缩掉了；
- 大段中间日志进了主 transcript，事后回翻很难定位用户到底说过什么；
- 一次 cron 自动化跑完，主会话上下文涨一截，后续对话明显变"糊"。

根因一致：执行型任务的中间态，混进了对话型会话。

## 做法

1. **先分类任务**。需要来回确认的留在主会话；目标明确、可独立完成的，派给子 Agent。
2. **spawn 独立 session**。用 `sessions_spawn` 给子 Agent 一份自包含的任务简报（目标、输入路径、期望产物），它在全新 session 里跑，有自己的 context 文件，与主会话互不可见。
3. **收窄返回面**。子 Agent 结束后只有最终结果回传，中间 transcript 留在它自己的 session 里。我在简报里明确要求：返回结论 + 产物路径 + 异常项，控制在千字以内。
4. **按任务收权**。spawn 时限制工具白名单，比如只给读文件和执行脚本，不给发消息、改配置。爆炸半径自然小。
5. **隔离写操作**。临时产物放独立工作目录；确实要写记忆，加任务前缀当命名空间，避免跨 session 串味。
6. **管生命周期**。并发上限、超时、TTL 都配上，跑完的子 session 定期清理，别让孤儿 session 堆积占盘。

## 踩坑点

- **子 Agent 想向用户提问**：它没挂 channel，问题会直接卡住。任务简报必须写成"无需确认、按默认策略执行"，或者显式设计一条把问题路由回主会话的通路。
- **最后把整个 transcript 塞回来**：隔离做了，返回一步破功。返回内容要有硬性长度约束。
- **凭证透传过宽**：默认继承全部环境变量很方便，但违背最小权限，按任务显式声明。
- **多个子 Agent 抢同一批文件**：并发场景给每个任务独立工作目录，避免写冲突。
- **排查困难**：子 session 默认不留名，出问题翻不到。给关键任务打标签，transcript 单独归档。

## 可复用建议

- 一条判断原则：**主会话做调度和对话，子 Agent 做执行**。用这条划分任务归属，基本不会错。
- 给返回结果定预算（比如 2KB），超了让子 Agent 自己先摘要。
- 工具白名单默认最小、按需放开。
- 定期看 per-session 的 token 用量，异常膨胀基本就是隔离失效的信号。

## 总结

session 隔离不是一个开关，而是一种任务边界的划分习惯：把执行过程的脏、长、重关在子 session 里，只让结论回到主会话。配置本身不难，难的是写任务简报时就想清楚"什么该回来、什么不该"。想清楚这一点，长任务的稳定性和主会话的回复质量都会有肉眼可见的改善。
