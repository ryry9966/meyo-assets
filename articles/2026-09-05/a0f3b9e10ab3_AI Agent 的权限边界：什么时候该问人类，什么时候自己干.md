## 背景

Agent 接上 MCP 和插件之后，能做的事从"聊天"变成了"动手"：写文件、调内部 API、发消息、跑 shell。真正的问题不再是"它能不能做到"，而是"哪些事它可以自己做，哪些事必须停下来问人"。这个问题没有银弹，但可以收敛成一套可维护的策略，而不是在系统提示里写一句"请谨慎操作"。

## 问题

实际跑起来最常见的两种失败：

- **过度询问**：每一步都要确认，人变成点击机器，几轮之后开始无脑点"允许"，确认疲劳比不设确认更危险。
- **过度行动**：删数据、给真实用户发消息、改生产配置，模型在长任务里"顺手"就做了，事后只有日志里一行参数能还原现场。

## 做法

我们给每个工具打两个标签：**可逆性**和**爆炸半径**，然后落成四级：

| 级别 | 定义 | 处理方式 |
|---|---|---|
| L0 | 只读、沙箱内操作 | 直接执行 |
| L1 | 可逆写（工作区文件、新建分支、草稿） | 执行 + 留痕 |
| L2 | 难逆但影响小（发测试群消息、建 PR） | 计划确认 |
| L3 | 不可逆或高影响（删除、生产部署、对外发送、花钱） | 必须问人，带预览 |

具体步骤：

1. **盘点工具**：把 agent 可触达的 MCP tools 全部列出来，标注读写属性、目标系统、副作用范围。这张表就是权限策略的唯一事实来源。
2. **写进工具描述**：MCP tool 的 description 不只是给模型看的说明，也是策略载体。明确写出"该工具影响什么、不碰什么"，比在系统提示里喊话有效得多。
3. **工程层拦截**：L3 操作不要指望模型自觉。在工具网关或插件层加一道闸，命中 L3 就返回"需要人工确认"，让 agent 先输出结构化计划（改什么、范围、回滚方案）再放行。
4. **计划确认代替逐步确认**：允许 agent 先跑完整个只读/可逆部分，输出一份带 diff 的计划，人确认一次，而不是每个动作点一次。
5. **预算兜底**：设调用次数、耗时、金额上限，超限自动暂停并汇报，这是防止任务跑飞的最后一道保险。

## 踩坑点

- **只在 prompt 里写"危险操作请先询问"**，没有工程拦截。长任务跑几十轮后模型会漂移，自己判断"这个应该没问题"就执行了。prompt 是意愿，不是闸门。
- **工具描述含糊**：一个 delete 类工具没说清删除范围，模型在边界情况只能猜，猜错就是事故。
- **测试和生产共用一套工具**没有环境隔离，"dry-run" 直接变成了真跑。
- **权限漂移**：会话开头批准了一次"清理临时目录"，后面被推广成"清理数据目录"。高危授权应绑定到单次计划的上下文里，而不是会话级通用放行。

## 可复用建议

- 新接入工具默认 L3，观察一到两周再降级，降级动作写进变更记录。
- 确认信息要结构化：给 diff、给目标系统、给回滚方案，不要让 agent 用一句"可以继续吗"来问。
- 保留全部工具调用的参数和结果日志，定期回放，看 agent 实际怎么用权限——比开会讨论"它会不会乱来"有用得多。
- 分级表跟着工具清单一起 review，接新工具时就过一遍，别等出事再补。

## 总结

权限边界的本质不是"要不要人管"，而是**把确认次数压缩到少而关键**：可逆的事自己干并留痕，不可逆的事带着完整上下文来问。策略要落在工具分级和工程闸门上，prompt 只负责让模型理解这套规则。按这套做法落地后，agent 的确认请求通常会降到原来的十分之一左右，而真正关键的操作一次都没漏问——这就是目标状态。
