## 背景

用 OpenClaw 做日常自动化一段时间后，单 agent 的瓶颈很明显：一堆互不依赖的任务——同时整理三个数据源、给几个仓库跑检查、批量生成报告——只能一个接一个串行执行，墙钟时间全耗在排队上。OpenClaw 支持在主 agent 下挂多个 subagent，各自有独立的会话上下文和工具权限，这给并行化提供了一个干净的切口。

## 问题

但“能开多进程”不等于“适合并行”。动手前要想清楚三件事：任务之间是否真的无共享状态；每个 subagent 返回什么；失败了怎么处理。我最早一次尝试是把五个子任务直接并行丢出去，结果两个 subagent 同时改同一个仓库的工作区，git 状态直接打架，返工比串行还慢。

## 做法

我的落地步骤，供参考：

1. **拆任务，先做依赖分析。** 把主任务画成依赖图，只把“叶子级、互不写同一资源”的任务下放；有先后依赖的留在主 agent 串行。
2. **每个 subagent 一份明确的任务卡。** 输入结构化（路径、参数、约束），输出约定固定格式——我一般要求返回一段摘要加一个结果文件路径，禁止把原始日志整个塞回上下文。
3. **资源隔离。** 涉及代码的任务，每个 subagent 用独立的 worktree/分支；涉及外部 API 的，提前算好配额。
4. **限流并发。** 不是开得越多越好，我通常压在 3–4，给重试留余量。
5. **主 agent 只做聚合与校验。** 收齐结果后做一致性检查，异常的子任务单独重跑，不整批重来。

## 踩坑点

- **上下文爆炸**：subagent 把完整输出直接返回，主 agent 上下文几轮就撑爆。必须约定“摘要 + 结果落盘”。
- **隐式依赖**：两个任务看着独立，其实都要写同一份配置文件。拆分时按“写入目标”划分，而不是按业务语义。
- **失败静默**：某个 subagent 超时退出，主 agent 没感知，拿残缺结果继续聚合。每个子任务必须有超时和失败上报。
- **过度并行**：并发一高，工具端 API 限流，整体反而更慢，还污染重试逻辑。

## 可复用建议

- 把任务卡和输出格式固化成模板，存进项目约定文档，新任务套模板即可。
- 给每个 subagent 单独的日志文件，排障时按文件回放，比翻聊天记录高效得多。
- 加一个“校验型” subagent 专门复核聚合结果，成本很低，但能拦住大部分低级错误。

## 总结

Subagent 编排的价值不在“多个 AI 很酷”，而在把串行等待换成结构化并行，同时用隔离和约定把风险关进笼子。建议先从两个互不相关的只读任务试起，跑通“任务卡—聚合—校验”这条链路，再逐步放开写操作的并行。编排是工程问题，不是模型问题——约定先行，效果自然稳。
