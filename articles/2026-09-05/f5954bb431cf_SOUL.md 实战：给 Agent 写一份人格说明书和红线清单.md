## 背景

OpenClaw 的 agent 行为由 workspace 里的一组 Markdown 文件驱动：`AGENTS.md` 管流程和工具约定，`USER.md` 记用户偏好，`SOUL.md` 则回答一个更基本的问题——这个 agent 是谁。很多人装完直接跑，SOUL.md 停留在模板默认的那几句，短期看不出问题，跑久了各种不对劲就冒出来。

## 问题

没有认真写 SOUL.md 的 agent，常见三种表现：

1. **人格漂移**：上午回复严谨克制，晚上开始插科打诨，长会话里尤甚。
2. **边界模糊**：什么都接。包括未经确认的破坏性 shell 命令、替用户对外做承诺、在不确定时硬编答案。
3. **风格与场景错配**：工作群里过于随意，私人频道里又冷得像文档。

这些不是模型能力问题，是配置缺位。

## 做法

我的 SOUL.md 固定四段，总共 35 行左右：

**1. 身份定位（2-3 行）。** 一句话说清角色和立场，例如"你是一个面向个人自动化的工程助手，优先准确性，其次效率"。

**2. 沟通风格（8-10 行）。** 写可观察的行为，不写形容词。不要写"友善专业"，要写"中文回复；不确定时明确说'我不确定'；给结论前先给一句依据"。

**3. 价值排序（3-5 行）。** 明确冲突时谁让谁：安全 > 准确 > 用户情绪。这条在"用户催促 + 操作有风险"的场景里非常关键。

**4. 红线与升级规则（10-15 行）。** 用"如果 X，则 Y"句式：删除类操作先确认；涉及付款和对外通信必须有人过目；连续两次工具失败就停下来报告，而不是换个姿势硬试。

写完做两件事：用 git 管起来，每次改动留记录；准备一组边界测试 prompt（诱导执行危险命令、诱导编造事实、诱导过度承诺），改一版测一次，当回归测试用。

## 踩坑点

- **写太长。** SOUL.md 每轮都进上下文，200 行的人格说明只会稀释注意力、烧 token。35 行能说清的别写 100 行。
- **把它当安全边界。** SOUL.md 是软约束，模型可能"理解但违背"。真正的权限控制要靠 gateway 工具白名单、沙箱和 MCP 侧的 scope 收紧。SOUL.md 负责引导，配置负责兜底。
- **和 AGENTS.md 抢活。** SOUL.md 管"是谁"，AGENTS.md 管"怎么干活"。把工具使用规范塞进 SOUL.md，两边都难维护。
- **改完不重开会话。** 新会话才会加载新版，对着旧上下文测半天等于白测。
- **长会话漂移。** 跑一整天的 agent，建议在任务节点让它重读 SOUL.md，或者干脆定时重开。

## 可复用建议

- 四段骨架（身份 / 风格 / 排序 / 红线）可以直接抄，先跑通再加细节。
- 红线全部用条件句式，可测试、可审计。
- 语气分渠道：工作通道和深夜闲聊的差异用 channel 级 override 微调，SOUL.md 只保留公共人格。
- 边界测试 prompt 存成固定文件，每次改人格跑一遍，形成回归习惯。

## 总结

SOUL.md 是 OpenClaw 里性价比最高的一类配置：不写代码、十分钟起草，却直接决定 agent 长期表现的稳定性。定位要想清楚——它塑造倾向，而非提供防护；防护靠权限配置。先写 35 行，接上 git 和回归测试，比堆一篇长文有用得多。
