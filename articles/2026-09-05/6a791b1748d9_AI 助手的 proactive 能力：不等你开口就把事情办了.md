## 背景

绝大多数 agent 的使用模式是被动应答：你发消息，它回复。但真正省时间的场景往往反过来——CI 挂了你还没发现，它先说；两小时后有会，它提前把材料翻出来；磁盘快满，它直接给出清理建议。OpenClaw 这类常驻 agent 天然具备做 proactive 的条件：有心跳/定时器、有 MCP 工具能读状态、有消息通道能触达你。条件具备，但不少人的实践停在「每半小时问一次模型有什么要提醒的」，结果要么太吵，要么太贵。

## 问题

proactive 的核心矛盾不是「能不能想到」，而是「该不该开口」。把心跳 prompt 写成「看看有什么值得提醒我的」，会撞上三个典型问题：

1. **噪音**：模型倾向于说点什么，几天后你开始无视它，信噪比崩塌；
2. **成本**：心跳每轮都消耗 token，宽泛的 prompt 等于高频跑完整推理；
3. **风险**：无人值守时的主动操作，权限边界不清就是事故源头。

## 做法：检查—判断—升级 三段式

**第 1 步，明确触发源。** 定时心跳负责周期巡检，webhook/文件事件负责瞬时信号，两者分开，不要混在同一个 prompt 里。

**第 2 步，把「检查什么」写成清单，而不是开放问题。** 用 MCP 的只读工具拉状态，规则用数据表达：

```yaml
heartbeat:
  every: 30m
  checks:
    - ci_status (repo: main)
    - calendar_next_2h
    - disk_usage > 85%
  gate:
    quiet_hours: ["23:00", "08:00"]
    cooldown: 120m
    max_per_day: 5
  output: "仅当规则命中时输出，否则保持沉默"
```

**第 3 步，动作分级。** 低风险且可逆的操作（整理文件、生成日报草稿）可以自动执行并汇报；高风险动作（对外发消息、删除、付费）一律只准备草稿，等你一键确认。默认只挂只读 allowlist，写权限单独申请。

**第 4 步，留审计。** 每次主动触发记一行日志：时间、命中规则、执行动作。每周回看一次，砍掉从来没人理会的规则。

## 踩坑点

- **去重缺失**。CI 失败那条规则一口气提醒了 12 次——把状态做 hash（repo + run_id）存文件，报过就不再报，直到状态变化。
- **把工具报错当事实**。MCP 调用超时后模型脑补「服务器可能挂了」。要求它引用工具原始输出，拿不到数据一律按「无数据」处理，不触发提醒。
- **心跳 prompt 太宽**。即便写了清单，模型偶尔仍会自由发挥。在 prompt 末尾硬性要求「无规则命中就只回复静默标记」，并在解析层直接吞掉静默标记。
- **时区**。quiet_hours 写成 UTC，早上七点被吵醒。心跳运行用的本地时区要显式传入。
- **成本失控**。巡检阶段换小模型，命中规则后才升级主模型做完整推理，token 花销能降一个量级。

## 可复用建议

- **规则即配置**：checks/gate 写成 YAML 之类的数据，别埋在自然语言里，方便 review 和版本化。
- **权限单调递增**：先只读巡检两周，再开「草稿待确认」，最后才对个别低风险动作放自动执行，别跳级。
- **用信噪比衡量**：数一数每周主动消息里有多少被你真正处理了，低于一半就说明 gate 太松。

## 总结

proactive 不是把 prompt 写得更聪明，而是触发源、判断规则、克制机制三件事的工程组合。先让它学会沉默，再让它学会开口——顺序反了，你得到的就是一个没人理的告警群。
