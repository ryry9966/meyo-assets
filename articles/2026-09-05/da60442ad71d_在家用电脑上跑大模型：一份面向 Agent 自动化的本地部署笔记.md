## 背景

用 OpenClaw 跑自动化一段时间后，我的 agent 日常要处理大量重复任务：总结 RSS、归类剪贴板、批量整理文件、调几个自建 MCP 工具。这些活儿大多不复杂，但全走云端 API，一是成本在涨，二是部分内容（私人笔记、家庭照片描述、私有仓库代码）我不想出网。于是花了两个周末，把本地模型接进自动化栈，这篇记录过程和踩坑。

## 问题

家用机部署的核心矛盾只有一个：**显存（或统一内存）是硬上限**，且同时被三样东西瓜分——模型权重、KV cache、运行时开销。很多教程只说"7B 模型 8G 显存能跑"，不提 agent 场景上下文动辄上万 token，KV cache 一样吃显存。另一个问题是工具调用质量：榜单跑分不错的模型，放进 OpenClaw 连续调三五个工具，JSON 格式崩掉的概率完全是另一回事。

## 做法

1. **盘点硬件**。12GB 显存 → 14B Q4 或 8B Q8；24GB → 32B Q4 或 Qwen3-30B-A3B 这类 MoE；Mac 32GB 统一内存跑 30B 级 MoE，速度可用。
2. **选运行时**。单用户场景我直接用 Ollama：自带 OpenAI 兼容端点（`localhost:11434/v1`），量化管理省心。需要压并发吞吐再考虑 vLLM。
3. **量化 Q4_K_M 起步**，重要任务再上 Q6。Q4 与 Q8 在工具调用正确率上的差距，比聊天质量上的差距更明显，值得单独测。
4. **接入 OpenClaw**。base_url 指向本地端点即可，MCP 工具层零改动。我先接管了两个低风险插件：网页正文摘要和日志归类。
5. **回放压测**。翻出最近 20 条真实 agent 对话逐条重跑，统计工具调用成功率和平均 token 数，而不是看公共榜单。

## 踩坑点

- **上下文被悄悄截断**。Ollama 默认上下文偏小，agent 多轮之后表现为"突然失忆"，没有任何报错。务必显式调大 `num_ctx`，并把它算进显存预算。
- **显存估算漏了 KV cache**。权重刚好塞满的配置，长会话一来就 OOM，建议留 20%–30% 余量。
- **小模型 tool call 不稳**。优先选原生支持 function calling 的模型系；温度压到 0.2 以下后，格式崩坏率明显下降。
- **本地模型会自信地编造路径和命令**。涉及写文件、执行 shell 的工具，确认环节和沙箱不能省——本地跑反而更容易放松警惕。

## 可复用建议

- **分层路由**：本地承担高频低价任务（摘要、分类、格式化），复杂推理回退云端，配一个失败自动升级的开关。
- 把 `num_ctx`、温度、超时写进配置文件，别靠记性。
- 评估模型只认自己任务的回放数据，榜单只用来缩小候选范围。
- 记录每类任务本地 vs 云端的耗时与成本，两周后数据会替你做决定。

## 总结

本地部署不是替代云端，而是给自动化栈加一层便宜、离线、可控的底座。建议从一两个低风险插件场景切入，用回放数据验证工具调用成功率，再决定推广多大比例。两个周末的投入，换来的是深夜批量任务不再烧 API 费、私人数据可以不出网——这笔账，对我来说是划算的。
