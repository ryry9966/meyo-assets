# RSS + AI 摘要：一条能长期跑的信息流管线

## 背景

信息获取这块，RSS 依然是最可控的协议：拉取式、结构化、没有推荐算法插手。问题是订阅多了以后，一天几百条 item，人根本读不过来。我的做法是让 OpenClaw 的 agent 定时接管「筛选 + 摘要 + 推送」这一段，把人从流水线里挪到最后一个环节。

## 问题

直接做会遇到三件事：原始 feed 噪音大，真值得读的不到一成；LLM 调用有成本，不能什么都塞进去；摘要想长期运行，稳定性和去重比单次效果更重要。

## 做法

整条管线拆成四段，各自独立、可单独重跑：

1. **采集**：用 RSSHub / miniflux 聚合源，cron 每 30 分钟抓一次，按 guid 存入 SQLite，只让新条目往下走。
2. **过滤**：先跑规则——关键词黑名单、来源权重、标题长度，砍掉明显噪音。这步不花钱，还能省大量 token。
3. **摘要**：剩下的丢给 agent，prompt 要求结构化输出：一句话概括、3 个要点、相关度评分（0-10）。低于 6 分直接归档不推送。全文截断到前 4000 字符，对判断影响很小。
4. **推送**：过筛结果聚合成日报，走 webhook 发到 Telegram，同时落一份 markdown 到本地，方便回溯。

用 MCP 的话，RSS 抓取和 webhook 推送各封一个 tool，agent 只负责中间的判断层，职责干净。

## 踩坑点

- **feed 会静默挂掉**。有的源不报错、只是不再更新。加了「单源超过 48 小时无更新就告警」的检查才兜住这类问题。
- **去重比想象中难**。同一事件多个源的 guid 和标题都不同，只靠哈希不够。目前用标题相似度粗筛，效果一般但够用；想精细可以上 embedding，成本自己权衡。
- **结构化输出会解析失败**。模型偶尔多字段、漏字段，必须有 fallback：解析失败就降级为原文前两段直接推送，别让一条坏数据卡死队列。
- **摘要幻觉**。prompt 里明确要求「只基于原文，原文没有的信息写『无』」，并在推送里保留原文链接方便抽查。抽样核对过，加了约束后基本没有编造。
- **成本失控**。最初没做规则预过滤，一天 token 花了平时三倍。教训：越便宜的过滤越要放前面。

## 可复用建议

- 源配置全放 YAML，加源只改配置不动代码；
- 每个阶段落日志和中间产物，出问题能定位到段；
- 先跑「每日一报」验证两周，确认质量和成本后再提频；
- prompt 进版本管理，摘要风格变了能回滚。

## 总结

这套管线没用到什么新东西：RSS、cron、SQLite、一个 agent。它的价值在于把「看什么」的决定权留给人，把重复劳动交给流程。跑了一个多月，日均推送十来条，误报可控，token 成本平稳。信息工具的正确目标不是看得更多，而是更少、但更准。
