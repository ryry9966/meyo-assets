## 背景

对话式 Agent 有个结构性短板：会话之间完全失忆。系统提示词是全局共享的，内置 memory 要么黑盒不可审计，要么摘要质量不稳定。而「我是谁、环境里有什么、我希望你怎么协作」这类信息恰恰高度稳定、结构清晰，天然适合声明式维护。USER.md 的思路很简单：把这部分上下文从「模型猜」变成「你写」。

## 问题

不写 USER.md 的代价很具体：

- 每个新会话重复交代环境，重复三遍后你就懒得说了，Agent 于是按默认假设干活——给 Nix 用户推荐 Docker，给 Go 项目写 Python 脚本；
- 颗粒度不匹配，有人要结论先行，有人要看推理过程，每次都得纠正；
- 依赖内置 memory 则更糟：它记了什么、为什么这么记，你无法 review，错了也没法一键修正。

## 做法与步骤

1. 在固定路径建文件，例如 `~/.openclaw/USER.md`，放进一个独立 git 仓库管理。
2. 分区写，推荐五个固定小节：**IDENTITY**（角色与工作重心）、**STACK**（语言/工具/OS，版本号写死）、**PREFERENCES**（沟通与代码风格，写成可执行指令而非性格描述）、**CURRENT**（当前项目一句话快照，标注更新日期）、**BOUNDARIES**（红线：不自动 commit、不引新依赖、不碰某目录）。
3. 挂载：在启动引导或 system prompt 注入阶段读取该文件；走 MCP 的话包一个只读 file resource，Agent 按需取用。
4. 分层：全局 USER.md 放默认值，项目根目录的 AGENTS.md / CLAUDE.md 可覆盖它，优先级在提示词里写明，避免两边打架。
5. 维护节奏：每周固定 10 分钟过一遍 CURRENT 节，过期的删掉。

## 踩坑点

- **写太长**。超过百行就是负资产，token 翻倍且关键约束被稀释。约束宁少而硬。
- **把易变信息写死**。三个月前的「正在做 X」会让 Agent 自信地给出过时建议，比没有信息更糟——所以要标日期、定期清。
- **描述情绪而非行为**。「我很急」模型没法执行，「直接给结论，过程放折叠区」才能生效。
- **泄露敏感信息**。这份文件每次请求都会注入，API key、内网域名、真实客户名一律不写。
- **只写不更**。放 git 里，diff 能直接解释 Agent 行为为什么变了，也能逼你自己维护。

## 可复用建议

- 让 Agent 参与维护：每周末让它对照本周对话，提议对 USER.md 的增删，你人工 review 后合并。它比你更清楚哪些假设在反复出现。
- 用固定任务做回归测试：一句「帮我写个部署脚本」，看它是否还需要你补上下文——这就是 USER.md 生效与否的试金石。
- 红线单独成节并加显式标记。模型对禁止类指令的位置和密度敏感，混在散文里容易被忽略。

## 总结

USER.md 没有任何技术含量，只是把「你希望 Agent 怎么对待你」从隐式期待变成显式配置：版本化、可审计、可回滚。经验上它解决的是最高频的两类摩擦——重复交代与错误假设。先写 30 行跑一周，再决定要不要扩展，比一开始设计大而全的模板划算得多。
