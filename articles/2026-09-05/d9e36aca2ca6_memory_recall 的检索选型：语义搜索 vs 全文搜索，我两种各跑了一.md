## 背景

Agent 的 memory_recall 是回答前从记忆库捞相关记录的那一步。我的助手（基于 OpenClaw 的日常助理，挂了几个 MCP 工具）跑了几个月，记忆库攒了两千多条：会议结论、报错排查记录、配置偏好、项目决策。之前一直是最朴素的检索方案，最近专门做了一轮选型实验，语义搜索和全文搜索各跑一个月，把数据和建议记在这里。

## 问题

两种检索各有明显失效场景：

- **全文搜索**（SQLite FTS5 / BM25）对精确 token 极强：报错码、函数名、路径、配置键，搜 `ERR_CONN_RESET` 一条不漏。但换个说法就失效——库里记的是“网关超时重试三次”，用户问“那次请求卡住的事”，命中为零。
- **语义搜索**（本地 embedding + 余弦相似度）擅长同义改写，中文口语化查询表现好。但对标识符类内容很差：搜某个工单号，返回的是“语义相近”的别的工单，还偶发不相关的高分结果。

## 做法

最终落地的是混合方案，步骤可复现：

1. 记忆条目统一结构：`content` + `tags` + `timestamp`，写入时同时进 FTS 索引和向量库。
2. 全文通道：FTS5 开 trigram tokenizer（对中文必须，后面细说），BM25 排序，叠加按天衰减的时间权重。
3. 语义通道：bge-small-zh 本地跑 embedding，维度多少不重要，关键是别中途换模型。
4. 融合：RRF（k=60）合并两路排名，取 top 5 注入上下文。条目在几千量级时完全够用。
5. 建 50 条固定评测查询（改写、精确 ID、时间指代各占一部分），每次调整跑一遍，看 hit@5。

结果：纯全文 hit@5 约 78%，纯语义约 71%，混合 89%。两路各自接住了对方漏掉的那部分。

## 踩坑点

- FTS5 默认 unicode61 分词器把整段中文当一个 token，中文查询基本全空。必须换 trigram（SQLite 3.34+）或接 jieba。trigram 索引体积约为原文 3 倍，两千条无所谓，十万条要掂量。
- BM25 高频词污染：“项目”“开会”这类词在记忆库里到处都是，会拉上一堆废话。常见词过滤 + 短查询降权有改善。
- embedding 对 ID / 报错码天然弱，换模型解决不了，这类查询老实走全文通道。
- top_k 别贪大。从 8 调到 5 后回答质量反而上升——塞太多召回会稀释注意力，模型开始编造没发生过的细节。
- 写入后索引延迟：向量批量更新时刚写的记忆查不到，改成写后同步 upsert。

## 可复用建议

- **先上全文搜索作基线**，别直接跳向量。记忆库几千条以内，BM25 + trigram + 时间衰减大概率已经够。
- **评测集比直觉可靠**。拿 30~50 条真实查询（含改写）当回归测试，任何检索改动都跑一遍。
- 两路检索收敛到**一个 recall 接口**后面，留 `mode=auto|fts|vector` 参数，排查时可以强制单通道对照。
- 记录每条记忆**最后一次被召回的时间**，长期零召回的条目要么合并要么删。

## 总结

“语义 vs 全文”不是二选一，而是分层：全文保精确 token 召回，语义兜改写召回，RRF 缝合的成本很低。我的判断标准很简单——记忆里标识符多就全文优先，口语化查询多就加语义通道。两者都不贵，真正贵的是没有评测集就凭感觉调。
