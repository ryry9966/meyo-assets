## 背景

大多数 Agent 的默认工作模式是被动应答：你不发消息，它就完全静止。但真实的助理场景里，有价值的事情往往不发生在"你提问的那一刻"——早上该有份摘要、CI 挂了该有人告诉你、日程冲突该提前提醒。

OpenClaw 内置了心跳机制（heartbeat）：Agent 按固定间隔被自动唤醒一次。而 `HEARTBEAT.md` 是这个机制的用户入口——在工作区放这个文件，Agent 每次醒来会先读它，按指示做检查、跑任务、决定要不要打扰你。文件不存在或为空时，心跳基本被跳过，接近零开销。

## 问题：被动等问 vs 主动巡检

用 HEARTBEAT.md 之前，我只有两条路：要么手动问（"帮我看看 CI 红没红"），要么写 cron 脚本推通知。前者靠人记，后者没有判断力——脚本只会复读状态，做不出"这个值连续三次偏高才值得说"这种决策。

心跳补的就是中间这块：**定时唤醒 + 带上下文的判断 + 条件上报**。

## 做法与步骤

1. 确认心跳已启用。间隔默认约 30 分钟，可通过配置（如 `HEARTBEAT_INTERVAL_SECS`）调整。
2. 在 Agent 工作区创建 `HEARTBEAT.md`。
3. 用清单式写法描述任务，重点是"触发条件"和"上报规则"：

```markdown
# Heartbeat

## 每次心跳
- 检查日志目录是否有新增 ERROR，连续 2 次以上才提醒。

## 每天 09:00（仅工作日）
- 汇总：未读邮件、今日日程、assigned 给我的 open PR。
- 输出到 Telegram，控制在 10 行内。

## 静默规则
- 23:00–08:00 不发消息，除非磁盘使用率 > 90%。
```

4. 跑一两天，观察心跳日志和 token 消耗，再决定加任务还是删任务。

## 踩坑点

- **别把它当 cron 写**。这是给 LLM 看的指令，不是精确调度器。"每天 9 点"大致能做到，分钟级精度别指望；精确调度交给系统 cron 触发更稳。
- **无条件任务很烧 token**。"每次心跳都报一次天气"，30 分钟一次就是每天 48 次调用。尽量写成条件触发 + 条件上报。
- **文件本身有读取成本**。每次心跳都会把整个文件读进上下文，保持精简，删掉过时条目。
- **模糊指令会导致漂移**。"帮我盯着仓库"每次执行的理解都可能不一样。要写清看什么、阈值多少、何时上报。
- **长任务会重叠**。心跳间隔短于任务耗时会排队或重复执行，重活改由显式指令或外部调度触发。
- **警惕提醒疲劳**。跑一周后审计：哪些心跳消息你从没点开过？删掉对应任务。

## 可复用建议

- 任务分三档：**每次必查**（轻量、本地）、**条件上报**（带阈值）、**定时汇总**（每天一两次）。多数需求属于第二档。
- 上报规则固定三要素：发到哪个渠道、几行以内、什么条件才发。这三句话能解决大部分噪音。
- HEARTBEAT.md 进 git 管理，改任务走 commit，方便回溯"它当时为什么做了这件事"。
- 从一两个任务起步跑一周，看 token 账单和消息质量，再逐步加。心跳是复利型功能，前提是每条任务都配得上一次唤醒。

## 总结

HEARTBEAT.md 的价值不在"自动化"本身——cron 早就做到了——而在于把**判断力**接进了定时执行。文件很小，写法朴素，但它改变的是交互模型：Agent 从一个你问它答的工具，变成一个会自己巡检、只在必要时开口的值守角色。建议从"每天早上一条摘要"开始，跑一周你就知道它该往哪个方向长了。
