## 背景

OpenClaw 的会话大多是无状态的：每次唤醒，Agent 拿到的是系统提示词、工作区文件和检索到的记忆。记忆检索是概率性的——这次召回、下次未必。而 USER.md 是确定性的那一层：它放在工作区根目录，每次会话稳定注入上下文，内容完全由你自己维护。

说白了，AGENTS.md 告诉 Agent“这个项目怎么干活”，USER.md 告诉它“我在和谁干活”。

## 问题

没有这份文件的典型症状：

- 你是后端工程师，它反复推荐前端方案；
- 明明说过用 zsh + macOS，它每次都给 bash + Linux 命令；
- 回复风格忽长忽短，你要的“直接给结论、附一句理由”从没稳定复现；
- 时区、称呼、禁用工具，全靠每次口头重申。

单个问题都不大，但累积起来让你不停做重复校正。记忆系统能缓解一部分，但“我是谁、我怎么工作”这类高频事实，不该依赖召回运气。

## 做法

1. 在工作区根目录建 USER.md，控制在 40–60 行。它每次都占上下文，每一行都有成本。
2. 只写会改变 Agent 行为的条目，建议分四块：
   - **身份与角色**：职业、当前关注方向、技术栈；
   - **环境**：OS、shell、编辑器、主力语言与版本、时区；
   - **偏好**：回复风格（先结论后细节、中文回复、注释语言）、禁区（不用的框架、不想看的寒暄）；
   - **指针**：指向项目细节文档的路径，而不是把细节堆进来。
3. 每次发现 Agent 犯了“知道我是谁就不会犯”的错，回来加一行，最多一行。这是这个文件唯一的增长方式。
4. 放进 git。换机器、换项目，用符号链接共享同一份。

最小骨架示例：

```markdown
# USER
## 角色
后端工程师，当前主线：Agent 工具链与自动化。
## 环境
macOS 15 / zsh；主力语言 Python、Go；编辑器 Neovim；时区 UTC+8。
## 偏好
- 先给结论，再给一句理由；不要开场白。
- 代码示例默认 Go。
## 禁区
- 不用 docker-compose 命令行编排，直接说明 compose 文件写法。
```

## 踩坑点

- **写成简历**。“十年经验、负责过 XX 系统”对 Agent 没有操作意义，删掉；“回复不超过 200 字”才有。
- **信息过期**。换了技术栈不更新，Agent 会拿着旧偏好持续产出错误建议——过期的画像比没有更糟。设个季度检查的习惯。
- **指令冲突**。又写“保持简洁”又写“详细解释权衡”，Agent 会随机选一边。冲突条目合并成一句明确的话。
- **敏感信息**。USER.md 会随上下文发往模型 API，密钥、住址、手机号别放。
- **和 AGENTS.md 抢地盘**。项目约定写 AGENTS.md，个人画像写 USER.md，重复会导致行为不一致。

## 可复用建议

- **一行原则**：每条都过一遍“删掉这行，Agent 行为会变吗”的测试，通不过就删。
- **冷启动可以偷懒**：让 Agent 读你最近几百条对话替你起草 USER.md，然后手动删掉八成——它会写得太全，你要的是太准。
- **团队场景可拆变体**：按角色维护一份 ROLE.md，个人 USER.md 只留引用，避免几十个人各写一份互相漂移。

## 总结

USER.md 不是新概念，只是把 prompt 工程里最朴素的技巧产品化：用一份小而准的静态文件，兜住个性化里最确定的那部分。记忆系统负责长尾，USER.md 负责基线。花二十分钟写四十行，省下的是之后每次会话的重复校正。
