## 背景

用 OpenClaw 做自动化久了，单 Agent 的瓶颈会越来越明显：一个主会话里既要调研资料、又要写代码、还要跑验证，上下文被塞得越来越脏，任务串行执行，一个长任务卡住后面全排队。

Subagent 编排就是针对这个问题的：主 Agent 只做拆解、分发和汇总，具体执行交给多个并行的子 Agent。OpenClaw 的架构天然适合这个模式——gateway 常驻、工具经 MCP/插件接入、每个子任务可以跑在独立会话里，互不污染上下文。

## 问题

我最早的场景是批量整理本地文档：30 个 markdown 文件要各自提取摘要、分类、重命名，再汇总成一份索引。单 Agent 做这件事有三个痛点：

1. **上下文爆炸**：30 个文件的内容全灌进主会话，后面的推理质量明显下降；
2. **串行太慢**：一个文件平均 40 秒，全程 20 分钟以上；
3. **中途出错难恢复**：跑到第 17 个文件出错，之前的结果和主任务状态搅在一起。

## 做法

我的编排方式分四步，核心原则是：**主 Agent 只管调度，子 Agent 只管单一职责**。

**第一步：任务拆解要“可独立完成”。** 每个子任务必须自包含——给它文件路径、期望输出格式、产出落盘位置，不依赖其他子任务的结果。依赖关系留在主 Agent 层处理。

**第二步：收敛子 Agent 的工具权限。** 做文档整理的子 Agent 只开文件读写，不开 shell 和网络。权限越窄，跑偏概率越低，出问题也好定位。

**第三步：控制并发，结果落盘而不是回传全文。** 并发开 4 路左右（过高会撞 API 限流）。子 Agent 完成后把产物写到磁盘，只向主 Agent 回传一句结构化摘要，比如“done, 输出于 output/xx.md，分类为 tech”。这一条是最关键的，直接决定主会话上下文是否干净。

**第四步：主 Agent 做聚合与校验。** 收齐所有摘要后统一汇总、抽查产物文件、处理失败项。失败的不重跑整个批次，只单独重试那几个。

## 踩坑点

- **子 Agent 谎报完成**。它会输出“任务已完成”但实际没写文件。对策：主 Agent 收到摘要后必须抽查产物是否存在，不信自述。
- **共享文件竞态**。两个子 Agent 同时写同一个索引文件，后写的覆盖先写的。对策：每个子 Agent 写自己的独立文件，聚合阶段才合并。
- **提示词泄漏**。子 Agent 拿到主任务的大段上下文后开始“顺手”做别的事。对策：给子 Agent 的 prompt 只包含它需要的最小信息。
- **Token 成本失控**。并发 8 路 + 长上下文，一轮下来花费是串行的三倍多。对策：并发度和上下文长度都要设上限，先小批量试跑再放量。

## 可复用建议

1. 把子任务的 prompt 做成模板存成文件，主 Agent 只填变量，保证行为一致；
2. 子 Agent 一律“产物落盘 + 一句话摘要”作为返回协议；
3. 并发从 2 路起步，观察限流和成本再加；
4. 批量任务先跑 3 个样本验证全链路，再全量执行；
5. 给每个子 Agent 单独的会话目录，方便事后排查。

## 总结

Subagent 编排的价值不在“多开几个 AI”，而在**职责隔离**：主 Agent 保持干净的调度视角，子 Agent 在窄权限、窄上下文里干活。收益是速度和上下文质量，代价是必须自己搭好产物校验、竞态隔离和成本控制这三道闸。我的文档整理场景从 20 分钟降到 6 分钟，且中途出错不再需要重跑全量——这才是编排真正值钱的地方。
