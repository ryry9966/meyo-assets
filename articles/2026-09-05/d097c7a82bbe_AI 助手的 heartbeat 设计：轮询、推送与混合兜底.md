## 背景

OpenClaw 这类常驻 agent 有一个容易被忽视的基础事实：它大部分时间在"睡"。heartbeat（心跳）就是叫醒它的闹钟——agent 定期醒来，检查 HEARTBEAT.md 里的待办、扫一遍定时任务，没事就继续睡。默认半小时一次，实现简单，成本可控。

但一旦你想让 agent 对外部事件做实时反应——CI 挂了、收到邮件、传感器超阈值——就会碰到一个经典取舍：继续等下一次心跳（轮询），还是把事件推给 agent（推送）。

## 问题

两种模式各有硬伤：

- **轮询**：延迟上限等于心跳间隔，30 分钟的心跳意味着最坏情况事件要等半小时才被处理。缩短间隔则带来空转——绝大多数醒来无事可做，但每次醒来都是一次真实的模型调用，token 账单会诚实反映这一点。
- **推送**：延迟低，但要求有一条"打进来"的通道。本机部署的 agent 通常在 NAT 后面，没有公网入口；网关 webhook、消息 bot、队列消费者，每多一个组件就多一份鉴权、重试和去重的维护成本。而且推送不保证送达——网络抖一下事件就丢了，agent 甚至不知道自己错过了什么。

## 做法

我的结论是混合方案：**推送管时效，心跳兜底**。

1. **按延迟要求给事件分级**。要求分钟内响应的走推送（webhook → 本地队列 → 注入会话）；容忍小时级延迟的写进 HEARTBEAT.md，等心跳处理。
2. **推送链路保持"哑"**。webhook 只做三件事：验签、落盘、立即返回 200。不要在入口里跑 agent 逻辑，重试由发送方驱动，你的入口才永远可用。
3. **心跳瘦身**。HEARTBEAT.md 只放检查清单和待办索引，重活交给后台任务。心跳醒来先消化积压事件，没有就立刻结束——空转路径越短，省的都是真金白银。
4. **对账机制**。每个事件带单调递增序号，心跳醒来比对本地水位线，发现缺口说明推送丢了，主动拉取补齐。这就是"用推送降低延迟，用轮询保证正确性"。

## 踩坑点

- 把心跳间隔从 30 分钟压到 5 分钟，token 成本大约涨了六倍，而九成唤醒无事发生。先做事件分级，再动间隔。
- webhook 忘了验签，等于把 agent 的触发器暴露在公网上，任何能 POST 的人都能驱动它干活。
- 事件在会话运行中到达会有并发问题：两条写入路径抢同一个会话文件。加锁或统一排队，别靠运气。
- 推送重试导致重复投递是常态而非异常，去重键（事件 ID）要在入口就处理掉。
- 别在心跳里跑长任务，会阻塞下一轮心跳，表现就像 agent "假死"。

## 可复用建议

- 没有公网入口、事件频率低：纯轮询，够用，别过度设计。
- 实时性是硬需求：推送 + 持久化队列 + ack，缺一不可。
- 生产环境长期跑：一律混合。推送丢了不致命，因为心跳会对账——这是 watchdog 思路在 agent 上的直接套用。
- 空转成本还能再压：心跳先用便宜模型做分诊，判断"有没有事"，有事再切主模型。

## 总结

轮询和推送不是二选一，而是分工：推送解决"快"，轮询解决"稳"。heartbeat 的价值恰恰在于它笨——不管上游发生什么，它都会在下一拍醒来检查一遍。把实时性交给推送，把确定性留给心跳，agent 才能在成本和响应速度之间站得住。
