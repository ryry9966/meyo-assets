## 背景

编排任务跑久了基本都会遇到同一个问题：主会话越用越"糊"。委托给子 agent 的任务明明执行完了，主会话却变得迟钝、答非所问，甚至开始复读子过程中的工具输出。根因大多不是模型问题，而是 session 隔离没做干净。

## 三种典型的污染

1. **上下文污染**：子 agent 的原始 tool 输出、长日志、失败重试记录被整段拼回主会话，上下文窗口被中间产物吃掉，主任务的有效信息密度骤降。
2. **状态污染**：子 agent 直接写共享 memory、覆盖工作区文件，或改动了主会话依赖的中间结果，主流程后续步骤读到的是被动过的数据。
3. **控制流污染**：子 agent 卡死或反复重试，主会话跟着等、跟着错，一轮下来什么结论都没沉淀。

## 做法

我们的约定很简单：子 agent 是"只进不出的工人"，主会话是"唯一的协调者"。落到 OpenClaw 配置上是四步：

**1. 独立 session id。** 每个子 agent 用独立 session，transcript 单独落盘。主会话里只保留一行委托记录（谁、做什么、结果指针），不保留过程。

**2. 定义返回契约。** 子 agent 结束时只回传结构化摘要：结论、关键数据、产出文件路径、失败原因（如有）。字段固定，长度限死。原始工具输出留在子会话里，主会话需要追溯时按指针去查。

**3. 收敛权限与工作区。** 工具白名单按任务最小化；文件读写限定在子目录（如 `workspace/tasks/<task_id>/`），对共享 memory 只追加不覆盖，或只写 staging 区，由主会话审核后合并。

**4. 设上限和失败语义。** 轮次 / token 上限、超时、失败即终止且不回写任何东西——宁可让主会话收到一句"任务失败，原因 X"，也不要收到半成品。

## 踩坑点

- 最初图省事把子 agent 的完整 transcript 拼回主上下文，两三个子任务之后主会话就开始丢主线。务必用摘要替换，不要拼接。
- 子 agent 和主会话共用 session 文件，断点恢复时回放顺序错乱，排查了很久才定位。session 必须物理分离，别共用一个文件。
- 并发子 agent 写同一个汇总文件，偶发互相覆盖。现在每个子 agent 只写自己的目录，合并动作只由主会话执行。
- 子 agent 的系统提示里没写"你不与用户对话"，它自作主张输出了面向用户的话术，被原样回传。角色边界要显式声明，别默认模型能猜到。

## 可复用建议

- 把返回契约做成固定模板（JSON schema 或固定段落结构），所有子 agent 通用，减少每次编排的临场发挥。
- 目录即隔离：约定 `workspace/{main, tasks/<id>}/` 结构，配合主会话的合并动作，比一套复杂权限系统更耐维护。
- 子会话日志按 task_id 归档，不要删。审计和复现问题全靠它。
- 在主会话侧加一个简单的"回传体积"监控，子 agent 摘要一旦超过阈值就告警，通常是契约被执行歪了。

## 总结

session 隔离的本质不是"藏起来不让主会话看见"，而是控制信息进入主会话的口径：**只进结论，不进过程；只进审核过的状态，不进原始操作。** 做到这一点，编排规模上去之后主会话依然稳定。以上做法我们已在多个长任务里验证过，欢迎回帖交流你们的隔离方案。
