## 背景

OpenClaw 的定时任务本质上是一次**无人值守的 agent 运行**：到点触发，模型带着你写的那段 instruction 冷启动，执行完把结果送到指定渠道。我目前在生产环境跑了四五个这样的任务——每日早报、服务器巡检、RSS 摘要、每周周报。跑了一两个月回头看，这些 instruction 被改的次数远超预期。根本原因想明白后很简单：**定时任务的 prompt 和对话 prompt 是两种东西**。

## 问题出在哪

对话场景里用户在线，模型理解偏了可以追问；cron 任务没有这个条件。常见的失败模式：

- **上下文真空**："帮我总结一下今天的消息"——什么叫今天？以哪个时区为准？模型只能猜。
- **结果无处落地**：任务跑完了，结论留在会话里，你根本没看到。
- **工具路径不明**：该走 MCP、插件还是本地脚本？模型自由发挥，每次跑法还不一样。
- **失败静默**：数据源挂了，模型就"编"一份看起来合理的摘要发出来，比不发更糟。

## 我的写法：按任务说明书来写

现在每条 cron instruction 都按这个骨架写：

```text
【任务】每天 08:00 生成本日待办摘要。
【时间锚点】以你当前的系统时间和时区为准，统计截至此刻的待办。
【数据来源】仅使用 memory/todo.md 和 calendar MCP 工具，不要访问其他渠道。
【输出】整理为不超过 10 条的列表，按优先级排序，通过 Telegram 发给 owner。
【兜底】任一数据源拉取失败时，不要推测内容，直接发送一条失败原因通知。
【静默规则】若无待办事项，不发送任何消息。
```

对应五个要点：

1. **自我包含**。假设模型对"之前聊过什么"一无所知，所有背景写进 instruction。
2. **显式时间锚点**。永远写"以当前系统时间/时区为准"，不要依赖模型自己对"今天""昨天"的理解。
3. **锁定工具路径**。点名用哪个 MCP / skill / 文件，并禁止绕路。否则模型每次选路不同，结果不可复现。
4. **定义输出契约**。发到哪个渠道、什么格式、多长上限，一次说清。
5. **写清兜底与静默**。失败时做什么，无事发生时做不做什么。这条最容易被忽略。

## 踩坑点

- **相对时间歧义**。最早写"总结昨天的群消息"，服务器在 UTC，我按东八区理解，统计窗口错位 8 小时。显式声明时区后解决。
- **instruction 里塞大段静态上下文**。曾把项目背景整段贴进去，每次触发都烧 token。改成背景写进文件，instruction 里只给路径。
- **高频任务没有静默规则**。巡检任务每 30 分钟跑一次，没事也发"一切正常"，一晚上 16 条消息。加上"仅异常时发送"之后才可用。
- **结果不可复现**。同一条 instruction 两次跑出不同结构，排查发现是没锁定工具，模型有时走 MCP 有时走内置搜索。点名工具后稳定。

## 可复用建议

- 把 cron instruction 当成**给夜班值班的交接文档**来写，而不是聊天消息。
- 沉淀个人模板：任务 / 时间锚点 / 数据来源 / 输出契约 / 兜底 / 静默，六段式。
- 新任务先低频试跑（如每天一次），观察三五天再调频率。
- instruction 存档进 git——它和代码一样需要版本管理与变更追溯。

## 总结

Cron 任务 instruction 的质量，决定了无人值守自动化的上限。核心就一句话：**假设执行者对上下文一无所知，而且你不在线**。把时间、工具、输出、兜底全部显式化，定时任务才能从"碰运气"变成"可交付"。
