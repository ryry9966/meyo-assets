## 背景

OpenClaw 里跑多步任务时，主会话很容易变成"杂物间"：子任务的中间推理、MCP 工具返回的大段 JSON、失败重试的报错栈，全堆在同一个 context 里。跑几轮之后主会话开始"失忆"、成本飙升，模型还会引用早已过期的中间状态。

我们在一条自动化流水线（抓取 → 清洗 → 汇总）里做了子 Agent 隔离改造，主会话 token 消耗降了一个量级，行为也稳定多了。这篇记录做法和坑。

## 问题：污染从哪来

三类典型污染源：

1. **工具输出直写主 context**。子任务调用 MCP 工具，返回值默认进入当前会话，几 KB 的 JSON 就够挤掉关键指令。
2. **子 Agent 的思考过程留在主会话**。主模型看到的"历史"混入了子任务细节，后续决策被带偏。
3. **副作用共享**。两个子 Agent 写同一个工作目录，或共用一个有状态 MCP server，状态互相覆盖。

## 做法

核心原则：**子会话是廉价的，主会话是珍贵的；边界处只传结构化摘要。**

1. **隔离运行**。子 Agent 用独立 session 启动（`isolated_session: true`），有自己的 context 窗口和工具白名单。
2. **显式输入契约**。启动时只传任务描述 + 必要的最小上下文快照，不要把整个历史塞过去。
3. **显式输出契约**。子 Agent 返回固定 schema 的 JSON 摘要；大产物落盘，主会话只拿文件路径引用。
4. **限预算**。子会话设 max turns 和超时，防止重试循环打爆自己的 context。
5. **独立留存**。子 session 日志单独存，主链路出问题时可回放定位，但不进主 context。

## 踩坑点

- **隔太狠**。子 Agent 拿不到关键背景，产出跑偏。经验是传"结论级摘要"——别传原始历史，也别传空白。
- **返回值又大又长**。隔离白做了。给输出加长度上限，超限时先在子会话内做一轮自摘要再返回。
- **有状态 MCP server 是暗通道**。session 隔离不等于状态隔离，共享 server 连接要确认无会话内缓存，必要时每个子 Agent 独立实例。
- **共享工作目录冲突**。给每个子 Agent 独立子目录，汇总阶段统一合并。
- **调试期别急着清子 session**。保留期设长一点（比如 24h），排障全靠它。

## 可复用建议

- 给每类子 Agent 写一页"契约文档"：输入字段、输出 schema、工具白名单、预算。新任务直接套模板。
- 主会话对子 Agent 的感知收敛为三件事：任务 ID、状态、结果引用。其他一律不可见。
- 隔离前后各测一轮 tokens/任务和任务成功率，用数字说话。
- 子 Agent 产出质量差时，先检查输入契约是否缺上下文，再动模型参数。

## 总结

Session 隔离的本质不是"多开几个会话"，而是在边界处建立显式契约：输入给快照，输出给摘要，副作用走文件系统引用。做到这三点，主会话就能长期只装"决策需要的东西"，多 Agent 流水线才跑得久。
