## 背景

日常开发里有一块不起眼但持续的成本：写提交信息、拆分提交、清理过期分支、整理 PR 描述。这些事机械重复，但做不好会污染提交历史。AI 助手通过 MCP 接入本地工具之后，"让 agent 直接操作 Git" 从想法变成了可以落地的实践。这套流程我们在 OpenClaw 工作流里跑了几个月，把踩过的坑和最终形态整理如下。

## 问题

直接把 Git 交给 agent，会遇到三类麻烦：

1. **提交信息质量不可控**。模型若凭"记忆"而不是真实 diff 写信息，会出现文不对题。
2. **危险操作不可逆**。force push、amend 已推送分支、直接往 main 提交，一旦发生很难收拾。
3. **提交内容越界**。`git add -A` 会把 `.env`、构建产物一并带上，agent 不会替你把关。

## 做法

方案分三层：

**1. 用 MCP Git 工具替代裸 shell。** 接入 mcp-server-git 这类只暴露细粒度操作（status / diff / add / commit / branch）的服务端，agent 拿不到高危入口。这是最小权限原则，比在提示词里写"请不要 force push"可靠得多。

**2. 把约定写进仓库。** 在 `AGENTS.md`（或等价的 agent 指令文件）里固化：Conventional Commits 格式、分支命名规则（`feat/xxx`、`fix/xxx`）、禁止事项（不 amend 已推送提交、不用 `--no-verify`）。任何 agent 进来先读这份文件，输出风格自然统一。

**3. 人审确认，只审一次。** 流程固定为：agent 读 diff → 生成提交信息和涉及文件清单 → 人确认 → 执行提交。分支清理同理：agent 列出"已合并且超过 14 天未活动"的候选分支，人确认后批量删除。所有改历史的操作（rebase、合并、发布）始终不进自动化。

## 踩坑点

- **信息与 diff 脱节**：最初把需求描述直接喂给 agent 让它写信息，结果和实际改动对不上。必须基于真实 diff 写，改动复杂时先让它复述一遍再落笔。
- **自提交循环**：agent 改完代码会顺手把中间态 commit 掉，历史很快变脏。约定里明确"只提交用户确认的内容"。
- **大 diff 撑爆上下文**：几百行以上的改动，先读 `git diff --stat` 挑重点文件，分批处理。
- **pre-commit hook 失败后的重试死循环**：agent 会反复 commit。约定失败一次就停下交给人。
- **secrets 风险**：即使有 `.gitignore`，也建议在 MCP 层加一份文件黑名单（`*.env`、`*.pem`），双保险。

## 可复用建议

- 约定文件放仓库里而不是 agent 配置里，跟着代码走，团队共享。
- 所有写操作走"生成 → 展示 → 确认 → 执行"四步，没有例外。
- 权限分级：读操作随意，写操作确认，历史操作禁用。
- 保留 shell 审计日志，出问题能回放 agent 做过什么。

## 总结

AI 管 Git 的正确分工是：agent 处理信息密度高的机械劳动——读 diff、写信息、找过期分支；人保留对历史的否决权。前期花半天把约定文件和权限边界搭好，后面几个月的收益是持续的：提交历史可读了，分支不再堆积，而且至今没有出过一次需要回滚的事故。自动化不必一步到位，从"只让 agent 写提交信息"开始，跑顺了再扩。
