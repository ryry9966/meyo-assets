## 背景

MCP（Model Context Protocol）是 Anthropic 在 2024 年底开源的一套协议，目标很朴素：给"模型"和"工具/数据"之间定一个标准接口。可以类比成 AI 时代的 LSP——编辑器和语言实现各自只对接协议，不需要两两适配。

## 它到底解决什么问题

在 MCP 之前，Agent 接工具是纯手工活：

- 写一个 Agent，接数据库要写一遍工具函数，接 GitHub 又写一遍；
- 换一个模型或框架，工具层代码全部重写；
- N 个应用 × M 个工具 = N×M 套胶水代码。

MCP 把乘法变成加法：工具方实现一次 MCP Server，任何支持 MCP 的 Host（Claude Desktop、OpenClaw 等）都能直接用；反过来 Host 侧也只需实现一次 Client。协议基于 JSON-RPC 2.0，传输层主流两种：stdio（本地子进程）和 Streamable HTTP（远程服务）。

对开发者来说，真正需要理解的只有三个概念：

- **Tools**：模型可主动调用的动作（查询、写入、执行）；
- **Resources**：由应用侧控制的上下文数据，模型只读；
- **Prompts**：面向用户触发的模板。

90% 的场景你只需要 Tools。

## 动手路径（以最小可用为准）

1. **选 SDK**：官方有 Python 和 TypeScript SDK，`pip install mcp` 或 `npx @modelcontextprotocol/sdk`。
2. **写一个只含一个 tool 的 server**：比如"列出某目录下的文件"，函数签名 + docstring 就是给模型看的接口说明。
3. **用 MCP Inspector 本地验证**：`npx @modelcontextprotocol/inspector`，先在 Inspector 里手动调用成功，再接 Host。
4. **接入 Host**：在 OpenClaw 的 MCP 配置里声明 server 启动命令与参数（stdio 模式）；远程服务则填 URL。
5. **观察真实调用**：让模型完成一个任务，看它是否选对工具、传参是否合理，再迭代描述文案。

## 踩坑点

- **工具描述就是 API 文档。** 模型靠 description 和参数 schema 决定用不用这个工具。我们踩过最大的坑是工具名太泛（如 `search`），改成 `search_orders_by_date` 后调用准确率明显上升。
- **返回值会吃掉上下文。** 一个接口返回 10MB JSON，模型直接被撑爆。在 server 层就做过滤、分页、截断，只返回模型需要的字段。
- **stdio server 崩了整个会话挂掉。** 未捕获异常必须兜底，返回结构化错误给模型，而不是让它看到一堆堆栈。
- **写操作要有确认机制。** 涉及删除、发送、支付这类副作用工具，要么设计成"先预览再执行"两步，要么在 Host 层开人工确认。
- **传输协议有版本坑。** 早期教程里的 SSE 传输已被 Streamable HTTP 取代，跑不通时先查 SDK changelog。

## 可复用建议

- 一个 Server 只管一个领域，工具数量个位数起步，够用再加；
- 错误信息写给模型看：说清"错在哪、该改什么参数"，比堆栈有用得多；
- 把工具 schema 当合同维护，改字段名前先想下游模型的调用习惯；
- 所有写操作尽量幂等——Agent 重试是常态，不是异常；
- 优先复用社区现成 Server（文件系统、数据库、浏览器），自己只写业务独有的部分。

## 总结

MCP 不是什么智能层面的突破，它解决的是工程问题：把 Agent 生态里最脏的胶水层标准化。它的价值随 Host 和 Server 数量增长而复利——你今天写的一个 server，明天可能在所有支持 MCP 的客户端里都能跑。如果你在维护多个 Agent 或多个内部工具，值得花一个下午把第一个最小 server 跑通。
