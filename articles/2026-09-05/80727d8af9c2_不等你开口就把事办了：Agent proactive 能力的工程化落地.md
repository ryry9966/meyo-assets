# 背景

现在多数 Agent 的交互模型仍是"你问我答"：用户发消息，模型响应，会话结束。但很多高价值任务天然不是用户发起的——晨报该在八点生成、监控指标越线该立刻汇报、收件箱出现特定邮件该提醒。这类事全等人开口，Agent 就只是个高级搜索框。

随着定时调度、Webhook、文件监听等触发手段和 MCP 工具生态成熟，让 Agent 主动干活在工程上已经可行。问题不在能不能做，而在怎么做才不会变成噪音机器。

# 问题

把 proactive 做砸的方式非常一致：Agent 每十分钟扫一次状态，有点动静就发消息，用户三天后直接关掉通知。核心矛盾是——主动触发的成本由用户承担（被打断），收益却不确定。所以工程上的关键是加一层"该不该开口"的评估，而不是把触发器直接怼到发消息上。

# 做法

我们在 OpenClaw 插件侧把触发链路拆成四段：

1. **触发源**。三类够用：定时（cron）、事件（Webhook / 文件变更 / 邮件到达）、状态（阈值判断，如"磁盘超 90%"）。所有触发源统一收敛进一个事件队列，Agent 只消费队列。
2. **评估门**。事件进来先跑一次轻量判断：值不值得打断用户？依据写进 prompt：重要性、时效性、是否与近期动作重复、是否在免打扰时段。不达标就静默记日志。
3. **上下文重建**。评估通过后**重新拉取**当前状态再执行，不要用触发时缓存的旧数据——数据可能早变了。
4. **分级执行**。只读操作（汇总、提醒）直接做；写操作（替用户发消息、改配置、调外部 API）默认降级为"给出建议 + 请求确认"，只有白名单里的低风险动作才自动执行。

外加两条硬规则：每次主动动作记审计日志（触发源、评估结论、执行结果）；每个动作带幂等键，防同一事件重复触发。

# 踩坑点

- **自激循环**。最阴险的坑：Agent 的写操作本身又产生新事件，再次触发自己。我们踩过一次——自动回复的邮件又进了被监听的收件箱。解法是给自动产物打标记、触发源过滤自家输出，再配全局频率上限兜底。
- **上下文过期**。凌晨拉的状态，早上执行时早已失效。评估和执行之间必须重新取证。
- **时区与漂移**。cron 默认服务器时区，用户在另一时区，"早上八点"会变成下午四点。调度时间统一按用户时区存储和计算。
- **成本失控**。高频轮询每次都过模型评估，账单很难看。阈值类判断用规则前置过滤，只有模糊事件才交给模型。

# 可复用建议

- 第一版只做只读主动：只汇报、不动手，跑两周看信噪比，再考虑放开写权限。
- 给用户设"打断预算"，如每天最多 3 次主动消息，超出就合并成一条摘要。
- 每条主动消息自带三要素：为什么是现在、证据是什么、给几个可选项。缺一条就别发。
- 触发器做成声明式配置而非硬编码，用户可自行增删、调阈值。
- 留负反馈入口：用户点一次"这条没用"，就下调对应触发源权重。

# 总结

Proactive 能力的本质不是模型更聪明，而是**触发设计 + 评估门 + 权限分级**的工程组合。先只读后写入，先低频后加密，每层都有日志和熔断。做对了，Agent 是助手；做错了，它就是最大的噪音源。
