## 背景

用 OpenClaw 挂一个定时 Agent 往社区发日报、变更摘要或话题整理，是很多团队的常规玩法。实现本身不难：cron 触发 → MCP 拉数据 → LLM 生成 → 调发帖 API。难的是发出去之后，频道里的人一眼认出"这是机器人"，互动寥寥，甚至被管理员限制。

## 问题：机器人味从哪来

复盘我们早期被吐槽的几次发帖，"机器人感"基本来自三点：

1. **时间太准**。每天 9:00:00 整发出，误差不超过一秒。
2. **结构太稳**。标题格式、段落顺序、结尾签名每篇一样。
3. **不看现场**。频道里正吵得热烈，机器人硬插一篇官方腔日报。

本质都是确定性：调度确定、模板确定、行为对上下文零响应。

## 做法

**第一步：调度层加抖动。** 不要裸用 `0 9 * * *`，改成在时间窗内随机取点。我们用两段随机：先在 9:00–11:00 内抽小时偏移，再抽分钟偏移，避免总落在窗口头部。同时加 5% 概率直接跳过当天——真人也有不发帖的日子。

**第二步：内容层去模板化。** 同一份数据准备 3–4 种结构变体，prompt 里显式要求换开头方式和段落组织，去掉固定结尾语。注意：只换 emoji 不算变体。

**第三步：发布前上下文检查。** 发帖前先查频道最近 30 分钟活跃度：正在热聊就延迟 20–40 分钟，或改为以回复形式挂到当前讨论下；若与刚才某条消息内容高度重合，降级为一句简短补充。

**第四步：频率硬约束。** 单频道每日上限、两帖最小间隔、夜间静默时段。这些是硬规则，不参与随机。

这套逻辑我们抽成了独立的 MCP tool，配置大致是：

```yaml
window: "09:00-11:00"
skip_probability: 0.05
min_gap_minutes: 90
daily_cap: 2
quiet_hours: "01:00-07:30"
context_check: true
```

## 踩坑点

- **均匀随机也可疑**。永远落在 9–11 点本身就是模式。解法是每两周重抽窗口，偶尔挪到下午。
- **重试导致双发**。抖动在调度层，但发帖失败重试没做幂等，出现过同内容隔两分钟发两次。发帖前先查近期相似度。
- **时区**。服务器 UTC、社区 UTC+8，静默时段一开始全错位。
- **抖动救不了频率**。一天八条，节奏再自然也是刷屏。先降频，再谈节奏。

## 可复用建议

- 把"什么时候发"和"发什么"拆成两个独立决策，调度器只管时间。
- 上线初期压低频率观察两周，比全速上线再回退安全得多。
- 每周导出实际发布时间序列看一眼，肉眼能看出规律，就说明还不够散。
- 上下文检查比内容生成更值得花 token——它决定这条帖子会不会被当噪音。

## 总结

不像机器人的关键，不是把自动化藏起来，而是把确定性换成受约束的随机，并让 Agent 对社区现场有基本感知。时间抖动、结构变体、上下文检查、频率硬顶，四件事成本都不高，叠起来效果明显。自动化负责省人力，节奏控制负责让省下来的人力真的换来互动。
