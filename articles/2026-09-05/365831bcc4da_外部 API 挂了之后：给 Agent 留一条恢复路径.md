## 背景

跑长任务的 Agent，链路里少则一个 LLM API，多则串着搜索、数据库、各类 MCP 工具和内部服务。demo 阶段一切正常，一旦进真实环境，最常见的事故往往不是模型答错，而是某个外部依赖中途 503 或超时——整个多步任务直接断掉，前面十几轮工具调用的结果全部作废。

## 问题

多数框架的默认行为是“调用失败就抛异常”，Agent 把异常一路往上抛，任务终止。更麻烦的是三种放大效应：

1. **重试风暴**：多个并发实例同时重试，把半死的服务彻底打挂；
2. **重复副作用**：非幂等操作（写库、下单、发消息）重试后被执行了两次；
3. **状态丢失**：中间结果没有持久化，恢复只能从头跑，成本和风险都翻倍。

## 做法

按四层处理，从便宜到贵：

**1. 先分类错误。** 可重试：网络超时、429、5xx；不可重试：400/401/403、参数校验失败、业务逻辑错误。分类错了，后面全白做——把 401 重试十次只会更糟。

**2. 重试加退避和抖动。** 指数退避（如 1s→2s→4s，封顶 30s），叠加随机 jitter 避免所有实例齐步走。最多 3~5 次，之后升级处理，不要死磕。

**3. 断路器 + 降级。** 连续 N 次失败就熔断一段时间，期间直接走降级路径：备用 provider、缓存结果，或者明确报告“该工具暂不可用，任务暂停在第 X 步”。宁可诚实地失败，也不要拿过期缓存伪装成功。

**4. 检查点与幂等。** 每完成一步就把结构化状态落盘：已完成步骤、中间结果、下一步计划。恢复时从检查点续跑，而不是重放全部。所有写操作带幂等键，让服务端按键去重。

在 MCP/插件场景，这套逻辑应该做在客户端的统一封装层，而不是指望每个工具服务自己处理好。

## 踩坑点

- `catch` 了所有异常然后无脑重试，401 重试十次还触发了对方风控；
- 长时间的 LLM 调用没设超时，一个挂起的请求把整个任务卡死；
- 检查点里存了 session token 或已过期的上下文，恢复后照样报错；
- 熔断阈值太敏感，服务一抖就熔断、一恢复就放量，来回震荡；
- 状态只存单机内存，进程一重启全部归零；
- 重试时没带幂等键，服务端写入了重复记录。

## 可复用建议

- 把所有外部调用收口到统一的 tool-call 层，超时、重试、熔断、结构化日志只写一次；
- 错误用结构化对象表达（类型、是否可重试、建议动作），不要裸抛字符串；
- 定期做故障演练：用 mock 直接返回 503 或超时，验证恢复路径真的能走通；
- 给用户（或上游 Agent）明确的状态输出：卡在哪一步、为什么、下一步会怎样。

## 总结

错误恢复不是让 Agent 永远不出错，而是把“出错”当成一条被设计过的正常路径。分类、退避、熔断、检查点这四件事做扎实，外部 API 挂掉时，你的 Agent 是从第 7 步续跑，而不是从第 0 步重来——这就是可用性差距的真实来源。
