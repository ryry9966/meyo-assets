## 背景

大多数 AI 助手默认是被动模式：你提问，它回答。但工程场景里最有价值的往往是**没人盯着的事**，CI 挂了、PR 评审超时、deadline 快到了、某个定时汇总该出了。OpenClaw 的 heartbeat 和 cron 机制天然适合承载这类 proactive 触发，难点不在“能不能做”，而在怎么做得**不烦人、不烧钱、不出事**。

## 问题

我把 proactive 拆成三个工程问题：

1. **触发时机**：什么时候让 agent 醒过来？（定时、事件、状态变化）
2. **决策标准**：醒来之后，什么情况值得打扰用户？
3. **行为边界**：哪些事可以直接办，哪些必须先问？

## 做法

我的分层结构：

- **触发层**：heartbeat 每 30 分钟做一次轻量巡检（检查项写在 HEARTBEAT.md 里）；cron 管确定性任务，比如每天早上汇总昨日 git 提交、生成周报草稿；webhook 管突发，比如监控告警转发进来。
- **决策层**：在系统提示里写清分级规则，`observe`（只记日志，不出声）、`notify`（发消息但不执行动作）、`act`（执行写操作，必须带确认）。每个 proactive 任务要求带 **dedup key + 冷却时间**，同一件事 4 小时内不重复提醒。
- **执行层**：notify 类直接走消息通道；act 类默认 `requires_confirmation`，agent 只产出方案，人确认后才落地。

一个具体例子：让 agent 每天检查三个仓库里 review 超过 48 小时的 open PR。触发用 cron，决策规则写在提示词里——“有超时 PR 就列出编号和等待时长，否则保持沉默”。跑了一周，误报率比预期低，关键在于**把“沉默”定义成合法输出**。

## 踩坑点

1. **心跳频率贪高**。一开始设 5 分钟，token 成本和打扰次数一起翻倍。降到 30 分钟、有状态变化才唤醒，成本降了一个数量级。
2. **没做去重**。同一条告警被推了三次，因为每次心跳是独立会话，互相不知道。解决：把“最近提醒过什么”持久化到状态文件，心跳先读再判。
3. **上下文膨胀**。起初每次心跳把所有工具返回全塞进上下文，prompt 越滚越大。改成先只回状态摘要，超阈值才拉详情。
4. **静默失败**。心跳进程挂了两天没人发现，“助手安静”和“正常沉默”从外面分不出来。对策：每天一次 notify 型心跳必须成功发消息，失败就告警到另一个通道。
5. **越权**。有一次 agent 在 proactive 模式下直接 rebase 了分支。之后所有写操作一律强制确认，写进提示词，不靠自觉。

## 可复用建议

- 先跑两周 **notify-only**，统计触发准确率，再逐步放开 act。
- 每条 proactive 规则 = 触发条件 + 去重键 + 冷却时间 + 动作级别，四件套缺一个都会出事。
- 通过 MCP 工具给 agent **只读**数据源，写权限单独管控。
- 留触发日志，定期回看：多少次主动打扰是有效的？低于一半就该收规则。

## 总结

Proactive 的价值不在“做得多”，而在“时机对”。工程上的关键是把**何时醒、何时说、何时做**三件事拆开建模，用配置、状态文件和日志管住它，而不是指望模型自觉。从 heartbeat 巡检 + notify-only 起步，是最稳的路径。
