## 背景

团队日报这件事，写的人烦，看的人也烦。信息其实都在：git 提交、CI 流水线、告警事件、工单流转，但散落在四五个系统里，靠人手工汇总，一来耗时，二来遗漏。我们的目标是让 OpenClaw 每天定时产出一份"有据可查"的日报——不是让模型自由发挥，而是让它基于结构化数据做组织与转述。

## 问题

直接把原始日志丢给 Agent 生成日报，会踩三个坑：一是日志量大、噪音多，token 轻易爆掉；二是模型面对非结构化文本容易脑补，产出"看起来专业但查无实据"的句子；三是格式不稳定，今天表格明天列点，下游阅读体验差。结论很明确：**采集和压缩必须发生在 Agent 之外，模型只负责最后的"写"。**

## 做法：五步流水线

整条链路由 cron + 脚本 + OpenClaw 定时任务串起来：

1. **采集层**。三组脚本分别拉取过去 24h 的 git commit（含作者、仓库、PR 链接）、CI 失败记录、告警与工单状态变化。各自输出 JSON，先落盘，不直接进模型。
2. **归一化**。统一成一条 schema：`{timestamp, source, actor, action, severity, meta}`。时区统一 UTC+8，时间戳统一 ISO 格式。
3. **聚合与切片**。按仓库/服务分组，同类事件合并计数（"重构分支提交 23 次"，而不是 23 条记录）。每组限制条数，超限只保留 severity 高的。
4. **Agent 撰写**。OpenClaw 定时任务读入聚合后的 JSON，system prompt 里硬性约束：只允许转述输入数据中出现的事实，禁止推测原因；输出固定 Markdown 模板（概览 / 变更明细 / 风险项 / 待跟进）。MCP 工具只开一个只读文件接口，不给联网。
5. **投递与归档**。渲染结果经 webhook 推送到群，同时把"输入 JSON + 输出报告"一起归档到按日期命名的目录，方便回溯。

## 踩坑点

- **时区**。日志源有 UTC 也有本地时间，第一版把凌晨的告警算到了前一天，改成入口处统一转换才稳。
- **幂等**。cron 重跑会重复推送，现在每次任务先写当日 run_id，已存在则跳过。
- **截断**。某天 CI 大面积失败，聚合 JSON 仍然超长。策略是按 severity 优先截断，并在日报中明确标注"当日事件过多，已省略 N 条"，而不是默默丢弃。
- **脱敏**。commit message 里出现过内网地址和临时 token，采集层加了正则脱敏——这一步必须发生在归档之前。
- **模板漂移**。换模型版本后输出格式偶尔跑偏，靠固定模板 + few-shot 示例压住。

## 可复用建议

- **Schema 优先**：先定中间格式，再写采集脚本和提示词，顺序别反。
- **Agent 只做"写作层"**：采集、聚合、脱敏全放普通脚本，可测试、可重放。
- **宁可空日报，不要静默失败**：无事件的日期推送"今日无变更"，链路是否健康一眼可见。
- **输入输出一起归档**：日报里每个数字都能回溯到原始记录。

## 总结

这套东西没有用到任何高深技术，价值在于把"写日报"拆成"结构化"和"转述"两件事：前者交给确定性脚本，后者才交给模型。跑了一个多月，日报从每天约 20 分钟的人工变成零介入，可信度反而更高——因为每一条都有据可查。
