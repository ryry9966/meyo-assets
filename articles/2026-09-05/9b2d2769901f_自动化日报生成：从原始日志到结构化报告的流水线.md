## 背景

每天写日报，最耗时的不是写，而是整理。我们的 Agent 运行平台每天产生大量日志：任务执行记录、工具调用失败、插件告警，分散在几个不同位置。之前靠人翻日志挑重点，一天三四十分钟还经常漏项。这篇文章记录我们把它做成自动化流水线的过程，思路对任何"原始日志 → 日报"的场景都适用。

## 问题

动手前明确了几条约束：

1. 日志格式不统一：JSON 行、纯文本、结构化事件混着来；
2. 全量喂给 LLM 不可行：一天数百万 token，而且模型会"编"出不存在的告警；
3. 日报必须有结构：不是一段模糊总结，而是能对比、能归档的字段；
4. 必须可降级：模型服务挂了，日报不能开天窗。

## 做法

流水线分四层，各自独立、可单独替换。

**1. 采集与预处理（纯规则，无模型）**
定时任务每小时拉一次原始日志，统一转成中间格式——这是整个设计里最重要的一步：

```json
{"ts": "...", "source": "agent-runtime", "level": "warn",
 "event": "tool_call_failed", "key": "web-scraper", "detail": "..."}
```

不管上游什么格式，进管道前先归一。字段映射写在一个配置文件里，新日志源加一条映射即可。

**2. 聚合与筛选（纯规则）**
按 key + event 分组去重，同类失败合并计数；过滤心跳类 info 噪声；对每条聚合结果对比过去 7 天同时段基线做异常检测。产出的"值得报告事件"通常一天 20~50 条。

**3. LLM 归纳（Agent + 结构化输出）**
把筛选后的事件列表交给 OpenClaw 定时 Agent，prompt 只要求两件事：合并语义重复的条目、为每条写一句人话解释。输出强制走 JSON Schema：

```json
{"items": [{"category": "...", "severity": "low|mid|high",
            "summary": "...", "suggestion": "..."}]}
```

校验失败自动重试一次，再失败走规则模板兜底。

**4. 渲染与分发**
Schema 数据渲染成 Markdown 模板，落到归档目录（文件名带日期），再通过 webhook 推到群里。

## 踩坑点

- **全量日志直接进模型**：第一版偷懒把日志尾部 50k token 丢给 Agent，结果模型编造了一条不存在的数据库告警。教训：模型只做"归纳"，不做"筛选"，筛选必须用确定性规则。
- **时区**：日志时间戳是 UTC，日报按本地日期切，午夜前后的任务会被归错天。在预处理层统一转成业务时区。
- **长行截断**：解析器对超长行默认截断，JSON 解析失败率约 2%。改为"截断但打 truncated 标记"，失败样本进隔离目录人工抽查。
- **重复报告**：手动补跑一次任务，群里出现两份日报。改成按"报告日期"做幂等键，同日期覆盖写而不是追加。
- **结构化输出漂移**：模型偶尔把 severity 写成 `warning`。Schema 里用枚举加一层兜底映射解决。

## 可复用建议

1. **中间层 schema 是核心资产**：上游格式变了改映射，下游需求变了改渲染，中间不动。别让 LLM 直接对接原始日志。
2. **规则做确定性的事，模型做语义的事**：筛选、去重、统计交给规则；归纳、解释交给模型。这个分工会同时压低成本和幻觉率。
3. **必须有降级路径**：LLM 失败时输出规则模板版（缺"解释"字段但数字都在），比开天窗好得多。
4. **保留原始聚合结果**：LLM 输出与规则聚合结果分开存，事后可审计"模型有没有说谎"。
5. 用 MCP 封装"读日志、写归档、发通知"三类工具，Agent 只负责编排，其余环节不依赖模型。

## 总结

上线后，日报的人工耗时从每天半小时降到零，异常日人工复核即可。核心经验一句话：**把 LLM 放在管道末端做归纳，前面用确定性工程把输入收拾干净**。整条链路没有任何"智能"魔法，可测试、可回放、可审计——自动化报告要的恰恰是这种无聊的可靠。
