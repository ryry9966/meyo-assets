## 背景

我们团队每天要出一份日报：服务运行情况、昨天合并的 PR、CI 失败记录、值得关注的告警。以前的做法是运维同学早上花四十分钟翻日志、翻群消息、拼 Markdown。内容没大错，但这活儿重复、枯燥，还容易漏。

这篇帖子记录我把这条流程改成自动化流水线的过程。核心思路一句话：**确定性的活交给脚本，概率性的活（总结、判断）交给 Agent，中间用固定的数据结构隔开。**

## 问题

原始日志有三个特点，决定了不能直接扔给 Agent：

1. **量大**。一天的访问日志、CI 日志、git 记录拼起来远超上下文窗口，直接塞进去既贵又容易被截断。
2. **脏**。时间戳时区不一、多行堆栈、重复告警，原始形态喂给模型，总结质量全凭运气。
3. **格式不稳定**。让模型自由发挥，今天出 bullet 明天出表格，下游没法归档和对比。

## 做法

流水线分四段，前三段纯脚本，最后一段用 OpenClaw Agent：

**1. 采集（cron 触发）**
每天 07:30 定时任务拉三类数据：按天切割的应用日志、git 提交记录、CI 结果 API。每类落成一个 JSON 文件，schema 固定：`timestamp / source / level / event`。

**2. 聚合**
脚本做确定性统计：错误按模块分组计数、告警去重、时间统一到 UTC+8、CI 失败只保留最后一次的失败步骤。产出一份聚合摘要（通常 2-3KB），外加一份"异常清单"——用硬规则筛出的错误率超阈值、连续失败的 job 等条目。

**3. 渲染骨架**
用固定 Markdown 模板填入统计数字，生成报告的"确定部分"。这段不经过任何模型，数字永远是对的。

**4. Agent 总结**
把聚合摘要 + 异常清单交给 OpenClaw Agent，配两个 MCP 工具：一个查历史日报（用于对比"错误率比昨天高/低"），一个负责归档并回调 webhook 推送到群。Prompt 里只让它做三件事：给异常清单排序、写一段不超过 150 字的整体评述、对需要人跟进的项标记 `TODO`。

## 踩坑点

- **别让 Agent 摸原始日志**。第一版我偷懒直接喂日志文件，输出看着合理，但编造了一个不存在的服务名。改成只喂聚合结果后，幻觉基本消失——它没有发挥空间了。
- **时区错位**。有一台机器是 UTC，"昨天"的统计窗口偏了 8 小时，连续两天日报漏掉凌晨告警。现在采集层统一转时区，聚合层只认一个时区。
- **输出格式漂移**。Agent 偶尔把 `TODO` 写成"待跟进"，下游解析挂掉。解法是在归档工具里加 schema 校验，不合法就打回重试一次。
- **流水线静默失败**。最难排查的一次是 webhook token 过期，日报三天没发出去但没人发现。现在加了一条心跳：无论成败，流水线结束都往群里发一条简短状态，失败时附带阶段名。

## 可复用建议

- **接口即契约**：段与段之间用固定 schema 的 JSON，任何一段都能单独替换、单独重跑。
- **留原始数据**：采集结果按日期归档，出问题可以离线重放整条流水线，不用等第二天。
- **灰度信任**：前两周 Agent 产出只进草稿，人确认后再推送；稳定后放开自动发送，但保留发送前的 diff 预览。
- **评述要短**：限制字数比在 prompt 里写"请简明扼要"有效得多。

## 总结

流水线上线两个月，日报制作从每天 40 分钟降到接近 0，中途只出过上面那几次问题。体会是：自动化日报的价值不在"AI 写文章"，而在先把数据收拾干净——LLM 只负责最后 10% 的归纳和措辞。结构越固定，自动化越可靠。
