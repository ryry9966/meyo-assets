## 背景

在 OpenClaw 这类常驻型 agent 环境里，“任务只执行一次”其实是稀缺事件：

- 定时任务到点触发，宿主机重启后补跑一次；
- 消息平台的事件通知本身就可能重复投递；
- agent 调用 MCP 工具失败后按策略重试；
- 手动重跑某个失败的工作流。

底层调度和传输普遍按 at-least-once 设计——宁可重复，不可丢失。所以重复执行不是异常，而是常态。幂等性就是让“重复执行”和“执行一次”产生相同结果的设计约束。

## 问题

几个真实会撞上的场景：

- 定时日报任务，agent 崩溃重启后补跑，群里同一份日报发了两遍；
- “有新 issue 就建工单”的插件遇到消息重投，建出两个一模一样的工单；
- agent 重试某个写文件的工具，append 型日志直接翻倍。

这些都不是 bug，而是没把幂等当成设计前提。

## 做法

1. **给操作分类。** 只读操作天然幂等，不用管；`create`、`append`、`send` 这类有副作用的操作才是重点。
2. **定义稳定的幂等键。** 用业务身份而不是运行时身份：`task_id + 目标 + 时间窗口`。不要用 uuid 或时间戳——重试时它每次都变，等于没防。比如日报任务：`digest:{chat_id}:{date}`。
3. **原子地“查了再写”。** 先 SELECT 再 INSERT 挡不住并发，两个 worker 会同时通过检查。用数据库唯一约束 + `INSERT IGNORE`，或 Redis 的 `SET NX EX`，把登记和判断合并成一个原子操作：

```python
key = f"digest:{chat_id}:{today}"
if not redis.set(key, 1, nx=True, ex=86400):
    return  # 本窗口已处理，直接跳过
run_digest(chat_id)
```

4. **写操作尽量 upsert 化。** 文件用临时文件 + rename 原子替换，数据库用 `ON CONFLICT DO UPDATE`，把重复执行收敛成“覆盖出同样的结果”。
5. **定时任务加锁。** 长任务配短周期会重叠执行，用文件锁或 DB advisory lock 保证单实例运行。锁不替代幂等，只是减少触发面。

## 踩坑点

- **幂等键掺了随机数或时间戳**：重试时 key 变了，防了个寂寞。key 必须在同一次逻辑执行的所有重试中保持一致。
- **只加 key，不做原子登记**：check 和 set 之间的竞态窗口照样放行两个请求。
- **TTL 设太短**：重试在 key 过期后才到达，照样重复。TTL 应大于最大重试窗口。
- **只管了自己的代码**：你自己幂等了，但下游第三方 API 的“发消息”不是幂等的。要么用上游支持的幂等参数，要么把调用记录也纳入 key 管理。
- **无脑 `retry=3`**：对非幂等操作，盲目重试等于放大副作用。先分类，再决定重试策略。

## 可复用建议

- 写任何自动化任务前先回答：**这个任务被连跑两次会怎样？** 答不上来就别上线。
- 每个副作用路径配一个自然键加一张“已处理”集合，成本十分钟；事故后补幂等，成本一个通宵。
- 主动测试：部署后手动连触发两次，核对结果是否一致，比任何代码评审都有效。
- 日志里带上幂等键，排查“到底执行了几次”时一目了然。
- 把幂等属性写进 MCP 工具的描述里，让 agent 知道哪些工具可以安全重试，哪些碰不得。

## 总结

框架保证 at-least-once，你负责让每次执行“重复无害”。幂等不是锦上添花的优化，而是自动化系统的地基——它决定了你敢不敢按重跑按钮，也决定了半夜告警来临时你是安心睡觉还是爬起来手工对账。
