## 背景

OpenClaw 里的自动化任务，大多跑在“不可靠”的环境中：定时触发器可能重叠、MCP 工具调用会超时重试、webhook 会重复投递、人还会手滑再点一次执行。只要自动化活得够久，“同一个操作被执行两次”不是会不会发生的问题，而是什么时候发生的问题。

## 问题

很多脚本第一次跑都很正常，出事都出在重试上。几个典型场景：

- 定时任务超时被拉起，群里发了两条一模一样的告警；
- Agent 重试一次工具调用，工单系统里多了一条重复工单；
- webhook 重投递，下游库存被扣了两次。

根因是同一个：操作不幂等，“执行一次”和“执行两次”的结果不一样。而网络传输层只能保证 at-least-once，去重的责任永远落在你自己的业务代码里。

## 做法

核心思路：给每次**逻辑操作**定义一个稳定的幂等键，让下游按键去重。

1. **定义幂等键**。用业务语义生成，例如 `task_id + target_id + biz_date`。关键是每次重试必须算出同一个键，所以键的生成要放在工具/插件代码里，绝不能让 LLM 每次现场发挥。
2. **下游按键去重**。写库用 upsert，靠唯一索引兜底；发消息前先查“这个键处理过没有”；调用第三方 API 时带上它支持的幂等头。
3. **用条件写代替“先查后写”**。不要“查一下不存在再插入”——并发时两个 worker 会同时通过检查。直接让数据库唯一约束拒绝第二次写入。
4. **状态机收敛**。给任务定状态（pending / running / done / failed），已到终态的操作直接跳过，重试只允许从 failed 重新进入。
5. **落操作台账**。每次执行记一条（key、时间、结果），重试基于台账恢复现场，而不是靠猜“上次跑到哪”。

## 踩坑点

- **每次重试生成新 UUID 当键**：等于没做幂等，这是最常见的错误。
- **检查与写入之间存在竞态**：应用层 if 判断挡不住并发，必须依赖存储层约束。
- **只幂等了一半**：写库成功了，但消息是在写库之后发的；重试时库去重了，消息却又发了一遍。副作用有多个时，要么把每个副作用都记台账，要么把副作用收敛到台账写入之后。
- **去重缓存 TTL 太短**：缓存 5 分钟过期，可上游重试窗口有 30 分钟。
- **键太宽或太窄**：太宽会吞掉合法的重复操作，太细则去不了重。键的粒度应对应“一次业务意图”。

## 可复用建议

- 把“接受客户端传入幂等键”写进 MCP 工具和插件接口的设计规范；
- 默认用 upsert，除非有明确理由不用；
- 破坏性操作（删除、覆盖）改用条件删除或带版本号的更新，天然幂等；
- 定时任务加分布式锁，或加“上个周期未完成则跳过”的守卫；
- 幂等键里带时间窗口字段（如日期），既防短期重复，又不影响隔天的合法重跑。

## 总结

幂等不是锦上添花的高级特性，而是自动化的入场券。传输层给你的是 at-least-once，业务层必须自己补上“至少一次 + 去重 = 效果上的恰好一次”。先定稳定的幂等键，再让存储层约束兜底，最后用台账覆盖多副作用的场景——做到这三层，重试和重复触发就从事故源，变成了可以放心依赖的容错机制。
