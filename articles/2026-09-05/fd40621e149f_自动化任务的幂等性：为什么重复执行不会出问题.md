## 背景

跑 OpenClaw 的自动化一段时间后，你会发现一个规律：**重试是常态，不是异常**。cron 任务赶上网络抖动、webhook 到达后 gateway 超时、MCP 工具调用卡住后客户端重新发起、进程重启后队列里的任务被重新消费——这些场景都会让同一条指令被执行不止一次。

幂等性就是这里的分水岭：幂等的任务，重复执行十次和执行一次结果一样；不幂等的任务，第二次执行就是事故的开始。

## 问题

几个真实感很强的例子：

- 日报任务每天 cron 触发一次，某天网关超时自动重试，群里出现两条一模一样的日报；
- webhook 触发的文件整理任务，Agent 已经归档完文件，响应没送达，触发方重发，Agent 又"归档"一遍，日志里出现重复操作记录；
- 调外部 API 的插件（下单、发消息、建工单），超时后重试，外部系统里多了一条脏数据。

共同点：副作用发生在"成功但响应丢失"的灰色地带。靠"不重试"解决不了——那样丢失执行反而成了常态。

## 做法

核心思路一句话：**给每次执行一个稳定的业务键，并在副作用发生前检查它。**

1. **定义幂等键。** key 来自触发语义而不是执行时刻：cron 任务用"任务名+执行日期"，webhook 用事件自带的事件 ID。不要用时间戳或随机 UUID 当 key——每次重试生成的 key 都不同，等于没做。
2. **先落意图，再执行。** 执行前把 key 写入"已执行表"（SQLite 或本地 JSON 都行），靠唯一索引兜底；插入失败说明跑过，直接跳过。注意是先 INSERT 再干活，不要先 SELECT 再 INSERT——两个并发重试可能同时查到"没跑过"，然后双写。
3. **输出尽量覆盖式。** 让任务产出"最终状态"而非"增量追加"：配置整块重写、报表按日期覆盖文件、写临时文件后原子 rename。这类操作天然幂等。
4. **外部调用带幂等参数。** 支持幂等键的 API（支付、消息类很多都支持）一定带上；不支持的，在插件里自己包一层去重。
5. **条件更新抢任务。** 队列型任务用 `UPDATE ... WHERE status='pending'`，看受影响行数判断是否抢到，避免多实例重复消费。

## 踩坑点

- **key 粒度错了。** key 设计成"每天一个"，但任务合法地一天跑多次（比如手动补跑），就把合法执行也挡掉了。粒度要匹配业务语义。
- **"看似幂等"的操作带着不幂等的尾巴。** 删除类任务重复执行无害，但每次都发一条通知，用户就会被轰炸。副作用要整体评估。
- **假失败。** 外部 API 已经成功，只是响应超时。重试被幂等层拦住是对的，但日志要能对上——否则你以为失败了，人工又补一次。
- **原子 rename 只在同盘内原子。** 跨挂载点、共享盘不成立，别想当然。
- **检查和执行之间没有原子性。** 任何"先查一下再说"的写法在并发重试下都会翻车，交给唯一约束和条件更新。

## 可复用建议

- 把幂等做成插件/工具层的**默认能力**：统一入口注入幂等键，共用一张已执行表，别让每个任务自己造轮子。
- 给每个自动化任务写一行"幂等声明"：key 是什么、检查点在哪、非幂等的部分如何处理。三个月后的你会感谢这行注释。
- 验证方法很朴素：staging 里手动连续触发两次，确认副作用只发生一次；再用脚本模拟连续重试打一遍。
- 对幂等冲突打监控点：冲突次数突然升高，通常说明上游在异常重试，比用户投诉早发现。

## 总结

幂等不是工程洁癖，而是自动化值得信任的前提。OpenClaw 里 cron、webhook、MCP 工具、消息触发入口越多，越要假设"同一条指令会到达两次"。记住这个最小模式：**稳定业务键 + 唯一约束 + 先落意图再执行**。做到这一步，你的自动化才敢放心地挂上重试。
