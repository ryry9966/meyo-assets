## 背景

大多数 AI 助手的默认形态是被动应答：你发消息，它回消息。但个人助理的真正价值往往在"你没意识到的问题，它先处理了"。OpenClaw 这类常驻网关型 agent 天然具备做 proactive 的条件——一直在线、有工具、有状态，缺的只是触发机制和边界设计。

## 问题

把"主动"直接丢给模型是不行的，实践中会立刻遇到三个问题：

1. **触发从哪来？** 没有事件源，模型不会自己醒来。
2. **噪音控制**：推送过多，用户会关通知，信任一次性归零。
3. **失控风险**：没人在回路里，agent 自主执行写操作出错的代价，远高于答错一句话。

## 做法

以"每天早上推送一份简报 + CI 挂了主动提醒"为例：

1. **接入事件源**。在网关配置里启用 cron/heartbeat 定时唤醒 agent；webhook 事件（如 CI 失败）直接注入会话。
2. **写清 proactive 指令**。在 workspace 的 agent 指令中明确：哪些任务允许主动执行（只读汇总）、哪些必须先问（任何写操作）、打扰式推送的每日上限（比如 ≤3 条）。
3. **接工具**。通过 MCP server 挂上日历、GitHub、监控查询等只读工具。
4. **加状态文件防重**。agent 每次主动动作前读写一个 JSON 状态文件，记录"已推送过什么"，避免同一个 CI 失败推五遍。
5. **分级投递**。低价值结果写入日志文件，用户想看再看；高价值才走消息通道推送。

## 踩坑点

- **心跳自唤醒循环**：cron 唤醒 agent，agent 的动作又触发新事件，形成环。解法是给主动任务打标，事件处理时跳过自己产生的记录。
- **时区问题**：cron 按服务器时区跑，"早上八点"的简报在凌晨三点推出来。在配置里显式声明时区。
- **工具失败无人兜底**：主动执行时用户不在场，工具报错要落到日志，并在下次心跳时自检，不能静默丢弃。
- **指令冲突**：proactive 指令和原有 system prompt 打架，出现"它以为它在帮忙"的过度行为。建议每次只加一条主动规则，观察一周再加下一条。

## 可复用建议

- **先只读后写入**：proactive 第一步只做汇总和提醒，写操作全部走用户确认。
- **每个主动行为留开关**：配置粒度到单个任务，而不是全局 on/off。
- **预算思维**：按"重要性 × 紧急度 × 置信度"打分，低于阈值只记日志、不打扰。
- **全量审计**：agent 的自主动作要留下可回溯记录，出问题能复盘。

## 总结

Proactive 不是让模型"更聪明"，而是一个工程问题：事件源、决策边界、状态管理、失败兜底，四件事做扎实，主动能力才敢开。建议先从一份每天准时的简报跑起，稳定之后再逐步放开触发面——主动能力的上限，取决于你敢给它多大的边界。
