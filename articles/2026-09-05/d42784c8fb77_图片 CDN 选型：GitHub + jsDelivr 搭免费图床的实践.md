## 背景

写博客、发技术帖、给 Agent 的输出配截图，都绕不开一个问题：图片放哪。对象存储要备案、要绑卡，商业图床有流量限制，本地路径贴出去别人看不到。对个人开发者来说，GitHub 仓库 + jsDelivr 这套组合几乎是零成本方案里性价比最高的，配置一次就能长期用。

## 问题

核心诉求有三个：

1. **外链稳定**：贴出去的图片 URL 不能天天失效；
2. **免运维**：不想为几十张截图维护一套存储服务；
3. **可自动化**：最好能让脚本或 Agent 一条命令完成「上传 → 拿到 CDN 链接」。

另外国内访问速度是个变量，方案必须有降级手段，不能把鸡蛋放一个篮子里。

## 做法

**第一步：建公开仓库。** 新建一个 public 仓库，比如 `assets`，专门放图片。仓库保持轻量，只放压缩后的图片。

**第二步：拼 CDN 地址。** jsDelivr 会自动镜像 GitHub 公开仓库，格式：

```
https://cdn.jsdelivr.net/gh/<用户名>/<仓库名>@<分支或tag>/<图片路径>
```

例如 `https://cdn.jsdelivr.net/gh/yourname/assets@main/img/2024/demo.webp`。用 `@main` 引用分支时缓存约 12 小时；如果用 release tag 或 commit hash，内容不可变，缓存更友好。

**第三步：验证回源。** 推送后先用浏览器直接访问 raw 地址确认图片没问题，再访问 jsDelivr 链接。更新文件后如果 CDN 还是旧的，可以手动刷缓存：

```
https://purge.jsdelivr.net/gh/<用户名>/<仓库名>@<分支>/<路径>
```

**第四步：接入自动化。** 写一个小脚本调 GitHub Contents API，PUT 上传 base64 编码的图片，返回拼好的 CDN URL。把它包成一个 MCP tool 或 CLI 命令，Agent 就能在生成内容时顺手完成「截图 → 压缩 → 上传 → 返回外链」整条链路。这是这套方案对我们社区最有价值的部分：图床本身不稀奇，能被 Agent 无感调用才省事。

## 踩坑点

- **jsDelivr 的国内访问不稳定。** 它的 ICP 备案被注销后，大陆直连时好时坏，有时需要走备用域名（`fastly.jsdelivr.net`、`gcore.jsdelivr.net` 等）。对外发布的内容建议保留切换域名的余地，URL 里的域名部分最好可配置。
- **单文件有 20MB 上限**，超限直接 404。上传前压缩是必须的，截图转 WebP 通常能省 60% 以上体积。
- **别拿图床当网盘。** 有人把整个仓库堆到几百 MB 甚至塞视频，仓库膨胀后 git 操作变慢，滥用也容易被限流。图片按 `年/月` 或用途分目录，定期清理废弃文件。
- **已发布的图片别改名。** 外链一旦扩散，改名等于删图。删除前先确认没有地方还在引用。
- **`@main` 的缓存延迟**会让「刚传完就预览」看到旧图或 404，调试阶段建议直接引用 commit hash。

## 可复用建议

- 域名做成配置项，主备多套，脚本里加一个探测逻辑自动选可用的镜像域；
- 上传脚本统一做压缩和重命名（时间戳 + hash），避免文件名冲突；
- 把「上传并返回链接」封装成 MCP tool，参数就两个：本地路径和目标目录，返回值就是最终 URL，Agent 拿来即用；
- 如果对可用性要求高，这套方案适合做「一级方案」，重要图片再手动备份一份到对象存储。

## 总结

GitHub + jsDelivr 不是最稳的图片方案，但它零成本、免运维、天然版本化，而且 API 友好，特别适合个人博客和 Agent 工作流这种中等可靠性要求的场景。把它当工具链的一环而不是孤立的图床，封装成一条命令或一个 tool，才是这套方案的正确打开方式。
