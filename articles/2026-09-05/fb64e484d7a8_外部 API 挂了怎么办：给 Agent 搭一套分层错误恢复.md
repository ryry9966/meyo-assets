## 背景

Agent 和传统服务最大的区别：失败会被放大。传统服务里一次 API 调用失败就是一次 5xx；在 Agent 里，一次失败可能被 LLM 解读、重试、换个姿势再试，几轮下来 token 烧掉、任务卡死，甚至模型开始"编"结果。我们环境里最贵的故障，往往不是 API 本身挂掉，而是 Agent 对"挂掉"的错误反应。

## 常见的几种失败模式

- **超时 / 5xx / 429**：可重试类错误，但策略不对会雪上加霜
- **4xx**：不可重试，重试只会浪费配额
- **最隐蔽的**：API 返回 200 但数据质量劣化（限流降级、缓存过期），Agent 拿着垃圾数据继续推理，全程无报警

## 做法：分层兜底

**Layer 0 · 错误分类。** 第一步是把错误归类，不要一律重试：

```python
RETRYABLE = {408, 429, 500, 502, 503, 504}
# 其余 4xx 直接判失败，走结构化错误交给上层
```

**Layer 1 · 工具层重试。** 指数退避 + 抖动，控制在 2~3 次。在 MCP server / 工具封装层做，**不要交给模型自己重试**。

**Layer 2 · 超时与熔断。** 每次调用设硬超时；同一 endpoint 连续失败 N 次后熔断，期间直接走 fallback、不发真请求。熔断粒度到 endpoint，别做全局——一个接口挂了不该连带禁用其他接口。

**Layer 3 · 降级。** 按业务选：读缓存旧数据 / 换备用 provider / 标记"数据不可用"后跳过依赖该数据的步骤。关键是降级产出必须打标记（如 `degraded: true`），别和正常数据混着污染下游。

**Layer 4 · 把失败结构化地还给模型。** 兜不住的，最终要 Agent 决策。但喂给模型的不是堆栈，而是：

```json
{
  "status": "failed",
  "error_type": "upstream_unavailable",
  "retry_exhausted": true,
  "suggested_action": "switch_tool_or_ask_user"
}
```

同时给模型设重试预算：最多再试 1 次，且必须换参数或换工具，防止同一路径死循环。

## 踩坑点

1. **让 LLM 自己管重试。** 它不记得试过几次，同一段循环能跑五六轮，一晚上烧掉一个季度的 token 预算。重试永远在代码层做。
2. **把原始堆栈塞给模型。** 轻则道歉式输出刷屏，重则幻觉出一个"看起来合理"的返回值，错误被静默吞掉。
3. **退避没加抖动。** 服务恢复瞬间，几百个 Agent 同时重放请求，把刚喘过气的 API 再打挂一次。
4. **降级数据不打标。** 排查问题时才发现某天报表的数据来源是三天前的缓存，没人知情。
5. **429 也无脑重试。** 先读 `Retry-After` 头，没有再按退避走，别自己加码。

## 可复用清单

- 工具调用：硬超时 + 最多 3 次退避重试 + 抖动
- 熔断：按 endpoint，连续 5 次失败断开，半开状态探测恢复
- 兜底顺序：缓存 → 备用源 → 明确失败；产出必带 `degraded` 标记
- 交给模型：结构化错误 + 重试预算 + 强制换策略
- 观测：每个工具的失败率、熔断状态要有指标，日志里记录每次降级事件

## 总结

Agent 的可靠性工程，核心不是"让 API 不挂"，而是承认它一定会挂，提前把反应写进代码，而不是留给模型临场发挥。一句话原则：**可重试的在代码层退避重试，不可重试的快速失败，兜不住的降级并打标，最后才把一个干净的决策交给模型。** 做完这套你会发现，大部分所谓"Agent 失控"，其实只是缺了中间那几层。
