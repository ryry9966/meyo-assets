## 背景

OpenClaw 这类常驻型 Agent 和一次性对话机器人最大的区别，是它有持续存在的工作区（workspace）。SOUL.md 就放在工作区根目录，随上下文注入系统提示，定义这个 Agent 是谁、什么语气、哪些事不碰。很多人装完直接跑，SOUL.md 用默认模板甚至空着——能跑，但行为不可预期。

## 问题

没有明确人格与边界的 Agent，实践中会暴露三类典型毛病：

1. **行为漂移**：会话拉长或换模型后，语气和行事风格不一致，昨天谨慎的工具调用今天变得激进。
2. **边界模糊**：Agent 自作主张执行破坏性操作（删文件、群发消息、对外发请求），因为没人告诉它“先问一句”。
3. **调试无锚点**：行为出问题时，你不知道该改系统提示、任务描述还是工具配置——预期散落在各处。

## 做法

我的 SOUL.md 控制在 40 行以内，分四段：

1. **身份与语气**（5–8 行）：一句话身份定位 + 具体的语气规则。别写“友好专业”这种形容词，写“回复用短句，先给结论再给理由；不确定时明说不确定”。
2. **硬边界**（10 行左右）：绝对禁止项 + 需确认项。例如：批量删除文件、对外发网络请求、修改配置前，必须先列出变更内容并等待确认。
3. **不确定性处理**：遇到超出能力的任务如何降级——明确说做不了、给出替代路径，而不是硬编一个结果。
4. **与工具的关系**：约定 MCP 工具报错时的行为（重试几次、何时上报），避免 Agent 陷入重试循环或静默失败。

改完后重启会话或重新加载工作区，用几个边界用例验证：让它删一个目录、发一条消息，看它是否按规则先确认。

## 踩坑点

- **写太长**：超过一两百行，关键规则会被稀释。我砍掉一半篇幅后，边界遵守率反而明显上升。
- **形容词堆砌**：“聪明、可靠、有帮助”没有约束力，可执行的行为描述才有。
- **和工具描述冲突**：某个 MCP 工具的 description 写着“可直接执行”，会和 SOUL.md 的确认规则打架，Agent 行为变得随机。原则是以 SOUL.md 为准，同时回头修工具描述，消掉歧义。
- **出事不回写**：Agent 每越界一次，就该变成 SOUL.md 里的一条新规则。这个文件是活的，不是一次性的配置。

## 可复用建议

- 把 SOUL.md 纳入 git，提交信息写清“为什么改”，它天然就是 Agent 的行为变更日志。
- 人格（SOUL.md）与任务规则（AGENTS.md 或任务说明）分开维护，别混在一起。
- 模型升级后重跑一遍边界用例：新模型对同一份人格文件的“理解”可能不同。
- 准备 5–10 条对抗性测试指令，每次改动后都跑一遍，形成回归测试的习惯。

## 总结

SOUL.md 不是玄学，本质是把你对 Agent 的行为预期，固化成一份可版本管理、可迭代、可测试的规则文件。写得越具体、越短、越贴合你实际踩过的坑，Agent 就越稳。建议每个常驻 Agent 都从一份 30 行的 SOUL.md 起步，然后在真实使用中把它磨出来。
