## 背景

信息源没变少，耐心在变少。订阅了几十个博客和周刊，RSS 阅读器里未读常年四位数，真正读完的不到一成。与其硬啃，不如让 Agent 先读一遍：我要的不是原文搬运，而是每天早上一条“值得看什么、为什么值得看”的摘要推送。

## 问题

这件事拆开是三个工程问题：

1. 定时拉取 RSS 并准确识别“新条目”；
2. 全文提取——大部分源只给摘要，甚至不给；
3. 让模型产出结构化、可信的摘要，同时控制 token 成本。

## 做法

我用 OpenClaw 的 cron skill 加自定义脚本搭了这条管线，整体五步：

1. **订阅清单**：`feeds.yaml` 维护源列表，每条标注分类（backend / agent / 论文）和权重。
2. **拉取与去重**：cron 每 4 小时跑一次，rss-parser 解析，用 `guid || link` 的 hash 写入 `seen.json`，只处理增量。
3. **全文提取**：对 description 过短的条目抓原文页面，走 readability 提取正文，截断到 4000 字符。这一步我封装成了一个 MCP tool，方便其他 skill 复用。
4. **两段式摘要**：先用便宜模型打相关性分（0–10），低于 6 直接丢弃；过线的再调主力模型产出结构化 JSON——标题、一句话结论、2–3 个要点、原文链接。prompt 里明确“只允许基于给定文本总结，信息不足就标注 insufficient"。
5. **聚合推送**：按分类合并成日报，经 channel 推到 Telegram，同时落一份 Markdown 到笔记目录。

核心提示词模板大致是：

```text
你是技术信息过滤助手。基于以下原文输出 JSON：
{"title": "...", "tldr": "一句话", "points": ["..."], "score_reason": "..."}
禁止引入原文之外的信息。
```

## 踩坑点

- **GUID 不可信**：个别源的 guid 会变，导致重复推送。改成 `hash(link 规范化后的 path)` 后才稳住。
- **Cron 重叠**：全文提取慢时会拖过下一个调度点，加了个简单的文件锁（pid 检查）解决。
- **空正文幻觉**：某些源只有标题，模型会脑补内容。现在正文少于 200 字符就只归档不总结。
- **成本失控**：第一版对所有条目都调主力模型，一天跑下来 token 不便宜。改成“先过滤、再精读”的两段式后，成本降到约 1/5。
- **格式差异**：Atom 和 RSS 2.0 字段名不一致，日期解析统一交给库，别手写正则。

## 可复用建议

- 状态持久化越简单越好：一个 JSON 文件就够，别为去重上数据库。
- “过滤”和“摘要”分开建模：便宜模型干粗活，贵模型只看过线内容。
- 推送内容必须带原文链接，摘要只是索引，最终判断留给自己。
- prompt 里写死输出 schema，下游解析才不会每天有惊喜。

## 总结

这条管线跑了两周，每天早上一条 10 条以内的日报，未读焦虑确实降了。它不替我做判断，只是把“筛”这个体力活自动化了。后续打算加上点击反馈回写权重，让过滤模型越用越懂我的口味。如果你也在 OpenClaw 上做信息流自动化，欢迎交流去重和成本控制的做法。
