## 背景

大多数 Agent 的日常是被动应答：你问，它答，然后沉睡。但值班类需求天然不是问答——每天早上拉一遍仓库动态、盯磁盘水位、检查 CI 是否红了。这类事以前靠 cron 加一堆胶水脚本，逻辑散落在 Agent 体系之外，改一次需求要动两个地方。

OpenClaw 的 heartbeat 机制就是为了把这个闭环收回 Agent 内：网关按固定间隔（默认 30 分钟）唤醒一次 agent，agent 醒来第一件事是读工作区根目录的 `HEARTBEAT.md`。文件里有待办就执行，没有就返回 `HEARTBEAT_OK`，这条回复会被吞掉，用户端完全无感。

## 做法

1. **确认心跳已开启**。检查 `openclaw.json` 里 `agents.defaults.heartbeat.every` 的配置，需要更细粒度就按 agent 单独覆盖间隔。
2. **把任务写成"运行手册"**。在 `~/.openclaw/workspace/HEARTBEAT.md` 里每条任务写清三件事：触发条件（什么时间/什么状态）、执行动作（调用哪个工具或 MCP 能力）、上报阈值（什么结果才值得打扰我）。例如："每天 9 点后首次心跳，汇总昨日主仓 commit 与失败 CI，仅在有失败时发频道。"
3. **写明沉默规则**。明确一句"不满足任何阈值时只回复 HEARTBEAT_OK"。这一句的价值比十条任务都大。
4. **短间隔验证**。先把间隔调成 2 分钟，看日志里心跳会话的实际行为，确认触发判断和时间逻辑没问题再调回生产间隔。
5. **接真实工具**。心跳会话里同样能调 MCP 工具和插件，让它去查 GitHub 通知、请求监控 API，而不是靠模型"想"。

## 踩坑点

- **心跳不是 cron**。它是固定间隔唤醒，"每天 9 点"靠模型自己看时间，间隔 30 分钟就意味着可能有漂移。要么接受 ±30 分钟误差，要么缩短间隔，别指望精确调度。
- **每次心跳都是一次真实会话**，都消耗 token。HEARTBEAT.md 保持精简，不做的任务及时删，间隔别无脑调到 5 分钟。
- **过度热情是默认病**。不写清楚"仅超过 80% 磁盘才报"，它会天天向你汇报 47%。
- **Agent 有权限改自己的 HEARTBEAT.md**。这可以是特性（自己维护待办），也可以是事故来源（把自己该干的事改没了）。工作区建议进 git，改动可追溯。
- **心跳会话和你的会话可能并发**。心跳里别安排重活，长任务让它拆给子 agent 或标记延迟执行。

## 可复用建议

- 把 HEARTBEAT.md 当成 **runbook as prompt** 来维护：每条 = 条件 + 动作 + 阈值 + 沉默规则，四要素缺一个就容易跑偏。
- 贵的检查放心跳里做条件触发，重的分析只在阈值命中时派子 agent，控制单位成本。
- 每周看一次心跳日志：从不触发的条目删掉，频繁触发的收紧阈值。
- 原则只有一句：**静默是默认，打扰是例外**。

## 总结

HEARTBEAT.md 的本质是把"主动性"变成可预算的工程参数：间隔、阈值、沉默规则都写在纸面上，而不是藏在模型的不确定行为里。建议从一两个高价值检查起步——比如 CI 失败告警或每日摘要——跑两周、看完日志再扩。主动做事的 Agent 很酷，但工程上更值钱的，是那个知道什么时候闭嘴的 Agent。
