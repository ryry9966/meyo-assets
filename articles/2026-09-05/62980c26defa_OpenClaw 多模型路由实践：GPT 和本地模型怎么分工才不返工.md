## 背景

Agent 跑一段时间后，大多数人都会撞上同一个分叉口：全用 GPT 这类云端强模型，效果稳但 token 账单和隐私问题摆在那里；全换本地模型（Ollama/vLLM 跑 Qwen、DeepSeek），便宜可控，可复杂任务就开始掉链子。OpenClaw 本身支持多 provider 配置，难点从来不在"能不能接"，而在"怎么分"。

## 问题：一刀切的代价

拿我们团队一条自动化流水线（抓取 → 解析 → 规划 → 工具调用 → 汇总）做过对比：

- 全云模型：月度 token 成本里约六成花在解析、格式化输出这类低难度任务上，纯浪费；
- 全本地：规划节点成功率从 92% 左右掉到 70%，工具参数填错触发重试，反而更慢、隐性成本更高。

任务难度分布极不均匀，统一模型必然在某一端付出代价。

## 做法

**1. 先拆角色，再谈路由。** 把工作流节点按能力要求分三类：

- 规划、多步推理：云端强模型；
- 结构化输出、工具参数生成、摘要：本地 7B–14B 足够；
- embedding、意图分类：本地小模型即可。

**2. 多 provider 并挂。** OpenClaw 配置里同时挂云端 API 和本地 OpenAI 兼容端点（vLLM / Ollama 都行）：

```yaml
providers:
  cloud: { model: gpt-4o, ... }
  local: { base_url: "http://127.0.0.1:11434/v1", model: qwen2.5:14b }
routing:
  plan: cloud
  tool_call: local
  summarize: local
  fallback: local -> cloud
```

字段名以你手上的 OpenClaw 版本为准，思路一致即可。

**3. 节点级显式指定模型**，不要依赖全局默认，否则改配置时容易漏。

**4. 关键节点加 schema 校验 + 一次重试。** 本地模型输出不合规就重试一次，仍失败则升级到云端，并把这次降级记进日志。

## 踩坑点

- **本地模型的 function calling 质量参差**，参数幻觉很常见。永远不要裸信它吐的 JSON，校验是底线。
- **上下文截断坑**：云端跑一半切到本地，历史消息超长会被截断，agent 表现突然变笨还找不到原因。路由边界固定在"会话段落"级别，别在任务中途切。
- **参数漂移**：两套模型的 temperature、system prompt 不统一，同一任务输出风格不一致，下游解析就挂。prompt 模板抽成公共文件，两边引用同一份。
- **路由规则本身是负债**。关键词硬编码的路由表半年后没人敢动，规则数量控制在一屏以内，超了就说明该重构工作流了。

## 可复用建议

- **先建 50–100 条评测集再动路由**。没有 baseline 的路由调优全是玄学。
- **fallback 链比精确路由更值钱**：本地优先省钱，连续两次失败升级云端，事后看降级日志反向修规则，这比一开始就追求"精准分发"务实得多。
- **只盯三个数**：每节点 token 花费、结构化输出通过率、端到端延迟。周会扫一眼足够，别建复杂面板。

## 总结

多模型路由不是省钱技巧，而是把"模型能力"当稀缺资源做分配的工程问题。经验值浓缩成四句：规划给强模型、执行给本地模型、路由规则保持极简、一切以评测数据说话。先把工作流拆清楚，路由方案会自然浮出来——反过来先调路由，多半是在给混乱的工作流打补丁。
