## 背景

多数人对 Agent 的使用是一问一答：你提问，它回答，结束。但 OpenClaw 的 Agent 通常是常驻运行的——跑在一台 VPS 或家里的小主机上，接着消息通道，挂着整套 MCP 工具。问题是，除了你主动开口的瞬间，它一直处于"待命但不干活"的状态。

OpenClaw 的 Heartbeat 机制就是为此设计的：每隔一段可配置的时间（默认 30 分钟），Agent 自动醒来一次，读取工作区里的 `HEARTBEAT.md`，判断有没有需要处理的事。它不是 cron 那样执行固定命令，而是给 Agent 一份"常备任务清单"，每次醒来由它自己判断：要不要做、做完了值不值得打扰你。

## 问题

没有 HEARTBEAT.md 时，你就是调度器。查收件箱、扫 GitHub 通知、生成每日摘要，全靠你记得来问一句。Agent 的能力和上下文都在，但你不说话它就永远不动。

而朴素地"放开主动性"更糟：如果 Agent 每次心跳都汇报点什么，聊天窗口很快被它刷屏，结局一定是你把它静音，主动性机制名存实亡。所以核心问题不是"怎么让它主动"，而是**怎么让它只在值得的时候说话，其余时间保持安静**。

## 做法

1. **建文件**：在工作区根目录（如 `~/.openclaw/workspace/`）创建 `HEARTBEAT.md`，纯 Markdown，一行一条任务。
2. **写清触发条件和输出标准**。反例："帮我盯着邮件"。正例："检查收件箱，仅当有来自指定发件人的未读邮件时通知我，否则不发送任何消息"。
3. **配置心跳间隔**：默认 30 分钟，可按需调到 15–60 分钟。注意每次心跳都是一次完整的模型唤醒，频率越高 token 开销越大。
4. **确立静默约定**：在文件顶部写明"无事则静默"。Agent 没事时只回一个固定 ack（不会推送到你的聊天里），你收不到任何消息。
5. **搭配 MCP 工具**：心跳任务可以调用文件系统、GitHub、日历等工具，但单条任务建议控制在两三次调用以内。
6. **像运维手册一样迭代**：每周过一遍，频繁误报的任务删掉，从不触发的任务改得更具体。

## 踩坑点

- **心跳不是 cron**。"每天 8 点"无法精确调度，只能表达为"当天 8 点后的第一次心跳"。需要准点触发的任务，让系统 cron 写一个标记文件，心跳读它即可。
- **高频心跳 + 大模型 = 账单悄然膨胀**。见过有人设 5 分钟一跳、挂十几个任务，日常 token 消耗反而超过正式使用。
- **长任务不要放心跳里**。心跳应在几十秒内完成，重活交给脚本或 cron 跑，Agent 只负责读结果、做判断。
- **不要在 Agent 执行心跳中途大改文件**。改动要到下一次心跳才生效，小步修改没问题，整段重写容易踩到时序。

## 可复用建议

- 把文件分成三段：**静默规则**（永远放最前）、**固定简报**（如"当日首次心跳输出昨日 commit 摘要"）、**条件告警**（条件满足才出声）。
- 把 `HEARTBEAT.md` 纳入 git，每次修改走 diff review，像管理运维手册一样管理它。
- 定义三级通知：静默 / 并入每日摘要 / 立即提醒。绝大多数任务应该落在前两级。
- 从一两条任务起步，稳定跑一周再加。宁可 Agent 太安静，也不要一开始就刷屏。

## 总结

HEARTBEAT.md 的价值不在于让 Agent "更主动"，而在于让主动性可控：指令是声明式的、可评审的、可版本化的，静默是默认态。当它只在有事时敲门，每一次敲门才值得你认真对待。第一次收到它主动发来的消息并真的帮你省了一步时，这个机制就开始产生回报了。
