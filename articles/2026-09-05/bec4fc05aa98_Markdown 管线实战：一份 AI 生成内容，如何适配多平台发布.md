## 背景

在 OpenClaw 的日常工作流里，Agent 产出的内容大多是 Markdown：笔记、周报、教程、发布公告。问题在于这些内容最终要落到不同平台——公众号、知乎、掘金、GitHub、自建静态站。每个平台对 Markdown 的支持差异很大，“写一次，到处发”在理想里很美，实际会碎一地。

我最近把发布流程整理成了一条管线，核心思路是：**单一事实源 + 受限方言 + 薄适配层**。

## 问题

先列痛点：

1. **AI 生成不受控**。模型经常输出 footnote、Mermaid、深层嵌套列表，甚至多个 H1。
2. **平台方言冲突**。公众号编辑器会剥掉 `<style>` 和 class，知乎对部分 GFM 语法不认，任务列表在三端表现各异。
3. **资源路径失效**。本地相对路径图片跨平台搬运后全是死链。
4. **人工适配不可持续**。每次发布都手动调格式，重复劳动还容易出错。

## 做法

管线分四段：

**1. 约束生成端。** 在 Agent 的 system prompt 里明确“发布用 Markdown 方言”：只用 GFM 安全子集——标题最多到 H4、有且仅有一个 H1、不用 footnote、示意图全部预渲染成图片、元数据放 YAML front-matter。配合 markdownlint 做硬校验，不合规直接打回重生成。

**2. 统一中间表示。** 生成结果先过 remark/rehype 清洗：规范化列表缩进、补齐表格、图片链接改写为图床绝对 URL。这一步输出“规范 Markdown”，所有平台共用同一份。

**3. 薄适配层。** 每个平台一个 adapter，只做增量转换：

- 公众号：HTML 渲染后把所有样式内联，代码高亮转成带内联样式的 span；
- 知乎/掘金：基本直发，重点做图床域名白名单校验；
- 静态站：原样进构建，保留最高保真度。

**4. 自动化触发。** 整条管线封装成脚本，push 到发布分支自动执行；同时注册为 OpenClaw 的工具，Agent 写完内容可自行调用完成"lint → 转换 → 预览链接”闭环，我再人工确认发布。

## 踩坑点

- 公众号连 `data-style` 这类属性都会清洗，别想留 hook，样式必须全部内联，且只按标签生效。
- 表格在手机端极窄，宽表直接爆版。现在超过 4 列的内容一律改写成列表。
- Mermaid 不预渲染的话，公众号里就是一坨代码块。构建期用 mermaid-cli 出图，且建议转 PNG——部分客户端对 SVG 的支持也不稳定。
- AI 爱用 `*强调*`，但有些平台只认 `_`，清洗阶段统一转下划线。
- 行尾两空格换行的语法在不同渲染器行为不一致，发布前统一替换为硬段落。

## 可复用建议

1. 给团队/Agent 写一页纸的“Markdown 方言规范”，比事后修补省十倍精力。
2. 维护一张平台约束矩阵（支持/不支持/需转换），接新平台先填表再写 adapter。
3. 转换逻辑收口在一条 remark 插件链里，adapter 只做薄封装，避免逻辑散落。
4. 每个平台留一份“金样本”做快照测试，渲染结果 diff 变化就报警。
5. 发布脚本必须带 dry-run 模式，先出预览链接，人工确认再推。

## 总结

这条管线没有黑科技，本质是把“格式适配”从发布时刻提前到了生成时刻：约束住源头，收敛中间态，让平台差异被薄薄一层 adapter 吃掉。上线两个月，单篇内容的多平台发布从半小时压缩到两三分钟，错版率基本归零。如果你也在用 Agent 批量产出内容，建议先把方言规范定下来——其余都是体力活。
