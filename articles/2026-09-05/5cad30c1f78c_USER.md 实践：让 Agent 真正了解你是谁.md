## 背景

用 OpenClaw 跑个人 Assistant 一段时间后会发现，Agent 对"你"的认知基本靠猜：时区靠推断，语言风格靠当前这条消息，技术栈靠项目文件。项目侧有 AGENTS.md 这类约定管"怎么干活"，但"干活的人是谁、有什么偏好、有什么禁区"一直没有落点。社区里比较成熟的做法，是在 workspace 根目录维护一份 USER.md——它在每次会话启动时随系统上下文注入，相当于给 Agent 的"用户侧 README"。

## 问题

没有这份文件时，个性化信息散落在聊天记录里，带来三类麻烦：

1. **重复解释**。每个新会话都要再说一遍"用 pnpm 别用 npm""中文回复、先结论后细节"。
2. **行为漂移**。Agent 每次对你的猜测可能不同，同类请求给出不一致的处理方式。
3. **无法审计**。偏好埋在几百条消息里，改不动、删不掉，也说不清 Agent 现在到底"以为"你是什么样的人。

## 做法

1. **建文件、定分区**。在 workspace 根目录建 USER.md，按区块组织：环境（OS、时区、语言）、偏好（回复风格、详略程度）、技术栈（语言、包管理器、部署方式）、默认行为（如"改配置前先展示 diff"）、禁区（如"不要主动重启服务"）、项目索引（一句话一条，指向对应项目目录）。
2. **写事实，不写叙事**。每条一句话、主语明确、可判定真伪。"部署用 Docker Compose，单机"是好条目；"我对技术比较有追求"是废条目。
3. **控制体积**。这份文件每个会话都进上下文，建议预算 2KB 或 150 行以内。宁可精，不要全。
4. **建立维护机制**。用 git 管理；让 Agent 提供一个"记一下 xxx"的入口（自建命令或 MCP tool 都行），产出是"追加一行到 USER.md 的建议 diff"，由你确认后落盘。每月 review 一次，过期项直接删。

## 踩坑点

- **写成自传**。长篇背景故事只会稀释关键信息，Agent 反而抓不住重点。
- **混入时效性内容**。"这个月在赶 X 项目"三个月后就是误导。长期事实进 USER.md，动态的事进 MEMORY 或任务系统。
- **放敏感信息**。API key、内网地址不要写。USER.md 会随 workspace 被同步或备份，密钥一律走环境变量和 secret 管理。
- **与项目级文件冲突**。项目文件说用 npm、USER.md 说 pnpm，Agent 会摇摆。要明确优先级：项目文件覆盖个人文件，并在 USER.md 里写一句声明。
- **让 Agent 无确认自写**。幻觉一旦被固化成"事实"，后续每个会话都在引用错误信息，排查成本很高。必须人工确认 diff。

## 可复用建议

- **分层清晰**：USER.md 管"我是谁"，AGENTS.md 管"怎么干活"，MEMORY 管"发生过什么"。三者不重复，可互相引用。
- **条目格式统一**：`- 部署：Docker Compose，单机`。冒号前是类别，人肉好扫读，后续也方便脚本化校验。
- **禁区单独成区并置顶**，安全类约束的优先级应高于偏好。
- 团队场景可以衍生出 TEAM.md，规则相同：小、准、可审计。

## 总结

USER.md 的本质，是把"Agent 了解你"从聊天记录里的隐式沉淀，变成一份显式、可版本化、可审计的配置。写好的标准不是全，而是四个字：**小**（控制 token 预算）、**准**（只放可判定的事实）、**新**（定期清过期项）、**分层**（不和项目文件打架）。半小时建好初版，之后每次维护一分钟，换来的是 Agent 输出一致性的明显提升。建议每个跑 OpenClaw 的 workspace 都配一份。
