## 背景

在 OpenClaw 这类常驻 Agent 环境里，“同一个任务被执行两次”不是意外，而是常态：cron 到点触发但上一轮还没跑完、消息通道重发、Agent 超时后自我重试、你手动补跑一次昨晚失败的任务。触发路径越多，重复就越不可避免。

问题在于，我们的任务描述往往是“动作式”的：发一条消息、建一个日程、追加一行记录。这类操作天然不幂等——跑一次和跑三次，结果不一样。

## 问题

非幂等在单人试用阶段暴露不出来，一旦稳定运行就开始积累脏数据：频道里同一份日报发两遍、日历里出现重复事件、笔记目录多出 `notes(1).md`。更麻烦的是排查困难——你会先怀疑逻辑 bug，而实际上每一次执行单看都是“成功”的。

## 做法

核心思路一句话：把“执行动作”改写成“对齐状态”。

1. **用确定性主键。** 任务的外部标识要从输入推导，而不是从模型输出推导。比如日报笔记固定用 `daily-2025-06-07.md` 这种由日期决定的文件名，重复执行就是覆盖写同一个文件；如果文件名靠 Agent 现场起，两次运行就是两个文件。
2. **写前先查。** 把指令从“创建日程”改成“查 X 日该标题的日程是否已存在，不存在才创建”。MCP 工具层面可以封装成 upsert 语义。提示词同理：与其写“发送日报”，不如写“确保今天的日报已发送且内容为最新汇总”——“确保”句式天然可重入。
3. **入口去重。** 插件的事件回调先按事件 ID 去重，通道重发就不会重复触发；再配一个简单的 JSON 或 SQLite 记“任务键 + 输入哈希”。但注意：记账和真正执行之间可能崩，账本只能减少重复，不能兜底。
4. **通知类任务降频聚合。** 按事件逐条推送天然容易重复，改成窗口聚合（每小时或每天汇总一次），重复的影响面会小很多。

## 踩坑点

- **让 LLM 自己判断“是否已做过”。** 模型会漏看、会幻觉，存在性判断必须走确定性的工具调用，不能靠模型看一眼。
- **并发竞态。** 两个实例同时“查了不存在，然后都去写”。简单做法是调度不重叠 + 任务加锁，别指望“不会那么巧”。
- **时间主键没固定时区。** “今天”在重启前后、跨机器可能不是同一天。
- **多层重试叠加。** HTTP 客户端在重试、Agent 在重试、调度器也在重试，幂等要保证的是任意组合下结果一致。

## 可复用建议

- 心态上默认：任何自动化任务总有一天会跑两次，按这个假设设计。
- 词表替换：create → upsert，追加 → 对账，逐条通知 → 聚合摘要。
- 验收动作很简单：测试环境把同一任务连跑两遍，diff 前后状态。跑两遍还干净，才算及格。

## 总结

幂等不是调度器给你的保证，而是你写进任务定义和工具实现里的属性。把“做某事”改写成“让世界达到某个状态”，重试、重启、补跑就从风险变成了无害操作——这也是自动化敢长期无人值守的前提。
