# 自动化任务的幂等性：重复执行不该靠运气

在 OpenClaw、Agent、MCP 插件和自动化实践里，任务被重复触发不是小概率事件，而是一种常态。用户可能连续点了两次按钮；调度器超时后重试；Webhook 因为对端没收到 200 而重新投递；Agent 在一次规划里重复调用同一个工具；MCP 客户端因为网络抖动重新发起请求。

如果你写的任务默认“一次执行只发生一次”，那么重复执行时就会出问题：重复插入数据、重复发送通知、重复调用外部 API、计数被多加、状态被旧数据覆盖。更麻烦的是，有些失败发生在“写库成功、通知失败”这种半成品状态，重试时又写一遍，造成部分重复。

幂等性不是高深概念，它只是回答一个问题：**同一份输入重复执行多次，结果和副作用是否仍然正确。**

## 问题：非幂等任务长什么样

一个典型场景：用 OpenClaw 写了一个自动化，收到 GitHub issue 事件后自动打标签并评论。如果 Webhook 重试或队列重复消费，脚本没有幂等保护，就会给同一个 issue 重复评论、重复打标签。

另一个常见场景：Agent 调用一个 MCP 工具 `create_row`。第一次调用其实已经成功，但响应超时，Agent 判定失败并重试，于是表里出现两条几乎一样的记录。这类问题在长链路里非常隐蔽：前面步骤成功，后面步骤失败，重跑整个流程就会放大副作用。

常见的非幂等写法：

- 每次执行都生成新 ID，直接 insert；
- 先发通知再写库，或先写库再发通知，但没有统一事务；
- 用“当前时间 + 随机数”作为去重键，重试时无法识别；
- 认为只有创建操作需要幂等，更新、删除、计数同样可能重复。

## 做法：把“可重复执行”设计进去

### 1. 给任务一个稳定幂等键

幂等键必须是同一次业务动作在多次执行中保持不变的标识。优先使用业务单号、事件 ID、`source + external_id`。例如 GitHub issue 可以用 `repo + issue_number + event_type + action`，或直接用 webhook 的 `x-github-delivery`。OpenClaw 流程启动时也可以生成 `run_id`，但重试时要沿用同一个 `run_id`。

不要用时间戳、随机数或数据库自增 ID 做幂等键，因为它们每次执行都不同。

### 2. 在入口做“已处理”检查

用一个轻量存储保存幂等键状态，例如 SQLite、Redis 或本地文件。执行前先检查：

- 如果 key 不存在，标记为 `processing`，然后执行；
- 如果 key 已经是 `done`，跳过执行，或返回上次缓存的结果；
- 如果 key 是 `processing`，说明正在执行，需判断是否超时，避免死锁。

SQLite 可以用一张表：

```sql
CREATE TABLE idempotency_keys (
  key TEXT PRIMARY KEY,
  status TEXT NOT NULL, -- processing | done | failed
  result TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

Redis 可以用 `SET key value NX EX 300` 抢占，执行完更新状态。

### 3. 对副作用分组处理

把副作用分成两类：能先检查的，和只能执行一次的。

- **能先检查的**：调用外部 API 前先查询当前状态。比如打标签前先 `get labels`，评论前先 `search comments`。MCP 工具如果支持 `upsert` 或 `get_or_create`，优先使用。
- **只能执行一次的**：如发送短信、扣库存、触发下游任务。这类操作需要配合幂等键和状态记录，执行前先确认未执行过。

### 4. 让操作本身可重复

如果无法完全避免重复，就把操作做成可重入。例如：

- 用 `INSERT ... ON CONFLICT DO UPDATE` 代替纯 `INSERT`；
- 更新时带上版本号或条件，避免旧状态覆盖新状态；
- 记录操作日志，即使重复执行也能追踪和补偿。

### 5. 测试幂等

写自动化测试或手动验证时，把同一个输入执行两次，断言：

- 最终状态一致；
- 外部副作用只发生一次，如只发了一条评论、只创建了一条记录。

这个测试应该成为插件和流程的标准检查项。

## 踩坑点

1. **把前端防抖当幂等**。按钮禁用只能防用户双击，防不住队列重试、Webhook 重复投递、Agent 重规划。

2. **“先检查后执行”不是原子操作**。并发场景下两个执行都通过了检查。需要唯一索引、分布式锁或原子抢占。

3. **用自增 ID 做幂等键**。重试时记录还没创建，或者两次执行生成不同 ID。

4. **processing 状态不释放**。任务崩溃后，key 永远停在 `processing`，后续执行全部阻塞。需要为 processing 设置过期时间或租约。

5. **盲目缓存结果**。某些结果包含时效性信息或敏感数据，缓存返回可能造成脏读或泄露。

## 可复用建议

- 在 OpenClaw 流程里，把 `idempotency_key` 作为每个 step 的 context 必备字段，写进插件和工具的约定。
- MCP 工具设计时尽量暴露 `upsert` 或 `get_or_create` 语义，并在工具描述里说明重复调用是否安全。
- 外部 API 封装时记录 `request_id`，方便对端去重。
- 重试策略要设上限和退避，不要无限重试；失败后保留状态和错误信息，便于人工介入。
- 执行日志里记录幂等键、输入摘要、输出摘要和耗时，排查重复问题时非常有用。

## 总结

自动化任务的可重复执行能力，不是某个复杂系统才需要的东西。只要你的流程可能被重试、被重复触发、被并发调用，就应该在设计时问一句：**这段逻辑跑两次，会不会出问题？**

在 OpenClaw、Agent、MCP 这类链路里，重复执行是常态。幂等性不是附加功能，而是自动化可靠性的基础设施。把幂等键、状态检查、可重入操作和重复执行测试纳入日常工程习惯，能避免大量难以排查的“偶发重复”问题。
