## 背景

我的订阅源分散在技术博客、安全公告、产品更新和几个垂直社区。每天新增几十条，真正值得点开的不到十分之一。RSS 阅读器解决了聚合，但没解决筛选和消化。后来尝试“AI 读全文再总结”，发现不稳定、贵，而且经常被长文或垃圾内容拖慢。

在 OpenClaw 这类 Agent 环境里，这类需求更适合拆成一条可重试、可观测、可复用的管线，而不是单次脚本或一次性 prompt。

## 问题拆解

核心矛盾不是“AI 能不能摘要”，而是：

- 原始 RSS 质量参差，正文提取失败率高；
- LLM 输出不结构化，后续无法自动过滤；
- 任务必须幂等、可重试，否则容易重复推送或漏推；
- 一旦源变多，状态管理、成本和可维护性会迅速恶化。

所以目标是：把 RSS、正文提取、LLM 摘要、过滤推送串成管线，每一步都能独立调试和恢复。

## 做法 / 步骤

### 1. 采集与正文提取

用 `rss-parser` 抓源，设置 timeout、UA、ETag/Last-Modified 做增量更新。很多 RSS 只给摘要，需要正文。优先使用 RSSHub 路由获得全文或稳定输出；备选方案是用 Readability / Mozilla Readability 从原文 URL 提取。

提取后做一次清洗：去掉脚本、导航、广告、空段落，并限制最大长度，例如 6000 tokens。原始数据（feed_id、link、pubDate、title、content_hash）持久化到 SQLite。

### 2. 去重与状态机

按 `link` 的 sha256 做唯一键。新增内容先入库，状态为 `pending`。标题相似度可用 simhash 或 MinHash 去近重复，但只在同一 feed 内做阈值过滤，避免把同一事件的后续更新误杀。

每次运行只处理状态为 `pending` 且未超过重试上限的条目。所有状态变更必须落盘，不能只放在内存里。

### 3. AI 摘要与打标

不建议把所有条目一次性塞给模型。可以每次取 5–10 条，使用 OpenClaw 的 Agent 调度 LLM。prompt 强制输出 JSON：

- `summary`：不超过 100 字；
- `tags`：标签数组；
- `relevance_score`：0–10；
- `worth_reading`：布尔值；
- `reason`：判断理由。

模型用轻量级或中等规模即可，温度设低。加 JSON schema 校验，失败重试一次，再失败就标记为 `failed` 并保留原文，不推送。摘要要保留事实，不要生成不确定信息；相关度评分要基于用户提供的关注方向。

### 4. 过滤与推送

设置 `relevance_score >= 7` 且 `worth_reading = true` 才推送。推送适配器可以是 Telegram、飞书、邮件或 Notion。模板固定：标题、来源、摘要、标签、原文链接、评分。

推送前做幂等检查，记录 `delivered_at`，避免重复发送。可以先增加 dry-run 模式，输出到本地 Markdown 或终端，确认过滤逻辑正常再开放真实推送。

## 踩坑点

- **正文提取失败率比想象高**：很多站点反爬或需要 JS 渲染。提取失败时不要强行丢给 AI，先标记 `skip`，或只使用 RSS 摘要。
- **LLM 输出不稳定**：即使声明了 JSON schema，也可能出现多余文本、字段缺失。解析器要容错，优先提取第一个 JSON 块。
- **长文截断导致摘要失真**：可以在输入前按段落压缩，或者在 prompt 里要求“只提取与关注方向相关的部分”。
- **抓取频率与封禁**：RSS 抓取间隔不要低于 30 分钟，对同一域名做并发限制。
- **状态丢失**：重启后 `pending` 和 `delivered` 状态必须能从数据库恢复，否则会重复处理或漏推送。
- **成本**：不要对每篇文章都调用大模型。先用规则过滤明显无关内容，再用小模型初筛，最后大模型精读。

## 可复用建议

- 将 RSS 抓取、正文提取、LLM 摘要、推送分别封装成 MCP tools 或 OpenClaw plugin，例如 `rss_fetch`、`extract_content`、`llm_summarize`、`push_digest`，便于单独调试和复用。
- 所有步骤输出结构化日志，每条目有 `run_id`、状态、耗时、模型用量。
- 保留原始数据，AI 摘要可以随时重跑，不需要重新抓取。
- 设置每日限额和告警：例如每日最多处理 200 条，失败率超过 10% 通知。
- 从 3–5 个高质量源开始跑通，再逐步增加源，不要一次性接几十个。

## 总结

RSS + AI 摘要的自动化信息流管线，价值不在“接入 AI”，而在于把不稳定、长链条的任务变得可维护。关键动作是：正文清洗、状态持久化、结构化输出、幂等推送、可观测性。先把这些基础做好，后续再扩展成 Agent 自动筛选、自动归档，会更顺手。
