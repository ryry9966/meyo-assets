# 自动化日报生成：从原始日志到结构化报告的流水线

## 背景

维护多个服务或 Agent 应用时，每天早上的第一件事往往是翻日志、看告警、对聊天记录、整理“昨天发生了什么”。这些信息散落在多个系统里：应用日志、网关访问日志、任务调度记录、MCP 调用链、插件的调试输出。原始信息量大，但真正需要日报呈现的只有一小部分。

如果每天人工重复这件事，不仅耗时，而且容易漏掉关键异常。我们实际跑了一套日报自动化流水线，核心思路不是“把日志丢给 LLM 让它写”，而是先把原始日志压缩成结构化中间层，再交给 Agent 做摘要和输出。

## 问题

直接拿原始日志做日报，通常会遇到几个具体问题：

1. **上下文爆炸**：单日日志可能几十 MB，直接喂给 Agent 会超出 token 限制，或者混入大量重复模板信息。
2. **统计不可靠**：让 LLM 直接从日志里数“错误数”“P95 延迟”，很容易因为日志截断或上下文丢失产生幻觉。
3. **时区和去重**：日志系统可能用 UTC 记录，业务视角却按本地时间，直接切割窗口会错位；重复采集也会造成事件重复计数。
4. **敏感信息**：日志里可能有用户 ID、token、内部路径，不能原样进入日报。
5. **失败难追踪**：日报生成失败后，如果没有保留原始结构化数据，很难知道是采集丢日志，还是摘要阶段出错。

## 做法

我们没有一步到位做“智能日报”，而是把它拆成五步，每步都相对确定。

### 1. 采集与切分

用脚本或插件从日志源按时间窗口拉取数据。常见源包括 Loki、Elasticsearch、CloudWatch、本地文件、MCP server 暴露的查询接口。统一转成 JSON 行格式，保留 `trace_id`、`service`、`level`、`timestamp`、`message` 这些基础字段。

时间窗口用本地时区计算起始和结束时间，再转成日志系统使用的时区，避免 8 小时错位。

### 2. 清洗与结构化

这一步尽量用规则完成，不要依赖模型。用正则或解析器提取：

- 错误码、异常类型
- 接口路径、耗时
- 涉及的 Agent 任务或插件名
- 用户影响面字段，如 `affected_user_count`

同时做两件事：**过滤噪声**（健康检查、心跳、重复 DEBUG）和**脱敏**。脱敏最好在进入中间层之前完成，后续所有导出都自动脱敏。

### 3. 聚合与预计算

在生成报告前，先确定性地算好指标：

```text
错误总数、按服务/错误码分组
P95 / P99 延迟
变更记录条数
告警触发次数
失败任务列表及 trace_id
```

这些数字不要交给 LLM 去数，而是由代码统计好，作为结构化数据传给 Agent。LLM 的职责只放在“趋势判断”“异常解释”“明日关注”这类主观部分。

### 4. 生成日报骨架

固定日报模板，减少 Agent 自由发挥空间。示例结构：

```markdown
## 昨日概览
- 总请求量 / 错误率
- P95 延迟
- 变更与发布

## 异常与风险
- 错误码 TOP3
- 关联告警
- 需人工关注的事项

## 自动化任务
- 成功 / 失败 / 重试情况

## 结论与建议
- 由 Agent 生成，只基于上游结构化数据
```

我们会在 prompt 里明确约束：不要新增没有出现在结构化数据里的数字；如果信息不足，写“数据不足”，不要补齐。

### 5. 推送与留档

日报生成后推送到钉钉/企业微信/Slack 或邮件。落盘时保存两份：

- `report.md`：给人看的报告
- `report.json`：结构化中间层，包含原始统计与关键日志索引

这样某天日报异常时，可以直接检查 JSON，不用重新跑全量日志。

## 踩坑点

1. **不要让 LLM 做算术**。把计数、求和、百分位提前算好，这个坑最常出现。
2. **时区不统一**。日志系统 UTC，业务本地时区，切割窗口要显式转换，否则日报内容会错位一天。
3. **重复日志导致重复计数**。同一事件可能从多个通道上报，需要在结构化时按事件 ID 去重。
4. **模板太松导致报告风格漂移**。一旦放开自由格式，Agent 可能会写得很长但信息密度低。固定字段和小节标题后，质量明显稳定。
5. **只保留 Markdown 不保留中间层**。后续排障会非常痛苦，建议 JSON 中间层和 Markdown 一起存。
6. **敏感信息脱敏位置太晚**。如果脱敏放在 LLM 之前，即使 prompt 泄露或模型出错，原始敏感信息也不会进入报告。

## 可复用建议

- **先做结构化中间层，再引入 Agent**。结构化数据是整条流水线的契约，不应随意改变 schema。
- **用 MCP 暴露日志查询工具，而不是复制日志**。Agent 需要更多上下文时，通过 MCP 按条件查，而不是把整包日志塞进 prompt。
- **日报模板与统计逻辑分开维护**。模板调整不应影响统计，统计错误也不该让日报整体失败。
- **保留 trace_id 和原始日志链接**。日报里看到异常，一键跳回现场，比复制错误文本有用得多。
- **设置阈值与异常标记**。比如错误率超过 1% 或 P95 突增时，在日报顶部自动标红，而不是让读者自己发现。

## 总结

自动化日报的关键不是让 Agent 更“聪明”地读日志，而是先通过规则和结构化把噪声压下去，让 Agent 只处理它擅长的部分：归纳、解释和建议。这样整条流水线可控、可复现，也更容易排障。对于 OpenClaw / Agent / MCP 场景，这套方法同样适用，尤其是当你已经有日志或任务执行记录，但每天还在手工汇总时，值得先做一版最小流水线：采集 → 结构化 → 统计 → 固定模板 → 推送。跑通后，再逐步引入更复杂的分析与联动。
