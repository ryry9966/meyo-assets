## 背景

在 OpenClaw 的 Agent 实践中，很多自动化任务都依赖外部 API：天气、翻译、支付、数据查询、模型推理。外部 API 并不总是可靠，超时、429、5xx、连接重置、返回半截 JSON 都是常见的工程问题。

如果只把外部调用包成一个 MCP 工具或插件函数，然后交给 Agent 自己判断错误，很快会遇到两类问题：一是 Agent 反复重试，消耗 token 还把第三方服务打挂；二是异常被吞掉后返回空结果，Agent 误以为“没有数据”，继续执行后续逻辑，造成静默错误。

真正可靠的错误恢复，应该放在确定性的代码层，而不是让模型在对话循环里即兴发挥。

## 问题

典型场景：一个定时任务让 Agent 抓取某个 API 的数据，写入本地库。API 突然 500，或者网络抖动超时。此时常见的失败模式有：

- 所有请求都盲目重试，包括 401/403 这类不应重试的错误。
- 重试没有退避，多个并发任务同时打同一个接口，形成重试风暴。
- 外部 API 挂掉后，工具返回空列表，Agent 认为“确实没有新数据”。
- 超时设置过长，Agent 卡在某个工具调用上，整个任务队列被堵住。
- 降级逻辑没有标记数据来源，下游把缓存或兜底数据当成实时数据使用。

## 做法 / 步骤

### 1. 先定义统一的外部调用结果结构

不要直接把 `fetch` 的异常抛给 Agent。建议在插件或 MCP server 内封装一层，返回结构化结果：

```ts
type ExternalResult<T> =
  | { ok: true; data: T; source: "live" | "cache" | "fallback"; stale?: boolean }
  | { ok: false; error: ExternalError };

type ExternalError = {
  code: "TIMEOUT" | "RATE_LIMITED" | "UPSTREAM_5XX" | "BAD_REQUEST" | "AUTH_FAILED" | "NETWORK";
  retryable: boolean;
  message: string;
  requestId?: string;
};
```

这样 Agent 看到的不是一堆异常文本，而是一个可以决策的结构化信号。

### 2. 在工具层做超时、重试、熔断

不要把重试逻辑写在 Agent 的 prompt 里。工程上更合理的是放在插件或 MCP server 的外部调用客户端中。

建议策略：

- 超时：单次请求 10 秒左右，避免任务长时间挂起。
- 重试：只对超时、网络错误、429、5xx 重试。401/403/400 不重试。
- 退避：指数退避加 jitter，比如 base 200ms，max 2s，最多 3 次。
- 熔断：连续失败 5 次后打开熔断器，30 秒内直接失败，不请求上游。
- 半开：熔断时间过后，只放一个请求探测，成功则关闭，失败则继续熔断。

这些逻辑可以用一个小型 client wrapper 统一实现，所有外部 API 调用都走这个入口。

### 3. 准备降级路径

外部 API 挂掉时，Agent 不应该直接失败退出，也不应该假装成功。比较实用的降级策略：

- 缓存降级：本地缓存过期后，如果外部请求失败，返回最后一份成功数据，并标记 `stale: true`。
- 静态兜底：对非关键数据返回默认值或空结果，但必须在结构里标明 `source: "fallback"`。
- 延迟处理：把失败任务写入队列或状态表，稍后重试，而不是让 Agent 死等。

例如 MCP 工具返回：

```json
{
  "ok": true,
  "data": { "price": 12.4 },
  "source": "cache",
  "stale": true
}
```

Agent 可以根据 `stale` 字段调整话术，比如告诉用户“当前数据可能不是最新”。

### 4. 持久化任务状态

如果任务链路较长，不要在 Agent 对话循环里直接做外部调用后继续执行关键写操作。推荐把外部调用放在独立步骤，状态落库：

- `pending`：待调用
- `retrying`：失败重试中
- `degraded`：已降级
- `failed`：最终失败
- `succeeded`：成功

这样即使进程重启，任务也不会丢失，也方便后续补跑。

### 5. 可观测性

每次外部调用至少记录：

- 请求 URL 或 API 名称
- 耗时
- 状态码或错误码
- 是否命中缓存 / 降级
- request_id

这些日志可以帮助定位是上游挂了、自身超时配置问题，还是 Agent 误用了工具。

## 踩坑点

- **让 LLM 根据错误文本自行重试**：很容易变成死循环，或者模型自己“脑补”修复方式，重复调用同一个坏接口。
- **所有异常都重试**：401/403 重试只会浪费配额，甚至触发账户风控。
- **重试没有 jitter**：多个任务同时重试，容易把上游服务打成雪崩。
- **超时时间太长**：Agent 卡在工具调用上，整个自动化流程被拖死。
- **降级不标记来源**：下游逻辑把过期缓存当成实时数据，产生错误决策。
- **MCP 工具异常被吞掉返回空数组**：Agent 会认为“没有数据”，然后正常结束，属于静默故障。
- **只处理失败，不处理半成功**：外部 API 可能返回 200 但 body 不完整，需要做 schema 校验。

## 可复用建议

1. 封装一个统一的 `externalClient`，所有外呼都经过它，内部统一处理超时、重试、熔断、错误分类。
2. 给 Agent 的错误信息里包含 `retryable`、`reason`、`requestId`，让模型做有限决策，而不是无限重试。
3. 关键流程使用队列或状态表，避免外部调用直接嵌在 Agent 的对话循环里。
4. 对重要数据开启 stale-while-error 缓存：失败时先返回旧数据，后台异步刷新。
5. 提供降级开关，外部依赖异常时可以手动或自动切到兜底模式。

## 总结

外部 API 挂掉不是偶发事故，而是自动化系统必须面对的常态。Agent 的错误恢复能力，核心不在于让模型更聪明地处理错误文本，而在于把重试、熔断、降级、缓存、状态持久化做成确定性的工程基础设施。

在 OpenClaw 的插件或 MCP server 里做好这一层，Agent 才能稳定地跑下去，而不是每次外部依赖一抖动，就把自动化流程变成一场重试风暴。
