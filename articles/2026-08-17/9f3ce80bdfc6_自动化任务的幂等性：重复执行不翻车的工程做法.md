# 自动化任务的幂等性：重复执行不翻车的工程做法

在 OpenClaw / Agent / MCP 这类自动化链路里，重复执行不是偶发事故，而是常态。定时任务可能重叠，Agent 调用 MCP 工具可能超时后重试，插件可能因为服务重启重复消费事件。真正决定系统稳不稳的，不是“能不能避免重复执行”，而是“重复执行之后结果是否还正确”。

## 背景：重试是常态，不是 bug

一个典型的场景：Agent 调用 `create_issue` 创建工单，MCP server 响应超时，Agent 判断失败并自动重试。第一次调用其实已经创建成功，第二次又创建一条，用户看到两条一模一样的工单。类似问题也会出现在订单同步、通知发送、文件生成、数据写入等任务里。

非幂等自动化带来的问题包括：重复创建资源、重复扣款或计费、重复发送通知骚扰用户、覆盖有效状态、统计数据翻倍。只要系统允许重试，就必须默认任务可能被执行多次。

## 问题：为什么“查一下再写”还是不够

不少插件会先查询目标是否已存在，不存在才写入。但“查询—判断—写入”不是一个原子操作。并发场景下，两个执行实例同时查到不存在，然后都写入，仍然会产生重复数据。另外，如果只用随机生成的 `uuid4()` 作为每轮调用的标识，重试时每次都会生成新 ID，幂等逻辑完全失效。

还有一类隐藏问题：有些团队只在业务主流程做了幂等，却忽略了日志、统计埋点、通知推送等附属副作用。结果主数据没问题，但用户收到两条“任务已开始”的通知，或者监控图表里的执行次数翻倍。

## 做法：把幂等做成基础设施

### 1. 为业务操作设计稳定的幂等键

关键不是“每次调用生成一个 ID”，而是“同一个业务操作重复执行时使用同一个 ID”。例如 `biz:order:PO12345:create`，或者用业务单号 + 操作类型组成确定性 key。MCP 工具可以在请求参数里接收 `idempotency_key`，服务端用它判断是否已经处理过。

### 2. 入口先检查执行状态

维护一张执行记录表，例如：

```text
task_executions(
  execution_key,
  status,        -- pending / running / succeeded / failed
  result_payload,
  created_at,
  updated_at
)
```

任务开始时，先尝试把记录置为 `running`。如果已有记录为 `succeeded`，直接返回之前的结果，不再执行副作用。这能覆盖大部分顺序重复调用。

### 3. 用数据库唯一约束兜底

只在应用层检查是不够的，拿唯一索引兜底才能应对并发。给执行表建：

```text
UNIQUE KEY (workspace_id, idempotency_key)
```

写入时使用 `INSERT ... ON CONFLICT DO NOTHING`，冲突就说明已经执行过，读取已有记录返回即可。这样即使两个执行实例同时进入，也只会有一个成功写入。

### 4. 副作用使用条件写入或状态机

更新数据时避免无条件 `set status = 'done'`。更安全的写法是：

```text
UPDATE tasks SET status = 'done'
WHERE task_id = ? AND status = 'pending'
```

有条件更新可以防止重复任务把已失败、已取消的单子直接改成完成。外部 API 调用如果不能天然幂等，则先查后写，并且把操作 ID 写在远端系统的自定义字段里，方便后续对账。

### 5. 重试策略区分错误类型

不是所有错误都该重试。超时、网络抖动、5xx 可以重试；明确的 4xx 业务失败、参数错误、唯一键冲突不应该盲目重试。重试时不要修改 payload，否则同一个幂等键对应的内容不一致，反而产生更难排查的问题。

### 6. 保留 operation_id 用于对账

所有关键写操作都记录 `operation_id`，写入日志、返回体、远端资源标记。出现重复数据时，可以快速定位是哪一轮执行、哪个 key 失效。对于无法回滚的外部系统，对账任务比死磕原子性更实用。

## 踩坑点

- 每次调用都生成新的 `uuid4()` 作为幂等键，等于没有幂等。
- 把时间戳放进幂等键，重试时间变了就重复执行。
- 只在 prompt 或注释里写“不要重复执行”，没有任何工程约束。
- 只检查不约束，并发时仍然双写。
- 忽略通知、统计、日志等附属副作用的幂等。
- 重试时改了请求体，同一个 key 对应不同内容，导致结果漂移。

## 可复用建议

在 OpenClaw 自定义工具或 MCP server 中，为所有写操作统一增加 `idempotency_key` 参数，并在服务端封装一个 `run_idempotent(key, fn)` 执行器。定时任务可以加 Redis `SET NX` 或数据库行锁防止重叠执行。每个自动化任务都应写一个“重复执行测试”：同一输入连续触发两次，断言业务结果数量为 1，并且第二次返回的是首次执行结果。

## 总结

自动化任务不可能保证只执行一次，但可以做到执行多次结果一致。幂等不是取消重试，而是让重试变得安全。把它作为 MCP、插件、Agent 工具的默认契约，而不是等到线上重复数据出现后再补救。让“重复执行不会出问题”成为可测试、可观测、可对账的工程标准。
