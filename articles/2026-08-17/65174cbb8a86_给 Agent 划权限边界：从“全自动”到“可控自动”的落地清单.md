# 给 Agent 划权限边界：从“全自动”到“可控自动”的落地清单

## 背景

OpenClaw 接入 MCP、插件和自动化脚本后，Agent 能做的事越来越多：读文件、查数据库、发消息、改配置，甚至操作云资源。但能力扩展也带来一个老问题：**哪些动作可以自己干，哪些必须停下来问人？**

如果默认全自动，一条错误指令可能删掉生产数据；如果默认全人工，Agent 又退化成聊天机器人。实际工程里，权限边界不是“要么全给，要么全锁”，而是按风险、可逆性、上下文置信度做分层控制。

## 问题

很多团队一开始只设两个档位：只读或全量。结果要么 Agent 什么都做不了，要么用户为了省事直接给最高权限。更麻烦的是，MCP server 来自不同来源，光看工具名很难判断副作用——`delete_file` 很明显，但 `run_query` 可能是只读，也可能触发存储过程写入。

核心问题可以拆成三个：

1. 哪些操作应该默认自动？
2. 哪些操作需要确认？
3. 确认到什么粒度，才不会让用户疲劳或盲目点同意？

## 做法/步骤

### 1. 给动作分风险等级

不要只分“读/写”，建议按四个等级落地：

- **L0 安全只读**：纯查询、读取本地文件、获取状态。自动执行，但需禁止携带凭据或敏感信息。
- **L1 低风险可逆**：创建临时文件、追加日志、发草稿消息。自动执行，但记录审计日志。
- **L2 中风险可逆/低风险不可逆**：修改配置、删除非关键数据、发送正式消息。需要人类确认。
- **L3 高风险/不可逆**：删除生产数据、转账、发布上线、修改权限。需要人类审批并二次确认。

这个分级可以写成策略文件，和代码分离。比如 YAML：

```yaml
default_risk: L2
tools:
  read_file: L0
  append_log: L1
  delete_file: L3
  send_message: L2
```

### 2. 让 MCP 工具声明副作用

MCP server 的 tool manifest 里，除 name/description 外，建议补充 `risk_level`、`side_effects`、`required_scopes`。OpenClaw 侧在调用前做策略检查：工具声明的等级超过当前允许阈值时，自动进入审批流程。

这里有一个关键点：**不要完全信任工具自报的等级**。实际落地时，可以在 MCP 客户端层做一层代理，强制把某些工具标记为高风险，或者对工具参数做白名单过滤。

### 3. 把置信度纳入决策

同一个动作，在不同上下文里风险不同。比如“删除 `/tmp/test.txt`” 和 “删除 `/data/backup/*`” 是完全不同的风险。可以在 Agent 决策链路里增加一个置信度判断：

- 目标明确、参数来自用户明确指令 → 高置信，可自动执行 L1/L2。
- 目标模糊、参数由 Agent 自己推断 → 降低自动权限阈值，建议询问。
- 涉及多步依赖、一旦失败需要回滚 → 提前生成执行计划，先给人类预览，再执行。

实现上，可以在 prompt 或 policy 里加入规则：**当置信度低于 0.8 或影响范围超过当前会话已确认范围时，必须询问。**

### 4. 设计可降级的审批流

审批不应该是简单的 yes/no。理想状态是：Agent 生成待执行动作，附上参数、理由、影响范围，人类可以：

- 批准
- 拒绝
- 修改参数后批准
- 临时授权同类操作 N 次或 T 分钟内有效

同时设置超时回退。人类 5 分钟没响应，默认拒绝并回滚到安全状态，避免 Agent 卡在等待里。

### 5. 记录审计日志

每次自动执行和审批决策都要留痕，至少包含：工具名、参数摘要、风险等级、决策来源（自动/人工）、时间戳、会话 ID。这样出了问题能复盘，也能根据历史数据调整策略。

## 踩坑点

### 误区一：把“只读”当绝对安全

有些 MCP server 的“只读”工具会触发缓存刷新、计费查询或返回敏感数据。最好区分 `read_only` 和 `safe_read`，后者才允许无审批自动执行。对于不熟悉的工具，默认按 L2 处理。

### 误区二：审批太密集，用户盲目点“同意”

如果每写一个文件都弹窗，用户很快会条件反射点同意。可以设置“限时授权”：用户确认一次后，同类低风险操作在 10 分钟内自动通过。同时把风险等级高的操作单独用更明显的确认方式，比如要求输入确认短语。

### 误区三：忽略会话上下文

上次会话里确认过的操作，不代表这次也安全。权限授权要带 scope 和 TTL，不能全局缓存“允许删除”。否则换一个项目，Agent 可能带着旧授权删掉别的目录。

### 误区四：MCP server 声明与实际行为不一致

有些插件声明 safe，实际执行写操作。如果可能，把 MCP server 跑在沙箱或容器里，限制文件系统、网络、环境变量访问。权限边界不仅靠声明，还要靠运行时隔离。

## 可复用建议

1. **把权限策略外置**：用 YAML/JSON 维护风险等级、默认策略、工具覆盖，不要硬编码在 Agent 代码里。
2. **默认最小权限**：先只允许 L0/L1，跑一段时间看日志，再逐步放宽到 L2。
3. **高风险动作先 dry-run**：能预览执行计划的先预览，尤其是删除、发布、批量修改类操作。
4. **在 MCP 客户端层做统一拦截**：不要每个工具自己实现权限检查，集中处理更可靠。
5. **定期复盘审批日志**：哪些操作经常被拒绝？哪些自动操作后来出了问题？用数据调整边界。

## 总结

Agent 权限边界不是一次性配置，而是一套持续迭代的工程策略。核心思路是：**按风险分层，结合上下文置信度，用可降级的审批流和审计日志保持人类控制权。** 目标不是让 Agent 永远不来打扰人，而是让它在可接受风险范围内尽量自主，同时保证每一次“自己干”都有据可查，每一次“问人类”都问在关键点上。
