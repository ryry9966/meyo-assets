## 背景

最近在 OpenClaw 里做资料整理自动化，场景是：给定一个项目名，需要同时收集 GitHub 仓库信息、官方文档更新、社区讨论摘要。如果让一个 agent 顺序跑，耗时长，而且抓回来的内容混在同一个上下文里，后面分析时很容易串味。

一开始的做法是写一个长 prompt，让主 agent 一步步执行。结果经常跑到第二步就开始等网页超时，或者第三步忘了第一步的结论。后来把任务拆成多个 subagent，让它们并行执行，主 agent 只做调度和汇总。效果比较明显，但坑也不少。

## 问题

单个 agent 处理可分解任务时，主要问题是串行等待和上下文污染。例如：

- 抓 GitHub 要 20 秒，读文档要 30 秒，分析社区要 15 秒，顺序执行至少 65 秒；
- 三个来源的内容混在一起，主 agent 容易把 A 项目的文档当成 B 项目的说明；
- 某个子任务失败，整个流程卡住，前面的工作也白做。

如果把任务拆成多个 subagent 并行执行，可以缩短总耗时，但也引入新问题：子 agent 输出结构不一致、并发写文件冲突、主 agent 上下文爆炸、部分任务超时拖累整体。

下面是我在 OpenClaw 中实践的一套做法。

## 做法/步骤

### 1. 定义子 agent 的能力边界

先为每类子任务建独立 session，不要共用上下文。每个 subagent 的 system prompt 只描述一类事，并限定工具权限。

例如：

- `gh-scout`：只负责查 GitHub 仓库信息，返回结构化数据；
- `doc-reader`：只负责读取指定 URL 的文档，提取更新时间、关键段落；
- `community-analyzer`：只负责分析社区讨论的 sentiment 和主要问题。

### 2. 主 agent 生成任务清单

主 agent 拿到用户输入后，先拆任务，输出结构化 JSON：

```json
{
  "tasks": [
    {"id": "github", "agent": "gh-scout", "input": "owner/repo"},
    {"id": "docs", "agent": "doc-reader", "input": "https://docs.example.com"},
    {"id": "community", "agent": "community-analyzer", "input": "project_name"}
  ]
}
```

这里关键是任务之间无依赖才能并行，有依赖就分批次执行。

### 3. 通过 MCP 工具或并行执行器调用 subagent

在 OpenClaw 中，我把 subagent 暴露成 MCP 工具，主 agent 通过 `mcp_call_tool` 调用。并发数控制在 2-3，不要一上来开 10 个，容易触发限流或资源争抢。

### 4. 约定子 agent 输出格式

每个 subagent 必须返回 JSON，字段固定：

```json
{
  "status": "ok",
  "summary": "一句以内的摘要",
  "key_facts": ["事实1", "事实2"],
  "error": null
}
```

要求输出前加 ```json 代码块，方便解析。主 agent 只读取 `summary` 和 `key_facts`，不读取全文。

### 5. 合并结果时只保留摘要

主 agent 把多个 subagent 的返回合并成一个最终报告。中间产出的全文内容让 subagent 自己写到独立临时文件，主 agent 需要时再读文件，而不是直接把全文塞进上下文。

## 踩坑点

- **输出格式漂移**：子 agent 有时不按约定返回 JSON，而是直接给 Markdown 段落。解决：在 system prompt 里给 few-shot 示例，并用正则剥离 ```json 代码块；解析失败就重试一次，并把失败样本记到日志。

- **并发写文件冲突**：多个 subagent 写同一个输出文件会互相覆盖。解决：每个 subagent 写独立文件或目录，最终由主 agent 合并。

- **超时拖累整体**：某个 subagent 卡在网页抓取，主流程一直等。解决：为每个任务设置独立超时，超时后标记为 `timeout`，不阻塞其他任务汇总。

- **主 agent 上下文爆炸**：如果直接拼接所有 subagent 返回全文，窗口很快耗尽。解决：只保留摘要字段，必要时把全文写盘，主 agent 按需读盘。

- **子 agent 幻觉未校验**：比如 GitHub 返回的内容被 agent 自由发挥。解决：对关键数据做确定性校验，能调 API 的就不让 agent 自己 “理解”，直接取结构字段。

## 可复用建议

- 把 subagent 编排抽象成技能或插件，不要在 prompt 里硬编码任务列表。
- 给每个 subagent 配置独立日志，记录耗时、状态码、错误信息，方便排障。
- 做依赖分析：无依赖的并行，有依赖的用事件或状态标记串行执行。
- 并发上限设为 2-3，优先保证稳定性和可观测性，而不是盲目压时间。
- 对关键结果做确定性校验，不要完全信任 agent 总结，尤其涉及数字、链接、版本号。

## 总结

Subagent 并行编排适合 I/O 密集型或可分解任务，能明显缩短总耗时，但复杂度转移到编排层。工程化的关键是控制上下文、约定输出结构、限制并发、独立文件隔离。如果任务本身是强推理链，拆分带来的收益不大，反而增加同步开销。实践时先把“并行”和“串行”边界想清楚，再动手写调度逻辑。
