## 背景

在 OpenClaw 里跑 Agent、MCP 插件和自动化任务时，很容易陷入两个极端：要么所有请求都压给 GPT，成本高、延迟不稳定；要么为了省钱把本地模型当万能替代，结果工具调用和复杂规划经常失败。

实际上，多数 OpenClaw 工作流并不是每个环节都需要强模型。真正需要 GPT 的是“想清楚怎么做”的部分，而“具体执行和清洗”部分，本地模型往往足够。本文将我们在 OpenClaw 中实践的一套多模型路由方案整理出来，重点说明什么时候该用 GPT，什么时候可以放心下沉到本地模型。

## 问题

OpenClaw 场景中，模型请求大致可以分成三类：

1. **规划与编排**：理解目标、拆解步骤、选择工具、处理异常。
2. **工具调用与 MCP 交互**：生成符合 schema 的 function call、解析工具返回。
3. **文本处理**：意图识别、实体抽取、摘要、格式转换、代码补全、分类。

第一类和第二类对指令遵循、上下文理解和稳定输出要求很高，本地模型尤其是 7B/14B 量化模型容易出错。第三类通常结构相对固定，输入输出模式清晰，是本地模型的甜点区。

如果不加区分，让本地模型直接驱动 MCP 工具或者做多步规划，很容易出现不按 schema 返回、漏参数、误解工具返回、重复调用甚至死循环。

## 做法 / 步骤

### 1. 先做任务分层，而不是直接写规则

我们把 OpenClaw 里的任务按“是否允许出错、是否需要工具编排、上下文长度”三个维度划分。

- **低风险、无工具、短上下文**：默认走本地模型。
- **高风险、涉及 MCP/插件调用、多步规划**：走 GPT。
- **长上下文或需要复杂推理**：即使没有工具也走 GPT。

这样划分比单纯按任务名称匹配更稳定。

### 2. 部署本地模型暴露 OpenAI 兼容接口

使用 Ollama 或 llama.cpp 部署本地模型，例如 `qwen2.5-coder-7b-instruct` 或 `qwen2.5-14b-instruct`。通过 FastAPI 包一层 OpenAI 兼容接口，方便接入 OpenClaw。

```text
POST /v1/chat/completions
POST /v1/completions
```

这样 OpenClaw 侧不需要区分云端与本地，统一走 OpenAI 格式。本地模型建议保持默认 temperature，避免随机性过大。

### 3. 在 OpenClaw 侧设置路由规则

OpenClaw 的配置里可以加一个路由层。下面是一个简化示例，字段名以你当前版本为准：

```yaml
routing:
  default: local
  rules:
    - name: planning_tool_orchestration
      when:
        task_type: [planning, multi_step, mcp_call]
      use: gpt-4o-mini
    - name: long_context
      when:
        min_input_tokens: 8000
      use: gpt-4o
    - name: local_safe_tasks
      when:
        task_type: [classification, extraction, summarization, code_completion]
        max_tool_calls: 0
      use: local
```

实际使用中，我们会在进入模型前先跑一个轻量分类器。分类器本身也由本地模型执行，只输出 `task_type`，不直接参与业务逻辑。这样分类成本极低，又能把 GPT 从简单任务里解放出来。

### 4. 设置失败回退与熔断

本地模型失败时不要立刻无脑切 GPT。先判断失败类型：

- **JSON/工具 schema 解析失败**：原样重试一次；如果仍失败，再切换 GPT，并带上错误信息。
- **超时或推理服务不可用**：直接走 GPT，同时记录本地服务健康状态。
- **连续失败达到阈值**：5 分钟内 10 次失败，暂时将默认路由切到 GPT，避免任务堆积。

这样既能保证稳定性，也能控制云端成本。

## 踩坑点

### 1. 不要让本地模型直接驱动 MCP 工具

本地模型在 function calling 上的 schema 遵循度不够稳定。我们在 `qwen2.5-coder-7b-instruct` 上测试，简单单工具调用还行，但涉及多工具选择、参数嵌套、工具返回理解时，失败率明显上升。解决方案是：MCP 调用、工具编排一律走 GPT；本地模型只负责无工具的预处理和后处理。

### 2. 上下文窗口差异

不少本地模型实际可用上下文只有 4K/8K，量化后还会进一步缩水。RAG 切片多的时候，本地模型很容易丢失中间信息。建议在路由规则里加上 `min_input_tokens` 判断，超过阈值直接走 GPT。

### 3. 关键字路由容易误判

早期我们按消息内容里是否包含“规划”“分析”等关键词分流，结果经常把简单分类误判成复杂规划。后来改为先让本地分类器输出 `task_type`，再由路由层根据类型决策，准确率提升很多。

### 4. 本地推理服务并发与显存

本地模型部署在单卡或消费级 GPU 上时，并发一高就会排队。OpenClaw 里大量异步任务同时进来，本地模型可能成为瓶颈。建议：

- 限制本地模型并发请求数；
- 超过并发上限的请求直接走 GPT，而不是等待；
- 本地服务只处理短平快任务，长生成任务另行排队。

### 5. 回退费用容易失控

如果不对回退次数做限制，一次活动可能让本地模型反复失败、反复切换 GPT，最终成本反而更高。我们在路由层加了计数和预算：每个任务类型单独记录回退次数，超过预算后改为直接 GPT 并告警。

## 可复用建议

1. **默认本地，复杂云端**：把默认模型设为本地，规则只把复杂任务提级到 GPT。这样简单任务天然省钱，复杂任务也不会漏。
2. **本地模型先做分类，再做路由**：用本地小型模型输出任务类型、风险等级、预期工具调用数，路由层据此判断。
3. **统一 OpenAI 兼容接口**：云端和本地模型使用同一套调用格式，降低切换成本。
4. **记录维度要全**：至少记录 `model`、`task_type`、`input_tokens`、`output_tokens`、`latency`、`success`、`fallback_reason`。有这些数据才能回头优化路由规则。
5. **定期回测本地模型能力**：每月用固定评测集跑一次本地模型，特别是工具调用和 JSON 输出稳定性。如果本地模型在某一类任务上成功率长期低于 95%，就把这类任务永久提级到 GPT。

## 总结

多模型路由不是简单把 GPT 换成便宜的本地模型，而是让云端负责“想”，本地负责“做”。在 OpenClaw 的 Agent、MCP、插件、自动化场景里，规划、工具编排和异常处理交给 GPT；分类、抽取、补全、摘要这些确定性强、模式清晰的任务交给本地模型。

我们最终的目标是：在稳定性和可观测性不下降的前提下，把简单任务的单位成本降下来，同时让 GPT 集中在真正需要强推理的环节上。这样既能控制成本，也能减少不必要的延迟和失败风险。
