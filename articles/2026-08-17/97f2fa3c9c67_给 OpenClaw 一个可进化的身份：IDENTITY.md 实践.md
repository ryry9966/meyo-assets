## 背景

在 OpenClaw 里跑 Agent、MCP、插件和自动化任务时，最常见的问题不是模型能力不够，而是每次新会话都要重新交代“我是谁、我在哪、能做什么、不能做什么”。这些信息通常散落在 system prompt、规则文件、插件配置和对话历史里，时间一长就会出现冲突：同一台机器上的 Agent，有时很守规矩，有时却会越过边界。

## 问题

身份信息分散会带来几个直接后果：

- 行为漂移：同一个任务，不同会话的表现不一致。
- 调试困难：出问题时，你不知道 Agent 当时的运行边界到底是什么。
- 更新成本高：改了一处提示词，其他位置还是旧规则。
- 权限失控：工具权限和文件路径写在多个地方，很难收口。

解决思路不是继续加提示词，而是把“身份”收敛到一个可维护、可版本化的文件里。

## 做法/步骤

### 1. 建立最小 IDENTITY.md 结构

不要写散文，写运行事实。建议包含六个区：身份、工作目录、能力清单、边界、失败处理、修订记录。

```markdown
# IDENTITY.md
---
version: 1.3.0
updated: 2025-01-20
role: local-automation-agent
---

## 我是谁
- 运行环境：Linux / macOS
- 工作目录：/home/user/openclaw-workspace
- 主要任务：定时抓取 RSS、整理 Markdown、执行本地脚本

## 能力
- 可执行：python3, node, pandoc, git
- 可用 MCP：filesystem, fetch, sqlite

## 边界
- 禁止修改 /etc、~/.ssh
- 写文件前先输出 dry-run 结果
- 网络请求仅允许白名单域名

## 失败处理
- 连续失败 2 次后停止并输出诊断
- 不自动重试删除、支付、发送类操作
```

### 2. 让 OpenClaw 在会话启动时加载

可以在配置中指定身份文件：

```yaml
identity:
  file: ./IDENTITY.md
  reload_on_change: true
  auto_review: true
```

或者使用 bootstrap 指令，在每次会话开始时显式读取：

```text
/session load ./IDENTITY.md
```

关键是：加载必须发生在任何工具调用之前。否则边界形同虚设。

### 3. 版本化与人工审批

不要把 IDENTITY.md 设成 Agent 可直接改写。更好的方式是让它提出修改建议，生成 diff，人工合并。例如：

```text
建议将“允许域名”增加 api.example.com
理由：RSS 抓取任务新增了该数据源
```

### 4. 动态状态外置

身份文件只写稳定的身份信息，不写今天抓了几条、上次失败时间。动态状态放到 `state.json` 或任务目录，避免身份文件频繁变化。

## 踩坑点

- **文件过长**：超过 150 行后，Agent 会抓不住重点。建议控制在 80–120 行。
- **路径写死**：不同机器路径不同。尽量用环境变量或相对路径，例如 `$WORKSPACE`。
- **加载时序错误**：如果 Agent 在身份加载前就开始执行，边界不会生效。用最小启动脚本验证加载顺序。
- **多份身份文件**：不要同时维护 system prompt、rules.md、IDENTITY.md 三份重复内容。选 IDENTITY.md 作为唯一事实源，其他位置只引用。
- **过度拟人化**：写“你是一个严谨的工程师”不如写“写文件前先 dry-run，禁止删除 .git 目录”。运行边界比人格描述更有效。

## 可复用建议

- 把 IDENTITY.md 纳入 git 仓库，变更要有 commit message。
- 每两周做一次身份审计：删除不再使用的工具权限、更新过时路径。
- 设置 `auto_review: true`，让 Agent 在每次会话结束时检查自己是否越界，并输出一行审计结果。
- 对危险操作采用“默认拒绝”，而不是“默认允许再约束”。

## 总结

IDENTITY.md 的价值不是让 AI 有“人设”，而是给 OpenClaw 一个可版本化、可审查、可回滚的运行身份。它解决的不是“AI 不够聪明”，而是“AI 的行为不可预测”。把身份文件当成代码维护，Agent 才会真正像一个可控的自动化组件。
