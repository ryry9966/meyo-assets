## 背景

给 Agent 接上 MCP、插件和自动化脚本之后，最容易被忽略的问题不是“它能不能做”，而是“它应不应该直接做”。

权限给少了，每一步都要确认，Agent 退化成一个带对话界面的手动触发器；权限给多了，一次误判、一个提示词注入、一个工具描述偏差，就可能变成不可逆操作。尤其在 OpenClaw 这类允许 Agent 组合多个 MCP 工具、执行长链路任务的场景里，权限边界不是安全部门的理论题，而是每个自动化实践者都要自己画清楚的工程线。

## 问题

“什么时候该问人类”没有统一答案，因为风险取决于操作类型、影响范围、可逆性、上下文和成本。但如果不提前定规则，就会陷入两种常见失败：

- **过度确认**：连读文件、查状态都要点同意，自动化失去意义。
- **过度放权**：Agent 在会话内被诱导后执行删除、推送、付费调用，事后才发现权限早已越界。

所以需要一个简单、可落地、不依赖模型自觉的决策框架。

## 做法：三层权限模型

我目前在用的方式是把工具调用分成三类：自动执行、确认后执行、拒绝/审批后执行。判断顺序固定，避免每次临时拍脑袋。

### 1. 先问三个问题

面对一个工具调用，先过三道判断：

1. **是否只读？**  
   只读操作通常风险较低，但不是绝对安全，后面会讲。

2. **是否可逆？**  
   创建、修改、删除、推送、发送，可逆性依次下降。可逆操作可以更宽松。

3. **影响范围是否受限？**  
   只影响单个测试文件、临时容器、个人日历，风险低；影响共享目录、生产数据库、公开仓库、付费 API，风险高。

### 2. 按风险分层

根据上面的判断，可以做一个简单的表格：

| 操作类型 | 例子 | 默认策略 |
|---|---|---|
| 只读且范围小 | 读本地配置、查日历、git status | 自动执行 |
| 可逆写入 | 写临时文件、创建草稿、本地分支 | 自动或日志告警 |
| 不可逆/高成本 | 删除文件、git push、发邮件、付费 API | 确认后执行 |
| 高风险/权限变更 | 批量删除、修改权限、生产部署、删除远端资源 | 拒绝或人工审批 |

这个表格不要只写在文档里，要落到工具策略配置里。例如在 OpenClaw 的 MCP 工具层可以做类似限制：

```yaml
tool_policies:
  file_read:
    default: auto
  file_write:
    default: confirm_if_path_outside_workspace
  shell:
    default: confirm
  http_request:
    default: confirm_if_host_not_in_allowlist
  github_push:
    default: confirm
  github_delete_repo:
    default: deny
```

关键点：**策略要参数级，不能只到工具名粒度**。`file_read` 和 `file_delete` 必须分开；甚至同一个 `shell`，执行 `ls` 和执行 `rm -rf` 的风险也完全不同。如果工具策略不支持参数级判断，就尽量拆成更细的工具或包一层前置校验。

### 3. 确认机制不要做成“一次性开关”

很多 Agent 运行环境支持会话内确认一次后，后续同类操作不再询问。这个设计很方便，但容易出问题。建议把授权作用域控制在“短时间 + 明确目标 + 限定参数”内，而不是“整个会话”。

例如：“允许在 `/tmp/agent-test/` 下写文件，10 分钟内有效”，比“允许文件写入”安全得多。如果运行环境不支持这种细粒度授权，就自己在工具描述和系统提示里写明边界，并在关键步骤前强制重新确认。

## 踩坑点

### 1. 以为“只读”等于安全

只读操作也可能泄露敏感信息、消耗大量配额，或被用来探测内网。一个“读取网页内容”的 MCP 工具，如果被提示词注入指向 `http://169.254.169.254/latest/meta-data/`，就可能把云环境元数据带出来。只读工具也要做域名/路径白名单和返回内容过滤。

### 2. 让模型自己判断风险

模型会推理，但也会被上下文带偏。不能把权限判断完全交给 Agent 的“自觉”。权限策略应该由外部配置强约束，模型只负责选择调用哪个工具，不负责判断这个工具此刻是否危险。

### 3. 工具描述与真实能力不一致

MCP server 的工具描述如果写得太宽泛，模型会误解能力。比如描述写“执行系统命令”，实际只应该允许执行特定脚本。描述必须与实际权限一致，否则模型很容易越界调用。

### 4. 批量任务里的确认疲劳

批量操作时，用户连续点了几十次“同意”后，基本不会再认真看。重要操作不应该靠高频确认来保底，而是应该在批量任务开始前做一次总确认，并明确任务边界。任务执行中出现边界外操作，直接中止，而不是逐条确认。

### 5. 缺少审计和回滚

即使有确认，也可能点错。关键写操作要有日志、dry-run 或回滚方案。比如删除前先移动到回收站/归档目录，而不是直接物理删除。

## 可复用建议

1. **给工具分级，而不是给 Agent 分级**。工具是权限的最小单位，先把工具风险等级理清。
2. **权限策略外部化**。不要只写在系统提示里，要落到配置文件、MCP 工具白名单、命令执行沙箱等机制上。
3. **参数级策略优先于工具级策略**。同一个工具，高风险参数需要确认，低风险参数可以自动。
4. **确认授权要限定作用域和时间**。避免一次性授权整个会话。
5. **关键操作做预检和回滚**。能 dry-run 就 dry-run，删除操作先归档再清理。
6. **记录决策依据**。每次确认或拒绝，最好带上操作参数和影响范围，方便事后复盘。

## 总结

AI Agent 的权限边界不是“信不信任模型”的问题，而是把人的判断放在不可逆和高成本节点上。能自动的让它自动，不能自动的才打断人。好的权限设计不会让用户觉得被频繁打扰，也不会让 Agent 处于无约束状态。

在 OpenClaw 这类 Agent 实践里，MCP 工具越多、链路越长，越需要提前划清这条线。工具策略、确认机制和审计日志，就是这条线落到工程里的三块基石。
