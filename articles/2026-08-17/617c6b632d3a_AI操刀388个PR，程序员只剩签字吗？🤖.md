388个PR全部由AI操刀，180个已经合并。这个数据最近在开发者社区里被反复转发。它和“Claude之父”所说的“程序员只剩下签字”放在一起，很容易变成一句耸动结论：AI已经能独立完成软件工程，程序员只需点头。但如果把PR、合并、签字拆开看，真正重要的不是AI做了多少，而是它为什么能合并、谁在兜底、哪些环节没有被看见。



## 一、388个PR从哪里来：从“补全”到“Agent”


- 过去十年，AI辅助编程走过了几个阶段。2010年代的工具主要做语法补全；2021年 GitHub Copilot 把行级、块级补全变成常态。
- 2024年后，以 Claude Code、Codex、Gemini CLI 为代表的 Agent 型工具出现。它们不再只补一句代码，而是可以读取仓库、运行 shell、修改文件、执行测试，甚至直接开一个 Pull Request。
- 388个PR如果放在传统开发里，可能需要数个工程师工作数周；但AI Agent可以在短时间内按模板、批量、并发地生成大量改动。
- 值得注意：这388个PR大概率不是同等难度。自动升级依赖、修复 lint、批量重命名、生成测试、替换废弃 API，这类任务边界清晰，最适合 AI 批量操作。
- SWE-bench 等基准中，Agent 在部分真实 issue 上已展现可用水平，但解决率、复现率和测试依赖仍是关键变量。也就是说，AI不是“会写代码”，而是“在给定的验收条件下，能完成一部分工程任务”。

## 二、180个合并的技术真相：能通过检查才算数


- 合并率约 46%。这个数字在工程上不能简单用“高”或“低”评价。
- 一个 PR 从创建到合并，通常要经过：diff 生成 -> 本地/远程 CI -> 单元测试 -> 静态检查 -> 类型检查 -> 人工 review -> merge。
- AI 能跑通这条链路，前提是项目已经有较高自动化程度：有测试覆盖、有 lint/format 规则、有 type check、有清晰的 CI 流水线。
- 剩下的208个未合并，可能死于：测试不稳定、改动范围过大、破坏公共接口、与架构方向冲突、重复造轮子，或纯粹因为 review 资源不够。
- 换句话说，“180个已合并”赞扬的不只是AI，还包括这个团队已有的工程质量防线。没有CI和测试的项目，AI提交的PR更容易变成“看起来能跑”的噪声。

## 三、程序员只剩签字？三个被忽略的前提


1. 任务需要被精确切分。AI 擅长在有明确输入输出、明确约束的条件下工作；把模糊业务需求翻译成可验收任务，仍然是人或更强架构能力的活。
2. 验收标准已经存在。测试、类型、覆盖率、性能基线，这些不是AI从天上带下来的，而是团队长年累月积累的工程资产。
3. 失败成本可控。自动合并的180个PR大概率集中在低风险区域。支付、鉴权、数据库迁移、权限变更等核心模块，签字不只是流程，而是责任承担。
- “签字”之所以存在，不是因为它轻，而是因为它把风险判断、架构一致性、业务上下文压缩到了最后一道闸门。

## 四、当AI大量提交PR，软件工程会怎么变


- 首要瓶颈会从“写代码”转移到“评审代码”。PR数量暴增后，人类的 review bandwidth 可能被迅速耗尽。
- 开发者的角色会继续偏移：从亲自写 diff，转向写任务规格、设计测试策略、审计AI意图、维护项目上下文。
- 技术债可能以更快速度累积。AI 为了通过测试，有时会给出表面正确、结构糟糕的实现；如果评审来不及看，糟糕抽象会埋进代码库。
- 责任归属并不会消失。AI 没有执照、不承担 on-call、不会在半夜被叫醒。最终签署合并的工程师、团队或 release manager 仍然承担后果。
- 安全与合规也会被放大：AI是否读取了敏感配置、生成的依赖是否存在许可证风险、代码是否泄露内部逻辑，这些都要额外审查。

最后，给正在面对这波AI编程潮的工程师三条建议：
1. 别只看PR数量，看验收质量。先把测试覆盖率、CI耗时、静态检查、灰度发布这些客观防线搭好，再放大AI的吞吐量。
2. 把AI当高频外包，而不是全职员工。给它清晰任务规格、边界和完成定义；每次合并前问一句：如果这段代码明早挂了，我能快速回滚吗？
3. 练好“提出问题”的能力。写代码的速度会被AI拉平，真正拉开差距的是需求拆解、系统抽象、风险判断和跨模块权衡。
