## 背景：MCP 之前的接入方式有多碎

在 MCP 出现之前，给 Agent 接工具是一件非常“手工”的事。比如你有一个天气查询、一个数据库查询、一个文件读取工具，想同时给 OpenClaw、Claude Desktop、自研 Agent 用，通常要写多套 adapter。

每个框架对 function calling 的格式要求不一样：参数 schema 怎么声明、错误怎么返回、工具列表怎么发现，全都没有统一约定。工具开发者要适配 N 个平台，Agent 开发者要维护 M 个插件。这就是典型的 N×M 重复适配问题。

Model Context Protocol（MCP）解决的问题，就是把“模型如何使用外部能力”这件事标准化。它不提升模型本身的能力，而是减少接入层的重复劳动。

## MCP 到底规定了什么

MCP 采用客户端-服务端架构，通信基于 JSON-RPC 2.0。一个 MCP Server 可以暴露三类能力：

- **Tools**：可被模型调用的函数，比如查天气、执行 SQL。
- **Resources**：可被模型读取的数据源，比如文件、数据库表结构。
- **Prompts**：可复用的提示模板。

Host 是实际运行 Agent 的程序，比如 OpenClaw、Claude Desktop。Host 内部通过 MCP Client 连接一个或多个 MCP Server。模型只看到统一协议，不关心工具是 Python 写的还是远程 HTTP 服务。

传输层支持几种方式：

- **stdio**：本地进程通信，适合本机工具。
- **SSE**：早期远程传输方案，部分实现存在断线重连问题。
- **Streamable HTTP**：目前更推荐的远程传输方式。

## 一个最小实践

用 Python SDK 写一个只读的加法工具，验证整条链路。

`demo_server.py`：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Return the sum of two integers."""
    return a + b

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

然后在 OpenClaw 的 MCP 配置里加一个 server 条目，通常是一个 `mcpServers` 映射：

```json
{
  "mcpServers": {
    "demo": {
      "command": "python",
      "args": ["/absolute/path/to/demo_server.py"],
      "env": {}
    }
  }
}
```

重启 Host 后，工具列表里应该会出现 `add`。调用 `add(2, 3)`，返回 5，说明协议链路已经打通。

## 踩坑点

1. **传输方式别选错**  
   本地工具用 stdio，远程服务优先用 streamable HTTP。SSE 在部分 SDK 上对长连接支持不稳定，生产环境尽量避开。

2. **description 和 schema 是模型的“API 文档”**  
   模型依赖工具名称、描述和 inputSchema 来决定怎么调用。描述写得太含糊，比如只写“query data”，模型很容易传错参数。最好写清楚：什么时候用、参数含义、返回什么。

3. **stdio 启动路径问题**  
   Host 启动 stdio server 时，相对路径可能不是你以为的目录。配置里建议用绝对路径，或者显式指定 `cwd`。环境变量也要通过 `env` 字段传入，而不是依赖当前 shell。

4. **权限边界要提前划清**  
   MCP server 本质上是一个本地或远程命令执行入口。不要随意接入第三方 server，尤其是带文件系统、shell 能力的。即使自己写，也要把“只读”和“写操作”分开。

5. **大返回体会撑爆上下文**  
   如果工具返回整张表或一个大 JSON，很容易消耗大量 token。应该在 server 端做分页、截断或聚合，而不是把原始数据全量吐给模型。

## 可复用建议

- **从只读工具开始**：先接查询类工具，稳定后再加写操作。
- **严格定义 JSON Schema**：`required`、`type`、`enum` 都写清楚，减少模型自由发挥的空间。
- **单独建一个 `mcp-servers` 仓库**：把工具和 Host 解耦，方便多个 Agent 复用。
- **用 inspector 调试**：`npx @modelcontextprotocol/inspector python demo_server.py` 可以交互式查看工具列表和调用结果。
- **记录调用日志**：至少记录 tool name、参数、耗时、返回大小，方便排查“模型为什么没调对”这类问题。

## 总结

MCP 解决的是工具接入的标准化问题，把原来分散的 adapter 变成相对统一的连接器。它不是银弹，不会让你的模型变得更聪明，也不会自动写好业务逻辑。

如果工具只在单个框架内部使用，MCP 可能是额外抽象；但一旦要在多个 Host 之间复用同一批工具，或者在团队内共享工具能力，MCP 的维护成本优势就会很明显。

建议从一个小而清晰的只读工具开始，跑通“配置 → 发现 → 调用 → 返回”的完整链路，再逐步扩展到更复杂的工具集。
