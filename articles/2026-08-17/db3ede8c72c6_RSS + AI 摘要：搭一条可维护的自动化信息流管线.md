## 背景

RSS 源订阅多了以后，真正的问题不是“看不到”，而是“看不完”。把每条全文丢给大模型做摘要，表面上解决了信息过载，实际上会带来重复推送、摘要质量不稳定、上下文成本高、首次运行爆炸式推送等新问题。

在 OpenClaw / Agent 环境里，定时任务、MCP 调用、LLM 能力都已经具备，但要让 RSS + AI 摘要真正可维护，不能只靠一个 prompt 解决。它应该是一条管线：**抓取 → 规范化 → 去重 → 过滤 → 摘要 → 分发**。

## 问题

常见做法是“抓 RSS → 塞给 LLM → 推送结果”。这条链路跑通很容易，但工程上很快会遇到：

- 重复条目反复推送
- 首次运行时历史条目全部涌入
- LLM 输出的 JSON 格式不稳，导致分发失败
- 抓正文时触发反爬或超时
- 调度频率和源更新频率不匹配，容易被限流

所以要把它当成一个可恢复的批处理任务，而不是一段简单脚本。

## 做法 / 步骤

### 1. 抓取与规范化

抓取层可以选用 `rss-parser`、`feedparser`，或直接接 RSS 类 MCP server。关键不是“能不能抓到”，而是抓完后的字段统一。

建议将每个条目规范为：

```
source, link, title, guid, pubDate, summary, content
```

其中 `guid` 优先使用源提供的值；如果缺失，退回 `link`；如果 link 也不稳定，再用 `title + pubDate` 做复合键。

### 2. 去重与状态

用 SQLite 保存处理状态。表结构不用复杂，核心字段：

```text
source, link_hash, published_at, title, status, summary, created_at
```

`link_hash` 推荐用 `sha1(link)` 或 `sha1(guid)`。每次运行先查 hash，已存在则跳过。

首次运行时开启 `init` 模式：只写入状态，不推送摘要。否则你会一次性收到几十条“新”内容。

### 3. 过滤层

不要把所有内容都交给 LLM。先用规则粗筛：

- 标题关键词，例如“release / 漏洞 / 更新 / 上新”
- 指定域名或作者
- 发布时间窗口，例如只看最近 24 小时
- 最小内容长度，过滤只有一句话或无正文的条目

过滤层的主要作用是省钱、降噪，也能减少 LLM 被低质量内容干扰。

### 4. 摘要层

建议使用结构化 prompt，让模型输出 JSON：

```json
{
  "title": "原文标题",
  "score": 7,
  "summary": "两句话以内的中文摘要",
  "keywords": ["a", "b"],
  "action_items": []
}
```

评分和摘要可以分两步：先用便宜模型做相关性打分，只对高分的条目生成完整摘要。输入长度要截断，正文保留前 1500–2500 字即可。正文优先使用 RSS 源提供的 `content:encoded` 或 `summary`；需要全文时再用 readability 提取，并设置超时、UA 和重试。

### 5. 分发层

摘要生成后，可以通过 OpenClaw 的 Agent 或自定义命令分发到飞书、Telegram、通知插件，或者追加到 Markdown/Obsidian 文件。

### 6. 调度

用 cron 或 OpenClaw 的定时任务触发。建议每 15–30 分钟跑一次，按源粒度控制。每次运行结束输出统计：抓取多少、过滤多少、摘要多少、推送多少。

## 踩坑点

- **GUID 不稳定**：部分源会变 guid，或者同一篇文章有多个 link。去重只用 guid 不够，必要时组合 link + title 做 fallback。
- **首次运行爆量**：一定要有 init 模式，只建状态不发推送。
- **LLM JSON 不合法**：模型偶尔会输出 markdown 包裹的 JSON。设置 `response_format` 后仍要做一层解析容错，比如剥掉首尾三引号，失败就重试一次。
- **正文抓取被拦**：不要对每个源都爬全文。优先用 RSS 自带的 content 字段，必要时再降级到正文提取，并控制并发和频率。
- **调度频率过高**：10 分钟一次全量抓取并不会让你更快，只会更快被源站限流。根据源更新频率设置轮询间隔。
- **每源都值得 AI 摘要吗**：低信噪比源只做标题过滤和链接推送，可能比全文摘要更实用。

## 可复用建议

- 把管线拆成独立模块：`fetch → filter → summarize → deliver`，每层都能单独跑测试。
- 状态库里保留原始 error，便于回看为什么某条没推送。
- Prompt 和代码放一个仓库，做版本控制，不要单独散落在聊天记录里。
- 先接 1–2 个源跑一周，确认重复率和摘要质量后再扩展。
- 保留人工 review 开关：可以生成摘要后先落盘，人工确认后再推送。

## 总结

RSS + AI 摘要的终点不是“全自动读完”，而是把“读”变成“审”。一条稳定的信息流管线，重点不在模型能力，而在去重、过滤、状态管理和可观测性。先把管线做可恢复，再逐步提高摘要质量，比一次性接几十个源要可靠得多。
