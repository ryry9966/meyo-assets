## 背景

很多 Agent 在长任务里不是“不聪明”，而是“记不住”。你刚告诉它“代码风格用严格 TypeScript，不要 any”，它下一个会话又给你生成一堆 `any`；你反复纠正输出格式，它还是把结论写在第一行。

问题通常不在模型能力，而在记忆系统没有设计。上下文窗口只能当工作记忆，不能当长期存储。想做自动化、插件、MCP 工作流，必须把“偏好”从模型脑内搬到外部系统。

在 OpenClaw 环境里，这件事可以做得比较工程化：不追求花哨的向量记忆，而是先分层、定边界、给来源、可回滚。

## 问题

实际使用中，Agent 记忆容易踩几个坑：

- 偏好散落各处：一部分在系统提示词，一部分在脚本注释，一部分在临时笔记里。
- 写入无规则：模型会把一次偶然选择写进长期记忆，越记越脏。
- 检索无边界：一次性注入大量“记忆”，占用上下文，反而干扰当前任务。
- 偏好会变：没有版本和失效机制，旧偏好一直覆盖新偏好。

所以真正的难点不是“记住更多”，而是“记对、少记、说清来源”。

## 做法 / 步骤

### 1. 把记忆分成三层

我建议至少分三层：

| 层级 | 生命周期 | 存储位置 | 典型内容 |
|---|---|---|---|
| L0 工作记忆 | 当前会话 | 上下文窗口 | 当前任务状态、中间结果 |
| L1 会话记忆 | 一次项目/会话内 | 临时文件 | 本次项目约定、临时路径 |
| L2 长期偏好 | 跨会话 | MCP memory server / JSON 文件 | 稳定偏好、语言、格式、工具链 |

长期偏好只放真正稳定、可复用的东西，不要把任务状态放进去。

### 2. 长期偏好用结构化 JSON 约束

比起自然语言段落，结构化字段更可靠。一个最小可用 schema 可以是这样：

```json
{
  "preferences": [
    {
      "id": "code-style",
      "scope": ["repo:workflow"],
      "content": "TypeScript 严格模式，不使用 any",
      "source": "user_confirmed",
      "updated_at": "2025-01-01T10:00:00Z",
      "ttl": "persistent"
    }
  ]
}
```

关键字段是 `source` 和 `scope`：

- `source`: `user_confirmed` / `inferred` / `session`
- `scope`: 限制这条偏好在哪些场景下生效

只有 `user_confirmed` 才能自动进入长期记忆；`inferred` 必须经过确认或二次触发。

### 3. 写入规则：少写、确认、留痕

不要让模型随时写记忆。推荐规则：

- 用户明确说“记住……”时，直接写入。
- 用户重复纠正同一问题两次以上，才允许生成候选偏好。
- 候选偏好写入前，在任务内确认，或至少写日志。
- 更新同一条偏好时保留历史版本，不要静默覆盖。

这样可以把“偏好污染”控制住。

### 4. 检索注入：按 scope 拉取，不全部塞入

长期记忆不能全量注入。需要在系统提示词里放一个单独区块：

```text
[用户偏好 / 可信度: 高]
- 代码风格: TypeScript 严格模式，不使用 any
- 输出格式: 先给结论，再给步骤
```

限制最多注入 5-8 条，按 `updated_at` 和 `source` 排序。`inferred` 标记为低可信度，避免 Agent 把它当硬规则。

### 5. 在 OpenClaw 中用 MCP 落地

如果已经支持 MCP，可以直接用 MCP memory server 或自建 filesystem MCP：

- `get_preferences(query)`：按 scope / 关键词拉取偏好。
- `save_preference(payload)`：按 schema 写入长期偏好。

如果不想引入额外服务，一个本地 JSON 文件加两个工具也够用。关键是读写接口稳定，Agent 知道什么时候该读、什么时候该写。

## 踩坑点

1. **把会话状态写进长期记忆**  
   例如“当前正在调试登录接口”被写进 L2，下次检索到已经过期，还占注入名额。

2. **允许 `inferred` 直接写入**  
   模型会因为一次偶然行为“推断”你的偏好。比如你某次让它用中文回复，它就把“用户喜欢中文”写进长期记忆。实际上你只是当时在测中文模型。

3. **大段自然语言写记忆**  
   语义检索不可控，输入“不要 any”可能匹配不到“禁止 any”。结构化字段 + 关键词比纯向量可靠得多。

4. **偏好冲突不处理**  
   同一条 key 出现多次，模型不知道听哪个。解决思路是按 `scope + updated_at + source` 加权，冲突时降级为低可信度，或直接询问用户。

5. **写入太频繁**  
   每次工具调用都写一次记忆，会导致工具调用开销大、记忆膨胀。可以限制一个会话内最多 N 次写入，或任务结束前批量写入。

6. **MCP 不可用时 Agent 装记得**  
   记忆服务挂了，模型可能因为上下文里没有记忆就“假装记得”。应设计降级路径：读取失败时，Agent 要明确说“我当前没有长期记忆，无法确认这个偏好”。

## 可复用建议

- **边界优先于容量**：先定义 `scope`、`namespace`、`TTL`，再谈存储方式。
- **长期记忆只存稳定偏好，不存任务状态**。
- **有写入日志**：记录谁在什么时候写入了什么，以及触发原因。这会帮你在 Agent 行为异常时定位到具体记忆。
- **从最小实现开始**：一个 JSON 文件 + 两个 MCP 工具，通常比向量库可靠。
- **可回滚**：偏好更新保留旧值，或提供 `disable` 状态，而不是直接删除。
- **失败要显式**：记忆读取失败、无匹配、冲突未解决，都让 Agent 明确说清楚，而不是猜。

## 总结

Agent 记忆系统不是“存更多”，而是分层、有边界、有来源、可检索、可回滚。

在 OpenClaw 里落地，最实用的路径是：三层记忆 + JSON schema 约束 + MCP 外置存储 + 严格写入规则。让模型多记，不如让它少记、记对、说清来源。

真正可靠的偏好记忆，不是“它越来越像你”，而是你在下一次任务里，不再需要重复同一句话。
