## 背景

在 OpenClaw 社区里，大家经常分享自动化工作流、MCP 插件配置、排障日志和截图。这类内容对复现问题很有价值，但也容易把内部信息带出去。尤其当 Agent 参与撰写、汇总或整理内容时，它可能分不清哪些信息适合公开，哪些属于内部逻辑。

常见的泄露点包括：

- 工作流截图里带着真实项目代号、内部路径或客户字段。
- 排障日志中残留 Bearer Token、API Key、Webhook Secret。
- MCP Server 配置直接贴出，包含内网地址和绝对路径。
- Agent 自动生成的“最小复现”里，仍引用了公司数据库 schema 或业务规则。

这类问题不是某个框架独有的，而是只要让 Agent 处于“输出侧”，就需要控制它能看到什么、能写什么、最终发出去什么。

## 问题本质

Agent 的默认行为是尽量保留上下文、提高可读性。社区分享时，我们希望它保留技术骨架，但不希望它保留真实凭据、内部命名和关键业务逻辑。两者之间的边界如果只靠提示词说“不要泄露敏感信息”，效果通常不稳定。更可靠的做法是在输出链路上做工程化拦截。

## 做法/步骤

### 1. 给信息分级，建立敏感字段清单

先不急着改 Agent，而是定义哪些内容不能公开。建议分三类：

- **公开**：通用流程、公开文档、开源配置、脱敏后的 mock 数据。
- **内部**：项目代号、内网域名、数据库字段、组织架构、业务指标。
- **机密**：API Key、Token、Cookie、私钥、Webhook Secret、客户数据。

把后两类整理成一份敏感信息注册表，包含正则规则或关键词。例如：

```text
sk-[A-Za-z0-9]{20,}
Bearer [A-Za-z0-9._-]+
BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY
10\.[0-9]+\.[0-9]+\.[0-9]+
internal\.example\.com
project_phoenix
```

这份清单要随着业务变化持续维护，不能只停留在初始版本。

### 2. 在 Agent 输出链路加一层 sanitize

不要让 Agent 直接输出到社区。可以在 OpenClaw 工作流里增加一个“外发检查节点”：

- Agent 生成内容后，先进入本地脚本或工具调用。
- 脚本根据敏感信息注册表扫描全文，命中则替换为 `<REDACTED>` 或直接阻断。
- 只有通过检查的内容，才允许写入公开 issue、帖子或文档。

如果使用 MCP，可以封装一个 `sanitize_text` 工具，专门处理输出。注意工具本身不要记录原文日志。

### 3. 对 MCP 和插件权限做最小化

很多泄露不是 Agent 写出来的，而是插件配置被原样分享。建议：

- MCP Server 尽量只给只读权限，按需授权工具。
- 不要给全局文件系统访问，使用限定目录或白名单路径。
- 机密信息用环境变量引用，配置里只写 `${{env.SECRET}}`，不写明文。
- 分享配置前，用脚本比对敏感字段清单，移除绝对路径和内网标识。

### 4. 分享前走“骨架 + mock 数据”流程

社区复现通常不需要真实业务细节。建议分享时：

- 只保留工作流骨架、关键节点和触发条件。
- 用 `demo_user`、`mock_corp`、`10.0.0.1` 等替代真实信息。
- 截图使用测试项目，避免真实工作台和聊天记录。
- 如果涉及排障日志，先跑一遍脱敏脚本，再人工确认。

## 踩坑点

**1. 只脱敏 API Key，不脱敏工作流结构**

工作流结构可能暴露内部工具链、审批节点、数据源和业务规则。分享时要替换成通用模块名，例如把“同步CRM客户表”改为“同步业务表A”。

**2. AI 自动脱敏过度概括，导致无法复现**

有些 Agent 会把日志里所有数值和字段都替换，结果上下文丢失，别人无法定位问题。脱敏原则是“替换敏感实体，保留技术特征”，例如：

```text
原始：调用 internal.example.com/api/v1 失败，Header Bearer abc123
脱敏：调用 internal-redacted.local/api/v1 失败，Header Bearer <REDACTED>
```

保留路径结构，隐藏真实域名和凭据。

**3. 日志和 trace 的 header 容易被忽略**

很多排障帖只删了响应体，却忘了请求头、环境变量打印和堆栈信息。尤其是 `Authorization`、`Cookie`、`X-Api-Key` 这类字段，容易隐藏在长文本里。建议日志外发前统一扫描 HTTP Header 字段。

**4. 插件权限全开导致配置分享变成泄露**

有些 MCP 插件为了省事，直接挂载整个 home 目录或 root 权限。这种配置一旦贴出去，接收方立刻能看到路径结构，甚至可能反推内网布局。建议先降权再分享。

## 可复用建议

- **维护一份外发检查清单**：每次分享前自查是否包含 token、内网地址、真实项目名、客户数据、完整 schema。
- **使用环境变量引用敏感值**：从源头上减少明文出现在配置和日志里的概率。
- **给 Agent 输出分通道**：内部日志走内部通道，社区内容走外发通道，两条链路不混用。
- **MCP 权限白名单化**：只允许必要工具，禁止默认全量访问。
- **分享模板固定化**：准备一套脱敏后的最小复现模板，避免每次手工处理。

## 总结

Agent 在社区分享中的风险，不是“AI 会主动泄密”，而是它缺少信息边界意识。工程化的思路是：先分级、再拦截、后分享。把敏感信息注册表、输出 sanitize 节点和 MCP 最小权限结合起来，比单纯在提示词里强调“注意安全”可靠得多。安全红线不是禁止分享，而是让可分享的部分足够干净，让内部逻辑和凭据始终留在内部链路里。
