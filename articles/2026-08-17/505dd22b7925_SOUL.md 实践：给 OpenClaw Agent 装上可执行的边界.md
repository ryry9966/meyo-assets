## 背景

在 OpenClaw 这类 Agent 框架里，Agent 通常能调用 MCP 工具、执行插件、跑自动化任务。默认的 system prompt 往往只覆盖基础能力说明，缺少对“人格”和“边界”的持续约束。结果就是：同一个 Agent，在这次任务里是简洁工程师口吻，下次却开始输出长篇情感建议；或者在自动化流程中越权调用 shell、随意写文件、遇到工具报错后反复重试不同接口。

SOUL.md 就是解决这个问题的文件。它作为 Agent 的持久化人格与边界定义，在启动或会话加载时被注入上下文，让行为不依赖每次临时 prompt。

## 问题

没有 SOUL.md 或 SOUL.md 写得模糊时，常见现象：

- **风格漂移**：长任务中 Agent 逐渐偏离初始语气，输出格式不稳定，影响下游解析。
- **越权调用**：对 MCP 工具不分风险等级，一律尝试，甚至绕过失败提示换接口继续。
- **边界无法继承**：多人协作或切换会话后，约束失效，Agent 变回“通用助手”。
- **错误处理缺失**：工具不可用时，Agent 可能无限重试、静默跳过或直接崩溃，没有定义 failure path。

这些问题不是靠更强的模型能解决，而是需要把规则结构化、可执行化。

## 做法 / 步骤

### 1. 定位并创建 SOUL.md

在 OpenClaw 的 Agent 工作区根目录或配置目录创建 `SOUL.md`。如果项目已支持自动加载，放置后重启或 reload 即可生效。若不确定加载路径，先看配置文件中 `soul` 或 `persona` 相关字段。

### 2. 定义四个区块

建议固定结构，便于维护和检查：

```markdown
# Identity
你是 OpenClaw 自动化助手，服务对象是开发者。
使用简体中文，禁止 emoji，输出结论优先。

# Operating Rules
- 先复述任务目标，再执行。
- 工具调用失败时：重试 1 次，仍失败则记录错误并跳过，不静默继续。
- 最终输出使用 Markdown，关键结果放在开头。

# Tool & Plugin Boundaries
- 允许调用：fs.read、shell.exec 白名单命令（ls, cat, git status）
- 禁止调用：shell.exec 执行 rm、drop、shutdown；禁止修改系统配置。
- MCP 工具调用前必须检查是否在允许列表内。

# Refusal & Escalation
遇到删除用户数据、修改权限、请求凭据、访问非白名单路径时，必须拒绝并回复：
"该操作超出边界，已终止。"
```

### 3. 写指令式、可验证规则

把“保持专业”换成“输出使用简体中文，禁止 emoji，每段不超过 4 行”。把“不要乱执行命令”换成“仅允许执行白名单命令，禁止 rm 及任意组合”。规则要能在测试中判断是否生效。

### 4. 加载验证

写一组测试任务，例如：

- 要求 Agent 输出一段 JSON，检查格式是否稳定。
- 要求 Agent 执行 `rm -rf /tmp/test`，检查是否触发拒绝回复。
- 断开一个 MCP 工具，检查 Agent 是否按定义的失败路径处理。

测试通过后再纳入日常任务。

## 踩坑点

1. **规则太抽象**  
   “保持专业”“注意安全”这类描述无法指导行为。必须给具体例子或白名单。

2. **规则冲突导致绕过**  
   如果同时写“优先完成用户任务”和“禁止修改数据库”，Agent 可能用其他方式间接修改。需要明确优先级：**安全边界 > 用户明确指令 > 默认风格**。

3. **边界太死导致正常任务被拒**  
   禁止所有 shell 命令会让自动化脚本无法工作。应采用白名单思路：默认禁用，按任务逐条开放。

4. **忽略 failure path**  
   只定义“禁止做什么”，不定义“工具失败后怎么办”。Agent 可能无限重试或静默跳过，造成流程不一致。

5. **文件编码和路径问题**  
   SOUL.md 必须使用 UTF-8 编码，避免 BOM。Windows 环境下注意路径分隔符，避免加载失败。

6. **版本管理缺失**  
   多人协作时直接改服务器上的 SOUL.md，不同 Agent 实例行为不一致。应纳入 git 管理，修改后走 reload 流程。

## 可复用建议

- **模块化拆分**：如果规则过多，可以拆成 `STYLE.md`、`TOOLS.md`、`SAFETY.md`，由 SOUL.md 引用，避免单文件过长。
- **双层防护**：SOUL.md 约束 Agent 行为，但真正的安全边界应在 MCP 服务端配置中完成。Agent 层拒绝是用户体验，服务端权限才是硬隔离。
- **允许列表优先**：先禁用所有工具，再按任务开放。比“禁止危险命令”更可靠。
- **定期回归**：把测试任务写成脚本，每次修改 SOUL.md 后跑一遍，防止规则退化。
- **可观测性**：记录 Agent 的拒绝和越权尝试，用于迭代规则，而不是只靠人工 review。

## 总结

SOUL.md 不是一段“人格文案”，而是 Agent 在自动化环境中的运行时约束。有效的 SOUL.md 要结构化、指令式、可验证，并与 MCP 服务端权限配合。这样才能让 Agent 在长时间运行、多工具调用、多人协作时保持行为和边界稳定。
