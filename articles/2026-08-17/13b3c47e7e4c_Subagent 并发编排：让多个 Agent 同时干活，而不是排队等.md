## 背景

单个 Agent 处理多源任务时，串行执行是最大的效率瓶颈。比如要同时抓取 5 个数据源、分别清洗、再汇总成报告，串行调用工具的总时长线性累加。更麻烦的是上下文污染：5 个数据源的原始内容全部堆进主 Agent 的上下文，格式互相干扰，主 Agent 容易在长 prompt 里“失焦”，漏掉关键字段或开始编造。

在 OpenClaw 这类 Agent 框架里，subagent 是解决这个问题的常用手段。把独立任务拆给多个 subagent 并行执行，主 Agent 只负责调度和汇总。但并行编排不是开线程那么简单，拆分不当、返回值不规范、并发限流，都会让并行变成灾难。

## 问题

实际做的时候，最常见的坑有三个：

1. **任务边界模糊**。把有依赖关系的任务强行并行，比如“先登录再查询”，subagent 之间互相等待，甚至共享状态冲突。
2. **返回结构不一致**。subagent 返回自由文本，主 Agent 合并结果时又要重新理解一遍，既要消耗 token，又容易出错。
3. **结果回流导致上下文爆炸**。subagent 把原始全文吐回来，主 Agent 再复述一遍，长 prompt 下稳定性直线下降。

另外还有并发数过高触发上游 API/RSS/数据库限流、错误被吞、重试不幂等等工程问题。

## 做法/步骤

我在 OpenClaw 里的实践是：**把 subagent 封装成 MCP 工具，主 Agent 只调度，不搬运数据。**

**1. 先拆任务，再考虑并行**

判断标准很简单：任务之间无共享写、结果可独立校验、各自有独立数据源。符合这三个条件的才适合并行。例如“抓取 5 个 RSS 源并分类”适合并行；“先登录拿到 token 再查询用户信息”不适合，必须串行。

**2. 固定 subagent 的输入输出 schema**

每个 subagent 只做一件事，输入和输出都用 JSON 约束。例如一个抓取工具：

```json
{
  "source_id": "rss_001",
  "status": "ok",
  "items": [{"title": "...", "url": "...", "summary": "..."}],
  "error": null
}
```

返回结构里必须带 `status` 和 `error` 字段，否则主 Agent 无法判断成败。

**3. 用调度层控制并发，而不是让主 Agent 直接开多线程**

主 Agent 生成任务列表，调用一个 `run_parallel(tasks[])` 工具。调度层负责并发执行、限流、重试和错误收集。并发数默认控制在 3-5，不是越多越好。比如抓取 RSS 时并发 5 个可能很快，但打数据库可能直接把连接池打满。

**4. 只回传摘要，原始结果落盘或写库**

subagent 返回的内容应该是压缩后的结构化摘要，而不是原始全文。原始数据可以写文件、写入 SQLite，或者存到对象存储。主 Agent 只拿到一个 `result_id` 和简要统计，需要时再按 id 调取。这样可以避免上下文被中间结果塞爆。

**5. 日志带 task_id，失败可单独追踪**

每个并行任务分配一个 `task_id`，subagent 的所有日志都带上这个 id。汇总时统计失败率，失败的 task_id 可以单独重试，不需要重新跑全量。

## 踩坑点

- **subagent 返回自由文本**。这是最常见的坑。subagent 一旦开始“自由发挥”，合并逻辑就会变得极其脆弱。必须在 subagent 的 system prompt 里给出 JSON 示例，并在调度层做 schema 校验，不符合的直接丢弃并重试。
- **并发数过高触发限流**。上游 API 或数据库通常有速率限制。并发 10 个抓取任务，很可能前面 3 个成功，后面 7 个全部 429。调度层要做指数退避，并且对同一数据源的请求做串行化。
- **上下文回流**。subagent 返回全文，主 Agent 又复述一遍，token 消耗直接翻倍。解决方式是“摘要回传 + 原始结果落盘”，主 Agent 只读摘要。
- **错误被吞**。并行任务里一个失败，主 Agent 可能直接忽略，最后汇总出来的报告缺数据。返回值必须带 `error` 字段，调度层统计失败率，失败率超过阈值就终止并提示人工介入。
- **重试不幂等**。如果 subagent 里有写操作，失败重试可能导致重复写入。写操作要设计幂等键，或者 subagent 只生成写入计划，由主 Agent 统一执行。

## 可复用建议

- **接口先行**。先定义每个 subagent 的 input/output schema，再写 prompt 和逻辑。不要边写边改。
- **“摘要 + 落盘”模式**。subagent 返回摘要，原始结果写文件或数据库。主 Agent 只读摘要，需要明细时再按 id 拉取。
- **给 subagent 限制 token**。subagent 跑偏时可能输出超长文本，设置 `max_tokens` 能避免单点失控。
- **并发数从 2 开始调**。先跑通，再逐步提高并发，观察上游限流情况和内存占用。
- **把调度逻辑做成可复用工具**。封装成 OpenClaw 插件或 MCP 工具后，主 Agent 只需要关注任务拆分和结果汇总，不用每次都在 prompt 里重新描述并发逻辑。
- **关键写操作加人工确认**。如果 subagent 的输出会触发写库、发消息、改配置，最好在主 Agent 汇总后加一个 `approve` 步骤，避免并行误操作。

## 总结

subagent 并行适合 I/O 密集、上下文隔离、结果汇总型的任务，比如多源抓取、批量查询、并行分析。它不适合强依赖链、需要共享状态或频繁回滚的场景。工程上真正重要的是三件事：**合理的任务拆分、固定的返回 schema、克制的上下文回流**。并行不是越多越好，先把串行跑通，再拆出真正独立的单元去并行，你会少踩很多坑。
