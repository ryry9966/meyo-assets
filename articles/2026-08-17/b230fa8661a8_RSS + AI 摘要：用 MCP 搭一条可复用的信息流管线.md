## 背景

RSS 是最省心的信息源协议，但订阅数量一多，未读数就会变成负担。与其每天在阅读器里扫标题，不如把“抓取、去重、摘要、过滤、推送”交给 Agent 跑成一条管线。在 OpenClaw 生态里，MCP 工具很适合承载这些单一职责节点：每个节点可独立测试、替换和复用。

## 要解决的问题

常规 RSS 阅读器能提供聚合和未读数，但缺少两个关键能力：一是按你的关注点重写摘要，二是自动分流。直接让 Agent 每篇都读全文再总结不现实：token 消耗大、重复处理多、推送噪音高。因此需要把管线固化下来，而不是每次手动粘贴给模型。

## 做法/步骤

### 1. 用 MCP 暴露 RSS 抓取工具

写一个 `rss_fetch` MCP 工具，输入 feed URL，输出标准化条目字段：`guid/link、title、summary、published_at、source`。解析优先读 `content:encoded` 或 `summary`，没有正文就先给标题和摘要。使用 `feedparser` 一类库处理，不要手写 XML 解析。

标准化输出很重要。不同 feed 的字段差异很大，统一成同一结构后，后面的摘要、去重、推送才能稳定工作。

### 2. 增量去重

本地放一个 SQLite 表 `seen_items`，以 `guid` 为主键；如果 feed 没有稳定 guid，用 `link + published_at` 做 hash。抓回来先插入表，返回本次新增条目，只对新增条目做后续摘要。

不要用标题去重。很多站点会改标题、做 A/B 测试，标题 hash 容易造成漏处理或重复处理。

### 3. AI 摘要与结构化输出

对每条新增条目调用 LLM，prompt 固定为：

- 一句话摘要
- 关键观点，2-3 条
- 可操作项
- 重要性 1-5

要求只输出 JSON，并用 JSON Schema 约束，避免自由文本解析失败。为控制成本，正文截断到 1500-2000 tokens。小模型够用就优先用小模型，摘要任务不需要强推理。

### 4. 过滤与推送

规则过滤先于 AI 判断：源白名单、关键词、发布时间窗口。AI 重要性只做二次排序，不要直接决定推送，否则误判会产生噪音。

建议分三层：重要性大于等于 4 或命中关键规则的，进即时通道；3 分进每日汇总；其余丢弃或只写日志。阈值先保守，跑几天观察分布再调整。

### 5. 调度与容错

用 cron 或 OpenClaw 定时任务每 30 分钟跑一轮。源级 try/except：某个 feed 失败不影响其他源。条件请求带 `ETag/Last-Modified`，失败指数退避，避免被源站封禁。

## 踩坑点

- **RSS 格式不统一**：有的只有标题，有的 `summary` 带大量 HTML，有的日期缺时区。统一转成 UTC 并清洗标签，否则摘要里会混入样式字符。
- **guid 不稳定**：部分站点 guid 每次变，或完全缺失。此时兜底用 `link + pubDate`，不要只依赖 guid。
- **全文抓取成本高**：RSS 没正文时，如果每篇都去抓原文并做 readability，延迟和失败率都会明显上升。建议先基于标题/摘要跑摘要，确实重要的再抓全文。
- **JSON 输出不稳定**：模型偶尔会多输出说明文字。用 JSON Schema 约束，解析失败重试一次；仍失败则丢弃该条并记录，不阻塞管线。
- **推送噪音**：AI 对“重要”容易打分偏高。阈值宁可保守，先减少推送数量，稳定后再放宽。
- **轮询礼仪**：高频抓取会被源站限流甚至封 IP。条件请求、随机 jitter、失败退避都要有，别把 RSS 当实时接口轮询。

## 可复用建议

- 拆成独立 MCP 工具：`rss_fetch`、`rss_dedup`、`ai_summarize`、`rss_push`。单一职责方便调试和替换。
- 状态外置，用 SQLite 而非进程内存。提供 `dry-run` 参数，只打印不推送，先观察再上线。
- 日志至少记录：源、新增条数、摘要 token、耗时、失败原因。排障效率高很多。
- 先跑一个小闭环：3 个源、1 个推送通道、1 个摘要模板。稳定后再加源和策略。

## 总结

RSS + AI 摘要不是替代阅读，而是把信息从“全文未读压力”降成“可扫读的卡片”。用 MCP 把管线拆开，工程上更可维护。先保证去重、容错、成本控制，再谈智能过滤。跑通一周后再优化 prompt 和阈值，往往比一开始做复杂策略更有效。
