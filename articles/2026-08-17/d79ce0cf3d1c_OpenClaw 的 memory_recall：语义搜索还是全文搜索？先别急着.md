## 背景

在 OpenClaw 里给 Agent 接长期记忆时，`memory_recall` 是绕不开的入口。工具调用结果、用户偏好、任务片段、报错修复记录都会往记忆库里写。随着条目从几百条涨到几万条，召回质量直接决定 Agent 是“记得住关键信息”，还是“翻出一堆不相关的内容丢进上下文”。

于是自然会纠结：`memory_recall` 到底该用语义搜索，还是全文搜索？

## 问题

很多教程把语义搜索当成默认答案，但工程实践里不是这样。

- **全文搜索**对命令、报错码、API 名、文件路径、日期等精确匹配很稳，但在中文场景下，分词不一致会导致漏召回。比如“连接池超时”和“connection pool timeout”可能完全搜不到彼此。
- **语义搜索**能覆盖“意思相近但关键词不同”的查询，比如“把超时调大”和“timeout 配置增大”。但它对短文本、数字编号、专有名词经常误召回，而且 embedding 版本变化会让历史分数不可比。

所以真实问题不是二选一，而是：**在 memory_recall 管线里，如何组合两者，并让召回结果稳定可评估。**

## 做法/步骤

我在 OpenClaw 里踩过几轮，比较实用的路线如下。

### 1. 先加结构化过滤，再做搜索

不要一上来就对全库做向量检索。记忆条目通常有 `source`、`type`、`created_at`、`importance` 等字段。先用结构化条件缩小候选集，比如：

```yaml
memory_recall:
  filter_fields: [source, type, created_after]
```

如果查询里能提取出“最近三天”“来自 Redis 相关工具”，就先把候选集从几万条降到几百条，后面怎么搜都会更稳。

### 2. 先跑全文搜索 baseline

用 SQLite FTS5 或 Meilisearch 做全文检索。中文建议配置 trigram 或 ngram tokenizer，避免默认分词器把“连接池”“超时时间”切坏。

```yaml
fulltext:
  engine: sqlite-fts5
  tokenizer: trigram
```

### 3. 小评估集对比语义搜索

建 10-20 条真实查询，标注期望命中的记忆 id。查询类型要覆盖：

- 精确关键词：`Redis timeout 报错`
- 语义改写：`上次那个连接超时怎么修的`
- 专有名词：`MCP server 重启后 session 丢失`
- 时间相关：`前天配置的数据库连接池`

跑语义搜索时，用本地 embedding 如 `bge-small-zh-v1.5`，存 sqlite-vec 或 Chroma。记录 `hit@1`、`hit@3`、`mrr`。

你会发现：全文搜索在精确关键词和专有名词上更好；语义搜索在口语化改写上更好。

### 4. 混合召回用 RRF 融合

不要直接比较 BM25 分数和余弦相似度，量纲不同。用 Reciprocal Rank Fusion 更稳：

```yaml
fusion: rrf
rrf_k: 60
final_top_k: 5
```

RRF 只关心排名，不关心绝对分数，避免某一路分数虚高。

### 5. 设置语义分数阈值，回退全文

语义分数低的时候不要硬塞。可以设置：

```yaml
min_semantic_score: 0.35
```

低于阈值就只保留全文结果。这样能减少短文本 embedding 导致的“什么都像”。

## 踩坑点

- **中文分词不一致**：默认分词器会把“连接池超时”拆成“连接”“池”“超时”，导致精确查询漏召回。上 trigram 后精确匹配好很多，但索引体积会变大。
- **短文本 embedding 漂移**：像“是的”“OK”“已完成”这类记忆，embedding 彼此相似度很高，语义搜索会大量误召回。建议过滤掉少于 N 字符的条目，或对查询先做简单意图判断。
- **embedding 模型版本变化**：换模型后旧记忆的向量不能直接和新查询比较，必须重嵌入。不要在线上直接切换模型而不重建索引。
- **向量索引写入锁库**：如果每次工具调用都同步写向量索引，sqlite 场景很容易锁库。建议批量提交或异步更新，memory_recall 只读索引。
- **top-k 不是越大越好**：召回 10 条以上会稀释上下文，实测 top 3-5 比 top 10 更稳。Agent 的上下文窗口是稀缺资源。

## 可复用建议

1. **先结构化，后全文，语义作为补充**。这条路径能覆盖大多数真实场景，不要一上来就全向量检索。
2. **建立最小评估集**。每次改 embedding 模型、索引参数或融合权重，都要重跑一遍，不要凭感觉调。
3. **给记忆条目加权**。用户偏好、固定配置类记忆提权，流水日志降权，召回时按 `importance` 加权会比纯搜索更符合预期。
4. **记录召回日志**。每次 `memory_recall` 后记录 query、返回 id、用户是否采纳或修正。这些数据是后续调优最真实的数据来源。
5. **混合召回不是银弹**。如果查询本身有明确结构，比如“列出昨天所有报错”，结构化过滤 + 全文搜索就够了，不需要语义搜索强行参与。

## 总结

`memory_recall` 不是一个“语义 vs 全文”的选择题，而是一条召回管线。工程上更务实的顺序是：结构化过滤缩小范围 → 全文搜索保底精确匹配 → 语义搜索补充意图改写 → RRF 融合排序 → 阈值截断 + 评估集闭环。

语义搜索有价值，但它不是 memory 召回的起点。先让全文搜索和结构化过滤跑稳，再逐步引入向量检索，会让整个记忆系统更可控。
