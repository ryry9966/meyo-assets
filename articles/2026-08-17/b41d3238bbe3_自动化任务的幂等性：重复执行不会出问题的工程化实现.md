在 OpenClaw、Agent、MCP 插件和定时自动化场景里，重复执行几乎无法避免：模型可能重新生成一次工具调用，队列可能重复投递，用户可能双击触发，定时任务可能上一次还没跑完下一次又启动。真正能保护系统的，不是“尽量避免重复”，而是让重复执行不产生额外副作用。这就是幂等性。

## 一、背景：重复执行不一定是 bug

在分布式和 Agent 场景中，大多数任务投递语义是“至少一次”。也就是说，系统只保证任务会到达，不保证只到达一次。OpenClaw 里的插件、MCP 工具、自动化脚本，随时可能因为重试、超时补偿、人工重复触发而被执行多次。

如果没有幂等设计，常见后果包括：

- 同一条消息发给用户两次；
- 同一个工单、订单、支付请求被创建或提交两次；
- 同一个文件被重复生成、覆盖或追加；
- 重复调用外部 API，触发限流或产生脏数据。

因此，自动化任务的健壮性，很大程度取决于消费端能否安全处理重复执行。

## 二、问题：重复执行为什么会造成“额外影响”

我们可以把一次任务拆成两部分：

1. 内部计算：例如读参数、拼 prompt、做逻辑判断；
2. 外部副作用：例如写数据库、发消息、调第三方 API、生成文件。

幂等性重点不是“不让任务重复运行”，而是“重复运行不会产生额外外部副作用”。如果一个任务只做查询，或者计算结果幂等，那重复执行问题不大；但一旦涉及写入、发送、支付、建单，就需要显式设计。

常见的非幂等来源：

- 每次执行都用新的随机 ID，无法识别这是同一次逻辑任务；
- 判断“是否已经执行过”和“写入执行状态”不是原子操作；
- 只在内存或日志里记录“已执行”，服务重启后丢失；
- 副作用已经发生，但状态标记失败，重试后再次执行。

## 三、做法：把幂等性落到执行链路上

### 1. 设计业务唯一键

幂等的前提是“能识别同一次逻辑任务”。不要把每次执行时生成的随机 UUID 当作幂等依据。可靠的业务唯一键通常来自：

- 参数组合的哈希：`task_type + target_id + date_window`；
- 上游已有的业务单号；
- Agent 任务创建时生成的 `task_id`，所有子步骤继承它作为前缀。

例如一个“每天给指定用户生成摘要并发送”的任务，唯一键可以是：

```text
daily_summary:user_123:2025-03-15
```

这样同一天、同一用户、同一任务，无论触发多少次，都能被识别为同一逻辑操作。

### 2. 入口先抢占状态

仅靠“先查一下再执行”会有并发竞争：两个请求同时查到“未执行”，然后都继续执行。必须让“检查并占用”成为原子操作。

常用方案：

- 数据库唯一约束：给幂等键建唯一索引，插入执行记录时冲突则跳过；
- Redis：`SET idempotency_key value NX EX 3600`，只有第一个请求能抢到锁；
- 状态机条件更新：

```sql
UPDATE tasks
SET status = 'running'
WHERE id = ? AND status = 'pending';
```

如果影响行数为 0，说明已经有别的执行在跑，当前请求应直接返回已有结果或跳过。

### 3. 外部副作用尽量改造成可重入

有些外部系统天然支持幂等，例如支付、订单、短信服务通常提供 `idempotency_key` 参数。调用时传入与内部幂等键一致的值，服务端会帮助去重。

对于不支持幂等的副作用，需要自己做一层去重：

- 发消息：在消息内容或元数据里带上唯一业务 ID，消费端按 ID 去重；
- 写文件：先写临时文件，再原子重命名；或按内容哈希判断是否需要重新生成；
- 调 API：在本地保存 `key -> response` 映射，命中时直接返回缓存结果。

### 4. 重试策略与错误分类

重复执行和重试强相关。重试不当会放大非幂等问题。建议：

- 只对可重试错误重试，例如超时、5xx、限流；
- 对 4xx 业务错误不盲目重试；
- 使用指数退避加抖动，避免短时间内大量重复；
- 重试时复用同一个幂等键，而不是重新生成。

### 5. 验证方式

设计完幂等逻辑后，需要主动制造重复：

- 并发触发同一个幂等键 100 次，观察是否只产生一条副作用；
- 跑一次重复执行脚本，比对数据库记录数、消息发送数、文件数量；
- 模拟“副作用已发生但状态未标记”的情况，检查重试是否会再次触发。

## 四、踩坑点

### 1. 唯一键粒度错误

唯一键太粗，会误拦正常任务。例如把“每日任务”唯一键设置成只有 `task_type`，那么同一天所有用户只会执行一次。太细则无法去重，例如把随机 ID 也放进唯一键，那么每次都不同，幂等失效。

### 2. 只做“查一下再插”

这是最典型的并发问题。代码里先查询是否存在，再决定是否插入，两个并发请求会同时通过检查。务必用唯一约束或原子抢占兜底。

### 3. 状态存在内存或日志

服务重启后状态丢失，后续重复请求会重新执行。幂等状态必须持久化，或者使用带 TTL 的 Redis 等外部存储，TTL 要覆盖任务可能重复的时间窗口。

### 4. 副作用已发生，状态却置为失败

例如外部 API 创建订单成功，但网络超时，任务被标记为失败。下次重试时，如果直接再次调用，就会重复创建。解决办法是把外部返回值或外部唯一 ID 一并保存，重试前先按该 ID 查询真实状态。

### 5. 忽略 Webhook 和回调重复

MCP 服务或插件接收 Webhook 时，外部平台也可能重复推送。应记录 `event_id` 并按 `event_id` 去重，而不是只按业务数据判断。

## 五、可复用建议

在 OpenClaw 的插件、MCP 工具和自动化任务里，可以沉淀一套统一的幂等执行器：

```python
result = run_idempotent(
    key="daily_summary:user_123:2025-03-15",
    ttl=3600,
    fn=generate_and_send_summary
)
```

这个执行器内部负责：

- 使用 `key` 抢占幂等锁；
- 如果已存在结果，直接返回缓存结果；
- 如果未执行，执行 `fn` 并保存结果；
- 失败时释放锁或标记状态，避免永久阻塞。

对 MCP 工具/插件，建议在参数中增加 `idempotencyKey`，并在服务端保存 `key -> response`。对定时任务，默认加锁，避免上一次未结束下一次又启动。对每个工具/插件，在文档里明确标注它的幂等范围，例如“同一参数重复调用只发送一次消息”。

## 总结

幂等性不是“不会重复执行”，而是“重复执行不会产生额外影响”。在 Agent、MCP、插件和自动化任务中，重复执行是常态，幂等设计是工程底线。具体落地时可以遵循一条简单路径：

1. 先定义业务唯一键；
2. 用唯一约束或原子锁抢占执行权；
3. 外部副作用尽量改造成可重入；
4. 重试复用同一个幂等键；
5. 用并发和重复执行测试验证。

这套思路不依赖具体框架，适合沉淀到 OpenClaw 的自动化实践里。真正可靠的自动化任务，不是跑得快，而是重复跑也不出事。
