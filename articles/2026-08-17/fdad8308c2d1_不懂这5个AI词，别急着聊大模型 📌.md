最近刷 AI 新闻，常看到 Token、Agent、RAG、上下文窗口、Transformer 这些词。它们像 AI 圈的口令，聊产品、选供应商、看财报都会撞上。有人用这些词制造认知差，也有人被满屏黑话劝退。其实拆开看，这 5 个词分别对应模型的“计量单位、工作记忆、底层架构、外挂知识、行动能力”。弄懂它们不保证写出算法论文，但足够让你在 90% 的讨论里不被带偏。



## 1. Token：模型处理文本的“最小计量单位”

Token 不是“单词”，也不是“汉字”，而是模型分词后的最小单元。

- 英文里 “apple” 可能是 1 个 token，“unbelievable” 可能被拆成 “un”+“believ”+“able” 三个 token；中文一个汉字常占 1~2 个 token。不同模型的 tokenizer 规则不同，所以同一个句子在 GPT-4、Claude、Gemini 里 token 数可能不一样。
- 很多大模型采用 BPE（Byte Pair Encoding）这类分词算法，把出现频率高的字符组合合并成一个 token。好处是能平衡词表大小和表达效率，代价是我们读起来不那么直观。
- 为什么它关键？因为 API 计费按 token，上下文窗口按 token 计算，生成速度常以 tokens/s 衡量。粗略估算：1000 token 大约对应 750 个英文单词，或 500~600 个汉字。具体数字因模型而异，但做成本判断已足够。
- 举个例子：一个客服机器人平均每次请求输入 2000 token、输出 400 token，每天 1 万次调用，就是 2400 万 token/天。用 API 单价一乘，就能判断这项功能是赚钱还是亏本。很多产品看似聪明，其实死于 token 账单。

## 2. 上下文窗口：模型的“工作记忆”


上下文窗口（Context Window）是模型一次能“看到”的 token 总量，通常输入和输出共享。

- 早期 GPT-3 只有 2048 token，现在 128K、200K、甚至 1M token 窗口已不稀奇。窗口越大，单次可以塞进更多资料、保持更长对话。
- 但要理解一个机制：Transformer 的注意力计算复杂度大致随序列长度平方增长。长上下文不是免费的，它会推高显存占用、延迟和推理成本。现在有很多优化，如稀疏注意力、状态空间模型，但仍然存在工程约束。
- 产品上，很多读写场景都在靠上下文窗口：上传长 PDF、分析代码仓库、持续对话记忆。判断一个产品是否靠谱，最直接的问题是：“全文放进窗口了，还是只检索了几页？” 只检索几页的，本质更接近 RAG，而不是真正的长上下文。
- 还有一个现象叫 “lost in the middle”：有研究发现，模型对长文本中间位置的信息利用得不如开头和结尾。所以即使窗口很大，关键信息最好放在提示词首尾，或者用清晰分段。
- 实用判断：如果你的任务只需要最近 2000 token，就不必为 1M token 窗口付溢价。长窗口是能力，但不是所有场景都划算。

## 3. Transformer：现代大模型的“地基”

Transformer 是当下大多数大语言模型的底层架构。

- 它来自 Google 团队 2017 年发表的论文《Attention Is All You Need》，最初面向机器翻译任务。核心机制是自注意力（Self-Attention），让序列里的每个 token 都能直接和其他 token 建立联系，而不是像旧循环网络那样一步步传递。
- 这个改变意义很大：训练可以大规模并行，模型能更好捕捉长距离依赖。GPT 里的 “T” 就是 Transformer。ChatGPT、Claude、Gemini、文心一言等主流产品，背后基本都是 Transformer 的变体。
- 从规模上看，2018 年 GPT-1 约 1.17 亿参数，到 GPT-3 的 1750 亿参数，架构的扩展性让“堆参数、堆数据”成为可能。但参数多不等于强，数据和训练方法同样重要。
- 对普通用户来说，不需要手推注意力公式，只要知道：当别人说“模型升级了架构”，通常就是在动 Transformer 的某一层、注意力机制或训练目标。这比玄学解释更接近事实。

## 4. RAG：让模型学会“查资料”

RAG 是 Retrieval-Augmented Generation，检索增强生成。

- 直观解释：模型在回答前，先去外部知识库里检索相关资料，把资料拼进提示词，再基于参考资料作答。这样答案更容易溯源，也能接入企业私有文档。
- 典型流程：用户提问 -> 向量化查询 -> 在向量数据库检索 top-k 相关片段 -> 拼接为上下文 -> 大模型生成答案 -> 可附引用来源。
- 它为什么火？一是减少幻觉，答案有出处；二是企业不用重新训练模型，更新知识库即可；三是成本比微调低得多。很多客服、法务、内部知识库问答系统，都是“RAG 为主、微调为辅”。
- 和微调的区别：微调会修改模型权重，适合学特定风格、稳定格式或领域行为；RAG 不改变权重，适合事实更新快、来源可解释的场景。两者不是互斥，常见组合是：微调让模型更听话，RAG 让模型知道最新事实。
- 避坑点：RAG 的瓶颈往往不在大模型，而在检索质量、文档切分和排序。如果底层文档写得一团糟，RAG 也救不了。

## 5. Agent：从“问答”到“干活”

Agent 不是单纯聊天机器人，而是一个能规划、调用工具、记住状态、执行动作的智能体。

- 常见组件：模型（大脑）、记忆（短期/长期）、工具调用（搜索、API、代码执行）、规划（拆任务、反思、重试）。很多框架把这类流程称为 ReAct，即 Reasoning + Acting。
- 例子：用户说“整理上周会议纪要，提取行动项并发送邮件给负责人”。Agent 可能先读文档、抽取行动项、按人归类、调用邮件工具发送，遇到权限不足会暂停询问。
- 这背后不再是“一问一答”，而是任务闭环。企业关注的是任务完成率、人工接管率、执行耗时，而不是聊天是否流畅。
- Agent 的风险也来自“行动能力”。一个能发邮件、改配置、调 API 的 Agent，一旦理解错指令，代价可能很大。所以权限边界、关键操作确认、只读模式是工程上必须处理的点。
- 可以这样记：LLM 负责“说”，Agent 负责“做”；RAG 负责“查”，上下文窗口负责“记”。

## 最后：三条实用建议


- 建议一：用框架记词。Token 是“计量单位”，上下文窗口是“工作记忆”，Transformer 是“底层架构”，RAG 是“外挂资料”，Agent 是“会干活的机器人”。先记住这个映射，再看技术文章会轻松很多。
- 建议二：算成本先问两个数。单次请求大概多少 token？长任务需要多大上下文窗口？把这两个数字乘上调用量再对比价格。很多时候，一个方案不是技术不行，而是 token 账单太贵。
- 建议三：别把术语当效果。一个产品说自己用了 Agent、RAG、长上下文，不代表它真能解决你的问题。最靠谱的做法是拿 3~5 个真实任务做小样本测试，看准确率、耗时、人工接管率。

冷思考：AI 领域造词速度比模型迭代还快，很多新词只是旧概念的重新包装。抓住“输入、记忆、架构、外挂、行动”这条线，你就能过滤掉大部分噪音，把注意力放回任务本身。
