## 背景

在 OpenClaw/Agent 里做长期记忆，`memory_recall` 通常是最后一道关口：上层把用户输入、任务上下文、历史决策丢进来，希望召回最相关的记忆片段。实现上最常见两条路线：

- **全文搜索**：BM25、SQLite FTS5、MeiliSearch 这类，靠词项匹配。
- **语义搜索**：embedding 向量化后做余弦相似度，靠语义相近。

很多实践里会二选一，但工程上真正稳定的做法往往是“双路召回 + 重排”。下面是我在一套本地 MCP/插件环境里踩过的实际经验。

## 问题

单纯全文搜索的短板很明显：用户说“把上次那个超时的任务重试一下”，记忆里存的是“task timeout retry”，字面不匹配就漏召回。

单纯语义搜索也不省心：命令名、报错码、ID、URL、配置项这些强精确匹配的东西，向量检索容易“想太多”。比如 `ERR_SSL_PROTOCOL_ERROR` 被语义模型召回成“证书过期排查记录”，表面上相关，实际不是同一条。

所以问题不是“哪个好”，而是你的 memory 里到底存的是哪类数据，以及上层 query 更偏向精确还是模糊。

## 做法

### 1. 先分数据类型

给记忆加元数据，至少区分：

- `type=command`：命令、ID、报错码、路径、API 名。
- `type=note`：决策、总结、聊天记录、模糊描述。
- `type=log`：带时间窗的运行日志。

这一步决定后续召回优先级。

### 2. 建两套索引

本地场景不建议一上来就上向量数据库。SQLite FTS5 + `sqlite-vec` 或内存 numpy 足够，数据量在十万级以内完全没问题。

你可以让 `memory_recall` 暴露一个混合模式：

```json
{
  "memory_recall": {
    "index": "sqlite://./memory.db",
    "fts": "fts5",
    "embedding_model": "bge-small-zh",
    "merge": "rrf",
    "top_k": 8
  }
}
```

工具调用类似：

```text
memory_recall(query, mode="hybrid", scope="project_a", top_k=8)
```

### 3. 双路召回 + RRF

一路 FTS5 返回 BM25 分数，一路向量返回 cosine。不要直接线性加权，用 RRF 更稳：

```text
score(doc) = sum(1 / (k + rank_i))
```

`k` 一般取 60。这样两边量纲不同没关系，也不会因为某个分数异常大而压过另一路。

### 4. 阈值和过滤

每路单独设阈值，过滤掉明显不相关的候选。阈值不要拍脑袋，先跑 50 条 query 看分布。`type=command` 的候选优先走全文结果；`type=note` 的候选优先走语义结果。最后再按 `scope`、时间窗、活跃度做一次简单过滤。

## 踩坑点

### FTS5 对中文不友好

SQLite FTS5 默认 `unicode61` tokenizer 处理中文等于没分词。连续中文文本会被切得很怪，召回效果差。

**做法**：写入时用 jieba 等做分词，存到影子列，FTS 索引影子列；或者用 `trigram` tokenizer。trigram 在短词和错误码上比 jieba 稳定，但索引体积会变大。

### embedding 模型要归一化

中文备注、对话总结如果用英文通用模型，效果会打折。本地可跑 `bge-small-zh` 这类小模型。向量一定要做 L2 归一化，否则 cosine 结果受长度影响。chunk 长度建议 200–500 token，重叠 50–100，不然长文段整体 embedding 会稀释关键词密度。

### 语义阈值别照搬 0.7

中文 paraphrase 的 cosine 阈值经常落在 0.55–0.75。如果你设 0.7，很多合理召回会被干掉。建议先打一批 dev query，统计正负样本分数分布，再定阈值。

### 混合召回不是“加个向量库”

最差实践是把全文结果和向量结果直接按分数相加。BM25 分数不是归一化的，不同索引、不同查询长度都会漂，直接相加基本是拼运气。

## 可复用建议

- **默认 `mode=hybrid`**，但允许 Agent 根据任务显式指定 `keyword` 或 `semantic`。
- **强精确 ID/命令/报错码，永远保留一条全文优先路径**。
- **语义搜索用于 notes、总结、对话历史、模糊描述**。
- **建立小评测集**：至少 50 条 query，记录 hit@1、hit@5、MRR。每次改模型、chunk、分词、阈值都跑一遍，不然调参就是玄学。
- **保留 `score` 和 `sources` 返回**，让上层 Agent 能判断置信度。低于阈值的宁可返回“无记忆”，也别硬塞一个错误上下文。

## 总结

`memory_recall` 不是一个“语义 vs 全文”的二选一问题。全文解决字面一致，语义解决意思相近。双路召回加 RRF 重排，在本地 SQLite 就能搭起来，成本低、足够稳。先把数据类型和召回路径分清楚，再谈模型和调参，比换向量数据库更有实际收益。
