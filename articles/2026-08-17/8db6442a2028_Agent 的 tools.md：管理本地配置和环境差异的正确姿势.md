## 背景

在 OpenClaw / Agent / MCP 的自动化实践里，经常出现一种尴尬：同一个 Agent 工作流，在开发机跑得很顺，换到同事电脑、CI 容器或一台新服务器上就各种报错。问题通常不是 Agent 能力不行，而是它根本不知道当前机器长什么样。

Python 是 3.10 还是 3.12？`ffmpeg` 装在 `/usr/local/bin` 还是 `/opt/homebrew/bin`？某个内部服务是要走代理还是直连？这些信息对工具调用成功与否影响很大，却很少被显式提供给 Agent。

`tools.md` 就是用来解决这件事的：它不是给人看的 README，而是一份给 Agent 看的“本机环境说明”。它把路径、版本、环境变量、平台差异、验证命令和已知限制集中起来，作为上下文注入到 Agent 的规划与执行过程中。

## 问题

很多项目已经写了 README、`requirements.txt`、`.env.example`，但 Agent 不会主动去读这些文件，或者读到了也不知道哪些信息对当前任务关键。更常见的做法是把环境信息随口写在聊天里，比如“你记得用 `/opt/homebrew/bin/ffmpeg`”，这既不持久，也难以复用。

另一个问题是路径硬编码。开发者为了快速调通，直接让 Agent 使用某个绝对路径，结果换个环境就失效。更隐蔽的问题还包括：

- 同一台机器上有多个 Python 版本，Agent 用了错误解释器；
- macOS 和 Linux 的命令参数不同，Agent 按一种平台执行；
- 需要 `sudo` 或交互确认的操作，Agent 无权限却反复尝试；
- 把 API key、数据库密码等敏感信息写进环境说明，导致泄露。

## 做法与步骤

### 1. 在 Agent 工作区根目录创建 tools.md

内容应该面向工具调用，而不是面向人类阅读。建议至少包含以下区块：

- **工具清单**：当前环境可用的 CLI、SDK、系统工具及其版本；
- **路径别名**：关键二进制、数据目录、项目根目录；
- **环境变量**：需要提前加载的非敏感变量，例如 `PYTHONPATH`、`NODE_ENV`；
- **验证命令**：用于确认环境是否就绪的命令及预期输出；
- **平台差异**：`darwin` / `linux` / `win32` 下的不同命令或参数；
- **已知限制**：哪些工具不可用、哪些路径只读、哪些操作需要人工确认。

一个最小示例：

```markdown
# tools.md

## 运行时
- Python: 3.11.8（`python3 --version`）
- Node: 20.11.0（`node --version`）
- ffmpeg: 6.1（路径 `/opt/homebrew/bin/ffmpeg`）

## 路径
- 项目根目录: `$PROJECT_ROOT`
- 临时目录: `$PROJECT_ROOT/tmp`

## 环境变量
- `PYTHONPATH=$PROJECT_ROOT/src`
- `FFMPEG_BINARY=/opt/homebrew/bin/ffmpeg`

## 平台分支
- macOS: 音频设备用 `avfoundation`
- Linux: 音频设备用 `pulse`

## 已知限制
- 禁止直接操作 `/etc` 下的系统配置
- 需要写入 `~/Library/Application Support` 时先创建目录
```

### 2. 把 tools.md 注入 Agent 上下文

不要指望 Agent 自动发现这个文件。可以在 system prompt 里加入固定指令：“在执行任何工具调用前，先阅读工作区根目录的 `tools.md`，并优先遵循其中的路径、版本和平台分支。”如果使用 OpenClaw 的项目策略或 MCP 资源，也可以把 `tools.md` 作为一个可读取的资源暴露给 Agent，让它在规划阶段主动获取。

更工程化的做法是把 `tools.md` 挂到一个 MCP 工具的参数描述中，这样 Agent 在调用工具前能获得环境约束。对于支持文件读取的 Agent，直接让它读取文件并提取关键约束，比自然语言复述更可靠。

### 3. 用可执行命令替代自然语言描述

“确保 ffmpeg 可用”这种描述对 Agent 没有可操作性。应该写成：

```markdown
验证命令：`ffmpeg -version | head -n 1`
预期输出：`ffmpeg version 6.1`
失败处理：如果命令不存在，检查 `$FFMPEG_BINARY` 是否已加入 PATH，或使用绝对路径 `/opt/homebrew/bin/ffmpeg`。
```

这样 Agent 可以自己验证环境状态，而不是盲目尝试。

### 4. 保持 tools.md 与真实环境同步

环境变更后，旧版 `tools.md` 会误导 Agent，比没有更糟。可以用一个简单的脚本生成或校验 `tools.md`，例如：

```bash
make tools-md
# 或
./scripts/generate_tools_md.sh
```

在 CI 里增加一步检查，确保文档中声明的工具版本与实际版本一致。这比人工维护可靠得多。

## 踩坑点

1. **把 secrets 写进 tools.md 并提交仓库**。任何 token、密码、私钥都不应该出现在这个文件里。环境变量只写名字，不写值。

2. **文件越写越长，上下文容易超限**。tools.md 不是百科全书，只保留与当前项目工具调用强相关的信息。可以把机器级信息放到全局文件，项目级信息保持精炼。

3. **只写一次就不再更新**。环境漂移后，Agent 会拿着过期信息执行，产生更难排查的错误。建议把 `tools.md` 纳入版本管理，并在环境变更时同步更新。

4. **失败处理写得太模糊**。像“如果失败就重试”或“换一种方式”这种描述，Agent 很难判断何时停止、如何选择替代方案。必须给出明确的判定条件和下一步命令。

5. **忽略权限边界**。如果某个操作需要 `sudo` 或交互确认，必须在 tools.md 中显式声明，否则 Agent 会反复尝试无权限操作，浪费时间和资源。

6. **平台分支没写清楚**。同一个工具在 macOS 和 Linux 下参数不同，如果只按一种平台描述，换环境就会出错。

## 可复用建议

- **分层管理**：全局 `~/.openclaw/tools.md` 放机器级通用配置；项目根目录 `tools.md` 放项目级配置；用户级可以覆盖部分字段。这样避免重复，也方便迁移。
- **使用占位符而不是绝对路径**：优先写 `$PROJECT_ROOT`、`$HOME` 这类可解析的变量，减少因用户目录不同导致的失效。
- **与 MCP 工具描述结合**：如果 Agent 通过 MCP 调用工具，可以把相关环境约束写到 MCP 工具的 `description` 里，这样每次工具选择都会携带上下文。
- **提供模板**：在团队内部维护一个 `tools.md` 模板，新项目直接复制并填写，降低落成本。
- **定期校验**：用脚本或 CI 输出工具版本和路径，自动更新 `tools.md` 中的“机器指纹”部分，避免人工遗漏。

## 总结

`tools.md` 不是银弹，也不是什么新概念。它做的是把原本散落在开发者脑子里、聊天记录里、README 里的环境差异，变成一份结构化、可执行、可版本化的上下文。对于 Agent 这种依赖工具调用的系统来说，环境差异不是“额外信息”，而是“操作前提”。把这件事做扎实，很多看似随机的工作流失败都会消失。
