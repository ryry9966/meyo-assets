最近一条在开发者圈热传的消息来自 36kr：某个代码仓库在短时间内让 AI 自动提交了 388 个 Pull Request，其中 180 个已经被合并进主干；与此同时，Claude 背后的核心人物抛出一句更刺激的判断——程序员以后可能只剩下“签字”这个动作。

这句话当然有情绪放大，但数据是硬邦邦的。388 个 PR、180 个合并，意味着 AI 不只是补全一行代码，而是开始以“提案者”身份走完整套代码协作流程。我们不妨把它拆开看：PR 是什么、AI 怎么操刀、合并率怎么读、程序员的价值会转移到哪里。



## 一、先拆概念：AI 操刀 PR 到底操的是什么

PR（Pull Request）是代码协作里的“变更请求”。开发者把一段代码改动打包，说明改了什么、为什么改，然后请求仓库维护者把它合并到主分支。传统上，一个 PR 背后通常是一个人：读需求、改代码、跑测试、写描述、等人 review。

“AI 操刀”并不是说 AI 拿着账号随意合并代码，而是指这样一条链路：

- 输入：一个 issue、一条需求描述，或者一段失败测试日志。
- 处理：AI agent 读取仓库文件、定位相关代码、生成补丁（patch/diff）。
- 验证：自动运行测试、lint、类型检查，失败后自己修改。
- 输出：按照模板生成标题、描述、变更摘要，正式提交一个 PR。
- 合并：需要人类 reviewer 点击审批或合并按钮。

所以“AI 操刀”更多是“AI 作为提案者 + 自动化验证者”，而人类仍然握着合并权。388 个 PR 里有 180 个合并，合并率约 46%。这个数字一方面说明 AI 已经能稳定产出可被接受的代码提案，另一方面也说明还有超过一半的 PR 没有通过，远没到“全自动软件工程”。

## 二、AI 自动 PR 的工作机制：为什么能跑起来


AI 能自动开 PR，不是因为某个模型突然会写大项目，而是因为它被塞进了一个由工具、测试和权限组成的闭环里。典型流程可以拆成五步：

1. **任务解析**  
   模型从 issue 或待办事项中提取目标，生成执行计划。比如“把依赖从旧版本升级到新版本，同时修掉弃用 API”。

2. **代码检索**  
   通过文件搜索、符号索引、AST 解析，把相关文件和历史 commit 拼成上下文。上下文质量直接决定生成质量，很多失败 PR 就死在上下文不全。

3. **补丁生成**  
   模型输出 diff，而不是整份文件。这样既有可解释性，也方便 review。随后会调用 formatter、compiler 做第一次纠错。

4. **验证闭环**  
   跑单测、集成测试、lint、类型检查。失败后把错误日志喂回模型，让它继续修改。这个“生成—测试—修复”的循环是 AI PR 质量提升的关键。

5. **提交与说明**  
   按模板生成 PR 标题和描述，附上测试结果、变更摘要、风险评估，帮助 reviewer 快速判断。

要支撑这套流程，三个技术点很关键：

- **Context engineering**：把最相关的文件、符号、依赖、历史提交塞进模型，而不是把整个仓库硬塞。
- **Tool use / MCP**：模型可以执行只读命令、查看 diff、读取 CI 日志，不再只靠静态提示。
- **Sandbox 与权限隔离**：AI 在沙箱中跑测试，不能直接推主分支；合并必须由人确认。

这也能解释为什么这波变化发生在最近两年：从 2021 年 GitHub Copilot 的补全，到 Cursor、Claude Code、各类 coding agent，工具链逐渐从“帮写一行”进化到“帮走完一个 PR”。

## 三、180/388 这个数字该怎么读：合并率不是全部

看到 46% 合并率，有人觉得“很强”，有人觉得“一半被拒，也没那么神”。这两种读法都太粗糙。

合并率高低，取决于任务类型：

- **机械性、范围明确的任务**：依赖升级、简单重构、测试补充、文档同步，AI 合并率往往较高，因为验收标准清晰。
- **需要隐性知识或架构判断的任务**：涉及跨模块副作用、性能权衡、向后兼容、模糊需求，AI 容易生成“能跑但不对”的代码，合并率自然下降。

那些没合并的 PR，也不是零成本。它们会消耗 reviewer 的时间、占用 CI 资源，甚至让仓库历史变脏。所以只看“开了多少 PR”没有意义，真正该看的指标至少包括：

- 净合并时间：从 PR 创建到合并，比人工快了多少？
- revert 率：合并后是否被回滚？
- 后续缺陷率：合并后有多少 bug 是 AI 代码引入的？
- reviewer 总耗时：人类审查 AI PR 是不是反而更累？

另外，人类 PR 的首次通过率在不同项目里差异也很大。成熟项目、强 CI 的项目，人类 PR 也可能反复修改。因此，拿 46% 和“程序员平均水平”直接比较，参考价值有限。更诚实的说法是：AI 已经能承担一部分低风险、高重复的 PR 工作，但它的合并率高度依赖任务边界和验证强度。

## 四、程序员角色变化：从“写代码”到“审代码、签代码”

“程序员只剩下签字”这个说法，更接近一种注意力转移的预言，而不是岗位消失的宣告。

如果 AI 真的开始批量提交可用 PR，程序员的工作重心会发生三个变化：

- **写规格，而不只是写实现**。把需求翻译成足够清楚的验收标准、边界条件、限制条件，这件事会变得比手写一段算法更值钱。
- **审 diff，而不是盯格式**。review 的重点从“这行写得丑不丑”转向“这个改动会不会引入安全、性能、兼容性风险”。
- **设计测试与护栏**。测试用例从“事后补的证明”变成“事前定义的验收信”；测试写得越好，AI 提交的可用率越高。

一个比较贴切的类比是航空：自动驾驶没有让飞行员消失，但飞行员的职责从持续操纵飞机，变成了监控系统、处理异常、做关键决策。飞行员仍然对整机负责，签不了字的人反而不能进驾驶舱。

所以在 AI PR 时代，“签字”不是更轻松，而是责任更前置。合并按钮背后，是对 AI 生成的代码负最终责任。审查能力不足的团队，反而会在这场自动化里吃亏。

## 五、冷思考与实用建议


如果团队准备把 AI PR 引入真实仓库，有四点值得提前想清楚：

1. **先把 AI 当实习生，不当正式工**  
   默认不信任 AI 提交的 diff。要求它给出测试结果、复现步骤、变更说明；没有测试的 PR 一律不合并。

2. **从低风险任务开始建立信任**  
   依赖升级、格式化、文档、补充测试、删除死代码，这些任务边界清楚、回滚成本低。跑通之后再逐步扩展。

3. **设置硬护栏，禁止自主合并**  
   强制 CI、覆盖率阈值、安全扫描、license 检查都通过，才允许进入人工 merge。不要给 AI 直接写主分支的权限。

4. **用数据决定扩展范围**  
   持续记录 AI PR 的合并率、revert 率、review 时长、后续缺陷率。数据好看再放开，数据不好就缩范围。

最后回到那句话。388 个 PR、180 个合并，确实是一个值得注意的拐点，但它证明的不是“程序员只剩签字”，而是软件工程正在长出新的协作界面：人类从文本生产者，逐渐转向质量守门人。自动化写代码不等于自动化软件工程，需求澄清、架构权衡、事故响应，仍然需要人来兜底。
