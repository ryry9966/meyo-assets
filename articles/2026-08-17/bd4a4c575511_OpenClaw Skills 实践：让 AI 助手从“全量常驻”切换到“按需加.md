## 背景：能力越多，上下文越重

在 OpenClaw 或类似 Agent 自动化环境里，我们常把 MCP 工具、本地脚本、业务规则、系统提示词都往主配置里塞。初期确实方便，但能力一多，问题就明显：

- 每轮对话都要携带大量工具定义和说明，上下文成本高；
- 多个能力之间的指令互相干扰，模型容易选错工具；
- 新增或修改能力时，不得不改动主配置，风险集中；
- 复杂任务里，模型会“看到”很多无关能力，反而降低决策质量。

OpenClaw 的 Skills 机制提供了一种更工程化的方式：把能力封装成独立模块，主 Agent 只保留轻量索引，任务命中时再加载对应能力详情。

## 问题：我们需要的是“目录”，不是“堆满的书架”

如果把所有 Skill 正文都挂在 system prompt 下面，本质上还是全量加载。真正的按需加载需要两层结构：

1. **索引层**：轻量、常驻，只包含技能名称、触发条件、一句话描述；
2. **详情层**：重内容、按需读取，包含具体指令、脚本路径、输入输出约定、注意事项。

这样主 Agent 在规划阶段只看到“目录”，确定需要某个能力后，再去读取详情并执行。既能控制上下文，也能让每个 Skill 的指令更完整，不必因为担心占用空间而写得过于简略。

## 做法：一个最小可用的 Skill 结构

以“提取 PDF 表格”为例，可以按下面的方式组织：

```text
skills/
  pdf-table-extract/
    SKILL.md
    extract_tables.py
    requirements.txt
```

`SKILL.md` 里建议包含以下元信息：

```yaml
---
name: pdf-table-extract
description: 从 PDF 中提取表格并输出 CSV
when_to_use: 用户要求提取 PDF 表格、批量转换表格型 PDF
inputs: 一个或多个 PDF 文件路径
outputs: CSV 文件路径或表格预览
permissions: 读取文件、写入当前工作目录
---
```

正文再补充具体步骤、调用示例、错误处理。这样模型在索引层看到 `when_to_use`，判断命中后再读取 `SKILL.md` 全文。

主 Agent 的索引可以简化成：

```text
可用 Skills：
- pdf-table-extract：提取 PDF 表格，当用户要求处理表格型 PDF 时使用
- text-summary：本地文本摘要，当用户要求总结长文本时使用
```

实际执行时，让模型通过文件读取工具获取对应 `SKILL.md`，而不是在启动时全部注入。

## 踩坑点

### 1. 触发条件写得模糊，模型不加载

描述里只写“处理 PDF”不够明确。模型可能在“阅读 PDF 内容”和“提取表格”之间犹豫。建议写清正例和反例：

```yaml
when_to_use: 用户明确要求“提取表格”“导出 CSV”“表格数据”
not_for: 普通文字阅读、翻译、摘要
```

### 2. 脚本路径和工作目录不一致

Skill 加载后，脚本里的相对路径可能失效。建议在 `SKILL.md` 和脚本里都使用基于 Skill 目录的绝对路径，或者要求执行时显式切换到 Skill 目录：

```text
cd skills/pdf-table-extract && python extract_tables.py --input "$INPUT"
```

否则容易出现“文件找不到”或“输出到了错误目录”。

### 3. 只加载指令，不控制权限

按需加载不等于随意执行。Skill 如果涉及 shell、网络、文件写入，需要加一层权限约束。可以在元数据里声明 `permissions`，主 Agent 在加载后只开放白名单操作；涉及删除、覆盖、外部请求时要求二次确认。

### 4. 索引更新不及时

改了 `SKILL.md` 的触发条件，但主 Agent 的索引还是旧缓存，导致该触发时不触发。建议每次 Skill 变更后重新生成索引，或者把索引做成动态读取目录文件，而不是手写一份静态列表。

### 5. 多个 Skill 功能重叠

例如“PDF 表格提取”和“OCR 识别”都能处理扫描件。模型可能反复横跳。解决方法是给 Skill 定义优先级或互斥关系，比如在索引里标注“扫描件优先使用 OCR Skill”。

## 可复用建议

- **先做索引卡片，再写完整文档**。每个 Skill 先用 3 行说清楚“什么时候用、输入什么、输出什么”，确认稳定后再补充正文。
- **用结构化元数据校验**。JSON/YAML 元数据可以脚本校验必填字段，避免描述缺失或格式错误。
- **为每个 Skill 写一个最小测试任务**。例如给一个示例 PDF，预期输出包含几行表格。更新后跑一遍，验证触发和输出。
- **记录命中率和加载耗时**。如果某个 Skill 长期未被触发，说明描述或场景有问题；如果加载耗时高，考虑拆分详情。
- **把读操作和写操作分开**。只读 Skill 可以自动执行；写操作或外部请求放在独立的确认步骤里。

## 总结

Skills 机制的价值不是“增加更多提示词”，而是把能力从常驻上下文里拆出来，变成可发现、可校验、可按需加载的模块。工程上的关键是：

1. 轻量索引常驻，详情按需读取；
2. 触发条件明确，正反例都有；
3. 路径、权限、版本都要管；
4. 用测试和命中率来持续优化。

这样 OpenClaw 上的 Agent 才能在能力增长的同时，保持上下文可控、行为稳定。
