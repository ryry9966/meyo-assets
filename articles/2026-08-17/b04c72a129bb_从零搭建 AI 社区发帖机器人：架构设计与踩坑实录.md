## 背景

在 OpenClaw-CN 社区维护项目的过程中，我每周需要同步更新日志、使用技巧和 FAQ 汇总。手工发布不仅耗时，还经常因为格式不统一、忘记发布而被社区用户追问。于是我尝试搭建一个半自动发帖机器人：它负责从内容源读取 Markdown、生成摘要与排版、等待人工确认，最后通过社区网页完成发布。

社区没有开放 API，只有 Web 编辑器。因此发布通道只能走浏览器自动化。这篇文章记录我的架构设计和实际踩坑，给同样在用 OpenClaw/Agent/MCP/插件做自动化的朋友一些参考。

## 问题拆解

发帖机器人看似简单，实际需要解决四个问题：

1. **内容源与格式**：Markdown 需要转换成社区编辑器支持的格式。
2. **发布通道**：没有 API，需要模拟登录、填表、提交。
3. **审核机制**：完全自动发布容易出事故，需要人工确认环节。
4. **可靠性与幂等**：网络超时、验证码、重复提交都会导致发布失败或重复发帖。

## 架构设计

我采用分层架构，核心是 **OpenClaw 作为 Agent 编排层**，通过 MCP 协议接入发布工具。

```
Git 仓库（内容源）
   ↓
OpenClaw Agent（调度 + LLM 排版）
   ↓
人工审核（CLI 确认）
   ↓
MCP Server（社区发布工具）
   ↓
SQLite（发布记录 + 幂等控制）
```

具体技术栈：

- **内容源**：Git 仓库，按日期存放 Markdown 文件。
- **编排层**：OpenClaw，负责读取内容、调用 LLM 生成摘要和标签、触发审核和发布。
- **发布工具**：自定义 MCP Server，内部封装 Playwright 浏览器自动化。
- **状态记录**：SQLite，记录每次发布的标题、内容 hash、状态、错误信息。

发布工具的 MCP 工具定义大致如下：

```json
{
  "name": "publish_post",
  "parameters": {
    "title": "string",
    "content": "string",
    "tags": "string[]",
    "dry_run": "boolean"
  }
}
```

`dry_run` 默认为 `true`，只生成预览截图，不真实提交。审核通过后，Agent 再以 `dry_run: false` 调用。

## 核心步骤

### 1. 内容预处理

Agent 读取 Git 仓库中的 Markdown，调用 LLM 完成以下转换：

- 生成 30 字以内的中文摘要。
- 提取 3-5 个标签。
- 将 GFM 代码块、表格转换为社区编辑器支持的格式（如 `[code]...[/code]`）。
- 图片统一转为外链，避免编辑器上传失败。

转换结果写入 `preview.md`，等待人工确认。

### 2. 登录态管理

社区登录需要 Cookie 和部分浏览器指纹。我使用 Playwright 的 `storageState` 持久化登录态：

```bash
# 首次手动登录后保存状态
npx playwright codegen --save-storage=auth.json
```

后续启动浏览器时加载 `auth.json`，避免每次重新登录。注意：该文件包含敏感信息，不要提交到 Git。

### 3. 发布通道

MCP Server 内部流程：

1. 启动持久化浏览器上下文，加载登录态。
2. 打开发帖页面，使用 `text=` 选择器定位标题、正文、标签输入框。
3. 填入内容，点击「预览」，截图保存。
4. 如果 `dry_run` 为 `true`，返回截图路径并结束。
5. 否则点击「发布」，等待页面跳转或成功提示。
6. 记录发布结果到 SQLite。

### 4. 审核与触发

审核通过 CLI 命令完成：

```bash
openclaw-agent publish --file=2024-07-01.md --confirm
```

也可以接入 GitHub Actions，每天晚上定时运行，生成预览并提交 PR，人工 merge 后触发真实发布。

## 踩坑实录

### 坑 1：登录态频繁失效

社区有 Cloudflare 防护，headless 浏览器直接访问会被拦截。即使加载 `storageState`，有时也会触发验证码。

**解决方案**：

- 优先使用 `headful` 模式调试，确认选择器和流程无误后再切回 headless。
- 定期手动巡检登录态，发现失效及时更新 `auth.json`。
- 在 MCP Server 中加入失败检测：如果页面出现验证码，立刻截图并返回明确错误。

### 坑 2：Markdown 兼容性差

社区编辑器不支持 GFM 的代码块、表格和脚注。直接粘贴会格式错乱。

**解决方案**：

- 写一个转换脚本，在 LLM 排版之后、发送到发布工具之前执行。
- 代码块转为 `[code]` 标签，表格转为列表或图片。
- 保留原始 Markdown 在 Git 中，转换后的版本只用于发布。

### 坑 3：MCP 工具超时

发布操作在 headless 下可能耗时 60 秒以上，默认 MCP 工具超时只有 30 秒，导致 Agent 误判为失败。

**解决方案**：

- 在 MCP Server 端将该工具超时设置为 120 秒。
- 实现重试机制：如果超时，先查询 SQLite 确认是否已发布成功。
- 使用内容 hash 作为幂等键，避免重复提交。

### 坑 4：选择器脆弱

社区前端偶尔更新，CSS 选择器会变化，导致填表失败。

**解决方案**：

- 优先使用 Playwright 的 `text=` 选择器，如 `page.get_by_label("标题")`。
- 封装页面对象层，把选择器集中管理，便于快速修改。
- 失败时自动截图，返回给 Agent 作为调试信息。

### 坑 5：重复发布

网络抖动可能导致提交成功但响应超时，Agent 重试后重复发帖。

**解决方案**：

- 每次发布前计算内容 hash，写入 SQLite。
- 发布前检查最近是否有相同 hash 的成功记录。
- 如果存在，直接返回已有帖子链接，不再重复提交。

## 可复用建议

1. **用 MCP 封装社区能力，而不是在 Agent prompt 里写网页操作步骤**。关注点分离后，Agent 只关心内容生成和调度，维护成本低很多。
2. **先做只读工具**。例如读取草稿、预览，验证登录和解析流程，再写发布工具。
3. **所有发布动作默认 dry-run**。真实发布需要显式确认，避免误操作。
4. **记录每次发布的 hash 和状态**。这是实现幂等和重试的基础。
5. **优先寻找官方 API 或 RSS/Atom 接口**。DOM 自动化是最后手段，维护成本高。
6. **不要完全自动直发**。保留人工确认环节，尤其是公共社区，合规和内容质量比自动化更重要。

## 总结

这个发帖机器人最终为我每天节省 20-30 分钟，发布格式统一，漏发也减少了。但它的维护成本在于登录态和选择器的脆弱性，需要定期人工巡检。如果你的社区有开放 API，强烈建议优先走 API。如果只能浏览器自动化，把发布逻辑封装成 MCP 工具，能让整个系统清晰很多。

自动化不只是“让机器替人干活”，更重要的是把流程标准化，让每一次发布都可审计、可回滚、可恢复。
