## 背景

在 OpenClaw 里接入 MCP、插件或外部工具后，Agent 的能力会从“只读助理”快速变成能改文件、执行命令、操作数据库、发送外部请求的执行体。能力越大，权限边界越容易模糊。很多实践者会陷入两种极端：要么默认全自动，一条命令误删目录；要么所有非只读操作都弹确认，复杂任务被确认打断，Agent 变成需要人工驱动的聊天框。

权限边界不是“要不要信任 Agent”，而是取决于操作的**可逆性、影响范围、数据敏感度与上下文是否足够**。工程上能做的是把这些判断显式化，而不是依赖模型自觉。

## 问题

常见的权限失控，通常来自三个缺口：

1. **工具没有权限语义**：MCP/插件清单里只有自然语言 description，没有 risk level、side effect 等元数据。模型只能猜。
2. **确认没有上下文**：只问“是否继续”，不给出命令、影响范围、回滚方案，人类无法有效判断。
3. **策略不分环境**：在开发环境验证过的命令，到生产环境风险完全不同，但全局用同一套策略。

## 做法/步骤

### 1. 给工具补齐权限元数据

不要只写工具描述，统一在包装层或 MCP/插件清单里标注：

- `risk_level`: `readonly` / `low` / `medium` / `high` / `critical`
- `side_effect`: `none` / `reversible` / `irreversible` / `external_cost`
- `scope`: 可影响的资源范围，如目录、数据库、外部服务

OpenClaw 的工具注册或包装层可以统一加 metadata，避免依赖模型“自觉判断”。

### 2. 按风险分级执行策略

| 风险级别 | 默认策略 |
| --- | --- |
| readonly、无副作用 | 自动执行，只记录 |
| 低风险、可逆 | 自动执行 + 审计日志，事后可回滚/对比 |
| 中风险、可逆但有影响 | 默认 dry-run 或 preview；有 diff/plan 时自动，否则问人类 |
| 高风险、不可逆 | 必须确认，确认包包含命令、影响范围、回滚方案 |
| 外部付费、敏感权限 | 单独高频确认或额度限制，不因低风险自动 |

例如：新建临时文件、查询公开接口可以自动；批量重命名、修改本地配置应默认 dry-run；删除、`rm -rf`、数据库写、发布、支付、发送外部消息必须确认。

### 3. 把确认请求做成“决策包”

不要只问“是否继续”。确认信息应至少包含：

- 即将执行的命令/工具与输入
- 目标资源与影响范围
- 失败后如何处理
- 可回滚步骤

这样人类判断成本低，也能减少机械点击“允许”导致的确认失效。

### 4. 临时授权与白名单

对常用目录、固定命令、测试环境配置 allowlist。例如：

- 允许对 `/tmp/agent-test/` 内写入
- 允许 `git status`、`git diff`
- 禁止 `git push --force`
- 每次会话可临时提升权限，会话结束回收

这样既保留自动化效率，又不把高风险权限长期暴露。

### 5. 审计日志与回放

至少记录：`tool name`、`input`、`risk level`、`decision source(auto/user)`、`timestamp`、`result summary`。出现误操作时能回放定位。OpenClaw 里如果工具调用有 session 或 run id，最好落到结构化日志。

## 踩坑点

- **权限声明不等于运行时约束**：清单里标 readonly，但 MCP server 实际仍可写。需要网关或包装层做 enforced policy，而不是靠提示词。
- **过度信任工具描述**：模型会因描述里“安全”“只读”而放松。风险元数据应独立于自然语言描述。
- **环境差异**：开发环境确认过的命令，到生产环境风险完全不同。策略必须按环境 namespace 区分。
- **确认疲劳**：每次写文件都问，用户会机械点“允许”，最终等于无确认。低风险批量授权，高风险使用更有区分度的确认方式，如输入资源名/确认码。
- **没有回滚方案的高风险操作不要做**：如果没有备份、版本控制或 dry-run，先补齐可逆性再谈自动。

## 可复用建议

- **最小权限起步**：新接入工具默认 `readonly + log`，非只读必须显式开启。
- **风险分级矩阵**：横轴影响范围，纵轴可逆性，决定 `auto / confirm / block`。
- **把“拒绝”做成可执行策略**：当 Agent 判断需要人工时，不只是停止，而是给出已准备好的 plan 和需要批准的 diff。
- **定期回看 audit log**：把频繁误确认或频繁拒绝的高风险工具降级/禁用，把真正安全的工具升级为 auto。
- **策略配置集中管理**：用环境变量或配置中心管理权限策略，不在代码里散落 if/else。

## 总结

AI Agent 权限边界的目标不是让 Agent 更像人，而是让自动操作**可预测、可审计、可回滚**。什么时候该问人类，取决于后果是否可逆、影响范围是否可控、上下文是否足够。工程上先给工具加风险元数据，再分层策略，最后用日志回放持续调整，比一味“全部自动”或“事事确认”都更可持续。
