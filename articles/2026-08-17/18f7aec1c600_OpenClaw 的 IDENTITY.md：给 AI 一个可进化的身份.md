## 背景：Agent 越来越能干活，身份却越来越容易漂

在 OpenClaw 里接入多个 MCP、插件和自动化脚本后，一个常见的感受是：Agent 能力变强了，但“它到底按哪套规则办事”开始变得不稳定。

同一个项目，今天让它写代码，它会严格遵循 lint；明天换一个会话，它可能开始自由发挥。项目约定、工具偏好、禁用命令、目录结构、失败教训，散落在 system prompt、README、MCP tool description、插件配置甚至某次聊天记录里。

问题不是上下文不够，而是没有一个稳定的“身份合同”。

## 问题：信息很多，但没有单一事实来源

OpenClaw 的 Agent 每次启动时，会拼装大量上下文：系统提示词、工具声明、插件能力、项目文件。这些信息各自为政，优先级不清晰。

例如：

- system prompt 里说“默认只读，不要改文件”
- MCP 工具描述里说“可以修改配置”
- 项目 README 里说“不要触碰 data/ 目录”
- 上一轮会话里你口头说“这次先放开 data/ 目录权限”

Agent 最后可能选择最容易被注意到的指令，而不是最重要的指令。

IDENTITY.md 的定位，就是把这些分散的身份信息收敛成一个可版本化、可加载、可更新的单一文件。

## 做法：把 IDENTITY.md 当成可版本化的运行时身份

### 1. 先建立最小模板

不要从“人格设定”开始，从边界和约束开始。

建议固定几个区块：

```markdown
# IDENTITY.md

## identity
这个 Agent 在本项目中的角色：后端自动化维护者。

## scope
允许：修改 src/、tests/、docs/。
禁止：修改 data/、deploy/、*.secret。

## project_layout
- src/：核心代码
- tests/：pytest
- scripts/：运维脚本

## tool_policy
- 优先使用 MCP 的 file_reader 读取文件
- 修改文件前先输出 diff
- 不使用 shell 执行联网下载

## failure_modes
- 触发条件：路径含空格时，shell 命令未加引号
- 期望行为：所有 shell 路径参数加双引号
- 验证方式：运行 scripts/check_paths.sh 无报错

## change_log
- 2025-01-04：新增 data/ 目录只读约束，避免误删
```

关键是把规则写成可执行、可验证的句子，而不是“你要细心”“你要专业”。

### 2. 接入 OpenClaw 的加载链

具体做法取决于你的启动方式：

- 如果使用 bootstrap prompt，将 IDENTITY.md 内容注入 system prompt 的固定位置；
- 如果使用 MCP，可以把 IDENTITY.md 暴露成一个 resource，例如 `identity://project`；
- 如果使用插件，可以在 session start 时读取文件并放入上下文。

目标是：**只从一个文件加载身份信息**，不要在多处复制。否则又会回到漂移状态。

### 3. 建立更新机制

身份文件不应该是一成不变的。每完成一次任务或复盘一次事故，就往 `change_log` 里追加一条。

推荐使用“触发条件 → 期望行为 → 验证方式”三段式：

- 触发条件：什么情况下会出问题；
- 期望行为：Agent 应该怎么做；
- 验证方式：怎么判断规则仍然有效。

这样身份文件就从“静态说明”变成了“可进化的交接班记录”。

## 踩坑点

### 1. 文件太长，规则失效

IDENTITY.md 超过 200 行或约 8000 token 后，模型很容易只关注前半部分，后面的规则被忽略。

**做法**：冷热分离。高频规则留在 IDENTITY.md，冷门规则放到 `docs/OPERATIONS.md`，由 Agent 按需读取。

### 2. 把敏感信息写进去

不要把 token、内网地址、数据库密码、用户数据样例放进 IDENTITY.md。身份文件会被频繁加载，可能进入日志、调试输出或模型上下文。

**做法**：只写“去 data/ 目录读取凭证”，不写凭证本身。

### 3. 过度拟人化

“你是一个追求完美的工程师”这类句子对实际行为约束很弱。

**做法**：改成“默认先给方案，再给代码，最后给验证命令”。

### 4. 情绪化记录

“上次你又把 data/ 删了”这种写法没有可执行价值，还会让 Agent 生成防御性输出。

**做法**：写成可验证规则：“当目标路径包含 data/ 时，先输出只读提示，不要执行删除操作。”

### 5. 多版本漂移

本地、服务器、git 仓库各有一份 IDENTITY.md，内容逐渐不一致。

**做法**：把 IDENTITY.md 纳入版本控制，像评审代码一样评审身份更新。

### 6. 与 MCP 工具描述冲突

有些 MCP 工具描述会带“可以修改任意文件”之类的能力声明，与 IDENTITY.md 的约束打架。

**做法**：在系统提示词中明确优先级：项目 IDENTITY.md 的 scope 约束高于工具默认描述。

## 可复用建议

- **保持短小**：控制在 150–250 行，优先保留高频约束。
- **结构化条目**：所有规则尽量用“触发条件 / 期望行为 / 验证方式”格式。
- **冷热分离**：热规则在 IDENTITY.md，冷规则在 docs。
- **版本化**：IDENTITY.md 跟随项目 git 仓库，更新要提交、要说明原因。
- **定期复盘更新**：不要等 Agent 完全跑偏再改，每次任务收尾时追加一条有效记录。
- **开放一个调试入口**：可以给 OpenClaw 加一个 `/identity` 命令或 MCP tool，让 Agent 输出它当前加载的身份文件内容，便于排查是否加载成功。

## 总结

IDENTITY.md 不是让 AI 更像人，而是让它更像一个可靠的工程组件。

它解决的核心问题是：**在一个多工具、多插件、多会话的 OpenClaw 环境里，Agent 的行为规则是否有稳定来源、能否随时间演进、是否可以回滚和评审。**

先建一个最小文件，接入加载链，再通过复盘逐步进化。不要一开始就追求完整，保持短小、可验证、可更新，比写一份完美的“AI 人设”有用得多。
