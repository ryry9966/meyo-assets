## 背景

E2E 测试是保障核心流程的最后防线，但编写和维护成本极高。我们团队维护着一套基于 Playwright 的测试套件，覆盖约 200 条用例。每次 UI 调整，选择器失效、断言错误频发。我们试过让 ChatGPT 直接生成测试代码，但结果往往“形似神非”：能跑通 happy path，边界条件和断言经常出错，代码结构混乱，后续几乎无法维护。后来我们尝试引入 Agent 协作，把“写测试”变成一个多步骤的工程流程，效果有明显改善。

## 问题拆解

直接让大模型写测试的缺陷主要有三个：

1. 不了解页面真实结构，易产生不存在的选择器；
2. 不知道测试数据的约束，只考虑理想路径；
3. 生成的代码结构混乱，没有 Page Object 等抽象，难以维护。

单轮生成无法解决这些问题，需要引入一个带反馈循环的 Agent 系统。

## 做法：四阶段 Agent 流水线

我们基于 OpenClaw 生态内的 Agent 能力，结合 MCP（Model Context Protocol）搭建了一个“探索-计划-生成-验证”的迭代管道。

### 1. 页面探索阶段

Agent 通过 MCP 调用 Playwright 浏览器的 DOM 快照接口，浏览目标页面，提取可见元素的 role、label、test-id 等语义信息。Agent 会记录页面的关键交互路径和可能的断言点（如文案、状态变化）。这一步解决选择器脆弱问题，让后续生成基于真实 DOM 而不是想象。

### 2. 测试计划生成

Agent 根据需求描述（例如“用户登录后修改密码”）加上探索到的页面信息，生成一个结构化测试计划：包含前置条件、操作步骤、每一步的断言、后置清理。计划用 JSON Schema 约束，避免自然语言歧义。这一步相当于让模型先思考“测什么”，再考虑“怎么写”。

### 3. 代码生成与约束

Agent 按照测试计划和预设的 Page Object 模板生成 Playwright 测试代码。我们强制要求使用 data-testid 优先、role 次之、避免 CSS 路径。同时用 ESLint 和 Prettier 规范代码格式。生成的代码会先经过静态检查，不通过则自动修复或重新生成。

### 4. 执行验证与反馈

生成的测试直接由 Agent 通过 MCP 调用 Playwright 执行。如果测试失败，Agent 会分析失败原因（选择器问题、断言问题还是真实 bug），并决定是否修改代码后重试。设置最大重试次数为 3 次，避免死循环。

## 踩坑点

- **幻觉依然存在**：即使有 DOM 快照，Agent 偶尔会“脑补”不存在的元素，特别是在动态加载或 iframe 场景。解决方案是要求 Agent 在生成代码前，对每个关键选择器执行一次存在性检查。
- **测试数据污染**：E2E 测试常需要独立数据。Agent 生成的代码如果硬编码数据，会导致重复运行冲突。后来我们改为让 Agent 调用测试数据工厂，生成随机或隔离的数据。
- **执行循环死锁**：当测试失败原因模糊时，Agent 可能反复修改但问题依旧，消耗大量 token 和时间。我们设置了“失败分类器”，区分环境问题、选择器问题和产品 bug，只有选择器问题才触发代码修改，环境问题直接标记为 skip，产品 bug 则输出报告。
- **成本控制**：完整探索+生成+验证一次平均消耗 50k-150k token。需要合理裁剪探索范围，只对变更页面做增量探索，而不是每次全量扫描。

## 可复用建议

- **把 Agent 当作实习生，而不是全自动机器人**。给它明确的输入（需求+页面快照）、工具（MCP 浏览器控制）和验收标准（测试通过+代码 lint 通过）。
- **强制 Page Object 模式**，将页面元素定位集中管理，Agent 只修改 page object 相关文件，降低维护面。
- **建立“黄金路径”测试集**，让 Agent 在修改前先运行现有测试，确保不破坏已有功能。
- **记录 Agent 的决策日志**，方便人工审计和后续优化 prompt。

## 总结

Agent 协作写 E2E 测试不是“一键生成”的魔法，而是一个需要工程化设计的管道。我们的经验表明，通过探索-计划-生成-验证的闭环，配合 MCP 接入真实浏览器，可以把测试编写效率提升 2-3 倍，且生成的测试可维护性明显高于直接 LLM 输出。但不要期望零人工干预：边界用例、复杂交互和数据管理仍然需要测试工程师把控。务实的态度是让 Agent 处理重复的、结构化的部分，人类专注于策略和异常场景。
