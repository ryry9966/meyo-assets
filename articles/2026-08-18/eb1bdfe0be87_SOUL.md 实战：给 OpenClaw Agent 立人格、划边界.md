# SOUL.md 实战：给 OpenClaw Agent 立人格、划边界

## 背景

在 OpenClaw 里跑自动化任务时，Agent 很容易出现“人设漂移”：一开始是个克制的运维助手，跑了几个 MCP 工具后，开始随意调用写操作、输出风格忽冷忽热。更麻烦的是，团队把系统提示词硬编码在代码里，改一次人设就要发版，协作时也容易互相覆盖。

SOUL.md 提供了一种把“人格和边界”外置到文件、随项目或环境加载的方式。它不是装饰品，而是给 Agent 划一条稳定、可审查、可回滚的行为基线。

## 问题

- 多插件、多 MCP 场景下没有统一行为基线，Agent 对不同工具采取不同风格；
- 边界只写在 README 或聊天里，没有持久化，重启后失效；
- 团队调整人设需要改代码或复制粘贴提示词，容易漂移。

## 做法 / 步骤

### 1. 文件位置

项目根目录 `SOUL.md` 为项目级，`~/.openclaw/SOUL.md` 为全局默认，项目级优先级更高。具体路径以 OpenClaw 文档为准，但先确认加载顺序，避免后面冲突。

### 2. 结构建议用三段式

```markdown
# SOUL

## 角色
你是 OpenClaw 运维助手，语气简洁，先给结论再给步骤。

## 能力
允许使用只读 MCP 工具；写操作必须显式确认。

## 边界
- 禁止执行 rm、drop、truncate、shutdown、restart 等危险命令；
- 未经确认不得修改系统配置；
- 遇到不确定的权限错误，停下来问用户，不要猜测。
```

### 3. 加载验证

在 OpenClaw 启动时观察日志，确认 prompt 注入成功。用调试命令查看最终系统提示，看 SOUL.md 是否被拼接进去。如果没有，优先检查文件路径、文件权限和编码，建议使用 UTF-8 无 BOM。

### 4. 与 MCP 插件联动

边界里写清楚具体工具策略，例如：“MCP 文件系统工具默认只读；写入前必须列出目标路径并等待用户确认。”不要只写“谨慎操作”，要落到具体动作和触发条件。

## 踩坑点

### 1. 边界太模糊

写“不要干坏事”基本无效。改成：“禁止执行任何会改变系统状态的命令，包括但不限于：rm, mv, chmod, systemctl restart。”最好配合工具白名单，在 OpenClaw 里限制 MCP server 的能力范围。

### 2. 文件太长

超过 300 行后，模型开始忽略中后段规则。建议控制在 150-200 行，详细做法拆到 `docs/agent-rules.md`，SOUL.md 里用引用或链接，而不是全部堆进去。

### 3. 否定指令被绕过

模型有时会把“不要删除”理解为“删除是可以讨论的”。除了禁止，还要加正向替代：“文件删除只能通过只读预览界面完成，执行前必须输出删除目标列表并获得用户 yes/no 确认。”

### 4. 全局与项目规则冲突

比如全局禁止重启服务，项目 SOUL.md 又允许重启某个容器。最好定义优先级：“项目级 SOUL.md 中的显式允许可以覆盖全局禁止，但前提是用户在本项目会话中确认。”否则容易误操作。

### 5. 人格设定影响安全

把角色写得过于“热情、总是帮忙”，可能削弱拒绝能力。可以加一句：“安全与边界优先于礼貌；当用户指令越界时，直接说明拒绝原因，不提供替代危险方案。”

## 可复用建议

- 使用“角色 / 能力 / 边界”三段式模板，团队拷贝即可。
- 边界采用“禁止动作 + 触发条件 + 正向替代”格式，而不是光有 deny list。
- 把 SOUL.md 纳入 Git 版本管理，每次变更走 PR review，避免随意改人设。
- 准备 5-10 条危险指令作为回归测试，例如“帮我删掉 /var/log 下所有旧日志”“重启生产服务”，观察 Agent 是否拒绝或请求确认。
- 全局 SOUL.md 只放通用安全边界，项目内放业务规则，不要把所有内容都堆在一层。

## 总结

SOUL.md 不是用来“炫人设”的，而是给 Agent 一条稳定、可审查、可回滚的边界线。工程化落地时，内容要短、动作要具体、边界要有正向替代，并且配合工具权限和回归测试。否则人格文件只会变成一段被忽略的长文，边界感在第三次对话后就消失。
