## 背景

大多数 AI 助手还是“叫一下动一下”：你发指令，它执行。真正想要的是它能在 CI 挂了、服务异常、依赖过期、issue 长时间无人认领时主动介入。这种“不等你开口就把事情办了”的能力，在 agent 体系里叫 proactive。

OpenClaw 的 agent 框架提供了定时触发、事件驱动和 MCP 工具接入。利用这些能力，可以让 agent 周期性检查外部状态，遇到异常时先分析、再通知或执行有限动作。本文记录我在 OpenClaw-CN 环境中做的一个 proactive 实例：CI 失败主动排查与通知。

## 问题

我们团队的 CI 失败经常发生在夜间或跨时区协作时。等第二天人工发现，已经错过最佳修复窗口。最初的方案是直接接 Prometheus Alert 推送到飞书，但 alert 只有“失败了”，没有“为什么失败”。于是我用 OpenClaw 做一个 proactive agent：定时拉取 CI 失败任务，分析日志，输出结论，按严重程度决定是通知还是自动重试。

## 做法/步骤

### 1. 明确触发源和频率

在 OpenClaw 中配置 cron trigger。我们选择每 15 分钟检查一次 GitHub Actions 最近失败记录，避免实时 webhook 带来的洪峰。关键代码大概是这样：

```yaml
tasks:
  - name: ci-failure-watchdog
    schedule: "*/15 * * * *"
    input:
      source: github
      repo: openclaw-cn/openclaw
      event: workflow_run_failed
      since: 15m
```

### 2. 用 MCP 工具取数，而不是直接塞原始日志

最初我把整个失败日志直接作为上下文传给模型，结果 token 消耗巨大，而且模型容易被堆栈噪音带偏。后面改为先用 MCP 工具拉取结构化数据：失败步骤名、退出码、日志尾部 200 行，再用一个小脚本过滤掉常见的无关输出（如 `##[debug]`）。

### 3. 写清代理行为边界

这一步很重要。我在 prompt 里约束 agent：

```text
你是 CI 值守代理。只做以下事情：
- 判断失败原因是否已知 flaky（基于历史标记）
- 如果是 flaky，调用 ci_retry 工具重试一次
- 如果不是，提取关键错误并通知到飞书
- 禁止修改代码、禁止关闭 issue、禁止执行超过一次重试
```

这样避免 agent 自作主张把代码“修坏”。

### 4. 半自动运行一周

第一周只发通知，不执行任何自动重试。让团队观察误报率和分析准确率。第二周才开放自动重试，并且每次重试都附带 agent 的分析依据，方便人工复核。

## 踩坑点

**触发循环**：有一次 agent 自动重试后又失败，又触发新事件，陷入重试风暴。解决方案是给每个 workflow run 加幂等 key，已处理的事件不再重复触发；同时对同一任务的一小时内重试次数做上限。

**上下文爆炸**：直接把日志倒给模型，单次成本能翻十倍。改成结构化取数 + 尾部截断后，单次 token 从 3 万降到 3 千。

**静默失败**：proactive 任务没有用户主动盯着，如果 cron 没跑起来，你可能很久才发现。建议对 agent 本身加 heartbeat 监控，比如让它每隔 6 小时向运维群发一次“我还活着”。

**权限过大**：最早我给 agent 配了 `repo write` 权限，发现它分析日志时会“顺手”修改 issue 标签。后来改成最小权限：只读 + 重试权限 + 通知权限，其他一律不给。

## 可复用建议

- **从通知开始**：先让 agent 只做“发现 + 分析 + 通知”，跑稳后再放开执行权限。
- **事件 schema 化**：所有外部事件统一转成固定 JSON 结构，方便 agent 和日志系统处理。
- **把 agent 当 pipeline 的一步**：不要让它端到端全包。预处理、去重、限流、持久化都可以在 OpenClaw 的任务插件层完成，模型只做最擅长的那部分。
- **记录每一次 proactive 决策**：保留输入、输出、执行结果。这样当 agent 做错时，你能回溯它当时的上下文，而不是猜。
- **设置人工熔断**：给 proactive 任务配一个手动开关，比如 `/ci watchdog off`，一旦发现异常可以快速停掉。

## 总结

Proactive 能力不是“让模型更聪明”，而是把触发、取数、过滤、权限、监控这些工程链路搭好。OpenClaw 的定时任务、MCP 工具和插件机制足够实现一个可靠的 proactive agent。关键是控制边界、保留人工介入路径、做好可观测性。做到这些，你的助手才能真正“不等开口就把事办了”，而不是变成一个制造惊喜的自动化事故源。
