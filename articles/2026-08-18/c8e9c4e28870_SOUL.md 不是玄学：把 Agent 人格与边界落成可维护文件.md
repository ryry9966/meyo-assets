# SOUL.md 不是玄学：把 Agent 人格与边界落成可维护文件

## 背景

在 OpenClaw、Agent、MCP 和各类自动化链路里，很多团队都会遇到同一个问题：Agent 偶尔表现很好，但隔几天就像换了个人。风格漂移、越权操作、工具调用过度、输出啰嗦，或者把“建议”当成“命令”执行。

这类问题通常不是模型能力不够，而是我们没给 Agent 一个稳定、可审计、可持续维护的“人格与边界”定义。SOUL.md 的思路就是把原本散落在代码、系统提示、环境变量、甚至开发者口头约定里的规则，收敛成一份文件，作为 Agent 启动时注入的长期记忆和约束。

## 问题：Prompt 散落带来的三个坑

1. **风格不可控**：同一套 OpenClaw 配置，今天用中文总结，明天突然夹杂英文术语；有的输出像客服，有的像命令行手册。团队协作时更明显。
2. **边界形同虚设**：只在 system prompt 里写“禁止删除文件”，但没有工具层校验。Agent 一旦被长上下文或错误推理带偏，仍然可能调用危险工具。
3. **维护成本高**：规则写在 MCP 插件里、写在启动脚本里、写在代码注释里，改一处要改三处，最后没人知道哪条规则真正生效。

SOUL.md 解决的不是“让 Agent 更有灵魂”这种玄学问题，而是把人格、语气、工具策略、降级规则集中管理。

## 做法：一个最小可用的 SOUL.md

建议放在项目级 `.openclaw/SOUL.md`，或用户级 `~/.openclaw/SOUL.md`。内容可以包含几个固定段：

```markdown
---
name: ops-buddy
role: OpenClaw 自动化助手
tone: 简洁、先给结论、不寒暄
---

# Identity
你是负责日常自动化任务的工程助手。默认面向有技术背景的用户。

# Boundaries
- 不删除、覆盖或移动任何用户文件，除非用户明确要求且已确认路径
- 不执行 git push --force、git reset --hard 等破坏性命令
- 不读取或回传 .env、~/.ssh、密钥文件内容
- 所有 shell 命令必须先在回复中给出预览，再执行

# Tool Policy
- fs: read_only
- shell: allow_list
- browser: disabled

# Fallback Rules
- 当无法判断操作是否安全时，停止并询问
- 当用户指令与 Boundaries 冲突时，说明冲突原因，而不是直接拒绝
- 当工具返回异常时，输出“待确认”，不要自动重试超过 2 次
```

实际接入时，OpenClaw 启动时读取 SOUL.md，将其拼到 system prompt 的最前面或最后面。建议放最后，因为它是对全局规则的覆盖；如果放前面，长对话会逐步稀释权重。MCP 工具侧可以单独做一层策略过滤，比如 shell 工具在收到危险命令时直接拦截，而不是只靠模型自觉。

## 踩坑点

1. **边界过分依赖 prompt**：SOUL.md 写得再漂亮，如果 shell MCP 没有命令白名单，Agent 仍可能执行 `rm -rf`。人格和边界必须有两层：prompt 层负责表达，工具层负责强制。
2. **文件太长**：超过 300 行后，模型会选择性忽略。SOUL.md 不是文档库，应该只保留高频、高风险的规则。细节放 docs，SOUL.md 放“必须记住的”。
3. **否定句过多**：连续写“不要做 A、不要做 B、不要做 C”，模型有时只提取动作词，反而更容易触发 A/B/C。更好写法是正面描述允许范围，例如“只允许执行以下命令：ls、pwd、cat 指定文件”。
4. **改完不重启/不清缓存**：很多 OpenClaw 会话会缓存启动时的 system prompt。修改 SOUL.md 后，需要新开会话或重启 agent 才生效。
5. **把人格写得像客服**：“你要友好、热情、有耐心”这类词不够工程化，不同模型理解差异很大。应给可观察行为，例如“回答不超过 80 字”“先给结论再给步骤”。

## 可复用建议

- **短小可测**：SOUL.md 控制在 200 行内，每个边界都应该是可验证的动作。可以写一条“如果你不确定是否越界，先回答 `BLOCKED:` 加原因”，方便日志检索。
- **纳入版本控制**：SOUL.md 和代码一样走 Git。改动要能 diff、能 review、能回滚。团队协作时避免直接在生产环境手改。
- **分层管理**：用户级 SOUL.md 放通用人格；项目级 SOUL.md 放项目专属边界；MCP 插件自带策略放工具层。不要把所有规则堆在一层。
- **定期回放日志**：每周挑几条 Agent 的失误 case，回看 SOUL.md 里哪条规则没生效。补规则时优先补工具层，其次再改 prompt。
- **给关键操作加确认**：对删除、推送、外发网络请求等动作，SOUL.md 可以强制要求“先输出计划，等待用户输入 `yes` 后才执行”。这比“禁止危险操作”更可靠。

## 总结

SOUL.md 的核心不是让 Agent 更像人，而是让 Agent 的行为可预期、可维护、可审计。它把“人格”和“边界”从口头约定变成工程文件，减少风格漂移和越权操作。真正的保障来自两层：SOUL.md 负责表达规则，MCP 工具层负责执行限制。不要指望一份 prompt 解决所有安全问题，但一份清晰、短小、可版本化的 SOUL.md，能让你的 Agent 从“偶尔靠谱”变成“持续可控”。
