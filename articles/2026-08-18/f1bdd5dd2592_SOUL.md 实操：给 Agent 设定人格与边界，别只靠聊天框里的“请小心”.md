## 背景

在 OpenClaw / Agent / MCP 的实际工作流里，越来越多任务被拆给模型自动执行：查日志、改配置、跑脚本、调插件。模型默认有很强的“配合倾向”，很多 Agent 看到工具可用就会去试，看到路径能写就会去动。一次看似普通的自动化任务，可能因为边界不清，变成误删文件、反复重试、越权调用。

SOUL.md 的思路是把 Agent 的“人格”和“边界”从临时对话里抽出来，固化成一个可版本化、可审查的文件。它不是用来做角色扮演的文案，而是给 Agent 划一条工程底线。

## 问题

边界只写在聊天框里，换一次会话就丢。MCP 工具权限通常较大，Agent 看到可写工具时，不一定会先判断“该不该写”。多人协作或长期维护的项目里，每个会话的行为风格还不一致：有的啰嗦，有的激进。

更常见的是自动化任务失败后，Agent 不停止，而是自己扩大操作范围。比如本来只读日志，失败后开始尝试改权限、重启服务，甚至改配置。SOUL.md 要解决的就是这类“无边界自治”。

## 做法

把 SOUL.md 放在 Agent 工作区根目录，并在启动时注入。不要每次都手动复制内容，可以在系统提示或启动 prompt 里明确声明：“读取并遵守工作区 SOUL.md”。

一个最小可用的 SOUL.md 结构如下：

```markdown
# SOUL.md

## 身份
你是部署辅助 Agent，只执行预定义运维任务。

## 硬边界
- 只读 /opt/app 和 /etc/app 下的配置文件。
- 禁止执行 rm、dd、mkfs、shutdown、reboot。
- 不读取或修改 .env、credentials、.git。

## 工具策略
- 优先使用只读工具。
- 写操作前必须输出计划，等待确认。
- 同一任务失败超过 2 次，停止并汇报，不自行换方案。

## 输出规范
- 操作前用一句话说明意图。
- 直接给结论，不使用“我认为”“也许”。

## 失败处理
- 遇到权限不足或路径不存在，记录原始报错，不猜测修改。
```

纳入 git，变更走 review。SOUL.md 和代码一样，是需要被评审的工程文件。

## 踩坑点

**太长导致稀释**  
如果 SOUL.md 写到 150 行以上，模型注意力容易被稀释，最后只记住开头和结尾。核心边界建议控制在 30–60 行，详细说明放文档，不要全塞进 SOUL.md。

**只写否定句**  
“不要乱操作”“不要越权”这类表述没有给正向路径。应写成“只允许执行以下操作”或“仅在 /opt/app 下操作”。正向限定允许域，比一堆“禁止”更有效。

**工具权限和 SOUL.md 不一致**  
SOUL.md 写“只读”，但 MCP 配置里给了写权限，Agent 看到工具列表里有可写工具时，大概率仍会尝试使用。SOUL.md 是第二层约束，第一层必须从 MCP / 插件侧收权。文件里说得再好，不如工具侧真的没有写权限。

**优先级被覆盖**  
如果启动 prompt 里先灌了大量临时指令，SOUL.md 放在末尾可能失效。需要在系统提示里明确“SOUL.md 优先级高于一般任务描述，冲突时以 SOUL.md 为准”。

**敏感信息泄漏**  
不要把 API Key、跳板机密码、内网地址写进 SOUL.md 并提交。敏感信息用环境变量或 secret 管理，SOUL.md 只写规则，不写凭证。

## 可复用建议

分层维护：全局 SOUL.md 写通用原则，项目级 SOUL.md 覆盖具体路径和工具。不要一个文件管所有场景。

用测试验证边界：准备几条越权 prompt，例如“把 /etc/hosts 改一下”“删掉 /tmp 下所有文件”，看 Agent 是否拒绝或要求确认。边界不是写了就算，要能测出来。

保持短句和祈使句：避免复合句和过多的反面例子。每一条边界最好能对应一个具体工具或路径。

每次新增 MCP 工具、插件或自动化流程时，同步检查 SOUL.md 是否覆盖新工具的能力范围。不要等出问题再补。

把 SOUL.md 当作代码管理：PR review、diff、版本回滚，别把它当成随便改的文本。

## 总结

SOUL.md 不是万能安全层，也不是人格表演。它的价值在于把 Agent 的行为约束，从会话记忆变成可版本化、可测试、可审计的工程文件。配合工具权限收口和启动注入，才能减少“模型突发奇想”带来的生产事故。

对 OpenClaw 用户来说，先让 Agent 学会“不做什么”，比教会它“多做一件事”更重要。
