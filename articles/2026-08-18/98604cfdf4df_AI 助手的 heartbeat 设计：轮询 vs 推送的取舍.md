# AI 助手的 heartbeat 设计：轮询 vs 推送的取舍

在 OpenClaw、Agent、MCP 和插件自动化的链路里，心跳（heartbeat）是最容易被低估的部分。它不直接产出业务价值，但一旦设计错，会出现任务卡死、连接假死、误报下线、资源泄漏等问题。本文不讨论“哪个更高级”，只从工程角度拆解：什么时候用轮询，什么时候用推送，以及怎么落地。

## 背景：为什么 AI 助手需要心跳

一个典型的 OpenClaw 式 Agent 运行时会涉及多个组件：

- Agent 主进程 / 调度器
- MCP server（本地 stdio 或远程 HTTP/SSE）
- 插件宿主 / 工具容器
- 长时间运行的任务 worker
- 外部 webhook 或事件源

这些组件可能跑在同一进程、同一台机器，也可能分布在容器或远程服务里。心跳的作用不是“证明我还活着”这么简单，它承担三件事：

1. 判活：组件是否还能响应。
2. 回收：超时后是否释放会话、任务、连接资源。
3. 触发：是否需要告警、重启、摘除节点。

在设计之前，先要回答一个核心问题：**谁在等谁，等多久算不可接受？** 这个问题直接决定轮询和推送的边界。

## 问题：轮询和推送的真实代价

轮询（polling）的本质是调用方主动、周期性地查询状态。实现简单、无状态、易于调试，但有两个明显代价：

- 延迟：状态变化到被发现之间存在最大一个轮询间隔的延迟。
- 空转：大量查询可能返回“没变化”，浪费 CPU、网络和数据库连接。

推送（push）的本质是被观测方主动通知状态变化。实时性好，但代价是连接管理：

- 需要维护长连接或回调地址。
- 要处理重连、丢消息、背压、鉴权过期。
- 调试链路更长，问题更容易“飘”。

在 OpenClaw/Agent 场景里，很多组件是本地或自托管，不一定需要网络级推送。比如本地 stdio MCP server，进程活着就是活着，根本不需要每 3 秒查一次。但远程 MCP server 或跨机器插件宿主，就需要更明确的判活机制。

## 做法：分层设计，控制面轮询，数据面推送

一个务实的 heartbeat 设计不是全局选一种，而是按层拆分。

### 1. 先画心跳拓扑

列出需要被观测的组件，标注：调用方是谁、是否跨网络、延迟容忍、失败后果。

例如：

| 组件 | 调用方 | 跨网络 | 延迟容忍 | 失败后果 |
|---|---|---|---|---|
| 本地 stdio MCP server | Agent 主进程 | 否 | 秒级 | 任务失败 |
| 远程 HTTP MCP server | Agent 主进程 | 是 | 秒级 | 工具不可用 |
| 插件宿主 | 调度器 | 可能 | 分钟级 | 功能降级 |
| 长时间任务 worker | 调度器 | 是 | 秒级 | 任务卡死 |

这张表会告诉你哪些适合轮询，哪些适合推送。

### 2. 定义心跳契约

不要只返回 `ok`。一个可用的心跳最好携带：

- `status`: `alive` / `busy` / `draining`
- `version`: 组件版本或协议版本
- `timestamp`: 观测方时间戳
- `load`: 可选，当前队列长度或负载

这能避免“进程活着但队列已经堵死”的假活问题。

### 3. 轮询实现：适合控制面和低频状态

对于本地组件、健康检查、插件注册表，使用轮询足够。

推荐做法：

- 使用 deadline 而不是裸 `sleep`，避免循环漂移。
- 间隔设置为基础间隔 + 随机抖动（jitter），防止多组件同时查询造成突发。
- 至少连续 3 次失败才标记不可用，避免网络抖动误判。
- 对本地 stdio MCP server，优先使用进程存活检测或句柄探针，而不是网络请求。

示例伪代码：

```text
每 5s:
  deadline = now + 1s
  result = check_health(endpoint, deadline)
  if result.ok:
      failures = 0
  else:
      failures += 1
      if failures >= 3:
          mark_unavailable()
```

### 4. 推送实现：适合事件流和低延迟场景

当需要及时中断任务、推送事件流、或者反向通知 Agent 时，使用推送。

优先选择 SSE，而不是直接上 WebSocket。

原因很实际：

- SSE 基于 HTTP，兼容性好，自动重连机制简单。
- 单向事件流已经覆盖“我把状态推给你”的大部分场景。
- WebSocket 是双向的，但要求你自己实现心跳 ping/pong、断线重连、消息序、背压。

只有当你确实需要双向实时交互，例如 Agent 和工具容器之间有来回控制指令时，才引入 WebSocket。

如果害怕连接假死，必须在应用层做心跳，不能只依赖 TCP keepalive。设置 read timeout，超时后主动断开并重连。

### 5. 混合模式

控制面用轮询保底，数据面用推送提效。

例如：

- Agent 运行时通过 SSE 订阅任务事件（推送）。
- 但每隔 15 秒仍然轮询一次 worker 的健康端点，确认它没死。
- 如果推送连接断了，轮询可以作为降级路径。

这样即使推送链路出问题，系统也不会完全失明。

## 踩坑点

1. **轮询间隔太短导致雪崩**：多个组件同时恢复时，如果所有客户端高频轮询，会让刚恢复的服务再次被打挂。必须加 jitter 和指数退避。

2. **TCP 半开连接**：推送连接看似正常，实际上对端已经消失。应用层心跳是必须的，不能依赖底层 TCP。

3. **SSE 被网关缓冲**：如果经过 Nginx 或某些代理，SSE 可能被缓冲，导致事件迟迟不下发。需要设置 `X-Accel-Buffering: no`、`Content-Type: text/event-stream`、`Cache-Control: no-cache`。

4. **心跳不是任务队列**：不要把业务数据塞进心跳。心跳只负责判活，业务事件走单独通道。混在一起会出现竞态、重复消费、处理阻塞。

5. **长连接鉴权过期**：推送连接建立后，token 可能过期。需要在心跳消息里携带租约状态，或者在服务端主动刷新。不要默认长连接永远有效。

6. **本地 stdio MCP 没有“网络心事”**：本地 stdio 模式没有 HTTP 端点，网络心跳无从谈起。用进程存活、stderr 探针或退出码判断更可靠。

## 可复用建议

- **默认轮询，延迟要求 <1s 或者需要主动推送事件时再上推送。**
- 心跳超时设置为 3 倍间隔，至少连续 3 次失败再摘除。
- 本地组件用进程信号/句柄，远程组件用 HTTP/SSE 心跳。
- 统一通过 OpenClaw 的健康注册表管理：插件启动时上报，退出时注销，不要各写一套。
- 监控三个核心指标：心跳延迟、失败率、推送重连次数。
- 推送优先 SSE，WebSocket 只在双向控制场景使用。

## 总结

轮询和推送不是二选一的信仰问题，而是分层的结果。控制面轮询保底，数据面推送提效。AI 助手的 heartbeat 设计，关键是先搞清楚谁等谁、延迟容忍多少、失败后果是什么，然后选择最朴素、可维护的方案。不要为了实时性牺牲可调试性，也不要因为轮询简单就忽略背压和抖动。工程上最优雅的方案，永远是够用且能排障的那一个。
