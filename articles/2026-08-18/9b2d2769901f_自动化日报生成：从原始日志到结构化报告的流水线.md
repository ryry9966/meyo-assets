## 背景

个人或小团队写日报时，素材往往散落在 Git 提交、CI 构建日志、监控告警、业务指标和工单记录里。人工汇总要频繁切换系统、复制粘贴、判断哪些值得写，最后产出的日报还可能漏掉关键风险。

自动化日报的常见做法是直接把原始日志丢给 LLM，让它“生成一篇日报”。这样很容易得到一个看起来通顺、但偏离事实的结果：要么只堆砌日志，要么编造完成项。更务实的做法是把它当成一条小型数据流水线：采集 → 清洗/结构化 → 约束生成 → 校验 → 投递。

## 问题

原始日志有三个明显问题：

1. **多源异构**：git log、CI logs、告警记录、任务系统的字段和格式完全不同。
2. **噪音大**：构建日志里充满依赖下载、缓存命中、DEBUG 行，直接进上下文会消耗大量 token。
3. **时间与归因混乱**：提交时间、触发时间、完成时间可能跨天，甚至来自不同时区。

如果不在进入 LLM 前处理这些问题，日报生成就会不稳定，时而好时而差。

## 做法/步骤

### 1. 先定义日报 schema

不要一上来写 prompt，先固定结构化字段。例如：

```json
{
  "date": "2025-01-15",
  "projects": ["backend"],
  "completed": [],
  "in_progress": [],
  "risks": [],
  "metrics": {},
  "next_steps": []
}
```

这能约束后续生成，也方便程序校验和归档。

### 2. 采集层：用 MCP 统一数据源

把每个系统封装成 MCP server，由 Agent 通过工具调用获取结构化返回。例如 `git-mcp` 暴露 `list_commits(since, repo)`，`ci-mcp` 暴露 `list_pipelines(since)`，`monitor-mcp` 暴露 `list_alerts(since)`。

工具返回尽量是 JSON，而不是 Markdown 或 HTML：

```json
{
  "source": "git",
  "repo": "backend",
  "commits": [
    {
      "hash": "abc123",
      "message": "fix: retry queue overflow",
      "timestamp": "2025-01-15T22:10:00+08:00"
    }
  ]
}
```

每个条目保留 `source` 和原始链接或 hash，便于日报追溯到证据。

### 3. 清洗与归一化

在 Agent 内部加一个轻量预处理步骤，不一定要 LLM：

- 过滤依赖下载、缓存、DEBUG 行；
- 对超长日志做头尾保留 + 最大长度截断；
- 统一时间为 `YYYY-MM-DD HH:mm:ss+08:00`；
- 标记来源、仓库、触发人。

清洗后的数据才是进入 prompt 的上下文。

### 4. 生成层：模板与数据分离

把 prompt 模板和数据分开维护，不要每次拼一大段自然语言。模板可以类似：

```text
你是日报生成器。仅根据下方 JSON 数据生成日报。
要求：
1. 每个结论后附加来源 ID，如 [git:abc123]；
2. 数据中没有的内容不要补充；
3. 缺失字段写“无记录”；
4. 按四段输出：完成 / 进行中 / 风险 / 下一步。
数据如下：
{{cleaned_json}}
```

这样比让模型自由发挥稳定得多，也方便版本化管理。

### 5. 校验与投递

生成后用一个简单脚本校验：日期是否正确、来源 ID 是否都能在原始数据中找到、有没有明显幻觉字段。校验通过后再通过插件推送到飞书/企微/邮件。投递失败时保留本地 Markdown，避免重复推送。

## 踩坑点

1. **时区不一致**：git 可能用本地时间，CI 用 UTC，合并后日期错位。最好在采集层统一转换，不要留到生成层。
2. **长日志直接塞给 LLM**：几万行 CI 日志会挤爆上下文，模型容易忽略中段信息。必须清洗和截断。
3. **模型自动补全未发生的事**：看到“修复重试队列”就写“已上线”。要求每个结论带来源 ID，并且校验来源是否存在。
4. **MCP 返回结构变化**：有些 MCP server 会改返回格式或返回 Markdown。封装一层 adapter，统一输出固定字段。
5. **空数据生成空报告**：定时触发时当天可能没有提交或告警。采集后先判断是否为空，为空则跳过或发送简短“今日无记录”，不要硬生成。

## 可复用建议

- 先做采集和清洗，再接 LLM。数据质量决定日报质量。
- 用 MCP 封装数据源，而不是在 prompt 里硬编码 shell 命令，便于替换工具、做权限控制和缓存。
- 保留 commit hash、告警 ID、原始链接。可追溯的日报才有工程价值。
- prompt 模板、清洗规则、schema 都做版本控制。
- 流水线尽量幂等：同一天跑两次结果一致，不重复投递。

## 总结

自动化日报不是“让 LLM 读日志写总结”，而是一条小流水线：结构化采集 → 清洗归一 → 约束生成 → 校验投递。每一步都可以做得轻，但缺一步都可能让日报从工具变成负担。对 OpenClaw/Agent 用户来说，最实际的落地方式是一个 MCP 数据源 + 一个稳定模板 + 一个校验脚本，先跑通 80% 的日常汇总，再逐步增加智能归因。
