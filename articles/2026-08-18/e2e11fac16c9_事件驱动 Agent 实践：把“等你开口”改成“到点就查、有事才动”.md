## 背景

多数 OpenClaw/Agent 实践里，助手像接线员：用户发消息，触发工具调用。查日志、发报告、重启服务，基本都得先有人开口。一旦没人盯着，告警进了群也没人处理，巡检任务被遗忘。

Proactive 能力不是让模型“更主动地聊天”，而是让 Agent 具备事件驱动和定时触发能力，在满足条件时自己执行工具，并在有副作用前留好审批和审计。

## 问题

直接给 Agent 加个 cron 并不难，难在边界：

1. 误触发后无回滚；
2. 工具副作用不可控；
3. 决策链太长导致上下文膨胀；
4. 通知轰炸，最后没人看。

没有分级和确认机制，proactive 很快会变成“半夜自动重启生产环境”。

## 做法：四层结构

我落地时用四层：

**事件源 -> 策略层 -> 执行层 -> 记录/通知**

### 1. 事件源：两种够用

- 定时巡检：cron 每 30 分钟跑一次。
- 外部事件：webhook 接收 GitLab、监控、工单事件。

在 OpenClaw 里，外部事件可以通过一个极简 MCP server 暴露 `subscribe_event` / `list_events`，事件先写入本地 SQLite 队列，避免直接触发模型。这样事件可以去重、限流和重放。

### 2. 策略层：别让模型自由发挥

先定义 JSON 规则，模型只做规则内的判断。例如：

```json
{
  "id": "disk_high_001",
  "trigger": "cron:disk_check",
  "condition": "disk_usage > 85",
  "action": "send_summary_to_ops",
  "approval": "auto_if_low_risk",
  "max_runs_per_day": 3
}
```

模型收到事件后，调用 `check_disk` 工具获取数据，再判断是否满足 `condition`。判断要求结构化输出，不输出自由文本。结构化结果便于执行和审计，也能避免模型“给自己加戏”。

### 3. 执行层：分级执行

- **L0：只读/通知**，自动执行。如查询证书到期、生成日报。
- **L1：低风险变更**，dry-run 后自动执行。如清理超过 7 天的临时文件。
- **L2：高风险操作**，必须审批。如重启服务、改 DNS、批量删除。

工具声明时注明级别，执行前统一走 `preflight`：是否白名单、是否幂等、是否在维护窗口。L2 先挂起，等人确认。

### 4. 记录/通知

每次 proactive 执行写 `event_log`：事件 ID、规则 ID、判断依据、工具调用、结果、副作用。通知只发摘要，不逐条轰炸。连续同类事件合并后再发。

## 踩坑点

- **阈值抖动导致误触发**：磁盘 85% 可能刚清理完又触发。规则里加冷却时间，同一规则 2 小时内不重复执行。
- **webhook 重复投递**：必须按事件 ID 去重，否则会并发执行多次。
- **工具副作用比想象大**：`cleanup` 可能误删白名单外文件。清理类命令先列清单，确认后再删。
- **模型自由度过高**：如果让模型自己决定“要不要执行”，它会倾向于每次都有动作。限制候选动作，不允许模型发明新工具组合。
- **通知太多**：proactive 的价值是减少人工，不是把人工变成处理通知流水线。

## 可复用建议

1. **先上影子模式**：只记录不执行，跑一周看准确率。准确率 > 95% 再自动执行 L0/L1。
2. **动作必须有幂等键**：例如清理任务用文件 hash 或日期后缀，防止重复执行。
3. **上下文不要无限长**：每次 proactive 任务用独立 session，只传事件上下文和工具结果；历史结论存外部存储。
4. **失败默认转人工**：模型判断失败或工具超时，不要自动重试高风险操作。
5. **设置全局预算**：每小时最多 20 次工具调用，每天最多 50 次写操作。
6. **通知带 `trace_id` 和 replay 入口**：方便回查为什么触发。

## 总结

Proactive 能力落地不靠模型“更聪明”，而靠事件源、规则、分级执行和审计闭环。先让助手在低风险、可回滚、可观察的范围内主动做事，再逐步放开 L2 审批。做到“不等你开口”，但每一步都留痕、可停、可回溯，这才是能上生产的 proactive。
