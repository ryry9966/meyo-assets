## 背景

大多数 AI 助手还是“问一句动一下”的 turn-based 工具。真正有价值的 proactive 不是让模型主动找你聊天，而是把监控、提醒、摘要、低风险维护从人工轮询里解放出来：CI 挂了它先汇总日志，工作日早上它先整理日历和未读邮件，依赖版本有安全公告它先查影响面。

问题在于，proactive 很容易被做成“每隔 5 分钟让 LLM 看一次世界”，token 爆炸、噪声多、权限不可控。本文面向 OpenClaw / Agent / MCP / 插件自动化实践者，给一套能落地的工程化拆法。

## 问题

想做 proactive 时，通常会撞上四个坑：

1. **触发不可靠**：轮询太密费 token，太疏漏事件。
2. **重复执行**：webhook 重试、事件重复投递，导致同一个问题被处理多次。
3. **权限过大**：为了让模型“主动办事”，直接给 shell / 发消息 / 写文件权限，一次误判就麻烦。
4. **打扰失控**：agent 太勤快，通知刷屏，最后被用户关掉。

所以要做的不是“让模型更主动”，而是把 proactive 拆成一条可观测、可回滚、可降级的 pipeline。

## 做法 / 步骤

### 1. 先选一件低风险、高确定、可回滚的事

不要一上来做“自动提交代码”或“自动回复客户”。推荐起点：

- CI 失败后，自动汇总最近 20 条日志和变更 commit，发给自己。
- 每个工作日早上，生成当日日历 + 未读重要邮件摘要。
- 检测到依赖安全公告时，列出受影响项目，只提醒不升级。

共同点是：**动作主要是读和汇总，写操作也有明确边界**。

### 2. 把触发源标准化成事件

不要直接让 LLM 去轮询网页或 API。优先使用 webhook，如果没有 webhook，再用 cron 做增量拉取。

在 OpenClaw 里可以让插件接收 webhook，或者由外部服务把事件推到一个统一入口。事件最好带上幂等键：

```json
{
  "id": "evt_01J9Q...",
  "source": "github",
  "type": "workflow_run.failed",
  "repo": "org/api",
  "branch": "main",
  "ts": "2025-01-01T08:00:00Z",
  "dedupe_key": "github:org/api:workflow:ci:main"
}
```

`dedupe_key` 不是给模型看的，是给执行器去重用的。

### 3. 策略层：先规则，再 LLM

不要每来一个事件都让 LLM 自由决定。先在代码里做静态过滤：

- 来源是否在白名单？
- 是否在冷却窗口内？
- 事件类型是否值得通知？
- 当前用户是否已经屏蔽该来源？

过滤完，再给 LLM 一个小上下文做决策。关键是把模型输出限制在**预定义动作集合**里：

```json
{
  "decision": "post_summary",
  "confidence": 0.87,
  "reason": "CI failed on main branch after merge",
  "allowed_actions": ["post_summary", "create_issue", "noop"]
}
```

LLM 只负责从已有动作里选，而不是现场生成工具调用。这样能大幅降低越权概率。

### 4. 执行器按风险分级确认

把动作分成三类：

- **低风险**：只读、只发给自己，自动执行。
- **中风险**：创建 issue、发群消息、生成 PR 草稿，先 dry-run 或要求确认。
- **高风险**：写生产、删除资源、外部发送，默认禁止，除非用户显式开启。

在 OpenClaw / MCP 工具封装动作时，建议直接让工具声明 `auto_approve: false`，由外层策略决定是否放行。不要让模型绕过确认。

### 5. 记录完整链路，支持回滚

每次 proactive 动作都应记录：

```text
event_id -> dedupe_key -> decision -> action -> result -> user_feedback
```

动作必须是幂等的。比如创建 issue 时用 `dedupe_key` 做唯一约束，重复事件来了不会重复创建。对创建类动作，至少要支持人工删除或标记为误报。

## 踩坑点

- **轮询风暴**：cron 每 5 分钟全量扫一次日历和邮件，token 很快就烧完。用增量游标 / 事件订阅，限制每次最大处理条数。
- **webhook 重复投递**：GitHub、企业微信等都可能重试。没有 `dedupe_key` 的 proactive agent 一定会重复执行。
- **上下文膨胀**：不要把最近 200 条日志和历史决策全塞给 LLM。只给事件摘要、受影响资源、可用动作定义。
- **时区错误**：做晨报或日历提醒时，必须用用户本地时区。服务器 UTC 8 点可能是用户的半夜。
- **模型越权**：开放任意 shell 或网络请求给 proactive agent，等于把定时炸弹设成自动引爆。用 allowlist tools + JSON Schema 限制动作。
- **通知疲劳**：一条 CI 失败发 5 条消息，比不发更糟。加冷却时间，或者合并成每日摘要。

## 可复用建议

1. **先跑影子模式**：只记录 decision 和 action，不实际执行，连续观察 3 天。看误报率、漏报率和重复率。
2. **从“通知我”开始**：先让 agent 生成摘要、建议、候选动作，用户确认后再逐步放开。
3. **永远保留 kill switch**：一条命令或一个环境变量就能全局禁用 proactive 执行。
4. **把 proactive 当 pipeline，而不是 prompt**：事件接入、去重、规则过滤、LLM 判定、动作执行、反馈回传，每一层都能单独测试和降级。
5. **收集用户反馈**：用户回复“停”“别再发了”“确认”都应进入状态，影响后续决策。

## 总结

proactive 不是让模型变聪明，而是让它在事件驱动、权限约束和可观测性的闭环里干活。最小系统可以简单到：

```text
webhook -> 去重 -> 规则过滤 -> LLM 选动作 -> 白名单执行 -> 发给自己
```

先做低风险、可回滚的事，跑通链路后再逐步放开权限。这样的 proactive agent 才能真正稳定运行，而不是三天后被关掉。
