## 背景

很多 OpenClaw 的 Agent、MCP、插件和自动化流程默认挂在云端模型上。云端 API 在延迟、限流、隐私和调试成本上都有不可控的地方：每次改提示词都要走网络，长任务可能被限速，内部数据也不一定方便外发。

家用电脑部署本地 LLM，不是为了替代云端大模型，而是提供一个离线、低成本、可反复调试的推理节点。跑得动小模型之后，很多意图分类、参数抽取、小段总结、MCP 工具编排测试都可以在本地完成，等流程稳定后再切云端大模型放大效果。

## 问题

家用电脑跑大模型的核心瓶颈不是“能不能跑”，而是：

1. 显存和内存带宽有限；
2. KV cache 会随上下文长度迅速吃掉显存；
3. 小模型工具调用能力不稳定，容易出现 JSON 格式错误或“只说不做”；
4. 本地生成速度较慢，Agent 默认超时时间可能不够；
5. 并发能力弱，多个自动化任务同时打进来容易排队甚至超时。

这些问题如果不在部署阶段控制住，后续接入 OpenClaw 时会出现大量诡异失败。

## 做法 / 步骤

### 1. 先盘点硬件

NVIDIA 独显最省心。8GB 显存是入门线，16GB 显存可以比较舒服地跑 7B/8B 模型的 Q4 量化，甚至 14B 模型短上下文。没有独显也可以用 CPU 或统一内存跑，但速度通常只有 1-5 tokens/s，适合非实时任务。

### 2. 选模型与量化

建议从指令模型开始，不要用基座模型。7B/8B 级别可优先试：

- Qwen2.5-7B-Instruct
- Llama-3.1-8B-Instruct
- Mistral-7B-Instruct

显存允许可上 Qwen2.5-14B-Instruct。量化格式优先 GGUF Q4_K_M，平衡显存与质量。Q8 显存几乎翻倍，收益有限；Q3 及以下工具调用能力下降明显。

### 3. 部署栈选择

- **Ollama**：最省事，自带 OpenAI 兼容接口，适合快速接入；
- **llama.cpp server**：控制更细，适合 GGUF 手动调参；
- **vLLM**：吞吐更高，但对显存和编译环境要求更重，家用单卡不一定要上。

如果只是给 OpenClaw 提供本地模型，Ollama 或 llama.cpp server 足够。

### 4. 启动与关键参数

Ollama 示例：

```bash
ollama run qwen2.5:7b-instruct-q4_K_M
```

拉模型前先确认量化标签，避免默认拉取非量化或过大版本。启动服务后设置环境变量：

```bash
export OLLAMA_NUM_PARALLEL=1
export OLLAMA_MAX_LOADED_MODELS=1
```

上下文长度按需设置，默认可以先用 4096，不要一上来就 8192 或 32768。上下文越大，KV cache 越占显存，生成速度也越慢。

llama.cpp server 示例：

```bash
llama-server -m qwen2.5-7b-instruct-q4_k_m.gguf \
  --ctx-size 4096 --n-gpu-layers 99 \
  --host 0.0.0.0 --port 8080
```

### 5. 接入 OpenClaw

本地服务通常提供 OpenAI 兼容接口，接入时只需要改 `base_url`、`api_key` 和 `model` 名称。Ollama 默认地址为：

```text
http://127.0.0.1:11434/v1
```

`api_key` 可以随便填，`model` 使用 Ollama 中的模型名。接入后先跑一次 `chat/completions` 验证，再放给 Agent 用。

### 6. 验证工具调用

本地小模型接入 Agent 后，先不要直接上复杂流程。用简单任务测试它能否稳定返回 `tool_calls`，例如：

> 从“帮我查一下北京天气”中提取城市名称。

确认模型能按预期返回工具调用，再逐步增加 MCP 工具数量。工具太多或 schema 太复杂，7B/8B 模型很容易跑偏。

## 踩坑点

- **上下文开太大**：8GB 显存跑 7B 模型，上下文开到 32k 大概率 OOM 或速度崩掉。Agent 长会话要配合摘要、截断或重置上下文，而不是无限把 `num_ctx` 调大。
- **小模型“假工具调用”**：它会用自然语言说“我来调用某工具”，但没有真正输出结构化 `tool_calls`。解决办法是选 Instruct 模型、降低 temperature、在提示词中明确工具调用格式，必要时用 JSON mode 或 grammar 约束。
- **并发超时**：本地模型一次推理可能 10-30 秒。OpenClaw 或 MCP 客户端默认超时时间往往不够，需要把请求超时和重试策略调大。并发任务最好排队，不要同时压多个请求。
- **模型版本漂移**：同一个模型名在不同时间可能指向不同量化或不同版本。建议固定完整模型标签，例如 `qwen2.5:7b-instruct-q4_K_M`，不要写 `latest`。
- **工具太多导致退化**：给本地模型一次挂十几个工具，选择准确率会明显下降。建议按场景拆成多个小工具集，减少单次选择负担。

## 可复用建议

1. 先跑通一个 7B/8B 的 Q4_K_M 模型，8GB 显存通常可以稳定运行 4k 上下文。
2. 统一走 OpenAI 兼容接口，这样本地和云端切换只改 `base_url` 与 `model`，不用改 OpenClaw 主流程。
3. 把本地模型定位成“离线调试节点”和“小任务执行器”，不要让它做长文档理解、复杂推理或大段代码生成。
4. 提示词里明确输出格式；temperature 设 0.1-0.2；必要时限制 `max_tokens`，避免模型自由发挥。
5. 监控 `tokens/s` 和显存占用。如果速度长期低于可接受阈值，说明模型、量化或上下文设置需要调整。
6. 记录每次失败的 prompt 和返回，本地模型的稳定性是调出来的，不是一次性配置出来的。

## 总结

在家用电脑上部署本地 LLM，不是把云端模型搬回家，而是建立一个可控的离线推理端点。关键是控制量化与上下文、保证工具调用结构稳定、接入 OpenAI 兼容层，再逐步纳入 OpenClaw 的 Agent 与 MCP 工作流。跑通这个链路后，很多自动化调试和轻量任务就能在不依赖外部 API 的情况下完成。
