# Git 自动化：让 AI 助手帮你管理代码提交和分支

在 OpenClaw、Agent 或 MCP 工作流里，AI 改完代码后通常会出现一段“人肉收尾”的断层：手动 `git status`、挑文件、写 commit message、切分支。任务一多，这个收尾动作比改代码还容易出错。于是很自然会想：能不能让 AI 助手自己管好提交和分支？

答案是可以，但不建议直接把 shell 丢给 AI。本文分享一套在 OpenClaw 环境中可落地的 Git 自动化做法，重点是“受控”而不是“全自动”。

## 背景与问题

让 AI 直接执行 `git add . && git commit` 看起来省事，实际有三个典型风险：

1. **误提交**：临时文件、`.env`、构建产物被一并提交。
2. **分支混乱**：并行任务都在 `main` 上工作，合并冲突频繁。
3. **提交信息不可用**：自动生成的 message 过于随意，回滚时看不懂。

所以工程化目标很明确：AI 可以执行 Git 操作，但必须通过受限接口，并且遵守与团队一致的分支和提交规范。

## 做法：把 Git 包装成受控工具

### 1. 用 Git MCP Server 代替裸 shell

在 OpenClaw 中接入一个 Git MCP Server，只暴露白名单操作。常见配置大致如下：

```json
{
  "mcpServers": {
    "git": {
      "command": "npx",
      "args": ["-y", "some-git-mcp-server"],
      "env": {
        "GIT_SAFE_DIR": "/path/to/your/repo"
      }
    }
  }
}
```

白名单建议只保留：`status`、`diff`、`branch`、`checkout -b`、`add`、`commit`、`log`。`push`、`reset --hard`、`push --force` 等写操作不要暴露给 Agent，或者只暴露给人工确认节点。

### 2. 在系统提示词中写入 Git 规则

OpenClaw 的系统提示词里明确告诉 Agent：

- 每次操作前先跑 `status --porcelain` 和 `diff`。
- 只 `add` 与当前任务相关的文件，禁止使用 `git add .`。
- 提交信息遵循 Conventional Commits：`type(scope): summary`。
- 新功能或修复必须从最新 `main` 创建分支，不直接提交到 `main`。
- 完成后返回 commit hash，不自动 push。

示例工作流：

```text
用户：修复登录接口超时问题
Agent：
1. git status --porcelain
2. 创建分支 fix/login-timeout
3. 修改相关代码
4. git diff 检查改动
5. 生成 commit message：fix(auth): set login request timeout to 10s
6. 提交并返回 commit hash
```

### 3. 加一道 pre-commit 检查

即使 AI 遵守规则，也建议在仓库里配置 pre-commit hook，做两件事：

- **敏感信息扫描**：用 `gitleaks` 或 `trufflehog` 拦截密钥、token。
- **最小化 lint**：只做快检，不做重构建，避免 Agent 提交被阻塞。

这样即使 AI 误加了文件，也有一层工程兜底。

## 踩坑点

实际用下来，有四个坑比较常见：

**1. `git add .` 误提交敏感文件**  
Agent 为了省事会一次性 add 所有文件。解决方式是白名单操作里强制 `add` 必须带路径参数，并在提示词里写“未跟踪文件必须逐个人工确认”。

**2. 提交信息格式漂移**  
自动生成的 message 有时候是英文，有时候是中文，有时候没有 type。可以在提示词里给 3 个 few-shot 示例，并要求最终 message 必须匹配正则 `^(feat|fix|docs|refactor|test|chore)(\(.+\))?: .+`。

**3. 并行任务都在 main 上**  
Agent 默认在当前分支工作，导致多个任务交叉污染。解决方式是每个任务开始前强制 `fetch` 并从最新 `main` 创建独立分支，分支名带任务 ID。

**4. 容器里 Git 身份缺失**  
很多自动化环境里没有配置 `user.name` 和 `user.email`，提交直接失败。在 Dockerfile 或启动脚本里显式配置一个 bot 身份，例如：

```bash
git config user.name "openclaw-bot"
git config user.email "bot@local"
```

## 可复用建议

如果你的团队也想做 Git 自动化，可以从这五条开始：

1. **唯一入口**：Git 操作通过 MCP Git Server 完成，禁止 Agent 执行 shell 命令。
2. **白名单优先**：只暴露 `status/diff/add/commit/branch/log`，写操作默认关闭。
3. **提交规范前置**：在提示词中固定 Conventional Commits 格式，并要求返回前自检 diff。
4. **分支策略统一**：每任务一分支，命名 `type/issue-id-slug`，从不直接提交 `main`。
5. **人工审阅节点**：自动提交后由人 push 或创建 PR，不自动推送到远端。

## 总结

Git 自动化能明显减少 Agent 工作流里的上下文切换，但前提是把 Git 当作“受限工具”，而不是“开放终端”。通过 MCP 白名单、提交规范、分支策略和 pre-commit 检查，可以让 AI 助手稳定地管理代码提交，同时保留足够的人工控制力。工程化的核心不是让 AI 替你做一切，而是让 AI 的可疑操作有边界。
