昨晚 GitHub 大规模宕机约 7 小时，很多团队的 push、PR、CI/CD 和 issue 联动全部卡住。开发者一边刷状态页，一边在社交平台发 “GitHub is down” 的表情包。宕机尚未完全恢复，Cursor 火速上线 Agent 版代码托管平台的消息又跟了上来。有人把它当成一次精准的“截胡”，也有人认为这更像一个信号：代码托管正在从“存代码的地方”转向“管 AI 工作流的地方”。本文从两个维度拆解：传统托管为什么一宕就是 7 小时；Agent 托管到底在解决什么问题。



## GitHub 为什么一宕就是 7 小时？
- GitHub 不是单一服务，而是由 Git 对象存储、API 网关、Web 前端、Actions、Pages、Notifications、Search 等数十个系统组成。任何一个核心依赖抖动，都可能通过重试放大成雪崩。
- 7 小时的恢复时间说明大概率不是简单的静态文件故障，而是涉及存储层、数据库或元数据服务。处理流程通常包括：摘流量、定位、回滚配置、数据校验、逐步放量。每一环在大规模系统中都很耗时。
- 从可用性角度看，全年累计 7 小时已经相当严重。很多企业 SLO 要求 99.99%，7 小时相当于把全年不可用时间预算一次用掉大半。
- 根因往往不是“Git 挂了”，而是平台层挂了。Git 本身是分布式协议，但 GitHub 把 PR、权限、Issue、CI 状态都放在中心化数据库里。分布式仓库并没有带来分布式协作的韧性。
- 例子：过去的 GitHub 事故中，DNS 配置错误、数据库主从切换失败、网络分区都曾触发过大面积不可用。这次的具体根因要等详细报告，但模式高度相似。



## Cursor 的 Agent 托管到底“托管”了什么？
- 传统代码托管托管的是：Git 仓库、分支、tag、PR、CI 配置、制品。Agent 版托管之所以值得关注，是因为它可能开始托管“Agent 运行环境”。
- 想象一个任务：Agent 读到 issue，自动改 5 个文件，跑测试，失败后回滚，再提交 PR。中间会产生大量状态：模型请求、工具调用、中间 diff、失败日志、最终 diff、评审结果。这些如果只靠 Git commit 记录，会丢失大量上下文。
- Agent 托管平台需要记录的不只是“代码变成了什么样”，还有“谁在什么时间、基于什么输入、调用了什么工具、为什么这样改”。这很像给 AI 行为做审计日志。
- 技术实现上，可能包括：任务队列、模型调用追踪、工具沙箱、快照与回滚、权限隔离。对开发者来说，工作流会从“我写好代码再提交”变成“我定义任务，审阅 Agent 的提交”。
- 一个值得注意的风险是密钥和权限。Agent 往往需要写权限才能完成任务，一旦模型被提示注入或产生幻觉，可能制造垃圾 PR，甚至误改关键文件。没有 gate 的 Agent 托管是不安全的。



## 从 Git 仓库到 Agent 工作流：底层逻辑在变
- Git 是为人类协作设计的：commit message 给人看，diff 给人读，branch 给人讨论。Agent 提交频率可能是人类的几十倍甚至上百倍，一天上千次 commit 并不夸张。
- 如果继续用传统 PR 流程审 Agent 的每一个 commit，人会先崩溃。更合理的抽象是 task、run、checkpoint，而不是 branch；评审的对象不是单个 commit，而是一个任务的结果。
- 存储层也会改变。传统 Git 对象库加关系数据库可能不够用，更需要事件日志、时间序列、向量索引来追踪 Agent 行为和检索代码上下文。
- 例如，Cursor 这类 AI 工具已经在本地构建代码索引，Agent 托管平台如果再叠加行为日志，就会变成“代码 + 行为”的双数据库。掌握这些元数据的平台，未来可能成为 AI 开发工具链的入口。
- 商业视角看，Git 仓库是商品化的基础设施，而 Agent 工作流元数据是新的高价值层。谁把“AI 怎么改代码”这件事结构化了，谁就掌握了下一代开发者的注意力。



## 别急着喊“替代 GitHub”：3 条冷思考
- 迁移成本不是代码搬家，而是生态锁定。Issues、Actions、PR 历史、第三方集成、团队权限、安全审计，这些比 Git 对象更难迁移。新平台可以快速复制 Git 存储，但很难复制生态。
- GitHub 本身也在加 AI：Copilot、Actions 的智能能力、代码扫描和安全告警。大厂不会坐视 Agent 托管崛起。更可能的格局是共存：GitHub 继续当协作底座，Agent 托管作为新的垂直层处理高频率 AI 提交。
- 对开发者来说，最该做的不是选边站，而是降低单点依赖。
- 实用建议：
  1. 不要把核心仓库、CI 和权限全部绑死在一个平台。至少保留 Git 镜像、备份和可导出的 CI 配置。
  2. 引入 Agent 写代码时，设置强制的 review gate、任务级权限和审计日志，防止幻觉提交混入主干。
  3. 评估任何新的托管平台时，看三个指标：故障恢复时间目标、数据可导出性、第三方 API 开放度。避免从 GitHub 的锁定跳到另一种锁定。

这次 GitHub 宕机是一次对集中式开发基础设施的压力测试，而 Cursor 的动作则提示我们：Agent 时代，代码托管可能不再是“仓库托管”，而是“工作流托管”。结论不必急着下，但基础设施的韧性，应该被放到更高优先级。
