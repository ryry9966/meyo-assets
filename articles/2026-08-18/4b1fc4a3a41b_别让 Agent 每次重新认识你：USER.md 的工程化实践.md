## 背景

AI Agent 现在不缺工具，缺的是关于“你”的上下文。MCP 能接文件系统、GitHub、数据库，插件能跑脚本、调接口，但模型本身并不知道你常用的 Python 是 3.12 还是 3.8，不知道你习惯先看 diff 再提交，也不清楚哪些目录绝对不能碰。

于是每次新会话，你都得重新解释一遍环境、偏好、红线。更糟的是，当 Agent 在无人确认的情况下直接执行高风险操作时，问题往往不是因为模型笨，而是因为你的约束没有被持久化。

USER.md 就是解决这个问题的：一份给 Agent 看的用户档案。

## 问题

典型场景是：你让 Agent 修改一个自动化脚本，它默认用 `python3` 命令，结果系统里 `python3` 指向 3.9，而项目依赖需要 3.12。或者你让它整理文件，它“顺手”清理了 `/tmp` 下你正在调试的临时数据。

这些问题的共同点是：Agent 在缺少用户上下文的情况下做了“合理但错误”的推断。而 USER.md 的作用，就是把这些推断依据提前写清楚。

## 做法 / 步骤

### 1. 确定 USER.md 的层级

不要把所有信息都塞进一个文件。建议分三层：

- **用户级**：放在 Agent 的用户配置目录，例如 `~/.config/agent/USER.md`，描述跨项目的个人环境与偏好。
- **项目级**：放在仓库根目录，例如 `AGENT.md` 或 `docs/USER.md`，描述当前项目的技术栈、目录结构、常用命令。
- **会话级**：临时说明，直接贴在当前任务开头，例如“本次只改 test/ 下的文件，不要动 src/”。

多数 OpenClaw/Agent 框架支持在系统指令中 include 用户级文件，项目级文件则可以随仓库一起版本控制。

### 2. USER.md 应该写什么

一个可用的 USER.md 不需要很长，但要覆盖五类信息：

```markdown
# USER.md

## 我是谁
- 主要语言：Python 3.12 / TypeScript
- 操作系统：macOS 14，部分脚本部署在 Ubuntu 22.04

## 环境
- 所有项目放在 ~/workspace 下
- 虚拟环境统一用 .venv，不要用 conda

## 偏好
- 涉及文件删除/移动时，先列出清单，等待确认
- 默认不要自动执行 git push --force

## 红线
- 不要修改 ~/.ssh 下的任何文件
- 不要读取 .env 中的密钥并打印到终端

## 工具链
- 常用 MCP：filesystem、github、sqlite
- 日志统一用 structured logging，不要 print 调试信息
```

重点是：每一条都应该是**可验证、可执行**的，而不是抽象描述。例如“要小心操作”没有用，写成“删除文件前必须先列出清单等待确认”才有用。

### 3. 注入方式

在 OpenClaw 这类框架里，通常有两种方式：

- 把 USER.md 路径加入系统 prompt 的 include 列表，每次会话自动加载。
- 通过 MCP 的 memory/filesystem 工具，让 Agent 在需要时主动读取。

建议用第一种方式，因为 Agent 不会每次主动去找 USER.md，只有强制注入才稳定。

## 踩坑点

1. **写成流水账**：USER.md 超过 200 行后，模型容易忽略关键约束。保持短，单文件尽量控制在 60 行以内，其余放到项目级文件。
2. **写太多“不要做 X”**：消极指令过多会导致模型注意力分散。优先写正面行为，例如“执行写操作前先输出 plan”，而不是“不要乱改文件”。
3. **记录敏感信息**：不要把密码、API key 写进 USER.md。即使文件在本地，也可能被 Agent 误读或写进日志。敏感信息用环境变量。
4. **更新滞后**：你换了 Python 版本，但 USER.md 还写着 3.11，Agent 就会按旧环境执行。每次环境变更后，顺手更新。
5. **与项目配置冲突**：用户级写“默认不自动 push”，项目级写“自动化发布需要自动 push”，这种冲突会让 Agent 行为不稳定。建议项目级优先级高于用户级，并在项目文件里明确覆盖规则。

## 可复用建议

- **分层 + 优先级**：用户级写好跨项目约束，项目级覆盖具体行为，会话级做临时补充。
- **用“当...时，必须先...否则...”句式**：这种条件约束比简单禁令更容易被模型遵守。例如“当删除的文件数超过 3 个时，必须先列出完整路径并等待用户确认”。
- **每次会话开场做一次约束确认**：让 Agent 用一句话复述本次任务的三条关键约束，快速验证 USER.md 是否生效。
- **纳入版本控制**：项目级 USER.md 应随代码提交，非敏感信息可以团队共享，减少新人配置成本。
- **定期做“垃圾清理”**：每月删掉已经过时的条目，避免文件膨胀。

## 总结

USER.md 不是灵丹妙药，它只是把反复沟通的成本，转化为一次性的结构维护。对于 OpenClaw/Agent 这类强工具调用场景，它能显著减少“环境猜错”“命令越界”这类问题。关键不是写得多，而是写得准、更新勤、可验证。把你的用户档案当作一份工程文档来维护，Agent 才会真正“了解”你，而不是每次从零开始猜。
