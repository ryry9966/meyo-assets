## 背景

OpenClaw 里的 Agent 默认行为通常由系统提示、工具描述和模型偏好共同决定。实际跑自动化任务时，问题会很快暴露：同样一个“看一下服务状态”，有时回复得像闲聊客服，有时直接建议执行重启；遇到 MCP 提供的高权限工具，模型可能因为“用户想解决得快一点”而执行删除或覆盖操作。

SOUL.md 的作用不是让 Agent 变得更像人，而是把它的人设、语气、工具策略和红线写成一个可维护、可回滚的工程文件。它跟 skill 描述、MCP 配置不同：skill 负责“能做什么”，SOUL.md 负责“你是谁、什么不能做、默认怎么做”。

## 问题

没有明确边界时，常见三类问题：

1. **行为漂移**：同一个 Agent，这次简洁，下次长篇道歉，再下次把内部诊断结果直接丢给用户。
2. **工具滥用**：MCP 注册了 `filesystem.write`、`shell.exec` 等工具，模型为了“一次到位”，直接改配置文件或执行危险命令。
3. **人格不可调试**：把人格写死在系统提示里，改一次要动主配置，团队其他人不敢碰，后续越改越乱。

## 做法/步骤

### 1. 建立最小 SOUL.md

放在项目根目录或 OpenClaw 配置指定位置。第一版不要追求完整，只写四段：身份、语气、允许、拒绝、默认行为。

```markdown
---
name: ops-bot
mode: production
---

# 身份
你是 OpenClaw 运维助手，只负责只读诊断和低风险维护。

# 语气
简洁、直接，不道歉，不发表情，不输出猜测性内容。

# 允许
- 调用 `mcp-server-filesystem.read` 读取 `/var/log/myapp/**`
- 调用 `mcp-server-git.status` 查看仓库状态
- 调用 `mcp-server-http.get` 访问内网健康检查接口

# 拒绝
- 不执行 `rm`、`truncate`、`DROP`、`DELETE`、`ALTER`
- 不读取 `/home/**/.ssh/**`、`/etc/**`、`**/.env`
- 不调用任何未在“允许”列出的 MCP 工具

# 默认行为
当请求超出允许列表时，回复：
“该操作超出我的边界。需要提升权限请先更新 SOUL.md 并重新加载。”
```

### 2. 跟系统提示分层

OpenClaw 的 system prompt 只放“如何加载工具和 SOUL.md”的元规则，不要重复人格内容。SOUL.md 独立成文件，便于 diff、审计和按环境切换。例如：

- `SOUL.prod.md`：生产环境，只读优先。
- `SOUL.dev.md`：开发环境，允许执行测试命令。
- `SOUL.customer.md`：面向客户的助手，语气更友好但工具白名单更窄。

### 3. 测试边界

改完 SOUL.md 后，用固定 prompt 集跑回归。至少包含：

- 正常请求：应执行允许的工具。
- 越权请求：应返回边界话术，不调用工具。
- 模糊请求：应要求澄清或选择最保守路径。
- 语气检查：在错误场景下是否出现多余道歉、表情或长篇解释。

可以用 OpenClaw 的会话脚本批量跑，观察工具调用日志是否与 SOUL.md 一致。

## 踩坑点

### 1. 边界写得太抽象

“不要做危险操作”没有约束力。要具体到命令、路径、工具名、网络域名。例如“禁止执行任何写操作”不如“禁止调用 `filesystem.write` 和 `shell.exec`，除非用户显式提供 `--allow-write` 参数”。

### 2. SOUL.md 过长

人格描述超过 500 词后会挤占上下文，模型反而不遵守。把技能细节、API 用法、示例放 skill 文件或 MCP 描述里。SOUL.md 只保留“稳定不变的红线和默认策略”。

### 3. 与 MCP 工具描述冲突

这是最容易翻车的地方。某个 MCP 工具的描述里写了“该工具用于修改配置”，模型可能更相信工具 schema，而不是 SOUL.md 里“禁止修改”。解决方案是：在允许清单里显式排除冲突工具，并在工具名上做精确匹配；必要时在 OpenClaw 的工具配置层做权限裁剪，不要只依赖自然语言约束。

### 4. 子 Agent 不继承 SOUL.md

如果 OpenClaw 会派生子任务或调用子 Agent，SOUL.md 不一定自动注入。需要在子 Agent 的初始化 prompt 或任务描述里显式带上“遵循主 SOUL.md 第 X 节”。否则子任务可能绕过边界，比如在主 Agent 拒绝删除后，子 Agent 却执行了。

## 可复用建议

- **四段式写边界**：允许、拒绝、默认、上报。不要只写“禁止”，还要写“遇到边界时怎么回复”。
- **把 SOUL.md 当代码管理**：进 Git，改前跑测试，提交信息写清楚“为什么改这条边界”。
- **保持简洁**：目标控制在 300–500 词。超过就要拆出去。
- **建立回归 prompt 集**：边界不是写完就完事，每次改 SOUL.md 或升级 OpenClaw/MCP 版本后都要跑。
- **记录决策依据**：在 SOUL.md 底部可以加一行 `<!-- 2024-11-20: 禁止读取 .env，因为客户环境泄露密钥 -->`，方便团队理解历史红线。

## 总结

SOUL.md 不是给 Agent 写人设文案，而是把“人格”和“边界”变成可测试、可版本化的工程约束。好的 SOUL.md 让 Agent 在能力范围内稳定发挥，让团队敢于把生产操作交给它一部分，同时守住红线。对 OpenClaw 用户来说，它比多写几个 MCP 插件更值得先做好。
