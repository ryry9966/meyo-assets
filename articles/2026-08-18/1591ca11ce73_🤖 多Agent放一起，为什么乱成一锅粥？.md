Anthropic 近期公开的工程观察，把多 Agent 协作的隐患摆上了台面：单个 Agent 跑任务时表现稳定，一旦把几个 Agent 放进同一工作区协同，反而开始抢工具、传错话、重复劳动，严重时一个格式错误就能拖垮整条链路。36氪的报道标题很形象——“放一起乱成一锅粥”。这锅不是模型突然变笨，而是多智能体协作自带几类结构性风险。拆开看，问题比想象中更工程化。



## 一、多 Agent 不是“人越多越好”

很多人直觉上认为，一个 Agent 能做好一件事，多个 Agent 协作应该更强。但多 Agent 系统本质上是分布式决策，不是简单堆人力。

- 单个 Agent 拥有完整上下文，目标单一，输出可以直接执行。
- 多个 Agent 把任务拆成若干局部上下文，每个 Agent 只理解自己那一小块，系统正确性开始依赖“接口契约”。
- 通信通道随 Agent 数量平方级增长：n 个 Agent 两两通信，潜在通道是 n(n-1)/2。10 个 Agent 就有 45 条潜在通道，任何一条出问题都可能污染全局。
- 可靠性沿链路快速衰减。假设每个 Agent 单步正确率是 0.99，链式依赖 10 步后整体理论正确率约 0.90；如果单步正确率降到 0.95，10 步后只剩约 0.60。
- 因此，多 Agent 不是性能补丁，而是复杂度预算。很多任务用单 Agent 加确定性工具反而更稳。

多 Agent 的优势只在任务可分解、子目标清晰、结果可独立验证时才会成立。否则，协调成本会迅速吃掉收益。

## 二、乱成一锅粥的四个机制



多 Agent 协作的混沌，通常不是某一个大 bug，而是四类机制叠加。

1. **目标漂移与局部最优**

每个 Agent 都被独立 prompt 优化，指标并不一致。检索 Agent 追求召回率，可能塞入大量噪声；总结 Agent 为了控制 token，把关键约束删掉；执行 Agent 拿到模糊任务后自行脑补。局部最优组合起来，整体目标反而没人负责。

2. **通信失真与“传话游戏”**

Agent 之间靠文本或 JSON 传信息，每经过一层都会被改写、省略、压缩。原始需求“毛利率要按 Q3 非 GAAP 口径，剔除一次性收益”传到最后，可能只剩“做一张 Q3 利润率表”。这就像传话游戏，信息熵逐级丢失，下游还会把上游的猜测当成事实。

3. **资源争用与死锁**

多个 Agent 共享浏览器实例、代码执行器、数据库、文件系统。没有事务、锁和版本控制时，会出现覆盖写、读中间态、循环等待。两个 Agent 同时修改同一份文件，最终文件可能变成“缝合怪”；一个 Agent 等另一个确认，另一个等它先输出，系统直接卡死。

4. **级联失败与雪崩**

一个 Agent 返回格式错误，下游解析崩溃；重试又制造新请求，占满队列。错误像微服务雪崩一样扩散。多 Agent 链路里，上游的小错误不再是小错误，而是会放大的触发点。链路越长，恢复越困难。

## 三、单 Agent 没问题，协作为什么就崩？

单 Agent 的强，来自封闭上下文与单一目标。一旦进入多 Agent 环境，很多分布式系统老问题会重新出现，而且还叠加了模型不确定性。

- 传统软件接口稳定：字段、类型、错误码明确。大模型输出有随机性，契约天然脆弱。
- 多智能体强化学习中存在非平稳性：每个 Agent 都在更新策略，其他 Agent 的策略也在变化，环境对所有 Agent 都不稳定，收敛难度大幅上升。
- 社会困境也会出现：个体理性导致集体非理性。比如每个 Agent 都想尽快抢到工具，结果互相阻塞；或者为了完成自己的子目标，隐藏信息、修饰结果，反而破坏全局。
- 分布式系统里的协调、一致性、故障隔离问题，在多 Agent 中一个不少。拜占庭将军问题关于不可靠节点协作的困难，在模型输出不确定的语境下被进一步放大。

所以，多 Agent 协作不是“让 AI 们开个会”那么简单，它更像维护一个微型分布式系统。

## 四、工程防“一锅粥”的几条硬措施



如果一定要上多 Agent，需要按工程系统来治理，而不是按对话机器人来调用。

1. **先做必要性审查**：能用单 Agent + 工具解决，就不要拆多 Agent。拆分的前提是子任务边界清晰、目标可独立验证。
2. **固定接口，不要自由发挥**：把多 Agent 当“工作流”，不当“自由讨论组”。输入输出 schema、版本号、超时、重试上限、幂等键都要明确。
3. **引入编排者或汇总者**：至少有一个全局视角的 Agent 或脚本，负责目标对齐、冲突仲裁、结果汇总，完全去中心化通常很难稳定。
4. **关键接口用结构化数据**：别让自然语言成为系统契约。下游解析失败要有兜底和降级，而不是直接崩溃。
5. **可观测性拉满**：记录每个 Agent 的输入输出、延迟、重试、冲突，链路要能回溯到具体节点。
6. **关键路径留确定性兜底**：财务计算、权限控制、线上写操作，留给确定性代码或单体模型。多 Agent 只做增强、探索、非关键路径。

Anthropic 的观察也指向同一个结论：多 Agent 适合边界清晰、可独立评估的任务，否则协调成本会吃掉增量收益。

## 五、三条冷思考

1. **复杂度预算要单列**。多 Agent 会带来通信、调试、评估、运维成本。不要把“上多 Agent”当成技术升级，先算清它省下的时间是否大于新增的协调成本。
2. **自然语言不适合当协议**。Agent 之间如果依赖自由文本传关键约束，必然走向传话游戏。稳定 schema、校验、版本控制，比单纯优化 prompt 更重要。
3. **上线前用失败清单做红队**。至少测五类：死锁、重复劳动、关键信息漏传、下游误读、雪崩恢复。能稳定通过再谈扩展。

多 Agent 的“乱”，不是 AI 能力不够，而是我们低估了协作本身的成本。把系统边界、通信协议和失败模式管住，才能避免一锅粥。
