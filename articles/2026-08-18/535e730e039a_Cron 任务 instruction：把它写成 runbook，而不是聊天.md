## 背景

在 OpenClaw 里配置 cron 任务时，很多人会写成这样：

> 每天早上 9 点帮我总结重要新闻并推送。

结果往往是：格式漂移、重复执行、空数据时开始编造、工具调用名写错，或者任务失败后完全静默。原因不是模型不行，而是 **cron 任务没有交互澄清的机会**。instruction 必须同时承担目标定义、边界约束、输出协议和异常处理。

定时任务的 instruction 不是聊天，是给 agent 的一次性执行手册。

## 问题

常见的 cron instruction 问题集中在四类：

1. **目标模糊**：例如“重要新闻”“有价值的更新”，没有可操作标准。
2. **输出不可解析**：通知管道、群机器人、存储插件通常需要稳定结构，但模型会自由发挥 Markdown、寒暄或额外解释。
3. **冷启动无状态**：每次运行不会记得上次结果，如果没有显式约束，容易重复处理或漏处理。
4. **失败静默**：cron 不会追问，出错时如果不约定输出错误状态，使用者根本不知道任务失败。

## 做法：把 instruction 写成 runbook

下面是一个可复用的结构化模板，适用于 OpenClaw cron / MCP 工具 / 插件任务。

```text
[任务身份]
你是 daily-hn-briefing，运行在 OpenClaw cron。
只处理当前触发周期，不要等待下一次触发。

[目标]
从 Hacker News 获取过去 24 小时内 score >= 100 的前 10 条，
生成中文摘要并保存。

[可用工具]
hacker_news_top_stories, save_note

[执行步骤]
1. 调用 hacker_news_top_stories(limit=30)
2. 过滤 score < 100 或发布时间超过 24h 的条目
3. 若过滤后为空，直接输出 NO_NEW_DATA，不要调用 save_note
4. 对剩余条目生成纯文本：排名、标题、链接、3 句以内摘要
5. 调用 save_note(title="HN Daily", content=...)

[输出格式]
成功：{"status":"ok","saved":10,"top_titles":["..."]}
无数据：{"status":"no_data","saved":0}
失败：{"status":"error","step":"...","reason":"..."}

[约束]
- 不要输出额外解释、问候或 Markdown 表格
- 工具报错时重试 1 次，仍失败则输出 error JSON
- 不要修改标题和链接
- 不要自行扩大筛选范围
```

这个模板的核心不是字数多，而是每一段都有明确作用：

- **任务身份**：防止 agent 把自己当成交互助手。
- **目标**：把“重要”变成可执行阈值。
- **可用工具**：锁定工具名，避免模型幻觉调用。
- **执行步骤**：给出确定性流程，而不是开放决策。
- **输出格式**：固定 schema，下游才能解析。
- **约束**：告诉 agent 什么时候停下、什么不能做。

## 踩坑点

### 1. 时间语义冲突

cron 表达式已经负责调度，但 instruction 里再写“每天早上 9 点”，模型可能误以为要等待到 9 点才执行，或者在时区判断上出错。  
**写法**：统一写成“当前触发周期”。

### 2. 没有定义空数据处理

如果过滤后没有数据，模型很容易为了“完成任务”而编造条目。  
**写法**：约定哨兵值，例如 `NO_NEW_DATA`，并明确禁止后续工具调用。

### 3. JSON 字段漂移

只写“返回 JSON”不够，字段名每次都可能变，导致推送端解析失败。  
**写法**：给出一行完整 example，字段名固定，模型会倾向于复刻。

### 4. 步骤过多导致上下文截断

一次拉取 100 条、要求逐条分析、再生成长摘要，容易在中途耗尽上下文。  
**写法**：限制数量上限、摘要长度、工具调用次数，例如“最多 5 步”“摘要不超过 3 句”。

### 5. 失败不报错

工具调用失败后，模型可能自行跳过，最终只输出一个看似正常的总结。  
**写法**：约定失败 JSON，并要求在指定步骤失败时不得继续后续动作。

## 可复用建议

1. **固定 schema**：所有 cron 任务统一输出 `status` 字段，便于日志和告警。
2. **提供 dry-run 模式**：在 instruction 中定义 `{"dry_run": true}` 时只返回执行计划，不调用写工具。测试时可以手动触发。
3. **版本化 prompt**：把 `v1.0.0` 写进任务身份，改动时方便回滚和对比。
4. **限制自由度**：越自动化的场景，越要减少模型决策空间。能用阈值、白名单、固定字段表达的，就不要用自然语言描述。
5. **失败哨兵**：空数据、超时、工具不可用、重试耗尽，分别给出不同状态输出。
6. **记录每次运行结果**：让 agent 输出一个稳定 JSON，再由外部系统记录，而不是依赖模型自己“记住”上次状态。

## 总结

OpenClaw 的 cron 任务本质上是一个冷启动、无交互、结果进入管道的执行环境。好的 instruction 应该像一份 runbook：目标可验证，步骤确定，输出可解析，异常可上报。把 agent 当一次性执行器，而不是聊天对象，才能真正降低定时任务的失败率。
