## 背景

在 OpenClaw 里，单个 Agent 处理复杂任务时，经常要同时做信息收集、代码检查、文档生成。串行执行不仅慢，还容易让上下文膨胀：前面的中间结果污染后续推理，某个步骤失败会中断整条链路。

Subagent 的价值是把大任务拆成多个上下文独立的小任务，并行执行，主 Agent 只负责调度、校验和汇总。这样既隔离了上下文，也能把延迟从“任务时间之和”降到“最长子任务时间”。

但 subagent 编排不是简单多开几个线程。真正落地时，问题往往出在任务拆分、共享状态、工具冲突和结果汇总上。

## 问题

并行编排主要面临五个坑：

1. **任务拆得太细**：调度开销超过实际收益，主 Agent 反而被淹没。
2. **上下文隔离反噬**：Subagent 看不到主 Agent 的对话历史，重要背景没显式传入，导致“我以为它知道”。
3. **工具/文件冲突**：多个 subagent 同时写文件或调用有状态 MCP 服务，产生竞态。
4. **输出格式混乱**：每个 subagent 返回自然语言，主 Agent 汇总时还要再解析一遍。
5. **失败无法隔离**：一个子任务失败拖垮整体，或者被静默丢弃。

## 做法/步骤

以一个典型场景为例：代码合并前，需要并行做代码审查、文档更新、测试用例生成。它们之间没有强依赖，适合 subagent 并行。

### 1. 拆任务时只看“是否有共享中间状态”

可以并行的是：独立数据源调研、多文件静态检查、测试生成与文档生成。  
不要并行的是：有严格先后依赖、需要频繁交换中间结果的任务。

拆完后，给每个 subagent 定义清晰的边界，避免重复计算。

### 2. 为每个 subagent 配置独立上下文和最小权限

在 OpenClaw 的 subagent 配置中，不要把全部工具都塞给每个 subagent。只给必要工具，控制影响面。

```yaml
subagents:
  code-review:
    prompt: "只审查 src/ 下本次改动，输出 JSON 格式问题清单"
    tools: [read, grep, git_diff]
    timeout: 120s
  doc-gen:
    prompt: "根据 docs/ 下现有风格，生成新增 API 的文档"
    tools: [read, write_docs]
    timeout: 90s
  test-gen:
    prompt: "为新增模块生成最小可用测试，不修改既有测试"
    tools: [read, write_tests]
    timeout: 120s
```

注意：写操作尽量只限一个 subagent，或者按路径分区。不要让多个 subagent 同时写同一目录。

### 3. 主 Agent 只做派发和汇总，限制并发

主 Agent 不要参与具体执行。派发时设置合理并发，例如 `max_workers: 3`。并发数不是越大越好，受 MCP server 连接数、API 速率限制和本机资源约束。

主 Agent 只接收每个 subagent 的结构化摘要，不要把完整中间过程灌回上下文，否则又回到上下文膨胀的老路。

### 4. 统一输出契约

给每个 subagent 指定输出 schema，例如：

```json
{
  "status": "ok",
  "findings": [],
  "artifacts": []
}
```

这样主 Agent 汇总时不需要再做自然语言解析，直接按字段合并。失败时也返回同一结构：

```json
{
  "status": "failed",
  "findings": [],
  "artifacts": [],
  "error": "MCP connection timeout"
}
```

### 5. 失败隔离与重试

单个 subagent 失败不应中断整体。主 Agent 收到 `status: failed` 后，可以对该子任务重试一次。若仍失败，把错误记录到最终报告，而不是静默丢弃。这样既能保留部分成功结果，也能暴露问题。

## 踩坑点

- **上下文隔离不是万能**：重要背景必须显式写进每个 subagent 的 prompt。比如项目结构、命名规范、约束条件，不要假设 subagent 会继承主 Agent 的上下文。
- **工具冲突比想象中常见**：有状态 MCP 服务在并行时会暴露连接数问题。部分本地 MCP server 不支持多客户端并发，需要串行或加锁。遇到偶发超时，先降并发排查，不要直接重试。
- **成本会成倍放大**：并行 subagent 消耗的 token 是线性叠加的。只对“单上下文过大”或“延迟敏感”的任务使用并行，小任务串行即可。
- **结果漂亮不代表正确**：Subagent 可能返回格式完美的 JSON，但内容是错的。主 Agent 要抽查关键结论，而不是直接拼接了事。

## 可复用建议

- **模板化**：把常用 subagent prompt 和输出 schema 放到 `.openclaw/subagents/` 下，作为仓库模板复用。
- **小步试验**：先并行 2 个，跑通结果汇聚，再逐步增加并发。
- **记录开销**：给每个 subagent 加 `timeout` 和 token 统计，方便后续优化。
- **职责单一**：主 Agent 只做调度、校验、汇总。一旦主 Agent 开始参与具体执行，上下文边界就容易模糊。

## 总结

Subagent 并行编排适合“可拆分、轻依赖、重隔离”的任务。在 OpenClaw 里，它不应该被当成万能加速开关，而是上下文管理和失败隔离的工具。控制并发、统一输出契约、显式传递背景，才能真正比单 Agent 串行更稳。

工程上，先把一个并行链路跑通、记录开销、再逐步扩展，比一开始就上复杂编排更可靠。
