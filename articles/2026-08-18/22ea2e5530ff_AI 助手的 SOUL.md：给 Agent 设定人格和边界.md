# AI 助手的 SOUL.md：给 Agent 设定人格和边界

## 背景

在用 OpenClaw 接 Agent、MCP 和自动化插件时，有一个问题会反复出现：Agent 能力很强，但行为不稳定。今天让它查日志，它顺手帮你“优化”了一个配置文件；换个会话，它从简洁风变成话痨；再换个模型，连禁止操作都开始打擦边球。

这些问题通常不是因为模型不行，而是因为人格和边界没有作为工程资产被固定下来。每次靠临时 prompt 口头约束，效果必然漂移。

SOUL.md 的思路很简单：给 Agent 一份持久化的“人格与边界文件”，像代码一样被版本管理、被测试、被复用。

## 问题

常见的三个具体痛点：

1. **行为漂移**：同一个任务在不同会话里，Agent 的语气、主动性、风险偏好不一样。
2. **边界靠自觉**：只在 prompt 里写“不要删库”，但工具权限本身是全开的，模型一旦被长上下文带偏就可能越界。
3. **规则分散**：一部分规则在系统提示里，一部分在 MCP 描述里，一部分在插件 README 里，出问题后很难定位是哪条约束失效。

SOUL.md 不是万能药，但它能把“人设”和“红线”收敛到一个可审查、可版本化的文件里。

## 做法

### 1. 建立一个最小 SOUL.md

放在项目根目录，或 `~/.openclaw/` 下，由启动器读取后注入系统提示。内容分五块：

```markdown
# SOUL.md

## 身份
你是运维助手。语气简洁、直接，不编造命令输出。

## 工作范围
只处理用户明确提出的任务。修改文件前先说明影响范围。

## 工具边界
允许：读日志、查状态、执行 dry-run。
禁止：删除、重启生产服务、修改权限，除非用户本轮明确确认。

## 失败处理
连续两次失败后停止，报告已尝试步骤和证据，不自行换方案硬来。

## 输出约定
涉及命令时给出可复现命令；不确定时标注“未验证”。
```

这个模板的关键不是写得多，而是每一条都可判断、可验证。

### 2. 注入与版本化

将 SOUL.md 作为项目资产纳入 Git。OpenClaw 启动时读取内容，拼到 system prompt 的稳定位置。不要在每次会话里让用户手动粘贴。

如果同时存在全局 SOUL.md 和项目 SOUL.md，明确优先级。建议项目级覆盖全局级，避免规则互相打架。

### 3. 与 MCP/插件权限对齐

SOUL.md 里的“禁止”必须对应工具层的 allowlist。比如 SOUL.md 写“禁止重启生产服务”，那么 MCP server 的配置里就不要暴露 restart 能力，或者用 allowlist 只放行 read/status/dry-run。

软约束和硬约束要分开。SOUL.md 主要是软约束，负责意图对齐；MCP 权限是硬约束，负责兜底。只靠前者，早晚被绕过。

## 踩坑点

1. **写太长**：超过 80 行的 SOUL.md，Agent 只会抓住最前面几条。规则越多，权重越低。尽量控制在 40–60 行。

2. **规则不可验证**：写“保持专业”不如写“不使用表情符号，不输出主观形容词”。模糊规则等于没有规则。

3. **边界写太死**：禁止所有写操作后，Agent 连生成修复脚本都拒绝。边界要留出“用户明确确认后允许”的通道，而不是一刀切。

4. **把敏感信息写进去**：SOUL.md 可能被随项目分享或打印到日志里。不要把 token、内网地址、密码放进去。敏感信息走环境变量或密钥管理。

5. **只改文件不测**：改完 SOUL.md 后，要用固定用例回归。比如“让它尝试删除一个测试文件，观察是否拒绝”“让它连续失败两次，观察是否停止”。

## 可复用建议

- **用负面清单优先**：先写“禁止做什么”，再写“应该怎么做”。模型对禁令更敏感。
- **短句 + 分块**：每条规则不超过一行，块之间空行，避免大段叙述。
- **纳入 CI 检查**：可以用脚本检查 SOUL.md 是否包含明文密钥、是否超过行数限制。
- **做回归用例集**：准备 5–8 个典型场景，每次改完 SOUL.md 跑一遍，记录行为变化。
- **双层防护**：SOUL.md 管“意图”，MCP allowlist 管“能力”。不要用前者替代后者。

## 总结

SOUL.md 不是玄学，也不是“给 AI 写灵魂”的营销话术。它是一份工程文件，用来降低 Agent 的行为方差，减少越界操作，让自动化任务更可预测。

真正有效的人格设定，不是写得漂亮，而是能被版本管理、被测试、被工具权限兜底。把 SOUL.md 当作代码来维护，它才会在长时间运行里持续起作用。
