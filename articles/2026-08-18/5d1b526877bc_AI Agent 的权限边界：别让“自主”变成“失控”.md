## 背景

接上 MCP、插件和本地脚本之后，Agent 的能力边界被迅速打开：能读文件、能发请求、能改配置、能触发部署。但大多数事故不是“模型太笨”，而是“它被允许做的事太多”。

一次误删目录、一次错误群发、一次把测试配置推到生产，都可能让一个提效工具变成事故源。真正需要解决的问题不是“要不要给 Agent 权限”，而是：**什么时候该自己干，什么时候必须停下来问人类。**

## 问题

实践中常见两个极端：

- **全自动**：工具权限一把梭，模型拿到写权限后一路执行，出问题只能事后补救；
- **全人工**：每次工具调用都要确认，Agent 退化成聊天机器人，审批疲劳让用户闭眼点“允许”。

权限边界的关键不是“问”或“不问”，而是**在什么条件下问**。工程上需要一套可演进的策略，而不是靠 prompt 里写“不要做危险操作”。

## 做法：给工具分级，把边界落到执行层

### 1. 先做工具风险分级

把 OpenClaw 中接入的 MCP 工具、插件动作、本地命令按两个维度打分：**影响面**和**可逆性**。

| 等级 | 典型动作 | 默认策略 |
|------|----------|----------|
| L0 只读 | `read_file`、`search`、`list`、`diff` | 自动执行 |
| L1 可逆写 | 创建草稿、写临时文件、更新 issue | 白名单内自动，否则询问 |
| L2 不可逆/外发 | `delete`、`merge`、`send_email`、webhook、付款 | 必须询问 |
| L3 环境级 | `sudo`、变更 IaC、生产部署 | 默认拒绝，需二次确认 |

这个分级不要只写在文档里，要落到配置中。例如：

```yaml
tools:
  - name: file_read
    risk: L0
    auto: true
  - name: git_push
    risk: L2
    auto: false
    approval_prompt: "是否推送到 {remote}/{branch}？"
  - name: deploy_prod
    risk: L3
    auto: false
    require_second_confirm: true
```

### 2. 用策略函数代替模型判断

在 Agent 执行工具前加一个策略层：

```python
def should_ask(tool, context, params):
    if tool.risk >= 2:
        return True
    if tool.risk == 1 and params.target not in ALLOWED_WRITE_PATHS:
        return True
    if is_batch(params) and not in_working_hours():
        return True
    if detect_rate_anomaly(tool.name):
        return True
    return False
```

关键点：**模型不能绕过这个策略层**。即使模型被注入“忘记规则”，执行前的硬校验仍然会拦截。

### 3. 审批界面要有上下文

不要只弹一个“允许 / 拒绝”。用户需要看到：

- 要执行的具体命令或工具调用全文
- 参数和影响范围，如目标路径、分支、收件人
- 是否可回滚，如果不能回滚，要明确标红
- 触发原因：Agent 为什么要做这个操作

例如：“即将执行 `git push origin main`，会修改远程 main 分支。可回滚方式：`git revert` 或 reset。是否继续？”

### 4. 读操作自动，写操作先 dry-run

对于写操作，优先支持 dry-run 或沙箱。文件写入先在临时目录完成，生成 diff 后再由用户确认落盘。这样可以把很多 L1 操作从“询问”降级为“展示 diff 后自动执行”，减少打断。

## 踩坑点

- **把整个 MCP server 当成权限单元**：一个 server 可能同时暴露 read 和 write 工具，直接授权等于扩大攻击面。要按工具粒度控制。
- **依赖模型自觉**：prompt 注入可以让模型“忘记”安全规则。硬限制必须在执行层，不在对话层。
- **审批疲劳**：所有写操作都问，用户会逐步变成“无脑允许”。分级的目的就是只对真正不可逆的操作打断。
- **忽略频率和组合**：单个 L1 工具安全，但短时间调用 100 次可能危险。策略里要加入速率和累计影响检查。
- **测试与生产策略不一致**：测试环境可以自动跑通，生产环境需要重新评估。很多人把测试策略直接复制到生产，埋下隐患。

## 可复用建议

1. **新接入的 MCP/插件默认只读**，跑通一段时间后再逐步放开写权限。
2. **维护自动执行白名单**：只读工具 + 明确的低风险写操作，其它默认进入审批。
3. **权限策略代码化**，放在版本库里 review，不要散落在 Agent 配置或系统提示词里。
4. **记录每次误拦截和误放行**，每周复盘调整工具分级。权限边界不是一次配好就完事。
5. **高危操作预留冷静期**：删除类操作可以先移到回收站，24 小时后再真正清理。

## 总结

Agent 权限边界的核心不是“信不信任模型”，而是**把信任工程化**。好的边界让 Agent 能自己干大多数安全的事，只在影响不可逆或超出白名单时打断人类。这个边界需要数据反馈和持续调参，而不是一次配置终身有效。
