## 背景

在 OpenClaw 里接多个模型后，很快会碰到一个现实问题：不是所有请求都值得发给 GPT 这类云端闭源模型。全量走 GPT，成本、延迟和上下文长度都不可控；全量走本地模型，遇到多步工具调用或者复杂指令，失败率会明显上升。

OpenClaw 本身适合做插件、MCP 工具编排和自动化流程，很多任务是流水线式的：意图识别、实体抽取、格式化输出、结构化判断。这些任务里，真正需要强推理和复杂指令遵循的只是一小部分。把这一小部分识别出来，就是多模型路由的核心。

## 问题

我在实际使用中遇到的主要矛盾有三个：

1. **能力差异**：本地模型在“抽取字段并返回 JSON”这类任务上表现尚可，但一旦涉及多轮工具调用、递归地检查 MCP 返回结果、或者处理长代码上下文，就容易丢步骤、重复调用、生成非法 JSON。
2. **成本与延迟**：GPT 对简单任务并不划算。一次简单文本改写、关键词提取也走 GPT，不仅慢，还会消耗 token 预算。自动化脚本高频调用时尤其明显。
3. **上下文连续性**：如果同一个会话里一会儿本地模型一会儿 GPT，系统提示词的理解方式、输出格式和风格会有偏差，导致下游插件解析不稳定。

所以需要一套稳定、可解释、可失败回退的路由规则，而不是每次凭感觉切换。

## 做法/步骤

我目前在 OpenClaw 里的路由策略分四层，配置核心是“任务类型 + 能力要求 + 回退条件”。

**第一层：静态规则路由**

先在 OpenClaw 的 router 配置里定义 task 类型和模型映射。示例：

```yaml
router:
  default: local
  rules:
    - task: text_classification
      model: local
    - task: entity_extraction
      model: local
    - task: text_summarization
      model: local
    - task: json_normalization
      model: local
    - task: multi_step_agent
      model: gpt
    - task: code_review
      model: gpt
    - task: long_context_reasoning
      model: gpt
```

这里的关键不是“文本任务都本地”，而是把“是否需要多步工具调用”和“是否需要长上下文推理”作为云端模型的触发条件。实体抽取、分类、摘要、格式整理这类任务，OpenClaw 里的插件通常只需要一次模型调用，本地模型完全能覆盖。

**第二层：复杂度判断**

对于不能提前写死的请求，OpenClaw 在做 MCP 工具调用前会先判断任务复杂度。我加了一个简单的复杂度标记：

- 单次输入、不需要工具、输出为 JSON/text → `low`
- 需要调用 1 个 MCP 工具、输出格式固定 → `medium`
- 需要调用多个 MCP 工具、需要根据中间结果决策 → `high`
- 需要长代码分析、跨文件推理、或者输入超过本地模型上下文窗口安全线 → `high`

`low` 和 `medium` 走本地，`high` 才升级到 GPT。

**第三层：本地模型能力约束**

本地模型部署时，尽量固定为支持结构化输出的推理后端，例如用 Ollama 或 vLLM 时开启 `json_schema` 约束，不要只靠提示词要求“输出 JSON”。OpenClaw 的插件如果依赖 MCP 工具，本地模型需要对工具描述有较好兼容性。我目前只让本地模型处理“无工具或单一工具”的任务，避免它在多工具选择上出问题。

**第四层：失败回退**

本地模型失败时要有明确升级条件，而不是立即报错。常见的回退触发条件：

- 输出解析失败超过 2 次
- JSON Schema 校验失败
- 工具调用参数缺失
- 本地模型返回空内容或重复内容
- 任务被标记为 `high`，本地模型自动跳过

回退到 GPT 后，OpenClaw 会带着同一份任务描述和工具上下文重新执行，避免状态丢失。升级后的结果会写回当前会话，保证后续步骤连续。

## 踩坑点

**1. 不要只按“是否敏感数据”路由**

有人觉得只要涉及内部数据就走本地，涉及公开数据就走 GPT。这个标准太粗糙。真正影响成功率的是任务结构和上下文长度。即使是敏感数据，简单的脱敏后字段抽取也可以走本地；反之，非敏感的长链条任务走本地也可能失败。

**2. 本地模型工具调用格式不稳定**

尤其是 7B/14B 级别的本地模型，在 MCP 工具选择和参数生成上很脆。一次调用返回了 `tool_name` 但少了 `arguments`，或者参数被包进普通文本里。需要加一层参数校验和后处理，必要时用正则把工具调用从文本里捞回来，而不是直接信任返回的 JSON。

**3. 上下文窗口差异**

本地模型常用 8k 或 32k 上下文，GPT 可能 128k 以上。如果一个任务在本地模型里被截断，它不会报错，而是会“编造”或者忽略中后段信息。路由时要保守计算：输入 token 超过本地模型上下文窗口 70% 的，应直接升到 GPT。

**4. 混用模型导致系统提示词失效**

同一个 OpenClaw agent，如果系统提示词写得太“GPT 化”，本地模型容易理解偏。建议为本地模型准备一份更短、更直接的系统提示词，减少复杂约束，多用示例。

**5. 不要用本地模型做最终决策兜底**

如果一条自动化链路最后需要“判断执行是否成功”，并且结果会触发后续写库、发送、发布等副作用操作，不要让本地模型单独做。这个判断应该要么交给 GPT，要么交给确定性的规则校验。

## 可复用建议

- **维护 task registry**：把 OpenClaw 里的常见任务列成清单，标注每类任务的最低模型能力，避免每次手动判断。
- **先本地后云端**：默认所有请求走本地模型，只有命中复杂度阈值或回退条件时才升级。这样成本更可控。
- **给本地模型加结构化约束**：强制 JSON Schema，减少下游解析成本。
- **监控升级率**：记录“本地模型处理了多少、升级到 GPT 多少、升级原因是什么”。如果某类任务升级率超过 30%，说明它本来就不适合本地模型，直接改规则，不再硬扛。
- **把回退做成无感**：升级到 GPT 时，OpenClaw 应复用已有上下文和工具状态，不要在失败后另起一轮。

## 总结

多模型路由不是简单的“能省则省”，而是把不同能力等级的模型放到合适的位置。OpenClaw 里，本地模型适合承担高频、低复杂度、结构化输出和无需多步工具调用的任务；GPT 适合承担多步 agent、长上下文推理、代码分析和关键决策任务。关键是把规则做成可配置、可监控、可回退的工程链路，而不是靠人工每次判断。

当你在 OpenClaw 中看到升级率稳定在一个合理区间，且本地模型失败不再直接影响业务链路时，说明路由策略基本到位了。
