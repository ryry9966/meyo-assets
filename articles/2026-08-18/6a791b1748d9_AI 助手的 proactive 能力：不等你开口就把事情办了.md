# 背景：为什么需要主动的 AI 助手

大多数基于 MCP / Agent 的助手目前是“应答式”的：你发指令，它调用工具、返回结果。这适合对话场景，但真实工程中有一类需求是“无人值守”——比如仓库 CI 挂了、依赖出现高危漏洞、某个服务磁盘快满了，你希望助手自己发现、自己判断、自己通知甚至修复。

这类能力通常被称为 proactive。但 proactive 不是把模型调得“更主动”就能实现，它需要一条完整的触发、判断、执行、确认链路。OpenClaw 社区里很多人已经接入 MCP 工具，但往往卡在“工具能调，但没人触发”这一步。

# 问题：MCP 本身不解决触发

MCP 解决的是工具标准化调用，它不管“什么时候该调”。如果你只是把一个 GitHub MCP server 接进 agent，它不会主动去查 issue 或 CI 状态。要让它主动干活，你至少得补上两类东西：

1. **触发器**：定时任务、webhook、消息队列事件、文件系统监听等。
2. **判断与执行策略**：什么情况下可以自己动手，什么情况下必须先报告等确认。

否则你得到的只是一个“会调工具但不会自己醒来”的助手。

# 做法：以“仓库巡检助手”为例

我以一个真实可复现的场景为例：让助手每小时检查一次指定 GitHub 仓库的 CI 状态、近 1 小时新增 issue 和 PR 评论，如果有异常则主动发通知，并对低风险事项自动打标签。

## 步骤 1：接好 MCP 工具

先通过 MCP 接入 GitHub 查询和操作能力。典型的 MCP 配置大致如下：

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"]
    }
  }
}
```

此时你可以在 agent 里手动说“查一下 xx 仓库的 CI 状态”，它能返回结果。但这只是应答。

## 步骤 2：加一个外部触发器

用 cron 或 systemd timer 每小时跑一次 agent 任务。例如 crontab：

```
0 * * * * cd /opt/agent && openclaw run --task "repo-health-check" --repo owner/repo
```

`repo-health-check` 是一个预定义任务，不是自由对话。它内部会带着结构化的 prompt 去调用 MCP 工具。

## 步骤 3：设计巡检 prompt

任务 prompt 要写清楚“你现在是主动巡检，不是回答用户问题”。例如：

```text
你是仓库巡检助手。当前时间：{now}
仓库：{repo}
请完成以下动作：
1. 拉取最近一次 CI 运行状态。
2. 拉取近 1 小时新增 issue 和 PR 评论。
3. 判断是否存在需要主动处理的问题。

处理规则：
- 若 CI 失败且是最近一次提交导致，自动添加标签 ci-fail，并在对应 PR 下评论一条简短原因。
- 若 issue 标题包含 security 或 CVE，立即发通知到 #alerts 频道，不要自动执行其他操作。
- 其他低风险事项只记录到日志，不自动执行。

输出 JSON：
{"actions": [{"type": "label|comment|notify|log", "target": "...", "reason": "..."}]}
```

## 步骤 4：加确认与权限控制

自动执行的操作要分层。低风险（打标签、发日志）可以自动做；高风险（合并 PR、删除资源、对外通知）默认 dry-run，只生成建议，由人工确认后执行。实现上可以在 executor 前加一个 `require_approval` 字段，或者在 prompt 里明确“所有写操作先输出计划，等待确认”。

## 步骤 5：记录决策日志

每次主动触发都要记录：触发时间、触发原因、拉取到的数据摘要、判断结果、执行了哪些动作、是否经过确认。这样出了问题可以回溯，也方便后续优化 prompt。

# 踩坑点

- **轮询 ≠ 事件驱动**。定时 cron 是伪 proactive，它只是周期性地“主动”，不是真正的事件触发。如果要求时效性，尽量用 webhook 直接触发 agent，而不是等下一个轮询周期。但 webhook 接入复杂，需要处理签名、重试、排重。
- **上下文污染与成本**。如果每次巡检都把全量数据塞进 prompt，token 消耗会很高，而且模型容易在大量无关信息里误判。最好做增量 diff：只传上一次巡检以来变化的内容，或者先用脚本过滤出值得看的事件。
- **LLM 判断不稳定**。模型对“是否需要处理”的判断可能忽紧忽松。建议用结构化输出 + 规则兜底：例如先用规则过滤出明确需要告警的条件（CI failed, security 关键词），再让 LLM 做二次摘要，而不是完全依赖模型判断。
- **自动写操作可能被平台限制**。例如自动评论太频繁会被 GitHub 视为 spam。实际使用时要控制频率、加去重机制，避免重复对同一 PR 多次评论。
- **权限别一下给太满**。最初只授予读权限和低风险写权限，等稳定运行一段时间再逐步放开。不要一上来就给 delete、merge、admin 权限。

# 可复用建议

1. **把 trigger、planner、executor、notifier 分层**。触发器只负责唤醒，planner 负责决定做什么，executor 负责调工具，notifier 负责通知。这样更换任意一层都不影响其他部分。
2. **先报后做**。对大部分场景，先发送摘要到通知频道，再根据确认执行，比直接自动执行更稳妥。可以设置“静默模式”，只报告不执行。
3. **为 proactive 行为建一个专门的日志表**。记录 trigger 类型、时间、判断置信度、执行结果。这个日志本身也是后续调 prompt 和规则的数据来源。
4. **充分利用 MCP 的标准化能力**。把常用巡检操作封装成 MCP 工具（例如 `get_ci_status`、`list_recent_issues`、`apply_label`），这样无论是定时任务还是对话触发，都能复用同一套工具。
5. **从低风险场景开始**。先做“只读 + 通知”的 proactive 助手，跑通整条链路后，再逐步开放自动打标签、自动评论、自动修简单配置等低风险写操作。

# 总结

Proactive 能力的关键不在于模型有多聪明，而在于工程上把“什么时候做、做什么、做到什么程度、出了事怎么追溯”这条链路补齐。MCP 提供了工具标准，但触发、判断和权限控制仍然需要自己设计。一个稳定的 proactive 助手，通常是从一个很小的定时巡检开始，逐步加入规则、确认机制和日志，而不是一步到位追求全自动。

对 OpenClaw / MCP 使用者来说，最值得投入的是把触发器和执行策略独立出来，让助手从“会聊天”变成“会值班”。
