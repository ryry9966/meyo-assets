## 背景

在 OpenClaw 这类 Agent 编排里，外部 API 不是可选项，而是任务链的承重墙。天气、搜索、支付、模型推理、MCP 工具，任何一个 5xx、超时或限流，都可能让已经跑了十几步的任务断在半路。

更麻烦的是，故障往往不是单次失败。上游抖动会引发重试风暴，重试又可能放大故障；而 Agent 一旦把错误堆栈反复塞回上下文，后续推理质量也会迅速下降。

## 问题

最典型的做法是只包一层 `try/except`，把异常吞掉或直接抛给模型。这样要么任务静默出错，要么模型开始根据半截信息“编结果”。另一个常见问题是重试策略过于粗暴：对 4xx 和 5xx 一视同仁，对写操作重复提交，最终把上游打挂或造成重复扣款。

所以需要把错误恢复从“临时补丁”提升为任务链路的一部分：分类、退避、熔断、降级、持久化、可观测，缺一不可。

## 做法 / 步骤

### 1. 先分类，再决定重试

不是所有错误都该重试。至少分成四类：

- 可重试：网络超时、连接重置、429、5xx。
- 不可重试：400 参数错误、401/403 鉴权失败、404 资源不存在。
- 可降级：非关键数据，例如推荐列表、天气摘要、搜索结果。
- 致命错误：支付、发送消息、写数据库这类关键动作失败。

工具层可以先返回结构化错误，而不是把裸异常丢给 Agent：

```text
{ "ok": false, "type": "retryable", "provider": "weather", "request_id": "..." }
```

### 2. 指数退避 + 抖动，限制重试次数

固定间隔重试会同步冲击上游。推荐指数退避加随机抖动：

```text
delay = min(base * 2^attempt, max_delay) + random_jitter
```

例如 `base=200ms, max_delay=5s, max_retries=3`。429 时优先读取 `Retry-After`，没有则走默认退避。对没有幂等保证的写接口，重试次数应更保守，甚至可以设为 0 或 1。

### 3. 熔断与半开探测

上游连续失败达到阈值后，与其继续打，不如直接熔断。简单状态机即可：

```text
closed -> open（连续失败 N 次）
open -> half_open（冷却时间过后）
half_open -> closed（探测成功）
half_open -> open（探测失败）
```

熔断期间走降级路径，快速失败，避免任务长时间悬挂。阈值要结合实际调用量设置，别把一次网络抖动误判成服务不可用。

### 4. 降级路径要显式

非关键数据可以准备 fallback：缓存、备用 API、静态默认值或延迟队列。关键是降级结果必须标记清楚：

```text
{ "ok": true, "degraded": true, "source": "cache", "cached_at": "..." }
```

不要静默返回旧数据。否则用户或下游 Agent 会把它当成实时结果继续决策。

### 5. 任务状态落库，恢复时幂等

长任务必须在关键步骤之间保存 checkpoint。失败后从最近 checkpoint 恢复，而不是从头跑。对于支付、发消息等写操作，强制传入幂等键：

```text
task_id + step_name + idempotency_key
```

即使重放，也只会生效一次。

### 6. 可观测

每次外部调用至少记录：`request_id`、`attempt`、`latency_ms`、`status_code`、`fallback_used`。这些字段在故障复盘时比“偶尔会超时”有用得多。

## 踩坑点

- **对非幂等接口重试**：比如重发短信、重复下单。重试前先确认接口是否幂等。
- **把工具超时误判为业务失败**：上游可能已经成功处理，只是响应慢。对写操作，超时后应先查询状态，而不是直接重试。
- **熔断阈值过于敏感**：一次抖动就全部降级，反而降低可用性。
- **降级结果不打标**：旧数据当成新数据，用户完全不知情。
- **不保存 checkpoint**：任务跑到第 15 步失败，恢复时从头开始，浪费 token 和时间。
- **把完整堆栈反复塞进 Agent 上下文**：错误信息要做摘要，只给模型必要的失败原因和下一步选择。

## 可复用建议

给所有外部工具包一个统一的包装层，集中处理重试、熔断、降级和日志。策略配置化，不要散落在每个工具代码里。缓存和 fallback 必须带新鲜度标记。对关键写操作强制幂等键。最后，把故障注入当成常规测试：手动让某个 API 返回 500、超时、429，看 Agent 是否能体面降级并继续推进。

## 总结

外部 API 挂掉不可怕，可怕的是 Agent 在失败面前没有既定策略：要么疯狂重试，要么静默返回错误结果。把错误分类、退避重试、熔断、降级、checkpoint 和可观测串成一条链路，大部分外部故障都可以被限制在局部，不会演变成整个任务链的崩溃。

工程上最实用的一句话：**让失败可见、可恢复、可降级，而不是让 Agent 替你“猜”过去。**
