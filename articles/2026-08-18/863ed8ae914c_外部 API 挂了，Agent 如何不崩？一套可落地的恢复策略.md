## 背景

做 OpenClaw、MCP 或插件自动化的同学基本都会遇到同一个场景：Agent 跑着跑着，某个外部 API 突然开始超时、限流或返回 500。常见于搜索工具、天气接口、支付回调、LLM 供应商、向量库，甚至内部 HTTP 服务。

很多人第一反应是加 try-catch，或者让 Agent 自己“看着办”。但实际工程里，外部 API 故障不是异常，而是常态。错误恢复应该被设计进 Agent 的工具调用层，而不是靠模型临场发挥。

## 问题

典型表现有几类：

- 工具调用抛 500/timeout，异常直接冒泡到主流程，任务中断。
- 原始错误堆栈被塞进上下文，模型开始“幻觉修复”，输出更离谱的结果。
- 无限重试导致限流加剧，自己的服务反过来把外部 API 打挂。
- MCP 连接断开后，工具列表缓存失效，后续调用全部失败。
- 降级逻辑静默返回空数据，Agent 误以为任务成功，用户得到错误结论。

这些问题的共同点是：缺少统一的错误分类、重试策略、熔断和降级机制。

## 做法/步骤

### 1. 在工具/MCP 层统一错误包装

不要直接抛异常。让每个工具返回统一结构：

```json
{
  "ok": false,
  "code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "degraded": false,
  "data": null,
  "message": "search_api timeout after 3000ms"
}
```

至少区分三类错误：

- `retryable`：超时、429、5xx 网络抖动。
- `non_retryable`：参数错误、鉴权失败、资源不存在。
- `degraded`：主源不可用，但可以用缓存或备用源返回结果。

### 2. 对可重试错误做指数退避 + 抖动

不要固定间隔重试，也不要无限重试。建议：

- 最大重试次数：2-3 次。
- 初始间隔：500ms-1s。
- 退避倍数：2x。
- 加入随机抖动，避免重试风暴。
- 设置总预算，比如单次工具调用总耗时不超过 8 秒。

### 3. 加一个简单熔断器

连续失败达到阈值后，直接快速失败，不再打外部 API。熔断器状态机可以很简单：

- 连续失败 >= 3 次：打开熔断。
- 打开后冷却 30-60 秒。
- 冷却结束进入半开状态，放一个探测请求。
- 探测成功关断，失败继续打开。

这一步不用引入复杂库，在工具层维护一个内存状态即可。多实例部署时，可以用 Redis 存熔断状态。

### 4. 设计降级策略，并显式告诉 Agent

降级不是“返回空就算了”。要明确告诉模型：这个结果是降级的。

例如搜索 API 挂掉时：

```json
{
  "ok": true,
  "degraded": true,
  "source": "cache",
  "cached_at": "2025-01-20T10:00:00Z",
  "data": [...]
}
```

同时把降级语义写进系统提示词或工具描述：

> 当工具返回 degraded=true 时，你必须告知用户当前使用的是缓存数据，并说明数据可能不是最新的，不要编造新鲜度。

这样比让模型自己猜测要稳定得多。

### 5. 保存状态与幂等

Agent 任务通常有多步。外部 API 失败后，如果前面的写操作没有幂等保护，重试会导致重复扣款、重复发消息、重复创建记录。

建议：

- 为写操作生成幂等键，放在请求头或参数里。
- 任务步骤落盘，记录已成功步骤。
- 失败后从断点续跑，而不是从头再来。

### 6. 增加可观测性

至少记录：外部 API 名称、错误码、耗时、重试次数、是否降级、熔断状态。日志里带 trace_id，方便串联 Agent 的完整调用链。

## 踩坑点

- **把原始堆栈塞回模型**：模型会尝试“分析”Python traceback，然后给出看似合理实则错误的修复。只把结构化后的 `message` 和 `code` 交给模型。
- **无限重试**：很多 API 限流是重试加重导致的。重试预算比“多试几次”更重要。
- **静默降级**：返回空列表或空对象，不标记 `degraded`，Agent 会认为没有数据，用户被误导。
- **MCP 断连不处理**：长连接断开后，工具列表可能还是旧的。建议加心跳检测，断线后自动重连并刷新工具列表，而不是等调用失败才发现。
- **只处理异常，不演练**：真正故障时才发现降级路径有 bug。

## 可复用建议

- 工具统一返回 `{ ok, code, retryable, degraded, data, message }`，所有外部调用都走这一层。
- 维护一个 `apiStatus` 状态机：`healthy / degraded / open / half_open`。
- 重试参数做成配置：最大重试次数、退避基数、总超时。
- 给每个外部 API 准备一个 fallback plan，哪怕是返回“暂时不可用”的明确错误。
- 定期做故障演练：手动停掉一个模拟 API，观察 Agent 是否按预期降级、是否重复写操作、是否正确告知用户。

## 总结

外部 API 挂了不是意外，而是系统运行的一部分。对 AI Agent 来说，错误恢复的重点不是“抓住异常”，而是：

1. 结构化错误，让模型能理解发生了什么。
2. 控制重试和熔断，避免雪崩。
3. 明确降级语义，避免模型编造。
4. 保证幂等和可观测，让失败可追踪、可恢复。

把这套逻辑做进工具层或 MCP 封装里，比让 Agent 自由发挥可靠得多。
