## 背景

现在社区里不少 OpenClaw 用户把 Agent 接进微信群、Discord、飞书、论坛自动回复，再挂上内部 MCP、插件、知识库，让自动化直接参与讨论、处理工单、查询后台。方便是方便，但安全边界很容易被忽略。

真正的风险往往不是 API key 被直接贴出来，而是更隐蔽的工作流泄露：内部项目代号、目录结构、客户沟通模板、审批人、内网域名、数据口径、云资源 ID。这些信息单独看可能不敏感，拼起来就能还原一套内部打法。

## 问题

这类泄露通常不是“模型主动叛变”，而是数据流设计有缺口。典型路径包括：

- 内部工具返回完整上下文，模型做摘要时把敏感片段带进回复；
- 插件读取 `.env`、本地文件或配置，把路径、用户名、内网地址织进社区消息；
- MCP server 工具描述诱导模型调用内部接口，结果被原样公开；
- 社区自动回复和内部调试共用同一个 workspace、记忆或日志；
- 链接预览、附件文件名、截图文字成为泄露通道。

所以防线要卡在数据流上，不能只靠提示词。

## 做法/步骤

### 1. 画出外发边界

明确哪些工具能读内部数据，哪些动作能向社区发送消息。不要把这两类权限放在同一个 Agent 默认能力里。可以用一张简单表格区分：

| 能力 | 内部 Agent | 社区 Agent |
|---|---|---|
| 读知识库 | 可读完整版 | 只读公开版 |
| 调用内部 MCP | 可调用 | 默认禁止 |
| 发消息到社区 | 默认禁止 | 需审批 |
| 读取本地 .env | 可读 | 禁止 |

### 2. 最小权限

社区场景单独建 Agent 实例，只挂公开工具和白名单 MCP。内部知识库工具即使可读，也不要让它直接带出原文；能不发到社区的，就不要给社区机器人开放。

### 3. 输出过滤

在 Agent 最终回复进入社区前，加一层 sanitizer。至少匹配这些模式：

- 密钥、token、API key
- 手机号、邮箱、身份证号
- 内网域名、IP、绝对路径
- 环境变量名、云资源 ARN、内部项目代号

命中后阻断或打码，并记录事件。不要只做简单正则，最好先对 base64、URL 编码做解码再匹配。

### 4. 外发审批

主动发帖、回复、上传文件、调用 webhook 都走延迟队列，先 dry-run 或人工审批。高频且低风险的内容可以设白名单模板，但不要默认放行。

### 5. 审计与脱敏

记录每次工具调用的参数和输出，但日志本身要脱敏。原始事件放到隔离存储，保留短周期，避免排障日志变成二次泄露源。

### 6. 提示词约束只作辅助

可以在系统提示里写“不要复述路径、变量名、密钥”，但它只能是最后一层。模型在长上下文和工具返回干扰下，很容易绕过这类约束。

## 踩坑点

- **只靠 prompt 说“不要泄露”无效**。工具返回内容一旦进入上下文，模型只是做摘要，很难保证不把敏感片段带出来。
- **脱敏正则太浅**。base64、URL 编码、截图文字、附件文件名、内网短域名都会漏。需要对常见编码先解码，对文件做文本提取。
- **日志和告警本身泄露**。为了排障记录完整消息，结果日志机器人又把原文发到群里。
- **链接预览泄露**。内部链接被群机器人展开后，标题、摘要、域名可能暴露。社区外发消息最好关闭链接预览。
- **MCP server 权限过大**。一个 MCP 工具返回整个配置文件，模型不一定能判断敏感。限制 MCP 只暴露必要方法，并在 server 端做脱敏。
- **社区 bot 和内部 Agent 共用记忆**。内部对话记忆被带到社区回复里，这是很隐蔽的泄露。

## 可复用建议

- **默认拒绝外发**。把“发到社区”视为高风险动作，需要显式授权。
- **统一外发网关**。所有插件、工作流发消息都经过同一个 pre-publish 过滤器，不要在各自分支里实现。
- **短期凭证**。MCP 和插件不要持有长期 key，用短期 token，限制来源 IP 和工具范围。
- **最小上下文**。给社区 Agent 的 system prompt 和工具输出都裁剪到公开信息，不要把内部 SOP 全文塞进去。
- **红队测试**。用包含内部路径、密钥格式、客户名的测试集，定期跑一次，看是否会被外发。
- **记录业务目的**。每个外发动作要能在日志里回答：谁触发、读到了哪些工具、最终内容是否通过过滤。

## 总结

Agent 安全红线不是“防止 AI 变坏”，而是“防止自动化把不该外发的数据带出去”。在 OpenClaw 的插件、MCP、工作流里，把边界做在数据流上：最小权限、输出过滤、外发审批、审计脱敏。这样社区自动化才敢长期跑，而不是跑三天就出一次事故。
