## 背景

做技术内容分发的人大概率经历过这种尴尬：新写了一篇 OpenClaw 插件实践，想同步到 Twitter、Discord、Reddit、中文社区，手忙脚乱复制粘贴，稍不注意几分钟内发了四五条几乎一样的帖子。然后账号安静了——不是没人看，是被平台暂时限制了。

用 Agent 或 MCP 工具做自动化发布后，这个问题没有自然消失，反而因为“一键群发”的惯性被放大了。我们需要的不是一个更快的内容喷子，而是一个懂节奏、会看场合的发布助手。

## 问题拆解

所谓“刷屏”，从工程角度看是两个维度的事：

- **频率维度**：在任意单一平台，短时间发送过多内容，触发了反滥用阈值。Twitter 的隐藏限流、Discord 的全局速率限制、Reddit 的 post karma 门槛，背后都是频率异动检测。
- **重复度维度**：完全相同的正文、相同的链接、相同的媒体文件，被多个平台的反垃圾模型标记为 cross‑posting 或 spam。

如果自动化同步只是把同一条 payload 轮询推到各平台 webhook / API，那么早晚会触发这两条线。真正的边界在于：**同步 ≠ 复制，发布 ≠ 即时全量**。

## 做法：构建带“平台感”的分发流水线

整个方案可以拆成三层：队列调度、内容适配、平台执行。用 OpenClaw 的 Agent + MCP 工具实现，不引入额外的编排框架。

### 1. 队列与节流

不要让用户直接触发“发布”。所有待发内容统一进入一个全局队列，每条任务携带`targetPlatforms`、`preferredTimeWindow`、`contentPayload`。由单线程或并发受控的调度器按平台分别管理冷却期。

最低限度的配置：

```
platforms:
  twitter:
    minIntervalMinutes: 90
    maxPerDay: 4
    maxPayloadLength: 280
  discord:
    minIntervalMinutes: 60
    maxPerDay: 6
    maxPayloadLength: 2000
  reddit:
    minIntervalMinutes: 120
    maxPerDay: 2
```

调度器每次出队时检查该平台的上次发布时间和当日计数，不满足就推后到最早可发送的时点。这个逻辑完全可以在一个 MCP 工具 `schedule‑post` 中实现，对外暴露给 Agent 调用。

踩坑点：**不要用 sleep 占坑**。sleep 阻塞会导致整个调度卡死。正确的做法是使用时间窗口判断 + 任务重新入队，或者基于 Redis 的延迟队列（BullMQ / SQS 延迟消息）。

### 2. 内容适配，而不是格式转换

很多人理解的“适配”是加个平台前缀，比如 Discord 消息前加个 `**New post:**`。这对重复度检查几乎没用。

工程上可行的做法是为同一篇内容生成**三个变体**：一条富于互动的（适合 Twitter）、一条总结性的（适合 Discord 摘要频道）、一条稍详细的解释（适合 Reddit 或中文社区）。可以借助 Agent 调用 LLM 做 rewriting，但必须指定严格的约束：

- 保留核心链接不变
- 禁止生成过分夸张的推广语言
- 每个变体长度严格匹配平台限制
- 媒体资源 URL 可以复用，但标题/摘要文本需要不同

把这些适配规则封装成 MCP 工具 `adapt‑content`，输入是原始帖子，输出是按平台分组的文本。适配过程中加入随机小尾巴（如日期、短文哈希）能进一步降低 fingerprint 相似度，但不要为了反检测搞成营销号风格。

### 3. 执行与异常降级

平台 API 在真·限流时返回的状态码和错误体各不相同。Twitter v2 返回 `429`，Discord 用 `X‑RateLimit‑Remaining` 头，Reddit 返回 `"you are doing that too much"`。不合理的重试是刷屏的隐形推手。

执行侧 MCP 工具 `post‑to‑platform` 的处理策略：

- **429 / rate limited**：任务标记为“被限”，把 `nextRetryAt` 设为 `Retry‑After` 头的时间或未来 15 分钟，不再盲目重试。
- **500 / 临时错误**：最多两次退避重试，间隔指数级增长。
- **不明状态 / 超时**：记录日志，人工确认。不要假设未收到 200 就等于失败而再次发布。

这些逻辑写死在工具里，Agent 只关心“发布是否进入待处理状态”，不参与重试决策，避免 LLM 胡乱补偿导致多发。

### 4. 可观测性：至少看得见是不是在刷

多数自动化被骂不是因为技术错，而是因为作者以为自己没刷，实际已经刷了。需要一页简单的状态视图：

- 各平台上次发布时间
- 当日各平台已发布条数 / 上限
- 当前队列长度
- 最近 24h 错误统计

用 OpenClaw 内置的日志通道或外部 webhook 把异常推送到 Discord 自己的告警频道，一句话告警就可以阻止灾难扩散。

## 踩坑记录

- **不同平台的 Link unfurling 会造成“加倍曝光”假象**：Discord 和 Twitter 会自动展开链接，导致一条消息看起来幅面很大，容易被管理员认定为“刷屏”。解决办法是控制摘要文本长度，或者在 Discord 禁用自动展开。
- **中文标点与 Twitter 字符数计算**：Twitter 对 CJK 字符计数为 2，但 API 的行为有细微变化。适配时按 140 个汉字控制，规避边界。
- **时区不敏感**：队列中的时间窗口如果全用 UTC，容易在中国的白天触发 Reddit 的深夜低互动时段。让 Agent 理解目标社区活跃时间比按固定延迟更合理。

## 可复用建议

1. **抽象成 MCP 工具组**：`schedule‑post`、`adapt‑content`、`post‑to‑platform` 三个工具组合即可，不绑定特定 Agent 框架。
2. **以“作者手动确认”为后门**：Agent 可以建议发布计划，但留一个 `approve` 指令，尤其对 Reddit 这种高永久性平台。
3. **用配置表驱动，不要硬编码**：社区规则会变，Twitter 从 140 变 280 再变 4000，把规则外置为 YAML/JSON 比改动代码安全。
4. **别急着全自动**：先跑一周半自动（生成内容但由人点击发送），收集各平台限流窗口的真实数据，再逐步放开。

## 总结

多社区同步真正的边界不在技术能不能发出去，而在发出去的节奏是否被社区接受。自动化的目标不是让一个人看起来同时在线 4 个平台，而是让内容在恰当的时点、恰当的口吻下自然出现。用队列控制频率、用适配降低重复、用降级避免雪崩，这套工程原则比任何一键群发插件都更长命。

工程上守住这个边界，Agent 才不再是刷屏工具，而是内容运营的稳定后端。
