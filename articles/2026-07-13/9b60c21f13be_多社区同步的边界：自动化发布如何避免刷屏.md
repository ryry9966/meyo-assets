## 为什么同步变成了刷屏

做开源项目、维护技术频道或者运营个人品牌时，总有把一条消息同步到多个社区的需求：Discord、Telegram、Twitter、掘金、微信公众号……一次人工分发耗时且容易遗漏，于是自然想到用 OpenClaw + MCP 这类自动化管线，让 Agent 代为发布。初期效果不错，但很快你会发现，频道的未读消息数突然拉满，群友开始@你「别刷了」，甚至账号被短暂禁言。

自动化同步本身没有错，但「自动化」很容易退化成「无差别广播」：同一条通知在五分钟内出现在六个平台，而且每隔两小时又重复一次，因为某个事件触发了重复推送。问题不在于工具能力太强，而在于我们很少在发布管线里加边界。

## 边界在哪里

真正的刷屏风险集中在三个维度：

1. **时间维度**：短时间窗口内对同一平台密集发布，尤其是内容完全一致或高度相似的条目。
2. **跨平台无感知**：运营者以为「每个平台只发一条」，但接收者可能同时关注了你的多个渠道，在信息流里撞见好几遍。
3. **事件重入**：自动化触发条件过于宽泛（比如每收到一个 webhook 就发一条），缺乏去重和限流，一个波动就会产生连锁重复。

所以避免刷屏的本质是给自动发布加上有「人类感」的节奏控制：平台合宜、时间分散、内容去重。

## 一个可落地的调度设计

下面是基于 OpenClaw + MCP 构建的发布调度方案，核心思路是将「发布意图」和「发布动作」解耦，中间用队列和限制器做缓冲。

**步骤 1：定义统一发布任务**

不要直接从触发器调用平台接口。把每次需要同步的内容封装为一个 `PublishIntent` 对象：

```json
{
  "content_hash": "abc123",
  "text": "...",
  "platforms": ["discord", "telegram"],
  "priority": "normal",
  "created_at": "2025-01-..."
}
```

`content_hash` 是对正文标准化后的哈希（去除空格、统一小写等），用于后续去重。

**步骤 2：构建发布队列与限流层**

在 Agent 内部维护一个基于 Redis 或内存的队列。为每个平台单独建立速率限制器（token bucket），比如：

- Discord 同一频道：每 10 分钟最多 1 条
- Telegram 频道：每 30 分钟最多 1 条
- Twitter：每 60 分钟最多 2 条
- 全局每日上限：所有平台合计不超过 20 条

当新任务到达时，检查该平台的 bucket 是否有可用令牌，若无则将任务推迟到下一个可用时间窗口。

**步骤 3：去重与合并**

在限流层之前，先查重：

- 用 `content_hash` 查最近 24 小时内是否已发布过相同内容到该平台，如果已发，直接丢弃。
- 若 1 小时内有多条低优先级内容等待发往同一平台，可以合并为一条带要点列表的消息，减少打扰。

合并逻辑不用太复杂：对等待队列中同平台的任务做一次简单聚合，正文用 `- 内容1\n- 内容2` 拼接即可。这样可以显著压低频次。

**步骤 4：实现平台适配器**

通过 MCP 服务器管理不同平台的凭据和格式化。不同平台对 Markdown、字数、@提及的支持差异很大。建议在适配器里做好剪裁，避免发出去后格式错乱引发重复编辑（编辑又可能产生新通知）。

**步骤 5：安全退避与监控**

如果平台返回 429 或 rate limit 错误，自适应用指数退避重试，并将该平台当前的 bucket 容量临时调整为 0，冷却一段时间。同时把异常记到 OpenClaw 的运行日志中，方便定位是哪条任务触发的限制。

## 踩过的坑

1. **分布式重复**：如果多个 Agent 实例同时扫描同一数据源（例如多个 worker 消费同一队列），没有分布式锁会导致同一个 `PublishIntent` 被执行多次。解决方式是在队列任务中带上唯一 dedup key，并利用 Redis `SETNX` 做执行锁。

2. **误判去重**：仅靠 content_hash 不去重修订版。比如改动一个错别字就生成新哈希，还是会被发出去。改进方案是用文本相似度（如 SimHash）配合编辑距离，设定相似度阈值（>0.9）视为重复。

3. **跨时区深夜推送**：假如你习惯在 UTC+8 的白天设计自动化，却忘了欧美社区的深夜时段。应当在配置中为每个平台设置「静默窗口」，例如 22:00-08:00 本地时间不发布（紧急通知可豁免）。

4. **平台每日限额远低于想象**：新账号或未认证应用的 API limit 可能非常小。Twitter 免费 API 每月只有 1500 条推文，平均每天 50 条，还得留给回复等操作。部署前务必查清限额，并在调度器里设硬上限，避免触发封禁。

## 可复用的配置模板

我在多个项目中复用的是这样一份 YAML 边界配置，Agent 启动时加载：

```yaml
rate_limits:
  discord:
    min_interval_seconds: 600
    max_daily: 10
    silent_hours: "23:00-07:00"
  telegram:
    min_interval_seconds: 1800
    max_daily: 10
  twitter:
    min_interval_seconds: 3600
    max_daily: 5
    silent_hours: "01:00-05:00"
global:
  max_daily: 20
  dedup_window_hours: 24
  similarity_threshold: 0.9
```

然后让 OpenClaw 在接收到需要同步的消息时，先通过调度控制器检查这些规则，再决定放入队列还是延迟。

## 总结

同步自动化的尽头不是「发得越多越好」，而是让每条消息在合适的时机、以恰当的形式到达不同社区，避免让关注者感到被刷屏。加入时间间隔、去重、合并和平台限额这些边界并不复杂，但它们是把「机器广播」拉回「有人味发布」的关键。每次调整这些参数时，不妨翻看几个平台的实况，问问自己：如果我连续看到这三条通知，会觉得烦吗？答案会告诉你边界该设在哪儿。
