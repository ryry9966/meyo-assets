## 背景

维护一个内容发布工作流时，经常遇到“写完发完博客，还要手动分发到微博超话”的重复劳动。如果是团队协作或需要规律更新的账号，手动操作不仅耗时，还容易遗漏。我们希望借助 OpenClaw 的 Agent 能力，把“从内容源提取摘要→配图→发到指定超话→记录发布状态”整条链路自动化。

微博开放平台对超话发帖的支持并不友好：发帖接口参数隐晦、图片上传独立于发帖流程、频率控制规则未文档化。要实现稳定运行，需要在接口调用、错误处理和状态持久化上多下功夫。

本文记录一个基于 OpenClaw 自定义 Action 的超话同步实践，聚焦图片上传、限流策略和发布状态归档三个关键点。

## 问题拆解

目标流程可以概括为：

1. 输入待发布内容（标题、正文、图片本地路径或 URL）。
2. 上传图片至微博图床，获取 `pid`。
3. 调用超话发帖接口，携带 `pid` 和超话 ID。
4. 应对接口限流，避免触发封禁。
5. 记录每次发布结果，支持失败重试与隔天继续。

其中，步骤 2 和 3 的接口并未在公开文档中清晰给出，且存在以下工程难点：

- **图片上传**：必须使用微博的 `picupload` 接口，返回的 `pid` 是发帖参数的关键依赖，但该接口容易被频率限制，且需要有效的登录态。
- **超话发帖**：需要指定 `topic_id`，纯文本发帖可以不带图片，但带图片时必须先获得 `pid`。接口返回中无明确的发布状态，需要靠后续查询确认。
- **限流**：官方未公布明确阈值，实测中，单账号连续发帖 >3 次/小时 或 图片上传 >5 次/10 分钟，容易触发“发布失败”或账号操作受限。
- **状态归档**：没有持久化记录，出了问题无法回溯，难以做增量同步。

## 做法与步骤

### 1. 整体架构

在 OpenClaw 中定义一个 `WeiboChaohuaPublisher` Action，它内部维护一个任务状态机，状态流转为：

```
PENDING → UPLOADING_IMAGE → IMAGE_UPLOADED → POSTING → POSTED
       ↘ FAILED (终态)      ↘ WAITING_RETRY
```

所有状态变更都会写入一个 SQLite 本地库（或简化为 JSON 文件），方便跨重启保留。

### 2. 图片上传

微博图片上传接口可简化为：

```
POST https://picupload.weibo.com/interface/pic_upload.php
参数: 
  - access_token 或 cookie
  - data: 图片二进制，multipart/form-data
  - 其他固定参数 (app, s, etc.)
```

我们复用已有的账号登录态（通过 `sub` cookie 的方式保持会话），避免频繁换取 token。（注：OpenClaw 中可以通过 Secret 管理凭证，不硬编码。）

关键处理：
- 上传成功会返回 `{"code":1, "data":{"pics":{"pic_1":{"pid":"xxx"}}}}`，提取 `pid`。
- 如果返回错误码 `10021`（命中频率限制），状态转为 `WAITING_RETRY`，并记录下次可重试时间（当前时间 + 10 分钟）。
- 图片需要在本地做缓存，避免重复上传同一文件。通过图片 hash 索引已有 `pid`，减少接口调用。

### 3. 超话发帖

发帖接口使用 `https://weibo.com/aj/mblog/add?ajwtype=1`，需要携带以下参数（部分）：

- `text`: 帖子正文，需包含超话标签，如“#超话名称#”。
- `topic_id`: 超话 ID。
- `pic_id`: 上传获得的 `pid`，可选。
- `location`, `appkey` 等辅助参数。

调用时需构造完整的 cookie 和 header（`Referer` 等），降低被风控概率。

返回 JSON 中如果有 `code == "100000"` 即成功，否则解析 `msg` 分析原因。常见的除了限流，还有“内容违规”或“超话等级不足”。前者需要人工介入，后者可通过积累经验规则自动跳过。

### 4. 限流控制

我们采用令牌桶 + 退避策略：

- **发帖桶**：1 次/20 分钟，桶容量 1。
- **图片上传桶**：5 次/10 分钟，桶容量 5。

在 Action 执行前先检查令牌，无令牌则直接抛 `RateLimitError`，由调度层（OpenClaw 的定时器或外部 cron）在下一周期重试。

如果收到微博明确限流错误（`10021`），对相关操作设置冷静期 15 分钟，并记入状态文件，方便监控。

### 5. 状态归档

每次发布完成后，将以下信息写入归档：

```json
{
  "content_hash": "...",
  "title": "...",
  "super_topic_id": "...",
  "image_pids": [],
  "status": "POSTED",
  "posted_at": "2025-03-28T10:12:00Z",
  "weibo_post_id": "xxxxxxxx"
}
```

失败记录额外保留错误码和错误信息，支持后续自动重试或人工排查。配合 OpenClaw 的 Log 插件，可输出到本地 Markdown 表格，一目了然。

## 踩坑点

1. **图片上传反 CSRF**：接口需要精确的 `Referer` 和 `X-Requested-With` 头，否则返回“请求来源不合法”。这要求 Action 必须模拟完整的浏览器行为。
2. **cookie 过期**：长期运行时登录态会失效，表现为发帖返回登录重定向。需要增加登录态检查，失效时走重新登录流程（通过自动化 playwright 或手动更新 cookie 字符串）。
3. **超话 ID 非公开获取**：除了网页 URL 中能拿到，API 文档不直接提供。我们通过抓包固定了几个频道的 ID，硬编码在配置中。
4. **发帖文案中的 `#` 处理**：超话名称中若含特殊符号，需要精确匹配，否则帖子不会出现在超话页面，只算普通博文。
5. **状态文件并发写**：如果同时跑多个 Action 实例（不推荐），会出现状态覆盖。最终改为单实例串行执行，利用文件锁 `fcntl` 保证。

## 可复用建议

- **抽象成通用 Publisher 插件**：将微博超话发布逻辑剥离为 `social_media_publisher` 的 Tool，支持配置不同平台（如小红书、即刻）。这样未来扩展只需实现对应的接口适配器。
- **内置状态机**：推荐使用 `python-statemachine` 或简单的 Enum + while 循环管理状态，让重试和恢复逻辑清晰。
- **避免“聪明”的调度**：不要试图在短时间内高频率发布“优化效率”，除非你有多个账号切换。稳定性远比速度重要。
- **记录发布物料的指纹**：通过内容 hash 去重，防止重复发布同一篇内容（尤其是在调试期）。
- **指标输出**：将成功/失败次数、限流等待次数导出为 OpenClaw 的 Metric，接入简单的 dashboard（如 grafana + sqlite exporter），让状态一目了然。

## 总结

这次实践让我再次感受到，自动化社媒发布的瓶颈往往不在 Agent 能力本身，而在于对平台反爬/风控策略的工程化应对。通过图片上传的缓存与去重、严格的令牌桶限流、完备的状态归档，我们将一个脆弱的“脚本”打磨成了可以长期运行的可靠 Action。

如果你同样在用 OpenClaw 做内容分发，不妨从这三个点入手：上传链路独立、限流宁可保守、归档要能回溯。代码并不复杂，关键是别偷懒。

*以上接口信息基于 2025 年初的微博网页端行为，随时可能变化，请以最新抓包为准。*
