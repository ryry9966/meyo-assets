# 微博超话同步踩坑：图片上传、限流与状态归档实战

## 背景

我们在运营多个微博超话时，需要定期向不同超话同步带有图片的资讯内容。手工操作重复且容易遗漏，于是决定构建一个基于 OpenClaw 的自动化同步 Agent。OpenClaw 的任务引擎与 MCP 工具调用机制很适合这类“获取内容 → 转换 → 发布”的流水线，但真正落地时，才发现微博超话同步的细节远比预想中复杂，尤其是**图片上传、接口限流和状态归档**这三个环节。本文围绕这些坑点，梳理一套可工程化落地的实践方案。

## 问题拆解

### 图片上传的特殊性

普通微博发图可通过 `statuses/share` 直接上传，但超话发帖需要先将图片上传至微博图床获取 `pid`，再将 `pid` 填入超话发帖接口。这意味着需要独立维护图片上传链路，且微博的图片接口对 `Referer`、`UA`、`cookie` 非常敏感，稍有偏差就会上传失败。

### 限流与风控

微博对单账号的发帖频率有隐形限制。连续发帖会触发 `"频繁操作"` 错误（返回码通常为 `100001` 或自定义提示），同时图片上传也可能被独立限流。没有合理的退避策略，账号极易被短暂静默甚至封禁操作。

### 状态归档的必要性

自动化脚本可能在任意环节中断（网络波动、进程崩溃、微博返回异常），如果没有可靠的状态记录，就必然出现**重复发帖或漏发**。一条推送可能因为“看起来没成功”而被重复发布多次，破坏超话秩序。必须设计一套与业务逻辑解耦的归档机制，保证“发前能查、发后能记、异常能恢复”。

## 工程化做法

我们基于 OpenClaw 的工作流串联整体逻辑，并通过 MCP 协议封装微博操作为可复用的工具。整体链路如下：

1. **登录态维护**：事先通过扫码获取微博 cookie，存储到环境变量或本地配置，并在每次请求前检查有效性（若失效则告警，人工重登）。
2. **图片上传工具**：接收本地图片路径或图片 URL，完成“下载 -> 上传到微博图床 -> 返回 pid”的闭环。
3. **超话发帖工具**：传入文本内容、图片 pid 列表、超话 ID，构造请求并发布。
4. **限流控制器**：基于 Redis 或本地文件的计数窗口，控制两次发帖最小间隔；遇到限流错误时执行指数退避。
5. **状态归档器**：使用 SQLite 记录每次发帖的幂等键（内容哈希 + 超话 ID）、帖子 mid、发帖时间、状态（pending/success/failed），提供查询与更新接口。

OpenClaw 中的 Agent 只需按序列调用这些 MCP 工具，将同步任务声明为工作流，就能实现端到端自动化。

### 图片上传链路（核心步骤）

图片上传的关键是获取 `upload_url` 并使用 multipart 上传：

```
GET https://picupload.weibo.com/interface/pic_upload.php? ... &mime=image/jpeg&data=base64&url=0
```

需要提前准备正确的 `Referer`（一般设置为 `https://weibo.com/`）和登录 cookie。上传成功后，接口返回形如 `<pid>xxxxx</pid>` 的 XML，提取其中 `pid` 即可。随后在超话发帖接口中将 `pid` 拼入 `pic_id` 字段。

### 超话发帖接口

发帖时使用 `https://weibo.com/aj/mblog/add?ajwvr=6` 的 POST 请求，form data 需要包括：
- `text`：微博正文
- `pic_id`：拼接的图片 pid
- `topic_id`：超话 ID（containerid 尾号部分）
- `st`：从超话页面获取的 token（部分情况下需要，不传可能被拒）

### 限流处理

我们设定最小发帖间隔为 90 秒，并在触发“频繁操作”时暂停 5 分钟后重试。消息队列里引入退避策略，失败次数越多等待时间越长，同时通知监控。

### 状态归档与幂等

每条待发内容生成一个唯一键 `task_key = md5(content_hash + topic_id)`，发帖前查询归档表：
- 若存在且状态为 `success`，直接跳过；
- 若存在状态为 `failed`，且重试次数未超限，则重试；
- 若不存在，执行发帖并插入记录。发帖成功后立即更新状态并保存微博返回的 `mid`。

这种方式能有效避免重复，也方便回溯任何一次的同步结果。

## 踩坑实录

- **图片上传的 Referer 与跨域**：不设置 `Referer` 或使用了错误的域名会导致上传失败，返回 `-100` 错误。移动端接口与 PC 端接口对 Referer 要求不同，必须先抓包确认当前可用域。
- **限流错误码混淆**：有时候返回的并不是标准错误码，而是弹窗文本，需做模糊匹配。另外，图片上传有时被限流，却返回 200 但内容为空，极易被当成成功跳过，须严格校验返回值。
- **状态归档并发冲突**：如果多个工作流实例同时检查任务，很可能会产生竞态，导致同一任务被提交两次。务必给幂等查询和插入加重试或乐观锁，SQLite 中可使用 `UNIQUE` 约束 + `INSERT OR IGNORE` 来规避。
- **Cookie 过期无提示**：一旦 cookie 失效，所有请求会静默失败或被重定向，必须在请求级封装拦截器，检测到登录态异常时立即告警并暂停工作流。

## 可复用建议

1. **封装 MCP 工具**：把微博发帖、图片上传、状态检查分别实现为 MCP 的 Tool，通过 OpenClaw 的 Agent 快速编排；这样任何其它内容同步项目都可以直接复用。
2. **限流配置外部化**：将间隔时间、退避系数、最大重试次数做成 config，不同账号、不同时间段可动态调整。
3. **状态归档单独服务化**：如果任务量增大，SQLite 可能成为瓶颈，可切换至轻量键值库或用 Redis 做幂等层，同时保留持久化归档。

## 总结

微博超话自动化同步看似只是一个“发帖”动作，但当引入图片、面对非官方接口的隐性限流、并追求长期稳定运行时，工程复杂度会迅速上升。我们从实践中总结出的关键是：**独立维护图片上传链路、精细处理限流退避、并将状态归档做到幂等和可恢复**。借助 OpenClaw 的任务引擎和 MCP 工具抽象，这些能力可以被很好地封装和复用，让自动化 Agent 真正可靠地服务于内容分发。
