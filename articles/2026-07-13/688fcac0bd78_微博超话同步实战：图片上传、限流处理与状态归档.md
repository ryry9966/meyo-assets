## 背景

有跨平台内容分发需求的运营团队，经常会尝试用自动化脚本把外部系统生成的内容同步到微博超话。常见的触发场景包括：公司官方博客发布新文章后，自动以摘要+封面图的形式推送到对应的产品超话；或者是用 Agent 定期抓取 RSS，摘要后发布。

在 OpenClaw 的技术语境下，这类工作非常适合用 plan-act 结构的自动化插件完成。然而一旦落地到微博的实际接口，就会接连碰壁——尤其是图片上传、接口限流以及多轮重试后的状态追溯。本文记录了一次完整的同步链路设计，不涉及具体产品名，只讨论工程做法和可复用的经验。

## 问题拆解

微博超话发帖并没有独立的 API，本质上还是调用 `statuses/update` 接口，只是文本中必须包含 `#超话名称#` 才能被收录进对应社区。这意味着我们要解决的两个核心问题是：**图片上传** 和 **发布限流**。再加上自动任务通常无人值守，**状态归档** 就成了避免重复发布和排查故障的唯一依据。

实际遇到的问题包括：

1. 官方文档对图片上传的 multipart 参数描述有疏漏，直接按文档拼装请求会收到 `pic_id` 为空或 400 错误。
2. 连续调用发布接口很快撞上 IP 维度或用户维度的频率限制，没有退避策略的任务会在若干次失败后直接丢弃剩余条目。
3. 重试逻辑和业务代码耦合，出现一次网络超时后，同一篇文章可能被发布两次。
4. 没有持久化记录，白天运营发现缺帖时，已无法判断是哪一步失败。

## 做法

### 1. 图片上传的可靠流程

微博 OAuth2 授权后，标准的上传步骤是：先通过 `statuses/upload` 以 multipart/form-data 上传图片，获取 `pic_id`；然后将 `pic_id` 随文本一起传给 `statuses/update`。这里有两个易错点：

- **参数名必须严格使用 `pic`**：部分旧文档写的是 `pic[0]` 或 `media`，但实际上只认 `pic`。我用 Python 的 `requests` 库，组装时写 `files={'pic': ('cover.jpg', open(path, 'rb'), 'image/jpeg')}`，其他参数如 `access_token` 要放在 URL 查询串，不能混在 form-data 里。
- **上传地址不需要拼 `?access_token=...` 在 body 里**：官方示例有时把 token 放在 POST body，但实际接口只能从 query string 取 token，且上传接口的基础路径是 `https://api.weibo.com/2/statuses/upload.json`，不要错用成 `https://upload.api.weibo.com/...`。

为了减少网络波动影响，上传环节增加了带退避的重试：仅在 5xx 或连接重置时重试最多 3 次，4xx 错误（如 token 过期）直接向上抛出，避免无效重试。

### 2. 限流应对

微博接口的限流维度比较复杂：有应用级、用户级和 IP 级。自动化任务的调用往往是短时间密集调用，我最常遇到的错误码是 `10022`（IP 请求超限）和 `10023`（用户请求超限）。解决方式不是硬等，而是在一个限流器内排队：

- 使用令牌桶控制调用速率，例如设定每秒最多 1 次发布请求，突发允许 2 次。每次 `statuses/update` 前消耗一个令牌，无令牌时异步等待。
- 对于返回特定错误码（如 10022、10023、10004），捕获后线程休眠相应秒数（根据 `error_code` 映射的退避时间，一般 60 秒起），然后重新入队，而不是直接失败。
- 任务调度层面，单次同步任务拆成“取内容 → 上传图片 → 发布”的流水线，各环节独立的速率控制，避免图片上传挤占发布令牌。

### 3. 状态归档设计

用 SQLite 维护一张简单的同步状态表：

| 字段 | 说明 |
|------|------|
| `content_id` | 源内容唯一标识（例如文章 ID + 超话 ID 的 hash） |
| `status` | pending / uploading / published / failed |
| `pic_id` | 上传成功后保存 |
| `weibo_id` | 发布成功后返回的微博 ID |
| `retry_count` | 当前重试次数 |
| `last_error` | 最近一次错误信息 |
| `created_at` / `updated_at` | 时间戳 |

每次进入同步流程时，先根据 `content_id` 查表：

- `published` 且 `weibo_id` 有效 → 跳过。
- `uploading` 但 `updated_at` 超过 10 分钟无进展 → 认为上传卡死，重置为 `pending` 重新处理。
- `failed` 且 `retry_count < 3` → 允许重试，并递增计数。
- `failed` 且超出重试上限 → 移动到人工检查死信表。

这一设计避免了重复发帖，也使得任何时间点都能快速知道“哪些内容还没发出去”。

## 踩坑记录

- **超话话题必须紧贴文字**：`#超话名称#` 前后不能有标点粘连，否则微博分词器可能识别失败。最好在话题后加一个半角空格再继续正文。
- **pic_id 生命期隐式有效**：官方文档没有明确说明，但实测超过 3 天未使用的 `pic_id` 会失效，发布时会返回图片错误。对策是上传后立即使用，不缓存。
- **内网环境调用需要固定 IP**：如果服务部署在云函数或动态出口的机器，IP 维度的限流会异常严重。建议出口绑定弹性 IP 并在微博开放平台完成 IP 白名单报备。
- **别把 token 当持久态**：测试环境的 token 过期后，任务会连续报 400 错误并被归档为 `failed`，直到发现无法自动恢复。必须加入 token 刷新逻辑，失败时自动使用 refresh_token 换取新 token 并更新配置。

## 可复用建议

如果你正在 OpenClaw 生态下构建类似的自动化插件，可以把以下模块抽成可复用组件：

- **WeiboClient**：封装鉴权、图片上传、文本发布及错误码处理，对外暴露简单的 `post_with_image(content, image_path, supertopic)` 方法。
- **RateLimiter**：基于令牌桶的通用限流器，发布和上传各自实例化，避免相互干扰。
- **StateStore**：归档层的抽象接口，支持内存、SQLite 或远端 DB，便于测试和切换。

把这些模块挂载在 OpenClaw 的 tool / skill 中，就可以让 Agent 根据计划自主选择调用，而不是把每一步都硬编码在流程里。

## 总结

微博超话同步的难点并不在接口本身有多复杂，而在于分布式任务中容易被忽视的工程细节：正确的图片上传参数、多维度的限流、以及可靠的状态追踪。一次完整的实践后，整个管道的稳定性会有质的提升，从“跑几次就挂”变成可以安心让它定时运行的后台服务。对于 OpenClaw 社区正在进行各种自动化探索的同学，这类端到端的工程笔记应该能省下不少翻文档和踩坑的时间。
