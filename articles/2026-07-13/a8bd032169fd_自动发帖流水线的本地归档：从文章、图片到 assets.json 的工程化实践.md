## 背景

在自动化发帖流水线中，常见的做法是：Agent 生成或拼装文章，通过 MCP 或插件直接推送到目标平台（公众号、知乎、Twitter、Discord 等），任务结束即丢弃中间产物。短期内这提升了效率，但长期来看，内容资产散落在各种 API 回调与临时目录中，团队很难回溯某一篇文章的原始版本、证明版权归属，或者对历史帖子进行批量分析、迁移与复用。

更普遍的场景是，文章引用了多张图片——部分来自本地生成，部分来自远端截图。流水线跑完后，这些图片要么留着占用 CI 缓存，要么被清理掉，后续想对某篇爆款文章做二次编辑或翻译时，发现图片已经找不到原始副本。

将这些中间产物系统化地“沉淀”成**本地归档**，并辅以结构化的 `assets.json`，能显著提升内容工程的可追溯性、可移植性和可维护性。本文面向熟悉 OpenClaw、Agent、MCP 及插件机制的开发者，描述一套可直接集成到现有流水线的归地方案。

## 问题定义

一条典型的自动发帖流水线会产出三类资产：

1. **文章正文**：Markdown 或富文本，最终发布版本。
2. **图片资源**：可能是本地截图、Canvas 生成图、下载的配图、平台要求的封面等。
3. **元数据**：标题、标签、发布时间、目标平台、是否已发布成功、用户自定义字段等。

如果这些资产仅靠日志或数据库一条记录来关联，后期检索成本很高。例如你想知道“上个月发在知乎的某篇文章用了哪些图片”，就需要去翻平台后台，或者从杂乱的文件夹中猜测。**缺少一份本地 `assets.json` 将资产关系显式化，是当前很多流水线的痛点。**

## 目标与设计原则

归档的目标不是全量镜像平台，而是保留**生成端的最终有效产出**，满足以下需求：

- **离线可读**：在无网络环境中能打开文章并看到图片。
- **结构化索引**：通过 `assets.json` 快速定位某篇文章的所有资源。
- **版本可回溯**：归档目录纳入 Git 管理，每次发布形成一个 commit。
- **非侵入性**：不对现有发布流程做破坏性修改，归档失败不应阻塞发布。

设计上遵循“最小可用归档”原则：不要过度设计字段，保证每个流水线节点都能低成本接入。

## 归档目录结构

推荐按日期和文章 slug 组织，例如：

```
content-archive/
  2025/
    03/
      2025-03-27-how-to-build-pipeline/
        post.md
        images/
          cover.png
          diagram_01.png
          screenshot_login.png
        assets.json
```

- `post.md`：最终发布的完整 Markdown，图片引用保持原始远程 URL（便于直接复制到平台编辑器），但在归档中不做本地路径替换。如需离线浏览，由 `assets.json` 提供本地图片映射。
- `images/`：所有关联图片的本地副本。文件名使用有意义的英文，避免 `img_001.png` 这类无意义命名。如果原始 URL 中的文件名不可读，可以用内容摘要或 hash 重命名，并在 `assets.json` 中记录映射。
- `assets.json`：结构化记录所有资产关系，下面给出参考结构。

## 关键结构：assets.json

`assets.json` 不需要承载全部业务字段，但至少应包含文章标识、时间、平台、标签和图片清单。一个最小示例：

```json
{
  "slug": "2025-03-27-how-to-build-pipeline",
  "title": "如何搭建自动化发帖流水线",
  "created_at": "2025-03-27T10:30:00Z",
  "platforms": ["zhihu", "twitter"],
  "tags": ["automation", "openclaw", "agent"],
  "post_file": "post.md",
  "images": [
    {
      "file": "images/cover.png",
      "original_url": "https://cdn.example.com/img/cover_abc123.png",
      "alt_text": "流水线架构图",
      "width": 1200,
      "height": 630
    },
    {
      "file": "images/diagram_01.png",
      "original_url": null,
      "alt_text": "MCP 交互流程",
      "note": "本地生成"
    }
  ],
  "archive_version": "1.0"
}
```

字段都是平铺的，方便任何语言解析。`platforms` 字段记录这篇文章实际推送到了哪些平台，可以为后续平台维度的检索提供便利。

## 集成到流水线的步骤

以 OpenClaw 流水线为例，归档动作可以作为一个 **Post-action Hook** 或独立的 **归档 MCP 工具** 放在发布成功后执行。步骤如下：

1. **文章落盘**  
   在内容生成完成后（可能是 Agent 输出的 Markdown 文本），立即将最终版本写入 `post.md`。如果团队需要保留草稿，可以在生成阶段就写入一个 `draft/` 目录，发布成功后再移动到正式归档位置。

2. **图片收集**  
   解析文章中的图片引用（正则匹配 `![]()` 或 HTML `<img>`），逐一检查：
   - 本地生成的图片：直接复制到 `images/` 目录。
   - 远程图片：通过 HTTP 下载并保存。为了避免重复下载，可以对比已有文件的 hash。下载时注意处理重定向、404 和超时，失败则记录在 `assets.json` 的 `images` 数组中并标记为 `download_failed: true`。

3. **生成 assets.json**  
   收集上述信息，按约定结构生成 JSON 文件。建议在归档工具内部提供一个模板方法，避免不同流水线节点各自为战，导致 JSON 结构漂移。

4. **版本提交**  
   将整个归档目录 `git add` 并提交。提交信息建议包含文章 slug 和发布平台，如 `archive: 2025-03-27-how-to-build-pipeline (zhihu, twitter)`。如果团队使用 monorepo 管理内容，归档目录可能就在主仓库内，直接提交即可。

5. **错误处理**  
   归档失败不应影响发布流程的返回状态。可以将归档错误记录到日志或发送告警，但不要因为一张图片下载超时就回滚已成功的发布。更工程化的做法是，归档模块用独立的 try-catch 包裹，并使用队列或延时重试机制处理临时性失败。

## 踩坑点与应对策略

### 图片路径与引用问题
远程图片可能为相对路径、无协议（`//cdn.example.com/img.png`）、或需要特殊 User-Agent 下载。归档工具应统一将引用标准化为绝对 URL 再进行下载。同时，保留原始引用不变，避免影响再次发布。如果要打造离线可读的文章，可以额外生成一份本地路径版本（如 `post_local.md`），但不入版控，由脚本按需生成。

### 文件名冲突与可读性
远程图片文件名可能无意义或重复，例如 `1.png` 被多个平台引用。建议按 `slug-描述-hash前8位.扩展名` 重命名，并在 `assets.json` 中保存原始 URL。描述可以从图片 alt 文本或上下文提取，若无，则使用 `image_index`。

### 平台特有资源
如微信公众号的封面、不同尺寸的缩略图等，属于平台的产物，不属于原始生成稿。这些资源可以单独归档到 `platforms/` 子目录，并在 `assets.json` 中增加 `platforms` 数组记录每个平台的专用资源路径。

### assets.json 膨胀
如果一篇文章有几十张图片，JSON 会变大。保持 `images` 数组为基本描述即可，不存储图片 base64 或大量 meta。需要更丰富的图片分析数据（如主体色、OCR 文本）时，可以再生成独立的 `images_analyzed.json`，避免核心元数据臃肿。

### 并发与多流水线写入
若多个 Agent 同时触发归档同一篇文章，可能出现竞争写。通过目录 slug 加锁（例如文件锁）可以避免。最简单的方式是让归档步骤串行执行，或者在归档前检查目标目录是否已存在并决策是覆盖还是跳过。

## 可复用建议

- **归档工具模块化**：将“收集文章 + 下载图片 + 生成 assets.json”封装成独立脚本或 MCP 工具，所有发帖流水线统一调用。避免每个流水线用不同语言实现，增加维护成本。
- **模板化 assets.json**：使用 JSON Schema 约束字段，并提供默认生成模板，新接入的 Agent 只需填充核心字段即可。
- **结合内容中台**：如果团队已有内容管理后台，可以将本地归档作为内容中台的“源端”，触发 Webhook 同步到后台，形成双保险。
- **定期清理**：本地归档会占用磁盘空间，可以设置保留策略，例如清理半年前的图片缓存（保留 JSON 和 Markdown），需要时再从图床或平台重新拉取。

## 总结

自动发帖流水线中加入本地归档环节，本质上是用很小的工程代价为内容资产建立“物账相符”的本地副本。它不仅解决了长期困扰运营和开发的“文章图片去哪了”问题，也为后续的内容分析、跨平台同步、版本回溯提供了坚实基础。

这套方案的要点在于：**轻量结构、异步归档、失败不阻塞、元数据先行**。在 OpenClaw 生态中，完全可以作为插件或标准 Action 提供给社区复用，让每一次自动发帖都变成一次内容资产的沉淀，而非一次性的信息排放。
