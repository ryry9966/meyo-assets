## 背景

在 OpenClaw 生态里，很多人已经用 Agent + MCP 搭建了内容生产与多平台发布的自动化流水线。文章写完、封面生成、一键推送到多个渠道，效率提升明显。但一个容易被忽视的问题是：**发布完的内容就这样散落在各个平台，本地没有任何留存**。当你想复盘历史文章、迁移平台，或者因为某个平台删帖而丢失内容时，才发现没有一个能快速检索、复现的本地副本。

本地归档并不是“多存一份 markdown”，而是要结构化地保留文章原始内容、图片资产、发布元信息，使得未来无论是重新编辑、自动化分析还是二次分发都依然可控。

## 问题拆解

一个完整的自动发帖流程通常包含：选题 → 撰稿 → 图片/封面生成 → 平台适配 → 发布。如果不在流程中嵌入归档步骤，会带来几个具体痛点：

1. **文章版本丢失**：发布后的修改不会同步回本地，最终本地只剩初稿或孤立的片段。
2. **图片引用断裂**：生成的文章中图片可能是临时 URL、外链或者云端生成后就被清理，离线无法查看。
3. **元数据散落**：发布时间、各平台链接、slug、标签等信息全靠记忆或零散记录，难以回溯。
4. **无法批量操作**：想对所有历史文章做一次 RAG 索引或者风格分析，缺少统一的入口。

## 做法：归档流水线设计

我们可以在现有发帖 Agent 的末端挂载一个「归档步骤」，将发布结束后的内容写入本地仓库。整体结构如下：

```
Auto Post Pipeline
├── ContentWriter (写文章)
├── ImageGenerator (生成配图/封面)
├── PlatformPublishers (多平台发布)
└── Archiver (本地归档)  ← 新增
```

Archiver 不参与发布成败判断，只在发布完成后被调用，属于旁路流程，不影响主链路稳定性。

### 1. 目录结构与资产约定

采用每个帖子一个目录的方式，目录名用 `{YYYYMMDD}-{slug}`：

```
posts/
  20250101-hello-world/
    index.md
    images/
      cover.png
      figure-1.png
    assets.json
```

- `index.md`：完整的文章内容，所有图片引用使用相对路径 `images/...`。
- `images/`：存放该文章相关的所有本地化图片。
- `assets.json`：记录该帖的结构化元数据。

### 2. assets.json 设计

```json
{
  "slug": "hello-world",
  "title": "Hello World",
  "created_at": "2025-01-01T10:00:00Z",
  "platforms": {
    "wechat": "https://mp.weixin.qq.com/s/xxxx",
    "juejin": "https://juejin.cn/post/xxxx"
  },
  "tags": ["automation", "openclaw"],
  "images": [
    "cover.png",
    "figure-1.png"
  ]
}
```

这份文件既可以被人类阅读，也可以被脚本解析。后续做索引，只需扫描所有 `assets.json`。

### 3. 归档步骤的实现

在 OpenClaw 里，最常见的做法是用 MCP server 暴露一个 `archive_post` 工具。这个工具接收发布后的结构化对象：

- `markdown_content`: 文章正文
- `image_map`: {"原图URL": "本地目标文件名"}
- `platform_links`: {平台名: URL}
- `metadata`: slug、标题、日期、标签等

工具内部执行逻辑：

1. 根据 slug 和日期拼接目录，若目录已存在则幂等退出或按策略覆盖。
2. 把 `markdown_content` 中所有图片 URL 替换为 `images/xxx`，写入 `index.md`。
3. 下载图片到 `images/` 目录（支持并发下载并重试）。
4. 组装 `assets.json` 并写入。

Agent 只需在发布成功后，把各平台返回的链接和原始 markdown 一起传入 `archive_post` 即可。整个归档过程对 Agent 透明。

如果你没有 MCP server，也可以直接用 Node.js 脚本 hook 在流水线末端，原理一致。

## 踩坑与工程细节

实践中，这个看似简单的归档器踩过不少坑：

**图片引用替换不彻底**  
markdown 中的图片除了 `![](url)`，还有可能是 HTML `<img>` 标签、短代码等。替换时只处理 Markdown 标准语法会遗漏。需要额外支持常见变体，或者在生成文章时就约束只使用纯 Markdown 图片语法。

**下载图片的文件名冲突**  
如果多个图片原始文件名相同，直接保留原名会覆盖。建议使用 `cover.png` 这种固定角色名加序号 `figure-1.png`，在归档时通过参数指定，而非依赖 URL 中的文件名。

**幂等与增量归档**  
流水线可能因为发帖失败而重试，也可能手动补归档。如果直接覆盖，会丢掉手动修正的内容。一个安全的策略是：如果目录已存在，只补充缺少的图片，不覆盖 `index.md` 和 `assets.json`，或者使用 Git 版本管理来处理冲突。

**大文件与存储成本**  
封面图一般可控，但如果文章内嵌了动图或高清图片，本地归档体积会快速膨胀。可以设定尺寸阈值，超过限制的图片降采样或只存缩略图，原始大图保留云端引用。

**assets.json 并发写入**  
如果你的发帖流水线是并发执行的，可能会同时操作同一个文件。通过使用以 slug 为维度的独立目录，配合文件原子写入（先写临时文件再 rename），基本可以避免竞态。

## 可复用建议

把归档逻辑抽离成一个可配置的通用模块，适合长期维护：

- **配置化路径**：支持通过环境变量设置归档根目录 `ARCHIVE_ROOT`。
- **插件化图片下载器**：可切换本地下载、COS 上传并记录 URL 等策略。
- **兼容多平台返回格式**：平台返回的链接结构不同，做一个 adapter 层统一成 `platform_links` 对象。
- **以 Git 驱动版本**：如果归档目录是 Git 仓库，可以在每次归档后自动 commit，记录变更历史，这样即使误操作也能回溯。

在 OpenClaw 中，可以将这个模块封装成一个 Skill 或 MCP Tool Set，供任何一个内容自动化 Agent 调用。多个 agent 共享同一套归档规范，整个知识库就会逐渐积累成可控的资产。

## 总结

自动发帖流水线追求效率的同时，也需要本地归档这条“护城河”。通过文章 Markdown、图片与 `assets.json` 的结构化存储，你可以得到一份完全属于自己、可离线检索、可版本管理的全量内容库。它不增加发布延迟，也不影响发布成功率，却在长期运营中扮演了数据底座的色。在工程上做到幂等、路径可控、图片管理稳健，这套机制就可以成为你所有内容工作流的标配。

下一步可以考虑基于这些本地归档做更多事情：自动生成全文 RSS、构建个人内容搜索、甚至用历史数据微调你的写作 Agent。土地整理好了，种什么都会更容易。
