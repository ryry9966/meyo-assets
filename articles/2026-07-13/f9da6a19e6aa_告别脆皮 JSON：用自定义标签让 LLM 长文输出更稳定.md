在 OpenClaw、MCP 或 Agent 管线里串联多个 LLM 调用时，我们经常要求模型输出一段结构化的长文本，比如会议纪要、分析报告、多段翻译、甚至是带有嵌套段落的配置描述。最直觉的做法是让它返回 JSON，但实际跑起来就发现，JSON 在长文场景下的稳定性比想象中差得多。

这篇文章是我在给 OpenClaw 管线增加“多步骤总结生成”节点时踩过的坑，以及最终切换到自定义标签格式后获得高稳定性的工程实践。

---

## 1. 问题场景

典型需求：让 LLM 阅读一篇长文档，输出包含标题、摘要、正文段落、要点列表的总结结果，后续由下游的 Markdown 渲染器或结构化存储服务消费。

最初的设计：Prompt 里要求模型输出严格的 JSON 格式，字段包括 `title`、`summary`、`body`（一个段落列表，每个段落又有多个句子）。

期望结果：

```json
{
  "title": "...",
  "summary": "...",
  "body": [
    {
      "heading": "背景",
      "content": [
        "句子1", "句子2"
      ]
    }
  ]
}
```

实际产出的问题：

- **末尾缺失闭合括号**：长 JSON 输出时，有时 `]` 或 `}` 在最后几行被截断（尤其是 token 限制或 streaming 延迟关闭）。
- **字符串内部未转义引号**：当段落内容包含英文双引号时，模型偶尔会输出未经转义的内容，导致 JSON 解析失败。即便明确提示“请转义”，长文本中依然偶尔遗漏。
- **嵌套层级错误**：数组与对象的边界搞混，比如 `"content": { ... }` 或数组缺失逗号。
- **修复成本高**：简单的 `json.loads` 无法使用，需要编写复杂的正则修复函数，且面对不确定的缺失部分，修复成功率不高。

这在 Agent 链路中是致命的：一个节点的输出无法被下一个节点正确解析，整个自动化管道就会卡住，需要人工重新触发。

---

## 2. 从 JSON 转向自定义标签格式的想法

既然不是所有结构化输出都必须要用 JSON，而我们下游任务实际上只是需要 **分段标记明确的文本**，那可以设计一种更宽松的标签格式，与模型生成文本的自然倾向更贴合。

核心思路：用明确的 XML 风格自定义标签（如 `<section>`、`<heading>`、`<point>`）来分隔内容块，同时保留纯文本为主的格式。解析器只依赖标签边界和简单的状态机，不要求完整的嵌套正确性，甚至可以做子串匹配查找。

示例格式：

```
<title>项目进展报告 Q3</title>
<summary>本报告总结了 Q3 的项目里程碑、风险和资源状况。</summary>
<section>
  <heading>里程碑完成情况</heading>
  <point>M1 按时交付，性能指标达标。</point>
  <point>M2 因第三方依赖延迟，预计推迟一周。</point>
</section>
<section>
  <heading>风险与应对</heading>
  <point>硬件供应紧张，已启用备选供应商。</point>
</section>
```

这种格式看起来不那么“标准”，但它在长文场景下有以下优势：

- **容错性强**：即便末尾缺失闭合标签，我们仍可以解析已获得的部分，或按最外层的完整标签提取数据。
- **不需要转义**：内容里可以自由使用双引号、花括号，只要不出现 `<section>` 这类预定义标签关键字即可（即使出现，也可以约定特殊编码或直接用近似词替代）。
- **易于 token 对齐**：模型生成标签时更像是自然分段，不易因跳脱括号而产生语法错误。实测使用 GPT-4、Claude 3.5 生成 2000+ 字的长输出时，标签格式的截断率远低于 JSON。

---

## 3. 在 OpenClaw 管线中的工程落地

### 3.1 解析器设计

我们编写了一个基于行的标签解析器，核心逻辑是扫描每行内容，识别 `<tag>` 和 `</tag>`，将内容映射为 Python 字典或结构体。解析器不强求整个文档完整，只提取它能识别的标签块。

几个关键点：

- 如果 `<section>` 标签缺失闭合，就假定它延伸到文档末尾。
- 没有显式 `<title>`，则取第一个 `<section>` 之前的文本作为标题降级处理。
- 对 `<point>` 列表，不要求同级统一，允许多个 `<section>` 间独立解析。

这使得即使模型输出不完美，我们仍能成功抽出至少 80% 的有效信息，对于下游展示或存储已经足够。

### 3.2 Prompt 工程化

提示词部分我们做了两点强化：

1. **明确标签边界，禁止使用未声明的 XML 标签**，告知模型“只有以下标签是合法的，其余 `<` `>` 符号请在内容中避免或替换为全角字符”。
2. **提供“失败保护”示例**，比如展示一个标签缺失闭合但仍可解析的样例，降低模型因追求完美而强行补全的心理倾向（实践表明这有助于减少截断）。

### 3.3 与 MCP 工具的配合

在我们的 MCP 服务器中，有一个工具专门用来返回这种标签格式的总结，通过 MCP 的 `Resource` 或 `Tool` 接口提供给 Agent。Agent 在调用该工具时，不需要关心 JSON 解析，只需将返回的标签文本原样传递给下游渲染。同时，渲染节点调用同一解析器，快速转换为前端需要的 JSON 数据。整体链路从脆皮 JSON 变为健壮的标签管道。

## 4. 踩坑记录

- **标签命名冲突**：如果文档原文包含类似 `<section>` 的文字，模型可能在生成内容中不小心写出来，导致解析错乱。我们的解决办法是要求模型对内容中的尖括号使用全角 `＜＞` 或 `&lt;` 实体，或者在解析时先对标签进行关键词检测和跳过逻辑。
- **嵌套标签复杂化**：避免设计过深的嵌套结构。我们最终只保持两层：`<section>` 包含 `<heading>` 和 `<point>`，没有三层以上。事实证明这已经满足绝大多数长文结构需求，且复杂度低，出错率极低。
- **模型混淆中英标签**：有时模型会输出 `<标题>` 或混合格式。通过在 Prompt 中强调“只能使用以下英文标签”并给出例子，可大幅降低此问题。

---

## 5. 可复用建议

- **优先考虑用分隔标签替代 JSON，当且仅当输出是长文本且对语法完整性要求高时**。如果只是传一两个短值，JSON 依然 OK。
- **数据结构扁平化**，少嵌套，多并列，利于容错解析。
- **在开发环境中建立测试用例集**，涵盖截断、缺失闭合、多余空格等各种异常情况，确保解析器能正常降级。
- **不要尝试构建“通用”的标签解析器**，而是为当前的输出约定写一个最小可行的解析模块，这样维护成本低，可靠性高。

---

## 6. 总结

从 JSON 转向自定义标签格式，本质上是放弃了语法层面的严格性，换取了文本生成端的稳定性和解析端的实用性。对于 OpenClaw/Agent/MCP 这类务实的自动化管线，这是一次很划算的交换。如果你的管道里还在为长文输出的 JSON 解析写一堆 try-catch 和正则修复，不妨试试这种简化的标签方式，也许会发现管道的可靠性有明显提升。
