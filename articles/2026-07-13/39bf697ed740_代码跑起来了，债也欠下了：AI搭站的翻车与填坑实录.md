Trae 最近在独立开发者圈子里火得发烫。不是因为它能写出多精妙的算法，而是让很多不懂代码的人，在 30 分钟内真的生成了一个能上线的小网站。社交媒体上一水的“我用中文描述，AI 帮我写了个导航站”，评论区则分两派：一派当场要求分享 Prompt，另一派默默截图说“你先试试上线后会不会崩”。

这不是反调，这是一种工程师的本能警惕。任何技术上新工具带来的初期效率提升，都会在长期维护中把省掉的时间加倍还回来。Reddit 上有个帖子标题很精准：“I built it in 3 hours, I fixed it for 3 weeks.” 既然大家已经在热火朝天地用 Trae（以及同类如 Bolt、Lovable、Cursor 在内的一整条 AI IDE 光谱）搭网站，不如把话说开：翻车路线图是什么？补救手段有哪些？更重要的是，从一开始埋下了哪些你日后深夜挠头的雷。

## AI 搭站为什么“快得不像真的”

AI 撸网站的“快”，主要在三个层面，叠加后形成了一种“开发民主化”的错觉。

**1. 从 Prompt 到完整文件的跳跃**
传统建站流程中，即便你写一个静态登录页，也需要在脑海里完成 HTML 语义、CSS 布局、JS 交互逻辑的翻译。Trae 这类工具直接把这个翻译链压缩成一步：“生成一个 SaaS 风格的 landing page，hero 区用左右分栏，右侧放一个带有邮箱验证的表单。” 模型输出完整 `index.html`、`style.css`，甚至往 `utils/auth.js` 里塞了基本的邮箱正则校验。

**2. 预设模板栈的即时组合**
所谓“30 分钟出站”，多数情况是 AI 调用了一个庞大的、不可见的模板组件库。导航栏、FAQ 折叠块、定价卡片，这些都不是每次重新生成的，而是从训练集中拼装出来的。这正好解释了为什么大家生成出来的页面，你总觉得在某个 Product Hunt 排队产品上见过：审美统一，但毫无品牌辨识度。

**3. 滚动 Debug 的瞬时反馈**
最大的效率红利不在生成，而在 Debug 闭环。把终端报错 Ctrl+C 贴进对话框，模型通常能 5 秒内给出修复代码。这让即便是零基础的用户，也能靠“复制粘贴 + 错误截图”这种纯本能操作，把一个千疮百孔的项目推着往前走很远。

## 翻车现场：那些上线后才炸的雷

速度快是主观体验，把东西放到生产环境之后的静默崩溃，才是客观现实。几个高频翻车场景：

- **Auth 层的 token 裸奔**：AI 生成的登录系统，有一批在 `localStorage` 里直接存 JWT，且没有设置 `httpOnly` 和 `secure flag`。这在本地 `localhost` 上一切正常，但一旦部署到 HTTPS 域名下，等于把用户会话暴露在 XSS 攻击面里。更糟的是，很多生成的 API 路由根本就没做鉴权中间件，用的是伪代码级的三元判断 `if (user) { next() }`。

- **API key 硬编码进前端 bundle**：这个雷属于经典得让人心疼。模型在调用 Supabase 或 OpenAI 接口时，习惯把初始化代码连同 `secret_key` 一并塞进 `main.js`。部署上线后，任何人都可以通过浏览器 F12 的 Sources 面板找到你的 key，然后被拿去挖矿或者消耗你的 API 配额。

- **数据库 Schema 设计缺失索引**：当你用自然语言描述“做个用户目录，包含头像、昵称、简介”，AI 建出的表通常是 `CREATE TABLE users (id, name, bio, avatar_url)`，没有主键以外的任何索引，也没有做字段长度约束。这在你导入 50 条测试数据时飞快，在 5000 条时开始有明显卡顿，在 5 万条时查询超时——因为每搜一个用户都在做全表扫描。

- **前端包体积失控**：为了满足“做出来要好看”的 Prompt，模型经常把整个 Tailwind CDN 甚至 Lodash 全集引进去，却只为了用一个 `_.capitalize`。当 Lighthouse 给出 Performance 分数 23 的时候，你才开始手工拆包——注意，这时你没有写过一两行这个页面的代码，拆包的痛苦全部由你来承担。

## 补救工具箱：你能修什么，以及怎么修

假设你已经把网站部署上线，并且开始收到用户反馈，以下是分优先级的补救路线。

**级别一：安全问题，立刻修**
1. 全局搜索代码库中的 `api_key`、`secret`、`password` 字符串，全部迁移到 `.env` 文件中，并在 `.gitignore` 里忽略该文件。CI/CD 管道上通过环境变量注入。
2. 检查所有 API route handler，确保每个请求都经过鉴权中间件。如果是 Next.js，直接在 `middleware.ts` 中统一处理；如果是 Express，写一个 `auth middleware` 挂载到需要保护的路由上。
3. 打开浏览器的 Application 面板，确认没有任何 token 暴露在 `localStorage` 或 `sessionStorage` 中。JWT 应只存在于 `httpOnly cookie` 内。

**级别二：性能问题，做最小侵入式优化**
1. 用 `lighthouse` 或 `PageSpeed Insights` 跑一遍，找出阻塞渲染的资源。通常 AI 生成的页面引用了过多的外部字体和 icons 库，可以把它们合并、压缩或延迟加载。
2. 检查数据库的 `WHERE`、`JOIN`、`ORDER BY` 字段是否建立了索引。在 Supabase / PlanetScale 等控制台可直接查看慢查询日志，根据查询频率最高的前 3 个 SQL 加索引。
3. 对于纯展示型网站，把首页 HTML 做一次静态生成（SSG），配一条 CDN 规则缓存 24 小时。这能瞬间把首次内容绘制速度拉到一个可以跟人解释的水平。

**级别三：可维护性，建立最低限度的结构**
1. 把 AI 一次性吐出的 800 行单文件组件拆分成合理的模块（至少 page / component / util 三层）。
2. 把散落在各处的 magic string 提炼成常量文件。
3. 给项目写一个 `README.md`，哪怕只解释三件事：这个站干嘛的、怎么本地跑、部署在哪里。

## 埋雷清单：你未来 6 个月会感谢现在看到这张表

有些东西现在不修，系统也不会立刻崩溃。但产品一旦有起色，它们就是最大的技术债务。

- **环境配置混乱**：本地 dev / staging / production 的数据库连接串混用，某天在本地删了一个字段，线上直接白屏。必须在项目早期就建立 `NODE_ENV` 分支配置。
- **没有日志系统**：AI 生成的代码里 `console.log` 满天飞，但真正的生产错误没有捕获也没有追踪。至少挂一个 Sentry 或 Logtail，否则用户反馈“点不开”时你只能干瞪眼。
- **SEO 元信息缺失**：AI 搭站通常只管视觉不管 `<head>`。`title` 是 “Untitled”，`meta description` 是空。Google 收录后，你的网站在搜索结果里会是一条没有面孔的链接。
- **依赖黑洞**：`package.json` 里躺着 47 个依赖，其中一半是 AI 为了某个功能一次性引入但实际已经没用的库。不在初期清理，半年后版本升级时你会面对依赖冲突地狱。
- **测试为零**：这几乎是所有 AI 生成项目的通病。别急着写单元测试，但至少对三条核心用户路径（注册→登录→核心功能使用）跑一遍手动 E2E 流程，把步骤写在 Notion 里，每次部署前花 5 分钟走一遍。

## 三个务实建议

1. AI 搭站是一门“速写”，不是一项“免维护”承诺。它的正确使用场景是验证想法，即在 48 小时内把一个脑内概念推到线上看用户是否点击，而不是在没有技术评审的情况下把它当做生产基座。
2. 如果你已经决定让 AI 生成的代码进入生产，请至少做一次“安全 + 性能”的二人简单 review。花 200 块钱找一个懂服务端的开发过来看 2 小时，可能省下未来 20 小时的救火。
3. 在第一次部署上线前，手工操作一遍从代码仓库 clone、安装依赖、build、启动的全流程。AI 生成的代码最容易在这个环节暴露隐藏的环境依赖。如果你自己都跑不起来，运维就变成一种永无止境的黑箱博弈。

工具的锋利与危险从来是一体两面。Trae 把建站这件事的效率推到了极致，但也把排查问题的门槛拉到了同一个高度——毕竟，看别人写的代码都费劲，看 AI 写的更是如此。
