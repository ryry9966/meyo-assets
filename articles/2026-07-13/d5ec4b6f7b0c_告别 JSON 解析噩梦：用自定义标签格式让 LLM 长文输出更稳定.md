## 背景

在 OpenClaw、MCP 插件、Agent 编排等自动化流程中，我们经常需要让大语言模型输出结构化数据，以便下游节点解析执行。比如让 LLM 分析一篇长文档后返回摘要、关键词和行动项，或者生成多步任务计划。很长一段时间里，JSON 是这类需求的首选格式——它可读性好，生态工具齐全，几乎所有编程语言都能一键解析。

问题在长文输出场景下开始集中爆发。一旦模型生成的文本变长、嵌套层级增加，或者内容中出现特殊字符（引号、换行、代码块、Markdown 模板），JSON 的严格语法就成了阿喀琉斯之踵。即便在 prompt 中反复强调“输出合法 JSON”，解析阶段依然频繁遇到：

- 尾部多了一个逗号；
- 字符串内未转义的双引号；
- 模型在 JSON 外“热心”地加了 Markdown 代码围栏；
- 字段值里混入了未转义的控制字符。

在自动化链路里，一次 JSON.parse 异常就可能让整个流水线卡住，而靠重试又浪费 token 和时间。在面对复杂长文结构时，我开始尝试切换到**基于标签（Tag）的标记格式**，用类似 XML 的自定义标签包裹输出内容，再用简单的文本提取代替严格的 JSON 解析，稳定性明显提升。这篇文章将还原从“坏 JSON”到标签格式的完整实践，希望对同样在 Agent 工程中折腾结构化输出的同行有帮助。

## 问题拆解：为什么长文 JSON 极易失败？

根本原因有两点：

1. **模型是生成式的，不是编译器**。它对语法的自我约束力随序列长度衰减。尤其在生成数百行嵌套内容时，注意力分散，很容易在某个角落埋下语法地雷。
2. **JSON 对字符转义的零容忍**。`"`、`\`、换行符等在结构化数据中是合法的，但必须被正确转义。LLM 在开放文本中自然输出的引号往往直接嵌入字符串值，破坏整体结构。

即便使用支持 JSON Mode 的 API，也未必能完全避免。因为一旦 prompt 要求输出非常规 schema（如包含多段自由文本），模型仍可能在 JSON 内部写出未经转义的内容。更不用说很多自动化场景需要混合自然语言和结构化数据一起返回，纯粹 JSON 在这种“半结构化”要求前显得力不从心。

## 做法：从 JSON 切换到标签格式

核心思路很简单：放弃让模型输出完美的 JSON，转而定义一套**仅需“开始-结束”配对标签**的约定。下游用轻量级标签提取器拿到各部分内容，最坏情况下也只是丢失部分数据，不会让整个管线崩溃。

### 1. 设计标签结构

以一个“文档分析 + 行动计划”输出为例，我定义了如下格式：

```
<analysis>
……自由分析文本，可以包含引号、换行无限制……
</analysis>
<keywords>关键词1, 关键词2, 关键词3</keywords>
<action_plan>
- 步骤一
- 步骤二
</action_plan>
```

三个标签分别对应三个输出模块。标签名采用下划线分隔的小写英文，避免与 Markdown 语法冲突。**关键点是标签内的内容不再做任何转义要求**，模型可以“随心所欲”地写。

在 prompt 中，我这样描述输出规则：

```
你必须严格按照以下标签格式输出，不要添加解释，不要使用 Markdown 代码围栏：
<analysis>你的分析内容</analysis>
<keywords>逗号分隔的关键词</keywords>
<action_plan>行动计划 Markdown 列表</action_plan>
```

### 2. 解析器实现

用简单的状态机或正则提取。以 Python 为例：

```python
import re

def extract_tagged_content(text, tag):
    pattern = rf'<{tag}>(.*?)</{tag}>'
    match = re.search(pattern, text, re.DOTALL)
    return match.group(1).strip() if match else None
```

如果需要处理嵌套标签（极少出现），可以改用栈式解析，但通常不建议模型输出嵌套标签，保持一层平级即可。解析失败时，我可以根据返回 `None` 做降级处理，比如仅提取已知有把握的部分，而不是整个输出作废。

在实际 Agent 工作流中，我还封装了一个 `TaggedResponse` 类，自动提取多标签内容，并做基本的类型校验。配合 MCP 工具，可以将这个解析器作为一个 standard 工具供不同 skill 调用。

### 3. 在 OpenClaw 中集成

如果使用 OpenClaw 的编排器，可以在 LLM 节点后串联一个“标签解析”节点，利用自定义工具调用上述解析逻辑。例如，让 OpenClaw 的一次对话回复经过解析节点，将 `<analysis>` 内容送入下一个总结节点，将 `<action_plan>` 内容直接提交给 GitHub issue 创建工具。整个流程对模型长文输出不再有脆弱的单点解析依赖。

## 踩坑点：标签格式并非银弹

在实践中也遇到几个典型问题：

1. **模型忘记闭合标签**  
   长输出时，模型偶尔会漏掉结束标签，或者误写成 `<analysis>...</analys>`。解决方式是：在 prompt 中明确要求“在输出结束前检查所有标签是否闭合”，同时解析层对缺失闭合标签做容错（比如取到文末，或下一个标签开始处作为结束）。

2. **内容中混入与标签相同的关键词**  
   例如分析文本里自然出现了 `<analysis>` 这个字符串。可选方案：
   - 使用更独特的标签名，如 `<oa_analysis>` 降低概率。
   - 要求模型如果必须在内容中出现标签名，采用 HTML 实体编码（如 `&lt;analysis&gt;`），不过会引入新的约束，与“自由文本”初衷偏离。经过权衡，我选择**不处理这种极低概率事件**，在提示中加一句“内容中避免出现与标签完全相同的字符串”基本能规避 99% 的情况。

3. **多标签序列不保序**  
   模型可能出现 `B` 标签内容穿插在 `A` 标签之前，但这种情况发生概率极低，暂时忽略不计。如果严格要求顺序，可以多次调用、逐段生成。

## 可复用建议

- **首选严格 JSON 的场景**：短小、高度约束的数据结构（如纯数字、枚举值）。此时 JSON Mode 稳定，且下游做 schema 校验方便。
- **首选标签格式的场景**：输出包含长文本、自然语言段落、代码片段、Markdown 内容，或嵌套深度大但不需要复杂解析层级时。标签格式本质是把解析容错权掌握在自己手里。
- **混合使用**：输出最外层用标签结构，内部某个标签内容再独立用 JSON（确保是短小片段）。例如 `<metadata>{"id": 123, "type":"report"}</metadata>`，这部分 JSON 可单独抽取且出错面小。
- **解析层做降级**：永远不要让一次格式错误终止整个工作流。解析失败时，可以让 Agent 自我修复提示（如“请按格式重新输出，注意闭合标签”），或回退到纯文本提取。
- **建立 MCP 工具**：将标签提取器封装成 MCP 工具，方便多个 OpenClaw 技能复用，减少重复实现。

## 总结

从强迫 LLM 输出完美 JSON，到接受“标签格式”这种容错性更强的约定，本质上是工程化思维的一次切换——不再期待模型做编译器，而是设计一套能与模型生成特性共存的输出协议。标签格式在长文输出的稳定性、下游解析的健壮性上带来了明显改善，尤其适合在 Agent 自动化链路中充当“胶水”。如果你也正在被 bad JSON 拖慢自动化流程，不妨在下一个长文结构节点中尝试这种轻量的标记方案。
