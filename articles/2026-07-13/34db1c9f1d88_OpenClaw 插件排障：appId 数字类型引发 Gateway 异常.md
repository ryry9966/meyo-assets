## 背景

在 OpenClaw 生态里，插件是衔接 Agent 与外部服务的关键组件。我们团队最近在为一个内部 MCP 网关编写 OpenClaw 插件时，遇到一个看似微不足道、却足以让整个调用链路瘫痪的问题：插件配置中的 `appId` 使用了数字类型，导致 Gateway 拒绝请求。最终定位到是序列化类型不匹配 —— 这恰恰是很多插件开发者容易忽略的细节。

## 问题复现

插件的核心功能很简单：调用公司内部网关的一个 REST 接口，进行应用级别的元数据查询。插件配置长这样（已脱敏）：

```yaml
gateway:
  baseUrl: https://gateway.internal.example.com
  appId: 800123
  secret: ${GATEWAY_SECRET}
```

插件启动、注册正常，OpenClaw 的 Agent 也能正常触发对应的工具调用。但每次实际请求 Gateway 时，都会直接返回 `HTTP 400 Bad Request`，响应体里只有一个含糊的 `{"error":"invalid_request"}`，没有任何字段级别的提示。Gateway 的日志只记录了一句签名校验失败，未暴露具体参数差异。

最开始怀疑是签名算法实现问题，检查了时间戳、nonce、签名拼接顺序，甚至还重新生成了密钥，问题依旧。又检查了网络、代理、TLS 证书，全部正常。直到在代理层抓了请求体，才发现端倪：

```json
{
  "appId": 800123,
  "timestamp": 1720012345,
  "nonce": "abc123",
  "signature": "xxx"
}
```

而 Gateway 接口文档定义的 `appId` 字段类型是 `string`，预期是 `"800123"`。这里序列化得到的是数字，Gateway 在做签名校验前，会对请求体进行严格的类型反序列化，一旦类型不匹配，直接认定为非法请求，返回 400。

## 做法与排查步骤

以下是完整的排障路径，保留了工程现场的原始记录，供读者参考：

1. **检查插件运行日志**  
   确认 OpenClaw 加载插件、生成工具调用没有报配置解析错误，记录实际的请求 URL、Header 和 Body（若日志脱敏，可以临时调高日志级别）。

2. **截获实际请求**  
   在插件侧增加一个调试代理（或使用 mitmproxy, Wireshark 抓包），完整捕获请求体。这里我们推荐在开发环境使用 `http.Transport` 的 `DumpRequest` 方法，避免依赖外部工具。

3. **比对接入文档**  
   逐字段检查请求体的类型与接口规范。Gateway 接口如果使用 JSON Schema 或强类型定义（如 OpenAPI），字段类型不符会直接导致 400/422。

4. **修正配置中的类型**  
   将 `appId: 800123` 改为 `appId: "800123"`，即在 YAML 中显式使用引号标记字符串。同时检查其他数值型标识符，如 `tenantId`、`clusterId` 等，确保它们一致。

5. **回归测试**  
   重新触发工具调用，确认 Gateway 返回正常，并再次抓包验证 `appId` 已变为字符串 `"800123"`。

## 踩坑点

- **YAML 隐式类型推断**  
  YAML 解析器会将纯数字的值自动解释为整数，只有当值被引号包裹时才会作为字符串。很多开发者在配置文件中写 `appId: 800123` 时，并不觉得这跟 `"800123"` 有区别，直到看到序列化结果才恍然大悟。

- **Gateway 的错误信息弱化**  
  本案例中 Gateway 只返回 `invalid_request`，没有明确指出字段类型错误，导致排查方向一度跑偏。这种“静默失败”在生产环境里非常致命。

- **日志脱敏掩盖问题**  
  如果插件运行日志对请求体做了 MD5/部分遮蔽，可能无法直接看到 `appId` 的实际类型，无形中增加了排查难度。建议在调试时临时输出完整的请求体，并确保敏感字段单独处理。

## 可复用建议

1. **ID 类字段永远使用字符串类型**  
   无论来源是配置文件、环境变量还是数据库，凡是作为标识符（appId、userId、sessionId 等）的字段，在应用层统一以字符串形式传递。数字型标识符一旦跨越系统边界，极易遭遇类型强制转换或精度丢失。

2. **在插件侧增加请求体类型断言**  
   可以在插件初始化时，用 JSON Schema 或简单的类型校验，确保序列化后的请求体完全符合接口文档。例如，校验 `typeof body.appId === 'string'`，尽早暴露配置错误。

3. **利用 OpenClaw 的插件配置验证能力**  
   如果 OpenClaw 插件框架支持 JSON Schema 或 TypeScript 类型定义，请明确声明 `appId` 为 `string`，这样在加载配置时就能捕获类型错误，将排查时机提前到启动阶段。

4. **建立接口契约回归用例**  
   将抓包得到的请求体样本保存为测试 fixture，在 CI 中自动对比 Gateway 的 OpenAPI 规范，确保每次变更都不会引入类型不匹配。

5. **合理的日志策略**  
   在调试模式下输出完整请求体，线上模式脱敏但保留字段结构，这样可以利用结构对比快速定位类型问题。

## 总结

这起由 `appId` 的数字类型引发的 Gateway 异常，本质上是一个配置序列化与接口契约不一致的问题。它的隐蔽性在于：配置文件看起来正确，插件启动无报错，错误只在真实调用时暴露，且网关反馈信息模糊。对插件开发者而言，这提醒我们要对“类型”保持高度敏感——尤其是在与外部系统交互时，数字与字符串的差异不应被轻视。将标识符严格约束为字符串，并在工程链路中植入校验点，是避免这类静默失败最直接、有效的手段。
