# 给自动化脚本加本地目录白名单：Agent 文件访问护栏落地指南

## 背景
基于 Agent 的自动化流程常需要接触本地文件系统——读写临时文件、下载产物、执行本地脚本。无论你用 OpenClaw 构建工作流，还是通过 MCP server 给大模型暴露文件工具，稍有不慎就会让一个“智能体”获得 `rm -rf /` 的等效能力。如果只用环境变量或 `allowed_paths` 配置来“信任”工具实现，几乎等于裸奔。真正需要的是一个**目录白名单护栏**：Agent 只能操作预先定义的安全目录，任何超出范围的读写都被拦截。

## 问题拆解
一个看似简单的文件操作，可能从多个层面逃逸：
- 相对路径被 Agent 的工作目录放大（`../../.ssh/id_rsa`）
- 符号链接指向白名单外的真实路径
- 命令行工具注入 `$()` 或反引号绕过路径检查
- 创建文件时路径还不存在，但父目录是敏感目录

因此，护栏必须做到：**解析到真实绝对路径、拒绝跨白名单操作、覆盖读写删除及命令执行场景**。

## 落地做法

### 1. 定义白名单并实现路径检查函数
以 Python 为例，对 Agent 调用的文件工具进行统一入口校验：

```python
from pathlib import Path
import os
from typing import List

class FileGuard:
    def __init__(self, allowed_dirs: List[str]):
        # 预先解析为真实绝对路径
        self.allowed = [Path(d).resolve() for d in allowed_dirs]

    def check(self, path_str: str, operation: str = "access"):
        target = Path(path_str).resolve()

        # 对于写操作，如果文件不存在，则需要父目录在白名单内
        if not target.exists() and operation in ("write", "create"):
            parent = target.parent
            if not any(self._is_inside(parent, d) for d in self.allowed):
                raise PermissionError(f"Access denied: {target} is outside allowed dirs")
        elif not any(self._is_inside(target, d) for d in self.allowed):
            raise PermissionError(f"Access denied: {target} is outside allowed dirs")

    def _is_inside(self, target: Path, allowed: Path) -> bool:
        # Python 3.9+ 可直接用 target.is_relative_to(allowed)，此处兼容旧版
        try:
            target.relative_to(allowed)
            return True
        except ValueError:
            return False
```

要点：
- **始终 `resolve()`**：消除符号链接、`.` 与 `..`。
- **白名单本身也 resolve**：存放路径时去掉可能的链接干扰。
- **覆盖「创建新文件」的情况**：文件尚不存在则需要校验其父目录。
- **区分操作类型**：读、写、删除、执行都需要套用检查。

### 2. 集成到 Agent 的工具入口
假设你的 Agent 工具是函数装饰器，可以随手加一个 `@file_guard(allowed_dirs)`：

```python
def file_tool(func):
    def wrapper(*args, **kwargs):
        path = kwargs.get("path") or args[0]
        guard.check(path, operation=func.__name__)
        return func(*args, **kwargs)
    return wrapper
```

对于允许 Agent 执行的 Shell 命令，除了路径白名单，还需要收紧命令本身。**推荐直接用受限的 subprocess 执行，不用 `shell=True`**，并限定可执行二进制路径（如 `/usr/bin/cat`），将路径参数显式传入而非构建命令字符串。

如果确实必须通过 shell，则需要对命令字符串做额外清洗，但那是另一个复杂度的话题，核心思路：**将文件操作从 shell 中剥离，单独使用文件工具，而不是给 Agent 任意 shell 权限**。

### 3. MCP 场景的实现
如果你使用 MCP Server 暴露文件系统能力，可以在 server 端对所有 `read_file`、`write_file`、`list_directory` 等 handler 应用相同的 `FileGuard` 检查。这样即使模型“意图”越权，server 也会直接返回权限错误，既不伤害系统，也能让 Agent 从错误中学习。

## 踩坑记录

- **符号链接逃逸**  
  曾经只做了 `os.path.abspath` 但未用 `resolve()`，攻击者在允许目录内创建一个指向 `/etc/passwd` 的软链接，轻松越权。`realpath`/`resolve()` 是必需品。
- **Windows 路径分隔符和大小写**  
  `resolve()` 在 Windows 上会转为大写形式且带 `\\?\` 前缀，需要确保白名单也使用相同规范化方式。使用 `Path` 比较时通常能处理，但要注意跨平台匹配。
- **`Path.is_relative_to` 的陷阱**  
  在 Python 3.9 之前没有这个方法，自己实现时注意 `relative_to` 抛出的 `ValueError` 判断。另外确保白名单目录不以 `/` 结尾造成误判。
- **权限继承到子进程**  
  如果你调用了外部脚本，这个脚本不受 Python 的护栏限制。所以，**不要将 Agent 运行在能 sudo 的环境里**，或者完全禁用 shell 命令，改用嵌入式 DSL。
- **临时文件目录模糊**  
  如果 Agent 需要写临时文件，要明确给一个白名单内的临时目录，而不是 `/tmp` 下的任意位置。

## 可复用的工程建议
1. **封装成独立模块**：在项目里提供一个 `file_guard` 包，配置化白名单路径，支持 yaml/env 注入。
2. **审计日志**：对每次被拒绝的访问记录完整信息（时间、目标路径、操作、调用栈），便于排障和安全审计。
3. **与权限体系结合**：OpenClaw 插件或 MCP server 往往有 capability 声明，可以在声明中标记“需要文件访问”，并关联白名单策略。
4. **测试用例**：用 `pytest` 编写越权用例（包含 `..`、符号链接、绝对路径等），确保每一次重构不会打破护栏。
5. **兜底策略**：除了白名单，设置「禁止访问的路径黑名单」作为辅助（如 `/etc`, `~/.ssh`），双重保险。

## 总结
Agent 的文件访问护栏不是什么高深的安全魔法，而是需要在工程早期就植入的、几行代码就能完成的路径白名单检查。它解决的不是概率性 bug，而是确定性的越权风险。花一个小时把 `resolve() + 白名单前缀匹配` 写成通用模块，集成到每个文件工具入口，远比事后清理被误删的生产文件划算。当下个 Agent 说“让我帮你整理一下文件”时，你至少知道它只会在你指定的沙箱里折腾。
