## 背景

在 Agent 或自动化脚本中集成本地文件操作（日志落盘、缓存读写、导出报表、处理用户上传）是常见需求。一旦 Agent 获得了文件系统访问能力，潜在风险就随之而来：恶意 prompt 可能诱导 Agent 读取 `~/.ssh/id_rsa`，错误的路径拼接可能覆盖系统配置，不设限的写操作可能导致磁盘写满或敏感信息泄漏。

传统的“信任开发者”模型在 Agent 场景下不再足够——Agent 的指令来源多样，即使你写了一个可靠的 MCP 工具接口，下游 LLM 也可能生成包含路径穿越参数的调用。真正需要的，是一层细粒度的工程护栏：**限定脚本或工具函数只能读写预先指定的本地目录**，其他路径一律拒绝。

本文面向在 OpenClaw / MCP / 插件生态中构建自动化流程的工程师，给出一个轻量、可审计、易于复用的实现方案，并总结踩坑点与生产级加固建议。

## 问题

- Agent 调用文件工具时，路径参数完全由 LLM 生成，难以事前穷举所有合法输入。
- 常规的路径拼接容易受 `..`、符号链接、绝对路径、空字节截断等技巧绕过。
- 简单的黑名单（如禁止 `/etc`）无法覆盖所有敏感区域，尤其在不同操作系统上。
- 需要设计一个既满足功能需求（读日志、写临时文件），又能在无感性能开销下强制实施的机制。

## 做法：一个可注入的文件访问守卫

我们选择通过 **路径规范化 + 前缀匹配白名单** 的方式，封装一个“安全文件访问层”。所有需要读写本地文件的方法，都必须通过这层校验。

### 1. 定义白名单规则

在工具初始化时，从配置文件或环境变量加载允许访问的目录列表，例如：

```python
ALLOWED_ROOTS = [
    "/data/agent-output",
    "/tmp/agent-sandbox",
]
```

设计原则：
- 每个白名单目录都是一个 `Path` 对象，解析成绝对路径。
- 区分读写权限：可以分别配置 `read_roots` 和 `write_roots`。
- 不允许将根目录 `/` 或用户主目录 `~` 作为白名单——这等同于放弃防护。

### 2. 路径校验核心逻辑

使用 `pathlib` 对用户传入的路径（可能与工作目录有关联）进行三步操作：

```python
import os
from pathlib import Path

def safe_resolve(path: str, allowed_roots: list[Path]) -> Path:
    # 拒绝空路径或包含 '\0' 的注入
    if not path or '\0' in path:
        raise ValueError("Invalid path")
    # 将相对路径基于一个固定的安全基目录解析（防止相对路径逃逸）
    base = Path("/var/empty")   # 不存在且不可写的锚点
    candidate = (base / path).resolve()
    # 检查规范化后的路径是否以任一允许根目录开头
    for root in allowed_roots:
        try:
            candidate.relative_to(root)
            return candidate
        except ValueError:
            continue
    raise PermissionError(f"Access denied: {path}")
```

关键点：
- 使用一个“无权限”的锚目录 `/var/empty`（或类似不存在的路径），让相对路径 `../../etc/passwd` 在 `resolve()` 后会保持在锚目录之下，不会上溯到真实系统根目录。最终我们只关心候选路径是否落于白名单。
- `candidate.relative_to(root)` 是 Python 3.9+ 的方法，可正确处理路径前缀，同时避免字符串前缀的欺骗（例如 `/data/output` vs `/data/output-bak`）。

### 3. 集成到 Agent 工具

以 MCP 为例，在工具处理函数入口处调用安全路径检查：

```python
async def handle_read_file(path: str) -> str:
    safe_path = safe_resolve(path, config.read_roots)
    # 后续业务逻辑中直接使用 safe_path
    return await aiofiles.open(safe_path).read()
```

在工具描述（Prompt 中的 function schema）里，可以明确告诉模型“仅 `/data/agent-output` 下的文件可读”，减少无效尝试。

### 4. 日志与告警

任何被拦截的非法访问都不应只是抛出异常，还需要记录告警日志（包含时间戳、请求的原始路径、调用栈），方便发现攻击或误用。


## 踩坑点

1. **符号链接绕过**  
   `resolve()` 只会解析符号链接本身，但如果白名单目录中存在指向外部的软链接，`candidate.relative_to(root)` 仍会接受已解析后的外部路径。需要在挂载文件系统时确保白名单目录不包含外部符号链接，或在代码中额外遍历检查每一级路径是否为符号链接，二选一。

2. **Windows 盘符与路径分隔符**  
   在 Windows 上，`resolve()` 会加上盘符，而白名单配置也需要统一使用盘符绝对路径。跨平台工程建议在配置阶段就强制规范为 `PureWindowsPath` 或 `PurePosixPath`，并与运行时对齐。

3. **并发与临时文件**  
   如果多个 Agent 共享同一白名单目录，要注意文件名冲突。实现时可以给每个任务分配一个唯一的子目录（如 `/data/agent-output/{task_id}/`），并在任务启动时动态注册该路径到白名单。

4. **相对路径锚点选择**  
   如果使用真实存在的目录作为锚点（如 `/tmp`），攻击者可能通过精心构造的相对路径访问 `/tmp` 下的敏感内容（其他进程的临时文件）。因此锚点最好是一个不存在的孤立目录，并确保不会因 `mkdir` 而被实际创建。

5. **性能误区**  
   路径校验本身开销极低（微秒级），不必担心影响吞吐。但应避免在每次文件 I/O 时重复加载配置文件，建议在白名单初始化后缓存为 `frozenset`。

## 可复用建议

- **将安全层抽成独立模块**：`sandbox.filesystem` 提供 `SafeFileReader`, `SafeFileWriter` 两个对象，内聚所有配置与校验逻辑，方便在多个工具间复用。
- **配置化白名单**：通过 YAML/JSON 文件或环境变量注入，避免硬编码，适配不同部署环境。
- **集成单元测试**：编写测试用例覆盖 `../../etc/passwd`、绝对路径 `/etc/passwd`、符号链接、空字符串、包含 `\0` 的路径等，每次修改校验逻辑后自动验证。
- **分层防护**：除了应用层校验，考虑在容器层面屏蔽敏感目录（Docker `--read-only`、`--tmpfs`、bind mount 指定子目录），纵深防御。
- **审计友好**：每次合法访问记录操作者（Agent 会话 ID）、操作类型、文件路径，发生安全事故时可回溯。

## 总结

为自动化脚本加上本地目录白名单，不是过度设计，而是在 Agent 具备文件操纵能力后的必要工程护栏。通过“路径规范化 + 前缀匹配 + 锚点隔离”的轻量方案，可以在几乎不增加复杂度的前提下，显著缩小攻击面。几个容易被忽视的细节（符号链接、Windows 盘符、锚点选择）处理妥当后，该机制即可稳定运行于生产环境。

安全是渐进式的，先限制住“可以访问哪些目录”，再逐步细化“在这些目录里可以做什么”，就能在不牺牲灵活性的同时，让自动化变得更可控。
