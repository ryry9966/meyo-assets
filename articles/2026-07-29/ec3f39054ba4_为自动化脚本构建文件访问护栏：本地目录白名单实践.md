## 背景：Agent 操作文件的隐藏风险

当下越来越多的自动化工具链——无论是基于 MCP 的工具服务器、OpenClaw 插件，还是自建的 Agent 脚本——都开始直接触碰文件系统：读写配置、生成报告、清理临时文件。即便模型指令看似严谨，真正的风险往往来自**执行层的失控**：提示注入、编码疏忽、依赖库的意外行为，都可能让脚本越权访问 `~/.ssh`、`/etc/passwd` 或项目外的数据目录。

仅仅依赖“模型不会乱来”是危险的。我们需要在工程层面建立硬性护栏，让脚本只能操作明确允许的本地目录，就像给自动化脚本套上一个安全沙箱。

## 问题：简单的路径检查为什么不够

最直觉的做法是在读写前对路径做一次前缀检查：

```python
def is_safe(base, target):
    return os.path.abspath(target).startswith(os.path.abspath(base))
```

这段代码至少有三个绕过方式：
1. **路径遍历**：`../../secrets.env` 一顿往回走就能跳出 `base`。
2. **部分匹配**：白名单是 `/var/app`，攻击者指定 `/var/app-dump/etc`，前缀匹配通过。
3. **符号链接**：在白名单目录内放置一个指向 `/etc` 的软链接，读写该链接就能操作系统文件。

因此，适合工程环境的护栏必须解决：路径解析、符号链接追踪、以及边界严格比对。

## 做法：实现一次可靠的路径白名单校验

以下以 Node.js 为例（Python 逻辑完全对应），展示一个可复用的 `resolveSafePath` 函数：

```javascript
const path = require('path');
const fs = require('fs');

function resolveSafePath(allowedBase, userPath) {
  // 1. 将 userPath 解析为绝对路径（合并白名单基路径）
  const resolved = path.resolve(allowedBase, userPath);

  // 2. 追踪符号链接得到最终真实路径
  let real;
  try {
    real = fs.realpathSync(resolved);
  } catch (err) {
    throw new Error(`Path resolution failed: ${err.message}`);
  }

  // 3. 确保真实路径以白名单开头（防止部分匹配）
  const normalizedBase = path.resolve(allowedBase) + path.sep;
  if (!real.startsWith(normalizedBase)) {
    throw new Error(`Access denied: "${userPath}" resolves outside allowed base directory`);
  }

  return real;
}
```

**关键步骤说明**：
- 使用 `path.resolve` 将相对路径转换为绝对路径，消除 `..` 的影响。
- 调用 `fs.realpathSync` 解析所有符号链接，拿到真正的文件系统位置。这是防御软链接绕过的核心。
- 检查时在白名单末尾追加 `path.sep`（在 Linux 上是 `/`，Windows 上是 `\`），避免 `/var/app` 与 `/var/app-2` 的前缀混淆。
- 如果路径不存在、无权限或解析后越界，一律抛出错误，拒绝访问。

在读写操作前统一调用该函数：

```javascript
const finalPath = resolveSafePath('/home/user/project-allowed', inputPath);
await fs.promises.writeFile(finalPath, content);
```

## 踩坑记录

### 1. 符号链接的“合法化”骗局
即使白名单内没有恶意链接，某些构建工具（如 `node_modules/.bin`）会大量使用软链接。如果忘记 `realpath`，这些链接很容易成为跳板。验证时一定要用**同步版本**，避免异步间隙被竞态条件利用。

### 2. 路径分隔符的跨平台陷阱
Windows 上运行自动化脚本需格外注意：
- 盘符 `C:` 与 `c:` 需统一大小写。
- 路径分隔符为 `\`，`startsWith` 检查时必须使用 `path.sep` 而非硬编码 `/`。
- `path.resolve` 在 Windows 下会保留当前盘符，若白名单与当前工作目录不在同一驱动器，行为可能不符合预期。建议将白名单也转化为带盘符的绝对路径。

### 3. 不存在的路径与竞态条件
当 `userPath` 指向一个**此刻还不存在**的路径时，`fs.realpathSync` 会直接报错。对于写操作，可以退而求其次：先检查待创建文件的父目录真实性，再在真实父目录下创建文件，最后再次确认实际写入路径。减少验证窗是必要的工程脏活。

### 4. 文件描述符与原子操作
如果直接使用文件描述符操作已打开的句柄，仍需在 `open` 时完成校验，不能仅做路径字符串检查。因此，封装一个安全版本的 `open` 很有价值。

## 可复用建议

- **封装为独立中间件**：将白名单验证做成 MCP 工具的前置拦截器，所有 `readFile`、`writeFile`、`deleteFile` 操作必须经过 `resolveSafePath` 检查。这样业务代码无需关心安全细节。
- **与系统权限配合**：应用层校验不能取代操作系统级别的隔离。建议以受限用户运行 Agent 进程，进一步收缩其实际可访问范围。
- **引入审计日志**：每次校验通过和拒绝都应记录时间、请求路径、解析结果。当出现异常行为时，日志能快速定位是配置错误还是攻击尝试。
- **测试用例不可省**：至少编写 5 类用例：
  - 常规白名单内路径
  - 使用 `../` 的遍历攻击
  - 符号链接指向白名单内/外
  - 部分目录名匹配（如 `app` vs `app-data`）
  - 路径不存在的写入场景

## 总结

给自动化脚本加目录白名单并不是高深的技术，但它是构建可信 Agent 的基础工程习惯。方案的核心在于：**解析真实路径 + 严格前缀判定**。配合少量同步 API 调用与跨平台边界处理，就能有效封堵绝大多数本地文件逃逸手段。在追求“自动化一切”的同时，让每一次文件访问都有据可循、有界可控，才是工程实践该有的安全意识。
