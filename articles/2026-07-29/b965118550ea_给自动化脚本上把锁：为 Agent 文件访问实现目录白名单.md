## 问题：你的 Agent 到底能碰哪些文件？

OpenClaw、MCP 等 Agent 框架让自然语言驱动本地操作变得异常简单，但也带来了一个几乎被所有人低估的安全隐患——**文件访问不受控**。

典型场景：你让 Agent “帮我整理桌面上的截图”，它确实处理了 PNG/JPG，但同时也有能力读取 `~/.ssh/id_rsa` 或者覆盖掉 `.zshrc`。当前很多自动化脚本和插件直接调用 `open()`、`shutil.move()` 或者 `subprocess`，没有任何路径约束。只要 Agent 能执行，它就能操作用户有权限看到的任何路径。

这并不是耸人听闻，而是一个确定性存在的攻击面：**攻击者只要能让 Agent 产生恶意或者错误的指令意图，就能实现文件窃取或破坏**。即使完全离线使用，一个 prompt 拼写错误也可能导致文件被移到意外位置。

所以我们需要一种轻量、可落地、不依赖厚重沙箱方案的工程化方案——**文件访问目录白名单**。

## 核心思路：拦截所有本地文件操作入口

最简单暴力的做法是：在 Agent 启动的实际文件工具中，硬编码一个白名单，拒绝一切不在名单内的路径。例如，允许列表是：

```
/data/projects/agent-workspace
/tmp/agent_sandbox
```

任何试图访问 `/etc/passwd` 或 `~/Documents` 的操作都被被提前拒止。

在 OpenClaw 的插件 / MCP server 中，你需要改造那些向模型暴露的“文件工具”。假设你有一个 `write_file` 函数，原来的实现可能是：

```python
def write_file(path: str, content: str):
    with open(path, 'w') as f:
        f.write(content)
```

改造后，加入白名单校验：

```python
import os
from pathlib import Path

ALLOWED_ROOTS = [
    Path("/data/projects/agent-workspace").resolve(),
    Path("/tmp/agent_sandbox").resolve(),
]

def is_safe_path(path: str) -> bool:
    p = Path(path).resolve(strict=False)
    return any(p.is_relative_to(root) for root in ALLOWED_ROOTS)

def write_file(path: str, content: str):
    if not is_safe_path(path):
        raise PermissionError(f"Access to {path} is forbidden by whitelist")
    # 原写入逻辑...
```

这里有几个关键点：

1. **统一用 `Path.resolve()` 处理所有路径**，消除符号链接、`..`、相对路径等绕过方式。
2. **使用 `strict=False`** 避免因路径不存在而抛异常，先校验再操作。
3. **`is_relative_to`** （Python 3.9+）能精准判断一个路径是否落在允许的目录树内，连根目录路径都能正确匹配。

同样的逻辑，你需要在 `read_file`、`list_directory`、`run_command` 等每一个可操作文件系统的工具上挂载这个校验。

## 工程化落地：装饰器 + 配置中心

实际项目里，白名单不应该写死在代码中，而应从配置文件读取：

```yaml
# agent_config.yaml
security:
  allowed_roots:
    - /data/projects/agent-workspace
    - /tmp/agent_sandbox
```

然后编写一个可复用的装饰器：

```python
def require_path_whitelist(path_arg: str):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            target = kwargs.get(path_arg) or (args[0] if args else None)
            if not target or not is_safe_path(target):
                raise PermissionError(...)
            return func(*args, **kwargs)
        return wrapper
    return decorator
```

业务工具直接用：

```python
@require_path_whitelist('path')
def delete_file(path: str):
    os.remove(path)
```

当 Agent 通过 function calling / tool use 触发这些工具时，白名单校验无感插入，不依赖模型本身的“道德判断”。

## 踩坑记录

### 1. 符号链接的“隐身衣”

即使你做了 `resolve()`，也要注意：**创建符号链接的操作本身是否需要白名单？** 如果你允许 Agent 在允许目录内执行任意命令，它完全可以通过 `ln -s /etc/shadow ./link` 把敏感文件暴露出来，然后通过白名单内的读接口访问。

解决方案：禁止 Agent 任意创建符号链接，或者在读文件的校验环节对符号链接目标做二次判断。更彻底的方式是直接禁止工具调用 `ln`，或者使用 `openat2` 的 `RESOLVE_NO_SYMLINKS` flags（Linux 5.6+），但这对 Python 封装较麻烦，工程上可以直接回到进程能力限制。

### 2. 临时文件与跨工具污染

你的 Agent 可能会调用系统命令，例如 `ffmpeg` 生成缩略图，而 `ffmpeg` 的临时输出可能落在 `/tmp` 下。如果你把整个 `/tmp` 加入白名单，实际上又放开了全局临时目录，可能与其他用户服务产生冲突。建议在白名单内固定一个专用子目录，例如 `/tmp/agent_sandbox`，并让所有子进程在那个目录下工作（通过 `cwd` 或环境变量 `TMPDIR`）。

### 3. Windows 路径与权限

在 Windows 上，`is_relative_to` 对盘符的处理必须小心。同一个盘下，`C:\aaa` 和 `C:\bbb` 是独立的，但 `resolve()` 可能无法处理跨盘符的访问（Windows 不允许）。**统一使用 Path.resolve() 在 Windows 上对相对路径有效，但要注意网络路径、设备路径**。如果你必须跨平台，可以考虑在路径处理前转换成绝对路径，再做前缀比较。

## 复用建议

- **明确定义 Agent 的工作区**：让白名单目录成为 Agent 唯一合法的读写范围，其他一切目录拒绝访问。
- **文件访问统一走 wrapper 函数**：不要在工具里直接裸调用 `open()`，整个项目通过一个 `safe_open()` 包裹。
- **日志、告警与审计**：每次拦截操作都记录原始请求路径、调用栈、时间，便于事后排查是否存在攻击企图或 prompt 异常。
- **与已有的容器 / sandbox 方案互补**：目录白名单是应用层防线，docker / firejail 是 OS 层防线，两者不冲突，组合使用更安全。

## 总结

给自动化脚本加上目录白名单不是“将来要做”的可选项，而是在任何允许 Agent 进行文件操作的场景中就应该默认存在的防护措施。实现成本极低，只需要改造少量工具函数，收益却直接堵死了一整类“意外文件损坏”和“半恶意数据泄露”的通道。

把它当作代码质量的一部分，每一次新工具接入时，先问一句：**它的文件访问范围被限制了吗？**
