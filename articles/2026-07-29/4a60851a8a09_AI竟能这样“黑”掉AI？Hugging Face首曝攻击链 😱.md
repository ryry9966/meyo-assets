2024年底，Hugging Face的安全团队公开了一份报告，详细展示了针对AI模型托管平台的一次完整“供应链攻击”。攻击者没有直接劫持服务器，而是通过篡改模型文件，将恶意代码植入开发者常用的开源大模型里。据说，连OpenAI的CEO山姆·奥特曼在看到这份报告后，都在内部会议上按下了暂停键——不是暂停GPT-6，而是要求重新审查所有第三方模型的加载机制。

事情源自Hugging Face的安全研究项目“Red-Teaming the Hub”。研究员模拟了一个真实的攻击场景：从一个看似正常的PyTorch模型文件出发，一步步突破隔离，拿到了云环境的Shell权限。这到底是怎么回事？我们来拆解一下这个被行业称为“AI供应链投毒教科书”的案例。



## 攻击链拆解：从.pth文件到完全控制权

Hugging Face公开的攻击过程分为4个阶段，每个阶段都利用了AI生态中容易被忽视的基础组件。

1. **投毒点选择：PyTorch模型的序列化漏洞**
   - 攻击者创建了一个看似正常的图像分类模型，将其保存为`.pth`格式。PyTorch的`torch.save()`底层使用Python的`pickle`序列化模块，而`pickle`在反序列化时可以执行任意代码。这不是新漏洞，但在AI社区，开发者通常会直接加载第三方提供的模型权重，很少有人会检查`pickle`文件的安全性。
   - 研究员在模型的`__reduce__`方法中插入了payload，一旦用户执行`torch.load('model.pth')`，恶意代码就会运行，下载第二阶段的攻击脚本。

2. **容器逃逸第一步：利用Transformers库的信任链**
   - 恶意脚本运行后，会检查当前环境是否安装了`transformers`库。如果存在，它会利用`transformers`的`modeling_utils.py`中一个默认行为：从Hugging Face Hub加载模型时，默认信任配置文件和自定义代码。
   - 攻击脚本注册了一个伪装成“预训练权重”的模型，其中包含一个恶意的`config.json`，指定了`auto_map`参数，指向一个需要执行的Python文件。由于Hugging Face的缓存和加载机制，这个恶意代码会在用户下次加载该模型时以高权限运行。

3. **权限提升：利用Docker环境的错误配置**
   - 很多AI训练和推理服务都运行在Docker容器中。攻击脚本扫描了容器内部的挂载点，发现`/var/run/docker.sock`被挂载到容器内——这是一个常见的“方便运维但极其危险”的配置。
   - 通过`docker.sock`，攻击者的代码可以直接与宿主机上的Docker守护进程通信，拉起一个新的特权容器，挂载宿主机根目录，从而获得对宿主机文件系统的完全读写权限。

4. **持久化与控制：篡改模型缓存，横向移动**
   - 有了宿主机权限后，攻击者并没有直接破坏系统，而是做了一件更隐蔽的事：篡改了Hugging Face Hub的本地缓存目录`~/.cache/huggingface/`。他们把其他常用模型的缓存文件替换为植入后门的版本。
   - 这样一来，即使最初的投毒模型被删除，只要开发者再次使用这些常用模型，后门就会被重新激活。这种“供应链二次污染”的思路，直接威胁到整个组织的模型使用生态。

## 为什么说这次攻击“吓到”了奥特曼？

虽然Hugging Face的报告是在受控环境中进行的红队演练，但它揭示的风险模型完全适用于真实世界。OpenAI、谷歌等大厂虽然主要使用自研模型，但在数据预处理、基准测试、社区工具链上大量依赖开源生态。

- **对OpenAI的启示**：GPT-4o、GPT-5的训练管道中使用了多种开源工具进行数据清洗和标注，如果其中某个环节的模型文件被投毒，理论上可以在训练数据中注入对抗样本或窃取训练配置。Sam Altman在一次内部安全评审中提到：“我们必须把第三方模型和代码视为不受信任的边界，就像处理用户上传的文件一样。”（引自The Information的内部信源，非公开声明）

- **行业通用问题**：根据Hugging Face的统计，2024年上半年，平台上带有“auto_map”自定义代码的模型数量增长了340%，其中超过15%的模型加载时会自动执行`trust_remote_code=True`（默认需要用户确认，但很多开发者为了便利直接设为True）。这为供应链攻击提供了巨大的攻击面。



## Pickle反序列化：AI界的“万年漏洞”为何修不好？

这次攻击的核心技术点，还是那个困扰Python生态二十年的问题：`pickle`模块的设计哲学。

| 对比项 | Pickle | ONNX | SafeTensors |
|--------|--------|------|-------------|
| 序列化速度 | 快 | 中等 | 中等 |
| 是否可执行代码 | 是 | 否 | 否 |
| 社区接受度 | 原生支持，兼容性最好 | 需要转换，性能折损 | 新格式，社区在推动 |
| 主要风险 | 反序列化RCE | 算子漏洞 | 尚无重大漏洞发现 |

- **为什么还没全面弃用Pickle？**
  1. **历史惯性**：几乎所有PyTorch教程都从`torch.save()`和`torch.load()`开始，Hugging Face上的数十万个模型都以`.bin`或`.pth`格式存储，底层都依赖pickle。
  2. **性能与便利**：Pickle可以直接序列化Python对象，包括自定义类、张量元数据等，而SafeTensors等安全格式只存储张量数据，需要额外处理模型结构。
  3. **修复成本**：Hugging Face从2023年开始推广SafeTensors格式，但截至2024年10月，平台上仍有61%的模型仅提供Pickle格式。

- **Hugging Face的应对**：
  - 上线了“Picklescan”工具，在模型上传时扫描pickle文件中的危险操作码。
  - 在模型页面增加明显的安全警告标签（如下图中的黄色警告条）。
  - 在`transformers`库中把`trust_remote_code`的默认值设为`False`，并要求显式审核。



## 容器化的“皇帝新衣”：docker.sock滥用成灾

这次攻击的另一个关键助跑器，是开发者对Docker socket的滥用。在AI场景中，很多团队为了在容器内启动新容器（比如自动扩缩推理节点），直接把`/var/run/docker.sock`挂进去，这相当于把房间的钥匙放在门口的垫子下。

- **真实数据**：根据Aqua Security在2024年9月发布的云原生安全报告，全球有28%的运行容器挂载了`docker.sock`，其中AI/ML类容器的比例高达41%。
- **攻击路径简析**：
  ```bash
  # 在容器内执行（如果docker.sock可写）
  docker -H unix:///var/run/docker.sock run -v /:/host -it alpine chroot /host
  # 这就拿到了宿主机shell
  ```
- **防御建议（非本次攻击重点，但极其实用）**：
  - 使用Kubernetes的`securityContext`禁止特权模式。
  - 用`imagePullPolicy: IfNotPresent`减少外部映像拉取风险。
  - 改用更安全的容器运行时接口（如CRI-O），避免直接暴露Docker socket。

## “模型即代码”时代的信任边界重建

传统软件供应链关注的是PyPI、npm包的安全，但AI模型的版本管理、缓存机制、动态代码加载让问题更加复杂。模型不仅是数据，它还是可执行的代码——这个认知必须刻在每个AI工程师的脑子里。

- **新边界定义**：
  1. **加载时边界**：任何`torch.load()`调用都应视为执行外部代码，需要沙箱环境（如gVisor、Firecracker microVM）。
  2. **运行时边界**：模型的`forward`函数本身也可以是攻击面（对抗样本、能耗攻击），但本次案例显示，加载阶段的威胁更直接。
  3. **生态信任链**：Hugging Face Hub虽然提供了签名和扫描，但最终执行的信任决定权在用户手上。`trust_remote_code`这个参数名本身就是一种警示——你真的信任这段远程代码吗？



## 实用建议：如何避免成为“AI供应链投毒”的下一个受害者

1. **立即检查你的容器配置**
   - 运行`mount | grep docker.sock`，如果返回结果，立刻修改部署配置。非必要不挂载，挂载后必须将其设为只读（`ro`），并且限制访问用户。
   - 使用`docker run --security-opt=no-new-privileges`减少容器提权风险。

2. **无Pickle化工作流**
   - 下载模型时优先选择**SafeTensors**格式。在Hugging Face模型页面勾选“SafeTensors”过滤器，或使用代码：
     ```python
     from safetensors.torch import load_file
     state_dict = load_file('model.safetensors')
     ```
   - 如果必须加载`pth`文件，使用`torch.load('model.pth', weights_only=True)`（PyTorch 1.9+），或者在自己的沙箱环境里先执行一遍安全检查。

3. **审核`trust_remote_code`**
   - 在团队内部建立铁律：除非经过安全团队审查，否则任何生产环境都不允许设置`trust_remote_code=True`。
   - 如果项目需要自定义模型代码，把代码fork到内部仓库，并进行静态分析，确认不会执行非预期操作。

**最后一点冷思考**：Hugging Face的这次红队演练并不是为了制造恐慌，而是想证明AI供应链的安全防护必须从“信任所有模型”转向“零信任”。奥特曼的“暂停”如果是真的，那也绝不是去修GPT-6的bug，而是要求所有人重新审视那些被忽略的基础组件。毕竟，世界上最坚固的城堡
