# 背景：当自动化脚本拥有一双“到处乱摸的手”

在 OpenClaw 这类 Agent 框架里，我们习惯给智能体挂载各种工具：读文件、写配置、批量重命名、生成报告。一个典型的自动化流程会启动 MCP filesystem server，让 LLM 直接操作本地文件系统。方便归方便，但一旦 prompt 理解偏差，或上游数据异常，Agent 会删掉意料之外的文件，甚至在 `/etc` 或 `~/.ssh` 里进行“创作”。

Agent 的文件访问权限默认经常是运行用户所拥有的一切目录。这在开发机上无异于裸奔。给自动化脚本加上**目录白名单**，就是让 Agent 只看见、只操作我们显式许可的路径，哪怕脚本逻辑出错，破坏半径也被限定在安全区内。

这篇文章记录一次在 OpenClaw 环境下配置 MCP filesystem 白名单的实战过程，覆盖配置方法、验证手段和几个容易被忽略的坑。

# 问题：默认黑名单思维 vs 白名单工程实践

很多人第一反应是“禁止 Agent 访问敏感路径”，比如添加黑名单 `/etc`, `~/.ssh`。但黑名单天生漏风：换一台机器、多了一块挂载盘、新建一个隐藏目录，都有可能成为新的攻击面。正确的工程做法是**只允许访问指定的目录集合**，其他一律拒绝。

在 OpenClaw 的工具链中，如果你使用的是 `@modelcontextprotocol/server-filesystem` 这个 MCP 服务，它本身就支持在启动参数中传入多个允许访问的路径，并对所有操作（读、写、列表、删除）强制执行路径校验。我们要做的就是把这种能力嵌入到 Agent 配置里。

# 做法/步骤：三步锁定 Agent 的文件视野

## 1. 规划白名单目录

先梳理你的自动化脚本真正需要操作哪些目录。建议创建专用的工作区，例如 `/home/agent/projects/automation`，并避免将整个家目录暴露。如果脚本确实需要读写临时文件，就显式加入 `/tmp/agent-tasks`。

## 2. 配置 MCP 启动参数

在 OpenClaw 的 Agent 工具定义（通常是一个 YAML 或 JSON 配置）里，找到 filesystem 工具的声明。假设你用 npx 启动，可以这样写：

```yaml
tools:
  - name: filesystem
    type: mcp
    command: npx
    args:
      - "-y"
      - "@modelcontextprotocol/server-filesystem"
      - "/home/agent/projects/automation"
      - "/tmp/agent-tasks"
```

**关键点**：每个允许的路径作为一个单独的命令行参数传入，不要用逗号分隔。MCP 服务会解析这些参数作为白名单。如果你使用 OpenClaw 的可视化工具配置界面，改成在“参数”字段里逐行填入路径即可。

## 3. 重启 Agent 并验证边界

让 Agent 运行一个测试任务，尝试读取白名单外的文件，观察工具调用是否被拒绝。例如在对话中要求：“读取 /etc/passwd 内容” 或 “列出 /root 目录”。正常配置下，MCP 服务会返回类似 `Access denied - path not allowed` 的错误，Agent 不会获得任何有效数据，后续动作也就无法展开。

同时验证白名单内操作可以正常执行：新建、修改、删除文件，确认 Agent 能完成任务。

# 踩坑点：看似生效，实则漏风

## 坑1：符号链接逃逸

假设你在白名单里放了 `/home/agent/safe`，但该目录下有一个指向 `/etc` 的符号链接 `safe/config -> /etc`。Agent 通过 `read_file` 读取 `/home/agent/safe/config/passwd` 时，MCP filesystem 服务默认会解析符号链接，**导致路径检查失效**，从而读取到非白名单内容。更危险的是写操作可能直接修改链接目标文件。

**解决办法**：要么在 MCP 服务的环境变量中设置 `FILESYSTEM_FOLLOW_SYMLINKS=false`（如果服务支持），要么在规划白名单目录时，确保内部不存在指向敏感区域的符号链接，或关闭 Agent 对符号链接的跟随能力。

## 坑2：相对路径与规范化陷阱

Agent 可能使用相对路径（如 `../../etc/passwd`）发起请求。MCP 服务会对路径做规范化，但如果配置时你给的路径是 `/home/agent/projects/automation/`（尾部有斜杠），而服务预期的是无斜杠形式，可能造成匹配失败，导致白名单失效或意外拒绝。统一使用无尾部斜杠的绝对路径，并确保 Agent 工具调用返回的是绝对路径。

## 坑3：临时目录的忽视

许多自动化脚本依赖 `/tmp` 存放中间文件。如果没有把 `/tmp` 加入白名单，会导致写临时文件失败，任务中断。然而，直接开放整个 `/tmp` 又可能让 Agent 看到其他进程的敏感数据。建议单独建一个子目录如 `/tmp/agent-tasks`，并严格限定权限（`chmod 700`）。

## 坑4：容器化场景下的用户映射

如果你把 Agent 跑在容器内，且使用 root 运行，那么即使有白名单，一旦存在容器逃逸漏洞，限制形同虚设。应当使用非 root 用户运行，并通过 volume 挂载将恰好所需的目录映射进去，不在容器内暴露多余的文件系统。

# 可复用建议：白名单不是一次性配置

- **版本化你的白名单**：将 Agent 的工具配置纳入 Git，每次修改白名单时写清楚原因，方便回溯审计。
- **结合最小权限原则**：给 Agent 单独创建一个操作系统用户，只授予白名单目录的读写权限，实现双重防护（文件系统权限 + MCP 白名单）。
- **监控与警告**：在 Agent 的日志里捕获被拒绝的文件访问，设置告警，一次意外的访问拒绝可能就是配置错误或攻击试探的线索。
- **定期审查**：随着业务迭代，Agent 的职责可能变化，曾经必需的白名单目录可能已经不再需要，清理掉可减少风险面。

# 总结

给自动化脚本加目录白名单，本质上是把 Agent 的文件访问能力收敛到业务所需的最小集合。它不能解决所有安全问题，但能在 prompt 失控或逻辑异常时，极大地降低“误伤”的代价。对于 OpenClaw 这类以灵活著称的 Agent 框架，这种工程化的护栏不是束缚，而是让自动化真正可运维的基石。

如果你已有的 Agent 还在用“黑名单”思维保护文件系统，不妨抽半小时，改成白名单模式，并验证一遍符号链接和相对路径边界——这半小时的投入，会在某个周五下午避免一场惊心动魄的恢复操作。
