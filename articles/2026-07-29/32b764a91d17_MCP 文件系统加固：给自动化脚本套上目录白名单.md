Agent 自动化处理文件的场景越来越多：自动整理下载目录、清洗日志、批量重命名项目资源，甚至通过 MCP 的 filesystem server 直接读写宿主机文件。但默认的文件系统工具往往不做任何路径限制，一旦 prompt 的不确定性导致 Agent 误解析参数，就可能误删系统配置、泄露敏感文件。在工具调用链里加一层目录白名单，是最小成本且有效的工程护栏。

## 问题：你的 Agent 可能正在越界

以 MCP 官方提供的 `@modelcontextprotocol/server-filesystem` 为例，它注册了 `read_file`、`write_file`、`create_directory`、`list_directory` 等一系列工具，允许访问启动时指定的一个或多个目录，但很多自建 MCP 或用 SDK 快速搭出来的 filesystem 实现，常常忘了加限制，直接暴露整个文件系统。即便配置了允许目录，有些实现只对 `list_directory` 做约束，读写接口仍然不校验，或者校验逻辑有漏洞。

另外，在 OpenClaw 这类平台上，你可以自定义插件调用本地脚本，如果脚本内部只是简单接受文件路径参数直接传给 `open()` 或 `shutil`，那和裸奔没区别。所以，给文件操作加一个“本地目录白名单”是必要的。

## 做法：路径校验中间件

核心思路很简单：**所有文件访问工具在执行实际操作前，必须将传入路径规范化为绝对路径，并验证其是否位于预设的白名单目录子树内。**

我用 Python + `pathlib` 实现一个可复用的校验层，并能直接注入到 MCP 工具或自定义自动化脚本里。

### 1. 白名单配置

从环境变量或配置文件读取，方便不同环境切换，且避免硬编码。

```python
import os
from pathlib import Path

ALLOWED_BASES = [
    Path(p).resolve()
    for p in os.getenv("AGENT_ALLOWED_DIRS", "").split(":")
    if p
]
```

容器化部署时，通过 `AGENT_ALLOWED_DIRS=/data/project:/data/output` 注入白名单。

### 2. 路径许可函数

```python
def is_path_allowed(target: str | Path) -> bool:
    try:
        resolved = Path(target).resolve()
    except (OSError, RuntimeError):
        return False

    for base in ALLOWED_BASES:
        try:
            # Python 3.9+ is_relative_to 保证子目录关系
            if resolved == base or resolved.is_relative_to(base):
                return True
        except ValueError:  # Windows 不同盘符等情况
            continue
    return False
```

要点：
- 必须 `resolve()`，把 `../`、符号链接、`~` 全部展开成绝对路径；不 resolve 的字符串前缀匹配完全不可靠。
- 检查 `resolved == base` 允许白名单目录本身被读写。
- `is_relative_to()` 自动处理路径分隔符，比手工 `startswith` 安全。
- 捕获异常：路径不合法或符号链接循环时，直接拒绝。

### 3. 注入工具层

在 MCP 工具的 handler 中，调用 `is_path_allowed()` 作为第一步。以自定义的 `write_file` 为例：

```python
async def handle_write_file(arguments):
    file_path = arguments.get("path")
    if not is_path_allowed(file_path):
        raise PermissionError(f"Access denied: {file_path}")

    # ... 正常读写逻辑
```

对于 `list_directory`，先验目录权限后，还可以过滤返回结果，只展示同样在白名单内的子项，避免信息泄露。

## 踩坑记录

**1. 符号链接穿越**  
`Path.resolve()` 会跟随符号链接解析到真实路径。如果允许目录内有一个指向 `/etc` 的软链接，`resolve()` 后变成 `/etc`，会被白名单拒绝。但这正是我们期望的行为。需要注意，如果你故意允许内部链接指向外部（例如共享缓存目录），那要么把目标目录也加入白名单，要么用 `os.path.realpath` 控制是否跟随链接，要权衡安全性。

**2. Windows 陷阱**  
`is_relative_to()` 在跨盘符时会抛出 `ValueError`，需要捕获并返回 `False`。此外，路径大小写问题可以使用 `os.path.normcase` 做额外归一化，但通常 `resolve()` 后的路径已包含系统正确的大小写，直接比较是可行的。

**3. glob 与通配符**  
如果工具暴露了 `glob` 或 `search_files` 能力，需要警惕用户传入 `../../*`，在调用 `glob` 前必须校验基础目录部分。建议先提取可能的目录前缀（最左不带通配符的部分），校验通过后才执行 `glob`，然后对每个匹配结果再次逐一校验是否在白名单内。千万不要直接传给 `shutil.rmtree` 等危险操作。

**4. 临时文件目录**  
有时脚本需要写临时文件到 `/tmp`，这往往会超出白名单。解决办法：把特定临时目录（最好是进程隔离的 `tempfile.mkdtemp()`）动态加入白名单，或让 Agent 只能使用白名单内的临时子目录，由外部定时清理。

## 可复用建议

- **装饰器化**：写一个 `@require_allowed_path` 装饰器，自动校验 `path` 参数，减少重复代码。
- **统一入口**：如果你使用 OpenClaw 的自定义插件，可以在插件基类中统一加一层文件访问门面，所有本地 I/O 都走这个门面，禁止插件直接 `import os` 乱读。
- **日志与告警**：拒绝访问时记录完整路径和调用栈，便于发现 prompt 是否试图越权。
- **与系统级限制配合**：应用层的白名单是基础，容器化时配合 `readOnlyRootFilesystem`、seccomp 等，可以构成纵深防御。

## 总结

Agent 的安全感不是来自信任 prompt，而是来自工具链的每一个约束点。文件目录白名单实现简单、开销极低，却能堵住很大一部分误用和恶意利用的路径。在 OpenClaw 或任何自动化实践中，这一步值得成为基础设施的一部分：先把 Agent 关进项目的“院子”里，再慢慢教它怎么走。
