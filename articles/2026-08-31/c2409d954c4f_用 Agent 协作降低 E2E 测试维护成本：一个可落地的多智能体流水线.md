## 背景

E2E 测试的维护成本一直不低：页面一改版，选择器失效；业务流程一变，用例要跟着改。传统做法是手工写 Playwright/Cypress 用例，业务稳定时还好，一旦产品快速迭代，测试代码很容易变成“改不动、删不掉”的负债。

这两年 Agent 和 MCP 生态起来后，不少人尝试让 AI 直接生成 E2E 脚本。实际体验是：单 Agent 能写，但很不稳定。它容易生成脆弱的 CSS 选择器、漏掉异步等待、不理解业务上下文，执行失败后也只会泛泛地“再试一次”。所以问题不是“AI 能不能写测试”，而是“怎么让 AI 稳定地写、可维护地写”。

## 核心问题

单个 Agent 承担了太多角色：它既要理解页面结构，又要理解业务意图，还要生成可执行代码并修复失败。任何一环出错都会连累整体。更麻烦的是，模型对 DOM 和可访问性树的理解容易失真，直接输出的代码往往化“能用”为“碰运气”。

## 做法：拆成多个 Agent 协作

我们实践下来比较稳的方式，是拆成四个职责明确的 Agent，通过 MCP 工具连接浏览器、代码仓库和 CI。

**1. Explorer Agent**
负责探索页面，不写代码。它通过浏览器 MCP 拿到可访问性树和截图，输出一份页面对象描述 JSON，包括关键区域、可交互元素、潜在的 `data-testid`、动态加载区域等。这个步骤把“页面长什么样”变为结构化上下文。

**2. Spec Agent**
接收人类给的自然语言用例和 Explorer 的结果，生成中间 DSL。DSL 不绑定具体框架，形如：
```
open "用户登录"
fill "手机号" with "13800000000"
fill "验证码" with "123456"
click "登录"
expect "欢迎回来" visible
```
这一步把业务意图和页面结构解耦，避免后续直接改代码。

**3. Writer Agent**
把 DSL 转成 Playwright 测试代码。这里有两个硬约束：第一，必须走 Page Object 模式；第二，选择器优先级固定为 `data-testid` > `role` + accessible name > 稳定的 `id`，禁止使用 `nth-child`、深层 CSS 路径。模型只会生成符合模板的代码，减少天马行空。

**4. Runner / Repair Agent**
在隔离环境中执行测试，捕获失败截图、DOM 快照和 console 日志。失败后尝试修复，最多两轮；若两轮后仍失败，保留失败产物并生成一份“待人工处理”报告，不自动继续改。

## 可复用的落地步骤

1. 准备一个浏览器 MCP server（例如 Playwright MCP）和一个 Git MCP server，让 Agent 能操作页面、读取和提交测试代码。
2. 先让 Explorer 对目标页面做一次结构化探索，把结果存成 JSON 文件，后续 Agent 共享这份上下文。
3. 由人类写业务意图，Spec Agent 产出 DSL。DSL 需要人工粗审一遍，确认业务步骤和断言是否符合预期。
4. Writer Agent 生成测试代码，提交为一个 PR，触发 CI 跑测试。
5. Runner 收集失败信息并尝试修复。修复 diff 必须经过人工确认后才能合并，不自动合入。
6. 每轮迭代后，把 Explorer 的页面描述、Spec 的 DSL、Writer 的代码和 Runner 的失败产物归档，方便后续回溯。

## 踩坑点

- **选择器脆弱是最大坑。** 即使提示词里禁止 `nth-child`，模型偶尔还是会用。做法是在 Writer 的输出校验阶段加一个静态检查：发现 `nth-child`、 `/html/body/...`、多个组合 CSS 时直接打回重写。
- **可访问性树太长，模型会漏。** 大页面一次性塞进去反而降低准确率。让 Explorer 按区域分块探索，每块单独生成摘要，再拼成完整 JSON。
- **动态内容坑。** 模型喜欢生成 `sleep(3000)` 或没有等待。Runner 执行时若发现超时，Repair Agent 要优先引入显式等待条件，例如 `expect(locator).toBeVisible()`，而不是加 sleep。
- **测试数据污染。** 多个 Agent 反复执行同一用例，会把测试环境搞脏。每个用例运行前必须做独立 fixture 或数据重置，否则越修复越乱。
- **修复循环可能越改越错。** 第一次修复失败后，模型常会扩大选择器范围，导致断言变弱。必须限制修复次数，并且每次修复 diff 需要解释原因，避免静默降低测试强度。
- **本地和 CI 环境差异。** 截图断言在 headless 下可能因字体渲染产生像素级差异。建议只对关键区域做截图对比，其余用 DOM/可访问性树断言。

## 可复用建议

- **把稳定性放在“契约”上。** 和前端约定统一使用 `data-testid`，这个 id 由测试团队维护，Agent 只负责使用。比起让模型猜 CSS，契约能解决大部分维护痛点。
- **让 Agent 产出 DSL 而非最终代码。** DSL 更容易审查、版本管理和复用。页面改版时只改 Page Object 映射，业务 DSL 基本不动。
- **对称使用截图和可访问性树。** 截图帮模型理解视觉布局，可访问性树提供结构化信息。只给其中一个都会导致误判。
- **人工 gate 不能省。** 至少在初期，所有 Agent 生成的代码都要走 PR 评审。等稳定运行一两个月后，再开放低风险用例的自动合并。
- **成本控制要早做。** Explorer 和 Runner 可以用本地小模型，Spec 和 Writer 用能力更强的大模型。缓存页面描述和 DSL，避免每次运行都重复探索。

## 总结

多 Agent 协作写 E2E 测试的收益，不是“省掉测试工程师”，而是把重复、易错的维护工作拆给不同 agent，让人专注于业务意图和边界判断。这个方案要落地，关键是把 Agent 的输出约束在可审查、可回滚的范围内：DSL + Page Object + 人工 gate + 有限修复循环。没有这些约束，Agent 协作只会从“人肉维护”变成“人肉给 AI 擦屁股”。
