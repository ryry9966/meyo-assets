## 背景

用 Agent 做文件整理、批量重命名、报告生成时，最让人担心的是误删。一个看起来无害的 prompt，比如“清理临时文件”，如果 Agent 对目录结构理解有偏差，可能把重要文件当垃圾。OpenClaw 的 sandbox 模型不是给 Agent 一个“永不删除”的承诺，而是通过边界、重定向和审计把删除动作变成可控制、可回滚的操作。

## 问题：删除权限与安全边界如何共存

传统脚本可以直接 unlink；Agent 一旦获得 shell 或文件工具，理论上也能做到。问题在于我们既要让 Agent 完成清理、重构、归档等需要“写”的任务，又不能给它任意删除用户目录的能力。

OpenClaw 的做法可以拆成三层：

1. **默认最小权限**：Agent 只对显式挂载的工作目录有写权限，用户目录默认只读或不可见。
2. **删除重定向**：删除操作不直接 unlink，而是将目标移动到沙箱内的回收站暂存区。
3. **审计与确认**：高风险删除（如跨目录、批量匹配）会生成审计事件，需要用户确认或二次策略匹配。

## 做法/步骤

以一套典型的 Linux 单机部署为例，我的配置思路如下。

**第一步：定义沙箱边界**

在 OpenClaw 的 sandbox 配置中声明允许 Agent 读写的路径。例如只给 `/data/agent-workspace` 写权限，`/home/user/Documents` 只读挂载，`/home/user/.ssh` 不挂载。这样即使 Agent 执行 `rm -rf /home/user/Documents/*`，它看到的也是只读文件系统，删除会失败。

**第二步：开启删除重定向**

对 Agent 使用的文件工具（如 `delete`、`move_to_trash`）配置 trash 策略。删除操作将文件移动到 `/data/agent-workspace/.trash/YYYYMMDD/`，而不是直接 unlink。真正删除由用户在确认后执行 `purge`，或者保留 7 天后由清理任务处理。

**第三步：对高风险操作加确认钩子**

对于匹配 `rm -rf`、`find ... -delete`、批量删除超过 N 个文件的操作，OpenClaw 的 policy hook 会中断执行，向用户发出确认请求。确认可以通过 CLI 交互或 API 回调完成。这样可以拦截“清理所有 .log”误伤实际需要的日志。

**第四步：保留审计日志**

记录每次删除动作的原始路径、目标回收站路径、触发 prompt、时间戳和操作者。审计日志放在沙箱外，Agent 不可写。这样即使发生意外，也能追溯是哪一步、哪个 prompt 导致的。

## 踩坑点

1. **符号链接逃逸**：如果只做路径白名单，Agent 可能通过工作目录中的符号链接访问沙箱外文件。需要在挂载时禁止跟随符号链接，或使用 Landlock/AppArmor 限制路径解析。OpenClaw 的容器化后端通常默认处理，但手动挂载时要检查。

2. **MCP 插件绕过沙箱**：OpenClaw 的 Agent 可能通过 MCP 调用外部插件。如果插件运行在宿主机且未继承 sandbox 限制，它会变成后门。要确保所有 MCP server 与 Agent 运行在同一约束环境，或者在插件清单中明确其权限边界。

3. **回收站占用磁盘**：删除重定向后，文件并未真正释放空间。批量删除大文件时，回收站可能迅速占满磁盘。建议配置容量上限和自动清理周期，例如超过 5GB 或 7 天自动 purge，但 purge 动作需要额外确认。

4. **“重命名”被当成删除**：Agent 可能通过 `mv` 覆盖已有文件，这在审计上不显示为删除，但数据已丢失。建议对覆盖操作也进行重定向或要求显式 `--force`，并在审计中记录覆盖事件。

5. **过分信任“只读”**：只读挂载可以防止从该路径直接删除，但如果 Agent 对目录有写权限且目录内有硬链接，删除硬链接可能影响原文件。使用 `noexec`、`nosuid` 和禁止硬链接跨目录可以降低风险。

## 可复用建议

- **最小权限不只是一句口号**：不要把整个 `/home/user` 给 Agent。为每类任务创建独立 workspace，只读挂载必要目录。
- **删除默认进回收站，purge 需要显式授权**：把“删除”拆成“移到回收站”和“清空回收站”两个动作，后者由人工触发。
- **策略与机制分离**：沙箱提供机制（只读、隔离、重定向），但策略（哪些路径可写、何时需要确认）要在配置中显式声明，并随着任务变化更新。
- **监控和演练**：定期检查审计日志，模拟误删场景验证恢复流程。不要等真实事故再测试。
- **插件和工具要同等约束**：任何能执行代码的入口（shell、MCP、插件）都应纳入沙箱范围，不能只限制主 Agent。

## 总结

OpenClaw 的 sandbox 模型让 Agent 不会“轻易”误删文件，不是因为它道德高尚或者模型理解力完美，而是因为它在工程上把危险操作隔离在可回滚的边界内。误删仍然可能发生，但通过最小权限、删除重定向、确认钩子和审计，我们能把损失降到最低，并且知道发生了什么。

安全模型的终点不是“零风险”，而是“可恢复、可追溯、可控制”。这对自动化实践用户来说，比任何“绝对安全”的承诺都更实在。
