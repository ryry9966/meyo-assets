## 背景：权限失控的两端

在 OpenClaw 这类 Agent 框架里，我们接入 MCP 工具、插件和自动化脚本后，经常陷入两难：要么让 Agent 全自动执行，结果一个误判删了测试环境；要么每一步都弹确认框，Agent 沦为“带着手铐的搬运工”，效率还不如手动操作。

问题不在于“信不信任 Agent”，而在于**权限边界没有被显式建模**。很多实践者凭感觉设置权限，要么过松要么过紧，最后要么出事要么弃用。这篇文章不讨论哲学层面的 AI 安全，只讲工程上怎么落一个能用的权限分层方案。

## 问题：权限边界需要回答三个问题

1. 哪些操作可以**自主执行**，哪些必须**人工确认**，哪些**禁止执行**？
2. 确认的依据是什么？工具类型、参数值、当前会话上下文，还是历史行为？
3. 边界如何**动态调整**，而不是写死在代码里每次改都要重新部署？

没有统一答案，但可以抽象出一个可复用的模型。

## 做法：四层风险分级 + 三态确认机制

### 第一步：给每个工具/操作打风险标签

建议分成四级：

- **L0 只读**：查询、搜索、读文件、调用只读 API。这类操作默认允许，不弹确认。但注意：有些“只读”操作会有副作用，比如 `kubectl get` 没问题，但 `terraform plan` 会刷新状态文件，需要单独标记。
- **L1 低风险写**：创建临时文件、写日志、更新缓存、发送测试请求。这类操作可以设置白名单，同一参数组合连续出现 N 次后自动批准。
- **L2 高风险写**：修改配置文件、部署服务、批量更新数据、发送通知。这类操作默认需要人工确认，但可以提供“批量确认”接口，一次确认后续同类操作。
- **L3 不可逆/外部影响**：删除资源、转账、发布到生产、执行系统命令、调用付费 API。这类操作**必须强制人工确认**，且确认时需要展示操作摘要、影响范围、回滚方案。

在 MCP 工具层，可以通过工具的 `annotations` 字段（如果支持）或者自定义 `permission_required` 元数据声明风险等级。Agent 在执行前读取元数据，按当前策略决定走哪条路径。

### 第二步：实现三态确认机制

不要只有“自动执行”和“人工确认”两态，中间加一个“条件确认”：

- **自动执行**：满足白名单规则的操作，记录决策日志后直接执行。
- **条件确认**：需要人工确认，但 Agent 先把上下文打包好（工具名、参数、预期影响、风险等级、相似历史操作），用户只需要点“同意/拒绝”，不用重新输入任何信息。
- **强制确认 + 二次验证**：对 L3 操作，除了常规确认，还要输入一个简短的确认短语（比如“DELETE prod-db”），防止误点。

条件确认是效率的关键。很多 Agent 确认框只抛一个原始 JSON，用户根本看不懂，只能拒绝。正确做法是**让 Agent 生成自然语言摘要**，同时附带原始数据供高级用户查看。

### 第三步：决策日志与审计回溯

每次权限决策（自动批准、人工批准、拒绝）都记录以下字段：时间、会话 ID、工具名、参数摘要、风险等级、决策结果、决策依据（白名单命中/人工确认/拒绝原因）。日志至少保留 30 天，支持按工具、用户、时间段过滤。

这一步不是为了合规，而是为了**事后回溯**：如果 Agent 误操作了，你能从日志里看出当时为什么放行，是白名单太宽还是上下文误导了用户。

## 踩坑点

### 坑1：过度确认让 Agent 失去价值

有一个真实案例：一个团队给所有写操作都加了确认，结果 Agent 每天弹 200 多个确认框，用户根本来不及看，直接点“同意”，确认就形同虚设了。正确做法是**分层**：L1 用白名单自动批准，L2 用条件确认（摘要清晰），只有 L3 才强制确认。

### 坑2：工具元数据缺失或错误

MCP 工具开发者经常不标 risk level，或者把 `delete` 标成 `write`。Agent 框架如果不做兜底，就会执行危险操作。建议在 Agent 侧维护一个**覆盖表**：对已知的危险工具名（`rm`、`drop`、`delete`、`exec`、`transfer`）强制提升风险等级，即使工具声明是 L1 也按 L3 处理。

### 坑3：动态环境变化没有触发重新评估

假设你定义了一条白名单规则：“允许在 `staging` 命名空间执行 `kubectl apply`”。但某天有人把 `staging` 的上下文切换到了生产，Agent 不会自动感知，白名单继续生效。解决方案：**在确认机制里检查环境标识**，如果环境与白名单定义时不符，降级为强制确认。这要求白名单规则包含环境上下文，而不是只有工具名。

## 可复用建议

- **默认拒绝，显式允许**：所有 L2 及以上操作初始状态都是“需要确认”，白名单规则需要手动添加，而不是反过来。
- **提供 dry-run 模式**：对 L2/L3 操作，让 Agent 先输出“如果执行，会发生什么”的详尽模拟结果，用户确认后再真正执行。这个模式对调试权限边界非常有用。
- **确认摘要要带“差异”**：如果 Agent 要修改一个配置文件，不要只显示“将修改 app.yaml”，而是展示 diff 片段。用户看完 diff 再决定是否放行，比看一个模糊的描述可靠得多。
- **定期审计白名单**：白名单规则会随着项目演进而失效。每个月拉一次“自动执行排名”，看看哪些规则被频繁命中但可能已经不再安全，主动收紧。

## 总结

AI Agent 的权限边界不是一个静态开关，而是一套**风险分级 + 动态确认 + 审计回溯**的组合策略。核心原则是：

- 低风险操作尽量自主，高风险操作强制人工；
- 确认要提供清晰上下文，而不是抛原始数据；
- 边界要能随环境变化自动调整，白名单要定期复审。

在 OpenClaw 这类框架里，建议把权限策略做成一个独立模块，通过 hook 或中间件嵌入工具调用链，而不是散落在各个插件里。这样你可以随时调整策略，而不需要改动 Agent 的业务逻辑。先把权限分层跑起来，再逐步优化，比一开始就追求“完美安全”更实际。
