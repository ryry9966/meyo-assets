## 背景

团队里每天都需要看系统运行状态：请求量、错误率、慢查询、异常告警。早期大家靠手动翻日志，后来用简单脚本把日志尾部贴到群里，但效果很差——要么信息过载，要么漏掉关键异常。我们最终搭了一条从原始日志到结构化日报的流水线，运行了几个月，基本稳定。这里记录一下实现方式、踩过的坑，以及可以复用的思路。

## 问题

原始日志有两个特点：**格式杂**和**量大**。Nginx 访问日志、应用错误日志、数据库慢查询日志，字段完全不一样；单台机器一天几 GB 的日志，直接转发没有任何意义。我们需要的是提炼后的指标和事件，而不是日志本身。

很多现成方案只解决了“采集”这一步，比如用 Filebeat 把日志集中到 Elasticsearch，但后续的日报生成还是靠人肉查询，或者用定时任务拼接几段文本。中间缺少一层**结构化抽象**，导致日报内容不稳定、维护成本高。

## 做法/步骤

我们按照采集、解析、聚合、渲染、推送五个阶段来设计。

### 1. 日志采集

用 cron 定时把各机器上的日志文件 rsync 到一台处理机上，按天分目录存放。没有引入 Filebeat 或 Vector，因为规模不大，rsync 足够简单。关键是**延迟处理**：每天凌晨处理前一天的数据，避免日志轮转导致文件不完整。

### 2. 解析与清洗

写一个 Python 脚本，对每类日志用正则或 `parse` 库提取字段。例如 Nginx 日志提取时间、状态码、请求耗时、URL；应用错误日志提取级别、服务名、错误信息。统一输出为 JSON Lines，每条记录包含固定字段：

```json
{"ts": "2025-01-15T10:23:45Z", "level": "ERROR", "service": "order", "msg": "db timeout", "extra": {}}
```

解析失败的行不丢弃，而是放入 `parse_error` 字段并保留原始内容，方便后续排查。

### 3. 聚合与指标计算

用 pandas 或 sqlite 按小时聚合。计算请求量、错误率、P95 延迟、慢查询 Top 5、异常事件列表。聚合逻辑用 SQL 或者 pandas 的 groupby 都行，我们选择了 sqlite，因为中间结果可以落盘，方便重跑和审查。

### 4. 结构化报告生成

定义一个报告 schema，包含摘要、指标表、异常事件、趋势描述。用 Jinja2 模板渲染成 Markdown，再转成 HTML 或直接推送到 IM。模板不直接拼接日志片段，只引用聚合后的数据，避免格式混乱。

### 5. 推送与归档

通过 Webhook 推送到飞书或钉钉群，同时把原始日志、中间 JSONL、最终报告都归档到对象存储，保留 30 天。这样事后可以追溯“日报里这个错误到底来自哪条日志”。

## 踩坑点

1. **日志轮转导致文件不完整**：rsync 时可能恰好遇到日志切割，文件只同步了一半。解决办法是处理前先检查文件大小是否稳定，或者直接使用 `logrotate` 的 `copytruncate` 模式。
2. **时区不一致**：不同机器时区可能不同，统一在解析阶段转成 UTC 存储，展示时再转本地时间。否则聚合结果会错位。
3. **正则解析失败静默丢弃**：早期我们直接跳过解析失败的行，结果日报里错误数为零，但实际有严重异常。后来改成保留失败行并单独计数，如果失败率超过阈值就告警。
4. **空数据窗口被当成正常**：凌晨某个小时没有请求，错误率计算为 0，但可能是服务挂了。需要区分“没有数据”和“数据为零”。
5. **模板注入**：错误信息里如果包含 Markdown 特殊字符，直接拼进模板会破坏格式甚至执行脚本。渲染前必须转义。
6. **定时任务失败无人感知**：cron 脚本报错后日报就没了，团队还以为一切正常。需要给生成任务本身加监控，失败时发告警。

## 可复用建议

- **解析规则配置化**：用 YAML 定义每个日志类型的字段提取规则，新增日志类型时只改配置，不改代码。
- **中间数据落盘**：保存 JSONL 或 Parquet 格式的中间结果，方便重跑、调试和审计。
- **任务幂等设计**：同一天的数据重复执行不会重复推送，比如用日期作为唯一标识，推送前检查是否已生成。
- **接入 OpenClaw 插件**：可以把整条流水线封装成一个 OpenClaw 定时任务插件，通过 MCP 调用外部脚本和 IM 接口，触发方式更灵活。
- **报告尽量数据驱动**：避免让 Agent 生成大段自然语言描述，因为容易出现幻觉。用指标、表格、事件列表来表达，只在摘要部分用一两句话总结。

## 总结

自动化日报的核心不是“自动把日志贴出来”，而是**把原始日志提炼成结构化数据，再基于数据生成报告**。原始日志保持可追溯，中间层可审查，报告可扩展。这条流水线跑通后，每天的日报生成只需要几十秒，内容稳定、维护成本低，也方便后续接入更复杂的分析和告警。
