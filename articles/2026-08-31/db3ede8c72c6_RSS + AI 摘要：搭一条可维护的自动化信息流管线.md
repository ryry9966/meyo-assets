## 背景

订阅了几十个 RSS 源之后，最真实的问题不是“信息不够”，而是“推送太多、看不完”。尤其是面向 OpenClaw、Agent、MCP 这类自动化实践者，我们订阅的源往往包含大量长文：技术博客、发布说明、安全公告、行业周报。如果每条都读全文，时间成本极高；如果只读标题，又容易漏掉关键动作项。

一个自然的想法是让 AI 做摘要。但直接把 RSS 全文丢给模型，会遇到 token 爆炸、超时、上下文窗口不够、源格式脏乱、重复推送等问题。所以这件事值得认真搭成一条管线，而不是写一个一次性 prompt。

## 问题拆解

RSS + AI 摘要管线要解决四类问题：

1. **抓取与标准化**：不同源的 RSS 字段完整度差异很大，有些只有摘要，有些是全文 HTML。
2. **清洗与截断**：网页正文里混着导航、广告、脚本、相关推荐，直接喂模型很浪费。
3. **摘要结构化**：模型输出必须是程序可消费的 JSON，而不是一段自然语言。
4. **状态与去重**：同一条目可能跨源重复，或者源更新时重新推送旧内容。

下面按一条最小可用的工程化管线来拆解。

## 做法/步骤

### 1. 抓取层：统一入口

建议不要直接让 Agent 解析 RSS，而是用专门的抓取器。可以用 rsshub、miniflux、feedparser 这类工具，把源统一成标准字段：

```json
{
  "feed_url": "...",
  "title": "...",
  "link": "...",
  "guid": "...",
  "published": "...",
  "content_html": "...",
  "summary": "..."
}
```

关键原则：保留原始 `guid`、`link`、`published`，不要急着清洗，后面去重要用。

### 2. 清洗层：只保留正文

对 `content_html` 做 HTML 转纯文本，移除 script、style、nav、footer、广告容器。如果正文太短，再尝试用 readability 类提取器去抓原文。最后做长度截断，单条控制在 6000–10000 字符以内，避免模型上下文被单条长文占满。

这个阶段别调用大模型，纯规则处理即可，成本最低。

### 3. 摘要层：结构化 Prompt + 工具调用

让 Agent 输出 JSON，字段建议固定为：

- `title`：规范后的标题
- `tl;dr`：2–3 句话的核心摘要
- `key_points`：3–5 个要点
- `action_items`：如果原文包含可执行动作，比如升级、迁移、配置变更，单独列出
- `tags`：主题标签，便于后续过滤
- `confidence`：摘要可信度，0–1

Prompt 里要求模型引用原文短语，不要凭空生成事实；temperature 设低，例如 0.2；并限制输出为纯 JSON，不要 markdown 代码块。更稳妥的做法是用 function calling / MCP 工具定义 JSON Schema，让模型直接填充结构化字段。

### 4. 去重与状态层

用 SQLite 或 KV 存储保存已处理条目的唯一键。唯一键建议使用 `feed_url + guid + published` 的组合，不要只依赖 `guid`，因为有些源的 `guid` 不稳定。存一份 `hash(content)` 也可以作为兜底。

每次运行后记录：

- 抓取到多少条
- 新增多少条
- 成功摘要多少条
- 推送多少条
- 失败条数与原因

### 5. 推送与调度

推送层可以接企业微信、飞书、Telegram、Discord 等。按 `tags` 分频道，或者做每日汇总。调度建议用 OpenClaw 的定时任务能力，不要对每个源都用固定间隔抓取。活跃源 15–30 分钟一次，低活跃源 2–6 小时一次；连续失败自动退避，避免无效请求。

## 踩坑点

**1. RSS 源字段不齐**

有的源没有 `guid`，有的 `published` 缺失。不要假设字段一定存在，抓取后先做字段兜底：`guid` 缺失就用 `link` 代替，`published` 缺失就用抓取时间。否则去重逻辑会直接崩溃。

**2. 摘要幻觉**

低 temperature 不代表不幻觉，尤其是科技新闻源。建议在 prompt 里要求“只基于原文进行摘要，不补充原文没有的数字、日期或结论”。如果输出中出现原文没有的版本号或时间，直接丢弃重试。

**3. 结构化输出不稳定**

如果模型返回了 markdown 包裹的 JSON，或者字段类型错误，后续程序会解析失败。解法是严格用 JSON Schema，并且在解析失败时做一次自动修复，例如去除 ```json 包裹、修正尾逗号；再失败就记入死信队列，不要阻塞整批任务。

**4. 成本与超时**

同时处理几十条长文很容易超时。控制每批条数，例如一次最多处理 10 条；先用关键词/标签做本地过滤，只送高价值内容给模型。像安全公告、版本发布这类源，摘要价值高；营销软文或转载内容可以直接略过。

**5. 重复推送**

最典型的是同一篇文章被多个源转载。去重不能只靠 `guid`，最好加上标题相似度或 URL 归一化，例如去掉 utm 参数、统一 http/https。把已推送条目的 `hash` 保留 30 天，足够覆盖大部分重复场景。

## 可复用建议

把源配置做成 YAML/JSON，而不是硬编码：

```yaml
sources:
  - name: "security-advisories"
    url: "https://example.com/feed.xml"
    category: "security"
    max_items: 20
    schedule: "*/30 * * * *"
    prompt_overrides:
      focus: "提取漏洞编号、影响版本、修复建议"
    output_channel: "security"
```

摘要 Prompt 模板化，每个源可以覆盖关注点。抓取和摘要分开做，便于单独调试。RSS 抓取可以封装成一个 MCP 工具，OpenClaw 通过工具调用组合出完整流程，而不是把所有逻辑塞进一个插件。

另外要监控整条管线：每个源的成功率、平均摘要耗时、推送失败次数。连续失败的源自动禁用并发送告警，否则时间一长，你会忘记某个源已经沉默很久。

## 总结

RSS + AI 摘要管线的核心目标不是“让 AI 读更多”，而是把非结构化信息压缩成可决策的粒度。一条可维护的管线至少要具备：标准化抓取、规则清洗、结构化摘要、可靠去重、可观测状态。对于 OpenClaw 用户，这很适合作为第一个完整的自动化信息流项目——它不复杂，但能暴露很多真实工程问题，比如状态管理、失败重试、成本控制和结构化输出稳定性。先把这些做扎实，后面再接更多 Agent 能力会轻松很多。
