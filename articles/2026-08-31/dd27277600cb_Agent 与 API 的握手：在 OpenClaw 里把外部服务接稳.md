## 背景

OpenClaw 里的 Agent 能规划、调用工具、执行任务，但真正产生业务价值的是它连接的外部服务：数据库、内部 API、第三方 SaaS、文件系统等。对接外部服务不是简单发一个 HTTP 请求，而是要把外部世界的不可控性关进笼子里。常见的对接路径有三类：直接调用 HTTP API、通过 MCP server 暴露工具、注册自定义插件/工具函数。无论哪条路，都会遇到同一类问题。

## 问题

很多对接在 demo 阶段很顺利，一到实际使用就暴露问题。比如：API 返回 20KB JSON，Agent 把整个响应塞进上下文，导致 token 消耗爆炸、推理变慢；遇到 429 或 5xx 时 Agent 直接放弃，而不是重试或降级；字段语义不清晰，Agent 把 `created_at` 当成当地时间；分页接口只读第一页就下结论。这些问题的根源是：外部 API 不是为 Agent 设计的，它不会主动适配 Agent 的上下文限制和容错需求。

## 做法/步骤

我的做法是先把外部服务封装成“薄工具层”，再让 Agent 调用，而不是让 Agent 直接面对原始 API。

1. **定义工具边界**。对外部服务，每个工具只做一件事，输入参数显式声明，输出只保留 Agent 真正需要的字段。例如查询订单接口，不要返回整个订单对象，只返回订单号、状态、金额、更新时间四个字段，并在工具描述里写清楚字段含义。

2. **选择对接方式**。如果已有现成 MCP server，优先用 MCP；否则在 OpenClaw 的工具注册机制里写一个函数，内部用 HTTP 客户端调用外部 API。函数内做参数校验、错误映射和响应裁剪。

3. **处理错误和重试**。对 401/403 直接抛出明确错误，提示检查凭证；对 429 读取 `Retry-After` 做退避重试；对 5xx 做有限次重试，超过阈值返回降级结果或让 Agent 告知用户稍后重试。写操作必须带幂等键，避免重试造成重复写入。

4. **限制上下文占用**。给工具返回设置大小上限，比如超过 2000 字符就截断或摘要。不要假设 Agent 会自动忽略无关字段，它不会。

5. **加可观测**。记录每次工具调用的参数、状态码、耗时、返回大小、截断情况。这样当 Agent 行为异常时，你能快速定位是外部服务问题还是 Agent 理解问题。

## 踩坑点

- 把鉴权 token 硬编码在工具描述或 prompt 里，Agent 可能把 token 当普通参数传给其他工具。
- 忘记处理非 200 响应体，比如某些 API 在 4xx 时返回 HTML 错误页，JSON 解析直接崩。
- 分页处理缺失：很多 API 默认每页 20 条，Agent 只取第一页就回答“没有更多数据”。
- 时区和时间格式不一致：API 返回 UTC 时间，Agent 当成本地时间，导致任务调度错误。
- MCP server 本身不稳定，连接超时后 Agent 卡在初始化阶段，没有降级路径。

## 可复用建议

- 把外部服务对接做成独立模块，不要在 Agent 主逻辑里散落 HTTP 调用。
- 工具描述要写“何时用、参数是什么、返回什么、失败时返回什么”，不要只写一句“查询订单”。
- 对读操作可以使用短期缓存，减少重复调用；对写操作必须幂等。
- 用 contract test 固定 API 输出结构，外部服务改字段时能提前发现。
- 在 OpenClaw 里设置工具级超时和最大返回字节数，防止单个工具拖垮整个 Agent 运行。

## 总结

Agent 对接外部服务的本质，是把不可控的外部世界翻译成 Agent 可消费的受控接口。控制住边界、错误和上下文大小，比写出能跑通的代码更重要。先把工具层做薄做稳，再让 Agent 去握手，协作才会顺畅。
