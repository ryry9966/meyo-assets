# Markdown 管线：从 AI 生成到多平台发布的格式适配

## 背景

在 OpenClaw、Agent、MCP 这类自动化工作流里，让模型输出 Markdown 几乎成了默认选择：结构清晰、易于解析，也方便后续用脚本处理。但当这些内容要分发到不同平台——公众号、知乎、Notion、飞书文档、GitHub Pages——麻烦才真正开始。同一个 Markdown 文件在不同平台渲染结果可能完全不同，甚至直接报错或丢失内容。

## 问题

核心矛盾在于：AI 生成的 Markdown 往往“过于标准”或“过于自由”。模型习惯输出完整 GFM 语法、Front Matter、emoji、代码块、表格、脚注等，但各平台对这些特性的支持并不一致。例如，公众号编辑器和知乎对代码块语言标注的识别很弱，Notion 需要转换成块结构而不是纯文本，飞书对表格和嵌套列表的支持有限。如果每次发布都手动调整，不仅低效，还容易引入格式错误。

## 做法/步骤

我们团队的做法是把“AI 生成 → 发布”拆成一条可复用的 Markdown 管线，大致分四步。

**1. 定义中间表示（IR）**  
先约定一个“平台无关”的 Markdown 子集。例如：标题只用 H1-H3；代码块必须带语言标注；图片统一使用本地相对路径或占位符，后续由适配器处理；表格只保留简单结构（不超过 5 列，无合并单元格）；不使用 Front Matter、脚注、内嵌 HTML 和复杂嵌套列表。这个子集不是硬性规定，而是所有适配器共同遵守的契约。在 AI 提示词里也明确要求按这个子集输出，减少后续清洗成本。

**2. 清洗与规范化**  
即便有提示词约束，模型输出仍可能出现偏差。所以需要一个清洗脚本（Node/Python 均可），对原始 Markdown 做以下处理：剥离 Front Matter；统一换行符为 `\n`，压缩多余空行；补全缺失的代码块语言标注（默认设为 `text`）；将全角标点、特殊空格转换为半角或标准空格；检查图片路径，替换为本地相对路径；移除不支持的语法（脚注、内嵌 HTML 等），或降级为纯文本。这一步可以做成 OpenClaw 插件或 MCP 工具，方便在 Agent 流程中自动调用。

**3. 平台适配器**  
每个目标平台写一个独立的 adapter，输入规范 Markdown，输出平台需要的格式。公众号/知乎需要先上传图片到图床并替换链接，代码块语言标注改为平台支持的少数几种，表格酌情转为图片或列表。Notion 需要调用 API 将 Markdown 解析为块（段落、标题、代码块、项目符号等），并处理行内样式。飞书文档类似。GitHub Pages/Hugo 则保留 Markdown，但需要处理 Front Matter 和图片路径。适配器之间互不影响，新增平台只需新增一个文件。我们没有引入重量级框架，就是一组函数加单元测试。

**4. 发布管线**  
将以上步骤串联成一条 CLI 命令或 OpenClaw 工作流：`原始 Markdown → 清洗 → 平台适配器 → 渲染预览 → 发布 API`。发布前先做一次本地渲染预览或调用平台草稿接口，确认无误后再推送。这样即使某一步出问题，也能快速定位。

## 踩坑点

实践中几个常见坑：

- **代码块语言标注**：公众号后台不识别 `rust`、`typescript` 等语言名，会退化为无高亮甚至丢失语言信息。适配器需要维护一张语言映射表，把不支持的映射到 `text` 或 `python`/`javascript`。
- **图片外链防盗链**：知乎、公众号对图片外链限制严格，直接引用原始图床可能 403。正确做法是上传到平台自己的图床或使用白名单域名。
- **表格渲染**：Notion 和飞书对表格支持尚可，但公众号/知乎在移动端表格很容易错位。建议宽表格转图片，窄表格保留。
- **Front Matter 泄漏**：如果 AI 输出包含 YAML Front Matter，直接粘贴到公众号会显示成乱码。清洗阶段必须强制剥离。
- **换行差异**：GFM 中单个换行符会被忽略，但部分平台会按 `<br>` 渲染，导致段落被意外打断。统一用空行分段，行尾不加两个空格。
- **emoji 与特殊字符**：飞书、Notion 支持较好，公众号可能显示不全。适配器可配置移除或替换为文本。

## 可复用建议

- **保留原始 Markdown 作为 source of truth**：适配器只做转换，不修改原文件，方便溯源和重新发布。
- **适配器做成可插拔结构**：每个平台一个目录或模块，输入输出接口统一，便于测试和扩展。
- **加入渲染对比测试**：准备一组样例 Markdown，分别跑各适配器，人工抽查渲染结果。可以用截图对比或平台草稿预览。
- **版本控制 + CI**：将 Markdown 源文件和发布脚本纳入 Git，合并时自动触发预览构建，避免手误。
- **日志与回滚**：发布失败时保留原始内容和错误日志，支持一键重发或回退到上一个版本。

## 总结

这条 Markdown 管线并不复杂，但解决了实际工作中“一次生成、多端发布”的重复劳动。关键不在于追求完美转换，而是先定义一个够用的子集，再通过适配器隔离差异。如果只发一两个平台，手动调整也许更快；但一旦平台数量超过三个，工程化管线就能显著降低维护成本。对 OpenClaw 用户来说，把清洗和适配做成 MCP 工具或插件，可以无缝嵌入 Agent 流程，让内容分发真正自动化。
