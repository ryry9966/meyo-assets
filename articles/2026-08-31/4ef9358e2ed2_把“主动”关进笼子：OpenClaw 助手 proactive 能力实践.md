## 背景

大多数 Agent 助手长期处于“被动响应”状态：你发指令，它执行；你问一句，它答一句。真正进入运维、巡检、监控、自动化场景后，很多需求其实更适合反过来——不用等用户开口，系统发现问题后主动触发 Agent 去核实、通知、生成处理建议，甚至在安全范围内直接处理。

在 OpenClaw 这类 Agent/插件/MCP 环境里，proactive 能力通常可以拆成三层：

- 触发层：定时任务、事件钩子、阈值告警
- 执行层：Agent 调用 MCP 工具、脚本、插件
- 决策层：只通知、生成草案、自动执行

但 proactive 一旦放开，风险和收益同样明显。

## 问题

最典型的问题是：给 Agent 配一个 cron，再把工具权限给大一点，它就变成了一个半夜可能会自己改配置、重复发通知、甚至误删资源的“主动故障源”。

常见的工程问题包括：

- 定时轮询过密，token 消耗和 API 限流
- 同一事件被多个 worker 重复处理
- proactive 执行结果污染主对话上下文
- 没有 dry-run 和回滚路径
- 通知太多，用户开始无视

## 做法/步骤

我的做法是先把 proactive 动作限制在“低风险、可回滚、可通知”范围内，再逐步放开。

### 1. 白名单决定能做什么

只允许这些动作自动执行或半自动执行：

- 证书过期检查
- 磁盘使用率巡检
- 日志异常聚类
- PR/Issue 超时提醒
- 依赖版本安全告警

不允许直接执行：自动合并、自动删除、自动重启、批量修改配置。这些一律只生成建议，等待人工确认。

### 2. 触发层尽量事件驱动

能接事件钩子就不要用短间隔轮询。比如：

- Webhook 收到 CI 失败事件后再触发
- 监控系统回调触发
- 文件变更触发 MCP server

必须轮询的，加冷却时间，通常 5 到 10 分钟一次即可。

### 3. 执行层强制 dry-run 和证据收集

Agent 执行工具时先跑 dry-run，或先调用 read-only 工具收集上下文。比如磁盘告警时，先执行 `df -h`、`du` 抽样，不直接清理文件。

执行链路上，每个 action 都必须有：

- `trigger`：由什么触发
- `input`：输入快照
- `tool`：调用哪个工具
- `action`：准备做什么
- `result`：执行结果
- `rollback`：回滚或撤销方式

### 4. 决策层做分级处理

我一般分三级：

- **Level 1**：只通知。发到 IM 或工单，Agent 不采取动作。
- **Level 2**：生成处理草案。用户回复“执行”后才真正操作。
- **Level 3**：白名单内自动执行，但必须附带回滚命令和审计记录。

Level 3 范围要非常窄，例如“给超时 PR 打标签”“创建一条提醒日历”。

### 5. 去重与锁

用 Redis 或本地状态文件记录 fingerprint，例如 `disk_usage_sda1_high`，冷却时间内不重复处理。多个 worker 同时跑时，用分布式锁或至少文件锁保护。

### 6. 审计独立于对话

proactive 执行结果不要直接塞进主 session。可以写到一个独立队列、审计表或单独的 channel。这样不会污染后续正常对话，也方便回查。

## 踩坑点

### 1. 轮询风暴

早期用每分钟 cron 跑一次巡检，结果一晚上烧掉大量 token，还触发上游限流。改成事件触发 + 10 分钟冷却后，成本明显下降。

### 2. 重复执行

没有 fingerprint 和锁的时候，多个容器实例同时看到同一条告警，每个都发一遍处理建议，用户被重复打扰。后来所有 proactive job 都先抢锁，拿不到锁直接退出。

### 3. 上下文污染

把历史 proactive 结果留在 session 里，后续被动对话会受影响。比如用户问“最近有什么问题？”Agent 可能把三天前的误报告警也当成当前上下文。独立队列能避免这类问题。

### 4. 权限过大

给 Agent 配了 `restart`、`delete` 权限，结果一次误触发了服务重启。教训是：非白名单动作一律 dry-run 或只生成命令，不允许直接执行。

### 5. 误报疲劳

通知太频繁，用户开始无视。阈值需要加“连续 N 次异常才通知”，或者按影响程度分级，避免单次抖动就触发。

## 可复用建议

1. **影子模式先跑一周**：只记录“如果放开会做什么”，不实际执行。
2. **动作白名单化**：read-only、创建工单、打标签、发通知优先。
3. **所有动作带 TTL**：超过时间未确认的待执行草案自动过期。
4. **可观测性**：日志里能看到 trigger、tool、action、result、rollback。
5. **关闭路径要简单**：一个命令或一个配置项就能关掉 proactive，避免失控。

## 总结

proactive 能力不是“让 Agent 更聪明地自动回复”，而是触发器、策略、权限、去重和审计的组合。先把主动性关进笼子，用白名单和 dry-run 约束它，再根据真实运行数据逐步放开。对 OpenClaw 场景来说，一个可回滚、可观测、可关闭的 proactive Agent，才真正值得在生产里跑。
