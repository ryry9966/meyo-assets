在 OpenClaw、Agent、MCP 插件这类自动化系统里，任务通常不是“跑一次就结束”的。定时器重试、事件重复投递、Agent 多次规划、外部回调超时后手动重跑，都会让同一段逻辑被反复触发。一个看似简单的问题：重复执行会不会出问题？如果出了，往往不是崩溃，而是重复扣款、重复发消息、重复插入数据、状态被错误覆盖。解决这个问题的核心，就是幂等性。

## 背景：为什么重复执行无法避免

自动化任务的触发源往往不可靠。以 MCP 工具调用为例，Agent 可能因为上下文超时或模型重试，对同一个工具发起两次相同参数的调用；定时任务因为进程重启，导致同一时间窗口内跑了两次；消息队列因为消费确认超时，把同一条消息重新投递。指望“上游一定只触发一次”是不现实的。更现实的做法是：让任务本身容忍重复触发，多次执行的效果与执行一次一致。

## 问题：非幂等任务常见的三类故障

1. **重复写入**：先查询再插入，但并发下两个请求都查不到记录，于是都插入成功。  
2. **外部副作用叠加**：调用支付、发送短信、创建工单等外部 API 时，如果没有唯一请求标识，重试就会导致重复扣款或重复通知。  
3. **状态覆盖**：比如任务从 `pending` 改为 `running`，再改为 `done`。如果重试时拿到旧状态直接写回，可能把已经完成的任务改回 `running`，造成状态混乱。

## 做法/步骤：四层幂等设计

### 1. 定义业务幂等键

每个任务必须有一个稳定的唯一标识，由业务字段组合而成，而不是随机生成的执行 ID。例如：

- 定时对账任务：`reconcile:{biz_date}:{account_id}`
- MCP 工具创建订单：`create_order:{user_id}:{idempotency_token}`
- 消息处理：`event:{event_type}:{event_id}`

这个键要能唯一对应一次业务动作，而不是一次执行过程。

### 2. 用唯一约束落库，替代裸查询

不要只依赖 `SELECT` 判断记录是否存在。数据库唯一约束是并发安全的最后一道防线。

```sql
CREATE TABLE idempotency_records (
    idempotency_key TEXT PRIMARY KEY,
    task_type       TEXT NOT NULL,
    status          TEXT NOT NULL DEFAULT 'processing',
    result          JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

执行任务前先插入一条 `processing` 记录，利用主键冲突判断是否已有任务在处理。这样可以避免并发的 check-then-act 竞态。

### 3. 用条件更新代替盲目写状态

更新状态时必须带上预期前置状态，避免旧请求覆盖新状态。

```sql
UPDATE tasks
SET status = 'done', updated_at = now()
WHERE id = $1 AND status = 'running';
```

如果影响行数为 0，说明状态已经变化，重试请求不应再继续推进。对于关键业务，可以在事务里同时检查影响行数，为 0 则直接返回已有结果。

### 4. 外部调用携带幂等键

调用支付、短信、邮件、工单等外部系统时，把本地幂等键作为请求参数传给对方（如果对方支持）。如果不支持，则在本地记录调用状态：

- 调用前：在本地写入 `calling` 状态并提交事务。
- 调用后：根据响应更新为 `success` 或 `failed`。
- 重试时：如果本地状态已是 `success`，直接返回之前保存的结果，不再重复调用外部 API。

## 踩坑点

- **唯一约束冲突被吞掉后直接返回**：如果冲突时直接返回“成功”，但原任务其实失败了，重试会永远无法继续。正确做法是：冲突时读取原记录，如果原记录是 `processing` 且已超时，则允许接管或触发人工确认；如果是 `failed`，则重新执行；如果是 `success`，直接返回结果。  
- **幂等键粒度太粗或太细**：太粗（比如只按 `user_id` 区分）会导致不同业务动作被错误去重；太细（比如加入随机数）会让重试无法命中。键的设计必须对应业务动作的唯一性，而不是执行实例的唯一性。  
- **长事务里调用外部 API**：如果本地事务未提交就调用外部 API，外部成功但本地回滚，会导致本地没有记录，重试时再次调用外部。应尽量缩短事务边界，先提交本地状态，再调用外部。  
- **状态机设计不完整**：只考虑 `pending -> done`，没有考虑 `failed`、`retrying`、`timeout` 等中间状态，导致重试逻辑无法安全收敛。

## 可复用建议

封装一个通用的幂等执行器，把上面的步骤收敛成工具函数。伪代码示意：

```python
def run_idempotently(key, task_type, fn):
    # 1. 尝试插入 processing 记录
    inserted = db.insert(key, task_type, 'processing')
    if not inserted:
        existing = db.get(key)
        if existing.status == 'success':
            return existing.result
        if existing.status == 'failed':
            db.update_status(key, 'processing')
        else:
            # processing 且未超时，说明已有执行者，直接等待或返回
            return wait_for_result(key)
    # 2. 执行业务逻辑
    try:
        result = fn()
        db.update(key, status='success', result=result)
        return result
    except Exception as e:
        db.update(key, status='failed', result={'error': str(e)})
        raise
```

同时，给所有外部调用统一附上 `idempotency_key`，并在日志中记录该键。排查问题时，用同一个键能串起整个调用链路。

## 总结

幂等性不是“保证任务只执行一次”，而是“重复执行不会产生额外副作用”。在动手写自动化任务之前，先回答三个问题：

1. 这个任务的唯一业务标识是什么？  
2. 重复触发时，哪些副作用必须被消除？  
3. 外部依赖是否支持幂等？不支持的话，本地如何兜底？

把这三个问题想清楚，再配合唯一约束、条件更新和幂等执行器，重复执行就不再是隐患，而是系统容错能力的体现。
