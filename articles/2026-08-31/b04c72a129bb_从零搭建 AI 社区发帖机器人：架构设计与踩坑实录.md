## 背景

OpenClaw-CN 社区日常会产生不少值得沉淀的讨论：踩坑记录、插件用法、MCP 调试经验。如果每篇都靠人工整理，很容易被日常消息淹没。我们想做一个内部辅助机器人，只负责“生成草稿”，发布前必须有人确认，避免公开频道出现低质量自动内容。

## 问题

最早用一段 Python 脚本直接抓话题、拼 Prompt、请求社区 API，问题很多：Prompt 输出不稳定、社区限流、重复内容、鉴权信息散落。更麻烦的是，发布和草稿混在一起，一旦误触就会直接发出去。

后来我们把方案改成 OpenClaw Agent + MCP Server + 审核队列，关键边界是：Agent 只能创建草稿，不能直接发布。

## 做法/步骤

1. 数据侧：用一个轻量采集器读取社区 RSS/最近讨论，做去重和长度过滤。
2. 生成侧：OpenClaw Agent 根据结构化 Prompt 输出 JSON，字段固定为 title、summary、body、tags、source_urls、confidence。必须用 JSON Schema 约束，失败就重试。
3. 接口侧：MCP Server 只暴露三个工具：create_draft、preview_draft、publish_draft。publish_draft 需要独立审批参数，Agent 默认没有调用权限。
4. 审核侧：草稿写入 SQLite，CLI 里人工 approve/reject。通过后进入发布队列，限速发送。
5. 发布侧：只对单标签或单个子频道灰度，带指数退避，失败不无限重试。

关键架构很短：

```
sources -> cleaner -> LLM draft -> MCP create_draft
                -> human review -> publish queue -> community API
```

## 踩坑点

**JSON 不稳定**：模型偶尔会输出多余字段、Markdown 代码块包裹、或把 confidence 写成字符串。不要只靠“请输出 JSON”，必须用 JSON Schema 校验，失败后携带错误信息重试一次；再失败就丢弃，不要反复消耗 token。

**限流比想象中频繁**：社区 API 可能按 IP 和 token 双重限流。我们把发布动作放进单队列，间隔 30 秒以上，指数退避只做 3 次，超过就标记为人工处理。

**上下文越长越容易跑题**：直接把整栋楼塞给模型，生成结果会偏向末尾楼层或某条热门回复。需要先按时间窗口和相关性打分，只取前 8–12 条作为 source。

**鉴权不能进 Prompt**：社区 token 放环境变量，MCP Server 启动时读取；Prompt 里只出现 source 摘要，不出现任何密钥或 cookie。

**重复内容**：同一讨论可能被采集多次。对标题和正文摘要做 SHA-256，发布前查重，重复就直接丢弃并记录。

**时区问题**：定时任务容易把 UTC 和本地时间搞混。统一用 UTC，审核界面再转本地显示。

## 可复用建议

- 公开社区尽量采用“草稿 + 人工审核”，不要让 Agent 直接发布。
- 用 MCP 封装社区 API，而不是用浏览器自动化硬点按钮；有 API 就优先 API。
- 所有 LLM 输出都落日志，保留 prompt hash 和输出 hash，方便回放。
- 先圈定一个标签或子频道试运行两周，再决定是否扩大。
- 把“生成”和“发布”权限拆开，运维上会少很多事故。

## 总结

现在这个小机器人每周能稳定产出 3–5 篇待审核草稿，人工只需要改标题和删段落，发布仍由人确认。它不算“智能发帖”，更像一个带接口约束的草稿整理器。对 OpenClaw/MCP 用户来说，最值得复用的不是某段 Prompt，而是把权限边界和失败处理做在前面。
