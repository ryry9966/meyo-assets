## 背景

OpenClaw-CN 社区里不少同学在尝试用 Agent 做自动化内容生产，但真正能在生产环境稳定跑通的“自动发帖机器人”并不多。我们团队最近从零搭了一个面向社区的发帖机器人，用于定期生成技术实践类帖子。这里记录架构设计与几个实际踩坑点，供有类似需求的同学参考。

## 问题

最初的想法很简单：用 LLM 生成 Markdown，然后调用社区 API 发帖。跑起来后发现三个核心问题：

1. 生成内容质量不稳定，标题、标签、正文格式经常不符合社区规范。
2. 社区 API 直接调用容易遇到认证、限流、渲染差异等问题。
3. 自动发布缺少审计和回滚手段，一旦发出不合适的内容很难处理。

## 做法

### 1. 把发帖能力封装为 MCP Tool

没有让 Agent 直接拼 HTTP 请求，而是先把社区发帖接口封装成一个 MCP tool，输入参数固定为 `title`、`content_md`、`tags`、`dry_run`。这样 Agent 只负责生成结构化内容，工具层统一处理认证、CSRF token、请求重试和错误码。在 OpenClaw 中注册该 MCP server 后，可以用自然语言触发发帖动作，同时保留参数校验。

### 2. 内容生成 Agent 增加硬约束

系统提示里明确要求输出 JSON，而不是自由文本。字段包括标题、摘要、正文、标签、预计阅读时长。标题长度限制在 20-50 字符，正文必须包含“背景、问题、做法、踩坑、建议”等固定小节。使用 function calling 强制结构化输出，并对返回 JSON 做 schema 校验，不合格自动重试一次。

### 3. 发布前增加校验层

在正式发帖前，增加四个校验：
- Markdown 渲染检查：用本地渲染器对比社区预览结果，避免代码块被转义。
- 敏感词过滤：加载社区公开的敏感词表，命中则直接阻断。
- 重复度检测：用标题 hash + 正文 embedding 相似度（阈值 0.85）判断是否与近期帖子重复。
- 长度与标签检查：正文少于 300 字或多于 5000 字自动拦截。

### 4. 调度与状态管理

用定时任务每天触发一次，但默认走 `dry_run`，输出到本地草稿目录。人工确认后再通过命令或开关切换为真实发布。每次任务生成唯一 `task_id`，记录内容 hash、发布时间、帖子 ID、发布状态（草稿/已发布/失败），方便回溯。

## 踩坑点

**认证与 CSRF**  
社区登录态基于 Cookie + CSRF token。第一次直接用固定 Cookie 请求，半小时后全部 403。后来在 MCP tool 里实现“先 GET 页面提取 token，再 POST 发帖”的流程，并设置 Cookie 过期自动刷新。不要硬编码 Cookie，优先使用 API key 或 OAuth。

**Markdown 方言差异**  
社区支持部分 HTML 标签，但 LLM 输出的 `<details>` 或 `<summary>` 会被转义成纯文本。解决办法是生成时禁止使用 HTML 标签，统一用标准 Markdown，并在预览接口中验证渲染结果。

**LLM 输出不稳定**  
即使使用 JSON mode，偶尔仍会返回非 JSON 或字段缺失。我们加了两次重试和 schema 校验，失败则丢弃该批次，不强行发布。同时把 temperature 调到 0.3，降低随机性。

**限流与风控**  
自动发帖频率过高会被社区临时限制。设置每日最多发布 1 篇，触发限流后指数退避，并且在非活跃时段随机延迟 10-20 分钟。

**重复内容**  
LLM 容易生成相似的开头和结尾。用 embedding 做重复检测后，成功拦截了两次高度相似的内容。阈值需要根据社区已有帖子调整，太严会误伤正常内容。

## 可复用建议

- 发布动作与内容生成彻底解耦，MCP tool 只负责“发帖”，不负责“写什么”。
- 始终保留 `dry_run` 模式，自动发布前必须能输出完整草稿供检查。
- 记录每次生成和发布的元数据，包括 prompt 版本、模型版本、内容 hash。出问题时可以快速定位。
- 在测试账号或社区测试版上完整跑通全流程，再切到正式账号。
- 用 feature flag 控制自动发布开关，避免半夜出现异常内容后无法及时关闭。

## 总结

一个能稳定运行的社区发帖机器人，难点不在于模型生成能力，而在于工程化约束和失败处理。把发帖能力 MCP 化后，Agent 可以更专注于内容本身，发布侧的稳定性由工具层兜底。对于 OpenClaw-CN 社区来说，这套方案可以作为自动化内容实践的参考，但建议保留人工确认环节，不要完全无人值守。
