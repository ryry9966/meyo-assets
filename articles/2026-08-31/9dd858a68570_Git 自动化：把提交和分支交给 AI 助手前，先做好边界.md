## 背景

在 OpenClaw 场景里，Git 自动化常被理解成“让 agent 自己敲命令”。但真正适合落地的，其实是 commit message 生成、分支命名、PR 描述这类低风险重复劳动。模型确实能给出不错的 diff 摘要，但 Git 有状态、不可逆、影响多人协作，代理不能拿全局 shell。

## 问题

直接把 `bash` 或 `shell` 工具交给 agent，容易遇到三类问题：

- 误提交 `.env`、密钥、证书等敏感文件。
- `git commit -am` 把未 staged 的工作区改动一起打包。
- 分支名和提交信息随意生成，短期省事，长期难以追溯。

这些问题不是换更强模型能解决的，而是需要约束工具面和流程。

## 做法/步骤

### 1. 只暴露受限 Git 工具

在 OpenClaw 里可以接 Git MCP server，或自定义命令插件。只允许：

```
git status --short
git diff --cached --stat
git diff --cached -- <path>
git branch --list
git log --oneline -10
```

另加两个动作：`commit_suggest` 与 `branch_suggest`，默认都不执行写操作。`push` 单独放，必须人工确认。

### 2. 先审 staged area，再生成信息

模型生成提交信息前，先做一层检查：

```bash
git diff --cached --name-only | grep -Ei '(^|/)(\.env|.*\.pem|.*\.key|id_rsa|.*\.p12)$' && {
  echo "sensitive file in staging, abort"
  exit 1
}
```

同时限制 diff 大小。比如超过 2000 行，只给模型 `git diff --cached --stat` 和文件列表，不喂完整补丁；二进制文件直接跳过。

### 3. 让模型只产出 message，不直接执行

给模型固定输出 JSON：

```json
{"type":"feat","scope":"auth","subject":"add login rate limit","body":"avoid brute force on /login"}
```

脚本负责校验：type 是否在允许列表，subject 是否小于 50 字符，是否包含非法字符。校验失败最多重试一次，不无限 loop。

### 4. 分支名走白名单

根据任务 slug 或 issue 号生成分支，例如 `feat/oauth-refresh`。脚本用正则校验：

```
^[a-z]+/[a-z0-9._-]+$
```

中文、空格、斜杠异常、过长全部拒绝或转换。生成前检查 `git branch --list` 是否已存在。

### 5. 默认 dry-run，留下审计

每次先输出将要执行的命令和提交信息，人工确认后再执行。追加日志到 `.git-ai.log`，记录时间、分支、提交信息 hash、是否已 push。这样出问题能回溯，而不是只看 shell history。

## 踩坑点

- **message 格式不合法**：模型常输出 `feat:subject` 缺空格，或 subject 太长。必须加 parser。
- **大 diff 撑爆 context**：不要给完整 worktree，只给 staged diff，且要截断。
- **自动 `git add -A` 危险**：让用户先 `git add` 指定内容，agent 只处理暂存区。
- **pre-commit hooks 修改文件**：如果 hook 会格式化代码，先跑 hook，再生成 commit message，否则摘要基于旧 diff。
- **push 前不检查远端**：如果远端有新提交，自动化分支 push 前先 `git fetch`，用 `git rev-list --left-right --count` 检查，落后就停下。
- **Windows 换行与 autocrlf**：在 Windows 与 Linux 混合环境，diff 可能充满行尾差异，先统一 `.gitattributes`。

## 可复用建议

1. 先做只读接入，再开 commit suggest，再开本地分支，最后才放开 push dry-run。
2. 禁止自动 push、禁止 force push、禁止 `git checkout -- .` 这类破坏性命令。
3. 将敏感文件和 diff 上限做成配置项，不同仓库可复用同一插件。
4. 小脚本可以做成 OpenClaw 的共享工具，参数包括：`MAX_DIFF_LINES`、`ALLOWED_TYPES`、`BRANCH_PREFIX`、`SENSITIVE_PATTERNS`。
5. 放在测试仓库或 bare clone 里验证：模拟敏感文件、二进制 diff、远端领先等情况。

## 总结

Git 自动化适合从“消息生成 + 分支命名”开始，因为它可回滚、容易审计，收益也明显。真正值得谨慎的是 push、merge、rebase 和破坏性 git 命令。把工具面缩小、只消费 staged diff、保留人工确认，这些工程边界比模型能力更关键。
