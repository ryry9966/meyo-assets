## 背景

在 OpenClaw 生态里，用 Agent 配合 MCP 做社区内容发布已经很常见：定时抓取技术动态、自动生成摘要、通过插件发到 Discourse、Slack、Reddit 等平台。但很多团队在跑通流程后，很快会遇到账号异常：验证码频繁、帖子被折叠、甚至封禁。我们做社区维护自动化时也踩过坑，后来才明白：平台反作弊盯的不只是“你是不是机器人”，更是“你的行为模式有多不像人”。

## 问题

最初我们的脚本非常简单：每隔 6 小时发一条，内容从固定模板拼装，发完直接退出。上线第二周，账号就被要求手机验证。分析日志发现，发布时间几乎分毫不差，标题结构高度一致，且发帖后没有任何后续行为。这种模式在平台侧几乎等同于机器人特征。

## 做法 / 步骤

### 1. 拆分动作，拉长操作链路

不要再把发帖看作一次 API 提交。我们改为状态机：进入社区 → 浏览列表 2-5 秒 → 打开发帖页 → 停顿 → 写入标题 → 停顿 → 写入正文 → 预览 → 停顿 → 提交。每个状态之间的延迟单独随机，并且允许偶尔取消一次再重来。整个流程从 2 秒拉长到 40-90 秒。

### 2. 用长尾分布代替均匀随机

人类操作间隔不是均匀分布，更接近对数正态或重尾分布。我们用 Python 的 `random.gammavariate` 生成延迟，参数设为形状 2、尺度 30（单位秒），然后加上最小基础延迟 20 秒。这样大部分延迟在 60-120 秒，但偶尔会出现 10 分钟以上的长间隔。发帖间隔也用类似思路：基础冷却 1 小时，加上 gamma 抖动，每天保持 2-4 条。

### 3. 内容模板加噪声

只替换时间、标签不够。我们做了三层变化：一是从多篇源文章混合生成摘要；二是用本地小模型做同义改写，控制改写强度；三是随机插入或删除一些过渡词。发布前人工抽检一次，确保内容通顺。

### 4. 发布后不要立刻退出

脚本发帖后会模拟浏览帖子列表、查看通知，随机停留 15-40 秒。每周再有 1-2 次自动“点赞”或“回复”行为，但这些行为也设置低频上限，避免被判定为营销互动。

### 5. 熔断和灰度

设置每日上限 3 条，连续发布后至少冷却 4 小时。一旦响应码出现异常（如 302 到验证码页、429），立刻停止当天所有任务并推送告警到人工。

## 踩坑点

**第一个坑是“随机乱跳”反而更假。** 早期我们把延迟设成 `random.randint(30, 300)` 秒，结果平台还是标记了。因为真实用户不会在 30 秒和 5 分钟之间均匀摇摆。改用 Gamma 分布后，行为曲线明显更像人。

**第二个坑是忽略时区。** 我们的脚本按服务器本地时间执行，但目标社区主要活跃在北美时段。后来加上了社区活跃时段权重，在目标时区的 9:00-23:00 之间发帖，避开当地凌晨。

**第三个坑是复用同一个 cookie/token。** 即使节奏完美，如果多个账号共用同一个会话或 IP，平台会通过设备指纹关联。我们后来做了账号隔离，每个账号独立 cookie、独立 UA，IP 通过代理池按需分配。

**第四个坑是 API 调用痕迹。** 很多平台 API 有固定顺序和 headers，和浏览器行为差异明显。我们的做法是优先通过 Playwright 驱动真实浏览器操作，而不是直接调私有 API；如果必须用 API，则尽量补全 headers 和必要的预热请求。

## 可复用建议

- 把所有节奏参数抽到配置文件：最小值、最大延迟、分布参数、每日上限、活跃时段。不要硬编码在代码里。
- 用结构化日志记录每次动作的开始时间、延迟、结果，方便事后回溯。定期导出一周日志，用脚本计算延迟分布，和真实用户数据对比。
- 先用小号在低风险社区跑 7-14 天，观察触发验证码的概率，再逐步放大。
- 不要把自动化和人工完全对立。每周保留 1-2 条纯手动发帖，或者让 Agent 生成草稿、人工确认后发布，能有效降低账号风险。
- 如果社区有 API 频率限制，注意和 Web 行为区分。API 调用频率可以高一些，但发布动作本身不能密集。

## 总结

社区自动发帖的节奏控制，本质上是在工程实现上模拟人类操作的自然分布，同时保证内容质量。它不是简单的“加个 sleep”，而是把发布流程拆解成可观测、可调节的状态机。做到这一点后，我们的账号稳定运行了两个多月，没有再触发风控。最后提醒一句：自动化是提效工具，不要用它去骚扰社区；节奏控制的目标是让工具隐形，让内容被看到。
