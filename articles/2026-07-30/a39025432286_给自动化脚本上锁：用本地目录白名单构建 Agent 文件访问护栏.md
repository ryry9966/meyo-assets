## 问题背景

当你的 Agent 开始执行文件操作，风险就来了。

玩过 OpenClaw、MCP 插件或自定义 Agent 自动化的朋友一定见过这种配置：

```yaml
tools:
  - file_write
  - file_read
  - shell
```

为了让 Agent 能干点实事，我们往往会给它开放文件读写能力。但开放之后，你可能很快会面临一个很现实的问题——这个货要是把 `~/.ssh/id_rsa` 给读了，或者往 `/etc/passwd` 里追加点什么，那乐子就大了。

即便你认为自己 prompt 已经写得足够严谨，也无法保证模型在幻觉或者复杂上下文下不会 “失手”。这时候，如果不在工具层面做约束，相当于让 Agent 裸奔在你的文件系统上。

这就是文件访问护栏的适用场景：不是禁用文件操作，而是**把文件操作限制在你指定的那些目录里**。

本文基于我最近给内部工具链中的一个 Python Agent 增加目录白名单的实际经历，分享如何用最直接的方式给自动化脚本套上文件访问的笼子，以及中间趟过的坑。

---

## 核心思路

不依赖任何外部安全框架，用约 120 行 Python 实现一个带目录白名单的 file access wrapper：将所有 Agent 工具调用的文件路径，先通过一个 `AccessGuard` 检查是否落在允许的路径列表中，再放行给真实的文件操作函数。

整体设计要点：

- 白名单由绝对路径目录组成，支持递归包含子目录。
- 路径名校验使用 `os.path.realpath` 处理符号链接穿越。
- 禁止通过 `..` 跳转到白名单之外。
- 同时覆盖读写、创建、删除操作，防止通过重命名/链接变相突破。

## 实现步骤

### 1. 定义白名单与防护类

```python
import os
from pathlib import Path
from typing import List, Union

class AccessGuard:
    """只允许在指定目录范围内进行文件操作"""

    def __init__(self, allowed_dirs: List[Union[str, Path]]):
        # 存储规范化后的目录路径
        self.allowed_dirs = [
            os.path.realpath(Path(d)) for d in allowed_dirs
        ]

    def _is_allowed(self, target: Path) -> bool:
        real_target = os.path.realpath(target)
        for allowed in self.allowed_dirs:
            try:
                # 目标路径是否是 allowed 的子路径
                real_target.relative_to(allowed)
                return True
            except ValueError:
                continue
        return False

    def validate(self, file_path: Union[str, Path]):
        if not self._is_allowed(Path(file_path)):
            raise PermissionError(
                f"Access to '{file_path}' is not allowed. "
                f"Allowed directories: {self.allowed_dirs}"
            )
```

要点：
- 使用 `os.path.realpath` 解决符号链接问题，避免用户在白名单目录内建一个指向 `/etc` 的软链来绕过检查。
- `relative_to` 若目标路径不以允许路径开头会抛出 `ValueError`，直接捕获返回 False。

### 2. 包装文件操作函数

针对 Agent 实际需要的文件操作，对 `open`、`os.remove`、`os.rename` 等做封装。

```python
import shutil

class GuardedFileOps:
    def __init__(self, guard: AccessGuard):
        self.guard = guard

    def read_text(self, path: str) -> str:
        self.guard.validate(path)
        return Path(path).read_text()

    def write_text(self, path: str, content: str):
        self.guard.validate(path)
        Path(path).write_text(content)

    def remove(self, path: str):
        self.guard.validate(path)
        os.remove(path)

    def rename(self, src: str, dst: str):
        self.guard.validate(src)
        self.guard.validate(dst)
        os.rename(src, dst)

    def copy(self, src: str, dst: str):
        self.guard.validate(src)
        self.guard.validate(dst)
        shutil.copy2(src, dst)
```

> 注意：`rename` 和 `copy` 必须同时对源和目标进行校验，否则白名单内的文件可以被移动到不受限区域，造成二次泄露。

### 3. 接入 Agent 工具调用

假设你的 Agent 原本直接通过 `open()` 写文件，现在统一改为先实例化 GuardedFileOps，然后在工具描述里调用封装后的方法。

```python
guard = AccessGuard(allowed_dirs=["/app/workspace", "/data/output"])
file_ops = GuardedFileOps(guard)

# 在 Agent 的工具定义中
def tool_write_file(path: str, content: str):
    file_ops.write_text(path, content)
    return "ok"
```

一旦 Agent 尝试写 `/app/workspace/../../../etc/hosts`，`validate` 会立即抛出异常，阻止实际 I/O 发生。

## 踩坑记录

### 坑1：相对路径变成当前工作目录的受害者

Agent 有时会生成类似 `output/result.txt` 的相对路径。如果你的工作目录在白名单外，`os.path.realpath` 之后该路径可能落在 `/home/user/output` 而非 `/data/output`，导致校验失败。

**解法：** 在 `validate` 前对相对路径按规则拼接一个基目录，通常在工具定义时限定基目录为白名单内的一个主工作区。

```python
def tool_write_file(path: str, content: str):
    if not os.path.isabs(path):
        path = os.path.join("/app/workspace", path)
    file_ops.write_text(path, content)
```

### 坑2：临时文件机制绕过校验

Agent 可能会通过写入临时文件，再重命名的方式覆盖目标文件。如果只在 `rename` 目标上做校验，但在临时文件阶段没管，可能让临时目录成为攻击面。

**解法：** 对 `tempfile` 相关操作同样接管，必须在允许目录内生成临时文件。

### 坑3：函数调用路径与 Agent 实际执行环境不一致

如果你在 Docker 容器内跑 Agent，本地白名单目录要确保挂载点正确。有时候容器内看到的路径与实际宿主机路径不同，会造成 `realpath` 解析后完全不在白名单内。

**解法：** 检查容器内 `realpath` 解析结果，确保白名单目录列表与解析后的一致。

## 可复用建议

1. **最小化白名单**  
   只给 Agent 开放必要的目录，比如一个纯净的项目 workspace 和只读的数据集目录。不要图省事把 `/home` 或 `/tmp` 加进去。

2. **读写权限分离**  
   如果业务允许，可以构造两个防护实例：一个只读 Guard（只允许 read 操作）、一个可写 Guard。让工具声明自己需要的权限等级。

3. **日志与监控**  
   当 `validate` 抛出 `PermissionError` 时，务必记录原始请求路径、时间、Agent 会话 ID。这些日志是发现模型越狱或 prompt injection 尝试的一手线索。

4. **测试用例要包含边界**  
   至少覆盖：
   - 绝对路径直接超越白名单
   - 符号链接指向外部
   - `../../../` 路径遍历
   - 文件重命名/拷贝的双方校验
   - 通过 NFS 挂载点访问非白名单路径（视环境而定）

5. **不要相信客户端的规范路径**  
   Agent 输出的路径永远是不可信的。就算你的 prompt 里写死了 `请只在 /workspace 下操作`，文件操作 API 还是必须再做一次强制校验。

---

## 总结

这套基于目录白名单的文件访问护栏，实现量非常小，但实际拦截效果很好。它不依赖任何复杂的 IAM 或内核级 MAC 机制，适合在 Agent 工具调用链的最后一环直接内嵌。

在大模型普遍拥有文件能力且行为不可完全预测的前提下，与其通过 prompt 画线，不如用代码筑墙。毕竟，prompt 是给模型看的，护栏是给模型犯错时兜底的。
