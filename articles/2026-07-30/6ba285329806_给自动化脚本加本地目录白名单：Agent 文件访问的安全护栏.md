## 背景：当 Agent 开始动你的文件系统

在 OpenClaw 生态里，Agent 通过 MCP 或自定义插件获得文件读写能力已越来越普遍。常见场景包括：用脚本批量整理下载文件夹、让 Agent 帮你重命名一组 markdown 文档、或者通过自动化工具定期导出数据到指定目录。

问题是，这些操作一旦“越界”——比如遍历到系统目录、误删配置文件、或者读走敏感 dotfiles——代价就远大于便利。即使是我们自己写的脚本，在逻辑 bug 或路径拼接错误下也很容易写出范围。更何况，当你把一个文件操作能力暴露给远端 MCP 服务器或者一个能生成代码的 Agent，信任边界会变得更模糊。

所以我们需要一个工程上可落地的方案：**给文件访问加白名单护栏**——只允许操作明确指定的目录，其他路径一律拒绝，哪怕代码写错了也不会越界。

## 问题的本质：路径检查远比看起来脆弱

最简单的想法是：在操作前判断路径是否以白名单目录开头。类似 `path.startswith('/allowed')`。但这几乎没有防护作用：

- `../` 路径穿越：`/allowed/../etc/passwd` 会被直接放行。
- 符号链接绕路：白名单目录下放置一个指向 `/etc` 的符号链接，瞬间打破边界。
- 相对路径解析：当前工作目录不同，同样的相对路径可能解析到意料之外的地方。
- 大小写不敏感文件系统（macOS/Windows）下，`/ALLOWED/secret` 可能与白名单匹配不一致。
- 路径规范化差异：`/allowed/subdir/../secret` 真实指向 `/allowed/secret`，虽然合法，但可能不是你想要暴露的。

更隐蔽的是，某些库（比如 `pathlib.Path.resolve()`）在处理不存在的路径时行为不一，可能返回含 `..` 的未解析路径，也可能抛异常，这又给检查逻辑埋坑。

## 做法：一个健壮的路径白名单校验器

下面的实现核心思路：**始终将待检查路径彻底解析为真实绝对路径**，再与同样解析后的白名单目录做前缀匹配。在此之上，强制要求目标路径已经存在（针对读取操作），或父目录已存在（针对写入操作），防止通过伪造未解析路径绕过检查。

```python
import os
from pathlib import Path
from typing import List, Union

class FilesystemGuard:
    """
    文件访问护栏，限定操作必须在白名单目录内。
    """
    def __init__(self, allowed_dirs: List[Union[str, Path]]):
        # 存储已解析的真实路径
        self.allowed_real = set()
        for d in allowed_dirs:
            self.allowed_real.add(self._realpath(d))

    @staticmethod
    def _realpath(path: Union[str, Path]) -> Path:
        """包装 realpath，统一返回 Path"""
        return Path(os.path.realpath(str(path)))

    def validate(self, target: Union[str, Path], must_exist: bool = False) -> Path:
        """
        验证目标路径是否在白名单内。
        - 如果 must_exist=True，要求路径存在，否则拒绝。
        - 如果路径不存在，将校验其父目录。
        返回解析后的安全路径。
        """
        target = Path(target)
        # 先尝试解析真实路径，若不存在则使用其父目录解析
        resolved_parent = self._realpath(target.parent)
        # 构造预期完整真实路径（规范化但不要求存在）
        candidate = (resolved_parent / target.name).resolve()

        # 检查是否在任何白名单目录下
        for allowed in self.allowed_real:
            try:
                # 使用 relative_to 验证前缀关系，不抛异常即通过
                candidate.relative_to(allowed)
            except ValueError:
                continue
            else:
                # 如果要求路径存在，但实际不存在，拒绝
                if must_exist and not candidate.exists():
                    raise PermissionError(
                        f"Required path {candidate} does not exist"
                    )
                return candidate
        raise PermissionError(
            f"Access to {candidate} denied: not under allowed directories"
        )
```

使用时，将 Guard 注入到文件操作工具函数中：

```python
guard = FilesystemGuard(allowed_dirs=['/home/user/project/data', '/tmp/agent_workspace'])

def safe_read(filepath: str) -> str:
    safe_path = guard.validate(filepath, must_exist=True)
    return safe_path.read_text()

def safe_write(filepath: str, content: str):
    safe_path = guard.validate(filepath, must_exist=False)
    safe_path.parent.mkdir(parents=True, exist_ok=True)
    safe_path.write_text(content)
```

这样，任何越界操作都会在 I/O 之前被拦截，抛出的 `PermissionError` 可供上层捕获并记录，而不会直接将异常路径透传给磁盘。

## 踩坑实录

1. **符号链接陷阱**：`os.path.realpath` 会跟随符号链接，这意味着白名单目录本身就不能是符号链接，否则真实路径可能不在白名单中。如果必须支持符号链接，可改用 `Path.resolve()` 并小心处理挂载点，但更安全的做法是要求管理员提供链路终点路径。

2. **并发与 TOCTOU**：校验和实际文件操作之间存在微小时间窗口，但护栏的主要目的是防止代码逻辑错误和显式攻击，而非内核级 race condition。若极端场景需要原子性，可以结合 `os.open` 的 `O_NOFOLLOW` 等标志，但这会提升复杂度。

3. **Windows 兼容性**：`os.path.realpath` 在 Windows 上不区分大小写，但盘符可能是大写或小写，标准化建议统一使用 `str(Path).lower()` 进行额外对比，或使用 `os.path.normcase`。

4. **临时目录膨胀**：白名单中加入 `/tmp` 后，可能误将 Agent 缓存、其他用户文件暴露。建议更精确地指定 `/tmp/agent-{uid}` 形式，并利用环境变量隔离。

5. **MCP 文件系统服务器的默认范围**：许多 MCP filesystem server 允许通过配置参数指定允许目录，但它们内部实现未必严格做了上述校验。如果自行封装，务必在服务器层面就接入 Guard，而不是依赖 Agent 自觉。

## 可复用建议

- **抽象为装饰器或上下文管理器**：对批量脚本，用 `@guard.require()` 装饰函数，或 `with guard.scope():` 上下文，能减少遗漏。
- **配置外置**：将白名单目录放在 `.env` 或 YAML 里，与项目绑定，随代码仓库分发。
- **与日志/审计打通**：在 deny 时记录完整的请求路径、调用栈信息，方便快速定位是哪个 Agent 动作越界。
- **集成到插件开发模板**：如果你在 OpenClaw 中开发自定义工具，可以把 Guard 作为工具函数的“前置中间件”，降低社区贡献者误伤用户文件系统的风险。
- **测试用例**：针对符号链接、路径穿越、特殊字符、不存在的父目录等场景编写单元测试。像 `/dev/null`、`/proc/self/fd` 这类特殊文件也应被白名单排除，除非明确需要。

## 总结

用简单的路径前缀判断做文件访问控制，几乎等同于没有防护。工程上可行的方案必须基于真实路径解析与严格前缀匹配，并充分考虑符号链接、路径不存在等边界条件。在此基础上，将校验逻辑封装为可复用的 Guard，再注入到任何与文件系统交互的自动化脚本或 MCP 工具中，就能在不牺牲易用性的前提下，大幅降低 Agent “走错路”引发的故障。

在 OpenClaw 生态逐步拥抱高度自动化时，这种护栏不是过度设计，而是让自动化跑得放心的一项必要基础设施。
