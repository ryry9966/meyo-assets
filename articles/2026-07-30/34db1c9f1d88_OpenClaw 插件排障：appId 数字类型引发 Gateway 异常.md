## 背景

OpenClaw 插件通过统一的 API Gateway 完成认证与路由，`appId` 是其中最基础的租户识别字段。在一次数据源插件开发中，我在配置文件里顺手写了一个纯数字的 `appId`，例如：

```yaml
appId: 123456
```

原本以为只是一个简单的身份标识，结果插件运行后所有通过 Gateway 的请求都返回 `400`，并附带回一句毫无感情的报错：

```json
{"error":"invalid_request","message":"appId must be a string"}
```

这个排障过程很短，但背后暴露出的类型安全意识缺失，对 OpenClaw 插件开发者来说很有复盘价值。

## 问题表现

插件启动时没有抛出异常，健康检查也通过，唯独当实际操作触发对外部服务的请求时，Gateway 统一返回 `400`。日志中看到的原始请求 payload 大致如下：

```json
{
  "appId": 123456,
  "action": "query",
  "params": { ... }
}
```

而正常通过的请求体，`appId` 外层必须是双引号包裹的字符串 `"123456"`。显然，纯数字的 `appId` 被序列化为了 JSON 的 `number` 类型，而 Gateway 的 schema 校验要求必须是 `string`。

## 排障步骤

### 1. 确认 Gateway 侧契约
查阅 Gateway 文档（或 OpenAPI 定义），发现 `appId` 字段的类型定义为 `string`，且描述里明确写了 “租户标识，仅接受字符串”。Gateway 的请求校验模块会在解析 JSON 后使用 JSON Schema 或类似机制进行类型校验，一旦发现 type 不匹配，直接拒绝。

### 2. 抓取实际请求体
在插件侧开启 debug 日志，打印发送给 Gateway 的完整 body。使用 `curl` 重放相同请求，确认问题稳定复现。

### 3. 回溯 appId 的来源
appId 从 YAML 配置文件读取，使用了 `js-yaml` 的 `load()` 方法。在 Node.js 环境中，YAML 解析器会将不带引号的纯数字自动转为 `number`，而 `123456` 正是如此。这导致插件内存中持有的 `appId` 就是数字类型。

### 4. 修复与验证
有两种修复方式：
- **配置层面**：在 YAML 中给 appId 加引号，`appId: "123456"`。
- **代码层面**：读取配置后显式转换为字符串，`const appId = String(config.appId);`。

我选择了双管齐下：配置侧增加引号，代码侧增加防御性转换并记录一条 warning 日志，提示“appId 应为字符串，已自动转换”。重新部署后请求恢复正常。

## 踩坑点

这个排障过程中有几点容易被忽视：

1. **YAML 的隐性类型推断**：`1.0` 变浮点数、`yes` 变布尔值、纯数字变 number，这些都是 YAML 规范的一部分，容易被开发者忽略。特别是当配置文件由非技术人员维护时，更容易写出不带引号的数字。
2. **Gateway 的严格类型检查**：很多网关或 API 服务并不会自动将 `123456` 转换为 `"123456"`，符合 OpenAPI/JSON Schema 的严格模式会要求类型完全一致。而 Gateway 返回的错误信息可能比较泛化，不一定直接指向“类型错误”，容易误导排查方向。
3. **静默的类型不安全**：如果使用的是 TypeScript，但配置文件解析结果被声明为 `any` 或笼统的 `Record<string, unknown>`，类型检查在编译期不会报警，问题只会在运行时暴露。
4. **测试覆盖不足**：单元测试可能只验证了业务逻辑，没有用真实的 Gateway 契约进行集成测试，导致这类类型问题溜到联调阶段才发现。

## 可复用建议

对于 OpenClaw 插件开发者，无论你使用的是 TypeScript 还是 Python，以下几个原则可以大幅减少此类类型事故：

1. **标识类字段强制使用字符串**：无论读取自配置文件、环境变量还是数据库，`appId`、`userId`、`tenantId` 等标识都统一转为字符串。可以在工具函数中封装 `getAppId()`，内部做 `String()` 转换并记录警告。
2. **接入 JSON Schema 校验配置**：在插件加载配置后，立即使用 ajv 等库校验整个配置对象，确保 `appId` 的类型为 `string`，并给出友好错误提示。这比依赖 Gateway 的远端校验反馈更快、更清晰。
3. **启用 TypeScript 严格模式，并精细定义配置类型**：避免使用 `any`。定义类似 `AppConfig { appId: string }` 的接口，解析 YAML 后通过类型守卫或 zod/yup 进行运行时断言。
4. **在 Gateway 侧返回可调试的错误**：如果你是 Gateway 的维护者，可以在校验失败时返回更具体的错误，如 `“appId: expected string, got number”`，并包含请求体中的实际类型，帮助调用方快速定位。
5. **集成测试里包含类型边界用例**：针对插件的 Gateway 调用层，编写测试时覆盖 `appId` 为数字、null、超长字符串等异常输入，确保报错清晰可识，而不是抛出 500 内部错误。

## 总结

`appId` 的类型问题看似微小，但暴露了从配置读取、内存传递到网络序列化整个链路中多个环节的类型契约漏洞。在自动化实践中，Gateway 就是契约的守门人，插件开发必须尊重其接口定义的类型。工程化的意义不在于写出花哨的算法，而在于让这些隐式转换不再成为排查一小时起跳的“幽灵 bug”。下一次，不管是 `appId` 还是其他标识，养成“标识一律是字符串”的肌肉记忆，往往比事后加十个断言更实在。
