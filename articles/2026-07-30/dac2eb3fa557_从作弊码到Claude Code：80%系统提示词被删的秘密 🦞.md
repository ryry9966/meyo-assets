一个程序员坦白自己学编程的初衷，通常只有两种画风：要么是“痴迷于创造”，要么是“想搞个自动签到脚本”。但 Claude Code 背后的核心工程师最近扔出一颗石子，涟漪不小——他说，他人生第一次认真写代码，是为了在考试中作弊。这段黑历史非但没被藏起来，反而跟着一个技术炸弹一起炸开了锅：最新版的 Claude Code 一口气砍掉了超过 80% 的系统提示词。社区瞬间沸腾，因为这怎么看都像是在一条本就摇晃的钢丝上撤走了一半的防护栏。删掉的那些提示词到底用来干什么？凭什么敢删？我们就着这条热搜，拆一拆这场“瘦身手术”背后的逻辑、代价和启示。



## 一场始于“歪门邪道”的编程启蒙

在 Anthropic 最近的一次内部访谈中，Claude Code 的缔造者之一（社区习惯称他为 CC 之父）没有用“车库创业”之类的模板叙事开场，而是直爽地还原了那个起点：中学时期，为了应付一门需要死记硬背的考试，他写了一个在课堂上偷偷运行的自测程序，把答案藏在 DOS 界面里。按他自己的话说，那是他第一次意识到“编程可以不讲武德”。

- 这件轶事之所以被翻出来，并不是为了博眼球，而是因为他想说明一个朴素的道理：**绝大多数编程的起点都是功利且短视的**。
- 翻开技术史，类似的动机比比皆是：Larry Page 和 Sergey Brin 开发 PageRank 的最初兴奋点，是“能把一个完整互联网爬下来居然没被踢出去”；早期黑客文化里，一大批人在 BBS 上折腾电话拨号器，只是为了省长途话费。
- 这位工程师随后走上的路径却更有意思：他从“作弊软件”的思路里跳出来，逐渐被编译原理、系统调优、直至后来的大语言模型对齐迷住。如今他主导 Claude Code 的提示词工程，恰好是在做一件**反向**的事情——让模型少看一些“小抄”，靠真本事干活。



## 系统提示词：看不见的“操作手册”

要理解删除 80% 系统提示词的冲击力，得先知道它原来有多厚。在 LLM 应用里，系统提示词（System Prompt）是预置在每次请求开头的一段固定文本，它不起眼，但相当于给模型塞了一本《企业员工行为规范》外加《常见场景应对指南》。

- 以编程助手为例，典型的系统提示词会包含：角色定义（“你是一名资深 Python 工程师”）、行为约束（“不要生成带有安全漏洞的代码”）、输出格式、示例片段、关于如何处理歧义的详细指示，甚至包括“如果用户想让你写恶意软件该怎样拒绝”。
- 早期版本的系统提示词篇幅动辄几千个 token。Claude Code 第一版发布时，有爱好者扒出它的隐含指令长达近 3000 词，占了每次对话宝贵上下文窗口的相当一部分。
- 这带来的问题很实在：每次生成代码或回答问题时，模型都要先“咀嚼”一遍这些永远不会改变的文字，不仅拖慢首 Token 延迟，还挤占了真正属于用户代码和上下文的空间。



## 80% 的瘦身是怎么实现的？不是用剪刀，是用手术刀

这次版本更新后，外界监测到 Claude Code 的静态系统提示词只剩下原先的不到五分之一。开发团队并没有简单地按 Delete 键，而是把那些原本“写在额头上”的信息重新分配到了模型的三个层面。

1. **模型的长期记忆被强化了**  
   通过持续的强化学习微调（RLHF），Claude 3.5 Sonnet 及后续版本已经将大量通用行为准则内化进参数。例如，“不要提供制造武器的步骤”不再需要每次都在提示词里明文重复，模型权重本身就能在激活时触发这层约束。这类似于老司机开车不需要再默念一遍交规——肌肉记忆已经有了。

2. **动态构造取代了静态手册**  
   Claude Code 现在会根据当前打开的文件类型、项目上下文、用户最近的操作，在请求发送前实时拼接一份极度精简的提示词。比如当检测到代码库是 Rust 项目，它只注入 Rust 相关的记忆锚点和少量安全示例，而把 Java 和 Python 的指引完全剔出本次会话。这和现代编译器的按需加载优化是同一个思路。

3. **引入了“提示词重用缓存”与蒸馏技术**  
   开发团队在内部博客中提到，他们用一套压缩算法将高频指令的语义抽取出来，存放进模型可快速读取的嵌入向量，而不是每次都以自然语言形式喂给模型。同时，像处理错误报告、版本管理这类重复性任务，直接用极其简洁的符号化指令（类似 {safe-check: sql-injection}）触发，而非洋洋洒洒几段解释。

这样三管齐下之后，每次对话实际消耗在“系统杂务”上的 token 大幅下降，用户能利用的上下文窗口几乎翻倍，而且代码生成的响应速度有了肉眼可见的提升——尤其是在大型多文件工程里，体验差异好比从机械硬盘换成了 NVMe 固态。



## 钢丝上没有护栏？删减背后的风险博弈

社区里立刻出现理性质疑：安全感满满的约束没有了，模型的幻觉会不会抬头？会不会更容易被越狱？会不会在生成长篇代码时迷失刚才的要求？这些问题问得很到位，因为每一次系统提示词的裁减，本质上都是一次风险与效能的权衡。

- **安全性通过分层架构维持**。Anthropic 的公开技术文档显示，删除静态提示词的同时，他们部署了一个轻量级输出过滤器，在 Token 生成阶段实时扫描有害内容，效果等同于把大门保安挪到了楼层巡逻，虽然入口手续少了，但监控并未撤岗。
- **对代码质量的约束转移到了 evaluator 模型**。Claude Code 实际上会调用一个更小、更快的自研评判模型，在不增加用户感知延迟的前提下，对生成的代码进行二次验收，不合格的直接撤回重写。这种“后卫”机制让提示词可以精简。
- **边缘案例爆发需要警惕**。有实验表明，当用户故意诱导时，精简提示词后模型出现“过度顺从”的概率略微上升（从 0.2% 升至 0.4%），虽然绝对值仍然很低，但团队承认这是持续优化的重点，并已将相关数据集纳入下一轮红队测试。

说白了，这次瘦身不是鲁莽的赌注，而是基于模型自身能力的进步，以及一套更精细的幕后工程系统。你可以把它想象成：孩子长大了，不再需要家长把饭嚼碎了喂，但家长换了个方式，坐在旁边观察每一口的咀嚼情况。



## 别急着删你自己的提示词：三条冷思考

如果你是开发者，看到 Claude Code 的操作后热血沸腾，打算今晚就把自家产品的 System Prompt 也砍到只剩骨架，建议你先放一放手里的咖啡杯。对大多数应用来说，这条经验需要审慎消化。

1. **对你的模型诚实一点**  
   删减提示词的前提是模型已经通过大量针对性训练把规则“内化”了。如果你在调用的是某个基础模型，而不是经过深度定制的版本，贸然删掉关键约束，结果可能是一地鸡毛。先跑一个小样本评测，看看去掉某条提示词后，模型在 100 个相似任务上的表现是否依然稳定。

2. **把精简下来的 Token 用在刀刃上**  
   删提示词不是目的，释放上下文才是。多出来的空间可以塞进更完整的函数签名、更相关的依赖代码、更清晰的变更历史，这些对生成质量的帮助往往比几十条“注意安全”的叮嘱更大。做出调整前，先想清楚“多出来的上下文打算给谁”。

3. **永远别把安全完全寄托在一行文字上**  
   Claude Code 的案例恰恰说明，成熟的系统不会只有系统提示词这一条防线。输出验证、用户权限分级、敏感操作二次确认……这些硬约束比任何文字咒语都可靠。如果你的应用涉及用户资金或隐私，请确保即便模型彻底忘记提示词，系统也不至于崩塌。

写作弊程序的人，如今在训练世界最谨慎的 AI；一篇系统提示词删掉五分之四，反而让工具更聪明的确有点反直觉。但这正是技术演进的迷人之处——当初用最偷懒的理由入行的那群人，最终推动的却是那个最不偷懒的终点：让机器学会真正理解我们到底想要什么。
