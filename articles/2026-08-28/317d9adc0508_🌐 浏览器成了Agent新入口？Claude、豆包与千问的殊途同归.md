AI 助手正在从“动嘴”变成“动手”。Claude 终于把浏览器塞进对话框，豆包工作流早把网页操作做成标准节点，千问系列也绕不开这个方向。与其说谁抄谁，不如说浏览器正在成为所有 Agent 的公共基础设施。过去用户问 AI“帮我查一下”，现在可以问“帮我去后台导出订单，再填到物流表格里”。这一步跨出去，竞争的底层逻辑就变了。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/2e83c96159f37266.png)

## 一、Claude 这一步补上了什么

很多用户对“AI 联网”的印象还停留在搜索增强：模型把问题转成搜索词，抓几条摘要塞进上下文。这次 Claude 的内置浏览器不是这个量级。

1. **从“搜索”到“浏览”**：内置浏览器意味着模型可以打开具体页面、读取正文、在页面内跳转，甚至执行点击、输入、提交等操作。它不再只是“听说网页”，而是“走进网页”。

2. **与 RPA 的区别**：传统 RPA 靠录制固定流程，元素一变就崩。LLM 驱动的浏览器操作可以理解自然语言指令，比如“去后台导出近 7 天订单，再打开物流平台批量查询”，遇到弹窗或布局微调也能自己尝试绕过。

3. **Claude 的底气**：Anthropic 之前已经通过 Computer Use 放出过截图和像素坐标操作电脑的能力。浏览器工具有更结构化的 DOM 树，比像素级操作更省 token，也更容易判断“当前点的是什么”。这一步更像是把通用能力收窄到一个高频、刚需的场景里。

## 二、豆包“工作”早怎么干的

字节系在浏览器自动化上走得非常“产品化”。豆包电脑版和扣子工作流里，网页操作早不是黑科技，而是模块。

- **节点式编排**：扣子（Coze）把“打开网页”“读取网页”“点击元素”“填写表单”做成可视化节点，用户可以像搭积木一样串成一条工作流。豆包电脑版把这套能力藏进更傻瓜的对话入口，用户只说“帮我比价”“帮我填周报数据”，后面是同一套浏览器执行引擎。

- **场景优先**：字节的打法不是先做“通用 Agent”，而是从办公、内容处理、电商比价等高频场景切进去。场景越具体，容错要求越高，但用户感知也越强。比如“打开某个后台，抓取昨日投放消耗，写入飞书多维表格”，在字节生态里可以做成一条半自动化流水线。

- **生态协同**：浏览器操作和飞书、抖音电商、巨量引擎等系统天然接得上。一个工作流可以同时读取网页和内部文档，这比单点浏览器工具更有商业想象力。浏览器在这里不是功能，而是连接器。

千问们也没闲着。Qwen 系列在工具调用、代码执行、多模态理解上持续加码，部分发布里明确提到手机与电脑操作能力。各家实现路径不同，但目标一致：让模型能像人一样使用软件。

## 三、为什么浏览器成了必争之地

核心原因很朴素：Web 是今天最大的、无需开放 API 的“接口集合”。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/7f0b4484da87c80d.png)

1. **Web 是最通用的环境**：几乎所有企业服务都有网页版。浏览器操作能覆盖大量没有 API、或 API 申请门槛高的系统。对 Agent 来说，会操作浏览器，等于拥有了一个庞大的“可执行函数库”。

2. **数据飞轮的价值**：模型在浏览器里执行任务，每一步点击、停留、重试都会成为高质量过程数据。谁能积累更多“真实网页操作轨迹”，谁就能更快训练出更稳的 Agent。这在强化学习和过程监督里极有价值。

3. **从对话到交付**：用户要的不是“建议”，而是“结果”。浏览器的加入让 AI 第一次具备完整的“输入-操作-输出”闭环。没有执行能力，再聪明的对话也只是顾问。

4. **安全边界成为产品壁垒**：浏览器操作天然涉及账号、支付、隐私。谁能把“让模型干活”和“不让模型乱来”之间的平衡做好，谁就能建立信任。这里的技术点包括沙箱环境、敏感操作人工确认、权限最小化、可回放审计等。

## 四、现实差距：内置不等于好用

别把“内置浏览器”想成科幻片。实际体验中，还有三个硬指标。

- **成功率**：长链路任务里，任何一步点击失败或页面加载慢都可能让整个流程中断。模型的“鲁棒性”比“能打开网页”重要得多。当前各家在简单搜索、单页读取上表现不错，但在跨站、登录、验证码、复杂表单场景下仍有明显折损。

- **成本**：一次多步浏览器任务可能消耗几十到几百次模型调用。深度推理模型每一步都要“看页面、想下一步”，token 消耗惊人。对开发者来说，自动化收益必须大于推理成本，否则只能做低频任务。

- **安全与信任**：漏洞风险、误操作、数据泄露。浏览器 Agent 往往需要用户登录态，一旦被提示词注入攻击诱导执行错误操作，损失比聊天胡说严重得多。可靠的确认机制和只读优先原则，比功能炫技更关键。

## 五、给普通用户和开发者的三条建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/598ef5f3665f276b.png)

1. **把浏览器 Agent 当实习生，别当资深员工**：第一周只让它干只读、低风险、可验证的活，比如查资料、提取列表、比价。等到你摸清它在哪些网站容易翻车，再逐渐放开填表、提交等写操作。

2. **敏感操作永远保留最后一棒**：支付、删除、群发、发布这类动作，至少设置人工确认。权限上能用子账号就用子账号，能给只读 view 就不要给 admin。真出问题，可回放日志比“我明明没点”有用得多。

3. **小任务先跑通，再拼长流程**：不要把十步任务一次性交给 Agent。先拆成两三个短流程，单独验证成功率。短流程稳定了，再考虑编排。这样既省 token，也更容易定位是哪一步在“说谎”。

浏览器能力不是万能药，也不是新鲜概念。它更像一条把大语言模型从“聊天框”拖进“真实工作台”的传送带。谁能把传送带修得更稳、更安全、更便宜，谁才能在下一轮 Agent 竞争中站住脚。
