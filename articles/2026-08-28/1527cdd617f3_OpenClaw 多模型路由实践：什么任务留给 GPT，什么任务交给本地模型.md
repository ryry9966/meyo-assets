## 背景

OpenClaw 接入多模型之后，很容易出现两个极端：一种是所有请求都打给 GPT，成本高、延迟不稳，简单任务也要等云端返回；另一种是本地模型硬扛复杂推理、工具编排，结果在 agent loop 里反复失败。多模型路由不是“谁更强就选谁”，而是给每类任务找到成本、延迟、隐私和能力都能接受的下限。

在 OpenClaw 的 Agent/MCP/插件链路里，路由点通常放在任务进入 agent loop 之前。现在比较可行的做法是：用一个轻量 pre-router 先做意图识别和标签判断，再决定走本地、云端还是混合路径。

## 问题

如果不做路由，实际工程里最常见的三类问题：

1. **成本与延迟失控**：大量可本地完成的分类、摘要、格式转换任务占用云端额度，并发时首 token 延迟明显。
2. **隐私边界模糊**：带用户文件名、目录结构、内部配置的 prompt 直接发到云端，事后才发现敏感信息外发。
3. **本地模型能力越界**：把多步规划、跨文档推理、多工具协同交给本地小模型，结果工具调用格式错误、上下文截断后漏掉关键信息。

这些问题不是换一个更强模型能解决的，需要一层稳定的路由策略。

## 做法 / 步骤

### 1. 给请求打标签

在 OpenClaw 入口加一个轻量 pre-router，建议让本地小模型输出结构化 JSON，字段控制在 4-6 个：

```json
{
  "task_type": "summary",
  "sensitivity": "low",
  "need_tools": false,
  "max_latency_ms": 1500,
  "min_context_tokens": 2000
}
```

这个 JSON 不落盘，仅用于路由。标签空间不要太大，4-6 类足够，否则本地小模型容易分错。

### 2. 定义路由规则

可以先从 3 条规则起步：

- **本地直接执行**：文本清洗、短文本分类、摘要、格式转换、正则类提取、本地代码补全、简单 JSON 结构化输出。
- **云端执行**：多步 agent 规划、跨段落/跨文档推理、需要联网搜索或浏览器操作、工具数量超过 5 个的复杂编排、高质量长文生成。
- **混合执行**：本地生成初稿，GPT 修编；或 GPT 做规划，子任务交本地模型执行。

### 3. 设置降级链路

路由不是一次判定就结束。建议在 OpenClaw 里配置：

- 本地模型超时、输出格式错误、工具调用连续失败时，回退到 GPT。
- GPT 限流、超预算或返回错误时，回退到本地小模型做降级输出，并标记 `degraded=true`，便于后续统计。

## 踩坑点

1. **本地模型工具调用不稳**。不是所有本地模型都适合 function calling。如果 MCP 工具数量多，本地模型容易乱选工具。建议缩短工具描述，或者把工具选择交给云端，本地只做无工具任务和单工具任务。
2. **上下文窗口小导致漏信息**。本地 8k/32k 窗口很常见，长输入直接截断会丢关键约束。路由前用字符数估算 token，超过本地窗口 70% 就走云端或先做分块。
3. **不要只靠关键词做隐私检测**。用户文件内容、路径、内部配置容易漏判。更稳的策略是：默认带用户文件内容的任务不进云端，除非已完成本地脱敏或用户显式允许。
4. **路由规则过重**。一开始就上十几条规则很难维护，调试成本高。建议从 3-5 条规则起步，稳定后再增补。
5. **不要在每个 tool round 里反复切模型**。同一 agent loop 内频繁切换会导致上下文割裂，工具调用状态混乱。路由应尽量在任务入口一次决定。

## 可复用建议

- **保留 override 参数**：`force=local` 或 `force=gpt`，调试和线上干预都很实用。
- **记录路由日志**：`router_decision`、`fallback_count`、`latency_ms`、`cost_est`、`task_type` 这些字段要落日志，便于统计每个分支的成功率和成本。
- **维护回归集**：准备 20-50 条 golden cases，覆盖复杂推理、工具调用、结构化输出、隐私拒答，路由规则调整后先跑回归。
- **云端和本地分别调 prompt**：同一个 system prompt 在不同模型上表现差异很大，不要共用一套模板。
- **用环境变量控制阈值**：比如本地超时时间、上下文 token 上限、是否允许云端回退，方便 A/B 测试，不用改代码。

## 总结

OpenClaw 的多模型路由本质上是“用最小成本达到任务下限”，而不是“选出最强模型”。先把任务标签和降级链路搭起来，再根据线上日志逐步调整规则。工程上真正有用的路由往往很朴素：本地能扛住的别上云，敏感数据默认不过边界，复杂任务允许花更多成本换稳定性。规则先简单，后演进，比一开始就追求完美路由更实际。
