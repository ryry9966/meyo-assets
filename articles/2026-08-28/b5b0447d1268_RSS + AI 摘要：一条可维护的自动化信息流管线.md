## 背景

OpenClaw / Agent 场景里，信息输入质量往往比模型调用次数更关键。RSS 是成本最低的信源之一，但原始条目噪音大、格式杂，直接喂给 Agent 只会增加幻觉和误判。最近我把日常信息源改成“RSS + AI 摘要”管线，核心不是“接个模型”，而是把抓取、摘要、去重、推送拆开，让每一段都可重试、可观测、可替换。

## 问题

实际搭建时会遇到几个工程问题：

- 很多 feed 只有标题或截断摘要，直接给 AI 容易编内容。
- 模型输出不稳定，JSON 不合法、摘要长度失控。
- 推送重复：同一篇文章因为 URL 参数、标题标点变化而被推多次。
- 故障难排查：抓取失败、摘要失败、推送失败混在一起，日志不清晰。

## 做法 / 步骤

### 1. 用 Miniflux 或 RSSHub 统一源入口

建议自建 Miniflux，好处是它有清晰的 API、过滤规则和已读/未读状态。RSSHub 负责把不提供 RSS 的站点转成 feed。源配置建议用 YAML，方便启停和维护：

```yaml
feeds:
  - url: https://rsshub.example/github/trending
    tags: [dev, trending]
    enabled: true
    prompt: summarize_tech
  - url: https://example.com/blog/feed
    tags: [blog]
    enabled: true
    prompt: summarize_brief
```

### 2. 正文提取

对只有摘要的条目，用 trafilatura 或 readability 抓正文。必须设置超时、UA、最大长度，抓取失败时降级使用原摘要，不要中断整条管线。

```python
from trafilatura import extract

def get_content(url, fallback_summary: str) -> str:
    try:
        downloaded = fetch(url, timeout=8, user_agent="Mozilla/5.0 ...")
        text = extract(downloaded)
        return text[:4000] if text else fallback_summary
    except Exception:
        return fallback_summary
```

### 3. AI 摘要用固定 schema

不要只写一句“帮我总结”，要要求模型只输出 JSON，并限制字段和摘要长度。这样可以做后续过滤、评分和路由。建议低温、限 token、逐条处理；批量可以省钱，但失败会扩散。

```json
{
  "summary": "不超过60字的中文摘要",
  "keywords": ["a", "b"],
  "score": 1,
  "skip": false
}
```

解析时剥掉可能的 markdown fence，再用 `json.loads`，失败重试一次。结构稳定后，推送端只需判断 `skip` 和 `score`。

### 4. 状态与去重

用 Redis 存 normalized URL hash，TTL 30 天。不要只用标题 hash，标题中的标点、大小写变化会造成重复。更稳的是用 Miniflux 的 entry id，或者把 URL 的 query 参数排序后再 hash。

Miniflux 本身支持已读/未读状态，处理完才标记已读；失败条目保留未读，下轮重试。

### 5. OpenClaw 集成

我更倾向把摘要能力封装成 MCP tool，而不是在 plugin 里写死 HTTP 调用。例如定义一个 `summarize_entry(url, title, content)`，OpenClaw 需要时调用，而不是全量推送。推送端可以用 Telegram、飞书或 bark，只发摘要、原文链接和关键词。

定时任务每 10 分钟拉取一次未读条目即可，不必追求实时。管线结构大致是：

Miniflux → 正文提取 → AI 摘要 → schema 校验 → 去重 → 推送 / 更新状态

## 踩坑点

- **摘要幻觉**：短内容不要强制总结，直接返回标题或首段即可；给模型的内容要截断到合理长度。
- **JSON 输出不稳定**：部分模型会输出 markdown fence 或多余解释，解析前先做正则剥离，失败回退为纯文本截断。
- **反爬导致正文丢失**：不要过度依赖全文抓取，抓取失败就保留原始摘要，至少保证管线不断。
- **推送频率失控**：做冷却时间和时间窗口合并，避免一个突发 feed 刷屏。
- **只在本地测试成功**：真正的问题是长期运行后的状态错乱，定时跑几十轮才能暴露。

## 可复用建议

- 配置驱动：feed 列表、提示词模板、推送目标、冷却时间全部放配置文件，不要改代码。
- 把摘要模块做成独立 tool，方便在 OpenClaw 的多个任务里复用。
- 永远保留原文链接，AI 摘要只是入口，不能替代原文。
- 加基础监控：错误率、处理延迟、每日推送数，超过阈值通知管理端。

## 总结

这条管线不复杂，真正重要的是状态、去重和摘要约束。AI 只负责压缩信息，稳定性靠工程兜底。把 RSS 抓取和 AI 摘要解耦后，OpenClaw 只是调度和通知层，后续换模型、换推送渠道都不会伤筋动骨。
