## 背景

在 OpenClaw 的自动化工作流里，让 Agent 直接产出 Markdown 已经非常普遍。无论是日报、周报、技术笔记，还是从 API 抓取后汇总的内容，Agent 输出的第一版通常是 Markdown。但一旦要把这些内容发到公众号、知乎、掘金、GitHub 或 Notion，问题就来了：同一个 .md 文件在不同平台的渲染结果差别很大。

我们最初的做法是让 Agent 针对每个平台单独生成一份文本。结果维护成本很高，同一个内容要写多套 prompt，还容易出现信息漂移。后来改成了“一份源 Markdown + 一层适配管线”，稳定性明显提升。

## 问题

AI 生成的 Markdown 常见问题不是语法错误，而是“过于灵活”。比如：

- 代码块语言标注缺失或不统一：```python 和 ```Python 在某些平台会被当成纯文本。
- 表格宽度和对齐标记不完整，微信、知乎容易塌。
- 图片链接使用临时 URL 或相对路径，发布后失效。
- 标题层级跳跃，从 # 直接到 ###，渲染成目录时很难看。
- Front matter 或 HTML 注释被平台渲染成正文。
- 行内 HTML、自定义容器（::: tip）在多数平台不识别。

这些问题单靠提示词无法完全消除，需要一条确定性的后处理管线。

## 做法

我们把管线拆成四步：

1. 规范源 Markdown  
   Agent 输出后先经过 `markdownlint` 或类似规则做基础检查。只允许 CommonMark 子集：标题、段落、列表、代码块、表格、链接、图片、引用。禁止自定义容器、脚注、内联 HTML。标题层级必须连续，代码块必须注明语言。

2. 提取元信息  
   使用 Front Matter 保存标题、摘要、标签、封面图、发布时间。发布适配器只读取这些字段，平台特有的元数据在适配层生成，不进入源文件。

3. 平台适配层  
   每个平台一个适配脚本或转换函数。比如：
   - 公众号：代码块转为带样式的 `<section>` 或保留空格缩进，图片转成图床外链，标题加 emoji 前处理。
   - 知乎：将 Front Matter 移除，代码块语言标注统一转为小写，表格补齐对齐符。
   - GitHub/Notion：相对路径图片改为仓库绝对路径，Notion 表格需要转为 CSV 导入或使用 API。

4. 输出与校验  
   发布前用每个平台的预览接口或本地渲染器做一次校验。例如用 `markdown-it` 渲染后对比 DOM 结构，避免表格丢失或代码块塌陷。

在 OpenClaw 中，这一步可以做成一个 MCP 工具或插件。Agent 生成 Markdown 后调用 `publish-adapter`，传入目标平台列表，返回多个适配后的文件。中间产物保留在 `output/` 目录，方便 diff。

## 踩坑点

- 平台对 HTML 标签的过滤策略不一致。公众号几乎过滤所有 `<style>`，知乎会保留部分，GitHub 支持 `<details>`。适配层不要依赖 HTML，除非你只在单一平台发布。
- 代码块换行和缩进。AI 经常在代码块里混入制表符和空格，Markdown 渲染没问题，但复制到公众号编辑器会变成全角空格或丢失。建议在清洗阶段统一将制表符替换为四个空格。
- 图片防盗链。公众号图片必须传到自己的素材库，知乎可以直接用外链但有压缩。最好在管线里加一个图片上传步骤，返回平台专用 URL。
- 表格在移动端阅读体验差。如果表格列数超过 4 列，建议适配层自动转成列表或截图。
- Agent 输出不稳定：有时候会生成 Emoji 标题、有时候不会。建议在源规范中明确禁止 emoji 进入标题，emoji 只用于正文装饰。

## 可复用建议

- 保留原始 Markdown 作为 source of truth，适配后的文件只用于发布，不反向覆盖。
- 平台规则做成配置，不要硬编码在脚本里。比如 `platforms/wechat.yaml` 定义是否允许 HTML、代码块样式、图片处理方式。
- 写一个最小测试集：包含标题、列表、表格、代码块、图片、引用，每次改适配层后跑一遍。
- 用 git diff 检查适配结果，避免适配器引入非预期改动。
- 不要把这条管线做成“万能转换器”。只覆盖你真正发布的平台，其他平台等需要时再加。

## 总结

Markdown 管线解决的不是“生成”，而是“落地”。让 Agent 专注内容，让管线负责格式适配，比反复调 prompt 更可控。多平台发布的核心不是转换工具多强，而是源格式足够克制、适配层足够独立。这样即使平台规则变化，也只需要改一个适配器，而不是重写整个流程。
