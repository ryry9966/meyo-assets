在 OpenClaw/Agent 实践里，我把 memory_recall 当长期记忆入口。最开始只用语义搜索，后来发现精确匹配很弱；切到全文搜索，又出现自然语言召回不足。最后改成“元数据过滤 + 混合检索 + 固定评估集”，稳定了不少。

## 背景

memory_recall 一般提供 write/query/delete，底层可能是向量库、全文索引，或者两者兼容。Agent 需要把历史偏好、项目约定、报错记录、命令片段写入记忆，在后续任务里按需召回。选型错误的表现很典型：该召回的没召回，不该召回的被灌进上下文，最后 Agent 总结时被噪声带偏。

## 问题

语义搜索，也就是 embedding 相似度，擅长“意思接近但措辞不同”的自然语言记忆。例如“用户希望输出尽量简洁”和“不要啰嗦”，向量距离近，容易互相命中。

全文搜索，比如 BM25、FTS、关键词匹配，擅长精确标识符、错误码、路径、命令、版本号。例如 `EAI_AGAIN`、`/data/cache`、`redis-server`、`openclaw-runner` 这一类内容。

这两类场景混用时，语义搜索容易把“MySQL 连接超时”召回成“Redis 超时”，因为它们语义相近；全文搜索则在用户换一种自然语言问法时无能为力。所以问题不是“哪个更好”，而是“当前记忆该走哪条路，或者怎么合并”。

## 做法/步骤

1. **先给记忆分类。**  
   写入时至少带 `type`：`fact`、`preference`、`incident`、`command`、`doc`。自然语言偏好走语义，命令与报错走全文。

2. **写入侧结构化。**  
   不要只存一段长文本。建议存：原文、摘要、标签、项目、时间、重要度。摘要用于语义召回，标签和原文用于全文召回。例如：

```json
{
  "text": "redis 连接超时，最终确认是 maxclients 设置过低",
  "summary": "redis 连接超时由 maxclients 过低导致",
  "tags": ["redis", "timeout", "maxclients"],
  "type": "incident",
  "project": "openclaw-runner",
  "status": "resolved"
}
```

3. **封装查询。**  
   业务侧不直接依赖底层检索参数，只调用一个内部封装：

```json
{
  "query": "redis 连接超时怎么处理",
  "filters": {"project": "openclaw-runner", "type": ["incident", "command"]},
  "search": ["fulltext", "semantic"],
  "top_k": 8,
  "merge": "rrf"
}
```

4. **混合检索。**  
   不要直接比较向量分和 BM25 分。可以用 RRF 合并两个列表；或者全文命中优先，语义补充。通常做法是：全文 score 高于阈值直接返回；否则语义 `top_k` 进入候选，再做去重。

5. **建固定评估集。**  
   我准备了 30 条 query，包含精确错误码、模糊意图、混合对象。每次调整 embedding 模型、`top_k`、阈值或过滤条件，跑一遍 `hit@5` 和噪音率。没有评估集，很难判断改动是变好还是变差。

## 踩坑点

- 纯语义召回容易丢细节。排障场景里，错误码、端口、路径一个都不能错，向量相似度高不代表可执行。
- 全文搜索对中文分词敏感。默认分词器可能把“登录用户”拆成“登录/用户”，倒排命中不稳定。建议用 trigram 或配置 ICU 分词；英文场景注意大小写、下划线和连字符。
- 元数据过滤不要后补。记忆库一大，再想按 `project`、`type` 过滤，会发现大量旧数据没有这些字段。
- `top_k` 不宜贪大。召回 20 条，真正相关的可能被挤到后面；Agent 上下文有限，5 到 10 条通常够用。
- 如果不固定评估集，单凭体感很容易得出“好像准了”的结论，换个 query 就不行。

## 可复用建议

- 能用全文精确匹配的，不要让语义猜。错误码、命令、路径、版本号、专有名词优先走全文。
- 写入侧比召回侧更重要。原始记录里带上摘要和标签，召回效果会明显提升。
- 把 memory_recall 封装成内部工具，业务侧不直接依赖底层参数。以后切换 embedding、FTS 或合并策略，只改封装层。
- 先做元数据过滤，再做检索。过滤条件应来自任务上下文，例如项目、环境、用户、时间范围。
- 对关键场景做负样本。例如“已解决且不再复现的历史报错”可以在写入时标 `status=resolved`，召回时排除。

## 总结

语义搜索和全文搜索不是替代关系。记忆库很小、内容都是自然语言时，语义搜索够用；一旦出现命令、报错、路径、标识符，就需要全文搜索兜底。比较稳的组合是：写入结构化 + 元数据过滤 + 全文优先 + 语义补充 + RRF 合并 + 固定评估集。这样 memory_recall 才能从“能存能查”变成“查得准、不灌噪声”。
