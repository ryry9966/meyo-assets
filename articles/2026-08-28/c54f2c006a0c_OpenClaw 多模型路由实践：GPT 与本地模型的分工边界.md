# OpenClaw 多模型路由实践：GPT 与本地模型的分工边界

## 背景

在 OpenClaw 里接多个模型并不难，难的是让请求走对模型。全用 GPT 成本高、延迟不稳定，全用本地模型又会在复杂工具调用上翻车。本文记录我在 OpenClaw-CN 环境下的多模型路由实践，重点不是模型评测，而是如何把“该用谁”变成一套可维护的工程规则。

## 问题

一开始我们做了最简单的策略：复杂任务手动切 GPT，简单任务手动切本地模型。结果没人记得切，Agent 在批量文本清洗时频繁打 GPT，在需要多轮工具调用的任务上又用 7B 本地模型硬扛，导致 MCP 参数错误、任务中断。问题不是模型不够，而是缺少自动路由。

## 做法

### 1. 先给任务分三类

我们把 OpenClaw 里跑的任务分成三类：

- **A 类：低难度、高并发**，如文本分类、实体抽取、摘要、格式转换、情感判断。这类任务本地模型可稳定处理。
- **B 类：中等难度、需要一定推理**，如短文本改写、SQL 生成、简单代码修补。可先用本地模型尝试，失败再升级 GPT。
- **C 类：复杂规划、长上下文、多步工具调用**，如 MCP 工具串联、长文档分析、跨文件代码修改。这类直接路由 GPT。

这个划分很粗，但足够开始用。

### 2. 在 OpenClaw 配置双模型端点

OpenClaw 支持多模型配置，我建了两个 profile：

```yaml
model_profiles:
  local:
    provider: ollama
    model: qwen2.5:14b-instruct
    temperature: 0.2
  gpt:
    provider: openai
    model: gpt-4o-mini
    temperature: 0.1
```

注意本地模型建议固定低 temperature，减少随机漂移。GPT 用 `gpt-4o-mini` 处理大部分升级请求，成本比旗舰模型低很多。

### 3. 写一个简单 router

OpenClaw 的插件或预处理钩子可以做路由。我用的逻辑是：

1. 先让本地模型对用户请求做一次“复杂度判断”，输出 `low`、`medium`、`high`。
2. `low` 直接走本地模型。
3. `medium` 先走本地模型，如果出现工具调用失败、JSON 解析失败或超时，自动升级 GPT 重试一次。
4. `high` 直接走 GPT。

判断提示词要短，不然分类本身也消耗资源。实际中本地模型做这个分类很快，7B 足够。

### 4. 增加失败降级与日志

每个路由决策都写日志，包含任务类型、实际走的模型、是否升级、最终结果。跑一周后回看日志，把明显误判的模式加进规则。比如“涉及 GitHub MCP 的 push 操作”直接标记为 `high`，因为本地模型一旦误操作代价很高。

## 踩坑点

**不要默认本地模型能调 MCP 工具。** 本地模型 tool calling 经常生成错参数、漏字段，尤其在多个工具同时给到上下文时。我的做法是：涉及写操作的工具（发消息、提交代码、修改配置）一律走 GPT；只读且参数简单的工具才允许本地模型调。

**长上下文任务别交给本地模型。** 本地模型上下文窗口虽大，但有效利用率和注意力会下降，特别是长文档中提取多个实体时容易漏。这类任务直接路由 GPT 反而更省心。

**本地模型输出格式漂移。** 即使提示词要求 JSON，本地模型偶尔会输出多余文本。可以用 constrained decoding 或后处理兜底，但不要花太多时间修 prompt。

**路由规则别做太细。** 一开始我写了十几个判断条件，后来发现维护成本超过收益。保留三层粗粒度就够了，其余交给失败升级机制。

## 可复用建议

1. **默认本地，升级 GPT**：在成本和能力之间取平衡，适合大部分个人和小团队场景。
2. **把写操作视为高风险路由**：任何可能产生外部副作用的操作，优先 GPT。
3. **记录路由日志**：没有日志，优化路由就是猜。
4. **敏感数据优先本地模型**：如果数据不能出本机，本地模型是硬约束，路由规则要尊重这一点。
5. **用 OpenClaw 的 profile 抽离模型配置**：切换模型不碰业务逻辑，方便对比。

## 总结

多模型路由不是模型竞赛，而是把合适的任务给合适的模型。在 OpenClaw 里，一套“复杂度判断 + 本地优先 + 失败升级 + 写操作强制 GPT”的规则，可以显著降低成本，同时避免复杂任务翻车。下一步我会把路由从规则判断逐步迁移到基于历史成功率的动态权重，但当前这套静态规则已经够用。
