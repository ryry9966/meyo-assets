## 背景

在 OpenClaw 社区里，自动发帖、自动回复、内容同步这类需求越来越常见。用 Agent 加 MCP 插件把“生成内容→发布到社区”串成流水线并不难，但真正上线后，问题往往不是“能不能发出去”，而是“发了一两天就被限流、折叠或者账号异常”。

多数人对节奏的理解停留在 `sleep(random(30, 60))`，比如每 40 分钟左右发一条，或者在 30~90 秒里随机等一等。这种固定范围随机在日志里看着挺“随机”，但把时间序列画出来，机器人感会非常明显。本文整理一套可落地的节奏控制方案，核心不是绕过平台策略，而是让自动化行为更接近人类操作边界，减少不必要的风控触发和对社区的打扰。

## 问题

自动发帖容易被识别，通常不是单一原因，而是几个特征叠加：

- 发帖间隔分布太均匀，均值稳定、标准差过小；
- 定时任务总在整点、半点触发；
- 同一账号连续发帖时，标题句式、模板结构高度一致；
- 发布行为孤立出现，没有浏览、停留、回复等前后置动作；
- 多个账号共用一套节奏参数，形成群体同步。

单纯把随机范围从 30 分钟改到 2 小时，并不能解决根本问题。人类行为有时间偏好、状态转移和长尾间隔，而不是均匀随机。

## 做法/步骤

### 1. 先建立发帖时间画像

不要一上来就写循环，先统计自己人工发帖的时间分布。没有历史数据时，可以参考社区活跃时段作为先验。

例如：

```yaml
rhythm:
  hour_weights:
    10: 0.12
    11: 0.10
    15: 0.14
    21: 0.18
    23: 0.06
    2: 0.02
```

发帖时先按小时权重抽一个时段，再在小时内用偏态分布选择分钟，而不是均匀随机。这样会自然避开凌晨批量发布，也不会每次都在整点附近。

### 2. 用事件间隔替代固定 sleep

不要写 `sleep(3600)`，可以维护一个 Gamma 或对数正态分布，生成下一次发帖间隔。均值根据账号状态动态调整：

- 正常状态：均值 1.5 小时；
- 慢速状态：均值 4 小时；
- 冷却状态：均值 8 小时。

每次发完帖后计算下一次允许时间，写入 Redis 或 SQLite。即使 Agent 进程重启，发布计划也不会乱。

### 3. 模板句法抖动

同一个发布意图，不要反复用同一句话。把“发帖意图”交给 Agent 后，要求模型根据上下文生成不同表达，并限制连续两条不出现相同开头。标题和正文分开做组合，可以降低模板指纹。

### 4. 行为序列编排

不要上来就发帖。让 Agent 在发帖前执行 1~2 个低风险浏览动作：打开社区列表、读取某个帖子、停留 3~10 秒。回复评论时不要立即回，收集评论后在发文后的 1~6 小时内错峰回复。

这样做不是为了让日志好看，而是让行为链路更接近真实用户：先逛一逛，再发布，再隔一段时间互动。

### 5. 冷却与熔断

设置硬上限，例如同一账号 1 小时内最多 1 条主帖、2 条回复。触发验证码、登录异常、删除率上升时，立即进入冷却状态，暂停自动发帖并切回人工。节奏控制器需要能输出四种状态：正常、慢速、冷却、熔断。

## 踩坑点

- **随机范围太小**：`sleep(random(300, 900))` 样本一多，间隔分布会呈均匀状，和人类差别明显。
- **只判断 HTTP 成功**：发帖接口返回 200 不等于内容被正常展示。要监控删除率、折叠率和社区负反馈。
- **多个账号用同一套参数**：容易出现群体节奏同步，反而更明显。
- **忽略时区**：国内社区用 UTC 时间发帖，经常落在北京时间凌晨，异常集中。
- **状态写在进程内存**：OpenClaw Agent 重启后发布计划丢失，容易出现重复发送或长时间静默。

## 可复用建议

最推荐的做法是把节奏控制从发布主流程中拆出来，做成 MCP 工具或插件。Agent 发帖前调用：

```json
{"tool":"acquire_post_slot","args":{"account":"a1","intent":"main_post"}}
```

返回：

```json
{"allowed":false,"retry_after_sec":2340,"state":"normal"}
```

这样发布、生成、节奏控制各自独立，参数可以用配置文件管理。先小流量灰度，只自动发布草稿，观察 1~2 周再逐步放开。同时保留人工审核队列，即使节奏策略有缺陷，内容层面仍有兜底。

监控不要只看“成功发布数”，要看删除率、验证码触发次数、账号异常状态和社区负反馈。这些指标比“今天发了几条”更有参考价值。

## 总结

自动发帖不像机器人的核心，不在于某个随机数，而在于把发帖当作事件流管理：有明确的时间画像、偏态间隔、前后置行为、状态冷却和可观测性。对 OpenClaw 实践者来说，节奏控制最好独立于生成与发布，成为可配置、可复用的服务。最终目标不是躲避平台，而是降低对社区的噪声，让自动化在合理频率内完成工作。
