# AI Agent 权限边界：不要用“自觉”代替策略

## 背景：Agent 不再只是“回答”

在 OpenClaw、MCP、插件自动化这类环境里，Agent 的行为边界已经不只是“模型能不能说”，而是“工具能不能调”。它会读文件、写配置、发请求、跑脚本，甚至操作浏览器和外部服务。权限一旦放开，风险就从生成错误文本变成真实副作用：误删目录、误发通知、把测试动作作用到生产环境。

## 问题：要么太烦，要么太危险

如果每一步都问人类，Agent 就会退化成需要人工点击的批处理脚本；如果完全自主，一次错误的工具调用可能造成不可逆损失。常见做法是在系统提示词里写“遇到危险操作先问我”，但这等于把安全边界交给模型自觉。模型会受上下文、工具描述和任务目标影响，判断并不稳定。

真正可用的做法，是把权限判断从模型内部拿出来，变成策略层。

## 做法：把动作分级，而不是按心情判断

我倾向于把 Agent 可执行的动作分成四个风险等级：

- **L0 只读 / 低风险可逆**：列目录、读文件、查询状态、搜索日志。默认自动执行，但要限时、限次、限命名空间。
- **L1 可逆写 / 白名单路径**：写临时文件、创建分支、打 tag。允许自动执行，但必须限定目录、仓库或资源前缀。
- **L2 不可逆或有外部副作用**：删除非空目录、发送通知、合并 PR、部署到测试环境。需要人类确认。
- **L3 破坏性 / 资金 / 权限 / 批量**：支付、删除生产数据、改 IAM、群发消息、清空缓存。必须进入审批流，甚至要求双人确认。

实现上不要只写 prompt，而是把策略外置到工具调用前：

1. **盘点工具**：给每个 MCP 工具标注 `risk_level`、`requires_approval`、`allowed_namespaces`。
2. **策略外置**：用 JSON/YAML 维护权限配置，不要散落在系统提示词里。
3. **加 pre-hook 检查**：Agent 发出 `tool_call` 时，策略引擎先判断。L0/L1 放行，L2/L3 转成 approval request。
4. **确认信息要具体**：展示动作、参数、影响范围、回滚方案、超时时间，而不是只弹一个“是否继续？”。
5. **记录决策**：每次自动放行和人工确认都写审计日志，包含模型意图、策略命中、最终结果。

在 OpenClaw/MCP 场景里，可以把“approve”做成一个人工审批工具，或者先把高风险动作路由到 dry-run 模式，输出变更计划，再由人确认。

## 踩坑点

- **把模型判断当安全边界**：模型会因 prompt 变化而改变行为。策略必须在模型之外。
- **工具描述太模糊**：模型不知道工具会删数据，就会乱调。工具描述里要写清副作用、影响范围和不可逆性。
- **确认疲劳**：所有写操作都问，用户很快会麻木并习惯点“允许”。要分级，低频高风险才问。
- **只防写不防读**：读取生产客户数据、密钥也可能越权。读操作也要按数据敏感度控制。
- **环境不分**：测试和生产用同一套工具配置。生产应更严格，或使用只读凭据。
- **批量操作放大风险**：单条删除可逆，批量删除不可逆。策略要看数量和范围，不只动作名。

## 可复用建议

- 默认拒绝，白名单放行。
- 高风险动作必须有 dry-run 或 plan 先行。
- 人工确认要带上下文和回滚方案，不要只是一个 yes/no。
- 权限策略放在配置文件里，别写在系统提示词里。
- 对自动放行设置限流、预算、超时。
- 定期复盘审计日志，把频繁误拦或漏拦的动作调整等级。

## 总结

Agent 权限边界不是“什么时候该问人类”的哲学题，而是“动作风险等级 + 策略引擎 + 人工确认 + 审计”的工程题。先收紧，再根据真实误报放开；让 Agent 在低风险区自己干，在高风险区停下来问人。不要用模型的自觉替代可执行、可审计的策略。
