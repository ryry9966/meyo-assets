## 背景

大多数 Agent 框架默认是 request-response：用户发消息，模型调用工具，返回结果。它在对话式场景下足够稳定，但很多自动化场景真正需要的是另一种形态——事件发生、条件满足、预授权动作执行、全程留痕。比如仓库里出现带 `bug` 标签且 24 小时无人回复的 issue，或者日历里两个待确认事项发生冲突。

这类 proactive 能力如果直接让 LLM 自由判断“要不要做”，通常会出现三个问题：判断不稳定、容易过度主动、动作边界模糊。更工程化的做法是把决策拆成两层：规则负责触发和边界，LLM 只负责生成内容或工具参数。

下面是一个我在 OpenClaw 中跑通的最小实践，不涉及复杂调度，适合拿去做模板。

## 问题

我们需要解决的核心不是“让模型主动”，而是把主动限制在可预期、可回滚、可审计的范围里。否则 proactive agent 很快会变成三类失败：

- 误报：模型觉得你需要，于是频繁触发低价值动作。
- 越权：模型为了“把事情办了”，调用未限制的 MCP 工具或执行危险操作。
- 不可追踪：动作发生后没有原始上下文，排障时无法复盘。

因此，这个实践的目标是：用代码规则决定“该不该动”，用受限 MCP 工具决定“能动什么”，用审计记录决定“动错了怎么退”。

## 做法 / 步骤

**1. 选一个失败成本低的窄场景**

不要一上来做“通用主动助手”。建议从一个明确条件、明确动作、失败后可回滚的场景开始。例如：监测指定 GitHub 仓库的 issue，如果满足“标签为 bug、状态为 open、超过 24 小时无新评论”，则创建诊断分支并写一条 issue 评论。

**2. 事件源与规则触发**

用 cron 或 webhook 作为事件源。每隔 10 分钟拉取一次目标 issue，条件写在普通代码里，不要放进 prompt 让模型判断。筛选逻辑类似：

```python
def should_act(issue):
    return (
        issue["label"] == "bug"
        and issue["state"] == "open"
        and hours_since(issue["last_comment"]) > 24
        and not already_acted(issue["id"], "create_branch")
    )
```

其中 `already_acted()` 是幂等检查，避免重复触发。

**3. 通过 MCP 工具执行，而不是让模型自由发挥**

在 OpenClaw 中注册一个专用 MCP 工具，例如 `create_diagnostic_branch`。它的能力只限定为：在指定 repo 下创建 `proactive/<issue_number>` 分支，并写入一份诊断记录草稿。LLM 只负责根据 issue payload 生成分支内容，不负责选择执行哪个工具，也不直接接触 Git 命令。

工具描述要写清楚前置条件、副作用和幂等行为。这样模型在调用前会受工具描述约束，减少乱调用的概率。

**4. dry-run 与审批层级**

所有 proactive 动作建议分三级：

- dry-run：只输出计划，不执行任何写操作。
- 需要确认：生成计划后推到审核队列，人工确认后再执行。
- 自动执行：仅限低风险动作，但必须强制写审计日志。

第一周只跑 dry-run 或“需要确认”，观察触发质量后再逐步放开。

**5. 闭环记录**

每次触发保存一条记录，字段至少包括：

```text
run_id, trigger_time, source, rule_version,
issue_id, dry_run, decision, tool_call,
result, rollback_status
```

同时保留原始事件 payload，不要只存摘要。事件触发场景没有对话历史，原始 payload 是事后排障的唯一依据。

## 踩坑点

- **重复触发**：同一个 issue 可能多次满足条件，导致重复建分支。必须在工具调用前做幂等查询，并让工具本身支持幂等键。
- **权限过大**：给 MCP 用的 token 要限定到目标仓库和分支前缀，禁止 `delete`、`force_push`、`settings` 等权限。工具运行环境最好隔离，不挂载全局配置。
- **通知噪音**：proactive 结果的默认通道应是低干扰路径，比如写 issue 评论或创建任务卡片。只有高优先级、高置信度的结果才推即时消息，否则用户会很快关闭通知。
- **上下文丢失**：事件触发时没有用户对话历史。不要把原始 payload 丢弃后只给模型一句“看看这个”，否则排障时连触发条件都还原不出来。
- **工具描述不写副作用**：模型可能在一次任务里反复调用同一个工具，消耗配额并产生冗余操作。工具描述中必须写明“该操作会创建分支”“同一 issue 只允许执行一次”。

## 可复用建议

- 使用“触发器-规则-动作-审计”四层模板。换场景时只替换事件源和动作工具，规则层保持纯代码。
- 先只做“主动发现”，不要马上做“主动执行”。跑一周数据，统计误报率和漏报率，再决定是否开启自动执行。
- 在 OpenClaw 层维护一个全局 kill switch，例如支持 `/pause` 或环境变量关闭所有主动动作。任何时候都能一键停。
- 保持 LLM 只做内容生成，不做触发判断。判断条件写在代码里，规则变更也要带版本号，方便回溯决策差异。
- 每个 proactive 工具都要求提供 dry-run 和 rollback 方式。没有回滚方案的动作，不要进入自动执行层。

## 总结

proactive 能力的真正价值不在“快”，而在把低价值但确定性的判断外移给系统。规则负责“该不该动”，MCP 工具负责“能动什么”，审计负责“动错了怎么办”。先跑通一个失败成本低的窄场景，比一上来做通用主动助手更实际，也更能在 OpenClaw 里长期稳定运行。
