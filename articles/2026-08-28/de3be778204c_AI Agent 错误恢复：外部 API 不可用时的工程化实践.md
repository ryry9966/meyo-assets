在 Agent 工作流里，外部 API 很少会“按剧本”失败。更常见的是：搜索服务开始 5xx，天气接口超时 20 秒，支付回调返回 429，某个 MCP 工具突然不在了。如果我们的 Agent 只是线性地“调用—解析—下一步”，一个外部依赖抖动就可能让整个任务中断；更糟的是，重跑时因为缺少状态记录，可能重复发消息、重复扣费或重复写入。

这里想讨论的不是“怎么避免 API 挂”，而是 API 挂了以后，Agent 如何体面地失败、恢复并继续完成能完成的部分。

## 问题：失败不可怕，失控的失败才可怕

典型问题有三类：

1. **无差别重试**：把 400、401 也当临时错误重试，既浪费配额，又可能触发风控。
2. **无熔断**：一个下游已经连续失败，Agent 仍然每次都等满超时，整个队列被拖垮。
3. **无降级**：某个非关键数据源挂了，本来可以用缓存或跳过，但流程直接终止。

这在 OpenClaw/Agent/MCP 场景里尤其明显，因为工具调用往往被封装成“黑盒”，错误被吞掉或只返回一行 `API error`，上层很难判断下一步。

## 做法/步骤

### 1. 先定义错误模型，再写重试

不要只判断 `success` 和 `fail`。至少把错误分成：

- **可重试**：网络超时、连接重置、429、5xx。
- **不可重试**：400、401、403、参数错误、资源不存在。
- **可降级**：数据缺失、非关键服务不可用、返回结构变化。

可以在统一 API 客户端里维护一个错误分类函数。这样每个工具不用各自实现一套 `try/except`。

### 2. 重试使用指数退避 + 抖动

固定间隔重试容易在下游恢复瞬间形成重试风暴。推荐指数退避：

```
delay = min(base * 2 ** attempt, max_delay)
delay += random(0, jitter)
```

同时限制最大次数，例如 3 次。对 **非幂等 POST** 要特别谨慎：如果请求可能产生副作用（发送消息、创建订单、扣减额度），要么不自动重试，要么在请求中带幂等键。

### 3. 给下游加熔断

当某个 API 连续失败 N 次后，短时间不再真实调用，直接返回“熔断中”或走降级。熔断器状态机可以很简单：

- closed：正常调用。
- open：失败达到阈值，快速失败。
- half-open：等待一段时间后放一个探测请求，成功则恢复，失败则重新计时。

在 MCP 工具封装层做熔断比在单个插件里做更合适，因为上层调度能看到“这个工具暂时不可用”。

### 4. 准备降级与兜底

对非强一致场景，可以：

- 返回最近一次成功响应缓存。
- 返回本地静态兜底数据。
- 换用备用数据源。
- 返回部分结果，并给结果打上 `degraded` 标记。

例如天气接口失败时，可以返回“最近一次缓存的城市天气，数据时间 2 小时前”，而不是让 Agent 直接报错。用户和上层 Agent 应能区分“完整数据”和“降级数据”。

### 5. 状态检查点：失败后从中间恢复

长任务如果跑了 5 步才在最后一步挂掉，重跑整个流程可能产生重复副作用。建议在关键步骤之间写检查点：

- 把已完成的步骤、结果摘要、幂等键写入本地状态文件或数据库。
- 任务开始前先检查是否已有未完成的检查点。
- 恢复时跳过已完成步骤，只重跑失败步骤。

这不一定是重型状态机，一个 JSON 文件或 SQLite 表就能解决很多问题。

### 6. 可观测输出

失败时不要让 Agent 只输出 `Request failed`。至少结构化记录：

- 工具名/API 名
- 错误分类
- 重试次数
- 是否降级
- 用户可读的下一步建议

这些信息可以对用户展示，也可以让上游 Agent 根据错误类型决定是否换策略。

## 踩坑点

- **把 400 当临时错误重试**：浪费配额，甚至触发安全告警。
- **无限重试**：下游恢复后，堆积的重试请求可能直接把它再次打挂。
- **对非幂等操作自动重试**：这是最危险的一类，可能出现重复支付或重复外呼。
- **降级缓存不设有效期**：用户拿到的是过期数据，还以为是实时数据。
- **状态文件与任务并发冲突**：多个 worker 同时读写同一检查点文件，可能损坏状态。
- **忽略超时设置**：一个挂起的 API 可以让 Agent 卡住很久，尤其在没有显式 timeout 的 SDK 里。

## 可复用建议

1. **封装统一 API 客户端**：内置超时、重试、熔断、降级和错误分类。
2. **策略配置化**：不同工具配置不同重试次数、超时和降级开关，不要硬编码。
3. **关键写操作带幂等键**：就算重试或重跑，也不会产生重复副作用。
4. **定期做故障演练**：手动把某个外部 API 停掉，观察 Agent 是否能按预期降级或恢复。
5. **降级结果显式标记**：让下游和用户知道数据不完整，避免静默错误。
6. **把 MCP 工具不可用当作正常情况处理**：在 OpenClaw 流程里，工具发现/调用失败不应总是致命错误。

## 总结

外部 API 挂掉不是概率问题，而是时间问题。对 AI Agent 来说，错误恢复能力比“一次成功”更重要。与其在每个插件里写分散的 `try/except`，不如在统一调用层做好错误分类、指数退避、熔断、降级和状态恢复。这样当某个搜索服务 5xx、某个 MCP 工具超时、某个支付回调 429 时，Agent 不会跟着挂，而是尽量完成可完成的部分，并把失败信息清楚地交给下一层处理。
