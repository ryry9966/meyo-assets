## 背景

在 OpenClaw 这类 Agent 编排环境里，AI 助手通常不是一次性请求-响应，而是常驻进程、插件或 MCP server 的组合。一个典型场景：助手通过 MCP 调用了一个异步工具，工具在远端执行几分钟，期间宿主进程需要知道任务是否完成、是否被取消、连接是否还活着。

heartbeat 不只是“我还在”，而是状态同步的最小载体。它通常包含两类信息：存活信号和业务游标。轮询和推送的取舍，直接影响延迟、资源消耗和排障成本。

## 问题

轮询方案：客户端按固定间隔请求任务状态。实现简单，无状态服务端容易扩展，但存在无效请求和固定延迟。一个 1 秒轮询的助手，大部分请求可能是空返回。

推送方案：服务端通过 WebSocket、SSE 或 webhook 主动通知。延迟低、带宽友好，但要求客户端有可达通道，或能维持出站长连接。在 NAT、企业代理、容器短生命周期环境里，入站 webhook 往往不可靠。

常见翻车点是：为了省事全用 5 秒轮询，或选了推送但没做业务层重连与去重，最后状态乱序、事件重复。

## 做法/步骤

### 1. 先定义 heartbeat 契约

不要一上来选传输。先把 heartbeat 消息字段定下来：

```json
{
  "id": "hb_01H...",
  "ts": 1710000000,
  "seq": 42,
  "status": "healthy|degraded|busy",
  "task_id": "task_123",
  "cursor": "event_0041"
}
```

`seq` 单调递增，用于检测乱序和丢失；`cursor` 是业务事件游标，不是时间戳。心跳与业务事件可以同通道，但要在结构上分开。

### 2. 选择传输：优先出站推送，轮询做兜底

- 如果助手、插件或 MCP server 能保持出站 WebSocket 或 SSE，直接用推送。SSE 更适合单向事件流，实现比 WebSocket 简单，且能走普通 HTTP 代理。
- 如果运行在无长连接环境，或服务端无法维持大量连接，用轮询或长轮询。长轮询通过 `cursor` 增量拉取，把空轮询的浪费降下来。
- 入站 webhook 只适合客户端有公网地址或通过隧道可达的场景，不建议作为唯一通道。

### 3. 实现一个最小状态机

```
CONNECTING -> HEALTHY -> DEGRADED -> DISCONNECTED
```

连接建立后进入 HEALTHY；连续丢失 2-3 个心跳进入 DEGRADED，服务端可标记任务为“不确定”；超过阈值进入 DISCONNECTED，触发重连或降级轮询。关键是：网络失联不应直接杀死业务任务，先标记不确定，给恢复留窗口。

### 4. 轮询的增量游标

如果做轮询，接口设计成：

```
GET /tasks/{task_id}/events?cursor=event_0041&limit=50
```

服务端返回 `next_cursor` 和事件列表。客户端必须幂等处理，因为重试可能重复返回同一段事件。用时间戳过滤会因时钟偏移漏事件，不建议。

### 5. 推送的保活与回放

WebSocket/SSE 需要应用层心跳，不能只依赖 TCP 或底层库的 ping。心跳包带上 `seq`，客户端收到后检查连续性。断线重连后用 `cursor` 或 `seq` 回放缺口。服务端要保留短期事件缓冲区，比如最近 5 分钟或最近 500 条。

## 踩坑点

- **心跳间隔过短**：见过 1 秒一次的心跳，大量连接时把服务端 CPU 和日志打满。15-30 秒足够。
- **业务大事件阻塞心跳**：如果心跳和任务结果共用一个通道，一个大文件事件可能让心跳延迟，导致误判失联。心跳发送应独立于业务事件队列。
- **只重连不校验**：底层库自动重连后，业务层没有用 `seq` 补齐缺口，重复或丢失事件最终表现为 AI 助手重复执行工具。
- **假健康**：连接还在，心跳正常，但消费者线程已卡死。健康检查应包含处理延迟指标，比如 `event_lag`。
- **推送失败没有降级**：长连接被代理静默断开后，一直等推送，任务长时间无状态。推送连续失败应自动切到轮询。

## 可复用建议

- 心跳间隔 15-30 秒，超时阈值设为 2-3 个心跳周期。
- 心跳消息必须有 `seq` 和 `cursor`，不要用时间戳做事件游标。
- 优先 SSE/WebSocket 出站连接，webhook 作为补充。
- 暴露指标：`heartbeat_latency`、`missed_heartbeats`、`reconnect_count`、`event_lag`。这些指标比日志更容易定位问题。
- 降级路径要提前设计：推送失败自动切换轮询，轮询压力大时切回推送。两种模式共享同一套事件回放逻辑，减少双份实现。

## 总结

轮询和推送不是对立的，而是同一套 heartbeat 契约下的两种传输策略。工程上更务实的做法是：用出站推送获得低延迟，用增量轮询作为兜底，用 `seq`/`cursor` 保证事件不重不丢，用状态机容忍网络抖动。把心跳从“存活探针”升级为“状态同步层”，AI 助手的长任务才会稳定、可观测、可恢复。
