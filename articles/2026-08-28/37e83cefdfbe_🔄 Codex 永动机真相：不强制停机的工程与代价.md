OpenAI 的 Codex 又上热搜了，这次不是因为写代码多强，而是被曝出内部代码疑似存在“不强制休眠、不停机”的机制。社区里有人戏称这是把 AI 代理做成了永动机。那么，这个“永动机”到底是怎么回事？是精心设计，还是一个被误解的工程细节？今天不吹不黑，从代码逻辑、资源成本和实际使用场景拆一下。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/8a786a415104b4e3.png)

## 一、永动机的代码长什么样？

先看现象。通常云代理（cloud agent）在空闲一段时间后会触发 idle timeout，自动挂起或销毁，以节省计算资源。但这次曝光的代码显示，Codex 内部可能有一段“不肯睡”的逻辑。

- 有一种典型模式是 keep-alive 循环：每隔几十秒，程序会主动发送一次心跳，把空闲计时器清零。
- 另一种更激进的做法，是直接在循环条件里做文章：只要任务没有被显式标记为 `done`，就继续执行下一步，同时重置 idle timer。
- 用伪代码描述，类似这样：`while True: if task_queue: execute_next_task(); reset_idle_timer()`。这意味着，只要任务队列里还有东西，进程就永远不会自然退出。
- 这种设计在开源 agent 项目里并不罕见，早期一些项目为了规避云平台的自动回收，也会写类似的自重启脚本。

换句话说，这相当于在软件层面给进程加了一个“起搏器”。只要循环条件为真，它就会一直活下去。

## 二、为什么需要“不停机”？工程上的真实需求

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/9bab58570ccc05e0.png)

很多人看到“永动机”三个字，第一反应是浪费资源。但先别急着喷，任何反常设计背后往往有现实约束。

- **长任务连续性**：复杂重构、跨文件代码迁移、大型测试修复，通常需要几十分钟甚至几个小时。如果代理每 20 分钟空闲就停机，用户体验会非常差。
- **状态保持**：运行中的依赖安装、编译缓存、调试上下文，如果频繁重启，代价极高。一次重启可能丢掉全部中间状态，任务等于白干。
- **任务完成率**：对于 Codex 这类云开发环境，完成率是付费产品的核心指标。宁可多烧一点 token，也要保证任务能跑完。
- **真实场景举例**：开发者提交一个跨 200 个文件的批量重命名任务。代理需要先扫描依赖关系，再分批修改，整个流程可能持续 2 小时。如果中间用户去开个会、喝杯咖啡，回来发现任务因为空闲超时被终止了，这才是真正的灾难。

所以，从工程逻辑上看，“不强制停机”并非完全不合理。它解决的是长时任务场景下的连续性痛点。

## 三、永动的代价：资源、安全和失控风险



但问题也摆在那里。一个没有“刹车”的系统，迟早会撞墙。

- **资源成本失控**：持续运行意味着持续调用模型。按单次 agent 任务平均消耗数万到数十万 token 估算，一位用户如果放任代理运行 24 小时，消耗的 token 可能达到数百万，成本轻松超过几十美元，而正常任务可能只需 1/10。
- **安全风险**：失控循环可能在错误分支上重复执行操作，比如重复提交代码、重复触发外部 API、甚至误删文件。在云开发环境里，这不是小问题。
- **工程反模式**：没有熔断机制的长循环，一旦进入死循环，只能靠外部 kill，增加运维负担。软件工程里最忌讳“只能启动、不能停止”的系统。
- **类比**：热力学意义上的永动机违背能量守恒，软件工程中的“永动机”则违背“可控性”原则。一个不可观测、不可干预的进程，本质上是不可信的。

## 四、冷静看待曝光：设计还是漏洞？



信息源是内部代码曝光，但“曝光”不等于“实锤”。

- 这类代码通常来自逆向工程、开源仓库泄漏，或者某个内部分支。它不一定是官方正式发布的行为。
- 可能只是一个调试分支、一组实验参数，或者默认值设置得过于激进，并非蓄意设计“永动机”。
- 反过来说，如果官方默许这种行为，也可能是在特定试点项目中测试长任务代理的极限，收集真实数据。
- 截至目前，OpenAI 并没有公开声明该代码的意图，社区讨论仍以推测为主。把“永动机”当成产品特性，还为时过早。

## 五、三条实用建议：给使用者和工程师的冷却阀

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/a2c0a40a0b5b8fc9.png)

无论真相如何，这件事对使用者和工程师都有提醒：自动化不眠，不代表可以无脑放养。

1. **如果你是 API 用户或 Codex 使用者**：务必在控制台设置最大 token 预算、最大运行时长和告警阈值。别让“自动续命”变成自动烧钱。
2. **如果你在做类似 Agent 系统**：给循环加熔断——最大迭代次数、异常退出、人工确认点。任何 `while True` 都该有对应的 `break`。
3. **冷思考**：AI 不眠不代表更聪明，只代表它消耗更多资源。工程上真正值得追求的，是“该睡就睡、该醒就醒”的动态调度能力，而不是让进程无脑狂奔。

永动机式的代理提醒我们，自动化不是没有代价的。可控的持续运行，才是工程的正解。
