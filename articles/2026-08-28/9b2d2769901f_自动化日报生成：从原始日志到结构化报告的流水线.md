## 背景

每天写日报的成本不只是“写”那几分钟，而是把散落在 Git commit、CI 日志、任务卡片、群聊记录里的信息捞出来、判断哪些值得写、再统一口径。人工汇总容易漏掉跨时区部署，或把 WIP 当成完成项。

在 OpenClaw 生态里，这件事更适合用 Agent + MCP + 插件组成一条小流水线：定时拉取原始日志，清洗成结构化事件，再渲染成固定格式的日报。

## 问题

原始日志通常有四个问题：

1. **非结构化**：Git commit、CI job、任务卡片格式完全不同。
2. **噪音多**：重试、debug、自动 bump version 等无意义事件混在一起。
3. **时间线混乱**：UTC、本地时区、服务器时间混杂，按天切分容易错位。
4. **重复与增量难处理**：轮询和 webhook 可能重复，全量拉取会爆上下文。

如果不先解决这些问题，直接让 LLM 读原始日志生成日报，结果要么漏项，要么编造。

## 做法/步骤

### 1. 数据源接入

用 MCP 或插件把数据源统一成工具调用。例如 Git MCP 读 commit 列表，CI API 插件读 job 状态，任务系统插件读卡片变更。Agent 只调度和汇总，不直接接触原始输出。

### 2. 清洗与标准化

在插件层或轻量脚本里，把不同来源映射到统一事件结构：

```json
{
  "source": "git",
  "id": "repo:commit_sha",
  "time": "2025-01-01T09:30:00+08:00",
  "type": "commit",
  "summary": "fix: 修复日报流水线时区偏移",
  "url": "https://...",
  "status": "done"
}
```

过滤规则尽量简单：排除 WIP、debug、自动 bump version；保留 merge、deploy、issue close、release 等关键事件。

### 3. 增量拉取与去重

记录每个数据源的上次游标或时间戳，只拉新增事件。去重用 `source + id` 做哈希，写入本地 SQLite 或 KV 缓存。不要依赖“感觉没重复”，重复事件会让日报出现两条一模一样的完成项。

### 4. 分段聚合

不要把一天全部事件一次性塞给模型。先按项目或类型分组，让 Agent 对每个分组生成短摘要，再汇总成日报。这样上下文可控，也容易定位哪一段出错。

### 5. 模板渲染

用固定 Markdown 模板输出，例如：

```markdown
## 今日完成
- [项目A] 修复时区偏移 (#123)
## 进行中
- [项目B] 重构日志清洗插件
## 风险
- CI 夜间任务失败，待重跑
## 明日计划
- 补充增量拉取测试
```

模板变量来自结构化事件，LLM 只做措辞和排序，不自由发挥格式。

### 6. 发布与回写

生成后先发到草稿群或文档，人工确认后再正式发布。发布成功后，插件把日报链接回写到任务系统或归档表，方便追溯。

## 踩坑点

- **时区**：所有时间不先转成目标时区再切分，跨午夜事件会落到错误日期。建议在清洗层统一转换。
- **重复拉取**：同时开 webhook 和轮询时，同一事件会进来两次。必须做幂等。
- **上下文爆炸**：不要拼接完整 CI 日志。只保留失败摘要、耗时、commit 关联信息，原始日志放链接。
- **幻觉**：约束 Agent 只基于事件摘要生成，不允许补全没有 id/url 的“可能完成”。每个完成项都带来源链接，没有链接就归入“待确认”。
- **模板漂移**：模型偶尔会改 Markdown 结构。生成后做一次格式校验，失败则回退到固定模板或重新生成。

## 可复用建议

1. **先跑通单项目单源**：一个 Git 源加一个任务系统，能出日报再扩展。
2. **固定 schema 优先**：统一事件结构是整条流水线的核心，清洗层不要省。
3. **保留原始链接**：每条日报内容都能跳回原 commit/工单，方便 review。
4. **加入人工确认**：日报先草稿后发布，比全自动发布更可控。
5. **成本控制**：清洗和聚合用轻量模型，最终润色才用强模型。
6. **清洗层复用**：结构化事件流后续可以接告警、周报、项目简报，不只是日报。

## 总结

自动化日报的难点不在“生成文字”，而在把原始日志变成可信的结构化事件流。只要做好适配、清洗、增量去重和模板约束，日报就能从负担变成日志治理的副产品。MCP 负责取数，插件负责清洗，Agent 负责汇总，最后输出一份人愿意看的报告。
