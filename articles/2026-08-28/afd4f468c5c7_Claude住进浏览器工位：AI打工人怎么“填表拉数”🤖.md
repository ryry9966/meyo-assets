大模型刚刚出现时，我们习惯把它当作对话框里的“大脑”：你问，它答。但最近 Claude 的新动向让很多人意识到，AI 不仅会写，还会“动手”——它能打开浏览器、移动鼠标、点击按钮、填写表单、跨页面拉取数据。与其说它学会了新技能，不如说它第一次拥有了一个虚拟工位。这不是又一个聊天机器人更新，而是一次从“语言输出”到“界面操作”的跨越。



## 一次“填表拉数”背后到底发生了什么

很多人第一次看到演示时，会以为 Claude 直接接管了操作系统。更准确地说，Claude 通过 Computer Use 能力，获得了对电脑界面的操作权限：它不靠事先写好的脚本，而是像人一样“看屏幕—做动作—再看屏幕”。

一个典型的填表拉数任务大致是这样的：

1. 模型截取当前屏幕画面，识别浏览器、按钮、输入框、表格区域。
2. 它将视觉信息转换成下一步动作，例如“把鼠标移动到搜索框”“点击导出按钮”“选中第三行第二列”。
3. 通过虚拟鼠标和键盘执行动作，停留片刻等待页面加载。
4. 再次截图，判断前一步是否成功，有没有弹窗、报错或跳转。
5. 循环执行，直到完成任务，或者遇到需要人工确认的敏感操作。

这里的关键不是“AI 能打开网页”，而是它开始处理真实世界中模糊、多变、没有标准 API 的工作界面。传统 RPA 依赖固定元素定位，页面改版就失效；Computer Use 更接近“视觉 + 动作”的模式，页面变了也能重新理解。

## 为什么是浏览器：最接近真实工位的沙盒

浏览器可能是 AI 进入企业流程最自然的第一站。理由有三：

- 知识工作的主界面大多已经网页化：CRM、ERP、OA、招聘系统、数据后台、财务软件，几乎都跑在浏览器里。
- 不需要为每个系统开发接口：很多内部系统没有开放 API，或者 API 权限申请周期很长，让 AI 像人一样操作界面，反而降低了集成成本。
- 浏览器相对容易隔离和监控：相比之下，直接控制系统级权限风险更大；浏览器窗口可以被录制、限制、单独登录账号。

因此，与其说 Claude 长出了浏览器，不如说它被放进了一个“数字工位”：有屏幕可看、有鼠标键盘可用，还有一圈护栏。

## 它不是 RPA 2.0，但也别神化

有人会问：这和十年前的 RPA 有什么区别？其实两者处在不同维度。

- 传统 RPA 是“精确但脆弱”的录像回放。它靠固定选择器和脚本运行，页面稳定时效率很高，页面一改版就可能直接中断。
- Computer Use 是“概率化但灵活”的新手操作员。它能根据截图重新识别界面，即使布局变化也有一定适应能力，但同一个任务每次可能点得不太一样。
- 所以它不会立刻替代 RPA，更可能先补位那些“用 RPA 做太脆、人工做太烦”的中间地带。

这句话值得记住：RPA 适合长期稳定、规则明确的流程；AI agent 适合半结构化、变化多、需要理解界面的场景。

## 技术机制：从“看见”到“点击”的闭环

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/e7017c66f7bdf445.png)

Computer Use 的核心并不是一个简单的“浏览器插件”，而是一个感知—决策—动作的闭环系统。

- 感知端：模型接收屏幕截图序列，而不是网页源码。它需要理解布局、图标、颜色、滚动条位置，甚至识别弹窗和 loading 状态。
- 决策端：多模态模型将截图与任务目标结合，生成下一步操作。由于任务可能长达几十步，模型需要具备一定的长程规划和错误恢复能力，比如点击没反应时尝试刷新，或发现误操作后回退。
- 动作端：输出空间包括鼠标移动、左键、右键、拖拽、键盘输入、滚动、快捷键等。这些动作被转换成系统事件执行。
- 护栏：在敏感操作前触发确认，比如涉及支付、删除、发送邮件、修改权限时，默认需要人工批准。

这种设计的好处是通用性：理论上，任何人类能在屏幕上完成的操作，都可以被描述为“截图 + 动作”序列。但代价也很明显——速度比人慢，成本不低，而且模型在开放场景中仍有不少误操作。

公开测试中，早期 Computer Use 模型在 OSWorld 这类真实操作系统交互基准上的成功率不到两成，而人类通常在七成以上。这意味着它更适合可控、重复、有明确检查点的工作，而不是自由探索。

## 能填表到什么程度：当前能力与边界

如果拿一个初级实习生来类比，Claude 目前大约是这样：听话、不知疲倦，但经验不足，遇到非常规情况容易卡住。

它能做得不错的任务：

- 从固定页面复制字段，粘贴到另一个表单；
- 按照已有 Excel 列表逐条查询后台，抓取订单状态、客户信息；
- 导出报表、整理 CSV、批量重命名、归档到指定文件夹；
- 在页面之间搬运标准化数据，比如把招聘网站候选人信息录入内部系统。

它目前还不够可靠的任务：

- 涉及验证码、滑块、短信验证、生物识别的环节；
- 需要主观判断的业务，比如“这条客户备注是否算投诉”；
- 对模糊指令的理解，例如“把那个表弄一下”，它可能不知道该点哪里；
- 高风险写操作，例如删除客户、发起退款、修改价格。

换句话说，它更适合“手和眼”的重复劳动，而不是需要“判断和签字”的决策环节。

## 企业/个人使用前的三条冷建议

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/1b420e72da11c7c0.png)

如果你准备让 AI 打工人上工，先别急着给它最高权限账号。下面三条原则比选工具更重要。

1. 按可逆性分级，而不是按任务难易分级。  
   先让它做只读、可回滚、有日志的操作，比如查数据、导报表、整理表格。凡是涉及支付、删除、外发邮件、修改主数据，都必须有人工确认或事后审计。

2. 给 AI 单独账号，而不是共用你的账号。  
   单独账号可以限制数据范围、权限和登录时段。关闭“记住密码”，拆开敏感模块。不要让它用管理员账号跑流程，一旦误点，止损难度完全不同。

3. 先跑 10 条样本，再谈提效。  
   任何自动化项目都有“演示很顺，上线翻车”的风险。正确做法是：写清楚任务说明、设置检查点、录制操作日志，先人工核对 10 条样本。如果准确率达不到业务底线，就先把它当作“辅助生成草稿”的工具，而不是无人值守员工。

从更长期的视角看，这种能力不会让“填表”这个动作消失，但会改变它的组织方式。未来的知识工作里，可能多出一个新岗位：不是自己填表的人，而是给 AI 排班、写任务卡、做质量抽检的人。AI 打工人有了工位以后，真正稀缺的是知道该让它做什么、不做什么的人。
