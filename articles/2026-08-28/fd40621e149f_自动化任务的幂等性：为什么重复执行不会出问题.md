# 自动化任务的幂等性：为什么重复执行不会出问题

## 背景：自动化系统天然会重复

在 OpenClaw、Agent、MCP 以及各类插件组成的自动化链路里，几乎没有“只会执行一次”的调用。定时任务可能重叠运行；webhook 因为超时被服务端重发；Agent 调用工具失败后框架自动重试；插件被用户连续点击；MCP server 重启后未完成任务重新入队。

如果每个动作都假定“只触发一次”，很快会遇到重复副作用。常见翻车现场包括：

- 同一个 webhook 事件到达两次，重复创建工单或重复发通知。
- Agent 工具调用超时，框架重试后工具实际执行了两次。
- 插件被连点，触发多次外部 API 创建资源。
- 任务队列 at-least-once 投递，worker 重复消费。

目标不是消除重复调用，而是让重复调用不产生额外业务副作用。

## 问题：为什么“重试”不等于“幂等”

很多自动化框架自带重试，但重试只能保证“再执行一次”，不能保证“第二次不会重复生效”。如果第一次请求已经写入数据库、扣减额度、发出消息，第二次原样重放会再次产生副作用。

幂等性必须在业务层显式设计，而不是依赖框架默认行为。

## 做法：三层幂等设计

### 1. 给每次操作分配稳定幂等键

不要用随机 UUID 当幂等键，那只能标识请求，不能去重。应由业务事件生成稳定键，例如：

- webhook：`event_type + source_id + resource_id`
- 定时任务：`task_name + business_date`
- 工具调用：`tool_name + 关键参数 hash`
- 插件操作：`user_id + action + target_id`

请求进入时检查该 key 是否已处理。已处理则直接返回已有结果，不再执行业务逻辑。

### 2. 用数据库唯一约束或状态机做最终防线

在关键资源表上加唯一约束，例如 `(tenant_id, external_id)` 或 `(task_name, business_date)`。即使缓存去重失效，写入数据库时也会触发冲突，从而阻止重复创建。

创建类操作优先使用 upsert/PUT 语义，而不是无条件 insert/POST。

对于长任务，设置状态字段：`pending`、`running`、`done`、`failed`。重入时先原子更新状态：

- `pending -> running`：获得执行权。
- `running`：跳过或检查心跳。
- `done`：直接返回结果。
- `failed`：按策略重试。

### 3. 对外部副作用做记录与对账

如果外部 API 不支持幂等，就在本地记录 `idempotency_key -> external_request_id/status`。发送前检查记录，发送后保存结果。对无法确定是否成功的请求，优先用查询接口确认状态，而不是直接重试。定期对账可以兜住极端情况。

## 可复用示例：Agent 工具调用的幂等装饰器

可以用一个轻量装饰器/中间件处理：

```python
def idempotent_tool(tool_name, key_func):
    def wrapper(*args, **kwargs):
        idem_key = f"{tool_name}:{key_func(*args, **kwargs)}"
        existing = store.get(idem_key)
        if existing:
            return existing
        result = run_tool(*args, **kwargs)
        store.set(idem_key, result)
        return result
    return wrapper
```

这里 `key_func` 必须根据业务参数生成稳定值，而不是每次随机。存储需要支持并发安全，最好用数据库唯一约束或 Redis `SETNX`。

## 踩坑点

- 只在前端防抖/禁用按钮，后端没有幂等，重复请求仍会穿透。
- 唯一约束范围错误：多租户只加 `external_id`，不同租户冲突导致误去重。
- Redis 去重 TTL 过短：重要业务用数据库唯一约束兜底，不要只依赖缓存。
- 并发 check-then-act 竞态：两个请求同时通过检查。必须用原子操作或唯一约束捕获冲突。
- 把“失败重试”当成幂等：第一次执行已经部分成功，第二次重复执行仍可能重复扣减。
- 状态机判断不是原子更新：两个 worker 同时读到 `pending`，同时执行。
- 外部 API 没有幂等支持时盲目重试：需要先确认状态或对账。

## 可复用建议

- 每个自动化任务入口都要求携带 `operation_id` 或 `idempotency_key`，并在日志中记录。
- 将幂等键生成规则写进插件/工具开发文档，避免每个开发者自行发明。
- 对关键写操作加数据库唯一约束，作为最后防线。
- 对消息/通知类操作维护发送记录表，确保同一条业务消息只发一次。
- 每次上线新自动化前，测试重复触发、并发重放、乱序到达、重启恢复四种场景。

## 总结

自动化任务的幂等性不是“防止重复执行”，而是“重复执行不产生额外副作用”。在 OpenClaw/Agent/MCP/插件实践中，把稳定幂等键、数据库唯一约束、状态机前置检查作为默认工程动作，可以显著减少重复触发带来的脏数据、重复消息和外部资源泄漏。与其事后修数据，不如在入口处让第二次执行变成安全的 no-op。
