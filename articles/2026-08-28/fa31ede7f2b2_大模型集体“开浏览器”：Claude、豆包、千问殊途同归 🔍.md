Claude 内置浏览器消息一出，讨论又绕回老问题：大模型到底需不需要“手”？豆包工作流早已把浏览器自动化做成节点，通义千问们也不可能绕开这条路。表面看是功能叠加，实则是 Agent 从“对话工具”向“执行代理”迁移的必经节点。与其争谁先谁后，不如拆开看背后的技术逻辑、落地难度与产品分叉。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/34941557d5b58c92.png)

## 浏览器对大模型意味着什么：从读网页到操作网页
![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/444d1808507b3afd.png)

大模型的知识有截止时间，也无法实时感知互联网。过去常见解法是检索增强（RAG），让模型“读”搜索到的网页片段，但它仍然只能输出答案，不能推进真实任务。内置浏览器或浏览器工具带来的变化是：模型可以点按钮、填表单、滚动、等待、提交，形成多步闭环。

- 举个例子：用户说“帮我查一下明天北京到上海最便宜的机票”，传统助手只能给一个搜索建议；具备浏览器能力的 Agent 可以打开票务页、输入日期、等待结果、按价格排序、截取选项。
- 技术路径上，这不是突然出现的。2023 年 function calling 让模型能调用外部函数；2024 年 Anthropic 推出 Computer Use、OpenAI 发布 Operator、Google 展示 Mariner，都在做“让模型操作界面”这件事。
- 数据现实：网页自动化基准 WebArena、WebVoyager 显示，任务成功率仍偏低，但短链路任务已开始可用。浏览器内置的价值，是把这个能力从开发者 demo 拉进日常产品。

## 豆包工作流早这样干：不是按钮，是可编排节点

豆包/扣子生态更早把浏览器自动化做成工作流组件，开发者可以像搭积木一样拖出“打开网页—点击元素—提取数据—返回结果”，再接上定时器、数据库、大模型节点。

- 底层通常使用 Playwright、Puppeteer 或无头浏览器，再结合 DOM 解析和模型规划。目标不是“帮用户打开一个网页”，而是把网页操作封装成可复用、可组合的执行单元。
- 字节系产品有大量内容处理、电商运营、自动比价等场景，天然需要这种自动化能力，因此产品化得更早。
- 和 Claude 内置浏览器的差异更多是产品形态：豆包偏平台化、工作流化，面向开发者和自动化场景；Claude 偏对话入口直接可用，面向普通用户。
- 举例：一个运营配置“每天 9 点抓取竞品价格并写入表格”，只需要把“定时触发—浏览器节点—大模型解析—表格写入”连成一条链，无需写完整脚本。

## 千问们为什么绕不过：Agent 竞赛的执行层正在收敛

通义千问/Qwen 在开源模型能力上并不弱，但 Agent 要真正落地，只靠模型权重不够，必须有一个稳定、可观测的环境去交互。浏览器恰恰是最通用的环境。

- 任何面向办公、电商、内容、本地生活、SaaS 的 Agent，最终都需要读网页、填表单、抓数据、下单或查询。浏览器能力不是某些产品的差异点，而是通用底座。
- 竞品压力来自多个方向：OpenAI Operator、Google Mariner、Anthropic Claude、字节豆包等都在做。路线已经收敛，不再是“要不要做”，而是“做得多稳、多便宜”。
- 开源生态也在加速：browser-use、Playwright MCP 等项目让浏览器自动化从定制开发变成标准工具，进一步拉低门槛，也倒逼闭源产品提高体验。
- 难点包括登录态、验证码、反爬、动态页面、跨站跳转、安全沙箱、成本控制。千问们如果只做对话不做执行，产品会滑向“能说不能做”的一侧。

## 内置浏览器真正的门槛：不是“能打开”，而是“控得住”

把浏览器打开只是一个动作，真正难的是让模型在高度异构、频繁变化的网页环境里稳定完成任务。可以拆成三层来看：

1. **访问层**：浏览器沙箱、代理、登录态管理、验证码识别、频率限制。
2. **操控层**：DOM 理解、视觉定位、自动重试、弹窗处理、异常恢复。
3. **决策层**：多步规划、状态跟踪、失败回滚、成本预算。

- 页面改版、区域差异、A/B 测试都可能导致 Agent 断裂。一个按钮颜色变一下，对人不算事，对模型可能需要重新适应。
- 多模态路线可以缓解：截图+像素坐标（类似 Computer Use/Operator）不依赖 HTML 结构，但成本和延迟更高；DOM 路线快但脆弱，两套方案往往要混合使用。
- 安全与合规同样绕不开：自动操作涉及目标网站条款、账号风控、数据隐私，平台需要提供隔离环境和审计能力。
- 商业差异开始分化：Claude 强在推理与代码能力，适合复杂多步任务；豆包强在工作流生态与业务场景，适合可复制执行链；千问强在开源和云生态，可能走“模型+云浏览器+MCP”路线。

## 给开发者和产品团队的3条冷思考
![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/011dbc6a976b6554.png)

1. **把浏览器当“环境”，不要当“功能”**。不要只做一个入口，而是要设计可观测、可回滚、可审计的工具链，否则上线后排查问题会非常痛苦。
2. **先用三步任务验证闭环**。比如“打开页面→读取价格→写入表格”，跑通后再扩展跨站、多步、条件分支。小闭环比大 demo 更有价值。
3. **为失败做设计**。网站改版、验证码、风控、超时都要有明确异常路径，记录每个步骤状态，让模型能重试或降级。失败率才是护城河。

浏览器内置不是秘密武器，而是 Agent 时代的基础设施。谁先把任务成功率做上去、把单位任务成本降下来，谁才能真正跨过“能打开网页”的幻觉线。
