在 OpenClaw 环境里配 Cron 任务，最常见的翻车点不是 cron 表达式写错，而是 instruction 写得像需求，不像运行手册。比如“每天早上帮我整理行业新闻”，Agent 收到后可能会因为缺少数据源、输出位置、时区、失败策略，做出完全不同的结果。本文整理一套可复用的 instruction 模板和排错清单。

## 背景：为什么 Cron 任务对 instruction 更敏感

普通对话中，用户可以追问、澄清，但 Cron 触发时通常没有交互。Agent 一旦理解偏差，就会在无人值守状态下执行错误动作。定时任务还容易叠加时区、重复执行、静默失败等问题。OpenClaw/MCP/插件场景下，Agent 可能调用外部工具，这就更需要把边界写死。

## 问题：常见的四类失败

1. **时间与执行环境不明确**：只写 `0 8 * * *`，不知道按哪个时区跑；服务器在 UTC，用户在国内，结果半夜执行。
2. **动作太模糊**：“整理”“分析”“发送”，无法验证对错。
3. **没有幂等设计**：每次运行都追加内容，重复触发后文件里出现多份旧数据。
4. **失败静默**：任务报错但没有任何日志或通知，用户几天后才发现没产出。

## 做法：用固定模板写 instruction

建议把每个 Cron 任务的 instruction 写成以下七段。不是每项都要很长，但关键信息不能缺。

### 1. Role

告诉 Agent 它这次只扮演什么角色，避免它调用无关技能。

```text
Role: 你是一个只负责生成每日技术简报的编辑助手。
```

### 2. Trigger

写清楚 cron 表达式、时区，并用自然语言复述一次。

```text
Trigger: 0 8 * * * (TZ=Asia/Shanghai)，即每天北京时间 08:00 执行。
```

### 3. Input

明确数据来源、路径、工具或 MCP 能力。没有输入来源就写明“无需外部输入”。

```text
Input: 读取 workspace/notes/inbox/ 下最近 48 小时内修改的 .md 文件。
```

### 4. Steps

用编号列出动作，每步只做一件事。不要写“顺便”，不要留下自由发挥空间。

```text
Steps:
1. 读取 Input 中的文件。
2. 提取标题、核心观点、出现的工具/产品名称。
3. 按时间倒序整理为 5 条以内。
4. 写入 Output 指定文件。
```

### 5. Constraints

限制长度、格式、禁止事项。比如：不调用未列出的 API、不修改配置、不发送消息、最多读 20 个文件。

```text
Constraints:
- 每条不超过 80 字。
- 不读取 workspace/notes/private/。
- 不调用任何搜索 API。
```

### 6. Output

指定输出路径、文件名、覆盖还是追加。这里要显式写幂等策略。

```text
Output: 写入 workspace/reports/daily-YYYY-MM-DD.md。
若目标文件已存在，则覆盖写入，不要追加。
```

### 7. Failure

失败时怎么做：记录日志、返回状态、是否重试。

```text
Failure:
- 写日志到 workspace/logs/cron-daily.log。
- 如果失败，不要自动重试，仅在下次触发时再执行。
```

这个模板的核心是：让 instruction 像一份“单人运维 runbook”，而不是一句话需求。

## 踩坑点

- **时区必须显式**。不要在 instruction 里写“早上”，要写 `08:00 + Asia/Shanghai`。如果 OpenClaw 支持环境变量，优先在任务配置里固定 `TZ`。
- **“整理”是最危险的动词**。把它替换成可验证动作：读取、过滤、排序、写入、返回摘要。
- **相对路径会漂移**。Agent 的工作目录可能因会话不同而变化，尽量写绝对路径或 `workspace/` 开头的项目内路径。
- **重复执行没有保护**。用“固定文件名 + 覆盖写入”代替“追加”，或者用日期作为文件名时检查是否已存在。
- **没有输出就是没有验收**。让任务返回一段摘要：处理了几个文件、生成到哪里、是否失败。这样用户至少能看到结果。
- **工具权限过宽**。Cron 任务不要绑定整套插件能力，只给需要的 MCP/工具，减少误调用。

## 可复用建议

1. 把 instruction 存进版本库，和任务配置一起管理，变更留 diff。
2. 新增 Cron 任务先手动跑一次 dry run，读日志确认路径和时区正确。
3. 一个任务只做一件事。多个需求拆成多个 Cron，避免步骤间互相影响。
4. 维护一张任务清单：任务名、trigger、输入、输出、最近状态。不要只靠聊天记录。
5. 设置失败熔断：连续失败 3 次就暂停任务并通知，避免无人值守下持续浪费。
6. 把“失败日志”当作第一现场。日志路径固定，格式一致，便于排查。

## 总结

Cron 任务的 instruction 不需要写得像论文，但要写得像测试用例：触发条件、输入、步骤、约束、输出、失败处理都能回答。对 OpenClaw 这类 Agent 自动化来说，定时任务的可靠性不取决于模型多强，而取决于你给它划定的边界多清楚。把 instruction 当 runbook 维护，Cron 任务才能从“会跑”变成“可靠地跑”。
