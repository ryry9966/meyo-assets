## 背景

在 OpenClaw / Agent / MCP 的自动化实践里，社区自动发帖属于“容易跑通但很难跑稳”的场景。很多方案一开始都长这样：cron 定时触发 → 大模型生成一段内容 → 调社区 API 提交。功能看着正常，但账号很快会被限流、帖子折叠甚至封禁。

问题通常不在“是不是自动发”，而在自动化痕迹太重。固定间隔、固定句式、固定操作路径、失败后无脑重试，这些行为比“发帖”本身更早暴露机器人身份。

## 问题

社区风控不只看单次请求间隔，还会看行为序列。一个账号如果总是每天同一分钟发帖、标题模板相似、浏览和发帖比例异常、发完立刻退出、失败后 3 秒重试，就很容易被识别。

所以节奏控制不是简单 `sleep`，而是把“发帖”还原成一个有时间、有状态、可观测、可退避的会话任务。

## 做法与步骤

### 1. 把发帖拆成状态机

不要让一个函数同时完成“生成 + 发布”。用 MCP 工具链拆分：

`get_board_context` → `pick_topic` → `draft_post` → `preview_content` → `submit_post` → `verify_result`

每个工具调用之间由 policy 层插入等待时间。这样即使内容被风控拦截，也能看到是卡在 preview 还是 submit。

### 2. 间隔要“会话化”，不要只加随机秒数

人发帖前通常有一个过程：打开社区、看几个帖子、犹豫标题、修改内容、发布后停留一会。可以按会话总时长分配：

- 浏览占 40%–60%
- 草稿与修改占 20%–30%
- 发布和检查占 10%–20%

单次会话控制在 6–12 分钟，而不是 5 秒完成所有动作。

抖动函数可以这样写：

```python
def next_delay(base, rng):
    return base * rng.uniform(0.8, 1.25)
```

但更重要的是把多个步骤的延迟累加起来，让整体分布接近人类操作时间，而不是孤立的随机等待。

### 3. 内容指纹与去重

对生成内容做标准化：去掉链接、日期、ID，只保留正文主体；再提取字符 bigram 或做轻量哈希。阈值超过 0.7 就重写，或从语料池换一种开头。

避免总用“大家好，今天来聊聊……”这类开场。可以维护多套开头模板：提问式、观察式、结论先行。标题也不要用固定长度句法。

### 4. 时间窗口与作息

发帖时间应落在目标社区活跃时段内，但不要落在整点。比如：

- 10:00–11:30
- 14:30–17:00
- 20:00–22:30

窗口内再叠加 3–17 分钟的随机偏移。定时任务本身也要加秒级抖动，不要用精确到秒的 cron。

### 5. 失败退避与熔断

失败后不要立即重试。采用指数退避，并设置熔断阈值。连续 2 次失败后，当日任务暂停，并记录错误类型。让系统“知道”风控可能正在观察，而不是继续撞墙。

### 6. 可观测性

每次执行记录：

`task_id`, `planned_delay`, `actual_delay`, `content_fingerprint`, `result`, `status_code`, `retry_count`

面板上能看出间隔分布、重复度、成功率。若某一窗口成功率低于 70%，自动切到 `dry_run` 模式，只生成不发布。

## 踩坑点

- **只加随机 sleep 不等于像人**。人发帖前后还有阅读、编辑、停顿，这些中间步骤要体现在工具调用序列里。
- **忽略环境一致性**。UA、时区、登录态、IP 出口、浏览器指纹，任何一处不一致都可能让节奏控制前功尽弃。
- **内容生成温度过低或过高**。太低容易模板化，太高容易跑题。建议温度控制在 0.6–0.8，再做后置规则过滤。
- **多账号共用一套人格**。不同账号要有不同的间隔范围、语料池、口头禅、回复风格，避免行为相关性过高。
- **失败后重试太激进**。连续快速重试本身就是强机器人信号。

## 可复用建议

把节奏控制抽成 policy 配置，挂在 MCP 工具调用中间件上。例如：

```json
{
  "min_interval_ms": 45000,
  "max_interval_ms": 170000,
  "daily_limit": 2,
  "active_windows": ["10:00-11:30", "14:30-17:00", "20:00-22:30"],
  "backoff_base_ms": 120000,
  "max_retries": 2,
  "fingerprint_threshold": 0.7,
  "dry_run": false
}
```

每次任务读取 policy，在工具调用前后写日志。这样节奏调整不写死在代码里，也可以通过 feature flag 随时关闭。

上线前建议先 dry-run 一周，只生成内容、记录指纹、间隔和窗口分布，不实际发布。观察数据是否落在人类行为边界内，再小流量开一个账号验证。

## 总结

让自动发帖不像机器人的核心不是“更慢”，而是把发帖建模成一个有状态、有边界、可观测的会话。间隔抖动只是其中一环，内容去重、时间窗口、退避熔断、环境一致性和数据闭环同样重要。社区风控识别的是规律，我们要做的就是把规律藏在一组受控的随机变量里。
