## 背景

在 OpenClaw / Agent / MCP 这类实践里，很多人把“记住偏好”理解成两件事：要么在 system prompt 里手写几行固定规则，要么让 Agent 自己翻历史聊天记录。前者能覆盖简单场景，但偏好一多就难以维护；后者看起来更智能，实际执行时经常把一次性指令、当时上下文里的让步、甚至用户随口说的话误判为长期偏好。

结果是：Agent 有时记住了不该记的，有时又漏掉真正重要的偏好；用户重复纠正，Agent 仍然用旧规则回应。记忆不是“存得越多越好”，而是要让偏好能在正确场景被检索、被注入、被纠错。

## 问题

常见失败模式主要有几类：

1. **全量注入污染上下文**：把所有偏好塞进 system prompt，任务还没开始，token 已经被大量无关偏好占满。
2. **自然语言堆砌**：偏好写成一段段散文，Agent 无法稳定解析，容易产生歧义。
3. **没有作用域**：用户说“代码风格用 4 空格缩进”是只对某个仓库生效，还是全局生效？没有 scope 就会冲突。
4. **一次性指令被误记**：用户说“这次先不要自动部署”，Agent 把它写进长期记忆，下次依然不部署。
5. **冲突无策略**：同一偏好先后出现不同值，系统不知道听哪个。

## 做法 / 步骤

我更推荐把 Agent 记忆拆成三层，而不是一个混沌的“记忆库”。

**第一层：短期对话状态**  
只存在于当前会话或任务周期内，例如“本次任务目标”“已完成的步骤”“临时约束”。这类信息不需要长期化，会话结束即可丢弃。

**第二层：长期偏好**  
需要跨会话保留，例如“回复语言用中文”“代码风格用 ruff 默认配置”“部署前先手动确认”。这类偏好要结构化，并有作用域、来源、置信度。

**第三层：规则 / 约束**  
属于硬性边界，例如“不要读取 home 目录下除 projects 以外的文件”“禁止自动推送 main 分支”。这类规则应尽量少而明确，避免频繁变动。

具体实现上，我建议用 MCP server 提供三个基础工具：

- `memory_search(query, scope?)`：按语义或关键词检索偏好。
- `memory_save(entry)`：保存或更新偏好。
- `memory_list(scope?)`：列出某个作用域下的偏好。

偏好数据用 JSON 存储，schema 可以很精简：

```json
{
  "id": "pref_01",
  "domain": "code-style",
  "key": "indent",
  "value": "4-spaces",
  "scope": "repo:openclaw-cn/agent",
  "confidence": 0.9,
  "source": "user_explicit",
  "updated_at": "2025-01-01T00:00:00Z"
}
```

关键字段是 `scope`、`source`、`confidence`。它们决定了一条偏好在什么时候可以被注入。

注入策略不要全量注入，而是按当前任务上下文检索。比如当前任务涉及代码生成，就只拉取 `repo:xxx` 和 `global` 作用域下的代码风格偏好，取置信度最高的前 N 条放入 system prompt。这样上下文干净，Agent 也更容易遵守。

**提取与确认流程：**

1. 用户显式说“记住 / 以后都 / 默认”时，直接保存，置信度设高。
2. 用户没有显式说，但 Agent 从多次行为中推断出偏好时，先保存为低置信度，`source` 标记为 `inferred`。
3. 同一偏好第二次、第三次出现时，提升置信度。
4. 提供 `/memory` 命令让用户查看、删除、纠正偏好。用户纠正时，以 `user_explicit` 覆盖旧值。

## 踩坑点

**把短期限制写成长期偏好**  
用户说“这次先跳过测试”，Agent 可能把“跳过测试”记为长期偏好。解决方法是区分 `scope: session` 和 `scope: long-term`，短期约束直接放第一层，不进入持久化存储。

**偏好冲突没有仲裁规则**  
当同一 key 出现不同 value 时，不要简单覆盖。可以按优先级仲裁：用户显式纠正 > 高置信度偏好 > 低置信度推断；作用域越具体越优先。例如 `repo:xxx` 的规则优先于 `global`。

**自然语言记忆难以检索**  
如果偏好只存在聊天日志里，检索会不稳定。结构化 JSON 更适合确定性读写，语义检索只作为补充，不要作为唯一入口。

**把记忆库做成黑箱**  
用户不知道 Agent 记住了什么，就会逐渐失去信任。一定要提供可读、可编辑的入口。哪怕只是一个 `/memory list` 或一个 YAML 文件，都比完全黑箱好。

**隐私和日志污染**  
记忆写入时避免把整段用户输入原样落盘，尤其是 token、密码、个人路径。只保存必要 key-value，日志里不要输出完整记忆内容。

## 可复用建议

- **偏好文件用 JSON 或 YAML，不要用自然语言段落**。结构化数据更容易校验、合并、去重。
- **给每条偏好加 `scope`**。至少区分 `global`、`repo`、`session`、`project`。
- **系统提示只注入相关偏好**。用检索而非全量拼接。
- **提供显式记忆管理命令**。让用户能说“记住 X”“忘记 Y”“我改主意了”。
- **记录来源和更新时间**。冲突时能追溯，也方便清理过期偏好。
- **做一个最小记忆测试集**。每次改注入逻辑后，跑几条固定场景，确认 Agent 是否按偏好执行。

## 总结

Agent 记忆系统的核心不是把更多东西塞进上下文，而是把偏好变成可检索、可作用域、可纠错的结构化数据。短期状态归短期，长期偏好归长期，硬性规则保持少而清晰。用 MCP 工具做读写，用显式命令做纠错，用测试集验证效果。这样记忆才不会变成 Agent 的新负担，而是真正减少重复沟通的执行基础。
