先别急着把“小龙绕过办公 agent”当成一个攻击事件。热搜里被反复讨论的“小龙”，更像是那类自动化脚本、第三方工具或实验性 Agent 框架的代号。它做的事情并不神秘：不通过官方办公 Agent 的推荐路径，直接完成审批、发消息、写表格、拉数据。真正值得讨论的，不是谁赢了谁，而是为什么办公 Agent 可以被绕过，以及企业应该怎样看待这种绕过。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/67a8d477402df9bb.png)

## 办公 Agent 并不是一道安全边界

很多人的默认假设是：公司上了办公 Agent，它就像一个带权限的智能管家，所有自动化操作都必须经过它。但从工程实现看，它更多是一个“调度中间层”。

- 典型办公 Agent 的链路是：用户指令 → LLM 解析 → 工具调用（tool calling）→ 企业应用 API。
- 真正有权限的不是 Agent，而是它背后的账号、token、API Key，以及浏览器登录态。
- 不少 Agent 在审批、发消息时，只是代替人调用了某个内部接口；接口校验的仍是“这个账号能否操作”，而不是“这个操作是否由 Agent 发起”。
- 也就是说，Agent 更像一个自动化外壳，不是独立的安全网关。

历史背景也很类似。从早期 Excel 宏、按键精灵，到后来的 RPA，再到今天的 LLM Agent，自动化的核心一直没变：用程序替代重复人工。变的只是交互方式更自然、能理解更多模糊指令。但只要是外壳，就有可能被绕开。

## “绕过”绕掉的通常是什么？

“小龙绕过办公 agent”这句话容易让人误解为“打败了 AI”。实际上被绕过的，往往不是智能能力，而是平台附加的管控、审计和限流。

- 官方 Agent 路径可能包括：权限校验、操作留痕、审批策略、频率限制、敏感动作二次确认。
- 绕过路径可能直接调用内部 API，或在浏览器里模拟点击，从而跳过这些附属机制。
- 结果就是：同一个人、同一个账号、同一个操作，但一条路径有完整审计，另一条路径只留下很少甚至没有日志。
- 效率上的差异很直接：少几次确认、少几个中间步骤、少一点 UI 等待。

举一个虚构但常见的例子：市场部同事要批量给 200 条线索打标签。官方 Agent 要求逐条确认，因为涉及客户数据。一个脚本可以直接调用 CRM 的批量更新接口，几秒钟完成。表面看效率很高，但如果脚本里的标签映射错了一列，错误也会被批量写入，而且没有日志可查。绕过的代价不是安全被入侵，而是治理被旁路。



## 常见技术路径：API、RPA、浏览器与 MCP

把“绕过办公 Agent”拆开看，常见路径可以归为几类。

1. **私有 API 逆用**：通过抓包等方式拿到企业内部应用接口，用脚本重放请求。好处是稳定、快速，坏处是接口一旦变化就要维护。
2. **RPA / UI 自动化**：影刀、UiPath、Playwright 这类工具直接操作界面，点击按钮、填写表单。它不碰后端接口，但同样可以绕过 Agent。
3. **浏览器插件与脚本注入**：在企业微信、飞书、钉钉的 Web 端注入脚本，拦截请求、修改 DOM，一键批量操作。
4. **MCP 工具注册**：不少 Agent 框架支持 Model Context Protocol，开发者可以注册自定义工具。如果权限设计不严，模型就能调用到范围之外的接口。

这些路径的共同点是：它们都使用合法账号和合法设备，只是没有走官方 Agent 的推荐通道。因此传统安全设备很难从“身份可信度”上发现异常。

## 为什么防御起来很别扭？

这是整个话题里最值得展开的部分。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/e2e888243fcf71f5.png)

- 办公场景中，“人在操作”和“脚本在操作”没有天然边界。同一个人可能上午手动点审批，下午用脚本批量处理。
- 传统安全产品擅长看 IP、设备、账号是否异常，但“绕过”行为往往来自可信身份，特征不明显。
- 企业内部的自动化需求非常分散：销售要批量发消息，财务要批量导表，运营要自动汇总日报。这些需求本身合理，只是走了旁路。
- 行为检测需要识别非人类操作，比如鼠标轨迹、调用频率、操作时间分布、接口序列。但准确率有限，误报一多，安全告警就没人看了。
- 如果安全团队一味封堵，很容易陷入“猫鼠游戏”：封掉一个接口，新的自动化工具又会冒出来。

所以问题不在“小龙”有多强，而在于办公 Agent 平台在权限模型、审计能力和开放生态上，还没有跟上用户对自动化的实际需求。

## 真正的风险点在哪里？

把视角拉回企业视角，值得警惕的通常不是“有人用了脚本”，而是三件事。

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/256ebda979d2e45e.png)

1. **不可审计**：操作没有留痕，出现问题无法回溯。
2. **权限过大**：一个自动化脚本拿到的 token，可能远超过完成当前任务所需的最小权限。
3. **第三方工具不可控**：员工使用外部工具时，数据可能经过第三方服务器，或脚本被植入额外逻辑。

如果一家公司的办公 Agent 能被轻易绕过，说明它把“安全边界”错误地寄托在了 Agent 这一层，而没有下沉到 API、账号和权限系统。更麻烦的是，很多自动化脚本会把 API Key 硬编码在本地文件里，一旦员工离职或设备丢失，这个 Key 就可能变成长期暴露的入口。

## 三条冷思考

绕开办公 Agent 这件事，本质上不是安全对抗的胜负，而是效率需求与治理能力之间的摩擦。

1. **把“绕过”当成需求信号**：员工愿意花时间写脚本、调 API，说明官方流程存在明显摩擦。企业与其追着封堵，不如先问一句：哪个环节让人不想用官方路径？
2. **把权限管到接口层**：不要只信任 UI 和 Agent 外壳。API、MCP、RPA、浏览器插件都需要纳入统一的身份、权限与审计体系。最小权限原则在这里不是口号，而是关键动作。
3. **提供低摩擦的合规通道**：公布稳定的 API/SDK、提供可审计的自动化平台，让员工在合规环境里也能高效完成批量操作，往往比围堵更有效。



办公 Agent 的价值不在“挡住所有自动化”，而是让自动化可视、可控、可回溯。小龙能绕过它，是一个提醒：真正的安全边界，永远不该只放在最外层。
