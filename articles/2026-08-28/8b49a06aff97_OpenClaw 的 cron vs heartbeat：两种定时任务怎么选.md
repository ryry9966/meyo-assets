## 背景

OpenClaw 里想做自动化，基本绕不开两个内置触发：`cron` 和 `heartbeat`。它们都能让 agent 周期性地“醒来”执行任务，但在配置、语义和适用场景上不是一回事。刚接触时很容易混用，结果要么任务漏跑，要么同一个 agent 被反复唤醒，状态越跑越脏。

这篇文章不讨论“谁更强”，只从工程使用角度讲清楚：什么时候选 cron，什么时候选 heartbeat，以及排障时该看哪里。

## 问题

典型的困惑是：  
- 我想每天早上 9 点生成一份简报，该用哪个？  
- 我想每 30 分钟检查一次服务健康，该用哪个？  
- 为什么 heartbeat 任务经常重复触发？  
- 为什么 cron 任务有时不按预期执行？

核心在于：cron 面向“墙钟时间点”，heartbeat 面向“运行节奏”。

## 做法/步骤

### 1. 先分清触发语义

`cron` 使用标准 cron 表达式，匹配系统时区下的具体时间点。例如：

```json
{
  "agents": {
    "defaults": {
      "cron": [
        {
          "name": "morning-brief",
          "schedule": "0 9 * * *",
          "task": "从数据源拉取昨日数据，生成简短晨报"
        }
      ]
    }
  }
}
```

它适合“每天/每周/每月固定时刻”的任务。触发条件由日历决定，和 agent 启动多久、上次是否成功没有关系。

`heartbeat` 则更像一个固定间隔的脉冲。例如：

```json
{
  "agents": {
    "defaults": {
      "heartbeat": {
        "interval": "30m",
        "task": "检查待处理队列、未确认告警和磁盘占用"
      }
    }
  }
}
```

它适合“每隔一段时间就巡检一次”的场景。触发节奏由间隔决定，不关心现在是几点。

### 2. 按任务性质选择

一个简单判断：

- 任务与自然时间有关：用 cron。比如“工作日早上 8:30 发提醒”“每周五下午归档”。
- 任务只与时间间隔有关：用 heartbeat。比如“每 20 分钟扫描一次失败任务”“每 15 分钟刷新缓存”。
- 任务需要避免在业务高峰期执行：优先 cron，因为可以精确避开。
- 任务必须在多个时间点同时覆盖：cron 可以写多条，heartbeat 只有单一间隔。

### 3. 混合使用时的推荐结构

不要把所有事情都塞进 heartbeat。工程上可以把两类任务分层：

- `cron` 负责有业务含义的定时作业：数据拉取、报表、外部同步、提醒。
- `heartbeat` 负责 agent 自身或系统的自愈巡检：连接状态、积压队列、资源阈值、临时文件清理。

这样职责清晰，也更方便回滚和定位。

## 踩坑点

**1. cron 时区不是本地时区**  
容器默认时区常常是 UTC。配置 `0 9 * * *` 你以为早上九点，实际可能是下午五点多。先确认宿主机或容器的 `TZ`，再写表达式。必要时在配置中显式声明时区。

**2. heartbeat 会放大上下文增长**  
heartbeat 每次唤醒 agent 都可能带上历史 memory 或 session 片段。如果任务输出很长，几轮之后上下文就会膨胀，token 消耗和响应变慢。建议 heartbeat 任务保持短输出，或者显式裁剪/不回写 memory。

**3. 重入和重叠执行**  
cron 任务如果上次还没结束，下一次触发可能再次进入，导致并发写同一状态文件。heartbeat 同理。一定要做幂等：外部队列、状态目录里的 run id、文件锁，或至少在任务开头检查是否存在同类运行。

**4. 把 cron 配到插件层级没生效**  
OpenClaw 中不同层级配置会有合并规则。插件自己声明 cron 和 agent defaults 里的 cron 可能作用在不同 agent。排障时先确认最终生效配置，而不是只看配置文件表面。

**5. 短 interval 测试心跳**  
把 heartbeat interval 设成 10s 来验证逻辑很正常，但容易留下“心跳风暴”影响其他任务。测试完记得恢复，或者用单独测试 agent。

## 可复用建议

1. 所有定时任务都写成幂等，即使触发器偶尔重入也不产生脏数据。
2. 给每个任务命名，并输出明确的 run 开始/结束日志，方便回溯。
3. 外部长任务不要直接在 cron 里做完整处理，可以 cron 触发出队，由 worker 或后续 agent 消费。
4. heartbeat 只做“检查并报告”，不要做复杂决策；需要决策时把结果交给 cron 或人工流。
5. 配置变更后手动触发一次，验证最终配置是否生效，再等自然周期。

## 总结

OpenClaw 中，cron 负责“到点执行”，heartbeat 负责“按节奏执行”。选择依据不是哪个更高级，而是任务是否绑定真实时间。混用并不可怕，关键是任务边界清晰、幂等、可观测。把业务定时作业交给 cron，把自愈巡检交给 heartbeat，能避免大部分定时任务带来的奇怪问题。
