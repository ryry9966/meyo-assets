# Git 自动化：让 AI 助手帮你管理代码提交和分支

## 背景

在 OpenClaw 这类 Agent 自动化环境里，很多 Git 操作是重复且规则明确的：看状态、建分支、写提交、推远端。这些动作天然适合交给 AI 处理，但直接把 shell 权限放开给 Agent，风险会迅速超过收益。更实际的做法是：只暴露有限的 Git 能力，让 AI 在受控边界内完成提交和分支管理。

## 问题

一个常见误区是给 Agent 配一个 `bash` 工具，然后让它“自己看着办”。结果通常是：

- `git add .` 把构建产物、本地配置、密钥文件一起提交；
- commit message 出现幻觉内容，或只有 “fix bug”；
- 误切分支导致未提交修改丢失；
- 冲突处理时 AI 自己“聪明地”合并，反而引入错误。

所以问题不是“能不能让 AI 操作 Git”，而是“怎么把 Git 暴露给 AI 才能稳定、可审计、不闯祸”。

## 做法 / 步骤

### 1. 用 MCP 暴露白名单 Git 命令

不要给 Agent 原生的 shell 工具。可以接 Git MCP，或自己包一层只允许固定命令的工具。最小可用集合建议：

```text
允许：
git status
git diff --stat
git diff -- <path>
git log --oneline -n 20
git branch --show-current
git branch --list
git add <whitelist-path>
git commit -m "<message>"
git checkout -b <branch>
git push -u origin <branch>

禁止：
git push --force
git reset --hard
git clean -fd
git branch -D
删除远程分支
任何 git config、credential 修改
```

白名单路径可以限定为 `src/`、`docs/`、`tests/`，避免 Agent 误提交根目录下的 `.env`、`dist/`、`node_modules/`。

### 2. 把规则写进系统提示词或规则文件

在 OpenClaw 的任务配置里明确：

```text
你是 Git 自动化助手。
- 只使用提供的 Git 工具，不要求额外 shell 权限。
- 提交前必须运行 git status 和 git diff --stat。
- 禁止提交包含密钥、token、构建产物的文件。
- commit message 使用 conventional commits 格式。
- 任何 push、删除分支、force 操作必须先给出计划并等待用户确认。
```

将这段规则版本化管理，比每次在对话里口头约束更可靠。

### 3. 先生成计划，再执行写操作

对稍微复杂的任务，让 Agent 先输出类似下面的计划：

```text
计划：
1. 从 main 切出 feat/openclaw-git-automation
2. 暂存 src/git_tools.py、tests/test_git_tools.py
3. 提交：feat(git): add safe git automation helpers
4. 不自动 push，等待确认
```

用户确认后，Agent 再按计划执行。这样能把大多数误操作拦在执行前。

### 4. 在提交前加一层轻量检查

可以用 pre-commit hook 或 CI 做最后兜底，例如检查：

- 是否有大文件、密钥模式；
- commit message 是否符合规范；
- 是否误提交了非白名单路径。

Agent 的提交不会绕过这些 hook，等于给自动化再加一道防线。

## 踩坑点

1. **`git add .` 是最常见的灾难来源。** 即使 Prompt 里写了“不要 add .”，Agent 在上下文较长时仍可能偷懒。最好在工具层直接禁止无参数 `git add`，只允许逐个文件或白名单路径。

2. **commit message 会“一本正经地编造”。** 如果 Agent 没有看到完整 diff，它会根据任务描述生成看似合理但实际不准确的提交信息。因此提交前必须让 Agent 读取 `git diff`，并限制 diff 长度，必要时只提交部分文件。

3. **未提交修改被分支切换搞丢。** 让 Agent 在切分支前先确认 `git status --porcelain` 为空，或者先 `stash` 并记录。不要假设 Agent 会主动处理。

4. **冲突不要全自动解决。** 自动 merge/rebase 在冲突时很容易选择错误的一侧。建议遇到冲突就停下来，把冲突文件和相关 diff 交给用户，而不是让 Agent 继续“修复”。

5. **身份和凭证要隔离。** 给 Agent 使用独立的机器人账号或 token，`user.name` 和 `user.email` 也单独配置。不要用个人主账号跑自动化，审计时容易混在一起。

6. **上下文窗口有限。** 大型 diff 会被截断，Agent 只看到部分改动就提交。可以限制单次提交的文件数量，或按模块拆分提交任务。

## 可复用建议

- **只读先行。** 任何写操作前先跑 `status` 和 `diff --stat`，这一步不是浪费时间，是建立可验证上下文。
- **默认不 push。** push 和删除分支必须有人工确认，写入工具层比写在 Prompt 里更可靠。
- **模板化提交信息。** 给 Agent 一个固定模板，例如 `feat|fix|docs|chore(scope): summary`，降低随意发挥。
- **保留审计日志。** 记录 Agent 执行的每条 Git 命令和结果，方便回溯“这个提交到底是谁让它干的”。
- **从小任务开始。** 先让 Agent 负责生成分支名和 commit message，提交仍由人执行；稳定后再逐步放开。

## 总结

Git 自动化不是把 shell 丢给 AI，而是把高频、规则明确的操作封装成受限工具，再通过清晰的 Prompt 和审批流程控制风险。对 OpenClaw 用户来说，最值得投入的不是“让 AI 做更多”，而是“让 AI 做错时能被拦下”。先把边界和检查做好，提交和分支管理才能稳定地交给 AI 助手。
