## 背景

日常开发里，Git 操作很琐碎：提交信息写得随意、分支命名不统一、切分支前忘记检查工作区、PR 描述缺失。这些问题单独看不严重，但仓库变大、协作者变多之后，追溯成本会明显上升。

在 OpenClaw / Agent / MCP 的实践中，Git 是一个很适合交给 AI 助手处理的场景：它规则明确、命令可审计、风险相对可控。只要把权限边界设好，AI 可以帮我们做提交信息整理、变更摘要、分支创建等低风险操作，而不是让人每次手写 `git add` 和 `commit message`。

## 问题

直接让 AI 全自动管理仓库并不现实。真正的难点不是“能不能执行 Git 命令”，而是：

- 哪些文件可以自动提交，哪些必须人工确认；
- 大 diff 会不会撑爆上下文窗口；
- 分支切换会不会误伤未提交改动；
- 是否允许 push，是否需要强制禁止 force push；
- 提交信息是否基于真实 diff，而不是 AI 自己编造。

所以工程化的目标不是“AI 替你提交”，而是“AI 帮你整理，你保留确认和 push 权限”。

## 做法 / 步骤

### 1. 接入 Git MCP Server

在 OpenClaw 中挂载一个 Git MCP Server，常见工具包括 `git_status`、`git_diff_unstaged`、`git_diff_staged`、`git_add`、`git_commit`、`git_create_branch`、`git_checkout`、`git_log`。

建议把工具拆成只读和写操作两类：只读工具默认开放，写操作需要用户确认或显式授权。这样可以避免 Agent 在长任务里自作主张提交。

### 2. 写清楚 Agent 的提交规则

仓库里维护一个 `AGENTS.md` 或 `.openclaw/git.md`，把规则固定下来。例如：

- 提交信息遵循 Conventional Commits；
- 默认只 add 已跟踪文件，未跟踪文件必须显式确认；
- 禁止提交 `.env`、`.pem`、`*.local` 等敏感文件；
- 禁止 `push --force`，默认不允许 push 到 `main` / `master`；
- 执行写操作前先返回计划，等用户确认。

这些规则比模型能力更重要，能避免很多“好心办坏事”。

### 3. 提交流程

用户说“帮我提交当前改动”时，建议流程是：

```
git status --porcelain
git diff --stat
git diff -- <file>
```

Agent 先看状态和统计，再按文件读取 diff。如果变更文件很多，先让用户选择范围，而不是一次性把所有 diff 塞进上下文。

生成提交信息时，用模板约束：

```
type(scope): subject

- 主要修改点
- 变更原因
```

然后列出将要 add 的文件和完整 message，等用户确认后再执行 `git_add` 和 `git_commit`。

### 4. 分支流程

分支操作更危险。切分支前必须先检查工作区：

```
git status --porcelain
```

如果工作区不干净，提示用户先 commit 或 stash，不能直接 checkout。

创建分支时可以做命名校验，例如统一用：

```
feat/<issue-id>-<slug>
fix/<issue-id>-<slug>
chore/<slug>
```

Agent 可以生成候选分支名，但最终创建前让用户确认。

### 5. 用 pre-commit 兜底

把 lint、格式检查、单测放到 pre-commit hook 里。AI 提交时如果 hook 失败，把错误输出返回给 Agent，让它修正或提示用户处理。这样即使提交信息被 AI 写好了，也不会绕过质量检查。

## 踩坑点

**大 diff 爆上下文**

`git diff` 在大型仓库里可能非常大。不要直接全量读取。先 `git diff --stat`，再限制路径和行数。比如变更超过 20 个文件时，让用户指定要提交的文件，而不是全部处理。

**误提交未跟踪文件**

AI 很容易把 `git add .` 当成默认操作。必须明确：默认只 add 已跟踪文件。未跟踪文件要逐个列出，确认后才加入。尤其要防止把 `.env`、本地配置、密钥文件加进去。

**分支切换丢改动**

切分支前必须检查 `git status --porcelain`。有未提交改动时，不能直接 checkout。可以提示 `git stash` 或先提交到当前分支。不要信任 AI 的“应该没问题”。

**权限失控**

不要给 Agent 完整的 push 权限。最好使用只读 token，或者只允许 push 到用户自己的 fork 分支。禁止 force push 和直接修改受保护分支。

**提交信息幻觉**

AI 有时会生成与 diff 不符的提交信息。要求它引用具体文件名或函数名，并且提交前用 `git diff --cached` 再次确认暂存区内容。不要把模型的描述直接当成事实。

## 可复用建议

- 维护仓库级 `AGENTS.md`，让每个 Agent 进入仓库时都能读到规则；
- 提交信息模板固定下来，减少返工；
- 写操作前先输出计划，确认后再执行；
- 记录 Agent 的 Git 操作日志，便于审计；
- 分支命名用脚本或规则校验；
- 对敏感路径设置白名单/黑名单，防止误提交。

## 总结

Git 自动化适合作为 Agent 实践的入门场景：它足够常见，收益也很直接。关键不是让 AI 拥有更多权限，而是把边界设计清楚。让 AI 做 diff 阅读、提交信息整理、分支命名建议和状态检查，人保留最终确认和 push 权限。

当 AI 开始管理 Git 时，最好的结果不是“更快地提交”，而是“更少地返工”。这也是工程化自动化真正该追求的方向。
