## 背景

OpenClaw-CN 社区里插件更新、MCP 工具收录、踩坑复盘这类内容，很适合沉淀成主题帖。我们最初想做一个机器人：给定主题，自动生成技术帖并发布。第一个版本很简单，定时任务调 LLM 生成 Markdown，再通过社区 API 发出去。跑了一周，删了 3 篇格式混乱的帖子，还触发过一次限流。

于是推倒重来，把重心从“自动发布”移到“可审核、可回滚、可追踪”的管道上。

## 问题定义

1. 生成质量不稳定：标题超长、段落堆砌、代码块丢失。
2. 社区规范和 API 限制较多：标签数量、外链规则、Markdown 渲染差异。
3. 发布链路不可观测：失败后不知道卡在生成、审核还是发布哪一步。
4. 缺少回滚手段：错误帖子删不掉或需要人工处理。

## 做法/步骤

### 1. 先做生成和预览，不接发布

第一周机器人只生成本地 Markdown 文件，通过内部渠道预览。稳定后才接发布 API。这个阶段解决了一个核心问题：内容格式是否达到社区可接受标准。

### 2. 用 OpenClaw 组织 Agent 与 MCP 工具

把社区发布能力封装成 MCP 工具：

- `community.create_post`
- `community.update_post`
- `community.delete_post`
- `community.health_check`

Agent 分成三层：

- **采集层**：从 RSS、GitHub release、内部 issue 聚合原始条目。
- **生成层**：做摘要、改写、标题生成，输出结构化 JSON，不允许直接输出最终正文。
- **执行层**：根据状态机决定调用哪个 MCP 工具。

### 3. 引入状态机与审核队列

帖子状态固定为：

`draft -> validating -> ready_for_review -> approved -> publishing -> published | failed`

只有低风险内容，比如社区周报，允许自动发布；其他内容必须进入审核队列，由人工确认后再发布。状态机让每一步都可追踪，也方便统计卡点。

### 4. 发布前 dry-run 与幂等

每次发布前生成 Markdown 预览，发到内部审核频道。发布请求带上 `idempotency_key`，使用内容指纹，即标题、正文、来源 URL 三者的 sha256，防止重复提交。

### 5. 记录与回滚

每次发布记录：指纹、状态、API 返回、耗时、错误信息。失败进入失败队列，支持一键调 `community.delete_post` 或 `community.update_post` 回滚。

## 踩坑点

- **Markdown 渲染不一致**：本地预览正常，社区 API 会吞掉部分 HTML 标签。统一用 sanitize 白名单处理。
- **JSON 输出不稳定**：最早靠 prompt 让模型输出 JSON，经常少括号。改成 function calling / tool schema 后稳定很多。
- **MCP 工具超时**：社区 API 偶尔超过 30 秒，会把 Agent 卡住。把工具超时设 10 秒，失败重试 3 次，并给用户返回明确错误。
- **时区问题**：定时任务用 UTC，但社区用户习惯北京时间。统一在发布前转换，日志里同时记录 UTC 和本地时间。
- **内容指纹不够**：只对正文做指纹，改个标题又会发一次。改成标题、正文、来源 URL 联合指纹。
- **外链触发风控**：去掉 tracking 参数，外链进人工审核白名单。

## 可复用建议

- 生成与发布分离，写操作必须可回滚。
- Prompt 版本与模型版本一起记录，出问题可回滚到上一版。
- 先跑影子模式：生成但不发布，和人工整理结果做对比。
- MCP 工具设计成幂等，必须有明确 ID 和 `idempotency_key`。
- 保留 `source_url`、原始作者、发布时间等元数据，便于溯源。
- 观察指标：发布成功率、审核通过率、重复率、平均人工修改次数。

## 总结

AI 社区发帖机器人最实用的部分不是“自动发”，而是“标准化管道”。真正长期运行的版本里，规则校验、状态机、审核队列和回滚机制占了一大半工作量。OpenClaw 的 Agent + MCP 工具链适合做这种结构化流程，但别把所有判断都交给模型：规则管边界，LLM 管内容，人工管例外，这样才不容易翻车。
