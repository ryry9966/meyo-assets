“只降价20%，账单却少80%。”这个说法拆开看像一道反直觉的算术题：账单约等于单价乘以 token 消耗量，单价只降20%，除非 token 消耗量也大幅下降，否则总账单不可能少80%。最近 GPT-5.6 被拉到 Claude 擅长的编程赛道比较，社区说它“重算编程账”，真正值得拆的不是标价牌上的每百万 token 价格，而是完成一个编程任务的成本结构被改了。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/39b4e6429b8d4117.png)

## 1. 账单公式：降单价只是明面上的变量

编程 AI 的账单很少是“一次调用多少钱”，更像一组多变量函数。要看懂“降20%省80%”，先把变量列出来。

- **输入 token 要计费**：系统提示、仓库索引、最近文件、工具定义、历史对话，这些内容经常重复发送。
- **输出 token 更贵**：代码、解释、diff、工具调用参数；很多平台的输出单价是输入的 3~5 倍。
- **缓存命中另算**：多数 API 对缓存命中的输入 token 只收很低费用，cached 和 uncached 可能相差一个数量级。
- **推理 token 是隐藏项**：思维链、内部规划如果纳入计费，任务越复杂，这部分越贵。
- **重试和多轮往返是乘法器**：Agent 调用一次工具，往往要重新携带上下文；十几次工具调用会把成本放大。

从 2021 年 Codex 只做单文件补全，到现在 Agent 读整个仓库，输入 token 从几百膨胀到几十万；输出侧也从补全几行代码，变成生成完整 PR 描述、测试计划和回归分析。看不懂这些变量，只看单价，很容易误判。

所以，账单≈单价×有效 token 量。如果单价降20%，同时有效 token 量降75%，最终就是 0.8×0.25=0.2，少80%。这就是这道算术题的完整答案：单价只是其中一个变量。

## 2. 编程任务里，token 都花在哪了

很多人以为编程模型的主要开销是“生成代码”，但在实际工作流里，token 消耗大头可能不在生成，而在输入和重复往返。

- **长上下文是刚性成本**：一个中型项目只读上下文可能就占 20k~60k token。目录树、接口签名、相关代码片段、测试文件，每轮对话都全量重发，成本线性上升。
- **工具调用是乘法器**：一次修复 bug 可能触发多次文件搜索、读取、运行测试。每次工具往返都要携带大量 JSON 和状态，形成“输入—调用—返回—再输入”的长链条。
- **输出冗余很常见**：模型为了把思路讲清楚，常会先解释、再给完整代码、再补测试建议。对熟手工程师，只需要一段 diff，但账单不会因为你不需要解释而减少。
- **失败重试是隐藏税**：一次修改后测试不过，Agent 会带着错误日志再次调用，错误上下文越滚越大。



以一次典型代码修改为例：一个 500 文件的中型服务，仓库索引和相关接口定义可能就有 35k token。Agent 要跨 5 个文件修复一个问题，可能读取文件 7 次，每次请求携带 8k~20k token，历史消息不断膨胀，最终输入侧消耗可以轻松超过 500k token。输出方面，如果模型返回“完整函数实现+说明”，可能达到 1200~1800 token；如果改成“只输出结构化 diff”，同样修改可能只消耗 200~400 token。输入缓存命中率则决定那几十 k token 是按原价，还是按接近一折的价格计费。

## 3. GPT-5.6 的“省法”可能藏在三个底层动作

如果“降价20%、账单少80%”成立，背后不会是简单的标价调整，更可能是 token 消耗结构被重做。从公开信息和行业规律看，有三个方向最值得关注。

- **输出从“作文”变“diff”**：在编程 Agent 场景里，新模型或许默认返回 unified diff、JSON patch 或结构化修改指令，而不是带注释的完整文件。输出 token 从 1500 降到 200，降幅就是 85% 以上。
- **缓存命中率大幅提升**：模型如果能把系统提示、工具定义、仓库上下文的缓存键稳定复用，大量输入可以按 cached 价格计费。某些平台上，cached input 价格只有 uncached 的十分之一甚至更低。Prompt caching 的原理是对长前缀做哈希，新请求若与缓存前缀相同，只对新增部分全额计费，前缀部分按缓存价处理。
- **按难度分层推理**：简单补全、重命名、解释代码、写单元测试，不需要长思维链。模型如果能在低难度任务上少烧 reasoning token，就能省下一大块隐藏成本。结构化输出也会减少解析错误，间接降低重试次数。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/d2df41a5b8c0f050.png)

这三点有一个共同特征：它们都属于“有效 token 消耗优化”，而不是单纯让每 token 变便宜。这也是为什么账单降幅会远大于单价降幅。

## 4. 为什么是 Claude 的地盘

过去一两年，Claude 在编程领域积累了不少实际口碑。长上下文、代码生成质量、缓存设计，以及围绕它成长起来的一批 CLI 和 IDE 工具，让很多开发团队把 Claude 当作默认选择。

- Claude 的缓存机制让长上下文工作流成本可控，适合需要反复读仓库的编程 Agent。
- 它的代码编辑体验相对成熟，很多团队在“改文件、跑测试、给 diff”的闭环里形成了依赖。
- GPT-5.6 这次带来的压力，不是“每百万 token 便宜 20%”，而是“完成一个 PR、修一个 bug、跑一遍审查的总花费可能少一大截”。

竞争焦点正在从“每百万 token 多少钱”转向“单位任务成本”。当大量生产级 Agent 开始批量跑重构、测试生成、代码审查时，总成本比单价更能决定选型。对开发者来说，评估指标也在从单纯的 pass@1，慢慢变成 cost per resolved task。

## 5. 便宜之后，真正该重算的三笔账

降价是好事，但便宜不自动等于划算。团队如果因为“账单少八成”就切换，最好先重算三笔账。

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-08-28/72aad3db6d423cce.png)

1. **别只盯 input/output 标价，先看自己的 token 结构**  
   如果你的场景输入 token 占比超过 70%，缓存命中率比单价敏感得多；如果输出大量解释性文字，那模型是否精简输出才是省钱关键。可以先统计近 30 天调用日志，算清楚输入输出比、缓存命中率和重试率。

2. **优化缓存键，比盲目调低 temperature 更实际**  
   把系统提示拆成稳定前缀、把仓库上下文分块、让工具定义保持一致，往往比换一个便宜模型还能压成本。缓存命中率每提升 10 个点，可能比单价降 20% 更划算。

3. **旧 prompt 可能需要重写**  
   当模型从“详细解释+完整代码”转向“精简 diff”，原来那些“请给出完整实现”的指令，反而可能诱导多余输出，甚至破坏工具调用格式。最好用小的 eval set 评估新模型的输出格式、diff 质量，以及返回 token 中有效内容占比。

说白了，真正值得羡慕的不是“省了八成”，而是这背后对 token 消耗结构的重新设计。编程 AI 的成本竞争，已经过了只拼单价的第一阶段，进入拼缓存、拼输出精简、拼任务完成效率的第二阶段。下一次再看到“降价 XX%，账单少 XX%”的消息，先别急着欢呼，问一句：它到底少发了多少 token？
