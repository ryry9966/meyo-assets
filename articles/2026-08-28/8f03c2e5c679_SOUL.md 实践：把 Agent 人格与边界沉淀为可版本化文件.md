## 背景

在 OpenClaw 里给 Agent 配置人格，最容易出现的问题是：把身份、语气、工具边界、异常处理全部塞进 system prompt。单个 Agent 还能维护，一旦项目里出现多个 Agent、多套 MCP 工具和自动化流程，prompt 会迅速膨胀，改一处可能影响全局，也很难评审和回滚。

SOUL.md 更适合作为稳定的角色层文件。它不负责框架规则，也不负责具体任务指令，而是单独维护“这个 Agent 是谁、能做什么、不能做什么、遇到边界时怎么办”。

## 问题

实际使用中常见三类问题：

1. **人格漂移**：同一个 Agent 在不同会话里语气和行为不稳定，有时保守，有时激进。
2. **权限边界不清**：MCP 工具暴露后，Agent 会尝试调用未授权的写操作或删除操作。
3. **维护失控**：多人修改 system prompt，没有版本记录，改坏了难以定位。

SOUL.md 的价值不是写“更高级”的人设文案，而是把行为契约工程化。

## 做法 / 步骤

### 1. 用固定结构写 SOUL.md

不建议写成长段落。建议至少包含 Identity、Voice、Allow、Deny、Escalation、Tool Policy 六个小节。示例：

```md
---
id: ops-agent
version: 1.2.0
owner: platform
---

# Identity
你是 OpenClaw 运维助手，只做诊断与可逆操作。

# Voice
先给结论，再给证据；不用“可能”“建议”开头。

# Allow
- 查询日志
- 只读检查
- 生成变更方案

# Deny
- 删除、重启、修改生产配置
- 绕过人工确认直接执行高危动作

# Escalation
影响生产或无法判断时，停止操作并输出人工处理步骤。

# Tool Policy
- MCP 工具白名单前缀：read_, get_, list_
- 禁止调用：write_, delete_, exec_
```

### 2. 与 system prompt 分层加载

system prompt 只放框架规则，例如“遵守 SOUL.md 中的边界”“工具调用前先检查 Tool Policy”。SOUL.md 作为角色层单独注入。OpenClaw 项目可以按任务选择不同 SOUL 文件，例如 `soul/ops.md`、`soul/docs.md`。

### 3. 把边界下沉到 MCP / 插件层

SOUL.md 里的 Deny 是意图约束，不能替代真实权限控制。MCP server 必须配置 allowlist、只读 token，或在代理层拦截危险工具。Agent 侧的边界声明和 MCP 侧的能力限制，二者缺一不可。

### 4. 用回归用例验证

准备 10-20 条测试，覆盖：

- 是否拒绝越界操作；
- 工具失败时是否按 Escalation 输出；
- 多轮对话后是否保持 Voice；
- 是否只调用 Tool Policy 允许的工具前缀。

## 踩坑点

- **太长导致规则失效**：SOUL.md 超过 1.5KB 后，模型容易忽略中后段内容。建议控制在 200-400 词，尽量用列表而非散文。
- **与 system prompt 冲突**：system 说“尽量完成任务”，SOUL 说“禁止自动执行”，模型可能倾向服从更系统的指令。关键词要统一，不要把 Deny 写成“尽量别做”。
- **只靠提示词限制 MCP 权限**：这是一层纸。工具 schema 一旦暴露，在诱导下 Agent 仍可能尝试调用。必须在 MCP server 端做最小权限。
- **多 Agent 共用同一个 SOUL**：客服 SOUL 套到运维 Agent 上，会出现“礼貌但危险”的行为。每个 Agent 应使用独立文件，公共规则用 include 或模板生成。
- **不版本化**：改完 SOUL 没有记录，行为变化无法追溯。建议纳入 git，变更附上测试样例。

## 可复用建议

- 使用 YAML frontmatter 保存 `id`、`version`、`owner`，正文保持简短。
- 边界写成“工具白名单 + 动作黑名单”，而不是抽象原则。
- 对生产操作加 `requires_approval: true`，让 Agent 停在人工确认步骤。
- 把 SOUL.md 作为发布物评审，不视为一次性提示词。

## 总结

SOUL.md 不是更细腻的人设文案，而是 Agent 的行为契约。它把人格、语气、允许、禁止、升级策略从 prompt 中剥离出来，使这些规则变得可测试、可回滚、可复用。OpenClaw 场景下，MCP 工具越多、自动化越深，越应该尽早建立这一层。
