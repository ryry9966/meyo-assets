## 背景

维护技术社区久了，每周固定产出几篇原创帖，会占用大量时间。选题、写初稿、排版、发布、检查格式，这些动作高度重复。我们的目标不是用一个“通用大模型”自动写爆款，而是把发帖流程中稳定重复的部分自动化，把最终审核权和选题方向留在人手里。

基于 OpenClaw 的 Agent 能力，配合 MCP 工具封装社区接口，我们搭了一套半自动发帖管线。它本质上是一个“生成-审核-发布”的状态机，而不是一个长链条的生成式 agent。

## 问题

最初尝试让一个 Agent 从选题到发布一条龙执行，结果失败率很高。问题集中在几类：

- 内容风格漂移：长任务中上下文变长，模型越写越偏。
- 平台接口脆弱：登录态失效、限频、接口字段变更。
- 草稿丢失：Agent 上下文超限，已生成内容没落盘。
- 重复发布：定时任务重试造成重复提交。
- 代码块渲染异常：Markdown 中的代码块在平台端被转义或截断。

这些问题不能靠调提示词解决，需要把流程拆开，隔离易错环节。

## 做法/步骤

### 1. 架构分层

调度层（cron）触发任务，任务进入队列。OpenClaw Agent 负责内容生成，但只产出草稿，不直接发布。发布由独立的发布执行器完成。

数据流向：

```
cron -> 任务队列 -> 生成 Agent -> 草稿库(SQLite) -> 审核 -> 发布执行器 -> 平台 API
```

草稿库是唯一事实源，Agent 不保留生成内容，只读写草稿状态。

### 2. MCP 工具封装

把社区接口封装成一个 MCP Server，提供 `create_post`、`update_post`、`check_status`、`upload_image` 等工具。认证、签名、限频处理都收在工具内部，Agent 只看到简单的参数。

这样做的好处是，平台接口变动时只改 MCP Server，不动 Agent 逻辑。

### 3. 生成与发布解耦

生成 Agent 分三阶段：选题 -> 大纲 -> 正文。每个阶段结束后写入 SQLite，再进入下一阶段。任务失败可以从断点重试，不浪费已经生成的内容。

发布执行器从草稿库捞取 `approved` 状态的文章，带退避重试、超时控制、发布后回写状态。发布前做内容指纹查重。

### 4. 审核与防护

发布前增加规则审：敏感词过滤、外链检查、标题长度、代码块完整性。规则通过后进入 `approved` 状态，等待发布。首发内容保留人工审核节点。

## 踩坑点

**登录态比预期脆弱**  
平台 cookie 大约 3-6 小时失效，有的接口还需要额外的 token 签名。刚开始直接把 cookie 写死在配置里，发布经常失败。后来在 MCP 工具内加入认证校验接口，失效即告警并暂停任务，避免连续失败被封禁。

**限频不是均匀的**  
发帖接口表面允许 5 分钟 3 次，但连续失败会触发临时封禁。用固定间隔重试会雪上加霜。换成指数退避加随机抖动后，失败率明显下降。

**LLM 输出 JSON 仍然会漂移**  
即使约束了 JSON Schema，部分模型在长文本中还是会出现字段缺失或类型错误。解析失败时，我们选择退回上一阶段，保留已生成的部分，只重试缺失字段，而不是整个重来。

**草稿丢失**  
Agent 在长任务中容易上下文超限，导致生成内容丢失。解决办法是每阶段强制落盘，Agent 不把草稿留在内存里。

**重复发布**  
定时任务重试和发布执行器重试叠加，容易重复发帖。通过状态机保证幂等：只有 `approved` 状态才能进入发布，发布中状态禁止并发。发布前用标题+正文的 hash 做查重。

**代码块被平台渲染坏**  
Markdown 代码块中的特殊字符或超长内容会被平台转义或截断。发布前做字符转义和长度检查，必要时用图片替代长代码片段。

## 可复用建议

- **生成与发布解耦**：不要让 Agent 直接操作发布接口，草稿库作为中间层。
- **状态机优先**：`draft -> review -> approved -> publishing -> published -> failed`，每个状态可重入。
- **人工审核节点保留**：至少首发内容要人工抽检，规则审不能替代一切。
- **MCP 工具尽量薄**：只做接口适配，不掺入业务规则，后续也可以插件化接入现有体系。
- **发布前 dry-run**：记录将要发布的内容，回滚时只改状态不删除，留下可追溯记录。
- **灰度运行**：先在冷门板块跑 1 周，观察失败率和内容质量，再逐步扩大。

## 总结

这套系统没有“一键生成爆款”的能力，它解决的是重复劳动和易错点隔离。稳定运行 3 周后，人工每周只需花 20 分钟左右审稿和调整选题，发布失败率控制在可接受范围。后续如果要扩展到多平台，每增加一个平台都要重新评估认证和限频，不能简单复用同一套参数。

对 OpenClaw 的用户来说，最有价值的不是让 Agent 完成所有事，而是用 MCP 和草稿库把链路拆开，让每一步都可观测、可重试、可回滚。
