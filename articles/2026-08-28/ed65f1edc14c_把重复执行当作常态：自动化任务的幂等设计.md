## 背景：自动化环境里，重试不是异常，而是常态

在 OpenClaw、Agent、MCP 工具和插件编排场景里，任务很少会“只执行一次”。定时任务可能重叠，Webhook 可能重复投递，Agent 调用 MCP 工具超时后会重试，插件可能因上游 at-least-once 语义被触发多次。

如果把“每个任务默认只跑一次”当成前提，系统很快就会暴露出重复创建资源、重复发送消息、重复写库等问题。正确做法不是尽量阻止重复执行，而是让重复执行不产生额外副作用，也就是幂等。

## 问题：重复执行会在哪里出问题

一个常见的例子：MCP 工具负责创建工单。第一次调用已经成功，但客户端没有拿到响应，于是重试。如果没有幂等设计，第二次调用会生成一张重复工单。

另一个典型场景：定时同步任务预计 5 分钟跑完，结果某次跑了 8 分钟，下一次 cron 又启动了一个实例。两个实例同时处理同一批数据，如果没有锁和去重，就会出现重复处理。

这些问题不是重试机制本身造成的，而是副作用的入口没有幂等保护。

## 做法：给每个副作用设计幂等入口

### 1. 为外部动作引入幂等键

给每个会改变状态的动作设置 `idempotency_key`，可以由调用方生成，也可以使用业务自然唯一标识，例如订单号、工单号、消息 ID、任务 ID。

以 MCP 工具为例，工具入参可以统一增加一个可选字段：

```json
{
  "action": "create_ticket",
  "idempotency_key": "ticket-20250618-0001"
}
```

服务端保存“键 -> 结果”。重复请求携带相同键时，直接返回第一次的结果，不再执行业务逻辑。

### 2. 用数据库唯一约束兜底

只靠“先查一下是否存在再插入”并不安全。并发下两个请求同时查询都查不到，随后都会插入。必须让数据库唯一约束成为最后一道防线。

例如：

```sql
ALTER TABLE tickets ADD CONSTRAINT uniq_ticket_task_id UNIQUE (task_id);
```

插入时捕获唯一冲突，然后返回已存在记录。这样即使上层去重失效，也不会产生重复数据。

### 3. 把“读-判断-写”改成条件更新

很多重复执行来自经典的 read-then-write 流程：先查状态，判断可以处理，再更新状态。这个窗口会被并发请求穿透。

改成原子条件更新：

```sql
UPDATE tasks
SET status = 'running', lease_until = now() + interval '5 minute'
WHERE id = ? AND status = 'pending';
```

如果影响行数为 0，说明该任务已经被其他实例处理，直接跳过。

### 4. 用状态机控制合法流转

把任务状态定义成明确的状态机，例如：

`pending -> running -> done`

或：

`pending -> running -> failed -> retryable`

重复调用时，如果任务已经处于 `done`，直接返回成功结果；如果处于 `running`，则检查租约是否超时。这样可以避免长任务被错误重复启动，也能防止已失败任务被无限重复执行。

### 5. 对 MCP 工具和插件做统一封装

不要把幂等逻辑分散在每个工具实现里，否则很容易遗漏。可以在工具调用层加一层包装：

- 调用前根据 `action + idempotency_key` 查缓存/数据库；
- 命中则直接返回缓存结果；
- 未命中则执行业务逻辑，并写入结果；
- 执行失败时根据错误类型决定是否缓存失败结果。

这样插件开发者只需要关心业务动作本身。

## 踩坑点

### 1. 幂等键范围设置不当

太粗：比如整个任务只用一个 `task_id`，但任务内部有多个阶段。第一次成功后，第二阶段重复请求可能被误判为“已执行过”，导致必要步骤被跳过。

太细：每次请求都新生成一个 UUID。这样每一次都看起来是新的，幂等键等于没有。

建议按“一个外部副作用一个幂等键”的粒度设计，而不是按整个任务，也不是按每次请求。

### 2. 副作用没有被完全纳入幂等入口

业务写入已经幂等了，但通知、日志、审计事件可能仍然在重复发送。比如重复请求命中缓存不执行主业务，但代码仍然在缓存返回前发了一次通知。

解决方法是把通知、审计这类副作用也放进结果记录或事务范围内，确保只有第一次真正执行时才会触发。

### 3. 失败重复比成功重复更难处理

成功重复通常容易通过缓存结果解决。但失败后的重试可能更危险，尤其是涉及外部支付、跨系统写入时。

例如一次扣款请求超时，本地不确定远端是否成功。此时不能盲目重试扣款，而应该先查询远端状态，或者使用对账机制。幂等不是简单重放，而是要先确认状态。

### 4. 只有锁，没有租约和续租

定时任务加了分布式锁，但如果锁没有过期时间，进程崩溃后锁永远不释放；如果过期时间太短，长任务还在跑，锁提前释放，新实例又进来重复处理。

建议使用带租约的锁，并在任务执行过程中定期续租。

## 可复用建议

- 每个 MCP 工具、插件动作都提供一个 `idempotency_key` 参数，或在上下文中注入 `trace_id` / `parent_id`。
- 设计一张幂等表：

```sql
CREATE TABLE idempotency_records (
  key TEXT PRIMARY KEY,
  namespace TEXT NOT NULL,
  result JSONB,
  status TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expire_at TIMESTAMPTZ
);
```

- 对外部 API 调用统一封装重试逻辑：重试时复用同一个幂等键；超时后先查远端状态，而不是直接重放。
- 定时任务启动前必须假设上一次实例可能还在运行。使用分布式锁，并按业务唯一键对数据进行去重。
- 将幂等设计评审纳入插件和 MCP 工具的上线 checklist，而不是等线上重复数据出现后再补救。

## 总结

自动化任务可靠性不来自“尽量不重复执行”，而来自“重复执行也不会改变结果”。把重试、并发和任务重叠当作常态，在设计插件、MCP 工具和定时任务时，给每个副作用一个幂等入口，用数据库唯一约束兜底，用状态机控制流转。这样无论是补跑、回填失败数据，还是上游重试，都不会把系统推向混乱。
