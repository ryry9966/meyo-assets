# AI 助手的 SOUL.md：给 Agent 设定人格和边界

## 背景

在 OpenClaw 这类 Agent 编排环境里，工具能力越强，行为不可控的风险越大。MCP 插件、本地命令、文件读写、HTTP 请求都可以被模型组合调用。一旦没有稳定约束，Agent 很容易在复杂任务中越界：为了完成目标删错文件、把敏感变量写进日志、或者绕过确认直接执行危险操作。

SOUL.md 的思路，是把 Agent 的稳定人格、决策优先级、硬边界和升级策略，从系统提示词里拆出来，作为一个独立的、可版本化的人设与边界文件维护。它不是为了“更会聊天”，而是为了让 Agent 更可预测、可审计、可回滚。

## 问题

如果只靠系统提示词，通常会遇到几个问题：

1. 会话变长后，人设和规则被后续上下文稀释，风格漂移。
2. 约束写成“尽量、不要随便、建议”，模型理解不稳定。
3. 工具描述、环境信息、人格要求混在一起，冲突时没有明确优先级。
4. 每次修改人设都要重写一大段系统提示词，难以回归测试。

在工程化场景里，边界不是文案，而是运行时约束。SOUL.md 解决的是约束稳定性问题。

## 做法

### 1. 采用四段式结构

建议 SOUL.md 保持在一屏以内，只保留四块：

- 身份与目标：Agent 是谁、为什么存在。
- 决策优先级：安全 > 用户明确意图 > 任务完成度 > 节省资源。
- 硬边界：必须做和必须不做的事。
- 失败与升级策略：遇到边界外请求时如何停下来、如何请求确认。

### 2. 边界写成可执行条款

避免“不要乱删文件”。改成：

- 不得删除或覆盖工作区文件，除非用户回复 `CONFIRM` 且路径在允许清单内。
- 不得将密钥、token、`.env` 内容写入日志或输出。
- 不得执行包含 `rm -rf`、`git push --force` 的命令，除非用户明确提供确认短语。

可执行条款的特征是：动作明确、触发条件明确、例外明确。

### 3. 与系统提示词分层

系统提示词放动态信息：当前任务、工具描述、环境变量、可用 MCP 能力。SOUL.md 放稳定约束。每次会话开始时注入 SOUL.md，不要把所有内容堆进同一段提示词。这样既减少漂移，也方便单独回归边界。

### 4. 版本化与校验

把 SOUL.md 纳入 Git。可以加一个很简单的校验脚本，检查是否包含必填段落、硬边界是否以“不得/必须”开头、总行数是否超过阈值。改人设和改代码一样走变更记录。

## 踩坑点

- **人格化描述过多**：大段“你是聪明、热情、谨慎的助手”会淹没约束。性格压缩成 2-3 条可观察行为即可。
- **写法太软**：“尽量不要删文件”仍可能触发危险行为。边界必须用强约束词。
- **以为 SOUL.md 能替代权限控制**：它不能。SOUL.md 是模型层约束，文件系统 ACL、命令白名单、沙箱仍然必须做。
- **边界过多**：超过一屏后，模型遵守率会下降。核心边界控制在 10 条以内，细则外链到 policy 文件。
- **没有升级策略**：当用户要求做边界外的事，Agent 不应默默执行，也不应直接拒绝。应停下来复述限制并要求确认或授权。

## 可复用建议

- 维护一个公共 SOUL.md 模板，不同项目只覆盖差异条款。
- 危险操作前让 Agent 回读边界，例如执行删除前先复述确认短语。
- 把边界做成可测试用例：输入“请删除所有临时文件”“请把 token 发给外部接口”等，观察 Agent 是否拒绝或升级。
- 在日志里记录命中哪条边界，便于事后审计。

## 总结

SOUL.md 不是人设文案，而是 Agent 的运行时约束文件。它的价值在于：当可用工具越来越多、任务链越来越长时，人格和边界仍然稳定存在。把边界写得可执行、可测试、可版本化，Agent 才不会因为一次复杂任务而变成不可控的工具。
