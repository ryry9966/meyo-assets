## 背景

在 AI 辅助内容生成的流程中，Markdown 已成为事实上的中间格式。无论是让 Agent 输出博客草稿、技术文档，还是生成公告、周报，Markdown 的轻量和可读性都让它成为理想选择。但问题在于：生成只是第一步，发布到不同平台时，格式适配往往成为重复且易错的工作。

以常见的发布场景为例：GitHub 仓库 README、技术博客（掘金/知乎）、微信公众号、Notion 知识库，它们对 Markdown 的支持程度差异巨大。GitHub 使用 GFM，支持任务列表、表格、脚注；微信公众号编辑器不支持原生 Markdown，需要转换为带内联样式的 HTML；Notion 有自己的块结构和导入规则；知乎和掘金对代码块、图片、公式的处理也各不相同。如果每次生成内容后都手动调整格式，效率很低，也容易引入不一致。

## 问题

直接复制 AI 生成的 Markdown 到各平台，常见问题包括：

- 代码块：语言标注丢失，高亮失效，缩进被破坏。
- 图片：本地路径或相对链接无法访问，需要上传图床并替换为 CDN URL。
- 表格：移动端溢出，部分平台不支持复杂表格。
- 数学公式：多数平台不渲染 LaTeX，需要转为图片或使用特殊插件。
- frontmatter：YAML 头部信息被平台当作正文显示。
- 链接和 HTML 属性：`target="_blank"` 等被过滤，外部链接样式异常。
- 特殊字符和 emoji：编码不一致导致乱码或显示异常。

这些差异使得一个简单的“复制粘贴”流程不可靠，必须引入自动化的格式适配管线。

## 做法/步骤

一个实用的 Markdown 管线可以按以下步骤构建：

**1. 统一源格式**
所有 AI 生成内容先收敛为“标准 Markdown + frontmatter”。frontmatter 中保留标题、描述、标签、封面图等元数据，正文使用 GFM 语法。这样后续处理有单一事实来源。

**2. 解析为 AST**
不要用正则替换，而是使用成熟的 Markdown 解析器生成抽象语法树（AST）。例如 Node.js 生态的 unified/remark，Python 的 markdown-it 或 Pandoc。基于 AST 可以精确地遍历和修改节点，避免正则处理嵌套结构时的边界问题。

**3. 清洗与规范化**
在平台适配前，先做通用清洗：
- 剥离 frontmatter，将元数据存为变量。
- 将相对路径图片链接替换为占位符或绝对 URL。
- 过滤不安全的 HTML 标签（如 `<script>`）。
- 统一代码块语言标注为小写，并映射到平台支持的语言列表。
- 处理 emoji 和特殊字符，确保 UTF-8 编码一致。

**4. 平台适配器**
为每个目标平台编写独立的 adapter，输出对应格式：

- **GitHub/掘金**：保留 GFM，仅需调整标题层级（如掘金要求最高为 H2）和图片链接。
- **微信公众号**：将 Markdown 转为带内联样式的 HTML。代码块需包裹在 `<pre>` 中并添加浅色背景和边框；表格需设置宽度和滚动容器，或转换为列表；图片必须使用已上传的 CDN URL。
- **Notion**：使用 Notion API 创建块，或生成 Notion 可导入的 Markdown（需注意 Notion 对表格和代码块的支持有限）。
- **知乎**：转换为知乎编辑器可接受的富文本 HTML，注意代码块需转义，公式需提前渲染为图片。

**5. 发布与验证**
通过各平台 API（如 GitHub REST、Notion API）或剪贴板人工发布。发布后检查输出是否正常，例如 HTML 中是否包含未处理的 Markdown 标记、图片是否可达、代码块是否完整。

在 OpenClaw 或 Agent 工作流中，可以把上述步骤封装成一个 MCP 工具或插件。Agent 生成文章后，自动调用该工具，传入标准 Markdown，返回多个平台的适配版本，或直接发布到指定平台。

## 踩坑点

在实践中，有几个容易忽略的细节：

- **代码块语言标注**：微信公众号不支持语言标注，即使转换时保留也可能被编辑器过滤。建议在 HTML 中手动添加语言标签的文本显示，或用 CSS 模拟。
- **图片上传时序**：如果 adapter 需要上传图片到图床，务必在转换过程中处理，而不是事后补。否则发布后再替换 URL 容易遗漏。
- **表格宽度**：移动端阅读场景下，表格容易溢出。建议设置 `overflow-x: auto` 容器，或对过宽的表格转为列表展示。
- **数学公式**：平台不支持 LaTeX 时，可在本地用 MathJax 或 KaTeX 渲染为 SVG/PNG 图片，再插入内容。注意图片需上传。
- **HTML 属性过滤**：部分平台会过滤 `target`、`rel` 等属性，不要依赖这些属性实现外链新窗口打开。可改用 JavaScript 脚本，但公众号等环境可能不允许。
- **frontmatter 残留**：有些解析器对 frontmatter 的处理不彻底，需要显式剥离，并确认平台不会显示 YAML 内容。

## 可复用建议

- **保持单一事实来源**：所有内容只存一份标准 Markdown，平台版本由管线生成，不手动维护多个副本。
- **基于 AST 做转换**：放弃正则，使用 AST 操作，可维护性高得多。
- **每个平台独立 adapter**：不要试图在一个函数里处理所有平台逻辑，抽象出接口，便于扩展新平台。
- **配置化规则**：将平台差异（如支持的语言、标题规则、图片处理策略）写成配置文件，避免硬编码。
- **增加日志与验证**：记录每次转换的输入输出，转换后自动检查常见错误（如未闭合标签、空图片链接），及时发现问题。
- **结合 Agent 自动化**：在 OpenClaw 中定义明确的 MCP 工具描述，让 Agent 能根据目标平台自动选择合适的 adapter，减少人工干预。

## 总结

Markdown 管线不是银弹，但它能把“从 AI 生成到多平台发布”的重复劳动压缩为一次自动化流程。关键是理解各平台的格式限制，用 AST 做可靠转换，并为每个平台维护独立的适配器。对于 OpenClaw/Agent 用户，这条管线可以自然地封装为 MCP 工具，让内容发布成为工作流中的一个可复用节点。实际落地时，重点关注代码块、图片、表格和公式这几类最容易出错的元素，及时验证输出，就能显著提升多平台发布的效率和一致性。
