## 背景：插件式 Agent 集成正在失控

过去一年，做 Agent 工具集成时最累的不是模型能力，而是“接工具”。每接入一个外部能力，比如文件读写、GitHub、数据库、浏览器，都要写一层胶水代码：适配鉴权、定义参数、处理错误、写工具描述。换一个 Agent 宿主，这些事基本要重来一遍。

MCP（Model Context Protocol）想解决的正是这个问题。它不是新的模型能力，也不是某个平台独有功能，而是一套标准化的上下文与工具调用协议。可以把 MCP 理解为 Agent 世界的 USB-C：设备还是那些设备，只是接口统一了。

## 问题：没有 MCP 之前，集成有多痛

假设你要让 OpenClaw 同时访问文件系统、PostgreSQL 和 GitHub。

传统做法是写三个插件，每个插件各自实现一套调用逻辑。不同插件对错误处理、权限控制、返回结构的理解都不一样。模型看到的是三套风格差异很大的工具描述，调用成功率不稳定。维护时还要分别排查三个插件的状态。

更麻烦的是复用。一个已经写好的文件系统插件，换到另一个 Agent 宿主通常不能直接跑，因为宿主的插件 API 不同。MCP 把“工具提供方”和“工具使用方”解耦：工具提供方只实现一次 MCP server，宿主管道只实现一次 MCP client，之后可以互相复用。

## 做法：用最小 MCP 配置跑通流程

MCP 架构里有三个角色：

- **Host**：宿主程序，例如 OpenClaw、桌面 Agent、自研编排器。
- **Client**：宿主内的 MCP 客户端，负责与 server 通信。
- **Server**：实际暴露工具、资源或提示词的进程。

工程中使用最多的是 tools。一个典型的 MCP server 配置如下，许多宿主都兼容类似格式：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/data/allowed"]
    }
  }
}
```

接入 OpenClaw 时，通常只需要在配置里增加这样一个条目。启动宿主后，先确认工具是否被正确列出，再测试一个简单调用，例如让模型读取 `/data/allowed` 下的一个文件。

如果是自研 MCP server，建议先用 MCP Inspector 单独测试。先在外部把 server 跑通，确认能列出工具、能返回结果，再接入宿主。不要一上来就在宿主里调试，链路太长，排错成本高。

## 踩坑点：实际工程里最容易翻车的地方

**第一，stdio 输出污染。** 很多 MCP server 默认走 stdin/stdout 通信。如果 server 启动时打印了普通日志到 stdout，会破坏 JSON-RPC 消息流，表现为宿主管道连接后立刻断开或工具列表为空。日志必须打到 stderr，或直接关闭。

**第二，工具返回过大。** 让模型读取一个 10MB 日志文件，返回结果直接把上下文窗口打爆。MCP 本身不负责截断，限长需要在 server 层或宿主层做。建议每个工具都设置返回上限，例如最多返回 500 行或 20KB。

**第三，权限给得太宽。** 不少文件系统 server 示例把根目录 `/` 或 `C:\` 暴露出去。模型一旦误操作，代价非常高。始终把允许访问的目录限制在最小范围，并且优先给只读权限，除非场景明确要求写入。

**第四，npx 首次启动问题。** 使用 `npx` 拉取 server 包时，第一次启动可能因为网络问题失败，或者因为版本漂移导致行为变化。生产环境建议锁定版本，或者安装到本地后直接执行入口文件。

**第五，工具描述太模糊。** MCP 工具能否被模型正确触发，主要看 tool description 质量。像“执行命令”这种描述基本没用。需要写清楚：什么时候用、输入什么、返回什么、有什么限制。

## 可复用建议

- **最小暴露原则**：一个 MCP server 只暴露当前任务必需的工具，宁少勿多。工具太多会消耗上下文，还容易让模型选择错误。
- **结果有限化**：每个工具在 server 层做截断，不要把原始大对象全量返回。
- **环境变量外置**：密钥、路径、数据库连接串不要硬编码在配置里，通过环境变量注入。
- **独立测试**：任何新 MCP server 都先在 Inspector 或命令行交互中验证，再交给 Agent。
- **进程健康检查**：stdio 型 server 会随宿主退出而退出，但长期运行时也可能卡死。可以给 server 增加超时和 watchdog。
- **写好工具描述模板**：统一使用“用途 + 输入参数 + 返回结果 + 注意事项”四段式描述，能明显提升工具的触发准确率。

## 总结

MCP 解决的本质问题不是“让模型更强”，而是让工具接入从 N×M 的胶水代码，收敛为 M+N 的协议实现。对 OpenClaw 这类 Agent 实践来说，MCP 的价值在于：工具可以沉淀、可以复用、可以独立测试。

但它也不是银弹。真正决定 Agent 稳定性的，仍然是你给模型暴露了哪些工具、权限边界划在哪里、返回结果是否受控。协议统一之后，治理能力才是下一步的关键。

如果你已经在 OpenClaw 里接 MCP，建议从文件系统或数据库这类低风险工具开始，跑通一条“配置 → 测试 → 调用 → 截断”的完整链路，再逐步扩展工具面。
