## 一、背景

在 OpenClaw 这类 Agent 工作流里，分享自动化实践已经变成日常。一个能跑通的流程往往会包含：提示词模板、MCP 工具配置、插件调用链、示例输出、环境变量片段，甚至一段排障日志。

问题在于，Agent 的输出不是完全可控的静态文本。同一个流程，在不同上下文里运行，可能会把沉淀在系统提示、工具描述、向量库检索结果或历史会话里的内部信息“顺带”写进最终结果。分享者以为自己只是贴了一段工作流，实际可能已经把内网域名、目录结构、客户名称或 API 密钥暴露给了社区。

这比人工写文档泄露更隐蔽。人写文档时会刻意隐去敏感字段，Agent 则可能因为一条工具返回、一段历史对话，就把不该出现的内容自然语言化。

## 二、问题边界

先把泄露渠道想清楚，比上来就加过滤规则更有效。社区场景里，常见泄露集中在四类：

1. **提示词/工具描述**：为了说明流程，直接贴出包含内部系统名的系统提示；MCP server 的 description 里写了内网服务地址或数据表名。
2. **示例输出**：Agent 跑出的样例结果里带出真实路径、用户名、IP、客户简称。
3. **配置文件**：分享 `config.json`、`.env.example` 时，把真实 token 或内部 endpoint 带进去。
4. **排障日志**：截取一段 agent 运行日志，里面包含 headers、cookie、数据库连接串或检索片段。

这些信息的共同特点是：**分享时看起来像“正常工作流的一部分”，但失去上下文后，就能拼出内部系统轮廓。**

## 三、做法与步骤

下面是一套我们目前在用的流程，偏工程化，不依赖单一工具。

### 1. 先做数据分级，不做全量脱敏

把可能进入 Agent 上下文的数据分为三类：

- **公开**：代码结构、通用参数、公开 API 名称。
- **内部**：内网域名、服务名、目录路径、团队术语。
- **机密**：token、密钥、客户数据、个人信息、未公开业务指标。

分享前只允许出现“公开”类信息。内部信息要替换成占位符；机密信息直接禁止进入可分享流程。

### 2. 分享前跑一条脱敏流水线

不建议只靠人眼检查。可以在本地跑一个轻量扫描脚本，对准备发布的 Markdown、JSON、截图文本做三道处理：

- **规则扫描**：匹配 `sk-`、`Bearer`、`api_key`、`password`、`token`、`secret`、`BEGIN PRIVATE KEY`、`mongodb://`、`postgres://` 等模式。
- **实体替换**：用正则替换 IP、邮箱、内网域名（如 `*.internal`、`*.local`、`10.*`、`192.168.*`）、路径 `/home/用户名/`、公司英文名。
- **人工抽检**：重点看示例输出、日志代码块和截图。截图里的信息非常容易漏，建议统一用纯色块遮罩。

### 3. 给 Agent 加发布边界

如果 Agent 会参与“整理分享内容”，在系统提示里明确：

> 输出面向公开社区，不得包含 token、私钥、内网地址、真实路径、客户名称、未公开业务数据。如检测到敏感内容，用 `<REDACTED>` 替换并继续。

这个边界不能只写在第一层。如果 Agent 会调用检索工具或读取本地文件，还要在工具返回后加一道输出过滤。否则系统提示会被上下文淹没。

### 4. MCP/插件权限最小化

MCP 工具描述尽量不携带敏感上下文。比如：

- 不写 “读取公司订单库 `prod_order_db`”，写 “读取指定数据源中的订单记录”。
- 工具只暴露必要 scope，分享示例时用只读视图，不要给写入、删除权限。
- 配置文件拆成 `config.example.yaml` 和本地 `config.local.yaml`，后者不入库、不分享。

### 5. 发布前做一次审计回放

如果条件允许，把要分享的流程重新跑一遍，记录工具调用和最终输出。对比这份记录与准备发布的内容，确认没有多余信息。多人协作时，至少需要一位非原作者做“冷眼审阅”，因为原作者容易对内部术语习以为常。

## 四、踩坑点

1. **示例跑通了就急着贴，结果里面带真实 token。** 尤其 AI 自动生成示例时，可能从环境变量里直接取。
2. **只检查正文，不检查截图。** 截图里的终端、环境变量面板、日志头最容易泄露。
3. **以为是 `.env.example`，其实复制的是真 `.env`。** 这种属于高频事故。
4. **把完整排障日志贴出去求帮助。** 日志中的 headers 或 session cookie 可能仍然有效。
5. **向量库检索把内部知识片段带进输出。** 分享前没有清空或隔离知识库索引。
6. **Agent 自动合并多轮上下文，把私聊内容写进公开回复。** 必须用输出边界切断。

## 五、可复用建议

- 所有密钥、token 放进 secrets manager，工作流里只引用变量名，不落盘。
- 准备分享模板：提示词模板、MCP 配置模板、输出模板，默认使用 `example.com`、`REDACTED`、`your_api_key` 等占位符。
- 把脱敏脚本放进预提交或发布前检查，不用人工逐行看。
- 对公开分享的流程做一次“红队测试”：故意在上下文里埋入假敏感数据，看 Agent 是否会吐出来。
- 社区发布前使用检查清单：是否含真实凭据、内网地址、真实路径、客户名、日志、截图、检索片段。
- 截图遮罩不要用马赛克，马赛克在部分场景下可被恢复；使用实心色块覆盖。

## 六、总结

安全红线不是不让分享，而是让分享不携带上下文。对 Agent 工作流用户来说，最危险的不是有人故意泄露，而是 AI 在生成、整理、总结过程中把内部信息“自然”地夹带出来。

建立“数据分级 + 发布前脱敏 + Agent 输出边界 + 最小权限配置 + 人工审阅”的组合，比任何单点规则都有效。工程上不追求绝对安全，但要把明显可避免的泄露路径全部堵上。社区协作的价值在于方法交换，而不是把生产环境顺便交换出去。
