前几天圈子里有个挺有意思的小新闻：OpenAI 的 Codex CLI 开始兼容国产开源模型，有人第一时间把 DeepSeek 接了上去，跑通了。听起来像是"开源生态又下一城"，但实测下来的口径却出奇一致——能用，但门槛还是太高，体验离"开箱即用"差着两三个版本号。

这事儿值得拆开聊聊。它不是简单的"A 兼容 B"的工程小新闻，背后牵扯到模型能力对齐、工具调用协议、工程封装这三层很现实的问题。今天这篇就从原理到上手，一层层捋一捋。

## Codex CLI 是什么，为什么它"兼容国产模型"是件事

先把背景对齐一下，免得后面聊得云里雾里。

- **Codex CLI** 是 OpenAI 在 2024 年底到 2025 年陆续推出的命令行编程助手，定位类似 Claude Code、Aider 这类"在终端里干活"的 AI 编码工具。它能读你的代码库、执行 shell 命令、写文件、跑测试，是 agent 形态而不是单纯的聊天框。
- 之前它是**强绑定 OpenAI 模型**的，只能用 gpt-4o、o 系列那一票闭源模型。换句话说，你想用它，得给 OpenAI 充值。
- 这次的变化在于：它开始支持自定义 `base_url` 和 `model`，理论上任何兼容 OpenAI API 协议的模型都能塞进去。DeepSeek、Qwen、GLM、Kimi，包括本地跑 Ollama 起的 llama.cpp，都进入了"可接入"的射程。

为什么这件事让圈子热闹了一下？两个原因：

1. **成本**：OpenAI 的 o 系列推理模型按 token 烧钱速度感人，一个稍微复杂的 agent 任务跑几轮，几块钱就没了。DeepSeek 的 API 价格大概只有前者的几十分之一，开源版本还能本地部署，成本接近"电费"。
2. **数据落地**：很多团队不愿意把代码库喂给境外 API，能换成国产/本地模型，合规层面省心不少。

所以"兼容 = 解锁了一种新的玩法"，这个判断是成立的。但"能玩"和"好玩"之间，还隔着一条工程鸿沟。

## 实测里到底卡在哪：三个层面的不对齐

大家测下来反馈最集中的几个问题，可以归到三层：

**第一层：协议兼容不是 100%**

- OpenAI 的 Chat Completions API 表面上是行业事实标准，但**函数调用（function calling / tool use）**这部分各家实现差异不小。
- Codex CLI 大量依赖 tool calling 来执行"读文件、写文件、跑命令"这套循环。一旦模型返回的 `tool_calls` 字段格式有偏差（比如参数 JSON 偶尔不闭合、缺字段、用了 markdown 包裹），整个 agent 循环就断了。
- DeepSeek-V3、V3.1 在 function calling 上做了对齐，但稳定性比起 GPT-4o 这种"被千万开发者打磨过"的模型还是差一截。复杂任务跑十轮，可能有一两轮在格式上翻车。

**第二层：长上下文 + 推理深度的差距**

- Codex 这类 agent 工作流，一次任务的上下文经常爆到 50k–100k token：项目结构、关键文件、历史操作日志、错误回显……全要塞进去。
- 闭源旗舰模型在 128k 甚至 1M 上下文下还能保持"注意力不涣散"，而很多开源模型号称支持长上下文，实测在 30k 之后召回精度明显下滑——也就是俗称的"中间遗忘"（lost in the middle）。
- 推理深度上，o1/o3 这类带显式 reasoning 的模型在多步规划上有明显优势。DeepSeek-R1 是国产里最接近这一档的，但 Codex CLI 对 R1 的 `reasoning_content` 字段处理目前还不算优雅，需要手动 patch。

**第三层：工程封装的细节**

- 真正用过的人会发现，Codex CLI 里有不少"隐藏的 prompt 工程"——system prompt 是为 OpenAI 模型写的，里面甚至有针对特定模型行为习惯的 workaround。
- 把这套 prompt 直接喂给 DeepSeek，模型可能会"理解到了，但执行偏了"。比如它会把本该直接调用 tool 的步骤，先用自然语言解释一遍，浪费 token 不说，还容易触发循环卡死。
- 解决方案是改 prompt、加 few-shot 例子、调温度、限制 max_tokens——每一步都要工程师手动 tune。这就是"门槛高"三个字最直白的来源。

## 为什么这种"接得上但不顺手"是常态

这一段稍微展开聊一下原理，理解了底层就不会对"半兼容"感到意外。

- **API 协议是契约，模型行为是习惯**。两个模型即使都遵守同一个 API 格式，输出的"风格、节奏、停下来的时机"也完全不同。这就像两个程序员都用 Git，但一个习惯 squash merge，一个偏爱 rebase，协作起来还是会别扭。
- **Agent 工具的 prompt 是过拟合的**。Codex、Cursor、Cline 这些工具，它们的 system prompt 都是针对特定模型反复迭代出来的——这是一种隐性的"模型耦合"。换模型 = 换运行时，你不能指望脚本不改。
- **Benchmark 分数 ≠ Agent 表现**。DeepSeek-V3 在很多榜单上接近甚至超过 GPT-4o，但榜单测的是单轮问答、固定格式的代码题。Agent 工作流考验的是"自我纠错、长程规划、工具使用稳定性"，这部分目前没有统一 benchmark，体感差距比榜单显示的要大。

一个类比：开源模型现在像是一台马力很猛的发动机，但 Codex 这类工具的底盘、变速箱、ECU 都是为另一台发动机调校的。直接换上去能转，但起步顿挫、油耗飙升、偶尔熄火，都属于正常现象。

## 如果你现在就想接，务实的接法是什么

给到真的想动手的人一个相对实用的路径，按从易到难排：

1. **先用 DeepSeek 官方 API + 中间层代理**。比如开源的 one-api、new-api 这类项目，能把各家模型统一成 OpenAI 协议，顺带处理一些字段差异。Codex CLI 把 `base_url` 指过去，省一半坑。
2. **任务分级**。简单的"补全注释、解释这段代码、生成单测"用国产模型完全够；涉及多文件改造、跨模块重构这种重活儿，先别省那点 token，用闭源旗舰跑。
3. **改 prompt 而不是改模型**。如果你愿意花一两天读 Codex CLI 源码，把 system prompt 里那几段针对 OpenAI 模型的 workaround 改掉，DeepSeek 的发挥能上一个台阶。这事社区已经有人在做，关注几个相关的 fork 就行。
4. **本地模型留给"小而频繁"的场景**。32B 以下的模型（Qwen2.5-Coder-32B 之类）本地跑 Codex，做代码补全、commit message 生成这类高频小任务非常香，延迟低、零成本。
5. **关注 R1 系推理模型的适配进度**。Agent 任务真正吃推理能力，等 Codex CLI 对 reasoning model 的支持成熟之后，国产模型在这个赛道才真有戏。

## 三条冷思考

聊到这儿，留三句话给愿意往下想一层的朋友：

- **"兼容"是个连续值，不是布尔值**。看到"X 支持 Y"的新闻，先别急着上头，问一句"支持到什么程度、哪些场景能跑稳"，比盲目尝鲜省时间。
- **开源模型的真实瓶颈正在从"模型本身"转移到"工具链"**。模型能力差距在缩小，但围绕模型的 IDE 插件、Agent 框架、评测体系，闭源生态仍然领先 6–12 个月。这才是接下来值得投入的地方。
- **工具不会等你升级习惯，但你可以挑会等你的工具**。如果你只是想把 AI 用顺，挑一个稳定的组合用熟比频繁换栈更划算；如果你是想做工具，那这段"半兼容"的混乱期反而是机会窗口——填坑的人，从来都最先收到红利。

能跑通是 0 到 1，跑得顺是 1 到 10。这次 Codex 兼容国产模型的实测，本质上是把第二段路程的难度，明明白白地摆到了大家面前。
