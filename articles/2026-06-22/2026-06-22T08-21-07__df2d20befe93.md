前几天 OpenAI 给 Codex 加了一个被网友戏称为「复读机」的新能力——你演示一遍操作，它学会之后照着干。听起来像是把「师傅带徒弟」搬进了 IDE。这事在开发者圈子里讨论得挺热闹，有人觉得是生产力质变，也有人觉得是噱头。今天咱们就把这层窗户纸捅破，聊聊「教 AI 干活」这件事，到底新在哪、原理是什么、能用来做什么、又有哪些坑。

## 「复读机」到底是个啥功能

抛开营销话术，这个功能的本质是 **Demonstration-based Task Learning**（基于示范的任务学习），可以理解为给 AI 录一段「操作宏」，但比传统宏聪明得多。

- **传统宏 / RPA**：你点哪它点哪，坐标、控件名写死，页面一改就崩。
- **Codex 复读机**：你演示一次完整流程，它把你做的事情抽象成**意图**和**步骤**，下次能在变化的环境里复现。

举个具体的例子：

1. 你打开终端，执行 `git pull`，发现冲突，手动解决，跑 `npm test`，全绿后 `git push`。
2. 你把这一连串操作「示范」给 Codex。
3. 下次再有 PR 进来，它能自己走一遍：拉代码 → 检测冲突 → 尝试合并 → 跑测试 → 失败了就打回，绿了就推送。

关键差别在于：它学到的不是「在第 372 像素点点击」，而是「冲突解决后必须跑测试再 push」这种**流程语义**。这背后的支撑是大模型对代码、命令行、文件系统的语义理解能力，再叠加一层 trace 回放机制。

## 它的技术底子从哪来

这事看似新鲜，其实学术界铺垫了很多年，背后至少有三条技术脉络在汇合：

**1. Programming by Demonstration (PBD)**

上世纪 80 年代就有人研究，让用户演示一遍操作，系统归纳成程序。早期最大的问题是「泛化」——演示一次只能学到具体动作，换个文件名就不会了。大模型刚好补上了泛化这块短板。

**2. Tool Use & Agent Loop**

2023 年起，ReAct、Toolformer、Function Calling 这些范式让模型学会调用外部工具。Codex 的复读机本质上是把**用户行为序列**也变成一种工具调用日志，让模型在 Reasoning-Acting 的循环里学会什么时候用哪个工具。

**3. Trajectory / Replay Buffer**

这个概念来自强化学习。模型记录下「状态—动作—结果」三元组，遇到相似状态时召回历史 trajectory 作为参考。Codex 实际上把你的演示存成了一种轻量 trajectory，下次推理时既看当前任务，也参考你之前的「标准答案」。

所以「复读机」三个字虽然调侃，但确实抓住了精髓：它不是死记硬背，而是**带语义理解的回放**。

## 哪些场景真的能落地

抛开 demo 视频里那些精挑细选的例子，结合实际开发流程，下面这些场景最容易吃到红利：

- **重复性 DevOps 任务**：发版前的 checklist——跑 lint、跑测试、生成 changelog、打 tag、推镜像。这种链路长、步骤固定但又偶有异常的活，最适合「演示一次，长期复用」。
- **代码迁移与批量改造**：比如把项目从 Vue 2 升到 Vue 3，把 `class component` 改写成 `function component`。你示范改一个文件，让它在剩下 200 个文件里照搬模式。
- **Bug 复现脚本**：遇到一个偶发 bug，你手动复现了一次，让 AI 把过程固化成可重放的脚本，方便回归测试。
- **数据预处理流水线**：把一份 csv 清洗、去重、归一化、入库的步骤示范一遍，下次换个数据源直接套。
- **新人 onboarding**：老员工把「本地环境怎么搭」演示一次，新人的 AI 助手照着复现，省掉一份 README 永远不更新的痛苦。

不太适合的场景也得说清楚：

- **创造性强、每次都不同**的任务，比如架构设计、UI 创意，演示无意义。
- **强依赖隐性知识**的任务，比如「这个字段为什么必须保留」，光看操作学不到。
- **高风险操作**，比如生产库写入、删数据，演示一遍就敢让 AI 跑？哥们冷静点。

## 「教 AI」和「写 Prompt」的差别

很多人会问：那这玩意和我精心写 prompt 有啥本质区别？区别其实不小。

| 维度 | Prompt | 演示式教学 |
|---|---|---|
| 输入形式 | 自然语言描述 | 实际操作 trace |
| 信息密度 | 低，依赖文字精确度 | 高，含上下文、中间状态 |
| 学习成本 | 反复调 prompt | 操作一次即可 |
| 复现稳定性 | 容易因措辞偏差跑偏 | 有具体 trace 做锚点 |
| 适合人群 | 善于表达的人 | 擅长动手的人 |

打个比方：prompt 像是给徒弟写菜谱，而演示式教学是直接让徒弟看你颠勺。前者需要你把所有 tacit knowledge（隐性知识）翻译成文字，后者把翻译这一步省了——这对很多说不清但能做出来的工程师来说，门槛大幅降低。

但演示也有局限：**你示范的就是它学到的上限**。如果你演示的流程本身就低效、有 bug，它会忠实地把这些缺陷学下来。所以 Codex 团队也强调了「示范质量」的重要性，并提供了让用户标注关键步骤、忽略干扰动作的接口。

## 对开发者意味着什么

往大了说，这是 AI 编程从「补全代码」到「接管工作流」的一次跨越。Copilot 时代 AI 是个聪明的输入法，Codex 复读机时代它开始尝试做你的实习生。

几个值得关注的变化趋势：

- **工作流本身变成可交易资产**：以前你写一个能跑通发版流程的脚本，那是私货；以后这种「示范包」可能像 npm 包一样可以分享、组合、版本管理。
- **隐性知识开始显性化**：团队里那些「只有老王知道怎么处理」的玄学操作，会被慢慢沉淀成可复用的演示样本。这对组织来说价值巨大。
- **测试和审计的重要性上升**：当 AI 开始执行真实操作而不仅仅是写代码，每一个动作的可追溯性、可回滚性变得至关重要。「AI 干了啥」会成为新的日志维度。
- **「教 AI 的能力」成为新软技能**：就像十年前会写 SQL 是基本功，未来会拆解任务、做出干净示范、给 AI 留出合适反馈通道，可能是开发者的新基本功。

## 三条冷思考

聊得再热闹，落到实处还是得理性。最后给三条建议，写完关电脑能用得上的那种：

1. **先小范围试，别上来就 all in**。挑一个低风险、高重复的流程（比如自己电脑上的 setup 脚本）来跑，跑顺了再往关键链路挪。AI 出错的代价跟它替你省的时间是要算总账的。
2. **演示之前先把流程本身梳理干净**。乱糟糟的工作流给 AI 看一遍，得到的是一个乱糟糟还会自动复制的工作流。把这事当成「写文档」的机会，反而能倒逼自己把流程标准化。
3. **始终保留 human-in-the-loop**。尤其是涉及外部系统、生产数据、不可逆操作的地方，AI 可以执行，但确认权留在自己手里。「能自动」不等于「该全自动」，这是这一代 AI 工具最容易踩的坑。

工具再聪明，最终把它用出价值的还是人。「教 AI 干活」听起来是 AI 在学，其实最大的受益方是被迫把自己工作流梳理一遍的你。
