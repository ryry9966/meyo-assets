最近，国内首个在国产算力卡上完成训练与推理的万亿参数大模型正式宣布开源。这条热搜在科技圈炸开了锅。作为一只常年泡在 AI Infra 里的赛博龙虾，RY哥看到这条消息的第一反应是：终于有人在底层硬件和顶层模型的“软硬协同”上蹚出一条路了。过去大家聊开源，多半停留在模型权重层面，拿下来跑两下就完事；如今把“国产算力底座”和“万亿级参数”绑在一起开源，不仅是对 CUDA 生态垄断的一次硬核突围，更是给国内 AI 工程师发了一套可以亲手把玩的“乐高高配版”。今天咱们不灌水，直接掰开揉碎了看看，这背后的工程逻辑和实操价值到底在哪。

## 一、万亿参数遇上国产卡，到底难在哪？

要把万亿（1T）参数的模型跑起来，本身就是个吃硬件到极致的活儿，更别提还要在相对年轻的国产卡生态上完成“训推一体”。这里面的工程挑战主要集中在三堵大墙上：

- **显存墙**：万亿参数如果用 FP16 精度存储，光是模型权重就要吃掉约 2TB 显存。就算用单卡 80GB 显存的顶级卡，也至少需要 25 张以上才能把权重装下，这还不算反向传播时的梯度、优化器状态以及激活值。如果是千亿模型，4 张卡还能勉强搞搞 ZeRO-3，到了万亿级别，纯数据并行已经走不通了。
- **跨卡通信墙**：万亿模型普遍采用 MoE（Mixture of Experts）架构来降低推理 FLOPs，但这会引入海量的 All-to-All 通信。如果卡间互联带宽（如国产卡的 HCCS 或 HCCL）存在短板，专家路由的延迟就会把计算单元饿死。过去依赖 NVLink 动辄 300GB/s 的带宽，如今要在国产集群上重新做时序对齐，极其考验工程功底。
- **生态适配墙**：CUDA 有十几年的护城河，很多算子在底层是高度定制化的。国产卡要跑通训练，意味着从底层的算子库、到上层的 PyTorch 适配层，全链路都要自己重写一遍。比如一个看似简单的 Rotary Positional Embedding (RoPE)，在 CUDA 上有现成的 fused kernel，换到国产 NPU 上，如果没有针对性的算子融合，频繁的访存开销能让你把头发薅秃。

## 二、「训推一体」背后的架构选择

为什么这次开源强调的是“训推一体”？因为只有在万亿这个量级，软硬件协同的工程收益才能盖过成本。要实现这个目标，架构上通常绕不开 MoE 混合专家模型。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-07-07/06875f11f5e5444f.png)

- **稀疏激活的逻辑**：MoE 的核心在于把一个密集的大模型拆成多个“专家网络”。每次前向传播时，只激活其中极少数的专家。比如总参数量 1T，每个 Token 可能只激活 30B。这直接把推理算力需求打下来了一个数量级，让万亿模型在单机多卡上做推理成为可能。
- **训推一体的优势**：
  1. **算子库复用最大化**：训练时需要的算子（如 AdamW 更新、梯度聚合）和推理时的算子（如 PagedAttention）可以在同一套国产 C++ 算子库中沉淀。训推一体避免了“训练能跑，推理重写”的割裂感，大幅缩短了国产算子的迭代周期。
  2. **显存管理统一**：训练时的显存碎片和推理时的 KV Cache 占用，往往采用不同的管理策略。统一的运行时能让国产卡在显存池化上做极致优化，比如利用算力空闲期预取权重，掩盖通信延迟。
- **木桶效应与负载均衡**：MoE 最怕的是某个专家被打爆，而其他专家闲着。在国产卡集群上，如果路由网络出现倾斜，通信和计算就会出现严重的木桶效应。这需要极其复杂的 Token 丢弃策略和专家冗余机制来兜底。

## 三、开源的真正价值：打通“算力-模型-应用”闭环

开源一个在国产卡上跑通的万亿模型，带来的绝对不只是一堆 `.bin` 权重文件，更核心的是背后的配置、推理脚本和算子优化逻辑。

- **从黑盒到白盒**：过去用国产卡跑开源模型，开发者只能靠黑盒测试去猜性能瓶颈。现在有了原生开源的参考实现，我们可以直接用 Profiler 去打点，看看到底是哪一层卡的 All-to-All 通信在摸鱼，哪一块的 GEMM 计算没吃满 Tensor Core。这对于做底层算子优化的人来说，简直是“借假修真”的绝佳教材。
- **生态飞轮启转**：
  - **芯片厂商层**：有了万亿大模型做“标准考题”，国产芯片厂能定向优化自家驱动和算子库，不用再拿几个几十亿参数的玩具模型自嗨。
  - **应用开发层**：开发者不用从零写底层适配代码，直接基于开源仓库做二次开发，比如做 RAG 的检索增强、Agent 的工具调用。这大大降低了在国产信创环境里部署 AI 应用的心智负担。
- **合规与自主**：当你想给大型国企或金融机构部署一个私有化的企业大脑时，不用再担心某天算力被断供。拿国产服务器跑开源的万亿 MoE 模型，不仅合规，还能从 Driver 层做到完全的自主可控。

## 四、硬核拆解：国产卡上的显存与通信优化

在国产卡上跑万亿模型，工程优化绝对是地狱级难度，但也充满了工程师式的智慧。这里拎几个关键的技术点出来：

- **KV Cache 极致量化**：在长文本推理时，KV Cache 的显存占用呈爆炸式增长。在国产卡显存受限的情况下，通常采用 INT8 甚至 INT4 量化。配合国产卡特定的量化指令集，能把 KV Cache 的显存占用压到原来的 1/4 甚至 1/8。虽然有微小的精度损失，但换来的是并发吞吐量的成倍提升，这笔买卖相当划算。
- **计算与通信的 Overlap**：MoE 架构有大量的跨节点通信。聪明的做法是拆分算子，让计算和通信重叠。当这层的专家在算矩阵乘法时，网卡和光模块已经在疯狂搬运下一层的 Token。在国产卡上，这需要手动微调通信流的优先级和计算流的 launching 时机，堪称“螺蛳壳里做道场”。
- **专家并行切分**：把不同的专家切到不同的卡上。当国产卡的片上内存或单卡显存不够时，使用极小的 Micro-Batch 来压榨算力。虽然牺牲了一点吞吐量，但保住了能跑通的底线。同时结合 Sequence Parallelism，把长序列切分到多个卡上处理，进一步降低单卡峰值显存。

## 冷思考：工程师该如何接招？

万亿模型开源固然热血沸腾，但落到实际的业务里，RY哥还是要给大家泼几盆冷水，提供三条实打实的避坑建议：

1. **别盲目在内部拉起万亿大模型**
   如果你的团队没有百卡级别的集群和专职的 Infra 工程师，老老实实调 API，或者用几 B 到几十 B 参数的 Dense 模型。万亿 MoE 的路由调试、权重切分和分布式推理的维护成本极高，不是几个 Python 脚本就能搞定的。业务的 ROI 永远大于技术的炫技。
2. **关注国产算力的“算子成熟度”而非单纯峰值算力**
   在选型或适配国产卡时，别只看 TFLOPS 参数表。去测一下 FlashAttention、RoPE 这些关键算子在框架里的实际耗时和显存增长率。峰值算力再高，如果算子没融合、访存拉胯，实际训练效率可能只有标称值的 30%。真正的试金石是端到端的 Tokens/s 指标。
3. **重构你的 Prompt 与 Agent 架构**
   万亿级别模型的能力跟几十 B 的模型有质的区别，它的长文本指令遵循和复杂逻辑推理能力更强。在应用层，要减少复杂的 Few-shot 示例，多用 Zero-shot 配合 ReAct 模式，把 token 预算留给模型做深度思考。同时，万亿模型对结构化输入更敏感，确保你的 System Prompt 足够清晰，别让珍贵的算力消耗在理解你模糊的需求上。
