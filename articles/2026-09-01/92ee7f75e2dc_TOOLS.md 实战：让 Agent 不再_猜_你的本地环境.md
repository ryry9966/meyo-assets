# 背景

OpenClaw 的 agent 工作区里躺着几个约定俗成的 Markdown 文件：`AGENTS.md` 管行为规则，`SOUL.md` 管人设，`MEMORY.md` 管长期记忆。其中最容易被冷落的是 `TOOLS.md`——很多人装完就忘，或者只留了模板里的一行注释。

这很可惜。`TOOLS.md` 的定位其实很明确：向 agent 描述"**这台机器**长什么样"。它是 agent 启动时会读取的环境说明书，也是整个工作区里唯一应该承载机器级事实的地方。

# 问题

没有它（或写得含糊）时，agent 对本地环境的认知全靠猜。典型翻车场景：

- 在 Mac 上让它装依赖，它默认敲 `apt`；换到 Linux 服务器，它又去找 `brew`；
- 它把输出写到 `~/Downloads`，而你服务器上的用户根本没这个目录；
- 同一份任务在两台机器上行为不一致：一台用 pyenv，一台用 uv，它分不清；
- 通知走哪个通道、媒体文件放哪里，每次都要口头交代一遍。

这些不是 prompt 技巧能兜住的——它们是**环境差异**，应该被显式记录，而不是让 agent 在每个会话里重新推断。

# 做法

**1. 先分清信息归属。** 机器级事实（包管理器、路径、端口）进 `TOOLS.md`；跨会话的个人偏好进 `USER.md`；工作过程中产生的事实进 `MEMORY.md`。混着放，后面没法维护。

**2. 写什么。** 建议固定五个小节，每节三五行：

- **机器身份**：主机名、用途（"这台是家里的媒体服务器，Ubuntu 24.04"）
- **包与运行时**：用什么装软件、Python 由谁管理、禁止全局 pip install
- **路径约定**：下载、媒体、日志各在哪，哪些目录只读
- **服务与通道**：本机跑了哪些服务、端口，通知走哪个 channel
- **红线**：明确禁止项（"不要动 systemd 单元"、"不要清理 /var/log"）

**3. 多机管理。** 每台机器一个独立 workspace，`TOOLS.md` 各写各的；通用规则沉淀到 `AGENTS.md`。用私有 git 仓管 workspace 时，同步模板不要覆盖它，只允许它存在机器间差异。

**4. 写完验证。** 开一个**新会话**直接问："这台机器用什么包管理器？日志目录在哪？"答得出来且与文件一致，说明加载链路是通的。旧会话可能还挂着旧上下文，别用它验证。

# 踩坑点

- **写太长。** 它每次会话都进上下文，几十行短句足够，别写成运维手册；
- **过期比缺失更糟。** 重装系统、换机器后记得更新，文件头可以加一行"最后验证：2025-06"；
- **别放密钥。** 它是明文且会被读进上下文，token、API key 一律走环境变量；
- **事实和指令混写。** "日志在 /var/log/app"是事实，放这里；"每周清一次日志"是指令，放 `AGENTS.md` 或 cron。

# 可复用建议

- 新机器 onboarding 固定花 10 分钟填一遍，把它当流程而不是随手事；
- 拿不准某条该不该写进去，问一句：**换台机器这条还成立吗？** 不成立就属于 `TOOLS.md`；
- 多设备场景维护一份空模板放仓库里，README 指向它，减少口头传授。

# 总结

`TOOLS.md` 解决的不是 prompt 问题，而是知识归属问题：把隐性、易变、机器绑定的环境事实显式化，让 agent 从"每次猜"变成"开卷查"。写好这一个文件，你在多台机器间迁移 agent 的成本，会从"重新调教"降到"对一遍清单"。
