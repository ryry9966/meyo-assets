# OpenClaw 的 IDENTITY.md：给 AI 一个可进化的身份

## 背景

在 OpenClaw 编排多个 Agent 时，我们常遇到这样的问题：同一个代码审查 Agent，今天说话简洁，明天啰嗦；这一轮允许调用 GitHub API，下一轮却越权执行本地命令。这些现象的背后，是缺少一个稳定、可追踪、可更新的身份定义。很多人把 system prompt 直接写在 Agent 配置或代码里，散落各处，无法保持一致，更无法随项目演进。

IDENTITY.md 是一种轻量级的身份文件，放在项目仓库中，作为 Agent 的“行为宪法”。它不是一篇散文，而是一组结构化约束，像代码一样被维护。

## 问题

没有身份文件时，AI 的行为完全依赖每次传入的临时 prompt，容易漂移；有了身份文件但管理随意，也会出现三个典型问题：内容膨胀占用上下文、约束绝对化导致僵化、修改无审查导致行为失控。

## 做法与步骤

1. **创建 IDENTITY.md**，写入核心身份字段。建议包含：
   - `role`: 一句话定义角色，如“你是 OpenClaw 项目的代码审查助手”。
   - `scope`: 明确职责边界，如“只审查 diff，不做架构建议”。
   - `tone`: 语气要求，如“简洁、直接、给出行号”。
   - `decision_rules`: 关键决策规则，如“发现安全漏洞必须阻断合并”。
   - `allowed_tools`: 允许使用的工具列表。
   - `memory`: 需要长期记住的上下文，如术语、常用路径。
2. **加载方式**：在 OpenClaw 配置中引用该文件，例如在 `openclaw.yaml` 中设置 `identity_file: ./IDENTITY.md`，或通过 pre-prompt 钩子把文件内容注入 system prompt。确保每个 Agent 实例启动时自动读取。
3. **版本管理**：将 IDENTITY.md 加入 Git，更新走 PR 流程。变更说明必须回答“为什么改”和“影响哪些行为”。
4. **反馈更新**：定期回顾 Agent 输出，发现与身份不符的行为，记入 issue，然后按需修订 IDENTITY.md，形成“表现 → 反馈 → 进化”闭环。

## 踩坑点

- **上下文膨胀**：把大量项目背景、名词解释写进身份文件，导致 system prompt 过长，挤占任务上下文。建议身份文件控制在 500 字以内，详细背景放文档，由 Agent 按需检索。
- **约束绝对化**：写“永远不要调用写操作”或“总是保持简短”，遇到必须写文件的场景时，AI 可能强制拒绝，无法完成任务。应采用“默认只读，除非用户明确授权”这类可协商表述。
- **优先级冲突**：身份约束与单次任务指令冲突。比如身份要求“每次回复不超过 3 行”，但用户要求“详细分析”。需要设定优先级并测试，通常任务指令应高于身份约束，但安全规则例外。
- **无审查修改**：多人协作时，有人直接改 IDENTITY.md 而不通知，导致其他成员看到 Agent 行为突变。可以通过 CODEOWNERS 文件限制修改权限，或要求 PR 审批。
- **工具边界缺失**：身份未声明工具权限，Agent 可能通过 MCP 调用未预期工具。建议显式列出允许和禁止的工具，并在工具调用层做二次校验。

## 可复用建议

- **模板化**：团队统一 IDENTITY.md 模板，固定字段顺序和格式，降低阅读成本。模板可以放在 `templates/` 目录。
- **分层设计**：把身份拆成三层：核心身份（稳定，少变）、项目上下文（按需动态加载）、任务指令（会话级，优先级最高）。核心身份只放最基础的行为准则。
- **自动化校验**：写一个简单脚本检查字段完整性、字数上限，接入 pre-commit 或 CI。
- **回归测试**：准备一组代表性 prompt，每次更新身份后跑一遍，对比输出是否符合期望，避免“改进”实际导致退化。
- **把身份当代码**：用提交历史追踪 Agent 的“性格变化”，遇到问题时可以快速回滚到上一个稳定版本。

## 总结

IDENTITY.md 给 OpenClaw 中的 AI 提供了一个可进化的身份锚点。它不像泛泛的“角色设定”那样随意，而是通过结构化字段、版本控制和反馈循环，让 Agent 行为稳定且可预期。工程化的关键在于：精简、分层、审查、测试。当你开始用维护代码的方式维护身份文件，AI 的可靠性会明显提升。
