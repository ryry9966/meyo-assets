## 背景

在 OpenClaw 这类 agent 自动化里，触发源天然很杂：cron 定时、消息指令、webhook 回调，还有人工那句"再跑一次"。叠加网络超时重试、agent 重启后的任务恢复，同一个任务被执行两次以上是常态，不是例外。消息系统里这叫 at-least-once 投递：基础设施只能保证"至少送达一次"，多出来的那一次，得靠任务自己兜住。

## 问题

非幂等操作在重复执行时会放大副作用：通知发两遍、工单或文件建两份、计数加两次。更隐蔽的是"中途失败后重试"——前半段已经生效，重试又从头执行一遍。日志看起来一切正常，只是结果悄悄多了。

先把定义摆清楚：幂等指执行一次和执行 N 次，最终状态一致。"把状态设为 done"是幂等的，"计数器加一"不是。HTTP 里 PUT 和 POST 的区别，就是这个道理。

## 做法

1. **给任务分类**。天然幂等：按 key 覆盖写、upsert、按条件删除。非幂等：追加、自增、发消息、创建资源。后者才是需要处理的。
2. **用确定性的幂等键**。键从触发语义推导，比如 hash(任务名 + 触发载荷 + 业务日期)，而不是每次运行随机生成的 UUID——重试一次键就变了，等于没有。
3. **落一个执行账本**。一张 SQLite 表（key, status, updated_at）够用。执行前查键：done 就跳过，running 视情况接管，唯一索引兜底并发。
4. **步骤级 checkpoint**。长任务按步骤记录进度，重试从断点续跑，而不是整段重来。
5. **外部调用透传幂等键**。支持 Idempotency-Key 的 API 一定要传；不支持的（比如某些发消息的 MCP 工具），在插件层加去重：发送前先写 outbox 记录，确认成功后再标记。

## 踩坑点

- **键里掺了执行时间**。用"当前时间戳"生成键，一分钟后的重试就成了新键。应该用业务时间窗口（当天、该批次）。
- **查完再写不是原子的**。两个并发运行都通过了检查，然后各跑一遍。靠数据库唯一约束或 setnx，别靠应用层的 if。
- **只在任务末尾标成功**。中途崩溃，前面白做还要重做。checkpoint 粒度要细。
- **超时不等于失败**。请求可能已经成功，只是响应丢了——这正是幂等性存在的理由。抱着"没报错就是没执行"的假设写代码，一定会翻车。
- **过早清理账本记录**。下游还没确认就删掉 done 记录，一崩就是重复副作用。

## 可复用建议

- 心法一句话：**写全量，不写增量；"设置为"优于"加上"**。
- 把执行账本做成公共小工具，所有定时任务复用，任务配置里显式声明幂等键。
- 排查非幂等的外部调用，在插件或 MCP 工具层统一加去重，所有调用方受益。
- 写一个专门的测试：同一任务连跑两遍，断言终态不变。幂等性是可以做回归测试的。
- 代码评审时，把"这个操作跑两次会怎样"当成固定问题问一遍。

## 总结

幂等性不是锦上添花的优化，而是重试和调度的前提。在触发源不可控、重试不可避免的前提下，"跑两次等于跑一次"应该作为设计要求写进每个自动化任务，而不是等出现重复数据之后再回来补课。
