## 背景：重复执行不是意外，而是常态

在 OpenClaw 的定时任务、MCP 工具调用、Webhook 插件和 Agent 流程里，重复执行通常不是代码写得差，而是系统语义决定的：

- Cron 上一次任务还没结束，下一次调度又启动；
- MCP server 超时后，框架自动重试同一个 tool call；
- Webhook 因网络问题重复投递；
- Agent 在一次任务里重复选择同一个工具。

这些场景的共同点是 **at-least-once**：消息或触发至少会到一次，但不保证只到一次。所以工程上要解决的不是“禁止重复执行”，而是“重复执行不会产生重复副作用”。这就是幂等性。

一个实际表现：如果你做一个“每小时拉取一次外部数据并写入本地表”的 OpenClaw 插件，重复触发可能造成重复记录；如果是“支付成功后开通权限”，重复执行可能造成重复开通或重复扣减资源。问题不在调度框架，而在写入链路没有幂等边界。

## 问题拆解：重复执行在哪里出事

重复执行最常见的三类副作用：

1. **重复写入**：同一条业务对象被插入多次；
2. **非幂等变更**：`stock = stock - 1` 这种操作执行两次就扣两次；
3. **外部副作用**：重复发短信、邮件、调用支付接口、创建远程资源。

只要任务边界里存在这三类动作，就需要把“任务执行”改造成“带有幂等键的业务操作”。

## 做法：给任务加一个业务幂等键

### 1. 不依赖任务 ID，依赖业务键

任务 ID 每次执行可能都不同，所以不能用它做幂等。应该从业务对象提取稳定键。

例如 OpenClaw 定时同步任务：

```python
op_key = sha1(
    f"{tenant}:{source}:{entity_id}:{date_str}"
).hexdigest()
```

MCP 工具类似：某个写操作最好接收 `idempotency_key`，或者由 `resource_id + action + version` 生成。重复的 Agent tool call 带着同一个 key 到达，服务端就能识别为同一次操作。

### 2. 用存储层唯一约束做最后防线

不要只在应用层判断“查一下有没有，没有就插入”。并发下两个请求可能同时查不到，然后都插入。

推荐做法：

```sql
INSERT INTO task_dedup(op_key, status, created_at)
VALUES (:op_key, 'processing', now())
ON CONFLICT(op_key) DO NOTHING;
```

如果插入返回 0 行，说明这个 key 已经存在，可以直接返回已有结果，或者进入等待/检查流程。

对业务表也一样，能在表上建唯一索引的，尽量建。比如“同一来源、同一对象、同一天”只允许一条记录，天然阻止重复写入。

### 3. 把非幂等变更改成条件更新

库存扣减、余额变更这类操作，需要把“扣”的动作与幂等键绑定。

错误做法：

```sql
UPDATE stock SET count = count - 1 WHERE sku = :sku;
```

重复执行就会重复扣减。正确做法是让变更记录唯一，例如：

```sql
INSERT INTO stock_ledger(op_key, sku, delta, created_at)
VALUES (:op_key, :sku, -1, now())
ON CONFLICT(op_key) DO NOTHING;

UPDATE stock SET count = count - 1
WHERE sku = :sku
AND EXISTS (
    SELECT 1 FROM stock_ledger
    WHERE op_key = :op_key
    AND status = 'applied'
);
```

真正产生效果的是 `stock_ledger` 那条唯一记录，变更只会在首次写入成功后应用。

### 4. 对进行中的任务处理“重复触发”

如果同一个 op_key 第一次还在执行，第二次触发不能简单返回 `success`，否则可能造成两个执行体同时跑。

可以把状态机拆成：

- `processing`：已有执行体在处理；
- `success`：已完成；
- `failed`：允许重试；
- `expired`：租约超时，可重新抢占。

对于耗时任务，可以加 `lease_until` 字段，超过时间没心跳才允许新执行体接管。这比单纯“重复请求直接返回成功”更稳。

## 踩坑点

1. **只靠时间去重**：比如“5 分钟内重复丢弃”，上游 10 分钟后重试仍然重复；
2. **key 拼接不稳定**：字段顺序不同、JSON 序列化不稳定，导致同一操作生成不同 key；
3. **先删后插破坏幂等**：有人用 `DELETE` 再 `INSERT` 代替 upsert，会把原有的完成记录删掉，重复执行；
4. **把非幂等外部调用当成功返回**：短信、邮件、支付接口通常无法通过数据库唯一约束回滚。这类外部动作要单独做 provider 侧幂等，或者先记录请求、成功后再标记，不重复发送；
5. **只对入口做去重，不对 DB 做主键约束**：入口去重一漏，数据就脏。

## 可复用建议

- 所有“写类型”MCP 工具都建议支持 `idempotency_key`，Agent 重试时复用同一个 key；
- OpenClaw 定时任务用“执行窗口 + 对象 ID + 动作”生成 key：`sync:{source}:{entity}:{day}`；
- 去重表保留 7–30 天，视上游重试窗口而定；
- 优先使用天然唯一键，例如 `org/repo/date`，不要什么都用随机 UUID；
- 对关键链路加四件套：**入口幂等键 + 数据库唯一约束 + 条件更新 + 可重复返回结果**；
- 把重复请求返回保存的原始结果，而不是重新执行一遍，能减少下游压力。

## 总结

幂等性不是框架开关，也不是 Agent 自带能力，它是一组工程约束。对 OpenClaw、Agent、MCP 这类自动化系统来说，任务重复执行是常态，真正决定系统稳不稳的，是每个写操作是否拥有稳定幂等键，以及存储层是否兜底。

当你下一次发现重复任务时，不要急着加锁去“阻止重复触发”，先检查能否让重复触发变得无害。
