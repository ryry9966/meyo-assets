---

在 OpenClaw 这类 Agent、MCP、插件组合的自动化环境里，任务来源和触发方式很多：定时任务、Webhook 回调、消息事件、模型工具调用重试。同一个逻辑被执行两次甚至多次，不是小概率事件，而是常态。真正的问题不是“重复执行”，而是“重复执行是否会产生额外副作用”。幂等性要解决的就是后者。

## 背景

自动化链路里，重试几乎无处不在。HTTP 超时、Webhook ack 未及时返回、队列重投、Agent 自己判断“上一步没成功”再次调用工具，都会让同一个业务事件进入执行流程多次。OpenClaw 插件收到第三方回调时，对方可能因为没收到 200 重推；MCP 工具调用超时后，模型可能重新发起同一请求。如果这些任务不做幂等设计，重复执行会变成脏数据、重复外呼、重复建单。

## 问题

一个典型场景：插件收到“工单已更新”的 Webhook，执行“同步到本地库并通知用户”。第一次执行成功，但响应慢了，上游认为失败，重推了同一条 event。没有幂等设计时，本地会写入两条记录，用户收到两条通知。另一个例子：MCP 写工具“创建工单”在服务端已创建成功，但客户端超时后重试，结果生成了两张内容相同的工单。根因不是重试，而是任务没有定义“什么算同一次执行”。

## 做法/步骤

**1. 给每个任务定义幂等键**

幂等键是业务事件的唯一标识。外部事件用 `event_id`，消息用 `message_id`，定时快照用 `business_date`。不要每次执行都新生成一个 UUID 当作幂等键，那样重试会全部变成新事件。

**2. 数据库唯一约束兜底**

应用层判断“是否已处理”很容易有竞态。更可靠的做法是在存储层建唯一索引：

```sql
ALTER TABLE task_execution
  ADD CONSTRAINT uq_task_source_external
  UNIQUE (source, external_id);
```

写入时用冲突忽略：

```sql
INSERT INTO task_execution (source, external_id, status, payload)
VALUES ('jira', 'EVT-1001', 'pending', '{}')
ON CONFLICT (source, external_id) DO NOTHING;
```

如果冲突，就读取已有记录并返回相同结果，而不是再次执行副作用。

**3. 用状态机管理任务生命周期**

任务状态至少包含 `pending`、`running`、`done`、`failed`。重复触发时，`done` 或 `failed` 直接返回；`pending` 或 `running` 需要检查是否已有执行者。布尔字段 `is_processed` 难以表达中间状态，不建议作为唯一判断。

**4. 外部 API 调用传递幂等键**

创建订单、开工作业、发送通知等有副作用的调用，尽量使用服务端支持的 `Idempotency-Key` 机制。若不支持，则本地缓存“请求指纹 + 响应”，相同指纹直接返回缓存。

**5. MCP 工具读写分离**

读操作天然幂等，可以放心重试。写操作必须要求参数中携带 `request_id` 或 `idempotency_key`，并在工具描述中明确：同 key 重复调用不会重复产生副作用。

## 踩坑点

- **check-then-act 不原子**：先查“有没有处理过”，再插入，并发生两个执行都会通过检查。唯一索引是最终防线。
- **幂等键选得过粗或过细**：用“当天日期”当键，同一天的不同事件会被误判为重复；用随机值当键，重试全部失效。
- **只做内存去重**：OpenClaw 重启或多实例部署后，内存集合丢失，去重失效。
- **状态机过于宽松**：没有拦截终态任务，失败后重复触发仍会再次执行副作用。
- **外部平台幂等窗口有限**：有些服务的 `idempotency_key` 只保留 24 小时，长周期重试可能突破窗口，需要本地持久化最终结果。
- **日志里看不到幂等键**：排障时无法判断同一条日志是重复执行还是新事件。

## 可复用建议

- 写自动化任务前先回答：哪个字段组合能唯一标识一次业务事件？
- 数据库唯一索引是最后一道防线，不要只依赖应用层 `if`。
- 重试时务必携带相同幂等键，不要重新生成。
- 对 MCP 写工具，参数中强制要求 `request_id`，缺失则拒绝执行。
- 保持读写分离。读接口可以无条件重试，写接口必须有去重。
- 定期统计重复触发命中率。如果某任务重复命中异常升高，先排查上游事件源，而不是盲目增加重试次数。

## 总结

幂等性不是高深概念，而是自动化任务的基础卫生。重复执行不可怕，可怕的是没有定义“同一次”是什么。把幂等键、数据库唯一约束、状态机三件事落到每个写操作上，重复执行就不会从故障演变成事故。在 Agent、MCP、插件组合的链路里，重试和重放无法避免，但额外的副作用可以被设计掉。
