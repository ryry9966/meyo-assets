## 背景

跑 Agent 自动化久了会发现一个规律：任何会被自动触发的任务，迟早会被执行不止一次。定时任务重叠触发、网络超时后的重试、消息队列的 redeliver、用户手动"再跑一遍"，还有 LLM Agent 在报错后自作主张的重试。在 OpenClaw 这类可插拔的环境里，插件和 MCP 工具是别人写的、调度是你配的，重试逻辑分散在各处，很难保证"只执行一次"。

所以工程上真正的目标不是"不重复"，而是"重复了也没事"——这就是幂等性：同一操作执行一次和执行 N 次，最终状态一致。

## 问题：非幂等的代价

几个典型场景：

- 失败告警走"发消息"插件，超时重试三次，群里出现三条一样的告警；
- 定时任务生成日报，文件名带 `datetime.now()`，重跑一次多出一份 `report_1432.md`；
- Agent 调"创建工单"工具，响应丢失后重试，开出两张重复工单。

共性是：副作用（写文件、发消息、调外部 API）没有幂等保护，而触发层（调度器、重试器、Agent 决策）默认会重复。

## 做法：四步

1. **定一个稳定的幂等键。** 键必须来自任务的业务身份，而不是运行时随机量。cron 任务用"任务名 + 调度周期"（如 `daily-report@2025-06-01`），事件触发用事件 ID。不要用进程内生成的 UUID 或当前时间戳。
2. **执行前先查状态。** 把"做过没有"落在外部可查的地方：SQLite、状态文件、Redis 都行。命中幂等键就直接跳过，或返回上次结果。
3. **写入尽量用 upsert / 覆盖语义。** 文件用固定路径覆盖写，不追加；数据库用唯一索引或 `ON CONFLICT`；外部 API 优先选支持幂等键的接口，把键透传过去。
4. **check 与 act 之间加原子占位。** 单纯"先查后写"在并发下有竞态。用 `SET NX`、唯一索引冲突或文件锁，谁占到谁执行，另一个直接退出。

伪代码大致是：

```python
key = f"daily-report@{schedule_date}"
if not lock.acquire(key):        # 原子占位
    return
if state.get(key) == "done":     # 执行前查状态
    return
result = do_work()               # 内部全部 upsert 语义
state.set(key, "done")
```

## 踩坑点

- **幂等键里混进时间戳。** `now()` 精确到秒，重试落在下一秒，判重失效。键里只放业务周期，不放执行时刻。
- **成功但响应丢了。** 网络超时不代表服务端没执行。对非幂等写操作，重试前先查询远端状态，而不是盲目重发。
- **只在提示词里叮嘱模型"别重复"。** 靠不住。LLM 会忘、会误判，幂等必须做在工具层、插件层，模型层只是锦上添花。
- **清理逻辑忘了幂等。** 删除要写成"存在才删，不存在也算成功"，否则异常路径上清理步骤自己报错。
- **并发实例。** 手动触发和定时触发撞车是常态，别假设单实例运行。

## 可复用建议

- 给每个自定义 MCP 工具在描述里写明幂等语义：幂等 / 非幂等 / 需要幂等键。调用方（包括 Agent）据此决定重试策略。
- 沉淀一组 `ensure_*` 工具：`ensure_file`、`ensure_message`、`ensure_record`，语义统一为"确保达到目标状态"，判重在内部处理。
- 上线前做一次重放测试：同一条任务手动连跑两遍，diff 两次的输出和外部副作用，没有变化才算过关。

## 总结

幂等不是高级优化，而是自动化的默认假设。调度会重叠、网络会超时、Agent 会重试——把"这段代码会被执行两次"当作设计前提，用稳定的幂等键、前置状态检查、upsert 语义和原子占位，把重复执行变成无害操作。做到这一点，你的自动化才敢真的无人值守。
