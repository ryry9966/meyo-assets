## 背景

社区里跑常驻 Agent 的人越来越多了：接 MCP、挂插件、加定时任务，工作流一旦跑顺，就忍不住想分享。但调试期的日常是贴日志、贴配置、贴 prompt——而 Agent 的上下文里，往往混着不该出去的东西：内网地址、密钥、客户数据、私有工作流的实现细节。一次"大佬帮我看看这个报错"，可能就是一次泄露。

## 问题在哪

实际观察下来，泄露主要走三条路：

1. **工具权限过宽**。filesystem 类 MCP 挂到根目录或整个 home，Agent 能读到 `.env`、内部文档、密钥文件；它"乐于助人"，会把读到的东西写进总结。
2. **输出即上下文**。RAG 检索到的内部文档被原文引用进回答；用户复制回答贴到社区，等于把文档贴了出去。
3. **人为贴出**。日志 URL 的 query 里带 token，截图漏了 Authorization 头，配置文件原样上传。

还有一个更隐蔽的问题：很多人在系统提示里写"不要泄露内部信息"，就以为安全了。提示词是软约束，上下文一长、多轮一绕，它就会被稀释。真正的红线只能靠权限。

## 怎么做

**第一步：权限收敛。** MCP server 按需启用，能只读就不给写；敏感路径（`.env`、密钥目录、内部文档）放在 Agent 工作区之外，或在 MCP 配置里显式 deny；出站网络走白名单；执行命令、对外发消息这类高危工具，开人工确认。

**第二步：导出即脱敏。** 写一个十几行的 redact 脚本，正则匹配 token/JWT、内网 IP 段、自定义域名、手机号，替换成 `<REDACTED>`。把它变成贴日志前的固定动作，而不是靠记性。例如：

```bash
grep -E "(sk-[A-Za-z0-9]{20,}|eyJ[A-Za-z0-9_-]{10,}|192\.168\.|\.internal)" app.log
```

有命中就先处理再贴。

**第三步：配置分区。** 把"可公开的工作流说明"和"内部实现"分开存放。Agent 可读路径里只放前者；内部细节连上下文都不进，自然谈不上泄露。

**第四步：贴前三查。** 密钥、内网地址与真实域名、客户/业务数据。截图裁掉请求头，真实值用占位符替换。

## 踩坑点

- **workspace 打包带走 `.env`**：让 Agent 帮忙打包或备份工作区，密钥一起进了压缩包。
- **脱敏正则漏网**：base64/JWT 形态的密钥、自定义 TLD 的内网域名（如 `.corp`）经常匹配不到。
- **内部文档喂给 Agent 求优化**：把私有工作流文档丢给 Agent 要"改进建议"，回答被直接贴出——文档进了上下文，就应视为可能公开。
- **社区内容反注入**：让 Agent 自动读取并执行帖子里的指令，是另一个方向的坑。工具调用保持确认，别全自动。

## 可复用的东西

- 一份 redact 正则清单（token、JWT、内网段、自定义域名、手机号），团队共用一份，随泄露案例持续补充。
- 一份最小权限 MCP 配置模板，新 Agent 从模板起步，而不是从全量权限起步。
- 贴前"三查"清单，写进社区置顶和 issue 模板。
- 每月一次审计：过一遍每个 Agent 挂了哪些工具、能读哪些路径。

## 总结

Agent 的安全红线，不是一句提示词，而是两道闸门：**权限边界**决定它能碰到什么，**导出流程**决定什么能出去。把脱敏做成默认动作，把权限从模板起步，社区分享才敢真正放开手脚。泄露往往不是恶意攻击，而是一次热心的"帮看看报错"——用流程挡住它，比提醒每个人小心更可靠。
