## 背景

我订阅的信息源散落在几十个博客、GitHub Releases 和几份 newsletter 里。RSS 仍然是最可控的订阅协议，但"订阅了"和"读完了"是两回事——高峰期一天几百条 entry，逐条读不现实。目标定得很朴素：让 AI 做第一轮过滤和压缩，只把"今天值得看的"推送给我，原始链接始终保留。

## 问题

拆下来主要是四个：

- 不少源只给 summary，直接拿去总结会丢信息；抓全文又多一层抓取和清洗
- 每条都喂大模型，成本和延迟都不可接受
- 同一事件多源重复，日报会被灌水
- 管线长（抓取 → 清洗 → 摘要 → 过滤 → 投递），任何一环断了当天就没产出

## 做法

分层搭，每层职责单一：

1. **数据源分级**。订阅列表全部放进 OPML/YAML，分两档：核心源（15 个左右，每日出摘要）、边缘源（只进周报）。源列表是配置，代码不动。
2. **定时抓取**。用 OpenClaw 的定时任务每天早上触发，抓取封装成一个 MCP 工具：带 ETag/Last-Modified 做增量，并发 ≤ 3，失败重试两次后降级跳过。entry 落 SQLite，以 guid 去重。
3. **清洗与正文抽取**。只有 summary 的条目回抓原文页，readability 抽正文，去掉脚本和广告，截断到 4000 字符左右。这一步直接决定摘要质量，比 prompt 调优收益大。
4. **两段式摘要**。先用小模型给每条打分（0-10 + 标签），≥ 7 的留下；留下的再由大模型做结构化摘要，输出固定 JSON：一句话摘要、3 条要点、tags、原文链接。prompt 里明确约束"只基于原文总结，原文没有的写'原文未提及'"。
5. **投递**。聚合成一份 Markdown 日报，走 OpenClaw 的消息通道推到 IM。摘要只做导航，不替代点开原文。

## 踩坑点

- **pubDate 时区**。有的源给 UTC，有的给本地时间还不带时区，直接比较会漏条或重复。统一转 UTC 入库，去重用 guid + link 双键。
- **RSSHub 限流**。自建实例加缓存比公共实例可靠，抓取频率别高于每小时一次。
- **摘要幻觉**。第一版 LLM 会把原文没有的观点"补全"进摘要。加上"只基于原文"约束，并每天随机抽查 5 条人工核对，问题基本消失。
- **语义去重**。标题相似度 + 当日标签重合，效果够用，暂时没必要引入 embedding 模型。
- **成本**。两段式（小模型过滤 + 大模型精摘）后，月成本降到全量喂大模型的四分之一左右。

## 可复用建议

- 先定结构化输出的 schema，再写 prompt。下游 Agent 消费 JSON 比解析自由文本稳定得多。
- 原始数据全量落 SQLite，随时可以重跑摘要或换模型重建，别只存最终结果。
- 从 10 个源开始跑两周，观察打分分布再调阈值，别一上来求全。
- 加一个源健康检查：连续 30 天无更新的源自动静默并通知，避免管线里堆死链接。

## 总结

这条管线稳定跑了一个多月，日报从日均三百条压到十条上下，晨间阅读时间控制在十五分钟内。体验上的结论：AI 在这里做的是过滤和压缩，不是替代阅读；工程量的大头在清洗、去重和成本控制，不在模型本身。如果你也在用 OpenClaw 做自动化，建议从"一个定时任务 + 一个 RSS MCP 工具"起步，最小可运行版本一百来行就够了，先跑通再迭代。
