最近，Kimi 被曝向微软 Azure、亚马逊 AWS、谷歌云提出一项要求：如果要在云平台上架其开源模型，并提供托管推理服务，需要把相关收入的 30% 分给模型方。消息一出，很多人的第一反应是“开源模型不是免费吗？怎么开始收租了？”其实，这更像开源软件与云厂商之间持续多年的“渠道税”博弈，在大模型时代的重演。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-01/b2d044ec069a4f46.png)

## 一、30% 为什么扎眼：云厂商赚的是“管道费”，模型方不想只当“原料商”

- 云厂商托管开源模型，主要收入来自推理 API 调用。以头部开源模型为例，按需推理的定价通常比裸 GPU 成本高出 50%～150%，中间包含弹性扩缩容、SLA、监控、合规等费用。行业分析普遍认为，成熟 AI 推理服务的毛利率可以做到 50% 以上，高于传统 IaaS。
- 模型方投入大量算力和数据训练出高质量权重，但在云平台上架后，只能赚到一次性授权费，甚至完全赚不到钱。用户每调用一次 API，云厂商赚大头，模型方只能看着。
- Kimi 提出的 30%，刚好对标苹果 App Store / 谷歌 Play 的抽成比例，也接近云市场对独立软件供应商的返佣上限。但模型不是普通软件，它是生成式 AI 的核心“原料”。当原料稀缺时，供应商就有底气谈分成。
- 举一个简化例子：某企业通过云平台调用开源模型，月账单 1 万美元。若按 30% 分成，模型方拿走 3000 美元，云厂商留下 7000 美元用于覆盖 GPU、网络和运维。云厂商未必不能接受，因为模型方可能同步提供权重更新、量化版本、安全对齐等持续维护。

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-01/0461972356a28e54.png)

## 二、开源不等于免费：从 Apache 2.0 到“开放权重 + 商业限制”

- 传统开源软件许可证（GPL、Apache 2.0、MIT）允许商业使用，但云厂商可以合法“白嫖”开源代码并包装成云服务。例如早期 AWS 托管 Elasticsearch，直接冲击了 Elastic 的商业收入。后来 Elastic 变更许可证、MongoDB 推出 SSPL、Redis 采用 RSAL，核心目的都是限制云厂商“只索取不回报”。
- 大模型时代，“开源”这个词被泛化。很多所谓开源模型，实际是开放权重（open weights），不是完整的开源软件。例如 Llama 2/3 的社区许可对月活超过 7 亿的云厂商额外授权有要求；部分国产开源模型也区分商用场景，只是条款没有大张旗鼓宣传。
- Kimi 的做法很可能不是修改开源许可证，而是通过云市场分销协议实现分成：权重仍然可以免费下载，但如果你通过云平台提供托管 API，且规模达到一定阈值，就要按收入分成。这类似“源码免费、托管收费”的双轨制。
- 历史已经反复验证：Redis、MongoDB、Elasticsearch 都走过“先开源做大生态，再通过许可证或商业协议向云厂商收保护费”的路。开源模型正在复制这条路径，只不过货币化对象从“代码库”变成了“权重 + 推理服务”。



## 三、云厂商会不会答应？算一笔三方账

- 云厂商如果拒绝上架某个热门模型，可能失去一批企业客户，尤其在 AI 应用爆发期，客户会优先选择模型齐全的平台。自己复刻或微调类似模型，成本高、周期长，还不一定能匹配社区生态。
- 如果接受 30% 分成，云厂商通常有两个选择：自己消化，压缩利润；或者把成本转嫁给最终客户，在 API 定价中单列“模型许可费”。从历史看，后者更常见，因为 IaaS 竞争已很激烈，很少云厂商愿意长期贴钱。
- 对模型方而言，分成收入可以覆盖后续版本迭代、红队测试、适配优化等成本，更重要的是防止云厂商用低价模型 API 倾销，把模型方锁死在“只做训练、不碰分发”的弱势位置。
- Kimi 如果只在自家平台提供 API，收入全归自己，但很难触达 AWS/Azure 上庞大的存量企业客户。通过云厂商分发，让出一部分收入换规模，30% 更像是“渠道费”而不是“税”。
- 风险同样存在：如果头部云厂商集体抵制，模型方可能失去海外市场；如果接受，最终 API 价格可能上涨，或者出现“自带模型”折扣——企业自己下载权重部署可绕过部分费用。



## 四、开发者和企业会受什么影响？

- 直接下载权重、在自己的 GPU 集群上自部署的开发者，大概率不受分成影响。因为分成发生在云平台托管服务层面，不是对开源权重本身收费。
- 通过云 API 调用模型的企业，可能会看到账单里出现单独的“模型许可费”或整体价格微调。类似云市场镜像既有软件许可费 + 基础设施费。
- 创业公司和个人开发者需要重新评估成本：如果模型方能从云平台分成，可能更有动力提供官方托管或平价方案，但也可能让第三方中转服务变得更复杂。
- 行业可能分化：头部模型（性能强、社区活跃）有资格谈 30% 甚至更高；长尾开源模型很难要价，甚至需要付费上架求曝光。马太效应加剧。
- 工程师要特别关注合同里的“间接收入”定义：分成基数是仅指 API 调用，还是包括微调服务、私有化部署支持？不同口径对成本影响差异巨大。

## 五、冷思考：开源模型的“收租”能持续吗？

- 护城河不在权重本身，而在生态、数据飞轮、持续迭代能力。如果模型方停止更新，云厂商完全可以用旧权重继续服务，分成协议能否覆盖旧版本？这是一个未解问题。
- 分成价格战可能出现：Kimi 要 30%，其他开源模型可能用 10% 或 0 分成抢云厂商资源，形成类似开源数据库“open core”的竞争格局。最终只有少数头部模型能真正收到钱。
- 跨境数据、收入审计、第三方托管等场景下，分成计算与核验成本很高。可能催生标准化协议、链上审计或第三方数据服务。
- 类比音乐流媒体：唱片公司能拿到 60%～70% 分成，是因为内容极度稀缺且版权强制。云平台与模型方的博弈，取决于模型的可替代性。如果模型效果可以被竞品 1～2 个月内追上，30% 就是脆弱的。

最后，三条冷思考/实用建议：

1. **开发者选型**：如果需要稳定 SLA 和合规，使用云托管 API 时留意账单是否拆分“模型许可费”；如果成本敏感，自部署 + 推理优化框架仍是首选。
2. **模型厂商**：不要把 30% 当标准答案。可以设计“分层分成”：基础推理低分成，高级微调、专属部署高分成，与云厂商共建生态，而不是简单抽税。
3. **观察指标**：未来 12 个月，看头部开源模型的上架条款、云厂商的“自带模型”折扣、以及是否有第三方审计分成。这决定“收租”是长期趋势还是短期试探。
