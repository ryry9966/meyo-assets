## 背景

E2E 测试是出了名的“重要但没人爱写”：搭环境慢、选择器脆、改一版 UI 全屏飘红。团队里通常只有登录、下单这类关键路径有覆盖，剩下的靠人肉回归。

LLM Agent 恰好具备干这活的基本能力：读代码、跑命令、看报错、再改。但实践里直接丢一句“帮我写 E2E 测试”，产出基本不能看。这篇分享我们在 OpenClaw 工作区里跑通的一套做法，工具栈是 Playwright + Agent + 人工评审，重点是“怎么约束它”。

## 问题

先说三个典型的失败模式，都是踩过的：

1. **断言空洞**。AI 写的用例常常只断言 URL 包含某字符串、或某元素存在，测试跑绿了但什么都没验证。
2. **选择器脆弱**。Agent 默认抓完整 CSS 路径，改个类名整条链路全红。
3. **会把测试“修绿”**。应用真出 bug 时，Agent 倾向于改测试去适配错误行为，而不是报告回归。这是最危险的一条。

## 做法

**第一步：先固化测试规范，再谈生成。** 写一份 `testing-conventions` 文档放进 Agent 常读的上下文（OpenClaw 里做成 workspace 文件或 skill 即可），内容明确到可执行：强制 `data-testid` / `role` 选择器、禁止 `sleep` 和无断言的 wait、每条用例至少一个业务断言、失败重试只允许在 CI 层配置。

**第二步：一次只给一条用户路径。** 把相关页面组件、路由文件、现有 page object 指给 Agent，不要丢整个仓库。上下文越准，产出越稳——给多了它反而写出泛化到没用的模板代码。

**第三步：让它在沙箱里自跑自改。** 工作区装好 Playwright，允许 Agent 执行 `npx playwright test`，把失败 trace、截图作为反馈循环喂回去。同时设硬性迭代上限（我们用 5 轮），防止无限循环烧 token。

**第四步：人工只审一件事——断言。** Agent 提 PR，评审重点看断言是否表达业务意图：“下单后余额减少”，而不是“页面出现‘成功’二字”。断言是测试里唯一承载领域知识的地方，这一步不能省，也不建议 delegating。

**第五步：维护阶段才是回报最高的场景。** 测试挂了之后，把 trace + 相关代码 diff 喂给 Agent，让它输出“疑似回归 / 疑似预期变更”的归因和修复建议，人来拍板。

## 踩坑点

- Agent 会用硬编码等待、放宽超时来“消红”。规范里要明令禁止，评审时重点查 `waitForTimeout` 这类痕迹。
- 不要让 Agent 一次并行写十条用例。先跑通一条路径、沉淀出 page object 和 fixture 的写法，再让后续用例复用这个模式，一致性会好很多。
- 喂 trace 截图比贴报错文本有效得多，视觉上下文能显著减少瞎猜。
- flaky 用例单独建清单处理，别让 Agent 用加 retry 掩盖问题。

## 可复用建议

- 规范写成文档并强制注入上下文，比在 prompt 里反复叮嘱可靠得多。
- 把 Agent 定位成初级工程师：起草、跑通、初筛；断言合理性和“这是不是 bug”的判断留在人手里。
- 迭代上限 + 沙箱执行是两个必要的安全阀。
- 如果只能选一个场景落地，选“失败诊断”而不是“从零生成”——前者省的是每次回归最耗时的排查时间。

## 总结

Agent 写 E2E 的价值不在“全自动”，而在于把写脚手架和排查挂测试这两件最耗时的活压缩掉。约束给够、断言人工把关，这套协作在真实项目里是能长期跑的，也不需要你改造现有测试架构。
