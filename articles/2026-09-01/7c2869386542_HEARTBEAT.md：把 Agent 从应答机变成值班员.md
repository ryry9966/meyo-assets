## 背景：被动应答的天花板

大部分 Agent 的默认形态是"你问我答"：你不开口，它不动。但运维里真正烦人的事往往相反——PR 有没有新 review、备份目录昨晚有没有落盘、日历今天有没有冲突。这些事的共同点是**时机不确定，需要周期性看一眼再判断**，靠人肉轮询总会漏。

OpenClaw 给了一个朴素但有效的机制：heartbeat（心跳）。每隔一段时间（默认 30 分钟），主会话被注入一次心跳触发，Agent 醒来读 workspace 根目录的 `HEARTBEAT.md`，按清单决定干不干活。文件缺失或为空，心跳直接跳过，近乎零成本；有内容则执行检查，无事可做时只回一个约定 token（`HEARTBEAT_OK`），不产生对外消息。

## 问题：cron 能定时，但不能判断

cron 适合"每天 8:30 报数"这种固定时刻任务。可一旦条件变成"有未推送提交**且**距上次提醒超过 4 小时"，shell 就开始难写。heartbeat 的分工在这里：**"什么时候看"交给定时器，"看完怎么办"交给模型**，且心跳里照常可以调 MCP 工具（git、fetch、calendar 等）。

## 做法：五步跑起来

1. **建文件**：`~/.openclaw/workspace/HEARTBEAT.md`，改完即生效（每个心跳重新读取），不用重启。
2. **写检查项**，每条讲清条件、动作、静默规则：

```markdown
# Heartbeat 检查清单
- 每次心跳检查 ~/projects/api 的 git status；
  若有未推送提交且距上次提醒超过 4 小时，提醒我一次，
  并把时间写进 .heartbeat-state.json
- 早上 9 点后的第一次心跳：汇总昨日未读 GitHub 通知，一条消息发我
- 其余情况一律只回 HEARTBEAT_OK
```

3. **调间隔**：`agents.defaults.heartbeat.every`，可按 agent 覆盖（键名以你所用版本文档为准）。轻量检查可 15 分钟，重活别低于 1 小时。
4. **控成本**：每条任务都写明"无事时只回 HEARTBEAT_OK"，并配一个状态小文件记录"上次提醒时间"，防止重复打扰。
5. **分工**：精确时刻的任务给 cron，heartbeat 只做"周期巡检 + 自主判断"。

## 踩坑点

- **清单写成愿望清单**：十几个检查项堆一个文件里，每次心跳都是一次完整模型调用，token 成本随清单长度线性上涨。控制在 30 行以内，重状态放外部文件。
- **Agent 过度热情**：没有静默规则时，它可能每半小时"汇报"一次。每条任务必须回答"什么情况下闭嘴"。
- **主会话污染**：心跳跑在主会话里，输出会进历史。心跳输出尽量短，长结果写文件、消息里给路径。
- **间隔小于任务耗时**：一次还没跑完下一次又触发。间隔要明显大于单次任务的最坏耗时。
- **把它当事件监听**：heartbeat 不是 fsnotify，感知不了"文件刚变了"，只能"醒来时看一眼"。实时监控用别的手段。

## 可复用建议

- **四段式模板**：上下文（看哪里）、条件（什么算有事）、动作（做什么）、静默（何时闭嘴）。
- **状态外置**：HEARTBEAT.md 只放指令不放数据，"上次提醒时间"这类易变信息进 JSON 状态文件。
- **先跑一件**：单个任务观察一周实际触发频率和成本，再决定加第二个。

## 总结

HEARTBEAT.md 的本质是把值班表贴在 Agent 面前：定时醒来、按表巡检、没事归位。两个闸门决定体验——`HEARTBEAT_OK` 控成本，间隔与静默规则控打扰。从一件真正值得盯的事开始，比一次塞满清单有效得多。
