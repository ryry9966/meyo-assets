## 背景

做 Agent 和 MCP 插件开发一段时间后，我发现两类需求特别适合本地模型：一是涉及私人数据的自动化（本地文件整理、日记摘要、聊天记录归档），数据不出门更安心；二是高频、低强度的后台任务（定时打标、分类、摘要），走 API 账单不小还有限速。本地模型不是替代云端，而是补一个"常驻、免费、可控"的档位。

## 问题

动手前先泼两盆冷水，这是我和几个社区朋友反复验证过的：

1. **"我的机器能跑 70B" 和 "70B 能干 agent 的活"是两回事。** 推理跑通只是及格线，agent 场景真正考验工具调用稳定性、长上下文和吞吐。
2. **MCP 工具一多，上下文先爆。** 十几个工具的 schema 加 system prompt 轻松吃掉几千 token，8k 上下文的模型基本做不了正经 agent 任务。

## 做法

我的环境：32GB 内存 + RTX 4060Ti 16G（朋友的 4090 和纯 CPU 机器也跑通了，结论通用）。步骤如下：

**1. 选运行时。** 图省事选 Ollama，一条命令起服务，自带 OpenAI 兼容接口；要精细控制 prompt 模板和量化格式用 llama.cpp；Linux + N 卡且需要并发吞吐可上 vLLM。建议从 Ollama 起步，跑通再迁移。

**2. 选模型和量化。** 实用区间是 7B–14B，Q4_K_M 起步。Qwen 系列对中文和 function calling 支持都不错，14B Q4 约 9GB 显存，16G 卡能留出 KV cache 余量。别一上来追 32B/70B，先保证链路通。

**3. 拉长上下文。** agent 任务建议直接设 16k–32k。注意 KV cache 额外吃显存，14B 模型开 32k 上下文大约再多 2–4GB，量入为出。

**4. 接入 OpenClaw。** base_url 指到本地端口，模型名按运行时的注册名填。建议做成配置项而不是写死，随时能切回云端。

**5. 用真实链路验收。** 跑三个典型 case：单工具调用、多轮工具链、一个必失败的调用（验证模型能否读错误信息并自我纠正）。三关过了才算部署完成。

## 踩坑点

- **工具调用格式不匹配是最常见的坑。** 同一个模型，有的框架调得好好的，换一套 chat template 就开始瞎编参数或死循环。出问题先核对运行时的对话模板与框架要求的格式是否一致。
- **量化太狠会破坏 JSON 输出。** Q2/Q3 的模型输出结构化数据容易漏字段、掺杂质。做 agent 至少 Q4，关键场景 Q5/Q6。
- **温度别照抄云端习惯。** 本地小模型 0.6–0.7 配合合理的 repeat penalty 比较稳，拉到 1.0 容易胡言。
- **常驻服务占显存。** 模型加载后显存不释放，打游戏、剪视频前记得先卸载。
- **吞吐预期要现实。** 4060Ti 上 14B Q4 约 20–30 token/s，agent 一步思考 15–30 秒很正常。高频循环建议"本地做规划摘要、云端做关键决策"的混合架构。

## 可复用建议

- 固定一套 3–5 个 case 的评测脚本，换模型或量化后跑一遍，十分钟出结论，别凭感觉换。
- 记录显存基线：模型规格、上下文长度、实测 token/s、峰值显存，下次选型直接查表。
- 把"本地/云端"做成 agent 配置里的一个开关：敏感数据走本地，重任务走云端。

## 总结

本地部署的门槛已经从"折腾 CUDA"降到"会改配置文件"，难点转移到了**模型能力与 agent 需求的匹配**上。我的建议：用 14B 级别模型跑通全链路，把它当作开发调试和隐私场景的常备档位，而不是硬刚云端旗舰。跑通之后你会发现，本地模型最大的价值不是省钱，而是让 agent 自动化可以毫无心理负担地 7×24 跑着。
