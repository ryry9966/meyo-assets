## 背景

在 OpenClaw / Agent / MCP / 插件这类自动化实践场景里，我们经常把 AI 助手接入日常开发流程，让它处理一些重复性高、规则明确但人工做起来繁琐的事情。Git 提交信息、分支命名、PR 描述就是很典型的例子：手动写 commit message 容易风格不一，分支名常常随手起成 `fix-bug`、`test`，PR 描述在赶进度时经常空白。这些问题不致命，但会持续消耗团队的代码审查效率和回溯成本。

与其要求每个开发者都严格遵循规范，不如让 AI 助手在关键节点自动介入，把「生成规范文本」这件事从人的脑子里外包出去。本文分享一套可落地的 Git 自动化方案，重点不是「AI 帮你写代码」，而是「AI 帮你维护 Git 元信息」。

## 问题拆解

我们真正想让 AI 助手做的有三件事：

1. **自动生成 commit message**：根据暂存区的 diff 内容，产出符合团队约定（如 Conventional Commits）的提交信息。
2. **自动创建规范分支**：根据一句需求描述，生成 slug 化的分支名，如 `feat/payment-refund-flow`。
3. **自动补全 PR 描述**：在推送分支或创建 PR 时，汇总变更内容生成描述，减少手动填写。

这三件事的共同点是：输入明确、输出有模板、失败影响可控。适合做成自动化，而不是让开发者在终端里手动调用 AI。

## 做法 / 步骤

### 1. 基础准备：一个可调用的 AI 接口

在 OpenClaw 环境中，你可以直接复用现有的模型服务，也可以用一个极简的脚本封装 OpenAI 兼容接口。假设我们有一个 `ai_git` 命令，接收提示词和标准输入，输出文本。

```bash
# 伪代码，实际按你的模型服务调整
ai_git "根据以下 diff 生成一条 Conventional Commit" < /tmp/git.diff
```

也可以把这部分封装成 MCP server，通过 OpenClaw 的 Agent 能力调用。但为了降低复杂度，一开始用 shell 脚本加 API 调用就足够。

### 2. 自动生成 commit message：prepare-commit-msg hook

在仓库的 `.git/hooks/prepare-commit-msg` 中加入逻辑：当用户执行 `git commit` 且没有手动提供 `-m` 参数时，自动调用 AI 生成提交信息。

关键点是**只在非交互模式下生效**，避免打断用户手动输入。脚本流程：

- 读取 `.git/COMMIT_EDITMSG` 判断是否为空模板。
- 如果非空（用户已写），直接退出。
- 获取 `git diff --cached --stat` 和 `git diff --cached`。
- 把 diff 传给 AI，要求输出一行 commit message。
- 将结果写入 `.git/COMMIT_EDITMSG`。

注意限制 diff 大小：如果变更超过 8KB，只传文件名和统计信息，避免模型上下文过长或请求超时。

### 3. 自动创建规范分支：git alias + 脚本

在全局 `.gitconfig` 中添加别名：

```ini
[alias]
    ab = "!f() { git checkout -b $(ai_git \"将以下需求转换为 kebab-case 分支名，带 feat/fix/refactor 前缀: $1\"); }; f"
```

使用方式：

```bash
git ab "增加支付退款流程"
```

AI 会返回 `feat/payment-refund-flow`，脚本将其传给 `git checkout -b`。这里要加一层校验：确保输出只包含小写字母、数字、`/`、`-`，否则 fallback 到用户手动输入。

### 4. PR 描述生成：GitHub Action 或本地命令

如果团队使用 GitHub，可以在 `.github/workflows/pr-description.yml` 中加一步，在 PR 创建或更新时调用 AI，用 PR 的 diff 生成描述。也可以用本地命令手动触发：

```bash
gh pr create --title "..." --body "$(ai_git '根据分支和 diff 生成 PR 描述')"
```

这一步不必强制自动化，提供命令即可，避免 Action 中引入外部调用导致 CI 不稳定。

## 踩坑点

1. **hook 中调用 AI 增加延迟**：`git commit` 会等待 AI 返回，网络慢时体验很差。务必设置超时（如 5 秒），超时则跳过 AI，保留空模板让用户手动填写。
2. **大 diff 导致上下文溢出**：不要无脑传完整 diff。先限制 `--stat`，超过阈值只传文件列表和关键变更摘要。
3. **AI 输出不稳定**：模型可能返回多行、带解释、甚至 markdown 格式。必须用脚本做后处理：提取第一行、去除前缀标记、验证是否符合约定格式。
4. **分支名非法字符**：AI 可能返回空格、大写、中文字符。必须在执行 checkout 前用正则过滤，不合法则回退。
5. **敏感代码泄漏**：如果你使用外部 API，diff 中的代码会被发送到第三方。内部项目建议使用本地模型或私有部署的接口。
6. **hook 脚本阻塞提交**：如果脚本出错或 AI 不可用，`git commit` 会失败。所有 AI 调用都要包在 `if` 条件中，失败时静默跳过。
7. **Windows 兼容性**：`.git/hooks` 在 Windows 上可能是 CRLF 或不同 shell。如果团队有 Windows 用户，用 Python 脚本代替纯 bash。

## 可复用建议

- **把 AI 调用封装成独立命令**：不要在每个 hook 里直接写 curl。统一入口方便替换模型、切换 API、记录日志。
- **提供 dry-run 模式**：`AI_GIT_DRY_RUN=1` 时只打印即将执行的命令，不实际修改仓库。
- **缓存结果**：对相同 diff 的 commit message 生成结果可以缓存几分钟，避免重复请求。
- **可降级**：AI 不可用时，退回空提交信息或默认分支名，不影响开发流程。
- **用 MCP 暴露 Git 操作**：在 OpenClaw 中，可以把 `git status`、`git diff`、`git commit` 等封装成 MCP tools，让 Agent 在对话中直接完成「查看变更 → 生成提交 → 创建分支」的完整链路。但生产环境仍建议保留脚本作为底层实现，MCP 只做编排。
- **记录 AI 生成内容**：在 commit message 末尾或 PR 描述中加一个标记（例如 `Generated with AI, review manually`），方便回溯。

## 总结

Git 自动化是 AI 助手落地开发流程的一个低风险切入点。它不改变代码本身，只优化元信息，失败影响可控，收益却很明显：提交历史更清晰、分支命名更规范、PR 评审更高效。

但工程化最关键的一点是：**AI 只能建议，不能替人做最终决策**。所有自动生成的内容都要允许人工覆盖，所有对外部 API 的调用都要有降级策略。把 AI 放进 Git hook 里，不是为了让提交更快，而是为了让规范执行更省心。

在 OpenClaw-CN 社区，很多成员已经在用 MCP、Agent、插件做类似的事情。希望这套思路能帮你把「AI 管理 Git」从想法变成可复用的脚本，而不是又一篇营销文。
