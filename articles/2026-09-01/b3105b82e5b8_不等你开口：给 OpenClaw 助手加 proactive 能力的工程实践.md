## 背景

大多数 agent 交互是「你问它答」：用户发消息，助手响应，会话结束。这套模式跑通很容易，但用久了会发现一个尴尬的事实——很多事其实不需要你记得去问。CI 挂了、磁盘快满了、某个 issue 三天没人回，这些信号一直存在，只是没人把它们推到你面前。

Proactive 能力指的就是这个：助手在没有用户输入的情况下，自己感知、判断、行动（或至少提醒）。OpenClaw 天然适合做这件事：常驻运行、有 cron 调度、有 MCP 工具层，还有自己的消息通道。

## 问题

但 proactive 是个「演示五分钟，落地两周」的功能，核心难点有三个：

1. **噪音**。助手动不动就发消息，一周后你把它静音了，proactive 价值直接归零。
2. **上下文**。主动触发的运行没有会话历史，agent 不知道之前说过什么，容易重复报告。
3. **权限**。没人盯着的时候 agent 自作主张改了配置，你连发生的时机都不知道。

## 做法

我的做法是把 proactive 拆成一条「感知 → 门控 → 行动」的流水线，三个环节分开治理。

**第一步：分类触发源。** 实际用下来就三类：

- 时间触发：cron 定时任务，比如每天早上拉一次 GitHub 通知做摘要；
- 事件触发：webhook / 文件监听，比如 repo 有新 push、服务器告警回调；
- 状态触发：心跳自检，agent 周期性扫一轮状态，判断「有没有值得说的」。

**第二步：加门控（关键）。** 不是所有信号都值得打断用户。我在触发 prompt 里强制加一层判断：先评估「这条信息是否需要人现在知道」，输出三档——立即通知、并入每日摘要、丢弃。门控用便宜的小模型跑，只有决定行动时才升级到大模型，成本能压一个数量级。

**第三步：分级行动权限。** 读操作（查状态、拉数据）自动执行；写操作先产出草稿等你确认；高危操作（改配置、发外部消息）一律白名单。主动场景下默认值应该是「只说不做」。

## 踩坑点

- **心跳频率贪高**。一开始设 5 分钟一次，token 烧得心疼，大部分轮次还输出「无事发生」。改成 30 分钟 + 事件触发兜底，覆盖率没掉。
- **重复触发**。cron 和 webhook 同时命中一个事件，发了两条一样的消息。解法很土：状态文件记录最近处理过的事件 ID，触发前查重，保证幂等。
- **主动运行丢上下文**。第一次跑每日摘要，把昨天报过的问题又报了一遍。解法是把「已报告事项」写进持久化记忆文件，每次主动运行时注入。
- **时区**。cron 用了 UTC，摘要每天下午才到。低级但真实。

## 可复用建议

- 从一个高频、低危、你真的会看的场景起步（比如 repo issue 摘要），跑两周再扩。
- 观察和行动分成两条链路，出问题时能单独关掉行动侧。
- 所有主动行为落一条 append-only 日志：什么触发、做了什么判断、发了什么，事后审计全靠它。
- 量化静音率：主动消息连续一周没被回复或点击，就降频。价值以「你会不会看」为准，不以「它多勤快」为准。
- 默认沉默，宁可少说，不可说错。

## 总结

Proactive 不是让 agent 更「智能」，而是让它更「守规矩地主动」：感知交给触发器，判断交给门控，行动交给分级权限，审计交给日志。OpenClaw 的常驻 + 调度 + 工具层结构刚好能承载这条流水线。先让它在一件小事上可靠地先开口，比一次性堆十个自动化有用得多。
