## 背景

在 OpenClaw、MCP、插件和自动化工作流里，Agent 经常要执行的不只是“查一下”，而是“改一下”——删文件、发请求、写数据库、调外部 API。权限一旦放开，Agent 就可能把测试环境的清理命令跑进生产库；权限收得太紧，每一步都弹确认，自动化又失去意义。

真正要解决的问题不是“要不要限制”，而是：**哪些操作可以默认执行，哪些必须暂停等人类确认，哪些应该直接禁止。**

## 问题

很多 Agent 项目的权限设计只有两档：全自动或全手动。结果是要么用户对弹窗麻木，习惯性点“允许”；要么开发者为了省事，给 Agent 一个超级 token，什么都干。权限边界不能靠感觉，需要一套可工程化、可审计、可回滚的策略。

## 做法 / 步骤

### 1. 先给工具做风险分级

不要按工具名称一刀切，要按“动作 + 对象 + 影响面”分：

| 级别 | 典型操作 | 默认策略 |
|------|----------|----------|
| 只读 | 查询日志、读文件、GET 请求 | 自动执行，记录摘要 |
| 可逆写 | 创建临时文件、打 tag、发可撤回消息 | 自动执行，保留回滚信息 |
| 不可逆写 | 删除、覆盖、发送外部通知、转账 | 必须人类确认 |
| 高危 | 批量删除、修改权限、执行任意 shell | 默认禁止，或双人确认 |

注意：同样是删除，`rm ./tmp/cache.txt` 和 `rm -rf /data/*` 不在一个级别。权限策略要能识别参数，而不是只看工具名。

### 2. 把策略做成中间件，而不是散落在代码里

在 OpenClaw/Agent 的工具调用链里，建议加一层 permission middleware。例如：

```json
{
  "tool": "file.delete",
  "rules": [
    {
      "path_pattern": "^/tmp/agent/.*",
      "max_size_kb": 512,
      "action": "allow",
      "reason": "temp files only"
    },
    {
      "path_pattern": "^/data/.*",
      "action": "ask",
      "require_context": true
    },
    {
      "path_pattern": ".*",
      "action": "deny"
    }
  ]
}
```

这层中间件可以在 MCP client 侧、插件加载器里，或者 Agent 的执行器前置完成。关键是：**策略独立于模型**，模型不能自己绕过。

### 3. 人类确认时，必须带上“上下文 + 差异”

不要只问“是否允许执行 file.delete？”。要给出：

- 将要执行的完整命令和参数
- 影响范围：会删除哪些文件、覆盖哪些数据
- 可回滚性：有没有备份、能不能撤销
- 发起原因：Agent 为什么认为需要这一步

例如：

> Agent 请求删除 `/data/uploads/tmp_20240601.tar.gz`  
> 大小：214 MB  
> 该文件已备份到 `/backup/uploads/`  
> 原因：释放磁盘空间，任务 #281 需要 1.2 GB 可用空间

只有带着这些信息，“询问”才不是形式主义。

### 4. 环境感知 + 干跑模式

同一个工具，在 dev 环境可以自动执行，在 prod 环境必须确认。建议在权限策略里加入 `env` 维度。对于批量操作，先让 Agent 生成“执行计划”，以 dry-run 模式输出会做什么，人类确认后再真正执行。

## 踩坑点

- **把“询问”当万能选项**：频繁确认会让用户疲劳，最终变成条件反射点“允许”。只对真正不可逆或高影响的操作询问。
- **只按工具名拦截**：`shell.exec` 可以是 `ls`，也可以是 `curl | sh`。必须解析参数、命令和对象。
- **忽略 MCP server 自身的权限**：用户给插件开了“写文件”权限，但底层 MCP server 可能还拥有更高权限。要分层检查，不能只信任外层。
- **没有回滚设计**：很多事故不是权限判断错误，而是没有备份。写操作前能留快照就留快照，能幂等就幂等。
- **策略只写在文档里**：文档会过时，代码和配置不会。把权限矩阵落成可测试的策略文件。

## 可复用建议

1. 维护一张权限矩阵表：工具、动作、对象、环境、默认策略、回滚方式。
2. 用策略即代码的方式管理权限，纳入版本控制和 code review。
3. 新工具接入时，默认 `deny` 或 `ask`，跑通只读场景后再逐步放开。
4. 每次确认都记录 decision log：谁、什么时间、因为什么允许/拒绝了哪个操作。
5. 定期复盘“误拦截”和“误放行”，调整风险分级，而不是固定不变。

## 总结

Agent 的权限边界不是一道静态的墙，而是一套持续调整的策略。工程上能做的是：**把风险分级、把策略外置、把确认做扎实、把回滚准备好。** 剩下的，才是把决定权交给模型还是人类。

对于 OpenClaw 这类工具链，最实用的起点是：先让 Agent 只读，再给一个可逆写的小白名单，最后针对不可逆操作设计真正有效的人机确认。别一上来就追求“全自动”，也别用弹窗假装“可控”。
