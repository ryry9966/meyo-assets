## 背景

Agent 接上 MCP 工具之后，能力边界从"聊天"变成了"动手"：读仓库、写文件、调接口、发消息。但多数团队对"哪些动作自动执行、哪些必须等人点头"没有明确规则，全靠写 prompt 时的直觉，比如加一句"危险操作请先确认"。问题是，模型对"危险"的理解和你不一样。

## 问题

实际跑起来只有两种失败模式：

1. **事事请示**。每个写操作都弹确认，人变成流水线上的人肉按钮，自动化价值归零，最后大家干脆把确认关掉。
2. **从不请示**。某天 agent 把测试环境的批量删除脚本跑在了生产库上，或者把半成品公告发进了客户群。一次事故抹掉三个月的信任。

核心认知：**判断标准不在模型里，在工具和数据的风险属性里**。指望模型"自觉"不可靠，边界必须做在工具层。

## 做法：按工具分级，而不是按任务分级

给接入的每个 MCP 工具/插件按两个维度打标：**爆炸半径**（影响一条数据还是整个系统）和**可逆性**（能不能回滚），落到四档：

| 档位 | 典型动作 | 策略 |
|---|---|---|
| L0 只读 | get / list / search | 直接放行 |
| L1 可逆写 | 写工作目录文件、本地 commit、建草稿 | 放行 + 审计日志 |
| L2 不可逆/外发 | 发消息、发邮件、部署、改线上配置 | 必须确认 |
| L3 高危 | 删数据、支付、权限变更、批量操作 | 确认 + 白名单 |

三个配套动作：

1. **确认必须带上下文**。不是问"我可以执行吗"，而是给出 diff、目标地址、影响范围、回滚方式。人三秒能看懂，才会真的看。
2. **能用 dry-run 就先 dry-run**。部署类工具支持 plan/preview 的，把 L2 降级成"预览 + 一键执行"，确认成本大幅下降。
3. **自动执行的动作全部留痕**。哪个会话、什么时候、调了什么、参数是什么。没有日志，事后复盘和收紧边界都无从谈起。

## 踩坑点

- **粒度错误**：让用户批准整个 plan，agent 中途换了工具或改了参数，批准就失效了。确认要落在"动作级"，不是"任务级"。
- **确认疲劳**：弹窗一多，用户开始无脑点 yes，确认机制形同虚设。宁可收紧 L2 的定义，也别让确认变成噪音。
- **权限蔓延**：图省事把某个工具从 L2 挪到 L1，没人记录、没人评审，出事时是静默的。改档位要走和改代码一样的 review 流程。
- **读写混合的工具**：一个 MCP 工具既能查又能改，分级直接失效。拆成两个工具，或至少拆成两个参数域。
- **环境混淆**：同一个"执行 SQL"的工具指向测试和生产，风险完全不同。环境要显式传入并体现在确认信息里。

## 可复用建议

- 拿不准时问三句：**可逆吗？影响面多大？错了损失多少时间或钱？** 三个答案里有两个不妙，就归入需确认档位。
- 默认策略：**只读默认放行，外发默认拦截**。白名单思维，不要黑名单思维。
- 确认信息四件套：动作 + 对象 + 影响范围 + 回滚方式，缺一个就别弹。
- 每月复盘一次审计日志：从未被拒绝的确认项可以降档，被拒绝过的要收紧。边界是活的，不是一次配完就不管的。

## 总结

权限边界不是一句 prompt 能解决的事，它是工具设计 + 分级策略 + 确认交互 + 审计闭环的组合工程。这四件事落地之后，你才敢真的放手让 agent 跑长任务——因为它知道在哪该停，你也知道它停下来的原因。
