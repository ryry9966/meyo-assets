## 背景

Agent 跑久了会攒下一堆记忆条目：用户偏好、项目上下文、踩过的坑。`memory_recall` 的职责是在对话时把这些东西捞回来塞进上下文。捞得好不好，直接决定助手是"记得你"还是"一本正经地编"。常见两条路线：全文搜索（关键词/BM25）和语义搜索（embedding + 向量相似度）。社区里经常吵"哪个更好"，我最近在自己的 OpenClaw 记忆层上把两种都实现了，分享一下实测结论。

## 问题

两条路线各有一个典型翻车场景：

- 全文搜索：语义改写就哑火。之前记过"偏好深色主题"，用户后来问"夜间模式怎么设置"，关键词对不上，检索不到。
- 语义搜索：太"聪明"反而容易召回似是而非的内容。查"上次的部署脚本"，top1 可能是一条主题相近但完全无关的笔记，还带着挺高的相似度分数。

另外两个现实约束：中文分词，以及 embedding 的成本/延迟（走 API 每次 recall 都要算一次 query 向量）。

## 做法

1. **同一份记忆库，两套索引。** 约 600 条记忆条目，每条一个原子事实，带时间戳和来源。全文侧用 SQLite FTS5（中文 tokenizer 有坑，见下文）；语义侧用本地 `bge-small-zh` 生成向量，余弦相似度取 top-5。
2. **自建小型评测集。** 手写 30 条查询（一半是改写、一半含精确标识符如文件名、报错码），人工判定 top-5 是否命中，做粗糙的命中率统计。
3. **结果（仅供参考，非严谨 benchmark）：**
   - 精确标识符类查询：全文搜索明显占优；语义搜索经常召回主题相近的"邻居"。
   - 改写/跨表达类查询：语义搜索占优，全文几乎全军覆没。
   - 两者都翻车：否定句和时间敏感事实（"不要再用 npm"会被"用 npm"的高分条目污染）。
4. **上混合检索。** 两路各取 top-8，用 RRF（倒数排名融合）合并取 top-5；语义分数低于阈值时自动退回 FTS 兜底。改动量不大，收益明显。

## 踩坑点

- **FTS5 默认 tokenizer 对中文基本不可用**，英文按空格切，中文会整段成一个 token。用 jieba 预分词后入索引，或直接换 trigram tokenizer。
- **记忆条目别写成大段总结**。一条一大段，两种检索的粒度都会被拉垮，段落中间的事实根本捞不出来。原子化 + 时间戳是性价比最高的重构。
- **相似度阈值别硬编码**。不同 embedding 模型的分数分布差很远，0.8 对 A 模型是高置信、对 B 模型是垃圾。拿自己的数据看一遍分布再定。
- **召回条数要克制**。top-5 之外的东西塞进上下文，边际收益趋零，token 开销和干扰都在涨。宁缺毋滥。
- **别迷信语义 top-1**。加一层便宜的加权（近期度、条目重要性）比上 reranker 划算。

## 可复用建议

- **默认做混合，别二选一**。RRF 融合十几行代码，能同时吃到两边的长处。
- **FTS 永远值得留作 baseline**：零外部依赖、零延迟、对精确词是杀手锏。
- **记忆条目设计 > 检索算法**。原子化、带元数据、定期清理过期条目，比换 embedding 模型的提升更稳定。
- **把 recall 命中情况记日志**。攒几十条真实查询的评测集，比看任何别人的榜单都有说服力。

## 总结

语义搜索和全文搜索不是替代关系，是互补关系：前者管"换个说法也找得到"，后者管"精确的东西一击命中"。对个人 Agent 这种混合型记忆库，RRF 混合 + FTS 兜底是目前我用下来最省心、最可解释的方案。先跑通 FTS 基线，再加语义一路对比着看，比一上来就 all-in 向量库踏实得多。
