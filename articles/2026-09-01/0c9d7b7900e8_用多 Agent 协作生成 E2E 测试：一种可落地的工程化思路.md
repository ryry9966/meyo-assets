## 背景

E2E 测试维护成本高，尤其在前端频繁迭代时，选择器失效、业务流程变化会让用例快速腐化。传统录制回放或手写 Playwright/Cypress 脚本，往往在需求更新后需要大量返工。AI 能生成代码，但直接让单个模型输出完整测试用例，容易出现选择器猜测、断言缺失、无法执行验证的问题。一个更务实的做法是引入 Agent 协作：不同 Agent 分别负责理解页面、生成步骤、执行校验、修复回归。

## 问题

单 Agent 写 E2E 测试的典型失败模式：

- 直接看代码生成测试，但前端渲染后 DOM 结构可能不同（虚拟 DOM、动态 class 等）。
- 生成脆弱的选择器，例如随机 class 或深层 XPath。
- 只生成 happy path，忽略边界场景和失败断言。
- 生成后不执行，无法发现运行时错误。
- 维护时无法定位哪些用例受页面变更影响。

这些问题不是单纯“提示词优化”能解决，而是需要引入真实浏览器上下文和可执行的反馈闭环。

## 做法/步骤

以 OpenClaw 编排 Playwright MCP 为例，可以拆成四个 Agent：

1. **侦察 Agent**：用 Playwright MCP 打开目标页面，抓取真实 DOM、可访问性树、路由与关键交互元素，输出结构化页面模型。
2. **用例设计 Agent**：基于页面模型和产品需求文本，生成测试场景列表（用户路径、预期结果、关键断言），不直接写代码。
3. **编码 Agent**：把场景列表转成 Playwright 测试代码，强制使用 `data-testid`、`role`、`label` 等稳定选择器；若元素缺失，标记 TODO 并报告。
4. **执行与修复 Agent**：运行测试，收集失败信息（截图、console、网络错误），将失败上下文返回给编码 Agent 做小步修复，循环直到通过或达到上限。

关键步骤：

- 先让侦察 Agent 输出 JSON 结构，包含每步可交互元素及推荐选择器。
- 设计 Agent 输出 Given/When/Then 或简化的操作序列。
- 编码 Agent 只复用侦察结果中的选择器，避免自行猜 DOM。
- 执行 Agent 必须真实启动浏览器，不能只做静态检查。
- 将 MCP 工具结果（DOM 片段、错误堆栈）作为上下文回传，形成闭环。

## 踩坑点

- **选择器漂移**：AI 倾向于使用看到的临时 class。约束它优先 `data-testid`、`role`、`aria-label`，否则拒绝生成。如果页面缺少这些属性，侦察 Agent 应提示开发补充或使用更稳定的层级。
- **幻觉操作**：模型会生成不存在的按钮或步骤。执行 Agent 必须验证每个操作是否可执行，失败即停止并反馈。
- **循环修复发散**：修复 Agent 可能反复修改但不收敛。设置最大迭代次数（如 3-5 次），且每轮只允许改动失败用例的局部，不允许重写整个文件。
- **上下文过长**：抓取整个 DOM 会爆 token。裁剪时保留可交互元素、语义角色、表单控件，过滤无关容器和脚本。
- **动态内容**：加载延迟或动画导致元素尚未出现。侦察 Agent 应显式等待网络空闲或关键元素可见后再抓取；执行 Agent 使用 `expect` 轮询而非固定 `sleep`。
- **忽略断言**：生成代码可能只点击不验证。在用例设计阶段强制要求每个场景至少两个断言：状态变化、数据或 UI 反馈。

## 可复用建议

- 把 Agent 协作流程做成 OpenClaw 插件或 MCP 工作流，输入为「页面 URL + 需求描述」，输出为可运行测试文件与执行报告。
- 侦察 Agent 输出的页面模型可以缓存，页面未变更时复用，避免重复抓取。
- 建立选择器约定：项目全局使用 `data-testid`，开发与 AI 共同遵守，这是自动化稳定的基础。
- 用 Git 管理生成结果。每次生成前先 pull 最新代码；执行失败后由修复 Agent 生成 patch，而不是直接修改工作区，便于 review。
- 在 CI 中运行：把「生成/修复」作为测试失败后的辅助步骤，但人工确认改动后再合入，防止 AI 生成脆弱用例进入主干。

## 总结

多 Agent 协作写 E2E 测试，核心不是“让 AI 一把梭”，而是把「理解页面、设计场景、写代码、执行验证」拆开，让每个 Agent 只做自己擅长的事，并用 MCP 工具提供真实浏览器上下文。这样做可以降低选择器脆弱性，形成可执行、可回归的测试生成闭环。工程化的关键仍然是约束与反馈循环，而不是模型能力本身。
