## 背景

在 OpenClaw、Agent、MCP 或插件自动化场景里，同一个任务常常会被多次触发：

- Webhook 因上游超时重试，同一条事件被投递了两次；
- 定时任务和手动触发同时启动；
- Agent 工具调用过程中，用户点击了多次；
- MCP 服务端或客户端因为网络抖动自动重发请求。

如果没有幂等设计，这些重复触发就会产生额外副作用：重复建工单、重复发消息、重复写数据、重复调用外部 API。你很难靠“尽量别重复触发”来规避，因为重试、并发、超时这些是分布式系统的常态。

## 问题

典型的翻车场景是：一个自动化插件订阅了工单系统的 Webhook，收到“用户已支付”事件后，自动在内部系统创建开通记录。某天上游 Webhook 超时，30 秒后重投了一次同一条事件。插件没有做去重，结果给同一个用户开通了两遍，生成了两条生效中的开通记录。

另一个常见问题是：定时任务每天凌晨运行，把当天数据汇总后推送报告。某次任务跑到一半被运维手动重跑了一次，结果报告发了两份，数据也被统计了两遍。

根因不是“任务逻辑写错了”，而是任务缺少一个稳定的幂等边界：**什么算同一次业务操作**。

## 做法 / 步骤

### 1. 为每次任务确定业务唯一键

不要直接用随机 UUID 作为幂等键，因为重试时 UUID 会变。优先从业务负载中提取或派生：

- Webhook 事件：优先用上游提供的事件 ID，如 `payment.succeeded` 的 event id；
- 定时任务：用业务时间窗口，如 `report:2026-04-20`，而不是当前执行时间；
- Agent 工具调用：由调用方传入稳定的业务标识，如 `user_id + action + resource_id`；
- 如果上游没有 ID，可以基于关键字段做确定性哈希，例如 `sha256(action + user_id + resource_id + 业务日期)`。

### 2. 用原子操作做“先占位再执行”

幂等的核心不是“检查一下有没有执行过”，而是“检查 + 占位”必须原子。否则两个并发请求同时检查都发现没执行过，然后都继续执行。

推荐做法：

- 数据库：建唯一约束，`INSERT ... ON CONFLICT DO NOTHING` 或 `INSERT IGNORE`，用幂等键当唯一键。拿到插入成功的一方继续执行，失败的一方直接返回“已处理”。
- Redis：`SET idempotency_key value NX EX 3600`。`NX` 保证只有一个请求能设置成功。
- 如果使用关系型数据库但不想建表，也可以用 `SELECT ... FOR UPDATE` 配合事务，但并发量高时不如唯一约束可靠。

### 3. 状态机代替布尔标记

不要只用一个 `done` 布尔字段。建议至少区分：

- `pending`：已占位，尚未执行；
- `processing`：正在执行；
- `done`：执行成功；
- `failed`：执行失败，可重试。

这样即使任务执行到一半崩溃，也不会被误判为“已处理”。下次重试时可以根据状态决定是继续、重做还是人工介入。

### 4. 外部副作用用 Outbox 或事务消息

如果任务要发通知、调第三方 API、推送 MCP 响应，这些外部副作用通常无法回滚。直接执行容易造成“本地标记成功但外部没成功”或“外部成功但本地没更新”。

更稳的做法：

1. 先写本地 outbox 表或事件表，记录待发送的消息；
2. 后台投递进程读取 outbox 并发送；
3. 发送成功后更新 outbox 状态为已发送；
4. 任务幂等键只关联业务状态，不直接关联外部投递成功。

这样即使投递重试，也能通过 outbox 的唯一约束避免重复发送。

## 踩坑点

1. **用随机 UUID 当幂等键**：重试或重放时 ID 不同，幂等直接失效。
2. **只检查不锁定**：并发场景下两个请求都读到“未处理”，然后都执行。
3. **唯一约束范围过大或过小**：过大会误拦截不同业务，比如只用 `user_id` 当唯一键，用户第二次合法操作被丢弃；过小会漏重复，比如键里包含当前时间戳。
4. **占位过期时间太短**：任务还在执行，Redis key 过期了，重试请求再次进入。过期时间要明显大于任务最大执行时长。
5. **把“幂等”当成“只执行一次”**：实际上幂等是“重复执行不产生额外副作用”。如果任务本身有副作用，需要把副作用做成可重复或可确认。
6. **不测试重复场景**：只在正常路径下测试，没模拟重试、并发、超时重投，上线后才发现重复。

## 可复用建议

- 对入站 Webhook、定时任务、Agent 工具调用，默认要求提供稳定幂等键；没有就基于业务字段派生。
- 在数据库层加唯一约束兜底，不要只依赖应用层 `if` 检查。
- 使用状态机管理任务生命周期，避免布尔字段。
- 外部副作用统一走 Outbox / 事件表，先写本地再异步投递。
- 记录 `idempotency_key`、`created_at`、`status`，方便事后排查重复来源。
- 发布前至少用三个用例验证：重复投递、并发触发、超时重试。

## 总结

自动化任务的幂等性不是“加个锁”或“加个唯一键”就完事，它要求你先想清楚业务上什么操作算同一次，然后把唯一键、原子占位、状态机、Outbox 这几个手段组合起来。重复执行不会出问题的关键，不是阻止重复，而是让重复变得无害。

在 OpenClaw / Agent / MCP 这类插件和工具链路里，幂等性应该作为默认设计，而不是出了问题再补。越早把键和状态模型定清楚，后面排查重复问题的成本越低。
