## 背景

Agent 默认是无状态的。每次会话结束，上下文清零——你上周告诉过它"提交信息不要带 emoji"、"时区是 UTC+8"、"用 pnpm 不用 npm"，这周它照样犯。在 OpenClaw 这类常驻个人助手的场景里，这个矛盾尤其明显：助手越贴近日常，用户对"它应该记得我"的预期就越强。

## 问题

我最初试过两条路，都不理想：

1. **全塞进 system prompt**。偏好条目涨到 40 多条后，注入 token 超过 2k，指令遵循明显变差，成本也上去了。
2. **对聊天记录做向量检索**。能召回事实，但"偏好"不是孤立事实——它需要稳定存在、可冲突裁决、可被用户修改，RAG 恰恰不擅长这些。

结论：记忆不是一个检索问题，而是一个数据生命周期问题。

## 做法

我在自己的实例上落了一版分层方案，核心是把记忆拆成三层，各自走不同的生命周期：

- **偏好层（semantic）**：结构化用户画像，key-value 形式，存 `memory/profile.json`，人可读可改；
- **情景层（episodic）**：会话结束后的摘要，带时间戳，只留 30 天，用于"上次聊到哪了"；
- **过程层（procedural）**：沉淀下来的操作习惯，比如"部署前先跑 lint"，以 skill 配置形式存在。

流程五步：

1. **提取**：会话结束时用便宜模型跑一次抽取，输出候选条目 `{key, value, source, confidence, ts}`。不在主循环里做，避免拖延迟。
2. **合并**：按 key 去重。冲突规则显式写死——用户明确说的 > agent 推断的，新的 > 旧的，保留来源便于回溯。
3. **注入**：会话启动只注入偏好层，硬上限 500 token；长尾事实走 `memory_search` 工具按需查，不预注入。
4. **遗忘**：条目带 confidence，连续 N 个会话未被强化就降级归档，不直接删。
5. **纠错回路**：用户纠正助手（"我说过我用 pnpm"）视为最高优先级写入，source 标记为 explicit。

把记忆包成 MCP 工具（memory_get / memory_search / memory_write）而不是 prompt 魔法，好处是任何 agent 都能挂载，且行为可测。

## 踩坑点

- **记忆污染**：用户提过一次的东西被当成稳定偏好。加了两道闸：confidence 低于阈值不入库；单次提及需二次出现才转正。
- **冲突静默覆盖**：早期旧偏好一直压着新的，排查半天才发现没按时间戳排序。冲突裁决逻辑必须显式实现，别指望模型自己判断。
- **注入过多**：贪心把情景层摘要也塞进 prompt，结果助手开始"复述历史"而不是干活。注入预算是硬约束，超了只保留高 confidence 条目。
- **隐私**：记忆文件含真实个人上下文，默认本地存储，不进任何同步盘；提供 `memory inspect / edit / purge` 命令，用户能看能删，这是信任底线。

## 可复用建议

- **记忆文件当代码管**：进 git，diff 可见，改坏了能回滚。
- **source 字段从第一天就加**：facts 和 inferred 分开存，混了以后没法清理。
- **先做最简版**：一个 markdown 画像 + 会话末提取，能覆盖八成需求；条目过百再上向量检索。
- **留一套小评测**：跨会话问"我的时区是什么"，验证记忆链路没断。

## 总结

让助手"记住你"，难点不在模型而在工程：清晰的 schema、完整的写-合并-查-忘生命周期、以及把控制权交还给用户。从最简单的结构化文件起步，先解决"记得住"，再迭代"记得准"。
