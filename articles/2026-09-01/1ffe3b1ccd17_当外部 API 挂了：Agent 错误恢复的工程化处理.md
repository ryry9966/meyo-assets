## 背景

跑过自动化 Agent 的人都有体感：链路里最脆的从来不是模型，而是外部依赖——搜索 API、天气接口、支付回调，甚至上游 LLM 本身。OpenClaw 的插件 / MCP 工具链一旦接了五六个外部服务，“某个 API 挂了”就不是意外，而是日常。问题在于大多数框架对工具失败的默认处理非常原始。

## 问题

典型故障形态有四类：超时、429 限流、5xx、返回结构突变。它们需要的处理完全不同，但常见的两种默认行为都很糟：

- 直接抛异常，整条任务链中断；
- 更糟：把空结果当正常数据继续跑，Agent 顺着编出一份看似合理的报告。

无脑“重试三次”则是第三种常见错误——它对参数错误无效，对限流有害。

## 做法：四层恢复策略

**1. 先分类，再决定动作。** 4xx（参数错、鉴权失败）重试没有意义，直接失败并带原因；超时、5xx、429 才是重试对象，且 429 要读 `Retry-After` 头。

**2. 指数退避 + 抖动。** 1s → 2s → 4s，每次加随机偏移，避免服务恢复瞬间所有实例一起打过去。

**3. 熔断与降级。** 连续 N 次失败进入冷却期，走降级路径：返回缓存、切备用数据源，并在结果里明确标注“数据可能过期”。

**4. 把结构化错误喂回模型，而不是让它猜。**

```json
{ "ok": false, "error_type": "rate_limit",
  "retryable": true, "hint": "retry after 60s" }
```

这比抛一个堆栈好得多——模型能据此决定等待、换工具，还是老实告诉用户“这事现在办不了”。写操作（下单、发消息）必须带幂等键，重试才安全。

策略建议收敛到一处配置：

```yaml
retry:
  max_attempts: 3
  backoff: exponential
  base_delay: 1s
  jitter: 0.3
  retry_on: [timeout, 5xx, 429]
circuit_breaker:
  threshold: 5
  cooldown: 60s
fallback:
  strategy: cache_with_stale_flag
```

## 踩坑点

- 重试非幂等的 POST → 重复扣款、重复发消息；
- 不设超时 → Agent 卡死还持续烧 token，连接和读取超时要分开设；
- 重试里套重试 → 三层嵌套把 3 次变成 27 次；
- 原始异常直接丢给模型 → 它开始“幻觉式恢复”，编造不存在的修复步骤；
- 降级太安静 → 故障持续三天没人发现。

## 可复用建议

- **统一错误信封**：所有 MCP 工具输出同一结构，重试策略只在配置层出现一次；
- **每个工具配 kill-switch**：出问题先摘除，别让单点拖垮整个 Agent；
- **故障注入测试**：mock 出 500、超时、慢响应，观察 Agent 表现，比上线后祈祷有用；
- **记录每次工具调用的状态码、耗时、重试次数**：事后排障全靠它。

## 总结

错误恢复不是“加重试”这一个动作，而是分类、退避、熔断、降级、可观测的组合拳。目标不是让 Agent 永远成功，而是让它失败得可控、诚实、可解释——挂了就说挂了，降级就标明降级。这比一个从不报错、却悄悄编数据的 Agent 可靠得多。
