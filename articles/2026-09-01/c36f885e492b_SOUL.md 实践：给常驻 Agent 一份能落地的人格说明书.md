## 背景

跑 OpenClaw 这类常驻 Agent，和写一个一次性脚本完全不同：它会跨会话、跨渠道（终端、Telegram、群聊）持续运行，还要调用 MCP 工具和插件。Agent 的"人格"和行为边界如果散落在各个 system prompt、插件配置、节点备注里，很快就没人说得清它到底该是什么样。

OpenClaw 的做法是把这件事收敛到一个文件：workspace 根目录的 `SOUL.md`。每轮对话它都会被注入上下文，相当于 Agent 的单一事实来源（single source of truth）。

## 问题

没有这份文件时，常见症状：

- 同一个 Agent 在终端里简洁克制，进了群聊就变话痨；
- 该拒绝的请求照单全收，比如未经确认就执行删除类操作；
- 上周口头定好的规矩，换个会话就"失忆"；
- 多处 prompt 各写一套，改了一处忘了另一处，行为漂移。

根因都一样：人格和边界没有集中管理。

## 做法

1. **建文件**：在 workspace 根目录创建 `SOUL.md`，先从 20 行写起。
2. **分四段**：身份（我是谁、什么语气）、原则（拿不准时优先什么）、边界（明确不做什么）、与用户的关系（协助者而非讨好者）。
3. **和 AGENTS.md 分工**：`SOUL.md` 管"我是谁"，`AGENTS.md` 管"活怎么干"。操作步骤、工具用法不要塞进 SOUL.md。
4. **边界写成具体行为**："不主动发送任何外部链接，除非我明确要求"，而不是"谨慎行事"。前者可验证，后者是废话。
5. **迭代维护**：Agent 犯一次错，就加一条针对性规则；某条规则连续一个月没触发，删掉。
6. **进 git**：人格变更走 commit，能 review、能回滚。

## 踩坑点

- **写太长**。SOUL.md 每轮都占上下文，几百行不仅费 token，还会稀释关键规则。控制在 60 行以内。
- **形容词堆砌**。"诚实、可靠、友好"约等于没写，模型无法执行形容词，只能执行场景。
- **规则互相冲突**。"回答务必简短"和"重要决策必须解释权衡"放一起，Agent 会随机选一边。冲突时写清优先级。
- **把 SOUL.md 当保险箱**。它是给模型读的，也可能被间接引用进回复，密钥、地址别放。
- **以为写了就完事**。超长会话和模型升级都会导致漂移，定期用几个对抗性提问测一遍边界是否还生效。

## 可复用建议

- 句式统一用"当 X 时，做 Y"，方便后续按场景增删。
- 单独维护一个"翻车记录"文档，它是 SOUL.md 最好的需求来源。
- 边界宁少勿多：5 条执行到位，好过 30 条互相打架。
- 每次升级模型大版本后，重读一遍 SOUL.md，删掉已被模型默认行为覆盖的条目。

## 总结

SOUL.md 的价值不在于"让 Agent 更像人"，而在于把人格和边界变成可版本化、可 review、可测试的工程产物。把它当代码维护——小步提交、定期修剪、出了 bug 补测试——Agent 的行为才会长期稳定。
