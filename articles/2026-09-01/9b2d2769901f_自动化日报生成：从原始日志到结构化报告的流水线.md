## 背景

团队日常进展散落在 git 提交、CI 结果、Agent 任务日志和告警里。日报靠人拼凑，漏项、口径不一，还固定吃掉每天半小时。我们的做法是：用 OpenClaw 搭一条定时流水线，让代码做确定性工作，Agent 只负责语义压缩。

## 问题

最直觉的方案——"把日志直接丢给模型写日报"——跑不通，卡在三点：

- 原始日志量大且噪，DEBUG 心跳类条目占九成，直接进上下文既贵又稀释重点；
- 让 LLM 自由发挥最终文案，格式天天漂移，下游没法稳定消费；
- 日报本质是"事实陈述"，幻觉不可接受，必须能回溯到原始证据。

## 做法

按四层拆开：

1. **采集层（定时触发 + 脚本）**：固定时间拉取当天的 git log、CI 摘要、Agent 运行记录、ERROR 级日志，各源独立落盘为 JSON，时间戳在采集层统一归一化。
2. **压缩层（纯代码）**：去重、过滤心跳、按模块聚合计数、截断超长条目，产出一份紧凑的 digest JSON。这一层不经过模型，完全可控。
3. **摘要层（OpenClaw Agent + MCP）**：Agent 读取 digest，必要时通过 MCP 工具回查细节（比如某次失败任务的完整输出），最终输出严格符合预定义 JSON Schema 的结构化字段：今日完成、异常与归因、风险、明日计划。Schema 校验不过就重试，连续失败则降级为"原始 digest 附件 + 失败标记"，保证日报不缺席。
4. **渲染与投递层（模板 + webhook）**：最终 Markdown 由模板引擎从 JSON 渲染，LLM 不碰排版。成品推送群里，digest 与报告同时归档，留审计入口。

## 踩坑点

- **时区边界**：日志源混用 UTC 和本地时间，第一版把凌晨的提交算到了前一天。所有时间在采集层统一转换，日报边界在配置里显式声明。
- **幂等性**：手动重跑导致群里出现两条日报。改为按"日期"做幂等键，重跑覆盖而非追加。
- **静默失败**：脚本挂掉没人发现，连续两天没日报才被提起。调度层补了失败即告警，投递成功也发一条轻量回执。
- **Schema 漂移**：模型偶尔在数组字段里塞字符串。JSON Schema 严格校验 + 一次自动修复重试，基本兜住了。

## 可复用建议

- 先定报告 Schema，再写 prompt，顺序别反；
- 代码负责"筛与算"，Agent 负责"读与归纳"，模板负责"排版"，三层职责不要混；
- digest 必须落盘，报告有争议时能回溯到原始证据；
- 先在低风险频道灰度一周，人工抽查准确率，再逐步扩大数据源。

## 总结

这条流水线的核心不是"让 AI 写日报"，而是把日报拆成确定性的数据处理、受 Schema 约束的语义压缩、确定性的模板渲染三段。Agent 被关在结构里，出错可降级、结果可审计。骨架跑稳之后，换个数据源就是周报或值班交接记录，边际成本很低。
