## 背景

我们团队每天要在群里发一封日报：昨日构建次数、失败用例、线上告警摘要、待跟进事项。以前是值班同学手动翻日志拼出来的，耗时二十分钟起步，且每个人统计口径都不一样。后来我用 OpenClaw 定时任务加几个 MCP 工具，把它做成了流水线，跑了两个多月，基本零人工介入。

## 问题

最初的做法很直接：cron 拉取当天原始日志，一股脑塞给 Agent，让它"总结成日报"。结果不理想：

- **数字会错**。模型自己数出来的"失败 23 次"和实际对不上，偶尔还编造没发生过的告警。
- **格式漂移**。今天列表明天段落，下游没法归档比对。
- **日志一多就截断**，尾部信息丢失，而夜里出的问题恰恰在尾部。

根因很清楚：把"确定性计算"交给了概率性组件。

## 做法

现在的流水线分四段，Agent 只负责最后一段：

1. **采集**：cron 每小时跑一次脚本，把 CI 日志、告警平台 webhook、工单系统增量拉到 `daily/YYYY-MM-DD/` 目录，按来源分文件。
2. **结构化**：纯代码解析器（不经过模型）把日志压成 JSONL，每行固定字段：`ts / source / level / case_id / status / duration_ms`。解析失败的行写入 `quarantine.log`，不静默丢弃。
3. **聚合**：还是代码。按天算出指标 JSON——总数、失败分布、TopN 慢用例、去重后的告警时间线。这是日报里所有数字的唯一来源。
4. **生成**：Agent 读指标 JSON 和模板骨架，只做两件事：给异常段写两句人话解读，把告警时间线转成易读短句。产出先过 JSON Schema 校验，再经 MCP 推送到群 webhook，同时留一份 Markdown 进仓库。

## 踩坑点

- **别让模型碰原始日志**。它适合解读，不适合计数。所有数字由代码算好，模型只做"引用"，prompt 里明确禁止自行计算。
- **时区**。CI 日志是 UTC，日报口径是本地时间，第一版把跨天任务归错了日子。现在采集层统一转成带时区的 ISO 时间。
- **上游格式变更**。某天字段名一改，解析器静默产出全空指标，日报照发不误。后来加了硬校验：解析成功率低于阈值就告警并暂停发送。
- **幂等**。cron 重试导致同一份日报发过两遍。现在生成文件名带日期加内容 hash，推送前查重。
- **模板即契约**。日报结构写进 Schema，模型只填字符串槽位，格式漂移问题彻底消失。

## 可复用建议

- 先定 Schema 再写 prompt，让产出可机检，而不是靠肉眼审。
- 采集、解析、聚合、生成四段解耦，中间产物落盘，任何一段都能单独重跑和回测。
- 给流水线留降级出口：数据异常时宁可发"待人工核查"，也别发一份好看的错数日报。
- 上线后抽两周的产出人工核对数字，口径确认无误再放手。

## 总结

这条流水线的核心经验就一句：确定性的事交给代码，表达性的事交给 Agent，中间用 Schema 把两者焊住。日报只是载体，同一套结构套周报、事故复盘摘要都成立。相比"一句话让 Agent 全搞定"，多写百来行解析代码，换来数字可信、格式稳定、出错能定位到具体段——这笔账在自动化场景里永远是划算的。
