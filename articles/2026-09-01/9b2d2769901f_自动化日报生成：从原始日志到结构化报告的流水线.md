## 背景

在 OpenClaw/Agent 工具链里做自动化日报，最常见的错误是把原始日志一股脑丢给模型，期待它直接输出日报。实际工程里，Git 提交、CI 运行、监控告警、工单状态、群聊结论来自不同系统，格式、粒度、时区、噪声都不同。模型能写句子，但不能替你负责“哪些事实可信”。

## 问题边界

日报生成的核心不是文笔，而是把“原始日志”压成“结构化事实”，再交给模型做受控表达。没有这条前置流水线，会出现三类问题：

- 日志噪声大，模型漏掉关键事件；
- 上下文过长，成本高且摘要不稳定；
- 模型在信息不足时编造链接、负责人或时间。

## 做法：四条流水线

### 1. 先定义报告结构

不要先写 prompt，先定义输出 schema。建议固定为：

- 今日概览
- 关键事件
- 风险与异常
- 数据指标
- 明日计划

结构化字段至少包含：`event_type`、`severity`、`actor`、`system`、`time`、`status`、`link`、`raw_summary`。后续生成和校验都围绕这个结构。

### 2. 采集与清洗

用 MCP 连接器或插件从 Git、CI、告警、工单系统采集原始日志。采集层只做三件事：

- 按业务时区过滤时间窗口；
- 去重，合并同一事件的多条日志；
- 字段归一化，统一时间、状态、级别。

这一步不要调用 LLM，使用规则和固定映射即可。日志里经常有 token、密码、内网地址，进入模型前必须做脱敏。

### 3. 规则预聚合，不是全量喂入

把清洗后的日志聚合成紧凑事实。例如：

```json
{
  "project": "billing",
  "event_type": "deploy",
  "count": 3,
  "success": 2,
  "failed": 1,
  "duration_min": 18,
  "related_links": ["https://ci.example.com/run/123"]
}
```

一个简单的聚合策略是按 `project + event_type + status` 分组，输出数量、耗时、失败原因摘要。这样模型的输入从几百条日志降到几十条事实。

### 4. 受控生成与校验

Prompt 输入结构化事实，而不是原始日志。要求：

- 只使用给定事实，不补充未提供信息；
- 缺失数据写“无”，不推测；
- 链接只允许出现在白名单字段；
- 输出 JSON 或固定 Markdown 模板；
- 使用低温度，必要时用 few-shot。

生成后做一次 JSON Schema 校验和链接白名单校验。不通过就回退到模板日报，而不是发布半成品。

## 踩坑点

- **时区边界**：CI 时间通常是 UTC，业务日报按本地时区统计。所有时间窗口必须在入口统一转换，不能等模型理解。
- **空数据日**：当天没有事件时，模型容易编造“无异常但存在风险”。建议在生成前判断事实数量，为空时直接走空模板。
- **MCP 工具失败**：某个数据源挂了，不能静默继续。日报里应标注“该数据源本次未采集到”，否则读者会把缺失当正常。
- **Markdown 转义**：日志里包含 `|`、反引号、HTML 片段时，直接拼接会破坏表格。生成前做一次转义。
- **模型幻觉链接**：即使 prompt 强调不要编造，模型仍可能生成不存在的地址。链接必须由采集层提供，生成后只允许引用已有链接。

## 可复用建议

- 把流水线拆成可检查的节点：`raw -> normalized -> facts -> draft -> final`，每个节点落盘，方便回放和排障。
- 模型只负责“从结构化事实到自然语言”，不要让它承担采集、清洗、聚合职责。
- Prompt、schema、few-shot 示例都纳入版本管理，改动可回滚。
- 日报头部带上数据时间窗、数据源覆盖率、生成耗时、流水线版本。
- 先做 dry-run：生成后只输出到测试频道或本地文件，稳定一周后再接入正式发布。

## 总结

自动化日报的难点不在“能不能写”，而在“写得是否可信”。一条可复用的流水线应该先做确定性清洗和聚合，再让 Agent 做受控生成。这样即使模型偶尔出错，也不会污染事实层；即使某个数据源失败，也不会让日报变成猜测。

下一步可以考虑把这条流水线接到更多 MCP 数据源，或者让 Agent 根据历史日报识别“值得写进日报”的事件，而不是机械汇总所有日志。
