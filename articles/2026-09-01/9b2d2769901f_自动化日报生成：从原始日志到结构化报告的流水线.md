## 背景
团队每天需要汇总多个系统的运行情况：应用日志、Agent/MCP 调用记录、定时任务输出、关键错误事件。此前靠人工翻 Grafana、ELK 再粘贴成日报，耗时且格式不一致。引入 OpenClaw 后，我们把它定位为“调度与摘要层”，而不是让模型直接读全量日志。

## 问题
原始日志最麻烦的几点：
- 多来源格式不一致，时间戳时区不同；
- 噪声大，心跳、debug、重复堆栈可能占 80%；
- 直接丢给 LLM 会爆上下文，且输出 JSON 不稳定；
- 报告既要可读，也要能机器校验，不能每次人工复核格式。

因此目标不是“让 Agent 帮我写日报”，而是一条可重复、可审计、可降级的自动化流水线。

## 做法 / 步骤
### 1. 采集原始日志
通过 OpenClaw Agent 在每天固定时间触发，用 MCP 工具从文件目录、HTTP API 或消息队列拉取前 24 小时数据。原始文件按 `raw/YYYYMMDD/{source}.log` 落盘，保留现场，便于排障。

### 2. 归一化中间结构
先不着急总结，把每条日志转成统一 JSON：

```json
{
  "ts": "2026-01-20T08:12:30Z",
  "level": "ERROR",
  "source": "payment-api",
  "event_type": "timeout",
  "message": "upstream timeout",
  "trace_id": "abc123",
  "duration_ms": 3200
}
```

这一步用脚本或插件完成，不建议靠模型抽取字段，成本和错误率都不可控。`ts` 统一 UTC，渲染时再转本地时区。

### 3. 过滤与聚合
按 `source`、`level`、错误签名做聚合，去掉重复堆栈和 heartbeat。只保留：
- 错误数 Top N；
- 新增错误签名；
- 慢请求 Top N；
- Agent/MCP 工具调用失败。

确定性聚合用规则完成，不占用模型能力。

### 4. 分段摘要
把过滤后的数据按“小时窗口”或“事件簇”切块，交给 LLM 输出严格 JSON，要求只输出 `summary`、`key_events`、`risks`、`actions` 四类字段。用小模型做分段摘要，最后合并一次生成总览。OpenClaw 里使用 Agent 工具调用即可，不把全量日志塞进 system prompt。

### 5. 渲染与分发
用模板引擎生成 Markdown/HTML。模板固定章节：昨日概览、异常事件、变更记录、待跟进事项。最后通过 webhook 发到 IM 或邮件。若出现 P0/P1 级别错误，报告自动标记“需要人工 review”。

## 踩坑点
- **上下文溢出**：即使过滤后，一天日志仍可能超出窗口。务必先聚合再摘要，不要“直接读文件”。
- **时间戳不一致**：所有时间先转 UTC 存储，渲染时再转本地时区。我们踩过跨天日志被归错日期的问题。
- **LLM JSON 不稳定**：加 schema 校验，失败自动重试一次；再失败则退化为规则生成摘要，不要卡死流水线。
- **MCP shell 权限过大**：跑日志采集的容器要限制命令 allowlist，避免误执行。
- **敏感信息**：日志里的 token、手机号、用户 ID 要在进 LLM 前脱敏，否则审阅链会外泄。

## 可复用建议
- 把中间 JSON contract 定清楚，来源和模板都解耦，后续新增日志源只需加采集器。
- 确定性聚合用规则，语义总结才用 LLM。不要把所有逻辑塞进 prompt。
- 报告 schema 加版本号，输出文件名带日期，支持 `--since` 或 `--dry-run`，保证可重跑和可审计。
- 先做一个最小可用版：只接一个日志源，跑通“采集 → 归一化 → 聚合 → 摘要 → 渲染”，再逐步加源。
- 对失败的工具调用单独开一个视图。Agent 的失败模式和应用日志不一样，容易漏。

## 总结
这条流水线让日报从“每天 30-40 分钟人工整理”变成“5 分钟 review 异常”。它并不复杂，但胜在结构清晰：原始日志 -> 统一 JSON -> 聚合 -> 分段摘要 -> 模板渲染。OpenClaw 的价值在于把 MCP 工具、Agent 调用和模板串起来，而不是替代所有环节。先把中间结构做好，后面再换模型、加插件都会轻松很多。
