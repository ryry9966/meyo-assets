# 自动化任务的幂等性：重复执行为什么不该出问题

## 背景：重试是常态，不是异常

在 OpenClaw、Agent、MCP 插件和各类自动化任务里，重复执行的来源比想象中多：用户重复点击、消息队列重复投递、Agent 内部超时重试、定时任务上次没跑完下次又启动、人工补偿重跑。如果把“只执行一次”当作默认前提，系统早晚会出事故。

更现实的做法是反过来设计：默认任务可能被执行多次，并保证重复执行不会产生额外副作用。这就是幂等性。

## 问题：非幂等任务的实际代价

一个典型场景：某个 MCP 工具负责“创建工单”。如果插件收到重复调用而没有幂等控制，就会创建两张一模一样的工单，后续还要人工合并或删除。再比如“发送通知”动作，Agent 重试一次，用户就收到两条一样的消息。更危险的是库存扣减、资金操作、外部 API 调用——重复执行可能直接造成资产损失。

幂等性不是优化项，而是自动化系统可靠性的底线。

## 做法：四层幂等防护

### 1. 幂等键：给每次业务操作一个唯一标识

每个写操作都应该有一个 `idempotency_key`。这个键可以由调用方传入，也可以根据业务参数确定性生成，例如 `order_id + action_type`。在 OpenClaw 的 MCP 工具 schema 中，建议把 `idempotency_key` 作为写操作的必填参数，并在工具描述里声明“重复调用安全”。

### 2. 入口状态检查：先查后写，但要原子

处理请求前，先检查该幂等键是否已经处理过。如果已完成，直接返回上次的结果或成功标记。关键是不能用普通的“先查后写”，因为并发下会有竞态。可以用 Redis 的 `SET key value NX EX 60` 实现简易原子锁，或者用数据库的 `INSERT ... ON CONFLICT DO NOTHING`。

### 3. 数据库唯一约束兜底

在关键表上建立唯一索引，把幂等键作为唯一字段之一。例如 `unique(order_id, action_type)`。这样即使应用层检查漏了，数据库也会拒绝重复插入，从最底层保证不产生重复数据。

### 4. 状态机约束

如果业务流程有明确状态，只允许从特定前置状态流转到目标状态。比如“待处理 → 处理中 → 已完成”，更新时使用条件更新：`UPDATE ... SET status='已完成' WHERE id=? AND status='处理中'`。这样重复的“完成”操作会被条件过滤掉。

## 踩坑点

### 竞态条件：先查后写不是原子操作

两个并发请求同时查到“未处理”，然后都执行了业务逻辑。解决方式只有原子操作：Redis `SET NX EX` 或数据库唯一约束。不要依赖内存去重，多实例部署下会失效。

### 幂等键粒度过粗或过细

太粗：所有“创建”操作共用同一个键，导致不同请求被误判为重复，用户的操作被吞掉。太细：每次随机生成新键，幂等完全失效。应该基于业务唯一性生成稳定键。

### 副作用游离在主流程外

主记录幂等了，但通知、webhook、邮件等副作用每次重试都发一次。解决方案：把副作用也纳入状态管理，或者采用 outbox 模式——先记录待发送意图，由异步 worker 发送，发送成功后再标记完成。

### 部分成功：多步操作中途失败

比如先扣款再发货，发货失败后重试，扣款可能重复执行。需要把每个步骤都做成幂等，或者用 Saga 模式记录补偿动作。

### 缓存结果过期

直接返回上次成功结果时，如果上游数据已经变化，可能返回过期数据。需要设置合理的缓存失效时间，或在返回缓存结果时附带明确的时间戳标记。

## 可复用建议

- 在 OpenClaw 插件开发中，对所有写操作强制要求 `idempotency_key`，并在工具描述里写清楚“重复调用返回相同结果”。
- 用 Redis 实现一个幂等装饰器：`SET key token NX EX 60` 成功则执行业务，失败则 `GET key` 返回既有结果。
- 数据库表设计时，为业务唯一标识字段加唯一索引，不要把唯一性只放在应用层。
- 对外部 API 调用使用 outbox 模式，先记录意图，再异步发送，避免重复通知。
- 在任务编排里，只有幂等的步骤才适合配置自动重试；非幂等步骤要么改造为幂等，要么人工确认后重跑。

## 总结

幂等性让“失败后重试”变成安全的默认策略。对自动化任务来说，重复执行不出问题意味着系统可以自愈、运维可以放心重跑、Agent 可以大胆重试。把幂等键、唯一约束、状态机、副作用管理做扎实，比事后修复重复数据要省得多，也更符合工程化的长期收益。
