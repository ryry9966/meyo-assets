# OpenClaw 沙箱安全模型拆解：为什么 Agent 不会误删文件

## 一、背景：Agent 的工具调用天然危险

不管是用 OpenClaw 做代码生成、文件整理还是插件自动化，Agent 一旦接入文件系统工具，就存在“误删”风险。典型的不可靠因素有三个：

1. 提示词注入导致 Agent 执行非预期删除操作；
2. 路径拼接错误，比如把 `/workspace/tmp/` 拼成 `/workspace/`，删除范围扩大；
3. 插件或 MCP 工具绕过主 Agent 的意图，直接调 shell 执行破坏性命令。

单纯靠“提示词要求 Agent 不要乱删”是不可靠的。OpenClaw 的做法是把安全约束下沉到沙箱层，让文件系统本身成为最后一道闸门。

## 二、问题：哪些场景最容易“误删”

在真实使用中，误删通常不是 Agent 突然变坏，而是下面几类问题叠加：

- 工作目录开放过大：把整个家目录或 `/` 作为可写路径；
- shell 工具未被限制：Agent 可以直接执行 `rm`、`unlink` 等命令；
- 符号链接逃逸：Agent 删除的是一个链接，但实际指向沙箱外目录；
- 自动确认：破坏性操作虽然弹了确认，但用户习惯性点“允许”。

OpenClaw 的沙箱模型主要解决的是：让 Agent 只能碰你允许它碰的文件，并且破坏性操作必须经过明确确认或可回滚。

## 三、做法与步骤：理解 OpenClaw 的默认沙箱结构

### 1. 读写路径白名单是基础

OpenClaw 不会默认允许 Agent 访问所有文件系统。通常需要在沙箱配置中声明 `allowed_paths`，只有这些路径下的文件才能被读取或写入。例如：

```yaml
sandbox:
  allowed_paths:
    - ./workspace
    - ./cache
  deny_paths:
    - ~/.ssh
    - ~/.config
    - ~/Documents
```

如果 Agent 尝试删除 `~/.ssh/id_rsa`，即使它在对话中“以为”自己有权限，文件系统层也会直接拒绝。

### 2. 写保护与 overlay 模式

OpenClaw 支持 overlay 沙箱模式。开启后，Agent 的写操作会先落到临时层，不会直接修改真实文件。只有在明确执行提交操作时，临时层才会合并回实际目录。

```yaml
sandbox:
  mode: overlay
  snapshot_interval: 50
```

这种模式非常适合“先让 Agent 做一批操作，人工检查 diff 后再落盘”的工作流。即使 Agent 删错文件，也可以从快照或临时层恢复。

### 3. 破坏性操作强制确认

对删除、覆盖、清空等破坏性操作，OpenClaw 建议开启确认门禁：

```yaml
destructive_ops:
  requires_confirmation: true
```

在工具层面，`delete`、`unlink`、`rmtree` 等操作不会直接执行，而是先返回一个确认请求，由用户在 UI 或 CLI 中审批。审批信息里会显示目标路径、操作类型和影响范围。

### 4. 路径规范化与逃逸防护

OpenClaw 在工具入口会做路径规范化：解析符号链接、统一相对路径、检查 `..` 是否越界。即使 Agent 传入了 `./workspace/../../etc/passwd`，沙箱也会把它规范化到真实路径，再判断是否在 `allowed_paths` 内。

对于符号链接，OpenClaw 默认不允许通过链接写入或删除沙箱外的目标。这意味着，如果沙箱内有一个指向 `~/Documents` 的链接，Agent 删除这个链接时只会删除链接本身，不会误删链接指向的真实文件。

### 5. 审计日志与回滚

每次文件操作都会生成事务记录。如果发现误删，可以直接回滚：

```bash
openclaw sandbox rollback <transaction-id>
```

在 overlay 模式下，回滚更简单：丢弃临时层即可。不过要注意，如果你已经执行了 commit，回滚就需要依赖快照或备份了。

## 四、踩坑点：沙箱不是万能保险

### 1. overlay 模式容易让人误以为文件已经写好

Agent 在 overlay 模式下写文件，可能在临时层里能看到结果，但真实目录并没有变化。如果另一个进程或用户去读真实路径，会读到旧内容。使用 overlay 时，一定要明确何时 commit，避免“文件凭空消失”的困惑。

### 2. 不要用 root 运行 Agent

沙箱的很多路径限制依赖操作系统权限。如果用 root 跑 OpenClaw，进程可能有权绕过部分路径检查，或者访问本应被禁止的系统文件。建议使用普通用户，并通过目录权限配合沙箱策略。

### 3. 过度开放 `/tmp` 会造成跨任务污染

很多配置会把 `/tmp` 加入白名单，方便插件写临时文件。但 `/tmp` 是全局共享的，多个 OpenClaw 会话或 Agent 任务可能互相干扰。建议为每个会话分配独立临时目录，例如 `/tmp/openclaw/<session-id>/`，并把该目录加入白名单。

### 4. 符号链接测试不可省略

即使有路径规范化，也建议实际测试：在沙箱内创建一个指向沙箱外目录的符号链接，然后让 Agent 尝试删除链接或链接目标。观察是否被正确拦截。很多“误删”事故都来自符号链接逃逸，而不是路径遍历。

### 5. 确认弹窗疲劳会导致误点

强制确认虽然安全，但用户如果每次都不看就点允许，安全门禁就形同虚设。对于不熟悉的脚本或批量删除操作，建议先用 dry-run 模式，或者让 Agent 先列出将要删除的文件清单，人工确认后再执行。

## 五、可复用建议

1. **最小权限原则**：只给 Agent 工作目录和专用缓存目录，不要轻易开放家目录、下载目录或系统目录。
2. **分离读/写工具**：不要让 Agent 直接使用无限制 shell。读写文件通过受控工具完成，shell 只在必要时开放且单独设置权限。
3. **插件与 MCP 同样受沙箱约束**：第三方 MCP 或插件不能继承比主 Agent 更宽的沙箱策略。如果插件需要网络访问，单独设置 egress 规则，不要和文件系统权限混在一起。
4. **定期查看沙箱日志**：关注 `DENY` 事件。如果某个操作频繁被拦截，说明 Agent 的路径规划或插件权限配置可能有问题，需要调整任务说明或白名单。
5. **关键目录做双重保护**：沙箱白名单之外，建议再用 git 或系统备份保存重要数据。沙箱防的是误删，不是硬件损坏或系统级故障。

## 六、总结

OpenClaw 的沙箱安全模型不是靠提示词“劝” Agent 不要乱删，而是通过文件系统白名单、overlay 临时层、破坏性操作确认、路径规范化和审计回滚，组成多层防线。误删通常不是沙箱失效，而是配置过宽、用户盲目确认或忽略了 overlay 的提交机制。

工程上比较稳妥的做法是：默认只给最小可写路径；删除操作始终确认；不熟悉的任务先 dry-run；定期检查沙箱日志和回滚能力。做到这几点，Agent 基本不会因为提示词注入或路径错误把你的文件删掉。
