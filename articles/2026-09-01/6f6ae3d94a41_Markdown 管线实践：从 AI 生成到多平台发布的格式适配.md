## 背景

在 OpenClaw 的自动化工作流里，Agent 生成 Markdown 内容后，经常需要发布到多个平台：GitHub 仓库、静态博客、公众号、知乎等。AI 生成的内容通常包含丰富的 Markdown 扩展语法，比如任务列表、脚注、LaTeX 公式、内嵌 HTML 等。这些语法在不同平台的解析器下表现差异极大：GitHub 支持任务列表和脚注，公众号编辑器几乎不支持标准 Markdown，知乎对表格和公式的支持有限，静态博客生成器又依赖特定的 front matter。

如果没有一个统一的处理管线，每次发布都会变成手动修格式的体力活，而且随着 Agent 生成内容的数量增加，维护成本会失控。

## 问题

直接复用 AI 生成的 Markdown 会踩到这些典型的坑：

- **平台方言差异**：同样的任务列表 `- [ ]` 在 GitHub 正常，在公众号里会变成普通文本或丢失复选框。
- **表格支持不一致**：公众号原生不支持 Markdown 表格，需要转成 HTML 表格或图片；知乎对复杂表格的解析容易错位。
- **代码块高亮**：语言标注（如 ```python）在部分平台会被剥离，导致高亮失效。
- **图片链接**：相对路径在平台发布后失效，需要提前上传图床并替换为绝对 URL。
- **公式渲染**：LaTeX 公式在多数内容平台无法直接渲染，需要转成图片或依赖第三方服务。
- **front matter**：静态站点生成器要求 YAML/TOML 头部，而其他平台如果收到这段内容会直接显示为乱码。

这些问题的本质是：AI 生成的是“理想 Markdown”，而每个平台只实现了 Markdown 的一个子集或方言。我们需要一个中间表示和转换层。

## 做法 / 步骤

在实践中，我采用了一个轻量的 Markdown 管线，核心思路是“解析为 AST → 适配器转换 → 输出”。

### 1. 定义基线规范

使用 CommonMark 作为基线，限制扩展语法范围。允许表格、围栏代码块、图片链接、任务列表，但禁止任意 HTML（仅白名单内联标签如 `<kbd>`）。这样保证中间格式是可控的。

### 2. 解析为 AST

用 `unified` + `remark-parse` 或 `markdown-it` 将 Markdown 解析为 AST。AST 的好处是可以用代码遍历节点，而不是用正则做文本替换——正则处理嵌套列表或代码块内的 Markdown 符号时非常脆弱。

下面是一个简化的示例，展示如何用 `unified` 提取所有图片节点：

```javascript
import { unified } from 'unified'
import remarkParse from 'remark-parse'
import { selectAll } from 'unist-util-select'

const tree = unified().use(remarkParse).parse(md)
const images = selectAll('image', tree)
// 批量处理图片链接替换
```

### 3. 编写平台适配器

每个目标平台对应一个适配器函数，输入 AST，输出转换后的 AST 或字符串。适配器专注于解决该平台的限制：

- **GitHub**：保留任务列表和脚注，清理 front matter，输出标准 Markdown。
- **公众号**：将 Markdown 表格转为 HTML `<table>`，任务列表转换为普通无序列表，公式节点替换为图片 URL。
- **静态博客（如 Hexo/Hugo）**：注入 front matter，保留扩展语法，设置摘要截断点。
- **知乎**：表格转为 HTML，公式转图片，限制代码块长度。

在 OpenClaw 中，这些适配器可以封装成 MCP 工具，或者作为工作流中的脚本节点。Agent 生成内容后，自动触发管线，产出多个平台版本。

### 4. 编排与回滚

管线处理时保留原始 Markdown 作为 source of truth，每个平台的输出单独存储。如果某个平台格式出错，可以单独重新生成该平台的输出，而不影响其他平台。

## 踩坑点

实际搭建过程中，这些坑需要特别注意：

- **表格转换时列宽丢失**：Markdown 表格的列宽信息不在 AST 中，转为 HTML 时需要额外计算。建议用 `remark-gfm` 的 table 节点，配合 `to-hast` 并设置 `allowDangerousHtml`。
- **代码块语言标注被剥离**：部分平台的 Markdown 渲染器会把语言标注当作普通文本。可以在输出时用 HTML 注释或平台允许的方式保留语言信息，例如公众号可用第三方编辑器识别 `language-xxx` 类。
- **图片尺寸**：平台对图片有大小限制，但 Markdown 本身不支持尺寸。可以在管线中集成图片压缩步骤，生成多种尺寸版本，根据不同平台选择。
- **相对链接**：AI 生成的内容里常出现相对链接或锚点，发布到平台后指向不存在。需要遍历所有链接节点，对相对路径做绝对化或短链替换。
- **嵌套列表缩进**：不同解析器对 2 空格、4 空格缩进的容错不同。在解析前统一将缩进规范化为 2 空格，避免歧义。
- **front matter 误显示**：如果不小心把带 YAML 头的内容发给公众号，头部会原样显示。适配器必须剥离或转换所有 front matter。

## 可复用建议

- **用 AST，不要用正则**：正则无法准确匹配嵌套结构，一旦内容中出现代码块内的 `#` 或列表内的表格，就会误伤。
- **配置驱动适配器**：把平台限制定义成配置（如 `supportsTable: false`），而不是写死逻辑。新增平台时只需添加配置和少量转换函数。
- **保留原始 Markdown**：转换产物可以随时丢弃重建，但原始内容必须保留。这让你可以随时升级适配器或修复 bug。
- **编写测试集**：收集 AI 生成内容的真实样本，作为每个适配器的测试用例。尤其要覆盖表格、公式、嵌套列表、代码块内特殊字符这几类。
- **幂等设计**：管线执行两次应得到相同结果。避免使用时间戳或随机数，否则无法做 diff 对比。

## 总结

Markdown 管线化处理是 AI 内容自动化发布中容易被忽视但至关重要的一环。通过定义中间 AST 和可替换的适配器，可以大幅减少多平台发布的格式事故。工程化的做法是保持简单、可测试、可回滚，而不是试图用一个万能转换器解决所有问题。在 OpenClaw 的 Agent 工作流中，这个管线可以作为一个稳定的下游节点，让 AI 生成的内容真正“一次生成，多处适配”。
