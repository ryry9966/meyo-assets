## 背景

我在跑一个 OpenClaw 个人 Agent，早期挂能力的方式很粗暴：把所有操作指南——部署规约、日志排查、通知格式——全部塞进 system prompt。指南只有三四份时还能忍受，到了第十份暴露出两个问题：每次对话还没干活就背着几千 token 的固定开销；模型偶尔“抓错”指南，把上周的发布规约用在不相干的场景里。

## 问题

本质是能力供给和上下文成本的矛盾：绝大多数能力在单次任务里根本用不到，却常驻上下文。“全量背在身上”的加载方式带来三个具体伤害：

- 固定开销随能力数量线性上涨，直接推高成本和首响延迟；
- 指南越多，触发边界越模糊，能力之间互相干扰；
- 内容混在一个文件里，改一处要回归验证所有能力。

Skills 机制就是针对这个矛盾的解法。

## 原理：三层渐进披露

Skills 的思路类似懒加载，分三层按需展开：

1. **启动层**：会话建立时只注入每个 skill 的 `name` 和一句话 `description`，每个几十 token，挂几十个技能也负担得起；
2. **触发层**：模型判断当前任务命中某个 skill 的描述时，才去读它的完整 `SKILL.md` 正文；
3. **展开层**：正文里可以再引用更多文件——详细规格、可执行脚本——真正用到才加载。

目录结构大致是：

```
~/.openclaw/skills/
  weekly-report/
    SKILL.md             # 入口：元数据 + 使用步骤
    scripts/build.py     # 确定性逻辑放脚本
    references/style.md  # 长参考资料
```

`SKILL.md` 头部的元数据是关键：

```yaml
---
name: weekly-report
description: 生成并导出周报 PDF。触发场景：用户提到"导出周报""把本周报告发给老板"；不用于日常闲聊总结
---
```

实操步骤：建目录和 SKILL.md；description 写成"检索词"（动词 + 对象 + 边界场景）；正文控制在两百行内，细节外推到 references/；确定性操作写成脚本，markdown 只写调用方式和前置条件；最后开新会话，用两三种不同说法验证触发是否可靠。

## 踩坑点

1. **description 写得太泛**。“处理文档相关任务”这种描述基本不会触发，要贴近用户真实会说出口的话来写。
2. **一个 skill 干十件事**。瑞士军刀式技能必然正文膨胀，按需加载就失去意义，宁可拆细。
3. **脚本路径想当然**。Agent 的工作目录不一定在 skill 所在处，skill 里要写清如何定位自己的目录，别依赖 cwd。
4. **同名覆盖**。用户级 skill 可以覆盖同名技能，排查“改了怎么没生效”时先想到这条。
5. **改完不换会话**。技能列表可能在会话启动时载入，老会话看不到更新，验证一律开新会话。

## 可复用建议

- **脚本是事实源，markdown 是说明书**。逻辑、校验、报错处理放脚本，SKILL.md 只写调用时机和前置条件，这样模型执行的方差最小。
- **一次只加一个 skill**，观察几天触发行为再扩展，别一口气迁移十份旧指南。
- **skills 目录入 git**，回滚和回溯都靠它。
- **和 MCP 的分工**：连接外部系统、标准工具协议走 MCP server；“我们团队这类事怎么做”属于 Skills。前者管能力接入，后者管能力规约。

## 总结

Skills 的价值在于把能力加载从“启动时全量背诵”改成“用到时按需查阅”：上下文里只留一份轻量索引，细节和脚本延迟到触发后。相比写一个 MCP server，它的门槛低得多——一个 markdown 加几个脚本就能跑起来，很适合作为个人和团队沉淀 Agent 能力的默认方式。我目前的分工是：MCP 管连接，Skills 管规约，system prompt 只留人格和全局边界。
