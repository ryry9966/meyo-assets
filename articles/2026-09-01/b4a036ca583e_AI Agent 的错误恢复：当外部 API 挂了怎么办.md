## 背景

跑过长期自动化任务的人都有体感：Agent 本身的逻辑往往不是最先挂的，先挂的是它依赖的外部 API——搜索接口限流、模型供应商 5xx、MCP 工具背后的服务超时。一次性脚本失败了重跑就行，但 Agent 卡在多步任务中间时，失败处理方式直接决定任务是"降级完成"还是"整段报废"。

## 问题

实际观察下来，API 故障时 Agent 常见三种死法：

1. **幻觉兜底**：工具返回报错，模型没有承认失败，而是"编"了一个看似合理的结果继续往下走。
2. **重试风暴**：在提示词里写"失败了就重试"，Agent 立刻原地循环，token 和配额双爆炸。
3. **状态丢失**：前五步成功、第六步失败，没有断点，只能从头再来——而前面可能已经产生了副作用（发过通知、写过库）。

## 做法

我们的原则是：**重试放在工具层，决策放在 Agent 层，状态放在磁盘上。** 分四步：

**1. 工具层做错误分类与重试。** 在 MCP 工具/插件封装里把错误分成两类：瞬态（超时、429、5xx）和永久（401、403、参数错误）。瞬态错误用指数退避 + 抖动重试，上限 3 次；永久错误直接返回结构化失败。这一切发生在代码里，Agent 只看到最终结果。

**2. 统一返回信封。** 工具结果固定为 `{ok, data, error: {type, retryable, message}, meta: {ts, source}}`。Agent 拿到的是可判断的结构，而不是一坨堆栈字符串——这是避免幻觉兜底最有效的一招。

**3. 给每条关键路径准备降级方案。** 缓存快照、备用供应商、或者"跳过并标记"。在系统提示里明确写死规则：某工具失败时，优先读缓存并注明数据截止时间；没有缓存就暂停任务并向人报告，禁止自行编造。

**4. 断点与熔断。** 每个有副作用的步骤执行前，把计划与已完成步骤落盘，失败后从断点恢复。同一工具连续失败 N 次触发熔断，冷却窗口内切换到降级路径或挂起工作流。

## 踩坑点

- **别在提示词里做重试**。语言模型的"重试"没有退避、没有上限，重试策略必须是代码。
- **401 也重试是纯浪费**。先分类再重试，认证错误该走的是告警，不是循环。
- **超时要设单次上限**。一次 60 秒的挂起会卡死整个 Agent 循环，宁可快速失败进入重试。
- **非幂等操作不能裸重试**。"创建工单"重试三次可能生成三张工单，用幂等键或先查后建。
- **降级数据必须带时间戳**。否则 Agent 会把昨天的缓存当成实时数据，自信满满地输出错误结论。
- **区分"空结果"和"出错"**。很多 API 返回 200 + 空数组，别让 Agent 把它当失败去重试。

## 可复用建议

- 把错误信封和重试策略做成公共封装，所有插件统一接入，别每个工具各写一套。
- 长任务开工前先做一次轻量健康检查（打一次低成本接口），失败就别启动。
- 在系统提示里维护一份"降级决策表"：工具 → 失败 → 动作，三列，越短越好。
- 日志里记录每次调用的耗时、状态码、重试次数，故障率突增时先看图再猜。

## 总结

错误恢复不是提示词工程问题，是系统工程问题。把机械的重试交给工具层，把"失败后怎么办"的判断交给 Agent，把恢复的依据落在持久化状态上。三层各司其职，外部 API 挂掉时，你的 Agent 才能从"整段报废"变成"降级完成、事后可查"。
