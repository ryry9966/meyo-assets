## 背景

跑 Agent 自动化的人迟早都会遇到：流程编排得好好的，某个 MCP 工具背后的外部 API 突然 503、限流、或者干脆超时。传统服务挂了就是报错，但 Agent 挂法要花哨得多——它会疯狂重试烧 token，会编一个"看起来合理"的假结果，也可能在一个工具上死循环，把本来能救回来的任务整个拖死。

这篇帖子里，我梳理一下自己在 OpenClaw 流程里处理外部 API 故障的一套做法，核心思路一句话：**重试交给代码，判断交给模型，诚实交给用户。**

## 问题：Agent 的失败模式和传统服务不一样

- **LLM 驱动的重试不可控**：让模型自己决定"再试几次"，它要么一次就放弃，要么循环调到天荒地老。
- **幻觉式降级**：工具返回错误后，模型有时不承认失败，而是"推测"一个结果继续往下走，这比直接报错危险得多。
- **错误污染上下文**：把一整页 HTML 错误页或堆栈塞进对话，轻则浪费 token，重则诱导模型去"解析"这些垃圾。
- **超时不等于失败**：写操作超时后请求可能已经成功，盲目重试会造成重复创建。

## 做法

**1. 在工具层做错误分类。** 429、503、超时属于可重试；401、400、404 属于重试也没用。这一步在 MCP 工具封装里用代码判断，不要指望模型看状态码。

**2. 有界重试 + 指数退避 + 抖动。** 重试逻辑写在封装层，比如最多 3 次，间隔 1s/2s/4s 加随机抖动。必须有上限，并且抖动不能省——否则 API 恢复瞬间你的所有并发任务会一起砸过去。

**3. 给模型结构化的错误信封。** 工具失败时返回类似 `{"status": "unavailable", "retry_after": 30, "hint": "provider degraded"}` 的紧凑结构，而不是原始报错。模型拿到这个才知道该等、该换路、还是该上报。

**4. 建降级链。** 主 API → 备用 provider → 本地缓存（标注数据时间）→ 明确告知用户"当前只能给出降级结果"。关键是最后一环：宁可少给，不要编造。

**5. 加断路器。** 连续 N 次失败后，把该工具标记为不可用并冷却一段时间，Agent 规划时直接绕开，避免每个任务都去撞一遍墙。

**6. 长任务做检查点。** 多步骤工作流把中间状态落盘，恢复时从最后一个成功步骤续跑，而不是从头再来。

## 踩坑点

- **写操作重试没做幂等**：POST 超时后直接重试，结果创建了两个订单。带幂等键，或者重试前先查一次。
- **静默降级**：拿两小时前的缓存数据当实时数据用，用户不会原谅这种"善意的谎言"。降级必须显式声明。
- **断路器太敏感**：provider 偶发抖动就熔断，反复开关比不熔断还乱。冷却时间和阈值要按实际 SLA 调。
- **退避太长**：单次等 60 秒，整个任务预算早就爆了。退避上限要小于任务总超时。

## 可复用建议

1. 给所有 MCP 工具封装统一的错误信封格式，一次定义，处处受益。
2. 在会话状态里维护一份"工具健康表"，Agent 规划时可以直接参考。
3. 每次重试/降级/熔断都打日志，带原因码，事后复盘全靠它。
4. CI 里放一个可以随时 kill 的 mock API，专门测故障路径——故障处理逻辑不测就等于没写。
5. 降级策略写成配置，别写在 prompt 里靠模型"记住"。

## 总结

外部 API 挂掉不是异常，是常态。Agent 的错误恢复本质上是个系统工程问题：代码层负责重试、熔断、幂等这些确定性的事；模型层只负责根据结构化信息做路线判断；而对用户，永远如实告知数据来自哪里、是不是降级结果。把这三层职责分清楚，你的 Agent 才能在依赖抖动时依然体面地跑完任务。
