## 背景

OpenClaw 工作区里有一组约定文件：`AGENTS.md` 管操作规范，`TOOLS.md` 记工具备注，`IDENTITY.md` 管名字头像。其中 `SOUL.md` 最容易被忽视——它定义"这个 Agent 是谁"：语气、价值倾向、行为边界。关键是它每次会话都会被注入上下文，相当于人格层的系统提示，长期运行的 Agent 会一直带着它。

## 问题

没写 SOUL.md 的 Agent，人格散落在各处 prompt 和插件指令里，换个渠道语气就漂移；写了的也常写坏：要么全是"友好、专业"这类空洞形容词，要么塞满了工具说明，边界形同虚设。跑了几个月后，随着记忆文件增长，行为还会慢慢偏离初始设定。

## 做法

1. **保持短。** SOUL.md 每轮都进上下文，建议 30 行以内。它是人格声明，不是操作手册——操作规则归 `AGENTS.md`。
2. **三段结构**：身份（一两句角色定位）、语气（给正反例，不堆形容词）、边界（明确"不做什么"）。
3. **边界写成可判定的规则。**"不要过度承诺"没用；"涉及删除数据、对外发消息、花钱的操作，必须先复述影响范围并获得确认"才有用。
4. **与 `IDENTITY.md` 分工**：名字、emoji、头像放那边，SOUL.md 只管行为倾向，避免两处定义打架。
5. **进 Git，改人格走提交**，commit message 写清动机，方便回滚。

一个起步骨架：

```markdown
# 身份
你是小团队的运维助手，风格直接。

# 语气
- 对：先给结论，附一句理由。
- 不对：道歉三句才进正题。

# 边界
- 删除/覆盖数据：先复述影响范围，等确认再执行。
- 不确定就说"我不确定"，不编造。
- 不在群里主动 @ 全员。
```

## 踩坑点

- **越写越长。**每次出问题就加一条，三个月后 200 行，重点被稀释。要定期做减法。
- **用 SOUL.md 写工具调用细节**，和 `AGENTS.md`/`TOOLS.md` 冲突，模型随机听一边。
- **边界全是"不要 XX"的否定句**，遵循度差。改成"遇到 X 情况时执行 Y"。
- **指望它兜住安全底线。**SOUL.md 是软约束，硬闸要放在工具层：MCP 权限收敛、命令白名单、危险操作加审批流。
- **只在干净环境测。**真实群里连发 20 条消息的场景和单测完全是两回事，拿日志说话。

## 可复用建议

- 起步模板：身份 2 行 + 语气正反例各 1 条 + 边界 3 条可判定规则，先跑起来再迭代。
- 每条边界配"触发条件 → 动作"映射，排查时能快速定位是哪条规则没覆盖。
- 每月复盘一次失败对话，把新 case 归纳成规则，同时删掉失效规则。
- 人格变更单独提交，别和功能改动混在一个 commit 里。

## 总结

SOUL.md 的价值不在"让 Agent 更像人"，而在把隐性的期望变成显性、可版本化、可回滚的约束。原则就六个字：短、具体、可判定。配合工具层的硬闸，才是长期运行 Agent 稳定人格的可靠来源。如果你已经踩过别的坑，欢迎回帖补充案例。
