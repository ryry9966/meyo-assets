## 背景

用 OpenClaw 跑了一段时间日常自动化后，最明显的瓶颈不是模型能力，而是主 Agent 的串行执行。让它"调研 5 个仓库的 MCP 实现、分别总结、再做一遍兼容性检查"，它会一条条排队做，context 越滚越大，中途一个任务卡住，后面全部跟着等。

subagent 编排解决的就是这个问题：主 Agent 只做拆解和汇总，脏活下发给多个并行的 subagent，各自带独立 context 和受限权限。

## 做法

以"批量审查多个模块代码并出报告"为例，我的编排流程分四步：

1. **拆任务**。主 Agent 把总目标切成互不依赖的子任务，每个写清楚：目标、输入、边界（只准碰哪个目录）、输出格式。拆分原则是"改动的文件集合不相交"，这是能并行的前提。
2. **起 subagent**。每个子任务起一个 subagent，prompt 用统一模板：目标 + 范围 + 禁止事项 + 返回格式。工具权限按需给，能只读就不给写。
3. **并行跑，限制并发**。同时最多 3~5 个。产出强制为结构化摘要：状态（成功/失败）+ 结论 + 产物路径，禁止把完整日志塞回主线程。
4. **主 Agent 汇总**。收齐结果后做二次判断：失败的子任务决定重试，还是降级为串行处理。

## 踩坑点

- **两个 subagent 改同一个文件**。并行写冲突比想象中容易发生，哪怕任务描述里写了边界。现在每个 subagent 用独立工作目录，最后由主 Agent 统一合并。
- **subagent 静默失败**。返回空结果时，主 Agent 容易当成"没问题"。返回格式里必须有显式 status 字段，缺字段一律按失败处理。
- **并发一开就烧 token**。8 个 subagent 同时跑，一轮下来成本触目惊心，还容易撞上 API 限流。并发上限 3~5 是我实测比较稳的区间。
- **返回内容太长**。subagent 稍微"热心"一点就会把中间过程全写回来，主 Agent 的 context 立刻被污染。模板里明确"只返回结论和产物路径"很关键。
- **非幂等操作别下放**。发消息、部署这类动作不要交给并行 subagent 随手执行，收敛到主 Agent 串行做。

## 可复用建议

- 先串行跑通一次，确认拆分合理，再开并行。并行只是加速手段，不是设计起点。
- subagent prompt 模板固定下来，放进插件或脚本里复用，别每次手写。
- 每个 subagent 的输入输出落盘留档，出问题能回放定位，不用靠回忆。
- 任务粒度控制在"单次会话能独立完成"的量级，太大了等于没拆。

## 总结

subagent 编排的核心不是"快"，而是隔离：主 Agent 保持干净的调度视角，subagent 各自带着受限的 context 和权限去做一件小事。把拆分边界、返回格式、并发上限这三件事定死，并行带来的收益就是稳定的；定不死，它带来的混乱会比速度更明显。
