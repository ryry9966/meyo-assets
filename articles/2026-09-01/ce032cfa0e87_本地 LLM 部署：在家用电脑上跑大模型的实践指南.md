## 背景

过去一年我把不少自动化任务从云端 API 迁到了本地模型。动机很朴素：隐私（对话和工具调用日志不想出内网）、成本（Agent 高频调用时 token 费用累积很快）、以及断网可用。这篇帖记录我在一台 32GB 内存 + 16G 显存显卡的家用机上跑 7B~14B 模型的完整过程，重点面向想把本地模型接进 Agent / MCP 工具链的场景。

## 问题

本地部署的核心矛盾是显存。模型权重 + KV cache + 运行时开销都要挤进 VRAM，一旦溢出就回落到内存甚至磁盘，速度断崖式下跌。另外，Agent 场景对模型的要求和聊天不同：结构化输出（JSON、函数调用）的稳定性比“回答像不像人”重要得多，这也是很多人本地模型玩不转 Agent 的根因。

## 做法与步骤

1. **盘清硬件**。显存决定上限：8G 跑 7B Q4 量化比较从容；16G 可以摸到 14B；32G 以上再考虑 32B。纯 CPU 也能跑，但速度通常只够异步批处理。
2. **选运行时**。推荐 llama.cpp 或 Ollama 起步，一条命令拉模型，自带 OpenAI 兼容端点；追求吞吐再上 vLLM 或 llama-server 的 continuous batching。
3. **选模型**。中文环境优先 Qwen 系列；做函数调用务必选官方标注支持 tool use 的版本，别用社区魔改的 merged 模型当 Agent 主力。
4. **量化选择**。Q4_K_M 是性价比拐点，Q8 几乎无损但显存翻倍。Agent 工具调用建议 Q5 以上，Q4 以下偶发 JSON 字段错乱。
5. **接入 Agent**。运行时启动后暴露 `/v1/chat/completions`，把 Agent 框架或 MCP 客户端的 base_url 指过去即可，同时把 timeout 放宽——本地首 token 延迟比云端高。

## 踩坑点

- **KV cache 是隐形杀手**。上下文从 4k 拉到 32k，显存占用可能翻倍，OOM 常发生在“权重明明装得下”的时候。启动参数里显式限制 context 长度。
- **量化伤工具调用**。小模型 + 激进量化，函数调用参数容易漏字段。宁可换小一档的模型，也不要压到 Q3。
- **长上下文拖慢一切**。重复 system prompt 的开销很大，确认运行时开启了 prompt caching，实测能省一半以上的预填充时间。
- **散热降频**。长时间 Agent 循环调用让显卡持续满载，笔记本用户尤其注意，实测降频前后速度能差 30%。

## 可复用建议

- 显存粗算公式：参数量(B) × 量化位宽 ÷ 8 ≈ 权重 GB，再预留 20%~50% 给 KV cache 和运行时。
- 主力和轻任务分开：14B 做规划与复杂工具调用，7B 做摘要、分类这类高频低难度任务，用路由规则分发。
- 别追求全本地。混合架构（本地处理敏感数据、云端处理长上下文推理）往往是最优解，按任务敏感级别路由。

## 总结

本地 LLM 在家用硬件上已经完全可用，但它的定位是“特定任务的专业工兵”，不是云端旗舰的平替。把模型选型、量化档位、上下文长度这三件事想清楚，再接进 Agent 工具链，体验会好很多。欢迎在评论区交流各自的硬件配置和实测速度。
