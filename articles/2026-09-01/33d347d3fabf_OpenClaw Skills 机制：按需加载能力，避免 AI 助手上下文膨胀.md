## 背景

在 OpenClaw 或类似 Agent 框架的实践中，很多团队习惯把工具、脚本、外部 API 等能力一次性注入系统提示或工具列表。早期演示阶段没有问题，但进入实际业务后，能力数量会从几个快速增长到几十个。每次请求都携带完整工具定义，不仅推高 token 消耗，模型在大量无关工具中做选择也更容易出错。

OpenClaw Skills 机制的核心思路是：把能力拆分为独立 skill，通过声明式描述与触发条件，由技能管理器在会话中按需加载，而不是全量常驻。

## 问题

如果所有能力常驻上下文，会带来几个典型痛点：

- **上下文膨胀**：无关技能说明挤占窗口，长对话后期可用空间变少。
- **工具干扰**：模型面对过多相似工具，容易出现选错、遗漏或参数混淆。
- **维护成本**：新增一个技能需要修改全局配置，回归测试范围大。
- **权限边界**：高权限能力常驻，安全风险增加，尤其是写操作或敏感数据访问。

## 做法 / 步骤

下面是一套可落地的 Skills 机制实现思路，适合在 OpenClaw 项目中使用。

### 1. 定义技能元数据

每个 skill 至少包含：`name`、`description`、`triggers`、`tools`、`permissions`、`deps`。示例：

```yaml
name: git-issue
description: 创建、查询、更新 Git 仓库 issue
triggers:
  keywords: [issue, bug, 缺陷]
  intent: create_issue
tools:
  - git_create_issue
  - git_list_issues
permissions: [repo:write]
deps: [git-auth]
```

### 2. 触发识别

在会话预处理阶段，先用轻量规则或小模型判断用户输入命中了哪些 skills。可以基于关键词、意图分类或 embedding 相似度。这个阶段不加载技能本体，只输出候选 skill 列表，尽量控制开销。

### 3. 动态加载

SkillManager 根据候选列表，把对应 system prompt 片段、工具 schema、few-shot 示例注入当前会话，同时注册工具到运行时。未命中的 skill 不进入上下文，从而减少 token 占用和工具干扰。

### 4. 生命周期管理

加载后可以设置 TTL 或按对话轮数自动卸载。常用技能可以常驻，低频技能用后即释放，保持上下文干净。

### 5. 监控与回退

记录每个 skill 的触发命中率、平均 token 增量、工具调用成功率。若技能加载失败或工具执行超时，回退到最小可用模式，只保留基础对话能力。

## 踩坑点

在实际使用中，这几个问题比较常见：

- **触发条件写得太宽**：比如 `keywords` 包含“查询”，几乎所有问题都会命中，退化为全量加载。建议用更具体的 intent 或短语组合，并限制单次最多加载 3-5 个 skills。
- **描述与用户表达不一致**：用户问“怎么提 bug”可能不会出现“创建 issue”。需要在 `triggers` 中补充口语化表达，或用少量样本做 paraphrase。
- **依赖冲突**：两个 skill 依赖不同版本的同一库，或工具名重复。加载时要做命名空间隔离，例如 `git.issue.create`。
- **加载顺序不稳定**：模型对 system prompt 拼接顺序敏感。建议固定 skill 加载顺序，或按优先级排序后注入。
- **权限未确认**：高权限技能被触发后直接加载，可能带来风险。可以在加载前加入确认步骤，或默认只读，写操作需要用户确认。

## 可复用建议

- 技能保持单一职责，一个 skill 只做一件事，方便组合与测试。
- 用结构化元数据管理版本、作者、依赖、权限，便于审核和追溯。
- 建立触发准确率回归集，每次修改 `triggers` 后跑一批典型 query 验证命中。
- 监控 token 预算，如果平均增量超过阈值，优先优化描述或拆分技能。
- 为高权限操作增加人工确认或二次校验，避免动态加载扩大攻击面。

## 总结

OpenClaw Skills 机制的价值不在于多一个工具列表，而是把能力从“常驻上下文”变成“按需挂载”。通过元数据、触发识别、动态加载、生命周期管理与监控回退，可以显著降低上下文占用，减少工具干扰，同时保持系统可维护性和安全边界。如果你的 OpenClaw 项目已经感受到上下文压力或工具选择混乱，可以尝试从一个小而清晰的技能开始，逐步迁移，而不是一次性重构所有工具。
