## 背景

用 OpenClaw 这类 Agent 做内容自动化，产出格式几乎默认是 Markdown：LLM 写得顺手，MCP 工具、静态站点、笔记库也都认。但"生成"到"发布"之间隔着一段常被低估的距离——同一份 .md，发到公众号、知乎、掘金、GitHub Pages，效果各不相同。

## 问题

四个典型痛点：

1. **平台方言差异**：GFM 表格、任务列表、脚注、数学公式，各平台支持程度参差；
2. **LLM 输出不稳定**：同一 prompt，这次是标准 Markdown，下次夹一段内联 HTML，标题层级随手跳；
3. **资源引用失效**：本地相对路径的图片、未上传的附件，发布即断链；
4. **手工适配不可持续**：每接一个新平台，就要重做一遍格式清洗。

## 做法

核心思路是"一次规范化，按端适配"，管线拆四段：

**1. 捕获与约束。** 在 Agent 的 system prompt 和输出 schema 里限定：只允许 CommonMark + GFM 子集，禁用内联 HTML 和脚注。管线是兜底，不是唯一防线。

**2. 规范化。** 用 remark/unified（或 pandoc）把 Markdown 解析成 AST，在这一层清洗：标题层级归一、深嵌套列表拍平、段落内硬换行合并、HTML 节点剥离或降级。所有操作基于 AST，不要用正则改写 Markdown 文本。

**3. 端适配。** 每个平台写一个 mdast transformer，按"方言矩阵"转换节点：公众号不支持 GFM 表格，就降级为简化结构；知乎剥掉任务列表，就转普通列表。规则集中在一个配置文件里，可审查、可测试。

**4. 资源处理与校验。** 图片先上传图床/对象存储并回写 URL；最后跑 lint（markdownlint + 自定义规则），目标平台不允许的节点类型直接报错，不静默丢弃。

整条管线封装成一个 MCP tool 或 Agent skill：Agent 只负责产出规范 Markdown，发布侧的脏活全部下沉。

## 踩坑点

- **正则改写是最大的坑。** Markdown 嵌套结构用正则处理必出事，尤其代码块里的 `*` 和 `_`。
- **幂等性。** 同一篇文档可能被管线跑多次，转义和转换必须幂等，否则 `*` 会被反复转义成 `\*`。
- **代码块语言标记**：别删，但也别指望所有平台都识别，高亮失败的降级方案要提前想好。
- **公式记法**：`$...$` 与 `\(...\)` 各平台表现不一，规范化阶段统一成目标端支持的写法。
- **别信"支持 Markdown"的承诺**：用样例文档做快照测试，每次改动对比渲染结果。

## 可复用建议

- 维护一张**平台方言矩阵**：节点类型 × 平台，标注允许/降级/禁止三态，接新平台只填表；
- 准备 3~5 篇覆盖全特性的样例文档（长表格、深嵌套、代码、公式、图片），作为固定测试集；
- 对未知节点类型默认**报错而非忽略**，fail closed；
- Agent prompt 约束 + 管线校验双保险，缺一不可。

## 总结

这条管线没有黑科技，价值在于把格式适配从每次发布的手工劳动，变成可测试、可复用的工程资产。Agent 负责内容，管线负责形态；边界划清之后，接入一个新平台就只是多写一个 transformer 的事。
