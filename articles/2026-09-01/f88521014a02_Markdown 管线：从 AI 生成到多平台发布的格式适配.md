## 背景

在 OpenClaw、Agent、MCP 和插件驱动的自动化发布里，Markdown 几乎已经成为模型输出的默认格式。模型产出一篇文章、一段总结或一个卡片后，下一步往往是把这份 Markdown 推到微信公众号、知乎、掘金、Notion、GitHub、Mastodon 等不同平台。但“能生成 Markdown”和“能稳定发布到多平台”之间，隔着一条容易被人低估的格式适配链路。

不少团队的做法是：模型输出什么就直接发，哪里报错就补一个 if-else；平台不支持表格，就临时加一个函数把表格转成图片；微信代码块高亮不对，就再包一层转换。结果一段时间后，发布代码里堆满了平台专属的胶水逻辑，每一次模型升级或平台规则变化都要牵一发动全身。

这篇文章想整理一条相对稳定的 Markdown 管线：从 AI 生成时的约束，到中间规范化，再到多平台适配和发布检查。重点不是追求“一次生成完美”，而是把链路拆开，让每一步都可测试、可替换。

## 问题

实际踩到的坑主要有几类：

1. **模型输出不稳定**：有时候用 ATX 标题（`#`），有时候用 Setext 标题（`===`）；代码块可能不带语言标识；列表缩进有时是两个空格，有时是四个；偶尔还会把 YAML frontmatter 泄漏到正文。
2. **平台渲染差异大**：微信公众号对 Markdown 支持有限，代码块、表格、链接卡片都需要额外处理；知乎编辑器不支持原生表格；Notion 的 block 导入有嵌套层级限制；Mastodon 限字符数，标题和列表会显得非常啰嗦。
3. **资源链接和图片问题**：模型给的图片链接可能是临时图床，或者相对路径；发布后图片几天就失效，代码块里的语言标签到了平台侧变成乱码。
4. **HTML 和特殊字符**：模型为了排版效果会插入 `<div>`、`<br>`、`<iframe>`，但很多平台会直接过滤或转义；`@`、`#`、`---` 等符号在特定平台会触发 mention、话题或分割线，导致内容被意外截断。

如果这些逻辑都写在发布脚本里，很快会变成一坨难以维护的胶水代码。

## 做法/步骤

我现在的管线大致分成四层：生成约束、解析规范化、中间表示、平台适配器。

**1. 生成侧约束**

在 Agent 的 system prompt 或工具描述里明确要求模型只输出受限的 Markdown 结构。例如：

- 正文只允许使用 `#`、`##`、`###` 三级标题，不允许 Setext 标题。
- 代码块必须带语言标识，如 ` ```python `。
- 禁止内嵌 HTML，禁止 frontmatter，禁止 shortcode。
- 图片必须使用绝对 URL；表格最多 4 列，超过就拆成列表。
- 链接使用标准 `[text](url)` 形式。

约束不是为了让模型完全听话，而是为了在解析层减少分支。即使模型偶尔越界，后面也有兜底。

**2. 解析与规范化**

无论 Markdown 来自 OpenAI、Claude 还是本地文件，统一先经过一个规范化模块。我用的是 `unified` 生态里的 `remark-parse` 和 `remark-stringify`，在 AST 层做修复：

- 强制统一标题层级：如果第一级标题出现多个，自动降级或合并。
- 修复代码块：补齐缺失的语言标识，用空行分隔代码块和正文。
- 统一列表缩进为四个空格或标准列表节点。
- 移除 YAML frontmatter 并提取 `title`、`summary`、`tags` 等元数据。
- 清洗 HTML：白名单之外的全部转义或删除。
- 图片相对路径统一解析为绝对地址，并检查 URL 是否可达。

这层的输出是一个干净的、平台无关的 AST 或中间对象。

**3. 中间表示**

不建议让每个平台适配器直接面对 Markdown 字符串。可以定义一个轻量 schema，比如：

```
{
  meta: { title, summary, tags, cover },
  blocks: [
    { type: "heading", level: 2, children: [...] },
    { type: "paragraph", children: [...] },
    { type: "code", language: "python", value: "..." },
    { type: "table", headers: [...], rows: [...] },
    { type: "image", url: "...", alt: "..." }
  ]
}
```

适配器只面向这个 schema 编程，不关心原始 Markdown 长什么样。同时保留一份原始 Markdown 和内容哈希，用于幂等发布和回溯。

**4. 平台适配器**

每个平台实现一个 renderer，输入中间 schema，输出平台需要的格式：

- **微信公众号**：先把 Markdown 转成带内联样式的 HTML，再交给排版工具处理代码块和表格；表格过大时自动转成图片。
- **知乎**：表格转成列表或图片，代码块语言标签映射到知乎支持的语言列表。
- **Notion**：用 blocks API 导入，但注意嵌套层级不能超过 2 层，否则拆分成多个 block。
- **GitHub / 静态博客**：直接输出规范化后的 Markdown，保留原始代码块和表格。
- **Mastodon**：只保留 `summary` 和正文第一段，链接放到尾部，去掉标题符号和多余空行。

适配器要保持无状态、纯函数式。不要在适配器里做业务判断或调用外部服务，外部操作（上传图片、鉴权）统一放到发布层。

**5. 发布检查**

在本地或 CI 中加入 `markdownlint` 和自定义规则检查；对每篇内容生成 HTML 快照或截图做 diff；发布前用平台预览接口或草稿箱确认格式。

## 踩坑点

- **代码块语言丢失**：模型有时输出 ``` 但忘了语言，或语言写错（`py`、`python3`）。规范化时要维护一个语言别名表，把常见简称映射到标准名，并在平台适配器里再映射到平台支持的语言。
- **表格被平台压扁**：微信和知乎对表格列数、单元格长度敏感。我的做法是超过 4 列或单元格过长时，直接转成图片或列表，不要硬推。
- **YAML frontmatter 泄漏**：模型可能把 `---` 开头的 metadata 写进正文，解析层要先于渲染层剥离，并把 `---` 转义为普通分割线。
- **图片临时链接**：发布前最好自动下载图片并上传到自有 OSS 或平台图床。相对路径在本地能显示，发布后就全挂。
- **MCP/插件调用顺序**：如果 MCP 工具链里同时有“总结”和“发布”两个步骤，尽量把规范化放在总结之后、发布之前，避免模型输出直接流入适配器。

## 可复用建议

- 把“规范化”和“平台适配”做成两个 MCP 工具或插件，Agent 在发布前自动调用。工具参数只需要目标平台名和内容哈希。
- 平台差异配置放在 YAML/JSON 里维护，不要散落在代码分支。新增平台时只加配置和 renderer，不改核心解析逻辑。
- 保留原始 Markdown 和中间 schema 的版本记录，发布失败时方便对比是什么变化导致的。
- 不要完全依赖 `pandoc` 这类转换器做最终发布。它可以用来快速调试，但生产环境还是要在 AST 层做定制后处理。
- 对于多平台同步，先在单个平台把格式调通，再扩展其他平台。不要一上来就写一个“万能适配器”，那样会陷入平台特例的泥潭。

## 总结

Markdown 管线从 AI 生成到多平台发布，核心不是让模型输出完美格式，而是把生成、规范化、适配、发布拆成独立的层。每层只做一件事，错误可以定位，平台可以替换。对于 OpenClaw 这类多 Agent、多插件、多平台的自动化场景，这种分层思路比一把梭的胶水代码要可靠得多。
