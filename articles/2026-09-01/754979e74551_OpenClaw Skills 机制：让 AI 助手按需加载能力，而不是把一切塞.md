## 背景

OpenClaw 的 Skills 是一套"渐进式披露"的能力加载机制，核心是三层结构：

1. **元数据层**：启动时模型只看到每个技能的 `name` + `description`，几乎不占上下文；
2. **正文层**：任务匹配时，才把完整的 `SKILL.md` 读进来；
3. **资源层**：正文里引用的脚本、模板、参考文档，用到时才展开。

也就是说，装 20 个技能和装 2 个技能，常驻成本可能差不多——前提是你按这个机制来写。

## 问题

我之前的做法是把常用操作流程全部写进系统提示词，结果两个问题：一是上下文常年挂着几千 token，绝大多数会话根本用不上；二是内容一多，模型注意力被稀释，真正要执行的流程反而做得不严格。后来又装了一批 MCP server，工具列表爆炸，问题更明显。Skills 正好是用来解这个的，但写得不对，它会退化成"换了个地方堆提示词"。

## 做法

1. **建目录**：个人技能放 `~/.openclaw/workspace/skills/<skill-name>/SKILL.md`，可复用、跨机器的放全局 skills 目录。
2. **写 frontmatter，重点是 description**。它是模型决定是否加载的唯一依据，要写成触发条件式的句子，包含你平时描述这类任务的关键词。比如"当需要批量重命名截图、按日期归档图片时使用"，而不是"图片工具"。
3. **正文当入口索引用**，控制在几十行：步骤骨架、边界条件、何时调用哪个脚本。参数表、长流程这类细节拆到同目录的 reference 文件，正文里用相对路径引用。
4. **能用脚本的不用散文**。确定性操作（调 API、处理文件）写成脚本放进技能目录，让助手执行脚本，而不是每次自由发挥。
5. **用一个真实任务验证**：观察是否触发、加载了哪些文件。没触发，先改 description，而不是往正文里堆内容。

## 踩坑点

- **description 太泛**（如"帮你处理文件"）会频繁误触发；**太窄**则永远不触发。写完问自己：我会用什么话向助手描述这个需求？
- **把所有细节塞进 SKILL.md**，等于把系统提示词的问题原样复发，渐进式披露就失效了。
- **frontmatter 的 YAML 格式错误会导致技能被静默跳过**。每次改动后，在 CLI 或控制台的技能列表里确认它还在、状态正常。
- 技能里引用的脚本记得 `chmod +x`，路径用相对技能目录的路径；**不要把 token 写死在 SKILL.md 里**，走环境变量。
- 技能装太多，元数据本身也在积累。定期审计，停用不再用的。

## 可复用建议

- **一个技能 = 一个能力**，组合优于大而全的巨型技能。
- 把个人技能目录放进 git 仓库：多机同步、改动可回滚，也方便分享给团队。
- 调优顺序固定下来：先 description，再正文结构，最后才加资源文件。90% 的"技能不生效"问题出在第一层。
- 把"这次会话加载了什么"当作健康指标：如果模型经常加载了用不上的技能，先收紧 description。

## 总结

Skills 机制的价值不在"能装多少"，而在"默认加载了多少"。把元数据当索引写、把正文当入口写、把确定性逻辑下沉到脚本，助手才能在需要时精准取用能力，上下文保持干净。这套写法成本低——一个文件夹加一个 Markdown 文件就能起步，建议从把你最常重复口述的那个流程做成第一个技能开始。
