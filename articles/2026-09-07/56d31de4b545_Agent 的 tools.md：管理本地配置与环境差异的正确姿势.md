## 背景

跑 Agent 做自动化久了，你会发现同一个任务在这台机器上顺利跑通，换一台就翻车：路径不对、包管理器不一样、Docker 没装、端口被占。根因大多不是模型能力问题，而是 Agent 缺一份“这台机器到底长什么样”的事实清单。tools.md 就是干这个的：一个让 Agent 启动时读取的环境说明文件，思路类似 AGENTS.md，但聚焦在工具与环境本身。

## 问题

常见的错误姿势有三种：

1. 把环境假设硬编码进 prompt 或 skill，比如“用 brew 安装”，到了 Linux 上直接失败；
2. 每次都让 Agent 现场探测环境，浪费大量 token，还可能得出错误结论；
3. 配置散落在多个文件里，改了一处忘了另一处，Agent 拿到的是过期信息。

## 做法

我的方案是分层维护两份文件：

- **仓库级 `tools.md`（提交到 git）**：写可移植的事实——操作系统类别、默认 shell、运行时版本、工具调用约定（统一用相对路径、输出重定向到哪个目录）、禁止事项（不动系统目录、不做全局安装）。
- **机器级 `tools.local.md`（加入 .gitignore）**：写本机特有信息——绝对路径、本地服务端口、代理设置、GPU 等资源差异。

落地步骤：

1. 先做一次清点：把实际能跑通的命令逐条记录，`python3 --version`、`docker info` 这类，别凭记忆写；
2. 按上面的分层写两份文件，每条信息“一行一事”，可验证；
3. 文件末尾写明优先级：local 覆盖 base，冲突时以 local 为准；
4. 给 Agent 加一条指令：执行失败且怀疑环境问题时，先查 tools.md，再提修改建议，而不是反复硬试；
5. 工具链变动后更新文件并标注日期，当代码一样 review。

## 踩坑点

- **密钥写进文件**：tools.md 会被 Agent 全文读入，也容易被截图、被同步。密钥一律引用环境变量名，不写值。
- **写“应该有”而不是“实际有”**：过期文档比没有文档更糟，每条尽量附验证命令。
- **文件太长**：它是上下文不是文档站，超过一屏就该砍，Agent 用不到的别写。
- **和 AGENTS.md 重复**：职责分清——AGENTS.md 写行为规范，tools.md 写环境事实，互相引用而不是复制。
- **忽略 shell 差异**：PowerShell 和 bash 的语法差异足以让脚本全挂，文件里显式声明 shell。
- **local 文件忘了 gitignore**：个人路径和内网地址跟着仓库泄出去，这类事故我见过不止一次。

## 可复用建议

- 把 tools.md 当代码管：进 review、有变更记录、有负责人。
- 模板只需五段：环境概况、可用工具清单（含验证命令）、路径约定、服务与端口、禁止事项。
- 让 Agent 参与维护：允许它提出“检测到 X 不可用，建议更新 tools.md”，人确认后合入，比纯人工维护鲜活得多。
- 新环境部署时跑一遍冒烟脚本：按文件逐条验证，不过关的当场修。

## 总结

tools.md 的价值不在文件本身，而在于把“环境差异”从隐性踩坑变成显性契约：仓库级管共识，本地级管个性，密钥永远不落盘。做完这一步，Agent 在不同机器上的行为稳定性会有肉眼可见的提升——这是我在多个项目里反复验证过的、投入产出比最高的一类工程化改造。
