## 背景

Agent 的能力边界，基本由外部依赖决定：LLM 推理接口、MCP 工具、各类插件和第三方 API。本地跑通的那一刻很爽，但进了生产环境，外部 API 挂掉不是“会不会发生”的问题，而是“什么时候发生、以什么姿势发生”的问题。

传统 Web 服务挂了，最多报个 500；Agent 挂了，症状往往更隐蔽——无限重试烧 token、模型编一个“看起来合理”的结果糊弄过去、或者带着脏数据跑完整条流水线。错误恢复不是锦上添花的健壮性优化，而是 Agent 设计的一部分。

## 问题：Agent 会放大故障

同样是下游 API 超时，普通程序会抛异常停下来，Agent 却倾向于“继续想办法”。模型的自然反应是立刻重试、换个姿势重试，甚至在不告诉你的情况下跳过失败步骤继续往下走。结果是：故障被放大成 token 消耗、限流封禁和静默的错误数据。所以恢复策略必须由代码兜底，不能指望模型自觉。

## 做法：四层防线

**1. 超时 + 指数退避重试。** 先给每次调用设硬超时，避免单次请求卡死整个循环。重试要分类：4xx（除 429）不重试，5xx、超时、网络错误才重试；指数退避加随机抖动，上限 3 次左右。不要把重试节奏交给模型——它看到报错的第一反应往往是立刻再试一次，等于在服务端高负载时再踩一脚。

**2. 熔断。** 连续 N 次失败后进入熔断状态，冷却期内直接快速失败，不再打真实请求；冷却结束进入半开状态，放行一次探测请求确认是否恢复。这保护的不只是下游，还有你自己的重试预算。

**3. 降级与兜底。** 提前准备备选路径：备用 API、本地缓存、或干脆明确告知“该工具暂不可用”。关键是把失败作为结构化数据返回给模型，比如 `{"status":"error","retryable":false,"reason":"upstream timeout"}`，并在系统提示里写死一条：工具失败时禁止编造结果。宁可让 Agent 回一句“查询服务暂时不可用”，也不要让它瞎编一个天气或价格。

**4. 幂等与断点续跑。** 重试的前提是幂等。读操作无所谓，写操作必须带幂等键，否则一次超时后的重试就是两次下单、两条消息。同时把中间状态落盘，恢复时从失败步骤继续，而不是整个任务推倒重来。

## 踩坑点

- 无退避的立即重试：越挂越打，429 变成事实上的永久封禁；
- 幻觉兜底：模型把报错信息当素材，编出自信满满的假答案，这是最危险的静默失败；
- 吞掉错误返回空结果：下游无法区分“没数据”和“挂了”；
- 超时设得太长（比如 60 秒），Agent 每步都等满，一个任务跑半小时；
- 熔断阈值太敏感，一次抖动就熔断，恢复后又立刻打满。

## 可复用建议

把所有工具调用收敛到一个统一的 client 层（或装饰器），超时、重试、熔断参数集中配置，不要散落在各个插件里各写一套。错误信息统一结构化，让模型“读得懂”失败原因。加一个全局降级开关，极端情况下 Agent 自动切换到“只读 + 诚实告知”模式。最后做故障注入：把 mock API 关掉完整跑一遍，看 Agent 是优雅降级还是当场发疯——这一步暴露的问题比任何 code review 都多。

## 总结

外部 API 挂掉是常态，Agent 的可靠性不取决于“永不失败”，而取决于失败之后的行为是否可预期：快速失败、有限重试、诚实降级、幂等续跑。这四件事做扎实了，Agent 才敢放到无人值守的场景里跑。
