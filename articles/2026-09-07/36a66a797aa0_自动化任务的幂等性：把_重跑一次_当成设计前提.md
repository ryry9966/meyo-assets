## 背景

在 OpenClaw 里做自动化，跑久了你会发现一件事：**任务被重复执行不是异常，而是常态**。定时任务在 agent 卡死重启后再触发一次；网络超时后 MCP 客户端重试同一次工具调用；你自己看到结果不对，手动再跑一遍。调度器、传输层、人，三个层面都在制造重复。

## 问题

问题在于我们写任务时默认"只跑一次"。一个每天汇总 issue 发到频道的 cron 任务，重试后发了两条一样的消息；一个给客户建档的插件，超时重跑建了两条记录。副作用（发消息、写库、建文件）不断叠加，排查的人以为是 bug，其实是设计里没给"重复"留位置。幂等性解决的就是这个：**同一操作执行一次和执行多次，最终状态一致**。

## 做法

核心三步：

**1. 定义确定性的幂等键。** 从业务输入推导，而不是用时间戳或随机数。比如 `hash(job_name + business_date + target_id)`——同一天对同一目标的运行，键相同。

**2. 先占位，后执行。** 执行前把幂等键写进状态存储（SQLite 一张表就够），状态分 `claimed / done`。插入冲突说明有人在跑或已跑完，直接退出；执行完改成 `done`；给 `claimed` 加过期时间，防止上次崩溃留下死锁。

```sql
CREATE TABLE runs (
  run_key    TEXT PRIMARY KEY,
  status     TEXT,      -- claimed / done
  updated_at INTEGER
);
-- 开始：INSERT，冲突则跳过
-- 收尾：UPDATE status = 'done'
```

**3. 让操作本身幂等。** 能 upsert 就别 insert；文件用固定文件名覆盖写，别递增命名；发消息改成"查有没有同键消息，有就编辑，没有才发"。

## 踩坑点

- **键的粒度错。** 太粗（整天一个键）会把合法的第二次运行也吞掉；太细（带时间戳）永远不会去重。键要对应"业务上的一次意图"，不是"进程上的一次执行"。
- **先做事后记账。** 成功后才写记录，崩溃发生在两者之间照样重复。必须先占位。
- **把超时当失败。** 请求发出去了但没收到响应，结果是未知的。正确动作是先查状态再决定，而不是无脑重试。
- **多层重试叠加。** 调度器重试 + agent 重试 + 插件内部重试，三层各来一次就是三次。去重要做在最靠近副作用的那层，幂等键向下游透传。
- **并发竞态。** "先查有没有再创建"在两个实例同时跑时会双创建。占位必须用数据库唯一约束或 SETNX 这类原子操作，别用查了再写。

## 可复用建议

- 写任何自动化任务前，先回答一个问题："**这个任务被执行两次会怎样？**"
- 优先用**对账式（reconcile）**写法：每次运行先计算目标完整状态，再把现状改成目标状态。天然幂等，手动重跑还能顺便修复漂移。
- 幂等键写进日志和产出物，出问题能追溯是哪次意图。
- 留一个跳过占位的 `--force` 出口和 dry-run 模式，别让幂等机制变成修不了的死锁。
- 写 MCP 工具/插件时，把幂等层封装在插件内部，而不是指望调用方不重复调用——agent 侧的重试你控制不了。

## 总结

自动化系统里，重复执行是常态而非异常：调度器会重试，网络会重试，人也会手滑。把幂等键、先占位后执行、reconcile 式写入变成习惯，重复就从风险变成了安全网——你甚至可以放心让任务"每天多跑几次"来对冲偶发失败。
