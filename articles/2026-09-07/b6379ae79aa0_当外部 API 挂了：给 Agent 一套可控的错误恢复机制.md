## 背景

跑 Agent 这半年，我最深的一个体会是：本地代码再稳，链路也稳不过外部依赖。搜索、天气、邮件、自建的 MCP server、各家模型 API——一次任务要串七八个外部调用。我在自己的部署里粗略统计过一周的 tool call，失败集中在三类：超时、429 限流、上游 5xx。真正因为参数写错而失败的反而是少数。

## 问题

外部 API 挂掉时，Agent 常见三种糟糕表现：

1. **无限重试烧 token**：模型收到报错后自作主张"再试一次"，循环到会话超限；
2. **顺着报错编结果**：原始异常文本喂给模型，它开始推测"可能是网络波动，数据应该是……"，然后一本正经地输出编造内容；
3. **单点拖垮全局**：一个依赖卡 60 秒，整个任务链和会话一起陪葬。

根因大多是插件把工具调用当成"要么成功、要么抛异常"，没有中间态设计。

## 做法

按顺序做这几件事：

**1. 先分类，别一刀切。** 超时 / 网络错误 / 5xx → 可重试；4xx（参数、鉴权）→ 重试没意义，直接结构化失败；429 → 尊重 `Retry-After`，或切备用通道。

**2. 重试写在插件代码里，不要写进 prompt。** 让模型负责"重试几次"完全不可控。用有界重试：3 次，指数退避 + 随机抖动：

```ts
async function callWithRetry<T>(fn: () => Promise<T>, max = 3) {
  for (let i = 0; i < max; i++) {
    try {
      return await withTimeout(fn(), 10_000);
    } catch (e) {
      if (!isRetryable(e) || i === max - 1) throw toToolError(e);
      const backoff = Math.min(2 ** i * 1000, 8000);
      await sleep(backoff + Math.random() * 500);
    }
  }
}
```

**3. 设预算。** 单次调用 10 秒上限，整个任务 60 秒预算，超了就进入降级，别让用户对着转圈的会话发呆。

**4. 加熔断。** 同一工具连续 5 次失败 → open 60 秒，期间快速失败；半开状态放一个探测请求验证恢复。

**5. 准备降级路径。** 优先级：备用工具（换搜索源）→ 缓存的上次成功结果（明确标注数据时间）→ 如实告诉用户"这步做不了，原因是 X"。

**6. 给模型结构化错误，而不是堆栈。** 我们内部的约定：

```json
{ "ok": false,
  "error": { "code": "UPSTREAM_TIMEOUT",
             "retryable": true,
             "hint": "主搜索源不可用，可改用备用搜索工具" } }
```

模型拿到 `hint` 就知道该走备选，而不是自由发挥。

**7. 记录每次调用结果。** 失败率数据是之后调重试次数、熔断阈值的唯一依据，拍脑袋定参数都会后悔。

## 踩坑点

- **对非幂等接口重试**：消息发两遍、订单下两单。重试前先确认幂等，或加幂等键；
- **退避没加抖动**：多个会话同步恢复，形成重试风暴，把刚恢复的服务再打挂；
- **把 429 当 5xx**：不看 `Retry-After` 硬重试，越试越限；
- **熔断没有半开探测**：要么永远 open，要么在阈值附近疯狂 flapping；
- **错误语义没写进工具描述**：MCP 工具的 description 里应写明可能的错误码和含义，模型才能做出正确决策。

## 可复用建议

- 把 `callWithRetry` + 结构化错误封成一个公共 wrapper，所有插件统一走它，别每个插件各写一套；
- 新接一个外部 API 时过一遍小清单：有超时吗？哪些错误可重试？接口幂等吗？有降级路径吗？四个问题答不上来就先别上线。

## 总结

错误恢复的目标不是让任务永不失败，而是**让失败发生在可控的位置**：插件层而不是模型层，结构化返回而不是自由文本，有界重试而不是无限循环。外部 API 一定会挂，区别只在于挂的那一刻，你的 Agent 是清楚地告诉你"这条路不通，我走了备选方案"，还是默默烧掉你的 token。前者才配叫工程化。
