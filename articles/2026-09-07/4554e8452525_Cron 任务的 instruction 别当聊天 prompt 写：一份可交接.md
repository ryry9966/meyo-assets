## 背景

OpenClaw 的 cron 任务本质上是一段"无人值守的 prompt"：到点触发、独立会话、跑完即走。很多人把平时聊天用的语气直接贴进去——"帮我看下今天的 issue，重要的整理一下"。白天对话里这样写没问题，因为有上下文、有追问、你在场。定时任务里，这些全都没有。

## 问题

Cron instruction 的失败模式很集中：

- 输出目标没写死，agent 自己挑了个 channel 发；
- "今天""最近"这类相对时间没有锚点，跨时区直接漂移；
- 没有失败分支，工具一报错 agent 就开始即兴发挥；
- 没有"无事可做"的出口，为了让任务显得有产出而编造内容。

这些都不是模型能力问题，是 prompt 没按 runbook 的标准写。

## 做法

我现在的模板固定五段，一段都不能省：

```text
任务：每日 issue 晨报（09:00 Asia/Shanghai）
输入：用 github_list_issues 读取 repo=xxx，state=open，label=needs-review
输出：向 session「ops」发送一条消息，格式固定：
      首行"今日待审 N 个"，之后每行"编号 标题 负责人"
约束：只使用工具返回的数据，禁止推测；不执行其他操作
失败：N=0 时发送"今日无待审"；工具调用失败则报告原因，重试不超过 1 次
```

关键点逐条说：

1. **时间锚定**：把时区写进正文，不只靠 cron 表达式。表达式负责"什么时候醒"，正文负责"醒来后怎么理解时间"。
2. **输出写死到具体 session/channel**，格式给模板，不给自由发挥的空间。
3. **必须写禁令**：能用什么工具、不能用什么、完成后不许再做什么。无人值守场景里，"不要做什么"比"要做什么"更保命。
4. **失败分支是一等公民**：空结果、工具报错、数据不全，三种情况各给一条明确出路。

## 踩坑

- **疑问句是事故源**。"帮我看看……好吗？"在无人会话里可能换来 agent 的反问，然后挂到超时。全部改成祈使句。
- **一个 cron 干五件事**。出问题不知道是哪段 instruction 的锅。拆成单职责，必要时用"上一个任务的输出落文件 → 下一个任务读文件"串管线。
- **改 instruction 不留版本**。每版留档，一次只改一个变量，回滚才有依据。
- **引用了已改名的插件工具**。插件升级后工具名变了，cron 会静默失败。新版本上线后把所有 cron 跑一遍做冒烟测试。
- **高频 + 长输出**。每 15 分钟跑一次还要求全文摘录，token 账单很难看，输出改成只报增量。

## 可复用建议

- 心态转变：cron instruction 不是聊天 prompt，是写给值班员的操作手册，可复现 > 聪明。
- 上线节奏：先按日频跑一周，输出稳定后再提频。
- 留痕：所有 cron 输出固定落到一个审计 channel，回溯有据。
- 新增定时任务前先答三个问题：数据从哪来？结果发到哪？失败时它该干什么？答不上来就先别上线。

## 总结

定时任务里的 agent 是一个没有你、也问不到你的执行者。收起聊天直觉，用时间锚点、写死的输出、明确的禁令和失败分支，把每条 cron 写成一份能交接的 runbook——稳定性和账单都会好看很多。
