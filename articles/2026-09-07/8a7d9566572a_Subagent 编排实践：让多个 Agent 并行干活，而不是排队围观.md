## 背景

用 OpenClaw 这类 Agent 框架跑了一段时间后，多数人会撞到同一个天花板：单 Agent 循环。所有工具调用、文件读写、中间推理都堆在同一个上下文里，任务一复杂，上下文被中间产物塞满，模型开始"忘记"最初目标；串行执行也让长任务慢得难以接受。

## 问题

具体来说有三个：

1. **上下文污染**：探索过程的噪音（读过的文件、失败的尝试）全部留在主上下文，挤占有效推理空间；
2. **串行瓶颈**：互不依赖的子任务只能排队执行；
3. **恢复困难**：一个环节失败，整条链路重跑。

## 做法

我们最终收敛到 **orchestrator-worker** 模式，核心三步：

**1. 任务切分与契约定义。** 主 Agent 先做规划，把任务拆成相对独立的子任务。关键不是拆得细，而是每个子任务有明确契约：输入是什么、期望输出格式是什么（通常要求结构化摘要，限制在几百字）、完成标准是什么。

**2. 隔离上下文派发。** 每个 subagent 拿到独立上下文窗口，只包含任务契约和必要的最小背景。它内部可以自由探索、试错，这些噪音不会回流主上下文。相互独立的子任务并行跑。

**3. 结果聚合与校验。** subagent 返回压缩后的结构化结果，orchestrator 负责汇总、交叉校验、决定是否补跑。失败的任务单独重试，不影响其他分支。

## 踩坑点

- **结果回灌**：早期让 subagent 返回完整日志，几个并行任务直接把主上下文撑爆。后来强制"结论 + 关键证据"格式，并限制返回长度。
- **共享资源竞争**：两个 subagent 同时改同一文件、同一 git 分支，直接互相覆盖。解法是给写文件的子任务分配独立工作目录或分支，合并动作只留给 orchestrator。
- **缺乏父级上下文**：subagent 不知道全局目标，输出方向跑偏。契约里必须写清"为什么做这件事"，而不只是"做什么"。
- **成本翻倍**：并行 5 个 subagent，token 消耗接近 6 倍单 Agent。拆分前先估算收益，简单任务不值得编排。
- **拆分过细**：orchestrator 本身的规划与聚合也有开销。粒度到"每个子任务需要多轮工具调用"这一级即可，再细就是给编排器打工。

## 可复用建议

1. subagent 数量控制在 3–5 个，超过这个数先怀疑拆分方式，而不是加机器；
2. 任务契约模板化：目标、输入、输出格式、限制、完成标准，五项固定；
3. 文件操作一律隔离工作区，写冲突从机制上消灭，而不是靠提示词祈祷；
4. 每次派发记录完整输入输出，失败可以离线重放定位，不用现场考古；
5. 先串行验证子任务能独立完成，再改成并行——并行只是加速手段，不是正确性前提。

## 总结

subagent 编排不是银弹，本质是三笔交易：用隔离上下文换专注度，用并行换时间，用结构化契约换可控性。它适合"可拆分、子任务相对独立、单任务又足够复杂"的场景；如果任务本身就是一条流水线，老实的串行链路反而更稳。建议从一个真实的长任务开始改造，把最耗上下文的探索部分先拆出去，体会收益后再扩大规模。
