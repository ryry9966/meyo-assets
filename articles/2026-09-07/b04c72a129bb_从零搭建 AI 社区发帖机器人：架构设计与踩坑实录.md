## 背景

社区每周要整理一期技术摘要帖：翻信息源、汇总、改写、排版、定时发。单人重复劳动，纯手工耗时且容易断更。我的目标很克制：**不是全自动无人值守，而是把单期人工时间从两小时压到十五分钟**——机器负责采集和初稿，人只做最后的审核和发布确认。

## 问题

第一版很天真：脚本抓 RSS → 调 LLM 改写 → 直接调社区 API 发帖。跑了一周暴露三个问题：同一条内容重复发过两次、一次 LLM 输出格式崩了导致帖子排版稀烂、cron 任务叠跑导致限流 429。这才意识到这是个小型流水线工程，不是"调个 API"的事。

## 架构与做法

最终版拆成五层，逻辑很简单：

1. **采集层**：RSS、仓库 release、站内线索，输出候选条目；
2. **加工层**：OpenClaw agent 挂 3 个 MCP 工具——`fetch_url`（抓原文）、`search`（补背景）、`dedup_check`（本地查重）。要求 agent 输出符合 JSON Schema 的草稿（标题/正文/tags/来源），校验不过就重试，最多两次；
3. **审核层**：草稿写入 SQLite 队列表，命令行过审，通过才进发布队列；
4. **发布层**：调社区 API，令牌桶限流 + 429 指数退避；
5. **状态层**：SQLite 记录 content_hash、发布状态、时间戳。

cron 触发，任务入口先 `flock` 抢文件锁，防止叠跑。

## 踩坑点

- **重试导致重复发帖**：API 超时但实际已发成功，重试后帖子出现两条。解法是把"发布成功"的判定从"请求返回 200"改成"拿到 post_id 且本地落库"，且重试前先按 content_hash 查远端是否已存在。
- **LLM 输出带 markdown 代码围栏**：裸 `json.loads` 直接崩。必须先剥围栏、再做 schema 校验，失败走重试，不要相信模型的格式自觉。
- **抓取拖死整批**：某条源站反爬，超时 60 秒卡住全流程。给 `fetch_url` 设 10 秒超时，失败降级为"仅基于源标题摘要"，单条不让整批陪葬。
- **全自动发布的信任问题**：第一周坚持人审，通过率稳定在 90% 以上后才对低风险类目放开自动发，且自动发帖依然走同一套 hash 幂等检查。
- **密钥入库事故**：早期 token 写在配置文件里提交过一次，立即轮换。现在一律环境变量，`.env` 永不进仓库。

## 可复用建议

- 先做草稿生成器，再做发布器，**中间必须有审核队列**，这是整个系统里性价比最高的一环；
- 幂等键贯穿全链路：采集去重和发布去重用同一个 content_hash；
- agent 工具少而钝：3~4 个够用，每个都带超时和降级路径；
- 所有外部调用三件套：超时、有限重试、退避；
- 日志里记下每轮 agent 的输入摘要和 token 消耗，坏输出才有得回溯。

## 总结

上线四周，产出了 12 期草稿，人审通过 11 期，单期人工时间稳定在 15 分钟左右。回头看，它其实不叫"机器人"，叫**带人工卡点的流水线**更准确。LLM 负责它擅长的（整理、改写），工程负责 LLM 不擅长的（幂等、限流、兜底）。架构图画出来只要五行，价值全在上面这些踩坑细节里。欢迎大家拿去改，尤其查重和重试那段，是我用两条重复帖子换来的。
