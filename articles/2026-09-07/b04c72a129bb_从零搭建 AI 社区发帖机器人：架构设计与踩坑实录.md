我们社区每周都有值得沉淀的内容：高质量 issue 讨论、群里的答疑、新插件的上手记录。以前靠人工整理成周报发帖，坚持三个月就断了。于是我花两周做了个发帖机器人：定时采集社区动态，Agent 生成草稿，人工确认后自动发布到论坛。

目标很明确——**不追求全自动，先追求稳定周更**。

## 问题定义

动手前定下三条约束，后来证明它们就是整个架构的骨架：

1. 内容质量红线：宁可不发，不发水帖；
2. 发布可靠性：论坛 API 有频控，重试绝不能导致重复发帖；
3. 可维护性：以后可能同时发论坛和 RSS，不能把发布逻辑写死。

## 架构与实施步骤

最终分了五层：

- **采集层**：cron 触发，抓取 GitHub issues、RSS、置顶讨论，统一清洗成 JSON 入 SQLite；
- **生成层**：OpenClaw Agent 挂载 MCP 工具读取采集结果，输出结构化 JSON（标题、正文、标签）；
- **校验层**：JSON Schema 校验、链接真实性检查、内容指纹去重；
- **发布层**：每个目标平台一个 adapter，内部带频控队列；
- **状态层**：`draft → approved → published / failed` 状态机，全流程落库。

实施顺序上有个关键决定：**前两周只跑 dry-run**，草稿全部写库不发帖，人工评估质量达标后才接入真实发布。这一步后来救了我们不止一次。

## 踩坑实录

**1. 重复发帖。** 第一周就出现：发布请求超时，程序重试，论坛端实际已成功——帖子发了两遍。解法是以「日期 + 内容指纹」做幂等键，发布前先查目标平台是否已存在同指纹内容。

**2. 幻觉链接。** Agent 会编出看起来很合理的 issue 链接。解法很硬：链接只允许来自采集层数据，Agent 只能引用不能生成；校验层对每个链接发 HEAD 请求确认存在。

**3. 上下文膨胀。** 最初把一整周 issue 全文塞给 Agent，token 成本翻倍且摘要质量下降。改成采集层先粗筛并预摘要，Agent 只拿 top-N 条目加元信息。

**4. 频控踩线。** 论坛 API 返回 429 后盲目重试会越拖越死。发布队列加了指数退避加冷却窗口，把 429 当暂停信号而非错误处理。

**5. 定时重叠。** 一次服务器重启导致 cron 补跑，周报生成两次。补上 DB 唯一约束加运行锁才算根治。

## 可复用建议

- **生成与发布严格分离**：Agent 只输出 JSON，发布器只认 JSON。这条解耦让换平台、换模型都变成小事。
- **一切落盘**：每次 LLM 调用的输入输出都存档，出问题可以精确回放，不用靠猜。
- **幂等优先**：任何有副作用的操作（发帖、评论）都必须带指纹去重。
- **先 draft 两周**：放开自动化的时机不是"能跑通"，而是"连续两周不需要人工改稿"。
- **adapter 模式**：新增目标平台只需实现一个发布接口，核心流程零改动。

## 总结

这个项目里，prompt 和 Agent 编排大概只占 20% 的工作量，剩下 80% 是幂等、频控、校验、状态机这些"不性感"的工程。但恰恰是这 80% 决定了机器人能活过第一个月。Demo 一晚上，运维一学期——建议每个想做社区机器人的朋友，都从 dry-run 模式开始。
