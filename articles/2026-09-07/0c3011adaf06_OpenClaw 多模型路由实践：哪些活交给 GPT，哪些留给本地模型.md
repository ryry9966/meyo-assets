## 背景

OpenClaw 的典型形态是：一个常驻网关接住消息和定时任务，主 Agent 通过 MCP 调工具，跑各种自动化。很多人环境搭好后只挂一个模型——要么全程 GPT 级云端模型，月底账单难看；要么全程本地小模型，Agent 一跑多步工具调用就翻车。多模型路由解决的就是这件事：让不同性质的请求走不同档位的模型。

## 问题：路由的判断标准是什么

先给结论：判断维度不是"模型强不强"，而是任务的三类属性。

1. **推理密度**：是否需要规划、多步工具调用、长上下文取舍。典型如主 Agent 的对话循环、代码修改、复杂报错排查。
2. **调用量**：cron 定时摘要、消息分类打标、批量去重，这类任务量大但单步简单。
3. **数据敏感度**：涉及本地私有文件、聊天记录、密钥路径的内容，优先考虑不出网。

## 做法

1. **主 Agent 用云端强模型，配 fallback 链。** 主循环需要稳定遵循工具 schema、维持多步状态，这块省的钱抵不上一次失败重试。链路设为：云端主模型 → 第二家云端 → 本地模型，兜底限流和断网。
2. **把"量大活"拆给本地模型的子 Agent。** OpenClaw 支持给不同 Agent 配不同模型，把 cron 摘要、频道打标这类任务拆成独立 Agent 挂本地小模型，主模型只管主线对话。
3. **敏感任务显式走本地。** 读私有目录、处理含密钥路径的日志，直接在 Agent 配置里写死走本地，不要依赖默认路由。
4. **度量后再调。** 每个 Agent 单独记 token 用量和工具调用成功率，跑两周再改路由表，别凭感觉调。

## 踩坑点

- **本地小模型"聊天没问题，工具全崩"。** 用闲聊测试选型是最大的坑，务必拿真实 MCP 工具链测 tool-call 的 JSON 合规率。
- **上下文长度差异导致静默截断。** 本地模型上下文短，长会话一压缩，Agent 会忘掉前面的约束，表现为"莫名不守规矩"。
- **fallback 静默涨价。** 本地失败回退到云端后成本悄悄上升，要给回退事件加告警或计数器。
- **不同模型工具调用格式不同。** 换模型后要重新验证，别假设一套 prompt 全通吃。

## 可复用建议

- 一张简表做决策：规划/编码/长链路 → 云端强模型；摘要/分类/格式化 → 本地小模型；私有数据 → 本地；兜底 → 本地。
- 模型选择放在 Agent 配置层而不是 prompt 层，方便单独回滚。
- 每月用 10~20 个真实历史任务做回归评测，路由表跟着数据走，而不是跟着体感走。

## 总结

多模型路由本质是工作负载分类问题。我的默认策略：Agent 主循环交给云端强模型保可靠性，高频低难度批量任务和敏感数据交给本地模型控成本、划边界。先量化、再路由，路由表是活的配置，不是一次性决策。
