## 背景

OpenClaw 的 cron 任务本质上很简单：到点之后，平台把任务里配置的那段 instruction 作为 prompt 发给 agent，让它自主执行。听起来和聊天没区别，但运行环境完全不同——**没有人在旁边**。它不会来问你"这个文件在哪""格式要不要调""查不到怎么办"。

所以 cron instruction 的写作目标和交互式 prompt 不一样：交互式 prompt 追求引导对话，cron instruction 追求**单次、无人监督、结果可预期**。写得好是自动化，写得差就是一个定时触发的幻觉发生器。

## 三个典型翻车场景

1. **指令不自包含**。写了"按我们上次讨论的格式整理"，但 cron 触发时不存在"上次"那轮对话，模型只能猜。
2. **时间感知不可靠**。instruction 里写"今天的日报"，而模型对当前日期的感知并不总是准，尤其跨时区、跨月时。
3. **输出没定型**。结果要推送到群聊或写入文件，但没给模板，今天一个格式明天一个格式，下游没法消费。

## 做法：五段式模板

我现在的 cron instruction 基本都按这个骨架写：

```markdown
【目标】一句话说清这个任务要产出什么。
【数据源】明确列出用哪个工具/命令/文件，路径写死。
【步骤】1/2/3 编号，每步一个动作。
【输出】固定模板，字段化，给长度上限。
【异常】缺数据写 N/A 不推测；工具失败只报错误摘要；
        顺带声明"不要做"的事。
```

举例，"每天早上汇总进展"这种需求：

❌ 初版：*每天八点看看我昨天的提交和 TODO，发个日报。*

✅ 改后：
*【目标】生成昨日工作日报并推送。【数据源】用 shell 执行 git log 获取提交；读 /path/to/TODO.md。【步骤】先调用时间工具确认昨天日期 → 拉取提交 → 读取 TODO → 按模板汇总。【输出】三段：已完成 / 进行中 / 风险，每段不超过 5 条，总长 200 字内。【异常】无提交则写"昨日无提交"；任一工具失败时只报告原因，不编造内容。*

改完后输出立刻稳定：字段齐、长度可控、缺数据时会明说。

## 踩坑点

- **日期交给模型推算**。改为在步骤里强制"第一步先获取当前时间"，或由脚本把日期注入 prompt。这是最低频也最烦人的翻车点。
- **调度逻辑混进 instruction**。"如果今天是周五就……"这类规则尽量放进 cron 表达式或独立判断；instruction 只负责"这一跑该做什么"，否则两处规则打架很难排查。
- **缺数据时让模型自由发挥**。必须显式写"查不到就标注，不要推测"。模型默认倾向补全，无人值守时补全等于编造。
- **先挂 schedule 再验证**。建议先手动触发试跑两三次，确认输出稳定再启用定时。prompt 也是要跑单测的。
- **任务越改越乱**。改动时注释掉旧逻辑，或拆成小任务。instruction 没有版本管理，三天后你自己都不知道哪句是干嘛的。

## 可复用建议

1. **自包含原则**：假设运行时不存在任何聊天上下文，所有信息写进 instruction。
2. **数据源显式**：每个动作对应的工具/命令/路径写死，不给"你自己找找"的空间。
3. **输出模板化**：字段名固定，长度给上限。
4. **失败路径显式**：静默跳过、告警、还是部分输出，三选一写清楚。
5. **当代码维护**：改 instruction 要有变更意识，关键任务留 changelog。

## 总结

Cron instruction 的本质，是写给一个**永远不会来问你**的执行者。你在交互对话里靠追问补上的所有信息——日期、路径、格式、边界——都必须预先写死在 instruction 里。把它当成一份给外包同事的交接文档来写，任务就稳了。
