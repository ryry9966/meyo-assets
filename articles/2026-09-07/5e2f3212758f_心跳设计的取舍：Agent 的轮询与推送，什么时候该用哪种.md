## 背景

OpenClaw 的 heartbeat（心跳）本质上是给 Agent 加了一个自我唤醒机制：网关按固定间隔（默认 30 分钟）触发一次轻量运行，Agent 读一份 `HEARTBEAT.md` 清单，判断有没有值得汇报的事。它解决的是一个朴素的问题——Agent 默认是被动响应的，只有人来消息才动；心跳让它具备最低限度的主动性。

但实践里常见一个误区：把心跳当成万能的"定时巡检"，什么检查都往里塞。结果 token 烧了、消息刷屏，真正的事件反而被淹没。

## 问题：两套触发模型，各管一半

心跳是轮询（polling）：由时间驱动，Agent 定期醒来问一句"有事吗"。推送（push）是事件驱动：外部系统在事情发生时主动通知——GitHub webhook、监控告警、MCP 工具回调。

取舍其实很清楚：

- **能推送的源，轮询是浪费。** 事件发生时刻是已知的，靠定时器去猜，要么延迟一个周期，要么缩短间隔烧钱。
- **推不了的源，只能轮询。** 本地文件变化、没有 webhook 的 RSS、自研脚本的状态——外部系统不知道也不关心你的 Agent 存在。
- **心跳还有个隐藏职责：兜底自检。** 比如"上次后台任务跑完没"，这类元状态检查没有外部事件源，轮询是唯一选择。

## 做法：事件优先，心跳兜底

我们的落地步骤：

1. **盘点**所有需要 Agent 周期性关注的检查项，分成两类：外部系统已知时刻的（能接 webhook / MCP 通知），和只能本机观察的。
2. **第一类全部改推送。** OpenClaw 的 webhook 入口和 MCP 工具足够覆盖常见场景，改完后这些项从 `HEARTBEAT.md` 里删掉。
3. **第二类留在心跳清单里**，且每项写成"条件 + 动作"格式：满足什么条件才动作，否则静默。心跳的默认产出应该是"无话可说"。
4. **调间隔。** 30 分钟对绝大多数巡检够用；别低于 15 分钟，除非在做短窗口监控——那种场景更适合外部监控系统的推送。
5. **输出隔离。** 心跳消息走独立的心跳频道，不和主对话混在一起，主动消息不至于打断人。

## 踩坑点

- **静默没配好。** 早期心跳每次都汇报"一切正常"，一天几十条，用户很快麻木。务必让"无事发生"等于零输出。
- **token 成本低估。** 30 分钟一次就是一天 48 次运行。如果每次都跑完整模型加长清单，成本不低。能轻量判断先过滤的，别进主模型。
- **用心跳盯"怕错过"的事。** 轮询天然有窗口期，两跳之间发生又自愈的故障，心跳永远看不见。凡是"错过就完了"的告警，必须推送。
- **推送端点裸奔。** 为接 webhook 暴露公网入口却没加鉴权，等于给 Agent 开了个无门禁的 API。
- **宿主机休眠。** 跑在笔记本上的网关，合盖后心跳就停了，但"没消息"容易被误读为"没事"。要对心跳自身的时间戳做监控，间隔过久要报警。

## 可复用建议

- 一句话原则：**推送管"知道时刻的事"，轮询管"不知道时刻的事"**，心跳是后者的载体，不是全家的心脏。
- `HEARTBEAT.md` 当代码管：进版本库、写清每项的触发条件，避免清单腐化成大杂烩。
- 心跳里只做**检查**，不做**执行**。执行交给事件触发或显式指令，心跳发现问题后发通知即可。
- 给心跳加观测：记录每次 tick 的时间和产出。回看一周，你大概率会发现一半的清单项可以删。

## 总结

心跳不是越多越负责，恰恰相反——心跳清单的长短，反映的是事件化改造的完成度。理想状态是清单越来越短：能推送的都推了，剩下的只有真正无事件源的本机检查。轮询是成本，推送是投资。按这个视角做取舍，Agent 的主动性才不会变成负担。
