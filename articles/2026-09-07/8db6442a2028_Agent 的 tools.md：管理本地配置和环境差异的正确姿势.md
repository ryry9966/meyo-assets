## 背景

跑 OpenClaw 一段时间后会发现一个规律：模型能力是标准的，但每台机器都不一样。路径、包管理器、端口、代理设置、Node 版本……这些信息不进代码仓库，却直接决定 agent 每次执行是否靠谱。tools.md 的定位很简单：一份写给 agent 看的本地环境说明，随上下文注入，把“这台机器怎么干活”从隐性知识变成显性配置。

## 问题

没有 tools.md 时，环境信息通常散在四处：系统提示词里硬编码、`.env`、MCP 配置、口头约定。后果有三类：

1. **换机即坏。** agent 默认 `apt`，你的机器是 `brew`；默认 `pnpm`，仓库锁的是 `npm`。
2. **泄漏风险。** 为了让 agent 干活，把内网地址、token 写进提示词，然后提示词进了版本库。
3. **漂移。** 环境改了没人记得，文档、提示词、真实环境三者各说各话。agent 拿着过期信息执行，比不给它信息更糟。

## 做法

推荐三层结构：

- **全局层**：`~/.openclaw/tools.md`，写跨项目通用习惯，如默认编辑器、代理、shell。
- **项目层**：仓库根目录 `TOOLS.md`，进版本库，只写与机器无关的事实：脚本入口、端口约定、已知坑。
- **机器层**：`tools.local.md`，进 `.gitignore`，写绝对路径、本机包管理器、本地服务地址。

写入四原则：

1. **写指令不写描述。**“Python 统一用 `uv run`，不要直接调 python” 优于 “本项目用 uv”。
2. **agent 能自己探测的不写。** 目录结构、依赖列表让它现场查，省 token 也避免过期。
3. **密钥永远不进 tools.md。** 只写指路信息，例如 “API key 在系统 keychain，用 `op read` 获取”。
4. **单文件控制在 100 行内**，最重要的规则放最前面。

## 踩坑点

- **文档与现实的优先级。** 实测中 agent 对 tools.md 的信任度高于现场探测，文档错了比没有更危险。建议在文件头部声明：“若与探测结果冲突，以探测为准并报告差异。”
- **平台差异不标注。** macOS 和 Linux 的 `sed -i`、`date` 语法都不同，要么写清平台，要么给两条命令。
- **重复声明。** 同一端口约定同时出现在项目层和机器层，改一处漏一处。原则：一个事实只在一层出现。
- **只在出事后更新。** tools.md 应纳入“环境变更即更新”的肌肉记忆，优先级等同于改 CI 配置。

## 可复用建议

- 用脚本生成机器层初版：采集 PATH、包管理器、Docker 状态，人工删减后使用。
- CI 里跑一次 gitleaks 扫 tools.md，防止手滑提交密钥。
- 把“核对 tools.md 与环境是否一致”做成例行任务，让 agent 开工前自检一轮并输出差异清单。
- 模板保持四段：工具与调用方式 / 路径与环境 / 端口与服务 / 已知坑。

## 总结

tools.md 不是又一份文档，而是把环境差异从隐性的提示词污染，变成分层、可审计、可校验的显性配置。**三层分离、写指令不写描述、冲突时以探测为准**，这三个原则能覆盖 90% 的场景。先从给当前项目补一份 50 行以内的 tools.md 开始，一周后你会回来删掉提示词里那些硬编码的路径。
