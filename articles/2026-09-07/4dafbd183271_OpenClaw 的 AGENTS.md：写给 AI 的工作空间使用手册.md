# 背景

用 OpenClaw 这类 agent 工具跑任务时，一个常见体验是：同一个工作空间，换一次会话，agent 就"失忆"了。它不知道项目用 pnpm 还是 npm，不知道 `generated/` 下的文件是生成物不能手改，也不知道跑测试前要先起一个本地依赖。README 是写给人看的，而 agent 缺一份写给它的说明——这就是 AGENTS.md 的定位：放在工作空间根目录，OpenClaw 在会话启动时自动读取的工作约定。

# 问题

没有 AGENTS.md，agent 只能靠猜。典型症状：

- 用错包管理器，装出一把不一致的 lock 文件；
- 直接手改生成目录，下次代码生成后被覆盖；
- 测试命令猜错，反复试错烧掉大量 token；
- 每次对话都要人工重复一遍"先跑 bootstrap 脚本"。

这些不是模型能力问题，是上下文缺失问题。与其在聊天里反复口述，不如把规则固化成一个文件。

# 做法

1. **建文件**：在工作空间根目录放 `AGENTS.md`，会话初始化时会被注入上下文。monorepo 可在子目录放嵌套版本，只作用于各自子树。
2. **定骨架**：推荐六段——项目一句话概述、环境与依赖、常用命令（build/test/lint）、目录说明（明确标注生成物）、代码约定、禁止触碰清单。
3. **用祈使句**：写"提交前运行测试，失败则修复"，而不是"本项目测试使用 vitest"。规则要指向行为，不是描述事实。
4. **控长度**：整个文件建议 60 行以内。每一行都占上下文，只保留会改变 agent 行为的信息。
5. **进版本库**：像评审代码一样评审它的 diff，改动要有 commit 记录。
6. **持续迭代**：agent 犯同一种错两次，补一条规则；某条规则三个月没触发过，删掉。

# 踩坑点

- **复制 README**：面向人类的安装教程和项目宣传语，对 agent 是纯噪音。
- **写太长**：几百行的"手册"会稀释重点，关键规则反而被淹没、不被遵守。
- **规则过时**：重构后忘了同步，错误指令比没有指令更糟。
- **措辞模糊**："尽量""通常"无法被执行，要么写明确阈值，要么删掉。
- **写入敏感信息**：这个文件会进上下文，也会进 git 历史，密钥和内网地址不要放。

# 可复用建议

- 把每条规则写成可验证的形式："遇到 X，做 Y"，方便判断规则是否真的生效。
- 让 agent 参与维护：它犯错后，让它自己提议一条规则追加进 AGENTS.md，人工 review 后合入。
- 团队沉淀一份公共模板（命令区留空），新项目复制后十分钟填完。
- 每次改 CI 或构建脚本，顺手检查 AGENTS.md 是否需要同步，把它加进发布 checklist。

# 总结

AGENTS.md 的本质，是把团队里"老人才知道"的隐性知识显性化，交给 AI 当作工作空间的使用手册。投入一两个小时，换来的是每次会话可预期的行为。它不是写完就结束的文档，而是需要随代码一起演化的活配置——维护它的成本，远低于每次会话重新解释一遍的成本。
