## 背景

OpenClaw 的 Agent 默认是被动模式：你发消息，它回复。这对问答够用，但对巡检、提醒、定期汇总这类任务天然不合适——你不去问，它就永远不动。

HEARTBEAT.md 是 workspace 根目录下的一个约定文件。Agent 会按配置间隔醒来一次，读取这个文件，判断有没有该做的事，做完继续睡。它不是新协议，本质就是"定时任务 + 一个 markdown 约定"，但足以改变使用姿势：从"人记得问"变成"文件记得写"。

## 问题

之前我在主会话里维护一串"记得帮我做 XX"的口头清单，实际效果很差：

- 换了会话上下文就丢，Agent 不会主动延续；
- 巡检类任务（看磁盘、查监控、汇总订阅源）没有触发时机，全靠我某天想起来；
- 真正的异常往往在没人在场时发生，等我发现已经晚了。

核心矛盾是：Agent 没有固定的"上班时间"，也就没有固定的职责边界。

## 做法

1. **建文件**。在 workspace 根目录创建 `HEARTBEAT.md`，首次可以只有一两行。
2. **配间隔**。在 `openclaw.json` 里设 `agents.defaults.heartbeat.intervalMins`（默认 30 分钟）。调试期建议临时调到 2 分钟，稳定后再放回去。
3. **写条目**。一行一条，格式固定为"条件 + 动作 + 汇报方式"，例如：
   - "磁盘占用超过 90% 时清理缓存并通知我；低于则静默"
   - "每天早上 8 点汇总一次未读 RSS 条目，超过 20 条只给标题"
4. **约定静默**。明确写一句"无事可做时不要发消息"，否则每 30 分钟会收到一次"一切正常"。
5. **验证**。调短间隔跑半天，翻日志确认心跳确实读到了文件、条目被执行、静默约定生效。

## 踩坑点

- **Token 成本是真实的**。每次心跳都是一次完整推理，条目越多烧得越快。我把无关任务从 HEARTBEAT.md 移到 cron 触发后，月消耗降了一半以上。
- **条目含糊 = Agent 瞎猜**。早期写过"关注一下服务器状态"，结果它每隔一轮就汇报一次没用的摘要。改成明确的阈值和动作后才稳定。
- **心跳会话的上下文和主会话不完全共享**。任务结果要主动落到文件或推送出来，别指望"上次心跳我记得"。
- **通知轰炸**。没有静默约定时，agent 会把每次巡检都当回事。必要时加上"安静时段"条款，比如夜间只处理红色级别事件。
- **文件会腐烂**。任务加了不删，一个月后 HEARTBEAT.md 变成垃圾场，每次心跳都在浪费 token 读它。

## 可复用建议

- 用统一模板写条目：**触发条件 → 动作 → 汇报级别**（静默 / 记录 / 通知），三种级别区分清楚。
- 定时类、轮询类任务优先用 cron 或 MCP 工具触发，HEARTBEAT.md 只留"需要判断该不该做"的事，别把它当 cron 用。
- 每周花两分钟清理一次 HEARTBEAT.md，删掉失效条目，像维护代码一样维护它。
- 重磅任务先在短间隔 + 测试环境下验证一轮，再上线到正式频道。

## 总结

HEARTBEAT.md 的价值不在于技术多复杂，而在于它把 Agent 的职责写成了一个可版本管理、可 review 的文件。配合合理的间隔、明确的静默约定和定期清理，Agent 才能真正做到"该出手时出手，没事不打扰"。建议从一两条低风险任务起步，跑稳了再扩。
