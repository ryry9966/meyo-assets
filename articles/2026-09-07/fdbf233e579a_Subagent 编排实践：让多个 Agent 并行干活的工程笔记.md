## 背景

单 Agent 循环（LLM → 工具调用 → 观察 → 再推理）在任务变大后会撞上两个硬约束：上下文窗口和串行执行。比如"调研十个仓库并汇总"这类任务，单 Agent 的做法是把十份原始内容依次读进同一个上下文，前面的材料不断挤占后面的推理空间，而且全程串行，耗时线性增长。

Subagent 编排是常见的解法：主 Agent 不自己干活，而是把任务拆给多个独立的子 Agent 并行执行。每个子 Agent 有自己的上下文，只把精炼后的结果回传。

## 问题

实践里真正的痛点不是"能不能并行"，而是：

1. **上下文污染**：调研类任务的中间产物（网页原文、长日志）质量参差，混进主上下文后直接干扰后续判断；
2. **串行等待**：爬取、构建、测试这类慢工具调用串行跑，总时长难以接受；
3. **职责不清**：一个 Agent 同时负责拆解、执行、校验，出错后很难定位是哪一环的问题。

## 做法与步骤

我们采用"调度-执行-汇聚"三段结构：

**第一步：任务拆解。** 主 Agent 先输出结构化任务清单（JSON），每项包含目标、输入、产出格式。拆解要保证子任务之间没有共享写资源——这是能否并行的前提。

**第二步：spawn 子 Agent。** 每个子任务起一个独立会话，prompt 只给该任务需要的信息，输出强制 JSON 并带 `status` 字段。子 Agent 之间互不可见。

**第三步：并行执行与容错。** 用线程池或异步任务并发跑，设单任务超时。单个子 Agent 失败不阻塞整体，标记后进重试或降级队列。

**第四步：汇聚。** 主 Agent 只读子 Agent 的结构化结果，不读原始中间产物；汇聚时做去重和冲突处理。

最简的编排循环大概长这样：

```text
plan    = main_agent.decompose(goal)
results = pool.map(spawn_subagent, plan.tasks, timeout=120)
merged  = main_agent.aggregate(results)
```

## 踩坑点

1. **子 Agent 上下文给太少。** 为了省 token 只发一句话任务，子 Agent 缺背景反复试错，反而更贵。经验是：任务描述 + 必要输入 + 输出 schema，三样给全。
2. **共享文件系统写冲突。** 并行子 Agent 写同一个文件会互相覆盖。解法是各写各的临时目录，由主 Agent 统一合并。
3. **聚合丢失细节。** 子 Agent 返回过度压缩的结论，主 Agent 无法校验。建议结果里带证据引用（来源路径、行号），方便事后抽查。
4. **并发度不设上限。** 二十个子 Agent 同时打 MCP 工具或外部 API，直接触发限流。并发数要和下游承受能力对齐，建议从 3–5 起步。
5. **该串行时强行并行。** 有依赖的任务（先调研后写码）拆开并行只会制造返工。编排前先画依赖图，只有无依赖的层才并行。

## 可复用建议

- 给子 Agent 定一套固定输入/输出 schema，所有任务复用，调试成本大幅下降；
- 回传强制结构化（JSON + status + evidence），禁止自由文本；
- 每类子 Agent 记录耗时和 token 消耗，跑几轮就能判断哪类任务根本不值得并行；
- 失败降级策略提前定好：重试一次 → 换更小的模型 → 标记人工兜底，不要无限重试。

## 总结

Subagent 编排的本质不是"更多的 AI"，而是把**上下文隔离**和**并行执行**变成显式的工程结构。它适合大规模、只读、可拆分的任务；对强依赖、强状态的流程，老老实实串行更稳。先把 schema、并发上限、容错策略这三件事定下来，编排才可能长期跑在无人值守的环境里。
