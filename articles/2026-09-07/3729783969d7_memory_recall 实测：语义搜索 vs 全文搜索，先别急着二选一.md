## 背景

Agent 常驻化之后，`memory_recall` 成了我这边调用频率最高的工具之一。记忆后端常见的两条路线：**语义搜索**（embedding 进向量库，按相近度召回）和**全文搜索**（BM25 / SQLite FTS5 / 干脆 grep）。社区里两种声音都有，但很少有人拿自己的真实查询对过数据。

## 问题

我的 agent 跑了两三个月，记忆条目 800 多条：项目决策、踩坑记录、用户偏好、报错解法。用语义搜索时发现一个尴尬现象——问“上次那个 API 超时怎么解决的”，它返回了几条讲“接口容错设计”的泛化笔记，而真正带错误码和参数名的原文排在第五开外。反过来，把查询措辞换成“调用挂起”，全文搜索直接扑空。

也就是说：语义擅长“意思相近”，全文擅长“字面精确”，而 recall 的真实查询是两种混着来的。

## 做法

我没直接换方案，先做了个很小的评测集：

1. 从会话日志里捞 40 条真实发起过的 recall 查询，人工标注每条期望命中的记忆条目；
2. 同一批记忆、同一批查询，分别跑语义和全文两路，记录 hit@3；
3. 结果：语义 27/40，全文 24/40，重合 19 条——各有约五分之一的查询**只有对方能答对**；
4. 于是上混合检索：两路各取 top5，用 RRF（倒数排名融合）合并，取前 3 条回填上下文。hit@3 到 35/40。

实现上只需要把 recall 工具改成先查两路再合并，没有引入新依赖；向量库和 FTS 索引指向同一份记忆存储，写入侧零改动。

## 踩坑点

- **中文分词**：SQLite FTS5 默认 tokenizer 对中文基本无效，得换 trigram 或接 jieba，否则全文那一路是摆设。
- **中英混排内容**：记忆里大量命令、参数名、报错原文，通用中文 embedding 对纯 token 类内容召回不稳，评测别只测纯中文问句。
- **阈值别调太死**：向量相似度分数跨查询不可比，固定阈值经常漏召回或塞满噪音。RRF 只看排名不看分数，反而省心。
- **旧记忆霸榜**：同一话题反复出现时老条目长期靠前。加时间衰减和 project 标签过滤，比换模型有效得多。

## 可复用建议

- 记忆条数几百以内时，先上全文搜索就够，别为“先进”引入向量库；
- 出现“换个说法就查不到”再补语义路，混合 + RRF 是性价比最高的默认解；
- 评测集保持 30–50 条真实查询，换 embedding 模型、改 chunk 策略后重跑，五分钟的事；
- 写入时带结构化元数据（时间、项目、类型），检索时先过滤再排序，比任何检索算法都更改变局。

## 总结

语义 vs 全文不是二选一，而是“哪一种召回失败由谁兜底”的问题。拿你自己的查询数据测一遍，答案通常比社区争论清晰得多。
