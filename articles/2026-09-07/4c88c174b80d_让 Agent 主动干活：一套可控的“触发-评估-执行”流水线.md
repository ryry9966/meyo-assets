## 背景

大多数 AI 助手的默认形态是被动应答：用户提问，模型回答，会话结束。但对做自动化的同学来说，真正的价值往往在会话之外——定时汇总、监听变化、在问题发生前提醒。随着 MCP 工具生态和调度类插件的成熟，让 Agent 具备 proactive 能力（不等你开口就把事情办了）已经从概念演示变成一个可落地的工程问题。

## 问题

主动不等于勤快。实际跑起来，常见的三类翻车：

- **吵**：一点风吹草动就推送，三天后用户关掉所有通知；
- **错**：基于过期上下文行动，把昨天的问题当新闻报；
- **越界**：没经确认就执行写操作，动了不该动的东西。

本质是缺一条受控链路：谁触发、凭什么判断值得行动、行动权限有多大、出了问题怎么看见。

## 做法

以“每天主动盯一次数据异常 + 邮件出现关键词时起草回复”为例，拆成四步：

1. **定义触发源**。定时类用 cron/scheduler 插件；事件类用 webhook、文件监听；状态类用低频轮询。触发源只负责“叫醒”，不带业务判断。
2. **唤醒-评估-行动三段式**。Agent 被唤醒后先拉实时上下文（不信任缓存摘要），再由一次低成本评估决定是否继续：给出可校验的判断标准（如“偏离基线超过 2 个标准差才算异常”），低于阈值就静默记录、不打扰。
3. **分层权限**。L0 只读观察；L1 生成草稿等确认；L2 执行白名单内的写操作；L3 高危动作必须人工二次确认。用 MCP 的工具范围控制把权限落到配置里，而不是写在 prompt 里求模型自觉。
4. **可观测**。每次主动行为写日志：触发源、上下文快照、评估结论、执行结果，用同一个 trace ID 串起来。每周复盘一次“打扰命中率”，据此调阈值。

## 踩坑点

- **触发风暴**：同一事件被监听器捕获多次，Agent 反复行动。加去重键和冷却窗口，同键 N 分钟内只处理一次。
- **自激励循环**：Agent 自己的动作又产生事件触发自己，轻则空转重则死循环。给自产事件打标，评估阶段直接跳过。
- **评估标准模糊**：让模型自己判断“这个重要吗”，结果它觉得什么都重要。把标准量化成条件，并配几个正反例。
- **静默失败**：无人值守任务挂了没人知道。失败必须落日志，并汇入每日摘要，而不是实时轰炸。

## 可复用建议

- **先只读，后写入**：第一阶段只做主动摘要/提醒，跑两周确认信噪比，再逐级开放写权限。
- **把“打扰”当配额管理**：给每天的用户中断设上限，超限的合并进日报。
- **三者分离**：触发逻辑放配置、评估逻辑放 prompt、执行逻辑放白名单——改哪个都可控、可审查。
- **每个主动动作可回放**：保留触发时的上下文快照，复盘时能还原“它当时为什么这么做”。

## 总结

Proactive 能力的核心不是“多做事”，而是“判断什么时候该做事、什么时候该闭嘴”。触发源、评估门、权限分层、可观测，四件套凑齐，它才能从演示走向日常。建议从一条只读的定时摘要开始，把打扰预算和回放日志建好，再逐步放开手脚。
