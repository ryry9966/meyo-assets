## 背景

E2E 测试是团队最容易欠账的部分：写起来慢、断言琐碎、UI 一改就红。多数团队的选择是少写、只覆盖关键路径，剩下靠肉眼回归。LLM 出现后，“让 AI 写测试”看似顺理成章，但直接把需求丢给模型，得到往往是引用不存在选择器的测试——看着像模像样，跑起来全是红的。问题不在模型能力，而在缺少真实的反馈回路。这正是 Agent + MCP 能发力的地方。

## 问题拆解

让 Agent 参与 E2E，本质要解决三件事：

1. **定位**：Agent 不知道页面的真实结构，选择器全靠猜；
2. **执行**：Agent 写完没人跑，错误无法被发现和修正；
3. **判断**：测试红了，是产品 bug 还是测试写得烂，Agent 默认分不清。

## 做法

我们内部跑通了一条协作流水线，四个环节，通过 MCP 工具串联：

1. **约定先行**：仓库里维护一份测试约定文档（fixture 写法、登录态注入、数据准备方式），作为 Agent 的上下文注入。没有这份文档，每个 PR 的测试风格都会漂移。
2. **探索 Agent**：通过浏览器类 MCP 工具（Playwright MCP 一类）拿到页面的 accessibility snapshot 而非原始 HTML，按用户流程走一遍，产出“步骤 + 关键断言”的自然语言清单。人可以在这步介入改写。
3. **编写 Agent**：拿着清单和约定文档生成 Playwright 代码，每条用例只覆盖一个流程。
4. **运行 + 修复 Agent**：执行测试，失败时把 trace、截图、console 日志回喂给模型，定位是选择器错、时序问题还是断言过弱。设置迭代上限（我们用 3 次），超限转人工。

核心原则：**Agent 只提 PR，CI 是唯一裁判。**

## 踩坑点

- **永远绿的测试**：Agent 很爱写“元素可见即通过”的弱断言。我们在约定里强制要求数据级断言（断言列表内容、跳转后的 URL 参数），review 时专门盯断言。
- **waitForTimeout 泛滥**：模型习惯用固定等待糊弄 flaky。直接用 ESLint 规则禁掉，逼它走 auto-waiting 语义。
- **把 bug 修“没了”**：产品真有 bug 时，Agent 会倾向改测试让它变绿。流程里加了一步强制分类：每次失败必须先标记“测试问题 / 产品问题”，产品问题一律出 ticket，不许动测试。
- **上下文爆炸**：整页 accessibility tree 很大，多轮下来 token 成本难看。只喂当前流程涉及的路由快照，其余裁剪。

## 可复用建议

- 一次只给一个用户流程，任务粒度小，成功率明显更高；
- 测试约定文档放仓库里版本化，像对待 AGENTS.md 一样对待它——它比换更强的模型更有用；
- 失败产物（trace / screenshot）是 Agent 最好的上下文，跑不起来就别让它闭门造车；
- 人工 review 的重点不是代码风格，而是断言质量和 flaky 风险。

## 总结

Agent 写 E2E 这件事，价值排序是：真实执行反馈 > 页面结构 grounding > 模型本身。把 Agent 当成一个需要明确规范、需要反馈、需要验收的初级工程师来用，产出质量是可用的；当成一键生成器来用，只会收获一堆永不失败的假测试。
