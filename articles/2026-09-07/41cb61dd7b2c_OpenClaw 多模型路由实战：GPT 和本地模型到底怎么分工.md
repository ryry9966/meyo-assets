## 背景

OpenClaw 的模型层是开放的：主 agent、子 agent、MCP 工具链、插件各自都可以指定不同的 provider。社区里常见两种极端：一种全程 GPT，月底账单比服务器租金还高；另一种为了省钱全切本地小模型，结果工具调用成功率暴跌，agent 变成"看起来在干活"。多模型路由要解决的不是"哪个模型最好"，而是"哪类请求配哪类模型"。

## 问题拆解

把一次 agent 运行拆开看，调用点大致四类：

1. 主循环的规划与决策——需要强推理和长上下文；
2. 工具调用的参数生成——要求严格符合函数签名；
3. 摘要、分类、格式化——能力要求低，但调用量大；
4. Embedding / 召回——和推理模型基本无关。

这四类请求的成本敏感度和质量敏感度完全不同，混在同一个模型上跑，必然有一边在浪费。

## 路由方案

我的做法是三层分工：

- **规划层（云端强模型）**：主 agent 用 GPT 级别的模型。规划错了后面全白干，这里不省。
- **执行层（本地模型）**：格式化、简单摘要、独立子任务交给 Ollama 跑的本地模型。OpenClaw 里给子 agent 单独配 provider 即可。
- **回退层**：本地模型解析失败或超时，自动 fallback 到云端并记日志。

具体步骤：

1. 配置里按 agent 粒度声明模型，不要全局一个模型；
2. 每次调用记录 model、tokens、latency、成功与否四个指标；
3. 用真实任务跑一周，按调用点统计失败率，再决定哪些能下沉到本地。

## 踩坑点

- **本地模型的 function calling 不稳定**：同一份 schema，云端基本全过，本地 7B 级模型经常多字段、漏引号。涉及工具调用的链路别轻易下沉。
- **上下文长度陷阱**：云端 128k，本地可能只有 8k～32k。同一份 prompt 直接丢给本地模型会被静默截断，agent 表现变差但你很难找到原因。
- **路由判断本身别用大模型做**：规则引擎或简单分类器就够，否则省下的钱又赔回去。
- **fallback 要真演练过**：我见过配置了降级、但本地服务挂掉后 agent 直接卡死的案例，回退路径没跑过等于没有。

## 可复用建议

- 先测量再迁移，没有 metrics 之前不谈路由优化；
- 灰度切换，迁移一批验证一批，不要一次全切；
- 把"哪些任务用过哪些模型、效果如何"整理成文档，团队内复用；
- 本地模型选型优先看指令遵循和 JSON 输出稳定性，而不是跑分。

## 总结

多模型路由的本质是按请求特征做资源分配：规划保质量，执行控成本，回退兜底。OpenClaw 的灵活配置让这套思路落地成本很低，真正难的是坚持测量、以及克制地省钱。
