## 背景

用 Agent 做自动化跑久了会遇到一个瓶颈：所有事都挤在一个主循环里串行执行。比如让 Agent 一次性完成"跑测试 + 审查三个模块的代码 + 生成变更文档"，它只能一件件来，跑一轮十几分钟。更麻烦的是各种工具输出（日志、文件内容、lint 结果）全部堆进主上下文，几轮之后主 Agent 开始"失忆"，前面定下的约定后面就忘了。

Subagent 编排就是针对这个问题：主 Agent（orchestrator）负责拆任务、派发、汇总，实际干活交给多个子 Agent 并行执行，每个子 Agent 拥有独立的上下文窗口。

## 做法

以我们仓库里"每周代码巡检"这条自动化为例，结构如下：

1. **拆任务**。主 Agent 把目标拆成互不依赖的子任务：模块 A 审查、模块 B 审查、依赖版本检查。拆分标准很朴素——两个子任务之间没有数据依赖，就适合并行。
2. **写清楚 subagent contract**。每个子 Agent 的 prompt 包含三部分：任务描述、项目约定（编码规范、路径、禁改文件）、固定输出格式（结论摘要不超过 20 行 + 产出文件路径）。
3. **并行派发**。主 Agent 在一个回合内同时发起三个子 Agent 调用，各自独立上下文，互不可见。
4. **只读并行，写入收敛**。子 Agent 只做分析并把报告写到各自的临时文件，任何对仓库的修改统一由主 Agent 在汇总阶段执行，从根上避免写冲突。
5. **汇总与留痕**。主 Agent 读取各报告文件做合并，输出总报告；每个子 Agent 的完整轨迹落盘存档，出问题能回溯。

## 踩坑点

- **上下文隔离过头**。最早我们只给子 Agent 一句任务描述，结果它不了解项目约定，产出的报告格式五花八门，主 Agent 汇总反而更累。后来固定了"简报模板"，每次派发都带上约定段落，一次跑通。
- **过度拆分**。有一次把 5 个高度相关的检查拆成 5 个子 Agent，每个都要重新读一遍配置和公共上下文，总 token 消耗比单 Agent 串行还高，也没快多少。并行收益来自独立性，不是数量。
- **摘要丢信息**。子 Agent 返回的 summary 压缩掉了关键细节，等主 Agent 想追问时子 Agent 已经销毁。改成"详细内容写文件、摘要走返回值"之后稳定多了。
- **失控循环**。一个子 Agent 在某个报错上反复重试，烧掉了大量额度。现在每个子 Agent 都有轮数上限和超时，超限即终止，并在汇总里标注失败原因。
- **MCP 工具限流**。多个子 Agent 同时打同一个 MCP 数据源会触发限流。要么错峰派发，要么给不同子 Agent 分配不同的只读数据源。

## 可复用建议

- 判断能不能并行只看一条：子任务之间是否共享可变数据。逻辑相似但读写同一份文件的任务，老老实实串行。
- Orchestrator 保持"笨"：只做规划、派发、聚合，自己不碰重工具。它越简单，整体越稳。
- 子 Agent 一律设计成幂等：任何子任务挂了可以单独重跑，不需要重跑整条链。
- 先从 2~3 个子 Agent 起步，验证汇总质量达标后再扩大规模，别一上来就 fan-out 十个。

## 总结

Subagent 编排的核心收益不只是"快"，更重要的是上下文隔离和故障隔离：主上下文保持干净，单点失败不拖垮全局。把它当成上下文工程的一部分来设计，而不是单纯的并发加速器，落地时会顺很多。
