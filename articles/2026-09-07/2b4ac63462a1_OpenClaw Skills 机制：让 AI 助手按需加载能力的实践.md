## 背景

Agent 跑一段时间后，能力清单容易失控：十几个 MCP server、一堆插件、再加上自定义 prompt 片段，全部塞进系统提示词。结果是上下文常驻占用居高不下，模型在几十个工具描述里做选择题，命中率和响应质量都在下降。

Skills 机制解决的就是这个问题：把能力拆成独立的技能包，会话启动时只注入「名字 + 一句描述」，正文和脚本在任务真正匹配时才加载。本质上是把能力上下文从常驻内存改成了懒加载。

## 问题

全量加载的代价不只是 token：

- **上下文膨胀**：每个工具的 schema 都占预算，长会话后期关键信息容易被压缩掉
- **注意力稀释**：候选工具越多，模型选错的概率越高，功能相近的工具尤其明显
- **能力无法沉淀**：踩过的坑、固定流程散落在聊天记录里，换个会话就丢了

## 做法

以「生成 PDF 周报」为例，最小结构如下：

```
skills/
└── pdf-report/
    ├── SKILL.md              # 触发条件 + 执行说明
    ├── scripts/
    │   └── build_report.py
    └── templates/
        └── weekly.md
```

`SKILL.md` 分两部分：frontmatter 里的 `description` 决定什么时候被触发，正文只在命中后才进入上下文。

```markdown
---
name: pdf-report
description: 当用户要求生成周报、导出 PDF、汇总本周成本或工单数据时使用。
---

1. 读取 data/ 下的 CSV，校验必要字段
2. 运行 scripts/build_report.py 生成图表
3. 用 templates/weekly.md 渲染，输出到 output/
```

落地步骤：

1. 在 skills 目录下按上述结构建文件夹，`description` 用「什么情况下用」的句式写，不要写成功能宣传语
2. 确定性步骤（跑脚本、固定格式转换）写成脚本放进技能包，判断性内容才写进正文
3. 重启会话重新扫描，用几句真实口吻的指令验证触发是否命中
4. 技能包进 git，和代码一样走 review

## 踩坑点

- **description 写成说明书**：写「这是一个 PDF 生成工具」基本不会触发；要写清楚触发场景和用户实际会说的话
- **正文过长**：SKILL.md 写上千行，等于变相全量加载，懒加载失去意义。正文控制在几十行，细节拆到子文件按需读取
- **脚本依赖没声明**：Python 版本、pip 包不写清，换台机器直接跑挂。在正文注明依赖，或在脚本头部做检查
- **职责重叠**：两个技能都能「处理日志」，模型会随机选。要么合并，要么在描述里明确边界
- **数量膨胀**：技能多了之后，元数据本身也成了上下文负担。定期审计，一个月没触发过的下线或归档

## 可复用建议

- 一个技能只做一件事，宁可多拆不要聚合
- description 控制在一两句话，包含触发动词和场景词
- 团队维护共享 skill 仓库，按目录划分领域，像管理基础设施代码一样管理
- 排查「不触发」问题时，先问自己：用户这句话里有没有 description 中的词

## 总结

Skills 机制的价值不在于省了多少 token，而在于把「模型该知道什么」变成一个可工程化管理的问题：按需分页、可 review、可版本化。能力不再是堆在系统提示词里的常驻负担，而是随任务动态装载的库。把高频流程沉淀成技能包，是目前性价比最高的一类 Agent 优化。
