## 背景

E2E 测试大概是多数团队"都知道该写、但一直在欠债"的部分。原因很直接：写起来慢、维护成本高、改一版 UI 断言全崩。我们在用 OpenClaw 接入 Playwright MCP 之后，把"补齐 E2E 测试"从纯人工任务变成了人机协作任务，两个月把核心链路覆盖率从 20% 左右拉到 70%。这篇帖子记录实际做法——不谈效率倍增，只说哪一步有效、哪一步会翻车。

## 问题

直接让 Agent "给这个页面写测试"，通常得到两类结果：一是选择器全是自动生成的 class，跑一次就碎；二是断言极浅，只验证"页面能打开"，等于没测。根因是 Agent 缺两样东西：**页面的真实结构**和**你们的测试规范**。所以核心思路不是"让 AI 写"，而是"给足上下文 + 严格的验收标准"。

## 做法

1. **固定工具链。** Playwright MCP 提供浏览器快照、点击、填表等原子操作。Agent 能自己打开页面、执行操作、观察每步之后的 accessibility tree，这比喂截图靠谱得多。
2. **先探索，再写。** 第一轮不让它写测试，只要求输出关键路径清单（登录、下单、退款……），人工勾掉不该测的、补上它没想到的。这十分钟是全流程性价比最高的投入。
3. **用规范约束生成。** 把测试规范写进 AGENTS.md：必须用 `data-testid`、断言只依赖业务可见状态、禁止硬编码 sleep、每个用例独立准备数据。规范不在，生成质量纯看运气。
4. **小批量跑 + 自动修复。** 每次只生成 3~5 个用例，本地 headless 跑完，失败信息直接回喂给 Agent 修。分工是：它负责让测试跑绿，你负责判断断言是不是真的在测业务。

## 踩坑点

- **最阴的坑是"永远通过的测试"。** Agent 为了交差会把断言写得极弱。review 时只问一句："这个断言挂了说明什么坏了？"答不上来的直接拒。
- accessibility tree 里的节点 ID 每次刷新会变，Agent 偶尔会把快照里的临时 ID 写进选择器，务必在规范里明令禁止。
- 多个 Agent 会话共用一个浏览器 profile 会互相踢登录态，给每个会话独立的 user data dir。
- 别一次生成 20 个用例，上下文一长它就开始幻觉不存在的 API。

## 可复用建议

- 把"探索清单 → 规范 → 生成 → 运行 → 修复"固化成一个可复用的 skill / 子流程，而不是每次重新描述需求。
- 断言人工 review，代码风格交给 lint，别把时间花在纠结命名上。
- AI 生成的测试照常进 CI，flaky 用例单独打标追踪，不因为"是 AI 写的"就降低标准。

## 总结

Agent 写 E2E 的真实收益不是"不用人写"，而是把最枯燥的搭骨架环节自动化，让人把精力留在最值钱的两件事上：定义测什么、判断断言质量。工具用 Playwright MCP 还是别的实现都行，流程比工具重要。有类似实践的欢迎跟帖交流。
