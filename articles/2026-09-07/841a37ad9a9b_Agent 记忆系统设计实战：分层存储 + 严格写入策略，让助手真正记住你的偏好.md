## 背景

LLM 本身无状态，每次会话都是“失忆”重启。在 OpenClaw 里跑 Agent 时，最常见的抱怨不是模型不够聪明，而是“每次都要重新说一遍：用 pnpm、测试跑 vitest、commit 别加 emoji”。这些偏好琐碎、分散、跨会话，靠人肉每次塞进 system prompt 既贵又不现实。记忆系统要解决的就是这个 gap。

## 问题：为什么常见做法都不够用

三种典型方案各有硬伤：

1. **全量塞 system prompt**：上下文膨胀、注意力稀释、成本线性涨。塞到几十条后，模型反而开始“忘记”重点。
2. **直接对聊天记录做 RAG**：向量相似度擅长按话题召回，但偏好不是话题——“总是开 TypeScript strict” 和某次聊 TS 的对话，在 embedding 空间里关系很弱。
3. **让模型自由发挥记**：没有 schema、没有去重，三天后记忆库全是“用户今天心情不错”这类噪声。

核心矛盾：写入太勤污染上下文，写入太懒又记不住。

## 做法：分层存储 + 三条写入纪律

存储分三层：

- **工作记忆**：当前会话上下文，不落盘；
- **情景记忆**：会话结束后的摘要（做了什么、定了什么），进向量库，按需召回；
- **偏好记忆**：结构化存储，这是重点。每条带 schema：`{ scope: user | project, type: preference | decision | constraint, content, confidence, updated_at }`。

写入策略比存储选型更重要：

1. **不在对话中实时写**。会话结束（或每 N 轮）跑一次抽取 pass，prompt 里写死约束：只提取“跨会话仍成立的事实”，忽略寒暄和一次性指令。
2. **写入前查重合并**。新偏好与旧记录冲突时（“用 tabs” → “改用 spaces”），不直接覆盖，置 superseded 标记并保留版本，最新一条生效。
3. **低置信度先问用户**：“这个要不要记下来？”一次确认能过滤掉八成垃圾。

读取策略：

- 偏好记忆小而结构化，会话启动时按 scope 全量注入，控制在 300–500 token；
- 情景记忆只在相关时走 RAG，不默认注入。

工程上，我把 `memory_write` / `memory_search` / `memory_list` 做成了 MCP tools。好处有两个：任何支持 MCP 的客户端都能复用这套记忆；用户可以用 `memory_list` 随时查看、编辑、删除——可审计这件事，直接决定用户信不信你的记忆系统。

## 踩坑点

- **scope 混淆**：把个人偏好写进 project 层，换项目立刻翻车。scope 必须在写入时定死，不要事后猜。
- **抽取 pass 太激进**：“只记持久事实”这条约束要写得非常硬，否则模型看到什么都想存。
- **没有冲突处理**：旧偏好压过新偏好，用户以为说了没用。版本化 + `updated_at` 是底线。
- **注入无上限**：记忆涨到几十条后忘了设 token 预算，一次注入吃掉小半个窗口。
- **用纯向量召回偏好**：偏好必须结构化，向量库只管情景摘要。

## 可复用建议

1. 别一上来就上向量库。一张 SQLite 表加 schema 字段就能撑起偏好记忆，向量库留给情景摘要。
2. 把记忆操作做成显式工具而非隐式行为，可观测、可测试、可移植。
3. 准备一个小评测集：跨 3 个会话后问“我的测试框架是什么”，每次改 prompt 后回归跑一遍，防止把记忆改坏。
4. 给记忆加 TTL 或衰减机制——过期的偏好比没有记忆更糟。

## 总结

记忆系统本质是工程问题：schema、写入策略、scope 隔离、token 预算、可审计，每一项的影响都比“换个更强的模型”大。从一张结构化偏好表起步，先让 20 条高频偏好被稳定记住，再考虑扩展——这比一步到位的“智能记忆”靠谱得多。
