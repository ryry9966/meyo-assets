## 背景

E2E 测试大概是前端工程里投入产出比最难看的一块：写起来慢、断言脆、UI 一改就红一片，团队里通常只有一两个人愿意维护。Agent 框架和 MCP 成熟之后，一个自然的想法出现了：让模型自己驱动浏览器，把操作路径直接翻译成测试代码。我们在一个中后台项目里试了两个月，下面是能跑通的流程和踩过的坑。

## 问题

直接把需求文档丢给模型说“帮我写 Playwright 测试”，产出基本不可用：选择器靠 class 名猜、等待全靠 sleep、断言只检查页面不报错。这类测试 CI 全绿，但什么都测不出来——比没写更糟，因为它制造了虚假的安全感。

核心矛盾在于：模型没有真实页面上下文，而人又不想手动把上下文喂给它。

## 做法

方案是把 Agent 接入 MCP，只给它两类工具——浏览器操作和仓库读写，流程分四步：

1. **真实操作驱动生成**。通过 Playwright MCP 让 Agent 实际打开页面走用户路径，每一步记录可访问性快照而非整页 DOM，基于快照生成选择器，优先 `data-testid`，其次 role + name。
2. **约定先行**。仓库里放一份测试风格说明（命名、断言粒度、禁止 sleep、必须等待状态而非时间），作为系统上下文注入。这一步的收益比换更强的模型大得多。
3. **人工审 PR，Agent 不直接合**。审的重点只有两条：断言是否真的校验了业务结果；失败时能否定位原因。弱断言一律打回。
4. **失败自愈回路**。CI 挂掉的用例把报错和截图回喂给 Agent，它先判断是产品 bug 还是选择器漂移：前者开 issue，后者提修复 PR，人做最终裁决。

两个月后的结果是：核心链路 40 多条用例里约七成由 Agent 生成或修复，人力主要花在定义“哪些流程值得测”。

## 踩坑点

- **永远通过的测试**：Agent 倾向写“能跑过”的用例，断言经常退化成形式化检查，审 PR 时这是第一优先级。
- **sleep 依赖**：不约束的话 Agent 会大量使用固定等待，用例又慢又 flaky，风格说明里必须显式禁止。
- **选择器漂移**：深层 CSS 路径重构一次全崩，必须统一要求 `data-testid` 并配套 review 规范。
- **测试数据污染**：并行跑时写死的数据互相打架，最后抽了带随机后缀的 seed 工具才稳住。
- **过度生成**：放开限制它一晚能产出两百条重复用例。对策是维护一份人工确认的“黄金流程清单”，每次只让它覆盖清单的下一项。

## 可复用建议

- 给 Agent 的不是权限而是边界：工具白名单只留浏览器和仓库读写，禁止执行任意命令。
- 测试规范当作 prompt 资产维护，和代码一起进版本管理。
- 自愈回路只允许提 PR，合入权始终在人手里。
- 先用 5～10 条核心流程试点，验证断言质量后再扩量，别一上来全量铺开。

## 总结

Agent 写 E2E 的价值不在“全自动”，而在于把最枯燥的三件事——选择器、等待、样板代码——从人手里拿走。测试策略、断言标准和合入门槛仍必须由人定义。把它当成一个手很快但需要严格 code review 的初级工程师来用，体验会好很多；当成无人值守的测试机器人来用，大概率翻车。
