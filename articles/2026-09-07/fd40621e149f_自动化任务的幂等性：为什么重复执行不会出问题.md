## 背景

跑 OpenClaw 自动化一段时间后，你会发现一个规律：**任务被触发两次不是异常，而是常态**。定时任务重叠、Agent 超时重试、消息重投、用户手动补跑——触发链路上的每一环都可能让同一个逻辑执行多遍。MCP 客户端重试、cron 补跑错过的调度点、插件事件重复投递，都是日常。

## 问题

幂等性（Idempotency）指：同一操作执行一次和执行多次，最终效果一致。很多自动化脚本天然不满足：

- 每天追加写一次摘要文件 → 重跑就是两份摘要
- 收到 webhook 就创建工单 → 重试就是重复工单
- Agent 调 MCP 工具发通知 → 超时重试，用户收到两条一样的消息

共同点在于：这些操作是"做一次加一次"，而不是"确保达到某个状态"。

## 做法

1. **给每次逻辑执行定一个幂等键。** 最简单的形式：任务名 + 业务时间窗。比如每日摘要用 `digest-2025-06-01`，同一窗口内重复触发只执行一次。
2. **先查状态，再决定写不写。** 执行前查执行记录（文件、SQLite 等任意持久化存储），键存在就跳过。别用内存变量去重——进程一重启就失效。
3. **把"追加操作"改写成"确保状态"。** `append(summary)` 改成 `upsert(key=今天)`；`create(ticket)` 改成 `ensure(ticket_id)`。目标态语义天然幂等。
4. **给 MCP 工具留去重口子。** 自己写 MCP 工具时，加一个可选的 `idempotency_key` 参数，服务端按 key 去重并返回首次结果，调用方重试就是安全的。
5. **记录执行结果。** 成功、失败、跳过都落盘，排查时有据可查。

## 踩坑点

- **"查了再写"不是原子的。** 两个实例同时查到"没有执行记录"，然后同时执行。多实例部署时，要么加锁，要么靠存储层约束兜底（比如 SQLite 唯一索引冲突即视为已执行）。
- **部分失败最坑。** 副作用已经发生（消息发出去了），但响应没传回来，调用方重试。去重判断必须放在副作用发生**之前**。
- **幂等键的粒度。** 太粗（只用任务名）会拦掉合法补跑；太细（每次触发新生成）等于没去重。键应绑定"业务上的一次执行"，不是"技术上的一次调用"。
- **时间窗的时区。** 用日期做键，先定死 UTC 还是本地时区，否则跨天任务会出现"昨天没跑、今天跑两次"。

## 可复用建议

- 写任何定时/触发型任务前先问一句：**这个任务跑两遍会怎样？** 答不上来就先设计幂等键。
- 能用"目标态"描述的任务，别用"动作序列"描述。
- 上线前在测试环境故意连跑两次，验证结果一致——这应该成为自动化任务的验收标准之一。
- 团队内沉淀一份通用的执行记录约定（存储位置、键格式），插件和脚本都往里写，避免各搞一套。

## 总结

幂等性不是高级概念，本质是防御性设计：承认"重复触发一定会发生"，然后让系统在重复面前保持稳定。对 OpenClaw 用户来说，从给每个定时任务加一个幂等键开始，成本很低，收益立竿见影——你可以放心重试、放心补跑、放心调调度频率，而不用担心数据被写坏。
