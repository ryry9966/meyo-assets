## 背景

在 OpenClaw 里跑一个长期 Agent，迟早会碰到"心跳"问题：助手不能只在你发消息时才活着。定时提醒、盯一个长任务、监控目录变化、定期同步 MCP 数据源——这些都需要 Agent 在"没人说话"的时候自己醒过来。

OpenClaw 的心跳机制本质上是定时唤醒 + 读取心跳清单，这是一个天然的**轮询模型**。但轮询不是唯一选择，事件推送（webhook、MCP 通知）也可以驱动 Agent。心跳设计的核心问题其实是：**谁来决定 Agent 什么时候醒来？**

## 问题

**轮询的两个代价：**

- **成本**：每次心跳都是一次完整唤醒。如果心跳直接走 LLM，5 分钟一次间隔一天就是 288 次唤醒，而其中绝大多数无事可做，token 全部白烧。
- **延迟**：事件落在两次心跳之间，最坏要等一个完整周期。

**推送的代价：**

- **可靠性**：Agent 重启、断网、部署窗口期，推送消息直接丢。本地跑的 Agent 还要解决回调可达性，webhook 并不总是可行。
- **调试难度**：轮询出问题看日志就行；推送链路长（事件源 → 回调 → 队列 → Agent），断在哪一环都要排查。

## 做法

我们的结论是混合：**推送为主，轮询兜底**。落地步骤：

1. **给事件源分级**。按容忍延迟分三类：秒级（用户消息、关键告警）、分钟级（文件变更、CI 结果）、小时级（日报、同步）。分级决定走哪条链路。
2. **建一个便宜的门卫**。所有事件先进轻量队列（一个 SQLite 表就够）。Agent 醒来后先由非 LLM 的 gate 检查队列，空队列直接睡回去，不消耗 token。
3. **秒级事件走推送**。MCP 通知或回调写入队列并触发唤醒。顺序必须是先落盘、再触发，通知失败也不丢事件。
4. **轮询降级为兜底**。心跳间隔拉长到 10–30 分钟，职责只剩两个：扫队列、补偿漏掉的事件。
5. **幂等是硬要求**。每个事件带去重键，处理前先查重。推送重试和轮询补偿必然带来重复投递，不幂等就会重复回复用户。
6. **记账**。记录每次唤醒的原因、token 花费、事件端到端延迟。没有这些数字，调间隔全靠猜。

## 踩坑点

- **心跳直接调 LLM**。最贵的写法。务必在唤醒和模型调用之间加一层便宜判断。
- **推送没落盘**。回调到达时 Agent 恰好在重启，事件就没了。先写队列再触发，顺序不能反。
- **所有事件都走推送**。把小时级日报也做成实时推送，链路复杂度翻倍，收益为零。
- **心跳里干重活**。心跳处理器自己卡 30 秒，下一跳直接堆积。心跳只做"发现该做的事"，重活交给任务队列。
- **多 Agent 同间隔轮询**。统一间隔会造成周期性尖峰，加随机抖动（jitter）打散。
- **全量记录心跳日志**。"无事发生"也写日志，两天撑爆磁盘。只记异常和有效唤醒。

## 可复用建议

- 默认架构：**队列 + 便宜 gate + 推送触发 + 长间隔轮询兜底**。
- 先问"这个事件能容忍多久延迟"，再选链路，而不是反过来。
- 任何跨链路的事件都假设会重复到达，处理逻辑一律幂等。
- 心跳间隔是成本旋钮：有记账数据后再调，不要拍脑袋。

## 总结

轮询和推送不是二选一。轮询简单可靠，适合兜底；推送低延迟，适合关键路径；队列是两者之间的缓冲层。给 OpenClaw Agent 做心跳，建议顺序是：先建队列和 gate，再加推送，最后把轮询拉长当保险。这个顺序反过来做，返工概率很高。
