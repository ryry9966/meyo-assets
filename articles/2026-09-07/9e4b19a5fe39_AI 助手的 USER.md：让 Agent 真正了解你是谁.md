## 背景

用 OpenClaw 这类常驻 Agent 一段时间后，你会反复遇到同一个问题：每次新会话，模型都不认识你。你是谁、用什么技术栈、偏好什么回复风格、有哪些明确的"不要做"——这些要么靠每次重复，要么靠 MEMORY.md 里的零散记录碰运气。系统提示词是面向所有人的，而你需要的恰恰是"只属于你"的那部分上下文。

USER.md 就是补这一块的：一个放在工作区根目录、随会话注入上下文的静态个人档案。它不神秘，本质上是把你对助手的长期期望固化成一个文件。

## 问题

观察自己和社区里几个跑了较久的工作区，失败模式集中在三类：

1. **信息散落**。个人背景、偏好、项目上下文混在 MEMORY.md 和聊天记录里，模型每次都要"考古"，提取结果不稳定。
2. **写成小作文**。大段自我叙述，关键信息密度低，还白白挤占上下文预算。
3. **边界不清**。把 API key、证件号也写进去——USER.md 会被注入每一次会话，任何能读工作区的插件都看得见。

## 做法

我目前的 USER.md 约 80 行，结构如下：

```markdown
# USER
## 基本信息
- 职业 / 角色 / 所在时区
## 技术环境
- 主力语言、框架、OS、部署方式
## 协作偏好
- 先给结论，再给解释
- 代码默认带错误处理，不写解释显而易见逻辑的注释
## 禁区
- 不主动重构没要求动的代码
## 当前项目快照
- 三五行，最近在做什么
```

几条写法经验：

- **声明式短句，一行一条**。模型对声明式规则的执行效率远高于叙事段落。
- **控制在 100 行以内**。它每次会话都注入，长度直接吃上下文预算。
- **和 MEMORY.md 分工明确**：USER.md 管"我是谁"，相对稳定；MEMORY.md 管"发生过什么"，动态累积。交叉内容定期归位。
- **放 git 管版本**。改坏了能回滚，也能回看你对 Agent 期望的演变。

一个省力的维护方式：每月让 Agent 自己审查一次，提示词就一句——"对照近一个月会话，指出 USER.md 中过时或缺失的条目，只给 diff 建议，不要直接改"。人只负责审和批。

## 踩坑点

- **敏感信息别进 USER.md**。密钥走环境变量或密钥管理；注入上下文的文件要按"最坏情况被第三方插件读到"来设计。
- **别和 SOUL.md 打架**。人格、语气只在 SOUL.md 定义，USER.md 只写事实和偏好。两处重复定义，Agent 行为会摇摆。
- **别指望它当记忆**。USER.md 是静态画像，不是记忆系统。会话中临时产生的事实进 MEMORY.md，别往这里堆。
- **写了不维护等于没写**。过时的技术栈比没有更糟——模型会基于错误前提给建议。

## 可复用建议

- 起步用五个分区模板：基本信息、技术环境、协作偏好、禁区、项目快照，够用了。
- 规则必须可执行。"沟通高效一点"是废话，"先给结论，再给理由"才是规则。
- 把 USER.md 当代码 review：每条改动问一句"这条能被模型无歧义地执行吗"。

## 总结

在 OpenClaw 的各类配置里，USER.md 大概是投入产出比最高的一个：十分钟写第一版，之后每月修剪十分钟，换来的是 Agent 不再每次从零认识你。它解决不了记忆问题，也替代不了好的系统提示词，但作为"你是谁"的单一事实来源，值得一开始就写对。
