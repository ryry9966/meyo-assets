## 背景

我平时用 OpenClaw 挂了几个自动化任务：定时整理浏览记录生成日报、读本地日志做摘要、通过几个 MCP server 操作文件系统。这些任务每天要调用上百次模型，走云端 API 既花钱，又把笔记、浏览记录这些隐私数据送了出去。于是有了把模型搬回本地的念头。本文记录在一张 8GB 显存的显卡上，把本地模型接进 Agent 工作流的完整过程。

## 问题

先说结论：本地跑模型和本地跑聊天是两回事。聊天只要首 token 快就行，而 Agent 负载有三个硬要求：

1. **工具调用必须稳定**——function calling 格式错一次，整条自动化链路就断；
2. **上下文要够长**——系统提示 + MCP 工具描述 + 多轮历史，很容易吃掉一万多 token；
3. **吞吐要扛得住并发**——Agent 并行发多个工具调用时不能排队等到超时。

## 做法

**1. 先算显存账。** 经验公式：模型文件大小 + KV cache ≈ 显存占用。8GB 显存跑 7B 的 Q4_K_M 量化很从容；14B 需要压缩 KV cache 或部分 offload；32B 基本要 24GB。先明确预算再选模型。

**2. 运行时选 Ollama。** 对个人用户，Ollama 的 OpenAI 兼容接口最省事，Agent 网关里改一行 base URL 就能接上。追求极限性能再考虑 llama.cpp 或 vLLM。

**3. 模型选 Qwen 系列。** 中文场景 + 原生工具调用支持，7B/14B 是家用卡的主力区间。量化默认 Q4_K_M，显存富余再升 Q5。

**4. 三个必改参数：**
- `num_ctx` 拉到 16384 起，默认值对 Agent 来说严重不够；
- `keep_alive` 设长一点，避免每次调用重新加载权重；
- 开 flash attention + KV cache 量化（`q8_0`），长上下文下省一大截显存。

**5. 接入后先跑冒烟测试。** 让 Agent 连续执行 20 次工具调用，统计成功率和 tokens/s，达标了再上生产任务。

## 踩坑点

- **上下文静默截断**：没改 `num_ctx` 时，长对话开头的内容被直接丢掉，表现为 Agent "忘了"系统提示，日志里却看不出原因。
- **量化后工具调用退化**：同一个模型，Q4 下偶尔输出残缺 JSON。解法是启用结构化输出约束（Ollama 的 structured outputs），把 schema 硬约束住，成功率立刻拉满。
- **temperature 没调**：默认 0.8 对工具调用太高，降到 0.1~0.2 稳定很多。
- **并发排队**：Ollama 默认串行处理请求，Agent 并行发三个工具调用会互相等。要么调大 `OLLAMA_NUM_PARALLEL`，要么接受排队并给超时留足余量。

## 可复用建议

1. **分层路由比全本地更实际**：分类、摘要、格式化这类简单任务交给本地 7B，复杂规划仍走云端。成本降一个量级，体验几乎不损失。
2. **把性能数据记下来**：首 token 延迟、tokens/s、单任务总耗时，换模型换参数时有对照，不靠玄学。
3. **工具描述做减法**：本地模型的上下文更金贵，MCP server 的工具列表能砍就砍——每个省下的 token 都是真金白银的显存。

## 总结

家用卡跑 Agent 已经不是玩票：8GB 显存跑 7B，足够覆盖一半以上的日常自动化任务。换来的不只是省钱，而是任务数据不出门、服务不限流、凌晨三点也能跑批。真正的工作量不在"装个 Ollama"，而在上下文长度、并发、结构化输出这几处细节调校。建议从一个低风险任务（比如日志摘要）开始接入，跑稳一周再逐步扩大范围。
