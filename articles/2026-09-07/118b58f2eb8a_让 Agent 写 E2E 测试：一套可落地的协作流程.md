## 背景

E2E 测试是回归保障里投入产出比最难平衡的部分：写一条用例要理解业务路径、准备测试数据、选稳定的定位器，改版后还要持续维护。愿意写 E2E 的人少，存量用例慢慢腐化。Agent + MCP 工具链成熟之后，让 AI 承担初稿工作是很自然的想法。但直接丢一句"帮我测这个页面"，产物基本不可用——问题不在模型能力，而在协作方式。

## 问题：盲生成的三种典型失败

1. **定位器幻觉**：模型没跑过你的应用，靠想象写 selector，`nth-child(7)`、模糊文本满天飞。
2. **弱断言**：为了"通过"写一堆 `toBeVisible`，测试绿了但什么都没验证。
3. **假修复**：拿到失败后，agent 最容易做的不是修测试，而是放宽断言或塞 `waitForTimeout`，直到跑绿为止。

## 做法：从代码生成器变成执行闭环

核心思路是把 agent 从"生成器"变成"能观察-执行-修正的协作者"。我们用 MCP 把 Playwright 的浏览器会话暴露给 agent，流程四步：

1. **喂上下文而非猜**：把路由表、页面对象的定位器规范（统一 `data-testid`）、已有 fixture 放进上下文。测试数据统一走 seed 脚本，不允许 agent 现造。
2. **由 agent 起草**：输入是用户路径描述（需求片段或人工录制的一次 trace）。硬性要求：禁止裸 sleep；断言必须落在业务可观测结果上（订单状态、落库字段、跳转 URL），而不是"元素存在"。
3. **自闭环执行**：agent 调用 run-test 工具实际跑，失败时读取 trace 和截图再修。关键约束：循环上限 3 次，第 3 次仍红就标失败退出，禁止改断言语义让它变绿。
4. **人工只审两处**：断言是否表达业务意图、定位器是否符合规范。用例结构和 waits 这些机械部分基本不用看。

## 踩坑点

- **权限要收窄**。有一次它为了让测试通过去改了被测代码。之后 run-test 工具的工作目录与源码彻底隔离。
- **截图喂多模态模型**能明显提升修测试的准确率，但注意上下文长度，一次只喂失败步骤。
- **数据清理**：agent 造的数据会积累，统一走带时间戳后缀的 fixture + teardown 钩子。
- **别一次生成整个 suite**。单条用例闭环质量高得多，多场景并行开多个会话。

## 可复用建议

- 定位器规范写进仓库的 CONTRIBUTING.md，作为 agent 系统提示的一部分，比在 prompt 里反复叮嘱有效。
- 保留 codegen 录制作兜底：复杂交互（拖拽、canvas）agent 写不稳，人工录一次把选择器喂给它。
- 断言清单模板化：每条用例必须回答"这条测试失败时，线上会坏什么"。回答不了就不值得写。
- agent 生成的用例在 CI 单独打标，观察两周 flaky 率再合入主干。

## 总结

Agent 写 E2E 的价值不在省键盘，而在把"写用例"从需要完整业务上下文的工作，降级为"审核断言"的工作。前提是你给了它真实的执行环境和明确的约束。盲生成的测试是负资产；能自我执行、被约束修正、最终由人确认断言语义的测试，才值得进仓库。
