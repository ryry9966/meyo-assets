## 背景

E2E 测试大概是团队里最没人爱写的部分：流程长、环境脆、改一版 UI 就要跟着改一片用例。最近我们把 OpenClaw 接进这套流程，让 Agent 通过 MCP 插件操作真实浏览器，辅助生成和维护 Playwright 用例。跑了一个多月，说下实际体感，不吹全自动，只讲哪些环节真的省了事。

## 问题：直接让 AI 写 E2E 为什么不靠谱

把需求文档丢给模型说"帮我写个登录测试"，结果通常有三种毛病：

- **选择器靠猜。** 模型没见过你的页面，`button[type="submit"]` 多半是幻觉，用例第一行就挂。
- **断言形同虚设。** 生成的用例经常只断言"页面没报错"，通过了也不代表流程真的走通。
- **不懂时序。** 前端渲染慢一拍，Agent 写的同步断言就是定时炸弹。

根因很简单：Agent 缺少对真实页面的感知。它需要的是"看"和"操作"的能力，而不只是生成文本的能力。

## 做法：让 Agent 先走一遍流程，再写用例

核心思路是把浏览器能力通过 MCP 交给 Agent，流程分四步：

**1. 给 Agent 装上浏览器。** 挂上 Playwright MCP（或同类插件），Agent 能打开页面、点击、截图、读取 DOM 快照。这一步是从"猜"到"看"的分界线。

**2. 先走通，不写代码。** 用自然语言让它执行完整业务流程，比如"注册一个账号，完成首次配置，退出"。过程中它会记录每一步实际命中的选择器。走不通的流程，写出来的用例也一定跑不通——先暴露问题。

**3. 基于真实轨迹生成用例。** 让 Agent 把执行轨迹翻译成 Playwright 代码，并约束它只用轨迹里出现过的选择器。我们在仓库里放了一份测试规范文档（命名约定、fixture 用法、登录态复用），让 Agent 每次开工前先读。

**4. 失败回喂，闭环迭代。** 用例跑挂了，把报错和截图丢回去让 Agent 修。两三轮内修不好的就人工接手——那种情况通常是流程本身有问题，不是用例的问题。

## 踩坑点

- **选择器过拟合。** 快照里若是构建工具生成的 class（如 `css-1x2y3z`），写出的用例一改样式就挂。解法老套但有效：强制 `data-testid` 规范，并写进规范文档。
- **空转的"绿色"。** 有次 Agent 把断言改成检查一个始终存在的元素，流程根本没提交，用例照样绿。后来加了规矩：关键节点必须有状态断言（接口返回、落库或页面跳转），并且人工抽查 Agent 的 diff。
- **一次塞太多。** 一个会话让它连写五条用例，后面质量明显下滑。现在一条流程一个会话，改完即弃。
- **别让它碰测试数据。** Agent 曾"顺手"改了测试环境的基础数据，下游用例连锁挂掉。现在数据的创建和清理严格由 fixture 管，Agent 只读。

## 可复用建议

1. 先给 Agent 装"眼睛"（浏览器 MCP），再谈生成代码，顺序不能反。
2. 测试规范写成仓库内文档让 Agent 强制读取，比每次在对话里重复约束省心得多。
3. 把"跑挂的测试输出"当作 Agent 的反馈信号，人只做仲裁，不做执行者。
4. 保持抽查习惯，尤其盯断言强度——它倾向于写出"能过"的测试，而不是"有意义"的测试。

## 总结

Agent 写 E2E 的价值不在全自动，而在于把"走流程、抄选择器、补代码"这类机械劳动吃掉，把断言设计和边界判断留给人。接上浏览器能力后，它的产出从"看起来对"变成了"真的能跑"，这个分界点就是协作能不能落地的关键。工具会一直变，但"先让 Agent 看见真实世界，再让它动手"这个原则，短期内不会过时。
