## 背景

玩 Agent 的人大多已经习惯了 CLAUDE.md / AGENTS.md 这类项目级上下文文件：进仓库、读约定、按规范干活。但实践久了会发现一个盲区——Agent 知道项目是什么，却不知道"我"是谁。

每次新会话，我都要重复交代：主力语言是 Go 不是 Python，机器是 macOS + Homebrew，代码注释用中文，别写长篇原理科普。这些信息跨项目、跨工具通用，却散落在每次对话里，说一遍忘一遍。

## 做法

我的方案是在全局配置目录维护一份 USER.md（比如 `~/.openclaw/USER.md`），在 Agent 启动引导阶段注入系统提示。结构和项目文件刻意分开：

- **身份与环境**：角色（后端/平台）、操作系统、包管理器、网络与代理约束
- **技术栈偏好**：语言版本、框架选型，以及明确"不用什么"——这往往比"用什么"信息量更大
- **协作风格**：回答详略、注释语言、是否先给方案再动手
- **禁区清单**：不自动 commit、不改全局配置等硬约束

写法上两条原则。第一，短。全文控制在 60 行以内，它是每次会话的固定开销，长文等于烧 token。第二，写"偏好 + 理由"，而不是命令式法条。"默认用 table-driven 测试，方便补 case"就比"必须用 table-driven"在边界场景下表现更好。

## 分层与加载

关键设计是三层分离：USER.md 管"我是谁"，项目里的 AGENTS.md 管"这个项目怎么干"，会话记忆管"最近聊到哪"。USER.md 走全局注入，项目文件进仓库，互不污染。我把它放进个人 dotfiles 仓库做版本管理，换机器直接同步。

加载上没搞复杂机制：启动模板里一行 include 引用即可，用 MCP resource 暴露也行，本质是保证它稳定出现在 system prompt 里。

## 踩坑点

1. **塞项目细节**。早期我把某个服务的端口约定写进了 USER.md，结果切到别的项目时 Agent 一直引用错误上下文。个人文件只放跨项目成立的结论。
2. **敏感信息**。这份文件会被同步、可能被截图分享，密钥、内网地址一律用占位符，真实值走环境变量。
3. **信息过期**。换了技术栈没更新文件，Agent 按旧偏好给方案，比没有文件更误导。我定了节奏：每季度 review 一次，当配置维护。
4. **写成法律条文**。满篇"永远/必须"会让 Agent 在该变通时变得僵硬，偏好式表述的鲁棒性明显更好。

## 可复用建议

- 把 USER.md 当配置而不是笔记：进版本库、有 review 周期、改动留 commit message
- 用"决策记录"口吻写：为什么偏好比偏好本身更有迁移价值
- 团队场景：USER.md 属于个人，不进公司仓库；可沉淀一份脱敏 TEMPLATE 供同事起稿
- 与 Agent 自带记忆互补：记忆是概率性的，USER.md 是确定性的，冲突时以后者为准

## 总结

Agent 的能力上限取决于上下文质量，而"用户是谁"是上下文里最稳定、复用率最高的部分。一份 60 行以内的 USER.md，维护成本几乎为零，换来的是每个新会话少解释十分钟。它不炫技，但属于那种"做过就回不去"的基础工程。
