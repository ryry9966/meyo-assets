## 背景

Agent 项目跑久了会发现一个规律：模型本身很少是故障源，真正打断自动化流程的，几乎都是外部依赖——LLM 供应商限流、MCP 工具背后的第三方 API 超时、token 过期、DNS 抖动。单次请求失败不可怕，可怕的是失败发生在 Agent 循环里。

## 问题：失败会被循环放大

Agent 循环对失败有乘数效应，三个典型场景：

1. **重试风暴**：SDK 内置重试 + 你在 wrapper 里写的重试 + 模型自己决定"再试一次"，三层叠加后一个 429 能打出几十个请求，直接把配额锁死。
2. **假成功**：工具抛异常被上层 `try/except` 吞掉，返回空结果，模型以为查询正常，基于空数据继续推理，错误被带到下游。
3. **卡死**：HTTP 客户端没设超时，一条挂起的连接让整个编排线程永远等下去。

## 做法：四层防线

### 1. 先分类，再重试

错误分两类处理：**可重试**（429 / 5xx / 超时 / 网络抖动）走指数退避 + jitter，尊重 `Retry-After`，上限 3 次左右；**不可重试**（400 / 401 / 403 / 404）立即失败并回传原因，重试只是在浪费 token。

### 2. 统一调用外壳

所有工具和 MCP 调用走同一个 wrapper，内部做四件事：连接/读取超时、错误分类、受控重试、日志埋点。无论上游实现多糙，外壳保证行为一致。关键设计：失败时不抛裸异常，而是返回结构化错误：

```json
{
  "ok": false,
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "message": "上游搜索服务超时",
  "hint": "可改用备选工具或稍后重试"
}
```

模型拿到的是可决策的信息，不是一堆堆栈，也不是静默的空值。

### 3. 熔断与降级

同一工具连续失败 N 次就打开熔断器，冷却期内快速失败，不再去敲上游。降级路径写死在配置里：主 API → 备 API → 带明确标记的降级结果。最重要的一步：把熔断状态注入上下文，让规划层"知道"这个工具当前不健康，模型通常会自己换路线，而不是反复撞墙。

### 4. 断点与幂等

长任务做 checkpoint，恢复时从最近状态继续，而不是重跑全程。所有有副作用的调用（写库、发消息、支付类）必须带幂等键——否则重试就是重复扣款。

## 踩坑点

- **重试只做一层**。SDK 自动重试和 wrapper 重试二选一，叠着用就是攻击自己。
- **非幂等操作默认不重试**，除非确认有幂等键。
- **退避不加 jitter**，多 worker 场景会同步重试，形成惊群。
- **熔断状态要跨进程共享**（放 Redis 之类），否则每个 worker 各自去试探挂掉的服务。
- **给模型的错误信息要克制**：完整堆栈会诱发幻觉式修复，只说"出错了"会让模型瞎猜。一两句结构化描述刚好。
- **别忘了总预算超时**：单次调用有超时不够，整个任务还要有 wall-clock 上限，防止"每步都正常但整体跑不完"。

## 可复用建议

- 写一个通用 tool harness（装饰器或中间件），超时/分类/重试/结构化错误只实现一次，所有插件复用。
- 给团队定一个统一的错误返回 schema，Agent 端处理逻辑就能收敛成一份代码。
- 把工具健康度当作一等公民暴露给规划层，而不是藏在日志里。
- 熔断打开时打告警——人应该在模型绕路之前就知道出了问题。

## 总结

错误恢复不是 prompt 问题，是系统工程问题。Agent 循环会放大你写下的任何失败处理逻辑：处理得好，一次失败只是触发重新规划的信号；处理不好，一次限流就是整条流水线的雪崩。先把外壳建扎实，再谈智能化。
