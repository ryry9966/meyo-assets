## 背景

Agent 的能力面在快速扩大。接上 MCP 之后，一个本地常驻的助手可以读文件、跑 shell、调 API、发消息，理论上能碰的东西和半个运维差不太多。但实际用下来都会遇到同一个尴尬：全放开，迟早出事；事事都问，人就退化成确认按钮点击器，而且很快会开始无脑点"允许"。

权限边界的问题本质上不是"给多少权限"，而是"什么时候该打断人"。这里整理一套我们在实际部署中沉淀下来的分级规则，足够简单，可以直接抄。

## 问题

把 Agent 可能执行的动作摊开看，难的不是技术实现，而是判定。同一个"发消息"动作，往群里发日报草稿和给客户发正式通知，风险完全不同。所以按动作名做黑白名单是不够的，必须按动作的性质分级。

## 做法：两维度四象限

我们用两个维度给每个工具打标：

- **可逆性**：做错了能不能撤回？（写临时文件 vs 删目录）
- **影响面**：只影响自己的环境，还是会影响外部世界？（本地重建索引 vs 向外部系统发请求）

由此得到四个象限：

| | 影响面：内部 | 影响面：外部 |
|---|---|---|
| **可逆** | 自动执行 + 日志 | 自动执行，但走可撤回路径（草稿、可删消息） |
| **不可逆** | 首次确认，之后进白名单 | 必须人审，带上下文确认 |

对应到实现：

1. **在工具定义层打标**。给 MCP 工具或插件配置显式声明 risk 级别，不要散落在 system prompt 里靠模型自觉。
2. **硬闸门**。高风险调用在执行层强制拦截，进入"提案—确认—执行"流程：Agent 先产出将要执行的具体内容（命令原文、消息全文、diff），人看到实体再批。规则只写在 prompt 里不算数，长对话中一定会漂移。
3. **确认要带上下文**。拒绝"是否继续？"这种确认，要给"将执行 X，影响 Y，回滚方式是 Z"。
4. **限流和预算**。单位时间操作次数、批量规模、金额上限，超了必须问。
5. **审计日志**。所有自动执行的动作落盘。跑一周后回看日志来定级，比拍脑袋准得多。

## 踩坑点

- **确认疲劳**是最大的坑。问得越多，人批准得越机械，权限系统反而失效。宁可让白名单覆盖 90% 的高频低风险操作，把人的注意力留给真正需要判断的 10%。
- **白名单蔓延**。每次图省事"临时"加进免确认的条目，半年后没人记得当初为什么加。免确认清单要定期清理，最好默认带过期时间。
- **确认超时的默认行为**。人不在时任务挂起，有些实现超时后会自动执行——超时必须默认取消，宁可重跑，不可默认放行。
- **Agent 拆分调用绕过阈值**。比如把一次大批量删除拆成多次小调用。阈值判断要放在执行层做聚合统计，不能只看单次调用参数。

## 可复用建议

- 默认拒绝，显式放行（deny by default），别反过来。
- 新接入的工具先跑两周 dry-run / 只读模式，用真实日志定级后再放开。
- 外发类操作永远走草稿或预览路径——把"不可逆"变成"可逆"，是最便宜的降险手段。
- 把权限当产品问题迭代：每两周看一次审计日志，调整一次分级。

## 总结

权限边界不是"安全 vs 效率"的二选一，而是把"问人"这个动作本身设计好：问得少，问得准，问的时候把决策所需的信息全部摆出来。做到这三点，自动化才敢真正放手。
