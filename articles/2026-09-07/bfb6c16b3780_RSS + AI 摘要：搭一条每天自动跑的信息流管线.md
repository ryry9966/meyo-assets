## 背景

信息源没变少，时间在变少。RSS 看似过时，但它是唯一不打算法推荐、完全自主可控的分发协议。过去懒得认真用 RSS，很大一个原因是"订阅了也读不完"；现在 LLM 的摘要成本已经低到可以忽略，这件事值得重做一遍。

## 问题

我的痛点很具体：订阅了四十多个技术博客和周刊，每天真正点开的不超过五个；偶尔回头清 unread，发现八成内容一句话就能带过。目标是：每天早上收到一份自动摘要，重要条目保留原文链接，点不点由我自己决定。

## 做法

整条管线拆成四个独立阶段，各自一个脚本，中间用 SQLite 存原始条目：

1. **抓取**：用 feedparser 拉全部 feed 落库，字段记 guid、标题、链接、发布时间、正文（有全文就存全文）。
2. **预筛**：关键词黑名单 + 标题相似度去重。同一事件多来源报道非常常见，这一步通常能砍掉 60% 以上的条目量，直接决定 token 账单。
3. **摘要**：把预筛后的条目分批喂给模型，prompt 约束为三段式——一句话摘要、关键要点、原文要点依据，禁止编造文本外信息，每条保留原文链接。
4. **推送与回流**：拼成 Markdown 日报，通过 OpenClaw 的消息通道推给订阅端；同时把"是否点开"记录回 SQLite，用于后续调整来源权重。

这条管线还可以包成一个 MCP tool，让 Agent 在需要回答"今天圈子里有什么新东西"时直接查询当日摘要，而不是自己重新抓一遍 feed——这是把它接进 OpenClaw 比较自然的姿势。

## 踩坑点

- **很多 feed 只有 summary 没有全文**，直接摘要会丢上下文。对这类条目按链接抓一次正文，失败就降级为"仅列标题"。
- **预筛比摘要重要**。上来就让模型读全文，一天跑下来 token 是预估的好几倍。先便宜后贵，是一切批处理管线的基本原则。
- **摘要幻觉比想象中常见**，尤其是版本号、日期这类细节。prompt 里强制"不确定就写不确定"，并对数字类字段做正则抽查。
- **cron 重叠触发会重复推送**。用 guid 做幂等键，推送前查一下当天是否已发过。
- feed 里的相对链接、编码错误、XML 转义问题比想象中多，解析层要写得宽容一些。

## 可复用建议

- 各阶段解耦、中间态落库，任何一段挂了都能从断点续跑。
- 摘要 prompt 放配置文件而不是写死在代码里，你会反复调它。
- 永远保留原文链接，AI 摘要是索引不是替代品。
- 顺手记录成本和条目量，跑一周后你会需要这些数据来砍订阅源。

## 总结

这条管线一个下午能搭完，之后每天自动产出一份可控的信息流。RSS + LLM 的组合本身没有技术难度，价值在"预筛逻辑"和"摘要质量反馈"这两个持续迭代的部分。它不负责让你读到好内容，只保证坏内容不再占用注意力——这个定位想清楚了，工具就不会越搭越复杂。
