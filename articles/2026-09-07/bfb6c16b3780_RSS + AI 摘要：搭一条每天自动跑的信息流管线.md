## 背景

信息源越订越多，真正读完的比例却越来越低。RSS 是少数格式稳定、可程序化处理的信息源——不依赖推荐算法，条目自带标题、链接、时间戳。我的目标很简单：把"读"这一步交给脚本和模型，人只看压缩后的结果。

## 问题

直接跑会遇到三个现实问题：

1. 订阅源条目量很大，逐条调模型又贵又慢，而且大部分条目本来不值得摘要；
2. 很多站的 RSS 只给摘要不给正文，模型拿不到足够上下文；
3. 管线跑久了会积累脏数据：重复转载、失效链接、模型偶尔编造的"引用"。

## 做法

整条管线分四层，每层独立可替换：

**1. 源采集。** 站点原生 RSS 优先，没有的用 RSSHub 补。全部导出成一份 OPML 作为单一事实来源，增删订阅只改这个文件。

**2. 清洗入库。** 用 feedparser 拉条目，按 GUID + URL 归一化去重（去掉 utm 参数、统一协议头）。正文缺失的条目走一遍抓取 + readability 提取，结果写入本地 SQLite，只存结构化字段。

**3. 两段式摘要。** 第一段是便宜的规则过滤：关键词打分 + 来源权重，先砍掉六成以上噪音。剩下的按主题聚类分批，每批 8–12 条塞进同一次请求，让模型输出结构化 JSON：标题、一句话摘要、值得深读的理由、置信度。温度设 0，prompt 进版本库。

**4. 汇编推送。** 定时任务（cron 或 OpenClaw 的定时 agent）每天固定时间把 JSON 汇编成一份 Markdown 日报：先放 Top 5 深读项，再按来源分组列简摘，落到笔记仓库，同时用 bot 推到群里。

## 踩坑点

- **别让模型逐条摘要。** 早期按条目调 API，一天的量要跑几百次请求，成本和延迟都不可接受。分批 + 先过滤之后，请求数降了一个数量级。
- **幻觉链接。** 模型偶尔会"补全"一个不存在的原文链接。约束它只能输出输入里已有的 URL，并在汇编层做链接比对，对不上的直接丢弃该字段。
- **重复与转载。** 不同源经常互相转载，标题去重不够，我加了 URL 归一化 + 标题相似度（编辑距离阈值）双保险。
- **状态要落盘。** 记录已处理 GUID 的集合，任务失败重跑时不会重复推送。这个文件比想象中重要。
- **时区。** 拉取窗口按 UTC 存储，展示时再转本地，否则"昨日新增"会莫名多出或缺少几条。

## 可复用建议

- 中间层用结构化 JSON，别从 RSS 直接拼 prompt，后面换模型或换输出渠道都不用动上游。
- 先规则后模型：能用启发式解决的不进 LLM，省钱且更可控。
- prompt 当代码管理，改模板记录 diff，方便回溯"那天日报风格为什么变了"。
- 把日报目录暴露成 MCP 工具/资源，agent 需要背景资料时可以直接检索这份语料，不用重复抓取。
- 输出纯 Markdown，可 grep、可 diff、可被下游流水线直接消费。

## 总结

这条管线没有用到复杂组件：feedparser、SQLite、一个模型 API、cron。核心思路是"规则做粗筛，模型做压缩，人做最终决策"。跑了一个多月，每天的阅读时间从翻几十个 tab 缩到几分钟，信噪比可接受。它最大的价值不在于省时间，而在于让信息获取变成一条可观测、可调整的流水线——哪天摘要质量下降，你能定位到是源、过滤还是 prompt 的问题。
