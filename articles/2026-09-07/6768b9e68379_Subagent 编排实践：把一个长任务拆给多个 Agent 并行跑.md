## 背景

单 agent 串行处理长任务的老问题，跑过大任务的都遇过：上下文越滚越长，前面的结论开始丢；一个 MCP 工具偶发超时，整条链路跟着阻塞；三个互不依赖的子任务排着队串行执行，纯粹浪费等待时间。

OpenClaw 的 agent 支持通过 task 工具派生 subagent（拥有独立上下文的子会话），配合 MCP 工具白名单就能做并行。最近我把一个「代码库巡检」任务（安全扫描 + 依赖分析 + 文档比对）从串行约 40 分钟压到 15 分钟左右，这篇记录具体做法和踩过的坑。

## 做法

1. **主 agent 只规划，不干活。** 先输出结构化任务清单，每个子任务包含：目标、输入范围、产出格式、验收标准。规划质量决定整个编排的上限。
2. **派发即收紧权限。** 用 task 派生 subagent，并行度上限 3。每个 subagent 只挂必需工具：扫描类任务只给 read/grep/glob，不给 write 和 shell 写操作。
3. **文件系统隔离。** 每个 subagent 使用独立工作目录（或强制文件名前缀），禁止写共享路径。
4. **强制结构化返回。** 约定产出为：几百字内的 Markdown 摘要 + 结论 JSON + 证据文件路径。主 agent 需要细节时按路径再读。
5. **失败处理收敛。** 单次重试，再失败就把错误原文交回主 agent，由主 agent 决定跳过还是降级，不在子任务里死磕。
6. **主 agent 统一收口。** 负责合并、去重、冲突仲裁，最终只写一份报告。

## 踩坑点

- **并行写同一文件互相覆盖。** 两个 subagent 都往 workspace 根写 `report.md`，后写的赢，先写的成果静默丢失。改成独立目录后才解决。
- **权限继承太宽。** subagent 默认拿到主 agent 的全部工具，有个子任务「顺手」改了配置文件。白名单必须在派发时显式声明，不要指望继承策略。
- **429 限流被当成 bug。** 三个 subagent 同时打同一个模型和工具，触发速率限制，报错信息完全不提限流。加指数退避，或把并行度降到 2。
- **汇总环节爆上下文。** 最初让 subagent 返回完整原始输出，主 agent 上下文反而先爆。改为只收摘要 + 路径，是最关键的一次修正。
- **隐式依赖导致读到旧数据。** B 任务默认 A 已产出文件，并行后 B 读到的是旧版本。结论很明确：有数据依赖就串行，只有真正无依赖的分支才值得并行。

## 可复用建议

- 把任务清单格式固化成 skill 或提示词模板，每次编排复用，别每次现场发挥。
- 并行度从 2 起步，观察限流情况和汇总质量，再逐步上调。
- 每个子任务写清「完成定义」。验收标准模糊的子任务，宁可拆细，或者留人工兜底。
- 全程 trace 落盘：派发参数、返回摘要、耗时、失败原因。复盘和回放全靠它，出了问题不用靠猜。

## 总结

subagent 编排的核心不是「开得越多越快」，而是两件事：**隔离**（上下文、权限、文件系统各自独立）和**收口**（结构化返回、统一仲裁）。并行解决的是时间问题，隔离和结构化解决的是正确性问题——后者更容易被忽略，出的事故也更隐蔽。建议先拿一个无状态、可重跑的任务（代码扫描、资料汇总这类）练手，把模板和失败路径跑顺，再逐步上到有副作用的流程。
