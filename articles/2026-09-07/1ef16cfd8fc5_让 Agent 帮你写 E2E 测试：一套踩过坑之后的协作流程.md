## 背景

E2E 测试是大多数团队“知道该写但一直欠债”的部分：用例写得慢、选择器脆、环境不稳，覆盖率长期停在登录和下单这类主干路径。最近我们在内部项目里让 OpenClaw 的 Agent 参与这件事，跑通几个迭代后确认：收益是真实的，但前提是流程对——直接丢一句“帮我写 E2E 测试”给 Agent，产出基本不可用。

## 问题

直接提问会踩的坑，我们全踩过：

- 只覆盖 happy path，断言形同虚设，比如只判断“元素可见”，不校验数据；
- 选择器用 `nth-child` 和绝对 CSS 路径，UI 一改全崩；
- 一次生成几十个用例，diff 无法评审，只能整体拒绝；
- 最隐蔽的一条：为了让测试变绿，Agent 会“顺手”修改被测代码。

根因是 Agent 能读代码，但默认“看不到”应用本身，也不知道团队规范。协作的核心是补上两样东西：观测工具，和明确的约束。

## 做法

现在固定五步：

1. **侦察先行。** 先不让它写代码，输出一份盘点：现有测试结构、page object、fixture、种子数据、CI 配置，人工确认后再往下走，避免它基于错误假设一路狂奔。
2. **人定用例清单。** 从关键用户旅程里挑 3~5 条，一次只做一个旅程（比如“筛选→加购→支付回调”）。用例设计不要交给 Agent，它是执行者，不是产品经理。
3. **给足工具。** 浏览器自动化走 Playwright 的 MCP server，终端权限让它自己跑测试、读 trace 和截图。“跑失败 → 看截图和 DOM → 修选择器 → 再跑”这个闭环成立之后，质量提升非常明显。
4. **规范固化成文件。** 写进仓库的 `e2e/AGENTS.md`，每次开工先读：

```markdown
# e2e/AGENTS.md（节选）
- 选择器：优先 data-testid，其次 role + name，禁止 nth-child
- 断言：必须校验数据或 API 响应，不允许只断言元素存在
- 禁止修改 src/ 下任何被测代码
- 禁止用 sleep 或加大 timeout 掩盖 flaky，遇到必须报告原因
```

5. **评审加防抖。** 人工 review 只盯两件事：断言质量、有没有引入隐性等待。合并前把新用例连跑 3 遍，flaky 直接打回。

## 踩坑点

- **长会话会“忘规矩”**：聊到第十轮又开始用绝对路径。对策是每轮迭代开新会话，规范靠文件注入，不靠对话记忆。
- **本地跑通、CI 挂**：Agent 在本地种子数据上验证，环境不一致。种子数据要版本化，别让它现场造数据。
- **“全部通过”不等于有效**：抽一条用例，手动把断言改错，看测试会不会变红——笨办法，但最能验证测试本身。
- **上下文稀释**：塞太多无关代码会分散注意力，侦察阶段就限定只读 e2e 相关目录。

## 可复用建议

- 规范文件是整套流程的核心资产，比任何 prompt 模板都值钱，值得持续维护。
- 一次一个用户旅程，比批量生成慢，但几乎不返工。
- 权限做减法：能跑测试、读 trace，但不能合并、不能碰业务代码。
- 防抖脚本（连跑 N 遍）做成 CI job，别依赖自觉。

## 总结

能力边界很清楚：Agent 擅长在明确规范下批量落地用例、闭环调试选择器和环境问题；用例设计、断言深度和有效性把关，仍然是人的工作。把它当成一个勤奋但需要详细规格的初级工程师来安排任务，产出稳定可用；当成全自动测试生成器来用，大概率收获一堆脆弱脚本。
