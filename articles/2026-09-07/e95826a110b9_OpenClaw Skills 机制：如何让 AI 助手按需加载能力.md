# OpenClaw Skills 机制：如何让 AI 助手按需加载能力

## 背景

很多人的 Agent 是这么长起来的：系统提示词里堆了几十条流程说明，MCP server 挂了十几个，工具列表先吃掉几千 token。单看每条都有用，合在一起模型反而变笨——指令互相干扰、工具选错、窗口被静态说明占满。OpenClaw 的 Skills 机制就是冲着这个问题来的：把能力拆成独立技能包，平时只暴露一行描述，命中时才加载正文。

## 问题本质

按需加载的核心是渐进式披露，分三层：

- **L0 元数据**：`name` + `description`，常驻上下文，每个技能几十 token；
- **L1 正文**：`SKILL.md` 的 markdown 主体，触发后才读入；
- **L2 资源**：`references/` 文档、`scripts/` 脚本，正文里引用、执行时才碰。

## 做法

**1. 一个技能一个目录：**

```
skills/
└── log-analysis/
    ├── SKILL.md
    ├── scripts/parse.py
    └── references/log-format.md
```

**2. frontmatter 只写两个字段：**

```yaml
---
name: log-analysis
description: 当用户要求排查服务报错、分析日志文件或提取错误模式时使用。
---
```

正文写操作步骤，控制在 200 行以内；固定流程写成脚本，别用自然语言让模型即兴发挥。

**3. description 就是触发开关。** 模型启动时只看到这一行，靠它决定是否读正文。所以描述要写成触发条件（“当…时使用”），而不是功能清单（“本技能支持…”）。

**4. 验证：** 准备两类 prompt，一类应触发、一类不该触发，各跑一遍看命中率，再决定拆分或合并。

## 踩坑点

- **description 写成功能介绍** → 永远不触发；写成万能描述 → 乱触发。固定用“当用户做 X / 任务涉及 Y”句式。
- **把所有细节塞进正文**，等于换个地方堆上下文。长资料拆到 `references/`，正文只留流程骨架。
- **两个技能抢同一个触发场景**。一个技能只覆盖一类工作流，重叠就合并。
- **脚本写死绝对路径、依赖特定环境**，换台机器就挂。用相对路径，假设最小运行环境。
- **skills 目录不进版本库**，改坏了说不清。把它当代码管理，提交信息写清动了哪个技能。

## 可复用建议

- description 模板：当【具体任务/关键词】出现时使用；输入是【X】，产出是【Y】。
- 按工作流拆，不按工具拆。“发周报”是一个技能，“调用某个 API”不是。
- 技能保持无状态，不依赖“上轮对话记住了什么”。
- 加一条日志，记录每次实际加载了哪些技能。上线一周后，你会想砍掉一半。

另外说清它和 MCP 的关系：MCP 负责把工具接到外部系统，Skills 负责组织“怎么用这些工具”的流程知识。互补，不是替代。

## 总结

Skills 的价值不在“多了一种插件”，而在于把提示词工程从“一个越来越大的 prompt”变成“一组有触发边界的模块”：启动上下文恒定，能力随任务加载。最快的迁移路径，就是把你现有系统提示词里的流程段落逐段拆出来，变成一个个技能。
