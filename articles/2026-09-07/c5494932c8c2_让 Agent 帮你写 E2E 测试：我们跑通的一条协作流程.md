## 背景

E2E 测试一直是最费人力的那一层：用例逻辑不难，但写起来琐碎、维护成本高、稍有波动就 flaky。最近我们把 OpenClaw 接到测试仓库上，用 Agent + Playwright MCP 的方式让 AI 参与 E2E 用例编写，跑了几个迭代之后，整理出一条比较稳的协作流程，供大家参考。

## 问题

先说直接让 Agent"帮写测试"会发生什么。最早的做法是把页面 URL 和需求描述丢给模型，让它直接输出测试代码，结果三类问题反复出现：

1. **选择器靠猜**：模型看不到真实 DOM，会编出 `button.submit` 这类看似合理、实际不存在的定位器；
2. **断言空转**：用例看起来很完整，但只断言了"页面不报错"，没有验证任何业务结果；
3. **等待乱写**：大量 `waitForTimeout(3000)`，本地能过，CI 必 flaky。

结论很直接：Agent 没有对页面的真实感知时，产出只是"看起来像测试的代码"。

## 做法

核心思路是把 Agent 从"猜"改成"看"，分四步。

**第一步：给 Agent 一双眼睛。** 通过 MCP 把 Playwright 挂到 OpenClaw 上，让 Agent 能打开页面、截图、读取可达性快照。这一步之后选择器不再靠猜，Agent 能拿到 `data-testid` 的真实值。

**第二步：定契约再生成。** 先让 Agent 扫一遍目标页面，输出它计划使用的定位器清单，人工确认哪些符合约定（我们要求所有交互元素必须有 `data-testid`），然后才开始生成用例。生成时明确两条硬约束：禁止 `waitForTimeout`；断言必须落在业务结果上（订单状态、接口返回、落库数据），而不是 UI 细节。

**第三步：跑失败循环。** 生成的用例直接进 CI，失败后把报错信息和 trace 截图喂回给 Agent 让它修。这个循环里 Agent 表现很好——trace 里的信息足够它判断是选择器漂了还是时序问题。

**第四步：人工只审一件事——断言。** 我们约定：选择器和操作步骤 Agent 可以自主调整，但断言的增删必须人工过目。断言决定测试的价值，这一层不能放权。

## 踩坑点

- **不要给全量页面快照。** 上下文很快爆炸。正确做法是让它按流程逐页打开、逐页提取，只保留定位器和关键文本。
- **trace 截图比报错文本有用。** 只贴报错，Agent 经常瞎猜；配上失败时刻的截图，一次修复率明显提高。
- **警惕"全绿幻觉"。** Agent 修 flaky 用例时倾向加 retry。我们限定 retry 上限 1 次，且必须在改动说明里写原因。
- **权限收窄。** Playwright MCP 只指向测试环境地址，生产配置不进上下文。

## 可复用建议

- 把定位器约定和禁止模式（`waitForTimeout`、深层 CSS 层级选择器）写进一份稳定的系统提示或项目说明，Agent 每次生成前先读；
- Agent 产出的用例统一放 `e2e/agent-draft/` 目录，一律视为草稿，人工审查转正后才合并进主干；
- 用例文件头部保留一段"用例意图"注释（该用例验证什么业务），生成时让 Agent 必填，审查时先看意图再看代码。

## 总结

这轮实践下来，E2E 用例的编写效率大约是纯人工的两到三倍，但更重要的变化是心态：以前没人想碰测试，现在补一条用例的成本低到可以被随手做掉。Agent 在这件事里的合理定位是"有眼睛的初级工程师"——让它看真实页面、跑真实用例，而断言背后的价值判断，留在人手里。
