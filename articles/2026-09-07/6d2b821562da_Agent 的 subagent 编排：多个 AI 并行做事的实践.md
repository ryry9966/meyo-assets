## 背景

单 agent 串行干活有个天花板：一个长任务跑下来，上下文越堆越脏，后半程质量明显下滑。而任务里往往混着一批彼此独立的子活——比如"重构五个模块""给二十个接口补单测""调研三个候选方案"，串行做纯粹浪费时钟。OpenClaw 提供 session spawn / subagent 能力之后，把这些子活拆出去并行跑，是我们最近落地最多的一类改造。

## 问题

直接上手会撞到三个典型障碍：

1. **上下文隔离的代价**。subagent 看不到父 agent 的对话历史。你以为是"派活"，实际是"交接给一个失忆的新员工"。
2. **写冲突**。多个 subagent 同时改同一批文件，轻则互相覆盖，重则工作区直接报废。
3. **结果回流污染**。subagent 返回大段原文，父 agent 上下文迅速膨胀，编排本身反而成了新瓶颈。

## 做法

我们跑通的稳定套路是"任务合同 + 隔离写域 + 结构化回流"：

**第一步：拆任务，判独立性。** 只有满足"输入明确、产出有界、写路径互不依赖"的子任务才值得派发。拆不动就别硬拆，串行不一定慢。

**第二步：写任务合同。** 每个 subagent 的 prompt 显式带上四件事：目标、允许触碰的文件范围、禁止事项、输出格式。我们固定要求 JSON：`status / files_changed / summary / blockers` 四个字段。派发前由父 agent 把 subagent 需要的最小上下文直接注入 prompt，绝不指望它"自己去仓库里找"。

**第三步：并行派发 + 分域写入。** subagent 各写各的文件，有交叉的部分留给父 agent 统一处理。并行度控制在 2–4 个——再多就撞 API 限流，token 账单也不好看。

**第四步：父 agent 汇总与验收。** 收齐结构化结果后，由父 agent 做交叉检查（例如让 A 的产出作为 B 的输入做一致性校验），最后统一提交。subagent 永远不做最终集成——这是父 agent 的职责，也是它的上下文不能随便砍的原因。

## 踩坑点

- **subagent 拿不到该有的信息**：九成失败源于派发 prompt 写得太省。宁可多贴一段代码，也别让它自己猜。
- **结构化输出没校验**：模型偶尔不按格式回。parse 失败重试一次，再失败降级为串行，别硬吞脏数据。
- **单个失败阻塞全局**：用 `Promise.allSettled` 这类语义收集结果，失败的子任务打标后交给父 agent 决定重试还是放弃。
- **summary 太长**：把 summary 字段限在两百字内，细节让它落盘到指定文件，父 agent 需要时按路径再读。

## 可复用建议

- 把"任务合同"做成模板存进团队知识库，新任务只填变量；
- 写一个通用的 `dispatch_subagents` 插件，封装派发、收集、校验三件事，不要在每个 skill 里重复造；
- 所有 subagent 的中间产物统一落盘到固定目录，编排失败后可从断点恢复，而不是全量重跑。

## 总结

subagent 编排的本质不是"更多 AI"，而是更严格的工程约束：任务可拆、写域隔离、结果有契约。三点都做到，并行才是加速；做不到，并行只是把混乱平方。建议从一个三个子任务的批处理场景开始试，跑通合同和回收流程后再扩规模。
