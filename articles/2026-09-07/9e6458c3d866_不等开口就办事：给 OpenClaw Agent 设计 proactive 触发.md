## 背景

大多数 AI 助手的默认形态是被动的：你发消息，它回应。但真正省时间的能力恰恰藏在"没有对话"的间隙里——CI 挂了主动提醒、每天早上把昨天的 issue 汇总好、发现日历冲突提前打招呼。OpenClaw 这类常驻型 agent 框架，加上 MCP 的工具生态，已经具备让 agent"自己醒来干活"的条件，缺的是一套克制的触发设计。

## 问题

第一版 proactive 通常很糟：agent 每隔几分钟报一次"一切正常"；或者一次心跳里连跑五个工具把 token 烧掉；更糟的是自己触发自己形成回环。主动性不是"多说话"，而是"在对的条件下说一次有用的话"。核心矛盾在于：**触发要敏感，输出要克制**。

## 做法：三层触发 + 一层闸门

**1. 定时触发（heartbeat / cron）**
心跳机制按周期唤醒 agent，任务清单写在 `HEARTBEAT.md`；需要精确时刻的用 cron 任务投递一条 prompt。心跳间隔建议 15–30 分钟起步，别一上来就 1 分钟。

**2. 事件触发（webhook）**
外部系统（监控、CI、邮件）POST 到网关，agent 收到后自行决定处理方式。事件型触发最省成本，因为只在有事时才唤醒。

**3. 状态触发（条件判断）**
agent 醒来后先用 MCP 工具查状态，满足条件才动手，不满足直接静默结束。`HEARTBEAT.md` 里写的应该是"条件 + 动作 + 阈值"，而不是"每次醒来做 A/B/C"。

**4. 输出闸门**
给主动消息加三类规则：
- 去重：同一问题 N 小时内不重复报
- 静默时段：夜间只记录不推送
- 分级：花钱、对外发消息的动作必须等确认

## 踩坑点

- **心跳里跑重工具**：每次心跳都全量拉数据，token 成本线性上涨。改成先查轻量状态接口，有变化再拉详情。
- **自触发回环**：agent 处理 webhook 后又发消息，触发自己的 hook，会话雪崩。给事件加来源标记，同一来源不二次触发。
- **记忆污染**：主动任务的结果全塞进记忆文件，几天后上下文全是噪音。中间结果只写日志，只有"值得记住的结论"才进记忆。
- **时区没对齐**：cron 用 UTC、你用本地时间，早上八点的"每日汇总"变成晚上八点。

## 可复用建议

- 把每条主动行为定义成"条件 → 动作 → 抑制规则"三元组，集中在一个文件里管理，别散落在 prompt 里。
- 每条主动消息附带"为什么现在告诉你"，方便事后审计触发逻辑。
- 新任务先跑 dry-run：只记录会做什么、不真执行，观察几天再放开。
- 设单日主动消息配额，超了就静默。宁可漏报，不要轰炸。

## 总结

Proactive 的本质，是把"人记住去找 agent"变成"agent 在条件成立时找到人"。工程难点不在触发器，而在抑制——去重、静默、确认、成本上限。先用最小的定时任务跑通闭环，再逐步叠加事件和状态触发，每一层都配上闸门，agent 才会从聊天工具变成真正省心的助理。
