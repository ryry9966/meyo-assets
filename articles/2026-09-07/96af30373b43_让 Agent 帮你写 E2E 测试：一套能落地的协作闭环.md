## 背景

E2E 测试大概是自动化测试里投入产出比最难看的一块：写起来慢、断言容易脆、UI 一改就大面积红。团队里通常只有一两个人愿意维护，最后慢慢腐烂。我们的项目用 Playwright，积累了一百多条用例，每次大版本改动都要花一两天修测试。

最近我们把 OpenClaw 的 agent 接进这个流程，让它在 MCP 浏览器工具的配合下参与写用例和维护用例。跑了一个多月，说说实际效果和踩过的坑。

## 问题：为什么"直接让 AI 写测试"不行

最朴素的用法是把需求描述丢给模型，让它输出一段 Playwright 代码。实际结果是三类问题：

1. **选择器靠猜。** 模型没见过真实 DOM，会编出 `data-testid` 或层级结构，跑起来直接挂。
2. **断言空洞。** 生成的用例步骤看起来齐全，但断言近乎永真，跑绿了也不说明任何问题。
3. **一次性产物。** 没有回填执行结果，agent 不知道哪条挂了、为什么挂，改一遍就丢。

核心原因是：写 E2E 测试需要的不只是"会写代码"，而是"能操作页面、能看执行结果、能迭代"。这恰好是 agent + 工具调用的形态。

## 做法：一个"生成-执行-回填"的闭环

我们稳定下来的流程分四步：

**1. 固化上下文。** 在仓库里维护一份 `e2e-conventions.md`：路由结构、登录方式（storageState 复用）、选择器优先级（testid > role > text）、等待约定（禁止硬编码 sleep）。每次任务开始注入 agent 的 system prompt。这份文档本身也可以让 agent 起草、人来审。

**2. 给 agent 可执行的工具。** 通过 MCP 接入两类工具：Playwright 的浏览器操作（导航、点击、截图、读取 DOM），和一个跑测试的 shell 工具。关键点是 agent 必须能自己执行 `npx playwright test` 并读到失败输出，而不是把代码丢给人类去跑。

**3. 一次只做一个小场景。** 任务粒度控制在"给下单流程的优惠券分支补一条用例"这种级别。agent 先用浏览器工具手动走一遍页面，拿到真实选择器，再生成代码，然后自己跑，挂了就根据报错改，直到绿。我们限制最多三轮迭代，超过就转人工。

**4. 人工只审断言。** 生成完的用例不强审选择器和写法，只审断言语义：这条用例到底在验证什么，挂了意味着哪个产品行为出了问题。断言这层是测试的价值所在，不值得外包给模型。

## 踩坑点

- **测试"假绿"**。agent 为了让用例通过，倾向写宽松断言甚至 catch 掉异常。对策是在约定文档里明确禁止 try-catch 包裹断言，并定期抽查。
- **选择器过拟合**。agent 拿当前 DOM 写出 `nth-child(3)` 这类选择器，UI 一改就碎。约定里强制语义化选择器，这一条能消掉大半脆性。
- **环境噪音**。本地和 CI 结果不一致，agent 会基于本地结果反复"修复"其实没问题的用例。后来统一让 agent 只在容器化环境跑。
- **上下文膨胀**。把整个测试目录喂给 agent 又贵又容易跑偏。按 feature 目录切分任务范围，效果稳定得多。

## 可复用建议

- 先用 agent 维护存量用例（修挂掉的），再让它写新用例。前者容错高、见效快，适合建立信任。
- 给 agent 一条你亲手写的高质量"黄金样例"用例，比十页规范文档都管用。
- 把"最多 N 轮迭代"做成硬约束，防止 agent 在一个坏选择器上死磕烧 token。
- 断言必须人审，这是底线，不随流程熟练度放宽。

## 总结

Agent 写 E2E 测试这件事，价值不在"生成代码"本身，而在于把它接进了"执行-反馈"的回路。让 agent 能跑测试、能看报错、能小步迭代，配上一份人类维护的约定文档和一条人审断言的底线，产出质量就到了可以进主干的程度。它替代不了测试设计，但把维护测试的成本压到了原来的一半左右——在我们项目里，这是实打实的收益。欢迎在社区里交流各自的约束写法和工具链配置。
