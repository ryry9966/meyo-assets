## 背景

Agent 接上工具之后，核心问题就从"它能不能做"变成了"它该不该先问我"。一个典型的 OpenClaw 会话里，agent 手里同时握着 shell、文件读写、HTTP 请求和一排 MCP 插件。每一步都弹确认，人很快会退化成自动点"允许"的机器；每一步都放行，一次事故就够喝一壶。后来我把权限边界当成一个显式策略来维护，才算稳定下来。

## 问题在哪

常见误区不是"太松"或"太紧"，而是分类维度错了。多数人按工具划线：这个插件危险、那个安全。但风险取决于动作本身——同一个文件删除工具，清临时目录和删项目根目录是两码事。按工具分类，边界要么粗到没用，要么细到没法维护。

## 一个可用的分档标准

判断一个动作前，先问三个问题：

1. **可逆吗？** 一条命令能不能回滚？
2. **波及面多大？** 只在工作区内，还是会出目录、出机器、出钱包？
3. **agent 自己含糊吗？** 参数是明确的，还是它在猜？

据此把动作分四档：

| 档位 | 判定 | 处理方式 |
|---|---|---|
| L0 | 只读，无副作用 | 自动执行 |
| L1 | 可逆，且限工作区内 | 自动执行 + 留痕 |
| L2 | 不可逆 / 出工作区 / 动数据 | 先出方案，确认后执行 |
| L3 | 高危（生产删除、支付、外发、密钥） | 不给工具，而不是每次问 |

L3 那行是重点：真正危险的事，不该靠"每次确认"兜底，而是干脆不出现在工具箱里。确认机制防失误，不防滥用。

## 在 OpenClaw 里怎么落地

1. 盘点当前 agent 能触达的全部工具，按三问逐个打标。
2. 网关配置里给工具分档：L0/L1 进白名单，L2 挂确认门（approval）。
3. 确认时强制展示"计划"而不是问"是否继续"：要执行的命令、目标路径、影响范围，一次贴全。
4. 给 L2 准备独立的低权限凭证；dry-run 和真实执行用不同身份。
5. 每周翻一次自动放行的日志：如果某类写操作一直安全，就考虑升到 L1；反之降档加确认。

## 踩坑记录

- **审批疲劳**：问得太频繁，人就开始无脑放行，比不问更糟。宁可收紧 L1 的定义，也别稀释 L2 的严肃性。
- **模糊提问**："我可以继续吗？"是坏问题。不带上下文的确认等于没确认。
- **事后确认**：请求已经发出去了才来问，顺序错了。确认必须挡在副作用发生之前。
- **"记住我的选择"用在删除上**：批量放行省几秒，赌的是整个工作区。
- **凭证权限大于确认级别**：工具本身拿着 admin key，确认门就形同虚设。先收凭证，再谈门禁。

## 可复用的建议

- 把"问人"设计成展示 diff，不是 yes/no。
- 不可逆动作永远要新鲜确认，不缓存、不批量。
- 降低确认成本：上下文一次给全，别让人反问三轮才看懂要发生什么。
- 边界是调出来的，不是一次设计出来的——用日志反推分档。

## 总结

权限边界不是静态清单，而是随使用持续校准的策略。压缩成一句话：**可逆且局部的事自己干；不可逆、出圈或含糊的事，先出方案再问人；真正危险的事，别让它进工具箱。**
