## 背景

Agent 接上 MCP 和插件之后，能力上限变了：能读文件、跑 shell、调外部 API、发消息、花钱。以前“模型只出建议，人来执行”，现在执行环节往往就是模型自己。于是每个接了工具的 agent 都绕不开同一个问题：哪些动作可以直接干，哪些必须先问人。

## 问题

实际项目里通常走向两个极端：

- **什么都不问**：效率很高，直到某天它清理“临时文件”删掉了配置目录，或者把测试消息发给了真实用户。
- **什么都问**：每个动作都弹确认，人很快进入无脑点确认模式，审批形同虚设，agent 退化成一个很贵的对话框。

两个极端本质是同一件事：**“问人”没有被工程化，全靠开发者临场的感觉。**

## 做法：把判定线写成规则

我把每个工具动作按四个维度评估，再映射到处置级别。

**四个维度：**

1. **可逆性**：改了能不能一键回滚？git 提交可逆，删库、发出去的消息不可逆。
2. **影响半径**：只碰自己的工作区，还是波及他人数据或外部系统？
3. **成本**：单次调用多少钱，一天上限多少？
4. **可见性**：结果对外可不可见？写草稿和对外发言是两码事。

**映射到四级处置：**

- **直接执行**：只读、可逆、半径在自己沙箱内。读文件、跑测试、查文档。
- **执行后汇报**：可逆但留痕。写代码、提交到自己的分支——先干，日志可查。
- **先问再干**：不可逆、影响他人、或成本超阈值。删数据、对外发消息、部署生产、付费 API 超额度。
- **禁止**：工具层面直接不授权，比在提示词里写“不要做”可靠得多。

在 OpenClaw 里落地时，前三档分别对应：工具白名单直接放行、带确认门的调用、不挂载的工具。判定逻辑放在网关/包装层做，别指望模型自己判断——它对“这条 rm 危不危险”的评估不稳定，规则必须是确定性的。

默认从紧，观察后放宽：新工具先按“先问再干”跑一两周，日志确认调用时机稳定后再降级。放宽永远比收紧容易。

## 踩坑点

1. **问得太碎等于没问**。一次任务弹十次确认，人会麻木。低风险动作合并为“执行后汇报”，把分量留给少数高危动作。
2. **批量打包审批**。模型把五个动作塞进一句“我要做这五件事，可以吗”，人扫一眼就批了。要求每个不可逆动作单独确认，且先展示预览。
3. **事后问而非事前问**。“我已经发出去了，这样 OK 吗”是通知不是审批。确认门必须卡在执行之前。
4. **工具描述含糊**。模型靠 description 评估风险，`send_msg` 和 `send_msg_to_all_users` 在它眼里风险完全不同。把作用域和副作用写清楚，比在系统提示里喊话有效。
5. **“临时”提权忘回收**。调试时给过 admin token，两周后还在。给 agent 的凭证要单独建、最小权限、带过期时间。

## 可复用建议

- 接新工具先回答四个问题：可逆吗、影响谁、花多少、别人看得到吗。
- 判定规则写在代码或配置里，不写进提示词。
- 自动执行的动作全部落审计日志，事后能还原“它为什么这么做”。
- 高危动作先展示 diff、收件人、金额，再确认。
- 确认通道设超时：超时默认拒绝并挂起，而不是默认执行。

## 总结

权限边界不是“信不信任 agent”的态度问题，而是一张明确的分级表：只读放行，可逆的放行加审计，不可逆和影响别人的必须事前确认，不该碰的干脆不给。把“问人”从一种感觉变成一条规则，agent 才能真正放开手，去做那些值得自动化的事。
