## 背景：上下文才是真正的稀缺资源

和 Agent 协作时间长了会发现，瓶颈往往不是模型能力，而是上下文预算。早期我把部署流程、日志排查、周报模板全塞进系统提示词，结果技能越多，指令互相干扰越严重，命中率反而下降。OpenClaw 的 Skills 机制用**渐进式披露**解决这个问题：常驻上下文里只有每个技能的名称和一行描述，正文（SKILL.md 的 body）只在任务匹配时才被 agent 主动读取。

## 问题：全量注入的三宗罪

1. **注意力稀释**：无关指令占据上下文，模型容易选错工具；
2. **成本线性上涨**：每多一个技能，每轮对话都在付 token 税；
3. **缓存失效**：改一处提示词，整个 prompt cache 作废。

## 做法：五步落地一个 Skill

**1. 建目录。** 技能放在 `~/.openclaw/workspace/skills/<name>/` 下，核心是一个 `SKILL.md`：

```markdown
---
name: deploy-check
description: 用户要求部署、发布或检查线上服务健康状态时使用。
---
构建 → 推送镜像 → 滚动更新 → curl 健康检查，失败时回滚。
详细 runbook 见本目录下 runbook.md。
```

**2. description 写触发条件，不是功能清单。** 这是整个机制成败的关键。写"什么时候用"，不要写"能做什么"。

**3. 正文保持精悍。** 步骤、坑、判断分支写清楚，长文档拆到附属文件里，正文里只留一句"见 xxx.md"。OpenClaw 会注入技能根路径，脚本用相对路径引用即可。

**4. 生效验证。** 新开会话后用 `/skills` 查看列表；想强制常驻可加 `always: true`（慎用）。

**5. 测试触发。** 抛一个匹配任务，观察 agent 是否去读 SKILL.md 而不是瞎猜。不命中就回头改 description。

## 踩坑记录

- **description 太泛**：写"辅助开发"这种描述，几乎永远不会被触发；
- **正文贪长**：300 行的 SKILL.md 一旦加载，等于换了个地方全量注入；
- **依赖门控静默失败**：frontmatter 里声明了 `env` 或 `binaries`，环境不满足时技能直接不加载，且没有醒目报错，建议先手动验证依赖存在；
- **旧会话不生效**：SKILL.md 改完后，已开的会话里内容已被缓存，必须新开会话；
- **同名覆盖**：workspace 技能会覆盖内置同名技能，排查"行为变了"时先查这个。

## 可复用建议

- 优先沉淀**高频 SOP**：部署检查、告警初筛、固定格式的日报，这类流程化内容收益最大；
- **一个技能一个职责**，别做"大而全"的万能技能；
- description 用统一句式（"在……时使用"），团队审阅时一眼能扫完；
- 每月清一次低频技能，技能列表本身也是需要维护的资产。

## 总结

Skills 的价值不在于"给助手加了很多功能"，而在于把上下文当作预算来管理：**描述写准、正文写短、细节外置、脚本落地**。做到这四点，技能数量涨到几十个，日常对话的上下文开销也几乎不变——这才是这套机制真正的杠杆。
