## 背景

Agent 的价值不在于会说话，而在于把话说完之后真的能动手。一个只会调用内置工具的 OpenClaw Agent，天花板很低。真正让它能在生产里站住脚的，是对外部服务的对接能力：查工单系统、写数据库、触发 CI、调内部网关。这一步做扎实了，Agent 才从"演示品"变成"工具"。

## 问题

对接外部 API，团队通常卡在三件事上：

1. **鉴权与密钥管理**：API key 放进系统提示词等于裸奔，进了上下文还会随对话被日志记录。
2. **接口契约不清**：模型靠猜构造参数，字段名差一个下划线就是一次静默失败。
3. **失败不可观测**：超时、限流、4xx/5xx 混在一起，模型只收到一句模糊报错，既不能重试也不能自愈。

## 做法

OpenClaw 生态里主流路径有两条：MCP Server 和插件。建议按以下顺序落地：

**第一步：把服务包成 MCP 工具。** 每个工具只做一件事，输入输出用 JSON Schema 显式声明。描述要写得像给新同事的交接文档：参数含义、单位、必填项、典型错误码。模型读的就是这些描述。

**第二步：鉴权收敛到配置层。** 凭证放环境变量或密钥管理服务，工具运行时注入，绝不出现在对话上下文。配置文件里只留引用名，不留明文。

**第三步：给工具加护栏。** 超时设短（5–10 秒起步），重试带指数退避，写操作要求幂等键，错误返回附结构化的 reason 和 hint——模型拿到 hint 才能修正参数再试。

**第四步：灰度与审计。** 先在只读接口上验证，工具调用全量落日志（入参、出参、耗时、错误码），稳定跑一周再放开写权限。

## 踩坑点

- **描述偷懒，模型买单。**"查询订单"这种描述，模型分不清是查 ID 还是查手机号。描述多写三行，故障少一半。
- **让模型自由拼接 URL。** path 和 query 必须全部参数化，模型只填空、不拼字符串，否则注入风险真实存在。
- **大响应直接塞上下文。** 一次拉回 500 条记录，token 瞬间爆炸还稀释注意力。工具层做分页或摘要，只返回必要字段。
- **忽略幂等性。** 网络抖动触发重试，同一条工单建了三次。写操作先想清楚重试语义再上线。
- **错误信息只有"请求失败"。** 模型只会原样重试。错误要区分"可重试"（429、超时）和"应终止"（401、参数错），并给人类可读的提示。

## 可复用建议

- 建一个内部工具模板仓库：schema、超时、重试、日志、鉴权注入全部预制，新接一个服务只填业务逻辑。
- 工具数量克制：超过十几个，模型选错工具的概率明显上升，同类工具合并或分组。
- 每个工具配一条最小冒烟用例进 CI，防止上游 API 改版后悄悄坏掉。
- 定期翻日志里"调错工具"的样本，这些通常是描述写得不够好的信号。

## 总结

对接外部服务不是"能调通"就算完成，而是一套契约工程：清晰的 schema、收敛的鉴权、带语义的错误、可审计的调用链。OpenClaw Agent 的能力上限，往往就取决于这套握手协议做得有多扎实。把工具当产品做，而不是当胶水代码做，Agent 才值得被托付真实任务。
