## 背景

Agent 的价值在于"能动手"，而动手的本质是调用外部 API。在 OpenClaw 生态里主要有两条路径：一是通过 MCP（Model Context Protocol）接入现成的工具服务，二是自己写一层薄封装注册为插件工具。无论哪条路，核心问题都一样：让模型"看懂"接口，让接口"信任"调用。

## 问题

实际对接时最常见的三类故障：

1. **模型误用工具**，schema 描述模糊，参数填错或漏填；
2. **调用链路不稳**——超时、限流、重试风暴，一次故障拖垮整个任务；
3. **故障不可诊断**，错误返回是一坨原始堆栈，模型不知道该重试、换参数还是放弃。

这些问题多数不是 API 本身的锅，而是"握手协议"没设计好。

## 做法

我的经验是按五步走：

**第一步：选接入形态。** 只读、低频的查询类服务，优先用现成的 MCP server；有私有鉴权或业务逻辑的，自己写适配层。不要一开始就造轮子，也不要把复杂业务硬塞进通用工具。

**第二步：把 API 翻译成模型语言。** 每个工具写清楚：做什么、参数含义、单位、边界条件、返回结构。描述是写给模型看的 prompt，不是写给程序员的注释。"page: 第几页"不如"page: 从 1 开始的整数，默认 1，最大 100"。

**第三步：鉴权与配置外置。** API key 走环境变量或 secret 管理，绝不写进工具描述和日志。启动时校验配置，缺 key 就 fail fast。

**第四步：加工程护栏。** 显式超时（建议 10–30s）、有限次指数退避重试（只重试幂等请求）、限流时尊重 Retry-After。长任务用异步模式：先返回任务 ID，再由轮询工具查状态。

**第五步：设计"给模型看的错误"。** 错误要结构化且可决策：`{"error": "rate_limited", "retry_after": 30}` 远好于一段 404 HTML。让模型一眼判断下一步。

## 踩坑点

- **工具太多反而变笨。** 单个 agent 挂 20+ 个相似工具，选择准确率明显下降，按场景拆分或做工具分组。
- **非幂等操作裸奔。** 发消息、下订单类接口不加幂等键，超时重试就会重复执行。
- **secret 进了日志。** 调试日志把 header 全打出来，key 落盘，日志务必脱敏。
- **返回体过大。** 一个接口返回几千条 JSON 直接撑爆上下文，适配层要做分页和字段裁剪。
- **类型不宽容。** 模型传 `"2024-01-01"` 给要求时间戳的参数，适配层应做转换而不是直接报错。

## 可复用建议

1. 建一层薄 adapter，统一骨架：入参校验 → 调 API → 裁剪响应 → 结构化错误；
2. 提供 dry-run 参数，让 agent 能"试调"而不落库；
3. 把高频接口的调用示例写进工具描述，实测能显著降低参数错误率；
4. 用固定脚本做冒烟测试，schema 改动后先跑一遍再上线。

## 总结

对接外部服务不是"接上就完"，而是一次协议设计：模型是调用方，API 是被调用方，适配层是翻译官兼保安。描述写得清楚、错误给得明确、护栏立得住，握手才算稳。把这套骨架沉淀下来，下一个服务接入就只是填空题。
