## 背景

Agent 框架本身解决的是“推理和调度”，但一个 agent 真正能干活的边界，取决于它能摸到哪些外部服务。OpenClaw 的思路是把外部能力统一抽象成工具：无论背后是一个 REST API、一个数据库还是一条消息队列，对模型来说都只是“可调用的工具”。这个抽象很干净，但干净的抽象意味着对接时的脏活——认证、裁剪、超时、错误翻译——全都压在了写 MCP server / 插件的人身上。

## 问题

最近把内部工单系统和告警平台接进 OpenClaw，过程中反复出现三类问题：

1. **模型传参自由发挥**：工具描述写得含糊，模型自己猜参数格式，日期一会儿是时间戳一会儿是中文。
2. **上下文被响应撑爆**：接口返回几百行 JSON 原样进对话，几轮之后 token 消耗失控。
3. **错误处理失效**：接口超时或 4xx 时只回一句 "request failed"，模型开始编造结果。

这些不是模型能力问题，是对接层的工程问题。

## 做法

按这个顺序做，基本可以少走弯路：

**第一步：圈定暴露面。** 先只挂只读、幂等的接口。列表类接口必须带分页参数，并在工具描述里写明默认返回条数上限。

**第二步：把工具描述当 prompt 写。** description 和参数说明是给模型看的文档，不是给人看的 API doc。每个参数给一个示例值，写清格式约定（`YYYY-MM-DD` 还是时间戳）。这一步投入产出比最高。

**第三步：裁剪返回体。** 在 MCP server 层做字段投影，只返回 agent 决策需要的字段；大文本截断，并附提示“可用 detail 参数获取全文”。

**第四步：凭证外置。** API key 走环境变量或 secret 管理，配置文件里只留引用。不要把 token 放进系统提示词——它会被 trace 和日志带出去。

**第五步：超时与错误结构化。** 每个工具调用设硬超时（我们的经验是 10–15 秒），错误统一成 `{ ok, error_code, hint }` 三段结构，hint 里写清模型下一步该做什么，比如“缩小时间范围后重试”。

**第六步：灰度放开写操作。** 只读跑稳一周后再挂写入接口，并在 OpenClaw 侧加人工确认环节。

## 踩坑点

- **参数示例比长篇描述有效。** 与其写三段说明，不如直接给一个正确调用的样例。
- **不要透传原始错误。** DNS 失败、连接重置这类底层报错对模型是噪音，要在插件层翻译成可操作的建议。
- **警惕隐式状态依赖。** 两个工具各自单测都能跑通，但 agent 自行组合时调用顺序可能不对；依赖关系强的，干脆合成一个复合工具。
- **trace 日志比想象中重要。** 上线后靠 trace 才发现模型频繁用错时区参数——这类问题只有看真实调用记录才会暴露。

## 可复用建议

- 把“工具描述 + 参数示例 + 错误 hint”做成团队模板，新服务接入照着填，不靠个人手感。
- 所有工具共享同一套错误结构和超时配置，agent 的行为才可预期。
- 接入清单固定为六项：只读优先、描述含示例、返回裁剪、凭证外置、超时加结构化错误、写操作带确认。

## 总结

对接外部服务的本质不是“让 API 能被调用”，而是“让模型正确地使用 API”。认证、超时、裁剪是工程问题；工具描述和错误返回其实是 prompt 工程问题。把这两类问题分开对待，OpenClaw 里的工具接入就从碰运气变成可以复制的流程。
