## 背景

订阅了 40 多个 RSS 源之后，每天全文阅读变得不现实。AI 摘要的价值不在"替你读"，而在"替你筛"。OpenClaw 自带定时任务和 skill 体系，正好把这件事做成一条稳定跑着的管线，每天早晚各产出一条日报。

## 问题

三个核心痛点：

1. **时间**：30+ 篇全文阅读，一天两小时起步；
2. **噪音**：实测八成条目可以跳过，但混在列表里没法一眼分辨；
3. **成本**：全量塞给 LLM 做 summary，token 消耗完全撑不住。

## 做法

管线拆成五段：**抓取 → 去重 → 分诊 → 摘要 → 推送**，每段独立、幂等。

**1. 抓取**：cron 定时拉 OPML 里的全部 feed，没有原生源的站点用 RSSHub 补。原始条目先落 SQLite，字段包括 guid、link、title、published、raw_html、fetched_at——先存原文，后面怎么加工都行。

**2. 去重**：guid 并不完全可靠（RSSHub 路由重启后可能变化），用 link 哈希 + 标题相似度做双保险。

**3. 分诊**：用便宜的模型先跑一遍，输出结构化 JSON，三档分类——`值得读 / 可略 / 忽略`。只有"值得读"的条目进入第二级摘要，换更好的模型，单条输入限制 3000 字符。摘要 prompt 要求：不超过 3 条要点，加一句"为什么值得读"，必须保留原文链接。

**4. 推送**：汇成一条 markdown 日报，通过 OpenClaw 的消息渠道发到 Telegram。被标记"内容疑似截断"的条目只列标题，不硬编摘要。

整条管线包成一个 OpenClaw skill，除了定时触发，agent 收到"今天有什么值得看的"这类消息时也能手动跑一次。

## 踩坑点

- **全文截断导致幻觉**：很多 feed 的 description 只有前 200 字，直接摘必然编内容。检测截断（原文过短且以省略号结尾）就回源抓正文，抓不到就明确标记，宁缺毋滥。
- **结构化输出不稳定**：模型返回的 JSON 经常裹着 markdown 代码块，做一次容错解析，失败重试一次，再失败就降级为"仅标题"。
- **推送疲劳**：最初每小时推一次，三天就麻木了。改成每日一条汇总，只有高优先级条目才即时提醒。
- **RSSHub 路由静默失效**：不报错，就是不更新。给每个 feed 记录最后成功时间，连续失败 N 次就在日报末尾提示自己该修路由了。
- **token 成本**：全量摘要一天成本可观。加上分诊 + 摘要缓存（同一条永不重复处理）之后，降了一个量级。

## 可复用建议

- **先存原文，后加工**：模型迭代了可以直接全量重跑，历史数据不浪费。
- **让 AI 做分诊而不是全文摘要**：性价比高得多，也更不容易翻车。
- **每段幂等、可独立重跑**：排障时逐段验证，不用每次从头排查。
- **日报永远带原文链接**：摘要只是路由，不是阅读的替代品，重要条目还是要点进去。

## 总结

RSS 提供了最稳定、可预期的输入层，AI 负责压缩和分诊。这套方案不追求"全自动阅读"，而是把"筛"的成本降到接近零——目前每天维护成本约等于零，省下的阅读时间很实在。下一步计划把"值得读"条目自动归档到本地笔记，作为个人知识库的入口，跑通后再分享。
