## 背景

每天项目维护会前，我需要汇总 GitHub Actions、Slack 讨论、线上告警和工单变动。人工汇总的问题不是“写不出来”，而是信息源一多，原始日志格式混乱、噪音重，真正值得写进日报的往往只有十几条。最早尝试让 Agent 直接读原始日志生成日报，结果要么上下文爆掉，要么把时间线和责任人都搞错。

## 问题

原始日志直接进 LLM 有三个典型问题：

1. **上下文超限**：CI 日志动辄几千行，全量喂入不现实。
2. **结构化不稳定**：自然语言输出日报字段时有时无，后续无法入库或 diff。
3. **噪音干扰**：大量 INFO、缓存命中、机器人回复会淹没真实风险。

因此我把流水线拆成四段：采集 -> 标准化 -> 事件提取 -> 报告生成。

## 做法

### 1. 采集：用 MCP 封装只读数据源

在 OpenClaw 里挂了三个 MCP 工具：GitHub Actions 日志读取、Slack 频道消息拉取、监控告警查询。工具全部只读，限制时间范围和条数，避免 Agent 误操作。例如 `github_list_failed_runs` 只返回失败 run，不提供 rerun 能力。

### 2. 标准化：规则先清洗，不急着上 LLM

原始日志先过 Python 脚本做三件事：

- **统一时区**：全部转成 Asia/Shanghai，避免 UTC 和本地时间混排。
- **按时间桶分组**：30 分钟一个桶，保留桶内事件顺序。
- **截断**：单条日志超过 2000 字符只保留头部和尾部错误栈。

这一步没有用 LLM，纯规则处理，速度很快。

### 3. 事件提取：高置信规则 + Agent 摘要

清洗后的日志进入“事件提取器”。高置信事件用正则匹配：`failed`、`error`、`timeout`、`deploy`、`revert`、`security alert`。匹配到的直接生成结构化事件，带时间、来源、级别、原文链接。

剩下没匹配到的片段，才交给 Agent 做摘要，并要求它回答三个问题：这件事是否影响交付？是否需要今天跟进？涉及哪些人或服务？输出 JSON。

### 4. 报告生成：模板 + schema 约束

最后用固定 Markdown 模板生成日报。Agent 只负责填充字段，不负责排版。输出 schema 收敛到 5 个字段：

- `date`
- `summary`（2-3 句）
- `key_events`（数组，每条含 time/source/level/note/link）
- `risks`
- `follow_ups`

生成后写入 `report/YYYY-MM-DD.md`，并附上原始日志索引链接，方便人工复核。

## 踩坑点

- **LLM 直接读原始日志会编造时间线**。尤其是跨时区日志，模型经常把 UTC 时间当成北京时间。所以时区转换必须在预处理完成，不能让模型算。
- **结构化输出不稳定时，不要增加 prompt 复杂度**。先把 schema 字段砍到最少，再用 JSON mode + retry。我在字段超过 8 个时重试率明显上升。
- **长日志截断别只留头部**。很多关键错误栈在尾部，只取前 2000 字符会丢掉根因。建议头尾各保留，中间用省略标记。
- **MCP 工具权限不要开写操作**。曾给过一个“标记已处理”的写工具，结果 Agent 在测试时把一条未确认的告警标记了，差点漏报。现在所有数据源工具只读，写操作放人工审批流。

## 可复用建议

- **先规则后 LLM**：能正则确认的事件不要用模型归纳，省钱也稳定。
- **日志索引比日报正文更重要**：日报里每条事件都带原始链接或文件行号，人工复核才有依据。
- **把日报模板版本化**：模板改动走 Git，避免 Agent 生成格式漂移。
- **保留失败现场**：生成日报失败时，把标准化后的中间文件存到临时目录，便于排查是采集问题还是生成问题。
- **日报不是终点**：可以再加一个轻量 review 插件，对生成结果做字段完整性检查，缺字段就退回重试。

## 总结

这条流水线跑了两周，最明显的变化不是日报变“聪明”，而是变得可核查。原始日志经过规则预处理后，Agent 的输入从几千行降到几十条候选事件，生成结果稳定很多。对 OpenClaw 用户来说，MCP 只读工具 + 规则预清洗 + 小 schema 生成，是一套比较务实的组合。
