最近开发者圈子里流传一个说法：OpenAI 的 Codex 开始支持从 Claude Code “一键迁移”。所谓“家当”——项目规则、MCP 连接、自定义命令——据说都能搬进 Codex；唯独 Claude 本身，不在迁移清单里。这里的“Claude”不是指某个文件夹，而是 Claude Code 背后的模型能力与决策风格。



## 一、先看“家当”清单：能搬走的都是什么

Claude Code 在开发者手里已经不只是补全工具，更像一个会读项目、会调工具、会执行长任务的 agentic coding 工作台。长期使用下来，真正沉淀为“家当”的，通常有四类：

- **项目规则文件**：比如 `CLAUDE.md`，描述目录结构、编码规范、测试命令、提交习惯等。很多团队把这类文件放在项目根目录，让模型每次启动都自动加载。
- **MCP 配置**：通过 `mcpServers` 声明连接的外部工具，比如 GitHub、Postgres、浏览器、issue tracker。Anthropic 在 2024 年把 MCP 推成开放协议后，这部分逐渐成为 agent 工具调用的标准接口。
- **自定义命令与脚本**：用户自己写的 slash commands、shell 脚本，用来完成固定任务，如“生成 changelog”“跑回归测试”“检查依赖安全”。
- **环境变量与偏好**：API key、代理地址、模型参数、是否自动执行命令、是否显示 diff 等。

这些资产有一个共同点：它们都是可序列化的文本。位于 `~/.claude/` 或项目根目录，格式不外乎 JSON、TOML、Markdown、Shell。Codex 的迁移工具要做的事情，在工程上并不神秘——解析这些文件，把 Anthropic 的字段映射成 Codex 的字段，把规则文件复制或改名，把 MCP endpoint 重新注册。

例如，Claude Code 里的 `CLAUDE.md` 到 Codex 环境可能对应 `AGENTS.md`；MCP server 的声明结构在两边略有差异，转换器会补齐字段、调整默认值。严格说，这不是“搬空”，而是一次配置层的翻译与重建。

## 二、迁移的技术现实：控制面与模型层



如果把 Claude Code 拆开看，会得到两部分：上面是配置控制面，下面是模型能力层。一键迁移主要发生在控制面。

- **可迁移的控制面**：规则、工具连接、命令、环境变量、记忆偏好。它们像插在墙上的插座和家具，位置、形状、标签都能被读到，也能被重新部署到另一套系统。
- **不可迁移的模型能力层**：Transformer 权重、训练数据分布、强化学习阶段的目标、长上下文处理策略、采样与安全约束、agentic 推理中的隐式偏好。这些并不存在于 `~/.claude/` 下，无法用 JSON 表示，也无法通过一键脚本导出。

用个不太精确但直观的比喻：配置文件是房间里的家具，模型是房子的地基和管线。搬家时，家具可以打包，电源插座可以重排，但地基不会随车走。

同样的 `CLAUDE.md`，写一句“遇到不确定时先询问用户”，Claude 可能表现为执行到关键步骤前暂停确认；换一个模型，可能把它理解成每一步都问，也可能为了效率直接尝试最小修复。这种差异不是靠更详细的规则就能完全消除，因为它来自模型在训练中形成的决策分布。

## 三、真正带不走的是什么？

迁移后很多人会发现，最难复制的不是规则，而是一种“默认手感”。它至少包括四件事：

1. **长任务稳定性**：在大型 repo 里，Claude Code 经常能保持“读取—计划—修改—跑测试—回溯”的循环不容易断。这不是提示词写得好，而是模型在长上下文和 agentic 任务上的行为倾向。
2. **错误恢复风格**：测试挂了、依赖缺失、需求模糊时，模型是回到现状排查，还是先做最小改动再验证，不同的训练策略会给出完全不同的路径。
3. **代码品味**：命名、抽象、注释密度、错误处理方式等，虽然用户可以写规则，但规则只能划定大方向，真正落笔还是模型。
4. **安全边界**：面对危险命令、密钥处理、外部内容里的指令注入，模型是否拒绝或要求确认，属于训练阶段植入的策略，不是配置文件能完全描述的。

所以那句“唯独带不走 Claude”并不矫情。杯子、桌子都能搬走，但泡出来的咖啡不是一个味。

## 四、OpenAI 的策略：不是搬空，是降低切换成本

从商业上理解，这个工具的目标不是真的要“搬空”Claude Code，而是把开发者的迁移成本压到最低。

- **降低用户的心理门槛**：手动重建规则、重新配 MCP、重新熟悉参数，这些琐碎步骤会阻止很多人尝试 Codex。一键迁移把它们省掉，用户试错成本立刻下降。
- **扩大 Codex 的入口**：Codex 背后是 OpenAI 的模型家族、云端任务和多模态能力。用户一旦把工作流搬进去，后续试用新模型、订阅新功能的路径会变得很短。
- **护城河不在配置，而在模型**：Anthropic 的 Claude Code 从未把配置文件当成秘密武器。配置是开放的、可解析的；真正难复制的是 Claude 模型本身，以及它与用户工作流长期磨合出来的隐性适配。

因此，“搬空”的说法更适合当作社区里的夸张表达。更准确的事实是：OpenAI 搬走的是切换成本，没有搬走 Claude 的核心体验。

## 五、迁移前，可以带着三个判断



如果你正在考虑把 Claude Code 的工作流迁到 Codex，三个实用建议可能比一键按钮更有价值：

- **先做可回滚迁移，不要立刻删除 Claude Code**。迁移工具可能遗漏自定义字段，也可能把某个 MCP 配置转错。至少保留原环境两周，能随时退回，比省事重要。
- **用同一个任务做 A/B，而不是凭第一印象**。挑一个中等复杂度的真实 issue，让两边分别完成，比较完成率、修改范围、测试通过率和人工修正时间。不要只看“导入成功”或“界面好看”。
- **把项目知识写成中性配置，减少对单一 CLI 的绑定**。尽量使用标准 MCP、通用规则文件、独立 shell 脚本，减少对某个 CLI 专有字段的依赖。这样无论以后工具怎么变，迁移代价都会小很多。

这次“一键迁移”真正值得关注的，不是谁家的导入按钮更好用，而是工具链可以搬家，模型能力不能简单复制。选择 Codex 还是 Claude Code，最终还要看：你依赖的是配置，还是配置背后的决策质量。
