# OpenClaw 定时任务选型：cron 还是 heartbeat，别只看“能不能定时”

在 OpenClaw 里挂定时任务，很容易把 cron 和 heartbeat 当成同一种东西：反正都是“到点了自动跑”。但真上生产环境，选错触发方式带来的不是功能问题，而是重复执行、任务堆积、时区错乱、重启后行为不一致这类工程问题。

这篇文章不贴大而全的配置模板，只讲一个判断：**你的任务到底关心“日历时间”，还是关心“固定节奏”。**

---

## 背景：两种触发类型解决的不是同一类问题

OpenClaw 的任务配置里，常见两种定时触发：

- **cron**：基于日历表达式触发，比如每天 09:00、每周一 00:30。
- **heartbeat**：基于固定间隔触发，比如每 30 秒、每 5 分钟跑一次。

两者的核心差异不在表达式长短，而在语义：

- cron 的语义是“**在某个时间点发生**”；
- heartbeat 的语义是“**每隔一段时间发生一次**”。

这个差异在短间隔、长任务、重启恢复、多实例部署时会被迅速放大。

---

## 问题：为什么不能混用

一个典型错误是：用 heartbeat 做每日报表。

比如配置 `interval: 24h`，你以为它会每天同一时间跑。实际上 heartbeat 从进程启动那一刻开始计时。只要你重启过 OpenClaw、部署过新版本、或者进程被 OOM 拉起来过，触发时间就会整体偏移。可能今天 09:00 跑，明天 09:13，后天 08:47。

反过来，用 cron 做秒级探活也不合适。cron 的最小粒度通常到分钟，且大量短间隔 cron 会让调度器承担不必要的日历计算负担。心跳场景下，你更关心“上一个检查周期是否正常”，而不是“必须在 10:00:00 整触发”。

---

## 做法：按任务性质选择

### 适合 cron 的任务

- 日报、周报、月报
- 固定时间的数据拉取
- 业务对账、结算
- 需要“自然日/工作日/月末”语义的任务

判断标准一句话：**如果任务说明书里出现“每天 9 点”“每周一”“每月 1 号”，就用 cron。**

OpenClaw 中一个常见配置思路如下：

```yaml
tasks:
  - name: daily-report
    type: cron
    expr: "0 9 * * *"
    timezone: "Asia/Shanghai"
    action: invoke
    target: daily_report_agent
```

### 适合 heartbeat 的任务

- 队列消费/轮询
- 资源巡检、健康检查
- 事件驱动前的兜底扫描
- 需要“尽量快发现变化”的任务

判断标准：**如果你的目标是“保持检查频率”，而不是“在某个日历时间发生”，用 heartbeat。**

```yaml
tasks:
  - name: queue-watcher
    type: heartbeat
    interval: 30s
    action: invoke
    target: queue_worker_agent
```

## 踩坑点：真正容易出问题的不是选择，是边界

### 1. cron 时区默认 UTC

这是最常遇到的坑。任务配置里写了 `0 9 * * *`，以为早上 9 点跑，结果日志显示 UTC 时间，实际 17 点才触发。OpenClaw 如果运行在容器里，容器时区还未必是 `Asia/Shanghai`。

**做法：显式配置 `timezone`，并且用日志验证一次触发时间。**

### 2. 多实例 cron 重复触发

生产环境如果 OpenClaw 跑了多个实例，或者任务执行器横向扩容，同一个 cron 任务可能被多个实例同时触发。heartbeat 也一样，多个实例会各自计时、各自触发。

**做法：对关键任务加分布式锁，或用数据库唯一键做幂等。不要默认 OpenClaw 会替你处理重复触发。**

### 3. heartbeat 任务堆积

heartbeat 间隔 30 秒，但如果任务本身跑 45 秒，下一次触发又来了。没有并发控制的话，任务会堆叠，最后资源耗尽。

**做法：开启 `skip if running` 或等价配置；给任务设置超时；对慢任务不要用短 heartbeat。**

### 4. 重启后行为不一致

cron 重启后是否补跑、heartbeat 重启后从零计时的行为，需要在选型前确定。不同配置下，重启可能会导致“今天日报漏跑”或“心跳间隔被重置”。

**做法：关键任务在恢复后先检查今天是否已执行，再跑业务逻辑。**

---

## 可复用建议

1. **先写任务描述，再看表选型**  
   任务说明里出现“每天/每周/每月”，用 cron；出现“每 N 秒/分钟检查一次”，用 heartbeat。

2. **固定时间 + 高可用 = cron + 锁**  
   不要假设调度器是单点。

3. **短周期 + 有状态 = heartbeat + skip-if-running + timeout**  
   三个条件缺一不可。

4. **任务命名带触发类型**  
   例如 `daily-report-cron`、`queue-watcher-hb`，后续排查日志时能一眼定位。

5. **所有生产定时任务都要可观测**  
   至少记录：触发时间、任务耗时、是否跳过、是否重试。没有这些，定时任务就是黑盒。

---

## 总结

cron 和 heartbeat 不是“粗粒度 vs 细粒度”的差别，而是“日历语义 vs 节奏语义”的差别。

选 cron 的时候，你要管理的是时区、重复触发、漏跑；选 heartbeat 的时候，你要管理的是间隔漂移、任务堆积、重启恢复。把这两个语义搞混，才是大多数定时任务事故的起点。

如果只记一条：**任务说明里带“每天几点”，用 cron；带“每隔多久”，用 heartbeat。剩下的是工程兜底。**
