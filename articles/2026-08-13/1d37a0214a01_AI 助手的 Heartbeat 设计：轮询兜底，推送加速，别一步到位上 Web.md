## 背景

在 OpenClaw、Agent、MCP server 以及插件自动化场景里，heartbeat 从来不只是“我还活着”。它通常承担四类职责：

- **liveness**：进程/插件/MCP 连接是否存活
- **progress**：长任务执行到哪一步
- **result**：最终结果或错误回传
- **control**：取消、暂停、调整参数

很多实现会掉进两个极端：要么高频轮询，把本地插件或 MCP server 打满；要么一上来就 WebSocket/SSE，随后被断线重连、鉴权、多实例状态同步拖垮。

## 问题

轮询实现简单，客户端只需要定时 GET。但延迟和无效请求会随任务数线性增长。比如一个 MCP 工具执行长任务，每 2 秒拉一次 `/status`，50 个并发任务就是每秒 25 次请求，其中大部分状态根本没变。

推送延迟低，服务端有变化立即下发。但它要求连接管理、断线补偿、事件乱序去重、背压控制。如果部署在 Nginx 后面，SSE 还可能被缓冲，导致事件迟迟不到客户端。

所以核心不是“轮询还是推送”，而是：**默认轮询兜底，按需推送加速**。

## 做法/步骤

### 1. 先拆事件类型，不要混在一起

建议至少把 heartbeat 拆成四类：`liveness`、`progress`、`result`、`control`。不要让一个接口既上报存活，又携带大段进度，又处理取消确认。

### 2. 任务启动返回 task_id

长任务不要同步等待结果。启动时返回 `task_id` 和初始状态，后续所有查询、推送都挂到 `task_id` 上。这能避免客户端和服务端各自维护一套隐式状态。

### 3. 低频轮询作为兜底

保留一个轻量查询接口：

```text
GET /tasks/{task_id}/status
```

返回内容尽量小：

```json
{
  "task_id": "abc",
  "state": "running",
  "seq": 42,
  "updated_at": "2025-01-01T00:00:00Z"
}
```

轮询间隔可以放到 15–30 秒。它不是主要实时通道，但能保证推送断开后系统仍可用。

### 4. 需要低延迟时再加推送

如果状态变化需要秒级感知，再加 SSE。SSE 适合单向状态流；只有需要双向高频控制时才考虑 WebSocket。

事件只推变化，不推全量。比如：

```text
event: progress
data: {"task_id":"abc","seq":43,"percent":60}
```

客户端如果发现序号不连续，可以重新拉一次完整状态。

### 5. 推送断开自动降级

客户端监听 SSE `onerror` 或连接关闭后，自动切回轮询。重连成功后再切回 SSE。不要让推送成为唯一依赖。

### 6. 心跳状态存储

多实例部署时，心跳状态放 Redis，并设置 TTL。超过 3 个心跳周期没有更新就标记 `stale`。不要只存单机内存，否则负载均衡后状态会分裂。

## 踩坑点

### 1. 轮询间隔太短

见过插件每 1 秒拉一次 `/status`，并发起来后数据库 QPS 冲到 300+，其中大量查询无变化。轮询间隔应该根据任务时长和可接受延迟来定，而不是拍脑袋。

### 2. 推送链路假死

TCP 连接还在，但应用层已经不产数据。不能只依赖 TCP 判断存活。SSE 需要定期发注释行或 `ping` 事件；WebSocket 需要应用层 ping/pong。

### 3. Nginx/代理缓冲 SSE

Nginx 默认会缓冲响应，导致 SSE 事件不即时到达。需要：

```nginx
proxy_buffering off;
proxy_cache off;
proxy_set_header X-Accel-Buffering no;
```

否则你会看到事件等很久才一批一批地到。

### 4. 每个心跳都写数据库

如果每次 heartbeat 都直接更新 MySQL/Postgres，任务多了会锁表、写放大。正确做法是先写 Redis，定期批量落库，或者只写状态变化。

### 5. 控制信号不要走事件流确认

取消操作用 `POST /tasks/{id}/cancel` 直接下发。事件流只负责通知状态已经变成 `canceled`。不要在事件流里做请求-确认往返，复杂度会爆炸。

### 6. 重连风暴

客户端断线后同时重连，可能把服务打挂。重连要加指数退避和随机抖动，例如 1s、2s、4s、8s，最大 30s，并加上 ±20% jitter。

## 可复用建议

- **默认架构：低频轮询兜底 + SSE/WebSocket 推送加速。** 轮询永远保留，作为降级路径。
- **心跳数据结构尽量小。** 只传 `task_id`、`state`、`seq`、`timestamp`。详细 progress 单独拉取，不要塞进心跳。
- **把 heartbeat 参数做成配置。** `interval`、`stale_after`、`retry_backoff` 都应该可调，不同插件/任务可能需要不同值。
- **客户端必须幂等。** 事件可能重复、乱序。用 `seq` 去重，发现缺口时主动拉取完整状态。
- **监控三个指标：心跳延迟、心跳丢失率、重连次数。** 如果重连次数突然上升，通常不是客户端问题，而是服务端或网络有问题。

## 总结

Heartbeat 设计不是选轮询还是推送，而是选“默认轮询 + 按需推送”。先把状态机、幂等、降级路径做清楚，再考虑 WebSocket。工程上最稳的方案，往往是看起来最朴素的方案：一个轻量轮询接口，一个可选的 SSE 事件流，以及一套明确的降级规则。
