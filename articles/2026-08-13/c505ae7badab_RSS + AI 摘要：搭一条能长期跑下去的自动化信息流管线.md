## 背景：信息过载不是源太多，而是“处理不过来”

我订阅了大概 60 多个 RSS 源，覆盖安全公告、开源项目 release、技术博客、行业报告。真正的问题不是看不到信息，而是每天打开 Reader 后面对两三百条未读，最后只精读了不到 5 条。

很多“AI 信息助理”项目一上来就做得很重：向量库、知识图谱、多步 Agent、自动写报告。实际跑两周就发现维护成本远超收益。这篇文章想讲一条更朴素的管线：RSS 抓取 → 规则过滤 → AI 摘要 → 推送。目标不是“全自动知识库”，而是把每天需要人工判断的信息，压缩到 20 条以内。

## 问题拆解

一条可用的自动化信息流管线，至少要解决四件事：

1. **源质量参差**：有的源一天更新几十条，有的源经常抓不到正文。
2. **重复与噪音**：同一事件会被多个源报道，相似标题需要归并。
3. **摘要不能只是缩短**：需要保留“为什么值得看”的判断。
4. **推送频率克制**：推送过多，等于没有推送；推送过少，又漏掉关键信息。

## 做法与步骤

我当前使用的管线如下：

```
RSS 源
  ↓
Miniflux / FreshRSS（抓取、分组合并、保留已读状态）
  ↓
定时任务：每小时拉取未读条目
  ↓
规则过滤（关键词、源权重、标题正则）
  ↓
去重归并（标题相似度 / URL 归一化）
  ↓
AI 摘要（结构化输出）
  ↓
落盘 SQLite + 推送（Telegram / ntfy / 邮件）
```

### 1. RSS 层：用 Miniflux 而不是裸跑 feedparser

建议把抓取和状态管理交给专门的 RSS 服务。Miniflux 或 FreshRSS 都能处理重试、ETag、缓存、已读标记。自行用 feedparser 写抓取很快会遇到编码、超时、登录墙、Cloudflare 验证等问题。

Miniflux 提供简单的 REST API，可以按 category、status=unread、after 时间拉取条目。这样 Agent 或定时脚本不需要关心 RSS 原始格式。

### 2. 过滤与去重：先规则，后模型

不要一上来就让 LLM 判断“是否重要”。先做确定性过滤：

- 白名单关键词：项目名、CVE 编号、指定技术栈。
- 黑名单：招聘、广告、转载声明、抽奖。
- 源权重：核心源直接通过，泛技术媒体仅保留高互动或长文。
- URL 归一化后精确去重。
- 标题相似度：对标题做小写、去标点、移除版本号差异，再用 difflib 或 simhash 归并。

这一步能把原始 200 条压到 40 条左右，节省大量 token。

### 3. AI 摘要：要求结构化，但别过度结构化

摘要 prompt 我固定成三行：

```
你是一个技术信息过滤助理。
请阅读以下 RSS 条目，输出 JSON：
{
  "relevance": 0-10,
  "summary": "不超过40字的中文摘要",
  "technical_point": "关键技术点或变化，没有则写无",
  "action": "需要用户行动/阅读理由，例如影响范围、破坏性变更、复现步骤"
}
只输出 JSON，不要解释。
```

关键点：**让模型给出“行动理由”而不是复述标题**。对安全公告类源，`action` 需要说明影响面；对 release 类源，需要点出 breaking change；对博客类源，需要说明是否提供可复现代码。

我会按源类型拆 prompt。批量调用时用 JSON mode 或 function calling，避免 Markdown 包裹 JSON 需要二次清洗。

### 4. 调度与状态：OpenClaw/Agent 只做编排，不做存储

我让 OpenClaw 里的 Agent 每小时执行一次计划任务：

1. 调用 Miniflux API 拉取未读。
2. 跑过滤脚本。
3. 对剩余条目逐批调用 LLM。
4. 写 SQLite，并根据 `relevance` 阈值决定是否推送。
5. 将已处理条目标记为已读。

状态全部落 SQLite，不依赖 Agent 的短期记忆。这样 Agent 重启、上下文丢失都不影响处理结果。

推送使用 Telegram bot。每天推送上限设为 15 条，超过则合并到一条“今日还需人工扫读 N 条”的汇总消息。

## 踩坑点

**1. RSS 正文缺失**
很多博客 RSS 只提供摘要或前 200 字。如果你只给 LLM 摘要而不给正文，输出质量会明显下降。应对方法：优先用 Miniflux 的 `content` 抓取；若正文仍为空，则用 source URL 尝试 `trafilatura` 抽取正文；再失败则直接跳过该源并记录。

**2. 相似度归并误伤**
不同源的同一事件标题可能差异很大。纯标题相似度无法处理“公告 A 修复漏洞”和“漏洞详情分析”这种有价值差异的内容。建议归并只针对同一 URL、同一 CVE/版本号、同一项目名且发布时间接近的条目，不要全局去重。

**3. LLM 输出不稳定**
即使要求 JSON，模型偶尔仍会返回带 Markdown 代码块的结果，或字段缺失。解析层要做 schema 校验和异常重试；重试一次仍失败则降级为原始标题推送，避免整批卡住。

**4. 推送阈值难调**
`relevance` 评分为 0-10，但模型评分分布往往集中在 6-8，区分度不高。可以在 prompt 里加入锚点：例如“安全公告影响广泛为 8 分以上，常规博客为 4-6 分”。也可以改为二分类：是否值得推到前台。

**5. 费用与延迟**
每小时调一次 LLM，60 个源会产生固定 token 消耗。中等规模日处理 200-300 条，用轻量模型足够，不要用旗舰模型做摘要。批量接口能明显降低延迟。

## 可复用建议

- **中间态先落盘**：每一步的输出都存 SQLite/JSONL，方便回溯哪一步误杀或漏掉。
- **保留“原始标题 + 链接”**：AI 摘要再准也不能替代原文，推送必须带链接。
- **分阶段上线**：先只跑过滤和去重，人工读一周，确认规则有效后再接入 AI 摘要和推送。
- **允许低优先级不推送**：所有条目都生成摘要，但只有高相关性才推送。低相关条目保留在 SQLite 里，可随时按天查询。
- **记录失败源**：连续多次抓取失败或正文抽取失败的源，自动降权或暂停，避免管线被坏源拖累。

## 总结

这条管线没有什么“智能体自动发现信息价值”的魔法，本质上是把原来纯人工的“刷 RSS、判断重不重要、提炼重点”变成一个确定性的流水线。AI 只负责其中最不可替代的那一步：在过滤之后，把几十条候选压缩成十几条可行动摘要。

对 OpenClaw/Agent 用户来说，更适合把 Agent 当编排器和异常处理器，而不是信息存储和执行主体。状态外置、步骤可回放、失败可降级，才能让这种管线跑过一个月、一个季度，而不是演示三天后停更。

先把 60 个源压到 20 条以内，比做一个能“自动生成每日情报报告”的系统更值得做。
