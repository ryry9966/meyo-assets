# 用 HEARTBEAT.md 给 OpenClaw Agent 加一个心跳：从被动问答到主动值守

## 背景

在 OpenClaw 上跑 Agent 一段时间后，会发现一个很尴尬的问题：大多数 Agent 仍然是“问一句动一下”。它有能力调 MCP 工具、读文件、查日志、操作 Issue，但如果你不主动发消息，它就一直闲着。

很多适合自动化的场景——日志巡检、未处理 Bug 跟踪、队列任务消化、数据源变化检测——本质上不需要人每次提问。它们缺的不是模型能力，而是一个稳定的“主动触发协议”。

## 问题

被动 Agent 的典型表现：

- 日志出现 ERROR，但只有等你打开会话问“帮我看看日志”才会被发现。
- MCP 工具明明能查 GitHub Issues，但未处理 Bug 一直堆积。
- 你写了一个队列文件，Agent 不会自己消费，需要你手动逐条丢给它。

要让 Agent 主动做事，不能只靠 system prompt 里写“你要主动一点”。这种模糊指令很快会被遗忘，或者变成随机行为。我们需要一个明确的、可执行、可审计的入口文件，也就是 `HEARTBEAT.md`。

## 做法

### 1. 定义 HEARTBEAT.md

把它放在 Agent 的工作目录下，作为心跳协议。内容尽量结构化，不要写散文。

示例：

```markdown
# HEARTBEAT.md

## 触发
- 每次空闲会话开始或定时调度触发时执行一次。
- 如果 .heartbeat/state.json 中 last_run 距今小于 25 分钟，跳过。

## 检查项
1. 读取 ./logs/app.log 最后 200 行，查找 ERROR/CRITICAL。
   - 成功标准：无新增错误，或错误已记录。
   - 输出：新增错误计数。
2. 调用 MCP 工具 github.list_issues，筛选 label=bug 且 update > 1d。
   - 成功标准：返回列表。
   - 输出：未处理 Bug 数。
3. 检查 .heartbeat/queue.md 是否有待处理任务。
   - 若有，只读取并列出，不直接执行写操作。

## 输出
将结果追加到 .heartbeat/log/YYYY-MM-DD.md，格式：
| 时间 | 检查项 | 状态 | 摘要 |
```

### 2. 注入到 Agent 配置

在 OpenClaw 的 Agent 引导文件或 system prompt 中加入：

```text
你是一个常驻 Agent。每次会话开始或收到心跳调度时，先读取 HEARTBEAT.md，按协议执行。只读检查可以直接执行；任何写操作必须先说明意图并等待人工确认。
```

这样心跳文件成为 Agent 的“默认入口”，而不是依赖某次对话上下文。

### 3. 用调度器触发

可以用 cron 或 systemd timer 定期触发 Agent 会话：

```bash
*/30 * * * * cd /opt/agent && openclaw run --task heartbeat
```

具体命令以你使用的 OpenClaw 版本为准。关键是触发后 Agent 第一件事是读 `HEARTBEAT.md`，而不是等待用户输入。

### 4. 写入状态文件

心跳任务必须幂等。用 `.heartbeat/state.json` 记录：

```json
{
  "last_run": "2025-04-11T10:30:00Z",
  "last_success": true,
  "cursor": "app.log:2025-04-11T10:29:58Z",
  "last_issue_id": 1203
}
```

下次运行时先读状态，避免重复扫描和重复上报。

## 踩坑点

**1. 频率过高导致 token 消耗失控**

最早我们把心跳设为 5 分钟一次，Agent 每次都会重新扫描整个仓库或全量日志，token 消耗很大。后来改成“先读 state 文件，超过阈值再执行”，成本明显下降。

**2. 让心跳直接执行写操作**

有次让 Agent 自动重启失败服务，结果它没有确认就把整个 docker-compose 重启了，影响到了其他容器。后来规则改成：心跳只报告，重启、删除、合并这类写操作必须人工确认。

**3. MCP 工具返回过大 JSON**

Agent 很容易在长 JSON 里漏掉关键字段。可以要求 MCP 工具或中间层返回摘要，而不是全量数据。心跳里只处理结构化摘要，会稳定很多。

**4. 输出没有固定格式**

如果心跳日志是自然语言描述，后面很难 grep 和审计。统一用 Markdown 表格或 JSON Lines，排查问题时会省很多时间。

## 可复用建议

- 先从一个只读检查项开始，跑通整个心跳链路，再逐步增加。
- 所有写操作加审批门槛，心跳阶段只读为主。
- 每次心跳只做 3–5 项，避免上下文过长导致漂移。
- 失败也要记录。心跳失败不能静默，否则会变成“以为它在跑，其实早停了”。
- 把心跳日志当作审计和提示词优化的素材，每隔一段时间回头看看误报率和漏报率。

## 总结

`HEARTBEAT.md` 不是另一个花哨的规范，它更像给 Agent 装了一个低频、可预期的循环系统。核心不是“让 AI 更主动”这种模糊目标，而是把主动行为固化成可解析、可执行、可回滚的文件协议。

对 OpenClaw 用户来说，这套做法的成本很低：一个 Markdown 文件、一个状态文件、一个定时触发。跑通之后，Agent 会从“等你提问的应答机”，慢慢变成真正能在后台值守的自动化节点。
