# 社区自动发帖的节奏控制：从固定间隔到行为拟真

## 背景

用 OpenClaw、MCP 或自建 Agent 做社区自动发帖时，大多数方案只解决“能不能发出去”，很少认真处理“发得多像人”。常见实现是：内容生成后 `sleep 3600` 再发下一条，或者干脆批量执行。上线前几天可能正常，但很快会碰到验证码、限流、帖子仅自己可见，甚至账号被限制。

真正的问题不在“有没有延迟”，而在节奏是否像真实用户。社区风控通常不只盯单条行为，而是看时间分布、内容指纹、交互轨迹和失败模式。把节奏控制做成工程化模块，比单纯加随机数有效得多。

## 问题拆解：为什么“随机延迟”不够

随机延迟只解决单次间隔的机械感。它至少漏掉四件事：

1. **日内分布**：真人不会在凌晨 3 点频繁发帖。完全随机可能产生凌晨高频、白天沉默的异常模式。
2. **内容重复度**：即使时间像人，内容如果总是同一模板加几个词替换，平台文本指纹很快会聚类。
3. **路径完整性**：正常用户发帖前会浏览、点赞、回复，而不是登录后直接发帖。
4. **失败后的行为**：触发验证码或审帖失败后，继续按原计划发帖是典型的机器人特征。

所以节奏控制需要覆盖时间、内容、行为、失败处理四个维度。

## 做法：三层节奏 + 行为预热

### 1. 定义人类作息窗口

把发帖时间限制在合理窗口内，而不是全天随机。例如：

```yaml
schedule:
  timezone: Asia/Shanghai
  windows:
    - ["09:00", "11:30"]
    - ["14:30", "17:30"]
    - ["20:00", "23:00"]
  base_interval_min: 45
  jitter_ratio: 0.4
  max_posts_per_day: 3
  cooldown_after_active_days: 3
  cooldown_days: 1
```

在窗口内生成发帖时间，并避开整点、半点。例如用 `base_interval_min * (1 ± jitter_ratio)` 计算下一次间隔。

### 2. 三级节奏控制

节奏至少分三个层级：

- **单帖间隔**：基础间隔加抖动。比如 45 分钟基础值，抖动 ±40%，实际间隔在 27–63 分钟之间。不要用固定值，也不要大范围完全随机。
- **日内配额**：每天最多发 2–4 帖，分不同时段。新账号建议从每天 1–2 帖开始。
- **周级冷却**：连续活跃 3 天后休 1–2 天，模拟真实用户的间歇性活跃。

这个逻辑可以封装成一个 `Pacer` 模块：输入窗口、配额、冷却规则，输出下一次可执行时间。建议使用确定性随机种子，便于回放和调试。

### 3. 内容生成侧加变异

同一主题让 Agent 生成 3–5 个候选标题和正文变体，做相似度阈值过滤。例如用 MinHash 或简单的 n-gram 去重，保证两次发帖内容相似度低于 0.6。不要只替换一两个词，最好改变句式结构、段落顺序和具体例子。

### 4. 行为预热

发帖前先执行 1–2 步轻量交互：浏览目标板块、点赞一条相关帖子、或回复一条短评论。路径可以随机选择，但不要每次完全一样。这样可以降低“登录即发帖”的突兀感。

### 5. 失败退避与熔断

遇到验证码、限流、审帖失败时，指数退避：第一次失败等待 2 小时，第二次 6 小时，第三次暂停当天任务。连续多天失败则进入熔断状态，停止自动发帖并输出告警，而不是继续重试。

## 踩坑点

- **随机范围太大**：一个 10 分钟到 10 小时的随机间隔，看似随机，实际会产生凌晨发帖或短时间连发。随机必须受作息窗口约束。
- **文本指纹相似**：即使间隔控制得很好，如果正文结构固定、只替换名词，平台仍能通过相似度识别。内容变异要与节奏控制同时做。
- **多账号行为一致**：多个账号使用同一 IP、同一设备指纹、同一时间发帖，即使单个账号节奏正常，也会被关联识别。尽量错开账号活跃窗口，避免共用指纹。
- **只关注发帖动作**：发帖成功不代表安全。后续的点赞、回复、编辑记录也会进入风控。自动发帖后不要立即关闭会话，可以留出 5–10 分钟的“在线尾巴”。
- **API 与 Web 行为不一致**：如果发帖走 API，但浏览、点赞走 Web，注意 User-Agent、TLS 指纹和操作间隔要接近真实浏览器。混用 API 和自动化浏览器时，容易产生行为断层。

## 可复用建议

1. **配置外置**：所有节奏参数放进配置文件，不要硬编码在代码里。这样可以根据不同社区平台调整。
2. **实现 dry-run 模式**：只生成发帖计划，不实际执行。把计划打印成时间轴，观察一天、一周的分布是否像人。
3. **解耦内容与节奏**：内容生成器只负责产出候选，Pacer 只负责决定何时发。两者独立测试，便于定位问题。
4. **从保守值起步**：新账号前两周每天 1–2 帖，间隔 90 分钟以上，观察平台反馈。没触发验证码再逐步放宽。
5. **记录审计日志**：每次动作记录时间、间隔、内容 hash、平台返回、是否触发风控。这样被限制时能回溯到具体参数。

## 总结

社区自动发帖不像机器人，核心不是“更随机”，而是把人类行为拆成可量化的维度：时间分布、内容变异、行为路径、失败策略。三层节奏控制加上小幅行为预热，配合保守参数和审计日志，比单纯 `random sleep` 可靠得多。先让系统“看起来像一个有点懒的真实用户”，再考虑提升频率，这条路径在工程上更可持续。
