## 背景

在 OpenClaw 这类 Agent 框架里，MCP 工具/插件通常会直接调用外部 API，比如搜索、天气、翻译、数据库、支付接口。很多自动化任务跑起来的前提，是这些外部 API 稳定可用。

但现实是：外部 API 一定会挂。可能是限流、超时、5xx、网络抖动，也可能是上游发布故障。Agent 与普通脚本最大的区别是，它在循环里做工具调用，一旦某个工具抛错，模型会根据错误信息“即兴发挥”——可能反复重试，也可能直接编一个结果，还有可能把错误信息写进记忆，污染后续推理。

所以错误恢复不能只靠模型聪明，得在工具层和 Agent 层之间建立一套明确的契约。

## 问题

常见的外部 API 故障大致三类：

1. **暂时性错误**：限流 429、短时 5xx、网络超时。重试往往有效。
2. **确定性错误**：参数错误 400、无权限 401/403、资源不存在 404。重试无效，应该终止。
3. **长时间不可用**：上游宕机、连续限流。需要熔断或降级，而不是继续尝试。

如果把原始异常直接抛给模型，模型很难区分“再试一次就好”和“别再试了”。它可能对 401 重试五次，也可能遇到一次 500 就放弃整个任务。更糟的是，有些框架把堆栈信息也塞给模型，既浪费 token，又干扰判断。

## 做法/步骤

### 1. 在工具层做错误分类，返回结构化错误

不要直接抛异常给 Agent。让工具返回结构化 JSON，例如：

```json
{
  "error_type": "rate_limited",
  "retryable": true,
  "retry_after_ms": 2000,
  "message": "上游限流，建议退避后重试"
}
```

这样模型只需要读取 `retryable` 字段，不需要理解堆栈。

### 2. 工具层内置超时与重试

超时是必须的。一个 API 挂起 30 秒，整个 Agent 任务链都会卡死。建议默认超时 5–10 秒，外部 API 调用统一走一个带超时的 HTTP 客户端。

重试策略用指数退避 + 抖动，避免重试风暴。重试次数控制在 2–3 次，并且只对 **幂等操作** 重试。GET、查询类可以重试；POST、写操作默认不重试，除非有幂等键。

### 3. 熔断与降级

如果同一个 API 在短时间内连续失败 N 次，可以短暂熔断，直接返回降级结果或结构化错误，让 Agent 走备用路径。例如：搜索 API 熔断后，返回缓存结果，并标记 `stale=true`。

降级只适合只读场景。写操作不要静默降级，否则会造成数据丢失或重复提交。

### 4. 给 Agent 明确的恢复协议

在工具描述或系统提示里写清楚：

> 如果返回 `retryable=true`，可以对同一个参数重试一次；如果 `retryable=false`，不要重试，直接向用户报告错误。

这比让模型自己“看着办”稳定得多。

### 5. 可观测性

记录每次外部调用的耗时、状态码、重试次数、是否熔断、是否降级。外部 API 故障往往是间歇性的，有日志才能定位是上游问题还是自己的策略问题。

## 踩坑点

- **把重试逻辑放在 Agent 层**：模型会随机重试，可能调用五六次，既费钱又容易把上下文刷爆。重试必须在工具层完成。
- **不设超时**：一个 API 卡死，整个自动化流程全部阻塞。
- **对非幂等 POST 重试**：可能造成重复下单、重复发送。写操作一定要谨慎。
- **静默降级不标记 stale**：模型把过期数据当实时数据，输出错误结论。
- **一次抖动就熔断很久**：熔断时间要短，比如 30 秒，避免过度降级。
- **把整个堆栈塞给模型**：浪费 token，干扰模型判断。错误信息要精简。

## 可复用建议

- 封装一个统一的外部 API 客户端，内置超时、重试、熔断、错误分类。不要在每个工具里重复实现。
- 策略配置化：不同 API 定义不同策略，例如搜索 API 允许降级，支付 API 禁止重试。
- 在 Agent 系统提示里加入错误处理协议，让模型知道什么情况可以重试、什么情况必须终止。
- 对写操作加幂等键，或先查询是否已执行。
- 给外部 API 加可用性监控，主动告警，而不是等任务失败才被动发现。

## 总结

外部 API 挂掉是常态，不是异常。AI Agent 的错误恢复核心不是让模型更聪明，而是把“能不能重试、要不要降级、该不该停下来”这些决策前移到工具层。工具层负责扛住短期故障，Agent 层负责在明确提示下做任务决策。两者之间有一份结构化错误协议，自动化流程才会稳。

不要指望模型自己硬扛 API 故障。工程上的事，还是在工程层解决。
