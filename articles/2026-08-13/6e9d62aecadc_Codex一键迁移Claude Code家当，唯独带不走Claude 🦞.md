这几天，开发者圈子里最像“搬家”的新闻，是 OpenAI 给 Claude Code 用户递来了一把钥匙：家当可以一键搬进 Codex。配置文件、MCP 服务器、自定义指令、甚至部分项目记忆，都被做成了导入项。听起来像换个房子，家具原样搬走。可真搬过去的人发现，有一件最重要的东西，搬不动。



## 一、这次“搬家”，到底搬了哪些东西？

在讨论“带不走”之前，先看哪些东西真的能带走。Claude Code 这类终端 AI 编程代理，日常使用会沉淀一批文本资产：

- `CLAUDE.md` / `.claude/settings.json`：项目规则、编码规范、约束条件。
- MCP（Model Context Protocol）服务器列表：连接外部工具、数据库、浏览器、知识库的“插座”。
- 自定义 slash commands 和 prompt 模板：常用操作封装成的命令。
- 部分对话历史和项目记忆文件，记录“这个项目怎么构建、怎么测试、有哪些坑”。

这些看似零散，但共同点很明确：都是可序列化的文本，能被解析、映射、重新写入另一个工具。迁移难度并不高，类似把浏览器书签导出再导入另一个浏览器。关键不是文件格式，而是文件背后的行为习惯。

## 二、一键进 Codex，技术上是怎么做到的？



工具迁移能“一键”，依赖的是这几年 AI 开发工具堆栈的隐性标准化：

- 配置文件从二进制/私有格式，逐渐转向 Markdown、JSON、YAML 等可读格式。
- MCP 成为连接外部能力的开放协议，让“工具调用链”可以跨平台复用。
- 大量规则被写在项目根目录的明文文件里，而不是藏在工具数据库深处。

Codex 做的导入器，本质上是一条流水线：

1. 扫描：识别目标目录中 Claude Code 常见配置文件名。
2. 解析：把 Markdown 规则、JSON 设置、命令模板结构化。
3. 映射：将 Claude Code 的字段对应到 Codex 自己的配置体系。
4. 校验与写入：检查冲突后生成新配置，并给出迁移报告。

这套流程和旧手机换新手机导数据类似：通讯录、相册、Wi-Fi 密码都能过去，但你的输入法词库、App 登录状态、消息推送习惯，经常是另一回事。

## 三、唯独带不走 Claude：真正难迁移的是什么？



文件可以搬，行为搬不走。开发者用惯了 Claude Code，真正离不开的往往不是那几行配置，而是下面这些“非结构化资产”：

- 模型推理风格：同一个需求，Claude 可能倾向于先写测试再实现，Codex 可能直接改代码。代码审美、重构时机、错误恢复策略，都是模型权重和行为策略共同塑造的。
- 隐性项目记忆：很多“这个 bug 上次怎么修的”“这个函数不要动”“本地环境有个特殊变量”没有被写进任何文件，只存在于你与工具的长期交互里。即使有摘要记忆功能，也不可能 100% 覆盖。
- 第三方生态与 hooks：Claude Code 周围长出了一圈插件、Git hooks、CI 集成、团队自定义脚本。迁移工具时，配置能过去，但这些插件不一定有对应实现。
- 账号、额度与团队权限：订阅关系、成本控制、审批流、审计日志，这些属于平台层，不是配置层。
- “手感”：什么时候该追问、什么时候直接动手、报错时先看哪一行，这种交互节奏很难被导出。

一句话：你搬走了厨房里的锅碗瓢盆，但没搬走那个熟悉你口味、知道你火候的厨师。

## 四、从“抢模型”到“抢工作流”：竞争逻辑变了



OpenAI 愿意花力气做迁移工具，本身就说明 AI 编程竞争已经进入新阶段：

- 基座模型能力差距在缩小：当代码生成、推理、工具调用都达到不错水平后，单纯比 benchmark 已经很难拉开用户差距。
- 切换成本的重心从“配置”转向“行为与生态”：配置可导入，但隐性习惯和插件生态不可导入，因此先把你拉进自己的生态，再靠时间积累新习惯，是更聪明的打法。
- 数据飞轮效应：你越用某个工具，它越了解你的项目和个人偏好；反过来，迁移到新工具初期的不适应，会让你觉得“还是老工具顺手”。
- 迁移功能本质是一种获客手段：降低离开旧工具的门槛，同时把用户数据导入自己的反馈闭环。

这很像当年的浏览器战争：收藏夹、密码、Cookie 都能导入，但你的插件组合、地址栏联想、自动填充逻辑，最终把你留在了某个浏览器里。AI 编程工具正在复制同样的路径。

## 收尾：三条冷思考与实用建议

与其纠结哪个工具更强，不如把迁移这件事当成一次对自身工作流的审计。

1. 把资产分层管理：规则、prompts、MCP 配置用 Git 版本控制，保持工具无关；关键决策、踩坑记录写进项目文档，减少对单一工具隐性记忆的依赖。
2. 定期做“逃生演练”：每季度手动把核心配置导出，尝试用另一套工具完成一次真实任务。不是为了马上切换，而是验证你的工作流有多少被绑定在某个平台上。
3. 迁移要灰度，不要一把梭：先选两个典型任务做对比，观察模型在重构、测试、报错处理上的行为差异，记录哪些偏差可接受、哪些不可接受，再决定是否全面切换。

工具可以一键搬空家当，但“顺手”这件事，只能靠时间重新长出来。
