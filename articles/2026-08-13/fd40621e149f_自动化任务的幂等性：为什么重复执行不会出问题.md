## 背景

自动化任务通常被设计成“执行一次”，但真实环境里重复触发几乎是常态：网络超时重试、消息队列至少一次投递、定时任务上次没跑完又到点、用户重复点击、Agent 多步调用中工具超时被框架重试。

在 OpenClaw、Agent、MCP、插件这些场景里，问题更明显。一个 MCP 工具可能在远端已经执行成功，但因为响应超时，Agent 认为失败并再次调用。插件被事件触发时，同一事件也可能重复推送。没有幂等性，重复执行就会变成重复副作用。

## 问题

非幂等自动化任务常见表现：

- 重复发消息、发邮件、创建工单；
- 重复建资源、重复写库；
- 余额、积分被重复扣减；
- 统计日志重复计数，数据翻倍；
- Agent 判断“没成功”再执行一次，结果产生两条业务记录。

根因通常是：执行动作和副作用没有绑定，缺少“同一业务意图只生效一次”的约束。

## 做法 / 步骤

### 1. 给业务动作分配幂等键

每个业务动作入口生成或透传一个 `operation_id` / `idempotency_key`。来源可以是任务 ID、事件 ID、上游请求 ID。不要每次重试都生成新的随机 UUID，否则没有去重效果。

### 2. 数据库层做唯一约束

例如：

```sql
UNIQUE(workspace_id, operation_id)
```

执行时先插入一条状态为 `processing` 的记录，成功后再更新为 `success`。重复执行会命中唯一键冲突，这时读取已有结果并返回，而不是报错。

### 3. 外部 API 尽量使用幂等键

很多支付、消息、对象存储接口支持 `Idempotency-Key`、`ClientToken` 或类似参数。把本地 `operation_id` 透传给外部服务，即使网络重试也不会重复创建资源。

### 4. 工具层封装幂等执行器

在 MCP 工具或插件内部封装：

```text
run_once(key, fn)
```

内部处理唯一约束、状态检查和结果缓存。重复调用同一 `key` 时，直接返回首次执行结果。工具描述里可以声明“使用 `request_id` 去重，可安全重试”。

### 5. 状态机前置检查

例如“创建实例”前检查是否已有实例；任务只允许从 `pending` 进入执行；更新操作使用版本号或乐观锁。状态检查能拦住一大类重复执行。

### 6. 记录副作用来源

每次操作记录来源 `event_id`、`message_id` 或 `request_id`。出了重复问题，能快速定位是哪条消息、哪次重试引起的。

## 踩坑点

- **先查后写竞态**：并发下两个请求同时查到不存在，都执行创建。应依赖数据库唯一索引捕获冲突，而不是只靠 `SELECT` 判断。
- **唯一键冲突直接报错**：冲突后应转成“读取已有结果并返回”，否则重试还是失败。
- **用时间戳或随机数当幂等键**：每次重试都会变，完全无法去重。
- **本地事务未提交**：执行成功但返回前崩溃，重试时可能仍看到 `pending` 状态。需要处理 stale pending，例如设置超时并允许重新执行。
- **第三方 API 不支持幂等键**：本地需要记录 outbound request 哈希或引用号，避免重复发送；也可对请求参数摘要做唯一约束。
- **事件重复消费**：消费者处理完成后未确认或未记录消息偏移，同一条消息被处理两次。应记录源事件 ID 并去重。
- **只做工具级幂等，不做流程级**：单个工具幂等，但 Agent 整体编排重复，仍可能产生一致的重复步骤和结果。建议在流程入口定义 `operation_id` 并贯穿所有子步骤。

## 可复用建议

- OpenClaw 插件 / MCP 工具统一提供 `idempotency_key` 参数，默认从任务上下文继承。
- 数据库表设计时，把幂等键放进唯一索引，而不是只靠应用层判断。
- 把副作用组织为“意图记录 + 执行结果”，重试时能返回相同输出。
- 对不支持幂等的外部服务，至少保留 outbox / 事件日志，做到可审计、可补偿。
- 测试覆盖连续调用两次、并发调用、成功失败边界、超时重试场景。把“重复调用不产生额外副作用”写进测试用例。

## 总结

幂等不是复杂技术，而是一种工程约束。它让自动化任务从“重复执行可能产生副作用”，变成“重复执行只是重复确认结果”。

对 OpenClaw、Agent、MCP 和插件场景来说，越早把 `operation_id` 和唯一约束做进工具层，后续重试、补跑、恢复就越省心。重复执行不可怕，可怕的是每次重复都产生新的副作用。
