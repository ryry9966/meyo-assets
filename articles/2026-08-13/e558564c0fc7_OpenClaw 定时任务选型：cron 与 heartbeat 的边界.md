## 背景

在 OpenClaw 里挂 Agent、MCP 工具或插件自动化时，定时触发是常见需求。比如定时拉取 GitHub 通知、扫描任务队列、刷新缓存、做健康检查。OpenClaw 提供了两种常见的定时机制：`cron` 和 `heartbeat`。它们都能“定时执行”，但调度模型完全不同。

不少同学会把两者混用，结果出现任务重复执行、心跳漂移、时区错乱或者 MCP 调用阻塞。本文从工程化角度拆一下：什么时候用 cron，什么时候用 heartbeat，以及踩坑点。

## 问题

cron 和 heartbeat 的核心区别不是“一个间隔长、一个间隔短”，而是时间语义不同。

- `cron`：按**日历时间**触发，比如每天 08:00、每周一 09:30。
- `heartbeat`：按**相对节奏**循环，比如进程启动后每 30 秒执行一次。

如果选错，典型症状包括：

- 用 heartbeat 做每天报表，设 `interval: 24h`，结果重启后从下午 3 点开始算周期，日报永远不在早上发。
- 用 cron 做每 10 秒健康检查，任务堆积、日志爆炸，MCP 工具调用超时后互相阻塞。
- 任务执行时间超过触发间隔，上一次没跑完，下一次又来了，导致重复消费或写冲突。

## 做法 / 步骤

### 1. 先判断触发语义

拿到一个定时需求，先问三个问题：

- **时间敏感吗？** 必须“每天 8 点整”触发，还是“每 30 秒左右”即可？
- **频率多高？** 低于分钟级的高频循环，基本告别 cron。
- **能跳过吗？** 如果系统忙，这次不执行是否可接受？

根据答案选择：

| 场景 | 推荐 |
|---|---|
| 每天/每周固定时间 | cron |
| 启动后持续检查、补偿、watchdog | heartbeat |
| 高频队列监听、缓存刷新 | heartbeat |
| 低频定时同步、备份、清理 | cron |

### 2. 配置思路

以 OpenClaw 风格的任务配置为例：

```yaml
# 日历时间：每天早上 8 点聚合昨天 GitHub 通知
- name: github_daily_digest
  trigger: cron
  cron: "0 8 * * *"
  action: mcp.github.list_notifications
  options:
    tz: "Asia/Shanghai"
    overlap: skip
```

```yaml
# 相对节奏：每 20 秒检查一次队列，但不直接处理重任务
- name: queue_watchdog
  trigger: heartbeat
  interval: 20s
  run_immediately: true
  action: mcp.queue.peek
  options:
    timeout: 10s
```

### 3. 让 heartbeat 只做“检查者”

高频率任务里，不要让 heartbeat 直接执行耗时业务。比如 MCP 工具调用可能需要 30 秒，而 heartbeat 间隔只有 20 秒，就会发生 tick 阻塞。正确做法是：heartbeat 只检查状态、发现待处理事件，然后交给队列或 worker 处理。

## 踩坑点

1. **时区不一致**  
   cron 在容器里经常是 UTC，配置了本地时间但日志显示 UTC，导致“为什么半夜跑了”。统一设置 `tz`，或者全部显式用 UTC。

2. **heartbeat 漂移**  
   heartbeat 不是“整点心跳”，它以进程启动时间作为起点。比如间隔 60 秒，启动在 10:00:30，后续就一直在 30 秒处触发。如果需要对齐整点，要设置 `start_at`，或者首次执行时等到下一个整分/整时。

3. **任务重叠**  
   cron 任务执行时间超过触发间隔，下一次又触发，可能同时写同一个文件、发重复消息。给任务加 `overlap: skip`，或用外部锁/单飞机制。

4. **静默失败**  
   heartbeat 任务内部异常如果被框架吞掉，可能几小时后才发现。每次执行必须输出错误日志、退出码或健康指标。最好给任务生成 `run_id`，方便串起日志。

5. **MCP 调用超时**  
   MCP 工具调用往往不是即时返回。要在任务配置里设置 `timeout`，并确保超时后不会继续堆积下一次 tick。

## 可复用建议

- **cron 适合**：日报、周报、定时同步、备份、过期清理、定时巡检。特征是频率低、墙钟时间敏感、幂等。
- **heartbeat 适合**：队列监听、缓存刷新、健康检查、补偿扫描、watchdog。特征是频率高、状态循环、允许跳过或积压。
- **混用时保持单向依赖**：heartbeat 只做发现/检查，不直接执行重业务；真正处理交给队列或 cron 驱动。
- **规则**：如果间隔大于 1 小时且必须“每天固定点”，不要用 heartbeat；如果间隔小于 1 分钟且要求持续运行，不要用 cron。
- **所有任务都加上**：`timeout`、并发控制、`run_id`、错误日志和基础指标。关键任务要做“上次未完成时再次触发”的演练。

## 总结

cron 管“什么时候做”，heartbeat 管“是否持续在做”。OpenClaw 里两者的选择取决于任务的时间语义、频率和可跳过性。选错了不会立刻挂，但会带来重复执行、漂移、阻塞和静默失败。工程上最好的方式，是让 cron 承担日历时间敏感的低频任务，让 heartbeat 承担高频率的状态循环，再用队列或 worker 隔离重任务。
