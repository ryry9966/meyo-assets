# OpenClaw 的 IDENTITY.md：给 AI 一个可进化的身份

## 背景

在 OpenClaw 的实际使用中，系统提示词往往被塞在 `config.yaml`、启动脚本或者某个 Python 文件里。一开始没什么问题，但随着项目迭代，我发现自己频繁遇到三类情况：

- 修改提示词没有记录，出问题只能靠记忆回滚；
- 多设备、多环境下的 AI 行为不一致；
- 想让 AI 记住一些长期偏好（比如“用户喜欢用 JSON 返回结果”），只能手动加到提示词里，越积越乱。

这些问题本质上都指向同一个根因：**AI 的身份定义没有被当成一个独立、可版本化、可进化的资产来管理**。于是我把身份相关内容全部抽离到一个文件里，命名为 `IDENTITY.md`，让 OpenClaw 在启动时加载它。半年下来，这个文件成了我所有自动化流程里最稳定的“地基”。

## 问题拆解

传统做法里，AI 的身份定义是“一次性配置”，一旦写入就很少再动。但真实协作中，AI 需要知道自己是谁、能做什么、不能做什么、用户偏好什么，这些信息会随着项目推进发生变化。如果这些变化散落在对话历史或临时变量里，下次冷启动就全丢了。所以需要一个**单一事实源（single source of truth）**，既能被 OpenClaw 稳定读取，又能像代码一样被 review、diff、回滚。

## 做法 / 步骤

### 1. 建立 IDENTITY.md 的结构

我用的结构大致如下，放在项目根目录或 `.openclaw/` 下：

```markdown
# IDENTITY.md

## 元信息
- 版本: 1.2.0
- 最后更新: 2025-03-14
- 维护者: @yourname

## 角色与目标
你是项目 `foo` 的自动化助手，负责数据处理、脚本执行、报告生成。目标是减少重复劳动，保证输出格式一致。

## 硬性约束
- 不修改 `data/raw/` 下的任何文件。
- 不向外部 API 发送用户隐私数据。
- 所有删除操作必须显式确认。

## 风格指南
- 默认使用中文回复。
- 技术输出使用 Markdown，优先给代码块。
- 遇到不确定的配置项，先查询 `docs/config.md`，不要臆测。

## 长期记忆
- 用户偏好输出 JSON（2025-02-11 确认）。
- 生产环境数据库连接超时设为 15s（2025-03-01 决策）。
- 脚本 `retrain.py` 不要自动运行，需手动触发。
```

### 2. 让 OpenClaw 加载文件

在 OpenClaw 的配置中，通过外部文件引入系统提示词。不同版本的配置方式略有差异，但核心思想是：**不要在代码里硬编码系统提示，而是引用文件路径**。例如（示意）：

```yaml
system_prompt_files:
  - .openclaw/IDENTITY.md
  - .openclaw/PROJECT_RULES.md
```

这样每次启动都会读取最新内容，不需要改代码。

### 3. 用 Git 管理身份变更

把 `IDENTITY.md` 纳入版本控制，每次修改都写清楚提交说明，比如 `fix: 移除已废弃的 FTP 上传约束` 或 `feat: 添加用户偏好：报告使用 PDF 格式`。这样任何一次行为异常都能回溯到具体变更。

### 4. 设计“进化”机制

进化不是让 AI 自己改文件，而是**从对话中提取候选事实，人工确认后更新**。我的流程是：

- 每周从 OpenClaw 的对话日志中，用简单脚本/正则提取用户明确表达的偏好或项目决策；
- 生成一个 diff，放在 `IDENTITY.md` 的 `## 长期记忆` 区块顶部；
- 人工 review 后合并，更新版本号。

如果不想写脚本，也可以手动追加，关键是保持“提取→审核→更新”的闭环。

### 5. 定期清理，防止膨胀

我会在每月初检查 `IDENTITY.md` 的长度。超过 200 行或某个 token 上限时，把过时的记忆移到 `ARCHIVE.md` 或直接删除。只保留当前有效的约束和偏好。

## 踩坑点

### 1. 文件过大导致上下文被挤占
早期我把所有历史决策都往里塞，结果 OpenClaw 每次启动都要消耗大量 token 处理身份文件，任务还没开始就已经“累了”。后来限制在 150 行以内，只保留高价值信息。必要时用分段加载：例如 `IDENTITY.md` 只保留核心身份，项目规则放到 `PROJECT_RULES.md`，按需加载。

### 2. 自动更新带来的错误固化
有一次我做了个自动化脚本，让 AI 根据对话自动往 `IDENTITY.md` 里写“用户喜欢 X”。结果用户随口说了一句“以后都用 CSV 吧”，就被记录成硬性偏好了，导致后续所有输出都变成 CSV，用户反而要额外转换。教训：**自动写入必须有人工审核闸门**，尤其涉及权限、数据格式、敏感操作。

### 3. 多环境身份混淆
开发环境里写的约束（比如“允许删除临时文件”）不能带到生产环境。我的做法是使用模板 + 环境变量：`IDENTITY.md.tpl` 中 `{{ENV}}` 替换为 `dev`、`prod` 等，再生成实际文件。或者把环境相关约束单独放在 `ENV_{{ENV}}.md` 里，按需加载。

### 4. 编码与路径问题
中文内容务必保存为 UTF-8 无 BOM，否则在某些平台上会出现乱码。文件路径不要包含中文或空格，避免加载失败。建议统一放在 `.openclaw/` 目录下，与代码仓库一起管理。

## 可复用建议

- **把 IDENTITY.md 当代码看**：用 PR、版本号、变更日志（CHANGELOG）来管理，而不是随便编辑。
- **保持结构固定**：用 Markdown 二级标题分区块，方便脚本解析和 diff。
- **单一事实源**：同一类信息只出现在一个地方，不要在不同文件里重复定义。
- **结合 MCP 的 memory 服务**：可以用 MCP 提供的短时记忆能力辅助，但长期身份仍以 `IDENTITY.md` 为准，避免记忆漂移。
- **多人协作时分离文件**：个人偏好放在 `.openclaw/personal/` 下，团队规范放在 `IDENTITY.md` 或 `TEAM_RULES.md`，通过配置合并加载。

## 总结

`IDENTITY.md` 解决的不是“让 AI 更像人”，而是**让 AI 的行为定义从一次性配置，变成可持续演进、可审计、可回滚的工程资产**。在 OpenClaw 这类 Agent / MCP / 插件生态里，身份管理的稳定性直接决定了自动化流程的可靠性。把身份写进文件、纳入版本控制、建立人工审核的进化闭环，比任何花哨的提示词技巧都更实用。对于长期项目，这可能是性价比最高的一步改造。
