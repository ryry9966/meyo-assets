# memory_recall 实测：语义搜索与全文搜索的召回差异与组合方案

## 背景
在 OpenClaw 的 Agent 记忆链路里，memory_recall 经常是决定回答质量的第一道关卡。典型调用路径是：用户问题进来后，先召回相关记忆片段，再拼进上下文让模型回答。召回方式大致有两条路线：全文搜索（FTS）和语义搜索（embedding + 向量检索）。很多同学会问“直接上向量库是不是更先进”，但实测下来这不是替换关系。

## 问题
全文搜索依赖词面匹配，对改写、同义表达、口语化查询不友好。语义搜索对长尾语义理解更好，但对精确 token、编号、协议错误码、代码符号不敏感。单用任何一边，都会出现“记得住但召不回”。

我在本地记忆库上做了小规模对比：约 600 条记忆片段，40 条查询，分别走 SQLite FTS5 和向量检索。结果大致如下：

- FTS5：recall@5 0.62，精确关键词命中稳定，但语义改写基本漏。
- 向量检索：recall@5 0.71，语义查询好，但错误码、路径、版本号这类精确信息漏得明显。
- 混合召回：recall@5 0.86，且排序更稳定。

## 做法/步骤
1. **统一记忆写入格式**：每条记忆至少包含 `memory_id, content, agent_id, created_at, tags`。写入前做基础清洗：去重、截断、保留错误码/路径/命令原文。
2. **全文索引**：SQLite FTS5，中文用 `tokenize='trigram'`，避免默认分词对中文不友好。索引 `content` 和 `tags`。
3. **向量索引**：用 bge-m3 或 text-embedding-3-small 生成 embedding，存 sqlite-vec 或 LanceDB。维度固定，归一化后用 cosine 距离。
4. **memory_recall 接口**：输入 query，先分别召回 top_k=10，再用 RRF 合并：
   ```python
   score = 1.0 / (60 + rank_fts) + 1.0 / (60 + rank_vec)
   ```
   60 是平滑常数，避免 rank 0 过重。
5. **后处理**：过滤 `score < threshold` 的结果，再按 agent_id/time 做简单衰减或截断，最后返回 top_k。

## 踩坑点
- **中文分词坑最多**：FTS5 默认 unicode61 会把连续中文当整词，召回很差。换 trigram 后索引体积变大，但短词命中明显变好。如果记忆里有大量英文/代码，建议对代码类字段单独用普通 tokenizer 并保留原文。
- **语义搜索不是“无脑 top_k”**：向量相似度没有绝对阈值，很多人直接取前 5 条，导致不相关记忆混入上下文，模型反而被带偏。建议在开发环境打印检索 score 分布，找一个适合自己库的 cutoff。
- **精确 token 被语义搜索吃掉**：例如查询 `MQTT_ERR_TLS` 时，向量检索可能返回“TLS 连接失败”但不返回原文，因为 embedding 对这类硬编码符号不敏感。这类 case 必须靠 FTS 兜底。
- **混合排序不要直接用相似度相加**：embedding score 和 BM25 score 量纲不同，直接相加容易让某一侧主导。RRF 简单有效，但 k 值要按召回数量调。
- **写入不规范会放大两边缺陷**：如果记忆内容是聊天原文、没有保留命令/错误码，那再好的召回也救不回来。建议写入侧做“关键 token 保留 + 语义摘要”双份存储。

## 可复用建议
- 小规模先做评测集，别急着换库。拿 30-50 条真实查询，标记期望记忆，跑 recall@5 / MRR。
- 默认架构：FTS 做 base，语义做 expand，RRF 合并。内存库不大时，SQLite FTS5 + sqlite-vec 足够。
- 结构化过滤放前面：agent_id、user_id、时间范围先过滤，再检索，能显著降噪。
- 记录未命中 query，定期回流补充同义词、别名，或调整 chunk 大小。
- 如果 embedding 模型更换，必须重跑评测集，因为召回分布会变。

## 总结
memory_recall 里“语义搜索 vs 全文搜索”不是二选一。工程上更实用的做法是：全文搜索保证精确命中，语义搜索覆盖改写和模糊意图，再用 RRF 做融合。先把写入规范和小评测集建起来，比直接上复杂向量库更能解决问题。
