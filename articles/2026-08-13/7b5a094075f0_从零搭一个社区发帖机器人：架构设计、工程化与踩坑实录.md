## 背景

在 OpenClaw 社区维护内容时，手动发帖重复劳动很多：格式化、配版块、改标题、传附件，一套流程下来并不比写内容少。于是我们尝试搭一个社区发帖机器人，目标不是全自动无人值守，而是把“生成—审核—执行”串起来，减少重复操作，同时保留人工兜底。

## 问题

一开始最容易低估的，不是内容生成，而是社区系统本身：登录态不稳定、发帖接口字段不透明、Markdown 渲染差异大、失败重试容易重复发帖、新号频率高会触发风控。所以架构上必须把生成和执行解耦，把发帖当成不可靠外部资源处理。

## 做法

### 1. 分层结构

机器人拆成五层：

- **生成层**：OpenClaw Agent 调 LLM，输出结构化字段：`title / body / tags / category / refs`。为了让内容不水，会注入近期社区高互动帖子标题和回复片段，要求包含一个具体观点或数据来源。
- **审核层**：本地 SQLite 草稿表，状态机为 `draft → pending → approved → published → rejected`。规则检查包括外链、社区敏感词、字数、Markdown 结构完整性。
- **执行层**：优先使用社区开放 API；没有公开 API 时，通过 MCP Browser 工具跑 Playwright，复用浏览器上下文完成发帖。
- **状态层**：SQLite 记录每次发帖的幂等 `client_id`、目标版块、草稿摘要、返回状态、最终 URL。
- **调度层**：OpenClaw 定时任务从选题池生成草稿，审核通过后进入发布队列，按随机间隔执行。

### 2. 发布执行细节

执行层最需要注意的是“像真实用户一样操作”。

- 登录态用 Playwright `storageState` 保存，复用浏览器上下文。
- 发帖前先 GET 表单页，解析 `csrf-token`、`form_id`、`x-requested-with` 等隐藏字段，再构造提交。
- 提交后不立即信任成功响应，而是回读用户主页或版块列表，用 `client_id` 确认是否真的发布成功。

### 3. 内容生成细节

不让 LLM 直接输出长文，而是输出 JSON。标题控制在社区标题字数范围内，正文避免过度使用代码块、表格、脚注。生成完成后由本地渲染器检查 Markdown 兼容性，不支持的语法自动降级为普通段落或列表。

## 踩坑点

**登录态失效盲区**  
`storageState` 文件存在不代表会话有效，可能内部已经 302 到登录页。每次任务前先请求 `/api/me` 或设置页做校验，失效则告警并转人工扫码，不要自动重登，否则容易触发安全验证。

**CSRF 和隐藏字段**  
很多社区发帖不是简单 POST `title + content`。前端可能带 `csrf-token`、`x-requested-with`、动态 `form_id` 甚至 cookies 里的 `xf_session`。只拿 API 文档套参数很容易 403。正确做法是先 GET 表单页，解析后再提交。

**重复发帖**  
超时重试是最常见的重复来源。第一次请求可能已经成功，但响应超时；盲目重试就会发两篇。必须让每次草稿携带幂等 `client_id`，发布前先查询是否已存在，存在则只回填 URL，不重新提交。

**Markdown 渲染不一致**  
同一篇内容在编辑器和最终帖子页面可能渲染不同：换行丢失、代码块变纯文本、链接不解析。发布后要回读帖子内容，做文本相似度比对。偏差超过阈值就进入待修状态，必要时撤回或人工修改。

**新号风控**  
新账号自动发帖频率高，很快会触发验证码、禁言甚至封号。建议新号先人工运营一到两周，机器人每日只发 1–2 篇，间隔随机化，正文做局部改写，避免同模板重复。

**内容同质化**  
LLM 容易生成“正确的废话”。只靠提示词不够，需要给生成层喂社区近期的真实讨论、高回复标题和观点。每篇草稿必须有至少一个具体主张或数据来源，否则审核层直接打回。

## 可复用建议

- **生成、审核、执行必须分离**，不要让 LLM 输出直接发出去。
- **把发布状态机化**，每个草稿都有生命周期，所有动作可追踪、可回滚。
- **先做草稿箱集成**，而不是直接发帖。草稿箱既能验证格式，也能绕开部分风控。
- **保留完整日志和快照**：标题、正文、提交参数、返回状态、最终 URL。出问题时能快速定位。
- **多账号隔离**：每个账号独立浏览器 context 和 `storageState` 路径，禁止共享 cookie。
- **如果社区没有公开 API，优先做半自动**：生成草稿后由人工在页面上确认发布，比全自动稳定得多。

## 总结

社区发帖机器人的真正难点不在生成内容，而在外部社区系统的状态管理、格式兼容和风控对抗。把生成与执行解耦、做强审核、用幂等重试和可观测日志兜底，才能稳定运行。OpenClaw 和 MCP 更适合做编排与工具接入，但不要追求无人值守。半自动 + 人工确认，往往是更务实的落地路径。
