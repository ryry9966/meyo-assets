## 背景

在 OpenClaw 的 Agent 工作流里，单个 Agent 既要拆解任务、又要执行具体操作，还要维护大量上下文，很容易出现三个问题：上下文窗口被历史信息占满、多任务指令互相干扰、串行执行导致总耗时线性增长。最近我在一个代码库巡检和文档生成的自动化项目里，尝试用主 Agent 调度多个 subagent 并行做事，效果明显，但也踩了一些工程化的坑。这篇文章把可复用的部分整理出来。

## 问题

核心问题不是“能不能并行”，而是“如何可靠地并行”。具体包括：subagent 的上下文如何隔离、任务结果如何结构化返回、并发数怎么控制、异常如何不阻塞整体流程。下面按实践步骤展开。

## 做法/步骤

**1. 主 Agent 只做三件事：拆解任务、下发 subagent、汇总结果。**  
不要在主 Agent 里做具体执行，否则上下文会快速膨胀，并发优势也会消失。

**2. 把每个 subagent 设计成单一职责的独立 agent 实例。**  
只接收必要输入（如文件路径、检查规则、目标描述），不继承主 Agent 的完整对话历史。这样每个 subagent 的上下文干净、可控，输出也稳定。

**3. 用 MCP 暴露统一的 task 工具，subagent 通过该工具获取输入、上报进度、返回结果。**  
在 OpenClaw 里，我习惯用 Python 写一个轻量任务队列，基于 `asyncio.Semaphore` 控制最大并发数为 3。任务队列负责创建 subagent 实例、传递参数、收集返回值，主 Agent 只等待最终汇总。

**4. 每个 subagent 返回结构化 JSON。**  
例如 `{"status":"ok","summary":"...","issues":[]}`。主 Agent 校验 schema 后再合并，避免解析异常。

**5. 举例：代码库巡检任务拆成三个 subagent 并行跑。**  
- subagent A：运行 lint 检查，返回问题列表  
- subagent B：检查依赖漏洞，返回漏洞摘要  
- subagent C：检查 README 与代码接口一致性，返回不一致项  

三者并行执行，总耗时从串行约 4 分钟降到 1 分半。

## 踩坑点

- **上下文污染**：一开始我把主 Agent 的全部对话历史塞给 subagent，导致 subagent 被无关信息干扰，输出不稳定。后来改为只传任务描述和必要文件片段。
- **并发过高触发限流**：本地同时跑 5 个 subagent 调用同一个 LLM API，直接触发 429。用信号量限制并发后解决。
- **输出格式漂移**：subagent 有时返回纯文本而非 JSON，导致主 Agent 解析失败。我在 prompt 里强制要求 JSON 且提供示例，并在解析失败时重试一次。
- **资源竞争**：两个 subagent 同时写同一个报告文件，导致内容交错。改为每个 subagent 写独立临时文件，最后由主 Agent 合并。
- **汇总过早**：主 Agent 在部分 subagent 未完成时就尝试汇总，结果缺失。用 `asyncio.gather` 等待全部完成，并设置超时。

## 可复用建议

- 任务队列加超时和重试，避免单个 subagent 卡死拖垮整体。
- subagent 的 prompt 模板尽量精简，只包含必要上下文，并固定输出格式。
- 用日志记录每次 subagent 的输入、输出、耗时，方便回溯。
- 如果 subagent 需要访问外部服务，通过 MCP 统一提供工具，避免各自实现。
- 并发数根据 API 限流和本地资源调整，建议从 2-3 开始测试。
- 主 Agent 的汇总逻辑要做防御性处理：对缺失、超时、格式错误的结果做兜底。

## 总结

subagent 并行编排不是银弹，但它确实能把串行任务变成可控的并发执行。在 OpenClaw 生态里，结合 MCP 和轻量任务队列，可以快速落地。关键是把主 Agent 的调度职责和 subagent 的执行职责分开，并做好上下文隔离、格式约束和异常处理。这套模式在代码巡检、多源信息汇总、文档生成等场景都能复用，适合已经熟悉 OpenClaw 基础工作流的用户进一步提效。
