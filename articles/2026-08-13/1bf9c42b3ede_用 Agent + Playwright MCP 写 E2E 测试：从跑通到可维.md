## 背景

在 OpenClaw 这类 Agent 框架里，浏览器操作越来越容易封装成 MCP server。比如把 Playwright 的 `navigate`、`click`、`snapshot`、`evaluate` 暴露给 Agent 后，Agent 可以真实驱动页面，而不只是根据文档猜接口。

但“能操作浏览器”和“能写出可维护的 E2E 测试”之间还有很大距离。我们做自动化测试时，真正耗时的不是第一次写出脚本，而是后续业务变更后选择器失效、断言过脆、登录态难处理、测试数据互相污染。本文记录一次用 Agent + Playwright MCP 协作写 E2E 测试的实践，重点在过程中踩到的坑和可复用做法。

## 问题

传统 E2E 测试有两个痛点：

1. 编写成本高：需要人工找到稳定选择器，处理等待、登录、fixture 数据。
2. 维护成本更高：页面改版后，测试大量失败，修复往往比重新写还慢。

如果直接让 Agent 用浏览器 MCP 自动生成测试，很容易得到一份“看起来能跑，但一碰就碎”的脚本。典型问题包括：选择器是 `div:nth-child(3) > span` 这种长路径；所有断言都依赖页面文案；没有处理异步请求完成状态；登录态每次跑都要重新走 UI。

因此目标不是“让 AI 全自动写测试”，而是把 Agent 当作一个能快速试错、生成初稿、并根据失败信息迭代的协作者。

## 做法/步骤

### 1. 先给 Agent 可观测上下文，而不是丢一个 URL

直接让 Agent 读 HTML 源码很容易被噪音淹没。Playwright MCP 里的 accessibility snapshot（`page.accessibility.snapshot` 或类似能力）比原始 DOM 更适合作为上下文。它只包含角色、名称、可交互元素，能大幅减少 Agent 误判。

我的第一步是让 Agent 先按路径走一遍页面：

- 打开测试环境 URL
- 点击登录按钮
- 用测试账号登录
- 进入目标功能页
- 创建一个测试资源
- 断言资源出现在列表里

每步操作后，让 Agent 记录 snapshot 片段，不急着生成代码。

### 2. 让 Agent 生成测试骨架，而不是完整脚本

路径跑通后，让 Agent 用 Playwright 测试框架生成一个 `spec` 文件骨架，要求：

- 使用 `data-testid` 作为首选选择器
- 每个操作前等待元素可见
- 登录态通过 `storageState` 或 API 注入，而不是 UI 登录
- 测试数据使用随机后缀，避免并行冲突

这个阶段只要求骨架能表达流程，不要求一次通过。

### 3. 回放失败后，把错误栈和页面快照喂回 Agent

第一次生成大概率失败。我的做法是把失败信息、错误栈、失败时的页面 snapshot 一起粘回给 Agent，要求它只修复选择器和等待逻辑，不允许扩展测试范围。这样迭代两到三轮，基本能得到一份可跑的测试。

### 4. 人工 review 后固化为模板

能跑通只是底线。我会人工检查三点：

- 是否依赖了易变文案
- 是否混入了 UI 登录
- 断言是否验证了关键业务状态，而不是只看“页面没报错”

确认后把结构固化成模板，后续类似页面让 Agent 按模板生成，效率会高很多。

## 踩坑点

### 1. Agent 偏好长 CSS 路径

这是最常见的问题。Agent 在没有明确约束时，会倾向于用 `div > div > div:nth-child(2) > button` 这种选择器。看起来精确，实际页面稍有结构调整就全挂。

解决办法是：在 prompt 里硬性要求优先 `data-testid`，没有 testid 时使用角色 + 可访问名称，禁止使用超过三层的结构性选择器。

### 2. iframe 和 shadow DOM 穿透差

很多后台系统嵌入了 iframe 或使用了 shadow DOM。Agent 在 snapshot 里看不到 iframe 内部结构，生成的代码会直接失败。需要显式告诉它先切换 frame，或者通过 `page.frames()` 找到目标 frame 再操作。

### 3. 登录态和验证码不能硬刚

如果让 Agent 每次走 UI 登录，测试会又慢又脆。遇到验证码基本无解。正确做法是提前准备测试账号的 `storageState`，或者让 Agent 调用后端 API 获取 token 后注入浏览器上下文。这一步最好由人配置好，不要期望 Agent 自己处理。

### 4. 上下文窗口被长页面快照撑爆

复杂页面 snapshot 可能很大，Agent 操作几步后上下文就溢出，开始丢失早期信息，进而生成错误代码。需要限制每次快照只保留关键区域，或者让 Agent 在每一步只读取当前视口内的可交互元素。

### 5. 权限过大导致误操作

把浏览器 MCP 全量开放给 Agent 有风险。测试环境里误点删除按钮、误提交表单都发生过。建议给 MCP server 配置操作白名单，或者使用只读模式先行探索，确认路径后再开放写操作。

## 可复用建议

- **统一 `data-testid` 规范**：没有稳定选择器，Agent 写不出可维护测试。这是前置工程投入。
- **让 Agent 只负责“初稿 + 修复”，人负责“验收 + 模板化”**。
- **使用测试专用账号和隔离环境**，避免污染真实数据。
- **回放必须在 CLI 或 CI 里验证**，不要只让 Agent 自己说“通过了”。
- **把登录态、fixture、清理逻辑做成 fixture 或 helper**，让 Agent 复用，而不是每次生成新逻辑。
- **控制单次 Agent 任务范围**：一次只生成一个用户路径的测试，避免多路径混杂导致上下文爆炸。

## 总结

Agent + Playwright MCP 确实能明显降低 E2E 测试的编写成本，但前提是工程约束足够清晰。稳定的选择器规范、隔离的测试环境、可注入的登录态、受限的浏览器权限，这些基础建设比 Agent 本身更重要。

比较适合的定位是：让 Agent 在已经规范化的项目里快速生成测试初稿，并根据失败信息迭代修复；人则负责设计测试路径、review 断言质量、维护测试基建。这个协作模式下，E2E 测试的维护成本会从“每改一次页面修一堆选择器”，变成“Agent 先修，人再确认”，更接近可持续的自动化实践。
