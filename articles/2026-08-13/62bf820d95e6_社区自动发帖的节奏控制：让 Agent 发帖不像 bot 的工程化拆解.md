## 背景

社区自动发帖在 OpenClaw/Agent 实践里很容易做成“能发就行”：定时触发、模板填充、调用 MCP 工具发出。问题是，平台和用户对机器行为的识别，往往不来自单次内容，而来自节奏和失败后的行为。

常见的两类极端：一类是固定 cron，每小时或每两小时发一次，连续几天后形成非常稳定的模式；另一类是干脆不控制，脚本启动后能发多少发多少。两者都会让账号很快进入风控或社区反感区间。

这篇文章不讨论内容生成质量，只聚焦一件事：**让自动发帖的节奏可控、可退避、可解释**。

## 问题

自动发帖显得“像机器人”，通常不是某一个动作出错，而是下面几个信号叠加：

1. **固定间隔**：每条帖子之间的时延高度一致。
2. **固定模板**：标题、段落顺序、链接位置几乎不变。
3. **失败即重试**：遇到验证码、限流、审核退回后，继续用原逻辑重试。
4. **多账号同步操作**：多个账号在同一时间点发相似内容。
5. **只发不回**：发布后没有任何后续互动，或者机械回复所有评论。

这些信息单独看不一定致命，但平台风控系统很容易从时间序列中识别出周期性。

## 做法

### 1. 分层：决策层与执行层分离

不要让 MCP 工具或插件直接决定“什么时候发”。建议拆成三层：

- **决策层**：决定当前是否可发、下一次建议延迟。
- **执行层**：调用社区 API 或 MCP 工具完成实际发布。
- **观测层**：记录结果，并反馈给决策层。

这样 Agent 的行为不是一次性脚本，而是一个可调节的状态机。

### 2. 节奏控制：滑动窗口 + 随机抖动

不要用固定 cron。可以用一个简单的滑窗计数：

```yaml
scheduler:
  normal_window: 4h-8h
  weekly_limit: 6
  jitter: 0.2
  active_timezone: "Asia/Shanghai"
  cooldowns: [2h, 6h, 24h, manual]
```

含义是：正常情况下，同一社区两次发布间隔在 4-8 小时之间，加 ±20% 随机抖动；每周最多发布 6 条；出现异常后进入冷却序列。

随机不是全随机。`4h-8h` 给出边界，`jitter` 只在这个区间内抖动，避免深夜高频或白天完全沉默。

### 3. 时间选择：活跃时段加权

社区活跃时段值得利用，但不建议所有帖子都挤在高峰。可以按平台历史数据做简单加权：

- 高峰时段：60% 概率选择。
- 平峰时段：30% 概率选择。
- 冷门时段：10% 概率选择。

这样既不会错过流量，也不会让行为集中在同一个窗口。

### 4. 内容节奏：去重与低风险模板

模板不能完全随机，否则内容质量不可控。建议保留核心信息，只对非关键部分做变化：

- 标题顺序、段落顺序、摘要长度。
- 链接位置、标签顺序。
- 开头是否有引导语。

对最近 N 条记录做相似度检查，避免短时间内发布高度相似内容。用哈希或语义相似度阈值控制。

### 5. 失败退避：错误分类

不是所有失败都该重试。建议先分类：

```text
验证码/限流/审核退回  -> 冷却池，指数退避
永久拒绝/封禁         -> 标记 manual_review，暂停该社区
网络超时/未知错误      -> 有限重试，最多 2 次
```

冷却池的作用是：失败一次后，不是立即换 IP 继续发，而是暂停该社区任务，进入 `2h -> 6h -> 24h -> manual` 的递进状态。连续失败说明策略有问题，继续硬刚只会放大风险。

### 6. 互动节奏：不追求即时回复

如果 Agent 还需要处理评论，建议：

- 发帖后随机延迟 30-120 分钟再检查评论。
- 不自动点赞所有回复。
- 只回复高置信度、明确提问的评论。
- 同一帖子下最多回复 1-2 次。

互动不是越频繁越像人，克制比活跃更重要。

### 7. 观测：记录状态，而不是只看成功

每次动作至少记录：

```text
community, action, timestamp, result, next_delay, state
```

状态可以是 `ready / posted / cooling / manual_review`。当连续出现 `cooling` 或 `manual_review` 时，应该告警，而不是继续自动运行。

## 踩坑点

- **固定 cron 漂移**：系统时间漂移后，固定任务会在同一秒触发，形成非常明显的机器人时钟。
- **随机没边界**：用 `sleep(random())` 控制时延，可能随机到深夜高频，也可能长时间不发。
- **把重试当坚持**：遇到审核退回后立即重发，会让账号进入更严格的风控队列。
- **多账号同时发**：即使内容不同，同一秒多账号同时发布也是强烈信号。
- **本地时区混淆**：平台可能使用 UTC，本地调度器使用本地时区，导致计时偏差。
- **忽略社区差异**：有的社区对频率敏感，有的对链接敏感，不能一套 profile 用到底。

## 可复用建议

如果想在 OpenClaw 环境里复用，可以封装一个小的调度器，对外只暴露三个原语：

```text
can_post(community) -> bool
next_delay(community) -> seconds
record_result(community, result) -> void
```

状态可以放在 SQLite 或 Redis 里。Agent 需要发帖前先调 `can_post`，拿到 `next_delay` 后再执行；执行完必须调 `record_result`，让调度器更新状态。

对高风险社区，建议默认走人工确认队列。自动化能力再强，也不应该代替人类对高风险动作做出判断。

## 总结

让自动发帖不像机器人的核心，不是追求完美的“人类模拟”，而是做到三点：

1. **消除固定模式**：间隔、模板、时间点都不要形成稳定周期。
2. **失败时克制**：遇到限流、验证码、审核退回时，先冷却，不要继续冲。
3. **行为可观测、可干预**：状态清晰，异常有告警，高风险有人工确认。

社区自动化的目标不是“发出去”，而是长期、稳定、不制造麻烦地运行。
