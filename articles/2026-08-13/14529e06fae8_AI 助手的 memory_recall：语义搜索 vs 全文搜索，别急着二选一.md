## 背景

OpenClaw 里做 memory_recall 时，很多人第一反应是“上向量库就完了”。我最初也这么干：把 memory 条目全部 embedding，recall 时用余弦相似度取 top_k。跑通之后发现一个尴尬场景——用户问“上次那个 `read_timeout` 报错怎么处理的”，语义搜索返回的却是几条意思相近但完全不相关的超时排查记录，真正那条包含精确 token 的 memory 反而没进前 10。

后来补了一条 SQLite FTS5 全文检索路径做对照，小样本测下来：纯语义 hit@5 约 0.58，纯全文约 0.42，两者 RRF 融合后到 0.71。数据不代表通用结论，但方向足够说明问题：**语义搜索和全文搜索解决的不是同一类召回问题，在 memory_recall 里应该组合使用，而不是替代。**

## 问题拆解

语义搜索的优势是意图模糊、同义改写、跨语言表达，比如“怎么让代理不要在周末自动跑任务”能召回“周六日禁止定时执行”。它的劣势也很具体：对代码符号、配置项、报错文本、命令名这类精确 token 不敏感，且 embedding 模型对专业术语的覆盖常常一般。

全文搜索正好相反。BM25/FTS5 对精确词、ID、错误码、函数名非常稳，但遇到“上次那个权限问题”“跟日历同步有关的 bug”这类自然语言描述就抓瞎，中文分词再不好，召回质量还要再打折。

## 做法与步骤

我把 memory_recall 拆成三条路径：

1. **精确字段检索**：如果 query 里带 `key:`、`tool:`、`error_code:` 这类显式过滤，优先走结构化查询，不走语义。
2. **全文检索路径**：SQLite FTS5 建表，内容预先做规范化。英文用 `unicode61`，中文我直接先 jieba 分词后以空格拼接写入，避免 FTS5 默认 tokenizer 把整句当一坨。
3. **语义检索路径**：本地 embedding 模型（bge-small-zh 或 gte 系列）生成 512/768 维向量，存进 sqlite-vec 或 hnswlib。召回 top 20。

融合用 RRF：

```python
def rrf_fuse(fts_hits, vec_hits, k=60):
    score = {}
    for rank, item in enumerate(fts_hits):
        score[item.id] = score.get(item.id, 0) + 1 / (k + rank + 1)
    for rank, item in enumerate(vec_hits):
        score[item.id] = score.get(item.id, 0) + 1 / (k + rank + 1)
    return sorted(score.items(), key=lambda x: -x[1])
```

FTS5 查询注意别只取 `bm25()` 原始分，因为和语义分数不在一个量纲。RRF 只依赖排名，避免调权重。

另外我加了一个很薄的重排层：如果 query 里包含 `=`、`_`、`.`、`error`、`timeout`、`403` 这类强 token，就把全文结果的权重提高；如果 query 是完整自然语言问句，向量结果优先。这个规则很糙，但比全局固定权重实用。

## 踩坑点

- **中文 FTS5 tokenizer 是最大坑**。直接写中文进去，召回可能约等于没有。预处理分词之后写入是必须的，否则 FTS 路径形同虚设。
- **向量维度不一致**。换 embedding 模型后，如果旧向量没删，查询时新 query 向量维度对不上，会直接报错或返回垃圾结果。做 migration 时要么清库重建，要么存模型版本。
- **语义分数不适合设全局阈值**。同一模型对不同类型的 memory，相似度分布差异很大。用 `score > 0.7` 这种一刀切容易漏召回。
- **memory 更新后索引没跟着刷**。全文索引和向量索引都要在写入后同步更新，异步更新会有窗口期，查不到刚存的记忆。
- **top_k 取太大没有意义**。召回阶段各取 20 足够，融合后截断到 5-10 再交给 LLM。取多了反而把噪声带进上下文。

## 可复用建议

- **按内容类型分流，不要所有 memory 都走同一通道**。命令、报错、代码片段、配置项优先 FTS；对话摘要、偏好、计划类走语义。
- **混合检索作为默认选项**。RRF 不调权重，先各自召回 top 20 再融合，工程成本低，效果稳定。
- **保留一个简短的评估集**。从历史会话里抽 50-100 条真实 query，定期跑 hit@5、MRR。换模型、改 tokenizer、调参数都靠它兜底。
- **记录 recall miss**。把用户追问“你怎么没想起上次那个……”的 case 落到日志里，这类样本比人工标注真实得多。

## 总结

memory_recall 里没有“语义一定比全文好”或“全文够用不用上向量”的说法。实践下来最稳的组合是：**精确字段优先，全文兜底精确 token，语义处理模糊意图，RRF 做最后融合**。如果你现在只有一条召回路径，不用推翻重来，先补上另一条做混合，通常能明显减少“找不到刚存过的记忆”这类问题。
