## 背景

在 OpenClaw 的 Agent、MCP 和插件实践中，外部 API 已经成为链路的默认组成部分。模型推理、搜索、数据库、通知、支付……任何一环的第三方服务抖动，都可能让一个自动化任务卡死。

更常见的是：API 返回 500，Agent 开始反复重试；重试几次后 token 烧掉不少，任务状态也丢了；或者降级时返回空数据，LLM 直接编一个结果。所以外部 API 故障处理不能靠 try/except 兜底，需要独立设计。

## 问题

外部 API 挂了，对 Agent 系统通常表现为几类：

- 超时挂起，整个流程不返回；
- 无限重试，造成配额和 token 浪费；
- 非幂等操作被重复执行，如重复发信、重复建单；
- 降级逻辑返回“空答案”，被 LLM 当作真实结果；
- 恢复后无法续跑，只能从头再来。

## 做法/步骤

### 1. 先做错误分类

把 API 错误分为三类：可重试、不可重试、语义失败。可重试包括 429、5xx、网络超时、连接重置；不可重试包括 400、401、403、参数校验失败；语义失败是请求成功但返回体为空、格式异常或业务码错误。分类可以在工具封装层完成，不要交给 LLM 判断。

### 2. 限制重试与退避

对可重试错误，采用指数退避加随机抖动，并设置最大次数和总时长。示例：最多 3 次，间隔 1s/2s/4s ± jitter。总预算建议不超过 10s。重试预算用完就快速失败，进入降级。

### 3. 加熔断与隔离

连续失败达到阈值后打开熔断器，后续请求直接失败，不再打下游。熔断器分 closed/open/half-open 三态。open 一段时间后进入 half-open，只放少量探测请求，成功则恢复，失败继续 open。阈值可以按“连续失败 5 次”或“30 秒内错误率 > 50%”。

### 4. 准备降级链

每个关键工具都应有 fallback chain。例如：实时天气 API 失败 -> 读取 30 分钟内的缓存 -> 使用备用数据源 -> 返回“当前不可用”。要注意降级结果必须显式标注来源，避免 LLM 把旧数据当成实时数据。

### 5. 持久化任务状态

在调用外部 API 前，保存任务检查点：当前步骤、输入参数、已完成的副作用、外部请求 ID。这样任务中断后可以从检查点恢复，而不是重跑。对可能产生副作用的操作，增加幂等键。

### 6. 可观测与告警

记录每次外部调用的 API 名称、状态码、耗时、重试次数、是否命中缓存、熔断状态。对错误率和 p95 延迟设置告警。没有日志，排障只能靠猜。

## 踩坑点

- **不要重试 4xx**：参数错误重试多少次也不会成功，还可能触发风控。
- **重试预算不要交给 LLM**：如果工具描述里写“失败可重试”，Agent 可能反复调用同一个工具。应在工具层强制限制。
- **非幂等操作必须有幂等键**：尤其是创建类 API，否则一次网络超时后重试，可能产生两条记录。
- **降级返回空值要显式表达**：可以返回“NO_DATA_AVAILABLE”或“当前数据不可用”，不要让空字符串进入上下文。
- **超时时间别设太长**：宁可快速失败，也不要让整个 Agent 流程长时间挂起。
- **熔断恢复要渐进**：half-open 只放少量请求，避免一恢复就被打崩。

## 可复用建议

把外部 API 调用统一封装成带策略的客户端：超时、重试、熔断、降级、日志、幂等键。每个工具再根据自己的语义定义 fallback，而不是套用全局策略。可以在 MCP server 或插件层实现这些逻辑，让 Agent 只看到“稳定的工具”。

定期做故障演练：手动停掉一个 API，观察 Agent 是否能快速失败、降级、恢复。这比上线后被动挨打有效得多。

## 总结

外部 API 挂了不是异常，是常态。Agent 的错误恢复能力，取决于你为它设计了多强的“快速失败、有限重试、显式降级、保留现场、可观测”机制。把这些下沉到工具层，Agent 才不会被一个第三方故障放大成更大的事故。
