## 背景

在 OpenClaw / Agent / MCP 的自动化链路里，外部 API 经常是执行核心：天气、搜索、数据库、支付、对象存储、第三方 SaaS。请求失败、超时、限流、返回结构变更，这些都无法避免。

关键问题是：Agent 如果直接暴露原始异常，轻则任务中断，重则开始“幻觉”——编造 API 结果、重复调用、忽略错误继续执行。错误恢复的目标不是消灭故障，而是让失败可控、可解释、可降级。

## 问题

常见的工程缺口：

- 没有错误分类，所有异常同样处理；
- 盲目重试导致重复副作用或任务堆积；
- 降级数据被当成实时数据使用；
- MCP 工具返回的错误格式混乱，上层 Agent 无法判断严重程度；
- 缺少熔断，一个 API 挂掉拖慢整个自动化流程。

## 做法 / 步骤

### 1. 先定义错误模型

在调用外部 API 的边界处封装一个结构，不要直接抛裸异常。建议至少包含：

- `retryable`：是否可重试；
- `fallback`：是否有降级值；
- `severity`：fatal / degraded / warning；
- `message`：给 Agent 看的一句话。

例如：

```json
{
  "status": "degraded",
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": false,
  "fallback_used": true,
  "message": "外部天气服务超时，返回最近一次缓存结果"
}
```

这个结构比“请求失败”更利于 Agent 决策。

### 2. 重试只留给安全场景

对幂等 GET 可以重试；POST、创建类请求要谨慎。重试策略建议：

- 超时 3–8 秒，不要无限等待；
- 指数退避 + 随机抖动，如 200ms、400ms、800ms，最多 3 次；
- 对 429 / 503 可重试，对 400 / 401 / 403 不重试；
- 每次重试都带上同一 `trace_id`，方便排查。

### 3. 给 Agent 明确的降级协议

在 MCP 工具描述和系统提示中写明：工具返回 `degraded` 时，可以继续，但必须告知用户数据可能不是实时；返回 `fatal` 时，停止当前步骤并询问用户，不要自行编造结果。

降级来源可以是：

- 最近一次成功响应缓存；
- 本地规则或静态兜底；
- 另一个可替换 API；
- 直接返回“该能力暂不可用”。

### 4. 熔断与隔离

连续失败 N 次后打开熔断，短时间内不再请求故障 API，直接走降级。半开状态允许少量探测请求，成功则关闭熔断。不同 API 要独立熔断，避免一个外部服务影响全局。

### 5. 可观测性

记录错误码、耗时、重试次数、是否降级、降级原因。输出结构化日志，并给 Agent 运行记录加标记。没有这些数据，线上问题只能靠猜测。

## 踩坑点

- 对非幂等接口重试，导致重复下单、重复发消息；
- 无限重试让自动化任务超时排队，费用和资源占用上升；
- 缓存降级数据没有过期时间，Agent 当成实时数据继续分析；
- 把原始异常堆栈直接喂给 Agent，模型容易编造原因或假装成功；
- 所有外部 API 使用同一套超时和重试配置，慢接口拖垮快接口；
- MCP 工具的错误格式没有统一，Agent 在不同工具间行为不一致。

## 可复用建议

- 封装一个统一的 `external_call` 或 `safe_api_call`，集中处理超时、重试、熔断、降级、日志；
- 在 Agent 工具说明里加入“错误返回协议”示例，让模型学会区分 `degraded` 与 `fatal`；
- 为关键 API 准备离线兜底数据，并标注数据时间；
- 给降级结果加前缀或字段，如 `fallback_used: true`，避免静默降级；
- 定期做故障演练：手动把外部 API mock 成超时、5xx、返回异常结构，观察 Agent 行为是否符合预期。

## 总结

外部 API 挂了不是 Agent 的智商问题，而是工程边界问题。与其让模型在异常里“自由发挥”，不如把重试、熔断、降级、结构化错误做在工具层。Agent 只需要做它擅长的事：根据明确的状态码和降级信息，决定继续、降级还是停止。这样系统在外部依赖不可靠时，仍能保持可预测和可解释。
