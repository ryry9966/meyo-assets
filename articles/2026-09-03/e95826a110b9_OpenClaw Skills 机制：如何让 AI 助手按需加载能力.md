# OpenClaw Skills 机制：如何让 AI 助手按需加载能力

## 背景：上下文是稀缺资源

Agent 圈这一年聊得最多的不是模型能力，而是上下文管理。一个接了 MCP、挂了十几个工具的助手，系统提示词动辄上万 token：工具描述、操作规程、团队规范全堆在开头。结果是模型每次推理都背着全部行李上路——贵、慢，而且指令越多，选错工具的概率越高。

OpenClaw 的 Skills 机制就是针对这个问题：把能力拆成独立的技能包，启动时只注册索引，用到时才加载正文。它和 MCP 不冲突——MCP 解决"有什么工具"，Skills 解决"什么时候、按什么流程用"。

## 问题：全量注入的三个代价

1. **token 成本**：没被用到的说明书也在计费；
2. **干扰**：无关指令稀释关键指令，表现为该调 A 工具时调了 B；
3. **维护**：一个巨型 system prompt，改一行要回归测试全部能力。

## 做法：三级渐进式加载

Skills 的核心是 progressive disclosure，分三层：

- **第一层，元数据常驻**：每个技能只有 name + description 进入上下文，几十 token；
- **第二层，正文按需**：模型判断任务匹配某个 description 时，才读取该技能的 SKILL.md 全文；
- **第三层，引用再展开**：正文可以指向更深的参考文件或可执行脚本，真正需要时才读、才执行。

写一个技能只需要一个目录：

```
skills/
  csv-report/
    SKILL.md        # frontmatter(name, description) + 正文
    make_report.py  # 可选：脚本
```

SKILL.md 的关键在 frontmatter 的 description，它是触发器。写法建议是"做什么 + 何时用"：

```yaml
---
name: csv-report
description: 生成周度数据报表。当用户要求导出、汇总 CSV 或产出报表时使用。
---
```

正文写操作步骤，能脚本化的尽量指向脚本，而不是用自然语言复述流程。

## 踩坑点

- **description 太模糊**："辅助处理数据"这类表述，要么永远不触发，要么什么都触发。触发条件要具体到动词和场景。
- **技能数量失控**：每个技能的元数据都常驻，五十个技能的索引本身就是新的上下文负担。按真实使用频率裁剪。
- **正文塞满长文档**：把三千字参考资料全写进 SKILL.md，触发即爆。长资料拆成引用文件，放第三层。
- **脚本副作用**：技能里的脚本会真的被执行，涉及删除、外发的操作要加确认逻辑或 dry-run 参数。
- **版本漂移**：技能内引用的路径、接口变了没人发现。技能要纳入代码评审和 CI，当代码对待。

## 可复用建议

- 一个技能只做一件事，命名用动词短语；
- description 用"当……时使用"句式，覆盖用户可能说的关键词；
- 可重复的操作优先写成脚本，确定性远高于 prose 描述；
- 用真实历史任务做触发测试：抽十条旧 query 回放，看命中是否正确；
- 定期清理：一个季度没触发的技能，删。

## 总结

Skills 机制的本质，是把 prompt 工程从"写一篇大文章"变成"维护一个图书馆"：目录常驻，书按需借。我们团队改造后，常驻上下文体积降了六成左右，工具误选率明显下降，新增能力也不再需要改主提示词。它不神秘，就是上下文管理里最朴素的懒加载思想——但需要持续运营技能库的质量，否则图书馆很快会变成杂物间。
