## 背景

跑 Agent 久了都会遇到同一个问题：能力越接越多，上下文越来越肥。接了七八个 MCP server，再叠一堆常驻指令，一个普通请求还没开始干活，系统提示词就先吃掉大几千 token。更麻烦的是，工具列表一长，模型选错工具、幻觉出不存在的参数的概率明显上升。

OpenClaw 的 Skills 机制就是冲着这个来的：**能力默认不进上下文，只在需要时加载**。思路类似懒加载——常驻的只有每个 skill 的元信息（名称 + 一句话描述），命中之后才把完整指令注入本轮对话。

## 问题

在用 Skills 之前，我维持能力的方式基本是往系统提示词里堆规则：日志排查一套、周报生成一套、部署检查一套。实际痛点有三个：

1. 全量常驻，token 成本线性上涨，且稀释了真正重要的指令；
2. 规则之间互相干扰，模型偶尔在错误场景套用错误流程；
3. 改一条规则要动整个提示词，没法独立维护、独立分享。

## 做法

一个 skill 就是一个文件夹，核心是 `SKILL.md`，分两层：

```markdown
---
name: log-triage
description: 当用户要求排查服务报错、统计错误分布或定位异常请求时使用。
---

# 日志排查流程

1. 运行 scripts/collect_errors.sh 拉取最近一小时错误日志
2. 按状态码分组统计，输出 Top 3 错误及时间窗
3. 处理建议参考 references/playbook.md
```

落地步骤：

1. **建目录**：在 workspace 的 `skills/log-triage/` 下放 `SKILL.md`，脚本和参考资料放在同目录的 `scripts/`、`references/` 里。
2. **写 description**：这一行是路由依据，要写成触发条件而不是功能简介——"当用户要求……时使用"，并把用户实际会说的高频词放进去。
3. **写正文**：只写命中之后才需要的操作步骤，长文档、脚本全部外置，用相对路径引用。
4. **验证加载**：重启会话后用 skill 列表命令确认已被索引，然后拿一句典型用户请求实测是否触发、注入的正文是否完整。

关键在于三层渐进暴露：元信息常驻 → 正文按需注入 → 脚本和引用文档由正文引导二次加载。每一层都只让模型看到"当下够用"的信息。

## 踩坑点

- **description 写成功能清单**。早期我写"用于日志分析和统计"，结果闲聊提到"日志"两个字也会触发。改成明确的"当用户要求排查/统计报错时使用"后误触明显减少。
- **正文贪长**。有个 skill 塞了 3000 字的操作手册，触发一次等于把常驻的负担换了个时机背回来。手册拆到 `references/`，正文只留决策骨架。
- **命名撞车**。skill 名和内置命令、MCP 工具名太接近时，模型的路由会犹豫，实测换一个不冲突的前缀就稳定了。
- **敏感信息直接写进正文**。SKILL.md 触发时会被读进上下文，密钥、内网地址不要放，放环境变量或让脚本自己读配置。
- **多个 skill 描述重叠**。两个 skill 都声称处理"部署"，模型有时会同时加载。把边界写进 description，比如一个只管"构建产物"，另一个只管"发布上线"。

## 可复用建议

- description 当触发器写，不是当文档写；
- 一个 skill 只干一类事，宁可拆小也不要做大而全的"万能流程"；
- 模板、checklist、长手册外置成引用文件，正文控制在几百字；
- skills 目录用 git 管，改动可回溯，团队可以直接复用彼此沉淀的流程；
- 定期看会话日志确认触发情况，触发不准就回头改 description，这是迭代成本最低的一层。

## 总结

Skills 的价值不在"多了一种插件格式"，而在于把上下文当成显式预算来管理：常驻的只留索引，能力按需进场。对我自己的实例来说，把四套常驻流程改造成 skill 后，日常请求的系统开销降了约三分之一，误用工具的情况也基本消失。建议从你最重复、流程最固定的那件事开始写第一个 skill，跑通触发链路后再逐步迁移。
