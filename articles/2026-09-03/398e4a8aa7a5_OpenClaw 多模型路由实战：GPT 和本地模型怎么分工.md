## 背景

OpenClaw 跑起来的 agent 任务其实不是同质的。一条典型自动化流程里有规划、工具调用、结果摘要、向量检索，各环节对模型能力的要求差别很大。我之前把所有请求都打到云端旗舰模型，月底 token 账单很难看，复盘后发现六成以上的调用——固定格式输出、简单分类、短文本摘要——本地 7B/14B 模型完全接得住。

## 问题

多模型接进来之后，真正的难题变成路由：什么请求走云端，什么走本地？规则太粗，本地模型接不住复杂推理，任务失败率上升；规则太细，维护一堆 if-else，比模型本身还难改。

## 做法

我的路由分四步搭：

1. **注册模型端点**。在 provider 配置里同时登记云端（GPT 系列）和本地服务（vLLM/Ollama），给每个模型打标签：`reasoning` / `tool-call` / `embedding` / `cheap`。
2. **给 skill 声明能力档位**。在 skill 定义里加 `model_tier` 字段：规划和多步推理标 `high`，格式化调用和摘要标 `low`，MCP 检索的 embedding 单独固定一个本地模型。
3. **按任务类型路由，不按内容路由**。默认走本地；命中升级条件才转云端——上下文超过本地窗口的 80%、工具调用连续两次解析失败、用户显式要求高质量输出。
4. **配置 fallback 链**。本地服务超时（我设 8 秒）或报错，自动降级到云端，同时往日志通道发一条告警。

## 踩坑点

- **本地模型的 function calling 格式不稳定**。同一份 JSON Schema，GPT 稳定输出，本地模型偶尔多逗号或字段名变形。解法是在工具层加 schema 校验 + 本地重试一次，再失败就升级云端。
- **MCP 工具的长输出撑爆上下文**。本地模型窗口小，一次网页抓取的原始输出直接溢出。路由前加一步预处理：长输出先在本地摘要，再判断是否升级。
- **embedding 模型不能混用**。前期一半向量云端生成、一半本地生成，检索质量肉眼可见地掉。embedding 必须全链路固定同一个模型，换模型就要重建索引。
- **Ollama 换模型有冷加载**。在两个本地模型间切换时，几秒的加载把“省钱”变成“卡顿”。同一台机器尽量收敛到一个本地模型，或改用 vLLM 常驻。

## 可复用建议

- 路由粒度做到 skill 级就够，别做 prompt 级分类，省下的钱抵不上误判成本。
- 上线前跑一个 50~100 条历史任务的回归集，对比路由前后的成功率、p95 延迟、单任务成本，三个数字贴进项目 README。
- 关键路径（涉及写操作、对外发消息的任务）永远保留云端兜底。
- 路由决策打日志：哪个 skill、走了哪个模型、为什么升级。一周后回看，你会发现最初的规则有一半是拍脑袋。

## 总结

多模型路由不是“能省则省”，而是把能力档位和任务类型对齐。OpenClaw 里最划算的分工是：本地模型吃掉高频、格式化、隐私敏感的调用，云端模型只处理长推理和兜底。先用最粗的规则跑起来，再用日志数据修正，比一开始就设计精巧的路由策略靠谱得多。
