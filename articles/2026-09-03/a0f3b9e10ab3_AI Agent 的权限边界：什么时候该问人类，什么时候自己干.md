## 背景

给 Agent 接上工具之后，最头疼的不是它不会干，而是不知道该让它干到哪一步。OpenClaw 里挂上 MCP 工具、插件、shell 权限之后，Agent 能读文件、调 API、发消息、改配置——能力越强，“这一步要不要人点头”的问题就越具体。

## 问题

实践中常见两种翻车方式，方向正好相反：

1. **事事都问。** 每次文件写入、每条命令都要确认，用户很快进入“无脑点同意”状态。这时确认机制形同虚设，危险操作混在十条普通确认里一起被放行。
2. **什么都不问。** Agent 在一次“帮我清理一下”里删掉不该删的目录，或者测试环境写的脚本顺手跑到了生产库。

两种失败的本质相同：权限边界没有工程化，全靠 prompt 里一句“小心点”。

## 做法

我们把所有工具按两个维度分桶：**可逆性**（能不能撤回）和**影响面**（是否外部可见、是否花钱、是否动生产），得出三档策略：

- **auto**：只读、可逆、影响限于本机。读文件、查库、跑 lint，直接干。
- **notify**：可逆但外部可见。发消息、建 issue、写仓库文件。Agent 自己执行，结束后汇报一句。
- **confirm**：不可逆或高危。删除、付款、对外发布、改权限、动生产。必须停下问人，且确认请求必须自包含：干了什么、为什么、影响范围、怎么回滚。

落地要点：

1. **边界写在工具层，不写在 prompt 里。** MCP server 开只读模式，危险工具单独拆出、按需挂载。插件权限同理：默认全关，逐个放行。
2. **确认请求带上下文。** 附上 diff、目标环境、预计影响，让用户五秒做出正确判断，而不是五分钟考古对话记录。
3. **加资源护栏。** 单次任务最大工具调用数、最大花费、运行时间窗，超限自动停，而不是继续。
4. **全量审计日志。** 每次工具调用记录参数和结果，出事能复盘。

## 踩坑点

- **“要不要继续？”不等于确认。** 这种无上下文的确认问多了，等于在训练用户无脑点同意。
- **白名单别按文件配。** 按文件路径维护 allowlist 一周就崩，按目录、按工具粒度才养得起。
- **循环任务里别嵌 confirm。** 批量任务中间停下等确认，人不在就卡死；要么提前拿批量授权，要么把任务拆小。
- **prompt 里的“不要删数据”不是权限系统。** 模型会忘、会被长上下文稀释，硬边界只能落在工具层。

## 可复用建议

- 三档制（auto / notify / confirm）够用，别发明更细的分级，维护不动。
- 每周看一次审计日志：高频被 confirm 的事项评估降级为 notify，出过误操作的就升级。
- 子 Agent 和插件继承最小权限，不要默认共享主 Agent 的全部工具。
- 把确认请求模板固化下来——这是提升确认质量性价比最高的一件事。

## 总结

权限边界不是安全补丁，而是 Agent 产品化的一部分。原则一句话：**可逆的自己干，不可逆的带上下文来问；问人的次数要少，但每一次都值得认真看。** 省下来的确认成本，才养得起关键节点上那一下“再想想”。
