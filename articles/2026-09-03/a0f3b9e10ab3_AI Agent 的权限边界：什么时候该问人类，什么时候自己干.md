## 背景

Agent 框架跑起来之后，最先遇到的往往不是能力问题，而是权限问题。接上 MCP 工具、插件、shell、文件系统之后，agent 理论上什么都能干——真正的工程问题于是变成：**哪些动作它可以直接执行，哪些必须停下来等人类确认？**

这个边界划不好，两个方向都会翻车：问得太勤，人沦为确认框点击机器，自动化形同虚设；问得太少，一次误操作就够删库、发错消息、烧掉预算。

## 问题

典型现象：demo 阶段一切正常，一跑真实任务，要么每小时弹十几个确认框，要么半夜自动执行了没人审查过的批量操作。根源是没有一套**显式的决策规则**，默认策略全靠框架出厂设置，出事了才开始补。

## 做法：按“可逆性 × 影响范围”分级

我们的做法是给每个接入的工具打两个标签：

- **可逆性**：动作能否撤销？读文件、查询 API 可逆；发消息、写数据库、调用付费接口不可逆或难以撤销。
- **影响范围**：只影响 agent 自己的工作目录，还是波及生产环境、真实用户、真实资金？

据此分四档：

| 档位 | 典型动作 | 策略 |
|---|---|---|
| 可逆 + 小范围 | 读文件、搜索、写本地草稿 | 全自动，仅记日志 |
| 可逆 + 大范围 | 批量读取线上数据 | 自动，但限流限额 |
| 不可逆 + 小范围 | 写测试环境 | 自动，保留回滚脚本 |
| 不可逆 + 大范围 | 发正式消息、生产变更、花钱 | 必须人工确认 |

落地步骤：

1. 盘点所有工具（MCP server、插件、shell 命令），逐个打标分级。
2. **在工具层而不是 prompt 层配置策略**。prompt 里写“请谨慎操作”没有约束力，工具级的 allowlist 和确认开关才是硬边界。
3. 对不可逆动作强制输出执行摘要：改什么、影响谁、怎么回滚，让人类 30 秒内能做判断。
4. 所有自动执行的动作留完整日志，含参数和结果。
5. 每周复盘误判案例，动态调整分级。

## 踩坑点

- **确认疲劳**：确认框一多，人就开始无脑点“允许”。宁可让几个低风险动作也走确认，也不要稀释确认通道的可信度。
- **无上下文的提问**：“可以继续吗？”这类问题等于没问。必须附带 diff、目标清单、预计开销和备选方案。
- **伪装成读操作的工具**：有些“查询”工具会消耗配额或触发 webhook。打标时别只看工具名，要看实际副作用。
- **重试导致重复执行**：不可逆动作要带幂等键，否则超时重试一次，消息发两遍。
- **批量是放大器**：单条无害的操作循环一百次就是事故。批量和循环要整体视为一个动作重新评估档位。

## 可复用建议

- **默认宁紧勿松**：新接入的工具先按“需确认”跑一周，确认无副作用再降级为自动。
- **确认请求必须可决策**：有上下文、有后果、有替代选项，否则不如不问。
- **给 agent 配预算**：次数、金额、时长三重上限，超限自动停下问人——这是最便宜的保险。
- **权限策略进版本库**：分级规则写成配置文件，和代码一样走 review。权限也是代码。

## 总结

权限边界不是“信任 agent 多少”的哲学问题，而是一个可以工程化的分类问题：用可逆性和影响范围给动作分级，在工具层强制执行，让每一次人工确认都携带足够信息。agent 的自主性是省出来的，不是放出来的——先把高风险动作管住，剩下的自动化才敢真正放开跑。
