## 背景

Agent 跑起来之后，调用量结构往往出乎意料：一个看似简单的任务，背后可能是「规划 → 挑工具 → 填参数 → 汇总」十几轮调用。如果每一轮都打给云端旗舰模型，费用和首 token 延迟会成倍放大；反过来全换成本地小模型，长上下文规划和复杂工具编排又明显掉链子。多模型路由解决的就是这个错配问题。

## 问题

OpenClaw 里最常见的两种极端配置：所有 agent 绑一个云端模型，或全绑一个本地模型。前者单次 demo 不心疼，放进定时任务跑一晚上账单就上来了；后者省了钱，但 tool call 格式坏、上下文截断、跑偏，排查成本往往比模型费还高。核心问题是：**哪些调用必须强，哪些够用就行。**

## 做法与步骤

**1. 先给任务分类，路由依据是任务类型，不是模型偏好。** 我们把调用归成四类：

- 多步规划、跨工具编排 → 云端强模型（GPT 档）
- 工具选择与参数填充 → 本地 7B 档 + strict schema 校验
- 摘要、格式化、翻译等收尾工作 → 本地
- 涉及隐私或内网数据的上下文 → 强制本地，不允许出机器

**2. 路由做两层：规则先行，模型兜底。** 第一层用 skill 声明 + token 长度 + 任务 tag 的规则判断，零成本；规则盖不住的，再用一次便宜的小模型做分类。千万别让路由决策本身也去调旗舰模型，否则成本结构直接崩掉。

**3. 在 OpenClaw 配置里落到 skill 粒度：**

```yaml
skills:
  planner:
    model: gpt-4.1          # 规划类走云端
  tool-caller:
    model: qwen2.5-7b-q4    # 结构化输出走本地
    fallback: gpt-4.1-mini
    max_retries: 2
  privacy-filter:
    policy: local-only
```

**4. 加熔断式 fallback。** 本地连续失败 2 次降级到云端，但 fallback 要设时间窗，避免「本地一挂 → 全部流量打到云端」的雪崩。

## 踩坑点

- **工具调用格式差异**：不同模型对 function calling schema 的遵循度差很多。本地模型必须配 schema 校验 + 失败重试，否则参数幻觉非常隐蔽，往往到下游工具执行时才炸。
- **本地不等于低延迟**：GPU 被训练或推理任务占着时，本地反而更慢。切路由之前先压测 P95，别凭感觉。
- **上下文窗口不齐**：8k 的本地模型被塞进 20k 上下文会静默截断，路由规则里要带长度检查这一项。
- **质量回归没人看**：改了路由策略后，坏结果往往几天后才暴露。建议留一条 shadow 通道，抽 5% 流量双跑对比。

## 可复用建议

- 维护一张「任务类型 → 模型」映射表，放进 repo 做版本管理。改路由等于改配置，而不是改代码。
- 每次调用记录 task tag、选中模型、token 数、延迟。这份路由日志是之后调参的唯一依据，第一天就要记。
- 给每个 agent 设日预算上限，超限自动整体降级到本地档。
- 固定一小批 golden tasks，每次调整路由跑一遍做回归，成本很低但能兜住大部分翻车。

## 总结

多模型路由的目标不是「最强模型 everywhere」，而是把每一类调用放到**够用、且最便宜或最快**的位置。经验顺序是：规则先行、模型兜底、数据说话——先把路由日志记起来，后续优化自然有方向。
