## 背景

我们群里不少自动化流程已经从"单轮问答"演进到"多步任务"：让 Agent 扫一批仓库、汇总多条数据源、对插件跑批量检查。早期做法都是主 Agent 一步步串行做，任务一多，等半小时是常态，而且所有中间过程都堆在主对话里。

## 问题

串行执行有三个明显的工程问题：

1. **慢**：20 个相互独立的子任务排队跑，总时长是累加的；
2. **上下文污染**：子任务的中间输出（原始日志、网页正文）把主上下文撑爆，后续推理质量肉眼可见地下降；
3. **单点阻塞**：一个子任务卡住，整条流水线停摆。

## 做法

我们的方案是经典的 fan-out / fan-in：主 Agent 只负责拆解、分发、汇总，具体执行交给 subagent。步骤如下：

1. **判断可并行性**。只有相互独立、无共享写目标的任务才拆出去。有依赖关系的保持串行，别为了并行硬拆。
2. **给每个 subagent 自包含的 prompt**。subagent 看不到主对话历史，所以目标、输入材料、可用工具、输出格式必须一次说清。我们固定了模板：目标 / 输入材料 / 禁止事项 / 返回格式（JSON 或固定小节）。
3. **限制并发**。同时跑 3~5 个，超出的排队，不要一次拉满。
4. **约束返回体积**。要求 subagent 只回结论加关键证据，禁止贴原始日志。主 Agent 聚合后的结果控制在几百 token 内。
5. **独立超时与失败兜底**。单个 subagent 超时不影响其他；失败的任务主 Agent 记录后降级处理——重试一次或标记跳过。

## 踩坑点

- **prompt 不自包含**：最常见。subagent 拿着"继续处理刚才那个文件"这种指令只能瞎猜。所有引用必须在子 prompt 里展开成具体路径和内容。
- **并发写同一文件**：三个 subagent 同时改一份配置，后写的覆盖先写的。写操作要么串行，要么各写独立文件再由主 Agent 合并。
- **结果太啰嗦**：模型默认喜欢长篇汇报，几个来回主上下文就爆。必须在子 prompt 里硬性规定返回格式和长度上限。
- **限流与成本**：并行 8 个 subagent 一夜跑光额度。并发数要和 API 配额联动，加个简单的令牌桶控制。
- **该串行的硬并行**：比如"先拉列表、再逐条处理"，拆成并行只会制造脏数据。

## 可复用建议

- 把 subagent prompt 模板沉淀成项目内文件，和 MCP 工具白名单一起版本化管理；
- 每个 subagent 记录耗时、token 消耗、成败状态，方便复盘哪类任务真正适合并行；
- 汇总阶段让主 Agent 做二次校验（抽查一到两个结果），不要全信；
- 并行收益最大的场景是批量只读任务（扫描、摘要、检查）；收益最小的是强顺序写操作。

## 总结

subagent 编排本质是工程问题而非模型问题：拆得对、prompt 自包含、返回收敛、失败隔离——四个条件满足了，多 agent 并行才真正提速。我们的经验是从 2~3 个并发起步，跑稳了再往上加；拆解粒度宁小勿大，出了问题好定位。欢迎大家把自己跑出来的并发数和失败率贴出来对照。
