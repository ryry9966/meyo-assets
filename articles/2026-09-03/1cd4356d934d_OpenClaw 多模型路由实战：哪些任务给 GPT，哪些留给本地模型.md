## 背景

OpenClaw 跑起来之后是一个常驻的 agent 网关：多渠道消息进来，skill 和 MCP 工具被调用，模型在后面干活。用不了多久就会遇到第一个现实问题——账单。所有任务都走 GPT，一个月轻则几十刀；全换本地模型，又发现复杂任务频频翻车。多模型路由解决的就是"不同任务配不同模型"，而 OpenClaw 恰好把模型配置、skill 级覆盖、fallback 链这些口子都留好了。

## 问题

把日常流量摊开看，大致三类：

- 大量低价值任务：消息摘要、心跳检查、日志归并。让 GPT 干是浪费；
- 少量高价值任务：多工具 agent 循环、长上下文排查。本地模型干不稳；
- 中间地带：分类、改写、简单问答，两边都行。

痛点不是"哪个模型不行"，而是错配。

## 做法

1. **先给任务画像，再谈路由。** 按三个维度打标：需要几次工具调用、上下文长度、是否涉及隐私。这三项基本决定了模型的下限。
2. **配好两套 provider。** 云端走 GPT 系列；本地用 Ollama 挂一个支持 function calling 的模型，我从 Qwen2.5 14B 起步，够用。注意别选不支持 tool call 的小模型。
3. **分层指定模型。** 全局默认给云端强模型；对确定性低风险的 skill 单独 override 成本地模型；再配一条 fallback 链，云端限流或断网时降级到本地。简化后大致是：

```json
{
  "agents": { "defaults": { "model": "openai/gpt-4o" } },
  "skills": { "summarize": { "model": "ollama/qwen2.5:14b" } },
  "routing": { "fallback": ["openai/gpt-4o", "ollama/qwen2.5:14b"] }
}
```

（字段名以你版本的实际配置为准。）

4. **隐私相关走硬路由。** 涉及私人频道、凭据处理的会话直接绑定本地模型，不走任何"智能判断"。规则越简单越可靠。
5. **跑两周，看日志再调。** 按路由维度统计 token 消耗、失败率、平均延迟，用数据决定下一步把哪个任务降级或升级。

## 踩坑点

- **本地模型的 function calling 是重灾区。** 小模型在多工具循环里会输出不合法 JSON 或凭空调用不存在的工具，表现为 agent 卡死。选型时务必实测 tool call，别只看跑分。
- **上下文长度错配。** 云端习惯了 128k，本地 8k 模型接手长会话会静默截断。给 fallback 加提醒，不要让降级无声发生。
- **冷启动延迟。** 本地模型首次加载十几秒，消息超时判失败又触发重试，雪上加霜。常驻开一个 keep-alive。
- **心跳和后台任务是 token 黑洞。** OpenClaw 的定时任务单次不贵，积少成多，这类任务全丢给本地模型。
- **别迷信动态路由。** 让一个小模型判断"该用哪个模型"，判断本身也会错，而且错了极难排查。我最终退回了规则路由。

## 可复用建议

- 按"任务形状"路由，而不是按模型名字路由：工具调用数、上下文长度、隐私等级，三个维度写死规则。
- 初始策略保守些：全走云端，再逐个把确定性高的任务降级到本地，每降一个观察一周。
- fallback 链要短，两级足够；每一级降级都要可感知（日志、通知）。
- 给每条路由留统计数据。路由策略是调出来的，不是设计出来的。

## 总结

多模型路由不是省钱的技巧，而是把"任务的形状"和"模型的能力"做匹配的工程问题。OpenClaw 把口子留好了，剩下的是画好任务画像、配对、验证。先跑通再优化——规则路由加两级 fallback 这套朴素做法，已经覆盖了我 90% 的场景。
