## 背景

E2E 测试一直是最让人焦虑的一层：单测好写但覆盖不了集成路径，E2E 能兜底但维护成本高。常见现象是——写的时候兴致勃勃，三个月后 CI 红了没人修，最后整套用例被 skip。

Agent 出现后，很多人的第一反应是"让它直接从代码生成测试"。我试了一轮，这条路不太对。下面分享我们目前跑得比较稳的方案：让 Agent 基于真实浏览行为生成用例，并在 CI 中自我修复。

## 问题

直接让 LLM"读代码写 Playwright 测试"有三个硬伤：

1. **选择器是猜的**。模型没有真实 DOM，写出来的 `getByText` 十有八九跑不过。
2. **业务流是脑补的**。真实操作路径里有大量隐式前置：登录态、引导弹窗、灰度开关，代码里看不出来。
3. **断言力度失控**。要么只断言不报错（约等于没测），要么断言到具体文案，改个按钮就全红。

所以核心思路是：不让 Agent 凭空想象，让它先"操作一遍"，再基于操作记录生成测试。

## 做法

我们的链路：OpenClaw Agent + 浏览器 MCP（Playwright MCP）+ 仓库内的测试规范文档。

1. **喂规范**。把团队测试约定写成 `testing.md` 放在仓库：页面必须用 role/name 定位、断言断结果不断过程、数据统一走 seed fixture。这份文档是地基，生成质量的上限基本取决于它。
2. **录制意图**。通过浏览器 MCP 真实走一遍核心路径，比如"提交一个订单"。每一步工具调用本身就是结构化记录：访问的 URL、点击的 role、看到的响应。
3. **生成用例**。把操作记录 + testing.md 一起交给 Agent，产出 Playwright 文件。因为输入来自真实 DOM 的 role/name，选择器基本不用返工。
4. **失败回灌**。本地或 CI 跑一遍，失败用例把报错信息和 trace snapshot 丢回给 Agent 修复。约束一条：**Agent 只允许修定位和等待，不允许改断言语义**，改断言必须人来。
5. **入库评审**。生成物和普通 PR 一样走 review，重点只看一件事：断言是否断在业务结果上。

## 踩坑点

- **不要让 Agent 在 CI 里自由探索**。探索阶段放开没关系，修复阶段必须限定改动范围，否则它会用 `waitForTimeout(3000)` 这类手段把测试"修绿"。
- **登录态**。E2E 最大的噪声源。用 storageState 预置会话，别让每个用例都走一遍 UI 登录，又慢又容易 flaky。
- **模型会幻觉 API**。生成时偶尔编造不存在的方法，第一轮跑挂是正常的，回灌一轮基本收敛。
- **成本控制**。每次回灌都带 trace 截图会迅速吃 token。只在断言失败时传截图，定位类错误只传文本。

## 可复用建议

- testing.md 越具体越好，把"禁止 waitForTimeout""必须 seed 数据"这类硬规则写进去，比在 prompt 里喊口号有效得多。
- 把"生成"和"修复"拆成两个独立子任务，边界清晰才好控。
- 断言语义永远人审。Agent 负责让它跑起来，人负责让它测得对。
- 先从 3~5 条核心路径做起（下单、登录、退款），别一上来铺全量。

## 总结

这套方案的实质：把 E2E 里"体力部分"（定位、样板、修 selector）交给 Agent，把"判断部分"（测什么、断什么算对）留在人手上。上线两个月，核心路径覆盖从 4 条涨到 17 条，CI 里 selector 过期导致的红灯基本消失。它没有替代测试思维，只是把写测试的门槛降到了"走一遍流程"的程度。就这个杠杆而言，值。
