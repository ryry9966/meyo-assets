## 背景

RSS 并没有死。技术博客、GitHub Release、论文预印本、播客，大量高质量信源依然靠 feed 分发。问题在于 feed 本身没有过滤能力：订阅三十个源之后，每天未读轻松上千条，最后的结果往往是彻底放弃阅读。

我的思路是：RSS 负责"把信息送到门口"，LLM 负责"判断值不值得开门"。管线里 Agent 的角色刻意克制——不做全自动决策，只做粗筛和摘要，最终读什么仍由自己决定。

## 做法

整套管线拆成五步，一台小 VPS 或家里的 NAS 就能跑：

1. **采集**：cron 定时拉取 OPML 里的全部 feed，解析出标题、链接、正文、发布时间。这一步普通 HTTP + XML 解析就够，不需要 Agent。
2. **清洗去重**：截断正文（比如前 4000 字符）、剥掉 HTML 标签、按链接 + 标题 hash 建去重缓存。不同源互相转载很常见，不去重就是在烧 token。
3. **粗筛**：用便宜的小模型对每条打分（相关 / 可能相关 / 无关），关注范围写在 prompt 里。无关条目直接归档，不进下一步。
4. **摘要**：留下的条目换能力更强的模型，生成两三句摘要加一句"为什么值得读"，落库。
5. **推送**：每天固定时间聚合成一份 Markdown 日报。我选择写本地 Markdown 再同步进笔记库，接 Telegram bot 或 webhook 也一样。

如果用 OpenClaw 的 MCP 插件体系，第 1、2 步可以封装成 fetch / clean 两个 tool，第 3、4 步交给 agent 循环调用，调度用一个最简单的定时触发即可，不必引入更重的框架。

## 踩坑点

- **正文太短时模型会编**。很多 feed 只给摘要，模型拿到两行正文会脑补出完整内容。解法：正文低于字数阈值时，prompt 里强制只输出"信息不足，建议读原文"，禁止展开。
- **pubDate 不可信**。不少源时间戳是错的，按它去重或排序会出鬼。以"首次见到该链接的时间"为准。
- **编码**。个别中文老站是 GBK，按 UTF-8 硬解会得到乱码，再被 LLM 摘要成一堆幻觉。入库前强制做编码探测。
- **成本失控**。粗筛和摘要合并成一步会很烧钱。改成两段式（小模型筛、大模型摘）后，我的月成本降了一个数量级。
- **静默失败**。cron 挂了你是不知道的。加心跳：管线每天成功跑完给自己发一条通知，没收到就说明出问题了。

## 可复用建议

- 原始条目永远落库存档。摘要可以随时重跑，原文丢了就只能重新爬。
- prompt 里显式写"不知道就说不知道"，宁可漏摘要，不要幻觉。
- 日报优于实时推送。实时推送会重新制造焦虑，日报强迫你批处理。
- 把关注领域写进配置而非 prompt 硬编码，兴趣变了只改配置。

## 总结

这条管线没有任何黑科技，本质是"定时任务 + 结构化数据 + 两次 LLM 调用"。它最大的价值不是省时间，而是把"要不要读"这个决策从情绪驱动变成清单驱动。工程上刻意保持简单：能 cron 解决的不上队列，能模板解决的不上框架。信息管线的可靠性，恰恰来自它的无聊。
