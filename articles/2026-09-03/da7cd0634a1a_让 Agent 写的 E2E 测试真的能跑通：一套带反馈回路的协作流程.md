## 背景

E2E 测试是大多数团队"知道该写但一直欠债"的部分：写起来慢、选择器脆、环境一变就全红。最近我们在内部项目里让 Agent 参与这件事，跑了几个月后沉淀出一套可复现的流程。

先说清楚前提：这里讲的**不是**"给一段需求描述让模型吐测试代码"。那种一次性生成存活率很低。真正有价值的，是把 Agent 接进一个有真实反馈回路的协作流程。

## 问题

直接让模型生成 E2E 测试，典型失败模式有四种：

1. **选择器靠猜**——模型没见过运行时 DOM，生成的 CSS/XPath 大概率不存在，或页面一改就碎；
2. **测试从未真正运行**——代码看起来像样，但没人跑过，assert 甚至是恒真的；
3. **等待写法糟糕**——满屏 `sleep(3000)`，本地偶尔绿，CI 上随机挂；
4. **断言粒度失控**——要么啥都断言（脆），要么只断言页面没报错（弱）。

共同根源：Agent 缺少"真实反馈"，代码写完没人告诉它对不对。

## 做法

核心思路：**把测试执行环境包装成 Agent 可调用的工具，让它自己跑、自己看失败、自己修。**

我们的栈是 Playwright + OpenClaw Agent + 一个自写的 MCP server，分四步：

**1. 封装三个 MCP 工具**
- `browser_snapshot`：返回页面可访问性树（不是完整 DOM，太占上下文）
- `run_test`：执行指定用例，返回结构化失败信息（错误类型、截图路径、失败断言）
- `list_routes`：暴露应用路由和测试环境入口，让 Agent 不用猜 URL

**2. 给 Agent 一份测试约定文档**
放在仓库里（如 `TESTING.md`）：选择器优先用 role + 可访问名称、禁止 sleep、登录走 fixture、数据用工厂函数。Agent 生成前先读这份文档，比在 prompt 里反复强调管用。

**3. 生成—运行—修复闭环**
流程是：读用户故事 / PR 描述 → 用 `browser_snapshot` 确认真实页面结构 → 生成测试 → 调 `run_test` → 失败就读输出改 → 通过为止。修复最多 5 轮，超过就停下交给人，避免无限循环烧 token。

**4. 人只审断言**
生成的 PR 里，fixture、import、describe 结构基本不用看，review 精力集中在断言是否表达了真实业务行为。

## 踩坑点

- **别让 Agent 碰完整 DOM**。一个中后台页面的 HTML 轻松几十 K token，可访问性树小一个数量级，且更接近"用户看到什么"。
- **测试必须至少绿一次才能进主干**。我们用 CI 卡了：新测试文件没有对应的成功运行记录就直接拒绝合并。听着严，但挡掉了大量"看起来对"的测试。
- **警惕过度拟合当前 UI**。Agent 很爱断言具体文案和第 N 个元素的位置。约定文档里明确：断言行为和角色，不断言实现细节。
- **staging 要有隔离数据**。Agent 反复跑会造脏数据，给测试专用账号和独立数据空间，别让它碰真实用户数据。

## 可复用建议

- 反馈回路比 prompt 技巧重要，`run_test` 返回的失败信息质量直接决定修复成功率；
- 约定文档放仓库、进版本管理，让 Agent 读文件而不是读你的 system prompt；
- 修复轮数必须有硬上限；
- 人的位置从"写测试"移到"定义什么算测试通过"。

## 总结

这套流程跑下来，核心路径的 E2E 覆盖从约 30% 提到 75%，人工投入集中在约定制定和 review 上。Agent 不是替你决定"测什么"，而是替你完成"写出来并跑到绿"这个体力活。边界感清楚了，这件事才可持续。欢迎在社区里交流你们的 MCP 工具封装方式。
