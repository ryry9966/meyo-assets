## 背景

Agent 的能力边界基本等于它能调用的外部服务：LLM API、搜索、数据库、MCP 工具、第三方 SaaS。这些依赖没有一个承诺可用。写 demo 时一切正常，一旦跑长任务、定时任务或并发上去，429、超时、5xx、配额耗尽会轮番出现。错误恢复不是锦上添花，而是 Agent 能不能上生产的分水岭——不管你用 OpenClaw 插件、MCP server 还是自研 harness，这道题都绕不开。

## 问题：三种典型死法

1. **无限重试**：模型收到报错后自己决定"再试一次"，循环烧 token，任务永不结束。
2. **幻觉兜底**：工具失败后模型不承认失败，编造一个"看起来合理"的结果继续往下走。这是最危险的一种。
3. **级联阻塞**：某个 API 卡 60 秒超时，Agent 每一步都等它，整个任务被拖死。

根因通常是同一个：重试策略写在 prompt 里而不是代码里，错误信息以一坨字符串回传给模型。

## 做法：四层防线

**第一层，错误分类。** 超时、429、5xx 是瞬态错误，可重试；401、404、参数错误是永久错误，重试无意义。分类在工具封装层做，不要指望模型判断。

**第二层，代码侧重试。** 指数退避加抖动（jitter），最多 3 次，尊重 `Retry-After` 头。重试次数和间隔由代码控制，模型只接收"已重试仍失败"的最终结论。

**第三层，熔断与降级。** 同一工具连续失败 N 次，熔断打开，冷却窗口内直接快速失败，不再真调 API。降级要有预案：备用服务商、过期缓存，或干脆声明"此能力暂不可用"，把任务改为部分完成。

**第四层，结构化错误回传。** 给模型的不是报错堆栈，而是这样的 JSON：

```json
{
  "status": "error",
  "error_code": "UPSTREAM_TIMEOUT",
  "retryable": false,
  "suggestion": "跳过搜索，基于已有资料继续，并在结论中注明信息可能不完整"
}
```

同时给整个任务设总预算：最大步数、最大重试次数、token 上限，由 harness 强制执行，而不是靠模型自觉。

## 踩坑点

- **对非幂等操作重试**：POST 下单、支付这类请求，客户端超时可能对方已经成功，盲目重试就是重复扣款。写操作必须带幂等键。
- **退避不加抖动**：多个 Agent 同时恢复，请求同时打到服务端，瞬间又触发限流。
- **把 429 当普通 5xx**：限流要退避更久甚至直接降级，不能一锅炖。
- **超时设太宽**：单次 60 秒超时放进 30 步的 Agent 循环，最坏情况不可接受。工具调用建议 10–30 秒封顶。
- **静默降级**：用了缓存旧数据却不告诉模型和用户，结论里混入过期信息无人知晓。

## 可复用建议

- 所有工具调用走统一封装：超时 + 重试 + 熔断 + 结构化错误，一个地方改策略，全局生效。
- 给每个工具维护一张降级矩阵：挂了之后用什么替代，替代数据如何标注。
- 错误分类日志与正常 trace 分开存，方便统计哪个上游是"惯犯"。
- 在 system prompt 里明确告诉模型：工具失败是正常情况，按 `suggestion` 字段行动，禁止编造结果。

## 总结

错误恢复是系统工程问题，不是 prompt 问题。原则一句话：**策略放在代码里，事实交给模型，降级要有预案，写操作必须幂等。** Agent 的可靠性不取决于它成功时多聪明，而取决于依赖挂掉时，它是否还能体面地收场。
