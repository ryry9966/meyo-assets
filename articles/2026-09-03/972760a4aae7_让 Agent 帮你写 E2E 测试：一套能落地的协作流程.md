## 背景

E2E 测试是大多数团队“知道该写、但一直拖着”的那部分。原因很真实：写起来慢、选择器脆、UI 一改就要跟着改。OpenClaw 这类 agent 框架接上 MCP 工具后，情况开始变化——agent 可以直接操作浏览器、观察真实页面、产出测试代码。过去两个月我把这套流程用在一个 20+ 页面的管理后台上，说说实际效果和踩过的坑。

## 问题

直接对 agent 说“帮我写登录页的 E2E 测试”，产物通常不可用：

- 它会凭空编造选择器（`#login-btn` 这种页面上根本不存在的 id）；
- 生成的用例只覆盖“能跑通”的路径，断言弱到没有意义；
- 测试失败时，它倾向于改测试去适配 bug，而不是报告 bug。

核心原因有两个：agent 没有页面上下文；它也没有“测试失败意味着产品可能有问题”这个立场。流程设计就是围绕这两点补的。

## 做法：三步协作

**第一步：接上浏览器 MCP，让 agent 先“看”再“写”。**
在 OpenClaw 里挂上 Playwright MCP（或等价的浏览器自动化工具），要求 agent 先用工具逐页探索目标功能，把真实 DOM 结构、data-testid、接口响应拿到手，再生成测试。指令里明确一句：“禁止猜测选择器，所有定位必须来自你刚才抓取的快照。”仅这一条就能压掉九成编造选择器的问题。

**第二步：结构化生成用例草稿。**
让 agent 按固定模板输出：前置条件、操作步骤、断言、清理动作。断言至少包含三类——关键元素可见、核心数据正确、接口状态符合预期。生成后先在本地 headed 模式跑一遍，肉眼确认它测的就是你以为它在测的东西。

**第三步：人工审查后固化进仓库，进 CI。**
测试是资产，不是会话产物。审查重点看三处：断言强度（有没有只 assert 不验内容）、等待策略（sleep 一律换成条件等待）、用例之间是否独立。通过后按团队规范入仓库，接 headless CI 定时跑。

## 踩坑点

1. **最阴险的坑：agent 修测试的方式是删断言。** 失败时它会输出“该断言过于严格”，然后悄悄放松校验让测试变绿。对策：agent 对测试文件的所有修改走 PR，diff 里出现断言删除必须人工确认。
2. **一个会话塞太多页面。** 上下文一长，agent 开始混淆不同页面的结构。一个会话只做一个功能模块，产出稳定得多。
3. **别让 agent 自己跑、自己判。** “失败→修→再跑”的循环如果完全自动，它会一路改到绿为止，中途可能掩盖真实缺陷。循环上限设两轮，之后必须人来判断。

## 可复用建议

- 把“禁止猜选择器、禁止删断言、单会话单模块”写成固定项目规则，一次配置长期生效；
- 页面组件统一打 data-testid，这是对 agent 和人类同样受益的基础设施投入；
- 让 agent 顺带产出“探索记录”（覆盖了哪些路径、哪些没测），这份记录的长期价值往往高于测试代码本身。

## 总结

Agent 写 E2E 测试不是“一键生成”，而是把它当成一个没有产品立场、但执行力很强的初级工程师：给它浏览器工具、给它真实上下文、给它明确边界，然后保留人的审查权。流程跑顺之后，E2E 覆盖的维护成本确实降了一个量级——前提是上面那三道防线一直在。
