## 背景

OpenClaw 这类本地 Agent 默认是无状态的：每个 session 开始时，模型对你是空白的。上下文窗口再大，也不可能把几个月的对话都塞进去。所以"记住用户偏好"不是模型能力问题，而是一个纯粹的工程设计问题：存什么、什么时候写、什么时候读、怎么过期。

## 问题：大多数失败来自"什么都想记"

我最早的做法很朴素：让模型在对话结束后把"值得记的东西"追加到一个 memory 文件。跑两周就露馅了——文件里塞满了"用户今天在调 k8s""下周要出差"这类会话级信息，真正稳定的偏好（回复用中文、代码示例优先 Python、不要主动加 emoji）被淹没在噪音里。检索回来十条，八条没用，注入后反而稀释了 system prompt 的有效性。

结论：记忆系统的核心不是存储，是**筛选和时效管理**。

## 做法：一条最小可行的记忆管线

我用一个 MCP memory 工具 + SQLite（带 embedding 列）搭了四步：

1. **记录结构先行**。每条记忆是结构化记录，不是自由文本：`{type: preference|fact|instruction, content, scope, confidence, created_at, last_hit_at, source_session}`。类型字段决定这条记忆能不能长期保留。

2. **写入路径：先过滤**。session 结束时（可挂在 OpenClaw 的 session end 钩子或定时任务上）跑一次抽取，但 prompt 里写死判定标准：只收"跨会话稳定、可泛化"的偏好，单次任务的上下文一律不收。抽取结果先和现有记忆做相似度比对，超过阈值就合并或提升 confidence，而不是新增一条。

3. **读取路径：检索注入**。每次新 session 用当前用户消息做向量检索，取 top-5，压缩成一段紧凑文本注入 system prompt。检索不到就什么都不加——空注入好过错误注入。

4. **冲突与遗忘**。同 scope 出现矛盾记忆时不简单覆盖：新记录 confidence 更高才替换，并保留来源。`last_hit_at` 超 30 天且 confidence 低的认识降级，90 天归档。用户主动纠正（"别再这么做了"）走显式删除接口，优先级最高。

## 踩坑点

- **抽取过宽**：宁可漏收，不可滥收。只收用户显式表达的偏好（"我喜欢/我总是/以后都"），效果比"智能地记一切"好得多。
- **把 session 内指令当偏好**："这轮回答简短点"是会话指令，写成持久记忆会长期污染输出风格。
- **注入膨胀**：记忆块超过几百 token 后，模型行为明显变化，表现为过度迎合或答非所问。top-k 和单条长度都要硬限制。
- **中文短句的 embedding 区分度差**：偏好类文本往往只有一句话，纯向量检索容易误合并，建议阈值之外再加一层类型/关键词过滤。
- **隐私**：记忆里有大量个人信息，删除入口必须是一等公民，不能只靠管理员改库。

## 可复用建议

- 先写死 schema 再写逻辑，后期加字段比改字段容易。
- 每条记忆强制带 `source_session`，排查"这条记忆哪来的"能省大量时间。
- 准备 20 条左右的回归测试集（偏好 + 对话片段 + 期望召回），每次改抽取 prompt 后跑一遍。
- 在界面上让用户能看到、能删记忆——透明度决定信任度。

## 总结

Agent 记忆不是"给模型加个硬盘"，而是一条有写入过滤、有检索纪律、有过期机制的数据管线。建议从小 schema + 严格抽取标准起步，用真实使用数据迭代，而不是一开始就追求"全知助手"。跑通这条最小管线后，再考虑跨设备同步和多用户隔离，节奏会稳很多。
