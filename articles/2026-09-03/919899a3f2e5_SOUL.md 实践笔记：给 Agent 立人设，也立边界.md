## 背景

OpenClaw 的工作区里有几个约定俗成的 Markdown：`AGENTS.md` 管行为规范，`TOOLS.md` 记使用偏好，而 `SOUL.md` 管的是"这个助手是谁"。很多人把三者混着写，或者干脆不写 SOUL.md，结果就是 Agent 长期运行后表现漂移——今天话多，明天冷淡，遇到冲突请求时立场忽左忽右。

SOUL.md 不是玄学。它本质上是一段会被注入上下文的人格与边界声明，作用类似新员工手册第一页：你是谁，你的做事原则是什么，什么情况该拒绝或上报。

## 问题

不写 SOUL.md 的常见后果：

- **人设不一致**：多次会话之间语气、称呼、幽默感随机变化，用户信任感下降。
- **边界模糊**：Agent 过度讨好，用户说"帮我绕过这个限制"它也想办法配合；或者反过来，动不动拒绝正常请求。
- **角色越位**：主动替用户做重大决定，或替项目做技术选型表态，其实并没有被授权。
- **调试困难**：出问题时分不清是模型能力问题、工具问题，还是人格指令互相打架。

## 做法

我的 SOUL.md 保持在 60 行以内，分四段：

1. **身份与语气**（约 15 行）：一句话定位（例如"你是团队的运维助手，服务对象是内部工程师"），再加语气约定：简洁、不卖萌、先给结论再给依据。写具体行为，不写抽象形容词——"回复先给结论"比"要专业"有用得多。

2. **边界**（约 20 行）：明确列出三类事：**不做**（如绕过权限、伪造数据）、**需确认**（如删除操作、对外发送）、**上报**（如发现疑似安全事件）。每条对应可观察的行为，而不是价值观口号。

3. **冲突处理原则**：当用户要求与边界冲突时，回复结构固定为"不能做 + 一句原因 + 一个替代方案"，不装死也不长篇说教。

4. **一段反模式**：比如不主动推荐未接入的工具、不臆造 MCP 工具的能力、不确定时直说不确定。

写完后重启 Agent 会话使其生效，然后跑几个对抗性测试：让它做越界的事、问它自己是谁、让它复述自己的原则，看输出是否符合预期。

## 踩坑点

- **写太长**：超过一两百行后，关键边界会被稀释，模型注意力是有限资源。SOUL.md 管人格，AGENTS.md 管流程，别把操作步骤塞进来。
- **抽象词堆砌**："聪明、友好、可靠"没有可执行性。每一条都要能回答"这条指令如何改变它的输出"。
- **不做版本管理**：SOUL.md 是活文件，放 Git 里。每次行为异常先 diff，很多"模型变笨了"其实是上次手改引入了矛盾指令。
- **自相矛盾**：一边写"永远不要问澄清问题"，一边写"重要操作必须确认"，模型只能随机选一个，行为看起来就像抽风。
- **当安全护栏用**：SOUL.md 是人格约束，不是防御墙。真正的权限控制在工具层和网关层做，不要指望一段 Markdown 挡住注入攻击。

## 可复用建议

- **模板骨架**：身份一段、语气三到五条、边界三列（不做/需确认/上报）、冲突处理一段、反模式一列。
- **迭代节奏**：每周回顾一次对话日志，把翻车案例反推成一条新边界，同时删掉从未触发作用的旧条款——SOUL.md 只增不减会慢慢失效。
- **一句话检验**：任何新用户读完你的 SOUL.md，应该能准确预测这个助手对三种典型消息的回复方式。
- **团队共用时当代码 review**：改人格要有 commit message 说明动机，避免某个人半夜顺手改出一张"话痨"。

## 总结

SOUL.md 的价值不在"让 Agent 更像人"，而在让它的行为**可预测、可解释、可审计**。人格是产品的一部分，边界是工程的一部分。写得越具体、越短、越接近真实约束，Agent 就越稳定。建议先从 30 行开始跑两周，再决定加什么——这比一次写一份完美人设靠谱得多。
