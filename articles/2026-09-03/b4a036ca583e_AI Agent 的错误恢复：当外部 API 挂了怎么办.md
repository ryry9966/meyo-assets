## 背景

Agent 自动化跑起来之后，最大的不稳定因素往往不是模型本身，而是外部依赖：LLM 供应商限流、MCP 工具超时、第三方 API 改版、鉴权 token 过期。本地脚本挂了可以看日志重跑，Agent 挂在长任务中间，代价是整条上下文和已经烧掉的 token。所以错误恢复不是补个 try/catch 的事，而是 Agent 层需要专门设计的一部分。

## 问题在哪

常见的三种失败模式：

1. **直接崩**：一个工具返回 500，整个 run 中断，前面的步骤全部作废。
2. **无限重试**：Agent 收到错误后反复调用同一个接口，每次重试都要过一遍 LLM，钱在烧，任务没进展。
3. **幻觉兜底**：错误以非结构化文本返回，模型"脑补"一个结果继续往下走。下游拿到假数据，比崩溃更难排查。

## 做法：分层下沉到工具执行层

核心思路是把错误处理从"prompt 里叮嘱模型"下沉为"工具执行层的工程约定"。

**第一层：统一的调用包装器。** 每次外部调用都经过同一个 executor：设置单次超时（比如 10s）和整个 run 的总时间预算。重试只针对可重试错误——429、5xx、网络超时；401/403/参数错误直接失败，不浪费重试次数。指数退避加抖动，避免重试风暴。

**第二层：错误结构化后再交给模型。** 不要把原始堆栈或 HTML 错误页塞给 LLM。统一返回类似 `{"ok": false, "code": "TIMEOUT", "retryable": true, "hint": "上游搜索服务暂不可用"}` 的对象，模型才能据此判断：换工具、降级，还是停下来问人。

**第三层：降级链。** 关键依赖准备 fallback：主 API 挂了切备用源，再不行用缓存数据并明确标注"数据可能过期"，最后才是跳过该步骤、在最终报告里注明。原则是让任务**小步失败**，而不是整单失败。

**第四层：幂等与断点。** 有副作用的操作（发消息、建工单、写库）必须带幂等键，否则重试就是重复执行。长任务在每步之后落盘状态，挂了从断点续跑，而不是从头来过。

## 踩坑点

- **重试预算按"单次调用"设置而不是按"整个 run"**：一轮任务调几十次工具，累积重试次数会失控。
- **把空结果当错误吞掉**：工具失败时返回空数组，Agent 理解成"查无数据"，结论全错。失败和空结果必须区分。
- **重试非幂等写操作**：用户收到三条一模一样的通知。
- **缺熔断**：上游已经连续挂了，Agent 还在每一轮里撞一次，浪费 token 也拖长任务。连续 N 次同类错误后应短路该工具。
- **只测 happy path**：上线前用 mock 注入 500 和超时，确认 Agent 真的走了降级分支，而不是靠运气。

## 可复用建议

- 所有工具调用走同一个带超时/重试/错误归一化的 wrapper，不要每个插件各写一套。
- 系统提示里写清降级策略："某工具不可用时，优先 X，其次 Y，都不可用则停下说明原因"，比事到临头让模型自由发挥可靠。
- 错误按类别打点（超时/限流/鉴权/5xx），跑一周数据，就知道该优先加固哪类问题。
- 错误对象里带 `hint` 字段，比让模型自己从报错文本里猜下一步稳得多。

## 总结

外部 API 一定会挂，这不是概率问题，是时间问题。Agent 错误恢复的目标不是"不失败"，而是**失败得小、重试得聪明、降级得体面**。把这套机制做在工具执行层，让模型只负责决策，系统才撑得起无人值守的长任务。
