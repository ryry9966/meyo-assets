## 背景

大多数 agent 的默认形态是问答机：你发消息，它回复，会话结束。但 OpenClaw 的架构里其实留了几个不起眼的口子——gateway 常驻、agent 可以被 cron 调度、还有周期性 heartbeat。这三样拼起来，“主动服务”就不再是产品演示里的噱头，而是一个可以落地的工程问题。

## 问题

在 system prompt 里写“请主动一点”是没用的。主动性 = 触发器 + 判断 + 行动 + 克制的汇报，四件事缺一不可。直接给 agent 开 heartbeat，常见的两种翻车：要么每次心跳都来汇报“一切正常”，通知轰炸让人直接关掉推送；要么判断标准模糊，半夜替你执行了不该执行的操作。下面是我把 OpenClaw 从“问答机”调成“值班助理”的过程。

## 做法

1. **盘点场景**。先列出真正值得主动的事项，而不是让 agent 自己想。我选了三个：每日晨报（日程 + 天气 + 昨晚 CI 结果）、关注的仓库出了新 release 时提醒、工作目录里超过两周未处理的 TODO 文件。
2. **选触发器**。固定时间的用 cron（`openclaw cron add`），“有变化才说”的用 heartbeat 周期唤醒。不要全塞给 heartbeat——定时任务的成本是可预期的（具体命令和字段名以你部署的版本为准，思路通用）。
3. **写可判定的规则**。每个主动任务单独一个 skill，prompt 里写死分级：L0 只写 journal 不打扰；L1 攒着，并入晨报；L2 即时通知；L3 必须我确认才执行。关键是给“什么值得打扰”一个可判定条件，比如“CI 失败且发生在 main 分支”才是 L2，而不是“感觉重要就告诉我”。
4. **接受限的行动工具**。通过 MCP / 插件接只读工具（git log、RSS、日历）。主动场景一律先只读，写操作走 L3 人工确认。
5. **去重与状态**。journal 里记 key（仓库 + 事件类型），心跳判断前先查一遍，避免同一件事每天提醒一次。

## 踩坑点

- **心跳间隔太短**：token 成本线性上涨，中间思考还会污染主对话的 memory。我用 30 分钟起步，观察一周再调。
- **没有去重**：同一个 release 提醒连报三天，用户会本能地关通知，之后真重要的也看不到了。
- **判断标准写成形容词**：模型对“重要”的理解和你不一样，必须落到分支名、阈值、时间窗口这类可判定条件上。
- **权限过大**：proactive 触发的执行没有人在旁边盯着，删文件、对外发消息、花钱这类高危工具默认关闭。
- **上下文污染**：心跳会话和日常会话共享 memory 时，主动任务的杂念会拉低日常对话质量，建议隔离或定期清理。

## 可复用建议

- 把“主动性”当成分级系统来设计，而不是一个开关。
- 一个主动任务 = 一个独立 skill + 独立状态文件，方便单独停用和回放日志。
- 新任务先跑一周“静默模式”：只写 journal 不推送，人工 review 它“想说的话”，再逐步放开通知。这一步通常能过滤掉八成的噪音规则。

## 总结

Proactive 不是玄学，而是调度器 + 可判定的判断规则 + 受限的行动工具 + 克制的汇报策略。OpenClaw 的 heartbeat、cron 和插件体系已经把管道铺好了，真正难的是设计“什么值得打扰用户”这条线。建议从只读、低频、阈值明确的场景开始，跑顺了再谈更大胆的自动化。
