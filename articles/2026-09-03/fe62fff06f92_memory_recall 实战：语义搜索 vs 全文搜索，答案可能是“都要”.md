## 背景

OpenClaw 的 `memory_recall` 本质上是一个可插拔的检索入口：Agent 拿到用户请求后，从记忆库里召回相关片段塞进上下文。社区里被问最多的问题之一就是——用向量语义搜索，还是传统全文搜索（BM25/LIKE）？

我们团队给一个长期运行的助手 Agent 维护记忆库半年多了，四千多条对话片段和决策笔记，两种方案都认真跑过，踩坑不少，这里把结论摊开讲。

## 问题

**语义搜索**擅长“换个说法也能找到”：用户问“上次部署失败怎么解决的”，能命中一条写着“K8s rollout 卡住，已回滚”的笔记。但它对精确标识符很弱——“cluster-7 的 API key”、“config.py 里那个 bug id”这类查询，在 embedding 空间里几乎是噪声，召回质量崩塌。

**全文搜索**正好相反：错误码、函数名、项目代号这类精确串查询非常可靠，但用户一换措辞、用同义词，召回率就掉下来。中文场景还有分词这个额外变量。

## 做法

我们最终落在混合检索上，核心四步：

1. **记忆切小块**：一条记忆 = 一个事实，50–200 字，避免大段对话原文。写入时带上元数据：时间戳、项目标签、记忆类型（决策/报错/事实/偏好）。
2. **双通道并行**：向量检索取 top 8；BM25（中文走 jieba 分词）也取 top 8。
3. **RRF 融合排序**：两路分数直接相加没有意义（量纲不可比），用 Reciprocal Rank Fusion，k 取 60，合并后取 top 4–5。
4. **可选精排**：有条件就加一个小 cross-encoder 对 top 10 重排；没条件就按 RRF 排名叠一个时间衰减权重。

上线前先建一个 30–50 条的评测集，一半“换说法”类查询，一半“精确标识符”类，人工盯 recall@5。我们实测：纯语义在标识符类查询上召回率 60% 上下，纯全文在换说法类上 65% 左右，混合后两类都稳定在 85% 以上。

## 踩坑点

- **embedding 中文短标识符基本没用**。别指望换模型解决，靠全文通道兜底。
- **BM25 默认空白分词在中文上全军覆没**，务必接 jieba 或字符 n-gram。
- **k 给太大反而坏事**：记忆片段塞进 prompt 又耗 token 又分散注意力，4–6 条足够。
- **时间信息会被向量排序打乱**。时间戳放元数据里，融合时做 recency boost，否则“上周”干不过“去年”。
- **向量检索前先按元数据过滤**，后过滤会凑不满 k 条。
- **失败查询写进评测集**。检索质量是持续迭代项，不是一次性配置。

## 可复用建议

- 决策规则：查询含精确标识符（ID、错误码、文件名）→ 全文优先；自然语言转述 → 语义优先；拿不准 → 混合。
- 记忆写入时切好粒度、写全元数据，比换检索算法收益更大。
- 召回日志一定要留，每周抽样看哪些查询落空了。
- RRF 几乎不用调参，是融合排序的默认答案。
- 模型升级只动向量通道，BM25 管线保持独立，方便单独回归测试。

## 总结

语义和全文没有标准答案，取决于你的查询分布。但 memory_recall 的真实场景里，用户查询是“转述”和“精确查”混着来的，混合检索 + RRF 是工程成本最低、召回最稳的落地方案。先花半天建一个 30 条的评测集，再按失败日志迭代——比反复纠结模型选型有用得多。
