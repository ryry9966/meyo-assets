## 背景

E2E 测试是很多团队"都知道该写、但一直欠债"的部分。手写一条完整用户路径的用例往往要半天，页面一改版选择器批量失效，维护成本远高于单测。我们团队近几个月用 OpenClaw 的 Agent 配合浏览器类 MCP 工具（Playwright 风格的 server）来分担这块工作，说说真实体验。

先给结论：Agent 写 E2E 不是"一键生成测试套件"，而是把人从抄写样板代码里解放出来，把精力转移到设计覆盖范围和审查断言上。流程跑顺后，单条用例的产出时间大约缩到原来的三分之一，前提是流程要约束得住。

## 问题

直接丢一句"帮我给登录页写 E2E"，大概率得到三类垃圾：

1. **幻觉元素**：用例引用了页面上根本不存在的按钮和文案，第一行就挂。
2. **弱断言**：只断言"页面能打开"，等于没测。
3. **脆弱选择器**：满屏 `.css-1x2y3z` 这类构建产物类名，改一次 UI 全红。

根因是 Agent 缺两样东西：真实页面结构，和项目的测试规范。

## 做法

流程分五步，关键在前两步：

**1. 先给上下文，不要先要代码。** 用 MCP 浏览器工具打开目标页面，抓取 accessibility tree 快照喂给 Agent，让它基于真实 DOM 产出用例清单——注意是清单，不是代码。人对着清单确认覆盖范围，这一步别省，用例设计错了后面全白干。

**2. 用规范文档约束生成。** 在仓库里放一份测试规范（也可以并进 AGENTS.md），写清楚：统一 `getByTestId`、必须复用现有 fixture、登录态用 storageState、断言用 `expect(...).toBeVisible()` 而非固定 sleep。Agent 会严格遵守，前提是你真的写了。

**3. 小批量生成。** 一次让它写 2-3 条，而不是整个套件。指定目标文件路径，并让它先读相邻的已有测试文件，模仿既有风格。

**4. 跑挂了就喂回去。** 把报错和截图直接贴回对话让它自己修。多数失败是选择器错位或等待不足，Agent 修这类问题比人翻文档快。

**5. 定期做选择器审计。** 隔段时间让 Agent 扫一遍测试目录，报告仍在用脆弱选择器的用例，并给出补充 `data-testid` 的清单，交给前端一起改。

## 踩坑点

- **别信"生成即通过"**。我们最初一次生成 30 条，表面跑通一半，细看大量断言是 goto 后直接 expect URL——假覆盖。断言必须逐条人工过。
- **固定 sleep 是毒药**。Agent 很爱写 `waitForTimeout(3000)`，本地能过，CI 一慢就 flaky。规范里明确禁止，要求带轮询的断言。
- **CI 与本地环境差异**：时区、随机种子、未 mock 的第三方请求都会造成"本地绿 CI 红"。把环境变量和数据种子写进约定，让 Agent 生成时统一处理。
- **让它读旧代码，别让它发明模式**。不给参考文件时，Agent 会自造一套 helper，很快仓库里出现三套登录逻辑。

## 可复用建议

- 把测试规范当 Agent 的"入职文档"来维护，值得花一小时写好。
- 用例清单先行、代码后行，人是评审者不是打字员。
- 报错回喂是最省时间的环节，把你的反馈 prompt 模板化保存。
- E2E 总量要克制，只覆盖关键路径；批量生成低价值用例只是增加维护税。

## 总结

Agent 参与 E2E 的真实收益不在"写得快"，而在降低维护测试的心理成本——改版之后你愿意跑一遍、修一遍，而不是直接删掉。工具链（Agent + MCP 浏览器 + 规范文档）都不新，新的是把它们串成一个有约束的循环。建议从最稳定的 5 条核心路径开始试，两周后再决定是否扩大。
