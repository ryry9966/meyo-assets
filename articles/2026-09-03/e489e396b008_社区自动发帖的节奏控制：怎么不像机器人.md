## 背景

我们社区有几个常驻 Agent 任务：每日摘要、新帖归档提醒、周报。内容用 OpenClaw workflow 生成，走 MCP 发到论坛和群聊。功能不复杂，但上线第一周就被管理员找上门：某天凌晨两点，积压的摘要一次性发了 7 条，间隔整齐的 30 分钟——内容没问题，观感像刷屏。

## 问题：节奏比内容更容易暴露

翻车通常不在内容质量，而在发布模式：

- **突发**：任务完成后把积压内容一次性灌出去；
- **过于规整**：固定 cron，比如每小时整点一条，比人还准时；
- **无时段意识**：在社区活跃高峰之外的时段发不重要内容；
- **回复秒回**：被 @ 之后 3 秒出现，比任何签名都像机器人。

## 做法

核心思路一句话：**把“生成”和“发布”拆开，中间加一层节奏控制器**。

**1. 队列与发布器分离。** Agent 产出只写队列，发布器按自己的节奏消费。这是后续一切控制的前提。

**2. 间隔加抖动，但要加对地方。** 不要“固定 30 分钟 ± 随机 5”，而是设最小间隔（如 25 分钟）+ 区间随机（25–55 分钟），并把抖动作用在“下一次可用时间”上，而不是计划时间上，否则重启后会重新对齐整点。

**3. 安静时段与每日上限。** 每个渠道配 quiet hours（如 01:00–08:00 不发非紧急内容）和 daily cap（每渠道每天 ≤4 条）。摘要错过高峰期，宁可推迟到下一个窗口。

**4. 追赶要降速。** 宕机恢复后队列积压是常态，追赶速率应设为正常速率的一半，或直接丢弃低优先级项、只补关键项。“追平”的执念是刷屏的主要来源。

**5. 回复单独管理。** 对 @ 的响应走独立通道：人为延迟 1–5 分钟随机；深夜收到的，次日早上集中处理。上下文丢了就引用回复，别硬追时效。

配置层面大致长这样：

```yaml
pacing:
  min_gap_minutes: 25
  max_gap_minutes: 55
  quiet_hours: "01:00-08:00"
  daily_cap_per_channel: 4
  catchup_rate: 0.5
```

## 踩坑点

- **均匀随机也会背靠背。** 每条独立采样间隔，可能一个 5 分钟一个 8 分钟。间隔约束必须建立在“全局上一条发布时间”上，不是各自的计划时间。
- **时区。** quiet hours 一定显式写时区，默认 UTC 会把安静时段平移到白天。
- **重启补发。** cron 重启后任务全部触发，发布器必须自带限速，不能信任上游。
- **别伪装人类。** 故意加错别字、模拟“打字延迟”这类事不要做——用户看得出来，一旦被识破比机器人更糟。目标是节奏上尊重社区，不是冒充人。签名里大方标注“由 Agent 自动发布”，配合合理的节奏，接受度反而更高。

## 可复用建议

- 节奏控制器做成独立模块，任何渠道（论坛、IM、RSS）都过同一层；
- 每周看一次发布时间分布图，“机器感”肉眼一眼就能看出来；
- 优先级分级：关键告警可穿透 quiet hours，其余一律排队；
- 上线前拿自己的频道先跑一周，把自己当普通用户回看时间线。

## 总结

自动发帖的“不像机器人”，本质不是模仿人类，而是尊重社区的注意力节奏。拆开生成与发布、加对抖动、设安静时段与上限、追赶降速——四件事做完，大部分观感问题就消失了。保持透明，控制节奏，比任何伪装都有效。
