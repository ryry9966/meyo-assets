## 背景

我们用 OpenClaw agent 挂定时任务，通过一个 MCP 插件对接论坛 API，自动发每周摘要和版本公告。功能本身很稳定，但上线两周后被社区管理员点名：发帖时间太规律，凌晨三点准时出现，一小时内连发五条，一眼就是机器人。复盘下来这不是风控对抗问题，而是调度层缺少节奏设计。

## 问题拆解

- cron 固定周期触发，时间戳指纹明显
- 队列积压后一次性倾泻（burst），观感像刷屏
- 多个 agent 共用同一账号，发布窗口互相叠加
- 失败重试没有幂等，出现重复帖
- 内容模板高度一致，签名块哈希级相同

## 做法

**1. 出站队列 + 配额。** 所有内容先进 outbox 表，由独立的 publisher 进程消费，而不是生成即发布。每个频道设每日上限和最小间隔。

**2. 加抖动，但别用均匀随机。** 在目标时间窗上做随机偏移，按历史活跃分布加权，避免"每小时整点 ±5 分钟"这种可预测模式。静默时段写进配置：本地 01:00–08:00 不发。

**3. 全局信号量。** 多个 agent/插件共享发布通道时，用集中式令牌桶，保证同一身份在同一时间窗内只有一条消息出去。

**4. 抑制规则。** 事件驱动：检测到频道内有故障讨论或高热争议时，挂起非必要公告。公告晚两小时发没有损失，撞上去观感很差。

**5. 分级审批。** 公告、周报这类低频高影响内容走"草稿 → 人工确认 → 发布"；回复类高时效内容走自动通道，但限速更严。

**6. 内容多样性。** 标题模板轮换、开头句式轮换、去掉完全相同的签名块。目的不是伪装成真人，而是避免机器可识别的重复。

## 踩坑点

- 只对发送时间加 jitter，cron 触发日志还是整点，排查自己问题时会被混淆
- 时区错位：服务器 UTC，社区本地 UTC+8，"活跃时段"判断偏了六小时
- 重试缺幂等键，论坛端出现两条相同帖子；后来给 outbox 加了 client_msg_id 才解决
- 均匀随机抖动的分布本身可被统计识别，对公开社区够用，但别误以为它等于"拟人"

## 可复用建议

- 把配额、静默时段、jitter 范围、冷却时间统一放进一个 pacing 配置文件，别散落在代码里
- 每次发布决策记一条日志：时间 + 原因码（`quota_ok` / `quiet_hours_skip` / `suppressed_by_incident`），方便周会复盘
- 订阅负反馈：被折叠、被举报、连续 N 次零互动，自动降频
- 设计原则：先假设自己是机器人，再逐条消除机器人的证据

## 总结

节奏控制的本质，是把"定时触发"升级为"带约束的出站策略"。outbox、配额、抖动、抑制、分级审批，五个组件都不复杂，用 OpenClaw 的 cron 调度加一个 MCP 发布接口就能搭起来。目标不是装人，而是让自动化在社区里表现为一个守规矩、可预期、不给别人添堵的成员。
