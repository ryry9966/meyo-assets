## 背景

单 Agent 跑长任务的老问题：上下文很快被工具返回值塞满。让它“查 10 个仓库的配置差异”或者“排查一个 5xx 报错”，主 Agent 读完中间结果，真正做判断的余量已经不多了。而且执行是串行的——明明查日志、查部署记录、重放失败请求这三件事互不依赖，却要排队等前一步跑完。

我们的做法是把这类任务拆给 subagent：主 Agent 只做拆解和汇总，子任务并行分发给多个小 Agent 各自执行。

## 问题定义

- 主 Agent 上下文被中间产物污染，推理质量下降；
- 独立子任务串行执行，墙钟时间不可接受；
- 长链条在第七步挂掉，只能从头再来。

## 做法

结构上三层：**编排者（dispatcher）→ 执行者（workers）→ 汇总者（aggregator）**，可以合在一个 Agent 的不同阶段里。

1. **拆任务，先定契约再写 prompt。** 每个子任务写清三样：输入是什么、期望输出什么格式、允许用哪些工具。契约不明确，子代理就会自由发挥。
2. **收紧工具面。** 子代理默认只读，工具按需白名单。排查任务里，读日志的子代理不需要写权限。
3. **并行派发，带超时和重试预算。** 每个子任务独立超时，挂了不阻塞兄弟任务，超时部分标记降级。
4. **结构化回收。** 要求子代理返回固定字段的 JSON：`findings`、`evidence`、`artifacts`、`status`。拒绝自由散文，否则汇总阶段没法对齐。
5. **汇总去重。** aggregator 合并结果、标记冲突项，最终结论必须能回溯到具体子任务编号。

一个实际案例：排查接口 5xx，dispatcher 拆出三个子代理——A 读网关日志，B 比对最近两次部署 diff，C 重放失败请求。三者并行，aggregator 把 B 发现的“配置未随部署更新”和 C 的复现结果拼成一条完整归因链，整个流程从串行的 6 分钟压到 2 分钟出头。

## 踩坑点

1. **子代理没有全局上下文。** 它不知道任务背景，契约里必须把必要信息显式带过去，别指望“它应该懂”。
2. **并发写冲突。** 两个子代理同时 patch 同一个文件，后写覆盖先写。要么预先切分写入空间，要么写操作统一收归 dispatcher 审核。
3. **扇出过宽。** 一口气开 8 个以上子代理，成本陡增，汇总质量反而掉。实践中 3~5 个是甜点位。
4. **递归派生失控。** 子代理自己又拉起子代理，形成循环。在配置层直接禁止，只允许 dispatcher 一层派生。
5. **失败传染。** 一个子代理 hang 住拖垮整批。逐任务超时 + 支持部分结果汇总，是底线能力。
6. **汇总幻觉。** aggregator 会脑补子代理没给的细节。强制结论引用子任务编号，对不上的条目直接丢弃。

## 可复用建议

- **契约先行**：输出 schema 没定下来之前不写子代理 prompt；
- 子代理数量控制在 3~5，单任务超时 + 全局预算双上限；
- 子任务设计成幂等，重试才是安全的；
- 每次派发和回收都落结构化日志，方便复盘和重放；
- 写操作集中化，子代理保持只读为主。

## 总结

subagent 编排的价值不在“更多 Agent”，而在**上下文隔离 + 有界并行**。dispatcher 真正的工作量在任务拆解和契约设计——契约做对了，并行几乎是免费的；做错了，你得到的只是更多份互相矛盾的中间产物。
