## 背景

OpenClaw 的定位是常驻 agent 网关：接消息渠道、挂 MCP 工具、跑定时任务。跑起来之后你会发现，绝大部分 token 消耗来自大量"低价值密度"调用——消息摘要、记忆压缩、意图分类、工具参数抽取——而真正需要强推理的规划类任务，一天可能就几十次。全走 GPT 太贵且隐私说不通，全走本地又不稳，这就是多模型路由要解决的问题。

## 问题

两种典型的错误姿势：

1. **一把梭云端**：所有请求都打到旗舰模型，月账单难看，私聊渠道的内容全部出网。
2. **一把梭本地**：14B 级模型跑日常对话没问题，但一遇到多工具编排、长上下文规划就开始丢步骤、输出格式崩。

## 做法：按任务分层

我目前在用的三层划分：

- **L1 规划与复杂工具调用** → 云端旗舰：多步规划、代码生成、出错代价高的任务
- **L2 常规对话与摘要** → 本地中档模型（14B–32B 量化）：闲聊、日报、记忆整理
- **L3 分类与抽取** → 本地小模型或规则：意图判断、关键词抽取、路由决策本身

落地步骤：

1. 在 provider 配置里同时注册云端和本地后端（Ollama / vLLM 都行），分别起别名。
2. 按 agent/skill 显式指定模型，高风险技能绑云端，摘要类绑本地。示意如下（字段名以你的版本为准）：

```yaml
agents:
  planner:
    model: gpt-4o-class
  summarizer:
    model: local-qwen-14b
fallback:
  - local-qwen-14b
  - gpt-4o-mini-class
```

3. 配 fallback 链：本地优先、超时或格式解析失败时升级云端。反过来（云端优先、降级本地）适合成本不敏感但要求高可用的场景。
4. 路由判断本身用最便宜的模型或规则做——别用旗舰模型给自己当调度员。

## 踩坑点

- **工具调用格式差异**：不少本地模型对 function calling 是"能用但不稳"，参数 JSON 经常带杂质。务必加严格 schema 校验加重试，重试失败才升级云端，别一失败就降级到旗舰。
- **上下文窗口别想当然**：本地 14B 常见 8k–32k，云端 128k+。长会话路由到本地会静默截断，症状是"模型忘了前文"，很难排查。路由层先做长度判断再分发。
- **Embedding 别混用**：记忆库一旦混入两种 embedding 模型的向量，检索质量会莫名下降。固定一个并把版本记下来。
- **首 token 延迟 ≠ 总延迟**：本地模型首 token 快但总时长可能更长。交互渠道看首 token，后台任务看总时长，分开测。

## 可复用建议

- 给每条路由打标，按 route 维度统计 token、失败率、升级率，跑一周就能看出分层是否合理。
- 路由配置进 git，改动写清楚 commit message。
- **升级率是最有信号量的指标**：某条本地路由升级率持续超过 15%，说明任务和模型不匹配，别硬扛。
- 留一个一键全云的逃生开关，排查问题时先排除路由变量。

## 总结

多模型路由不是省钱技巧，而是把任务按风险和复杂度分层的工程决策。原则很简单：出错代价高、上下文长的给云端；高频、低风险、涉隐私的给本地；路由判断本身用最便宜的。先用最粗糙的三层跑两周，看数据再调，比一开始就设计精细规则有用得多。
