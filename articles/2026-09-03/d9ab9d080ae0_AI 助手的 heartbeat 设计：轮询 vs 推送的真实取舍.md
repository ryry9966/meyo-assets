## 背景

OpenClaw 里的不少任务不靠用户发消息驱动：定时汇总、盯订阅源、跟进未完成事项、巡检 MCP 工具侧的状态变化。这些都需要 Agent"自己醒来"。醒来机制无非两条路：心跳轮询（定时主动看状态）和推送（事件发生时被动唤醒）。两种我们都在生产里跑过一段时间，这篇记录取舍。

## 问题

只用心跳的典型症状：

- **延迟错配**：5 分钟一次的心跳，对"被 @ 后要尽快回"这种事不可接受；
- **空转成本**：每次唤醒不设闸门就直进模型，一天 288 次里九成以上是"没事发生"，token 白烧。

只用推送的坑：Agent 掉线/重启期间如果没有持久化缓冲，事件直接丢；at-least-once 投递带来重复处理；webhook 需要可达入口，内网/NAT 环境部署成本陡增。

本质区别：**轮询读的是状态，推送传的是事件**。状态漏读了下次还能读到（自愈），事件丢了就是丢了。这个差异决定了各自的适用面：

| 维度 | 心跳轮询 | 事件推送 |
|---|---|---|
| 延迟 | ≤ 间隔 | 近实时 |
| 丢数据 | 天然自愈 | 需持久化缓冲 |
| 部署 | 无入口要求 | 需可达端点 / broker |
| 成本风险 | 空转唤醒 | 重复投递处理 |

## 做法

**第一步：给任务分类，不要用同一种唤醒覆盖所有任务。** 延迟敏感、有明确触发源（新消息、新文件、上游 webhook）走推送；周期巡检、对账、日报、兜底清理走心跳。

**第二步：心跳端做三层节流。**

1. 调度层：cron / 间隔 + 随机抖动，多实例别整点齐跳，夜间降频；
2. 闸门层：在插件代码里做确定性预检——未读数、文件 mtime、上游版本号，全空直接返回，不进模型。这一层省的是大头；
3. 模型层：只喂摘要 payload（队列深度、距上次动作时间、待办 id 列表），不贴原始日志；约定一个"无事可做"的轻量返回，让空转成本接近零。

**第三步：推送端补三件事。** 持久化缓冲（SQLite / Redis Stream 都够用），事件先落盘再处理，重启不丢；幂等键，处理完才 ack，靠 event id 去重；重试设上限和死信出口，别让一条毒消息堵死队列。

**第四步：混合。** 生产里最终形态基本都是推送管延迟、心跳兜底：推送触发即时唤醒；心跳降到 15–30 分钟一次，只做两件事——对账（补回推送漏掉的状态差异）和存活监测（连续 N 次心跳没打点就告警）。存活信号是白捡的，别浪费。

## 踩坑点

- **账单惊魂**：早期 5 分钟心跳直进模型，一周烧的 token 比正常对话还多。加确定性闸门后空转成本降了两个数量级。
- **重复回复**：webhook 重试 + 没做幂等，同一条消息回了用户三次。event id 去重是底线，不是优化。
- **心跳 payload 塞满上下文**：贴原始日志又贵又让模型更难判断"要不要动作"。喂摘要、喂增量。
- **整点齐跳**：十几个 Agent 都配 `*/5` 的 cron，并发把上游 MCP 服务打到限流。加抖动、错峰。
- **只推送不对账**：一次 broker 故障丢了一小时事件，第二天心跳巡检才发现。事件系统必须配状态对账。

## 可复用建议

- 判断口诀：**怕慢用推送，怕丢用心跳，两个都怕就混合**。
- 闸门优先：一行代码能判断的事，不要花一次模型调用。
- 心跳间隔起点：巡检类 15–30 分钟足够，除非有真实 SLA，别低于 5 分钟。
- 监控三个数：唤醒次数、空转率（无事可做占比）、事件端到端延迟。空转率突升往往说明上游出问题了。
- 心跳 payload 结构化（id、计数、时间戳），别用自然语言日志。

## 总结

轮询 vs 推送不是二选一，而是分工：推送解决"及时"，心跳解决"不丢"和"活着"。落地顺序建议先把心跳 + 闸门做稳——它同时给你兜底和存活信号，再按延迟需求逐个任务加推送。把便宜的确定性代码放在最前面，把昂贵的模型调用放在最后面，这套唤醒机制就不会失控。
