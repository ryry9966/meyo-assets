## 背景

Agent 默认无状态：每次新会话都要重新交代一遍"提交信息用中文""部署目标是家里的 NAS""别在回复里用 emoji"。这不是模型能力问题，是记忆系统的工程问题。过去一年在 OpenClaw 上写插件和 MCP 工具的过程中，我把助手记忆从"能存"迭代到"敢用"，记一些实际经验。

## 问题：三种常见失败形态

1. **全量塞 system prompt**：偏好十几条时还行，两个月后变成 3000 token 的噪音，模型反而开始忽略其中的关键约束。
2. **只做 RAG 检索**：相似度阈值调不好，要么召回一堆无关项，要么关键偏好根本没被召回。
3. **让模型自由地"记"**：它会把一次性任务上下文（"用户在调试摄像头驱动"）当成长期偏好，一个月后这些过期事实开始污染行为。

核心矛盾：写太保守记不住，写太激进记忆库变垃圾场。

## 做法：分层 + 结构化 + 双闸门

**1. 分层。** 会话内靠上下文窗口；session 结束用钩子生成两三句摘要（episodic），回答"上周做到哪了"；跨会话的偏好和事实单独存（semantic），这是本文重点。

**2. 结构化。** 偏好不要存自由文本，一条一个原子事实：

```json
{
  "category": "coding",
  "key": "commit_message_language",
  "value": "zh-CN",
  "source": "explicit",
  "confidence": 0.95,
  "updated_at": "2025-06-01",
  "hit_count": 17
}
```

`source` 区分显式与推断，`confidence` 决定它能不能被注入。

**3. 写入闸门。** 显式偏好（"以后都……"）高置信直写；推断偏好必须满足"同类行为 ≥3 次且无反例"才升级 confidence。同 key 新值覆盖旧值、旧值留历史，绝不让"用 npm"和"用 pnpm"同时存在。

**4. 读取策略。** 会话启动时按 category + 关键词粗筛，向量精排取 top-N，硬性预算 500 token 以内。宁缺毋滥：漏掉的偏好用户会再说一遍，代价远小于注入一堆错误约束。

**5. 修正与遗忘。** 提供 `/memory list`、`/memory del` 这样的显式出口，用户能看、能删，这是信任的基础。每条记忆记录被纠正次数，连续两次被纠正自动降权。

## 踩坑点

- **任务上下文混进偏好**："现在在做什么"进 episodic，"一直希望怎样"才进 semantic，这条规则要写死在抽取 prompt 里。
- **推断生效太快**：连续两天用某个库 ≠ 想永久切换，置信门必须卡住。
- **矛盾记忆不合并**：新旧偏好同时被召回，模型行为会精神分裂，merge 逻辑不能省。
- **注入过多导致僵化**：有段时间我注入了 80 条偏好，结果助手连我随口提的临时方案都不敢换。

## 可复用建议

- 先跑两周"仅显式记忆"，再放开推断，成本最低。
- schema 里 `source` / `confidence` / `updated_at` 一个都别省，后续所有策略都依赖它们。
- 把记忆做成独立的 MCP server（search / save / delete 三个工具），别写死在某个 agent 里，换模型、换前端都能复用。
- 观测两个指标：偏好命中率、被纠正率。没有指标就没法调阈值。

## 总结

记忆系统不是玄学，是保守写入、按需读取、可审计的数据工程问题。先让用户能看见和删除，再谈智能化——宁可记不住，不要记错。
