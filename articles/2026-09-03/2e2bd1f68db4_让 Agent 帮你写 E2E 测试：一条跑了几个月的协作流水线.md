## 背景

E2E 是最“该写但最不想写”的一层测试：用例长、选择器脆、维护贵。多数团队只在核心链路铺一小段 Playwright，其余靠人肉回归。直接“丢个 URL 让模型生成测试”我们都试过，产物基本是能跑但什么都没验证的冒烟脚本。后来我们在 OpenClaw 里用多 Agent 加 MCP 工具搭了一条流水线，稳定跑了几个月，这里记录做法与教训。

## 问题

让模型裸写 E2E，典型失败模式有三个：

1. **断言空洞**——只验证“页面打开了”，不验证业务结果；
2. **选择器脆弱**——照搬快照里哈希化的 class，一次构建就挂；
3. **幻觉 API**——调用当前版本不存在的方法，或者自己 mock 自己。

更深一层：测试“通过”不等于“有效”。永远绿的流水线比没有测试更危险，因为它制造虚假信心。所以这条流水线的设计目标不是“生成代码”，而是“生成可被证伪的用例”。

## 做法：四步流水线

在 OpenClaw 里拆成四个角色编排：

**1. 约定先行。** 写一份 `test-conventions.md`：选择器优先级 data-testid > role > 文本；禁止 sleep；每条用例必须断言至少一个业务不变量（订单状态、余额变化、跳转结果）；测试数据自建自清。该文件注入后续所有 Agent——约定即代码。

**2. 探索 Agent 产出流程规格。** 给它挂 Playwright 的 MCP server，限定 staging 环境和测试账号，沿目标链路（如“优惠券下单”）走一遍，输出结构化 `flow-spec.json`：每步用户动作、关键 DOM 状态、网络请求、业务不变量。这是全流水线最重要的人工可审产物——人在这层纠正 Agent 对业务的理解，成本最低。

**3. 写测 Agent 生成用例。** 输入 flow-spec + 约定文件 + 两三个存量“金标准”用例做 few-shot，输出 Playwright spec。生成后立刻跑 TypeScript 编译和一次真实执行，报错与 trace 回喂修复，最多 3 轮。

**4. 审查 Agent + 变异验证。** 逐条检查：有无断言、断言是否绑定不变量、是否依赖前置数据。然后做关键一步：在 staging 临时破坏一个返回值（或改 mock），确认相关用例真的会红。“测测试”能抓住大部分空洞用例。

全程 Agent 只开 PR，合入权在人。

## 踩坑点

- **选择器漂移**：即使约定写明，模型偶尔仍抄 class。加了 lint 规则禁 `locator('.xxx-hash')` 形式，CI 直接挡。
- **数据污染**：早期用例在 staging 留下垃圾订单互相干扰。现强制每条用例通过 API fixture 建数、teardown 清理。
- **迭代失控**：修 trace 偶尔死循环（改 A 坏 B）。给修复 Agent 设了轮数与 token 预算上限，超限转人工。
- **幻觉 API**：把项目锁定的 Playwright 类型定义喂进上下文后基本消失，TS 编译回喂兜底。
- **别全站铺量**：先挑登录和核心交易两条高价值链路，跑顺再扩。

## 可复用建议

1. `flow-spec` 这层中间产物值得专门设计：它解耦探索与生成，也是人介入的最优点。
2. 约定写成文件而非口头规则，Agent 与新同事读同一份。
3. 变异验证成本极低、收益极高，凡 AI 生成测试的场景都该加。
4. 修复循环放 CI、合入权留人，这条边界别让。
5. 验收标准一句话：删掉被测功能，它必须红。

## 总结

跑下来，Agent 承担了约七成机械工作（样板、选择器、fixture、修 trace），人保留两件事：定义业务不变量，以及判断“这条测试值不值得存在”。这套东西的价值不在模型本身，而在约定文件和流程规格这两个可沉淀、可 review 的资产上。工具会换代，资产不会。
