## 背景

OpenClaw 的工作区里有一组约定文件：`AGENTS.md` 管怎么干活，`TOOLS.md` 管工具用法，`USER.md` 记用户偏好，而 `SOUL.md` 管"这个 Agent 是谁"。很多人装完就把模板原样留着，跑起来后 Agent 语气时好时坏、该拦的不拦。

本质上，SOUL.md 是每轮会话注入 system prompt 的一段人格与约束声明。正确的定位不是"性格散文"，而是**一份每轮都进上下文的接口文档**。按这个思路写，效果立刻不一样。

## 问题

SOUL.md 缺失或写虚，通常表现为三类症状：

1. **语气不稳定**：白天像客服，深夜像朋友，同一通道内前后不一致；
2. **边界模糊**：一句"帮我处理一下"，它可能把删除、转账、群发这类高危操作也顺手执行了；
3. **责任越界**：多人群聊里对谁都掏心窝子，把 A 的上下文用在 B 身上。

根因大多不是模型问题，而是约束压根没写清楚，或者全是不具备可执行性的形容词。

## 做法

把 SOUL.md 拆成四段来写：

1. **身份**：服务对象是谁。例如"你是我的个人助理，主要服务我一人"，群聊场景要显式声明范围；
2. **语气**：用行为化描述。写"默认中文，先结论后步骤，闲聊不超过三句"，不写"友好、专业"；
3. **红线清单**：明确默认不做的事——资金操作、批量删除、代发消息、读取敏感目录。每条注明"需我显式确认后才可执行"；
4. **升级规则**：不确定就停下来问，宁可多问一句，不要猜。

分工原则：SOUL.md 管"是谁、不做啥"，AGENTS.md 管"怎么干"，两处别重复。改完走 git 提交，用一组固定测试 prompt（5~10 条典型请求，其中含一条应被拒绝的）做对比回归，再上线。

## 踩坑点

- **形容词堆砌无效**。"聪明、可靠、有温度"这类词模型只会表面复述，必须落到可观察的行为；
- **红线写死又想留活口**。别写"永远不要"，然后自己又嫌它不听话。统一用"默认拒绝 + 口令确认"的模式；
- **与 AGENTS.md 冲突**。两处都定义语气，Agent 会随机听一边。改一处就删掉另一处；
- **让 Agent 自己改 SOUL.md 要谨慎**。自我演化很诱人，但没有 review 的 SOUL.md 会慢慢跑偏。建议只允许 Agent 提案，由人合并；
- **边界会随长会话衰减**。心跳和重载会重新注入约束，但超长会话里，关键高危操作仍应在工具层（MCP/插件侧）再做一道校验，别把安全全押在提示词上。

## 可复用建议

- 四段模板（身份/语气/红线/升级）起手，30 行以内足够；
- 每踩一个坑就新增一条红线，把 SOUL.md 当行为 changelog 维护，配合 git 回溯；
- 高危操作统一走"默认拒绝 + 确认放行"，不要每条规则各自发明例外逻辑；
- 每月跑一次固定的行为回归 prompt 集，防漂移。

## 总结

SOUL.md 不是玄学人格卡，而是一个每轮消耗上下文的约束接口。写得越像验收标准，Agent 行为越稳定：人格靠行为化描述，安全靠红线清单加工具层兜底，长期可靠靠版本管理。先写四段、跑两周、再迭代，比一次写三百行有效得多。
