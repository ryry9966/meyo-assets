## 背景

大多数 Agent 的默认形态是被动应答：你不发消息，它就静止。但个人助理、服务看护这类场景里，真正有价值的恰恰是"没人的时候它也在看"。OpenClaw 用一个非常轻的机制解决这个问题：心跳（heartbeat），核心载体就是工作区里的 `HEARTBEAT.md`。

## 问题

"主动"做起来很容易变味：

- 用传统 cron 硬编码，逻辑僵化，稍微一点判断就要写一堆脚本；
- 让 Agent 自由发挥，它又可能每次心跳都"汇报点什么"，频繁打扰还烧 token。

`HEARTBEAT.md` 的设计意图就是取中间：把判断权交给模型，把边界用清单写死。

## 做法

三步：

1. 在工作区根目录创建 `HEARTBEAT.md`（例如 `~/.openclaw/workspace/HEARTBEAT.md`）；
2. 写任务清单，每条任务尽量包含：触发条件、动作、跳过条件；
3. 在配置中调整心跳间隔（不同版本字段略有差异，默认约 30 分钟）。

运行机制：每次心跳触发时，`HEARTBEAT.md` 的内容被注入上下文，Agent 逐条评估。没事可做时回复 `HEARTBEAT_OK`，网关会吞掉这条回复，用户完全无感；有事时才会真正行动——发消息、调工具、走 MCP。

一个可直接抄的骨架：

```markdown
# 心跳任务
- 检查 GitHub Actions：仅当有失败的 workflow 时汇总名称并通知我，否则跳过。
- 服务器磁盘：用量 > 85% 才报告，低于阈值一律跳过。
- 每天 08:00–21:00 之外不做任何事，直接 HEARTBEAT_OK。
- 低优先级信息先攒着，凑满一次 digest 再汇报。
```

## 踩坑点

- **指令含糊**："帮我留意邮件"这类写法会让 Agent 每个周期都觉得"有事"。必须写清什么算有事、什么直接跳过。
- **任务不自包含**：心跳上下文和主会话不完全一样，依赖长对话记忆的任务会悄悄失效。每条任务要假设它是"从零醒来"。
- **成本**：即使最终只回一句 `HEARTBEAT_OK`，每次心跳也是一次真实的模型调用。间隔别调到分钟级，清单控制在 10 条以内。
- **高危操作**：删文件、对外发消息这类需要确认的动作不要放进心跳，至少写成"仅报告、不执行"。
- **调试等待**：改完 `HEARTBEAT.md` 要等下一个周期才生效，验证时别干等，把间隔临时调短或手动触发一次。

## 可复用建议

- 把它当 SOP 写：每条任务固定"条件 / 动作 / 报告格式"三段式；
- 低优先级信息合并成 digest 一次说完，这是控制打扰的关键；
- 复杂调度交给 cron 或 MCP 触发，心跳只做轻巡检和汇总，两者别混；
- 定期看日志里 Agent 在心跳中实际做了什么，防止行为漂移；
- 每月清理一次清单，删掉过时任务——它和 crontab 一样会腐化。

## 总结

`HEARTBEAT.md` 不是什么调度框架，本质是把一张"值班巡检表"交给一个会判断的执行者。它的上限不取决于机制，而取决于你有没有把"什么算有事、什么算没事"写清楚。写清楚了，Agent 的主动性才是可用且可控的。
