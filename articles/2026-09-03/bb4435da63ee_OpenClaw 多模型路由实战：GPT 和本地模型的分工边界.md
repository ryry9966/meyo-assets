## 背景

OpenClaw 的架构决定了它天生适合多模型：它跑在你自己的机器上，云端 GPT/Claude 和本地 Ollama、LM Studio 都只是配置里的一行模型引用。很多人的第一版配置是“全走云端”，一个月后账单劝退；第二版是“全走本地”，然后发现稍微复杂点的工具链任务就翻车。多模型路由，就是在两者之间找一条工程上说得过去的中间路线。

## 问题

任务特征其实分三档：

- 闲聊、消息摘要、文本分类：本地 7B~14B 完全够，数据还不出口；
- 写代码、多步工具调用、长上下文阅读：云端大模型在指令遵从和 function calling 稳定性上仍有明显优势；
- 涉及隐私数据的任务：哪怕质量降一档，也应该留在本地。

单模型配置没法同时满足这三条，所以路由的核心是把“任务特征”映射到“模型能力”。

## 做法

1. **定两档**。primary 给云端（如 `openai/gpt-4o`），second 给本地（如 `ollama/qwen2.5:14b`），先别上第三档。
2. **全局配兜底，agent 单独绑定**。在 `~/.openclaw/openclaw.json` 里给默认 agent 配 primary + fallbacks；再按用途拆 agent——“日常问答/摘要” agent 绑本地，“编码/工具密集” agent 绑云端。
3. **判断标准固定成三条**：是否依赖稳定的工具调用、上下文是否超过本地窗口、是否含敏感数据。第三条优先级最高。

```jsonc
// ~/.openclaw/openclaw.json（节选，JSONC 格式，允许注释）
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "openai/gpt-4o",
        "fallbacks": ["ollama/qwen2.5:14b"]
      }
    }
  }
}
```

（字段名以你实际版本的文档为准，改完记得重启 gateway。）

## 踩坑点

- **本地模型的工具调用可靠性**。小参数模型 schema 遵从差，工具循环可能卡死或反复调用。选明确支持 function calling 的模型，参数量别低于 7B，换模型前先用几条测例过一遍。
- **上下文窗口静默溢出**。本地 8k/32k 在长会话里很快耗尽，报错未必直观，外在表现是“回答突然变蠢”。长会话要定期重置。
- **静默降级**。本地模型返回格式坏了但不报错，fallback 悄悄切到云端，账单月底才发现异常。务必给模型切换加日志，每周看一次。
- **配置格式**。openclaw.json 是 JSONC，带注释，用纯 JSON 校验器会报错；改完不重启不生效，旧会话可能还挂在旧模型上。

## 可复用建议

- 先用“两档制”跑两周，看用量统计里两档的真实分布，再决定要不要加档；
- 云端当兜底而不是默认，方向是“默认本地、失败升级”，而不是反过来；
- 维护一个 10 条左右的工具调用小测例集，作为更换本地模型前的回归测试；
- 敏感数据走本地这件事，靠 agent 绑定来强制，不要依赖提示词自觉。

## 总结

多模型路由不是省钱小技巧，而是任务与能力的匹配问题。OpenClaw 的好处是整个路由都在你自己的机器上，改一行配置就能灰度验证，试错成本几乎为零。先用最笨的两档策略跑通闭环，再谈精细化——大多数个人场景，两档已经够用。
