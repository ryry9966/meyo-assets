## 背景

OpenClaw 的 agent 本身只会两件事：推理和调用工具。所有"真实世界"的能力——查数据、发消息、操作文件系统之外的任何东西——都来自外部 API。所以 agent 的能力边界，本质上就是它握得到手的 API 边界。这篇帖子记录我把几个外部服务接进 OpenClaw 的过程，重点不是某个具体服务，而是那条可以复用的对接路径。

## 问题

直接上手通常会遇到三个典型问题：

1. **语义不通**。API 文档是写给工程师看的，参数命名、错误码、分页逻辑都不是模型天然理解的语言。
2. **上下文是稀缺资源**。一个返回几 KB JSON 的接口，原样喂给模型，几次调用就把会话撑爆。
3. **安全边界模糊**。密钥放哪、日志记什么、agent 能否自主触发有副作用的操作，都需要事先想清楚。

## 做法

OpenClaw 对接外部服务主要有两条路：**skill**（模型可读的说明 + 可执行脚本）和 **MCP server**（标准化工具协议）。我的选型原则很简单：一次性的内部脚本用 skill；要跨项目复用、或社区已有现成实现的服务用 MCP。

具体步骤：

1. **先用 curl 走通 API**。接 agent 之前，手工确认鉴权方式、必要参数、返回结构。这一步省下的调试时间远超投入。
2. **写薄适配层**。无论 skill 脚本还是 MCP tool，只做三件事：注入凭证、裁剪返回体（只留模型需要的字段）、把错误码翻译成一句人话。业务逻辑留在适配层内部，不进 prompt。
3. **认真写工具描述**。参数说明要写成"给新同事的交接文档"：什么类型、什么格式、什么场景该用这个工具。描述质量直接决定调用准确率。
4. **设超时和重试**。网络调用默认 30 秒超时；写操作考虑幂等，避免 agent 重试造成重复副作用。
5. **小步验证**。接入后先在受控会话里跑几个典型任务，观察参数传递和错误恢复，再放开日常使用。

## 踩坑点

- **工具描述含糊是误调用的头号原因**。我曾把两个相似工具的描述写得太接近，agent 频繁选错。在描述里明确"用于 X 场景，不要用于 Y"后立刻好转。
- **返回体不裁剪**。某列表接口默认返回 100 条记录，模型拿到后开始幻觉式总结。裁到前 5 条加总数，问题消失。
- **密钥进上下文**。早期我把 token 写在配置示例里，一次调试日志全打出来了。现在凭证只走环境变量，适配层内做了脱敏。
- **无超时的长请求**。一个报表接口偶尔跑 3 分钟，agent 会话整个卡住。加超时 + 异步任务轮询后解决。
- **写操作没有确认环节**。让 agent 直接调写入接口风险很高，我在适配层加了 dry-run 参数，写操作默认只预览。

## 可复用建议

- 适配层保持"薄"：转换、裁剪、翻译错误，三件事之外不做更多。
- 每个 tool call 落日志：入参、出参摘要、耗时。排障时这是唯一可靠的依据。
- 工具数量克制：agent 面对几十个工具时选择准确率明显下降，按场景拆分 skill 比堆一个大而全的工具集有效。
- 错误信息写给模型看，不是写给人看："start_date 应为 YYYY-MM-DD 格式"远比 "400 Bad Request" 有用。

## 总结

对接外部服务的核心不是"让模型会调 API"，而是替模型把 API 包好：鉴权收进环境、返回裁到最小、错误翻译成人话、副作用加上闸门。OpenClaw 提供了 skill 和 MCP 两条路径，选哪条不关键，关键是适配层的质量——它决定了 agent 是"能用"还是"可靠"。先手工走通，再写薄适配，最后小步放量，这套流程接任何服务都适用。
