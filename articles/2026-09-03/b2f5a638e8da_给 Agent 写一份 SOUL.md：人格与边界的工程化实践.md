## 背景

OpenClaw 的 Agent 不是每次调用都"裸奔"的模型：workspace 里的一组 Markdown 文件会在会话启动时注入上下文，`SOUL.md` 就是其中定义"我是谁"的那份。它不改模型参数，而是用可版本管理的方式塑造行为——本质上是一段持续生效的 system prompt，改动成本几乎为零。

## 问题

没有 SOUL.md 时，我踩过三类麻烦：

1. **人格漂移**：Telegram 上简洁直接，CLI 里又变成啰嗦的客服，隔几天口吻再变一次。
2. **边界模糊**：Agent"热心"过头——主动给联系人发消息、没确认就执行删除命令、工具调用失败时编个结果圆场。
3. **不可协作**：行为像抽卡，没法 review，也没法回滚。

## 做法

我的 SOUL.md 固定五段，控制在 40 行以内：

1. **身份**：一两句。给谁服务、以什么姿态说话。
2. **语气**：写具体行为而不是形容词。"回复不超过 5 句，先结论后细节"远比"简洁友好"有效。
3. **语言**：跟随用户语言回复，中文语境不夹英文。
4. **边界**：负向且可执行，一条对应一个动作。
5. **升级规则**：什么情况必须问人，而不是自己猜。

示例片段：

```markdown
# 边界
- 未经确认，不执行删除/覆盖类命令
- 不向通讯录以外的联系人发消息
- 工具调用失败时如实说明，不编造结果
```

写完用 git 管理，改动走 commit + diff；改完 `/new` 开新会话验证。建议备三个固定测试 prompt：一个过去导致话痨的、一个诱导越权的、一个中英混合的，每次修改后跑一遍。

## 踩坑点

- **只写"不要做什么"，不给替代动作**。模型会过度谨慎，正常请求也频繁确认。负向规则后补一句"应改为：先复述命令再请求确认"。
- **写成小作文**。SOUL.md 每个会话都占上下文，超过 50 行收益急剧下降。过程性规则（部署流程、目录约定）放 AGENTS.md，别和 SOUL.md 重复。
- **改了没生效**。进行中的会话不会自动重读，需要 `/new` 或重启 gateway，否则你会怀疑人生。
- **把它当沙箱**。SOUL.md 是提示层约束，拦不住真越权。删库、发消息、扣费这类硬边界要落在工具层：allowlist、exec 审批、gateway 权限。提示词是第一道防线，不是唯一一道。
- **多 Agent 场景改错文件**。每个 Agent 有独立 workspace，先确认路径再动手。

## 可复用建议

- 分层存放：稳定人格放 SOUL.md，用户事实放 USER.md，事件流水放 MEMORY.md。
- 规则冲突比没有规则更糟，写完通读一遍，"简洁"和"逐步详细解释"不能同时出现。
- 用 Agent 自述验收：让它描述自己的语气和红线，与 SOUL.md 逐条对照，偏差大的条目说明写法有问题。

## 总结

SOUL.md 的价值不在"给 AI 注入灵魂"这类叙事，而在于把 Agent 行为中最不稳定的部分，变成一份可 review、可回滚、可测试的文本。二十行写清楚的边界，胜过两百行的抒情。建议从自己最近一次踩坑记录开始写，比抄模板有效得多。
