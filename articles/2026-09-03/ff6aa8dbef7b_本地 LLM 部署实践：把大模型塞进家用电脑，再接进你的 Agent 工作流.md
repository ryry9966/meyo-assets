## 背景

跑 Agent 自动化的同学大多遇到过这几个场景：脚本要处理私人数据（聊天记录、本地文件、内部笔记），不想传给云端；Agent 循环几十轮，token 账单肉眼可见地涨；或者单纯希望断网时流程也能跑。这时候本地模型的价值就出来了——不是替代云端，而是作为流程里的一个可控节点。

## 问题

落地前有三个绕不开的问题：

1. **我的机器能不能跑？** 显存/内存决定上限；
2. **选哪个模型？** 中文能力、指令遵循、工具调用质量参差不齐；
3. **它能不能稳定地做 function calling？** 这是对 Agent 用户最关键、也最容易被忽略的一条。聊天聊得好，不代表工具调用参数生成得稳。

## 做法

**第一步：盘点硬件。** 粗略估算（Q4 量化）：7B 约占 5GB，14B 约占 9GB，32B 约占 20GB。有独立显存优先用显存；Mac 统一内存跑 14B/32B 也相当可用。纯 CPU 能跑，但 Agent 多轮循环下延迟会很难受。

**第二步：选运行时。** 推荐从 Ollama 开始：一条命令拉模型，自带 OpenAI 兼容接口（默认 `:11434/v1`），后续接任何框架都方便。需要精细控制再下沉到 llama.cpp。

**第三步：选模型。** 中文 + 工具调用场景，Qwen 系列是目前稳妥的起点。建议路径：先跑 7B/8B 级别验证管线通不通，再用真实任务评估是否值得升到 14B/32B。

**第四步：接入 Agent。** 把 base_url 指到本地端点，重点验证三件事：工具 schema 是否被正确解析、多工具选择是否准确、长 system prompt + 工具定义是否撑爆上下文。

**第五步：用真实任务压测。** 把你的典型 Agent 任务跑 20 遍，统计工具调用失败率和参数错误率——这比任何排行榜都诚实。

## 踩坑点

- **量化档位别压太狠。** Q4 以下，模型输出 JSON 工具参数时容易缺字段、混入多余文本。Agent 用途建议 Q4_K_M 起步，重要节点上 Q5/Q6。
- **上下文窗口要显式设置。** 运行时常有默认的短上下文，Agent 的 system prompt + 工具定义很容易超。设大 `num_ctx` 的同时注意 KV cache 的额外显存开销，别只看模型权重占用。
- **不是所有模型都支持并行/多工具调用**，有些会输出被 markdown 包裹的 JSON，解析层要做容错。
- **别迷信跑分。** 32B 在你自己的流水线里输给调教得当的 14B，是常发生的事。

## 可复用建议

- **建一个私有评测集**：10~20 条真实 Agent 任务，每次换模型/换量化跑一遍当回归测试。
- **路由模式**：简单分类、抽取步骤交给本地小模型，规划与复杂推理走云端，成本和延迟都能砍掉一大截。
- **版本钉死**：模型版本、量化档、运行时 commit 记进一张模型卡，避免"上周还好好的"式排障。
- 笔记本注意散热，持续推理会降频，长任务跑之前先做 10 分钟稳定性观察。

## 总结

家用电脑跑 7B~32B 模型在今天已经是工程上成熟的事，但对 Agent 用户来说，真正的门槛不是"能不能跑起来"，而是"工具调用稳不稳"。建议从小模型起步、用真实任务评估、按难度路由——本地模型是工作流里的一个零件，选零件的标准是适配，不是参数量。
