## 背景

E2E 测试大概是团队里最没人爱写的部分：用例长、选择器脆、UI 一改全红。最近我把 Playwright 的 MCP server 接进 OpenClaw，让多个 agent 分工协作来生成和维护 E2E 测试，跑了几轮真实迭代后流程基本稳定，这里记录一套可复制的做法。

## 问题：一把梭生成的测试基本不能用

最直觉的用法是把需求文档丢给模型，说"帮我写个 Playwright 测试"。实际效果通常很差：

- **选择器靠猜**：模型没见过你的页面，会写出 `.btn-primary > div:nth-child(2)` 这种东西
- **断言注水**：模型倾向写"能通过"的断言，比如只验证元素可见，不验证数据正确
- **修不动**：跑挂之后把报错扔回去，模型开始盲改等待时间，越改越脆

根因只有一个：模型缺少对真实页面结构的感知。所以核心思路是——先让一个 agent 去看，再让另一个去写，最后一个专门负责跑和修。

## 做法：三角色流水线

**1. 探索 agent（Explorer）**
通过 MCP 打开目标页面，不做乱点乱试，而是按用户路径遍历关键流程（登录 → 核心操作 → 结果页）。每一步导出 accessibility snapshot（不是截图），拿到真实的 role、name 和层级结构，输出一份结构化的"页面地图"。

**2. 编写 agent（Writer）**
输入是页面地图 + 用户故事 + 团队测试规范，并带上硬性约束：

- 只允许 `getByRole` / `getByTestId`，禁止 CSS 路径选择器
- 每个用例必须包含至少一条业务断言（数据或状态），不能只有可见性断言
- 测试数据走独立 fixture，禁止写死共享账号

**3. 修复 agent（Runner）**
负责执行与修复。失败时只截取失败步骤前后的 trace 片段喂给模型——不要整份 trace，上下文会被噪音淹没。限定最多 3 轮修复，超过就打回人工，并附上失败归因摘要。

在 OpenClaw 里我把这三个角色封装成 skill，用子 agent 串行调度，跑完把代码 diff 和归因摘要推到群里等人审。

## 踩坑点

- **截图代替快照**：截图直观，但模型从像素里"脑补"选择器，错误率极高。一律用 accessibility snapshot。
- **弱断言混过关**：AI 生成的测试第一次全绿未必是好事。逐条人审断言是否表达了业务意图，记住"可见 ≠ 正确"。
- **测试数据污染**：agent 很爱复用同一个测试账号，导致用例间顺序敏感、连锁失败。规范里必须强制每次独立造数。
- **无限修复循环**：不设上限的话，agent 会反复微调 timeout 把 flaky 用例"修绿"。三轮上限 + 归因打回，比无限重试健康得多。
- **直接进 CI**：agent 产出的用例应先在本地隔离环境稳定跑若干次再入 CI，否则 flaky 会透支团队对整套测试的信任。

## 可复用建议

- 把"探索 → 生成 → 修复"沉淀成固定 skill / prompt 模板，角色分工越固定，产出越稳定
- 维护一份团队级断言清单（登录态、权限边界、金额精度这类必查项），作为 Writer 的强制输入
- 给 agent 产出的用例加统一前缀，定期统计"AI 用例存活率"，用数据决定要不要扩大使用范围

## 总结

Agent 写 E2E 测试的价值不在"全自动"，而在于接管最耗时的两段——摸清页面结构和修 flaky；断言的业务语义仍然留给人来把关。整套方案只依赖 MCP 浏览器能力和三个分工明确的 agent，任何支持 MCP 与子 agent 的框架都能照搬。建议先拿一条核心路径试点，跑顺了再铺开。
