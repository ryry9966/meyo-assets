最近科技圈流传一个挺唬人的说法：Runway 把代码"干掉了"。据 36kr 等媒体报道，这家以视频生成闻名的公司拿出了首个面向"界面"的世界模型——你描述一个需求，界面就自己长出来；你点一下按钮，模型实时算出下一个画面。没有前端工程，没有 React 组件，甚至没有一行传统意义上的代码。"代码已死"是标题党的夸张，还是真拐点？这篇把它拆开看。

![cover](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-03/890de8252895079e.png)

## 一、世界模型是什么：一个会"预判"的模拟器

World model 不是新词，它的谱系可以这样捋：

- 2018 年，Ha 与 Schmidhuber 发表经典论文《World Models》，用 VAE 加 RNN 让模型在"自己的梦里"学会打 Doom 风格的射击游戏——规则没人写，是模型从像素流里自己总结的。
- 之后 DeepMind 的 Dreamer 系列把它做成机器人控制的标配思路：先在模型的"想象"中推演，再到现实中行动。
- 2024 年 DeepMind 的 Genie 2 展示了更激进的玩法：给一张图，直接生成能走来走去的 3D 小世界；Google 的 GameNGen 则用扩散模型在 TPU 上跑起了《毁灭战士》，约 20fps。
- 它们的共同抽象只有一行：`s_{t+1} = f(s_t, a_t)`。给定当前状态和你做的动作，预测下一帧。区别在于：物理引擎是显式规则加精确计算，世界模型是从海量数据里学出来的统计规律。

Sora 这类视频模型已经隐式学到了一些物理直觉。Runway 的思路更进一步：既然能模拟物理世界，能不能直接模拟"软件世界"？

## 二、Runway的关键一步：把"世界"换成"界面"

![img1](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-03/8a35e3470c9472a2.png)

这是整件事最巧的地方。以前的 world model 都在啃物理世界这块硬骨头——重力、碰撞、水面。而软件界面其实是绝佳的"模拟对象"：

- **结构高度重复**：导航栏、按钮、表单、列表、抽屉菜单，翻来覆去就这几类模式，数据分布集中，远比开放物理世界好学。
- **交互语义清晰**：点击、输入、拖拽，动作空间有限，模型要学的"因果"相对单纯。
- **难点在文字**：界面里全是文字和数字，而扩散模型恰恰最容易把字糊掉、把数弄错——这是它必须迈过的坎。

它和此前"生成式 UI"的区别值得说清楚。过去的 generative UI 是 LLM 写前端代码、浏览器再渲染，中间仍隔着代码层；Runway 的做法是跳过代码，逐帧直接生成像素加交互——界面不是被"渲染"出来的，是被"想象"出来的。你描述一个记账工具，它的界面按需生长；你点"导出"，模型预测出下一个该出现的画面。软件第一次表现出一点"生物性"。

## 三、"代码被干掉了"？先算一笔账



标题很带感，但工程师的直觉应该先看账本。代码至少在三件事上仍然碾压：

- **确定性**：类型系统、单元测试、数据库事务，保证银行扣款精确到分。世界模型是统计规律，"大概对"在这里不值钱——如果模型给你的账户余额"幻觉"出一个数，你大概率不会觉得它浪漫。
- **成本**：执行一段 if-else 便宜得像白开水，单次调用近乎零成本；而扩散模型逐帧推理，交互级帧率意味着一个用户会话要持续占着一张 GPU。参考 GameNGen 用一整块 TPU 才跑出 20fps，粗略估算，两边成本差着两三个数量级。
- **可验证与合规**：金融、医疗、航空软件要审计、要日志、要无障碍适配。你怎么给一个"每次长得不太一样"的界面写验收标准？

所以更准确的结论是：被干掉的不是代码，而是"手写界面壳子"这个环节。数据、业务逻辑、权限、事务，这些"魂"依然是确定性代码的地盘；被生成的是"壳"，也就是呈现层与交互层。前端没有消失，它被压缩到了更薄、但更关键的一层。

## 四、哪些场景会先被改变：一个四问判断框架

![img2](https://cdn.jsdelivr.net/gh/ryry9966/meyo-assets@main/images/2026-09-03/90d322a3fde9dba9.png)

判断一个场景适不适合"生成式界面"，可以连问四个问题：

1. **错误容忍度**：错了会亏钱、出事故吗？支付后台不行，头脑风暴用的原型很行。
2. **复用频率**：一次性小工具，生成比开发划算；每天亿级调用的核心链路，代码依然便宜又稳定。
3. **状态复杂度**：购物车、账本这类需要精确长期记忆的状态，后端必须确定性实现。
4. **个性化价值**：不同人需要长得不一样的界面时，生成的优势最大——无障碍场景尤其典型，比如为低视力用户实时调整对比度和布局。

按这个框架推演，先被改变的大概率是：设计与原型（需求描述直接变成可点的原型，前端交接流程被大幅压缩）、一次性内部工具、演示与教育内容，以及"长尾软件需求"——绝大多数"要是有个小工具就好了"的念头，过去因为开发成本太高，永远停留在念头阶段。

对从业者来说，真正的变化是角色迁移：从"写组件"转向"定约束"——把设计系统、数据契约、验收标准写成生成器能执行的护栏（guardrails）。工具会越来越像园艺：你负责修枝和篱笆，生长交给模型。

## 五、三条冷思考



1. **别急着开除前端。** 像素级生成离生产可用还差确定性、成本、可测性三道坎，短期内它自动化的是"壳"，不是"魂"。真正该焦虑的不是岗位消失，而是自己的技能构成要不要换血。
2. **约束表达能力会升值。** 把"什么必须绝对正确"写成 schema、设计系统和测试，可能比手写组件更值钱。会用生成器的人会很多，能给生成器划边界的人很少。
3. **盯成本曲线，别盯发布会。** GPU 推理成本确实每年在降，但要再降两三个数量级才可能挤进日常应用。技术的时间表从来不由 demo 决定，而由单位成本决定——这是过去十年所有"取代 X"的故事里，最可靠的一条规律。

界面自己长出来这件事，短期看是原型工具的一次升级，长期看是软件形态的一次试探：从"造物"变成"培育"。代码不会死，但它可能退到幕后，像今天的汇编一样，成为少数人维护的地基。
