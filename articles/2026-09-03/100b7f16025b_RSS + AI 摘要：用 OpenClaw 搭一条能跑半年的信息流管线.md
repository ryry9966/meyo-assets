## 背景

信息源越来越散，算法推荐不可控，RSS 虽老但仍是唯一可编程、可审计的信息源。OpenClaw 恰好补齐了剩下几块：定时任务、skill/MCP 工具生态、以及直接把结果推进聊天渠道的能力。目标不是"让 AI 替我读一切"，而是把每天两三百条原始条目，压成十几条值得点开的线索。

## 问题

直接丢一句"每天帮我看看 RSS"给 Agent，前两周基本都会失败，原因很朴素：抓取不稳定、全文拿不到、摘要没标准、成本失控。这事得当成一条管线来建，而不是一个一次性 prompt。

## 做法

1. **选源**：控制在 5–10 个 feed，优先官方源；没有 RSS 的站点用 RSSHub 自托管补齐。别贪多，源数量和噪音成正比。
2. **抓取落库**：在 OpenClaw 挂一个每日定时任务，调用 RSS 解析的 skill 或 MCP 工具，把 title、link、published、content 全量写入本地 SQLite。主键用 link 的 hash，天然去重。
3. **预过滤**：先用关键词、来源白名单做粗筛，正文太短的直接跳过。这一步决定后面的 token 账单。
4. **摘要**：过滤后的条目按 5–10 条一批喂给模型，prompt 强约束输出 JSON：一句话摘要、主题标签、0–10 相关度。单条解析失败就单独重试，不要整批重来。
5. **投递**：按相关度排序拼成 Markdown 日报，经渠道插件推到 IM，同时归档一份到笔记目录，方便回溯。

## 踩坑点

- **很多 feed 只有 summary 没有全文**。拿截断文本去摘要，模型会一本正经地编内容。必须接一步正文抽取（readability 类工具），抽不到全文的条目只保留标题摘要，宁可少不可编。
- **定时任务会重叠**。摘要跑得慢，上一次没结束下一次又触发，结果重复推送。加一个简单的运行锁，或把 cron 间隔放宽。
- **模型输出格式漂移**。JSON 外面裹一层 Markdown 代码块是常态，解析器要容忍 \`\`\`json 包裹，并保留原始输出日志便于排查。
- **跨源重复**。同一件事三家都报，按标题做相似度合并，日报里只留一条。
- **RSSHub 公共实例经常超时**，重要的源建议自己跑一份。

## 可复用建议

- **阶段解耦**：抓取、过滤、摘要、投递各自独立、可重跑，中间态全部落盘。摘要模型随时可换，原始数据不受影响。
- **prompt 当配置文件**管理，进 git，改动可回滚、可对比。
- **记录每次摘要的 token 消耗**，成本不可见就会失控。
- **先跑最小闭环**：3 个源、每天一次，稳定运行两周后再加源、加渠道。

## 总结

这条管线代码量不大，真正的工作量在数据契约（落库字段、摘要 schema）和失败处理上。跑顺之后，每天早上收到一条一分钟内能扫完的日报，剩下的时间留给真正值得深读的东西。自动化管线的价值不在花哨，而在三个月后你还在用它。
