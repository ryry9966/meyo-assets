## 背景

单个 agent 处理长任务时有两个绕不开的瓶颈：一是上下文窗口被中间过程占满——读几个文件、跑几轮命令，真正做决策时上下文已经被无关细节污染；二是任务只能串行，所有等待时间叠加。把结构改成「一个主 agent 负责调度 + 若干 subagent 负责执行」，是我在 OpenClaw 日常自动化里用得最多、收益也最稳定的模式。

## 问题

- 主 agent 亲自干所有细节活，上下文膨胀后决策质量明显下降；
- 无依赖的任务被迫排队，比如「审查 10 个模块 + 生成部署文档 + 补测试」串行要等三倍时间；
- 子任务失败没有显式上报，主 agent 拿到残缺结果继续走，最终产出不可信。

## 做法

1. **划分职责。** 主 agent 只做三件事：拆任务、下发、汇总。所有读文件、搜代码、跑脚本的细节活下放给 subagent。
2. **每个 subagent 独立上下文。** prompt 里写清：输入是什么、期望输出格式（尽量 JSON 或固定段落）、失败时必须报 `error` 字段而不是编一个结果。
3. **按依赖关系排拓扑。** 无依赖的扇出并行，有依赖的做流水线（A 的输出作为 B 的输入）。我的并发上限经验值是 3~5，再高会撞 API 限流，边际收益也趋近于零。
4. **控制回传体积。** subagent 只回传摘要和结论，全量日志写文件，主 agent 需要时按路径去取。这一条直接决定主上下文能否撑住长任务。
5. **用 MCP / 插件收窄权限。** 每个 subagent 只挂它需要的工具集，比如负责查数据的 subagent 不给写文件的权限。

一个实际例子：做仓库重构前评估时，我起了四个 subagent——两个并行扫代码风格和依赖引用，一个查测试覆盖率，一个做汇总。主 agent 只收到四份结构化摘要，全程上下文占用不到单干方案的三分之一。

## 踩坑点

- **摘要回传后主 agent 又去「复述」全文**，等于白拆。要在 prompt 里明确要求它只引用结论。
- **共享文件引发写竞态**：两个执行者同时改一份配置。后来按文件分区任务才解决。
- **子任务静默失败最坑**。约定失败必须带 error 字段，主 agent 看到就降级处理，不猜。
- **拆得太细**，调度和拼接的开销超过并行收益。两三个动作能干完的事，不值得开 subagent。
- **并发没上限**：一次性起了八个，限流重试互相踩踏，反而比串行慢。

## 可复用建议

- 把 subagent 的 prompt 做成模板，输入/输出 schema 固化，新增任务类型只是换参数；
- 每次调用加 trace id，日志能串起来，排障不用翻半天；
- 先串行跑通一个子任务、验证输出质量，再放开并行；
- 定期看主 agent 的上下文占用，膨胀了先查回传内容，而不是急着加窗口。

## 总结

subagent 编排的本质是「上下文隔离 + 结果摘要回传」，并行只是顺带的收益。拆分粒度、回传体积、失败上报这三件事做对了，单 agent 干不动的任务就能稳定跑起来；做不对，并行只会更快地产出错误结论。建议从一个真实的长任务入手，先拆两路并行验证，跑顺了再逐步扩展。
