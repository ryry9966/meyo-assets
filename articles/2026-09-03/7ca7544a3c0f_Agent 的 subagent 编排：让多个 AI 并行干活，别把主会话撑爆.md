## 背景

用 OpenClaw 做自动化久了，最先撞到的天花板是“单 agent 串行”。让它批量整理 20 个目录、跑一轮多仓库调研、同时产出几份文档，主会话只能一轮一轮做：慢，而且所有中间细节都堆在主上下文里，token 烧得快，注意力还被稀释——越到后面的步骤，产出质量越明显下滑。

OpenClaw 支持主 agent 派生子会话（subagent）：子任务交给独立会话去跑，多个子会话并行执行，主会话只负责拆任务和收结果。这套机制用对了是质变，用错了就是一堆互相覆盖的文件和一串 429。

## 问题

三个具体问题：

1. **上下文污染**：中间过程全进主会话，长任务跑一半就开始丢细节。
2. **串行等待**：本可并行的独立任务被排队执行。
3. **并发冲突**：多个子 agent 同时写文件、打同一个 MCP 服务，互相踩。

还有一个隐性坑：子 agent 是全新会话，**不继承主对话历史**。很多人第一次用会默认它“知道背景”，结果跑出来的东西完全不对。

## 做法

我现在跑得比较稳的流程是四步：

**1. 拆分先行。** 主 agent 先产出子任务清单，每个子任务一段自包含描述：目标、输入在哪、输出写到哪、约束是什么、完成标准是什么。子 agent 看不到主会话，描述里缺一句，它就只能猜。

**2. 控制并行度。** 一次派 3~4 个，别无脑拉满。IO 型任务（读文件、整理目录）3~5 个很舒服；调外部 API 的按限流配额算，一般给配额的 70% 留余量。

**3. 结果落盘，不要全塞回消息。** 每个子 agent 把产物写到独立路径（如 `output/task_01/`），消息里只返回一两句摘要加产物路径。主 agent 聚合时按路径读文件，上下文干净得多。

**4. 聚合与校验。** 主 agent 逐个检查子产物是否符合完成标准，不合格的重派一次，再失败就降级为串行或标记人工介入。整个编排设总超时，防止某个子 agent 卡死拖垮全局。

## 踩坑点

- **并发写同一文件互相覆盖。** 早期让所有子 agent 往同一个 markdown 里追加，后写的把先写的冲掉了。改成“一人一个目录，最后由主 agent 合并”，问题消失。
- **MCP 工具限流。** 并行 8 个子 agent 打同一个 MCP 服务，key 一起 429。并行度按工具配额算，不是按机器算。
- **拆分过细反而慢。** 调度和聚合本身有开销，两个任务拆八个子 agent 属于负优化。经验粒度：一个子 agent 产出一个独立交付物。
- **先串行验证一个。** 新类型的任务，先串行跑通一个子 agent、确认任务描述没问题，再开并行。否则是 N 倍速地跑错。

## 可复用建议

- 固化一个子任务描述模板（目标 / 输入 / 输出路径 / 约束 / 完成标准），放进项目提示词，主 agent 拆任务时照着填。
- 输出目录约定成习惯：`task_NN` 独立目录，汇总文件只由主 agent 生成。
- 并行度、超时、重试预算写进配置，不要每次靠模型临场发挥。

## 总结

subagent 并行编排的收益，不来自“并发”本身，而来自两件事：**隔离上下文**（主会话不被细节淹没）和**独立产出**（子 agent 各自落盘，聚合只碰摘要）。先把单任务串行跑通，再拆分、限流、落盘、校验。这套流程在我这里跑了几周，长任务总耗时降到原来的三分之一左右，主会话 token 消耗降了一半以上。不玄学，就是工程。
