# 背景

用 OpenClaw 做自动化，几乎每个人都会走到同一个分叉口：想让 agent 定期干点活，框架里却有两条路——**cron jobs** 和 **heartbeat**。两者都能"定时触发"，但运行模型完全不同。选错了，轻则 token 翻倍，重则任务静默失败。

# 两者到底是什么

**cron**：独立调度器。到点后开一个独立会话，把你写好的 prompt 交给 agent 跑一次，跑完即止。它看不见你的主聊天记录，输出也不会污染主会话。任务定义放在 workspace 的 cron 配置（`jobs.json`）里。

**heartbeat**：主会话内的周期唤醒。默认约每 30 分钟往主会话注入一条心跳消息，agent 带着完整上下文自己判断：有事就回，没事保持沉默。它的"定时"是**间隔制**的，不是钟点制。

一句话区分：**cron 是闹钟，heartbeat 是巡逻。**

# 怎么选

先回答两个问题：

1. 这个任务必须在固定时刻发生吗？（每天九点发日报、每周五备份）→ **cron**
2. 这个任务依赖会话上下文、允许偶尔跳过吗？（盯收件箱、巡检订阅源、顺手维护 todo）→ **heartbeat**

**配置 cron 的要点：**

- 在 `jobs.json` 里定义调度表达式、prompt 和投递目标；
- prompt 必须自包含：不要写"刚才聊的那个事"，要写清完整指令和输出去向（写文件、发到某个 channel）。

**配置 heartbeat 的要点：**

- `HEARTBEAT_INTERVAL` 控制间隔（毫秒），`HEARTBEAT_TOKENS` 限制轻量回复的预算；
- 在 workspace 的 `HEARTBEAT.md` 里维护巡检清单，逐项写明"什么情况保持沉默，什么情况才回复"。

# 踩坑点

1. **心跳清单写成任务书。** 清单越长，agent 越"有活干"，每次心跳都输出长文，成本直线上升。正确姿势是反着写：默认沉默，异常才开口。
2. **cron 的 prompt 引用会话上下文。** cron 跑在独立会话里，"接着上面的讨论"在这等于空指针。需要上下文就创建任务时压进 prompt。
3. **心跳间隔贪短。** 5 分钟一次心跳叠加主会话的大上下文，等于每 5 分钟做一次全量推理。不是真·紧急巡检，30 分钟起步更合理。
4. **cron 失败静默。** 独立会话跑挂了没人知道。在 prompt 里加一句：失败时主动发消息说明原因。
5. **时区。** cron 按本机时区解释时间表达式，跑在服务器上的实例，先确认时区再定闹钟。

# 可复用建议

- **cron 输出落盘。** 把结果写到固定文件/目录当审计日志，排查问题时比翻聊天记录快得多。
- **混合模式。** heartbeat 巡检发现异常 → 让 agent 临时创建一次性 cron 跟进处理。适合"低频巡逻 + 事件响应"的组合。
- **心跳清单模板。** 每项 = 检查对象 + 沉默条件 + 触发条件 + 回复格式，整个文件控制在 10 行以内。
- **上线前手动跑一次。** 用 CLI 手动触发任务（`cron run`），确认输出符合预期，再交给调度器。

# 总结

| 维度 | cron | heartbeat |
|---|---|---|
| 触发方式 | 钟点 / 表达式 | 固定间隔 |
| 会话 | 独立、无记忆 | 主会话、带上下文 |
| 输出 | 必然产生 | 按需、可沉默 |
| 适合 | 定时日报、抓取、备份 | 收件箱巡检、提醒、轻量维护 |

选型一句话：**确定要发生的活交给 cron，需要"带脑子"巡逻的活交给 heartbeat。**

大多数人犯的第一个错，是用 heartbeat 干 cron 的活，然后疑惑为什么每天早上的日报总是九点十三分才来——因为巡逻队不看钟，只看步数。
