## 背景

大多数 Agent 的工作模式是拉式的：你发指令，它执行，然后停在原地等下一次。这种模式在"明确任务"下没问题，但现实中很多有价值的事并不发生在你开口的那一刻——CI 在凌晨红了、磁盘只剩 4%、某个依赖发了带安全公告的新版本。OpenClaw 的架构其实已经预留了 proactive 的口子：heartbeat 周期唤醒、cron 任务、MCP 工具和消息通道的组合，让 Agent 具备"定时看一眼 + 判断要不要说/做"的能力。问题不在能力缺失，而在怎么调到"有用且不烦人"。

## 问题

直接打开 heartbeat，通常得到两种失败结果：

1. **噪音型**：每 30 分钟醒来报告一次"一切正常"，三天后你把它静音；
2. **失控型**：无人值守时拿到写权限，自己"顺手"改了配置、发了消息，事后无法复盘它为什么这么做。

本质上是缺了一份工程契约：什么时候醒、醒来查什么、什么条件下可以行动、什么条件下只记录不说话。

## 做法

我们把 proactive 拆成四层：

1. **触发源分层**。低频心跳（2–4 小时）做常规巡检；cron 精确时间点做日报；事件驱动（MCP server 推送、文件变更 hook、git push）做即时类。不要把所有事塞进心跳，事件能触发的就用事件。
2. **检查-决策-行动流水线**。每次唤醒不让模型自由发挥，而是把"本次检查清单 + 上次状态"注入上下文，要求输出结构化结果：正常 / 需行动（附证据）/ 需确认。判断依据必须来自工具返回的真实数据，不允许模型"猜"。
3. **状态落盘**。在工作区维护一个轻量状态文件（类似 HEARTBEAT.md / ledger），记录"已报告过什么、什么时间、结论是什么"。没有这层，Agent 会在每次唤醒时重复报告同一件事——这是最常见的坑。
4. **权限分级**。只读类操作（查状态、读日志、汇总）允许静默执行；写类操作（发消息、改文件、调外部 API）必须带确认，或进入"摘要-批量"通道。无人值守运行单独配一份更小的工具白名单。

## 踩坑点

- **心跳太密**：token 成本线性上涨，信息增量趋近于零。我们从 15 分钟调到 3 小时后，成本降一个量级，价值反而上升。
- **时区错位**：cron 写的是 UTC，本地是 UTC+8，日报晚八小时送达。统一在配置里声明时区并写进注入指令。
- **重复报警**：没有状态文件时，同一条磁盘告警连报 6 次。加去重 + 升级策略（第 3 次起提升严重级别）。
- **prompt 漂移**：proactive 规则埋在系统提示词深处，长对话后被稀释。改成每次唤醒注入独立的短指令块。
- **幻觉触发**：让模型"自己想想有什么值得关注"，它会编造事件。触发源必须外部给定，模型只做判断。

## 可复用建议

- 从一个低风险场景起步：每日摘要或单一阈值告警，稳定跑两周再扩。
- 写一份一页的"主动行为契约"：允许做什么、静默阈值、免打扰时段、升级路径，直接作为唤醒时的注入内容。
- 所有 proactive 动作留审计日志，随时能回答"它昨晚为什么给我发那条消息"。
- 同类事件在时间窗口内聚合成一条 digest 推送，而不是逐条轰炸。

## 总结

Proactive 不是让 Agent 更"聪明"，而是给它一套可靠的唤醒、判断、行动与约束机制。OpenClaw 提供的是心跳、cron、MCP 和通道这些原语；真正决定体验的是你定的契约——多久醒、看什么、什么能默默做、什么必须问。把它当成一个需要 SLA 的小型后台服务来设计，proactive 才会从"花活"变成日常依赖。
