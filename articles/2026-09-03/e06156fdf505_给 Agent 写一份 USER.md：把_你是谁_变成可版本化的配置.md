## 背景

用 OpenClaw 这类常驻 Agent 一段时间后你会发现：它记不住你是谁。系统提示词写死了通用规则，对话记忆是黑盒——存了什么、何时存、权重多大，都不可控。于是每次新会话都得重新交代一遍：我在哪个时区、用什么技术栈、讨厌什么样的回答。

USER.md 补的就是这层缺口：一份放在 workspace 根目录、每次会话启动时被 Agent 读取的纯文本文件，专门声明"关于用户本人的稳定事实"。

## 问题

没有这层结构化上下文，常见症状有三类：

- **重复劳动**：每个新会话自我介绍一遍，换设备、换客户端后更甚；
- **建议泛化**：Agent 不知道你的角色和技术背景，回答永远偏入门；
- **记忆不可审计**：自带的记忆功能悄悄存了什么，看不到也改不了，出错无从修正。

本质上，用户上下文是个配置问题，不该是玄学问题。

## 做法

1. 在 workspace 根目录建 `USER.md`，按分区写事实：

```markdown
# 用户画像
## 基本信息
- 时区：Asia/Shanghai，工作时段 10:00-19:00
- 角色：后端工程师，主要维护 Go 服务

## 偏好
- 先给结论，推理过程放最后
- 代码示例用 Go，避免伪代码

## 当前项目
- 正在做 MCP 工具接入，截止本季度

## 禁忌
- 不主动重构我的旧代码
- 方案里不引入新依赖，除非我先问
```

2. **写事实，不写故事**。每条一行，可单独引用、单独更新。
3. **挂进启动流程**。OpenClaw 的 bootstrap 默认会读 workspace 下的 USER.md；自建 Agent 可在组装 system prompt 时注入，或通过 MCP resource 暴露给客户端。
4. **进 git**。像对待配置文件一样提交、diff、回滚。
5. **定修剪节奏**，比如每月一次。

## 踩坑点

- **写成小作文**。三段式自我介绍会烧掉上下文预算，重点被稀释。控制在 30–50 行。
- **放敏感信息**。USER.md 每次会话都进 prompt，密钥、证件号、不想让模型看到的内容一律别写。
- **和 MEMORY.md 打架**。过程性记忆里存了旧时区，USER.md 写了新时区，Agent 行为会摇摆。明确优先级：USER.md 为准，定期让它自查两者冲突。
- **信息过期**。项目结了、时区换了没更新，Agent 会自信地用错误事实服务你。
- **多机分叉**。VPS 和本地各维护一份，很快不一致。用 git 仓库做单一事实源。

## 可复用建议

- **当配置文件对待**：声明式、短、可 diff，杜绝叙事。
- **上下文分层**：USER.md 放跨项目稳定事实，PROJECT.md 放单项目上下文，MEMORY.md 只放过程性信息，三者职责不混。
- **让 Agent 自己提修订**：每周问一次"根据近期对话，USER.md 哪些条目需要新增或修改？"让它输出候选 diff，人工审核后合入。既避免静默漂移，也省得自己想不起该改什么。
- **新 Agent 冷启动**：换模型或接新工具时，第一件事就是把这份 USER.md 挂上。

## 总结

USER.md 的价值不在"让 AI 更懂你"这类修辞，而在于把用户上下文从不可审计的黑盒，变成可版本化、可审查、可协作编辑的一份配置。一个 markdown 文件、几十行事实，换来的是每次会话少说十句废话——这是 Agent 工程化里性价比最高的动作之一。
