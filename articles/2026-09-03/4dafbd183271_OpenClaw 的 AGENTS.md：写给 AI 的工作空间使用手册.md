## 背景：Agent 缺的不是能力，是“这里的规矩”

OpenClaw 的 Agent 每次会话启动都会读取 workspace 下的固定文件：SOUL.md 管性格，USER.md 管用户画像，而 AGENTS.md 管操作规程——这个工作空间怎么用、东西放哪、哪些事必须先问。它相当于新员工入职第一天拿到的那本《员工手册》，只不过读者是模型。

OpenClaw 初始化时会生成一份模板 AGENTS.md，但模板只是占位。真正让它起作用的，是把你和 Agent 之间反复发生的口头约定沉淀进去。

## 问题：没有手册时的三种典型症状

- 同类任务每次做法不一样：文件乱放、命名随机、备份时有时无；
- 同一句纠正反复说：“先备份再改”“别动 config”——会话一断就归零；
- Agent 自作主张做过头：直接替你发消息、清理目录。

这些不是模型能力问题，是上下文缺失。聊天里说的规则不持久，AGENTS.md 补的就是这一层。

## 做法：从 30 行的最小版本开始

1. 只写三类内容：空间布局（/media、/documents、MEMORY.md 各放什么）、硬性规则、固定流程（heartbeat 检查什么、日报格式）。
2. 规则用“触发条件 + 动作”写，不写形容词：

```markdown
## 硬规则
- 发送任何频道消息前，先给草稿等我确认
- 改配置文件前，先复制到 /backup 并带时间戳
- 批量删除一律不做，除非我在当次会话明确要求
```

3. 像代码一样维护：AGENTS.md 进 git。每次手动纠正 Agent 后问一句“这要不要固化成规则”，是就改文件、写清 commit message。
4. 子目录可放独立 AGENTS.md 覆盖上层规则，适合 projects 下各有构建约定的场景。

## 踩坑点

- **写成小作文**。手册全文进上下文，每行都消耗 token、稀释关键规则。我控制在 60 行内，超了就拆到 TOOLS.md 或独立文档再引用。
- **和 SOUL.md、系统提示冲突**。两处对同一行为给出不同指令，Agent 行为会摇摆。改规则前先全局搜一遍。
- **塞秘密**。token、密码别写，AGENTS.md 会被完整送进模型上下文。
- **当成安全边界**。它是强先验不是沙箱，高危操作要靠工具权限和审批机制兜底，文件管不住越权。
- **内容过期**。路径变了、skill 下线了，不改的手册就是负资产，建议每月 review 一次。

## 可复用建议

- 四段骨架起步：空间布局 / 硬规则 / 固定流程 / 禁止事项。
- “两次原则”：同一件事口头纠正第二次，就必须进 AGENTS.md。
- 能变成 checklist 的规则才值得写，“注意安全”这类不可验证的话删掉。
- README 写给人，AGENTS.md 写给 Agent，别混在一个文件里。
- 衡量标准很简单：统计你重复纠正的次数，趋近于零就说明手册起效了。

## 总结

AGENTS.md 的价值不在文件本身，而在把“你和 Agent 之间的默契”变成可版本化、可审查、可迁移的资产。先跑最小版本，再让每次踩坑反哺手册——三个月后它会长成最适合你工作流的样子，而且换模型、换设备都能带走。
