## 背景

OpenClaw 这类常驻 agent 有个绕不开的前提：模型自己不会“醒着”，所有主动性都来自外部触发。heartbeat（心跳）就是让 agent 周期性自我唤醒、检查待办的机制——比如唤醒后读一遍 HEARTBEAT.md，决定是继续睡还是干活。落到工程上只有两条路：定时轮询，或者事件方推送。我们团队在几个自动化项目里两种都跑过，这里记录一下真实取舍。

## 问题

轮询的问题不是“能不能用”，而是成本结构：每次 tick 如果都打到模型，哪怕 90% 是空转，token 账单和上下文污染都是真实的。推送则相反：省掉了空转，但引入一串分布式经典难题——NAT 穿透、断线重连期间的事件丢失、重复投递。更危险的是推送通道静默失效后，agent 会“永久沉睡”且无人察觉。

## 我们的分法与做法

1. **先分类事件，再选通道。** 即时性强的（IM 消息、webhook、CI 回调）走推送；容忍分钟级延迟的（日报、文件巡检、定时摘要）走轮询。不要指望一种机制覆盖所有场景。
2. **单一调度器 + 自适应间隔。** 轮询不做固定 interval：任务活跃期短间隔（约 60s），连续 N 次空转后指数退避到 10–30 分钟，有活动立即重置。多实例务必加随机抖动，避免重启后同一秒齐跳。
3. **tick 前设廉价闸门。** 心跳循环先做本地判断——队列是否非空、被监听文件的 mtime 是否变化、是否在免打扰时间窗——全为否则直接 noop 返回，绝不碰模型。这一步是我们 token 成本下降最明显的改动，建议直接做在插件层。
4. **推送通道至少做三件事：** HMAC 签名防伪造、幂等键防重复执行、序列号 + last-event-id 支持断线补拉。通道断了自动回退到轮询兜底。
5. **看门狗。** 推送通道连续 M 秒收不到任何事件（含 keepalive）就告警并临时切轮询。推送体系最大的风险是“无声地坏掉”，必须能被外部观测。

## 踩坑点

- 初版每个 tick 都调模型，一周账单翻倍，事后统计 noop 占比 92%。闸门必须前置，不能靠提示词让模型“自己判断没事”。
- push-only 上线第三天，网关重连窗口丢了两条事件，任务没跑也没人发现。之后所有推送都带序列号，可对账。
- 多实例重启后心跳齐跳，外部 API 瞬间触发限流。加 jitter 解决。
- 在心跳协程里同步执行长任务，后续 tick 全部堆积。改成心跳只入队，worker 单独消费。

## 可复用建议

- 延迟敏感走推送，轮询只作为活性下限，不当主力。
- 任何 tick 到达模型之前，必须先过一道本地闸门。
- 轮询、推送、cron 等所有触发路径，统一收敛到同一个幂等的任务入口。
- 给每次唤醒记录 wake reason，每周看一次空转率——它是最诚实的调参依据。

## 总结

这不是二选一，而是分层：推送管时效，轮询管兜底，闸门管成本。heartbeat 设计成熟的标志，不是心跳跳得多勤快，而是绝大多数心跳都能安静地什么都不做。
