## 背景

做自动化的人迟早会接受一个事实：**任务不会只跑一次**。调度器失败重试、webhook 重复投递、agent 推理超时后重新规划再调一次工具、用户手滑多点一次——执行侧普遍是“至少一次”（at-least-once）语义，重复执行是常态，不是异常。在 OpenClaw 这类 agent + MCP + 插件的自动化链路里，这一点尤其明显：LLM 的不确定性会放大重试和重规划的概率。

## 问题

幂等性的定义很简单：同一个操作执行一次和执行多次，最终结果一致。读操作天然幂等，麻烦全在写操作上——追加写文件、创建工单、发群消息、INSERT 一行、调计费接口。

最典型的场景：工具调用超时，客户端重试，但服务端其实已经执行成功，于是工单建了两条、消息发了两遍。这类问题在单人脚本时代靠肉眼兜底，一旦接进 agent 自动循环，就会以更高的频率、更隐蔽的方式出现。

## 做法

1. **先分类**。把链路里的操作分成读和写，写操作一律按“会被执行两次”来设计。
2. **定义稳定的幂等键**。键必须从业务语义派生，比如 `日期 + 来源 + 目标 + 动作`，而不是每次重试随机生成的 UUID。agent 重新规划后产生的“新任务”，只要语义相同，键就应该相同。
3. **用唯一约束兜底**。幂等键落数据库唯一索引，插入用 `INSERT ... ON CONFLICT DO NOTHING`（或 Redis SETNX 占位）。不要依赖应用层“先查再插”，两个并发实例会同时查到“不存在”。
4. **状态机收敛**。任务状态只允许单向流转（pending → done），副作用执行前检查状态，完成立即落库；已是 done 的重入直接跳过。
5. **工具层统一封装**。与其每个 MCP tool / 插件 handler 各写一套去重，不如在工具调用层做通用中间件：进入先验键，命中即返回上次结果。

## 踩坑点

- 用随机 UUID 当幂等键，重试时重新生成，等于没做。
- “先查后插”的竞态：去重必须靠唯一约束，不能只靠 if 判断。
- “副作用已完成、状态未落库”之间有崩溃窗口：发完消息后、写完状态前进程挂掉，重试就会再发一遍。缓解办法是先落“意向记录”再执行副作用，让账本先行。
- 默认外部 API 幂等：不是所有接口都支持 Idempotency-Key，接入前用重试实测一次。
- 去重表无限膨胀：给幂等键设过期时间，定期清理。

## 可复用建议

- 测试里固定加一条“重复执行”用例：同一任务跑两遍，断言副作用只发生一次。
- 幂等键规则写进团队约定：agent 产出的任务 ID 必须可由业务语义重建，而不是只在会话内有效。
- 对确实不可幂等的外部动作（发消息、付款），采用“先记账、后执行、执行完核销”的顺序，账本即事实来源。

## 总结

幂等性不是锦上添花，而是自动化从“能跑”到“敢开自动挡”的分水岭。重试机制保证任务至少执行一次，幂等设计保证执行多次也只算一次——两者拼在一起，你才敢让 agent 在没人盯着的时候碰生产数据。提前半天做设计，省掉的是未来无数条重复工单和半夜的清理脚本。
