## 背景

跑过一段时间自动化的人多半遇到过：每天定时推送摘要的 cron 任务因网络超时触发重试，群里出现两条一模一样的消息；或者 webhook 触发的工单创建，agent 超时后重新规划了一轮，系统里多出一张重复工单。

根因相同：我们默认自动化是“执行一次”，工程现实却是“至少一次”（at-least-once）。调度器重启、网络重试、手动补触发、agent 多轮自我修正，都可能让同一个任务跑两遍。这篇不讲分布式理论，只记录在 OpenClaw 自动化场景里，怎么用幂等性把“重复执行”变成无所谓的事。

## 问题

幂等的定义很朴素：同一操作执行一次和执行 N 次，最终结果一致。读操作大多天然幂等，出问题的都是写操作：

- append 追加文件或消息：跑两次内容翻倍；
- insert 新记录：没有唯一约束就产生重复数据；
- “做动作”型 API（发通知、建工单）：每调一次就是一次新副作用。

agent 场景还多一层：MCP 工具调用的超时重试、用户手动再触发一次，都是合法的重复来源，砍不掉，只能兼容。

## 做法

我的实践可以压缩成三步：

1. **给任务实例一个确定性 ID。** 不要用时间戳或随机 UUID——每次重试都会生成新 ID，去重直接失效。用“任务名 + 业务窗口”派生，比如按天汇总任务用 `任务名-当日日期`。同一窗口内的任何重试，ID 不变。

2. **执行前查状态，成功后落标记。** 标记文件、数据库一行记录、KV 键都行。关键是顺序：先检查“这个 ID 做过没有”，做完且确认成功后再写标记。标记写在成功之后，失败的任务才有机会被重新执行。

3. **写操作尽量改成“设状态”而不是“做动作”。** 能 upsert 就不要 insert，能整文件重新生成就不要 append，外部接口支持幂等键就一定带上。把“做某事”改写成“把某物置为目标状态”，天然可重放。

## 踩坑点

- **检查和写入不是原子的。** 两次触发并行跑，都查到“没做过”，然后都执行。低频任务也要用文件锁或数据库唯一约束兜底，别只靠先查后写。
- **标记写太早。** 任务还没成功就落了“已完成”，之后失败也不会重跑——这种静默失败比重复执行更难排查。
- **窗口边界没对齐。** “当天”按本地时区还是 UTC，跨零点的任务会因此漏跑或重跑，选一个并写死在代码里。
- **过度信任调度器。** “我的 cron 不会重复触发”是错觉，容器重启、手动补触发、上层框架的重试都会打破这个假设。

## 可复用建议

- 把“查状态 → 执行 → 落标记”封装成插件或工具调用的统一包装层，别在每个任务里手写一遍。
- 验收标准很简单：**故意连跑两次，结果应和跑一次完全一样。** 把这条写进自动化任务的测试用例。
- 对外部副作用（发消息、建工单），优先找带幂等键的接口；找不到就自己维护“业务 ID → 已执行”的映射表。

## 总结

幂等性不是高级技巧，而是一种预设：承认重复执行一定会发生，然后让结果与执行次数无关。确定性 ID 负责去重，成功后落标记负责重跑，“设状态优于做动作”负责写操作。做完这三件事，重试、重启、手动再触发，都从“事故”降级成“无事发生”。
