## 背景

过去一年，社区里跑的 Agent 从“能聊天”变成了“能动手”：接 MCP 工具、读写文件、调内部 API、跑定时任务。能力上来之后，真正让人睡不着觉的不再是“它做不了”，而是“它没问我就把事办了”。删错表、把草稿直接发到客户群、拿生产 key 去压测——长期跑 Agent 的人多少撞见过一次。

## 问题在哪

权限边界的本质是两个问题的组合：**这件事错了能不能撤回？撤回代价多大？**

很多团队把权限做成一个开关（全自动 / 全人工确认），两头都不对：全自动出一次事故就全线收紧，效率归零；全确认则很快出现“确认疲劳”，人开始无脑点同意，确认机制形同虚设。

## 做法：一张二维表

我们现在的做法是把 Agent 可调用的每个工具按两个维度打标：

- **可逆性**：只读 / 可回滚写 / 不可逆
- **影响面**：仅沙箱 / 本机 / 外部可见（发消息、付费、对外发布）

然后按象限定策略：

1. **只读 + 影响面受限**：自动执行。但要收敛范围——文件系统限定目录、HTTP 限定域名白名单，而不是给它一把万能钥匙。
2. **可逆写 + 影响面可控**：先 dry-run 输出 diff，Agent 自主决定是否 apply，全程留痕。
3. **不可逆或外部可见**：强制走确认通道。注意，确认不是让 Agent 在对话里问一句，而是调用一个显式的 approval 工具：请求挂起，人审批后返回，审批记录和参数快照一起落日志。
4. **涉及凭证、计费、批量删除**：无论多小，都问。

关键一点：策略放在工具注册层，而不是提示词里。提示词里写“请你谨慎一点”不是权限系统，是许愿。

## 踩坑点

- **确认疲劳**。曾对所有写操作都弹确认，一周后大家开始盲批。后来把确认收敛到真正不可逆的动作，量降了一个数量级，人才会认真看。
- **确认内容不做人话**。直接甩一段原始 JSON，人根本判断不了。确认卡片应该展示：做什么、影响哪些对象、diff、怎么回滚。
- **审批超时**。人不在，Agent 挂着干等。给 approval 加了超时后默认拒绝并记日志，才闭环。
- **批量操作逐条确认等于没有确认**。改成汇总一次：列出全部目标，确认一次，超过阈值再拆分。
- **参数级漏洞**。工具权限开了、参数没限，Agent 用合法的“读文件”把 `.env` 读走了。权限要落到参数白名单，不只是工具名。

## 可复用建议

- 新工具**默认拒绝**，跑两周、日志没问题再放行。
- 把“问人”做成一等公民工具而不是对话行为，这样才有审计。
- 每周过一次自动执行日志，重点看 Agent 偏离计划的调用——那是策略该调的信号。
- 留一个 break-glass 通道救急，但要大声记录。

## 总结

权限边界不是“信不信任模型”，而是一套随证据演化的策略：**读的自动，写的留痕，不可逆和出沙箱的问人，凭证永远问人。** 默认收紧，用日志慢慢放。宁可前期多批几次，也别让一次自动事故把团队对 Agent 的信任清零。
