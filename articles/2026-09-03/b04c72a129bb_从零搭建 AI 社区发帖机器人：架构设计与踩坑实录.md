## 背景

社区运营久了，有一类活特别机械：每周把合并的 PR、新版本、热门讨论整理成周报发出来。人肉干了两三轮就烦了——信息都摆在公开渠道里，缺的只是整理和发布，于是动手写了个发帖机器人。动手前先想清楚核心问题：难点从来不是"生成一篇文章"，而是怎么保证发出去的内容是真的、格式是对的、不会重复发、出了问题能回溯。

## 架构：四层流水线

整体分四层，每层独立可替换：

1. **触发层**：cron 定时 + GitHub Release webhook 双通道。定时兜底，事件驱动保时效。
2. **取数层**：一个薄的 MCP 工具封装，负责拉结构化数据（release notes、PR 列表、论坛 API 的热帖统计）。事实必须来自 API，不让模型自己"回忆"。
3. **生成层**：跑在 OpenClaw 上的 Agent 拿到结构化输入后按模板填槽。版本号、PR 标题、链接是硬占位，模型只负责写导读和每个条目的一句话摘要。
4. **发布层**：论坛 API 适配器，带重试、限流退避和幂等键。发布前草稿先投到内部频道，管理员回复确认才真正提交。

## 踩坑实录

**1. 让模型自由发挥等于造谣。** 第一版直接丢一句"写一篇周报"，产出看着很专业，但里面混进了两三个根本不存在的 PR 描述。改成模板填槽后——事实一律来自 API 返回的 JSON，模型只在指定字段内写措辞——幻觉问题基本消失。

**2. 重试导致重复发帖。** 发布接口超时后 cron 下一轮又跑了一遍，论坛出现两篇一模一样的内容。解法是幂等键：`hash(日期 + 内容摘要)`，发布前先查库，命中即跳过。这事应该第一天就做，而不是被坑之后。

**3. Markdown 方言不兼容。** 模型偏爱嵌套列表和 HTML 标签，论坛渲染器不认，帖子出来一团乱。加了一步预渲染校验：用论坛同款渲染器先渲染一遍，结构异常就打回重写。

**4. 全自动的信任成本太高。** 最初想省掉人工环节，结果一篇把"已关闭的 issue"写成"已修复"的帖子被顶到首页，解释成本比写帖本身高得多。现在保留三步闸门：草稿 → 审核 → 发布。等连续四周零修改通过，再考虑放宽。

**5. 凭证和时区。** token 被打进日志差点泄漏，后来统一走 secret 注入并做日志脱敏；cron 默认 UTC 导致"周报"拖到周一早上才发，改成显式声明时区。

## 可复用建议

- **事实与措辞分离**：结构化数据进模板，模型只写过渡文字。
- **幂等与去重从第一天开始**：定时任务一定会重跑。
- **把论坛 API 当不可靠服务**：超时、429、5xx 都按预期路径处理，别当异常。
- **全程留痕**：每次运行保存输入、草稿、终稿和发布结果，出问题能回放。
- **先窄后宽**：宁可先只做"搬运"，跑稳了再谈生成观点性内容。

## 总结

这类机器人 demo 十分钟，稳定跑两周起。真正的难点不在"能不能发出去"，而在护栏：模板约束、人工审核、幂等、审计日志。让模型做它擅长的事——组织语言；让代码做它该做的事——保证事实和流程。这是目前跑下来最省心的组合。代码整理后会开仓库，欢迎来拍架构。
