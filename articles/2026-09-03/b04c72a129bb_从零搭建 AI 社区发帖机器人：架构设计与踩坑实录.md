## 背景

我们社区每周都有几类固定内容要产：版本更新摘要、精华问答整理、新插件试用笔记。过去全靠人肉写，素材越攒越多，发布却越来越不稳定，经常憋两周才发一篇。于是花了一个周末，搭了一个定时发帖机器人。核心诉求很朴素：**数据可信、内容不油、发布可控**。

## 问题：为什么不能“一个 prompt 直接发”

最初版本就是 cron + LLM API：把上周的 commit 和 issue 列表丢给模型，输出直接调发帖接口。跑了三天就暴露三个致命问题：

1. 模型会**编造 issue 编号和链接**，读者一眼穿帮；
2. 语气飘向营销号，“重磅！”“效率拉满！”全出来了；
3. 网络抖动触发重试，**同一条内容发了两遍**。

结论很清楚：发帖机器人不是“生成问题”，而是“数据管线 + 发布流程”问题，生成只是其中一环。

## 现在的架构

四层，各层职责严格分离：

1. **采集层**：cron 定时拉 Git commits、issue 关闭记录、论坛热帖，先落本地 SQLite。这一步完全不经过 LLM。
2. **起草层**：OpenClaw agent 挂 MCP 工具（`query_digest`、`fetch_thread`），只允许基于工具返回的结构化数据写稿。prompt 里明确禁止自行生成任何 URL、编号、用户名。
3. **审核层**：草稿不直接发，推入 review 队列。用 MCP 的 approval 工具实现，我每天扫一眼，点过才发。
4. **发布层**：带幂等键（内容 hash + 目标板块）的发布器，重试前先查重，本地记录已发布 ID。

## 踩坑点

- **链接幻觉**：靠 prompt 说“不要编”没用。必须在代码层校验——发布器对草稿里每个 URL 和编号做存在性检查，查不到直接打回。
- **cron 任务重叠**：任务耗时从 40 秒涨到 6 分钟后两次执行撞车。用文件锁（flock）解决，别依赖“判断进程名”这种脆弱方案。
- **幂等键选错**：起初用时间戳做键，时区漂移导致同一内容换了键。改成“内容 hash + 板块”才稳定。
- **风格漂移**：在 system prompt 里贴三篇社区认可的旧帖当风格样本，再配一份明确的禁用词负面清单，比堆形容词管用得多。
- **MCP 工具静默失败**：论坛 API 偶发 502，agent 拿到空结果就开始“脑补”。现在要求所有工具返回必须带 `source` 和 `fetched_at` 字段，缺失即中止本轮。

## 可复用建议

1. 先跑通“采集 → 落库”，再接 LLM；**数据层永远不信任模型**。
2. 发布必须有幂等键和人工审核位，哪怕审核只是每天 30 秒。
3. LLM 只做“组织语言”，不做“提供事实”。
4. 把审核时拒掉的例子回灌进 prompt 负面清单，风格会越跑越稳。
5. 失败要可见：每轮结束往自己的频道推一条状态（成功/跳过/原因）。静默失败最伤信任。

## 总结

机器人现在每周稳定发 2–3 帖，人工介入约每篇 1 分钟。最大的收获不是省时间，而是它逼我把“内容生产”拆成了一条可测试的管线：数据可验证、发布可回滚、失败有信号。接下来计划把审核层改成多人投票，再观察风格稳定性。

代码本身不复杂，复杂的是把“AI 会犯错”当成设计前提——这大概是所有 Agent 落地的共同功课。欢迎在评论区交流你们的审核策略。
