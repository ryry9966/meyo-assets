## 背景

信息源多了之后，真正的问题不是"看不到"，而是"看不过来"。RSS 虽然老，但它是我目前唯一能完全控制的输入渠道：无算法、无推荐，可以精确到栏目级订阅。但原始 feed 只解决"聚合"，不解决"压缩"——一天几十上百条 item，逐条点开不现实。

所以我的目标是：每天固定时间跑一次管线，把当天的更新压成 10 条以内的摘要，推到 IM 里。整个方案基于 OpenClaw 的定时任务和 agent 能力实现。

## 做法

核心思路是把"确定性工作"和"模型工作"分开：

1. **抓取层用脚本，不用 agent。** 一个 Python 脚本用 feedparser 拉所有源，按 GUID/链接 hash 去重，与本地 SQLite 里的已处理记录比对，只保留新增条目。没有 RSS 的站点用 RSSHub 补源。
2. **预过滤。** 按 48 小时时间窗 + 关键词规则先砍掉约 70% 的噪音。这一步纯规则，零 token 成本。
3. **交给 agent 做摘要。** 把过滤后的条目（标题 + 截断到 500 字的正文）批量塞给 OpenClaw 的 agent，要求输出结构化 JSON：`title`、`one_liner`、`why_it_matters`、`score`。prompt 里明确"只能从给定条目中选，不得新增信息"。
4. **渲染推送。** 按 score 排序取前 10，渲染成固定版式的 Markdown，通过 OpenClaw 的消息通道发到 Telegram。cron 设在早上 8 点。

整个流程里 agent 只做第 3 步，抓取、去重、推送全是确定性代码。

## 踩坑点

- **正文长度失控。** 早期把全文直接丢给模型，一轮跑掉 8 万 token。后来统一截断 + 每批限 30 条，成本降了一个数量级。
- **模型编造链接和标题。** 解法是只让模型输出"选中条目的编号 + 摘要字段"，标题和链接由脚本从原始数据回填，模型碰不到 URL。再加一层 JSON schema 校验，失败重试一次，再失败跳过该条。
- **跨源重复。** 同一篇文常被三四个源同时收录，用"归一化标题 + 域名"做二次去重，比单靠链接靠谱。
- **单个 feed 挂掉拖垮整次运行。** 每个源单独 try/except，失败记日志跳过。老博客的 GBK 编码问题也要处理。
- **摘要太"通用"。** 让模型给每条打"值得我关注"的分数并写一句理由，prompt 里写清楚我的关注领域，低分条目直接不进摘要。

## 可复用建议

- **抓取和摘要分离**是这条管线的核心设计。凡是代码能确定的就不要让模型做，省钱且稳定。
- **状态要落盘。** SQLite 记录已处理 item 的 hash，保证幂等——cron 重复触发或中途崩溃都不会重发。
- **摘要版式固定。** 每天同样的结构，阅读时只扫 score 和一句话，两分钟处理完。
- **先规则后模型。** 关键词能过滤的不要浪费 token；预算敏感的场景可以小模型初筛、大模型只处理高分条目。

## 总结

跑了一个多月，这条管线每天早上稳定产出一份摘要，我几乎不再主动刷订阅器了。回头看，价值不在"AI 会写摘要"，而在前置的过滤和去重——AI 只是最后一层的压缩器。RSS 提供控制权，agent 提供压缩率，而管线的实际价值，取决于你花多少心思在筛选逻辑上。
