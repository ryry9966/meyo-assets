## 背景

过去一年大家习惯了给项目写 CLAUDE.md / AGENTS.md，告诉 Agent"这个仓库怎么干活"。但另一个问题一直没被认真对待：Agent 不知道**你是谁**。每次新开会话都要重复交代——用中文回复、机器是 macOS、包管理用 pnpm、别乱动 CI 配置。这些信息高度稳定，却在每次会话里被重新消费一遍。

USER.md 的思路很简单：把"关于我"的高频事实沉淀成一份静态 Markdown，放进全局上下文，让所有会话默认携带。

## 问题

目前的常见做法各有缺陷：

- **手动重复**：成本高，还容易漏；
- **依赖 Agent 自带 memory**：黑盒、不可 review、跨工具口径不一致，出错难以排查；
- **全塞进 system prompt**：改起来麻烦，和具体工具强绑定。

一份人类可读、可版本管理、工具无关的 USER.md，恰好补上这一层。

## 做法

以 OpenClaw 的 workspace 约定为例：

1. 在全局配置目录（如 `~/.openclaw/USER.md`）建文件，项目级可用同名文件覆盖或追加；
2. 内容按四个区块组织，控制在 30–60 行：

```markdown
# 环境
- macOS 15 + zsh；部署目标 Ubuntu 22.04
- Python 3.12 + uv / Node 22 + pnpm

# 代码偏好
- TypeScript 严格模式，禁止 any
- 小函数优先，测试用 vitest

# 沟通
- 中文回复；先给结论再给细节
- 不确定时直接问，不要猜

# 硬约束
- 不直接 push 主分支；不改 .github/ 下的 CI 配置
```

3. 纳入 dotfiles 仓库做版本管理，像维护 `.vimrc` 一样维护它；
4. **验证加载**：新开会话直接问"根据你的上下文，我的技术栈是什么"。答不上来，说明路径没配对。

## 踩坑点

- **写太长**。上下文预算有限，超长 USER.md 要么被截断，要么稀释关键信息。越重要的条目越靠前。
- **写愿望不写事实**。"尽量写高性能代码"没有可执行性，"列表查询必须分页，避免 N+1"才有。
- **放错层级**。项目特有的东西（构建命令、目录结构）属于项目级 AGENTS.md，别污染全局文件。
- **塞敏感信息**。token、内网地址、真实客户名一律不写——这份文件可能被多个工具读取。
- **忘了更新**。技术栈换了不改，Agent 会持续按旧假设干活。建议每季度 review 一次，看一眼 diff。
- **想当然它会被读**。不同工具的加载路径不一样，务必实测确认 OpenClaw 确实把它带进了上下文，而不是凭文档猜测。

## 可复用建议

- 分清职责：USER.md 管"静态、稳定、人写"的事实；Agent memory 管"运行时动态积累"。两者别混，memory 出问题时可以直接重置而不丢配置。
- 团队场景可以再放一份 SHARED.md（团队规范），与个人 USER.md 分开加载，避免个人信息混入协作上下文。
- 每次修改后，让 Agent 复述一遍要点，相当于给上下文做一次单元测试。
- 建议每条只写一行，能被删除的标准是：这条信息三个月内没让 Agent 的输出变好过，就删。

## 总结

USER.md 不是什么新协议，只是把"自我介绍"工程化：一份 50 行以内的文件，换来每个新会话不再从零开始。写初版投入半小时，之后随用随改，性价比很高。它解决的问题很小，但出现频率极高——这类事，往往最值得先做掉。
