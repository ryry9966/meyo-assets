## 背景

OpenClaw 这类常驻型 Agent 有个绕不开的问题：它不能只等你来问，还得在没人说话的时候自己干活——盯监控、扫收件箱、到点提醒。让 Agent 主动起来只有两条路：**轮询**（heartbeat，定时醒来检查一轮）和**推送**（事件发生时外部系统直接叫醒它）。

## 问题

两条路各有硬伤。轮询的代价是延迟和 token：间隔设 30 分钟，最坏情况你的告警晚 29 分钟才被处理；间隔设 1 分钟，一天 1440 次 heartbeat，大部分是"查了一圈啥也没有"，纯烧 token。推送的代价是可靠性：webhook 要公网可达，家里宽带 NAT 后面的机器根本收不到；MCP 的通知依赖长连接，连接一断事件就丢了。很多团队在"二选一"上纠结，其实是个伪问题。

## 做法

我们的实践分三步：

1. **任务分类**。按两个维度划：事件源是否可靠、延迟要求多高。监控告警、PR 评论这类有可靠事件源的走推送；"每天巡检一次磁盘"这类没有外部事件的走 heartbeat。
2. **heartbeat 做兜底基线**。默认 30 分钟一次，心跳时只读一份极简的 checklist 文件，无事则直接返回，不进主对话上下文；设 quiet hours，深夜降频到 2 小时一次。
3. **推送做低延迟通道，heartbeat 做对账**。webhook 收到事件后由网关插件唤醒 Agent 处理；同时 heartbeat 每轮追加一次对账：比对本地事件表和远端状态，补漏。这样即使推送丢了，最坏也只是延迟一个心跳周期。

关键约束：**所有任务必须幂等**。推送和 heartbeat 会在边界上重复触发同一件事，去重要靠任务自身的幂等性，而不是指望调度层不重复。

## 踩坑点

- **心跳频率拍脑袋定**。一开始设了 5 分钟，一天 token 花费涨了三倍，产出为零。后来把心跳间隔当成预算旋钮来调，而不是当成灵敏度旋钮。
- **推送通道静默失效**。家里机器的 webhook 隧道断了两天没人发现。之后给推送通道本身加了探活——通道健康也需要被监控。
- **重复执行**。推送触发和 heartbeat 对账同时命中同一条告警，通知发了两遍。加事件去重键后才解决。
- **心跳失败被吞掉**。heartbeat 异常如果只记 log，Agent 会"看起来活着，其实已经死了"。改成连续 3 次心跳失败就触发一条显式告警。

## 可复用建议

- 决策规则一句话：有可靠事件源且收得到推送 → 推送；否则 → 轮询；无论选哪种，都保留一个低频 heartbeat 做对账。
- 心跳检查内容保持极简，宁可多跳几次，也别让心跳 prompt 膨胀。
- 把"事件是否被处理"落成一张本地表，对账才有依据。
- 给推送通道自身配监控，不要假设它一直活着。

## 总结

heartbeat 是可靠性基线，推送是延迟优化，两者不是竞争关系。先用 heartbeat 兜住"一定会被处理"，再用推送提升"多快被处理"，剩下的工程活就是幂等、去重和对账。这套组合在我们环境里跑了一个多月，漏事件和 token 浪费都降到了可接受的水平。如果你在 OpenClaw 里只做一件事，先把 heartbeat 的 checklist 精简下来，收益最直接。
