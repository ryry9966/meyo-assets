## 背景

用 OpenClaw 当日常助理跑了几个季度，memory 目录从零散几条涨到上百条日记式记录之后，我发现真正决定它“记不记得住”的，不是 memory 写了多少，而是 `memory_recall` 的检索质量。OpenClaw 默认走全文检索（相当于对 `MEMORY.md` 和 `memory/*.md` 做关键词匹配），也可以配置 embedding 走语义检索。两条路线社区里吵了很久，我干脆拿自己的数据跑了一轮对比。

## 问题

我的实际痛点有三类：

1. **改述召回失败**：当时记的是“家里路由器网关 192.168.1.1，管理密码在备忘录”，三个月后问“家里的网关地址”，全文检索搜“网关”两个字，搜不到。
2. **中文短语问题**：连续中文没有词边界，全文检索的长句查询基本退化成子串匹配，命中率不稳。
3. **精确词恰好相反**：查版本号、命令名、错误码，全文一击即中；语义检索反而会“意译”跑偏。

## 做法

搭了个 20 条查询的土办法评测集：一半改述类，一半精确词类，人工标注期望命中的 memory 条目，两种模式各跑一遍。

1. **全文模式**：默认配置直接测。
2. **语义模式**：配置 embedding provider，对 memory 重建索引后测。

配置示意（字段名以你所用版本为准）：

```json
{
  "agents": {
    "defaults": {
      "memorySearch": {
        "provider": "openai",
        "model": "text-embedding-3-small"
      }
    }
  }
}
```

结果（样本小，仅供参考）：

| 维度 | 全文 | 语义 |
|---|---|---|
| 改述类命中 | 4/10 | 9/10 |
| 精确词命中 | 10/10 | 6/10 |
| 单次延迟 | <50ms | 300–800ms |
| 成本 | 0 | 每次查询和写入都有 embedding 调用 |

## 踩坑点

- **语义检索是外部 API 依赖**：断网或 key 失效时，recall 会静默变差。一定确认 fallback 行为，最好显式回退到全文。
- **索引陈旧**：手工改了 `MEMORY.md` 之后，embedding 索引不会立刻更新。我测出“召回变差”的案例里，有一半其实是忘了重建索引。
- **短查询表现一般**：两三个字的查询用语义搜经常漏，chunk 切太大也会稀释相关度，我最后按小节切块。
- **中英混写条目**：纯语义偶尔丢掉中文侧信息，评测集里两种语言都得覆盖。

## 可复用建议

1. memory 规模小（几百条以内）就别上语义。全文 + 把条目写成“关键词行 + 说明行”的固定格式，性价比最高。
2. 真要上，优先用 hybrid 思路：全文保精确词，语义保改述，结果合并。OpenClaw 的 memorySearch 配置里 fallback/混合的玩法值得用满。
3. 把“reindex 后再评测”写进习惯：每次改完 memory 必跑一遍固定查询集，否则你调的是玄学。
4. 检索质量的上限不在搜索算法，而在 memory 的写法。与其调参，不如约束自己写 memory 时带上时间、专有名词和别名。

## 总结

这不是二选一：全文是免费的基线，语义是花钱买泛化，hybrid 是工程上正确的答案。我目前的配置是：日常 hybrid，降级时回全文，高频精确词场景手工维护一个关键词索引段。`memory_recall` 的上限，取决于你的 memory 写得像不像一个“可检索的数据库”，而不是你选了哪个搜索引擎。
