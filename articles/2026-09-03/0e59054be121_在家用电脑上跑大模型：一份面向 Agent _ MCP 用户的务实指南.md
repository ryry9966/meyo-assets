# 背景

做 Agent / MCP 自动化的社区用户迟早会撞上两个问题：一是数据不想出本地——MCP 工具能读文件、跑命令，接云端模型意味着把这些上下文全部发出去；二是高频调用的成本。本地部署一个开源模型充当"常规任务工人"，是很多人的折中选择。

先泼冷水：本地模型在推理能力上与旗舰云端模型有可见差距。它卖点是"够用且可控"，不是"更强"。抱着升级大脑的预期入场，大概率会失望。

# 硬件与选型

Q4 量化下的经验值：

- 7B/8B：8GB 显存或 16GB 内存即可起步
- 14B：12GB 显存比较稳
- 32B：24GB 显存起步，否则会触发 CPU offload
- Mac 统一内存：看总量，32GB 机器跑 14B 很舒服

选型重点不是榜单分数，而是 **function calling 的可靠性**。Agent 场景下，一次格式错误的工具调用就是一轮重试。优先选官方声明支持工具调用、且有社区实测反馈的模型系（Qwen、Llama 3.1+ 这类），别只看跑分。

# 部署步骤

1. 装 Ollama（或 llama.cpp server / LM Studio），先 pull 一个 8B 级模型试水。
2. Ollama 自带 OpenAI 兼容接口 `http://localhost:11434/v1`，在 OpenClaw 的 provider 配置里当作自定义 OpenAI 兼容端点接入即可，API key 随意填。
3. 关键参数：把上下文长度**显式**调大（Ollama 默认 num_ctx 很小），设置 keep_alive 避免每次请求重新加载模型。
4. 先挂一个最简单的 MCP 工具做连通性测试，确认模型能稳定发起调用，再上完整工具集。
5. 用你真实的 Agent 任务跑一天，记录工具调用成功率和 token 速度，再决定是否升级模型。

# 踩坑点

- **上下文静默截断**：默认上下文太小，系统提示词和工具定义被截掉，表现为"模型不会用工具"，实际是工具定义根本没进上下文。这是最常见的误判。
- **显存溢出**：上下文一长，KV cache 涨得比权重快，超出显存后 offload 到 CPU，速度从 30 tok/s 掉到 3 tok/s，Agent 循环直接不可用。
- **并发串行**：本地推理基本是串行的，多个并行 Agent 任务会排队，超时重试还会加剧拥堵。
- **小模型的 JSON 输出**：temperature 调低，能上结构化输出约束就上，别指望 8B 模型在自由生成下每次都吐出合法 JSON。

# 可复用建议

- **分层路由**：摘要、分类、简单工具调用走本地；复杂推理走云端。路由本身用规则甚至小模型实现即可，不必做得很聪明。
- **固定回归集**：留一组固定的提示词 + 工具调用用例，每次换模型、改参数后跑一遍，五分钟判断这次改动是升级还是降级。
- **量化别太狠**：Agent 用途下 Q4_K_M 基本是底线，更激进的量化省下的显存，会被工具调用失败率加倍吃回去。
- **配置收敛**：本地端点也走统一的 provider 配置，换模型只是改一行，方便 A/B 对比。

# 总结

本地部署的价值在于可控：数据不出门、调用不计费、深夜批量任务随便跑。把 8B–14B 的本地模型当成 Agent 体系里"勤快但不太聪明的一线员工"，把难点留给云端，是当前家用硬件下最务实的架构。部署本身不难，难的是用真实任务持续度量——别凭聊天体感下结论。
