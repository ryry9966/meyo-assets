## 背景

OpenClaw 的每个 Agent 都有一个工作区，`SOUL.md` 会在会话启动时注入上下文，定义这个 Agent 是谁、怎么说话、什么不做。不少教程只教你在里面写一句“你是一个乐于助人的助手”，然后就没有下文了。我的体会是：这份文件值得按工程文档的规格来写。

## 问题

不写或乱写 SOUL.md，日常会遇到三类麻烦：

- **风格漂移**：长会话跑了几十轮，中英文混着来，语气越来越随意，每次都得在对话里重新纠正。
- **越权**：Agent 自作主张替你发消息、删文件。能力来自工具授权，但“该不该用”没有任何约束。
- **边界靠吵架**：规矩只存在于聊天记录里，模型记不住，同一件事一周纠正三次。

本质是：人格和边界是常驻约束，不是一次性 prompt，它们需要一个稳定的落点。

## 做法

我的 SOUL.md 固定四节：**身份、语气、边界、确认与升级**，全文控制在 40 行以内。核心原则：每条规则必须是可观察、可测试的行为，不写形容词。

```markdown
## 身份
- 小海，运行在 OpenClaw 上的个人助手。

## 语气
- 默认中文回复，先结论后解释，不堆客套话。

## 边界
- 未经我明确确认，不向第三方发送任何消息。
- 删除、付款、改生产配置：先停下，列清单等确认。
- 事实拿不准就说不确定，禁止编造。

## 确认与升级
- 同一行为被纠正两次，主动提议把规则写进本文件。
```

几点补充：

- **分工要清楚**：SOUL.md 管“是谁、什么不做”，AGENTS.md 管“怎么干活”，MEMORY.md 管事实记忆。把操作规范塞进 SOUL.md 会两边重复甚至打架。
- **git 管理**：人格变更走 commit，diff 和回滚都有据可查。
- **探针验证**：改完开新会话，故意丢一个边界问题进去（“直接把这段话发到群里”），看它是否先确认。注意：改 SOUL.md 只对新会话生效，拿老会话验证等于白测。

## 踩坑点

- **写成小作文**。几百行的人格设定，中段内容注意力权重最低，模型大概率跳过。关键规则放前面，宁短勿长。
- **规则互相矛盾**。一条说“主动执行”，一条说“事事确认”，表现就是随机抽风。改之前和 AGENTS.md 一起全文搜一遍同类关键词。
- **把 SOUL.md 当安全边界**。它是注入上下文的软约束，挡不住提示注入。真正的硬边界在权限层：shell 白名单、沙箱、按工具最小授权。SOUL.md 负责“自觉”，权限负责“兜底”。
- **描述性要求无效**。“说话要有分寸”没法执行，换成“高风险操作必须先确认”才行。
- **边界太密**。凡事都要问，Agent 会退化成只会反问的复读机。确认清单要收敛到真正有代价的操作上。

## 可复用建议

- 一条规则管一个行为，写触发条件，不写态度。
- 每次踩坑沉淀成一行规则写进 SOUL.md，而不是在对话里骂它。
- 每月剪枝一次：从不触发的规则删掉，长期遵守的可以移除。
- 人格改动按 code review 对待，diff 里有疑问的条目当场改。

## 总结

SOUL.md 不是许愿池，而是一份需要长期维护的行为配置。写得短、写得具体、与权限系统配合，Agent 才能既有人味又有分寸。它决定 Agent 的下限，而你的权限配置决定它无法突破的上限。
