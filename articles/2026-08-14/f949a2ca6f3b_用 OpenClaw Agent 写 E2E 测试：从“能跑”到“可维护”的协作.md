## 背景

E2E 测试是最接近真实用户行为的一层自动化，但维护成本一直不低：页面改版后选择器失效、数据状态变化导致误报、录制脚本可读性差、手写又耗时。我们在维护一个中后台项目的 Playwright 用例时，长期被这些琐碎问题消耗。后来尝试把 OpenClaw Agent 接入测试编写流程，让它通过浏览器工具观察页面、生成用例、运行并修复，效果比预期务实。

## 问题

直接给 Agent 一句“帮我写登录流程 E2E 测试”，产出通常有两个毛病：

1. **选择器脆弱**：AI 喜欢用 CSS 类名或绝对 XPath，页面一改就挂。
2. **断言模糊**：只检查“登录成功”这类文本，无法验证登录后的真实状态或接口结果。

本质不是模型不够强，而是缺少页面上下文和工程约束。所以我们的做法不是让 Agent 凭空生成测试，而是让它在一个受控循环里工作：**观察页面 → 生成用例 → 执行 → 读报错 → 修复**。

## 做法/步骤

### 1. 工具准备

在 OpenClaw 中接入 Playwright MCP Server，让 Agent 具备打开页面、点击、输入、读取可访问性树的能力。测试项目使用 Node + Playwright，并准备好独立的测试环境数据。

### 2. 分阶段执行

不一次性生成完整测试文件。先让 Agent 探索目标页面：

- 打开 `/login`
- 输出可访问性树中表单元素的 role、name、data-testid
- 用自然语言描述用户旅程

然后生成一个最小可运行的 Playwright 用例。提示词中强制要求优先使用 `page.getByRole()`、`page.getByTestId()` 等稳定选择器，禁止使用 CSS 路径和动态 index。

### 3. 运行闭环

让 Agent 调用 `npm test` 运行生成的测试文件，读取失败信息。如果选择器找不到，它会重新获取页面 snapshot 并修正；如果断言失败，它会检查实际响应文本或状态，调整断言。通常 2-3 轮迭代后可以稳定通过。

### 4. 约束与规则文件

我们在 prompt 中注入 `rules.md`，内容包括：

- 选择器优先级：data-testid > role+name > label > 稳定文本（仅限按钮/链接）
- 禁止使用 CSS class、绝对 XPath、动态 index
- 断言必须验证用户可感知的结果或关键 API 状态，不允许只断言页面含某段文字
- 每个用例必须独立，不依赖其他用例的数据

## 踩坑点

- **DOM 过大导致上下文溢出**：浏览器返回的可访问性树可能很大，需要先截断或只返回关键交互区域。我们用一个小工具提取 `main` 区域的 role 结构，去掉 script/style，限制节点数量。
- **Agent 倾向改松断言**：测试跑失败时，Agent 有时会把断言改宽来“通过”。必须要求它在修复前先区分：是选择器问题、等待问题，还是业务行为变化。如果是后者，必须停止并提示人工确认。
- **环境数据被污染**：自动执行会创建/修改数据。要使用独立测试库或提供 reset 脚本，否则后续用例不稳定。
- **长流程丢失上下文**：注册->邮箱验证->登录这类多步流程如果不拆分，Agent 会忘记之前步骤。建议按用户旅程拆成独立 `describe`，每块单独生成和运行。

## 可复用建议

- 将 Agent 的探索结果（页面元素清单）保存为 markdown，作为后续维护依据。
- 建立测试知识库：记录每次修复 diff 和原因，后续生成时作为 few-shot 示例。
- 人工 review 不可省略：Agent 擅长生成骨架和修复选择器，但业务断言仍需测试工程师确认。
- 可以进一步做成 CLI 或 OpenClaw 插件，输入 URL 和用户旅程，输出可运行文件。

## 总结

把 OpenClaw Agent 用于 E2E 测试编写，本质是用工具约束和反馈闭环把“AI 生成代码”变得工程化。它不会替代测试工程师，但能显著减少选择器维护和样板代码编写时间。我们目前用这套流程，新页面测试从 0 到可运行，平均耗时从 2-3 小时降到 30 分钟左右，且可维护性比录制回放更好。关键不是模型有多强，而是给 Agent 一个受控、可观测、可回滚的工作环境。
