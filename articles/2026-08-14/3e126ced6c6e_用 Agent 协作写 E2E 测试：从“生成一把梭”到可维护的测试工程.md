## 背景

E2E 测试的维护成本一直不低。页面改版、选择器失效、登录态过期、动态内容加载不稳定，都会让原本能跑的用例变成“红色告警”。AI 确实能帮你生成测试代码，但如果你只是丢一句“帮我写个登录页的 E2E 测试”，最后大概率会得到一份看似完整、实际跑不起来的 Playwright 脚本：选择器抓得很随意，断言全是文案，等待策略缺失。

在 OpenClaw 这类支持多 Agent 与 MCP 工具调用的环境里，更适合的做法不是让一个 Agent 一次性生成测试，而是把“探索页面、生成用例、执行验证、失败修复”拆成协作流。这样每个 Agent 的上下文更聚焦，输出更容易校验。

## 问题

单个 Agent 直接写 E2E 测试有几个典型问题：

- 没有真实页面上下文，只能靠猜 DOM 结构；
- 生成的 CSS class 选择器非常脆弱；
- 不会主动执行测试，无法根据失败信息修正；
- 容易把截图或静态文案当成业务断言；
- 长上下文里混入大量 HTML，导致模型抓不住重点。

本质上，缺的是一个“运行时反馈闭环”。测试代码必须被执行过、失败过、修过，才可能接近可维护状态。

## 做法 / 步骤

我在 OpenClaw 里用四个子 Agent 搭了一条 E2E 测试生成流水线，主 Agent 只做调度和参数传递。

### 1. 工具准备

先给 OpenClaw 接入 Playwright MCP。这样 Agent 可以真实打开浏览器、点击、读取可访问性树、截图、执行 JS，而不是只做文本推测。

MCP 配置大致如下：

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}
```

### 2. Explorer Agent：只做页面探索

Explorer 负责打开目标页面，收集关键交互元素和业务路径。它的输出不是一段测试代码，而是一份结构化的页面对象草稿，包含：

- 可点击元素：按钮、链接、菜单项；
- 输入元素：输入框、下拉框、文件上传；
- 关键状态：加载完成标志、错误提示区域；
- 路由变化：点击后是否跳转、URL 变化；
- API 请求：登录、提交表单时调用了哪些接口。

这里要给它强约束：优先读取 `data-testid`、`role`、`label`，不要把整页 HTML 塞进结果。最多输出 150 行以内的结构化 JSON 或 Markdown。

### 3. Generator Agent：根据草稿生成测试

Generator 只接收 Explorer 的草稿和一份需求描述，生成 Playwright 测试代码。Prompt 里明确规定：

- 选择器只允许 `data-testid`、`getByRole`、`getByLabel`；
- 等待策略使用 `expect(locator).toBeVisible()` 或 `waitForResponse`；
- 断言业务状态，例如“登录后跳转到 /dashboard，并出现用户菜单”，而不是断言按钮文案；
- 每个用例独立，不共享可变状态。

### 4. Runner Agent：执行并回传失败

Runner 执行 Generator 生成的测试，如果失败，把失败堆栈、截图、trace 片段回传给 Generator。Generator 根据失败信息修复，再交给 Runner，最多循环 3 轮。超过 3 轮仍失败，就标记为 `needs-human`，不再自动改。

这一步很关键。没有 Runner，Generator 永远不会知道自己的选择器有多脆弱；没有重试上限，协作流会陷入死循环。

### 5. Reviewer Agent 或人工确认

最后让 Reviewer 做一次稳定性检查：是否存在重复用例、是否有只靠截图通过的断言、是否覆盖了需求里的关键路径。如果团队已有测试基线，这一步也可以只做 diff review。

## 踩坑点

### 1. 选择器脆弱

AI 默认喜欢抓 `div > div > button`、`text=登录` 或动态 class。必须在一开始锁死选择器策略，否则生成的用例跑两次就挂。最有效的办法是开发侧补充 `data-testid`，但这需要跨团队推动。短期可以退回 `getByRole`，并禁止任何 xpath。

### 2. 登录态被忽略

每次跑 E2E 都重新登录，既慢又容易触发风控。建议使用 Playwright 的 `storageState` 保存登录态，Runner 执行前加载，而不是让 Agent 自己处理登录流程。

### 3. 动态内容等待不足

Agent 生成的代码经常在页面还没渲染完就点击、断言。需要强制加入 `await expect(page.getByRole('button', { name: '提交' })).toBeVisible()` 这类显式等待，或者等待关键 API 响应后再继续。

### 4. 把截图当断言

截图只能证明“看起来对了”，不能证明业务逻辑正确。应断言 DOM 结构、URL、网络响应、表单提交结果。截图仅用于失败排查。

### 5. 修复循环浪费 token

有时候测试挂掉不是选择器问题，而是测试环境没有权限、后端接口挂了、测试数据过期。Agent 一遍遍改选择器是徒劳的。设定最大重试轮数，并让 Runner 把环境错误和断言错误分类，能有效降低浪费。

### 6. 上下文膨胀

不要在 Agent 之间传整页 HTML。Explorer 输出应该只保留可访问性树片段和关键交互元素。否则多轮协作下来，上下文长度会爆炸，模型开始丢信息。

## 可复用建议

- **先把冒烟路径固化成 Golden Test**。让 Agent 在已有基线上做增量补充，而不是从零生成整个测试套件。
- **限制 Agent 可调用的 MCP 工具**。只暴露 `read_snapshot`、`click`、`fill`、`expect`、`screenshot` 等必要动作，避免 Agent 自己执行奇怪脚本。
- **用标签分层**：`@smoke`、`@e2e`、`@regression`，CI 里按标签执行，避免每次全量跑。
- **Prompt 模板版本化**。把选择器策略、等待策略、断言规则沉淀成团队模板，不同项目复用。
- **生成后必须真实跑一遍**。AI 生成的测试不算资产，只有通过 Runner 验证并入库的才算。

## 总结

Agent 协作写 E2E 测试的价值，不在于“自动生成一堆测试文件”，而在于把探索、生成、执行、修复串成一个可重复的工程闭环。比起让一个 Agent 大包大揽，拆成职责单一的子 Agent 更容易控制质量，也更容易定位问题。

如果你已经在 OpenClaw 上跑 Agent，可以先把 Playwright MCP 接进去，用一条登录路径做最小试验。不要追求一次性覆盖所有用例，先把“生成-执行-修复”的循环跑通，再逐步扩大到回归集。
