在 OpenClaw 里跑长任务 Agent 时，经常要面对一个很现实的问题：插件、MCP server、浏览器自动化服务或本地工具进程可能随时挂掉，而 Agent 自己并不知道。等真正调用到不可用服务时，往往已经浪费了几轮工具调用和上下文。heartbeat 就是给这些依赖加一层“活着且能接活”的探测。

但 heartbeat 很容易被做成两种极端：要么每 5 秒轮询一次，把 MCP server 或网关刷出压力；要么上推送，结果连接管理、重连、代理超时一堆坑。本文聊聊在 OpenClaw/Agent/MCP/插件自动化场景下，轮询和推送怎么选、怎么做，以及哪些坑值得避开。

## 背景

OpenClaw 的 Agent loop 通常依赖多个外部组件：MCP server、插件服务、HTTP API、浏览器控制端等。heartbeat 的主要目的不是“证明服务存在”，而是让调度层及时知道某个工具或数据源是否可用，以便在调用前降级、熔断或切换。

这类场景有几个特点：

- Agent 的调度频率不稳定，有时几分钟才调用一次外部服务。
- MCP server 可能通过 stdio、SSE 或 HTTP 暴露能力。
- 插件服务经常跑在容器或本地进程里，重启后端口还在但状态不一定 ready。
- 心跳信息如果进到 LLM 上下文，会消耗 token 并干扰推理。

## 问题

轮询实现简单，客户端定时请求 `/healthz` 或 `ping` 即可。但频率不好把握：太密会占用连接、触发限流；太疏则故障发现延迟高。

推送看起来更实时，但引入长连接后，要处理断线重连、鉴权、顺序、背压、代理超时。对于多数插件和 MCP 场景，推送并不是免维护的。

所以核心取舍不是“哪种技术更好”，而是：**你的故障容忍时间是多少？可维护的连接复杂度有多少？**

## 做法/步骤

### 1. 先区分 liveness 和 readiness

不要用一个 `/healthz` 同时表达“进程活着”和“能接活”。进程活着不代表 MCP server 已经初始化完成、数据库连接池可用、模型客户端已加载。

建议：

- `liveness`：进程在、事件循环没卡死。
- `readiness`：可以接受工具调用或数据请求。

例如 MCP server 返回 `status: "ready"` 才允许 Agent 调用工具。

### 2. 默认用低频轮询 + jitter

在 OpenClaw 插件或宿主层做轮询，不要每个 Agent 各自起一个高频探测。推荐频率从 30s 起步，加 ±20% jitter，避免多个客户端同时打同一服务。

示例心跳请求：

```text
GET /healthz
Timeout: 3s
```

连续 3 次失败才标记为不可用。恢复后先进入半开状态，成功 1 次再恢复。

### 3. 推送优先用 SSE

需要秒级状态更新时，优先用 SSE，而不是 WebSocket。SSE 基于 HTTP，天然支持重连、代理穿透、断线恢复，客户端可以用 `EventSource` 直接接。

服务端发送：

```text
event: heartbeat
data: {"ts":1710000000000,"status":"ready","load":0.4}
```

SSE 的关键是服务端要定期发送注释行或 keepalive，防止代理断开。

### 4. 心跳信息不要进 Agent 上下文

心跳应该放在宿主层或调度层处理，作为 metadata、header、独立事件通道存在。不要把每次心跳都转成 chat message 塞给模型，否则会污染上下文并消耗 token。

如果是 MCP，可以在宿主层调用 `ping` 或 `health` 方法，但不要通过 LLM 工具调用来完成心跳检测。

## 踩坑点

### 1. 轮询打满 MCP server

有些 MCP server 基于 stdio 或长连接，并发能力有限。高频轮询会占用连接通道，导致真正的工具调用排队或超时。建议心跳请求独立于工具通道，或者用 HTTP health 端点替代工具调用。

### 2. 反向代理静默断开 SSE/长连接

Nginx 默认 proxy read timeout 可能只有 60s。SSE 连接长时间没有业务消息时会被断开，客户端频繁重连。需要设置：

```nginx
proxy_buffering off;
proxy_read_timeout 3600s;
```

并在应用层发送 keepalive 注释行或短心跳。

### 3. 重连风暴

服务端重启后，所有客户端同时重连，瞬间打满连接队列。必须在客户端加重连抖动和指数退避，例如 1s、2s、4s，上限 30s。

### 4. 把 heartbeat 变成 token 黑洞

这是 Agent 场景最隐蔽的坑。心跳消息一旦进入 LLM 上下文，每轮对话可能多消耗几百 token。正确做法是：宿主层处理心跳，只把“服务不可用”或“服务恢复”的状态变化作为系统提示注入。

### 5. 忽略背压

如果推送客户端消费不过来，旧心跳会堆积。客户端应该丢弃过期心跳，只保留最新状态，或者做合并。

## 可复用建议

- 默认 30s 轮询 + jitter，失败阈值 3 次，指数退避上限 5min。
- 只有需要秒级感知才上 SSE；WebSocket 留给双向二进制或短交互。
- 心跳契约固定为 `type/ts/status/load/version`，用 epoch ms，别依赖本地时间。
- MCP server 暴露 `/healthz` 或 `ping`，不要通过 LLM 工具调用做健康检查。
- 在 OpenClaw 宿主层做统一健康检查，避免多个 Agent 对同一服务重复探测。
- 监控心跳 RTT、失败次数、恢复时间，这些数据比“服务是否在线”更有价值。

## 总结

轮询是基础，推送是优化。对 OpenClaw 这类 Agent 自动化场景，从低频轮询开始，把故障语义和降级路径定义清楚，比一开始就上复杂推送更务实。心跳不是越频繁越好，关键是让 Agent 在服务真正不可用之前或发生时，做出正确的降级决策，而不是把问题藏在一堆心跳日志里。
