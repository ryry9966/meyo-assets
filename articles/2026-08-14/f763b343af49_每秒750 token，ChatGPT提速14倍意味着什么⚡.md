“一夜提速14倍”这个说法，单看很像营销话术，但如果把它拆成 token、推理优化和工程权衡三层，能聊出不少硬核内容。近期网传 GPT-5.6 Sol 的推理速度达到每秒 750 token，比现有模式快约 14 倍。数字是否完全准确还有待官方基准，但“更快推理”的方向没有悬念。这篇文章不吹速度，只算技术账。



## 一、750 token/s 到底把什么变快了

先说明一个基础概念：token 不是单词，也不是字符，而是 BPE 这类分词算法切出来的子词单元。以英文为例，“unbelievable”可能被切成“un”和“believable”两个 token；中文常见模型里，一个汉字往往占 1~2 个 token。因此 750 token/s 不代表 750 个完整词，但在英文中大约相当于每秒 500 词以上，在中文里理论上接近每秒 400~500 个汉字。

对比来看，目前很多消费级聊天界面的输出速度在 30~80 token/s；如果能稳定跑到 750 token/s，大约就是 10~20 倍量级，网传的 14 倍在这个区间内。

用一个更直观的例子：生成一篇 1500 字左右的中文回答，假设按 2 token/字计算是 3000 token。速度 50 token/s 需要 60 秒，速度 750 token/s 只需要 4 秒。用户感知会从“等一杯咖啡”变成“刷新一下”。

这里还要区分两个阶段：prefill 和 decode。prefill 是模型第一次读入整段 prompt，decode 才是逐 token 输出。750 token/s 通常指 decode 阶段的稳态速度，而不是你按下回车后第一秒就能看到完整答案。



## 二、提速14倍不是魔法，而是推理链路重构

大模型生成文本是自回归的：每次只能根据前文预测下一个 token，然后把新 token 拼回上下文，再预测下一个。由于每一步都要访问长度为 L 的 KV cache，当批次大、序列长时，主要瓶颈不是 GPU 的浮点算力，而是显存带宽。

单纯加算力不划算，于是工程上出现了几条主流路线：

1. **投机解码（speculative decoding）**：先让一个小模型快速猜出 K 个 token，大模型再并行验证。如果前 n 个正确，就一次接受 n 个 token。平均每个大模型前向步骤能产出多个 token，可带来 2~3 倍提升。
2. **多头并行解码（Medusa 等）**：在大模型最后层加多个预测头，一次同时预测后续多个位置，换取吞吐。
3. **MoE 稀疏激活**：模型包含多个专家，但每次推理只激活一部分，降低每个 token 的实际算力消耗。
4. **量化与蒸馏**：用 FP8、INT8 等低精度权重减少显存读取；或把大模型能力蒸馏到小模型，降低绝对计算量。
5. **推理系统优化**：continuous batching 把多个请求拼批，提高 GPU 利用率；PagedAttention 减轻显存碎片；prefill/decode 分离可以把不同阶段调度到不同硬件。

所以 14 倍大概率不是某个开关被打开，而更像乘法叠加。如果每一步优化带来 1.4 倍、1.6 倍、2 倍，乘起来很容易到十几倍。硬件代际升级带来的显存带宽提升，也会直接反映在 decode 速度上。



## 三、每秒 token 是重要指标，但不是唯一指标

750 token/s 是吞吐指标，不是完整延迟指标。你发出去 50k token 的 prompt，prefill 阶段可能还要先处理几秒；如果输出只有 10 个 token，那 750 token/s 的优势几乎体现不出来。

投机解码等并行技术还会让输出出现轻微“短时停顿再跳一段”的节奏，因为多个候选要一起验证。如果采用激进量化或蒸馏，可能对复杂推理、长尾知识、多语言一致性带来退化。

另一个容易被忽略的是成本：速度提升让单卡能同时服务更多请求，但电力与显存带宽不会凭空消失。对用户来说，如果仍按 token 计费，快的体验未必等于更省钱；对服务商，吞吐密度提升通常能降低单位成本，但也会吸引更多调用。

更完整的评估至少还应该看：

- **TTFT（time to first token）**：第一个 token 多久出现。
- **TPOT（time per output token）**：后续每个 token 的稳定间隔。
- **tokens per dollar**：每块钱能买多少 token。
- **tokens per watt**：每瓦电能生成多少 token。

速度是体验的必要条件，但不是充分条件。一个又快又抖、长上下文掉速严重的模型，远不如一个中等速度但稳定的模型。



## 四、更快推理会先改变哪几类产品

实时语音可能是受益最明显的方向。语音交互的体感阈值大约在 300~500 毫秒。过去 LLM 生成一个短回复要 1~2 秒，常需靠预生成、流式播放来掩盖；750 token/s 可以把一个短回复的生成时间压缩到 0.2~0.5 秒以内，打断、插话、同声传译才有真正的产品意义。

代码补全也会更快。IDE 的本地补全通常在几十毫秒返回，云端 LLM 如果只跑 30 token/s，补一个 20 token 的建议要 0.6 秒，程序员会感觉卡；提升后可以接近本地 IntelliSense 的体验。

AI Agent 的收益更大。多步操作要反复调用工具、读回结果、再做决策，每一步生成时间缩短，任务完成时间会成倍下降。速度和稳定性直接决定一个 Agent 能不能跑完复杂流程。

内容生产也会从“生成一段等一段”变成实时协作流。过去用户等待时可能切走注意力，现在模型输出速度超过阅读速度，交互会从“读取结果”变成“筛选和编辑结果”。

但“想得快”不等于“想得深”。复杂数学证明或长链规划需要串行推理和多轮自我校验。如果模型没有足够的推理时间预算，快模型也许只是更快地给出自信的错误答案。速度提升解决的是吞吐和延迟，不直接解决推理能力上限。



最后，三条冷思考：

1. **看实测，不看截图**：关注公开 benchmark、复现脚本和自己 workload 下的 TTFT/TPOT，不要只信宣传稿里的单个数字。
2. **快不等于便宜**：比较 tokens per dollar 和 tokens per watt，才能判断是否值得切换。
3. **为产品而快**：如果业务不是实时语音、代码补全或多步 Agent，750 token/s 的收益可能有限；先把用户等待痛点和成本结构算清，再决定是否升级。
