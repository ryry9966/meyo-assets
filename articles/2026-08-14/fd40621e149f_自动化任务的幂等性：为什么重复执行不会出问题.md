在 OpenClaw、Agent、MCP 这类自动化链路里，任务从来不是“只跑一次”。定时触发、消息重投、人工补跑、Agent 重试，都会让同一个任务被执行多次。很多自动化事故不是逻辑写错，而是任务本身不幂等：重复执行产生重复数据、重复扣款、重复推送。

## 问题

一个常见场景：某个插件定时抓取数据，抓完后调用 MCP 工具写库并推送通知。某次写库超时，调度器判定失败并自动重试。结果数据被写入两次，通知也发了两条。排查代码时发现业务逻辑没有问题，问题在于整个执行链路没有幂等保护——重试对下游而言是一次全新的调用。

## 做法/步骤

### 1. 给任务实例一个稳定的幂等键

不要用随机 UUID 或当前时间戳作为幂等键，它们每次执行都不同。要用业务维度唯一标识，例如：

- `task:sync_order:{order_id}`
- `cron:daily_report:{date}`
- `agent:process_file:{file_hash}`

Agent 调用 MCP 工具时，可以在参数或请求头里显式传递 `idempotency_key`，由工具侧做去重。

### 2. 执行前先“占位”

用 Redis `SET key value NX EX` 或数据库唯一约束插入一条执行记录。如果占位失败，说明相同任务已经在执行或已经完成，直接返回已有结果或跳过。

注意：占位和业务操作之间要保持尽量短的事务边界。如果占位后进程崩溃，任务可能卡在“执行中”状态，需要配合超时释放或状态机处理。

### 3. 对副作用做“可检查再执行”

例如先查询是否已存在该订单的处理记录，没有再写入。对于发送通知这类没有查询接口的操作，可以先记录“待发送”，发送成功后更新为“成功”；重试时发现状态已是“成功”，直接跳过。

### 4. 给外部 API 传递幂等键

很多支付、消息、存储 API 原生支持 `Idempotency-Key` 头。即使你自己的代码不重试，上游 SDK 也可能因为网络问题重试。统一在 OpenClaw 插件或 MCP 客户端里封装：每次调用外部服务都生成稳定幂等键并传递过去。

### 5. 用数据库唯一约束兜底

数据库层加 `UNIQUE(task_key, biz_id)`。即使应用层检查有漏洞，重复插入也会被拒绝。捕获唯一约束冲突后，查询现有记录并返回，而不是报错。

## 踩坑点

- **把执行 ID 当幂等键**：执行 ID 每次运行都不同，幂等键必须业务稳定。
- **只做内存去重**：单实例有效，多实例部署或重启后失效，必须依赖持久化存储。
- **先查后写有竞态**：两个请求同时查询都不存在，然后都执行写入。要用 `INSERT ... ON DUPLICATE KEY` 或事务加唯一索引。
- **对无幂等能力的第三方调用“裸奔”**：比如发短信、推送，重复执行必然产生副作用，需要包一层状态机或队列消费确认。
- **假成功**：任务被幂等拦截后直接返回成功，但下游资源实际未准备好，造成“看起来成功、实际没做”。跳过时需要校验现有状态是否完整。

## 可复用建议

把幂等做成 OpenClaw 任务/插件的基础能力，而不是每个任务各写一遍。在任务入口统一生成、注册、检查幂等键；MCP 工具调用自动携带幂等键。每次写自动化任务前先问一句：“这个操作重复执行会发生什么？”如果答案不是“无影响”，就值得设计幂等。对非幂等操作，用状态机或队列消费确认，而不是直接执行。保留执行记录，方便人工补跑时判断哪些已做、哪些没做。

## 总结

自动化任务重复执行不是异常，而是常态。幂等性不是高深理论，而是几个工程习惯的组合：稳定幂等键、持久化占位、数据库唯一约束、下游幂等传递、状态可查。在 OpenClaw/Agent/MCP 场景里，越早把幂等做进插件和工具调用，后期排障成本越低。
