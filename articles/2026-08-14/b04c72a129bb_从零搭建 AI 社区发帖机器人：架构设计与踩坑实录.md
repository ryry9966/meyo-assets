## 背景

社区运营里，发帖这件事看起来简单，但量一大就很消耗人：整理素材、排版、选标签、预览、发布、发布后再改错别字。我们想做一个“半自动发帖机器人”，目标不是完全替代人，而是把重复部分自动化，保留人工确认环节。

技术栈选 OpenClaw 做任务编排，接入一个社区 HTTP API 的 MCP server，LLM 负责生成初稿和元数据。本文记录的是从零搭建到稳定可用的过程，重点写架构和踩坑。

## 问题

直接用“大模型 + 一句话 prompt”发帖会踩一堆坑：

- 生成内容不稳定，格式漂移严重，偶尔还输出多余解释。
- 发布涉及登录态、草稿、预览、正式发布多个步骤，中间容易断。
- 上下文容易被上一篇内容污染。
- 社区接口有限流和风控，频繁自动发布会触发验证码。
- 一旦自动发布失败，很难知道卡在哪一步。

所以一开始就没有做“全自动发布”，而是做成“生成草稿 → 人工确认 → 发布”的半自动链路。

## 做法

架构分四层：

1. **生成层**：OpenClaw agent + 本地素材库 + 结构化 prompt。
2. **审核层**：规则校验 + 人工确认。
3. **发布层**：MCP server 封装社区 API，只暴露草稿、预览、发布三个动作。
4. **状态层**：SQLite 记录任务状态、草稿 ID、重试次数、错误信息。

### 1. 生成层

素材库用本地 Markdown 片段，避免模型编造。每篇帖子 prompt 强制输出 JSON：

```json
{
  "title": "标题候选",
  "content": "Markdown 正文",
  "tags": ["OpenClaw", "MCP"],
  "summary": "摘要",
  "cover_prompt": "英文知识卡 prompt"
}
```

OpenClaw agent 每次只做一件事：读取素材片段 → 生成 JSON → 落盘。任务完成后立即清空上下文，避免多篇内容串味。

### 2. 审核层

生成结果先过规则校验：标题长度、标签数量、是否包含敏感词、外链是否在白名单内。规则通过后进入人工审核队列，人工可以在本地预览 Markdown 和渲染效果，确认后才会进入发布层。

这里没有让模型自己审自己，因为自审很容易放过格式漂移和事实错误。

### 3. 发布层

MCP server 封装了社区的草稿创建、草稿预览、正式发布接口。发布动作带幂等键：

```
create_draft(title, content, tags) -> draft_id
preview_draft(draft_id) -> rendered_html
publish_draft(draft_id, idempotency_key) -> post_id
```

每次发布前必须调用一次 preview，确认渲染结果和预期一致。发布接口返回 401 或触发了风控，直接转人工处理，不自动重试。

### 4. 状态层

任务状态机用 SQLite 记录：

```
pending → generated → approved → publishing → published / failed
```

每一步落盘，支持手动 resume。发布失败时保留 draft_id 和错误信息，避免重复创建草稿。

## 踩坑点

**1. JSON 输出不稳定**

指定 JSON schema 后，模型偶尔还会在 JSON 前后加解释文字，比如“好的，以下是结果：”。解决方法是解析时只提取第一个 `{...}` 块，解析失败直接进人工队列，不让坏数据进入发布层。

**2. 登录态失效**

社区 Cookie 过期或要求手机验证码时，发布接口会返回 401。我们不做自动重新登录，而是发通知给运营人工处理。因为自动过验证码会引入更多风险，收益不高。

**3. Markdown 渲染差异**

本地 Markdown 看起来正常，发布到社区后代码块换行被吞、列表缩进错乱。原因是社区渲染器对空行和缩进敏感。解决方法是发布前必须调 preview 接口，必要时把预览 HTML diff 展示给人工确认。

**4. 上下文污染**

早期在一个 OpenClaw session 里连续生成多篇，发现第二篇会混入第一篇的术语和结构。改成每个任务独立 session，并在每个生成任务结束后显式清空上下文，问题消失。

**5. 任务中断**

Agent 长链路在“生成 → 审核 → 发布”之间容易中断，比如网络超时、接口限流。状态落盘后可以从失败节点 resume，不需要从头重跑。

**6. 限流和风控**

社区对短时间创建草稿有频率限制。后面改成批量生成草稿、人工集中确认后再逐条发布，发布间隔加随机延迟。稳定性提升明显。

## 可复用建议

- **先做草稿，再做发布**。全自动发布看起来很酷，但一次事故就够受的。
- **发布动作必须幂等**。接口可能超时但实际发布成功，幂等键能避免重复发帖。
- **日志记录 prompt 版本和模型参数**。内容质量出问题时能快速定位是 prompt 改了还是模型换了。
- **MCP 解耦社区 API**。换站点时只改 MCP server，OpenClaw agent 和上层逻辑不动。
- **素材库用 Markdown 片段**，不要完全依赖模型生成事实内容。
- **状态要落盘**。不要只存在进程内存里，能 resume 的自动化才敢在生产用。

## 总结

这个发帖机器人从零到稳定，核心不在“让 AI 自动发帖”，而在把生成、审核、发布拆开，每一步都可观测、可重试、可人工介入。OpenClaw 负责编排，MCP 负责解耦接口，状态层负责兜底。现在它每天帮我生成草稿和元数据，人工确认后发布，整体省了不少重复劳动。全自动不是不能做，但工程上更划算的做法是：让机器做它擅长的，把人留在关键卡点上。
