## 背景：全量加载正在吃掉上下文和判断力

在 OpenClaw 里接入 MCP、插件、自动化脚本后，很容易出现一个尴尬局面：系统提示里塞了几十个工具描述，模型每次都要在大量能力里做选择。结果是上下文变长、响应变慢、工具误判率上升，甚至出现“看到一堆工具但不知道该用哪个”。

Skills 机制要解决的不是“提供更多能力”，而是“在正确的时间只暴露正确的能力”。

## 问题：能力越多，不等于助手越强

全量加载有几个具体代价：

- **Token 成本**：所有 skill 的说明、参数、示例都常驻上下文。
- **决策噪声**：工具太多时，模型容易选错或漏选。
- **权限暴露**：长期持有不必要权限，风险面变大。
- **维护困难**：新增能力会影响全局 prompt，牵一发动全身。

按需加载的核心思路是：先注册轻量索引，命中后再展开完整 skill。

## 做法：一个可落地的 Skill 按需加载流程

### 1. 定义 Skill 包结构

每个 skill 是一个目录，入口是 `SKILL.md`，用 frontmatter 描述触发条件、输入输出和权限。

```yaml
---
name: csv-analyzer
version: 1.0.0
description: 读取、清洗、统计 CSV 文件
when_to_use:
  triggers:
    - 用户提到 CSV/表格/逗号分隔文件
    - 需要对列做批量统计或筛选
  negative_triggers:
    - 数据库查询
    - 图片处理
inputs:
  - file_path
outputs:
  - summary_json
permissions:
  - read:./data
dependencies:
  - pandas>=2.0
---
```

正文写具体操作步骤、可调用的脚本、输出格式。关键点：`description` 和 `when_to_use` 要短，正文可以详细。

### 2. 启动时只建轻量索引

OpenClaw 扫描 skills 目录时，不要把 `SKILL.md` 全文塞进上下文。只提取 `name`、`description`、`when_to_use`、权限摘要，生成一个轻量 registry。

这个 registry 可以放内存，也可以落盘。每次用户请求进来，先查 registry，而不是先加载所有 skill。

### 3. 触发匹配，低分不加载

针对用户输入做检索或规则匹配。比如关键词匹配“CSV”“表格”“逗号分隔”，或者用 embedding 算相似度。设置阈值，低分不加载，但保留 top-k 候选供调试。

命中后，才把对应 `SKILL.md` 的正文追加到当前会话上下文，并临时开放声明的权限。

### 4. 执行后回收权限

skill 跑完后，释放临时权限。不要让某个 skill 的权限在整个会话期间一直挂着，尤其是涉及文件写入、网络请求、命令执行的能力。

### 5. 记录命中日志

记录每次请求的 query、候选 skill、得分、最终加载了什么、是否成功。没有这层日志，后面优化触发条件会很痛苦。

## 踩坑点

- **触发描述写太宽**：比如 `when_to_use: 数据分析` 会导致几乎所有任务都命中，按需变成全量。
- **触发描述写太窄**：用户换一个说法就匹配不到。需要在 triggers 里放常见同义表达，必要时加示例。
- **依赖没声明**：脚本里用了 pandas，但 manifest 没写 `dependencies`，加载后执行失败。加载前最好做一次环境检查。
- **权限边界模糊**：不要只靠 prompt 约束。skill 声明 `read:./data`，但实际脚本去读 `../secrets`，这种情况要在执行层做路径校验。
- **缓存未刷新**：skill 更新后，registry 还是旧版本。给每个 skill 加 version 或 content hash，加载时校验。
- **加载失败难排查**：模型没加载某个 skill，可能是检索没命中，也可能是 prompt 没给够信息。日志里记录候选列表和得分，能省很多时间。

## 可复用建议

1. **一个 skill 只做一件事**。入口描述不超过三句，正文再展开。
2. **入口窄、内容厚**。触发条件精准，加载后才有完整步骤。
3. **设置负向触发**。明确哪些场景不该加载，能减少误触发。
4. **高风险 skill 加显式确认**。涉及写入、删除、外部请求时，加载后先让用户确认。
5. **与 MCP 协同**。如果 skill 依赖某个 MCP server，只暴露需要的工具，不要让整个 server 都进来。
6. **定期回放未命中 case**。把漏触发、误触发的 query 拿出来，持续优化触发描述。

## 总结

OpenClaw Skills 机制的本质不是增加新工具，而是把“能力加载”从静态全量变成动态按需。落地的关键不在 skill 写得有多全，而在触发描述够不够准、权限边界够不够清、日志够不够可观测。先把一个高频 skill 跑通，再看命中率和误触发率，会比一次性设计一套复杂体系更实际。
