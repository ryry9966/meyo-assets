## 背景

用 OpenClaw、Agent 或插件做社区自动发帖，最容易踩的坑不是“能不能发出去”，而是“发出去之后账号还正不正常”。很多实现把节奏控制简单理解成 `sleep(random.uniform(300, 900))`，结果跑几天后帖子开始审核延迟、搜索不可见、互动归零，甚至账号被静默限流。

问题通常不在单次请求，而在行为序列的节奏特征。社区风控不只是看两次发帖间隔，还会看间隔分布、失败重试模式、内容重复度、账号活跃窗口、编辑/删除行为等。单点加随机延迟，解决不了这些特征。

## 问题

典型的“机器人感”来自以下几个工程缺陷：

- 间隔分布太均匀，长期直方图接近均匀分布，人类行为罕见这种模式。
- 所有账号共用一个调度节奏，形成集群特征。
- 内容模板替换几个词就发，文本相似度过高。
- 发布失败后立即重试，连续请求暴露自动化意图。
- 忽略目标社区时区，在低活跃时段高频发帖。
- 只监控“发帖成功率”，忽略影子封禁、限流、验证码等账号健康信号。

## 做法/步骤

我自己在 OpenClaw 里把发帖节奏拆成一个独立调度模块，而不是散落在各个插件里。核心是给每个账号维护一个状态机和下次可发时间，而不是每次发帖前临时 sleep。

### 1. 账号级状态机

每个账号在目标社区有独立状态：

```yaml
account_state:
  id: "acct_01"
  community: "forum_x"
  status: "scheduled" # idle / scheduled / cooldown / blocked
  next_allowed_time: "2025-01-01T10:12:03Z"
  consecutive_failures: 0
  cooldown_until: null
```

状态流转大致是：`idle -> scheduled -> publishing -> idle/cooldown`，连续失败达到阈值进入 `blocked`，需要人工或定时解除。

### 2. 间隔采样用长尾分布

不要用 `random.uniform`。我习惯用 Gamma 分布乘基础间隔，再加一点 jitter：

```python
interval = base_interval * min(3.0, max(0.6, random.gammavariate(shape=2.0, scale=0.3)))
next_allowed_time = now + interval + random.uniform(10, 120)
```

Gamma 分布能产生更多“偏短间隔 + 偶尔长间隔”的模式，更接近人类行为。每个账号使用不同随机种子，基础间隔也可以按账号微调，避免集群步调一致。

### 3. 内容指纹与降频

发帖前对正文计算 SimHash 或简单 MinHash，和目标社区近 7 天已发内容比对。如果相似度过高，就跳过或降低发布优先级，而不是照发。这比替换几个词更有效，因为风控侧也在做文本聚类。

### 4. 失败退避与冷却

发布失败不要原地重试。采用指数退避加抖动：

```text
retry_delay = min(3600, 300 * 2 ** attempt) + random.uniform(0, 60)
```

连续失败 3 次进入冷却，冷却时间按账号历史健康度计算，通常 6 小时起步。冷却期间不再发起任何写操作，包括编辑、删除、回复。

### 5. 观测账号健康，而不是只看 HTTP 200

发布成功返回 200 不代表帖子真的可见。需要记录：

- 发帖后 5 分钟、30 分钟，帖子是否能在未登录状态下搜索到。
- 是否出现验证码、审核延迟显著增加。
- 帖子的自然互动率是否突然下降。
- 账号历史操作是否被拒绝但无明确报错。

一旦检测到“影子封禁”信号，立即暂停该账号，而不是继续按原节奏发。

## 踩坑点

- **只加随机延迟**：间隔直方图太均匀，风控很容易识别。
- **固定模板**：文本向量高度聚集，即使间隔真实也会被内容侧标记。
- **多账号同步节奏**：同时间注册、同时间发帖、同时间休息，集群特征明显。
- **失败后立即重试**：连续失败请求是强暴露信号，比间隔异常更危险。
- **忽略低活跃时段**：目标社区本地时间凌晨三点高频发帖，明显不属于正常用户。
- **只看成功率**：账号可能已经限流，但发布接口仍返回成功。要同时监控可见性。

## 可复用建议

如果要在 OpenClaw 生态里复用，建议把节奏控制做成一个 MCP 或内部服务，所有发帖插件统一调用，不要在各自插件里实现 sleep。对外暴露最小接口：`can_post(account, community) -> bool/next_time`、`record_publish_result(account, result)`、`get_health(account)`。

灰度也很重要。新账号先进入“养号模式”：低频、只发低风险内容、优先保证账号健康指标，连续观察 7 天后再逐步放开频率。同时给每个账号配置独立的随机种子和轻微不同的分布参数，让行为差异化。

最后保留 kill switch。连续异常时，自动熔断比人工发现更快，也更可控。决策日志要记录每次发帖的间隔、内容指纹、失败重试次数和可见性结果，方便事后复盘。

## 总结

社区自动发帖的节奏控制，本质是行为模拟加风险预算管理，而不是延迟技巧。工程上需要把“节奏”从业务逻辑里抽出来，做成可配置、有状态、可观测、可退避的模块。真正有效的不是让机器人“看起来随机”，而是让它长期表现稳定、可解释，并且在账号健康度下降时能自动停下来。
