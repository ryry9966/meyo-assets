“黑鲸出水，DeepSeek下半场开始”这个话题，36kr 把它推到科技圈前排。字面上像一次发布，但更值得拆解的是“下半场”三个字。它意味着大模型竞争的主线正在换轨：训练侧的参数竞赛降温，推理侧的成本、延迟、工具调用与任务成功率，正在成为更硬的门槛。



## 一、黑鲸真正值得看的不是分数，而是成本结构

过去两年，行业判断模型强弱的主要方式是 benchmark 跑分。但分数有两个问题：一是和真实业务脱节，二是容易被针对优化。黑鲸这次被讨论，更多是因为它延续了 DeepSeek 在“能力够用 + 成本够低”路线上的打法。

- 能力锚点：基础模型在数学、代码、长文本上的差距逐渐缩小，单项高分带来的增量收益下降。
- 成本锚点：单位 token 价格和推理延迟，开始决定业务能不能规模化。
- 任务锚点：模型不再只是聊天，而是嵌入 Agent 工作流，完成多步、可验证任务。

举个例子：一个复杂 Agent 任务一次可能跑 20 万 token。如果 API 价格从 2 元/百万 token 降到 0.5 元，单次任务成本从 0.4 元降到 0.1 元。对演示没有差别，对每天百万次调用的产品，就是几十万元级别的月账单差距。

这也是为什么“出水”本身不如“成本曲线”值得关注。

## 二、为什么下半场是“推理经济”，不是参数暴力



推理成本在模型生命周期里会占据越来越高的比例。训练成本是一张门票，推理成本才是每天的房租。

1. **训练是 capex，推理是 opex。**  
   一次训练可能几百万到几千万人民币，但上线后如果每天几亿 token 调用，推理账单几个月就可能追平训练成本。行业里已有云厂商反馈，部分大客户的推理营收增速远高于训练。

2. **Agent 会成倍放大 token 消耗。**  
   一个单轮问答可能 500 token，但一次 Agent 任务可能经历：读取文档、检索、调用 API、自我纠错、再生成。单任务 token 很容易到 10 万以上。成本不降，Agent 产品只能停在限量内测。

3. **延迟与成本不是二选一，而是同一枚硬币。**  
   光便宜不够，用户等不起。工程上常见 PD 分离、连续批处理、投机采样、KV cache 压缩。这些优化做的不是“让模型更聪明”，而是让聪明模型跑得快、跑得省。

冷思考一条：不要只问“这个模型跑分多少”，更要问“同样任务成功率下，每千次任务的总成本是多少”。后者才是产品经理和技术负责人该盯的北极星指标。

## 三、开源不是情怀，是生态飞轮的杠杆

DeepSeek 一直强调开源权重。开源不是“不赚钱”，而是改变议价结构。

- 云厂商不再只卖闭源 API，而是卖推理算力、托管服务、微调工具链。
- 应用开发者可以私有化部署，把模型包进自己的产品里，数据不出域。
- 垂直行业能基于开源权重做领域微调，比如法律、医疗、工业质检。

历史背景可以插一句：Llama 开源让中小厂商第一次拿到可商用的大模型底座，DeepSeek 系列进一步把单位成本压低。结果不是“开源模型取代闭源模型”，而是生态分层更清晰：闭源模型拼天花板能力，开源模型拼工程化和可定制性。

举例：一家做合同审核的 SaaS 公司，调用公共 API 每年可能要花 200 万元；如果换成开源模型做私有化部署，GPU 摊销下来每年 60 万元，还能针对合同条款做 LoRA 微调。省下的钱未必只是成本，而是产品迭代的子弹。

## 四、产品半场的关键：从聊天窗口到 Agent 工作流

很多普通用户对“下半场”无感，因为日常还是对话框。但企业侧已经很明确：模型再好，也不能停在“会聊天”。

- 企业要的是任务完成率，不是回答流畅度。比如“从 PDF 发票中提取金额、税号、开票日期，准确率多少”。
- Agent 的难点在链路稳定性：读文件 → 抽取字段 → 调 API → 校验结果 → 写回数据库。任何一步错了，整条链路返工。
- 评测体系正在变化：静态 benchmark 只适合初筛，真正上线前要看任务成功率、工具调用准确率、端到端耗时、失败恢复率。

举例：一个代码生成产品，不只是看生成的代码能不能跑，还要看在给定单测下通过率、每次生成 token 开销、错误重试次数。这些指标才是用户续费的理由。

换句话说，模型能力强是一回事，把它嵌入到真实业务流程里还能“不翻车”，是另一回事。下半场的产品能力，更多体现在工程链路和数据治理上。

## 五、三条实用建议



1. **把“每任务成本”作为选型第一指标。**  
   先定义你的核心任务，再用自有数据集测延迟、成本、准确率。跑分高但推理贵，适合 demo，不适合上量。可以做一个简单的成本表：每千次任务 = 平均 token × 单价 × 重试系数。

2. **优先做可验证、可回滚的任务。**  
   代码生成、数据抽取、工单分类、报表摘要，这些任务有明确对错。先让模型在中间层输出，人工或规则复核，别一上来就让它直接面对客户做开放式承诺。

3. **对开源模型建立私有化评估基线。**  
   下载权重，准备 10 个真实任务，记录成功与失败模式。每次版本更新时重跑，观察有没有隐性退化。模型升级不等于业务升级，基线测试才是护栏。

大模型下半场不会更热闹，但会更实际。黑鲸出水只是一个信号：水面上的动作越来越小，水面下的工程与商业密度越来越高。
