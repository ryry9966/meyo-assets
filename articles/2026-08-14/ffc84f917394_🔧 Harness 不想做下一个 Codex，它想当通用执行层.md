DeepSeek 最近放出的 Harness，让很多人第一反应是：又一个 Codex？但仔细看它的设计取向，会发现事情没那么简单。它更像在解决一个更基础的问题：模型不再只输出文本，而是如何被安全、可控地接进真实执行环境。这篇文章不吹参数，只聊机制、差异与落地判断。



## 一、先拆词：Harness 不是模型，也不是单纯 CLI

很多人会把 Harness 当成“DeepSeek 版的 Codex CLI”，但它的定位更接近 agent runtime 或执行编排层。

- **模型是大脑，Harness 是神经与手脚**：LLM 本身只会预测 token，它不能自己打开文件、调 API、跑脚本。Harness 负责把模型的“意图”翻译成具体动作，再把动作结果送回模型。
- **它不是垂直工具**：Codex CLI 更偏向“代码仓库里的自动化任务工具”，默认场景是读代码、改代码、跑测试。Harness 则强调通用执行能力，可以接文件系统、浏览器、内部 API、数据库，甚至企业自己的业务工具。
- **技术组成并不神秘**：一个典型的 Harness 会包含主循环（plan-act-observe）、工具注册表、执行沙箱、上下文管理、token/成本控制、日志与审计模块。
- **一个不严谨但直观的类比**：如果模型是“一个很会说话的新同事”，Harness 就是给这位同事配的工位、电脑权限、流程单和监控摄像头。

所以 Harness 的重点不是“能写代码”，而是“能把模型嵌入真实工作流，并且动作可管理”。

## 二、关键机制：为什么“执行”比“生成”难一个量级



生成文本是单次概率采样，执行任务是多轮交互。Harness 要解决的核心问题，全都出在多轮交互里。

**1. 感知-行动循环带来高复杂度**

- agent 每走一步，都要把当前环境状态、工具返回、历史消息塞进上下文。
- 模型输出一个动作，动作改变环境，环境再产生新的观察。
- 这个循环不像聊天那么线性，可能出现分支、重试、回滚，甚至死循环。

**2. 上下文与 token 成本快速膨胀**

- 一次“把上周的 CSV 汇总成周报”任务，可能需要读文件、识别 schema、写脚本、运行、检查输出、修错、再运行。
- 每一步的工具返回都会占上下文，长任务很容易消耗几十万 token。
- 这也是为什么低成本模型在 agent 场景里优势明显：同样预算能跑更多步。

**3. 错误模式比聊天严重得多**

- 幻觉工具名、参数格式错误、误删文件、无限重试、错误覆盖已有数据。
- 聊天里说错一句话最多被纠正，执行环境里一个错误动作可能直接污染生产数据。

**4. 工程上必须做的约束**

- 工具 schema 要严格校验，不能让模型自由发挥参数。
- 设定最大步数、超时、人工确认点。
- 关键动作默认走“只读”，写入、删除、发布必须二次确认。
- 每一步都要留痕，否则出了问题无法复盘。

这些机制，才是 Harness 区别于“把 API 包一层”的关键。

## 三、它和 Codex 的真正差异：应用与底座

如果说 Codex 更像一个“任务型应用”，Harness 则更想成为“应用下面的底座”。

- **Codex 的路径是垂直收敛**：聚焦编码场景，把 repo 理解、代码生成、测试运行做到极致。
- **Harness 的路径是横向开放**：提供通用的工具接入、权限控制、循环控制、审计能力，让开发者自己定义任务边界。
- **类比一下**：Codex 像是 iOS 上一个很好用的效率 App；Harness 更像 SiriKit 或 Shortcuts，给你一套可编程的系统能力。
- **商业逻辑也不同**：垂直工具靠场景体验取胜，底座则靠生态和可嵌入性取胜。底座不一定更好用，但更容易被二次开发。

这解释了标题里那句“不想做下一个 Codex”。不是否定 Codex，而是不想只做一个编码自动化工具。

## 四、生态机会：谁更需要 Harness

短期看，Harness 最可能先在几类场景落地：

- **数据与报表自动化**：把分散的 CSV、Excel、数据库表汇总成结构化报告，动作相对标准，回报容易量化。
- **内部流程编排**：比如“收到邮件 → 提取信息 → 写入 CRM → 返回确认”，这类任务工具边界清晰。
- **本地/私有化部署团队**：DeepSeek 模型可以本地跑，Harness 作为控制面可以接本地模型，数据不出域。
- **不想被单一云绑定的开发者**：如果 Harness 兼容 MCP 或开放工具协议，工具生态可以跨平台复用。

但也要清醒：通用执行层听起来性感，落地时最大的限制往往不是模型能力，而是权限设计、错误恢复和人工兜底。

## 五、落地前 3 条冷思考



别急着把 Harness 接进生产环境，先做这三件事：

1. **从“半自动”开始**  
   先让 agent 只做只读分析，比如读取文件、生成摘要、检查数据质量。写入、删除、发布一律不做。跑通一个月，确认动作可预期，再逐步放开权限。

2. **把审计日志当一等公民**  
   每一步动作、工具参数、模型决策、环境变化都要留痕。没有日志的 agent，等于没有黑匣子的飞机。出问题时，你能回答“它为什么这么做”才是关键。

3. **计算真实成本，而不是只看模型单价**  
   模型单价低不代表任务便宜。一个长任务可能消耗几十万 token，加上重试和错误修复，成本可能翻倍。先估算单任务 token 预算和时延，再决定哪些任务值得自动化。

Harness 的发布，确实把“模型执行层”这个话题往前推了一步。但工具只是工具，真正决定它能不能用好的，还是人对边界的设定、对失败的设计，以及对成本的计算。
