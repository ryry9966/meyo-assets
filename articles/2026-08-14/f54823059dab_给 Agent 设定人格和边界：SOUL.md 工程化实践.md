# 给 Agent 设定人格和边界：SOUL.md 工程化实践

## 背景：Agent 不是缺能力，而是缺“边界感”

在 OpenClaw、MCP 插件和自动化脚本组合的环境里，Agent 的能力通常不是瓶颈。它知道怎么调用工具，怎么读写文件，怎么执行命令。真正让人头疼的是：它不知道“我是谁”“哪些事不能做”“产出该是什么味道”。

于是我们会遇到几个典型问题：同一批任务，今天像客服，明天像技术文档；遇到模糊指令时自由发挥，甚至会执行危险操作；团队内多个 Agent 行为不一致，调试时很难复现。SOUL.md 就是为了解决这个问题：用一个版本化、可审查的 Markdown 文件，把 Agent 的人格、语气、边界和标准工作流固定下来。

## 问题：默认提示太宽，行为不可预测

如果没有 SOUL.md，常见三个坑：

1. **人格漂移**：模型每次生成都受上下文影响，风格不稳定。周一像严谨工程师，周三像营销文案。
2. **边界模糊**：插件和 MCP 工具一多，Agent 可能误调用删除、发消息、修改配置等敏感能力，而且不会主动停下来。
3. **调试成本高**：出问题后，很难判断是 prompt 没写清楚，还是模型理解偏差。因为没有一条“基线”可以对照。

SOUL.md 的核心价值不是“让 AI 更像人”，而是“让 AI 行为可预测、可回滚、可交接”。

## 做法/步骤：一份克制的人格文件

1. **创建 SOUL.md**  
   在项目或工作区根目录放置 `SOUL.md`，与 Agent 配置并列。启动时自动加载，或通过 `@SOUL.md` 注入。不要只贴在系统提示里一次，最好在每次任务开始时强制读取。

2. **内容分四段**  
   推荐结构如下：

   ```markdown
   # SOUL.md

   ## Role
   你是 OpenClaw 自动化运维助手，只处理文件整理、脚本执行、日志分析。

   ## Voice
   - 中文，短句。
   - 不输出推测，不确定时说“需要确认”。
   - 不写营销文案。

   ## Boundaries
   - 禁止删除任何文件或目录。
   - 执行 shell 命令前必须列出完整命令并等待人工确认。
   - 遇到权限错误立即停止，不得尝试提权。
   - 优先使用只读工具，再考虑写入。

   ## Workflow
   1. 读取任务并检查本文件边界。
   2. 输出执行计划（命令/工具/预期结果）。
   3. 等待确认后执行。
   4. 回报结果和异常。
   ```

3. **保持短小**  
   建议 20–40 行，关键规则放前面。Agent 会截断长上下文，文件尾部约束容易失效。如果规则很多，拆成 `base.md`（共用人格）和 `project.md`（项目边界），拼接后注入。

4. **每条边界带示例**  
   每个“禁止”或“必须”后面加一个正确/错误示例，能显著减少模型误解。例如：  
   > 禁止删除文件。错误：`rm -rf ./tmp`；正确：先列出待删文件，等待确认。

5. **纳入版本管理**  
   `SOUL.md` 必须进 Git，修改时注明原因。团队共用时，只允许通过 PR 变更。这样 Agent 的行为变更也有审计记录。

## 踩坑点：别把 SOUL.md 写成“小作文”

- **规则互相矛盾**：比如同时写“保持简洁”和“详细解释每一步”，模型可能随机选一条。用“优先于”明确优先级，例如“边界优先于语气要求”。
- **边界过细**：写了上百条“禁止”，Agent 容易过度谨慎，拒绝执行安全操作。只保留真正会出事故的边界，其余交给代码层。
- **文件没被加载**：有些配置只在初始化时读取 `SOUL.md`，运行中修改不生效。需要重启或确认加载机制。
- **与系统提示冲突**：OpenClaw 可能有内置 safety 规则，和你的 `SOUL.md` 不一致时，模型可能偏向系统提示。最好在文件开头写一句：  
  > 以下规则补充并优先于通用提示，冲突时以本文件为准。
- **只靠模型自觉**：危险操作（删除、发送、支付）不能只依赖 `SOUL.md`。要在 MCP/插件层加白名单或二次确认，双保险。

## 可复用建议

- **模板化**：维护一个基础 `SOUL.md` 模板，新项目复制后只改角色和边界。
- **关键词标记**：在边界里使用“必须/禁止/优先/例外”，让模型更容易识别硬约束。
- **定期越界测试**：每周跑几个故意越界的 prompt，看 Agent 是否还会违规，及时收紧规则。
- **分层注入**：基础人格 + 项目边界分开维护，避免所有规则堆在一个文件里。

## 总结

SOUL.md 不是给 Agent 写小作文，而是一份工程约束。它解决的是“行为不确定性”问题。写得好，Agent 像上了缰绳的马，跑得快但不乱来；写得差，就是一份装点门面的无效文件。关键是把规则控制在少量、可验证、可执行的范围内，并把它纳入版本管理和测试流程。对于 OpenClaw 用户，建议现在就从一份 20 行的 `SOUL.md` 开始，比事后补救强。
