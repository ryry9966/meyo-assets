## 背景

在 OpenClaw 这类 Agent 编排环境里，外部 API 通常通过 MCP、插件或自定义工具接入。天气、搜索、数据库、支付、对象存储这些依赖，日常最容易出现的情况不是“完全不可用”，而是超时、限流、5xx、连接重置、返回结构悄悄变化。

很多 Agent 默认行为是：工具调用失败后，把原始报错丢给模型，模型再尝试换一种方式调用；或者工具内部做无脑重试，最终把上游打挂。真正工程上需要的，不是“永不失败”，而是失败时可控、可恢复、可降级。

## 问题

外部 API 挂掉时，常见问题有四个：

1. **重试风暴**：为了成功一次，短时间内发起大量请求，导致上游雪崩。
2. **非幂等操作重试**：POST/PATCH 被重复执行，产生重复订单、重复消息。
3. **错误信息透传**：把 HTML 错误页、堆栈、半截 JSON 直接塞给模型，污染上下文。
4. **缺少退出机制**：工具一直失败，Agent 一直尝试，单轮消耗大量 token 和时间。

## 做法 / 步骤

### 1. 统一超时与重试策略

每个外部 HTTP 调用必须设置 connect timeout 和 read timeout，不要使用默认的无限等待。重试只针对幂等请求，比如 GET、HEAD；POST/PATCH 默认不重试，除非你有明确幂等键。

重试次数建议 2 到 3 次，采用指数退避加随机抖动，例如 200ms、500ms、1.2s，并尊重 429 返回里的 `Retry-After`。

### 2. 做错误分类，而不是笼统失败

把外部依赖的失败映射成结构化错误：

- `timeout`：可重试
- `5xx`：可重试，但需要熔断
- `429`：限流，按 Retry-After 等待
- `4xx`：不可重试，直接返回友好提示
- `invalid_response`：数据契约问题，不重试

这样模型不需要理解原始网络错误，只要看到 `retryable: true/false` 就能做决策。

### 3. 引入熔断器

连续失败达到阈值后，打开熔断器，短时间内不再打真实请求。比如：连续 5 次失败后熔断 30 秒，之后放行一个探测请求。探测成功则半开转关闭，失败则继续冷却。

熔断器放在 adapter 层，而不是每个 MCP 工具里各自实现一套。OpenClaw 插件里封装一个统一的 `apiCall` 函数就很合适。

### 4. 缓存兜底

对变化不频繁的数据，如汇率、天气、搜索结果、配置，设置短 TTL 缓存。API 失败时返回最后一次成功的数据，并在响应里标记 `cached: true`、`stale: true`。

模型需要明确知道这是过期数据，避免在决策中把它当成实时数据使用。

### 5. 设置降级路径

关键流程要有备选方案或明确的 fail-open/fail-closed 策略。

查询类场景可以 fail-open：主 API 挂了返回默认值或缓存；写操作必须 fail-closed：明确返回失败，不让用户误以为操作成功。

例如支付状态查询不可用时，返回“暂时无法确认支付状态，请稍后重试”，并写日志，而不是伪造一个“成功”。

### 6. 在工具描述里约定错误处理

OpenClaw 工具描述里可以写：

> 如果返回 `retryable: false` 或 `cached: true`，不要重复调用，直接向用户说明当前状态。

这一点很重要。模型并不总能从原始错误中推断出正确行为，结构化错误加清晰描述可以减少很多无效重试。

### 7. 记录可观测性信息

每次外部调用至少记录：API 名称、状态码、耗时、重试次数、是否命中缓存、是否走降级。日志里带上统一的 request id，方便把 Agent 决策和外部依赖失败关联起来。

## 踩坑点

- **对非幂等写操作重试**：重复下单、重复发消息是最常见事故。写操作要么加幂等键，要么明确不自动重试。
- **重试次数过多**：总超时预算超出 Agent 单轮可接受范围，反而比直接失败更糟糕。
- **把原始错误全部丢给模型**：HTML、堆栈、超长响应会挤占上下文，甚至让模型产生错误推断。
- **熔断阈值过于敏感**：网络偶尔抖动就触发熔断，所有流量都走降级。阈值要结合真实流量设置。
- **只熔断不降级**：用户侧依然不可用，熔断只是保护了上游，没有保护用户体验。
- **MCP server 本身崩溃**：Agent 需要能感知工具不可用，而不是一直等待连接或重复调用。

## 可复用建议

1. **把外部依赖封装成 adapter**：统一处理超时、重试、熔断、缓存、日志，不要在 MCP 工具里散落裸 HTTP 请求。
2. **使用结构化错误返回**：`{ ok, data, error_code, cached, retryable, message }` 这种结构对模型友好，也方便上层判断。
3. **明确 fail-open / fail-closed**：查询可降级，写操作必须严格失败。
4. **定义每条依赖的“最大不可用容忍时间”**：超过就告警，而不是等用户来报。
5. **定期演练故障**：手动把某个 API 置为超时或返回 5xx，观察 Agent 是否按预期降级。

## 总结

外部 API 不可用是常态，不是意外。错误恢复的核心不是更多重试，而是分类、熔断、缓存和降级。对 Agent 来说，最好的错误处理是给它有限、清晰、可操作的信息，让它做出保守决策，而不是把一张 HTTP 报错页甩给它。

在 OpenClaw 里落地时，优先把韧性能力做在工具适配层，而不是依赖模型临场发挥。这样才能在真实 API 故障时，既保护上游，也保住用户体验。
