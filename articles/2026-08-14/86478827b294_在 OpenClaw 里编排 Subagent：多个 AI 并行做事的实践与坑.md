# 在 OpenClaw 里编排 Subagent：多个 AI 并行做事的实践与坑

## 背景：单 Agent 串行处理的三个硬伤

在 OpenClaw 里，我们习惯把所有事情交给一个主 Agent：让它读文件、调 MCP、写报告。单 Agent 在处理简单任务时够用，但一旦任务变长、变多，三个问题会很快暴露：

1. **上下文膨胀**：主 Agent 反复读取中间结果，聊天历史越堆越长，tokens 消耗陡增，甚至把关键信息挤出窗口。
2. **速度瓶颈**：串行执行意味着每个步骤都要等上一个步骤完成。批量任务里，大部分时间花在“等”上。
3. **错误连锁**：一个步骤失败，主 Agent 可能带着错误状态继续跑，后续步骤全部跑偏。

典型场景：批量检查 20 个仓库的健康状态、从多个数据源采集信息并汇总、对多个模块做独立的代码审查。这些任务天然可拆分，但用单 Agent 串行做，体验很差。

## 问题：什么时候适合引入 Subagent 并行

不是所有任务都适合并行。判断标准有三个：

- **可拆分**：任务能被切成多个相互独立的子任务，子任务之间不需要实时交换中间结果。
- **结果可汇总**：每个子任务能输出结构化结果，主 Agent 可以按统一格式合并。
- **IO 密集**：子任务大量时间花在等待 MCP 工具返回、文件读取、网络请求上，而不是复杂推理。

如果满足这些条件，用 Subagent 并行编排就能显著提升效率和稳定性。

## 做法：主 Agent 分派，Subagent 独立执行，主 Agent 汇总

以“批量检查 12 个 GitHub 仓库并生成健康报告”为例，在 OpenClaw 中落地 Subagent 编排的步骤如下。

### 1. 定义任务边界与产出物

主 Agent 先列出待处理仓库列表，并为每个仓库生成一个独立任务描述。任务描述只包含：仓库地址、需要检查的维度（最近提交、README 完整性、依赖漏洞）、输出格式要求。不做额外解释，避免信息过载。

### 2. 设计 Subagent 模板

在 OpenClaw 中，Subagent 通常以 Plugin 或 Tool 形式注册。每个 Subagent 的 System Prompt 要固定下来，包含：

- 角色：你是仓库健康检查员，只检查一个仓库。
- 可用工具：GitHub MCP 的只读接口（`get_repo`、`list_commits`、`get_readme`、`list_dependencies`）。
- 输出格式：严格返回 JSON，字段为 `repo`、`last_commit_days`、`has_readme`、`vulnerabilities_count`、`summary`。
- 禁止行为：不得写文件、不得修改仓库、不得调用其他 Subagent。

关键点：**工具权限最小化**。Subagent 只能拿到完成当前子任务必需的只读工具，不给任何写权限或无关工具，避免误操作。

### 3. 主 Agent 并发分派

主 Agent 通过工具调用逐个拉起 Subagent，把任务描述作为参数传入。OpenClaw 中可以通过 `task` 或 `spawn` 类型的工具实现。并发数控制在 3-5 个，避免同时打爆 MCP 服务。

每个 Subagent 执行完返回 JSON。主 Agent 收集所有返回，先做格式校验，再合并成一份总报告。

### 4. 结果收集与容错

主 Agent 为每个 Subagent 设置超时时间（如 120 秒）。超时或返回格式错误的，主 Agent 记一条失败记录，不阻塞其他任务。最终报告里区分“成功”“失败”和“部分成功”。

## 踩坑点：并行不是免费午餐

实际跑下来，有几个坑需要提前规避。

**输出格式漂移**：Subagent 有时不按 JSON schema 返回，比如多包了一层解释文字，或者字段名写错。主 Agent 汇总时解析失败，整个流程卡住。解决办法：在 Subagent prompt 里给一个完整的 JSON 示例，并在主 Agent 汇总前加一步“格式校验”，发现非 JSON 直接丢弃并记录。

**工具权限失控**：如果 Subagent 继承了主 Agent 的全部工具，它可能误调写文件、修改配置甚至发消息。必须显式声明可用工具白名单，禁止继承。

**上下文污染**：Subagent 如果携带主 Agent 的完整聊天历史，会浪费大量 tokens，还可能被无关信息干扰。每个 Subagent 应使用独立上下文，只接收任务描述和必要变量。

**并发限流**：多个 Subagent 同时调用同一个 MCP 服务，很容易触发 rate limit。控制并发数，并加入指数退避重试。OpenClaw 的 MCP 客户端通常支持 retry 配置，提前设好。

**错误隔离不足**：一个 Subagent 失败，如果主 Agent 没有兜底，可能把整个任务带崩。必须设置超时、失败返回结构化错误，主 Agent 降级处理，比如输出“该仓库检查失败，原因：超时”。

## 可复用建议

1. **输出 schema 先行**：在写 Subagent prompt 之前，先定义好 JSON schema。所有 Subagent 共用同一套模板，减少主 Agent 汇总成本。
2. **控制并发数**：从 3 个并发开始，观察 MCP 服务稳定性，再逐步调高。不要一上来就 20 个并发。
3. **给 Subagent 独立工作目录**：如果 Subagent 需要写临时文件，给它独立的 `/tmp/<task_id>/` 目录，避免文件互相覆盖。
4. **记录每次调用日志**：把主 Agent 分派的输入、Subagent 的输出、耗时、错误码写进日志。并行任务出问题时，没有日志几乎无法排障。
5. **先小规模试点**：拿 2-3 个仓库做一次端到端验证，确认输出格式、权限、超时都符合预期，再扩大到全量。

## 总结

Subagent 编排的核心不是“让多个 AI 同时干活”这个动作，而是**边界清晰**：任务边界清晰、工具权限清晰、输出格式清晰、错误处理清晰。OpenClaw 提供了足够的灵活度，但工程化能力要自己补上。

对于 IO 密集、可拆分的批量任务，Subagent 并行能显著降低时间成本和上下文消耗。但如果任务本身高度耦合、需要频繁交换中间推理状态，强行并行只会增加复杂度。先判断再编排，比盲目上并行重要得多。
