最近大模型圈有个讨论很热：如果一家大模型公司不做蒸馏，会付出什么代价？很多人把“蒸馏”简单理解成把大模型压小，省点显存。但在商业世界里，不蒸馏不是“少一个优化选项”，而更像坚持用一整栋楼的承重墙去开一家便利店——结构冗余，房租、电费、维护却一分不少。下面从几个关键成本项拆开看。



## 一、先把概念说清：蒸馏不是“缩水”，而是“学老师”

- 知识蒸馏的经典定义来自 Hinton 团队 2015 年的论文《Distilling the Knowledge in a Neural Network》。它的核心不是简单把参数减半，而是让一个小的“学生模型”去逼近大的“教师模型”的输出分布。
- 教师模型会对每个输入给出软标签（soft label），例如一张猫照片，教师可能输出：猫 85%、狗 10%、狐狸 3%、老虎 2%。学生模型学习这个完整概率分布后，不仅知道“这是猫”，还能学到“猫和狐狸在外观上比猫和老虎更接近”这类类别间相似性。这种信息是硬标签“猫=1，其他=0”给不了的。
- 还有一个关键参数叫温度（temperature），用于软化 softmax 输出，让学生更容易看到教师模型在错误类别上的微弱偏好。
- 剪枝是删参数，量化是降精度，蒸馏则是训练新模型去继承旧模型的知识表示。三者经常组合使用，但蒸馏更接近“能力迁移”。

## 二、最直接代价：推理成本与延迟，把利润吃掉



- 参数规模不是“数字大小”问题。模型越大，每生成一个 token 所需的 FLOPs 越多；同时 KV cache 随上下文长度增长，显存和带宽压力也直线上升。
- 一个直观对比：70B dense 模型和 7B 模型在相同并发、相同上下文条件下，推理吞吐可能差 5～10 倍。即便换成 MoE 架构，总显存占用和通信开销依然很大。
- 换算成商业账：如果一个 7B 模型每百万 token 推理成本是 1 元，70B 模型可能到 8～15 元。API 按 token 收费，毛利会被云资源、GPU 折旧和机房电费迅速吃掉。
- 延迟也是硬约束。代码补全、实时翻译、语音助手等场景通常要求低于 300ms 的首 token 响应。大模型长上下文下容易超过这个阈值；蒸馏后的小模型则更容易满足 SLA。
- 所以不做蒸馏的云端推理，有点像“用卡车送一杯咖啡”：不是不能送，而是每单都在亏。

## 三、端侧与私有化部署：不蒸馏等于放弃一半场景

- 手机、PC、汽车、IoT 设备的可用内存和功耗极其有限。一个 70B 模型即使做了 4bit 量化，也很难塞进手机 NPU 里流畅运行；而蒸馏到 1.5B～3B 再量化，就可以本地跑。
- 隐私和合规是另一个推手。金融、医疗、法务等客户通常不允许原始数据出域。如果不提供可私有化部署的小模型，就等于把这些客户挡在门外。
- 能耗不能忽视。训练阶段虽然集中，但推理是长期累积成本。同一请求，大模型跑一次可能消耗几倍到十几倍电能；蒸馏后单位请求能耗明显下降。
- 举例来说，本地相册搜索、输入法联想、语音唤醒这些高频功能，用户需要的是离线可用、低延迟、不耗流量。云端大模型再强，网络一走、隐私一卡，体验就断档。

## 四、生态与迭代：小模型是开发者和客户的“门票”

- 开源社区对 7B 以下模型更友好。开发者可以在单张消费级显卡上微调、部署、做实验。如果一个公司只提供 70B API，大量个人开发者和中小团队会流向更容易上手的小模型生态。
- 企业客户私有化交付往往要求模型权重，而不是 API 调用。不蒸馏意味着交付物太大、太难维护，商业谈判里会少一张关键牌。
- 迭代速度也是钱。大模型从头训练一遍可能数百万美元、周期数周；蒸馏一个学生模型可能几小时到几天。产品要快速试错、A/B 测试，小模型才是更好的实验载体。
- 历史上有过清晰样本：BERT 时代的 DistilBERT 只保留约 97% 的 GLUE 性能，但体积减少 40%、推理快 60%，迅速成为工业界常用底座。现在的大模型蒸馏，本质是同一逻辑在更大规模上的延续。
- 更现实的是竞争压力：如果对手用蒸馏把成本降 80%，同时保住 90% 的核心能力，你的高价 API 就会失去价格敏感客户。

## 五、不蒸馏也有合理理由：蒸馏不是免费午餐

- 复杂推理、长链条 Agent、大规模代码库理解等任务，能力往往有临界规模。强行蒸馏到很小，可能丢掉关键的长程依赖和规划能力。
- 一些前沿公司必须保留最大能力模型做研究、生成高质量数据、充当教师模型。这类模型不该被蒸馏替代，而是作为能力上限存在。
- 蒸馏本身需要高质量教师、足够数据和严谨评估。如果做得不好，学生模型可能更“自信地犯错”，而且错误更隐蔽，比大模型偶尔犯错更难排查。
- 还有一些替代或补充技术：MoE 稀疏激活、量化、投机解码、KV cache 压缩、prefix caching 等。不蒸馏不等于不优化，只是优化路径偏“大模型侧”。

## 最后：三条冷思考



1. **算总账，而不是只看参数。** 每百万 token 成本、QPS、延迟 SLA 要放在一起看。蒸馏能带来某个数量级的改善，但精度损失必须在业务指标里显式衡量。
2. **分层部署比单一大模型更健康。** 让大模型负责高难任务、数据生产和教师标注，小模型负责高频低难任务；中间用置信度阈值或路由做兜底。不要指望一个模型吃下所有场景。
3. **建立能力回归测试集。** 蒸馏后的小模型常在公开 benchmark 上“看起来不错”，到了垂直场景却容易露馅。建议自动化跑一批真实业务样本，重点观察长尾和边界 case，而不是只看平均分。
