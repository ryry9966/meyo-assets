## 背景

在 OpenClaw 里接 GPT-4o 或同级别云模型做自动化，一开始最省事：所有任务都丢给同一个模型。跑一段时间后会发现问题不在“模型不够强”，而在账单、延迟和不必要的复杂度。很多日志总结、实体抽取、格式转换类任务，并不需要云端大模型，但一旦混在 Agent 流程里，就会拖慢整体响应。

多模型路由不是简单把 GPT 换成本地模型，而是把任务按风险、复杂度和确定性拆开。本文记录我在 OpenClaw 上做路由的实践，重点不是省钱，而是让“该确定的步骤确定下来”。

## 问题

OpenClaw 里的 Agent、MCP 工具调用、插件任务通常不是单一模型调用，而是一条链：理解指令 → 选工具 → 生成参数 → 解析结果 → 下一步判断。不同环节对模型能力要求差别很大。

常见误区有两个：

1. 所有环节都用 GPT，成本高、延迟大，而且简单任务过度生成。
2. 把所有能下沉的任务都交给本地模型，结果 tool call 格式错误、JSON 解析失败、工具选错，自动化链路频繁中断。

所以需要一条明确的路由策略：**什么时候用 GPT，什么时候用本地模型，什么时候连模型都不需要。**

## 做法/步骤

### 1. 先审计任务，不急着换模型

把现有 OpenClaw 任务按这几个维度打分：

- 复杂度：是否需要多步推理、模糊意图理解、长上下文归纳
- 风险：失败后是否会造成外部副作用，例如写文件、发消息、调 API
- 敏感性：数据是否能出本地环境
- 延迟要求：是否需要亚秒级响应
- 输出确定性：是否有固定格式、固定分类、固定模板

我一般把任务分成三类：

| 任务类型 | 推荐模型 | 原因 |
|---|---|---|
| 意图识别、实体抽取、日志摘要、格式转换、简单分类 | 本地模型 | 确定性高、低风险、数据不出本机 |
| 复杂规划、多步 Agent 循环、代码生成、长文档推理 | GPT/云端强模型 | 需要稳定推理和复杂 tool call |
| 固定模板解析、状态判断、简单 if-else | 规则/模板 | 不需要消耗模型 token |

### 2. 给 OpenClaw 配路由策略

OpenClaw 里可以用策略文件或插件级配置做路由。下面是简化的策略示意，不是完整配置：

```yaml
router:
  rules:
    - name: log_summary
      pattern: "task:log_summary"
      model: local:qwen2.5-7b
      temperature: 0.1
    - name: entity_extract
      pattern: "task:entity_extract"
      model: local:qwen2.5-7b
      json_mode: true
    - name: mcp_read_tool
      pattern: "tool:github:read_file"
      model: local:qwen2.5-7b
      allowed_tools: ["read_file", "search_code"]
    - name: agent_planning
      pattern: "task:complex_planning"
      model: openai:gpt-4o-mini
      fallback: openai:gpt-4o
    - name: external_write_action
      pattern: "tool:github:create_pr"
      model: openai:gpt-4o
      require_confirm: true
```

关键不是模型名，而是**按任务和工具分开路由**。MCP 工具尤其要分读写：读操作可以本地模型，写操作默认走 GPT 或人工确认。

### 3. 本地模型调用 MCP 工具时，限制工具集

本地模型在 MCP 工具选择上容易出错。我的做法是：对本地模型只暴露 2–4 个只读工具，并把 JSON schema 写死。这样即使模型输出不够稳定，也不会产生危险副作用。

例如本地模型负责 GitHub 信息提取，只允许 `search_code` 和 `read_file`，不允许 `create_issue`、`create_pr`。工具选择由 GPT 做，本地模型只做参数填充和结果解析。

### 4. 设置 fallback 和观察指标

每个路由规则都要有 fallback。本地模型连续两次 JSON 解析失败，就自动切到 GPT，避免整条自动化链路卡死。

我主要看三个指标：任务成功率、平均响应时间、单任务 token 成本。不要只看本地模型“能用”，要看它在整条链路里是否减少了人工介入。

## 踩坑点

1. **本地模型 tool call 不稳定。** 7B 级模型在复杂工具选择上很容易错。不要让它自己决定调哪个工具，应该由上游显式指定，或者把工具数降到最少。
2. **JSON 输出不总是合法。** 即使开了 json_mode，量化模型偶尔还是会输出额外文本。需要在解析层加正则清理和重试。
3. **上下文窗口容易被撑爆。** 本地模型上下文有限，日志总结或长文档提取时，必须提前截断或分块，否则输出会明显退化。
4. **不要按模型能力“感觉”分。** 有些任务看起来简单，但实际依赖隐式知识。比如判断一条 issue 是否紧急，本地模型可能漏掉语气信息。这类任务应留给 GPT。
5. **量化模型对长 prompt 更敏感。** 同样任务，量化版本可能在短 prompt 下表现正常，prompt 一长就崩。路由时要把 prompt 长度纳入考虑。

## 可复用建议

- 从**只读、无副作用、输出结构化**的任务开始迁移本地模型。
- 把路由规则写成显式配置，不要散落在插件代码里。
- 给高风险写操作统一加人工确认，不管用哪个模型。
- 保留一批真实样本做回归测试，模型或参数调整后先跑一遍。
- 记录每类任务的成本和成功率，按月复盘，而不是一次性切完。
- 本地模型不要做复杂规划。它适合执行明确指令，不适合“你帮我看看这个仓库有什么问题”这类开放任务。

## 总结

OpenClaw 多模型路由的核心不是“哪个模型更强”，而是把任务拆到合适的执行层。GPT 适合规划、工具编排和高风险决策；本地模型适合确定性高、数据敏感或低延迟的执行类任务；规则和模板则能处理大量重复解析。

一条可落地的路径是：审计任务 → 按复杂度和风险分类 → 读写分离 MCP 工具 → 设置 fallback → 用真实样本回归。这样既不会为了省钱把自动化搞崩，也不会让简单任务一直占着云端模型的延迟和成本。
