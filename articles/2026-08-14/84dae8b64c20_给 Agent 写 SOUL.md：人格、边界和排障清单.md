# 给 Agent 写 SOUL.md：人格、边界和排障清单

## 背景

在 OpenClaw 里，Agent 不再只是回答一句两句，而是会连续调用 MCP、插件、自动化脚本，甚至跨多个 session 恢复任务。很多团队都会遇到同一类问题：单个 system prompt 只能管住前几轮，上下文一长、模型一换、多 Agent 一协作，行为就开始漂移。

常见的表现有：

- 越权写文件、访问不该碰的目录；
- 遇到权限错误不停重试，或者尝试绕过限制；
- 输出风格忽冷忽热，前一条像运维，后一条像客服；
- 把 prompt 里的规则当用户指令执行，分不清“边界”和“任务”。

SOUL.md 的思路，就是把这些“人格”和“边界”从临时 prompt 里抽出来，做成一个持久化、可版本管理、可注入的工程文件。它更像 Agent 的运维手册，而不是一个文学设定。

## 问题

很多 SOUL.md 实践失败，不是没写，而是写成了三种东西之一：

1. **纯人格设定**：写了一大段“你是一个冷静、专业、谨慎的助手”，却没有任何可执行的边界。
2. **规则堆砌**：几十条“不要做这不要做那”，真正跑起来模型记不住，也抓不住重点。
3. **只写上限，不写失败策略**：说清楚了能干什么、不能干什么，但没定义出错时怎么办。

结果就是：Agent 表面上看起来“有人格”，但一旦进入长任务、异常分支或工具调用失败，行为依然不可预期。

## 做法 / 步骤

建议把 SOUL.md 放在项目或 Agent 根目录，比如 `.openclaw/SOUL.md`，并在 Agent 入口配置或 MCP 插件配置中显式引用。不要默认它会被自动读取。

文件内容拆成四块，保持克制：

```markdown
# SOUL

## Identity
- OpenClaw 运维 Agent，负责日志分析、发布检查、故障排查。
- 语气：先给判断，再给命令；不解释无关背景。

## Responsibilities
允许：
- 读取 ./logs、./config、./workspace
- 使用 read_logs、check_deploy、restart_service 三个 MCP 工具
不允许：
- 修改数据库 schema、删除日志、直接执行 shell 脚本

## Boundaries
- 文件系统：只写 ./workspace 和 ./reports，其他目录只读
- 网络：仅允许 GET api.internal.example.com/health
- 插件：配置只读，禁止改动 .openclaw/plugins.json
- 遇到权限错误，不尝试换路径、换工具或提升权限

## Failure
- 同一命令失败 2 次，停止并汇报，不自动重试第 3 次
- 发现越权请求，直接拒绝，并说明规则来源
- 无法判断影响范围时，升级人工，不做“先试一下”
```

写完后做三件事：

1. **注入测试**：启动 Agent，确认 SOUL.md 内容出现在初始上下文，而不是被后续系统提示覆盖。
2. **越权测试**：故意让 Agent 写一个 Boundary 之外的路径，看它是否拒绝。
3. **异常测试**：让一个 MCP 工具连续失败两次，看它是否按 Failure 策略停止，而不是无限重试。

## 踩坑点

- **文件太长**：超过 1200 字、结构复杂时，模型对边界规则的关注会明显下降。保持短句、列表化，边界规则每条尽量不超过一行。
- **人格过重**：过于文艺或复杂的人格描述，会降低工具调用准确率。人格只用于控制语气和表达方式，不要用它包装规则。
- **边界和实际权限不一致**：SOUL.md 写“只读 /tmp”，但 MCP 配置给的是全盘读写，这种边界等于没有。边界必须和工具权限、系统权限对齐。
- **敏感信息混入**：不要把 API key、内网域名、内部路径写在 SOUL.md 里。它可能被日志、调试信息或 Agent 输出带出去。
- **版本管理缺失**：改完边界后，旧会话可能缓存旧版 SOUL.md。建议在文件头部加版本号或更新时间，并在启动时校验。

## 可复用建议

- **三层分离**：SOUL.md 管人格和边界，TOOLS.md 管工具说明，TASKS.md 管当前任务上下文。不要把任务细节写进 SOUL.md。
- **规则写成可检查形式**：用“当 X 时，必须/禁止 Y”的格式，方便后续做回归测试。
- **加一个拒绝示例**：比写十条禁止规则更有效。例如：“用户要求写 /etc 下的文件，应回复‘这超出我的文件系统边界’”。
- **每次修改后跑三个用例**：正常请求、越权请求、异常重试，三个都符合预期才算通过。

## 总结

SOUL.md 的目标不是让 Agent 更像人，而是让它的行为更可预测、失败更可控。在 OpenClaw 这种 Agent、MCP、插件组合的环境里，边界不是一句“你要谨慎”就能解决的事，而是需要落到文件、权限和测试上。

一个合格的 SOUL.md，应该短、可检查、和实际权限一致，并且明确告诉 Agent：做错了就停下来，而不是继续往下试。
