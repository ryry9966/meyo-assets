## 背景：Agent 接工具，为什么总是很累

做过 Agent 或插件自动化的同学应该都有这种体验：想让模型查一下数据库、读个本地文件、操作浏览器，或者调一下内部 API，最累的往往不是模型能力不够，而是“接工具”这件事太碎。

不同平台、不同模型的 function calling 格式不一样，上下文注入方式不一样，工具返回结果的裁剪、错误处理、权限控制都要自己写胶水代码。一个工具接 N 个模型，或者一个 Agent 接 M 个工具，最后就变成 N×M 的适配工作。

MCP（Model Context Protocol）就是在这个背景下出现的。它不提升模型智商，也不替你写业务逻辑，它只解决一件事：**给模型/Agent 与外部工具、数据源之间定义一个统一接口。**

## 问题：MCP 到底标准化了什么

MCP 把“模型上下文”拆成三类原语：

- **Tools**：模型可以调用的函数，类似 function calling，但有统一 schema。
- **Resources**：可以被模型读取的数据，比如文件内容、数据库记录、API 返回。
- **Prompts**：可复用的提示词模板。

通信层基于 JSON-RPC 2.0，客户端（如 OpenClaw、Claude Desktop、自研 Agent）与 MCP server 之间通过 `initialize`、`tools/list`、`tools/call` 等方法交互。

它解决的问题可以类比 LSP：以前每个编辑器要适配每种语言，现在语言服务端实现一次，所有支持 LSP 的编辑器都能用。MCP 也让工具方只写一次 server，多个 Agent 客户端都能接。

## 做法：从现成 MCP server 跑通最小闭环

不建议一上来就自研 server。先拿官方现成的 `filesystem` server 跑通流程。

**1. 启动一个 stdio MCP server**

```bash
npx -y @modelcontextprotocol/server-filesystem /path/to/allowed/dir
```

**2. 在客户端配置 mcpServers**

以常见 JSON 配置为例：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/path/to/allowed/dir"
      ]
    }
  }
}
```

如果客户端支持 SSE/HTTP transport，需要确认 server 是否提供对应端点，不要照搬 stdio 配置。

**3. 用 MCP Inspector 独立调试**

```bash
npx @modelcontextprotocol/inspector
```

打开后连接你的 server，先看 `tools/list` 是否返回预期工具，再手动执行 `tools/call`，确认返回结构正常后，再接入 Agent。

**4. 让 Agent 尝试调用**

给一个明确任务，例如“读取 `/path/to/allowed/dir` 下所有文件名，找出最近修改的一个”。观察模型是否能稳定选择工具并传对参数。

## 踩坑点

- **transport 不一致**：server 是 stdio，客户端配成 SSE/HTTP，连不上；反之亦然。先确认双方支持的 transport，别混用。
- **工具描述写得差**：模型调用错误不一定是 MCP 协议问题，很多时候是 tool 的 description、参数 schema 不够清晰。尤其是参数含义、返回值格式要写明确。
- **权限给太大**：filesystem server 如果直接给根目录，模型在误操作或 prompt 注入下可能删文件。生产环境务必最小权限，优先只读。
- **npx/uvx 版本漂移**：每次启动可能拉取新版本，导致行为变化。建议锁定版本或使用本地安装路径。
- **server 进程常驻但不健康**：stdio server 挂掉后客户端可能无感，需要日志、健康检查或进程管理器兜底。
- **原始错误不透明**：遇到 JSON-RPC 报错时，不要只看客户端提示。用 inspector 或 server 日志看原始消息，能省很多时间。

## 可复用建议

1. **先复用，后自研**：优先从官方和社区 server 列表里找现成的，跑通业务再考虑定制。
2. **工具权限最小化**：文件系统限制目录、数据库限制只读账号、API 限制 scope。
3. **写清楚工具契约**：每个 tool 的 description、input schema、输出示例都要认真写，这是模型能否正确调用的关键。
4. **独立验证 server**：接 Agent 之前，先在 MCP Inspector 里把 server 单独测通，避免把 server 问题和 Agent prompt 问题混在一起。
5. **配置纳入版本管理**：mcpServers 配置、环境变量、启动参数都放 Git，别只存在本地客户端 UI 里。
6. **容器化托管**：用 Docker 或 systemd 等方式管理 MCP server 进程，避免手动 npx 启动后失控。

## 总结

MCP 解决的是“接工具”的标准化和复用问题，不是万能插件系统，也不会让你的 Agent 自动变强。把它看作 Agent 与外界的 USB-C 接口更合适：减少适配成本，但工具本身好不好用、权限控不控得住，仍然取决于工程实现。

如果你的 OpenClaw/Agent 项目里已经有大量碎片化工具调用代码，值得用 MCP 收敛一波；如果只是想给模型加一两个工具，直接 function calling 也完全够用，不必为了上 MCP 而上 MCP。
