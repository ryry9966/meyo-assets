## 背景

在 OpenClaw 里跑 Agent、MCP 工具和自动化流程，模型选择会直接影响成本、延迟和稳定性。早期很多人的做法很简单：所有任务都走 GPT 系列。跑通没问题，但很快会遇到三个现实问题：

- 批量任务 token 成本高，日志摘要、实体抽取、格式转换这类简单劳动没必要占用云端额度。
- 实时链路延迟不可控，网络抖动、限流、排队都会拖慢自动化。
- 有些数据不能出内网，比如带手机号、密钥、内部系统日志的文本。

另一个极端是全切本地模型。7B/14B 模型在分类、抽取、脱敏上确实能干活，但一旦涉及多步规划、复杂工具调用或长上下文推理，失败率会明显上升。

所以问题不是“选一个模型”，而是“怎么在模型之间切”。多模型路由不是负载均衡，本质是任务匹配：把合适的任务分给合适的模型，同时保留失败回退路径。

## 问题

OpenClaw 支持配置多个模型 provider，但配置多模型只是第一步。真正容易踩的是这几类：

- 把敏感数据无脑发给 GPT，事后才发现不合规。
- 把需要严格 JSON 输出的任务交给本地小模型，结果解析频繁失败。
- 让模型自己决定“该用哪个模型”，路由行为不稳定，排障很痛苦。
- 本地模型超时或幻觉工具名后，整个 Agent 会话直接挂掉，没有回退。

## 做法/步骤

### 1. 先给任务分层

不建议一开始就做很细的路由表。先按两类分：

**A 类：值得走 GPT/云端模型**
- 多步规划、复杂工具编排
- 长上下文理解与跨文档推理
- 代码生成、代码审查
- 需要强指令遵循的高风险操作
- 用户直接可见的关键回复

**B 类：优先本地模型**
- 意图分类、情绪判断
- 实体抽取、结构化信息提取
- 敏感信息识别与脱敏
- 日志摘要、批量打标
- 格式转换、草稿生成
- 离线或弱网环境下的预处理

这个分类可以再扩，但一开始先跑通两类即可。

### 2. 部署一个稳定的本地模型

本地模型建议用 Ollama 或 vLLM 起服务。模型规模选 7B-14B，量化 Q4_K_M 或 Q5_K_M 通常够用。不要一上来就上 30B+，部署和推理延迟会抵消收益。

如果要做工具调用，优先选官方标注支持 function calling 的模型，但不要默认它一定稳定。实际工程里，7B 级别模型在 1-3 个简单工具、参数不超过两层的场景下可用性最好。

### 3. 在 OpenClaw 里配置多 provider

给不同模型起明确标签，例如：

- `gpt-4o-mini`：应付 A 类任务
- `local-qwen2.5-14b`：本地 B 类任务

OpenClaw 的路由可以放在工具定义或 Agent 执行前的一层轻量规则里。建议不要把这些标签散落在各个插件里，集中放在一个模型注册表配置中，方便统一修改。

### 4. 用规则路由，不要用模型自选

路由决策不要交给模型自己。模型自选路由不稳定，出错时很难定位。

更务实的做法是两条路选一：

- **前置分类器**：用户输入先过本地小模型，输出 `task_type`、`sensitivity`、`complexity`，OpenClaw 根据结果选择模型。
- **工具指定**：在 MCP 工具或插件定义中声明 `preferred_model`，比如“日志脱敏工具固定走本地模型”，“代码生成工具固定走 GPT”。

规则路由的好处是可预测、可回滚、可观测。

### 5. 设计回退路径

本地模型常见失败有：JSON 解析失败、工具调用参数错误、上下文超长、超时。回退策略建议“单步重试，不迁移整个会话”：

- 本地模型失败后，把**当前这一步**交给 GPT 重新执行。
- 不要直接把整个会话上下文切到 GPT，容易造成上下文错位和重复副作用。
- 如果本地模型已经执行了有副作用的操作，比如写库、发送消息，回退时要做幂等判断，避免重复执行。

### 6. 监控与记录

至少记录这些字段：模型名、任务类型、耗时、token 消耗、是否回退、失败原因。路由策略上线后，前两周的日志比任何经验都重要。

## 踩坑点

- **本地模型 JSON 不稳定**：不要只靠 prompt 说“输出 JSON”。用 JSON schema 约束采样或加一层解析重试。如果还是不行，就让本地模型输出简单键值对，上层再做格式化。
- **工具调用幻觉**：7B 模型会生成不存在的工具名或错误参数。控制工具数量，尽量一次只暴露 1-3 个工具。
- **上下文窗口小**：输入太长会直接截断或崩溃。先做截断、摘要或只送必要字段。
- **敏感数据边界**：先本地脱敏再送 GPT，不要反过来。本地模型也要跑在权限隔离环境里。
- **路由表别太细**：超过 5 类规则后维护成本会超过收益。先粗分，再按真实失败率调整。
- **不要用弱模型做关键决策**：涉及权限判断、资金操作、删除动作，不要省这点成本。

## 可复用建议

1. **复杂度/敏感度矩阵**：横轴复杂度，纵轴敏感度。复杂且敏感的任务可以本地预处理后人工确认，不要硬路由。
2. **影子模式对比**：新路由规则上线前，让 GPT 和本地模型同时跑一周，对比结果再切流量。
3. **统一输出格式**：无论哪个模型，都要求返回统一 JSON，上层解析不用感知模型差异。
4. **集中模型注册表**：记录每个模型的能力标签、上下文限制、成本、是否支持工具调用。
5. **批量/离线优先本地，实时关键链路优先 GPT**。
6. **路由函数保持小而清晰**，OpenClaw 是编排层，不要把路由逻辑复杂化。

## 总结

OpenClaw 多模型路由的合理目标不是“全自动”，而是“90% 简单任务本地消化，10% 高难度与高风险任务走 GPT，且失败可回退”。关键工程点只有四个：任务分层、规则路由、单步回退、认真记录日志。先跑通两类任务，再根据真实数据调整策略，比一开始就设计复杂路由更可靠。
