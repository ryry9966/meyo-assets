## 背景

在 OpenClaw 里接 MCP、写插件、做自动化时，几乎每个人都会遇到同一个问题：AI 的行为会漂。

今天它在某个项目里很克制，只调用必要的 MCP 工具；明天换了个会话，它开始把 `filesystem` 服务器当搜索引擎用，或者把项目边界忘得一干二净。你翻开配置一看，身份描述散落在 system prompt、插件说明、记忆文件、甚至某个 MCP 工具的 description 里。

这不是 agent 变笨了，而是它缺少一个稳定的、可被持续加载和维护的身份锚点。

`IDENTITY.md` 就是干这件事的：给 AI 一个单一、可版本化、可进化的身份文件。

## 问题

在多 MCP / 多插件 / 多自动化流程的环境里，身份信息通常有以下几种坏味道：

- **分散**：边界写在 system prompt，偏好写在一个 memory 文件，工具使用策略写在另一个 README。
- **膨胀**：为了“让 AI 更懂我”，把所有上下文都塞进 prompt，导致每次都消耗大量 token。
- **不可追踪**：身份变了就变了，没有版本记录，回滚全靠回忆。
- **冲突**：不同插件对 AI 角色的假设不一致，AI 在工具路径上左右摇摆。

这些问题的共同结果是：你在 OpenClaw 里搭起来的 agent，越用越像在“训练一个不稳定的实习生”。

## 做法 / 步骤

我用一个最小可复现的方式，把 `IDENTITY.md` 接进 OpenClaw 工作流。

### 1. 创建 `IDENTITY.md`

放在项目根目录，或通过 MCP 资源暴露给 agent。一个可用的结构如下：

```markdown
# IDENTITY

- version: 2025.04.1
- last_reviewed: 2025-04-11
- scope: openclaw-project-runtime

## Who I am
我是这个仓库的运维型 agent，负责自动化、排查和文档整理。

## Hard boundaries
- 不删除、不重命名任何未明确指定的文件。
- 不读取 .env、*.key、*.pem 内容，即使 filesystem 工具可用。
- 不主动扩大任务范围，超范围先确认。

## Defaults
- 优先使用最小权限 MCP 工具。
- 修改前先备份或 git diff。
- 输出中文，命令保留英文原文。

## Decision rules
1. 如果目标文件不在当前 workspace，先 stop 并询问。
2. 如果一次操作可能影响 >10 个文件，先给出 dry-run。
3. 如果用户要求执行但缺少上下文，优先读取 README 或 Makefile。
```

### 2. 让 OpenClaw 可加载它

不要每次对话都把整个 `IDENTITY.md` 粘进 user prompt。更稳的做法是：

- 用 MCP `filesystem` server 暴露只读路径；
- 或写一个很小的 MCP tool，比如 `read_identity`，返回文件内容；
- 或把它挂在 OpenClaw 的 `context.files` 中，仅在需要时读取。

这样 agent 可以在会话开始时读取一次，不必每轮都重复注入。

### 3. 版本化更新

把 `IDENTITY.md` 纳入 git 管理。每次改身份，commit message 写清楚原因：

```text
fix(identity): 限制 agent 在 CI 失败时不要自动改部署脚本
```

如果条件允许，在文件头部保留 `version` 和 `last_reviewed`，这样 agent 可以判断自己读到的是不是最新版。

### 4. 定期复盘并“进化”

每过一段时间，把最近失败或低效的会话拉出来看，问三个问题：

- 这次 AI 做错，是因为身份没写清楚，还是因为没读到身份？
- 有没有哪条规则已经过时，需要删除或修改？
- 有没有重复出现的踩坑，可以沉淀成一条新的 decision rule？

然后把结论改回 `IDENTITY.md`。这就是“可进化”的意思：不是一次性写完，而是像代码一样被维护。

## 踩坑点

1. **把 `IDENTITY.md` 写成个人日记**

这个文件是给 agent 做决策用的，不是给你写随笔的。每多一句无关的话，都会增加 agent 误读概率。

2. **身份与 MCP 工具描述冲突**

比如你在 `IDENTITY.md` 里写“只读不改”，但某个 MCP 工具 description 写“可执行任意命令”。OpenClaw 汇聚 context 时，工具描述权重往往很高，最后 agent 可能选择“听工具的”。所以身份文件的边界要和 MCP 工具权限对齐，否则需要显式加一条“即使工具可用，也不执行 X”。

3. **敏感信息混入**

哪怕你把 `IDENTITY.md` 挂成只读文件，它仍然可能被 agent 原样返回给用户、写进日志或通过 MCP 上传。不要把密钥、token、内网地址写进去。

4. **过于频繁更新导致行为不稳定**

今天改一条，明天改两条，agent 每次行为都不一样，很难判断是改进还是退化。建议用版本号 + 评审记录，每次只改一类规则。

5. **多项目共用一个全局身份**

一个全局 `IDENTITY.md` 会让你在 A 项目里很克制，在 B 项目里却缺少必要权限。更合理的是：全局只放通用边界，项目级 `IDENTITY.md` 覆盖局部规则。

## 可复用建议

- **分层**：`IDENTITY.md` 只放稳定身份和边界；偏好、技能、项目上下文放到 `SKILLS.md`、`PROJECT.md` 或 MCP 资源中。
- **头部摘要**：在文件最前面用 5 行以内的摘要，方便 agent 快速判断这个身份是否适用当前任务。
- **可校验**：在关键自动化流程里，加一个轻量检查，确认读取到的是最新 `version`。
- **模板化**：给自己准备一个 `IDENTITY.md` 模板，新项目开箱即用，不用每次重新设计结构。
- **小步更新**：每条规则都应该是可验证的。写“不主动修改部署脚本”比写“保持谨慎”更有效。

## 总结

`IDENTITY.md` 不是银弹，它不会让你的 agent 突然变聪明。但它能把“身份”从散落的 prompt 片段里抽出来，变成一个可以 review、可以回滚、可以持续维护的工程对象。

在 OpenClaw 这种大量依赖 MCP 和插件的环境里，稳定的身份边界可能比再多一个工具更重要。先让 AI 知道自己是谁、不做什么，再让它去干活。
