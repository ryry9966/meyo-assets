# Prompt 工程实战：Cron 任务应该怎么写 instruction

在 OpenClaw 这类 agent 自动化里，Cron 任务看似简单：定时触发一条 instruction，让模型去做事。但真正跑起来，常见结果是“第一次正常，第二次开始重复处理”“模型自由发挥，调了不该调的工具”“输出一堆自然语言，日志没法看”。这些问题通常不是模型能力不够，而是 instruction 写成了聊天请求，而不是作业手册。

## 背景：Cron 任务和聊天式指令不是一回事

Cron 任务有三个特点：无上下文、无人实时纠错、可重复触发。聊天式 instruction 依赖模型临场判断，一旦某个条件没写清，模型就会“合理脑补”。比如“每天早上整理未读邮件”，模型可能不知道什么是“已处理”，也不知道失败时要不要重试，更不知道输出到哪里。

所以，Cron 任务的 instruction 必须写成可执行的运行手册，而不是一句开放式的聊天命令。

## 问题：为什么 Cron 指令容易翻车

- **没有上下文**：模型不记得上次执行了什么，容易重复处理。
- **没有实时反馈**：人不在旁边纠正，错误会被自动放大。
- **自由度过高**：模型可能选择错误工具、错误时间范围，甚至产生副作用。
- **输出不统一**：自然语言输出很难进日志、报警或被后续任务消费。

## 做法：把 instruction 写成运行手册

### 1. 明确任务边界与完成判据

不要只写“整理邮件”，要写清来源、时间范围、去重标准、输出位置、怎样算完成。

示例：

> 从 Gmail 工具读取 24 小时内未回复的邮件；每封生成一段 80 字以内的中文摘要；写入 Obsidian 的 `inbox/邮件摘要.md`；如果文件已存在则追加，不覆盖。

### 2. 先检查再执行，设计幂等条件

Cron 会重复触发，instruction 必须让 agent 先判断“是否已经做过”。

示例：

> 开始前检查目标文件是否已有今日日期标题；若有，直接返回 `SKIPPED`，不要再次生成。

### 3. 锁定工具和权限

如果不限制，agent 可能为了完成任务调用意料之外的插件或 MCP。写清楚：

> 本次任务只允许使用 `gmail_read`、`obsidian_write`；禁止发送邮件、禁止删除邮件、禁止调用其他工具。

### 4. 要求结构化输出

Cron 任务需要被日志、报警、后续任务消费。自然语言输出很难解析。指定输出格式：

> 完成后只输出一行 JSON：`{"status":"OK","processed":3,"skipped":1,"file":"inbox/邮件摘要.md"}`；失败输出 `{"status":"ERROR","error":"..."}`。

### 5. 提供失败行为，而不是让模型自己决定

很多 Cron 任务在失败时被模型“重试到成功”，可能造成副作用。明确失败策略：

> 如果读取邮件失败，不要重试；直接输出 `ERROR` 并保留原始错误信息。

### 6. 给少量示例和反例

对容易歧义的步骤，给 1-2 个例子。例如“简短摘要”给出正例和反例：

> 正例：客户询问发票开具时间，需今天回复。  
> 反例：这是一封关于发票的邮件，客户想了解发票开具的时间，需要及时回复。

## 踩坑点

- **时间窗口不明确**：写“最近”会导致每次执行定义不同。写成“UTC+8 的过去 24 小时”或“自上次成功时间以来”。
- **上下文依赖过强**：Cron 触发时可能没有前一次对话记录。不要写“按上次讨论的方式”，要把关键参数写进 instruction。
- **指令太长，关键约束被淹没**：模型容易忽略中后段的条件。把硬约束放在开头或结尾，并加“必须”“禁止”等标记；如果指令太长，拆成多个任务或写进外部配置。
- **输出格式没有强制**：模型可能返回 markdown、解释文字或多余内容。要求“只输出一行 JSON，不要解释，不要代码块”。
- **工具权限过宽**：尤其在可以写文件、发消息、操作数据库的场景，要最小化权限。
- **时区问题**：Cron 表达式时间与 agent 工具返回时间不一致，导致漏数据或重复。统一指定时区，如“所有时间均为 Asia/Shanghai”。

## 可复用建议

可以维护一个 Cron instruction 模板：

```
[任务目标]
一句话描述。

[前置检查]
执行前必须检查的状态；满足什么条件直接 SKIP。

[执行步骤]
1. 使用工具X读取...
2. 按规则Y处理...
3. 写入...

[成功判据]
完成输出 OK，格式...

[失败处理]
失败时输出 ERROR，不重试/重试一次；保留错误信息。

[禁止事项]
禁止...
```

每次新任务从模板开始，避免漏掉关键块。写完先在 dry-run 或手动触发一次，看返回值、日志和副作用，再正式上定时。定期检查任务，如果某个任务频繁 SKIP 或 ERROR，说明 instruction 的判据或外部状态需要调整。

## 总结

Cron 任务不是“定时聊天”，而是一个没有人在场的自动化作业。把 instruction 写成运行手册：明确边界、幂等、结构化输出、失败策略，能显著减少返工和事故。对 OpenClaw 这类 agent 自动化来说，稳定的 Cron 不靠更聪明的模型，而靠更精确的约束。
