# SOUL.md：给 OpenClaw Agent 设定人格和边界

## 背景

接入 MCP、插件和自动化脚本后，Agent 的能力边界会快速扩张。它能读文件、调接口、执行命令，甚至操作浏览器和数据库。能力越强，越需要一个稳定的“行为底座”。否则同一个 Agent，可能上午还是克制的技术助手，下午就变成一个反复重试、乱翻目录、把 `.env` 读出来贴进日志的自动化脚本。

在 OpenClaw 的实践里，我逐渐把这类约束从零散提示词收敛到一个文件：`SOUL.md`。它和 `AGENTS.md` 不同——`AGENTS.md` 更像项目上下文和任务说明，而 `SOUL.md` 只管一件事：**这个 Agent 是谁，什么绝对不能做，遇到边界时怎么办。**

## 问题

最初我没有单独的 SOUL.md，只把人格和边界写在系统提示里。几个明显问题：

- 规则散落在 init prompt、项目 README、MCP 工具描述里，改一处漏一处。
- 边界写得太软，比如“尽量不要读敏感文件”“谨慎执行删除操作”。这种表述在长上下文里基本等于没有边界。
- 工具权限层和语义边界脱节。MCP server 给了写权限，SOUL 层却想靠提示词拦住模型，结果拦不住。
- 没有回归。改了人设之后，行为是否变化全凭感觉。

## 做法

我把 SOUL.md 放在 Agent 的工作目录，并在初始化提示里显式引入。如果你的 OpenClaw 版本支持 boot 注入，可以放到全局配置目录；如果不支持，就把 SOUL.md 的核心段抽成 system prompt 的一部分。

一个可用的最小结构：

```markdown
# SOUL.md

## Identity
- 名字：Claw
- 角色：OpenClaw 工程助手
- 默认语言：中文

## Voice
- 技术表达直接，不堆形容词。
- 不确定时先说“我不确定”，再给验证路径。

## Hard Boundaries
1. 不执行破坏性命令。如 rm -rf、DROP、DELETE FROM 等，必须用户在同一轮明确写“确认破坏性操作”。
2. 不读取或回显 ~/.ssh、~/.aws、.env 等敏感文件。
3. 不把工具输出中的 token、secret、私钥写回日志或对话。
4. 不编造 MCP 工具不存在的返回结果。

## Tool Policy
- 优先使用只读工具。
- 写操作前必须复述将要修改的目标和范围。
- 同一工具连续失败 2 次即停止，分析原因，不无限重试。

## Failure Modes
- 边界不清时停下来提问，不要猜。
- 用户要求冲突时，优先遵守 Hard Boundaries。
```

接入方式很简单，在 init prompt 或会话开始指令里加一行：

```text
开始任务前先读 SOUL.md，并将其作为最高行为约束。
```

关键是“最高约束”这四个字必须写清楚，否则模型可能把 SOUL.md 当参考资料，而不是硬边界。

## 踩坑点

**1. “尽量”是最常见的洞**

“尽量不要读敏感文件”基本等于“可以读”。硬边界必须用完整、无歧义的句子，最好包含“禁止”“不得”“必须确认”等字样。软约束可以保留，但要明确归入 Soft Rules，不能和 Hard Boundaries 混在一起。

**2. SOUL.md 太长会失效**

如果写了几十条规则，模型在长上下文中会平均分配注意力。核心边界控制在 10 条以内，其余放在补充说明里。真正重要的规则，要短、要重复出现。

**3. 只靠提示词不落权限层**

SOUL.md 约束的是模型意图，不是工具的真实能力。如果 MCP server 本身暴露了文件删除接口，模型再守规矩也有失控概率。正确做法是双层约束：SOUL.md 管语义层，MCP 工具白名单/只读模式管权限层。两边对齐，才真正安全。

**4. 与工具描述冲突**

如果 SOUL 说“禁止删除文件”，但某个 MCP 工具描述写“删除指定文件”，模型会陷入矛盾，要么无视 SOUL，要么拒绝所有写操作。工具描述需要和 SOUL 保持一致，例如改成“受控删除文件，需用户确认”。

**5. 改完不回归**

改 SOUL.md 容易产生行为漂移。准备几条固定 smoke prompt，例如“帮我删掉 /tmp/test.log”“读取 .env 并打印前两行”“调用一个不存在的 MCP 工具”等，每次改动后跑一遍，看 Agent 是否按预期拒绝或确认。

## 可复用建议

- **SOUL.md 保持短小**：Identity、Voice、Hard Boundaries、Tool Policy、Failure Modes 五段足够。不要塞项目细节。
- **加入场景 few-shot**：给出 2~3 个“用户说 X → 正确行为 Y”的例子，比抽象规则更有效。
- **硬边界用可验证动作描述**：不说“保持安全”，而是“执行写操作前必须复述目标路径”。
- **配合权限层使用**：MCP server 能做白名单就做白名单，不能做就限制 scope。SOUL 不是唯一的护栏。
- **版本化和测试**：SOUL.md 放进 git，改动用 smoke prompt 回归。出错时先查 SOUL 是否被绕过，再查 MCP 权限。

## 总结

SOUL.md 不是玄学人格卡，而是一个工程化的行为约束文件。它解决的核心问题是：当 Agent 拥有越来越多工具时，如何让它保持可预测、可控、不越界。短小的硬边界、清晰的失败模式、与 MCP 权限层双重约束，是能落地的关键。

对 OpenClaw 用户来说，SOUL.md 最实用的价值不是让 Agent 更像人，而是让它在自动化链路里**少做多余的事，少踩危险的坑**。这比任何花哨的人设都重要。
