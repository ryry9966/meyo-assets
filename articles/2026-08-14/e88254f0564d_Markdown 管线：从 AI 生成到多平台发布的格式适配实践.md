## 背景

在 OpenClaw / Agent 工作流里，AI 生成 Markdown 已经是默认输出。但同一份 Markdown 推到 GitHub、公众号、知乎、Notion、飞书，经常出现表格错位、代码块丢失高亮、公式不渲染、外链图片 403、frontmatter 被当正文等问题。原因只有一个：各平台实现的不是同一套 Markdown，而是多种方言。

如果不做格式适配，AI 产出越丰富（表格、代码、公式、任务列表），发布后走样越严重。比如公众号会把 Markdown 当纯文本展示；知乎吞掉 task list；Notion 把 YAML frontmatter 塞进正文开头；代码块语言标注在一些平台完全失效。

## 做法：中间格式 + 适配器

我的管线分三层：源 Markdown、规则处理、平台 adapter。

**1. 定义稳定的中间格式**

源 Markdown 只保留 CommonMark 安全子集，并做明确约束：

- frontmatter：只写 title、description、tags、date，不写嵌套对象
- fenced code block：必须带语言标识，不允许空语言
- 表格：不超过 4 列，避免移动端溢出
- 图片：统一使用绝对 URL，避免相对路径
- 数学公式：统一用 `$...$` 和 `$$...$$` 包裹，不使用平台特定语法

**2. 用 AST 处理，不要用正则硬匹配**

使用 unified/remark（或 Python 的 markdown-it-py）解析成 AST 再处理。我写了几个小插件：

- strip-frontmatter：剥离 YAML frontmatter 并转成平台元数据
- normalize-code-lang：把 `bash`、`shell`、`sh` 归一成各平台支持的别名
- task-list-to-ul：把 `- [ ]` 转成普通列表，适配不支持任务列表的平台
- table-guard：超过 4 列的表格标记为“需要转图片”，交给图片处理模块

这里强调一下：正则替换在代码块和嵌套结构中很容易误伤，AST 遍历才可控。

**3. 按平台写 adapter**

- **GitHub**：几乎直出，只处理相对路径图片和 frontmatter 里的自定义字段。
- **公众号**：代码块转成带行号的高亮 HTML；表格转图片或降级为列表；公式用 KaTeX 渲染成 SVG，再内联为 `<img>`。
- **知乎**：把外链图片上传到知乎图床并替换 URL；去除不支持的 HTML 标签；公式优先保留文本，复杂公式转图片。
- **Notion**：通过 HTML 导入，注意表格空行和分隔符；frontmatter 转成页面属性。
- **飞书**：统一把 task list 转成普通列表，代码块保留语言标注，公式转文本或图片。

**4. 封装成 MCP 工具或 CLI**

在 OpenClaw 里，我把整个管线注册成一个 MCP 工具：

```
md-pipeline build --target wechat --input post.md --output dist/
```

AI 生成 Markdown 后自动调用，产出 `post.wechat.html`、`post.zhihu.md`、`post.notion.html` 等目标文件。这样做的好处是：AI 只负责内容，不负责平台格式。

## 踩坑点

- **图片外链失效**：AI 返回的临时 URL 经常很快失效。必须统一转存到自己的对象存储或图床，再替换链接。图片处理要独立成模块：下载、压缩、上传、替换 URL 一条链，失败时回退原链接并输出告警。
- **代码块语言别名**：AI 可能输出 `bash`，但有的平台只认 `shell` 或 `sh`。需要做别名映射，并且不要随意去改语言名，否则高亮会错乱。
- **表格列数过多**：移动端阅读器不友好。建议在 pipeline 中设置阈值，超过 4 列自动转图片或列表，而不是硬塞。
- **数学公式**：公众号、飞书等不支持 LaTeX 渲染，裸发就是灾难。必须转换或降级为文本描述，不能假设平台支持。
- **换行符**：有些平台会折叠单个换行。需要把单换行替换为 `<br>` 或两个空格，但不要全局替换，否则代码块内部会被破坏。
- **frontmatter 泄漏**：很多平台不认识 YAML frontmatter，会直接显示在正文开头。适配层必须剥离并转成平台元数据。

## 可复用建议

- 转换规则配置化，不要写死在代码里。比如用一个 YAML 定义每个平台的行为：是否支持表格、是否支持公式、代码块如何处理。
- 保留原始 Markdown，所有转换产物放在 `dist/` 目录，源文件永不覆盖。这样换平台重新适配时不需要重新生成内容。
- 写一组最小测试用例覆盖各平台常见场景：标题层级、代码块、表格、任务列表、公式、图片、脚注。每次改 adapter 跑一遍，避免回归。
- 在 CI 中自动运行管线，例如 push 到仓库后自动生成多平台版本并归档。不要依赖手工操作，否则很快会忘记转换。

## 总结

Markdown 管线本质上是一个“中间格式 + 适配器”架构。不要让 AI 直接面向平台输出，而是让 AI 输出稳定的中间格式，由管线负责方言转换。这样既保持源内容一致，又避免为了某个平台去不断 hack 提示词。工程化的收益是：你只维护一套转换逻辑，而不是在每个平台后台上反复调格式。
