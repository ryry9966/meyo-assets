## 背景

团队里跑着不少 OpenClaw 自动化任务：定时抓取、数据清洗、Agent 调用、插件执行等。每天产生的原始日志分散在文件、数据库、消息队列和云日志服务里，格式也不统一。人工汇总日报非常耗时，而且容易漏掉关键异常。

我们后来把日报生成做成了一条流水线，核心思路不是“把日志丢给模型写总结”，而是先做确定性清洗和聚合，再让 LLM 只负责最终表达。这条流水线已经稳定跑了一段时间，下面把做法、踩坑点和可复用建议整理出来。

## 问题

直接生成日报会遇到几个典型问题：

- 日志源多、格式杂，Agent 很难直接理解。
- 原始日志噪音大，直接把一天日志塞给 LLM，上下文容易爆，且数值容易出错。
- 日报需要稳定结构：任务状态、耗时、错误、资源消耗、异常风险。
- 日报本身也是自动化任务，失败时需要可感知、可重试。

## 做法与步骤

### 1. 采集层：通过 MCP 封装日志读取

不要给 Agent 直接开放文件系统或数据库权限。我们用 MCP server 暴露只读日志查询工具，例如：

- `list_sources`：列出可用日志源。
- `query_logs(time_range, filters)`：按时间范围和过滤条件拉取原始日志。

OpenClaw 任务通过 MCP 工具访问日志，权限边界更清晰，也方便后续替换上游日志源。

### 2. 清洗与归一化：用确定性脚本，不用纯 prompt

在 Agent 节点里用 Python 脚本或 OpenClaw 插件做清洗。定义统一事件结构：

```json
{
  "timestamp": "2025-01-15T09:12:33+08:00",
  "source": "crawler-prod",
  "task_id": "task_20250115_0910",
  "event_type": "task_failed",
  "level": "error",
  "message": "short truncated message",
  "duration_ms": 12034,
  "tokens": 0,
  "extra": {}
}
```

原始 `message` 截断到 500 字符，避免噪声污染后续聚合。解析规则做成配置，不写死在插件里，上游日志格式变化时只改配置。

### 3. 聚合统计：输出中间 JSON，不让 LLM 算数

按 `task_id` 和 `source` 聚合，统计：

- 成功 / 失败 / 超时数量。
- P95 耗时。
- 总 token 消耗。
- 重试次数。
- 失败任务最近 3–5 条关联日志。

产出当天的 `daily_summary.json`。这个 JSON 是后续生成日报的输入，也是长期资产。

### 4. 生成日报：LLM 只做表达

将 `daily_summary.json`、固定模板和规则一起交给 LLM，生成 Markdown 日报。Prompt 里明确：

- 只基于给定 JSON 描述事实，不得编造数值。
- 只列出失败、超时、耗时异常的 Top 5。
- 禁止写“预计明日完成”等推测性内容。
- 输出固定结构：概览、任务明细、异常与风险、资源消耗、明日关注。

之后做一次结构校验，不符合格式就重试一次。

### 5. 发布与回溯

通过插件或 webhook 将日报发送到群聊或文档。日报底部附上原始数据链接、生成时间、流水线版本，方便溯源。

## 踩坑点

- **直接塞原始日志**：上下文容易超长，LLM 会把时间戳、级别等细节“脑补”错。必须先确定性聚合。
- **时区混乱**：日志可能 UTC 或本地时间，跨天任务容易重复或漏计。采集层统一转换到固定时区，日报标题注明时间范围。
- **解析规则脆弱**：上游一改日志格式，写死的正则就会崩。保留解析失败的原始前 N 行并标记 `unknown`，不要整条丢弃。
- **失败任务缺上下文**：只写 “Task X failed” 不够，需要按 `task_id` 提取最后几条日志或堆栈摘要。
- **日报本身失败无感知**：定时任务挂了没人知道。加一个 pipeline heartbeat，失败告警走独立通道。
- **模型输出漂移**：偶尔会加戏，写“建议明天上线”。Prompt 里禁止预测，输出后做 schema 校验，不符合就重试。

## 可复用建议

- **保留中间 JSON**：日报只是视图。每天积累的结构化数据后续可以做周报、趋势分析、异常率统计。
- **MCP 封装读取**：用工具边界控制 Agent 权限，避免误操作日志源。
- **模板和 Prompt 版本化**：和代码一起管理，方便回溯为什么某天格式变了。
- **先跑影子模式**：和人工日报对比一周，确认统计口径一致再切换正式。
- **输出保留 trace 链接**：日报里带上原始日志或 trace id，读者可以深入排查。

## 总结

自动化日报的稳定落地，关键不在于让模型“写得漂亮”，而在于把原始日志先变成可信、可验证的结构化数据。确定性管道负责清洗和聚合，LLM 只做最后表达。这样日报可追溯、可维护，也能作为后续数据分析的基础。
