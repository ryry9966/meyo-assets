人类有个经典现象叫 tip-of-the-tongue（舌尖现象），心理学上简称 TOT：明明知道那个词，却临时提取失败。现在这顶帽子也可以戴到大模型头上。谷歌最近用一组大规模 key-value 检索测试，把 GPT-5 等模型考到“钥匙丢了”——上下文里已经告诉它 key，它却拿不出对应 value。据报道，这项测试累计执行 450 万次查询，结果揭示了一个反直觉事实：长上下文不等于长记忆。



## 1. 实验怎么把 GPT-5 考到“丢钥匙”


- 测试设计像一个加强版“找钥匙”游戏：研究者向模型上下文塞入海量键值对，key 可以是一串 UUID/编号，value 是对应短文本或数字。
- 询问方式很直接：“请给出 key_7f3a 对应的 value”，模型必须从上下文里精确检索。
- 测试变量包括上下文长度、key 出现位置、信息密度，总计 450 万次查询。
- 结果显示：短上下文时准确率接近满分；当上下文拉长，尤其 key 位于中段时，准确率大幅下滑，部分场景接近随机水平。
- GPT-5 和主流模型都出现了同样的“U 型曲线”：开头和结尾记得牢，中间丢得厉害。这不是某个模型翻车，而是当前 Transformer 架构的共性问题。

## 2. “看过”为什么不能保证“记住”


- 大模型的“看”不是存储地址，而是一连串注意力权重。每预测一个 token，它都会对前文所有 token 计算相关性。上下文越长，注意力总量被越摊越薄。
- Softmax 归一化让 token 之间互相竞争分数：中间 token 没有位置优势，容易被前后的高频信息抢走注意力。
- KV cache 只是缓存历史计算结果，不是数据库索引。它不会按“key”建立哈希映射，因此无法像程序那样 O(1) 精确取回。
- 位置编码在长上下文下也会出现区分度下降，尤其是旋转位置编码在极端长度时，相对位置信号可能变弱。
- 训练数据中以短程依赖为主，长程精确检索样本不足。模型学到了“根据语境猜”，但没有学到“从长序列里稳定调取单一事实”。
- 人类 TOT 的机制也类似：不是记忆消失，而是提取线索不够强。大模型不是把 key 删掉，而是预测时没有走到那条路径。

## 3. 丢失的钥匙会砸中哪些真实任务


- 法律/合同审阅：关键责任条款夹在文档中部，模型可能漏掉，生成过于乐观的结论。
- 代码库问答：main 函数在文件末尾、核心定义在中部，模型可能只抓住开头 import，给出错误调用方式。
- 多轮对话：用户在几十轮之前设定的约束、角色或偏好，会被后续内容淹没，模型开始“选择性失忆”。
- RAG 检索增强：即使检索系统找回了正确文档，只要文档很长，模型也可能忽略文档中部的证据句。
- 长文档摘要：模型容易给开头和结尾更高权重，中间的重要转折或限定条件被抹平，摘要失真。

## 4. 三条建议：把钥匙挂回模型脖子上


1. 别把 token 窗口当可靠记忆。窗口大小只是“能塞进去多少”，不是“能稳定调取多少”。评估长上下文任务时，要专门测中段检索准确率。
2. 关键信息放在开头或结尾，必要时在结尾重述约束。比如让模型先读问题再读材料，或者把结论、用户要求放在最后再强调一遍。
3. 长文档先分块、再检索、最后局部精读。用 chunk + embedding/索引把长上下文拆成多个小上下文，让模型在高密度局部窗口内作答，而不是一次性吞下几百万 token。

当我们嘲笑大模型也会“话到嘴边想不起来”时，更值得警惕的是把长上下文宣传当作记忆能力。钥匙没有消失，只是注意力不够亮。未来模型需要的不只是更长的窗口，而是更可靠的索引、召回和复核机制。
