最近开源模型圈又被 GLM-5.3 刷了一波屏。官方给出的信息是，它在多个开源榜单里拿下 SOTA，代码、数学、指令跟随等方向都有明显抬升。但工程师看模型发布，向来不太容易被一个“榜一”说服——更容易被一句“能不能复现”说服。于是我把 GLM-5.3 接到 DeepSeek Harness 上跑了一轮，并做了一些必要的魔改。下面聊的不是这个模型有多强，而是开源评测里的门道、适配细节，以及分数之外更值得关注的东西。



## 一、GLM-5.3 的开源 SOTA，应该拆开看



先说一个基本判断：开源模型的 SOTA 是“配置依赖”的结果，不是一块固定招牌。同一个模型，换掉 prompt、few-shot 数量、采样参数或评分逻辑，分数可能上下浮动 3~5 个点，有时甚至更多。

- 官方所说的多个开源 SOTA，主要集中在几类任务：
  1. 知识推理：MMLU-Pro、GPQA 等变体；
  2. 代码能力：LiveCodeBench、SWE-bench 风格任务；
  3. 数学推理：AIME、MATH-500 等评测；
  4. 指令跟随：IFEval 或工具调用类评测。
- 但这类榜单只能说明“在特定测试条件下表现很好”，不能直接等价于“在所有真实场景中更可用”。
- 更值得看的是分数结构。例如：
  - 代码任务与数学任务同时在线，说明模型不只在语言表达上占优；
  - 长上下文中分数衰减曲线更平缓，说明模型不是只靠短窗口刷分；
  - 指令跟随与工具调用的稳定性，往往比绝对分更能预测实际体验。

举一个例子：同样在 MMLU 上，5-shot 与 0-shot 的差异可能超过 4 分；而如果把答案格式从“直接输出选项”改成“输出选项并解释理由”，分数又可能被打乱。因此看到 SOTA，先别急着换模型，先看清楚它背后的评测协议。

## 二、DeepSeek Harness 是什么，为什么要魔改



DeepSeek Harness 并不是什么神秘官方套件，它更接近一套针对 DeepSeek 系模型优化过的 lm-evaluation-harness 配置与适配层。它的作用是把模型加载、prompt 构造、采样、答案解析、指标计算串成一条可复现流水线。

典型流程大致是：

`model_class -> tokenizer -> chat_template -> build_prompt -> generate -> parse_answer -> metric`

这条链路里，DeepSeek Harness 对 DeepSeek-V3/R1 等模型做了不少“默认假设”：

- tokenizer 层面：使用 DeepSeek 特有的 BOS/EOS 标记；
- 对话模板层面：对 system prompt、assistant 和 user 角色标记做了固定处理；
- 生成参数层面：默认的 temperature、top_p、repetition_penalty 更适合 DeepSeek 系模型；
- 任务适配层面：部分任务的 few-shot 格式和截断逻辑写死在配置里。

如果直接把 GLM-5.3 塞进去，最容易出现三类问题：

1. tokenizer 不一致：prompt 被切错，尤其影响数学符号和代码 token；
2. chat template 错位：GLM 的角色标记与 DeepSeek 不同，导致 system instruction 失效；
3. 生成参数不匹配：默认参数可能让 GLM-5.3 生成过长、过短，或影响 logprob 任务。

所谓魔改，不是把 harness 推倒重写，而是在不改动评测数据的前提下，把模型后端、prompt 契约和指标层改成适配目标模型。这既是复现 SOTA 的前提，也是防止“假高分”或“假低分”的关键。

## 三、魔改实操：三个关键点



这一轮适配，我主要改了三个地方。对准备自己动手的读者，可以直接参考。

1. 模型加载层：替换后端，并固定显存/上下文配置
   - 如果只是快速验证，可以用 transformers 加载，但大批量评测建议上 vLLM；
   - 使用 vLLM 时，优先配置 `max_model_len` 为模型的真实上下文长度，避免长任务被截断；
   - 对 `trust_remote_code` 保持谨慎，先阅读远程代码再开启；
   - 固定 `tensor_parallel_size` 和 `gpu_memory_utilization`，避免评测过程中出现隐性 OOM 或 batch 不一致。

2. Chat template 与 tokenizer 层：不要复用 DeepSeek 模板
   - 使用 GLM-5.3 官方提供的 chat template，而不是直接继承 DeepSeek 的角色标记；
   - 明确 system prompt 的位置。不同模型对 system 支持的实现差异较大，放错位置可能导致指令跟随分数明显偏低；
   - 显式设置 EOS token。多个生成任务里，EOS 如果被当成普通 token 纳入 logprob 计算，会让多项选择类成绩出现系统性偏差；
   - 对代码和数学任务，检查是否需要关闭 `add_bos`。这个细节容易被忽略，但会影响首 token 概率。

3. 指标与答案解析层：把通用正则替换成任务感知评分
   - 代码任务不要只盯 pass@1，结合 pass@10 和真实可执行率看，更能反映工程价值；
   - 数学任务解析 `\boxed{}` 时不要写死单一样式，最好同时支持分数、小数和 LaTeX 多答案；
   - 指令跟随、工具调用类任务，建议采用固定版本 LLM-as-judge，并把 judge 的 prompt 与温度写进配置文件；
   - 遇到分数异常，先检查答案解析，再检查生成参数，最后再怀疑模型能力。

一个实际翻车案例：第一次跑 GPQA 时，GLM-5.3 的分数比官方低 8 个点。排查后发现，DeepSeek Harness 默认在答案末尾追加了 EOS token，而 GLM-5.3 在多选题里把这个 EOS 纳入概率计算，导致干扰。修正 EOS 处理逻辑后，分数回到正常区间。这也说明，很多所谓“模型不行”，其实是适配层不行。

## 四、冷思考：SOTA 分数不等于“能用”



模型发布时，榜单是最容易被传播的数字。但工程选型时，SOTA 只应该是一个初筛信号，不能当作最终决策依据。

开源模型评测至少有四个常见偏差：

1. 数据污染：训练语料可能见过公开评测集，高分不一定代表泛化能力；
2. 评测集过拟合：某些模型会针对高频 benchmark 优化采样策略或 prompt 风格；
3. 配置不可比：不同团队用的 prompt、few-shot、温度和截断方式不同，A 的 80 分可能与 B 的 75 分没有本质差异；
4. 指标噪声：多项选择的选项顺序、答案格式和解析逻辑都会影响最终数字。

更务实的做法是：把官方 SOTA 当成筛选入口，然后用三类私有数据做复测——业务真实问答、代码仓库级任务、带约束条件的文档处理。只有这些场景稳定，才值得进入下一步接入。

最后，三条实用建议：

1. 不要直接拿官方榜单分数做选型。先构造 20~50 条与业务最接近的私有评测集，用统一的 harness 跑通，再对比分数；
2. 魔改评测框架时，把 chat template、EOS token、上下文长度、采样参数写进 config，保证可复现。否则复盘时很容易“跑不出上次的分数”；
3. 把分数和成本放在一张表里看。一个 SOTA 模型如果推理慢 3 倍、显存占用高 40%，在真实服务里可能并不划算。分数之外，延迟、吞吐和稳定性才是上线后每天要面对的东西。

分数可以帮你筛掉明显不合格的模型，但选对模型，最终还是靠场景里的细节。
