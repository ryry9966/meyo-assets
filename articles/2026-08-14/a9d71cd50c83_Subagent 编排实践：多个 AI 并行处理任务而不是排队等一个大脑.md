## 背景

在 agent 自动化里，单 agent 处理复杂任务容易遇到三个问题：上下文窗口膨胀、任务串行等待、多步骤间信息污染。比如让一个 agent 同时扫描五个代码仓库并生成报告，它可能读到第三个仓库时已经忘记第一个仓库的关键细节。subagent 编排是一种工程化拆解手段：主 agent 只做调度与汇总，多个子 agent 并行执行独立子任务。

在 OpenClaw 的实践里，这不是“多开几个对话窗口”那么简单，需要处理任务拆分、上下文隔离、并发控制、失败重试和结果校验，否则并行带来的问题比串行还多。

## 问题

不是所有任务都适合并行。需要判断子任务之间是否低耦合、数据是否隔离、结果是否可合并。否则并行反而引入合并成本。另一个典型问题是上下文隔离不彻底，子任务之间通过共享 workspace 或 MCP 工具互相干扰。例如两个 subagent 同时写同一个文件，最后内容互相覆盖，主 agent 还浑然不知。

## 做法/步骤

1. **定义主 orchestrator 的职责**：拆任务、下发、收集、校验、汇总。主 agent 不应直接做具体执行，否则又退化成单 agent。
2. **按无依赖边界拆任务**。例如“分析 A 服务日志”“分析 B 服务日志”“扫描前端依赖漏洞”可以并行；“改数据库 schema 并迁移数据”和“基于新 schema 写接口”有依赖，不适合并行。
3. **为每个 subagent 创建独立 workspace 或 session**。在 OpenClaw 中，我会为每个 subagent 单独开一个 session，只挂载该子任务需要的目录或 MCP 工具。例如只读访问日志目录，或只允许访问特定数据库。
4. **下发任务时提供明确输入、输出格式和边界**。给每个 subagent 一个 JSON 任务描述，包含 task_id、输入路径、允许的工具、期望输出 schema、超时时间。
5. **控制并发**。即使工具支持并发，API 限流和本地资源也可能成为瓶颈。一般从 2-3 个并发开始，观察限流和任务成功率，再逐步增加。
6. **主 agent 汇总时做校验**。不是简单拼接结果，而是检查每个任务是否成功、输出是否符合 schema、是否有冲突。例如两个 subagent 同时修改同一份配置，主 agent 需要发现并处理冲突。

## 踩坑点

- **上下文给太少**：subagent 为了搞清背景反复调用工具，反而更慢更贵。给必要上下文，但不要给全量。
- **MCP 工具并发写冲突**：多个 subagent 同时写同一个文件或 SQLite 数据库，会出现锁或覆盖。解决：每个 subagent 写独立文件，汇总阶段再合并；数据库操作使用事务或串行化。
- **没有幂等设计**：失败重试导致重复数据。例如日志分析任务因超时重试，结果数据被插入两次。解决：用 task_id 做唯一键，支持覆盖或跳过已成功任务。
- **主 agent 直接拼接输出**：没有检查格式和内容，导致最终报告质量不稳定。解决：固定输出 schema，主 agent 做 schema 校验，必要时让子 agent 修正。
- **并发过高触发限流**：OpenClaw 或模型 API 可能有并发限制，一旦 429 会拖垮整个编排。解决：实现退避重试，并限制最大并发。
- **subagent 越权操作**：MCP 工具权限过宽，一个子任务可能误操作其他数据。解决：最小权限原则，给每个 subagent 单独配置允许的工具和路径。

## 可复用建议

- **先串行跑通，再并行化**。串行能验证任务描述是否清晰、输出是否可用，并行只是加速。
- **使用任务清单/manifest 管理 subagent 状态**：pending、running、success、failed。主 agent 根据清单做调度和恢复。
- **要求所有 subagent 输出 JSON**，而不是自然语言，便于汇总和校验。
- **保留每个 subagent 的完整 transcript 和日志**，出错时能快速定位是任务描述问题还是工具问题。
- **对可重试任务实现幂等**，对不可重试任务设置短超时和明确失败信号。
- **小规模起步**：2-3 个并发，任务数量控制在 5 个以内，观察稳定后再扩展。

## 总结

subagent 编排适合低耦合、可独立执行、结果可合并的任务，比如多数据源采集、多模块代码扫描、多文件批量重构。它不是银弹，依赖任务拆分的质量和工程化配套。上下文隔离、并发控制、幂等与可观测性，比“让多个 AI 同时跑”本身更重要。先跑通一个稳定的串行流程，再考虑并行，是避免翻车的务实路径。
