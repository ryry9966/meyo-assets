# AI Agent 的错误恢复：当外部 API 挂了的工程化解法

## 背景：只要依赖外部，就一定会有失败

在基于 OpenClaw 搭建 Agent 或自动化流程时，我们几乎绕不开对第三方 API 的调用：查天气、发消息、访问数据库、调用 LLM、触发 webhook……每个外部依赖都是一个潜在的故障点。一次网络抖动、上下游服务限流、API 密钥过期，甚至对方机房断电，都足以让精心设计的 Agent 链路直接断裂。

更麻烦的是，**Agent 通常比普通 Web 服务的调用链更长**。一个任务往往需要连续调用多个外部接口，并基于前一环节的返回值做决策。如果中间某一步突然抛出 HTTP 500，没有兜底逻辑，整个会话就会得到一句冰冷的“抱歉，我无法完成这个操作”，然后陷入沉默——这是工程上不可接受的。

## 问题拆解：API 挂掉的几种典型形态

实践中，“挂了”并不只有“服务不可达”这一种情况，至少要区分三类场景：

1. **瞬时故障**：超时、连接重置、偶发的 502/503，通常重试几次就能恢复。
2. **持续不可用**：API 密钥被禁用、对方服务彻底宕机，持续几分钟到几小时。
3. **逻辑异常但协议层正常**：返回 HTTP 200，但 body 里的数据格式变了，或者业务状态码提示配额耗尽、权限不足。

Agent 的错误恢复方案，需要同时覆盖这三层，否则就会有明显的盲区。

## 做法与步骤：构建一条韧性调用链

下面给出一个可以直接用在 OpenClaw 插件或 MCP 工具里的分层恢复方案。整体思路是：**重试 → 熔断 → 降级 → 兜底**，并在每一层做足可见性。

### 1. 为每次调用加上可控的重试机制

最简单的起步是用指数退避重试，但要严格控制边界。建议只对 `5xx`、`429`（限流）和网络超时类错误重试，对 `4xx` 客户端错误直接失败，避免无意义重试造成写操作重复。

以 Python 为例，在自定义工具函数上可以用一个简单的装饰器（非框架专属，所有 OpenClaw 插件风格通用）：

```python
import time
import random
import functools

def retry_on_transient(max_retries=3, base_delay=1.0):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(max_retries + 1):
                try:
                    return func(*args, **kwargs)
                except TransientAPIError as e:
                    last_exc = e
                    if attempt == max_retries:
                        raise
                    delay = base_delay * (2 ** attempt) + random.uniform(0, 0.5)
                    time.sleep(delay)
            raise last_exc
        return wrapper
    return decorator
```

这里的关键是让工具在抛出异常时区分 `TransientAPIError` 和不可恢复的 `FatalAPIError`。即使底层 SDK 不支持，也要在封装层把 4xx 和 5xx 拆开。

### 2. 构建简单的熔断器，避免重试风暴

如果 API 已经确认连续失败，继续重试只会浪费时间并增加对方负载。可以加一个内存级熔断器：最近 N 次调用中失败率超过阈值，直接短路一段时间。用文件或 Redis 存储熔断状态的版本也可以扩展到多进程 Agent。

实现上只要记录「连续失败次数」和「半开状态时间」即可。在 OpenClaw 插件中，你可以把熔断状态挂在工具级缓存或全局字典里，通过 key 区分不同 API 端点。

### 3. 降级与兜底：让 Agent 体面地失败

光重试和熔断只解决了“不要更糟”，真正影响体验的是「降级输出」。常见的降级策略包括：

- **返回缓存结果**：对时效性要求不高的查询（如汇率、天气概述），只要有过一次成功响应，就存入 TTL 缓存。API 失败时直接返回过期数据并注明时间。
- **功能裁剪**：比如翻译 API 挂了，Agent 可以直接返回原文，并说明“翻译服务暂时不可用，已返回源文本”。
- **使用本地能力替代**：当依赖的远程大模型 API 限流时，可自动 fallback 到本地运行的小模型（如 Ollama），哪怕是降低回答质量，也好过完全中断。

为方便 Agent 做后续决策，降级时应该在返回结构中附带一个 `degraded: true` 字段。这样上层 Planner 就能识别出当前信息质量下降，避免把模糊数据当作事实继续推理。

### 4. 把“失败”变成可观测事件

无论你做了多少防护，最终还是会有彻底失败的时刻。这时需要有清晰的日志和通知。建议在异常处理的最终层，将完整的请求上下文、错误信息、重试次数、熔断状态等打包成结构化日志，并可以通过 webhook 或消息推送通知开发者。

在 OpenClaw 的 MCP 工具中，可以利用 `server.sendLoggingMessage()` 将错误信息异步推送到客户端，方便调试。

## 踩坑点

- **无脑重试导致幂等性问题**：调用支付、创建订单这类非幂等 API 时，重试必须依赖幂等键，否则可能会重复创建资源。在封装层要显式区分读写。
- **缓存雪崩与脏读**：大面积 API 故障时，如果所有请求同时回退到缓存，可能导致本地负载飙升。可以引入随机化过期时间（TTL + jitter）。
- **降级数据的可信度未标明**：Agent 经常会把降级返回的过期数据当成可靠信息，进而产生错误结论。务必在提示词或响应中注明数据来源和更新时间。
- **熔断后恢复太慢**：一些实现使用很长的半开等待时间，导致短暂故障后服务长期不可用。建议半开探测间隔设置在 10~30 秒，并允许一次成功就关闭熔断。

## 可复用建议

在 OpenClaw 的生态里，你可以将这些模式沉淀为可复用的 **MCP 工具包装器**。例如，创建一个 `resilient_api_call` 函数，接收 endpoint、payload 和 fallback 回调，内部完成重试、熔断、缓存与降级，对外只暴露统一的返回格式。多个插件只要声明自己依赖的 API 特点（是否幂等、是否可缓存、可接受的最大数据延迟），就能直接复用同一套韧性逻辑。

如果使用 OpenClaw 的任务引擎，还可以把「降级动作」建模为工作流分支：当一个 API 节点失败时，自动走 fallback 子图，而不是把异常抛给用户。

## 总结

构建可靠的 AI Agent 不仅仅是设计正常路径，更是设计所有可能的异常路径。对外部 API 的失败处理，核心在于 **分层防御 + 显式降级 + 可观测**。当你把重试、熔断、缓存和兜底串联起来，就能让 Agent 在面对不可控的外部世界时，依然保持可用的姿态，而不是脆弱地崩溃。越早把这层韧性纳入工具和插件的标准封装，后续的业务逻辑就越少被突发中断拖垮。
