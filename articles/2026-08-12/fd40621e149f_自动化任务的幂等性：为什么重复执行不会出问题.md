## 背景：你的自动化脚本在“被重复”时有多脆弱？

在 OpenClaw 生态里，我们习惯用 MCP 工具、自定义插件或者 Agent 工作流去编排自动化任务——定时拉数据、事件触发通知、批量调用 API、自动写库。这些任务从设计上看是一条“单线”，但在真实环境里，同一段逻辑被执行多次的概率远比想象中高：

- 调度器因为时钟漂移、任务积压，把同一个窗口触发了两次；
- MCP 客户端因网络超时发起重试，实际上上一次调用已经在服务端执行成功；
- Agent 思考循环里，同一个工具被反复调用，因为上游没有严格去重；
- Kafka / MQ 消费端 rebalance 导致消息被重复投递。

如果你没有刻意做过幂等性设计，这些重复执行往往会产出重复数据、重复通知、重复扣款，甚至因为状态冲突把业务流程卡死。但反过来，一个真正工程化的自动化任务，应该在“被重复”时毫无波澜，要么安全跳过，要么重复执行但结果一致。

这篇文章不谈大词，只聚焦：在 OpenClaw/Agent/MCP/插件 的实际项目里，怎么落地“重复执行不会出问题”的幂等设计。

## 问题拆解：重复执行在哪些环节作恶

把自动化任务抽象成一个操作序列，常见有三种副作用：

1. **写安全：重复创建资源**  
   比如每收到一个 Webhook 就调用 API 创建工单，重复执行会产生多条相同工单。
2. **状态安全：重复推进状态机**  
   一个订单已支付，重复执行“支付确认”可能导致状态再次变化，发出两次发货指令。
3. **外部效应：重复通知/扣款**  
   发邮件、发钉钉消息、调支付接口，这些外部调用代价高且难以回滚。

这三类问题的解法都指向同一个原则：**为操作赋予业务唯一标识，并在执行前后进行防重判断**。

## 做法：搭建一个轻量级的“幂等防火墙”

下面是一个可以直接套用到 OpenClaw 插件、MCP 工具或普通 Python 任务里的设计路线。

### 1. 设计幂等键（Idempotency Key）

让每次任务执行都带上一个唯一标识。这个标识需要满足：相同业务含义的请求生成相同键，不同请求生成不同键。

实用方案：

```
idem_key = f"task:{task_name}:{business_id}:{event_id_or_timestamp}"
```

- `task_name`：任务逻辑名称，如 `create_order`、`send_notification`；
- `business_id`：业务主体 ID，比如订单号、用户 ID；
- `event_id_or_timestamp`：若上游能提供确定性的事件 ID（如 Kafka offset + partition），直接用；否则用精度合适的业务时间窗口（精确到分钟甚至秒），但需评估风险。

**很重要的一点**：不要在键里包含随机数，否则每次生成都不一样，防重直接失效。

### 2. 防重检查与记录——用数据库唯一约束兜底

流程是：收到任务 → 算出幂等键 → 检查该键是否已存在记录 → 若存在且状态为成功/处理中，则直接返回；否则执行，并在执行前立刻插入一条 `processing` 状态的记录。

在数据库层面的操作：

```sql
INSERT INTO idempotency_records (key, status, created_at)
VALUES ('task:send_notification:order_12345:20250401_1420', 'processing', NOW())
ON CONFLICT (key) DO NOTHING;
```

然后检查受影响行数：如果是 0，说明已存在记录，需要进一步读取状态决定是跳过还是等待（避免“处理中”的并发冲突）。若插入成功，开始执行业务逻辑。

**为什么不用 Redis 而用数据库？**  
Redis 灵活，但会面临持久化、过期清理后旧请求再打穿的风险。关系型数据库的唯一索引天然提供强一致的防重屏障，且能和业务数据放在同一个事务里（如果任务本身需要写库）。大多数自动化任务 QPS 不高，DB 完全撑得住。

### 3. 状态更新——保证可重试

任务执行完成后，更新记录状态：

```sql
UPDATE idempotency_records
SET status = 'success', result = '...'
WHERE key = '...' AND status = 'processing';
```

如果任务失败，可以更新为 `failed` 并记录错误信息，让后续调用方根据业务决定是否重试（比如用新的幂等键发起重试，或者人工介入）。

这样就形成了一条完整的“检查-插入-执行-终态更新”链路，即使在并发场景下，唯一索引也能保证只有一个线程真正执行任务。

## 实际踩坑：这些细节会让幂等名存实亡

### 1. 并发竞争时“检查-插入”不是原子的

不加锁的 `select + insert` 会在高并发下产生多个线程同时查出“不存在”，然后都去执行业务逻辑。正确的做法是用数据库的 `INSERT ... ON CONFLICT DO NOTHING` 或 Redis 的 `SETNX`，让“判断并占位”一步完成。如果插入返回冲突，去查询现有状态决定行为。

### 2. 幂等键的粒度过粗或过细

- 过粗：`task:send_notification:order_12345`（不含时间或事件维度），导致 order 的一生中只能发一次通知，显然不合理。
- 过细：加入了毫秒级随机串，每次都不一样，防重完全瓦解。

生产环境往往会为“一次性任务”加一个业务有效期窗口，如当天同类型任务只执行一次：`task:send_daily_report:user_{id}:2025-04-01`。

### 3. 分布式锁失效后的重复执行

很多同学喜欢用 Redis 分布式锁来防重，但锁过期是个大坑。如果任务执行时间超过锁 TTL，锁自动释放，其他实例会再次获得锁并执行，此时防重能力丢失。所以锁只能作为并发控制的辅助，最终的幂等还得靠状态记录和数据库唯一约束。

### 4. 记录清理带来的二次冲击

幂等记录表如果按时间定期清理，清理后旧键可能再次被“成功插入”，导致重复执行。清理策略必须和幂等键的语义匹配：如果一个键对应的业务操作窗口已完全关闭，那它就可以安全删除。或者干脆不删除，按分区归档。

### 5. MCP 工具或插件内部重试的隐藏执行

如果你的 MCP 工具函数内部有自己的重试逻辑（比如 HTTP 请求超时重试），要确保外层幂等键能穿透进去，或者工具本身对下游实现幂等调用。否则会出现：外层只记录了一次执行，但内层实际调了两次下游接口。

## 可复用建议：把幂等变成默认习惯

在 OpenClaw 项目里，我会把幂等逻辑封装成一个可复用的组件，尽可能让使用者零心智负担。

**Python 装饰器方案（伪代码）**：
```python
def idempotent(func):
    @wraps(func)
    def wrapper(*args, idem_key=None, **kwargs):
        key = idem_key or build_key(func.__name__, *args, **kwargs)
        record = db.insert_if_not_exists(key, status='processing')
        if not record.is_new:
            return handle_existing(record)
        try:
            result = func(*args, **kwargs)
            db.update_status(key, 'success', result)
            return result
        except Exception as e:
            db.update_status(key, 'failed', str(e))
            raise
    return wrapper
```

将这个装饰器应用到你的 MCP 工具函数或 Agent 的侧链路（side-effect）操作上，只需传入一个确定性的 `idem_key` 即可。

另外记住三条保底原则：

1. 永远在数据库层面增加与幂等键无关的**业务唯一约束**（如订单号、消息 ID），即便幂等系统部分失效，数据库也会拒绝重复数据写入。
2. 对外部系统调用，尽量要求它们支持幂等或提供去重参数（如 Stripe 的 `Idempotency-Key` 头）。
3. 监控幂等工作录的状态比例：`success` 远大于 `processing` 或 `failed` 才是健康状态。如果 `processing` 记录长时间驻留，说明存在僵死的并发任务。

## 总结

自动化任务的幂等性不是“高级优化”，而是构建可靠系统的基线。特别是在 Agent 和插件环境里，重复执行是常态而不是异常——调度器、重试机制、消息系统都会制造重复。与其事后修数据、补消息，不如在设计之初就为每一个有副作用的操作定义一个幂等键，并用数据库唯一约束作为最后的防线。

你不需要追求理论上的“精确一次”（exactly once），但一定要做到“有效一次”（effectively once）：无论调用多少次，业务结果与执行一次一致，且可安全重试。做到这一点，你的自动化流水线才能真正放心地托管给 OpenClaw 去跑。
