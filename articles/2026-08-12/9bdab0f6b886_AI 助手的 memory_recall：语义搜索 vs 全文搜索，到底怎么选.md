## 背景：记忆召回是长生命周期的 Agent 刚需

在 OpenClaw 这类可编排的 Agent 系统中，一旦 AI 需要处理跨会话、长链路的任务，memory 模块就成了必选项。无论是基于 MCP 的 memory server，还是插件化挂载的本地记忆库，核心流程都是：**写入记忆 → 存储 → 后续任务时召回最相关的几条记忆 → 注入上下文**。这个过程业界常称为 memory_recall。

然而，召回这一环却是最容易“沉默地出错”的地方。错误不是报异常，而是发给模型的记忆质量不足，导致回答偏离、幻觉增多，用户体感就是“它不记得了”。

我在为 OpenClaw 实现一个长期任务记忆插件时，遇到的核心问题就是：选择哪种召回策略？是当下流行的语义搜索（向量相似度），还是传统的全文搜索？这篇文章把两种方案的实测、踩坑与权衡整理出来，供有同样困惑的开发者参考。

---

## 问题：不是哪个更好，而是你的记忆长什么样

先抛开“语义搜索代表先进技术”这种先入为主的想法。技术选型要看记忆数据本身的特征。

以我的场景为例：记忆来自多轮对话的自动摘要、用户给过的偏好指令、以及 Agent 完成任务后保存的“经验片段”。这些记忆长短不一，但从检索需求看，大致分两类：

1. **事实型记忆**：用户的 API Key 名称、固定的配置参数、某次会议明确记录的截止日期。  
   这类记忆需要**精确匹配**，差一个字就完全无关。

2. **概念型记忆**：用户偏好某种风格的回答、常用某类工具的倾向、对某话题的态度。  
   这类记忆需要**语义层面的理解**，换一套说法也要能召回。

如果一律采用单一方案，必然顾此失彼。下面是两种方案的工程对比。

---

## 做法：两种方案的实现路径与实测表现

### 方案 A：纯语义搜索（向量化 + 余弦相似度）

**实现方式**：使用 `text-embedding-3-small` 对所有记忆生成 1536 维向量，存入 Qdrant（或 Chroma）。检索时，将当前查询同样向量化，按余弦相似度取 top-k。

**优点**：  
- 自然捕捉语义相关性。比如查询“上次给我画的图放在哪儿了”，能命中“插画生成输出路径”。  
- 对表述变体、多语言混合效果好。

**实测问题（踩坑点）**：  
- **语义漂移**：当记忆库中存在大量“相似但无关”的内容时，嵌入模型会把它们拉到相近区域。比如我存储了多段关于“模型性能调优”的讨论，结果查询“优化当前任务执行耗时”时，召回了调优过程的记忆，但实际需要的是“任务执行的计时日志”。  
- **对短事实不友好**：像 “API_KEY=sk-xxx” 这类记忆，向量距离相近的可能是完全不相关的配置，很难稳定命中。  
- **冷启动成本**：频繁写入记忆时，需要不断调用 embedding 服务，成本与延迟不能忽视。

### 方案 B：纯全文搜索（BM25/TSQuery）

**实现方式**：使用 PostgreSQL `pg_bigm` 扩展，建立对记忆内容的 trigram 索引，查询时用 `LIKE` 或 `ts_rank` 进行得分排序。

**优点**：  
- **精确可控**：对于包含特定关键词的记忆，召回准确率高。  
- **可解释性强**：可以看到是命中了哪个词，排查问题比向量距离直观。

**实测问题（踩坑点）**：  
- **同义词困境**：用户说“保存”，但记忆里写的是“持久化”，结果零召回。  
- **长文本退化**：长记忆匹配时，大量无关词稀释了相关性得分，top-k 被噪音占据。  
- **多语言分词难题**：CJK 语言需要添加额外的分词器，否则召回率极低。

## 可复用的建议：不要二选一，要组合拳

在实际生产环境里，我更推荐**混合检索 + 后处理**的策略，下面这套方案在 OpenClaw 的 memory 插件中运行稳定，复用性强。

### 第一阶段：多路粗召回（Fusion）

并行跑两条召回管线：  
- **语义召回**取 top-20  
- **全文召回**取 top-20  
将两路结果去重合并，得到一个 30～35 条候选集。这是为了避免早阶段过滤掉有效记忆。

### 第二阶段：重排序（Re-rank）

用 Cross-encoder 模型（如 `bge-reranker-base`）对候选集计算查询与记忆的成对相关性分数，取最终 top-5 返回。这一层能弥合初期检索的不足，例如将语义漂移但无关的高分项降权。

### 小技巧：为记忆打标签

在存储记忆时，自动提取结构化字段（标签、类型、时间），检索时用这些字段做硬过滤，可以显著提升召回质量。例如：只检索“偏好类”记忆，或只检索一周内的记忆。

**工具栈建议**：  
- 向量库：Qdrant（支持 payload 过滤 + 多向量）  
- 全文索引：单机用 SQLite FTS5，集群用 pg_bigm 或 OpenSearch  
- 重排序：可以离线部署 `reranker`，或调用 Cohere/Jina 的重排 API

## 总结

AI 助手的 memory_recall 选型没有银弹。语义搜索擅长理解，但不擅长精确；全文搜索擅长精确，但不擅长理解。一个务实的工程师不会试图用其中一种覆盖全部场景，而是在召回链路里分层设计，让每种方案发挥长处。

最后提醒一点：**记得持续评估**。随着记忆库增长，检索质量的分布会变化，定期用标注的查询-期望记忆对做离线评测，调整权重或切换模型，是避免记忆“不知不觉坏掉”的唯一办法。

在 OpenClaw-CN 社区里，我看到很多优秀的 Agent 实践聚焦于工具调用和流程编排，但请一定不要忽视记忆层。它有可能是你整个系统里，离“像人一样记住”最近的一环。
