## 背景：E2E 测试编写的高摩擦成本

端到端（E2E）测试的价值毋庸置疑，它能覆盖真实用户路径，保护核心流程不被回归破坏。但实际工程中，编写和维护 E2E 用例的人力成本一直居高不下，往往成为团队最先放弃的环节。几个典型痛点：

- **选择器脆弱**：前端频繁变动导致定位策略失效，维护脚本的时间甚至超过编写。
- **状态准备复杂**：登录态、数据预置、异步等待都需要大量样板代码。
- **编写效率低**：录制工具生成的代码质量差，手工编写又极度依赖对 Playwright / Cypress API 的熟练度。
- **断言策略单一**：容易陷入“看得见就算过”的浅层校验，遗漏业务逻辑异常。

过去一年，Agent 范式与 MCP（Model Context Protocol）的落地，让“AI 与浏览器实时交互”成为可能。我们的问题变为：能否将 Agent 作为测试协作体，在人工指导下完成探索、录制、生成、甚至自愈？

## 问题拆解：Agent 写测试，到底“写”什么

这里的“写”不是一次性把几百行脚本吐出来，而是一个多阶段的协作过程：

1. **意图表达**：用自然语言描述测试场景（如“从首页搜索商品，加入购物车，断言价格与结算页一致”）。
2. **探索与定位**：Agent 控制真实浏览器，理解页面结构，记录有效操作路径。
3. **脚本生成与抽象**：将操作序列转为可维护的 Playwright 代码，并抽象出合理的定位器、等待策略和断言。
4. **人工介入**：开发者审核生成代码，补充异常分支、压入 data-testid 等约定。

整个过程的核心挑战，不是“生成代码”本身，而是**如何让 Agent 产出的脚本具备工程可复用性**，而不只是一次性的操作回放。

## 做法：基于 Playwright MCP 的 Agent 协作流程

我们基于 MCP 协议搭建了一个可复现的闭环：Agent 端负责规划与决策，Playwright MCP 服务器负责浏览器操控。具体步骤：

### 1. 搭建 Playwright MCP Server
使用 `@anthropic/mcp-server-playwright` 或其他社区实现（`playwright-mcp`），暴露浏览器操控工具给 Agent：
```bash
npx @anthropic/mcp-server-playwright --headless=false
```
关键是保留非 headless 模式，让开发者可视化观察 Agent 的操作过程，同时允许人工打断。

### 2. 定义任务描述与约束
在 Agent 的 system prompt 中注入测试工程规约：
- 优先使用 `data-testid` 定位；若无，使用 `aria-label`，再降级为 Playwright 内置的文本/角色选择器。
- 每次操作后必须等待网络空闲或特定元素可见，防止竞态。
- 记录操作序列的同时，要求 Agent 输出“为什么选择该定位器”的解释。
- 限制最多探索步数为 15 步，避免无意义漫游。

### 3. 执行探索并截图标记
Agent 通过 MCP 调用浏览器导航、点击、输入。每步操作后调用截图工具，并在截图中框选交互元素。这样后期可回溯每一步的上下文，便于定位误操作点。

### 4. 从操作日志生成 Playwright 测试代码
Agent 将步骤记录转换为如下结构的 TypeScript 代码：
```typescript
test('search and add to cart', async ({ page }) => {
  await page.goto('/');
  await page.getByTestId('search-input').fill('test product');
  await page.getByRole('button', { name: 'Search' }).click();
  await expect(page.getByTestId('product-list')).toBeVisible();
  // ...后续步骤
});
```
同时为每个关键断言生成期望值的注释，便于人工校准。

### 5. 人工审查与 CI 集成
生成脚本后，开发者需：
- 替换掉个别仍不稳定的选择器；
- 补充边界条件（空搜索结果、网络错误重试）；
- 将脚本插入现有 Playwright 配置，连接 CI 服务。

## 踩坑记录：三个典型的“伪成功”

**坑 1：选择器“看似正确”实则脆弱**
Agent 常倾向使用文本定位（`text=加入购物车`），但多语言站点下文本会变化。我们强制要求 prompt 中声明“若元素无 data-testid，请输出警告，不生成代码”，并在人工审查阶段强调这一点。

**坑 2：忽略异步状态导致 flaky**
Agent 点击“结算”后立即断言价格，此时可能仍在请求中。解决方法是要求 Agent 在每步操作后插入 `expect(someIndicator).toBeVisible()` 作为隐式等待，并明确要求不要使用 `page.waitForTimeout`。

**坑 3：Agent 在长任务中“迷路”**
复杂流程中 Agent 会误触导航栏、弹窗，导致页面跳转丢失状态。对策：限定每次任务只覆盖一个连续路径，复杂场景拆分为多个短测试，Agent 负责单路径，人工负责组合编排。

## 可复用建议

- **将定位策略固化为团队规范**：在 Agent 的 prompt 中锁定 `data-testid` > `role` > `text` 的优先级，产出即规范。
- **生成“自愈”辅助层**：让 Agent 同时生成备选选择器列表，配合重试机制，降低维护成本。
- **Agent 生成的不只是代码，还有文档**：利用 Agent 输出的解释，自动生成测试用例描述，存入 TMS。
- **渐进式采纳**：先用于生成冒烟测试的草稿，再逐步扩展到核心交易链路。
- **搭配视觉模型做校验**：在关键步骤上增加截图对比（如 `toHaveScreenshot`），弥补纯结构化断言的不足。

## 总结

Agent 协作在 E2E 测试中的价值，不是取代测试工程师，而是把“从 0 到 60 分”的体力活交给 AI，让工程师专注在“60 到 90 分”的稳定性打磨和场景设计上。Playwright MCP 提供了一套干净的浏览器操控原语，结合 Agent 的规划能力，我们可以把测试编写的启动成本降低一个数量级。但在选择器规范、异步策略、任务拆分等方面，人工的工程判断依然不可或缺——而这些正是社区可以持续沉淀的最佳实践。
