## 背景：agent 需要记得更多

在 OpenClaw 里搭建一个稍微复杂的自动化助手时，很快就会碰到“记忆”问题。用户两周前问过的设备型号、上次脚本运行失败的报错信息、某个文件夹路径——这些东西如果每次对话都要重新输入，agent 就只是高级命令行，算不上真正的助手。

于是我为一套内部运维助手加了 `memory_recall` 工具：每当新对话启动，agent 会从历史对话日志里检索相关片段，拼进 system prompt。后续扩展成一个轻量记忆服务，用 MCP 工具暴露给 OpenClaw。

实现过程中，我需要决定核心检索方式：全文搜索（关键词匹配）还是语义搜索（向量相似度）。这两个方案各有利弊，在真实环境中踩了不少坑。本文是一次工程层面的复盘，包括方案选择、具体搭建、遇到的坑以及可复用的建议。

## 问题：两个方向，怎么取舍

场景非常简单：把每段对话分割成块（chunk），每条记录包含时间、角色、内容。召回时，输入当前用户问题，找到最相关的历史块，返回 top-K。

全文搜索（例如 BM25 或 SQLite FTS5）的优势是精确、跑得快、可解释性强，但无法处理同义词、改写。语义搜索用 embedding 做余弦相似度，擅长理解意图，但可能召回不相关的内容，长尾词容易漂移。

真实的 agent 场景里，纯粹用哪一个都不够好。运维助手查询风格很杂：有时用户直接贴错误码（精确匹配，全文优），有时用自然语言描述现象（语义优）。结论是：混合召回最可靠。

## 做法：本地跑一个混合召回 MCP 工具

我在 Assistant 服务器上搭了一个轻量的 memory 服务，核心依赖三个组件：

- **SQLite + FTS5**：做全文索引，同时存储块元数据（时间、角色）。
- **Sentence-Transformers (`all-MiniLM-L6-v2`)**：本地生成 embedding，无需外部 API。
- **MCP server (Python)**：暴露 `memory_recall` 工具，接收查询字符串，返回混合排序后的历史片段。

### 数据准备与索引

先把历史对话按 300~500 字符分块，去掉过短的无意义行。建表 SQL 大致如下：

```sql
CREATE VIRTUAL TABLE memory_fts USING fts5(
    chunk_id,
    content,
    role,
    timestamp
);
```

同时建一张 `chunks` 主表存放原始块，并新增一个 `embedding` 字段（BLOB 存放序列化的 float32 数组）。生成 embedding 的脚本用 `sentence-transformers` 批量处理，把结果写入对应的行。

这里一个容易忽视的点：**embedding 维度固定为 384（MiniLM），存储开销可控**。如果换更大的模型，BLOB 尺寸会迅速增大，注意 SQLite 页大小限制。

### 检索与混合排序

`memory_recall` 工具的处理流程：

1. 对查询 `q` 分别执行 FTS5 搜索和向量搜索。
2. FTS5 使用 `MATCH` 语句返回 BM25 分数，取 top-20。
3. 向量搜索：将 `q` 编码为 embedding，与库中所有块计算余弦相似度，取 top-20。全库计算在小规模（<1 万条）下完全可接受；规模更大时，可借助 `faiss` 建索引。
4. 两个结果列表用 **Reciprocal Rank Fusion (RRF)** 合并：`score(doc) = sum_{rank in list} 1/(k+rank)`，`k=60` 能平滑排名影响。
5. 最终返回前 5 条，附带原始文本和时间。

MCP server 端的工具定义示例（简化）：

```python
@server.tool()
async def memory_recall(query: str, top_k: int = 5) -> list:
    results = hybrid_search(query, top_k)
    # 返回列表，每一项包含 content, role, timestamp, score
    return results
```

在 OpenClaw 的 agent 配置里直接引用这个 MCP 工具即可。

### 效果对比

用同一个运维问题库（约 3000 条历史对话块）做了简单评测。典型例子：

- **错误码查询**“E1005”：FTS5 准确命中所有相关块；纯语义搜索最多返回两条相似错误的块，但掺杂不少噪音。
- **自然语言**“之前那个磁盘满的脚本怎么跑的？”：语义搜索 top-3 几乎全是磁盘满相关操作，FTS5 因为缺少“磁盘满”同义词，只靠“脚本”召回了一堆无关内容。
- 混合排序在这两类查询下都拿到了最好的前 5 精确率。

## 踩坑点

1. **向量搜索冷启动**：新增块后，如果不及时重建向量索引，语义搜索会遗漏最新内容。做了一个轻量触发器：新块入库后异步生成 embedding 并写入，但要注意并发读写时的行锁。
2. **FTS5 中文分词**：默认 tokenizer 对中文不友好，必须显式指定 `tokenize=unicode61` 或配合外部分词器（如 jieba 先分词再用空格连接后入 FTS）。否则“磁盘满”可能搜不到“磁盘使用率过高”。
3. **RRF 参数迷信**：早期把 k 值调得很大（比如 300），结果排名完全被 FTS5 主导。后来将 k 降到 40~60，两个检索源的作用才均衡。建议在自有数据集上用少量标注样本调一下。
4. **性能陷阱**：全库向量检索在 CPU 上跑 MiniLM 其实很快，但如果用 `cosine_similarity` 逐条计算 1 万条以上时，有明显延迟。可以提前把标准化后的 embedding 存成 MySQL/faiss 索引，召回时只做点积。对于个人助手，小于 5000 条就直接全量计算，省去额外索引维护。

## 可复用建议

- **先用 FTS 走第一关**：全文搜索快、资源消耗低，可以安全地放量召回到 20~30 条；然后再用语义或交叉编码器细排。不要直接在万级文档上跑语义粗排。
- **本地模型足够**：`all-MiniLM-L6-v2` 在意图召回上表现足够，不需要接 OpenAI embedding。隐私友好，延迟也低。
- **块大小和实践**：对话记忆块控制在 200~500 个 token，太长会稀释语义，太短缺少上下文。加入时间权重可以大幅提升近期相关片段的召回。
- **把 memory 当作独立服务维护**：不要和 agent 逻辑耦合。MCP 接口定义清晰，将来可以切换后端（例如换成 pgvector）而 OpenClaw 侧无需改动。
- **定期清理与归档**：长期记忆不是无限堆叠，设计 TTL 或自动摘要机制，避免检索噪声掩盖有效信息。

## 总结

全文搜索和语义搜索不是二选一，而是检索流水线上的上下游。在资源受限、文档规模不大的 agent 场景里，用 SQLite FTS5 + 本地 embedding + RRF 融合，是最经济且效果可靠的方案。纯语义搜索在模糊意图理解上有优势，但不可控的召回噪音会降低 agent 后续判断的质量；纯全文搜索则太僵化，损失大量可用记忆。把两者结合起来，你的 OpenClaw 助手才能真正从“对话”变成“经验”。
