## 背景：当 Agent 不只是聊天，而是真的在“干活”

OpenClaw 这类 Agent 框架的核心能力之一，是通过 MCP（Model Context Protocol）插件系统让 LLM 驱动真实世界的操作：读写文件、执行 Shell、发送 HTTP 请求、操作数据库甚至控制 IoT 设备。这带来了一个无法回避的工程问题：**哪些操作 Agent 能自己做，哪些必须经过人类确认？**

如果只把 Agent 当作聊天机器人，权限问题几乎不存在。但一旦接入 MCP server，一条 `rm -rf` 或一个 `DROP TABLE` 指令就可能通过模型推理被“聪明地”执行掉。简单粗暴地禁止所有高危操作会让 Agent 沦为玩具；而完全放开权限又无异于裸奔。

本文不讨论抽象的安全伦理，而是从工程实践角度，梳理在 OpenClaw + MCP 场景下如何为 Agent 设置合理的权限边界，包含可落地的分层模型、踩坑记录和可复用方案。

## 问题拆解：两种失败模式

在设计权限边界时，我们主要面临两类失败：

1. **过度询问**：Agent 每次想读个配置文件都弹窗请求批准，用户很快陷入“审批疲劳”，直接点“允许”，最终形同虚设。
2. **擅自行动**：Agent 在未被授权的情况下执行了破坏性操作，事后才发现为时已晚。

优秀的权限控制要在这两种失败模式之间找到平衡——既不给用户添堵，又不给灾难留后门。核心思路是：**让风险分级，让上下文决定是否打断**。

## 做法：基于风险等级的三层权限模型

我们在一个基于 OpenClaw 的内部运维助手上实践了如下分层，MCP 服务器通过工具描述中的自定义标签声明风险等级，Agent 运行时由权限中间件统一拦截。

### 1. 工具风险等级定义

将每一个 MCP 工具调用划分为三个等级：

- **safe**：只读操作、无副作用、不泄露敏感信息。例如 `read_file(path="/etc/hosts")`、`list_directory(path="/tmp")`。这类操作无需询问，由 Agent 自主调用。
- **ask**：有潜在副作用但可逆，或操作范围受限。例如 `execute_shell(command="systemctl restart nginx")`、`update_config(key, value)`。Agent 在调用前必须暂停推理，向用户展示将要执行的操作并请求一次性或条件性批准。
- **deny**：不可逆破坏性或安全敏感操作。例如 `execute_shell(command="rm -rf /data/*")`、`delete_user()`。Agent 在任何情况下都不被允许直接调用，只能输出建议，由人类手动执行。

等级声明示例（在 MCP tool 的 description 字段中通过约定前缀标记）：
```
[risk:ask] Execute a shell command on the production server. Must be confirmed.
```

### 2. 权限中间件实现

在 OpenClaw 的 `tool_invocation` 生命周期中插入一个拦截器，伪代码逻辑如下：

```python
def permission_middleware(tool_call):
    risk = extract_risk_level(tool_call.description)
    if risk == "safe":
        return invoke_directly(tool_call)
    if risk == "ask":
        # 检查是否已有会话级授权
        if session.has_permission(tool_call.signature):
            return invoke_directly(tool_call)
        # 否则中断，向用户展示待审批操作
        return request_human_approval(tool_call)
    if risk == "deny":
        return block_with_explanation(tool_call)
```

关键点在于**会话级临时授权**：用户一旦批准某个具体操作（如“重启 nginx”），在同一个任务会话内不必反复确认，避免审批疲劳。授权范围可以精确到参数哈希，防止参数变化导致授权被滥用。

### 3. 上下文感知的动态调整

纯粹基于规则的静态分级还不够。例如，`execute_shell(command="ls /home")` 通常是无害的，但如果 `/home` 下包含大量用户隐私目录，用户可能不希望 Agent 随意浏览。我们增加了**敏感路径 / 敏感参数匹配规则**：即使是 `safe` 操作，如果参数命中了预先配置的敏感模式（如路径包含 `.ssh/`），自动升级为 `ask` 等级。

这些规则以 JSON 配置文件形式加载，方便运维团队随时调整，无需修改代码。

## 踩坑点

### 坑1：工具描述不规范导致风险误判

早期我们依赖开发者自觉在 description 中标记风险，结果出现大量漏标、误标。一个 `delete_tmp_files` 被标成 `safe`，但清理脚本写得过于激进，把正在使用的临时文件也删了。后来强制要求所有 MCP 工具必须显式声明风险等级，并在 CI 中增加了静态检查：未标记的工具直接拒绝加载。

### 坑2：长任务链中的上下文丢失

Agent 执行多步任务时，中途暂停等待用户确认后，容易丢失之前的推理上下文，导致继续执行时做出不一致的决定。我们的对策是：在请求人类确认时，把当前 Agent 的“意图摘要”和“预期后续步骤”一并呈现，并在用户批准后将批准结果作为一条虚拟工具返回结果注入上下文，帮助模型保持连贯。

### 坑3：移动端 / 异步场景下的确认延迟

运维 Agent 往往不是实时盯屏的。如果用户在手机上收到一条确认请求，30 分钟后才批准，底层的 SSH 会话可能早已超时。解决方案是为 `ask` 类工具设置有效期（通常 5 分钟），超时自动拒绝并通知 Agent 重新规划。

## 可复用建议

1. **从 safe 起步，逐步开放**：新接入的 MCP 工具默认全部设为 `ask`，经过一段时间的观察和日志审计后，再将确实无害的操作降级为 `safe`。这一步不可逆反，谨慎为上。
2. **设计可撤销机制**：对于 `ask` 类操作，尽量让工具提供逆向操作（如 `deploy_version` 配套 `rollback_version`）。即使经过人类批准，也可在出问题时快速回退。
3. **输出可审计的决策日志**：每次权限判断（直通 / 询问 / 拒绝）都记录时间戳、调用参数、风险等级、最终决定。这些日志不仅是安全审计的需要，也是优化分级规则的依据。
4. **提供“为什么不能做”的解释**：当 Agent 拒绝执行 `deny` 操作时，不要只返回冷冰冰的“permission denied”，而要让模型生成一条包含原因和替代建议的消息。这会大幅降低用户对 Agent“不听话”的负面感受。
5. **避免把所有权限逻辑塞进 prompt**：有人试图用 system prompt 来约束“不要删库”，这是一种幻觉式安全。权限边界必须实现在工具调度层，而不是提示词层。

## 总结

AI Agent 的权限边界不是一个静态开关，而是一套需要持续迭代的工程体系。**“何时问人类、何时自己干”的本质，是在自动化效率和风险控制之间找到数据驱动的平衡点。** 通过将 MCP 工具按风险分级、在调用路径中插入可配置的权限中间件、并辅以上下文感知和审计日志，我们可以在不牺牲 Agent 实用性的前提下，守住安全的底线。

在 OpenClaw 的路线图中，权限控制模块还有很大增强空间，例如支持基于用户身份的细粒度授权、利用模型不确定性量化来决定是否询问等。但上述分层模型已经能覆盖大多数生产场景，并且足够简单，值得一试。
