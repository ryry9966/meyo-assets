## 背景

团队每天都需要从分散的日志源中汇总信息，手工编写日报——从几十个文件、Elasticsearch 索引或云监控面板里抓取异常、统计指标、梳理变更记录，再整理成固定格式发出。这件事重复、易出错，且严重依赖编写者对系统的熟悉程度。轮值的人不同，日报质量波动很大。

同时，我们的内部工具链已经接入了 OpenClaw 风格的 Agent 体系和若干 MCP 工具，如果能用一个可审计、可干预的流水线替代手工日报，就能把时间还给真正的排障和开发。

## 问题拆解

一条完整的自动化日报流水线需要解决三层问题：

1. **数据获取**：原始日志可能来自文件系统、ES 集群、Loki、数据库审计表，甚至 HTTP 接口，需要统一但可扩展的读取方式。
2. **信息提取与压缩**：原始日志体积常常远超 LLM 上下文窗口，必须做分块、摘要、去重和结构化，否则会触发幻觉或截断关键信息。
3. **报告生成与分发**：输出必须是格式稳定的结构化报告，不允许随意发挥；失败时必须提供可追踪的错误信息，而不是静默丢失。

## 实现方案

我们基于 Agent + MCP 服务器搭建了每日定时流水线，整体架构分四个部分：

### 1. MCP 工具层：统一日志读取接口

编写了三个 MCP 服务器提供工具调用：

- `elasticsearch_query`：负责从多个索引按时间范围、日志级别、关键词查询日志，返回结构化 JSON，内置分页与限流。
- `file_log_reader`：用于读取本地挂载的滚动日志文件，自动处理 gzip，通过正则过滤出当天的日志行。
- `metric_fetcher`：从 Prometheus 拉取前一天的关键指标（错误率、延迟 p99、磁盘使用率），返回聚合数据。

每个工具都向 Agent 暴露标准的 JSON schema，并自行处理认证、超时和重试逻辑。工具间做了解耦，Agent 根据日报模板的需求按需调用，不会一次性拉全量数据。

### 2. Agent 编排层：分阶段处理

Agent 使用 ReAct 模式，但我们将核心逻辑封装为有状态的多步流水线，减少自由发挥空间。

**Step 1 - 数据拉取**  
Agent 先调用 `elasticsearch_query` 获取 ERROR 和 WARN 级别日志，同时查询近 24 小时的慢查询记录；调用 `metric_fetcher` 拉取关键指标；根据配置决定是否调用 `file_log_reader` 补充应用日志。所有结果存入工作内存，不做即时总结。

**Step 2 - 分块摘要与异常识别**  
对于拉取到的日志数组，Agent 按 50 条一组进行切割。每一组发送给 LLM 要求提取：异常堆栈的关键行、影响的服务、首次发生时间、是否为已知错误码。同时附上一条约束 prompt：「只提取事实，不要推测根因，不要补充背景知识」。每组输出结构化 JSON，最后将所有分块结果合并去重。

**Step 3 - 聚合与模板填充**  
预先定义了一份 Markdown 模板，包含固定章节：概要、异常事件与影响范围、资源水位、慢查询 Top N、变更记录、待处理项。Agent 将 Step 2 的提取结果填入对应章节，对未拉取到数据的部分用 "N/A" 显式标注，不允许省略章节。

这份模板存储在配置文件中，Agent 通过 `fill_template` 工具函数完成填充，而非靠 prompt 硬编，保证了格式刚性。

**Step 4 - 发布与归档**  
最终报告通过内部 Webhook 发送到协作平台，同时写入对象存储作为归档。Agent 会返回一个包含报告摘要和归档链接的确认消息。

### 3. 定时触发与监控

使用 cron 定时任务在每日 8:00 UTC 触发 Agent 运行。关键点在于：

- 每次运行生成唯一 run_id，便于追踪。
- 任意一步失败时，Agent 会产出失败报告（包含失败步骤和原始上下文），并通过单独的告警 Webhook 发送，防止日报静默中断。
- 在连续 3 次失败时自动停用，等待人工介入。

## 踩坑记录

| 坑 | 现象 | 处理方式 |
|---|---|---|
| **上下文超限** | 一天 ERROR 日志 2000+ 条，直接塞入 LLM 导致截断或幻觉摘要。 | 强制分块，单块不超过 50 条，块间去掉重复堆栈后合并。 |
| **时区偏移** | 日志时间戳是 UTC，日报期望按北京时间展示，早期出现日期边界错位。 | 所有查询在 MCP 工具层统一转换为日报所需时区，禁止 Agent 自作主张转换。 |
| **提取假阳性** | LLM 有时把 INFO 日志中的「error: 0」误判为异常。 | 在模板填充前增加一层规则校验：如一个「异常事件」无异常级别标志，且堆栈为空，则丢弃。 |
| **模板章节丢失** | 当某天没有慢查询时，Agent 会直接删除该章节，导致订阅者疑惑。 | 利用 `fill_template` 函数强制性保留所有章节，无数据时输出「本日无」。 |
| **工具调用超时** | ES 查询偶发慢，Agent 等待超时后重试，但上下文已混乱。 | MCP 工具内置指数退避重试；Agent 层设置 2 次总重试上限，超过即输出失败报告。 |

## 可复用建议

- **日志读写与摘要逻辑解耦**：MCP 工具只负责返回原始或轻量聚合数据，不嵌入任何业务语义；摘要逻辑全部放在 Agent 的 pipeline 中，便于单独调试和优化。
- **用模板约束输出，不要相信 prompt 的格式承诺**：即使 prompt 严格描述格式，LLM 仍有概率删节或重新排序章节。用代码填充模板是最稳的方式。
- **为失败设计输出**：日报任务常见失败不是大问题，可怕的是失败后无人知晓。务必为流水线配置独立的告警通道和失败报告。
- **测试必须包含极端日志量**：日常测试容易忽略，一旦上线遇到日志暴增，上下文管理和分块逻辑才会暴露缺陷。模拟一万条 ERROR 的测试场景很有必要。

## 总结

这套从原始日志到结构化日报的自动化流水线已经稳定运行几个月。它没有引入复杂的状态管理或外部存储，完全依赖 Agent 的步骤编排和 MCP 工具层的能力。最大的收益不是节省了多少分钟，而是日报质量的方差被抹平，所有人都能信任同一份数据源。

如果你也在用 OpenClaw 生态，不妨先将最简单的日志来源封装成一个 MCP 工具，尝试运行一个最小化日报 Agent，再逐步加入错误识别和模板固化。从半自动化到完全自动化的过程中，你会更清楚自己的日志里到底哪些信息是真正重要的。
