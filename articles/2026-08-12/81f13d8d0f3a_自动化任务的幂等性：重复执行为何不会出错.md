## 为什么你总在担心“重复执行”

使用 OpenClaw 编排 Agent、通过 MCP 调用外部工具、或在插件里触发自动化流程时，有一个问题迟早会浮现：**同一个任务被执行了两次，然后系统里出现了两条重复记录、两封相同的通知，或更糟——同一个扣款动作被执行了两遍。**

根本原因不是代码写得差，而是很多触发源天然不具备“恰好一次”的保证：消息队列可能重推，用户可能连点按钮，定时任务可能因为调度延迟而重叠，网络超时后的重试策略也经常导致重复调用。换句话说，**重复执行不是异常，是分布式系统的常态**。如果你没办法让重复执行不发生，那就必须让重复执行没有副作用，这就是幂等性要解决的问题。

---

## 幂等性的工程定义

幂等（idempotency）在计算机里的含义很纯粹：一个操作，不管执行一次还是多次，只要输入相同，它对系统产生的副作用和执行一次完全一样，之后再次执行可以直接返回已有的结果，或者毫无副作用地跳过。

用自动化任务的语言翻译一下：
- 创建资源：如果资源已存在（由同一个业务键锁定），则直接返回已有资源，不报错也不新建。
- 状态变更：如果已经变更为目标状态，再次请求时忽略。
- 发送消息：如果这条消息已经发送过，就不再发送。

注意，这里并不要求“每次执行返回相同响应”，只要求**业务副作用**一致。幂等是业务逻辑的承诺，而不是传输协议的天然特性。

## 在 OpenClaw/MCP 场景下怎么做

围绕 Agent 和 MCP 的场景，实施幂等通常不需要重写系统，只需在几个关键点插入“去重”逻辑。

### 1. 为每个任务引入幂等键

让每个可能重复进入的任务都携带唯一标识，比如事件 ID、请求 ID、事务 ID。在 OpenClaw 的工作流中，可以由触发源生成，也可以由流程第一步根据业务参数（用户+操作类型+业务单号）哈希生成。这个键就是后面所有去重的锚点。

```text
idempotency_key = f"order.12345.charge.usd"
```

### 2. 任务开始时做“已处理”检查

在一个支持原子读写的存储中（Redis、数据库表、甚至本地 SQLite 都行），用幂等键查询是否已经存在。如果存在且状态为已完成，直接返回之前存储的结果或跳过；如果不存在，则执行业务逻辑，成功后写入记录。

### 3. 将“检查-执行-标记”做成原子或可串行化

这是最容易踩坑的地方。两个并发请求同时拿到“未处理”的状态，就可能双双执行。解决方法三选一：
- **唯一索引 + 插入看守记录**：在数据库里为幂等键建唯一索引，业务开始前先用 `INSERT` 写入一条 `processing` 状态记录，成功则继续，失败说明别人抢到了。
- **分布式锁**：用 Redis `SET NX` 对幂等键加短锁，执行完成后释放。
- **乐观锁**：对业务资源本身加版本号，重复执行时版本号条件不再满足，操作自动无效。

在 MCP 工具的封装中，这一步特别重要。比如你写了一个 `send_message` 的 MCP 工具，如果服务端没有幂等机制，那你必须在工具内部包一层本地幂等检查。

### 4. 外部 API 调用尽量使用带幂等支持的接口

很多支付或消息推送服务已经提供了幂等键参数（如 Stripe 的 `Idempotency-Key` 头部）。调用时直接把业务幂等键透传过去，就能把重复请求安全地交给对方去重。

## 踩坑记录：几个真实的翻车点

- **用随机值当幂等键**  
  见过有人用 UUID 当幂等键，每次请求重新生成，结果每次都是“新请求”，完全失效。幂等键必须由业务上下文或上游在第一次生成后保持稳定。

- **先标记后执行**  
  如果先插入 `completed` 状态再执行，执行失败后这个键就“脏”了，后续真实执行会直接被跳过。正确顺序是：插入 `processing` → 执行 → 更新为 `completed`。如果执行失败，应将状态停留在 `processing` 或删除记录，等待重试或超时回收。

- **忘记考虑部分成功**  
  假设任务包含两步：更新数据库 + 发送通知。第一步成功，第二步失败，然后你标记为完成。重试时会以为整个任务已完成，通知永远不会发出。应对方案是：要么将整体封装成一个事务，要么把任务拆成更小的幂等子任务各自去重（Saga 模式），要么在失败时不标记完成并触发补偿。

- **幂等键没有生命周期**  
  如果任务是一次性的（比如订单支付），幂等键可以长期保存。但如果是高频事件，存储会膨胀。需要根据业务设定过期时间（例如 7 天后查询源系统状态，而非依赖本地记录）。

## 可复用的落地建议

1. **OpenClaw 工作流节点输出携带幂等键**：每一个关键节点的输出里带上 `run_id + node_id + business_key`，下游节点用这个组合作为去重依据。
2. **MCP 工具统一增加幂等中间件**：写一个简单的 wrapper，在工具调用前从参数中提取 `idempotency_key`，查 Redis，命中则直接返回缓存结果。
3. **数据库表设计时先建唯一索引**：对业务主键或组合键建 `UNIQUE` 约束，天然防重复插入。
4. **消息消费者先落库再处理**：消费事件时，第一时间将 `event_id` 写入幂等表（insert ignore），再执行后续逻辑，确保就算消费者宕机重启，也不会重复处理。
5. **定时任务加执行窗口标识**：运行时生成一个批次 ID，每个执行单元用“批次 + 业务键”做幂等，防止定时重叠导致的重复跑。

## 总结

自动化任务的幂等性不是锦上添花的特性，而是生产环境里防重复、防资损、防脏数据的底线设计。在 OpenClaw 这类 Agent 自动化平台上，流程节点随时可能被重试，工具调用可能超时重发，把幂等逻辑嵌入到任务执行的骨子里，远比事后写脚本清理重复数据要划算。

记住一个原则：**假设所有输入都可能重复，并用唯一业务键和原子状态检查来消化掉这些重复。** 做到这一点，你的自动化任务就能坦然地面对不稳定网络、用户误操作和调度抖动，重复执行再也不会变成事故。
