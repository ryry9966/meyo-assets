## 背景

在 OpenClaw 里，Agent 不是孤立运行的。我们给它接入 MCP 工具、挂载本地文件系统、允许它执行 shell 命令——这时候，工作区就是一个沙箱，Agent 的行动半径很大。但半径越大，越需要一个「使用手册」：哪些命令是安全的、项目的构建流程是怎样的、目录结构遵循什么约定、测试跑在哪个脚本里。

以前，我们依靠系统提示、记忆库或者每次对话手敲说明。结果是：  
- 系统提示被塞进太多信息，维护成本高  
- 话题切换后 Agent 容易遗忘项目规则  
- 多人协作时，规则藏在各自脑子里，Agent 行为不一致  

OpenClaw 从 Codespace/Agent 类项目中汲取经验，提供了一套轻量约定：在项目根目录放置 **AGENTS.md**，OpenClaw 会在合适的时机将其注入 Agent 上下文，作为「工作空间使用手册」。不是新概念，但它把「项目即提示」这件事工程化了。

## 问题

没有 AGENTS.md 时，我们的典型踩坑场景：

1. **重复交代**：每次新对话都要说“项目用 pnpm，测试用 vitest，别碰 /data 目录”。  
2. **工具滥用**：Agent 擅自执行 `rm -rf` 或尝试修改配置外的路径。  
3. **流水线断裂**：Agent 不知道 CI 会用哪个 lint 命令，提交了不合规代码。  
4. **上下文浪费**：为了矫正行为，消耗大量 token 做解释，挤占了真正要解决的问题。  

## 做法与步骤

### 1. 创建 AGENTS.md

在项目根目录创建 `AGENTS.md`。OpenClaw 会自动发现并加载（默认行为；可以在 `openclaw.yaml` 中配置加载策略）。文件应遵循清晰的结构，避免长篇散文——Agent 读得越快，遵循度越高。

推荐最小骨架：

```markdown
# AGENTS.md
## 项目概览
- 用途：内部文档搜索 + 工单自动化
- 技术栈：Python 3.11, FastAPI, SQLite
- 运行环境：仅在工作区内，不可访问外网

## 目录结构
- `src/` 业务逻辑，按领域分层
- `tests/` pytest 测试，与 src 结构一一对应
- `scripts/` 常用运维脚本，Agent 只能执行 scripts/ 内的安全脚本
- `.data/` 挂载的外部数据，只读

## 常用命令
- 安装依赖：`uv sync`
- 启动开发服务：`uv run uvicorn main:app --reload`
- 运行全部测试：`uv run pytest -x`
- Lint：`uv run ruff check src/`
- 类型检查：`uv run mypy src/`

## 工作流约定
- 修改任何 Python 代码后，必须运行对应测试文件
- 不要直接修改 `.data/` 下的文件
- 凡是删除操作，先列出受影响文件请求人工确认
- 对外部服务的调用只能通过 `src/gateway/` 下的客户端，不得直接 curl
```

### 2. 让 Agent “看见”并使用

OpenClaw 在发起 Agent 会话时会将 AGENTS.md 内容预置到系统消息或首个 user 消息之前（具体插入位置取决于配置）。你可以通过以下方式验证：

- 新开一次对话，要求 Agent：`根据 AGENTS.md 描述项目的测试命令`。它应能准确返回 `uv run pytest -x`。
- 如果 Agent 忽略某些条目，检查 AGENTS.md 是否层级混乱、内容冗长。

### 3. 动态维护

AGENTS.md 不是一次性文档。随着项目演进，你可能需要维护多个版本。比如：
- 在 feature 分支里更新与当前分支相关的临时规则
- 利用 OpenClaw 的 `workspace` 配置项为不同目录指定不同的 AGENTS.md 路径
- 在 CI 中增加一个 `lint:rules` 检查 AGENTS.md 是否存在并满足最低行数、最少章节的要求

## 踩坑点

- **太长反而不读**：超过 400 行后，Agent 明显出现“信息丢失”。实践中控制在 80–150 行，用符号标题分段，关键命令用代码块包裹。  
- **太模糊等于没写**：像“遵循最佳实践”这类空话毫无意义。要提供具体的、可执行的指令。  
- **硬编码动态值**：版本号、密码、IP 不要写死。可以用占位符 `{{BASE_URL}}` 并在上下文中注入实际值，或依赖 Agent 通过工具读取配置。  
- **与系统提示冲突**：如果你在 OpenClaw 的全局 system prompt 里已经声明了目录结构，AGENTS.md 再声明一次可能导致 Agent 困惑。保持一处权威，其他地方只引用。  
- **Agent 不强制执行**：AGENTS.md 只是提示，Agent 如果被强指令覆盖（比如用户说“直接删掉那个目录”），仍然可能违反规则。真正的安全保障要结合沙箱权限和 MCP 工具的权限控制，不能只依赖文档。

## 可复用建议

1. **团队级规约**：把 AGENTS.md 纳入仓库模板，初始化项目时自动生成，强制所有项目都有。  
2. **缩减上下文开销**：将 AGENTS.md 看成“常驻记忆”，减少每次对话中必须重复的信息。统计过，对典型项目，它节省了每次对话 200–400 token 的规则交代量。  
3. **脚本化验证**：写一个小检查器，扫描 AGENTS.md 是否包含必选章节（如常用命令、目录结构），并在 CI 中运行。  
4. **搭配 `openclaw.yaml` 细调**：可以设置 `load_agents_md: always` 或 `only_new_session`，按需选择。也可以为不同 Agent 角色提供不同文件，例如 `AGENTS.reviewer.md`，通过 `agent_profile` 映射。  
5. **每次发布打 Tag 时回顾**：检查 AGENTS.md 是否仍反映最新工作流，防止文档腐化。

## 总结

AGENTS.md 解决的不是 Agent 能力问题，而是**共识问题**。它让项目结构、命令习惯、安全边界变成一种可解析、可加载的“工作空间上下文”，减少口头沟通和上下文浪费。实现成本近乎为零：无非是写好一个 Markdown，放在根目录。但它带来的行为一致性和效率提升，在长期维护多个 Agent 项目的场景里非常明显。

如果你正在维护一个需要 Agent 频繁交互的仓库，试一下：建一个不到 100 行的 AGENTS.md，然后观察 Agent 行为的变化。不需要炫技，只要把团队已经共识的事情写下来，就足以产生价值。
