## 背景：Agent 为什么需要“回忆”

在 OpenClaw 这类多 Agent 编排框架中，一个典型需求是让 Agent 记住过往对话、任务上下文或用户偏好。memory_recall 模块在做的事情，本质上就是一个“带条件的日志检索”——从不断增长的历史记录中，找到与当前问题最相关的一批片段，喂给 LLM 作为背景。

这个检索环节有两个主流路径：

- **全文搜索**（BM25/ES Lucene）：依靠词频、关键词匹配，速度快，对精确术语友好。
- **语义搜索**（Embedding + 向量索引）：把文本映射到稠密向量，计算相似度，能捕获同义和意图。

拿到项目里到底用哪个？或者怎么混用？我们在一组实际运行中的对话 Agent 上做了对比实验，这篇文章把结论和踩过的坑写出来，给正在做 memory 的同学一个理性的参考。

---

## 问题：看似简单的检索，实际两极分化

先看个典型场景：Agent 被问到“上次那个部署脚本的密码是啥？”。历史记录中可能有一条：

> “机器 10.0.1.5 的 SSH 密码是 `GbUy@912!`，已写入手动部署脚本。”

**全文搜索**：如果查询词是“部署脚本 密码”，BM25 能直接命中“部署脚本”和“密码”，返回这条记录的概率很高。

**语义搜索**：问句“密码是啥”和历史中的“密码是”语义接近，但“上次那个部署脚本”里的“那个”指代模糊，向量模型没办法消解这个指代，结果可能跑偏到另一个提到“脚本”但不含密码的片段。

反过来，如果用户问的是“有没有办法让服务吃内存别那么猛？”，历史里恰好有“JVM 参数调优降低内存占用”。全文搜索因为“吃内存”和“内存占用”没有直接词重合，BM25 可能失分严重，而语义搜索能匹配到。

这就引出核心矛盾：**你需要保证专有名词、实体、命令等精确信息的召回，又希望泛化口语和长尾问题。** 单一方案会有明显盲区。

## 做法：搭建一个混合召回实验

我们用 OpenClaw 的插件机制写了一个 `memory_recall` 工具，背后接两个索引：

1. **全文索引**：Elasticsearch，分词器 `ik_max_word`（中文）+ `standard`，存储原始文本和元数据。
2. **向量索引**：Chroma，嵌入模型 `text-embedding-3-small`（1536 维），分块大小 512 token，重叠 50 token。

实验流程：

1. 录入一个客服 Agent 约 2 个月的对话历史（清洗后 3.2 万条片段）。
2. 设计 60 个查询样本，覆盖“精确实体查询”“口语化提问”“混合指代”三类，人工标记相关片段作为 ground truth。
3. 分别用纯 BM25、纯向量、以及 **混合：BM25 初排 top-20 后再用向量重排（Rerank）**，记录 Recall@5、MRR、平均延迟。

混合召回的核心代码简化如下：

```python
def hybrid_search(query, top_k=5, bm25_candidates=20):
    # 1. BM25 全文初筛
    docs_bm25 = bm25_index.search(query, size=bm25_candidates)
    # 2. 向量相似度精排
    query_vec = embedding_model.encode(query)
    docs_chroma = chroma_index.query(query_vec, n_results=bm25_candidates)
    # 3. 结果融合：Reciprocal Rank Fusion
    fused = rrf(docs_bm25, docs_chroma, k=60)
    return fused[:top_k]
```

RRF 的 `k` 值用来平衡两个信号权重，后面踩坑会说到。

## 结果与踩坑点

**客观指标（部分）**:

| 方法 | 精确查询 Recall@5 | 口语查询 Recall@5 | 平均延迟 |
|------|------------------:|------------------:|---------:|
| BM25 | 0.92 | 0.43 | 12 ms |
| 向量 | 0.41 | 0.87 | 48 ms |
| 混合(RRF) | 0.94 | 0.89 | 63 ms |

混合方案能把两类查询的召回都拉到接近 0.9，但延迟成倍增加。下面是踩过的真实坑：

### 坑1：中文分词让 BM25 失真

`ik_max_word` 会把“数据库密码”切成“数据库”、“数据”、“库”、“密码”。如果用户搜“库密码”，竟然也能命中——看起来是好事，实则引入大量噪声，尤其是当历史里充满“数据库”这个词的时候。解决方式是改为 `ik_smart` 粗分，并对特定实体（比如密码、IP、UUID）使用自定义词典保留完整词。

### 坑2：向量搜索对短文本十分无力

问句“密码”和历史里几十条包含“密码”的片段计算相似度时，“密码”这个 token 在嵌入模型中几乎退化为一个通用符号，区分度极低。实验中发现，对于长度小于 10 个词的查询，纯粹靠向量检索几乎等于随机。我们的补救：当查询长度 ≤ 8 个词时，不再使用向量重排，直接回退到 BM25。

### 坑3：混合融合的权重比想象中敏感得多

RRF 的 `k` 设为 60 只是一个经验起点。不同场景下最优 `k` 可以从 20 到 200 波动。我们后来引入一个简单的自动调节：根据查询中名词密度（实体比例）动态设置向量权重，名词密集时大幅降低向量侧排名贡献，反过来则升高。这虽然不优雅，但工程上很有效。

### 坑4：嵌入模型的更新噩梦

如果换一个嵌入模型，整个向量库需要重建，哪怕只是模型微调权重。我们为此设计了版本号隔离和增量重建策略，避免宕机。这块对持续运行的生产 Agent 尤其重要。

## 可复用建议

根据这次实验和实际部署，我总结几条可以直接拿去用的经验：

- **“全文搜准，语义搜全”，按查询形态分流**：短查询、含专有名词时降低语义依赖；长查询、自然语言逻辑问题时提升语义权重。
- **先全文再语义是最经济的混合方式**：用 BM25 快速缩小候选集，再用向量重排，而不是全量向量检索，能在延迟可控的前提下拿到大部分语义收益。
- **中文场景务必定制词典**：把项目特有的术语（设备名、端口号、接口名、错误码）维护成自定义词典，全文索引的准确度会明显上升。
- **监控两个指标：实体召回率和延迟 P99**。实体丢了用户马上会投诉，延迟高了链路上游会超时，两者都没有妥协空间。
- **不要梦想“一套参数跑全局”**：如果 memory_recall 被多个 Agent 共用，最好提供策略配置干系，允许不同 Agent 选择不同的融合方式。

## 总结

AI 助手的 memory_recall 不是简单的搜索问题，而是“理解意图”和“尊重事实”之间的平衡。全文搜索和语义搜索不是替代关系，而是工程上的互补手段。在以 OpenClaw 这类强调可组合、可插拔的场景里，把召回做成可配置的管线（BM25 → Embedding 重排 + 规则干预），会比一上来就选择某种“高级 RAG 方案”更稳健。

更重要的是，你的索引质量、分词策略、融合权重，需要靠真实日志驱动的查询分析来持续校准，而不是一次性调参。脚踏实地把这一层做扎实，Agent 的长期记忆能力才能真正从“能跑”变成“好用”。
