## 问题背景

团队引入 AI Agent 写 E2E 测试的冲动不难理解：前端迭代快、测试用例跟不上，手写 Playwright/Cypress 脚本太慢，而现代 Agent 已经能操作浏览器，何不直接让它来生成测试？

我们先做了一个小范围实验：给定一个内部后台的 CRUD 页面，让搭载了 Playwright MCP 的 Agent 自己探索，然后输出一份“可运行”的 E2E 测试文件。结果首轮生成的脚本大约 40% 能一次跑通，其余失败原因集中在：

- 选择器不稳定（自动选取了动态 class 或 nth-child）；
- 缺乏对页面状态（loading、空数据、权限）的等待逻辑；
- 操作与断言之间没有合理的时序依赖。

也就是说，Agent 能“看见”页面，却很难凭空理解什么才是可靠的测试。这个问题促使我们放弃“一键生成”的想法，转向用 Agent 协作的方式：人负责制定测试契约，Agent 负责填充执行细节并持续维护。

## 方案思路：人与 Agent 的分工

我们把自动化测试生成拆成三个角色：

1. **人类开发者**：定义测试意图（例如“验证列表页的筛选与重置”）、提供稳定的定位策略（如 `data-testid`）、审查最终脚本。
2. **分析型 Agent**：读取前端代码和页面结构，提取可用的语义选择器，输出测试步骤的骨架。
3. **执行型 Agent**：通过 MCP 浏览器工具实际执行操作、观察结果，生成带有等待与断言的 Playwright 代码。

这一分工让 Agent 不再“盲猜”，而是基于明确契约工作。整个流程依赖的核心能力是：OpenClaw 的任务编排、Playwright MCP 的浏览器控制，以及一个自定义的“选择器策略”指令。

## 具体实现步骤

### 1. 准备环境与工具链

- 安装 Playwright MCP server（官方 `@anthropic/mcp-server-playwright` 或社区版本），并在 OpenClaw 中注册为浏览器工具。
- 为被测应用建立约定：所有可交互元素必须有 `data-testid`，动态列表项使用 `data-testid="row-${id}"` 模式。这一步不是“可选项”，是可靠性的根基。
- 准备一份页面对应的 TypeScript 类型或 OpenAPI schema，帮助 Agent 理解数据模型。

### 2. 定义测试意图（人）

用自然语言描述一个测试场景，并注明必要的定位符和预期行为。例如：

> 场景：筛选订单列表  
> 页面：/orders  
> 元素：筛选下拉 `data-testid="status-filter"`、表格行 `data-testid="order-row"`、重置按钮 `data-testid="reset-btn"`  
> 预期：选择“待发货”后，列表只显示对应记录，重置后恢复全部数据。

不用写具体代码，但必须明确输入、元素和断言。

### 3. 生成测试骨架（分析型 Agent）

分析 Agent 拿到上述意图和项目代码（组件、路由、hooks），它的工作是推测每一步需要用到的选择器和交互逻辑，输出一份结构化的步骤描述，类似：

```
1. 导航到 /orders
2. 等待 data-testid="order-row" 出现
3. 记录当前行数
4. 选择 status-filter 下拉的“待发货”选项
5. 等待列表更新，验证 order-row 数量减少且都包含状态“待发货”
6. 点击 reset-btn
7. 验证行数恢复到原始值
```

这一步本质是将模糊意图转为可操作步骤。我们会提示 Agent 优先使用 `data-testid`，避免任何基于 CSS class、id 或文本内容的选择器。

### 4. 生成可执行脚本（执行型 Agent）

执行 Agent 加载 Playwright MCP，按照步骤实际运行。它会生成带有 `page.waitForSelector`、`expect` 断言的 Playwright 代码。关键优化是：Agent 在每一步操作前自动注入“防御性等待”，并利用 MCP 的 accessibility snapshot 功能检查元素状态，而不是盲目 `click`。

生成的代码会被写回一个 `.spec.ts` 文件，并附带注释标记由 AI 生成的部分，方便将来 diff。

### 5. 执行与反馈闭环

生成的测试会立即通过 CI 运行。如果失败，Agent 读取测试报告和截图，尝试进行自我修复——比如替换选择器或调整等待策略，但只会对标记为 `/* ai-adjustable */` 的代码块进行修改。超过两次尝试仍失败则转为人工介入。

## 踩坑记录

- **选择器陷阱**：即使有 `data-testid`，Agent 仍倾向于用 `text=` 或 `role=` 定位，因为 MCP 工具返回的 snapshot 包含这些信息。解决办法是在系统提示里强制要求选择器格式白名单，遇到违规直接拒绝生成，返回修正提示。
- **状态等待不足**：Agent 生成的脚本经常忽略 debounce 输入、异步选项加载等。我们给执行 Agent 增加了“操作前隐性检查”：任何表单操作后，必须等待对应的网络请求完成或 DOM 稳定（利用 `waitForLoadState('networkidle')` 还不够，需要等待特定的 API 响应）。这需要把路由层面的 API mocking 信息暴露给 Agent。
- **跨用例数据污染**：生成多个测试时，Agent 没意识到 tests 之间共享状态，导致重置逻辑不全。于是我们在生成模板里强制加入 `beforeEach` 清理，并提示每次测试从唯一的种子数据开始。
- **Token 消耗巨大**：分析 Agent 需要阅读大量代码，执行 Agent 需要多轮浏览器交互。成本控制上，我们缓存页面的“选择器映射表”，让 Agent 只需读取一份精简的元数据而非完整源码。

## 可复用建议

- **从第一天就设计定位策略**：没有 `data-testid` 的页面，Agent 几乎不可能写出稳定测试。配合 eslint 插件强制组件暴露 testid，是一个低投入高回报的工程习惯。
- **让 Agent 输出“测试意图”，而非最终代码**：将脚本生成与意图定义解耦，人能清晰审查步骤是否合理，后期也容易手工调整代码。
- **限制 Agent 的修改权限**：只允许修改标记为 AI 生成的代码段，避免覆盖手写逻辑，也便于回滚。
- **把 MCP 当成执行平台，而不是智能体**：不要让 Agent 用通用推理来操作浏览器，而是给它明确的指令和约束。MCP 工具应当被封装成具有单一职责的高阶操作（如 `applyFilter`、`resetForm`），减少 Agent 的自由度，提升可预测性。
- **逐步建立测试知识库**：将已成功运行的测试步骤提炼为模板，供 Agent 复用，而不是每次都从零探索。

## 总结

AI Agent 写 E2E 测试最大的价值不是替代人，而是把机械、重复的浏览器操作和选择器维护工作自动化。人依然是测试设计的决策者：定义意图、制定定位策略、审查异常分支。Agent 的优势体现在将意图快速转化为可执行代码，并在页面变动后低成本地更新测试。

经过约两个月的实践，我们将新功能的 E2E 测试编写时间缩短了约 50%，但初期建立定位规范和分析模板投入了不少精力。这套方案对已有良好测试基础设施的团队更容易落地，如果项目仍处于“无 testid、无稳定选择器”的阶段，建议先把工程规范补上，再引入 Agent。
