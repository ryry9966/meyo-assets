## 背景：自动化任务为什么经常被“多执行一次”

在 OpenClaw 生态里写自动化，不管是 MCP 插件、Agent 决策流程还是定时任务，执行一次不成功就重试是常态。网络抖动、模型调用超时、上游服务限流，都会让同一段逻辑被跑第二遍、第三遍。

如果你用 Agent 触发工具调用（比如通过 MCP 操作外部 API），重试机制更隐蔽：模型可能因为反馈延迟，对同一个意图产生两次工具调用；或者流水线里的多个节点各自触发了相同的副作用操作。结果就是：明明没写 bug，系统却出现了重复创建、重复推送、状态来回跳的问题。

这些问题的本质不是“执行失败了”，而是“执行被重复了，但业务逻辑没守护好边界”。这个边界就叫**幂等性**。

## 问题：缺少幂等保护的实际后果

拿一个常见场景举例：你用 OpenClaw 插件实现「从飞书消息中提取任务，自动在 Linear 建 Issue」。流程大概是监听 webhook → 解析消息 → 调用 Linear API 创建 Issue。

如果 webhook 因为 5xx 被重发，或者解析步骤报错后重试成功，但创建 API 已经被调用过了，Linear 里就会出现两条一模一样的 Issue。更糟糕的是：你没办法简单翻查日志区分哪条是“真正应该创建”的，因为两条都是同一条消息触发的。

另一个典型场景：Agent 调用 MCP server 上的 `send_email` 工具，因为模型输出格式的小波动，同一封邮件被发送了两次。对用户而言，这就是不可接受的生产事故。

上面两个例子都不是代码写错了，而是**缺了一层幂等设计**。

## 做法：工程化的幂等实施路径

在 OpenClaw/Agent/MCP 的上下文中，实施幂等性可以参考下面四步走，每一步都对应一类操作模式。

### 1. 为每个动作定义唯一业务键

不要依赖消息 ID、客户端生成的请求 ID 或随机 UUID，这些要么不可靠，要么不可追溯。正确的做法是：从业务数据中构造一个**确定性唯一键**。

以创建 Linear Issue 为例，可以用 `teamId + title + 解析后的描述前N个字符` 做哈希，生成 `idempotency_key`。这样即使面对完全相同的消息，也能识别出“这是同一个意图”。

代码层面，典型的 MCP 工具实现可以这样：

```ts
const key = sha256(`${teamId}|${title}|${desc.slice(0, 80)}`);
const existing = await db.findIssueByKey(key);
if (existing) return existing;
```

### 2. 创建操作：先查后插，并用数据库唯一约束兜底

“先查后插”在并发场景下会有竞态，所以必须加唯一索引。对于状态类资源，建议使用 `INSERT … ON CONFLICT DO NOTHING`（Postgres）或等价的 upsert 语义，然后回查以确保拿到已存在的记录。

在 MCP 工具中包装第三方 API 调用时，先把幂等键和资源 ID 的映射落到本地数据库，再发起外部请求，可以避免“外部创建成功但本地没记下来”的尴尬局面。

### 3. 状态变更操作：使用 compare-and-swap（乐观锁）

很多自动化任务会更新资源状态，比如“标记为已处理”、“切换到下一阶段”。这时候要用前置条件保护，例如：

```sql
UPDATE tasks SET status = 'done'
WHERE id = $1 AND status = 'pending';
```

如果受影响行数为 0，说明状态已被其他流程改过，直接返回成功即可。Agent 多次触发同一个状态变更时，这种判断比依赖锁更轻量，也更易调试。

### 4. 利用外部 API 的幂等键特性

如果你调用的第三方服务支持 `Idempotency-Key` 头（例如 Stripe、OpenAI API、部分内部 RPC），一定要用上。即使对方 API 调用超时，你使用相同的 key 重试也是安全的。

对于不支持幂等键的 API，可以在 MCP 插件层做一层薄封装：先写日志表（key + 请求体摘要 + 响应），再实际调用，并在调用前检查是否已有成功记录。

## 踩坑点：这些细节最容易翻车

- **用时间戳当幂等键**：时钟漂移、不同服务器时差，都会导致同一个事件产生不同的键。
- **唯一约束字段过长**：直接用整个 payload 做唯一索引，在高频场景下会拖垮写入性能。应该用哈希摘要，长度控制在 64 字符内。
- **只防创建，不防状态切换**：同一个任务被“处理完成”两次，第二次可能因为状态已是完成态导致报错或回滚，必须设计为“到达终态后再次执行是安全的”。
- **分布式环境下的锁失效**：使用 Redis 锁做幂等时，如果没处理锁续期和锁释放的原子性，锁提前过期会让重复请求穿透。本地数据库唯一约束才是最后的防线。
- **重试导致幂等键冲突的新请求**：如果业务确实要创建两个内容相似的资源，幂等键会误伤。这时需要在键里加入不可逆的递增字段或业务时间窗，或者提供“强制新建”参数给显式调用方。

## 可复用建议

对于 OpenClaw 开发者，可以将幂等性做成一次基建，避免每次写插件都重新发明轮子：

1. 在 MCP 服务端抽取通用的 `withIdempotency(key, action)` 中间件。  
2. 在 Agent 调用链中，给每次工具调用注入 `call_id`，并在工具层记录 `call_id -> result` 映射，重复调用直接返回缓存结果（注意设置合理的过期时间）。  
3. 编写自动化流程时，强制要求每个副作用步骤提供幂等键，不存在则阻断流水线，倒逼设计前置。  
4. 单元测试里务必包含“同一逻辑连续执行两次”的用例，验证最终状态一致。

## 总结

自动化任务的幂等性不是“锦上添花”，而是“一开始就该有的韧性设计”。在 OpenClaw、Agent 和 MCP 这种高度依赖重试和异步触发的体系里，不处理重复执行，就等于把数据的一致性交到网络质量手里。

实现上不复杂：定义确定性业务键，用数据库唯一约束兜底，对状态变更用乐观锁，对创建用“查-插-回查”，再结合外部 API 的幂等能力。把这些模式固化成套件，之后的每一次重试才能安心。
