## 背景

在 OpenClaw 生态里，Agent 已经不再是“聊两句就结束”的玩具。真实项目中，一个 Agent 往往需要持续访问本地文件系统、调用多个 MCP 服务器、维护长期任务状态。裸用系统提示（system prompt）很快就失控：上下文窗口被挤占、指令冲突、工具链误用，甚至出现“Agent 知道自己能干什么，但不知道怎么干”的窘境。

OpenClaw 提供了一种工程化的解决方案：`AGENTS.md`。它是一个位于工作空间根目录的 Markdown 文件，充当 Agent 的《员工手册》——比系统提示更结构化、比代码注释更面向行为约束、比文档更可被 Agent 实时检索和遵循。

这篇帖子不讲泛概念，只讲一个务实的主题：怎么把 `AGENTS.md` 写对、用稳。

## 问题场景

在一个典型的信息采集流水线中，Agent 被要求：

- 从 Notion/Linear 读取任务卡片（通过 MCP）
- 抓取外网文章并清洗正文（通过浏览器插件与自定义工具）
- 将清洗后的文本写入本地 `data/` 目录并触发索引更新

运行几次后，你会看到这些现象：

1. **工具选错**：Agent 为了“图省事”用通用 HTTP 工具去调 Notion API，而不是走已经配好的 Notion MCP。
2. **目录混乱**：文件一会儿写到 `./output`，一会儿写到 `./data/raw`，因为提示里某个边界条件没覆盖。
3. **忘记约束**：凌晨跑的任务突然开始调用需人工审批的写库操作，因为系统提示里那段约束被自然压缩到上下文后部，不再生效。
4. **排查困难**：出问题时，你只能翻几十轮的对话记录去找 Agent 当时的决策依据。

这些不是模型能力的边界，而是**工作空间使用规范**的缺失。

## 核心做法：把 AGENTS.md 当成给 Agent 的 Onboarding Doc

### 1. 文件位置与加载机制

OpenClaw 在启动会话时会扫描工作空间根目录的 `AGENTS.md`，将其内容注入到 Agent 的工作上下文中。具体行为取决于配置，但默认优先级如下：

- `AGENTS.md` 内容会在系统提示之后、用户消息之前被编入。
- 如果使用多 Agent 编排，父 Agent 会读取自身的 `AGENTS.md`，子 Agent 也可能读取各自子目录下的 `AGENTS.md`（取决于编排策略）。

**关键实践**：不要把所有规则塞进一个文件。遵循“根目录管全局，子目录补局部”的原则。例如：

```
project/
├── AGENTS.md              # 全局工作规范
├── crawler/
│   └── AGENTS.md          # 爬取子任务专用规则
└── data-pipeline/
    └── AGENTS.md          # 数据管道规则
```

### 2. AGENTS.md 的结构设计

避免长散文。Agent 解析 Markdown 结构的能力远强于理解自然语言的隐性逻辑。推荐固定分节：

```markdown
# Workspace Manual

## 1. Mission & Scope
- 本工作空间的核心任务：...
- 不在本空间执行的操作：...

## 2. Toolchain Rules
- 可用工具列表及调用优先级
- 何时禁止使用通用工具代替专用 MCP
- 文件系统写入目录白名单与命名规范

## 3. Workflow Patterns
- 标准任务执行序列（Step 1/2/3）
- 异常分支处理（如网络超时 → 退避重试，不可直接放弃）

## 4. Constraints
- 禁止操作：修改 .git 目录、向外部发送未脱敏数据等
- 资源限制：单次读取大小上限、并行请求数
- 时间与状态持久化规则

## 5. Logging & Artifact Convention
- 日志输出路径：./logs/
- 中间产物命名：task-{id}-step-{n}.json
```

Agent 依赖标题层级来定位规则，所以**不要用加粗段落代替 H2/H3**。

### 3. 让规则“可验证”

模糊规则对 Agent 几乎没有约束力，需要做到：

- 目录白名单用绝对路径列表，而不是“写到合适的目录”。
- 工具选择规则写成：“当数据源为 Notion 时，**必须**使用 `notion-mcp` 的 `search` 接口，**禁止**降级为 `http-client`”。
- 失败重试规则给出具体参数：“最多重试 3 次，指数退避，初始等待 1s”。

OpenClaw 的 MCP 协议已经提供了工具描述，但你的 `AGENTS.md` 提供的是**工作空间本地的策略**——这是模型无法从工具描述推导的。

## 踩坑记录

### 坑 1：规则冲突导致 Agent 行为摇摆

如果你在系统提示里写了“优先使用本地缓存”，而在 `AGENTS.md` 里写了“始终从数据源实时获取”，Agent 会在这两者间反复横跳。**解决**：把系统提示里的策略全部迁入 `AGENTS.md`，避免双源头维护。系统提示只放角色定义和极少的高层指令。

### 坑 2：超长文件被截断

`AGENTS.md` 过长（超过 4000 token）可能导致模型对后半部分的关注度断崖式下降。解决方案：用**引用式分层**。将详细操作手册放到 `docs/agent-ops.md`，然后在 `AGENTS.md` 中写“详细规格参见 docs/agent-ops.md，仅在需要时检索该文件”。OpenClaw 支持文件检索工具，Agent 可以按需加载，而非全量注入。

### 坑 3：多 Agent 编排时的规则继承混乱

父 Agent 读取根目录的 `AGENTS.md`，但如果子 Agent 的会话初始化没有显式加载子目录的规则，就会套用父规则，导致子任务偏离预期。**解决**：在父 Agent 的编排指令中明确加载子目录 `AGENTS.md` 的步骤，并确保子 Agent 启动时以文件读取命令获得对应手册。

### 坑 4：静态规则无法覆盖动态约束

例如“当天收集的数据文件必须加日期前缀”这种随时间变化的规则，写在静态文件里容易被忽略。可以利用 OpenClaw 的模板变量功能（如果支持）或在任务开始时由脚本动态生成一个临时的 `AGENTS.task.md` 追加到工作上下文。

## 可复用建议

1. **模板化**：为常见自动化场景（信息采集、数据处理、报告生成）分别准备 `AGENTS.md` 模板，通过脚本按需复制进工作目录。
2. **版本控制**：`AGENTS.md` 属于基础设施的一部分，纳入 Git 管理，跟着项目迭代。变更时在 commit message 里标注“changes agent behavior”。
3. **最小化规则集**：每新增一条规则，问自己：“Agent 是否真的会因为没有这条规则而犯错？”删掉 80% 的“看起来有用”的指引。
4. **与 MCP 工具声明对齐**：定期检查 `AGENTS.md` 中的工具名称是否与实际 MCP 提供的工具名一致，避免因版本升级导致工具名变化而规则失效。
5. **加入自检步骤**：在 Workflow 的末尾增加一个“Rule Compliance Check”步骤，让 Agent 主动对照 `AGENTS.md` 检查本轮的输出是否符合目录、命名、工具使用等规则。这能大幅减少静默违规。

## 总结

`AGENTS.md` 不是银弹，也无法把不可靠的模型变成可靠的工程单元。但它是目前 OpenClaw 生态中，**成本最低、可维护性最高**的 Agent 行为治理切口。把工作空间的隐性知识显式地写成结构化的规则手册，让 Agent 像新入职的工程师一样被 onboarding，这是通往复杂自动化流程的必经之路。

真正好用的 `AGENTS.md`，不是写得最全的那份，而是让 Agent 摔跤次数最少的那份。
