## 背景：Agent 为什么需要“安全地”采集网页

在 OpenClaw、MCP 工具链和自动化插件的实践中，Agent 经常需要实时抓取外部网页来补充知识或执行任务。无论是自动化信息聚合，还是结合 Function Calling 完成的“感知-决策”闭环，网页内容采集几乎不可避免。

然而，直接使用原生 `fetch` 或 `axios` 发起请求、或者简单挂载一个 Puppeteer/Playwright 实例，很快就会暴露问题：

- 目标站点触发反爬机制，Agent 采集节点 IP 被短时间封禁；
- Headless 浏览器特征暴露，被注入验证码或直接拒绝服务；
- 采集频率失控，成为事实上的 DDoS 攻击，带来合规风险；
- 采集结果没有校验，Agent 基于错误或污染数据做出决策。

这些问题的代价不仅是采集失败，更可能影响整个 Agent 服务可用性，甚至带来法律隐患。因此，我们需要为 Agent 设计一套**稽核（Audit）优先**的网页采集管线，把安全、合规、可观测性变成基础设施，而不是事后补丁。

## 问题拆解：采集管线的三大挑战

为 Agent 构建安全的采集能力，通常面临三方面挑战：

1. **入口稽核——请求是否合法？**  
   是否尊重 robots.txt？是否携带合理 User-Agent？是否避免对含敏感路径的请求？

2. **行为稽核——行为是否像“正常人”？**  
   Headless 模式是否已被反制？鼠标移动、滚动、等待时间是否自然？是否随机化了浏览器指纹（Canvas、WebGL、字体等）？

3. **出口稽核——结果是否可信？**  
   返回内容是否为反爬页面（如验证码、空白页）？状态码是否异常？是否需要重试或降级为缓存？

## 实践步骤：构建三层稽核管线

以下基于 OpenClaw 生态（如 MCP 插件、浏览器自动化 MCP Server）给出的工程化做法。核心思路是把采集流程拆成三阶段，每阶段都加上可配置的稽核检查点。

### 1. 入口稽核：请求前的安全检查

在真正发起网络请求之前，增加一个轻量级校验模块。该模块作为每一次采集的“守门人”，完成：

- **robots.txt 检查**  
  解析目标域名的 robots.txt 规则，判断请求路径是否被允许。可以使用 Google 开源的 `robotstxt` 库，或直接在插件中集成解析逻辑。对于不允许的路径，拒绝请求并返回结构化错误给 Agent。

- **请求头合规检查**  
  强制使用真实的 User-Agent（例如最新版 Chrome），避免使用 Python-urllib 等默认标识。同时可以设定 Referer 策略（与目标同源或置空），移除不必要的自定义 Header。

- **频率与并发控制**  
  在 Agent 侧实现令牌桶或滑动窗口限流，针对同一域名控制每秒请求数。这个限流状态可以持久化到 Redis，实现跨 Worker 的全局频率管控。

在 OpenClaw 的 MCP 工具中，我们可以把这些逻辑封装为独立的 `validate_entry` 函数，在任何 `web_scrape` 动作执行前必须通过。

### 2. 行为稽核：浏览器指纹与模拟

当需要渲染动态页面时，使用浏览器自动化（Playwright/Puppeteer）成为必要。但普通的 Headless 模式几乎 100% 会被反爬服务识别。

**具体做法：**

- 使用 `puppeteer-extra` 搭配 `puppeteer-extra-plugin-stealth` 去掉自动化痕迹。该插件修补了多种检测点（如 `navigator.webdriver`、`chrome.runtime` 等）。
- 随机化视口尺寸、语言、时区、CPU 核心数等浏览器属性。
- 在页面加载过程中插入模拟人类行为：随机延迟、缓慢滚动、偶尔的鼠标悬停。可由简单的脚本自动生成，参数可配置。
- 代理 IP 池的建设要避免免费代理。推荐使用住宅 IP 代理服务，搭配域名级别的 IP 固定策略（Sticky Session），避免请求间 IP 频繁切换触发的异常检测。

**踩坑点：**  
- 即使加了 stealth 插件，一些高级反爬（如 Cloudflare 5秒盾、JS 挑战）仍可能阻挡。此时需评估是否真的需要实时渲染，或者可以用缓存/CDN 快照替代。  
- Headless 下的 WebGL 指纹可能仍然暴露，必要时可以考虑使用 `--use-gl=swiftshader` 甚至 `xvfb` 虚拟帧缓冲的方案，但成本会升高。

### 3. 出口稽核：响应校验与异常处理

采集完成不是终点，还需要校验返回内容是否有效。Agent 经常拿到空白页或验证码页，却直接当作正文使用，导致下游错误。

**出口稽核模块可以包含：**

- **状态码校验**：非 200/304 时记录并重试（如 429、5xx），对 403/401 等可快速失败并告警。
- **内容模式检查**：检测返回文本是否包含反爬关键词（captcha、Access Denied、cf-browser-verify 等）或空 body。如果匹配，则标记为失败并触发降级策略（例如使用上一次成功的缓存结果）。
- **输出格式标准化**：将 HTML 转成 Markdown 或纯文本，去除脚本、样式，方便 Agent 消费。这一步可以利用 `turndown`、`mozilla/readability` 等库完成。

## 工程化建议与可复用设计

将上述稽核逻辑打包成一个可复用的 MCP 插件或 OpenClaw Tool，对外暴露单一接口 `safe_scrape(url, options)`，内部串联三个阶段的稽核点。配置项以 YAML/JSON 形式维护，允许按域名覆盖规则：

```yaml
domains:
  example.com:
    robotstxt: enforce
    max_qps: 2
    stealth_required: true
    retry_on_block: 1
  another.org:
    robotstxt: warn
    max_qps: 10
    stealth_required: false
```

关键指标（如每次采集的稽核通过率、被屏蔽率、平均响应时间）通过日志/指标暴露出来，接入 Prometheus 或日志告警，尽早发现站点策略变化。

另外，对需要登录或特定 Cookie 的场景，可以将 Cookie 管理也纳入稽核流程，定期监测登录态是否失效，并自动触发刷新。

## 总结

“Web scraping 稽客”不是一套能一次性买到的成品，而是 Agent 工程师必须主动构建的采集安全防线。通过入口、行为、出口三层稽核，配合可配置的规则和可观测性，我们能够在保障采集能力的同时，把对目标站点的冲击和自身被封的风险降到最低。

在 OpenClaw-CN 的自动化实践中，MCP 插件、浏览器自动化引擎已经有了很好的基础，缺失的往往是这条稽核链路的显式设计和工程化。补齐它，你的 Agent 采集才能真正“活”得久、跑得稳。
