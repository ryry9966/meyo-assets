## 为什么需要在本地跑 LLM

如果你正在用 OpenClaw 构建 Agent、编排 MCP 插件或搭建私有自动化流程，迟早会面临一个问题：**推理延迟、API 费用和数据隐私**。托管服务虽然便利，但在高频任务（如逐轮工具调用、代码生成、长文档处理）中，网络抖动和按 Token 计费会迅速放大成本，同时将上下文发送到第三方也可能违反内部安全策略。

本地部署一个质量尚可的开源模型，能让这些自动化链路实现离线运行、零边际成本和全链路可控。本指南聚焦家用硬件（一张消费级显卡或 Apple Silicon）上的实践，目标是让你的本地 LLM 能稳定、可复现地接入 OpenClaw 生态。

## 硬性门槛：你能跑什么模型

先建立现实的性能预期。根据主流 7B-14B 参数的模型，大致对应：

- **4 GB 显存（如 GTX 1650）**：只能跑 Q2_K 量化的 7B，上下文窗口建议 ≤ 4096，生成速度约 5-10 token/s。
- **8 GB 显存（如 RTX 3070）**：可运行 Q4_K_M 量化的 7B 或 8B，上下文可开到 8192，速度 20-30 token/s。
- **12-16 GB 显存**：能跑 Q4 量化的 13B-14B 模型（如 Qwen2.5-14B、Mistral-Nemo），上下文 32k 仍可接受。
- **Apple M 系列（统一内存）**：16 GB 统一内存可跑 7B Q4 模型，32 GB 可尝试 14B 或 MoE 模型，内存带宽决定速度。

对于 Agent 场景，**7B-14B 模型完全够用**，只要选择指令遵循能力强的型号（如 Qwen2.5-7B-Instruct、Mistral-7B-Instruct-v0.3、DeepSeek-R1-Distill-Qwen-7B 等），并通过 Prompt 和工具定义精细控制。

## 选择推理运行时

目前家用场景最实用的两条路线：

**Ollama（推荐新手）**：一键安装、自动管理量化模型、提供 OpenAI 兼容 API。对 Mac/Linux/Windows 均有良好支持，与 OpenClaw 集成只需在配置中填 `http://localhost:11434/v1`。
**llama.cpp**：Ollama 的底层引擎，适合需要极致定制（自定义量化方案、LoRA 热加载、多 GPU 拆分）的高级用户。

对于大概率只需求 “跑一个 API 服务端” 的自动化用户，Ollama 的运维成本最低。本文以 Ollama 为例。

## 部署步骤（可复现）

### 1. 安装并启动服务

```bash
# Linux 下一键安装
curl -fsSL https://ollama.com/install.sh | sh

# 启动服务（默认监听 11434 端口）
ollama serve
```

### 2. 拉取量化模型

根据显存选择模型，务必使用带量化标签的版本。例如在 8 GB 显存设备上：

```bash
ollama pull qwen2.5:7b-instruct-q4_K_M
```

标签解释：`q4_K_M` 是兼顾质量与速度的 4-bit 量化，若显存不足可换 `q3_K_S`。模型可用 `ollama list` 查看。

### 3. 验证 API

```bash
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:7b-instruct-q4_K_M",
    "messages": [{"role":"user","content":"返回一个合法的 JSON，仅包含字段 ok:true"}]
  }'
```

你应该得到类似 `{"choices":[{"message":{"content":"{\"ok\":true}"}}]}` 的响应。这是后续一切集成的基础。

### 4. 接入 OpenClaw

在 OpenClaw 的 `config.yaml` 中，将 LLM 后端指向本地 Ollama：

```yaml
llm:
  provider: "openai_compatible"
  base_url: "http://localhost:11434/v1"
  api_key: "ollama"    # Ollama 不校验 key，仍须填任意非空值
  model: "qwen2.5:7b-instruct-q4_K_M"
```

重启 Agent 后，所有依赖 LLM 的模块（任务规划、工具选择、响应合成）都会走本地模型。你也可以通过 MCP 服务器让外部工具动态调用本地 LLM，只需配置相同的 endpoint。

## 踩坑与排障

### 模型不遵循工具调用格式

直接使用基座 Instruct 模型时，即使模型声称支持 function calling，实现也可能偏差。表现：返回的工具参数是纯文本而非 JSON，或者凭空添加额外字段。解决思路：

- 优先选经过 OpenAI 函数调用对齐的版本（如 `qwen2.5:7b-instruct-fp16` 这类官方 tag）。
- 在 System Prompt 中显式要求 “必须返回严格的 JSON，不附加任何解释”。
- 降低 `temperature`（如 0.1）并温和采样。

### 长上下文内存爆炸

默认上下文长度可能达 32768，但这对显存极其贪婪。以 7B Q4 模型为例，32k 上下文会额外占用 ~2 GB。若触发 OOM，可通过创建自定义 Modelfile 限制上下文：

```
FROM qwen2.5:7b-instruct-q4_K_M
PARAMETER num_ctx 8192
```

然后 `ollama create my-model -f ./Modelfile`，使用新模型名调用。

### 并发与吞吐量

Ollama 默认单请求串行，如果多个 Agent 同时调用会出现排队。可通过环境变量调整并行数：

```bash
OLLAMA_NUM_PARALLEL=4 ollama serve
```

但需注意，将同一张显卡的算力切分给多个并发请求，单请求延迟会显著上升。建议在内网部署多个实例或用 llama.cpp 的 `-np` 进行更细粒度控制。

### API 兼容性细节

虽然 Ollama 宣称兼容 OpenAI API，但流式传输的 `delta` 字段、`finish_reason` 等边缘行为可能与官方有微小差异。若 OpenClaw 报解析错误，可先关闭流式输出（`stream: false`）排查。

## 可复用的配置建议

- **统一命名**：用 `ollama create` 和自定义 Modelfile 给模型起稳定别名（如 `my-agent-llm`），避免升级量化版本后到处改配置。
- **预留监控**：附加一个简易的健康检测脚本，定时查询 `http://localhost:11434/api/tags`，若模型未加载可自动执行 `ollama pull`。
- **缓存系统提示**：OpenAI 兼容 API 中重复使用相同的 `system` 消息会避免重复 kv-cache 计算。Ollama 内部已有优化，但在设计中建议让 Agent 复用相同的系统提示前缀以提升速度。
- **模型备份**：将下载的模型目录（`~/.ollama/models`）纳入备份，避免数 GB 的模型重复下载。

## 总结

在家用电脑上部署一个符合生产需求的本地 LLM，关键在于**正确设定性能边界、选对量化版本、确保 API 兼容性**。对于 OpenClaw 这类自动化引擎，7B 量级、经过函数调用优化的 Instruct 模型能承接 80% 的非超长链式任务，同时让你完全掌控成本与数据。遇到问题多从显存占用、上下文长度和工具调用格式这三个维度排查，多数情况都能快速收敛。

本地 LLM 不是万能银弹，却是构建稳定私有 Agent 系统的坚实基础。希望这份指南能让你的下一个自动化项目不再受限于云 API 的账单和延迟。
