# LLM 输出解析的防御性编程：JSON 与标签格式混合处理实战

## 背景：为什么结构化输出总是“差不多对”

在用 OpenClaw 搭建自动化流程、Agent 工具链时，我们经常会要求 LLM 输出结构化数据，比如 JSON。然而现实是，即使 prompt 里反复强调“只输出 JSON”，模型依然可能：

- 在 JSON 前后加上 Markdown 代码块标记 ```json ... ```
- 在 JSON 对象外包裹自然语言解释
- 输出中包含尾随逗号或单引号
- 将 JSON 塞进 XML 类的自定义标签里，比如 `<result>...</result>`

这些问题在原型阶段尚可手工清洗，但一旦接入自动化管线，脆弱性就会成倍放大。

更麻烦的是，当流程里既有需要纯 JSON 的解析器，又有需要从特定标签中提取数据的 MCP 插件或下游工具时，单一格式假设会直接导致中断。我们需要一种**防御性解析策略**，能鲁棒地处理“JSON + 标签”混合体。

## 问题描述：标签包裹的 JSON 泥潭

考虑一个典型场景：你让 LLM 调用工具，要求它输出：

```json
{
  "tool": "search",
  "query": "OpenClaw debug mode"
}
```

实际拿到的原始字符串却是：

```
根据你的问题，我建议使用搜索工具：

<tool_call>
{
  "tool": "search",
  "query": "OpenClaw debug mode"
}
</tool_call>

这样就可以找到相关文档。
```

此时，简单地 `JSON.parse()` 会直接抛出异常，因为字符串不全是 JSON。使用正则 `/{[\s\S]*}/` 也可能错误地匹配到其他内容。

如果你还同时要求 LLM 输出思考过程（比如放在 `<thinking>` 标签内），那么字符串中可能存在多种标签块，其中只有某些块是需要解析为 JSON 的有效载荷。

## 防御性解析路径

我们的目标不是去猜测 LLM 的输出分布，而是构建一个**健壮、有序、逐步降级**的提取器。以下为在实践中收敛后效果稳定的做法。

### 第 1 步：定义期望结构

首先明确你关心的标签格式。例如，我们期望得到：

- 可选：`<thinking>...</thinking>` 内的推理文本
- 必有：`<tool_call>...</tool_call>` 内的 JSON 载荷

这种设计让 prompt 与解析器契约对齐：你允许模型解释，但要求它把关键数据严格封在标签内。

### 第 2 步：通用块提取器

避免一次性正则匹配整个文档。使用**逐标签提取**的策略：

```ts
function extractTagContent(text: string, tag: string): string | null {
  const openTag = `<${tag}>`;
  const closeTag = `</${tag}>`;

  const start = text.indexOf(openTag);
  if (start === -1) return null;
  
  const contentStart = start + openTag.length;
  const end = text.indexOf(closeTag, contentStart);
  if (end === -1) return null;

  return text.slice(contentStart, end).trim();
}
```

这个简单版本能处理多数情况。但注意：如果文本中标签是嵌套的（例如 `<tool_call>` 内又写了 `<tool_call>`），需要更智能的切割，但 LLM 输出通常不会如此自引用。

### 第 3 步：降级 JSON 解析

拿到标签内容后，开始尝试解析 JSON。注意，标签内部仍可能包含小段自然语言或 Markdown 符号。因此 JSON 解析需要**二次清理**：

1. 如果内容以 ```json 开头并 ``` 结尾，去除首尾代码块标记。
2. 尝试从第一个 `{` 到最后一个 `}` 截取。
3. 对提取片段执行 `JSON.parse()`。

降级流程：

```
标签内容 → 去代码块标记 → 定位首尾花括号 → JSON.parse
```

如果仍失败，可以记录原始内容并抛出结构化错误，方便上游重试或人工介入，而不是让整个管道静默降级。

### 第 4 步：混合提取与契约回退

当标签缺失时（模型没按 prompt 写标签），我们需要回退策略。此时可以从**纯 JSON 提取**入手：

- 尝试匹配 ```json ... ``` 代码块内的 JSON
- 再做全文本的首尾花括号截取
- 如果依然没有，检查是否只是键值对列表，考虑用正则补全为 JSON

关键点是，回退策略要分层，并且**每一步失败时都要保留清理后的字符串，方便调试**。不要默默地吞掉异常。

## 实际踩坑点

### 1. 不完整的标签闭合

模型有时输出 `<tool_call> { ... }` 忘记关闭标签。此时 `extractTagContent` 返回 `null`，进入回退。为了防止这种情况，可以在提取时增加“容忍未闭合标签”的模式：如果未找到闭合标签，则取从 openTag 之后到文本末尾的内容。但这可能会引入噪音，需要根据业务取舍。

### 2. 多重标签与重复键

某些模型会生成两个 `<tool_call>` 块，比如在解释和实际调用中各一个。我们的提取器默认取第一个。建议在 prompt 中明确“有且只有一个”标签，同时在代码中记录找到的块数，超过 1 时发出警告。

### 3. JSON 内部的标签字符

如果 JSON 值含有 `</tool_call>` 字符串，我们的 `indexOf` 会提前截断。解决方法是扫描时检查是否在 JSON 字符串内。对于 LLM 输出，这种概率极低，可暂不处理，但需要在注释中标记风险。

### 4. 换行与空白字符干扰

`indexOf` 不会受空白影响，但有些模型会生成 `< tool_call >`（带空格）。可以在调用标签提取前，用一步轻量正则清理标签两侧的空格：`text.replace(/<\s*(\/?)\s*(tool_call)\s*>/g, '<$1$2>')`。

## 可复用建议

- **契约优先**：在系统 prompt 中将输出格式约定为标签包裹的 JSON，并在代码里严格按该契约提取。
- **分层提取函数**：将标签提取、JSON 清理、JSON 解析拆成独立函数，便于组合与测试。
- **错误信息透传**：解析失败时，除了抛出异常，还附上清理前的原始片段和每一步中间结果，方便远程排障。
- **加入采样日志**：在 Agent 循环中抽样记录 LLM 的原始输出，尤其是在解析成功的边界情况（例如恰好从 Markdown 代码块中提取成功），监控非契约输出的比例。
- **单测覆盖脏数据**：准备 10-20 个真实场景中的“脏输出”作为 fixture，包括缺少标签、标签内嵌套多余字符、JSON 错误但可修复等情况，确保重构时不会引入回归。

## 总结

JSON 与标签的混合处理并不是高深技术，却常常成为自动化工作流的断点。防御性编程的核心不是“信任模型一定会输出完美 JSON”，而是**设计一个健壮的提取-清理-解析流水线，并清晰定义各层回退边界**。在 OpenClaw 这类强调可控性的 Agent 框架下，这种务实的解析策略能够显著减少无意义的运行中断，让你将精力放在流程逻辑本身，而不是和 LLM 的格式幻觉缠斗。
