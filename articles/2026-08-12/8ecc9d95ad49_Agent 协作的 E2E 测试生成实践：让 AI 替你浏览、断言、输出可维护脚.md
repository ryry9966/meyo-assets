# 背景：E2E 测试总在“写完就坏”

端到端（E2E）测试本该是质量兜底的最后一道防线，但在多数项目里，它变成了“写完很久不跑、一跑一堆红”的摆设。问题不在于测试框架本身——Playwright、Cypress 已经足够好用——而在于：

- 界面频繁微调，导致选择器失效；
- 业务流变更后，测试脚本跟不上，人工更新成本高；
- 编写新测试时，需要先反复手动探索页面，再翻译成代码，大量时间花在“把步骤录下来”的体力活上。

团队里通常只有少数人熟练掌握测试框架，测试覆盖的增长速度远赶不上产品迭代。最近半年，我们试着把 OpenClaw 这类 Agent 框架接入 E2E 链路，把“浏览页面、探索元素、生成测试脚本”的流程交给 AI 工具链协作完成，效果比预期中更工程化。这里把这个实践中踩过的坑和可复用的模式记录下来。

# 问题拆解：Agent 能做什么，不能做什么

要务实，先划边界。让 Agent 无监督生成全套 E2E 测试然后直接提交到 CI，现阶段不靠谱。但 **在人类监督下的半自动化流水线** 已经可用：

- **能做**：按自然语言指令完成浏览器操作，观察 DOM，生成 Playwright/Cypress 代码片段，包含合理的选择器和断言；
- **能做**：基于一张截图或一段描述，补充边界操作的步骤（例如等待网络空闲、断言 API 响应后再点击）；
- **不能做**：自己判断业务正确性，尤其涉及金额、库存等断言需要人工确认；
- **风险点**：生成的选择器可能是脆弱的 CSS 路径，必须强制约束使用稳定属性。

我们的目标是：**把“从 0 到 1 的测试草稿”的编写时间压缩 80%，人工只做审核和微调**。

# 做法与步骤

## 1. 准备 Agent 的“手”和“眼”：基于 MCP 的浏览器工具链

OpenClaw 通过 MCP（Model Context Protocol）连接外部工具。要让 Agent 操作浏览器，需要运行一个 Playwright MCP Server（例如 `@anthropic/mcp-server-playwright` 或社区维护的 `playwright-mcp`）。配置方式大致如下（以 OpenClaw 的 MCP 配置片段为例）：

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-playwright"],
      "env": {
        "PLAYWRIGHT_BROWSERS_PATH": "/tmp/playwright-browsers"
      }
    }
  }
}
```

启动 OpenClaw 后，Agent 自动挂载 `browser_navigate`、`browser_click`、`browser_snapshot`、`browser_take_screenshot` 等工具。此时你可以在对话中直接说：“打开 http://localhost:3000/products ，搜索 ‘无线耳机’，进入详情页，点击加入购物车，然后检查购物车图标数字是否变成 1。”

Agent 会逐步执行：导航 -> 快照获取可访问性树 -> 定位搜索框 -> 输入 -> 等待 -> 点击 -> 再次快照做断言。

## 2. 强制生成可维护的选择器

第一次使用时，Agent 默认倾向于生成这样的选择器：

```javascript
page.locator('#root > div > div:nth-child(2) > button')
```

这显然无法维护。因此必须**在系统提示中注入选择器规则**，每次对话生效。我用的模板如下（写在 OpenClaw 的 system prompt 或每次任务的指令前缀）：

> 生成测试代码时，选择器必须遵循以下优先级：
> 1. `data-testid` 属性（如 `[data-testid="add-to-cart"]`）
> 2. 有明确语义的 ARIA 角色（`role="button"` 配合 `name`）
> 3. 文本内容匹配（`getByText` / `getByRole('button', { name: '加入购物车' })`）
> 禁止使用绝对 CSS 路径、`nth-child`、随机 class。若页面上没有合适的 `data-testid`，需要在测试步骤前添加注释提醒开发补充。

这样，Agent 输出的代码会稳定很多。我们甚至让 Agent 在生成测试前，先对页面可访问性树做一次静态分析，建议前端应该补充哪些 `data-testid`，一并用注释写入生成的 spec 文件。

## 3. 从自然语言到可运行的测试文件

典型的单次对话流程：

1. 用户（测试/开发）描述测试场景，例如：“检查用户未登录时访问 /orders 页面是否会重定向到登录页，地址栏包含 `return_url`。”
2. Agent 导航，确认重定向发生，获取当前 URL。
3. Agent 生成测试代码，包含 `expect(page).toHaveURL(/login?return_url=/)` 的断言。代码以 Markdown 代码块返回，附带注释说明每一步意图。
4. 用户审查，若通过则手动粘贴到测试文件中，或通过脚本自动追加。

为了提高产出的一致性，我们维护了一份 **“测试场景指令模板”**，团队成员只需要填空即可发起 Agent 请求：

```
任务：为 [功能模块] 编写 E2E 测试
前置条件：[登录状态/数据准备]
操作步骤：
1. 导航到 [URL]
2. [步骤描述...]
预期：
- URL 应该 [匹配规则]
- 页面应包含 [可见文本/元素]
- API 响应应包含 [预期状态码或字段]
要求：生成 Playwright 测试代码，使用 data-testid 优先，禁止使用固定等待，用 waitForResponse 等待关键 API。
```

## 4. 接入 CI 的半自动管道

目前我们还没有做到 Agent 自动提交测试代码到仓库，而是保持“生成 → 人工确认 → 提交”的循环。但在 CI 中增加了一个辅助 job：当新的 spec 文件提交后，CI 会跑一遍测试，并把失败日志推送到一个固定的 OpenClaw 会话里，让 Agent 给出修复建议（例如“选择器失效，建议使用 getByRole 替换已消失的 CSS 类”）。这个“修复建议”环节已经帮助减少了约 30% 的维护沟通。

# 踩坑点

- **Token 消耗与上下文长度**：`browser_snapshot` 在复杂页面（如大型 Dashboard）可能返回几千行的可访问性树，一下子就塞满上下文。解决方案是要求 Agent 先用 `browser_evaluate` 提取关键片段，或者分区域截图后基于图像分析做点选，再对局部做 snapshot。
- **时序与等待的断言**：Agent 有时会忽略动态加载，生成没有等待的代码。一定要在任务指令里明确要求“等待网络空闲后再断言”，或者要求调用 `page.waitForResponse` 等待特定 API。
- **登录/Cookie 状态管理**：每次 Agent 新建浏览器上下文都是空态，需要专门设计“复用登录状态”流程。我们通过 Playwright 的 `storageState` 预注入，让 Agent 使用已认证的 context，而不是每次都走登录。
- **Agent 迷路**：如果页面有弹窗、多个 iframe，Agent 可能卡住。这时需要人工介入，用简短的指令纠正：“关闭弹窗，再继续”，它对阶段性指令的响应很敏捷。

# 可复用建议

1. **抽取出通用的选择器策略提示**，作为团队共享的 OpenClaw 配置文件片段，避免每次重复描述。
2. **用“测试场景模板”统一输入**，降低对提问者描述能力的要求，同时提高输出格式的一致性。
3. **将生成代码与 Page Object 模式结合**：在提示中要求 Agent 生成的不是裸 Playwright 操作，而是面向 Page Object 的类方法（如 `loginPage.submit()`）。这样生成的代码更容易直接融合进现有测试架构。
4. **建立一个“AI 辅助测试”技能卡**：把用过的有效 Prompts 沉淀到内部文档，例如“如何让 Agent 自动生成 API 拦截与 mock”、“如何处理列表分页的滚动加载”。

# 总结

让 Agent 协作写 E2E 测试，关键不在于 AI 有多聪明，而在于你给它划定了多少边界：用严格的指令约束选择器策略、等待逻辑、代码结构，它就能输出工程上可用的草稿。对已有的存量测试，它也能辅助定位失败原因和建议修复方案。我们目前在一个 200+ 测试用例的中型项目中，大约 40% 的新用例初稿由 Agent 生成，人工修改量平均在 10 行以内。

在可预见的未来，AI 不会取代测试工程师，但“手工编写重复操作代码”这件事确实可以被大幅削减。把精力释放出来，去设计更好的测试策略，这才是 Agent 协作的真正价值。
