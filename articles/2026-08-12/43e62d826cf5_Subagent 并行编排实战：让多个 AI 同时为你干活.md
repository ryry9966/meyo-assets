## 背景：为什么单个 Agent 不够用

当 Agent 被投入生产环境，你很快会发现，很多真实任务根本不适合“单线程思考”。收集 10 个数据源做交叉分析、同时审查多个仓库的代码变更、批量处理上百条用户反馈——串行执行既是效率灾难，也会让上下文长度膨胀到模型无法消化的地步。

在 OpenClaw 生态里，Agent 已经具备调用工具、读写文件、触发 MCP 服务的能力。但如果把所有这些操作塞进同一个 agent 会话，你会发现三个痛点：

- **上下文爆炸**：每处理一个子任务，输入输出都被塞进历史，很快超出 token 预算。
- **阻塞等待**：A 步骤做完才能开始 B，但 B 可能完全不依赖 A 的输出。
- **错误雪崩**：串行链条里一步出错，后半段全部白跑。

因此，我们需要一种**并行 Subagent 编排**方式，让主 Agent 能够创建多个独立子 agent，同时处理互不依赖的子任务，最后汇总结果。

## 问题：并行容易，控得住难

Subagent 编排的本质是并发编程，只是执行单元变成了 LLM 调用。主要挑战：

1. **并发控制**：API 有速率限制，成本也随并发数线性增长，不能无脑全并行。
2. **上下文隔离**：如果把整个主会话上下文传给 subagent，token 浪费严重，且容易产生幻觉。
3. **部分失败处理**：三个子任务成功、一个失败，汇总逻辑如何定义？
4. **结果合并**：子 agent 返回格式不统一，汇总 agent 容易混淆信息。

在 OpenClaw 中，这些可以通过 `subagent` 工具或自定义 task 封装来解决，但需要明确的工程化设计。

## 做法：以多源报告生成为例

假设我们要写一份行业竞品分析报告，需要同时获取三份财报信息、五条新闻摘要、两个用户评论区的情绪分析。以下是基于 OpenClaw 的实践步骤。

### 1. 任务拆解与 schema 定义
主 Agent 首先分析任务，拆出可并行的子任务，每个子任务有清晰的输入、期望输出 schema。

```
子任务示例：
- 任务 ID: fetch_financials
- 描述: 提取 A 公司 Q2 财报的关键数据
- 输入: { "url": "https://...", "company": "A" }
- 期望输出: { "summary": "...", "key_metrics": {...} }
```

这一步不是让 LLM 自由发挥，而是在主 Agent 的 system prompt 中规定好输出结构（例如 JSON 数组），方便程序化调度。

### 2. 并行调度 Subagent
使用 OpenClaw 的 `task` 工具（可以指定 `async: true`）或更低层的 API 调用，以受控并发数提交子任务。通常我们会封装一个调度器：

```
max_concurrency = 3
queue = [task1, task2, task3, ...]
results = []

for batch in chunk(queue, max_concurrency):
    batch_results = await run_subagents(batch)  # 并行运行
    results.extend(batch_results)
```

每个 subagent 收到的是**精简上下文**：仅包含该子任务的描述、输入 schema、必要环境信息，不携带无关历史。这通过创建新 conversation 或使用短 system prompt 实现。

### 3. 结果校验与重试
子 agent 返回后，主 Agent 可以快速校验输出是否符合 schema。如果缺失关键字段或出现明显 Hallucination，触发重试（最多 2 次），同时记录失败原因。

### 4. 汇总与报告生成
所有子结果收集完毕后，交给一个专门的汇总 subagent（或主 Agent 自己），按照预先定义的报告模板合并结果。此时汇总 agent 看到的是结构化数据，而非冗长的原始对话。

## 踩坑点

### 坑 1：忘记限制并发，触发速率限制
OpenAPI 的速率限制与你的付费 tier 相关。一个小经验：先以并发 2 跑通，逐步调高到 3~5，中途发现 429 错误立即加 backoff 或退避。不要一上来就全量并行。

### 坑 2：把主会话全部灌入 Subagent
很多人在实现时图省事，直接把主 agent 的全量上下文作为子 agent 的上下文。结果子 agent 在前几千 token 的历史里“迷路”，忘记自己要干什么。务必为子 agent 设计独立、简短的 prompt。

### 坑 3：汇总 Agent 拿到的是“黑箱”
如果子 agent 的输出格式随意（比如直接给了一长段文本），汇总 agent 很难正确提取和比较信息。解决方案就是前面提到的 schema 化输出，甚至可以要求子 agent 以 YAML 或 Markdown 表格返回数据。

### 坑 4：部分失败导致汇总阻塞
并行任务中的某个子 agent 可能因为网络、API 错误、解析失败而返回 null 或不完整结果。汇总逻辑必须能处理缺失项，比如在报告中标注“数据不可用”，而不是直接报错停止。

## 可复用建议

- **封装通用 Subagent 调度器**：抽象出一个 `parallelMap` 函数，接受任务列表、并发数、校验函数。一旦调通，后续所有类似需求直接复用。
- **利用 MCP 工具做数据获取**：如果子任务都是访问同一类服务（如网页抓取、数据库查询），可以预装对应的 MCP 工具到 subagent 配置中，减少 prompt 长度。
- **输出结构化规范**：强制子 agent 返回 JSON，并定义 schema（可以用 TypeScript 接口作为 prompt 描述），在主 agent 汇总前先通过代码校验，降低 LLM 出错概率。
- **缓存幂等任务结果**：如果子任务是带参数的数据抓取，可以对输入做哈希，将结果缓存到文件或 KV 存储，避免重复调用浪费 token。
- **监控与成本控制**：每次并行任务结束后，记录各个 subagent 的 token 消耗和耗时，观察是否存在个别子任务消耗异常，及时调整子 prompt 或拆分粒度。

## 总结

Subagent 并行编排不是银弹，但对于符合“多独立子任务”特征的工作流，它能成倍降低端到端时间，同时把上下文管理变得更干净。在 OpenClaw 的 Agent 框架下，你只需要组合好 `task` 工具、合理的上下文隔离和简单的并发控制逻辑，就可以让多个 AI 同时为你做事，而不会变成一团乱麻。

关键点概括：

- 拆任务、定 schema 是并行化的“地基”；
- 子 agent 的上下文越短越准；
- 受控并发 + 错误处理 + 结构化输出，一个都不能少。

当你下一次面对需要同时处理十几个数据源的 Agent 任务时，不妨试试把活儿分出去，让子 agent 们并行冲。
