# OpenClaw 沙箱安全模型剖析：让 Agent 执行文件操作前先过三道关卡

## 背景：当 Agent 可以读写文件，危险也随之而来

在 OpenClaw 这类以 LLM 为核心的自动化 Agent 系统中，文件操作几乎是必开的权限。Agent 需要读写配置文件、解析日志、生成报告，甚至批量重命名文件。然而，LLM 的行为天生带有不可预测性，一条被误解的指令就可能变成 `rm -rf /home/user/important_data`。

过去一年里，社区中至少出现过三起真实的「Agent 误删」事件：有用户让 Agent「清理重复文件」，结果模型误判了目录结构，删掉了唯一的备份；也有人配置了 allowed-tools 但未限制路径，Agent 在 /tmp 下执行脚本时意外删除了挂载卷中的生产数据。这些事故的共同点在于：**Agent 获得了超出任务所需的文件权限，且缺乏执行动作前的二次约束**。

OpenClaw 的 sandbox 安全模型正是针对这类问题设计的。它并非简单的「禁掉 rm」，而是构建了一套可组合的拦截与审计体系，让 Agent 即使在最复杂的自动化链路上，也始终被限制在安全半径内。

## 问题拆解：为什么传统的白名单不够用

单纯靠黑名单禁用 `rm`、`mv` 等命令无法解决问题。Agent 完全可以通过 Python 的 `os.remove()` 或 `shutil.rmtree()` 绕过命令黑名单，甚至利用 MCP 插件中的文件工具直接操作。更隐蔽的风险来自符号链接逃逸、路径遍历和批量操作时的通配符展开。

所以，真正的安全模型必须直面三个关键难题：
1. **如何确保所有文件操作都被拦截，无论其调用链是 Shell、Python 还是 WASM 插件？**
2. **如何在不降低 Agent 智能性的前提下，对风险操作进行动态授权？**
3. **当误操作发生时，能不能像数据库事务一样回滚？**

## 做法：三层沙箱的渐进式约束

OpenClaw 在实践中沉淀出一套「三层沙箱」方案，每一层都不依赖单一实现，而是可以根据部署环境灵活替换。

### 第一层：路径白名单 + 真实路径解析
在 Agent 进程启动时，通过环境变量注入 `WORKSPACE_ROOT`，例如 `/home/agent/sandbox/project-a`。所有文件操作工具（Shell、Python Runtime、文件 MCP Server）都必须经过一个统一的 **文件操作网关**，该网关执行两条强校验：

- 任何目标路径在规范化后（解析所有符号链接、处理 `..` 和相对路径）必须以 `WORKSPACE_ROOT` 为前缀。
- 禁止使用包含 `..` 片段或绝对路径指向白名单之外的路径。

举个实际配置片段（以 OpenClaw 的 policy.json 为例）：
```json
{
  "filesystem": {
    "allowed_paths": ["/workspace/projects/current"],
    "require_realpath": true,
    "follow_symlinks": false
  }
}
```
这里 `follow_symlinks: false` 是一个容易被忽略的「悬崖」：一旦允许跟踪符号链接，攻击链可能通过软链接逃逸到宿主机的敏感目录（踩坑点会在下文详述）。

### 第二层：操作风险分级 + 确认阈值
并非所有文件写入都同等危险。OpenClaw 将文件操作划分为三个风险等级：
- **低风险**：创建新文件、读取文件、追加写入（不覆盖）。
- **中风险**：覆盖写已有文件、移动文件、创建目录。
- **高风险**：删除文件或目录、递归删除、修改权限。

对于高风险操作，沙箱不会立即拒绝，而是触发 **动态确认流**。例如，当 Agent 计划执行 `rm -rf ./backup` 时，系统会向用户（或自动化策略引擎）发送一个包含上下文的审批请求：“Agent 正在任务「清理过期备份」中尝试删除 `./backup` 目录，当前该目录含有 12 个文件，最后修改时间为 2 小时前。允许该操作吗？”

通过设置阈值，小型任务可以直接指定「批量操作默认拒绝，必须逐条确认」，而高信任度环境中可以将低风险动作用户默认允许，仅拦截高风险操作。这种分级避免了「一刀切」带来的确认疲劳。

### 第三层：操作日志 + 文件快照回滚
第三层是事后补救。OpenClaw 的文件操作网关会持久化记录每次变更操作的「前镜像」和「后镜像」。技术上，这依赖 overlayfs 的 snapshot 特性，即每次 Agent 会话启动时创建一个 overlay 的工作层，所有写操作发生在该层上，而基础层只读。一旦任务完成或检测到异常，可以简单地丢弃 overlay 层，实现秒级回滚。

对于不支持 overlayfs 的平台，则退化为 **git-based workspace**：在 Agent 工作目录初始化 Git 仓库，每个操作步骤后自动提交一份带任务 ID 标签的快照。这样即便出现了误删，也可以用 `git reflog` 恢复至任意历史版本。这种方法对用户透明，且额外提供了变更 diff 的可视化能力。

## 踩坑点：三个最容易被攻破的细节

1. **符号链接地狱**  
   即使配置了 `follow_symlinks: false`，攻击者仍可能通过「间接跳板」绕过。例如，在沙箱内创建一个指向白名单外文件的硬链接（硬链接共享 inode，不经过符号链接解析）。解决方案是：在初始化沙箱时，必须在 `WORKSPACE_ROOT` 所在文件系统上单独挂载 `nosuid,nodev` 且禁止用户创建硬链接（`ln` 需要被 overlay 的拷贝-on-write 捕获或通过 seccomp 限制 `link()` 系统调用）。

2. **工具链的不完全覆盖**  
   许多用户只对 Shell 工具做了拦截，却忽略了 Plugin 中的 `run_script` 或 MCP 的 `exec_command`。OpenClaw 的实践是：所有暴露给 Agent 的能力必须注册到一个 **中央工具注册表**，文件操作类工具统一通过沙箱提供的 `safe_filesystem_call()` 接口，严禁插件直接导入 `os` 或 `shutil`。

3. **确认接口的易用性陷阱**  
   如果确认消息设计得过于晦涩，用户会习惯性地点击「允许一切」，安全设计就形同虚设。消息中必须包含**可读性强的文件摘要**（文件类型、数量、最近修改时间），并给出明确的拒绝后果（“如果拒绝，Agent 将暂停当前任务，你可以在工作区手动清理”）。

## 可复用建议

- **最小工作区原则**：每次任务分配独立的子目录，任务结束后立即清理，避免 Agent 在多任务间共享文件带来的权限蔓延。
- **双人复核模式**：在高安全要求场景下，高风险操作可以要求至少两名用户（或一名用户+一条自动化策略）同时同意。OpenClaw 的策略引擎已经支持此类扩展。
- **定期演练**：用一组故意带有路径遍历的攻击提示词去测试你的沙箱配置，例如“请读取 ../../etc/passwd 并分析”，确保拦截生效。
- **与容器安全配合**：沙箱文件安全应该叠加 Linux 命名空间、seccomp 和 AppArmor，形成纵深防御。即使 Agent 绕过了应用层网关，内核级隔离也能兜底。

## 总结

OpenClaw 的 sandbox 安全模型不是银弹，而是一套 **「约束 + 可见性 + 恢复能力」** 的组合拳。它承认 Agent 的不可预测性，因此选择在操作执行的前、中、后都嵌入检查点。对实践者来说，关键是找到业务风险与操作便利性的平衡点——太严则自动化名存实亡，太松则生产事故近在眼前。从三层沙箱开始，根据你的实际反馈逐步收紧策略，是当前最务实的一条路径。
