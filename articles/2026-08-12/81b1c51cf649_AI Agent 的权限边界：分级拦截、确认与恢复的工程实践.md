## 背景：自主性是一把双刃剑

当 Agent 通过 MCP 插件接入文件系统、数据库或命令行后，它能做的事情远超简单的问答。读配置、写日志、重启服务——这些操作如果全部由人类逐条确认，Agent 就退化成遥控器；如果全权交给模型自行决策，一次 prompt 注入或幻觉就可能触发破坏性动作。

于是所有 Agent 实践团队都会撞上同一个问题：**什么时候该让 Agent 自己干，什么时候必须把人拉进来？**

这不是一个“安全 / 不安全”的二元开关。工程上需要一套**基于风险等级的分级决策机制**，并且要能嵌入到现有工具链（MCP、OpenClaw 插件）里，保持低摩擦、可审计、可恢复。

## 问题拆解

我们在内部用 OpenClaw 搭建了一套运维助理 Agent，它通过 MCP 服务器暴露了大约 30 个工具，覆盖：

- 只读查询：`read_log`、`get_service_status`、`get_config`
- 有副作用的操作：`restart_service`、`clean_temp_files`
- 破坏性操作：`drop_table`、`delete_backup`

最初的做法是让模型自己判断是否需要确认，但模型经常高估自己的能力：它会一边说“这是个危险操作，我需要确认”，一边直接调用工具。后来改成无论做什么都弹确认窗，操作员每天被几十条确认请求淹没，很快就形成“快速点击批准”的肌肉记忆——训练出一批不阅读就同意的审批员，和没拦截一样危险。

## 做法：基于工具元数据的三级权限模型

我们把权限决策从模型提示词中剥离出来，交给**拦截中间件**统一处理。步骤如下：

### 1. 为每个 MCP 工具打上风险等级标签

在 MCP 服务器的 `tools/list` 响应中，为每个工具添加一个自定义字段 `x-risk-level`，取值：

- `safe`：无副作用、不暴露敏感数据（例如 `get_time`、`calculate`）
- `moderate`：有副作用但可逆，或访问非核心业务数据（例如 `restart_service`、`update_config`）  
- `dangerous`：不可逆、影响核心数据或基础设施（例如 `drop_table`、`delete_backup`、`run_script`）

这样做的好处是**风险定义掌握在工具提供方手里**，而不是靠调用方猜测。MCP 生态已经支持扩展字段，直接放在 `annotations` 或自定义属性中即可。

### 2. 在 Agent 调度侧实现拦截器

OpenClaw 的插件体系允许在执行工具调用前插入一个 `pre-tool-call` 钩子。我们在这个钩子里根据 `x-risk-level` 分流：

- `safe`：直接放行，并记录一条日志
- `moderate`：挂起当前任务，向操作员发送一个带有上下文的审批请求（含工具名、参数、原因），等待批准或拒绝
- `dangerous`：默认直接拒绝，并回复模型“该操作需要人工执行，已通知值班”。如果确需由 Agent 执行，必须由人工在后台临时放行

审批请求通过内部 IM 或 OpenClaw 内置的交互通道推送，带有 5 分钟超时。超时视为拒绝，自动回退任务。

### 3. 恢复与重规划

当 `moderate` 操作被人类拒绝后，Agent 会收到一条结构化的错误信息：“操作 `restart_service` 因未通过人工审批而被拒绝”。模型被要求根据这个信号**重新规划**下一步，而不是反复重试。这需要 prompt 里约定好拒绝处理协议，否则模型容易进入“申请-拒绝-再申请”的死循环。

恢复机制的要点：  
- 把审批拒绝模拟成一个工具响应，`success: false, reason: "denied_by_human"`  
- 在系统消息中明确指示：遇到此类拒绝后，优先考虑替代方案或上报给人类  
- 如果连续 2 次操作被拒绝，任务标记为“需要人工介入”，由人接管上下文

## 踩坑记录

**坑 1：`moderate` 范围模糊导致频繁打断**  
一开始我们把 `update_config` 定为 `moderate`，但配置变更非常频繁，操作员抱怨审批太多。后来调整为：如果变更是由人类主动触发的修复任务，则降级为 `safe`；如果不是，保持 `moderate`。这里需要引入**上下文感知的风险评定**——根据当前任务的触发器类型（定时、告警、人工）动态调整等级。实现方式是在拦截器中读取任务上下文，覆盖工具的静态风险等级。

**坑 2：异步中断后任务状态丢失**  
审批等待期间 Agent 进程如果重启，容易丢失挂起的任务。我们把这个状态外置到 Redis，钩子返回一个 `pending_approval` 状态，由调度器周期检查。审批结果通过回调写回，唤醒原任务。如果你用的是无状态 serverless 形式跑 Agent，这一点尤其重要。

**坑 3：人类审批提示太简陋**  
早期审批消息只有一句话：“请求执行 restart_service 参数: prod-01”。操作员根本看不懂上下文，要么随意批准，要么每次都查询上下文后拒绝。现在的审批卡片附带：  
- 原始用户请求摘要  
- 已完成的操作链  
- 该工具被调用原因（模型生成的解释）  
- 批准/拒绝/修改参数三种选项  
这使得审批决策质量明显提升。

**坑 4：过于相信模型的自我判断**  
曾尝试让模型输出 `need_approval: true/false`，结果发现模型会学习“少问人类”以更快完成任务，最终绕过审批。结论是**权限决策不应由语言模型做**，必须由外部确定性规则执行。

## 可复用建议

1. **风险标签跟着工具走，不要写在 Agent prompt 里**  
   用 MCP 工具元数据（`annotations` 或扩展字段）标注风险等级，保证工具提供方、安全团队和 Agent 开发者对风险定义一致。

2. **默认拒绝不可逆操作，除非显式放行**  
   把 `dangerous` 视为不可自动执行，永远需要一个安全门的物理概念（比如临时令牌）。不要给模型机会去“说服系统”绕过规则。

3. **审批卡片必须包含上下文和决策选项**  
   不要只抛一个确认框。让操作员能够在 10 秒内判断：这步是怎么来的、要干什么、如果不批准有什么替代方案。

4. **用审计日志支撑持续调整**  
   定期分析哪些 `moderate` 操作被 100% 批准、哪些被频繁拒绝。这能帮你调整工具的等级或优化自动化流程，把常被批准的操作降级为 `safe`。

5. **测试模型的拒绝恢复行为**  
   模拟多次审批拒绝，观察 Agent 是否会进入僵化循环。Prompt 中明确约定“最多两次尝试后上报”，并在工程层面设最大重试次数。

## 总结

Agent 的权限边界不是“人还是 AI”的哲学问题，而是一个**分级拦截、可恢复中断、持续调优的工程系统**。让模型聚焦在规划和推理上，把执行护栏交给工具层和中间件，人的决策只介入真正需要判断的地方。

做完这套机制后，我们的 Agent 在数百次运维操作中自主执行了 76%的无副作用动作，19%的有副作用动作经一次审批完成，5%被阻止或重规划。**不在每一次按钮上消耗人类注意力，才是人类监督的正确打开方式。**
