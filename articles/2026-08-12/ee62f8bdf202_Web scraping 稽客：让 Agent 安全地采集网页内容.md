## 为什么需要稽客

让 Agent 直接执行网页采集任务，很快会撞上现实世界的“软钉子”：某天突然发现目标站只返回 403，或者爬回来的内容全是乱码与验证码。更糟的情况是，无节制地请求会给对方服务带来压力，也可能踩到法律红线。在 OpenClaw 这类 Agent 框架里，如果采集行为完全交给 LLM 决定的工具调用，缺少一层统一的审计与约束，失控几乎是必然的。

**稽客**，我们内部叫做 Scraping Auditor，就是在 Agent 和真实网络之间插入的一层安全护栏。它不替代爬虫本身，而是对所有外发采集请求做准入、速率、合规性检查，同时记录行为日志便于回溯。可以将其理解为一个旁路审计代理，专门教 Agent “什么能做，什么必须停”。

这篇帖子面向已经有 OpenClaw/MCP/Tool 使用经验的开发者，分享我们在项目里落地稽客模式的实践路径。

## 核心设计：一条请求的稽核链条

稽客不是一块宏大的安全平台，而是一组可嵌入的检查点。我们把一次采集请求的生命周期抽象为四个环节，每个环节都是策略注入点：

1. **事前规则解析**：从目标域名的 `robots.txt`、站点声明、自定义策略文件中抽取出许可与禁止规则。
2. **请求准入**：发起 HTTP 请求前，验明路径是否在允许范围内，User-Agent 是否合规，是否携带合法的身份标识。
3. **运行时控制**：动态维护 Token Bucket 或滑动窗口，确保单域、全局请求速率不超标；出现 429 或验证码页面时自动退避、切换出口 IP。
4. **事后校验**：检查响应内容是否被风控页面替换（例如标题出现“请稍候”），并记录采集指纹用于问题排查。

在 OpenClaw 里，我们把稽客封装成一个 **MCP Tool**，暴露 `audit_request` 和 `inspect_response` 两个接口。Agent 计划发起抓取时，会先调用 `audit_request`，拿到经过校验的请求参数（可能被修改或拒绝）。下面是一个简化流程的 Python 示意：

```python
# 稽客 MCP Tool 内部逻辑片段
async def audit_request(url: str, headers: dict, context: dict):
    domain = extract_domain(url)
    rules = await load_rules(domain)  # 含 robots 解析缓存
    path = urlparse(url).path

    if not rules.allow(path):
        raise PolicyViolation("Path disallowed by robots.txt")

    headers["User-Agent"] = select_rotating_ua()
    if context.get("force_proxy"):
        url = wrap_proxy(url, context["proxy_pool"])

    await rate_limiter.acquire(domain)
    return {"url": url, "headers": headers}
```

Agent 实际执行采集的工具（比如一个 `web_fetch`）会使用稽客返回的参数。响应到达后，再经过 `inspect_response` 检查，如果发现疑似风控页面，工具会自动触发缓存刷新或通知 Agent 降级策略。

## 步骤化落地清单

要在你自己的 OpenClaw 项目中引入稽客，可以按下面的顺序推进：

1. **规则源接入**  
   至少支持 `robots.txt` 解析（可用 `urllib.robotparser`），并设置合理缓存（例如 TTL 1 小时）。不要每次都实时拉取，否则稽客本身就成了额外负担。

2. **身份与声明管理**  
   维护一个合规 User-Agent 池，包含常见浏览器标识，并可选择在自定义请求头中加入运营者联系方式（`X-Contact`）以保持透明。

3. **速率与并发控制**  
   我们采用 Redis 实现跨进程的滑动窗口计数，每个域名一个窗口。单域并发上限设得保守一些（初始建议 2～5 req/s），逐步根据目标站响应时间调整。切忌在没有限速的条件下批量抓取。

4. **退避与降级**  
   如果连续遇到 429，触发指数退避后依旧无效，应立即暂停该域名的所有请求一段时间（如 10 分钟），并通知 Agent 任务被挂起，转而处理其他来源的数据。

5. **集成到 OpenClaw**  
   把稽客注册为一个 MCP 工具或插件，在 Agent 的配置里声明：“任何需要访问 web 的工具调用都必须先经过稽客”。可以借助 OpenClaw 的工具前置钩子实现，让 Agent 无感接入。

## 容易踩的坑

- **robots.txt 规则粒度不足**  
  部分网站通过通配符或路径前缀声明禁止，但解析库可能处理不一致。务必针对 `*` 和 `$` 规则做单元测试，避免误伤合法路径。
- **动态页面的“假 200”**  
  现在很多反爬不用 HTTP 状态码，而是返回 200 但内容是一段 JavaScript 挑战或空白模板。`inspect_response` 必须加入正文特征检测（例如 `<title>Just a moment...</title>`），否则 Agent 会拿着无效内容继续生产错误结论。
- **Cookie 污染导致限速失效**  
  使用 Session 保持登录态时，Cookie 可能被风控标记。要为稽客设计独立的会话管理，支持匿名请求和认证请求的切换，避免一个被标记的会话拖垮整个 IP。
- **法律合规不是纯技术问题**  
  采集个人信息、绕过付费墙、违反 ToS 的采集，稽客无法一刀切解决。需要结合法律评审，将禁止域名列表、禁止采集的字段类型（如电子邮件）纳入策略配置，并在事前审批环节加入人工确认。

## 可复用建议

如果你想参考我们的实践，这里有几个起点：

- **策略文件结构**：用 YAML 定义黑白名单、速率、代理策略，Agent 运行时动态加载。这样可以不改代码调整策略，运维友好。
- **稽客 MCP 插件模板**：在 OpenClaw 的插件仓库中，可以基于我们开源的 `scrape-auditor` 骨架代码快速搭建；核心是 `audit_request` 和 `inspect_response` 两个 tool 定义，其余按需扩展。
- **监控与告警**：将每次违规事件（如被拒绝的请求、触发限速）推送到日志通道，并接入现有的告警系统。有了数字证据，后续治理才有的放矢。
- **渐进式提升安全水位**：先以日志记录模式运行稽客，只审计不阻断，分析一个完整业务周期后，再逐步开启阻断能力。这样可以避免一开始就误伤正常业务。

## 总结

把 Agent 的安全采集能力做成一个可插拔的稽客层，不是增加复杂度，而是把工程风险显式地管理起来。当你的 OpenClaw 实例开始每天自动执行上百次抓取时，这层护城河就是防止从“自动化助手”滑向“网络爬虫灾难”的关键。希望这篇实战笔记能帮助你在立项或重构采集管道时，找到一个现实可行的起点。
