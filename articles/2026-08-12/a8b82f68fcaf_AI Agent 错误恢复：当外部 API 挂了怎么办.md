# AI Agent 的错误恢复：当外部 API 挂了怎么办

## 背景：当 Agent 依赖的 API 崩溃，它不该跟着一起死

在 OpenClaw、Agent 框架、MCP 服务等场景里，我们的 Agent 往往需要调用外部 API：搜索、GPT 视觉、翻译、天气、数据库查询……这些调用链越长，脆弱性越高。一个下游 API 超时或返回 500，如果没有处理，Agent 可能直接抛出异常、中断任务、无限重试耗尽 token，或者在对话里给用户一句“抱歉，我无法完成”。

更常见的问题是：**开发者往往在“理想网络”下设计和测试**，上线后才遇到间歇性故障、限流、第三方 SLA 跳水。Agent 的错误恢复不能只靠 try-catch，它需要策略层、超时控制、降级路径和上下文保护。

这篇文章基于我们在 OpenClaw 社区内实践的经验，梳理一套 Agent 调用外部 API 时的容错与恢复方案。如果你正在维护 MCP 插件、OpenClaw 任务流水线，或任何会调用外部服务的 Agent，这些内容应该是可直接落地的。

## 问题场景

先看一个典型例子：一个资料整理 Agent，使用 MCP server 调用某个搜索 API，然后对结果做摘要。某天搜索 API 开始返回 503，Agent 的行为可能是：

- 重试 3 次，每次等 10 秒，整体任务延迟 30 秒后依然失败，整个整理任务丢失。
- 或者未设置超时，线程挂起，直到上层 scheduler 杀进程。
- 或者 API 返回了半截 HTML 错误页面（而不是 JSON），Agent 解析器崩溃，连同前面已经搜集的信息一起丢了。

这些都不应该是 Agent 的默认行为。我们需要的是：**及时失败、安全降级、可恢复的上下文保存**。

## 做法与步骤

### 1. 为所有外部调用建立超时与熔断器

在 OpenClaw 的插件或工具定义里，不要相信默认的超时设置。

```yaml
# OpenClaw 工具配置示例（伪代码）
tools:
  - name: search_api
    type: http
    endpoint: https://api.example.com/search
    timeout: 8s            # 单次调用超时
    retry: 2               # 最多重试次数
    circuit_breaker:
      failure_threshold: 5
      cooldown_seconds: 30
```

熔断器逻辑：如果 1 分钟内该工具连续失败 5 次，OpenClaw 将跳过该工具 30 秒，直接走降级路径。这避免雪崩效应。

**踩坑点**：很多开发者只在 HTTP 层设超时，忘记 Agent 的 Prompt 本身也是调用（LLM API）。如果你的 Agent 依赖的模型也在云端，同样需要超时、重试和降级 prompt。

### 2. 错误分类与响应策略

不要对所有异常一视同仁。把错误分为三类：

- **可重试**：网络瞬时抖动、限流 429（带 Retry-After）
- **不可重试但可降级**：API 返回空结果、权限错误、参数错误
- **致命错误**：认证失效、响应格式完全损坏

在你的工具封装函数中，显式抛出带有错误码的自定义异常，让 Agent 运行时据此决策。比如在 MCP 工具实现中：

```python
class UpstreamError(Exception):
    def __init__(self, message, recoverable: bool, retry_after: int = 0):
        ...
```

Agent 运行时可以根据 `recoverable` 决定是否重试，并把 `retry_after` 信息传递给调度器。

### 3. 为 Agent 构建“中断-恢复”上下文

这是最容易被忽略的一点。Agent 执行任务时往往有累积的中间状态（已收集的网页、已生成的草稿）。如果外部调用失败导致整个任务重启，前面的工作全部浪费。

我们的做法是：在 OpenClaw 的任务定义中引入 `checkpoint`。在调用风险较高的工具前，自动保存会话状态到 Redis 或本地文件。

```yaml
steps:
  - use: search_api
    checkpoint: true
  - use: summarizer
```

如果 `search_api` 失败并决定降级或终止，恢复时可从最近的 checkpoint 继续，而不是从零开始。对于长链路 Agent，这是关键的生产特性。

**踩坑点**：checkpoint 不要保存太大的二进制对象。只保存引用索引或状态机位置。如果要保存对话历史，考虑只保存最近 N 轮，避免 token 浪费。

### 4. 降级路径设计

当 API 不可用，Agent 应有一条 fallback 路线，让任务还能部分完成。

举个例子，如果实时搜索 API 挂了，可以：

- 回退到本地缓存的搜索结果（可能是 1 小时前的）
- 换用另一个搜索源（哪怕质量略低）
- 生成“部分结果”，并告知用户“部分数据可能不是最新的”

在 OpenClaw 工具定义中明确声明 `fallback_tool`，这样编排引擎可自动切换。

### 5. 可观测性与事后回溯

你需要知道 Agent 在哪里摔倒了。每次外部调用失败，记录结构化日志，包含：工具名、错误类型、HTTP 状态码、耗时、重试次数、是否触发降级。用 OpenTelemetry 或简单的 JSON 日志都可以。

设置告警：当某个外部工具的错误率超过阈值（例如 5 分钟内 10%），发通知，而不是等用户来抱怨。

## 可复用建议

- **把外部调用当作不可靠依赖**：任何工具都可能挂，Agent 默认应假设它会挂。
- **将重试逻辑放在 Agent 运行时层，而不是业务逻辑里**：不要在 prompt 里让 LLM 自己决定“要不要再试一次”，那样消耗 Token 且不可控。
- **设置全局最大执行时间**：Agent 任务总时间需要上限，防止降级路径也拥堵。
- **对“空结果”也要有处理**：API 返回 200 但内容为空，Agent 应该知道这是正常结果，而不是错误，避免进入误重试。

## 总结

AI Agent 的错误恢复不是靠加几行 try-catch 就能解决的。它需要在架构上分层：超时熔断器、错误分类、checkpoint、降级工具链和可观测性。这些组件能让你的 Agent 在面对混乱的外部世界时，既不会无谓死掉，也不会把异常暴露成糟糕的 UX。

如果你正在使用 OpenClaw 构建复杂的自动化流水线，尽快为你的每个 MCP 工具加上这些机制——在生产环境中，外部 API 挂掉不是“如果”的问题，而是“什么时候”的问题。
