## 背景：Agent 为什么会卡在 API 这一环

在 OpenClaw 社区，很多同学用 Agent 做了自动化助手、内部工具集成、数据处理管道。初期通过系统提示词或少量工具函数就能跑起来，但一旦需要查询第三方天气接口、调用内部 Jira API、或者通过 REST 触发某个流水线，问题就集中爆发：鉴权写死在代码里、接口返回的 HTML 报错直接塞给了 LLM、一次对话触发了数百次无意义的轮询调用……

本质上，Agent 调用外部 API 不像写脚本那样只管发请求收响应这么简单，它还涉及 **工具描述的准确性**、**异常时模型的决策行为** 和 **调用链路的可观测性**。在 OpenClaw 生态中，有两种主流做法可以让 Agent 与外部 API 握手：通过 **Function Calling** 直接定义工具，或者将 API 封装成 **MCP 服务** 再挂载给 Agent。下面我会以工程化视角把两条路径都走一遍，并给出可复用的踩坑经验。

## 问题拆解：为什么原生 HTTP 调用不适合直接喂给 Agent

先明确几个常见痛点：

1. **鉴权泄露与硬编码**  
   开发者图省事把 API Key 写在工具函数的字符串里，Agent 在流式输出中可能通过推理把这些信息吐出来，甚至被前端日志记录。

2. **响应格式混乱**  
   API 返回 XML、空白、错误页的 HTML，LLM 却试图解析并当成事实使用，造成幻觉扩散。

3. **重试与限流缺失**  
   没有退避策略，一次对话模型反复重试同一个参数，打到服务商返回 429，工具调用失败后 Agent 可能换上更差的参数继续试探。

4. **工具描述与模型意图不匹配**  
   描述写得太模糊，LLM 在不需要调用的时候也去调；或者描述太严格，该调用时却选择凭空回答。

这些问题的根因在于：**Agent 的工具调用表面上是“模型输出一个函数名和参数”，但本质上是信任链传递——模型信任工具描述，工具信任外部服务，外部服务返回数据后又要被模型解读。** 这个链条里任何一环没处理好，最终结果就不可靠。

## 做法与步骤

### 方案 A：在 OpenClaw 工具函数中封装 HTTP 调用

如果你只需要对接 1～2 个外部 API，直接在 OpenClaw 的 Python 工具定义中完成 HTTP 请求是最简单的方式。

**步骤：**

1. **定义清晰的工具 Schema**  
   用 JSON Schema 描述函数名、参数、参数类型和描述。一定要写明“何时应该使用该工具”，不要只写参数说明。

2. **实现安全调用层**  
   用 `httpx` 或 `aiohttp`，超时设 10s 以内。API Key 通过 `os.getenv` 读取，绝不硬编码。封装一个 `_call_api(endpoint, params)` 函数，内部处理状态码、JSON 解析、异常捕获。

3. **统一返回结构**  
   不论成功还是失败，工具返回给 Agent 的字符串应该是结构化摘要。例如成功时返回 JSON 中关键字段的人类可读描述；失败时返回 `"查询失败：服务返回 500，请稍后重试并告知用户"`，而不是直接把 traceback 交给模型。

4. **在 OpenClaw 中注册工具并测试**  
   将函数对象加入 Agent 的工具列表，先用 `dry_run` 或手动构造消息测试工具选择是否准确。尤其是要测“模型在不该调用时是否忍住没调用”。

### 方案 B：用 MCP Server 做一层代理

如果需要多个 Agent 共享同一组 API 能力，或者要隔离运行环境（比如公司内网的 API 不能从公网 Agent 直接访问），MCP 是更工程化的选择。

**步骤：**

1. **搭建一个轻量 MCP Server**  
   基于 `mcp` 或 `fastmcp`，暴露一个 `query_internal_api` 工具。工具内部做鉴权、限流、结果缓存。

2. **工具描述面向 Agent 优化**  
   和方案 A 一样，清晰告知工具用途，必要时在描述中加入正确的调用示例。

3. **在 OpenClaw 中配置 MCP 连接**  
   通过 JSON 配置或环境变量指向你的 MCP Server 地址，Agent 启动时自动加载工具列表。

4. **链路追踪**  
   在 MCP 层记录每个工具调用的耗时、参数和返回摘要，方便回溯模型是不是传错了参数。

## 踩坑记录

下面是我们在帮助几个社区同学联调时总结的高频坑，希望能帮你少花一两天调无头案件。

- **异常信息直接透传导致模型“学到”错误知识**  
  某同学的工具函数在 API 超时时返回了 Python 的 `TimeoutError` 堆栈，模型在之后的对话里总是“建议检查网络配置并把超时调整到 30s”，完全脱离了真实问题。正确做法是在工具内部 catch 所有异常，返回对用户友好的错误描述。

- **没有区分“空结果”和“查询失败”**  
  API 返回 `{"data": []}` 时，工具应该明确告诉模型“查询成功但无数据”，而不是直接返回空字符串。否则模型可能误判为调用失败并重复调用。

- **第三方 API 内容太长，超出上下文窗口**  
  一个 API 返回了 8000 tokens 的文档全文，Agent 直接报错 `context length exceeded`。解决方案是在工具函数中根据配置的 `max_tokens` 对结果做智能截断，保留最相关片段。

- **速率限制被忽略**  
  如果对接的是有 QPS 限制的内部 API，务必在工具层实现简单的令牌桶或退避重试，否则对话过程中一次误触就可能封 IP。

## 可复用建议

无论是 Function Calling 还是 MCP，有几个设计原则可以固化下来：

- **工具即边界**：把 API 调用封装在不可穿透的函数或服务里，Agent 永远看不到原始凭证与底层实现。
- **稳定输出格式**：每个工具函数返回结构统一，包含状态标识（成功/失败/部分结果）+ 摘要文本。
- **默认防御**：超时、重试次数、结果截断长度都在工具侧设定合理默认值，不要让模型决定重试逻辑。
- **可观测性**：至少在本地日志中保留每次工具调用的输入、输出和耗时，这是调试 Agent 行为的唯一可依赖数据源。
- **描述先行**：写工具描述时，把自己想象成模型——看到这段描述后，你会在什么情况下选择调用？你会怎么组装参数？

## 总结

Agent 与外部 API 的对接，表面看是个技术对接问题，实际考验的是 **“把不可控的外部世界封装成可靠工具”的工程能力**。在 OpenClaw 中，通过工具函数或 MCP Server，你可以构建一条从模型意图到真实服务的安全链路。核心并不在于多复杂的框架，而在于：稳定的鉴权管理、防御式的异常处理、以及足够精确的工具描述。做到这三点，你的 Agent 大概率就能稳定地“伸出握手”了。
