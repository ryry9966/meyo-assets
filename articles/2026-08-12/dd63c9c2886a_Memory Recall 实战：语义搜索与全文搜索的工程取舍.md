## 背景

在 OpenClaw 的 agent 闭环里，memory 模块的召回质量直接决定助手是“真的记得”还是“假装记得”。一个常见的场景是：用户一周前提过“我的 VPN 偏好 WireGuard，端口别用默认”，今天说“帮我配一下跳板机”，此时 agent 需要从海量历史会话中把那句偏好精准捡回来。

目前多数 agent 框架（包括 OpenClaw 的 memory 管线）都允许接入两类召回后端：

1. **基于倒排索引的全文搜索**（如 SQLite FTS5、Elasticsearch）
2. **基于 embedding 的语义搜索**（如 Chroma、Milvus、pgvector）

身边不少实践者会直接追语义搜索，但工程落地后发现有些坑只有跑过才知道。本文将复盘我们在 OpenClaw 中接入混合 memory recall 时的选型、对比与施工细节，给同样在 MCP/插件/自动化上深耕的朋友一份可复用的参考。

## 问题：语义搜索总是更好吗？

直觉上，语义搜索能理解“跳板机 ≈ 堡垒机 ≈ SSH tunnel”，全文搜索只会傻傻匹配字符串。实际落地中，这两个短板的杀伤力往往被忽略：

- **语义搜索的高召回低精度**：embedding 相似度可能把“我讨厌 WireGuard，太难配了”与“我的 WireGuard 配置偏好是……”拉得很近，因为关键词高度重叠。
- **全文搜索冷启动成本几乎为零**：不需要维护向量索引，没有 embedding 时延和费用，对于内存规模 <5000 条的轻量场景优势明显。
- **精准指令必须字面命中**：用户说的“IP 白名单：10.0.1.0/24”，用语义召回可能返回“10.0.1.5 这个地址……”，但 agent 要的是 CIDR 原文。

所以问题不是“哪个好”，而是“你的 memory 查询类型中，精确匹配与意图匹配分别占多少”。

## 做法：在 OpenClaw 中构建可切换的双通道召回

我们团队在 OpenClaw 中基于 MCP 封装了一个 `memory_recall` 工具，支持配置文件切换召回策略，方便在真实场景下 AB 对比。核心步骤如下：

### 1. 构建统一 retrieval 接口
```python
# openclaw_memory/retriever.py
class MemoryRetriever(Protocol):
    def retrieve(self, query: str, top_k: int, **kwargs) -> list[MemoryItem]:
        ...
```
分别实现 `FTSRetriever` 和 `SemanticRetriever`，均返回统一的 `MemoryItem` 列表，包含 `content`、`metadata`、`score`。

### 2. 语义通道落地细节
- 嵌入模型选取 `bge-small-zh`（本地部署，避免 API 延迟抖动）
- 使用 Chroma 作为向量库，instance 内存模式用于开发，持久化模式用于生产
- 入库时将原始对话按会话摘要 + 重要片段两种粒度向量化，而不是整段对话一股脑倒进去

### 3. 全文通道落地细节
- 选用 SQLite FTS5，轻量、零运维
- 建表时将时间戳、用户 ID 作为辅助字段，方便与 agent 上下文做权限过滤
- 自定义分词：对于 IP、端口、路径等追加 `prefix` 索引，保证子串命中（例如搜索“443”能匹配到“端口:443”）

### 4. 决策层切换逻辑
在 OpenClaw 的 memory 调度 prompt 中增加一条内部指令：
> 当查询包含精确值（IP、端口、路径、配置键）时优先调用 `memory_recall` 的 `fts` 通道，否则使用 `semantic` 通道。

这样 agent 可以根据用户意图自动路由，而不是硬绑定单一引擎。

## 踩坑点

- **向量冷启动噪音大**：如果 memory 条目少于 200 条，cosine similarity 的区分度很差，经常返回看似相关实则无关的段落。临时解法是小于阈值时自动 fallback 到全文搜索。
- **嵌入模型版本管理缺失导致召回崩塌**：一次升级 `bge-small-zh` 到 v2 后，新旧向量混在同一 collection 里，相似度排序全乱，artifact 型错误难以排查。补救措施：所有 chunk 元数据里强制记录 `embedding_model` 和 `version`，并写了个迁移脚本每次重索引。
- **混合召回排序难统一**：如果简单地用 RRF（倒数排名融合）合并两个列表，在全文结果明显更精准时会被语义结果的噪声拉低。最后采用了加权：若全文通道 top1 的 BM25 分数超过阈值，则全文结果权重提至 0.8，否则走默认 0.5/0.5。
- **上下文窗口的隐形浪费**：语义搜索返回的片段往往更长（因为 embedding 更适合段落级），容易撑爆 agent 的上下文，导致后续推理性能下降。我们强制所有召回片段截断到 300 字以内，哪怕语义更完整。

## 可复用建议

1. **从全文出发，按需加语义**：不要一上来就上向量库。先用 SQLite FTS5 跑通整个 memory 闭环，当出现“用户换了种说法就找不到了”的明确痛点时，再引入语义通道。
2. **对配置类、地址类信息保留原文索引**：不要把所有内容都无脑切 chunk 做 embedding，考虑为“低熵文本”单独建立结构化表（如 JSON 字段），在召回时直接 key-value 精准提取。
3. **为两种通道输出统一 metric 面板**：记录每次召回的 `hit_rate`（人工或规则判定是否命中）、`latency`、`token_consumption`。至少积累一周数据再做取舍。
4. **混合召回不是银弹，分层路由更经济**：在我们的实践中，明确意图（工具调用参数）走全文，模糊回忆（“上次那个什么来着”）走语义，准确率和成本平衡得最好。
5. **版本控制比选型更重要**：不论用哪种通道，embedding 模型、分词规则、chunk 策略的变更历程要像数据库 migration 一样能回滚、能溯源。

## 总结

在 OpenClaw 这类 agent 自动化场景下，语义搜索和全文搜索不是替代关系，而是两种不同温度的查询工具。全文搜索像“ctrl+F”，快速精准；语义搜索像“你还记不记得……”，慢但灵活。将二者用路由层而非归一化公式组合，能让 memory recall 在不同查询负载下都保持可用。

最终我们沉淀的思路是：**先保障所有可被精确命名的记忆一定能找回，再逐步提升模糊召回的能力。** 希望这份工程记录对正在折腾 agent memory 管线的同学有所帮助。
