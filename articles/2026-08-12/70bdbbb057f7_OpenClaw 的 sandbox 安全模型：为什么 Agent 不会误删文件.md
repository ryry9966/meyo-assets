# OpenClaw 的 sandbox 安全模型：为什么 Agent 不会误删文件

很多刚把 Agent 接入本地工作区的用户都会问同一个问题：它会不会哪天脑子一热，把我的代码库或配置文件删了？尤其在跑自动化任务、让 Agent 批量改文件时，这种焦虑更明显。OpenClaw 给出的答案不是“请相信模型”，而是一套默认不信任的 sandbox 安全模型。本文从工程角度拆解这套模型到底做了什么、应该怎么配置，以及有哪些容易踩的坑。

## 背景：误删不是模型问题，是权限问题

Agent 的“误删”通常不是模型产生了删除意图，而是它调用的工具没有边界。比如一个文件操作工具直接暴露了 `rm -rf`，或者 MCP 插件拿到了整个 home 目录的读写权限。模型只是根据 prompt 选择了工具，真正的风险来自工具背后的权限范围。OpenClaw 的 sandbox 思路很直接：**把文件系统的写权限从 Agent 手里拿走，除非你显式授予**。

## 做法：四层防线组成 sandbox

OpenClaw 的 sandbox 安全模型可以拆成四层，分别对应“默认拒绝、最小权限、可观测、可恢复”。

### 1. 默认只读挂载 + 显式授权

工作区默认以只读方式挂载，Agent 可以读文件、搜索代码、分析内容，但任何写操作都会被拒绝。只有你在配置中显式声明为可写的路径，才允许修改。一个最小配置示例如下（字段以你使用的 OpenClaw 版本为准）：

```yaml
sandbox:
  enabled: true
  default_policy: read-only
  mounts:
    - path: ./workspace
      access: read-write
    - path: /tmp/openclaw-cache
      access: read-write
  deny_patterns:
    - "*.pem"
    - "*.key"
    - ".env"
    - "*.secret"
```

这里 `./workspace` 是 Agent 可以改动的目录，`/tmp/openclaw-cache` 用于临时输出，其余位置全部只读。`deny_patterns` 是额外黑名单，即使路径在白名单内，匹配这些模式的文件也不允许写。

### 2. 干跑模式先预览

在正式执行批量修改前，可以开启 `dry_run: true`。此时 Agent 发起的每个文件写操作都会被记录并返回“将要执行的动作”，但不会真正落盘。你可以在审计日志里看到它准备改哪些文件、删哪些文件，确认无误后再关掉干跑。

这个模式对批量重命名、代码迁移、配置文件更新特别有用。它不能 100% 防止副作用，但能把风险从“执行后才发现”提前到“执行前预判”。

### 3. Copy-on-write 临时层

OpenClaw 的 sandbox 支持 OverlayFS 或类似 copy-on-write 机制。所有写操作先落到一个临时层，原始文件不动。如果任务跑完你觉得结果不对，可以直接丢弃临时层，工作区立刻回到任务前状态。如果结果正确，再把临时层合并回正式文件。

这个机制对“让 Agent 自己探索式地改代码”尤其有价值——你可以放心让它试错，坏了就回滚，不需要提前做完整备份。

### 4. 审计日志 + 回收站

每次文件变更都会记录来源：哪个 Agent、哪个工具、哪个 prompt、修改了哪个路径、前后哈希。审计日志默认写在 `.openclaw/audit.log`。同时 sandbox 会把删除的文件移动到 `.openclaw/trash` 而不是直接物理删除，即使误删也能恢复。

## 踩坑点：真实环境里容易忽略的细节

**1. 符号链接逃逸。** 如果 Agent 能访问一个符号链接，而链接指向白名单之外的路径，路径白名单就可能被绕过。OpenClaw 的路径校验需要先做 `realpath` 解析，确保最终目标路径仍然在允许范围内。自己写插件时也要注意这一点，不要只做字符串前缀匹配。

**2. MCP 插件可能绕过 sandbox。** 如果你给某个 MCP server 配置了独立的文件系统权限，它可能不受主 sandbox 的 `default_policy: read-only` 约束。每个 MCP server 都要单独设置 `allowed_directories`，不要假设全局配置会自动继承。

**3. 别为了方便把 home 目录整个加入白名单。** 一旦 home 可写，`.ssh`、`.aws`、`.gitconfig` 等敏感文件就全暴露了。宁可多花两分钟把需要的子目录逐个列出来。

**4. 干跑模式不是零风险。** 有些工具操作本身就带副作用，比如调用外部 API、写入数据库、发送网络请求。干跑只能拦截文件系统写操作，不能拦截所有副作用。对高风险操作还是需要二次确认或人工审批。

**5. 回收站会堆积。** `.openclaw/trash` 如果不定期清理，时间长了会占满磁盘。建议配合定时清理任务，保留最近 7 天的删除记录即可。

## 可复用建议

- **把 sandbox 配置纳入版本管理。** 不要只在本地改配置，把 `openclaw.yaml` 或等效文件提交到仓库，团队共用同一套安全基线。
- **故意测试越权行为。** 定期让 Agent 尝试删除白名单外的文件、写入敏感目录、跟随符号链接，验证 sandbox 是否正确拦截。
- **对删除和覆盖操作设置告警。** 审计日志里如果出现 `delete` 或 `truncate` 动作，自动推送通知到聊天群或邮件，第一时间发现异常。
- **最小权限原则同样适用于网络和数据库。** 文件系统只是其中一环，数据库账号、API key 也要按同样思路收敛权限。

## 总结

OpenClaw 的 sandbox 安全模型能防止 Agent 误删文件，靠的不是模型自觉，而是**默认只读、显式授权、干跑预览、写时复制、审计恢复**这一整套工程机制。你可以把它理解成给 Agent 装了一个“带刹车和行车记录仪的驾驶舱”：它能干活，但能碰哪里、能改什么、改坏了怎么回滚，都由你先定义好。

对工程化实践来说，这套模型最有价值的不是“它不会删文件”这个结论，而是**删了也能恢复、删之前能看见、删之后能追溯**。这三点做到了，才能真正放心把 Agent 放进工作区。
