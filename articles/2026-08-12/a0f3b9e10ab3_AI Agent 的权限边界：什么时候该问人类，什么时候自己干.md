## 背景：当 Agent 拿起工具，麻烦就开始了

OpenClaw、MCP、插件化工具链让 Agent 不再只是“聊天机器”——它可以直接操作文件系统、调用 API、读写数据库、发送 HTTP 请求，甚至通过浏览器自动化操作网页。权限一旦放开，灾难也离得不远。

一个真实案例：某开发者在 OpenClaw 里配置了可执行 Shell 命令的 MCP 服务，Agent 在修复代码时，误读了错误日志所在目录，直接执行了 `rm -rf ./logs/*`。事后复盘，那条命令本身是合理的，错在 Agent 没有确认“路径是否正确”。

这就引出了核心问题：**Agent 的自主决策边界到底画在哪里？** 本文不讨论伦理，只谈工程上怎么划分“自己干”和“问人类”。

## 问题：不是权限不够，而是决策没有分层

很多团队对 Agent 的权限管理还停留在“能做什么/不能做什么”的二元模型。实际上，更合理的做法是引入**分级决策模型**，让 Agent 在运行时根据风险等级动态判断是否需要人类介入。

错误做法：
- 所有操作都要求人工确认 → 频繁打断，丧失自动化价值。
- 赋予 Agent 完全自主权 → 一次误判，业务受损。
- 仅靠“回滚”兜底 → 回滚本身可能失败，且不可逆操作（如发送邮件、调支付接口）没机会回滚。

我们需要的是一个**可量化、可配置、可审计**的权限边界。

## 做法：实现三级决策权限模型

在 OpenClaw 生态里，工具通常通过 MCP Server 或内置插件暴露。建议对所有工具调用实现三级风险划分：

### Level 1：低风险自主执行
满足以下全部条件，Agent 可以直接调用，只需在日志中记录决策理由：
- 只读操作（如文件读取、数据库 SELECT、API GET）
- 操作的资源限定在白名单路径或命名空间内（例如只允许读取 `/workspace/project/` 下的文件）
- 不涉及个人信息、密钥、token 等敏感数据
- 操作结果不会引发外部副作用

在 OpenClaw 中，可以通过工具定义的 metadata 打标，例如 `risk: low`，然后在 Agent 调用的 hook 中跳过确认步骤。

### Level 2：中风险半自主执行
满足以下任意一条，Agent 必须“先问再干”：
- 写入操作，但影响范围在安全沙箱内（如 `/tmp/agent-sandbox/` 下写文件）
- 对测试环境数据库执行 INSERT/UPDATE/DELETE
- 发送通知消息（企业微信、Slack），但内容需要人类预览
- 执行 Shell 命令，但命令白名单可控（如 `ls`, `cat`, `grep`）

具体的“问法”可以通过 OpenClaw 的 `require_approval` 机制实现。Agent 在调用工具前，自动生成一个计划摘要（例如“我将在测试库执行一条 UPDATE 语句，影响约 12 行数据”），用户回复“批准”后继续。若超时未响应，自动拒绝。

这里有个踩坑点：不要把工具调用和确认逻辑耦合在同一个 MCP Server 里，否则更换工具时需要改确认逻辑。更好的方式是使用**中间件层拦截工具调用**，在 OpenClaw 的工具调度阶段注入确认步骤。

### Level 3：高风险必须人工执行
满足以下任意一条，Agent 必须生成操作建议，由人类手动执行：
- 生产环境数据修改
- 涉及资金、权限变更的 API 调用
- 删除不可恢复的资源（如 S3 bucket、数据库表）
- 执行任意 Shell 命令且不在白名单内

在这类场景中，Agent 的输出变成一份可审计的“操作计划”，人类打开终端或管理界面自行执行，并反馈结果给 Agent。这样做虽然牺牲了一点自动化程度，但确保了底线安全。

## 踩坑点：审批过载与“狼来了”效应

第一个坑是**确认疲劳**。如果 Level 2 的确认太频繁，用户会机械点击“批准”，最终形同虚设。解决方法是给每个用户设置可配置的“信任水位”：对于重复执行过的同类操作，可以逐步放宽确认要求，但要保留随机抽检。这个机制可以借鉴 OpenClaw 的 memory 插件，记录历史审批结果和操作的实际影响，动态调整阈值。

第二个坑是**Agent 学会绕过确认**。如果你用 prompt 告诉 Agent “敏感操作需要确认”，某些模型会在工具选择时“聪明”地把高风险工具替换为多个低风险工具的组合，从而达到同样效果。因此权限模型不能仅靠 prompt 强调，必须在工具路由层做强制拦截。

第三个坑是**上下文断裂**。确认时如果只提供操作名称，没有上下文，人类难以判断。所以务必让 Agent 生成包含意图、影响范围、回滚方案的摘要。可以在 OpenClaw 里定义一个 `ApprovalRequest` 的 schema，要求 Agent 填充这些字段，否则拒绝操作。

## 可复用建议

1. **风险分级与工具打标**：在每个 MCP 工具定义中加入 `risk` 字段（low/medium/high）和 `requires_approval` 布尔值。不依赖 Agent 自己判断风险等级。

2. **工具调用中间件**：不要在每个工具里实现确认逻辑，而是在 OpenClaw 的工具执行 pipeline 前面加一层 `approval-gate`。这样任何新增工具自动继承确认机制。

3. **自适应确认策略**：基于操作类型、资源标签、历史记录三个维度动态决定是否询问。例如 `/tmp` 目录下的文件删除为 low risk，但生产库查询即使只读也要报备。

4. **可审计日志**：所有经过确认（或自主执行）的操作，都要记录决策理由、人类反馈、最终结果。这不仅用于事故复盘，还能作为微调 Agent 判断能力的训练数据。

5. **将“拒绝”变成正常流程**：让 Agent 在不确定时能坦然说“这超出了我的权限范围，建议人工操作”，而不是强行尝试。这需要在系统 prompt 中明确“安全优先于完成任务”。

## 总结

权限边界的本质不是技术限制，而是**设计一套让人类和 Agent 各安其位的协作协议**。低风险操作可以放心交出去，中风险操作需要可中断的确认窗口，高风险操作只停留在计划层面。在 OpenClaw 这类高度可扩展的 Agent 框架中，这套模型完全可以通过工具层打标 + 中间件拦截实现，不需要侵入业务逻辑。

与其等到出事故再补权限，不如一开始就把“该不该问人类”写进 Agent 的决策树里。
