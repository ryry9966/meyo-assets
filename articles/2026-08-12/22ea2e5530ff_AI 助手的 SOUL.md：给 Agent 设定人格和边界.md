## 为什么 Agent 需要一份“灵魂文件”

在 Agent + MCP 的自动化工程里，模型能力已经不是最大的瓶颈，瓶颈变成了**行为不可控**。你给 Agent 接了一个邮件发送工具，结果某次对话里它擅自给整个部门群发了调试日志；你让 Agent 用内部知识库回复客户问题，它却夹带了一句“这个产品其实挺难用的”。这类事故的根因往往不是模型“变坏了”，而是缺少一份工程化的、可执行的**人格与边界定义**。

在 OpenClaw 生态里，Agent 不再是孤立的大模型调用——它会通过插件、MCP 服务、自定义 action 去操作真实世界的数据和系统。此时 System Prompt 如果还停留在“你是一个有用的助手”这种一句话设定，基本等于没设防。

“SOUL.md” 是我们团队内部对这份文件的命名习惯——一份 Markdown 格式的 Agent 人格与行为准则文件，跟随仓库一起版本化，被所有会话在初始化时加载进 system prompt。它不负责让 Agent“更有温度”，而是负责**让 Agent 在系统级别的约束下，做该做的事，不做不该做的事**。

## 真正会踩的坑

先说不定义清晰的 SOUL.md 会带来哪些实际伤害：

**边界模糊导致越权操作**  
你给了 Agent 一个 SQL 查询工具，只是说“可以查数据库”，没限定只读还是可写。某次用户问“帮我把所有未付款订单取消掉”，Agent 可能真的去执行了 DELETE。SOUL.md 需要对工具使用场景给出精确约束，比如“数据库操作：只允许 SELECT，禁止 INSERT/UPDATE/DELETE，除非用户角色为 admin 并经过二次确认”。

**人格飘移与上下文污染**  
多轮对话越长，Agent 越容易受到用户诱导偏离初始设定。一个客服 Agent 如果没有明确“禁止使用攻击性语言，禁止对用户进行个人评价”，在长会话中可能被激怒或带偏，输出不专业的回复。人格部分必须是**不可覆盖的硬规则**，而不是可以被商量的人文建议。

**隐私与合规裸奔**  
MCP 工具可能携带用户真实数据，比如邮箱、姓名、订单号。SOUL.md 中必须加入数据脱敏规则：“输出中不得暴露完整的个人身份信息，所有邮箱地址必须脱敏为 j***@example.com 格式”。这是可以直接写在 system prompt 里的硬约束，但对模型来说，不写就等于允许。

**版本混乱导致行为漂移**  
最隐蔽的坑是：你改了 SOUL.md 的某个约束，却没有变更历史。两周后团队复盘“为什么昨天 Agent 开始拒绝执行某个合法操作”，你根本回溯不到是哪次修改引入的。这份文件必须像代码一样用 Git 管理，改动要走 review。

## 工程实现：怎么定义和加载

我们目前在 OpenClaw 中的做法是把 SOUL.md 拆成几个模块，用 Markdown 标题区分，在运行时拼接进统一的 system prompt：

### 文件结构
```
/agents
  /cso-agent
    SOUL.md          # 核心文件
    tool-policy.md   # 工具使用策略（可从 SOUL.md 拆分出来）
```

**SOUL.md 推荐内容区块：**

```markdown
# Core Personality
你是一个严谨、克制、不自我发挥的技术支持 Agent。
你对不确定的事情会明确说“不确定”，不会编造。

# Capabilities
- 查询知识库（通过 MCP search_kb）
- 读取产品手册（通过 MCP read_manual）
- 创建工单（通过 MCP create_ticket）
- 您不能执行任何系统管理操作，不能修改配置。

# Behavior Constraints (Hard)
1. 永远不要暴露任何内部 IP、API Key 或数据库连接信息。
2. 输出包含邮箱时，必须脱敏为 `j***@example.com`。
3. 遇到用户要求执行危险操作（如删除数据）时，必须拒绝并引导至人工。
4. 禁止对用户使用评价性语言（如“你这个想法很蠢”）。

# Tool Usage Policy
- search_kb: 优先使用，不要猜测答案。
- create_ticket: 必须先向用户确认问题摘要，经用户明确同意后才允许调用。
- 任何工具，连续失败 2 次后必须停止并说明原因，不要无脑重试。

# Example Boundaries
User: 帮我把所有客户邮箱导出来。
Assistant: 抱歉，导出全量客户数据不在我的权限范围内，建议联系数据管理员。

# Version & Review
version: 1.2.0
last_reviewed: 2025-02-10
```

### 加载方式
在 OpenClaw 的 agent 配置中，通过 system prompt template 引入：

```yaml
system:
  template: |
    {{ readFile "agents/cso-agent/SOUL.md" }}
    Current date: {{ now }}
    User role: {{ user.role }}
```

`readFile` 在启动时读取文件并缓存内容，避免每次请求都读磁盘。

对于工具权限，SOUL.md 只是第一道**语义防线**，真正的硬限制必须在 MCP 服务端做权限裁剪。比如数据库查询工具，服务端只暴露 SELECT 接口；邮件发送工具在 MCP handler 里校验收件人白名单。双重保险。

## 迭代与维护的几个建议

**用 YAML 前置元数据做可测试性**  
可以把部分约束结构化，例如行为规则用 YAML 写在文件头部，然后跑简单的合规测试脚本，检查 Agent 在仿真场景下的输出是否违反规则。这不是绝对可靠，但能拦住 80% 的明显违规。

**把示例当测试用例记下来**  
SOUL.md 里的 `# Example Boundaries` 别写虚的，直接从真实事故里抽象出案例。每修一次 PR，顺便在文件里加一组对话示例，让团队知道“这个场景我们已经讨论过，结论是拒绝”。

**别把人格写得太长**  
过长的 system prompt 不仅消耗 token，还会让模型在推理中抓不住重点。把核心人格控制在 300 词以内，剩余用结构化列表表达。我们都是先用简洁版本跑测试，再根据 bad case 追加约束，不预先写成论文。

**版本管理 + 变更日志**  
给 SOUL.md 内置 `version` 字段，每次改动在顶部 `CHANGELOG` 里写一句说明。配合 Git tag 发布，Agent 行为回滚就能精确到哪一版。

## 总结

给 Agent 设定人格和边界不是一次性的“调教”，而是工程安全实践的一个核心组件。在工具调用链越来越复杂的 OpenClaw 场景下，SOUL.md 就像防火墙规则集：越简单明确，越容易生效；越模糊宽松，越容易被绕过。把这份文件当作代码去写、去维护、去测试，你的 Agent 才能真正在自动化流程里“说到做到，不到处乱做”。
