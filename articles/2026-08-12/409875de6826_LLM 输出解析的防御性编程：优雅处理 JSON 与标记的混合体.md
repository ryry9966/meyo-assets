# 背景

在构建基于 LLM 的 Agent、MCP 工具调用或自动化流水线时，我们经常需要模型返回结构化数据。JSON 是最自然的选择，但真实场景中的输出往往是“半结构化”的：模型可能在 JSON 前后添加自然语言解释、用 markdown 代码块包裹、甚至嵌入自定义 XML 标签。直接使用 `json.loads()` 十有八九会失败。

OpenClaw 的插件生态中，很多动作（Action）依赖 LLM 输出的解析结果驱动下一步操作。如果你的解析器只接受“干净 JSON”，生产环境会频繁出现非预期中断。本文分享一套轻量级的防御性解析策略，不引入额外库，却能覆盖 95% 的脏输出。

# 问题定义

典型的“脏”输出可能是这样的：

```
好的，以下是结果：
```json
{"action": "search", "query": "OpenClaw MCP error handling"}
```
注意替换占位符。
```

或者：

```
<response>
{"intent": "query_db", "params": {"table": "logs", "filter": {"level": "error"}}}
</response>
```

还有更棘手的：JSON 内部嵌套转义引号，末尾被截断，或者模型自作主张添加了注释。

我们的目标很明确：**从 LLM 的原始文本中提取一个合法、完整的 JSON 对象，将其交给下游，同时对无法恢复的情况给出可诊断的错误信息。**

# 做法与步骤

以下策略基于 Python 实现，可直接嵌入 OpenClaw 的 Action 或 MCP Server 代码中。

## 第一步：信号提取 —— 定位 JSON 边界

不要把整个字符串当 JSON 解析。先做三件事：

1. **移除最外层 markdown 代码块标记**  
   用正则匹配 `^```(?:json)?\n?` 开头和 `\n?```$` 结尾，去除它们。注意可能有多行前缀。

2. **提取被标签包裹的内容**  
   如果输出包含 XML/自定义标签，如 `<response> ... </response>`，先提取标签内的文本。可以使用 `re.search(r'<response>(.*?)</response>', text, re.DOTALL)` ，但更健壮的做法是找第一个 `{` 到最后一个 `}`。

3. **精确定位 JSON 片段**  
   采用“平衡括号法”：从第一个 `{` 开始，用计数器记录花括号的开闭，找到匹配的最后一个 `}`。这样能天然忽略 JSON 前后的任何非结构化文本。

```python
def extract_json_candidate(text: str) -> str:
    # 去除常见 markdown 代码块包裹
    text = re.sub(r'```(?:json)?\s*\n?', '', text)
    text = re.sub(r'\n?```', '', text)
    # 找到第一个 '{' 和匹配的 '}'
    start = text.find('{')
    if start == -1:
        return ''
    balance = 0
    for i, ch in enumerate(text[start:], start):
        if ch == '{':
            balance += 1
        elif ch == '}':
            balance -= 1
            if balance == 0:
                return text[start:i+1]
    return text[start:]
```

该函数返回一个候选 JSON 字符串，可能不完整，但已经是最大程度的干净片段。

## 第二步：修复与容错

即使提取了边界，内容仍可能有瑕疵。常见修复：

- **去除尾部逗号**：截断的 JSON 末尾经常多出逗号，如 `{"key": "value",}` 。用正则 `re.sub(r',\s*(?=[}\]])', '', candidate)` 移除。
- **处理字符串内的未转义控制字符**：可以用 `json.loads` 前尝试用 `ast.literal_eval` 预处理（仅限简单情况），但更实用的是对反斜杠进行转义：`candidate.replace('\\', '\\\\')` 时要小心误转义。更好的方法是将候选字符串用 `codecs.decode(candidate, 'unicode_escape')` 但风险较高。通常先尝试 `json.loads`，失败后再进行正则修复。
- **处理模型输出的注释**：JSON 不含注释，但 LLM 有时会插入 `// comment` 或 `/* ... */`。可以用移除注释的简单状态机处理，但多数场景下，如果注释在字符串值中会被解析错误，因此只在紧急修复时使用。

推荐的二次解析流程：

```python
import json

def robust_json_parse(text: str):
    candidate = extract_json_candidate(text)
    if not candidate:
        raise ValueError("No JSON candidate found")
    try:
        return json.loads(candidate)
    except json.JSONDecodeError as e:
        # 尝试尾部逗号修复
        fixed = re.sub(r',\s*(?=[}\]])', '', candidate)
        return json.loads(fixed)
```

这个简单的两阶段策略已经能解决大部分实际案例。

## 第三步：流式解析与截断处理

在 MCP 工具调用中，经常需要边接收 token 边解析部分 JSON。此时可以扩展上述思路：每次收到新 chunk，将累积文本通过 `extract_json_candidate` 得到当前最可能的片段，然后用 `json.JSONDecoder().raw_decode(candidate)` 尝试解析。`raw_decode` 不会在对象结束后报错，能返回解析到的对象和剩余部分，非常适合流式场景。

```python
decoder = json.JSONDecoder()
obj, idx = decoder.raw_decode(candidate)
# obj 为已解析对象，idx 为消耗的字符数
```

如果未解析完整，`idx` 会小于字符串长度，可以缓存未处理的部分，等待下一个 chunk。

# 踩坑点

1. **花括号在字符串值中出现**  
   比如 `{"text": "this is {curly}"}`。平衡括号法会误判最后一个 `}` 的位置。可以通过简单的状态机跟踪是否在字符串内来改进，但实现复杂度增加。在实践中，这种输出相对少见；如果遇到了，可回退到提取标签后直接 `json.loads` 的尝试。

2. **模型输出 JSON 数组** (`[...]`)  
   我们的提取逻辑只搜索 `{`，会丢失数组。需要同时兼容 `[`。可以修改为：寻找第一个非空字符为 `{` 或 `[`，并用对应的括号配对逻辑。

3. **模型输出多段 JSON**  
   比如 `{"a":1} {"b":2}`。这种输出不符合 JSON 规范，需要根据业务决定取第一个还是报错。可以通过 `raw_decode` 解析第一个对象后，看后面是否有下一个对象，如果有则记录警告。

4. **解析器静默返回错误结构**  
   如果 `json.loads` 失败后盲目补全，可能返回一个与预期 schema 不符的畸形数据。防御性编程要求我们必须做 schema 校验（例如使用 `pydantic` 或 `jsonschema`），失败即拒绝。

# 可复用建议

- 将上述 `extract_json_candidate` 和 `robust_json_parse` 封装为一个轻量级模块，在所有 LLM 调用点统一使用。  
- 在 OpenClaw 的 Action 定义中，接收 LLM 输出后立即调用该解析器，失败则抛出可识别的自定义异常，让 orchestrator 走重试或降级路径。  
- 所有解析错误都应记录原始输出的头尾各 200 字符，方便回溯。  
- 对于关键流程，永远不要假设 LLM 输出格式一定正确；在 prompt 中强调“只返回纯 JSON”有帮助，但不可依赖。

# 总结

LLM 输出解析是 Agent 工程的暗角。用防御性思想处理混合格式，不用追求完美解析器，而是为最常见的脏模式建立容错层。本文的边界提取 + 尾部逗号修复 + raw_decode 流式解析，已经能在零外部依赖下覆盖绝大多数真实状况。你的解析器越宽容，系统越稳定，但宽容必须有底线 —— 对无法恢复的错误要早失败、可观测。希望这套实践能让你在 OpenClaw 的自动化之旅中少踩几个坑。
