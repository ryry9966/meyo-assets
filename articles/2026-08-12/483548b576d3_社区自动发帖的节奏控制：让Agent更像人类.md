## 背景

用 Agent + MCP 工具链做社区内容运营时，最容易暴露机器人身份的不是内容质量，而是发帖节奏。一旦触发平台风控，账号权重下降、限流甚至封禁，整个自动化 pipeline 就废了。很多人在这一步直接选择第三方调度平台，但工程团队更希望完全掌控链路，把节奏控制做成一个可配置、可观测的模块。

我在 OpenClaw 生态里维护一个多账号社区发布 Agent，本文梳理其中关于“人味”节奏控制的设计思路、实现要点和踩过的坑。

## 问题拆解

社区反作弊系统通常关注三个维度：

- **时间一致性**：是否每天固定时间发布，相邻帖子间隔是否高度恒定。
- **操作连续性**：是否连续执行单一行为（只发帖不浏览、不互动），操作间缺乏停顿。
- **文本/行为指纹**：内容是否高度模板化，交互动作序列是否重复。

因此，节奏控制不是简单地在 `sleep(random(min,max))` 就能解决，而需要一套贴合真实用户行为的调度策略，在时间、操作序列、活跃窗口三个层面注入合理噪声。

## 工程实现：三级噪声模型

在现有 MCP 工具链基础上（例如通过 Puppeteer MCP Server 操作网页，或通过 HTTP API 仿真），我实现了一个“调度中间层”，封装为可独立运行的策略引擎。它采用三级噪声模型，每一级可独立配置参数。

### 第一级：活跃窗口与休眠期

真人不会全天候在线。我们把一天划分为 2-3 个“活跃窗口”，例如上午 9:00-11:30、下午 14:30-17:00、晚上 20:00-23:00。每个窗口内允许执行发布任务，其余时间为休眠期，所有任务延后到下一窗口。

窗口的定义不是固定死的时间段，而是一个基于日均分布的随机偏移。例如，上午窗口的起止时间每天会在 ±20 分钟内浮动：

```
base_start = 9:00
offset = random_gaussian(mean=0, std=10) 分钟
今日窗口开始 = base_start + offset, 限制在 8:40-9:20 之间
```

每个窗口的任务数量也受日总配额限制，日配额设置为波动值（例如目标 5 篇/天，实际取 4-6 篇），并用泊松分布分配到各个窗口，模拟有些天数不想发帖、有些天集中发帖的情况。

### 第二级：任务间隔抖动

同一个活跃窗口内，相邻帖子之间的间隔不能是固定值。我们使用**对数正态分布**生成间隔时间，其长尾特征能模拟人类偶尔走神或突然有事离开的场景：

```
avg_gap = 25  # 分钟
sigma = 0.4
gap = random.lognormvariate(mu=log(avg_gap), sigma=sigma)
# 裁剪到合理范围 [5, 120] 分钟
```

同时加入**最小变化阈值**：连续两个间隔完全相同（四舍五入到分钟）的概率极低，我们会强制微调，避免出现 `25, 25, 25` 这种模式。

为了更“真”，同一个窗口内，发帖之间还要穿插“浏览行为”——例如发布前读取首页推荐流一次，发布后查看自己主页动态一次，这些行为的间隔同样采用对数正态分布控制，且和主帖间隔交错编排，不能单独做一批浏览再发帖。

### 第三级：任务内操作节奏

单次发帖操作本身（打开编辑器、输入文本、上传图片、确认发布）也需要模拟人类节奏。要点：

- 每个操作步骤之间加入人类反应时间（200ms-800ms 随机），不要连续触发 DOM 事件。
- 文本输入速度因人而异，我们维护一个打字速度档案（40-80 字/分钟），并使用随机掉速（打字中断、删除重输）。对于支持 `type` 的自动化工具，改用逐步输入字符实现。
- 光标移动：在点击“发布”前，加入 0-3 次无目的的鼠标移动或页面微滚动（通过 `page.mouse.move` 随机坐标），模拟犹豫或最后检查。

这一级噪声如果缺席，平台可以通过事件时间戳序列建模轻易识别机器人。

## 踩坑点

1. **不要用均匀分布生成间隔**  
   早期使用 `random.randint(20,30)` 分钟做间隔，连续 7 天后账号被限流。均匀分布的概率密度是平的，而真人行为更集中在某个值附近但有长尾，对数正态分布更符合。

2. **跨窗口任务堆积导致 burster 效应**  
   如果下午活跃窗口开始时积压了 6 篇待发帖子，系统一次全部发出，即便间隔随机，也会异常密集。必须增加“最大窗口任务数”限制，挤出到下一个窗口。

3. **MCP 工具的超时与重试会打乱节律**  
   使用 Puppeteer MCP 操作时，偶尔元素等待超时或页面加载慢，导致实际间隔被拉长。调度引擎需要基于**实际执行完成时刻**计算下一任务延迟，而不是基于预估。否则积累误差会出现“暂停——突然连发”的现象。

4. **多个账号的行为指纹不能同源**  
   为每个账号生成不同的活跃窗口模板、打字速度档案和操作序列模式。最简单的方式是给每个账号分配一个“角色标签”（晨型人、夜猫子、碎片时间者），据此设置不同的基础参数，避免多个账号在同一时间段整齐划一地发文。

## 可复用建议

把节奏控制做成一个独立模块，暴露配置如下：

```yaml
rhythm:
  daily_quota: [4, 6]                # 日发帖量范围
  windows:
    - label: morning
      base_start: "09:00"
      base_end: "11:30"
      start_offset_std: 10           # 分钟
      end_offset_std: 15
    - label: afternoon
      base_start: "14:30"
      base_end: "17:00"
      start_offset_std: 10
      end_offset_std: 15
  gap_model: log_normal
  gap_params:
    mu_minutes: 3.2                  # ln(25)
    sigma: 0.4
    clip: [5, 120]
  per_action_delay: [200, 800]       # ms
  typing_speed_wpm: [45, 65]
  browsing_interleave: true
```

调度引擎根据此配置生成当日实际任务时刻表，然后再交给 MCP 执行层。这样即使执行层工具链变化（比如从 Puppeteer 换成 Playwright MCP），节奏控制逻辑依然不变。

调试时，将生成的时刻表和实际执行日志可视化，能够快速发现节奏异常。

## 总结

让 Agent 发帖不像机器人，本质上是对人行为的时间维、序列维、操作粒度三维建模。简单的随机延迟只是第一步，关键在于构建**窗口 + 对数正态 + 操作节律**的三级模型，并遵循“基于完成时刻驱动”的调度原则。把这一层从业务逻辑中剥离，做成可配置的中间件，会大幅降低账号风险和排查成本。在 OpenClaw 这类 Agent 框架下，节奏控制应被视为同内容生成一样重要的基础能力。
