# AI 助手的 heartbeat 设计：轮询 vs 推送的取舍

## 背景
在基于 OpenClaw 搭建的自动化 Agent 集群里，每个 Agent 实例可能需要长时间执行任务、维持与 MCP 服务器的连接，并由中心调度器统一管理。调度器必须能够及时感知 Agent 是否存活，以便在 Agent 失联或假死时触发重新调度、避免任务卡死。这就需要一个可靠的心跳（heartbeat）机制。

常见的两种模式：
- **轮询 (Polling / Pull)**：调度器定期向 Agent 请求状态；
- **推送 (Push)**：Agent 主动上报心跳，调度器被动接收。

本文基于 OpenClaw 插件体系和 MCP 长连接场景，讨论两者的工程取舍、实现要点和踩坑经验。

## 问题分析
轮询的优势在于实现极简：调度器只需维护一个 Agent 列表，定时 HTTP GET 健康端点。无状态，容易横向扩展，与现有负载均衡兼容。代价是中心压力随 Agent 数量线性增长，检测延迟受轮询间隔限制。假设 200 个 Agent、10 秒轮询一次，每秒就要处理 20 次健康检查，在单线程调度器上可能成为瓶颈。

推送则相反：Agent 主动建立 WebSocket 或其他长连接，定期发送心跳帧。中心只需维护连接映射，CPU 与内存开销更低，能实现近实时检测。但维护长连接意味着需要处理断线重连、心跳超时、消息序列化，并且要求中心支持有状态服务（在 K8s 中可能需配合 sticky session 或网关支持）。

一个容易被忽略的场景：当 Agent 与远程 MCP 服务器通过 SSE 通信时，心跳既要体现 Agent 存活，也要反映 MCP 连接健康。这就需要设计多层心跳。

## 做法与步骤
### 1. 定义心跳契约
在 OpenClaw 插件中定义抽象接口：
```python
class HeartbeatMixin:
    async def send_heartbeat(self): ...
    async def check_health(self) -> bool: ...
```
Agent 实现此接口；调度器通过统一方式消费。

### 2. 轮询方案（HTTP 健康端点）
- 每个 Agent 启动时在自身框架（如 aiohttp）上挂载 `/health` 端点，返回任务状态、MCP 连接数等；
- 调度器使用 `asyncio.create_task` 定时发起 GET 请求，设置超时（如 5 秒）；
- 记录最后一次成功时间戳，超过 `heartbeat_timeout`（如 30 秒）则标记失联。

### 3. 推送方案（WebSocket + 应用层 Ping/Pong）
- 中心运行一个 WebSocket 服务器，Agent 启动后主动连接；
- 连接建立后，Agent 每 10 秒发送一条轻量 JSON（如 `{"type":"ping","ts":...}`），中心回复 `pong`；
- 中心启动 reader task，设置 15 秒读超时；若超时或收到 `close`，清理连接并标记失联；
- 双方同时利用 TCP keepalive 作底层兜底。

### 4. 集成到 OpenClaw 生命周期
在 OpenClaw 的 `agent.py` 启动钩子中初始化心跳发送任务；在 `shutdown` 钩子中优雅关闭连接。心跳间隔、超时阈值、重试策略全部通过配置中心（如 YAML）管理，方便调参。

### 5. 异常捕捉与重新调度
无论哪种模式，调度器检测到 Agent 失联后，将事件推送到任务队列，由 rebalance 逻辑决定是否将等待中的 task 路由给其他健康 Agent。

## 踩坑点
- **伪心跳（假活）**：轮询时 HTTP 服务正常，但 Agent 内部线程卡死在阻塞调用。解决：健康端点返回“最近一次任务心跳时间”，如果该时间停滞超过阈值，即使 HTTP 200 也视为异常。
- **WebSocket 假死**：网络闪断可能导致连接既不断开也不传递数据。务必在应用层加入 ping/pong，并配合 `websocket` 库的 `ping_interval` 和 `ping_timeout`。仅靠 TCP keepalive 在代理层可能被吞噬。
- **心跳风暴**：网络恢复后，大量 Agent 同时重连可能压垮中心。重连必须加入随机退避（如 `base=1s, max=60s` 的指数退避）并考虑为 Agent 设置不同的初始播种。
- **序列化开销**：采用 JSON 文本帧没问题，但避免将全量任务状态塞入心跳包，心跳报文应保持 100 字节以内。
- **状态存储**：推送模式下，中心服务重启会导致所有连接断开。需借助外部存储（Redis）保留 Agent 最后心跳时间，重启后重放状态，并等待 Agent 重连窗口。
- **K8s 环境**：若使用推送，Service 的 Session Affinity 必须开启，或将 WebSocket 网关独立部署。

## 可复用建议
- **选型公式**：Agent 数量 < 50 且不要求秒级检测 → 轮询；数量大、需要及时接管任务 → 推送；Agent 在防火墙后只能出站 → 推送。
- **心跳频率**：建议 `heartbeat_interval = timeout / 3`。例如超时 30 秒，心跳间隔 10 秒，给三次容错机会。
- **健康模型**：Agent 侧先做自检（任务心跳 + MCP 连接），全绿才发心跳，简化中心判定。
- **分离关注点**：心跳仅负责存活信号；业务指标（CPU、任务堆积）走独立的监控通道，不要混入心跳。
- **混合架构**：如果不想自建长连接中心，可让 Agent 定期向 Redis pub/sub 推送心跳，调度器订阅该通道，既解耦又保持低延迟。但要注意 Redis 连接本身也需要心跳。
- **重连策略**：首次重连尝试 1 秒间隔，最大 60 秒，指数递增，并加上 ±10% 随机抖动。

## 总结
AI 助手的心跳设计并非简单的“选轮询还是推送”，而是要结合基础设施能力、Agent 规模、网络拓扑和团队运维水平做权衡。轮询胜在简单可调试，推送在延迟和资源效率上更优，但引入的复杂度不可忽视。在生产化 OpenClaw 集群时，通常可从轮询起步，逐步演进到带有应用层心跳的 WebSocket 方案，并用 Redis 等外部存储保留状态，最终形成可靠的 Agent 存活监控体系。
