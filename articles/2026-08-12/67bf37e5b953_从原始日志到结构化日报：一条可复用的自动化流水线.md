## 背景

在协同开发与运维场景中，日志和信息散落在多个系统：Slack 频道、GitHub 提交、Jira 工单、监控告警甚至数据库慢查询记录。每天手动汇总日报，不仅要反复切换工具，还容易遗漏关键上下文，格式也不统一。我们尝试在已有的 OpenClaw/MCP/Agent 工具链上，组装一条从多源原始日志到结构化日报的自动流水线，减少重复劳动的同时，让日报真正反映当天的工程进展与风险。

## 核心问题

- **来源异构且碎片化**：每条原始记录都是短文本，缺乏上下文关联。
- **非结构化转结构化**：需要从自然语言中提取“完成事项、进行中、阻碍、明日计划”。
- **幻觉与事实可控**：LLM 容易在概括时添加未经证实的细节。
- **生产环境健壮性**：需处理时区、去重、JSON 解析失败、token 成本等工程问题。

## 整体做法：基于 MCP + Agent 的流水线

我们把流程拆成 4 个阶段：采集 → 预处理 → 抽取与汇总 → 报告生成与分发。所有自动化逻辑用 OpenClaw 的任务编排能力驱动，依赖已有的 MCP 服务连接各数据源。

### 1. 多源数据采集
使用社区或自建的 MCP 插件定时拉取过去 24 小时的数据：

- `slack-mcp`：读取指定频道的消息（排除机器人消息、按线程去重）。
- `github-mcp`：获取仓库的 commits、PR、issue 评论。
- `jira-mcp`：查询分配给当前用户或项目的 issue 变更。
- 运维数据（如慢查询、告警）通过自定义的 HTTP MCP 插件抓取 API 摘要。

定时任务每天早上 8:00 触发，所有采集结果输出为统一的日志流，每条记录附带 `source`、`timestamp`（统一转成 UTC）和原始文本。

### 2. 预处理：清洗与去重
- **去重**：GitHub PR 标题和 Jira 链接往往在 Slack 中重复讨论，通过消息中的 URL 指纹和编辑距离去重。
- **截断与摘要**：对于长线程消息，只保留最新几条和前一天的上下文，防止 token 爆炸。
- **时间窗口对齐**：由于各系统时区不同，采集时强制转为 UTC，并在生成日报时转换为本地时区展示。

### 3. 两阶段抽取生成日报
这一步是关键。我们采用 Agent 分步处理，避免一次性处理大量原始日志导致输出不稳定。

**第一阶段：单源逐条提取**  
将预处理后的日志按来源分批，每批不超过 15 条，调用 LLM 提取结构化摘要。Prompt 要求严格：

> 仅基于提供的消息内容，提取以下字段并输出 JSON 数组：`date` (YYYY-MM-DD), `summary` (一句中文描述), `status` (completed/in_progress/blocked/planned), `assignee`, `risks` (简短风险描述，无则忽略)。不要编造任何未明确提及的信息。

输出格式约束为 Markdown 代码块内的 JSON，如：

```json
[{"date":"2025-03-27","summary":"修复登录页超时问题","status":"completed","assignee":"张三"}]
```

解析时，若 JSON 无效，回退到正则匹配或重试。

**第二阶段：跨源汇总与综合日报**  
将所有第一批产出的结构化条目拼接，再次调用 LLM，结合日报模板生成最终报告。模板固定为：

- 今日完成
- 进行中
- 阻碍与风险
- 明日计划

并要求 LLM 按重要性排序，标明原始来源引用，但不暴露原文。最终输出是纯 Markdown 格式。

### 4. 报告分发
生成的 Markdown 日报通过邮件 MCP（如 `resend-mcp`）发送给团队，或直接推送到指定 Slack 频道供人工 review。加入一个简单的人工审核环节：先在 `#daily-reports-draft` 发一份草稿，确认无误后手动或延时自动发送正式版。

## 踩坑记录

1. **时区处理**  
   最初采集时保留各源本地时间，汇总时出现时间线错乱。后统一在采集节点转 UTC，仅在展示侧转换。

2. **幻觉摘取**  
   早期 Prompt 约束不足，模型会把聊天中的玩笑话当成待办事项。加上“仅基于提供的日志，不要推测”并改为二阶段抽取后，准确率明显提高。

3. **JSON 解析失败**  
   LLM 偶尔会输出缺少右括号的 JSON，或附加大段解释。通过要求使用代码块包裹，并加入 `json.loads` 的重试机制（最多 3 次，失败则人工兜底），基本解决了稳定性问题。

4. **Token 成本控制**  
   所有原始消息直接给 LLM 的成本很高。我们采用摘要式预处理：对高频更新线程只取最近几条，并用短 hash 去重，成本下降了约 40%。

5. **敏感信息泄露**  
   某些日志可能包含 IP 或密钥。在预处理阶段增加简单的正则脱敏（如替换 IP 为 [REDACTED]）。同时确保 MCP 组件仅在内部网络运行，API key 通过环境变量注入。

## 可复用建议

- **优先使用现成 MCP 插件**，避免重复开发数据采集层。OpenClaw 生态中已有多个高质量的 MCP 服务。
- **用“两阶段抽取”替代一次性聚合**，提升结构化质量，减少幻觉。
- **将日报模板文件化**（如一个 `template.md`），方便团队根据不同项目调整。
- **保留人工审核回路**。完全自动化容易积累错误，初期设置草稿频道能平滑过渡。
- **监控与告警**：如果某天采集失败或 JSON 解析报错，应触发通知而不是静默失败。

## 总结

从原始日志到结构化日报的自动化流水线，技术栈并不复杂，但工程细节决定成败。利用 MCP 解决数据源异构问题，通过 Agent 编排多步提取，再配合严格 Prompt 和解析容错，可以建造一个稳定、低幻觉的日报生成系统。整个过程在真实生产环境中持续运行了数周，人工参与度从原先的 30 分钟/天下降到偶尔确认一次，团队信息同步的一致性也明显提升。如果你也在用 OpenClaw 或类似工具链，欢迎在此基础上继续优化，把日报真正变成工程基础设施的一部分。
