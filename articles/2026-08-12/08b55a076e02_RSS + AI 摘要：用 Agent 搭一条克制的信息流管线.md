## 背景

信息过载这件事，RSS 用户体会最深。订阅源一多，每天几百条未读，真正值得点开的可能不到 10%。AI 摘要听起来是天然解法：让 LLM 读一遍，输出三行要点，用户扫一眼决定要不要看原文。但真动手做，会发现“全自动摘要推送”很容易变成“全自动垃圾生成器”——要么摘要太长没人看，要么摘要质量飘忽，要么 token 成本失控。

所以这篇不聊宏大愿景，只讲一条能长期跑下去的 RSS + AI 摘要管线怎么搭。面向 OpenClaw / Agent / MCP 用户，但方案本身不绑定任何平台，核心是模块化与过滤优先。

## 问题拆解

一个可用的信息流管线，需要解决四件事：

1. **抓取**：RSS 源不稳定，编码乱、字段缺失、正文只有摘要。
2. **去重与过滤**：同一篇文章多源转发、utm 参数导致重复、广告和标题党混入。
3. **摘要生成**：LLM 输出格式不稳定，直接让模型自由发挥会得到散文而不是摘要。
4. **推送与调度**：批量处理、成本控制、失败重试。

如果直接把 RSS 塞给 Agent 让它“总结一下”，结果通常不可控。工程上更稳的做法是：**固定管线，Agent 只做其中一环**。

## 做法与步骤

我采用的架构如下：

```
RSS 源 → fetcher → 清洗/去重 → 过滤器 → summarizer(LLM) → 格式化 → 推送
```

### 1. 抓取与清洗

用 `feedparser` 拉取 RSS，但不要完全信任它。实践中至少要做三件事：

- 手动处理 HTTP 响应编码，避免 `feedparser` 遇到非 UTF-8 时乱码。
- 对 `entry.link` 做 URL 规范化：去掉 `utm_*`、`fbclid`、锚点，只保留 scheme + host + path + query 的稳定部分，再生成 hash 用于去重。
- 正文优先用 `trafilatura` 从原文提取，失败时回退到 RSS 自带的 `summary`，再失败就丢弃该条——不要为了“全量”牺牲质量。

### 2. 过滤优先于摘要

摘要的成本和噪音都来自这一步。建议在进入 LLM 之前，先用规则砍掉大部分：

- 标题长度低于 15 字符或高于 120 字符的直接丢弃。
- 关键词黑名单：广告、抽奖、推广、直播预告等。
- 白名单模式：只保留包含特定关键词的条目，比如“OpenClaw”“MCP”“Agent”“RSS”。
- 单次运行最多处理 20 条，超过的留到下一轮。

这一步能把进入摘要环节的条目减少 60%–80%，也是克制策略的核心。

### 3. AI 摘要：用固定 Schema 约束输出

不要用“请总结这篇文章”这种开放式 prompt。我用的模板是：

```
你是信息过滤助手。阅读以下文章，输出 JSON，不要输出其他内容。
{
  "summary": "一句话摘要，不超过 50 字",
  "points": ["三个要点，每点不超过 15 字"],
  "tags": ["2-4 个标签"],
  "score": 0-10 的可读性评分
}
文章标题：{title}
文章正文：{content}
```

原因：LLM 输出 JSON 时用 `response_format=json_object` 或 function calling 约束，解析失败率大幅降低。模型选便宜档位即可，摘要不需要深度推理。我常用 `gpt-4o-mini` 或 `claude-haiku`，批量处理时每千条约 $0.5–1.5，成本可控。

### 4. 推送与调度

摘要生成后，按时间倒序生成 Markdown digest，通过 Telegram Bot 或邮件推送。每条保留原文链接，摘要只做辅助筛选。调度用 cron 或 systemd timer，每 30–60 分钟跑一次。状态存 SQLite，包括已处理 hash、摘要结果、推送状态，方便断点续跑和排查。

在 OpenClaw 里，如果环境支持 MCP，可以把 `fetcher`、`summarizer` 封装成 MCP server，让 Agent 按需调用。但我的建议是：**批处理管线仍然独立运行，Agent 只负责触发或查询**。把整条链路交给 Agent 编排，反而增加不稳定因素。

## 踩坑点

1. **编码问题**：`feedparser` 对某些中文源会乱码。解决：先 `requests.get(url, timeout=10)` 拿到 `response.content`，再 `feedparser.parse(content)`。
2. **URL 去重不彻底**：不同源的同一篇文章 link 可能带不同跟踪参数。规范化后再 hash，否则重复摘要浪费 token。
3. **JSON 解析失败**：即使加了 JSON mode，模型偶尔还是会输出额外文字。处理方式是解析失败就丢弃该条，并在日志里记录原文链接，不要无限重试。
4. **正文提取为空的条目**：很多 RSS 只有摘要，没有全文。`trafilatura` 抓不到就回退 summary，再不行就跳过。
5. **推送频率过高**：RSS 源更新很快时，如果每轮都推 20 条，用户会直接关通知。设置单次推送上限（比如 5 条），多余的下次再推。
6. **成本失控**：直接对全量 RSS 做摘要，一个月 token 费用可能上百美元。过滤后再摘要，单日成本可以压到几美分。

## 可复用建议

- 把管线拆成 `fetcher.py`、`filter.py`、`summarizer.py`、`notify.py` 四个独立模块，每个模块输入输出都是 JSON，方便替换 LLM 或推送渠道。
- 用 SQLite 做持久化状态，不要只靠内存。某条处理失败时，下次运行能自动跳过或重试。
- 在 prompt 里固定输出 schema，让下游格式化逻辑完全无脑。
- 保留原文链接，摘要只做降噪，不做替代阅读。
- 如果 OpenClaw 支持 MCP，把 summarizer 封装成工具可以让 Agent 在对话中按需查询某条 RSS 的摘要，但不要用它替代定时批处理。

## 总结

RSS + AI 摘要的自动化管线，核心不是“让 AI 读完所有东西”，而是**用规则过滤掉大部分噪音，再用便宜的 LLM 把剩下的压缩成可扫读的摘要**。工程上保持模块化、状态持久化、输出 schema 化，这条管线就能稳定跑几个月而不需要天天维护。

对 OpenClaw 用户来说，MCP 和 Agent 是很好的扩展点，但先把批处理管线搭稳，再考虑让 Agent 参与进来。自动化信息流的第一原则是克制：少推一点，推准一点。
