在 OpenClaw 生态里写自动化任务，迟早会遇到同一个动作被执行两次：可能是 MCP 工具调用超时后框架自动重试，可能是 Agent 判断犹豫导致重复分流，也可能是你自己调试时反复点击运行。如果任务不是幂等的，每次重复都会产生副作用——多发一封邮件、多扣一次积分、多生成一条重复记录。本文从实际工程视角梳理幂等性在自动化任务中的落地方法，帮助你让“重复执行”不会造成问题。

## 背景：重试无处不在，幂等不是可选项

当我们用插件串联自动化流程时，网络抖动、下游 API 瞬时不可用、Agent 决策不确定等因素，使得“恰好执行一次”很难保证。常见场景：

- OpenClaw 的 Agent 调用 MCP 工具，工具端响应超时，但实际操作已在远端完成，Agent 会再次调用该工具。
- 用户手动重跑某段工作流，忘记清理上次产生的部分结果。
- 定时任务被调度器意外触发两次，其间间隔不到一秒。

在这些场景下，如果能保证任务**幂等**，即执行一次与执行多次对系统最终状态的影响相同，就不需要额外的补偿逻辑。

## 问题：非幂等操作的真实代价

一个典型反例：插件“创建 Notion 文档”每次调用都会新建页面，不带唯一标记。某日 API 超时，OpenClaw 自动重试，结果用户 Notion 里多了两页一模一样的内容。更严重的案例是：扣减库存接口因重试扣了两次，导致数据不一致。

这些问题的根本原因不是重试本身，而是**操作缺少与业务语义绑定的幂等控制点**。单纯记录“是否执行过”不够，因为并发场景下仍存在竞态条件。

## 做法：落地幂等的三个关键步骤

### 1. 找出自然的幂等键

幂等键（Idempotency Key）应当唯一标识一次业务操作意图，而不是一次系统调用。可以从业务上下文里提取，比如：

- 订单编号 + 操作类型（`order-1234-refund`）
- 外部事务 ID
- 用户请求的哈希

如果没有天然业务键，就让上游在发起操作时传入一个 UUID 作为幂等键，并在重试时复用同一个。

在 OpenClaw 自动化里，可以利用 **run‑id + 工具名称 + 关键参数摘要** 生成复合键。例如在 MCP 工具实现里，要求调用方传入 `idempotency_key`，或者由框架在调度时注入当前任务实例的唯一标识。

### 2. 实现“检查-执行-记录”闭环

无论用什么存储（Redis、SQLite、远端键值服务），流程基本一致：

1. 接收请求，提取幂等键。
2. 查询该键是否已有处理记录。
3. 若有记录且操作成功，直接返回缓存的成功结果。
4. 若有记录且操作为失败/处理中，根据业务决定是返回错误还是重试。
5. 若无记录，执行实际操作，并在完成后用**原子方式**写入记录（包含状态和返回体）。

关键点：第5步的“写入记录”必须与业务操作尽可能靠近，优先使用数据库唯一约束或分布式锁防止并发重复执行。最安全的模式是将业务数据变更和幂等记录放在同一个事务里；如果业务操作是外部 API，则先通过唯一约束“占位”，再执行 API，最后更新状态。

### 3. 处理部分失败与过期回收

外部 API 返回“成功”但响应体丢失，或写幂等记录前进程崩溃，都可能导致重复执行。应对策略：

- 采用 `pending` → `succeeded/failed` 的状态转换，允许后台任务扫描长时间 `pending` 的记录并查询远端实际状态。
- 为幂等键设定合理过期时间（例如 24 小时），使用 Redis TTL 自动清理；超出窗口后的重复请求视为新操作，防止无限存储。
- 如果业务本质不支持绝对幂等（例如发送短信），可降级为“至少一次投递 + 接收方去重”，并明确在插件文档中标注。

## 踩坑记录

**并发写冲突**  
早期实现用“先查 Redis，不存在再执行”，并发下仍会重复。修复方式是改用 `SET NX` 先占位，占位失败则认为已有在处理中的请求，直接轮询结果。

**幂等键粒度过粗**  
曾用 `{tool_name}:{user_id}` 作为键，导致同一用户的不同请求互相覆盖。后来改为包含业务唯一参数哈希的键，比如 `{tool}:{user_id}:{param_hash}`，但需注意参数序列化的一致性问题（JSON 字段顺序）。

**结果缓存不一致**  
幂等返回的缓存结果可能因为下游数据变化而失真。如果业务需要实时结果，可返回“请查询最新状态”的指引，而非旧结果。

## 可复用建议

- **在 OpenClaw 插件模板里预置幂等支持**：提供一个装饰器，自动解析 `idempotency_key`，集成内存/Redis 存储选型，开发者只需实现 `_execute_once` 逻辑。
- **用 MCP 协议字段传递幂等键**：将幂等键放入工具调用的 `_meta` 字段，由中间件统一处理，避免每个工具手动解析。
- **文档承诺幂等级别**：比如“在 24 小时内，使用相同幂等键的调用将返回相同结果，不会重复创建资源”，帮助上游决策。
- **测试幂等行为**：在自动化测试中始终包含“相同输入调用两次”的用例，验证第二次调用副作用为零且返回一致。

## 总结

幂等性不是新概念，但在自动化与 Agent 重试场景下变成刚需。核心思路是**用业务标识锁定操作意图，通过原子存储保证一次处理**。遵循这个模式，你的自动化任务面对重试、并发、手动重跑时，都能保持系统状态的整洁。下次再构建 MCP 工具或插件流程时，先把幂等键设计进去，比后续修补补偿逻辑省力得多。
