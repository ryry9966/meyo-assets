## 背景

在 OpenClaw 这类 AI 工具社区中，保持内容更新频率、及时回应用户问题是运营的一大痛点。我们团队在维护一个技术问答论坛时，发现人工发帖和跟进讨论的带宽明显跟不上社区的活跃节奏。于是决定尝试用 AI 构建一个社区发帖机器人，让它承担起定时发布技术话题、自动跟进回复、采集外部资讯再格式化输出的任务。

最初的预期很简单：一个 GPT 模型 + 社区 API 就能跑通。实际落地过程中，却在可控性、内容质量、多步骤编排和排障监控上踩了不少坑。这篇文章将复盘整个过程，并给出可复用的架构建议。

## 问题拆解

社区发帖机器人不是简单地“生成一段文字然后 POST 到接口”。我们面临的具体问题包括：

1. **内容质量与风格可控**：AI 生成的内容必须符合社区调性（工程化、克制、有细节），不能广告味太浓或泛泛而谈。
2. **多源信息整合**：自动发帖不只是凭空生成，还需要从 RSS、技术博客、GitHub Trending 等源头取数据，再提炼为适合社区讨论的主题。
3. **分步执行与会话保持**：一个完整的发帖-回复流程涉及多个步骤，需要记住上下文，不能每步都重新推理。
4. **异常处理与监控**：API 调用失败、生成内容为空、触发社区风控等问题必须有兜底和告警。
5. **可扩展性**：未来可能接入更多社区或自动化任务，架构不能是硬编码的单一脚本。

## 做法 / 步骤

### 1. 总体架构

最终采用 **Agent + 工具链** 的架构：

- **调度器**：基于 cron 定时触发任务，负责启动一次完整的发帖/回复流程。
- **任务编排引擎**：一个有限状态机，管理“获取素材→筛选→草稿生成→审核→发布→记录”的流转。
- **AI Agent**：通过 OpenAI 兼容接口调用本地或远端模型，用系统提示词严格限定输出风格和结构。Agent 可使用外部工具（RSS 解析、网页抓取、社区 API）完成多步操作。
- **工具层**：封装通用操作，如 `fetch_rss`、`search_github_trending`、`create_post`、`reply_to_post`，以及一个内部自检工具 `validate_content`。
- **日志与告警**：每个步骤记录耗时、返回状态码与摘要，异常时通过 Webhook 推送到内部通知群。

### 2. 提示词与输出控制

我们的一条核心经验是：**把提示词写成规范文档，而不仅是自然语言指令**。在系统提示词中明确了：

- 标题字数、必须包含的技术关键词；
- 正文必须分段，每段有明确功能（背景、步骤、注意事项）；
- 禁止使用感叹号、营销话术，语气保持在“冷静的同事分享”水平；
- 如有引用来源，必须在文末附链接。

同时使用 **结构化输出**（如 JSON 模式或 function calling）强制 Agent 返回 title、body、tags 等字段，避免需要正则匹配的不可靠解析。

### 3. 多步骤任务编排

一次典型的“从 GitHub Trending 生成发帖”任务如下：

1. 调度器触发 `daily_trending_post` 任务。
2. 编排引擎调用 `fetch_github_trending` 工具获得当日热门仓库。
3. Agent 筛选出与社区方向相关（例如 AI 工程化、Agent 工具）的 3 个仓库。
4. 对每个仓库调用 `fetch_readme_summary` 获取项目摘要。
5. Agent 综合信息生成一篇推荐帖草稿，调用 `validate_content` 工具自检。
6. 草稿经人工审核（或次级规则引擎）后，调用 `create_post` 发布。
7. 发布成功后记录消息 ID，并计划在 2 小时后调用 `reply_to_post` 进行互动。

所有步骤的状态都保存在任务上下文中，即使中途异常退出也能恢复或重试。

### 4. 社区 API 的接入与限速应对

社区 API 通常有频率限制和鉴权要求。我们在工具层实现了：

- **请求队列**：控制并发，确保不超过每秒请求数。
- **指数退避重试**：遇到 429 或 5xx 错误自动等待后重试，最多 3 次。
- **幂等性保护**：通过去重键避免重复发帖（如基于标题+日期的哈希）。

## 踩坑实录

1. **模型幻觉导致虚构链接**
   早期 Agent 生成帖子时，会自行编造“参考链接”且看起来很真。解决方案：强制要求所有链接必须来自工具实际抓取的数据，并在 `validate_content` 工具中检查 URL 是否存在于工具返回的原始列表里。

2. **任务上下文丢失**
   在多步调用中，如果每次只给模型当前步骤的输入，它容易遗忘前几步的约束。改进方案：使用任务级的上下文变量，每一步都将前置信息显式注入提示词，并保留关键输出作为后续步骤的参考。

3. **内容审核误杀**
   社区有敏感词过滤，AI 生成的正常技术术语偶尔被拦截（如某些 CVE 编号或特定库名）。解决：在发布前增加一层白名单替换规则，将已知被误杀的关键词用全角或零宽字符临时包装，发布后前端渲染时再还原。当然这需要与社区管理方协商。

4. **时间感知偏差**
   模型训练数据有截止日期，生成帖子的“最新”内容可能是过时的。我们通过工具注入当前日期和事件时间戳，并要求模型明确声明信息获取时间，避免误导读者。

## 可复用建议

- **从最小闭环开始**：先实现单一来源的定时发帖 + 日志，验证整个链路，再拓展工具和多步编排。
- **把提示词当作代码管理**：版本化提示词，进行 A/B 测试，记录每次改动对内容质量的影响。
- **工具接口统一化**：所有外部工具遵循相同的入参/出参规范，返回结构化 JSON 并包含错误码。这能让 Agent 自主选择和处理异常。
- **建立人工抽检机制**：即使是全自动流程，也保留一个待审核队列，定期抽检输出，并据此迭代提示词与规则。
- **监控更要监控“无输出”**：失败重试之外，更要关注“任务静默失败”的情况（例如爬虫返回空列表、Agent 判定无合适内容而跳过），这里容易积累信息盲区。

## 总结

用 AI 搭建社区发帖机器人，技术上并不复杂，但工程化落地的关键在于控制生成质量、编排多步骤任务、以及建立可靠的异常处理与监控体系。我们的实践表明，Agent+工具链的架构在灵活性和可维护性上都优于单一脚本，配合严格的提示工程与结构化输出，能够让机器人在保持社区调性的同时真正分担运营压力。

后续的迭代方向是引入用户反馈信号（点赞、回复数）作为质量评估，自动优化提示词和选题策略，让机器人越用越聪明。
