# LLM 输出解析的防御性编程：JSON 与标签格式混合处理

## 背景：当模型输出不再“听话”

在 OpenClaw 生态中，我们大量依赖结构化输出：Agent 调用工具需要严格 JSON，插件间传递消息常约定为 XML 标签或 Markdown 代码块。理想很丰满——设定 `response_format: { type: "json_object" }`，模型乖乖返回纯 JSON。但现实是，哪怕强如 GPT-4，在长上下文、复杂指令下也会返回“半结构化垃圾”：JSON 外包裹说明文字、Markdown 代码块内嵌套 XML 标签，甚至输出 `{'tool': ...}` 这种类 Python dict。

更棘手的是，MCP 服务器或自动化节点往往只消费单一格式，一旦解析失败，整个流水线中断。我们不得不面对一个工程真相：**把 LLM 当成不可靠的外部 API，用防御性编程兜底**。本文总结一套实战中行之有效的混合格式解析策略，聚焦 JSON 与标签（XML/Markdown）交织的场景。

## 问题：混合输出有多乱？

典型脏输入可能长这样：

```
我需要调用工具来查询天气。
```json
{
  "tool": "weather",
  "args": {
    "city": "Beijing"
  }
}
```
另外，我还需要输出<thinking>用户要求查询天气，我需要使用天气工具</thinking>。
```

这堆文本同时包含：自由文本说明、Markdown 代码块包裹的 JSON、XML 标签 `thinking`。单一解析器直接挂掉：`json.loads` 遇到前导文字抛异常，正则提取标签可能匹配到代码块内的假标签。

更隐蔽的问题是，某些模型会在 JSON 值内部插入未转义换行或注释，比如 `{"tool": "weather", // 调用天气}`，JSON 解析器直接崩溃。

## 做法：分层清洗 + 上下文感知提取

放弃一步到位的解析，改用管道式处理：

### 1. 输入预处理：建立统一基线
- 移除常见干扰：首尾空白、BOM 头、对话前缀（如 “Assistant:”）。
- 统一换行符为 `\n`。
- 若有明显对话包裹，尝试切掉第一个 `{` 或 `<` 之前的文本——但保守执行，避免误删。

### 2. 混合解构：分离不同格式片段
不在一棵树上吊死，用多个提取器并行尝试，按优先级取值：

**（1）Markdown 代码块提取**
优先查找 ````json ... ```` 或 ` ``` ... ````。正则 `r'```(?:json)?\s*([\s\S]*?)```'` 可捕获内容。如果存在多个，默认取第一个（或按位置接近期望字段）。提取后尝试 `json.loads`，失败则进入修复流程。

**（2）直接 JSON 查找**
用 `r'\{[\s\S]*\}'` 匹配最外层花括号，但要处理嵌套。更好的方式是找到第一个 `{` 和最后一个 `}` 的配对位置，使用一个括号平衡算法提取。对于类 Python dict 格式，可先用 `ast.literal_eval` 安全解析（注意真/假/空值需要替换为 Python 关键字）。

**（3）XML 标签提取**
针对 `<tool>...</tool>` 之类，用正则 `r'<(\w+)>([\s\S]*?)</\1>'` 收集所有标签内容转为字典。注意：若 JSON 内嵌标签，优先以 JSON 解析结果为准，避免重复提取。

### 3. JSON 修复流水线：专治各种小毛病
提取到疑似 JSON 字符串后，不要直接 `json.loads`，而是送入修复器：

- **移除尾随逗号**：JSON 对象或数组最后一个元素后的逗号是不合法的。正则 `r',\s*([}\]])'` 替换为 `$1`。
- **处理注释**：移除 `//` 和 `/* */` 风格注释（单行和多行）。注意字符串内的 `//` 不要误删，最好在非引号场景生效。
- **转义控制字符**：将字面换行替换为 `\n`，确保在字符串内。
- **修复单引号**：若整个字符串使用单引号，统一替换为双引号，并处理内部转义。
- **尝试多种解析器**：内置 `json.loads` → `json.loads(..., strict=False)` → 回退到 `demjson3` 或 `json5` 库。生产环境建议引入 `json5`，容忍注释、尾逗号、裸键等非标准语法。

### 4. 结果整合与优先级
定义清晰的结构化输出，如期望 `{"tool":..., "args":..., "thinking":...}`。整合规则：
- 如果从代码块或直接 JSON 成功解析出 `tool` 字段，则使用该 JSON。
- 缺失的 `thinking` 从 XML 标签补充。
- 若两者冲突，以 JSON 为准；若 JSON 不全，则尝试从其他格式片段补齐，并打日志标记降级。

## 踩坑点：工程中反复遇到的痛

- **贪婪匹配导致误吞**：提取最外层 json 时，`r'\{[\s\S]*\}'` 会匹配到字符串中后面的 `}`。必须实现括号计数法，确保成对匹配。
- **模型输出“类 JSON 但非 JSON”**：常见场景是 Python 字典格式，如 `{'tool': 'weather', 'args': {'city': 'Beijing'}}`。直接用 `json.loads` 失败，`ast.literal_eval` 虽可行，但需先替换 `None/True/False` 为 `None/True/False`（注意安全）。
- **XML 标签与 Markdown 冲突**：有的模型在代码块内写成 `<tool>xxx</tool>`，而外面同样有标签。提取时需限定上下文：如果代码块内部已解析出 JSON，就不再从其内部提取标签，避免重复。
- **修复器引入二次错误**：例如粗暴的正则 `',\s*}'` 替换会破坏字符串内的 `,}`。务必先识别字符串边界，仅在字符串外操作。可先用 `json.loads` 尝试，记录异常位置，定点修复，而不是全局正则清扫。

## 可复用建议：封装成 OpenClaw 中间件

把上述逻辑封装为一个 Python 工具函数 `parse_llm_hybrid_output(text, expected_schema=None)`，返回干净字典与元数据（来源、污染等级）。在 OpenClaw 的 Agent 循环或插件管道中，插入此解析器作为前置步骤，所有 LLM 响应都经过它处理。

测试集一定要包含以下极端样本：
- 前后带有长篇对话的 JSON
- 内嵌注释、尾逗号的 JSON
- Python 字典格式
- JSON 内包含未转义换行
- 多个 Markdown 代码块，只有第二个才是目标
- 缺少预期字段的破损 JSON

避免在解析逻辑里硬编码字段名，使用 `expected_schema` 做校验与补全，但允许降级返回部分字段，防止全有或全无导致的流程频繁中断。

## 总结

把 LLM 输出解析当成信号处理而非纯语法分析，心态上从“严格要求”转向“防御性宽容”。核心原则：**分层清洗、多路提取、修复优先、降级兜底**。在 OpenClaw 这类高度依赖 LLM 串联的系统中，稳固的解析层是自动化链条不断裂的基石。你花费在解析上的每一行代码，都会在凌晨三点的生产报警中给你回报。
