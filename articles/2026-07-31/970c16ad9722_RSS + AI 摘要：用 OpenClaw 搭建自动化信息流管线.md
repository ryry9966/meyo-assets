## 背景

信息过载不是什么新话题，但每天打开几十个 RSS 源、扫标题、点进文章、判断是否值得细读，这套动作累加起来依然消耗极大。RSS 本身解决了“聚合”问题，却没有解决“筛选和消化”问题。我们希望构建一条自动化管线：定期拉取订阅源、提取全文、生成高质量中文摘要，最终将一份浓缩简报投递到日常使用的终端（比如飞书、Telegram 或 Obsidian Daily Note）。整条管线应尽量少维护、可观测、可复用，并且成本可控。

社区里关于 Agent + 插件的讨论很多，本文就以 OpenClaw 为调度核心，结合 MCP 工具实现这条管线，给出工程化的搭建思路与真实踩坑记录。

## 核心问题

一键生成 RSS 摘要的工具并不少，但普遍存在三个痛点：

1. **全文抓取不稳定**：很多 RSS 源只输出截断内容，依赖第三方全文提取时经常遭遇反爬、付费墙或页面结构变更。
2. **摘要质量良莠不齐**：如果只是把标题缩短，价值不大；要让 AI 从中提炼关键信息，需要细致的 prompt 工程和模型选型。
3. **状态管理与错误恢复**：数百个源每天产生几千篇文章，如何避免重复处理、如何在部分源失败时不中断整条管线，且能事后重跑，这些都是工程上的硬骨头。

本文的方案会直面这几个问题。

## 实现步骤

### 1. 整体架构

整条管线大致分为四层：

- **采集层**：通过 RSSHub / Miniflux 统一管理订阅，输出标准 Feed。
- **提取层**：对每个条目，使用可配置的全文提取器（Mozilla Readability 封装或基于 headless 浏览器的 fallback）。
- **摘要层**：调用大模型（gpt-4o-mini 成本与质量平衡较好）进行结构化摘要，输出固定字段：核心观点、关键数据、可行动项。
- **分发层**：将摘要写入本地 Markdown，并通过 Webhook 推送到目标渠道。

OpenClaw 在这一架构中的角色是流程编排器：以定时任务触发 Agent，Agent 按顺序调用挂载的 MCP 工具完成上述四步，并负责状态持久化与错误处理。

### 2. OpenClaw Agent 配置要点

可以定义一个专门的信息摘要 Agent，挂载三个主要 MCP 工具：

- `rss-reader`：负责拉取指定时间窗口内的 Feed 条目，返回标准化 JSON。
- `full-text`：输入 URL，输出正文纯文本及元数据，内置重试与降级逻辑。
- `ai-summarizer`：通过 OpenAI 兼容接口调用模型，接收系统提示词和待处理文本，返回结构化摘要。

任务定义（Job）设置为每 6 小时或每天早 7 点执行一次。在工作流内部，Agent 会维护一个 `processed_urls` 集合（存储在 SQLite 或 OpenClaw 的状态管理器），每处理一条文章前先检查是否已存在。这样做到了幂等性。

关键技术细节：

- **去重粒度**：不能仅依赖 URL，有些站点会携带无意义的 `utm` 参数，需要标准化后再落盘。
- **批量调用**：为避免单篇文章频繁触发 API，将所有待处理条目积攒到一定数量后以 batch 方式调用 LLM，既节省成本也降低速率限制风险。
- **摘要提示词设计**：经过多轮调试，最终采用的提示词要求模型必须输出「3 个核心要点（每条不超过 40 字）」+「是否有具体数据或案例（若有，简要说明）」+「是否值得深读（是/否）」。严格限定输出长度，能有效避免模型自行发挥，也让最终简报简洁可用。

### 3. 全文提取的降级策略

全文提取是最容易翻车的环节。实践中我们设计了三级降级：

1. 优先使用 RSS 源中的 `content:encoded` 字段，如果已经包含超过 500 字的正文，直接使用。
2. 否则调用基于 Mozilla Readability 的提取服务（我们用过自部署的 `postlight/parser`，现在更倾向使用 MCP 工具封装好的 fetch+解析链路）。
3. 如果前两步都失败（超时、被拦截、返回空白），则记录错误，跳过该条目，并在汇总报告中注明失败 URL。重要的是 **不要阻塞后续条目**。失败条目可在下次调度时自动重试（设定最多重试 3 次）。

另外，一些反爬严重的媒体（如付费墙后的外媒）需要单独配置 session cookie 或使用 RSS 源内嵌的摘要代替全文，否则永远无法提取。这是一个需要持续维护的配置点。

## 踩坑记实

### 坑 1：全文提取超时拖垮整个 Agent

最初没有设置单条提取的超时时间，某一天某个源响应极慢，导致 Agent 任务卡死超过 30 分钟，后续所有摘要都无法生成。后来在工具调用层强制加入 15 秒超时，并且 Agent 配置了 `max_step_duration`，问题解决。

### 坑 2：摘要模型“点评化”

早期使用默认的系统提示词时，模型倾向于输出类似“这篇文章很有意思，推荐大家阅读”的社交媒体风格评语，完全不满足信息压缩的需求。调整为严格的角色设定（“你是一个专业的研究助理，必须提取事实性信息”）并限定输出格式后，风格才稳定下来。

### 坑 3：成本失控错觉

刚上线时，看到每天几千次 API 调用吓了一跳。实际结算后发现，gpt-4o-mini 处理 2000 篇文章的成本不到 1 美元，但心理冲击很大。建议在 Agent 中加入每日调用量统计和费用预估，有助于建立理性预期。

### 坑 4：RSSHub 自建不银弹

社区大量使用 RSSHub 扩展源，但自建实例需要持续更新规则，且常因上游改动而失效。非核心源可以接受部分失效，而关键信息源建议使用更稳定的商业 RSS 服务或直接订阅 Newsletter 的邮件侧入口。

## 可复用建议

1. **组件化设计**：将“采集-提取-摘要-推送”四个环节抽象成独立的 MCP 工具，便于替换。例如，某天想换成本地部署的 Qwen 模型做摘要，只需替换 `ai-summarizer` 工具的后端，其余部分无需变动。
2. **分级推送**：不是所有摘要都需要即时触达。可以设定：重要源（含“是否值得深读”标记为“是”）推送即时消息，普通摘要仅写入每日汇总，减少打扰。
3. **利用社区已有插件**：OpenClaw 社区已有 RSS、全文提取等工具包装，避免重复造轮子。启动一个新的管线时，先搜索现有 MCP 服务器，能节省大量时间。
4. **可观测性前置**：在 Agent 中埋入简单的健康指标——每日处理篇数、失败率、API 延迟——以 Webhook 形式发到同一个频道，方便监控管线是否“活着”。

## 总结

RSS + AI 摘要这条管线一旦跑通，每天的阅读体验会有质的变化：从“焦虑地刷标题”，变成“花 5 分钟看一下结构化要点，再决定是否点进原文”。在 OpenClaw 这类 Agent 框架的支撑下，整条链路的工程化难度大幅降低，重点反而落在 prompt 调试和错误降级这些软性工作上。

目前我们的管线已稳定运行三个月，每日处理约 400 篇文章，最终浓缩为不到 50 条关键摘要，信息摄入效率明显提升。如果你也在搭建类似系统，建议从最小源集开始，逐步打磨摘要风格与稳定性，再慢慢扩展订阅规模。
