一条反直觉的建议正在开发者社区疯传——Claude Code的项目负责人（圈内戏称为“Claude Code之父”）公开表示：每半年就应该清空一次 claude.md、skills 和 hooks，因为“模型自己会想办法”。这句话让很多把提示词当成精密咒语来打磨的工程师瞬间破防。我们花了大量时间调教的“思维外衣”，竟然成了需要定期卸下的负担？今天从原理层面拆解，为什么定期遗忘，反而能让编程助手变得更强大。



## 那些被清空的对象到底是什么
在 Claude Code 这类编码智能体里，有三样东西构成了开发者对模型行为的深度定制：

- **claude.md**：项目级“记忆文件”。里面通常写明了角色定义、代码风格、技术栈偏好、文件结构规范，甚至包括“不要用 jQuery”这类硬性约束。它类似于一个长期 system prompt，让模型一上来就知道自己在该工程中的位置。
- **skills**：可插拔的自定义能力模块。比如写一个「自动生成测试用例」的 skill，或者「调用某个内部 API 格式转换」的 skill。它们相当于给模型装了专门的“技能插件”，让它在特定任务上立竿见影。
- **hooks**：生命周期回调脚本。在模型输出前后自动触发，比如提交代码前跑 lint、输入请求时做敏感信息过滤、生成回答后追加监测日志。它们构建起一套自动化流水线。

这三者合在一起，就是一套精心调校的“软体外骨骼”。一方面它们极大提升了日常效率，但另一方面也埋下了越来越重的认知债务。

## 为什么必须定期清空？——认知债务的四个面孔

从认知科学和语言模型的机制来看，长期不变的自定义层会带来四种隐藏退化。这也正是 Claude Code 之父建议半年一清的逻辑内核。

1. **上下文污染——“迷失中间效应”的放大器**  
   大模型的上下文窗口看似能到 200K token，但有效注意力并不均匀分布。大量研究指出，当关键信息被埋在冗长上下文的中间部分时，模型容易忽略或遗忘它们。一份经过数月增补的 claude.md，往往塞满了无关注释、历史遗留的注意事项和不再适用的规则，反而把真正重要的任务描述推到了注意力边缘，直接拉低输出质量。

2. **路径依赖与技能僵化**  
   每一个 skill 和 hook 都是围绕当时的需求写的。半年后项目结构可能已经大变，但旧函数依然躺在那里。模型在决策时，会被这些熟悉的老路径吸引，倾向于调用历史遗留 skill 而不是去推理更优的新方案。比如一个为 Vue 2 写的代码生成 skill，在迁移到 Vue 3 时反而让模型输出过时的写法，抑制了自身对 Composition API 的泛化能力。

3. **抑制底层模型迭代收益**  
   半年时间里，基础模型往往已经经过了数次更新，内建能力大幅增强。过去需要用 hooks 强行补齐的逻辑，现在模型本身就能完成；过去必须写在 claude.md 里的规则，现在只需一句自然语言指令。如果不把这些“拐杖”拿走，你实际上是在用旧模型的上限，拖累新模型的下限。

4. **对抗性残留与不确定行为**  
   多轮交互中累积的临时 hooks，可能产生设计者都没预料到的互作用。尤其那些带副作用的回调，一旦触发条件变得模糊，就会像隐形的开关一样，让模型行为飘忽不定。定期清空等于给系统做一次软复位，把这些不可控的残留一次性抹掉。



理解了“为什么要忘”，更核心的问题是——忘记之后，模型真的能“自己想办法”吗？

## 清空之后，智能如何被重新释放
现代的强推理模型本来就具备少样本指令遵循和任务拆解能力。在没有那堆自定义“拐杖”时，它的行为反而更接近预训练阶段习得的通用知识图谱。你会看到三个显著变化：

- **从执行者变为规划者**：没有 skill 可调用，模型会拆解需求，写出最基础却最通用的代码结构，然后像人类一样现场设计解决方案，而非匹配历史模板。
- **回归第一性原理**：例如处理数据格式，失去定制的转换 skill 后，模型会直接利用标准库和语言特性从零构建流程。虽然第一步可能显得笨拙，但方案往往更健壮，不依赖过时的封装。
- **灵活的思维链探索**：Claude Code 内置的思考过程在轻量提示下能尝试更多分支路径，不被 hooks 预设的流水线束缚，反而可能发现更优的解法。

这背后是一条已经被多个实验验证的原理：对强模型而言，**最小必要上下文 + 清晰的任务边界**，往往优于一份滴水不漏却臃肿的说明书。

当然，这并非放之四海皆准的教条。清空操作有其明确的适用边界，盲目的“断舍离”一样会制造麻烦。

## 清空不是万能药：需要拿捏的平衡
不是每个场景都适合半年一清。对于以下情况，彻底清空可能得不偿失：

- 需要严格遵循内部安全规范或法律合规要求的项目；
- 多人协作的大型 monorepo，claude.md 充当团队编码约定的唯一载体；
- 某些 skills 封装了复杂且不经常变动的业务逻辑，重写成本极高。

正确的思路不是扔掉一切，而是建立“精简化—备份—测试”的周期机制。清空更像是园艺剪枝，而不是烧掉整个花园。

最终落到日常工程实践里，可以沉淀为三条可立刻用起来的建议。

## 三条务实建议：从今天起管理你的“模型记忆”

1. **Git 化你的记忆文件**  
   把 claude.md、skills、hooks 像源代码一样纳入版本管理。半年清空前在独立分支上做归档，清空后从最精简的必要项重新注入。这样既不怕丢失，又能对比前后模型行为的差异。

2. **坚持“最小必要原则”写作**  
   写下任何一条提示之前，问自己：“去掉这句话，模型自己会推理出来吗？” 凡是模型能在标准技术栈内自行判断的内容——比如通用代码风格、语言版本选择——就大胆留白。只保留必须由人类给定边界的信息，例如内部 API 域名、非公开的业务术语。

3. **渐进式淘汰，而非休克式清零**  
   不要一口气删光所有内容。先注释掉半年来未改动过的部分，运行一组覆盖核心场景的评估用例，观察模型的输出是否退化。如果稳定，再逐步删除，最终只留一张干净的精简卡片。这样可以在不中断工作流的情况下完成“记忆升级”。



## 冷思考：给提示工程做一次祛魅
Claude Code 之父的建议，本质上是对“过度提示工程”的一次温和反击。我们曾拼命往模型脑子里塞东西，以为那是驾驭强大智能的唯一方式。但技术的前进方向恰恰相反——模型越强，越需要自由思考的空间。半年清空一次记忆，不是强迫模型忘记过去，而是让每一行代码都重新回到它最本真的推理起点。或许，与模型的协作也该遵循一条朴素原则：**少一点咒语，多一点信任**。
