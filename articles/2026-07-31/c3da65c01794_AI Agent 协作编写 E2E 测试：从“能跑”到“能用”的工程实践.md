## 背景

端到端（E2E）测试是保障关键用户路径可用的最后防线，但编写和维护成本极高。一个登录流程的测试脚本，往往需要处理元素等待、选择器稳定性、跨环境数据隔离等问题。大型模型在生成单段代码上已表现不错，但直接让它输出一个可稳定运行的 E2E 测试脚本，仍然容易掉进“看起来对但跑不起来”的陷阱。尤其是当页面结构稍微复杂，模型幻觉会导致选择器失效、步骤遗漏或断言错位。

在 Agent 协作成为主流实践后，我开始尝试将“编写 E2E 测试”拆解为多个角色合作完成的任务链，而不再是单一 LLM 的一锤子买卖。这套流程在 OpenClaw 及 MCP 工具的支撑下，已经能够半自动地产出达到合入标准的 Playwright 测试用例。

## 问题

单一 Agent 的局限主要有三点：  
1. **缺乏真实页面上下文**：模型只能依赖训练数据中见过的静态结构，无法知晓当前被测系统的实际 DOM。  
2. **选择器脆弱**：自动生成的 CSS 或 XPath 选择器往往依赖过于具体的层级，稍一改动就挂。  
3. **错误修复能力弱**：出现失败时缺乏回溯页面状态并调整步骤的能力，只能人工介入。

我们需要一个能够**观察、生成、运行、修正**的闭环，这正是多 Agent 协作的长处。

## 做法：三 Agent 协作管线

我把流程拆成了三个 Agent 角色，通过文件系统 MCP 和 Shell MCP 串联，构成一条可循环的流水线。

### 1. Browser Reader Agent

职责：根据测试场景描述，操作浏览器进入目标页面，提取关键交互元素的属性和操作路径。  
工具链：Playwright MCP Server（提供 `navigate`、`snapshot`、`click` 等能力），配合视觉模型截图作为辅助定位。  
输出：一份结构化的 `page_map.json`，包含页面元素的可信选择器（优先 `data-testid`、`aria-label`，其次语义化 CSS）、操作类型和所需输入数据。

### 2. Test Writer Agent

职责：结合测试用例描述和 `page_map.json`，生成完整的 Playwright 测试脚本。  
关键点：  
- 使用 `page.waitForSelector` 或 `locator.waitFor()` 增加显式等待，而非假设元素立即出现。  
- 断言不仅检查可见性，还核对文案、URL、API 响应等。  
- 脚本结构遵循项目约定的 Page Object 或 fixture 模式，方便融合进已有测试套件。

### 3. Test Runner & Fixer Agent

职责：执行生成的脚本，捕获错误并分析原因，然后调起 Writer Agent 进行修正。  
流程：  
- 通过 Shell MCP 运行 `npx playwright test` 并收集输出。  
- 如果失败，提取错误行号、失败截图和 DOM 快照，拼装成反馈上下文发给 Writer。  
- Writer 根据错误类型（如“locator not found”、“timeout”）修正选择器或增加等待逻辑，再交给 Runner 重跑。  
- 设定最大迭代次数（通常 3 次），超过后保留差异记录交人工处理。

这些 Agent 之间的对话历史和中间产物都通过 JSON 文件在本地持久化，避免上下文断裂。MCP 提供的标准化接口让工具调用与模型解耦，更换底层浏览器驱动或测试框架时改动很小。

## 踩坑点

1. **动态列表和异步渲染**  
   对于无限滚动或延迟加载的列表，首次 snapshot 拿不到全部元素。解决办法是让 Browser Reader 在执行操作前插入“滚动到底部并等待网络静默”的原子步骤，并将此模式写入生成指令。

2. **跨环境数据污染**  
   生成的测试如果需要登录，账号信息容易硬编码。我们通过环境变量注入和 MCP 的“读取环境配置”能力，强制所有账号数据走外部注入，测试脚本中只引用变量名。

3. **过度拟合单次执行**  
   如果 Writer 只根据 Runner 的一次失败修改脚本，容易写出只对当前 session 有效的脆弱逻辑（例如依赖临时 token）。因此修正时必须要求 Writer 给出修改的“通用性说明”，并由另一个 Agent（可以是同一模型不同提示词）进行审查，判断是否针对了根因而非表象。

4. **选择器策略不统一**  
   我们强制约定优先使用 `data-testid`，如果页面未埋点，则由 Browser Reader 尝试用 AI 为关键元素生成建议的 `testid` 并写入前端代码仓库的 issue，推动开发侧配合。这一步虽然慢，但长期收益巨大。

## 可复用建议

- **封装为可配置流水线**：将三个 Agent 的提示词模板化，通过参数指定测试框架（Playwright/Cypress）、断言风格、截图策略等，适配不同项目。  
- **建立组件操作库**：对高频组件（表格、表单、弹窗）总结出标准选择器和交互流程，作为 few-shot 示例注入 Writer 的上下文，大幅提升生成质量。  
- **引入人工门禁**：生成完毕但尚未合入的测试，必须经过一次人工 review，重点关注断言是否完备，以及是否存在因页面改动导致的隐性失效。  
- **结合视觉定位兜底**：当基于 DOM 的选择器全部失败时，启用截图+视觉模型定位元素坐标进行点击，虽然速度慢，但能保证流程不会被琐碎 UI 变更卡死。  

## 总结

让 AI Agent 协作写 E2E 测试，并不是追求零人工，而是把机械的定位、编写、重试工作交给机器，让测试工程师聚焦在用例设计和边界思考上。这套方案在多个实际项目中已经跑通，平均能将一个新页面主流程的测试产出时间从小时级压缩到 20 分钟以内，且稳定性因强制使用 `data-testid` 而高于手写脚本。

真正落地的关键是：不要指望单个 Agent 一步到位，接受反馈闭环、持续沉淀工程规范，才能让 AI 辅助的测试从“能跑”进化到“能用”。
