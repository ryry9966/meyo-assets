## 背景：当 Agent 开始替你在公网“说话”

近半年，基于 MCP 协议的 Agent 自动化工作流在开发者和社区运营者中迅速普及。很典型的场景是：通过 OpenClaw 这类工具将 Agent 接入 GitHub Issue、Discord 频道、飞书话题群，自动响应 issue 处理、FAQ 回复、文档检索与社区问答。Agent 不再只是内部 Copilot，而是 *公共场域的数字化身*。

但问题也随之浮现。Agent 被赋予阅读私密代码库、内部文档、敏感日志、任务看板的权限后，它可能在全自动化流转中，把不该对外说的内容，粘贴到公共 issue、公开发帖或即时消息中。这已不是猜测——我们在若干闭门交流中都听到过真实事故：某团队 Agent 在回答用户问题时，把内部错误堆栈中含有的 Slack webhook URL 原样贴出，导致频道被垃圾消息灌满；另一个案例中，Agent 在公共 issue 中复述了未公开的功能规划，源自它读取了 Notion 内部产品路线图。

这一次，我们认真聊清楚 Agent 安全红线的问题根源、可落地的工程方案，以及那些容易踩的坑。

## 问题拆解：泄露链条长什么样

Agent 泄露信息很少是单一漏洞，更多是**权限面、工具链、输出通道**三者耦合的产物。

1. **过宽的上下文注入**。为了让回答更精准，开发者常把整篇内部文档、本周迭代计划、甚至完整日志 dump 塞进 prompt。Agent 并不理解“保密”边界，它只会基于上下文生成最相关的回答。
2. **工具调用无读写分离**。Agent 通过 MCP 服务器调用文件系统、数据库、接口。如果读工具没有范围限制，Agent 就能在回答用户“这个 bug 怎么修”时，自己跑去读取内部 config.yaml 并引用其中的 token 或 API key。
3. **输出面缺乏护栏**。从生文到执行回复可能是一条全自动链路。Agent 在 Discord 频道里直接回复用户，中间没有审核节点。更隐蔽的是，Agent 可能把内部信息以“代码块示例”的形式发出去，看似无害，实则是真实配置。
4. **Agent 对输出渠道缺乏区分意识**。一个通用 agent 可能既有私有的 debug 频道，又对接公共支持频道。它无法自行判断当前会话属于“公开发言”还是“内部诊断”。

## 工程做法：以 OpenClaw + MCP 为例的防御分层

我们不会推某个特定产品，只基于通用架构给出分层防御，可复用到大部分 Agent 编排框架。

### 第一层：最小化的上下文构造

给 Agent 构建提示词时，**坚持“回答该问题所需的最小上下文”**。对于可能含敏感信息的文档，采用检索增强生成（RAG）时，配置 chunk 级别过滤：

- 用元数据标签标记文档密级（如 `internal`, `confidential`）。
- 在检索阶段加入过滤器，对接公共用户的 Agent 仅检索 `public` 标记的文档。
- 在 prompt 中明确指令：“你绝对不应重复或引用任何带有机密标记的内容。如遇到此类内容，回复‘此问题无法在公开渠道回答’。”

踩坑点：很多人直接把向量数据库所有 chunk 都暴露给检索，以为“靠模型自觉”就行，这基本等于没有防线。

### 第二层：工具级权限控制（MCP 服务器侧）

如果你的 Agent 通过 MCP 服务器连接内部系统（GitHub, 数据库, 文件服务器），建议**为不同角色创建不同的 MCP 服务实例**：

- `mcp-public` 实例：只暴露公开文档源、公开 API，禁止任何写操作。
- `mcp-internal` 实例：供内部机器人使用，具备更高权限。

OpenClaw 的场景下，可以在 agent 定义中绑定特定 MCP 端点。切勿将内部和外部对话的 agent 指向同一个 mcp server。

此外，在 MCP 工具的描述中，可以增加提示：“该工具返回的数据可能包含内部信息，禁止在公共回复中原样输出”。这虽然依赖模型遵循指令，但能显著降低概率。

### 第三层：输出护栏与审核管道

对于面向社区的 agent，**永远不要直接从模型输出发送到公开频道**。中间加入一个轻量审核管道：

- **基于模式匹配的掩码**：编写正则屏蔽手机号、邮箱、token、API key 模式。可以在输出前自动替换为 `[REDACTED]` 并告警。
- **关键词告警**：检测输出中是否包含内部项目代号、域名、IP 地址、内部路径等。命中后临时拦截，转人工审核。
- **置信度阈值**：部分框架支持获取模型输出 token 的 logprobs。如果模型在输出可能敏感的片段时不确定，可以配置规则：当输出中出现内部关键词且 logprob 异常时，拦截。

踩坑点：不要只依赖 AI 预检。让另一个 LLM 去判断是否泄露，会增加延迟和成本，且可能泄露给审核模型本身。规则引擎虽生硬，但确定性高。

### 第四层：隔离的环境与可观测性

所有 Agent 交互日志必须持久化，并区分会话类型（internal / public）。配置告警规则：当公共会话的 agent 执行了读内部文件的工具调用（可通过工具名过滤），立即触发安全通知。

同时，为 Agent 设置**人工回退机制**：在无法确定信息是否可公开时，回复模板引导用户开内部工单，而不是冒险回答。

## 踩坑记录（来自真实实践）

- **日志系统自身泄露**：有人将 Agent 的完整 trace 发到 ELK，而 Kibana 仪表板又面向较宽团队。某次故障排查时，有人把包含内部 API 返回值的 trace 截图发到公共 issue。注意：安全不仅要管 Agent 本体，还要管围绕它的监控与排障链。
- **社区托管平台的数据残留**：Agent 在公共频道发送的内容可能被搜索引擎收录。即使很快删除，缓存、Wayback Machine 仍会留存。防御必须在发送前。
- **多模态 Agent 的新风险**：如果 Agent 能读取截图并描述，可能将内部看板截图内容转述成文本发出。这比代码引用更难检测。建议直接禁用公共 Agent 的多模态读图能力，除非确有必要。

## 可复用建议清单

1. 为每个 Agent 身份明确“公共”或“内部”标签，并在系统 prompt 中写死。
2. 公共 Agent 只能访问内容源中明确标记为 public 的分区。
3. 配置 MCP 服务器时，做好读写分离和域隔离，不为便利而共用一个实例。
4. 强制所有公共回复通过规则引擎，至少包含基于正则的敏感信息清洗。
5. 建立 Agent 行为审计日志，设置异常工具调用的报警。
6. 团队内定期做“Agent 红队测试”：刻意用诱导性提问测试是否外泄内部信息。

## 总结

Agent 安全不是“加一把锁”的问题，而是需要在数据层、工具层、输出层和运维层设置多道防线。对于面向社区的自动化 agent，**默认不信任模型能靠常识保密**，用工程手段强制最小权限、输出过滤和人工兜底。随着 MCP 生态的扩大，工具链会更复杂，但安全的第一性原理不变：不让 Agent 看到它不该看的，不让它能发出去不该发的。越早把防线做进工作流，未来重构成本越低。
