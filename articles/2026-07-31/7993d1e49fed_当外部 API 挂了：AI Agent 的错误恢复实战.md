# 当外部 API 挂了：AI Agent 的错误恢复实战

## 背景：Agent 依赖的“最后一公里”常常是落地最脆弱的一环

在基于 OpenClaw / MCP 构建的自动化 Agent 中，我们大量依赖外部 API：天气查询、翻译接口、搜索服务、OCR 识别、向量检索……这些 API 往往是 Agent 决策链条的最后一公里。然而，生产环境中外部服务**不可用**的时刻远比想象的多——临时性网络抖动、服务端 503、限流被触发、第三方 SLA 之外的故障，甚至只是 DNS 解析偶尔抽风。

一个没有错误恢复能力的 Agent，面对一次短暂的 HTTP 5xx 就可能直接抛出异常并终止任务，导致整个自动化流程失败。更糟糕的是，在无人值守的自动化场景下，这类故障往往直到业务方反馈才会被发现。

本文围绕“当外部 API 挂了，Agent 应该怎么办”这一问题，给出可直接落地的工程化方案，覆盖重试、熔断、降级、缓存等模式，并结合 MCP 插件的实际约束，梳理踩坑点和可复用建议。

## 问题抽象：不是所有错误都该平等对待

Agent 调用外部 API 可能遇到的错误大致分为两类：

1. **瞬时性错误**（Transient）：网络超时、短暂的 503、DNS 解析临时失败、服务限流返回 429。这类错误具有**可自愈性**，稍后重试大概率能成功。
2. **持久性错误**（Permanent）：认证失败（401）、权限不足（403）、服务长时间不可用、查询参数非法。这类错误重试无效，强行重试只会浪费资源并延长故障时间。

现实中还存在一种**灰色地带**：上游服务虽然返回 200，但响应内容不完整或含有异常空值。这种情况需要结合业务校验逻辑处理。

Agent 的错误恢复策略需要根据错误类型分流，同时考虑对外 API 的调用成本（计费、速率限制）和业务可接受的延迟上限。

## 实战做法：从装饰器到 MCP 工具级韧性

以下以 Python 生态为例（OpenClaw 插件 / MCP 服务端常用语言），给出一套可落地的分层容错方案。

### 1. 基础重试 + 指数退避

对**瞬时性错误**优先使用重试，加上指数退避和随机抖动，避免“雷群效应”把上游打死。Python 的 `tenacity` 库省去了大部分模板代码：

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
import httpx

RETRYABLE_STATUS = {429, 500, 502, 503, 504}

def is_retryable(exception):
    if isinstance(exception, httpx.HTTPStatusError):
        return exception.response.status_code in RETRYABLE_STATUS
    return isinstance(exception, (httpx.TimeoutException, httpx.ConnectError))

@retry(
    retry=retry_if_exception_type(Exception) | retry_if_exception(is_retryable),
    stop=stop_after_attempt(4),
    wait=wait_exponential(multiplier=1, min=1, max=10),
)
async def call_external_api(url, payload):
    async with httpx.AsyncClient(timeout=10) as client:
        resp = await client.post(url, json=payload)
        resp.raise_for_status()
        return resp.json()
```

### 2. 熔断器：防止雪上加霜

当外部 API 持续不可用时，Agent 不应反复重试造成自身任务堆积和上游压力。引入熔断器，在一定时间窗口内失败次数超过阈值后直接短路返回错误，避免无效调用。

简单实现可使用类似 `pybreaker` 的库，或直接用状态机：闭合 → 打开 → 半开。注意：半开状态下允许少量探测请求，探测成功则切回闭合状态，否则继续打开。

在 MCP 工具层面，可以在 tool handler 外包一层熔断装饰器，以工具名 + 参数去重生成熔断 Key，避免不同 API 之间互相影响。

### 3. 降级与缓存：让 Agent “能够回答什么就回答什么”

当外部 API 不可用且短期无法恢复时，降级是保证 Agent 仍能给出有限回答的关键。常见的降级策略包括：

- **静态降级**：返回预先配置的默认值，例如“天气服务暂不可用，提供过去一周的平均气温作为参考”。
- **缓存降级**：当 API 失败时，回退到本地缓存的上次成功响应（注意设置 TTL 并标记数据来源，让 Agent 在输出时注明“数据更新于 X 分钟前”）。
- **备用源切换**：如果 Agent 依赖的翻译 API 挂了，可切换至另一个 API 提供商，或在本地使用离线模型兜底。

在 MCP 工具定义中，可以在函数内部捕获异常后执行降级路径，并使用 `return` 返回降级结果，避免异常向 Agent 主流程泄漏。

### 4. 监控与可观测性

所有重试、熔断、降级事件都应该被记录并暴露指标。至少需要：

- 哪一把 API 在什么时间段触发了多少次重试？
- 熔断器打开与关闭的时间点。
- 降级调用次数及返回内容采样。

这样在故障复盘时才有数据支撑，而非猜测“大概因为网络问题”。

## 踩坑点：看起来完善，上线后依然出问题

**1. 重试放大效应**

如果一个 Agent 有多个工具并行调用 API A，每个工具又各自重试 3 次，那么 A 的异常可能导致请求量数倍放大。解决方案：在调用链路入口层（如统一 HTTP 客户端）做全局重试，而不是每个工具独立重试；或者对同一目标服务使用共享熔断状态。

**2. 熔断恢复逻辑缺失**

很多人只实现了熔断打开，但忘了设计半开探测和关闭条件，导致服务恢复后 Agent 依旧被熔断器阻止，需要手动重启。务必实现阶段转移：Open → (等待 `timeout`) → Half-Open → (探测成功) → Closed。

**3. 缓存穿透**

当 API 对特定参数返回 200 但空数据时，如果缓存了空值，可能造成业务错误。需对缓存结果做有效性校验，无效结果不入缓存，仅在降级时可能使用“最后有效数据”。

**4. 与 Agent 的交互协议模糊**

Agent 调用工具时，工具抛出异常和返回降级内容在语义上差异巨大。应该明确：降级返回时用 `content` 带 warning 文本，而不是抛出异常中断整个 ReAct 循环。OpenClaw 的 MCP 工具返回值最好统一为字典，包含 `status` 字段以标识数据可靠程度。

## 可复用建议

- **使用声明式容错装饰器模板**，统一项目中所有 API 调用的错误处理风格，降低新人接手的认知成本。
- **对 MCP 工具进行分层**：基础工具仅负责“与外部系统通信”，外层包装层负责重试/熔断/降级，保持职责单一。
- **错误分类配置化**：将哪些 HTTP 状态码 / 异常类型属于可重试、哪些属于熔断、哪些属于直接失败，提取到配置文件，方便调整而不需要改代码。
- **在开发阶段强制进行故障演练**：使用 toxiproxy 或简单的 mock server 模拟超时、5xx、慢响应，确保 Agent 的容错链完整。
- **关注上游 SLA 与自身超时**：重试总耗时不能超过 Agent 调用链路的用户等待容忍时间，否则任何恢复在用户眼里都等于“卡住”。

## 总结

AI Agent 的错误恢复不是“加个重试”就能解决的问题，而是一套组合拳：分清错误性质、控制调用成本、保障业务降级、保持可观测。在 OpenClaw / MCP 这类以工具调用为核心的自动化架构里，每一个对外依赖的工具都应被当作“不可靠的对端”来设计，才能真正让 Agent 在生产环境中跑得稳。

错误不可避免，但让 Agent 优雅地面对故障，是工程能力与玩具项目的分水岭。
