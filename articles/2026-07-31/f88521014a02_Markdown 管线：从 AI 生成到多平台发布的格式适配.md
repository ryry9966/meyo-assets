## 背景

在 Agent、MCP 与插件串联的日常里，Markdown 几乎成了 AI 输出的默认格式。大模型吐出来的内容本地预览很干净，但把它发到微信公众号、知乎、Notion 或者自建博客时，往往烂得一塌糊涂：代码块丢失高亮、图片不显示、标题层级错乱、特殊字符被吞……这些问题反复出现，手动修正的时间比写脚本还多。

造成这些现象的根源很简单：Markdown 只是一套轻量标记语言，而每个平台都有自己的解析规则与渲染约束。公众号只认内联样式的 HTML，Notion 有一整套 Block 模型，知乎虽然支持“Markdown 编辑”，但背后是一套定制化的扩展语法。如果每篇 AI 生成稿都要人工“本地预览 → 改格式 → 粘贴 → 再修一遍”，自动化就等于白干了。

## 管线设计与步骤

我们抽象了一条可复用的 Markdown 发布管线，核心思路是：**把平台适配和内容输出彻底解耦**。

### 1. 标准化输入
AI 生成的 Markdown 远谈不上规范：有时候标题后没空格，有时候缩进用 Tab，有时候代码块语言标注写成了 `python` 后面跟个换行。第一步用统一的格式化器扫一遍，比如 `remark` + `remark-gfm`，配合少数自定义规则，把不符合 CommonMark 或 GFM 语法的部分修掉。这一步能消除 70% 因为“低级格式错误”导致的平台兼容问题。

### 2. 中间表示：AST
解析成 AST（语法树）是整条管线的关键。使用 `mdast` 结构（通过 `unified` 解析链），后续所有操作都面向 AST 进行，而不是正则拼凑。这样做的好处是：
- 修改节点类型（比如降级 H1 到 H2）非常安全；
- 图片链接、代码块内容作为独立节点处理，不会因为正则没配好而改坏正文；
- 平台适配器能直接从 AST 渲染，避免“Markdown → 字符串 → 再次解析”的损耗。

### 3. 平台适配器实现
举例两个常用的适配思路：

**微信公众号**  
公众号编辑器本质上只认 HTML 片段，并且要求样式完全内敛。管线做法是：`remark-parse` → AST 变换 → `remark-rehype` → `rehype-stringify`，得到常规 HTML。然后针对微信：
- 用 `highlight.js` 将代码块转为带内联样式的 `<code>` 内容；
- 用工具把所有 class 样式转为 `style` 属性；
- 图片标签确保含有 `src` 且已经是图床上传后的绝对 URL（这一步一般在 AST 中就完成替换）。

**Notion**  
Notion API 接受的是 blocks 数组。可以从 AST 直接映射：heading → `heading_1/2/3`，paragraph → `paragraph`，code → `code` 并填充 `language`。难点在表格和富文本注解，需要细致处理内联的加粗、链接等标记，但 AST 恰好保留了这些结构。

### 4. 与 MCP / Agent 集成
把这一整套工具封装成一个 MCP server（或插件）之后，Agent 就具备了“发布前自动适配”的能力。Agent 只需提供原始 Markdown 和目标平台名，MCP 工具返回可直接发布的文本或直接调用平台 API 完成发布。这样既减少了人工介入，又避免了 Agent 因为“瞎猜平台格式”而出错。

## 踩坑与对策

- **代码块内联样式爆炸**：`highlight.js` 默认生成一堆 `class`，但微信会丢弃非内联样式。解决方案是在 `rehype` 阶段注入一个插件，遍历所有 `pre > code`，根据语言使用 `highlight.js` 的 `hljs.highlight` 得到 `value`，再把各个 token 的 class 映射成 style，利用 `rehype-raw` 注入。这部分性能不差，但要注意 `<` 和 `>` 的转义。
- **图片上传时机**：在 Markdown 里看到 `![](local.png)`，要提前替换为远程 URL。如果在渲染 HTML 之后再做，容易漏掉。建议在 AST 阶段就做图片检查与上传替换，并且加入重试机制，避免图床临时不可用导致发布中断。
- **表格兜底**：有些平台对 `thead` 和 `tbody` 样式支持差，导致表格线缺失。通用策略是在适配器中为表格加上 `border="1"` 和基础 cellpadding，保证最低限度的可读性。
- **H1 被强行降级**：一些公众号排版约定 H1 用作标题只用一次，更合理的是在适配器中配置标题偏移量，将 AST 中所有标题层级 +1，这样 H1 变 H2，以此类推。

## 可复用建议

1. **依赖统一**：选择 `unified` 生态（`remark`, `rehype`, `mdast`）作为管线核心，不要自己造 Parser，否则会把坑重复踩一遍。
2. **适配器做成可插拔**：每个平台一个独立模块，都导出 `(ast, options) => result` 接口，方便后续维护。
3. **提供 Clinet 端校验**：发布前在本地预览适配后的 HTML/BLOCK，并抓取常见问题（图片404、代码块无样式）。可以用 `cheerio` 迅速做校验。
4. **以 MCP 方式交付**：如果团队已经使用 Agent 串联工具，直接把管线暴露成 MCP 工具，非技术同学也能通过对话调用，降低使用门槛。

## 总结

Markdown 管线本来不是什么高深的东西，但极其吃工程细节。市面上很多“一键转换”工具要么覆盖平台有限，要么对 AI 输出的不规范格式毫无抵抗力。自己用 AST 管线的思路拼一条，投入两三天，换回的是长期不必再为格式问题焦虑。对于重度依赖 AI 内容输出的团队而言，这属于“磨刀不误砍柴工”的典型投资。
