# Agent 记忆系统设计：怎么让 AI 助手真正记住你的偏好

## 背景：无状态的 Agent 帮不了重复劳动

在 OpenClaw 里把常用的 MCP 工具、本地脚本连成 Agent 之后，一个很现实的痛点就冒出来了：每次对话都是从零开始。比如我让 Agent 帮我整理 GitHub Issues 并生成周报，它每次都问“用英文还是中文？”“报表存哪个目录？”“周报模板偏好吗？”哪怕昨天刚说过“用中文，模板用表格形式，放在 `~/notes/weekly` 下”，今天还得再交代一遍。

这种重复信息传递，本质上是因为 Agent 没有稳定、可检索的记忆系统。模型本身的上下文窗口虽然可以做短期记忆，但窗口一满、会话一切换，这些“约定”就丢了。对于自动化场景，这直接拉低了 Agent 的可用性：它更像一个需要时刻监督的实习生，而不是一个逐渐磨合的工作搭档。

## 问题拆解：记忆不是简单的存文本

设计 Agent 记忆时，真正要解决的并不是“怎么存聊天记录”，而是三个更细的问题：

1. **信息粒度和关联**  
   用户的偏好可能是全局的（比如“永远用英文回复”），也可能跟某个工具强关联（比如“git commit message 用 conventional commits 格式”），还可能是时间/场景敏感的（比如“代码 review 时用苛刻风格，其他时候随意”）。单纯把所有内容 dump 到一个长文本里，检索精度会很差。

2. **记忆的时效与冲突**  
   偏好会变化。上周说“输出日志用 JSON”，这周改成“用 YAML”。如果两个记忆并存且没有权重机制，Agent 要么随机抽一个，要么开始纠结反问，体验更加割裂。

3. **记忆对行为的影响控制**  
   记忆的最终目的是注入到 Agent 的决策流程中，但盲目把匹配到的记忆全塞进 prompt 会挤占推理空间，甚至引入无关或错误信息，导致生成质量下降。

## 工程实践：分层记忆 + 轻量检索管线

在基于 OpenClaw 的几次迭代中，我收敛到一套相对稳定的分层记忆方案，不需要重型向量数据库也能跑，适合个人或者小团队使用。

### 1. 定义三层记忆结构

- **短期记忆 = 会话上下文**  
  就是当前对话窗口内的消息，由模型自然处理。
- **工作记忆 = 当前任务状态**  
  比如执行到多步自动化流程的哪一步，下一步该做什么。一般在 Agent 内部用一个短 JSON 维护，任务结束即清。
- **长期记忆 = 持久化偏好 + 事实**  
  这是主角。内部再拆成两类：
  - **Profile 类**：固定结构，比如 `preferred_language`、`timezone`、`default_editor`，用 JSON 文件或 SQLite 单表维护。
  - **Memory 条目类**：自由文本记忆，每条包含内容、时间戳、来源会话 ID、重要性权重、标签（工具名、场景等）。

### 2. 记忆提取：在对话末尾由 LLM 做“课后总结”

不在对话过程中实时提取（容易扰动主任务），而是在会话结束时让 Agent 执行一个小型反思任务。具体做法是用固定 prompt 让 LLM 判断“本会话是否出现了新偏好或值得长期记住的事实”，输出结构化记忆条目，再由工程层写入存储。

关键控制点：给提取 prompt 加一组过滤条件，比如“只记录与默认设置不同的偏好”“不要记录一次性信息”“如果是更正之前已经有的记忆，标记旧记忆为 deprecated 而非新增”。这极大减少了记忆膨胀和重复。

### 3. 记忆检索与注入

每次新会话启动或执行任务前，Agent 执行一个检索步骤：

- 对当前用户指令和上下文做轻量 embedding（本地用 all-MiniLM-L6-v2 级别即可），在长期记忆库中做相似度检索。
- 对 profile 类记忆直接全量加载（量极小）。
- 取出的记忆条目按时间戳和重要性加权，去重后拼成一段“你的已知偏好”前缀，加在系统 prompt 最前面。

同时做一个熔断：如果检索到的记忆条目文本长度超过总 prompt 预算的 20%，则按重要性降序截断，防止记忆信息淹没主任务。

### 4. 记忆遗忘与更新

每条记忆都有一个 `decay_factor`，基于时间与末次命中频率计算。检索到的记忆在本次会话被明确确认后增加命中计数；超过一定时间未命中的条目会被定时任务（每天跑一次）移入冷存储，不再参与实时检索。用户也可以直接说“忘掉我之前关于 Git commit 的偏好”，Agent 通过工具调用来标记对应条目失效。

## 踩坑点实录

- **检索命中“相似但错误”的记忆**  
  比如“周报用英文”和“代码注释用英文”在向量空间里很接近，容易误注入。我的修复是在存储时强制要求记忆内容带上作用域标签（如 `[scope: report]`），检索时先用标签过滤，再向量匹配，精度提升明显。

- **记忆过期导致错误决策**  
  用户改了时区后，旧记忆里的“早晨 9 点”触发任务却按旧时区计算。解决办法是把环境变量级别的信息解耦到 profile 而不放入记忆条目，存储时记录有效时间窗口，发现冲突时由 Agent 主动确认。

- **隐私意外泄露**  
  在多租户场景或者一个 Agent 服务多个项目时，本项目的记忆不能流入其他会话。我的处理是每一条记忆都带 owner 字段，检索时强校验会话身份，同时在注入 prompt 时做一次脱敏检查（对 token、密钥之类模式做 mask）。

## 可复用建议

- **从 file-based profile 开始，不要一上来就引入向量库。** 先把最固定的偏好写成 JSON 文件加载，80% 的场景已经够用。
- **让记忆带有明确的时间戳和来源。** 出问题时能回溯“这是什么时候、在哪次对话记下的”。
- **把记忆修改做成可撤销。** 保留旧版本作为审计，而不是直接覆盖。
- **给记忆加上“软删除”标记，而不是直接物理删除。** 避免误删后完全丢失信息。
- **设计一个简单的记忆审查页面（即使只有 SQLite 中的表格）。** 让用户能主动查看、编辑 Agent 记住的偏好，比纯自然语言管理更可靠。

## 总结

让 Agent 真正“记住”你的偏好，关键在于把记忆当成一个需要全生命周期管理的小型数据系统来设计，而不是简单的文本追加。通过分层结构、轻量检索配合明确的更新与遗忘机制，可以让 OpenClaw Agent 从“总是忘事的工具人”逐渐变成能与你长期配合的合作体。这种工程化的记忆设计，付出的成本其实比想象中低，但带来的连贯性体验提升，往往是使用者感知最强的部分。
