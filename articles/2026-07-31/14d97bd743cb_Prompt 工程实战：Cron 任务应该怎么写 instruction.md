## 背景

在 OpenClaw 这类可编程 Agent 环境中，Cron 触发器是把自动化从“手动对话”推进到“无人值守”的关键分界线。典型场景：每天早上 9 点汇总 RSS 并生成简报、每小时检查一次数据库状态、交易日收盘后拉取行情并写入 Notion。这些任务都依赖类似下面这样的配置：

```yaml
triggers:
  - name: morning-brief
    schedule: "0 9 * * *"
    instruction: "汇总过去 24 小时未读文章，生成中文简报并通过飞书 Webhook 发送"
```

表面上看，只要 Cron 表达式写对，剩下就是 prompt 的事。实际跑起来，出问题的往往是那个 `instruction` 字段：Agent 要么漏掉步骤，要么重复操作，要么在失败时沉默。

## 问题

用一个真实案例说明。团队写过一个“每日归档”任务：

> schedule: `0 2 * * *`  
> instruction: “把昨天的日志文件打包上传到 OSS。”

前两周完全正常，第三周开始出现：同一天被打包两次，旧文件被覆盖，OSS 上的命名出现 `archive_2025-04-11.tar.gz` 和 `archive_2025-04-11(1).tar.gz`。根因是 Cron 机器和 Agent 容器的时区不一致，加上 instruction 里没有定义“昨天”的精确计算逻辑，Agent 用了自己的系统时间，而日志文件的命名基于服务器时间，两者偏差导致重复打包。

更隐蔽的问题在于 instruction 的**隐式上下文依赖**。Agent 每次被 Cron 唤醒时，并不天然拥有上一次执行的记忆，除非显式通过文件、数据库或外部状态传递。很多 instruction 习惯写：“继续上次未完成的工作”——这句话在没有共享状态的 Agent 面前毫无意义。

## 做法 / 步骤

为 Cron 任务写 instruction，建议从下面五个维度分解，然后拼成最终 prompt。

### 1. 明确时间语义

不要用“昨天”“最近一小时”这类模糊词。换成 Agent 可直接计算或通过参数注入的表达式。

- 使用明确的时区标记：`"以 Asia/Shanghai (UTC+8) 时间为准，当前时间由系统提供，用 `YYYY-MM-DD` 格式处理日期区间。"`
- 如果需要相对时间，给出计算方式：`"目标文件为 /data/logs/app-${date}.log，其中 ${date} = 当前日期 - 1 天（按 Asia/Shanghai 计算）。"`
- 利用环境变量注入：在调度框架中注入 `TRIGGER_TIME` 等变量，instruction 中引用它们。

### 2. 定义清晰的操作边界

必须回答三个问题：我从哪里开始？我到哪里结束？我处理哪些数据？

```text
步骤：
1. 扫描 /data/logs/ 目录下文件名匹配 `app-2025-04-*.log` 的文件。
2. 检查 OSS bucket `my-logs` 中是否已存在同名 `.tar.gz` 文件，若存在则跳过。
3. 对每个待处理文件执行：tar -czf <文件名>.tar.gz <文件名>，然后上传。
4. 上传成功后，将原文件移动到 /data/logs/archived/。
```

这里隐含地加入了幂等保证（检查 OSS 是否已有），以及完成后的清理动作，防止下一次执行重复操作。

### 3. 失败模式与重试策略

Cron 任务最大的敌人是“静默失败”。instruction 必须描述失败时做什么：

- “如果 OSS 上传失败，将错误信息写入 `/var/log/cron-upload-errors.log`，格式：`[时间] 文件名 失败原因`，不要重试。”
- “如果脚本执行超时（超过 120 秒），终止任务并通过企业微信 Webhook 发送告警，内容为任务名称、执行时间、失败阶段。”

同时要考虑**部分成功**：例如打包了三个文件，两个成功一个失败，instruction 需要说明是整体回滚还是保留成功部分。

### 4. 输入与输出的数据结构

避免让 Agent 猜测输出格式。如果需要写入数据库或发送消息，结构化要求要硬编码到 instruction 里。

```text
最终通过飞书机器人发送消息，JSON 格式严格如下：
{
  "msg_type": "interactive",
  "card": {
    "header": {"title": {"content": "每日日志归档报告", "tag": "plain_text"}},
    "elements": [
      {"tag": "div", "text": {"content": "成功: 3 个文件"}},
      {"tag": "div", "text": {"content": "失败: 1 个文件 (app-2025-04-09.log: 上传超时)"}}
    ]
  }
}
```

### 5. 幂等性指令

可重复执行是 Cron 任务的基本功。在 instruction 里直接写明：

- “任务可安全重放。每次执行前检查目标位置是否已有相同文件名的输出，若有则跳过。”
- “使用基于内容的哈希作为文件名的一部分，避免覆盖：`archive-${md5sum原文件前8位}.tar.gz`”

## 踩坑点

- **时区不一致**：Agent 容器、Cron 调度器、数据源可能使用不同时区。统一注入时区变量，并在 instruction 中显式声明。
- **环境变量缺失**：Cron 的执行环境通常极为精简，PATH、HOME、密钥文件可能都不存在。在 instruction 中要求 Agent 在执行前 source 特定的环境文件，或使用绝对路径。
- **Agent 上下文丢失**：长时间运行的 Agent 可能因为重启而丢失短期记忆。不要在 instruction 里依赖“上次的结果”，而应每次都从外部状态存储（文件、DB）中读取进度。
- **并发执行**：如果上一轮任务未结束，下一轮又被触发，会产生竞争。instruction 中应加入文件锁或标记检查：`"在执行前获取 /tmp/task.lock，若锁定失败则退出并记录。"`
- **Cron 表达式陷阱**：`*/5 * * * *` 可能在某些解析器里被误解，或者用户对 `?` 和 `*` 的差异不清晰。这是调度配置的问题，但 instruction 里可以防御性地写明预期频率（如“每 5 分钟执行一次”），一旦实测不符便于排查。

## 可复用建议

提炼一个 Cron instruction 模板，大部分场景可以直接套用：

```markdown
## 任务目标
[一句话描述]

## 时间与触发条件
- 时区: [明确时区]
- 触发时刻语义: [本次执行对应的业务时间窗口，如“处理从上次成功执行到当前时间之间产生的数据”]

## 输入
- 数据来源: [目录、API、数据库连接串]
- 时间范围: [如何计算起始时间和结束时间]

## 执行步骤
1. 前置检查: [锁、上一次执行状态、依赖服务可用性]
2. 核心操作: [具体命令或 API 调用，包含幂等逻辑]
3. 后置处理: [清理临时文件、更新状态标记、发送通知]

## 输出
- 格式: [JSON/Markdown/文件路径]
- 目标: [飞书 Webhook URL / 数据库表 / OSS 路径]

## 异常处理
- 错误分级: [可忽略错误 / 需告警错误 / 阻断性错误]
- 通知方式: [Webhook/日志文件/不通知]
- 重试策略: [无 / 固定次数 / 指数退避]

## 验证方法
- 手动执行时如何模拟: [给出 curl 命令或修改环境变量的方式]
```

团队维护这样一个模板后，Cron 任务的可靠性会大幅提升，排障成本明显下降。

## 总结

Cron 任务里的 instruction 不是操作备忘录，而是给 Agent 的确定性契约。写好它，需要你把“自动化”当成一个没有现场监督、需要自己处理所有意外的独立进程来看待。把时间语义、操作边界、失败模式和幂等性写清楚，就解决了 80% 的线上问题。剩下的 20% 来自仔细的环境管理和监控，那是另一个话题了。
