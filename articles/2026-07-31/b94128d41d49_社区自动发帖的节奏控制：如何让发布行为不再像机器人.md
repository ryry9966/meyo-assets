## 背景

在开源社区或技术社群里维护一个自动化账号，常用于发布每日一题、周报、版本更新或文档提醒。这类 Bot 一旦频率固定、输出雷同，很快就会被成员打上“机器人”标签，进而导致互动率下降，甚至被管理员限流或封禁。不少人会想到用 Agent 来提升内容质量，却忽略了**发布节奏**本身也是内容可信度的一部分。

在与 OpenClaw 生态配合的自动化管线中，我们可以在定时触发与最终发送之间插入一个**节奏控制层**，让同一个 Bot 的行为从“时钟一样准时”变成“像一个有作息的人”。

## 问题拆解

一个容易被看穿的自动发帖账号，通常具有以下特征：

1. **间隔时间固定**：每天 09:00:00 UTC 准时发送，误差不超过一秒。
2. **缺乏情境感知**：社区里正在激烈争论某个安全漏洞，它照常推送轻松的“今日冷知识”。
3. **内容格式毫无变化**：永远是同样的模板、同样的表情、同样的长度。
4. **不存在“手滑”和“犹豫”**：长篇内容瞬间完整出现，没有任何停顿或修改痕迹。
5. **从不响应外部事件**：节假日、周末、服务器宕机日，它照发不误。

节奏控制的目标不是完美伪装成人类，而是**消除可被简单规则识别出的机器特征**，降低被自动化审核或用户直觉判定的概率。

## 工程做法

我们在 OpenClaw 内实现一个轻量级的节奏控制 Agent，它位于定时调度器与实际发送动作之间，承担三个职责：间隔随机化、社区感知的动态调度和内容级微调。

### 1. 间隔随机化：用指数分布代替固定定时

固定间隔的最大问题是可预测。解决方法不是加入一个固定范围的随机抖动，而是采用**泊松过程**的思路：用指数分布生成下一次发布的时间间隔。泊松过程天然适合模拟人类独立随机事件的发生，因为人类发帖很少是周期性钟表驱动的，而更像是“想起来就去发”。

具体实现可以简单到：

```
next_interval = -ln(1 - random()) / lambda
```

其中 `lambda` 是单位时间内的平均发帖次数。比如你希望一天平均发 3 条，那么 `lambda = 3 / (24*3600)`。这样生成的时间间隔有长有短，可能出现连续两条很接近，也可能隔很久没有动静，符合人类的不规律性。

**踩坑点**：指数分布在 lambda 很小时会产生极长间隔，可能需要设置一个上限，避免连续数天不发。也可以截断至 `[min_interval, max_interval]`，但要注意截断后分布形状改变，仍然比均匀随机好。

### 2. 社区感知的调度：基于活跃度决定是否发布

单纯随机时间仍然可能在社区完全沉睡时发送，显得异常。我们通过 MCP 连接 Discord/飞书/论坛 API，实时获取当前在线人数或最近 15 分钟的消息量。

在决策逻辑中设定一个阈值，例如：

- 如果当前活跃用户数 < `activity_threshold`，则延迟发布，将任务重新入队，等待下一次决策窗口。
- 延迟次数超过上限（如 3 次），仍强制发布并记录原因，避免永久阻塞。

这需要用 MCP 工具封装实时指标查询，Agent 在每次准备发送前调用该工具，根据返回值判断“现在是否合适”。

**踩坑点**：API 调用可能引入网络延迟或频率限制。需要对工具调用做缓存和退避，建议活跃度数据缓存 1-2 分钟，避免每次决策都直连 API。

### 3. 内容微调与分批发送

长文本一次性出现是非常强的机器特征。对于长篇公告或文章摘要，可以让 Agent 将内容拆分为 2-3 条消息，并在每条之间随机停顿 2~8 秒，模拟打字或修改过程。还可以在消息末尾随机选择是否附加一条“（编辑：补充了一点说明）”，制造人工修订的痕迹。

如果发送平台支持“正在输入…”状态，则触发该状态保持一段随机时间再实际发送，这需要平台的 SDK 支持。

**踩坑点**：分段发送可能被当成刷屏，尤其在微信群等场景。需要根据社区规范调整，可配合“合并转发”或使用 Thread。

### 4. 外部事件的跳过机制

如果社区突然出现异常事件（如安全漏洞应急、主库故障），Bot 仍自顾自发送娱乐内容会非常突兀。可以设置一个简单的情绪/关键词检测工具，MCP 连接最近消息流，当出现“紧急”“宕机”“CVE”等术语且频率突增时，自动跳过本轮发布。

该判断也可以在 Agent 的思维链中完成：将最近 N 条消息作为上下文，让模型判断“现在是否适合发送技术分享”，将 publish 决策交给 AI 而不是硬编码。

**踩坑点**：模型判断有一定延迟和成本。更好的做法是先做规则快速过滤，只有模糊边界时才让模型介入。

## 可复用的抽象建议

不要把这些逻辑零散地写在发布脚本里。建议封装成一个**节奏控制器 MCP 工具**或 OpenClaw 插件，对外提供：

- `schedule_next(context)`：根据历史发布记录返回下次建议时间。
- `should_skip(context)`：基于社区状态和事件检测返回是否跳过。
- `post_with_human_touch(content)`：执行分段、打字延迟、模拟修改等。

配置项包括：平均频率 lambda、活跃度阈值、最大延迟次数、分段发送开关、打字延迟范围。这样任何自动化项目只需接入该工具，即可获得节奏控制能力，而不必重造轮子。

## 总结

社区自动发帖不被当成机器人的关键，不在于一条消息写得多么“有温度”，而在于整个发布行为序列**没有可被简单规则捕捉的机械特征**。通过泊松间隔、活跃度感知调度、内容微调和上下文跳过，就能极大降低判定概率。

在 OpenClaw 体系中，利用 Agent 的决策能力和 MCP 的连接能力，我们可以把节奏控制器做成一个独立的、可插拔的基础设施组件，让每一个需要输出的自动化流程都能“像人一样”喘息。

节奏控制不是欺骗，而是让自动化工具以更低的干扰融入社群协作，从而真正达到服务社区的目的。
