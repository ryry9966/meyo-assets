## 背景
在 OpenClaw 这类 Agent 编排框架里，LLM 调用是最频繁也最昂贵的环节。任务拆解、工具选择、函数调用、结果汇总，每一步都可能涉及模型推理。日常跑自动化流程时，如果所有请求都走 GPT‑4o，账单很快会失控；全部换成本地模型（如 Llama 3.1、Qwen2.5）又会碰到推理能力不足、长上下文丢失、指令跟随不稳定等问题。

“全部上云”和“全部本地”都不是工程最优解，合理做法是按任务特征动态路由：简单、高频、隐私敏感的任务走本地，复杂、需要深度推理或长上下文的任务走 GPT。这样能在成本、延迟与效果之间拿到更好的平衡。

## 问题拆解：什么时候该用谁
决定路由策略前，最好先做一次任务画像。下图是我在实际项目中用到的判断维度：

- **任务复杂度**  
  纯文本摘要、关键词提取、分类、简单翻译 → 本地模型完全够用。  
  需要多步推理、数学计算、结构化代码生成、多角色对话协调 → GPT‑4o 更可靠。
- **数据敏感度**  
  涉及个人身份信息、内部业务数据、未公开的设计文档 → 优先本地甚至纯离线，避免数据出域。
- **上下文长度**  
  短上下文（< 4K token）本地模型应付自如；一旦上到 8K 甚至 32K，大部分本地模型注意力衰减严重，并且推理速度骤降，此时云端的 128K 上下文优势明显。
- **延迟与并发**  
  本地模型在 1–2 并发时响应很快，但在 Agent 并发调用多个工具时会突然变成瓶颈。GPT API 的弹性扩缩能扛住突发流量。
- **成本**  
  单次调用的绝对价格只是一面，还要看任务体量。一天几万次分类请求如果全跑 GPT，开支可观；但如果只用本地模型处理关键步骤导致任务失败需要重试，隐性成本也不低。

## 在 OpenClaw 里的落地做法
OpenClaw 的 flow 配置支持 `model` 字段指定模型名称，结合它的路由机制，可以将任务分流。假设你的 OpenClaw 环境中已经配置了两个后端：`openai/gpt-4o` 和 `ollama/qwen2.5:14b`（本地模型）。

### 1. 手动条件路由
最直观的方式是根据 task 的标签或元信息在 flow 定义里写上条件。例如：

```yaml
tasks:
  - name: classify_intent
    model: ollama/qwen2.5:14b   # 简单分类走本地
    prompt: "..."
  - name: generate_code
    model: openai/gpt-4o
    prompt: "..."
```

如果一个节点里需要根据数据内容动态选择，可以用 Python 自定义节点：

```python
def router(state):
    if len(state['input_text']) < 200 and not state.get('requires_reasoning'):
        return {"model": "ollama/qwen2.5:14b"}
    else:
        return {"model": "openai/gpt-4o"}
```

然后在 flow 的 `model` 字段使用 `{{ router.model }}` 动态注入。这种做法直接，缺点是需要提前分析任务特征，而且每个路由判断都依赖人工规则，覆盖面窄。

### 2. 加入轻量级分类器
为了减少人工规则，可以在 Router 节点前增加一个本地小模型做“任务分类”。用一个 1B–3B 的模型极快地阅读用户输入或上游结果，输出类别标签如 `simple_lookup`、`reasoning`、`sensitive`。之后分支选择模型。

OpenClaw 中可以这样编排：

```
[用户输入] → classifier (phi-3:mini) → 输出 task_type
                                       ├─ simple_lookup → local LLM
                                       └─ reasoning      → GPT-4o
```

分类器 prompt 要写得尽量结构化，输出严格 JSON，避免解析错误。实测中分类准确率能达到 85–90%，漏网之鱼用 fallback 机制兜底。

### 3. 隐私路由
对于 PII 数据，我在 entrypoint 处做一次正则扫描或 NER 检测（可用本地库 presidio），如果命中敏感实体，整个 session 强制锁定在本地模型，并且不记录日志到云端。

## 踩坑点
- **本地模型输出不稳定**  
  Ollama 的本地模型经常偏离指令，尤其在需要特定 JSON schema 时。最好配合 auto‑retry + schema validator，失败两次后降级到 GPT，但必须设置最大 retry 成本预算。
- **分类器误判导致任务质量断崖**  
  比如把多步推理误判为“简单查找”，结果本地模型给了一个看似正确实则虚构的答案。建议对关键路径保留人工检查点，或对输出质量自动评分，低于阈值的自动升级模型。
- **上下文格式不兼容**  
  GPT‑4o 和 Llama 系列对 system/user/assistant 的角色标记不完全相同，切换模型时容易丢失 system prompt。可以在 Router 节点后面跟一个 Adapter 节点，统一将消息历史转成目标模型的格式。
- **本地模型并发瓶颈**  
  单个 Ollama 实例通常只能高效处理 2–4 并发，Agent 同时调用 5 个工具时，第 5 个会超时。解决方案：要么做请求队列+超时重试，要么部署多个本地实例做负载均衡（但资源占用大）。对于突发高并发，不如直接甩给 GPT API。
- **成本估算易被忽略**  
  有人以为切到本地模型就零成本，但电费、GPU 折旧、维护成本也是支出。建议按 token 成本做内部计价（哪怕本地虚拟计价），从而对比方案总开销。

## 可复用建议
1. **从规则路由开始，逐步引入分类器**  
   先用简单条件维护一两周，积累典型任务模式，再训练/调优小分类器。一下子搞得很复杂容易自噬。
2. **记录每次路由决策和最终评分**  
   将“选择了哪个模型”和“该次回复质量评分”都存下来，方便回溯和优化规则。可以直接写入 OpenClaw 的 state 并在下游做异步评估。
3. **保留开关和灰度能力**  
   所有路由规则都做成可配置的 feature flag，出现问题时能一键回滚到全部用 GPT，避免线上事故。
4. **关注模型能力边界，而不是仅看 benchmark**  
   有些本地模型在 HumanEval 上分不低，但在多轮对话里容易“失忆”，要多做端到端场景测试。
5. **本地模型镜像版本固定**  
   不要自动拉取最新版，避免某天模型更新后行为突变，导致路由失效。用 container tag 锁定版本。

## 总结
在 OpenClaw 中做多模型路由不是简单的“贵的用 GPT，便宜的用本地”，而是需要根据任务复杂度、数据敏感度、上下文长度、并发模式建立一套可演进的调度策略。最开始可以硬编码几条规则，用数据验证它的有效性，再慢慢加入自动分类和 fallback 机制。做好了，代理系统的可用性与成本控制会同时上一个台阶；做不好，就可能陷入“本地模型搞砸—人工救火—成本反超”的恶性循环。

把路由决策当做 Agent 自己的一个 meta‑task 来设计，它本身就是值得迭代工程化的地方。
