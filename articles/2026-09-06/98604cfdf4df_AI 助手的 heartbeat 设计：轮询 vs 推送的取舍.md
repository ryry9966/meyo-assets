## 背景

OpenClaw 这类常驻 Agent 有个绕不开的问题：它什么时候该“醒”。定时提醒、日报汇总、MCP 事件回调、插件消息……触发来源不同，合适的唤醒机制也不同。目前主流就两条路：heartbeat 式轮询（定时注入一条轻量提示让 Agent 自查），以及推送（事件到了主动叫醒）。

## 问题

轮询简单可靠，但代价线性增长：每分钟醒一次，一天就是 1440 次唤醒，哪怕九成唤醒无事可做，上下文注入和 token 开销照付不误，还会把会话上下文越撑越脏。推送省资源、延迟低，但工程上麻烦不少：要暴露可达的接收端、处理重试与去重，而且失败往往是静默的——你没收到，就等于永远没收到。选错机制的症状很典型：要么 token 烧得肉疼，要么消息莫名丢。

## 做法

我的原则是**按触发源分类，推送优先、轮询兜底**：

1. **先给任务分类**。时间驱动的（每天 9 点日报、每周回顾）天然适合 heartbeat/cron；事件驱动的（新邮件、CI 结果、文件变更）必须走推送，靠 MCP 通知或 webhook 插件注入。
2. **轮询分层**：默认低频（比如 15 分钟一次）作为兜底清扫，只在活跃会话期间临时收紧到分钟级。
3. **唤醒先过便宜检查，再决定是否调模型**。本地规则判断有无待办，无事就直接睡回去，不进 LLM。
4. **推送侧加幂等键和队列**：每条事件带唯一 ID，消费前查重；推送失败进重试队列，指数退避，超上限落死信并告警。
5. **记录每次唤醒的 reason 和结果**，统计“空唤醒率”。这个指标是调间隔的唯一依据，别拍脑袋。

## 踩坑点

- heartbeat 频率照抄别人的配置，结果 token 账单翻倍。间隔必须和自己的任务密度匹配。
- 推送去重没做，一次网络重试导致同一条消息回复了两遍，用户体验很差。
- 家宽/NAT 环境收不到 webhook，推送看起来“配置成功”但从未到达。要么加轮询兜底，要么走中转网关。
- Agent 离线期间错过的 heartbeat，恢复后没有补偿逻辑，提醒直接蒸发。补一个“错过窗口”扫描。

## 可复用建议

- 把“推送优先、轮询兜底”固化为默认模式，不要按任务逐个纠结。
- 幂等键 + 队列 + 死信是推送链路三件套，缺一个都会在半夜出事。
- 空唤醒率高于 80% 就该降频或改推送。
- 所有静默失败都要留痕：送达回执、重试日志，比任何告警都先救你。

## 总结

轮询和推送不是对立选项，而是两类触发源的不同映射：时间驱动交给 heartbeat，事件驱动交给推送，再用低频轮询兜住推送的所有失败模式。这套组合在我这儿稳定跑了几个月，token 花销降了一个量级，消息也没再丢过。有不同实践欢迎在评论区交流。
