## 背景

让 agent 长驻之后，第一个绕不开的问题是：它怎么知道"现在该干活了"？外部消息到达、定时任务到期、某个文件变化、某个服务状态异常——这些触发点最终都要落到一个唤醒机制上。OpenClaw 的 heartbeat 就是这个角色：agent 按固定间隔被拉起，检查一遍待办，有事处理，没事继续睡。

听起来简单，但轮询和推送这两种路线的选择，直接决定了系统的延迟、成本和可靠性下限。

## 两种机制的真实差异

**轮询（polling）**：agent 定时醒来，主动检查状态。优点是实现极简、不依赖网络入口、本地就能跑；缺点是延迟上限等于轮询间隔，且每次唤醒都有固定成本——对 LLM agent 来说就是 token。

**推送（push / webhook / 事件驱动）**：外部事件发生时主动通知 agent。延迟低、无事件时不消耗资源；但要求有个可达的入口（公网回调、消息队列、长连接），且你必须处理通知丢失、重复、乱序这些分布式老问题。

纯轮询的账很好算：假设每次 heartbeat 注入 800 token、间隔 5 分钟，一天就是 23 万 token 的"空转税"，哪怕模型便宜也经不住。纯推送的问题更隐蔽：webhook 服务重启、内网穿透断连、回调 URL 过期，任何一环挂了，你的 agent 就静默失联——没有报错，只是什么都不发生。

## 我的做法：轮询兜底 + 推送加速

实践下来比较稳的架构是两层：

1. **推送做主通道**。邮件、IM 消息、监控告警这类即时性要求高的事件，走 webhook 或消息队列直接触发 agent。延迟从分钟级降到秒级。
2. **轮询做兜底**。保留一个较长的 heartbeat 间隔（比如 30 分钟），每次醒来做三件事：检查推送通道健康、扫描是否错过的事件、处理定时任务（每日摘要、定期巡检）。

配置上的几个关键点：

- **按任务分级设置间隔**。巡检类 30 分钟够了，别一刀切设 1 分钟。
- **heartbeat 内容最小化**。唤醒时只注入一份精简的检查清单（类似 HEARTBEAT.md 的思路），而不是完整上下文。无任务时让 agent 返回极短的占位响应，禁止它自由发挥。
- **推送侧做幂等**。每条事件带 ID，agent 侧去重；推送失败进重试队列，超过阈值降级为"等下次 heartbeat 扫描"。
- **记录唤醒日志**。每次 heartbeat 记一行：触发源、耗时、是否有任务。一周后回头看，你会清楚知道哪些轮询是纯浪费。

## 踩坑点

- **间隔太短的代价是复利的**。1 分钟一次的 heartbeat，看起来"响应快"，实际是把成本花在 99% 的空转上。
- **agent 醒来后的话痨问题**。没有明确"无事可做则沉默"的约定，agent 每次 heartbeat 都生成一段总结发到群里，几天后你就想把它关了。
- **推送通道的假活**。长连接断了但进程没崩，监控显示正常，事件却全在丢。兜底轮询必须真的会检查通道状态，而不是摆设。
- **定时任务堆积**。agent 处理慢时，多个到期任务并发触发，token 消耗瞬间翻倍还容易互相踩。加个简单的队列串行化。
- **本机休眠**。笔记本上跑的 agent，heartbeat 间隔再准也敌不过系统睡眠。唤醒后先校时再补跑错过的任务。

## 可复用建议

- 默认选轮询起步，能跑通后再按事件类型逐个引入推送，不要一上来就上消息总线。
- 把"每次唤醒成本"当作显式参数写进配置，和延迟要求放在一起权衡。
- 任何推送通道都必须有一个轮询式的对账机制，哪怕频率很低。
- 沉默是 heartbeat 的默认行为，有事才说话。

## 总结

轮询和推送不是二选一，而是分工：推送负责"快"，轮询负责"稳"。heartbeat 的本质是用可控的成本换取 agent 的存在感——间隔、注入内容、沉默约定，这三件事定义清楚了，你的助手才既能及时响应，又不会在深夜偷偷烧掉你的额度。
