## 背景

单个 Agent 串行干活的瓶颈很直观：给一个仓库的 20 个模块批量补单测，串行要跑一晚上；中间输出还会把主上下文塞满，跑到后半段推理质量明显下降。我们在 OpenClaw 的实践里把主 Agent 改造成“调度者”，用 subagent 并行处理独立子任务，稳定跑了几轮之后整理出这套做法。

## 问题

直接并行会撞上三类典型故障：

1. **主上下文污染**：subagent 返回大段原始输出，父 Agent 几轮就撑爆上下文。
2. **资源冲突**：多个 subagent 同时写同一个文件、共用一个 MCP 工具实例（浏览器、git 等），互相覆盖或排队报错。
3. **失控放大**：并发数一高触发限流，成本飙升；一个 subagent 卡死，整体被拖住。

## 做法

拆解原则只有一条：只并行“输入输出明确、彼此无依赖”的子任务。

1. **父 Agent 先规划**：把任务拆成 N 份，每份写清楚输入、独立输出路径、完成标准。有依赖关系的部分宁可留在串行阶段。
2. **给每个 subagent 划地盘**：分配独立工作目录，禁止写共享文件；约定返回格式为“状态 + 关键结论（300 字内）+ 产物路径”。
3. **结果落盘，不回传原文**：中间产物写文件，父 Agent 只读摘要，需要细节再按路径去取。
4. **控制并发在 2~4 路**：父 Agent 层设超时，单个超时标记失败、不阻塞其余任务。
5. **汇总校验**：父 Agent 交叉核对各路产物（比如把合并后的代码统一编译一遍），而不是照单全收。

改成 4 路并行加汇总校验后，前面那个补单测的活一个多小时收工，主上下文全程只装摘要。

## 踩坑点

- subagent 彼此看不见进度，有依赖的任务拆成并行必然翻车。正确顺序是先串行跑通全流程，再并行其中稳定的部分。
- 不约束返回格式是最常见的事故来源，一次大输出就可能毁掉整个会话的上下文。
- 共享的 MCP 工具实例要按 subagent 拆分，否则排队等待加报错，比串行还慢。
- 重试逻辑放在父 Agent 层做，subagent 自行重试容易进入死循环。
- 并行并不省 token：调度开销加上重复的系统提示词，总成本往往比串行高 30% 以上，值得的任务才并行。

## 可复用建议

- 沉淀一个“调度者提示词模板”：角色限定为分发与汇总，明令禁止自己动手做子任务。
- 统一 subagent 返回 schema，父 Agent 的解析和汇总逻辑就能写死，不用每次现场发挥。
- 把文件系统当黑板用：目录结构即任务清单，天然支持断点续跑和人工补位。
- 每次编排留存日志，复盘哪个子任务慢、哪个失败，再据此调整并发数。

## 总结

subagent 编排的本质是让 Agent 从执行者变成管理者。加速是表层的收益，真正的收益是上下文隔离——每个 subagent 只背自己那摊事的上下文，主 Agent 始终保持清醒。纪律比并发数重要：任务边界清晰、返回格式统一、结果落盘可查，这三件事做扎实，两路并行就已经比单线程强很多。
