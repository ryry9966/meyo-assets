## 背景

多数人对 Agent 的使用模式是「你问，它答」。但一个部署在自己服务器上、7×24 在线的个人 Agent，一天里绝大多数时间其实闲着。OpenClaw 里有个很小的机制专门解决这个问题：工作区根目录下的 HEARTBEAT.md。Agent 每隔固定间隔（默认 30 分钟）被「心跳」唤醒一次，读取这个文件，逐条评估里面的待办，有事就处理并通知，没事就保持沉默。

它本质上回答了一个问题：怎么让 Agent 在没人提问的时间段里，低成本、有边界地主动做事。

## 问题

被动式 Agent 有三个盲区：

- **时效性事件没人盯**：磁盘写满、证书过期、CI 挂了，这些都是等你想起来就晚了的事。
- **系统 cron 太笨**：cron 能定时执行，但不能判断——它不会在磁盘 85% 时才报警，只会固定时刻无脑跑。
- **主动等于花钱**：每次唤醒都是一轮模型调用，没有约束的话，主动性会被成本和通知噪音拖垮。

HEARTBEAT.md 是三者的折中：定时的「推理」，而不是定时的「执行」。

## 做法：三步跑起来

1. 在工作区根目录创建 HEARTBEAT.md，写少量可判定的条目：

```markdown
# 心跳清单

- 执行 `df -h /`：根分区使用率超过 85% 时告警。
  结果记录到 workspace/state/disk.md；同一问题连续 3 次才发消息，否则只记录。
- 检查 gateway 日志新增的 ERROR：仅当错误模式与上次记录不同时才通知。
- 本轮无任何需要处理的事项时，直接回复 NO_REPLY。
```

2. 按需调间隔。环境变量 `HEARTBEAT_INTERVAL` 控制唤醒频率（分钟），默认 30。观察一周再调，别一上来就设 5。

3. 让它静默。把文件清空即可整体跳过心跳处理，Agent 不产生任何通知，适合出差、休假场景。

关键在条目写法。我总结成四要素：**触发条件（带阈值）、动作（具体命令）、通知策略（何时发、何时只记）、状态落盘（写本地文件用于去重）**。缺了状态落盘，几乎必然遭遇重复告警。

## 踩坑点

- **成本按心跳计**。文件越长、间隔越短，账单越高。贵的检查（调外部 API）合并或降频，便宜的本地命令才配得上高频。
- **条目模糊是灾难**。「帮我看看邮件」会让 Agent 要么乱调工具要么天天骚扰你，改成「未读超过 10 封时摘要前 5 封」。
- **心跳不是 cron**。「每天早上 9 点提醒」这类任务，心跳本身不认识时刻——要么在条目里让 Agent 自己算下一次触发，要么交给系统 cron。
- **别把重活放心跳里**。心跳跑在主会话循环里，一个十分钟的长任务会拖垮整个节奏。心跳只做「检查 + 决定是否升级」，重活让它发消息问你。
- **静默失败要主动防**。心跳出错你收不到提醒，建议每周加一条自检：连续多次心跳无产出，就在下次对话里汇报。
- 排障先确认心跳真的在跑：看 gateway 日志里的心跳记录，不要靠猜。

## 可复用建议

- 条目控制在 5 条以内，每月修剪一次：删掉从未触发和天天触发的——前者没用，后者该改写成 cron 或修产品逻辑。
- 用 git 管 HEARTBEAT.md，改动可回溯，也方便多机同步。
- 「监控类」和「例行类」分开写：监控类要有明确阈值和升级策略，例行类（如工作日例会提醒）用 cron 更省。

## 总结

HEARTBEAT.md 的价值不在功能多强，而在它给「主动性」加了两道约束：定时唤醒控制成本，清单条目控制边界。核心纪律就一条——每个条目必须可判定、有阈值、有去重。做到这些，Agent 就从一台问答机，变成一个会主动来敲门、但不会为小事半夜敲门的值班同事。
