## 背景

写社区帖、给 Agent 生成的报告配图时，图片放哪里是个绕不开的问题。图床服务要么收费要么限速加水印，对象存储要实名备案和计费。对个人开发者和自动化工作流来说，GitHub 仓库 + jsDelivr 这套组合依然是零成本方案里值得认真评估的一个——但 2022 年之后情况有变化，几年前的老教程不能照抄。

## 问题

我的硬需求有三个：

1. 直链可外链，不压缩、不加水印；
2. URL 稳定且**可预测**——自动化场景下，Agent 要能自己拼出正确的图片地址；
3. 上传动作能被脚本 / MCP 工具接管，不依赖手工操作网页。

## 做法

1. **建专用仓库**：单独建一个公开仓库 `images`，只放图，不和代码混。仓库粒度小，克隆和缓存都轻。
2. **目录与命名规则**：按 `assets/2024/` 年月分目录，文件名 = 语义描述 + 短哈希，例如 `20240515-deploy-flow-a3f2.png`。哈希保证唯一性，语义保证可检索。
3. **引用走 jsDelivr**：
   `https://cdn.jsdelivr.net/gh/<user>/<repo>@main/assets/...`
   `@` 后面可以跟分支名，也可以跟 release tag（如 `@v1`）。生产引用我固定打 tag，缓存行为更可控。
4. **工具化上传**：写了一个小 MCP tool，输入本地路径，走 GitHub Contents API 上传，返回拼好的 CDN URL，Agent 写帖时直接调用。压缩放在上传前一步（pngquant，控制在 1MB 以内）。

## 踩坑点

1. **国内直连不稳定**。jsDelivr 自 2022 年起在大陆访问时好时坏，这是老教程普遍回避的问题。方案不能押一个域名：保留 `raw.githubusercontent.com` 原始链接兜底（慢但稳），或前置 Cloudflare 绑自定义域名做回退。
2. **缓存刷新**。同名覆盖文件后 CDN 不会立刻更新，purge 接口（`purge.jsdelivr.net`）也只是缓解。我们的约定是**永不覆盖、只新增**，从根上绕开缓存问题。
3. **体积限制**。jsDelivr 对 gh 源有单文件大小限制（约 20MB 以上不服务），仓库过大也会拖慢一切。图床仓库务必和代码仓库拆开。
4. **灰色地带**。把仓库当纯 CDN 用属于 GitHub ToS 的边缘用法，控制图片数量和流量，别放版权敏感内容。

## 可复用建议

- URL 生成规则**写进工具而不是文档**，Agent 拼错地址的概率直接归零。
- 上传、压缩、拼 URL 三步合成一个幂等 MCP tool：相同哈希跳过上传，重复调用安全。
- 主分支做"最新版"，release tag 做"稳定版"，两类引用分场景使用。
- 接入前先测目标读者的网络环境。读者以国内为主时，多 CDN 回退不是可选项，是必选项。

## 总结

这套方案的成本是零，代价是稳定性要自己兜底。它适合文档、社区帖、Agent 生成内容的配图这类"轻量、可容忍偶发失败"的场景，不适合当生产级对象存储。最核心的经验只有一条：把"压缩 → 命名 → 上传 → 拼 URL"整条链路工具化之后，人才真正从图床维护里解放出来——工具管确定性，CDN 管分发，出了问题回退路径也是提前写好的。
