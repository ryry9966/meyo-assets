## 背景

大多数时候，我们和 Agent 的交互是被动式的：你提问，它回答，会话结束。但个人助理场景里，真正有价值的事往往是反过来的——CI 挂了要有人告诉我，磁盘快满要有人提醒我，每天早上要有人把昨晚的信息汇总好端上来。

OpenClaw 为此内置了一个很轻的机制：每个 agent 的 workspace 里可以放一个 `HEARTBEAT.md`，调度器按固定间隔（默认约 30 分钟，可配置）把文件内容注入给 agent，相当于定时戳它一下："现在看看，有没有你该做的事。"

## 问题

在没有 heartbeat 之前，实现"主动行为"的常见路径是：外部 cron 调 API、自己拼 system prompt、结果再想办法塞回会话。三条链路三个状态源，改一次需求要动三处。

Heartbeat 把这件事压缩成"维护一个 Markdown 文件"：主动性变成了一份可以被版本管理、被 code review 的配置。

## 做法

1. 在 agent workspace 根目录创建 `HEARTBEAT.md`；
2. 每个任务按三段式写：**触发条件 / 检查动作 / 上报规则**；
3. 在配置中调整心跳间隔与投递目标（发到哪个会话或渠道）；
4. 约定静默协议：无事可报时回复 `HEARTBEAT_OK`，这条回复不会投递给用户，只消耗一次便宜的判定；
5. 检查动作交给工具完成：shell 脚本、MCP 工具、文件读取，agent 只负责判断和汇总。

一份我自己在用的示例：

```markdown
# Heartbeat Tasks

- 每 6 小时：检查仓库 CI 状态，仅在有新失败时通知，附失败 job 名。
- 每天 09:00：汇总过去 24h 的 newsletter 邮件，输出三行以内摘要。
- 磁盘使用率 > 85%：立即提醒；否则 HEARTBEAT_OK。
- 其余情况一律 HEARTBEAT_OK，不要主动寒暄。
```

最后一条是刻意加的兜底，见下文。

## 踩坑点

- **没有静默规则就是骚扰**。早期版本我没写兜底条款，agent 每半小时发一句"目前没有需要处理的事项"，两天后我把它关了。规则必须明确到"什么情况才允许说话"。
- **心跳是真实成本的轮询**。每个 tick 都是一次模型调用，任务描述越长、工具越多，单次开销越大。判定条件尽量前置到脚本层，让模型只处理"已经成立"的情况。
- **文件别写长**。超过一屏，指令之间开始互相冲突，agent 表现会变得不可预测。任务多了做减法，或拆到不同 agent。
- **注意时段**。夜间心跳照跑，凌晨发消息并不浪漫。把"只在 08:00–23:00 活动"写成显式规则。
- **心跳里别干重活**。长任务会与手动会话抢上下文，也容易超时。心跳只做检查和汇总，重任务写入待办，由你确认后再触发。

## 可复用建议

- 用三段式模板写每个条目，条件写不清楚的任务先不要放进心跳；
- "是否打扰用户"必须由明确规则决定，不要交给模型自由发挥；
- 让心跳把每次动作追加到本地日志（如 `heartbeat.log`），出问题可回溯；
- 心跳产出的长内容落盘成文件，消息里只给一行摘要和路径；
- 心跳和手动会话共享同一个 workspace，可以互相接力：心跳发现问题 → 写入 `todo.md` → 你下次问"有什么待办"时它自然接上。

## 总结

HEARTBEAT.md 没有什么黑科技，它只是把"定时 + 一段提示词 + 一套静默协议"固化成了 workspace 里的一个文件。但正因为它足够简单，主动性才变得可维护：有 diff、有历史、可以 review。一个实用的判断标准是——如果你的需求能用 cron 表达式加一页纸规则写清楚，它就适合放进心跳；反之，老老实实用外部调度。
