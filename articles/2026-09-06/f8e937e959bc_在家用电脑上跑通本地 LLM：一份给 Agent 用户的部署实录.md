## 背景

做 Agent 和自动化的人对两个问题都不陌生：云端 API 的账单，和数据出域的顾虑。而日常高频的小任务——意图识别、分类、结构化抽取、MCP 工具调用的路由判断——其实并不需要旗舰模型。我的场景是 OpenClaw 挂了一组 MCP 工具，需要一个"常驻值班"的小模型做工具选择和参数抽取，每次调用只有几十 token，为这点量走一次网络往返并不划算。于是决定把这一层搬回本地。

## 问题

动手前我有两个误解：

1. **以为跑本地模型必须有 24G 显卡。** 实际上 7B 的 Q4 量化模型体积在 5G 上下，纯 CPU 也能跑，只是慢；
2. **以为"能跑起来"就等于"能接进 Agent"。** 真正的难点是本地模型的 function calling 兼容性——不少模型把工具调用输出成自由文本，和标准 `tool_calls` 格式对不上，Agent 层解析直接失败。

## 做法

**第一步：盘硬件。** 我的机器是 RTX 3060 12G + 32G 内存。经验公式：显存占用 ≈ 模型权重 + KV cache。7B Q4 约占 5G，剩 7G 给上下文；14B Q4 约 9G，上下文只能开 4K~8K。注意 KV cache 随上下文线性增长，这是最容易被忽略的开销。

**第二步：选运行时。** 三条路按需选：

- **Ollama**：开箱即用，`pull` 完天然暴露 OpenAI 兼容接口，最适合快速接入 OpenClaw；
- **llama.cpp**：控制粒度最细，可用 `-ngl` 做 GPU 层卸载，"半显半存"的过渡态很实用；
- **vLLM**：并发场景再上，单用户自动化暂时用不到。

**第三步：接入 OpenClaw。** `base_url` 指向本地端口，模型名填本地 tag。关键动作是写了一个 10 条用例的冒烟脚本，每条都是真实的 MCP 工具调用意图，跑一遍统计 `tool_calls` 解析成功率。对 function calling 做过微调的模型（如 Qwen 系列 Instruct 版），成功率明显高于同参数量的通用模型。

**第四步：调参数。** 结构化输出场景把 temperature 压到 0.1 以下、top_p 收紧。Agent 路由不需要创造力。

## 踩坑点

- **工具调用格式不兼容**：部分模型把调用意图写成散文。解法是系统提示里给 few-shot 示例，并在 Agent 侧加一层宽松解析兜底；
- **上下文开大就 OOM**：KV cache 比想象中吃显存，8K 上下文比 4K 多占 2G 以上。按实际会话长度估算，再留 20% 余量；
- **冷启动慢**：首次加载 30~60 秒，自动化脚本里要有健康检查和重试，或用 `keep_alive` 让模型常驻；
- **采样参数没调**：默认 0.7 的温度下结构化输出偶发字段缺失，排查了一晚才发现是它。

## 可复用建议

1. **用自己的 workload 评测**，别信排行榜。20 条真实任务的脚本比任何 benchmark 都诚实；
2. **职责分离**：本地小模型干路由和抽取，云端大模型兜底复杂推理，Agent 侧按任务类型路由；
3. **固化模型清单**：模型名、量化版本、上下文长度、实测显存占用、工具调用测试结果，换机器时直接查表；
4. **打日志**：token 数和延迟是后续调优的唯一依据。

## 总结

本地部署的工程含量不高，门槛主要在预期管理：它不会替代云端旗舰模型，但在高频、低复杂度、隐私敏感的 Agent 环节，性价比极高。一张 12G 显卡加一晚上时间，足够把 OpenClaw 的工具调用层搬回家跑。先跑通最小链路，再谈优化。
