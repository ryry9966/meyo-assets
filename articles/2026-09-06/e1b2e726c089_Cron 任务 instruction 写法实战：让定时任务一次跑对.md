## 背景

OpenClaw 这类常驻 agent 支持用 cron 表达式挂定时任务：每天早上汇总一次邮件、每周巡检一次服务状态、定点拉日历。它和交互式对话最大的区别是——**触发时没有上下文、没有追问机会，instruction 就是任务运行时的全部输入**。写得好，任务长期稳定产出；写得随意，就会出现输出格式天天变、半夜推送"今天没有异常"这类糟心结果。

## 三个典型问题

1. **冷启动**：定时任务没有历史对话，"按老样子整理一份"这种指令等于没写。
2. **输出漂移**："总结一下昨天的工作"没有格式约束，模型每次自由发挥，推送忽长忽短。
3. **无人值守**：执行中调用的 MCP 工具需要确认，或数据源挂了，而 instruction 没写兜底策略——轻则挂起，重则编造数据。

## 做法：把 instruction 当作业规格书来写

我目前按六段式组织，每段一两句话：

```text
[目标] 每天 8 点汇总过去 24 小时的邮件。
[来源] 调用 mail MCP 工具，按收件时间过滤。
[输出] 固定模板：紧急事项 / 需要回复 / 可忽略，每节最多 3 条。
[投递] 发送到 Telegram 默认会话；无内容则不发送。
[异常] 工具调用失败时回复"数据源不可用"，不要猜测内容。
[时间] "过去 24 小时"以触发时刻为锚点，按本地时区计算。
```

几点说明：

- **自包含**。不引用"之前的对话"，账号、路径、渠道名直接写进 instruction。
- **格式钉死**。给模板和条数上限，产出才可预期，也方便下游任务解析。
- **静默规则**。明确"无结果就不推送"，否则每天一条废话。
- **异常语义优先**。宁可收到一条失败通知，也不要一份看着正常实则编造的报告。
- **控制长度**。instruction 压在几百 token 内，长材料放文件，引用路径即可。

## 踩坑点

- **时区**：调度器按 UTC 排，agent 按"今天"理解，每天错 8 小时。时间锚点必须显式写。
- **确认型工具**：cron 里调用需要确认的 MCP 工具会卡住任务。要么改配置跳过确认，要么换无确认的实现。
- **重复触发**：任务重跑或补偿触发会重复推送，涉及外发的任务要写明幂等要求，如"同一天只发一条"。
- **过度授权**：写"发现异常就自动处理"，agent 可能真去执行重启。定时任务默认只读加汇报，写操作单独审批。

## 可复用建议

1. 所有 cron instruction 集中放一个文件或仓库，改动走 review，出问题能回滚。
2. 新任务先手动触发两三次（直接让 agent 执行一遍 instruction），确认产出稳定再挂调度。
3. 复杂任务拆成"采集"和"报告"两个任务：前者落文件，后者只读文件，出错能定位环节。
4. 定期翻历史推送，格式漂移了就回来收紧模板。

## 总结

cron 任务的 instruction 本质是一份无人值守的作业规格书：目标、来源、格式、投递、异常、时间，六要素写清楚就能长期稳定跑。核心心法一句话——**假设运行时除了这段 instruction 之外什么都没有**。按这个标准写，大多数"定时任务不稳定"的问题会消失大半。
