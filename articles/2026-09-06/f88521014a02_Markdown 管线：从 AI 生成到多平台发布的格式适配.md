## 背景

用 Agent 产出内容之后，真正耗时间的往往不是写作，而是“最后一公里”：同一份 Markdown，公众号要内联样式的 HTML，知乎对标签有自己的白名单，Hugo/Hexo 依赖 frontmatter，Notion 又是另一套块结构。手工逐平台改格式，枯燥且必然出错。我们在社区跑了几个月自动化发布实践后，把这件事沉淀成了一条可维护的管线。

## 问题在哪

三个层面：

1. **源头不可控**：LLM 输出的 Markdown 方言不统一——有人用 `***` 加粗，有人夹裸 HTML，表格对齐符号五花八门。
2. **目标异构**：各平台渲染引擎差异大，公众号剥离 `<style>`，静态站点要求元数据，数学公式有 KaTeX / MathJax / 图片三种命运。
3. **资源依赖**：本地图片路径、相对链接、防盗链图床，任何一处都会让发布结果“看起来对，点开就崩”。

## 做法：把格式适配当编译问题

核心思路：**以 mdast（Markdown AST）为中间表示，每个平台只是一个序列化器。**

**Step 1 收敛源方言。** 在 Agent 的生成模板里明确约束：CommonMark + GFM 子集，禁用裸 HTML，代码块标注语言，图片必须带 alt。不靠提示词祈祷——生成后用 remark-lint 校验，不达标自动重试。

**Step 2 AST 级转换，不碰正则。** 用 unified/remark 解析成 mdast，所有改写——标题层级映射、图片链接替换、代码块拆分——都在树上做。正则处理嵌套代码块必炸，这条路不要走。

**Step 3 平台适配器插件化。** 每个目标一个 transformer：

- 公众号：md → HTML + 内联样式（juice 或 renderer 直接输出 style），代码高亮预计算成带颜色的 span；
- 静态站点：补 frontmatter，标题、slug、tags 从结构化元数据注入；
- 知乎/掘金：走各自 API 或剪贴板方案，转换时降级不支持的节点（如脚注转文末列表）。

**Step 4 资源处理独立成环。** 图片先上传到目标平台或图床，拿到 URL 后回写 AST 再序列化，避免“先序列化再做字符串替换”。

**Step 5 发布前 lint + 干跑。** 校验死链、图片 alt、超长代码行，输出 HTML 预览 diff，人工确认后再真实推送。

## 踩坑点

- **公众号剥样式**：外链 CSS 全失效，必须内联；且 `<section>` 嵌套过深会被部分客户端渲染异常，层级控制在三四层内。
- **移动端代码折行**：发布端补救很丑，在生成端就限制行宽（建议 80 字符内）更干净。
- **下划线误伤**：中英混排时 `snake_case` 容易被部分平台解析成斜体，lint 阶段加一条规则提前转义。
- **重复转换**：不做内容哈希缓存，改一个错别字会触发全平台重推，幂等性要在管线层保证。
- **API 限流**：多平台并发发布容易被限流，发布器内置指数退避重试，比失败后手工补发靠谱。

## 可复用建议

1. 先定义自己的“最小 Markdown 规范”并 lint 它，这是整条管线的地基。
2. 适配器保持纯函数：输入 AST + 配置，输出目标格式，方便单测和离线调试。
3. 新平台接入只写新的 serializer，核心管线零改动。
4. 保留发布日志（目标、内容哈希、结果、错误），回溯和补偿全靠它。

## 总结

多平台格式适配的本质是编译：LLM 产出的是不稳定的源码，mdast 是 IR，平台适配器是后端，lint 和干跑是 CI。把这条链路搭起来之后，“一次生成、多端发布”才从口号变成每天敢跑的日常流程。适配器模板和 lint 规则集已整理在社区仓库，欢迎按自己的目标平台裁剪。
