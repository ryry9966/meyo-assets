## 背景

Agent 产出的内容越来越多以 Markdown 为载体：写文档、发周报、生成博客。但“生成”只是第一步，真正的摩擦出现在发布环节——同一个 `.md` 文件，丢到 GitHub 上渲染正常，粘进公众号样式全丢；发到掘金代码块高亮错乱；知乎的表格直接被拍平。

## 问题

我们的场景：Agent（通过 MCP 调用本地文件系统与工具）每天产出若干篇 Markdown，需要同步发布到四个目标——静态博客（Hugo）、GitHub 仓库、公众号草稿、掘金。手工复制粘贴改格式，一篇要 15 分钟，还经常漏改图片链接。

核心矛盾在于：AI 负责内容，但格式适配是**确定性工作**，不该交给模型反复执行。正确做法是把“格式”从“内容”里剥离出来，做成一条可复现的管线。

## 做法

整体思路：**canonical source + 多渲染目标**。

1. **规范化源文件**。Agent 只允许写入统一目录，约定 frontmatter（title、tags、targets），全文最多一个 h1。写入后立即用 remark-lint 校验，不合格直接打回给 Agent 重写。
2. **AST 化处理，禁止用正则改 Markdown**。用 unified/remark 把文档解析成 MDAST，所有转换写成作用于 AST 的纯函数：
   - 剥离平台不支持的 HTML 标签，转成等价 Markdown；
   - 图片链接重写：先上传到自有 OSS，再替换为外链；
   - 脚注语法归一（GFM 与 pandoc 写法不同）；
   - 代码块语言按映射表统一（如 `shell` → `bash`）。
3. **按 target 分发转换**。每个平台一个 transform 插件。例如公众号目标渲染成带内联样式的 HTML（公众号编辑器不吃外部 CSS），博客目标则直接输出 Hugo 格式并调整相对路径。
4. **CI 预览 + dry-run**。发布命令默认只产出四个目标文件到 `dist/`，diff 确认后才真正推送。Agent 全程只碰源文件，不碰发布逻辑。

## 踩坑点

- **正则改 Markdown 必炸**。嵌套列表、代码块里的 `#`、表格内的管道符都会误伤。换成 AST 操作后这类 bug 清零。
- **AI 生成内容有三种脏**：标题层级跳跃（开头就是 h3）、代码块缺语言标注、结尾附带“希望对你有帮助”式客套话。归一化阶段统一处理，别指望每个模型都守规矩。
- **公众号图片防盗链**。外链图会被替换或裂图，必须转存，没有捷径。
- **别让 LLM 做格式转换**。试过让模型“改写成公众号格式”，快是快，但每次输出有细微抖动，长文还会丢段落。确定性转换交给脚本，模型只负责写内容。

## 可复用建议

- 转换函数用 fixture 测试：每个平台存两三组典型输入输出对，回归跑一遍，几分钟搭好护栏。
- frontmatter 的 `targets` 字段控制分发范围，某篇只发博客就只走博客管线，避免“全量群发”。
- 公众号排版类库（基于内联样式的渲染器）可以引入，但外面要包一层自己的 transform，别让管线直接耦合第三方实现。

## 总结

Markdown 管线的价值不在于“自动发帖”这个动作，而在于把格式适配从模型行为变成工程行为：可测试、可回滚、可 diff。Agent 写一次，管线渲染 N 次；出了问题改插件，而不是改提示词。
