## 背景

做 Agent 自动化一段时间后，几乎都会撞上同一个瓶颈：能力越多，系统提示词越长。早期常见做法是把所有工具说明、操作规范、领域知识一次性写进 system prompt，结果是上下文占用大、模型在相似能力之间摇摆、改一条说明要通读全文。OpenClaw 的 Skills 机制就是针对这个问题：把能力拆成独立的技能包，平时只保留一行摘要，真正用到时才加载完整内容。

## 问题：全量加载的代价

- **token 成本**：大量技能描述常驻上下文，但绝大部分会话根本用不到；
- **选择准确率**：候选能力太多，模型容易误选或漏选；
- **维护困难**：所有能力耦合在一份大提示词里，牵一发动全身。

## 工作方式：三级渐进加载

Skills 本质是一套约定好的目录结构：

```text
skills/
  pdf-report/
    SKILL.md        # frontmatter + 使用说明
    scripts/
      render.py     # 可执行脚本，不占上下文
  log-analyzer/
    SKILL.md
```

加载分三级：

1. **启动时**：只读取每个技能的 `name` + `description`（几十 token），相当于"目录页"；
2. **触发时**：用户请求命中某条 description，该技能的 SKILL.md 正文才进入上下文；
3. **执行时**：正文引用的脚本和数据文件，仅在真正调用时才被读取或运行。

关键在第三级：脚本是靠"执行"来交付能力的，模型只需知道它存在及如何调用。一个 500 行的处理脚本，上下文成本接近于零。

## 实操步骤

1. 按 SKILL.md 规范写 frontmatter，description 用一句话讲清"什么时候该用我"，带上具体触发词（如"CSV"、"周报"、"回滚"）；
2. 正文只写模型无法自行推断的内容：业务规则、参数约定、边界情况；
3. 能落成脚本的逻辑就落成脚本，SKILL.md 里只留调用说明；
4. 用真实查询做触发测试，看日志确认加载的是预期技能。

## 踩坑点

- **description 太泛会误触发，太窄则永远不命中**。建议拿真实问法反推：这条描述能覆盖几类提问？
- 把多个不相关能力打包成一个巨型技能，触发粒度直接失控；
- SKILL.md 里写死绝对路径或环境变量，换台机器就失效，应改为参数传入；
- 文档与脚本版本漂移：脚本改了说明没改，模型按旧文档调用直接报错。技能要进版本库，和代码一样走 review。

## 可复用建议

- **单一职责**：一个技能解决一类问题，宁可多建几个小的；
- description 是唯一的路由信号，值得反复打磨；
- 给技能加载加日志，统计命中率，长期不触发的技能考虑合并或删除；
- 密钥、内网地址等敏感信息绝不写进技能文件。

## 总结

Skills 的核心不是"更多能力"，而是"更准的加载"。description 当路由、正文当说明书、脚本当执行体，三层各司其职之后，上下文占用与能力数量彻底解耦。对维护多技能 Agent 的团队来说，这是把提示词工程变成可持续工程实践的关键一步。
