## 背景

OpenClaw 的 agent 大部分时间处于空闲，heartbeat 是把它"叫醒"的机制：每到间隔（默认 30 分钟），session 被唤醒，读一遍任务清单（通常是 `HEARTBEAT.md`），决定做事还是跳过。这是一套典型的轮询设计。社区里最常见的问题之一就是：既然都讲究事件驱动了，为什么不全部改成 webhook 推送？

## 问题

轮询和推送其实对应两类不同的需求：

- **轮询**回答的是"有没有什么事需要我现在处理"——包括外部不会主动通知你的事：磁盘快满了、长期任务该收尾了、清单里攒了三条待办。
- **推送**回答的是"外部刚刚发生了什么"——邮件到了、CI 跑完、群里有人 @你。

把两者混在一个机制里，会出现两种典型失败：纯轮询烧 token 且延迟高；纯推送则在 agent 离线、重启、断网时丢事件，而且永远无法"自己想起来做事"。

## 做法

我们的实践是混合架构，三步：

1. **给 heartbeat 降负。** heartbeat 只保留低频、主动式的巡检项，清单每项一行。无事可做时让模型回 `HEARTBEAT_OK` 跳过，单次消耗从几千 token 降到几百。
2. **事件走通道推送。** 邮件、CI、消息平台的事件通过各自的通道插件或 MCP 工具直接推给 agent，延迟秒级。这些入口自带认证和重连，不必自己暴露公网 webhook。
3. **按延迟容忍度定间隔。** 判断标准很简单：一个事件能接受的响应延迟如果小于轮询间隔，就必须走推送；否则留在 heartbeat 里。我们从 30 分钟起步，观察一周日志再调。

## 踩坑点

- **间隔调太短。** 有人为了"实时"把 heartbeat 压到 1 分钟，结果配额一天烧完，而且模型在没有新信息时容易编造动作。先统计"实际触发率"，再定间隔。
- **heartbeat 里干重活。** 巡检时顺手跑了个长任务，阻塞主 session、污染上下文。重活应派发给子任务或后台执行，heartbeat 本身要快进快出。
- **动作不幂等。** 轮询天然可能重复触发（session 重启、间隔重叠），没有幂等键就会出现重复发消息、重复建 issue。每个 heartbeat 动作都应带去重标识。
- **推送静默失败。** webhook 返回 200 但 agent 实际没处理，事件就丢了。至少留一条兜底轮询，作为看门狗定期对账。

## 可复用建议

- 把 heartbeat 当**看门狗**，不是事件总线。事件总线交给通道和插件。
- 保持清单轻量：巡检项超过十行就该拆分或降频。
- 记录每次心跳的"跳过 / 触发"比例，这是调间隔最硬的依据。
- 任何被动机制都要留主动兜底，反之亦然。

## 总结

轮询和推送不是二选一，而是分工：推送负责外部事件的低延迟到达，heartbeat 负责自发的、外部无从通知的巡检。OpenClaw 默认的轮询式 heartbeat 看似"不先进"，但它解决的问题恰恰是纯事件驱动覆盖不了的——让 agent 在没有任何人找它的时候，也能自己想起来该做什么。先跑通默认配置，用日志说话，再决定哪里需要推送，是成本最低的路径。
