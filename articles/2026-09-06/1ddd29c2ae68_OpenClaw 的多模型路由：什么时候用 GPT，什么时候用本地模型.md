## 背景

跑 Agent 的人迟早会算一笔账：一条完整的任务链里，真正需要强推理的步骤往往只占两三成，其余是结构化抽取、格式转换、简单分类。全走 GPT 这类旗舰云端模型，成本和延迟都难看；全走本地小模型，复杂任务又容易翻车。OpenClaw 的多模型路由就是为这个矛盾准备的，但很多人配完之后效果一般——问题通常不在配置本身，而在路由策略。

## 问题

我统计过团队一个月的任务日志，分布大致是：

- 规划与多步工具编排：约 20%，错误代价最高
- 长上下文摘要与改写：约 30%，可容忍小瑕疵
- 结构化抽取、格式化：约 40%，本地小模型基本够用
- 涉及私有数据的任务：占比不定，但去向必须可控

混合路由的难点不是“能不能切”，而是三个：什么时候切、切错了怎么发现、降级链路是否可控。

## 做法

我们的落地步骤，供参考：

1. **先分两档，别贪多。** 起步只做两档：本地 7B 级量化模型处理机械任务，旗舰云模型处理规划和复杂工具调用。档位一多，维护成本指数上升。
2. **按任务类型路由，不按内容猜。** 在 OpenClaw 的 agent / 工具配置里显式声明该任务用哪一档，比运行时让小模型当“裁判”评估难度稳定得多。
3. **显式升级，不做静默降级。** 本地模型置信度低或校验失败时才升级到云模型，并把“为什么升级”写进日志；云模型失败时先重试一次再落本地，避免静默丢质量。
4. **给任务打敏感级标签。** 带 privacy 标签的任务硬性只走本地，在路由层拦截，而不是靠 prompt 里写“请不要外传”。
5. **建一个小回归集。** 20~30 个覆盖各档位的典型任务，每次改路由规则后跑一遍，对比成功率并做人工抽查。

## 踩坑点

- **静默质量下降最危险。** 本地模型生成的工具调用参数“看起来对”，实际缺字段，下游报错时很难想到是路由的锅——我们靠回归集加参数校验才定位到。
- **本地模型的上下文窗口是隐形成本。** 把 30k token 塞给小模型，截断后输出残缺，重试反而更贵。路由前先做 token 预算判断。
- **本地 ≠ 低延迟。** 消费级显卡跑大上下文推理，端到端延迟可能比 API 还慢，别把“本地快”当默认假设，实测为准。
- **升级循环烧钱。** 失败→升级→失败→再升级的链路必须设硬上限（我们设为 2 次），否则一次故障能烧掉一周省下的钱。

## 可复用建议

- 路由决策必须带 reason 字段落日志，事后排障全靠它
- 敏感数据走本地用硬约束实现，别用提示词做软约束
- 成本与质量的衡量口径先定好，否则优化没有锚点
- 每季度复盘一次任务分布，路由规则不是配一次就终身有效

## 总结

多模型路由本质是经济学加可靠性工程问题：不是“哪个模型更好”，而是“哪类任务配哪个档位、错了怎么兜底”。两档起步、按任务类型显式路由、升级可观测、敏感数据硬隔离——这四条做到，OpenClaw 的混合路由就能稳定跑起来，成本能降一半以上，而质量损失控制在基本无感的范围。
