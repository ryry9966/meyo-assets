## 背景

单 Agent 串行跑任务，规模一大就会遇到三个老问题：上下文被中间结果塞满，后期质量明显下降；工具调用一个个排队，纯等待；一个任务里混着检索、处理、校验多种角色，互相污染。OpenClaw 的 agent 支持把子任务委托给 subagent，主 Agent 只负责拆解、派发和汇总，这套模式在批量处理场景下收益最大。

## 问题

举个我们真实跑过的例子：批量处理 20 份文档，每份要做摘要、抽取字段、写入单独的结果文件。单 Agent 做，跑到十几份时开始漏字段、格式漂移；串行耗时一小时以上；中途一次调用失败，恢复起来很别扭。这就是典型的“该并行、该隔离”的活。

## 做法

我们最终的流程分五步：

1. **拆任务**：主 Agent 先把工作切成相互独立的子任务，每个子任务写成一份契约——输入路径、期望输出、写入位置、明确“不要做什么”。
2. **隔离工作区**：每个 subagent 只写自己的输出目录（或临时分支），禁止直接改共享文件。
3. **并行拉起**：用框架的 subagent 能力或脚本并发调用，并发数显式控制在 3–5，避免触发 rate limit。
4. **结构化返回**：要求 subagent 返回固定格式的 JSON 摘要加结果文件路径，不把全文塞回上下文。
5. **确定性汇总**：合并、校验交给脚本做，不靠主 Agent“凭记忆”整合。

伪流程大概是这样：

```text
main:
  tasks = split(original_task)
  for batch in chunks(tasks, 4):
    results += parallel_run(subagent, batch, timeout=120s)
  report = merge_and_validate(results)   # 脚本，不是 LLM
```

## 踩坑点

- **并发写冲突**：多个 subagent 写同一文件，或共用一个有状态的 MCP 工具（比如同一个浏览器实例），必炸。状态类工具要么每实例一份，要么排队。
- **返回结果过长**：不限定格式，subagent 会把整份中间产物贴回来，主 Agent 上下文照样爆炸。契约里写死返回长度。
- **一个失败卡死全局**：每个子任务必须有超时和失败兜底，失败的记下来单独重跑，别让整批重来。
- **拆分不彻底**：子任务之间有隐式依赖，并行就出错。先花五分钟确认依赖关系，有依赖的老实串行。
- **成本翻倍**：并行 N 个 agent，token 就是 N 倍。先用 3–5 个样本试跑，确认质量再放量。

## 可复用建议

- **契约先行**：subagent 的输入输出落成文件和 JSON 格式定义，换模型、换框架都能复用。
- **能用脚本就别用 LLM**：合并、去重、校验这类确定性工作，写十行脚本比让主 Agent 总结可靠得多。
- **三个参数显式配**：并发数、超时、重试次数，写在配置里，不要靠默认值。
- **窄职责**：一个 subagent 只干一件事，职责越窄越稳定，排查也容易。
- **留日志**：每个 subagent 的输入、输出、耗时落盘，出问题能复盘到具体是哪个子任务。

## 总结

subagent 编排的核心不是“更多的 AI”，而是任务边界的工程化：拆得干净、隔离到位、汇总交给确定性代码。建议先挑一个真实的小批量任务把整套流程跑通，再逐步提高并发。编排做得好，主 Agent 上下文干净，整体耗时和稳定性都会有一个台阶式的改善。
