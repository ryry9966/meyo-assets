## 背景

我的 OpenClaw 实例跑了三个月，最初是单模型策略：所有请求——心跳摘要、MCP 工具调用、规划、闲聊——全走同一个旗舰模型。月底看账单才发现，真正需要强推理的任务可能只占请求量的两成，剩下八成是例行的格式化、去重和摘要，全在烧贵的 token。这期做了一次路由重构，把 GPT 和本地模型的分工固定下来，账单降到原来的四成左右，核心任务质量没有回退。

## 问题

多模型路由的核心不是"哪个模型更强"，而是**什么任务配什么模型**。判断维度就三个：

- **能力**：工具调用稳定性、长上下文表现、指令遵循
- **成本**：token 单价，以及本地电费和时间成本
- **隐私**：数据是否允许出本机

## 做法

**第一步：给任务分层。** 我的分层方案：

- **T0**：心跳摘要、定时任务、文本格式化 → 本地 7B 级模型（Ollama 起一个就够）
- **T1**：日常对话、单步检索类 MCP 调用 → 中档云模型
- **T2**：多步规划、代码生成、复杂工具编排 → 旗舰云模型

**第二步：配置主模型和 fallback。** 在 `openclaw.json` 里把主模型设为 T1，fallback 链只用来保可用性，不用来保质量。

**第三步：per-agent 覆盖。** 子 agent 单独指定模型字段——规划类固定 T2，摘要类固定 T0。这是收益最大的一步，多数流量其实活在子 agent 里。

**第四步：隐私绑死。** 涉及本地文件和内网 MCP 的数据源强制走本地模型，哪怕质量打折，这条不参与权衡。

**第五步：观测。** 记录每层的平均 token 消耗和耗时，两周后回头调一次分层，边界经常划错。

## 踩坑点

1. **本地模型的 function calling 不可靠。** 小模型对复杂 tool schema 的参数填充成功率明显下降，会出参数幻觉。T0 只分派无工具或单工具任务，别让本地模型碰多工具编排。
2. **本地不一定快。** 消费级显卡跑 14B 长输出，端到端延迟可能比云 API 还高。路由别只看单价，把延迟也算进成本。
3. **fallback 会掩盖配额耗尽。** 主模型 429 后静默降级，你以为在用旗舰，实际一直跑在中档，规划质量莫名其妙变差还查不到原因。降级必须打日志。
4. **摘要任务从一而终。** 本地模型做记忆摘要、云模型做对话，两边对"重要程度"的判断不一致，会静默丢记忆。摘要链路固定一个模型。
5. **长上下文先压缩再喂。** 本地模型 context window 小，超长输入直接截断会丢关键信息，在路由层前面加一步压缩。

## 可复用建议

- 先跑一周"全旗舰"拿基线账单和质量样本，再逐层下放，每下放一层做一次 A/B 对比，别一刀切。
- 路由规则写成显式清单（任务 → 模型 → 理由），放进 workspace 当文档。改配置时对着清单改，比记忆可靠。
- 本地模型当**兜底**而不是**主力**：云 API 挂了降级保命，恢复即回切。
- 不要追求全自动智能路由。显式规则加定期人工复核，在个人 agent 场景下比任何"自动选择最优模型"的方案都稳。

## 总结

多模型路由的本质是承认任务异质性——心跳摘要和多步规划不该花同样的钱。OpenClaw 的价值在于路由点全部显式可配：主模型、fallback 链、per-agent 覆盖。先把任务分层，让便宜模型吃掉量，让旗舰模型只出现在真正需要它的地方。这套分层跑稳之后，再考虑往精细调。
