## 背景

用 Agent 做日常自动化的人都会遇到同一个问题：每次新会话，助手都是"失忆"的。上下文窗口再大，也只是单次会话的记忆。你上周告诉它"部署用 pnpm 不要用 npm"，这周它照样 `npm install`。模型没有错，是我们没给它装记忆系统。

## 问题：三种常见的失败做法

1. **全量塞上下文**：把历史对话直接拼进 prompt，token 成本线性上涨，关键偏好被噪声淹没。
2. **只存不删**：记忆只增不减，三个月后"用户喜欢深色主题"和"用户最近改用浅色主题"同时存在，互相打架。
3. **裸向量检索**：只靠 embedding 相似度召回，语义相近但已过期的记忆会被优先命中。

## 做法：分层结构 + 五步落地

**第一步，分层。** 我目前把记忆拆成四层：

- 工作记忆：当前会话上下文，不落盘；
- 偏好记忆（profile）：稳定的用户偏好，如语言、代码风格、部署习惯；
- 事件记忆（episodic）：具体交互事实，带时间戳；
- 流程记忆（procedural）：学到的操作步骤，如"这个项目的发布流程是……"。

**第二步，最小存储结构。** 不需要一上来就上向量库，SQLite 一张表就够：

```sql
memory(id, category, content, source,
       confidence, created_at, last_used_at, hit_count)
```

`source` 区分用户显式说出的（"记住：我用 pnpm"）和 Agent 自己推断的，后者 confidence 初始打低。

**第三步，两条写入路径。** 显式写入由用户指令触发，直接入库；隐式提取在会话结束时跑一遍，让模型从对话里抽取"值得记住的事实"，但必须经过去重和置信度过滤才入库。

**第四步，混合检索注入。** 每次会话启动，按 `关键词匹配 + embedding 相似度 + 时间衰减 + confidence` 综合打分，取 top-k（我设 8 条）拼进 system prompt。宁少勿多。

**第五步，读写封装成 MCP 工具。** 给 Agent 提供 `memory_read` / `memory_write` / `memory_delete`，让它能自我管理记忆，用户也能用自然语言增删查。这一步是体验分水岭——记忆从"系统黑盒"变成"可对话的资源"。

## 踩坑点

- **一次性事件被存成永久偏好**。用户某次说"今天想吃辣"，不该进 profile。隐式提取时强制模型区分"事实 vs 临时状态"，临时状态不入库。
- **旧记忆静默覆盖新输入**。检测到冲突时先标记、问一句用户，确认后再更新，不要默认"新的赢"。
- **检索漂移**。embedding 分数高的往往是措辞相近但不相关的记忆，务必叠加关键词和 recency 权重。
- **敏感信息入库**。API key、密码类内容在工具层做拦截过滤，别指望模型自觉。
- **没有遗忘机制**。`last_used_at` 超过 60 天且 `hit_count` 为 0 的记忆，降权或归档。

## 可复用建议

- 先用结构化存储跑通闭环，再考虑向量库，顺序别反；
- 给用户一个"列出你记住的关于我的所有内容"的指令，可解释性比准确率更早决定信任；
- 记忆命中要打日志，否则没法评估召回质量；
- 定期跑一次"记忆整理"任务：合并重复、降权过期、归档低置信条目。

## 总结

记忆系统的本质不是"记住更多"，而是"记对、记新、该忘就忘"。分层结构解决记什么，混合检索解决怎么取，MCP 工具化解决谁来管，遗忘与冲突策略解决怎么活得久。从一张 SQLite 表加两三个 MCP 工具开始，比一上来就搭完整 RAG 管线实在得多。欢迎在评论区交流你们的记忆层设计。
