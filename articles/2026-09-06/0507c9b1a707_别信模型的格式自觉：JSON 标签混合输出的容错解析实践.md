## 背景

在 OpenClaw 的 Agent 工作流和插件开发里，让模型按约定格式输出结构化数据是最常见的上下游契约：prompt 里要求“把结果包在 `<json>` 标签里”或“用 ```json 围栏输出”，下游做字符串截取再 `parse`。Demo 阶段一切正常，一旦跑批，格式漂移就开始了。

## 问题：实测遇到的几种“违约”

- 同一个 prompt，有时带围栏，有时裸 JSON；
- 标签名变形：`<JSON>`、`< json >`，甚至自作主张换成 `<output>`；
- 标签内外夹带解释文字，偶尔还把 markdown 代码块嵌进标签里；
- 中文语境下出现全角标点、中文引号、尾逗号；
- 低频但致命：输出两个拼接的 JSON 对象，或对象数组来回切换。

先找 `<json>` 再 parse 的朴素写法，线上很快会被一条坏数据打穿整个自动化任务。

## 做法：分层降级的解析管道

核心思路是把**提取**和**解析**拆开，各自做多级 fallback，最后强制过 schema 校验，失败进入带错误反馈的重试：

1. **提取层**：依次尝试 原文 → 剥围栏 → 取标签内文（标签名做大小写与空白容忍）→ 括号配平扫描第一个完整的 `{...}` / `[...]`。括号扫描必须跳过字符串字面量内部的花括号。
2. **修复层**：去 BOM/零宽字符、全角标点转半角、去尾逗号。只做低风险修复，不猜字段。
3. **解析层**：先标准 `parse`，失败退到容错库，仍失败记 None 并保留原始输出。
4. **校验层**：pydantic/zod 校验字段与类型，不通过视同解析失败。
5. **重试层**：把“原始输出片段 + 具体解析错误”拼回 prompt 让模型自修，上限 2 次，温度调低。

```python
def parse_llm_json(text: str, schema):
    for raw in extract_candidates(text):   # 围栏/标签/括号配平，多路候选
        s = light_clean(raw)               # 全角标点、BOM、尾逗号
        for parse in (json.loads, repair_json):
            try:
                return schema.model_validate(parse(s))
            except Exception:
                continue
    raise ParseError(raw_text=text)        # 落库告警，不无限重试
```

## 踩坑点

- `/{.*}/` 贪婪匹配会把解释文字一起吞掉，非贪婪又在嵌套处提前截断。最终都要回到字符串感知的括号配平，别指望一行正则解决。
- 标签内容里再出现 ``` 围栏时，非贪婪匹配会提前闭合，提取出半截 JSON。先取标签、再剥围栏，顺序别反。
- 重试时不带具体报错，模型大概率原样复读；把 parse 的报错位置和行号带回去，修复率明显提高。
- `response_format` / JSON mode 不是银弹：各 provider 支持度不一，外层契约一变就失效，fallback 管道仍然要留。
- 别追求 100% 修复率。超过重试上限就落库告警、人工看 badcase，比无限重试烧 token 划算。
- 日志里务必保留原始输出（截断也行），否则事后无法区分是 prompt 问题还是解析问题。

## 可复用建议

- 解析器做成独立模块 + 单测，线上坏样本（脱敏后）直接沉淀成用例，回归有据可依。
- 契约尽量简化：能要纯 JSON 就别套标签，能套标签就别再要求 markdown。格式要求越多，违约面越大。
- schema 校验放最外层，任何 fallback 的漏网之鱼都会被拦住，保证下游拿到的永远是合法结构。
- 新接模型或升版本时，先跑一小批格式回归再放量。

## 总结

LLM 输出解析的防御性编程，本质是把概率性的文本翻译成确定性的结构：提取降级、轻量修复、严格校验、带反馈重试、超限落库。一句话概括原则——**契约要严，解析要松**：对模型的输出保持宽容，对进入下游的数据保持严格。
