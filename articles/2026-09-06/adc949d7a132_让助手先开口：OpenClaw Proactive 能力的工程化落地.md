## 背景

大多数 agent 的默认工作模式是拉式的：你发一条消息，它回一条。这套模式在"我有一个问题"的场景下很好用，但真正省时间的往往是另一类事——CI 挂了你还没看到，它已经把报错摘要和嫌疑 commit 整理好了；明天两个会撞车，它提前一晚提醒你改日程。这就是 proactive 能力：不等用户开口，由事件或时间驱动 agent 先行动。

OpenClaw 在网关层其实已经给了三块积木：cron（定时触发）、webhook（外部事件注入）、heartbeat（周期性自检）。难点不在"能不能做"，而在怎么做得不像一个烦人的告警系统。

## 问题

实践中主动式 agent 有三个典型困境：

1. 事件量大，每条都过一遍模型，token 成本和噪音一起爆炸；
2. agent 自己的动作会产生新事件，再把自己唤醒，形成回环；
3. 打扰过度，用户把通知一关，proactive 的价值直接归零。

## 做法与步骤

我的落地路径分五步：

1. **梳理事件源并分流**。定时类任务（日报、巡检）走 cron，不要压在高频 heartbeat 上；外部事件（CI、issue、邮件）统一走 webhook 进固定入口。
2. **廉价预过滤**。规则先行：阈值判断、关键词匹配、去重检查，命中了才唤醒模型。HEARTBEAT.md 只保留 3–5 个高信号检查项，每项写清楚触发条件，并明确"无事可报就保持沉默"。
3. **输出分三级**：silent（只写日志）、digest（攒到固定时间发摘要）、ping（立即打扰）。配静默窗口，比如 23:00–8:00 只允许 digest。
4. **动作白名单 + 确认门槛**。低风险动作（记日志、改草稿、生成摘要）自动执行；有外部副作用的（给第三方发消息、花钱、删东西）只出建议，等人确认。
5. **幂等与去重**。事件带来源标记和 ID，agent 自己产生的事件打上 own 标签并过滤；通知状态落到本地文件，避免同一件事说两遍。

## 踩坑点

- **通知疲劳**：默认心跳间隔下，模型每次醒来都"觉得有事要汇报"，一晚上 ping 我五次。解法是把"没有值得说的事就不要输出"写进提示词，并把汇报门槛量化（只有失败或超阈值才报）。
- **自触发回环**：agent 往仓库 push，CI webhook 又把它叫醒，它再发消息再触发。解法是来源过滤 + 冷却时间，同类事件 N 分钟内只处理一次。
- **HEARTBEAT.md 写成愿望清单**：十几条检查项每次心跳全量跑，成本翻倍还互相干扰。清单要短，低频检查挪去 cron。
- **时区与静默没配**：凌晨三点收到"早安日报"。静默窗口要在网关层硬性配置，不要指望模型自己判断。

## 可复用建议

- 从 2–3 个高信号、低噪音的场景起步：CI 失败、日程冲突、证书/磁盘到期，跑顺了再扩。
- 先 dry-run 一周：所有主动行为只记日志、不发通知，统计命中率和误报率，数字说得过去再放开打扰。
- 每次主动行为落一条审计日志（触发源、依据、动作），出问题能回溯"它为什么找我"。
- 校准标准想成"你希望一个靠谱同事怎么找你"，而不是"监控告警怎么发"。前者是帮忙，后者迟早被静音。

## 总结

Proactive 的价值不在"做得多"，而在"说得准"。工程上的核心是三件事：模型之前先过滤，输出按打扰程度分级，权限按副作用大小收紧。先把误报率压下来，再谈自动化程度——一个安静时没存在感、出事时第一时间出现的助手，才是用户愿意长期留着的助手。
