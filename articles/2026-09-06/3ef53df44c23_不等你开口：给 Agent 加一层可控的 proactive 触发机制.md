## 背景

多数人用 Agent 的方式仍是拉模式：人发指令，模型执行。而 OpenClaw 这类常驻助手网关的出现，让推模式成为可能——助手长期在线、有定时任务、挂着 MCP 工具、能接事件回调，具备"主动出手"的全部基础设施。但不少部署止步于每天推一条早安摘要，proactive 的真正价值没被用起来。

## 问题

主动能力面临两个矛盾：

1. **不主动**，助手退化为一个带延迟的问答机；**太主动**，通知轰炸会迅速耗尽用户信任。
2. 主动执行写操作风险高：触发时的上下文可能已经过时，agent 基于错误前提动手，损害比不作为大得多。

所以核心问题不是"能不能主动"，而是**什么情况下主动、主动到什么程度**。

## 做法：拆成三层，各自可控

**触发层**——所有主动行为必须有明确来源：

- 定时：cron 驱动，如每天早八点拉取 CI 状态、日历、未读 PR；
- 事件：webhook / MCP 事件通知，如 PR 合并、构建失败；
- 巡检：agent 周期性观察某状态，如磁盘水位、订阅源更新。

**决策层**——触发不等于行动，中间加一道门槛判断"值不值得打扰用户"。用一个轻量 prompt 让模型输出三档结论：`ignore`（不提）、`digest`（攒进摘要）、`alert`（立即通知）。判断素材必须带原始触发内容和相关上下文，不允许裸判断；阈值宁可调高。

**行动层**——写操作默认"备好不执行"：agent 把邮件草稿、工单内容、变更 diff 准备好，推一张待确认卡片，用户回一句才落地。读操作（汇总、检索）可以直接做，但输出必须附来源，方便事后核查。另外给每类触发设**日配额 + 免打扰时段**，超限自动降级为 digest。

## 踩坑点

1. **自触发循环**：agent 主动发出的消息又触发了自己的事件监听，形成风暴。给所有主动产出打来源标记，事件消费侧统一过滤。
2. **过时上下文**：cron 任务引用了三天前的会话记忆，结论全错。主动任务每次重新拉取事实源，记忆只做背景、不做依据。
3. **Token 成本失控**：巡检频率高，每轮都带全量系统提示词。判断环节换小模型或精简提示词，主模型只处理升级后的 alert。
4. **信任透支**：上线头两天 alert 太多，用户开始无差别忽略推送，之后真警报也失效。灰度期把 alert 档全部降为 digest，观察一周误报率再放开。

## 可复用建议

- 先做只读 proactive（摘要、预警），稳定两周后再开写操作；
- 所有主动行为落日志：触发源、决策理由、执行结果，全程可审计；
- 每条 proactive 流程留总开关和一键降级；
- 三档决策、配额、静默时段，三件套缺一不可。

## 总结

proactive 不是把 agent 调得更"聪明"，而是给它一套克制的触发与门控机制：触发层解决"何时醒"，决策层解决"说不说"，行动层解决"做多少"。三层拆开后每一层都能独立调试、独立回滚——这正是它比一坨自动化脚本更可维护的原因。建议从一条每天早上的只读摘要起步，跑两周看误报率，再决定往前走多远。
