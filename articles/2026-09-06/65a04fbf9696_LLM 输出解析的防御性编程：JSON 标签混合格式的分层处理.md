## 背景

在 OpenClaw 的插件和自动化流程里，LLM 输出经常被当结构化数据用：Agent 之间传递任务、MCP 工具返回结果、插件解析模型给出的配置。我们习惯在 prompt 里约定格式，比如“只输出 `<json>...</json>` 标签包裹的内容”。但只要跑得够多，格式一定会漂移——同一个 prompt，长上下文和短上下文、不同模型版本，输出形态可能完全不同。

## 问题

翻了一段线上日志，同一约定下至少出现七种形态：

1. 裸 JSON；
2. 代码围栏包裹；
3. `<json>` 标签，但大小写随机（`<JSON>`、`<Json>`）；
4. 围栏外面又套标签，或标签里再套围栏；
5. 前后带解释性文字；
6. JSON 内部有尾逗号、`//` 注释，value 里混入全角引号；
7. 因 max_tokens 截断，围栏或标签根本没闭合。

解析器只要假设其中一种形态，流水线就会“偶发”报错——这是最难受的一类问题，单独重跑往往复现不了。

## 做法

我的方案是把提取逻辑收敛到一个模块，按“从干净到脏”分层尝试：

1. **直接解析**：先 `json.loads`，处理裸 JSON；
2. **剥围栏**：去掉代码围栏和语言标记后再解析；
3. **标签提取**：正则 `<\s*json[^>]*>(.*?)</\s*json\s*>`，忽略大小写、开 dotall，取最后一个匹配；
4. **括号配平扫描**：正则搞不定嵌套时，做字符串感知的花括号配平，找到第一个完整的 JSON 对象；
5. **容错解析**：以上都失败，再用 json5/修复库处理尾逗号和注释，结果标记为 repaired；
6. **Schema 校验**：pydantic 过一遍，把“解析失败”和“字段不符”分成两类错误上报。

配套两条规则：每层命中都写日志（strategy 字段，方便统计哪层扛了多少量）；检测到括号不配平且围栏未闭合的，判定为截断，走重试路径而不是修复——截断修出来的数据大概率是错的。

## 踩坑点

- 正则 `.*?` 处理不了嵌套对象，括号配平扫描绕不开；
- 配平扫描必须跳过字符串字面量，否则 value 里一个 `"}"` 会让扫描提前截断；
- 中文 value 里的全角引号是合法内容，只有出现在 key 和结构位置才算错，不要做全局替换；
- 多个候选块时我选“最后一个能解析的”：模型常在结尾自我纠正，后面的块往往才是最终答案；
- 静默修复会掩盖问题：修复率要进监控，超过阈值说明该改 prompt 或换模型，而不是继续加解析层；
- 截断和“格式脏”是两类故障，混在一起修不如分开处理。

## 可复用建议

- 解析逻辑只放一个模块，策略顺序固定，命中层写进遥测字段；
- 把线上真实坏样本沉淀成单测用例，解析器改动走版本化；
- 平台支持结构化输出/工具调用时优先用，但 fallback 解析器永远保留；
- prompt 里的格式约定照写，同时默认它一定会被违反。

## 总结

防御性解析不是不信任模型，而是承认“格式漂移是输入的一部分”。把脏处理收敛成一条可观测的流水线，比在每个调用点散落 try/except 靠谱得多，也让“该修 prompt 还是该修代码”变成一个可以拿数据回答的问题。欢迎在社区帖子里贴你遇到的坏样本，攒多了可以一起维护一份公共测试集。
