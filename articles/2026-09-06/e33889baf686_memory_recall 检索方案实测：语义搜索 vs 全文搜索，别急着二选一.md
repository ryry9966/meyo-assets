## 背景

OpenClaw 助手跑了一段时间后，memory 里积累了几千条会话摘要、用户偏好和项目上下文。`memory_recall` 就是把这些旧记忆捞回来的入口——捞不准，助手要么“失忆”，要么一本正经地编。我们在自托管实例上分别接了语义检索和全文检索，跑了两周真实流量，这里记录对比结论。

## 问题

两条路线各有明显短板：

- **语义搜索**（embedding + 向量库）：擅长“意思相近”的召回，比如问“上次那个部署脚本”能命中“CI 发布流程”的记录；但对精确标识符（错误码、模块名、用户 ID）召回质量差，还引入了 embedding 服务依赖。
- **全文搜索**（FTS5/BM25）：对关键词、代号、错误码是精确命中，零额外依赖；但对换一种说法的查询几乎无能为力，中文分词配置不当会进一步恶化。

单独用哪个都有硬伤。真正的问题是：在我们的真实查询分布下差距有多大，值不值得上混合方案。

## 做法

1. 抽样 200 条真实 recall 查询，人工标注“期望命中的记忆条目”，做成小型评测集。
2. 两个索引指向同一份记忆数据：FTS5 建倒排（配 jieba 分词），另一路走 bge-m3 embedding + sqlite-vec。
3. 分别统计 Top-5 / Top-10 命中率；再加一路混合检索（两路结果用 RRF 融合）做对照组。
4. 对比 recall@k、平均延迟和索引维护成本。

## 实测结论

- Top-5 命中率：语义约 62%，全文约 55%，混合约 81%。提升来自两类查询互补——语义补上了换说法的查询，全文补上了精确标识符。
- 语义检索对 embedding 模型很敏感：换模型就得全量重建向量，这个维护成本别低估。
- 混合方案延迟增加约 30–40ms（两路检索 + 融合），对助手场景完全可接受。

## 踩坑点

1. **中文全文检索必须配分词器**。FTS5 默认按空格切，中文查询基本失效，这是最容易翻车的一步。
2. 记忆条目过长时检索质量骤降。按“一条记忆一个事实”的粒度切分，比按固定 token 数切分效果好得多。
3. embedding 维度别贪大。记忆量在 10 万条以内时，1024 维的收益趋近于零，反而拖慢建库和查询。
4. 评测集别有偏。我们早期全是“改写型查询”，导致低估了全文检索对标识符的价值，差点误判方案。

## 可复用建议

- 记忆量小（几千条以内）且查询偏精确匹配：FTS5 + 好的中文分词器就够了，别过度设计。
- 记忆量大、查询口语化：直接上混合检索，RRF 融合是性价比最高的做法，不需要训练任何模型。
- 永远保留一份 100–200 条的评测集，每次改检索参数跑一遍，比肉眼对比靠谱得多。
- recall 未命中的查询记得落日志，评测集从这里持续补充，形成正反馈。

## 总结

语义和全文不是二选一，而是召回分布互补的两路信号。对 OpenClaw 这类需要长期记忆的助手，混合检索 + RRF 是当前最稳的工程解：实现成本低、无训练依赖、结果可解释。先建评测集，再谈优化——这是这次实测最大的教训。
