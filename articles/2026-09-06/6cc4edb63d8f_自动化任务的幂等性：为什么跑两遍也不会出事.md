# 幂等性：让自动化任务敢被重跑

## 背景

在 OpenClaw 的日常使用里，你的大部分自动化任务本质都是「可重复触发」的：cron 定时器到点就跑、webhook 超时会重投、Agent 调 MCP 工具报错时会自己重试、网关重启后队列里的任务继续执行，再加上你自己手滑点一次「重新运行」。**重试不是异常路径，是常态**。写任务时如果不假设它会被跑两遍，迟早还债。

## 问题

很多脚本是按「一次性动作」写的：发一条消息、建一张工单、往日历插一个事件。第一次跑都对，重试之后就出事——消息发两遍、工单建两条、事件重复。这就是非幂等：同一个操作执行一次和执行两次，最终状态不一样。

## 做法

1. **先分类。** 只读操作天然幂等；带唯一键的写入（upsert、覆盖写）天然幂等；真正麻烦的是追加/触发型操作（create、send、append）。
2. **构造确定性键。** 别用随机 UUID，用业务语义拼 key：`日期 + 来源 + 目标哈希`。任务重跑多少次，key 都一样，去重才有依据。
3. **让存储层兜底。** 用唯一索引 + upsert（如 `INSERT ... ON CONFLICT DO NOTHING`）替代「先查再插」。先查后写有并发竞态，约束才是最后防线。
4. **外部 API 用幂等机制。** 不少 API 支持 Idempotency-Key，把第 2 步的 key 传进去。
5. **通知类操作记小账本。** 一张 SQLite 表（key、status、updated_at）够了：先记意图，执行，再改状态；下次跑，已完成的直接跳过。
6. **尽量声明式。** 与其「执行动作」，不如「声明期望状态」：脚本对比实际与期望，有差异才收敛，没差异就什么都不做。Terraform/Ansible 的思路完全适用于 Agent 任务。

## 踩坑点

- **先查后插的竞态**：两个并发任务都查到「不存在」，然后都插入。别赌时序，上存储约束。
- **随机 ID**：每次运行重新生成 UUID，等于永久关闭去重。
- **账本与动作不同步**：消息发出去了，改状态失败，下轮就会重发。接受「至少一次 + 接收端去重」，别追求绝对精确一次。
- **Cron 重叠**：长任务和下一轮撞车。锁（文件锁/advisory lock）解决并发，幂等解决重试，两个都要有，不能互相替代。
- **Key 里的时区坑**：一次按 UTC、一次按本地时间，「今天」不是同一天，直接重复。
- **盲目重试非幂等 POST**：支付、发送类接口，没有幂等 key 就别放进自动重试路径。
- **MCP 工具要服务端幂等**：Agent 在报错语义模糊时会重复调同一个工具，别指望调用方永远小心。

## 可复用建议

- MCP 工具和脚本默认写成 ensure/upsert 风格。
- 全局留一张去重账本表，比事后修复便宜得多。
- 提供 dry-run 模式：先只记录「将要做什么」，一眼看出哪些操作会跑两次。
- 把幂等写进测试：连续跑两遍任务，断言第二遍状态无变化。
- 触发和效果分离：触发可以重复，效果必须去重。

## 总结

幂等不是运气好，是设计决策。Agent 自动化里重试和重跑不可避免，让每次写入要么天然收敛，要么有确定性 key 加存储约束。做到这一点，「再跑一遍」就只是一次无害的确认。
