## 背景

OpenClaw 的工作区里有一批约定文件：AGENTS.md 管流程，TOOLS.md 管工具，MEMORY.md 管记忆，而 SOUL.md 管“这个 agent 是谁”。它会在每次会话启动时注入 system prompt，是少数你能直接用 Markdown 控制、且立即生效的“人格层”。

很多人的 SOUL.md 停留在“你是一个友好的助手”这一行。不算错，但等于放弃了这层配置面。

## 问题

不带人格与边界定义的 agent，实践中会遇到几类典型状况：

- **语气漂移**：同一个 agent 在聊天渠道里话痨，在 CLI 里冷冰冰，长会话后半段开始自创口头禅。
- **过度顺从**：随口一句“帮我把 cron 里的任务清一下”，它真去执行了，没有确认环节。
- **边界模糊**：不知道哪些该问、哪些该做、哪些直接拒绝，行为全靠模型默认值兜底。
- **排障困难**：出问题时说不清“它为什么这么回答”，因为根本没有成文依据。

这些本质上都不是模型能力问题，而是规范缺位。

## 做法

一份能长期维护的 SOUL.md，建议控制在 100 行以内，分四段写：

1. **身份**：两三句话，写清名字、定位、服务对象。“你负责维护我的个人工作区、消息和自动化任务”，比“你是一个强大的 AI”有用得多。
2. **语气**：给正反例，不给形容词。“回复短句、先结论后细节；不用客套开场白；用户说‘随便’时给默认方案而不是追问。”
3. **边界**：最有价值的部分。明确列出——哪些操作需要确认（删文件、给真人发消息、花钱）；哪些直接拒绝（读取某些目录、付费操作）；冲突时以谁为准（安全 > 用户指令 > 效率）。
4. **降级策略**：拿不准时怎么办——问一句、声明假设后继续、还是停下等指令。

示例骨架：

```markdown
# SOUL

## 身份
我是 kira，维护这台机器上的个人工作流与消息渠道。

## 语气
- 中文短句，先结论后细节
- 禁止：客套开场白、无信息量的道歉

## 边界
- 需确认：rm、git push --force、对外发消息
- 拒绝：读取 ~/.ssh、任何付费操作
- 与 AGENTS.md 冲突时，安全条款优先

## 拿不准时
先复述理解，得到确认再动手。
```

写完放进 git。SOUL.md 是配置，不是日记，要有 diff 和回滚。

## 踩坑点

- **写太长**。塞满 500 行人生哲理，注入后被稀释，关键边界反而失效。边界条款要少而硬。
- **和 AGENTS.md 抢地盘**。SOUL.md 管“是谁、什么不能做”，AGENTS.md 管“怎么干活”。同一规则写两处，迟早改漏一处。
- **只有形容词没有行为**。“保持专业”无法执行；“报错时先贴日志再给猜测”可以执行。
- **改完不生效就怀疑人生**。会话中途不热加载，重开会话或重启 gateway 再验证。
- **把密钥、地址写进去**。它会进 system prompt，也可能随日志外泄。

## 可复用建议

- 用“红队三问”做回归测试：让它删一个文件（看是否确认）、发一条消息（看是否先摘要）、问一个边界话题（看是否拒绝）。每次改完跑一遍。
- 人格改版走 PR，让同好 review，别人一眼能看出你写的是“愿望”还是“规范”。
- 边界用“白名单 + 默认拒绝”，通常比罗列黑名单稳。

## 总结

SOUL.md 的价值不在让 agent 更“像人”，而在把你对行为的模糊预期，变成一份可版本化、可测试、可回滚的规范。先写 20 行真的会被执行的条款，比写 200 行人设小作文有用。人格是迭代出来的，不是一次写完的。
