## 背景

OpenClaw 插件和 MCP 工具链里，大量环节依赖模型输出结构化数据：工具参数、路由决策、信息抽取。只要要求模型"把 JSON 混在自然语言里输出"，格式就不可控。即便有 JSON mode / structured output，工程上总有一部分调用走不了：跨 provider、走中转模型、或者业务上本来就要求边解释边给数据。所以防御性解析不是可选项，是基础设施。

## 问题

翻一翻线上日志，同一个 prompt 的输出大致有这几种形态：

- 直接是合法 JSON；
- 被 ```json 围栏包裹；
- 前后带说明文字，JSON 夹在中间；
- 被自造标签包住，比如 `<result>...</result>`；
- "接近 JSON"的东西：单引号、尾逗号、注释、字符串里没转义的换行。

麻烦在于这些形态随机出现。裸写 `json.loads()` 意味着链路成功率取决于模型状态，每次失败重试都是真实的延迟和 token 成本。

## 做法：分层处理，每层只做一件事

核心思路是"提取 → 清洗 → 修复 → 校验 → 兜底重试"，逐层降级：

1. **提取层**：先直接解析；失败后按优先级取候选——围栏内容 > 标签内容 > 括号平衡扫描。括号扫描必须用状态机跳过字符串内部，否则字符串里的大括号会破坏深度计数。
2. **清洗层**：只做无损操作，比如去尾逗号。
3. **修复层**：`json_repair` 这类库做宽松兜底。
4. **校验层**：Pydantic schema 校验，parse 成功只是及格线。
5. **重试层**：把解析错误信息回喂给模型。

一个精简版骨架（生产版建议把清洗叠加到每层候选上）：

```python
import json, re
import json_repair

TAG_RE = re.compile(r"<(?:result|json|output)>(.+?)</(?:result|json|output)>", re.S | re.I)

def extract_candidate(text: str) -> str:
    # 围栏：取第一个 ``` 到最后一个 ```，避免嵌套代码块被非贪婪正则截断
    if text.count("```") >= 2:
        seg = text[text.index("```"):text.rindex("```")]
        return re.sub(r"^```(?:json)?\s*", "", seg)
    m = TAG_RE.search(text)
    return m.group(1) if m else text

def balanced_object(text: str):
    """返回第一个括号平衡的 {...}，字符串内部不参与深度计数"""
    depth, start, in_str, esc = 0, None, False, False
    for i, ch in enumerate(text):
        if in_str:
            if esc: esc = False
            elif ch == "\\": esc = True
            elif ch == '"': in_str = False
        elif ch == '"':
            in_str = True
        elif ch == "{":
            if depth == 0: start = i
            depth += 1
        elif ch == "}":
            depth -= 1
            if depth == 0 and start is not None:
                return text[start:i + 1]
    return None

def parse_llm_json(raw: str):
    cand = extract_candidate(raw.strip())
    attempts = [
        cand,
        balanced_object(cand) or cand,
        re.sub(r",\s*([}\]])", r"\1", cand),   # 尾逗号
    ]
    for s in attempts:
        try:
            return json.loads(s)
        except (json.JSONDecodeError, TypeError):
            continue
    return json_repair.loads(cand)             # 最后的宽松修复
```

## 踩坑点

1. `find('{')` + `rfind('}')` 的经典写法，遇到字符串值里含大括号的样本就崩（比如要求输出里带代码片段）。
2. 非贪婪正则 ```` ```(?:json)?(.*?)``` ```` 在输出内含嵌套代码块时会截断到内层围栏，取首尾围栏区间更稳。
3. 全局替换单引号、中文引号来"修 JSON"，会破坏字符串字面量本身——用户文本里恰好有引号就完了。引号修复永远放最后一层。
4. json5 / json_repair 的宽松是双刃剑，`NaN`、`Infinity` 会被默默接受，下游数值计算直接带毒。
5. 解析成功 ≠ 数据正确。枚举越界、类型对但取值错，都要靠 schema 层拦，Pydantic 比裸 dict 靠谱得多。
6. 失败时只记异常不记原始输出，复盘时两眼一抹黑。原始输出必须完整落日志。

## 可复用建议

- **解析器写成纯函数，坏样本进 fixture**：每次线上翻车就把那条原始输出存成 pytest 用例。半年后这个模块会是全仓库最稳的代码。
- **prompt 侧照做但不信任**：few-shot 给格式示例、明说"只输出 JSON，不要解释"，能消掉大部分脏输出，剩下的交给解析器。
- **能用 structured output 就优先用**，防御解析是兜底，不是首选方案。
- **重试时带错误回喂**："你的上一次输出无法解析，错误是 XXX，请修正"，比原样重发有效得多。
- **schema 设计降低模型难度**：能用 enum 就别用自由字符串，能平铺就别深嵌套，模型在深层嵌套上的错误率明显更高。

## 总结

一句话：假设每一次输出都是脏的，解析链路按"提取→清洗→修复→校验→兜底重试"分层，每层单一职责、可单测、可观测。防御性解析的价值不在某个巧妙的正则，而在于让 prompt 约束、schema 校验和日志各自承担明确责任，链路才不会因为模型一次"自由发挥"整体雪崩。建议直接把上面的骨架搬进你的插件 utils，从下一个坏样本开始养用例。
