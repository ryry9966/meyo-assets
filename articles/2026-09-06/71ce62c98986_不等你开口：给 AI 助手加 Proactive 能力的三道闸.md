## 背景

多数 Agent 交互还是"你问我答"。但日常使用里价值最高的往往是另一类：助手在你没开口时就注意到事情并处理掉——早上汇总昨夜的 CI 失败、磁盘快满时提醒、长任务跑完主动通知。等定时调度、Webhook、MCP 工具这套基础设施成熟后，把被动应答的机器人升级成主动干活的助手，不需要多少黑魔法，但需要一点工程设计。

## 问题

直接让 Agent"主动一点"几乎必然翻车，常见三种死法：

1. **噪音轰炸**：模型没有成本概念，每小时挤一条"没事但我觉得该汇报"的消息，三天后你开始无视它的一切推送。
2. **越权行动**：你让它"检查一下"，它理解为"检查并顺手修好"，悄悄改了配置、给同事发了消息。
3. **成本失控**：主动任务 24 小时在跑，轮询间隔设小一点，月底账单教你做人。

本质矛盾是：proactive 的价值来自"时机对"，而模型天然倾向"多说多做"。所以核心不是让 Agent 更主动，而是给它装三道闸。

## 做法：触发层 → 门槛层 → 执行层

**1. 设计触发源，别让 Agent 自己醒。** 三类触发挂在外部：时间型（cron，如每天 8:30 晨报）、事件型（Webhook / 文件监听，如 PR 合并、日志报错）、状态型（低频轮询 + 阈值，如磁盘超 90%）。

**2. 触发与决策分离，先过门槛再叫醒大模型。** 触发层只投递紧凑的结构化载荷（事件类型、关键数据、时间戳），不要把历史上下文全塞进去。门槛层用便宜的手段先过滤：规则（阈值、白名单）加一次低成本模型判断——"这事值得打断用户吗"。大多数噪音在这一层被拦下，写日志而不是推送。

**3. 动作分级。** 静默（记日志、更新状态）、批量（攒进每日摘要）、即时（真紧急才推，消息里必须带上"为什么找你"）、需确认（发消息给第三方、花钱、删除等一切有副作用的动作，默认进确认队列）。

**4. 限流与审计。** 每个技能配冷却时间（同主题 4 小时不重复推）和每日预算（调用次数 + token 上限），所有主动行为落日志，每周复盘调阈值。

## 踩坑点

- **Webhook 重试导致重复触发**：给每个事件生成幂等键，门槛层查重。
- **时区**：cron 按 UTC 跑，人在东八区，晨报变下午报。调度层显式声明时区。
- **上下文膨胀**：主动任务没有"本轮对话"可依赖，早期把最近 N 条历史全带上，单次触发的 token 是平时几倍。改成按技能预置一份"最小上下文卡"。
- **模型把"查看"升级成"处理"**：工具权限按技能收窄，只读技能不给写工具，别指望 prompt 能管住它。
- **告警疲劳复发**：上线两周推送变多，是阈值没跟着环境变。把"每周日志复盘"本身做成一个 cron 任务。

## 可复用建议

1. 新技能先只做"读 + 记录"，跑两周看日志质量，再解锁推送和写动作。
2. 默认摘要制，即时推送是特权不是默认。
3. 门槛层优先用规则，模型判断留给规则写不出的模糊场景。
4. 每个技能必须有一键关闭开关，且关闭动作不经过模型。

## 总结

Proactive 的工程核心不是"让 Agent 更聪明"，而是把主动权拆成三件事：谁触发、值不值得打扰、能做什么。触发、门槛、分级权限三道闸装好之后，助手才从"随叫随到"变成"不必你叫"。从小处做起，先让它的主动安静地有价值，再谈更多。
