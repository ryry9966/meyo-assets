## 背景

用 OpenClaw 做自动化时，主 agent 默认是“一条线干活”：先查资料、再处理文件、再跑任务、最后汇总。事情一多，上下文很快被中间产物塞满，速度也上不去。subagent 机制提供了另一条路：主 agent 只做拆解和汇总，具体的活儿分发给多个子 agent 并行执行。最近我用这套模式重写了每日巡检流程，把整体耗时压到原来的三分之一左右，这里记录一下做法和坑。

## 问题

原场景是每天巡检几十个数据源再合成日报，单 agent 跑下来有两个问题：一是串行太慢；二是所有中间结果都堆在主上下文里，跑到后半程 agent 开始“忘事”，输出格式也漂。本质上，是把“调度”和“执行”混在了同一个上下文里——这是大多数编排问题的根源。

## 做法

我把编排拆成三层：

1. **主 agent（调度层）**：只负责拆任务、发任务、收结果、出结论，不碰具体工具。上下文保持干净。
2. **子 agent（执行层）**：每个子 agent 只领一个明确的小任务 + 最小工具集。比如“检查源 A，按固定格式返回状态”。
3. **汇总规则**：约定子 agent 返回结构化结果（JSON 或固定字段），主 agent 只看结果、不看过程。

派发时用 OpenClaw 的 subagent 能力并行跑，每个子 agent 有独立上下文，跑完即回收。主 agent 拿到几份结构化摘要后一次性合成日报。同样的模式也适用于批量代码审查、多源信息收集这类“任务可切分、彼此无依赖”的场景。

## 踩坑点

- **并发不是越多越好**：一次开十几个子 agent，很快撞上 API 限流和配额，反而比 3~5 个并发更慢。我的稳定值是 3~5。
- **子 agent 提示词太泛**：只说“帮我查一下”基本必然返工。每个子任务要写清输入、输出格式、失败时返回什么。
- **并行写同一文件**：两个子 agent 同时写一个状态文件会互相覆盖。要么各写各的文件，要么落盘只交给主 agent。
- **不设超时**：一个子 agent 卡住会拖死整批。务必给每个子任务加超时和失败兜底。
- **返回格式不锁死**：汇总阶段会非常痛苦。格式必须在派发前就约定好。

## 可复用建议

- 子 agent 提示词五段模板：任务目标 / 输入 / 允许的工具 / 输出格式 / 失败时的返回值，一段不落。
- 子 agent 上下文宁小勿大，只给完成任务必需的信息。
- 把子任务设计成幂等：任何一项失败可以单独重跑，不牵连整批。
- 每次派发和返回都落日志，排查问题时比翻会话记录快得多。
- 先用 2 个子 agent 验证格式流转，确认无误再放大并发。

## 总结

subagent 编排的核心不是“多开几个 AI”，而是**调度与执行分离**：主 agent 保持轻上下文做决策，子 agent 各自带小上下文干活，用结构化结果回传。控制并发、锁死格式、设好超时，这套模式就能稳定支撑日常自动化里大部分“可并行”的场景。先小规模验证，再逐步放大，比一步到位省很多返工。
