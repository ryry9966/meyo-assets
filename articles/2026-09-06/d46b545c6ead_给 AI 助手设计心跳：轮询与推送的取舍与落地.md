## 背景

跑 OpenClaw 这类常驻 Agent，迟早会碰到一个需求：它不能只靠用户消息驱动。定时汇总、健康自检、盯外部状态、失败任务重试——这些活都要求 Agent 在“没人说话”的时候也能按节拍醒来。这个节拍机制就是 heartbeat。

## 问题

实现心跳有两条经典路线：

- **轮询**：定时器按固定间隔唤醒 Agent，让它自己检查有没有事做；
- **推送**：外部事件（webhook、消息队列、文件变更）主动唤醒 Agent。

纯轮询的痛点是浪费：绝大多数唤醒是 no-op，但每次唤醒都可能触发一次模型调用，token 成本和噪音随频率线性增长。纯推送的痛点是脆弱：延迟确实低，但要求事件源可靠、入口可达，任何一环丢事件，Agent 就永久失忆——而且本地部署常常根本没有公网入口。

## 做法

我现在的方案是“推送为主、轮询兜底”，分四步落地：

1. **触发源分级。** 消息类要求分钟级延迟，走推送；汇总、备份、对账类容忍小时级延迟，走轮询。先分级，再选通道。
2. **轮询层做“哑定时器 + 廉价预检”。** cron 只负责唤醒一个本地脚本，脚本用确定性逻辑（队列长度、文件 mtime、上次失败标记）判断是否值得唤醒模型。九成心跳在这里就结束，一次模型调用都不花。
3. **推送层统一入口。** 所有 webhook / 队列事件先落到本地 SQLite 事件表，带 `event_id` 唯一索引做幂等，再唤醒 Agent。Agent 崩了，事件也不丢。
4. **心跳兼职对账。** 每次轮询顺带扫一遍事件表：有没有超时未处理的事件、有没有连续失败的推送源，有就补跑。这样即使推送链路抖动，最多延迟一个心跳周期。

## 踩坑点

- **让 LLM 自己当定时判断者。** 早期版本每次心跳都调模型“想想有没有事”，一晚上烧掉的成本比一天的正经任务还高。预检必须在模型外做。
- **推送重试没有幂等键。** 一次 webhook 重放，同一任务被执行了三遍。事件表 + `event_id` 唯一索引解决。
- **心跳任务重叠。** 上一轮没跑完，下一轮又进来。加了带租约的锁文件，持有期间直接跳过本轮。
- **把 MCP 工具塞进预检。** 某个查外部状态的 MCP 工具偶尔 30 秒超时，直接把心跳循环拖死。预检只用本地确定性逻辑，重活留给模型决策后的执行阶段。
- **只看触发，不看 no-op 率。** 后来加了决策日志（醒来 / 预检结果 / 是否行动），no-op 率长期高于 90% 就该拉长间隔或改事件驱动。

## 可复用建议

- 一句话原则：**推送管延迟，轮询管正确性。** 推送负责“快”，心跳负责“不丢”。
- 定时器越蠢越好，不要把智能放进调度层。
- 上推送之前先有持久化事件表，否则等于裸奔。
- 用 no-op 率反推心跳间隔，而不是拍脑袋定个 5 分钟。

## 总结

Heartbeat 本身不复杂，复杂的是成本、延迟、可靠性三者的平衡。对我而言最终形态是：带廉价预检的慢心跳做底座，持久化 + 幂等的快推送做主干。落地顺序建议先跑通轮询、再加推送——反过来做，大概率返工。
