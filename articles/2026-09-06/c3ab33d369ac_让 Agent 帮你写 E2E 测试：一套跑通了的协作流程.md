## 背景

E2E 测试是工程里"都知道该写、但总被延后"的部分。原因是成本：覆盖一条"登录 → 下单 → 查列表"的用例，要理解页面结构、等待时机、数据准备，改一版 UI 又得跟着改。我所在项目的 E2E 覆盖长期停在核心链路三五条的水平。

Agent 出现后情况变了。它擅长的循环——读代码、跑命令、看报错、改一版再跑——恰好和写 E2E 测试的工作模式吻合。最近我把这套流程在两个项目里跑通，记录一下做法和坑。

## 问题：直接让 AI 写测试为什么不行

第一反应是"把这个页面写个 Playwright 测试"，结果基本不可用：

- **选择器靠猜**：模型没看过真实 DOM，会编造不存在的 `class` 和 `id`；
- **断言形同虚设**：不少生成用例只做 `page.goto` 然后截图，跑起来永远绿；
- **无人验证**：一次性生成二十条用例，人工逐条修的成本比重写还高。

结论是：**Agent 必须在"能执行测试、能看到失败输出"的闭环里工作**，否则产出只是看起来像测试的文本。

## 做法

以 Playwright 为例，我的步骤：

1. **准备基线**。手写一条能稳定跑通的用例放在 `e2e/smoke.spec.ts`，作为风格参照：选择器统一 `data-testid`、等待靠 `expect` 自动重试、禁用 `sleep`、fixture 写法固定。
2. **给 Agent 工具**。通过 MCP/插件给它三样东西：仓库读写权限（限制在 `e2e/` 目录）、执行 `npx playwright test` 的权限、失败时读取 trace 报告的路径。关键是它能自己跑、自己看输出，而不是你把报错贴给它。
3. **小批量下发任务**。一次只写一条用户路径。任务里明确：先读对应页面组件拿真实选择器，再写用例，跑一遍，失败就修，最多迭代 3 轮。
4. **人工审查**。重点看三处：断言是否落在业务数据上（订单状态、接口返回），而不是"页面能打开"；有没有 `waitForTimeout` 这类脆弱等待；用例之间是否共享状态。
5. **进 CI**。通过的用例合入后跑在 PR 流水线，Agent 后续的代码改动开始被测试保护。

实测下来，一条中等复杂度的流程（表单校验 + 提交 + 列表刷新）一轮任务约 5–10 分钟，一次通过率六七成，剩余问题集中在选择器和异步等待。

## 踩坑点

- **别给生产环境权限**。Agent 会执行命令，测试账号和环境变量要隔离，MCP 工具的 scope 最小化。
- **迭代上限必须写死在任务里**。否则遇到跑不过的用例它会反复改，烧掉大量 token 也不收敛。
- **警惕"永远绿"的用例**。模型倾向写不会失败的断言来"完成任务"，审查时优先砍掉没有业务断言的用例。
- **数据污染**。两条用例往同一个测试账号建数据，第二遍就挂。要求 Agent 用带随机后缀的数据，或在 fixture 里做清理。

## 可复用建议

- 把"测试风格指南"写成仓库内一个 markdown 文件，作为每次 Agent 任务的必读输入，比在 prompt 里重复要求稳定得多。
- 任务模板存进 repo，三段式：目标路径、迭代上限、验收标准，同事可以直接复用。
- 把选择器规范（`data-testid` 命名规则）写进前端 lint。Agent 写的选择器就是页面上真实存在的，用例质量会明显提升。

## 总结

Agent 写 E2E 测试的价值不在"全自动生成"，而在把每条用例的边际成本压到人工的几分之一。核心是闭环：给它执行和报错的能力，小批量下发，人工守住断言质量这条线。这套流程不绑定特定模型，在 OpenClaw 里接任何 Agent + MCP 工具组合都能跑起来。
