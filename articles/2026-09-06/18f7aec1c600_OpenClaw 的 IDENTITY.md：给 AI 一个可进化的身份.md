## 背景

OpenClaw 的 Agent 是长期运行的：多会话、多渠道、还可能跨模型切换。它的系统提示词不是写死在配置里的，而是由 workspace 下的一组文件在运行时拼装——`SOUL.md` 管价值观和行为底线，`USER.md` 管用户画像，`TOOLS.md` 管工具约定，而 `IDENTITY.md` 负责"我是谁"这一层：名字、形象、角色定位、语气边界。

很多同学第一次跑通网关后就再没打开过这个文件。结果就是 Agent 用着一套默认的通用身份，能用，但没有记忆点，也没有随使用沉淀的机制。

## 问题

实践里反复出现这几类麻烦：

- **语气漂移**：换个模型或隔几周再聊，同一个 Agent 的说话方式判若两人；
- **多人共用，感知分裂**：团队里每个人调教的方向不同，对外表现时而是极客时而是客服；
- **改动无迹可循**：身份被随手改过几次，为什么这么改、谁改的，全靠回忆；
- **想让它"自我成长"又不敢放手**：直接让 Agent 改自己的身份文件，几周后就不可控了。

## 做法

**1. 用结构化字段，别写散文。** 最小可用版本控制在 20 行以内，字段化表达：

```markdown
# IDENTITY
- Name: Nova
- Creature: 猫形机器人
- Vibe: 简洁直接，偶尔冷幽默
- Boundaries: 不替用户做财务/医疗决定；不确定时明说
```

注入的 token 预算很宝贵，身份文件越长权重越稀释。

**2. 纳入 git 管理。** 它本来就是个文件，`commit` 时写清动机，重要节点打 tag。身份变更从此有 diff 可看、有版本可回滚。

**3. 建立受控的进化回路。** 不让 Agent 直接写自己的身份。复盘时让它把"身份修订建议"输出到独立文件（如 `identity-proposals.md`），人工评审后再合并进 `IDENTITY.md`。进化发生在对话之外，变更发生在评审之内。

**4. 分层设计。** 稳定内核（角色、边界）+ 可变外壳（称呼、语气细节）。内核跨渠道共享，外壳放在渠道级配置里调。

**5. 模型升级后 re-baseline。** 准备 5~10 条探测 prompt（自我介绍、越界请求、典型语气场景），新旧模型各跑一遍，确认身份还在边界内。

## 踩坑点

- **写成小作文**：身份和任务指令抢注意力，行为反而变差；
- **职责串门**：把用户偏好、项目上下文塞进来，这些属于 `USER.md` 和记忆层；
- **让 Agent 自动 commit 身份变更**：漂移快、回滚难，评审环节不能省；
- **多 Agent 复制同一份文件**：只改名字不改描述，用户分不清谁是谁；
- **与 system prompt 里手写的 persona 冲突**：重复定义等于埋雷，注入有优先级，排查起来很费时间。

## 可复用建议

- 把身份当代码：字段化、走 PR、留 changelog；
- 事件驱动进化：每次行为翻车，针对性补一条边界规则，别定期大改；
- 身份测试集固化为脚本，每次变更跑一遍，防止隐性回归。

## 总结

`IDENTITY.md` 的价值不在于让 Agent"像一个人"，而在于把身份从散落在对话里的印象，变成一个可审查、可回滚、可渐进演化的工程对象。文件很小，但它是 Agent 长期行为一致性的锚点。建议今天就把默认模板换成自己的最小版本，交给 git，然后让它跟着你们的真实使用慢慢长。
