## 背景

在 OpenClaw 这类常驻型 Agent 架构里，heartbeat（心跳）是个绕不开的组件。网关进程活着，但"活着"不等于"知道该干活了"。用户的下一条消息是被动到达的，而提醒、监控、定时任务、外部状态变化，都需要 Agent 主动感知。heartbeat 解决的就是这个问题：**Agent 靠什么机制知道自己该醒过来做点什么**。

常见两条路：轮询（定时醒来检查）和推送（事件到达时被唤醒）。先说结论：多数场景下答案不是二选一，而是"推送为主、轮询兜底"。

## 问题

纯轮询的代价很直白。假设心跳间隔 30 分钟，一天 48 个周期，每周期都跑一遍检查逻辑。如果检查里嵌了 LLM 调用，token 消耗和动辄 95% 的空转比会很难看。更隐蔽的是延迟：事件发生在两次心跳之间，最坏要等一个完整周期才被处理。

纯推送看起来优雅，但前置条件一堆：可达的 webhook 端点或消息队列、签名校验、重试、幂等。最要命的是**丢事件**——Agent 重启窗口期、网络抖动、队列积压，任何一环出问题，事件就没了，而且你不知道它没了。轮询至少保证最终一致，推送不保证。

## 做法与步骤

我们在实践中收敛成一个分层方案：

1. **推送做主路径**。外部事件（webhook、MCP 通知、插件回调）直接投递到 Agent 的事件队列，立即触发处理。每条事件带幂等键，处理前先查重。
2. **心跳做对账**。低频心跳（15–30 分钟一次）只做三件事：扫描待办与状态表、比对最后处理位点、补发漏掉的事件。它是反熵机制，不承担实时性。
3. **检查逻辑分层**。心跳内部先做本地廉价检查（读状态文件、查 DB 标志位），确认有活才升级到重操作（LLM 调用、外部 API）。没活就直接睡回去，单次心跳成本近乎为零。
4. **间隔加抖动**。固定间隔在多实例场景会同频共振，全部挤在同一秒醒来。给间隔加 ±10% 随机抖动，失败时叠加退避。

## 踩坑点

- **心跳本身触发 LLM 调用**：最常见的事故。把"醒来"和"干活"耦合了，空转心跳也在烧 token。检查必须先廉价、后昂贵。
- **心跳是阻塞的**：某次心跳里调了个慢 API，把整个消息循环卡死三分钟，用户消息全在排队。心跳应走独立任务，并设超时。
- **推送无幂等**：webhook 重试导致同一个提醒触发两次。幂等键 + 去重表，两行代码的事，别省。
- **重启丢事件**：事件队列放内存，进程一挂全没。要么持久化，要么明确接受"心跳对账兜底"这个事实。
- **日志噪音**：每次心跳都打一行日志，一周几万行无效日志，真问题被淹没。只记录异常心跳和有实际工作的心跳。

## 可复用建议

- 判断标准一句话：**实时性要求高且事件源可控 → 推送为主；事件源不可控或要最终一致 → 轮询兜底**。两者不冲突，是互补关系。
- 心跳契约要显式写下来：做什么、不做什么、超时多少、连续失败几次告警。别让心跳变成"顺手再做点啥"的垃圾场。
- 给心跳加指标：触发次数、耗时分布、升级到重操作的比例。升级比例突然升高，通常意味着推送链路坏了——心跳指标反过来成了推送的监控哨。

## 总结

轮询和推送不是对立的架构选型，而是可靠性光谱的两端。推送给你低延迟，轮询给你确定性下界，heartbeat 的正确定位就是那个"下界"——它保证再烂的推送链路也不会让事件永久丢失。把心跳做轻、做对账、做兜底，把实时性交给推送，Agent 才能既省 token 又不失联。
