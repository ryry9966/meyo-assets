# Agent 的 tools.md：管理本地配置和环境差异的正确姿势

## 背景

Agent 用久了会发现，最影响稳定性的不是模型能力，而是环境：同一套任务，在公司笔记本上跑得顺，换到家里的 Linux 服务器就报错。原因很朴素——Agent 对环境的认知全靠猜。它记得「用 brew 装」，但那台机器是 Ubuntu；它记得项目在 `~/work`，但服务器上路径是 `/srv/projects`。

tools.md 的思路是：把这些环境事实写成一份 Agent 开工前必读的声明文件，放在工作区根目录，会话启动时自动加载。它不是继续往系统提示词里堆料，而是把「这台机器能干什么、不能干什么」收敛成一份可维护的接口文档。

## 问题

不管理环境差异，代价落在三处：

1. **试错成本**。Agent 用错包管理器、猜错路径，一错就是好几轮工具调用，token 和时间双输。
2. **无单一事实来源**。每台机器口头交代一遍，换个会话又忘，同样的坑反复踩。
3. **信任崩塌**。环境信息一旦过期（比如 Node 升级了），Agent 按旧信息执行失败，之后它就开始不信文件、自由发挥，比没有文件更糟。

## 做法与步骤

我采用的是两层结构：

- `tools.md`：进版本库，只写所有机器通用的事实和约定；
- `tools.local.md`：加入 gitignore，写本机差异（真实路径、端口、代理），在 tools.md 里只留一行「本机差异见 tools.local.md」。

条目尽量结构化，写成 Agent 好解析的清单而不是散文：

```markdown
# tools.md
## 包管理
- macOS 用 brew；Linux 用 apt，禁止在 Linux 上调 brew
## 运行时
- node >= 20，执行前用 `node -v` 确认，不要假设
## 路径
- 一律用 $HOME 展开，禁止硬编码用户名
## 网络
- 拉取依赖走代理，具体见 tools.local.md
## 禁止
- 不执行全局 install -g，不动系统目录
```

再加一步自检：写一个 `env-check.sh`，逐条验证 tools.md 里的断言（命令是否存在、版本是否达标），并约定 Agent 会话开始先跑它。文件说 node >= 20，脚本发现实际是 18，Agent 要么停下问人，要么把差异回写到 tools.local.md。这样文件与现实的漂移会在第一轮被发现，而不是在第三次构建失败之后。

## 踩坑点

- **写成散文**。大段自然语言的 tools.md，Agent 会漏读。一行一个断言，带小节标题，方便引用「按 tools.md 的网络节执行」。
- **把密钥写进去还提交了**。tools.md 永远只写「密钥在哪个 env 文件、叫什么变量名」，不写值，local 文件同理只写引用。
- **改了文件会话没重载**。不少框架只在会话启动时读一次，调完配置要重开会话，或明确让 Agent 重新读取。
- **越写越长**。所有条目都要进上下文，通用且高频的留 tools.md，冷门的挪到项目子文件，用到再读。
- **平台差异写死**。路径统一走 `$HOME`，命令写成「平台：命令」的映射，别留给 Agent 自由推理。

## 可复用建议

- 把 tools.md 当**环境的 API 文档**维护：改了环境就同步改文件，优先级等同改代码。
- 自检脚本放进 CI 或定时任务，每周跑一次，发现漂移直接开 issue。
- 多机场景给每台机器一份 tools.local.md，文件名带主机名，方便 diff 和同步。
- 新机器接入固定三步：clone 仓库 → 生成 tools.local.md → 跑 env-check。

## 总结

Agent 的可靠性，一半在模型，一半在你喂给它的环境事实。tools.md 的价值不在文件本身，而在「声明、自检、漂移即修」这个闭环：文件描述环境，脚本验证环境，差异及时回写。把这三件事做扎实，同一套任务跨机器迁移的失败率会肉眼可见地降下来。
