## 背景

跑 Agent 的人一般不止一台机器：办公笔记本、家里的小主机、一台云上 GPU。OpenClaw 这类框架里，Agent 执行任务前需要知道本机有什么——Python 在哪、装了哪些 CLI、代理怎么走、某个插件依赖哪个二进制。很多人把这些信息直接写进系统提示词，或者散落在 `.bashrc`、个人笔记、口头约定里。

## 问题

后果很典型：换一台机器，Agent 开口就是 `/usr/local/bin/xxx`，而那台机器上根本没有；同事拉了同一个项目，Agent 给出的命令在他的环境跑不通；更糟的是有人把带 token 的配置文件提交进了仓库。本质是同一个问题：**环境描述没有和具体机器解耦，也没有单一可信来源**。

## 做法

我的方案是把 `tools.md` 拆成两层：

1. **基线层（入库）**：`tools.md` 放仓库里，只写与机器无关的内容——工具清单、调用约定、项目对环境的要求、禁忌操作。团队共享，进版本控制。
2. **本机层（不入库）**：`tools.local.md` 由探测脚本在本机生成，写实际状态：解释器的绝对路径、已装 CLI 及版本、代理地址、GPU 与端口占用。加进 `.gitignore`。

Agent 读取时先基线、再本机覆盖，合并视图就是"这台机器的真实情况"。生成脚本要幂等，输出排序稳定（方便 diff），文件头部带生成时间戳。秘密一律不落盘，`tools.md` 里只写环境变量名，让 Agent 引用名称而不是读到值。

落地步骤：

1. 定 schema：`runtime / paths / tools / network / constraints` 五个固定段落；
2. 写 `probe.sh`（或 `.py`），探测后输出本机层文件；
3. 基线层进仓库，本机层进 ignore；个人机器差异同步的是脚本本身，不是产物；
4. 给 Agent 加一条约束：执行命令前先核对 `tools.md`；文件只读，变更只能通过重新生成；
5. 用冒烟提示词验证："列出当前可用工具及版本"，确认合并视图正确。

## 踩坑点

- **别让 Agent 直接编辑 `tools.md`**。它是生成产物，被 Agent 改过之后就变成"看起来可信的谎言"，比没有更糟。
- **写 `python` 不如写解释器绝对路径**。venv、conda、系统 Python 混用时，只记名字一定会翻车。
- **控制篇幅**。这个文件是要进上下文的，塞满无关条目会稀释注意力，用不上的段落直接删。
- **升级后忘记重新探测**。时间戳就是干这个的：Agent 看到超过 N 天的时间戳，应当提醒重跑脚本。
- Windows 与 Unix 的路径、shell 语法差异要在基线层显式声明，而不是靠假设。

## 可复用建议

把 `tools.md` 当基础设施即代码对待：**手写的是 schema 和生成脚本，生成的是本机事实**。一份基线对多台本机；秘密走引用不走内容；输出保持稳定排序便于审计。这套结构迁移到任何基于 MCP 或插件机制的 Agent 上都成立——工具发现本身就是配置问题，配置问题就该用配置工程的方式解决。

## 总结

环境差异没法消灭，只能结构化。两层 `tools.md` 加一个幂等探测脚本，成本大约一个下午，换来的是换机零成本、团队口径一致，以及 Agent 不再对着不存在的路径一本正经地报错。
