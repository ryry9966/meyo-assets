## 背景

Agent 工作流里，LLM 输出的默认载体是 Markdown。写作、周报、笔记都能直接用，但一旦要发布——公众号、知乎、掘金、博客、GitHub README——就会发现"标准 Markdown"其实是个幻觉：每个平台渲染规则不同，支持的语法子集不同，连列表缩进的处理都不一样。手动逐平台改格式，一次两次还行，周更三次之后就是纯体力劳动。

我们的做法是把这一步做成管线：Agent 只负责产出一份"规范源"，格式适配交给确定性代码。这篇记录管线设计和踩过的坑。

## 问题

- 同一份 Markdown 在不同平台的渲染差异：表格、代码高亮、脚注、任务列表各有各的脾气。
- AI 产出不可控：模型偶尔混入 HTML 标签、超嵌套引用、非标语法。
- 公众号根本不吃标准 Markdown，需要内联样式的 HTML。
- 图片防盗链、相对路径跨平台失效。

核心矛盾：AI 生成的"多样性"与发布端的"严格约束"之间，缺一个确定性的中间层。

## 做法

管线分四层：

1. **源规范层**。约束 AI 只用一个 Markdown 子集：标题、段落、列表、一级表格、代码块、图片、行内样式。子集写进共享的 prompt 片段，frontmatter 声明元数据和目标平台。
2. **Lint 层**。产出先跑结构校验：非法标签、裸链接、超嵌套列表，直接打回让 Agent 重写，而不是静默修复。经验是让模型修自己的输出，比脚本修补干净得多。
3. **适配层**。每个目标平台一个 transformer，纯函数：输入规范 AST，输出目标格式。公众号转 HTML + 内联样式；知乎转其方言；README 保留原样但重写相对链接。可以包成 MCP tool 供 Agent 编排调用，也可以就是一组脚本加 Makefile——规模小就选后者，别过度设计。
4. **渲染校验层**。用预览接口或离线渲染器生成快照，与上一版 diff，图片 404、表格塌陷这类异常在 CI 拦截。

## 踩坑点

- 公众号必须内联样式：class 全部失效，代码高亮要在转换阶段用 Shiki 展开成带 style 的 span，别指望前端渲染。
- 脚注别用：`[^1]` 在部分平台渲染成乱码，统一降级为行内括号注。
- 表格控制在 5 列以内，移动端必塌。
- 图片一律先传图床拿绝对 URL，源文件不写相对路径。
- 目录锚点按平台重生成，GitHub 和博客的 heading id 规则不同，不能复用。
- 最重要的一条：**别在 prompt 里解决格式问题**。"输出适配公众号格式"这类指令成功率低且无法回归测试，格式是代码的事。

## 可复用建议

- 单一事实源，平台差异全部下沉到适配器，这是整套设计的全部哲学。
- 每个平台维护 golden files（输入 → 期望输出快照），改 transformer 跑 diff，回归成本趋近于零。
- Markdown 子集作为项目级共享 prompt 片段，所有 Agent 任务引用同一份，不要各写各的。
- lint 打回优于静默修复，尤其面对 AI 产出时。

## 总结

AI 写作的上半场（生成）已经足够好，工程量真正在下半场（分发）。把格式适配从"人肉 + prompt"挪到"规范子集 + 确定性 transformer + 快照测试"，一次投入长期省时间。管线本身一天能搭完，难的是忍住不在 prompt 里继续堆格式要求。
