## 背景

OpenClaw 的价值不在“会聊”，而在“能动手”。Agent 接到任务后真正落地的动作——查库存、建工单、跑查询——几乎都要经过外部 API。这篇帖整理社区里几种常见对接方式，以及一路踩过的坑，供大家少走弯路。

## 问题：裸调 API 为什么不够

不少人的第一版做法，是给模型一个“你可以发 HTTP 请求”的通用工具，然后就会看到：

- 模型现场拼 URL、拼 JSON，参数名全靠记忆，错一个字段就是一轮重试；
- 鉴权 token 散落在对话上下文里，日志一导出全是密钥；
- 对方接口慢一点，Agent 干等到超时，整个会话僵住。

本质原因是：模型擅长“决定做什么”，不擅长“精确描述怎么做”。对接这件事应该收敛成结构化的接口，而不是让模型即兴发挥。

## 做法与步骤

建议把对接分三层看，按成本从低到高选：

**1. 现成 MCP Server 优先。** 数据库、搜索、代码托管这类常见服务，社区大多已有现成 MCP 实现，配好密钥就能用。先查一遍，别重复造轮子。

**2. 没有就自建一个薄 MCP server。** 核心是三件事：

- 每个工具一个明确动词，`create_ticket` 就是创建工单，不要做成 `do_action` 大杂烩；
- 用 JSON Schema 把参数类型钉死，`required` 字段写全，模型自由发挥的空间越小越好；
- description 是写给模型看的：说清楚什么时候该用、什么时候不该用、返回长什么样。

**3. 只有一次性的内网接口，才用通用 HTTP 工具兜底。** 即便如此也要包一层：固定 base URL、路径白名单、统一鉴权出口。

对接完别急着上主流程。准备十条左右的“金标准问题”，覆盖正常路径、参数缺失、服务报错三种情况，跑一遍确认工具选择和参数填充都对。

## 踩坑点

- **返回值太大塞爆上下文。** 接口返回 200 条记录就原样吐给模型，两三轮就爆 token。应在工具层裁剪：返回前 N 条加总数，需要更多让模型显式分页。
- **非幂等操作盲目重试。** 下单、发通知这类工具，超时后重试可能造成重复。要么给工具加幂等键，要么在工具描述里把重试语义写清楚。
- **把 API 返回当指令。** 第三方返回内容里若混进“请忽略之前的规则”这类文本，模型可能照办。工具结果必须当作数据注入，不能拼接成对话。
- **密钥进日志。** 工具调用日志默认脱敏，`token`、`password` 这类字段在序列化时替换掉。
- **没有超时和降级。** 每个工具调用都要有明确超时，超时后返回结构化错误而不是空字符串——模型得知道“失败了”才会换路径。

## 可复用建议

沉淀成一份对接 checklist，新服务照着过一遍：

1. 一个工具一个动词，Schema 类型完整；
2. description 写清使用时机与边界；
3. 返回值裁剪到“模型刚好够用”；
4. 超时、重试、幂等三件套想清楚再上线；
5. 日志脱敏，失败时返回结构化错误。

这五条比事后排障便宜得多，尤其最后两条，几乎每出一次事故都值得复盘一次。

## 总结

Agent 与外部服务对接，工程上没有魔法：把“模型决策”和“精确执行”分开，用 MCP 把接口收敛成类型明确、描述清晰的小工具，再补上超时、脱敏、幂等这些常规防守。握手握稳了，后面所有的自动化才有地基。欢迎在社区帖子里跟贴你踩过的坑，我们会持续把案例整理进这篇。
