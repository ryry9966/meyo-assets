## 背景

OpenClaw 的 cron 任务本质很简单：到点后，调度器把你写的那段 instruction 原样交给 agent 执行，再把结果投递到指定通道。它不是传统 crontab——没有脚本，只有一段自然语言；也不是交互式对话——没有人在线追问、纠偏。

这个差异决定了 cron instruction 是一类特殊的 prompt：**无人值守、无上下文、失败静默**。写得随手，任务会"看起来能跑"，但结果质量随模型发挥漂移。

## 问题

我踩过的坑，估计不少人也踩过：

1. **相对时间没有锚点**。写"汇总今天的资讯"，任务凌晨跑还是早上跑，"今天"含义完全不同，叠加时区配置更是灾难。
2. **输出没有格式约定**。结果是一段自由发挥的散文，想接下游脚本或做归档时根本没法解析。
3. **没有失败分支**。工具调用挂了，模型倾向于"编一个看起来合理的结果"补位——静默失败最伤。
4. **任务太重**。一个 instruction 塞"抓取 + 分析 + 发送 + 归档"，中途一步失败整段作废，还不知道断在哪。

核心认识：cron instruction 不是命令，是一份**契约**。你要在写它的那一刻，替未来那个没有你的执行现场，把边界情况全部想清楚。

## 做法

我把写 cron instruction 拆成五步：

1. **锚定时间**：显式写明时区，把"今天/昨天"翻译成"以当前时间为锚点的前 24 小时"这类可计算描述。
2. **锁定来源和范围**：用哪个工具、查哪些 repo / 关键词、过滤条件是什么，写死，不给模型"自行选择来源"的空间。
3. **固化输出结构**：固定段落或 JSON，字段名写死。下游要解析就用 JSON，人要看就用固定段落。
4. **写失败路径**：明确部分失败、全部失败各自怎么处理，要求输出显式标记（如 `RUN_FAILED`），禁止编造和静默跳过。
5. **收窄副作用**：cron 上下文里只保留读操作和"投递结果"这一个写动作，评论、修改、删除不要出现在定时任务里。

一个我实际在用的骨架：

```
任务：<一句话说清做什么>
时间基准：TZ=Asia/Shanghai，"过去 24h" = 当前时间往前 24 小时
步骤：
1. 用 <工具> 查询 <范围>，条件：<过滤>
2. 按 <字段> 排序，取前 N 条
输出格式（严格遵守）：
## 摘要
## 明细
## 状态   ← OK / PARTIAL / RUN_FAILED + 原因
失败处理：
- 单项失败：明细中标注 FAILED:<名称>，不编造
- 全部失败：只输出 RUN_FAILED 和原因
投递：结果发往 <通道>；除此之外不执行任何写操作
```

上线前先手动触发三到五次，并故意断网、填错参数验证失败分支，再放开定时。

## 踩坑点

- **别用对话窗口验证**。直接把 instruction 贴到对话里跑，历史上下文会兜底，表现好于 cron 的干净会话，验不出真实水平。要用 cron 的手动触发。
- **输出结构别太复杂**。字段超过十个，模型开始漏。模板里的"状态"段是我后来加的，专门用来判断一次运行值不值得看。
- **高频小任务不如低频聚合**。每 15 分钟跑一次轻查询，不如每小时聚合一次，token 成本和消息噪音都低。
- **结果要留档**。只投递不落盘，排障时没有现场。建议结果同时写一份带时间戳的本地文件。

## 可复用建议

一句话版本：**把 cron instruction 当 API 文档写，别当聊天消息写**。目标、来源、格式、失败、副作用，五个要素齐了，任务才算定义完成。另外每次只改一处，改完手动跑两轮再上线，避免"顺手优化"引入回归。

## 总结

cron 任务的可靠性上限，在你写下 instruction 的那一刻就决定了。多花十分钟把契约写严，好过事后翻日志猜模型当时为什么那么做。欢迎在回帖里贴出你们生产环境在跑的 cron instruction，一起沉淀几套经过验证的模板。
