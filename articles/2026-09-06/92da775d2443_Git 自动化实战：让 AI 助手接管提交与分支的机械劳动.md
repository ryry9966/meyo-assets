## 背景

日常开发里，Git 相关的机械操作占了不少时间：想一句符合规范的 commit message、按命名约定建分支、删掉一堆已合并的残留分支、给 PR 拼变更说明。这些事不难，但很打断心流。Agent 能力成熟之后（本地 Agent + MCP 工具链的组合），这批活是很好的自动化切入点——前提是流程可控。

## 问题

我们团队真实遇到的三类痛点：

1. **commit message 质量不稳定**。review 时经常只能看到“改了什么”，看不到“为什么改”。
2. **分支残留**。合并后不删、命名随缘，一个月后 `git branch` 一屏放不下。
3. **让 Agent 直接跑 git 命令风险高**。误 add 敏感文件、推错分支、甚至 force push，任何一件都是事故。

## 做法

分四步收敛，逐步放权：

**1. 能力白名单化。** 不要给 Agent 一个裸 shell。用 git MCP server，或者自己封一层命令集：`status`、`diff`、`add`、`commit`、`branch`、`push`。每条命令显式写进工具描述，`push -f`、`reset --hard` 这类直接不暴露。

**2. Commit message 流程。** 固定提示模板：Agent 读 `diff` → 按约定式提交输出 type/scope/subject → 只生成、不执行 → 我确认后它再提交。同时禁止 `git add -A` 和 `git add .`，只允许 add 明确列出的文件。

**3. 分支生命周期。** 命名规则写进 Agent 的规则文件（`feat/`、`fix/`、`chore/` 前缀 + issue 号）。每周跑一次清理任务：`git branch --merged main` 列出候选，输出清单等确认后再批量删除。

**4. PR 描述生成。** 拿 diff + commit 历史让 Agent 产出变更摘要和影响面，人只校对。这一步基本零风险，可以先上。

## 踩坑点

- **`git add -A` 是最大事故源。** Agent 看到 untracked 的 `.env` 也可能顺手提交。我们加了 pre-commit hook 扫敏感文件，配合白名单做双保险。
- **push 必须先 dry-run。** 流程固定为 `push --dry-run` 看输出，确认后再真推。保护分支（main、release）不进白名单。
- **message 风格会漂移。** 隔几天写法就变。把 2-3 个固定示例写进规则文件，比一句“写得规范点”有效得多。
- **冲突处理不可靠。** rebase/merge 冲突时 Agent 倾向乱选策略。这一步保留人工，Agent 只负责列出冲突文件和给出摘要。

## 可复用建议

- 核心原则：**Agent 生成，人确认，机器门禁**。commitlint/husky 这类硬校验是最后防线，永远不要依赖 prompt 约束。
- 所有 Agent 的 git 操作留日志：执行了什么命令、动了哪些文件，出问题能回放。
- 规范文件（命名、message 格式）独立维护一份，Agent 规则和 CI 共用，避免两套标准。
- 权限逐步放开：先只读（`status`/`log`/`diff`）跑两周，再放 commit，最后才是 push。

## 总结

这套流程在我们仓库跑了两个月，commit message 规范率明显上升，分支残留基本清零，没有出过误提交事故。体验上的变化是：Git 杂活从“动手做”变成“看一眼、点个头”。AI 助手做 Git 自动化的价值不在全自动，而在把机械劳动压缩成一次确认——收敛权限、硬校验兜底、关键节点留给人，就能安心用起来。
