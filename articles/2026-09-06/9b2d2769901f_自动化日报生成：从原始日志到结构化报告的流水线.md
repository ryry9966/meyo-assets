## 背景

团队推进依赖日报，但写日报本身是个苦差：git 提交、CI 构建、issue 流转、agent 会话记录散落在不同系统里，人工汇总既要翻多个后台，又容易漏关键变更。我们在 OpenClaw 上搭了一条流水线，让 agent 每天定时把原始日志压成结构化日报，稳定跑了一个月，这里把做法和坑整理出来。

## 问题

直接把原始日志丢给 LLM 让它"写个日报"，会遇到三个典型问题：

1. **上下文装不下**：日志量随团队活跃度波动，高峰日轻松超出预算；
2. **数字不可信**：模型自由发挥时，统计数字经常编造；
3. **格式漂移**：今天一个样式明天一个样式，下游阅读成本高。

根因是缺了一个中间层：先结构化，再总结。

## 做法

流水线分四步，由一个定时任务驱动：

**第一步：采集。** cron 触发脚本，分别拉取 git log（`--since` 昨日零点）、CI API 构建记录、issue 变更事件、OpenClaw agent 会话摘要，每类单独落盘为 JSONL。

**第二步：归一化。** 轻量转换器把所有事件映射到统一 schema：`{ts, source, actor, action, summary, ref}`。这一步是纯规则代码，不经过模型，保证数字层绝对准确。同时在这里做预聚合——按仓库/服务合并同类提交，把上千条原始事件压到几十条摘要行。

**第三步：生成。** 归一化数据 + 固定模板交给 OpenClaw agent。Prompt 明确约束：只允许引用输入数据中的数字，每个板块标注数据来源行数，禁止补充输入之外的信息。板块固定为：整体概览、按项目变更明细、异常与阻塞、明日关注。

**第四步：校验与投递。** 生成结果先过 schema 校验和数字抽查（脚本比对输入中的 commit 数、构建成功率与正文数字），通过后经 webhook 推到群频道，同时归档 Markdown 和原始 JSON 供回溯。

## 踩坑点

- **时区**：上游日志有 UTC 有本地时间，第一天就出现"未来事件"。归一化层统一时区，并在 schema 里保留原始时区字段。
- **日志突刺**：某天 CI 大规模重跑，事件量翻倍，聚合维度不够导致正文截断。后来改为"仓库+结果"两级聚合，超阈值时输出到附件。
- **上游格式变更**：CI API 升级后字段改名，采集层静默产出空数据。加了最低数据量断言：某来源低于历史均值三成即告警，而不是照常生成一份"看起来正常"的空日报。
- **模型越界**：即使有约束，agent 偶尔会脑补原因分析。给板块加 must-cite（引用数据行号），校验时核对引用存在性，不通过重试一次。

## 可复用建议

1. **采集与生成分离**：归一化层是流水线的价值核心，模型只负责措辞和归纳，不负责事实。
2. **schema 定版本**：日报 JSON 加 `version` 字段，下游按版本解析，避免后续演进踩塌。
3. **保留原始快照**：除投递正文外，把当天结构化输入一并归档，方便复盘"模型为什么这么写"。
4. **失败要可见**：任何一环挂掉，宁可发一条"今日日报生成失败"的通知，也不要静默。

## 总结

这条流水线的核心思路很朴素：**规则代码管事实，模型管表达，校验层兜底**。成本主要在归一化层，但 schema 稳定后，加新数据源只是加一个采集器。对已在用 OpenClaw 做自动化的团队，日报是验证"结构化输入 + 约束生成 + 后置校验"这套模式成本最低的场景，跑通后可以直接平移到周报、变更通报。
