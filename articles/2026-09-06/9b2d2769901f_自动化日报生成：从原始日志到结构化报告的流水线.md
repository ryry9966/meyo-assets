## 背景

团队每天要交的日报内容大同小异：服务异常数、构建结果、代码合并、关键指标。人工写有三个老问题：耗时、口径不一、漏项。值班当天事一多，日报就变成"一切正常"四个字，事后排查才发现当天早有苗头。

我们用 OpenClaw 的调度能力加一组 MCP 工具搭了一条日报流水线，稳定跑了两个多月。这篇文章记录做法和踩过的坑。

## 问题拆解

从原始日志到日报，中间隔着四件事：

1. **数据分散**：日志在服务端、提交在仓库、告警在监控群，格式和时区都不统一；
2. **量大**：一天的 debug 日志直接丢给模型，token 先爆，重点也被稀释；
3. **可信度**：让模型直接"写日报"，数字容易被改写甚至脑补；
4. **可靠性**：流水线挂了没人知道，或者重跑产出两份报告。

所以核心思路只有一句：**确定性的事情交给代码，模型只做归因和措辞**。

## 做法分四层

**采集层。** 定时任务从各数据源拉取，统一转成 JSON Lines 中间格式，每条记录带 `source / ts / level / module / payload` 字段。时间戳统一按 UTC 存储、按本地时区聚合，避免切天错乱。

**清洗聚合层。** 纯代码：去重、过滤心跳类噪音、按模块分组、计算统计量（错误数、构建成功率、变更列表）。这一层输出一份"事实数据"，是日报里所有数字的唯一来源。

**摘要层。** 把聚合后的结构化数据喂给 agent，而不是原始日志。输出用 JSON Schema 约束字段，数字要求原样引用、禁止模型自行计算。跑完再校验一遍：数值与事实数据比对，不一致直接拒绝渲染。

**渲染投递层。** Markdown 模板渲染，推送群 webhook 并归档到对象存储，文件名按日期做 key，天然幂等。外加一条监控：到点没产出就告警——宁可报错，不出空报告。

## 踩坑点

- **时区**：第一版按服务器时间切天，跨零点的告警被算到前一天，改为 UTC 存储后才解决。
- **模型改数字**：试过让模型"顺手整理数字"，错误数 3 被写成 13。改成代码算数、模型只写"为什么"，问题消失。
- **token 超限**：直接喂原始日志必超限，分层聚合后输入量降了两个数量级。
- **静默失败**：曾有三天报告实际在复用缓存，没人发现。加上"产出即心跳"的监控才堵住。
- **敏感信息**：日志里混着 token 和内网地址，采集层必须先脱敏，投递前再扫一遍。

## 可复用建议

1. 先定中间格式 schema，再写采集器，别让格式随数据源漂移；
2. 中间产物全部落盘，出问题可回放、可补算；
3. LLM 输出永远走 schema 校验，数字类字段与源头比对；
4. 把"取日报"封装成 MCP 工具，agent 按需读数即可，不必每次重跑全链路；
5. 报告模板走版本管理，历史报告可追溯口径。

## 总结

这条流水线的价值不在于省下写日报的十分钟，而在于把**事实采集**和**结论生成**分开了：代码保证数字可信，模型负责让结论可读。跑稳之后，同一份中间数据层还能顺手支撑周报和值班交接，边际成本很低。如果你也有被"一切正常"支配的值班经历，建议从采集层开始动手，先把事实数据做扎实。
