## 背景

我们团队的日常节奏里，日报是绕不开的事：昨天部署了什么、出了哪些告警、哪些任务没跑完，都要在早会前汇总一遍。信息本身不缺——服务日志、CI 记录、任务系统里都有——缺的是把它们收拢成一份"能看"的报告。之前靠人工翻日志，每天 20~40 分钟，还经常漏。

于是花了一个周末，用 OpenClaw 的定时任务加一个 MCP 数据源插件，搭了一条从原始日志到结构化日报的流水线。跑了一个多月，稳定够用，把过程和坑记录下来。

## 问题定义

动手前先明确三个硬约束：

1. **日报不能缺席**：哪怕上游全挂，也要发出降级版本；
2. **内容可追溯**：报告里每个数字都能回查到原始日志；
3. **格式稳定**：收报告的是人和下游脚本，字段不能天天变。

## 做法：五段式流水线

**1. 采集与标准化。** cron 定时触发，拉取"昨天"时间窗内所有日志源，统一转成 JSON Lines 中间格式：`timestamp / source / level / event_type / message`。这一步只做归一化，不做任何判断。

**2. 规则降噪。** 纯规则把几十万行压到几百条关键事件：按错误码聚合、去重、过滤心跳类噪音。错误码先做归一化映射（同一种超时在不同服务里写法不一样），否则 Top N 统计会被碎片化。

**3. 机械统计。** 生成确定性统计块：错误 Top N、各来源事件计数、与前一日的环比。这部分完全不经 LLM，数字绝对可靠。

**4. LLM 润色。** 把统计块和关键事件摘要交给 Agent，按固定 JSON schema 输出（概况 / 异常 / 待办三段），再用模板渲染成 Markdown。原则：LLM 只看统计结果和摘要，永远不看原始日志。

**5. 校验与推送。** schema 校验失败重试两次，仍失败则回退到纯模板报告（只有统计数字，没有自然语言）；推送带 run_id，webhook 侧去重，防止任务重跑发两份。

## 踩坑点

- **一开始让 LLM 直接读原始日志**：超上下文、幻觉频发、token 费用感人。改成"规则层出事实，LLM 只做表述"后问题全部消失。
- **时区边界**：日志是 UTC，我按本地时区算"昨天"，切分边界差 8 小时，凌晨事件掉进今天的窗口。后来统一 UTC 存储，只在展示层转换。
- **JSON 输出抖动**：模型偶尔在 JSON 外包一句解释。temperature 降到 0.2，加 schema 校验重试，基本根治。
- **重跑不幂等**：修完 bug 手动重跑，群里收到两份日报。加 run_id 去重解决。
- **噪声污染统计**：一个死循环重试把错误计数刷成 Top 1，报告完全失真。加了聚合上限和"同类错误折叠"规则。

## 可复用建议

1. **中间 JSONL 层是整条流水线的灵魂**。有了它，任何一段都能单独重放、单测、离线调试；排查"为什么日报里少了这条"只需 grep 中间文件。
2. **确定性优先**：凡是规则能算的（计数、聚合、环比）都不交给模型，LLM 只负责"把事实说清楚"。
3. **保留每次运行的输入输出快照**，成本极低，出问题时价值极高。
4. **先做最小闭环**：一个日志源、一个推送渠道，跑稳后再横向接新源。我们是第二次迭代才加的第二个数据源。

## 总结

核心思路是分层：采集归一 → 规则降噪 → 机械统计 → LLM 表述 → 校验推送。LLM 是表达层的一环，而不是全部。跑通之后，日报从"每天一项人力任务"变成"每天扫一眼的产物"，偶尔漏报也能靠中间层快照快速定位。如果你也在被日报类工作消耗，建议从"先把日志变成结构化中间格式"这一步开始，后面每一步都会顺很多。
