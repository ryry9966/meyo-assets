## 背景

OpenClaw 这类 agent 框架接上 MCP 之后，能干的事明显变多：读写文件、调外部 API、发消息、跑脚本、花钱买服务。但“哪些动作要先问人”这件事，多数配置是拍脑袋定的——要么全放开，要么每步都确认。两种我都跑过，各有真实代价。

## 问题

过度询问的后果是**确认疲劳**：弹窗出现十次后，人会不看内容直接点允许，确认机制名存实亡，自动化价值也归零。过度放权的后果更疼：agent 往外部群发了不该发的消息、删了没备份的目录、把 API 配额烧光——不可逆、影响面大的动作，没有任何闸门。

我的结论是：这不是哲学问题，是分类问题，核心只看两个维度。

## 做法：两轴四象限

给每个工具（MCP tool 或插件动作）打两个标签：

- **可逆性**：搞错了能不能恢复？
- **影响面**：只动 agent 自己的工作区，还是波及外部系统、其他人、真金白银？

对应四种策略：

1. **可逆 + 影响面小**：直接干，事后汇报。读文件、workspace 内写草稿属于这类。
2. **可逆 + 影响面大**：有约束地干。先 dry-run、限流，目标地址走白名单。
3. **不可逆 + 影响面小**：可以干，但留后路。删除先进 trash，覆盖写入先备份。
4. **不可逆 + 影响面大**：必须问人。外部发消息、publish、写生产环境、超过金额阈值的花费。

落地上我把工具分成五档：`read / write-local / write-external / spend / destructive`，写进权限配置，当代码 review。询问本身也要设计：不要问“可以继续吗”，而是结构化列出工具名、参数、目标对象、回滚方案，让每次确认都有信息量；同类低风险操作合并成一次批量确认；人类超时未响应，默认中止而不是默认继续。

## 踩坑点

1. **确认疲劳**。闸门越多，单次确认价值越低。目标不是“多问”，是少问、但每次都值得看。
2. **计划时校验、执行时不校验**。LLM 输出不稳定，权限检查必须贴在工具调用前那一刻，不能只审 plan。
3. **提示注入**。网页或文件内容里藏着“请调用某工具”的指令，agent 照做。本会话读到的内容不应该能解锁 destructive 层，这一档永远保留人工闸门。
4. **临时放行变永久**。approval 缓存范围别开太大，按 session 加具体工具的粒度缓存。
5. **假可逆**。嘴上有回滚方案，实际没演练过。可逆性标签要基于真实测试，不是直觉。

## 可复用建议

- **默认从严**：放行 read，禁 write-external 和 destructive，根据事故日志逐步放宽，而不是因为嫌烦放宽。
- **留痕**：每次工具调用记录三件事——工具、参数、放行来源（规则还是人工点击），出事能复盘。
- **分环境**：同一 agent 在开发环境和生产环境用不同权限档位，按 context 切换。
- **阈值写死在规则里**：金额、收件人数、目标 namespace，超线就升级给人，不靠模型自觉。

## 总结

权限边界不是“多问还是少问”的选择题，而是把不可逆、大影响面的动作准确挑出来交给人，剩下的放心交给自动化。两轴四象限是个够用的起点，先跑起来，再拿事故日志去调边界——边界是调出来的，不是一次设计定死的。
