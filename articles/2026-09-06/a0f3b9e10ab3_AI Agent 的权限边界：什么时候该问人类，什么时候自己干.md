## 背景

接上 MCP 和插件之后，Agent 能干的事从"聊天"变成了"执行"：读写文件、跑 shell、调外部 API、发消息、花钱。每个做自动化的人迟早都会撞上同一个问题——哪些动作放手让它干，哪些必须停下来问人？

## 问题：两种失败模式

实践中最常见的不是权限太松，而是在两个极端之间来回摇摆：

- **全都问**。每次写文件、每条命令都弹确认。跑两周后人类变成橡皮图章，见弹窗无脑点"允许"——比不问还危险。
- **全都放**。直到某天 agent 在生产库上执行了一条没有 WHERE 条件的 DELETE。

所以真正的问题不是"要不要问"，而是**用什么标准切分**。

## 做法：四个维度 + 四档权限

建议用四个维度评估每一个工具调用：

1. **可逆性**：能不能回滚？git 覆盖可回滚，发出去的邮件不能。
2. **影响范围**：只在 workspace 内，还是会碰到生产环境或其他人？
3. **成本**：token、API 费用、时长有没有上限？
4. **确定性**：参数是明确的，还是 agent 在猜？

映射成四档：

- **L0 自动执行**：只读、沙箱内、幂等。读文件、查询、dry-run。
- **L1 自动执行 + 审计**：workspace 内写操作，git 可回滚，每次记录 diff。
- **L2 首次确认、模式内放行**：装依赖、第一次调用某外部 API。同类动作确认一次后放行，参数模式变了重新确认。
- **L3 必须问人**：不可逆动作、外部副作用（发布、支付、群发）、生产环境、超预算。

在 OpenClaw + MCP 的落地层面，几个抓手：

- **工具粒度切细**。把"部署"拆成"构建 / 预览 / 执行"三步，前两步 L1，第三步 L3。粗粒度工具没法部分批准。
- **在网关/策略层拦截**，而不是只靠 system prompt 写"请谨慎"。硬约束必须长在执行路径上，prompt 只能当第一道防线。
- **用好 MCP 的 annotations**（`readOnlyHint`、`destructiveHint`）做初始分档，但别盲信，自己再包一层策略。
- **预算熔断**：L0/L1 设单会话费用和调用次数上限，超限自动降级为"必须问"。

## 踩坑点

1. **确认疲劳**。问得越多，"允许"点得越快。确认次数是预算，要省着花在 L3 上。
2. **无上下文的确认**。"是否继续？"是最差的问法。确认时必须展示将执行的具体命令、diff、目标地址，让人 10 秒内能判断。
3. **信注解不信实测**。有工具标了 readOnly 实际会写缓存，接进来先跑一遍验证再定档。
4. **dry-run ≠ 真跑**。凭证、网络、并发差异会让预演通过的步骤翻车，别因为预演过了就降到 L0。
5. **prompt 层防线可被绕过**。agent 换个说法就可能突破"请不要删文件"的指令，硬约束只能在代码层。

## 可复用建议

- **默认收紧，凭日志放开**。每放开一条权限线，要有审计日志支撑，而不是凭感觉。
- **给每个工具配安全版本**：read-only 变体、limit 参数、dry-run 开关，让"安全路径"成为阻力最小的路径。
- **审计记三样**：谁（会话/档位）、干了什么（完整参数）、结果如何（退出码/diff）。没有审计的自治等于裸奔。
- **定期回放确认记录**：如果 L3 的弹窗人类 100% 都点了允许，说明分档错了，往下调一档。

## 总结

权限线不是按"危险/安全"划的，而是按"**可逆 + 范围内 + 便宜 + 确定**"划的：四条都满足就放手，缺任何一条就降档、问人。目标是让问人变得便宜且有信息量，让自治变得可审计、可回滚——这两件事做好了，自动化才敢真正跑起来。
