## 背景

OpenClaw 的 cron 任务，本质上是"定时把一段 instruction 喂给 agent，让它独立跑完一次再汇报"。这和聊天里的 prompt 有个关键差别：**执行时没有对话上下文，没人在场回答反问，输出会直接进通知渠道**。

很多人把 cron instruction 写成聊天语气——"帮我看看昨天有什么新 issue"。跑起来就会发现：要么 agent 反问"你想看哪个仓库？"然后空转，要么每天发一堆"一切正常"，要么任务挂了两周没人知道。

## 我的做法

把 cron instruction 当成**给值班同事写的交接文档**来写。读者是一个刚被唤醒、没有记忆、没人可问的 agent。按五段组织：

**1. 目标与触发时间**。写清时区和数据窗口。"每天 9 点"不如"工作日 09:00（Asia/Shanghai）触发，检查过去 24 小时的数据"。相对窗口比"今天"可靠，不会因为执行时刻漂移而漏数据。

**2. 数据源和工具边界**。明确用哪个工具、不许做什么。不写的话，agent 经常自作主张去抓一堆网页，token 翻倍还抓错东西。

**3. 判断条件**。最容易被忽略的一段：什么情况下输出、什么情况下静默。没有静默条款的 cron 任务是通知疲劳的主要来源。

**4. 输出格式**。行数上限写死，结构固定（编号、标题、严重度），面向"人类扫一眼"优化。

**5. 失败路径**。工具挂了怎么办？正确答案是"报告失败"，而不是沉默或编数据。

一个我实际在用的骨架：

```
任务：工作日 09:00（Asia/Shanghai）执行
目标：检查 <仓库> 过去 24 小时新增的 bug 类 issue
数据源：用 GitHub 工具按创建时间过滤；不要浏览网页
静默条件：无新增则直接结束，不发送任何消息
输出：≤10 行，每条含编号/标题/严重度，末尾一句总体判断
失败：工具调用失败时发送"数据源不可用：<原因>"，禁止编造
```

## 踩坑点

- **对话式写法**：instruction 里出现"帮我看看"，agent 可能反问，而 cron 没人应答，任务就挂在等待状态。
- **没有静默条款**：每天三条"一切正常"，一周后用户开始无脑忽略通知，真正的问题反而被淹没。
- **"今天"这种模糊窗口**：任务在 00:10 执行时"今天"几乎没有数据，改成"过去 24 小时"立刻正常。
- **失败静默**：任务挂了但没走失败路径，你以为它在跑，其实已经停了两周。失败必须可见。
- **上下文塞进 instruction**：有人把几百行背景资料直接粘进去，每次触发都烧一遍 token。改成让 agent 现场用工具去读，instruction 只留指针。
- **改完不测**：修改后先手动触发一次看输出，再等自然周期，别上线第二天才发现写错了。

## 可复用建议

- 一事一任务。别把磁盘检查、issue 汇总、日报塞进同一个 instruction，出问题没法单独定位。
- instruction 只写"判断逻辑和格式"，数据让 agent 现取，保持它短小稳定。
- 定期审计输出历史：如果"正常类消息"占比超过一半，回头补静默条件。
- 输出里带一句"本次数据窗口"，回溯时方便对齐时间。

## 总结

cron instruction 的质量可以用三个维度衡量：**信息自包含度**（不看上下文也能执行）、**判断条件明确度**（什么时候说话、什么时候沉默）、**失败路径完备度**（挂了会不会有人知道）。三条都到位，定时任务才算真正自动化；缺任何一条，它都只是个定时产生噪音的脚本。
