## 背景

Agent 类工具越用越深之后，一个矛盾会逐渐浮现：本地文件、聊天记录、日程这些隐私数据都在往模型手里送，但走云端 API 总有点不踏实，加上按 token 计费和限流，长跑自动化的成本也不低。

近两年量化技术成熟后，7B~32B 级别的模型在家用显卡上已经可用。OpenClaw 这类框架走 OpenAI 兼容协议，理论上把 base URL 指到本地服务就能跑。听起来很简单，实际是另一回事。

## 问题

我拿一台 4060 Ti 16G 的机器测了两周，结论是：**"能聊天"和"能干活"之间差距很大**。Agent 场景的核心是工具调用（function calling / MCP），而小模型恰恰在这上面最容易翻车——参数格式错、幻觉出不存在的工具名、该调工具时自说自话。此外长上下文的显存开销、中文 token 效率，都是文档不会告诉你的坑。

## 做法

1. **确认硬件基线**：8GB 显存跑 7~8B 的 Q4 量化；12GB 跑 14B；24GB 可以碰 32B。纯 CPU 也能跑，但 5~10 tok/s 只适合后台批处理。
2. **选推理框架**：求省心用 Ollama，要细粒度控制用 llama.cpp server，需要并发上 vLLM。都开 OpenAI 兼容端点。
3. **选模型**：只看两点——官方标注支持 tool calling 的 instruct 版本，以及对中文友好。实测 Qwen 系列在中文指令和工具调用上最稳。
4. **量化从 Q4_K_M 起步**：别追 Q8，省下来的显存留给上下文窗口，性价比高得多。
5. **建回归用例**：接入 Agent 后，准备 10~20 条覆盖真实工具调用的测试任务，跑通率低于 80% 就降级或换模型。这一步不能省。

## 踩坑点

- **工具 schema 被静默丢弃**：Ollama 原生协议和 OpenAI 兼容层对 tools 参数的透传实现不一致，表现为模型瞎编参数名。升级版本后对比日志才定位到。
- **上下文窗口默认值太小**：Ollama 默认 num_ctx 很小，Agent 的 system prompt 加工具描述轻松撑爆，外在表现是"忘指令"。开到 16k~32k，但注意 KV cache 随长度线性吃显存。
- **部分 offload 是断崖**：显存不够时把部分层放 CPU，速度会从 40 tok/s 直接掉到个位数，提前测好层数的平衡点。
- **temperature 拉低**：跑工具调用用 0.1~0.3，创造性需求另开一个模型实例。
- **冷启动**：模型加载要几十秒，常驻服务记得配 keep_alive，否则自动化任务里全是莫名超时。

## 可复用建议

- **把本地模型当"档位"，不是"替代品"**：路由策略里，隐私敏感和简单任务走本地，复杂推理仍走云端，混合最划算。
- **固化评测集**：换模型、换量化、升级推理框架，都先跑一遍同一套用例，避免凭感觉切换。
- **显存做预算**：模型权重 + KV cache + 系统占用，整体留 20% 余量，别压满。

## 总结

12GB 显存的家用电脑，目前已经能稳定胜任 Agent 的日常工具调用任务。但验收标准必须是工具调用跑通率，而不是 demo 里的聊天流畅度。工程重心应该放在推理服务配置和回归测试上，而不是追新模型——模型会过时，这套流程不会。
