## 背景

跑 Agent 自动化的同学大概率见过这个场景：流水线跑到一半，某个外部 API——搜索、天气、数据库、某个 MCP 工具背后的上游服务——开始超时或批量返回 503。传统服务挂了会重试、告警、熔断；Agent 的麻烦在于，失败信息会被塞进上下文，模型会"自行解读"：要么反复重试把 token 烧光，要么编一个看起来合理的结果继续往下跑，下游拿到的是假数据。

## 问题：三种典型翻车

1. **重试失控**：把"再试一次"的决策交给模型。每轮循环消耗 token，几次之后上下文塞满，整个 run 超时。
2. **幻觉兜底**：工具返回一句模糊的报错字符串，模型倾向于把它补全成"合理"结果，而不是承认失败。
3. **级联阻塞**：一个非关键依赖挂掉，整条链路卡死或全部作废。

## 做法：重试放代码里，决策协议给模型

**1. 在插件层做错误分类。** 不要把原始异常或 HTML 错误页丢给模型。给每个 MCP 工具包一层统一的 adapter，输出结构化错误信封：

```json
{"status": "error", "code": "UPSTREAM_TIMEOUT", "retryable": true}
```

至少区分两类：超时/429（可重试）和 401/400（重试无意义）。

**2. 确定性重试。** 指数退避加抖动，上限 3 次左右，尊重 Retry-After 头。重试发生在 adapter 内部，Agent 只看到最终结果。

**3. 熔断。** 连续 N 次失败后把工具标记为 degraded，冷却期内直接返回"工具暂不可用"，不再请求上游。

**4. 给 Agent 一条失败协议**（写进系统提示）：优先切备用工具 → 允许使用缓存/过期数据（必须声明时间戳）→ 全部失败则明确回答"无法完成，原因是 X"，禁止编造。

**5. 断点续跑。** 每步的输入输出落盘，恢复时从失败步骤继续，而不是整个 run 重来。

**6. 观测。** 记录每次工具调用的耗时、错误码、重试次数，事后才能回答"为什么挂"。

## 踩坑点

- **非幂等操作别盲目重试**：发消息、下单这类操作要带幂等键，否则重试一次就重复执行一次。
- **429 和 500 混为一谈**：对限流不加退避地硬重试，只会把上游打得更死。
- **熔断冷却时间拍脑袋**：太短等于继续打爆上游，太长 Agent 会误判为永久不可用。
- **静默降级**：退回旧数据却不声明，用户以为拿到的是实时结果，这是信任问题。
- **错误信封格式漂移**：字段随手改，模型行为跟着漂。schema 定下来就别动。

## 可复用建议

- 所有插件共用同一个 resilience adapter（超时、分类、重试、熔断），不要每个工具各写一套。
- 做故障注入测试：搭一个可配置故障率的 mock 端点，比如 30% 概率返回 503，观察 Agent 的真实表现。
- 把"失败协议"当测试用例：手动挂掉搜索工具，检查输出是否引用缓存、是否如实声明失败。
- 错误码命名收敛：`UPSTREAM_TIMEOUT / RATE_LIMITED / AUTH_FAILED / INVALID_PARAM` 四类起步，够用很久。

## 总结

错误恢复本质是系统设计问题，不是提示词问题。确定性的控制——重试、熔断、降级顺序——放在代码层；模型只负责在明确给定的选项里做决策，并如实传达失败。让失败可见、可复盘、可续跑，Agent 才算从演示品变成生产工具。
