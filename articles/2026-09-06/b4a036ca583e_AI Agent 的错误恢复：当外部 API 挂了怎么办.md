## 背景

跑 Agent 自动化的人迟早会遇到这个场景：流程执行到一半，某个外部 API 开始 504、限流或直接超时。LLM 供应商抖动、搜索接口触发 rate limit、内部服务发版重启——上游故障不是"会不会发生"的问题，而是"什么时候发生"的问题。在 OpenClaw 生态里，工具大多通过 MCP server 或插件接入，上游一挂，Agent 的表现通常分三种：卡死、空转烧 token，或者最糟的一种——编造一个看起来正常的执行结果继续往下走。

## 问题：Agent 默认不擅长处理故障

实际观察下来，常见的坏行为有四类：

1. **盲目重试循环**。模型收到报错后反复调用同一个工具，参数几乎不变，直到上下文被错误信息填满。
2. **幻觉成功**。错误信息太含糊（比如只返回一句 "request failed"），模型接不上真实结果，就自己脑补一份继续执行。
3. **阻塞拖死整条链**。HTTP 客户端没设超时，一个慢接口把整个会话挂住几十秒甚至永久。
4. **错误一视同仁**。429 限流和 401 鉴权失败被同等对待，前者等 5 秒就能恢复，后者重试一万次也没用。

## 做法：把恢复机制下沉到工具层

核心思路一句话：**重试、超时、熔断是工程问题，不要交给模型决策**。Agent 只负责"出错之后选哪条路"的业务决策。

**1. 错误分类 + 结构化返回。** 在 MCP 工具的响应里显式区分错误类型，让模型看得懂：

```json
{
  "status": "error",
  "type": "upstream_rate_limit",
  "retryable": true,
  "retry_after": 5,
  "hint": "上游限流，建议等待后重试或切换降级方案"
}
```

**2. 重试下沉。** 在插件封装层做有界重试：最多 2~3 次，指数退避加随机抖动。模型层面的"重试"几乎总是在浪费 token。

**3. 失败要快、要说清楚。** 每个外部调用设硬超时（10~15 秒一般够用）。失败时把结构化错误抛回给模型，而不是吞掉后返回空结果。

**4. 准备降级路径。** 典型优先级：本地缓存 → 备用数据源 → 带"数据可能过期"标记的旧结果 → 明确告知用户并暂停。关键是降级时要在结果里打标，别让模型把旧数据当新数据用。

**5. 熔断。** 某工具在窗口期内连续失败 N 次，就标记为不可用并冷却几分钟，期间直接返回"该工具暂时不可用"，省掉无意义的等待。

## 踩坑点

- **让模型自己重试**是最常见的坑：它缺乏退避意识，经常用一模一样的参数连打十次。
- **错误信息只写一句 "failed"**，等于亲手把模型推向幻觉。错误要带类型、带建议。
- **把 429 当致命错误**直接放弃，其实加个 5 秒等待就能过。
- **重试没有 jitter**：服务恢复的瞬间被所有定时重试再次打挂。
- **降级不声明**：静默返回缓存数据，模型和用户都不知道数据是旧的，这类问题上线后极难排查。

## 可复用建议

- 给所有工具定一个统一的响应信封：`status / type / retryable / hint` 四个字段，写进插件开发规范。
- 超时、重试、熔断全部放在 MCP server 层，Agent 侧只保留"选哪条降级路径"的决策。
- 专门测试失败路径：把 mock API 杀掉跑一遍流程，观察 Agent 是停、是降级、还是编结果。
- 每次上游失败都落日志并带上请求 ID，事后复盘才有依据。

## 总结

外部 API 挂掉是常态而不是异常。好的 Agent 架构不指望模型"聪明地"扛住故障，而是把恢复做成确定性的工程机制：工具层管重试和熔断，模型层管降级决策，两层职责分清，故障时的行为才可预期。花一个下午把这套信封和降级路径补上，比事后清理一次幻觉事故划算得多。
