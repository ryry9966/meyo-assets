## 背景

OpenClaw-CN 社区每周都有固定内容要产出：精华帖整理、插件速递、周报摘要。过去靠版主人肉整理，费时且不稳定。我的目标是基于 OpenClaw 搭一个发帖机器人：定时抓取信息源 → Agent 生成草稿 → 审核后自动发帖。听起来一天能写完的活，实际迭代了三轮架构才算稳下来。这篇把设计和踩的坑都摊开讲。

## 问题定义

动手前先列了四条硬约束，后来证明每条都对应至少一次事故：

1. **内容必须真实**：链接、插件名、版本号不允许幻觉；
2. **不能重复发帖**：调度重试、服务重启都要幂等；
3. **必须可控**：发布前要有审核点，不能 Agent 直接对外；
4. **成本可控**：不能每轮都把全量历史塞给模型。

## 架构与做法

整体分四层，职责严格分开：

- **调度层**：cron 触发 OpenClaw 定时任务，每次新建独立 session；
- **采集层**：MCP 工具 `fetch_sources`，从 GitHub releases、RSS、社区站 API 拉结构化数据；
- **生成层**：Agent 只做摘要、改写、排版，系统提示词明确"链接与版本号只能来自工具返回"；
- **发布层**：自研 `publish` 插件，两阶段发布，内部带限流与去重。

发布接口的核心约定只有一个字段：

```text
publish(title, body, dedupe_key)
# dedupe_key = hash(内容源条目 ID)，库中存在则直接跳过
```

## 踩坑实录

**1. Agent 自由发挥，出现虚构链接。** 第一版让模型直接写正文，三天出现两次不存在的 URL。修复：引用必须来自工具返回的 payload 写进系统提示词，同时 publish 插件里做 URL 域名白名单校验，提示词 + 代码双重兜底。

**2. 调度重试导致重复发帖。** 任务失败自动重试，同一篇帖子发了两遍。修复：dedupe_key 幂等 + 数据库唯一索引，重试自然变成空操作。

**3. 复用 session 造成上下文污染。** 图省事共用一个会话，模型开始"记得"上一轮的草稿，把旧内容混进新帖。修复：每次调度强制新 session，状态全部外置到数据库，不依赖对话记忆。

**4. 社区 API 限流 429。** 修复：令牌桶 + 指数退避放进发布插件，不要指望模型自己控制发布节奏。

**5. token 消耗翻倍。** 长源文直接进上下文太贵。修复：采集层先做分段摘要，生成层只拿一级摘要和元数据。

## 可复用建议

- **工具管事实，Agent 管表达**：凡必须为真的字段（链接、版本、数字）一律由工具返回并校验；
- **对外动作全部幂等**：dedupe key 从内容源派生，别用时间戳；
- **发布权限收敛到单一插件**：审计、限流、去重都在这一层做，别散落各处；
- **两阶段发布（draft → publish）**：性价比最高的安全阀；
- **保留 prompt 与工具调用 trace 日志**：排障时可以直接回放现场。

## 总结

这个项目代码量不大，核心工作量在"约束 Agent"而不是"实现功能"。这类自动化的可靠性，来源不是更强的模型，而是清晰的边界：什么由工具保证，什么由人审核，什么靠幂等兜底。把这三件事想清楚，换任何 Agent 框架都能落地。欢迎在社区帖下交流你们的去重与审核方案。
