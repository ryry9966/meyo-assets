## 背景

社区内容一直靠几个人手动发，节奏不稳，素材也散。我的想法很朴素：让 Agent 承担"找素材、写草稿"，人只做审核和拍板。所以目标不是全自动水帖，而是一条半自动流水线：**素材收集 → 草稿生成 → 人工审核 → 定时发布**。

## 架构

整体四层：

- **触发层**：cron 定时唤起任务，不搞常驻进程；
- **Agent 层**：OpenClaw 负责编排，只挂三个 MCP 工具；
- **工具层**：素材抓取（RSS/关键词）、草稿读写（本地 drafts/ 目录）、发布（论坛 API，唯一有写权限的工具）；
- **状态层**：SQLite 维护任务状态机 `collected → drafted → approved → published / failed`。

发布工具刻意做窄：只留 `create_post(title, body, tags)` 一个入口，token 放在 MCP server 的环境变量里，Agent 上下文中永远不出现凭证。

## 做法与步骤

1. 先把发布 MCP server 单独写好、单独测通，再接 Agent——工具不可靠，上层全是空中楼阁；
2. 素材抓取后做两层去重：正文归一化后哈希 + 标题相似度阈值；
3. Agent 生成草稿写入 `drafts/`，强制附带素材来源链接；
4. 审核脚本逐条展示草稿，confirm 后进入发布队列；
5. 发布带指数退避重试，幂等键用任务 ID。

## 踩坑实录

1. **全自动第一天就翻车**。放开审核直接发布，产出全是标题党和同一话题的换皮重写。教训：去重要在"选题"层面做，不能只查正文哈希；频次也要封顶，一天两篇。
2. **工具报错被 Agent 无限重试**。论坛限流返回 429，Agent 不死心地连续重试，把配额打光。修复分两处：工具内部做退避，同时在任务指令里明确"发布失败两次即终止并标记 failed"。
3. **崩溃恢复导致重复发帖**。发布到一半进程挂了，重启后又发一遍。把发布拆成 `reserve`（写幂等键占位）+ `confirm` 两步，重启后先查占位记录再决定是否重发。
4. **Markdown 转义**。草稿本地渲染没问题，发到论坛后代码块里的下划线和星号被吃掉。发布工具里统一做一遍 sanitize，别指望 Agent 输出永远干净。
5. **凭证管理**。早期图省事把 token 塞进提示词，日志里到处都是。收进 MCP server 环境变量后，审计和轮换都简单了。

## 可复用建议

- 半自动优先，全自动后置；审核环节是安全带，别急着拆；
- 写权限只给一个窄工具，其余工具一律只读；
- 每次发布落一条审计记录：prompt 版本、素材链接、输出、帖子 URL，出问题能回放；
- 给 Agent 设步数预算，防止在"再润色一遍"里死循环；
- prompt 和工具代码一起进 git，版本对得上才谈得上复现。

## 总结

这套东西代码量不大，MCP server 加编排脚本不到五百行，真正的工作量都在状态机和失败路径上。Agent 负责生成，系统负责兜底——把不确定性关在审核环节里，机器人才能长期稳定地跑下去。
