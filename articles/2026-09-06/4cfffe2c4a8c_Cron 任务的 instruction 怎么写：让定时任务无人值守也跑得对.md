## 背景

OpenClaw 的 cron 任务和聊天是两种完全不同的执行场景。聊天里 agent 可以追问、你可以随时纠正；cron 任务是到点唤醒、单轮执行、结果投递到指定通道，中间没有任何人盯着。instruction 写得稍含糊，任务就安静地跑偏——不报错、不重试，第二天照常再跑一遍错误的东西。

我维护着四五个定时任务（早报汇总、仓库巡检、日志摘要、周报草稿），踩了不少坑之后，把写 cron instruction 的经验整理如下。

## 核心问题：把聊天 prompt 搬进 cron

最常见的失败模式有三种：

1. **相对时间歧义**。“总结今天的消息”——agent 内部时钟、调度器触发时间、你预期的日期可能对不上，跨零点触发时尤其混乱。
2. **输出契约缺失**。任务跑完了，但结果投到哪、什么格式、多长，instruction 里没说，输出随机。
3. **失败静默**。数据源挂了、工具调用失败时，模型倾向于“编一点内容凑数”，你收到的早报看起来正常，其实是幻觉。

## 做法：按接口文档的标准写

我现在的 instruction 骨架长这样：

```text
任务：一句话说明做什么
时间：时区固定 Asia/Shanghai；处理日期用占位符，由调度参数注入
数据源：明确到具体 MCP 工具 / 插件 / 路径
步骤：编号列出，3~5 步以内
输出：
- 投递目标（频道 / 会话 / 文件路径）
- 格式约束（条数、字段、长度上限）
- 空结果与失败的处理：查不到就如实回复"任务失败：<原因>"，禁止编造
预算：最多 N 次工具调用，不执行范围外操作
```

几个关键点展开：

**时间一律显式化。** 触发时刻交给 cron 表达式，instruction 里不要重复描述时间，只声明时区和处理日期。日期用占位符注入，比让 agent 自己猜“今天”可靠得多。

**幂等优先。** 每条输出带上处理日期，去重基于日期而不是“上次运行”。这样任务重跑不会产出两份重复早报，也能一眼判断“今天到底跑没跑过”。

**失败要有出口。** 明确写“数据为空或调用失败时，只回报失败原因”。这句话是幻觉防火墙，实测能拦掉大部分“模型好心编内容”的情况。

**给预算上界。** 无人值守任务最大的风险是发散。限定工具调用次数和操作范围，超限就收手汇报，而不是无限追查。

## 踩坑点

- **instruction 腐化**：每次出问题就往里补一句规则，半年后变成上千字的缝合怪，模型抓不住重点。我每两周裁剪一次，删掉过期规则。
- **新旧并存**：改完 instruction，旧的调度实例可能还在跑，先确认线上只有一份配置。
- **行为漂移**：模型或框架升级后，同一 instruction 的表现会变。关键任务建议升级后手动触发两三次抽检，别等用户发现早报没来。
- **灰度验证**：新任务先设 30 分钟一次的短周期，盯两三轮输出，确认投递格式和失败路径都对，再放宽到正式周期。

## 可复用建议

- 把 cron instruction 当长期运行的程序来审，而不是一次性聊天消息。
- 输出契约三要素——投递目标、格式、失败路径——缺一不可。
- 每个 cron 任务对应独立配置，方便单独禁用和排障。
- 留一个手动触发入口，验证改动时不用等 cron 到点。

## 总结

Cron instruction 写得好不好，判断标准很朴素：你敢不敢一周不看它的输出。把输入写死、输出立契约、失败留出口、预算设上界——做到这四条，定时任务才能从“偶尔跑对的玩具”变成真正省心的自动化。
