## 背景

做 Agent 自动化这两年，我逐步把一部分模型调用从云端 API 挪到了本地。原因很实际：一轮 Agent 任务动辄几十次调用，API 账单涨得很快；而且自动化脚本经常要碰个人数据——本地文件、聊天记录、浏览器历史，过云总归不放心。关键是，结构化任务（工具选择、JSON 抽取、分类摘要）对模型能力要求没那么高，7B~14B 级别的小模型在本地已经够用。

## 问题

难点不在“跑起来”，而在“跑得稳”：家用硬件显存有限；Agent 框架要求 OpenAI 兼容接口和可靠的工具调用；上下文长度、量化精度、推理速度互相牵制，配置不对时，表现往往是莫名其妙的工具调用失败，而不是报错。

## 做法

1. **盘点硬件**。先确认显存/内存上限：7B Q4 量化约 5GB，14B 约 9GB，32B 约 20GB。显存不够会自动 offload 到 CPU，速度断崖式下降——宁可选小一号的模型。
2. **选推理后端**。快速上手用 Ollama；要精细控制采样和模板用 llama.cpp；多卡且追求吞吐再考虑 vLLM。家用场景前两者足够。
3. **选模型**。别只看榜单，核心是工具调用（function calling）是否可靠。建议实测：给它几个 MCP 工具定义，跑十轮真实任务，看参数填充和调用触发稳不稳。
4. **暴露兼容接口**。Ollama 自带 OpenAI 兼容端点，把 Agent 框架的 base_url 指到 `http://localhost:11434/v1` 即可。显式设置上下文长度和模型驻留时间，别用默认值。
5. **压测与回归**。固定一套真实任务评测脚本，记录 tokens/s、首 token 延迟、工具调用成功率，每次改配置后跑一遍。

## 踩坑点

- **上下文截断是头号隐形杀手**。Ollama 默认 num_ctx 很小，系统提示加一堆工具定义塞进去就被截断，表现为模型“忘了”工具。务必显式调大，并注意 KV cache 的额外显存开销。
- **量化太狠会破坏结构化输出**。Q4 以下 JSON 格式错误率明显上升，工具调用场景优先 Q5/Q6。
- **模型卡宣称支持工具调用 ≠ 你当前的推理模板支持**，换模板后必须重测。
- **keep_alive 没设好**，模型反复冷加载，每次十几秒，Agent 体验极差。
- 温度别照抄云端默认值，工具调用建议压到 0.1~0.3，并配合 JSON schema 约束输出，别靠 prompt 祈祷。

## 可复用建议

- 做分层路由：规划与复杂推理走云端，工具执行与格式化走本地，成本和隐私都兼顾。
- 把模型清单、量化版本、上下文配置写进版本化的配置文件，换机器可复现。
- 保留那份评测脚本——它比任何榜单都真实。

## 总结

本地部署的价值不是替代云端，而是给 Agent 架构多一层可控的选择。先用小模型把工具调用链路跑通，再依据真实任务数据决定哪些环节留在本地。这条路径，比盲目追新模型划算得多。
