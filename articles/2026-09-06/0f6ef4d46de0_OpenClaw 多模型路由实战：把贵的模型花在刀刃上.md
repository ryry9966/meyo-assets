## 背景

在 OpenClaw 的日常使用里，一个 Agent 任务的完整链路往往包括：意图理解、任务规划、MCP 工具调用、结果摘要、格式化输出。很多团队初期图省事，全链路都挂在一个 GPT 级模型上，跑得动，但账单和延迟很快就教做人。另一边，本地部署的模型（Ollama/vLLM 起个 Qwen 或 DeepSeek 蒸馏版）便宜、数据不出机器，但在复杂规划和长上下文上明显吃力。多模型路由要解决的就是这个分工问题。

## 问题

真正的问题不是“哪个模型更强”，而是：**链路上每个环节对模型能力的要求不一样**。用同一个模型服务所有环节，必然在某几处浪费（成本/延迟），在另外几处埋雷（隐私、超时、上下文溢出）。

## 做法

社区里跑得比较稳的方案，是按“环节”而不是按“用户”路由，分五步：

1. **拆环节**。把自己的 agent loop 拆成五类：规划、代码/复杂生成、工具参数填充、摘要压缩、格式校验。
2. **小样本实测**。每类准备 20–50 条真实样本，分别用 GPT 级模型和本地模型跑，记录通过率、延迟、单次成本，形成一张“环节-模型”矩阵。
3. **配路由规则**。在模型池打标签（能力档位、上下文长度、是否可出网），规则示例：规划与代码 → 云端旗舰；参数填充、摘要、格式化 → 本地 7B/14B；命中敏感数据关键词 → 强制本地。
4. **加降级链**。云端超时/限流时回落本地，保证任务不断；本地连续失败三次则升级云端，并打标记。
5. **可观测**。按环节记录每次调用的模型、token 数、失败原因，每周看一次分布，矩阵跟着数据改。

## 踩坑点

- 本地模型的 function calling 合规性差，JSON 经常缺字段或夹带注释。开 strict JSON / 语法约束解码，MCP 工具侧再做一层 schema 校验兜底。
- 本地模型上下文普遍 8k–32k，MCP 返回的大段结果直接塞进去会**静默截断**，外在表现是“模型突然变笨”。先在路由层做摘要压缩再喂。
- 弱 GPU 上本地大模型未必更快，先实测延迟再定路由，别想当然。
- 混用模型后输出风格和格式会漂移，多步链路里尤其明显。模板和 few-shot 要按模型档位分别维护。
- 路由规则本身也会出错，误把难任务分给小模型是最隐蔽的静默降质。留 5–10% 流量走云端做对照组，定期用裁判模型抽检。

## 可复用建议

- **起步只分两档**：强模型 + 弱模型。别一上来五六个模型，规则多了没人维护。
- Prompt 写成“最小公约数”版本，保证同一段提示词在两档都能跑，差异部分用按模型注入的系统前缀解决。
- 敏感数据（密钥、内网地址、客户信息）走本地白名单路由，这条规则优先级永远最高。
- 路由决策必须能被一个配置项强制覆盖（`force_model`），线上出问题要能秒级回滚。

## 总结

多模型路由不是一次性配置，而是一个持续运营的 ops 问题。核心动作就三件：**拆环节、小样本实测、留对照组**。先用两档模型把链路跑起来，让数据告诉你哪里该升级、哪里可以继续省钱——这比任何“通用最佳实践”都可靠。欢迎在社区帖里贴你自己的环节-模型矩阵，大家互相抄作业。
