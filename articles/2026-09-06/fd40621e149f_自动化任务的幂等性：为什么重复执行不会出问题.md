## 背景

在 OpenClaw 的日常使用里，任务重复执行几乎是常态：Agent 重试一次超时的 MCP 调用、定时任务和手动触发撞车、webhook 重投、或者你调试时多跑了一遍脚本。问题从来不在“跑几次”，而在“跑多次之后，系统最终状态是否正确”——这就是幂等性：同一操作执行一次和执行 N 次，效果相同。

## 问题

多数自动化脚本的副作用默认是非幂等的，典型例子：

- `echo "export FOO=1" >> ~/.zshrc`，跑三遍就多三行；
- 插件调 `POST /users` 建账号，重试产生重复用户；
- Agent 发通知，一次卡顿后群里收到两条相同告警；
- 定时器注册逻辑没去重，crontab 里堆了一堆重复条目。

这些单次看都“没问题”，叠上重试就成了脏状态，而且往往很久之后才被发现。

## 做法

我的习惯是把任务里的每个副作用拎出来，按三类处理：

1. **能用“确保语义”就不用“创建语义”。** 把“新增一条规则”改成“渲染完整期望状态后 diff 应用”；建目录用 `mkdir -p`，写配置用模板生成临时文件再原子替换（`mv`），API 能 upsert 就不用 POST。重复执行只是收敛到同一状态。

2. **无法幂等的外部调用，加幂等键。** 对发通知、建工单这类天然累积的操作，为每个逻辑动作生成稳定 key（任务 ID + 步骤名 + 目标日期，不要掺时间戳和随机数），执行前查本地 SQLite 或文件锁：命中即跳过，成功后落盘。MCP 工具若服务端支持幂等 header，优先用服务端的。

3. **写入全部原子化。** 临时文件加 rename，避免读到半截状态。

验证方法很朴素：**故意连续跑两遍，再 diff 一次状态**（配置、数据库、已发消息数）。第二遍零副作用，才算过关。

## 踩坑点

- **check-then-act 竞态**：先查再建在并发下会双双通过检查。要么用唯一约束、文件锁，要么容忍唯一冲突后吞掉异常。
- **幂等键粒度**：掺了时间戳或 LLM 随机输出的 key 永远不会命中，等于没做；粒度太粗又会误杀合法的二次执行。key 必须从任务意图派生，与 Agent 输出的随机性无关。
- **先记录还是后记录**：执行前记 key，崩溃时可能漏执行（at-most-once）；执行后记，崩溃窗口内重试会重复（at-least-once）。通知类宁选后者，状态变更类通常前者更稳。
- **容易漏掉的副作用**：日志、埋点、Agent 发的评论、git commit——这些同样改变状态。

## 可复用建议

- 封装 MCP 工具时默认提供 `ensure_xxx` 而非 `create_xxx`；
- 给插件层做一个 dedupe helper（SQLite 一张表就够），所有外部副作用统一过一遍；
- 把“跑两遍 + 状态 diff”写进任务上线 checklist；
- 保留 run journal（key、时间、结果），排查重复问题时极其好用。

## 总结

幂等性不是装饰，而是让自动化敢于重试、敢于重跑的前提。有了它，Agent 的重试逻辑、你的手动干预、调度器的重复触发，都从“潜在事故”变成“无害操作”。下次写自动化任务时，先问一句：这段代码跑两遍，世界会不会变坏？
