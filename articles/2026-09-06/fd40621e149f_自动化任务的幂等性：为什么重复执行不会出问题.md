## 背景

跑自动化之后会发现一个规律：凡是会重复触发的东西，终究会重复触发。定时任务的重试、webhook 的重投、Agent 循环里的二次调用、MCP 工具调用的超时重发——编排层几乎都默认“至少执行一次”。这不是 bug，是可靠性设计使然。问题在于，我们写很多动作时的心智是“只执行一次”，而不是“执行多次也安全”。

## 问题

两个真实感很强的场景：

1. 每日摘要任务，Agent 生成内容后调用插件“追加写入”日志文件。某次网络抖动导致上层误判失败而重试，文件里出现两份当天摘要。
2. 调用外部 API 创建工单，请求超时，但服务端其实已创建成功。客户端重试，产生重复工单。

共同点是副作用不可重复。而系统压力大、网络不稳时，恰好是最容易触发重试的时候——重复副作用总在你最没精力处理时出现。

## 做法

核心思路一句话：让“跑两次”和“跑一次”的结果等价。

1. **定义稳定的幂等键**。键必须来自业务语义，比如 `digest-2025-06-01`、`sync-repoA-commit-abc123`。不要用时间戳或随机数——每次重试生成新键，等于没做。
2. **把“追加”改成“确保状态”**。写文件用覆盖加原子重命名而不是 append；写数据库用唯一约束加 upsert；发消息带消息 ID，下游按 ID 去重。
3. **维护执行台账**。一个 sqlite 或 json 文件就够：键 → 状态（进行中/完成）。执行前先查，查到“完成”直接跳过。
4. **外部 API 分情况**。支持幂等键头的（支付、主流云厂商的写接口）直接传；不支持的就“先查后建”，并接受查询结果有短暂延迟。
5. **在编排入口统一去重**。Agent 框架或调度层拿到触发事件后，先按幂等键查台账，再决定是否下发工具调用。去重放得越靠前，改动面越小。

## 踩坑点

- **超时 ≠ 失败**。最危险的重试是“不知道成功没成功”的重试。先查询真实状态，再决定重发还是跳过。
- **检查与执行之间存在竞态**。两个并发实例同时查台账、都看到“未执行”、都去跑。台账要加锁，或者把唯一约束当最后防线。
- **台账写入本身要原子**。先写临时文件再 rename，别直接覆盖。否则崩溃时留下半条记录，状态机反而变成新的故障源。
- **幂等键里混入变化量**。把“第 N 次运行”或当前时间拼进键里，重试语义就断了。键必须能从触发事件本身推导出来。

## 可复用建议

- 给每个自动化任务加一条验收标准：“同一事件投递两次，终态一致、副作用只有一份。”写进 review checklist。
- 优先描述“期望状态”而非“执行动作”。“让 A 与 B 同步”天然幂等；“往 A 添加 A 与 B 的差异”不是。
- 幂等键在编排层生成一次、层层透传，不要每个工具各造各的。
- 上线前故意跑两遍，diff 终态。这个测试花十分钟，能省掉一次凌晨处理重复告警。

## 总结

幂等性不是一个库或中间件，而是一种设计习惯：假设一切都会重试，把重复当作常态来设计。当任务做到“重复执行不出问题”，才真正敢放进无人值守的环境。自动化的可信，正是建立在这类不起眼的约束上。
