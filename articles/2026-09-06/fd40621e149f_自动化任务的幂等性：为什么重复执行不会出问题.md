## 背景

在 OpenClaw 里跑的自动化任务，大多不是"跑一次就完"的：cron 定时触发、webhook 回调、失败重试、多端网关同时在线……这些机制叠加起来，同一段任务逻辑被执行两三次是常态而非异常。分布式系统的老经验在这里同样适用：只要存在重试，交付语义就是 at-least-once，重复无法根除，只能设计掉。

## 问题

典型翻车场景：一个每天定时让 agent 汇总 issue 并发到群里的任务，某次网络抖动导致网关超时重试，群里出现两条一模一样的汇总。再比如 agent 调用 MCP 工具"创建工单"，第一次调用实际成功但响应超时，重试后产生了重复工单。

这类问题不报错、不崩溃，只在数据里留下脏东西，等发现时往往已经难清理。根因很简单：任务的副作用（写库、发消息、创建资源）不幂等——执行一次和执行两次，结果不一样。

## 做法

我目前分四层处理，从任务设计到下游兜底：

1. **描述"目标状态"，而不是"动作"。** 把"给频道发一条今日汇总"改写成"确保频道里存在今天的汇总消息"。前者执行两次发两条，后者天然幂等。
2. **给每次执行定一个稳定的幂等键。** key = 任务 ID + 业务日期 + 目标对象，例如 `daily-digest:2025-06-01:#dev`。注意别把时间戳或随机数拼进 key，那等于自废武功。
3. **执行前查执行日志，执行后原子写日志。** 在 workspace 里放一个 run journal（JSONL 够用），执行前查 key 是否已有 success 记录，有则跳过。写记录时先写临时文件再 rename，避免半截内容被下次读到。
4. **下游加唯一约束兜底。** 数据库给业务键建唯一索引；发消息场景靠消费端按"内容 hash + 时间窗"去重。最后一道防线，永远放在离数据最近的地方。

## 踩坑点

- **check-then-act 竞态。** 两个并发触发同时通过"日志里没记录"的检查，然后都执行。任务可能并发时，光查日志不够，还要配文件锁，或让调度器保证单实例。
- **锁不跨进程生命周期。** 网关重启后内存锁失效。幂等键和日志必须持久化，锁只是优化，不是保证。
- **重试会叠加。** 网关层重试一次、插件内再重试一次，两个副本就变成四个。幂等控制要在最外层统一收口，不要每层各搞一套。
- **不要假设 MCP 工具幂等。** 很多工具是纯"动作"语义（create、send）。用包一层自己的 key 再调用，比指望上游帮你去重现实得多。

## 可复用建议

- 写任何定时/触发任务前先回答一个问题：**"这个任务今天意外跑三次，会怎样？"** 答不上来就先别上线。
- 把 run journal + 幂等键 + 原子写做成公共 helper，所有自动化任务共用，别每个脚本各写一套。
- 能用 upsert 就不要 insert，能"确保存在"就不要"新增一条"。

## 总结

幂等性不是可选的工程美德，而是自动化系统的入场券。重试和重复触发一定会发生，区别只在于你的任务是"重复执行会翻车"还是"重复执行无害"。OpenClaw 这类 agent 网关放大了触发来源和频率，也放大了不幂等的代价——把幂等键和执行日志做成基础设施，后面每一个新任务都会省心。
