## 背景

项目级上下文文件（AGENTS.md 这类）已经是成熟实践：把仓库约定、构建命令、代码风格写进去，Agent 进门就能读到。但大多数人没给"自己"建一份对应的文件。结果就是：Agent 对项目了如指掌，对你一无所知。

## 问题

具体是三类重复成本：

1. **每次会话重新自我介绍**。操作系统、shell、包管理器、部署方式、回复语言、详略偏好……说一遍几十秒，一个月下来不少。
2. **Agent 用默认假设替你做决定**。你没说，它就用 npm、就加 sudo、就写长篇解释。它不是错，是不认识你。
3. **纠正不沉淀**。同一个偏好你在十个会话里纠正了十次，第十一次它还是老样子。聊天记录不是记忆，跨工具、跨模型时尤其如此。

## 做法

我在 OpenClaw 的工作区维护一份 USER.md，随系统提示自动加载。结构约 40 行，分五段：

```markdown
# 用户画像（Agent 必读）

## 环境
- macOS 15 / zsh；包管理一律 pnpm，禁止 fallback 到 npm
- Node 22 LTS；Python 3.12（uv 管理）

## 偏好
- 中文回复，技术名词保留英文
- 先给结论，细节放后面
- 代码不加无意义注释

## 红线
- 不主动 git push，不执行 sudo
- 删除文件前必须列出清单等我确认

## 当前上下文（随时过期，弱信任）
- 正在迁移消息队列，暂不引入新依赖

## 协作方式
- 修改我的表述前，先复述你的理解
```

接入方式看架构：OpenClaw 可将工作区文件作为 workspace 上下文加载；用 MCP 的可以包成只读 resource；最朴素的做法是启动时拼进 system prompt。关键是**固定路径 + 自动加载**，别靠人肉粘贴。

配套一个更新机制：**两振出局**——同一件事我纠正 Agent 两次，就写进 USER.md。文件本身进 git，改动能追溯。

## 踩坑点

- **写太长**。第一版我写了 150 行，上下文被撑爆，核心指令反而被稀释。30~60 行够用，每条都必须影响行为，否则删。
- **过期信息比没有更糟**。档案里留着旧技术栈，Agent 会自信地按旧栈出方案，而且它不会怀疑"档案"本身。稳定事实和易变状态要分开，"当前上下文"那段明确标弱信任、定期清空。
- **敏感信息别放**。这份文件会进每一次请求，token、手机号、内网地址一律不写。
- **别写成性格说明书**。"我喜欢高效沟通"这种话无法被执行，等于没写。要写成可验证的动作："回复先给结论，不超过 200 字"。
- **与项目级文件的优先级冲突**。踩过一次：项目 AGENTS.md 要求 pnpm，我 USER.md 里也写了，后来项目换工具就打架。定规则：技术事实以项目为准，个人偏好以 USER.md 为准。

## 可复用建议

- 把 USER.md 当**配置**而不是日记：小、版本化、定期 review（我每月看一次）。
- 每条写成"约束 + 动作"，能被 Agent 直接执行。
- 可加一段"失联处理"：超时怎么办、哪些操作要等确认——自动化场景特别有用。
- 定期让 Agent 自查："列出你从我的用户档案中已知的信息"，能直接暴露未被加载或被覆盖的条目。
- 团队场景可衍生 ROLE.md，给不同成员的协作 Agent 各配一份。

## 总结

USER.md 是成本极低的基建：一个 markdown 文件、几十行、每月十分钟。换来的是 Agent 不再每次"重新认识你"，纠正次数明显下降，跨工具行为也一致。它解决不了记忆的所有问题，但把"你是谁"从会话流水里捞出来变成显式配置，是当前最划算的一步。先从三行红线写起，比追求完美模板重要。
