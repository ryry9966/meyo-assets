## 为什么需要“按需加载”能力

在 AI 助手工程的早期阶段，我们习惯把所有工具、提示、知识一次性塞进 Agent 的上下文或工具列表里。这在原型阶段行得通，一旦场景复杂化就暴露三个问题：

- **启动沉重**：每次会话预加载全部能力，导致初始化耗时膨胀，token 消耗巨大。
- **上下文污染**：无关的能力描述和工具定义挤占宝贵的上下文窗口，干扰模型注意力，甚至引发错误工具调用。
- **维护灾难**：能力之间隐含耦合，增删一个功能需要全局回归。

于是产生了“按需加载能力”的设计需求——让助手核心保持轻量，只有在需要时才动态激活某项能力，用后即收回。OpenClaw 的 Skills 机制就是为了解决这一系列问题而生的。

## Skills 的工作模型

在 OpenClaw 中，一个 Skill 是一组可独立装载、可组合的功能单元，包含：

- 提示片段（系统指令、角色定义、Few-shot 示例）
- 工具声明（API 调用、本地脚本、MCP 工具等的包装）
- 资源（静态知识文件、向量库索引、配置模板）

Skill 不会常驻于 Agent 的 prompt 中，而是在触发条件满足时被激活，完成后可以主动卸载。这和我们熟悉的 MCP 服务器动态发现工具有相似的理念，但 Skills 的粒度更小，更偏向“语义能力”而非“通信协议”。

## 实现步骤：从定义到调用

### 1. 按约定组织 Skill 目录

在项目的 `skills/` 下，每个 Skill 一个子目录，至少含一个 `skill.md` 清单文件：

```
skills/
└── weather/
    ├── skill.md
    ├── prompt/
    │   └── system.md
    └── tools/
        └── get_weather.py
```

`skill.md` 是自描述清单，典型结构：

```markdown
---
name: weather
description: 查询指定城市的实时天气和预报
triggers:
  - 天气
  - 气温
  - 要下雨吗
load_strategy: auto
unload_after: 2min
---
```

- `triggers`：当用户输入匹配这些关键词时，Skill 被自动激活。
- `load_strategy`：`auto` 表示关键词触发自动加载；还可以设为 `manual`，仅通过指令显式加载。
- `unload_after`：闲时自动卸载时间，避免长期占用资源。

### 2. 编写能力内容

`prompt/system.md` 会被注入到系统消息中，例如：

```markdown
你是一个天气查询助手，可以使用内置工具 get_weather 查询天气。
仅回答与天气相关的问题，不要提供其他建议。
```

`tools/get_weather.py` 是一个可执行脚本，OpenClaw 会将其封装为函数工具。需遵循接口约定：接收 JSON args，输出 JSON 结果。

### 3. 在 Agent 配置中启用 Skills 加载器

在 Agent 配置文件（例如 `agent.yaml`）中声明 skills 根路径和加载策略：

```yaml
skills:
  path: ./skills
  auto_discover: true
  default_unload_after: 5min
```

OpenClaw 启动时会扫描目录，建立索引。此时 Skill 文件只被解析元数据，提示和工具并不会被真正注入。

### 4. 运行时激活与卸载

当用户输入触发某个 Skill 时，加载器会将对应的系统提示追加到当前会话上下文，工具注册到可用工具列表。一旦接下来的 N 分钟内没有再次触发该 Skill（或主动关闭），加载器将其注销，释放上下文。

你也可以通过指令显式控制：

- `/skill load weather`  手动加载
- `/skill unload weather` 手动卸载
- `/skill list` 查看当前已加载的技能

## 踩坑点

实际项目里，按需加载带来了便利，也埋了几个坑：

- **提示注入顺序**：多个 Skill 被同时激活时，系统提示按加载时间顺序追加，可能导致指令冲突。建议给每个 Skill 明确指令作用域，避免互相覆盖全局行为。
- **工具命名冲突**：不同 Skill 定义了同名工具（如 `search`）时，后加载的会覆盖前一个。解决方法是使用前缀命名，例如 `weather_search`、`docs_search`。
- **卸载时机不当**：如果 Skill 在任务中途被闲置卸载，后续引用会失败。`unload_after` 要略大于用户自然思考间隔，或改为任务结束显式卸载。
- **热加载失败**：修改 Skill 文件后，直接 `reload` 可能因内部状态不一致而失败，推荐重启 Agent 或通过 `/skill reload <name>` 重新解析。
- **资源泄漏**：部分 Skill 打开了外部连接（数据库、浏览器实例），卸载时若未正确清理，会累积资源。务必在 Skill 工具实现中提供 `cleanup` 钩子。

## 可复用的工程建议

1. **将能力原子化**：一个 Skill 只做一件事。复杂流程通过组合多个小程序实现，而非写一个庞然大物。
2. **编写自检清单**：每个 Skill 应包含测试提示和预期输出，方便回归。例如在 `skill.md` 中加入 `test_scenario` 字段，指向一个测试脚本。
3. **利用 MCP 做后端**：对于重度工具调用，可以把 Skill 的工具实现封装为 MCP 服务器，技能加载只是注册一个 MCP 客户端，彻底解耦资源和运行环境。
4. **建立 Skill 版本和依赖声明**：当技能间有依赖（例如基础爬虫技能被多个上层技能复用），在 `skill.md` 中用 `requires` 字段声明，让加载器自动处理依赖顺序。
5. **监控加载频次**：打出加载、卸载事件日志，分析哪个技能使用率低、耗时高，优化触发词和卸载策略。

## 小结

OpenClaw 的 Skills 机制让 AI 助手从“大而全”转向“轻而灵”。核心 Agent 只需要维持基础对话能力，具体领域能力在需要时被透明地注入。这降低了上下文成本，提高了可维护性，也为多人协作开发能力模块提供了清晰边界。

如果你已经在使用 MCP 或插件体系，Skills 可以看作是一种更贴近“意图”的细粒度能力片段。它不替代 MCP，而是与之互补——MCP 解决工具发现和通信，Skills 解决“什么时候该用什么能力”的调度问题。把两者结合，你就能构建出一个可以持续演进、按需生长的 Agent 系统。
