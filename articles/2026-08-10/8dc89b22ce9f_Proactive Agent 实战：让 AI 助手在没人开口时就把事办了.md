# Proactive Agent 实战：让 AI 助手在没人开口时就把事办了

## 背景：从“应声虫”到“未卜先知”

当前绝大多数 AI 助手都是被动响应式的：你问一句，它答一句。这种模式足够应付客服问答或知识检索，但一进入自动化流程或运维场景就显得力不从心。没人想半夜爬起来手动问助手“现在哪些服务挂了”，更没人愿意每天 9 点输入“帮我生成本日站会摘要”。

**Proactive（主动式）能力**的本质，是让 Agent 基于时间、事件或上下文变化，独立完成“感知→决策→执行”闭环。这不等于蛮横地替用户做决定，而是在用户明确授权的范围内，把低价值、重复性的判断与操作自动化掉。

在 MCP (Model Context Protocol) 与插件生态逐步完善的今天，agent 已经有了标准化的“手脚”去读取日历、查询数据库、发送消息、操作文件。剩下的关键问题变成：**如何安全、可控地把“主动触发”这件事工程化落地？**

## 核心问题：触发器 + 决策链

要让 agent 主动办事，至少需要解决两个基座问题：

1. **什么时候醒来**（触发器）  
   - 定时调度：cron 类规则，适合日报、周报、定期巡检。  
   - 事件驱动：webhook、文件系统变动、消息队列新消息、数据库变更通知。  
   - 阈值触发：监控指标达到红线（例如 CPU 超过 90%）。

2. **醒来后怎么做**（决策-执行链）  
   - 收集上下文：通过 MCP tools 拉取当前状态（系统指标、未读邮件、今日会议等）。  
   - 思考与规划：把上下文物化成 prompt，交给 LLM 做出判断，输出需要调用的工具序列。  
   - 安全执行：对高风险操作实施二次确认或白名单拦截。  
   - 记录与反馈：把结果写回用户可见的渠道（群通知、看板、日志），并允许用户给出修正指令。

下面给出一个可落地的最小实现示例，假设我们已有一个通过 MCP 暴露的日历工具和消息通知工具。

## 做法：一个可运行的主循环

**1. 触发器选用 cron**  
在服务器上用系统 cron 或 Python 的 `schedule` 库，每天早 8 点触发一次。触发器只负责唤醒，不包含业务。

**2. 上下文收集**  
唤醒后，agent 调用 MCP 工具 `calendar.list_events` 拉取当天已安排的事件，并调用 `slack.post_message` 的只读模拟，获取最近通知历史（避免重复提醒）。

**3. LLM 决策**  
把收集到的结构化上下文封装成一个函数调用请求。提示词大致为：

```
你是用户的执行助理。当前时间为 {timestamp}。
以下是今天的日历事件：{events_json}
你需要：
- 检查未来24小时内是否有冲突事件。
- 如有冲突，生成一条建议的 Slack 提醒草稿。
输出调用：
  send_slack_reminder(conflict_detail: str, suggestion: str)
或
  no_action()
```

这里的核心技巧是 **不给 LLM 直接执行权限**，只让它返回“要调用什么工具以及参数”。执行动作会经过一层本地校验。

**4. 安全执行与熔断**  
在执行真实操作前，比对工具白名单（例如 `send_slack_reminder` 允许，`delete_calendar_event` 禁止）。对于可能误操作的调用，可以临时生成一条草稿并发送到“人工确认频道”，要求用户回复 `yes` 后再真正执行。

**5. 反馈闭环**  
无论执行还是跳过，agent 都将决策理由和结果写入日志数据库，供后续分析误判比例，逐步收紧 prompt 与规则。

## 踩坑实录

- **幻觉导致误操作**  
  LLM 可能会凭空编造 `send_slack_reminder` 需要的参数。**解法**：必须对 LLM 输出的函数调用做 JSON Schema 校验和字段合理性检查，例如日期必须在今天±1天范围内，不合理则退回重试或降级为只读通知。

- **打扰频率失控**  
  一个 proactive agent 最招人烦的地方是“太主动”。巡检频率过高或因一次未修复的异常反复推送。**解法**：引入冷却时间和变化摘要推送。例如相同冲突 2 小时内不再告警，除非事件详情变化超过 30%。

- **权限边界不清晰**  
  如果 agent 可以自由读取全公司日历并写入任意频道，出一次事故信任就崩塌。**解法**：MCP 工具的 scope 最小化，单独为 proactive 角色创建只读或受限 token。敏感操作一律经过人工确认通道。

- **状态膨胀**  
  当 agent 需要记忆上次什么做了什么没做，会不自觉地积累大量会话状态。**解法**：将持久化状态（如已处理事件 ID 集合）外置到轻量 KV 存储，而非塞进 prompt。每次唤醒只读取必要的差量状态。

## 可复用建议

如果你打算在自己的 agent 项目中加入 proactive 能力，可以从以下几个层面抽象：

1. **分离关注点**：将 `Trigger`、`ContextGatherer`、`DecisionEngine`、`ActionExecutor`、`FeedbackLogger` 拆成独立模块，方便替换触发器类型（从 cron 换到 Kafka 只需改 trigger）。
2. **工具皆 MCP**：所有能力（读日历、发消息、查日志）都对接到 MCP server，搭配标准工具描述。这样 agent 不需要关心底层实现，迁移到不同环境时只需切换 server 配置。
3. **设置安全网“护栏”**：
   - 操作分级：Level 0 只读，Level 1 发送通知，Level 2 修改数据，Level 3 删除/重启。Proactive agent 默认只允许 Level 0-1。
   - 每次决策前抓取一次“用户当前状态”（勿扰模式、休假标记），若判定不宜打扰则自动抑制。
4. **从简单场景起步**：不要一上来就做“全自动运维”。建议从日报摘要、日历冲突提醒、过期证书检查这类低风险、纯报警的场景开始，跑通整个链路再逐步放开写操作。

## 总结

Proactive 能力是 agent 从玩具走向工具的关键一步。它不再等待用户“念咒语”，而是主动识别等待执行的低熵任务。MCP 的标准化让“感知”和“执行”的成本大幅降低，你可以快速给助手接上眼睛和手脚。

但主动不是鲁莽。工程实践里，触发器、决策链、安全护栏和反馈闭环缺一不可。只要设计得当，一个安静在后台检查日历、帮你提前提醒冲突而不需要你开口的 agent，可能比一个每分钟在群里刷存在感的“智能管家”更值得信赖。
