## 背景：Agent 自主执行带来的“误删恐惧”

当你让一个 LLM Agent 自动完成“整理项目目录，清理过期构建产物”这件事时，最怕的不是它什么都没做，而是它把 `src/` 当作垃圾、把 `.git` 当成临时文件一并删了。这种恐惧在 Agent 获得文件系统读写能力后会迅速放大，尤其在生产环境或本地工作目录中。

OpenClaw 设计之初就考虑了这个问题。它不是简单地给 Agent 挂一个权限提示，而是在文件系统层实现了一套可控的安全沙箱。本文围绕该沙箱模型，解析它如何从机制上避免“误删文件”这件事，并给出可落地的配置和实践建议。

## 问题：漏洞不在模型，在环境隔离

很多人会把误删归咎于 Agent 没理解指令，但实际上即便提示工程做得再好，模型生成的命令也可能因为上下文偏差、路径拼写错误、符号链接解析异常等问题引发灾难。真正的问题在于**执行环境没有隔离边界**。如果 Agent 看到的文件系统就是宿主机的全部目录树，一次 `rm -rf /home/user/project/*` 就会造成不可逆损失。

常见的“轻量沙箱”做法是跑在 Docker 容器里，但容器内依然能看到完整的 Linux 根文件系统，如果挂载了宿主机卷，危险依然存在；而单纯通过 prompt 约束 Agent 的行为又不可靠。我们需要一套精细化的文件系统权限控制，把 Agent 的破坏力限制在预期范围。

## OpenClaw sandbox 安全模型：做法与步骤

OpenClaw 的沙箱模型结合了三层控制：路径白名单、只读挂载与写时复制（CoW）层、系统调用过滤。

### 1. 工作区隔离与路径白名单
每个 Agent 实例启动时，都会在宿主机上创建一个独立的工作目录（如 `/var/lib/openclaw/agents/<agent-id>/wksp`），Agent 所有文件读写操作默认都在该目录内完成。通过配置 `workspace` 字段，可以将宿主机的特定目录以只读方式映射进工作区：

```yaml
agent:
  workspace:
    root: /var/lib/openclaw/agents/agent-01/wksp
    readOnlyMounts:
      - hostPath: /home/user/project/reference
        mountPath: /mnt/reference
    writableMounts:
      - hostPath: /home/user/project/output
        mountPath: /mnt/output
```

Agent 看到的是一个根目录为 workspace root 的文件系统，要访问 `reference` 只能读，要输出结果只能写到 `output`。其他宿主机路径完全不可见，连 `/etc/passwd` 都看不到，误删无处可及。

### 2. 写时复制层与回滚
对于允许写入的挂载点，OpenClaw 不会直接操作宿主机文件，而是在一个 overlay 文件系统上记录所有更改。写入的数据先写入临时层，任务结束后，如果定义了 `autoCommit: false`，则所有写操作不会持久化到宿主目录。即便 Agent 在输出目录执行了 `rm -rf /mnt/output/*`，重启后宿主机上的原始数据毫发无伤。这个机制对实验性任务价值极高。

### 3. 系统调用过滤
OpenClaw 通过 seccomp 规则禁止了部分系统调用（如 `unlink` 对受保护路径、`rename` 跨设备等），进一步限制 Agent 异常行为。例如，即便通过某些方式获得了宿主机路径，调用 `unlinkat` 也会被拦截并抛出异常，Agent 会收到“操作不允许”的错误反馈，而不是静默破坏。

## 踩坑点：实际使用中不容忽视的问题

1. **白名单路径粒度失衡**  
   如果把需要读取的项目根目录整个只读挂载，Agent 会看到大量无关文件，不仅拖慢扫描，还可能因为符号链接或 `.git` 导致非预期行为。建议仅挂载最小必要子目录。

2. **overlay 磁盘占用**  
   如果 Agent 大量生成临时文件（例如数据分析任务），overlay 层会迅速膨胀，写满 `/var/lib/openclaw` 所在分区。需要设置 `storageQuota` 限制，并配合定期清理策略。

3. **权限拒绝导致的静默失败**  
   当 Agent 尝试写入不允许的路径时，seccomp 拦截并让进程收到 `EPERM`。如果不捕获错误，Agent 可能误以为操作成功，缺少必要的告警机制。建议在 Agent 执行日志中开启 `kickedLogLevel: verbose`，并监控 `permission_denied` 事件。

4. **跨挂载点原子性问题**  
   如果 Agent 试图在同一任务中同时处理只读和可写挂载点的文件移动，由于 overlay 层的限制，跨越边界的 `mv` 操作会降级为“复制+删除”，可能导致中间状态不一致。设计任务时应避免此类操作。

## 可复用建议

- **一 Agent 一工作区**：为每个 Agent 实例生成唯一工作区 ID，任务完成后可选择提交或丢弃。这是防止串扰和误删的第一道防线。  
- **最小权限原则**：只读挂载仅包含任务输入所需文件，可写挂载仅指向指定输出目录，严禁挂载 `$HOME` 或 `/`。  
- **开启审计与回滚**：在生产环境中始终启用 `autoCommit: false`，任务结束后人工检查产物，确认无误再提交；结合审计日志回溯 Agent 的所有文件操作。  
- **性能与安全权衡**：对于高频 I/O 任务，评估是否需要关闭部分 seccomp 规则以提升性能，但要有辅助监控补位。  
- **测试“破坏”场景**：定期在 staging 环境故意让 Agent 执行 `rm -rf /`、修改系统配置等，验证沙箱拦截是否健全。

## 总结

OpenClaw 的沙箱模型通过路径隔离、只读挂载、写时复制与系统调用过滤，从根本上化解了 Agent 误删文件的恐惧。这不是一个“防君子不防小人”的提示词技巧，而是在执行层为自动化操作划定了硬边界。即便如此，沙箱也不是银弹：合理的挂载策略、资源限额和监控审计同样不可缺席。把这些工程措施配上，你才能放心地把 `rm` 权限交给一个自主决策的 Agent。
