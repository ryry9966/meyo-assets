# Prompt 工程实战：Cron 任务的 instruction 应该长什么样？

## 背景：被“一句话 cron”坑过的人都懂

在 OpenClaw 这类 Agent 编排环境里，Cron 是最朴素的自动化入口——定时触发、无需人工介入，听起来很适合巡检、日报、数据同步这类重复操作。

多数人第一次配 Cron 时，注意力全在「任务做什么」上，Instruction 往往随手写成一句大白话，例如：

> 每小时检查一次服务健康状态，有问题通知我。

等上线后，你可能很快会遇到三件事之一：

1. 每条 cron tick 都给你发一条“一切正常”的消息，比闹钟还准时；
2. 真出问题时反而静悄悄，因为 Agent 不知道什么叫“有问题”；
3. 报告的时间戳是 UTC，你每次都要心算 +8 小时。

我把这些归结为一个核心原因：**Cron 环境下，Agent 没有对话历史、没有上下文纠正机会，你的 Instruction 就是它全部的行为边界。** 它不像人，能根据你的语气揣摩意图；它只会严格（且可能愚蠢地）执行你写的每一个字。

## 一个真实翻车现场

我需要一个「每天 9:00 检查 SSL 证书到期情况，仅当剩余天数不足 30 天时通知到企业微信」的 Cron。

第一个版本的 Instruction 长这样：

```
每天早上 9 点，检查公司所有域名的 SSL 证书到期时间，快过期了就提醒我。
```

结果第二天早上，我收到了 8 条消息，每一条都是“证书还有 200 多天，正常”。Agent 把“快过期”理解成了“只要我检查了，就应该输出结果”。更有意思的是，它是按触发时刻的 UTC 时间来判断“早上 9 点”的，但我的期望是北京时间。

问题很清楚：**模糊的需求描述 ≠ Cron Instruction**。

## 做法：像写程序一样写 Instruction

经过几次迭代，我总结出一套实践方法。核心思路是：**把 Cron Instruction 当成一个无状态函数的合约，明确输入、处理逻辑、输出和异常路径。**

### 1. 先解决环境与身份问题

Cron 没有“上一轮对话”可以继承，所以 Agent 是谁、在什么时间、什么时区工作，必须写清楚。我会在 Instruction 开头固定一段：

```
你是运维助手。当前任务由 cron 在每天北京时间 09:00 触发。
执行前请使用工具获取当前北京时间，不要依赖系统默认时区。
```

### 2. 用“条件-动作”代替自然语言描述

“有问题通知我”太模糊。需要把判断条件量化，并且明确输出抑制逻辑。改后的版本：

```
使用【SSL证书检查工具】查询以下域名：example.com, api.example.com。
对每个域名，获取证书到期日。
计算 (到期日 - 当前北京时间) 的天数差。
仅当天数差 < 30 时，才向【企业微信通知工具】发送一条 Markdown 消息。
如果所有域名的天数差都 >= 30，不发送任何消息。
```

这样 Agent 就不会画蛇添足地汇报“一切正常”，因为它的输出接口被严格约束了。

### 3. 输出格式必须给 Schema，不是例子

即使你给了例子，Agent 仍可能在格式上自由发挥。我习惯直接给出要使用的工具和参数结构，类似：

```
调用通知工具时，参数为：
{
  "msgtype": "markdown",
  "markdown": {
    "content": "## SSL 证书到期预警\n- 域名：{domain}\n- 剩余天数：{days}\n- 到期日期：{expiry_date}"
  }
}
```

并要求 `{domain}`、`{days}`、`{expiry_date}` 从实际检查结果中填入。这比写“用 markdown 格式通知”可靠得多。

### 4. 必须定义异常路径

Cron 执行时没有人实时盯着，如果工具调用失败、返回非预期结构，Agent 默认可能只是吐出报错堆栈然后沉寂。至少需要约定：

```
如果工具调用失败或返回空结果，立即使用通知工具发送一条“证书检查任务执行异常”的简要消息，包含错误原因。
重试 1 次，间隔 5 秒。
```

这样才算闭环。

### 5. 考虑幂等与去重

Cron 可能因为服务重启等原因意外重复触发。如果你的任务会创建资源（如发邮件、写数据库），需要在 Instruction 中加上去重逻辑，例如：

```
先检查上一次成功执行的时间（可从日志工具获取），如果距离当前执行不足 30 分钟，则跳过本次任务。
```

## 踩坑清单

- **时区陷阱**：Cron 表达式的时区、Agent 运行环境时区、业务期望时区三者如果不一致，必定出问题。强制在 Instruction 中要求 Agent 主动获取指定时区的时间。
- **工具白名单差异**：有些平台 Cron 场景下暴露的工具集和 Web 对话不同，可能缺少你需要的工具。确认一下哪些工具对 Cron 可见。
- **输出不可见**：没有明确通知目标的 Cron 等于“暗中操作”。一定要指定输出通道——通知、日志文件、Webhook 均可。
- **上下文长度膨胀**：如果你把大段参考文档（如内部域名列表）直接塞进 Instruction，可能会挤占工具调用的窗口。改成让 Agent 去读一个固定链接或调用数据源工具。
- **“沉默失败”**：Agent 尝试兜底、但无明确兜底策略时，可能什么都不做，表面看起来“执行成功”。一定要规定“失败时必须通知人”。

## 可复用的 Instruction 模板

在实际工程里，我几乎所有的 Cron 任务都套用同一个模版，只替换业务部分：

```
## 角色与环境
你是【角色】。当前任务由 cron 触发，周期性执行。
请使用工具获取当前【时区】时间，不要依赖系统时区。

## 输入数据
使用【工具A】获取【具体数据源或参数】。

## 处理逻辑
1. 对获取的数据执行【判断条件/计算公式】。
2. 如果【异常条件】，则执行【动作】；否则，执行【动作或跳过】。

## 输出要求
仅当满足【条件】时，调用【通知/写入工具】，输出格式：
{
  "参数": "值"
}
不满足条件时，不产生输出。

## 异常处理
如果工具调用失败，重试 1 次。若仍失败，使用通知工具发送告警消息，内容包含失败步骤和错误信息。

## 幂等
执行前检查最近一次成功执行时间，如果在【容忍间隔】内，跳过本次。
```

这个模板没有炫技的成分，但能挡住 80% 的模糊需求导致的奇怪行为。

## 总结

很多人把 Prompt Engineering 理解成“用精妙的文字让模型输出更好”，但在 Cron 这种工程化场景里，好的 Instruction 更接近于写接口契约：**把边界说死，把异常管住，把输出定型。** 如果你每次写 Cron Instruction 都像在写一个需求文档，那你大概率走在了正确的方向上。

下一次配 Cron 时，不妨先花 10 分钟把条件量化、把通知策略写清楚，你未来会感谢现在的自己。
