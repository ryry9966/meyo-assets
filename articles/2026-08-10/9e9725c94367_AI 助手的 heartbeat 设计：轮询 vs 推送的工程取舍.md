## 背景：为什么 AI 助手需要心跳

在 OpenClaw 这类以 Agent/MCP/插件为核心的自动化框架中，AI 助手经常需要感知外部世界的异步变化：长时间运行的工具调用、后台任务状态更新、插件热加载、MCP 服务端推送新资源等。心跳（heartbeat）机制就是让系统各个部分互相确认“我还活着，你还在听”的基础协议。

但心跳不止是存活检测。设计不好的心跳会变成噪声风暴，尤其当 Agent 并发调用多个 MCP 服务、插件进程、远程 worker 时，上百个轮询连接可能在数秒内把服务器拖垮。本文不讨论教科书式的协议对比，而是从一个真实工程视角，梳理我们在 OpenClaw 生态中构建心跳机制时的权衡与落地经验。

## 核心矛盾：轮询简单，推送高效，但都不是银弹

### 轮询（Polling）

客户端定时发起请求询问状态。实现门槛极低：一个 `setInterval` 加上 HTTP GET 就能工作。

**优点：**
- 无状态，极易调试，完全兼容 HTTP 基础设施（代理、负载均衡、防火墙）。
- 适合低频、对延迟不敏感的场景，比如插件版本检查、每日任务状态同步。

**工程痛点：**
- 空转成本高：大部分请求返回“没有新消息”，浪费带宽和 CPU。
- 时延与开销的折中：缩短轮询间隔可以降低端到端延迟，但压力呈线性增长。在一个有 50 个活跃 MCP 会话的 Agent 中，3 秒轮询意味着每秒近 17 次请求，还没算 Keep-Alive 的开销。
- 缺乏背压：当服务端积压大量事件时，轮询客户端可能永远追不上。

### 推送（Push，基于 SSE / WebSocket）

服务端主动向客户端下发事件，客户端保持长连接。

**优点：**
- 实时性高，没有无效轮询开销，天然适合事件驱动的 Agent 流程。
- 支持流式响应，比如 MCP 的 `resources/updated` 通知、长时间工具执行的进度输出。

**工程痛点：**
- 连接状态管理复杂。SSE 看似轻量，但在多层代理后面容易断连，需要客户端实现健壮的重连逻辑。
- 推送通道容易被企业防火墙、反向代理的超时配置静默断开，排查困难。
- 服务端需要维护连接状态和心跳发送，增加了内存与并发模型复杂度（特别是多 worker 进程下如何广播事件）。

## 我们的做法：混合心跳 + 协议自适应

在 OpenClaw 的实践里，我们不追求全局统一，而是根据通信层级的特性，分层设计心跳：

### 1. Agent ↔ MCP 服务端：强制 SSE 推送 + 应用层心跳

对于 MCP 的 `notifications` 通道，规范本身就是基于 SSE 的推送。我们复用同一个通道发送 `heartbeat` 自定义通知，每 15 秒一次。Agent 侧设置 45 秒超时，连续两次未收到心跳则认为连接失效，主动重连。

**具体步骤：**
- 在 MCP 服务端，每 15 秒通过 `/sse` 流写入一条 `event: heartbeat\ndata: {"ts": ...}\n\n`。
- 客户端使用 `EventSource` 时，记录上次收到 `heartbeat` 事件的时间戳。用一个独立定时器每 5 秒检查一次差值，超过阈值则主动关闭连接并重连。
- 重连使用指数退避，初始 1 秒，上限 30 秒，避免重试风暴。

### 2. 插件宿主 ↔ 插件进程：长轮询退避 + 探测帧

部分插件运行在受限的子进程中，不方便持有长连接，我们采用 HTTP 长轮询（Long Polling）作为退避方案。

- 插件向宿主发起 `/poll` 请求，携带上次事件序号和 30 秒超时。
- 宿主在 30 秒内有新事件立即返回，否则等到超时返回空响应。
- 插件收到响应后立即发起下一次长轮询，保证永远有一个悬挂请求。
- 宿主同时记录每个插件的最近活跃时间，超过 60 秒无任何轮询视为掉线。

**踩坑点：**
- 浏览器或某些 HTTP 库对长轮询的默认超时可能短于应用层超时，导致请求被底层断开却未向上抛出错误。必须显式设置 socket 超时 > 长轮询超时。
- 多个插件同时长轮询时，宿主的 HTTP 并发数激增，需用连接池限制，我们通过 `maxSockets` 约束在 100 以内。

### 3. Agent 内部异步任务：基于状态机的心跳抑制

Agent 发起工具调用后，往往需要等待异步结果。如果每个等待都用轮询，CPU 很快会被空耗殆尽。我们的方案是：
- 工具启动后即返回 `taskId`，并注册一个 `onComplete` 回调。
- 执行环境通过内部消息总线推送到 Agent 的调度器，而不是让 Agent 循环查询。
- 对于外部无法推送的场景（如第三方 HTTP API），才回退到轮询，但会做指数间隔延长：最开始 1 秒一次，3 次后延长到 5 秒，10 次后变为 30 秒，防止无效高频轮询。

## 可复用的实践建议

- **分层决策**：实时的推送通道用 SSE/WebSocket，低频查询用普通轮询，中间地带用长轮询。不要用单一方案硬套所有路径。
- **心跳超时三倍法则**：客户端超时阈值设为心跳间隔的 3 倍，避免因 GC 暂停或网络抖动导致误报断连。
- **加噪声检测**：如果短时间内收到大量重连，一定是某处配置不对或网络震荡，应触发告警并降低重试频率被应用层熔断。
- **所有心跳可观测**：记录心跳丢包率、重连次数、连接时长，接入现有监控，把心跳作为首类健康指标。
- **MCP 实践者注意**：MCP 规范目前对心跳没有强制定义，可以约定使用自定义 `heartbeat` 通知，但在连入第三方 MCP 服务时应允许关闭或适配，防止协议冲突。

## 总结

AI 助手的心跳设计，本质是在“简单低效”和“复杂实时”之间做权衡。在工程落地中，我们并没有创造新协议，而是通过分层混合、自适应退避、可观测性兜底，把轮询的可靠与推送的效率结合起来。对 OpenClaw 用户而言，理解这些取舍，可以帮助你在搭建多 Agent、多插件系统时，避免一边倒地选择轮询而被资源耗尽，或者完全拥抱推送却被连接管理的细节淹没。

务实一点：先用最可靠的轮询跑通流程，再在关键路径上引入推送，同时保留降级为轮询的开关。这种渐进式的工程思路，比追求完美的协议设计更能稳定交付价值。
