## 背景：Agent 的“失忆症”

OpenClaw 生态里，基于 MCP 或插件搭建的 Agent 已经能完成很多单次任务：查天气、发邮件、调 API。但多数 Agent 在会话结束后就“恢复出厂设置”，每次交互都要重新告知偏好、风格、常用工具链。这种失忆问题在持续协作的场景下尤其致命——比如用 Agent 管理日程、辅助写代码、自动化私人工作流。

Agent 记忆系统的目标，就是在不破坏安全与可控性的前提下，让 Agent 像 Unix 工具一样“无状态但可配置”，又像长期助手一样“记住你的习惯”。

## 问题拆解：记忆到底该记什么？

工程上可以把记忆分成三层：

1. **短期记忆**：当前会话上下文。无状态方案（每次传全量消息）可行，但窗口有限、成本高、容易注入噪声。
2. **用户档案**：稳定的元偏好。比如“代码风格：Rust 优先；输出语言：中文；时区：Asia/Shanghai”。这类数据量小、变化少，适合用文件或 KV 存储。
3. **长期情景记忆**：从历史交互中提取的模式，比如“部署前喜欢先 dry-run”、“会议纪要格式偏好”。需要结构化存储和置信度管理。

三层记忆各有难点。档案容易变成“垃圾填埋”，长期记忆最难做好：提取不准会变成噪音，过度记忆会让 prompt 臃肿，错误的记忆比没有记忆更危险。

## 做法：一套可落地的轻量记忆栈

以 OpenClaw + MCP 为例，可以搭一套渐进式记忆系统：

### 1. 用户档案：以文件为单一事实来源

在 `~/.openclaw/user_profile.yaml` 维护：

```yaml
meta:
  timezone: Asia/Shanghai
  lang: zh-CN
prefs:
  code_style:
    language: Rust
    formatter: cargo fmt
  writing:
    tone: engineering
    avoid_phrases: ["leverage", "delightful"]
tools:
  defaults:
    kubernetes_context: prod-cluster
  shortcuts:
    depl: kubectl apply -f
```

通过 MCP 的 `file-server` 或自定义 `memory` 插件，Agent 在每次任务开始前加载该文件，拼入系统提示。用户用 `claw config edit` 或对话指令 (`remember: my default K8s context is staging`) 直接修改，避免 Agent 自作主张更新。

### 2. 短期记忆管理：按需裁剪上下文

不要无脑传所有历史。在 Agent 循环中增加一个“压缩”步骤：当 token 数接近阈值时，用 LLM 对已发生动作做摘要，保留关键决策点、错误信息和未完成目标，丢弃冗余的中间输出。OpenClaw 的 `context_compressor` 插件可以做成 MCP tool，接收消息列表返回压缩版。

摘要过程中顺带提取可归档的偏好线索（见下一步），但不立即写入档案，而是暂存到“候选记忆缓冲区”。

### 3. 长期情景记忆：异步提取 + 人工仲裁

在会话结束后，触发一个离线任务（或用低优先级模型）扫描压缩后的对话摘要，提取以下模式：
- “用户在 X 情境下倾向于 Y”
- “用户显式表达了 Z 偏好”

输出每条记忆附带置信度（0-1）和证据片段。低于 0.7 的进入 `~/.openclaw/memory_inbox.yaml`，等待用户确认；高于阈值的自动合并到档案，但标记为 `auto: true`，下次会话显示来源以便质疑。

存储用 SQLite + 简单向量索引（chDB 或 sqlite-vss），方便本地查询相似历史情境。比如：“上次遇到类似报错时用户做了什么？”

### 4. 记忆注入：按需检索而非全量堆砌

每次任务开始在档案中加载稳定偏好，然后根据当前任务描述在长期记忆库里检索 top-3 相关条目，以 `---user memories (auto retrieved)---` 块插入系统提示末尾。并在 UI 中提示用户“本会话使用了 3 条历史记忆”，保持透明。

## 踩坑实录

- **档案膨胀**：用户曾输入 `remember: I like Python`，一周后又让其用 Go，Agent 却频繁推荐 Python。解决：为每条偏好加 `last_used` 时间戳，超出 30 天未触发的自动降权或归档到“休眠记忆”。
- **偏好冲突**：代码风格既想要 `cargo fmt` 又想要 `rustfmt.toml` 特定配置。在档案里用 `priority` 字段解决，短路径（工具级）覆盖长路径（全局级）。
- **记忆泄露风险**：档案里留了 API endpoint 测试地址，Agent 在给外部建议时差点引用。必须支持 `private: true` 标记，注入时过滤。
- **冷启动**：新用户没有任何档案，Agent 行为不稳定。建议提供一个 `claw init` 向导，主动问 5-6 个问题，生成初始档案。也能避免 LLM 猜测偏好时的幻觉。

## 可复用建议

1. **从文件起步，够用再上数据库**。本地 YAML 足够覆盖 80% 的档案需求，且用户能直接编辑，无黑箱感。
2. **把记忆服务封装成 MCP 工具**：`get_profile`、`upsert_prefs`、`search_memories`。这样 Agent 本身调用记忆就像调其他 API，逻辑内聚、容易测试。
3. **所有自动记忆都必须可溯源**。在 prompt 里附带记忆来源和提取时间，让用户可以 `/trace-memory` 查看并撤销。
4. **定期清理**：写一个 cron job 每周扫描过期记忆、低置信度且未确认的候选记忆，生成清理报告并推送给用户，避免记忆库腐化。
5. **尊重边界**：不要默默记录。Agent 想记下偏好时，应礼貌询问：“我注意到你倾向于 X，要记住吗？[y/n]”。

## 总结

Agent 记忆系统的核心矛盾是“自动化带来便利”与“过度记忆侵犯控制感”之间的平衡。工程上最可靠的路径是：用文件保持用户控制权，用短期压缩和异步提取降本增效，用置信度与人工仲裁守住质量底线，用 MCP 封装让记忆组件可插拔。

最终效果不是让 Agent 显得“通人性”，而是让它像称职的工程师搭档——不必每句话都重复背景，但你随时可以纠正它的“印象”。
