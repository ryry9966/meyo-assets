# Agent 的 HEARTBEAT.md：让 AI 主动做事而不是等你提问

## 背景：Agent 为什么需要心跳

基于 LLM 的 Agent 大多数时候还是“问—答”模式：你发一条消息，它处理一条。但在实际工程里，大量维护性任务需要的不是反应，而是**周期性主动检查**——比如每小时扫描一次新开 Issue、每天早晨拉取监控指标生成简报、每 15 分钟校验 CI 状态等。

传统解法是把这些任务写成定时脚本，但脚本缺乏 Agent 的语义判断能力（比如“这个 Issue 是不是需要紧急响应”），维护成本随着规则增长快速膨胀。我们希望有一种方式，让 Agent 带着它的工具库和推理能力，**以定期心跳触发的形式主动做事**，而不是等用户来敲门。

## 问题拆解

要让 Agent 具备主动执行能力，需要解决三个工程关注点：

1. **任务定义**：如何用声明式的方式告诉 Agent，每个心跳周期该“想什么、查什么、做什么”？
2. **触发与调度**：谁负责按时唤醒 Agent，并把这个周期任务以最自然的方式喂给它？
3. **运行时的健壮性**：如何避免重复执行、API 限流、上下文膨胀这些自动化里常见的硬伤？

## 核心做法：引入 HEARTBEAT.md

我们用一个 Markdown 文件 `HEARTBEAT.md` 作为 Agent 心跳任务的“程序说明书”。它既不是代码，也不是 prompt 模板，而是一份**可读、可版本控制、可由 Agent 解析的任务定义**。

### 步骤 1：编写 HEARTBEAT.md

文件使用 YAML front matter 声明调度参数，正文用自然语言描述每次心跳需要执行的检查逻辑与动作。下面是一个监控 GitHub 新 Issue 的示例：

```markdown
---
heartbeat: every 30 minutes
mcp_servers: [github]
max_steps: 8
idempotency_store: redis://... # 幂等状态存储地址
---

# 每 30 分钟检查一次示例仓库的新 Issue

你需要使用 GitHub MCP 工具完成以下工作：

1. 获取仓库 `myorg/my-service` 最近 30 分钟内创建的 Issue 列表。
2. 对每条新 Issue 进行判断：
   - 如果标题包含“bug”、“崩溃”、“500”，且正文包含错误堆栈，则：
     - 添加标签 `triage/urgent`
     - 在 Issue 内回复一条简短确认，告知已自动标记，人工将在 1 小时内响应。
   - 如果是功能建议，添加标签 `enhancement`，无需回复。
3. 将本次处理过的 Issue ID 存入幂等存储，避免下次重复处理。
```

正文的要求是**可执行的、有明确判断分支的**，就像给一个初级工程师写 checklist。Agent 读到这些段落时，会像执行任务指令一样分步调用工具。

### 步骤 2：让 Agent 框架理解并调度心跳

以 OpenClaw 为例，它支持通过插件扩展触发方式。具体做法是编写一个 `heartbeat-loader` 插件：

1. 启动时（或按 cron 表达式）读取项目根目录的 `HEARTBEAT.md`。
2. 解析 front matter 拿到 `heartbeat` 间隔，注册对应的时间触发器。
3. 每次触发时，将整个 `HEARTBEAT.md` 的正文作为系统消息的一部分注入 Agent 会话，同时附带一个特殊的用户消息：“[心跳] 现在是 {timestamp}，请按 HEARTBEAT 任务描述执行检查。”
4. Agent 执行结束后，该会话不会保留到下一次心跳，避免上下文无限增长。

> 非 OpenClaw 环境也容易迁移：用系统 cron 调用 CLI 命令 `agent run --task-file HEARTBEAT.md`，一样可以实现定时执行。

### 步骤 3：配置幂等与安全围栏

心跳任务最怕两件事：重复执行和工具越权。

- **幂等**：让 Agent 在每次任务中都检查 `idempotency_store`（Redis、SQLite 等）里上次处理的资源 ID 集合，执行前先过滤。
- **工具白名单**：通过 `mcp_servers: [github]` 明确限制本次心跳可以调用的 MCP 服务器，框架在执行时自动屏蔽其它工具。防止“它突然去改 DNS 记录”的意外。
- **速率保护**：Agent 框架应在调度层保证任务不会在上一轮完成前再次触发；同时限制工具调用频率（例如对 GitHub API 的调用不超过 5 次/分钟）。

## 踩坑与排障

在实践中，以下几个点容易翻车：

- **心跳间隔与任务耗时不匹配**：如果任务需要 20 分钟才能跑完，但 heartbeat 设成 15 分钟，会导致任务堆积。解决办法是增加 `timeout` 字段，并在调度侧加锁。
- **LLM 对“最近 30 分钟”的时间解析不准**：避免让 Agent 自行计算时间窗口，而是由调度器在注入的提示中直接给出开始时间戳和结束时间戳，例如：“请查询 2025-03-17T12:00Z 至 2025-03-17T12:30Z 创建的所有 Issue”。
- **自然语言描述过度宽松**：如果只写“处理新 Issue”，Agent 的执行结果会非常随机。必须给出具体的判断树和动作，就像上文的示例一样工程化。
- **状态存储失败导致的重复动作**：若 Redis 不可用，Agent 可能会重复打标签或重复回复。需要增加一个“如果无法查询幂等存储，仅记录警告，不做变更”的兜底逻辑。

## 可复用建议

1. **HEARTBEAT.md 模板化**：为常见心跳场景（监控仓库、日报生成、SSL 证书检查等）提供模板，降低编写成本。
2. **心跳输出标准化**：让 Agent 在每次心跳结束时输出一份结构化摘要（成功/失败/跳过/错误），写入 `heartbeat.log.jsonl`，方便后续审计和告警。
3. **接入 MCP 缓存**：利用 MCP 服务器的 `resource` 缓存机制避免每次心跳都从零拉取大量数据。
4. **逐步放权**：新写的心跳任务先以 `dry-run` 模式运行，即工具调用只记录不执行，观察一两轮后再放开。
5. **与插件市场结合**：将成熟的心跳任务打包成 OpenClaw 插件，通过一个安装命令就直接部署到团队的工作空间。

## 总结

`HEARTBEAT.md` 这个模式把 Agent 从“被动应答”拉到“主动值守”的位置。它不是一个魔法方案，而是将定时调度、Agent 推理和 MCP 工具链缝合在一起的工程实践。核心收益在于：用一份人可读的 Markdown 文件，替代过去需要写脚本、维护规则引擎才能实现的自动化——同时保留 Agent 的判断弹性。只要把幂等、限流和明确的检查分支做好，它完全可以成为生产环境中可靠的守护者。
