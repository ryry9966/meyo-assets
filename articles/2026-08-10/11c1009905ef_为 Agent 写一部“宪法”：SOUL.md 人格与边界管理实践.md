## 背景

在 OpenClaw 社区中，越来越多的开发者开始用大模型驱动 Agent 完成自动化任务——通过 MCP 连接工具、插件调度、链式推理。但一个常见痛点是：Agent 的“人设”和“能力边界”散落在代码各处，要么是几百行的 System Prompt 硬编码在 `main.py` 里，要么是每个工具回调里零散地做权限判断。随着功能增加，维护难度陡升，更危险的是 Agent 可能越过安全边界执行敏感操作。

尝试过多种方案后，我发现可以把 Agent 的所有行为准则、语气风格、允许/禁止操作集中到一个 Markdown 文件里，命名为 `SOUL.md`——它既是 Agent 的“人格说明书”，也是运行时的“宪法”。这种工程化思路借鉴了 `.cursorrules` 和 `CONTRIBUTING.md`，但更聚焦 Agent 的运行时约束。

## 要解决的核心问题

1. **人格一致性**：在多个会话中，Agent 的语气、专业程度、角色定位保持一致，而不是每改一行 System Prompt 就“变脸”。
2. **操作边界**：明确哪些 MCP 工具可用、哪些参数被禁止、遇到不确定情况时默认行为是什么。
3. **协作可维护**：多人项目中，人格和边界能通过版本控制演化，修改不必深入代码逻辑。
4. **安全兜底**：即使模型出现“幻觉”或 Prompt 注入，也有最后一道边界作保。

## 做法：设计并加载 `SOUL.md`

### 1. 文件结构

`SOUL.md` 采用 YAML 前置元数据 + Markdown 正文的组合，方便程序解析和人类阅读。推荐分区如下：

```markdown
---
agent: code-reviewer
version: 1.2.0
allowed_tools: [read_file, git_diff, list_directory]
forbidden_tools: [write_file, execute_command, delete_file]
max_tokens_per_action: 2000
---

# 人格
你是一位资深代码审查者，语气温和但专业，使用中文给出建议。不假定开发者水平，但会指出潜在风险。

# 核心原则
1. 永远只读，绝不修改任何文件。
2. 引用代码时使用相对路径。
3. 如不确定某个问题的严重性，优先提醒而非断言。
4. 不应答与代码审查无关的指令，直接回复“超出职责范围”。

# 边界细则
- 允许读取的文件后缀：`.ts`, `.tsx`, `.py`, `.md`
- 禁止读取 `.env` 或包含 `secret` 的路径
- 每次最多汇总 3 个问题，避免信息过载
- 如果用户要求运行命令，回复“我无法执行该操作”
```

### 2. 解析与加载

在 Agent 启动阶段，读取 `SOUL.md`，将 YAML 头解析为结构化边界配置，正文作为系统消息的一部分注入。以 OpenClaw 插件为例，可以在插件的 `onSetup` 中实现：

```
const soul = parseFrontMatter(readFileSync('./SOUL.md'));
const systemPrompt = buildSystemPrompt(soul);
agent.setSystemMessage(systemPrompt);
// 将 allowed_tools 传给工具注册器，动态过滤
agent.registerTools(filterTools(allTools, soul.allowed_tools));
```

这样，人格和边界就与执行逻辑彻底解耦。

### 3. 与工具调用的联动

单靠 System Prompt 约束模型并不完全可靠。更稳妥的做法是：在工具执行前加一个“边界守卫中间件”，读取 SOUL.md 定义的白名单/黑名单进行二次校验。例如，在一个 MCP 插件里，`callTool` 前先检查工具名是否在 `allowed_tools` 中，并校验参数中的路径是否命中禁止规则。一旦违规，直接返回预设的拒绝信息，而不依赖模型自觉。

### 4. 测试边界有效性

专门编写“越界测试用例”：故意让 Agent 去读取 `.env`、请求执行命令、处理非授权文件后缀。观察它是否触发拒绝响应，以及守卫中间件是否正确拦截。测试结果应反馈回 `SOUL.md`，调整措辞或规则。

## 踩坑点

- **Token 膨胀**：如果 SOUL.md 内容冗长，每次对话都携带完整人格描述会浪费上下文窗口。解决方法：将静态部分做成摘要（如“你是一位审慎的代码审查者，详见你的 SOUL”），将具体规则放在边界守卫中，不占用模型注意力。
- **模型忽略规则**：小型模型或幻觉严重的模型可能无视“只能读某某文件”的限制。此时必须依赖工具层的硬拦截，而不能只靠 Prompt。
- **修改不生效**：开发时改了 `SOUL.md`，但 Agent 长期运行未重启。建议增加文件监控，检测到变更后自动重载系统消息和工具过滤器（注意并发安全）。
- **边界太死板**：一次把太多工具列入 `forbidden_tools`，导致无法完成合理任务。应该渐进式收紧，每次只加一条，观察 Agent 表现。
- **协作冲突**：不同开发者用不同本地 `SOUL.md` 测试，结果不一致。应将 `SOUL.md` 提交到仓库，并规定环境变量覆盖优先级。

## 可复用建议

1. **模板化**：为常见角色（代码助手、数据分析、客服代理）提供 `SOUL.md` 模板，放在项目脚手架里。
2. **模块拆分**：当规则变复杂，可以拆成 `soul.personality.md` 和 `soul.boundary.yaml`，各司其职。
3. **CI 校验**：在持续集成中增加 `soul-lint` 检查，确保必填字段（如 `allowed_tools`、`version`）存在，格式合规。
4. **审计日志**：一旦边界守卫拦截操作，记录时间、触发条件、请求工具，方便发现异常使用模式。
5. **版本标记**：每次改动人设或边界，递增 `version` 并在提交信息中说明理由，便于回溯“为什么 Agent 突然变严格了”。

## 总结

`SOUL.md` 做的不只是把 Prompt 移到文件里，而是把 Agent 的人格与边界上升到“可配置、可测试、可审计”的工程级别。它像一份活文档，连接着产品意图、安全策略和模型行为。对于 OpenClaw 生态中的插件和 Agent 实践者来说，这或许是一个低成本、高收益的治理手段。

下次你准备给 Agent 加一条“别这么做”的规则时，不妨反问自己：这条规则该放在代码的 if 里，还是 `SOUL.md` 的约束里？答案往往都是后者。
