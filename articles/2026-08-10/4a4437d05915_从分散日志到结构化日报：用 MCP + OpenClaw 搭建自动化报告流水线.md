## 背景

团队的日报流程常年处在“上午补报告、下午翻日志”的状态。多个系统的原始日志散落在 Elasticsearch、ClickHouse、Loki 和本地文件中，格式不一，每次手动组装日报都要反复切换工具、复制粘贴、调整措辞。更难受的是，一旦某个系统变更了日志字段，报告里的数字就悄悄走样，直到被追问才暴露。

我们需要一条可长期运行的流水线，把原始日志自动转化为结构化的日报，输出到飞书或邮件，同时保证内容可审计、可回溯。

## 问题拆解

组装一份日报，本质是完成三个步骤：

1. 从多个数据源拉取指定时间窗口的原始日志或聚合数据。
2. 按业务领域提取关键指标、异常事件、趋势变化。
3. 用统一的 Markdown 模板生成报告并推送。

人工操作的问题在于步骤 1 的上下文切换成本高，步骤 2 容易遗漏或误判，步骤 3 则是重复的体力劳动。所以设计自动化流水线时，重点要解决的是**数据接入的统一性**和**指标提取的可靠性**，而不是单纯让大模型“写一份报告”。

## 方案设计：基于 MCP + OpenClaw 的日报 Agent

我们选择 OpenClaw 作为任务编排 Agent，MCP（Model Context Protocol）负责统一数据源接口。整体架构如下：

- **MCP Servers**：分别对接 Elasticsearch、数据库、本地日志目录，暴露标准化查询能力。
- **OpenClaw Agent**：定义日报生成的工具链与 system prompt，按模板调度工具、分析结果、填充报告。
- **调度层**：cron job 每日触发，执行 Agent 运行，输出 Markdown 并推送到飞书 Webhook。

### 步骤 1：用 MCP 封装日志查询

社区已有不少现成的 MCP Server 实现，比如 `elasticsearch-mcp-server`、`clickhouse-mcp-server`。关键点是 **把时间窗口、索引名、查询条件参数化**，避免硬编码。

以 Elasticsearch 为例，封装三个工具：

- `search_errors(start, end)`：返回 5xx/4xx 错误数以及 Top 10 错误信息。
- `search_slow_queries(start, end, threshold_ms)`：返回慢查询列表及耗时。
- `get_service_health(start, end)`：按服务名聚合请求量、P99 延迟、可用性。

工具返回的应是**预聚合的 JSON 结构**，而不是原始日志行。这个设计至关重要——后文的踩坑记录会说明原因。

### 步骤 2：定义日报模板与 Agent 行为

日报模板固定为三部分：概览（关键指标）、异常事件、变化说明。System prompt 中明确 Agent 的职责：

- 调用工具获取数据，**不做任何统计计算**，仅对照模板整理事实。
- 比较今日与昨日数据时，必须通过工具获取昨日快照，不得凭记忆推断。
- 若某个工具调用失败，需在报告中明确标注“未能获取”，不允许臆测补全。

Toolchain 配置里，把上述 MCP 工具注册到 Agent，并指定每个工具的超时与重试策略。为了让报告语气稳定，我们在 prompt 里给出固定句式，例如：“今日错误数 {N}，较昨日 {变化描述}，主要来自服务 {S}。”

### 步骤 3：Agent 执行与报告产出

执行流程如下：

1. Agent 计算起止时间（通常为昨天 00:00:00 到 23:59:59，时区规范使用 UTC+8）。
2. 并行调用三个工具获取数据，同时拉取昨日缓存数据（一份 JSON 快照文件，由上一次运行写入）。
3. 将获取的 JSON 数据注入 prompt，让 LLM 按模板组装报告 Markdown。
4. 将生成的 Markdown 通过 `send_feishu_message` 工具推送，同时把今日数据写入缓存供明日对比。

我们通过 OpenClaw 的 `agent.run()` 方法触发整条链路，cron 脚本只需一行命令。报告发出后，也会把原始 JSON 和最终 Markdown 存入对象存储，用于事后核验。

## 踩坑记录

### 1. 别让大模型做“算数”
第一个版本直接把 100 条原始日志塞给 LLM，要求它统计错误数、计算平均耗时。结果经常出现幻觉：数字对不上、时间顺序错乱、凭空杜撰服务名。补救办法就是**所有聚合都在 MCP 工具内部完成**，LLM 只负责解读和排版。工具返回的就是结构化指标，不再包含原始日志正文。

### 2. 长日志截断导致关键信息丢失
即使返回聚合结果，当 Top 10 错误信息中包含完整堆栈时，token 消耗很容易超出限制。我们改为：工具只返回首条错误消息的前 200 字符，并附带一个 `detail_link`（Grafana 或 Kibana 链接）供深入查看。日报内遇到截断的内容会标记“已截断，详情见链接”。

### 3. 时间边界与时区混淆
日志时间戳多为 UTC，但业务按北京时间划分“天”。如果工具查询的时间窗口写死 UTC，就会出现跨天偏差。统一做法：Agent 在组装查询参数时，显式使用 `Asia/Shanghai` 时区计算起止，并将时间转换为日志源的时区（Elasticsearch 中通过 `time_zone` 参数处理）。

### 4. 依赖缓存的文件竞争
如果两次 cron 执行间隔过短（比如手动重跑），可能同时读写缓存文件导致数据损坏。我们简单加了一个文件锁，使用 `flock` 保证同一时间只有一个 Agent 实例在操作缓存。

## 可复用建议

- **日志格式标准化先行**：无论后面用多少自动化手段，如果日志不是 JSON lines 且缺少关键字段（如 `service`、`level`、`message`、`timestamp`），日报质量无从保证。投时间统一日志格式比写复杂解析逻辑收益更高。
- **预聚合，再交给 LLM**：让 MCP 工具完成数学统计、排序、去重，LLM 只做事实陈述和模板填充。这能极大降低幻觉风险，也节省 token 开销。
- **保留中间产物**：存储每次运行的工具返回数据和最终报告，便于调试不可复现的“为什么那天报告写错了”的问题。
- **增量对比用快照**：日报中的“变化”项不要依赖 LLM 的记忆，应通过对比今日快照与昨日快照实现，逻辑放在工具或脚本层完成。
- **工具超时与降级**：任何一个数据源超时或报错，Agent 应继续生成报告，但把该部分标记为未获取，避免整个日报中断。

## 总结

自动化日报的难点不在于“让 AI 写报告”，而在于把**不可靠的日志变成可靠的结构化输入**。MCP 帮助我们统一了数据接入的协议，OpenClaw 提供的 Agent 模式则让工具调度和模板组织变得可维护。实际落地时，把聚合逻辑从 LLM 剥离到工具层、严格控制 token 消耗、做好时间对齐与缓存管理，才能让这条流水线从“能跑”变成“敢用”。

一个月跑下来，人工介入的次数从每天 30 分钟降到偶尔抽查，日报的准确性和一致性有明显提升。最关键的是，当某个数据源变更时，只需调整对应的 MCP 工具实现，Agent 侧完全无感，维护成本很低。
