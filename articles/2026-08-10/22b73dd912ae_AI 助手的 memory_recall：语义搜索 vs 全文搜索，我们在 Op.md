## 1. 背景：Agent 的记忆召回到底在选什么

在与 OpenClaw Agent 长期交互、执行自动化任务时，**会话上下文与历史行为的持久化**几乎是所有能力扩展的前提。无论你是写 MCP 工具、做自动化脚本编排，还是给 Agent 搭长期记忆插件，都会遇到同一个问题：当一段历史对话、工具调用日志或文档摘要被存下来后，怎么在需要的时候**精准又经济地**把它们找回来？

这个操作通常被封装成 `memory_recall` 或类似的函数。社区最常见的两种实现思路：

- **语义搜索**：对记忆文本做 embedding，存进向量数据库，召回时用余弦相似度取 top-K。
- **全文搜索**：基于倒排索引、BM25 等关键词匹配能力，按字面命中度排序。

看起来语义搜索是“现代”方案，全文搜索是“上一代”。但我们在 OpenClaw 的记忆服务里把两种方法跑过一轮真实使用后发现，**工程上根本没有哪个能通吃**，选错方向带来的噪音比“没召回”还要致命。

## 2. 真正的问题：怎么定义“好”的召回

问题源于两个典型场景的冲突。

**场景 A：故障分析助手的工具调用记忆**

Agent 记录了一条日志：“2025-03-17 21:02 deploy_app failed, exit code 137, job_id=xxxx-xxxx”。当用户提问“上次部署失败的错误码是什么？”时，语义搜索很可能把“deploy_failed”和“部署不成功”这种相似句排在前面，而准确包含“exit code 137”的原始日志因为 vector 距离不够近，被挤到第三页。**这时需要的是精确的 token 命中，而不是模糊的语义近似。**

**场景 B：用户与 Agent 的开放式对话记忆**

用户曾提到“最近感觉接口延迟明显上升”，Agent 后续需要回忆起这个“关于性能下降的观测”。如果只用全文检索，很可能因为“延迟”、“上升”被当成普通词，而完全漏掉；语义搜索却能捕捉到“延迟上升→性能问题”的隐含关系。

很明显，单一检索策略在这两类需求面前会顾此失彼。而实际记忆数据往往**混合了结构化日志、自然语言对话、代码片段和唯一标识符**，这就要求我们重新思考 `memory_recall` 的实现。

## 3. 做法：混合召回 + 动态加权 + 重排序

我们并没有选择一上来就上最重的模型，而是沿着**索引分层 → 合并 → 重排**的路径落地，兼顾成本和效果。

### 3.1 记忆入库：双索引，同文档

每条记忆（chunk）在落库时同时建立两套索引：

- **全文索引**：使用 Elasticsearch 或内存级的 mini-lm 倒排，保留原始分词和 BM25 打分。
- **向量索引**：用 bge-small-zh 或 all-MiniLM-L6-v2 生成 384 维 embedding，存入 FAISS / Qdrant。

关键点是 **chunk 切分规则完全一致**，避免后续去重时的语义漂移。

### 3.2 召回阶段：分别取 Top-K 并去重合并

查询的时候：

1. 对用户 query 做 embedding，从向量索引召回 K1 条（例如 15 条）。
2. 对同样的 query 做分词送入全文索引，召回 K2 条（例如 15 条）。
3. 将两路召回的结果按 memory_id 去重，合并成候选集（通常 20-30 条）。

这一步在我们的 MCP 实现中只用不到 200 行代码，性能基本取决于索引 latency。

### 3.3 重排序与动态权重

去重后的候选集送入一个轻量级重排序模型（如 bge-reranker-base），计算相关性分数。重排后分值作为最终排序依据。

更关键的一步——**为不同任务动态调整初筛权重**：

- 如果 Agent 当前上下文包含 `error code`、`job_id`、`uuid` 等模式，我们对全文索引的候选提升 1.5 倍原始 BM25 分数后再送入重排。
- 如果上下文是“总结一下之前我们聊的目标”、“回顾上次讨论”，则语义召回的分数权重略高。

这个策略通过解析 query 的简单规则或一个极小的分类器即可实现，引入的额外开销几乎为零。

### 3.4 接入 OpenClaw 的记忆服务

我们把上述逻辑封装成了一个 MCP memory server，暴露 `search_memory` 工具，内部根据 `search_mode` 参数允许调用方主动要求 `hybrid`、`semantic` 或 `fulltext`，方便在特定插件里强行覆盖默认策略。

## 4. 踩坑小结：这些事文档不会告诉你

1. **短文本的语义搜索近乎残疾**  
   日志行或错误码（比如 `ERR_CONN_REFUSED`）embedding 后几乎聚成一团，相似度差异极小，很容易把不相关的高分条目混进来。解决办法是把短记忆拼接固定长度的上下文前缀再入库，或者对长度 < 20 字符的 chunk 强制走全文索引为主。

2. **向量索引的“过相似”噪声**  
   如果记忆库中有大量同质化内容（如重复的部署成功日志），向量相似度会全部接近 0.95，重排也难以挽救。必须结合时间戳、记忆类型等做预过滤，不要把召回全交给模型。

3. **混合去重的坑**  
   不同搜索路径返回的 chunk 可能因为索引时的微小差异而产生几乎相同但 memory_id 不同的条目，导致结果近乎重复。要求切分算法全局唯一，并在合并时用文本哈希去重，不是只比较 ID。

4. **reranker 延迟和成本**  
   即使 reranker 是轻量模型，在候选集达到 50 条以上并且并发调用时，P99 延迟会明显上升。我们最终锁死重排序候选数 ≤ 30，超出部分用分数截断。

## 5. 可复用建议

- **优先评估记忆内容的“精确度需求”**：如果记忆里超过 60% 是结构化字段、编码或固定指令，全文检索权重必须给足。
- **不要丢弃 BM25**：在很多 Agent 场景里，它的稳定性和可解释性远高于向量得分。
- **短期记忆和长期记忆分层**：短期对话记忆可用纯语义，长期审计日志型记忆建议全文为主。
- **监控召回 hit rate**：在 memory 服务里埋点记录每种模式下的命中率，方便事后回溯调权。

## 6. 总结

`memory_recall` 不是一道单选题。语义搜索在理解意图上不可替代，全文搜索在精确定位实体和 token 时依然是性价比最高的选择。在 OpenClaw 这种既要处理操作日志、又要理解自然语言指令的工程实践中，**轻量混合召回 + 动态加权 + 重排序**是一条被验证可走通的路。把复杂留给索引和合并逻辑，把简洁留给 Agent 的调用接口，才是长期维护友好的做法。
