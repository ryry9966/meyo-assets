## 背景

在 OpenClaw 生态里用 MCP 给 Agent 接上数据库、文件系统、HTTP 接口之后，我们面对的不再是“能不能调通”，而是“该不该让它自己干”。一旦 Agent 能写文件、发邮件、删资源，没有权限边界就等于裸奔。但一刀切地所有操作都弹窗问人，又会把自动化打进冷宫。怎么划这条线，就成了工程上绕不开的问题。

## 问题：为什么简单的“是/否”不够用

最常见的做法是每个 Tool 加一个 `requires_approval` 布尔值。上线第一周勉强能用，第二周就开始失控：

- 信息型操作（读文件列表、查状态）被打断，效率极低。
- 破坏性操作（删库、改线上配置）可能被 Agent 在“高置信度”下自动执行——而 LLM 的置信度报告并不可靠。
- 交互式任务中多次触发审批，上下文断裂后用户忘了“之前批了什么”，反而增加了误批风险。
- 工具组合绕过限制：Agent 无法直接 `rm -rf`，却可能通过脚本解释器调用同样效果的操作。

所以需要一套工程化的分级决策，而不是简单的二元开关。

## 做法：分级决策与可编程审批

我们在基于 OpenClaw 的 Agent 中实现了一个 **权限决策中间件**，放在 MCP 客户端与工具调用之间，结构如下：

![cover]

整个决策链分成四个阶段：

### 1. 动作分级
为每个 MCP Tool 定义影响标签，而不是只标“危险/安全”。我们用了三类：
- `read-only`：无状态变更，自动放行。
- `local-edit`：本地资源变更（工作区文件、容器内状态），允许在一定条件下自动执行。
- `external-effect`：会触发第三方 API 调用、发送消息、修改远程数据库等，默认必须审批。

分级配置放在工具注册的 metadata 里，OpenClaw 的 Tool 声明本身就支持自定义属性。

### 2. 参数级风险评分
标签只决定门槛，参数决定实际风险强度。例如 `write_file` 属于 `local-edit`，但如果路径是 `/etc/systemd` 且内容是 unit 文件，风险就跃升。我们让 Agent 在工具调用决策前，输出一个结构化的 `risk_estimate`，包含：
- `impact_scope`：影响范围（session / workspace / host / remote）
- `reversibility`：是否可逆
- `data_sensitivity`：是否涉及密钥、用户数据

这个评分 **不用 Agent 的一句话总结**，而是要求它填充固定 JSON 字段，这样能较大程度上减少幻觉。

### 3. 动态策略匹配
代码里维护一个策略结构：

```yaml
policies:
  - id: low-risk-auto
    condition: impact_scope == "workspace" AND reversibility == true
    action: auto_approve
  - id: sensitive-data-ask
    condition: data_sensitivity >= 3
    action: require_approval
  - id: default-deny
    condition: action_type == "external-effect"
    action: require_approval
```

当工具调用请求携带分级标签和风险评分后，策略引擎按优先级匹配，找到第一个命中的规则决定是 `auto_approve`、`require_approval` 还是 `block`。策略本身存储在可热加载的配置中，方便运维调整，不需要重启 Agent。

### 4. 审批交互闭环
到了必须问人的那一步，我们利用 OpenClaw 的 **Human-in-the-loop 挂载点**。审批卡片会展示：
- 工具名与参数
- 预估影响范围与风险评估
- 可选的“记住本次任务内同样类型操作”选项（减少重复打断）

用户批准后，中间件注入一个临时 token，授权本次调用及后续同策略操作，任务链结束后 token 失效。这样就避免了“批一个命令，后续都能飞”的权限放大问题。

## 踩坑点

**坑1：风险评分仍会“客气”**
即使要求结构化输出，LLM 对风险有时过于保守或过于乐观。我们遇到 Agent 把 `rm -rf /tmp/cache` 标为 `impact_scope=session`，但实际 `/tmp/cache` 同时被其他服务使用。**解法**：评分只作为参考，最终裁决必经过文件路径白名单或守护进程的二次确认。不要让 LLM 的评分成为唯一依据。

**坑2：审批回调中的上下文丢失**
Agent 在等待审批时，对话上下文可能被压缩，回来后搞不清楚“刚才干嘛”。**解法**：在 approval 挂起时，把当前任务摘要、待执行工具快照持久化到 session store，恢复时重新注入为 system prompt，保证 agent 能续接。

**坑3：高频只读操作被拉跨**
初期我们把 `read_only` 全部自动放行，但遇到一个抓取 API 数据的工具，它虽然是只读，但每次调用扣第三方配额。**解法**：给工具的 metadata 增加 `cost_profile`，如果带配额消耗或性能影响，即使只读也提升到需要审批或限频。

## 可复用建议

- **最小权限 + 临时授权**：每次只给 Agent 本次任务必要的最小工具集，配合短期 token，不要给长期凭证。
- **可逆性优先**：优先提供能够回滚的操作（如版本化写文件、数据库事务），让自动执行有退路。
- **决策日志与审计**：把每次工具调用的分级、评分、策略命中、审批结果写入结构化日志，定期复查误干预与漏网操作，持续调整阈值。
- **白名单快车道**：对已验证的安全路径、命令模板，允许用户建立“本项目中不再询问”的规则，让 Agent 在安全半径内真正自动驾驶。
- **环境感知**：测试环境和生产环境自动切换策略，staging 可以大幅放权，production 收紧到必须审批。

## 总结

AI Agent 的权限边界，不是一个“信任还是不信任”的哲学问题，而是一套可量化、可配置、可回滚的工程机制。我们不必替 Agent 决定一切，也不必让它决定一切，而是建一个能随风险自适应收紧或放松的“动态篱笆”。在 OpenClaw 的 MCP 生态里，工具描述、风险评分、策略引擎和 Human-in-the-loop 钩子已经提供了所有拼图，差的就是那份愿意把边界打磨到可编程的耐心。
