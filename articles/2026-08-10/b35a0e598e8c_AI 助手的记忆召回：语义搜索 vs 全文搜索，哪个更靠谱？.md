## 背景

很多人在给 AI 助手（尤其是在 OpenClaw 这类支持长期记忆的 Agent 框架里）做 memory recall 时，会碰到一个很基础但容易踩坑的选择：到底用语义搜索（向量检索），还是全文搜索（关键词匹配）？网上多数讨论偏向“语义搜索更智能”，但真实的工程环境里，一个选错，召回率和准确率双双拉胯。本文基于我们在 OpenClaw 插件和 MCP 记忆模块上的实际调试经验，把两种方式的优劣、混合使用的落地细节，以及常见的踩坑点整理出来。

## 问题场景

假设我们有一个长期运行的 AI 助手，需要根据用户的当前提问，从历史记忆库中召回相关的对话片段、任务记录、偏好信息。典型需求：

- 用户说“上次那个分析报告再跑一遍”，助手需要找到具体“哪个报告”。
- 用户说“帮我把上次的 PPT 改成蓝色主题”，需要找到那条提及 PPT 的记忆。
- 多轮任务型对话中，需要把任务进度、工具调用结果存下来，下次恢复上下文。

记忆存储一般用 JSON/结构化文档，每条记忆包含时间戳、内容摘要、原始对话、标签等。召回时，把用户当前 query 与记忆库做匹配，选出 Top-K。

这个场景下，我们分别试了纯语义搜索和纯全文搜索，结论是：各有一堆坑，最后用混合策略才稳住。

## 语义搜索：不是银弹

语义搜索基于 embedding 向量相似度，能够理解“语义相近但用词不同”的内容。比如“分析报告”可以匹配“周度营收分析”这种记忆。

我们在 OpenClaw 的一个记忆插件里，使用本地 `sentence-transformers` 模型（all-MiniLM-L6-v2）生成 embedding，再用 Chroma 做向量存储。初期效果看起来不错，但很快暴露几个问题：

**1. 实体/专有名词模糊匹配失败**  
用户问“把 BG-2025-Q1 那个表格发我”，语义模型会把 BG-2025-Q1 当作一个整体向量化，但库里有记忆“BG2025Q1 表格已生成”，由于连字符和大小写差异，embedding 距离并不近，导致召不回。这种精确字符串匹配，语义模型不擅长。

**2. 短查询召回漂移**  
用户只输入“那个报告”，语义向量在空间中与大量记忆都有中等相似度，却未必与真实目标最匹配。Top-K 很容易被其他高频词污染。比如记忆库里有很多“报告生成失败”“报告格式调整”，一个“报告” query 可以匹配一堆，但真正想要的是“Q4 营收分析报告已完成”。

**3. 多语言混合时语义空间坍缩**  
很多用户的中文对话夹杂英文术语（API, token, buffer），通用嵌入模型在中英混合短句上表现不稳定，召回结果经常混杂一两种语言的不相关内容。

**4. 时间衰减失效**  
纯语义搜索不考虑记忆的时间新鲜度，只按向量距离排序。如果历史记忆里有同类任务多次出现，很容易把旧内容排到前面，但这往往不是用户想要的“上次的”。

## 全文搜索：太硬，但管用

我们对比尝试了 SQLite FTS5 做全文索引，把每条记忆的文本内容、标签、结构化字段（如标题、文件名）都建了倒排索引。查询时用 `MATCH` 语法，按 rank 排序。好处很明显：

- 实体精确匹配 100% 命中。BG-2025-Q1 作为独立 token 被索引，带不带连字符都能用分词策略兜底。
- 逻辑明确，调试可解释。谁排在前面一目了然。
- 配合 BM25 算法，短查询不容易完全跑偏，只要有 token 匹配，就能召回。

但缺点同样突出：

- 同义词和表述差异完全无法覆盖。比如“营收分析报告”检索不到“收入分析表”。
- 依赖分词质量，中文分词如果用 jieba，专有组合词常被切开，导致漏召回。
- 无法理解句子结构，“帮我把 PPT 改蓝色”和“蓝色 PPT 已经改好”可能因为词序和短语句法不同，得分差异很大。

## 混合策略：工程化落地做法

最终我们采用了“语义召回 + 全文过滤/重排序 + 时间衰减”的三段式流水线，整个 pipeline 在 OpenClaw 的 memory recall 工具里实现。

### 步骤

1. **粗召回（语义）**  
   用向量相似度从向量库取 Top-N（我们设 20）。这个阶段保证语义覆盖面，不要求精确。

2. **精过滤（全文）**  
   对候选集进行 FTS5 关键字匹配，提取关键实体和结构化字段（日期、文件名、任务 ID）。如果 query 含明显的实体关键词（如编号、URL、文件后缀），则大幅加权这些匹配项。

3. **融合重排**  
   综合三个分数：
   - 语义相似度得分 (normalized 0~1)
   - 全文匹配得分 (BM25 归一化)
   - 时间新鲜度衰减因子
   
   加权公式：`final = α * semantic_score + β * FTS_score + γ * time_decay`  
   我们最终取 α=0.5, β=0.3, γ=0.2，且 β 在实体命中时动态调高至 0.6。

4. **再排序 & 截断**  
   取 top-5 返回给 LLM，作为 memory 上下文。

### 可复用的代码梗概

（在 OpenClaw 的 memory action 中实现，Python）

```python
def hybrid_recall(query, memory_store, vector_index, fts_index, top_k=5):
    # 1. 向量粗召回
    vec_results = vector_index.search(query, top_n=20)
    # 2. 提取实体关键词
    keywords = extract_entities(query)  # 简单的正则+词典
    # 3. 全文打分
    fts_scores = fts_index.match(query, candidates=vec_results)
    # 4. 时间衰减
    timestamps = [mem['ts'] for mem in vec_results]
    decay = compute_time_decay(timestamps)
    # 5. 融合
    final_scores = (
        0.5 * normalize(vec_results['scores'])
        + 0.3 * normalize(fts_scores)
        + 0.2 * decay
    )
    return rerank(vec_results, final_scores)[:top_k]
```

## 踩坑点

- **关键词提取不要太重**。我们一开始用 NER 模型提取实体，延迟太高（本地推理 >100ms），后来改用规则+缓存高频词表，延迟降到 5ms 以内。
- **时间衰减不能线性**。如果用户刚刚创建的记忆权重过高，会把语义关联强但稍旧的结果挤掉。我们用了指数衰减 `exp(-λ * Δt)`，λ 可调。
- **混合排序容易出现边界不稳定**。当语义分和全文分都很低时，时间因子可能把完全不相关的记忆推到前面。我们给总分设了下限阈值，低于 0.2 直接丢弃。
- **存储开销**。需要同时维护向量 DB 和 FTS 索引，但索引可以基于同一个 SQLite 数据库，Chroma 也可用内部 SQLite 存储，整体可接受。

## 可复用建议

1. **如果不涉及多语义/跨语言，单一全文搜索就够用**。很多内部工具型 Agent 的任务记忆都是模板化的，关键词匹配效率高且可控。
2. **语义搜索一定要搭配精确过滤**。别指望 embedding 解决所有问题，至少在实体级要加保护。
3. **保留原始记忆的元数据**（创建时间、类型、关联任务 ID），它们对重排序至关重要。
4. **在 OpenClaw 中，把 recall 作为一个独立 Tool 或 MCP server，方便调试和替换**。不要硬编码在主逻辑里，这样混用策略可以随时调整。

## 总结

语义搜索和全文搜索在 memory recall 里，不是谁替代谁，而是互补。语义负责“理解意图”，全文负责“抓住实体”，时间因子负责“别翻旧账”。三者结合，才能让 AI 助手准确回忆起“上次那个”到底是什么。在实际的 OpenClaw 插件开发中，我们最终选择了混合路线，并在不同记忆量级（1k~50k 条）下验证了稳定性和延迟。希望这个思路能给同样在折腾 Agent 记忆的同学一点参考。
