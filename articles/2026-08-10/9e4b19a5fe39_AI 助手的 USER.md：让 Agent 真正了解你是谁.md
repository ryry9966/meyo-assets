你有多少次在和 AI 编程助手对话时，先花三分钟解释自己的技术栈、项目结构和代码习惯？又有多少次因为 Agent 忘记你用的究竟是 pnpm 还是 yarn，而生成了一堆错误的依赖安装命令？

问题的本质很清楚：**Agent 缺乏关于“你”的持久上下文**。每次对话都像第一次合作，你不得不重复那些早就该被记住的信息。OpenClaw、Claude Code、Cursor 或者基于 MCP 自定义的 Agent 工作流，都绕不开这个短板。

一个轻量但极其有效的解法是——**给 Agent 一份 USER.md**。

## 1. 背景：Agent 的“失忆症”

现在的 AI Agent 已经能理解代码、调用工具、执行计划，但它们对长期个性化信息的记忆依然依赖外部系统。无论是通过 system prompt 注入，还是借助 MCP server 动态提供上下文，能让 Agent 持续了解“当前在和谁协作”的能力，会直接决定输出的贴合度。

所谓 USER.md，就是一份存放关于你——而非项目——的结构化 Markdown 文档。它可以告诉 Agent：

- 你的常用技术栈与版本偏好  
- 操作系统、Shell、编辑器及快捷键习惯  
- 个人代码风格规则（命名、注释、测试框架）  
- 当前正在处理的项目、关键目录结构与痛点  
- 你默认想要避免的做法或已知的坑

用工程的思维看，这相当于把 onboarding 一个新同事时你需要交代的内容，写成了 Agent 能随时查阅的单一事实来源。

## 2. 实践：创建并注入 USER.md

### 2.1 内容选择与结构化

一份能持续维护的 USER.md，首先要做到**信息密度高但篇幅克制**。建议用清晰的标题分层，例如：

```markdown
# 关于我
- 角色：全栈 / 后端偏重
- 主力语言：TypeScript, Python
- 常用框架：Next.js, FastAPI

# 环境与工具
- OS: macOS (zsh) / 远端 Linux (bash)
- 编辑器：VS Code，偏好 Vim 键位
- 包管理：pnpm (前端), uv (Python)

# 项目上下文
- 当前项目：OpenClaw 插件市场重构
- 目录约定：`src/` 下按功能分包，`test/` 平行放置
- 测试框架：Vitest + Testing Library

# 代码偏好
- 优先使用 async/await，避免裸 Promise
- 组件文件使用 `kebab-case.tsx` 命名
- 接口定义集中在 `types/`，不分散在各文件头部

# 反模式 / 永远不要做的事
- 不要在没有显式告知的情况下修改 `package-lock.json`
- 不要引入超过 50kB 的新依赖（除非明确要求）
```

把内容控制在 150-300 行以内，避免 token 浪费。过于琐碎的习惯反而会干扰模型输出。

### 2.2 注入方式

不同的 Agent 框架对接方式不同，核心原则是让 USER.md 在对话开始时就进入上下文。常见做法：

- **System Prompt 注入**：在 OpenClaw 或自建 Agent 中，将 USER.md 的内容拼接到 system prompt 的底部。例如：  
  ```
  ## User Profile
  [这里是 USER.md 内容]
  ```
- **MCP 资源提供**：写一个简单的 MCP server，暴露 `user-profile://default` 资源，Agent 按需调用 `read_resource` 获取最新的 USER.md。这能实现动态更新而无需重启进程。
- **项目级约定文件**：在项目根目录放置 `.agent/user.md`，由 Agent 的启动脚本在每次会话时读取并注入。配合 `.gitignore` 避免将个人信息提交到团队仓库。

对于需要频繁切换项目的人，建议使用符号链接或脚本动态生成 USER.md，根据当前工作目录自动引用不同的配置文件。

## 3. 踩坑与反思

在实际使用中，有几个常见问题值得注意：

**信息过载**  
第一次写 USER.md 容易变成“个人百科”，什么都往里面塞。Agent 的上下文窗口有限，当 user profile 超过 2000 token 时，不仅成本上升，还会稀释真正重要的指令。定期清理，像维护 CI 配置一样对待它。

**隐私泄露**  
USER.md 里很容易出现本地绝对路径、内网地址或个人邮箱。如果将它注入到云端 Agent（比如企业版 Copilot），要确保内容经过审查，或者只在本地运行的 Agent 中使用完整版。另一个办法是分层：维护一份“安全版”用于云端，一份完整版仅用于本地。

**与项目规格的冲突**  
项目可能有自己的 `.cursorrules` 或 `README_AGENT.md`。如果同时存在 USER.md 与项目级规范，要明确优先级。通常做法是：项目规范优先于个人偏好，除非标注“个人习惯仅供参考”。

**格式兼容**  
某些工具链的 prompt 渲染会吞掉 Markdown 的部分结构。建议避免使用复杂的嵌套列表或代码块中的语法高亮，保持纯文本可读性。表格在 system prompt 中也可能被破坏，可用列表替代。

## 4. 可复用建议

- **模板工程化**：创建一个 `~/.config/agent/user-base.md` 作为模板，新建项目时复制并填写项目特定的上下文部分。  
- **动态上下文**：可以通过 MCP 拉取 GitHub 个人主页、LinkedIn、dotfiles 仓库的 README 来自动生成部分内容，减少手动维护成本。  
- **版本控制**：保留 USER.md 的历史版本，可以在换工具或新 Agent 上线时，快速适配。  
- **检查清单**：在 Agent 生成代码后，对照 USER.md 里的反模式清单快速 review，将其内化为一部分的自动化 lint 习惯。

## 5. 总结

给 Agent 写一份 USER.md，本质上是在教它成为你的“长期合作者”而非“一次性工具”。这项投资不大，却能在后续几十、上百次对话中持续回收效率——每次少解释一句环境配置，少纠正一次代码风格，累积起来都是实打实的工程收益。

文件不长，把它当作你的 Agent onboarding document。写了，你的 Agent 才真的认识你。
