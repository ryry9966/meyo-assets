## 背景

团队在日常开发中重复最多的操作，往往不是写业务逻辑，而是 Git。每次提交都要组织 commit message，每次新建分支都要思考命名规则，合并前还得回顾本次改了什么、影响面在哪里。这些机械但需要自解释力的工作，恰好是语言模型擅长的。

在 OpenClaw 生态里，我们已经有能力通过 Agent、MCP 工具链和自动化流程，把 Git 的常规操作交给 AI 处理，同时保留人工审核的最终把控。这篇文章记录一次真实落地过程：如何让 AI 助手根据暂存区 diff 生成符合 conventional commit 的信息，并自动创建规范分支，以及过程中踩过的坑。

## 问题

手工写 commit message 有两个极端：要么过于随意，如 `fix bug`、`update`，追溯时毫无上下文；要么花费过多精力咬文嚼字，打断心流。分支命名同样如此，`feature/xxx`、`fix/yyy` 看似统一，但不同开发者对同一功能的理解不同，分支名容易偏离规范。更麻烦的是，开 Pull Request 时需要整理的描述、变更摘要，往往靠人眼重新扫描 diff，效率低且容易遗漏关键变更。

理想的工程状态是：在完成一个逻辑单元修改后，人只需要执行类似 `ai-commit` 的命令（或让 Agent 自动感知暂存区变化），AI 读取 diff 后生成标准提交信息、创建对应类型分支，并在推送后自动生成 PR 描述草稿。人仅需确认或微调。

## 做法

### 1. 工具基础：MCP Git 插件

OpenClaw 的 MCP 协议可以连接外部工具，包括 Git 操作。我们使用一个通用的 Git MCP server（可自行实现或选用社区实现），暴露 `git diff --cached`、`git log`、`git branch`、`git commit` 等能力。Agent 通过自然语言或预定义工作流调用这些接口。

### 2. 智能提交生成流程

整个自动提交流程拆解为四个步骤，由 Agent 编排：

1. **读取暂存区变更**：调用 `git diff --cached` 获取当前暂存所有文件 diff，限制单文件超过 500 行时做截断处理，避免 token 爆炸。  
2. **分析变更意图**：将 diff 喂给 LLM，提示词要求按以下结构输出 JSON：  
   - `type`: feat/fix/docs/refactor/test/chore 等  
   - `scope`: 影响模块名（自动从路径推断）  
   - `short`: 50 字符内的简要描述  
   - `body`: 详细说明（可选）  
   - `breaking`: 是否包含破坏性变更  
   - `branch_prefix`: 对应分支前缀（如 `feat/`、`fix/`）  
3. **生成并执行操作**：Agent 根据返回 JSON 拼装 `git commit -m "<type>(<scope>): <short>" -m "<body>"`，若存在 `!breaking` 则在末尾加 `BREAKING CHANGE` 脚注。同时检查当前分支是否已符合命名，若不符则询问是否新建 `{branch_prefix}/{slugified_short}` 分支。  
4. **人工确认**：最终 commit message 生成后，在终端或 OpenClaw 对话框中预览，并等待 y/n 确认。不做静默提交，这是一个重要的安全红线。

### 3. 自动分支创建与 PR 描述

当一个新功能开始但尚未建立分支时，可以设计一条指令：“Start feature：支持用户导出 Excel”。Agent 会调用 LLM 生成分支名 `feat/export-excel`，创建并切换分支，同时生成一个初始的空 commit（仅含 `chore: init feature branch`），方便后续跟踪。  

在 PR 阶段，Agent 拉取 `main..current` 的所有提交信息，结合 `git diff main...` 生成 PR 摘要，模板化地输出背景、变更、影响范围、测试说明，开发者只需在 GitHub 上做最后确认。

## 踩坑点

**1. diff 超出 token 限制**  
大型 PR 一次性 diff 很容易超出模型上下文窗口。解决方案是分而治之：先按文件拆解，汇总时让模型逐个生成文件级摘要，再由第二层模型聚合。或者强制要求开发者分批暂存、多次提交，保持每次变更原子化。我们在提示词中强调“如果你认为 diff 过大，请建议拆分提交”。

**2. 生成 commit 信息不准确或虚泛**  
有时模型会忽略核心逻辑，仅描述表面变更，比如将业务策略调整简单写成 `update logic`。我们通过 few-shot 示例和强调“说明动机而非实现”来缓解，并规定如果 `body` 为空则必须重新生成。即便如此，也不能完全信任，人工预览环节必不可少。

**3. 分支命名冲突与混乱**  
自动分支名基于简要描述生成，可能和已有分支重复，或 slug 化结果太模糊（如 `feat/update`）。我们加入检查逻辑：若分支已存在，追加数字后缀并提醒开发者；同时设定最小分支名长度（至少 3 个有意义单词），否则退回人工命名。

**4. 权限和依赖**  
MCP Git 插件默认在本地用户权限下运行，可以执行任意 Git 命令。这意味着要严格限制其作用域，避免 `push --force` 等危险指令。我们在 Agent 层加了权限配置，只允许明确注册的 safe commands，并禁止强制推送或操作保护分支。

## 可复用建议

- **使用约定式提交但不死板**：允许 AI 在 `type` 边界不清晰时请求用户选择，防止乱分类。  
- **与 git hooks 集成**：可以在 `commit-msg` hook 中调 Agent 做二次校验，拦截不规范信息。但注意不要在 hook 内产生过长时间网络调用，建议异步或缓存。  
- **提供模板分支生命周期管理**：例如 `feat/`、`fix/` 分支合并后自动清理，由 Agent 在每日晨会前生成分支健康报告。  
- **保留回退路径**：自动化不是全自动驾驶。确保每个关键操作都有 `--dry-run` 模式，并且所有生成文案先写入临时文件供人工 review。  
- **抽象成 OpenClaw Skill**：将上述能力封装为可复用的 Skill，供团队成员一键安装，降低配置成本。

## 总结

用 AI 管理 Git 并不是要取代开发者对代码仓库的理解，而是把“翻译 diff → 文字说明”这个费时过程自动化。在一个可控、可审查的框架下，它能显著降低提交规范化的摩擦，并让分支管理更有序。关键设计在于：始终保留人机确认节点，限定操作范围，并通过结构化提示词约束生成质量。如此，Git 自动化才能真正融入工程流，而不是制造新的混乱。

你可以从单个最痛的点开始——比如只自动生成 commit message——逐步扩展到分支、PR 描述，循序渐进。
