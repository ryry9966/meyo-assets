## 背景：AI 助手为什么需要心跳

在构建基于 OpenClaw 的 Agent、MCP 插件或自动化工作流时，我们经常会遇到一个基础但容易被忽略的问题：**如何确认对端仍然“活着”且可用**？无论是长时间运行的 Agent 与服务端之间的连接保活，还是 MCP 客户端与多个 MCP 服务器之间的健康监测，心跳（Heartbeat）都是保证系统可靠性的第一道防线。

心跳机制的设计直接影响资源消耗、实时性、网络适应性和后续的故障恢复策略。在实际工程中，最常见的选择是轮询（Polling）和推送（Push）两种模式。选型不当，轻则增加不必要的网络开销，重则导致连接假死、消息丢失，甚至整个自动化流水线中断。

本文面向有一定工程经验的 OpenClaw 实践者，梳理在 Agent/插件/MCP 架构中心跳设计的取舍、实现要点以及常见的踩坑点，提供可复用的选型建议。

## 问题：轮询与推送的矛盾点

- **轮询（Polling）**：客户端以固定间隔向服务端发送请求（如 HTTP GET `/health` 或 MCP 的 `ping` 请求），通过响应判断对端状态。  
  优点：实现简单，无状态，容易穿透防火墙/NAT。  
  缺点：延迟与资源消耗不可兼得——间隔短则增加服务端压力，间隔长则故障发现延迟大；在大量 Agent 实例同时运行时，可能引发心跳风暴。

- **推送（Push）**：服务端通过长连接或消息通道（WebSocket、Server-Sent Events、HTTP/2 Server Push、MCP Notifications）主动向客户端发送心跳，客户端只需被动接收。  
  优点：实时性高，带宽占用更平滑，适合事件驱动的 Agent 场景。  
  缺点：需要维护长连接，对网络层要求更高（代理超时、NAT 映射老化、负载均衡器空闲断开等）；客户端需处理连接中断重连，并实现心跳超时检测（收不到推送即视为故障）。

更麻烦的是：**在真实生产环境下，几乎不存在单一完美的模式**。例如，防火墙静默 kill 空闲 WebSocket 后，服务端推送的心跳无法到达客户端，而服务端仍认为客户端在线，造成状态不一致。

## 做法：混合心跳架构设计

基于 OpenClaw 的 Agent 场景，我们采用 **“以推送为主，轮询为兜底”** 的混合心跳设计，以下是一个经过验证的工程化步骤。

### 1. 建立双向心跳通道
- 使用 WebSocket（或 MCP 的 Streamable HTTP + SSE）建立长连接，作为主心跳通道。
- 在连接建立时，服务端与客户端约定心跳参数：服务端推送间隔 `push_interval`（如 20s），客户端超时容忍窗口 `missed_max`（如 3 次未收到即判定断连）。

### 2. 推送心跳实现
服务端启动定时任务，每隔 `push_interval` 发送轻量心跳帧（如 `{"type":"heartbeat","ts":1717000000}`）。客户端在 `missed_max * push_interval` 内未收到任何心跳，则主动断开连接并触发重连。

**关键点**：不依赖 TCP keepalive 等底层机制，应用层心跳可控可观测。

### 3. 兜底轮询
对于无法升级长连接的环境（如部分 HTTP-only 的插件沙箱），或以较低代价验证服务端完整性的场景，增加一个低频轮询端点 `/health`。间隔可设为 60~120 秒，仅用于验证服务端业务逻辑是否正常（数据库可达、MCP 工具可调用），而不是普通连接健康。

### 4. 故障处理与重连策略
- 推送检测失败 → 立即触发重连，采用指数退避（初始 1s，上限 30s），避免重连风暴。
- 轮询兜底失败 → 除重连外，还需上报异常事件到 Agent 的监控管道，供上层调度器决策（如任务迁移、告警）。
- 服务端侧：通过记录客户端最后心跳时间，在超时（如 3×push_interval）后主动清理会话，避免僵尸连接堆积。

## 踩坑点

- **NAT/代理超时死亡**：很多云环境或公司网络会在 30~60 秒无数据后关闭空闲连接。推送心跳间隔必须低于该阈值，建议 20~25 秒。测试时用 `conntrack -L` 查看 NAT 状态。
- **“心跳欺骗”失效**：仅依赖推送心跳，一旦推送通道故障而客户端未能及时感知，就会严重耽误恢复。必须配合客户端的主动超时检测，以及兜底轮询进行二次确认。
- **心跳帧与业务帧混淆**：有些实现将业务消息同时当作心跳，一旦某段时间无业务流量，连接就被误判死亡。一定要保持独立的心跳信令，哪怕只是一个空 pong。
- **多实例下的心跳风暴**：当大量 Agent 同时重启，兜底轮询可能对 `/health` 端点造成瞬时压力。可在客户端使用 jitter（随机抖动，±20% 间隔）打散请求高峰期。

## 可复用建议

1. **健康检查分层**：将“连接存活”和“业务可用”解耦。长连接心跳只管连接，轮询 `/health` 或 MCP 的 `tools/list` 唤回用于业务探活。
2. **利用 MCP Notifications**：如果你的插件架构基于 MCP，可考虑使用 MCP 的 `notifications/initialized` 或扩展自定义通知来承载心跳，避免额外端口或协议。
3. **可观测性打点**：在客户端侧记录心跳失败次数、重连延迟；在服务端侧记录心跳超时清理数。这些指标是后续优化间隔参数的唯一依据。
4. **配置可调**：将心跳间隔、超时倍数、重试策略做成 Agent 配置文件的一部分，适应不同部署环境。

## 总结

轮询和推送并非非此即彼的对立方案。在 AI 助手工程化实践中，主推送 + 低频轮询兜底的混合心跳机制，兼顾了实时性和鲁棒性。更重要的是，任何心跳设计都必须实际验证网络中间件的行为，并持续通过可观测数据调优，否则“看上去很美”的协议选择，最终可能会在一个业务低谷的凌晨，变成一条没有告警的生产故障。
