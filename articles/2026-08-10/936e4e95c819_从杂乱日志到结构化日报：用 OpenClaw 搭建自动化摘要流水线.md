## 背景

我们维护的线上服务每天会产生大量运行日志、云监控告警、接口调用统计等原始数据。早期日报靠人工登录不同系统摘取信息，再手动汇总成 Markdown，耗时且遗漏严重。后来引入 OpenClaw 的 Agent 能力，结合 MCP 协议将数据源抽象成工具，构建了一条从原始日志到结构化报告的全自动化流水线。目前这套流程每天凌晨执行，生成报告后直接推送到飞书群，人工只需复核异常项。

## 要解决的问题

看似简单的“收集→汇总→发送”，工程上的难点集中在三点：

1. **数据源异构**：日志在 ElasticSearch，指标在 Prometheus，变更记录在内部 CMDB。Agent 需要跨多个后端查询，且每个后端认证方式不同。
2. **非结构化日志解析**：错误日志往往是半结构化的栈轨迹，直接塞进报告毫无可读性，需要提取关键信息并分类。
3. **可靠性**：凌晨执行时，若某个数据源超时或返回异常，不能整条流水线崩溃，生成的报告要有“降级说明”字段，并通知值班人员。

## 方案与步骤

### 1. 用 MCP 封装数据查询能力

按照 OpenClaw 的 MCP 规范，为每个数据源实现一个轻量的 Tool Server：

- `es-query`：接受索引名、DSL 查询体，返回聚合后的日志摘要。内置时间范围强制对齐凌晨时段，避免 Agent 传入错误时间窗。
- `prometheus-query`：封装 `query_range`，返回关键指标（QPS、P99 延迟、错误率）的最大/最小/平均值，并输出图表链接。
- `cmdb-changes`：返回当天变更记录列表，过滤敏感字段后输出。

每个 Tool 统一返回 JSON，结构包含 `data`、`error_message`、`diagnostic` 字段，方便 Agent 判断数据可用性。

### 2. 设计分阶段的 Agent Prompt

单次对话让 Agent 完成“查数据+分析+写报告”很容易超过 token 窗口或产生幻觉。我们将 Prompt 拆分成三个阶段，由 OpenClaw 的流水线引擎串联：

- **数据收集阶段**：固定系统指令，要求使用上述 MCP 工具并行查询三个数据源，并将返回的 JSON 原样保存在上下文变量中，不做删减。禁止在该阶段生成解释性文字。
- **分析分类阶段**：读取前一阶段的原始 JSON，对错误日志进行模式聚合（相似堆栈合并），提取 Top-N 高频错误、突增指标、与过去三天对比的异常检测。要求输出结构化的“异常清单”和“常规指标摘要”。
- **报告生成阶段**：使用预定义模板，填充分析结果。模板固定为四部分：关键指标一览、异常事件列表、变更记录、自动诊断建议。降级说明在任一数据源不可用时自动插入。

三个阶段各自独立执行，中间通过文件或 KV 存储传递数据，便于单点重跑和调试。

### 3. 构建流水线并接入通知

使用 OpenClaw 的计划任务触发，早晨 7:00 执行。流水线配置中定义了节点之间的依赖和失败处理：

- 若数据收集阶段部分 Tool 返回错误，标记 `partial_data: true`，后续阶段继续执行，但建议部分减少置信度陈述。
- 报告生成后，通过飞书 Webhook 发送 Markdown 消息。同时上传完整的 JSON 过程文件到对象存储，供追溯。

## 踩坑记录

**日志截断与 token 管理**  
早期为了“全面”，Agent 在数据收集阶段直接将 ES 的原始日志全量吐出，导致上下文溢出。后来改为在 Tool 内部做聚合和采样：只返回 topN 错误指纹 + 各错误指纹的一条例样，有效减少 80% 的 token 消耗。记住： Tool 不是原始数据管道，而是摘要计算层。

**Agent 捏造无中生有的建议**  
分析阶段曾出现 Agent 根据错误日志名称臆造“可能的根因”，而这些建议缺少事实依据，误导值班同学。最终要求该阶段**仅输出观测到的事实模式，不做因果推断**，诊断建议改为引用 runbook 链接或直接写“待人工分析”，大幅降低噪声。

**Prometheus 查询卡死**  
凌晨偶发 Prometheus 响应缓慢，导致 Tool 调用超时。单一重试机制不够，后来将所有 Tool 调用都加上 `timeout`（5s）和熔断器，连续失败三次则整个数据源降级，并在报告中增加“数据缺失”标记。Tool 实现时务必处理 Context deadline。

## 可复用的建议

1. **Tool 就是边界**：把数据清洗、聚合、屏蔽敏感信息的逻辑下沉到 MCP Tool 内部，Agent 只做编排和语言转换。每个 Tool 输出“可展示的片段”而不是裸数据。
2. **分阶段必然带来状态管理问题**：用极简的 JSON 中间文件传递上下文，不要跨阶段依赖 Agent 记忆，也不要把多阶段塞进一个超长历史对话。
3. **错误处理要显式化**：任何异常都必须转化为报告里的可读字段（`data_quality: degraded`），否则流水线“看起来成功”才是最危险的。

## 总结

这套自动化日报流水线把原来 40 分钟的人工整理压缩到 2 分钟的全自动执行，而且错误日志的分类比人工更一致。核心不是 Agent 有多智能，而是通过 MCP 封装、分阶段 Prompt 和显式降级设计，把它约束成一个可控的工程组件。如果你的日报场景类似，可以考虑这套“工具做重，Agent 做轻”的模式，稳定远优于炫技。
