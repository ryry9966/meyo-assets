## 背景

团队维护着多个微服务，每天产生的应用日志分散在 Loki、Elasticsearch 和云厂商的日志服务里。过去靠值班同事手动翻看、复制粘贴关键错误和业务指标来拼凑日报，不仅枯燥，还经常漏掉重要异常。我们尝试过定时脚本聚合数值类指标，但对自然语言描述的事件（如“用户登录模块在 03:12—03:22 间超时率突增”）仍然需要人肉提取。

OpenClaw 的 Workflow + Agent 能力，加上 MCP 协议对数据源的统一抽象，让我们有条件在不改造现有日志基础设施的前提下，搭一条自动化日报流水线。这篇帖子记录整个实现过程、踩过的坑和可复用的工程化经验。

## 问题定义

目标：每天早上 8:30，在飞书群内收到一份包含以下内容的结构化日报：

- 过去 24 小时内所有 `ERROR` / `CRITICAL` 级别日志摘要（去重、归类）
- 关键业务事件的异常波动（如支付回调失败次数同比昨天上升 30%）
- 由 LLM 生成的一段 150 字以内的“今日风险提示”自然语言总结

约束条件：
- 不修改现有日志采集管道
- 可以接受 5 分钟以内的端到端延迟
- 日报格式必须稳定，不能因为模型幻觉丢失章节

## 整体流水线设计

我们基于 OpenClaw 的 `Workflow` 串联了 4 个核心节点，并通过 MCP Server 读写外部数据。结构如下：

```
定时触发 (Cron Trigger)
  -> 节点1: 日志拉取 (MCP Client -> 自建日志查询 MCP Server)
  -> 节点2: 日志分段与噪音过滤 (Python Function Node)
  -> 节点3: 结构化摘要提取 (Agent Node, 调用 LLM)
  -> 节点4: 报告组装与推送 (Template Render + Webhook Node)
```

**数据源适配层**  
我们没有直接让 Agent 去调 Loki/ES 的 API，而是用 FastAPI 写了一个极简的 MCP Server，暴露 `search_logs` 工具，内部根据参数转发到对应的日志后端。这样做的好处是把认证、索引切换、分页逻辑全部封闭在 Server 内部，OpenClaw 侧只面对标准化的工具调用。

## 关键步骤与做法

### 1. 时间窗口与游标管理
触发时，先从持久化存储（我们用了一个简单的 SQLite 表）读取上次成功抓取的截止时间戳 `last_cursor`，然后以 `last_cursor` 为起点，当前整点前一分钟为终点，避免边界遗漏。抓取完成后，待报告成功推送再更新游标，实现断点续传。

### 2. 日志分段与噪音过滤
日志查询一次可能返回几千条 raw message。直接把全文塞给 LLM 会超出上下文窗口。我们在节点 2 做了一个预处理：
- 按 `service_name` 分组
- 每组内按时间排序，用 4000 字符为上限切分成多个 chunk
- 对每个 chunk 做正则预过滤：去除健康检查、重复堆栈前 3 行之外的追踪信息
- 保留原始日志 ID，便于后续溯源

### 3. 结构化摘要提取
对每个 chunk 调用一次 LLM，使用固定的 System Prompt 要求输出 JSON 格式：

```json
{
  "errors": [{"type": "short_category", "count": 2, "sample": "..."}],
  "warnings": [],
  "notable_events": []
}
```

这一步最容易出现幻觉：模型会“总结”出日志中不存在的错误类型。我们强制要求在 `sample` 字段中原文摘录一条典型日志，并在 Agent Node 的输出后挂了一个校验函数，凡是 `sample` 字段无法在原始 chunk 中找到子串匹配的条目，直接丢弃。

### 4. 跨 chunk 合并与业务指标对比
所有 chunk 的结构化结果汇集后，按 `type` 合并 count，生成全局错误报告。同时，针对业务事件（如支付回调失败、第三方 API 超时），我们会比较最近 24 小时与上一个 24 小时周期的计数，标注异常增幅。这一部分用纯 Python 完成，不依赖 LLM。

### 5. 报告渲染与推送
将合并后的结构化数据 + 数值对比 + 昨天的日报摘要模板，一同送入最后一个 Agent Node，要求生成约 150 字的风险提示，并严格遵循 Markdown 模板拼接成完整日报。推送通过飞书机器人 Webhook 完成。

## 踩坑记录

**上下文长度预估失准**  
最初按字符数切分，但模型 token 化后中文字符长度差异巨大。后来改为用 `tiktoken` 近似计数，确保每个 chunk 不超过 3000 token，给生成留足冗余。

**并发写入游标冲突**  
有次因为手动重跑 Workflow 和定时触发同时触发，导致游标被回退。解决方式是加乐观锁，更新游标时检查 `WHERE last_cursor < new_cursor`，失败则放弃本实例。

**日志时区混乱**  
Loki 存储 UTC 时间戳，但查询参数是北京时间。转化失误导致部分日志被重复抓取。此后所有内部处理统一用 epoch 秒，只在推送前格式化为本地时间。

**模型输出不稳定**  
曾遇到 LLM 在 JSON 中夹带 `` ```json `` Markdown 标记，直接导致解析失败。在 Agent Node 的 `output_format` 里开启了 `json_object` 模式，并增加了正则提取后备逻辑。

## 可复用建议

1. **MCP 做数据抽象**：即使后端是多个异构日志系统，也只用暴露一个 `search_logs` 工具，把适配成本限制在 Server 内部。
2. **校验链不可省略**：对 LLM 的输出做规则兜底（子串验证、JSON Schema 校验），否则上线一周内必出现坏格式。
3. **分离提取与叙事**：数值对比、聚合统计用确定性代码完成；自然语言总结仅用于“风险提示”这类高附加值部分，避免全篇依赖 LLM 生成。
4. **可配置的 Prompt 模板**：将不同服务的关注级别、错误类型分组做成配置文件驱动，增减服务无需改 Workflow 逻辑。
5. **沉淀示例日志库**：我们逐步收集了常见的噪音日志特征，现在预处理过滤精度已经很高，新人维护时可以直接参考。

## 总结

这条流水线已经稳定运行三个多月，日均处理 10 万行级别原始日志，生成日报的整体准确率（无事实错误、无遗漏已知严重错误）保持在可接受范围。最重要的体验是：**把 LLM 当成一个有限的、需要被约束的文本转换器，而不是全知全能的报告生成器**，才能让自动化日报真正可依赖。
