## 背景

在跟 Agent 打交道的几个月里，最消耗耐心的事情之一就是重复交代偏好。每次新开一个会话，或者上下文窗口撑满重置后，之前说过的“我不需要每次都给步骤编号”“输出代码时用 TypeScript 而不是 JavaScript”“项目默认用的是 pnpm”就得再说一遍。模型本身没有“自我”，Agent 更没有长期记忆。

OpenClaw 的工具调用机制、MCP 服务和插件体系已经能让 Agent 稳定地访问外部资源，但大部分自动化实践的落点还是“一次性任务”。要让 Agent 真正扮演一个持续合作的助手，记忆系统是绕不过去的基础设施。

## 问题拆解

设计记忆系统之前，先明确要解决的三类问题：

1. **偏好记忆**（你是谁、你喜欢什么）  
   比如缩进风格、命名偏好、回答语言、技术栈选择。这类信息稳定，很少变动。

2. **事实记忆**（项目/上下文相关）  
   比如“这个项目的数据库用的是 PostgreSQL，端口 5433”。有一定生命周期，项目结束可能就失效了。

3. **程序性记忆**（你习惯怎么协作）  
   比如“需求不清晰时先反问确认，不要直接写代码”“每次修改后自动跑一遍 linter”。

从工程角度看，记忆系统的核心挑战不是“存”，而是：
- 什么时候该记？
- 用什么粒度记？
- 怎么在需要的时候精准取到，而又不撑爆上下文窗口？

## 做法：基于 MCP 工具的分层记忆

这里给出一套在 OpenClaw 生态里可以直接落地的方案，不需要额外引入重型框架。核心思路是把记忆能力抽象成两个最简单的工具：`save_memory` 和 `query_memory`，通过 MCP 服务暴露给 Agent。

### 1. 定义数据结构

用最小的 Schema，降低 Agent 的理解成本：

```typescript
interface MemoryItem {
  id: string;
  type: "preference" | "fact" | "procedural";
  content: string;          // 自然语言描述
  tags: string[];           // 便于过滤
  importance: 1 | 2 | 3;   // 1-总是记住，3-可遗忘
  createdAt: number;
  lastAccessedAt: number;
  ttl?: number;             // 过期时间戳
}
```

后端存储直接用本地 JSON 文件或 SQLite，单文件零依赖，方便版本控制和迁移。如果记忆量大，可以换成 LiteFS 或 Chroma 做向量检索，但**一般个人使用场景下，标签 + 关键词匹配就已经够用了**。

### 2. 实现 MCP 工具

在 OpenClaw 的 `mcp.json` 里注册两个工具：

- `save_memory(content, type, tags, importance, ttl?)`  
  逻辑很简单：清洗 content（去掉过长的、明显是临时指令的内容），检查是否有语义重复的记忆，如果已有类似项，则更新而非新增。

- `query_memory(query, type?, limit?)`  
  先用标签过滤，再对 content 做简单的 TF-IDF 相似度匹配（或直接调本地 embedding 模型），返回 top-k 条。单次检索默认限制在 5 条以内，防止上下文污染。

### 3. 在 Agent 的系统提示里植入“记忆管理者”角色

不强制每一次对话都去写记忆，而是让 Agent 自主判断。系统提示里加入类似这样的指令：

> 当你发现用户表达了稳定的偏好、重复了三次以上的习惯、或明确说“请记住……”时，应该调用 save_memory。在每次开始解答问题前，调用 query_memory 检查是否有相关的偏好或事实。如果记忆与用户当前请求冲突，以用户最新表达为准。

这一步很关键：**Agent 需要知道“忘记”也是一种能力**。不要试图记住一切，上下文本身就是记忆的一部分。

### 4. 遗忘与更新策略

记忆膨胀是后期最大的坑。工程上做三层控制：

- **TTL 过期**：事实类记忆默认 90 天过期，偏好类永不过期但可被覆写。
- **重要性衰减**：每查询一次，`lastAccessedAt` 更新；如果一个记忆超过 30 天未被访问，自动降级 `importance`。
- **会话级强制清理**：用户说“忘掉之前关于……的所有设定”时，触发 `delete_memory_by_tag` 操作。

### 5. 接入项目工作流

把记忆文件放在项目根目录的 `.agent/memory.json`，通过 `.gitignore` 排除或被团队共享（如果你信任你的队友）。这样不同项目可以有不同的 Agent 记忆沙箱。MCP 服务启动时读取对应目录，实现项目级隔离。

## 踩坑记录

1. **嵌入模型的成本和必要性**  
   一开始我接了一个本地的 text-embedding-3-small，以为语义检索更准。实际对于偏好和事实记忆，关键词 + 标签的查全率高得多，延迟和成本却低一个数量级。除非记忆量级到 10k+ 条，否则别轻易上向量数据库。

2. **上下文窗口被记忆淹死**  
   有一次 `query_memory` 返回了 15 条“可能相关”的记忆，占掉 2000+ token，反而把当前问题的质量拉低了。后来加死限制：每次最多注入 3 条，且总 token 不超过 500。

3. **记了不该记的东西**  
   用户随口发的牢骚、临时的异常指令，都被 Agent 当偏好存了。后来在 `save_memory` 里加了一条校验：如果 content 中包含感叹号比例过高、或纯粹是否定句（“不要……算了”），直接忽略并返回“这条看起来像临时反馈，我不会记”。

4. **多 Agent 共享记忆的冲突**  
   如果你有多个 Agent 配置（比如 code-agent、doc-agent），共用同一份记忆文件时容易产生矛盾。建议不同 Agent 存不同的 `type` 标签，或直接分文件管理。

## 可复用建议

- **先做最小闭环**：一个 JSON 文件 + 两个工具，跑通再优化，不要一开始就设计“完美的记忆图谱”。
- **记忆即工具**：抽象成 MCP 接口，这样 Agent 升级、框架迁移时，记忆层可以原地保留。
- **给用户控制权**：提供 `list_memory`、`delete_memory`、`clear_memory` 三个配套工具，让用户随时审查和清理。
- **监控**：在工具返回里打印日志，记录每次记忆注入对最终回答的影响（简单比对 token 消耗和输出变化），这是以后调参的数据基础。

## 总结

Agent 记忆系统的本质是一套“信息生命期管理”策略，而不只是把东西存下来。在 OpenClaw 的插件/MCP 体系下，用最朴素的 JSON 文件 + 两个工具，就能让 Agent 从“一次性工具”变成一个能积累经验的协作伙伴。别急着上复杂方案，先让自己的 Agent 记住你最喜欢用哪个包管理器，这小小的改善就足够打动人了。
