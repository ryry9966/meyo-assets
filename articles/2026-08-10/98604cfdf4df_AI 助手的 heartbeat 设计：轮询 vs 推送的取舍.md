## 背景：为什么 AI 助手需要 heartbeat

在 OpenClaw 这类 Agent 框架里，一个典型的工作流通常涉及多个插件的协作。插件 A 负责文件解析，插件 B 处理大模型调用，插件 C 推送结果到外部系统。这些组件可能跑在同一个进程里，也可能分布在不同的容器或服务中。想让这条链路上每个环节都「知道彼此还活着、干活干到哪儿了」，就需要一套心跳（heartbeat）机制。

heartbeat 不只是判断存活。在长时间运行的自动化任务（比如批量数据分析、MCP 工具调用、Agent 之间的状态同步）中，它还得携带进度信息、错误状态，甚至触发重试或降级策略。选型的关键问题就落到了「轮询」和「推送」这两种通信模式上。

## 问题：两个方向，各自挣扎

轮询是直觉上最简单的方案。每隔几秒，去问一下「好了没」。对客户端来说，一个 `setInterval` 再加一个 HTTP 请求就搞定了；服务端也只需要提供一个无状态的 REST 接口。但工程上的痛点几乎立刻浮出来：

- 延迟和资源无法兼得。如果追求低延迟，间隔就得缩短，服务端 QPS 迅速上升，大部分请求拿到的只是「还没好」的状态码；如果放宽间隔，任务明明已经完成，客户端却要等到下一个轮询时刻才能感知。
- 状态同步不自然。任务出现中间态（50%、80%）时，客户端只能拿到离散的快照，无法形成连续进度感知。
- 扩展性受限。当要监控的组件数量增多，轮询的请求量会线性甚至指数级增长，尤其是微服务或插件数量多的时候。

推送（WebSocket、SSE）解决了实时性的问题，服务端在状态变化时可以主动告知客户端。可惜，它把复杂性转移到了连接管理和可靠性上：

- 连接可能静默断开。中间代理、负载均衡器或 NAT 网关可能因为空闲超时掐掉 WebSocket 连接，而 TCP 层的半开连接很难被即时发现。
- 需要应用层心跳。WebSocket 虽然有内置的 ping/pong 帧，但很多框架（包括 Node.js 的 `ws`）默认没有开启，需要显式配置，且部分客户端不支持自动回复 pong。
- 重连状态要恢复。推送中途断开，客户端重新连上后，需要一套机制（如携带最后接收的事件 ID）来补发错过的消息，否则会出现状态丢帧。

这两种方式的影响在 AI 助手场景里会被放大。Agent 之间的任务编排经常是树状依赖的，一个子任务的状态遗漏，可能让整个 DAG 执行停滞或者出现重复操作。

## 做法：从「能用」到「好用」的工程化选型

实际落地时，我习惯把 heartbeat 切分为两个维度分别做决策：**状态查询模式**和**连接保活机制**。

### 1. 定义轻量 heartbeat 协议

无论用哪种模式，先约定一个统一的消息结构，例如：

```json
{
  "type": "heartbeat",
  "timestamp": 1715000000,
  "status": "running",
  "progress": 0.75,
  "error_code": null,
  "trace_id": "abc123"
}
```

这样客户端和服务端可以复用同一套解析逻辑，后续切换模式时改动最小。

### 2. 轮询方案：用条件请求减少无效传输

如果场景允许 2~5 秒的延迟，轮询完全够用。关键优化点是服务端返回 `ETag` 或 `Last-Modified` 头，客户端下次请求时带上 `If-None-Match` 或 `If-Modified-Since`。状态没有变化时，服务端直接返回 `304 Not Modified`，完全省去传输体和序列化开销。

踩坑点：很多初学者在服务端不设缓存标识，导致每个请求都返回完整 JSON，网络带宽被白白吃掉。另外，客户端要处理服务端短暂无响应的情况，建议加上超时和错误重试，但不对同一个过期请求做无限重试。

### 3. 推送方案：WebSocket + 强制应用层 heartbeat

需要亚秒级反馈的任务（如插件执行过程中的日志流、Agent 实时对话），建议上 WebSocket。搭建步骤：

1. 服务端启用 WebSocket 协议，并配置 `heartbeat` 间隔（例如每 30 秒发送 ping）。
2. 客户端连接后启动定时器，如果在 2~3 个 heartbeat 周期内没有收到任何消息或 pong 响应，主动关闭连接并重连。
3. 重连时携带上次收到的最新的消息 ID，服务端据此从事件队列中补推遗漏的消息。

这里我踩过的最大坑是：**把 TCP 层的 keepalive 当成应用层心跳**。Linux 的 `tcp_keepalive` 默认探测间隔是 7200 秒，远水解不了近火。必须自己实现应用层的心跳，否则经过负载均衡或云服务商的网络设备时，空闲连接会在几十秒到几分钟内被静默清理。

另一个隐藏问题是多实例部署。如果服务端有多个副本，客户端重连后可能落到另一个副本上，而那个副本并没有缓存消息历史。解决方案是将会话状态外移到 Redis 或数据库，或者在负载均衡器上配置会话保持（sticky session），但后者配合滚动发布时又会引发新问题。建议采用外移状态的方式，对规模扩展更友好。

### 4. SSE 作为轻推送的折中

对于服务端向客户端单向推送进度（如 MCP 工具执行结果、批处理任务日志），Server-Sent Events 足够轻量。HTTP 协议的天然优势让它在消息代理和防火墙面前更友好。为了检测连接死活，同样需要服务端每隔一段时间发送一条注释行（`: heartbeat\n\n`），客户端在 `onerror` 时触发重连。

不同浏览器的 EventSource 实现有差异，Node.js 客户端可以选择 `eventsource` 包，重连逻辑更可控。

## 踩坑点总结

- **轮询间隔选择**：按最高可容忍延迟的 1/3 设置为上限。例如容许 3 秒延迟，那么轮询间隔不超过 1 秒。
- **WebSocket 重连风暴**：重试策略必须加入指数退避（1s、2s、4s...上限 30s），避免服务端重启时大量客户端同时冲击。
- **推送下的状态一致性**：推送只是通知「状态变了」，客户端应该重新拉取一次完整状态，而不是仅仅依赖推送体里的片段。
- **混合模式**：生产环境可以考虑 WebSocket 主通道 + 轮询降级的模式。WebSocket 断开期间自动切回低频轮询，连接恢复后注销轮询定时器。

## 可复用建议

在 OpenClaw 的插件开发或 Agent 调度中，可以沉淀这样一套策略：
- 插件注册时同时暴露一个健康检查 HTTP 端点（`GET /health`）和一个可选的 WebSocket 升级端点。
- Agent 启动后，优先尝试 WebSocket 连接；若失败则回退到轮询 `/health`，并带上上次已知状态的时间戳作为查询参数。
- 监控线程统一处理两种模式的超时和状态机转换，业务逻辑只关心最终的状态回调。

## 总结

轮询和推送不是非此即彼的技术信仰问题，而是延迟需求、资源预算与工程复杂度之间的权衡。对于多数 OpenClaw 社区里的自动化任务场景，我的经验是：**以轮询起步，在性能瓶颈或体验要求明确后再引入推送，并在推送侧花大力气把重连、心跳和状态恢复做扎实。** 这条原则让我们在快速迭代功能的同时，避免过早陷入分布式连接的泥潭。
