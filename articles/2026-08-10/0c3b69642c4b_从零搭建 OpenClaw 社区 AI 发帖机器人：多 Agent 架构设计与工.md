## 背景与动机

在 OpenClaw 社区维护技术内容时，常需要将本地笔记、项目总结或每周精选整理成标准化帖子。人工撰写不仅重复，还容易遗漏格式细节。于是动手搭了一个基于 OpenClaw 框架的发帖机器人，让它根据简短主题或参考资料，自动生成结构清晰、风格一致的技术帖，并直接发布到社区。

选择 OpenClaw 框架的原因很简单：原生支持 Multi-Agent 编排、内置插件市场（Discourse API 插件）、且可通过 MCP 接入私有知识库，非常适合这条“内容生成-审核-发布”流水线。本贴记录完整架构、关键实现步骤和那些让人头疼的深坑，希望能给同样想做社区自动化的朋友一点参考。

## 架构设计

整体采用四层 Agent 协作模式，所有 Agent 均运行在 OpenClaw 的 `Orchestrator` 中，以消息总线的形式串联。

1. **输入解析 Agent**  
将用户给出的主题或 Markdown 草稿规范化，抽取关键词、识别意图（技术分享/项目展示/问题讨论），并生成内容纲要。

2. **内容生成 Agent**  
核心创作单元。根据纲要生成正文，同时通过 MCP 连接本地向量知识库（如 OpenClaw 文档、过往高质量帖子）确保技术点准确，避免胡说。这里配置了温度较低的模型（如 GPT-4o-mini）来控制稳定性。

3. **审核优化 Agent**  
对生成内容进行多维度检查：敏感词、标签规范性、Markdown 语法、社区发帖模板等。发现偏差会打回重写，并附修改建议。这一步调用了社区公开的 “发帖规范” JSON schema 做结构化校验。

4. **发布 Agent**  
优先使用 OpenClaw 内置的 Discourse API 插件直接创建帖子，失败时自动降级为 Playwright 浏览器模拟发布。支持草稿预览和手动确认开关。

架构流：用户输入 → Orchestrator 分配任务 → 各 Agent 通过内存共享上下文 → 发布结果回传。为降低耦合，Agent 间只传递结构化消息，不直接调用彼此函数。

## 核心流程拆解

1. **环境准备**  
- 安装 OpenClaw 框架，配置`openclaw.yaml`启用插件：`discourse_api`、`playwright_browser`。  
- 注册社区账号并获取 API Key（Discourse `admin` 权限下的全局 key），配置到环境变量。  
- 部署 MCP 服务：使用`mcp-server-vectordb`挂载本地知识库索引。

2. **提示词模板设计**  
为避免 Agent 自由发挥偏离社区风格，为每个 Agent 预制了 System Prompt 模板。例如，内容生成 Agent 的模板明确要求“使用务实、克制的语气，禁止营销腔，每段不超过 4 句，优先使用技术术语原文，代码块标注语言”。模板通过 OpenClaw 的 `prompt_registry` 统一管理，支持热更新。

3. **发布流程实现**  
在 OpenClaw 的任务定义中，将发布逻辑封装为一个 `Skill`，内部先尝试调用 `discourse_api.create_post`，捕获限流或权限异常后，自动切换到 Playwright 方案。Playwright 方案会复用已保存的浏览器 Session，减少登录耗时。发布前所有内容会存入中间草稿栈，等待人工审核信号（可配置为自动跳过）。

## 关键踩坑与解决方案

**坑 1：Discourse API 的 Markdown 兼容问题**  
社区基于 Discourse，它默认使用 CommonMark 但略有扩展。直接粘贴 AI 生成的 Markdown 容易出现表格不对齐、HTML 标签被转义、连续代码块无空行导致渲染失败。  
**解法**：在审核 Agent 中添加专用后处理步骤——将所有 ` ``` ` 代码块前后强制插入空行；表格用 `|` 对齐并禁止使用 HTML 表格；自动将 `<img>` 转换为 Discourse 的图片上传引用。还写了一个 50 行的 Python 脚本基于 `mistune` 做二次解析，输出确保安全的 Discourse Markdown。

**坑 2：Agent 上下文窗口溢出**  
当生成超长帖子（比如项目文档全貌）时，多个 Agent 串联导致上下文迅速膨胀，超出模型最大 token 限制，Orchestrator 直接返回截断错误。  
**解法**：给每个 Agent 设置严格的上下文裁剪策略，仅保留上一环节输出的摘要与修改建议，不携带全文历史。同时为内容生成 Agent 引入分段生成机制：先将大纲拆分为多个小节，逐节生成，最后由组装 Agent 拼接。这样单次调用 token 消耗稳定在 2k 以内。

**坑 3：定时任务触发与冷启动**  
最初用 cron 定时触发时，Orchestrator 的复用会话偶尔会携带过期 cookie，导致发布失败，且没有主动刷新的逻辑。  
**解法**：在每次定时任务开始前，强制进行一次 Discourse API 的健康检查（ping），若失败则重置 Plugin 的 Session 并重新登录。同时在 Playwright 降级分支增加强制清理 `user_data_dir` 的逻辑，避免残留状态。

**坑 4：敏感词误伤与社区规范动态变化**  
静态敏感词表维护不及时，经常误判正常技术词（如“代理”被拦）。  
**解法**：审核 Agent 不止做关键词匹配，还调用一个轻量分类模型判断整句意图。同时将社区最新的“发帖规范”定期通过 MCP 同步到知识库，审核时动态比对最新规则。

## 可复用建议

- **从插件开始，不要重复造轮子**：优先使用 OpenClaw 市场中的 Discourse 插件，它已处理了大部分鉴权和参数封装，你只需专注业务流。  
- **流式输出加中间缓冲**：生成内容时开启流式（stream），避免用户长时间等待；但发布环节必须等待全量内容生成完毕并校验通过，切勿边生成边发帖。  
- **人工兜底必留**：即使是全自动流水线，也保留一个“草稿箱”功能，允许关键时刻人工介入修改。我用的是 OpenClaw 的 `human_in_the_loop` 模式，一条消息即可中止发布。  
- **监控发布成功率**：给发布 Agent 加上简单的 Prometheus 指标（如 `post_success_total`、`fallback_playwright_total`），能快速发现社区 API 策略变更。  
- **知识库及时更新**：每周自动抓取社区精选帖和前几页高热话题，转写为 Embedding 存进 MCP 知识库，保证生成内容上下文不落伍。

## 总结

用 OpenClaw 的多 Agent 架构搭建社区发帖机器人，真正耗时的地方并不是 AI 生成本身，而是如何让它稳定、合规、美观地落地到实际论坛。把精力放在格式化后处理、降级机制和人工审核开关上，远比单纯优化提示词更划算。这套方案目前已在 OpenClaw-CN 内部分享小范围试运行，每周生成 3~5 篇高质量帖子，人工修改率不到 10%。如果你也有类似的自动化发帖需求，希望这些踩坑记录能帮你少走弯路。
