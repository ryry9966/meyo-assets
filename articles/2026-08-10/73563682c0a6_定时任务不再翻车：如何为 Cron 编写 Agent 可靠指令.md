## 背景

在 OpenClaw 这类 AI Agent 平台上，Cron 任务允许用户按固定时间调度 Agent 自动执行操作，比如定时汇总 RSS、同步数据、发送日报或触发工作流。这些任务通常通过 MCP 工具或内置插件来完成实际动作，而 Agent 的行为则由一个自然语言 Instruction（指令）驱动。  
很多用户以为“只要写了几个时间点，Agent 就能按时干活”。实际上，如果 Instruction 写得模糊、缺少执行约束，Cron 任务很容易变成“按时翻车”——误触发、漏触发、时区错乱、重复写入数据都是常见结果。

本文不讨论 Cron 表达式本身的基本语法，而是聚焦在 **如何为 Cron 任务写一份工程化、可复现的 Instruction**。面向已经在用 OpenClaw/Agent/MCP/插件搭建自动化流程的读者。

## 问题：模糊的指令是 Cron 的慢性毒药

一个典型的反面例子：

```
每天早上 9 点帮我拉取最新新闻，总结一下，然后发到 Discord。
```

这段 Instruction 至少带来以下隐患：

1. **没有明确的执行边界**：Agent 可能当场就执行一次，认为这是一次性对话任务，而不会等到明天 9 点再按 Cron 调度触发。
2. **时区缺失**：9 点是哪个时区？Agent 可能默认 UTC，导致你的日报在凌晨发出。
3. **任务细节靠“猜”**：“拉取最新新闻” 从哪里拉？RSS 源还是网页？用哪个工具？Agent 可能随意选择并不存在的 API，凭空生成内容。
4. **容错与幂等性为 0**：一旦某一次执行失败，没有重试机制，也不会通知你。更致命的是，如果任务因为网络抖动超时后又被 Cron 再次触发，可能产生两条重复的 Discord 消息。
5. **Cron 表达式与语义冲突**：你以为“每天早上 9 点”对应 `0 9 * * *`，但如果 Agent 自行将“每天”理解成了“工作日”，实际行为会出现偏差。

要让 Cron 任务真正稳定运行，必须把 Instruction 从“给朋友的口头交代”升级为“给机器的执行契约”。

## 做法：把 Instruction 写成分层契约

我们以“工作日 9:00（北京时间）拉取某 RSS 源，用 LLM 生成三条中文摘要，通过 Discord MCP 发送”为例，展示一个可复现的 Instruction 结构。

### 1. 明确触发与上下文

```markdown
你是一个定时执行的助手。以下任务由 Cron 调度器触发，**不是即时对话**。
- 触发时间：周一至周五，北京时间 09:00
- Cron 表达式：0 9 * * 1-5 (时区 Asia/Shanghai)
- 每次触发时，你会看到本 Instruction 作为唯一的上下文，没有前后对话记忆。
```

这段文字做了两件事：声明调度器与 Agent 的关系，并把时区和 Cron 表达式写死，防止 Agent 自行推断。

### 2. 按步骤定义动作，严禁发挥

```markdown
请严格按照以下步骤执行，不要跳过、合并或发明额外步骤。

步骤 1（读取数据）：
- 使用 MCP 工具 `rss_fetch` 读取源：https://example.com/feed.xml
- 提取最近 12 小时内发布的条目，最多 10 条。
- 如果工具调用失败，记录错误并进入步骤 3 的错误处理分支。

步骤 2（生成摘要）：
- 对每条条目，调用内置 LLM 生成长度不超过 140 字的中文摘要。
- 按“标题 + 链接 + 摘要”的格式组织为一条消息。
- 注意：只使用步骤 1 实际返回的数据，不允许编造新闻。

步骤 3（发送到 Discord）：
- 使用 MCP 工具 `discord_send`，将步骤 2 生成的消息发送到频道 ID：123456789。
- 如果发送成功，输出一行日志：“Cron task completed successfully at {timestamp}”。
- 如果任何步骤失败，发送一条仅包含报错信息的 Discord 消息到同一频道，并以 “CRON_ERROR” 开头。
```

关键点在于：**步骤必须编号，且明确调用哪个工具、工具参数、以及成败处理路径**。这相当于把 Instruction 变成了一份微型的“工作流定义”。

### 3. 加入幂等与去重保护

Cron 任务的常见痛点之一是：上一次执行还没结束，下一次又来了。此时如果没有保护机制，可能产生重复数据。可以在 Instruction 中增加一个检查点：

```markdown
执行前置检查：
- 开始执行前，读取共享状态文件（MCP 工具 `state_read`，key=last_discord_cron_date）。
- 如果上一次成功发送的日期与今天相同，本次跳过所有步骤，直接输出“Already executed today, skipping”。
- 步骤 3 发送成功后，立即写入 `last_discord_cron_date = {今日日期}`。
```

如果你没有状态存储，可以退而求其次：在 Discord 消息中携带唯一 batch ID（如日期+任务名），手动审查时也更容易发现重复。

### 4. 定义清晰的“完成信号”

Agent 在 Cron 场景下尤其需要明确的终止语句，否则可能停留在工具调用后“思考”或追加无用评论。在 Instruction 末尾加上：

```markdown
完成以上步骤后，只输出“DONE”。不要生成任何额外说明或建议。
```

这能减少 Agent 的无意义输出，也让日志更干净。

## 踩坑记录

- **Cron 日与星期同时指定**：像 `0 9 1 * 1` 这样的表达式，如果以为是指“每月 1 号且周一执行”，大多数调度器实际上会取 `OR` 逻辑，导致每月 1 号和每个周一都触发。务必只选一种约束方式。
- **Agent 对时间的理解偏差**：当 Instruction 里出现“每天”“每小时”时，Agent 可能把 Cron 调度时间忘掉，而用对话界面里的“当前时间”去计算。所以永远显式给出 Cron 表达式和时区。
- **MCP 工具的认证过期**：定时任务经常因长期未登录导致 Token 失效。Instruction 里最好添加：“如果工具调用返回 401/403，立即通过 `notify_webhook` 发送报警”，而不是让 Agent 无限制重试。
- **指令太长被截断**：如果 Instruction 超过平台允许的上下文长度，后半段可能丢失，Agent 只会执行前面几步。建议将非必要的背景说明移出，只保留执行逻辑。

## 可复用建议

1. **采用模板**：建立一个 Cron Instruction 模板，包含 `触发定义`、`前置检查`、`步骤列表`、`错误处理`、`完成信号` 五段，每次新建任务时只改参数和工具名。
2. **分离执行与汇报**：不要把详细的分析报告写在 Cron 主流程里。主流程只做“获取->处理->发送”，详细报告可存入文件或通过另一个轻量指令生成。这能降低单次执行的耗时与失败面。
3. **善用 dry-run**：先通过即时对话，只发给人一个测试频道，验证每个步骤的工具调用都正确。确认无误后，再切换到正式的 Cron 与生产频道。
4. **记录执行日志**：在每条 Discord 消息或日志中附带 `execution_id = {任务名}-{日期}-{随机短码}`，便于后续排障。
5. **把 Cron 也纳入配置**：如果所用平台支持在 Instruction 内部无歧义地声明 Cron（例如通过 frontmatter），那就写进去，不要把调度配置和任务指令完全分离在两个界面，这能让你在查看指令时一眼看到调度约定。

## 总结

为 Cron 写 Instruction 的本质不是写提示词，而是写一份**确定性的执行规范**。你必须放弃“Agent 很聪明，会自己领会”的幻想，把时区、步骤、工具调用、错误处理全部显式化。这样，Cron 任务才能从“偶尔能用”变成“长期可靠”的自动化节点。

一个稳定的 Cron Agent 不是靠精妙的 prompt tricks，而是靠清晰、可测试、可监控的工程约束。
