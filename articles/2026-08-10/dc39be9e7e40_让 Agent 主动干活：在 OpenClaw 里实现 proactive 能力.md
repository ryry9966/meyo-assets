## 背景

大多数 AI 助手的工作模式是“命令-响应”：你说一句，它动一下。但在实际工程中，有一类需求天然需要**主动触发**——监控报警后的自动止损、代码仓库有新 PR 时立即审查、日程变更时主动协调时间，等等。这类场景里，等用户开口，时效性已经丢了。

OpenClaw 社区中，Agent 可以通过 MCP（Model Context Protocol）连接大量工具，但默认的对话循环依然是用户驱动的。要让 Agent“不等你开口就把事情办了”，就需要跳出纯对话框架，引入**事件/时间驱动的执行能力**。

这篇文章从一个真实需求切入：**自动 code review**，记录我用 OpenClaw 的 Agent + MCP 工具实现 proactive pipeline 的做法、踩的坑和可复用的经验。

---

## 问题

团队维护一个中大型仓库，每天有 5~10 个 PR 进入。虽然有 code review 规范，但高峰时段经常积压，等到人工 review 时上下文已经变冷，修改成本也上升。

理想方案：有一个 Agent，**每 30 分钟自动检查**组织下所有未评论的 PR，对 diff 做初步分析，把可疑片段、命名问题、潜在逻辑缺陷直接以行级评论的形式贴到 GitHub 上。这样 reviewer 拿到的是一个半成品，只要确认或驳回即可，大幅降低认知负担。

这件事在 OpenClaw 里能做吗？可以，但需要解决几个核心问题：

- 如何让 Agent 定期执行，而不是等人发消息？
- 如何把 GitHub 信息变成 Agent 能处理的工具调用？
- 如何避免重复评论、误报、API 限流等工程麻烦？

---

## 做法 / 步骤

### 1. 基础设施：MCP Server + Agent 定义

OpenClaw 支持通过 `mcpServers` 配置接入外部工具。我使用的是社区发布的 `@anthropic/mcp-server-github`，它封装了常见的 GitHub API：列出 PR、获取 diff、创建 review 评论等。

Agent 侧定义了一个 system prompt，告诉它角色是“严谨但友善的 code reviewer”，需要关注：

- 逻辑错误、空指针（对应语言是 TypeScript / Python）
- 可读性差的长函数、嵌套过深
- 未处理异常的异步调用
- 变量命名与注释不一致

并明确要求：**每条 review 必须附上具体代码行号和文件路径**，避免空泛评论。

### 2. 触发机制：从 cron 到 OpenClaw scheduler

OpenClaw 原生并没有像传统 workflow 引擎那样的 cron 调度器，但它的 Agent 可以长驻运行，并在对话循环中接受外部事件。

我的做法是：在 Agent 运行环境里额外跑一个轻量级 Node.js cron 进程，每 30 分钟向 Agent 的对话接口发送一条特殊消息，内容类似：

```
[system-trigger] 执行代码审查检查
```

Agent 收到这条消息后，根据 system prompt 里的“触发规则”理解这是一次主动任务，进入工具调用流程。

> 踩坑点 1：早期直接用 HTTP 请求向 OpenClaw endpoint 发 user 消息，但 agent 会把“执行检查”这句话当成用户意图去闲聊。后来改成在 system prompt 中约定特殊前缀，并将该消息的 role 设为 `system`，Agent 才稳定进入指定流程。

### 3. 执行流程：查 PR → 判重 → 获取 diff → 分析 → 评论

Agent 按照如下步骤操作（每一步都是 MCP 工具调用）：

1. 调用 `list_pull_requests` 获取目标仓库所有开放 PR。
2. 对每个 PR，调用 `list_reviews` 检查是否已有本 app 的评论，避免重复。
3. 对未评论的 PR，调用 `get_pull_request_diff` 获取 diff 文本。
4. 将 diff 分段（超过 8000 token 时分批）喂给模型，逐段分析。
5. 对分析出的问题，调用 `create_pull_request_review_comment` 贴到具体代码行。

整个流程由 Agent 自己工具调用链完成，cron 只负责点火。Agent 的上下文里会维持一个“本轮已处理 PR 列表”，处理完自动停止，不会无限循环。

### 4. 调优与监控

第一次上线后跑了一周，效果非常好，但也暴露了大量工程细节：

- **Token 消耗巨大**：单个大 PR 的 diff 可能超过 3 万 token，几次工具调用就烧掉大量额度。后来加入 diff 过滤（忽略自动生成文件、仅 review 核心业务目录），并设置单次任务最大 token 上限。
- **幻觉行号**：Agent 偶尔会评论不存在的行号，导致 API 调用失败。通过强制要求“引用 diff 中实际出现的 `@@` 行号段”并做格式校验，错误率大幅下降。
- **评论风格不一致**：有时太啰嗦，有时只给一句“这里可能有问题”。后来在 system prompt 内嵌了 3 个 good / bad 示例，行为稳定很多。

## 可复用建议

如果你想在 OpenClaw 中实现类似的 proactive 能力，可以考虑下面这些模式：

1. **用 system 消息充当内部事件总线**  
   不要直接把 cron 消息当作 user 输入，会被对话逻辑污染。约定特殊前缀，以 system 角色注入，然后在 prompt 中定义“收到这类消息时进入任务模式”。

2. **让 Agent 自己持有状态，但不依赖长期记忆**  
   本轮任务的状态（已处理 PR 列表、中间结果）存在 Agent 的上下文变量里，任务结束即释放。不要依赖跨会话的长期记忆，会引入不可控的累积错误。

3. **所有写操作都加“安全开关”**  
   涉及发评论、提 issue、发邮件等不可逆操作，建议加上确认步骤，或者先在日志中预览一次。我的做法：先在本地环境跑 dry-run 模式，打印评论内容，确认无误后再上生产。

4. **做好限流和退避**  
   GitHub API 有严格限流，MCP server 最好内置重试和指数退避。Agent 调用工具时如果连续失败，应主动中断任务并记录告警，不要死循环重试。

5. **覆盖不到的边界，交给人工 fallback**  
   Proactive 不等于全自动。我们在每个 review 评论末尾固定加上一句：“此评论由 AI 自动生成，请 reviewer 确认或直接关闭。” 明确区分人与机器的责任边界。

## 总结

实现 proactive 的核心不是某个炫酷算法，而是**把 Agent 从“对话机器人”改造成“事件驱动的执行单元”**。在 OpenClaw 里，通过 system 消息注入 + MCP 工具链，可以零额外平台依赖地做出可靠的自驱任务。

这条路能复用到很多场景：数据库慢查询自动分析并提 issue、监控告警自动跑诊断脚本、日报生成、竞品更新追踪……本质上都是“定期感知 → 分析 → 动作”的流水线。

唯一的提醒是：**proactive 越主动，犯错的风险越大**。所以在设计流程时，请一定把“可回滚、有预览、有人工抽查”这三个原则埋进去，才能真正让 Agent 替你办事，而不是替你闯祸。
