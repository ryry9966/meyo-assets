## 背景：当 Agent 学会上网，麻烦也来了

基于 OpenClaw 构建的 Agent 经常需要实时网页内容：查询文档、读取商品价格、监测状态变化。最简单的办法就是让 Agent 直接 HTTP GET，但现实很快教做人——请求被拒、IP 被 ban、验证码拦路，甚至触发了远程站点的风控告警。

这些问题的根源不是“爬虫”，而是“裸奔的爬虫”。直接请求缺乏身份伪装、没有速率约束、不理 robots.txt、对需要 JavaScript 渲染的页面无能为力。一个长期运行的自动化助手，如果不对网页采集环节做工程化治理，必然会变成不稳定的故障源。

因此我们需要一个位于 Agent 与目标站点之间的“稽客层”——专门为 Agent 设计的安全抓取中间件，既满足自动化信息获取需求，又避免踩中反爬红线。

## 问题拆解：Agent 抓取为何容易“翻车”

1. **指纹单一**：固定 User-Agent、固定 IP、无 Referer，几秒内就被识别为脚本流量。
2. **速率不控**：Agent 可能短时间内多次请求同一域名，触发频率限制。
3. **忽略 robots.txt**：标准爬取规范被无视，法律风险与现实封禁并存。
4. **动态内容抓瞎**：大量站点靠前端渲染，静态 fetch 拿到的只是空壳 HTML。
5. **无退避与重试机制**：遇到 429/503 无等待立即重试，加剧封禁。
6. **无状态管理**：需要登录或 Cookie 的场景下，请求间状态断裂。

## 做法：构建稽核中间层，并通过 MCP 接入 OpenClaw

核心思路是把“安全抓取”封装成一个独立的 MCP Server，Agent 只调用该 Server 提供的 `fetch` 工具，所有反反爬、合规、缓存策略在内部闭环。

### 1. 工具接口设计

为 Agent 提供一个简单的工具定义：

- `url` – 目标地址
- `method` – GET/POST
- `headers` – 可选，自定义头部
- `render_js` – 是否需要无头浏览器渲染（默认 false）
- `timeout` – 超时时间

尽量让 Agent 的调用侧保持简单，复杂度沉淀在后端。

### 2. 策略引擎实现（Node.js 示例）

使用 `robots-txt` 库在每次请求前检查对应域名的 robots.txt（可配置关闭），如果路径被禁止则直接返回错误原因。通过后，进入请求执行管道：

**静态请求路径**：使用 `got` 或 `node-fetch`，从 UA 池随机选择 User-Agent，配合代理池替换来源 IP。全局维护一个 `rateLimiter`（例如每个域名最小间隔 800ms）限制并发与频率。

**动态渲染路径**：对于 `render_js: true` 的请求，启动 Puppeteer / Playwright 实例，加载 `puppeteer-extra-plugin-stealth` 消除自动化痕迹。设置 viewport、语言、时区等指纹，避免被立刻识别。由于无头浏览器开销大，需要池化管理浏览器实例，并限制同时打开的标签数量。

**缓存层**：对相同 URL 的 GET 请求在短期内（例如 5 分钟）直接返回缓存结果，防止 Agent 重复触发同一请求。

**重试与退避**：遇到 429/503 时，以指数退避重试最多 3 次，并将该域名的速率临时降到更低。

### 3. 作为 MCP Server 暴露

将上述能力封装为符合 Model Context Protocol 的 Server，启动后 Agent（如通过 OpenClaw 的 MCP 插件）可像调用本地函数一样发起安全抓取。示例工具调用：

```json
{
  "name": "safe_fetch",
  "arguments": {
    "url": "https://example.com/data",
    "render_js": true
  }
}
```

返回的内容包含状态码、响应体（文本/HTML）、是否来自缓存、处理耗时等元数据，方便 Agent 做后续决策。

## 踩坑记录

**坑 1：Cloudflare / 验证码墙**  
即使用了 stealth 插件，部分站点（如 Cloudflare Turnstile）仍会弹出验证码。目前无法完美通用解决，需要针对特定站点预录 Cookie 或采用人工打码后备方案。对于 Agent 场景，与其硬搞，不如在策略层标记“不可自动化抓取”，避免浪费时间。

**坑 2：无头浏览器内存泄漏**  
长时间运行的 MCP Server 如果没有定时回收浏览器进程，内存会持续增长。必须设置每个浏览器实例的最大存活时间（如 20 分钟）和请求次数上限，到期后强制重启。

**坑 3：robots.txt 误杀**  
某些站点的 robots.txt 会禁止所有 User-Agent，但实际上对非商业低频抓取持容忍态度。因此 robots 检查应做成可配置的白名单放行或降级策略，而非一刀切。

**坑 4：动态页面内容变化**  
即使渲染成功，页面也可能因为懒加载或 API 请求延迟而未包含目标数据。需要额外实现“等待选择器出现”的超时机制，并返回部分内容时标记 `partial` 状态，让 Agent 决定是否重试。

## 可复用建议

- **配置化一切**：域名白名单/黑名单、代理策略、速率限制、是否允许 JS 渲染、缓存 TTL 等都通过配置文件管理，不同 Agent 工作负载可用不同 profile。
- **审计日志**：记录每次请求的目标、参数、是否命中缓存、最终状态，方便排障和合规审查。
- **PII 过滤**：若抓取内容可能包含敏感信息，可在返回给 Agent 前做正则脱敏，降低隐私风险。
- **容器化部署与资源限制**：将 MCP Server 打包为 Docker，限制 CPU 和内存，通过 `--max-old-space-size` 等参数控制 Node.js 内存，避免失控。
- **录制回放模式**：针对高频访问的复杂交互页面，可以人工浏览录制 HAR 或浏览器操作，再让 Agent 使用回放方式获取稳定数据——既避反爬，又保证数据一致性。

## 总结

让 Agent 自由上网不等于裸奔。通过构建一个懂尊重、会伪装的稽核中间层，不仅能大幅降低封禁概率，还让整个采集过程从不可控的“碰运气”变成可审计、可管理的工程管线。接入 OpenClaw 的 MCP 生态后，这套安全抓取能力可以低摩擦地复用到多个 Agent 工作流中。

工程上不必追求“完美模拟真人”，但要做到有节制的自动化：遵守规则、控制频率、伪装合理、主动失败而不是被动挨打——这就是为 Agent 安全采集网页的实用哲学。
