## 背景

在 OpenClaw、自建 Agent、MCP 工具链等自动化场景里，我们大量依赖 LLM 返回结构化的动作描述、工具调用参数或数据块。最理想的方式是要求模型输出纯 JSON，直接 `json.loads` 即可进入下一步。但现实中，模型的输出几乎一定会被包裹在 Markdown 代码块、自定义XML标签（如 `<action>`、`<tool_call>`、`<response>`）、前置的自然语言解释，或者混排多种格式。

当这些结构化输出被丢给下一级插件或自动化流程时，脆弱的解析逻辑会导致整条链路中断，强迫人工介入。经过多个项目的打磨，我们沉淀出一套 **防御性解析策略**，在保持代码简洁的前提下，将解析成功率从七成左右提升到接近 99%。

## 典型问题

最常见的三种“非纯净 JSON”模式：

1. **Markdown 代码围栏**  
   ````json\n{"key": "value"}\n````，甚至前后有说明文字。
2. **自定义标签包裹**  
   如 `<thinking>...</thinking>` 中间杂糅，或 `<tool_calls>[{...}]</tool_calls>`，JSON 体嵌在标签内。
3. **多段混排**  
   尾部追加 `请检查以上结果`，或输出类似 `分析：... \n 结果为 {"a": 1}`。

直接调用 `json.loads(text)` 会立刻抛出异常，即使做了基础的字符串清理，嵌套标签、中英文引号混用、流式分块导致的截断也常让人头疼。

## 做法与步骤

我们实现了一个可复用的解析函数，遵循“从净到脏、逐层降级”的原则。

### 1. 标准化预处理
```python
def defensive_json_parse(text: str):
    # 去除零宽字符、BOM，统一换行
    text = text.strip().replace('\ufeff', '')
```
先剥离两端空白与不可见字符。部分 LLM 接口会带上 BOM 或对话历史残留的控制符。

### 2. 清理 Markdown 代码块
```python
import re
fence_pattern = r'```(?:json)?\s*\n?(.*?)\n?```'
match = re.search(fence_pattern, text, re.DOTALL)
if match:
    text = match.group(1).strip()
```
这里使用非贪婪匹配，然后从中提取内容；如果找不到，保持原文本。这可以解决七成以上的包裹问题。

### 3. 从自定义标签中提取
当输出中存在类似 `<tool_call>` 时：
```python
tag_match = re.search(r'<\w+>(.*?)</\w+>', text, re.DOTALL)
# 更好的方式：提取最外层大括号对
brace_start = text.find('{')
brace_end = text.rfind('}')
if brace_start != -1 and brace_end != -1:
    candidate = text[brace_start:brace_end+1]
```
对于可能存在嵌套标签的情况，直接定位第一个 `{` 和最后一个 `}` 最稳健，即使前有文字后有结尾标签。但如果模型在同一条消息中输出了多个独立的 JSON 对象，则需要根据业务规则 (取第一个 or 合并为数组) 另行决策。

### 4. 尝试解析并修复常见错误
```python
import json
try:
    return json.loads(text)
except json.JSONDecodeError:
    pass
```
若失败，尝试修复尾部逗号、单引号：
```python
# 用简单的正则修正单引号为双引号（注意转义）
fixed = re.sub(r"(?<!\\)'", '"', text)
# 删除尾部逗号： ,\s*} 或 ,\s*]
fixed = re.sub(r',\s*([}\]])', r'\1', fixed)
try:
    return json.loads(fixed)
except:
    pass
```
这一步可以采用 `json5` 或 `demjson3` 库（需评估依赖），它们能容忍注释、尾部逗号等，但引入三方库在轻量 Skill 或 MCP 工具中需谨慎。

### 5. 最终降级
如果以上均失败，记录原始文本和错误日志，返回一个包含原始文本的字典或直接 raise 自定义异常，由上层业务决定回退策略（例如要求 LLM 重试、提取纯文本、或者人工接管）。

## 踩坑点

- **流式分块截断**  
  使用 `Completion` 流式场景，JSON 可能被切在 `{"na` 处。必须在客户端拼接完整消息（检测是否末尾有未闭合的引号/括号）后再送入解析器。
- **中文引号与全角字符**  
  某些模型会输出 `{'键'：'值'}`，需要做一次全角转半角及中文引号替换。
- **解释性文本与 JSON 粘连**  
  如 `解释：{"a": 1} 请继续`，采用 `rfind('}')` 会保证取到最后的大括号，但若后续还有有效内容就需要位置判断。
- **数组输出包裹**  
  当 JSON 是一个数组 `[{...}, {...}]` 时，`brace_start` 方法会失效。统一改用 `text.find('{')` 或 `text.find('[')` 的最小值，并配对到正确的闭合符。可以写一个辅助函数 `extract_balanced_json(text)`，利用栈实现。

## 可复用建议

在 OpenClaw 或 MCP 工具中，建议将这个解析器封装为一个独立的 `parse_llm_output` 工具函数，供所有 Skill 调用：

- 支持开关式修复策略（是否启用单引号修正、是否允许 json5）。
- 增加 `expect_type` 参数（dict 或 list），让函数做类型检查。
- 返回 `(parsed_object, error)` 元组，避免异常中断主流程。
- 与提示工程配合：在系统提示中强调“仅输出 JSON，不要包裹在代码块或标签中”，并从解析失败日志反推提示词优化点。

更进一步，可设计 **重试回路**：当解析失败时，自动将错误消息和原始片段注入到新的对话轮次，让 LLM 自己修正格式，此策略在 Agent 循环中非常有效。

## 总结

防御性解析并非要让代码变得庞大而脆弱，而是通过 **逐层剥离、多次尝试、温和降级** 的思路，将复杂的格式兼容问题收敛到一个可控的函数内。实践中，单靠这一层就能消灭绝大多数因格式造成的自动化卡点。整洁的 JSON 是理想，混乱的格式是常态，用工程手段去弥合二者之间的鸿沟，正是自动化实践者需要付出的成本。
