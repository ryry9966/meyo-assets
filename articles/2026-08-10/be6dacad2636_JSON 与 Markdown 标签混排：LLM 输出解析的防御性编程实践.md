## 背景

在基于大语言模型构建 Agent、MCP 工具或自动化插件时，我们经常要求模型输出结构化的 JSON，以便下游代码直接解析使用。理想情况下，模型应该返回纯 JSON 字符串，但实际部署中，无论提示词如何精心设计，总会遇到以下几种非预期输出：

- 包裹在 Markdown 代码块中（```json ... ```）
- 代码块带语言标识但前后包含多余空白
- 代码块被注释或强调语法污染（如 ` ```json "data"...`）
- 首部或尾部附加非 JSON 的说明文字
- 模型输出多个 JSON 块，混合普通文本

如果解析器写得过于理想化，仅用 `json.loads()` 处理原始输出，就会频繁抛出解析异常，导致自动化流程中断。本文介绍一套在 OpenClaw/Agent 上下文中可复用的防御性解析策略，用最小的依赖成本处理 JSON 与 Markdown 标签的混合格式。

## 典型问题场景

假设你有一个 MCP 服务，需要从 LLM 获取一个清单数据。你期望的返回格式是：

```json
{"action": "analyze", "targets": ["file1.py", "file2.py"]}
```

但实际收到的字符串可能是：

```
好的，这是分析结果：
```json
{
  "action": "analyze",
  "targets": ["file1.py", "file2.py"]
}
```
希望这对你有帮助！
```

或者更恶劣的情况：

```
```json
{"action": "analyze"}
```
备注：以上为初版结果。
```

如果直接用 `json.loads()` 处理，会因为前后有非法字符而报错。在自动化流水线中，这类错误会导致 Agent 后续步骤无法继续。

## 防御性解析的做法与步骤

### 1. 拒绝盲目解析：先清洗，后加载

核心思路是**从不信任原始字符串**，总是先提取可能的 JSON 部分，再尝试解析。步骤如下：

- 去除字符串首尾空白
- 尝试用正则表达式提取被 ```json 或 ``` 包裹的内容
- 如果提取失败，则将整个字符串送入备选策略
- 对提取出的候选字符串进行二次清理（去除尾随逗号、注释等常见噪声）
- 最后使用 `json.loads()` 解析，若不成功再尝试使用更宽松的解析器（如 `json5`）

### 2. 最小可用实现

```python
import re
import json

def extract_json_from_mixed(text: str) -> str | None:
    """
    从包含 Markdown 标记的字符串中提取最可能的 JSON 块。
    返回解析后的 dict，若失败则返回 None。
    """
    # 去除可能的前后空白
    text = text.strip()
    
    # 规则1: 匹配 ```json ... ``` 或 ``` ... ``` 代码块
    code_block_pattern = r"```(?:json)?\s*\n?(.*?)\n?```"
    matches = re.findall(code_block_pattern, text, re.DOTALL | re.IGNORECASE)
    
    candidates = []
    if matches:
        # 有多个代码块时，优先选择内容最长的那个（通常是数据块）
        candidates = matches
    
    # 如果未找到代码块，将整个文本作为候选
    if not candidates:
        candidates = [text]
    
    for candidate in candidates:
        candidate = candidate.strip()
        # 清洗常见噪声：开头的逗号、多余的空白行
        candidate = re.sub(r'^[,;:\s]+', '', candidate)
        candidate = re.sub(r'[,;:\s]+$', '', candidate)
        
        try:
            # 尝试标准 JSON
            return json.loads(candidate)
        except json.JSONDecodeError:
            # 可以集成 json5 库处理尾随逗号、注释等（可选）
            pass
    
    # 全部尝试失败
    return None
```

### 3. 结合 LLM 调用时的防御流程

在 OpenClaw 插件或 Agent 工具中，建议采用以下调用链：

1. 调用 LLM，获取原始响应文本
2. 使用上述 `extract_json_from_mixed` 提取解析结果
3. 若返回 `None`，不应立刻崩溃，而是记录原始输出到日志，然后降级返回一个安全的默认值或触发重试逻辑（带上更强的格式约束提示）
4. 如果对数据完整性要求高，可在解析成功后额外校验必选字段，不符合期望时同样进入降级策略

这种“尝试+降级”的模式比硬解码更能保证 Agent 长期运行的稳定性。

## 踩坑点

根据多次在 MCP 工具开发中的经验，以下几个坑需要特别注意：

- **代码块内嵌反引号**：LLM 偶尔会输出 ```` ```json {"key": "value with ```"} ``` ````。正则 `.*?` 的贪婪性要正确处理，建议使用 `re.DOTALL` 且基于结尾 ``` 做最短匹配，但遇到嵌套反引号时仍可能截断错误。可增加启发式判别：检查候选块中 `{` 与 `}` 数量的平衡，选择最可能的一个。

- **模型输出带有行内注释或尾随逗号**：标准 `json` 库无法解析这些，可选方案是引入 `json5` 或 `pyjson5` 作为容错解析器。但需权衡依赖引入的成本，对于大多数场景，强制模型输出符合规范的 JSON 并从提示词层面约束效果更好。

- **多个 JSON 块混合解释**：例如模型在列表中给出了多个对象的 JSON 块解释。应优先提取最后一个或最长的一段。通常数据块是最后一个代码块。

- **字符编码与 BOM**：极少见但致命的干扰，如果字符串开头有 `\ufeff`，`json.loads` 会直接报错。建议统一去除。

## 可复用建议

- **封装成工具函数**：将上述提取逻辑封装为 `robust_json_loads()`，放于项目 utils 层，所有 LLM 调用点统一使用。
- **补充提示词策略**：防御性解析是最后一道防线，更好的是从源头约束。在提示词中要求模型“请严格输出纯 JSON，不要添加 Markdown 标记或解释”，并给出合法输出示例。结合 few-shot 示例能大幅降低畸变率。
- **日志与监控**：将解析失败时的原始输出写入日志，并统计出现频率。这有助于发现模型切换或 prompt 退化带来的新问题模式。
- **渐进降级**：当 JSON 块提取失败时，不要直接失败，可以尝试将整个响应作为字符串赋予结构（例如作为“note”字段），让业务层自行判断是否可接受。

## 总结

让 LLM 输出结构化 JSON 是自动化 Agent 和 MCP 插件的关键环节，但真实世界的模型输出往往带有 Markdown 标记和各种噪声。通过“先提取代码块再解析”的防御性策略，配合降级逻辑，能够在保持代码简单的同时极大降低解析中断的风险。这个思路不仅适用于 JSON，也适合任何需要从非结构化文本中提取结构化数据的场景。实用、克制、可投放生产，是我们在构建 OpenClaw 生态工具时的基本设计原则。
