你在用 OpenClaw 搭 Agent、连 MCP、跑自动化脚本的时候，迟早会撞到一个很实际的问题：**AI 输出不稳定，角色感忽强忽弱，甚至关键流程里“忘了自己该干什么”。** 你把系统提示词塞进每个任务里，结果越维护越乱，跨项目复用几乎不可能。

OpenClaw 的 `IDENTITY.md` 就是针对这个场景设计的。它不是又一个提示词模板，而是一个**结构化、可进化的 AI 身份文件**，专门给 Agent 提供长期记忆和运行基线。这篇文章不会空谈概念，只说工程上的用法、坑点，以及我自己的复用习惯。

---

## 背景：为什么系统提示词不够用了

多数人最开始的做法是在每次调用 LLM 时，把角色描述、工具使用规则、输出格式全部塞进 `system prompt`。这在原型阶段没问题，但一旦：

- 同一个 Agent 需要跨多个 task 保持同一行为；
- 不同环境（开发/测试/生产）需要略微调整角色参数；
- 团队里多人共用同一个 Agent 骨架，

单纯的 prompt 拼接就会带来大量重复、不一致和调试噩梦。

OpenClaw 的解决思路是：**把“我是谁”“我会用什么工具”“我必须遵守什么规则”抽离成一个独立文件，由运行时注入。** 这个文件就是 `IDENTITY.md`。

---

## IDENTITY.md 到底是什么

在 OpenClaw 项目根目录下，你可以放置一个 `IDENTITY.md`，它会被 Agent 运行时自动读取，作为**最高优先级的身份描述**，附加到每次 LLM 交互中（具体行为取决于你使用的插件或 Runner）。

关键不是文件名，而是它的**结构化约定**。社区实践下来，一个可靠的 `IDENTITY.md` 通常包含四块：

1. **核心身份（不可变）**：名称、定位、语气、能力边界；
2. **工具链声明**：明确列出 MCP 工具、插件，以及何时使用；
3. **硬约束**：绝对禁止的行为、内容安全、输出格式限制；
4. **可进化区域**：允许 Agent 在执行中更新的运行时记忆、用户偏好等。

第四块是 `IDENTITY.md` 区别于静态 system prompt 的最大特点——它是一份“活文档”。

## 实际做法：让身份随任务自我调整

下面是一个简化但可用的 `IDENTITY.md` 结构（摘自我自己的实验项目）：

```markdown
# IDENTITY

## 核心身份
我是 OpenClaw Dev Assistant，专注帮助用户编写、调试和部署 OpenClaw 插件与自动化流程。
语气：务实、直接、工程化。不提供非技术建议。

## 工具链
- 文件系统 (MCP file tool)
- Shell 命令执行 (bash)
- Slack 通知 (slack-mcp)
- 浏览器控制 (playwright)
触发规则：用户提到“部署”时必须使用 Slack 通知；涉及代码修改前必须先备份文件。

## 硬约束
- 绝不修改 /etc 下的系统配置
- 输出代码时不要包含 token 或密钥
- 所有解释必须附带可复现步骤

## 运行时记忆
<!-- 以下区域由 Agent 在任务中自行更新 -->
- 用户偏好脚本语言：Python (默认)
- 长期目标：暂无
```

### 如何启用可进化性

单独一个 `IDENTITY.md` 并不会自动更新。你需要配合 **OpenClaw 的文件读写能力**，让 Agent 在识别到重要信息时主动回写。

一个可行模式是：在任务描述中明确给 Agent 权限：

```text
当任务涉及用户偏好、长期目标或关键上下文变更时，
请更新 IDENTITY.md 中的“运行时记忆”区域。
只追加或修改该区域，不更改其他部分。
```

经过三五次交互后，Agent 会把“用户喜欢 YAML 配置而不是 JSON”“项目当前处于私有测试阶段”等信息沉淀进去，后续会话无需重复说明。

## 踩坑点：三个容易翻车的地方

### 1. 身份描述过长，反被 LLM 忽略

有人把 `IDENTITY.md` 写成了一本操作手册，大段 Markdown 表格和条件分支。结果是 LLM 因为上下文窗口压力或注意力衰减，直接忽略后半段。

**解法**：保持核心身份在 200 字以内，硬约束用列表，不要超过 8 条。细则放到外部文档，仅在 `IDENTITY.md` 里引用路径。

### 2. 允许 Agent 修改身份文本造成漂移

如果你给了 Agent 自由修改“核心身份”的权限，大概十轮对话之后它会把自己变成“全能 AI 助手”，原有的人设和约束荡然无存。

**硬性规则**：只开放“运行时记忆”区域的写入权限。核心身份、工具链、硬约束三段必须保持只读。你可以在任务 prompt 里用 Markdown 注释强化这一点，或者用文件权限做物理隔离（比如把不可变部分放在另一个文件中，由系统注入）。

### 3. 工具链声明与实际可用工具不同步

`IDENTITY.md` 里写了一大堆工具，但实际 MCP 配置里没提供，结果 Agent 一开始就会尝试调用不存在的方法，导致失败循环。

**建议**：工具链部分必须由**部署脚本自动生成**，不要手写。写一个简单的 hook，在启动 Agent 前扫描 `mcp.json` 或插件配置，生成工具清单并注入到 `IDENTITY.md` 中。这样永远保持同步。

## 可复用建议

- **模块化身份片段**：不要把 `IDENTITY.md` 写成一个巨型文件。把可复用的部分（比如通用的代码审查规则）拆成 `identity/base_code_review.md`，在 OpenClaw 的配置里用 merge 逻辑拼装。这样跨项目复用时只改差异部分。
- **版本化你的身份文件**：AI 行为对提示词极其敏感。把 `IDENTITY.md` 纳入 Git 管理，并在每次调整后记录实际效果变化。我习惯在 commit message 里注明“v2.3: 增加硬约束 no-sudo，解决了 Agent 建议 rm -rf / 的问题”。
- **利用环境变量做差异化**：用占位符，比如 `${USER_NAME}`，在运行时由 OpenClaw 替换。这样同一个身份文件可以在多个环境中使用，而 AI 看到的是最终解开的文本，不会泄露模板变量。
- **设置身份刷新策略**：长期运行的 Agent，“运行时记忆”部分会不停增长，最终超出有用范围。加一个周期性清理逻辑：比如每 7 天或当行数超过 30 行时，由 AI 自己总结并压缩记忆。把压缩算法写成固定规则，避免 AI 随便丢弃重要信息。

---

## 总结

`IDENTITY.md` 不是什么银弹，它只是一个把“AI 角色管理”工程化的手段。它能解决的问题很明确：**让 Agent 的行为在长期运行和多场景复用中保持一致性，并降低维护成本。** 但它解决不了提示词本身的根本脆弱性，也没法替代充分的测试。

如果你已经在用 OpenClaw 跑稍微复杂一点的自动化流，值得花半小时把散落在各处的 prompt 收敛到一个结构化的 `IDENTITY.md` 里。然后设置好权限边界、生成工具链、配上版本控制，你会发现后续的调试和迭代顺畅很多。

> 最终，给 AI 一个身份，不是让它更像人，而是让它更可预测。
