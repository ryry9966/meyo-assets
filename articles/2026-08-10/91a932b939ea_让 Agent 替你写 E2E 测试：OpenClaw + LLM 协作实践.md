## 背景：E2E 测试的“维护债”

端到端测试是保障用户流程完整性的最后一道防线，但它的维护成本一直是前端团队的痛点。用例越积越多，每一步都依赖脆弱的 UI 选择器；产品迭代一频繁，测试脚本就成片飘红。更尴尬的是，失败往往不是因为功能真坏了，而是某个按钮的 class 变了，或者异步加载的等待时间不够。

过去两年，社区把希望寄托在 AI 自动生成测试上。GPT-4 或 Claude 确实能根据截图或 DOM 片段写出看起来像样的测试代码，但落地时问题很多：生成的选择器不稳定、不懂你的业务数据、无法处理登录态和多步骤交互。于是我们开始思考，能不能让 AI 不只“写”测试，还能“跑”测试，并且接管整个“编写—执行—修复”的闭环？这就是 Agent 协作的思路。

## 问题：AI 写测试的三大失效模式

单纯把页面 HTML 丢给大模型让它输出 Playwright 脚本，通常会遇到：

1. **选择器幻觉**：模型倾向于用长串 CSS 选择器，比如 `.ant-btn-primary > span`，页面结构稍有调整就断裂。  
2. **时序假阳性**：代码里写死 `waitForTimeout(3000)`，在慢网环境下可能仍然不够，快网又浪费时间。  
3. **上下文断裂**：一次对话只能覆盖单个用例，无法复用登录、前置状态，也感知不到跨页面的流转逻辑。

要让 AI 真正产生工程可用的测试，需要给它一个能实际操作浏览器的环境，让它通过“试错”来自我校正。这正是 Agent 和传统 Tool-use 的区别：Agent 会主动观察页面状态，调整行为，而不是被动回答。

## 做法：OpenClaw Agent + Playwright MCP 的协作流水线

这里我们使用 OpenClaw 作为浏览器自动化基座，它内置了本地可控的浏览器实例，并通过 MCP（Model Context Protocol）对外暴露成 LLM 可用的工具。整体流水线分为三步：探索、生成、自愈。

### 1. Agent 探索：形成可执行的页面知识

用 OpenClaw 启动一个带 session 的浏览器上下文（已有登录态或 mock 数据），让 LLM 驱动 Agent 描述关键页面和用户流。Agent 可以调用 `browse_snapshot` 获取可访问性树（axe-core）、`browse_take_screenshot` 截图、`browse_click` 执行点击，并把返回的状态编入上下文。

这一步不是直接用代码生成测试，而是让 Agent 生成一份**操作日志**——记录了每一步用到的**稳定标识**（我们强制使用 `data-testid` 或文本锚点）、等待策略（`waitForResponse` / `waitForSelector`）和断言点（某个文本是否可见）。

### 2. LLM 转译成测试代码，并支持 Page Object 模板

拿到操作日志后，再用 LLM 将它转译成 Playwright 代码。我们预先提供了 Page Object 骨架模板，要求模型必须把定位器封装到 Page 类里，并且只允许使用 `page.getByTestId` 或 `page.getByRole` 等语义 API。

生成的代码会经过一次静态校验：检查是否引用了未定义的 fixture、是否包含全网断言（如 `toHaveURL` 带死域名）、是否有多余的 `waitForTimeout`。校验通过的代码会被提交到临时分支，触发 CI。

### 3. 失败自愈：让 Agent 根据错误信息修复

CI 中一旦有用例失败，Agent 会收到 Playwright report（截图、trace、错误日志）。它可以再次打开浏览器，在相同路径上重放，对比预期与实际状态的差异。如果是简单选择器过期，Agent 会尝试用当前页面重新定位，并提交补丁；如果是业务逻辑真的变了，则自动给测试打上 `skip` 标记并通知人工评审。

这套流水线在内部运行了约两个月，新增功能的 E2E 测试 80% 的初稿由 Agent 生成，人工修正时间从平均 25 分钟降到 5 分钟。更关键的是，老的测试不再因为 UI 微调就大量失败。

## 踩坑点 & 可复用建议

**坑 1：Agent 探索时盲目点击导致脏数据。**  
Agent 很可能会点到“删除”按钮或提交空表单，把测试环境搞乱。解法是为 Agent 的 session 启用**只读模式**（OpenClaw 支持 `--read-only` 标记拦截写请求），或者使用数据库快照/沙箱环境，并设定点击前需二次确认的规则。

**坑 2：生成的测试过于贴近当前 UI 的“快照”。**  
模板里的 Page Object 虽然限制了定位器类型，但 LLM 还是会忍不住把页面标题、列表数量等过多细节作为断言。我们增加了一条 prompt 约束：断言仅验证业务关键路径（如付款成功、订单生成），其余 UI 元素只做存在性而不检查精确内容。

**坑 3：自愈不够智能，容易覆盖真实缺陷。**  
如果一个测试失败是因为后端接口返回了错误数据，Agent 可能会把它当成正常的更新并“修复”预期，导致测试丧失防护力。我们给自愈步骤设置了严格的阈值：只有当失败原因是 NoSuchElement、Timeout（非网络类）或者定位器失效时才允许自动修复，任何断言失败都直接抛给人。

**可复用建议：**  
- 预先在页面注入 `data-testid` 至关重要。可以和前端约定，所有可交互元素自动生成稳定 testid。  
- 把 Agent 的能力封装成 MCP tool，方便在不同项目里复用。你甚至可以写一个 `generate_e2e` 的 MCP 服务，输入 PRD 描述或用户故事，直接输出测试初稿。  
- 人机协作流程要短：Agent 的补丁以 Draft PR 形式出现，人工只用点 “approve” 即可合入，避免 review 负担。  
- 永远不要让 Agent 直接操作生产环境，仅限预发布/staging，并且做好网络隔离。

## 总结

AI 写测试不是把页面 dump 给 GPT 就结束的魔法，而是一套需要精心设计的工程流水线。OpenClaw 这种可被 LLM 操控的真实浏览器环境，加上 Agent 的观察-执行-修复闭环，才让“自动化编写自动化测试”变得可信。

如果你已经在用 Playwright，不妨试着把第一个用例的生成交给 Agent，然后逐步把维护也自动化。当测试不再只是消耗你的时间，而是能自我进化时，E2E 的 ROI 会发生质变。
