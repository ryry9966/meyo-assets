## 背景：Agent 为什么需要 Heartbeat

在 OpenClaw 生态里搭建自动化助手时，很多任务并不是瞬时完成的。例如通过 MCP 调用外部服务生成长报告、触发 CI/CD 流水线、等待人工审批节点——这些异步流程会让 Agent 进入“等待中”状态。为了让上游用户、调度器或前端感知任务是否存活、何时完成，我们必须设计一套 heartbeat 机制。

Heartbeat 在这里有两层含义：一是**连接保活**，确认 Agent 与平台、外部系统之间的长连接未断开；二是**状态同步**，持续告知“我还在处理，以及当前进展”。本文聚焦在后者，也就是 Agent 等待异步结果时，选择轮询（Polling）还是推送（Push）来同步任务状态。

## 问题：两种模式的根本差异

轮询模式下，Agent 或以 Agent 为中心的中控模块，按固定间隔向任务执行端（或 API）发起查询：“任务好了吗？” 推送模式则反过来，执行端在状态变化时主动回调 Agent，或者通过长连接推送事件。

两者的权衡点很明确：

- **延迟**：轮询间隔决定了平均延迟（interval/2），推送几乎是实时。
- **资源开销**：轮询会产生大量无效请求，推送只需维护少量长连接。
- **复杂度**：轮询开发简单，只需一个循环 + HTTP 请求；推送需要处理连接管理、鉴权、重连、背压。
- **网络约束**：轮询天然穿透 NAT/防火墙，推送则要求 Agent 端暴露公网端点，或依赖 WebSocket/SSE 等长连接通道。
- **可靠性**：轮询对短暂服务中断更宽容，推送如果连接断开容易丢失事件。

对于 OpenClaw 的插件/MCP 用户来说，这两条路都有落地空间，但需要根据部署场景取舍。

## 做法：在 OpenClaw 中落地两种 Heartbeat

### 1. 轮询式心跳

利用 OpenClaw 的 cron 或 scheduler 插件，可以很轻量地实现轮询。假设 Agent 提交了一个异步任务获得 `taskId`，我们在 Agent 的流程里增加一个循环步骤：

```yaml
- name: Wait for task completion
  loop:
    until: "result.status == 'completed'"
    interval: 5s
    timeout: 10m
  action: check_task_status
```

内部实现就是每隔 5 秒调用任务状态 API。需要注意：

- 设置合理的超时时间，否则 Agent 可能永远阻塞。
- 对 API 做幂等处理，避免重复请求引发副作用。
- 如果在 serverless 环境中运行，长时间轮询会导致函数超时，此时更适合把轮询转移到外部系统（如专门的状态检查定时器），然后通过回调唤醒 Agent。

### 2. 推送式心跳

推送的典型实现是注册 Webhook，或者利用 MCP 的 notifications 通道。当 OpenClaw Agent 作为 MCP Client 时，可以要求 Server 在状态变化时发送 `notifications/status`：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/status",
  "params": {
    "taskId": "abc123",
    "status": "completed",
    "result": "..."
  }
}
```

Agent 端需要常驻监听，这在 OpenClaw 里可以通过 `mcp server` 或更简单的 HTTP 服务实现。如果网络环境限制较多（如 Agent 在本地运行，难以接收外部请求），可以选择 WebSocket 让 Agent 作为客户端连接一个消息中间件，由任务执行端将状态推送到中间件，再转发给 Agent。

## 踩坑点

1. **轮询雷区：速率限制与惊群**
   多个 Agent 同时轮询同一个 API 时，很容易触发速率限制。一定要在客户端侧引入指数退避和抖动，或者引入共享缓存，由单一 worker 轮询后广播结果。

2. **推送的“静默断开”**
   WebSocket 或 SSE 连接可能因防火墙、代理超时而中断。必须实现应用层心跳（ping/pong），并在断开后自动重连，同时补拉可能在中断期间丢失的事件。不要仅依赖 TCP keepalive。

3. **无序事件和幂等**
   推送可能出现乱序，需要在 Agent 侧基于 `version` 或 `timestamp` 做冲突检测。同时保证处理逻辑幂等——同一个完成事件发送两次不应导致重复动作。

4. **本地开发的网络阻碍**
   在本地跑 OpenClaw Agent 时，推送要求的内网穿透（如 ngrok）增加了调试难度。很多团队因此选择早期用轮询验证逻辑，生产切推送。轮询“先跑通，后优化”的策略是务实的。

## 可复用建议

- **混合模式**：先轮询，如果任务预估时间较长（>30s）且有推送能力，则动态升级为长连接推送。轮询作为降级通道存在。
- **Heartbeat 契约设计**：状态确认不仅要有 `status`，还应包含 `progress、eta、lastHeartbeatAt`，方便上层展示和异常检测。
- **监控与告警**：无论哪种模式，都应记录心跳缺失的时间，并设置告警阈值（例如三倍心跳间隔无响应）。
- **利用 OpenClaw 的插件机制**：将轮询/推送逻辑封装成可复用的 Plugin，既能在不同 Agent 间共享，又能通过配置灵活切换通道。

## 总结

轮询和推送并不是非此即彼的宗教选择。在 Agent heartbeat 设计中，它们更像是“低开发成本、高鲁棒性”与“低延迟、高吞吐”之间的工程权衡。在 OpenClaw 这类自动化框架下，先以最小可用方式（通常是轮询）打通链路，再根据实际延迟要求、网络拓扑和运维成本，逐步引入推送并保留轮询作为逃生通道，是值得推荐的务实路径。毕竟，heartbeat 的核心目的不是炫技，而是让异步协作的各方都能确信——“我还活着，事情在推进”。
