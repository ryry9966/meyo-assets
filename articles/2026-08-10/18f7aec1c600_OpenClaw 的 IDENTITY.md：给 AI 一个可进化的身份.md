## 问题：静态身份让 Agent 越跑越“死”

我们给 OpenClaw 里的 Agent 定义角色、指令、知识库，跑几个任务似乎一切正常。但时间一长，这东西就显出尴尬的一面：它不会从错误里长记性，不会主动优化自己的行为策略，昨天刚踩过的坑今天原样再踩一遍。你给的提示词再精细，也只是一次性的“出厂设定”，用久了反而变成束缚。

需求的根源并不复杂：Agent 在执行真实任务时，持续产生有效的新信息——用户偏好、成功路径、环境变动、纠正后的知识——可这些信息绝大多数被丢弃了。剩下的那一小撮，靠人工整理、重新注入系统提示或外部记忆，效率低、容易遗漏，而且没有一个“身份级”的锚点来承载它们。

OpenClaw 的 `IDENTITY.md` 正是针对这个问题设计的：它不是简单的角色描述，而是一个可读、可写、可版本管理的“身份文件”，让 Agent 在可控的范围内自行进化。

## IDENTITY.md 是什么

本质上，它是一个带结构化约束的 Markdown 文件，存放在 Agent 的工作目录下，随任务执行与记忆更新而演进。结构大致如下：

```
---
version: 1.2.0
immutable_core: [principles, role]
evolution:
  enabled: true
  strategy: incremental_summary
  max_self_improvement_entries: 20
---

# 身份声明

## 角色
技术文档助手，专注环境搭建排障。

## 不可变原则 (immutable)
- 回答必须包含可复现步骤。
- 不猜测未验证的配置值。

## 长期记忆
- 用户环境: Ubuntu 22.04, Python 3.10, OpenClaw v2.1
- 常遇问题: 插件 MAVEN_OPTS 未传递到子进程

## 自改进记录 (self-improvement)
- 2025-03-19: 学会了用 ldconfig 刷新共享库缓存，解决 90% 的 “找不到 .so” 问题。
- 2025-03-21: 发现该用户不喜欢 Markdown 折叠块，此后回答改用分段标题。
```

核心逻辑：  
- **不可变区域**保证 Agent 不会因为自改而忘记根本角色或安全指令；  
- **长期记忆**存放事实性知识，可由 Agent 在任务中通过函数调用更新；  
- **自改进记录**是进化输出的落点，存放策略性、经验性的抽象总结。

文件本身既是提示词的一部分，也是记忆的真实存储。OpenClaw 每次构造系统提示时都会注入这个文件的最新版本，进化就自然生效。

## 怎么让它“进化”起来

步骤不复杂，但需要精细设计触发与写入机制。

### 1. 创建初始模板
先在 Agent 目录下手动创建 `IDENTITY.md`，设定 immutable 内容、初始化长期记忆，自改进记录留空或写一条初始教训。推荐使用 YAML frontmatter 锁定配置，降低解析出错概率。

### 2. 配置进化钩子
OpenClaw 支持在任务或会话结束后执行一个 `evolution_hook` 脚本。典型流程：

1. 获取当前 `IDENTITY.md` 的内容。  
2. 收集本轮对话中重要的新事实、用户反馈、成功或失败模式。  
3. 调用 LLM，给一个极简 Prompt，要求输出符合自改进字段格式的条目（通常 1–3 条最佳）。  
4. 将新条目追加到 self-improvement 区域，检查条目数量上限，必要时删除最旧的非关键条目。  
5. 写入文件并递增版本号。

关键约束：Hook 严禁触碰 immutable 区域和 YAML 预设配置；操作越界需直接中止并告警。

### 3. 设定进化策略
我推荐从最简单的 `incremental_summary` 开始——每次只根据本轮对话生成增量总结，不重塑已有记忆。待稳定后再尝试 `merge_and_dedup` 或 `retrospective` 策略，后者会定期回顾多条自改进记录，提炼出更凝练的原则。

### 4. 启用 Git 追踪
将 Agent 的 `IDENTITY.md` 纳入版本控制。进化就是一次 commit，回滚就是 `git revert`。这比任何自定义的备份机制都可靠。

## 踩坑记录

经过多次迭代，我遇到的最具破坏性的问题有以下三个：

- **自改进“口嗨”**  
  早期 Hook 直接让 LLM 生成经验总结，但没有任何事实验证。结果 Agent 把一次偶然成功当成通用规律写入自我改进，后续任务执行反而被带偏。解决方式：增加一个简单过滤步骤，要求自改进条目必须附带“支持证据”——即引用本轮对话中的具体消息 ID 或成功日志片段。

- **循环覆盖陷阱**  
  如果进化策略是每次完全重写整个 self-improvement 区域，LLM 很容易把前几次的有效改进丢弃，重蹈覆辙。这就是为什么最初推荐增量追加而非全量重写。追加后再按条目上限清理，可以用“最后修改时间+引用次数”做权重排序。

- **写入冲突导致文件损坏**  
  OpenClaw 可能在同一时间有多步操作想更新 `IDENTITY.md`。没有锁机制时，文件会被并发改写弄乱。简单方案：在 Hook 内实现单文件锁（使用 `flock` 或类似原语），超过 2 秒未获取锁则放弃本次更新并记录日志。

## 可复用建议

1. **把身份当成代码仓库，不是日记本**  
   强制所有 Agent 的 `IDENTITY.md` 放在独立 git 仓库中，配置 pre-commit 校验 schema。这样即便进化出了问题，也可以 diff 审查、revert 恢复。

2. **进化频率“宁慢勿乱”**  
   不要每个对话回合都触发进化。建议设置“有效对话轮次阈值”或“新信息量触发器”——比如本轮对话中出现了不在已有长期记忆里的实体、或者用户给出了明确纠正，才启动 Hook。

3. **建立人工审核通道**  
   在生产环境，将自改进记录先写入一个 `_proposed` 文件，通过 MCP 服务推送到审核队列，由人工或规则引擎 Approve 后再合并回正式 `IDENTITY.md`。这样既保留了自我进化的效率，又兜住了质量底线。

4. **用不可变区域做“安全锚”**  
   将合规条款、输出格式限制、禁止使用的词汇等放入 immutable 区域，并在 Hook 解析时明确设置写保护。这是防止 Agent 行为偏航的最后一道硬防线。

5. **监控进化信号**  
   定时统计 self-improvement 条目的数量、长度、变化趋势，如果出现条目数量激增但每条信息量递减，很可能意味着进化策略在退化，需要介入调整 Prompt 模板。

## 总结

`IDENTITY.md` 不是又一个花里胡哨的 Agent 配置文件，而是将 “持续学习” 从口号变成工程实践的关键载体。它让每次任务的经验不再随风而逝，让 Agent 从“每次重启就失忆”的工具人，变成能越用越顺手的协作者。唯一要留神的是：不给进化加边界，就容易长成想都想不到的东西。守住 immutable 底线，版本管理做透，这个机制就可以放心投产。
