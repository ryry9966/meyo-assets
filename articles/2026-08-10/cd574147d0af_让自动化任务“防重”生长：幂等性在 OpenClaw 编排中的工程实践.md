# 让自动化任务“防重”生长：幂等性在 OpenClaw 编排中的工程实践

## 背景：一个被重复执行的告警聚合任务

最近在 OpenClaw 上跑了一个自动化流程：从 Kafka 拉取系统告警，按团队维度聚合后通过 MCP 插件写入工单系统，并在钉钉群发送通知。上线初期一切正常，直到某天凌晨，服务器在极短时间内发出相同的三条重复告警 —— 于是同一个工单被创建了三次，群里也连刷三条 @全体成员。

排查发现，问题出在告警网关的重试超时逻辑：上游认为消息发送失败，实际上 MCP 写入已成功，重试触发了任务二次执行。这不是一个复杂 Bug，但暴露了自动化的一个关键缺口 —— **任务缺乏幂等性设计**。

## 问题：为什么“重复执行”会变成事故？

在 OpenClaw 这类编排框架中，任务重复执行常源于以下几类场景：

- **消息队列 at-least-once 投递**：Kafka、Redis Stream 等在 rebalance 或超时重试时可能重复投递同一条消息。
- **定时任务重叠**：cron 调度的任务执行时间超过间隔，新实例在旧实例结束前又启动。
- **工作流重试策略**：Agent 或 MCP 调用失败后，框架自动重试整个节点，导致上游已成功操作的重复执行。
- **手动回放/补偿**：运维人员为修复数据手动回放事件，若任务不幂等就会产生副作用。

“非幂等任务”的典型表现是：多次执行积累副作用，比如重复创建资源、多次扣减库存、重复发送通知，最终数据错乱或资源浪费。要避免这些，我们需要让任务本身的执行不因重复而改变终态 —— 这即是幂等性。

## 做法：在 OpenClaw 任务中落地幂等保证

我踩完坑后，在 OpenClaw 里沉淀了一套轻量幂等设计模式，不依赖外部复杂组件，仅靠任务本身和存储层完成。

### 1. 为每一次“业务意图”生成幂等键

核心思路是：在任务触发时，提取一个能唯一标识本次业务操作的键。例如告警聚合任务中，我用 `{source}.{team}.{alert_window_ts}` 生成幂等键，形如 `prometheus.team-backend.1710000000`。这个键会贯穿整个流程，写入时作为去重依据。

在 OpenClaw 的流式处理节点中，我在任务入口做了键生成：

```yaml
- id: gen_idem_key
  type: transform
  input: ${trigger.event}
  script: |
    const ts = Math.floor(event.time / 300) * 300; // 5分钟窗口
    return `${event.source}.${event.team}.${ts}`;
```

### 2. 利用存储层唯一约束实现“尝试写入”而非“检查后写入”

避免 `if not exists then insert` 的竞态条件是关键。我直接在工单系统的创建 MCP 调用中，将幂等键作为 `idempotency_key` 传入，后端数据库表对 `idempotency_key` 建立唯一索引。如果工单系统不支持幂等键，就用独立状态表：

```sql
CREATE TABLE task_idempotency (
    key VARCHAR(255) PRIMARY KEY,
    status VARCHAR(20) NOT NULL DEFAULT 'processing',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

在 OpenClaw 里调用这个表：

```yaml
- id: check_or_insert
  type: mcp_call
  server: db_ops
  tool: execute_sql
  params:
    sql: |
      INSERT INTO task_idempotency (key, status) VALUES (?, 'processing')
      ON CONFLICT (key) DO NOTHING
    params: [${gen_idem_key.output}]
```

只有当插入成功（影响行数 1）时，才继续执行下游核心逻辑；若返回 0，则判定为重复执行，可以跳过或等待上一次结果。

### 3. 为状态迁移设计可重放的步骤

有些任务包含多个外部操作，比如先创建工单再发通知。我采用“小步骤检查点”模式，每一步成功后记录状态，步骤间允许重放时检查已完成的动作。

例如在 `task_idempotency` 表中添加 `step` 字段，记录已完成步骤列表。重入时按序检查，已完成的步骤直接跳过。这样即使任务在中途失败被重试，也只会执行未完成的部分，而不会重复创建资源。

### 4. 在定时任务中增加分布式锁

对于可能重叠的 cron 任务，除了幂等键，我还加了基于数据库的分布式锁（如 `SELECT ... FOR UPDATE NOWAIT` 或利用 `INSERT ... ON CONFLICT` 实现锁抢占）。这防止了控制面并发执行，配合幂等键使任务无论被调度几次都安全。

## 踩坑点

- **幂等键范围设计不当**：曾用一个太粗粒度的键（仅基于团队），结果同一窗口不同告警源的告警被错误去重，导致漏掉工单。键的粒度必须精确到“一次业务事件”。
- **重试时直接跳过引发的空洞**：早期方案中，如果查到幂等键存在就直接 `return`，但上次执行可能未完成，结果留下一个 `processing` 状态的工单。实际应该轮询状态或通过回调获知结果，而非简单丢弃。
- **MCP 插件内置重试叠加**：有的 MCP 插件内部也有重试机制，两次重试叠加产生多余写入。需要控制 OpenClaw 层的重试策略与插件自身的一致，通常是让插件返回幂等错误码，OpenClaw 将状态记为成功以避免再次尝试。
- **只做了幂等却忘记了通知降噪**：即使任务幂等了，告警通知还是多次发出。最终在通知节点前也加了频率控制，根据幂等键和通知时间窗口限流。

## 可复用建议

- **所有对外写操作都应该携带幂等键**，无论是数据库写入、API 调用还是消息发送，把它当作任务的基本契约。
- **优先使用“原子检查并执行”而非“检查-执行”两步模式**，利用数据库唯一约束或支持幂等的 API（如 Stripe、微信支付等）自带的 `idempotency_key`。
- **在 OpenClaw 中把幂等当成一个可组合的算子**，可以写成通用的 `idempotency_gate` 函数节点，输入 key 和超时配置，后续节点只在首次执行时触发。
- **监控重复触发频率**：为幂等键命中次数设置指标，过高可能意味着上游重试风暴或键设计有误，早期发现。

## 总结

自动化任务的可靠性，不只体现在它能稳定运行，更体现在它被意外重复执行时，不会带来额外破坏。幂等性不是额外需求，而是任务设计的默认姿态。在 OpenClaw 的实际使用中，生成唯一业务标识、利用存储约束原子化、配合状态检查点，就能在不引入复杂中间件的前提下，低成本地构建“防重”能力。

下一次你在凌晨收到重复告警时，希望看到的不是三条工单和三次全员通知，而是一条工单加上一条“重复已忽略”的日志 —— 这就是幂等设计带给自动化的安全感。
