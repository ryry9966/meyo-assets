## 为什么需要 Git 自动化

你是否也在重复这样的操作：写完一段代码，`git add`，然后盯着命令行纠结提交信息怎么写？“fix bug”“update code”显然不合格，团队规范要求 `type(scope): description` 格式，还要写清楚改动原因。一天下来，光是在提交信息上消耗的心力就不少。更烦人的是，功能开发到一半需要切出去修一个线上问题，分支命名、切换、合并之后，大脑上下文已丢了一半。

这些问题单靠记命令解决不了，本质上是 Git 操作与开发者思考过程之间存在一道手动翻译的鸿沟。如果我们能让 AI 助手安全地读取暂存区变更、生成符合规范的提交信息，甚至帮你新建分支、查找历史，就能把“用什么命令、怎么写描述”完全外包出去，你只需要确认即可。

## 选型：为什么用 MCP 而不是普通脚本

常规思路是写一个 Shell 函数，调用 LLM API 生成提交信息，再用 `git commit -m` 顶上去。但这种方式有两个硬伤：一是无法让 AI 真正“看见”仓库的完整上下文（如最近提交历史、当前分支、未跟踪文件等），只能你手动喂；二是与 Agent 工作流割裂，每次还得手动触发、复制粘贴。

Model Context Protocol (MCP) 正好解决了这个问题。通过实现一个轻量的 Git MCP 服务器，把 Git 操作抽象成标准工具（tools），Agent 就可以在任何需要的时候自行调用。比如它可以先 `git status` 查看状态，再 `git diff` 读取变更，最后决定如何提交；如果发现当前分支混乱，还能列出分支并帮你切换到正确的分支。所有这些都是在 Agent “脑内”自动发生的，不必打断你的编码流。

在 OpenClaw 这类 Agent 框架里，接入 Git MCP 服务器只需定义工具列表，然后让 LLM 在有需要时调用。下面给出一个可落地的方案。

## 搭建步骤

### 1. 部署一个 Git MCP 服务器

社区已有开箱可用的 `@modelcontextprotocol/server-git`，但直接使用会因为路径限制、权限问题在本地环境中折腾一阵。更稳妥的方式是自己实现一个最小可用版本，核心工具包括：

- `git_status` — 返回工作区和暂存区状态
- `git_diff_staged` — 返回暂存区差异（用于生成提交信息）
- `git_log` — 最近 N 条提交记录
- `git_branch` — 列出本地分支、当前分支
- `git_checkout` — 切换或创建分支
- `git_commit` — 执行提交（危险操作，需要确认机制）

这个 MCP 服务器用 Python（FastMCP）或 Node.js 实现都行，暴露在本地 stdio 通道。所有读写 Git 的操作都在用户本机完成，无需外部服务。

**注意：** 服务器的 `run_command` 必须严格过滤危险指令，比如禁止 `push --force`、`reset --hard` 等，避免 Agent 失控。对每次外发的命令记录到日志。

### 2. 在 OpenClaw 中挂载工具

假设你已经在使用 OpenClaw 作为本地 Agent 助手，配置文件中加入：

```yaml
mcp_servers:
  - name: git-local
    command: ["python", "/path/to/git_mcp_server.py"]
    args: []
```

启动 Agent 后，它会自动加载这些工具，并在遇到相关需求时调用。只需对 Agent 说“帮我提交暂存区代码”，它就会执行 `git_status` → `git_diff_staged` → 生成提交信息 → 等你确认后 `git_commit`。

### 3. 设计一个智能提交流程

为了安全且高质量，提交流程分四步：

1. **检查状态**：`git status` 如果暂存区为空，提醒用户先 `git add`。
2. **生成提交信息**：读取 `git diff --staged` 和最近 5 条 `git log --oneline`，让 LLM 分析变更意图，生成 Conventional Commits 格式的建议，并附带简短的改动说明。提示词中要强调“只描述事实、不臆测意图”。
3. **用户确认**：Agent 在终端或聊天界面展示信息，等待 `yes/no` 确认。**绝不自动提交**。
4. **执行并反馈**：提交成功后报告 commit hash 和摘要。

对于分支管理，Agent 可以根据你的描述（如“创建 fix/login-redirect 分支从 main 拉出”）自动校验当前是否有未提交改动，确保工作区干净后再 `git checkout -b`。

### 4. 集成到日常编辑器或终端

完成上述后，你可以通过 OpenClaw 的前端聊天面板、VS Code 插件或终端命令行与 Git Agent 交互。真正好用的时候，你可能不会特意打开一个对话窗口，而是用快捷键唤起一个输入框，说“提交暂存区”或“切到新分支 feature/payment”，回车，Agent 在后台完成余下操作。这层体验可以用 OpenClaw 的自定义命令和快捷操作来实现。

## 踩坑记录

**1. 非暂存区变更干扰**  
Agent 调用 `git diff` 时默认是工作区未暂存的内容，如果你只希望 AI 看到暂存区，必须明确使用 `--staged`，否则生成的提交信息会张冠李戴。

**2. 中文和特殊字符**  
如果你的代码注释或变更文件中包含中文、emoji，LLM 可能误以为这些是变更意图，导致提交信息离题。可以在 prompt 中明确“忽略代码注释和字符串字面量，只关注逻辑变更”。

**3. 大 diff 超出上下文窗口**  
一个巨型 commit 的 diff 可能上万行，直接喂给 LLM 会被截断，且 token 消耗巨大。需要做 diff 压缩：只保留文件名和关键增删行（如使用 `diff --stat` 先判断，再针对性截取前 N 行）。更好的做法是从工程上避免巨大 commit。

**4. 权限与安全**  
如果把 `git push` 也交给 Agent，一旦生成错误的分支名或覆盖远端，恢复成本极高。强烈建议 CI/CD 流程仍由人工或受控流水线触发，Agent 只负责本地操作。建议在 MCP 服务器里维护一个操作白名单。

**5. Agent 的“过度热心”**  
有时 Agent 在你的上下文里读到“提交”一词，就可能尝试调用提交工具，哪怕你没有暂存任何文件。需要让工具在暂存区为空时返回明确的“不能提交”信息，并让 Agent 的 system prompt 明确：仅在用户显式要求 Git 操作时才动用这些工具。

## 可复用建议

- **从“建议模式”开始**：头一两周只启用 `git_diff_staged` 和 `git_log`，让 Agent 产出提交信息，你手动执行。逐步建立信任后再开放 `git_commit`。
- **团队使用统一的提交规范**：在 Agent 的系统提示中硬编码你们团队的 Conventional Commits 格式、scope 列表，保证输出一致。
- **记录 Agent 操作日志**：每次工具调用都写日志，便于回溯误操作。推荐 JSONL 格式，包含时间戳、命令、输出、Agent 决策原因。
- **结合 pre-commit hook**：Agent 生成的提交信息虽然规范，仍然可能包含拼写错误或不合理的 scope。配一个 lint-commit-message 的钩子，可以在提交前挡一道。
- **不要替代 Git 学习**：自动化是为了省去重复性操作，而不是让人不懂 Git。团队新人需要先理解原理，再享受便利。

## 总结

Git 自动化不是新鲜话题，但借助 MCP 和 Agent 框架，我们可以让 AI 主动理解仓库上下文、参与决策，而不是被动接受参数。这种“工具型 Agent”的模式除了 Git，还可以复用到数据库查询、文件管理等场景。关键在于把握安全边界——赋予 AI 足够的信息和受限的行动能力，保留人的最终确认。如此，代码管理才能真正从负担退回到背景中。
