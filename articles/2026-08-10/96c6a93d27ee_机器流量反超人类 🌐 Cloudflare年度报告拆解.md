互联网上最早的一批爬虫，初衷是为了给搜索引擎建立索引。它们有礼貌、守规矩，会认真读你写在 robots.txt 里的规则。可如今，当你打开网站的后台统计，会发现大量请求根本不是来自活生生的人——而是某种自动化程序，有些在帮你被搜索引擎找到，有些则在无休止地抓你的内容、猜你的密码、薅你的库存。十几年过去，这两股力量的消长，终于迈过了一条有象征意义的界线。



## 机器流量过半：Cloudflare 2024 数据说明了什么

Cloudflare 在最新发布的年度互联网趋势报告中，将流量粗暴地分为两大类：**人类流量**和**机器流量**。前者是真正有人在浏览器里点击、滑动、阅读；后者则是所有由自动化程序发起的请求，不管善意恶意。在这份报告里，机器流量占比首次超过了 50%，也就是说，整个网络上非人类产生的请求，已经多于人类自身。

以下几个数字尤其值得拆开看：

- **整体流量结构**：机器流量占比超过 51%，人类流量则首次降至半数以下。这个比例不是针对某类特殊站点，而是 Cloudflare 全球网络上万亿级请求的聚合结果。
- **“好的”机器人和“坏的”机器人**：Cloudflare 将机器流量进一步切分。**良性 bot** 包括搜索引擎爬虫、监测探针、RSS 阅读器、合法 API 调用等，约占整体流量的 17%；**恶意 bot** 包括内容抓取、撞库、刷票、DDoS 脚本等，占比约 34%。
- **电商与SaaS领域最拥挤**：在电商和 SaaS 应用中，机器流量甚至超过 60%，其中恶意 bot 在账号注册、登录、支付接口上表现得异常活跃，这类流量的峰值往往和促销、抢购事件高度重合。
- **增长趋势上，恶意 bot 节奏更快**：过去两年里，良性 bot 的占比相对稳定，而恶意 bot 占比持续走高，2024 年同比增幅超过 30%。

换句话说，不是互联网更“智能”了，而是互联网更“自动化”了——并且相当一部分自动化并不怀好意。



## 机器流量的真实面貌：分类与工作原理

要把“机器流量反超”这件事讲清楚，必须回到一个很基础的问题：这些流量到底从哪儿来，长什么样。在实际运维和安全运营中，一般会把自动化流量分成三大类，每类的目的、行为模式、对服务器的消耗都截然不同。

**第一类：基础设施型良性 bot**

这类流量的典型代表是 Googlebot、Bingbot、Applebot，也包括各类监控工具如 UptimeRobot、Pingdom，以及合规的 API 集成调用。它们在请求头中通常会主动声明身份（User-Agent），尊重 robots.txt，并且不会模拟鼠标移动、点击这类行为。

- 搜索引擎爬虫：现代搜索引擎的爬虫远比想象中复杂，会执行一定的 JavaScript 渲染，甚至会根据站点稳定性自动调整抓取频率。
- 站点监测：每隔几十秒发一次 HTTP HEAD 请求，检查状态码和响应时间，流量虽小但极其规律。
- 第三方 API 集成：如 GitHub Actions 触发 webhook、支付回调、邮件服务收发的自动链接检查等。

**第二类：商业化的灰色爬虫**

这一类很让人头疼，因为它们往往拥有合法公司的背书，比如某些数据分析平台、情报搜集服务、AI 训练数据采集，其爬取行为可能游走在法律和道德边缘。它们会使用真实浏览器的完整渲染环境，伪装用户代理，轮换 IP 池，甚至购买住宅代理来混入“普通人家宽带”流量的外观。

- AI 训练数据采集：为了构建大规模语料库、图像库，大量无差别的抓取行为并不考虑数据归属。
- 动态定价监测：机票、酒店、电商价格抓取，高频请求会直接推高业务方的基础设施成本。
- 社交媒体监听：通过模拟真实用户登录、翻页，获取 UGC 内容数据。

**第三类：完全恶意的攻击型 bot**

这一类就是安全团队长期对抗的对手，不以“看到内容”为目的，而以“破坏业务”为目标。常见形态包括：

- 撞库与凭证填充：利用已泄露的用户名密码组合，批量尝试登录。由于成功率通常很低，所以需要海量请求。
- 库存囤积与自动结账：在抢购模式下，一个恶意脚本完成选货、填地址、提交支付的全流程，比人工快数百毫秒。
- 应用层 DDoS 脚本：聚合大量肉鸡或云函数，伪造正常 URL 访问，耗死目标服务器连接数或带宽。
- 信用欺诈与虚假注册：机器程序批量注册账号、刷优惠券、刷评价，对平台生态构成慢性毒害。

理解这些分类之后，再去看 Cloudflare 那个“51% 反超”的数据，就能明白：增长的主要驱动力并不是 Googlebot 们变多了，而是灰色爬虫和恶意 bot 的军备竞赛在持续升级。

## 这一信号对业务和开发者的真实影响

机器流量过半绝不只是一个抽象的宏观指标，它对每个跑在公网上的服务都有具体而微的冲击。

- **基础设施成本被噪声摊高**：不管是按带宽计费还是按请求量计费，来自恶意 bot 的无效流量都意味着白花花的银子。一些小型 SaaS 团队发现，一个被盯上的登录接口，一个月能产生上千万次撞库请求，占掉三成以上的云账单。
- **运维与 SRE 团队的误判风险**：机器流量带来的请求峰值，可能被现有监控系统错误地识别为“产品需求增长”，从而触发自动扩容，进一步放大资源浪费。更糟的是，这些噪声会把真正的性能瓶颈、用户行为指标淹没。
- **数据决策被污染**：产品团队看 PV/UV、转化率、用户留存，如果流量中过半是机器，原始日志的可信度会大幅下降。商业智能报表里的“日活上升”也许只是爬虫脚本更新了一个批次。
- **防御策略被迫从“边界”转向“行为”**：传统的 IP 限制、UA 黑名单已近乎失效，因为攻击者使用住宅代理和 Headless 浏览器越来越普遍。现在的检测越来越依赖交互行为分析、鼠标轨迹模拟检测、设备指纹和每次请求的熵值计算。



## 三条冷思考与可落地的应对建议

面对这样一个机器主导的互联网环境，既不需要悲观，也不可能靠一两条规则就高枕无忧。真正有效的思路是从架构层面，把“机器流量是常态”作为默认假设。

**1. 将流量分类前置到入口层，而非事后分析**

不要在日志堆积成山后再去筛选人和机器。在 CDN、反向代理或网关层就接入 bot 管理能力，对请求按风险等级实时标记。Cloudflare 自身提供的 Bot Management 以及开源方案如 Nginx + Lua 配合行为指纹逻辑，都是可参考的路径。核心指标是：能不能在几百微秒内判定一个陌生请求的威胁等级。

**2. 为“好的机器流量”设计一条专属通道**

你永远需要 Google 索引你的页面，也永远需要 Stripe 的回调能正常到达，所以不要一刀切地对所有自动化流量施加重验证。为已知的良性用户代理做白名单匹配、为 API 流量强制走独立子域名并实施严格的 schema 校验，可以把“欢迎的机器人”和“不速之客”有效分流。

**3. 成本核算时，把恶意 bot 当作一类基础资源消耗项**

就像你会预估带宽费用、数据库费用一样，未来做 SaaS 的财务模型时，应当有一个专门的“bot mitigation 成本系数”。这个系数和你的业务被黑产青睐的程度正相关，尤其涉及交易、优惠券、用户积分这些可直接变现的环节。提前计入成本，才不会在体量增长后被撞得措手不及。

机器流量反超人类，不是一个需要恐慌的转折，而是一个宣告：互联网已经从“默认信任”的早期阶段，彻底进入“默认质疑”的架构阶段。对于开发者、架构师和安全工程师来说，接下来工作的默认语境，不再是“人怎么用服务”，而是“如何在机器占多数的网络里，依然可靠且经济地服务好那不到一半的人类”。
