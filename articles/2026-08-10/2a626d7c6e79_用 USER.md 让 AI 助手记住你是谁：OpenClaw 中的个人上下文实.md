## 背景

在把 Agent 接入日常开发、写作或自动化流程的过程中，有一个问题反复出现：**助手不知道“我”是谁**。每个会话都需要重新解释项目结构、工具偏好、命名习惯，甚至要手动声明“我是后端，我不用 TypeScript”。这不仅是时间浪费，更会让 Agent 在上下文不足时做出偏离预期的决策。

OpenClaw 及其兼容的 Agent 生态（例如支持 MCP 协议的本地智能体）普遍认同一个设计原则：**通过文件系统传递长期上下文**。其中 `AGENTS.md`/`PROJECT.md` 负责描述项目级的规则，而 `USER.md` 用来存放个人维度的元信息。本文记录我在 OpenClaw 中落地 `USER.md` 的过程、坑点和可复用的经验。

## 问题：为什么需要显式的个人配置？

我第一次尝试让 OpenClaw 的代码 Agent 帮忙重构一个 Python 脚本时，它给出了一个非常“标准”的方案——用 `black` 格式化、添加完整类型注解、引入 `poetry` 管理依赖。但实际上我习惯用 `ruff`，讨厌 `poetry` 的非标准 `pyproject.toml` 写法，并且更倾向保留一些动态类型的灵活性。这些偏好没有任何一个 AI 能凭空猜到。

同样的问题出现在写文档时：我喜欢中文加英文术语混排，但拒绝英文引号，Agent 却总是输出全半角混乱的内容。每次纠正都很消耗 token，而这些问题本可以一次性解决。

也就是说，**Agent 缺少“用户模型”**。OpenClaw 支持在系统提示词中注入额外文件，我们可以利用这点，将个人上下文集中到一个 `USER.md` 中，让它作为每次对话的隐形背景。

## 做法：创建并挂载 USER.md

### 1. 确认 OpenClaw 的上下文加载机制

OpenClaw 默认会读取工作目录下的 `AGENTS.md`（或 `OPENCLAW.md`），并注入到系统消息中。对于用户级别的配置，文档推荐放在 `~/.openclaw/USER.md`，或者通过 `openclaw.yaml` 的 `context` 字段显式指定路径。我更倾向于放在 home 目录，这样对所有项目生效。

### 2. 编写 USER.md

内容不需要面面俱到，但必须**结构化**并**对 token 友好**。我的做法是分为以下几个区块：

- **身份与工作域**：角色、常用语言、主要工作内容。
- **工具偏好**：包管理器、格式化工具、linter、测试框架等。
- **代码风格速查**：缩进、引号、命名规则等。
- **写作偏好**：语言、术语大小写、列表风格。
- **硬约束**：绝对不要做的事，例如“不要主动引入新的依赖”。

一个极简示例（我已经脱敏）：

```markdown
# USER.md

## Identity
- Role: Backend/SRE engineer, Python & Rust.
- Daily tasks: writing API services, infrastructure automation, CLIs.

## Tools
- Package manager: pip-tools (requirements.in), cargo for Rust.
- Formatter: ruff format, line-length 100.
- Linter: ruff, clippy.
- Test: pytest, with --strict-markers.

## Code Style
- Indent: 4 spaces.
- Quotes: double quotes for strings that may contain single quotes.
- Naming: snake_case for Python, PascalCase for Rust types.
- Always use pathlib, avoid os.path.

## Writing
- Language: Simplified Chinese mixed with English terms.
- Punctuation: Chinese punctuation marks, no English quotes in Chinese context.
- Lists: use bullet points, no numbering unless order matters.

## Hard Constraints
- NEVER add new dependencies without asking.
- NEVER change project structure.
- NEVER generate poetry-based pyproject.toml.
```

### 3. 在 OpenClaw 中启用

如果不做任何额外配置，OpenClaw 不会自动读取 home 目录的 `USER.md`。我使用 `openclaw.yaml` 的 `context` 字段来显式引用：

```yaml
# ~/.openclaw/openclaw.yaml
context:
  files:
    - ~/.openclaw/USER.md
```

保存后，重新启动 OpenClaw（或重新加载配置），系统提示词会自动拼接该文件的内容。可以通过 `openclaw debug context`（如果可用）或简单对话来验证：问“你知道我用什么格式化工具吗？”它应该回答 `ruff format`。

### 4. 与项目级 AGENTS.md 分层

项目级配置放在工作目录的 `AGENTS.md`，描述项目特定的架构、目录结构、业务规则等。用户级偏好放在 `USER.md`。两者的交集——例如项目也遵循某些全局偏好——可以不在项目级重复，让 Agent 同时从两个源读取。我在实践中会确保 `AGENTS.md` 以项目规则为重，必要时覆盖 `USER.md` 中的习惯，比如某个项目强制用 `black`，我会在项目文件中写明，并加上“本项目忽略个人 formatter 偏好”。

## 踩坑点

### 内容膨胀导致 token 浪费

最初我把 USER.md 写成了简历加备忘录，包含工作经历、教育背景、常用书签……一次对话被悄悄吃了近 800 token。Agent 虽然对答如流，但在复杂任务中因为上下文窗口被挤占而出现截断。教训：**只放影响决策的偏好，绝不要放闲聊信息**。建议定期用 token 计算工具统计，控制在 300 token 以内。

### 编码和特殊字符

我习惯在 Markdown 中使用 emoji，但 OpenClaw 的模型有时会将 emoji 解释为奇怪的符号。后来把所有 emoji 去掉，改用纯文本标签。另外，`USER.md` 文件必须保持 UTF-8 无 BOM 编码，否则会在某些平台的注入环节出现乱码，导致 Agent 理解错误。这个问题在 Windows 的 WSL 和纯 Windows 环境间复制文件时尤其容易发生。

### 更新后未重新加载

修改 USER.md 后，OpenClaw 不会自动热加载，需要重启。如果对话服务长时间运行，你可能以为偏好已经改了，实际上旧内容还在。我的经验是：**改完立刻重启，并做一次回归提问**。

### 隐私泄漏风险

USER.md 的内容会被送入云端或本地模型，如果使用了第三方 API，所有偏好相当于明文发送。因此不要在里面写任何密钥、内部域名、客户信息。给一个人名或通用工具名称没有问题，但具体的项目路径、内部库名要谨慎。对于极其敏感的信息，还是手动在会话中临时提供。

## 可复用建议

- **分层管理**：`USER.md`（我） + `AGENTS.md`（项目） + 会话内临时指令。让每层各司其职。
- **版本控制**：把 `USER.md` 纳入 dotfiles 管理。换了机器立即恢复上下文。
- **可测试性**：准备几个固定的提问用例，每次修改后验证 Agent 的回答是否符合预期。例如：“请按照我的代码风格初始化一个 Python 脚本骨架。”
- **显式约束优先**：偏好描述用“使用 A，不要用 B”的形式，比“我喜欢 A”更不容易被模型忽略。
- **定期瘦身**：每个月检查一次，把不再使用的工具或习惯移除。Agent 不需要了解你的历史，它只需要现在有效的信息。

## 总结

`USER.md` 是一个低成本的个人化手段，让 OpenClaw 这类 Agent 框架能够更快地进入工作状态。它的本质是把“我”这个最难传递的上下文，变成可维护、可注入的静态文件。在实践里，我感受到的收益不是巨大的效率飞跃，而是一种**摩擦感的消失**——不用再重复那些“你知道我不用 poetry 吧”之类的废话。

做这件事不需要复杂的插件或 MCP 服务，核心就是编辑一个 Markdown、改一行配置，然后维护它。如果你已经在用 OpenClaw 或类似的 Agent 系统，建议花 30 分钟创建自己的 USER.md，你会发现很多无用的来回纠正就此消失。
