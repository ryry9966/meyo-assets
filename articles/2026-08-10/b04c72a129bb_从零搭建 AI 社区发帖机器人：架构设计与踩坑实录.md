## 背景

在 OpenClaw 社区的建设过程中，我们发现高质量的技术内容严重依赖作者手动整理与发布，更新节奏难以持续。自动化工具虽然不少，但大多是为通用社交平台设计的，缺少对程序员社区语境（Markdown 格式、技术标签、代码块处理、社区 API 稳定性）的适配。于是决定自己动手，搭一个能按规则生成帖子、自主发布并监控反馈的发帖机器人。

需求很明确：
- 能从技术文章库中提取或生成符合社区调性的帖子；
- 支持 Markdown 与代码块格式，处理好转义与渲染；
- 有合理的发布频率控制，防止刷屏；
- 接入社区 API，处理鉴权、限流与异常重试；
- 发布后可记录状态，便于回溯和统计。

## 架构设计

整体采用轻量 pipeline 架构，以松耦合的方式组织组件：

```
[内容源] → [生成/选择] → [格式化与校验] → [发布调度] → [社区 API] → [状态存储]
```

**内容源**：本地 Markdown 文件库 + 手工维护的选题表。优先使用人工审核过的内容，避免 LLM 幻觉。待生成阶段，允许基于选定主题让 Agent 草拟，但所有草稿均需走人工审核流程，机器人不直接发布未审核内容。

**生成/选择**：基于 OpenAI 兼容 API 调用本地大模型，用固定 System Prompt 要求输出符合社区规范的帖子，包括标题、正文、标签、摘要。用 `temperature=0.3` 控制稳定性，并让模型输出 JSON 结构化数据以便后续解析。

**格式化与校验**：将生成的 JSON 转为 Markdown，并对代码块进行语法高亮标记处理。校验层包含：
- 字数检查（正文不超过 3000 字）；
- 标签是否存在（与社区现有标签集比对）；
- Markdown 语法正确性（用 remark 库解析，失败则返回重试）；
- 检测是否包含未闭合的代码块或非法字符。

**发布调度**：用 Node.js 的 `node-cron` 实现定时触发，目前设为每 3 天下午 2 点执行。为避免高并发导致限流，每次只发布一篇。若当天已有任务执行中，则跳过。

**社区 API 适配**：OpenClaw 社区基于 Discourse，有较完善的 REST API。我们封装了以下操作：
- 登录获取 cookie 与 CSRF token；
- 创建帖子（POST /posts.json）；
- 查询帖子状态（GET /t/{id}.json）；
- 错误处理与重试（指数退避，最多 3 次）。

认证信息通过环境变量注入，不在代码中硬编码。

**状态存储**：用 SQLite 本地数据库记录已发布帖子的 ID、主题、发布时间、API 返回状态，以及草稿是否已审核。便于回查，避免重复发布。

## 踩坑实录

### 1. Discourse API 的 CSRF 陷阱
首次尝试直接发送 POST 请求创建帖子，总是返回 403。查文档发现需要先 GET `/session/csrf.json` 获取 token，然后再带上 `X-CSRF-Token` 头。更坑的是 cookie 必须保存并在后续请求中携带，否则 token 会失效。我们用 `axios` 实例启用了 `withCredentials` 和 cookie jar 手动管理，才最终稳定。

### 2. Markdown 转义地狱
生成的帖子中如果包含 Discourse 的特殊语法（如 `[poll]`）或者重复的 HTML 实体，会导致渲染异常。我们的做法是在生成 Prompt 中明确禁止使用扩展语法，并在格式化阶段做一次 `pre-render` 检查，用 `markdown-it` 渲染后提取纯文本，检测是否丢失内容。另外，代码块中的反引号数量需要严格匹配，否则直接破坏页面布局，这一块我们写了专门的验证函数。

### 3. 频率控制与限流
即便按 3 天一次设计，中间调试阶段也曾因连续调测触发 Discourse 的 rate limiting，导致 IP 被临时屏蔽。最终在代码中加入重试装饰器，遇到 429 时等待 `Retry-After` 时间再尝试。同时在测试环境增加开关，可以调整 cron 表达式为手动触发模式，避免误操作。

### 4. Agent 生成内容的质量偏差
早期尝试全自动生成，发现模型容易写出“小红书体”或过度总结的风格，不适合技术社区。后来改为“脚本生成 → 人工修改 → 审核入库”的半自动化流程。机器人只发布已通过人工审核的帖子草稿，GenAI 负责辅助提炼摘要和 Tag，质量显著提升。

## 可复用建议

1. **从最小可行自动化做起**：不要一上来就追求全自动，先做一个“本地生成 → 手动粘贴”的工具链，逐步把发布环节接入 API。
2. **为社区 API 写独立的适配层**：即便 Discourse 看似标准，不同论坛版本细节差异很大，独立封装便于替换和维护。
3. **设计清晰的内容审核机制**：尤其是面向开放社区的 AI 生成内容，必须有一条人工确认的环节。我们使用 SQLite 中的 `reviewed` 字段做闸门，简单可靠。
4. **监控与日志**：将每次发布的结果记录到文件，包括请求参数、响应码、错误信息，便于排障。接入简单的健康检查（如 Uptime Kuma）监控机器人存活状态。
5. **环境隔离**：开发和测试使用单独的测试社区或 Docker 搭建的 Discourse 实例，避免污染生产环境。

## 总结

这个机器人的核心不是技术复杂度，而是如何在工程约束下平稳运行：处理好 API 的怪异行为、确保内容格式一致、设置有效的人工护栏。目前它已稳定运行近两个月，累计发布 15 篇高质量技术帖，未出现一次格式故障或误发。后续计划加入帖子互动数据的抓取，用于反馈内容选题优化。

对于想尝试类似实践的 OpenClaw 社区用户，希望这份实录能帮你在踩坑之前，先省下几分力气。

*如果你也在搭建类似的自动化流程，欢迎到社区交流 API 适配、Agent Prompt 设计或调度策略的细节。*
