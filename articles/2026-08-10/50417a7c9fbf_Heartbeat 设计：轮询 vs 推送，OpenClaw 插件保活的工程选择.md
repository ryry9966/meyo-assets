在基于 OpenClaw 的 Agent 或插件体系中，我们常常需要让一个长期运行的组件（例如后台任务执行器、MCP 服务器或自定义插件进程）对外暴露健康状态，并在异常时尽早触发自动恢复。**Heartbeat（心跳）** 是最基础的保活与检测手段。围绕“轮询”与“推送”两种风格的选型，并不只是技术好奇心，它会直接影响系统的延迟敏感性、资源开销和运维心智。

## 背景
在一个典型的 OpenClaw 部署里，可能有多个 Agent 插件以独立进程或容器形式运行。Manager 负责调度与监控，它需要知道每个 Agent 是否存活、能否正常处理请求。如果 Agent 进程僵死但未退出，或者网络发生分区，没有合理的心跳机制，故障发现可能会延迟数分钟，导致任务积压或自动化链路中断。

常用的两种心跳模式：
- **轮询 (Polling)**：Manager 定期向 Agent 发起健康检查请求（如 HTTP `GET /health`），根据响应判断存活。
- **推送 (Push)**：Agent 主动通过长连接（WebSocket、TCP 或 SSE）定期向 Manager 发送心跳帧，Manager 根据收包间隔判断丢失。

两种模式看似都能完成“我还活着”的信号传递，但在工程落地时会面临不同的取舍。

## 问题
当你开始设计心跳时，至少要回答三个问题：
1. **故障发现的最大延迟能接受多少？**
2. **系统规模有多大？连接数、节点数会导致带宽或 CPU 成为瓶颈吗？**
3. **网络环境是否可控？** 是否存在 NAT、代理、负载均衡器会掐断空闲连接？

轮询的优势在于实现极其简单，基于无状态的 HTTP，天然兼容各种中间件；代价是“检查间隔”就是故障发现的最小时延，而且当 Agent 数量膨胀后，Manager 的请求压力线性增长。推送则可以在秒级甚至亚秒级发现故障，并且节省不必要的请求，但要求维持长连接，需要处理断线、重连风暴、背压等问题。

## 做法/步骤
以 OpenClaw 插件体系为例，我们给 Agent 添加心跳接口，并让 Manager 支持两种后端。

**1. 定义统一的心跳抽象**
```python
class HeartbeatService(ABC):
    @abstractmethod
    async def start(self): ...
    @abstractmethod
    async def stop(self): ...
    @abstractmethod
    def last_seen(self) -> float: ...
```
Agent 侧实现 `AgentHeartbeat`，Manager 侧实现 `HeartbeatMonitor`。

**2. 轮询实现**
Agent 暴露 `/healthz` 端点，返回当前时间戳和自身状态。Manager 侧每 T 秒发起 GET 请求，若连续 N 次超时或状态异常，则将 Agent 标记为不可达并触发告警/重建。代码仅需标准 HTTP 客户端，几乎无状态。

**3. 推送实现**
Agent 在启动时建立到 Manager 的 WebSocket 连接，每 heartbeat_interval 秒发送一条 `{"type":"ping","ts":...}`。Manager 启动一个超时定时器，每次收到 ping 重置定时器。若超时未收到，则累计丢失次数，达到阈值后判定失联。
WebSocket 断开时，Agent 采用指数退避重连，并尽快重新注册。

**4. 集成到插件生命周期**
在 OpenClaw 插件的 `on_start` 中调用 `heartbeat.start()`，在 `on_stop` 中调用 `heartbeat.stop()` 优雅关闭连接。Manager 侧监听节点事件，结合心跳状态做统一调度。

## 踩坑点
- **空闲连接被中间设备掐断**：常见于云负载均衡器或 NAT 网关。即使使用 WebSocket，如果心跳间隔大于中间件的空闲超时（如 60 秒），连接会被静默断开。**必须让应用层心跳间隔显著小于该阈值**，比如 15~30 秒。
- **轮询间隔的“时间陷阱”**：如果 Manager 串行轮询所有节点，当节点数量大时，每个节点的有效检査周期会被拉长，容易误判超时。应使用异步并发检测，并为每个 Agent 单独维护时间线。
- **推送重连风暴**：Manager 短暂重启，所有 Agent 同时检测到断线并瞬间重连，可能造成 SYN flood。一定要在 Agent 侧加入随机抖动（jitter），并使用逐步增大间隔的重试策略。
- **时钟偏移**：不要用 Agent 本地时间直接参与超时计算。最好由 Manager 生成时间戳并比较收发间隔，或者用单调时钟。
- **误判与抖动**：网络瞬间丢包不应立即判定死亡。设置失联阈值（如连续丢失 3 个心跳）能显著提高容错性。

## 可复用建议
1. **小而美的默认选择**：如果节点数在二三十以内且对故障延迟不敏感（分钟级可接受），**轮询**是实现最简单、最不容易出错的方案。直接用 HTTP + 间隔 30~60 秒，配合连续失败计数。
2. **需要实时性或大规模场景，选推送**：WebSocket + 应用层心跳 + 退避重连。注意选型时考虑边缘代理的超时配置。
3. **混合方案降低成本**：Agent 主动推送心跳，Manager 仅在长时间未收到信号时才回退到 HTTP 主动探活，作为双重验证，能减少“假死”误报。
4. **心跳数据附加负载**：在 ping 帧中顺路携带队列深度、内存占用等轻量指标，将心跳扩展为可观测性管道，一次传输两个价值。
5. **统一抽象**：在 OpenClaw 生态里，建议将 `IHeartbeat` 抽象为插件标准接口，不论插件内部用哪种方式，Manager 都能透明监控。

## 总结
轮询与推送并不是非黑即白的对立，更多是一种“延迟换简单”还是“实时换复杂”的工程权衡。在 OpenClaw 的插件化实践中，初期用轮询快速验证，同时预留推送接口；当系统规模上去后，再按需切换到长连接推送心跳，可能是最务实的演进路径。

无论选择哪种，务必把心跳的超时阈值、重试策略和异常处理放在配置文件里，并接入监控。因为一个看似不起眼的心跳参数，往往是深夜故障时最先暴露的短板。
