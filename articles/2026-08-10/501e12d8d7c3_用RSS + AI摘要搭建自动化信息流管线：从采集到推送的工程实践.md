## 背景

信息源越来越多，但真正值得精读的内容占比很低。RSS 能帮我们把分散的信源重新聚合，但即便聚合后，每天数百条未读仍然会让人产生焦虑。于是很自然地想到：能不能让 AI 先帮我读一遍，只把真正相关、有价值的内容提炼出来，推送到我面前？

在 OpenClaw 社区，很多朋友已经在用 Agent + MCP 处理自动化任务。这篇文章分享一个实际跑通的管线：从 RSS 采集、AI 摘要到多渠道推送，整套流程用不到 300 行代码完成，部署在单台轻量服务器上，稳定运行了两个月。

## 问题拆解

如果只做“调用 OpenAI 生成摘要”，其实很容易。但一旦变成需要长期运行的管线，就会遇到真实问题：

1. **RSS 源质量参差不齐**：有的只输出标题和摘要，有的全文输出但夹杂大量广告或无关段落。
2. **重复内容**：同一事件被多个源报道，摘要如果高度相似就是浪费。
3. **AI 调用成本与稳定性**：摘要太长 token 消耗陡增，API 限流、网络超时需要重试策略。
4. **文章内容提取**：很多 RSS 只有截断内容，需要抓取原文清洗后再送入 AI。
5. **推送渠道**：不同场景（即时消息、稍后阅读、归档）需要不同分发策略。

下面就是一个能处理这些问题的具体方案。

## 选型与架构

整体管线分成三层：采集层、摘要与去重层、分发层。

- **RSS 后端**：Miniflux（自带全文抓取、去重、过滤规则，API 友好）
- **AI 摘要**：OpenAI GPT-4o-mini（成本低、响应快，摘要场景足够）
- **推送**：Telegram Bot（即时通知）+ 自动更新到 Markdown 知识库（供本地搜索）
- **调度**：Systemd timer 每小时触发一次摘要脚本
- **Agent 层（可选）**：用 OpenClaw Agent 调度整个流程，方便人工干预（比如“重新摘要今天的所有未读”）。

为什么不用无头浏览器爬全文？Miniflux 的“Fetch original content”已经能覆盖 80% 的站点，特殊站点用自定义抓取规则补齐，避免引入 Puppeteer 的维护成本。

## 实现步骤

### 1. 配置 Miniflux

docker-compose 起一个 Miniflux 实例，导入 OPML，打开“Fetch original content”和“Rewrite Rules”。设置规则过滤已知的低质源，或只保留特定分类的未读条目。

API 访问用 token，后续脚本直接调 `/v1/entries?status=unread&limit=20&order=published_at` 拿到最近未读。

### 2. 构建摘要脚本

脚本核心逻辑：

1. 从 Miniflux API 拿未读条目，每条取出 `title`, `content`（或 `original_content`）, `url`, `feed_title`。
2. 内容清洗：移除 HTML 标签，保留文本，用 `unidecode` 规范化，限制长度在 1500 词以内（超长尾部截断，避免丢失主旨）。
3. 判断是否需要摘要：标题长度 + 内容长度过短的直接跳过，标记为“无需摘要”。
4. 构建 prompt，要求输出 JSON 格式：`{“summary_zh”: “...”, “topics”: [...], “relevance”: low/medium/high}`。relevance 用于后续过滤，只推送 medium/high。
5. 调用 OpenAI API，带重试（tenacity 库），超时 15 秒，失败后标记错误，下次再重试。
6. 摘要结果写回 Miniflux 条目的“备注”字段（用作记录），同时更新为已读（避免重复处理）。

### 3. 去重逻辑

比较关键：根据 URL 的域名路径去重，以及标题的相似度（用 difflib）。同一小时内，如果两条标题相似度 > 0.8 且来自不同源，只保留一条进行摘要，另一条标记为“重复”。这避免了多源报道同一条新闻时的冗余调用。

### 4. 推送模块

- Telegram：用 `python-telegram-bot` 发送格式化消息，含摘要、文章来源、链接。根据不同 relevance，设置不同通知级别（high 弹出提醒，medium 静默）。
- Markdown 归档：每天生成一个 `daily-digest.md`，按 topic 分组，存入 Obsidian 知识库，自动同步。

### 5. 定时与监控

Systemd timer 每小时触发脚本，脚本内用 flock 文件锁避免并发。脚本末尾上报执行状态（成功/失败、处理条数、API 花费）到自建的 Uptime Kuma push 端点，异常时 Telegram 告警。

如果使用 OpenClaw Agent，可以把这几个步骤封装成 MCP 工具，让 Agent 自主决定何时重新处理、调整过滤阈值，甚至直接对话查询今天摘要。

## 踩坑复盘

**坑1：原文抓取失败**  
Miniflux 的全文抓取依赖 CSS 选择器或 Readability 算法，部分 SPA 站点无法提取。我的解法是维护一个 `fallback_fetch.py`，对特定域名直接用 `requests` + `BeautifulSoup` 定点抓取，然后注入到条目的 `content` 字段。

**坑2：摘要质量飘忽**  
最初 prompt 要求“一句话总结”，结果经常丢失关键主体。后来改成强制输出“一句话事件描述 + 一个关键背景”，并给出 good/bad examples，稳定性大升。另外，如果内容过短但标题很标题党，AI 摘要反而画蛇添足，于是加了最小内容长度阈值（< 200 字符直接跳过）。

**坑3：API 费用超预期**  
GPT-4o-mini 虽然便宜，但如果不对内容截断，一篇长文消耗 3000+ token，高频源一天能花掉 0.5 美元。强力截断（1500 词上限）后，日均费用降到了 0.1 美元以内，且摘要质量几乎没降——因为文章核心信息大多在前半段。

**坑4：重复处理已读条目**  
由于写回“已读”是 API 调用，如果脚本中途崩溃，可能部分条目被摘要但未标记已读，下次又重复调用。解决方式是引入“处理状态流水账”：每条条目经过处理后，在本地 SQLite 记录 `entry_id` 和 `processed_at`，下次跳过已有记录。幂等性很重要。

## 可复用建议

- **配置外部化**：API key、阈值、推送目标都用环境变量或 YAML 配置文件，不要写死在代码里。
- **脚本模块化**：拉取、清洗、摘要、推送各自独立为函数，方便替换单个环节（比如想把推送从 Telegram 切到钉钉机器人）。
- **容器化**：用 Docker 打包脚本和依赖，跟 Miniflux 放在同一个 compose 文件里，通过 internal network 通信，部署和迁移都很省心。
- **日志与回溯**：所有 AI 响应都落盘存日志，出现问题能回溯是哪条 prompt 没写好，而不是对着账单干瞪眼。
- **从简单开始**：先不要上 Agent/MCP，用最朴素的 cron 把流程跑通，确认稳定后，再把部分决策交给 Agent（比如“这周技术类摘要质量下降，帮我调整 prompt”）。

## 总结

这是一套典型的“缩小关注圈”工具：把 RSS 的全面监控能力，与 AI 的提炼能力结合，用很低的成本把信息流压缩到每天只需要扫几眼。工程上的关键不在 AI，而在于对异常情况的处理：抓取失败、重复内容、API 波动、状态持久化。把这些补丁打好后，管线可以做到数月无人值守。

如果你也在用 OpenClaw 做个人自动化，这套管线很适合作为一个稳定的“信息获取器”MCP 服务接入，后续再叠加自动归档、知识图谱甚至自动生成周报，都是水到渠成的事。
