## 背景：为什么你需要一条 AI 摘要管线

关注的技术源从十几个涨到几十个之后，每天扫一眼标题已经无法判断信息质量。更麻烦的是，不同源的更新频率差异巨大：有的日更几十条，有的沉寂两周突然丢一篇精品。我把这个叫做“信息收割悖论”——订阅越多，漏掉真正重要的内容的概率反而越大。

常见的解法是用 RSS 阅读器加手动筛选，但根本问题还是“人肉判断”的成本太高。2024 年底我开始尝试把 RSS 抓取、AI 摘要、去重推送串成一条管线，让它默默在服务器上跑，只在手机通知栏给我一条 100 字以内的中文摘要。这条管线已经稳定运行了将近四个月，日均处理 200+ 条条目，累计帮我省下每天至少 40 分钟的扫源时间。

这篇文章想分享的是工程视角下的管线设计，不追求酷炫 demo，重点放在“怎么让它在真实环境里不崩、不重复、不烧钱”。

## 问题拆解

一个看似简单的“抓 RSS → 叫 AI 总结 → 推给我”的流程，实际跑起来会遇到这些坑：

1. **去重与增量**：feed 的 `<guid>` 并非总是可靠，有些站干脆没有；重复拉取导致 API 浪费。
2. **大正文处理**：部分 RSS 条目直接塞进几 KB 的 HTML，不加截断直接喂给 LLM 会炸 token 或超出上下文长度。
3. **API 异常与重试**：OpenAI 兼容接口的间歇性 429/503，再加上免费模型的速率限制，不做重试逻辑会丢条目。
4. **推送风暴**：一旦哪个源批量更新历史文章，或者你刚初始化管线，几十条摘要短时间内涌入通知，反而变成干扰。
5. **状态跟踪**：想知道管线是不是死了、某条为什么没推送成功，没有持久化记录就只能靠猜。

## 做法：一条工程化的管线架构

我最终选了一个相对保守但高度可控的方案：Python 主控 + SQLite 本地状态 + 自部署 LLM 接口（兼用付费 API 做 fallback），用 systemd timer 做调度，推送走 Telegram Bot。

### 1. 抓取与增量去重

使用 `feedparser` 做核心解析，每次抓取后提取 `(feed_url, entry_id, link)` 三元组。`entry_id` 优先取 `<id>` 或 `<guid>`，不存在时回退到 `link` 做 SHA256。所有处理过的条目 ID 写入 SQLite 表：

```sql
CREATE TABLE IF NOT EXISTS processed (
    id TEXT PRIMARY KEY,
    feed_url TEXT,
    published TEXT,
    fetched_at TEXT
);
```

每次拉取新条目时 `WHERE id NOT IN (SELECT id FROM processed)`，然后批量 `INSERT OR IGNORE`。这解决了绝大部分重复问题。

部分源（尤其是博客园、少数独立博客）的 `<link>` 会带上各种 UTM 参数，导致同一个真实文章生成不同 ID。所以在入库前用正则去掉常见跟踪参数，例如 `utm_source`, `utm_medium`, `utm_campaign`。

### 2. 构建摘要 prompt 与上下文裁剪

我需要的摘要非常具体：中文，100 字左右，必须包含“核心观点/技术点”，如果文章是教程，给出一句话的适用场景。为了减少幻觉，我强制要求“不要总结你猜的内容，缺失就写‘未提及’”。

上下文裁剪策略：
- 优先取 `<content:encoded>` 或 `summary`，如果没有正文就到源页面抓取（`requests` + `BeautifulSoup` 提取 `<article>` 或主内容区），但给抓取设 5 秒超时，避免饿死管线。
- 正文超过 2000 个 token 的，用 `tiktoken` 计算后截断到 1800 token 以内，保留开头和前三分之一，再加最后 300 个字符，因为很多技术文章结尾有结论。

### 3. API 调用与重试

LLM 调用的关键不是一次性成功，而是优雅失败。我用了一个简单的带指数退避的重试逻辑：

```python
for attempt in range(MAX_RETRIES):
    try:
        response = client.chat.completions.create(...)
        break
    except Exception as e:
        if attempt < MAX_RETRIES - 1:
            time.sleep(2 ** attempt)
        else:
            # 记录失败并回退摘要为标题前80字
            summary = item.title[:80] + "..."
```

同时维护一个 `api_fail_count` 计数器，当连续失败超过阈值时主动停止本轮抓取，并向我的 Telegram 发送告警。这阻止了某次 API 集体宕机烧光重试预算的问题。

### 4. 推送与反风暴

每生成一条摘要，先不直接推送，而是追加到一个内存列表。本轮所有源处理完毕后，按 publish 时间倒序排列，只推送最新 10 条（这个数字可以调节）。多余的历史条目只入库不推送，避免初始化时被数百条历史淹掉。

推送消息格式也比较克制：

```
【📰 技术摘要】
《使用 eBPF 调试 Go 程序的内核路径》
摘要：文章介绍了通过 eBPF uprobe 钩子捕获 Go 函数参数的方法，适合定位性能问题。详细步骤涵盖 BCC 工具编写与符号表解析。
来源：example.com
```

用 Telegram 的 `parse_mode=HTML` 做简单标记，关闭 web page preview。

### 5. 调度与健康检查

systemd timer 每 30 分钟触发一次（对一般博客源足够了）。另外有一个独立的 cron 任务，每天凌晨检查 SQLite 中最近 24 小时的新增条目数。如果为 0，可能全部源失效或脚本卡死，同样发告警。

## 我踩过的坑

- **RSS 格式的千奇百怪**：有的源把正文放在 `description`，反而 `content:encoded` 是空的；有的时区混乱，`published_parsed` 为 None 导致处理逻辑崩溃。建议统一用 `dateutil.parser` 做解析，并设默认值 `datetime.now(timezone.utc)`。
- **LLM 输出不总是 JSON**：即使你 prompt 里要求“只返回纯文本摘要，不要额外解释”，有些模型还是会在开头加“好的，这是摘要：”。加 `stop=["\n\n"]` 或做后处理“去掉开头引导语”能解决九成问题。
- **内存泄漏风险**：如果你像我一样在一个进程里循环处理几十个源，注意关闭 `requests` 的 response 和 beautifulsoup 的临时对象。用 `with` 和 `finally` 确保释放。
- **隐私担忧**：有敏感源？可以针对某些 feed 配置独立的 API key，或者路由到本地 Llama 接口，避免数据外传。

## 可复用建议

如果你不想从头造轮子，可以利用 OpenClaw/MCP 的现有工具拼装管线：

- 用 `rss-reader` MCP server 统一抓取，暴露标准化条目接口。
- 将去重逻辑写成一个小型 Agent，每次读取本地 JSON 文件判断是否已处理，并更新状态。
- 使用 OpenClaw 的工作流节点串联“抓取 → 过滤 → 摘要 → 推送”，每个步骤独立、可观测。
- 在推送节点前引入一个“摘要质量检查”步骤：词数过少、包含“无法总结”等字样则自动丢弃或降级为标题通知。

此外，强烈建议将这组工具打包进一个可复用的 `docker-compose` 环境，方便换服务器时一键拉起。我的运行成本：一台 1C1G VPS 跑 Python 脚本 + 本地 llama.cpp 做免费摘要，每月仅电费成本（if 托管）几乎为零；用 GPT-3.5 时日均 token 消耗在 40k 左右，月花费约 $2。

## 总结

RSS + AI 摘要管线不是新鲜事，但让它像一个可靠的微服务那样持续运行，需要处理的细节远比 demo 多。关键设计决策包括：健壮的去重 ID 生成、Prompt 的严谨约束、带退避的 API 调用、防推送风暴策略，以及可观测性（日志与告警）。

一旦稳定下来，你会发现它变成了一个“信息雷达”——不再主动刷源，而是等管线做好预处理，把真正值得读的内容推到你面前。希望这篇工程记录能帮你少踩一些坑，快速搭出一个属于自己的、低调但很能打的自动化信息流。
