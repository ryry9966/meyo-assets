如果说大模型圈也有“德比大战”，那 OpenAI 与 Anthropic 的恩怨绝对能排进前三。近日，Codex 与 Claude Code 的两位负责人罕见地在社交平台公开互呛，从基准测试的公平性一路吵到模型安全与产品理念，火药味直接溢出屏幕。一边是背靠微软、占据先发优势的代码生成标杆，另一边是由前 OpenAI 核心员工创立、高举安全大旗的后起之秀。这场隔空对线，表面看是工程师的意气之争，背后却藏着从技术选型到商业路线的深层裂变。



## 一、到底在吵什么？拆解互撕的三大核心战场


公开对喷的起因并不复杂：Claude Code 在一次内部评测中声称在真实开发场景下对复杂任务的理解力优于 Codex，随后 Codex 负责人直接抛出多组公开基准测试数据反击，两边粉丝迅速下场，演变成一场 AI 圈的大型“benchmark 论战”。如果仔细梳理双方被截图的发言，矛盾主要集中在三个层面：

- **基准测试的选择性报告**
  - Codex 一方强调 HumanEval、MBPP 等经典 Python 函数补全任务上，GPT-4 底座带来的单次生成通过率依然大幅领先。
  - Claude Code 则更多地引用 SWE-bench、MultiPL-E 等多文件、跨语言场景数据，突出长上下文理解与安全性过滤上的优势。
  - 问题在于，双方的测试集、温度参数、评估方式没有统一口径，“吊打”一词的出现更多是情绪输出，而非严格意义上的学术对比。

- **“代码安全”的话语权争夺**
  - Anthropic 从成立之初就将“宪法式 AI”作为核心卖点，Claude Code 内置的多层安全校验会显式拒绝生成可能存在 SQL 注入、硬编码密钥等风险的代码片段。
  - Codex 的路线更倾向于给出完整的、功能优先的建议，再交由开发者自行审查，认为过度阉割会损害生产力。
  - 此次互撕中，Claude 方直接批评对手“在安全基准上长期低分”，而 Codex 方则回怼这是“用安全之名行能力不足之实”，将安全与可用性的经典平衡问题推到了台前。

- **商业生态的排他性**
  - 双方负责人对对方与第三方工具的集成方式也颇有微词。Codex 已深度嵌入 GitHub Copilot、Azure 云服务；Claude Code 则与 Amazon Bedrock、Sourcegraph 等平台合作，各自形成了封闭或半封闭的插件体系。
  - 互撕中出现了“锁死用户”与“破坏开放标准”的相互指责，这本质上是对开发者社区流量的争夺，也是云厂商代理人战争的缩影。

从技术争论到人身攻击的升级，只花了一天时间。但普通开发者真正该关心的，并不是谁吵赢了，而是这两个模型在技术基因上到底有哪些根本不同。

## 二、Codex 与 Claude Code：技术路线的根本分歧


在代码生成领域，OpenAI 与 Anthropic 走在两条截然不同的道路上，这也是吵得起来的技术根源。

**1. 底座模型的架构差异**
- Codex 系列从最初的 12B 参数专有模型进化到如今的 GPT-4 统一底座，采用稠密 Transformer 架构，强调一步到位的推理能力，尤其在单次生成短至中等长度代码时延迟极低。
- Claude Code 基于 Claude 3.5/4 系列，在长上下文窗口（200K token）上下了重注，通过旋转位置编码等技术拓展了“视野”，更适合阅读整个代码仓库后生成跨文件的修改，但这也会带来更长的首 token 生成时间。

**2. 训练数据与微调策略**
- Codex 的训练数据大量来自 GitHub 公开仓库，经过严格的法律合规清洗，但依然以英语代码注释为主，对非英语文档的支持相对薄弱。
- Anthropic 在预训练阶段就刻意增加大量安全示例与高质量技术文档，Claude Code 的强化学习微调阶段还引入了“有害代码识别”的奖励模型，使得它在拒绝不安全请求时表现得更为强硬。
- 一个典型例子是：当用户要求“写一个可以绕过登录的脚本”时，Codex 可能会生成一段注释警告但依然给出代码；而 Claude Code 大概率会直接拒绝并解释原因。

**3. 上下文处理与工具调用**
- Claude Code 支持多文件同时加载，并能在提示词中显式指定文件的读写操作，这与 Anthropic 大力推广的“安全工具使用”范式一脉相承。
- Codex 虽然也支持文件上下文，但更多依赖 IDE 插件（如 VS Code）自动切分窗口，模型本身对工具调用的原生支持相对更保守，倾向于通过函数签名推断意图。

这些技术分歧并非一朝一夕形成，而是两家公司从创始之初就完全不同的哲学选择。

## 三、从“师出同门”到“公开对喷”：安全派与加速派的路线战争


Anthropic 的创始人 Dario Amodei 和 Daniela Amodei 都曾是 OpenAI 的核心成员，2020 年因对商业化速度与安全投入的战略分歧而离开。这次 Codex 与 Claude Code 负责人的口水战，本质上就是两种世界观在代码生成领域的投影。

- **加速派逻辑（OpenAI / Codex）**
  1. 只有大规模部署，才能收集足够多的真实世界反馈，从而快速迭代。
  2. 安全应当通过“使用中的自动对齐”来实现，而不是事前设置过多硬约束。
  3. 代码生成工具首先必须“有用”，束缚太多会导致开发者转向其他工具，失去改进安全机制的机会。

- **安全派逻辑（Anthropic / Claude Code）**
  1. 代码是直接运行在基础设施上的指令，单次恶性输出就可能造成不可逆损失，因此“默认安全”必须内置。
  2. 通过宪法式 AI 提前设定价值边界，即便牺牲部分灵活性，也可以守住底线。
  3. 长远看，只有值得信任的工具才能建立开发者忠诚度，绕过安全的短期便利终将被市场惩罚。

这场路线之争也反映在各自的产品策略上：OpenAI 的 GitHub Copilot 已经有超过 100 万付费用户，走的是“先圈地再补安全”的路径；Anthropic 则通过 Amazon 生态稳扎稳打，主打企业级合规与安全审计。双方负责人的激烈对线，更像是在给各自阵营的开发者打气，同时也向投资人传递“我们才是正确方向”的信号。

## 冷思考：三则给开发者的务实建议

口水战看着热闹，但作为真正每天与代码打交道的工程师，被热度带着跑是最不划算的。与其站队，不如保持清醒。

1. **把公开基准当作参考系，而非唯一真理**
   - 所有基准测试都有盲区：HumanEval 偏重算法题，SWE-bench 偏重真实 issue 修复，没有一个能全面覆盖你的日常工作。
   - 建议用自己语言栈、自己项目的真实代码片段做一个私有评测集，定期用最新的模型 API 跑一遍，关注延迟、正确率、代码风格的一致性，这才是属于你的“北极星指标”。

2. **安全与生产力不是二元对立，而是分层把关**
   - 完全可以组合使用多个模型：用 Codex 快速生成初稿，再让 Claude Code 做安全审查和代码解释；或者反过来，用 Claude 生成安全敏感的核心模块，用 Codex 加速胶水代码。
   - 无论哪个模型输出的代码，都必须经过静态分析工具、单元测试、人工 code review，没有一个 AI 能替你承担生产事故的责任。

3. **关注开源替代，减少对单一阵营的依赖**
   - Meta 的 Code Llama、Hugging Face 的 StarCoder、开源社区的 DeepSeek Coder 等都在快速追赶，部分场景下已经可以接近闭源模型的效果。
   - 在一个公司内部，将模型 API 封装成统一接口，允许随时切换后端，是避免被“互撕”波及的技术投资。

AI 代码助手的战争才刚刚开始，两位负责人的互撕或许不是最后一次。对开发者而言，最好的应对方式不是围观情绪，而是在自己的终端里，用真实代码给它们打出属于自己的分数。
